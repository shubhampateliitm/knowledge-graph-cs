@@+ pubsub
history: Publish–subscribe grew out of 1980s research on distributed event notification (for example the Information Bus at Teknekron, later TIBCO, described in a 1993 SOSP paper) and became a standard enterprise pattern through message-oriented middleware: TIBCO Rendezvous, IBM MQ topics and the Java Message Service (1998). Cloud and internet-scale systems later separated it from queues: Kafka (2011) made subscriptions a matter of each reader tracking its own position in a durable log; Google Cloud Pub/Sub, Amazon SNS and Azure Event Grid offered managed fan-out; MQTT (1999, widely used from the 2010s) brought lightweight pub/sub to IoT devices.
practice: Decide early whether subscribers need history. If a new subscriber must be able to read the past, use a log-based system (Kafka, Pulsar) with adequate retention; if only live delivery matters, a broker-based fan-out (SNS, Redis pub/sub, MQTT) is simpler. Name topics after business events ('order-placed'), not after consumers, so new subscribers can join without changing producers. Define schemas and compatibility rules from the start, and plan for duplicates: most pub/sub systems deliver at least once, so every subscriber should be idempotent.

@@+ mqueue
history: Message queues are older than the web: IBM's MQSeries (1993) and Microsoft MSMQ connected enterprise applications reliably, and the AMQP standard (2006, from JPMorgan) led to RabbitMQ (2007). Cloud services followed: Amazon SQS (2004, one of the first AWS services), Azure Service Bus, Google Cloud Tasks. Task-queue libraries (Celery, Sidekiq, Resque) popularized background job processing in web applications. Kafka 4.2's share groups (2026) brought queue semantics to log-based systems.
practice: Use a queue when each message is a unit of work that one worker should do, and order across messages does not matter much. Set a visibility timeout or acknowledgement deadline longer than the slowest normal processing time, and make handlers idempotent, because a crash after doing the work but before acknowledging will cause redelivery. Configure a dead-letter queue with a maximum delivery count so poison messages do not block everything, and alert on its depth. Watch queue age (oldest message), not just length: age tells you how far behind you are in time.

@@+ batchproc
history: Batch processing is the oldest computing workload: payroll and billing runs on mainframes, scheduled by job control language. At web scale, Google's MapReduce (2004) made it possible to run batch jobs over thousands of commodity machines with automatic fault tolerance; Hadoop (2006) cloned it in open source. Higher-level tools followed (Pig, Hive, Cascading, FlumeJava), then Spark (2010–2014) kept intermediate data in memory and became the standard engine. Today batch jobs usually run on Spark, cloud warehouses or lakehouse SQL engines, orchestrated by Airflow, Dagster or declarative pipelines.
practice: Make every batch job idempotent and re-runnable for a given time window: write outputs to a partition or table version that is replaced atomically, so a retry never doubles data. Process incrementally where possible (only new partitions or changed rows) instead of reprocessing everything. Track freshness and completeness (did yesterday's partition arrive, with the expected row count?) as first-class metrics. Size jobs by data volume and skew, not just by cluster size, and keep backfills cheap by designing jobs to accept a date range.

@@+ lambdakappa
history: Nathan Marz described the Lambda architecture around 2011, while building Storm at BackType and Twitter: a batch layer (Hadoop) recomputes accurate views from all data, a speed layer (Storm) gives approximate real-time updates, and a serving layer merges them. It addressed the immaturity of stream processors at the time. Jay Kreps's 2014 essay 'Questioning the Lambda Architecture' proposed the Kappa architecture: keep a replayable log (Kafka) and a single stream-processing code path; to recompute, start a new job reading the log from the beginning and switch over when it catches up. As stream processors (Flink, Kafka Streams, Spark Structured Streaming) gained exactly-once state and event-time handling, Kappa-style designs became common, and lakehouses blurred the line further by letting the same tables serve both streaming and batch.
practice: Avoid maintaining two implementations of the same logic if you can; divergence between batch and streaming results is the main pain of Lambda. If you need real-time results and occasional full recomputation, keep enough log retention (or an archive in the lakehouse) to replay, and design jobs so a second version can run in parallel and be validated before cut-over. Use batch for heavy historical corrections and streaming for fresh data only when a single engine and code path (for example Spark or Flink in both modes) can serve both.

@@+ eventsourcing
history: Accounting ledgers are event sourcing on paper: balances are derived from transactions, never edited. In software, Greg Young popularized CQRS (command query responsibility segregation) and event sourcing around 2010, building on domain-driven design (Eric Evans, 2003) and earlier ideas such as Bertrand Meyer's command–query separation. Martin Fowler's writing spread the pattern; tools such as EventStoreDB and Axon, and Kafka as a shared log, made it practical. Durable-execution engines like Temporal apply the same idea to workflows: the state of a workflow is its event history.
practice: Use event sourcing where history matters to the business (finance, orders, audit, collaborative editing) or where many read models must be derived from the same facts. Name events in the past tense after business facts ('PaymentCaptured'), keep them immutable, and version their schemas. Plan for long histories: snapshot aggregates periodically so rebuilding state does not replay millions of events. Accept eventual consistency between the write side and read models, and make projections idempotent so they can be rebuilt from scratch.

@@+ datalake
history: The term 'data lake' was coined by James Dixon (Pentaho) around 2010, contrasting a lake of raw data with a bottled 'data mart'. Hadoop's HDFS made it cheap to store everything in files, and Hive put SQL tables on top. Moving to cloud object storage (Amazon S3 from 2006, then Azure and Google Cloud Storage) made lakes cheaper and separated storage from compute. By the late 2010s many lakes had become 'data swamps': files without schemas, owners or quality checks. Table formats (Delta, Iceberg, Hudi), catalogs and governance tools turned lakes into lakehouses.
practice: Even in a raw lake, enforce a minimal contract: a catalog entry, an owner, a schema and a partitioning scheme for every dataset. Store data in open columnar formats (Parquet) and avoid many small files. Lock down raw zones and expose curated tables instead. Use object-storage lifecycle rules to move old data to cheaper tiers, and keep a clear record of where personal data lives so that deletion requests can be honoured.

@@+ warehouse
history: Bill Inmon defined the data warehouse in the early 1990s as a subject-oriented, integrated, time-variant, non-volatile store for decision support; Ralph Kimball's dimensional modelling (1996) gave it its typical star-schema design. Teradata, Oracle, IBM and Microsoft dominated on-premises warehouses, with massively parallel appliances (Netezza, Greenplum, Vertica) in the 2000s. Cloud warehouses changed the economics: Amazon Redshift (2012), Google BigQuery (2011, based on Dremel) and Snowflake (2014) separated storage from compute and priced by use. Since the 2020s warehouses and lakehouses have converged: warehouses read open table formats, and lakehouses offer warehouse-grade SQL.
practice: Model for the questions people ask: star schemas with clear grain, conformed dimensions and documented metrics definitions. Control cost by partitioning and clustering large tables, avoiding SELECT * and limiting who can run unbounded queries; monitor the most expensive queries weekly. Keep transformation logic in version-controlled code (dbt or declarative pipelines) with tests, and treat the semantic layer (metric definitions) as a product so dashboards agree.

@@+ medallion
history: The medallion naming (bronze, silver, gold) was popularized by Databricks around 2019–2020 for lakehouse pipelines, but the idea is older: staging, integration and presentation layers in classic warehouses, and the raw, cleansed and curated zones of data lakes. It became widespread with Delta Lake and Delta Live Tables, and appears in most lakehouse reference architectures.
practice: Keep bronze as an append-only, replayable copy of source data (with ingestion metadata such as load time and source file), so any later layer can be rebuilt. Put deduplication, type casting, conformance and quality checks in silver, with data-quality expectations that quarantine bad rows. Build gold tables for specific consumers (dashboards, features, exports) and document their grain and freshness. Avoid adding layers for their own sake: the value is in clear contracts between layers, not in the number of copies.

@@+ oltp
history: Online transaction processing began with airline reservation systems such as SABRE (IBM and American Airlines, 1960s) and banking systems. Relational databases (System R, Oracle, DB2, from the late 1970s) and Jim Gray's transaction concepts made OLTP the core of business computing; the TPC benchmarks (TPC-A in 1989, TPC-C in 1992) measured it. Open-source databases (MySQL 1995, PostgreSQL 1996) brought it to the web. Distributed SQL systems (Spanner, CockroachDB, TiDB, Aurora's distributed storage) extended OLTP across machines and regions in the 2010s.
practice: Keep transactions short and touch few rows; design indexes for every frequent query; avoid hot rows (single counters updated by everyone). Use the database's constraints (unique, foreign keys, checks) to enforce invariants. Separate analytics from OLTP using replicas, CDC to a lakehouse, or HTAP features, so long reports never slow down customer-facing writes. Plan capacity with headroom for write peaks and connection pooling.

@@+ htap
history: Gartner coined 'hybrid transactional/analytical processing' in 2014, but the idea goes back to research on combining row and column stores. SAP HANA (2010) ran both on an in-memory columnar engine; Oracle and SQL Server added in-memory column stores (2014–2016); HyPer (TUM, acquired by Tableau) showed fast OLTP and OLAP on one engine with snapshots. Newer distributed systems (TiDB with TiFlash, SingleStore, and Postgres extensions) keep a row store for transactions and a columnar replica for analytics, kept in sync by the replication log.
practice: Use HTAP when analytics truly must see data within seconds of commit and the analytic queries are modest; for heavy analytics over long history, a separate lakehouse fed by CDC is usually cheaper and safer. Watch for resource isolation: analytic scans must not starve transactional work, so check whether the system runs them on separate replicas. Measure replication lag to the columnar copy, since 'fresh' is only as fresh as that lag.

@@+ rtanalytics
history: Real-time analytics stores arose to serve analytics to many users at once with fresh data: Druid (Metamarkets, 2011) for ad analytics dashboards, Pinot (LinkedIn, 2014) for member-facing analytics, ClickHouse (Yandex, open-sourced 2016) for web analytics, and later Rockset and StarRocks. They combined streaming ingestion from Kafka, columnar segments, indexes and scatter–gather query execution.
practice: Start from the query patterns and concurrency: which filters, group-bys and time ranges, how many queries per second, what p99 latency. Partition and sort data to match the most common filter, add indexes or pre-aggregations only for frequent expensive queries, and keep the raw long-term history in the lakehouse. Test with realistic concurrency and skew; most real-time OLAP incidents come from a new unindexed query pattern or a hot tenant.

@@+ searchengine
history: Information retrieval research dates back to the 1950s–1960s (Hans Peter Luhn's indexing at IBM, Gerard Salton's SMART system and the vector space model), with probabilistic models and TF–IDF in the 1970s and BM25 in the 1990s. Web search engines (AltaVista 1995, Google 1998 with PageRank) brought it to everyone. Doug Cutting's Lucene (1999) became the dominant open-source library, wrapped by Solr (2004) and Elasticsearch (2010). From 2019, neural retrieval (BERT re-rankers, dense embeddings) and hybrid search added semantic matching, and RAG made search a core part of LLM applications.
practice: Measure relevance with a judged query set before and after every change (analyzers, synonyms, boosts, embeddings). Combine keyword and vector retrieval for user-facing search, and re-rank the top results. Design mappings carefully (text versus keyword fields), keep shards a sensible size, and plan reindexing with aliases. Log queries with no results; they show where content or synonyms are missing.

@@+ mpp
history: Massively parallel processing databases emerged in the 1980s: Teradata (1984) and research systems such as Gamma and Grace partitioned data across nodes and ran query operators in parallel. In the 2000s, Netezza, Greenplum, Vertica and Aster brought MPP to commodity hardware. The Hadoop ecosystem then produced SQL-on-Hadoop engines (Impala 2012, Presto 2013 at Facebook, later Trino) and Spark SQL. Cloud warehouses (Redshift, BigQuery, Snowflake) are MPP systems with separated storage; DuckDB and DataFusion brought fast vectorized engines to single machines.
practice: Distribute large tables on the keys you join on, so joins can run locally without shuffling. Keep statistics fresh so the optimizer picks good join orders and algorithms. Watch for data skew (one join key with huge volume) and spill to disk; both show up as a few slow tasks. For federated engines like Trino, push filters to the sources and avoid cross-source joins of large tables.

@@+ catalog
history: Database system catalogs (the tables describing tables) date from System R. In the Hadoop era, the Hive Metastore (2010) became the shared catalog for many engines. Data discovery and governance tools followed (Apache Atlas, LinkedIn DataHub 2019, Lyft Amundsen, Collibra, Alation). Lakehouses made catalogs critical infrastructure: Unity Catalog (Databricks, open-sourced 2024), AWS Glue, Snowflake's Polaris (open-sourced as Apache Polaris), and the Iceberg REST catalog specification now perform atomic commits, vend storage credentials and enforce permissions across engines.
practice: Register every production table in one catalog with an owner, description, classification (for example personal data) and lineage. Grant access by groups and roles at the catalog level, never by sharing storage credentials. Automate lineage capture from pipelines so impact analysis ('what breaks if I change this column?') is possible. Choose a catalog that your engines support for both reads and writes, because the catalog is where cross-engine lock-in now happens.

@@+ workflow
history: Cron (1975) scheduled jobs on Unix for decades. Data teams built dependency-aware schedulers as pipelines grew: Oozie for Hadoop (2010), Luigi at Spotify (2012) and Apache Airflow at Airbnb (2014), which defined pipelines as Python code. Newer tools (Prefect, Dagster with its asset-centric model, Argo Workflows on Kubernetes) and durable-execution engines (Temporal) addressed Airflow's limits, while declarative pipelines moved dependency management into the data engines themselves.
practice: Keep orchestrators for orchestration and do heavy work in the engines they call. Make tasks idempotent and parameterized by a logical date so retries and backfills are safe. Define data-aware dependencies (wait for a partition or table version) instead of fixed times. Monitor service-level expectations for important outputs (for example 'gold table ready by 06:00') rather than individual task success, and keep DAGs small and readable.
