@@+ microservices
history: Service-oriented architecture (SOA) in the 2000s split enterprise systems into services connected by heavyweight middleware (enterprise service buses, SOAP). Amazon moved to small, independently owned services in the early 2000s (Jeff Bezos's 'API mandate' memo is often cited), and Netflix's migration to the cloud (2009–2016) produced influential open-source tooling (Hystrix, Eureka, Zuul). James Lewis and Martin Fowler's 2014 article named 'microservices'. Containers and Kubernetes made deploying many services practical; by the 2020s, a counter-movement toward 'modular monoliths' highlighted the costs for smaller teams.
practice: Draw service boundaries around business capabilities owned by one team, not around technical layers. Give each service its own data store and expose data through APIs or events, never through shared tables. Budget for the distributed-systems tax: timeouts, retries with backoff, idempotency keys, circuit breakers, tracing and contract tests. If a team cannot deploy its service independently, the split has not delivered its main benefit; start with a well-structured monolith and extract services where scaling or team independence demands it.

@@+ servicemesh
history: Large internet companies first built resilience into client libraries (Twitter's Finagle, Netflix's Hystrix and Ribbon). Linkerd (2016, from Buoyant, built on Finagle) and Istio (2017, Google, IBM and Lyft, built on Lyft's Envoy proxy) moved that logic into sidecar proxies beside each service, configured centrally. Later work reduced overhead: Istio's ambient mode (sidecar-less, 2022 onwards) and eBPF-based meshes such as Cilium.
practice: Adopt a mesh when you need uniform mutual TLS, traffic policies and telemetry across many services and languages; for a handful of services, libraries or a gateway may suffice. Roll it out gradually, starting with observability and mTLS in permissive mode. Set retry and timeout policies carefully so the mesh does not multiply retries already done by applications. Budget for the added latency (typically sub-millisecond per hop) and the operational load of upgrading the control plane.

@@+ apigateway
history: Reverse proxies (Apache httpd, NGINX from 2004, HAProxy) fronted web applications for years. As public APIs and microservices grew, dedicated API gateways added authentication, rate limiting, request transformation and developer portals: Apigee (2004), Kong (2015, on NGINX), Amazon API Gateway (2015), Envoy-based gateways and the Kubernetes Gateway API (generally available in 2023). AI gateways (routing and limiting LLM API calls) are the newest variant.
practice: Keep the gateway thin: authentication, rate limits, routing, TLS termination and observability belong there; business logic does not. Enforce per-client quotas and return clear 429 responses with retry hints. Version APIs explicitly and deprecate with notice. Make the gateway highly available and test its failure modes, because it is a single point every request passes through.

@@+ loadbalancing
history: Early web load balancing used DNS round robin; hardware appliances (F5 BIG-IP, from 1997) dominated data centres in the 2000s. Software balancers (HAProxy 2001, NGINX, LVS in the Linux kernel) and cloud load balancers replaced most appliances. Google's Maglev (2016) showed software load balancing at internet scale with consistent hashing; client-side balancing (gRPC) and service meshes moved decisions into clients and sidecars. Research on 'power of two choices' (Mitzenmacher, 1996) explained why picking the less loaded of two random servers works so well.
practice: Use health checks that test real readiness, not just that a port is open. Prefer least-requests or 'power of two choices' over plain round robin when request costs vary. Use consistent hashing only when affinity matters (caches, sessions), and drain connections gracefully during deployments. Remember that long-lived connections (HTTP/2, gRPC, WebSockets) need request-level balancing, or new servers will receive no traffic.

@@+ cloudcomp
history: Utility computing was imagined in the 1960s (John McCarthy). Amazon Web Services launched S3 and EC2 in 2006, renting storage and virtual machines by the hour; Google App Engine (2008) and Microsoft Azure (2010) followed. Cloud-native services (managed databases, queues, analytics, machine learning) shifted operations to providers, and Kubernetes (2014) became a common layer across clouds. Since 2023, demand for GPUs for AI has made capacity, power and cost of accelerators central to cloud strategy.
practice: Design for failure of instances and zones: spread across availability zones, keep state in managed, replicated services, and automate recovery. Treat cost as an engineering metric: tag resources by team and workload, use autoscaling and right-sizing, commit to discounts only for steady load, and watch data-transfer charges between zones and regions, which surprise many teams. Keep infrastructure in code so environments are reproducible.

@@+ serverless
history: Google App Engine (2008) offered platform-as-a-service where developers did not manage servers; AWS Lambda (2014) introduced functions billed per invocation and per millisecond, triggered by events. Serverless expanded to databases (Aurora Serverless, DynamoDB on-demand), containers (Cloud Run, Fargate), analytics (BigQuery, serverless Spark and SQL warehouses) and edge functions (Cloudflare Workers, 2017). Firecracker microVMs (AWS, 2018) made fast, isolated function start-up practical.
practice: Use serverless for spiky or low-volume workloads and event glue; for steady high load, compare costs with provisioned capacity. Keep functions small, stateless and idempotent (events may be delivered twice), and set timeouts and concurrency limits to protect downstream databases. Measure cold-start latency on your runtime and mitigate it with provisioned concurrency or lighter runtimes if user-facing latency matters.

@@+ containers
history: Unix chroot (1979) isolated file systems; FreeBSD jails (2000), Solaris Zones (2004) and Linux namespaces (from 2002) and cgroups (2007, from Google) built full process isolation. LXC (2008) combined them. Docker (2013) made containers easy with layered images, a simple CLI and a registry, and the Open Container Initiative (2015) standardized image and runtime formats. Kubernetes (2014) made containers the unit of deployment, and sandboxed runtimes (gVisor 2018, Firecracker, Kata Containers) strengthened isolation for untrusted code.
practice: Build small, reproducible images from minimal base images, pin versions and scan for vulnerabilities. Run as a non-root user with read-only file systems where possible. Set CPU and memory requests (and memory limits) so schedulers and the kernel can protect neighbours. Remember that containers share the host kernel: run untrusted code (including AI-agent tool execution) in a stronger sandbox such as gVisor or a microVM.

@@+ virtualization
history: IBM's CP-40 and VM/370 (1967–1972) ran multiple virtual machines on mainframes; Popek and Goldberg (1974) formalized when an architecture can be efficiently virtualized. x86 did not meet those requirements, so VMware (1998) used binary translation and Xen (2003) used paravirtualization. Hardware support (Intel VT-x 2005, AMD-V 2006, then nested page tables) made virtualization cheap; Linux KVM (2007) turned the kernel into a hypervisor. Cloud computing runs on it, with hardware offload cards such as AWS Nitro (2017) moving networking and storage virtualization off the main CPU.
practice: Use VMs when you need strong isolation (multi-tenant workloads, different kernels) and containers for density and speed inside them. Watch for 'noisy neighbour' effects and steal time on shared hosts. For performance-sensitive workloads, prefer instance types with dedicated cores, large pages and SR-IOV or offloaded networking. Live migration and snapshots are powerful for operations but can pause workloads briefly.

@@+ orchestration
history: Google's Borg (from about 2003) ran nearly all of Google's workloads on shared clusters; its successor research system Omega explored shared-state scheduling. Apache Mesos (2009, Berkeley) offered two-level scheduling for frameworks such as Spark and Marathon, and HashiCorp Nomad (2015) offered a simpler scheduler. Kubernetes (2014) combined Borg's lessons with Docker containers and a declarative API, and by 2017 had become the industry standard; Spark removed Mesos support in 4.0 (2025).
practice: Treat the orchestrator as a platform product: offer teams templates and guardrails (resource requests, probes, disruption budgets, security policies) rather than raw access. Keep cluster add-ons few and upgraded regularly. Run stateful systems only with mature operators and tested backup and restore. Monitor scheduling failures, pending pods and node pressure, which reveal capacity problems before outages.

@@+ iac
history: Configuration management tools (CFEngine 1993, Puppet 2005, Chef 2009, Ansible 2012) automated server setup. Cloud APIs made whole environments programmable: AWS CloudFormation (2011) and HashiCorp Terraform (2014) declared infrastructure as code with plans and state. Pulumi (2018) and the AWS CDK used general-purpose languages. Terraform's 2023 licence change led to the OpenTofu fork under the Linux Foundation. GitOps tools (Argo CD, Flux) applied the same reconcile-from-git idea to Kubernetes.
practice: Keep infrastructure code in version control with review, run plan in CI and apply from automation, not laptops. Store state remotely with locking, and split it by environment and blast radius so one mistake cannot destroy everything. Detect and fix drift regularly, and avoid hand edits in consoles. Write modules with clear inputs and sensible defaults so teams reuse rather than copy.

@@+ cdn
history: Akamai (1998) pioneered content delivery networks to relieve congested servers, using DNS to send users to nearby edge caches. CDNs grew with video streaming and e-commerce; Cloudflare (2010), Fastly (2011) and cloud providers' CDNs added programmable edges, security (DDoS protection, web application firewalls) and anycast routing. Netflix built Open Connect (2012), placing its own caches inside internet service providers. Edge computing (Workers, Compute@Edge, Lambda@Edge) runs code at CDN locations.
practice: Set cache headers deliberately (Cache-Control, surrogate keys) and version static assets with content hashes so they can be cached for a long time. Measure cache hit ratio by content type and region, and use purge APIs for urgent invalidation. Keep origin capacity sized for cache misses during purges or edge failures. For video, use segment-friendly caching and origin shielding so many edges do not stampede the origin.

@@+ observability
history: System monitoring began with tools like Nagios (1999) for checks and Graphite (2008) for time series. Google's Dapper paper (2010) introduced large-scale distributed tracing, followed by Zipkin and Jaeger. Prometheus (SoundCloud, 2012; CNCF 2016) became the standard for metrics, and Google's SRE book (2016) popularized service-level objectives and error budgets. Honeycomb and others promoted high-cardinality event-based observability; OpenTelemetry (2019, merging OpenTracing and OpenCensus) standardized instrumentation for traces, metrics and logs.
practice: Define service-level objectives for user-facing behaviour (latency, availability, freshness) and alert on burn rate, not on every metric. Instrument with OpenTelemetry so traces, metrics and logs share context (trace IDs in logs). Control cardinality and volume: sample traces, aggregate metrics and set log retention by value. For data pipelines, observe data itself (freshness, volume, schema and null rates), not just job success.

@@+ security
history: Perimeter security (firewalls from the late 1980s, VPNs) assumed the inside network was trusted. Repeated breaches showed attackers moving freely once inside, and Google's BeyondCorp (2014) introduced zero-trust access based on device and user identity. Cloud computing made identity and access management, key management and encryption standard building blocks; supply-chain attacks (SolarWinds 2020, Log4Shell 2021) pushed software bills of materials and signed builds (Sigstore, SLSA). AI agents now add new attack surfaces such as prompt injection.
practice: Apply least privilege everywhere: short-lived credentials, scoped roles, no shared secrets in code. Encrypt in transit (TLS, mTLS) and at rest with managed keys. Patch quickly and track dependencies with SBOMs and vulnerability scanning. Log security-relevant events centrally and rehearse incident response. For agent systems, treat all model inputs from tools and documents as untrusted and gate risky actions behind permissions or human approval.

@@+ mlops
history: Google's 2015 paper 'Hidden Technical Debt in Machine Learning Systems' showed that model code is a small part of real ML systems. Companies built internal platforms (Uber's Michelangelo 2017, Facebook's FBLearner, Google's TFX), and open-source tools followed: MLflow (Databricks, 2018), Kubeflow (2018), feature stores (Feast 2019) and model registries. The rise of LLMs added prompt management, evaluation suites and LLM observability ('LLMOps').
practice: Version everything that determines a model: code, data snapshot, features, hyperparameters and environment, so any model can be reproduced. Automate training and evaluation pipelines with gates (a new model must beat the current one on held-out data and checks for bias and drift). Deploy with canaries or shadow traffic, and monitor input distributions, prediction distributions and business outcomes. Keep a fast rollback path to the previous model.

@@+ featurestore
history: Uber's Michelangelo platform (2017) described a feature store to share features between training and serving and avoid 'training–serving skew'. Airbnb (Zipline), Twitter and others built similar systems; Feast (Gojek and Google, 2019) and Tecton (2019, from the Michelangelo team) offered open-source and commercial versions, and data platforms (Databricks, Vertex AI, SageMaker) added built-in feature stores.
practice: Define each feature once with its owner, freshness and computation logic, and generate both offline (training) and online (serving) values from the same definition. Use point-in-time-correct joins for training data, so features reflect only information available at prediction time (no leakage). Monitor online freshness and missing values, and keep the online store small and fast (often Redis, DynamoDB or similar).

@@+ ml
history: Arthur Samuel coined 'machine learning' in 1959 for a checkers program that improved by playing itself. Statistical learning theory (Vapnik and Chervonenkis), decision trees (ID3 1986, CART 1984), support vector machines (1995), random forests (2001) and boosting (AdaBoost 1995, gradient boosting 2001) defined the field before deep learning. Practical libraries (scikit-learn 2007, XGBoost 2014, LightGBM 2017) made these methods standard in industry, where they still power much of ranking, fraud detection, forecasting and ad prediction.
practice: Start every problem with a simple baseline (logistic regression or gradient-boosted trees) and an evaluation that mirrors production: split by time or by entity, measure the metric the business cares about, and check calibration. Most gains come from better data and features, not fancier models. Watch for leakage, class imbalance and distribution shift, and monitor models after deployment.

@@+ rl
history: Reinforcement learning combines ideas from animal learning psychology, optimal control and dynamic programming (Bellman, 1950s). Temporal-difference learning (Sutton, 1988), Q-learning (Watkins, 1989) and TD-Gammon (Tesauro, 1992, which learned backgammon by self-play) set the foundations. Deep RL took off with DQN on Atari (2013–2015) and AlphaGo (2016); PPO (2017) became the default policy-gradient method. RL from human feedback (2017 onwards) and, from 2024, RL with verifiable rewards for reasoning models made RL central to training language models.
practice: Use RL only when actions affect future states and rewards; many 'RL' problems are really supervised learning or bandits. Invest in the environment and reward design first, because agents exploit any loophole. Prefer simulation and offline evaluation before acting in the real world, and constrain actions for safety. Track reward and the behaviours behind it, since reward going up does not always mean the intended behaviour improved.
