@@ ffmpeg
value: FFmpeg is a free, open-source set of C libraries and command-line tools that can read, decode, change, encode and write almost any audio or video format. Most media software is built on it. VLC and Chromium-based browsers decode with its libraries, YouTube and broadcast pipelines transcode with it, OBS, HandBrake and many cloud transcoders wrap it, and countless scripts call the ffmpeg command. If a system takes video in one shape and produces another, FFmpeg is probably inside.
The problem it solves is combinatorial. There are hundreds of codecs (H.264, HEVC, AV1, AAC, Opus, ProRes) and dozens of containers (MP4, MKV, MPEG-TS, WebM, HLS, DASH). Each has its own bitstream and timestamp rules, and one converter per pair of formats is impossible. FFmpeg puts one shared data model in the middle: compressed packets and decoded frames, each with timestamps. Any demuxer can then feed any decoder, any filter can process any frame, and any encoder can feed any muxer. N input formats and M output formats need N + M components instead of N × M converters.
For the layers above (streaming platforms, server-side ad insertion, ACR reference capture, machine-learning jobs that need raw frames), FFmpeg turns "support format X" into a library call. Three lower concepts give it its value. Video streaming (L1) defines the pipeline FFmpeg implements: ingest, decode, process, encode, package. Codecs (H.264 / HEVC / AV1, L0) are the algorithms inside libavcodec, written natively or wrapped from external libraries such as x264, x265, SVT-AV1 and dav1d. C and C++ (L0) give exact control over memory layout and, together with hand-written SIMD assembly, the speed to decode or convert hundreds of frames per second on one server.
terms: Container — a format (MP4, MKV, MPEG-TS) that interleaves audio, video and subtitle streams with their timestamps; it compresses nothing itself.
Codec — the algorithm that encodes or decodes one stream, for example H.264 for video or AAC for audio.
Demuxer and muxer — the parts that split a container into per-stream packets, and write packets back into one.
Packet (AVPacket) — one unit of compressed data, usually one frame, with timestamps and a stream index.
Frame (AVFrame) — one decoded picture or block of audio samples in raw form.
PTS and DTS — when a frame is shown and when it must be decoded; they differ when B-frames are reordered.
Time base — the unit of a stream's timestamps as a fraction of a second, for example 1/90000 in MPEG-TS.
Filter graph — a directed graph of filters (scale, crop, overlay, loudness) that frames pass through between decoder and encoder.
Stream copy — moving compressed packets to the output without decoding (-c copy); fast, but it can only cut at keyframes.
history: Fabrice Bellard started FFmpeg in 2000, publishing under the pseudonym Gérard Lantau. The name joins "FF" (fast forward) with MPEG, the standards group. PC video then depended on closed codecs installed one by one; an open library for MPEG-1, MPEG-2 and MPEG-4 Part 2 removed that dependence. Michael Niedermayer led the project from about 2004 to 2015 and wrote large parts of libavcodec, including much of the H.264 decoder.
In 2011 a group of developers who disagreed with how the project was run forked it as Libav. For a few years Debian and Ubuntu shipped Libav instead of FFmpeg. FFmpeg kept merging most Libav changes and released faster; distributions moved back to FFmpeg around 2015, and Libav later became inactive.
The ecosystem grew around the core. VideoLAN's x264 (from 2004) became the best-known H.264 encoder and is used through FFmpeg as libx264. Royalty-free formats followed: VP8, VP9 and AV1, wrapped as libvpx, libaom and SVT-AV1, with VideoLAN's dav1d as the fast AV1 decoder.
Recent releases show where the work goes now: the GPU and parallelism. FFmpeg 6.1 (2023) added vendor-neutral Vulkan decoding. 7.0 "Dijkstra" (April 2024) made the ffmpeg tool multi-threaded, so its pipeline stages run in parallel. 8.0 "Huffman" (August 2025) added a Whisper speech-to-text filter and codecs written as Vulkan compute shaders. 8.1 "Hoare" (March 2026) added Direct3D 12 H.264 and AV1 encoding. The current major release is 9.0 "Lei" (August 2026; 9.0.2 in September 2026), with more Vulkan decoders and AVX-512 code. In 2025 FFmpeg was also at the centre of a debate about open-source funding: its developers said the code is written almost entirely by volunteers and asked large companies that report bugs found by automated tools to help pay for fixes.
how: FFmpeg is a few main libraries plus three tools. libavformat reads and writes containers and network protocols (files, HTTP, RTMP, SRT, HLS). libavcodec holds the decoders and encoders. libavfilter runs filter graphs. libswscale scales pictures and converts pixel formats; libswresample does the same for audio. libavdevice captures from cameras and screens, and libavutil holds shared code and data structures. The tools are ffmpeg (convert), ffprobe (inspect) and ffplay (a simple player).
Every job follows the same pipeline: demux, decode, filter, encode, mux. First libavformat probes the input. It scores each known format by how well the first bytes match, then reads enough packets to learn each stream's codec, resolution and frame rate. The demuxer then produces packets. Each packet carries a stream index, compressed bytes, a PTS, a DTS and a duration. The decoder uses a send-and-receive interface (introduced in 2016): you send packets and receive frames, because one packet can produce zero, one or several frames. A video decoder holds frames back while B-frames are reordered, and an encoder holds frames while it looks ahead. Decoded frames are raw planes. For 8-bit 4:2:0 video, the Y (brightness) plane is full size and the two colour planes are each a quarter size, so a 1920×1080 frame takes about 3.1 MB. Frames and packets are reference-counted buffers, so filters and outputs can share one picture without copying it.
Timestamps are the part that causes most real bugs. Each stream has its own time base. MPEG-TS uses 90 kHz ticks, so at 30 frames per second each frame lasts 3,000 ticks. MP4 stores a separate timescale per track. FFmpeg converts between time bases with exact integer arithmetic (av_rescale_q) so that rounding does not drift over a long file. B-frames make decode order differ from display order: frames are decoded as I P B B but shown as I B B P. DTS must increase steadily for the decoder, while PTS jumps back and forth. Warnings such as "non-monotonic DTS" and audio that slowly falls out of sync usually come from inputs whose timestamps break these rules.
Between decoder and encoder sits libavfilter. A filter graph is a set of filters connected by pads, written as text such as [0:v]scale=1280:720,fps=30[v]. Before any frame flows, the graph negotiates formats: each filter lists the pixel formats it accepts, and FFmpeg inserts conversions where two neighbours disagree. Common filters in streaming work are scale, fps, setsar (fixes the pixel aspect ratio), loudnorm (EBU R128 loudness), overlay, drawtext, split (one input, several outputs) and libvmaf (a perceptual quality score).
The codecs concept supplies the algorithms. FFmpeg has native decoders for almost every format, including H.264, HEVC, VP9 and AV1. Most production encoders are wrapped libraries: libx264, libx265, libsvtav1, libaom, libvpx, libopus. FFmpeg maps its common options onto each encoder: -b:v (target bitrate), -maxrate and -bufsize (the VBV buffer that caps peaks), -crf (constant quality), -g (maximum distance between keyframes) and -preset (speed against compression). The same option can mean slightly different things in different encoders.
C and assembly supply the speed. FFmpeg is written in C (C11 since version 7.0). C gives control over memory alignment and picture strides, has no garbage-collection pauses, and compiles for every operating system and CPU. The hottest loops, such as inverse transforms, motion-compensation interpolation, pixel-format conversion and block difference sums, are written by hand in assembly for x86 (SSE, AVX2, AVX-512), ARM (NEON) and RISC-V (vector). At start-up FFmpeg detects the CPU's features and fills tables of function pointers with the fastest version. One AVX2 instruction works on 32 bytes and one AVX-512 instruction on 64 bytes, so a loop over 8-bit pixels handles 32 or 64 pixels at a time. On top of this, decoders use frame threading (several frames decoded in parallel, limited by which frames reference which) and slice threading.
Hardware acceleration moves decode and encode onto fixed-function blocks. With options such as -hwaccel cuda, vaapi, videotoolbox, qsv or vulkan, frames can stay in GPU memory from decoder through filters (for example scale_cuda) to encoder (for example h264_nvenc), which avoids copying each 3 MB frame across the PCIe bus. Hardware encoders are very fast, but at the same bitrate they usually give somewhat lower quality than slow software presets. Finally, the muxer writes the result: MP4 (with -movflags +faststart to put the index at the front for progressive playback), fragmented MP4 and CMAF, MPEG-TS, or the hls and dash muxers, which cut segments and write playlists for the streaming layer above.

example: A CTV platform uses server-side ad insertion. A 30-second ad arrives as a mezzanine file: 1920×1080, 29.97 frames per second, Apple ProRes 422 HQ video (roughly 220 Mbit/s, so about 800 MB) and 24-bit PCM stereo audio at 48 kHz. The content it will be stitched into uses an H.264 ladder of three renditions: 1080p at 6 Mbit/s, 720p at 3 Mbit/s and 360p at 0.8 Mbit/s, with a keyframe every 2 seconds, 6-second segments and AAC audio at 128 kbit/s and 48 kHz. If the ad does not match the content's codec, frame rate, keyframes or audio rate, many CTV players stall at the splice or the ad is skipped.
Step 1, inspect. ffprobe -show_streams ad.mov reports codec prores, 1920×1080, frame rate 30000/1001 (29.97 fps) and audio pcm_s24le at 48,000 Hz.
Step 2, decode once and encode three times. One command does this: ffmpeg -i ad.mov -filter_complex "[0:v]split=3[a][b][c];[b]scale=1280:720[m];[c]scale=640:360[s]" -map "[a]" -map 0:a -c:v libx264 -b:v 6M -maxrate 6M -bufsize 12M -g 60 -keyint_min 60 -sc_threshold 0 -c:a aac -b:a 128k -ar 48000 ad_1080.mp4, followed by the same options with "[m]" and 3M for ad_720.mp4 and with "[s]" and 800k for ad_360.mp4. Options apply to the output file that follows them. A keyframe every 60 frames gives 60 × 1001/30000 = 2.002 seconds. Setting -sc_threshold 0 stops the encoder from adding extra keyframes at scene cuts, so keyframes fall on the same frames in all three renditions.
Step 3, sizes. 1080p: 6 Mbit/s × 30 s = 180 Mbit = 22.5 MB. 720p: 3 × 30 = 90 Mbit = 11.25 MB. 360p: 0.8 × 30 = 24 Mbit = 3 MB. Audio adds 128 kbit/s × 30 s = 3.84 Mbit, about 0.48 MB per rendition. About 800 MB becomes about 38 MB.
Step 4, cost. Encoding time grows roughly with the number of pixels. A 1080p frame has 2.07 million pixels, 720p has 0.92 million and 360p has 0.23 million, a total of 3.22 million. The whole ladder therefore costs about 3.22 / 2.07 = 1.56 times one 1080p encode, and the ProRes source is decoded only once instead of three times. Suppose libx264 at the medium preset encodes this 1080p content at 120 frames per second on your server (an assumption; measure it). The ad has 900 frames, so 1080p alone takes 900 / 120 = 7.5 seconds and the ladder roughly 7.5 × 1.56 ≈ 12 seconds.
Step 5, timestamps and segments. When packaged into MPEG-TS, each frame lasts 90,000 × 1001/30000 = 3,003 ticks. A segment of three GOPs is 180 frames = 540,540 ticks = 6.006 seconds, which is why Apple's HLS guidelines mention 6.006-second segments for 29.97 fps content. The 900 frames make exactly 5 segments, 30.03 seconds in total.
Step 6, check. Run ffprobe -select_streams v -show_entries frame=pict_type,pts_time on each output and confirm that I-frames appear at 0, 2.002, 4.004 seconds and so on in all three files. Then score each rendition against the source with the libvmaf filter.
intuition: FFmpeg is a universal adapter: every format plugs into one common socket, packets and frames with timestamps, so any input can be joined to any output.
This design follows the physics of media. Every format, however different on disk, becomes the same two things on the way through: compressed packets on one side of the codec and raw frames on the other. If you standardise those two shapes, and the clock they are measured with, every new format costs one component, not a converter for each existing format. That is the same idea as a compiler's intermediate representation: many front ends, many back ends, one shared form in the middle.
The rest is engineering for volume. Video is large (3 MB per raw HD frame, 30 to 60 frames per second), so the design avoids copies with reference-counted buffers, keeps hot loops in assembly, and lets frames stay on the GPU.
mistakes: People often think -c copy is a fast way to re-encode. In fact it does not decode at all. It moves compressed packets into a new container, so it cannot change resolution, bitrate or codec, and a cut can only start on a keyframe. Asking to start at 13 seconds in a file with keyframes every 2 seconds gives a start at a nearby keyframe, or a few seconds of broken picture.
People often think FFmpeg is itself a codec, so "FFmpeg quality" is one thing. In fact FFmpeg is a framework. Quality depends on which encoder you choose and how you set it: libx264 at a slow preset and h264_nvenc produce different pictures at the same bitrate.
People often think -b:v 3M guarantees a 3 Mbit/s stream. In fact it is an average target. Without -maxrate and -bufsize, short peaks can be several times higher, and an HLS player that trusted the advertised bandwidth will stall. Streaming encodes need a capped rate.
People often think an FFmpeg binary can be shipped anywhere because FFmpeg is free. In fact the default build is LGPL, a build with x264 or x265 (--enable-gpl) is GPL, and a build with --enable-nonfree (for example fdk-aac) may not be redistributed at all. Codec patents are a separate question from the software licence: using H.264 or HEVC commercially can require patent royalties even if the code is free.
friction: The command line is hard to use correctly. Option order matters (an option before -i applies to the input, after it to the next output), stream selection rules are subtle, and defaults and option names change between major versions. Version 7.0 removed APIs deprecated before 6.0, and 9.0 removed old NVENC options and support for NVENC SDKs older than 11.1. Scripts that worked for years can break on upgrade.
The library API also changes. Major version bumps break binary compatibility, Linux distributions ship different versions, and an application that links the system FFmpeg may behave differently on each machine. Many teams ship a static build or a container image with a fixed version.
Security is a constant cost. FFmpeg contains hundreds of decoders, many for rare formats, and all of them parse untrusted bytes in C. Continuous fuzzing finds memory bugs every week; one lead developer alone has fixed more than 2,700 issues reported by Google's OSS-Fuzz. The 2025 funding debate showed the tension: large companies depend on this code, but the people fixing it are mostly volunteers.
Hardware paths differ by platform and driver: a filter graph built for NVIDIA needs different filters on Intel or Apple, and consumer GPUs limit concurrent encode sessions. Software AV1 encoding at high-quality presets is still many times slower than H.264.
practice: Inspect before you transform. Run ffprobe on every input and log codec, resolution, frame rate, time base and audio layout; most pipeline failures are surprises in the input. Record ffmpeg -version and the build options in each job's metadata, and pin the version in a container image so a rebuild cannot silently change output.
For adaptive streaming, make keyframes predictable: a fixed GOP (-g and -keyint_min equal), -sc_threshold 0, or -force_key_frames "expr:gte(t,n_forced*2)" for a keyframe every 2 seconds. Always cap the rate with -maxrate and -bufsize. Decode once and split the frames to all renditions rather than running one process per rendition.
For quality decisions, measure instead of guessing. Use the libvmaf filter to compare renditions with the source, and test presets on your own content: sports, animation and dark drama scenes compress very differently. For files encoded once and watched many times, slower presets usually pay for themselves in bandwidth.
For throughput, keep frames on the GPU end to end (for example -hwaccel cuda -hwaccel_output_format cuda with scale_cuda and h264_nvenc). For live channels, prefer hardware or fast presets and accept a somewhat higher bitrate.
For untrusted uploads, treat FFmpeg as an attack surface. Run it in a sandbox with CPU, memory and time limits, restrict accepted formats and protocols (the format_whitelist and protocol_whitelist options), and refuse inputs above a maximum resolution and duration. From code, use the send-and-receive API and rescale every timestamp with av_rescale_q; in Python, PyAV exposes the same objects.
quiz: What do libavformat, libavcodec and libavfilter each do? || libavformat demuxes and muxes containers and protocols. libavcodec turns packets into frames and frames into packets. libavfilter runs filter graphs (scaling, loudness) on decoded frames.
Why does the decoding API let you send packets and receive frames separately, instead of returning one frame per packet? || One packet can produce zero, one or several frames. Decoders delay output while B-frames are reordered and encoders buffer frames for look-ahead, so input and output must be decoupled.
Why do ABR ladders need a fixed GOP and -sc_threshold 0? || Players switch rendition at segment boundaries, and each segment must start with a keyframe at the same time in every rendition. Scene-cut keyframes would appear at different places in each rendition and misalign the segments.
At 29.97 fps in a 90 kHz time base, how many ticks does one frame last, and how long is a 180-frame segment? || 90,000 × 1001/30000 = 3,003 ticks per frame. 180 × 3,003 = 540,540 ticks, which is 6.006 seconds.
When would you choose h264_nvenc over libx264 at a slow preset? || For live channels or very high volume, where speed and cost per stream matter more than the last 10–30% of compression. For on-demand files encoded once and watched many times, the slow software preset usually wins, because the saved bandwidth pays back on every view.

@@ codecs
value: A video codec compresses moving pictures so they can be stored and sent over networks. Raw 1080p video at 30 frames per second, with 8-bit samples and 4:2:0 colour, is 1920 × 1080 × 1.5 bytes = 3.1 MB per frame, or about 746 Mbit/s. A streaming service sends the same picture at 4 to 8 Mbit/s, about 100 to 180 times less. Without that factor there would be no streaming, no video calls and no CTV advertising: a single raw HD stream would fill a home internet connection many times over.
H.264/AVC (2003), HEVC/H.265 (2013), VP9 (2013), AV1 (2018) and VVC/H.266 (2020) are the codecs that matter today, and AV2 (2026) is the next one. They all use the same basic recipe and differ in how many prediction choices they offer and how cleverly they code the choices. Each generation saves roughly 30–50% bitrate at the same visual quality, and pays for it with several times more encoding computation. H.264 still plays everywhere and remains the safe choice for ad creatives. HEVC dominates 4K and HDR on TVs. AV1 is now a large share of streaming: Netflix reported in December 2025 that about 30% of its streaming used AV1.
Three lower concepts carry the work. Video streaming (L1) is the reason codecs matter: bandwidth is the main cost of delivering video, and the codec sets it. Motion compensation (L2) removes temporal redundancy: most of a frame is the previous frame moved a little, so the encoder sends motion vectors instead of pixels. The DCT and transform coding (L2) remove spatial redundancy: the small leftover differences are turned into a few significant frequency coefficients, and quantisation throws away detail the eye does not notice.
terms: Intra prediction — predicting a block from decoded pixels of the same frame, along a chosen direction.
Inter prediction — predicting a block from a block in another frame, displaced by a motion vector.
Residual — the difference between the real block and its prediction; this is what gets transformed and coded.
Transform — an integer approximation of the DCT that turns a residual block into frequency coefficients.
Quantisation — dividing coefficients by a step size and rounding; the only step that loses information, and the main quality knob.
QP — the quantisation parameter; in H.264 and HEVC the step size doubles every 6 QP.
Entropy coding — lossless coding of all decisions and coefficients into bits (CABAC in H.264/HEVC, a multi-symbol arithmetic coder in AV1).
I, P and B frames — frames coded with intra prediction only, with prediction from earlier frames, and with prediction from both earlier and later frames.
GOP — the group of pictures from one keyframe to the next; decoding can start only at a keyframe (an IDR frame in H.264/HEVC).
Rate control — the encoder logic that chooses QP per frame and block to hit a bitrate or quality target (CBR, VBR, CRF).
history: Digital video coding grew out of two ideas from the 1970s. Ahmed, Natarajan and Rao described the discrete cosine transform in 1974, and researchers showed that predicting a frame from a displaced previous frame removed most of the data. ITU-T H.261 (1988) combined them for video calls over ISDN lines at multiples of 64 kbit/s. MPEG-1 (1993) did it for Video CD, and MPEG-2/H.262 (1995) for DVD and digital broadcast. MPEG-2 is still used in many cable and satellite systems.
H.264/AVC was approved in May 2003 by the Joint Video Team of ITU-T VCEG and ISO/IEC MPEG. It roughly halved MPEG-2 bitrates, with 4×4 integer transforms, quarter-pixel motion vectors, multiple reference frames, an in-loop deblocking filter and CABAC. It arrived as broadband grew, became the format of YouTube, Blu-ray and the iPhone, and is still the most widely supported video format.
HEVC (2013) roughly halved H.264 again, mainly for HD and 4K. Its licensing went badly: three competing patent pools (MPEG LA, HEVC Advance and Velos Media) plus independent patent holders made the total cost unclear for streaming companies. That uncertainty is why Google pushed its royalty-free VP9 (2013), and why Amazon, Cisco, Google, Intel, Microsoft, Mozilla and Netflix founded the Alliance for Open Media in 2015. AOMedia released AV1 in 2018, about 30% more efficient than VP9, under a royalty-free licence. Hardware decoders followed slowly, but by the early 2020s most new TVs, GPUs and phones could decode AV1; Apple added it with the A17 Pro and M3 chips in 2023.
VVC/H.266 was finalised in July 2020 and saves about half the bitrate of HEVC, but has seen little streaming use so far. AOMedia released the AV2 specification in mid-2026 and claims about 30% better compression than AV1; no consumer devices decode it in hardware yet. Licensing keeps moving too: in December 2025 Access Advance announced it would acquire Via LA's HEVC and VVC pool, and its Video Distribution Patent pool (2025) also claims patents on streaming with AV1 and VP9.
how: A codec standard defines only the bitstream and the decoder. The encoder is free to make any choices that produce a valid bitstream, so two H.264 encoders can differ greatly in quality. Every mainstream codec uses the same hybrid loop. The picture is split into blocks. For each block the encoder predicts the pixels, subtracts the prediction to get a residual, transforms and quantises the residual, and entropy-codes the result. It then decodes its own output, exactly as the decoder will, and uses that reconstruction as the reference for later predictions. Using the reconstruction, not the original, is essential: if encoder and decoder predicted from different pictures, small errors would grow frame after frame.
The first step is splitting. H.264 uses fixed 16×16 macroblocks that can be divided down to 4×4 for prediction. HEVC uses coding tree units of up to 64×64, split by a quadtree into coding units, prediction units and transform units. AV1 uses superblocks of up to 128×128 with a ten-way partition tree that allows rectangles such as 4:1. VVC adds binary and ternary splits inside a quadtree. Large blocks cover flat sky or a studio background with almost no bits; small blocks follow edges and faces. Choosing the split is a search the encoder pays for in computation.
Intra prediction fills a block from the decoded pixels just above and to the left. H.264 has 9 directions for 4×4 blocks, HEVC has 33 angular modes plus DC and planar, AV1 has 56 directional modes plus smooth and Paeth modes and chroma-from-luma, and VVC has 65 angles. More directions fit diagonal edges more closely, so the residual is smaller.
Inter prediction is where motion compensation does its work. For each block the encoder searches nearby positions in one or more reference frames for the best match, and sends a motion vector. Vectors have quarter-pixel precision (one-eighth in some AV1 and VVC modes); the decoder builds in-between pixel values with interpolation filters, such as H.264's 6-tap filter for half-pixel positions. The vector itself is coded as the difference from a vector predicted from neighbouring blocks, because neighbouring blocks usually move together. B-frames average a prediction from an earlier and a later frame, which handles uncovered background and noise well. This is why B-frames are coded out of display order. Newer codecs add merge modes (copy a neighbour's motion exactly), affine motion for zoom and rotation (VVC) and global motion (AV1).
The DCT and transform coding concept handles the residual. A smooth residual block transformed with a DCT-like transform puts nearly all its energy into a few low-frequency coefficients. H.264 uses a 4×4 integer transform, built only from additions and shifts, so encoder and decoder compute exactly the same numbers; older MPEG decoders that used floating-point inverse DCTs could drift apart. HEVC allows 4×4 to 32×32 and uses a DST for small intra blocks. AV1 combines DCT, ADST, flipped ADST and identity transforms horizontally and vertically, up to 64×64.
Quantisation is where information is lost. Each coefficient is divided by a step size and rounded. In H.264 and HEVC, QP runs from 0 to 51 for 8-bit video, and the step size doubles every 6 QP: QP 22 gives a step of about 8 and QP 28 a step of about 16. Most high-frequency coefficients become zero. Encoders also use per-frequency weighting and adaptive quantisation, giving more bits to flat areas where blocking is easy to see and fewer to busy texture.
Entropy coding turns all decisions (split flags, modes, vectors, coefficients) into bits without further loss. CABAC, used by H.264 Main profile and above and by all of HEVC, turns each value into binary decisions and codes each with an arithmetic coder whose probability adapts to the data; it saves about 9–14% over H.264's simpler CAVLC. AV1 uses an adaptive arithmetic coder over symbols with up to 16 values. Last, in-loop filters clean the reconstruction before it becomes a reference: deblocking smooths block edges, HEVC adds sample adaptive offset, and AV1 adds CDEF and loop restoration. AV1 can also remove film grain before encoding and resynthesise it in the decoder, saving many bits on grainy films.

example: Start with the arithmetic of a stream. Raw 1080p30 with 4:2:0 colour is 1920 × 1080 × 1.5 = 3,110,400 bytes per frame, × 30 = 93.3 MB/s = 746 Mbit/s. Apple's HLS guidelines list 6,000 to 7,800 kbit/s for 1080p H.264, and 4,500 to 5,800 kbit/s for 1080p HEVC. At 6 Mbit/s, H.264 compresses about 124 times; HEVC at 4.5 Mbit/s compresses about 166 times for similar quality.
Where do the bits go? Take a 2-second GOP at 30 fps: 60 frames. Suppose the I-frame costs 200 KB, each of 19 P-frames 20 KB and each of 40 B-frames 8 KB (plausible numbers for a talk show). The total is 200 + 380 + 320 = 900 KB per 2 seconds, which is 450 KB/s or 3.6 Mbit/s. The single I-frame is 22% of the bits. This is why shorter keyframe intervals, which help fast channel changes and ABR switching, cost bandwidth.
Now one block in a P-frame. A 16×16 block on a presenter's shoulder best matches the previous frame 3.25 pixels to the left, so the motion vector is (−13, 0) in quarter-pixel units. Its neighbours moved by (−12, 0), so the encoder sends only the difference (−1, 0), a few bits. After subtracting the prediction, one 4×4 part of the residual is:
rows 5 5 5 5 / 5 5 5 5 / 3 3 3 3 / 3 3 3 3 (brightness differences, on a 0–255 scale)
The H.264 core transform multiplies by the matrix with rows [1 1 1 1], [2 1 −1 −2], [1 −1 −1 1], [1 −2 2 −1] on both sides. Because every row is constant, the horizontal pass leaves only the first column: 20, 20, 12, 12. The vertical pass gives 20 + 20 + 12 + 12 = 64, then 2×20 + 20 − 12 − 2×12 = 24, then 20 − 20 − 12 + 12 = 0, then 20 − 2×20 + 2×12 − 12 = −8. Sixteen residual values became three non-zero coefficients: 64, 24 and −8.
Quantise with a step of 16 (about QP 28; H.264 folds the transform's scaling factors into this step, which we ignore here). 64/16 = 4; 24/16 = 1.5, which becomes 1 because, for inter blocks, typical H.264 encoders round with an offset of about 1/6 instead of 1/2 (a dead zone that saves bits); −8/16 = −0.5 becomes 0. Only two numbers, 4 and 1, are entropy-coded, roughly a dozen bits instead of 16 values.
The decoder multiplies back (64 and 16) and inverts the transform. The reconstructed rows are 4.8, 4.4, 3.6 and 3.2, which round to 5, 4, 4, 3 against the original 5, 5, 3, 3. No pixel is off by more than one brightness level out of 255. That is the whole trade in one block: a tiny, invisible error for a large saving. Raising QP to 34 doubles the step to 32, the 24 also becomes 0, and the block is sent as a flat DC level, cheaper again but now visibly smoothed.
intuition: Send what changes, approximately, in the frequencies the eye cares about.
Consecutive frames are mostly the same scene shifted a little, so describing the shift is far cheaper than redrawing the picture. What prediction cannot explain is usually small and smooth, and smooth signals are described by a few low frequencies. The eye is much less sensitive to fine high-frequency detail and to small errors in colour than in brightness, so those parts can be coarsened or dropped. Each stage removes a different kind of redundancy: in time (motion compensation), in space (intra prediction and the transform), in perception (quantisation and 4:2:0 colour) and in statistics (entropy coding).
The closed loop is the other natural idea. Because the encoder decodes its own output and predicts only from that, the decoder sees exactly the same references. Errors stay bounded instead of piling up, and every keyframe resets the chain.
mistakes: People often think a codec standard defines the encoder. In fact it defines only the bitstream and the decoder. Encoder quality depends on the implementation and its settings: x264 at a slow preset and a cheap hardware encoder both produce valid H.264, at very different quality per bit.
People often think a newer codec is always better to deploy. In fact the gain only reaches viewers whose devices can decode it in hardware. Software decoding of HEVC or AV1 on an older TV or set-top box may stutter or drain power, so services keep H.264 renditions as a fallback, and ad creatives are usually delivered in H.264.
People often think bitrate alone sets quality. In fact the same bitrate looks very different on different content: a static news desk at 2 Mbit/s can look better than fast sports at 6 Mbit/s. This is why services moved from fixed ladders to per-title and per-shot encoding, measured with metrics such as VMAF.
People often think "AV1 is royalty-free" means no patent risk. In fact AOMedia members license their patents royalty-free, but outside pools (Sisvel, and Access Advance's Video Distribution pool) claim patents that read on AV1 and VP9. Most large streamers use AV1 anyway, but it is a legal question, not a settled fact.
friction: Compression costs computation, and the cost rises fast. Each generation multiplies encoder search: more block shapes, more modes, more reference frames. Slow presets of AV1 and VVC encoders can run far below real time even on many cores. This suits a film encoded once and watched millions of times, but not live sports or a long tail of user uploads, where H.264 or hardware encoders still win.
Hardware decides adoption. A codec reaches TVs only when it is built into the system-on-chip, which takes years from specification to shelf, and TVs stay in homes for many years after that. In 2026, AV2 has a specification but no consumer hardware. CTV platforms therefore keep several codecs in their ladders, multiplying encoding and storage cost.
Licensing shaped the market as much as engineering. HEVC's fragmented pools slowed its use on the web, which created AOMedia; VVC's uptake has been held back by similar uncertainty. The pool consolidation announced in December 2025 may simplify HEVC and VVC licensing, while the new streaming pools add new uncertainty for AV1.
Quality is hard to measure. PSNR is cheap but does not match human perception well. VMAF is better but was trained mostly on certain content and viewing conditions. Banding in dark scenes, grain, and errors near text or faces can escape the numbers. Low-latency live encoding also limits the tools: B-frames and look-ahead add delay, so a live stream needs more bits for the same quality.
practice: Choose codecs by device support first. For CTV, check which codecs and profiles each platform decodes in hardware (H.264 High, HEVC Main 10 for HDR, AV1 on newer TVs), and keep an H.264 ladder for everything else. Deliver ad creatives as H.264 mezzanines and let the ad-insertion system transcode them to match each content ladder.
Use constrained quality for on-demand: a CRF-style target with -maxrate and -bufsize caps, so easy scenes save bits and hard scenes stay within the player's buffer model. Use CBR-like settings only where a fixed pipe demands it. Fix the keyframe interval (often 2 seconds) and disable scene-cut keyframes for adaptive streaming, so segments align across renditions.
Spend encoder time where views are. A title watched a million times justifies slow presets, AV1, per-title ladders and even per-shot optimisation. Live channels and user uploads usually use fast presets or hardware encoders. Measure with VMAF and with real viewing on target TVs, not only on a laptop screen, and check dark scenes for banding; 10-bit encoding often fixes banding even for SDR content.
When something looks wrong, read the bitstream, not the file name: ffprobe or a stream analyser shows profile, level, GOP structure, frame types and QP per frame. A level too high for a device or a missing IDR at a segment start explains many CTV playback failures.
quiz: What are the four main stages of a hybrid video codec, and which one loses information? || Prediction (intra or inter), transform of the residual, quantisation, and entropy coding. Only quantisation loses information; the other stages are exactly reversible.
Why does the encoder predict from its own reconstructed frames instead of the original source frames? || The decoder only has the reconstructed frames. Predicting from the originals would give the two sides different references, and the differences would accumulate frame after frame into visible drift.
Why are B-frames cheaper than P-frames, and what do they cost? || They predict from both an earlier and a later frame and can average the two, which handles uncovered areas and noise, so residuals are smaller. The cost is reordering: decoding out of display order adds delay and memory.
In H.264 the step size is about 16 at QP 28. What is it at QP 34 and at QP 22, and what happens to bitrate roughly? || The step doubles every 6 QP: about 32 at QP 34 and about 8 at QP 22. A larger step zeroes more coefficients, so bitrate drops a lot (very roughly by half per +6 QP) and quality falls.
A CTV service wants to add AV1 to its H.264 ladder. What should it weigh? || AV1 often saves around 40–50% bitrate versus H.264 at equal quality, but only on devices that decode it in hardware, and the extra ladder costs encoding compute and storage. It pays off for popular titles on newer TVs; the H.264 ladder stays for older devices and ads.

@@ hlsdash
value: HLS (HTTP Live Streaming, Apple, 2009) and MPEG-DASH (Dynamic Adaptive Streaming over HTTP, ISO/IEC, 2012) are how almost all internet video is delivered today. Both turn a video into many small files, a few seconds each, encoded at several bitrates, plus a text manifest that lists them. The player downloads the manifest, then fetches the files one after another with ordinary HTTP requests, and for each file it picks the bitrate the network can carry at that moment. Every CTV app, phone video player and web player that streams films, live sports or news uses one or both.
The problem they solved was scale. Before them, streaming used special servers and protocols (RTSP, RTMP, Windows Media) that kept a stateful connection open for every viewer, were often blocked by firewalls, and could not be cached by the content delivery networks (CDNs) that already served the web. HLS and DASH make video look like web content: immutable files that any HTTP cache can store. One edge server can then serve thousands of viewers from one cached copy, and the same CDN that serves images serves video.
Three lower concepts provide the parts. Video streaming (L1) provides the overall model: encode once into segments, distribute through CDNs, play on the client. Adaptive bitrate (L2) provides the control loop in the player that switches renditions segment by segment, trading picture quality against the risk of stalling. HTTP (L3) provides the transport: stateless GET requests, caching headers, byte ranges and, with HTTP/2 and HTTP/3, many requests over one connection. For the layer above (CTV apps, server-side ad insertion, DRM, live sports), HLS and DASH are the delivery format everything else plugs into.
terms: Rendition (variant, Representation) — one encoding of the content at a given bitrate and resolution.
Encoding ladder — the set of renditions, for example 360p at 0.4 Mbit/s up to 1080p at 6 Mbit/s.
Segment — a short media file, typically 2 to 6 seconds, that starts with a keyframe so it can be decoded on its own.
Multivariant playlist — the top HLS manifest (.m3u8) that lists the renditions with their bandwidth, codecs and resolution.
Media playlist — the HLS manifest of one rendition, listing its segments in order with their durations.
MPD — the DASH manifest, an XML Media Presentation Description of Periods, Adaptation Sets and Representations.
CMAF — the Common Media Application Format (ISO/IEC 23000-19, 2018): fragmented-MP4 segments that both HLS and DASH can use.
Target duration — the maximum segment duration in an HLS playlist; it sets how often live players reload and how far behind live they play.
SSAI — server-side ad insertion: a server rewrites the manifest so that ad segments replace content segments for each viewer.
SCTE-35 — the cable-industry standard for cue messages that mark ad breaks in a stream.
history: In the early 2000s, streaming meant RealNetworks and RTSP, Microsoft Windows Media and, from about 2002, Adobe Flash with RTMP. Each needed its own server software, kept one connection per viewer, and scaled poorly. In the mid-2000s Move Networks showed that video could be cut into small files and fetched over plain HTTP, switching quality between files. Microsoft followed with Smooth Streaming for Silverlight (around 2008), Apple with HLS, and Adobe with HDS (2010).
Apple introduced HLS with iPhone OS 3.0 in 2009, and Roger Pantos published it as an Internet-Draft in May 2009. Its design was deliberately simple: a text playlist of MPEG-TS segments, which any web server could host. Because Apple required HLS for long video streams in iPhone apps, it spread quickly. The IETF published it as RFC 8216 in August 2017, and the second edition is still evolving as draft-pantos-hls-rfc8216bis (revision 22, May 2026).
MPEG answered the format split with DASH, an open standard published as ISO/IEC 23009-1 in 2012; its sixth edition followed in 2026. DASH is codec-agnostic and describes segments with templates instead of listing every file. For years services had to package everything twice: MPEG-TS for HLS and fragmented MP4 for DASH. Apple added fragmented MP4 to HLS in 2016, and Apple and Microsoft proposed CMAF, standardised in 2018, so one set of segments can serve both formats.
Then latency became the issue, because live sports at 20 to 30 seconds behind broadcast were spoiled by phone notifications. Apple announced Low-Latency HLS in 2019 (shipped in 2020) with partial segments and blocking playlist reloads, and the DASH Industry Forum defined low-latency DASH with chunked CMAF. Recent HLS additions include interstitials for ads (2021) and content steering between CDNs (2022).
how: Everything starts with a keyframe-aligned encoding ladder. The encoder (often FFmpeg or a commercial transcoder) produces each rendition with keyframes at the same timestamps, for example every 2 seconds. A packager then cuts each rendition at those keyframes into segments. In CMAF, a rendition has one initialisation segment (codec configuration, with no media) and many media segments, each a moof box (sample table) plus an mdat box (compressed frames). Because every segment of every rendition starts with a keyframe at the same time, a player can stop one rendition after segment 41 and start another at segment 42 without a glitch.
HLS describes this with two levels of text playlists. The multivariant playlist has one EXT-X-STREAM-INF line per rendition with BANDWIDTH (the peak segment bitrate), AVERAGE-BANDWIDTH, CODECS (for example avc1.640028,mp4a.40.2), RESOLUTION and FRAME-RATE, followed by the URI of that rendition's media playlist. Each media playlist starts with EXT-X-TARGETDURATION and EXT-X-MEDIA-SEQUENCE (the number of the first listed segment), then lists segments as EXTINF duration lines followed by URIs. A video-on-demand playlist ends with EXT-X-ENDLIST. A live playlist is a sliding window: the packager appends new segments and drops old ones, and the player reloads the playlist about once per target duration. EXT-X-PROGRAM-DATE-TIME ties segments to wall-clock time, which ad tracking and synchronisation need.
DASH packs the same information into one XML file. A Period is a stretch of content (an ad break can be its own Period). Inside it, an Adaptation Set groups interchangeable streams (all video renditions, or English audio), and each Representation is one rendition with its bandwidth and codecs. Segments are usually described by a template such as video_$RepresentationID$_$Number$.m4s, so the manifest does not grow with the number of segments. For live streams the MPD gives an availabilityStartTime, and the player computes from its own clock which segment number should exist now. That is why DASH players must synchronise their clocks (the UTCTiming element), while HLS players simply read the newest segment from the playlist.
The adaptive bitrate concept runs in the player. After each download the player knows the segment size and how long it took, so it can estimate throughput, often with a moving average. A throughput rule picks the highest rendition whose bitrate is below a safety fraction (say 80%) of the estimate. A buffer rule, such as BBA from Netflix research (2014), maps the seconds of video already buffered to a bitrate: a nearly empty buffer means low quality, a full buffer allows high quality. BOLA (2016), used in dash.js, and model-predictive controllers combine both signals. The buffer is the real safety margin: while it holds 20 seconds of video, a slow download only reduces the margin, but when it reaches zero the picture freezes. Players also avoid switching too often, because frequent quality changes annoy viewers.
HTTP and the CDN carry the load. Media segments never change once written, so they get long cache lifetimes, and an edge server that has one copy can serve every viewer of that rendition. Live media playlists change every few seconds, so they get short lifetimes, often around half the target duration. CDNs collapse simultaneous requests for the same missing object into one request to the origin, which protects the origin at the start of a big live event. Byte-range requests let one large file stand in for many segments. HTTP/2 and HTTP/3 multiplex requests on one connection, which helps low-latency modes that make many small requests.
Latency is mostly a design choice. RFC 8216 tells players not to start closer than three target durations from the end of a live playlist, so with 6-second segments the player sits at least 18 seconds behind the newest segment, plus encoding, packaging and CDN delay. Low-Latency HLS splits each segment into parts (EXT-X-PART, recommended around 1 second). The player asks for the next playlist version with query parameters (_HLS_msn and _HLS_part), and the server holds the request until that part exists (blocking reload). Preload hints let the player request the next part before it is complete. PART-HOLD-BACK must be at least three part durations, so end-to-end latency falls to roughly 3 to 6 seconds. Low-latency DASH achieves similar results by sending CMAF chunks of a segment with chunked HTTP transfer while the segment is still being encoded.
Ads and content protection sit on top of these formats. SCTE-35 cues from the broadcast mark ad breaks; in HLS they appear as EXT-X-DATERANGE tags with SCTE35-OUT and SCTE35-IN attributes (or the older, non-standard EXT-X-CUE-OUT), and in DASH as events in an EventStream. An SSAI server calls an ad decision server (usually returning VAST), then writes a personalised manifest for each viewer in which ad segments replace content segments. EXT-X-DISCONTINUITY tags warn the player that timestamps and encoding parameters change at the splice; in DASH the ad is a separate Period. For DRM, Common Encryption with the cbcs scheme lets one encrypted set of CMAF segments work with Apple FairPlay, Google Widevine and Microsoft PlayReady; HLS signals keys with EXT-X-KEY, and DASH with ContentProtection elements.

example: A CTV app streams a live football match. The ladder has four renditions: 1080p at 6.0 Mbit/s, 720p at 3.0 Mbit/s, 432p at 1.1 Mbit/s and 360p at 0.365 Mbit/s, with 6-second segments and keyframes every 2 seconds. Segment sizes follow from bitrate × duration: 6.0 × 6 = 36 Mbit = 4.5 MB for 1080p, 2.25 MB for 720p, about 0.83 MB for 432p and about 0.27 MB for 360p.
Start-up. The player's throughput estimate is 20 Mbit/s and its rule is "highest bitrate below 80% of the estimate". 0.8 × 20 = 16 Mbit/s, so it picks 1080p. A 1080p segment takes 36 Mbit / 20 Mbit/s = 1.8 seconds to download but adds 6 seconds of video, so the buffer grows by 6 − 1.8 = 4.2 seconds per segment until it reaches the live limit.
A drop. Someone in the house starts a large download and the TV's share falls to 4 Mbit/s. The next 1080p segment now takes 36 / 4 = 9 seconds, so the buffer shrinks by 9 − 6 = 3 seconds. The player measures the slow download and lowers its estimate. 0.8 × 4 = 3.2 Mbit/s, so it picks 720p for the next segment: 18 Mbit / 4 = 4.5 seconds, and the buffer grows again by 1.5 seconds per segment. With 15 seconds of buffer the viewer sees only a softer picture. With only 6 seconds of buffer, the 9-second download would have frozen the picture for about 3 seconds. Low latency and stall resistance pull against each other.
Latency. With 6-second segments, the player stays at least 3 × 6 = 18 seconds behind the newest segment. Add about 2 seconds of encoding and packaging and 1 second of CDN delay: about 21 seconds behind the broadcast. With Low-Latency HLS, 1-second parts and a PART-HOLD-BACK of 3 seconds, the same pipeline runs about 3 + 2 + 1 = 6 seconds behind, or less with a faster encoder.
CDN load. One million viewers watch at 6 Mbit/s on average: 6 Tbit/s leaves the CDN edges. The origin sees far less. If 500 edge locations each fetch each new segment of each of 4 renditions once, the origin serves 500 × 4 / 6 ≈ 333 segment requests per second. The playlists are different: every player reloads its media playlist every 6 seconds, which is 1,000,000 / 6 ≈ 167,000 requests per second, but with a 3-second cache lifetime the edges answer almost all of them.
Now add SSAI. Each viewer gets a personalised playlist that names their own ads, so playlists can no longer be shared from cache. The SSAI service must generate about 167,000 playlists per second, and during an ad break it must also make ad decisions for a million viewers within a few seconds. The segments still scale, because ad segments are shared files; the manifests become the bottleneck.
intuition: Turn a video into a list of small files, and let each player choose the right size for each moment.
The insight is to move intelligence to the edge that has the information. Only the player knows its own throughput, buffer level and screen size, so the player chooses. The server side becomes static files, which the web already knows how to copy, cache and serve at enormous scale. Short segments give the player frequent decision points, and aligned keyframes make every decision point a clean switch.
This mirrors how HTTP made the web scale: stateless requests, immutable resources and caches everywhere. Video did not need a new network; it needed to be cut into pieces the existing network already understood. The cost of the idea is also natural: a player that decides only every few seconds, from data that is a few seconds old, must keep a buffer, and the buffer is exactly what makes these formats run behind live.
mistakes: People often think HLS means MPEG-TS and DASH means MP4. In fact HLS has supported fragmented MP4 since 2016, and with CMAF one set of segments can serve both. The real differences are the manifest format, how live timing is described and how DRM is signalled.
People often think the server adapts the bitrate. In fact the client decides everything; the server only serves files. The exception is SSAI, where a server personalises the manifest, but even then the player still chooses the rendition.
People often think shorter segments are the way to low latency. In fact most latency comes from the hold-back and the player's buffer. Very short segments add requests and keyframes, which costs bitrate, and give ABR less data per decision. Low-Latency HLS keeps normal segments and adds parts inside them.
People often think the BANDWIDTH attribute in HLS is the average bitrate. In fact it is the peak segment bitrate; the average belongs in AVERAGE-BANDWIDTH. Writing the average as BANDWIDTH makes players choose renditions they cannot sustain during complex scenes.
People often think discontinuity tags are optional when splicing ads. In fact, when an ad has different timestamps or encoding parameters, a missing EXT-X-DISCONTINUITY makes many CTV players stall, drop audio or lose sync at the splice.
friction: Latency, stability and cost cannot all be optimised together. Low-latency modes keep small buffers, so they stall more easily on bad networks, and they multiply playlist and part requests, which costs CDN money. Many services still run normal latency for most content and reserve low latency for live sports.
SSAI moves the scaling problem from segments to manifests. Personalised playlists cannot be cached, ad decisions must happen within a few seconds for millions of viewers at the same moment, and ad creatives must be transcoded to match each content ladder before they can be stitched. Tracking is also harder: when the server fetches ads, impression beacons come from the server, and buyers must trust the server's report and the device data it forwards.
CTV devices are fragmented. Roku, Tizen, webOS, Android TV, Fire TV, game consoles and older set-top boxes each have their own player with its own handling of discontinuities, DRM, codecs and manifest edge cases. A stream that plays on one platform can fail on another, and many bugs appear only on real devices.
Two formats and three DRM systems still mean extra packaging, testing and storage, even with CMAF. ABR algorithms also behave badly when several players share one bottleneck: they can oscillate, or fail to share bandwidth fairly. Measuring quality of experience needs data from both the player and the CDN; the CTA-5004 Common Media Client Data standard sends player metrics with each request for this reason.
practice: Package once in CMAF with cbcs encryption and generate both HLS and DASH manifests from the same segments. Use fixed keyframe intervals (often 2 seconds) aligned across renditions, and segment durations that are constant and a whole number of GOPs; Apple recommends 6-second segments with keyframes every 2 seconds.
Write manifests carefully. Set BANDWIDTH to the measured peak and AVERAGE-BANDWIDTH to the average, give exact CODECS strings so devices can reject what they cannot decode, and include EXT-X-PROGRAM-DATE-TIME in live playlists. Apple requires at least six segments in a live playlist and recommends at least 15 minutes of window for live content.
Configure the CDN by object type. Media segments get long cache lifetimes; live playlists get short ones, around half the target duration; use an origin shield and request collapsing for large live events. Monitor the cache hit ratio, because a drop usually means a manifest or URL is accidentally unique per viewer.
For SSAI, condition the content at the encoder so an IDR frame falls exactly on each SCTE-35 splice point, pre-transcode ad creatives to the content ladder, always mark splices with discontinuities or Periods, and pre-compute ad decisions where you can, because break starts create huge request spikes.
Measure quality of experience per device model: start-up time, rebuffering ratio, average bitrate and switch frequency. Join player metrics (CMCD) with CDN logs, and keep a lab of real CTV devices for every release.

value: Automatic content recognition (ACR) identifies what audio or video is playing by computing a compact fingerprint of the signal and matching it against a reference database. Shazam made it famous on phones in 2002–03: hold the phone up to a song and get its name in seconds. On smart TVs, ACR software built into the TV identifies what is on the screen, whatever the source: a cable or satellite box on HDMI, an antenna, a streaming app or a game console. The output is a stream of timestamped facts such as "TV 42 showed channel 23, programme X, from 20:14:02, and ad creative cr998 at 20:15:30".
Those facts power a large part of TV advertising. They give viewership measurement for linear and streaming TV, audience segments ("watched cricket this week"), proof of exposure to linear TV ads, retargeting of linear viewers on CTV, incremental reach (who saw the CTV campaign but not the linear one) and attribution (did exposed households later visit a store or website). ACR data from smart TVs and set-top boxes now feeds TV currency measurement: in January 2025 the Media Rating Council accredited Nielsen's Big Data + Panel, which combines Nielsen's panel with set-top box and smart-TV data from about 45 million US households.
Two lower concepts carry the mechanism. Content recognition (L1) gives the system design: reference capture of every monitored channel and catalogue, a matching service, and rules that resolve ambiguity in time and channel. Audio and video fingerprinting (L2) gives the core technique: features that survive compression, scaling, overlays and noise, packed into short bit strings that can be compared by Hamming distance and found quickly in large indexes. ACR is these two applied to the special conditions of a TV: millions of devices, thousands of live channels, seconds of delay, and strict consent rules.
terms: Fingerprint — a short bit string computed from a few frames or a short piece of audio that stays nearly the same when the content is compressed, scaled or slightly altered.
Reference — fingerprints computed by the ACR provider from known content (live channel feeds, on-demand titles, ad creatives), stored with content ID and timestamp.
Query — the fingerprints a TV sends, with its own timestamps and a device identifier.
Hamming distance — the number of bit positions in which two fingerprints differ; small distance means similar content.
Offset — the time difference between a device sample and the matching reference sample; a stable offset across many samples confirms a match.
Viewing event — a session built from many matched samples: device, content or channel, start time and end time.
Ad library — reference fingerprints of known ad creatives, matched regardless of which channel aired them.
Watermark — an inaudible or invisible code embedded into content at the source; an alternative to fingerprinting that needs the broadcaster's cooperation.
Footprint — the set of opted-in devices that report ACR data; it is large but not a random sample of all homes.
history: Practical audio fingerprinting appeared around 2000. Jaap Haitsma and Ton Kalker at Philips (2002) computed 32-bit sub-fingerprints from energy differences between frequency bands and matched them by bit error rate. Avery Wang of Shazam (paper 2003; the service launched in the UK in 2002 through the short code 2580) hashed pairs of spectrogram peaks and matched by finding many hashes at one consistent time offset. Both worked from short, noisy samples recorded through a phone microphone. Apple acquired Shazam in 2018. Gracenote, which began as the CD database CDDB, built fingerprint and metadata services and was bought by Nielsen in 2017.
TV makers saw that the TV itself was the best place to recognise content, because it sees the final picture from every input. Through the 2010s, Vizio (with its Inscape unit), Samsung, LG, Roku and independent companies such as Samba TV and Alphonso deployed ACR on tens of millions of screens. LG took a controlling stake in Alphonso in 2021, now LG Ad Solutions. Viewing data became an advertising asset: it could show which homes saw a linear TV ad and connect them to CTV and digital campaigns.
Regulators then defined the rules. In February 2017 Vizio agreed to pay $2.2 million to the US Federal Trade Commission and New Jersey for collecting second-by-second viewing data from about 11 million TVs since 2014 without clear consent; the order required prominent disclosure and affirmative opt-in. In December 2025 the Texas attorney general sued Samsung, LG, Sony, Hisense and TCL under the state's deceptive trade practices law, alleging among other things that the TVs captured screen images as often as every 500 milliseconds without proper consent. In February 2026 Samsung agreed to collect ACR data from Texans only with express prior consent; the other cases continue. In parallel, ACR data entered official currency through accredited big-data measurement, so the technology is now judged both on accuracy and on consent.
how: The TV side is a small client in the TV's firmware. It samples the final picture (after decoding and scaling, so it sees cable, antenna, apps and HDMI inputs alike), the audio output, or both, a few times per second. It does not need to send video. It reduces each sample to a fingerprint of a few bytes and uploads batches of fingerprints every few seconds, with the device's timestamps and an identifier. Whether the client runs at all depends on the viewer's opt-in choice in the TV's privacy settings. Audio and video each have weak spots. Audio still works when the picture is covered by a menu or shrunk into a corner, but fails when the TV is muted or when the same music is reused across programmes. Video works while muted but suffers under overlays. Many systems use both and combine the evidence. The TV's clock also matters: matching depends on timestamps, so the client keeps its clock synchronised (for example with NTP) or reports its clock error.
The fingerprinting concept decides what those bytes are. A common video design shrinks the frame to a small grey grid, for example 9 × 8 blocks of average brightness, and sets one bit per block: is this block brighter than its right neighbour? Recompression, resizing, small colour shifts and a change in overall brightness rarely change those comparisons, so the 64 bits stay nearly the same. This is the idea of ordinal measures: compare, do not measure. Audio designs follow Haitsma and Kalker, with 32 bits every 11.6 ms from the signs of energy differences across 33 frequency bands, or Wang, with hashes of spectrogram peak pairs. Features with little information, such as black frames, silence, a static slate or a channel logo on a plain background, give the same fingerprint on many channels, so good systems mark them as low-information and ignore them.
The reference side is where the content-recognition system design lives. A capture farm receives every monitored channel, in every market where local channels and local ads differ, and computes the same fingerprints from the feed in real time, stored with channel and timestamp. A live index holds the most recent minutes or hours of all channels; time-shifted viewing needs longer windows. A separate on-demand index holds fingerprints of films and series. The ad library holds each known creative; new creatives can be discovered automatically, because an unknown 15- or 30-second sequence that repeats across channels is very likely an ad.
Matching must find near neighbours, not only exact equals. For 64-bit video fingerprints, multi-index hashing is a standard method: split each fingerprint into four 16-bit chunks and keep one hash table per chunk position. If two fingerprints differ in at most 3 bits, at least one of the four chunks must be identical (pigeonhole principle), so four exact lookups find every candidate. Each candidate is then checked with an XOR and a population count, which takes a few CPU instructions. Audio landmark hashes are looked up exactly in an inverted index.
Single matches are not trusted; sequences are. The matcher computes, for each candidate reference, the offset between device time and reference time. A real match shows the same offset across many consecutive samples (for example, 4.0 seconds, which is the delay of this home's cable feed compared with the capture farm). Random false matches scatter across offsets. This is the same idea as Wang's histogram of time offsets: count votes per (reference, offset) pair and accept the winner only above a threshold.
Then ambiguity is resolved. The same programme may be simulcast on several channels, syndicated shows appear on many stations, and a national ad can air on every channel at once. The matcher prefers the candidate with the most consistent offset, uses local ad breaks and channel graphics that differ between feeds, and keeps the last confirmed channel when evidence is weak. Ads are recognised against the ad library independently of the channel, so an exposure is recorded even when the channel is uncertain.
Finally, matched samples are turned into events. Sessionisation joins consecutive matches into viewing events with start and end times, merges short gaps (a volume overlay, a menu), drops very short dwell times, and records ad exposures with seconds viewed. Each event carries the device ID, consent state and match confidence. Downstream, identity graphs connect devices to households, and measurement, audience segments and attribution are built in the data platform.

example: Sizing first. Suppose each TV computes a 64-bit video fingerprint twice per second: 16 bytes per second. It uploads a batch every 10 seconds, so 160 bytes of fingerprints plus about 100 bytes of headers. At prime time, 10 million opted-in TVs are on. That is 10,000,000 / 10 = 1 million uploads per second and 10,000,000 × 16 bytes = 160 MB/s of fingerprints. Uploading every 30 seconds instead cuts requests to about 333,000 per second, but the data arrives later.
The reference side is small by comparison. 3,000 channels × 2 fingerprints per second × 1,800 seconds (a 30-minute live window) = 10.8 million fingerprints, or 86 MB, which fits in memory on one machine and can be replicated. An on-demand catalogue of 100,000 hours adds 100,000 × 3,600 × 2 = 720 million fingerprints, about 5.8 GB.
Lookup cost. With four 16-bit chunk tables and 10.8 million entries, each bucket holds on average 10,800,000 / 65,536 ≈ 165 entries (real fingerprints are less uniform, which is why low-information ones are removed). One query makes 4 lookups and checks about 660 candidates. 20 million queries per second × 660 checks ≈ 13 billion XOR-and-popcount operations per second. At roughly 1 ns each that is about 13 CPU cores of pure comparison, before memory costs: easy to spread across a cluster.
Matching one batch. TV d42 sends 20 fingerprints sampled from 20:14:02.0 to 20:14:11.5. Eighteen of them match channel 23 within 3 bits, each at reference times 4.0 seconds earlier (20:13:58.0, 20:13:58.5, ...). The other two match nothing: the viewer opened the volume overlay. Channel 57 also gives 6 matches, at a steady offset of 11 seconds: it simulcasts the same match with a different score graphic, so only frames without graphics match it. A few unrelated channels give single matches at random offsets. The vote is 18 for (channel 23, 4.0 s) against 6 for (channel 57, 11 s), so the matcher records: d42 watched channel 23, "Cricket Final", from 20:14:02.
An ad. At 20:15:30 the fingerprints switch to a sequence that matches creative cr998 in the ad library for 28 of its 30 seconds; the viewer then changed channel. The event records an exposure to cr998 with 93% completion. Over a week, cr998 is matched on 2.4 million distinct TVs out of a 20-million-TV footprint: 12% reach within the footprint. To claim national reach, that number must be weighted against a representative panel, because the footprint over-represents some TV brands, regions and household types.
intuition: Recognise a song in a noisy café from the pattern of its strongest notes, not from every sound wave.
The design is natural once you separate two questions. "Is this the same content?" needs features that ignore what changes in transmission (compression, scaling, brightness, noise) and keep what the content itself fixes (where edges are, which regions are brighter, which frequencies peak when). Comparisons and peaks have exactly that property. "Is this match real?" needs evidence over time, because any single short fingerprint can collide by chance, but a long sequence of matches at one steady offset almost never does. Compact bits make the first question cheap; voting over time makes the second question reliable.
The split of work is natural too. The TV has little spare CPU and no copy of the reference library, so it only computes fingerprints. The server sees every channel at once, so it is the only place where "which of 3,000 channels is this?" can be answered.
mistakes: People often think a TV running ACR uploads what is on the screen. In typical designs it sends fingerprints of a few bytes per sample, not pictures or sound. But the privacy issue is not the size of the fingerprint; it is the viewing log that results, which regulators treat as personal data needing clear consent.
People often think ACR knows the channel directly. In fact it matches content, and the channel is inferred from which reference feed matched. Simulcasts, syndicated shows and national ads make channel attribution uncertain, and streaming apps have no channel at all, only a title.
People often think a match means a person watched. In fact it means the screen displayed the content. The TV may be on in an empty room, and ACR knows a device, not which household members were present. Person-level measurement needs panels or modelling.
People often think ACR data is a random sample of TV homes. In fact the footprint depends on which brands carry ACR, how many owners opt in, and which TVs are connected to the internet. It must be weighted to a representative panel or census before it can describe a national audience.
People often think fingerprints and watermarks are the same. A watermark is a code inserted at the source and read by a decoder, so it identifies content exactly but only where the broadcaster embedded it. A fingerprint needs no cooperation, but it requires a reference database and can be ambiguous.
friction: Consent and regulation are the largest constraints. Viewing history is sensitive, the 2017 Vizio order made affirmative opt-in the norm in the US, and the 2025 Texas lawsuits put consent screens themselves under scrutiny: how many clicks it takes to opt out compared with opting in. State privacy laws, deletion obligations (for example, California's Delete Act platform, which data brokers must process from August 2026) and data minimisation must be built into the pipeline, not added later.
Reference coverage is expensive. The US alone has 210 local TV markets, each with local stations and local ad breaks, so complete coverage means capture hardware or feeds per market, all running continuously. A broken feed silently turns into missing viewing for that channel. Time-shifted viewing, on-demand catalogues and new ad creatives each need their own reference pipeline.
Accuracy has hard cases: TV menus and picture-in-picture overlays, HDR tone mapping that changes pixel values, news tickers, live sports where graphics change constantly, game consoles and apps with no reference content, and identical content on many channels. Precision and recall trade against each other: looser thresholds catch more true matches and more false ones.
Finally, the data must be trusted by buyers and sellers who may disagree. Footprint bias, household-level identity, cross-device matching and the gap between "displayed" and "watched" all need calibration, published methodology and, for currency use, independent accreditation.
practice: Evaluate matching with labelled ground truth across content types (live sports, news, films, ads, games, menus) and report precision and recall separately per type and per channel, because a false ad exposure costs money and a missed one costs coverage. Monitor match rate per channel and market in real time; a sudden drop almost always means a reference feed problem, not a change in viewing.
Make the time model explicit. Store device time, reference time, offset and confidence on every match, use a stable vote threshold, and define sessionisation rules (minimum dwell, gap merging, end of session) in versioned code so results can be reproduced. Version the fingerprint algorithm and the reference indexes together; mixing versions silently lowers match rates.
Keep device clocks synchronised and watch the distribution of offsets per market; a shift in typical offset reveals a clock problem or a feed delay change before match rates fall.
Handle low-information content deliberately: filter black frames, slates, silence and static logos before indexing, and keep a separate path for detecting new ad creatives from repeated unknown sequences.
Treat consent as data. Carry the consent state and its timestamp on every event from ingestion, enforce it at query time, and make deletion requests propagate from raw fingerprints to derived segments and reports. Aggregate as early as the use case allows, apply minimum audience sizes in reports, and use clean rooms when joining viewing data with advertiser outcomes.
quiz: What does the reference side of an ACR system do? || It captures every monitored channel, on-demand title and ad creative, computes the same fingerprints as the TVs, and indexes them with content ID and timestamp for matching.
Why are video fingerprints often built from comparisons between blocks rather than from pixel values? || Compression, scaling and brightness or contrast changes alter pixel values but rarely change which of two neighbouring blocks is brighter. Comparison bits therefore stay stable across transmissions while still differing between different content.
Why does the matcher vote on a consistent time offset over many samples instead of trusting single matches? || Any one short fingerprint can collide with unrelated content by chance. A real match shows the same device-to-reference offset across many consecutive samples, while chance matches scatter, so voting separates them.
With 64-bit fingerprints split into four 16-bit chunks, why does a search with distance threshold 3 need only four exact lookups, and how many candidates come back from 10.8 million references? || If two fingerprints differ in at most 3 bits, at least one of the four chunks has no differing bit, so it matches exactly. Each table has 65,536 buckets, so each lookup returns about 10,800,000 / 65,536 ≈ 165 entries, about 660 candidates in total.
A measurement company must report exposure to a national linear TV ad. When would it prefer an audio watermark over ACR fingerprints? || A watermark embedded by the broadcaster identifies the exact content and source, with no reference database and no channel ambiguity. Fingerprints win when content is not watermarked or broadcasters will not cooperate, and they cover any input the TV displays.

@@ openrtb
value: OpenRTB is the IAB Tech Lab's standard protocol for real-time bidding. When an ad slot becomes available on a website, in an app or in a CTV ad break, a supply-side platform (SSP) or exchange sends a bid request, a JSON document over HTTP POST, to many demand-side platforms (DSPs) at once. Each DSP answers within a deadline, often around 100 to 300 ms, with a price and an ad, or with nothing. The exchange runs an auction, returns the winning ad to the player, and later sends the winner win, billing or loss notices. The whole exchange happens for each impression, millions of times per second across the industry.
Before OpenRTB, every exchange had its own API, and each new DSP connection took custom work. With a shared schema, N sellers and M buyers need N + M implementations instead of N × M. It also gives the whole market one vocabulary for impressions, devices, content, identifiers, privacy signals, deals and the supply chain. The standard is now close to universal. Google retired its own proprietary RTB protocol for Authorized Buyers in 2025 and moved to OpenRTB only, and Prebid Server, the open-source header-bidding server, speaks OpenRTB 2.6 internally.
Two lower concepts give it meaning. Programmatic advertising (L1) supplies the market structure: publishers and their SSPs on one side, advertisers and their DSPs on the other, with identity, measurement and money flowing between them. OpenRTB is the message format of that market. Ad auctions (L2) supply the decision rule: since 2017–2019 most exchanges run first-price auctions with floors and deals, and bidders shade their bids below their true value. OpenRTB carries the inputs to the auction (floors, deals, auction type) and its outputs (the clearing price, inserted into notification URLs).
terms: Bid request — the JSON object an exchange sends to bidders, describing one or more impressions and their context.
Imp — an impression object inside the request: one ad slot (banner, video, audio or native) with its floor and deals.
Bid response — the bidder's answer: bids that name an impression, a price and the ad markup (often VAST XML for video).
tmax — the maximum time in milliseconds the exchange waits for bids, including internet latency.
Bid floor — the minimum price, as a CPM, the seller will accept for an impression.
CPM — cost per mille: the price for 1,000 impressions; OpenRTB prices are CPMs even though each auction sells one impression.
Deal (PMP) — a pre-agreed buyer–seller arrangement, sent as a deal ID, often with its own floor.
nurl, burl, lurl — the win, billing and loss notice URLs a bidder includes in its bid; the exchange calls them with macros such as ${AUCTION_PRICE} filled in.
SupplyChain object (schain) — the list of every company that handled the request between publisher and bidder.
Ad pod — a group of video ads played in sequence in one break, such as a 90-second CTV ad break.
history: OpenRTB began in November 2010 as a pilot of six companies: three DSPs (DataXu, MediaMath and Turn) and three SSPs (Admeld, PubMatic and The Rubicon Project). The first specifications appeared in December 2010 and February 2011 (OpenRTB Mobile 1.0), and version 2.0 in June 2011 unified display, mobile and video. In January 2012, with version 2.1, the IAB adopted it as an official standard.
The 2.x line then followed the market. Version 2.3 (2015) added native ads. Version 2.5 (December 2016) added billing notices (burl), loss notices, header-bidding signals and a source object for the transaction ID. In 2017 the IAB Tech Lab published OpenRTB 3.0 together with AdCOM, a common object model separating the transport from the ad description, but adoption stayed low because 2.x worked well enough.
Fraud and opacity drove the next changes: ads.txt (2017) lists who may sell a publisher's inventory, app-ads.txt (2019) does the same for apps and CTV, and sellers.json with the SupplyChain object (2019) lets buyers trace every hop. At the same time, header bidding pushed exchanges from second-price to first-price auctions (Google completed its move in 2019), so the auction type in requests became mostly "first price".
OpenRTB 2.6 (April 2022) was shaped by CTV. It added ad pods, richer content and network metadata, structured user-agent data and the supply chain in the core, and it deprecated fields such as year of birth and gender. Since 2.6-202211 the version number changes only for breaking changes; updates are dated instead, and bidders must tolerate fields they do not know. Later updates added the Global Privacy Platform signals, metadata on how identifiers were inserted and matched (2.6-202409), and, in 2026, fields that say whether content is live. In November 2025 the IAB Tech Lab proposed the Agentic RTB Framework (ARTF), in which partners' code runs as containers inside the exchange and proposes changes to bid requests; it builds on OpenRTB rather than replacing it.
how: The flow starts with an ad request. A web page, an app SDK, a CTV player or a server-side ad insertion (SSAI) server asks the SSP for ads. The SSP builds a BidRequest. Its main parts are: id (the auction ID); imp, an array of impression objects, each with a format object (banner, video, audio or native), bidfloor and bidfloorcur, and an optional pmp object with deals; site or app (domain or app bundle, store URL, publisher, and a content object with title, series, genre, network, channel and livestream flags); device (user agent, IP, device type, make, model, operating system, advertising ID ifa, limit-ad-tracking flag and coarse geo); user (exchange user ID, the buyer's own user ID if cookie-synced, and extended IDs in eids); regs (COPPA, GDPR, and the Global Privacy Platform string with its section IDs); source (transaction ID and schain); tmax; at (auction type, 1 for first price); and blocked categories and advertiser domains.
The request travels as an HTTP POST, usually over persistent connections and often gzip-compressed, with an x-openrtb-version header. Each DSP has the remaining time to decide. A bidder parses the request, filters to campaigns whose targeting, budget and pacing allow a bid, looks up the device or household in an in-memory store (segments, frequency counts), runs prediction models, prices the bid and replies. The response has the request id, a seatbid array (one per buyer seat), and bids with impid, price (a CPM), adm (the ad markup, such as VAST XML for video) or a URL to fetch it, adomain, crid (creative ID), cat (content categories), dealid when the bid is for a deal, and the notice URLs. Most requests get no bid, and the recommended no-bid answer is an empty HTTP 204 response, which is cheap for both sides.
The auction concept enters at the exchange. It drops late bids, checks each bid against the floor, the deal terms and the publisher's blocked categories and advertiser domains, and ranks the rest. With at = 1 the winner pays its own bid. With at = 2 ("second price plus") it pays just above the second-highest bid. Because first-price winners pay what they bid, DSPs shade bids: they estimate the probability of winning at each price and choose the price that maximises expected value minus cost. Sellers respond with floors, including dynamic floors computed per request.
Notifications close the loop. Bids carry three URLs with macros. The exchange replaces ${AUCTION_PRICE} with the clearing price, ${AUCTION_ID} and ${AUCTION_IMP_ID} with identifiers, and ${AUCTION_LOSS} with a loss reason code (for example 100 for "bid below auction floor" and 102 for "lost to higher bid"). The win notice (nurl) says the bid won the auction. The billing notice (burl) is fired when the ad is actually rendered, such as when a video ad starts, and is the event that should drive billing. The loss notice (lurl) tells losers why they lost, which is the training signal for bid shading. Exchanges often encrypt the price in these URLs so only the buyer can read it.
CTV needed more than single slots, and 2.6 added ad pods. In a structured pod, each slot is its own imp with a fixed duration. In a dynamic pod, one imp describes a break by total duration (poddur), maximum number of ads (maxseq), allowed ad durations, and mincpmpersec, a floor expressed as CPM per second of ad. The bidder may return several bids with their durations (dur), and the exchange fills the break to maximise revenue under duration, competitive separation (for example, only one car advertiser per break) and frequency rules. CTV requests also set devicetype to 3 (connected TV) or 7 (set-top box), carry an IFA with its type, and describe content in detail: network, channel, series, genre and live status. With SSAI, the request comes from a server, so the SSP must forward the viewer's real IP address and user agent instead of the server's, or the impression looks like fraud.
Trust in the supply chain is part of the protocol. The schain object lists each node (the seller's domain asi, its seller ID sid, and whether it handled payment hp). A buyer can check every node against the publisher's ads.txt or app-ads.txt file and each seller's sellers.json file. If the chain is incomplete, or a reseller is not authorised, the buyer can refuse to bid. The volume makes all this an engineering problem: one SSP sending 200,000 requests per second to 20 DSPs emits 4 million requests per second, so SSPs shape traffic, sending each DSP only the requests it is likely to bid on, and DSPs keep request handling to a few milliseconds.

example: A CTV app reaches a 90-second ad break in a live cricket match. The SSAI server asks the SSP to fill it. The SSP sends one bid request with a dynamic pod: imp[0].video has poddur 90, maxseq 4, minduration 15, maxduration 30 and mincpmpersec 0.50. The device object says devicetype 3, the content object says genre cricket and livestream 1, and tmax is 500 ms. The floor per ad follows from the per-second floor: 0.50 × 15 = $7.50 CPM for a 15-second ad and 0.50 × 30 = $15.00 CPM for a 30-second ad.
Three DSPs answer in time. DSP A bids two 30-second ads: A1, a car brand, at $28 CPM, and A2, a telecom brand, at $24. DSP B bids B1, another car brand, 30 seconds at $26, and B2, a snack brand, 15 seconds at $12. DSP C bids C1, 30 seconds at $14.
The exchange checks floors first. C1 is $14 against a $15 floor, so it is rejected; DSP C's loss notice carries reason 100, "below auction floor". Next comes competitive separation: the publisher allows one car advertiser per break, so A1 and B1 cannot both play. Compare by price per second: A1 is 28/30 = 0.93, B1 is 0.87, A2 is 0.80 and B2 is 12/15 = 0.80. The exchange keeps A1 over B1 and fills the break with A1 (30 s), A2 (30 s) and B2 (15 s): 75 seconds and $28 + $24 + $12 = $64 per thousand breaks. B1 loses to A1 at a higher price. The remaining 15 seconds go to a promo for the channel's next match.
Money. This is a first-price auction, so each winner pays its bid. When A1 starts playing, the player or SSAI server fires A1's burl with ${AUCTION_PRICE} = 28.00, which means $28 / 1,000 = $0.028 for this one impression. If the viewer leaves after the first ad, A2 and B2 never start, their burls never fire, and they are not billed even though they won. This is why billing follows burl, not nurl.
Where did $28 come from? DSP A valued A1 at $40 CPM for this household. Its shading model estimated a 60% chance of winning at $28, 85% at $34 and 30% at $22. The expected surplus is 0.60 × (40 − 28) = $7.20 at $28, 0.85 × (40 − 34) = $5.10 at $34, and 0.30 × (40 − 22) = $5.40 at $22. So $28 is the best of the three. The loss notices DSP A receives on other auctions keep this model up to date.
Time. With tmax 500 ms and a network round trip of about 80 ms between the data centres, DSP A must respond within roughly 400 ms; its own internal budget is far smaller (tens of milliseconds), so that it never loses to timeouts. A late answer, even a high one, is simply dropped.
intuition: A stock exchange where the stock is a single ad view, and each trade settles in milliseconds.
The design follows from the deadline. A buyer cannot call the seller back to ask questions, so the request must carry everything needed to price the impression: what the slot is, where it is, who and what device is likely watching, what rules apply, and who handled it on the way. A shared schema is what lets thousands of independent companies trade with each other without bilateral contracts on data formats.
Separating the auction from the notices is equally natural. The auction decides in milliseconds, but whether the ad actually played is known only seconds later, on a device the exchange does not control. So OpenRTB records the decision first and the money second, through URLs that carry the price to the buyer at the moment each fact becomes true.
mistakes: People often think winning the auction means the ad was shown and must be paid for. In fact the win only means the bid was the best. Billing should follow the billing notice (burl) or the impression event, which fires only when the ad starts; in CTV pods, later ads often never play.
People often think tmax is the bidder's computing budget. In fact it includes internet latency in both directions, request parsing and queueing. A DSP that uses all of tmax for computation will time out often, so real bidders keep an internal budget far below it.
People often think OpenRTB 3.0 is the current standard. In fact the industry runs 2.6 with dated updates; 3.0 and AdCOM exist, but saw little adoption, and AdCOM is mostly used for its shared lists of values.
People often think the bid price is the price of one impression. In fact it is a CPM, the price per thousand impressions, while each auction sells one. A bid of 28.00 costs the buyer $0.028 when the impression happens.
People often think the device IP in a CTV request always belongs to the viewer. With SSAI the request may come from the ad-insertion server, and the SSP must forward the viewer's IP and user agent. When this is done wrongly, many households seem to share one IP, which breaks targeting, frequency capping and fraud detection.
friction: Volume and waste are the first problem. The same CTV impression can reach a DSP through several SSPs and resellers, so DSPs see many copies of one opportunity, and the industry pays for computation and bandwidth on requests that mostly receive no bid. Traffic shaping and supply-path optimisation reduce this, but each party filters with its own rules and incomplete knowledge.
Extension sprawl is the second. Much real traffic depends on ext fields that differ by exchange, and exchanges run different 2.x versions and dated updates. Bidders must parse liberally, keep per-exchange mappings, and still risk misreading a field. The standard's own rule, tolerate unknown fields, keeps the market working but slows change.
Signals are shrinking and contested. Consent strings, limit-ad-tracking flags, deprecated personal fields and resettable device IDs mean fewer requests carry stable identifiers.
CTV adds its own pain: pod filling with duration, separation and frequency rules is an optimisation the protocol only partly describes; SSAI hides the device behind a server; and spoofed CTV inventory, where fake servers imitate real apps, has cost buyers heavily. Finally, first-price auctions made pricing opaque: buyers shade, sellers raise floors, and both sides spend effort modelling each other. ARTF and similar ideas aim to cut latency and the number of hops, but they also move outside code into the exchange's data centre, which raises new trust questions.
practice: Parse defensively. Accept unknown fields, map ext fields per exchange, log a sample of raw requests per supply source, and alert when a field's fill rate changes suddenly. Record which 2.6 dated update each partner claims to support.
Budget time explicitly. Start from tmax, subtract the measured round trip and parsing time, and set an internal deadline with a safe margin. Answer no-bids quickly with HTTP 204, use persistent connections and compression, and watch timeout rate per exchange as a first-class metric.
Make money events idempotent. Count spend from burl or impression events, deduplicate by auction ID, impression ID and bid ID, and reconcile daily with each exchange's reports. Keep loss notices: they are the censored data your bid-shading model learns from.
For CTV, support pods properly: return several bids with dur, cat and adomain, respect mincpmpersec, and price per second of ad. Require the device IP and user agent to be the viewer's, and check app-ads.txt, sellers.json and the schain before bidding on CTV supply.
Treat privacy signals as hard rules. Read regs.gpp and gpp_sid (and older GDPR and US privacy fields where present), honour COPPA and limit-ad-tracking flags, and do not rely on deprecated fields such as year of birth. When designing your own SSP integrations, share traffic-shaping feedback with partners so both sides waste fewer requests.
quiz: Which parts of a bid request describe the slot, the inventory, the device, the person and the legal rules? || imp: the slot (format, floor, deals). site or app, with content: the inventory. device: hardware, IP and advertising ID. user: identifiers. regs: COPPA, GDPR and GPP privacy signals.
Why does OpenRTB have both a win notice (nurl) and a billing notice (burl)? || Winning and showing are different events. The win is known in milliseconds, but the ad may never render, for example when a viewer leaves a CTV break early, so billing follows burl, which fires when the ad starts.
Why do bidders shade bids in a first-price auction? || The winner pays its own bid, so bidding the full value leaves no profit. The bidder chooses the price that maximises probability of winning times (value − price), using win and loss history to estimate the win probability.
A dynamic pod has mincpmpersec 0.50. What are the floors for 15- and 30-second ads, and is a $14 CPM bid for a 30-second ad accepted? || 0.50 × 15 = $7.50 and 0.50 × 30 = $15.00 CPM. The $14 bid for a 30-second ad is below the $15 floor, so it is rejected, with loss reason 100.
Should an SSP send every bid request to every connected DSP? || Usually not. It multiplies bandwidth and compute on both sides, while most DSPs bid on a small fraction. Shaping traffic toward likely bidders saves cost but can miss an unexpected high bid, so shaping rules should be tested and shared with partners.

@@ pixels
value: A tracking pixel is an HTTP request that a web page, email, app or video player makes only to report that something happened. The classic form is a 1×1 transparent image whose URL carries the event data: <img src="https://px.example.com/i?ev=imp&cmp=77&cb=93841">. Loading the "image" sends a GET request with the parameters, the browser's cookies for that domain, the user agent and the IP address. The server logs the event and returns a tiny transparent GIF or an empty 204 response. A tag is the larger version: a script that collects more context and sends one or more such requests.
Pixels are the oldest measurement tool on the web and still the base of ad measurement. They count impressions and clicks, report video progress (start, quartiles, complete), record conversions on advertisers' sites, build retargeting audiences, and link identifiers between companies through cookie syncing. In CTV there is no browser and usually no cookie, but the idea is the same: the video player, or the server-side ad insertion (SSAI) server, requests the tracking URLs listed in the VAST ad response at each event. Almost every impression an advertiser pays for is counted by some pixel.
Four lower concepts make it work. HTTP (L3) is the whole transport: a pixel is just a GET or a small POST, with headers, redirects and caching rules. Cookies and device IDs (L2) let the server recognise the same browser or device across requests. Programmatic advertising (L1) defines what must be counted and paid for: impressions, clicks, completions, conversions. Identity resolution (L1) turns the identifiers that pixels carry into households and audiences, by joining pixel logs with identity graphs. For the layers above, pixels are the raw event stream on which reporting, billing, attribution and audience building rest.
terms: Pixel (beacon, web bug) — a request whose only purpose is to report an event; the image, if any, is irrelevant.
Tag — a JavaScript snippet that collects context (page, consent state, screen) and sends one or more pixel requests.
Macro — a placeholder in a tracking URL, such as [TIMESTAMP], [CACHEBUSTING] or ${AUCTION_PRICE}, replaced with a real value before the request is sent.
Cache buster — a random or time-based parameter that makes every URL unique, so no browser or proxy cache answers instead of the server.
First-party and third-party cookie — a cookie for the site the user is visiting, and a cookie for another domain embedded in that site.
Cookie sync — a chain of redirects in which two companies pass each other their IDs for the same browser and store the pair in a match table.
Fan-out — one incoming event forwarded to several partners, either by the client (many pixels) or by a server (server-to-server calls).
VAST tracking events — URLs in a VAST ad response for impression, start, firstQuartile, midpoint, thirdQuartile, complete, click and error.
Server-side tagging — sending events from the advertiser's own server to partners (for example through conversion APIs), instead of from the browser.
Event ID — a unique key per event, used to remove duplicates when the same event arrives more than once.
history: Lou Montulli invented cookies at Netscape in 1994 to give the stateless web a memory, and DoubleClick (1996) used third-party cookies on ad images to recognise browsers across many sites. In 1999 Richard M. Smith's "Web Bug FAQ", published with the Electronic Frontier Foundation, named the invisible 1×1 images "web bugs" and showed that they were also hidden in email. Analytics followed the same pattern: Urchin, bought by Google in 2005 and relaunched as Google Analytics, reported page views by loading a small GIF.
Programmatic advertising multiplied pixels. Ad servers, verification vendors, measurement companies and retargeters each wanted their own pixel on the page, and real-time bidding needed cookie syncing so that exchanges and bidders could recognise the same browser. Pages ended up with dozens of tags, which led to tag managers such as Google Tag Manager (2012). For video, the IAB's VAST (Video Ad Serving Template) standardised tracking events in ad responses; VAST 4.1 added guidance for server-side ad insertion, and the current version is VAST 4.3 (December 2022).
Then browsers and regulators pushed back. Safari's Intelligent Tracking Prevention (2017) restricted and then fully blocked third-party cookies; Firefox's Enhanced Tracking Protection (2019) blocked known trackers by default and later partitioned all third-party cookies per site. Chrome made cookies SameSite=Lax by default in 2020, so third-party cookies must now be marked SameSite=None; Secure. Chrome planned to remove third-party cookies, then decided to keep them, and in October 2025 Google retired most of its Privacy Sandbox replacements. Apple's Mail Privacy Protection (2021) preloads email images through proxies, which made email open pixels unreliable. GDPR (2018), the CCPA and later state laws made consent a requirement for many pixels, and lawsuits followed the Meta pixel on hospital and video websites. Industry moved part of collection to servers: server-side tag managers (2020) and conversion APIs that send events from the advertiser's server.
how: The browser path is simple. When the page or ad renders the image element, the browser builds a GET request to the pixel domain. The request line carries the query string, the event data. The headers carry the user agent, the Referer (limited by the page's Referrer-Policy), and any cookies the browser holds for that domain and is allowed to send in this context. The TCP connection reveals the IP address. The server parses the parameters, reads or sets an ID cookie (Set-Cookie: uid=...; Max-Age=...; SameSite=None; Secure for a third-party context), writes the event to a queue, and answers with a small transparent GIF or 204 No Content and Cache-Control: no-store. The cache buster in the URL makes sure no cache answers a repeat request.
HTTP supplies more than GET. A 302 redirect lets one pixel lead to another, which is how click tracking works: the click goes to the tracker, which logs it and redirects to the landing page. Script tags send data with navigator.sendBeacon or fetch with keepalive, which are POST requests that the browser completes even when the page is closing. Headers decide what the server learns: cookies only if the browser's policy allows them, the full page URL only if the Referrer-Policy allows it.
The cookies concept decides whether the server can recognise the browser next time. A first-party cookie, set on the site's own domain, survives most browser policies. A third-party cookie is blocked by default in Safari, partitioned per top-level site in Firefox (so it cannot follow the user across sites), and still allowed by default in Chrome. Safari also deletes storage written by JavaScript after 7 days without user interaction, and caps such cookies at 24 hours when the visitor arrived through a decorated tracking link. On mobile apps and CTV the identifier is instead the device advertising ID (IFA) when the user allows it, plus the IP address, which often identifies a household.
The identity concept turns these identifiers into people and households, and cookie syncing is its pixel-level mechanism. A page loads the SSP's sync pixel. The SSP reads its cookie (uid A9) and redirects the browser to the DSP's sync URL with ssp_uid=A9. The DSP reads its own cookie (uid Q3) and stores A9 ↔ Q3 in its match table. From then on, when the SSP sends a bid request with user ID A9, the DSP knows it is Q3. Each sync costs one or two redirects in the user's browser, so SSPs limit how many partners sync on each page view.
Fan-out is how one event reaches many parties. In client-side fan-out the page or player fires one pixel per partner, so each partner sees its own cookies and the real device IP, at the cost of more requests on the device and more data leaving it. In server-side fan-out the device fires one pixel, and the receiving server forwards the event to each partner over server-to-server calls with retries. The device does less work and delivery is more reliable, but partners only receive what the server chooses to forward, so the server must apply each partner's consent rules and field allow-list. Long tracking URLs with many macros cause their own problem: some players and ad systems truncate long URLs, so teams sometimes store the parameters server-side and send a short token instead.
The advertising concept defines the events. A display impression pixel fires when the ad renders. A conversion pixel on the advertiser's order-confirmation page reports a purchase, and attribution joins it with earlier impressions and clicks for the same ID within a lookback window. In video, the VAST response lists Impression URLs and TrackingEvents for start, firstQuartile, midpoint, thirdQuartile and complete, plus ClickTracking and Error URLs with an [ERRORCODE] macro. Each wrapper (a VAST that points to another VAST) adds its own trackers, so one CTV ad play can trigger more than ten requests.
CTV with SSAI changes who sends the pixel. In client-side beaconing the player fires the tracking URLs as playback reaches each point. In server-side beaconing the SSAI server fires them, often when it serves or stitches the ad segments. Partners then see the server's IP and user agent unless the server passes the device's own values, in macros or in headers such as X-Device-IP and X-Device-User-Agent. Server-fired events are timed by segment delivery, not by what the viewer actually watched, which is one source of counting differences between parties.
Behind the endpoint sits a data pipeline: edge servers acknowledge quickly and write events to a log such as Kafka; stream jobs validate, filter known bots and invalid traffic, remove duplicates by event ID and enrich with campaign data; the results feed billing, reporting and identity graphs.

example: A CTV app uses SSAI. One 30-second ad's VAST lists three Impression URLs (the ad server, a verification vendor and a measurement vendor) and two URLs for each of the five progress events (start, firstQuartile, midpoint, thirdQuartile, complete). One full play therefore fires 3 + 5 × 2 = 13 tracking requests. An ad break of four such ads fires 52.
Load. During a big live match, 2 million viewers reach the same break. That is 2,000,000 × 52 = 104 million requests, spread over about 2 minutes: 104,000,000 / 120 ≈ 870,000 requests per second. If each request has a 1.5 KB URL and about 0.5 KB of headers, inbound traffic is about 870,000 × 2 KB ≈ 1.7 GB/s, roughly 14 Gbit/s. With server-side beaconing, the SSAI fleet sends all of this, so its outbound HTTP capacity must be planned like a CDN's.
Duplicates. Suppose 1.5% of beacons are retried after a timeout whose first attempt actually arrived, and 0.5% are fired twice by a player bug. Without deduplication, impressions are over-counted by about 2%. For 10 million impressions at $28 CPM, the spend is 10,000,000 / 1,000 × 28 = $280,000, and 2% is $5,600 billed for nothing. The fix is a stable event ID, for example a hash of session ID, pod position, ad ID and event type, and a dedupe step that keeps the first copy.
Dedupe memory. At 1 billion events per day with a 24-hour window, an exact set of 16-byte keys needs about 16 GB plus overhead. Partitioned by key across 32 stream workers, that is about 0.5 GB each, easy to hold in keyed state with a time-to-live. A Bloom filter at 1% would need only about 1.2 GB, but it would wrongly drop 1% of real events as "seen before", which is not acceptable for billing; it is only useful as a pre-filter in front of an exact check.
Reconciliation. The ad server counts 10,000,000 impressions from server-side beacons; the measurement vendor, firing from the player, counts 9,650,000. The 3.5% gap comes from viewers who left before the first frame rendered, players that dropped requests on weak Wi-Fi, and different bot filters. Contracts usually tolerate a small discrepancy; anything larger is investigated by comparing event IDs and timestamps from both sides.
intuition: A doorbell that rings on a server every time someone looks.
The trick is that the web already had a universal, automatic request: every image on a page is fetched without asking anyone. Put information into the image's address, and the act of loading it becomes a message. The browser adds cookies and the network adds the IP address for free, so the receiver learns who, when and from where, as well as what. Everything that came later, scripts, beacons, VAST trackers and server-side APIs, is the same idea with more control over what is sent and by whom.
That is also why pixels are fragile. They depend on the client choosing to make a request and on browser rules about what that request may carry. When browsers, operating systems or laws change those rules, measurement changes with them. Moving collection to servers trades that fragility for a different one: the server knows less about the device, so the device's identity must be passed along explicitly.
mistakes: People often think a pixel is about the image. In fact the image is irrelevant; the request is the message. A 204 response works as well, and scripts, beacons and server-to-server calls are pixels in all but name.
People often think a pixel firing means a human saw the ad. In fact it means some software made a request. Pages fire pixels for ads below the fold, bots load pages, email proxies preload images, and SSAI servers fire beacons when segments are served. Real exposure needs invalid-traffic filtering, viewability measurement and, in CTV, careful timing rules.
People often think server-side tagging removes the need for consent. In fact privacy law applies to the data processing, not to the transport. Hashed emails and device IDs sent from a server are still personal data, and consent signals must be checked before forwarding.
People often think third-party cookies are gone everywhere. In fact Safari blocks them, Firefox partitions them per site, Chrome still allows them by default, and CTV never had them. Identity strategy must be different per environment.
People often think each pixel request arrives exactly once. In fact retries, player bugs, prefetching and network timeouts create duplicates and gaps, so every billing pipeline needs event IDs and deduplication.
friction: Browsers, blockers and operating systems keep removing what pixels can carry: cross-site cookies in Safari and Firefox, short lifetimes for script-written cookies, stripped tracking parameters, blocked tracker domains and mail image proxies. Each change silently lowers match rates and conversion counts, and the loss is hard to measure because the missing events never arrive.
Consent and law are the second constraint. GDPR and ePrivacy rules in Europe, the CCPA and other US state laws, the Video Privacy Protection Act in lawsuits about pixels on video pages, and healthcare privacy rules all limit what may be collected and shared. Deletion is now operational too: California's Delete Act platform requires registered data brokers to process consumer deletion requests at least every 45 days from August 2026, so identifiers collected by pixels must be traceable and deletable in every derived dataset.
Performance and reliability cost money. Dozens of tags slow pages; redirect chains add hundreds of milliseconds on mobile and TV networks; CTV players limit concurrent connections and may drop beacons when an ad break ends. Every party filters differently, so counts never match exactly, and reconciling discrepancies is a permanent task between buyers, sellers and vendors.
Security and privacy leaks are easy to create. Full page URLs in the Referer header can expose search terms or email addresses to third parties, open redirect endpoints used for syncing can be abused for phishing, and a pixel that forwards everything to every partner shares data that consent never covered.
practice: Make the endpoint fast and boring. Answer with 204 or a tiny GIF and Cache-Control: no-store, keep connections alive, terminate TLS at the edge, and write events to a durable log asynchronously; never put a database write in the request path. Track p99 latency and error rate per region.
Design the event schema before the endpoint. Include an event ID, event type, client and server timestamps, campaign, ad, session and pod identifiers, the consent string, the IP (truncated where policy requires) and the user agent. Deduplicate on the event ID in the stream processor with keyed state and a time-to-live; use Bloom filters only as a pre-filter.
Apply consent before fan-out, per partner. Read TCF, GPP and Global Privacy Control signals, keep a field allow-list per partner, store the consent state with the event, and make deletion requests reach raw logs and every derived table.
For fan-out, prefer server-to-server delivery with per-partner queues, retries with backoff and circuit breakers, so one slow partner cannot delay the others. When URLs get long, store the parameters behind a short token rather than risk truncation.
For CTV and VAST, always fill [CACHEBUSTING] and [TIMESTAMP], pass device IP and user agent on server-side beacons, and record whether each beacon was client-fired or server-fired. Reconcile counts with partners daily, keep URLs free of personal data, set a strict Referrer-Policy, and alert on sudden drops (a broken tag) or spikes (bots or duplicates) per placement.
quiz: What does a server receive and return in a classic tracking pixel? || It receives an HTTP GET whose query string carries the event data, with headers (cookies for its domain, user agent, Referer) and the client IP. It logs the event and returns a tiny transparent GIF or a 204 No Content with caching disabled.
Why do tracking URLs include a cache-busting parameter? || Without it, a browser, proxy or CDN might answer a repeated identical URL from cache, and the server would never see the second event. A random or time-based value makes each request unique.
How does a cookie sync let a DSP recognise an SSP's user ID? || The SSP's sync pixel reads the SSP cookie and redirects the browser to the DSP's sync URL with the SSP's user ID in the query. The DSP reads its own cookie from that request and stores the pair in a match table, so later bid requests with the SSP's ID map to the DSP's ID.
An SSAI break of four ads, each with 13 tracking URLs, plays to 2 million viewers over 2 minutes. What request rate must the beaconing system handle? || 4 × 13 × 2,000,000 = 104 million requests in 120 seconds, about 870,000 requests per second, before any retries.
When would you choose server-side beaconing over client-side beaconing in SSAI? || Server-side is more reliable and works on players that cannot fire trackers, but it is timed by segment delivery and hides the device unless the server forwards device IP and user agent. Client-side reflects real playback and shows partners the real device, but loses beacons on weak networks and limited players. Many platforms use client-side where the player supports it and server-side as a fallback.
