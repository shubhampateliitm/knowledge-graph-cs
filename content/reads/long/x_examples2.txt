@@+ kvcache
example: Take a 70B-class model with 80 layers, grouped-query attention with 8 key/value heads of dimension 128, and an FP16 cache (2 bytes per number). Per token, the cache stores K and V: 2 × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes, about 320 KB.
A chat with a 4,000-token history therefore holds about 1.3 GB of cache; a 128,000-token document, about 42 GB. On a node with 8 GPUs of 80 GB (640 GB total), the weights in FP8 take about 70 GB, leaving roughly 500 GB for caches and activations. If the engine gives about 125 GB of that to the KV cache (the rest goes to activations, buffers and headroom), there is room for about 380,000 tokens of active context: for example 95 users with 4,000 tokens each, or only 12 users with 32,000 tokens. Without grouped-query attention (64 KV heads instead of 8), the cache per token would be 8 times larger and the node would serve 8 times fewer users.
Each decode step reads every user's cache once. For the 95 users above, that is about 125 GB per step across the 8 GPUs, roughly 16 GB per GPU; at about 3 TB/s per GPU this takes around 5 ms, plus reading the weights, so steps take on the order of 10–15 ms and each user sees a token every step. Quantizing the cache to FP8 halves its size, allowing about twice as many users or contexts twice as long, at a small accuracy cost; prefix caching lets 95 users who share a 2,000-token system prompt store that prefix once instead of 95 times.

@@+ delta
example: A table events has commits 0 to 41 in _delta_log, with a checkpoint at version 40. A reader opening the table lists the log directory, finds 00000000000000000040.checkpoint.parquet and the JSON files 41.json; it loads the checkpoint (the full list of active files with their statistics) and applies 41.json's actions. It now knows the exact set of, say, 1,250 Parquet files that make up version 41.
A nightly job deletes all rows for user u77 (a privacy request). With deletion vectors enabled, it finds, using file statistics and a scan, the 3 files containing u77's rows, writes a small deletion-vector file for each (a Roaring bitmap of row positions to hide), and attempts to write 42.json containing 'remove file X, add file X with deletion vector DV1' for each of the three files.
At the same moment, a streaming job appends new data and tries to write 42.json too. Only one put-if-absent succeeds; suppose the streaming job wins. The delete job sees that 42.json now exists, reads it, finds that it only added new files and did not touch the 3 files it changed, so there is no conflict; it writes 43.json instead and succeeds. Had the streaming job also rewritten one of those 3 files (for example, by compacting it), the delete job would have failed with a concurrent-modification error and would need to retry from the new version.
Readers that started at version 41 keep reading their snapshot undisturbed. A week later, after the retention period, VACUUM physically removes data files no longer referenced by any retained version; and a later OPTIMIZE rewrites the 3 files without the deleted rows, so the deletion vectors are no longer needed.

@@+ spark
example: Join a 2 TB clicks table with a 50 MB campaigns table and count clicks per campaign name for one day: SELECT c.name, count(*) FROM clicks k JOIN campaigns c ON k.campaign_id = c.id WHERE k.date = '2026-10-25' GROUP BY c.name.
Catalyst pushes the date filter into the Parquet scan, so only that day's partition (say 60 GB, 480 files of about 128 MB) is read, and only the campaign_id column is needed from clicks. Because campaigns is small (under the broadcast threshold, about 10 MB by default, but AQE can decide at runtime that it is small enough after filtering), Spark broadcasts it to every executor; each task builds a hash table of campaigns in memory and probes it with its slice of clicks, with no shuffle of the big table.
The scan produces 480 tasks. Each task partially aggregates counts per campaign name (a few thousand distinct names) before a small shuffle sends partial counts to 200 reducer tasks; AQE notices that the shuffle output is only a few MB and coalesces those 200 partitions into a handful. The final stage merges counts. On a cluster with 200 cores, the scan stage runs in about 3 waves of tasks and the whole query takes tens of seconds.
Now imagine the planner had chosen a sort-merge join because statistics were missing: both sides would be shuffled by campaign_id. If one campaign had 40% of all clicks, one reducer would receive 40% of the data and run for many minutes while others idle. AQE's skew-join handling splits that partition into pieces, and an explicit broadcast hint avoids the shuffle entirely; this is exactly the kind of difference that turns an hour-long job into a minute.

@@+ flink
example: A job counts ad impressions per campaign in 1-minute event-time windows, reading a Kafka topic with 32 partitions at parallelism 32, keyed by campaign, with watermarks allowing 10 seconds of lateness and checkpoints every 60 seconds to object storage.
An impression with event time 10:00:59.8 arrives at 10:01:04 (it was delayed on a phone). The source records the partition offset and forwards the event; keyBy hashes the campaign ID to one of 32 parallel window tasks, which adds 1 to the RocksDB state entry (campaign c7, window 10:00–10:01). The source's watermark lags the highest event time it has seen by 10 seconds; the window task's watermark is the minimum over all its input channels. When that watermark passes 10:01:00, the window fires and emits (c7, 10:00–10:01, 18,412), and the state for that window is cleared.
An event for 10:00:30 arriving at 10:01:20, after the watermark has passed 10:01:10, is late: it is dropped or sent to a side output for correction, depending on configuration. If one Kafka partition receives no data (an idle partition), its watermark does not advance and holds back every window; idleness detection lets the job ignore it.
At 10:02:00 a checkpoint begins: barriers enter all 32 sources, which record their offsets; each window task snapshots its RocksDB state incrementally (only new SST files are uploaded) once barriers from all inputs arrive. The Kafka sink pre-commits its transaction. When all tasks acknowledge, the checkpoint completes and the sink commits, making the 10:01 results visible to read_committed consumers. If a TaskManager dies at 10:02:40, all tasks restore the 10:02:00 checkpoint and sources rewind to its offsets; events after that point are reprocessed, and because their earlier output was never committed, no window is double-counted.

@@+ queueing
example: A Kafka consumer service processes messages with an average service time of 4 ms per message per thread, using 8 threads: total capacity μ = 8 × 250 = 2,000 messages per second. Traffic λ averages 1,400 messages per second, so utilization ρ = 0.7.
Treating it roughly as an M/M/c queue with 8 servers, the average wait before service is small, under a few milliseconds, and total time per message is about 5 ms. Little's law: messages in the system L = λ × W = 1,400 × 0.005 = 7, so about 7 are in flight or waiting at any moment.
Now traffic grows 25% to 1,750 per second (ρ = 0.875). Waiting time rises about fivefold: with Erlang's formula for 8 servers, the average wait in the queue is about 2.5 ms, so about 6.5 ms in total. At 1,950 per second (ρ = 0.975), it reaches about 22 ms, and small bursts create backlogs that take minutes to drain; consumer lag graphs start showing sawtooth patterns. At 2,050 per second, arrivals exceed capacity: the queue (consumer lag) grows without limit until traffic drops or capacity is added.
Variability matters too. If 1% of messages take 200 ms (a slow external call), the average service time rises from 4 to about 6 ms (0.99 × 4 + 0.01 × 200), which cuts the 8 threads' capacity from 2,000 to about 1,340 messages per second, below the 1,400 arriving: the consumer can no longer keep up, and the slow messages also block threads so everything behind them waits; this is why splitting slow work into its own queue, or adding timeouts, can cut tail latency dramatically without adding capacity. The capacity plan that follows: keep peak utilization near 60–70%, and alert on lag growth rather than on CPU.

@@+ infotheory
example: A column records the device type of 1 billion TV events: 'smart_tv' 70%, 'stick' 20%, 'console' 9%, 'other' 1%. Stored as strings of about 8 bytes, that is 8 GB.
The entropy is H = −(0.7 log₂ 0.7 + 0.2 log₂ 0.2 + 0.09 log₂ 0.09 + 0.01 log₂ 0.01) ≈ 0.36 + 0.46 + 0.31 + 0.07 ≈ 1.2 bits per value. No lossless code can average fewer than 1.2 bits per event if events are independent, so the theoretical minimum is about 1.2 billion bits, roughly 150 MB. A dictionary with 2-bit codes needs 250 MB; a Huffman code (1 bit for smart_tv, 2 for stick, 3 for the others) averages 0.7 × 1 + 0.2 × 2 + 0.1 × 3 = 1.4 bits, about 175 MB. If the data is sorted by device type, run-length encoding collapses it to a handful of runs, because sorting creates structure that independent-symbol entropy does not capture.
The same arithmetic explains model training. A language model that assigns probability 0.25 to the actual next token pays −log₂ 0.25 = 2 bits of loss for it; averaging over all tokens gives the cross-entropy, and perplexity 2^H is the 'effective number of choices' the model hesitates between. Lowering the loss from 2.0 to 1.8 bits per token means the model's predictions now compress text about 10% better.

@@+ vmem
example: A process reads the address 0x7f3a_1c2d_5e48. The CPU splits the 48-bit virtual address into four 9-bit indexes and a 12-bit offset (for 4 KB pages). It first checks the TLB; on a miss, it walks the page tables: the CR3 register points to the top-level table, index 1 selects an entry pointing to the next table, and so on through four levels, each a memory access (often cached in L1 or L2). The final entry gives the physical frame, say 0x0005_8a3f_2000, plus permission bits; the offset 0xe48 completes the physical address. The translation is cached in the TLB for next time.
Suppose the final entry is marked not present because the page was never touched. The CPU raises a page fault; the kernel checks that the address belongs to a valid mapping (for example, the heap), allocates a free frame, zero-fills it, writes the page-table entry and returns; the instruction is retried and succeeds. That first touch cost a few microseconds. If the page had been swapped out or belonged to a memory-mapped file not in the page cache, the kernel would have read it from disk: tens of microseconds on NVMe, milliseconds on a hard disk.
With 2 MB huge pages, one TLB entry covers 512 times more memory, so a 64 GB database buffer pool needs about 32,768 entries instead of 16 million, and TLB misses largely disappear: the reason databases and JVMs often benefit from huge pages.

@@+ lightspeed
example: A database has replicas in Mumbai, Singapore and Frankfurt and uses a consensus protocol that needs a majority (2 of 3) to commit each write. The leader is in Mumbai.
Fibre distances along real cable routes are roughly 4,000–5,000 km from Mumbai to Singapore and 6,500–8,000 km to Frankfurt. At about 200,000 km/s, the one-way propagation time is at least 20–25 ms to Singapore and 33–40 ms to Frankfurt, and measured round trips are typically about 55–70 ms and 110–130 ms. A commit must wait for the fastest other replica (Singapore) to acknowledge: at least one round trip, about 60 ms, plus disk flushes. A client in Mumbai therefore sees every write take 60 ms or more, no matter how fast the servers are.
If the leader moves to Frankfurt (for example, after a failover), the nearest other replica is Mumbai or Singapore, over 110 ms away, and a client in Mumbai now pays the trip to Frankfurt as well: well over 200 ms per write. This is why multi-region databases let you pin leaders (or leaseholders) near the users who write most, and why many systems keep writes local and replicate asynchronously.
On a chip the same physics appears at a smaller scale: at 4 GHz one cycle is 0.25 ns, during which a signal in an on-chip wire travels only a few millimetres to centimetres, so a cache far across the die costs several cycles to reach.

@@+ rag
example: An internal assistant answers 'What is our retention policy for raw impression logs in the EU?'. The corpus has 40,000 documents split into about 500,000 chunks of 300–500 tokens, each embedded (1,024 dimensions) in an HNSW index, with a BM25 index alongside and metadata such as region, document date and permissions.
The question is embedded; vector search returns the 50 nearest chunks, and BM25 returns 50 chunks matching 'retention', 'impression' and 'EU'. Reciprocal rank fusion merges the two lists; a filter removes chunks the user cannot access and documents marked superseded. A cross-encoder re-ranker scores the remaining 80 chunks against the question and keeps the top 6. The prompt contains instructions ('answer only from the sources, cite chunk IDs, say if the answer is not present'), the 6 chunks with their titles and dates, and the question: about 4,000 tokens.
The model answers: 'Raw impression logs from EU devices are kept for 30 days, then aggregated [doc 812, §3]; the policy was updated in March [doc 1044]'. The application checks that the cited chunk IDs were in the context and shows links. Suppose the answer was wrong because the current policy lives in a slide deck that was never indexed: retrieval recall, not the model, failed. An evaluation set with expected source documents catches exactly this kind of error, which is why RAG teams measure retrieval separately from generation.

@@+ vectorsearch
example: A catalogue of 100 million products is embedded with 768 dimensions in float32: 768 × 4 bytes ≈ 3 KB per vector, about 300 GB in total, too much for one machine's RAM. Exact search for one query would compute 100 million dot products, roughly 77 billion multiply-adds, about a second of CPU time even with SIMD.
With product quantization (96 sub-vectors of 8 dimensions, each encoded with 1 byte), each vector shrinks to 96 bytes and the whole collection to about 9.6 GB, which fits in memory. An IVF index clusters the vectors into 65,536 lists; a query compares itself with the cluster centres, then scans only the 64 closest lists (about 100,000 vectors) using lookup tables for fast approximate distances, takes the best 500 candidates and re-ranks them with exact distances from full vectors on SSD. Latency: a few milliseconds; recall at 10 might be around 0.9–0.95, measured against exact search on sample queries.
An HNSW index instead would offer higher recall at very low latency but need the full vectors plus graph links (about 64 neighbours × 4 bytes per vector), well over 300 GB here, so it would have to be sharded across machines. Adding a filter 'in stock and in India' that matches only 2% of products makes graph search harder: the walk may find few qualifying neighbours, so systems use filter-aware traversal, pre-filtered partitions or larger candidate lists. These trade-offs (memory, recall, latency, filters) are what choosing a vector index is really about.

@@+ cachelayer
example: A user-profile API serves 50,000 requests per second; profiles live in PostgreSQL, where a lookup costs about 2 ms and the database comfortably handles 5,000 lookups per second. Popularity is skewed: 20% of profiles get 90% of traffic.
With a Redis cache-aside layer and a 10-minute time-to-live, suppose the hit rate is 92%. The database then sees 8% of traffic, 4,000 lookups per second, within its capacity, and average latency is about 0.92 × 0.3 ms + 0.08 × 2.3 ms ≈ 0.46 ms. If the hit rate drops to 80% after a release changes key names, the database sees 10,000 lookups per second, twice its capacity, and the whole API slows down: a cache's hit rate is a capacity number, not just a latency number.
Now a celebrity's profile expires at 18:00:00 while receiving 3,000 requests per second. Without protection, every request in the next 2 ms misses and goes to the database: a thundering herd. With request coalescing, the first miss rebuilds the entry and others wait for it (or get the slightly stale value), so the database sees one query. To avoid many keys expiring together after a bulk load, the time-to-live is set to 10 minutes plus a random 0–60 seconds.
When a user updates their profile, the API writes PostgreSQL and deletes the cache key; a CDC consumer also deletes the key on every committed change, covering writes from other services and closing the race where an older read re-populates the cache after the update.

@@+ exactlyonce
example: A Kafka Streams application reads clicks, counts clicks per campaign per minute and writes the counts to an output topic, with processing.guarantee = exactly_once_v2.
For each batch of input records, the application's transactional producer begins a transaction, updates the local state store (whose changes are also written to a changelog topic inside the same transaction), writes result records to the output topic, and adds the consumed input offsets to the transaction. Then it commits. All of these writes become visible together, or not at all.
Suppose the process crashes after writing results but before committing. On restart, the transaction coordinator aborts the open transaction. Older Kafka Streams versions fenced a stale instance through a shared transactional ID per task; with exactly_once_v2 (KIP-447, the only mode since Kafka 4.0), each stream thread has one transactional producer, and a zombie is fenced because its consumer-group generation, sent with the offsets in the transaction, is out of date. Consumers of the output topic with isolation.level = read_committed never see the aborted results. The input offsets were not committed, so the application re-reads those clicks, rebuilds state from the changelog and produces the counts again, this time committing. Each click affects the visible counts exactly once.
Now suppose the same application also called an external billing API for each click. That call is not part of the Kafka transaction: after the crash and replay, the API would be called twice. To make it safe, the application must send an idempotency key (for example, the click's topic, partition and offset) so that the billing service ignores the duplicate, or write a 'billing request' event to Kafka transactionally and let a separate idempotent consumer call the API.

@@+ partitioning
example: A topic carries viewing events from 30 million TVs, about 200,000 events per second. Keying by device ID with 64 partitions gives each partition about 3,100 events per second, evenly spread because device IDs hash uniformly, and keeps each device's events in order, which a sessionization job needs.
Keying by channel instead would be a mistake: the top channel during a cricket final might account for 25% of all events, so one partition would get 50,000 events per second while dozens get almost nothing; its consumer would fall behind and the parallelism of the other 63 partitions would be wasted. If the downstream job truly needs channel grouping, it can repartition by channel with pre-aggregation (count per channel per second inside each device-keyed task first, then shuffle the small partial counts).
Changing 64 partitions to 96 later moves most keys to different partitions (hash modulo 96 differs from modulo 64), so per-device ordering breaks across the change unless producers pause and consumers drain. Choosing 96 or 128 at the start, sized for expected growth and peak consumer parallelism, avoids that migration. In a lakehouse table built from the same data, partitioning by date (365 partitions per year) and clustering by device ID works well; partitioning by device ID would create 30 million tiny partitions.

@@+ llmserving
example: A support assistant receives 20 requests per second at peak. Each request has a 3,000-token prompt (a 2,000-token shared system prompt plus 1,000 tokens of conversation) and produces 300 output tokens. The target is time to first token under 1 second (p95) and at least 30 tokens per second per user.
Load: 20 × 300 = 6,000 output tokens per second to generate, and 20 × 3,000 = 60,000 prompt tokens per second to prefill. With prefix caching, the shared 2,000-token system prompt is computed once and reused, cutting prefill work to 20,000 tokens per second. On one GPU server running a mid-size model, prefill might process tens of thousands of tokens per second, and decode at batch size 64 might produce about 2,500 tokens per second in total (about 40 per user). Concurrency by Little's law: each request decodes for about 300 / 40 = 7.5 seconds, so 20 × 7.5 = 150 requests are in flight; at 64 per server, that needs 3 servers, plus headroom for peaks: perhaps 4.
Without continuous batching, requests would wait for whole batches to finish, and time to first token would blow past the target. Without chunked prefill, a single 30,000-token request (someone pasting a log file) would freeze decoding for everyone on its server for a noticeable fraction of a second. Quantizing to FP8 might let each server hold batch 96 instead of 64, cutting the fleet to 3 servers: the kind of decision that turns directly into cost per million tokens.
