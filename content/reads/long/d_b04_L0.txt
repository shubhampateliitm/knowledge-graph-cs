@@ duckdb
value: DuckDB is an analytical SQL database that runs inside your program. There is no server to install and no network connection: you import a library in Python, R, Java, Node.js, Rust or the command line, and queries run on threads inside your own process. It reads Parquet, CSV and JSON, pandas and Polars DataFrames, Arrow tables, its own single-file format and files on S3, and it answers analytical queries using every core of the machine.
The problem it solves is the gap between two bad options. For data between about 1 GB and a few hundred GB, pandas is single-threaded, loads everything into memory and has no query optimizer. SQLite is embedded and easy, but it stores rows and processes one row at a time, which is slow for aggregations over millions of rows. A server warehouse or a Spark cluster is fast, but it needs setup, costs money while idle, and moves results through a client protocol that can be slower than the query itself. DuckDB keeps the ease of SQLite and the execution design of a modern warehouse; it even runs in the browser as DuckDB-Wasm.
It stands on two lower concepts. OLAP analytics (L1) gives the design goal and the techniques: columnar storage, compression, vectorized operators and parallel scans, all tuned for queries that read many rows but few columns. C / C++ (L0) gives the control needed to build that engine as a small, dependency-free library: exact memory layouts, a custom buffer manager, no garbage-collection pauses, tight loops that compilers turn into SIMD instructions, and one codebase that compiles for servers, laptops and WebAssembly. The timing also matters: a 2026 laptop has 8 to 16 cores, 32 to 64 GB of memory and an NVMe disk that reads 3 to 7 GB/s, which is enough for most analytical datasets that companies actually query.
terms: In-process (embedded) database — a database that runs as a library inside the application's own process, so queries and results never cross a network.
Vector — DuckDB's unit of data in execution: up to 2,048 values of one column, processed together.
Vectorized execution — each operator processes a whole vector in one tight loop instead of one row per function call.
Pipeline — a chain of operators that data flows through without stopping; it ends at a pipeline breaker such as a hash-table build, aggregation or sort.
Morsel — a small chunk of input (for example one row group) handed to a worker thread; threads take morsels until none are left.
Row group — a horizontal slice of a table (about 122,880 rows in DuckDB's own format) whose columns are stored and compressed separately.
Projection and filter pushdown — reading only the columns a query needs, and skipping data whose stored min/max statistics prove the filter cannot match.
Spilling (out-of-core) — writing intermediate data such as hash-table partitions to temporary files when memory runs out, so the query still finishes.
MVCC — multi-version concurrency control: each transaction sees a consistent snapshot while others change the data.
history: DuckDB comes from the Database Architectures group at CWI, the Dutch national research institute for mathematics and computer science in Amsterdam, which built MonetDB (Martin Kersten, Peter Boncz and others, from the 1990s), one of the first column stores, and MonetDB/X100 (Boncz, Zukowski and Nes, CIDR 2005), which introduced vectorized execution and later became the commercial Vectorwise engine. Hannes Mühleisen and Mark Raasveldt first embedded MonetDB inside R and Python (MonetDBLite) and learned that a server design does not embed well. Their 2017 VLDB paper "Don't Hold My Data Hostage" also showed that sending a large result through a database client protocol such as ODBC or JDBC could take longer than computing it. Both lessons pointed to a database designed from the start to live inside the client.
They started DuckDB in 2018 and presented version 0.1 as a demo paper at SIGMOD 2019 in Amsterdam. In 2021 the engine moved from pull-based to push-based execution, which made parallel operators easier to write. DuckDB Labs, a CWI spin-off company, was announced in July 2021, and the non-profit DuckDB Foundation was set up the same year to hold the intellectual property under the MIT license. MotherDuck, a separate company that runs DuckDB as a cloud service, partnered with DuckDB Labs in November 2022.
Version 1.0 (June 3, 2024) promised a stable, backward-compatible storage format. Version 1.4.0 (September 2025) was the first long-term support (LTS) release. DuckLake, a lakehouse table format that keeps metadata in an ordinary SQL database and data in Parquet, was introduced in May 2025 and reached 1.0 in April 2026. Version 1.5 followed in March 2026. In August 2026 the company, renamed DuckLabs, announced that it would join Amazon Web Services; the projects stay MIT-licensed under the Foundation. DuckDB 2.0.0 LTS was released on October 21, 2026, with a client-server mode (the Quack protocol), asynchronous I/O, a new PEG-based SQL parser, a VARIANT type, triggers, and a new storage format that older versions cannot read. It is supported until at least October 2027.
how: A query starts in your process. In Python, `duckdb.sql("SELECT ...")` hands the text to the library, which parses it, binds names to tables and columns, and builds a logical plan. A name in the SQL that is not a table can be resolved as a variable of the host program (a "replacement scan"), so `SELECT * FROM df` reads a pandas or Polars DataFrame directly. Arrow data is read in place without copying, and results come back as Arrow, a DataFrame or NumPy arrays, so nothing is serialized over a socket.
The optimizer then rewrites the plan. It pushes filters and column lists down to the scans, unnests correlated subqueries into joins (the method of Neumann and Kemper, 2015), and chooses a join order with a dynamic-programming search driven by cardinality estimates.
Execution is vectorized, which is the core lesson of OLAP analytics. Data moves between operators as DataChunks: a set of column vectors with up to 2,048 values each. A filter does not copy rows; it produces a selection vector, a list of the positions that passed. Each operator runs one loop over a whole vector, so the cost of interpretation (a virtual call, a switch on the data type, a check for nulls) is paid once per 2,048 values instead of once per row. A vector of 2,048 eight-byte numbers is 16 KB, small enough to stay in the CPU's L1 or L2 cache while several operators work on it. This is where C++ adds value: templates generate one specialised loop per data type, and the compiler turns those loops into SIMD instructions. Vectors also have compressed forms (constant, dictionary, sequence) that operators can use without expanding them first. Strings are 16-byte records: strings of up to 12 bytes are stored inline, and longer ones keep a 4-byte prefix plus a pointer, so most comparisons never follow the pointer.
Parallelism uses push-based pipelines and morsels, following Leis and colleagues (SIGMOD 2014). The physical plan is cut into pipelines at pipeline breakers: building a hash table for a join, a hash aggregation, a sort. Each pipeline has a source (a table or file scan), streaming operators (filter, projection, hash-join probe) and a sink. A pool of worker threads, one per core by default, takes morsels from the source, pushes each vector through the operators, and writes into a thread-local part of the sink, for example a private hash table for a group-by. When the source is empty, the sink combines the local results once. Fast threads simply take more morsels, so uneven data balances itself without a central planner. A pipeline that depends on another (the probe side of a join needs the finished build side) waits for it.
Storage is a single database file plus a write-ahead log. Tables are split into row groups of about 122,880 rows. Inside each row group every column is stored separately in blocks of 256 KB and compressed with a light scheme chosen per segment (run-length, bit-packing, dictionary, FSST for strings, ALP for floats, Zstd and others). Each segment keeps min/max statistics (a zone map), so a scan can skip segments that cannot match a filter. Transactions use MVCC in the style of the HyPer system: a writer changes data in place and keeps the old versions in undo buffers, so readers see their snapshot. Many threads and connections inside one process can read and write at the same time, with optimistic conflict detection. Across processes, only one process may open a file for writing; others can open it read-only.
External data is read by the same engine. The Parquet reader reads only the column chunks a query needs and skips row groups using Parquet's min/max statistics. Since DuckDB parallelises a Parquet scan by row group, a file with one huge row group is read by one thread. The httpfs extension reads S3 and HTTP with range requests, and 2.0 keeps many reads in flight in the background, which matters when each object-storage request takes tens of milliseconds. Other extensions add Iceberg, Delta Lake, DuckLake, spatial types, and live PostgreSQL, MySQL and SQLite databases.
Finally, the large operators work beyond memory. A memory limit (80% of physical RAM by default) is enforced by one buffer manager that controls both table data and temporary data. Hash aggregation and hash joins partition their data by hash bits (radix partitioning); when memory is short, they write some partitions to a temporary directory and process them later, one at a time. Sorting and window functions spill in a similar way. A query on 300 GB of data can therefore finish on a machine with 32 GB of memory, more slowly but without failing.

example: An analyst has 30 days of ad impressions in Parquet: 300 million rows, 20 columns, about 36 GB on disk (roughly 120 bytes per row). The files are written in date order with row groups of 1 million rows, so there are 300 row groups. She runs `SELECT campaign_id, count(*), sum(cost) FROM 'imps/*.parquet' WHERE event_date >= DATE '2026-10-20' GROUP BY campaign_id` on a laptop with 10 cores.
Step 1, projection pushdown. The query uses 3 of the 20 columns. Suppose the compressed sizes are 1.5 bytes per row for campaign_id (dictionary encoded), 4 bytes for cost and 0.1 bytes for event_date (long runs of the same date). That is 5.6 bytes per row, so the 3 columns hold 300 million × 5.6 ≈ 1.7 GB, instead of 36 GB for the whole files.
Step 2, filter pushdown. The filter keeps the last 7 of 30 days. Each row group's min and max date is in the Parquet footer, so the reader skips the 230 row groups whose maximum date is before October 20, without reading them. About 70 row groups remain: 70 million rows and about 70 × 5.6 MB ≈ 390 MB to read. At 3 GB/s from NVMe, that is about 0.13 seconds of I/O.
Step 3, morsels. The 70 remaining row groups are morsels for 10 threads, about 7 each. Each thread decodes its morsel into vectors of 2,048 values, applies the date filter as a selection vector, and adds each row to its own small hash table keyed by campaign_id. With 5,000 campaigns, a local table is roughly 5,000 × 24 bytes ≈ 120 KB, which fits in the core's L2 cache. At the end the ten tables are merged: 50,000 entries, which takes well under a millisecond.
Step 4, why vectors matter. 70 million rows make about 34,000 vectors. If each of 3 operators pays about 100 ns of interpretation overhead per call, the overhead is 34,000 × 3 × 100 ns ≈ 10 ms. A tuple-at-a-time engine that pays even 20 ns per row per operator spends 70 million × 3 × 20 ns ≈ 4.2 seconds on the same overhead. The actual arithmetic (comparisons, hashing, additions) is similar in both designs; vectorization removes the bookkeeping around it.
The whole query takes well under a second. In pandas, the 3 columns for all 300 million rows would first be loaded into memory (about 7 GB as 8-byte values) and grouped on one core, which takes tens of seconds. If the data were not sorted by date, step 2 would skip almost nothing and DuckDB would read the full 1.7 GB: file layout matters as much as the engine.
intuition: DuckDB is a warehouse engine that you carry inside your program like a library, instead of a service you must visit over the network.
The design is natural once you look at where time goes in analytics on one machine. The data is local or in your process already, so a server only adds copying and a protocol. The queries read many rows and few columns, so columns, compression and min/max statistics remove most of the I/O. The remaining cost is the CPU loop, so vectors make every loop long and cheap, and morsels keep every core busy without a complex scheduler. Each piece removes one specific cost; together they make a laptop behave like a small cluster. SQLite showed that a database does not need a server when one application owns the data; DuckDB applies the same idea to analytics.
mistakes: People often think DuckDB is an in-memory database. In fact it has a persistent single-file format with a write-ahead log, it reads data from disk and object storage, and its large operators spill to disk when memory is short. In-memory mode is only one option.
People often think "embedded" means small or single-threaded. In fact DuckDB uses one worker thread per core by default and parallelises scans, joins, aggregations and sorts. Embedding removes the server, not the parallelism.
People often think several programs can write to the same DuckDB file at once, as with a server database. In fact only one process can open a file for writing; other processes can only read it. Many threads inside that one process can write. For many independent writers you need a server in front (DuckDB 2.0's server mode or MotherDuck) or a shared format such as DuckLake.
People often assume querying Parquet is as fast as querying DuckDB's own format. The DuckDB documentation reports TPC-H queries roughly 1.1 to 5 times slower on Parquet, because the native format has finer statistics and cheaper decoding. Parquet is the right choice for sharing data between tools; the native file is faster for repeated queries.
friction: Single-node is the main limit. One machine bounds the cores, memory bandwidth and local disk, and object storage throughput is bounded by one network interface (often 10 to 25 Gbit/s on cloud machines). Spilling keeps large queries alive but can make them many times slower, and a query with a poor join order can still exhaust the temporary disk.
Concurrency is limited by design. One writer process per file is fine for a notebook or a pipeline step, but a team that wants a shared, always-on database needs the newer server mode, MotherDuck, or DuckLake with a separate catalog database. These are recent (2.0 in October 2026, DuckLake 1.0 in April 2026), so operations knowledge is still young. Small, frequent single-row inserts and updates are slow compared with an OLTP database; DuckDB expects batches.
Running inside the host has costs too. DuckDB's memory competes with the host program's memory, a crash in the engine can take down the host, and the 80% default memory limit may be too high on a shared machine. Upgrades need care: databases written by 2.0 cannot be opened by 1.x, so every reader of a file must upgrade together. Finally, the optimizer depends on estimates; for complex queries over raw files without statistics, it can still choose a bad join order.
practice: Use DuckDB for single-machine analytics: exploring Parquet in object storage, local dbt development, transformation steps inside pipelines, test fixtures and analytics inside applications. Keep Spark, Databricks or a warehouse for multi-terabyte joins, many concurrent writers and shared governance.
Lay out files for it. Aim for Parquet row groups of 100,000 to 1 million rows and files of 100 MB to 10 GB, and have at least as many row groups as threads. Sort or partition by the columns you filter on most (usually date), so min/max statistics can skip data. Avoid thousands of tiny files on S3, because each file costs requests and footer reads.
Control resources explicitly when DuckDB shares a machine: `SET memory_limit = '16GB'`, `SET threads = 8`, and `SET temp_directory = '/fast/ssd/tmp'`. For large exports where row order does not matter, `SET preserve_insertion_order = false` lowers memory use. Read `EXPLAIN ANALYZE` output to see per-operator time and row counts, which shows whether filters were pushed into the scan.
For loading, use `COPY` or the Appender API instead of row-by-row INSERT. Write partitioned output with `COPY ... TO 'out' (FORMAT parquet, PARTITION_BY (event_date))`. In Python, move data as Arrow (`.arrow()`, `.pl()`) to avoid copies. Pin the DuckDB version in production, test 2.0 on a copy before upgrading shared files, and choose LTS releases (1.4, 2.0) for long-lived deployments.
quiz: Where does a DuckDB query run, and what does this remove compared with a client-server database? || On threads inside the application's own process. There is no server, network hop or client protocol, so results are handed over as Arrow or DataFrames without serialization.
Why does processing vectors of 2,048 values make DuckDB much faster than a tuple-at-a-time engine? || Each operator's interpretation overhead (function call, type switch, null checks) is paid once per vector instead of once per row, and tight loops over one column stay in cache and use SIMD.
How do morsels and pipelines let DuckDB use all cores without a central scheduler? || The plan is cut into pipelines at hash builds, aggregations and sorts. Threads repeatedly take a morsel of input, push it through the operators into a thread-local sink, and the sinks merge once at the end; faster threads just take more morsels.
A Parquet dataset has 400 row groups of 1 million rows each, sorted by date over 40 days. A query filters on the last 5 days and reads 3 columns of 4 bytes per row compressed. Roughly how much data must be read? || About 5/40 of the row groups survive the min/max check, so 50 row groups or 50 million rows. At 3 × 4 = 12 bytes per row, that is about 600 MB.
A team of ten analysts wants to share one DuckDB database file on a network drive and write to it from their own laptops. What would you advise? || Only one process can write a DuckDB file, so this will fail. Put one server in front (DuckDB 2.0 server mode or MotherDuck), use DuckLake with a shared SQL catalog and Parquet in object storage, or move shared tables to a warehouse.

@@ polars
value: Polars is a DataFrame library: you load a table, filter it, join it, group it and compute new columns, from Python (its main audience), Rust, R or Node.js. It does the same job as pandas, but it is built like a query engine. Its core is written in Rust, it keeps data in Apache Arrow's columnar memory layout, it runs on all CPU cores, and it can delay work until it has seen the whole query, so an optimizer can remove unneeded reads and computations first.
The problem it addresses is that pandas, the standard DataFrame tool for a decade, was designed for data that fits easily in memory on one core. pandas runs each operation immediately and in full, mostly on one thread. It often copies data, and anything not covered by its vectorized functions falls back to slow Python loops. On a 16-core laptop with tens of gigabytes of data, most of the machine sits idle while memory runs out. Polars keeps the DataFrame style that data scientists like, but runs it with the methods of analytical databases. On the Polars team's PDS-H benchmark (derived from TPC-H) at scale factor 10 on a 96-core machine in May 2025, Polars' streaming engine took about 3.9 seconds in total, DuckDB 5.9, PySpark 120 and pandas 366.
It stands on three lower concepts. Rust (L0) gives native speed without a garbage collector, safe multi-threading checked by the compiler, and freedom from Python's global interpreter lock while a query runs. Apache Arrow (L0) gives the memory format: each column is a contiguous buffer plus a validity bitmap, so scans are cache-friendly and data can be handed to DuckDB, PyArrow or other Arrow tools without copying. OLAP analytics (L1) gives the execution ideas: columnar processing, vectorized kernels, predicate and projection pushdown, parallel hash aggregation and, since 2.0, a streaming engine that processes data in chunks so it can handle more data than memory.
terms: DataFrame — a table of named, typed columns; in Polars each column is a Series backed by one or more Arrow arrays.
Expression — a description of a computation on columns, such as `pl.col("cost").sum()`, that Polars can optimize and run in parallel.
Eager API — operations run immediately on a DataFrame, as in pandas.
Lazy API — operations build a query plan (a LazyFrame) that runs only on `collect()`, after optimization.
Predicate pushdown — moving a filter as early as possible, ideally into the file reader, so fewer rows are read.
Projection pushdown — reading only the columns the query actually uses.
Streaming engine — the executor that processes data in small chunks (morsels) through a pipeline, keeping memory bounded; default since Polars 2.0.
Chunked array — a column stored as several Arrow arrays (chunks) instead of one, so appending does not need a copy.
GIL — Python's global interpreter lock, which lets only one thread run Python code at a time.
history: Ritchie Vink, a Dutch engineer, made the first commit on June 23, 2020, as a personal project to see how fast a DataFrame library written in Rust could be. He built it on arrow2, a Rust implementation of Arrow by Jorge Leitão. Python bindings soon became the main way people used it. In 2021 and 2022 Polars attracted attention by leading public DataFrame benchmarks, such as the H2O.ai database-like operations benchmark, often by large margins over pandas and Spark on one machine.
In 2023 Vink and Chiel Peters founded a company, Polars, in Amsterdam, with seed funding of about 4 million dollars led by Bain Capital Ventures. At the end of 2023 the team forked the parts of arrow2 it needed into its own crate, polars-arrow, so it could change types freely. The first use of that freedom (January 2024) was a new string layout: the "German string" view from the Umbra database, which Arrow also adopted as StringView. Each string is a 16-byte record holding the length, a 4-byte prefix and either the rest of the string (up to 12 bytes) or a pointer into a buffer. Filtering and joining strings then cost the same regardless of string length.
Polars 1.0 (July 1, 2024) declared the in-memory engine and API stable; it had more than 7 million monthly downloads. A GPU engine built with NVIDIA's RAPIDS cuDF entered open beta in September 2024. During 2024 and 2025 the team rewrote the streaming engine from scratch, combining morsel-driven parallelism with Rust's async state machines. Polars Cloud became generally available on AWS on September 3, 2025, with a distributed engine in open beta, and a Series A of 18 million euros led by Accel followed that month. Polars Distributed for Kubernetes (on your own machines) arrived in June 2026. Polars 2.0 (October 6, 2026) made the streaming engine the default for lazy queries and turned on spilling to disk by default.
how: Everything in Polars is an expression applied in a context. `df.select(...)`, `df.with_columns(...)`, `df.filter(...)` and `df.group_by(...).agg(...)` are contexts; inside them, expressions such as `(pl.col("cost") * 1.18).alias("cost_gst")` or `pl.col("user").n_unique()` describe column computations. An expression takes columns and returns a column, so it has no hidden state and no order dependence between independent expressions. That is what makes optimization and parallelism safe: in `agg(a.sum(), b.mean(), c.max())` the three expressions run on different threads at once.
With the lazy API, `pl.scan_parquet("events/*.parquet")` returns a LazyFrame: a logical plan, not data. Each method call adds a node. On `collect()`, the optimizer rewrites the plan. Predicate pushdown moves filters into the scan, where Parquet row-group statistics can skip data. Projection pushdown asks the reader for only the used columns. Slice pushdown means `head(10)` after a sort stops early. Common subplan elimination reads a file once when two branches use it. Expression simplification folds constants, type coercion picks the smallest correct types, and join reordering and cardinality estimates choose join and group-by strategies. You can print the result with `explain()`. The eager API exists for convenience, but internally it runs each step as a tiny lazy query, so it loses the whole-query optimizations.
Data lives in Arrow memory, which is where Arrow adds its value. A Series is a chunked array: a list of Arrow arrays, each a contiguous buffer of fixed-width values (for example 8 bytes per Int64) plus a validity bitmap with one bit per row for nulls. A kernel such as "add two Int64 columns" is a tight loop over two buffers that the compiler turns into SIMD instructions, and null handling is a bitwise AND of two bitmaps, 64 rows per machine word. Because the layout is Arrow's, `df.to_arrow()` and `pl.from_arrow(table)` usually just pass pointers, and DuckDB can query a Polars DataFrame in place. Polars keeps its own Arrow implementation, so a few types differ from standard Arrow (its categoricals, for example), and some conversions need a copy.
Rust adds value in three ways. First, speed without a garbage collector: memory is freed when the last owner drops it, so there are no pauses, and buffers are shared between DataFrames by reference counting, so `df.clone()` costs almost nothing. Second, safe parallelism: the compiler refuses code where two threads could change the same data without synchronisation, which lets a small team write a heavily multi-threaded engine. Third, no GIL: when Python calls `collect()`, Polars releases the interpreter lock and runs the whole plan in Rust on its thread pool. The cost appears when you leave Rust: `map_elements(lambda x: ...)` calls a Python function per row under the GIL, which can be a thousand times slower than a built-in expression.
Execution has two main engines. The older in-memory engine runs each plan node to completion and materializes its full result, using the Rayon work-stealing thread pool to split columns into chunks across cores. A parallel group-by first builds partial hash tables per thread, then partitions keys by hash so that each thread finishes one set of keys. This is fast, but peak memory can be several times the data size, and on large data the full intermediate results miss the CPU caches: in the same PDS-H runs at scale factor 100, the in-memory engine took 152 seconds against 24 for the streaming engine. The streaming engine, default since 2.0, cuts the plan into pipelines of nodes connected by channels. Sources produce morsels (chunks of rows), and each node is an async task that processes a morsel and passes it on, so many morsels are in flight across all cores while memory stays bounded. Operators that need all input (sort, a join's build side, group-by) keep state and emit results when their input ends. In 2.0, spilling to disk starts at roughly 80% of RAM, with a default disk budget of 64 GB; sort, window functions and many expressions already spill, and joins and group-bys are planned. One visible change is that the streaming engine does not keep row order for joins, group-bys and unpivot unless you set `maintain_order=True`.
Two more engines extend the same plan. The GPU engine (`collect(engine="gpu")`) sends supported plans to NVIDIA cuDF and falls back to the CPU for the rest. Polars Cloud runs a LazyFrame on remote machines, either on one large node or on the distributed engine, which splits the plan into stages and runs the open-source streaming engine on each worker, shuffling data between them. The same query text runs on a laptop, a GPU or a cluster, because the plan, not the user code, is what gets executed.

example: A data scientist has 50 million ad events in Parquet, 30 columns, about 8 bytes per value when decoded. She wants the number of distinct users and total cost per campaign for the last 7 of 30 days, where cost is in micro-dollars. The machine has 16 cores and 32 GB of memory.
In pandas, the usual code is `df = pd.read_parquet("events/")`, then a filter, then `df.groupby("campaign").agg(...)`. Reading all columns costs 50 million × 30 × 8 bytes ≈ 12 GB of memory before any work starts. The filter creates a new copy of the surviving rows, about 7/30 of the data, roughly 2.8 GB more. The group-by runs mostly on one core.
In Polars lazy, the plan is `pl.scan_parquet("events/").filter(pl.col("day") >= start).group_by("campaign").agg(pl.col("user_id").n_unique(), (pl.col("cost_micros").sum() / 1e6).alias("cost"))`. The optimizer sees that only 4 columns are used (day, campaign, user_id, cost_micros), so the reader decodes 4 of 30 columns: 50 million × 4 × 8 bytes ≈ 1.6 GB if every row were read. The filter is pushed into the scan. If the files are sorted by day, row-group statistics let the reader skip about 23/30 of the row groups, so it decodes about 1.6 × 7/30 ≈ 0.37 GB, from about 11.7 million rows.
The streaming engine then splits those rows into morsels across 16 cores, about 730,000 rows per core. Each core builds a partial table per campaign. Total cost is a simple running sum. Distinct users is harder: each partial table must keep a set of user IDs, and the sets are merged at the end. With 2,000 campaigns and 3 million distinct users, the merged sets hold at most a few million 8-byte IDs, tens of megabytes. Peak memory stays below 1 GB, against more than 15 GB for the pandas version.
Now a common mistake. Suppose she writes the cost conversion as `pl.col("cost_micros").map_elements(lambda c: c / 1e6)`. That calls Python once per row under the GIL: 11.7 million calls at roughly 0.2 microseconds each is about 2.3 seconds on one core. The expression `pl.col("cost_micros") / 1e6` is a SIMD loop over an Arrow buffer: 11.7 million divisions at about 1 nanosecond per value per core take about 12 ms on one core, and less across 16. The rule follows directly: stay inside expressions, because every trip back into Python costs about three orders of magnitude.
intuition: Polars is pandas rewritten as a query engine: you still describe tables and columns, but now a planner reads your whole request before any work begins.
The design is natural once you see that a chain of DataFrame operations is already a query. pandas runs it word by word, like a translator who must speak each word before hearing the sentence. Polars waits for the full sentence, so it can drop columns nobody asked for, apply filters early and run independent parts on different cores. Expressions make this possible because they are pure functions of columns. Arrow makes the data simple and shareable, and Rust makes heavy multi-threading safe. The streaming engine is the last step: if the whole plan is known, data can flow through it in small pieces instead of being materialized at every step.
mistakes: People often think Polars is "pandas but faster" and that pandas code can be ported line by line. In fact the APIs differ: Polars has no row index, prefers expressions to element-wise functions, is strict about types, and does not guarantee row order in streaming joins and group-bys. Ported pandas idioms (loops, `apply`, index alignment) give much of the speed away.
People often think the eager API gets the same optimizations as the lazy API. In fact eager calls run one step at a time, so there is no projection pushdown across steps and every intermediate result is materialized. Use `scan_*` and `collect()` for any non-trivial pipeline.
People often think Polars is always zero-copy with every Arrow tool. Most conversions to and from Arrow pass pointers, but Polars uses its own Arrow implementation and a few types differ, and conversion to pandas usually copies unless the pandas frame uses Arrow-backed types.
People often think the streaming engine handles any size of data since 2.0. In fact spilling in 2.0 covers sort, window functions and many expressions, but joins and group-bys that exceed memory are still planned work. A huge many-to-many join can still run out of memory.
friction: Polars is mainly a single-machine engine. The distributed engine and Polars Cloud are young (distributed in open beta from 2025, on-premises Kubernetes from June 2026), and they compete with Spark and Databricks, which have years of operational tooling, governance and catalog integration. For data that is many terabytes or shared by many writers, Polars usually sits beside a lakehouse rather than replacing it.
API change has been frequent. Before 1.0, releases often broke code; 2.0 again changed defaults (streaming by default, no guaranteed row order, stricter casting, removed APIs). Pin versions and read the upgrade guide. The ecosystem still expects pandas in many places: plotting libraries, scikit-learn pipelines and older internal code may need `to_pandas()`, which can copy data.
Some workloads fit poorly. Row-by-row custom logic in Python is slow, and writing it as a Rust plugin or a native expression takes effort. Out-of-core joins and group-bys are not complete. The streaming engine supports most but not all operations; unsupported parts fall back to the in-memory engine, which can raise peak memory without warning. Very wide tables (thousands of columns) and very small DataFrames gain little, because planning and thread overhead dominate. Finally, Polars SQL covers less of the SQL standard than a database such as DuckDB, although 2.0 made SQL a first-class interface.
practice: Use the lazy API by default: start with `pl.scan_parquet`, `scan_csv` or `scan_delta`, build the whole transformation, and call `collect()` once. Use `explain()` to check that filters and column selections reached the scan, and the query profiler to find slow nodes. Write logic as expressions (`when/then/otherwise`, `over()` for window functions, `list` and `str` namespaces) and treat `map_elements` as a last resort.
Lay out input data so pushdown helps: Parquet with reasonable row groups, sorted or partitioned by the columns you filter on. Use categorical or enum types for repeated strings, and the smallest correct integer types, to cut memory. Keep data in Polars or Arrow between steps; hand it to DuckDB through Arrow when SQL is easier, which costs no copy.
In 2.0, keep the streaming default, add `maintain_order=True` only where order truly matters, and watch disk use in temporary directories when spilling. For services that run Polars, limit threads with `POLARS_MAX_THREADS` so several workers do not compete for the same cores. Compared with Spark: a single node with 64 to 192 cores runs Polars on hundreds of gigabytes faster and more cheaply than a small cluster, so try one large machine before you reach for a distributed engine.
quiz: What is the difference between the eager and lazy APIs in Polars? || The eager API runs each operation immediately and materializes its result. The lazy API builds a query plan, optimizes the whole plan (pushdowns, subplan reuse, join ordering) and runs it only on `collect()`.
How does using Arrow memory help Polars both inside the engine and with other tools? || Inside, each column is a contiguous buffer plus a validity bitmap, so kernels are tight SIMD-friendly loops and null checks are bitwise operations. Outside, tools that speak Arrow (DuckDB, PyArrow) can share the same buffers without copying.
Why is `map_elements` with a Python lambda so much slower than a native expression? || It calls the Python interpreter once per row under the GIL, about a few hundred nanoseconds per call on one core. A native expression is a compiled loop over an Arrow buffer on many cores, around a nanosecond per value.
A query reads 4 of 40 columns of a 100-million-row Parquet dataset (8 bytes per decoded value) and its filter skips 75% of row groups. How much data is decoded, compared with reading everything? || Everything would be 100 million × 40 × 8 bytes = 32 GB. With projection pushdown, 4 columns give 3.2 GB, and with 75% of row groups skipped, about 0.8 GB, which is 40 times less.
When would you choose DuckDB or Spark instead of Polars? || DuckDB when the team prefers SQL, needs a persistent database file or broader SQL coverage. Spark when the data is many terabytes, the job needs mature distributed fault tolerance, or the organisation's governance and catalogs are built around Spark or Databricks.

@@ beam
value: Apache Beam is a programming model and set of SDKs (Java, Python, Go, plus SQL and YAML) for data pipelines that work on both finite data (batch) and endless data (streaming). You describe the pipeline once; a runner translates it to an execution engine such as Google Cloud Dataflow, Apache Flink or Apache Spark. Its name comes from Batch plus strEAM.
The problem it solves is that, before about 2015, companies wrote the same logic twice. A nightly MapReduce or Spark job computed exact results from yesterday's files, and a separate streaming job (Storm, for example) computed fast, approximate results from the live stream. This "Lambda architecture" doubled the code, and the two versions often disagreed. Beam's answer, taken from Google's Dataflow paper, is that batch is a special case of streaming: a finite dataset is a stream that ends. If the model handles time correctly, one program can produce both the fast early answer and the exact final answer, and the same program can re-process history.
Beam stands on two lower concepts. Batch processing (L1) contributes the pipeline style of MapReduce and FlumeJava: a graph of parallel element-wise steps and grouping steps, deferred evaluation so the runner can optimize the whole graph, combiners that pre-aggregate before a shuffle, and splitting of large inputs across workers. Stream processing (L1) contributes event time, watermarks, windows, per-key state and timers, and checkpointing. Beam's contribution is to make time an explicit part of the API, so that "what is computed" is separated from "which events belong together" and "when results are emitted". It is used most on Google Cloud, where Dataflow is the managed runner, and by companies that want one codebase for streaming and backfills.
terms: PCollection — an immutable, possibly unbounded collection of elements; each element carries a value, an event-time timestamp and one or more windows.
PTransform — a step that turns input PCollections into output PCollections; a pipeline is a graph of PTransforms.
ParDo and DoFn — the element-wise transform (ParDo) and the user function it runs for each element (DoFn); it can emit zero, one or many outputs.
GroupByKey and Combine — grouping all values of a key within each window; Combine does the same with an associative function that can pre-aggregate before the shuffle.
Event time and processing time — when an event happened, versus when the system sees it.
Window — a grouping of elements by event time: fixed, sliding, session or global.
Watermark — the runner's estimate that no more elements with event time earlier than T will arrive.
Trigger — a rule that decides when to emit a result (a pane) for a window, such as "at the watermark, plus every 30 seconds before it".
Accumulation mode — whether each new pane contains all data so far (accumulating) or only data since the last pane (discarding).
Runner — the component that translates a Beam pipeline to an engine and executes it.
history: Beam is the open-source form of ideas built at Google over a decade. MapReduce (2004) made large batch jobs simple. FlumeJava (Chambers and colleagues, PLDI 2010) let programmers write pipelines of parallel collections; it deferred evaluation and fused many small steps into a few MapReduce stages. MillWheel (Akidau and colleagues, VLDB 2013) provided low-latency streaming with per-key state, timers, exactly-once processing and low watermarks. Google combined the two into Cloud Dataflow, announced in 2014 and generally available in August 2015.
The paper "The Dataflow Model" (Tyler Akidau and ten co-authors, VLDB 2015) stated the theory. It argued that streaming systems cannot wait for complete data, because unbounded data is never complete, and that the right design lets users choose the trade-off between correctness, latency and cost. It described the model as four questions: what is computed, where in event time, when in processing time, and how refinements relate. Akidau's essays "Streaming 101" and "Streaming 102" (2015–2016) and the book "Streaming Systems" (Akidau, Chernyak and Lax, 2018) brought these ideas to a wide audience, and they shaped Apache Flink's event-time design.
In February 2016 Google donated the Dataflow SDKs to the Apache Incubator, together with runners for Flink (from data Artisans) and Spark (from Cloudera and others). Beam became a top-level Apache project, announced on January 10, 2017, and released its first stable version, 2.0.0, on May 17, 2017. The portability framework (about 2018–2020) let SDKs in any language run on any runner, which made Python and Go pipelines possible on Flink and Spark and enabled cross-language transforms. Later additions include Beam SQL (on Apache Calcite), state and timers, splittable DoFns, the RunInference transform for machine-learning models, Beam YAML, and Prism, a local runner written in Go. Beam releases about every six weeks; version 2.77.0 came out on October 7, 2026.
how: A Beam program builds a pipeline graph; it does not process data while it runs. `p | ReadFromKafka(...) | beam.Map(parse) | beam.WindowInto(FixedWindows(60)) | beam.CombinePerKey(sum) | WriteToBigQuery(...)` creates PCollections connected by PTransforms. Every composite transform expands into a few primitives: ParDo (element-wise work), GroupByKey (grouping, which means a shuffle across workers), Flatten (merge collections), Window.into (assign windows) and Impulse or Read (start reading). Nothing runs until `p.run()` hands the graph to a runner.
The runner then optimizes, using the batch-processing ideas from FlumeJava. Fusion merges consecutive ParDos into one stage, so an element passes from parse to filter to enrich inside one worker thread without being written anywhere. Every GroupByKey becomes a shuffle boundary. Combiner lifting turns `CombinePerKey(sum)` into a partial sum on each worker before the shuffle and a final sum after it, so a key with a million values sends a handful of partial sums over the network instead of a million values. Input is split into bundles that workers process in parallel; with splittable DoFns, a reader describes its work as a restriction, such as a byte range of a file or an offset range of a Kafka partition, which the runner can split while it runs to move work from slow workers to idle ones.
Time is where stream processing adds its value. Every element has an event-time timestamp, set by the source or by the user. WindowInto assigns each element to windows: fixed windows of 60 seconds, sliding windows (for example 10 minutes long, every minute), session windows that merge events separated by less than a gap, or one global window. GroupByKey and Combine then group by key and window together, so "sum per campaign" becomes "sum per campaign per minute" with no change to the summing code. That separation (the what versus the where) is the main idea of the model.
The watermark answers "how complete is the input?" Each source estimates it; for Kafka it is often based on the oldest unprocessed timestamp across partitions, and every later step's watermark is the minimum of its inputs' watermarks. When the watermark passes the end of a window, the runner believes the window is complete. This is a heuristic: data can still arrive later, for example from a phone that was offline. Two settings handle this. Allowed lateness says how long, in event time after the watermark passes, the runner keeps a window's state so late data can still update it; after that, the state is deleted and later data is dropped. A trigger says when to emit panes. The default emits once at the watermark and once for each late element. A common custom trigger adds early panes, for example every 30 seconds of processing time, to show partial results before the window is complete.
The accumulation mode says how successive panes relate. In accumulating mode each pane holds the full result so far, so the consumer should overwrite (upsert by key and window). In discarding mode each pane holds only the new data, so the consumer should add panes together. Beam's model also needs stateful processing beyond windows: a DoFn can declare per-key-and-window state (value, bag, map, combining) and timers in event time or processing time, which is enough to write custom sessionization, deduplication or rate limits.
Portability decides how user code meets the engine. The pipeline is serialized as a language-neutral protobuf graph (the Runner API). A runner such as the Flink runner translates it into Flink operators running on the JVM. When a fused stage contains Python or Go code, the runner starts SDK harness processes, often Docker containers, and streams bundles of elements to them over gRPC (the Fn API), which also carries state reads and writes and progress reports. This is how a Python pipeline can run on Flink, and how it can use Java's KafkaIO as a cross-language transform. It also explains a cost: every element that crosses between the JVM and a Python harness is encoded and decoded.
Correctness depends on the runner. The model assumes that each element's effect on state and output happens exactly once despite retries. Dataflow implements this with its own shuffle and deduplication; the Flink runner relies on Flink checkpoints. Sinks must still be idempotent or transactional, because a retried bundle may write twice otherwise. Runners differ in which features they support: Dataflow and Flink support the full streaming model, while the Spark runners have gaps (for example, the Structured Streaming runner is batch-only).

example: An ad platform counts clicks per campaign in 1-minute event-time windows. The pipeline uses fixed windows of 60 seconds, a trigger that fires early every 30 seconds of processing time, on time at the watermark, and again for each late element, allowed lateness of 10 minutes, and accumulating mode. Follow campaign 42 in window [12:00:00, 12:01:00). Each row below shows the event time, the processing time when it arrives, and the number of clicks.
Event a: 12:00:05, arrives 12:00:07, 3 clicks. Event b: 12:00:20, arrives 12:00:21, 5 clicks. At 12:00:30 processing time, the early trigger fires: EARLY pane, total 3 + 5 = 8. Event c: 12:00:50, arrives 12:00:58, 2 clicks. At 12:01:00 another early pane: 10.
At 12:01:05 processing time, the watermark passes 12:01:00. The window is believed complete: ON_TIME pane, 10. Event d: 12:00:40, arrives 12:01:20, 4 clicks. The watermark is already past the window, so d is late, but well within the 10-minute allowed lateness: LATE pane, 14. Event e: 12:00:30, arrives at 12:09:00 from a device that was offline, 1 click: LATE pane, 15. When the watermark passes 12:11:00 (end of window plus 10 minutes), the runner deletes the window's state. Event f: 12:00:15, arriving at 12:13:00 with 6 clicks, is dropped and only counted in a metric.
The consumer sees the panes 8, 10, 10, 14, 15 for this key and window. In accumulating mode it must overwrite: a BigQuery table updated by key and window ends at 15, the true count of everything that arrived in time. In discarding mode the panes would be 8, 2, 0, 4, 1, and the consumer must add them up to 15; if it overwrote them instead, it would report 1.
Now the cost of lateness. With 50,000 active campaigns, 1-minute windows and 10 minutes of allowed lateness, each campaign has about 11 open windows at any time: the current one plus ten that still accept late data. At about 50 bytes of state per key and window, that is 50,000 × 11 × 50 bytes ≈ 27.5 MB, which is small. With 1 hour of allowed lateness it becomes 61 open windows and about 150 MB; with per-user keys (say 20 million users) instead of campaigns, 1 hour of lateness needs about 61 GB of state. Lateness is a direct memory and storage cost.
Finally, re-run the same pipeline on yesterday's click files in batch. The input is bounded, so the watermark jumps to the end of time once all files are read, and every window fires once ON_TIME with all its data. For this window the result is 21, because event f, dropped by the streaming job, is simply present in the files. One program has produced both the streaming answer and the backfill, and they differ only by the data that missed the lateness deadline.
intuition: Beam treats a dataset like the counting of postal votes: you announce early totals, publish an official count when you believe all votes are in, and issue corrections when late envelopes arrive, until a deadline after which no corrections are accepted.
The design becomes natural once you accept that unbounded data is never complete. Every streaming system must then decide which events belong together and when to speak, even if it hides those decisions. Beam makes them explicit and independent: windows group by when events happened, triggers choose when to emit, and accumulation tells the consumer how to read repeated answers. With those choices visible, batch is no longer a separate world. It is the case where the input ends, the watermark reaches infinity and every window fires once. The runner abstraction follows from the same separation: if the program describes only what and when, the engine that executes it can be chosen later.
mistakes: People often think Beam is an engine like Spark or Flink. In fact Beam only defines pipelines; a runner executes them on an engine. Performance, fault tolerance and supported features come from that engine and its runner.
People often think the watermark guarantees that no late data will arrive. In fact it is an estimate. Data behind the watermark is late, and it is kept or dropped according to allowed lateness. A watermark that is too fast loses data; one that is too slow delays every result.
People often think "write once, run anywhere" means identical behavior on every runner. In fact runners support different parts of the model; some lack features such as certain triggers, state, timers or streaming entirely, and performance tuning is engine-specific. Moving a pipeline from Dataflow to Flink needs testing, not only a flag change.
People often think discarding and accumulating modes are a performance detail. In fact they change the meaning of the output. A consumer that overwrites discarding panes, or adds accumulating panes, gives wrong totals, as the example shows.
friction: The portability that defines Beam has costs. A Python pipeline on Flink or Dataflow passes every element between the runner and SDK harness processes over gRPC, with encoding and decoding each time; the overhead can dominate cheap per-element work. The abstraction also hides engine features: Flink users lose direct access to Flink's own APIs and tuning, and runner support for new engine versions lags behind the engines' own releases.
In practice most Beam production use runs on Google Cloud Dataflow, where the model is implemented most completely (autoscaling, dynamic work rebalancing, managed shuffle and Streaming Engine). Outside Google Cloud, most teams choose Flink or Spark Structured Streaming directly, so Beam's community and its library of connectors are smaller than theirs.
Streaming correctness remains hard. Watermarks stall when one source partition is idle or a single slow key holds them back. Hot keys limit parallelism, because all values for one key and window go to one worker. Long allowed lateness and session windows grow state, as the example computed. Updating a running streaming job requires compatible transform names and coders; renaming a step can force a drain and restart. Debugging is indirect, because user code runs inside fused stages on remote harnesses, and errors appear in runner logs far from the code that caused them. Finally, exactly-once output still depends on sinks that are idempotent or transactional.
practice: Choose Beam when you run on Google Cloud (Dataflow is the reason most teams use it), when you need one codebase for streaming and historical backfills, or when you want Python streaming pipelines on a managed service. On Kubernetes or Databricks with a JVM team, Flink or Spark used directly is usually simpler.
Design time first. For every aggregation, decide the windowing, the trigger and the allowed lateness from the business need: "dashboards every 30 seconds, final numbers within 10 minutes, ignore data later than 1 hour" maps directly onto early firings, the on-time pane and allowed lateness. Write sinks that match the accumulation mode: upserts keyed by key and window for accumulating, additive writes for discarding.
Use Combine instead of GroupByKey followed by a sum, so combiner lifting can pre-aggregate. Insert a Reshuffle after a step that expands a small input into many elements, because fusion would otherwise keep all the work on the few workers that read the input. Watch watermark lag (data freshness), system lag, the number of dropped late elements and hot-key warnings. Test event-time logic with TestStream, which lets a unit test advance the watermark and inject late data, and run tests locally on the Prism or Direct runner. Give transforms stable names so streaming jobs can be updated in place.
quiz: What are the four questions of the Dataflow model, and which Beam feature answers each? || What is computed (PTransforms such as ParDo and Combine), where in event time (windowing), when in processing time (watermarks and triggers), and how refinements relate (accumulation mode).
How does combiner lifting reduce the cost of `CombinePerKey(sum)`? || The runner computes partial sums on each worker before the shuffle, so only one partial result per key per worker crosses the network, instead of every value. This needs an associative and commutative combine function.

A team runs on AWS with Flink already in production and wants a new streaming job. Would you use Beam? || Usually not. Beam's main advantage, the managed Dataflow runner, is not available, the Flink runner adds an abstraction layer and lags Flink releases, and Python code adds harness overhead. Beam makes sense there only if portability or one codebase with existing Beam batch jobs matters more.

@@ mesos
value: Apache Mesos was a cluster manager: software that pooled the CPU, memory, disk and ports of many machines and shared them among several distributed systems at once. Its key idea was two-level scheduling. Mesos itself decided only which framework (Spark, a Hadoop job tracker, a service scheduler such as Marathon) should receive the next piece of free capacity, and it offered that capacity. The framework's own scheduler decided whether to accept the offer and which tasks to start in it. Mesos was retired to the Apache Attic in 2025, and Spark removed Mesos support in 4.0, so today it matters mainly as history and as a design lesson.
The problem it solved appeared around 2009. Companies ran a separate cluster for each system: one for Hadoop, one for MPI jobs, one for web services. Each cluster was sized for its own peak, so most machines were idle most of the time, and data had to be copied between clusters. Static partitioning of one cluster (say, half the machines for Hadoop) had the same problem. Mesos let all these systems share one pool at a fine grain, task by task, so that idle capacity in one system could be used by another within seconds. Twitter used it to run most of its services after 2010; Airbnb, Apple (for Siri), Netflix and Yelp also ran it in production.
Mesos stands on two lower concepts. Container orchestration (L1) defines the job: place work on machines, isolate it, restart it when machines fail and share capacity fairly. Mesos is one design point in that space, the offer-based, two-level one; Kubernetes is the main alternative. C / C++ (L0) gave a small, fast master that could handle tens of thousands of machines, and direct access to the Linux kernel features (cgroups and namespaces) used to isolate tasks. Understanding Mesos explains why Kubernetes chose a different design, and why Spark and YARN have the scheduling options they have.
terms: Framework — a distributed system that runs on Mesos; it has a scheduler (talks to the master) and executors (run tasks on machines).
Master — the central Mesos process that tracks free resources and sends offers; standby masters wait to take over.
Agent — the Mesos process on each machine (called "slave" before version 1.0) that reports resources and launches tasks.
Resource offer — a message from the master to one framework listing free resources on specific agents, such as 4 CPUs and 8 GB on agent 17.
Two-level scheduling — the master chooses which framework gets an offer; the framework chooses which tasks to run in it.
Dominant Resource Fairness (DRF) — a fairness rule for several resource types: give the next resources to the user whose largest share of any one resource is smallest.
Containerizer — the agent component that starts a task inside an isolated environment using cgroups and namespaces, or Docker.
Reservation and quota — ways to set aside resources for a role (a group of frameworks), so important work is not starved.
Filter — a framework's request not to be offered the same resources again for some seconds after it declines them.
history: Mesos began in 2009 at the UC Berkeley RAD Lab as a class project by PhD students Benjamin Hindman, Andy Konwinski and Matei Zaharia, with professor Ion Stoica. It was first called Nexus and was presented under that name at HotCloud 2009. To show that new frameworks could be built quickly on top of it, Zaharia wrote a small in-memory computing framework: that was the beginning of Apache Spark. The full system appeared in the NSDI 2011 paper "Mesos: A Platform for Fine-Grained Resource Sharing in the Data Center" (Hindman, Konwinski, Zaharia, Ghodsi, Joseph, Katz, Shenker and Stoica). The same group published Dominant Resource Fairness at NSDI 2011 and delay scheduling (EuroSys 2010), both connected to the problem of sharing clusters well.
In 2010 Hindman presented Mesos at Twitter, which was struggling with reliability, and Twitter adopted it along with Aurora, a service scheduler built there. Mesos entered the Apache Incubator in 2010 and graduated as a top-level Apache project in 2013. Mesosphere, founded in 2013, built Marathon (for long-running services), Chronos (cron jobs) and DC/OS, a "data-centre operating system" distribution. Version 1.0 (July 27, 2016) added HTTP APIs and a unified containerizer that could run Docker images without the Docker daemon.
Meanwhile, Google published Omega (EuroSys 2013), which argued that offer-based scheduling hides the global view of the cluster, and released Kubernetes in 2014. Kubernetes offered a single declarative API with built-in deployment, service discovery and scaling, while each Mesos framework had to build these itself. The ecosystem moved quickly to Kubernetes; Mesosphere renamed itself D2iQ and moved its products to Kubernetes. The last Mesos release, 1.11.0, came out on November 24, 2020. A vote to retire the project in April 2021 was cancelled two days later when volunteers offered to continue, but activity stayed low. Spark deprecated Mesos support in 3.2 and removed it in 4.0 (2025). The Apache board retired Mesos in August 2025, and it moved to the Attic in October 2025; the code is read-only, with an outside fork named Clusterd.
how: A Mesos cluster has a small set of master processes and one agent on every machine. The masters use ZooKeeper to elect one leader; the others are standbys. Each agent registers with the leader and reports what it has, for example `cpus:16; mem:65536; disk:500000; ports:[31000-32000]`. Frameworks register too. A framework has a scheduler, which can run anywhere and talks to the master, and executors, which run on agents and start the framework's tasks.
Scheduling happens in rounds. About once per second (the default allocation interval), the master's allocator module looks at free resources and decides which framework to offer them to. The default allocator uses Dominant Resource Fairness, organised hierarchically by roles: for each framework it computes the share of each resource type the framework already uses, takes the largest of those shares (its dominant share), and offers next to the framework with the smallest dominant share. Weights, quotas and reservations adjust this. The offer is a list of resources on particular agents, so the framework knows exactly which machines it could use.
The framework scheduler then makes its own decision, which is the second level. It may accept part of an offer and launch tasks in it, for example two tasks of 2 CPUs and 4 GB each on agent 17, and leave the rest unused. Unused parts return to the pool at once. It may decline the whole offer, adding a filter that says "do not offer me these resources for 5 seconds" (the default). This is how frameworks get data locality: Spark or Hadoop can decline offers on machines without the needed data and wait briefly for better ones, which is the idea of delay scheduling. The master never needs to understand the framework's rules about locality, gangs of tasks or placement; it only sees accepts and declines. That is the main benefit of the design: the central component stays simple and fast, and each framework keeps its own logic.
On the agent, a containerizer starts each task in isolation. The Mesos containerizer uses Linux cgroups to limit CPU shares and memory (a task that goes over its memory limit is killed) and namespaces to give tasks their own view of process IDs, network or mounts; it can also unpack Docker images itself. A Docker containerizer delegates to the Docker daemon instead. The executor reports task states (staging, running, finished, failed, lost) back through the agent and master to the scheduler.
Fault tolerance is shared between levels. If the leading master fails, ZooKeeper elects a standby; agents and schedulers re-register, and the new master rebuilds its view from them. The list of registered agents is kept in a replicated log so the master knows which machines to expect. If a scheduler fails, its tasks can keep running for a failover timeout while a new scheduler instance re-registers and reconciles task states. If an agent fails, its tasks are reported lost and the framework decides whether to restart them elsewhere. Mesos does not restart tasks itself; restarting, rolling updates and health checks are framework features. This is why Marathon and Aurora existed.
Here the two lower concepts show their contributions. From container orchestration come the jobs any cluster manager must do: resource accounting, isolation, placement and failure handling. Mesos split them between a central allocator and per-framework schedulers. From C++ came the implementation style: the master and agent are built on libprocess, a C++ actor library in which components exchange messages, so one master process could handle many thousands of agents and frameworks with low latency. The isolators call Linux kernel interfaces directly, which is natural in C++.
The design also has structural costs. A framework sees only what it is offered, not the whole cluster, so it cannot reason about global placement or preempt others. An offer locks those resources for one framework while it decides, so slow schedulers waste capacity; this is pessimistic concurrency, the main criticism in the Omega paper. A task that needs a large block (say 32 CPUs on one machine) may wait a long time, because free capacity arrives in small pieces and other frameworks take it first. Mesos added reservations, quotas, inverse offers for maintenance and revocable (oversubscribed) resources to soften these problems, which made the system more complex.

example: Take the example from the Dominant Resource Fairness paper and run it as Mesos offers. The cluster has 9 CPUs and 18 GB of memory in total. Framework A runs tasks that each need 1 CPU and 4 GB (memory-heavy). Framework B runs tasks that each need 3 CPUs and 1 GB (CPU-heavy). Both want as many tasks as they can get.
Round 1. Both use nothing, so the allocator offers to A first. A launches one task: it now holds 1/9 of the CPUs (0.11) and 4/18 of the memory (0.22), so its dominant share is 0.22, from memory. B is now lowest at 0, so B gets the next offer and launches one task: 3/9 of the CPUs (0.33) and 1/18 of the memory (0.06). B's dominant share is 0.33, from CPU.
Round 2. A has the smaller dominant share (0.22 against 0.33), so A gets the next offer and starts a second task: 2 CPUs and 8 GB, dominant share 8/18 = 0.44. Now B is lower (0.33), so B starts a second task: 6 CPUs and 2 GB, dominant share 6/9 = 0.67.
Round 3. A is lower (0.44), so A starts a third task: 3 CPUs and 12 GB, dominant share 12/18 = 0.67. Now the CPUs are exhausted: A uses 3 and B uses 6, which is all 9. B cannot start a third task (it needs 3 CPUs), and A cannot start a fourth (it needs 1 CPU). The allocation stops with A holding 3 tasks (3 CPUs, 12 GB) and B holding 2 tasks (6 CPUs, 2 GB). Both have a dominant share of 2/3, which is exactly what DRF aims for. 4 GB of memory stays free, but no task can use it without CPU.
Now the offer mechanics. Each round is roughly one allocation interval, about 1 second, so it took a few seconds to fill the cluster. Suppose B's tasks need a specific machine (for example, one with a GPU or local data) and an offer arrives for a different machine. B declines with the default 5-second filter. Those resources go back to the pool and may be offered to A instead, while B waits for an offer on the right machine. If the right machine is always busy with A's tasks, B can wait indefinitely; Mesos itself will not move A's tasks for B. A reservation for B's role on that machine, or a quota, is the fix. This is the trade-off of two-level scheduling in one picture: the master stays simple, but global goals such as "place this gang of tasks together" or "make room for this large task" are hard to reach.
intuition: Mesos was like a landlord who announces free rooms one batch at a time; each tenant decides which rooms to take, but no tenant ever sees the whole building.
The design was natural for 2009. Each framework (Hadoop, MPI, Spark) already had a sophisticated scheduler with its own rules about locality and task placement, and it was not realistic to put all those rules into one central scheduler. Offers let the central part stay small and general, and frameworks keep their own logic. The fairness question also had to be solved for several resources at once, and DRF gave a simple rule with good properties: no framework envies another's allocation, and no one gains by lying about its needs. What changed later was the workload. Once most work became long-running services in containers, it was more natural to describe the desired state once and let one scheduler with a global view make every placement, which is the Kubernetes model.
mistakes: People often think Mesos schedules tasks. In fact Mesos only allocates resources to frameworks through offers; the framework's scheduler decides what to run, where, and whether to restart failures. Without a framework such as Marathon or Aurora, Mesos does not keep a service running.
People often think two-level scheduling gives each framework a fixed part of the cluster. In fact offers are dynamic: resources flow to whichever framework DRF selects next, and they return to the pool as soon as tasks finish or offers are declined.
People often think Mesos and Kubernetes differ only in popularity. In fact the architectures differ. Kubernetes stores the full desired and current state in one API server and its scheduler sees every node; Mesos frameworks see only offered pieces. This difference explains Kubernetes' easier global placement and preemption, and Mesos' lighter central component.
People sometimes assume Mesos still has a maintained path forward. In fact the Apache project retired in 2025 and has had no release since 1.11.0 in 2020, and Spark 4.0 cannot run on it. Any remaining cluster needs a migration plan.
friction: The offer model has known limits. Frameworks lack a global view, so they cannot preempt other frameworks, plan placement across the cluster or easily schedule gangs of tasks that must start together. Offers lock resources while a scheduler thinks, so slow or buggy schedulers waste capacity; a scheduler that holds offers without using them (hoarding) can starve others. Large tasks suffer fragmentation, because free capacity arrives in small pieces. Reservations, quotas, revocable resources and maintenance inverse offers each fixed one problem but added concepts to learn.
Operations were demanding. A production setup needed ZooKeeper, the masters, agents on every machine, and one or more frameworks such as Marathon or Aurora, each with its own failure modes, upgrade cycle and API. Common platform features (service discovery, load balancing, secrets, rolling deployments, autoscaling) lived in different frameworks or in DC/OS, rather than in one consistent API. Stateful services needed persistent volumes and dynamic reservations, which only some frameworks supported.
Today the main friction is that the project is finished. There are no new releases, no security fixes from Apache and a shrinking set of people who know it. Spark 4.0 removed the Mesos scheduler backend, Marathon and Chronos are no longer actively developed, and Aurora was retired to the Attic earlier. Teams still running Mesos carry the full maintenance burden themselves or depend on an outside fork, and every year the migration gets harder as experience disappears.
practice: If you still operate Mesos, plan a migration. Inventory every framework and job type: long-running services (usually on Marathon or Aurora) map to Kubernetes Deployments and StatefulSets; cron jobs (Chronos) map to Kubernetes CronJobs or a workflow scheduler such as Airflow; Spark jobs must move to Kubernetes or YARN before any upgrade to Spark 4.x, since Spark 3.5 is the last line with Mesos support. Migrate one framework at a time, and keep resource requests similar so capacity planning stays valid.
If you are learning cluster scheduling, read Mesos for its ideas, which still apply. DRF is used beyond Mesos: YARN's Capacity and Fair schedulers can use dominant-resource calculations, and the Volcano batch scheduler for Kubernetes has a DRF plugin. The offer-and-decline pattern with short waits is delay scheduling, which Spark still uses for data locality (`spark.locality.wait`, default 3 seconds). Compare the Mesos, Omega, Borg and Kubernetes papers to see the trade-off between a simple central allocator with smart frameworks and a single scheduler with a global view.
When you design a platform on Kubernetes today, the Mesos lesson is to decide where scheduling logic lives. Put generic placement in the platform scheduler, and put workload-specific logic (gang scheduling, locality, elastic scaling) in operators or batch schedulers that work with the global API, rather than in separate silos.

value: YARN (Yet Another Resource Negotiator) is the resource manager of Apache Hadoop. It decides which application may use how much memory and CPU on which machine of a Hadoop cluster, starts that work in "containers", and watches it. Many engines run on it side by side: Spark, MapReduce, Hive on Tez, Flink and others. When you submit a Spark job to Amazon EMR on EC2, Google Dataproc or an on-premises Cloudera cluster, YARN is usually what gives the job its executors.
The problem it solved was the design of the first Hadoop. In Hadoop 1, one JobTracker process did everything: it tracked every machine, scheduled every map and reduce task of every job, and handled failures. It only understood MapReduce, it divided each machine into fixed "map slots" and "reduce slots" that were often idle, and at Yahoo it hit a scaling limit at around 4,000 machines. Engines that were not MapReduce, such as Spark, graph processing or MPI, had no clean way to share the cluster and its HDFS data. YARN split the JobTracker in two: a general ResourceManager that only hands out resources, and a per-application ApplicationMaster that manages its own tasks. Hadoop turned from "a MapReduce cluster" into a shared platform for many engines.
It stands on one lower concept, container orchestration (L1): the general problem of placing work on machines, isolating it, sharing capacity fairly between teams and recovering from failures. YARN is one classic design in that space: a central scheduler with hierarchical queues, which receives explicit requests from applications. That is different from Mesos, where the centre offers resources, and from Kubernetes, which reconciles declared desired state. For the layers above, YARN is what Spark's and MapReduce's schedulers talk to on Hadoop clusters: it gives them containers near their HDFS data, enforces each team's share and restarts failed application masters.
terms: ResourceManager (RM) — the central YARN service that knows the cluster's capacity and allocates containers to applications.
NodeManager (NM) — the agent on each machine that launches containers, enforces their limits and reports to the RM.
ApplicationMaster (AM) — a per-application process, running in a container, that asks the RM for containers and manages the application's tasks; Spark's driver plays this role in cluster mode.
Container — a lease on a machine for a fixed amount of memory and virtual cores, in which one process (for example a Spark executor) runs.
ResourceRequest — an AM's request: how many containers, of what size, with what priority, preferably on which hosts or racks.
Queue — a named share of the cluster, organised in a tree, with guaranteed and maximum capacity and access rules.
Capacity Scheduler — the queue scheduler from Yahoo: each queue has a guaranteed percentage and can grow into idle capacity.
Fair Scheduler — the queue scheduler from Facebook: running applications get equal shares over time, with weights and minimums.
Preemption — taking containers back from a queue that uses more than its share, so another queue can reach its guarantee.
history: Hadoop MapReduce, an open-source copy of Google's MapReduce, ran from 2006 with the JobTracker design. By 2008 Yahoo, its biggest user, saw the limits: one process for all jobs, fixed slots, no engines other than MapReduce and long outages when the JobTracker failed. Arun Murthy opened the Hadoop issue MAPREDUCE-279 in 2008 proposing "MapReduce 2.0", a split of resource management from job management. A team mostly at Yahoo, which spun off Hortonworks in 2011, built it. YARN shipped first in the Hadoop 0.23 alpha line in 2011 and became generally available in Hadoop 2.2.0 in October 2013. The paper "Apache Hadoop YARN: Yet Another Resource Negotiator" (Vavilapalli and 15 co-authors) won the best paper award at SoCC 2013.
YARN arrived when the data world wanted more than MapReduce. Apache Tez (a DAG engine for Hive and Pig), Spark, Storm, Giraph and Flink all added YARN support between 2013 and 2015, because that was how they could reach the data that companies had already stored in HDFS. Schedulers matured at the same time: the Capacity Scheduler came from Yahoo and the Fair Scheduler from Facebook.
Hadoop 3 (first GA release December 2017, with 3.1 and 3.2 in 2018) extended YARN beyond memory and CPU and beyond batch: resource types such as GPUs and FPGAs, Docker containers, placement constraints (for example "no two of these containers on one machine"), opportunistic containers that run in idle capacity and can be killed, YARN Federation to join several sub-clusters into one with tens of thousands of machines, a services framework for long-running applications, and the second-generation timeline service. Since then Kubernetes has become the default for new cloud platforms, and Databricks and most cloud-native engines do not use YARN. YARN remains in wide use where Hadoop lives: on-premises clusters, Amazon EMR on EC2 and Google Dataproc. Hadoop 3.4.0 was released in March 2024 and 3.5.0, the first release of the 3.5 line, on April 2, 2026.
how: Every machine runs a NodeManager. At start-up it registers with the ResourceManager and reports what it offers to YARN, set by `yarn.nodemanager.resource.memory-mb` and `yarn.nodemanager.resource.cpu-vcores`. These are configured, not measured, so an administrator usually leaves part of the machine for the operating system and the HDFS DataNode. After that, the NM sends a heartbeat about once per second with the state of its containers and its free capacity. The RM keeps the whole cluster's state in memory: nodes, queues, applications and containers.
An application starts with a client submission. The client sends the RM an application description, including how to launch the ApplicationMaster (a command, environment variables and files to download, usually from HDFS). The RM's ApplicationsManager places the application in a queue, allocates the first container for the AM, and tells that machine's NM to start it. The NM localizes the files (downloads them to local disk, with caching), then launches the AM process. In Spark's cluster mode the AM contains the Spark driver; in client mode the driver runs outside and a small ExecutorLauncher acts as the AM.
The AM then negotiates, and this is the core of the design. It registers with the RM and, on its own heartbeat (the allocate call), sends ResourceRequests: for example "10 containers of 22 GB and 5 vcores at priority 1, preferably on hosts h3 or h7, else rack r2, else anywhere". The RM's scheduler decides when and where to satisfy them. It usually allocates when a NodeManager heartbeat shows free space: it walks the queue tree, picks the queue furthest below its share, picks an application in it, and matches the request to the node, trying host, then rack, then any node (with a short delay to wait for locality). Requests are rounded up to a multiple of the minimum allocation (`yarn.scheduler.minimum-allocation-mb`, 1 GB by default) and capped at the maximum. The RM returns containers, which are leases signed with a token, and the AM contacts each NM directly to start its process in it. The AM alone decides what runs in each container, what to do when a task fails and when to give containers back.
Queues decide who gets what. With the Capacity Scheduler, an administrator defines a tree such as root → etl 60%, adhoc 30%, ml 10%. Each queue is guaranteed its percentage when it has demand, can grow up to a maximum capacity when others are idle, and limits how much one user can take. If a queue is below its guarantee and others are over theirs, preemption can kill the newest containers in the over-share queues after a timeout, so the guarantee is met within seconds or minutes instead of waiting for long jobs to finish. By default, sizes are compared by memory only; the DominantResourceCalculator applies Dominant Resource Fairness across memory and CPU (and other resource types). The Fair Scheduler gives applications equal shares over time, with weights, minimum shares and its own preemption settings.
The NodeManager enforces the lease. It monitors each container's process tree, and if the physical memory used goes over the container's size, it kills the container; this is the familiar Spark error "Container killed by YARN for exceeding memory limits". CPU isolation needs Linux cgroups to be enabled; without them, vcores are only bookkeeping. NMs can also host auxiliary services. The best known is the shuffle service: MapReduce's shuffle handler, or Spark's external shuffle service, which keeps serving a finished executor's shuffle files so Spark can release idle executors with dynamic allocation.
Failure handling is split, like everything else in YARN. If a container fails, the NM reports it and the AM decides whether to retry the task. If the AM fails, the RM starts a new attempt (2 attempts by default); applications that support it can keep running containers across AM attempts. If a NodeManager stops heartbeating (about 10 minutes by default), the RM marks it lost and tells the AMs that its containers are gone. The RM itself runs as an active and a standby process, with ZooKeeper electing the active one and storing application state; after a failover, NMs and AMs resynchronize with the new RM and running containers are kept (work-preserving restart).
The design gives the layer above a clean contract. MapReduce and Spark each keep their own task scheduling, retries and data locality logic in their AM, and YARN gives them only resources, fairness and isolation. This is what container orchestration means in YARN: a central scheduler with a global view of the cluster and of every queue's share, which applications talk to through explicit requests. The cost is that the RM is one busy component (Federation exists because one RM manages a few thousand machines well, not tens of thousands), and that applications must be written to negotiate with it.

example: A team runs Spark on a 20-node YARN cluster. Each node has 128 GB of memory and 32 cores. The administrator sets `yarn.nodemanager.resource.memory-mb` to 112 GB and `cpu-vcores` to 30, leaving 16 GB and 2 cores for the operating system, the NodeManager and the HDFS DataNode. The minimum allocation is 1 GB.
Step 1, container size. The job asks for executors with `spark.executor.memory = 20g` and `spark.executor.cores = 5`. Spark adds memory overhead for non-heap use (Python workers, network buffers): by default the larger of 384 MB and 10% of executor memory, here 2 GB. So each executor requests a 22 GB container. That is already a multiple of 1 GB, so no rounding is needed.
Step 2, packing. Per node, 112 / 22 = 5.09, so 5 executors fit, using 110 GB and leaving 2 GB idle. The cores are 5 × 5 = 25 of 30 vcores. With the default memory-only calculator, YARN would happily place a sixth executor if memory allowed, even with no vcores left; with the DominantResourceCalculator, both limits count. Across 20 nodes the cluster holds 100 executors and 500 cores. One container on one node is used by the AM (the driver, say 4 GB plus overhead), so in practice 99 executors fit if the driver shares a node with executors.
Step 3, queues. The Capacity Scheduler has etl at 60% and adhoc at 40%, and adhoc may grow to 100% when etl is idle. At night etl is empty, so an ad hoc job takes all 99 executors. At 02:00 the ETL job starts and asks for 60 executors. Its queue is guaranteed 60% of 2,240 GB, about 1,344 GB, which is 61 containers of 22 GB, but everything is in use. After the preemption timeout, the scheduler kills about 60 of the ad hoc job's newest containers. The ad hoc job's driver sees "executor lost", its tasks on those executors are re-run elsewhere later, and its shuffle files survive only if the external shuffle service is on.
Step 4, a memory kill. One executor runs a Python UDF that loads a 3 GB model into each Python worker. That memory is outside the 20 GB JVM heap, so it must fit in the 2 GB overhead, and it does not. The NodeManager sees the container's process tree reach about 24 GB against a 22 GB limit and kills it. The fix is to raise `spark.executor.memoryOverhead` (for example to 6 GB, making a 26 GB container), which means only 4 executors per node (104 GB) and 80 instead of 100 in total. Every memory setting changes how many executors the cluster can hold.
intuition: YARN is a central booking office for a shared building: each team's manager phones in exact room requests, the office books rooms according to each team's quota, and the managers decide what happens inside the rooms.
The split is natural once you ask who knows what. Only the cluster as a whole knows which machines are free and how much each team is entitled to; only the application knows its tasks, its data locations and how to recover from a failed task. Hadoop 1 put both kinds of knowledge into one JobTracker, which therefore had to understand MapReduce and could not scale. YARN gives each kind of knowledge its own process. The ResourceManager stays generic and keeps the global view needed for fair queues and preemption. The ApplicationMaster stays specific, so a new engine only needs a new AM, not changes to the cluster. Because applications ask explicitly, rather than being offered pieces as in Mesos, the central scheduler can see all pending demand at once.
mistakes: People often think YARN schedules Spark tasks. In fact YARN allocates containers for the driver and executors; Spark's own scheduler, inside the driver, decides which task runs in which executor. YARN never sees individual Spark tasks.
People often think a vcore is a physical CPU core that YARN reserves. In fact vcores are numbers configured per node; YARN only enforces CPU limits when cgroups are enabled, and with the default memory-only calculator it may not even count vcores when packing containers.
People often think the executor memory setting is the container size. In fact the container is executor memory plus overhead (and off-heap memory, if configured), rounded up to the minimum allocation. Memory kills almost always come from the part outside the JVM heap.
People often think YARN is obsolete because Kubernetes exists. In fact YARN still runs a large share of Spark and Hive workloads on EMR, Dataproc and on-premises Hadoop, it is still released (3.5.0 in 2026), and its queues, preemption and data-local scheduling remain more mature for shared batch clusters than Kubernetes' defaults.
friction: YARN is tied to the Hadoop ecosystem. It assumes Hadoop configuration files, Kerberos for security, HDFS for staging application files and logs, and Java-based daemons. Packaging dependencies is awkward: containers traditionally run on the host's operating system and Python environment, so a Python job needs its environment shipped as an archive or a Docker runtime that must be configured on every node. Long-running services are possible (the services framework, Docker containers) but much less natural than on Kubernetes, which has richer service discovery, rolling updates and a large tool ecosystem.
Resource accounting is coarse. Memory limits are enforced by periodic monitoring, so short spikes can pass and steady growth is killed; there is no memory sharing or overcommit by default, so clusters tuned for safety often sit at low real usage. Rounding to the minimum allocation and packing fixed-size containers leave gaps, as the example showed. Preemption kills work, which wastes compute and, without an external shuffle service, forces recomputation.
At scale, the single active ResourceManager becomes a bottleneck around several thousand machines and large numbers of pending requests, so very large sites use Federation, which adds a router and state store. Configuration is spread across many XML files with hundreds of settings whose defaults are rarely right. Finally, the momentum has moved away: Spark on Kubernetes, Databricks and serverless engines attract most new investment, so YARN expertise is getting rarer even where YARN still runs.
practice: Size containers deliberately. Start from the node: leave memory for the OS, the NodeManager and the DataNode, and set the NM memory and vcores to what remains. Choose executor sizes that divide that number well (for example 5 executors of 22 GB in 112 GB), set the overhead explicitly for jobs with Python or native libraries, and enable the DominantResourceCalculator so CPU is counted. Enable cgroups if teams share nodes and you need CPU isolation.
Design queues around teams and service levels: guaranteed capacity for production pipelines, elastic capacity for ad hoc work, user limits so one person cannot take a queue, and preemption with a timeout that matches how long production can wait. Turn on Spark's external shuffle service (or YARN's equivalent for your engine) together with dynamic allocation, so idle executors return to the queue without losing shuffle data.
Monitor pending versus allocated resources per queue, container kills by reason, AM attempts and NodeManager health. Read the NodeManager logs when a container dies: "exceeding physical memory limits" means raise the overhead or reduce per-executor parallelism, not executor heap. For new platforms without existing Hadoop, prefer Kubernetes or a managed Spark service; for existing Hadoop clusters, YARN on Hadoop 3.4 or 3.5 remains a sound, well-understood choice, and migration should be driven by a concrete need, not by fashion.

@@ hive
value: Apache Hive is a SQL data warehouse built on Hadoop. You write queries in HiveQL, a dialect of SQL, against tables whose data lives as ordinary files in HDFS or object storage. Hive compiles each query into a graph of distributed batch tasks (first MapReduce, today mostly Apache Tez) that YARN runs across the cluster. It also introduced the Hive Metastore, the catalog that maps a table name to its schema, file format and directory, which Spark, Trino, Impala and table formats such as Iceberg still use.
The problem it solved was access. In 2007 Facebook was storing large and fast-growing volumes of logs in Hadoop, but every question required a Java MapReduce program, written and debugged by an engineer. Analysts knew SQL, not MapReduce. Hive let them write `SELECT ... GROUP BY` and get a MapReduce job automatically. It also turned a pile of files into something that looked like a database: named tables, typed columns and partitions, defined once and shared by everyone. That pattern, files in a distributed file system plus a shared catalog plus SQL engines on top, is the "data lake", and later the lakehouse, which most data platforms still follow.
Hive stands on four lower concepts. Batch processing (L1) provides the execution model: queries become jobs of many parallel tasks that read large inputs, shuffle by key and write outputs, with failed tasks simply re-run. Distributed SQL (MPP, L1) provides the query-processing ideas: parallel scans, partitioned aggregation, shuffle and broadcast joins, and cost-based optimization. The Hive Metastore (L0) provides the catalog that stores schemas and partition locations, which is what makes a directory a table. HDFS (L0) provides the storage: a table is a directory, a partition is a subdirectory, and HDFS's atomic rename is how Hive publishes results. Today Hive execution is mostly replaced by Spark SQL, Trino and lakehouse engines, but its table model and metastore are everywhere.
terms: HiveQL — Hive's SQL dialect, with extensions for partitions, file formats and custom functions.
Schema on read — data is stored as files without checking it; the table's schema is applied only when a query reads the files.
Partition — a subset of a table stored in its own directory, named by a column value, such as `dt=2026-10-26/`; filters on that column skip whole directories.
Bucketing — splitting each partition into a fixed number of files by a hash of a column, which helps joins and sampling.
SerDe — serializer/deserializer: the code that turns bytes in a file into rows and columns, and back.
ORC — Optimized Row Columnar, a columnar file format created for Hive, with stripes, lightweight indexes and compression.
Tez — a DAG execution engine on YARN that runs a whole query as one job, replacing chains of MapReduce jobs.
LLAP — Live Long and Process: long-running Hive daemons with an in-memory data cache, for interactive queries.
ACID table — a Hive table that supports insert, update, delete and merge with transactions, using base and delta files plus compaction.
HiveServer2 — the service that accepts JDBC and ODBC connections, compiles queries and returns results.
history: Hive started at Facebook in 2007, led by Joydeep Sen Sarma and Ashish Thusoo. It was contributed to Hadoop in 2008, became an Apache Hadoop subproject and then, in 2010, a top-level Apache project. The VLDB 2009 paper "Hive: A Warehousing Solution over a Map-Reduce Framework" (Thusoo and colleagues) described the design: tables and partitions in HDFS directories, a metastore in a relational database, and a compiler that turns HiveQL into a DAG of MapReduce jobs. At Facebook, Hive quickly became the main way people used Hadoop.
MapReduce made Hive slow: every query stage was a separate job with tens of seconds of start-up cost, and every intermediate result was written to HDFS. From 2013, Hortonworks' "Stinger" initiative rebuilt the engine. ORC files arrived in Hive 0.11 (2013), HiveServer2 brought concurrent JDBC/ODBC clients, Tez became an execution engine, vectorized execution processed batches of rows instead of one row at a time (0.13, 2014), and a cost-based optimizer built on Apache Calcite arrived in 0.14 (2014). ACID transactions came in 0.14, and LLAP in Hive 2.0 (2016). Hive 3.0 (2018) made transactional tables the default for managed tables and changed their on-disk layout. Meanwhile Hive on Spark was added as another engine, and Facebook itself built Presto (2012) for interactive queries over the same metastore and files.
From about 2015, Spark SQL, Presto/Trino and Impala took most new workloads, because they were faster and easier to deploy. Hive's execution engine kept its users mainly in Hadoop distributions such as Cloudera's. Hive 4.0.0 (March 29, 2024) removed Hive on Spark and pointed users to Tez, and added native Iceberg table support. The 1.x, 2.x and 3.x lines were declared end of life in 2024. Hive 4.1.0 (July 2025) added JDK 17 support, a standalone metastore binary and Docker image, and a REST catalog server; 4.2.0 (November 2025) requires JDK 21; 4.2.1 (August 2026) fixed security issues.
how: A table in Hive is metadata plus a directory. `CREATE TABLE imps (user_id BIGINT, country STRING, cost DOUBLE, ...) PARTITIONED BY (dt STRING) STORED AS ORC` records in the metastore the columns, the partition column, the SerDe and file format, and a location such as `hdfs://nn/warehouse/imps/`. Each partition is a subdirectory, `.../imps/dt=2026-10-26/`, holding many ORC files. Note that dt is not stored inside the files; its value comes from the directory name. An external table points at files that other tools write, and dropping it keeps the files; a managed table's files belong to Hive. Because the schema is applied on read, loading data is just moving files into a directory, which is fast but means bad files are discovered only when queried.
A query arrives through HiveServer2 (from Beeline, a BI tool over JDBC or ODBC, or Airflow). The compiler parses HiveQL into a syntax tree, resolves names against the metastore, and builds a tree of logical operators: table scan, filter, join, group-by, reduce sink (the point where rows are shuffled by key) and file sink. The Calcite-based optimizer reorders joins using table and column statistics stored in the metastore, pushes filters down, and prunes partitions: with `WHERE dt >= '2026-10-20'`, it asks the metastore for the matching partitions only, so the other directories are never listed or read. Column pruning tells the ORC reader which columns to decode.
The physical plan cuts the operator tree at every shuffle. Each piece becomes a stage: with MapReduce, each stage is a separate MapReduce job; with Tez, each piece is a vertex in a single DAG. Map-side work (scan, filter, partial aggregation, broadcast join) runs in tasks that each read one input split, often a 256 MB range of a file, close to where HDFS stores the block. Reduce-side work (final aggregation, shuffle join, sort) receives rows partitioned by the hash of the key. This is the batch-processing contribution: thousands of independent tasks, a shuffle between stages, and fault tolerance by re-running any task whose machine fails. The MPP contribution is in the join and aggregation strategies. A map join loads a small table into a hash table in every task (a broadcast), avoiding a shuffle; Hive converts joins to map joins automatically when the small side is below a size threshold. A shuffle join sends both sides by join key to reducers. Bucket map joins and sort-merge-bucket joins use matching bucketing on both tables to join file by file without a full shuffle.
The engine matters for latency. In MapReduce, each stage starts a new job (application master, container requests, JVMs), which costs tens of seconds, and writes its output to HDFS with three replicas before the next stage can read it. Tez runs the whole DAG in one application, streams data between vertices through the shuffle, reuses containers between tasks, and can keep a session open between queries. Vectorized execution processes batches of 1,024 rows per operator call over ORC columns. LLAP goes further: long-running daemons on each node cache ORC data in memory in columnar form and execute query fragments, while Tez coordinates, so short queries can return in a second or two.
ORC is the storage half of this speed. A file is divided into stripes (often 64 MB or more) that store each column separately with run-length and dictionary encoding plus general compression such as Zlib, Snappy or Zstd. A light index keeps min/max values every 10,000 rows, and optional Bloom filters can be added per column, so a filter such as `country = 'IN'` can skip row groups inside a stripe. The file footer holds the stripe locations and column statistics, so a reader decodes only the columns and stripes it needs.
Transactions were added on top of immutable files. HDFS cannot update a file in place, so an ACID table stores a base directory plus delta directories. Each transaction gets a write ID from the metastore's transaction manager; an insert writes a new delta, and an update or delete writes delta or delete-delta files that refer to rows by ID. A reader merges the base with all committed deltas that are visible to its snapshot. Background compaction merges many small deltas into one (minor) or rewrites base plus deltas into a new base (major). Non-transactional tables use a simpler commit: tasks write files to a temporary directory, and when the job succeeds Hive renames the directory into place. On HDFS a rename is atomic and costs one metadata operation; on S3 it is a copy of every file, which is why directory-based tables are fragile on object storage.
The metastore is the piece that outlived the engine. It is a Thrift service backed by a relational database (MySQL or PostgreSQL), storing databases, tables, columns, partitions, locations, statistics, transactions and locks. Spark SQL, Trino, Impala, Flink and many other engines read and write the same metastore, so a table created by Hive is visible to all of them. Iceberg's Hive catalog stores only a pointer to the current metadata file in the metastore, and lets Iceberg handle the rest.

example: A table `imps` holds one year of ad impressions, partitioned by day: 365 partitions of about 200 GB of ORC each, roughly 73 TB, with 40 columns. An analyst runs `SELECT country, count(*) FROM imps WHERE dt BETWEEN '2026-10-20' AND '2026-10-26' AND platform = 'ctv' GROUP BY country`.
Step 1, partition pruning. The compiler asks the metastore for partitions with dt in that range and gets 7 directories back. The other 358 are never listed. The input drops from 73 TB to 7 × 200 GB = 1.4 TB of files.
Step 2, column pruning. Only country and platform are needed. Both are low-cardinality strings, which ORC dictionary-encodes into a few bits per row. Suppose they take 3% of the bytes; then about 1.4 TB × 0.03 ≈ 42 GB is actually decoded. Without columnar files, for example with text files, all 1.4 TB would be read and parsed.
Step 3, tasks. If Hive creates one map task per 256 MB of file, 1.4 TB gives about 5,500 tasks, and each decodes only about 8 MB of column data. On a cluster that gives this query 500 containers, that is 11 waves of tasks. Here task overhead, not data, dominates: if each task costs about 1 second of start-up and scheduling, overhead alone is about 11 seconds of wall time. Grouping several splits into one task (Tez does this) or using larger files cuts this cost directly.
Step 4, MapReduce versus Tez. This query has one shuffle, so MapReduce needs one job. Add a join to a campaign table and an ORDER BY with LIMIT 10, and MapReduce needs about three jobs. If each costs about 20 seconds to start and writes its output to HDFS with three replicas, a query over little data still takes about a minute before any real work. Tez runs the same plan as one DAG with three vertices, starts once, and passes data through the shuffle, so the same query takes seconds. The map join helps too: a 50 MB campaign table broadcast to 500 containers costs 25 GB of network transfer in total but avoids shuffling 7 days of impressions.
Step 5, the cost of small transactions. Suppose a streaming job writes into an ACID version of this table every minute, with 4 buckets. One day's partition then gets 1,440 delta directories with 4 files each, about 5,760 small files. A query must open and merge all of them, and listing them alone takes noticeable time. A minor compaction merges the deltas into one delta per bucket; a major compaction rewrites everything into a new base. Without regular compaction, read latency grows every hour the table is written.
intuition: Hive put a SQL front door on a distributed file system: the files stay where they are, and a shared catalog says which directory is which table.
The design was natural for its time and constraints. Hadoop already stored the data, and MapReduce already knew how to process it in parallel; the missing parts were a language people already knew and a shared definition of what the files meant. Mapping tables to directories and partitions to subdirectories needed no new storage system, made loading data as cheap as moving files, and let any program that could write files feed the warehouse. Schema on read fit messy log data whose format changed often. Compiling SQL into the existing batch engine reused its scale and fault tolerance. Every later improvement (ORC, Tez, vectorization, the cost-based optimizer, LLAP) kept this model and only removed overhead from it, which is why the model survived even where the engine did not.
mistakes: People often think Hive is a database that stores data. In fact Hive stores only metadata in the metastore; the data is plain files in HDFS or object storage, which other engines can read and write directly, sometimes behind Hive's back.
People often think partitions are always good, so more partitions are better. In fact each partition is a directory plus a metastore entry. Partitioning by hour and customer can create millions of tiny partitions, which slows the metastore, query planning and file listing more than pruning saves.
People often think Hive is still the MapReduce engine they knew. In fact modern Hive runs on Tez with vectorization, a Calcite optimizer and optionally LLAP; Hive on Spark was removed in 4.0, and MapReduce has been deprecated as a query engine since Hive 2.0.
People often think the metastore is part of Hive that dies with it. In fact the metastore is used by Spark, Trino, Impala, Flink and Iceberg's Hive catalog, and since 4.1 it ships as a standalone service. Many companies run the metastore without running any Hive queries.
friction: Directory-based tables have weak guarantees. Adding a partition, writing files and updating statistics are separate steps, so a reader can see a half-written partition, and two writers can overwrite each other. Commits rely on rename, which is atomic on HDFS but a slow copy on S3. Schema changes are fragile: renaming or reordering columns can make old files read wrong values, depending on the format. Table formats such as Iceberg, Delta Lake and Hudi fixed these problems with snapshot metadata and atomic commits, which is why new tables increasingly use them, often still registered in a Hive Metastore.
Performance and operations remain costly. Even on Tez, query start-up, task scheduling and YARN container allocation add seconds, so Hive is slower than Trino or Spark for interactive work unless LLAP is deployed, which adds long-running daemons and memory to manage. ACID tables need compaction to stay fast, and stuck or failed compactions are a common cause of slow queries. Small files from frequent loads hurt every engine that reads the table.
The metastore is a central dependency. A large number of partitions makes `get_partitions` calls slow and the backing database large; a single overloaded metastore can stall every engine in the company. Finally, the community and the vendors have moved on: most new investment goes to Spark, Trino and lakehouse catalogs, and Hive 4.2 requires JDK 21, so upgrading old clusters is a project in itself.
practice: Treat Hive's table model as the thing to understand, and Hive's engine as one choice among several. On an existing Hadoop cluster, run Hive 4 on Tez with ORC, vectorization and the cost-based optimizer, and compute statistics (`ANALYZE TABLE ... COMPUTE STATISTICS FOR COLUMNS`) so join ordering works. Use LLAP only when you need interactive latency and can afford the dedicated memory.
Design partitions for the filters people actually use, usually one date column at daily granularity, and keep each partition at hundreds of megabytes to many gigabytes. Avoid partitioning by high-cardinality columns; use bucketing or file sorting instead. Fight small files: write fewer, larger files, schedule compaction on ACID tables and watch the compaction queue.
For new tables, prefer an open table format. Hive 4 can create and query Iceberg tables directly, which gives atomic commits, hidden partitioning and safe schema evolution while keeping the same metastore for discovery. When migrating Hive SQL to Spark SQL or Trino, test carefully: functions, implicit casts, null handling and integer division differ slightly between dialects. Keep the metastore healthy: back up its database, size it for the number of partitions, and monitor its latency, because every engine depends on it.

@@ velox
value: Velox and Apache DataFusion are query-engine libraries: reusable, fast implementations of the parts of a database that actually process data, which other systems embed instead of writing their own. Velox, from Meta, is a C++ execution engine: it takes a plan that some other system has already optimized and runs it, with vectorized expressions, joins, aggregations, file readers, memory management and spilling. DataFusion, an Apache project written in Rust on Apache Arrow, is a more complete toolkit: it also includes a SQL parser, a DataFrame API, a planner and an optimizer, and every layer can be extended.
The problem is duplication. Meta found that its many data systems (Presto for interactive SQL, Spark for batch, stream processors, machine-learning data pipelines) each had its own execution engine, built and tuned separately. The same work was done several times, and the engines disagreed on details such as how a function treats nulls, which confused users who moved between them. Across the industry, every new database or time-series store spent years building a vectorized engine before it could work on what made it different. A shared engine library turns that cost into a dependency: improve the library once, and every system that embeds it gets faster.
These libraries now sit under many systems. Velox runs Presto C++ (Prestissimo) at Meta and IBM, and Apache Gluten, which offloads Spark SQL execution to Velox. DataFusion runs InfluxDB 3, GreptimeDB, Lance, delta-rs, the dbt Fusion engine and many smaller engines, plus Apache DataFusion Comet, another Spark accelerator. They stand on three lower concepts. OLAP analytics (L1) gives the techniques: columnar batches, vectorized operators and scan-heavy query patterns. Distributed SQL (MPP, L1) gives the context in which Velox works: the host engine splits a query into fragments and ships them to workers, and Velox runs each fragment, including the exchange operators that shuffle data between workers. C / C++ (L0) gives Velox control over memory and SIMD; DataFusion gets similar control from Rust.
terms: Execution engine — the part of a database that runs a physical plan over data: scans, filters, expressions, joins, aggregations, sorts.
Composable data system — a database assembled from shared, replaceable components (parser, optimizer, execution engine, file formats) instead of one monolith.
Plan fragment — the piece of a distributed query plan that runs on one worker between two shuffles.
Vector (RowVector, RecordBatch) — a batch of rows stored column by column; Velox calls batches RowVectors, DataFusion uses Arrow RecordBatches.
Encoding — how a vector stores values: flat (one value per row), constant (one value for all rows), dictionary (indices into a smaller set of values) or run-length.
Dictionary peeling — evaluating a function once per distinct dictionary value instead of once per row.
Substrait — an open, cross-language specification for query plans, used to hand a plan from one system to another.
Fallback — running an operator in the host engine (for example, Spark's JVM) when the native library does not support it, with conversion of data between formats.
Spilling — writing operator state (hash tables, sorted runs) to disk when memory runs out.
history: Database research had shown for years that vectorized, columnar execution was much faster for analytics: MonetDB/X100 (2005), then VectorWise, HyPer, and commercial engines. But each system implemented it alone. Meta built Velox to unify its engines and open-sourced it in 2022; the paper "Velox: Meta's Unified Execution Engine" (Pedreira and colleagues) appeared at VLDB 2022. It reported Prestissimo, Presto with Velox workers, reaching close to 10× speedups on some CPU-bound TPC-H queries and 6 to 7× on average on production interactive queries. Ahana (later part of IBM), Intel and Voltron Data were early partners, and Intel started Gluten to plug Velox into Spark. In 2023 Velox's authors and others published "The Composable Data Management System Manifesto" (VLDB 2023), which argued that databases should be built from shared components with open interfaces such as Arrow and Substrait.
DataFusion has a different origin. Andy Grove started it as a personal Rust project in the late 2010s and donated it to the Apache Arrow project in 2019. A broad community, including InfluxData, which rebuilt InfluxDB 3 on it, grew it into a full engine. The SIGMOD 2024 paper "Apache Arrow DataFusion: A Fast, Embeddable, Modular Analytic Query Engine" (Lamb and colleagues) described its design, and in 2024 it became a top-level Apache project. Apple donated the Comet Spark accelerator, built on DataFusion, in 2024. In the ClickBench results of November 2024, DataFusion 43 was the fastest engine for querying Parquet files, the first Rust engine to hold that position.
By October 2026 both are mature. DataFusion releases a major version about every two months: 54.0.0 in June 2026 and 55.0.0 in August 2026, with Comet 1.0 in August 2026. Velox has no numbered releases; engines build it from source. It moved to C++20 in 2025, gained an experimental GPU backend through NVIDIA cuDF (IBM and NVIDIA announced GPU-accelerated Presto C++ in June 2026), and Gluten became a top-level Apache project with Velox and ClickHouse backends.
how: Velox starts where planning ends. A host engine, such as a Presto coordinator, parses SQL, optimizes the plan and cuts it into fragments. Each worker receives a fragment as a tree of Velox plan nodes: table scan, filter, project, hash join, aggregation, order by, exchange. Velox has no SQL parser or optimizer of its own; it accepts a plan, which is what lets very different systems share it. The worker turns a fragment into a Task. A Task contains one or more pipelines, and each pipeline runs on several Drivers (threads); a Driver moves batches through a chain of Operators, from a source (a file scan or an exchange that receives shuffled data from other workers) to a sink (a hash-table build, an exchange that sends data, or the output). This is how Velox fits into distributed SQL: the host does the distribution, Velox does the fast work inside each node, including sending and receiving data in the host's wire format (Presto pages or Spark's UnsafeRow).
Data moves as vectors, the OLAP part of the design. A RowVector holds one child vector per column, and each child keeps its encoding: flat, constant, dictionary or run-length. Velox avoids decoding whenever it can. A Parquet column that is dictionary-encoded arrives as a dictionary vector; a filter that passes few rows wraps its input in a new dictionary of selected indices instead of copying; columns that a later filter may discard are lazy vectors, loaded only for rows that survive. Strings use a 16-byte view: a length, a 4-byte prefix, and either the rest of the string inline (up to 12 bytes) or a pointer. The same layout became Arrow's StringView, and Polars, DuckDB and DataFusion use equivalent layouts, which lets these systems exchange string data without conversion.
Expression evaluation is where most CPU time goes, and Velox spends much of its design there. Expressions are compiled into a tree once per query and then evaluated per batch. Dictionary peeling evaluates a function over the distinct values of a dictionary and reuses the result for every row that points to them. Constant inputs are evaluated once. Common subexpressions are computed once. For filters joined by AND, Velox measures each condition's time per row and the fraction of rows it passes while the query runs, and it reorders them so that cheap, selective conditions go first. Functions come in packages with Presto semantics or Spark semantics, because the same function name can behave differently in the two systems (for example, on integer overflow or invalid input), and the host must get exactly its own behavior.
Memory is managed explicitly, which is where C++ adds value. Every query has a tree of memory pools (query, task, operator), and an arbitrator moves memory between queries. When a hash join, aggregation or sort cannot grow, it spills partitions to disk and processes them later. C++ also lets Velox use SIMD intrinsics directly for filters, hashing and decoding, choose its own allocators, and avoid any garbage collector, which is why Spark (a JVM engine) gains by sending work to it.
DataFusion covers the whole path, in Rust on Arrow. SQL text is parsed by the sqlparser-rs library into an abstract syntax tree, converted into a LogicalPlan, and optimized by a list of rules: pushing filters and projections down, simplifying expressions, removing common subexpressions, decorrelating subqueries, and choosing join order and sides. The physical planner then builds an ExecutionPlan tree. Each node produces a number of output partitions as asynchronous streams of Arrow RecordBatches (8,192 rows by default), and the Tokio runtime schedules them across cores. Parallelism comes from partitioning: a RepartitionExec node redistributes batches by hash or round-robin between partitions, like the exchange operator in classic parallel databases. The Parquet reader prunes row groups and pages using statistics and Bloom filters and applies filters during decoding; since 2025, dynamic filters let a join or a top-N operator send a filter back to the scan while the query runs.
Extensibility is DataFusion's main design goal. A system can add its own table providers (data sources), catalogs, scalar, aggregate and window functions, optimizer rules, and custom plan nodes, and it can replace the SQL front end or skip it. InfluxDB adds time-series operators and its own storage; Comet takes Spark's physical plan, translates the supported parts into DataFusion plans and runs them natively inside Spark executors; Ballista distributes DataFusion plans across a cluster. Because the data is Arrow, results can be passed to Python, Polars, DuckDB or Arrow Flight without conversion.
The Spark accelerators show the contract between host and library. Gluten takes the physical plan after Spark's optimizer, converts the supported operators to Substrait, and runs them in Velox (or ClickHouse) through JNI inside each executor. Operators that the library cannot run fall back to Spark, with a conversion from columnar batches to Spark rows and back at each boundary. Gluten reports overall speedups of about 3× on TPC-H and TPC-DS at 3 TB, but real gains depend on how much of each query stays native.

example: A Spark job runs `SELECT country, sum(cost) FROM imps WHERE regexp_like(url, '/video/') AND upper(country_code) IN ('IN', 'US') GROUP BY country` over 1 billion rows of Parquet. The cluster enables Gluten with the Velox backend. Follow three mechanisms with numbers.
First, dictionary peeling. country_code is dictionary-encoded in Parquet with 200 distinct values. A row-at-a-time engine calls upper() 1 billion times. Velox receives dictionary vectors: if each batch of 10,000 rows carries a dictionary of up to 200 values, Velox calls upper() at most 200 times per batch, 100,000 batches × 200 = 20 million calls instead of 1 billion, 50 times fewer. When consecutive batches share the same dictionary, Velox can reuse earlier results, and the count falls further. The IN test also runs once per distinct value; each row then only looks up its precomputed result.
Second, filter order. Suppose the regular expression costs about 100 ns per row and passes 50% of rows, while the country test costs about 2 ns per row (after peeling) and passes 5%. In the written order, regex first, the cost per row is 100 + 0.5 × 2 = 101 ns, or 101 seconds of CPU for 1 billion rows. Velox measures both while running and moves the cheap, selective test first: 2 + 0.05 × 100 = 7 ns per row, about 7 seconds of CPU. That is about 14 times less work, found at run time without any statistics from the optimizer.
Third, the cost of fallback. Suppose the query also used a Spark function that Velox does not support, applied after the filter. Gluten must convert the surviving 25 million rows from Velox's columnar vectors to Spark's UnsafeRow format, run the function in the JVM, and convert back. If each conversion costs about 50 ns per row, that adds 25 million × 2 × 50 ns ≈ 2.5 seconds of CPU, which is acceptable. If the unsupported function were in the first filter, all 1 billion rows would be converted twice: about 100 seconds, more than the whole native query costs. That is why the first job in a Gluten or Comet rollout is to read the plan and find fallbacks, which both projects report in Spark's plan and UI.
For comparison, the same query in DataFusion SQL would be planned by DataFusion's own optimizer, read with 8,192-row Arrow batches split across the cores' partitions, and run without any JVM conversion at all. The trade-off is that DataFusion's SQL dialect and function behavior are its own, not Spark's or Presto's.
intuition: Velox and DataFusion are engine parts sold separately: like car makers buying the same proven gearbox, database builders share one well-tuned execution core and compete on everything else.
The idea is natural once you look at what modern analytic engines have in common. Inside one machine, they all scan columnar files, evaluate expressions over batches, build hash tables and spill when memory runs out, and the best techniques for each are known from research. What differs between systems is the outside: the SQL dialect, the catalog, the distribution strategy, the storage format, the user experience. Building the shared inside once, with clean inputs (a plan) and outputs (Arrow-compatible batches), lets each system focus on its own outside. It also makes behavior consistent: if two engines use the same function package, they compute the same answer.
mistakes: People often think Velox is a database or a query engine you can use directly. In fact Velox has no SQL parser, optimizer or client; it runs plans that a host system produces. DataFusion is closer to a usable engine (it has SQL and a CLI), but it is still mainly a library for building systems.
People often think plugging Velox or DataFusion into Spark makes every query several times faster. In fact gains depend on which operators and functions run natively. Fallbacks to the JVM add conversions, and I/O-bound or shuffle-bound jobs gain less than CPU-bound ones.
People often think a shared engine guarantees identical results across hosts. In fact SQL dialects differ in null handling, casting, overflow, rounding and string functions. Velox keeps separate Presto and Spark function packages for this reason, and mismatches still appear as bugs during migrations.
People often think DataFusion and Velox are interchangeable. In fact Velox is C++, execution-only and tied closely to Presto and Spark semantics; DataFusion is Rust, Arrow-native and covers SQL, planning and execution with extension points at every layer. The choice usually follows the host's language and how much of the engine you want to own.
friction: Integration is the hard part. A host must translate its plans, types and function semantics exactly, and every gap becomes either a fallback or a wrong answer. Decimal precision, timestamp time zones, collation and nested types are common sources of differences. Keeping that translation layer up to date as both the host and the library change is continuous work; Gluten and Comet each have teams dedicated to it.
Native code changes operations. A crash in C++ or unsafe Rust code can bring down a whole Spark executor, and memory used outside the JVM must be configured separately (off-heap settings), or YARN and Kubernetes kill containers. Debugging spans two languages and two runtimes, and profiles are harder to read.
Each library also has its own limits. Velox has no numbered releases and is built from source by each host, so versions are pinned by commit, and its governance remains led by Meta rather than a foundation. Its distributed behavior depends entirely on the host. DataFusion's partition-based parallelism can be less adaptive to skew than morsel-driven schedulers such as DuckDB's, and its rapid release cycle (a major version about every two months) means API changes for embedders. Both work best for analytical batch work; neither is designed for transactional workloads. Finally, the commercial proprietary engines in the same space, such as Databricks Photon or Snowflake's engine, are not open, so comparisons rely on vendor benchmarks.
practice: If you run Spark yourself and your jobs are CPU-bound (heavy expressions, aggregations, joins on Parquet), try Gluten with Velox or DataFusion Comet on a copy of real workloads. Start with the physical plan: list every fallback, fix or replace the functions that cause them, and measure end-to-end cost, not single-query speed. Set off-heap memory explicitly and watch native memory and spill metrics. On Databricks, the comparable choice is enabling Photon, which follows the same design but is proprietary.
If you are building a data product, such as a domain-specific database, a time-series store or a query service over your own format, start with DataFusion if your stack is Rust or Arrow-based. Implement a TableProvider for your storage, add your functions, and keep the rest. Choose Velox if you are building in C++ or need Presto or Spark semantics. In both cases, invest early in a test suite that compares results with a reference engine.
To learn the techniques, read the Velox paper for encodings, lazy vectors and adaptive filters, the DataFusion paper for an extensible engine design, and the Composable Data Management System Manifesto for why the industry is moving this way. Reading DataFusion's optimizer rules and physical operators is one of the most practical ways to study a real query engine end to end.
quiz: What is the main difference in scope between Velox and DataFusion? || Velox is an execution-only C++ library: it runs already-optimized plans and has no SQL parser or optimizer. DataFusion, in Rust on Arrow, includes SQL parsing, planning, optimization and execution, each extensible.
How does dictionary peeling save work in Velox? || When a column is dictionary-encoded, Velox evaluates a function once per distinct dictionary value and reuses the result for every row that references it, instead of evaluating it once per row.
Why does adaptive filter reordering help, and why must it happen at run time? || Evaluating cheap, selective conditions first means expensive ones run on fewer rows. Costs and selectivities depend on the actual data and functions, which the optimizer often cannot estimate, so Velox measures them while the query runs.
Filter A costs 80 ns per row and passes 40%; filter B costs 4 ns and passes 10%. What is the cost per row for each order? || A then B: 80 + 0.4 × 4 = 81.6 ns. B then A: 4 + 0.1 × 80 = 12 ns, about 7 times cheaper.
Your Spark jobs on YARN are CPU-bound, but many use custom Scala UDFs. Would you adopt Gluten? || Test carefully first. Custom JVM UDFs cannot run in Velox, so each one causes a fallback with columnar-to-row conversions that may cancel the gains. Adopt it for jobs that stay mostly native, and consider rewriting hot UDFs as built-in expressions.
