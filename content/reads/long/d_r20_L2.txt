@@ eventloop
value: An event loop lets one thread serve thousands of network connections. Instead of blocking on one connection until data arrives, the thread asks the operating system "which of my connections are ready right now?", handles only those, and asks again. The thread never sleeps while there is work, and it never waits on a connection that has nothing to say.
This solves a cost problem. The simple design is one thread per connection. It is easy to write, but every thread needs its own stack and kernel structures, and the scheduler must switch between them. At 10,000 connections this means 10,000 threads, memory pressure, and a lot of context switches, even though most connections are idle at any moment. This problem was famous around 1999 as the C10K problem (how to serve ten thousand clients on one machine). An event loop removes both costs: one thread, a small per-connection state object, and work only when the kernel reports an event.
For the layer above, the event loop is the base of almost every high-concurrency network server: NGINX, HAProxy, Envoy, Redis, Memcached, Node.js, Netty (which sits under many JVM services, and Kafka's network layer uses the same selector idea), Python asyncio, and the thread-per-core databases such as ScyllaDB and Redpanda. It gives caches and web front ends their low and steady latency. The layers below make it possible. I/O models (epoll, kqueue, io_uring) give the "which sockets are ready" call at a cost that depends on the number of ready sockets, not the number of open sockets. Context switching explains what a loop avoids paying. Threads explain what is being replaced, and why a loop still uses a few threads for blocking or CPU-heavy work.
terms: Reactor — the design pattern in which one loop waits for readiness events and dispatches each event to a handler.
Non-blocking socket — a socket on which read and write return at once with an error code (EAGAIN) instead of waiting when there is nothing to do.
Readiness notification — an OS report that a descriptor can be read or written without blocking (epoll, kqueue, poll).
Level-triggered — the OS keeps reporting a socket as ready for as long as unread data remains.
Edge-triggered — the OS reports a socket only when its state changes, so the handler must read until EAGAIN or it will not hear about the leftover data.
Handler (callback) — the small piece of code the loop runs for one event; it must finish quickly and must not block.
Completion-based I/O — the style in which you submit an operation (io_uring, Windows IOCP) and the OS tells you when it is finished, instead of telling you when you may start it (the proactor pattern).
Backpressure — slowing or pausing reads from a client when the output you owe it, or the work queue, is already too long.
history: Servers started with one process or thread per client. In 1983 the 4.2BSD system added select(), which let a single process wait on many descriptors, and System V added poll(). Both make the kernel scan every descriptor on every call, so cost grows with the number of open connections, and select() was limited to 1,024 descriptors by default. Douglas Schmidt described the Reactor pattern in 1995, giving the design its name: a synchronous demultiplexer waits for events and a dispatcher calls the right handler. In 1996, John Ousterhout gave his talk "Why Threads Are a Bad Idea (for most purposes)", arguing that event-driven code is simpler to reason about than threads that share state.
In 1999, Dan Kegel's page "The C10K problem" collected the techniques for serving 10,000 clients and made the case that the operating system interface, not the hardware, was the limit. The kernels responded. Jonathan Lemon added kqueue to FreeBSD 4.1 in 2000, and Davide Libenzi added epoll to Linux 2.5.44 in 2002. Both let the kernel keep the set of watched descriptors and return only the ready ones. Windows had its own completion-based answer, I/O completion ports, since 1994.
Libraries and servers followed. libevent appeared in 2000, NGINX was released in 2004 by Igor Sysoev as an answer to C10K for Apache-style servers, and Netty started in 2004 for Java. In 2009 Ryan Dahl released Node.js, which put an event loop (later the libuv library) under JavaScript, and Salvatore Sanfilippo released Redis, whose command execution runs on one thread. Python's asyncio arrived in 2014. In 2019 Jens Axboe added io_uring to Linux 5.1, which moves from "tell me when it is ready" to "do this and tell me when it is done", and removes most system calls from the hot path. Since JDK 21 (2023), Java virtual threads let you write blocking-style code while the runtime uses a poller underneath, which shows that the loop did not disappear; it moved below the programming model.
how: Setup comes first. The server creates a listening socket and puts it, and every accepted client socket, into non-blocking mode. It creates an epoll instance (epoll_create1) and registers each descriptor with the events it cares about (epoll_ctl with EPOLLIN for "readable"). The kernel now holds the interest list. This is the main contribution of the I/O model layer: with select or poll the program passes the whole list on every call and the kernel scans it, which costs O(number of watched sockets). With epoll the list lives in the kernel, the network stack adds a socket to a ready list when data arrives, and epoll_wait returns only the ready ones, so the cost is O(number of ready sockets).
The loop itself has four steps. First, call epoll_wait(epfd, events, max_events, timeout). The thread sleeps in the kernel until something is ready or the timeout ends; sleeping costs no CPU. Second, for each ready event, run its handler. For a readable socket the handler calls read() once (level-triggered) or until it returns EAGAIN (edge-triggered), appends the bytes to that connection's buffer, and checks whether a full request has arrived. Third, if a request is complete, the handler computes the reply and calls write(). If write() accepts only part of the bytes, because the socket's send buffer is full, the handler stores the rest in the connection state and registers interest in "writable" (EPOLLOUT); it must not wait. Fourth, run timers that have expired, then go back to step one.
Timers are part of the loop. The loop keeps a min-heap or a timer wheel of deadlines (idle-connection timeouts, retries, scheduled callbacks). The timeout given to epoll_wait is the time until the earliest deadline, so the thread wakes exactly when the first timer is due.
Because a handler may not wait, it cannot keep its place in the call stack. A request that needs three steps (read the request, query a backend, write the reply) must be split into three handler calls, with the progress stored in a per-connection object. This is the real cost of the style. Callbacks make the splitting explicit. Promises, and then async/await, let the compiler build this state machine for you, so the code looks sequential while each "await" is really "save state, return to the loop, resume when the event arrives". Thread switching is gone, which is the contribution of the context-switching layer: a thread switch costs roughly 1 to 5 microseconds directly plus cache misses afterwards, while a handler call is a plain function call.
Work that cannot be made non-blocking goes elsewhere. Disk file reads, DNS lookups through the C library, and CPU-heavy tasks such as compression or large JSON parsing would stop the whole loop. The loop hands them to a small pool of ordinary threads (libuv uses 4 threads by default for these) and receives the result through a wake-up channel, such as an eventfd or a pipe that is registered in epoll like any other descriptor. This is where threads still matter: the loop is one thread, and it relies on a few helper threads for the cases that do not fit.
One loop uses one core. To use all cores, servers run one loop per core. NGINX starts one worker process per core; Netty by default creates twice as many event-loop threads as cores; Envoy runs one worker thread per core. The kernel spreads new connections across loops, with SO_REUSEPORT (each loop has its own listening socket on the same port) or with a shared accept socket. A connection then lives on one loop for its whole life, so its state needs no locks. Redis shows the other extreme: commands run on a single thread, so every command is atomic without locks, and since Redis 6 optional I/O threads do only the socket reads and writes.
Finally, there are two models of I/O. Epoll and kqueue are readiness-based: the kernel says "you may read now", and the program then makes the read system call. io_uring is completion-based: the program places read, write or accept requests on a submission ring in shared memory, the kernel performs them, and the program reads results from a completion ring. Many operations can be submitted with one system call or none, and with polling mode the kernel thread picks up requests without any call. Under heavy load this removes a large share of the system-call overhead.

example: Take a service with 10,000 client connections. Each client sends one small request every 10 seconds, so the total rate is 1,000 requests per second. Each request needs about 20 microseconds of CPU: parse, look up, build a reply.
With one thread per connection, you have 10,000 threads. Even if the stack memory is mostly virtual, each thread has a kernel stack and scheduler state, and a small resident stack, so the cost is in the range of hundreds of megabytes. Each request wakes one thread, which means a context switch in and out (about 2 to 5 microseconds including cache effects, often more). The CPU time per request is 20 µs of work plus perhaps 5 µs of switching, which is fine, but the memory and the scheduler's work grow with every idle connection.
With one event loop, the 10,000 connections cost one small state object each (a few kilobytes of buffers). The work is 1,000 × 20 µs = 20 ms of CPU per second, which is 2% of one core. The loop is idle in epoll_wait for the other 98%.
Now add a hazard. Suppose 1% of requests need a slow step that takes 50 milliseconds, for example parsing a 5 MB JSON body in the handler. The slow requests arrive at 10 per second and occupy the loop for 10 × 50 ms = 500 ms of every second. The loop is blocked half of the time. A fast request that arrives at a random moment finds the loop busy with a slow handler with probability about 0.5. In that case it waits, on average, half of 50 ms, so 25 ms. About half of all requests now see waiting time between 0 and 50 ms, instead of the roughly 20 µs they would see alone. The median is still small, but p75 and p99 jump by a factor of more than 1,000, even though the average load looks like only 52% utilization.
The fix is to move the parse to a worker pool (the loop only passes the buffer and receives the result), or to split the work into pieces of under about 1 ms and yield back to the loop between pieces. After the fix, the loop spends at most a fraction of a millisecond per event, and the fast requests are served at their original latency. The slow requests still take 50 ms, but they no longer delay anyone else.
intuition: A waiter who serves whichever table raises a hand, instead of standing beside one table until the guests have finished eating.
Most connections are idle most of the time, so a thread that waits on one of them wastes itself. The event loop turns waiting into a question the kernel answers cheaply, "who needs me?", and keeps the thread busy only with real work. It also gives a free guarantee: because one thread runs one handler at a time, handlers never run at the same moment on the same data, so most of the state needs no locks. The price is the waiter's duty: never stand at a table for long. Every handler must be short.
mistakes: People often think an event loop is faster because it is "asynchronous" in itself. In fact one request is not served faster; usually it is a little slower than in a thread, because of the state saving. What improves is scale: the number of connections per machine, memory use, and the lack of context switching and locking at high concurrency.
People often think a single-threaded loop cannot use a multi-core machine. In fact servers run one loop per core (NGINX workers, Netty event-loop groups, Envoy workers, Redis Cluster shards). What is single-threaded is each connection's handling, which is what removes the locks. The design scales across cores by sharding connections or data, not by sharing them.
People often think "non-blocking" file reads work like non-blocking sockets. In fact epoll always reports regular files as ready, so a read from a disk file can still block the thread while the disk responds. This is why Node.js and libuv push file I/O onto a thread pool, and why io_uring, which can do real asynchronous file I/O, was a significant step.
People often think using async/await means the code runs in parallel. In fact async/await only lets one thread switch between tasks at each await. Two CPU-bound async functions on one loop run one after another. Parallel speed-up needs more threads or processes.
People often think a fast average latency proves the loop is healthy. In fact blocked-loop problems appear in the tail: a short stall delays every connection at once. Watch the loop lag (the delay of a timer that should fire every 10 ms) and the p99 latency, not the average.
tradeoffs: Choose an event loop when you hold many mostly idle connections (thousands or more), the work per event is small (tens of microseconds to a millisecond) and can be made non-blocking, and you want predictable tail latency with little memory per connection. Choose thread-per-request when concurrency is a few hundred, handlers call blocking libraries (JDBC drivers, legacy SDKs), or handlers run long CPU work. You give up simple sequential code and easy use of blocking libraries with the loop; you give up connection density and pay more in memory and context switches with threads.
Choose virtual threads (Java 21 and later) or goroutines (Go) when you want the density of an event loop but the readable, sequential style of blocking code. The runtime runs a poller and a small scheduler underneath. You pay with less control: scheduling is done by the runtime, there is some overhead per switch, and a library call that pins a thread can still hurt. Choose an explicit event loop when you need full control over scheduling, memory per connection, and latency, as in a proxy, a cache or a database.
Choose epoll or kqueue (readiness) when the platform is plain Linux or BSD and your hot path is network I/O with moderate rates. Choose io_uring (completion) when the rate is very high (hundreds of thousands of operations per second per core), when you need asynchronous disk I/O, or when system-call cost shows in a profile. You pay with a newer and larger kernel interface, a different security profile (some container platforms disable it) and more complex code.
Choose one loop per core with connections pinned to loops when throughput must scale with cores and connections are independent. Choose a single loop with worker threads when the shared state is small and consistency is important (Redis is the example), accepting that one core limits the throughput. Choose to move any step above about 1 ms to a worker pool; you pay with a hand-off cost of a few microseconds and the need for backpressure on the pool queue.
friction: The main failure is the blocked loop. One handler that calls a blocking function (a synchronous DNS lookup, a lock held by another thread, a large JSON parse, a regular expression with catastrophic backtracking) stalls every connection on that loop. These bugs are easy to introduce, rarely show in tests with a light load, and appear as tail-latency spikes in production. Detecting them needs measurement: loop-lag metrics, and in Node.js the event-loop delay histogram.
Programming cost is real. The control flow of one request is spread over many handler calls. Stack traces lose the history of how a request got to the current point, error handling is easy to forget at each step, and debugging is harder. Async/await improves the reading, but it can hide the same hazards, and it divides code into "colored" functions (async and not async) that cannot easily call each other.
One loop is also one core. A single hot connection, a hot key, or one expensive handler cannot be spread over cores. Fairness is a second problem: the loop processes ready events in a batch, and a connection that always has data (a fast uploader) can starve others unless the handler limits how much it reads per turn.
Memory and backpressure need care. If the loop reads requests faster than the backend answers, buffers grow without bound. A good server pauses reading from a socket when its output buffer or work queue is above a limit. Finally, the interface under the loop is not uniform: epoll, kqueue, IOCP and io_uring behave differently, and libraries such as libuv or Netty hide this at the price of lowest-common-denominator behavior.
practice: Keep every handler under about a millisecond, and measure it. In Node.js, monitor event-loop delay (perf_hooks monitorEventLoopDelay) and treat a p99 delay above a few milliseconds as a bug. In Netty, never run blocking code on an event-loop thread; use a separate executor group or offload explicitly. In Python asyncio, use run_in_executor for blocking calls and enable debug mode in tests, which logs callbacks that run for more than 100 ms.
Size loops from cores, not from connections: one loop per core, pinned if latency matters, with connections spread by SO_REUSEPORT or by the accept path. Use the worker pool for CPU work, but bound its queue and apply backpressure so that overload turns into fast rejections instead of unbounded memory growth. Set idle timeouts so that dead connections do not fill the table.
Use edge-triggered epoll only if you are sure to drain each socket until EAGAIN; level-triggered mode is safer and the speed difference is small for most services. Batch work inside the loop (read all ready events, then write replies together), and watch for the thundering herd when many loops wake for one new connection. When system calls become the bottleneck (visible in perf as time in read, write and epoll_wait), consider io_uring, with a library such as liburing or a runtime that supports it, and benchmark with your own workload, because gains depend on request size and rate.
When you need an event loop in an application, prefer a mature one (Netty, Tokio, libuv, asyncio) over writing your own; the hard parts are timers, wake-ups, error paths and portability, not the main loop.
interview: Why is epoll better than select or poll for 50,000 connections of which 100 are active? || Select and poll pass the full descriptor list to the kernel on every call and the kernel scans it, so cost is O(50,000) per wake-up. Epoll keeps the interest list in the kernel, the network stack puts ready sockets on a ready list, and epoll_wait returns only those, so cost is O(100). Select also has the 1,024-descriptor default limit.
What is the difference between level-triggered and edge-triggered epoll, and what bug do people hit with edge-triggered? || Level-triggered reports a socket while unread data remains; edge-triggered reports only when new data arrives. With edge-triggered you must read until EAGAIN. If you read once and stop, the leftover bytes stay unread, no new event comes, and the connection appears to hang. It also needs non-blocking sockets so the drain loop cannot block.
Your Node.js service has a good average latency but p99 spikes to 300 ms every few seconds. How do you investigate? || Suspect a blocked loop. Measure event-loop delay with monitorEventLoopDelay, take a CPU profile or flame graph around the spikes, and look for synchronous work: large JSON.parse, regex backtracking, sync file or crypto calls, or a GC pause. Move the work to worker threads or split it, then confirm that loop lag and p99 fall.
How would you scale one event loop beyond one core, and what do you give up? || Run one loop per core (processes or threads) and distribute connections with SO_REUSEPORT or an accept path. Each connection stays on one loop, so its state stays lock-free. You give up a single shared state: cross-loop data needs messages, or sharding by key, and a hot connection or key can still saturate one core.
How does io_uring change the event-loop design? || It is completion-based: you queue operations on a shared submission ring and read results from a completion ring, so many operations cost one system call or none, and it supports true asynchronous file I/O. The loop handles completions instead of readiness. It cuts system-call overhead at high rates, but needs a recent kernel, careful buffer lifetime management, and may be restricted by security policy.
Why does a thread-per-connection server fail at 100,000 connections while an event loop can hold them? || Each thread needs a kernel stack, a user stack and scheduler state, and the scheduler must track and switch among them; memory and switch cost grow linearly with connections even if idle. The loop stores only a small buffer and state per connection and does work only for ready ones. Virtual threads and goroutines get similar density by making the thread very small.
quiz: What does an event loop wait on between events? || It waits in a readiness call such as epoll_wait (or kqueue), which sleeps in the kernel until at least one registered socket is ready or the next timer is due.
Why does epoll scale better than select when most connections are idle? || The kernel keeps the interest list and a ready list, so epoll_wait returns only the ready descriptors and costs O(ready). Select and poll rescan the whole list on every call, costing O(watched).
Why must a handler on an event loop never block? || The loop is one thread. If a handler blocks, no other connection on that loop is served until it returns, so one slow request adds delay to all of them, which shows up as tail latency.
A loop handles 1,000 requests per second at 20 µs each, and 1% of requests block it for 50 ms. About what fraction of time is the loop blocked, and what do fast requests experience? || The slow requests take 10 × 50 ms = 500 ms per second, so the loop is blocked about 50% of the time. A fast request arriving at a random time waits on average about 25 ms with probability near one half.
When would you choose virtual threads or goroutines over an explicit event loop? || When concurrency is high but you want simple sequential code and the runtime can be trusted to schedule, as in a typical business service. Choose the explicit loop when you need tight control of latency, memory per connection and scheduling, as in a proxy, cache or database.

@@ zerocopy
value: Zero-copy I/O is a set of techniques for moving bytes from a file to a network connection (or between two descriptors) without the CPU copying them through a buffer in your program. A normal "read a file, write to a socket" loop moves each byte through memory four times and enters the kernel twice per chunk. With zero-copy, the kernel hands the data from the page cache to the network card, and the CPU copies nothing but small descriptors.
This matters because, in a data-serving system, the work is moving bytes. A server that sends 1.25 GB per second (10 Gbit/s) with ordinary read and write spends memory bandwidth and CPU on copies that change nothing: the program does not look at the data, it only passes it along. Memory bandwidth is shared by all cores, and copying also pushes useful data out of the CPU caches. Removing the copies frees cores for real work and raises the ceiling on throughput per machine.
For the layer above, zero-copy is the reason a Kafka broker can serve many consumers from a modest CPU. A consumer fetch is mostly "send these log bytes to that socket", and the log format on disk is the same as on the wire, so the broker never needs to touch the data. The same idea serves static files in NGINX and Apache, video from Netflix's Open Connect appliances, and object stores. The layers below provide each part. System calls (sendfile, splice) let one call move data inside the kernel. DMA lets the disk controller and the network card read and write memory without the CPU. The page cache holds the file data in kernel memory so it is ready to send. Sockets are the destination. Memory-mapped files are a related way to avoid a read() copy.
terms: Copy — the CPU moving bytes from one memory buffer to another; it costs memory bandwidth and CPU time.
DMA (direct memory access) — a device such as a disk controller or network card moving data to or from memory by itself, without the CPU copying it.
Page cache — kernel memory that holds recently used file data in pages (usually 4 KB), so repeated reads and sends avoid the disk.
User space and kernel space — the program's own memory versus protected kernel memory; crossing between them is a mode switch caused by a system call.
sendfile — a system call that sends data from a file descriptor to a socket inside the kernel.
Scatter-gather DMA — a network card feature that sends a packet assembled from several separate memory regions, so no one has to join them first.
splice — a system call that moves data between a file descriptor and a pipe by passing references to pages instead of copying bytes.
Kernel TLS (kTLS) — encryption of TLS records inside the kernel (and optionally in the network card), so that encrypted traffic can still use sendfile.
history: Early Unix servers used read() and write(), which was fine when networks were slow. In the late 1990s web servers began to saturate their memory buses, and the web-server community (Apache, Zeus, later NGINX) asked for a file-to-socket call. sendfile() appeared in FreeBSD and Linux around 1998 and 1999, and Linux 2.4 (2001) added support for scatter-gather DMA so that the CPU copy of the data could be removed too. In 2006 Linux 2.6.17 added splice() and tee(), a general way to move pages between descriptors through a pipe.
Research and industry then showed how large the gains were. The IO-Lite paper (Pai, Druschel and Zwaenepoel, OSDI 1999) proposed one shared buffer system to remove copies across the kernel and processes. IBM's 2008 developerWorks article "Efficient data transfer through zero copy" explained the four-copy and two-copy paths in a form engineers still cite. In 2011 the Kafka paper (Kreps, Narkhede and Rao) described using sendfile in the broker as a core design choice: Kafka relies on the operating system's page cache and avoids copies when consumers fetch data.
Encryption was the next obstacle, because encrypting in user space brings the data back into the program. Netflix and others worked on kernel TLS: FreeBSD got it first for Netflix's video servers, and Linux 4.13 (2017) added kTLS, so that sendfile works with TLS and, with suitable network cards, the card can encrypt. For programs that send data from their own buffers, Linux 4.14 (2017) added MSG_ZEROCOPY, where the kernel pins the program's pages instead of copying them. Linux 6.0 added zero-copy send to io_uring, and Linux 6.15 (2025) added zero-copy receive in io_uring, where the network card places packet payloads directly in memory that the program owns.
how: Start with the cost of the ordinary path, read() into a buffer and then write() to a socket. The data moves four times. (1) The disk controller uses DMA to put the file data into the page cache, if it is not cached already. (2) The CPU copies from the page cache into the program's buffer, during the read() call. (3) The CPU copies from the program's buffer into the kernel's socket buffer, during write(). (4) The network card uses DMA to read the socket buffer and send it. Two of these four are CPU copies, which cost memory bandwidth twice over: each CPU copy reads N bytes and writes N bytes. There are also two system calls, and four switches between user mode and kernel mode.
sendfile(out_fd, in_fd, offset, count) removes the trip through user space. The program asks the kernel to send count bytes of the file to the socket. The kernel takes the pages from the page cache and queues them for the network card. On the earliest implementations, the kernel still copied the data from the page cache into a socket buffer with the CPU (one CPU copy remained). With scatter-gather DMA, the kernel appends only descriptors (address and length of each page) to the socket buffer, and the network card gathers the payload straight from the page cache. Then the CPU moves no data bytes at all; the only two data transfers are DMA ones: disk to page cache (once, if not cached) and page cache to network card. Modern Linux implements sendfile with the splice machinery, which passes references to page-cache pages through an internal pipe buffer, with the same result. This is how the system-call layer, DMA and the page cache each contribute: the system call lets the program say "move this" in one step, the page cache keeps the bytes in a place the kernel can reach, and DMA makes the final step cost no CPU.
Memory-mapped files are the other tool from the layer below. mmap() maps the file's pages into the program's address space, so the program can read the bytes without a read() copy. But sending them with write() still copies from the mapped region into the socket buffer, so the path has three copies, and the program pays for page faults and TLB management. mmap is therefore a good way to avoid a copy when you want to look at the data (indexes, a database file), and a weaker way to send a file than sendfile. A related danger is that if another process truncates the file, a mapped read can raise SIGBUS.
splice(fd_in, fd_out) generalizes sendfile: one end must be a pipe, and the kernel moves page references between the pipe and a file or a socket. The tee() call duplicates pipe contents without copying. When the data is in program memory instead of a file, MSG_ZEROCOPY on send() lets the kernel pin the pages and let the card read them with DMA, and then the program is told through the socket's error queue when it may reuse the buffer. Pinning and accounting have a cost, so the Linux documentation says the flag is generally effective only for writes of about 10 KB or more.
Zero-copy only works if the program does not need to look at or change the bytes. Kafka makes sure of this by design: the log on disk stores batches in exactly the format that a consumer receives, and the broker uses FileChannel.transferTo in Java, which calls sendfile. When consumers are caught up, the data is in the page cache, so a fetch needs no disk read and no CPU copy. When TLS is enabled the broker encrypts in user space, so data must be read into the JVM, encrypted, and written, and the zero-copy path is lost (this is why kernel TLS is discussed for Kafka). The same holds when a broker must convert the message format for an old client.
The remaining cost is control. sendfile sends at most about 2 GB per call and may send fewer bytes than asked, so the caller loops on the return value. If the file is not cached, sendfile blocks while the disk reads the data, which is a problem for event loops: NGINX therefore offers thread-pool I/O for such reads. Finally, for the network path itself, kernel-bypass systems (DPDK, RDMA) go further and let applications talk to the card directly, at the price of bypassing the kernel's TCP stack.

example: A Kafka broker serves caught-up consumers at 10 Gbit/s, which is 1.25 GB/s of payload, all from the page cache. Let N be the bytes sent per second, so N = 1.25 GB/s.
With read() then write(), count the memory traffic. The first CPU copy reads N from the page cache and writes N into the user buffer: 2N. The second copy reads N and writes N into the socket buffer: 2N. The network card then reads N by DMA: N. The total is 5N = 6.25 GB/s of memory traffic. The CPU copies alone move 2N = 2.5 GB/s; a single core can copy roughly 5 to 10 GB/s, so this costs on the order of a quarter to a half of a core, and it grows with the rate. At 100 Gbit/s (12.5 GB/s), the CPU copies are 25 GB/s and need several cores, and the memory traffic of 62 GB/s is a large share of a server's bandwidth.
With sendfile and scatter-gather DMA, the card reads N directly from the page cache. The total memory traffic is N = 1.25 GB/s, five times lower, and the CPU does no data copy. With plain sendfile without gather support there is one CPU copy: 3N = 3.75 GB/s.
Now count calls. With 64 KB chunks, 1.25 GB/s needs about 19,500 chunks per second. The read/write loop makes about 39,000 system calls per second; sendfile with the same chunking makes about 19,500, and with 1 MB per call it makes about 1,200. Each call costs around a few hundred nanoseconds to a microsecond, so the call savings are small compared with the copy savings, but they add up at small chunk sizes.
Finally, turn on TLS. If the broker encrypts in the JVM, each byte is read into user memory (2N), encrypted (a read and a write of N, plus the cost of AES-GCM at several GB/s per core), and written to the socket buffer (2N). Zero-copy is gone, and the CPU cost is high: encryption alone at 1.25 GB/s uses a notable share of a core. With kernel TLS, sendfile works again; the kernel encrypts the page-cache bytes into the socket buffer (one pass over the data, no user-space crossing), and with a card that supports TLS offload even that pass moves to hardware.
intuition: Hand the parcel straight from the storeroom to the courier, instead of first carrying it through your office.
If the program does not change the bytes, every copy it makes is pure waste. Both ends of the transfer (the disk side and the network side) can already use DMA, and the kernel already holds the data in the page cache. The only missing piece was a way to tell the kernel, in one request, "connect these two". Zero-copy is that request. The design is natural because it moves the decision to the layer that knows where the bytes are.
mistakes: People often think "zero-copy" means the data is never copied. In fact it means no CPU copies through user space. DMA copies still happen (disk to page cache, page cache to network card), and the data still crosses the memory bus at least once. The point is to remove the copies that the CPU makes without adding value.
People often think mmap is the same as zero-copy for sending files. In fact mmap avoids the read() copy only. Sending the mapped bytes with write() still copies them into the socket buffer. A mapped file also adds page faults and TLB costs, and for databases it brings problems with error handling and flushing control that have been discussed in detail (Crotty, Leis and Pavlo, CIDR 2022).
People often think zero-copy always helps. In fact it helps most for large transfers of unchanged bytes. For small messages the saved copy is cheap compared with fixed costs, and MSG_ZEROCOPY is slower below about 10 KB because pinning pages and tracking completions cost more than the copy. For data that must be compressed, encrypted in user space or parsed, the CPU must touch it anyway.
People often think sendfile removes disk reads. In fact it removes copies, not I/O. If the file is not in the page cache, sendfile has to wait for the disk, and the call can block the calling thread. Kafka is fast when consumers are caught up and the data is cached; a consumer that reads old data forces disk reads and also evicts hot pages from the cache.
friction: The first limit is that the data cannot change on its way. Compression, user-space encryption, checksums computed by the program, format conversion and filtering all need the bytes in program memory, and each one ends the zero-copy path. Kafka keeps the fast path only because the on-disk format equals the wire format, and because TLS and message-format conversion are not used on that connection. Kernel TLS restores part of the benefit, but depends on the kernel version, supported ciphers and, for full offload, specific network cards.
The second limit is the page cache. Zero-copy removes copies, not disk reads. A consumer reading old data forces disk I/O, evicts hot pages and can slow every other consumer. In a container or a virtual machine, the cache is also shared with other processes and sized by memory limits, so a neighbour can change your hit rate. On an event loop, a sendfile that waits for the disk blocks the loop thread unless it is moved to a thread pool.
Third, the programming interface has edge cases. A single sendfile call moves at most about 2 GB and may send fewer bytes than requested, so callers must loop. A short write on a non-blocking socket needs bookkeeping for the file offset. MSG_ZEROCOPY needs completion tracking on the error queue and must not reuse the buffer before it arrives. Copies that look avoided can come back quietly: for example, when the network card lacks scatter-gather or checksum offload, the kernel falls back to copying.
Finally, shared pages carry correctness and security risks. If a file changes while it is being sent, the receiver can see a mix of old and new bytes; immutable log segments avoid this. The Dirty Pipe vulnerability in 2022 was a bug in how pipe buffers handled page-cache pages, which showed that zero-copy interfaces make page ownership part of the security model. The gain is also bounded: when the network card or the TLS cost, not the copies, is the bottleneck, removing copies will show no benefit.
practice: Use zero-copy where the bytes are served unchanged: static files, log segments, object bodies, large downloads. In NGINX, sendfile on; is the key setting, together with tcp_nopush on to fill packets and sendfile_max_chunk to stop one fast connection from monopolizing a worker. In Kafka, keep brokers on the plaintext or kernel-TLS path where the security model allows it, leave free memory for the page cache (do not give all RAM to the JVM heap), and keep consumers caught up so they read from cache.
Measure before and after. Look at CPU per GB served, memory bandwidth counters (perf, pcm), system-call counts (strace -c, perf trace), and the page-cache hit rate (for example with cachestat or vmtouch). If CPU is high in copy functions (copy_user_enhanced_fast_string or memcpy in a profile), copies are a real cost; if not, other work dominates. Check that the network card offloads are on (ethtool -k shows scatter-gather, TSO and checksum offload).
Choose chunk sizes in the tens of KB to MB range for sendfile. Handle partial sends and EAGAIN. For event-loop servers, make sure a cold-file read cannot block the loop: use a thread pool for file I/O or read-ahead hints (posix_fadvise, readahead). For TLS at high rates, test kernel TLS with your kernel and cipher, and watch the hardware offload support of your card.
For program-owned buffers, use MSG_ZEROCOPY or io_uring zero-copy send only for large writes and with a buffer pool whose lifetime is tied to completions. For receive-heavy services, io_uring zero-copy receive (Linux 6.15 and later) needs a supported card and queue setup; treat it as an advanced option for specialist workloads. Keep expectations realistic: the savings are largest in high-throughput file serving, not in request-and-reply services with small messages.
tradeoffs: Choose sendfile (or Java transferTo) when you serve whole files or log segments unchanged, the data is likely to be in the page cache, and chunks are large (tens of KB or more). Choose read/write with a user buffer when the program must inspect, filter, compress or re-encode the bytes, or when it is so small that call overhead dominates. You give up the ability to transform data with zero-copy; you give up CPU and memory bandwidth with the buffer path.
Choose kernel TLS (software, or hardware offload on a supporting network card) when you must encrypt and still want sendfile, for example a video or object server at 25 to 100 Gbit/s per machine. Choose user-space TLS (OpenSSL in the process) when your platform lacks kTLS, when you need features that the kernel path does not support, or when the traffic is small. You pay with more kernel-version dependence and harder debugging with kTLS, and with copies and CPU cycles with user-space TLS. Unencrypted data inside a trusted network is cheaper still, but that is a security decision, not only a performance one.
Choose mmap when you need random access to a file's contents inside the program (an index, a read-mostly data file) and the file fits well in memory. Choose read/pread with your own buffer pool when you need control over eviction, flushing order and error handling, as database engines often do. You give up predictable latency with mmap (page faults happen at any access) and you give up simplicity with a buffer pool.
Choose MSG_ZEROCOPY or io_uring zero-copy send only for large writes (about 10 KB and above) of buffers that stay unchanged until the completion arrives. Choose ordinary send for small messages. You pay with complexity in buffer lifetime and completion handling.

Why does Kafka's TLS setting reduce broker efficiency, and what are the options? || With TLS the broker must encrypt each byte, so it reads the data into the JVM, encrypts, and writes, which removes the sendfile path and adds CPU cost and copies. @@ batching
value: Batching means grouping many small operations and doing them together, so that the fixed cost of one operation is paid once for the whole group. Almost every operation in a computer system has two parts: a fixed cost that does not depend on how much you do (enter the kernel, send a packet header, wait for a disk flush, launch a GPU kernel, wait one network round trip) and a small cost per item. If the fixed part is 1 millisecond and the per-item part is 2 microseconds, one item per operation gives about 1,000 items per second, and 100 items per operation gives about 83,000 per second. Nothing got faster. The fixed cost was shared.
This is the cheapest large speed-up in systems work, and it is why a modern system rarely sends one record, one row or one request alone. Kafka producers collect records into batches per partition. Databases commit many transactions with one disk flush (group commit). Bulk loaders insert thousands of rows per statement. Operating systems merge packets and disk writes. GPUs reach good efficiency only when thousands of threads have work, and LLM servers combine requests from many users so that one pass through the model weights serves all of them.
The price is time. An item that waits for a batch to fill is delayed, and a bigger batch is a bigger unit of failure and memory use. So batching is always a trade between throughput and latency, and the layers below explain its shape. System calls are the classic fixed cost that batching amortizes (one call with many buffers instead of many calls). Queueing theory and Little's law say how waiting time, arrival rate and the number of items in the system relate, and therefore how large a batch can be before it hurts. Lock-free ring buffers hand whole batches between threads, so that the cost of cross-core synchronization is also shared.
terms: Fixed cost — the cost of one operation that does not depend on how many items it carries (a system call, a round trip, a flush).
Marginal cost — the extra cost for each additional item in the same operation.
Amortization — spreading a fixed cost over many items, so the cost per item falls to fixed ÷ batch size.
Batch size — the number of items (or bytes) in one operation; common limits are a count, a byte size, or both.
Linger time — the longest time the system waits for a batch to fill before sending what it has (Kafka's linger.ms).
Group commit — a database technique that makes the log records of many transactions durable with a single disk flush.
Natural batching — batches that form by themselves because items pile up while the previous operation is still running, without any added wait.
Half-throughput size — the batch size at which the fixed cost equals the total marginal cost; it equals fixed cost ÷ marginal cost, and beyond several times this size the gains are small.
history: Buffering is as old as input and output devices. Early operating systems read and wrote disk in blocks, and the Unix stdio library of the 1970s collected small writes into one large write. In 1984, John Nagle described a rule for TCP (RFC 896) that holds back small packets until earlier data is acknowledged, because sending 41-byte packets with one byte of data was wasting networks; the same year, database researchers (DeWitt and colleagues) described group commit, where one log flush commits many transactions. IBM's IMS Fast Path and Tandem's systems used it in production, and a 1987 paper by Helland and others on group-commit timers set out the question that remains: how long should the system wait for more work?
The idea moved into hardware and runtime design. Vector processors and then SIMD instructions in the 1990s and 2000s made it normal to process several values with one instruction. Network cards added segmentation and receive offload, so the kernel works on large buffers instead of 1,500-byte packets. GPUs, from around 2007 with CUDA, made large batches essential, because a kernel launch costs microseconds and a GPU needs tens of thousands of parallel threads to be busy.
Data systems built batching into their interfaces. Kafka (2011) designed its producer, broker and consumer around batches of records, sent and compressed together, and its paper lists batching of messages as one of the choices that give it high throughput. The LMAX Disruptor (2011) showed a lock-free ring buffer where consumers naturally process all events available since their last visit, which gives batching without a timer. For machine learning serving, Clipper (NSDI 2017) used adaptive batching to meet latency targets, and Orca (OSDI 2022) introduced iteration-level, or continuous, batching for LLMs, where requests join and leave the batch at every generation step instead of waiting for a whole batch to finish. Kafka itself changed the default producer linger time from 0 to 5 ms in version 4.0, to favor batching in typical workloads.
how: Start with a cost model. Suppose one operation costs F (fixed) plus c per item. Processing n items in one operation takes F + c·n. The cost per item is F/n + c, and the throughput is n ÷ (F + c·n). As n grows, throughput approaches 1/c, the best possible. Half of that best value is reached at n = F/c. For example, with F = 1 ms and c = 2 µs the half-throughput batch size is 500, and the limit is 500,000 items per second. At n = 100 the throughput is 100 ÷ 1.2 ms = 83,000 per second, already 83 times better than n = 1. Gains are steep at first and flatten after a few multiples of F/c.
The cost of waiting comes from the other side. If items arrive at rate λ and you wait to collect n of them, the first item waits about (n − 1)/λ and the average item about half of that. At 10,000 items per second and n = 100, the average wait to fill the batch is about 5 ms. Little's law (L = λ × W) links the number of items in the system, the arrival rate and the average time each spends there. It shows why batching is not free: larger batches raise W, so more items are in flight, and they need memory and, in distributed systems, more outstanding requests to keep the pipeline full. It also gives a stability condition. For the system to keep up, the arrival rate must be below the throughput at the chosen batch size, λ < n ÷ (F + c·n). When F is large, a small batch size cannot keep up with a high λ, and the queue grows without bound. Batching is therefore also a way to survive load: when the system is busy, larger batches appear and lift the capacity.
That leads to the two ways to decide when to send a batch. A size trigger sends when the batch reaches n items or b bytes. A time trigger sends when the oldest item has waited L (the linger time). Real systems use both, "whichever comes first": the size limit protects memory and caps the cost, the time limit protects latency when traffic is low. Kafka's producer shows it clearly. Records go into per-partition batches in memory. A batch is sent when it reaches batch.size bytes (16 KB by default), or when linger.ms has passed, or when the sender thread is free. With linger.ms = 0 batches still form under load: while one request to a broker is in flight, new records pile up in the next batch, and when the sender is free it ships whatever has gathered. This is natural batching, and it adapts without any timer: light traffic means batches of one with minimum latency, heavy traffic means big batches and high throughput.
Batching also improves the quality of other optimizations. Compression works on the whole batch, so repeated field names and values across records are found by the compressor, and ratios improve as batches grow (5 to 10 times for repetitive JSON is common, against 2 times for single records). Kafka compresses a batch once on the producer, stores it compressed on the broker, and passes it unchanged to consumers. Checksums, headers and index entries are also per batch. In a column store, one call that processes 1,000 values replaces 1,000 calls.
Handing batches between threads brings in the lock-free layer. A ring buffer with a producer cursor and a consumer cursor lets a consumer ask "what is the highest published sequence?" once and then process every item up to it. One cache-line transfer between cores, around 50 to 100 ns, is then shared by all the items in that range. Producers can also claim a range of slots with a single atomic operation. The synchronization cost per item drops in the same way as a system call per item does.
Finally, the system-call layer contributes the standard fixed costs. A system call costs roughly 0.1 to 1 microsecond with mitigations, much less than a network round trip but more than a function call, so interfaces were extended to batch: writev, sendmmsg and recvmmsg move many buffers or datagrams in one call, and io_uring submits many operations with one call or none. On the network, each packet carries about 66 bytes of Ethernet, IP and TCP headers, so a 100-byte message sent alone is more than one third overhead, while 100 of them in a 10 KB segment are less than 1%.

example: A database writes a commit record to its log, and each transaction must wait until that record is safely on disk. A disk flush (fsync) takes F = 1 ms on a typical cloud SSD, and appending the record costs c = 2 µs.
Without batching, each commit pays one flush: 1.002 ms per transaction, so the log can commit at most about 998 transactions per second, whatever the number of CPU cores. This is the ceiling many small systems meet first.
With group commit, transactions that arrive while a flush is in progress wait and are flushed together in the next one. Take 100 transactions per flush: 1 ms + 100 × 2 µs = 1.2 ms, so 83,000 commits per second, 83 times more. With 1,000 per flush the time is 3 ms and the rate 333,000 per second. Note that the flush time itself grew from 1 ms to 3 ms, so latency rose too.
Now look at latency at an arrival rate of 100,000 transactions per second. A batch of 100 fills in 1 ms, so the average transaction waits about 0.5 ms to be included, then about 1.2 ms for the flush: roughly 1.7 ms. A batch of 1,000 would need 10 ms to fill, average wait 5 ms, plus 3 ms: about 8 ms. If the SLO is 5 ms at p99, the larger batch breaks it, even though throughput is higher. With natural batching, the batch size adjusts to the load without a rule: when 100,000 transactions per second arrive and a flush takes about 1.2 ms, about 120 pile up during each flush, so batches settle at about 100 to 120 with no timer.
Now the Kafka producer. Events are 1 KB and the application sends 50,000 per second (50 MB/s). With batch.size = 16 KB, a batch holds about 16 events and is full after 0.32 ms; there are about 3,100 batches per second. Each request to the broker has a fixed cost of a round trip (about 0.5 to 1 ms inside one data centre) and some broker processing. With batch.size = 256 KB and linger.ms = 5, a batch gets 250 events after 5 ms, so about 200 batches per second, and fixed costs fall 15 times. If the JSON compresses 5 to 1 on the larger batch, the network carries about 10 MB/s instead of 50 MB/s. The price is up to 5 ms of added delay per event and larger memory use, which is a good trade for logs and metrics but possibly not for a payment event.
intuition: Drive one full truck instead of a hundred cars.
Every trip has a cost that does not depend on the load: the driver, the fuel to start, the road. A truck pays it once for many boxes. The only thing you give up is that the first box waits at the depot until the truck is loaded, so you pick a departure rule: leave when full, or at a fixed time, whichever comes first. The design is natural because the fixed cost is a property of the machine, not of the work, and the wait is a property of the arrival rate, not of the machine.
mistakes: People often think batching only adds latency. In fact under load it can reduce latency. If a system is saturated, each item waits in a long queue; bigger batches raise capacity, the queue drains, and the total time falls. The added latency of waiting matters only when the system has spare capacity.
People often think a bigger batch is always better. In fact the curve flattens after a few multiples of F/c, while latency, memory and failure cost keep growing linearly. Past the knee you pay without gain. In a vectorized engine or GPU, a batch that no longer fits in the cache or in GPU memory can even run slower.
People often think linger.ms = 0 means no batching. In fact Kafka still forms batches when records arrive faster than the sender can ship them, because they pile up while earlier requests are in flight. The setting removes the deliberate wait, not the batching.
People often think one batch size is right for a whole system. In fact the best size depends on the arrival rate and on the latency target of each stream. Kafka batches per partition, so a topic with 1,000 partitions and a low rate may produce batches of one or two records even with a large batch.size, because each partition fills slowly.
People often think batching changes semantics only in speed. In fact it changes failure behavior: a failed batch may be retried as a whole, so records can be duplicated or reordered unless the protocol handles it (idempotent producers, transactions), and one bad item can make a whole batch fail.
tradeoffs: Choose a larger batch with a longer linger time when the stream is a pipeline whose end-to-end deadline is seconds (logs, metrics, analytics events, bulk loads), when the fixed cost is high (cross-region round trips of 50 to 100 ms, cloud object-store requests billed per request, flushes of 1 ms or more), or when compression matters. Choose small batches or none when a user is waiting on the result (a payment, a click that must show a response), when traffic is low so the batch would only fill by waiting, or when the per-item cost dominates. You give up latency and memory with large batches; you give up throughput and pay more for requests with small ones.
Choose a time trigger (linger) together with a size trigger when traffic is variable: the size limit bounds memory during peaks, the time limit bounds delay in quiet periods. Choose natural, adaptive batching (send as soon as the previous operation completes) when you want the best latency at low load and automatic growth at high load, as in group commit and ring-buffer consumers. You give up a guaranteed batch size, so efficiency is less predictable, and you must make sure there is always at least one operation in flight.
Choose per-destination batches (per partition, per shard, per node) when order and routing matter, and accept that many destinations make batches small. Choose one shared batch with a re-split on the other side when the destinations are many and the rate per destination is low, at the cost of more complexity and mixed failure handling.
Choose continuous batching for GPU inference of language models, where requests have different lengths and join and leave at each step; choose static batching for fixed-size offline jobs such as embedding a corpus, where utilisation is easy to keep high and latency per item does not matter. You pay with scheduler complexity in the first case, and with idle slots when lengths vary in the second.
interview: Explain why batching improves throughput, using a cost model. || If an operation costs F plus c per item, then n items cost F + c·n and the cost per item is F/n + c. Throughput approaches 1/c as n grows, and half of it is reached at n = F/c. Batching works when F is large relative to c, such as a flush, a round trip or a system call, and is useless when per-item cost dominates.
How does a Kafka producer decide when to send a batch, and what do batch.size and linger.ms do? || Records are grouped per partition. A batch is sent when it reaches batch.size, when linger.ms has passed since its first record, or when the sender thread is free to send it. A longer linger and bigger size raise throughput and compression and add delay; with linger.ms = 0 batches still form under load.
Design a write-ahead log with group commit. What are the key steps and risks? || Writers append records to an in-memory buffer under a short lock and wait on a condition. One flusher thread takes the whole buffer, writes it, calls fsync once, then wakes all waiters whose records were included. Risks: wake-up ordering and lost waiters, fsync errors that must fail all of them (and not be retried silently), a batch that grows without bound, and a latency target broken by a long flush.
A service has p50 latency of 5 ms and p99 of 400 ms after you added batching with a 100 ms linger. What do you check? || Low-traffic periods and partitions where batches never fill, so items wait the full linger. When can batching reduce latency? || When the system is overloaded or near saturation. Per-item overhead makes capacity too small, queues grow, and every item waits. Larger batches raise capacity and the queue empties, so total latency falls. Below saturation batching only adds wait.
What is the interaction between Nagle's algorithm and delayed ACK, and how do you avoid the problem? || Nagle holds a small segment until the previous data is acknowledged, and delayed ACK makes the receiver wait (up to 40 ms on Linux, 200 ms on some systems) before acknowledging when it has nothing to send, so a write-write-read pattern can stall. Set TCP_NODELAY for request-response protocols and batch writes yourself (one write or writev per message).
friction: Latency is the first cost, and its worst part is the tail. The first item of a batch waits the longest, and a slow or failed batch delays every item in it. If the arrival rate drops, a size-only trigger can hold items for a very long time, so a time trigger is essential. Mixing items with different urgency in one batch gives the most urgent item the delay of the whole group.
Failure handling becomes harder. When one item in a batch of 500 is invalid, does the whole batch fail, or only that item? Retrying a whole batch can produce duplicates, and retrying out of order can reorder events. Systems need idempotence (Kafka's idempotent producer with sequence numbers), per-item status in responses, and a way to isolate a poison item (retry halves, or one by one). The size of a failure also grows with the batch: a lost 1 MB batch loses more than a lost 1 KB record.
Memory and resource use grow too. Buffers for many partitions or destinations multiply: 2,000 partitions with 1 MB batches would need 2 GB of producer memory. Large batches create garbage and memory pressure in managed runtimes, and in vectorized or GPU code a batch beyond the cache or device memory slows things down or fails. Uneven item sizes make a count limit unreliable, so byte limits are also needed.
Finally, batching hides cost and complicates measurement. Average latency can look fine while the tail includes the full wait. Backpressure is harder to reason about when a batch is in flight and more is piling up. Tuning is workload specific, since the best size depends on arrival rate, item size and the target latency, and these change during the day. Defaults are a compromise, and the right values are often found only by measuring the real system.
practice: Find the fixed cost first. Measure what one operation costs when it carries one item and when it carries a hundred; the ratio tells you the knee, F/c. If the fixed part is small, batching will not help. If it is a flush, a round trip or a request billed per call, batching is likely the biggest tuning gain you have.
Use a size limit and a time limit together, and expose both as settings. For Kafka producers, start from batch.size of 64 KB to 256 KB for throughput work and a linger.ms of 5 to 20 ms (the default is 5 ms in Kafka 4.0 and 0 before), turn on compression (lz4 or zstd), and make sure buffer.memory can hold batches for all the partitions you write. Watch the producer metrics batch-size-avg, records-per-request-avg and record-queue-time-avg: if the average batch is far below batch.size, you are limited by the rate or the linger, and a larger batch.size will do nothing.
For databases, use multi-row INSERT, JDBC batching (with the driver option that rewrites batches, such as rewriteBatchedStatements for MySQL), or COPY in PostgreSQL, with batches of hundreds to a few thousand rows, and commit once per batch. For Elasticsearch bulk requests, Elastic's guidance is to start with 1,000 to 5,000 documents or 5 to 15 MB per request and tune from there. For object stores, use multipart uploads and combine small files, because each request has a cost and a latency.
Make batches safe: use idempotent operations or sequence numbers, return per-item results, and isolate bad items. Keep latency-critical traffic off the batched path, or give it its own low-linger configuration. Use TCP_NODELAY for request-response traffic and assemble messages in your own buffer. Review batch settings when traffic changes by a large factor, and test at both low and high load, because a setting that is right at peak may add pure delay at night.
quiz: What are the two parts of an operation's cost that make batching useful? || A fixed cost per operation (a syscall, a round trip, a flush) and a smaller per-item cost. Batching pays the fixed part once for n items, so cost per item becomes F/n + c.
Why does Kafka still form batches when linger.ms = 0? || Records arrive while a request to the broker is already in flight. They accumulate in the next batch, and when the sender is free it ships everything gathered, so under load batches form without a deliberate wait.
Why does the benefit of a bigger batch flatten out? || Per-item cost is F/n + c, which falls toward c. Once F/n is small compared with c (a few multiples of n = F/c), more items save almost nothing, while latency, memory and failure cost keep rising.
With F = 1 ms per flush and c = 2 µs per record, what throughput do batches of 100 and 1,000 give? || 100 / (1 ms + 0.2 ms) = about 83,000 per second; 1,000 / (1 ms + 2 ms) = about 333,000 per second. The limit is 1/c = 500,000 per second.

Choose large batches for pipelines with loose deadlines and a high fixed cost.

value: Separating storage from compute means keeping the data in a shared, durable storage service (usually object storage such as Amazon S3) and running the machines that process it as a separate pool that you can start, stop, grow, shrink or duplicate without moving the data. The older design puts the data on the local disks of the same machines that process it. In that design, adding CPU means adding disks, adding disks means moving data, and shutting machines down means losing access to data or paying to keep it elsewhere.
The two resources are needed in very different amounts at different times. A table of 100 TB must be stored all the time, but it may be queried hard for only a few hours a day. If storage and compute are tied together, you pay for compute capacity around the clock to hold the data, you resize slowly because data must be copied to new nodes, and two teams who want to query the same data must share one cluster or keep two copies. With separation, storage costs about $0.02 per GB per month and does not change when compute changes, and compute can scale to zero between jobs.
For the layer above, this technique is the base of the data lake, the lakehouse, and modern cloud warehouses: Snowflake, BigQuery, Databricks, Redshift RA3, Athena, Trino on S3. It also underlies serverless platforms, where functions are stateless and keep state in shared services, and newer streaming systems that move Kafka log segments to object storage (tiered storage). The layers below make it work. TCP carries the bytes between compute and storage, and its throughput limit per connection explains why engines open many parallel connections. HTTP is the protocol of object stores (the S3 API: GET with a byte Range, PUT, multipart upload), and its request-per-object model shapes file layout and cost.
terms: Object storage — a service that stores immutable blobs under keys in a flat namespace, accessed with HTTP calls (S3, Google Cloud Storage, Azure Blob Storage).
Stateless compute — workers that hold no data that must survive them, so they can be added, removed or replaced at any time.
Shared-nothing — the older design in which each node owns a slice of the data on local disk and nodes do not share storage.
Disaggregation — another word for separating storage and compute (and sometimes memory) into independent pools connected by a network.
Local cache — a copy of hot data on the compute node's SSD or memory, which hides the latency of remote storage.
Range read — an HTTP GET that asks for only a byte range of an object, used to read one column chunk of a Parquet file.
Table format / catalog — metadata (Delta Lake, Iceberg, Hudi, or a warehouse's own metadata service) that says which files make up a table at a given version and makes commits atomic.
Egress / cross-AZ cost — the charge for data moved between availability zones or out of a region, which can exceed storage cost if the design moves data carelessly.
history: Early cluster systems put data next to compute on purpose. Google's GFS and MapReduce (2003 and 2004) ran tasks on the machine that held the data block, because in the 2000s a datacentre network was slow (1 Gbit/s links shared by many machines) and a local disk was faster than the network. Hadoop copied the design, and parallel databases such as Teradata and Greenplum were shared-nothing from the start.
Three changes reversed the trade-off. Datacentre networks became much faster: Google's Jupiter fabric (2015) gave about 1 petabit per second of bisection bandwidth, and cloud instances now have 25 to 200 Gbit/s links. Object storage became cheap and very durable: Amazon S3 launched in 2006, and designs for eleven nines of durability made it the default place for data. And in December 2020 S3 became strongly consistent for reads after writes and lists, which removed a major source of workarounds in data-lake tools.
Systems then built on this. Google's Dremel (2010) and BigQuery separated compute from the Colossus file system. The Snowflake paper (Dageville et al., SIGMOD 2016) described a warehouse with storage in S3, "virtual warehouses" of compute nodes with local SSD caches, and a separate metadata layer, and made the term widely known. Amazon Aurora (SIGMOD 2017) separated the database engine from a storage service that understands the redo log. Redshift added RA3 nodes with managed storage in 2019. Open table formats (Delta Lake, VLDB 2020; Iceberg; Hudi) gave transactions on top of plain object storage, which made the lakehouse possible. In 2023 and 2024 the idea reached streaming: WarpStream and others wrote Kafka-compatible logs directly to object storage, Kafka added tiered storage (KIP-405), and S3 gained conditional writes (If-None-Match in August 2024, If-Match in November 2024), which allow safe coordination without a separate lock service.
how: The structure has three parts: a durable store, a metadata service, and a stateless compute pool. The store is an object storage service that keeps immutable objects replicated across at least three availability zones. It gives durability and capacity without any effort from the engine, and it never needs rebalancing when compute changes. Objects cannot be modified in place, only replaced as a whole, which forces the engine to use immutable files: new data is written as new files, and old ones are removed later.
Compute reads over the network, using the layers below. The engine opens many HTTP connections to the store and issues range GET requests for exactly the bytes it needs. For a Parquet file this means reading the footer (the last few KB, which holds the schema and the position and min/max statistics of each column chunk), choosing the row groups that can match the filter, and fetching only the needed column chunks. A single S3 connection delivers roughly 50 to 100 MB/s after a first-byte delay of tens of milliseconds, so an engine needs dozens of concurrent requests per node to fill a 25 Gbit/s link (about 3 GB/s). Requests of 8 to 64 MB each give a good balance between throughput and request count; tiny requests waste time and money. Slow requests are common (the tail latency of object stores is much longer than the median), so engines issue a second, hedged request when one is slower than the 95th percentile.
To hide the latency of remote storage, every compute node keeps a cache on local NVMe SSD (and in memory). Local NVMe gives roughly 100 microseconds latency and several GB/s per drive, against tens of milliseconds for the first byte from S3. The cache is keyed by file and byte range. To make the cache effective, the scheduler sends the same file to the same node over time (consistent hashing), so that repeated queries find their data warm. This is also the weak point: when a cluster scales out or restarts, caches are cold and the first queries are slower.
The metadata service gives the system its transactions. A table is a set of immutable files plus a log or manifest that lists which files belong to which version. A writer adds files and then commits by atomically creating the next log entry. Delta Lake uses "put if absent" on log file names, Iceberg swaps a pointer in a catalog, and warehouses keep this in their own metadata database. A reader opens a particular version and sees a consistent snapshot, even while writers work. This is how the system gets ACID properties on top of a store that only knows about whole objects.
Elasticity follows from statelessness. Starting a compute cluster means starting machines and pointing them at the catalog; no data moves. Stopping it loses only the caches. Several clusters can read the same data at once with full isolation, for example an ETL cluster and a BI cluster, and a failed node needs no data recovery. Storage and compute are billed separately and scale independently. The same shape appears at other layers: Aurora separates the SQL engine from a log-structured storage fleet, and diskless Kafka designs write batches of records from many partitions to one object per flush, trading latency for cost.
What you pay for this is network and request overhead. Every cold read crosses the network. Object stores charge per request (roughly $0.0004 per 1,000 GETs and $0.005 per 1,000 PUTs in a US region), and have per-prefix request limits (about 5,500 reads and 3,500 writes per second per prefix for S3, which spreads across prefixes automatically but needs a good key layout). Small files multiply request count, so engines compact files into hundreds of MB, and layouts avoid listing very large directories.
The write path follows from immutability. An engine never edits a file in place. It writes new files (an insert becomes a new Parquet file; an update or delete either rewrites the affected files, called copy-on-write, or writes a small delta file that readers merge, called merge-on-read), then commits the new file list. Old files become garbage after a retention period, and a background job compacts many small files into fewer large ones. Each commit costs at least one conditional PUT to the log, so a table can take only a modest number of commits per second, and writers therefore batch their data into larger commits.

example: Consider a 100 TB analytics dataset. Queries run heavily for about 20 hours a week, using a cluster of 40 nodes at peak.
Coupled design. Each node has about 8 TB of usable local disk, and data is stored with 3 copies, so 300 TB needs about 38 nodes, say 40. These nodes must run all the time, because they hold the data. At an illustrative price of $2 per node-hour, 40 nodes × 720 hours is 28,800 node-hours per month, about $57,600. Doubling query power means adding nodes and waiting for data to be rebalanced, which for terabytes takes hours.
Separated design. The 100 TB are in object storage at about $0.023 per GB-month, so about $2,300 per month, and durability is built in. The 40-node cluster is started only when needed: 20 hours per week is about 87 hours a month, so 40 × 87 = 3,480 node-hours, about $6,960. The monthly total is about $9,300, one sixth of the coupled cost, with the same peak power. There is a catch: a cold start means cold caches, and the first queries read from S3. If the working set is 10 TB and each node reads at 2.2 GB/s with 32 connections, then 40 nodes load their share quickly, but the first pass is slower than a warm run.
Now check request cost and speed for scanning 10 TB. With 16 MB range reads, 10 TB is 625,000 GET requests, about $0.25. With 128 KB reads, it is 78 million requests, about $31, and each request pays a first-byte delay of tens of milliseconds, so the scan is also far slower. File and read sizes therefore decide the bill and the speed. At 2.2 GB/s per node, one node scans 10 TB in about 76 minutes and 40 nodes in under 2 minutes, as long as requests are large and parallel.
Finally, a new team wants to run its own heavy reports. In the coupled design they share the cluster and slow the others, or you copy 100 TB. In the separated design you start a second cluster against the same catalog in minutes. They see the same snapshot, and nobody is slowed.
intuition: A shared library with many reading rooms that open and close as needed, instead of every reader carrying their own copy of the books.
Storage and compute grow for different reasons: data grows with time, queries grow with people and deadlines. Binding them forces you to buy both whenever you need either. Once the network is fast enough and a storage service is durable and cheap, the right place to keep data is in one place that never moves, and the right place to put computing is wherever and whenever it is needed. The cost of that freedom is the walk to the library, which a local cache shortens.
mistakes: People often think separating storage and compute is always cheaper. In fact it is cheaper when compute use is bursty or the data is large and cold. A cluster that runs at high utilization all day on a hot working set can be cheaper and faster with local disks, because it avoids request charges, network cost and cache misses.
People often think object storage is a slow disk. In fact it is a different kind of system: very high aggregate throughput and durability, but a first-byte latency of tens of milliseconds, no in-place update, no rename-as-atomic (on some stores), and a cost per request. Treating it like a local file system causes slow, expensive code.
People often think the cache makes the network irrelevant. In fact the cache only helps repeated access to the same data. A scan of cold data, a new cluster, or a working set larger than the SSD all go to the network, so S3 throughput per node and request design still decide the performance of those queries.
People often think the table format is just a file listing. In fact it is the transaction layer. Without an atomic commit on a log or catalog, two writers or a writer and a reader on plain files would see partial or conflicting results, and S3 listing was historically not even consistent.
People often think stateless compute means no state at all. In fact the state moves: to the catalog, to the cache and to the shuffle. Intermediate shuffle data must live somewhere during a query, so engines either keep it on local disk (and lose it with the node) or write it to remote storage (and pay for it).
tradeoffs: Choose separated storage and compute when the data is large (tens of TB or more), usage is bursty or varies between teams, you want several isolated engines on the same data, or you need to scale compute in minutes. Choose coupled local-disk clusters when the workload is steady and heavy, the working set fits on local SSD, latency must be a few milliseconds at the tail, and you can manage rebalancing. You give up elasticity and isolation with local disks; you give up predictable low latency and some cost per scan with remote storage.
Choose object storage as the system of record with a local SSD cache when most reads are repeats of a hot working set that fits on the node (dashboards, recent partitions). Choose bigger or more nodes, or a distributed cache layer, when the working set is large and scans are repeated. Choose direct reads from S3 without a cache when queries are rare or large one-time scans, since caching would only add cost. You pay with a cold-start penalty and cache management in the first case.
Choose a single object-storage region and one availability-zone layout for the compute when data transfer cost matters: cross-AZ traffic is about $0.01 per GB in each direction, and cross-region transfer costs more and takes longer. Choose multiple regions only for disaster recovery or data residency, and accept replication cost and delay.
Choose S3 Standard for general data. Choose S3 Express One Zone (single-digit millisecond latency, one zone) for hot data such as shuffle or caches where one-zone durability is acceptable. Choose cheaper infrequent-access or archive tiers for cold data with the knowledge that retrieval is slower and may be charged. Choose a streaming system with local disks (classic Kafka) when end-to-end latency of a few milliseconds matters; choose object-storage-based streaming when cost and elasticity matter more than latency of hundreds of milliseconds.
interview: Why did the industry move from data locality (Hadoop) to separated storage and compute? || Networks became fast (25 to 100+ Gbit/s per node and large fabrics), object storage became cheap and durable, and workloads became bursty. Locality tied compute size to data size, so scaling or stopping a cluster meant moving data. With separation, storage is paid for once, and compute scales or stops independently, with caches recovering the locality benefit for hot data.
How do you get ACID transactions on S3, which only stores immutable objects? || Write new immutable data files, then commit by atomically publishing a new version in a log or catalog (Delta: create the next numbered log file only if absent; Iceberg: swap the metadata pointer; warehouses: a metadata database). Readers use a snapshot version. S3 strong consistency and conditional writes make the commit safe without an external lock for many designs.
Your queries on S3 are slow and expensive, with millions of GETs. What do you look at? || The file and read sizes. Many small files and small range reads multiply requests and add first-byte latency. Compact into files of hundreds of MB, read row groups and column chunks of 8 to 64 MB, use column pruning and min/max statistics, increase parallelism per node, add hedged retries, and cache hot footers and column chunks.
What happens to performance when a cluster auto-scales out from 4 to 40 nodes? || The new nodes start with cold caches, so the first queries read from S3 and are slower. Work is also redistributed, which changes which node caches which file. Warm up with prefetching, use consistent hashing so that most files stay on the same node, and set the scale-out in advance of the peak.
Where would you not separate storage and compute? || In latency-critical, steady, high-utilization systems such as an OLTP database or a low-latency stream, where the working set fits on local NVMe, tail latency of milliseconds matters and the network and request costs would exceed the savings. Even there, designs such as Aurora separate only the log or storage part.
How can Kafka use object storage, and what does it cost? || Tiered storage keeps recent segments on broker disks and moves old ones to object storage, which reduces disk cost and speeds up rebalancing. Diskless designs write batches directly to object storage and drop replication between brokers, saving cross-AZ cost, but add latency of hundreds of milliseconds and need a metadata layer to keep order.
friction: Latency is the first cost. A request to object storage takes tens of milliseconds to the first byte, against about 100 microseconds for local NVMe, so interactive queries on cold data are slower, and point lookups are poor. Caches fix repeated access but not first access, and they add their own complexity: eviction, invalidation when files are replaced, and cold starts after scaling or failures.
Cost has new shapes. Storage is cheap, but requests, cross-AZ transfers, cross-region transfers, and egress can dominate when file layout is bad, with millions of tiny files or chatty listings. Metadata operations (listing a prefix with a million objects) are slow. Per-prefix request limits and throttling (HTTP 503 SlowDown) need key design and retries. Because costs depend on access patterns, bills are harder to predict than node counts.
Consistency and coordination depend on the metadata layer. Object stores are consistent for single objects, but multi-object atomicity has to be built, and it is a bottleneck: every commit goes through one log or catalog, so thousands of tiny commits per second are a problem, and concurrent writers conflict and retry. Compaction, vacuuming and small-file cleanup become permanent maintenance tasks.
Finally, the network is shared and not free. Shuffles, joins and broadcast between compute nodes still need fast local networking; remote shuffle stores add latency. Noisy neighbors, instance network limits and throttled bandwidth show up as variable runtimes. Data gravity remains: once PBs are in one cloud's object store, moving them out has a large egress cost, so the storage service choice becomes a long-term lock-in decision.
practice: Design the layout of data for object storage first. Write large files (128 MB to 1 GB for analytics), use columnar formats with statistics (Parquet), partition by the filters you use but not so finely that partitions hold tiny files, and compact regularly (Delta OPTIMIZE, Iceberg rewrite_data_files). Avoid listing large prefixes in hot paths; read the table log instead.
Choose read sizes and parallelism deliberately: 8 to 64 MB range requests, dozens of concurrent requests per node, and retries with backoff and hedging for slow requests. Watch the request count and bytes per query, not only runtime. Enable local disk caching where the engine offers it (Databricks disk cache, Snowflake local SSD cache, Trino file-system cache), keep hot tables on stable clusters, and warm caches before known peaks.
Control cost by watching more than storage: set lifecycle rules for old versions and temporary files, keep compute and storage in the same region and, where possible, the same availability zone, and use VPC endpoints to avoid NAT and egress charges. Use auto-stop on idle clusters, and size clusters for the peak of each workload separately. Use vacuum and retention policies so old file versions do not accumulate.
Treat the metadata layer as a system of record: back up the log or catalog, limit concurrent writers, batch commits, and monitor commit conflicts. For streaming, use tiered storage in Kafka when retention is long and consumers mostly read the tail; consider object-storage-native streaming only where latency of hundreds of milliseconds is acceptable and cross-AZ cost is a major bill item. Test failure modes: a cold cluster, a throttled prefix and a regional S3 issue.

value: Thread-per-core (also called shared-nothing or shard-per-core) is a way to build a server so that each CPU core runs exactly one thread, and each thread owns its own slice of the data, its own memory, its own network queue and its own share of the disk. Cores do not share mutable data, so they never take locks and never fight over the same cache lines. When one core needs something that another core owns, it sends that core a message and the owner does the work.
The problem it solves appears when machines have many cores. A server today has 32, 64 or more cores. A program written with shared data and locks can use 4 or 8 cores well, then stops scaling: the cores spend time waiting for locks, and the cache line that holds the lock or a shared counter moves from core to core at a cost of tens to hundreds of nanoseconds per move. Adding cores then gives little or even less throughput. On top of this, the operating system scheduler moves threads between cores, and each move throws away the warm cache. Thread-per-core removes these costs by design, so throughput grows almost in line with core count and latency becomes steadier.
For the layer above, this design is behind ScyllaDB (a Cassandra-compatible database, built on the Seastar framework), Redpanda (a Kafka-compatible log), and the Rust runtimes Glommio and Monoio; DPDK-style packet processing and some trading systems follow the same idea. It is a mix of lower layers. CPU scheduling gives the pinning of one thread to one core, so the scheduler does not move work. Cache lines and locality explain why avoiding shared writes pays off. NUMA says each core should use memory from its own socket. Lock-free queues (single-producer, single-consumer) are the one place where cores do talk to each other, cheaply and without locks. Each core also runs an event loop, which is what lets one thread serve many requests without blocking.
terms: Shard — a partition of the data and the work; in this design one shard belongs to exactly one core.
Shared-nothing — an architecture in which workers share no mutable memory and communicate only by messages.
Core pinning (CPU affinity) — telling the operating system to run a thread only on one chosen core.
Cache-line bouncing — a cache line that two or more cores write alternately, so it moves between their caches again and again.
False sharing — two unrelated variables that sit on the same 64-byte cache line, so writes to one slow down the core that uses the other.
SPSC queue — a single-producer, single-consumer queue; with only one writer and one reader, it needs no locks and no atomic read-modify-write operations.
RSS (receive-side scaling) — a network card feature that hashes each connection to one of several receive queues, so different cores handle different connections.
Reactor — the per-core event loop that runs tasks, polls the network and disk, and must never block.
history: The idea has two roots. One is operating-systems research on many cores. The Corey paper (Boyd-Wickizer and others, OSDI 2008) argued that applications should control sharing explicitly, and "An Analysis of Linux Scalability to Many Cores" (OSDI 2010) measured how shared kernel data structures stopped Linux applications from scaling past a few dozen cores. The Barrelfish research system (ETH Zurich and Microsoft, 2009) went further and treated a multicore machine as a network of nodes that pass messages. Clements and colleagues (SOSP 2013) gave a rule for when sharing can be avoided: operations that commute can be implemented without conflicts.
The other root is high-performance networking. Linux got SO_REUSEPORT in 2013 (kernel 3.9), letting each thread own a listening socket, and network cards added multiple receive queues with RSS, so that packets for one connection always arrive on one core. DPDK (2010 onward) let user programs poll the card directly with one thread per core.
Seastar grew out of this. Avi Kivity and Dor Laor, who had created the KVM hypervisor, founded Cloudius Systems (later ScyllaDB) and built the Seastar framework for the OSv operating system and a Cassandra-compatible database. They released Seastar as open source in 2014 and ScyllaDB 1.0 appeared in 2016. Instead of Cassandra's pools of threads with shared memtables and locks, Scylla gives each core a shard of the data. Redpanda (Alex Gallego, 2019) used Seastar for a Kafka-compatible log in which each partition is a Raft group pinned to one core. Glommio (Glauber Costa, initially at Datadog) and ByteDance's Monoio brought the model to Rust on io_uring. TigerBeetle, a financial database, takes the idea to an extreme: the state machine of a replica runs on a single thread with no locks, with io_uring for I/O. These systems share a belief that the next speed-up comes from removing coordination between cores, not from faster cores.
how: The basic rule is that every piece of mutable data has exactly one owner thread, and that thread is pinned to one core. At start-up the process creates N threads for N cores (often leaving a core or two for the operating system and interrupts), and pins each with sched_setaffinity. This is where CPU scheduling contributes: the scheduler no longer has to decide where the thread runs, so it never migrates, its cache and its TLB stay warm, and there is no context switching between worker threads on a core. Some systems also isolate cores from other kernel work (isolcpus, interrupt affinity) so nothing else runs there.
Data is split into shards. A database hashes each key to a token and maps token ranges to cores. A log such as Redpanda assigns each partition to one core, and the replicated state machine for that partition lives only there. The owner is the only writer, so it needs no lock and no atomic operation on its data. This is the cache-line contribution: since a core is the only writer of its shard, the cache lines of that shard stay in its private L1 and L2 caches in the exclusive state, and the coherence protocol has nothing to do. A shared counter updated by 32 cores moves one line among 32 caches at roughly 50 to 100 ns per move; 32 per-core counters, added up only when read, move nothing.
Memory is split in the same way. At start-up the framework divides the machine's memory among the cores and, with NUMA awareness, takes each core's slice from the memory node of its own socket, so accesses stay local (a remote-socket access is often 1.5 to 2 times slower). Each core has its own allocator, with no global heap lock. The rule for freed memory is that it goes back to the core that owns it, through a message if needed.
The network and disk are split too. The network card spreads connections across receive queues by hashing, one queue per core, so a connection is read by the same core every time. Disk requests go through a per-core I/O queue using asynchronous I/O (Linux AIO or io_uring), with the framework's scheduler sharing disk bandwidth among cores. Each core runs its own event loop (the reactor): it runs a queue of small tasks, polls the network and disk for completions, and starts new work. Every task must be non-blocking; a task that blocks stalls its whole core, so the framework warns when a task runs for too long (the threshold is a few tens of milliseconds by default in Seastar), and it uses futures and continuations to express waiting.
Some requests need data owned by another core, for example a read for a key on shard 7 that arrives on a connection owned by core 3. The framework then sends a message from core 3 to core 7: the code looks like submit_to(shard, function) and returns a future. Behind it is a lock-free queue between each ordered pair of cores. Because each queue has exactly one producer and one consumer, it can be a ring buffer where the producer writes slots and advances a head index, and the consumer reads slots and advances a tail index, with only plain loads and stores plus memory barriers. This is the lock-free contribution. Messages are also batched: a core collects many requests for the same destination and sends them together, which makes the cost per message a few tens of nanoseconds plus one or two cache-line transfers.
Finally, clients can help. In ScyllaDB, shard-aware drivers choose the connection so the request arrives at the right core (the driver picks a local port that maps to the shard), so most requests need no cross-core hop. Together this gives a structure with no locks on data, no shared allocator, no thread migration and predictable cache behavior, at the cost of a different programming model.
Inside one core the work is cooperative. The reactor takes tasks from queues grouped by purpose (foreground queries, compaction, repair, streaming), gives each group a share of time, and runs each task to completion before choosing the next. Because there is no preemption between tasks, no task needs a lock against another task on the same core, and the scheduler can keep background work from starving foreground requests. The price is that every task must be short and must yield.

example: Imagine a service with 32 cores. Each request takes 10 µs of real work, so one core could do 100,000 requests per second, and the ideal total is 3.2 million per second. Every request must update a shared table protected by a mutex, and the critical section takes 1 µs.
With shared data and a lock. The lock is held 1 µs per request, and only one core at a time can hold it. The most the lock can serve is 1 / 1 µs = 1 million requests per second, whatever the number of cores. Real behavior is worse: the lock word and the table's cache lines move between cores (each move 50 to 100 ns), and waiting threads sleep and wake through the kernel when contention is high. So 32 cores deliver maybe 0.5 to 1 million requests per second, about 15 to 30% of the ideal, and the p99 latency grows because requests queue for the lock.
With shard-per-core. Hash the key to 1 of 32 shards. Each shard owns 1/32 of the table and needs no lock. A request arrives on a core chosen by the network card's hash. With probability 31/32 the key belongs to another core, so the request is forwarded, which costs perhaps 200 ns (two queue operations and a couple of cache-line transfers), and the reply returns the same way. The extra cost is 0.4 µs for most requests, so the work is about 10.4 µs, giving 96,000 requests per second per core and about 3.1 million in total, 96% of the ideal. If the client is shard-aware and sends the request to the right core, the extra cost disappears.
Now the weakness. Suppose one key receives 5% of the traffic. That key lives on one shard. At a total of 3.1 million per second, that shard would need 155,000 requests per second for the hot key alone, more than the 96,000 a core can do, so the throughput is capped at about 96,000 / 0.05 = 1.9 million per second, while 31 other cores are partly idle. Without sharding, a lock-based design would spread this load but pay the lock cost. Fixes for hot keys are to cache the value on all cores for reads, split the key into sub-keys (hot-key sharding, with merge on read), or give the hot shard more resources.
intuition: Each chef has their own station and ingredients, and passes plates between stations instead of reaching across each other.
The slow part of many cores is not computation but agreement: who may touch this data now. Locks and shared caches are a way to make cores agree, and every agreement costs a cache-line transfer. If you decide in advance which core owns which data, no agreement is needed at run time; the only cost is a message when ownership and the request do not meet. The design is natural because it turns a hardware fact (data moves between caches slowly, and private caches are fast) into a software rule (data stays where it is used).
mistakes: People often think thread-per-core means no communication between cores. In fact it means no shared mutable data. Cores communicate all the time, by messages, and the cost of those messages (and their latency when a queue is long) is a main design factor.
People often think it is the same as running one event loop per core, as Node.js or NGINX do. In fact those usually split connections but share data through the network or the database. Thread-per-core also splits memory, storage queues and data ownership, so a request is routed to the core that owns its data.
People often think more cores always means more throughput. In fact the gain depends on even load. A hot key, a large partition, or a skewed hash puts the extra load on one core, and the other cores cannot help, since they do not own the data.
People often think it removes the need for concurrency control. In fact it removes it inside one shard. Operations that touch several shards (multi-key transactions, secondary indexes, global limits) still need coordination, such as a two-phase protocol or a single coordinating shard, and that is often harder than with shared memory.
People often think a vCPU in the cloud is a core. In fact on most cloud instances a vCPU is a hyperthread, and two hyperthreads share one physical core's caches. Pinning two shards to sibling hyperthreads gives about 1.2 to 1.4 times one core, not two; planning for "N cores" must take this into account.
friction: Skew is the main problem. The design assumes the hash spreads load evenly across cores. A hot key, a large partition or a slow task on one shard cannot be helped by other cores, because they do not own the data. Rebalancing is hard: the number of shards is tied to the number of cores, so changing the core count means re-splitting data, and moving a shard between cores means moving state while serving requests. Static ownership trades the cost of locks for the risk of imbalance.
The programming model is demanding. Code must be asynchronous and non-blocking, written with futures or coroutines, and it cannot call libraries that block, take global locks, or assume that any thread may touch any object. Much of the ordinary ecosystem (JDBC drivers, many client SDKs, standard allocators and loggers) does not fit. Lifetimes are tricky: an object created on one core must be destroyed on that core, and passing data between cores means copying it or transferring ownership. Debugging is harder, since a bug can be an unexpected message order across queues, and a stalled task shows up as latency on a whole shard.
Cross-shard operations are expensive in both cost and complexity. Multi-key transactions, secondary indexes, scans over all shards and global counters need coordination that is no longer solved by a lock. Some designs route such operations through one coordinator core; others run a distributed protocol inside the machine. Throughput also depends on message-queue behavior: a full queue between two cores applies backpressure, and a cycle of cores waiting for each other can deadlock if queues are bounded.
Operations and hardware add friction. Busy-polling reactors use 100% of a core even when idle, which hides real utilization in monitoring and costs power. Cloud vCPUs are often hyperthreads and may suffer from noisy neighbours, so pinning is less effective than on bare metal. Interrupt and network-queue placement must match the core layout, or the benefits fade. The model pays most on large machines with fast network and storage; on a small instance with 2 or 4 cores the added complexity brings little.
practice: Use thread-per-core when you build a data-plane service that is bounded by CPU on small requests and runs on large dedicated machines: a key-value store, a message log, a proxy, a packet processor. For most business services, a normal thread pool or a work-stealing runtime is enough, simpler, and easier to hire for. Before choosing the model, profile your current system: if the top costs are lock contention, futex waits, cache misses on shared structures and context switches, thread-per-core is likely to help; if the time is in business logic and downstream calls, it will not.
If you adopt a framework, take one that already solves the hard parts: Seastar (C++), Glommio or Monoio (Rust), or use a product built on it such as ScyllaDB or Redpanda. Then follow its rules: never block in a task, keep tasks short (under a millisecond if possible), keep per-core state per core, and use the framework's cross-core call for anything else. Watch the reactor-stall and task-quota metrics, since these are the first signs of a problem.
Design the sharding key with care. Choose a key with high cardinality and even spread, add a salt or sub-key for known hot items, and measure per-core load, not only total CPU. Make clients shard-aware where the system supports it (ScyllaDB drivers do), so that requests land on the owning core. Leave a core or two for the operating system, interrupt handling and background tasks, and match network queues, interrupts and the application's cores.
On the machine, give the service dedicated hardware where you can: pin threads, set interrupt affinity, keep memory local to each socket, check that hyperthread siblings are used as you expect. Benchmark with realistic skew (Zipfian keys), not only uniform keys, and test what happens when one core is slowed down by a noisy neighbour.
tradeoffs: Choose thread-per-core when the machine has many cores (16 or more), the work is a high-rate stream of small requests (tens of microseconds each), data can be partitioned by key, and tail latency matters. Choose a conventional thread pool or work-stealing runtime when work is uneven, requests are long or call blocking libraries, the team needs the ordinary ecosystem, and the machine has few cores. You give up automatic load balancing and library compatibility with thread-per-core; you give up some scalability and p99 stability with shared pools.
Choose static sharding (fixed core ownership) when load is evenly spread by key and you want the simplest and fastest path. Choose some dynamic balancing (shard migration, request stealing from overloaded cores, or caches for hot keys) when skew is real. You pay with complexity, since moving ownership means moving state and making sure no request is lost during the move.
Choose a shard-aware client or routing layer when most requests can be sent directly to the owner: it removes the extra hop. Choose server-side forwarding when clients are simple or many, accepting an extra queue hop of a few hundred nanoseconds and a higher load on the receiving cores.
Choose busy polling (the core spins to check for work) when latency in microseconds matters and the machine is dedicated to the service. Choose interrupt-driven sleeping when the host is shared, power cost matters, or the load is often low. You give up 100% CPU use that shows no real work with polling; you give up some microseconds and waking jitter with sleeping.
interview: Why does a shared lock stop scaling with cores, even when the critical section is short? || The lock serializes the critical section, so throughput is capped at 1 / (critical-section time), and the cache line holding the lock moves between cores on every acquisition (tens to hundreds of ns). Waiting threads may sleep and wake via the kernel. By Amdahl's law, if 10% of the work is serialized, 10 times is the maximum speed-up at any core count.
How does a shard-per-core database handle a request that needs data from another shard? || It sends a message to the owning core through a lock-free single-producer single-consumer queue and gets the result as a future. The queues are one per ordered pair of cores, and messages are batched. Better still, a shard-aware client connects so the request lands on the owner. Cross-shard multi-key operations need an extra coordination step.
A single key receives 5% of the traffic on a 32-core thread-per-core system. What happens and what can you do? || The owner core saturates at its per-core limit, so total throughput is capped at that limit divided by 0.05, while other cores stay underused. Options: replicate read-only data to all cores, split the key into sub-keys and merge on read, move the other shards off that core, or use a different data structure for the hot item.
What are the memory and NUMA considerations in this design? || Each core gets its own memory slice from the local NUMA node, with its own allocator, so allocation needs no lock and accesses are local. Memory freed by a different core must return to the owner. If a shard touches remote-socket memory, latency rises 1.5 to 2 times. The slices are fixed at start-up, so memory can be wasted if shards are uneven.
How is this different from work stealing, and when would you use each? || Work stealing (Tokio, ForkJoin) lets any worker take tasks from others, giving good balance for uneven, divisible work at the cost of shared queues and lost cache locality. Thread-per-core keeps data and tasks on one core for locality and no locking. Use work stealing for compute with uneven tasks; use thread-per-core for partitionable, small-request, latency-sensitive services.
Why must code on a shard never block, and how do you find violations? || A blocking call stops the core's only thread, so every request on that shard waits, and there is no other thread to take over. Detect it with the reactor-stall warnings the framework emits, with stack traces at the stall, and by auditing libraries that call blocking system calls, DNS, or take global locks.
quiz: What does "shared-nothing" mean in a thread-per-core server? || Each core owns its data, memory, network queue and I/O queue exclusively, so there is no shared mutable state to lock. Cores cooperate only by sending messages.
Why does single-writer data avoid cache-coherence traffic? || Only the owner core writes the shard's cache lines, so they stay in that core's private cache in an exclusive state. No other core invalidates them, so the coherence protocol has nothing to transfer.
Why can cross-core messages use lock-free queues without atomic read-modify-write instructions? || Each queue has exactly one producer and one consumer. The producer only writes the head index and the consumer only writes the tail index, so plain stores with proper memory ordering are enough.
A core handles 96,000 requests per second. One key gets 5% of all traffic. What is the best total throughput? || The hot key's owner limits the system: 96,000 / 0.05 = about 1.92 million requests per second, however many cores exist.
When would you prefer a work-stealing thread pool over thread-per-core? || When the work is uneven or divisible (parallel computation, tasks of very different lengths), when blocking libraries are needed, or when the machine has few cores, because dynamic balancing then matters more than avoiding sharing.

@@ workstealing
value: Work stealing is a way to share parallel work among CPU cores without a central boss. Each worker thread keeps its own list of tasks. It runs them from its own list, and when the list is empty, it takes a task from the list of another worker. Busy workers are not interrupted and no global queue is needed. Work moves only when someone is idle, and that is exactly when moving it is useful.
The problem is uneven work. A parallel program splits a job into tasks, but tasks differ in size and often create more tasks while they run (a tree search, a recursive sort, a join over skewed data). If you divide the job evenly in advance, some cores finish early and wait while one core finishes the big pieces. If all cores take tasks from one shared queue, the queue becomes a lock or a hot cache line that every core hits on every task. Work stealing avoids both. Most of the time each core touches only its own queue, which costs a few nanoseconds and stays in its cache; communication happens only when a core has nothing to do.
For the layer above, this is the scheduler inside Cilk, Intel TBB, Java's ForkJoinPool (behind parallel streams and CompletableFuture's default executor), Rust's Rayon and the Tokio runtime, Go's runtime scheduler, .NET's thread pool, and many database engines and game engines. It gives DAG schedulers a simple way to keep P cores busy. The layers below provide the parts. Queues give the double-ended queue (deque) whose two ends serve two roles. Randomized algorithms give the random choice of victim that makes the analysis work and keeps thieves from piling on one worker. Threads supply the workers, normally one per core.
terms: Task — a small unit of work that can run on any worker; it may create (spawn) more tasks.
Deque — a double-ended queue; items can be added and removed at either end.
Owner — the worker that a deque belongs to; it pushes and pops at the bottom of its own deque.
Thief / victim — an idle worker that steals, and the worker it steals from; the thief takes from the top of the victim's deque.
Work (T₁) — the total time of the computation on one processor.
Span or critical path (T∞) — the longest chain of tasks that depend on each other; the time on infinitely many processors.
Parallelism — T₁ ÷ T∞, the largest useful speed-up; having many more tasks than processors is called parallel slack.
Grain size — the smallest piece of work for which the program still creates a new task; below it the code runs sequentially.
history: The idea comes from the Cilk project at MIT. Robert Blumofe and Charles Leiserson published "Scheduling Multithreaded Computations by Work Stealing" at FOCS in 1994 (a journal version followed in JACM, 1999). They proved that for a fully strict computation with work T₁ and critical path T∞, the randomized scheduler runs in expected time T₁/P + O(T∞) on P processors, which is optimal up to a constant, and that it uses at most P times the stack space of the sequential run. The earlier idea of stealing was in Burton and Sleep's work on functional programs (1981) and Halstead's Multilisp (1984).
Cilk-5 (Frigo, Leiserson and Randall, PLDI 1998) made it practical with the "work-first principle": put the cost of scheduling on the rare steals, not on the common spawn, so that a spawn costs little more than a function call. Arora, Blumofe and Plaxton (1998, 2001) gave a non-blocking deque and a bound for multiprogrammed machines. Chase and Lev (SPAA 2005) published the dynamic circular deque that most runtimes copy. Lê, Pop, Cohen and Zappa Nardelli (PPoPP 2013) showed a correct version for weak memory models such as ARM and Power, where earlier code could fail.
The idea reached mainstream languages through libraries. Doug Lea published the Java Fork/Join framework in 2000 and it shipped in Java 7 (2011), then powered parallel streams in Java 8. Intel TBB (2006) brought it to C++. Dmitry Vyukov redesigned Go's scheduler with work stealing in Go 1.1 (2013), and Rust's Rayon (2015) copied the Cilk model. The Tokio runtime added a multi-threaded work-stealing scheduler in 2019, which a rewrite made several times faster in benchmarks. The model is now the default way to run many small tasks on many cores.
how: Each of the P workers has a deque of tasks. The owner treats its deque as a stack: it pushes new tasks on the bottom and pops tasks from the bottom. This is last-in, first-out. A thief treats the victim's deque as a queue: it removes a task from the top, the oldest one. The two ends are different on purpose. In a divide-and-conquer program, the task at the top of the deque was created earliest, so it is the closest to the root of the task tree and is therefore the largest piece of remaining work. One steal gives the thief a lot to do, so steals are rare. The owner, by contrast, works on the newest, smallest tasks, whose data was just touched and is probably still in its cache, and its stack use stays small, just like a normal recursive program.
Take a parallel function that sums a range. If the range is small, sum it directly. Otherwise split it into a left half and a right half; spawn the right half as a task (push it on the bottom of the deque), compute the left half in the current thread, then try to pop the right half. If it is still there, nobody stole it, and the thread runs it itself, at the cost of a push and a pop (tens of nanoseconds). If it is gone, a thief took it, and the owner waits for the result or, better, runs other tasks while waiting. This is how Rayon's join and the Java ForkJoin fork and join work; Cilk instead lets a thief steal the continuation of the function, which gives stronger space bounds.
The scheduling loop of an idle worker is simple. Look at the own deque; if it is empty, pick another worker at random and try to steal from the top of its deque; if that fails, try another random victim; after many failures, park the thread (sleep) to save power and wake it when new work appears. The random choice is the contribution of randomized algorithms. A deterministic rule (always steal from worker 0, or scan in order) makes thieves collide on the same victim and can create bad cases. With random choice, the analysis shows that thieves spread over the workers, that the critical path shrinks by a constant fraction every P steal attempts in expectation, and so that the total number of steal attempts is O(P · T∞). Each attempt costs a cache miss or two, so the total scheduling overhead is small whenever the program has enough parallelism (T₁/T∞ much larger than P).
That gives the bound. Work is T₁, so with P cores each doing useful work at all times, you need T₁/P. The critical path cannot be sped up, and it adds up to O(T∞) in steal attempts and waiting. The expected time is therefore T₁/P + O(T∞). When T₁/T∞ ≫ P (parallel slack), the second term is negligible and the speed-up is nearly P. The lower bound is max(T₁/P, T∞), so the scheduler is within a constant factor of optimal. A simple greedy scheduler achieves T₁/P + T∞; the real value of stealing is that it gets close to this bound without any global state.
The deque itself is the hard part. The owner operates on the bottom with no atomic read-modify-write in the common case. A thief takes the top with a compare-and-swap (CAS) on the top index. In the Chase-Lev design, an array is used as a circular buffer with a top index and a bottom index; when it fills, the owner allocates a larger array. The only race is over the last element, when the owner pops and a thief steals at the same moment; this is resolved with a CAS on top, and exactly one wins. Memory ordering matters here: the owner needs a store-load barrier after decrementing bottom, and the thief must see the task contents before it sees the new bottom. This is why correct versions for ARM took years to get right.
Real runtimes add details. Tokio gives each worker a local queue of 256 tasks, with overflow going to a shared global queue, steals half of a victim's queue at once to cut the number of steals, and keeps a "LIFO slot" for the most recently spawned task to improve cache reuse. Go's scheduler has a similar local run queue of 256 goroutines per processor (P), steals half of another P's queue, and checks the global queue every 61 scheduling ticks so that it is not starved. ForkJoinPool lets workers help (run other tasks) while they wait for a join, and compensates when a task blocks.

example: Eight workers must process 80 independent tasks. Seventy-two tasks take 1 ms each, and eight tasks take 10 ms each. The total work is 72 × 1 + 8 × 10 = 152 ms. With 8 workers, the best possible time is 152 / 8 = 19 ms, and no schedule can be faster than the longest task, 10 ms.
Static split. Give each worker 10 consecutive tasks. If the eight long tasks happen to be the first eight, worker 0 gets all of them and 2 short ones: 82 ms. The other workers finish after 10 ms and sit idle. The total time is 82 ms, a speed-up of 152 / 82 = 1.9 times on 8 cores.
Work stealing. The tasks start in worker 0's deque (or distributed, it does not matter). Workers 1 to 7 are idle at the start, so they steal from the top of worker 0's deque. Each steal takes the oldest task, which here is a long task. After a few microseconds each worker holds one long task or a few short ones, and when a worker finishes it steals again. Idle workers keep taking whatever remains, so by the time the long tasks finish at about 10 ms, the short ones are shared among the workers. The total time ends close to 19 to 22 ms: near the 19 ms ideal, with a small cost for steals (80 steals at a microsecond or less each is under 0.1 ms in total). The speed-up is about 7 times. The theory gives T₁/P + T∞ ≤ 19 + 10 = 29 ms as an upper bound for a greedy schedule, and the real figure is far below it because the long tasks start early.
Now look at the structure of the parallel sum. Add 1,000,000 numbers with a grain size of 1,000. The work is about 1 million additions, roughly 1 ms. The task tree has 1,000 leaves of 1,000 numbers each and a depth of 10 splits. The critical path is one leaf (1,000 additions, about 1 µs) plus 10 levels of spawn and join, each tens of nanoseconds, so about 2 µs. The parallelism is 1 ms / 2 µs = 500, far above 8 cores, so the time on 8 cores is close to 1 ms / 8 = 125 µs, plus the overhead of about 1,000 task creations (tens of microseconds in total, mostly not stolen). If the grain size were 10, there would be 100,000 leaves and the overhead of creating tasks would be comparable to the additions themselves, so the program would be slower than the sequential version. The grain size therefore needs to be large enough for each task to take at least some microseconds.
intuition: Finish your own pile; when you are done, quietly take the oldest item from a busy colleague's pile.
The oldest item in a pile is the biggest, because big jobs are split into smaller ones as people work on them. A colleague who takes it gets a lot to do and will not need to come back soon, and the owner, who works on the small new items at the other end, is not disturbed. Because only idle people ask, nothing is moved when everyone is busy. The design is natural because it uses the one moment when the information is cheap: an idle worker knows by itself that it is idle.
mistakes: People often think work stealing needs a central scheduler that knows the load. In fact there is no global state. Each idle worker decides alone, by looking at one random victim. This is why it scales to many cores.
People often think stealing is the main activity of the scheduler. In fact most tasks are never stolen. A well-designed program with enough parallel slack has the owner push and pop its own tasks, and steals are O(P · T∞) in total, which is tiny compared with the number of tasks.
People often think more tasks are always better. In fact each task has a cost (allocation, a push and pop, a possible steal, and lost locality). If tasks are smaller than a few microseconds of work, the overhead can be larger than the work. The goal is enough parallel slack (maybe 8 to 10 times as many tasks as cores), not the maximum number.
People often think work stealing makes blocking code safe. In fact a task that blocks (waits on a socket, a lock, a sleep) holds a worker thread without doing work, and with few workers the pool can stall or deadlock. Runtimes provide escape hatches (Tokio's spawn_blocking, ForkJoinPool's ManagedBlocker), and CPU pools should be kept separate from blocking pools.
People often think work stealing guarantees fairness or order. In fact it is built for throughput of a computation, not for fairness among independent jobs. Tasks run in an order that depends on timing, results can be non-deterministic if the program has races or uses floating-point reductions, and the newest task runs first on the owner, so old tasks may wait.
friction: The first cost is locality. A stolen task runs on a core that does not have the data in its cache, and on a NUMA machine the data may sit in another socket's memory. Programs that touch large arrays can lose a lot to this; the usual remedy is to steal big chunks (so locality inside the chunk is preserved) and to prefer victims on the same socket. Stealing also causes cache-line traffic on the deques themselves, and false sharing between neighboring deque indices if they are not padded.
Blocking and mixed workloads are the second problem. Work stealing assumes that tasks are short, non-blocking, and CPU bound. If tasks block on I/O or locks, workers sit idle while there is work in other deques, or the pool grows threads to compensate and loses its benefit. Java's common pool is shared by all parallel streams in a process, so one slow stream can delay others. Latency-sensitive tasks mixed with large batch tasks have no priority mechanism by default.
Third, tuning the idle behavior is delicate. Spinning workers waste power and CPU, but parking and waking threads costs microseconds, and waking too many threads when one task arrives (a thundering herd) wastes time. Runtimes limit how many workers may search for work at once (Tokio allows at most about half), and add timeouts. Bad choices show up as high CPU use at low load or high latency on first tasks after a quiet period.
Finally, correctness is difficult. The deque algorithms are subtle and have had memory-ordering bugs on weak architectures. The theory covers fully strict fork-join computations; programs with arbitrary dependencies, locks held across spawns, or priorities fall outside the bounds. Debugging is also harder, since the schedule differs every run, and profiles must separate scheduling cost from useful work.
practice: Use a work-stealing runtime for CPU-bound, divide-and-conquer or data-parallel work: Rayon (par_iter, join) in Rust, ForkJoinPool or parallel streams in Java, TBB's parallel_for in C++, Cilk, or goroutines in Go. Express the work as many tasks with parallel slack, but stop splitting when a task falls below a grain size of roughly 10 to 100 microseconds of work (in Rayon use with_min_len, in Java a threshold). Measure the speed-up with 1, 2, 4, ... P workers; if it flattens early, look for the critical path, memory bandwidth, or locks.
Keep blocking work away from the CPU pool. In Tokio, use spawn_blocking or a separate runtime for blocking calls and file I/O; in Java, use a separate executor for blocking tasks rather than the common pool, or size a ForkJoinPool for it. In Go, goroutines that block in system calls are handled by the runtime, but CPU-bound loops should still be written to allow preemption (Go has had asynchronous preemption since 1.14). Since Go 1.25, GOMAXPROCS follows the container CPU limit by default, which avoids over-subscribing a limited container.
Be careful with shared state. Avoid locks held across spawns, and prefer reductions that combine per-task results. Floating-point sums vary in order, so results may differ in the last digits between runs. Watch the number of workers against the real CPU quota in containers, because too many workers in a throttled cgroup cause stalls.
Observe the scheduler. Tokio exposes steal counts and queue depths through its metrics; Java's ForkJoinPool reports steal count and queued tasks; Go has the scheduler trace (GODEBUG=schedtrace) and the execution tracer. Many steals relative to tasks can mean tasks are too coarse or the work is unbalanced; very high CPU with little progress can mean spinning. In data systems like Spark, note that executors do not steal work across tasks: the driver assigns tasks with locality preferences and uses speculative execution for stragglers, so data skew there is solved by repartitioning, not by stealing.
tradeoffs: Choose work stealing when tasks are uneven or created dynamically (recursive algorithms, graph and tree traversal, irregular loops), tasks run for microseconds to milliseconds, and you want good load balance with little tuning. Choose static partitioning when the work is regular and known in advance (an array operation with equal cost per element): it has no scheduling cost and gives perfect locality. You give up predictability and data locality with stealing; you give up balance with static splits.
Choose per-worker deques with stealing over one shared queue when the number of cores is more than a handful and tasks are short. A shared queue has simple fairness and priorities but its lock or head pointer becomes the bottleneck at high rates. Choose a shared queue (or a global queue plus stealing, as in Go and Tokio) when you need fairness among independent jobs, priorities or bounded queueing. You pay with contention on the shared queue, or with weaker fairness in the stealing design.
Choose thread-per-core sharding over work stealing when the work is tied to data that should stay on one core (a partitioned database, a log) and request sizes are small and uniform. Choose work stealing when the data is shared read-only or can be moved, and the load is uneven. Sharding removes sharing and gives stable latency, and stealing balances load and tolerates skew.
Choose to steal half of the victim's tasks (Tokio, Go) when tasks are tiny and steals should be rare; choose to steal one task when tasks are big and you want to keep work near its owner. Choose child stealing (Rayon, ForkJoin, TBB) for simple library implementation, and continuation stealing (Cilk) when you need the tight space bound and can use a compiler or runtime that supports it.
interview: Why does the owner use the bottom of its deque and the thief the top? || The owner works LIFO on the newest, smallest tasks, which keeps its cache warm and its stack depth like a sequential recursion, and it needs no atomic operations in the common case. The separation also means owner and thief rarely touch the same element.

It requires enough parallel slack (T₁/T∞ ≫ P), tasks that do not block, and random victim selection.

@@ lockfree
value: A lock-free data structure lets many threads read and change shared data (a queue, a stack, a map, a counter) without ever taking a lock. Each thread prepares its change privately and then publishes it with one atomic instruction, compare-and-swap (CAS), which succeeds only if nobody changed the data in the meantime. If it fails, the thread looks at the new state and tries again. The guarantee is about progress: if threads are running, at least one of them finishes its operation in a bounded number of steps, even if other threads are slow, descheduled or killed.
This matters because locks have failure modes that grow with scale. A thread that holds a lock and is paused (the scheduler preempts it for milliseconds, a page fault, a garbage-collection pause) blocks every other thread that needs the lock. Locks can deadlock, can cause priority inversion (a high-priority thread waits for a low-priority one), cannot be used safely inside signal handlers or interrupt handlers, and under heavy contention make threads sleep and wake through the kernel, which costs microseconds. A lock-free structure has none of these: nobody can hold others up.
For the layer above, lock-free structures are the plumbing of high-throughput systems: the LMAX Disruptor ring buffer in trading systems, the task queues inside Netty and the Seastar-style runtimes, java.util.concurrent's ConcurrentLinkedQueue, atomics and LongAdder, memory allocators, Linux's RCU and lock-less lists, and the cross-core queues of thread-per-core databases. They are also how batches are handed from one pipeline stage to another. Locks and atomics (L3) supply the CAS instruction itself. Memory models say in what order other threads see the writes, which decides whether the algorithm is correct. Cache coherence explains the real cost: even without locks, a contended CAS moves a cache line between cores. Queues and ring buffers are the most common shape of the structure.
terms: Compare-and-swap (CAS) — an atomic instruction: "if this memory location still holds value A, replace it with B, and tell me whether it worked".
Lock-free — a progress guarantee: whenever threads are running, at least one operation finishes in a bounded number of steps, so the system as a whole never stalls.
Wait-free — a stronger guarantee: every operation finishes in a bounded number of its own steps, whatever the other threads do.
Obstruction-free — the weakest of the three: an operation finishes if it runs alone for long enough, but competing threads can make each other retry forever.
ABA problem — a CAS succeeds because the value is the same as before, although it changed to something else and back in between, so the assumption "nothing changed" is false.
Memory reclamation — the problem of deciding when it is safe to free or reuse a removed node, since another thread may still be reading it.
Hazard pointer — a published per-thread pointer saying "I am using this node"; a node can be freed only if no hazard pointer names it.
Epoch-based reclamation — threads announce which global epoch they are in; garbage retired in an old epoch is freed once all threads have moved on.
history: The theory came first. In 1991 Maurice Herlihy's paper "Wait-Free Synchronization" proved that primitives differ in power. Plain reads and writes cannot solve consensus for two threads (consensus number 1), while compare-and-swap solves it for any number of threads, and so can build a wait-free version of any data structure (the universal construction). This is why every modern CPU offers CAS or its equivalent. In 1986, R. Kent Treiber had already described the stack that bears his name, and in 1996 Maged Michael and Michael Scott published the lock-free queue that Java still uses in ConcurrentLinkedQueue. Tim Harris gave a lock-free linked list in 2001.
Memory reclamation turned out to be harder than the algorithms. Michael's hazard pointers (2004) and Keir Fraser's epoch-based scheme (his 2004 thesis "Practical Lock-Freedom") gave two practical answers. Paul McKenney's read-copy-update (RCU) went into the Linux kernel in 2002 and is now used for thousands of kernel structures. Herlihy, Luchangco and Moir (2003) defined obstruction-freedom as a weaker and easier goal. Kogan and Petrank (2011) and Yang and Mellor-Crummey (2016) built wait-free queues that are fast in practice with a fast path and a slow helping path.
Engineering practice followed. The LMAX Disruptor (2011, Martin Thompson and colleagues) showed a single-writer ring buffer with sequence numbers and padding against false sharing, which handled millions of events per second per thread. Doug Lea's LongAdder (Java 8) reduced contention on counters by striping. The Rust ecosystem produced crossbeam (epoch reclamation) and Java produced JCTools (single-producer and multi-producer queues used inside Netty). Lê and colleagues (2013) fixed work-stealing deques for ARM, and the C++11 and Java 9 memory models gave portable names (acquire, release) to what these algorithms need.
how: The basic pattern is a CAS loop. Read the current state, compute a new state without changing anything shared, then try CAS(location, old, new). If the CAS succeeds, the operation took effect at that instant (its linearization point). If it fails, another thread changed the location, so read again and recompute. The Treiber stack shows it. The head pointer points to the top node. To push, create a node, set node.next = head, and CAS the head from the old value to the new node; if the CAS fails, repeat. To pop, read head = A and A.next = B, and CAS the head from A to B; if the CAS fails, repeat. Nothing is locked, and if one thread stops in the middle, the stack is still valid because no change is visible until its single CAS.
The CAS instruction is the contribution of the locks-and-atomics layer. On x86 it is LOCK CMPXCHG; on ARM it is a load-linked/store-conditional pair (LDXR/STXR) or the CAS instruction added in ARMv8.1. Hardware makes it atomic by holding the cache line in an exclusive state for the duration of the instruction. An uncontended CAS on a line already in the core's cache costs roughly 5 to 20 cycles, a few nanoseconds.
Correctness depends on the memory model. A pusher writes the node's fields and then publishes the node with a CAS. Another thread that reads the head and follows the pointer must see the node's fields as written. This needs the publishing CAS to have release semantics and the reader's load to have acquire semantics. On x86 the ordering is strong by default and a CAS is a full fence; on ARM and Power the programmer, or a language such as C++ or Java, must request the right ordering, and many bugs have been found only on weak machines.
Two problems remain. The first is the ABA problem. Take the stack A → B → C. Thread 1 starts a pop: it reads head = A and A.next = B, and is paused before its CAS. Thread 2 pops A, pops B, frees B, and pushes A back, so the stack is A → C. Thread 1 resumes and executes CAS(head, A, B). The head is A, as it expected, so the CAS succeeds, and the head becomes B, a freed node. The structure is corrupt, and C is lost. Solutions are to attach a version counter to the pointer (a 64-bit pointer plus a 64-bit tag compared with a double-width CAS, or a tag in unused pointer bits) so that A with version 1 differs from A with version 3, or to make sure memory cannot be reused while anyone may hold it.
That is the second problem and the harder one, memory reclamation. In a language with a garbage collector (Java, Go, C#) the collector does the job: node B is not reclaimed while thread 1 still holds a reference to it, so classic ABA through reuse cannot happen. In C, C++ and Rust, the algorithm must free nodes itself. With hazard pointers, a thread announces "I am about to use node A" in a shared slot, rereads the head to check that A is still there, and only then dereferences it. A thread that removes a node puts it on a retired list and frees it only after scanning all hazard slots and finding no one using it. Hazard pointers bound the amount of garbage, but cost a memory fence per node visited. With epoch-based reclamation, each thread marks itself active in the current global epoch while it works in the structure; a retired node is freed after the epoch has advanced twice, when no thread can still hold it. This is cheaper per operation, but one stalled thread can stop epochs advancing, so garbage grows. RCU is a variant for read-mostly data, where readers take no atomic operation at all and the writer waits for a grace period.
The last point is cost. Lock-free does not mean free of contention. When many cores CAS the same location, the cache line moves between cores in a modified state, each move taking tens to hundreds of nanoseconds, and most attempts fail and repeat. This is the coherence layer's contribution to the cost model: throughput on one hot location is limited to about one successful update per line transfer, roughly 10 to 20 million per second, however many cores try. Good designs therefore reduce sharing: striping (LongAdder), per-thread buffers, single-writer rings, and exponential backoff after a failed CAS.

example: A service counts requests with one shared 64-bit counter updated by 8 threads on 8 cores. Each thread runs a tight loop that does counter.incrementAndGet().
With one thread, the counter line stays in the core's cache, and an increment costs around 5 ns, so about 200 million increments per second. With 8 threads, every increment must get the line in an exclusive state. The line moves from core to core at about 50 to 100 ns per transfer, and these transfers are serialized, so the total rate falls to roughly 10 to 20 million per second, not 1.6 billion. Eight times more threads give about ten times less total throughput than one thread. If the code uses a CAS loop instead of an atomic add, many CAS attempts also fail and are repeated, wasting more transfers.
Now replace it with Java's LongAdder. It keeps an array of cells, and each thread updates a cell chosen by its thread id; if a CAS on a cell fails, the thread moves to another cell. Increments touch mostly private cache lines, so the speed is again about 5 to 10 ns per increment per thread, around 1 billion per second in total on 8 cores. The price is that reading the total means summing all cells, which costs more and is not an exact snapshot while updates continue. This is the same lesson as thread-per-core design: remove the sharing, not only the lock.
Next, a Treiber-stack trace to see the CAS loop. The stack holds A → B → C with head = A. Two threads push X and Y at the same time. T1 reads head = A, sets X.next = A. T2 reads head = A, sets Y.next = A. T1 executes CAS(head, A, X) and succeeds: head = X → A. T2 executes CAS(head, A, Y) and fails because head is now X. T2 rereads head = X, sets Y.next = X, and tries CAS(head, X, Y), which succeeds: Y → X → A → B → C. Both pushes took effect, in a valid order, and T2 paid one retry. If T1 had been paused after reading head, T2 would have completed its push anyway, which a lock-based stack cannot offer.
Finally, compare with a lock under preemption. If a thread holds a mutex and the scheduler removes it from its core, every other thread that needs the mutex sleeps until the owner runs again, which can take milliseconds on a loaded machine (typical scheduler time slices are in the range of a few to tens of milliseconds). In the lock-free stack, the paused thread has made no visible change, so the others proceed.
intuition: Instead of locking the door, write your change on a note and swap it in only if nobody else changed the page meanwhile; if they did, read the new page and try again.
Locking assumes that conflict is likely and prevents it up front. The CAS loop assumes that conflict is rare and detects it afterwards. When conflict is rare this wins, since the common case is one fast instruction. When conflict is constant, detection means repeated work. The hard part, as in any optimistic scheme, is making the detection exact: the "page" must really be the same page, which is why the ABA problem and memory reuse are the real subjects of the field.
mistakes: People often think lock-free means faster. In fact lock-free is a progress guarantee, not a speed claim. Under heavy contention on one location, a well-designed lock with backoff can match or beat a naive CAS loop, since failed CAS attempts waste cache-line transfers. The benefits are robustness to preemption and no deadlock, and good scalability when the design avoids sharing.
People often think lock-free means no waiting at all. In fact a thread can retry many times, and only the system as a whole is guaranteed to progress; one unlucky thread can starve. Only wait-free structures bound the steps of every operation, and they are more complex and often slower on average.
People often think that using java.util.concurrent makes everything lock-free. In fact ConcurrentHashMap uses CAS to insert into an empty bin but synchronizes on the bin's first node when there is a collision; ConcurrentLinkedQueue is lock-free but LinkedBlockingQueue uses locks. Read the documentation for the guarantee you need.
People often think the ABA problem is a theoretical curiosity. In fact it caused real corruption in memory allocators and queues in C and C++ code that recycles nodes through free lists. Garbage-collected languages mostly hide it, which is why the same algorithm is simple in Java and dangerous in C++.
People often think a test run that passes proves the algorithm is correct. In fact lock-free bugs depend on rare interleavings and on the memory model of the CPU. Code that works on x86 can fail on ARM. Use formal models, stress tests with thread sanitizers, and tools that explore interleavings (Loom for Rust, CDSChecker, model checkers).
friction: The first cost is difficulty. Designing a correct lock-free structure is research-level work, and published algorithms have contained bugs for years. Verification needs reasoning about every interleaving and about memory ordering on weak architectures. Teams that need a lock-free queue should almost always use a proven library (JCTools, crossbeam, Folly, Boost.Lockfree, the Disruptor) rather than invent one.
Memory reclamation is the second, and often the reason for choosing a garbage-collected language. Hazard pointers add a fence to each node access; epoch-based schemes can accumulate unbounded garbage if one thread stalls; reference counting adds contended atomic increments on every access. Each choice changes the performance and the guarantees of the whole structure, and none of them is free.
Contention remains. A hot CAS location serializes all threads on cache-line transfers, with failed attempts that waste work and power. Lock-free structures also tend to have poor locality, since linked nodes are scattered in memory, and queues with a single head and tail pointer become bottlenecks, which is why high-end designs use arrays and batching or per-thread structures. Unbounded structures can use unlimited memory when producers outrun consumers, so a lock-free queue needs separate backpressure.
Lastly, the guarantees can be weaker than they look. Operations like size(), iteration and bulk updates are often only weakly consistent, since there is no point in time at which the whole structure is frozen. Compound actions (check then act on two structures) are not atomic. Progress guarantees say nothing about fairness or latency of an individual thread, and in practice, a good mutex with a short critical section is often simpler, easier to debug and fast enough.
practice: Use a lock-free structure from a trusted library when you need a queue or map shared between threads and measurements show lock contention or latency spikes from preemption: JCTools or the Disruptor in Java for queues between pipeline stages, java.util.concurrent for general use, crossbeam in Rust, Folly or Boost.Lockfree in C++. Choose the narrowest queue that fits your pattern. A single-producer single-consumer queue is much faster and simpler than a multi-producer multi-consumer queue, and a bounded ring gives backpressure for free.
Reduce sharing before you remove locks. Partition data so that each thread owns its part, use per-thread counters (LongAdder, thread-local buffers) and combine results later, pad hot fields to separate cache lines to avoid false sharing, and pass batches instead of single items. In a ring buffer, let the consumer process everything available up to the producer's sequence in one pass.
When you write CAS loops yourself, keep them small: one CAS on one location, with the new state computed from a local copy. Add exponential backoff after repeated failures, state the memory ordering you need (acquire/release rather than the strongest by default), and avoid recycling nodes unless you have a reclamation scheme. In a garbage-collected language, prefer allocating a new immutable node to reusing one, as that removes the ABA problem.
Test hard. Run stress tests with many more threads than cores, run on ARM as well as x86, use ThreadSanitizer, and use interleaving explorers such as Loom (Rust) or model checkers. Measure with realistic contention and check tail latency and throughput against a simple mutex-based version, and keep the simple version if the lock-free one does not clearly win.
tradeoffs: Choose a mutex (or a read-write lock, or a concurrent map with striped locks) when critical sections are short, contention is moderate, correctness and maintainability matter most, and you do not need guarantees under preemption. Choose a lock-free structure when threads may be descheduled or paused inside critical sections (oversubscribed machines, garbage-collected runtimes with pauses), when you cannot block (interrupt handlers, real-time paths, signal handlers), or when throughput at high thread counts matters. You give up simplicity and easy verification with lock-free code; you give up robustness to stalls with locks.
Choose single-producer single-consumer or single-writer designs when you can arrange them, as with core-to-core messages and pipeline stages: they need no CAS at all, only ordered loads and stores, and run at tens of millions of messages per second. Choose multi-producer designs only when you need them, paying with a CAS on a shared tail pointer and contention. Choose striping or sharding (LongAdder, per-core queues) when one location is the bottleneck, and accept weaker snapshots and a more expensive read.
Choose wait-free algorithms when you need hard latency bounds, as in hard real-time and some trading or control paths. Choose lock-free when average throughput and system-wide progress are enough; wait-free versions are more complex and often slower. Choose obstruction-free when you want a simpler design and have a contention manager that avoids livelock.
Choose garbage collection, epochs or RCU for reclamation in read-mostly structures with short operations, and hazard pointers when you need bounded garbage and can pay the fence cost per node. Choose reference counting only when other schemes do not fit. You trade memory overhead and latency spikes against per-access cost.
interview: Implement a lock-free stack push and pop, and explain what can go wrong. || Push: loop { old = head; node.next = old; if CAS(head, old, node) break }. Pop: loop { old = head; if null return; next = old.next; if CAS(head, old, next) return old }. Why can a lock-free counter be slower than expected with many threads, and what do you do? || All threads update one cache line, which moves between cores for every update and serializes them at about 50 to 100 ns each, so total throughput is capped at 10 to 20 million per second and failed CAS attempts add waste. Use striped counters (LongAdder), per-thread counters merged on read, or shard the counter by core.
What is the difference between lock-free and wait-free, and when do you need wait-free? || Lock-free: some thread always makes progress, but an individual thread may retry indefinitely. Wait-free: each operation completes in a bounded number of its own steps. Use wait-free when worst-case latency per operation must be bounded, as in hard real-time systems. Otherwise lock-free (or a good lock) is usually simpler and faster.
Compare hazard pointers and epoch-based reclamation. || Hazard pointers: each reader publishes the node it uses, so reclamation is precise and garbage is bounded, but each node access needs a store plus fence. Epochs: readers only mark entry and exit, so reads are cheap, but one stalled thread blocks epoch advance and garbage can grow. RCU is the same idea for read-mostly data with grace periods.
Why does a program using a lock-free queue pass tests on x86 and fail on ARM? || x86 has a strong memory model (total store order) that hides missing ordering, while ARM and Power may reorder loads and stores, so a reader can see a node's pointer before its contents. Fix by publishing with release and reading with acquire, and test on weak hardware or with a model checker.
quiz: What does CAS do, and what makes a loop built from it lock-free? || CAS atomically replaces a value with a new one only if it still equals the expected value, and reports success. A thread whose CAS fails did so because another thread's CAS succeeded, so some operation always completes: the system makes progress without locks.
Why can a lock-free design survive a paused thread when a lock cannot? || A thread makes no visible change until its single CAS, so a paused thread leaves the structure valid. A paused lock holder blocks all others who need the lock.
What does the ABA problem break, and how does a version tag help? || A CAS succeeds because the value looks unchanged although it changed to another value and back, so the assumption about the rest of the structure is wrong. A version counter next to the pointer makes the two states differ, so the CAS fails.
Eight threads share one counter and each update costs a 60 ns cache-line transfer. About what is the maximum total update rate? || About 1 / 60 ns, roughly 16 million updates per second in total, whatever the number of threads.
When would you choose a mutex over a lock-free queue? || When contention is low to moderate, the code must be simple and verifiable, tasks are not time-critical under preemption, and you do not need to run in interrupt or real-time contexts. Many mutex-based queues are fast enough.

@@ concgc
value: Generational and concurrent garbage collectors are the techniques that let managed languages (Java, Scala, Kotlin, Go, C#) run with heaps of tens or hundreds of gigabytes and still pause the program for only milliseconds or less. A basic tracing collector must stop the program, find everything reachable, and free the rest; the pause grows with the heap or the live data, so a 64 GB heap could freeze a service for seconds. Two ideas fix this. Generational collection avoids most of the work by collecting only the young objects, which are nearly all garbage. Concurrent collection moves the remaining work to background threads that run while the program runs.
This matters for the systems you run. Kafka brokers, Spark executors and drivers, Flink, Elasticsearch, Cassandra and most Java services have heaps in the gigabyte range, and a stop-the-world pause is felt as a failed health check, a dropped broker session, a consumer rebalance, or a tail-latency spike. The collector choice (G1, ZGC, Shenandoah, Parallel) and its settings often decide whether p99 latency is steady or has periodic stalls. A GC pause longer than a timeout (for example the 45 s session timeout of a Kafka consumer or a ZooKeeper session) turns a performance problem into an outage.
The layers below make it possible. Garbage collection (L3) provides the base: tracing from roots, marking, copying and compacting. Memory models supply the discipline for barriers: small pieces of code that the runtime inserts at every reference read or write so that the collector and the running program agree about where objects are, even though both run at once. Virtual memory and paging let the collector manage address space in pages, remap pages cheaply, and return memory to the operating system.
terms: Young generation — the area where new objects are allocated; it is collected often, and most objects in it are already dead.
Old generation — the area for objects that survived several young collections; it is collected rarely.
Weak generational hypothesis — the observation that most objects die young.
Remembered set / card table — a record of which old-generation areas point into the young generation, so a young collection does not scan the whole old generation.
Write barrier — code run on every reference store; it records information for the collector (for example, marks a card dirty).
Load (read) barrier — code run on every reference load; it checks whether the pointer is still valid and repairs it if the object moved.
Concurrent marking — finding live objects while application threads are running.
SATB (snapshot-at-the-beginning) — a marking method that treats every object alive at the start of marking as live, by recording references that are overwritten during marking.
Evacuation — copying live objects out of a region into a new one so the old region can be reused as a whole.
history: Generational collection started with an observation. Lieberman and Hewitt (1983) noticed that young objects die sooner than old ones, and David Ungar's Generation Scavenging (1984, for Berkeley Smalltalk) gave the first practical collector that exploited this: copy the live young objects into a small space and ignore everything else. Appel (1989) simplified it for functional languages. By the late 1990s, HotSpot had a young generation with eden and two survivor spaces, and an old generation collected by mark-sweep-compact, with a stop-the-world pause.
Reducing pauses came next. The Concurrent Mark Sweep (CMS) collector ran most of the marking concurrently, but it left memory fragmented and sometimes fell back to a long full collection. The Garbage-First (G1) collector by Detlefs, Flood, Heller and Printezis (ISMM 2004) cut the heap into equal regions and collected the regions with the most garbage first, within a pause-time goal. G1 became the default collector in Java 9 (2017) and replaced CMS, which was removed in Java 14.
Fully concurrent compaction arrived from two directions. Azul's Pauseless collector (2005) and its successor C4 (2011) used a read barrier on commercial JVMs. In OpenJDK, Red Hat's Shenandoah (production in JDK 15, 2020) and Oracle's ZGC (Per Lidén, experimental in JDK 11 in 2018, production in JDK 15) move objects while the program runs, with pauses that do not grow with the heap. Generational ZGC arrived in JDK 21 (JEP 439, 2023), became the default mode of ZGC in JDK 23 (JEP 474), and the old non-generational mode was removed in JDK 24 (JEP 490). Generational Shenandoah became a product feature in JDK 25 (JEP 521). The trend is clear: the pause is now small, and the cost has moved to CPU and memory overhead.
how: Start with the base from the garbage-collection layer: a tracing collector finds the roots (thread stacks, static fields), follows references to mark everything reachable, and treats the rest as free. Done in one stop-the-world step, the pause is proportional to the live data (for marking and compaction) and can be seconds on large heaps. The two ideas change where and when the work happens.
Generational collection first. The heap is divided into a young and an old generation. New objects are allocated by bumping a pointer in eden, which costs a few instructions. When eden is full, a young collection starts. Its roots are the thread stacks, plus the old objects that point into the young generation. To find those without scanning the whole old generation, the runtime keeps a card table: one byte for each 512 bytes of old heap. Every reference store runs a write barrier that marks the card of the written object as dirty (a shift and a store). The collector scans only dirty cards. It copies the live young objects, usually a few percent of eden, into a survivor space or the old generation, and then eden is empty again at no extra cost. The pause is proportional to the survivors, not the heap. An object that survives enough young collections (up to 15 in HotSpot) is promoted to the old generation. This is why the weak generational hypothesis is so valuable: if 98% of the objects are dead at collection time, the young collection does 2% of the work of a full one.
G1 applies this to a heap divided into regions of 1 to 32 MB, about 2,000 regions in total. Each region is eden, survivor or old, and objects can be anywhere. Each region has a remembered set of the places that point into it, kept by a post-write barrier and background refinement threads, so any set of regions can be collected without scanning the rest. A young collection (or a mixed collection) is a stop-the-world evacuation: choose a collection set of regions, copy their live objects in parallel to empty regions, and free the sources. G1 measures how long copying took per region, so it can choose as many regions as fit inside the pause goal (200 ms by default, set by MaxGCPauseMillis). Old regions are chosen by garbage first: a concurrent marking cycle runs in the background (started when the heap passes an occupancy threshold), and tells G1 how much live data each old region holds. Marking uses SATB: a pre-write barrier records the old value of any reference that is overwritten while marking runs, so an object that was reachable when marking began cannot be lost. If copying runs out of space, G1 falls back to a full stop-the-world collection, which is the case to avoid.
ZGC and Shenandoah take the next step and also move objects concurrently. Moving objects while threads run is hard, because a thread might read a reference to the old copy while the collector has already made a new one. These collectors solve it with a load barrier, a short piece of code inserted at every reference load from the heap. In ZGC, pointers carry metadata bits (colors) that say whether the pointer is up to date. The barrier checks the bits with a mask and a branch. In the common case the pointer is good and the barrier costs a couple of instructions. If it is not, a slow path looks up the object's new address in a forwarding table, fixes the pointer and also writes the corrected pointer back into the field ("self-healing"), so the cost is paid once per field. A cycle has concurrent mark, concurrent selection of pages with the most garbage, and concurrent relocation: GC threads copy objects to new pages, and any application thread that touches an object not yet moved relocates it itself. The only pauses are short synchronizations at phase boundaries, where threads are handled one by one with handshakes, so the pause is under a millisecond and independent of heap size.
This is where the memory-model and virtual-memory layers add value. A barrier is only correct if its memory ordering is right: the collector marks objects while the application changes references, and without the right ordering (and the SATB or load-barrier discipline) a live object could be missed and freed. The collector also relies on pages: it relocates a whole page, then returns the virtual address range and its physical memory after all references are fixed. Earlier non-generational ZGC mapped each heap page at several virtual addresses, one per color, so that a pointer of any color resolved to the same memory. Generational ZGC (JEP 439) replaced this with explicit code in the barriers, which makes the memory use easier to measure and removes the heap size limit of 16 TB. It adds store barriers that maintain the remembered set from old to young objects and take part in marking.
Finally, concurrent collectors need resources. Background threads use CPU and compete with the application. The program must not allocate faster than the collector can free: if it does, ZGC stalls the allocating thread (an allocation stall) and G1 falls into a full collection. Therefore a concurrent collector needs spare heap (commonly the heap should be two to three times the live data) and spare cores.

example: A service has a 32 GB heap with 12 GB of live data. It allocates about 1 GB per second. We compare collectors by what happens in a minute.
Generational view. Eden is 3 GB, so a young collection starts every 3 seconds. Suppose 2% of eden survives: 60 MB. With several GC threads copying at around 0.5 GB per second each, say 4 threads at 2 GB/s, copying takes 30 ms, plus a few milliseconds to scan roots and dirty cards. So about 35 ms per young pause, 20 pauses per minute. Without generations, each collection would mark and sweep the 12 GB of live data, taking seconds.
Old generation. The service keeps 12 GB of live data and slowly promotes more. Say 5 MB per second are promoted (about 300 MB per minute). With the old generation at 20 GB capacity and 12 GB used, there is room for 8 GB, about 27 minutes of promotion. Before it fills, G1 starts concurrent marking (when occupancy reaches the initiating threshold, 45% of the heap by default) and then mixed collections. Marking 12 GB with 4 concurrent threads at about 1 GB/s each takes around 3 seconds, in the background. If instead the service falls behind and G1 does a full collection, it must mark and compact 12 GB with maybe 8 threads: several seconds of stop-the-world pause, enough to miss a heartbeat. This is the failure that tuning tries to prevent.
ZGC view. The pauses are under a millisecond, so the 35 ms young pauses disappear. The cost goes elsewhere: the load barrier adds a few percent to throughput, background threads use several cores during a cycle, and the cycle must finish before the heap fills. Free space is 20 GB and the allocation rate is 1 GB/s, so the collector has about 20 seconds of headroom, much more than the roughly 3 to 6 seconds a cycle needs. If the allocation rate rose to 6 GB/s, headroom would drop to about 3 seconds and allocation stalls would appear, so you add heap or cores or reduce allocation.
What would you choose? For a throughput job (a Spark batch executor), pauses of 35 ms every 3 seconds are irrelevant and the lower CPU cost of G1 or Parallel is better. For a low-latency API or a Kafka broker where a 200 ms pause hurts, ZGC or a tuned G1 with a 20 ms pause goal is better.
intuition: Clean the kitchen while people are still cooking in it, and tidy the counters that get messy fastest most often.
Most of the mess comes from things used once and thrown away, so a quick wipe of the busy counters removes nearly all of it. The rest is old, slow-moving clutter that can be sorted gradually, in the background, as long as every cook follows two rules: put a note when you move a pot (the write barrier), and look at the note when you take one (the load barrier). The design is natural because it moves cost from rare, long pauses to small, regular taxes on every memory access.
mistakes: People often think a bigger heap means longer pauses. In fact this is true for stop-the-world collectors that scan or compact everything, but not for ZGC or Shenandoah, whose pauses do not depend on heap size. For G1, young pauses depend on survivors and the pause goal, not on the heap size.
People often think concurrent means free. In fact barriers slow every reference access (a few percent in throughput), background threads take CPU, and the collector needs spare heap. A concurrent collector on a machine with no spare cores, or on a heap that is 90% live data, performs worse than a well-tuned stop-the-world one.
People often think "no pauses" means no GC problems. In fact if allocation outpaces collection you get allocation stalls (ZGC) or concurrent mode failure and full collections (G1), which are worse than ordinary pauses. A high allocation rate is the main driver of GC cost in all collectors.
People often think the GC covers all the memory of the process. In fact off-heap memory (Spark Tungsten buffers, Netty direct buffers, memory-mapped files, native libraries) is outside the collector's view, so a process can use far more memory than its heap size, and container limits can kill it even though the heap looks fine.
People often think the default collector is the same everywhere. In fact the JVM selects G1 on server-class machines, but picks Serial on small ones (one CPU or under about 1.8 GB of memory), and a proposal (JEP 523) would make G1 the default everywhere. Containers with small limits can quietly run Serial, so check with -Xlog:gc or jcmd.
friction: The first cost is overhead. Write and load barriers add instructions to the most frequent operations in a program. G1's barriers and remembered sets cost a few percent of throughput and 10 to 20% of memory for its bookkeeping; ZGC's load barriers cost a few percent more, and ZGC does not use compressed object pointers, so object references take 8 bytes rather than 4 and the heap holds fewer objects. Concurrent threads use CPU, which on a busy machine competes with the application.
Tuning remains workload-specific. G1 needs a pause goal that is realistic, an occupancy threshold that starts marking early enough, and enough headroom to avoid evacuation failure ("to-space exhausted"). Humongous objects (more than half a region, such as large arrays) are allocated directly into old regions and can fragment the heap. ZGC has few knobs, but needs enough heap and cores; the main control is the heap size.
Allocation rate is the hidden driver. Services that create a lot of short-lived garbage per request (boxing, string concatenation, JSON, protobuf copies) pay in frequent young collections and in barrier pressure. Reducing garbage (object reuse, primitive collections, off-heap buffers, avoiding copies) often beats tuning the collector, though it makes code less natural.
Finally, the pause is only one of several latency sources. Time to a safepoint (waiting for all threads to reach a stopping point), transparent huge page compaction, swapping, container CPU throttling and noisy neighbours all produce stalls that look like GC pauses. Memory also is a constraint: the total of heap, metaspace, thread stacks, direct buffers and code cache must fit in the container. Large heaps are still slow to start and to take heap dumps from, and a very large old generation takes long to mark whatever the collector.
practice: Choose the collector by the requirement, then measure. For batch and throughput workloads (Spark executors, batch ETL), Parallel or G1 are good: the pause is not important and the lowest CPU overhead counts. For latency-sensitive services, brokers and search nodes, start with G1 and a pause goal near the real SLO, and move to generational ZGC (JDK 21 and later; the default mode from JDK 23) if p99 pauses still hurt and you have spare cores and heap. Kafka's default scripts use G1 with a 20 ms pause goal and a lower occupancy threshold for marking (35%), which is a good starting point for brokers.
Always turn on GC logging (-Xlog:gc*:file=gc.log with rotation) and read it. Look at pause times, frequency, heap after collection (the real live set), allocation rate and promotion rate. Size the heap at roughly two to three times the live set for concurrent collectors. Set -Xms equal to -Xmx on servers to avoid resizing, and use -XX:MaxRAMPercentage in containers, leaving room for off-heap memory (Spark executors: heap plus memoryOverhead; Elasticsearch: heap at most half of RAM and below about 31 GB to keep compressed pointers).
Reduce allocation where it is cheap: reuse buffers, avoid intermediate objects in hot paths, use primitive arrays and columnar structures, and in Spark prefer built-in functions and the Tungsten/Photon off-heap engines over UDFs that create objects per row. Watch for the signs of trouble: promotion rates that rise steadily (a leak or oversized caches), full collections, "to-space exhausted" in G1 logs, allocation stalls in ZGC, and long time-to-safepoint.
Test with realistic load and heap contents, because a collector behaves differently on an empty heap. Use the same JDK version in test and production, since GC behavior changes between releases (G1 and ZGC improve with each one). Make sure the application can survive a rare long pause: set timeouts and session lifetimes longer than the worst pause you see.
tradeoffs: Choose Parallel GC when the job is a batch where total throughput matters and pauses of seconds are acceptable, the heap is a few GB to tens of GB, and you want the lowest overhead. Choose G1 as the general default for services with heaps of 4 GB to a few hundred GB and pause goals of 20 to 200 ms. Choose ZGC when p99 latency must stay near a millisecond on large heaps (tens of GB to terabytes) and you can pay a few percent of throughput, extra cores and spare heap. You give up throughput and memory for lower latency with ZGC; you give up predictability of pauses with Parallel.
Choose generational ZGC over the non-generational one (which no longer exists in JDK 24 and later) for almost every workload: in the Cassandra benchmark reported in the JEP, it needed about a quarter of the heap and gave about four times the throughput of the non-generational mode. Choose Shenandoah when you use a distribution that ships it (Red Hat and others) and want pause times independent of heap with a different barrier design; the practical difference from ZGC is small compared with the effect of your allocation rate.
Choose a smaller heap with off-heap or native structures when a huge on-heap cache creates long marking and promotion work; choose a larger heap when the live set is truly large and the collector is concurrent. Off-heap data avoids GC cost but moves memory management to your code and the container limit.
Choose to reduce allocation instead of tuning flags when GC accounts for more than about 10% of CPU or when pauses follow bursts of allocation. Choose to tune flags (pause goal, occupancy threshold, region size) after the allocation profile is understood. You pay in code complexity for the first, and in fragility across workloads and versions for the second.

@@ scattergather
value: Scatter–gather answers a query over data that is split across many machines. A coordinator (also called a broker or root) sends the query, or a piece of it, to every machine that may hold relevant data at the same time (scatter), waits for their partial answers, and combines them into one answer (gather). Each machine works on its own slice, so the total work is done in parallel, and the user sees the time of the slowest slice plus the cost of combining.
Data is split because it does not fit on one machine, or because one machine cannot scan it fast enough. A search index of 2 TB split into 20 shards of 100 GB lets 20 machines each search a small part at once, and a query that would take 2 seconds on one machine can take about 100 ms. When you cannot tell in advance which shard holds the answer (a text search, a filter on a column that is not the shard key, a top-k over everything), asking all of them is the only complete answer. Scatter–gather is the way search engines, OLAP stores, and sharded SQL and NoSQL systems do it: Elasticsearch and OpenSearch, Solr, Apache Pinot, Druid and ClickHouse clusters, Vitess and Citus, and Google's own web search.
For the layer above (search engines, real-time analytics), this technique is the query path. The layers below decide how it behaves. TCP carries the fan-out requests and the responses over many connections, and the burst of simultaneous responses that arrives at the coordinator can overflow its network buffers (the incast problem). Queueing theory (and the tail-at-scale analysis) explains the central cost: the query is as slow as the slowest of its parts, so a rare slow response at one machine becomes a common slow query when the fan-out is large.
terms: Shard — one slice of the data, held by one machine (and usually replicated on others).
Coordinator / broker — the node that receives the user's query, scatters it, and gathers and merges the answers.
Fan-out — the number of nodes one query is sent to.
Partial result — the answer a shard produces from its own data: a top-k list, partial sums, a sketch.
Pruning — skipping shards that cannot contain results, using the partition key, the time range or per-shard statistics.
Tail latency — the slow end of the latency distribution, such as the 99th percentile.
Hedged request — a second copy of a request sent to another replica when the first is slow, using the first answer that arrives.
Replica selection — choosing which copy of each shard to ask, for example by the shortest queue.
history: The pattern is old. Parallel database systems of the 1980s (Teradata, Gamma) split tables across nodes and had each node run its part of a query, with the results combined by one node. Google's web search of the early 2000s put the index in many shards, with a root server that sent each query to all of them and merged the best results, and Google's MapReduce paper (2004) described the same shape for batch computing: the map phase is the scatter and the reduce phase is the gather. Dremel (Melnik and others, VLDB 2010; the base of BigQuery) generalized it into a serving tree: a root sends the query to intermediate servers, which send to leaves, and the partial aggregates are merged on the way back, so no single node merges thousands of answers.
Open-source search and analytics followed: Lucene-based Solr (an Apache project from 2006), Elasticsearch (2010; Shay Banon), Druid (2011), and Apache Pinot (LinkedIn, open-sourced in 2015) all use a broker that scatters to servers holding segments. The weaknesses were understood slowly. Vasudevan and others (SIGCOMM 2009) described TCP incast, where many servers answering at once cause packet loss and timeouts at the receiver. Dean and Barroso's "The Tail at Scale" (CACM, 2013) showed with numbers why large fan-out makes tail latency dominant and described hedged and tied requests. Suresh and others (NSDI 2015) proposed C3, a replica selection scheme that cut tail latency in Cassandra. Today these techniques, such as adaptive replica selection and shard-level caching, are default parts of production systems.
how: A query goes through four steps: route, scatter, execute, gather. The first step is routing and pruning. The coordinator uses metadata to find the shards that can matter. If the query has an equality condition on the shard key, only one shard is needed and there is no scatter at all. If the query has a time range and the data is partitioned by time, only those partitions are used. Many systems also keep per-shard or per-segment statistics (minimum and maximum of a column, Bloom filters) and skip shards that cannot match; Elasticsearch has a "can_match" pre-filter phase for this. Every shard removed here is work and tail risk avoided, so pruning is the most effective tuning.
Next the coordinator scatters. It sends the sub-query to one replica of each remaining shard, concurrently, using non-blocking network calls over TCP connections it already holds, so no thread waits for a single shard (this is where an event loop helps). The choice of replica matters: round robin is simple, but adaptive replica selection uses the recent response time and queue length of each node and sends the request to the least loaded copy. Each request carries a timeout or deadline.
Each shard then executes locally on its own data and returns a partial result that is as small as possible. For a search, the shard finds its top k documents by score and returns only their IDs and scores. For an aggregation, it returns partial aggregates: sums and counts (an average is computed from the sum of sums and the sum of counts, never from an average of averages), minimum and maximum, counts per group, and sketches for things that cannot be combined exactly (HyperLogLog for distinct counts, t-digest or quantile sketches for percentiles). A shard does as much as possible before sending, because the network and the coordinator are the shared, scarce parts.
The gather step merges the partial results. For sorted lists, the coordinator uses a priority queue to take the best elements across S lists, in O(N log S) time for N elements. For group-by results, it merges hash tables by key and combines the partial aggregates. For top-k, it takes the global best k from the union. The coordinator may then do a second phase, such as the fetch step in Elasticsearch: after the query phase has identified the top 10 document IDs, it asks only the shards that own them for the stored fields. When group counts are large, a single coordinator becomes the bottleneck, so systems add intermediate merge levels, as in Dremel's tree.
Correctness needs care with top-k over aggregates. If each shard returns its local top k groups, the global top k may be wrong, because a group that is middling on every shard can be first globally. The fix is to fetch more than k from each shard (Elasticsearch's terms aggregation uses shard_size, by default 1.5 × size + 10) and to report an error bound, or to use two rounds, asking for the exact totals of candidate groups in a second step.
Finally the coordinator handles partial failure and slowness. It waits until all shards respond or the deadline passes. It can then fail the query, or return the partial result with a flag that says which shards did not answer (Elasticsearch reports shards failed and timed_out). To cut the tail, it can hedge: if a shard has not answered by the 95th percentile of its usual time, send the same request to another replica and use whichever answer arrives first. A variant, the tied request, sends to two replicas at once and each tells the other to cancel when it starts. The tail-at-scale paper reported that in a benchmark reading 1,000 keys spread over 100 servers, hedging after a 10 ms delay cut the 99.9th percentile of the whole operation from 1,800 ms to 74 ms with only 2% extra requests.
Queueing theory shows why scatter–gather scales differently from routing by key. Every query reaches every shard, so each shard sees the full query rate λ whatever the number of shards. If a shard needs s seconds of work per query, its utilization is ρ = λ × s. In the simplest queueing model (M/M/1) the mean time in the system is s ÷ (1 − ρ), so at ρ = 0.5 the shard is twice as slow as when idle, and at ρ = 0.9 it is ten times slower. Because the query waits for the worst shard, one shard at high utilization hurts every query. Capacity is therefore added with replicas, which divide λ among several copies of each shard, while shards are added only to cut the work per query.

example: Take an index split into 20 shards. For one shard, the response time has a median of 10 ms and a 99th percentile of 100 ms (1% of requests are slow, for example because of a garbage-collection pause or a busy disk). A query needs all 20 shards.
The query finishes when the slowest shard finishes. If each shard is slower than 100 ms with probability 1%, the chance that at least one of 20 is slow is 1 − 0.99²⁰ = 18%. So 18% of queries are at least as slow as a single shard's 99th percentile. Turn it around: the median query waits for the slowest of 20, so it takes as long as a shard's 0.5^(1/20) = 96.6th percentile response. The query's 99th percentile equals the shard's 0.99^(1/20) = 99.95th percentile. With 100 shards, 1 − 0.99¹⁰⁰ = 63% of queries are slower than the shard's 99th percentile, exactly the example in "The Tail at Scale".
Now hedge. Suppose the shard's 95th percentile is 30 ms. After 30 ms without an answer, send the request to the other replica. About 5% of shard requests get a duplicate, so the load rises by about 5%. A hedged request is slow only if both copies are slow, with probability about 1% × 1% = 0.01% (if slowness is independent). The chance that a query with 20 shards sees at least one slow one falls from 18% to about 1 − 0.9999²⁰ = 0.2%. This only works if slow responses are caused by something local to one replica, such as a GC pause, and not by the request itself.
Next, correctness of top-k. We ask for the top 1 term over 3 shards. Shard 1 counts: a = 10, c = 9. Shard 2: b = 10, c = 9. Shard 3: a = 1. If each shard returns only its top 1 term, the coordinator sees a = 10 + 1, b = 10, and chooses a = 11. But the true totals are a = 11, b = 10, c = 18. The right answer, c, was second on both shards and was never sent. If every shard returns its top 2, the coordinator sees c = 18 and gets it right. This is why systems over-fetch: the shard sends more than k candidates.
Finally, deep pagination. A search with from = 10,000 and size = 10 over 20 shards needs each shard to return its top 10,010 results, since the global rank 10,000 could come from any shard. The coordinator receives 20 × 10,010 ≈ 200,000 entries to produce 10. This is why Elasticsearch limits from + size to 10,000 by default and offers search_after instead.
intuition: Ask every branch office the same question, then add up their answers; the report is ready when the slowest branch replies.
The design is natural when no single office knows where the answer is. The work divides cleanly (each office searches its own files), and the combining step is small if every office summarizes before replying. The cost is that you must wait for everybody, so the weakest office sets the pace, and the more offices you ask, the more likely one of them is having a bad day.
mistakes: People often think adding shards always makes queries faster. In fact it makes each shard's work smaller but adds fan-out, so more of the latency comes from the slowest shard, the merge, and the network. Past some point more shards make the median slower and the tail much worse. It also does not raise query throughput: every query still reaches every shard, so each shard receives the full query rate.
People often think the tail is rare, so it can be ignored. In fact with fan-out the tail becomes the typical case. If one shard in a hundred is slow, most queries over 100 shards are slow. Look at the p99 of the query, and at the slowest shard of each query, not at the average per shard.
People often think each shard can return its local top k and the merge is exact. In fact this is true for ranking of documents by a score that is local to each document, but not for top groups by an aggregate (the example above). The shard must return more than k, or the system must run a second round.
People often think averages and distinct counts can be merged from partial answers. In fact an average of averages is wrong unless weighted by counts, and a distinct count cannot be merged from per-shard distinct counts because the same value may appear on several shards. Use sums and counts, or mergeable sketches such as HyperLogLog.
People often think a partial result is the same as an error. In fact many systems let you choose: fail fast, or return what arrived by the deadline with a flag. For search and dashboards, a slightly incomplete answer in 100 ms is often better than a perfect one in 3 seconds, as long as the user can see that it is incomplete.
friction: Tail latency is the main limit. The expected latency is the maximum of many random variables, and the shard-level p99 becomes the median. Garbage-collection pauses, compactions, noisy neighbors, cache misses and background merges all create slow responses on one shard at a time, and scatter–gather turns each of these into slow queries. Hedging reduces the tail, but adds load, and it does not help when all replicas are slow because the cluster is saturated, which is when it is most tempting to use it.
Throughput does not scale with shards. Each query costs a fixed amount at each shard (parsing, opening readers, scheduling) plus a share of the data work, so with S shards the cluster does about S times more fixed work per query. Many small shards waste CPU and memory; the common advice for Elasticsearch is shards of tens of gigabytes, not hundreds of tiny ones. To scale throughput you add replicas, which spread queries over more copies, not shards.
The coordinator and the network are shared bottlenecks. Merging S lists of large size uses memory and CPU on one node. Many shards answering at the same moment send a burst of data to one network port, which can cause packet loss and TCP retransmission timeouts (incast), so a query that should take 20 ms takes 200 ms or more. Mitigations are to limit response sizes, add intermediate merge layers, and cap concurrency per query.
Last, semantics are tricky. Results come from replicas at different points in time, so the same query can give slightly different answers. Relevance scores that depend on global statistics (IDF in text search) differ per shard, unless a pre-phase gathers global statistics (Elasticsearch's dfs_query_then_fetch). Deep pagination, sorting by non-indexed fields, and high-cardinality group-by are expensive, because each shard must return large lists.
practice: Prune before you fan out. Partition by the field most queries filter on (usually time), and make sure queries carry that filter, so only a few shards are touched. Where a natural key exists (tenant, user), route by it, so a query goes to one shard and does not scatter at all (Elasticsearch's routing parameter, Pinot's partition-aware routing). Check how many shards each query touches; a fan-out that grows with the data is a design problem.
Size shards sensibly: large enough that fixed per-shard cost is small relative to useful work (in Elasticsearch, tens of GB per shard; in Pinot and Druid, segments of hundreds of MB to a few GB), and not so large that one slow shard takes a long time. Keep the number of shards per node reasonable, and use replicas to raise throughput and to give the coordinator a choice of copies.
Set deadlines and decide the partial-result policy. Use per-shard timeouts shorter than the user's timeout, enable adaptive replica selection (default in recent Elasticsearch), and use hedging only for idempotent, cheap-to-repeat reads, with a delay near the p95 and a cap on the extra load. Return flags for incomplete results, and alert on shard failures and timeouts.
Keep the merge cheap. Ask for less: fields only when needed, a bounded size, search_after instead of deep from + size, approximate aggregations (cardinality sketches, percentiles) when exactness is not needed, and pre-aggregated rollups for dashboards. Measure the right things: per-shard latency distribution, the maximum shard latency per query, merge time at the coordinator, the number of shards touched, and queue sizes. The slowest shard in the slowest queries tells you where to look.
tradeoffs: Choose scatter–gather when queries cannot be routed by the shard key (text search, ad hoc filters, global top-k), the data is too large for one node, and the answer can be assembled from small partial results. Choose single-shard routing (partition by the query key) when most queries have a key such as a user or tenant: there is no fan-out, throughput scales linearly with shards, and latency is that of one node. You give up flexibility of queries when you partition by one key; you give up tail latency and throughput scaling with scatter–gather.
Choose fewer, larger shards when queries are many and mostly small, because the fixed per-shard cost and the fan-out dominate. Choose more, smaller shards when single queries are heavy scans that benefit from parallelism, the cluster is large, and you can accept lower throughput. The deciding numbers are the per-shard fixed cost (often a few milliseconds of CPU) against the per-shard data work, and the fan-out against the p99 of a single shard.
Choose hedged or tied requests when tail latency is the problem, reads are idempotent, replicas fail independently, and there is spare capacity (a few percent). Choose to reduce shard-level variance (fix GC, isolate compactions, cap query cost) when the cluster is near saturation, since hedging then makes things worse. You pay with extra load in the first case, and with engineering effort in the second.
Choose a single coordinator for modest fan-out (tens of shards, small partials) and a merge tree with intermediate aggregators for hundreds or thousands of leaves or large group-by results (as in Dremel and Pinot's multi-stage engine). Choose exact answers when a user checks totals, and sketches or approximate top-k when speed matters more than the last digits, with the error bound shown.
interview: Why does a larger fan-out hurt tail latency? Give the arithmetic. || The query waits for the slowest shard. If a shard is slow with probability p, a query over n shards is slow with probability 1 − (1 − p)ⁿ. For p = 1% and n = 100 it is 63%. So the shard-level p99 becomes about the query's median, and variance at any one node is multiplied by the fan-out.
How do hedged requests work, and what are their risks? || After a delay near the shard's p95, send a duplicate to another replica and take the first response, optionally cancelling the other. In a published benchmark this cut the p99.9 from 1,800 ms to 74 ms with 2% extra load. Risks: extra load that can tip an overloaded cluster over, non-idempotent requests, and correlated slowness, where all replicas are slow for the same reason.
A user asks for top 10 terms by count across 50 shards. Is merging each shard's top 10 enough? || No. A term that is mid-ranked on every shard can be the global winner. Each shard must return more than 10 candidates (Elasticsearch uses 1.5 × size + 10), and the system reports an error bound; for exactness a second round asks all shards for the exact counts of the candidates.
You add 4 more shards to a search cluster to speed it up, and p99 gets worse. Why? || Fan-out rose, so the slowest-of-n effect grew; each shard has more fixed overhead per query, which raises total CPU; the coordinator merges more lists; and each shard still receives every query, so throughput did not increase. If load is the issue, add replicas; if the data is the issue, reduce shards touched with pruning.
How would you design the query path of a time-series analytics store with 10,000 segments? || Partition and prune by time and, if present, a tenant key, keep per-segment min/max and Bloom filters, route using a broker that maps segments to servers, send one request per server (not per segment) with all its segments, merge on server before sending, use a tree of aggregators if large, set deadlines, hedge slow servers, and expose partial results with flags.
Why is deep pagination expensive in a scatter–gather system, and what do you do? || To find the global result at rank from + size, each shard must produce its top from + size items, and the coordinator merges S × (from + size) entries. Cost and memory grow linearly with depth and the number of shards. Use search_after (cursor on the last sort key), a point-in-time view, or limit depth.

@@ vectorized
value: Vectorized execution is a way for a database engine to run a query by passing batches of values (vectors of about a thousand values from one column) through the operators, instead of passing one row at a time. Each operator does its job in a tight loop over a vector: compare a thousand quantities with a constant, multiply a thousand prices by a thousand discounts, add them to a running sum. The cost of calling the operator, looking up types and moving to the next step is paid once per thousand values, not once per value.
This answers a specific problem. The classic engine design, the Volcano iterator model (every operator has a next() method that returns one row), is simple, but on modern CPUs it is slow for analytics. Each row passes through several virtual function calls, the CPU cannot keep its pipeline full, branches are hard to predict, and the work done per value is tiny compared with the overhead of getting to it. Measurements on row-at-a-time systems in the early 2000s showed the CPU doing real work in only a small part of the cycles. Vectorized engines run the same queries many times faster on the same hardware, often 10 to 100 times faster than a row-at-a-time interpreter on scans, filters and aggregations.
This is the execution core of modern analytical databases and lakehouse engines: DuckDB, ClickHouse, Databricks Photon, Meta's Velox, Snowflake, Vectorwise, and Spark's vectorized Parquet reader. For the layer above (OLAP systems and distributed SQL engines), it makes each core process many millions of rows per second, so fewer machines are needed for the same scan. The layers below make it work. SIMD instructions (SSE, AVX, NEON) apply one operation to 4, 8 or 16 values at once, and tight loops over arrays let the compiler use them. Cache lines and locality say that vectors should be small enough to stay in the L1 or L2 cache, and contiguous so that the hardware prefetcher works. Branch prediction explains why the loops should avoid data-dependent branches: selection vectors turn unpredictable if-statements into arithmetic.
terms: Vector (batch) — a small fixed-size array of values from one column, typically 1,000 to 4,000 values, that is passed between operators.
Selection vector — an array of the positions of the rows that are still alive after a filter, so later operators touch only those rows.
Primitive — a small, pre-compiled function that does one simple thing over a whole vector (for example, "add two columns" or "select values below a constant").
Volcano model — the older design in which each operator returns one row per next() call.
Pipeline breaker — an operator that must see all its input before it can output anything (sort, hash-table build), which ends a pipeline of streaming operators.
SIMD (single instruction, multiple data) — a CPU instruction that applies the same operation to several values in one register, for example 8 32-bit integers in a 256-bit AVX2 register.
Interpretation overhead — the CPU time spent deciding what to do (dispatching calls, checking types) instead of doing it.
Late materialization — keeping only positions or the needed columns as long as possible, and fetching other columns after filters have removed most rows.
history: The Volcano model, described by Goetz Graefe in 1994, made query engines modular: any operator can be plugged into any other through the same next() interface. It was designed when disk was the bottleneck and a function call per row was cheap in comparison. By the late 1990s the bottleneck had moved. CPUs had deep pipelines and caches, and researchers at CWI Amsterdam (Peter Boncz and Martin Kersten) found that database systems used only a small part of the CPU's capacity. Their column-store MonetDB processed one whole column at a time, which removed the per-row overhead but wrote every intermediate result, a full column, to memory, which then became the limit.
In 2005, Boncz, Zukowski and Nes published "MonetDB/X100: Hyper-Pipelining Query Execution" (CIDR). The idea was to take a middle path: process vectors of about a thousand values, small enough to stay in the CPU cache, large enough to amortize the interpretation cost. The prototype became the commercial system Vectorwise (2008 on). Other column stores took blocks of values at a time as well (C-Store and Vertica, Sybase IQ), and Snowflake's 2016 paper describes a columnar, vectorized engine.
Open source and cloud engines then adopted the design. ClickHouse (Yandex, open-sourced 2016) processes blocks of tens of thousands of rows. DuckDB (Raasveldt and Mühleisen, 2019) brought a vectorized engine into an embedded library, with vectors of 2,048 values. Apache Arrow (2016) gave engines a common columnar memory format. Databricks built Photon, a C++ vectorized engine, replacing Spark's JVM code generation for much of the work (SIGMOD 2022), and Meta published Velox (VLDB 2022) as a shared execution library. In 2018, Kersten and others compared vectorized and compiled engines in a careful study ("Everything You Always Wanted to Know About Compiled and Vectorized Queries But Were Afraid to Ask") and found them close in speed, with different strengths, which is why both approaches remain in use.
how: A vectorized engine builds a plan of operators in the usual way, but the interface changes: next() returns a batch of up to a few thousand rows, organized by column. Each column in a batch is a contiguous array of values (with a null bitmap), and the batch also carries a selection vector, a list of the row positions that are still valid. A scan operator reads a chunk of a column file, decompresses it into vectors, and passes it up. The operator above calls a pre-compiled primitive on each vector and passes the result on.
Take the expression price × (1 − discount) with the filter quantity < 24. The filter runs a primitive "select less-than, column and constant" over the quantity vector. It writes into the selection vector the positions of the values that pass: k = 0; for i in 0 … n−1: sel[k] = i; k += (qty[i] < 24). The loop has no if statement. It always writes the index, and only advances k when the condition is true. This is the branch-prediction layer's contribution: a branch that is true for 50% of rows at random is mispredicted about half the time, and each misprediction costs 15 to 20 cycles, which would be more than the whole comparison. The arithmetic version costs about 1 to 2 cycles per value whatever the selectivity. The next primitive, "1 − discount", runs over the discount vector, but only for the positions in the selection vector, then "price × that", then "sum into the accumulator".
Each primitive is a tiny loop over arrays of one type, with no function call inside the loop, no type checks, and no dependence between iterations. This is the best case for a compiler, which can unroll it and use SIMD: with AVX2, one instruction compares 8 32-bit integers, and AVX-512 handles 16. The interpretation cost (look up the primitive for these input types, call it) is paid once per vector, so about 1 / 1000 of a cycle per value, and the useful work becomes 1 to a few cycles per value. This is where the SIMD layer pays off. Where data-dependent selection prevents full SIMD use, modern instruction sets help with gather, compress and mask instructions.
Vector size is a compromise. One vector of 1,024 8-byte values is 8 KB. An expression with four intermediate vectors needs about 32 to 40 KB, which fits in the L1 data cache (32 to 48 KB) or at least in L2 (1 to 2 MB). That is the contribution of the cache layer: intermediate results do not go to main memory, so the engine is limited by the speed of the CPU instead of memory bandwidth. Vectors that are too small (10 values) bring back the call overhead. Vectors that are too large (a million values) make intermediate results spill out of cache, which is the problem of MonetDB's column-at-a-time design. The Kersten study found the best sizes around 1,000 to a few thousand values, and the optimum is flat.
Pipeline breakers need more care. For a hash aggregation or hash join build, the engine hashes a whole vector of keys with a SIMD-friendly primitive, then looks up all the buckets in a loop. Splitting these steps lets the CPU issue many independent memory loads at once and overlap their cache misses (or prefetch explicitly), which is a significant advantage over tuple-at-a-time code that stalls on every miss. Collisions are resolved with selection vectors that carry the unresolved rows to the next round.
Engines add more tricks around this core. Compressed vectors (constant, dictionary, run-length) let primitives work on a single value or on dictionary codes without expanding. Operators can adapt per batch: if a batch has no nulls, use the fast path. And because a batch is a plain array of fixed-size values, it is easy to exchange with other systems through Arrow, and to call from Python or JVM code without per-row conversion.
Parallelism fits the same structure. Each worker thread takes a chunk of input (a Parquet row group, or a few thousand rows called a morsel), runs the whole pipeline of operators on it vector by vector, and builds its own local hash table for an aggregation; when the input ends, the local tables are merged. Work is handed out in small pieces, so a fast thread simply takes more of them and the load balances itself, in the same spirit as work stealing. The vector is thus the unit of interpretation, of cache use and of scheduling at the same time.

example: Run SELECT sum(price × (1 − discount)) FROM lineitem WHERE quantity < 24 over 100 million rows on one core at 3 GHz. Selectivity is about 46% (quantity is between 1 and 50).
Row at a time. For each row the engine calls next() down a chain of three operators, evaluates the filter by walking an expression tree (one virtual call per node, perhaps five calls), then the projection (more calls), then the aggregate. Assume this costs about 150 cycles per row, which is realistic for an interpreted engine that has several virtual calls, poorly predicted branches and values moved through memory. That is 50 ns per row, so 100 million rows take 5 seconds.
Vectorized. The engine processes vectors of 1,024 rows. The filter primitive costs about 1.5 cycles per value, the two arithmetic primitives about 1 cycle per selected value (46 million values), and the sum about 1 cycle per value. Together this is roughly 1.5 + 0.46 × (1 + 1 + 1) ≈ 3 cycles per input row, plus about 100 cycles per vector for the call chain, which is 0.1 cycles per row. So about 3.1 cycles per row, 1 ns, and 100 million rows take about 0.1 s of compute. That is 50 times faster than the row-at-a-time estimate.
Now check memory. The query reads three 8-byte columns: 100 million × 3 × 8 B = 2.4 GB. A single core can stream roughly 10 GB/s from memory, so reading takes about 0.24 s. The engine is therefore now bound by memory bandwidth, not by the CPU. With compressed columns (say 3 to 4 times smaller) and with multiple cores, the scan gets faster again until the machine's total memory bandwidth is reached. This is the usual outcome of vectorization: the CPU stops being the problem, and the data layout and I/O become the problem.
Finally the cache argument. With vectors of 1,024 values, the three input vectors (24 KB) and two intermediate vectors (16 KB) total 40 KB, which fits the L1 cache of a modern core (48 KB) or at least L2. With column-at-a-time processing (MonetDB style), the intermediate column has 100 million values (800 MB), so every step writes it to memory and the next step reads it back, which doubles or triples the memory traffic. The vector size is chosen to avoid this.
intuition: Process a whole tray of cups at once instead of carrying them one by one.
Walking to the kitchen once per cup wastes most of the effort on the walk. A tray costs the same walk and carries a thousand cups. The tray must not be so big that you cannot carry it (it must stay in cache), and the cups on it must be alike so that one motion works for all (same type, contiguous in memory, so SIMD can handle several at a time). The design is natural because modern CPUs are fast at simple repeated work and slow at deciding what to do next, so the engine decides once per batch.
mistakes: People often think vectorized execution is the same as using SIMD instructions. In fact SIMD is one benefit. Most of the gain comes from removing per-row interpretation overhead and keeping data in cache. A vectorized engine without any explicit SIMD, only with loops the compiler can optimize, is still much faster than a row-at-a-time one.
People often think larger batches are always better. In fact beyond a few thousand values the intermediate vectors no longer fit in cache, and performance falls. The sweet spot (about 1,000 to 4,000 values) is flat and depends on the cache size, number of columns and expression depth.
People often think vectorized and compiled engines are different in kind and one must win. In fact the VLDB 2018 comparison found them close: compiled code is better for computation-heavy pipelines with many fused operators, while vectorized code can be better for memory-bound steps such as hash joins, where processing a batch lets the CPU overlap many cache misses. Many systems mix both.
People often think a vectorized engine makes any query fast. In fact it speeds up scans, filters, expression evaluation and aggregation. Work that cannot be expressed as loops over arrays, such as user-defined functions called per row, deeply nested data, or queries dominated by small result sets and index lookups, gains little. A row-based Python UDF in a vectorized engine pulls the engine back to row-at-a-time speed.
People often think vectors are copies of rows in a column format. In fact the point is that data stays columnar from storage to the CPU: the engine reads only the needed columns and never assembles rows until the end (late materialization). If rows are rebuilt early, much of the gain is lost.
friction: The model has costs of its own. Intermediate vectors must be materialized between primitives, so a complex expression such as a × b + c × d − e reads and writes several temporary vectors, adding traffic compared with compiled code that keeps one value in a register. If vectors do not fit in cache the benefit shrinks. Engines reduce this by fusing common sequences into a single primitive (for example, "multiply and add") or by choosing smaller vectors for wide queries.
Selection vectors and nulls add complexity. Every primitive must handle the case where only some positions are valid and where values may be null. Branch-free selection helps, but with very low selectivity (1 in 1,000) it does extra work per row, and with very high selectivity it is wasteful to keep a selection vector at all, so engines pick between selection vectors, bitmaps and physically compacting the vectors. Variable-length data such as strings is harder than fixed-width numbers: values are not the same size, so SIMD helps less and memory access is irregular.
Row-by-row logic breaks the model. UDFs written in Python or Java, complex predicates with subqueries per row, and stateful operators force the engine to leave the vector loop. The common fix is to give the UDF a batch (Arrow-based pandas UDFs in Spark), but the programmer must write the function to work on columns. Debugging is also different: a bug appears in a batch of thousands of values, and stack traces show primitives, not rows.
Finally, building a fast vectorized engine is a large engineering job. Each primitive is needed for each type and each combination (with or without selection vector, with or without nulls), which is a lot of code, often generated by templates or macros. Performance depends on compiler quality, CPU features (AVX-512 may lower the clock rate on some CPUs), and the data distribution. And the gain stops at the next bottleneck: I/O, decompression, network shuffles or memory bandwidth.
practice: Choose engines and formats that keep the pipeline columnar from disk to CPU. Store data as Parquet or ORC (or the engine's own format) with column pruning and statistics, so only the needed columns and row groups are read. In Spark, make sure the vectorized Parquet reader is on (it is by default, with batches of 4,096 rows), prefer built-in functions to UDFs, and on Databricks enable Photon for scan-heavy and aggregation-heavy workloads; Photon runs only the operators it supports and falls back to the JVM engine for the rest, so check the query plan for the fallbacks.
Avoid row-at-a-time code in the middle of a vectorized plan. Replace Python UDFs by SQL expressions or by Arrow-based vectorized UDFs, move string parsing and regular expressions to built-in functions, and keep column types simple (fixed-width numbers, dictionary-encoded strings) where you can. Use proper types: a string column of numbers or dates stops the engine from using fast numeric primitives.
When you evaluate or tune an engine, look at the right numbers: CPU cycles per row, cache misses, instructions per cycle, memory bandwidth in use. If a scan runs at 100 to 500 million rows per second per core, you are in the right range; if it is 5 million, something forces row-at-a-time processing. Compare query plans before and after changes, and look for operators that are not vectorized.
When building an engine, start with a small set of primitives for the common types, pick the vector size by experiment (1,024 or 2,048 is a good start), write selection with branch-free code, make operators work on whole vectors by contract, and test with different batch sizes, including 1 and a non-power-of-two, to find bugs in selection and null handling. Use Arrow as the exchange format when you need to connect with other systems.
tradeoffs: Choose a vectorized engine when the workload is analytical (scans, filters, aggregations, joins over many rows), data is stored by column, and you want good speed without a code generator and its compile latency. Choose a row-at-a-time (Volcano) or index-driven engine for OLTP, where a query touches a few rows and the batch would hold one or two rows; the overhead of building vectors is wasted there. You give up simple, flexible per-row code with vectors; you give up scan speed with rows.
Choose vectorized execution over compiled execution (whole-stage code generation) when you want fast start-up for short queries (no compile step of tens to hundreds of milliseconds), easier debugging and profiling (each primitive is an ordinary function), adaptivity per batch, and a native language engine that is easy to extend. Choose compiled execution when pipelines are long and computation-heavy, so keeping values in registers across many fused operators saves memory traffic, and queries run long enough to repay compilation. Many modern systems combine them: vectorized scans and hash tables, with compiled expressions.
Choose a smaller vector (512 to 1,024) for wide queries with many intermediate vectors or for machines with small caches, and a larger vector (2,048 to 4,096) for simple scans where per-vector overhead matters more. The curve is flat near the optimum, so do not tune before measuring. Choose selection vectors when selectivity is moderate to low and later operators are expensive; choose compaction (copying selected rows into a dense vector) when many operators follow and selectivity is very low.
Choose SIMD intrinsics or explicit kernels for hot primitives (filters, hashing, decoding) when profiling shows the compiler does not vectorize them; choose plain loops with compiler auto-vectorization elsewhere, for portability across x86 and ARM. You pay with maintenance and with hardware-specific code paths.
interview: Why is vector-at-a-time faster than tuple-at-a-time on the same hardware? || It amortizes the per-call overhead (virtual dispatch, type checks, branching to the next operator) over about a thousand values, leaves tight loops that the compiler can unroll and SIMD can accelerate, keeps intermediate data in L1 or L2 cache, and has predictable branches. Tuple-at-a-time spends most cycles on interpretation and mispredictions rather than useful work.
What is a selection vector, and why not just branch on each row? || It is an array of the positions that passed a filter, so later operators process only those rows. Building it with k += (cond) avoids a data-dependent branch. At about 50% selectivity a branch mispredicts about half the time at 15 to 20 cycles each, which can cost more than the rest of the work, while the branch-free loop costs a constant 1 to 2 cycles per value.
How do you pick the vector size? || It must be big enough that call overhead per value is negligible (hundreds of values) and small enough that the vectors used in an expression fit in L1 or L2 cache (a few thousand values at 8 bytes). Systems use 1,024 (X100), 2,048 (DuckDB), 4,096 (Spark's Parquet reader). Test sizes empirically; the optimum is flat.
Compare vectorized and compiled query execution. When does each win? || Compiled code fuses operators and keeps values in registers, so it wins on long computation-heavy pipelines, at the cost of compile latency and harder debugging. Vectorized code starts instantly, is easy to profile and extend, and can overlap memory misses across a batch in joins and aggregations. A 2018 study found them close, with each winning on some queries.
Why does a Python UDF slow down a Spark query that otherwise runs on a vectorized engine? || A row-based UDF forces the engine to leave the columnar batch loop: it converts data to rows, serializes to a Python process, calls the function per row, and converts back. This adds per-row overhead of microseconds, thousands of times the per-value cost of a primitive. Use built-in functions or Arrow-based vectorized UDFs that operate on whole columns.
How does vectorization help with hash joins, which are memory-bound? || The engine hashes a batch of keys at once, then probes the table in a loop. Many independent lookups are in flight, so the CPU overlaps cache misses (and software prefetching is easy). Tuple-at-a-time code stalls on each miss in turn. Collisions are handled by passing the unresolved positions on in a selection vector.
quiz: What three things does a vectorized engine pass between operators? || A batch of about a thousand values per column (contiguous arrays with null information), plus a selection vector listing the valid row positions. Operators call pre-compiled primitives over these arrays.
Why does branch-free selection (k += (x < c)) help? || It removes the data-dependent branch, so there are no mispredictions (15 to 20 cycles each at unpredictable selectivity), and the loop can be pipelined and vectorized, at a constant cost per value.
Why should the vector be small enough for the cache? || Intermediate results between primitives are written and read again. If the vectors fit in L1 or L2, these accesses are cheap. If they are as large as a column, every step goes through main memory and the engine becomes memory-bound.
If row-at-a-time takes 150 cycles per row and vectorized takes about 3 cycles per row, how long do 100 million rows take on a 3 GHz core in each case? || Row-at-a-time: 100M × 150 / 3 GHz = 5 s. Vectorized: 100M × 3 / 3 GHz = 0.1 s, so 50 times faster, until memory bandwidth (about 0.24 s for 2.4 GB at 10 GB/s) becomes the limit.
When would you choose a row-at-a-time engine over a vectorized one? || For OLTP-style workloads that read or update a few rows by key, where batches would contain one or two rows and building vectors is overhead; also for code dominated by per-row custom logic.

value: Whole-stage code generation is a technique in which a query engine writes, at run time, a small program that is specialized for one query, compiles it, and runs it. Instead of an interpreter that walks a tree of operators and calls each one for every row, the engine produces one tight loop that contains the filter, the projection and the partial aggregation of a whole pipeline of operators, fused together. The values of one row stay in CPU registers from the scan to the aggregate, and no function is called between the steps.
The reason is that general-purpose interpretation is expensive when the work per row is tiny. In the classic Volcano model, every operator has a next() method and a row passes through several virtual calls and is written to and read from memory at each step. The Databricks engineers who built Spark's version measured it: the generic engine needed about 15 nanoseconds per row to apply a simple filter, while the generated code needed about 1.1 nanoseconds, a 14-fold difference on the same hardware, and a hash join went from about 115 to about 4 nanoseconds per row. Code written by hand for exactly one query is faster than a general engine, and code generation lets the engine "write that code by hand" automatically for every query.
For the layer above (distributed SQL engines, MPP systems), this is how a CPU-bound operator pipeline gets close to hand-written speed: Spark SQL's Tungsten engine (since Spark 2.0), Thomas Neumann's HyPer and Umbra, Impala, PostgreSQL's JIT for expressions, Redshift's compiled segments, and Flink SQL. The layers below make it possible. JIT compilation (L3) turns the generated code into machine code while the program is running; in Spark this happens twice, first Janino compiles generated Java source to bytecode, then the JVM compiles hot bytecode to native code. Intermediate representations and SSA (L3) are what a code generator emits and an optimizer improves: HyPer emits LLVM IR, which the compiler optimizes with register allocation, inlining and constant propagation. CPU pipelining explains the payoff: straight-line code with few unpredictable branches and no indirect calls keeps the CPU's pipeline full.
terms: Volcano (iterator) model — the design in which each operator is an object with a next() method that returns one row to its parent.
Pipeline — a chain of operators through which a row can flow without being stored (scan, filter, projection, partial aggregate).
Pipeline breaker — an operator that must consume all of its input before it can output (sort, hash-table build, shuffle), so it ends a pipeline.
Operator fusion — merging several operators into one piece of code, so intermediate rows are not materialized.
Produce/consume model — Neumann's way of generating code: a parent asks a child to produce rows, and the child's generated code, for each row, inserts the parent's consume code inline.
Janino — a small, fast Java compiler library that Spark uses to compile generated Java source in memory, much faster than javac.
Virtual call — a call whose target is looked up at run time (through a table of function pointers), which blocks inlining and is hard for the CPU to predict.
Compilation latency — the time spent generating and compiling the code, paid before the first row is processed.
history: Using generated code to run queries is old: IBM's System R (1970s) compiled SQL statements to machine code. Later, interpreters became the norm, and Volcano (1994) is the best-known design. The idea returned when memory-bound disk systems became CPU-bound. In 2009–2010, Konstantinos Krikellas and others showed holistic query compilation to C code, and Thomas Neumann's HyPer system at TU Munich turned it into a design. His 2011 VLDB paper "Efficiently Compiling Efficient Query Plans for Modern Hardware" introduced the push-based produce/consume model and generated LLVM code for whole pipelines, getting performance similar to hand-written C.
Big data systems followed. Cloudera Impala (2012) used LLVM to compile expressions and tuple handling. Apache Spark started the Tungsten project in 2015 (binary row format, off-heap memory, cache-aware algorithms), and in Spark 2.0 (2016) Databricks added whole-stage code generation, described in the blog post "Apache Spark as a Compiler: Joining a Billion Rows per Second on a Laptop". PostgreSQL 11 (2018) added LLVM-based JIT for expressions and tuple decoding, written by Andres Freund. Amazon Redshift compiles query segments to C++ and caches them.
The costs then became the research subject. Compilation takes time, so Kohn, Leis and Neumann ("Adaptive Execution of Compiled Queries", ICDE 2018) proposed starting a query in a bytecode interpreter and switching to compiled code only for queries that run long enough. Umbra (Neumann and Freitag, CIDR 2020; Kersten and others, VLDB Journal 2021) generates its own low-latency intermediate language and has a fast code path that runs before the slower LLVM optimizations. In parallel, other teams chose vectorization instead: Kersten and others (VLDB 2018) showed that the two approaches are close, and Databricks built Photon (SIGMOD 2022), a C++ vectorized engine, partly because it is easier to build, debug and profile than generated code. Today both approaches exist, often in the same system.
how: Take a plan that computes SELECT sum(x * 2) FROM t WHERE x > 5. In a Volcano engine the plan is an Aggregate over a Project over a Filter over a Scan. For every row the aggregate calls project.next(), which calls filter.next(), which calls scan.next(). Each call is a virtual call that the compiler cannot inline, because the target is known only at run time. The row is passed through memory (an object or a buffer), and expressions such as x > 5 are evaluated by walking a small tree (one more virtual call for each node). The CPU spends most of its time on these calls and on branch mispredictions, not on the arithmetic.
Whole-stage code generation changes the execution model in four steps. First, the engine splits the plan into pipelines at pipeline breakers: the scan, filter, projection and the partial aggregate form one pipeline (Spark calls it a stage, and shows it with a star in EXPLAIN), and a shuffle (exchange) starts a new one. Second, for each pipeline it generates the source code of a single function. The generation uses the produce/consume protocol: the aggregate asks the project to produce, which asks the filter, which asks the scan; the scan generates a loop over rows, and inside the loop body each parent adds its own code, so the filter inserts "if (!(x > 5)) continue;", the projection inserts "long v = x * 2;" and the aggregate inserts "sum += v;". Because each operator contributes inline code, there are no calls between them.
The result is a loop like: for each row in the scan { int x = row.getInt(0); if (x > 5) { sum += x * 2; } }. The values x and sum are local variables that the compiler can keep in registers; the expression x * 2 is compiled with the constant 2 inlined; types are known, so no boxing or type checks remain. This is what the Databricks blog calls collapsing the query into a single function. The generated code is also much easier for the CPU: a short loop, a predictable branch, no indirect calls. This is where the CPU pipelining layer pays off.
Third, the code is compiled. Spark generates Java source text, compiles it with Janino into bytecode in memory (tens of milliseconds for a typical stage), loads the class, and runs it. The JVM then runs the bytecode in its interpreter at first and compiles hot loops to native code with the C1 and C2 JIT compilers; since the generated function contains a long-running loop, the JVM uses on-stack replacement to switch into the compiled version in the middle of the loop. HyPer and Umbra instead emit LLVM IR, which is in SSA form (each variable assigned once), run LLVM's optimizer, and produce machine code directly. This is the contribution of the intermediate-representation layer: the generator does not need to know about registers, instruction selection or scheduling; it states the computation in SSA and the compiler handles the machine details.
Fourth, the engine runs the code and handles the edges. A pipeline breaker such as the aggregate stores its state (a hash table, a running sum) in memory, and a second generated function reads that state to produce output for the next pipeline. Operators that cannot be generated (some user-defined functions, very wide schemas) cut the pipeline and fall back to the interpreter at that point. Spark limits codegen to plans with at most 100 fields per stage by default, and it checks the size of generated methods: the JVM rejects methods over 64 KB of bytecode, and HotSpot will not JIT-compile a method over 8,000 bytes by default, leaving it in the slow interpreter, so Spark splits code into smaller methods and falls back to interpreted execution when compilation fails.
Fused code also interacts with the data layout. Spark's scan reads Parquet in column batches with a vectorized reader, then a conversion step turns the batch into rows for the generated loop (the ColumnarToRow node in the plan), so the generated code is row-at-a-time inside a stage, but with no function call overhead. The point of fusion is to keep a row in registers through as many operators as possible; shuffles, sorts and hash-table builds write rows to memory anyway.

example: The Databricks measurements (single thread, Spark 1.6 against Spark 2.0 with whole-stage code generation) give a clear picture: a filter costs 15 ns per row against 1.1 ns; a sum without grouping 14 ns against 0.9 ns; a sum with grouping 79 ns against 10.7 ns; a hash join 115 ns against 4.0 ns; Parquet decoding of one integer column 120 ns against 13 ns. A sort-merge join barely changed: 750 ns against 700 ns.
Turn these into time. A table has 1 billion rows and the query is a filter followed by a sum. At 15 ns per row for the filter plus 14 ns per row for the sum, the interpreted engine needs about 29 ns × 10⁹ = 29 seconds of one core. With generated code the two steps fuse into one loop of about 1 to 2 ns per row, so 1 to 2 seconds. On 16 cores both numbers divide by about 16 (if the data is already in memory): roughly 1.8 seconds against 0.06 to 0.12 seconds. Now the compile cost: generating and compiling the stage takes perhaps 30 to 100 ms the first time. For the billion-row query this is a few percent of the interpreted time and pays for itself many times over. For a query over 10,000 rows, the interpreted engine needs 0.3 milliseconds and the compile cost of 50 ms is 150 times more than the work itself. This is why short and small queries do not benefit, and why some systems interpret first and compile later.
Next, why the sort-merge join barely improved. A sort-merge join is dominated by sorting and by memory access to large buffers, in which every comparison and copy misses the cache. Removing virtual calls does not remove those misses. The speed-up of fusion is large only where the CPU, not memory, is the limit. This is also the reason to remember that, in a real cluster, a shuffle or a disk read often takes longer than the whole in-CPU pipeline.
Finally, a look at the memory side of fusion. With the Volcano model, three operators pass each row through an object in memory: write 3 times and read 3 times a row of, say, 32 bytes. For 10⁹ rows that is 192 GB of moves inside the cache hierarchy (mostly L1 hits, so cheap but not free). In the fused loop, x and the product exist only in registers, and the only memory traffic is the scan itself and the final aggregate state. The saving is not only fewer instructions but also fewer loads and stores in the part of the pipeline that is hardest to speed up.
intuition: Rather than passing each item down a line of workers, write one worker's instructions that do all the steps in a single motion.
A general assembly line must work for every product, so every worker checks which product it is and hands it to the next worker. If you know the exact product in advance, you can write a single instruction sheet for one worker who does cut, drill and paint in one go. Writing the sheet costs time, so it pays only if there are many items. The design is natural because the engine knows the query before it starts, and everything that is known in advance (types, constants, the shape of the plan) can be baked into the code instead of being checked again for every row.
mistakes: People often think code generation is the same as the JVM's JIT compiler. In fact the JIT compiles the engine's general code, which still contains virtual calls and generic paths. Code generation writes a different program for this query. In Spark both happen: Janino compiles the generated source and then the JIT optimizes the hot loop.
People often think code generation always makes queries faster. In fact for short queries the compile time is larger than the run time, wide plans can produce huge methods that the JIT will not compile, and memory-bound operators (sorts, big joins, shuffles) gain little. The Databricks numbers show 10 to 100 times for CPU-bound primitives but almost nothing for the sort-merge join.
People often think the whole query becomes a single function. In fact only a pipeline does: pipeline breakers (shuffles, sorts, hash-table builds, some joins) cut the plan into several stages, and stages exchange data through memory or the network. The star numbers in Spark's EXPLAIN show the stage boundaries.
People often think code generation and vectorization are rivals where one must win. In fact Kersten and others (2018) found them close in speed: compiled code is better at fused, computation-heavy pipelines, vectorized code at memory-bound steps and at fast start-up. Spark uses vectorized scans feeding generated loops, and Photon chose the vectorized path for the whole engine.
People often think a UDF is compiled together with the plan. In fact a user-defined function written in Python or as an opaque function object is a black box to the generator. It cuts the stage, rows are passed to it one by one, and the benefit of fusion stops there.
friction: Compilation latency is the first cost. The engine must generate code, compile it and, in the JVM, wait for the JIT to warm up, which for a complex plan can take hundreds of milliseconds or even seconds before the first row is processed. For interactive queries over small data this is more than the query itself. Caches of compiled code help for repeated queries (Redshift, Spark's code cache), and adaptive systems start in an interpreter, but ad hoc queries often pay the full price.
Size and complexity limits come next. A very wide projection or a deep expression generates large methods. The JVM limits a method to 64 KB of bytecode, and HotSpot declines to JIT methods above 8,000 bytes, which makes code slow without any error. Engines split methods and cap the width of a stage, and then fall back to interpretation, so the performance of a query can change suddenly when a column is added. In Spark this appears as "Code of method grows beyond 64 KB" errors or as silent fallbacks.
Debugging and observability are harder. The code that runs is generated text or IR that the developer did not write, stack traces point into generated classes, and profilers show the fused loop as one block, so the time per operator is not visible. Engines add comments in the generated code and tools to print it (EXPLAIN CODEGEN), but reasoning about performance requires reading generated code.
There are also hardware and language limits. A row-at-a-time loop with branches is hard to turn into SIMD instructions, so generated code often does not use vector units, unlike a vectorized engine. In a JVM the generated code still allocates objects for strings and complex types and puts pressure on the garbage collector. The engine depends on a compiler stack (LLVM, Janino, the JIT) whose version, bugs and behavior become part of the engine. Finally, the correctness surface is larger: bugs in the generator appear only for certain plan shapes and types, which is a reason why some teams prefer the vectorized approach.
practice: In Spark, leave spark.sql.codegen.wholeStage on (the default) and learn to read plans: in EXPLAIN a star followed by a number marks operators fused into a stage. Look for operators without a star in the middle of a CPU-heavy pipeline; they cut the stage. Typical causes are Python UDFs, very wide schemas (more than 100 fields by default, setting spark.sql.codegen.maxFields), operators without codegen support, and expressions that generate huge methods. Replace UDFs by built-in functions, select only the columns you need early, and avoid giant CASE WHEN chains or hundreds of columns computed in one projection.
To see the generated code, use EXPLAIN CODEGEN (or df.explain("codegen")). If you see compilation errors or messages about methods that grow beyond 64 KB, simplify the expressions, split the query into steps, or accept the fallback (spark.sql.codegen.fallback keeps queries running when compilation fails). On Databricks, consider Photon for scan, filter, join and aggregation heavy workloads; it replaces the JVM-generated code with native vectorized code for the operators it supports.
Measure with a big enough input. Compare run time with and without whole-stage codegen on a representative query, and make sure the data is large enough that the compile cost is small compared with the run time. For interactive or short queries, reduce plan complexity or cache results; do not expect fusion to help.
In PostgreSQL, JIT is available from version 11 and is used when the planner's estimated cost is above jit_above_cost (100,000 by default). It helps long analytical queries with many rows and expressions, but can hurt short queries whose estimated cost crosses the threshold; many OLTP deployments turn it off (jit = off) or raise the thresholds. If you build an engine, begin with a good interpreter or vectorized engine, add compilation for the hottest pipelines, and consider a cheap interpreter-first, compile-later path.
tradeoffs: Choose whole-stage code generation when queries are CPU-bound pipelines of scans, filters, projections and aggregations over many rows (hundreds of millions to billions), run for seconds or more, and the plan shape is regular. Choose a vectorized interpreter when queries are short or ad hoc, start-up latency matters, you want the engine to be debuggable and easy to profile, and you can write the engine in a language with good SIMD support. You give up compile-time freedom and the fusion of registers with vectors; you give up the elimination of intermediate materialization with generated code.
Choose compilation of the whole pipeline (HyPer, Spark) when many operators are chained and computation dominates, so that keeping values in registers across them removes a lot of memory traffic. Choose compilation of expressions only (Trino, PostgreSQL) when you want a smaller, safer generator, faster compile, and operators written by hand. You trade some of the speed of full fusion for simpler engineering.
Choose the LLVM route when you control a native engine and can afford compilation times of tens to hundreds of milliseconds per query and a large dependency. Choose generating Java source or bytecode on the JVM when the engine already runs there, accepting JIT warm-up and method-size limits. Choose adaptive execution (interpret first, compile when the query turns out to be long) when your workload mixes very short and very long queries.
Choose to fall back to the interpreter, or to reduce the stage size, when a plan is wide or complex; choose to raise limits only after measuring that the JIT really compiles the larger methods. You pay with performance cliffs in the first case, and with risk of slow interpreted code in the second.
interview: Explain how whole-stage code generation removes overhead compared with the Volcano model. || Volcano makes a virtual next() call per operator per row, passes the row through memory, and evaluates expressions by walking a tree. Code generation fuses a pipeline into one loop whose body contains the filter, projection and aggregation inline, with typed local variables the compiler keeps in registers and constants inlined. There are no virtual calls or intermediate rows in the loop, and the CPU sees a short loop with predictable branches.
What is the produce/consume model? || Each operator generates code in two parts: produce asks the child to produce rows, and consume is called by the child's generated code once per row to add the parent's per-row code inline. Generation starts at the root, the leaf (scan) emits the loop, and every parent inserts its consume code inside it, so the pipeline becomes one function. Pipeline breakers store state and start a new pipeline.
Why did codegen speed up a filter 14 times and a sort-merge join barely at all? || A filter and a simple sum are CPU-bound: the cost was calls, branches and memory moves that fusion removes. A sort-merge join is dominated by sorting and cache-missing memory access, which fusion does not remove. Fusion pays only where the CPU is the bottleneck.
A Spark query on a wide table slowed down after adding more columns. What could be happening? || The stage may have passed the field limit (100 by default) or generated methods too large to compile, so codegen is switched off or the JIT leaves a huge method interpreted. Check the plan for stars, EXPLAIN CODEGEN for oversized methods, and logs for fallback warnings. Select fewer columns early, simplify expressions, or use Photon.
When would you prefer vectorized execution over compiled execution? || When start-up time matters (short or ad hoc queries), when you need to debug and profile operators, when memory-bound operators dominate (joins, aggregations with batched hash lookups), or when SIMD can be used. A 2018 comparison found the two within a small factor of each other, so the choice depends on workload and engineering cost.
How do HyPer or Umbra reduce compilation latency? || They generate compact code directly, avoid heavy optimizer passes for short queries, use a fast low-level code path first and optimize with LLVM later (Umbra's Flying Start), and can run a bytecode interpreter while compilation proceeds (adaptive execution), switching to the compiled version when it is ready.
quiz: What does a pipeline breaker do to code generation? || It must consume all its input before producing output, so it ends a pipeline: the code before it is one generated function, and the code after it starts a new one. Sorts, hash-table builds and shuffles are breakers.
Why can the generated loop keep values in registers while Volcano cannot? || In the fused loop, each value is a local variable of known type in one function, so the compiler assigns registers. In Volcano, each operator is a separate object and the row travels between them through memory via virtual calls.
In Spark's EXPLAIN, what does a star before an operator mean? || The operator is part of a whole-stage code generation stage (the number identifies the stage), fused with the other starred operators of that stage.
A billion-row query takes 29 s interpreted and about 1 s with codegen, and compiling costs 50 ms. A 10,000-row query takes 0.3 ms interpreted. Which one benefits? || The billion-row query: the compile cost is 5% of the run time and it saves 28 s. For the small query, the 50 ms compile time is about 150 times the interpreted run time, so code generation loses.
When would you choose adaptive execution (interpret first, compile later)? || When a workload mixes short and long queries and you cannot tell in advance which is which. The interpreter starts at once, and compiled code takes over only when the query turns out to run long enough to repay the compile time.
