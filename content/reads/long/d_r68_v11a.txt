@@ pruning
value: Pruning removes the parts of a trained neural network that matter least. The parts can be single weights, whole neurons, channels or attention heads. After removal, the network is smaller and, if the hardware allows it, faster. The key finding behind the field is that large networks are heavily over-parameterized. Many weights can be set to zero with little loss of accuracy, especially if the network is trained a little more afterwards.
Why does this matter to an engineer? Memory and compute are the main cost of running a model. A model that is half the size needs half the memory bandwidth, and in LLM serving, memory bandwidth is often the limit. Pruning is also one of the main tools for putting models on phones, cameras and other small devices. Courses such as MIT 6.5940 (TinyML and Efficient Deep Learning Computing) and Stanford CS 217 (Hardware Accelerators for ML) teach it for this reason.
There is one important catch. Setting a weight to zero does not by itself make anything faster. A dense matrix multiplication still reads every zero and multiplies it. Speed only comes when the zeros follow a pattern that the hardware or software can skip. This is why the topic has two halves: the algorithm that decides what to remove, and the structure of the zeros that decides whether the result is fast.
Pruning gives the layers above it a way to fit larger models into a fixed memory or latency budget. It sits next to quantization (fewer bits per weight) and distillation (a smaller student model). The three are usually combined.
terms: Sparsity — the fraction of weights that are exactly zero; 90% sparsity means one weight in ten is kept.
Unstructured pruning — removing individual weights anywhere in a matrix; it gives the highest accuracy at a given sparsity but irregular zeros that are hard to speed up.
Structured pruning — removing whole units such as channels, neurons or attention heads, so the remaining matrices are smaller and dense.
Semi-structured sparsity (N:M) — a fixed pattern where each group of M consecutive weights keeps at most N non-zeros; 2:4 means two of every four.
Saliency — a score that estimates how much the loss grows if a weight is removed; low-saliency weights are pruned first.
Magnitude pruning — using the absolute value of a weight as its saliency.
Mask — a binary tensor of the same shape as the weights; a 0 means the weight is pruned.
Fine-tuning (retraining) — training the pruned network for a few more steps so the remaining weights compensate.
One-shot pruning — pruning a trained model in a single pass, with no retraining; used for very large language models.
Sparse tensor core — GPU hardware that skips the zeros of a 2:4 sparse matrix and does the multiplication at up to twice the dense rate.
history: The idea is old. In 1989 Yann LeCun, John Denker and Sara Solla published "Optimal Brain Damage". They asked which weights can be deleted with the smallest increase in the loss. Their answer used the second derivative of the loss: a weight with a small value and a small curvature is cheap to remove. In 1993 Babak Hassibi and David Stork extended the idea with the full second-order information in "Optimal Brain Surgeon". These methods were too costly for large networks, but they set the frame: score each weight, remove the lowest, retrain.
The topic came back in 2015, when networks such as AlexNet (61 million parameters) and VGG-16 (138 million) were too large for phones. Song Han, Jeff Pool, John Tran and William Dally published "Learning both Weights and Connections for Efficient Neural Networks". The method was simple. Train the network, remove all weights below a threshold, retrain, and repeat. AlexNet fell from 61 million to 6.7 million parameters (9 times fewer) and VGG-16 from 138 million to 10.3 million (13 times fewer), with no loss of accuracy on ImageNet. Later in 2015 the same group published "Deep Compression", which added trained quantization and Huffman coding and reached 35 to 49 times smaller storage.
In 2018 Jonathan Frankle and Michael Carbin published the "lottery ticket hypothesis". A dense network contains small sub-networks that, trained alone from the same starting weights, reach similar accuracy. This changed how researchers thought about pruning: it is not only compression, it is also a search for a good small network.
The next problem was hardware. Unstructured zeros gave small files but little speed on GPUs. NVIDIA's Ampere GPUs (2020) added sparse tensor cores for the 2:4 pattern. A 2021 paper by Asit Mishra and colleagues describes the design and a simple training workflow for it. Then came large language models. In January 2023 Elias Frantar and Dan Alistarh published SparseGPT. It showed that a model with 175 billion parameters can be pruned to at least 50% sparsity in one shot, without retraining. In June 2023 Mingjie Sun, Zhuang Liu, Anna Bair and Zico Kolter published Wanda, a much simpler score that also needs no retraining.
how: Every pruning method answers three questions. Which weights to remove, how much to remove at once, and what to do afterwards. The patterns of zeros also decide how the model will run.
Step 1: choose a saliency score. The simplest score is the absolute value of the weight. This is magnitude pruning. It works because a small weight changes the output of its neuron only a little. The link to regularization is direct: an L1 penalty during training pushes many weights toward zero, so they become easy to prune. An L2 penalty shrinks weights smoothly, which also makes magnitude a better score. Han and colleagues found that L2 regularization with retraining gave the best final accuracy in their tests. Optimal Brain Damage uses a better score, half the curvature times the weight squared, but curvature is expensive to compute for large models.
Step 2: apply the score and make a mask. A local method keeps the same fraction in every layer. A global method ranks all weights in the network together and removes the lowest overall, so sensitive layers keep more. The mask is a tensor of zeros and ones. In PyTorch, the torch.nn.utils.prune module stores the original weights and a mask separately, and multiplies them in the forward pass. Training can then continue with the mask fixed.
Step 3: recover accuracy. Pruning many weights at once hurts the loss. The usual remedy is iterative: prune a little, fine-tune, prune again. Han and colleagues showed that this iterative process raised the reachable pruning rate on AlexNet from about 5 times to 9 times compared with one aggressive step. Distillation helps here. The dense model acts as a teacher, and the pruned model is trained to match the teacher's output probabilities, not only the labels. This gives the small model a richer training signal than the labels alone and usually recovers more accuracy.
Step 4: make the zeros useful. This is the hardware step. Unstructured sparsity at 90% needs an index for every non-zero weight. On a GPU, irregular memory access and index handling often cost more than the skipped math, so a 90% sparse matrix may run no faster than the dense one. Structured pruning removes whole channels or heads, so the result is a smaller dense matrix. Any hardware runs it faster, but accuracy falls sooner because the choice is coarse.
The middle path is the N:M pattern. In the 2:4 pattern, each group of four consecutive weights has at least two zeros. The sparse tensor core stores only the two non-zero values plus a 2-bit position for each. For 16-bit weights, four dense values take 64 bits, and the compressed form takes 2 times 16 plus 2 times 2, which is 36 bits. That is about 44% less memory. The hardware then selects the matching activations and multiplies only the non-zeros, at up to twice the dense math rate. The pattern is regular, so the load is balanced and the metadata is small. The paper describes a workflow: train dense, prune to 2:4 by keeping the two largest magnitudes in each group, then retrain with the same settings as the dense run. They report that this keeps accuracy over a wide range of networks.
For large language models, retraining is often too costly. SparseGPT prunes one layer at a time. For each layer it keeps the layer output close to the original on a small set of calibration inputs, and it updates the remaining weights to compensate for the removed ones. It handles 175-billion-parameter models in under 4.5 hours and also supports the 2:4 pattern. Wanda uses a cheaper score: the weight magnitude times the norm of the input activation that feeds the weight, compared within each output row. A small weight that always sees large inputs is kept. A larger weight that sees tiny inputs can go. No weight update is needed.
Whatever the method, always measure the real sparsity of each layer after pruning, since global ranking can leave some layers much denser than others. Pruning also stands on quantization and on the tensor core. Pruning removes entries. Quantization makes the remaining entries smaller, for example from 16 bits to 4 bits. The two effects multiply in size and are usually applied together. The tensor core is what turns the 2:4 pattern into real speed.

example: Take one row of 8 weights: [0.9, -0.05, 0.4, 0.02, -0.7, 0.1, 0.03, -0.3]. We will prune it three ways, to 50% sparsity each.
Magnitude, unstructured. Rank by absolute value: 0.9, 0.7, 0.4, 0.3, 0.1, 0.05, 0.03, 0.02. Keep the top four: 0.9, -0.7, 0.4, -0.3. The mask is [1, 0, 1, 0, 1, 0, 0, 1]. Four weights are zero, anywhere in the row.
Magnitude, 2:4. Split the row into two groups of four. Group one is [0.9, -0.05, 0.4, 0.02]; keep the two largest, 0.9 and 0.4. Group two is [-0.7, 0.1, 0.03, -0.3]; keep -0.7 and -0.3. The mask is [1, 0, 1, 0, 1, 0, 0, 1]. Here the result is the same as unstructured, but only by luck.
Now take a second row: [0.9, 0.8, 0.7, 0.01, 0.02, 0.03, 0.04, 0.5]. Unstructured pruning keeps 0.9, 0.8, 0.7 and 0.5. The 2:4 rule keeps only 0.9 and 0.8 in group one, so it must drop 0.7. In group two it keeps 0.5 and 0.04, although 0.04 is tiny. The 2:4 rule discards a large weight and keeps a small one to preserve the pattern. That is the accuracy cost of regularity.
Wanda. Suppose the input activations feeding these 8 weights have norms [1, 1, 1, 1, 0.1, 10, 1, 1]. The Wanda score is the weight magnitude times the input norm: [0.9, 0.05, 0.4, 0.02, 0.07, 1.0, 0.03, 0.3]. Now weight 0.1 (position 6) gets score 1.0 and is kept, and weight -0.7 (position 5) gets score 0.07 and is removed. The top four are 1.0, 0.9, 0.4 and 0.3. The mask is [1, 0, 1, 0, 0, 1, 0, 1]. Magnitude alone would have made the opposite choice at positions 5 and 6.
Storage. For a 4096 by 4096 layer in 16 bits, the dense weights take 16.8 million values times 2 bytes, which is about 33.5 MB. With 2:4 sparsity, the values take half of that, 16.8 MB, and the metadata takes 2 bits for each kept value, 8.4 million values times 2 bits, which is about 2.1 MB. The total is about 18.9 MB, which is 44% less than the dense layer. That matches the 36 versus 64 bits per group of four.
Speed. The tensor core can run at up to twice the dense math rate. A layer that is limited by math can become close to twice as fast. A layer that is limited by memory gains from the smaller read. Real end-to-end gains are usually lower, because other layers and the attention step do not shrink.
intuition: Pruning is like editing a long draft: you cut the sentences that carry the least meaning, then reread and fix the joins.
The idea is natural because training a large network is easier than training a small one. Many weights start with similar roles, and training spreads the work over them in a redundant way. Once the network knows the task, much of that redundancy can be removed. The lottery ticket result says the same thing from the other side: a good small network was already inside the big one.
The need for a regular pattern is also natural. A processor is fast when it does the same simple thing over regular data. Random zeros force it to look up where each value is. A fixed pattern such as 2:4 lets the designer put the lookup in the circuit once, for all values.
mistakes: People often think a model with 90% zero weights is ten times faster. In fact it is often not faster at all on a GPU, because the dense kernel still multiplies the zeros and a sparse kernel pays for indexes and irregular reads. Speed needs a structure that the hardware supports, such as 2:4, or the removal of whole channels.
People often think pruning only shrinks the file. In fact the file is the easy part. A pruned model saved in a dense format has the same size as before, because zeros are still stored. You must store it in a sparse format or remove whole structures to save memory.
People often think a pruned layer needs no more training. In fact most methods need fine-tuning or at least calibration, because removing weights shifts the outputs of the layer. One-shot methods such as SparseGPT and Wanda avoid full retraining, but SparseGPT still updates the remaining weights, and both use a small calibration set.
People often think the weights with the smallest magnitude are always the least important. In fact importance also depends on the inputs. In large language models a few input features have very large activations, so a small weight that reads such a feature can matter a lot. This is the observation that Wanda uses.
tradeoffs: Choose unstructured pruning when you need the best accuracy at a given parameter count and your runtime has a real sparse kernel, or you only want a smaller download. Choose structured pruning (channels, heads, layers) when you must run on ordinary hardware and want a guaranteed speed-up. You give up accuracy sooner with structured pruning, because removing a whole channel removes many weights at once, some of them important. You give up speed with unstructured pruning, because irregular zeros need indexes.
Choose 2:4 sparsity when you serve on NVIDIA Ampere or later GPUs and the layers are large matrix multiplications. You get a fixed 50% sparsity, up to twice the math rate and about 44% less weight memory for 16-bit values. You give up the freedom to choose the sparsity: it is always 50%, and the pattern can remove some large weights. Choose a higher unstructured sparsity, for example 70% to 90%, when the target is a CPU or a special accelerator with its own sparse support, or when only storage matters.
Choose one-shot pruning (SparseGPT, Wanda) when the model has billions of parameters and you cannot afford training. A pass over a 175-billion-parameter model takes hours, not weeks. You give up accuracy at high sparsity: results are good near 50% and drop quickly above 60% to 70%. Choose iterative prune and fine-tune when you can afford training. It reaches higher sparsity at the same accuracy, but it costs many training steps and tuning of the schedule.
Choose pruning over a smaller dense model when the large model has already learned something that a small model trained from scratch cannot match. Choose quantization first when you want the cheapest gain: going from 16-bit to 8-bit halves memory and is supported on all hardware. Pruning is the second step, once quantization is done. Often a distilled small model is a better choice than a pruned large one, because it is a normal dense model that runs everywhere. You give up the extra training run for the distillation.
friction: The largest problem is the gap between sparsity and speed. A paper can report 90% sparsity, while the real speed on a given GPU is flat. Always ask what kernel runs the sparse model, and measure latency on the target device, not the parameter count.
Accuracy loss is not uniform. Averages hide that pruned models can lose more on rare classes, on hard examples and on long-context behaviour. A model that keeps its perplexity may still lose on reasoning tasks. Test on the tasks you care about, not only on one headline metric.
The training recipe is hard to tune. There are many choices: the score, the schedule, the learning rate during fine-tuning, local or global ranking. Different papers do not always agree, because their baselines and training budgets differ. Many early results were also hard to compare, and later work built common benchmarks to fix this.
Pruning interacts with other compression. Quantization after pruning may behave differently than quantization before pruning. SparseGPT is designed to work with weight quantization, but the combination must still be checked. The sparse format also needs metadata, which cuts the gain: 2-bit indexes per value at 16 bits is a 12.5% overhead.
Finally, the gain on large language model serving depends on the phase. During decoding, the speed limit is usually reading weights from memory, so smaller weights help. During prefill with large batches, the limit is math, and the sparse tensor core helps. Attention and the key-value cache do not shrink with weight pruning, so the gain falls as the context grows.
practice: Start with the cheapest options. Measure the dense baseline for latency, memory and accuracy on your real tasks. Try 8-bit or 4-bit quantization first. If you still need more, add pruning.
If you serve on NVIDIA Ampere or later GPUs, 2:4 sparsity is the most practical pruning format. Prune the large linear layers to 2:4 with a magnitude rule or with a method such as SparseGPT, fine-tune if you can, and check the speed with your real batch sizes. Use the vendor library for sparse matrix multiplication. Small matrices and small batches can show little gain, so test the shapes you actually run.
For edge devices, think about the structure first. Remove channels or heads so the model stays dense, then use the normal compiler for the target. Use an iterative schedule: prune a few percent, fine-tune for a short time, repeat, and watch the accuracy after each round. Stop when the accuracy falls below your limit.
For large language models without a training budget, begin with Wanda. It needs only a calibration set and a forward pass. If the accuracy at 50% is not good enough, try SparseGPT, which costs more compute but updates the remaining weights. Keep the calibration data close to your real traffic.
Always save the mask with the model, and report the real sparsity per layer. Record the exact method and seeds so that another engineer can repeat the result. Compare the final model against a distilled dense model of the same size, because that is the honest alternative.
interview: A team prunes a model to 90% sparsity and sees no speed-up on GPUs. What is wrong and what would you do? || Unstructured zeros do not map to the dense kernels, and sparse kernels pay for index lookups and irregular reads, so the zeros are still computed or the overhead hides the gain. Move to a hardware pattern (2:4 on Ampere and later) or to structured pruning of channels and heads, and measure latency on the real device and batch size, not parameter count.
Why does 2:4 sparsity stop at 50%, and what does it cost in memory terms? || The pattern fixes two non-zeros per group of four so the hardware can use a small, fixed-size selector. At 16 bits, each group goes from 64 to 36 bits (two values and four metadata bits), a saving of about 44%, not 50%, because of the metadata. The fixed ratio may remove some large weights, so a short fine-tune is usually needed.
How does Wanda choose weights, and why does it beat plain magnitude on large language models? || It scores each weight by its magnitude times the norm of the input activation, and compares scores within each output row. Large language models have a few input features with very large activations, so a small weight that reads such a feature is important. Magnitude alone ignores this and removes it.
You can retrain, but the budget is small. Choose between pruning a large model and distilling a small one. || Compare on the real task at equal latency. Distillation gives a dense model that runs on any hardware with no sparse kernel risk, and it needs a full training run. Pruning keeps the large model's knowledge and needs only fine-tuning but depends on hardware support. Without a sparse kernel on the target, distillation or structured pruning is the safer choice.
Does pruning help the key-value cache in LLM serving? || No. Weight pruning shrinks the weights, not the cache, which grows with context length and batch size. For long contexts the cache dominates memory, so you need cache quantization, eviction or grouped-query attention as well. Head pruning is the exception, because removing a head removes its cache entries too.
What does the lottery ticket hypothesis claim and what is its practical limit? || A dense network contains a sparse sub-network that, trained alone from the same initial weights, reaches similar accuracy. In practice, finding the ticket needs a full training run and several prune rounds first, so the result explains pruning but does not make training cheaper.
quiz: What is the difference between structured and unstructured pruning? || Unstructured pruning removes individual weights anywhere, giving irregular zeros. Structured pruning removes whole units such as channels or heads, so the remaining matrices are smaller and dense.
Why does a 2:4 sparse matrix save 44% of memory at 16 bits, not 50%? || Four dense values take 64 bits. The 2:4 form stores two values (32 bits) plus a 2-bit position for each (4 bits), so 36 bits, which is 44% less than 64.
Why is iterative prune-and-fine-tune usually better than one large pruning step? || Removing many weights at once damages the loss too much for the remaining weights to recover. Small steps with retraining let the network adjust each time. Han and colleagues raised AlexNet's reachable rate from about 5 times to 9 times this way.
A layer has 8.4 million weights in 16 bits. How big is it after 2:4 sparsity, including metadata? || Dense size is 8.4 million times 2 bytes, about 16.8 MB. The values take half, 8.4 MB, and the 2-bit metadata for 4.2 million kept values takes about 1.05 MB, so the total is about 9.45 MB.
You must run a model on a CPU-only edge device with no sparse kernels. Which pruning style do you use? || Structured pruning, such as removing channels or heads, because the result is a smaller dense model that normal kernels run faster. Unstructured zeros would give a small file but no speed-up.

@@ graphemb
value: A graph embedding turns each node of a graph into a short list of numbers, called a vector. Nodes that are close or similar in the graph get vectors that are close in space. Once you have the vectors, you can use any ordinary machine learning tool: nearest-neighbour search, clustering, a classifier, or a recommender.
The problem it solves is that graphs do not fit machine learning tools. A model wants a fixed-size row of features for each example. A node has a variable number of neighbours, and its meaning depends on the whole surrounding network. Hand-made features, such as degree or the number of shared friends, take much effort and miss patterns. An embedding learns the features automatically from the structure of the graph.
DeepWalk (2014) and node2vec (2016) do this with a trick borrowed from language. They run short random walks on the graph and treat each walk like a sentence, with nodes as words. Then they train a skip-gram model, the same model used for word vectors. Nodes that appear near each other in many walks get similar vectors.
For an engineer in ad tech or data platforms, this is useful in three places. Item and user graphs give vectors for candidate retrieval in recommendation. Device, account and household graphs give vectors that score whether two identifiers belong to the same person or home. Any large graph of events, such as a product co-view graph, can feed link prediction. Stanford CS 224W (Machine Learning with Graphs) teaches the method as the first step before graph neural networks.
terms: Node embedding — a vector, usually 64 to 512 numbers, that stands for one node.
Random walk — a path that starts at a node and repeatedly moves to a randomly chosen neighbour.
Skip-gram — a model that learns a vector for each token by predicting the tokens that appear around it in a sequence.
Window size — how many steps before and after a node in a walk count as its context.
Negative sampling — a training shortcut that pushes a node away from a few random nodes instead of from all nodes.
Return parameter p — in node2vec, controls how likely a walk is to step back to the node it just left.
In-out parameter q — in node2vec, controls whether a walk stays near its start (breadth-first like) or moves outward (depth-first like).
Homophily — the tendency of connected nodes to be similar; one of the two structure types that node2vec can capture.
Structural equivalence — nodes that play the same role, such as hubs or bridges, even if they are far apart in the graph.
Transductive — a method that only gives vectors for nodes seen in training; a new node needs new training.
history: Word vectors came first. In 2013 Tomas Mikolov and colleagues showed that a skip-gram model trained on sentences gives vectors in which directions carry meaning, and that training can be fast with negative sampling. Researchers asked whether the same idea would work on graphs.
In 2014 Bryan Perozzi, Rami Al-Rfou and Steven Skiena published DeepWalk, "Online Learning of Social Representations", at the KDD conference. They noticed that in scale-free graphs the number of times a node appears in short random walks follows a power law, as words do in text. So a language model should work. DeepWalk beat methods that saw the whole graph, especially when many labels or edges were missing. In 2015 Jian Tang and colleagues published LINE, which trains directly on edges (first-order and second-order closeness) and scales to millions of nodes.
In 2016 Aditya Grover and Jure Leskovec, at Stanford, published node2vec. DeepWalk used uniform random walks. node2vec added two parameters, p and q, that bias the walk. This lets the user choose whether the vectors should capture communities or roles. The paper reports gains in multi-label classification and link prediction over DeepWalk and LINE.
In 2017 Jiezhong Qiu and colleagues published "Network Embedding as Matrix Factorization". They proved that DeepWalk, LINE, PTE and node2vec with negative sampling each correspond to factorizing a specific matrix built from the graph. This tied the field to the older world of spectral methods and matrix factorization, and it led to a direct factorization method called NetMF.
Scale and features were the next problems. In 2018 Rex Ying and colleagues at Pinterest published PinSage, which mixes random walks with graph convolutions and uses node features, for a graph of billions of items. In 2019 Adam Lerer and colleagues at Facebook published PyTorch-BigGraph, a system that partitions the graph so embeddings can be trained for billions of nodes and trillions of edges. Since then, graph neural networks have taken much of the research attention, but walk-based embeddings remain a cheap, strong baseline.
how: The method has two stages: make a corpus of walks, then train a skip-gram model on it.
Stage 1: generate walks. For each node, start several walks. DeepWalk's experiments used 80 walks per node, each 40 steps long. At each step, the walker moves to a uniformly random neighbour, or to a neighbour with probability proportional to the edge weight. This is a Markov chain on the graph: the next node depends only on the current node. The choice of graph theory matters here: the neighbourhood of a node, its degree and the connectivity of the graph decide which nodes appear together. Short walks are enough because the aim is local structure, not the stationary distribution of the chain.
Stage 2: train skip-gram. Slide a window over each walk. For every node in the walk, the nodes within w steps on either side are its context. DeepWalk used w = 10 and d = 128. The model keeps two vectors per node, one as a centre and one as a context. For each (centre, context) pair, it raises the dot product of the two vectors. To avoid computing a softmax over all nodes, it uses either hierarchical softmax (a binary tree over nodes, which cuts the cost from the number of nodes to its logarithm) or negative sampling (push the pair apart from a few random nodes). Training uses stochastic gradient descent, and many threads can update the vectors in parallel with little coordination.
node2vec changes only stage 1. Its walk is second-order: the next step depends on the current node v and the previous node t. For each neighbour x of v, the unnormalized weight is 1/p if x is t itself, 1 if x is also a neighbour of t, and 1/q if x is farther from t. A small q pushes the walk outward, like depth-first search, so nodes in similar roles get similar contexts. A small p keeps the walk close to its start, like breadth-first search, which captures local community structure. To keep this fast, the paper precomputes the transition probabilities and samples with the alias method, which takes constant time per step. The paper's usual settings were d = 128, 10 walks per node, walk length 80 and context size 10.
Some practical details decide the quality. After training, most people keep the centre vectors and drop the context vectors, though averaging the two can help. The learning rate starts high and falls to near zero over the run. Walks can be generated on the fly, so the full corpus is never stored. DeepWalk is also online: because the walks are local, new edges change only the walks near them, so you can continue training on new walks instead of starting again. The papers do not claim this is exact, and in practice teams retrain on a schedule. Each extra walk per node costs more compute, so test how many walks your task needs.
To score an edge for link prediction, combine the two node vectors into one edge vector. The node2vec paper tried the average, the element-wise product (Hadamard), and the L1 and L2 differences of the two vectors. It then trained an ordinary classifier on these edge vectors, using real edges as positives and random node pairs as negatives. This shows how little the downstream part needs: any standard classifier will do. The vector view links to embeddings in general. The vectors are the same kind of object as word vectors, and the same tools work: cosine similarity, approximate nearest-neighbour search and a downstream classifier.
The matrix view links to matrix factorization. Qiu and colleagues showed that DeepWalk with negative sampling implicitly factorizes a matrix of node co-occurrence statistics, related to a power of the random-walk transition matrix and to the normalized Laplacian. So the neural training is not magic: it finds a low-rank approximation of how often nodes meet in walks. This also explains why simple factorization methods can match it when the matrix is computed directly.
At large scale, the memory is the main problem. One million nodes with 128 numbers in 32 bits take 512 MB per vector table, and skip-gram keeps two tables. One billion nodes need about 512 GB per table. PyTorch-BigGraph cuts the nodes into partitions, loads two partitions at a time and trains on the edges between them. This lets the tables live on disk or on several machines.

example: Take a small graph. Nodes 1, 2, 3 form a triangle. Nodes 4, 5, 6 form a second triangle. One edge joins node 3 to node 4. We want vectors that put the two triangles in two groups.
Walk generation. Start at node 1. A walk with uniform steps could be 1, 2, 3, 1, 3, 4, 5, 6, 4, 3. Most steps stay inside one triangle, because each node has two triangle neighbours and only node 3 and node 4 have the bridge edge. Node 3 has three neighbours (1, 2 and 4), so the chance of crossing at node 3 is one third.
Training pairs. With a window of 2, the walk gives pairs such as (1, 2), (1, 3), (2, 3), (2, 1), (3, 1), (3, 4), (3, 5) and so on. Nodes 1, 2 and 3 appear together in many pairs. Nodes 1 and 6 almost never do. After training, the dot product of vectors 1 and 2 is high and the dot product of 1 and 6 is low or negative.
node2vec bias. Suppose the walker is at node 3 and came from node 1. Its neighbours are 1 (the node it came from), 2 (a neighbour of node 1) and 4 (not a neighbour of node 1). Set p = 0.25 and q = 4. The weights are 1/p = 4 for node 1, 1 for node 2 and 1/q = 0.25 for node 4. The sum is 5.25, so the probabilities are 0.76, 0.19 and 0.05. The walker rarely crosses the bridge, so the vectors separate the two communities strongly. Now set p = 4 and q = 0.25. The weights are 0.25, 1 and 4, so the probabilities are 0.05, 0.19 and 0.76. The walker leaves for node 4 most of the time, so walks travel across the graph and the vectors capture roles, such as "node that connects groups".
Corpus size. For a graph of 1 million nodes with 10 walks per node and walk length 80, there are 10 million walks and 800 million node tokens. With a window of 10 on each side, each token makes up to 20 pairs, about 16 billion pairs per pass. That is why training uses many threads and negative sampling instead of a full softmax.
Memory. 1 million nodes times 128 numbers times 4 bytes is 512 MB for each of the two tables, about 1 GB in all. For 100 million nodes the same setting needs about 100 GB, which is why partitioned systems exist.
intuition: Tell me who your neighbours are, and I will tell you who you are, in numbers.
The idea is natural because a random walk is a cheap way to sample the neighbourhood of a node. A node that is reachable by many short paths from another node will meet it often in walks. Skip-gram training turns "meet often" into "close in space". It is the same logic as words: a word is known by the company it keeps, and a node is known by the nodes around it.
This also explains the limits. The vector has only what the walks saw: the shape of the graph. It does not know the age of a user or the title of an item, unless you put them into the graph as extra nodes.
mistakes: People often think a node embedding stores the neighbours of the node. In fact it stores a compressed summary of walk statistics. You cannot recover the exact edges from it, and two nodes with similar vectors need not be connected.
People often think node2vec is just DeepWalk with a better model. In fact the training model is the same. Only the way the walks are sampled is different, through p and q. The gain comes from choosing which kind of neighbourhood the user wants to preserve.
People often think graph embeddings and graph neural networks are the same thing. In fact walk-based methods give one free vector per node and cannot handle a new node or use node features. A graph neural network learns a function from features and neighbours to a vector, so it can embed new nodes.
People often think the vectors from one training run can be compared with those of another run. In fact the space is arbitrary: rotating all the vectors gives an equally good solution. Only distances inside one run are meaningful. To compare runs, align them first, or train jointly.
tradeoffs: Choose DeepWalk or node2vec when you have a large graph, little or no node features, and you need vectors quickly. Training on one machine takes minutes to hours for millions of nodes. You give up the use of node features and the ability to embed new nodes without retraining. Choose a graph neural network (GraphSAGE, PinSage) when nodes have rich features, or when new nodes arrive all the time, as in a live user graph. You pay with a more complex model, sampling code and training that often needs GPUs.
Choose node2vec over DeepWalk when you know what you want: a small q for structural roles, or a small p and larger q for communities. You pay for two more parameters to tune, and the tuning needs labelled data. Choose DeepWalk when you have no labels to tune with. Its uniform walk is a sound default, and the node2vec paper reports that p = 1 and q = 1 behaves like DeepWalk.
Choose direct matrix factorization (NetMF, or a truncated SVD of a co-occurrence matrix) when the graph is small enough for a dense matrix, up to roughly tens of thousands of nodes. It is deterministic and has no sampling noise. You give up scale, because the matrix grows with the square of the node count. Choose walks and SGD when you have millions of nodes.
Choose a larger dimension, 128 to 256, for graphs with many distinct communities, and a smaller one, 32 to 64, for small graphs or low-latency retrieval. Each extra dimension costs memory and search time, and it can overfit sparse nodes. Choose a partitioned system such as PyTorch-BigGraph when the vector tables no longer fit on one machine.
friction: Walk-based embeddings are transductive. A new user or device has no vector until you retrain or run an approximate update. In ad tech, where identifiers arrive every second, this is a real problem. Teams often retrain on a schedule and fall back to a feature-based model for new nodes.
The vectors contain only structure. A node with few edges has noisy vectors, because it appears in few walks. High-degree hubs appear in many walks and dominate the contexts, which can blur the vectors of their neighbours.
Quality depends on the graph more than on the algorithm. A noisy graph, for example a device graph with false links from shared public networks, gives vectors that carry the noise. Evaluation is also awkward. There is no single loss to compare across methods, so you must test on a downstream task such as link prediction, and use a proper train and test split of edges.
Results vary with random seeds and with many hyperparameters: walk length, number of walks, window, dimension and negative samples. The space is arbitrary up to rotation, so vectors from different runs cannot be compared directly. Embeddings of sensitive graphs, such as social or identity graphs, can reveal private links, so they need the same privacy care as the graph itself.
practice: Begin with a clean graph and a clear question, such as "which items are co-viewed" or "which devices share a home". Remove edges you do not trust and decide whether edges have weights. Choose a task to measure, for example link prediction on held-out edges, before you train anything.
Use a library, not your own code. PyTorch Geometric has Node2Vec and DeepWalk-style models, and DGL has similar tools. For graphs that do not fit in one machine, use PyTorch-BigGraph or a distributed system. Start with d = 128, 10 walks per node, walk length 80 and window 10, which are the values the node2vec paper used for its baselines, and tune from there.
Split the edges into train and test sets before generating walks, or the walks will see the test edges. Compare against two simple baselines: common-neighbour counts, and a plain matrix factorization. If the embedding does not beat them, do not ship it.
For serving, store the vectors in an approximate nearest-neighbour index. Candidate retrieval for recommendation then becomes a nearest-neighbour search from a user or item vector. For identity matching, use the vector similarity as one feature in a scoring model, not as the final decision, and keep a human-readable rule for explanations.
Plan the refresh. Retrain on a schedule, keep the previous vectors for rollback, and check that downstream models do not depend on a fixed rotation of the space. If new nodes matter most, move to a graph neural network with features.

value: A proof assistant, also called an interactive theorem prover, is a program in which you write a mathematical statement and a proof of it, and the program checks every step. If the check passes, the proof is correct, with no need to trust a human reviewer. The main systems today are Lean 4, Rocq (the new name of Coq) and Isabelle.
The problem it solves is trust. Tests show that a program works on the inputs you tried. A human proof can contain a gap that no reviewer sees. A proof assistant closes both gaps for the statements you can write down. The result is a machine-checked fact: this program meets this specification, for all inputs.
The design has a useful split. The proof may be found by a human, by a script, or by an automatic search, and it can be complicated. But the check is done by a very small part called the kernel, a few thousand lines of code. You must trust only the kernel and the statement you wrote. Everything else, however clever, cannot make a false theorem pass.
Proof assistants are used for two kinds of work. One is mathematics: the Lean library Mathlib has about 290,000 theorems. The other is software and hardware: the seL4 operating system kernel, the CompCert C compiler and parts of the Cedar authorization language were proved with these tools. For a data or ML engineer, the practical meaning is that a small, critical core, such as a kernel, a compiler, a policy engine or a cryptographic routine, can be shown correct, while the rest of the system is still tested in the usual way. Courses such as Caltech CS 128 (Interactive Theorem Proving, using Coq) and MIT 6.5120 (Formal Reasoning About Programs) teach this.
terms: Theorem and proof — a statement written in a formal logic, and a structured argument that the kernel can check.
Kernel — the small program that checks each proof step against the rules of the logic; it is the only part that must be trusted.
Tactic — a command such as induction or simp that changes the current goal and builds part of the proof for you.
Goal — what is still to be proved, shown together with the assumptions in the context.
Dependent type — a type that depends on a value, such as a list of length n; it lets a type say what a program must do.
Curry–Howard correspondence — the match between proofs and programs: a proof of "A implies B" is a function from proofs of A to proofs of B.
Specification — a formal statement of what a program must do; it is the part that humans must get right.
Higher-order logic (HOL) — a logic with functions as values and quantifiers over them; Isabelle/HOL is built on it.
Proof term — the full object that a proof builds; the kernel type-checks it.
Automation — programs that find proof steps, such as simp, omega or Isabelle's Sledgehammer, which calls external provers.
history: The first steps came in the 1960s and 1970s. Nicolaas de Bruijn built Automath in the late 1960s, a language where proofs are checked by a small program. In 1972 Robin Milner and colleagues at Stanford began LCF, "Logic for Computable Functions". Its important idea, kept in later systems, was to make theorems an abstract type. Only a small kernel can create a value of type theorem, so any proof, however it was found, must go through the kernel. Milner also created the ML language to write the proof scripts.
In the 1980s the main families appeared. Thierry Coquand and Gérard Huet worked on the calculus of constructions, a type theory with dependent types, and the Coq system grew from it in 1989 at INRIA. Lawrence Paulson started Isabelle in 1986 as a generic prover, and Isabelle/HOL became its most used form. HOL systems, based on higher-order logic, were built in the same period.
The 2000s showed that large proofs were possible. In 2005 Georges Gonthier completed a Coq proof of the four colour theorem, and in 2012 his team completed the Feit–Thompson odd order theorem. In 2009 the seL4 team showed the first OS kernel with a machine-checked proof of functional correctness at the source-code level. That proof was about 200,000 lines of proof script for about 10,000 lines of kernel code, written in Isabelle/HOL. Xavier Leroy's CompCert, a C compiler proved correct in Coq, showed the same for compilers.
Lean was started by Leonardo de Moura at Microsoft Research in 2013. Lean 4, described by de Moura and Sebastian Ullrich in 2021, is both a proof assistant and a general programming language, written largely in itself. The community library Mathlib grew fast. Its statistics page now counts about 140,000 definitions and about 290,000 theorems. In 2024 Amazon's Cedar team described how they proved properties of Cedar's authorizer and validator in Lean, and found bugs while doing it. The Coq system was renamed Rocq. Rocq 9.0 came out in 2025, and Rocq 9.2.0 on 27 March 2026. Isabelle makes regular releases, and Isabelle2026 appeared in October 2026.
how: A proof assistant has four layers: a logic, a kernel, a language for writing proofs, and automation. Each rests on a lower idea.
The logic comes first. Lean and Rocq use a dependent type theory. Isabelle/HOL uses higher-order logic. Both are formal systems with a small, fixed set of rules. They give meaning to the words "statement" and "proof". This is the logic concept: the statement of a theorem is a formula, and an allowed step is a rule. Higher-order logic lets you quantify over functions and sets, which is enough for most of mathematics and for the semantics of programs.
The type theory adds the Curry–Howard idea from type systems. A statement is a type. A proof is a program of that type. A proof of "A implies B" is a function that takes a proof of A and returns a proof of B. The kernel then does only type checking: does this term have this type? That is a simple, well-understood algorithm. Dependent types go further. A type such as "a vector of length n" or "a sorted list" can say what a program must satisfy. So the same language can hold code and the proof that the code is correct.
The kernel is the trusted base. Every proof, however it was made, ends as a term that the kernel checks. The idea is the de Bruijn criterion: a proof assistant is trustworthy if it produces proofs that a small independent checker can verify. Kernels are a few thousand lines of code. Several systems even have independent checkers written by other people, so a bug in one kernel does not go unnoticed.
Above the kernel is the proof language. You state a goal and the assistant shows the current goal and the assumptions. You apply tactics. A tactic such as intro, rewrite, induction or cases changes the goal into smaller goals. The tactics build the proof term behind the scenes. This is how induction from ordinary mathematical proofs appears: the induction tactic splits a goal about all natural numbers into a base case and a step case, with the hypothesis for the smaller number in context. Proofs are the same logic a person uses on paper, written in a form a machine can check.
Automation does the routine work. A simplifier rewrites with known equations. Decision procedures such as omega solve linear arithmetic. Isabelle's Sledgehammer calls external automatic provers and then rebuilds their result as a kernel-checked proof. Automation is not trusted: if it makes a mistake, the kernel rejects the result. So you may use any heuristic you like.
To verify programs, you add the idea of Hoare logic. A program is described with a precondition and a postcondition: if the precondition holds before running, the postcondition holds after. In a proof assistant you define the meaning of the programming language, state the pre and postconditions, and prove them step by step. The tools differ in style. In the seL4 style, a model of the C code is connected to an abstract specification by a refinement proof. In the CompCert style, the compiler is written as functions in Rocq, and a theorem says the compiled program behaves like the source. In the Cedar style, an executable model is written and proved in Lean, and the fast production code in Rust is checked against the model by differential testing.
Libraries add up in layers, as in ordinary software. Because the same kernel checks every theorem, a new proof can use any earlier theorem without reading its proof again. Mathlib is built this way, and a change at the bottom is re-checked up the whole tower by the build system. This is also why proof maintenance is real work: a small change in a definition can break many proofs above it.
Last, the statement matters as much as the proof. The kernel guarantees only that the proof proves the statement as written. If the specification is too weak or wrong, the proof is correct but useless. Good teams review the statement carefully, test it with examples, and keep it as small and readable as they can.

example: Here is a proof in Lean 4 that adding zero on the left does nothing, for every natural number n. The statement is 0 + n = n.
```text
theorem zero_add_example (n : Nat) : 0 + n = n := by
  induction n with
  | zero => rfl
  | succ k ih => omega
```
Read it step by step. The first line states the theorem. The name is zero_add_example, the variable is n, a natural number, and the claim is 0 + n = n. The word `by` starts a tactic proof.
The tactic `induction n` splits the goal in two, as in a paper proof. The first goal is the base case: 0 + 0 = 0. The tactic `rfl` closes it, because both sides compute to the same value, 0. The second goal is the step case: assuming 0 + k = k (this is named `ih`, for induction hypothesis), prove 0 + (k + 1) = k + 1. The tactic `omega` is a decision procedure for linear arithmetic over integers and naturals, and it proves this at once.
Each tactic builds a piece of a proof term. When all goals are closed, Lean builds the complete term and its kernel checks that the term has the type of the theorem. If you wrote `rfl` where the two sides are not equal, Lean would stop with an error and show the goal. This is the usual working loop: look at the goal, choose a tactic, read the new goals, and repeat.
Now a scaled-up example in words. A team wants to show that a policy engine never allows a request that a "forbid" rule denies. They write the engine in Lean as a function from a policy set and a request to a decision. They state a theorem: for every policy set and request, if some forbid rule matches, the decision is deny. The proof goes by cases on the rule list and uses induction over it. The Cedar team reports that in doing such proofs for their validator, they found and fixed 4 bugs, and that differential random testing between the Lean model and the Rust code found 21 more.
For scale, the seL4 proof is about 200,000 lines of proof script for roughly 10,000 lines of kernel code. That is about 20 lines of proof for each line of code, which is the typical cost of full functional correctness. This is why teams verify a small core and not a whole application.
intuition: A proof assistant is a very strict referee who reads every line of your argument, never tires, and never takes your word for anything.
The design is natural because checking is much easier than finding. Finding a proof can need creativity, search and large effort. Checking a finished proof is a mechanical task. So the system lets you use any method to find the proof and keeps the part you must trust as small as possible. This is the same shape as many ideas in computing: a hard search with an easy check.
The link between programs and proofs is also natural. A type already says something about a program. A dependent type can say everything. Once types can express "this list is sorted", writing the program and proving it are the same activity.
mistakes: People often think a verified program has no bugs. In fact the proof covers only what the specification says, under the assumptions of the model. seL4's own team notes that the proof still depends on assumptions such as the hardware, the compiler and unverified boot code. A wrong or weak specification gives a correct proof of the wrong thing.
People often think a proof assistant finds the proof for you. In fact it checks proofs. It has automation for routine steps, and recent AI tools can suggest steps, but a human or a program must still give the proof. The kernel then accepts or rejects it.
People often think you must trust the whole proof assistant. In fact you trust only the kernel, plus the compiler and hardware that run it. Tactics and automation are outside the trusted base, because their results are re-checked.
People often think proof assistants are only for mathematicians. In fact large industrial results exist: seL4 for operating systems, CompCert for compilers, and Cedar for authorization. The cost is high, so the method is used for small and critical cores.
People often think Lean, Rocq and Isabelle are the same tool with different names. In fact their logics differ. Lean and Rocq use dependent type theory, and Isabelle/HOL uses simple higher-order logic with a separate proof language. This changes how you write statements, how much automation you get and which libraries exist.
tradeoffs: Choose a proof assistant when the cost of one bug is very high and the core is small, for example an OS kernel, a compiler, a cryptographic routine or an authorization engine. You pay roughly 10 to 20 lines of proof for each line of code, as in seL4, and you need engineers who can write proofs. Choose tests, property-based testing and model checking when the system is large, changes often, or a bug costs money but not lives. You give up certainty for coverage and speed.
Choose the Cedar-style approach, a proved model plus a fast production implementation checked by differential testing, when you want proofs but must ship in a mainstream language such as Rust. You give up a proof about the real code: the proof covers the model, and testing links the model to the code. Choose full code verification, as in seL4 and CompCert, when you need the proof to cover the shipped code. You pay in effort and in being limited to a verified language or subset.
Choose Lean 4 when you want a modern language that is also a general programming language, a fast-growing mathematics library, and good editor support. Choose Rocq when you want a mature system with large verified projects such as CompCert, and a long record in programming language research. Choose Isabelle/HOL when you want strong automation through Sledgehammer, a structured proof language (Isar) that reads close to a paper proof, and the seL4 ecosystem. All three can do serious work; the choice is often about the library you need and the team you have.
Choose dependent types (Lean, Rocq) when you want types and proofs in one language and you like programs that carry their proofs. Choose simple types with classical logic (Isabelle/HOL) when you want more automation and a familiar logic, and you do not need types that depend on values. You give up the elegance of types that carry proofs in the second case, and you give up some automation and some predictable behaviour in the first.
friction: The first problem is effort. Proofs are long, and a change in code can break many proofs. Maintenance is a large share of the cost. Proof engineering, meaning how to structure large developments so that they survive change, is a field of its own.
The second problem is the specification. It is hard to write a statement that is both true and meaningful, and the proof cannot tell you if the statement is the right one. Reviewers must read the specification as carefully as code, and often it is the only thing a non-expert can check.
The third problem is the trusted base. The kernel is small but not zero, and the proof relies on the model of the language, the compiler and the hardware. Real bugs in kernels of proof assistants have been found, rarely, and independent checkers reduce the risk.
The fourth problem is the learning curve. You must learn the logic, the tactic language and the library. Automation is uneven: some goals close at once, and others need long manual steps that are hard to guess. Different systems also differ, and libraries do not move easily between them.
Finally, there are limits of scope. Performance, concurrency under real hardware conditions and the behaviour of machine learning models are hard to specify. Verifying a neural network against a useful property is far harder than verifying an operating system kernel, because the property itself is unclear.
practice: Start small and pick one system. For a software engineer, Lean 4 or Rocq with the free textbooks is a good start: Software Foundations (for Rocq) and "Functional Programming in Lean" or "Theorem Proving in Lean 4". Prove simple facts about lists and natural numbers by induction. This builds the habit of reading the goal and choosing tactics.
Learn to write specifications. Take a small function, such as sorting, and write down what it must do: the output is sorted, and it is a permutation of the input. Then prove it. This shows how much work even a simple property takes and what it means to cover all inputs.
At work, apply proofs where they pay. Good candidates are a parser of untrusted input, a core data structure, an authorization or policy decision, or a financial calculation. Write a precise model, prove its key properties, and test the production code against the model. This is the verification-guided approach used for Cedar. Use property-based testing for the parts you do not model.
Keep the statement small and readable. Keep proofs modular, use automation for routine steps, and avoid proofs that depend on exact tactic output, since they break when libraries change. Pin the version of the tool and the libraries, because proofs are sensitive to changes. Use continuous integration to re-check all proofs on every commit.
For learning, the Caltech and MIT courses (CS 128 and 6.5120) are good paths for programmers. The Lean community, with its Zulip chat and Mathlib, is helpful for questions.

Explain the Curry–Howard correspondence in one example. || A proof of "A implies B" is a function that takes a proof of A and returns a proof of B. Checking the proof is then type checking. With dependent types, a type like "sorted list of length n" says what the program guarantees, so the code and its proof live in one language.
A team says their kernel is verified. What questions do you ask? || What exactly is the specification, and who reviewed it? What is assumed: hardware, compiler, boot code, concurrency model? Does the proof cover the shipped code or a model? How is the proof kept up to date as the code changes? A correct proof of a weak specification gives little assurance.
Why did the Cedar team prove a Lean model and test the Rust code, instead of verifying the Rust? || Proving the Lean model is practical and finds real bugs (4 in the validator by proof). Production code in Rust is fast and idiomatic, and differential random testing against the model found 21 more bugs. The cost is that the proof covers the model and testing links it to the code, so the guarantee for the shipped code is not absolute.
When would you not use a proof assistant? || When the system is large and changes weekly, when the specification is unclear (for example, a recommender's quality), or when the cost of a bug is moderate. Tests, property-based testing, model checking and runtime monitoring give better coverage per unit of effort in those cases.
How does induction in a proof assistant relate to induction on paper? || The induction tactic produces the same two goals as the paper proof: the base case and the step case with the induction hypothesis in context. The kernel checks that the resulting term really uses the induction principle correctly, so a missing case or a circular argument is rejected.
quiz: What does the kernel of a proof assistant do? || It checks that each proof term follows the rules of the logic. It is small, and it is the only part that must be trusted.
Why is the specification the weak point of a verified system? || The proof only shows the code meets the statement as written. If the statement is wrong, incomplete or assumes too much, the proof is correct but does not give the safety you want.
How does Curry–Howard turn proof checking into type checking? || A statement is a type and a proof is a program of that type. Checking a proof then means checking that the term has the stated type, which is a simple algorithm.
The seL4 proof had about 200,000 lines of proof script for about 10,000 lines of code. What is the ratio? || About 20 lines of proof for each line of code.
Which would you choose to verify a small authorization engine written in Rust, and how? || Write an executable model in a proof assistant such as Lean, prove its key properties, then test the Rust code against the model with differential random testing, as the Cedar team did. Full verification of the Rust code is possible but much more costly.
