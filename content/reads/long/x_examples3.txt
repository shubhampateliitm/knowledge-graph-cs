@@+ gc
example: A JVM service has an 8 GB heap with G1, handles 2,000 requests per second, and each request allocates about 500 KB of short-lived objects (parsed JSON, strings, buffers): 1 GB of allocation per second. Objects are allocated by bumping a pointer in each thread's local allocation buffer, which costs a few nanoseconds.
The young generation (say 2 GB of regions) fills in about 2 seconds. G1 then pauses application threads, finds live young objects by tracing from roots and from remembered sets (old-to-young references), and copies the survivors (perhaps 30 MB, since most request objects are already dead) to survivor regions. Cost is proportional to live data, not garbage, so this pause takes around 10–20 ms. Objects that survive several collections are promoted to old regions.
Suppose a cache in the service grows by 50 MB per minute and never evicts. Old regions fill; G1 starts concurrent marking at 45% heap occupancy, then mixed collections clean old regions with the most garbage. But the cache is live, not garbage, so old-generation space keeps shrinking until G1 cannot keep up and falls back to a full, stop-the-world collection of the whole heap, pausing for seconds; eventually an OutOfMemoryError. The fix is not a GC flag but bounding the cache. Switching the service to generational ZGC would shrink young and old pauses to under a millisecond, but it cannot rescue a heap whose live data keeps growing.

@@+ coordination
example: Three instances of a scheduler service must ensure only one runs scheduled jobs. Each instance, using etcd, creates a lease with a 10-second time-to-live and tries to create the key /scheduler/leader with its name, attached to the lease, using a transaction 'create only if the key does not exist'. Instance A succeeds (the key's creation revision is 1,204); B and C fail and instead watch the key.
A keeps its lease alive by refreshing it every 3 seconds. Whenever A starts a job, it passes revision 1,204 as a fencing token to the job store, which rejects any write tagged with a lower revision than the highest it has seen.
A's machine then freezes in a 15-second garbage-collection pause. Its lease expires, etcd deletes the key, and B and C are notified by their watch. B wins the next election with creation revision 1,219 and starts scheduling. When A wakes, it still believes it is leader for a moment and tries to write a job record with token 1,204; the job store rejects it because it has seen 1,219. A then notices its lease is gone and steps down. Without the fencing token, both A and B would have run jobs briefly, which is exactly the split-brain that coordination services exist to prevent, and why leases alone are not enough.

@@+ dl
example: Train a small image classifier on 50,000 labelled photos (cats, dogs, cars...) with a convolutional network of about 11 million weights (ResNet-18). Each step takes a mini-batch of 256 images, runs them forward through convolution, normalization and ReLU layers to produce 10 scores per image, turns scores into probabilities with softmax and computes the average cross-entropy loss.
Backpropagation then computes, in one backward pass, the gradient of that loss with respect to all 11 million weights, roughly twice the cost of the forward pass. The optimizer (SGD with momentum or AdamW) updates every weight slightly. One pass over the data (an epoch) is about 196 steps; training for 50 epochs is about 10,000 steps, which takes minutes to an hour on one modern GPU.
Watching the curves: training loss falls steadily; validation accuracy rises to around 90% and then flattens while training accuracy keeps climbing toward 100%: the model is starting to memorize. Data augmentation (random crops and flips), weight decay and early stopping push validation accuracy higher. Starting instead from a network pre-trained on millions of images and fine-tuning only for a few epochs typically beats training from scratch with far less compute: the reason pre-training and transfer learning dominate practice.

@@+ jvm
example: A Kafka broker's request-handling code calls a method that validates record batches. For the first couple of hundred calls, the JVM interprets its bytecode. With tiered compilation (the default), after about 200 invocations C1 compiles it quickly with profiling code that records which branches are taken and which classes appear at each call site; after several thousand more (thresholds are tunable, and about 5,000 invocations is typical), C2 recompiles it with aggressive optimizations: it inlines the small helper methods, sees that a call to an interface method always lands on one implementation and calls it directly, proves that a temporary object never escapes the method and removes its allocation, and unrolls a loop over bytes.
The compiled code is then about as fast as hand-written C for that path. If a new class later appears at that call site (say, a different compression codec), the speculation fails, the JVM deoptimizes back to the interpreter for that method and recompiles with the new profile; the brief slowdown is visible as a latency blip.
Meanwhile, the broker's heap is sized at 6 GB in a 32 GB container. The rest of memory is left mostly for the operating system's page cache, which holds recent log segments; Kafka deliberately keeps message data out of the JVM heap so that garbage collection stays short and consumers are served from the page cache via sendfile. A broker with a 28 GB heap would have less page cache, more GC work and slower consumers: an example where understanding the JVM leads to giving it less memory.

@@+ nvgpu
example: Training a 7-billion-parameter model on 1 trillion tokens needs about 6 × 7×10⁹ × 10¹² ≈ 4.2×10²² floating-point operations (the 6ND rule of thumb). An H100 delivers roughly 10¹⁵ dense BF16 FLOP/s at peak; at a realistic 40% utilization, 4×10¹⁴. One GPU would take about 10⁸ seconds (over 3 years); 256 GPUs take about 4.7 days.
Memory: the weights in BF16 take 14 GB, gradients another 14 GB, and AdamW's two moment estimates plus FP32 master weights about 84 GB more, over 110 GB in total, more than one 80 GB GPU. Sharding optimizer state and gradients across GPUs (ZeRO or FSDP) brings each GPU's share down to a few GB, leaving room for activations.
Communication: with data parallelism across 256 GPUs, every step all-reduces 14 GB of gradients. @@+ redis
example: A rate limiter allows each API key 100 requests per minute. For each request, the service runs a small Lua script (or MULTI/EXEC) on Redis: INCR rate:{key}:{current_minute}; if the result is 1, EXPIRE the key after 60 seconds; if the result exceeds 100, reject. @@+ consensus
example: A three-node etcd cluster in one region stores Kubernetes state. Each write (say, creating a pod object) goes to the leader, which appends it to its log, sends it to the two followers, and waits for one of them to persist it (2 of 3 is a majority). With 0.5 ms network round trips and 1 ms fsyncs, a commit takes about 2–3 ms, so the cluster handles thousands of small writes per second.
If one follower's disk becomes slow (fsync at 50 ms), commits still proceed using the other follower; the slow one falls behind. If the leader's disk becomes slow, every commit slows to its speed, heartbeats are delayed, and followers may start elections: leader churn is the classic symptom of slow disks in consensus systems.
Spread the same cluster across three regions 80 ms apart and every write needs at least one cross-region round trip: 80 ms or more. Add two more nodes (five in total) and you can survive two failures, but each write now waits for three nodes, usually including a farther one. This is the CAP and PACELC trade-off in numbers: consistency is bought with latency, and the price is set by distance and disks.

@@+ linalg
example: A recommendation system represents 10 million users and 1 million items with 64-dimensional vectors. Scoring one user against all items is a matrix–vector product: a 1,000,000 × 64 matrix times a 64-vector, 64 million multiply-adds, reading 256 MB of item vectors (float32). On a GPU with 2 TB/s of bandwidth this takes about 0.13 ms just to read the data, while the arithmetic would take far less: it is memory-bound.
Scoring 1,000 users at once is a matrix–matrix product (1,000,000 × 64 times 64 × 1,000): 64 billion multiply-adds, but the item matrix is read once for all 1,000 users. Now arithmetic dominates and the GPU's tensor cores run near peak; the arithmetic per user is unchanged, but the item matrix is read once for the whole batch, so memory traffic per user falls about 1,000-fold and the time per user drops by roughly two orders of magnitude. Batching turns memory-bound work into compute-bound work, the same reason LLM servers batch many users together.
Where do the vectors come from? Factorizing the sparse user × item interaction matrix (or training a two-tower network) finds a low-rank approximation: 10 million × 1 million interactions summarized by 64 numbers per user and per item. The singular value decomposition tells you how much information each extra dimension captures, which is how teams decide whether 64 or 256 dimensions are worth the memory.

@@+ memhier
example: Sum 100 million 4-byte integers (400 MB). Stored in an array and read sequentially, the hardware prefetcher streams cache lines ahead of use; the loop is limited by memory bandwidth, perhaps 20 GB/s for one core, so it takes about 20 ms, and with SIMD the arithmetic is nearly free.
Store the same numbers in a linked list of nodes scattered around the heap. Each step follows a pointer to an unpredictable address: a likely cache miss and a DRAM access of about 100 ns, and the CPU cannot prefetch because it does not know the next address until it loads the current node. 100 million misses × 100 ns = 10 seconds: 500 times slower for the same arithmetic.
This is why columnar engines store values in arrays, why B-trees use wide nodes, why hash tables with open addressing beat chained ones in practice, and why Java's array-of-objects can be much slower than a primitive array. At the next level, if the 400 MB array were on an NVMe SSD instead of in RAM, a sequential read at 3 GB/s would take about 130 ms, but random 4 KB reads would take about 100 µs each, again punishing random access.

@@+ transistor
example: An inverter (NOT gate) in CMOS uses two transistors: a p-type MOSFET connecting the output to the supply voltage (say 0.75 V) and an n-type MOSFET connecting it to ground. When the input is high, the n-type transistor conducts and the p-type does not, so the output is pulled to 0 V; when the input is low, the reverse happens. In either steady state, almost no current flows from supply to ground; energy is used mainly when the output switches and its capacitance is charged or discharged.
Each switch costs about \( C \times V^2 \) of energy. With a load capacitance of about 0.1 femtofarad and 0.75 V, that is roughly 5×10⁻¹⁷ joules. A chip with 10¹⁰ transistors, of which perhaps 10% switch every cycle at 3×10⁹ cycles per second, would use about 10¹⁰ × 0.1 × 3×10⁹ × 5×10⁻¹⁷ ≈ 150 W, which is the right order for a modern processor. Halving the voltage would cut that by four, which is why lowering voltage was the main lever for decades and why its end (around 2005) stopped clock speeds from rising.
Leakage adds power even when nothing switches: thin gate oxides and short channels let electrons tunnel or leak, which is why modern transistors wrap the gate around the channel (FinFETs, nanosheets) and use high-k dielectrics. Gates built from these switches form adders, registers and caches; billions of them, printed by lithography and wired by copper, make a GPU.

@@+ probability
example: A cluster has 2,000 servers; each fails independently on a given day with probability 0.001. The expected number of failures per day is 2,000 × 0.001 = 2. The probability of no failures at all in a day is 0.999²⁰⁰⁰ ≈ e⁻² ≈ 13.5%: most days, something breaks. That is why large systems treat failure as normal.
A Kafka partition is replicated on 3 brokers. If each broker independently has a 0.1% chance of being down at a given moment, the chance all three are down is 10⁻⁹. But failures are rarely independent: if all three share a rack and the rack's power fails (probability 0.01% per day), they fail together. Spreading replicas across racks or zones restores the independence the arithmetic assumes.
A Bloom filter with 10 bits per key and 7 hash functions: after inserting n keys into m = 10n bits, each bit is still 0 with probability about e^(−7/10) ≈ 0.50; a query for an absent key finds all 7 bits set with probability about 0.50⁷ ≈ 0.8%. A HyperLogLog with 2,048 registers has standard error 1.04/√2048 ≈ 2.3%. Each of these is a few lines of probability, and each decides real memory budgets.

After the node's heartbeats stop for about 50 seconds (the default node-monitor-grace-period in current releases; older releases used 40 seconds), the node controller marks it NotReady; its pods are evicted after a timeout, the ReplicaSet controller sees only 2 running replicas and creates a new pod, and the scheduler places it elsewhere. No human ran a script: each controller simply kept comparing desired and actual state. An update to the image triggers a rolling update: one new pod is created and must become ready before an old one is removed, so a broken image stalls the rollout instead of taking the service down.

example: An ad-fraud detector flags devices that generate more than 50 clicks in any 10-minute session window, reading click events from Kafka.
Events are keyed by device ID, so all clicks of one device reach the same parallel task, which keeps per-device state: the start of the current session and a click count. Session windows close after 2 minutes of inactivity. A watermark set 30 seconds behind the latest event time decides when a session is complete. When device d9's 51st click arrives within one session, the operator emits an alert immediately (an early trigger), and the final session count is emitted when the watermark passes the session's end plus the gap.
Clicks from a phone that was offline arrive 5 minutes late. They fall in a session that has already closed: depending on configuration they are dropped, sent to a side output for later correction, or allowed through an 'allowed lateness' period that updates the result and sends a correction downstream. The pipeline checkpoints state and Kafka offsets every 30 seconds; after a crash, it restores and replays from the checkpoint, and because its alerts go to a transactional Kafka sink, no alert is duplicated. The trade-off triangle is visible: shorter watermark delay gives faster alerts but more late data; longer delay gives completeness at the cost of latency and state.
