@@+ tcp
history: Vint Cerf and Bob Kahn described the Transmission Control Program in 1974; it was later split into TCP (reliable streams) and IP (best-effort packets), and the ARPANET switched to TCP/IP on 1 January 1983. In 1986 the young internet suffered 'congestion collapse', with throughput between Berkeley sites dropping about a thousandfold; Van Jacobson's 1988 algorithms (slow start, congestion avoidance, better retransmission timers) saved it and are still the basis of TCP behaviour.
Later decades refined rather than replaced it: window scaling and selective acknowledgements for fast long-distance links, CUBIC (Linux default since 2006) and BBR (2016) for congestion control, TCP Fast Open, and data-centre variants such as DCTCP. Because middleboxes and operating-system kernels made TCP very hard to change, Google built QUIC on UDP instead, and HTTP/3 now carries much web traffic over it. TCP remains the transport for most databases, Kafka, RPC frameworks and service-to-service traffic.
practice: For services, reuse connections (pooling, keep-alive) to avoid handshake and slow-start costs on every request, especially across regions. Set timeouts explicitly at every layer, and understand which ones fire first: connect timeout, read timeout and the application's own deadline. On high-latency, high-bandwidth links (cross-region replication, Kafka MirrorMaker), check that socket buffers are large enough for the bandwidth–delay product.
When debugging latency, separate network time from server time: compare round-trip time with request time, and look at retransmissions (ss -ti on Linux shows per-connection RTT, congestion window and retransmits). Many 'slow database' problems are actually retransmissions on a congested or lossy path.

@@+ vmem
history: Virtual memory was invented for the Atlas computer at the University of Manchester (1959–1962), which automatically moved pages between core memory and a magnetic drum, creating the illusion of one large memory. IBM's System/360 Model 67 and Multics (1960s) developed segmentation and paging further; Peter Denning's working-set model (1968) explained why paging works and how thrashing happens. Unix adopted paging on the VAX (BSD, late 1970s), and since then every general-purpose operating system has relied on it.
Hardware support grew alongside: translation lookaside buffers (TLBs) to cache translations, multi-level page tables for large address spaces, large pages (2 MB and 1 GB on x86-64) to reduce TLB misses, and nested page tables for virtual machines. The idea now reaches far beyond operating systems: GPUs have unified virtual memory, databases use it for buffer management ideas, and vLLM's PagedAttention applied it to the KV cache of language models in 2023.
how: Each process sees virtual addresses. The memory management unit translates them to physical addresses by walking page tables, typically four or five levels on x86-64, each level indexed by a slice of the address. Because a full walk costs several memory accesses, recent translations are cached in the TLB; a TLB miss costs tens to hundreds of cycles. Each page-table entry also carries permissions (read, write, execute, user or kernel) and status bits (present, accessed, dirty) that the kernel uses for protection, copy-on-write and page replacement.
Copy-on-write makes fork() cheap: parent and child share pages marked read-only until one writes, when the kernel copies just that page. Memory-mapped files and the page cache share the same machinery, so a file can be accessed as memory. Overcommit lets processes reserve more virtual memory than physically exists, betting that not all of it will be touched; when the bet fails, Linux's out-of-memory killer ends a process.
practice: For memory-heavy services (JVM data systems, databases, model servers), watch resident memory, page faults and swap activity, not just heap usage. Container memory limits count page cache and off-heap memory, which is why a JVM with a modest heap can still be killed. Consider huge pages for large in-memory databases and JVM heaps to reduce TLB misses, but test, because transparent huge pages can cause latency spikes during compaction.
Understand fork-and-copy-on-write behaviour in systems that snapshot by forking (Redis RDB persistence): a write-heavy workload during a snapshot can nearly double memory use.
ref: paper | The Working Set Model for Program Behavior | Peter Denning, CACM 1968 |
ref: book | Operating Systems: Three Easy Pieces, chapters on address translation and paging | Arpaci-Dusseau | https://pages.cs.wisc.edu/~remzi/OSTEP/

@@+ memhier
history: Maurice Wilkes proposed 'slave memories', the first caches, in 1965; IBM's System/360 Model 85 (1968) shipped one. As processors sped up much faster than DRAM, the gap (the 'memory wall', named by Wulf and McKee in 1995) forced ever deeper hierarchies: on-chip L1 and L2 caches in the 1990s, shared L3 caches with multicore chips in the 2000s, and stacked high-bandwidth memory beside GPUs in the 2010s. AMD's 3D V-Cache (2022) stacked extra cache directly on top of CPU cores.
Software adapted in waves. Cache-conscious data structures and algorithms (cache-oblivious algorithms, 1999), columnar databases and vectorized execution (2005), and IO-aware deep-learning kernels such as FlashAttention (2022) all come from treating data movement, not arithmetic, as the main cost. Today the hierarchy runs from registers through caches, DRAM, CXL-attached memory, local SSDs, network storage and object storage, and most performance engineering is about which level your working set lives in.
how: Approximate numbers on a modern server: L1 hit about 1 ns (32–64 KB per core), L2 about 3–5 ns (1–2 MB), L3 about 10–40 ns (tens to hundreds of MB, shared), DRAM about 80–120 ns, NVMe SSD read about 20–100 µs, network round trip in a data centre about 50–500 µs, cross-region about 50–150 ms. Bandwidth falls similarly: hundreds of GB/s from caches, about 100–500 GB/s from DRAM per socket, several TB/s from GPU HBM.
Caches work because of locality: temporal (recently used data is used again) and spatial (nearby data is used next). Data moves in 64-byte lines; hardware prefetchers detect sequential or strided patterns and fetch ahead. Misses are classified as compulsory (first touch), capacity (working set too big) and conflict (addresses mapping to the same set). On multicore chips, coherence keeps cached copies consistent, at the cost of traffic when cores share data that is written.
practice: Ask where your working set lives. If a hot index or table fits in RAM (or the page cache), performance is predictable; if it spills to disk or the network, expect a step change in latency. Lay data out for sequential access (arrays, columns, sorted files) rather than pointer chasing. Avoid false sharing in concurrent code by padding per-thread counters to separate cache lines.
Measure rather than guess: hardware counters (perf stat for cache misses, memory bandwidth) and flame graphs show when a program is memory-bound. On GPUs, compute arithmetic intensity and compare with the roofline to see whether more FLOPs or fewer bytes would help.
ref: paper | Hitting the Memory Wall: Implications of the Obvious | Wulf & McKee, ACM SIGARCH Computer Architecture News 1995 |
ref: paper | Cache-Oblivious Algorithms | Frigo, Leiserson, Prokop & Ramachandran, FOCS 1999 |

@@+ linalg
history: Systems of linear equations were solved in ancient China (the Nine Chapters, with a method equivalent to Gaussian elimination). Matrices and determinants were developed in the 18th and 19th centuries by Leibniz, Cramer, Gauss, Cayley and Sylvester; Grassmann and Peano defined abstract vector spaces. Quantum mechanics (1925 onwards) made linear algebra the language of physics.
Computing turned linear algebra into an industry. Numerical analysts (Turing, von Neumann, Wilkinson) studied rounding errors in matrix computations in the 1940s–1960s. The BLAS (1979) and LAPACK (1992) libraries standardized fast routines, and hardware vendors still tune them for every new chip. Google's PageRank (1998) was an eigenvector computation on the web graph. Deep learning made dense matrix multiplication the most important computation in the world; GPUs, tensor cores and TPUs are machines built to do it.
how: Most computing uses a few operations. Matrix–vector and matrix–matrix multiplication apply linear transformations (every neural network layer, every attention score). Solving linear systems and least squares fits models (regression). Eigen-decomposition and the singular value decomposition find a matrix's natural directions and their strengths: PCA, PageRank, spectral clustering, low-rank approximation and LoRA adapters all rely on them. Norms and inner products measure size and similarity (cosine similarity of embeddings).
The cost model is just as important as the algebra. Multiplying two n×n matrices takes about 2n³ floating-point operations but touches only 3n² numbers, so large multiplications have high arithmetic intensity and run near peak speed on GPUs; matrix–vector products touch as many numbers as they compute with, so they are memory-bound. That single fact explains why LLM training is compute-bound while single-user LLM decoding is memory-bound.
practice: Think in shapes. Before reading any model code, write down the shapes of the main tensors (batch, sequence, heads, dimensions) and the size of each matrix multiplication; most performance and memory questions answer themselves. Use library routines (BLAS, cuBLAS, PyTorch operators) instead of loops, and batch small operations into large ones.
For data work, low-rank structure is everywhere: embeddings, recommendation matrices and many feature sets can be compressed with SVD or PCA with little loss. For numerical stability, prefer QR or SVD-based solvers over explicitly inverting matrices.

@@+ probability
history: Probability theory began with gambling problems: Pascal and Fermat's letters (1654) on dividing stakes in an unfinished game. Bernoulli proved the first law of large numbers (1713), Bayes and Laplace developed inverse probability (1763, 1812), and Gauss and Laplace established the normal distribution and the central limit theorem. Kolmogorov's axioms (1933) gave probability a rigorous foundation in measure theory.
Computing has used probability from the start: Monte Carlo methods at Los Alamos (1940s), Shannon's information theory (1948), randomized algorithms (1970s), probabilistic data structures such as Bloom filters (1970), hashing analysis, queueing models of networks, and the probabilistic reasoning of modern AI, from Bayesian networks (1980s) to language models that output a probability distribution over every next token.
how: A few tools carry most of the work. Random variables and their distributions (Bernoulli, binomial, Poisson, exponential, normal, power-law) model events. Expectation is linear (the expected sum is the sum of expectations, even for dependent variables), which makes many analyses short. Variance and concentration inequalities say how far results stray from the expectation. Conditional probability and Bayes' rule update beliefs with evidence. Independence assumptions simplify models but are where many real-world errors come from.
In systems, probability explains hash collisions (the birthday bound), load balance under random placement (the 'power of two choices'), false-positive rates of Bloom filters, the accuracy of sketches and samples, queueing delays and failure rates in large clusters (if one machine fails once in three years, a cluster of 10,000 sees several failures a day).
practice: Make uncertainty explicit. When you report a metric from a sample or an experiment, report its confidence interval. When you size a system, model peaks and tails (p99, p999), not averages, and check whether your data is heavy-tailed, in which case averages are misleading. When something 'random' fails often, check the independence assumption: correlated failures (same rack, same deploy, same bug) are far more common than independent ones.
Build intuition with quick simulations: a few lines of Python estimating a collision rate or a tail latency often settle a design debate faster than algebra.

@@+ infotheory
history: Claude Shannon's 'A Mathematical Theory of Communication' (1948) created the field in one paper: entropy as the measure of information, the source coding theorem (data cannot be compressed below its entropy), and the noisy-channel coding theorem (reliable communication is possible up to a channel's capacity). Earlier work by Nyquist and Hartley (1920s) had measured information in telegraph systems. Huffman coding (1952), arithmetic coding (1970s) and Lempel–Ziv compression (1977–1978) turned the source theorem into practical tools; turbo codes (1993) and LDPC codes (rediscovered in the 1990s) finally approached the channel limit.
Information theory then spread far beyond communication: Kolmogorov complexity (1960s), the minimum description length principle, cross-entropy loss and KL divergence in machine learning, mutual information in feature selection and contrastive learning, and the view that language modelling is compression. Every Zstd file, video stream, 5G link and LLM training run uses its results.
how: Entropy H(X) = −Σ p(x) log₂ p(x) is the average number of bits needed to encode outcomes of X with the best possible code; it is highest when outcomes are equally likely. Cross-entropy H(p, q) is the average bits needed if you encode data from p using a code designed for q; the excess over H(p) is the KL divergence, always non-negative. Training a classifier or a language model by minimizing cross-entropy is therefore making its predictions an efficient code for the data. Mutual information I(X; Y) measures how much knowing one variable reduces uncertainty about another.
Channel capacity, C = B log₂(1 + S/N) for a bandwidth-limited channel with Gaussian noise, sets the maximum reliable rate; modulation and error-correcting codes are ways to approach it. Rate–distortion theory extends compression to lossy codecs: how few bits are needed for a given quality, which is exactly the trade-off video encoders make.
practice: Use entropy as a quick estimator. Before choosing an encoding for a column, count distinct values and their frequencies: low-entropy columns (status codes, countries) compress enormously with dictionaries; high-entropy ones (random IDs, hashes) barely compress at all. For model training, report loss in bits per token or perplexity to compare runs meaningfully.
When reasoning about prompts and contexts, remember the information view: tokens that are predictable from the rest add little; tokens that carry unique facts are what the model needs.
ref: book | Elements of Information Theory, 2nd ed. | Cover & Thomas, 2006 |
ref: book | The Information: A History, a Theory, a Flood | James Gleick, 2011 |

@@+ transistor
history: Julius Lilienfeld patented the idea of a field-effect transistor in 1925, but materials of the time could not make it work. At Bell Labs, John Bardeen and Walter Brattain demonstrated the point-contact transistor in December 1947, and William Shockley invented the junction transistor soon after; all three shared the 1956 Nobel Prize. Mohamed Atalla and Dawon Kahng built the first practical MOSFET at Bell Labs in 1959, the same period in which Jack Kilby (Texas Instruments) and Robert Noyce (Fairchild) invented the integrated circuit.
CMOS logic (Frank Wanlass, 1963) paired n-type and p-type transistors so that almost no current flows except while switching, which made dense, low-power chips possible. Gordon Moore's 1965 observation and Robert Dennard's 1974 scaling rules described decades of shrinking. When planar transistors leaked too much, the industry moved to high-k metal gates (2007), FinFETs (Intel 2011, then others) and gate-all-around nanosheets (Samsung from 2022; Intel and TSMC around 2025). The MOSFET is now the most manufactured device in history, with well over 10²² made.
how: A MOSFET has a source and a drain (heavily doped regions) separated by a channel, with a gate above the channel insulated by a thin oxide. In an n-type MOSFET, a positive gate voltage attracts electrons to the surface of the p-type silicon beneath, forming a conducting channel: the switch is on. Remove the voltage and the channel disappears: the switch is off. The threshold voltage, the gate's control over the channel and leakage when 'off' determine speed and power.
Power consumption explains modern chip design. Dynamic power is roughly capacitance × voltage² × frequency, so lowering voltage saves power quadratically. Dennard scaling let each generation shrink dimensions and voltage together, keeping power density constant; once voltage could no longer drop (because of leakage and the threshold voltage), clock speeds stalled near 3–5 GHz, and extra transistors went into more cores, bigger caches and specialized units such as GPUs and tensor cores.
practice: For software engineers, the practical lessons are economic. Performance gains now come from parallelism, specialization and efficiency rather than from faster single cores, so software that parallelizes well and uses accelerators keeps benefiting from new chips. Energy is a first-class cost: in data centres and on phones, the cheapest operation is the one you avoid, and data movement costs more than computation.
When evaluating hardware, look past 'process node' names (which no longer describe a physical size) to measured performance per watt and memory bandwidth for your workload.

@@+ queueing
history: Agner Krarup Erlang, an engineer at the Copenhagen Telephone Company, founded queueing theory around 1909–1917 to work out how many telephone lines and operators were needed. David Kendall introduced the A/B/c notation (1953), and John Little proved Little's law in 1961. Leonard Kleinrock's queueing models of packet-switched networks (1960s) helped justify the ARPANET design.
In computing, queueing theory became the basis of capacity planning and performance engineering: the 'universal scalability law', tail-latency analysis in large services (Dean and Barroso's 'The Tail at Scale', 2013), and the design of schedulers, load balancers and autoscalers. Every message queue, thread pool, connection pool, Kafka consumer group and LLM serving batch is a queue, whether or not its designers wrote down the model.
how: Little's law, L = λW, says the average number of items in a stable system equals the arrival rate times the average time each spends inside; it holds for almost any queue and needs no assumptions about distributions. For a single server with random (Poisson) arrivals and random (exponential) service times, the M/M/1 model, the average time in the system is 1/(μ − λ), so with utilization ρ = λ/μ, waiting time grows like ρ/(1 − ρ): at 50% utilization a request waits about as long as its service time, at 90% nine times as long, at 99% ninety-nine times.
Variability makes everything worse: the Pollaczek–Khinchine formula shows waiting time grows with the variance of service times, so a few slow requests hurt everyone. Multiple servers sharing one queue (M/M/c) perform much better than separate queues per server, which is why a single shared queue (or work stealing) beats random assignment. In fan-out systems, the response time is the maximum of many service times, so tail latency dominates.
practice: Run critical resources (disks, brokers, database CPUs, GPU servers) well below saturation, typically at 60–70% peak utilization, and treat the last 20% of capacity as a latency budget, not spare capacity. Use Little's law to size pools: concurrent requests in flight = requests per second × latency; if your connection pool or thread pool is smaller, requests will queue.
Measure queue depth and wait time directly (Kafka consumer lag, request queue time, pending tasks) because they warn of saturation earlier than CPU graphs. Reduce variability as well as averages: cap request sizes, separate slow and fast work into different queues, and use timeouts and load shedding so overload produces fast failures instead of unbounded waits.
ref: book | Performance Modeling and Design of Computer Systems: Queueing Theory in Action | Mor Harchol-Balter, 2013 |
ref: paper | A Proof for the Queuing Formula: L = λW | John Little, Operations Research 1961 |
