@@ spark-sss
value: Spark Structured Streaming lets you write a streaming job with the same DataFrame and SQL code as a batch job. Spark treats the stream as an unbounded input table: every new event is a new row appended to it. Your query defines a result table, and Spark keeps that result up to date by running the query again and again, each time only over the rows that arrived since the last run. You do not write code for offsets, retries, state files or recovery; the engine does that from a checkpoint directory.
A team that wants fresh numbers (a dashboard that is 30 seconds old, a fraud flag, a per-campaign spend counter, a feature table for a model) must otherwise write a long-running program that reads a log, keeps running totals, handles late events, survives crashes and does not double-count. For teams already on Spark and Databricks, Structured Streaming is the simplest route to streaming ETL: read Kafka, clean and join, and write Delta tables with exactly-once results. In ad tech this is the usual path for impression and click ingestion, pacing counters and CTV event pipelines.
It stands on three lower concepts. Apache Spark gives it the Catalyst planner and the same execution engine as batch SQL, so a streaming query gets the same optimizer, code generation and connectors. Apache Kafka is the usual source and sink: a partitioned, replayable log whose offsets Spark records in its checkpoint, so any batch can be re-read exactly. Stream processing (L1) gives the ideas it implements: operators over unbounded data, keyed state, event time, windows and watermarks. For the layer above, it is the engine under Databricks streaming tables and Lakeflow Declarative Pipelines. Since Spark 4.1 (December 2025), Real-Time Mode brings latency down from seconds to milliseconds for some queries.
terms: Micro-batch — a small Spark job that processes only the input that arrived since the previous one; the default execution model.
Trigger — the rule for when the next micro-batch starts: as soon as possible, every N seconds, once over all available data, or in real-time mode.
Offset — a position in a source, such as (topic, partition, offset) in Kafka; a pair of offsets names exactly which records one batch read.
Checkpoint location — a directory in durable storage holding the offset log, the commit log, query metadata and state files; it is the query's memory across restarts.
State store — a versioned key–value store, one per shuffle partition per stateful operator, holding running aggregates, join buffers or seen keys between batches.
Event time — the time an event happened, carried inside the record, as opposed to processing time, when Spark sees it.
Watermark — a moving threshold, the maximum event time seen minus a chosen delay; Spark assumes older data will not arrive, so it can close windows and drop state.
Output mode — append (emit only final new rows), update (emit rows that changed in this batch) or complete (emit the whole result every time).
Real-Time Mode — a trigger added in Spark 4.1 that runs long-lived tasks and passes records through without waiting for batch boundaries.
history: Spark's first streaming API was Spark Streaming, described by Matei Zaharia and colleagues in "Discretized Streams" (SOSP 2013). It cut the stream into small batches of RDDs (DStreams) and reused Spark's lineage-based recovery. Its gaps were real: time meant processing time, not event time; the API was separate from DataFrames and SQL; and exactly-once output was left to the user. In 2015 Google's Dataflow model paper (Akidau et al., VLDB 2015) gave the field a clear vocabulary of event time, windows, watermarks and triggers.
Structured Streaming was the answer. Michael Armbrust, Tathagata Das, Reynold Xin, Matei Zaharia and others at Databricks designed it as "streaming as incremental SQL". It arrived as an alpha in Spark 2.0 (July 2016) and was declared production-ready in Spark 2.2 (July 2017). Spark 2.3 (2018) added stream–stream joins and an experimental continuous processing mode. The SIGMOD 2018 paper reported 65 million records per second on the Yahoo Streaming Benchmark on a 40-core cluster, about twice Apache Flink and 90 times Kafka Streams in that setup.
Later releases filled operational gaps. Spark 3.2 (2021) added a built-in RocksDB state store, so state could grow beyond the JVM heap, and session windows. Databricks' Project Lightspeed (2022) then drove latency and state work: Spark 3.3 added Trigger.AvailableNow and Spark 3.4 asynchronous progress tracking and multiple stateful operators per query. Spark 4.0 (May 2025) added transformWithState, a new API for arbitrary state with timers and time-to-live, and a state data source for reading state as a table. Spark 4.1 (December 2025) added Real-Time Mode for stateless Scala queries from Kafka; Spark 4.2 (July 2026) brought it to PySpark and added stable source and sink names, so sources can change without breaking checkpoints. DStreams are now marked legacy.
how: You write spark.readStream (for example from Kafka), apply DataFrame operations, and call writeStream with a sink, a trigger, an output mode and a checkpoint location. Spark, the first concept this one stands on, parses the query with Catalyst exactly as it would a batch query. The difference is in execution: for each micro-batch, Spark replaces the streaming source in the logical plan with a bounded DataFrame for the new offset range and plans that batch. Stateful operators get extra nodes that restore state before the batch's rows are processed and save it after. Everything else (whole-stage code generation, shuffles, the Parquet and Delta writers) is the normal batch engine.
Each micro-batch follows a strict order. First, the driver asks every source for its latest available offsets; for Kafka this is the latest offset of each partition, optionally capped by maxOffsetsPerTrigger. Second, it writes batch number N and the start and end offsets into the file offsets/N in the checkpoint. This is a write-ahead log: the plan for the batch is durable before any work starts. Third, it runs the batch as an ordinary Spark job. Fourth, the sink writes the output. Fifth, the driver writes commits/N. Kafka, the second concept it stands on, is what makes the offset log useful: because Kafka keeps records addressable by offset for its retention period, Spark can read exactly the same range again after a failure. Spark does not commit offsets to a Kafka consumer group; the checkpoint is the only source of truth.
Recovery is then simple. On restart, if batch N appears in offsets but not in commits, it re-runs batch N with the same offsets, the same plan and the same state version, so it produces the same output. Re-running is safe only if the sink is idempotent. The Delta sink records the query ID and batch ID in the Delta transaction log and skips a batch it has already committed. In foreachBatch you get the same effect with the Delta options txnAppId and txnVersion, or a MERGE on a unique ID. The built-in Kafka sink is only at-least-once: after a crash, it may write some records twice. "Exactly-once" therefore means replayable source plus deterministic re-execution plus idempotent or transactional sink.
Stateful operators (streaming aggregation, dropDuplicates, stream–stream joins, flatMapGroupsWithState and transformWithState) carry data between batches. The rows are shuffled by key into spark.sql.shuffle.partitions partitions, and each partition of each operator has its own state store. Version N of a store is the state after batch N. The default provider keeps the state in a hash map in the executor's JVM heap, writes a delta file of changed keys to the checkpoint each batch, and writes periodic snapshots. The RocksDB provider keeps state in native memory and local disk (an LSM tree), uploads its files to the checkpoint, and with changelog checkpointing writes only the changes per batch. Millions of keys on the JVM heap cause long garbage-collection pauses, so large state belongs in RocksDB. The number of state partitions is fixed when the checkpoint is created and cannot change later.
Stream processing, the third concept, supplies the time model. You group by window(eventTime, "10 minutes") and declare withWatermark("eventTime", "30 minutes"). At the end of each batch, Spark computes the watermark as the maximum event time seen minus the delay, and uses it in the next batch. A window whose end is below the watermark is final: in append mode it is emitted once and its state is deleted. The guarantee is one-sided: an event less late than the delay is never dropped; an event later than that may be dropped. With several inputs, the global watermark is by default the minimum of their watermarks, so the slowest stream holds everyone back.
Output modes connect the result table to the sink. Append writes only rows that will never change, so aggregations in append mode need a watermark. Update writes only rows changed in this batch, which suits upserts. Complete rewrites the entire result each batch and is only for small aggregates.
Triggers set the rhythm. The default starts the next batch as soon as the previous one ends. ProcessingTime("1 minute") starts a batch every minute. AvailableNow processes everything currently available, possibly in several batches, and stops; it replaced Trigger.Once and turns a streaming query into an incremental batch job. The experimental continuous mode (2.3) offered about 1 ms latency but only at-least-once. Each micro-batch has a fixed planning and scheduling cost that sets a floor of roughly 100 ms. In Real-Time Mode, Spark launches one long-running task per Kafka partition, and records flow from source through operators to sink as they arrive, giving single-digit-millisecond p99 latency for stateless queries. The trigger duration (default 5 minutes, minimum 5 seconds) becomes only the checkpoint interval. In 4.1 and 4.2 it needs a Kafka source, update mode, a Kafka or foreach sink, and one free core per input partition. Stateful queries need a streaming shuffle between concurrently running stages; the development docs list aggregations and dropDuplicates for Spark 4.3.

example: A CTV pipeline reads impression events from a Kafka topic with 12 partitions at 30,000 events per second. It counts impressions per campaign in 10-minute tumbling windows by event time, with a 10-minute watermark, in append mode, and writes to Delta. The trigger is ProcessingTime("10 seconds").
Volume first. Each batch reads 30,000 × 10 = 300,000 events, about 25,000 per Kafka partition. If a batch takes 4 seconds, an event waits between 0 and 10 seconds for its batch to start and then 4 seconds of processing, so its latency is 4 to 14 seconds, about 9 seconds on average. If batches start taking more than 10 seconds, lag grows; that is the sign to add cores.
Now the watermark, step by step. Batch 1 contains events with event times 12:01 to 12:07. After it, the watermark is 12:07 − 10 min = 11:57. Batch 2 contains events from 12:05 to 12:12 and one late event at 11:58, which belongs to window [11:50, 12:00). The watermark in force is 11:57, below that window's end of 12:00, so the window is still open and the late event is counted. After batch 2, the maximum event time is 12:12, so the watermark becomes 12:02. In batch 3, the window [11:50, 12:00) has an end below 12:02, so Spark emits its final count to Delta and deletes its state. An event at 11:59 arriving in batch 3 is dropped, because its window is already closed. It was 13 minutes late, more than the 10-minute delay, so dropping it does not break the guarantee.
State size. Assume 5,000 active campaigns. A window stays in state from its first event until the watermark passes its end, which is about window length plus delay, 20 minutes, so roughly 3 windows per campaign are open at once: 15,000 rows. At about 100 bytes each, that is 1.5 MB, which is fine in the default store. If someone adds device_id to the grouping key with 50 million devices, state becomes 50 million × 3 × 100 bytes = 15 GB. Spread over 200 shuffle partitions that is 75 MB per partition; this needs the RocksDB provider and a careful look at whether the key is right.
Finally, recovery. Batch 42 logged partition 0 as offsets 1,000,000 to 1,025,000, wrote to Delta, and the driver crashed before commits/42. On restart Spark re-runs batch 42 over exactly those offsets with state version 41, and the Delta sink skips the write it already has. No impression is counted twice.
intuition: A stream is a table that keeps growing; Spark keeps re-answering your query, but only pays for the new rows.
The design is natural because most streaming questions are batch questions asked repeatedly: "count impressions per campaign per 10 minutes" has the same meaning whether you run it once over yesterday or continuously over today. If the engine can turn the query into an incremental plan, the user should not have to. Micro-batches make this cheap to build: each batch is an ordinary, deterministic Spark job over a known offset range, so recovery is "run that batch again", the same idea that made Spark itself fault-tolerant.
The checkpoint then works like a ledger. Before work starts, the plan is written down; after the output is safely stored, the batch is marked done. Anything between the two can be repeated, as long as repeating it is harmless. Watermarks add the last piece: a promise about how late data can be, which is what lets a never-ending query ever call a result final.
mistakes: People often think Spark commits its Kafka offsets to a consumer group, like a normal consumer. In fact the offsets live only in the checkpoint. Tools that measure lag through the consumer group show nothing useful unless you report progress yourself, for example from a StreamingQueryListener.
People often think "exactly-once" means no duplicates in any sink. In fact it means each batch's effect is applied once, which needs an idempotent or transactional sink. Delta is idempotent per batch; the Kafka sink and a custom foreach writer can produce duplicates after a failure.
People often think the trigger interval is the latency. In fact latency is the wait for the next batch plus the processing time, and a batch that runs longer than the interval delays all later ones. In Real-Time Mode the trigger duration is a checkpoint interval, not a latency target.
People often think a watermark drops every event later than the delay. In fact the guarantee is one-sided: events within the delay are always kept; later events are dropped only once their window's state has been removed.
People often think they can change any code and restart from the same checkpoint. In fact changing stateful operators, grouping keys, state schema or the number of shuffle partitions is not allowed, and before Spark 4.2 adding or reordering sources could also break recovery.
friction: Micro-batch latency has a floor of about 100 ms and is usually a few seconds in practice. Real-Time Mode removes that floor, but as of Spark 4.2 it supports only Kafka sources, update mode, a few sinks, no adaptive query execution, and it needs one dedicated core per input partition (plus cores for the stateful stage once that is supported). Flink still has more mature record-at-a-time stateful processing.
State is the main operational risk. A missing watermark, a high-cardinality key or an unbounded stream–stream join grows state until batches slow down or executors run out of memory. Because state partitions are fixed when the checkpoint is created, a query that outgrows its 200 partitions cannot simply be rescaled; you start a new checkpoint and rebuild state, often by reprocessing from Kafka, which only works if Kafka retention is long enough.
A lost or corrupted checkpoint means reprocessing from the source. Frequent triggers create many small files in Delta or Parquet, which slow readers and need compaction. On Databricks, Photon accelerates stateless streaming only; stateful operators run on the JVM path. Python stateful logic (transformWithStateInPandas) adds serialization cost between the JVM and Python.
practice: Give every query its own checkpoint location on durable storage, and never copy or share it. Decide spark.sql.shuffle.partitions before the first run of a stateful query, sized for future state, because you cannot change it later. Cap batch size with maxOffsetsPerTrigger (or maxFilesPerTrigger for files) so that a backlog after an outage is drained in steady batches rather than one huge one.
Put a watermark on every stateful aggregation and join, and choose the delay from measured lateness, not guesses. Use the RocksDB state store provider with changelog checkpointing when state exceeds a few million keys. Use the state data source (Spark 4.0+) to read state as a table when debugging. Write to Delta for exactly-once; in foreachBatch, make writes idempotent with txnAppId and txnVersion or a MERGE on a unique key.
Monitor each query's progress events: input rate versus processing rate (if processing is lower, lag grows), batch duration versus trigger interval, number of state rows and state memory, and the watermark value. Schedule OPTIMIZE or enable auto-compaction on streaming Delta tables. Use Trigger.AvailableNow when "every hour" freshness is enough; it gives streaming's incremental bookkeeping at batch cost. Choose Real-Time Mode only when you need sub-second latency and your query fits its limits, and run one such query per cluster.
quiz: Where does Structured Streaming store the Kafka offsets it has read? || In the offsets and commits logs in the query's checkpoint directory, not in a Kafka consumer group. The checkpoint is the only record of progress.
Why does writing offsets/N before running batch N make recovery safe? || The exact input range of batch N is durable before any output exists. After a crash, Spark re-runs batch N over the same offsets and state version, and an idempotent sink ignores the repeated write.
How does a watermark let Spark delete state for a windowed aggregation? || The watermark is the maximum event time seen minus the declared delay. Once a window's end is below it, Spark treats the window as final, emits it (in append mode) and removes its state.
A topic carries 20,000 events per second, the trigger is 15 seconds and each batch takes 6 seconds. How many events per batch, and what is the latency range? || 20,000 × 15 = 300,000 events per batch. An event waits 0 to 15 seconds for its batch and then 6 seconds of processing, so latency is about 6 to 21 seconds.
When would you choose Real-Time Mode, AvailableNow or a normal micro-batch trigger? || Real-Time Mode for sub-second needs such as fraud flags, if the query fits its limits (Kafka source, update mode, supported operators). AvailableNow when hourly freshness is enough and you want batch cost. A normal trigger for most streaming ETL that accepts seconds of latency.

@@ mapreduce
value: MapReduce is a programming model and a runtime for processing very large, fixed datasets on thousands of cheap machines that fail often. You write two functions. map takes one input record and emits zero or more (key, value) pairs. reduce takes one key and the list of all values emitted for it, and produces the output for that key. The framework does everything else: it splits the input, runs map tasks near the data, groups all pairs by key across the cluster (the shuffle), runs reduce tasks, writes the output, and re-runs any task whose machine dies.
The problem was real at Google in 2003. Building the web index, counting links and analysing logs meant reading tens of terabytes on hundreds or thousands of PCs, where some machine failed every day. Each team wrote its own distributed program and failure handling. MapReduce turned that into one well-tested library, so an engineer who knew only sequential programming could run a job over a petabyte. Through Hadoop it started the big-data era at Yahoo, Facebook, LinkedIn and most large enterprises between 2007 and 2015.
It stands on three lower concepts. HDFS stores the input and output: its 128 MB blocks become the input splits, its block locations tell the scheduler where to run each map, and its three replicas make the final output durable. Batch processing (L1) gives the contract: the input is finite and does not change during the job, so any task can be re-run and produce the same result. YARN gives the containers: each job gets an ApplicationMaster that asks YARN for map and reduce containers on chosen nodes. In 2026 MapReduce is legacy. Hadoop 3.5.0 (April 2026) still ships it, but new work runs on Spark, Flink or SQL engines. Its ideas (partition by key, sort-based shuffle, re-execution as recovery, speculative copies of slow tasks) live on inside every one of them.
terms: Input split — the piece of input one map task reads; by default one 128 MB HDFS block.
Map task — a process that reads one split record by record and calls map() on each record.
Partitioner — the function that picks which reduce task gets a key; by default hash(key) mod R, where R is the number of reducers.
Combiner — an optional "mini-reduce" run on map output before the shuffle, to shrink data such as many (word, 1) pairs into one (word, n).
Spill — writing a sorted part of the in-memory map output buffer to local disk when the buffer fills.
Shuffle — the transfer in which every reduce task fetches its partition from the output of every map task, then merges the pieces in key order.
Speculative execution — starting a backup copy of a slow task (a straggler) on another node and keeping whichever copy finishes first.
ApplicationMaster — the per-job process (MRAppMaster) that asks YARN for containers, tracks every task and re-runs failed ones.
OutputCommitter — moves a successful task attempt's output from a temporary directory to its final place, so only one attempt's output is visible.
history: Two Google papers set the direction. "The Google File System" (Ghemawat, Gobioff and Leung, SOSP 2003) described a file system for huge files on unreliable machines. "MapReduce: Simplified Data Processing on Large Clusters" (Jeffrey Dean and Sanjay Ghemawat, OSDI 2004) described the computing model on top of it. The paper reported a 1 TB sort in 891 seconds on about 1,800 machines, and said upwards of one thousand MapReduce jobs ran at Google every day. The idea itself was not new; map and reduce come from Lisp, and parallel databases already partitioned data by key. What was new was a simple interface plus a runtime built for constant machine failure.
Doug Cutting and Mike Cafarella were building the Nutch web crawler and needed the same capabilities. They wrote open-source versions of GFS and MapReduce in Nutch in 2004–2005. In early 2006 Cutting joined Yahoo, and the code became a separate project, Hadoop. It became a top-level Apache project in 2008, and that year a Yahoo Hadoop cluster sorted 1 TB in 209 seconds, beating the previous record of 297 seconds; it was the first time a Java or open-source program had won the benchmark. Writing raw map and reduce functions was slow work, so Yahoo built Pig and Facebook built Hive (both around 2008) to compile scripts and SQL into chains of MapReduce jobs. A SIGMOD 2009 study by Pavlo and colleagues found parallel databases much faster on most analytical tasks, though Hadoop was easier to set up and load.
Hadoop 2 (2013) split resource management out into YARN, so MapReduce became one application among many on the cluster. That opened the door for faster engines. Spark (Zaharia et al., NSDI 2012) kept data in memory between steps, which its authors showed could speed up iterative jobs by an order of magnitude. In June 2014 Google said it had moved on from MapReduce and launched Cloud Dataflow. Hive and Pig moved to Tez and Spark, and MapReduce has received only maintenance since. Hadoop 3.5.0 requires Java 17 on servers.
how: A job starts on the client. The client asks HDFS for the input files' block list and computes the input splits, normally one per block. It copies the job's JAR file and configuration to a staging directory in HDFS and submits the job to the YARN ResourceManager. YARN starts the job's ApplicationMaster in a container. The ApplicationMaster reads the split list, which includes the hosts that hold each block, and asks YARN for one container per map task with those hosts as preferences. The scheduler tries for a data-local container (same node as a replica), then rack-local, then any node. This is the main thing HDFS adds: with three replicas per block, there are three good places to run each map, so most maps read their 128 MB from a local disk instead of the network.
Inside a map task, a RecordReader turns the split into records; for text, the key is the byte offset of a line and the value is the line. map() is called once per record and writes (key, value) pairs into a circular in-memory buffer of 100 MB (mapreduce.task.io.sort.mb). When the buffer is 80% full, a background thread assigns each pair a partition with the partitioner, sorts the pairs by (partition, key), runs the combiner if there is one, and writes a sorted spill file to local disk while map() keeps filling the rest of the buffer. When the map finishes, its spill files are merged, ten at a time by default, into one sorted file per map task, with an index that says where each of the R partitions begins. This output goes to local disk, not HDFS: it is temporary, and replicating it would triple the cost.
The shuffle comes next. Reduce tasks are launched once 5% of the maps have finished, so that copying overlaps with mapping. Each reduce task asks the ApplicationMaster which maps are done, then fetches its own partition from each of them over HTTP, from a shuffle service that runs inside each NodeManager, five fetches in parallel by default. Fetched pieces are merged in memory and spilled to disk when memory is short. Only after the last map has finished can reduce() itself begin, because any map might still emit a value for any key. The final merge streams keys in sorted order, and reduce() is called once per key with an iterator over all its values. With M maps and R reducers, the shuffle is M × R separate transfers.
Reduce output is written to HDFS with normal three-way replication, first into a temporary directory for that task attempt. When the attempt succeeds, the OutputCommitter moves it into the job's output directory. Because only one attempt per task is ever committed, a task can be run twice without creating duplicate output.
Failure handling is where batch processing, the second concept, pays off. Because inputs are immutable and map and reduce are expected to be deterministic, the framework recovers by re-running work, never by repairing it. A failed task attempt is retried on another node, up to 4 attempts by default. If a whole node dies, the maps that ran there are re-run even if they had finished, because their output lived on that node's local disk; finished reduces are not re-run, because their output is safe in HDFS. If the ApplicationMaster dies, YARN starts a new one (2 attempts by default), and it can recover the state of finished tasks. Stragglers (tasks slowed by a bad disk or a busy node) are handled by speculative execution: near the end of a phase, the ApplicationMaster starts backup copies of the slowest tasks and keeps whichever copy finishes first. Google measured that disabling backup tasks made their sort 44% slower.
YARN, the third concept, supplies the machinery for all of this: containers with fixed memory and CPU, NodeManagers that run them and host the shuffle service, and a ResourceManager that shares the cluster between jobs and users through queues. Before YARN, Hadoop 1 had a single JobTracker that both scheduled the whole cluster and tracked every task of every job, which limited clusters to about 4,000 nodes.
The cost model follows. Every job reads from HDFS, writes every intermediate pair to local disk at least once, sorts it whether or not sorting is needed, sends it over the network, and writes the result to HDFS three times. Each task is also a new JVM, which takes roughly a second to start. For one large scan-and-aggregate job this overhead is small; for chains of jobs and iterative algorithms it dominates.

example: Start with word count on two tiny splits and R = 2 reducers. Split 1 is "the cat sat"; split 2 is "the dog sat the". Map 1 emits (the,1), (cat,1), (sat,1). Map 2 emits (the,1), (dog,1), (sat,1), (the,1), and its combiner merges these into (the,2), (dog,1), (sat,1), so 3 pairs cross the network instead of 4. Suppose the partitioner sends "sat" and "the" to reducer 0 and "cat" and "dog" to reducer 1. Reducer 0 fetches its partition from both maps and, after the merge, sees sat → [1, 1] and the → [1, 2]; it writes sat 2 and the 3. Reducer 1 sees cat → [1] and dog → [1]. Notice that the combiner is correct here only because addition can be done in any order and in any grouping.
Now a realistic size, as in the diagram. A job counts events per device over 1 TiB of logs in 128 MiB blocks: 1,048,576 MiB / 128 MiB = 8,192 splits, so 8,192 map tasks. The cluster has 100 nodes with 16 containers each, 1,600 slots. The maps need 8,192 / 1,600 ≈ 5.1 waves, so 6 rounds; if a map takes 60 seconds, the map phase takes about 6 minutes.
Choose R. The Hadoop guide suggests 0.95 × the number of slots, so R ≈ 0.95 × 1,600 = 1,520 reducers, all of which can start at once. Suppose the combiner shrinks the map output to 200 GB. Each map then produces 200 GB / 8,192 ≈ 24 MB, cut into 1,520 partitions of about 16 KB each. The shuffle is 8,192 × 1,520 ≈ 12.5 million separate fetches of 16 KB. That is why shuffles are limited by request overhead and disk seeks, not only by bandwidth, and why fewer, larger reducers or compressed map output often help. Each reducer receives 200 GB / 1,520 ≈ 132 MB, which it can merge mostly in memory.
Then a failure. One node dies just as the map phase ends. It had run about 8,192 / 100 ≈ 82 maps, and their outputs were on its local disk, so those 82 maps are re-run on other nodes. They fit in one partial wave (82 of 1,600 slots), so the job loses about one extra minute. Reducers that had not yet fetched from those maps wait; nothing else is lost. Finally, the output: 200 GB of results written to HDFS with three replicas is 600 GB of disk writes. If this job feeds a second MapReduce job, all of it is read back again.
intuition: Divide a huge pile of paperwork among many clerks, let each sort their share into labelled trays, send each label's trays to one clerk for the final total, and if a clerk falls ill, give their pile to someone else.
The design is natural once you accept two facts of large clusters: machines fail all the time, and moving data costs more than moving code. Making every step deterministic over immutable input turns failure recovery into "do it again somewhere else", which needs no coordination and no replicas of intermediate state.
The shuffle is the other insight. Almost every large computation (counting, joining, indexing, grouping) needs all records with the same key in one place. Hashing the key decides that place without any central directory, and sorting lets a reducer read each key's values as one contiguous run. Map and reduce are simply the two places where user code fits around that group-by-key.
mistakes: People often think MapReduce is just the map and reduce functions from functional programming. In fact the important part is between them: the distributed group-by-key (partition, sort, transfer, merge) and the failure model. The two user functions are the easy part.
People often think reducers wait idle until all maps finish. In fact reducers start copying when 5% of maps are done; only the call to reduce() must wait for the last map, because any map might still produce a value for any key.
People often think the combiner is the reducer run early, and always runs. In fact it may run zero, one or several times per map, so it must be associative and commutative and give the same type it receives. Sum and max work; a plain average does not (combine (sum, count) pairs instead).
People often think Hadoop means MapReduce. In fact Hadoop is HDFS, YARN and MapReduce. Many companies still run HDFS and YARN under Spark, Hive on Tez and Flink after retiring MapReduce itself.
People often think a job without a reducer count set will run in parallel. In fact the default mapreduce.job.reduces is 1, so a forgotten setting sends the entire shuffle to one task.
friction: The main cost is materialization: a 10-step pipeline does 10 rounds of full writes to replicated HDFS and reads back. Iterative machine learning, graph algorithms and multi-stage SQL suffer most; Spark's in-memory datasets cut such jobs from hours to minutes.
Latency is high even for small jobs. Submitting a job, starting an ApplicationMaster, and starting a JVM for each task takes tens of seconds before any data is read, so MapReduce was never usable for interactive queries. The sort-based shuffle always sorts, even when the job only needs grouping, and its M × R fetches grow quickly with cluster size.
The programming model is narrow. Joins must be written by hand as reduce-side joins (tag each record with its source and join in the reducer) or map-side joins (ship the small table to every map). Multi-step logic becomes a chain of jobs linked by HDFS directories and an external scheduler such as Oozie.
Skew is not handled automatically. One hot key (for example a null device ID) sends a huge share of the data to one reducer, and the job waits for it; speculative execution does not help, because the backup copy has the same amount of work. Many small input files create one map task each, and per-task overhead then dominates.
practice: For new work, use Spark (or Flink, or a SQL engine). If you still own MapReduce jobs, usually from old Hive, Pig, Oozie or Sqoop pipelines, migrate them; each job maps directly onto a Spark stage pair, with the shuffle key as the groupBy or join key.
When you must tune a running job, start with the shuffle. Add a combiner whenever the reduce is associative and commutative. Compress map output (mapreduce.map.output.compress with Snappy or LZ4); it costs little CPU and cuts disk and network. Set the reducer count explicitly, using the 0.95 × slots rule as a start, and aim for a few hundred MB to a few GB per reducer. Increase the sort buffer if the counters show many spills per map. Combine small input files with CombineFileInputFormat so that each map reads at least one block's worth of data.
Read the job counters; they show where time went: map input records, spilled records (more than map output records means repeated spills), shuffle bytes, and the slowest reducer's input size. A reducer with ten times the median input is skew; fix it by salting the hot key or by filtering bad keys before the shuffle. Turn off speculative execution for tasks that write to external systems, since two copies would write twice.
Keep the model in mind even if you never write a job: a Spark stage boundary and a Kafka Streams repartition topic are both MapReduce shuffles, and the M × R cost and re-execution model explain many problems in later systems.
quiz: What do the map and reduce functions take and return? || map takes one input record and emits zero or more (key, value) pairs. reduce takes one key and an iterator over all values for that key, and writes the output for that key.
Why are completed map tasks re-run when a node fails, but completed reduce tasks are not? || Map output is stored only on the local disk of the node that ran the map, so it is lost with the node. Reduce output is written to HDFS with three replicas, so it survives.
How does speculative execution reduce job time, and when does it not help? || It starts backup copies of the slowest tasks near the end of a phase and keeps the first to finish, which hides stragglers caused by bad machines. It does not help with skew, because the backup must process the same oversized partition.
A job has 4,000 maps and 500 reducers, and the map output after combining is 100 GB. How many shuffle fetches are there, and how big is each? || 4,000 × 500 = 2 million fetches. Each map outputs 100 GB / 4,000 = 25 MB, so each fetch is about 25 MB / 500 = 50 KB.
Why did Spark replace MapReduce for iterative jobs, and what did it give up? || MapReduce writes every step to disk and HDFS and starts a JVM per task, so each pass of an iterative algorithm pays full I/O. Spark keeps data in memory and recomputes lost partitions from lineage, at the cost of more memory pressure.

@@ hdfs
value: HDFS, the Hadoop Distributed File System, stores very large files across hundreds or thousands of ordinary servers and keeps them safe when disks and machines fail. It cuts each file into large blocks (128 MB by default), stores three copies of each block on different machines, and keeps all file metadata in one server, the NameNode. Its design goal was not low latency but high streaming throughput for batch jobs: read a whole 128 MB block from a local disk at full speed, on every node of the cluster at once.
For about ten years (roughly 2007 to 2017) HDFS was the storage layer of big data. MapReduce, Hive, HBase, Spark and Impala all read and wrote it, and Yahoo, Facebook, LinkedIn and most large enterprises ran clusters of thousands of nodes. It made the on-premises data lake possible: raw logs and Parquet or ORC tables lived as files in directories, and compute moved to the nodes that held the data. Many enterprises still run it in 2026, and LinkedIn reported 1 exabyte across its Hadoop clusters in 2021. But cloud object storage (Amazon S3, Azure Data Lake Storage, Google Cloud Storage) has replaced it for most new work, because it separates storage from compute and needs no NameNode to operate.
It stands on two lower concepts. The JVM runs every HDFS daemon; the NameNode keeps the entire namespace as Java objects on its heap, so Java's memory model and garbage collector set the practical limits on how many files a cluster can hold. The data lake (L1) defines the job HDFS does: cheap, durable, write-once storage for raw files, read later with whatever schema the reader chooses. For the layers above, HDFS gave MapReduce and Hive block locations for data-local scheduling. Its client interface, the Hadoop FileSystem API, outlived HDFS itself: Spark still reaches S3 and ADLS through s3a:// and abfs:// implementations of that API.
terms: Block — a fixed-size piece of a file, 128 MB by default, stored as an ordinary file on a DataNode's local disk.
NameNode — the server that holds the directory tree, each file's block list and each block's locations, all in memory.
DataNode — a server that stores blocks on its disks, serves reads and writes, and reports its blocks to the NameNode.
Replication factor — how many copies of each block exist; 3 by default.
Rack awareness — placement that knows which rack each node is in, so that copies of a block survive the loss of a whole rack.
Edit log — the NameNode's write-ahead log of namespace changes; with the fsimage checkpoint file it rebuilds the namespace after a restart.
Block report — a DataNode's periodic list of all blocks it holds; block locations are rebuilt from these, not stored on disk.
JournalNode — one of a small group of servers (usually 3) that store the shared edit log, so a standby NameNode can follow the active one.
Erasure coding — storing data blocks plus computed parity blocks instead of full copies; RS-6-3 keeps 6 data and 3 parity blocks.
history: HDFS copies the design of the Google File System (Ghemawat, Gobioff and Leung, SOSP 2003). GFS used 64 MB chunks, three replicas, and a single master holding all metadata in memory, on the bet that a single master is simple and fast enough if clients only ask it where data is and then read from the chunk servers directly. Doug Cutting and Mike Cafarella wrote an open-source version, NDFS, for the Nutch crawler in 2004–2005, and it became HDFS when Hadoop was split out in 2006, with Yahoo as the main developer.
Scale came quickly. The HDFS paper by Shvachko, Kuang, Radia and Chansler (MSST 2010) described Yahoo's clusters: about 25,000 servers storing 25 PB, with the largest cluster at 3,500 nodes, 60 million files and 63 million blocks, and NameNode hosts with up to 64 GB of RAM. The single NameNode was both the limit and the main risk. Hadoop 2 (2012–2013) added high availability (an active and a standby NameNode sharing an edit log on JournalNodes, with ZooKeeper deciding who is active) and federation (several independent NameNodes, each owning part of the namespace). The default block size rose from 64 MB to 128 MB.
Hadoop 3.0 (December 2017) added erasure coding, which cut storage overhead from 200% to 50% for cold data. LinkedIn's work on Observer NameNodes, standbys that also serve reads, tripled namespace throughput on their largest cluster, which by 2021 held 500 PB on 10,000 nodes and 1.1 billion namespace objects in a single 380 GB Java heap. Ozone, an object store built by Hadoop developers to escape the NameNode's limits, became a separate Apache top-level project in October 2020. Meanwhile the cloud moved the industry to object storage. Hadoop 3.5.0 (April 2026), the current line, requires Java 17 on servers and adds finer-grained locking inside the NameNode.
how: HDFS splits the roles cleanly. The NameNode stores metadata only: the tree of directories and files (inodes, with owners and permissions), each file's ordered list of block IDs, and, for each block, the DataNodes that hold it. File data never passes through the NameNode. DataNodes store each block as two local files, the data and a small checksum file, on an ordinary Linux file system. A client asks the NameNode where the blocks are and then talks to DataNodes directly. This is the key to scale: the NameNode handles small requests, while terabytes per second move between clients and DataNodes.
Writing a file works through a pipeline. The client asks the NameNode to create the file and then to add a block. The NameNode picks three DataNodes with its rack-aware policy: the first replica on the writer's own node if the writer is a DataNode (otherwise a random node), the second on a node in a different rack, and the third on another node in that same remote rack. This survives the loss of any one rack while sending only one copy across the slower links between racks. The client splits data into 64 KB packets and sends them to the first DataNode, which stores each packet and forwards it to the second, which forwards it to the third. Acknowledgements flow back along the same chain, and the client keeps a window of packets in flight. A CRC32C checksum is computed for every 512 bytes and stored with the block. Files are write-once: one writer holds a lease, data can be appended, but bytes cannot be changed in place.
Reading is simpler. The client gets the block list, with each block's DataNodes sorted by network distance, and reads from the nearest one, checking checksums as it goes. If a DataNode fails or a checksum does not match, the client reports the bad replica and reads another copy. When the reader runs on the same machine as a replica, short-circuit reads let it open the block file directly, bypassing the DataNode process. MapReduce and Hive used the same block locations to schedule tasks on the nodes that hold the data.
The NameNode keeps everything in memory, so it must be able to rebuild that memory after a crash. Every namespace change (create, rename, delete, add block) is written to the edit log and synced to disk before the client gets an answer; many concurrent changes are batched into one sync. Periodically, by default every hour or every million transactions, the log is merged into a new fsimage checkpoint. Block locations are not logged at all: on restart, every DataNode sends a full block report, and the NameNode stays in read-only safe mode until 99.9% of blocks have been reported. In a high-availability setup, the active NameNode writes each edit to three JournalNodes and continues once a majority (two) acknowledge. The standby NameNode reads the same edits, keeps an up-to-date copy of the namespace, receives block reports too, and takes over within seconds if ZooKeeper-based failover detects that the active one has died. The old active is fenced, so it cannot keep writing.
The JVM, the first concept HDFS stands on, explains its main limit. Each file, directory and block is a Java object graph on the NameNode's heap; a common rule of thumb is about 150 bytes per object, and LinkedIn's 380 GB heap held 1.1 billion objects, about 350 bytes each with all overhead. Large heaps mean garbage-collection tuning: a full collection on a heap of hundreds of GB stops the NameNode for a long pause, which looks like an outage to every client, so operators size the heap generations to avoid full collections entirely. The NameNode's internal locking also limits how many metadata operations per second it can process, which is why Hadoop 3.5 made locking finer-grained, and why Observer NameNodes and Router-based federation exist.
DataNodes keep the cluster healthy. Each sends a heartbeat every 3 seconds and a full block report every 6 hours by default. If heartbeats stop for about 10.5 minutes (two 5-minute recheck intervals plus ten heartbeats), the NameNode declares the node dead and schedules new copies of every block that now has fewer than three replicas, choosing sources and targets across the whole cluster. A balancer tool moves blocks to even out disk usage after nodes are added.
Erasure coding changes the storage arithmetic. With the RS-6-3-1024k policy, a file is striped in 1 MB cells across 6 data blocks, and 3 parity blocks are computed with Reed–Solomon coding. Any 6 of the 9 blocks rebuild the data, so it survives 3 failures, more than 3-way replication's 2, at 1.5× storage instead of 3×. The price is that reads and rebuilds touch many nodes, data locality is lost, and lost blocks must be recomputed with CPU work. It suits cold data. This is the data lake idea, the second concept, in practice: keep everything, cheaply, in open file formats, and let readers decide later what it means.

example: Take 100 TiB of event data in a cluster of 100 DataNodes. Stored as 128 MiB files, it is 100 × 1,048,576 MiB / 128 MiB = 819,200 files with one block each, about 1.64 million namespace objects. At roughly 150 bytes each, the NameNode needs about 246 MB of heap for them, which is trivial. Now suppose a careless streaming job wrote the same data as 1 MiB files. That is 104,857,600 files and as many blocks, about 210 million objects, or roughly 31 GB of heap at 150 bytes each (closer to 70 GB at LinkedIn's measured 350 bytes). The data is the same; the metadata is 128 times larger. Every job listing those files also makes 128 times more NameNode calls, and a MapReduce or Hive job would launch 128 times more tasks. This is the small-files problem in one calculation.
Storage cost next. With 3-way replication the 100 TiB needs 300 TiB of raw disk. With RS-6-3 it needs 100 × 9 / 6 = 150 TiB, saving 150 TiB, and it survives any 3 failed blocks per stripe instead of 2.
Now a write. One 128 MiB block is sent as 128 MiB / 64 KiB = 2,048 packets. Checksums are 4 bytes for each 512 bytes, so the block's checksum file is 128 MiB / 512 × 4 bytes = 1 MiB, about 0.8% extra. If the writer runs on DN1, the first copy is written locally, and each byte then crosses the network twice: DN1 to DN4 between racks, and DN4 to DN5 inside rack B.
Finally, a failed node. A DataNode with 12 disks of 16 TB, 70% full, holds about 134 TB. It stops sending heartbeats at 10:00:00. The NameNode marks it dead at about 10:10:30 (2 × 300 s + 10 × 3 s = 630 s) and starts re-replicating about one million blocks. Because the surviving copies are spread over the other 99 nodes, each node sends and receives roughly 134 TB / 99 ≈ 1.35 TB. If each node can spare 100 MB/s for recovery, that is about 13,500 seconds, close to 4 hours, during which those blocks have only two copies. A cluster of 10 nodes would need ten times longer. Spreading replicas widely is what makes recovery fast.
intuition: A library whose catalogue is held by one librarian with a perfect memory, while the books are spread over many shelves, each in three copies, and readers fetch books from the shelves themselves.
The design is natural for the problem it was built for. Batch jobs read whole files from start to end, so large blocks keep the catalogue small and turn reads into long sequential disk scans, the fastest thing a hard disk can do. Commodity machines fail often, so copies are cheaper than trying to make each machine reliable. Placing copies on two racks covers the most common large failure, a rack switch, without sending every copy over the slow links between racks.
The single NameNode looks like a weakness, and it is one at very large scale, but it makes everything else simple: one place decides where every block goes, renames are atomic metadata changes, and clients need no coordination among themselves. Keeping metadata in memory makes each decision take microseconds, and the edit log, a classic write-ahead log, makes that memory durable.
mistakes: People often think data flows through the NameNode. In fact clients only ask it where blocks are; all reads and writes go directly between clients and DataNodes, which is why one NameNode can serve thousands of nodes.
People often think a 1 MB file uses a full 128 MB block on disk. In fact a block file is only as large as its data. The cost of small files is NameNode memory and per-file overhead, not wasted disk.
People often think HDFS supports updates like a normal file system. In fact files are write-once with append only; there are no in-place writes. Table formats such as Delta and Iceberg add updates on top by writing new files and tracking them in a log.
People often think three replicas mean data can never be lost. In fact three simultaneous failures can lose blocks, deletion by a user or a bad job is replicated instantly, and a corrupted NameNode image loses the namespace. Backups, snapshots and trash still matter.
friction: The NameNode is the limit. All metadata must fit in one JVM heap, metadata operations go through one process, and large heaps need careful garbage-collection tuning. High availability, federation and Observer NameNodes help, but they add JournalNodes, ZooKeeper, routers and more operational knowledge. A namespace of a few hundred million objects is where most clusters start to suffer.
Small files are the classic failure. Streaming jobs, many partitions and frequent writes produce millions of tiny files that bloat NameNode memory and slow every listing and job start. Compaction has to be designed in from the start.
Storage and compute scale together. To add disk you add whole servers, with CPU and memory you may not need, and a cluster sized for peak compute wastes storage, or the reverse. Object storage lets each scale separately and charges for what is used. Running HDFS also means owning disk replacement, rebalancing, rolling upgrades, Kerberos security and capacity planning, which needs a dedicated team.
Its semantics are narrower than POSIX: no random writes, a single writer per file, and high latency for small reads. Erasure coding saves space but loses data locality and makes recovery heavier. Finally, the ecosystem is shrinking: fewer engines treat HDFS as their first target, and most new features land first in cloud object storage connectors.
practice: If you run HDFS today, watch the NameNode first: heap usage, garbage-collection pause times, RPC queue time and the count of files and blocks. Keep files large, ideally hundreds of MB to a few GB, by compacting outputs from streaming and frequently written tables, and set quotas on namespace objects per directory so one team cannot flood the namespace. Run high availability with three JournalNodes and automatic failover, and test failover regularly.
Use rack awareness (a correct topology script), keep the replication factor at 3 for hot data, and move cold data to erasure coding (RS-6-3 if you have at least 9 racks, otherwise check the policy against your rack count). Enable short-circuit reads for co-located compute. Keep HDFS trash enabled and take snapshots of critical directories before risky jobs. Run the balancer after adding nodes.
If you are planning a migration to object storage, as many teams moving to Databricks do, copy with DistCp, then fix the assumptions that break: directory renames are cheap in HDFS but slow, non-atomic copies in S3, so jobs that commit by renaming need committers designed for object stores, and table formats such as Delta or Iceberg are the safer target. Re-partition and compact during the move rather than copying a small-files problem into the cloud.
quiz: What does the NameNode store, and what does it not store? || It stores the directory tree, each file's list of blocks and each block's current locations, all in memory. It does not store file data, and it does not persist block locations; those are rebuilt from DataNode block reports.
Why does HDFS place the second and third replicas on one remote rack instead of three different racks? || One remote rack still protects against losing a whole rack, while only one copy crosses the slower links between racks during the write. Three racks would add cross-rack traffic with little extra safety.
How does a standby NameNode stay ready to take over? || The active NameNode writes every edit to a majority of JournalNodes; the standby reads and applies the same edits and also receives block reports, so its namespace is current. ZooKeeper-based failover promotes it and the old active is fenced.
How much NameNode heap do 50 million files of 2 MB each need, using 150 bytes per object? || Each file has one block, so about 100 million objects × 150 bytes ≈ 15 GB. The same 100 TB stored as 1 GB files would need about 100,000 files and 200,000 objects, about 30 MB.
When would you keep HDFS rather than move to object storage? || When a large on-premises cluster already exists, data must stay on site, and workloads benefit from data locality and cheap renames. For new or elastic workloads, object storage is usually cheaper and simpler because storage and compute scale separately.

@@ photon
value: Photon is Databricks' native query engine, written in C++. It runs SQL and DataFrame operations (scans, filters, joins, aggregations, sorts, window functions, shuffles and Delta or Parquet writes) instead of Spark's JVM execution, without any change to user code. Spark still parses and plans the query; Photon executes the parts of the plan it supports, over columnar batches of data, and hands the rest back to Spark. Databricks reports an average speedup of about 3× on customer workloads, with some queries above 10×.
It exists because the bottleneck moved. Around 2018–2020, lakehouse queries read columnar Parquet files from fast SSD caches and cloud storage, and the CPU, not the disk, became the limit. Spark's engine processes rows inside the JVM, with code generated per query, and it struggles with large heaps, garbage collection, wide rows, and the very irregular data of a lakehouse: many strings, many nulls, no constraints, columns that nobody cleaned. A warehouse vendor would have the CPU-efficient engine but not the openness; Databricks wanted warehouse speed on open Delta tables.
It stands on two lower concepts. C and C++ give it control of the machine: exact memory layout of each column, SIMD instructions that process 4 to 16 values at once, templates that produce specialized loops without per-row virtual calls, and no garbage collector or JIT warm-up. Distributed SQL (MPP, L1) gives the frame it fits into: the query is split into stages connected by shuffles and broadcasts, and each stage runs as many parallel tasks over partitions of the data. Photon does not replace that distributed layer; Spark's planner and scheduler still decide stages and tasks, and Photon makes each task's work much cheaper. For the layer above, Databricks, Photon is the engine of SQL warehouses and serverless compute, and it is enabled by default on classic clusters too.
terms: Vectorized execution — processing a batch of values of one column in a tight loop per operator, instead of passing one row at a time through all operators.
Column batch — Photon's unit of data: one vector per column plus a list of active rows, sized to stay in CPU caches.
Position list — the indices of rows in a batch that are still active after filters; a filter changes this list instead of copying data.
Kernel — a small, specialized function that runs one operation (hash, compare, add, upper-case) over a vector of values.
Whole-stage code generation — Spark's approach: generate and compile Java code for a whole chain of operators per query, so rows flow without virtual calls.
SIMD — single instruction, multiple data: CPU instructions (such as AVX2 or AVX-512) that apply one operation to several values at once.
JNI — the Java Native Interface, through which the executor JVM calls Photon's C++ library.
Transition node — the operator that converts Photon's columnar batches into Spark rows where the plan leaves Photon.
Adaptivity — choosing a specialized code path at run time from properties of the actual batch, such as "no nulls" or "all ASCII".
history: Spark's engine evolved in steps. Project Tungsten (2015–2016) moved Spark to compact binary rows and whole-stage code generation, which made Spark 2.0 much faster but kept execution inside the JVM. Meanwhile the database field had shown, with MonetDB/X100 (Boncz, Zukowski and Nes, CIDR 2005) and later systems such as Vectorwise and DuckDB, that vectorized, cache-friendly processing of columns is extremely efficient. Photon brings that approach to Spark.
Databricks announced Photon on 24 June 2020, as part of "Delta Engine". A public preview followed in June 2021. In November 2021 Databricks SQL with Photon set an officially audited record on the 100 TB TPC-DS benchmark. The paper "Photon: A Fast Query Engine for Lakehouse Systems" (Alexander Behm and 22 co-authors, including Reynold Xin and Matei Zaharia) appeared at SIGMOD 2022 and won its Best Industry Paper award; Spark received the SIGMOD Systems Award the same year. Photon became generally available in August 2022.
Since then its coverage has grown: sort, window functions and Delta writes, dynamic file pruning for MERGE, UPDATE and DELETE, predictive I/O, variant, geospatial types and collated strings. Photon also replaces sort-merge joins with hash joins. It is always on for SQL warehouses, serverless compute and serverless pipelines. The same idea now exists in open source: Meta's Velox C++ library (2022), Apache Gluten, which plugs Velox or ClickHouse into Spark, and Apache DataFusion Comet, a Rust-based Spark accelerator donated by Apple in 2024. Photon itself remains closed source and runs only on Databricks.
how: Photon enters at the end of query planning. Catalyst produces Spark's physical plan as usual. A Databricks rule then walks the plan from the bottom, starting at the file scans, and replaces each supported operator with its Photon version. When it reaches an operator Photon cannot run, for example a Python UDF, it inserts a transition node that converts Photon's columns into Spark rows, and everything above stays in Spark. Photon avoids switching back and forth in the middle of a plan, because each switch costs a conversion. This is the distributed-SQL frame, the second concept it stands on: stages, exchanges, broadcast joins and adaptive query execution remain Spark's, and Photon executes the operators inside each task.
At run time, Photon is a C++ library loaded inside each Spark executor's JVM. Spark's off-heap columnar scan output is handed to Photon by passing pointers, without copying, through an adapter node that makes one JNI call per batch. The Photon paper measured the cost of such a call at about 23 ns, about the same as a C++ virtual call, so it disappears when spread over a whole batch. In a no-op query, the adapter and transition together took well under 1% of the time. Photon writes shuffle data in its own format, so a Photon shuffle write must be read by a Photon shuffle read.
The core data structure is the column batch. Each column is a column vector: a contiguous buffer of values, a byte vector that marks nulls, and metadata such as whether all strings in it are ASCII. The batch also has a position list of the active rows. A filter does not copy surviving rows; it writes a shorter position list, and later operators process only those positions. The authors chose a position list over a bit mask because a mask forces every loop to visit every row, which wasted time on sparse batches.
Each operator is written as kernels, loops over vectors. A hash join's probe, for example, runs a hashing kernel over the whole batch, then a kernel that loads the hash-table bucket of each row, then a key comparison column by column; rows that did not match keep probing (the table uses quadratic probing). Keeping independent memory loads close together lets the CPU have many cache misses outstanding at once, which hides much of the memory latency. Kernels are C++ templates with variants for "this batch has no nulls" and "all rows are active". In those cases the loop has no branches and no indirection, and the compiler can turn it into SIMD instructions. This is what C++, the first concept, adds: you control layout and code shape closely enough that the hardware runs at full speed, and no garbage collector pauses the work.
Photon deliberately interprets vectorized operators instead of generating code like Spark. The authors gave three reasons. Interpreted C++ is easier to build and debug with normal tools. Operators stay separate, so each can report its own time and row counts in the query profile. And adaptivity is easy, because the choice of kernel is already a run-time dispatch. The cost of interpretation, one function call per batch per operator instead of per row, is spread over the batch. Where code generation would really help, such as expressions like BETWEEN, Photon adds hand-fused kernels.
Adaptivity matters most for lakehouse data. Before running a kernel, Photon checks properties of the batch: no nulls, no inactive rows, all ASCII strings. With all-ASCII input, upper() can run as a simple SIMD loop instead of full Unicode processing, which the paper measured at 3× faster than Spark and 4× faster than a general Unicode library. Sparse batches are compacted before a hash probe, which made TPC-DS query 24 1.5× faster. UUID strings can be re-encoded as 128-bit integers, which more than halved shuffle volume in one test. Decimals are computed with native integer arithmetic; that is the main reason TPC-H query 1 ran 23× faster.
Memory is shared with Spark. Photon reserves memory from Spark's unified memory manager, so Spark and Photon operators in one task compete for the same budget, and memory-hungry operators (hash joins, aggregations) can be asked to spill to disk under the same policy as Spark's. Photon's own allocations are native memory outside the JVM heap, so memory settings tuned for JVM-only execution may need changing.

example: Start with one batch, as in the diagram. Four rows have price 12, 7, 30, 9 and qty 1, null, 2, 3. The query is SELECT sum(price * qty) WHERE price > 10. The filter kernel compares the price vector with 10 in one loop and writes the position list [0, 2]; nothing is copied. The multiply kernel checks the batch metadata: qty has a null, but only at position 1, which is inactive, so for the active rows it computes 12 × 1 = 12 and 30 × 2 = 60. The aggregation kernel adds them, giving 72. On a real batch of thousands of rows, each of these steps is one tight loop, not one function call per row per operator.
Now the decision every Databricks user faces: is Photon worth its higher DBU rate? Photon compute consumes DBUs at a higher rate than the same instance without Photon; the exact multiplier depends on cloud, instance type and SKU, so for the arithmetic assume 2×. Take a nightly job on a cluster that costs $10 per hour in cloud VMs and $10 per hour in DBUs without Photon. It runs 2 hours, so it costs 2 × ($10 + $10) = $40.
The query profile shows that 70% of task time is in scans, joins and aggregations that Photon supports, and 30% is in a Python UDF that Photon does not support. Assume Photon makes the supported part 3× faster, the paper's average for customer workloads. New time = 2 h × (0.70 / 3 + 0.30) = 2 h × 0.533 ≈ 1.07 hours. New hourly cost = $10 VM + $20 DBU = $30, so the job costs 1.07 × $30 ≈ $32. Photon saves about 20% and finishes 56 minutes earlier.
Change one number. If the Python UDF takes 60% of the time, the new time is 2 h × (0.40 / 3 + 0.60) = 2 h × 0.733 ≈ 1.47 hours, and the cost is 1.47 × $30 ≈ $44. Now Photon is faster but costs 10% more. The break-even point is where the time ratio equals the cost-rate ratio: here, Photon must make the whole job at least $30 / $20 = 1.5× faster.
The best move is often to remove the blocker. If the UDF can be rewritten with built-in SQL functions, the whole plan stays in Photon. With 100% of the work at 3×, the job takes about 40 minutes and costs 0.67 × $30 ≈ $20, half the original. The lesson is that Photon's value is set by the fraction of the plan it covers, which you can read directly in the query profile.
intuition: Instead of carrying each customer's order through every station of a kitchen one at a time, Photon cuts all the onions, then cooks all the rice, then plates everything, with the knives already chosen for today's ingredients.
The idea is natural once you look at where a CPU spends time. A row-at-a-time engine pays for a function call, a type check and a branch for every row at every operator, and its data jumps around in memory. A vectorized engine pays those costs once per batch, then runs a loop over values packed next to each other, which is exactly what CPU caches, prefetchers and SIMD units are designed for.
Doing this in C++ removes the JVM's garbage collector and gives exact control over layout. Doing it inside Spark, instead of building a separate warehouse, keeps everything users already rely on: the same SQL, the same Delta tables, the same scheduler, with Spark as the fallback for anything Photon cannot yet do.
mistakes: People often think Photon is a different version of Spark that needs code changes. In fact it is a drop-in execution engine under Spark's planner; the same SQL and DataFrame code runs, and unsupported parts fall back to Spark automatically.
People often think Photon speeds up everything. In fact it helps CPU-bound SQL and DataFrame work. It does not speed up Python or Scala UDFs, RDD code, typed Dataset operations or stateful streaming, it gains little on queries limited by I/O or network, and queries that already finish in under about two seconds see no meaningful change.
People often think a query either runs in Photon or not. In fact it is decided operator by operator. A plan can run 95% in Photon or 5%; the query profile shows the share of task time spent in Photon, and one unsupported operator near the bottom of the plan can push almost everything back to Spark.
People often think Photon is just Spark with code generation in C++. In fact it rejects code generation and uses interpreted vectorized kernels with run-time adaptivity, which made it easier to debug, profile per operator and specialize to the data.
friction: Photon is proprietary and runs only on Databricks. You cannot inspect its code, run it locally or take it to another platform, and its behaviour can change between runtime versions. Rare semantic differences with Spark (the paper mentions decimal edge cases) are handled by Databricks' testing, not by you.
It costs more per hour. Photon compute is billed at a higher DBU rate, so it saves money only when the job becomes faster by more than that ratio. Jobs dominated by UDFs, external calls, small files or slow sources can be slower to finish per dollar.
Coverage is incomplete. UDFs, RDDs, typed Datasets and stateful streaming are not supported, and each boundary between Photon and Spark costs a column-to-row conversion. Because Photon converts from the bottom of the plan upward and avoids returning to Photon after a fallback, one unsupported expression low in a plan can leave most of the plan in Spark.
Finally, it solves CPU cost, not data layout. A full scan over badly clustered tables, a skewed join or millions of tiny files are still slow, only faster per byte.
practice: Use Photon-enabled compute for SQL-heavy ETL, BI queries and large joins and aggregations; SQL warehouses and serverless compute use it already. For each important job, open the query profile (or the Spark UI, where Photon operators are marked) and check the percentage of task time spent in Photon. If it is low, find the first unsupported operator from the bottom of the plan; it is usually a UDF.
Replace Python and Scala UDFs with built-in functions, SQL expressions or higher-order functions where possible, and move unavoidable UDFs as late in the pipeline as you can, after heavy joins and aggregations, so the expensive part stays in Photon. Avoid RDD and typed Dataset code in performance-critical paths.
Measure cost, not only time. Run the job with and without Photon on the same data and compare DBUs plus VM cost from the system billing tables; keep Photon where cost per run falls, and turn it off for jobs that are mostly Python, I/O-bound or tiny. Combine Photon with good data layout (liquid clustering, file sizes of hundreds of MB, statistics on filter columns), because data skipping removes work that no engine can make free. When you evaluate open alternatives (Gluten with Velox, DataFusion Comet), test the same queries; they follow the same design and the same coverage trade-offs.

value: Ray is a framework for running ordinary Python code on a cluster. You add @ray.remote to a function and it becomes a task that can run on any machine; you add it to a class and each instance becomes an actor, a long-lived process with its own state, whose methods you call remotely. Every remote call returns at once with a future (an ObjectRef), and results live in a shared-memory object store on each node, so large arrays can be passed between tasks without copying them through the driver.
The need came from machine learning. A modern ML workload mixes very different steps: CPU-heavy data loading, GPU training across many devices, hundreds of tuning trials that start and stop at different times, reinforcement learning with thousands of stateful simulators, and online serving with model replicas. Spark's model, in which every task in a stage runs the same function over a partition, fits ETL but not this mix. MPI fits fixed training jobs but has no fault tolerance or dynamic tasks. Ray fills the gap. Uber uses it for model training, tuning and data processing, and Amazon used it to compact more than 1.5 EiB of Parquet data in one quarter of 2024. Open-source LLM post-training frameworks such as OpenRLHF and veRL are built on it, and vLLM can use it for multi-node serving.
It stands on four lower concepts. Python gives the API and its limits: decorators make remote calls look like normal calls, pickle-based serialization moves functions and objects, and the global interpreter lock is why Ray parallelizes with separate worker processes rather than threads. Batch processing (L1) is the shape of Ray Data, which streams finite datasets in blocks through CPU and GPU stages. Machine learning (L1) supplies the workloads that shaped Ray's design (millisecond tasks, GPUs, stateful simulators), and MLOps (L1) the platform role: Ray Train, Tune and Serve plug into training, experiment tracking and serving pipelines, usually on Kubernetes through KubeRay. Since October 2025 Ray belongs to the PyTorch Foundation, which makes it part of the open PyTorch compute stack.
terms: Task — a remote call of a stateless Python function; it runs once on some worker and its result becomes an object.
Actor — an instance of a remote class living in its own worker process; it keeps state, and calls to its methods run one at a time in the order received.
ObjectRef — a future that names an object which may not exist yet; it can be passed to other tasks or resolved with ray.get().
Object store — a shared-memory area on each node (by default 30% of the node's RAM) that holds large task results and ray.put() values, readable without copying by all workers on that node.
Owner — the worker process that created an ObjectRef; it tracks the object's references, location and lineage.
Raylet — the per-node daemon that schedules work on that node's resources and moves objects between nodes.
GCS — the Global Control Service on the head node, which stores cluster-wide metadata: nodes, actors, jobs and placement groups.
Lineage reconstruction — recovering a lost object by re-running the task that produced it, using the description its owner kept.
Placement group — a reservation of a set of resource bundles (for example 8 GPUs on one node) that Ray schedules atomically, for gang-scheduled jobs such as distributed training.
history: Ray was developed in 2016–2017 at UC Berkeley's RISELab, the successor of the AMPLab that created Spark. Robert Nishihara and Philipp Moritz, PhD students working with Michael I. Jordan and Ion Stoica, were working on reinforcement learning, which needs millions of short simulation tasks, stateful simulators and model updates in a tight loop. Spark's latency per task and its lack of stateful workers made that awkward. "Ray: A Distributed Framework for Emerging AI Applications" (Moritz, Nishihara, Wang and others, OSDI 2018) described tasks, actors, a sharded global control store and a bottom-up distributed scheduler, and reported more than 1.8 million tasks per second.
Ray's creators founded Anyscale in 2019 to build a managed Ray service. The architecture was then redesigned around ownership ("Ownership: A Distributed Futures System for Fine-Grained Tasks", Wang et al., NSDI 2021): instead of recording every task in a central store, the worker that creates a future manages it. This took the control store off the critical path. Ray 1.0 came out in September 2020, and Ray 2.0 in August 2022 with a unified set of ML libraries. In 2022 a Ray-based shuffle (Exoshuffle) set the CloudSort record for cost, sorting 100 TB for about $97 on 40 cloud VMs.
In the LLM era Ray became common infrastructure for distributed training, batch inference and serving, and for reinforcement-learning-based post-training. In July 2024 Amazon described moving its exabyte-scale table compaction from Spark to Ray with 82% better cost efficiency per GiB. In October 2025 Anyscale contributed Ray to the PyTorch Foundation, under the Linux Foundation. In July 2026 the cloud provider Nscale agreed to acquire Anyscale; Ray itself stays community-governed. Releases come every few weeks; 2.59.0 appeared in October 2026.
how: A Ray cluster has one head node and any number of worker nodes. Every node runs a raylet, which schedules work on that node's resources (CPUs, GPUs, memory and custom labels) and manages its object store, plus a pool of Python worker processes. The head node also runs the GCS, which keeps cluster metadata, and usually the autoscaler and dashboard. Your driver script connects to the cluster and becomes the first owner of work.
When the driver calls f.remote(x), Ray serializes the function and its arguments, creates an ObjectRef for the result, and returns it immediately; the driver is the owner of that ref. The owner then asks its local raylet for a worker lease with the task's resource needs, {"CPU": 1} by default. If the local node has room, the raylet grants a worker. If not, it "spills back" and tells the owner to ask another node's raylet, chosen by Ray's default policy, which prefers nodes that hold the task's large arguments and then nodes with low utilization, picking randomly among the best 20%. Once it holds a lease, the owner sends the task straight to the leased worker and can reuse the lease for more tasks with the same resource shape. The GCS is not involved in any of this, so it does not become a bottleneck when a program submits many small tasks.
Results are stored by size. A small result (under about 100 KB) is sent back inline into the owner's in-process memory. A large result stays in the shared-memory object store of the node where it was produced. If a task on the same node needs it, ray.get() reads it without copying; a returned NumPy array points directly into shared memory and is read-only. This zero-copy path relies on Python's pickle protocol 5, which keeps large buffers separate from the rest of the serialized object. If a task on another node needs it, that node's object manager pulls the object in chunks from a node that has a copy. The owner counts references to every object it owns, across all processes; when the count reaches zero, all copies are freed. When an object store fills up, objects are spilled to local disk or cloud storage and restored on demand.
Actors give Ray state. Calling Counter.remote() starts a dedicated worker process that holds the instance; a.increment.remote() puts a call into that actor's queue, and calls run one at a time in the order they are submitted, so the actor's state needs no locks. Async actors and concurrency groups allow more parallelism when you need it. Actors hold expensive resources for a long time: a loaded model on a GPU, a database connection, a simulator, a replay buffer. Ray Train runs one actor per GPU around PyTorch's distributed training; Ray Serve runs model replicas as actors behind an HTTP proxy and scales their number with load; Ray Tune runs each trial as an actor and stops weak trials early.
Fault tolerance follows ownership. If a worker or node dies, a running task is retried, up to 3 times by default; exceptions raised by your own code are not retried unless you set retry_exceptions. If an object is lost because the node storing it died, its owner re-runs the task that created it, recursively if that task's inputs are also lost. This is lineage reconstruction, the same idea as Spark's RDD lineage, applied to individual futures. If the owner itself dies, everything it owns is lost and dependent calls fail with OwnerDiedError; the system does not try to recover owners. Actors are not restarted by default (max_restarts is 0); when restarted, they start with empty state unless your code checkpoints it.
The libraries apply the lower concepts. Ray Data is batch processing on Ray: a dataset is a list of blocks (usually Arrow tables), and a streaming executor pushes blocks through a chain of operators (read, map_batches on CPUs, inference on a GPU actor pool, write) with a bounded number of blocks in flight, so a 50 TB dataset never needs 50 TB of memory. Ray Train, Tune and Serve are the ML and MLOps layers (training, tuning, serving), and all are ordinary Ray programs built from tasks, actors and placement groups.

example: First, task size. The Ray documentation measures the overhead of an empty task at about 0.5 ms. Suppose you want to score 1,000,000 items, each taking 0.1 ms of CPU, on 64 cores. One task per item creates 1,000,000 × 0.5 ms = 500 seconds of overhead to do 100 seconds of work; on 64 cores the real work could take 100 / 64 ≈ 1.6 seconds, but the overhead dominates. Group 1,000 items per task instead: 1,000 tasks of 100 ms each. The overhead is now 1,000 × 0.5 ms = 0.5 seconds in total, and the job takes about 1,000 / 64 ≈ 16 rounds × 0.1 s ≈ 1.6 seconds plus a little. The rule from this arithmetic: make each task take at least tens of milliseconds.
Second, a batch-inference pipeline with Ray Data. You must score 10 million images with a vision model. Each of 8 GPUs, running as an actor with batch size 64, processes 400 images per second, so the GPU stage handles 8 × 400 = 3,200 images per second. Decoding and resizing on CPU runs at 50 images per second per core, so the CPU stage needs 3,200 / 50 = 64 cores to keep the GPUs busy; with fewer, the GPUs wait. With 64 CPU cores and 8 GPUs, the job takes 10,000,000 / 3,200 ≈ 3,125 seconds, about 52 minutes. This is the kind of heterogeneous pipeline that is natural in Ray and awkward in a stage-based engine.
Third, memory. On a node with 256 GB of RAM the default object store is 30%, about 77 GB; 16 blocks of 128 MB in flight use only 2 GB of it. But if a user collects all predictions to the driver with ray.get() on a list of 10,000 refs, each 20 MB, the driver must hold 200 GB. The driver crashes, and because it owned every object, all of them are lost. Writing results to storage from the workers avoids this.
Finally, a failure. Node B dies while holding object X, a 40 MB result of task A that another task still needs. X's owner, the driver, sees that the last copy is gone, re-runs A on a surviving node, and the dependent task continues. If A's inputs were also lost, Ray re-runs their tasks first. If an actor on node B held a model in GPU memory, it is gone unless you allowed restarts; with max_restarts=3 it restarts on another node with fresh state and reloads the model.
intuition: Ray makes a cluster feel like one big Python process: call a function or an object remotely and get a future back, and let the futures flow into other calls.
This design is natural because futures describe a program's dependencies without the programmer drawing a graph. When you pass an ObjectRef from one call into another, Ray learns that the second task needs the first task's result; the dependency graph builds itself as the program runs, which is exactly what dynamic workloads such as reinforcement learning or tuning need. Actors add the missing piece: state that stays in place, so a model or a simulator is loaded once and used thousands of times.
Ownership makes this scale. Each future is managed by the process that created it, so the bookkeeping is spread over all workers instead of one central scheduler, and failure recovery is local: the owner knows how to rebuild what it owns. The trade-off is fate sharing: if the owner dies, its objects die with it.
mistakes: People often think Ray is a Spark replacement for SQL and DataFrame work. In fact Ray has no query optimizer; Ray Data streams blocks through user functions. For joins, aggregations and SQL over tables, Spark, Trino or DuckDB are simpler and usually faster. Ray shines when work is heterogeneous, stateful or GPU-bound.
People often think more, smaller tasks mean more parallelism. In fact each task costs about half a millisecond of overhead, so tasks shorter than a few milliseconds spend most of their time on scheduling.
People often think ray.get() is cheap. In fact it blocks the caller and brings the data to it. Calling ray.get() inside a loop serializes the program, and calling it on many large objects can exhaust the driver's memory. Pass ObjectRefs into downstream tasks instead, or use ray.wait() to process results as they finish.
People often think actor state is fault-tolerant. In fact it lives in one process; actors are not restarted by default, and a restarted actor has fresh state unless you checkpoint it yourself.
People often think Ray's resource numbers limit real usage. In fact {"CPU": 1} is a scheduling label, not a cgroup limit; a task that starts 16 threads uses 16 cores anyway. Declare resources that match what the code really uses.
friction: Flexibility means you design the parallelism yourself: task sizes, batching, actor pools, back-pressure and where data lives. Mistakes in these choices show up as idle GPUs, scheduler overload or memory pressure rather than as errors.
Memory is the most common operational problem. The object store, worker heaps and the driver all compete for RAM. Objects stay pinned while any reference exists, so a forgotten reference leaks memory; spilling keeps jobs alive but can make them much slower; and the out-of-memory killer may terminate workers, which then shows up as retries. Ownership adds fate sharing: a crashed driver or a crashed owner task takes its objects with it.
Debugging is harder than in a single process. Errors arrive from remote workers, logs are spread across nodes, and performance problems need the dashboard, timeline traces and the "ray memory" tool. Serialization surprises are common: large closures captured by a remote function, objects that cannot be pickled, or copies where zero-copy was expected.
Operations need care too. The head node holds the GCS and is a single point of failure unless you configure GCS fault tolerance with external storage. Autoscaling with GPUs can be slow and expensive, because GPU nodes take minutes to start. Upgrades are frequent, and Ray versions on the driver and the cluster must match.
practice: Make tasks coarse: at least tens of milliseconds each, by batching items into one call. Use actors for anything expensive to initialize (models, clients, simulators) and actor pools for parallel inference. Never call ray.get() in a tight loop; pass ObjectRefs to the next task, or use ray.wait() to handle results as they finish. Put a large input once with ray.put() and pass the ref, instead of capturing it in many task closures.
Declare resources honestly: num_gpus for GPU code, num_cpus matching the threads you start, and memory for heavy tasks, so the scheduler does not overload nodes. Use placement groups for multi-GPU training so that all workers start together on the right nodes. Size the object store for your largest working set, watch spilling in the dashboard, and write big outputs to storage from the workers rather than collecting them in the driver.
For batch inference and ML preprocessing, start with Ray Data, which handles streaming, back-pressure and CPU-to-GPU pipelines for you; size the CPU stage so the GPUs never wait. For training, use Ray Train around your PyTorch code and checkpoint to cloud storage; for serving, use Ray Serve, with autoscaling bounds set from measured latency.
Run production clusters on Kubernetes with KubeRay or a managed service, enable GCS fault tolerance, and pin the same Ray and Python versions on driver and cluster. Keep SQL-style data preparation in Spark or a SQL engine and hand Ray the prepared data.

@@ dask
value: Dask is a Python library that runs familiar Python data code (pandas, NumPy, scikit-learn-style workflows and plain functions) in parallel, on all cores of a laptop or on a cluster of hundreds of machines. A Dask DataFrame is a collection of many pandas DataFrames, called partitions; a Dask Array is a grid of many NumPy arrays, called chunks. When you call an operation, Dask does not compute it. It records a task graph, a network of small Python function calls on partitions with their dependencies, and a scheduler later runs that graph on threads, processes or a cluster, spilling to disk when memory is short.
The problem it solves is the "pandas wall". Python's data tools are excellent but run on one core and need the whole dataset in memory, often 2 to 5 times its size during operations. Analysts and scientists hit this wall long before they need a Spark cluster, and rewriting their work for the JVM costs a lot. Dask keeps the same APIs and the same Python ecosystem. It is widely used in science (climate and geoscience through Xarray, imaging, genomics), in finance, and in ML preprocessing; RAPIDS uses it to spread GPU DataFrames over many GPUs, and HPC centres run it on SLURM and PBS clusters through dask-jobqueue.
It stands on two lower concepts. Python gives it everything: tasks are ordinary Python callables, data inside tasks are pandas and NumPy objects, the scheduler and workers are Python processes, and serialization uses pickle. Python also sets its limits, such as the global interpreter lock, which is why Dask's thread pools work well only for code that releases the lock (NumPy and pandas mostly do). Batch processing (L1) gives the model: a finite dataset split into partitions, lazy plans that are executed as a whole, and recovery by recomputing lost pieces. For the layer above, Dask is the parallel back end of Xarray and of many scientific and ML pipelines that want to stay in Python.
terms: Partition — one piece of a Dask DataFrame, itself a normal pandas DataFrame; partitions split the data along the index.
Chunk — one block of a Dask Array, itself a normal NumPy array.
Task graph — a set of tasks (a function plus its arguments) connected by data dependencies; the result of one task is an input to others.
Lazy evaluation — recording operations as a graph and running nothing until compute() or persist() is called.
Scheduler — the component that decides which task runs where and when: a thread pool, a process pool, or the distributed scheduler.
Worker — in a distributed cluster, a process with a thread pool that runs tasks and holds their results in memory or on disk.
Divisions — the known index boundaries of each partition; with them, Dask can route a lookup or join to the right partitions without a shuffle.
Shuffle — moving rows between partitions so that rows with the same key end up together, needed for joins and group-applies on unsorted keys.
Spilling — writing task results from a worker's memory to local disk when memory use passes a threshold.
history: Matthew Rocklin, then at Continuum Analytics (now Anaconda), created Dask as a small task-scheduling library for blocked NumPy algorithms; its first release reached PyPI in January 2015. His SciPy 2015 paper, "Dask: Parallel Computation with Blocked algorithms and Task Scheduling", described a parallel, out-of-core NumPy clone that coupled blocked algorithms with memory-aware scheduling, so that a laptop could process arrays larger than its RAM. Dask DataFrame, built the same way on top of pandas, followed soon after.
The distributed scheduler (the dask.distributed package, first released in late 2015) took Dask from one machine to clusters, with a central scheduler, workers, data locality, work stealing and a live dashboard. Xarray adopted Dask for chunked arrays, which made it the standard tool for large climate and satellite datasets. NVIDIA's RAPIDS team used it for multi-GPU DataFrames. Dask moved to calendar versioning in December 2020 (2020.12.0 followed 2.30.0). It is community-governed and fiscally sponsored by NumFOCUS, with full-time maintainers from companies including Anaconda and NVIDIA; Coiled sells it as a managed cloud service.
The DataFrame layer was then rebuilt. A peer-to-peer shuffle in the distributed scheduler, the default for clusters since early 2023, made large joins and set_index far more reliable than the old graph-based shuffle. In March 2024 (version 2024.3.0), Dask DataFrame gained a query planner, previously the separate dask-expr project, which optimizes the expression before building the graph. The legacy DataFrame implementation was removed in 2025.1.0. Recent releases in 2026 added pandas 3 compatibility and preliminary support for free-threaded Python 3.14; the current release is 2026.8.0 (August 2026).
how: Every Dask collection is a graph plus metadata. A Dask DataFrame knows its number of partitions, its divisions if the index is sorted, and its _meta, an empty pandas DataFrame with the right column names and types, so Dask can work out the type of every result without computing anything. When you write df[df.price > 10].groupby("campaign").clicks.sum(), Dask builds an expression tree, not data.
Since 2024.3.0, that expression goes through the query planner before it becomes a graph. The planner pushes column projections down, so read_parquet reads only the columns used later; pushes filters down into the Parquet reader where possible; avoids repeating a shuffle when data is already partitioned on the right column; and resizes partitions automatically when reading files. This is the same idea as a SQL optimizer, applied to pandas-style code. Only then is the expression lowered to a task graph: a set of keys, each with a Python function and arguments that may be other keys. A 2,000-partition DataFrame with five element-wise steps becomes about 10,000 tasks, many of which the planner fuses into one task per partition.
Operations fall into three shapes. Element-wise and row-wise work (arithmetic, filters, map_partitions) becomes one task per partition, with no communication. Reductions (sum, count, mean, groupby with a small result) use a tree: each partition is reduced alone, then results are combined in groups of split_every partial results at a time until one result remains. Operations that need all rows of a key together (merge on unsorted columns, set_index, groupby().apply()) need a shuffle. With a distributed cluster, Dask uses its peer-to-peer shuffle: each worker splits its partitions by the target partition of each row and sends the pieces directly to the workers that own those targets, buffering and spilling to disk, with only a small number of tasks in the graph. Without a cluster it shuffles through local disk. If the divisions are known, many of these operations avoid the shuffle completely, because Dask knows which partitions can contain which keys.
Batch processing, the second concept, appears in how the graph runs. Nothing happens until compute() (return a pandas or NumPy result to the client) or persist() (keep results in cluster memory). The local schedulers run the graph in a thread pool, the default for arrays and DataFrames, or a process pool. The distributed scheduler is a separate process that receives the whole graph from the client and sends tasks to workers. When it chooses a worker for a task, it estimates when the task could start on each candidate, counting both the worker's queue and the time to move the task's inputs over the network, and picks the earliest. When it chooses which task to run next, it prefers to finish branches already started (roughly last in, first out), so intermediate data can be freed soon. It also holds back new input tasks until workers have capacity (queuing, on by default), which stops a graph from loading all its input at once. Idle workers steal queued tasks from busy ones when the move is cheap.
Results stay on the worker that computed them, and other workers fetch them directly when they need them as inputs. The scheduler tracks where each result lives and frees it as soon as no remaining task needs it. Memory is protected by thresholds on each worker: at 60% of its memory limit (counting the results it manages) it starts writing results to disk, at 70% of total process memory it spills more aggressively, at 80% it pauses new tasks, and at 95% its nanny process kills and restarts it. Lost results are recomputed from the graph, which is the same lineage idea as Spark's.
Python, the first concept, shapes the costs. Each task is a Python function call plus scheduler bookkeeping in Python, which costs between about 200 microseconds and 1 millisecond. A graph of 10,000 tasks therefore has a few seconds of overhead, while a graph of 10 million tasks would overwhelm the single scheduler process. Inside each task, the real work runs in pandas, NumPy or Arrow code written in C, which releases the global interpreter lock, so a worker's threads can run in parallel. Pure-Python code inside tasks holds the lock; for that, use more worker processes with fewer threads each. Data moving between workers is serialized with pickle, with special handling for NumPy and pandas buffers to avoid extra copies.

example: Take 200 GB of click data in Parquet, processed on 8 workers with 4 threads and 32 GB of memory each (32 cores, 256 GB in total).
Partition size first. The Dask guide suggests about 100 MB per partition, so 200 GB / 100 MB = 2,000 partitions. A pipeline of 10 steps would give about 20,000 tasks before fusion; at 200 µs to 1 ms each, that is 4 to 20 seconds of scheduling overhead, small next to the work. Now suppose the files were written as 1 MB pieces and read one partition per file: 200,000 partitions and about 2 million tasks, which means 400 to 2,000 seconds of overhead and a slow, memory-hungry scheduler. At the other extreme, 10 GB partitions give only 20 tasks per step, so 12 of the 32 cores sit idle, and since pandas often needs 2 to 5 times a partition's size while working on it, a 10 GB partition can need 20 to 50 GB on a 32 GB worker.
Next, a reduction. Clicks per campaign is a groupby-sum, and there are 5,000 campaigns. Each of the 2,000 partitions produces a small table of at most 5,000 rows. With split_every = 8, the tree combines them in levels: 2,000 → 250 → 32 → 4 → 1, so four combine levels after the per-partition step. Only small tables cross the network; the 200 GB never moves.
Now a shuffle. Joining the clicks with a 50 GB impressions table on device_id, with no known divisions, needs every row to move to the partition that owns its key. With the peer-to-peer shuffle, roughly all 250 GB crosses the network once. At about 1 GB/s of usable network per worker, 8 workers move 8 GB/s together, so the transfer alone takes about 250 / 8 ≈ 31 seconds, plus disk spilling if the data does not fit in memory. If both tables had been written sorted by device_id, with known divisions, the join could pair partitions directly and move almost nothing.
Finally, memory limits on one worker with 32 GB: it begins spilling results to disk when managed results reach 60% (19.2 GB), spills harder at 70% of process memory (22.4 GB), stops starting new tasks at 80% (25.6 GB), and is killed and restarted at 95% (30.4 GB), after which its lost results are recomputed. If you see workers restarting, the usual cause is partitions too big for the per-task memory, not too few machines.
intuition: Cut a big table into many small pandas tables, and run your code on them like a to-do list where each item says which earlier items it needs.
This is natural because most data work is already parallel at heart. Filters and arithmetic act on each row alone, so each partition can be done by itself. Sums and counts can be done per partition and then added up. Only a few operations, such as joins on unsorted keys, really need rows from everywhere at once, and those are where the cost lives.
Recording a graph instead of running code at once is what makes the rest possible. A graph can be optimized before it runs, scheduled to keep memory low, spread over many machines, and partly recomputed after a failure, all without changing the user's pandas or NumPy code. Dask's main choice is to stay inside Python: you give up some raw speed and some scale, and in return you keep every Python library, debugger and habit you already have.
mistakes: People often think Dask makes pandas code faster on data that fits in memory. In fact parallelism has overhead, and a single pandas, Polars or DuckDB process is often faster when the data fits comfortably on one machine. Dask pays off when data is larger than memory or the work is heavy enough to use many cores.
People often think any pandas operation works the same way in Dask. In fact operations that need global order or position are expensive or unsupported: row positions with iloc, sorting, set_index and groupby().apply() trigger shuffles, and len(df) runs a computation. Many operations need a meta argument so Dask knows the output types.
People often think calling compute() several times is harmless. In fact each compute() runs the graph from the start, reading the data again. Compute several results in one call with dask.compute(a, b), or persist() a shared intermediate result first.
People often think more partitions always mean more parallelism. In fact each partition adds tasks and scheduler overhead. About 100 MB per partition, and at least a few partitions per core, is the usual balance.
friction: The central scheduler is a limit. All scheduling decisions run in one Python process, so graphs of millions of tasks become slow to submit and slow to schedule, and the scheduler's memory grows with the graph. Coarser partitions and fusion help, but very large jobs fit Spark's model better.
Shuffles and joins on unsorted keys are the expensive case. The peer-to-peer shuffle made them reliable, but they still move all the data across the network and spill to disk, and Dask has no cost-based join planning to choose join orders or broadcast sides from statistics, beyond simple rules. For SQL-style analytics on one large machine, DuckDB or Polars are usually much faster, and Spark is more mature at very large scale and has a deeper optimizer.
Pandas semantics do not always translate. Positional indexing, order-dependent operations and functions that need the whole column are restricted or costly, and user functions passed to map_partitions or apply must handle each partition independently. Debugging lazy code is harder too: an error inside a task appears only when the graph runs, far from the line that created it.
Memory behaviour needs attention. pandas' memory use can be several times the data size, unmanaged memory (memory used by libraries that Dask cannot see) can trigger pauses and restarts, and a worker restart forces recomputation of everything it held. Finally, Python code inside tasks that does not release the global interpreter lock limits each worker to about one core of real work per process.
practice: Start without Dask: try pandas with better types (categoricals, Arrow strings) or Polars or DuckDB on one machine. Move to Dask when data no longer fits or the work needs many cores, and start with a LocalCluster on your laptop before renting a cluster; the same code then runs on Kubernetes, on SLURM through dask-jobqueue, or on a managed service.
Size partitions at about 100 MB, and check df.npartitions after reading and after selective filters. Read Parquet with only the columns you need (the planner helps, but explicit is clearer) and write outputs sorted by the keys you will join on, so that later jobs have divisions and can skip shuffles. Use df.explain() to see the optimized plan.
Use the dashboard, normally on port 8787. The task stream shows idle time and communication; the memory view shows spilling and unmanaged memory; the progress view shows which step is slow. If workers spill or restart, make partitions smaller or give each worker more memory, not more workers. If CPU is low while tasks run, the code may be holding the global interpreter lock: use more processes with fewer threads each.
Call persist() on an intermediate result that several later computations reuse, and compute related results together with dask.compute(). Avoid groupby().apply() with arbitrary Python when a built-in aggregation exists, since built-ins use the cheap tree reduction instead of a shuffle. For arrays, choose chunks that match the access pattern; for example, chunk climate data by space when you analyse time series at each location.
quiz: What is a Dask DataFrame made of? || Many pandas DataFrames, called partitions, split along the index, plus metadata: the number of partitions, the divisions if the index is sorted, and an empty pandas frame (_meta) describing columns and types.
How does Dask compute a groupby-sum without moving all the data? || It runs the groupby-sum on each partition alone, producing small partial tables, then combines those tables in a tree, split_every at a time, until one result remains. Only the small partial results cross the network.
Why does the distributed scheduler hold back new input tasks and prefer to finish started branches? || To keep memory low: running branches to completion lets intermediate results be freed early, and queuing input tasks stops the cluster from loading all the input before downstream work can consume it.
You have 500 GB of data. How many partitions do you aim for, and roughly how much scheduling overhead does a 6-step pipeline add? || About 500 GB / 100 MB = 5,000 partitions. Six steps give about 30,000 tasks, and at 200 µs to 1 ms per task that is roughly 6 to 30 seconds of overhead.
When would you choose Dask over Spark, and when not? || Choose Dask when the team works in Python with pandas, NumPy or Xarray, the work includes custom array or scientific code, and data is from tens of GB to a few TB. Choose Spark for very large SQL-style ETL with many joins, where a mature optimizer, shuffle and lakehouse integration matter more than staying in Python.

@@ trino
value: Trino (originally Presto, created at Facebook in 2012) is a distributed SQL query engine for fast, interactive analytics over data that lives somewhere else. It owns no storage. Through connectors it reads lakehouse tables (Iceberg, Delta Lake, Hive), relational databases (PostgreSQL, MySQL, Oracle), Kafka, Elasticsearch and many other systems, and it can join across them in one query. A coordinator plans each query and a set of workers runs it, streaming data between them in memory, so a typical dashboard query over terabytes returns in seconds rather than minutes.
It was built to fix a specific pain. In 2012 Facebook's analysts queried a Hadoop warehouse of more than 300 PB through Hive, which compiled every SQL query into MapReduce jobs; even small questions took minutes, because each step was written to disk and every task started a new JVM. Today Trino serves ad-hoc analysis, BI dashboards, data exploration and federated queries; Starburst sells it commercially, and Amazon Athena's engine incorporates open-source Trino. The original Presto continues separately as PrestoDB at the Linux Foundation, used heavily at Meta.
It stands on two lower concepts. The JVM gives the runtime: Trino is written in Java, keeps one long-lived JVM per node shared by all queries, and generates JVM bytecode for each query's expressions so that the JIT compiler turns them into fast machine code. Distributed SQL (MPP, L1) gives the execution model: one query is split into stages, each stage runs as parallel tasks on many workers, and exchanges move data between stages by hash partitioning or broadcast. For the layer above, Trino is the SQL layer of many open lakehouses, sitting over Iceberg or Delta tables in object storage next to Spark, which does the heavy batch writing.
terms: Coordinator — the server that plans each query, schedules its tasks on workers and returns results to the client.
Worker — a server that runs tasks: it reads data through connectors and exchanges intermediate data with other workers.
Connector — a plugin that implements Trino's service provider interface for one kind of source, giving metadata, splits and data readers (and often writers).
Catalog — a configured instance of a connector, such as iceberg or postgresql; tables are named catalog.schema.table.
Split — a unit of work in a source, such as a byte range of a Parquet file or a shard of a database table.
Stage — one fragment of the distributed plan; stages form a tree, and each runs as one or more parallel tasks.
Page — Trino's unit of data in memory: a batch of rows stored column by column, one block per column.
Exchange — the transfer of pages from tasks of one stage to tasks of the next, through output buffers that consumers pull over HTTP.
Dynamic filtering — collecting the join keys of the small side at run time and using them to skip rows, files or partitions on the large side's scan.
Fault-tolerant execution — an optional mode that retries failed queries or tasks.
history: Martin Traverso, Dain Sundstrom and David Phillips joined Facebook's data infrastructure team and, with Eric Hwang, started Presto in the fall of 2012 to run low-latency analytics over Facebook's Hadoop data warehouse. The first production system ran in early 2013, and by the time Facebook open-sourced it in November 2013, more than a thousand employees ran over 30,000 queries a day on it, about 10 times more efficiently than Hive on MapReduce in CPU and latency. Its connector design let other companies point it at their own systems, and it spread quickly through internet companies and cloud services. The paper "Presto: SQL on Everything" (Sethi, Traverso, Sundstrom, Phillips and others, ICDE 2019) described clusters of up to about 1,000 nodes at Facebook processing hundreds of petabytes and quadrillions of rows per day.
In 2018 the founders disagreed with Facebook over how the project was governed, left the company, and in January 2019 created the Presto Software Foundation for their line, called PrestoSQL. In September 2019 Facebook set up a separate Presto Foundation under the Linux Foundation for PrestoDB and applied for the Presto trademark. On 27 December 2020 PrestoSQL was renamed Trino. The two projects have since diverged: Meta's PrestoDB moved toward native C++ workers built on the Velox library (described in "Presto: A Decade of SQL Analytics at Meta", SIGMOD 2023), while Trino stayed on the JVM.
Trino's largest architectural change came in May 2022 with Project Tardigrade, which added fault-tolerant execution so that long ETL queries could survive worker failures. Other steady work added a cost-based optimizer, dynamic filtering, Iceberg and Delta Lake connectors with writes, materialized views and table functions. The project releases often and follows modern Java closely: release 484 (15 October 2026) requires Java 25 and adds wider JSON support, a shared file system cache across catalogs and a limit on query output size.
how: A query begins at the coordinator. The client sends SQL over HTTP. The coordinator parses it, resolves every table through the catalogs' connectors (which supply column types and statistics), and builds a logical plan. The optimizer rewrites the plan with rules and, when table statistics exist, with costs: it pushes filters and column selections down, reorders joins, and chooses for each join whether to broadcast the smaller side to every worker or to hash-partition both sides across workers. Then it cuts the plan into fragments at every point where data must move between machines. Each fragment becomes a stage. This is the MPP model, the second concept Trino stands on: the work is split across workers, and exchanges connect the pieces.
The coordinator then creates tasks on workers through their REST API. Leaf stages read data. For each table scan, the coordinator asks the connector to enumerate splits, lazily and in small batches, and assigns them to the tasks with the shortest queues, preferring workers close to the data when locality matters. Intermediate stages do not read splits; they consume pages from the stages below. By default all stages are scheduled at once, so the whole query becomes a pipeline across the cluster. For batch-style queries a phased policy can start stages in dependency order to save memory.
Inside a task, work is organized as pipelines of operators: for example, scan, filter, project, then the probe side of a hash join and a partial aggregation. A driver is one running instance of a pipeline, and a task runs many drivers in parallel on the worker's thread pool. Data flows through operators as pages: columnar batches made of one block per column. Worker threads are shared by all queries through a multi-level feedback queue, and each driver runs for at most about one second before yielding, so a large query cannot starve small ones. This is how one cluster serves many concurrent dashboard users.
Exchanges connect stages. A task writes its output pages into an output buffer, partitioned by the next stage's hash key or copied for a broadcast. Downstream tasks pull pages from these buffers over HTTP with long polling, and each request acknowledges the previous one. Nothing is written to disk in the normal mode, so the first result rows can reach the client while later splits are still being read. If buffers stay full, Trino slows the producers; this back-pressure keeps memory bounded.
The JVM, the first concept, shapes performance. For each query, Trino generates JVM bytecode for its filter and projection expressions and for key parts of some operators, so each query's code becomes a separate class that the JIT can profile and compile into machine code specialized to it. Pages keep each column's values in large primitive arrays rather than one Java object per value, which keeps the garbage collector's work small even with large heaps; the documentation recommends giving the JVM about 70 to 85% of each node's memory. Long-lived JVMs keep compiled code warm across queries, the main reason Presto was so much faster than Hive on MapReduce, which started a new JVM per task.
Connectors are where federation happens. Each connector implements metadata (schemas, tables, statistics), split enumeration, page sources for reading and often page sinks for writing. The engine offers each connector parts of the plan to push down: filters, column selection, limits, aggregations and sometimes joins. The PostgreSQL connector can turn a WHERE clause into SQL run inside PostgreSQL; the Iceberg connector uses partition values and file statistics to skip files entirely. Dynamic filtering adds run-time pushdown: when the small side of a join has been read, its keys are collected and sent to the scan of the large side, which can then skip non-matching rows, row groups, files or partitions.
Memory and failures are where Trino differs most from Spark. Each query has memory limits per node and per cluster; when the cluster runs short of memory, Trino kills a query rather than letting the whole cluster stall. Spill to disk exists for joins and aggregations but is not the normal path. In the default mode, a worker failure fails every query that had tasks on it, and the client must retry. With fault-tolerant execution (retry-policy=QUERY or TASK), Trino can retry a whole query, or retry individual tasks; task retry requires an exchange manager that spools intermediate data to S3, Azure Blob Storage, Google Cloud Storage or HDFS. That makes long batch queries reliable, at the cost of extra latency and storage traffic.

example: An analyst asks for yesterday's spend per campaign for one advertiser, joining an Iceberg table in object storage with a PostgreSQL table, on a cluster of 20 workers:
SELECT c.name, sum(i.cost) FROM iceberg.ads.impressions i JOIN postgresql.crm.campaigns c ON i.campaign_id = c.id WHERE i.day = DATE '2026-10-25' AND c.advertiser = 'Acme' GROUP BY c.name.
Planning first. The impressions table is partitioned by day; one day holds 2 billion rows in 1,600 Parquet files of 250 MB, 400 GB in total. Partition pruning reads only that day. Column pruning reads only campaign_id and cost, about 30 GB of the 400 GB. The campaigns table has 50,000 rows, and the filter advertiser = 'Acme' is pushed into PostgreSQL, which returns 200 rows. Statistics tell the optimizer that the campaigns side is tiny, so it chooses a broadcast join: the 200 rows, a few KB, are copied to every worker, instead of shuffling 2 billion impression rows across the network.
Dynamic filtering helps more: the 200 campaign IDs are sent to the impressions scan, which drops non-Acme rows (say all but 40 million of the 2 billion) before the join, and skips whole row groups where Parquet statistics allow.
Scan time. The 30 GB of needed columns are spread as splits over 20 workers. If each worker reads about 1 GB/s from object storage, the scan takes about 30 / 20 = 1.5 seconds, or less after row-group skipping. Each worker computes a partial sum per campaign name, at most 200 groups, and sends those small tables through a partitioned exchange to the final aggregation. The result, 200 rows, streams to the client a few seconds after the query started.
Now a harder query: joining 2 billion impressions with 50 million clicks on impression_id. The clicks side must be built into a hash table. At roughly 40 bytes of data per row, doubled for hash-table overhead, that is 50,000,000 × 80 bytes = 4 GB. A broadcast join would put 4 GB on each of the 20 workers, 80 GB in total; a partitioned join hashes both sides by impression_id, so each worker builds about 200 MB of hash table, but now 2 billion impression rows cross the network. The cost-based optimizer weighs exactly this trade-off, and without statistics it may guess wrong.
Finally, failures. Suppose an ETL query runs for 40 minutes on 100 workers and, as an assumption, each worker fails with probability 0.1% per hour. The chance that some worker fails during the query is about 100 × (40 / 60) × 0.001 ≈ 6.7%. In the default mode, those runs fail and restart from zero. With retry-policy=TASK, only the lost tasks rerun, reading their inputs from the spooled exchange data.
intuition: Trino is a calculator that never owns the data: it reads where the data already lives, and it keeps every stage of the calculation running at once, passing partial results hand to hand.
This is natural for interactive questions. An analyst cares about latency, not about surviving a machine failure inside a 5-second query; if it fails, running it again costs 5 more seconds. So Trino drops the expensive insurance of writing intermediate data to disk, keeps everything in memory, and runs all stages in a pipeline. MapReduce and Spark make the opposite bet, which is right for jobs that take hours.
The connector model is just as natural. Data in a large company lives in many systems, and copying all of it into one warehouse is slow and expensive. A planner that understands each source well enough to push work into it, and an engine that can join the results, turns "where is the data?" into a catalog name in a SQL query.
mistakes: People often think Trino stores data or is a database. In fact it has no storage of its own; every table belongs to a connector, and query speed depends heavily on the source's format, layout and pushdown support.
People often think federated joins are free. In fact data from a source without pushdown is pulled through a single connection or a few splits, so joining a large table in a slow database can be dominated by reading from that database.
People often think Trino survives worker failures. In fact, in the default mode, a worker crash fails every query running on it. Fault-tolerant execution must be configured explicitly, and it adds overhead.
People often think more memory per query always fixes failures. In fact large joins fail from a wrong join distribution (broadcasting a large table) or a skewed key more often than from small limits. Table statistics and a good join order fix the cause.
friction: Memory is the main constraint. Hash joins and aggregations keep their state in memory; a query that does not fit is killed unless spill or fault-tolerant execution is configured, and a few huge queries can block many small ones. Clusters shared by dashboards and ETL need resource groups, memory limits and often separate clusters for each workload.
Without fault-tolerant execution, long queries are fragile: the chance of a failure grows with query length and cluster size. With it, intermediate data is written to external storage, which costs latency and storage traffic, and not every connector supports it.
Performance depends on everything below Trino: file sizes, partitioning, table statistics, connector pushdown, and the speed of the source. Missing statistics lead the cost-based optimizer to poor join orders or broadcasts that run out of memory. Federated queries against slow or unindexed databases put load on those systems and move a lot of data.
The coordinator is a single point of control: it plans every query, tracks every task and split, and serves results, so very high query rates or huge numbers of splits can make it a bottleneck, and its failure stops the cluster. Operating Trino also means following frequent releases and their Java requirements. Finally, it is a query engine, not an ETL platform: for long batch pipelines or streaming, Spark or Flink usually fit better.
practice: Use Trino for interactive SQL, BI dashboards and exploration over lakehouse tables, and for federated queries that join a few sources without copying them. Keep heavy, long ETL on Spark or on a Trino cluster dedicated to batch with retry-policy=TASK and an exchange manager on object storage.
Make the data easy to read: Parquet or ORC files of hundreds of MB, tables partitioned or sorted on common filters, and current statistics (run ANALYZE, or keep the table format's statistics up to date) so the cost-based optimizer chooses join orders and broadcast versus partitioned joins well. Check plans with EXPLAIN and EXPLAIN ANALYZE; look for full scans where you expected pruning, broadcasts of large tables, and stages with skewed input.
Protect the cluster. Set per-query memory and time limits, define resource groups for dashboards, ad-hoc users and batch, and watch queued queries, memory blocked, worker CPU and coordinator CPU. Size the JVM heap at about 70 to 85% of node memory, as the documentation recommends, and run the Java version the release requires.
For federation, check what each connector can push down: a filter or aggregation that runs inside PostgreSQL is far cheaper than pulling the table into Trino. Copy remote dimension tables into the lakehouse if they are joined constantly, and prefer Iceberg or Delta tables over plain Hive directories for file-level statistics and safe concurrent writes.
quiz: What do the coordinator and the workers each do in Trino? || The coordinator plans and optimizes queries, splits them into stages, schedules tasks, assigns splits and returns results. Workers run the tasks: they read splits through connectors and exchange pages with each other.
Why can Trino return results faster than a MapReduce-based engine such as early Hive? || It keeps long-lived JVMs with warm compiled code, runs all stages at once, and passes pages between stages in memory instead of writing them to disk and starting new processes for each step.
How does dynamic filtering speed up a join between a large fact table and a small filtered dimension table? || After the small side is read, its join keys are collected and pushed into the scan of the large side. The scan can then skip non-matching rows, row groups, files or partitions before they reach the join.
A build side has 30 million rows at about 80 bytes each in the hash table, on 15 workers. Compare memory for a broadcast and a partitioned join. || The hash table is 30,000,000 × 80 bytes = 2.4 GB. A broadcast join builds it on every worker, 15 × 2.4 = 36 GB in total. A partitioned join builds about 2.4 / 15 = 160 MB per worker, but must shuffle the probe side too.
When would you enable fault-tolerant execution, and what does it cost? || For long ETL or batch queries on large clusters, where a failure is likely and rerunning from scratch is expensive. It adds latency and storage traffic for spooled exchange data and is not supported by every connector, so batch clusters use it and interactive clusters usually do not.
