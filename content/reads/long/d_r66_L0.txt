@@ sns
value: Amazon SNS (Simple Notification Service) is a managed publish/subscribe service. A publisher sends one message to a **topic**. SNS then pushes a copy of that message to every **subscription** on the topic. The publisher does not know who the receivers are. A subscriber can be an SQS queue, a Lambda function, an HTTP(S) endpoint, an email address, a phone number (SMS), a mobile app (push notification) or an Amazon Data Firehose stream.
The problem is coupling. Without a topic, the service that creates an order must call billing, shipping, analytics and the email sender, one by one. Each new consumer means a change in the producer, and one slow consumer slows it. With a topic, the producer makes one call. Adding a consumer is a new subscription, with no change to the producer. SNS also covers a second job that queues do not: it reaches people and devices, not only programs. 
SNS is a **push** system and it does not keep a backlog. It delivers, retries for a while, and then forgets. This is the key difference from SQS (a queue that holds messages until a consumer pulls them) and from Kafka (a log that keeps messages and lets consumers re-read them). That is why the classic design is SNS plus SQS: SNS splits, and a queue in front of each consumer buffers. Queues are covered in the SQS read; this read covers the topic side.
Four lower concepts do the real work. Publish-subscribe (pubsub) gives the model: topics, subscriptions, and decoupling in time and identity. Delivery guarantees (deliverysem) explain why a standard topic is at-least-once and why FIFO topics add deduplication. Retries, backoff and jitter (retries) are the delivery policy of each protocol. The cloud (cloud) provides what you do not run yourself: storage in several Availability Zones, scaling to tens of thousands of publishes per second, IAM, encryption with KMS, and the telephone and mobile-push connections. The layer above is mostly Lambda and SQS consumers.
terms: Topic — a named channel with an ARN; publishers send to it and subscriptions hang off it.
Subscription — a link between a topic and one endpoint, with a protocol, an optional filter policy, an optional dead-letter queue and optional delivery settings.
Protocol — the kind of endpoint: `sqs`, `lambda`, `http`, `https`, `email`, `email-json`, `sms`, `application` (mobile push) or `firehose`.
Filter policy — a JSON document on a subscription that says which messages it accepts, by attributes or by body.
Message attribute — a typed key-value pair sent next to the message body; filter policies usually test these.
FIFO topic — a topic type with strict order inside each message group and deduplication within 5 minutes; it delivers only to SQS queues.
Message group ID — the label that defines which messages of a FIFO topic must stay in order, such as a customer ID.
Delivery policy — the retry rules for one protocol: how many attempts and how long to wait between them.
Dead-letter queue (DLQ) — an SQS queue attached to a subscription for messages SNS could not deliver.
history: SQS came first (beta 2004, general availability 2006). SNS followed in 2010 to add one-to-many push. At the start it offered HTTP, email and SQS endpoints. SMS and mobile push were added in later years. The main design choice was to keep SNS simple: a topic stores a message only until it is delivered. A backlog is the job of an SQS queue.
Subscription filter policies let each subscriber take only the messages it wants, so a topic can carry many event types. Dead-letter queues for subscriptions arrived on 14 November 2019, so a failed delivery no longer meant a lost message. FIFO topics launched on 22 October 2020, for workloads that need order and deduplication. Delivery to Amazon Data Firehose (January 2021) gives a no-code path from a topic to S3, Redshift or OpenSearch.
Since 2022 the changes have been about filtering and recovery. Payload-based filtering (22 November 2022) lets a policy look inside a JSON body instead of only at attributes. New operators (suffix, equals-ignore-case, OR) came on 16 November 2023. Message archiving and replay for FIFO topics (26 October 2023) lets a topic owner keep messages for up to 365 days and lets a subscriber replay a time window. In September 2023 SQS standard queues could subscribe to FIFO topics, which made them cheaper to consume. The `FifoThroughputScope` setting (21 January 2025) allows high-throughput FIFO topics. FCM v1 credentials are supported since January 2024, and SMS runs on AWS End User Messaging since September 2024. One thing went the other way: SNS message data protection stopped accepting new customers on 30 April 2026.
how: Step 1: create and publish. You create a topic (standard or FIFO) and call `Publish` or `PublishBatch` (up to 10 messages per call). A message has a body, optional attributes and, on FIFO topics, a group ID and a deduplication ID. The default size limit is 256 KiB and can be raised to 1 MiB with the topic attribute `MaximumMessageSize`; bigger payloads go to S3 using the Extended Client Library, and only a pointer is published. SNS checks IAM and the topic policy, can encrypt with a KMS key, and stores the message in several Availability Zones before it returns a `MessageId`. This is what the cloud layer adds: the publish is durable, but only until delivery ends.
Step 2: subscribe. A subscription binds one endpoint to the topic. HTTP(S) and email endpoints must confirm: SNS sends a confirmation message, and the endpoint calls the `SubscribeURL` (or the person clicks the link). Until then the subscription is `PendingConfirmation` and receives nothing.
Step 3: filter. By default a subscriber gets every message. A filter policy narrows this. The policy scope is `MessageAttributes` (the default) or `MessageBody`, which requires a JSON body and allows nested keys. Inside a policy, different keys are ANDed and the values in one array are ORed. Operators include exact match, prefix, suffix, equals-ignore-case, anything-but, numeric comparisons and ranges, `exists`, CIDR address match and `wildcard`. Limits: at most 5 keys, 150 value combinations, 256 KB per policy, 200 policies per topic. Policy changes can take up to 15 minutes to apply. Attribute filtering is free, and payload filtering is billed by the data scanned.
Step 4: fan out and deliver. For each matching subscription SNS creates one delivery task and pushes the message with the protocol's own rules. To SQS it calls `SendMessage`. To Lambda it makes an asynchronous invoke. To HTTP(S) it sends a POST, and the endpoint must answer within about 15 seconds. To email it uses SMTP. To mobile push it calls APNs, Firebase Cloud Messaging (FCM) or another platform service, using the device endpoint you registered. To SMS it uses the AWS SMS network. Deliveries are independent, so a slow HTTP endpoint does not hold back the SQS queue, and the order between subscribers is undefined. Raw message delivery strips the SNS JSON envelope for SQS, HTTP(S) and Firehose subscribers, so the consumer sees only the original body.
Step 5: retry. Each protocol has a delivery policy, with jitter on every wait. SNS retries when the endpoint is unavailable (server-side). For AWS-managed endpoints (SQS, Lambda, Firehose) the policy is 3 immediate tries, 2 tries 1 second apart, 10 tries with exponential backoff from 1 to 20 seconds, and then 100,000 tries 20 seconds apart: 100,015 attempts over about 23 days. For customer-managed endpoints (email, SMS, mobile push) it is 2 tries 10 seconds apart, 10 tries with backoff from 10 to 600 seconds, and 38 tries 600 seconds apart: 50 attempts over about 6 hours. Only HTTP(S) can be tuned: the `healthyRetryPolicy` sets minimum and maximum delay, retry counts and the backoff function (linear, arithmetic, geometric, exponential). The default is only 3 retries 20 seconds apart, and the total time cannot exceed 3,600 seconds. HTTP status 5xx and 429 are retried. Any other error, such as 400 or 404, is a permanent failure and is not retried. A `throttlePolicy` with `maxReceivesPerSecond` slows delivery to protect your endpoint without using up retries.
Step 6: give up safely. Client-side errors (the queue was deleted, the policy blocks SNS) are not retried. When retries run out, SNS discards the message unless the subscription has a redrive policy that names a DLQ. The DLQ is an SQS queue in the same account and Region (FIFO for a FIFO subscription). It belongs to the subscription, not the topic, because delivery happens per subscription. 
FIFO topics change steps 1 and 4. Messages with the same group ID are delivered in publish order, and SNS gives each message a 128-bit sequence number per group. A deduplication ID, or a hash of the body if content-based deduplication is on, makes SNS accept but not deliver a repeat within 5 minutes. Different groups run in parallel, each up to 300 messages per second. FIFO topics deliver only to SQS queues (FIFO for strict order, standard for cheaper best-effort), and a subscription to an email, SMS, mobile or HTTP(S) endpoint is refused. To reach a Lambda function, put an SQS queue in between.

example: A shop publishes 20 million order events per month to the topic `orders`. Each event is about 2 KB. It carries attributes `event` (String), `region` (String) and `amount` (Number). Three consumers subscribe. The analytics queue has no filter and gets everything. The shipping queue has this policy:
```json
{
  "event": ["order_created"],
  "region": [{"prefix": "eu-"}]
}
```
The fraud function has `{"amount": [{"numeric": [">=", 500]}]}`. Now publish one event: `event=order_created`, `region=eu-west`, `amount=250`. Analytics matches (no policy). Shipping matches, because `event` equals `order_created` and `region` starts with `eu-`. Fraud does not match, because 250 is below 500, and SNS does not call it at all. One publish led to two deliveries.
Now a failure. The shipping queue's owner changes the queue policy by mistake, and SNS can no longer send to it. This is a client-side error, so SNS does not retry. The message goes to the shipping subscription's DLQ if one is set, and is lost if not. Analytics keeps working. Later the owner fixes the policy. New messages flow again, but the old ones sit in the DLQ until you drain them. Compare a server-side error: if SQS has an outage, SNS retries on the AWS-managed schedule, from 1 s up to 20 s apart, for up to 23 days.
Now an HTTPS subscriber with `numRetries` 50, `numNoDelayRetries` 3, `numMinDelayRetries` 2, `numMaxDelayRetries` 35, delays from 1 to 60 s, exponential. The backoff phase has 50 − 3 − 2 − 35 = 10 tries. The waiting time is at most 2 × 1 s + 10 × 60 s + 35 × 60 s, about 2,700 s, which fits under the 3,600 s ceiling.
Last, cost, from the AWS price list for US East (N. Virginia), October 2026. Standard topic requests cost $0.50 per million, and each 64 KB of payload counts as one request, so 20 million 2 KB publishes cost 20 × $0.50 = $10. Delivery to SQS and Lambda has no per-message charge. HTTP delivery costs $0.60 per million after the first 100,000 each month. A single 200 KB message counts as 4 requests (200 / 64 rounded up). On a FIFO topic, publishing costs $0.30 per million requests plus $0.017 per GB, and each delivery costs $0.01 per million plus $0.001 per GB.
intuition: A post office box that makes copies: you drop one letter in, the clerk copies it and hands one to each person on the list, and does not keep the original once the copies are delivered.
This design is natural because the producer and the consumers have different needs. The producer wants to say "this happened" once and move on. Each consumer wants to react in its own way and at its own speed. A topic is the smallest thing that separates those two sides: it holds a list of interested parties and nothing more. Keeping data is a different job (disk, retention, offsets, replay), so SNS leaves it to SQS or to a log such as Kafka. Pushing also fits people and devices, because a phone cannot poll your servers.
mistakes: People often think SNS keeps messages for subscribers that are down. In fact SNS only retries for a limited time and then drops the message unless a DLQ is set. Standard topics have no replay. For long outages, put an SQS queue between the topic and the consumer.
People often think every failed delivery is retried. In fact only server-side failures follow the retry policy. If the endpoint is gone or its policy blocks SNS, SNS does not retry. For HTTP(S), only 5xx and 429 are retried, and a plain 400 or 404 is final.
People often think a FIFO topic gives exactly-once processing from end to end. In fact deduplication covers only a 5-minute window on the publish side, and the AWS documentation lists conditions: the SQS FIFO consumer must delete the message before its visibility timeout ends, and the subscription must have no filter policy (with a filter, delivery is at-most-once from the topic's point of view, since messages can be filtered out).
People often think a filter policy applies the moment you save it. In fact a change can take up to 15 minutes, so a deploy that changes a filter and a publisher together can briefly mis-route messages.
friction: A standard topic has no memory. There is no offset, no backlog view and no replay. You cannot ask what subscriber X missed yesterday, except through a DLQ, delivery logs or your own archive (for example a Firehose subscription writing to S3). FIFO topics can archive up to 365 days and replay, but only FIFO topics.
Delivery is at least once and order is best effort on standard topics. Duplicates happen on retries and lost acknowledgements. Two subscribers can see the same messages in different orders, and even FIFO topics promise no order between subscribers. Every consumer must be idempotent.
Quotas are per account per Region. The publish limit is 30,000 per second in US East (N. Virginia), 9,000 in US West (Oregon) and Europe (Ireland), and 1,500 or 300 in many other Regions for standard topics. A standard topic can have 12.5 million subscriptions, a FIFO topic only 100. A FIFO topic with default settings is capped at 3,000 messages or 20 MB per second; with `FifoThroughputScope` set to `MessageGroup` each group gets 300 per second, and you cannot switch back. A sudden jump in FIFO traffic can cause throttling for up to the 5-minute deduplication window while partitions are added.
Protocol limits: HTTP(S) endpoints must be public, because SNS does not support private HTTP(S) endpoints, and must answer in about 15 seconds. Mobile push depends on device tokens that go stale, and SNS disables endpoints that the platform rejects. If a device is offline longer than the push TTL (SNS default 4 weeks), the message is dropped. SMS needs a sandbox exit, sender registration in some countries, and country-specific prices.
Delivery success is visible only through CloudWatch metrics and delivery status logs that you must turn on.
tradeoffs: Choose SNS plus SQS fan-out when several services need the same event and each must keep working if the others are slow or down. Each queue has its own backlog, DLQ and scaling. You give up simplicity: more resources and policies, and one more hop.
Choose SNS directly to Lambda or HTTP(S) when events are low-volume and a message lost after retries is acceptable or caught by a DLQ. If the consumer is slow or bursty, use a queue in between: SNS can push faster than a webhook can take, and the HTTP default is only 3 retries.
Choose a standard topic when duplicates are harmless and you want every protocol and the highest throughput. Choose a FIFO topic when order per entity matters (price updates for one product) and the subscribers are SQS queues. Use a group ID with many distinct values. You give up protocols (SQS only), subscribers (100 per topic), topics (1,000) and some throughput, and exactly-once does not survive filter policies.
Choose SNS over EventBridge when you need very high publish rates (up to 30,000 per second per Region, against a classic-bus default of 10,000 PutEvents per second in US East), push, SMS or email, or plain fan-out. Choose EventBridge to route AWS and SaaS events with rich content rules, a schema registry and scheduling, if 5 targets per rule is enough on the classic bus. EventBridge retries for 24 hours and 185 times by default, much shorter than SNS's 23 days for SQS and Lambda. 
Choose Kafka, MSK or Kinesis when consumers must replay history or read from an offset, or the data is a long-lived log. Choose SNS when the event is a notification that is gone once delivered. Kafka gives replay but needs partition planning; SNS needs no operations but has no memory.
practice: Start from the failure case. For every subscription, write down what happens if the endpoint is down for 1 hour, 1 day and 1 week. For anything important use SNS to SQS, set a DLQ on the subscription (same account and Region), set the SQS queue's own DLQ, and alarm on `ApproximateNumberOfMessagesVisible` of both DLQs. Use that metric and not `NumberOfMessagesSent`, which does not count messages moved to a DLQ.
Put the routing data in message attributes (event type, tenant, version) and write filter policies on them. Attribute filtering is free and fast. Use payload-based filtering only when you cannot change publishers, because it is billed by data scanned. Roll out filter changes before the publisher change that needs them.
Turn on raw message delivery for SQS subscribers, so consumers parse your JSON and not the SNS envelope. For HTTP(S) endpoints, keep the envelope and verify its signature, using signature version 2 (SHA-256) when you can. Answer HTTP deliveries fast with 2xx and do the work later. Return 5xx only when you want a retry.
Make consumers idempotent with a stable business key; FIFO deduplication covers only 5 minutes. For FIFO, use the entity ID as group ID, and create the topic with `FifoThroughputScope=MessageGroup` if you may need more than 3,000 messages per second. Enable high throughput on the subscribed SQS FIFO queues too.
Turn on delivery status logging to CloudWatch. If you encrypt with a customer-managed KMS key, grant SNS and the publishers access to the key. Use PublishBatch for volume. For SMS, leave the sandbox early, register sender IDs where required and set a spend threshold. For push, refresh device tokens at each app start and delete disabled endpoints.
interview: Why is SNS usually paired with SQS, and what does each give you? || SNS gives one-to-many push and filtering, but no backlog: it retries for a while and then drops the message. An SQS queue per consumer gives each service its own buffer, retries, DLQ and scaling, so a slow consumer cannot hurt the others. SNS is the splitter and SQS is the buffer.
A subscriber is down for two hours. What happens on a standard topic to an SQS, a Lambda and an HTTPS subscriber? || SQS and Lambda are AWS-managed targets, so SNS retries for up to about 23 days and delivers when they return. The default HTTPS policy is 3 retries 20 seconds apart, so the message is dropped after about a minute unless you extend the policy (3,600 s at most) or set a DLQ. A client-side error is never retried.
How does a FIFO topic keep order and remove duplicates, and where does the guarantee end? || Order is per message group ID, with a sequence number per group; groups run in parallel, up to 300 messages per second each. A repeated deduplication ID within 5 minutes is accepted but not delivered. The guarantee ends at the SQS FIFO consumer and weakens with filter policies.
When would you pick EventBridge or Kafka over SNS? || EventBridge for AWS and SaaS event routing with rich rules, schema registry and archive, at lower rates. Kafka or Kinesis when consumers need replay from an offset or many independent readers of a long history. SNS for simple push fan-out, very high publish rates, or email, SMS and mobile.
Throttling appears on a FIFO topic when traffic doubles. What do you check? || The Regional account quota, the per-topic 3,000 per second limit in `Topic` scope, and the spread of group IDs. Switch to `MessageGroup` scope (one-way), use many distinct group IDs, enable high throughput on the SQS FIFO queues, and expect brief throttling while partitions are added.
quiz: What does an SNS subscription need besides the topic? || A protocol and an endpoint (for example `sqs` and a queue ARN). It can also have a filter policy, a DLQ and delivery settings. HTTP(S) and email subscriptions must be confirmed first.
Why does SNS retry an SQS target for about 23 days but an email target for only about 6 hours? || SQS and Lambda are AWS-managed endpoints that are expected to come back, so the policy allows 100,015 attempts (the last 100,000 every 20 s). Email, SMS and mobile push are customer-managed, so the policy is 50 attempts with backoff up to 600 s.
Why can a filter policy be wrong for up to 15 minutes after you change it? || Filter policies are eventually consistent, so a change can take up to 15 minutes to reach every delivery node. Old and new rules may both be used meanwhile.
A message body is 200 KB on a standard topic. How many requests are billed, and what do 20 million such publishes cost at $0.50 per million requests? || Each 64 KB chunk is one request, so 200 / 64 rounds up to 4 requests per message. 20 million messages are 80 million requests, so 80 × $0.50 = $40, before any delivery charges.
You need ordered updates per customer, and the consumers are one Lambda function and one webhook. Can you subscribe them to a FIFO topic directly? || No. FIFO topics deliver only to SQS queues. Publish with the customer ID as group ID and subscribe one SQS FIFO queue per consumer. The Lambda function reads its queue through an event source mapping, and a small worker reads the other queue and calls the webhook.
