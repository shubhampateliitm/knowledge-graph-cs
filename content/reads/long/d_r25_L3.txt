@@ hashtables
value: A hash table stores key-value pairs and finds the value for a key in constant time on average, no matter how many pairs it holds. A list needs a scan of n items. A sorted array or a tree needs about log₂ n steps (20 steps for a million keys). A hash table computes where the key lives from the key itself, so a lookup is usually one or two memory reads. This is the data structure behind Python dict, Java HashMap, Go map, Redis, symbol tables in compilers, deduplication, caches and the hash join in Spark and every database.
The layer above uses it everywhere. Partitioning and shuffle decide which machine receives a record with hash(key) mod N. Keyed state in a stream processor is a hash map per task. An LRU cache is a hash map plus a linked list. Bloom filters, HyperLogLog and count-min sketches are all hash functions writing into small arrays. Log compaction keeps a map from each key to its latest offset. If you remove hash tables from a modern data platform, almost nothing still works.
The layers below explain why it works and when it fails. Number theory (L4) gives the arithmetic of hash functions: reduction modulo a prime or a power of two. Probability (L4) says that if hash values look random, the expected chain or probe length depends only on the load factor, not on n. The birthday bound (L4) says collisions are not rare: after only about √m insertions into m slots, two keys probably share a slot, so every design needs a collision plan. Randomized algorithms (L3) supply universal hashing, where the function is chosen at random so no fixed input can hurt it. Amortized analysis (L3) shows that doubling the array when it fills makes insertion O(1) on average even though one insertion sometimes copies everything.
terms: Hash function — a function that maps a key of any size to a fixed-size number; equal keys always give equal numbers, and different keys should give very different numbers.
Bucket (slot) — one position in the table's underlying array.
Collision — two different keys that map to the same bucket.
Chaining — a collision strategy where each bucket holds a list (or tree) of all entries that landed there.
Open addressing — a collision strategy where all entries live in the array itself, and a colliding key is placed in another slot found by probing.
Probe sequence — the order of slots a lookup visits: linear probing tries i, i+1, i+2 and so on.
Load factor (α) — number of entries divided by number of buckets; the main measure of how full the table is.
Tombstone — a marker left in a slot after a deletion in open addressing, so that later lookups do not stop early.
Universal hashing — choosing the hash function at random from a family, so that for any two different keys the chance of collision is at most 1/m.
history: The idea appeared inside IBM in the early 1950s. Hans Peter Luhn wrote an internal memo in January 1953 that used buckets with linked lists, which is chaining. In the same period Gene Amdahl, Elaine Boehme, Nathaniel Rochester and Arthur Samuel used open addressing with linear probing in an assembler for the IBM 701. Memory was tiny and drums were slow, so a way to compute an address from a key instead of searching was very attractive. The name "hashing" comes from the picture of chopping a key into pieces and mixing them. Arnold Dumey (1956) and W. W. Peterson (1957) published early analyses.
In 1963 Donald Knuth analysed linear probing for the first time with exact mathematics. He often says this was the day he decided to study the analysis of algorithms as a field. His result still guides practice: the expected number of probes depends on the load factor α, and it explodes as α approaches 1.
Carter and Wegman (1977, journal version 1979) introduced universal hashing. Before this, the analysis assumed that keys are random. Their idea moved the randomness from the data to the algorithm: pick the function at random, and the guarantee holds for every input. Pagh and Rodler (2001) described cuckoo hashing, where a key has two possible places and lookup always takes at most two probes. Celis (1986) proposed Robin Hood hashing, which reduces the variance of probe lengths.
The security side became important later. Crosby and Wallach (USENIX Security 2003) showed that an attacker who knows the hash function can send keys that all collide and turn O(1) lookups into O(n). In 2011 researchers showed the attack working on many web frameworks, and languages reacted: Python switched to the keyed hash function SipHash in version 3.4 (2013), and Rust uses SipHash-1-3 by default. Engineering also changed. Google's Abseil library introduced the "Swiss table" at CppCon 2017, which probes 16 slots at once with SIMD instructions. Rust's standard HashMap has used a port of it (the hashbrown crate) since Rust 1.36 (2019), and Go 1.24 (2025) replaced its built-in map with a Swiss-table design.
how: A hash table has an array of m buckets and a hash function h. To insert key k, compute h(k) mod m, which gives a bucket index. To look up k, compute the same index and look there. The hash function is the first thing that matters. It must be deterministic, fast, and must spread keys so that every bucket is about equally likely. Number theory enters here: reducing modulo a prime, or multiplying by a large odd constant and keeping the high bits (multiplicative hashing), mixes the bits of the key. If the table size is a power of two, a plain "mod m" keeps only the low bits, so a weak hash that ignores high bits will cluster. Good functions (MurmurHash, xxHash, SipHash, wyhash) mix every input bit into every output bit.
Collisions are certain. The birthday bound says that with m = 1,000,000 buckets, the first collision is expected after only about √(π·m/2) ≈ 1,250 insertions, long before the table is full. So the table needs a rule for what to do. With chaining, each bucket points to a list of entries. Insert adds to the list; lookup walks the list comparing keys. Expected list length is the load factor α = n/m, so a successful lookup costs about 1 + α/2 comparisons and an unsuccessful one about α. Java's HashMap uses chaining, and since Java 8 it converts a long chain (8 or more entries, when the table has at least 64 buckets) into a balanced tree, so a hostile input costs O(log n) instead of O(n).
With open addressing there are no lists. Every entry is stored in the array. If slot h(k) is taken, the table probes another slot, and the lookup repeats the same sequence until it finds the key or an empty slot. Linear probing, which steps to the next slot, is the fastest in practice because consecutive slots share a cache line, so the extra probes are cheap. Its weakness is primary clustering: runs of occupied slots grow and merge. Knuth's formulas for the expected probes are ½(1 + 1/(1−α)) for a hit and ½(1 + 1/(1−α)²) for a miss. At α = 0.5 that is 1.5 and 2.5 probes; at α = 0.9 it is 5.5 and 50.5. This is why open-addressing tables resize well before they are full. Deletion is awkward: simply emptying a slot would break the probe chain of other keys, so the slot gets a tombstone, and tombstones are cleaned up at the next resize.
Modern designs refine this. Robin Hood hashing lets a new key steal a slot from an entry that is closer to its home position, which keeps probe lengths even. Swiss tables keep a separate array of one-byte control tags, one per slot, holding 7 bits of the hash. A lookup loads 16 tags with one SIMD instruction, compares them with the key's 7-bit tag at once, and checks the actual key only for the few slots that match. Because the tags are compact, most unsuccessful lookups never touch the key array at all. Abseil runs these tables at a maximum load of 7/8.
Resizing is where amortized analysis helps. When α passes a limit (0.75 in Java, about two thirds in CPython, 7/8 in Swiss tables), the table allocates an array twice as large and re-inserts every entry, because each index depends on m. One resize costs O(n). But the sizes double, so across n insertions the total copying is n + n/2 + n/4 + … < 2n. The average extra cost per insertion is a constant, and the table is O(1) amortized. The price is that one unlucky insertion pauses for the whole copy. Redis avoids the pause by growing incrementally: it keeps two tables and moves a few buckets on every operation.
Finally, the probability layer states the promise exactly. If h behaves like a random function, then the expected cost of an operation depends only on α. Universal hashing makes this true without assuming anything about the keys: with a function chosen at random from a universal family, any two keys collide with probability at most 1/m. Production tables usually do not pick a truly random function per table, but they seed the hash with a random value per process (Python, Rust) so an attacker cannot predict collisions.

example: Use the table in the diagram: 8 slots, h(k) = k mod 8, linear probing, maximum load 0.75. Insert 17, 25, 9, 4 and 12 in this order. Key 17 goes to slot 1. Key 25 has home slot 1 (25 mod 8 = 1), which is taken, so it moves to slot 2. Key 9 also has home slot 1, so it checks slots 1 and 2 and lands in slot 3. Key 4 goes to its home slot 4. Key 12 has home slot 4, which is taken, so it takes slot 5. We have 5 entries, so α = 5/8 = 0.625.
Now look up 33, which is not in the table. Its home slot is 33 mod 8 = 1. The lookup visits slots 1, 2, 3, 4, 5 and stops at slot 6, which is empty. That is 6 probes for one miss, while the formula for α = 0.625 predicts ½(1 + 1/0.375²) ≈ 4.1 on average. Our small, unlucky cluster is slightly worse than the average. Look up 9: slots 1, 2, 3 give 3 probes.
Delete 25. If we just empty slot 2, a later lookup of 9 would stop at slot 2 and wrongly say "not found". So we write a tombstone in slot 2. Lookup of 9 now passes over the tombstone and finds 9 in slot 3. A new insert of key 1 (home slot 1) may reuse the tombstone slot, after checking that key 1 does not already exist further along.
Insert 6, which goes to slot 6. Now 5 live entries and 1 tombstone use 6 of 8 slots, so α = 0.75 if tombstones are counted (they must be, because probes pass through them). The next insert would pass the limit, so the table first resizes to 16 slots and re-inserts only the live keys with h(k) = k mod 16: 17 → 1, 9 → 9, 4 → 4, 12 → 12, 6 → 6. The keys spread out, the old cluster is gone, and the tombstone disappears. The copying cost 5 re-insertions, which is about 1 extra operation for each of the insertions that came before it.
intuition: A coat check: your ticket number tells the attendant exactly which hook to go to, and a few unlucky tickets share a hook.
The idea is natural once you accept two facts. First, you cannot beat a direct jump: if the key tells you the address, you need no search. Second, you cannot make a perfect key-to-address map for all possible keys, because there are far more keys than slots, so collisions must be handled. Hashing separates the two jobs. The hash function makes keys look random, so that the load is spread evenly. The collision rule, chaining or probing, deals with the few clashes that remain. Probability then shows that the clashes stay few as long as the table is not too full. Resizing keeps it that way.
mistakes: People often think a hash table lookup is always O(1). In fact it is O(1) on average, under the assumption that the hash values spread evenly. With a bad hash function, or with keys chosen by an attacker, every key can land in one bucket and the lookup becomes O(n). Algorithmic-complexity attacks on web frameworks were real, and this is why Python and Rust use keyed hashes.
People often think a larger table is always better. In fact a table that is far too large wastes memory and also hurts speed, because entries spread over more cache lines and memory pages. Hash tables are already cache-unfriendly: a lookup is a random memory access, about 80 to 100 ns on a miss to main memory. Keep the load factor in the range the implementation is designed for.
People often think hash order is the same as insertion order or sorted order. In fact a classic hash table has no useful order, and iteration order may change after a resize. Python dict keeps insertion order (guaranteed since 3.7) by storing entries in a separate compact array and using the hash table only to hold indices into it. Java HashMap makes no promise, and LinkedHashMap adds a linked list to provide one.
People often think the hash of a value can be stored or compared across machines and versions. In fact built-in hashes are often randomized per process and change between versions. Never write Python hash() or Java hashCode() into files or use them to place data on shards. Use a specified function such as MurmurHash3, xxHash or SHA-256 with a fixed seed when the value must be stable.
friction: Hash tables give up order. Range queries ("all keys between a and b"), nearest neighbour and sorted iteration need a tree or a sorted structure, and this is why database indexes are mostly B-trees and hash indexes are limited to equality. A hash index also cannot be efficiently compressed or merged like sorted runs.
Resizing causes latency spikes. Doubling a table of 100 million entries copies gigabytes in one go, and for a service with a latency target this is a visible pause. Incremental rehashing (Redis, Go's old map) avoids the spike but needs two tables during the move, so memory use is temporarily higher and code is more complex. Tombstones add another cost: a table with many deletions can have a low live count but still slow probes, until a rebuild.
Memory overhead is large in managed languages. A boxed Java entry carries an object header, pointers and a cached hash, so a map of small integers can use 10 times the memory of the raw data. Open-addressing tables with inline entries avoid that, but they copy large values on resize and move them in memory, which breaks pointers to entries.
practice: Choose the structure by the question you ask. For "does this key exist" or "give me the value for this key" use a hash table. For anything with order or ranges use a tree or sorted array. If keys are small integers in a dense range, a plain array is better than any hash table.
Pre-size the table when you know the count. In Java, `new HashMap<>(expected / 0.75 + 1)`; in Rust, `HashMap::with_capacity`; in Python, building a dict from a list of pairs is already efficient. This avoids repeated resize and rehash. In Spark, watch for hash aggregation spilling: when the aggregation map no longer fits in the memory given to the task, the engine falls back to sort-based aggregation or spills partial maps to disk, and the job slows down sharply.
Use a hash function that fits the job. For in-memory tables use the language default, which is already tuned and often keyed. For partitioning data across machines or files, use a stable, specified function and remember that hash(key) mod N moves almost every key when N changes; consistent hashing or a fixed large number of virtual partitions fixes this. For untrusted keys, use a keyed function such as SipHash. For checksums or content addresses use a cryptographic hash, not a table hash.
Watch skew. Even a perfect hash function does not help if one key is far more frequent than others: a single hot key in a shuffle sends millions of rows to one reducer. Salt the hot key, or pre-aggregate before the shuffle. Finally, measure: the difference between a boxed map and a flat open-addressing map is often a factor of 2 to 5 in speed and memory for million-entry tables.
tradeoffs: Choose chaining when entries are large or deleted often, when the load factor may exceed 1, or when you need stable pointers to entries (the list nodes do not move on resize). Choose open addressing when entries are small, because inline storage and sequential probes use the CPU cache well; a flat table is often 2 to 3 times faster than a node-based one for lookups in a table that fits in cache. You give up simple deletion and stable addresses.
Choose linear probing with a low load factor (below about 0.7) when speed is the goal and the hash is good. Choose Robin Hood or Swiss-table layouts when you want to run at 0.85 to 0.9 load without the miss cost exploding, as Knuth's formula predicts at 50 probes for α = 0.9 with plain linear probing. The price is a more complex implementation and a control-byte array.
Choose a hash table over a balanced tree when you only need point lookups: O(1) expected against O(log n), and typically 2 to 5 times faster at a million keys. Choose the tree when you need sorted iteration, range scans, predecessor queries, or a worst-case latency guarantee, because a tree never has a resize pause or a collision storm. Choose a B-tree over a hash index in a database for the same reason, and because the B-tree handles data on disk with few block reads.
interview: Why is hash table lookup O(1) on average but O(n) in the worst case, and how do real systems protect against the worst case? || With a good hash function, keys spread evenly and the expected chain or probe length is a constant that depends only on the load factor. If all keys collide, one bucket holds everything and a lookup scans n entries. Systems defend with a random seed per process (SipHash in Python and Rust), universal hashing, or by turning long chains into balanced trees as Java 8 does, so the worst case is O(log n).
Walk me through why doubling the array makes insertion amortized O(1). What if you grow by a constant, like 100 slots, instead? || Doubling means resizes happen at sizes n, 2n, 4n and so on, so copies total less than 2n over n insertions, which is about 2 copy operations per insert on average. Growing by a fixed amount copies n + (n−100) + … which is about n²/200 in total, so insertion becomes O(n) amortized. Geometric growth is required.
You have a hash table that has been running for weeks with many inserts and deletes and it has become slow even though it holds few entries. What happened? || In an open-addressing table, deleted slots become tombstones. Lookups must probe through them, and they are not reused until a rebuild, so probe lengths grow even when the live count is low. Fix by counting tombstones toward the load factor and rehashing in place, or by using a design such as backward-shift deletion.
Your distributed job partitions with hash(key) mod 64 and sometimes one task runs 50 times longer than the rest. Diagnose it. || This is skew, not a bad hash: a few hot keys all hash to one partition. I would check key frequency, then salt hot keys across several partitions and merge afterwards, or pre-aggregate on the map side. A better hash function does not help because equal keys must always land together.
quiz: What is a collision, and why can a hash table never avoid them? || A collision is two different keys mapping to the same bucket. The number of possible keys is far larger than the number of buckets, and the birthday bound says that even with random hashing, collisions start after about √m insertions into m buckets.
Why must a hash table resize by a constant factor such as 2 rather than by a fixed number of slots? || Geometric growth makes the total copying cost over n insertions less than 2n, which gives O(1) amortized insertion. Adding a fixed number of slots each time makes the total copying grow like n², so insertion becomes O(n) amortized.
A linear-probing table has load factor 0.9. About how many probes does an unsuccessful lookup need, and what about at 0.5? || Using ½(1 + 1/(1−α)²): at α = 0.9 about 50.5 probes, at α = 0.5 about 2.5 probes. This is why open-addressing tables resize at 0.7 to 0.875 and not near full.
Why does deleting from an open-addressing table need a tombstone? || Lookups stop at the first empty slot. If a deleted entry's slot were emptied, a key that was placed after it by probing would become unreachable. The tombstone says "keep probing" until the next rebuild.
You need to store 50 million user IDs and test membership, with ordered scans never needed. Hash set or sorted array with binary search? || A hash set gives about one cache miss per lookup but costs 2 to 3 times the raw data size in memory. A sorted array of 8-byte IDs is 400 MB, compact and cache-friendly for scans, but each lookup is about 26 steps with several cache misses. If lookups are very frequent and memory allows, use a flat hash set; if memory is tight or the set is static, use the sorted array.

@@ trees
value: A tree is a structure where every item has one parent and any number of children, with one root at the top. This simple shape solves a problem that arrays and hash tables cannot: keeping data both fast to change and in order. A sorted array finds a key in log₂ n steps but needs O(n) moves to insert. A hash table inserts in O(1) but has no order. A balanced search tree does find, insert, delete, smallest, largest, predecessor and range scan all in O(log n). For a million keys, log₂ n is about 20 steps; for a billion keys it is 30.
Three families matter in practice. Search trees (binary search trees, AVL, red–black, B-trees) keep keys sorted. Heaps keep only the minimum (or maximum) at the top, which is exactly what a priority queue, a scheduler timer list or the "k best candidates" step of a search needs. Tries keep strings by shared prefix, so lookup costs the length of the key, not the size of the set. Java TreeMap, C++ std::map, Linux scheduler queues, database indexes, file system directories and autocomplete engines are all built from these.
The layers below give the foundations. Graph theory (L4) defines a tree as a connected graph with no cycles and gives the facts we use all the time: n nodes have n − 1 edges, there is exactly one path between any two nodes, and a tree of height h has at most 2^(h+1) − 1 nodes in the binary case. Proofs and induction (L4) are how we know the invariants hold: each rotation preserves the sorted order, each insertion keeps the heap property, and the height stays logarithmic. Above this layer, B-trees, inverted indexes, suffix trees, union–find, segment trees and Monte Carlo tree search are all trees with one more idea added.
terms: Node, root, leaf — a node holds data and links to its children; the root has no parent; a leaf has no children.
Height — the number of edges on the longest path from the root to a leaf; most operations cost O(height).
Binary search tree (BST) — a binary tree where every key in the left subtree is smaller than the node and every key in the right subtree is larger.
Balanced tree — a tree that keeps its height O(log n) by rebalancing after updates; AVL and red–black trees are the common kinds.
Rotation — a local rewiring of two or three links that changes the shape of a tree but keeps the in-order sequence of its keys.
Heap — a tree where every parent is smaller than (min-heap) or larger than (max-heap) its children; it gives fast access to the extreme element only.
Trie (prefix tree) — a tree where each edge is a character, and each path from the root spells a prefix of some key.
Fan-out — the number of children per node; a high fan-out gives a short tree, and B-trees use fan-outs of hundreds.
In-order traversal — visiting the left subtree, the node, then the right subtree; on a BST it yields the keys in sorted order.
history: Trees as a mathematical idea are old: Arthur Cayley counted trees in 1857, and family trees are older than that. For computers, the first binary search trees were described independently in the late 1950s, as machines needed to keep sorted tables that change. The weakness showed quickly: insert sorted keys 1, 2, 3, … into a plain BST and it becomes a linked list with height n.
The fix was balancing. Georgy Adelson-Velsky and Evgenii Landis published the AVL tree in 1962. It stores a balance value at each node and rotates to keep the left and right heights within 1 of each other, so the height stays below about 1.44 log₂ n. In 1972 Rudolf Bayer described "symmetric binary B-trees", which Leonidas Guibas and Robert Sedgewick (1978) recast as red–black trees. Red–black trees allow a looser balance (height at most 2 log₂(n+1)) and so do fewer rotations on updates, and that is why they became the standard in libraries.
Disk changed the design again. In 1970 Rudolf Bayer and Edward McCreight at Boeing invented the B-tree (paper published in 1972) for indexes on disk, where one node should fill one disk block and one block read is what costs. Heaps came from J. W. J. Williams (1964), who invented the binary heap for heapsort, and Robert Floyd showed in the same year that a heap can be built in O(n) time. René de la Briandais (1959) and Edward Fredkin (1960) described tries; Fredkin named them after "retrieval". Donald Morrison's PATRICIA (1968) compressed chains of single-child nodes, an idea now called a radix tree. Later work added randomization (treaps by Aragon and Seidel, 1989; skip lists by Pugh, 1989) and self-adjusting trees (splay trees by Sleator and Tarjan, 1985).
how: A binary search tree keeps one rule: for every node, all keys in its left subtree are smaller and all keys in its right subtree are larger. To search for k, start at the root. If k equals the node's key, stop. If k is smaller, go left; if larger, go right. Every step discards a whole subtree, so the cost is the height of the tree. Insertion searches for k, falls off the tree at a missing child, and places the new node there. Deletion of a node with two children replaces it by its in-order successor (the smallest key in the right subtree) and then removes that node, which has at most one child. An in-order walk visits the keys in sorted order, and the smallest and largest keys are the leftmost and rightmost nodes, so range queries are natural: find the start, then walk in order until the end.
Everything depends on the height, and a plain BST gives no promise: random insertions give an expected height of about 2 ln n (roughly 1.39 log₂ n), but sorted input gives height n. Balanced trees enforce a bound with rotations. A rotation takes a node and its child and swaps their roles, moving one subtree across, and the in-order sequence of keys does not change. An AVL tree checks after each insert that at every node on the path back to the root the two subtrees differ in height by at most 1; if not, one or two rotations repair it. A red–black tree colours nodes red or black with rules (the root is black, a red node has black children, every path from a node to its leaves has the same number of black nodes). Those rules imply that the longest path is at most twice the shortest, and insertion needs at most 2 rotations and some recolouring. Proofs by induction on the height establish both bounds, which is where the proof layer matters.
A heap uses a different invariant: each parent is no larger than its children. It does not sort anything, so it is cheaper to maintain. The usual binary heap is a complete binary tree stored in a plain array, with no pointers: the children of index i are at 2i + 1 and 2i + 2, and the parent is at (i − 1) / 2. To insert, append at the end and swap upward while smaller than the parent. To remove the minimum, take the root, move the last element to the root and swap it downward with the smaller child. Both cost O(log n) because the height is ⌊log₂ n⌋. Building a heap from n items by sifting down from the middle takes only O(n), because most nodes are near the bottom and move very little. Heapsort uses this to sort in O(n log n) time with no extra memory.
A trie spends one level per character. Each node has a map from the next character to a child, plus a flag "a key ends here". To look up a word of length L, follow L edges, so the cost is O(L) and does not depend on how many words are stored. Prefix queries ("all words starting with `inte`") are natural: walk to the prefix node, then enumerate its subtree. The price is memory: a naive node with a 256-entry child array is huge. Compact forms fix this: radix trees merge single-child chains into one edge labelled with a string, and finite-state transducers also share suffixes. Tokenizers use tries to find the longest matching token, and SGLang's prefix cache keeps prompts in a radix tree so branches share their common start.
Finally, the memory layer matters. A pointer-based binary tree stores one node per allocation, and a lookup of 20 levels can mean 20 cache misses of about 100 ns each, so 2 µs per lookup for a tree that does not fit in cache. Wide nodes reduce the height: a B-tree with fan-out 200 holds a billion keys in 4 levels, and its nodes match disk pages or cache lines, which is why it dominates storage. The array-based heap and the implicit "Eytzinger" layout of a sorted array are cache-friendlier ways of storing a tree without pointers.

example: Take the keys 10, 20, 30, inserted in this order into an empty BST. After 10 the root is 10. Key 20 is larger, so it becomes the right child. Key 30 is larger than 10 and larger than 20, so it goes right again. The tree is a chain of height 2, and a search for 30 costs 3 comparisons. With a million sorted keys the chain would need up to a million comparisons. An AVL tree notices after the third insert that node 10 has a right subtree of height 2 and an empty left subtree, a difference of 2. It rotates left at 10: key 20 becomes the root, with 10 on the left and 30 on the right. The in-order sequence is still 10, 20, 30, but the height is 1.
Now a min-heap, built by inserting 5, 3, 8, 1, 6 into an array. Insert 5: [5]. Insert 3: append, giving [5, 3]; its parent (index 0) is 5, which is larger, so swap: [3, 5]. Insert 8: [3, 5, 8], no swap since 3 < 8. Insert 1: append at index 3, giving [3, 5, 8, 1]; the parent of index 3 is index 1 (value 5), swap: [3, 1, 8, 5]; the parent of index 1 is index 0 (value 3), swap: [1, 3, 8, 5]. Insert 6: append at index 4, giving [1, 3, 8, 5, 6]; the parent is index 1 (value 3), and 6 > 3, so stop.
Remove the minimum. Take 1 from the root, move the last element 6 to the root: [6, 3, 8, 5]. Its children are 3 and 8; the smaller is 3, so swap: [3, 6, 8, 5]. Now 6 sits at index 1 with child 5 at index 3; swap again: [3, 5, 8, 6]. Done, after 2 swaps. The next minimum is 3.
intuition: A decision game of "higher or lower": each answer throws away half of what is left, so a million items need about twenty questions.
A tree is the shape of that game. The root asks the first question, each branch is an answer, and the leaves are the items. The shape guarantees that one path through the questions exists for every item and that the paths are short, as long as the tree stays bushy and does not stretch into a chain. Balancing rules, such as AVL or red–black, are only a way of paying a small constant cost on each update to keep the tree bushy. A heap relaxes the game: it only needs to know who is smallest, so it asks less of the structure and gets simpler and faster. A trie turns the game around and asks one question per character, so the cost depends on the key's length, not on the set.
mistakes: People often think a binary search tree always has O(log n) operations. In fact a plain BST has O(log n) height only on average for random insertion order. Insert sorted data, which is common in real systems (timestamps, auto-increment ids), and it becomes a linked list. Only self-balancing trees promise the bound.
People often think a heap keeps its elements sorted. In fact it only guarantees the root is the minimum and each parent is smaller than its children. Two siblings have no order, and finding an arbitrary element costs O(n). To iterate in order you must remove items one by one, which is a heapsort.
People often think a hash table makes trees unnecessary. In fact a tree answers questions that a hash cannot: the next key after k, all keys between a and b, the smallest key, the top-k. Ordered maps, time-series indexes and database indexes need these.
People often think that O(log n) with a binary tree beats everything for in-memory search. In fact for small n a sorted array with binary search, or even a linear scan, can be faster, because it reads contiguous memory. A pointer-chasing binary tree may take a cache miss at every level. The high fan-out of B-trees is not only for disks; in-memory B-trees (like Rust BTreeMap and Google's cpp-btree) often beat red–black trees.
friction: Trees are pointer-heavy and cache-unfriendly. A red–black node stores key, value, two child pointers, a parent pointer and a colour bit, so a tree of 8-byte keys may use 40 to 48 bytes per key, 5 times the data, and each level of a lookup is a likely cache miss. This is why storage engines use wide nodes and why in-memory databases often prefer hash tables, skip lists or cache-conscious trees (the Adaptive Radix Tree is one example).
Concurrency is hard. A rotation touches several nodes, so a balanced tree needs either a lock on a path or careful lock-free design, and readers can see half-finished rebalancing. Skip lists became popular in memtables because they avoid rotations. Persistent (copy-on-write) trees, used in file systems like Btrfs and in functional languages, avoid locking by copying the path from root to leaf on each update, at the price of more writes.
Rebalancing has a cost and a worst case. AVL trees rotate more often on updates; red–black trees tolerate more imbalance; splay trees give O(log n) only amortized, so one operation can take O(n). Deletion is the hardest to implement correctly, which is why teaching examples often skip it and production bugs often hide there.
practice: Pick the library structure by the operations you need. Use the standard ordered map (Java TreeMap, C++ std::map, Rust BTreeMap, Python sortedcontainers) when you need order, floor/ceiling lookups or range scans. Use a heap (Java PriorityQueue, Python heapq, C++ priority_queue) for "next smallest": timers, schedulers, Dijkstra's algorithm, top-k, merging k sorted streams. Use a trie or radix tree for prefix lookup, routing tables (longest prefix match) and autocomplete.
For top-k over a large stream, keep a min-heap of size k: each new item is compared with the root and replaces it if larger. This costs O(n log k) time and O(k) memory, and it needs no sorting. For merging k sorted files, a heap of k entries picks the next smallest in O(log k).
When the data lives on disk, think B-tree first: choose a node size equal to the page size, and remember that the number of keys per page, not n, controls the height. Keep keys short in internal nodes (prefix truncation) to raise the fan-out. Sorted bulk loading, which builds the tree bottom-up from sorted input, is much faster than inserting one by one and gives fuller pages.
In code you write yourself, prefer array-based layouts over pointers when the shape is fixed: a heap in an array, a segment tree in an array, a sorted array with binary search for static data. Do not hand-write red–black deletion. If a tree is shared by threads, check whether the library structure is thread-safe, and consider sharding or a concurrent skip list instead.
tradeoffs: Choose a hash table when you only need exact-key lookups, since it is O(1) expected and 2 to 5 times faster than a tree at a million keys. Choose a balanced tree when you need order: range scans, nearest-key queries, sorted iteration, or a worst-case guarantee with no resize pause. You give up some speed and memory for that order.
Choose a binary tree (AVL or red–black) for in-memory ordered maps up to a few million keys. Choose a B-tree with wide nodes when the data is on disk or when it is large in memory: a fan-out of 100 to 500 cuts the number of cache or page misses from about 20 to 3 or 4. The price is more complex node splitting and merging.
Choose AVL when reads dominate and you want the shallowest tree (height up to 1.44 log₂ n); choose red–black when updates are frequent, since it does fewer rotations (at most 2 per insert, at most 3 per delete). The difference is a constant factor, so most programmers should just use the library default.
Choose a binary heap when you only need the extreme element: insert and remove-min are O(log n) with a tiny constant and no pointers. Choose a balanced tree if you also need to delete arbitrary items or to find the next-larger key. Choose a d-ary heap (d = 4 or 8) when decrease-key is rare and cache misses dominate, since the shallower tree touches fewer lines.
interview: Why do we need self-balancing trees? What does a rotation do and why does it preserve correctness? || A plain BST degrades to a list on sorted input, so operations become O(n). Balanced trees repair the shape after each update. A rotation changes the parent–child relation of two nodes and moves one middle subtree across, but the in-order sequence of keys is unchanged, so the search property still holds while the height shrinks.
Why are database indexes B-trees and not red–black trees? || The cost on disk is block reads, not comparisons. A B-tree node is sized to one page and holds hundreds of keys, so the tree has 3 or 4 levels for a billion keys, against about 30 for a binary tree. Fewer levels mean fewer page reads, and the top levels stay cached. Range scans follow linked leaves sequentially.
How do you build a heap from n elements in O(n), and why is that not O(n log n)? || Place the elements in an array and sift down each internal node from the last one back to the root. A node at height h moves at most h levels, and half the nodes have height 0, a quarter height 1, and so on. The sum ∑ h·n/2^(h+1) converges to O(n).
Find the k largest of a billion numbers with limited memory. || Keep a min-heap of size k. For each number, if it is larger than the heap root, replace the root and sift down. This is O(n log k) time and O(k) memory, and it streams. If k is also huge, use a distributed approach: top-k per partition, then merge.
quiz: What does the in-order traversal of a BST give, and why? || The keys in sorted order. At each node it visits all smaller keys (left subtree), then the node, then all larger keys (right subtree), which is exactly the BST property applied recursively.
Why is the array form of a binary heap valid, and where are the children of index 5? || A heap is a complete binary tree: all levels are full except possibly the last, which fills from the left. So positions can be numbered level by level with no gaps. The children of index i are 2i + 1 and 2i + 2, so for 5 they are 11 and 12.
A B-tree has 200 keys per node. About how many levels hold one billion keys? || log₂₀₀(10⁹) = 9 / 2.3 ≈ 3.9, so 4 levels. A binary tree would need about 30 levels.
Why does inserting keys in sorted order hurt a plain BST but not a heap? || A BST puts each larger key to the right of the last one, giving a chain with height n. A heap has a fixed complete shape in an array, so its height is always ⌊log₂ n⌋ regardless of the order of insertion.
A scheduler must always run the task with the earliest deadline, and tasks are added and cancelled all the time. Heap or balanced tree? || A heap gives the earliest deadline in O(1) and insert in O(log n), but cancelling an arbitrary task is awkward (use lazy deletion or an index map). A balanced tree keyed by (deadline, id) supports insert, cancel and earliest in O(log n) each, at a higher constant cost.

value: Many engineering questions are questions about connections. Which jobs must run before this one? What is the cheapest route between two data centres? Which user IDs belong to the same household? Which service is stuck waiting for which? A graph, a set of nodes joined by edges, is the common form of all of these, and a small set of graph algorithms answers most of them: breadth-first search (BFS), depth-first search (DFS), shortest paths, topological sort, connected components and minimum spanning trees. Their costs are mostly O(V + E) or O((V + E) log V), where V is the number of nodes and E the number of edges, so they scale to millions of nodes on one machine.
The layer above uses them constantly. A DAG scheduler (Airflow, Spark, a build system) runs a topological sort of its task graph. Lineage-based recovery walks a dependency graph backwards to find which inputs to recompute. Deadlock detection looks for a cycle in the wait-for graph. An identity graph finds households as connected components over ID links. HNSW search for nearest neighbours is a greedy walk on a proximity graph. PageRank, backpropagation, the eBPF verifier and dataflow analysis in compilers all traverse graphs in a particular order.
The layers below supply the vocabulary and the guarantees. Graph theory (L4) defines paths, cycles, connectivity, trees and DAGs, and proves facts such as "a graph has a topological order if and only if it has no cycle" and "a minimum spanning tree contains the lightest edge across any cut". Network flow (L3) is both a user and a neighbour: it uses BFS or DFS to find augmenting paths, and in return it solves problems that look different, such as bipartite matching, disjoint paths and minimum cuts, as graph problems with a proof of optimality.
terms: Graph — a set of nodes (vertices) V and a set of edges E, each edge joining two nodes; edges may be directed and may carry weights.
Adjacency list — for each node, the list of its neighbours; it takes O(V + E) memory and is the usual representation for sparse graphs.
BFS (breadth-first search) — a traversal that visits nodes in order of their number of edges from the start, using a queue.
DFS (depth-first search) — a traversal that follows one path as deep as it can, then backs up, using recursion or a stack.
DAG — a directed acyclic graph: directed edges and no cycle; dependency graphs must be DAGs.
Topological order — a list of the nodes of a DAG in which every edge points from an earlier node to a later one.
Relaxation — the step "if going through u gives a shorter path to v than the best known, update the distance to v".
Strongly connected component — a maximal set of nodes in a directed graph in which every node can reach every other.
Minimum spanning tree (MST) — a set of V − 1 edges that connects all nodes with the smallest total weight.
history: Graph theory began with Leonhard Euler's solution of the Königsberg bridge problem in 1736. Graph algorithms as a part of computer science began in the 1950s, when computers and network problems arrived together. Ford and Fulkerson published their flow work in 1956. Edsger Dijkstra devised his shortest-path algorithm in 1956, reportedly in about twenty minutes while sitting in a café in Amsterdam, and published it in 1959. Richard Bellman (1958) and Lester Ford (1956) gave the algorithm that handles negative edge weights. Kruskal (1956) and Prim (1957, a rediscovery of a 1930 result by Jarník) gave the two classic MST algorithms; Borůvka had described the first one in 1926 for an electricity network in Moravia.
Edward Moore (1959) and C. Y. Lee (1961) described breadth-first search for finding paths through mazes and circuit boards. Robert Tarjan's work in 1972 showed that depth-first search is a powerful building block: with one DFS you get strongly connected components, biconnected components and topological order in linear time. This earned him, with John Hopcroft, the Turing Award in 1986. Hart, Nilsson and Raphael (1968) added a heuristic to Dijkstra's algorithm and created A*, for the Shakey robot. Fredman and Tarjan (1984) invented the Fibonacci heap and brought Dijkstra to O(E + V log V).
Big graphs forced a new style. Google's Pregel (2010) let programmers write a function per vertex that sends messages along edges in rounds, and Apache Giraph and Spark GraphX followed. In 2025 Duan, Mao, Mao, Shu and Yin posted a preprint showing the first directed shortest-path algorithm for non-negative weights that beats Dijkstra's bound on sparse graphs, O(m log^(2/3) n); it is theoretical so far and has not replaced Dijkstra in practice.
how: Everything starts with representing the graph. For a sparse graph, the usual choice is an adjacency list: an array indexed by node, each entry listing the neighbours (and weights). Memory is O(V + E), and visiting all neighbours of a node costs exactly its degree. An adjacency matrix uses V² memory and only makes sense for small or dense graphs. For graphs with billions of edges, the compressed sparse row layout stores all neighbour lists in one flat array plus an offset array, so that scans are sequential.
BFS takes a start node, puts it in a queue, and repeatedly removes a node and appends its unvisited neighbours, marking them when they are added. Nodes come out in order of distance in number of edges, so in an unweighted graph BFS gives shortest paths, and the parent pointers recorded on the way give the path itself. Each node enters the queue once and each edge is looked at once (twice if undirected), so the cost is O(V + E). DFS uses a stack, or recursion, to go deep first. It records the time each node is first entered and left. Those times classify the edges: an edge back to a node still on the stack is a back edge, and a directed graph has a cycle exactly when DFS finds one. Listing nodes by decreasing finish time gives a topological order, and Tarjan's algorithm uses a stack and low-link numbers to cut out strongly connected components in a single pass.
Topological sort has a second form that is friendlier to schedulers, Kahn's algorithm (1962). Count the incoming edges of every node. Put the nodes with zero incoming edges in a queue. Remove one, output it, and decrease the count of each of its successors; any successor that reaches zero joins the queue. If the output has fewer than V nodes at the end, the leftover nodes form a cycle. The nodes in the queue at any moment are exactly the tasks that can run in parallel, which is how DAG schedulers decide what to launch.
Dijkstra's algorithm handles non-negative weights. Keep a priority queue of nodes keyed by the best known distance. Pop the node u with the smallest distance; this distance is final, because any other route to u must go through a node with distance at least as large and edges are not negative (an argument by induction, from the proof layer). Then relax every edge (u, v): if dist[u] + w is less than dist[v], update dist[v]. With a binary heap the cost is O((V + E) log V). A* adds an estimate of the remaining distance to the goal, so the search leans toward the target and explores far fewer nodes if the estimate never overestimates. Bellman–Ford handles negative weights by relaxing every edge V − 1 times, at O(V·E) cost, and a V-th round that still improves something proves a negative cycle. The same idea runs in distance-vector routing protocols, where each router relaxes edges using distances announced by its neighbours. Floyd–Warshall computes all pairs in O(V³) with dynamic programming.
Connectivity and spanning trees come from simple rules. Connected components of an undirected graph come from one BFS or DFS per unvisited node. Kruskal's MST sorts edges by weight and adds an edge if it joins two different components, tested with union–find, so the cost is O(E log E). Prim's algorithm grows one tree from a start node using a priority queue, like Dijkstra. Both rely on the cut property: the lightest edge crossing any cut belongs to some MST. A useful trick connects the two ideas: collapse every strongly connected component into one node, and the result is always a DAG, so a graph with cycles can still be scheduled component by component. Many graphs are also implicit: a chess position, a Kubernetes object, or a state machine is never stored as a list, and BFS or DFS simply generates neighbours on demand, with a hash set of visited states. Max-flow, the other L3 neighbour, repeatedly runs BFS in a residual graph to find augmenting paths, and in return a flow answers matching and cut questions that plain traversal cannot.

example: Use the graph in the diagram. Dijkstra starts with dist[A] = 0 and all others infinite. Pop A, the smallest. Relax A–B: 0 + 4 = 4, so dist[B] = 4. Relax A–C: 0 + 1 = 1, so dist[C] = 1. The smallest unfinished node is C at 1. Relax C–B: 1 + 2 = 3, which beats 4, so dist[B] becomes 3. Relax C–D: 1 + 5 = 6, so dist[D] = 6. The smallest unfinished node is B at 3. Relax B–D: 3 + 1 = 4, which beats 6, so dist[D] becomes 4. Pop D at 4 and relax D–E: 4 + 3 = 7. Pop E at 7. The shortest route from A to E costs 7, along A, C, B, D, E. BFS would have found the route with the fewest edges, A–B–D–E (3 edges, cost 8), which is not the cheapest. That is the difference between hop count and weighted distance.
Now a scheduling example. A data pipeline has tasks: ingest, clean, enrich, join, report, with edges ingest → clean, ingest → enrich, clean → join, enrich → join, join → report. In-degrees: ingest 0, clean 1, enrich 1, join 2, report 1. Kahn's algorithm starts with the queue {ingest}. Remove ingest; clean and enrich drop to 0 and enter the queue. They can run in parallel. Remove clean: join drops from 2 to 1. Remove enrich: join drops to 0 and enters the queue. Remove join: report drops to 0. Remove report. The output has 5 nodes, so there is no cycle. If someone adds an edge report → ingest, the in-degree of ingest becomes 1, the queue starts empty, the output has 0 nodes, and the tool reports a cycle.
For scale, take a road network of 20 million intersections and 50 million road segments. Dijkstra with a binary heap does about (V + E) log₂ V ≈ 70 million × 24 ≈ 1.7 billion basic steps, a few seconds per query on one core. Routing services answer in milliseconds because they pre-process the graph (contraction hierarchies, hub labels) so a query touches only thousands of nodes. The raw algorithm is the baseline and the proof of correctness; the production system adds indexes on top.
intuition: BFS is a ripple spreading from a stone dropped in a pond; DFS is a person exploring a maze with a ball of string; Dijkstra is a ripple that moves slower over expensive edges.
The algorithms are natural because a graph has no global picture, only local facts: this node has these neighbours. Every graph algorithm is a rule for what to look at next and what to remember. BFS remembers the frontier and looks at the nearest nodes first. DFS remembers a path and looks at the newest first. Dijkstra remembers the frontier with distances and always settles the cheapest node, which is safe because no later route can undercut it. Topological sort just peels off nodes that have nothing waiting on them. Each rule is simple, and each visits every edge a bounded number of times, which is why the costs are near linear.
mistakes: People often think BFS and DFS differ only in the order of output. In fact they answer different questions. BFS gives fewest-hop paths in unweighted graphs and uses memory proportional to the widest layer. DFS gives structure (cycles, finish times, components) and uses memory proportional to the path depth, which can overflow a recursion stack on a long chain of a million nodes.
People often think Dijkstra works with any weights. In fact one negative edge breaks the argument that a popped distance is final, and the answer can be wrong. Use Bellman–Ford, or re-weight the graph with Johnson's method. Negative cycles make shortest paths undefined.
People often think a shortest path is unique and that "shortest" means fewest edges. In fact there can be many shortest paths, and the fewest-hop path can be the most expensive. Choose the algorithm by the weight model.
People often think graph algorithms are always cheap. In fact "O(V + E)" is cheap for one query, but all-pairs problems cost V × that, and on a graph with 100 million nodes even one pass over random memory takes minutes, since each neighbour lookup is a likely cache miss.
friction: Real graphs are huge, skewed and hard to split. Social, web and identity graphs have power-law degrees: a few nodes have millions of neighbours. A partition that balances nodes does not balance edges, and any cut of the graph across machines leaves many edges crossing machines, so each step of a traversal becomes network traffic. This is why vertex-centric systems like Pregel run in synchronous rounds and why distributed graph jobs often take many rounds to converge, for instance one round per hop in BFS.
Traversals are memory-bound. A BFS touches neighbours in an unpredictable order, so it runs far below the CPU's arithmetic speed. Specialized layouts, bitmaps for the frontier, and direction-optimizing BFS (switching from push to pull when the frontier is large) help, but they are tuned per graph.
Many natural problems are NP-hard: the shortest tour through all cities, the longest path, graph colouring, and the largest clique. For these, systems use heuristics and approximation. Dynamic graphs add another problem: when an edge changes, recomputing from scratch is wasteful, and incremental algorithms for shortest paths or components are much more complex. Finally, correctness depends on the model: self-loops, parallel edges, undirected versus directed, and integer overflow of distances are common sources of bugs.
practice: Use a library before writing your own: NetworkX for exploration, igraph or graph-tool for medium graphs, a graph database or GraphFrames/GraphX for data too large for one machine. For dependency ordering use a topological sort and always check for the cycle case, reporting the actual cycle to the user; Kubernetes controllers and package managers do this. For "who is connected to whom" at the scale of billions of IDs, run connected components with union–find or iterated label propagation in Spark, and watch for giant components created by one bad link (a shared device ID or a public IP).
Choose the algorithm from three questions: are edges weighted, can weights be negative, and do you need one source or all pairs. Unweighted: BFS. Non-negative weights: Dijkstra. Negative weights: Bellman–Ford. All pairs on a small graph: Floyd–Warshall. Known target and a good distance estimate: A*. DAG: relax edges in topological order and get shortest paths in O(V + E), even with negative weights.
Avoid recursion on deep graphs: write DFS with an explicit stack. Store graphs as arrays of integers (CSR), not objects. Mark visited nodes at the time you enqueue them, not when you dequeue them, or the queue can grow to O(E). Test with a path graph, a star graph, a cycle and a disconnected graph. For distributed jobs, filter hub nodes and look at degree distribution first, because one node with 50 million neighbours can sink a partition.
tradeoffs: Choose an adjacency list when the graph is sparse (E much less than V²), which covers almost all real graphs; choose an adjacency matrix when V is below a few thousand and you need constant-time edge tests or matrix algebra. The list saves memory; the matrix gives O(1) edge lookup but uses V² cells (a million nodes would need a terabit-scale matrix).
Choose BFS when you want fewest hops, or level-by-level processing with bounded memory per layer; choose DFS when you need structure such as cycles, topological order or components, and memory should be proportional to depth. You give up shortest paths with DFS and give up low memory with BFS on wide graphs.
Choose Dijkstra for non-negative weights; choose Bellman–Ford when negative weights exist, or when the algorithm must run in a distributed, message-passing form like a routing protocol. Dijkstra is faster, O((V + E) log V) against O(V·E), but Bellman–Ford is simple to distribute and detects negative cycles.
Choose A* or bidirectional search when you have a single source and target and a good heuristic; choose preprocessing (contraction hierarchies, landmarks) when you will answer millions of queries on a mostly static graph, spending minutes of build time and extra memory for microsecond queries.
Choose a single-machine in-memory library when the graph fits in RAM: 1 billion edges in CSR form need roughly 4 to 8 GB, and one machine is usually faster than a cluster. Choose a distributed graph system only when the graph is larger than a machine, and expect the network to dominate.
interview: How would you detect a deadlock, and what does it have to do with graph algorithms? || Build the wait-for graph, where an edge from A to B means A waits for a resource held by B. A deadlock is a cycle in it. Run DFS and look for a back edge, or run Kahn's algorithm and see whether nodes remain. Databases do this periodically or on lock timeout and abort one transaction in the cycle.
Why does Dijkstra fail with negative edges, and what do you use instead? || Dijkstra finalizes a node when it is popped, assuming no later path can be shorter, and a negative edge later can make a longer-looking path cheaper. Use Bellman–Ford, which relaxes all edges V − 1 times and detects negative cycles, or Johnson's algorithm, which re-weights edges using Bellman–Ford potentials and then runs Dijkstra from each source.
Given a build system with 10,000 targets, how do you find the order, the parallelism and the critical path? || Topological sort with Kahn's algorithm gives a valid order, and the nodes in the zero-in-degree queue at each moment can run in parallel. The critical path is the longest path in the DAG, computed by processing nodes in topological order and taking the maximum of predecessor finish times. Cycles are reported as errors.
You must find connected groups among 2 billion device IDs linked by 10 billion edges. How do you do it? || Use union–find in a distributed form or iterative label propagation: each node takes the minimum label of its neighbours until nothing changes, which takes a number of rounds close to the graph's diameter. In Spark, GraphFrames connectedComponents does this with checkpoints. Check for giant components caused by noisy links, and set a limit or remove hub IDs.
When would you use BFS over Dijkstra, and what is the cost difference? || When all edges have equal cost, because BFS finds shortest paths in O(V + E) with a plain queue, while Dijkstra pays an extra log factor for the heap. With only costs 0 and 1 you can use a deque (0–1 BFS) and stay linear.
quiz: What are the time and memory costs of BFS on an adjacency list? || Time O(V + E), because each node is enqueued once and each edge is examined once. Memory O(V) for the queue and visited marks, plus O(V + E) to hold the graph.
Why does a directed graph have a topological order only if it has no cycle? || In a cycle, each node must come before the next one around the loop, including the last before the first, which is impossible in any linear order. If there is no cycle, a node with no incoming edge always exists, and removing it leaves a smaller acyclic graph, so the order can be built step by step.
Run Dijkstra on edges S-A 2, S-B 5, A-B 1, B-T 2, A-T 6. What is the shortest S to T distance? || dist: A = 2, B = min(5, 2 + 1) = 3, T = min(3 + 2, 2 + 6) = 5. The shortest route is S, A, B, T with cost 5.
Why does Kruskal's algorithm need union–find? || For each edge in sorted order it must ask whether its endpoints are already connected, which would create a cycle. Union–find answers this in almost constant amortized time and merges components, so total time is dominated by sorting the edges, O(E log E).

@@ sorting
value: Sorting puts items in order by a key. The order itself is rarely the goal. Sorted data can be searched by halving, merged in one pass, deduplicated by looking at neighbours, grouped by key, and compressed because neighbouring values are similar. That is why sorting sits under so many systems: sort-merge joins, LSM-tree compaction, the shuffle in Spark and MapReduce, posting lists in a search index, Z-ordering of data files, and the construction of suffix arrays. When a database does "ORDER BY", "GROUP BY" or "DISTINCT" on a big table, it is often sorting.
Two facts shape everything. First, sorting by comparisons cannot be done faster than about n log₂ n steps, so a good algorithm is already at the limit and the engineering is about constants, memory and disk. Second, data is often larger than memory. External merge sort handles that by sorting memory-sized pieces and then merging them, so each byte is read and written only a couple of times. This is also how a Spark job sorts a terabyte.
The layers below make this precise. Combinatorics (L4) counts the n! possible orders of n items; to tell them apart by yes/no comparisons you need at least log₂(n!) ≈ n log₂ n − 1.44n of them. Asymptotic analysis (L4) and Big-O (L3) are the language for comparing quicksort, mergesort and radix sort. Randomized algorithms (L3) show that picking a random pivot gives quicksort an expected n log n time on every input, so no fixed input is bad.
terms: Comparison sort — an algorithm that learns about the order only by asking "is a before b?"; mergesort, quicksort and heapsort are comparison sorts.
Stable sort — a sort that keeps equal keys in their original relative order; this matters when you sort by one column after another.
In-place — using only O(1) or O(log n) extra memory beyond the input.
Run — a stretch of already sorted data; external sort writes runs and then merges them.
Pivot — the element quicksort uses to split the data into smaller and larger parts.
Partition — rearranging an array so that all items below the pivot come before all items above it.
k-way merge — merging k sorted inputs at once, usually with a heap or a tournament tree of k entries.
Radix sort — a non-comparison sort that processes keys digit by digit, in O(n·d) time for d digits.
Spill — writing data from memory to disk because it no longer fits; sorting is the main reason engines spill.
history: Sorting is one of the oldest uses of machines. Herman Hollerith's tabulating machines (1890 census) sorted punched cards by columns, and radix sort is exactly that procedure: card sorters ran one column at a time. John von Neumann wrote a merge sort program for the EDVAC in 1945, one of the first programs for a stored-program computer. Merging was the natural tool because early data lived on magnetic tape, which can only be read in order, and merging two tapes needs only sequential reads.
C. A. R. Hoare invented quicksort in 1959 while working on machine translation in Moscow, and published it in 1961. It sorted in place, and with good luck it beat merge sort on the memory systems of the day. J. W. J. Williams gave heapsort in 1964, with a guaranteed n log n and O(1) extra memory. Knuth's The Art of Computer Programming, Volume 3 (1973) collected the theory: tape merging patterns, replacement selection (which makes runs about twice as long as memory), and the information-theoretic lower bound.
Aggarwal and Vitter (1988) formalized sorting when data does not fit in memory. David Musser's introsort (1997) starts as quicksort and switches to heapsort if the recursion gets too deep, which protects against bad pivots; C++ std::sort follows this plan. Tim Peters wrote Timsort for Python in 2002; it finds natural runs in the input and merges them, so nearly sorted data costs close to O(n), and Java adopted it for objects in Java 7. Orson Peters' pattern-defeating quicksort (pdqsort, 2016) is used in Go (since 1.19) and Rust. In Rust 1.81 (2024), the standard library replaced its sorts by driftsort (stable) and ipnsort (unstable), which also panic if a comparison function is not a valid total order. At scale, the Sort Benchmark competitions drove distributed design: in 2014 a Spark cluster of 206 machines sorted 100 TB in about 23 minutes.
how: Start with the two best-known in-memory algorithms. Mergesort splits the array in half, sorts each half recursively, and merges the two sorted halves. Merging uses two pointers, one on each half; at each step it copies the smaller of the two current items and advances that pointer. The merge takes O(n) time, and the recursion has log₂ n levels, so the total is O(n log n) in every case. It is stable and needs O(n) extra space. Quicksort picks a pivot, partitions the array so that smaller items are on the left and larger items on the right, and then sorts each side recursively. Partitioning is a single sequential scan, which is very friendly to the CPU cache. On average it does about 1.39 n log₂ n comparisons. The worst case is O(n²), when the pivot is always the smallest or largest item. A random pivot, or the median of three samples, makes this vanishingly unlikely, and this is the use of randomized algorithms in the sorting story.
The counting argument shows why n log n is the floor. A comparison sort is a decision tree: each comparison has two outcomes, and each leaf is one possible output order. There are n! possible orders and the tree must have a leaf for each, so it has depth at least log₂(n!), which is about n log₂ n − 1.44n. For 5 items, 5! = 120 orders and log₂ 120 ≈ 6.9, so 7 comparisons are needed in the worst case. To beat the bound you must not compare: radix sort and counting sort use the digits of the key, and for 32-bit integers four passes of an 8-bit radix cost O(4n). Counting sort works like this: count how many items have each key value, turn the counts into running totals (these are the final start positions), and then place each item at its position, moving the position forward by one each time. Radix sort applies counting sort to one digit at a time, from the least significant digit to the most, and it is correct only because each pass is stable. Libraries use hybrids. Insertion sort handles small pieces (about 16 to 32 items) because it has a tiny constant. Timsort finds existing ascending or descending runs, extends short ones with insertion sort, and merges them in a stack discipline that keeps merges balanced.
External sorting follows the same principle with disk blocks in place of items. Let N be the data size, M the memory and B the block size. Pass 0 reads M bytes at a time, sorts them in memory with any fast algorithm, and writes each sorted run to disk. This makes N/M runs. The merge pass opens up to about M/B − 1 runs at once, with one block buffer for each run and one output buffer, and uses a heap to pick the smallest head item. If N/M is below M/B, a single merge pass finishes the job, so the whole sort reads and writes each byte exactly twice. Otherwise, it uses ⌈log_{M/B−1}(N/M)⌉ merge passes. The cost in I/O is about (N/B)·log_{M/B}(N/B) block transfers, matching the external-memory lower bound. All reads and writes are sequential, which suits disks and object stores. Replacement selection, which keeps a heap of the memory and outputs the smallest item that is not smaller than the last output, produces runs of about 2M on random data, halving the number of runs.
Distributed sorting adds a partitioning step. Sample the data, pick p − 1 splitters so that each of p machines receives about equal data, send each record to the machine for its range, and let each machine sort its part locally. Concatenating the outputs gives a globally sorted result. Spark's sort-based shuffle works this way: map tasks sort records by target partition (and optionally by key), write one file with an index, and reduce tasks fetch and merge their pieces. This is a place where sorting and the LSM tree meet, as compaction is a k-way merge of sorted runs. A k-way merge with a heap costs O(log k) per output item, which is why compaction prefers merging many files in one pass instead of repeatedly merging two.

example: Merge two sorted runs, [2, 5, 9] and [3, 4, 10]. Compare the heads 2 and 3: output 2. Compare 5 and 3: output 3. Compare 5 and 4: output 4. Compare 5 and 10: output 5. Compare 9 and 10: output 9. The first run is now empty, so copy the rest of the second: 10. The output is [2, 3, 4, 5, 9, 10], using 5 comparisons for 6 items. In general, merging two runs of total length n needs at most n − 1 comparisons. Mergesort of 8 items does 3 levels of merging, each level touching all 8 items, so about 8 × 3 = 24 item moves.
Now a quicksort partition on [7, 2, 9, 4, 3, 8] with the last item, 8, as the pivot. Keep a boundary i = 0 that counts the items smaller than the pivot, and scan j from left to right. Item 7 is smaller than 8: swap it with position i (itself) and set i = 1. Item 2 is smaller: i = 2. Item 9 is not smaller: skip. Item 4 is smaller: swap it with position 2, giving [7, 2, 4, 9, 3, 8], and i = 3. Item 3 is smaller: swap it with position 3, giving [7, 2, 4, 3, 9, 8], and i = 4. Finally swap the pivot with position i = 4: [7, 2, 4, 3, 8, 9]. Everything before 8 is smaller, everything after is larger, and 8 is in its final position. Recursion on [7, 2, 4, 3] and [9] finishes the sort.
Now the external case from the diagram. Sort 100 GB with 4 GB of memory. Pass 0 creates 100 / 4 = 25 runs. With blocks of 8 MB, a 25-way merge needs 26 buffers of 8 MB, about 208 MB, which fits easily in 4 GB. So one merge pass is enough. The total I/O is 2 × 100 GB for pass 0 (read plus write) and 2 × 100 GB for pass 1, so 400 GB. At 500 MB/s of sequential throughput that is 800 seconds, about 13 minutes. For a 1 TB input, there would be 250 runs, a 250-way merge needs 2 GB of buffers at 8 MB each, which is still possible, so the cost stays at two passes and 4 TB of I/O, about 2.2 hours on one disk, which is why real systems spread the data over many machines and disks. The number of passes grows very slowly: with 4 GB memory and 8 MB blocks the fan-in is about 500, so a single merge pass handles up to about 2 TB (500 runs of 4 GB), and two merge passes handle about 1 PB.
intuition: Sorting is the cost of turning chaos into an index: pay n log n once, and every later question about order, neighbours or duplicates becomes cheap.
Merging is natural because two sorted lists can be combined by looking only at their fronts: you never need to look back. That makes it a sequential-access algorithm, perfect for tapes, disks and networks. Quicksort is natural from a different angle: one cheap scan separates "small" from "large", and then the two sides are independent problems. Both are divide and conquer, and both reach n log n because there are log n levels of halving and each level touches every item once. The lower bound says this cannot be beaten by comparisons, because a single yes/no answer removes at most half of the remaining possible orders.
mistakes: People often think quicksort is always the fastest. In fact its worst case is O(n²), and it is not stable. Mergesort or Timsort is a better choice when you need stability, a guaranteed bound, or when the input is partly sorted. Library sorts are hybrids exactly for this reason.
People often think O(n log n) is the limit for all sorting. In fact the bound applies only to comparison sorts. Radix sort and counting sort sort integers or fixed-length keys in O(n·d) time, and in practice radix sort is very fast on large arrays of integers. The bound also says nothing about disk: the I/O cost, counted in blocks, is what matters when data is large.
People often think the sort should be stable by default. In fact many fast sorts (std::sort, Rust sort_unstable, Go sort.Slice) are not stable. If you sort records by one field and want ties to keep their earlier order, for example sorting by date and then by name, you must use a stable sort or add the earlier key to the comparison.
People often think a comparison function can be sloppy. In fact an inconsistent comparator (one that says a < b and b < a, or that compares floating point NaN values) can make sorts return garbage, loop, or crash; Java's TimSort throws "Comparison method violates its general contract", and Rust's new sorts may panic.
friction: Memory and disk dominate at scale. A sort that spills creates temporary files, doubles the I/O, and can be 10 times slower than an in-memory sort. In Spark, a skewed key sends most records to one reducer, so one task sorts and spills while the rest of the cluster waits. Sampling for range partitioning helps only when the sample reflects the data, and one extremely frequent key cannot be split by range at all.
Comparisons are not free. Sorting strings or composite keys compares many bytes, and each comparison may follow a pointer to a different cache line. Engines reduce this by sorting small fixed-size prefixes of the key (normalized key prefixes) next to the pointer, and by comparing binary-encoded keys with memcmp. Parallel sorting needs careful partitioning and merging, and the final merge step is hard to parallelize well.
Stability, memory and speed pull in different directions: stable merge-based sorts need O(n) extra space, in-place quicksort is not stable, and in-place stable sorts exist but are slow and complex. There is also the worst case of adversarial input; unseeded quicksort with a fixed pivot rule can be attacked, which is why libraries randomize or use introsort. Finally, sorting is often done when it is not needed: a top-k with a heap, a hash aggregation, or a partial sort can avoid the full n log n.
practice: Use the library sort and give it the right comparison. Check three properties first: is stability needed, is the data nearly sorted (Timsort wins), and are the keys integers or fixed-length (consider radix sort or a specialized library for big arrays). For top-k, use a heap or a partial sort (nth_element) instead of sorting everything.
In Spark and similar engines, remember where sorts hide: ORDER BY, sort-merge join, window functions with PARTITION BY and ORDER BY, and sort-based shuffle. If a stage spills to disk, raise the partition count so that each task's data fits in its memory, or increase executor memory. Watch for skew in the task time distribution: one task with 100 times the data of the median means a hot key. Salting the key, or broadcasting the smaller side of a join, avoids the sort altogether.
When writing data files, sort within the file on the columns you filter by. Sorted Parquet files give tight min/max statistics, so the reader can skip row groups, and sorted columns compress better (run-length and delta encoding). Z-ordering extends this to several columns by sorting on interleaved bits. For merging many sorted streams, use a k-way merge with a heap rather than concatenate-and-resort.
For external sorting outside a database, GNU sort handles files larger than memory with temporary files; give it `-S` for memory and a fast temporary directory with `-T`, and use `LC_ALL=C` to make byte comparison fast and predictable. In your own code, test the comparator on equal items, NaN and null, and on a large random sample.
tradeoffs: Choose mergesort or Timsort when you need stability, a worst-case O(n log n) guarantee, or nearly sorted input (Timsort approaches O(n)). Choose quicksort variants (introsort, pdqsort) when you sort primitive values in memory and want the lowest constant and no extra memory; you give up stability. Choose heapsort when you need a guaranteed n log n with O(1) extra memory and can tolerate poor cache behaviour.
Choose radix sort when keys are fixed-width integers or short strings and n is large (more than about a million): O(n·d) beats n log n, and 8-bit digits make 4 passes for 32-bit keys. Choose a comparison sort when keys are complex objects, when a custom ordering is needed, or when n is small, because radix sort needs extra memory and a key that can be split into digits.
Choose an in-memory sort when the data fits in 50 to 70% of available memory, since spilling is slow. Choose external merge sort when it does not, and size the runs and the merge fan-in so that one merge pass is enough; a second pass doubles the I/O. Choose to avoid the sort when an aggregation or index can answer the question: hash aggregation is O(n), while sort-based aggregation is O(n log n) but works under memory pressure because it can spill gracefully.
Choose sort-merge join over hash join when both inputs are huge or already sorted, or when the output must be sorted; choose hash join when one side fits in memory. Sort-merge join pays n log n up front but needs little memory and is robust against skew in the build side.
interview: Why can't a comparison sort beat n log n, and how do radix sorts get around it? || A comparison sort is a binary decision tree whose leaves are the n! possible orders, so its depth is at least log₂(n!) ≈ n log₂ n. Radix and counting sort do not compare; they use the key's digits to place items directly, so the lower bound does not apply, but they need keys with a bounded number of digits.
How would you sort 1 TB on a machine with 16 GB of memory? || External merge sort: sort 16 GB chunks into about 64 runs on disk, then do a 64-way merge with a heap and big read buffers (for example 64 MB each), writing the output sequentially. One merge pass is enough, so the I/O is about 4 TB of sequential transfer. I would overlap reading, sorting and writing with threads, and compress runs if disk is the bottleneck.
Quicksort has an O(n²) worst case. How do real libraries deal with it? || They choose pivots by median-of-three or by random sampling, and introsort or pdqsort count the recursion depth and switch to heapsort when it grows too large, or detect patterns such as already sorted input. This keeps the worst case at O(n log n) while retaining quicksort's speed in the common case.
Spark's sort-merge join has one task running for an hour while others finish in a minute. What do you check? || Key skew: one key has a huge number of rows, so one reducer sorts and merges most of the data. Check the key frequency, enable adaptive skew-join handling, salt the hot key, or broadcast the smaller side if it fits. Also check whether the task is spilling.
When is a stable sort required and how do you get stability from an unstable algorithm? || Stability is needed when sorting by multiple keys in separate passes or when ties must keep arrival order. To get it from an unstable sort, sort tuples of (key, original index), or put all keys into one comparison function.

Why does merging need only sequential reads, and why does that matter for external sorting? || Merge looks only at the front of each sorted input and moves forward, so it never goes back. value: Dynamic programming (DP) is a way to solve a problem that can be split into smaller versions of itself when those smaller versions repeat. A plain recursive solution then recomputes the same sub-answers again and again, and its cost grows exponentially. DP computes each sub-answer once, stores it in a table, and reuses it. Many problems fall from exponential time to polynomial time this way. Computing the 50th Fibonacci number by plain recursion needs about 40 billion calls; with a table it needs 50 additions.
You meet DP all over computing, often without its name. Diff tools use it to find the longest common subsequence of two files. Spell checkers and fuzzy matching use edit distance. Speech recognition and sequence tagging use the Viterbi algorithm. Genome aligners use Needleman–Wunsch and Smith–Waterman. A database query optimizer uses DP over subsets of tables to choose a join order. Shortest-path algorithms such as Bellman–Ford and Floyd–Warshall are DP. Reinforcement learning solves the Bellman equation by DP-style updates.
The layers below explain why it works. Optimization (L4) provides the key property, Bellman's principle of optimality: in an optimal solution, the part that remains after any first decision must itself be optimal for the smaller problem that results. Proofs and induction (L4) prove that the recurrence is correct, by induction on the size of the sub-problem, and that each table cell depends only on cells that are already filled. Markov decision processes (L4) are the setting in which Bellman created the method, where a sequence of decisions each changes the state, and the value of a state is the best immediate reward plus the value of the next state. The layer above, query optimization and range-query structures such as sparse tables, uses DP as a tool.
terms: Sub-problem — a smaller instance of the same problem, identified by a few parameters, such as "the first i characters of string A and the first j characters of string B".
State — the set of parameters that identifies one sub-problem; the number of states bounds the size of the table.
Recurrence — a formula that gives the answer for a state from the answers of smaller states.
Optimal substructure — the property that an optimal solution is made of optimal solutions to sub-problems.
Overlapping sub-problems — the property that the same sub-problems are needed many times; without it, DP gives no saving.
Memoization — top-down DP: write the recursive function and cache each result by its arguments.
Tabulation — bottom-up DP: fill a table in an order such that every cell's inputs are ready.
Base case — the smallest sub-problems whose answers are given directly, such as the empty string.
Pseudo-polynomial — a running time polynomial in the numeric value of the input, not in the number of bits needed to write it, as in the knapsack DP with cost O(n·W).
history: Richard Bellman developed dynamic programming in the early 1950s at the RAND Corporation, to solve multistage decision problems for the US Air Force, such as how to allocate resources over time. He wrote later that he chose the name "dynamic programming" partly because it sounded impressive and could not be used in a negative sense; the Secretary of Defense at the time disliked the word "research", and Bellman wanted a name that would not draw attention. "Programming" here means planning, in the sense of a schedule, not writing code. His book Dynamic Programming appeared in 1957, and his 1950s papers introduced the principle of optimality and what we now call the Bellman equation.
Computer science took the method up quickly. Levenshtein defined edit distance in 1965, and Wagner and Fischer (1974) gave the table algorithm that we use today. Viterbi (1967) published his decoding algorithm for convolutional codes, which is DP over the states of a hidden Markov model. Needleman and Wunsch (1970) aligned protein sequences with DP, and Smith and Waterman (1981) found the best matching sub-regions. Hirschberg (1975) showed how to recover a longest-common-subsequence alignment in linear space.
In databases, Selinger and colleagues in the IBM System R project (1979) used DP to pick the best join order: for each subset of tables, remember the cheapest plan, and build plans for larger subsets from plans for smaller ones. Almost all relational optimizers still start from that design. Bellman's equation also became the foundation of reinforcement learning: Sutton and Barto's textbook builds the whole field from DP ideas and approximates them when the state space is too large for a table.
how: To apply DP, work through four steps. First, define the state: the few numbers that describe a sub-problem fully. Second, write the recurrence: how the answer for a state follows from the answers of smaller states, by trying each possible first (or last) decision. Third, find the base cases. Fourth, choose an evaluation order so that every state is computed after the states it depends on. The cost is then (number of states) × (work per state). The art is choosing the state, because a wrong state either loses information, so the recurrence is incorrect, or keeps too much, so the table is huge.
Optimal substructure is the property that makes the recurrence valid. In shortest paths, if the best route from A to C goes through B, then its A-to-B part must be the best route from A to B; otherwise swapping in a better part would improve the whole route. This is Bellman's principle, and a short proof by contradiction shows it holds. Not every problem has it. The longest simple path in a graph does not: the best path from A to C through B may use vertices that the best A-to-B path also uses, so the pieces interact, and that problem is NP-hard. Overlapping sub-problems are the second requirement. Mergesort has optimal substructure, but its sub-problems never repeat, so memoization gives it nothing. DP pays off when the number of distinct states is small (polynomial) while the plain recursion tree is exponential.
There are two ways to run the same recurrence. Top-down with memoization keeps the natural recursive code and adds a cache keyed by the arguments. It computes only the states that are reachable, which can be far fewer than all states. Bottom-up tabulation fills an array in loops from the base cases up. It avoids recursion depth limits and function-call overhead, makes the access pattern regular and cache-friendly, and often allows keeping only the last row or two of the table. If cell (i, j) depends only on row i − 1 and the current row, memory drops from O(n·m) to O(m). The price is that you must work out a valid order of evaluation yourself.
Edit distance shows the pattern. State: D[i][j] is the minimum number of single-character edits (insert, delete, substitute) to turn the first i characters of A into the first j characters of B. Base cases: D[i][0] = i (delete i characters) and D[0][j] = j. Recurrence: D[i][j] is the minimum of D[i−1][j] + 1 (delete A[i]), D[i][j−1] + 1 (insert B[j]), and D[i−1][j−1] + c, where c is 0 if A[i] equals B[j] and 1 otherwise. The table has n·m cells and each takes O(1), so the cost is O(n·m), against the exponential cost of trying every edit script.
The table gives the value of the best solution, and the solution itself comes from remembering which choice won in each cell (a back-pointer) and walking back from the final cell. Many famous algorithms are this pattern on a graph. Shortest paths in a DAG take one pass in topological order: the state is the node, and dist[v] is the minimum over incoming edges of dist[u] + w. Bellman–Ford is the same recurrence with the number of edges used as an extra state. Viterbi decoding uses states (time step, hidden state) and takes the best previous hidden state at each step, so its cost is T × S² for T steps and S hidden states, instead of Sᵀ for trying every sequence. Subset DP appears in query optimizers. State: a set S of tables. Value: the cheapest plan to join exactly the tables of S. Recurrence: split S into two parts, take the best plans of both parts, and add the cost of joining them. There are 2ⁿ subsets, so the method is exact but exponential in the number of tables: fine for 10 tables (1,024 subsets), too slow for 30. PostgreSQL does exhaustive DP for fewer than 12 tables by default and switches to a genetic search (GEQO) above that threshold. Here DP is applied only where the state space is small enough, a general lesson. DP over the states of a Markov decision process works the same way: value iteration repeats V(s) = max over actions of [reward + discount × expected V(next state)] until the values stop changing.

Why the saving is real: plain recursion on two strings of length 6 and 7 branches three ways at each step, so it explores up to about 3^(6+7), over a million paths, with the same sub-problem reached many times. The table has 7 × 8 = 56 cells. For two documents of 10,000 characters each, the table has 100 million cells, and at about 1 ns per cell it takes around 0.1 to 0.5 seconds, while the recursive version is hopeless. This is also the limit: for two files of a million lines, the table has 10¹² cells, and diff tools use cleverer variants (Myers' algorithm, which is fast when the files are similar).
A second small example links DP to greedy. You have coins 1, 3 and 4 and must make 6 with the fewest coins. Greedy takes the largest coin first: 4 + 1 + 1, which is 3 coins. DP defines best[x] as the minimum number of coins to make x. best[0] = 0. best[1] = 1. best[2] = 2. best[3] = min(best[2], best[0]) + 1 = 1. best[4] = min(best[3], best[1], best[0]) + 1 = 1. best[5] = min(best[4], best[2], best[1]) + 1 = 2. best[6] = min(best[5], best[3], best[2]) + 1 = 2, using 3 + 3. The table has 7 entries and each looks at 3 coins, so the cost is O(amount × coins).
intuition: Never solve the same small puzzle twice; write the answer on a card and file it by the puzzle's description.
The idea is natural when you notice that a large decision is a chain of smaller decisions that share consequences. After you commit to the first step, what is left is a smaller problem of the same kind, and that smaller problem does not care how you reached it. If many different histories lead to the same remaining problem, you only need to solve it once. So the question is how many distinct remaining problems exist. If the answer is polynomial, the whole search collapses to filling a table with that many cells.
mistakes: People often think DP is a specific algorithm. In fact it is a design method. There is no single DP algorithm; each problem needs its own state and recurrence, and the creative step is choosing the state.
People often think memoization and DP are different techniques. In fact memoization is top-down DP: the same recurrence and the same states, evaluated lazily with a cache. Tabulation is the bottom-up version. They share the same asymptotic number of states, and the choice is about convenience, recursion depth and memory.
People often think DP always gives a fast algorithm. In fact its cost is the number of states times the work per state, and that number can be huge. The knapsack DP runs in O(n·W), which looks polynomial but is exponential in the number of bits of W, so knapsack is still NP-hard. Subset DP over n items has 2ⁿ states. Tracking many variables in a state causes the curse of dimensionality: every added variable multiplies the table size.
People often think that a greedy choice and a DP recurrence are interchangeable. In fact greedy commits to one choice without looking at the alternatives and is correct only when a special exchange property holds, as with interval scheduling. DP tries all choices through the table, and is correct more often but costs more. With coins 1, 3 and 4, greedy fails for the amount 6 while DP is right.
friction: Tables can be too large. Edit distance on two sequences of length 10⁶ needs 10¹² cells, and the DP over a state with ten variables each taking 100 values has 10²⁰ cells. This is the curse of dimensionality, and it is the reason approximate DP (reinforcement learning with neural networks), beam search and heuristic pruning exist. For time, tricks such as banded tables (only cells near the diagonal when strings are similar), and divide-and-conquer on space (Hirschberg), recover feasibility in some cases.
Finding the right state is hard and there is no mechanical way to do it. A wrong state fails quietly: the answers look plausible and are sometimes wrong. Test against brute force on small inputs. DP also gives only the value unless you store the choices; to reconstruct the solution you keep back-pointers (more memory), or recompute, or use a space-saving trick.
Not every problem has optimal substructure; the longest simple path, the travelling salesman problem (which has an O(n²·2ⁿ) DP, Held–Karp, still exponential) and many scheduling problems are hard. In distributed systems DP is awkward: the dependencies between cells make it hard to parallelise across machines, although anti-diagonal wavefronts parallelise well on GPUs and SIMD. Memoization adds hidden costs, a hash map entry per state, and deep recursion can overflow the stack.
practice: Start by writing the brute-force recursion, even if it is slow, and check that it is correct. Then ask what the arguments of the recursive function are; those are the state. If the same arguments repeat, add a cache (memoization) and count the distinct states. If the count is polynomial and small enough, you are done; if the recursion depth is a problem or you need speed, convert to a bottom-up loop. Verify against the brute force on random small inputs.
Design the state to be as small as possible. If a value is determined by others, drop it. Look for monotonic structure that allows a data structure to speed up the transition (a queue for sliding windows, a convex hull for linear cost functions). Use rolling arrays when only the previous row is needed, and use integer indices for states, not strings or tuples, to avoid hash overhead.
Know the classic patterns and recognise them: sequence alignment (edit distance, LCS, diff), knapsack and coin change, interval DP (matrix-chain order, optimal binary search trees), DP on trees (best choice for each subtree), subset DP for small n (up to about 20 elements), DP on a DAG (longest and shortest paths in topological order), and probability DP (expected values). In data work, the Viterbi algorithm decodes sequence models, and window functions compute running aggregates that are simple DP.
In a database, know that your optimizer does DP over join orders and stops at a table-count threshold, so queries with many joins may get worse plans; breaking a huge query into stages or giving join-order hints can help. For production code, prefer a library for diff, fuzzy matching and alignment, since they include banding, bit-parallel and other optimisations that you will not want to rewrite.
tradeoffs: Choose DP when the problem has optimal substructure, sub-problems repeat, and the number of states is polynomial and fits in memory; choose plain recursion or search when sub-problems rarely repeat, as in mergesort. You give up simplicity: the code needs a state definition and an evaluation order.
Choose top-down memoization when only a small part of the state space is reachable, or when you want the quickest correct code from a recursive definition. Choose bottom-up tabulation when all states are needed, when the recursion would be deep (hundreds of thousands of levels), or when you want a rolling array to cut memory from O(n·m) to O(m); you give up the automatic skipping of unreachable states.
Choose greedy over DP when you can prove a greedy-choice property (exchange argument); it is usually O(n log n) against O(n·W) or more for DP. Choose DP when the greedy choice can be wrong, as with arbitrary coin systems or weighted interval scheduling. When neither is exact enough, choose approximation: for knapsack, a fully polynomial approximation scheme gets within (1 + ε) of optimal in time polynomial in n and 1/ε.
Choose exact subset DP when n is small (up to about 20 to 25 items); choose heuristics, local search or integer programming when n is larger. For join ordering this is why PostgreSQL uses a genetic search above 12 tables: it trades plan quality for planning time.

value: Greedy and divide-and-conquer are the two most common ways to design an algorithm when you start from a blank page. A greedy algorithm builds the answer one step at a time and, at each step, takes the choice that looks best right now, without ever going back. A divide-and-conquer algorithm splits the problem into independent smaller problems of the same kind, solves each one recursively, and combines the answers. Greedy is simple and fast but correct only for problems with a special structure. Divide-and-conquer is almost always correct, and its cost can be read directly from a recurrence.
Both appear in the systems around you. Dijkstra's shortest paths, Kruskal's and Prim's minimum spanning trees, Huffman codes (inside gzip and many other compressors) and earliest-deadline-first scheduling are greedy. Mergesort, quicksort, binary search, the fast Fourier transform, Karatsuba multiplication, Strassen matrix multiplication and the distributed MapReduce model are divide-and-conquer. Tokenizer training with byte-pair encoding is greedy: it merges the most frequent adjacent pair, over and over.
The layers below give the tools for trusting these designs. Proofs and induction (L4) provide the exchange argument for greedy: take any optimal solution, swap in the greedy choice, and show it is still optimal, then repeat by induction. The same layer proves divide-and-conquer correct, since correctness for size n follows from correctness for the smaller sizes. Asymptotic analysis (L4) provides the recurrence T(n) = a·T(n/b) + f(n) and the master theorem that solves it, so the running time of a recursive algorithm can be read off in a few lines.
terms: Greedy choice — the locally best move available at the current step, chosen without looking ahead.
Exchange argument — a proof technique that shows a greedy choice can replace the corresponding choice in any optimal solution without making it worse.
Optimal substructure — after the first choice, the rest of an optimal solution is optimal for the smaller problem that remains.
Matroid — a structure on sets of items for which the plain greedy algorithm provably finds the best (maximum-weight) independent set.
Recurrence — an equation that writes the running time on size n in terms of the running time on smaller sizes.
Master theorem — a rule that solves T(n) = a·T(n/b) + f(n) by comparing f(n) with n^(log_b a).
Combine step — the work done after the recursive calls return, such as merging two sorted halves.
Approximation ratio — the guarantee that a heuristic's answer is within a factor of the optimum.
history: Divide-and-conquer is as old as binary search and as the Roman proverb, but it became a method of algorithm design in the computer age. Von Neumann's merge sort (1945) and Hoare's quicksort (1959) are early examples. In 1960 the young Anatoly Karatsuba, a student in Kolmogorov's seminar in Moscow, found that two n-digit numbers can be multiplied with three half-size multiplications instead of four, giving about n^1.585 instead of n². This disproved Kolmogorov's conjecture that n² was necessary. Strassen (1969) did the same for matrices: 7 multiplications of half-size blocks instead of 8, giving n^2.807. Cooley and Tukey (1965) published the fast Fourier transform, which turns an O(n²) transform into O(n log n); Gauss had used the idea around 1805. Bentley, Haken and Saxe (1980) stated the master theorem in the form used in textbooks.
Greedy methods grew out of the 1950s graph problems. Kruskal (1956) and Prim (1957) gave the two spanning-tree algorithms, and Dijkstra (1959) the shortest-path algorithm. David Huffman found his optimal prefix code in 1951–52 as a student in Robert Fano's information theory class at MIT, when he chose a term paper over the final exam; Fano and Shannon had a top-down method that was not always optimal, and Huffman's bottom-up greedy method was. The theory of why greedy works came with matroids: Hassler Whitney defined them in 1935, and Jack Edmonds (1971) showed that the greedy algorithm is optimal exactly on matroids. For problems where greedy is not exact, Johnson (1974), Lovász (1975) and Chvátal (1979) proved that greedy set cover is within a factor of about ln n of the optimum.
Today the two ideas have scaled out. MapReduce (Dean and Ghemawat, 2004) is divide-and-conquer across machines: split the input, process the pieces independently, and combine. In 2019 Harvey and van der Hoeven gave an O(n log n) algorithm for integer multiplication, closing a question open since Karatsuba. And byte-pair encoding, a 1994 compression idea by Philip Gage, was adapted by Sennrich and colleagues in 2016 for subword tokenization and is the greedy core of many language-model tokenizers.
how: Greedy first. The recipe is: define the order in which choices are made, make the best local choice, commit to it, and solve what remains. It is fast because it never explores alternatives: usually a sort or a priority queue, so O(n log n). The difficulty is proving it correct. The standard proof is an exchange argument. Take an optimal solution that differs from the greedy one at the first step. Show that you can change it to use the greedy choice instead, without making it worse. Then the first step is safe, and induction on the rest of the problem gives the full result. Each famous greedy algorithm needs the right local rule. For choosing the most meetings in one room, the right rule is "earliest finish time"; the rules "earliest start" and "shortest meeting" are wrong, and counterexamples are easy to build. For minimum spanning trees the rule is the cut property: the lightest edge crossing any cut is in some MST. For Huffman codes, repeatedly merge the two least frequent symbols into one.
Matroid theory explains when the pattern works. If the feasible sets form a matroid (a family in which any subset of a feasible set is feasible, and a smaller feasible set can always be extended from a larger one), then sorting items by weight and adding each one if the set stays feasible gives the maximum-weight answer. Spanning forests of a graph form a matroid, which is why Kruskal's algorithm is correct. When the structure is not a matroid, greedy can still be a good approximation. Greedy set cover repeatedly picks the set that covers the most uncovered elements and is within a factor of H_n ≈ ln n of optimal; no polynomial algorithm does substantially better unless P = NP.
Divide-and-conquer has three steps: divide the input into subproblems, conquer them by recursion (with a base case when they are small enough), and combine the results. The running time follows a recurrence T(n) = a·T(n/b) + f(n): a subproblems of size n/b, plus f(n) work to divide and combine. The master theorem compares f(n) with n^c, where c = log_b a, the total size of the leaves of the recursion tree. If f(n) grows more slowly than n^c, the leaves dominate and T(n) = Θ(n^c). If f(n) is about n^c, every level of the tree costs the same and there are log n levels, so T(n) = Θ(n^c log n). If f(n) grows faster, the root dominates and T(n) = Θ(f(n)). Mergesort has a = 2, b = 2, f(n) = n, so c = 1 and T = Θ(n log n). Binary search has a = 1, b = 2, f = 1, so T = Θ(log n). Karatsuba has a = 3, b = 2, f = n, so c = log₂ 3 ≈ 1.585 and the leaves dominate. Strassen has a = 7, b = 2, f = n², so c = log₂ 7 ≈ 2.807.
The same structure gives parallelism and I/O efficiency. The subproblems are independent, so they can run on different cores or machines, and the combine step is the only place where they meet. This is why MapReduce and Spark fit divide-and-conquer so naturally: a map over partitions, then a reduce that combines. For memory, a recursion that works on pieces small enough to fit in cache does so at every level without being told the cache size, which is the cache-oblivious idea. Divide-and-conquer also gives fast selection: quickselect finds the k-th smallest in expected O(n) time, and the median-of-medians method of Blum, Floyd, Pratt, Rivest and Tarjan (1973) makes this O(n) in the worst case.
Greedy and divide-and-conquer sometimes combine. Dijkstra is greedy and relies on a priority queue; Kruskal is greedy and relies on sorting, which is divide-and-conquer, and on union–find. The skill is to know which structure the problem has. If the choices interact, so that a good choice now can ruin later options, you need dynamic programming. If the subproblems are independent and the same shape, divide and conquer is natural. If a single best local rule can be proved by exchange, greedy is enough.

Divide-and-conquer with numbers: Karatsuba. To multiply two numbers of n digits, write each as high and low halves, x = x₁·B + x₀ and y = y₁·B + y₀, where B = 10^(n/2). The product needs x₁y₁, x₀y₀ and x₁y₀ + x₀y₁. The last term equals (x₁ + x₀)(y₁ + y₀) − x₁y₁ − x₀y₀, so three multiplications of half size are enough. For 1,000-digit numbers, schoolbook multiplication does about 10⁶ digit products. Karatsuba does about 1000^1.585 ≈ 57,000 at the pure recursive level; real libraries switch to schoolbook below a threshold of tens of digits, and use FFT-based methods beyond thousands of digits.

intuition: Greedy: always take the biggest coin. Divide-and-conquer: split the pile, sort each half, and merge.
Greedy works when the problem has no regret: a locally best choice can never block a better global answer, because anything you gave up can be exchanged back. Divide-and-conquer works when a problem has no tangle: the pieces do not interact, except at the final combining step. Both ideas reduce a big problem to smaller ones, but greedy shrinks it by one decision at a time, while divide-and-conquer shrinks it by a constant factor, which is why the second one gets log n depth and the fast algorithms.
mistakes: People often think greedy algorithms usually give the best answer. In fact they give the best answer only on problems with a proven greedy-choice property. For most problems they give a good heuristic at best. For coin change with arbitrary coins, shortest paths with negative edges, and the 0/1 knapsack, a greedy approach can be wrong.
People often think divide-and-conquer is always faster than a simple loop. In fact the combine step, the recursion overhead and the extra memory can dominate. Karatsuba is slower than schoolbook multiplication for numbers under a few dozen digits, and Strassen's matrix algorithm helps only for large matrices and has weaker numerical stability. Good implementations switch to a simple method at small sizes.
People often think splitting in half is required. In fact what matters is a constant-factor reduction: quicksort with a 90/10 split still gives O(n log n). Only a split into pieces of sizes 1 and n − 1 is bad, and that is exactly quicksort's worst case with a poor pivot.
People often think the master theorem covers all recurrences. In fact it needs equal-size subproblems of size n/b and a clean f(n). Unequal splits or recurrences like T(n) = T(n/3) + T(2n/3) + n need the Akra–Bazzi method or a recursion tree.
friction: Greedy has no built-in warning. A greedy algorithm that is wrong still returns an answer that looks reasonable, and the failure shows up only on special inputs. The proof is the only real check, and it can be hard; testing against brute force on small random cases is the practical defence. Even correct greedy algorithms can be sensitive to ties and to the exact definition of "best".
Divide-and-conquer has overheads and limits. Recursion has a call cost and can overflow the stack on deep or unbalanced splits. The combine step may need extra memory (mergesort needs O(n) of it) and may be hard to parallelise: the final merge in a parallel sort is a bottleneck. In a distributed system, the combine step is a shuffle across the network, which costs far more than the compute, and an uneven split (skew) leaves most machines idle.
For many real problems neither applies, because choices interact. Scheduling with deadlines and weights, bin packing and the travelling salesman problem are NP-hard, and only approximations are possible in polynomial time: greedy gives guarantees such as a factor of ln n for set cover or 2 for some matching problems, but not optimality. The theory of when greedy works is itself incomplete outside matroids and related structures such as greedoids and submodular functions, where greedy gives a (1 − 1/e) guarantee.
practice: Choose the strategy by looking at the structure of the problem. If a sorted order and a single rule seem to give the answer, test greedy: write a brute force, run both on thousands of random small cases, and look for a counterexample before trusting it. If you cannot find one, try to write the exchange argument in a few lines; if it does not come, suspect that you need DP.
For divide-and-conquer, write the recurrence first and solve it with the master theorem; this tells you the cost before you write any code. Choose the base case size by measurement: libraries switch to insertion sort below about 16 to 32 elements and to schoolbook multiplication below a few dozen digits. Avoid copying: pass indexes into the same array instead of slicing, and recurse on the smaller half first so the stack depth stays O(log n).
In data systems, recognise the pattern. A MapReduce or Spark job is divide-and-conquer over partitions: the map side must be independent, and the combine step (the reduce) should be associative and commutative so partial results can be merged in any order and combiners can run before the shuffle. Pre-aggregation on the map side is the combine step moved forward to shrink the shuffle. Greedy shows up in query planners (join order heuristics when DP is too costly), in bin-packing of tasks onto executors, in tokenizer training (BPE merges) and in compaction picking the largest file set first. Treat these as heuristics and measure them.
tradeoffs: Choose a greedy algorithm when you can prove the greedy-choice property (exchange argument or matroid structure) because you get O(n log n) time and tiny code; choose dynamic programming when you cannot, accepting O(n·W) or more states. If neither is exact enough, choose a greedy approximation with a proven ratio, such as ln n for set cover, and say so in the design.
Choose divide-and-conquer when subproblems are independent and equal in size, so work spreads over cores or machines and the recurrence gives a clear bound. Choose an iterative or streaming method when the combine step needs all the data at once or when memory and recursion depth matter. You give up easy parallelism with a loop but gain constant memory.
Choose the asymptotically better algorithm only above its crossover point: Karatsuba beats schoolbook multiplication above roughly 20 to 50 digits, Strassen beats the standard matrix product only above hundreds of rows, and FFT multiplication wins at thousands of digits. Below that, choose the simple method; the constant factors dominate.
Choose a top-down greedy for compression like Huffman when you need an optimal prefix code for known frequencies, and a greedy dictionary method such as BPE when you build a vocabulary from data and want something fast and good rather than optimal. The cost is that BPE's merge order is not the best possible vocabulary of that size.

@@ bigo
value: Big-O notation describes how the cost of an algorithm grows when the input grows. The cost can be time, memory, disk reads or network messages. It ignores constant factors and small inputs on purpose, and asks one question: if the input becomes 10 times larger, does the cost stay the same, grow 10 times, grow 100 times, or explode? An algorithm that takes 1 second for 1,000 items and is O(n²) will take about 100 seconds for 10,000 items and 28 hours for a million. An O(n log n) algorithm will take about 1.3 seconds for 10,000 items and 20 seconds for a million.
This is the first tool engineers use to judge a design before building it. It tells you why a nested loop join on two million-row tables never finishes while a hash join does, why listing a million small files is slow however fast the storage, and why an "N+1 query" pattern collapses under load. It also tells you which ideas will survive 10 or 1000 times more data, which is usually a more important question than shaving 20% from a loop.
The layer below, asymptotic analysis (L4), supplies the mathematics: the formal definitions of O, Ω and Θ as limits of growth, the rules for adding and multiplying them, and the standard comparisons such as "log n grows slower than any power of n". This read is the practical craft built on that: counting operations in code, choosing which operation to count, and knowing when the notation misleads. The layer above uses it everywhere: sorting is the classic O(n log n) problem, join algorithms are compared by their complexity, and small-file compaction exists because N file opens cost O(N) round trips.
terms: O(g(n)) — an upper bound: f(n) is O(g(n)) if, for large enough n, f(n) is at most a constant times g(n).
Ω(g(n)) — a lower bound: f(n) is at least a constant times g(n) for large n.
Θ(g(n)) — a tight bound: f(n) is both O(g(n)) and Ω(g(n)), so it grows at the same rate as g(n).
Worst case — the highest cost over all inputs of size n; the guarantee you can promise.
Average case — the expected cost over a stated distribution of inputs; it needs an assumption about the data.
Amortized cost — the cost per operation averaged over a long sequence, even if single operations vary.
Space complexity — the growth of extra memory used, not counting the input.
Polynomial, exponential — n^k for a fixed k versus c^n for a constant c > 1; the first is usually feasible and the second is not.
Input size — the quantity n you measure growth against; choosing it (items, bytes, digits) is part of the analysis.
history: The notation is older than computers. Paul Bachmann introduced the O symbol in 1894 in a book on number theory, to write "an error of the order of n". Edmund Landau popularized it in the early 1900s, which is why it is sometimes called Landau notation. For algorithms the idea became standard in the 1960s, as Juris Hartmanis and Richard Stearns (1965) founded computational complexity, defining classes by the time machines need as a function of input size. In 1976 Donald Knuth wrote "Big Omicron and Big Omega and Big Theta" for SIGACT News and argued that people were using O when they meant Θ; he defined Ω and Θ clearly, and textbooks followed.
The reason the field chose asymptotics is practical. In the 1960s every machine had a different speed and instruction set, so any statement in seconds was local. A statement such as "this sort takes n log n steps" is true on every machine. The RAM model, in which each basic operation takes unit time and memory access is free and uniform, made the counts precise. In the 1970s Tarjan and others added amortized analysis, and in 1988 Aggarwal and Vitter introduced the external-memory model because on disks the RAM model's counts stop predicting reality. Cache-aware and cache-oblivious models followed in the 1990s.
The lesson of the last decades is that the notation is a first filter, not the final answer. Strassen's matrix multiplication and the best-known multiplication algorithms are asymptotically better than the simple ones but win only for very large sizes. Some theoretical algorithms, called galactic algorithms by Lipton and Regan, are faster only for inputs larger than anything that fits in the universe. Engineers learned to combine the notation with measurement.
how: To analyse code, count the operations that dominate and express the count as a function of the input size n. A single loop over n items doing constant work is O(n). Two nested loops over the same n items are O(n²). A loop that halves the problem each time (binary search, or the height of a balanced tree) is O(log n), because n can be halved only log₂ n times before reaching 1. A loop that does O(log n) work inside an O(n) loop is O(n log n). Sequential steps add, and nested steps multiply, so the total is dominated by the largest term: n² + 5n + 100 is O(n²), because for large n the n² term outweighs the others, and the constants 5 and 100 do not change the growth rate.
Recursion is analysed with a recurrence. Binary search does one comparison and recurses on half: T(n) = T(n/2) + 1, which solves to O(log n). Mergesort splits in two, solves both halves and merges in O(n): T(n) = 2T(n/2) + n, which solves to O(n log n). Draw the recursion tree: each level does n work and there are log₂ n levels. Exponential growth comes from recursion that branches without sharing work: naive Fibonacci calls itself twice with sizes n − 1 and n − 2, so it takes about 1.6ⁿ calls, and the number of subsets of n items, 2ⁿ, grows the same way.
Which case? The worst case is a promise: no input will cost more. The average case needs a probability model. For example, quicksort with a random pivot is O(n log n) in expectation on every input, because the randomness is in the algorithm, not in the data. The best case is rarely useful. Amortized analysis covers a sequence of operations: appending to a dynamic array costs O(n) occasionally when it grows, but O(1) on average over the sequence, so we say O(1) amortized. These are different guarantees, and a system that must meet a latency target needs the worst case, while a batch job cares about the total.
The notation hides things on purpose, and engineers must put them back. The first is the constant factor: 100·n and n are both O(n), but they differ 100 times in practice. The second is the memory hierarchy. The RAM model says every access costs 1, but a hit in the L1 cache takes about 1 ns and a miss to main memory about 100 ns. A scan of an array, which is O(n), streams through memory at the speed of the bus, while a walk on a linked list of the same length, also O(n), can be 10 to 50 times slower because each step is a cache miss. The third is the size of n: for n under about 100, the asymptotically worse algorithm often wins, which is why libraries use insertion sort (O(n²)) for tiny ranges inside quicksort. The fourth is the choice of resource: counting comparisons is right for sorting in memory but wrong for sorting on disk, where block transfers matter.
Input size needs care. For numbers, the honest size is the number of bits, not the value. Testing whether N is prime by trying every divisor up to √N takes √N steps, which looks small, but N has only log₂ N bits, so the cost is exponential in the size of the input (2^(bits/2)). The knapsack dynamic program, which runs in O(n·W), has the same property and is called pseudo-polynomial. Logarithm bases do not matter, since log₂ n and log₁₀ n differ by a constant, but the base of an exponential does: 2ⁿ and 3ⁿ are different classes. Finally, the notation composes with the layers around it. A hash table lookup is O(1) expected because hashing spreads keys evenly; a balanced tree lookup is O(log n) in the worst case. Neither number says anything about the cost of hashing a long string, which is O(length of the key), so a table keyed by long strings has an extra factor. Reading complexity correctly means asking: what is n, which operation is counted, is this the worst, average or amortized case, and what does the memory system do?

example: Consider finding duplicates in a list of n = 1,000,000 user IDs. Method 1: for each ID, compare it with every later ID. The number of comparisons is n(n − 1)/2 ≈ 5 × 10¹¹. At 10⁹ comparisons per second that takes about 500 seconds, more than 8 minutes. Method 2: sort the IDs and compare neighbours. Sorting takes about n log₂ n ≈ 2 × 10⁷ comparisons, and the neighbour scan takes n more. At the same speed that is about 0.02 seconds; in reality, with cache misses and constant factors, roughly 100 milliseconds. Method 3: insert each ID into a hash set and check whether it was already there. That is n operations, O(n) expected, again about 50 to 100 milliseconds for a million IDs because each insert is a cache miss of about 100 ns. Method 1 is 5,000 times slower than the others at this size, and at 100 million IDs it would take about 58 days, while methods 2 and 3 would take under a minute or two.
Now the crossover. Suppose algorithm A costs 100·n·log₂ n (a heavy constant) and algorithm B costs n². At n = 100, A costs 100 × 100 × 6.6 = 66,400 and B costs 10,000, so B wins. At n = 1,000, A costs about 997,000 and B costs 1,000,000, a tie. At n = 10,000, A costs about 13.3 million and B costs 100 million, so A wins by 7.5 times. Asymptotics tell you who wins eventually, and the constants tell you when "eventually" starts. This is exactly why a sort routine uses insertion sort below roughly 16 to 32 items.
A third lesson comes from a hidden loop. A Python function checks `if x in my_list` inside a loop over 100,000 items. The `in` on a list is O(n), so the total is O(n²), 10¹⁰ checks, which takes minutes. Changing my_list to a set makes `in` O(1) and the whole function O(n), which takes milliseconds. The code looked linear, and the cost hid inside the operation. The same shape appears as the "N+1 query" problem: one query for 10,000 orders, then one query per order for its customer, so 10,001 round trips at 1 ms each is 10 seconds, against one join taking 50 ms.
intuition: Not how fast the program is now, but how much slower it gets when the problem becomes ten times bigger.
The notation is natural because the future is where programs break. A program that is fast on your test data and slow in production almost always has a growth rate problem, not a constant problem. Throwing away constants and small terms keeps only the part of the cost that will dominate as n grows, and that part is the same on every machine and in every language. It is a way to compare ideas, not implementations. The five or six classes (constant, logarithmic, linear, linearithmic, quadratic, exponential) are separated by such large gaps that they can be recognised at a glance, and a change of class beats any amount of tuning inside a class.
mistakes: People often think O(n) always beats O(n log n). In fact the notation hides constants and the memory system. A cache-friendly n log n algorithm on an array can beat a pointer-chasing O(n) algorithm for realistic sizes. log₂ n is only about 30 for a billion items, so it is often a small factor next to a cache miss.
People often think O(1) means fast. In fact it means the cost does not grow with n, not that the cost is small. A hash lookup that requires a network round trip of 1 ms is O(1) and slower than a scan of 1,000 items in memory, which is O(n).
People often think Big-O means worst case. In fact O is an upper bound on a function, and you can state it for any function: the best case, the average case or the worst case. "Quicksort is O(n²)" refers to the worst case; "quicksort is O(n log n) on average" refers to the average. Say which one you mean.
People often think the notation is only about time. In fact the same analysis applies to memory, disk reads, network messages and even energy. A recursive algorithm that is O(n) in time may be O(n) in stack space, which is the difference between working and a stack overflow. In data systems, shuffled bytes and the number of files opened are often the resource that matters.
People often think complexity analysis makes benchmarks unnecessary. In fact analysis tells you the shape and benchmarks tell you the constants and the crossover. Use both.
friction: The model is an idealization. It assumes uniform memory access, but real memory has caches, pages and NUMA nodes. It assumes the cost of an operation does not depend on n, but comparing two strings costs time proportional to their length, adding two big numbers costs time proportional to their digits, and a hash costs time proportional to the key. The word-RAM model fixes some of this by assuming that numbers fit in a machine word, which fails for cryptography and for exact big-number arithmetic.
Worst-case analysis can be too pessimistic. The simplex algorithm for linear programming is exponential in the worst case but fast on nearly all real inputs, and Spielman and Teng's smoothed analysis (2001) was invented to explain such cases. In the other direction, an algorithm that is fine on average can have terrible tail latency: one input in a million triggers the worst case, and a service that handles a million requests per hour meets it every hour. Amortized bounds hide the same spikes, such as a hash table resize.
Many important costs are not about computation at all. Network latency, disk seeks, lock contention, garbage collection and serialization do not follow a formula in n. Distributed systems add new dimensions (number of machines, shuffle size, skew) where the standard notation says little, and the analysis is replaced by cost models of bytes moved. Finally, a good complexity class can be useless if the input is adversarial or skewed: a hash join is O(n) only if the keys do not all collide, and a shuffle is balanced only if the data is not concentrated on one key.
practice: Estimate before you build. Write down n now and in a year, the complexity of the main loops, and the resulting operation count; if the count is above about 10⁹ for a single request or 10¹² for a batch job on one machine, the design needs a different algorithm or more machines. Remember the rule of thumb of 10⁸ to 10⁹ simple operations per second per core, and 100 ns per random memory access.
Learn to spot the hidden costs: a membership test on a list, string concatenation in a loop (copying the whole string each time, O(n²)), a sort inside a loop, a regex with backtracking, a query inside a loop, a join without a join condition (Cartesian product, n × m rows), and deleting from the front of an array. In Spark, a skewed join key or a UDF that scans a list for every row produces the same effect at cluster scale.
Use the doubling test on real code: run with n, 2n, 4n and look at the time ratios. A ratio near 2 means linear or n log n, near 4 means quadratic. Plot on a log-log scale and read the slope. Profile for the constant and the memory behaviour after you have chosen the right class, not before. Keep the notation honest in design documents: state which resource, which case, and what n is, for example "O(N) round trips to list N files, 10 ms each".
tradeoffs: Choose the better growth class over micro-optimization whenever the input will grow: moving from O(n²) to O(n log n) gives a gain that increases with n, while tuning constants gives a fixed factor. Choose to tune constants (layout, batching, vectorization) once the class is right and profiling shows where time goes.
Choose the simple, worse-class algorithm when n is small and bounded (under about 100 to 1,000 items): it has smaller constants, less memory and fewer bugs. A linear scan of 50 items in an array usually beats a hash lookup. Choose the sophisticated algorithm when n is large or unbounded. You give up simplicity and sometimes cache behaviour.
Choose to optimize for the worst case when you have latency targets, adversarial inputs or real-time deadlines (balanced trees, guaranteed pivots, incremental resizing); choose average or amortized bounds when you care about throughput over many operations and can tolerate occasional spikes (hash tables, dynamic arrays). The price of worst-case guarantees is usually a larger constant.
Choose time over space or space over time explicitly: a hash set gives O(1) lookups for O(n) memory, a sorted array gives O(log n) lookups with no extra index, and a Bloom filter gives approximate answers in a fraction of the memory. State both costs in the design, because most systems are limited by memory long before time.

@@ amortized
value: Some operations are cheap almost always and very expensive once in a while: appending to a dynamic array, inserting into a hash table, incrementing a binary counter, compacting an LSM tree. If you only look at the worst single operation, you conclude "O(n)" and reject a design that is in fact excellent. Amortized analysis fixes this by measuring the cost of a whole sequence of operations and dividing by the number of operations. The result is a guarantee about the total: any sequence of n operations costs at most n times the amortized cost per operation, with no assumption about luck or random input.
This is why a Python list append, a Java ArrayList add and a HashMap put are all described as O(1) even though each occasionally copies every element. It is also the argument behind union–find (nearly constant time per operation over a long sequence), splay trees, Fibonacci heaps (which make Dijkstra faster), and the write cost of log-structured storage. The theory tells you what to promise for throughput, and, equally important, what not to promise for latency.
The layer below, asymptotic analysis (L4), provides the notation and the habit of thinking about growth, here applied to a sum over a sequence instead of a single call. The layer above uses amortization in two main places. Hash tables rely on it so that resizing, which rebuilds the whole table, still leaves insertion at O(1) on average. Union–find uses it to show that path compression and union by rank give a cost per operation of the inverse Ackermann function α(n), which is below 5 for any input that could exist.
terms: Amortized cost — the total cost of a sequence of n operations, divided by n, in the worst case over all sequences.
Aggregate method — compute the total cost of the whole sequence directly and divide by the number of operations.
Accounting method — charge each operation a fixed amount; cheap operations are overcharged and the surplus (credit) pays for later expensive ones.
Potential method — define a number Φ for the state of the data structure; amortized cost = actual cost + change in Φ.
Potential function (Φ) — a non-negative measure of "stored-up work" in the structure, such as how full an array is.
Dynamic array — an array that grows by allocating a larger block and copying when it is full.
Growth factor — the ratio between the new and the old capacity at a resize (2 for doubling).
Worst-case cost — the cost of the single most expensive operation; amortized bounds do not limit it.
Incremental resizing — spreading the work of a rebuild over many operations to avoid one long pause.
history: Amortized analysis came out of the study of data structures in the 1970s. Early results already used the idea without the name: Hopcroft and Ullman (1973) bounded the cost of union–find operations over a sequence, and Tarjan (1975) proved the inverse Ackermann bound for it. Around 1980 Tarjan, Sleator and others made the technique systematic. Daniel Sleator and Robert Tarjan's 1985 papers on splay trees and on "Amortized efficiency of list update and paging rules" used potential functions to show that a self-adjusting structure with no stored balance information is as good, up to a constant, as the best static structure.
Tarjan's 1985 survey "Amortized Computational Complexity" (SIAM Journal on Algebraic and Discrete Methods) gave the three methods their standard form and is still the clearest short account. Fredman and Tarjan's Fibonacci heaps (1984) made decrease-key cost O(1) amortized, which gave Dijkstra's algorithm the O(E + V log V) bound. Textbooks (CLRS from its first edition in 1990) put the three methods in the core algorithms curriculum.
The technique became a daily tool because of dynamic arrays and hash tables in standard libraries, and later because of log-structured storage. Over time engineers also learned what it does not cover. Real-time systems and tail-latency-sensitive services found that an amortized O(1) structure can still stall for a long time on one call, and library authors began to offer incremental versions (Redis rehashes a table a few buckets at a time) and to pick gentler growth factors.
how: Take the standard example: a dynamic array that doubles when full. Appending to a non-full array writes one slot, which costs 1. Appending to a full array of size k allocates a new array of size 2k, copies k items, and writes one item, which costs k + 1. A single append can cost O(n), so the worst-case bound per operation is O(n). But the expensive appends happen at sizes 1, 2, 4, 8, ... 2^j, so their copy costs form a geometric series: 1 + 2 + 4 + ... + 2^j < 2·2^j ≤ 2n for n appends. The total cost of n appends is at most n (the writes) plus 2n (the copies), which is 3n. Divided by n, the amortized cost is at most 3: constant. This is the aggregate method.
The accounting method makes the same argument as a budget. Charge every append 3 coins. One coin pays for writing the item. The other two stay on the item as credit. When the array is full at size k, the k/2 items added since the last resize each carry 2 coins, giving k coins, exactly enough to copy all k items. The balance of coins never goes negative, so the total real cost never exceeds the total charge, which is 3n. The idea to remember is that the cheap operations prepay for the expensive one that follows.
The potential method turns the credit into a function of the state. For the dynamic array, define Φ = 2·size − capacity. Right after a resize, size is half of capacity, so Φ = 0. As the array fills, Φ rises by 2 on each append and reaches the capacity just when the array is full. The amortized cost of an operation is its actual cost plus the change in Φ. For a normal append: actual 1, ΔΦ = +2, amortized 3. For the append at a full array with size = capacity = k: actual k + 1, and Φ goes from k to 2(k + 1) − 2k = 2, so ΔΦ = 2 − k, and the amortized cost is (k + 1) + (2 − k) = 3. Both cases give 3, and because Φ is never negative and starts at 0, the sum of amortized costs bounds the sum of actual costs. The potential method is the most flexible of the three and is the one used to prove the bounds for splay trees and Fibonacci heaps.
The choice of growth factor matters. Multiplying the capacity by a constant r > 1 costs between 1/(r − 1) and r/(r − 1) element copies per append, depending on where n falls between two resizes: between 1 and 2 for r = 2, between 2 and 3 for r = 1.5, and between 8 and 9 for r = 1.125. Adding a fixed amount c instead (arithmetic growth) makes the copy total grow like n²/(2c), so the amortized cost is O(n), not constant. So geometric growth is required. Real libraries choose different factors: Java's ArrayList grows by 1.5 times, CPython's list by about 1.125 times plus a small constant, and Go's slices double up to 256 elements and then grow more slowly (towards 1.25 times). Smaller factors waste less memory and let freed blocks be reused, at the price of more copying.
Hash tables use exactly the same argument. When the load factor passes a limit, the table doubles and re-inserts all entries. Those rebuilds happen at sizes n, 2n, 4n, ..., so over n insertions the total re-insertion work is under 2n, and insertion is O(1) amortized. Notice the dependence on randomness: the expected O(1) of the hash comes from probability, while the O(1) of resizing comes from amortization, and a hash table's insertion cost is both "expected" and "amortized".
Other classic examples fit the same mould. A binary counter incremented n times flips at most 2n bits in total, because bit 0 flips every time, bit 1 every second time, bit 2 every fourth time, and so on, so the total is n + n/2 + n/4 + ... < 2n. A queue built from two stacks (push to the inbox, pop from the outbox, and when the outbox is empty move everything from the inbox) gives O(1) amortized for both operations, since each item is moved at most once. Union–find and splay trees are the harder examples, where the potential function is a clever sum over the tree.

example: Use the binary counter. Start at 000 and increment 8 times. The bit flips per increment are: 000 → 001 flips 1 bit; 001 → 010 flips 2; 010 → 011 flips 1; 011 → 100 flips 3; 100 → 101 flips 1; 101 → 110 flips 2; 110 → 111 flips 1; 111 → 1000 flips 4 (three bits back to 0 and one new bit to 1). The total is 1 + 2 + 1 + 3 + 1 + 2 + 1 + 4 = 15 flips for 8 increments, less than 2 × 8 = 16. The worst single increment (the last one) costs 4, which is log₂ n + 1, but the average is under 2. With the accounting method: charge 2 coins for every increment; one pays to set a bit from 0 to 1 and the other stays on that bit to pay for turning it back to 0 later. A carry flips 1-bits to 0 using only stored coins, so the account never goes negative.
Now the array in the diagram, with real numbers. Appending 17 items starting from capacity 1 does copies of 1, 2, 4, 8 and 16 items, which is 31 copies, plus 17 writes, so 48 steps and 2.8 per append. Scale this to 1 billion appends of 8-byte numbers. The capacity grows to 2^30 (about 1.07 billion) slots, which is about 8.6 GB. The total number of elements copied over all resizes is about 2^30, so about 8.6 GB of copying, which at 5 to 10 GB per second adds one or two seconds to a job that runs for minutes. That is a tiny average cost. But the last resize copies 2^29 elements (4.3 GB) in a single call and needs the old array (4.3 GB) and the new array (8.6 GB) in memory together, about 13 GB, and it blocks that thread for roughly half a second to a second. For a batch job this is irrelevant. For a service that must answer in 20 ms, it is a visible stall.
Compare growth by a constant. If the array grows by 1,000 slots at a time, then for 1 million appends there are 1,000 resizes, and the k-th one copies about 1,000·k items, so the total is 1,000 × (1,000 × 1,001 / 2) ≈ 5 × 10⁸ element copies, about 500 per append. At 10 million appends there are 10,000 resizes, the total is about 5 × 10¹⁰, and the cost is about 5,000 copies per append. The cost per append grows in proportion to n, which proves that growth must be proportional to the size.
intuition: Saving a little every month so that the annual bill, large as it is, never surprises you.
The idea is natural because most real costs come in lumps. You cannot buy half an array resize. But if the lumps are rare in proportion to the cheap steps, and each lump is only as big as the number of cheap steps that came before it, then spreading the lump over those steps gives a small, steady cost per step. Amortization is bookkeeping that makes this precise without assuming anything random: it is a worst-case statement about sequences, not an average over luck. The art lies in finding the right credit or potential that proves the budget never runs out.
mistakes: People often think amortized O(1) means every operation is O(1). In fact it means the average over any sequence is O(1). One operation can still cost O(n). A service with a latency target must care about this difference.
People often think amortized analysis is the same as average-case analysis. In fact average-case analysis averages over a probability distribution of inputs and can fail when the input is not random. Amortized analysis makes no assumption about the input: the bound holds for the worst possible sequence of operations. (Randomized algorithms, such as hashing, add a separate expectation over the algorithm's own random choices.)
People often think any expensive-occasionally operation is cheap on average. In fact the expensive steps must become rarer in proportion to their cost. Growing an array by a fixed number of slots has expensive steps that are not rare enough, and the amortized cost is O(n). The geometric spacing is what makes the sum converge.
People often think amortized bounds survive any use of the structure. In fact they can break when the structure is used in a way the analysis did not allow, such as persistent or backtracking use. If you keep an old version of a data structure whose state is right before an expensive operation, and repeat that operation on the old version many times, the credit is spent each time and the amortized bound fails. Persistent structures need worst-case bounds or lazy evaluation.
friction: The big limit is latency. An amortized bound says nothing about the longest single operation. A table with 100 million entries that doubles can pause for seconds; a garbage-collected heap that compacts can freeze the program. Real-time systems and databases with latency targets therefore use worst-case or incremental versions: Redis keeps two hash tables while it moves a few buckets on each command, and some language runtimes grow maps incrementally. The incremental version costs more code, more memory during the move, and a higher constant.
Amortization also hides resource peaks. During a doubling, old and new arrays exist at the same time, so peak memory is 3 times the old size at the instant of copying (old array, new array of 2 times its size). A process near its memory limit can die at a resize that the average cost never hinted at. Shrinking is a second trap: if an array doubles when full and halves when half-empty, alternating insert and delete near the boundary makes each call expensive; the standard fix is to shrink only when the array is a quarter full.
Proving amortized bounds takes cleverness: finding the potential function for splay trees or union–find is a research-level task, and a wrong potential gives wrong claims. In concurrent systems, amortization across threads is murky, because one thread can pay for work that benefits others, and parallel resizing needs coordination. Finally, in storage systems the amortized cost is often a write amplification factor (each byte rewritten about 10 to 30 times by compaction in an LSM tree), and the spikes appear as compaction stalls that must be throttled.
practice: Use the amortized O(1) structures from your standard library freely for throughput work: dynamic arrays, hash maps, string builders, deques. Reserve capacity when you know the final size (ArrayList(n), reserve() in C++ and Rust, with_capacity, a pre-sized HashMap). This removes all resizes and the memory spike with them.
For latency-sensitive paths, ask what the worst single call costs. Pre-allocate at startup, warm up tables before accepting traffic, shard a large table into many small ones so that each resize is small, or use an incremental structure. Measure the p99 and max latency, not only the average, because the spike is invisible in the mean. When a job's memory is close to the limit, remember the 2 to 3 times peak during growth.
For your own structures, write down the invariant you are amortizing over: "every item has paid 2 credits when it is inserted". If you cannot name the credit, you probably do not have an amortized bound. Never rely on amortized bounds across forked or persistent copies. In distributed systems, think of compaction, checkpointing and rebalancing as amortized costs that must be scheduled: throttle them, run them in the background, and watch for the day when the incoming rate exceeds the rate at which the debt can be paid.
tradeoffs: Choose an amortized structure (dynamic array, standard hash map) when you care about total throughput and can tolerate rare pauses; they are simpler and have smaller constants. Choose a worst-case or incremental structure (pre-sized table, incremental rehash, deamortized queue) when you have a latency target such as a p99 under 10 ms. You give up simplicity and some average speed.
Choose a growth factor of 2 for the fewest copies (1 to 2 per append) and the simplest code, when memory is plentiful; choose 1.5 or smaller when memory is tight or when you want freed blocks to be reusable for the next allocation, accepting 2 to 3 copies per append at 1.5 and more at smaller factors. The memory waste at a factor r is up to (r − 1)/r of the allocation: up to 50% at 2, 33% at 1.5.
Choose to pre-size when the final size is known or predictable: you remove the copies, the spikes and the peak. Choose lazy growth when the size is unknown and the cost of overestimating is high.
Choose amortized analysis to justify a design in a throughput budget and a worst-case analysis to justify it in a service-level objective. When the two disagree, the SLO wins.

value: Three small structures carry a large share of the traffic inside software. A queue holds items in arrival order so that work can be handed from a producer to a consumer. A ring buffer is a queue made from a fixed array whose end connects back to its start, so it never allocates and never moves data. A skip list is a sorted linked list with extra "express lanes" chosen by coin flips, which gives O(log n) search with a much simpler way to handle concurrent writers than a balanced tree. They are the parts behind Kafka's request queues, the LMAX Disruptor, network card descriptor rings, the io_uring interface to the Linux kernel, the memtable of RocksDB and LevelDB, and the sorted sets of Redis.
They matter because most systems are pipelines in which stages run at different speeds. A buffer between two stages absorbs bursts, and the choice of buffer decides what happens under load: does the producer wait, does work get dropped, or does memory grow until the process dies? Backpressure, rate limiting, windowing and work stealing all start from this choice. A token bucket is nothing but a bounded counter that is refilled at a steady rate.
The layers below supply the numbers. Probability (L4) is what makes skip lists work: each node's height is decided by flipping a coin, and the expected number of levels and the expected search path follow from simple geometric distributions. Queueing theory and Little's law (L4) tell you how big a buffer must be: the average number of items in a system equals the arrival rate times the time each item spends there, and the delay grows without bound as utilization approaches 100%. A queue is therefore not only a data structure; it is where latency is created.
terms: FIFO queue — first in, first out: items leave in the order they arrived.
Deque — a double-ended queue that allows adding and removing at both ends; work stealing uses one per worker.
Ring buffer (circular buffer) — a fixed-size array used as a queue, with head and tail positions that wrap around at the end.
SPSC — single producer, single consumer: the simple case in which only one thread writes and one thread reads, so no lock is needed.
Skip list — a layered linked list in which higher layers skip over many nodes, giving O(log n) expected search.
Memtable — the in-memory sorted structure of an LSM tree that takes new writes before they are flushed to disk.
False sharing — two threads writing different variables that sit in the same cache line, which forces the line to bounce between cores.
Backpressure — slowing or blocking the producer when the consumer cannot keep up.
Little's law — L = λ × W: average items in the system = arrival rate × average time in the system.
history: Queues are as old as computing: the first operating systems queued jobs, and Knuth's The Art of Computer Programming, Volume 1 (1968) describes queues, deques and circular lists as basic data structures. Ring buffers appeared in device drivers and in Unix pipes, where a producer and a consumer share a fixed buffer. John Little proved his law in 1961 ("A Proof for the Queuing Formula L = λW"), which turned buffer sizing into arithmetic.
William Pugh invented the skip list at the University of Maryland in 1989 (presented at a data structures workshop that year) and published "Skip Lists: A Probabilistic Alternative to Balanced Trees" in Communications of the ACM in June 1990. His argument was practical: balanced trees such as AVL and red–black trees need complicated rebalancing code, while a skip list needs only a random number generator. Later work showed that lock-free and concurrent skip lists are far simpler than concurrent balanced trees, and Java's ConcurrentSkipListMap (Java 6, 2006) was built on Doug Lea's concurrent design.
The 2000s and 2010s brought attention to the cost of locks and cache misses. LMAX, a London trading exchange, published its Disruptor in 2011: a pre-allocated ring buffer with sequence numbers, one writer per slot, and no locks. Martin Fowler's account said that one thread running the business logic could process about 6 million orders per second. The design also introduced the term "mechanical sympathy", meaning code written with the CPU's cache lines in mind. Jens Axboe's io_uring (Linux 5.1, 2019) used two rings shared between user space and the kernel, one for submissions and one for completions, to make I/O calls without a system call per operation. LevelDB (2011) and RocksDB made the skip list the default memtable of LSM stores.
how: A FIFO queue needs two operations: enqueue at the tail and dequeue at the head. A linked list does this with O(1) cost but allocates a node per item and scatters items in memory. An array-backed queue avoids that; the difficulty is that dequeuing from the front leaves a hole. A ring buffer solves it by treating the array as circular. Keep two counters, head (next item to read) and tail (next slot to write). To enqueue, store the item at index tail mod capacity and increment tail. To dequeue, read index head mod capacity and increment head. The queue is empty when head equals tail, and full when tail − head equals the capacity. If the capacity is a power of two, "mod capacity" is a bitwise AND with capacity − 1, a single cheap instruction. Letting the counters grow forever (as 64-bit numbers, which never overflow in practice) and applying the mask only when indexing removes the old puzzle of telling full from empty.
For one producer and one consumer, the ring buffer needs no lock. The producer is the only writer of tail, and the consumer is the only writer of head. The producer writes the item into its slot first and only then publishes the new tail with a "release" store; the consumer reads tail with an "acquire" load, which guarantees it sees the item contents. Each side reads the other's counter, but never writes it. This is the entire protocol, and it is why SPSC rings run at tens of millions of items per second. Two details dominate performance. First, head and tail must live on different cache lines (64 bytes on x86), because otherwise each write by one thread invalidates the other thread's cached copy, which is false sharing and can slow the ring several times. Second, each side can keep a cached copy of the other's counter and refresh it only when the ring looks full or empty, which cuts the cross-core traffic. Multiple producers need an atomic compare-and-swap or fetch-and-add to claim slots, and that is where the Disruptor's sequence numbers come in.
A bounded buffer forces a policy for the full case. The producer can block (backpressure), the new item can be dropped (load shedding, as in a network card), the oldest can be overwritten (a log ring), or the call can fail so the caller decides. An unbounded queue is not a policy; it moves the failure to memory exhaustion and hides overload as growing latency. Little's law gives the sizing: if 10,000 requests arrive per second and each spends 50 ms in the system, the average number in the system is 10,000 × 0.05 = 500. A buffer of 500 only just fits the average, so bursts require more, but a buffer much larger than needed only adds waiting time.
Queueing theory explains why queues grow so fast near saturation. For a simple single-server queue with random arrivals (M/M/1), the average number in the system is ρ/(1 − ρ), where ρ is utilization. At 50% utilization that is 1; at 90% it is 9; at 99% it is 99. Delay explodes while the system still looks "only 10% idle". This is the reason to keep utilization of shared resources below roughly 70–80% and to prefer small bounded queues.
A skip list is a sorted linked list in which some nodes also belong to higher lists. Every node is in level 1. When a node is inserted, flip a coin repeatedly: it joins level 2 with probability p, level 3 with probability p², and so on (p = 1/2 in the paper; Redis uses 1/4 with a limit of 32 levels). So level 2 has about n·p nodes, level 3 about n·p², and the number of levels is about log_{1/p} n. To search for a key, start at the top level of the head. Move right while the next node's key is smaller than the target; when it is not, drop one level and continue. At level 1 you are next to the answer. The expected number of steps is about (log_{1/p} n)/p, which is O(log n): for p = 1/2, roughly 2 log₂ n comparisons. Insertion searches in the same way, remembers the node where it dropped at each level, and splices the new node into those levels. Deletion is the reverse. There is no rebalancing, because the randomness keeps the structure balanced on average, and this is the reason it suits concurrency: an insertion changes a few pointers on its own path (with compare-and-swap, lock-free), where a tree rotation changes a shared subtree. A range scan simply follows the level-1 list. The probability layer gives the cost: a node reaches height h with probability p^(h−1), so the tallest node has height about log_{1/p} n, and the chance that a search takes many more steps than average falls exponentially. The memtable of an LSM tree also acts as a queue: writes enter the skip list at memory speed, and the flush to disk is the drain.

example: Walk through the ring buffer in the diagram. Capacity 8, head = 0, tail = 0. A producer enqueues items A to E: tail = 5, slots 0 to 4 are filled. A consumer dequeues A, B and C: head = 3. Size is 5 − 3 = 2. The producer enqueues F, G, H, I and J: slots 5, 6, 7 are used, then the counter 8 maps to slot 8 AND 7 = 0 and 9 maps to slot 1, which are free because A and B were consumed. Now tail = 10, head = 3, so size = 7 and one more slot is free. One more enqueue (K, into slot 2) makes tail − head = 8, which equals the capacity, so the ring is full, and the next enqueue must wait or drop. intuition: A ring buffer is a circular conveyor belt with one person putting items on and one taking them off; a skip list is a local train line with express stops.
The ring buffer is natural because the only thing that matters is the distance between the writer and the reader, and a fixed belt holds that distance in a fixed space: no allocation, no copying, and each side touches only its own counter. The skip list is natural because it gives a sorted list the same trick as binary search. If you could jump to the middle, you would halve the work. Instead of fixing the jump points, which would break on every insertion, each node tosses a coin to decide how far it can be jumped to, and the law of large numbers gives you about the right spacing for free.
mistakes: People often think a bigger buffer is always safer. In fact a large buffer only converts overload into delay: items wait longer, memory grows, and timeouts fire after the work is already useless. Network engineers call this bufferbloat. A small bounded buffer with a clear full-policy gives faster feedback.
People often think lock-free means fast. In fact a lock-free queue still pays for atomic operations and cache-line transfers, and under heavy contention from many producers it can be slower than a lock. The big wins of an SPSC ring come from having no sharing at all, not from the absence of a lock.
People often think skip lists are just a curiosity. In fact they sit in widely used systems: the default memtable in LevelDB and RocksDB, Redis sorted sets (together with a hash table), and Java's ConcurrentSkipListMap. Their worst case is O(n), but the probability of anything near that is negligible.
friction: A full queue forces a choice with no free option. Blocking can cause a chain of stalls and deadlocks when stages wait for each other in a cycle. Dropping loses data. Growing the buffer postpones the decision until memory runs out. Systems with several stages need the policy to be consistent across all stages, or one stage's silent drops hide the true load.
Low-level performance is delicate. False sharing between head and tail, a producer and consumer on different NUMA nodes, a missing memory barrier (which gives wrong results only on weakly ordered CPUs such as ARM), and a cache miss per slot on large items can each cost a factor of two to ten. Ring buffers also fix the item size or require indirection; variable-size messages need a framing scheme. Multi-producer, multi-consumer queues are much harder: the ABA problem, contention on the shared counter, and fairness all require care.
Skip lists have costs too. Each node stores several forward pointers (on average 1/(1 − p), which is 2 for p = 1/2 and 1.33 for p = 1/4), plus a random height, so memory overhead per entry is higher than for a packed B-tree. Pointer chasing makes them cache-unfriendly, and scans are slower than in a B-tree or sorted array. They give only probabilistic balance, which makes worst-case latency analysis awkward. Their dominant role in memtables works because the memtable is small, short-lived and write-heavy.
practice: Use the standard library queue for most application code, and choose the bounded variant (ArrayBlockingQueue, Go channels with a buffer, asyncio.Queue(maxsize=...)) so overload shows up as backpressure. Choose the capacity from Little's law with headroom for bursts, and expose the queue depth as a metric: the depth and the time spent waiting are the first signals of trouble. Set a timeout on blocking calls, and decide in advance what the full policy is.
For latency-critical paths between two threads, use an SPSC ring (for example Rust's crossbeam and rtrb crates, C++ folly ProducerConsumerQueue, or the Disruptor in Java). Pad the head and tail to separate cache lines, size the ring to a power of two, and batch: write or read several items per atomic update to cut the cost per item. Preallocate and reuse slots to avoid garbage collection pauses.
For sorted in-memory data with concurrent writers, a skip list is a good choice: use ConcurrentSkipListMap in Java or the memtable already built into your storage engine. In RocksDB, the skip list memtable is the default, and the write buffer size (64 MB by default) and the number of write buffers decide how long writes are absorbed before they stall. In Redis, sorted sets provide the skip list with rank queries; use ZRANGE with BYSCORE for ranges. Note that tuning the limits (write buffer size, queue depth) is usually worth more than changing the data structure.
tradeoffs: Choose a bounded queue over an unbounded one in almost every service. You give up the convenience of never blocking, and you gain a limit on memory and a visible signal of overload. Choose an unbounded queue only when the producer is itself bounded (for example a fixed number of tasks) or when losing the work is worse than running out of memory.
Choose a ring buffer when the item size is fixed (or a pointer), the throughput is high and the producer and consumer count is small: no allocation, great cache behaviour. Choose a linked-list or segmented queue when sizes vary, the maximum depth is unknown, or many producers join and leave; you pay in allocation and cache misses. Choose a lock-based queue for simplicity when the rate is under about a million items per second; choose lock-free or SPSC structures when a profile shows lock contention.
Choose a skip list over a balanced tree for concurrent in-memory ordered data and simple code: lock-free insertion and easy range scans, at the cost of more memory per key and only probabilistic balance. Choose a B-tree (or a cache-friendly in-memory B-tree) when the data is read-heavy, memory use matters, or scans must be fast, since the B-tree packs many keys in each cache line. Choose a hash table when order is not needed.
interview: Design a lock-free single-producer single-consumer ring buffer. What can go wrong? || Fixed array of power-of-two size, counters head and tail that only increase, index with a mask. The producer writes the slot, then does a release store of tail; the consumer does an acquire load of tail, reads the slot, then release-stores head. Problems: head and tail on the same cache line (false sharing), missing memory ordering on ARM, and treating full and empty incorrectly if counters wrap.
Explain how a skip list works and why it is O(log n) in expectation. || It is a sorted linked list where each node is promoted to higher levels with probability p. Search starts at the top and moves right until the next key is too large, then drops down. With p = 1/2 there are about log₂ n levels and about two steps per level, so about 2 log₂ n comparisons. The randomness keeps the spacing even without rebalancing.
Why do LSM stores use a skip list for the memtable and not a B-tree or a red–black tree? || A memtable is small, in memory, write-heavy and needs concurrent inserts and ordered iteration for flushing. A skip list inserts by changing a few pointers with compare-and-swap and keeps level 1 as a sorted list for the flush. A balanced tree has rotations that touch shared subtrees and need more complex locking.
Your service has latency spikes under load, and the request queue depth grows. How do you reason about it using Little's law? || Little's law says items in the system = arrival rate × time in system. If depth grows, either arrivals exceed service capacity or each request is taking longer. Check utilization: near 100% the queue grows without bound. Fix by reducing time per request, adding capacity, bounding the queue and shedding load, not by enlarging the queue.
quiz: How do you tell a full ring buffer from an empty one when head equals tail on a wrapped index? || Use counters that keep increasing and apply the mask only when indexing: empty means tail − head = 0 and full means tail − head = capacity. Another way is to keep one slot unused.
In a skip list with p = 1/2 and 1,000,000 keys, about how many levels are there and how many comparisons does a search need? || About log₂ 1,000,000 ≈ 20 levels, and roughly 2 × 20 = 40 comparisons on average.
A service receives 2,000 requests per second and each request spends 150 ms in the system. How many requests are in the system on average? || By Little's law, L = λ × W = 2,000 × 0.15 = 300 requests.
Why can head and tail sharing a cache line slow an SPSC ring buffer? || Each core writes its own counter, and every write invalidates the other core's copy of the whole 64-byte line. The line bounces between cores (false sharing) and each access becomes a cache miss. Padding puts them on separate lines.
You can choose a bounded queue of 100 or an unbounded queue for a service that sometimes receives 10 times its normal load for a minute. Which one, and what else do you need? || The bounded queue, with a full policy: reject or shed with a clear error (HTTP 429 or 503), and let clients retry with backoff. The unbounded queue would grow by many minutes of work, memory would increase and every request would time out after waiting. Add queue depth and wait-time metrics and alert on them.

@@ externalmem
value: The usual way to count the cost of an algorithm is to count CPU steps. This fails as soon as the data does not fit in memory, because then the cost is dominated by moving data between a slow big store (disk, SSD, object storage, the network) and a fast small one (RAM). One CPU step takes about a nanosecond. One random read from a spinning disk takes about 10 milliseconds, ten million times longer. The external-memory model (also called the I/O model or disk access model) is a simple fix: ignore the CPU, and count only the number of block transfers between the two levels. An algorithm that does fewer of them is faster in practice, often by orders of magnitude.
This one change in the unit of cost explains designs that otherwise look strange. Why B-trees have hundreds of children per node. Why LSM trees buffer writes and write them in large sorted batches. Why databases sort and merge instead of looking records up one at a time. Why Parquet files use row groups of about 128 MB with column chunks inside. Why Spark spills sorted runs to disk and merges them. All of these follow from one rule: pay for blocks, not for items, and use every byte of each block you pay for.
The layer below, asymptotic analysis (L4), supplies the method: describe cost as a function that grows with the input, now with the unit changed from CPU operations to block transfers, and with extra parameters for the block size B and the memory size M. The layer above is built directly on it: the B-tree minimizes the number of blocks on a search path, and the LSM tree minimizes the number of blocks written per inserted item. Sorting (L3) and join algorithms inherit the same bounds.
terms: Block (page) — the unit moved between disk and memory in one transfer, of B items (for example 4 KB for a database page or 128 MB for an HDFS block).
Memory size M — how many items fit in fast memory; a block transfer moves B of them.
N — the number of items in the problem; n = N/B is the number of blocks of data.
I/O (block transfer) — reading one block into memory or writing one block out; the quantity the model counts.
Scan — reading all N items in order, costing N/B transfers.
Fan-out — how many children a node has; in a B-tree about B, so the tree is only log_B N levels high.
Sequential versus random access — reading consecutive blocks versus jumping around; the first amortizes the latency over many blocks.
Cache-oblivious algorithm — an algorithm that is efficient for every B and M without knowing them, and so for all levels of the memory hierarchy.
Write amplification — the number of bytes physically written per byte the application wrote.
history: The problem is as old as magnetic tape and drums. Knuth's volume on sorting and searching (1973) is largely about how to sort with tapes, where only sequential reads are possible, and about balanced merging and replacement selection. Hong and Kung (1981) formalized the cost of moving data between a small fast memory and a large slow one in their "red-blue pebble game", and proved lower bounds for matrix multiplication and the FFT.
The model used today came from Alok Aggarwal and Jeffrey Vitter, "The Input/Output Complexity of Sorting and Related Problems" (Communications of the ACM, 1988). They defined N, M and B, proved that sorting needs Θ((N/B) log_{M/B}(N/B)) block transfers, and showed that external merge sort matches that bound. Within a few years a whole field followed: Vitter and Shriver extended the model to several disks (1994), Arge's buffer tree (1995) showed how to batch operations on trees, and Vitter's survey "Algorithms and Data Structures for External Memory" (2008) collected the results.
In the same decade database engineers applied the ideas. Bayer and McCreight had invented the B-tree in 1970, before the model existed, from exactly the same intuition. O'Neil, Cheng, Gawlick and O'Neil proposed the log-structured merge-tree in 1996 to cut the cost of random writes. Frigo, Leiserson, Prokop and Ramachandran (1999) introduced cache-oblivious algorithms, which reach the optimal bounds without knowing B or M, so they work for the CPU cache, main memory and disk at the same time. Brodal and Fagerberg (2003) showed the trade-off curve between insertion and search cost, which write-optimized trees such as the Bε-tree follow. In the 2010s, object stores such as Amazon S3 brought the model back with larger blocks: a request has a latency of tens of milliseconds, so it should read megabytes.
how: The model has a small number of rules. There are two levels of storage. Fast memory holds M items. Slow storage is unbounded and organized in blocks of B items. The CPU can compute for free on whatever is in memory. The only action that costs anything is an I/O: moving one block between the levels. The cost of an algorithm is its number of I/Os. Three quantities are used constantly. Scanning N items costs N/B I/Os, because you read each block once. Sorting N items costs about (N/B)·log_{M/B}(N/B) I/Os. Searching in an ordered index costs log_B N I/Os. Compare these with the CPU-model values N, N log₂ N and log₂ N: the model divides the cost of a scan by B, replaces the base 2 by M/B in the sorting logarithm, and replaces the base 2 by B in the search logarithm.
Each formula has a mechanism behind it. A scan reads blocks in order and uses every item in each block, so no block is read twice. Sorting works by external merge sort. First, read M items at a time, sort them in memory and write them as a sorted run: that is one pass over the data and produces N/M runs. Then merge many runs at once. With M items of memory you can keep one block buffer per run, so you can merge M/B − 1 runs in a single pass. Each pass reduces the number of runs by that factor, so the number of merge passes is about log_{M/B}(N/M). The logarithm has the huge base M/B, which is often tens of thousands, so the answer is almost always 1 or 2 passes. This is the same algorithm as in the sorting concept, seen here as the optimum rather than just a good idea.
Searching is where B-trees come from. A binary search tree on N items needs about log₂ N levels, and on disk each level costs a separate block read. A B-tree makes each node as large as a block and gives it about B children, so one block read narrows the search by a factor of B instead of 2. The height is log_B N. With B = 200 keys per node and N = 10⁹ keys, the height is about 4, against 30 for a binary tree. The top levels are small enough to stay in memory, so a real lookup costs 1 or 2 disk reads. The model also states a limit: any comparison-based search structure needs Ω(log_B N) I/Os, so the B-tree is optimal.
Writing is where the model gets interesting. Inserting into a B-tree costs about one random block write per insertion, since the new key lands in an arbitrary leaf. This is far from the lower bound for batch workloads. The buffer tree and the LSM tree reach lower cost by accumulating updates in memory, sorting them, and pushing them down in large batches. With a size ratio T between levels, an LSM tree with leveling rewrites each item about T/2 times per level, over log_T(N/M) levels, so the amortized cost per inserted item is about (T/B)·log_T(N/M) block writes: because it is divided by B, many items share every block write. With B = 1,000 items per block and a typical T = 10 over 4 levels, that is a few hundredths of a block write per insert, against one for the B-tree. The price is that a search may need to look in several levels.
How do you choose B in practice? The model says the block should be big enough to hide the latency of a request. A device with latency L and bandwidth W delivers the best value when you read about L × W bytes per request. For a hard disk with 10 ms seek and 200 MB/s that is 2 MB. For an NVMe SSD with 80 microseconds and 3 GB/s it is about 240 KB (the physical page is 4 to 16 KB, but requests below a few hundred KB leave bandwidth unused when queue depth is low). For S3 with 30 ms first-byte latency and 90 MB/s per stream it is about 2.7 MB. This is why Parquet row groups and HDFS blocks are tens to hundreds of megabytes, and why Spark reads files in 128 MB splits by default.

example: Start with the gap between sequential and random access. A table has one billion records of 100 bytes, which is 100 GB, on a hard disk with a 10 ms seek and 200 MB/s of sequential throughput. A full scan reads 100 GB / 200 MB/s = 500 seconds. Now fetch each record by a separate random read, one seek each: 10⁹ × 10 ms = 10⁷ seconds, which is 116 days. The ratio is about 20,000. Even reading in 4 KB blocks, which hold 40 records each, and touching all 25 million blocks in random order costs 25 × 10⁶ × 10 ms = 250,000 seconds, about 3 days, still 500 times worse than the scan. This is why a query planner will choose a full scan over an index when it expects to touch more than a small percentage of the rows, and why a join that looks up a record per row is hopeless.
Now the sort. Sort 1 TB with 64 GB of memory and 1 MB blocks. N/B = 10⁶ blocks, M/B = 65,536 buffers. The formula gives log_{65,536}(10⁶) = ln(10⁶)/ln(65,536) = 13.8 / 11.1 ≈ 1.25, so we expect two passes over the data. In detail: pass one reads 64 GB at a time, sorts it and writes 16 runs of 64 GB. Pass two merges all 16 runs at once (we have buffers for 65,535 of them). Each pass reads 1 TB and writes 1 TB, so the total traffic is 4 TB. At 1 GB/s of sequential bandwidth the sort takes about 4,000 seconds, a bit over an hour. A sort that used random access to place each record by its final position would need 10¹⁰ separate accesses and not finish for years.
Finally, the index. A B-tree over 10⁹ keys with 200 keys per node has height ⌈log₂₀₀ 10⁹⌉ = 4. The root and the second level (1 + 200 nodes of 8 KB, about 1.6 MB) stay in memory, and the third level (40,000 nodes, 320 MB) often does as well. A lookup then costs 1 or 2 disk reads, about 0.1 to 0.2 ms on NVMe or 10 to 20 ms on a hard disk. A binary search over a sorted file with the same keys would need about 30 reads with the last ones spread over different blocks, 300 ms on a hard disk.
intuition: When you can only carry one box at a time, you plan your trips around boxes, not around items.
The model is natural once you accept that the expensive thing is the trip, not the content. If a trip costs a fixed latency and the data comes in a block anyway, then a trip that uses only one item of the block wastes B − 1 of them. Every good external algorithm is therefore a way of making each trip useful: sort so that neighbours in order are neighbours on disk, batch writes so that many updates share one trip, and build wide trees so that one trip rules out most of the data. The logarithm base shows the payoff: a trip that is useful for B items shrinks the problem by a factor of B instead of 2.
mistakes: People often think that disk-based algorithms are just slower versions of in-memory algorithms. In fact the best algorithms are different. Binary search, quicksort with random partition access, and pointer-based trees are good in memory and bad on disk. B-trees, merge sort and sequential scans are good on disk. The problem changes shape when the unit of cost changes.
People often think SSDs make the model obsolete. In fact they shrink the gap but do not remove it. An NVMe read costs about 80 µs against 100 ns for DRAM, 800 times more, and a read below the 4 KB page size costs as much as a full page. Writes are done in pages but erased in blocks of megabytes, so random small writes cause write amplification. Cloud object stores bring back large blocks and high latency.
People often think the model is only about disks. In fact it applies to any two levels of the memory hierarchy: cache and RAM (B = 64 bytes), RAM and SSD, a node and the network, and a cluster and object storage. The shuffle phase of Spark and the page cache of a database are the same problem at other scales.
friction: The model is deliberately simple, and real storage breaks its assumptions. Latency and bandwidth are different things, so "one block" is not a fixed cost: sequential blocks are far cheaper than random ones, and the model does not distinguish them (the model with seeks, sometimes called affine, does). SSDs read faster than they write and have internal parallelism, so a single thread leaves most of the bandwidth unused; at queue depth 32 an NVMe drive may deliver ten times the IOPS of queue depth 1. Reads and writes cost differently, and the operating system's page cache, read-ahead and write-back change what an I/O even is.
Cloud storage adds more. Object stores have request costs (money per thousand GET requests) as well as latency, so there is a cost-based block size as well as a time-based one. Tail latency is large: some S3 requests take ten times the median. Distributed systems add network transfers as a third level, and the model must be extended with a cost per byte shuffled.
Tuning is still empirical. B-tree page size, the LSM size ratio T, the number of levels, Bloom filter bits and memory split between cache and write buffers all interact, and the best settings depend on the workload mix. Cache-oblivious algorithms promise independence from these parameters, but they carry larger constants and need tall caches, so production systems still tune. Finally, lower bounds in the model are for comparison-based operations on one disk; with indexes that use hashing or learned structures, the bounds are less settled.
practice: Think in blocks when you design a data layout. Make reads sequential, make them large (megabytes on disks and object stores), and make each read useful: column-oriented formats such as Parquet read only the columns you need, and sorting or clustering the data on the filter column lets min/max statistics skip row groups completely. Aim for files of 128 MB to 1 GB, and avoid thousands of small files, because each file costs a request latency (and in the table-format metadata) regardless of its size; compaction is how you restore the block size.
For indexes and storage choices, ask how many I/Os a typical operation costs and whether they are random or sequential. A B-tree gives 1 to 3 random reads per lookup and 1 or more random writes per update. An LSM tree gives low write cost and 1 to several reads per lookup, kept low by Bloom filters. Choose according to the read–write mix and the latency target. Keep the top of the index in memory and size the cache so that the working set fits.
In Spark and similar engines, treat spill as the sign of crossing M. If a stage spills, the data per task is larger than the memory per task. Fix it by raising the number of partitions so that each task's data fits in memory, or by increasing executor memory, before tuning anything else. Remember that the merge fan-in is limited by buffers: too many spill files per task with small buffers cause many small reads. Prefer a few large sequential files over many small ones, and compress, because compression raises the effective B.
tradeoffs: Choose a B-tree when reads and range scans dominate and updates are moderate: a lookup costs log_B N blocks and range scans follow linked leaves. Choose an LSM tree when writes dominate (logging, time series, ingestion): inserts cost a small fraction of a block, but reads may touch several levels and compaction rewrites data 10 to 30 times. You give up either read latency or write throughput.
Choose a large block size (megabytes) for scans and object storage, where latency is high and bandwidth is plentiful; choose a small block size (4 to 16 KB) for point lookups on local SSD, where reading more than you need wastes bandwidth and cache. The same table can use both: large files for scans, small pages inside for lookups.
Choose external merge sort when the data exceeds memory and the result must be ordered or grouped; choose hash partitioning when only grouping is needed and keys are not skewed. Sorting costs a little more CPU but gives ordered output and handles skew more gracefully; hashing is faster on uniform data but a single hot key can overflow a partition.
interview: What does the external-memory model count, and why is it a better predictor than the RAM model for large data? || It counts block transfers between a small fast memory of size M and a large slow store with blocks of size B. For data larger than memory the cost is dominated by these transfers: one random disk read costs millions of CPU instructions. The model captures why scans (N/B) are cheap, random access (N) is expensive, and sorting costs (N/B)·log_{M/B}(N/B).
Why do B-trees have a large fan-out, and how many levels does a billion-key B-tree have? || A node equals one block, and filling it with keys makes each read rule out a factor of B of the data. With 200 or more keys per node, one billion keys need about 4 levels, and the top two or three stay in memory, so a lookup costs 1 or 2 disk reads. A binary tree would need about 30.
How many passes does external merge sort need for 1 TB with 16 GB of memory and 4 MB blocks? || Memory holds 16 GB / 4 MB = 4,096 buffers. Pass 0 makes 1 TB / 16 GB = 64 runs. A merge can take up to about 4,095 runs, so one merge pass finishes. Two passes in total, about 4 TB of I/O.
Why is an LSM tree better than a B-tree for write-heavy loads in this model? || A B-tree insert dirties one random leaf, so it pays about one random block write per item. An LSM tree buffers items in memory, writes them in large sorted batches and merges runs sequentially, so each block write carries B items and the amortized cost per insert is about (T/B)·log_T(N/M), far below one write. The price is read amplification and compaction work.
Your Spark job spills heavily on a sort-merge join. How do you think about it in terms of the model? || The task's data exceeds its memory M, so it creates runs and merges them, doubling the I/O. Raise parallelism so each task's data fits, or add memory per task. If it still spills, check for skew, because a hot key makes one task far larger than M, and reduce data first with filters and column pruning.
quiz: State the three basic costs in the I/O model for N items, memory M and block size B. || Scan: N/B transfers. Sort: about (N/B)·log_{M/B}(N/B). Search in an ordered index (B-tree): log_B N.
Why does external merge sort usually need only two passes? || The merge can combine M/B − 1 runs at once, and M/B is typically tens of thousands. So after one pass creating N/M runs, one merge pass suffices unless N/M exceeds M/B.
A disk has 8 ms seek time and 250 MB/s bandwidth. What block size balances latency and bandwidth? || Latency × bandwidth = 0.008 s × 250 MB/s = 2 MB. Reading 2 MB per request spends about half the time on the seek and half on transfer; larger requests approach full bandwidth.
How many levels does a B-tree with 500 keys per node need for 10 billion keys? || log₅₀₀(10¹⁰) = 10 / 2.7 ≈ 3.7, so 4 levels.
You have to look up 5 million random rows from a 2 TB table on a hard disk. Is a scan or random lookups faster? || Random lookups cost 5 × 10⁶ × 10 ms = 50,000 s (14 hours); a scan of 2 TB at 200 MB/s is 10,000 s (2.8 hours). The scan wins, unless the data is on SSD or the requests can be sorted and batched.

@@ maxflow
value: Network flow answers a question that appears in many forms: given a network where each link can carry a limited amount, how much can you push from a source to a sink? The same algorithm decides how many pipelines a network can carry, how many ad impressions can be delivered to campaigns with caps, how many workers can be assigned to jobs they can do, which tasks to run on which machines, and where the narrowest bottleneck of a system lies. It also gives a proof of optimality that is rare in engineering: when the algorithm stops, it hands you a minimum cut, a small set of links whose total capacity equals the flow, which shows that no better solution exists.
Allocation problems in ad tech, scheduling and data placement have this shape. Supply (impressions, machine slots, storage) has to be matched to demand (campaign goals, jobs, replicas) through eligibility rules and capacities. Written as a flow network, the problem has a polynomial-time algorithm that finds the exact best answer, and when the demand cannot be met, the min cut names the exact bottleneck. Matching in bipartite graphs, edge-disjoint paths, project selection, baseball elimination and image segmentation are all reductions to flow.
The layers below show what the algorithm is made of. Graph algorithms (L3) contribute the search that finds a path with spare capacity, usually breadth-first search, and the vocabulary of residual graphs; in return the flow solves graph problems such as matching that plain traversal cannot. Linear programming and duality (L4) explain why the answer is exact: max flow is a linear program, its dual is the minimum cut, and strong duality says the two optima are equal. The integrality of flow (capacities that are integers give an optimal flow of integers) makes the LP useful for discrete assignment.
terms: Flow network — a directed graph with a source s, a sink t, and a capacity on every edge.
Flow — an assignment of a number to each edge, at most its capacity, such that at every node other than s and t the inflow equals the outflow.
Residual graph — the graph of remaining possibilities: each edge shows its spare capacity, and each edge with flow also has a reverse edge showing how much flow can be cancelled.
Augmenting path — a path from s to t in the residual graph; pushing flow along it increases the total flow.
Cut — a split of the nodes into a side containing s and a side containing t; its capacity is the sum of the capacities of the edges going from the s-side to the t-side.
Min cut — the cut with the smallest capacity; the narrowest bottleneck between s and t.
Bipartite matching — a set of edges between two groups of nodes in which no node appears twice.
Saturated edge — an edge whose flow equals its capacity.
Integrality theorem — if all capacities are integers, there is a maximum flow in which every edge carries an integer amount.
history: The problem has a military origin. In 1955, T. E. Harris and F. S. Ross wrote a secret RAND report for the US Air Force about the Soviet railway network, asking how much the rail lines could carry from the Soviet Union into Eastern Europe and which links, if cut, would stop the most traffic. In effect they stated the max-flow and min-cut problem. The report was declassified in 1999, and Alexander Schrijver's history of the problem tells the story. At RAND, Lester Ford and Delbert Fulkerson turned it into an algorithm in 1956 ("Maximal Flow Through a Network"), and proved the max-flow min-cut theorem. Elias, Feinstein and Shannon proved the same theorem independently in 1956.
Ford–Fulkerson has a weakness: with irrational capacities, or with an unlucky choice of paths, it can run for a very long time or never stop. Dinitz (1970) and Edmonds and Karp (1972) fixed this independently by always choosing the shortest augmenting path, which gives a polynomial bound: O(V·E²) for Edmonds–Karp. Hopcroft and Karp (1973) gave an O(E√V) algorithm for bipartite matching, the standard method for assignment, and Kuhn's Hungarian method (1955) solved the weighted version. Goldberg and Tarjan (1986, journal version 1988) introduced the push–relabel method, which stops thinking about whole paths and moves excess flow locally; it became the basis of the fastest practical codes. Orlin (2013) reached O(V·E). In 2022 Chen, Kyng, Liu, Peng, Probst Gutenberg and Sachdeva published an algorithm that runs in time m^(1+o(1)), almost linear in the number of edges, which settled the theoretical question; it is not yet practical.
Applications spread widely. Greig, Porteous and Seheult (1989) used min cut for image restoration, and Boykov and Kolmogorov's algorithm (2004) made graph-cut segmentation a standard tool in vision. Ad allocation entered with the guaranteed-delivery display market, and with the online matching results of Karp, Vazirani and Vazirani (1990) and the AdWords work of Mehta, Saberi, Vazirani and Vazirani (2007), which show how well one can do when impressions arrive one at a time and the future is unknown.
how: The simplest algorithm is Ford–Fulkerson. Start with zero flow. Repeat: find a path from s to t on which every edge has spare capacity; push the smallest spare amount along it (the bottleneck); update the flows. Stop when no such path exists. Finding the path is a graph search, so this is the place where the graph algorithms below the concept do their work: breadth-first search takes O(V + E) per path. Edmonds–Karp uses breadth-first search so that the path has the fewest edges, and this bounds the number of augmentations by O(V·E), giving the O(V·E²) total.
The crucial trick is the residual graph. After pushing flow on an edge u→v, two things are true: the edge has less spare capacity, and you now have the option to undo some of the flow. So the residual graph keeps the edge u→v with capacity (c − f) and adds a reverse edge v→u with capacity f. A later augmenting path may use the reverse edge, which means "send less flow along u→v after all, and use that capacity elsewhere". This lets the algorithm repair early mistakes. Without reverse edges, a greedy choice of paths could get stuck at a flow that is not the maximum; with them, the algorithm can never be stuck.
Why is the final flow maximum? When the search fails, let S be the set of nodes reachable from s in the residual graph; t is not in S. Every edge from S to the outside must be saturated (otherwise the search would have crossed it), and every edge coming back into S must carry zero flow (otherwise the reverse edge would let the search leave S). So the flow across the cut (S, rest) equals the cut's capacity. But no flow can exceed the capacity of any cut, because everything must cross it. A flow that equals the capacity of some cut is therefore maximum, and that cut is minimum. This is the max-flow min-cut theorem, and the algorithm proves it constructively. From the LP view, the flow variables are the primal and the cut indicators are the dual, so the equality is linear programming duality, and the algorithm is a combinatorial way of solving the LP.
Integrality follows from the construction. If all capacities are integers, each augmentation adds an integer bottleneck, so the flow stays integral at every step. This is why flow can model assignment: a fractional answer like "0.5 of a worker on job 1" cannot occur, while a general LP might give one.
Matching is the main reduction. For a bipartite graph with workers on the left and jobs on the right, add a source connected to each worker with capacity 1, a sink connected from each job with capacity 1, and edges from workers to the jobs they can do with capacity 1. An integral max flow selects a set of edges where each worker and each job is used at most once, which is a maximum matching. The min cut gives König's theorem (maximum matching equals minimum vertex cover) and Hall's condition for when every worker can be matched. With capacities greater than 1 on the source and sink edges, the same idea models supply and demand in allocation: this is how a campaign with a goal of 600 impressions is matched to supply segments that can provide them. Hopcroft–Karp speeds up unit-capacity matching to O(E√V) by augmenting along many shortest paths at once, and the push–relabel algorithm with heuristics (global relabeling, gap) is the practical choice for general networks.
Push–relabel works differently from path search. It gives each node a height, lets the source push as much as it can into its neighbours, and then repeatedly moves surplus (excess) from a node to a lower neighbour along an edge with spare capacity; when a node has excess but no lower neighbour, it raises its own height (relabels). Excess that cannot reach the sink drifts back to the source. All operations are local, which is why the method suits parallel hardware and why the best practical codes use it. Costs add a dimension. When each edge has a price per unit, the min-cost max-flow problem finds the cheapest way of sending the flow. It is solved by repeatedly augmenting along the cheapest residual path (successive shortest paths) or by network simplex, and covers weighted assignment and transportation problems. Multiple commodities (several different goods sharing the same links) are harder: integrality is lost, and the problem needs general linear programming.

example: Work the five-edge network in the diagram: s→a 1, s→b 1, a→b 1, a→t 1, b→t 1. A bad first choice is the path s→a→b→t with bottleneck 1. Push 1. Now s→a is saturated and b→t is saturated. The residual graph has: s→b with 1 spare, a→t with 1 spare, a→b with 0 spare, and the reverse edge b→a with 1 (we can undo the a→b flow). Without reverse edges, the search from s can reach only b, and from b nowhere, so we would stop at flow 1, although the maximum is 2. With the reverse edge, there is a path s→b→a→t. Its bottleneck is 1. Push 1: the s→b flow becomes 1, the reverse edge b→a cancels the flow on a→b (which falls to 0), and a→t gets 1. The final flows are s→a 1, a→t 1, s→b 1, b→t 1. Total flow is 2. The residual search from s finds nothing reachable except s itself, so S = {s}. The cut (S, rest) has capacity s→a + s→b = 2, which equals the flow. So the flow is maximum and the minimum cut is the two edges leaving s.
Now an ad-delivery allocation. Three audience segments with daily impression supply: S1 has 1,000 impressions, S2 has 500, S3 has 800. Three campaigns with daily goals: A wants 600 and can use S1 only; B wants 900 and can use S1, S2 or S3; C wants 700 and can use S3 only. Build the network: source to each segment with capacity equal to its supply, segment to campaign edges where targeting allows (capacity unlimited), campaign to sink with capacity equal to the goal. Max flow: C can take 700 from S3 (leaving 100 in S3), A can take 600 from S1 (leaving 400 in S1), and B takes 400 from S1, 500 from S2 and 100 from S3 = 1,000, of which 900 are needed. All goals (2,200 in total) are met out of 2,300 available. Now raise C's goal to 900. C can only draw on S3, which has 800. The max flow is A 600 + B 900 + C 800 = 2,300 against a total demand of 2,400, so 100 impressions of C's goal cannot be delivered. The min cut reports why: the set {C, S3} has demand 900 but eligible supply only 800. This is Hall's condition failing, and it tells the sales team which campaign cannot be filled and by how much, without trial and error.
intuition: Push water through pipes until no route has spare room; the narrowest set of pipes separating source from sink is the limit.
The idea is natural because of conservation. Whatever enters a junction must leave it, so the only way to carry more is to find a route that still has room somewhere. The residual graph is the honest bookkeeping of "where is there still room, and what could I take back". The cut is the other side of the same coin: if you can name a set of pipes that every route must cross and whose total capacity is X, nothing above X is possible. When the largest flow you can find equals the smallest cut you can name, both are proved at once. That is rare, and it is what makes the method trusted.
mistakes: People often think max flow is only about networks of pipes or roads. In fact it is a general tool for allocation and assignment. Any problem where items are matched to slots with capacities and eligibility can often be written as a flow, and the integrality theorem guarantees whole-number answers.
People often think greedy augmentation is enough, without reverse edges. In fact greedy path choices can lock in a bad decision. The reverse edges in the residual graph let later paths cancel earlier flow, and without them the algorithm may stop below the true maximum, as in the example above.
People often think flow can handle any cost or constraint. In fact plain max flow has one commodity, linear capacities and no fixed costs. Adding per-unit costs gives min-cost flow, which is still polynomial. But several commodities sharing links (multi-commodity flow) loses integrality, and fixed charges for using an edge or other combinatorial constraints (for example "at most two campaigns per segment") make the problem NP-hard.
People often think the fastest-looking algorithm in theory is the one to use. In fact the almost-linear-time algorithm of 2022 is a theoretical result with huge constants and complex machinery. In practice, Dinic or push–relabel with good heuristics, or the specialised Boykov–Kolmogorov method for vision, are what libraries implement.
friction: Real allocation problems often leave the pure flow model. They have non-linear objectives (diminishing returns, pacing), budgets that depend on price and bids, uncertain forecasts, and impressions that arrive online before the future supply is known. The online version cannot be solved exactly: the classic result is that no online algorithm can guarantee more than a 1 − 1/e ≈ 63% fraction of the optimal matching in the worst case, though stochastic and forecast-based methods do better in practice. When constraints are extra (frequency caps across campaigns, exclusion rules), the model becomes an integer or linear program, and the nice structure disappears.
Scale and memory are practical limits. Flow algorithms are graph traversals, with random memory access and little regularity, so they are hard to parallelise and slow on very large graphs; push–relabel parallelises better than augmenting paths, but efficient distributed versions are research-grade. A graph with billions of edges does not fit in one machine's memory. Many teams solve a coarse version (grouping similar segments) or use LP solvers with decomposition.
Numerical issues appear with real-valued capacities: floating point can leave tiny residuals that never reach zero, and Ford–Fulkerson with irrational capacities may not terminate. Use integers (impressions, cents) and scale. And flows are not unique: many optimal flows exist, and the algorithm returns an arbitrary one, which may be unfair or unstable between runs. If you need a particular choice, such as spreading delivery evenly, you add a secondary objective with costs.
practice: Recognise the shape. If you have items to assign, slots with capacities and rules for who can use what, ask whether it is a bipartite flow. If you need "the most that can be done" or "what is the bottleneck", flow gives both the number and the explanation. Use a library: NetworkX (maximum_flow, min_cut) for small problems, Google OR-Tools (SimpleMaxFlow, SimpleMinCostFlow) and LEMON or Boost Graph for large ones, and scipy.sparse.csgraph.maximum_flow or maximum_bipartite_matching when you already use SciPy.
Scale integers to avoid floating-point trouble: express supply in impressions and prices in micro-units. Collapse nodes before you solve: group impressions into segments with identical eligibility, which can shrink a graph from billions of impressions to thousands of segments. Always read the min cut when the flow is below demand; it names the unfilled campaigns and the supply that blocks them, and this is the output that planners and sales teams actually use.
When the model needs costs, use min-cost flow; when it needs side constraints or several commodities, go to a linear or integer programming solver (the flow model is then the starting formulation). For a production planner, keep the model simple and explainable, version the inputs, and check the plan against the real delivery with a tolerance. For matching of the assignment kind (tasks to machines, with weights), the Hungarian algorithm or min-cost flow are the tools; for unweighted matching, Hopcroft–Karp.
tradeoffs: Choose max flow when the problem is a single commodity with linear capacities and integer data: you get the exact optimum in polynomial time and a certificate of optimality. Choose linear or integer programming when you need several commodities, side constraints, or non-linear terms approximated by pieces; you give up the speed and the guaranteed integrality.
Choose Dinic or push–relabel for general large networks; choose Hopcroft–Karp for unit-capacity bipartite matching, which has the better bound, O(E√V); choose Edmonds–Karp only for teaching and tiny graphs.
Choose an offline flow plan when forecasts are good and the planning window is hours to a day; choose an online heuristic (balance, pacing, primal–dual) when decisions must be made per request and the future is uncertain, accepting a worst-case guarantee near 63% and better results in practice. A common design runs the offline flow periodically and uses its result as guidance for the online decisions.
Choose exact flow over a greedy rule such as "serve the campaign with the highest bid first" when the goals are hard guarantees and the constraints interact: greedy can starve a campaign that has narrow eligibility. You give up simplicity and some real-time responsiveness.
interview: State the max-flow min-cut theorem and give the intuition for why it is true. || In any flow network the maximum flow from s to t equals the minimum capacity of a cut separating them. Any flow must cross every cut, so flow is at most any cut's capacity. When augmenting paths run out, the nodes reachable from s form a cut whose forward edges are all saturated and backward edges empty, so the flow equals that cut's capacity, hence both are optimal.
Why does the residual graph need reverse edges? || Pushing flow on u→v might later turn out to be a mistake. The reverse edge v→u with capacity equal to the flow lets a later augmenting path cancel part of it and reroute. Without them, greedy path choices can stop at a non-maximum flow; with them, the absence of an augmenting path proves optimality.
How do you model assigning 10,000 tasks to 500 machines with capacity and eligibility constraints, and how do you detect infeasibility? || Source to each task with capacity 1, task to each eligible machine with capacity 1, machine to sink with the machine's capacity. If the max flow is below 10,000, the tasks are not all assignable, and the min cut (the reachable side of the residual graph) shows a set of tasks whose eligible machines have too little total capacity.
Compare Ford–Fulkerson, Edmonds–Karp and Dinic. || Ford–Fulkerson picks any augmenting path and may take time proportional to the flow value, or never stop with irrational capacities. Edmonds–Karp picks the shortest path by BFS and takes O(V·E²). Dinic builds a level graph with BFS and pushes a blocking flow with DFS, giving O(V²·E), and O(E√V) on unit-capacity bipartite graphs, and it is often the practical choice.
How does flow relate to linear programming? || Max flow is an LP with one variable per edge, capacity bounds and conservation constraints. Its dual is the min-cut LP, so strong duality gives max flow = min cut. Total unimodularity of the constraint matrix means vertices of the polytope are integral when capacities are integral, which is why the answer is whole numbers.
quiz: What are the two conditions a flow must satisfy? || Capacity: the flow on each edge is between 0 and its capacity. Conservation: at every node except the source and the sink, the total flow in equals the total flow out.
What does an augmenting path look like in the residual graph, and why does it include reverse edges? || It is a path from s to t using edges with spare capacity, either forward edges with unused capacity or reverse edges that cancel existing flow. Reverse edges let the algorithm undo earlier choices.
In the ad example, A (600, S1 only), B (900, any segment) and C (900, S3 only) face supplies S1 = 1,000, S2 = 500, S3 = 800. How much can be delivered, and what is the bottleneck? || A 600 + B 900 + C 800 = 2,300 of 2,400 demanded. C can only use S3 (800), so the 100 impressions short are due to that cut, {C, S3}: demand 900 against supply 800.
Why does an integer-capacity network always have an integer maximum flow? || Each augmentation adds the bottleneck of a path, which is an integer when all capacities and current flows are integers. So the flow stays integral at every step, and the algorithm stops with an integral maximum flow.
Edmonds–Karp runs in O(V·E²). For a graph with 1,000 nodes and 10,000 edges, what is the worst-case bound, and why is it rarely reached? || 1,000 × 10,000² = 10¹¹ steps in the worst case. In practice the number of augmentations is far below the V·E bound and each BFS stops early, so real runs take milliseconds to seconds; Dinic or push–relabel are faster still.
