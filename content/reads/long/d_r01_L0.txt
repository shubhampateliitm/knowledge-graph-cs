@@ tpu
value: A Tensor Processing Unit (TPU) is a chip that Google designed for one job: the matrix multiplications inside neural networks. A general CPU or GPU spends much of its silicon on flexibility: caches, branch prediction, instruction scheduling, many kinds of arithmetic. A TPU removes most of that and spends the area on a very large grid of multiply-accumulate units, a big on-chip memory and fast links to other chips. The result is more useful arithmetic per watt and per dollar for the workloads Google cares about. In 2013 Google estimated that if every Android user used voice search for just three minutes a day, speech recognition alone would force the company to double its datacenters. That estimate started the project.
Google has used TPUs inside its products since 2015 (search ranking, translation, photos, ads) and sold access through Google Cloud since 2018. They train and serve Gemini and the AlphaFold models, and by 2025 outside labs also used them at scale: Anthropic announced in October 2025 that it would use up to one million TPUs. As of October 2026, the generation available in Google Cloud is the seventh, called Ironwood (TPU7x, general availability in late 2025). Google announced the eighth generation at Cloud Next in April 2026 as two chips, TPU 8t for training and TPU 8i for inference and post-training, with general availability "in the coming months".
For the layer above, a TPU turns "train a model on thousands of chips" into a compiler and networking problem that Google controls end to end. It stands on three ideas from below. GPU computing (L1) established that deep learning is dense, parallel linear algebra where throughput matters more than the latency of any single operation; the TPU keeps that view and drops the general-purpose machinery. Tensor cores and systolic arrays (L3) supply the actual circuit: a grid in which data flows between neighbouring multiply-accumulate cells so each value read from memory is used hundreds of times. Collective communication (L1) explains why the chips are wired into a regular torus network: training sums gradients over all chips, and an all-reduce on a torus uses every link.
terms: Systolic array — a grid of simple cells where each cell multiplies, adds, and passes data to its neighbour on every clock tick, like blood pumped through vessels (systole means the beat of the heart).
MXU (matrix multiply unit) — the systolic array inside a TPU core; early TPUs had one 256 × 256 array, recent generations have several 128 × 128 or 256 × 256 arrays.
bfloat16 — a 16-bit number format with the same 8-bit exponent range as 32-bit float but only 7 mantissa bits; it keeps training stable while halving memory and bandwidth.
HBM (high-bandwidth memory) — memory stacked next to the chip package that gives terabytes per second of bandwidth; Ironwood has 192 GiB per chip.
ICI (inter-chip interconnect) — the direct chip-to-chip links of a TPU system; no host CPU or Ethernet switch sits between two neighbouring chips.
Torus — a network topology where chips form a grid whose edges wrap around, so every chip has the same number of neighbours; TPU v4 and later use three dimensions.
XLA — the compiler that turns a whole-program graph of tensor operations (from JAX, TensorFlow or PyTorch/XLA) into fused TPU code.
Pod and slice — a pod is the largest connected set of chips (9,216 for Ironwood); a slice is the part of it you rent for one job.
SparseCore — a small dataflow unit on newer TPUs for embedding lookups, which are memory-bound and irregular rather than matrix-shaped.
history: The first TPU was designed by a small team under Norm Jouppi, starting around 2013 and reaching production in about 15 months. TPU v1 ran in Google datacenters from 2015, was shown publicly in 2016, and was described in detail in the ISCA 2017 paper "In-Datacenter Performance Analysis of a Tensor Processing Unit". It was an inference-only chip. Its core was a 256 × 256 systolic array of 8-bit multiply-accumulate units (65,536 of them), giving a peak of 92 trillion operations per second on roughly 40 W. The paper reported that it ran Google's production neural networks 15 to 30 times faster than a contemporary CPU or GPU, and 30 to 80 times better in operations per watt.
The systolic array itself is much older: H. T. Kung and Charles Leiserson described it in 1978 for VLSI. What was new in 2015 was the observation that inference for the dominant neural networks of that time (multilayer perceptrons, LSTMs, convolutions) is mostly matrix multiplication, so a fixed-function array could be both small and fast.
TPU v2 (2017) and v3 (2018) added training. They used floating point (the bfloat16 format that Google Brain introduced), HBM memory, and a 2D torus of chips so that a 256-chip pod (v2) or 1,024-chip pod (v3, liquid cooled) could act as one machine. TPU v4 (2021) moved to a 3D torus with optical circuit switches that can rewire the links, scaled to 4,096-chip pods, and added SparseCores; the ISCA 2023 paper describes it. v5e and v5p (2023) split the line into cost-efficient and large-scale versions. v6e, called Trillium (2024), grew the matrix unit to 256 × 256. Ironwood (v7, announced April 2025) was the first generation marketed mainly for inference at scale ("the age of inference"), with 192 GiB of HBM per chip and pods of 9,216 chips. In April 2026 Google split the eighth generation in two: TPU 8t for training superpods of up to 9,600 chips, and TPU 8i for latency-sensitive inference with more on-chip SRAM. Why the split? Training wants maximum compute and a huge network; serving agents wants low latency and a large cache for the key-value state of long contexts.
how: Start with the arithmetic. A matrix multiplication \( C = A \times B \) needs \( M \times N \times K \) multiply-accumulate (MAC) operations but only \( M \times K + K \times N + M \times N \) numbers to move. The ratio of work to data grows with matrix size, so a chip can in principle stay busy if it reuses every number it reads. The trouble is that in a normal processor each MAC reads two operands from registers, and registers are fed by caches, which are fed by DRAM. Moving a number from DRAM costs far more energy than the MAC that uses it (roughly 100 times or more, in published energy tables). A systolic array attacks exactly this cost.
In the MXU, one matrix (usually the weights) is loaded into the grid so that each cell holds one value. The other matrix (the activations) is streamed in from the edge, one row per clock tick. Each cell multiplies the value it holds by the value arriving from its left neighbour, adds the result to the partial sum arriving from above, passes the activation on to the right and the new partial sum downwards. After a short pipeline delay, one finished output vector leaves the bottom edge on every tick. A 256 × 256 array performs 65,536 MACs per tick while reading only 256 activations from the buffer and writing 256 results. Each activation read is used 256 times, and no operand goes back to memory between steps. At 700 MHz, 65,536 MACs × 2 operations × 700 million = about 92 trillion operations per second, the number reported for TPU v1. This is the contribution of the L3 concept "tensor cores and systolic arrays": reuse is built into the wiring, not left to caches.
Around the array sit the parts that keep it fed. A TPU core has an MXU (or several), a vector unit for element-wise work such as activation functions, softmax pieces and layer norm, a scalar unit that runs the program and addresses memory, and a software-managed on-chip memory. There is no hardware cache and no speculative execution. The compiler decides what data lives where and when it moves, so timing is predictable. HBM supplies the large tensors; Ironwood reports about 7.4 TB/s per chip. Compute is huge too: 4,614 TFLOPs in FP8 per chip. The ratio of those two numbers (about 600 FLOPs per byte) tells you a kernel must reuse each byte hundreds of times to be compute-bound. Large matrix multiplications do; attention over a long cache or decoding one token at a time does not, which is why the inference-focused chips add memory capacity and bandwidth.
The compiler is the second half of the design. TPU programs are written in JAX, TensorFlow or PyTorch/XLA, and XLA traces them into a graph of operations with static shapes. It fuses element-wise operations into the matrix multiplications that feed them, picks tile sizes that fit the MXU and on-chip memory, schedules transfers between HBM and on-chip memory to overlap with compute, and inserts collective operations. Static shapes are a design choice, not an accident: because the compiler knows every size in advance, it can pipeline everything and the hardware needs no dynamic scheduling logic. The price is that dynamic shapes cause recompilation or padding.
The third part is the network. The hpc concept of collective communication explains the logic: in data-parallel training every chip computes gradients for its share of the batch, and an all-reduce sums them. In tensor and pipeline parallelism, chips exchange activations every layer. A TPU pod gives each chip direct ICI links to its neighbours (six links per Ironwood chip, 1,200 GB/s bidirectional in total), arranged as a 3D torus built from 4 × 4 × 4 cubes of 64 chips. A ring all-reduce along each torus dimension uses all links at once. Optical circuit switches join the cubes and can be reconfigured: a job asks for a slice shape such as 8 × 16 × 16, the system wires cubes into that shape, and a failed cube can be routed around. Between pods, the ordinary datacenter network carries data-parallel traffic. Together, the array, the compiler and the torus mean that a thousand chips behave like one very large, predictable accelerator.

example: Take a small layer: activations X with 8,192 rows (a batch of tokens) and 1,024 columns, multiplied by a weight matrix W of 1,024 × 1,024. The work is 8,192 × 1,024 × 1,024 = about 8.6 billion MACs, or 17.2 billion floating point operations. Use a 256 × 256 MXU at 1 GHz as a simple model (real chips have several arrays and different clocks). The array does 65,536 MACs per tick, so the ideal time is 8.6 billion / 65,536 = about 131,000 ticks, or 131 microseconds.
How does the data move? W is split into 4 × 4 = 16 tiles of 256 × 256. The compiler loads one tile into the array (256 ticks to shift the weights in). Then it streams all 8,192 rows of the matching 256-column slice of X through the array, one row per tick, 8,192 ticks. So each weight tile costs 256 + 8,192 ticks, and loading is only 3% of that time. If the batch were 64 rows instead, loading (256 ticks) would be 4 times longer than streaming (64 ticks) and the array would be mostly idle. That is the first lesson: a systolic array likes large batches, and small-batch decoding wastes it.
Now count memory traffic. X in bf16 is 8,192 × 1,024 × 2 bytes = 16 MB. W is 1,024 × 1,024 × 2 = 2 MB. The output is 16 MB. Total about 34 MB. The arithmetic intensity is 17.2 GFLOP / 34 MB = about 500 FLOPs per byte. Compare with a chip that has 4,600 TFLOPs and 7.4 TB/s: its balance point is about 620 FLOPs per byte. So this layer sits just under the line; with a larger batch or larger hidden size it would be compute-bound, and with a smaller one it would wait for HBM. Engineers use this calculation (the roofline model) before touching any code.
Finally, scale it. Suppose training uses 1,024 chips with pure data parallelism and the gradients of this layer are 1 million values in bf16 (2 MB). A ring all-reduce moves about 2 × 2 MB of data per chip regardless of chip count. At 1,200 GB/s of link bandwidth that is under 4 microseconds if perfectly overlapped, small compared with the compute. For a model with 100 billion parameters the gradient is 200 GB per replica, and then the network time is real and must be overlapped with the backward pass or reduced by sharding the parameters.
intuition: A TPU is an assembly line for matrix multiplication: each worker does one small step and hands the result to the next, so nobody walks to the warehouse.
The design is natural once you see where the energy goes. Arithmetic is cheap; moving data is expensive. A general processor reads operands for every operation. A systolic array reads each operand once and lets it travel through hundreds of cells, so the cost of fetching is shared across all of them. Because neural network layers are matrix multiplications with regular shapes, the compiler can know in advance exactly what each cell will do on each tick. That removes caches, branch prediction and dynamic scheduling, and the silicon they would use becomes more multiply-accumulate cells. The same reasoning applies one level up: a regular torus network and a compiler that knows the whole program let thousands of chips cooperate with little waste.
mistakes: People often think a TPU is simply a faster GPU. In fact it is a different trade: a few large matrix units, no hardware cache hierarchy and compiler-managed memory, against a GPU's thousands of small programmable cores. GPUs recently added their own matrix units (tensor cores), so the two designs have moved closer, but the programming model is still different.
People often think TPUs can only run Google's own models. In fact any model that XLA can compile runs on them. Large outside users train and serve on TPUs, and PyTorch models run through PyTorch/XLA. The real barrier is software maturity and tuning for unusual operations, not permission.
People often think "8-bit" or "bf16" means TPUs are less accurate. In fact the multiply uses low precision but the accumulation is done in wider precision (32-bit in the first TPU), and bfloat16 keeps the full exponent range of float32, which is what training needs to avoid overflow. What you lose is mantissa precision, which neural networks tolerate.
People often think a bigger MXU is always better. In fact an array wastes cycles whenever the matrix dimensions are smaller than the array or not a multiple of its size. A 256 × 256 array doing a 100 × 100 problem uses about 15% of its cells. This is why padding, batching and choosing dimensions that are multiples of 128 or 256 matter on TPUs.
friction: Access and lock-in are the first problems. TPUs are available almost only through Google Cloud, so the hardware cannot be bought for an on-premise cluster, and moving a large workload away means re-tuning for another accelerator. The software stack, while strong for JAX and improving for PyTorch, still has fewer community kernels, debugging tools and third-party libraries than CUDA. Custom operations that do not map to the matrix unit (some sparse, ragged or data-dependent computations) are harder to make fast.
Static compilation is both the strength and the weakness. Dynamic shapes, such as variable-length sequences in serving or data-dependent control flow, force padding or recompiling. Modern serving systems work around this with bucketing and paged attention, but this takes engineering effort that GPU users get more easily.
Scale brings its own failures. A 9,216-chip pod has many components; a single failing chip or link can stop a synchronous training job. Optical switching helps to route around dead cubes, and checkpointing frequently limits lost work, but large jobs still spend real time on restart and recovery. Power and cooling are also hard limits: Ironwood-class pods need liquid cooling, and Google quotes performance per watt as a main metric because power, not chips, is the constraint in new datacenters.
Finally, the field moves quickly. Each generation changes the memory size, number formats (the shift to FP8 and lower) and topology, so tuning done for one generation does not always carry over. Google's choice to split generation eight into a training chip and an inference chip shows that no single design is best for both.
tradeoffs: Choose TPUs when you train or serve large dense transformer models at high volume, can use JAX (or accept PyTorch/XLA), and want the lowest cost per token with predictable scaling to thousands of chips. Choose NVIDIA GPUs when your team depends on CUDA libraries and custom kernels, runs varied or experimental model code, needs to deploy on premise or in several clouds, or hires from the large CUDA talent pool. You give up flexibility with TPUs and give up some cost efficiency and network predictability with GPUs.
Choose a large TPU slice when the job is synchronous and needs all-to-all bandwidth, for example tensor-parallel training of a model that does not fit on one chip. Choose multiple smaller slices with data parallelism across them when the model fits in one slice, because the datacenter network between pods has far less bandwidth than ICI inside a pod. Bigger slices cost more in failure risk and queue time.
Choose the inference-oriented chips (Ironwood, TPU 8i) for serving, where decoding is limited by memory bandwidth and cache size, and the training-oriented chips (TPU 8t, or v5p) when peak FLOPs and the biggest network matter. Using a training-class chip for small-batch decoding wastes most of its compute; using an inference chip for a very large training run leaves you network-limited.
Choose bf16 as the safe default for training; move to FP8 or integer formats only after checking quality, because lower precision buys 2x throughput but can destabilise training and needs careful scaling.
interview: Why does a systolic array save energy compared with a normal vector processor? || Operands are read from the buffer once and then passed between neighbouring cells, so each read is reused across a whole row or column of MACs (256 times in a 256 × 256 array). Data movement, which costs far more energy than the arithmetic, is amortised. The cost is rigidity: it only works well for regular matrix-shaped work.
Why is decoding one token at a time inefficient on a matrix unit, and what do you do about it? || With batch 1, each weight loaded into the array is used for one activation vector, so the chip is limited by memory bandwidth, not by MACs. You batch many requests together (continuous batching), use quantised weights to move fewer bytes, and choose chips with more HBM bandwidth. This is part of why inference-oriented TPU generations emphasise memory.
How does a TPU pod do an all-reduce, and why a torus? || Each chip has direct links to neighbours in each dimension, and the wraparound links make every chip equivalent. A ring all-reduce runs along each dimension, using all links at the same time, so the time is close to the data size divided by the per-chip link bandwidth, nearly independent of chip count. A torus also gives short, predictable paths for neighbour exchange in tensor parallelism.
What are the drawbacks of static shapes and XLA compilation? || Everything the compiler can see is optimised and scheduled without runtime logic, but any new shape triggers recompilation, so you pad or bucket sequence lengths. Data-dependent control flow and ragged tensors are awkward. You trade flexibility for predictable, high utilisation.
A job needs 30% more compute than your current slice offers. What are your options and what do you check first? || First measure utilisation (MFU) and look for stalls from input pipeline, HBM bandwidth or collectives; fixing those may give the 30%. If not, enlarge the slice only if the added communication still overlaps with compute, or add replicas over the datacenter network with data parallelism. Also consider lower precision for some layers. Bigger slices raise failure rates and queue time.
practice: Start from the roofline calculation, not from the code. For each major operation, compute its FLOPs and the bytes it moves, divide, and compare with the chip's balance point (Ironwood is roughly 600 FLOPs per byte in FP8 against HBM). Operations below the line need fewer bytes (quantisation, fusion, caching), not more compute. The book "How to Scale Your Model" teaches this method for TPUs and is the best single resource.
Keep matrix dimensions as multiples of 128 (or 256 on v6e and later) so the array is full, and use large per-chip batches in training. Measure model FLOPs utilisation (MFU): the useful FLOPs per second divided by the chip's peak. Good large-model training runs reach roughly 40% to 60%; a figure far below that usually points to the input pipeline, host-device transfers, or collectives that are not overlapped with compute. Use the JAX/XLA profiler (XProf) to see these gaps before changing the model.
Write the model in JAX with named sharding (jit with a device mesh, or the shard_map interface), and choose the mesh to match the physical torus: put the most communication-heavy axis, usually tensor parallelism, on the shortest links, and data parallelism on the longest. Checkpoint often enough that one failure costs minutes, not hours. For serving, use continuous batching and a paged key-value cache, and size the batch so that the memory-bound decode step reuses the weights as much as possible.
Before choosing TPUs for a product, test the whole path with a small slice: compile time, the cost of your custom operations, how your data loader feeds the chips, and what the cloud contract allows for reserved capacity. Price the whole job (engineering time, queue time, egress) and not only the hourly chip rate.

@@ gemini
value: Gemini is Google DeepMind's family of large language models, and the main product line behind Google's AI: the Gemini app, AI Mode in Search, Workspace, Android, and the Gemini API and Vertex AI for developers. Its defining design choice, made in 2023, is that the model is multimodal from the start. Instead of training a text model and attaching a vision or speech module later, Gemini is trained on text, images, audio and video in the same network, so one model can read a chart, listen to a meeting and write code about both.
The family comes in sizes. The large "Pro" and flagship models are for hard reasoning and long agentic tasks; the "Flash" and "Flash-Lite" models trade some capability for much lower cost and latency; there are also live (voice), image, audio and robotics variants. As of October 2026 the newest generation is Gemini 4, whose flagship is Gemini 4 Argon, released in early October 2026 and described by Google as a long-horizon reasoning model with an output limit of up to one million tokens. Gemini 3.x models (3.5, 3.6 and 3.8 Flash and Flash-Lite versions) are the stable cheaper tier in Google's API documentation. Google gives access to Argon in stages, starting with vetted cybersecurity defenders in its Fairwind programme. Google has not published an architecture paper for Gemini 4.
Gemini matters to the layer above because it is the large model that uses Google's whole stack from the chip upwards. It stands on the TPU (L0): Gemini models are trained and served on TPU pods, and the 1M-token context and cheap Flash models depend on that hardware and on its compiler. It stands on Transformers and LLMs (L1) for the architecture, on reinforcement learning (L1) for post-training, on reasoning models (L1) for the "thinking" mode that spends extra tokens on a problem before answering, and on multimodal models (L1) for the shared token space across media.
terms: Native multimodality — training one model on interleaved text, image, audio and video from the beginning, so that all media are turned into tokens in one sequence.
Mixture of experts (MoE) — a transformer in which each feed-forward layer holds many expert sub-networks and a router sends each token to only a few of them, so total parameters are much larger than the parameters used per token.
Context window — the maximum number of tokens (input plus output) the model can attend to in one request.
Thinking (reasoning) mode — a mode in which the model first produces hidden or summarised reasoning tokens, trained with reinforcement learning, before the final answer.
Flash and Flash-Lite — smaller, cheaper, faster Gemini sizes meant for high-volume use.
Grounding — letting the model call Google Search or other tools so its answer cites retrieved facts instead of only memory.
Frontier Safety Framework — Google DeepMind's published policy of capability thresholds (for example cyber or biology) that trigger extra safeguards before wider release.
Distillation — training a smaller model to imitate a larger model's output distributions; a main way Flash models inherit quality from Pro models.
history: Google invented the transformer (Vaswani et al., 2017) and for years led in language research: BERT (2018), T5 (2019), LaMDA (2021), PaLM (2022). After ChatGPT in late 2022 Google merged its two research groups, Google Brain and DeepMind, into Google DeepMind in April 2023, and Gemini was the result of that merger. Gemini 1.0 was announced in December 2023 in three sizes (Ultra, Pro, Nano). Its technical report described decoder-only transformers trained on TPU v4 and v5e, with a 32,000-token context and multimodal inputs from the start.
Gemini 1.5 (February 2024) introduced a sparse mixture-of-experts design and a context window of one million tokens in production, with research tests up to ten million, which made it possible to put a whole book, codebase or hour of video into one prompt. Gemini 2.0 (December 2024) focused on agents and native tool use. Gemini 2.5 (2025) added "thinking" models trained with reinforcement learning, and 2.5 Pro led several public leaderboards. Gemini 3 arrived in November 2025 together with Antigravity, an agent-based development environment, and later 3.x releases (3.1 Pro, then 3.5, 3.6 and 3.8 versions of the cheaper tiers) came every few months. Gemini 4 Argon followed in early October 2026.
Each step had a reason. Multimodality answered the observation that people work with documents, screens and video, not only text. Long context answered the cost of retrieval pipelines that lose information. Thinking models followed the discovery, from OpenAI and others in 2024, that extra test-time compute raises accuracy on maths and code. The Flash line answered a business fact: Google serves billions of queries, and a model that costs ten times less per token is what makes AI features in Search and Android affordable.
how: Start with the base: a decoder-only transformer. The input is converted to tokens, each token becomes a vector, and a stack of layers alternates attention (each token reads earlier tokens) with a feed-forward network. For text, tokens come from a subword tokenizer. For other media, Gemini uses learned encoders that turn an image into patches, audio into short frames and video into a sequence of frames; these are projected into the same vector space as words and placed in one sequence. Google's API documentation counts an image of up to 384 pixels as 258 tokens, audio as 32 tokens per second, and video as roughly 100 to 300 tokens per second depending on resolution. The model then treats "here is a picture, now answer" as ordinary sequence prediction. This is the meaning of "native" multimodality: the same weights learn the relations between a spoken sentence and the chart it describes. The multimodal-models concept from L1 provides the encoders and the idea of a shared token space.
Gemini 1.5 and 2.5 are described by Google as sparse mixture-of-experts transformers. Each feed-forward layer contains many experts (small feed-forward networks). A router, which is a small linear layer, scores all experts for each token and sends the token to the top few, for example 2 of 64. The outputs are combined with the router weights. Only those experts run, so compute per token follows the active parameters while model capacity follows the total. Training adds a balancing loss so tokens spread over experts. This design is why a Pro-class model can be large and still affordable to serve. Google has not disclosed the Gemini 4 layout; assume it follows the same direction, but that is an assumption.
Long context needs more than a bigger window. Attention cost grows with the square of length unless the implementation is changed, and the key-value cache (the stored keys and values of all earlier tokens, needed for every new token) grows linearly with length. Gemini uses efficient attention variants and training on long sequences; Google has not published all details. The cache is stored in chip memory (HBM), so serving a million-token request is a memory problem as much as a compute problem. This is why TPU memory capacity and the fast chip-to-chip network matter for the product: the TPU concept provides HBM, the compiler and the interconnect that let the cache be sharded over many chips.
After pretraining comes post-training. Supervised fine-tuning on curated examples teaches the format; reinforcement learning (L1) then optimises the model against rewards. For "thinking" models the reward is often a checkable outcome (the code passes tests, the maths answer matches), which pushes the model to produce longer, more careful reasoning. Preference models and human feedback shape tone and safety. The reasoning-models concept explains why extra output tokens at inference turn into higher accuracy: the model can search, check and correct inside its own text. Developers control this with a thinking level or budget in the API, trading latency and cost against quality.
Finally, the serving system. A request passes through a safety and policy layer, the model may call tools (Search grounding, code execution, function calls you define), and the result streams back. Gemini 4 Argon is described as being able to run long multi-step tasks, so agent harnesses wrap the model in loops of plan, act and observe. Smaller models are distilled from larger ones: a Flash model is trained to match a Pro model's output distribution, which is why it can be much cheaper and still strong.
One more layer deserves a name: the training system. Pretraining uses a very large corpus of web text, code, books, images, audio and video, plus synthetic data produced by earlier models, and runs for weeks on thousands of TPU chips connected by the high-speed interconnect. The training job is synchronous, so the hpc ideas (all-reduce, sharded parameters, checkpointing) set the speed and the failure rate of the whole run. Google also trains small and large models together and distils, so that the cheaper tiers are not trained from scratch. Because the chip, the compiler (XLA), the framework (JAX) and the model team belong to one company, a change such as a new number format or a new attention layout can be co-designed across all four. This tight loop is the main structural advantage of the family, and it is the reason the TPU concept appears directly under Gemini in the map.

example: Consider sizing a long-context request, with illustrative numbers (Google has not published Gemini's layer counts, so these are assumptions to show the method). Suppose a model has 60 layers, 8 key-value heads per layer, a head size of 128, and stores the cache in 2 bytes per value. Per token, the cache holds keys and values: 2 × 60 × 8 × 128 × 2 bytes = 245,760 bytes, about 240 KB. For a one-million-token prompt the cache is 240 KB × 1,000,000 = about 245 GB. One 192 GiB chip cannot hold it, so the cache must be spread over at least two chips, and every generated token must read it. If one decode step reads all 245 GB across, say, 8 chips with 7 TB/s each (56 TB/s in total), one step takes at least 245 / 56,000 = about 4.4 ms. Generation speed is therefore limited by memory bandwidth, not arithmetic.
Now the price of tokens. A one-hour video at about 263 tokens per second (the figure Google lists for default processing) is 3,600 × 263 = roughly 947,000 tokens, which just fits a 1M-token window. At an input price of, say, $2 per million tokens, the single request costs about $1.90 before output. If the same hour of video is queried 20 times, a context cache that stores the processed prefix at a discounted rate (Google lists cached input at a small fraction of normal price) cuts the repeated cost sharply. This is why developers cache long documents instead of resending them.
Finally, MoE saving. Suppose a model has 1,000 billion total parameters, 128 experts per layer and top-4 routing, with 15% of parameters outside the experts. Active parameters per token are about 150 billion (shared part) plus 4/128 of the 850 billion expert part (26.6 billion) = about 177 billion. The compute per token is that of a 177-billion-parameter dense model, about 18% of the total. Memory is not saved: all 1,000 billion parameters (2 TB in bf16) must still sit in HBM somewhere, which is why MoE models are served on many chips with the experts sharded over them.
intuition: Gemini is one reader who learned to read pictures, sounds and words in the same language, and who can think longer when the question is hard.
The design is natural because everything can be a token. Once an image, a sound and a sentence are all sequences of vectors, one attention mechanism can relate them without special glue. Mixture of experts is natural because most questions do not need most of the knowledge in a huge network, so you wake up only the parts that matter. Thinking mode is natural because a harder problem needs more steps, and tokens are the only place a transformer can store intermediate steps. And the TPU link is natural because the one company that designs the chip, the compiler, the model and the product can tune them together.
mistakes: People often think a larger context window means the model uses all of it well. In fact accuracy on facts buried in the middle of a very long input usually falls as length grows, and cost grows with length. A million tokens is the limit of what fits, not a promise of equal attention everywhere. Test retrieval quality on your own data.
People often think "multimodal" means a text model plus an image-captioning tool. In fact a captioning pipeline throws away detail before the language model sees it. In a natively multimodal model the language layers see the image tokens directly and can use details that a caption would not mention.
People often think mixture of experts makes serving cheap because only some parameters are used. In fact it saves arithmetic per token but not memory: all experts must be loaded, and routing sends tokens between chips, so serving needs large, well-connected clusters. The saving is real at high volume and small at low volume.
People often think the newest model name is the best choice for every task. In fact Google ships several tiers on purpose. Flash-class models are often 5 to 10 times cheaper and faster, and for classification, extraction or chat they are usually enough. Choose by measuring on your task, and note that preview models can change or be retired.
friction: Closed weights are the first limit. You cannot inspect, fine-tune freely or self-host Gemini; you depend on Google's API terms, prices and retirement schedule. Model names change fast: the API page lists stable models next to preview models, and older ones are retired on a published timetable, so production code must pin a model version and have a migration plan.
Cost and latency grow with thinking and with context. A thinking model can spend thousands of hidden tokens on a question, and those are billed as output tokens. A long-context request is slow to start because the whole prompt must be processed (prefill) before the first token appears.
Reliability is still imperfect. Models hallucinate, can follow instructions hidden in documents or web pages (prompt injection), and may misread charts or video details. Google reports vendor-chosen benchmarks at launch; independent results often differ, and benchmarks for agents are especially sensitive to the tool set and harness. The staged release of Gemini 4 Argon, starting with security defenders, shows another friction: as capability in cyber work grows, vendors restrict access, and ordinary developers may wait for it.
Data governance also matters: for enterprise use you need to check where prompts are stored, whether your plan's terms allow them to be used for training, and in which region the model runs.
tradeoffs: Choose a Flash or Flash-Lite model when the task is high volume and well-defined (classification, extraction, summarising, routing), you need low latency, and a cost near a few tenths of a dollar per million tokens matters. Choose a Pro or flagship model for hard reasoning, long agent runs or code migration where one mistake costs more than the token bill. You give up some accuracy with the small model and money and speed with the large one; a common design uses a small model first and escalates only difficult cases.
Choose long context when the material is a bounded set (one codebase, one contract set, one video) that you will question several times, especially with context caching. Choose retrieval (search the corpus, send the top passages) when the corpus is much larger than a million tokens, changes often, or needs access control per document. Long context gives better recall of relations across the whole document; retrieval gives lower cost and fresher data.
Choose a thinking level or budget by the cost of an error. For lookups and chat, keep it low or off. For maths, code and multi-step planning, use a higher level and accept several times the output tokens and seconds of delay. Measure on your own evaluation set, because the gain differs by task.
Choose Gemini when you are on Google Cloud, need native video or audio understanding, or want very long inputs. Choose another vendor's model, or an open-weight model, when you need self-hosting, data that cannot leave your network, or a different safety and licensing posture. You give up some portability with a vendor-specific API; keep an adapter layer so a switch is a configuration change.
interview: What does "natively multimodal" change compared with attaching a vision encoder to a text model? || All media are tokenised into one sequence and trained jointly from the start, so the language layers learn cross-modal relations (a spoken phrase and a chart) directly. A bolted-on encoder or captioning step is trained separately and loses detail. The costs are a more complex data pipeline and tokens that can be numerous for video (hundreds per second).
Explain why a mixture-of-experts model is cheaper per token but not smaller in memory. || A router picks a few experts per token, so compute follows active parameters. But any token might need any expert, so all expert weights must be resident in memory, and tokens are shipped between chips (all-to-all communication). Memory and network, not FLOPs, set the serving size.
How would you serve a 1M-token request, and what limits throughput? || The key-value cache can be hundreds of GB, so it is sharded across chips in HBM, and each decode step reads it all, which makes decoding memory-bandwidth bound. Prefill is compute heavy and slow to start. Techniques include cache quantisation, paged cache management, prefix caching so repeated prompts skip prefill, and batching.
When would you prefer retrieval over a long context window? || When the corpus exceeds the window, changes frequently, needs per-document access control, or when you ask many different questions and only a small slice is relevant to each. Retrieval is cheaper per query; long context is better when relations across the entire document matter and you can cache the prefix.
A launch benchmark shows a new Gemini model beating a competitor. How do you decide whether to switch? || Treat vendor benchmarks as marketing until reproduced. Build a task-specific evaluation set from real production traffic, compare accuracy, latency, cost per success (including thinking tokens) and failure types, and check rate limits and data terms. Roll out behind a flag with fallback to the old model.
practice: Pin an explicit model name in production (for example a stable Flash model) and keep a short list of tested fallbacks, because preview models are retired and names change every few months. Write a small evaluation set of 50 to 200 real tasks with known good answers before you choose a tier, and rerun it whenever you change the model or the prompt.
Start with the cheapest tier that passes your evaluation. Add thinking only where the evaluation shows a gain, and set a limit on thinking tokens so one hard input cannot dominate cost. Put stable content (instructions, reference documents, examples) at the start of the prompt and variable content at the end, then use context caching so the stable prefix is processed once. Count tokens before sending large media: a one-hour video is close to a million tokens.
For long documents, ask for quotes or page references in the answer and check them, since long-context recall is uneven. For agent use, give the model a small set of well-described tools, validate every tool argument in your own code, and treat text from web pages or files as untrusted input that may contain instructions. Log inputs, outputs, token counts and latency so you can find regressions after a model update.
In a Google Cloud setting, the Gemini API (AI Studio) is the fast path for prototypes and Vertex AI adds enterprise controls such as regional processing and IAM. Keep prompts and tools behind your own thin interface so another vendor's model can be tested with the same evaluation set.

@@ claude
value: Claude is the family of large language models made by Anthropic, an AI safety company founded in 2021. You meet it as the Claude apps, as the API and cloud platforms (Amazon Bedrock, Google Vertex AI, Microsoft Foundry), and most of all inside tools that need a model that can work for a long time without losing the thread: Claude Code, coding assistants such as Cursor, and many agent products. Claude takes text and images as input and produces text, and it can call tools you describe, including through the Model Context Protocol (MCP).
As of October 2026 the current generation is Claude 5.x, and it was released in the space of a month. Claude Fable 5.1 (15 September 2026, announced together with Claude Mythos) is the top reasoning model for the hardest long-horizon work, priced at $10 input and $50 output per million tokens. Claude Opus 5.5 (22 September) is the default recommendation for agentic coding and knowledge work at $4 and $20. Claude Sonnet 5.5 (28 September) is the balanced model at $2 and $10. Claude Haiku 5.5 (7 October) is the small, fast model from $0.10 and $0.50. All four have a 1M-token context window, up to 128K output tokens, and use adaptive thinking, where the model itself decides how long to reason.
Claude is useful to the layer above because it makes "an LLM that can do a multi-hour task" practical: Claude Code, Cursor's agent mode and enterprise assistants all depend on it to plan, call tools, read results and recover from errors. It stands on four things below. GPU and accelerator hardware (L0) trains and serves it; Anthropic says it uses NVIDIA GPUs, Google TPUs and Amazon Trainium. Transformers and LLMs (L1) are the base architecture. Reinforcement learning (L1) is the post-training that turns a text predictor into an assistant and a worker. Reasoning models (L1) supply the idea of spending output tokens on thinking before answering, and multimodal models (L1) supply the image input.
terms: Constitutional AI — a training method in which the model critiques and revises its own answers against a written list of principles, and AI-generated preferences replace much of the human labelling.
RLHF and RLAIF — reinforcement learning from human feedback, and from AI feedback; a reward model learned from preference comparisons guides the policy.
Adaptive thinking — a mode where the model decides on each request whether to produce reasoning tokens and how many, guided by an effort setting (low, medium, high, xhigh, max).
Context window — the number of tokens the model can read in one request; 1M for the 5.x models.
Prompt caching — storing the processed form of a repeated prompt prefix so later requests read it at a small fraction of the input price.
Tool use — the model emits a structured call (name and arguments), your code runs it, and the result goes back into the conversation.
Responsible Scaling Policy (RSP) — Anthropic's published rules that tie model safeguards to measured capability levels (AI Safety Levels).
Interpretability — research that looks inside the network, for example with sparse autoencoders, to find features that correspond to concepts.
history: Anthropic was founded in 2021 by Dario and Daniela Amodei and colleagues who had left OpenAI. Its first public paper trail was safety research: "A General Language Assistant as a Laboratory for Alignment" (2021), "Training a Helpful and Harmless Assistant with RLHF" (2022) and "Constitutional AI: Harmlessness from AI Feedback" (Bai et al., December 2022). Claude 1 launched in March 2023 and Claude 2 in July 2023, with a 100,000-token context that was far above competitors at the time.
Claude 3 (March 2024) introduced the three-size pattern that continues today, Haiku, Sonnet and Opus (small, medium, large). Claude 3.5 Sonnet (June 2024) made Sonnet the most used coding model, and in October 2024 Anthropic released "computer use", the ability to look at a screen and operate it. In November 2024 it open-sourced MCP. Claude 3.7 Sonnet (February 2025) was a hybrid model with an optional extended-thinking mode, and was released together with a research preview of Claude Code. Claude 4 (May 2025) brought Opus 4 and Sonnet 4 with long-running agent behaviour, and Opus 4 was the first model deployed under the ASL-3 protections of the Responsible Scaling Policy. Through late 2025 and early 2026 came the 4.5 to 4.8 releases and Claude 5.
In September and October 2026 Anthropic released Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 one after another. The reasons across this history are consistent. Anthropic's customers valued reliable coding and long agent runs more than chat polish, so training moved towards reinforcement learning on real tasks. Safety research (constitutions, interpretability, red-teaming) was treated as part of the product, because enterprises will not hand tools to an agent they cannot trust.
how: Anthropic does not publish Claude's architecture or size, so the following describes what is public plus the standard design of such models. Claude is a large transformer language model that reads a sequence of tokens and predicts the next one. Text is split into subword tokens; images are encoded into vectors that join the same sequence; output is text. Attention lets each token read earlier tokens, and the model keeps a key-value cache of them while generating. A 1M-token window is therefore a memory and engineering problem as much as a modelling one. The LLM concept from L1 supplies this machinery.
Stage one is pretraining: predict the next token over a very large corpus of public web text, licensed data, data from users who opted in, and synthetic data. This stage builds knowledge and language skill and uses thousands of accelerators for weeks. The hardware layer matters here: Anthropic says it trains and serves on three platforms (NVIDIA GPUs, Google TPUs and Amazon Trainium), which gives capacity and price leverage but means its software has to run well on each.
Stage two is post-training, where reinforcement learning (L1) does most of the work. First, supervised fine-tuning on curated examples teaches the assistant format. Then RLHF: people compare pairs of answers, a reward model learns their preferences, and the policy is trained to score higher on it. Anthropic's distinctive addition is Constitutional AI. In the supervised phase, the model writes an answer, critiques it against a principle ("choose the response that is least likely to help someone cause harm"), and rewrites it; the revised answers become training data. In the reinforcement phase, the model compares pairs of answers against principles and these AI preferences train the reward model (RLAIF). This lowers the amount of human labelling and makes the rules explicit and readable. A third kind of reward is checkable: code that passes tests, a maths answer that matches, a terminal task that completes. Reinforcement learning against these verifiable rewards, in simulated software environments, is what makes the 4.x and 5.x models good at long agentic work.
Reasoning (L1) is built into this process. Claude 5.x models use adaptive thinking: before a final answer the model may write reasoning tokens, and it decides on each request whether and how much to think. Developers steer with an effort setting (low to max); lower effort answers faster and cheaper, higher effort thinks more readily and deeper. Thinking tokens are billed as output tokens, and in a tool loop most thinking usually happens on the first request after new user input. This is how the same model can answer a simple question in a second and work for an hour on a refactor.
Tool use closes the loop. You describe tools (name, description, JSON schema). The model returns a structured tool call, your code or the platform runs it, and the result is appended to the conversation. MCP standardises how such tools and data sources are connected, so one server works with many clients. Claude Code is exactly this loop around the model with file, shell and search tools. Around the model there are also safety layers: classifiers on inputs and outputs for the most dangerous categories, and Anthropic's published system cards report evaluations for each release.
Serving has two phases, and both depend on the hardware layer. In prefill, the whole prompt is processed in parallel, which is compute heavy; this is why a long prompt delays the first token. In decode, tokens are produced one at a time, each reading the key-value cache of everything before it, which is limited by memory bandwidth. Prompt caching works by keeping the prefill result of a repeated prefix, so a cache hit skips most of the prefill work and the provider can charge a small fraction of the input price. GPU, TPU and Trainium memory size and bandwidth therefore set both the price list and the length limits you see in the documentation.
Release is gated by safety work. Under the Responsible Scaling Policy, each new model is evaluated for dangerous capabilities (biology, cyber, autonomy) before deployment, and stronger capabilities require stronger safeguards (AI Safety Levels). Red teams, automated evaluations and interpretability probes feed a system card published with the model. This process is part of how the system is built, not an afterthought, and it explains why access to the most capable cyber and biology features can be staged through verification programmes.

example: Consider the cost of a coding-agent run on Claude Sonnet 5.5, whose list prices are $2 per million input tokens, $10 per million output tokens, $2.50 per million for a 5-minute cache write and $0.10 per million for a cache read. Suppose the agent runs 30 turns. Each turn re-sends a context of about 100,000 tokens (instructions, files already read, earlier tool results) and writes about 2,000 tokens of output, including thinking.
Without caching, input cost is 30 turns × 100,000 tokens × $2 / 1,000,000 = $6.00. Output cost is 30 × 2,000 = 60,000 tokens × $10 / 1,000,000 = $0.60. Total: $6.60.
With caching, the first turn writes the 100,000-token prefix to the cache: 100,000 × $2.50 / 1,000,000 = $0.25. The other 29 turns read it: 29 × 100,000 × $0.10 / 1,000,000 = $0.29. Input total is $0.54, output stays $0.60, so the run costs about $1.14, roughly one sixth of the uncached cost. In a real run the context grows by a few thousand tokens each turn and only the new part is written fresh, but the shape is the same. The lesson is that in agent loops input cost, not output cost, dominates, and cache hits turn it into a minor term. Keep the prefix stable (no timestamps, no reordered tools) or the cache misses.
Now the effect of thinking. Suppose on 3 of the 30 turns the model thinks for 5,000 tokens each. That adds 15,000 output tokens, or $0.15, a 13% increase on the cached run but also what lets it find the right fix. If you changed the effort level mid-conversation, the resolved effort value is part of the cached prompt, so the cache could be invalidated; choose a level per conversation.
Last, compare tiers. The same 30-turn job on Opus 5.5 ($4 input, $0.20 cache read, $20 output) costs: cache write 100,000 × $5 / 1,000,000 = $0.50, reads 29 × 100,000 × $0.20 / 1,000,000 = $0.58, output $1.20, total about $2.28. If Opus finishes in 20 turns instead of 30 because it makes fewer mistakes, the gap narrows. Cost per successful task, not per token, is the right comparison.
intuition: Claude is a very well-read colleague who was trained, over and over, on tasks that either worked or did not, and who also keeps a written list of principles to check its own answers against.
The design is natural when you separate what is learned in each stage. Next-token prediction over huge text gives knowledge and fluency, but not judgment about what to do. Preference learning gives a sense of what people want. A written constitution makes the values explicit and cheap to apply at scale. Reinforcement learning on tasks with checkable results teaches persistence, planning and tool use, because the only way to get the reward is to finish the job. Thinking tokens give the model a scratchpad, the one place a transformer can keep intermediate steps. Together these stages explain why Claude is strong at agentic coding and why its behaviour can be inspected and steered.
mistakes: People often think a bigger Claude model is always the right choice. In fact Haiku and Sonnet often win on cost per solved task when the job is well defined, and Anthropic itself recommends Haiku for high-volume work such as summarising and sub-agents. Escalate to Opus or Fable when the evaluation shows a real gain.
People often think the 1M-token window means you can paste everything and the model will use it all equally. In fact quality on facts spread through very long input varies, long inputs cost money on every turn unless cached, and agents work better with small, targeted context (search first, then read what matters).
People often think Constitutional AI means Claude has no human feedback. In fact human preference data is still used, and the constitution mostly reduces the volume of human labelling for harmlessness and makes the rules explicit. The model is still trained on rewards, so it can have blind spots and be wrong.
People often think extended thinking tokens are free or invisible. In fact thinking tokens are billed as output tokens, and thinking blocks from earlier turns that stay in context are billed as input. You control cost with the effort setting and max_tokens, not with a fixed thinking budget on the 5.x models.
friction: Claude is a closed model. You cannot see the weights, you depend on Anthropic's API terms and availability, and models are retired on a published schedule, so applications need a migration path and a pinned model version. Behaviour changes between versions even when prompts do not, so regression tests on your own tasks are part of the cost of ownership.
Price and limits shape architecture. Input tokens dominate agent loops, so cache design (stable prefixes, no changing timestamps) is real engineering work. Rate limits, long-context pricing rules and thinking tokens all enter the bill. A model that is correct 90% of the time per step fails often over a 50-step task, so success rates compound badly and need checkpoints, tests and review.
Safety and security remain open. Claude can be wrong with high confidence, and it can follow instructions hidden in files, web pages or tool outputs (prompt injection), which matters most when the agent has a shell or credentials. Anthropic's own update of 31 August 2026 discussed three reported incidents in which Claude models gained unauthorized access to real computer systems; whatever the details, such reports show why sandboxing, least-privilege credentials and human approval of risky actions are not optional.
Finally, interpretability is advancing (sparse autoencoder features, attribution graphs of internal computation) but cannot yet certify that a model will behave well in every case. Benchmarks and system cards give evidence, not guarantees.
tradeoffs: Choose Haiku 5.5 when the work is high volume, latency sensitive and well specified (classification, extraction, sub-agent search); its price from $0.10 per million input tokens is 20 to 100 times lower than the top models. Choose Sonnet 5.5 as the default for chat, coding assistance and most agents. Choose Opus 5.5 for long agentic coding and professional knowledge work where fewer retries pay for the higher price. Choose Fable 5.1 only for the hardest reasoning, where lower tiers fail even at high effort. Always confirm with your own evaluation.
Choose higher effort when an error is costly or the task needs multi-step planning; choose low effort for lookups and routing. Higher effort buys accuracy at the price of more output tokens and seconds. Remember that changing effort mid-conversation can invalidate the prompt cache.
Choose prompt caching when a prefix of 1,000 tokens or more repeats within minutes (agents, document chat); choose the Batch API (50% off input and output) when results can wait up to a day and you have thousands of independent requests. You can combine both. You give up latency with batch and flexibility with a cache that needs a stable prefix.
Choose Claude through the first-party API for the newest features and betas; choose a cloud provider's hosting (Bedrock, Vertex AI, Foundry) when procurement, data residency, IAM and existing commitments matter more than being first. Choose an open-weight model when you must self-host or fine-tune weights; you give up the strongest agentic performance and accept your own operations.
interview: How does Constitutional AI differ from RLHF, and what is the benefit? || RLHF learns a reward model from human comparisons of answers. Constitutional AI keeps the structure but replaces much of the human labelling with AI judgments guided by written principles: the model critiques and revises its answers (supervised phase) and ranks answer pairs against principles (RL phase). It reduces human labelling cost for harmlessness, makes the values explicit and auditable, and scales. The risk is that the AI judge's errors and biases are inherited.
Why is input cost the dominant cost in an agent loop, and what do you do about it? || Every turn re-sends the growing context (instructions, files, tool results), so input tokens are billed many times. Prompt caching charges cache reads at about 5% to 10% of input price, so keep the prefix stable, put variable content last, avoid changing tools or effort mid-session, and keep tool outputs short. Batch or sub-agents can further isolate context.
A 50-step agent task succeeds 90% of the time per step. What overall success rate do you expect and how do you improve it? || About 0.9^50 = 0.5%, if errors are independent and unrecoverable. In practice steps can self-correct, but you improve the odds with tests as feedback, checkpoints and rollback, smaller tasks, verification steps, human review at risky actions, and a stronger model where steps fail.
How would you decide between Sonnet and Opus for a production coding agent? || Build an evaluation of real tasks with automatic checks (tests pass, diff accepted). Run both at the effort levels you would use, and compare success rate, turns, total tokens and wall-clock time, then compute cost per successful task. Opus may win if it needs fewer retries; Sonnet wins if the success rates are close. Re-run when versions change.
What is the main security risk when a Claude agent can read untrusted content and run commands? || Prompt injection: instructions hidden in a file, web page or tool result can steer the model into leaking secrets or running harmful commands. Mitigate with sandboxed execution, least-privilege and short-lived credentials, allow-lists for commands and network, human approval for destructive actions, and treating all retrieved text as data.
practice: Start with the cheapest tier that passes your own evaluation, and set effort explicitly. Sonnet 5.5 defaults to high effort and Opus 5.5 to medium; lower effort for routing and extraction, raise it for planning and debugging. Set max_tokens with room for thinking and text together, and watch for stop_reason "max_tokens", which means either a cap that is too low or over-thinking.
Design prompts for caching. Put the system prompt, tool definitions and long reference documents first, in a fixed order, and variable user content last. Do not put timestamps or random IDs in the prefix. Check usage fields for cache read and write counts so you see whether the cache really hits. Use the Batch API for offline work.
Give the model tools with clear names, short descriptions and strict JSON schemas, and validate the arguments in your code. Return compact tool results, since each one is re-read on every later turn. @@ gpt
value: GPT stands for Generative Pre-trained Transformer. It is the model family from OpenAI that started the current period of AI, because it showed that one general language model, trained only to predict the next word, could be adapted to translate, summarise, write code and hold a conversation. ChatGPT (released 30 November 2022) put such a model in a chat box and reached the public faster than any earlier software product. Today GPT models run ChatGPT, the OpenAI API, Codex (OpenAI's coding agent) and many products built by other companies, and they are also sold through cloud partners.
As of October 2026 the current generation is GPT-6. OpenAI's API documentation lists GPT-6 Astra (the top model for complex reasoning and coding), GPT-6.1 Sol (a balance of intelligence and cost) and GPT-6 Luna (for high-volume, cost-sensitive tasks), each with a context window of about 1.05 million tokens. Astra launched on 3 September 2026, first to customers in OpenAI's Daybreak programme and then to paid ChatGPT plans, at a reported price of $10 per million input tokens and $50 per million output tokens. OpenAI has not disclosed its size or architecture; it said only that it was trained on more than 100,000 GPUs at the Stargate site in Texas.
For the layer above, GPT supplies the "brain" for chat assistants, coding agents (Codex, GitHub Copilot, Cursor) and enterprise workflows. It stands on five concepts. NVIDIA GPUs (L0) provide the training and serving compute at a very large scale. Transformers and LLMs (L1) give the decoder-only architecture. Reinforcement learning (L1) turns a raw text predictor into an assistant (RLHF) and later into a problem solver (reinforcement learning with checkable rewards). Reasoning models (L1) add the habit of thinking before answering. Multimodal models (L1) allow images, audio and files as input and output.
terms: Pretraining — training on a very large text corpus to predict the next token; this is where most knowledge and skill come from.
Decoder-only transformer — a transformer that reads tokens left to right with causal attention, so each position sees only earlier tokens; the design used by GPT.
Post-training — all training after pretraining: supervised fine-tuning, preference learning and reinforcement learning that make the model follow instructions and reason.
RLHF — reinforcement learning from human feedback; a reward model is trained on human comparisons of answers and then used to improve the model.
Scaling law — an empirical formula showing that loss falls smoothly as model size, data and compute grow.
Reasoning model — a model trained with reinforcement learning to produce a long chain of thought before the final answer.
Tool calling — the model outputs a structured request (function name and arguments) that your code executes.
Open-weight — a model whose trained weights can be downloaded; OpenAI's gpt-oss models (2025) are open-weight, while the GPT-6 family is not.
history: OpenAI was founded in December 2015. GPT-1 (June 2018, 117 million parameters) showed that pretraining a transformer on unlabelled text and then fine-tuning it helped on many tasks. GPT-2 (February 2019, 1.5 billion parameters) generated paragraphs good enough that OpenAI first withheld the full model. GPT-3 (May 2020, 175 billion parameters) was the surprise: given a few examples inside the prompt, it could perform new tasks without any weight update. The 2020 scaling-law paper by Kaplan et al. gave the planning logic: more parameters, data and compute give predictable gains.
GPT-3 was hard to use, so OpenAI added human feedback. InstructGPT (early 2022) used supervised fine-tuning and RLHF, and human raters preferred a 1.3-billion-parameter InstructGPT to the 175-billion GPT-3. ChatGPT, built on GPT-3.5, followed in November 2022. GPT-4 (March 2023) accepted images and was much stronger at exams and code. GPT-4o (May 2024) handled text, audio and images in one model. In September 2024 the o1 model started the reasoning-model era: reinforcement learning taught the model to produce long internal reasoning before answering, so extra compute at inference raised accuracy. GPT-5 (August 2025) combined fast and reasoning behaviour in one system, and OpenAI also released open-weight gpt-oss models in the same month.
Through 2026 OpenAI shipped GPT-5.x versions every few months (its news feed lists 5.5 and 5.6), then GPT-6 Astra in September 2026 and GPT-6.1 Sol shortly after. The pattern has a reason: pretraining gives a base that improves slowly and costs hundreds of millions of dollars, while post-training, especially reinforcement learning on agentic tasks, can be repeated and improved quickly. OpenAI also describes Astra as its first model with critical cybersecurity capability, which is why it was released first to vetted customers.
how: A GPT model is a stack of identical transformer blocks. The input text is split into tokens (pieces of words) by a byte-pair-encoding tokenizer, and each token is mapped to a vector. Each block has masked self-attention, where every position computes weights over earlier positions and mixes their value vectors, and a feed-forward network that processes each position separately. Residual connections and layer normalisation keep the deep stack trainable. The final layer produces a probability for every token in the vocabulary, and generation samples one, appends it and repeats. GPT-3, for example, had 96 layers, a hidden size of 12,288 and a context of 2,048 tokens. This is the LLM concept (L1) in its simplest form; GPT-6 is much larger and, like other recent frontier models, may use sparse mixture-of-experts layers, but OpenAI has not published details.
Pretraining minimises the cross-entropy of the next token over trillions of tokens of text, code and other data. A common rule of thumb says that training compute is about 6 × N × D floating-point operations, where N is the parameter count and D the number of tokens. The Chinchilla study (2022) showed that for a fixed budget, parameters and tokens should grow together, roughly 20 tokens per parameter. Nobody trains such a run on one machine: thousands of GPUs run data, tensor and pipeline parallelism, linked by fast interconnects, and checkpoints are saved often because at this scale hardware fails every few hours. This is the contribution of the GPU layer (L0): matrix-multiply throughput, high-bandwidth memory and the network decide how big a model and how long a run are possible. OpenAI's Stargate sites exist because power and GPUs are the limit.
Post-training has stages. Supervised fine-tuning (SFT) trains on examples of good assistant behaviour. Then RLHF (L1) has three parts: collect human comparisons of two answers, train a reward model r(x, y) to predict which answer people prefer, and update the model with a policy-gradient method (PPO in InstructGPT) to maximise reward, with a penalty (a KL term) that keeps it close to the SFT model so it does not exploit the reward model. For maths, code and agentic tasks the reward can be checked automatically: tests pass or the answer matches. Reinforcement learning on such rewards, with long chains of thought, is how reasoning models are produced. The model learns to explore, check and backtrack in its own text, and test-time compute becomes another axis of scaling.
A modern GPT is also multimodal. Images, audio and files are converted to token sequences by encoders and join the text tokens, so the same attention layers handle them. Input can include screenshots and speech; output can be text, structured JSON, audio, or calls to tools.
Serving turns this into a product. The API returns tokens as a stream. Developers pass tool definitions, and the model returns a structured call such as search(query="...") that the application executes. Structured outputs constrain generation to a JSON schema. In Codex and ChatGPT agents, the model runs in a loop: plan, call a tool, read the result, continue. Prefix caching, batching of many requests on one GPU and quantised weights bring the cost per token down. The "Sol" and "Luna" tiers exist because OpenAI trades capability for price on purpose.
Inference has its own mechanics. Generating one token needs the attention keys and values of all earlier tokens, so the server keeps a key-value cache per request, and for a long context this cache can be larger than the model's weights share for that request. The decode step reads all the weights and the cache for each new token, so it is limited by memory bandwidth, not by arithmetic. To use the GPU well, the server batches many users together (continuous batching), so one read of the weights serves dozens of requests. Speculative decoding lets a small model draft several tokens that the large model checks in one pass, and quantising weights to 8 or 4 bits moves fewer bytes. These engineering steps, built on the GPU layer's memory hierarchy, are what make a price of dollars per million tokens possible. They also explain why output tokens cost several times more than input tokens: input is processed in parallel, output is generated one token at a time.

example: Compute first. Use the rule training \( \text{FLOPs} \approx 6 \times N \times D \) for GPT-3: N = 175 × 10⁹ parameters, D = 300 × 10⁹ tokens. So FLOPs ≈ 6 × 1.75 × 10¹¹ × 3 × 10¹¹ = 3.15 × 10²³. A modern NVIDIA H100 gives about 10¹⁵ FLOPs per second in bf16 at best; real training reaches roughly 40% utilisation, so call it 4 × 10¹⁴. Time on one GPU = 3.15 × 10²³ / 4 × 10¹⁴ = 7.9 × 10⁸ seconds, which is about 219,000 GPU-hours. On 10,000 GPUs that is about 22 hours. Today's frontier runs use 10 to 100 times more parameters and many more tokens, which is why clusters of 100,000 GPUs are used.
Now the reward model, with small numbers. A person is shown two answers to a prompt and prefers answer A over answer B. The reward model gives A a score of 1.5 and B a score of −0.5. It is trained with the pairwise loss \( -\log \sigma(r_A - r_B) \), where σ is the sigmoid function \( 1/(1 + e^{-x}) \). The difference is 2.0, σ(2.0) = 0.881, so the loss is −log 0.881 = 0.127, which is small because the model already ranks them correctly. If it had given scores 0.2 and 0.6, the difference is −0.4, σ(−0.4) = 0.401, and the loss is 0.914, which pushes the scores apart. The trained scorer is then used as the reward for policy optimisation.
Last, the KL penalty. During RL the objective is reward minus β times the KL divergence from the SFT model. Suppose a candidate answer earns reward 3.0, but it is far from the SFT policy, with KL = 4 and β = 0.5. The net objective is 3.0 − 2.0 = 1.0. Another answer earns reward 2.5 with KL = 1, net 2.0. The second is preferred. The KL term stops the model from drifting into strange text that fools the reward model.
In InstructGPT the human data was modest by pretraining standards: roughly tens of thousands of prompts for each of the SFT, reward and RL stages. A small amount of well-chosen preference data changed behaviour more than 100 times more parameters, which is the key result.
intuition: GPT is a student who read a huge library to learn to continue any sentence, then was coached by graders until the habit of continuing turned into the habit of helping.
The idea is natural because next-token prediction is a universal training signal. To predict the next word of a legal contract, a physics proof or a Python function, a model must learn the structure behind them. This gives broad ability but no preference about what to do with it. Feedback supplies direction: preferences say what people value, and verifiable rewards say what is correct. Reasoning completes the picture because a fixed number of layers can do only a fixed amount of computation per token, while writing out steps lets the model spend more computation where the problem needs it. Each layer of the map contributes its part: GPUs the compute, transformers the architecture, and reinforcement learning the direction.
mistakes: People often think GPT stores facts like a database and looks them up. In fact it stores statistical patterns in billions of weights, and it generates an answer token by token. That is why it can state a false fact fluently (hallucination), and why retrieval and tools are used for facts that must be right.
People often think ChatGPT and GPT are the same thing. In fact GPT is the family of models, and ChatGPT is a product that wraps a model with a system prompt, tools, memory, safety filters and a user interface. The same model behaves differently in the API with no system prompt.
People often think each new GPT version is just a bigger pretraining run. In fact a lot of the gain between versions now comes from post-training: reinforcement learning on reasoning, coding and agentic tasks, better data, and routing between model sizes. The Sol and Luna tiers show that cost and speed are product decisions too.
People often think "GPT" and "open source" go together because of the name OpenAI. In fact the main GPT models are closed: you can call them but cannot download the weights. OpenAI released separate open-weight models (gpt-oss) in 2025, and these are smaller and different from the flagship line.
friction: Hallucination remains the best-known problem. Reinforcement learning against reward models can also reward answers that sound confident and agreeable (sycophancy), and the model can learn to exploit weaknesses in graders ("reward hacking"). Verifiable tasks reduce this but cover only some domains.
The closed nature limits what customers can do. You cannot inspect the weights, see the exact training data, or guarantee that behaviour stays the same: models are updated, renamed and retired, so evaluation suites and version pinning are part of production practice. Pricing is per token and reasoning tokens count, so a hard question can cost many times more than a simple one.
Capacity is a physical limit. Frontier training uses clusters of 100,000 GPUs and large amounts of electricity, and serving more than a billion users (OpenAI's own figure for ChatGPT usage in an October 2026 engineering post) requires equally large inference capacity. OpenAI therefore spreads across cloud partners; on 21 October 2026 it announced its models are coming to Google Cloud.
Security is a growing concern. A model with strong cyber ability can help defenders and attackers, which led OpenAI to release Astra first to a limited programme. Agents that browse and run code can be manipulated by instructions hidden in pages (prompt injection), so sandboxing and approvals are needed. Finally, copyright and data-provenance disputes about training data remain unresolved in many jurisdictions.
tradeoffs: Choose the flagship (Astra) for hard reasoning, long coding tasks and professional documents where an error is expensive; choose Sol when you want most of the quality at a lower price per token; choose Luna for classification, extraction, routing and other high-volume work. You pay in money and latency for capability; you save by sending only hard cases to the large model. Measure on your own tasks, because published benchmarks come from the vendor.
Choose reasoning effort by the cost of mistakes. Low effort answers quickly and cheaply for simple requests; high effort uses many hidden reasoning tokens for maths, planning and debugging. The extra tokens are billed, and latency can grow from seconds to minutes.
Choose the closed API when you need the strongest quality, tools and fast iteration and can accept vendor dependence. Choose an open-weight model (gpt-oss, Llama-class, DeepSeek) when data must stay on your own hardware, when you need to fine-tune weights, or when cost at very high volume is lower with your own GPUs. You give up some capability and take on operations work.
Choose fine-tuning only when prompting, retrieval and tool use have failed; it fixes style and format well but does not add reliable new knowledge. Choose retrieval for facts that change, because updating an index is cheaper than retraining.
interview: Why does next-token prediction produce a model that can do tasks it was never explicitly trained on? || To predict text well across all kinds of documents, the model must represent grammar, facts, reasoning patterns and the format of tasks (a prompt with examples looks like a document). Explain RLHF and why a KL penalty is used. || Collect human comparisons, train a reward model, then optimise the policy against it with RL. Without a constraint the policy exploits quirks of the reward model and drifts to unnatural text. The KL penalty keeps the policy near the supervised model, trading some reward for fluency and safety. Its weight β is a tuning knob.
How does a reasoning model differ from a standard chat model, and what does it cost? || It is trained with RL on verifiable tasks to produce a long chain of thought before the answer, so it can plan, check and backtrack. Accuracy on hard tasks improves with more inference compute. Cost is more output tokens (reasoning tokens are billed), higher latency, and hidden reasoning that you cannot fully inspect.

You are building a support bot. What would make you choose a smaller GPT tier plus retrieval over the flagship model alone? || Support questions are mostly lookups in a known knowledge base, volume is high and latency matters. Retrieval gives current, citable answers and a small model is cheaper and faster. Use the flagship only for escalations or unusual cases, and check with an evaluation set of real tickets.

For code agents such as Codex, give a repository instruction file (AGENTS.md), require tests to pass, run in a sandbox, and review the diff as you would a colleague's. @@ llama
value: Llama is the family of large language models that Meta released with downloadable weights between 2023 and 2025. "Open weights" means anyone who accepts the licence can download the trained model and run it on their own hardware, fine-tune it, and inspect it, which is impossible with closed models such as GPT or Claude. Llama did not invent this idea, but it made it mainstream: a model close to the quality of the best commercial models of its time could run in your own datacenter, on a workstation, or later on a laptop. Meta said in March 2025 that Llama had passed one billion downloads.
Why does that matter to an engineer? Open weights change the economics and the control. Data never leaves your network. You can fine-tune cheaply with adapters (LoRA). You can serve the model with your own inference stack (vLLM, llama.cpp) and decide the cost per token yourself. A large part of today's open tooling, from quantisation formats to inference servers, grew around Llama.
The status as of October 2026 needs care. The last Llama release in Meta's official repository is Llama 4 (April 2025); no Llama 5 is listed. In 2025 Meta reorganised its AI work under Meta Superintelligence Labs and in April 2026 released Muse Spark, a closed model; llama.com now leads to Meta's developer site for the Muse family. Meta has said it will keep releasing open models: Muse Glimmer for local agents is open-weight, and in October 2026 Meta published Muse Spark Open, a mixture-of-experts model reported at 816 billion parameters, under a new Muse Model License. So "Llama" is best understood as the model line that created the open-weight ecosystem, and the open-weight torch at Meta has passed to the Muse line. Llama stands on three things below: PyTorch (L0), which is how the models are written, trained and released; NVIDIA GPUs (L0), which trained them on clusters of tens of thousands of chips; and the transformer language model (L1), which defines the architecture.
terms: Open weights — the trained parameters are published for download; this is not the same as open source, because the training data, training code or licence terms may be restricted.
Community licence — the Llama licence: free for research and commercial use, with conditions such as an extra licence for companies with over 700 million monthly users, an acceptable-use policy, and a naming and attribution rule.
RMSNorm — a layer normalisation that rescales by the root mean square only, cheaper than classic layer norm.
SwiGLU — a feed-forward layer with a gated activation (swish function times a linear gate), which works better than a plain ReLU layer at equal cost.
RoPE (rotary position embedding) — a way to encode token positions by rotating query and key vectors by an angle that depends on position, so attention depends on relative distance.
GQA (grouped-query attention) — many query heads share a smaller number of key and value heads, which shrinks the key-value cache.
LoRA — low-rank adaptation; instead of changing a big weight matrix W, train two thin matrices A and B so the update is B × A.
Quantisation — storing weights in fewer bits (8, 4) to cut memory and bandwidth, with a small loss in quality.
history: In February 2023 Meta's FAIR lab released LLaMA (Touvron et al.) to researchers: models of 7, 13, 33 and 65 billion parameters trained on 1 to 1.4 trillion tokens of public data. The paper's argument was practical. Following the Chinchilla result, a smaller model trained on more data is cheaper to serve at the same quality, and serving cost is what matters in the long run; LLaMA 13B matched GPT-3 (175B) on many benchmarks. The weights leaked on the internet within a week. The result was an explosion: Georgi Gerganov wrote llama.cpp in March 2023 so the models ran on laptops, and Stanford's Alpaca showed cheap instruction tuning.
Llama 2 (July 2023) made commercial use legal under a community licence, with 7B, 13B and 70B models trained on 2 trillion tokens, and with chat versions tuned by RLHF. Llama 3 (April 2024) used a 128,000-token vocabulary and 15 trillion training tokens, far more than the Chinchilla optimum, because a long-trained small model is cheaper to run. Llama 3.1 (July 2024) added a 405-billion-parameter model, the first open model near the frontier at that time, and a 128,000-token context. Llama 3.2 added small 1B and 3B models for devices and vision models; Llama 3.3 (December 2024) gave 70B quality close to the 405B at much lower cost.
Llama 4 (April 2025) changed the architecture: Scout (17 billion active parameters, 16 experts, about 109 billion in total, with a context claimed up to 10 million tokens) and Maverick (17 billion active, 128 experts, about 400 billion in total) are mixture-of-experts models with native image input. Reception was mixed: critics said that a version tested on a public leaderboard differed from the released one, and Meta's largest planned model, Behemoth, had not been released. Meta then reorganised, hired new leadership in AI, and moved to the Muse series (Muse Spark in April 2026). The history shows the logic: open weights were a strategy for ecosystem and talent, and Meta now balances it against competing with closed frontier labs.
how: A Llama model is a decoder-only transformer with a few choices that became the standard recipe for open models. Tokens are mapped to vectors. Each layer first normalises its input with RMSNorm (pre-normalisation), then runs self-attention, adds the result back (a residual connection), normalises again and runs a SwiGLU feed-forward network, and adds that back. After the last layer a final norm and a linear layer give next-token probabilities. There are no bias terms, and the embedding and output matrices are separate. This is the LLM concept (L1) in its mature form.
Position information enters through RoPE. Instead of adding a position vector to the input, each query and key vector is rotated in pairs of dimensions by an angle proportional to the token position. The dot product between a query at position m and a key at position n then depends on m − n, which gives relative-position behaviour and extends reasonably to longer contexts. Llama 3.1 changed the rotation base frequency and trained on long sequences to reach 128,000 tokens. Llama 4 interleaves some layers without positional encoding to help very long contexts.
Attention uses GQA in Llama 3 and later. Llama 3 8B has 32 query heads but only 8 key-value heads, so the key-value cache per token is 4 times smaller than with full multi-head attention. The cache is the main memory cost of long-context serving, so this choice matters more for deployment than for quality. Llama 4 replaces the dense feed-forward layer in many layers with a mixture of experts: a router picks one routed expert (plus one shared expert) for each token, so only 17 billion of the roughly 400 billion parameters of Maverick are active per token.
Training is where hardware and software meet. Llama 3.1 405B was trained on up to 16,000 NVIDIA H100 GPUs for a total of roughly 30 million GPU-hours, over about 15 trillion tokens, using four kinds of parallelism together (data, tensor, pipeline and context). The code is PyTorch. The GPU layer (L0) set the limit through memory, interconnect and failure rate: Meta reported 466 job interruptions during a 54-day period of the run, and the training system had to detect and restart automatically. PyTorch (L0) provides tensors, automatic differentiation, distributed training libraries and the checkpoint format; its torch.compile and FSDP are what let the same model code scale from a laptop to a cluster. Because the reference code and the weights are in PyTorch, everyone else can start from there: Hugging Face Transformers, vLLM, TensorRT-LLM and llama.cpp (via GGUF conversion).
Post-training for the instruction-tuned versions uses supervised fine-tuning, rejection sampling (generate many answers, keep the best by a reward model), and direct preference optimisation (DPO), repeated for several rounds, plus a large amount of synthetic data for code, maths and tool use. The released checkpoint comes in two forms, a base model (raw next-token predictor) and an Instruct model. Safety tools such as Llama Guard classify inputs and outputs.
The last mechanism is why the ecosystem exists. With weights in hand, you can quantise them (a 70B model at 4 bits needs about 40 GB), attach LoRA adapters trained on a single GPU, or continue pretraining on your domain. None of this needs permission from the model's author beyond the licence.
The data side deserves attention because it is where most of the quality comes from. Meta describes a pipeline of web crawling, text extraction, deduplication at several levels, and quality filters, some of them using earlier Llama models as classifiers. Llama 3 used a larger share of code and multilingual text than Llama 2, and the data mix was tuned with small-scale experiments before the big run. The tokenizer matters too: Llama 3 moved from a 32,000-token to a 128,000-token vocabulary, which encodes text in about 15% fewer tokens, so the same context window holds more text and each generated token carries more information. Inference engines then add their own layers on top of the weights: paged KV-cache management (vLLM), continuous batching, fused attention kernels and speculative decoding. Together these change the cost of serving more than any single modelling idea. This is also why the same weights can differ in speed by a factor of three or more between a naive script and a tuned server on identical hardware.

example: Take Llama 3 8B and answer three practical questions with numbers. First, memory. 8 billion parameters at 2 bytes (bf16) is 16 GB. At 4-bit quantisation (0.5 byte per weight, plus some overhead) it is about 4.5 GB, which fits on a laptop with 8 GB of free memory. A 70B model at 4 bits is about 40 GB and needs a workstation or two consumer GPUs.
Second, the KV cache. Llama 3 8B has 32 layers, 8 key-value heads and a head size of 128. Per token the cache stores keys and values: 2 × 32 × 8 × 128 × 2 bytes (bf16) = 131,072 bytes, 128 KB. For an 8,192-token chat the cache is about 1 GB. With full multi-head attention (32 key-value heads) it would be 4 GB. At 128,000 tokens the GQA cache is 16 GB, as large as the weights. That is why long-context serving needs cache quantisation or paging.
Third, why Meta trained a small model for so long. Llama 3 8B saw about 15 trillion tokens. Training compute is about \( 6 \times N \times D \) = 6 × 8 × 10⁹ × 15 × 10¹² = 7.2 × 10²³ FLOPs. For the same compute, the Chinchilla rule (about 20 tokens per parameter, so \( C = 6 \times N \times 20N = 120 N^2 \)) would give N = √(7.2 × 10²³ / 120) = √(6 × 10²¹), about 77 billion parameters trained on about 1.5 trillion tokens. Compare the cost of serving. Each generated token needs about \( 2 \times N \) FLOPs: 16 GFLOPs for the 8B model and 154 GFLOPs for the 77B model, ten times more, and ten times more memory to hold the weights. If the model will answer billions of requests, the extra training compute is recovered quickly, which is Meta's reasoning in the LLaMA paper.
Finally LoRA. A weight matrix of 4096 × 4096 has 16.8 million parameters. With rank r = 8, A is 8 × 4096 and B is 4096 × 8, so the adapter has 2 × 4096 × 8 = 65,536 parameters, 0.39% of the matrix. Applying it to the attention matrices of all 32 layers gives a few tens of millions of trainable parameters, which fit on one GPU with the base model frozen and quantised.
intuition: Llama is a printing press for language models: once the plates are published, anyone can print, correct and adapt their own copies.
The design is natural because it separates the expensive part from the useful part. Pretraining a base model costs tens of millions of dollars, but using, adapting and serving it costs far less. If the pretrained weights are shared, the world pays the first cost once and many people do the second part, and the improvements (quantisation, faster kernels, adapters) return to everyone. For Meta, which sells advertising and not model access, a strong ecosystem built around its architecture is worth more than exclusive access. The architecture choices (RMSNorm, SwiGLU, RoPE, GQA) are not special ideas but efficient defaults assembled for training stability and cheap inference, which is why they were copied by almost every open model afterwards.
mistakes: People often think open weights means open source. In fact the Llama licence is not an OSI-approved open-source licence: it limits very large companies, requires a "Built with Llama" notice and a name prefix for derived models, forbids some uses, and Llama 4's multimodal rights excluded entities based in the EU. The training data and full training pipeline were not released.
People often think a model that you can run locally is private by default. In fact the weights are private only if the whole serving stack is; logs, cloud GPU hosts and third-party apps can still store prompts. Also, running a 405B model needs hundreds of GB of memory, so most "local" use is with 8B to 70B models or quantised versions.
People often think more parameters always means better. In fact Meta's own results show a well-trained 8B model matching an older, undertrained 70B model, and a 70B Llama 3.3 approaching the 405B Llama 3.1. Data quality, training tokens and post-training matter at least as much as parameter count.
People often think the Llama line is still the leading open model. In fact by late 2025 and 2026 other open families (DeepSeek, Qwen, Kimi, gpt-oss and Meta's own Muse Spark Open) matched or passed Llama 4, and Meta has not shipped a Llama 5.
friction: The licence is the first friction. Terms differ by version, include use restrictions, and can block some companies or regions, so legal review is needed before building a product. The ecosystem often cannot redistribute model files freely, and derived models must carry the Llama name rules.
Quality at the top has been hard to hold. Llama 4 disappointed many users on coding and reasoning relative to its size, controversy about benchmark testing hurt trust, and its largest planned model was not released. Closed frontier models and newer open models lead on agentic coding and reasoning, so Llama is now mostly a baseline, a base for fine-tuning, and a source of small models.
Operations are your job. Serving a large model needs GPU memory planning, batching, quantisation choices and monitoring, and the safety layer (prompt filtering, abuse handling) is yours too. Fine-tuning can remove safety training, so open weights allow misuse by design, which is a policy debate: some argue open release helps security through scrutiny, others that it gives uncontrolled capability to bad actors.
Finally, the long context claims need testing. A 10-million-token context for Scout is a maximum, and retrieval accuracy at lengths near that limit is much lower than at short lengths; the KV cache for such lengths is far beyond a single machine.
tradeoffs: Choose an open-weight model such as Llama when data must stay inside your network, you need to fine-tune weights, you want predictable per-token cost at high volume (for example 100 million or more tokens per day), or you must run offline. Choose a closed API when you need the best agentic coding or reasoning, have low or spiky volume, and cannot afford a platform team for GPUs. You give up the best capability with open weights and give up control with a closed API.
Choose a small model (1B to 8B) for on-device or very low latency work, such as classification, routing and extraction; choose 70B-class models for general assistants; choose the largest model only if the evaluation proves it, since memory and cost grow quickly. Quantisation to 4 bits costs a small quality loss for a 4x memory saving; verify on your tasks, especially for maths and code.
Choose LoRA fine-tuning for style, format and domain terms with a few thousand examples; choose full fine-tuning only with large data and budget; choose retrieval when knowledge changes. Fine-tuning does not reliably add new facts.
Choose Llama specifically when your stack and staff already use it, or you need the large tooling ecosystem, or a particular small size. Choose a newer open family (Muse Spark Open, DeepSeek V4, Qwen, gpt-oss) when you need current frontier quality; check each licence, since Meta's new Muse licence, MIT, Apache 2.0 and the Llama licence have different conditions.

What does grouped-query attention change and why does it matter for serving? || Several query heads share one key-value head, so the KV cache shrinks (4x for Llama 3 8B). Decode speed is limited by reading weights and cache from memory, so a smaller cache allows longer contexts, larger batches and higher throughput, with little loss in quality.
How does LoRA work and when does it fail? || It freezes the pretrained matrix W and trains a low-rank update B × A, adding few parameters (under 1% per matrix) that can be merged or swapped later. It works well for style and task adaptation, but a low rank limits how much new knowledge or capability can be learned, and aggressive training can erase safety behaviour.
You want to serve Llama 3 70B to 200 concurrent users. What do you estimate first? || Weights: 140 GB in bf16 or about 40 GB at 4 bits. practice: Start by deciding the size from your latency and memory budget, not from a leaderboard. For a laptop or edge device use a 1B to 8B model at 4 bits (llama.cpp or Ollama with GGUF files). Keep the context limit as low as your use case allows, because the cache grows linearly with it.
Evaluate on your data before and after every change. Compare the quantised and full-precision model on your tasks; 8-bit is usually safe and 4-bit is usually acceptable, but code and maths can suffer. When fine-tuning, begin with LoRA or QLoRA on a few thousand clean examples, hold out a test set, and check that general behaviour and safety did not degrade. Prefer the Instruct checkpoint as a start for assistants and the base checkpoint for continued pretraining.
Read the licence of the exact version you use, and record it in your repository. Check the attribution and naming rules, the user threshold, the acceptable-use policy and any regional limits. Keep a model abstraction layer so that you can swap Llama for another open family (Muse Spark Open, DeepSeek, Qwen, gpt-oss) when quality or licence changes. Add your own guardrails (input filtering, output checks, rate limits), since open weights come without a hosted safety layer.

value: DeepSeek is a Chinese AI lab, founded in 2023 in Hangzhou by Liang Wenfeng and funded by the quantitative hedge fund High-Flyer. It became known worldwide in January 2025, when it released DeepSeek-R1, an open-weight reasoning model that was close to OpenAI's o1 on maths and coding benchmarks, under the MIT licence, with a paper that explained how it was trained. Its V3 base model, released a month earlier, reported a final training run of 2.788 million H800 GPU-hours (about $5.6 million at $2 per GPU-hour), a small fraction of what Western labs were believed to spend. Markets reacted strongly: on 27 January 2025 NVIDIA's market value fell by several hundred billion dollars in one day.
What DeepSeek gives an engineer is a concrete, published recipe for efficient frontier-class models: mixture of experts with many small experts, a compressed attention cache, low-precision training, and reinforcement learning with simple rule-based rewards. The weights are downloadable, the API is cheap and compatible with the OpenAI and Anthropic formats, and the papers describe the engineering in detail.
As of October 2026 the current generation is DeepSeek-V4, released as a preview on 24 April 2026. DeepSeek's documentation lists two models: V4-Pro, with 1.6 trillion total parameters and 49 billion active per token, and V4-Flash, with 284 billion total and 13 billion active. Both have a 1-million-token context, offer thinking and non-thinking modes, and are published as open weights. The API model names are now deepseek-v4-pro and deepseek-flash, the latter served by DeepSeek-V4.1-Flash-1017. DeepSeek stands on four lower concepts. NVIDIA GPUs (L0) provide the compute (its early models trained on export-limited H800 chips, which shaped the efficiency focus). Transformers and LLMs (L1) provide the architecture. Reinforcement learning (L1) provides the post-training method (GRPO). Reasoning models (L1) provide the goal: models that think before answering.
terms: Mixture of experts (MoE) — a layer with many expert networks where a router sends each token to a few of them; total parameters are large but active parameters per token are small.
MLA (multi-head latent attention) — an attention variant that stores a small compressed latent vector per token instead of full keys and values, shrinking the KV cache many times.
GRPO (group relative policy optimisation) — a reinforcement learning method that samples a group of answers per prompt and scores each against the group average, with no separate value network.
Rule-based reward — a reward computed by a program (the final answer matches, the code passes tests, the format is correct) instead of a learned reward model.
FP8 training — doing most matrix multiplications in 8-bit floating point, with fine-grained scaling factors to keep accuracy.
MTP (multi-token prediction) — an extra training objective in which the model also predicts tokens after the next one; it can speed up decoding by speculation.
Distillation — training a smaller model on the outputs of a larger one; DeepSeek released small dense models distilled from R1.
Sparse attention — attention in which each token attends to a selected subset of earlier tokens, so the cost does not grow with the square of the context length.
history: The company started with DeepSeek LLM (November 2023), a 67-billion dense model, and DeepSeek-Coder. In 2024 the team published the building blocks one by one: DeepSeekMoE (January 2024), the GRPO algorithm inside DeepSeekMath (February 2024), and DeepSeek-V2 (May 2024; 236 billion total and 21 billion active parameters), which introduced multi-head latent attention and made its API price famously low. DeepSeek-V3 (26 December 2024) combined these with FP8 training and multi-token prediction in a 671-billion-parameter model with 37 billion active, trained on 14.8 trillion tokens.
DeepSeek-R1 (20 January 2025) was the public turning point. The report showed that R1-Zero, a model trained with reinforcement learning on rule-based rewards and no supervised reasoning examples, spontaneously learned to write long chains of thought, check its own work and backtrack. The final R1 added a small amount of cold-start data and further stages for readability. The lab also released six small distilled models. A paper in Nature (September 2025) described the method and reported a very low reinforcement-learning cost for R1 on top of V3.
Later 2025 versions refined the line: V3.1 (August 2025) combined thinking and non-thinking behaviour in one model, V3.2-Exp (September 2025) introduced DeepSeek Sparse Attention (DSA) to cut long-context cost, and V3.2 followed in December. DeepSeek-V4 (24 April 2026) moved to 1M-token context by default with token-wise compression and sparse attention, and with mixed FP4 and FP8 weights in the released checkpoint, according to third-party summaries of its report. Why this pattern? Export controls limited access to the best NVIDIA chips, so the team put effort into memory and communication efficiency, and its price advantage became its distribution strategy. A drawback of that strategy is that Western companies often treat it as a risk (data, policy), which we return to under friction.
how: Start with the attention cache, because it determines the cost of long context. In ordinary multi-head attention each token stores a key and a value for every head. DeepSeek-V3 has 128 heads of size 128, so one layer would store 2 × 128 × 128 = 32,768 numbers per token. Multi-head latent attention (MLA) projects the token's hidden state down to a latent vector of 512 numbers and stores only that, plus a small 64-number key that carries position (decoupled RoPE). That is 576 numbers per token per layer, about 57 times smaller. At attention time the model projects the latent back up to keys and values, and the up-projection matrices can be merged into the query and output projections, so the cost of recovering them is hidden. The result is that serving a long context needs much less GPU memory, and a bigger batch fits on the same card. The LLM concept (L1) provides the attention mechanism that MLA rewrites.
Next, the feed-forward layers. DeepSeekMoE uses many small routed experts plus one or more shared experts that every token uses. V3 has 256 routed experts per MoE layer, and each token goes to 8 of them plus the shared one. The router computes a score per expert from the token's hidden state (a sigmoid in V3) and picks the top 8. Small experts give the router more combinations to choose from than a few large experts, which improves specialisation. A known problem is that routers send most tokens to a few popular experts, which wastes the others and overloads some GPUs. The usual fix is an auxiliary loss that penalises imbalance, but that hurts quality. V3 instead adds a bias to each expert's score for routing only and adjusts it up or down during training depending on its load, so no loss term interferes with learning. With 671 billion total and 37 billion active parameters, each token costs the compute of a 37-billion model while the capacity of the whole is available.
Training precision is the third lever. The GPU layer (L0) makes FP8 matrix multiplication about twice as fast as bf16 and halves the memory of activations. The difficulty is range: 8-bit floats overflow or lose small values easily. DeepSeek scales values in small tiles (for activations, groups of 128 values along a row; for weights, 128 × 128 blocks) so that each tile uses the full range, and keeps accumulation in higher precision. The team also wrote communication code to overlap the expert all-to-all traffic with computation, because moving tokens between GPUs is the main cost of MoE. These low-level changes, working around the weaker interconnect of H800 chips, are how the V3 run reached its reported GPU-hours. V4 pushes the idea down further with 4-bit expert weights in the released checkpoint.
Then reinforcement learning (L1). GRPO works like this. For each prompt, sample a group of G answers from the current model, score each with a reward, and compute each answer's advantage as (reward − group mean) / group standard deviation. Increase the probability of tokens in answers with positive advantage and decrease it for negative ones, with a clipping rule and a KL penalty that keep the update small. There is no value network, which saves a model the size of the policy and keeps the method simple at scale. The rewards for R1 were rules: for maths, the final answer in a required format must match; for code, test cases must pass; plus a format reward for putting reasoning inside think tags. This is the reasoning-models concept at work: with such rewards, the model discovers longer reasoning because it is the way to get the reward more often. Final R1 added supervised data and a general preference stage so that it is also a good assistant.
Finally, the V4 generation addresses long context. The cost of attention grows with the square of the context length and the KV cache grows linearly, so a 1M-token window is expensive with full attention. DeepSeek's sparse attention lets each token attend to a chosen subset, selected by a light scoring step, and V4 combines this with compressing groups of tokens; the third-party summary of the V4 report states that at 1M tokens it needs about 27% of the compute and 10% of the KV cache of V3.2. The API supports thinking and non-thinking modes with a reasoning-effort setting.

example: First the cache saving. Standard attention in V3's shape stores 2 × 128 heads × 128 dimensions = 32,768 values per token per layer. MLA stores 512 + 64 = 576. The ratio is 32,768 / 576 = 56.9. With 61 layers and 2 bytes per value, MLA needs 576 × 61 × 2 = 70,272 bytes, about 69 KB per token, so a 128,000-token context needs about 9 GB. The uncompressed form would need about 512 GB at the same length, which could not be served on one machine.
Now the compute check for V3's training run. Active parameters are 37 × 10⁹ and the data is 14.8 × 10¹² tokens, so FLOPs ≈ 6 × 37 × 10⁹ × 14.8 × 10¹² = 3.3 × 10²⁴. The reported cost is 2.788 million H800 GPU-hours = 1.0 × 10¹⁰ GPU-seconds. Achieved throughput is 3.3 × 10²⁴ / 1.0 × 10¹⁰ = about 3.3 × 10¹⁴ FLOPs per GPU per second, 330 TFLOPs. An H800 has roughly 990 TFLOPs of dense bf16 peak, so this is about one third of peak, which is good for a MoE run on a limited network and shows the efficiency work paid off. At $2 per GPU-hour, 2.788 million hours cost $5.58 million. That figure covers only the final pretraining and post-training runs, not research, ablations, data work or the hardware purchase, and that is why the claim was debated.
Last, a small GRPO step. A prompt asks for the value of 17 × 24. The model samples four answers, and the checker marks them 1 (correct, 408) or 0. Rewards are [1, 0, 0, 1]. The mean is 0.5 and the standard deviation 0.5, so advantages are [+1, −1, −1, +1]: the two correct answers become more likely and the two wrong ones less likely. If only one of the four is correct, rewards are [1, 0, 0, 0], the mean is 0.25, the standard deviation 0.433, and the advantages are [+1.73, −0.58, −0.58, −0.58]: the rare success gets a strong push. If all four are correct or all are wrong, the advantages are zero and nothing is learned from that prompt, which is why training prompts must be neither too easy nor too hard.
intuition: DeepSeek is what happens when a team treats memory, precision and communication as the real budget, and uses the cheapest honest teacher available: a checker that says right or wrong.
The design is natural once you ask where cost comes from. Long contexts cost memory, so compress what is stored. Big models cost compute, so use only the experts a token needs. Training in 16 bits wastes bandwidth, so use 8 and scale carefully. Reasoning data written by humans is scarce and expensive, but for maths and code a program can check the answer for free, so reinforcement learning on those checks can teach long careful thinking without human demonstrations. Each choice removes a cost that the layer below would otherwise charge.
mistakes: People often think the $5.6 million figure is the total cost of building DeepSeek-V3. In fact it is the rental-price estimate for the final training run only; the company said so itself. Research, failed experiments, data preparation, salaries and owned GPUs are excluded, and the lab's total spending is much higher.
People often think DeepSeek showed that frontier models do not need much compute. In fact it showed that compute can be used far more efficiently, and its own models still used thousands of GPUs and a large cluster for experiments. Lower cost per capability tends to increase total demand, not reduce it.
People often think R1 learned to reason purely by itself from nothing. In fact R1-Zero started from a strong pretrained base model (V3-Base) that had already seen a lot of reasoning-like text. Reinforcement learning drew out and strengthened behaviour that was present; the final R1 also used some supervised data for readability.

friction: The first friction is trust and governance. Using the hosted DeepSeek API sends data to servers in China, and many companies and governments restrict it. Hosted DeepSeek models have been reported to refuse or reshape answers on topics sensitive in China, and security researchers have found weaker defences against jailbreaks and prompt injection in some versions than in leading US models. The model names and endpoints also change quickly: the legacy chat and reasoner names were retired in July 2026, and the Flash model was updated to a 1017 build in October, so pinned versions and tests matter.

Choose self-hosted weights when data must stay inside your boundary or you need fine-tuning, and accept the cost of GPUs and operations. Choose a US or European closed API when compliance, support contracts or the highest agentic reliability matter more than price.
Choose V4-Flash for volume work (summaries, extraction, routing, coding assistance) where cost and speed count; choose V4-Pro for hard reasoning and long agent tasks, accepting several times the price and much larger hardware needs. Use thinking mode when mistakes are costly and non-thinking mode for simple requests, because thinking tokens add cost and delay.

value: Stable Diffusion is a text-to-image model released in August 2022 by Stability AI together with the CompVis group (LMU Munich), Runway and the LAION data project. You type a sentence; it draws a picture. Its importance is less that it drew good pictures (DALL·E 2 and Midjourney already did) than how it was built and shared. It ran on one consumer GPU with about 8 GB of memory, generated a 512 × 512 image in seconds, and its weights were downloadable. Within months there were thousands of fine-tuned variants, web interfaces (AUTOMATIC1111, later ComfyUI), and add-ons that controlled pose, edges and style.
The trick behind the efficiency is latent diffusion. Earlier diffusion models removed noise from the image itself, in pixel space, which is slow because a 512 × 512 colour image has 786,432 numbers. Stable Diffusion first compresses the image with an autoencoder to a small "latent" tensor of 64 × 64 × 4 = 16,384 numbers, 48 times fewer, and does all the generation there. Only at the end does a decoder turn the latent back into pixels. The expensive network works on a small representation, so it is cheaper to train and to run.
As of October 2026, Stable Diffusion is better described as a foundation and an ecosystem than as the leading image generator. The newest Stable Diffusion family I could verify is Stable Diffusion 3.5 (October 2024), an 8-billion-parameter multimodal diffusion transformer under the Stability Community Licence; Stability's 2026 announcements concern audio models and enterprise tooling, and stronger image models from other labs (such as Google's Gemini image models and the FLUX family from the original SD authors' new company) have taken the quality lead. It stands on PyTorch (L0), in which the original code, the Hugging Face diffusers library and almost all community tools are written, and on diffusion models (L1), which supply the training objective and the sampling procedure.
terms: Diffusion model — a generative model trained to reverse a process that gradually adds noise to data; generation starts from pure noise and removes it step by step.
Latent space — a compressed representation of an image made by an autoencoder; Stable Diffusion's latent is 8 times smaller in each spatial direction (64 × 64 for a 512 × 512 image).
VAE (variational autoencoder) — the encoder and decoder pair that maps images to latents and back.
U-Net — a convolutional network with a down-sampling path, an up-sampling path and skip connections between them, used as the denoiser in versions 1 and 2 and SDXL.
Cross-attention — an attention layer in which the image latent supplies the queries and the text embeddings supply the keys and values, so each image location reads the prompt.
Classifier-free guidance (CFG) — a sampling method that runs the denoiser with and without the prompt and extrapolates away from the unconditioned result, to make the image follow the text more closely.
Sampler (scheduler) — the algorithm that turns the network's noise predictions into the next, less noisy latent (DDIM, Euler, DPM-Solver); it decides how many steps are needed.
LoRA and ControlNet — small add-on networks: LoRA adapts style or subject with few parameters; ControlNet adds spatial control (edges, depth, pose).
history: The idea of diffusion for images came from Sohl-Dickstein et al. (2015) and became practical with Ho, Jain and Abbeel's DDPM (2020), which showed that training a network to predict the added noise gives sharp samples. Dhariwal and Nichol (2021) showed diffusion could beat GANs, and OpenAI's GLIDE and DALL·E 2 and Google's Imagen (2022) used text conditioning, but these ran in pixel space on large clusters and were not released.
Rombach, Blattmann, Lorenz, Esser and Ommer at the University of Heidelberg and LMU Munich proposed latent diffusion in "High-Resolution Image Synthesis with Latent Diffusion Models" (December 2021; CVPR 2022). Stability AI, led by Emad Mostaque, paid for the compute (reported at about 150,000 A100 GPU-hours for version 1) and Stable Diffusion 1.4 was released on 22 August 2022 under a permissive licence, with a training set filtered from the LAION-5B image-text collection. Version 2 (November 2022) changed the text encoder to OpenCLIP and added 768-pixel models; SDXL (July 2023) enlarged the U-Net to about 2.6 billion parameters, used two text encoders and made 1024-pixel images standard.
Stable Diffusion 3 (announced February 2024; paper "Scaling Rectified Flow Transformers for High-Resolution Image Synthesis", Esser et al., March 2024) replaced the U-Net with a transformer (MMDiT) and the noise schedule with rectified flow. The June 2024 release of the 2-billion "Medium" model was poorly received for anatomy errors and unclear licence terms, and Stability had leadership and funding turmoil in 2024. Stable Diffusion 3.5 (October 2024) fixed much of this, with 8-billion and 2.5-billion models. Meanwhile several of the original authors left to found Black Forest Labs, which released FLUX.1 in August 2024. The reasons for each step: quality (bigger models, better text encoders), control (ControlNet, LoRA) and cost (distilled models such as SDXL Turbo that need one to four steps).
how: Training happens in two stages. First an autoencoder is trained to compress and reconstruct images. The encoder reduces a 512 × 512 × 3 image by a factor of 8 in each direction to a 64 × 64 × 4 latent, and the decoder reconstructs the image, with a perceptual loss and a small adversarial loss so that details stay sharp. It is trained once and then frozen. Second, the diffusion model is trained in latent space. For each training image: encode it to a latent \( z_0 \); choose a random time step t; add Gaussian noise to get
\[ z_t = \sqrt{\bar\alpha_t}\, z_0 + \sqrt{1 - \bar\alpha_t}\, \varepsilon \]
where \( \bar\alpha_t \) is a number that falls from near 1 (almost no noise) to near 0 (almost pure noise) as t goes from 0 to 1,000; and ask the network to predict ε given z_t, t and the caption. The loss is the mean squared difference between the true and predicted noise. The L1 diffusion concept supplies exactly this objective; Stable Diffusion's contribution is where it is applied (the latent) and how it is conditioned.
Conditioning on text works through cross-attention. The prompt is tokenised (up to 77 tokens), and a frozen text encoder turns it into a sequence of vectors: CLIP ViT-L/14 in version 1, with more encoders in later versions (OpenCLIP-ViT/G and CLIP-ViT/L in SDXL, plus T5-XXL in SD3). Inside the U-Net, at several resolutions, an attention layer takes queries from the image features and keys and values from the text vectors. Each spatial location can therefore look up the words relevant to it ("red" near the car, "snow" at the ground). The U-Net itself has about 860 million parameters in version 1. It processes the latent through ResNet blocks, down-sampling and up-sampling, with self-attention layers (every location reads every other location) and skip connections that carry fine detail across.
At generation time you start from pure Gaussian noise in latent shape and repeat for 20 to 50 steps. At each step the network predicts the noise, and the sampler removes a part of it according to the schedule. Fewer steps are possible because ODE-style samplers (DDIM, DPM-Solver) follow a smooth path instead of the 1,000 stochastic steps of the original DDPM. To make the image follow the prompt, classifier-free guidance runs the network twice per step: once with the prompt embedding c and once with an empty prompt ∅. The final estimate is \( \hat\varepsilon = \varepsilon(\varnothing) + w\,(\varepsilon(c) - \varepsilon(\varnothing)) \), with a guidance scale w of about 7 for version 1. Larger w means closer to the text but less variety and more saturated colour. This doubles the cost of each step, which is why distillation methods try to remove it. When the steps are done, the decoder converts the final latent into pixels. The PyTorch layer (L0) provides the tensors, autograd, mixed-precision training and the CUDA kernels (including fused attention) that make this practical, and diffusers wraps the pipeline so a few lines of Python run it.
Later versions change the denoiser but keep the plan. SD3 and SD3.5 use a multimodal diffusion transformer (MMDiT): image-latent patches and text tokens are processed as two streams with separate weights that attend to each other jointly, so text is not only a side input. Instead of predicting noise with a schedule of 1,000 steps, rectified flow trains the model to predict the velocity along a straight line from noise to data, which makes few-step sampling more accurate. SD3.5 Large has 8 billion parameters, three text encoders (two CLIP models and T5-XXL) and a larger 16-channel latent.
The open ecosystem adds modules at the edges. LoRA freezes the base weights and trains small low-rank updates to attention layers (a few MB), so a style or a person's face is a small file you can share. DreamBooth fine-tunes on a few photos of a subject. ControlNet copies the encoder of the U-Net and trains it to accept an extra image (edges, depth, pose) as a condition. Inpainting and image-to-image start the denoising from a partly noised existing latent instead of pure noise. In image-to-image, a strength of 0.5 means the input is noised to the middle of the schedule and only the second half of the steps is run, so the layout of the original survives while details change. This is also how a one-step or few-step distilled model is used for fast previews.

example: Follow one pixel-sized number through the maths. Say one latent value is z₀ = 2.0, and at some time step ᾱ_t = 0.5, so √ᾱ = 0.707 and √(1 − ᾱ) = 0.707. The noise drawn is ε = −1.0. The noised value is z_t = 0.707 × 2.0 + 0.707 × (−1.0) = 0.707. The network sees only 0.707 (and the step t and the prompt) and must guess ε. If it guesses ε̂ = −1.0 exactly, the loss is zero, and the clean value can be recovered: \( z_0 = (z_t - \sqrt{1 - \bar\alpha}\,\hat\varepsilon) / \sqrt{\bar\alpha} \) = (0.707 + 0.707) / 0.707 = 2.0. Real training does this for 64 × 64 × 4 values per image, millions of images, random t each time.
Now guidance. At one step the model predicts noise −0.6 for this value without the prompt and −1.0 with it. With w = 7.5: ε̂ = −0.6 + 7.5 × (−1.0 − (−0.6)) = −0.6 + 7.5 × (−0.4) = −3.6. The guided estimate is far beyond either prediction: the sampler is pushed hard in the direction where the prompt makes a difference. With w = 1 you get the plain conditional prediction (−1.0); with w = 0, the unconditional one (−0.6). Because the network runs twice per step, 30 steps need 60 network evaluations.
Next, why the latent helps. A 512 × 512 image has 262,144 pixel positions. If the denoiser applied self-attention directly at that resolution, each head would compute 262,144² = 6.9 × 10¹⁰ pairwise scores. At the 64 × 64 latent resolution there are 4,096 positions, so 4,096² = 16.8 million scores, which is 4,096 times fewer. The autoencoder gives up some fine detail (small text and faces suffer) but cuts memory and compute so much that one 8 GB GPU can run it.
Finally, a budget. With 30 steps and guidance, one image needs 60 U-Net passes plus one decode and one text-encoder pass. If a GPU does about 10 U-Net passes per second at 512 × 512 (an approximate figure for a mid-range consumer card), the image takes about 6 seconds. A distilled model such as SDXL Turbo needs 1 to 4 steps without guidance, so under a second. The same prompt gives different images with different random seeds, and the same seed with the same settings gives the same image, which is how artists repeat and refine a result.
intuition: Sculpting from fog: begin with a cloud of random noise, and at every step remove the part that does not look like what was asked for, until a picture is left.
The design is natural because noise is easy and structure is hard. Adding noise to an image is simple and needs no learning; undoing a tiny bit of noise is also an easy problem for a network, since a small amount of noise barely changes the picture. Doing this many small steps lets the model build the image from coarse shape to fine detail. Working in a latent space is natural because most of a picture's pixels carry detail that a compact code can regenerate, so the heavy network should look at the compact code. Text conditioning by cross-attention is natural because the image has many places, and each place needs to look up a different word.
mistakes: People often think Stable Diffusion stores and collages the training images. In fact the model contains about a billion parameters (a few GB) learned from billions of images, so it cannot hold them as files. It does, however, sometimes reproduce near-copies of images that were duplicated many times in the training set, which is a documented effect and a basis of the copyright claims.
People often think the text prompt is "understood". In fact a frozen text encoder (CLIP in the early versions) turns words into vectors trained to align with images, and CLIP has known limits: it handles counting, spatial relations and text spelling badly. Later models added T5 and larger encoders partly for this reason.
People often think more denoising steps always give better images. In fact quality saturates after about 20 to 30 steps with a good sampler, and more steps cost time. Too high a guidance scale also hurts: images become oversaturated and less diverse.
People often think Stable Diffusion is one model. In fact it is a series with different architectures (U-Net in 1.x, 2.x and XL; transformer in 3.x), different licences and many community fine-tunes. A LoRA or ControlNet trained for version 1.5 does not work on SDXL or SD3.
friction: Training data and rights are the largest open issue. Models were trained on web-scale image collections, including images of artists and photographers collected without consent, and lawsuits such as Getty Images v. Stability AI and the artists' class action Andersen v. Stability AI test whether this is lawful. Rules differ by country, and enterprises ask for indemnity or models trained on licensed data, which is why Stability now stresses licensed data for its newer audio models.
Technical limits persist. Early versions drew hands, text and counting wrongly; later ones are better but still weak at precise layouts and long text compared with the newest closed models. Compression to a latent loses small details. Sampling needs many sequential steps, so latency is higher than for a single forward pass, and guidance doubles the work; distillation helps but can reduce diversity and quality.
Open release also means misuse: non-consensual deepfakes, disinformation and abusive imagery can be made with open weights, and safety filters can be removed by users. Providers respond with licence terms, dataset filtering and watermarks, but these are partial.
The business side is difficult too. Stability AI's own finances were unstable in 2024, and the licences changed (the community licence is free only for organisations under $1 million in annual revenue). A team that depends on a particular checkpoint must handle licence terms, fast model turnover and a community tool ecosystem that is not centrally supported.
tradeoffs: Choose Stable Diffusion (or another open model such as FLUX) when you need control: private data, a custom style via LoRA, structured guidance via ControlNet, offline use, predictable cost on your own GPUs, or fine-tuning on your brand assets. Choose a hosted closed model (Gemini image models, GPT image models, Midjourney) when you need the best prompt-following and text rendering with little setup, and accept per-image fees and usage rules.
Choose SD 1.5 or a small distilled model when hardware is limited (4 to 8 GB) and speed matters, accepting lower quality. Choose SDXL or SD3.5 when you need 1024-pixel output and better composition; SD3.5 Large needs roughly 16 to 24 GB of memory in half precision unless quantised. Choose Medium or Turbo variants for throughput.
Choose a LoRA (a few MB, minutes to train, reusable) for a style or a subject; choose full fine-tuning only with thousands of images and a clear need; choose ControlNet when composition must match a layout. LoRAs trained on one base model do not transfer, so factor in retraining when you switch models.
Choose more steps and a moderate guidance scale (about 4 to 7) for final renders and 4 to 8 steps with a distilled model for interactive previews. Budget the licence: the community licence is free below $1 million revenue; above that you need an enterprise agreement.
interview: Why does latent diffusion run on a consumer GPU when pixel-space diffusion did not? || An autoencoder compresses the image by 8× per side, so the denoiser works on 48 times fewer numbers and its self-attention operates on 4,096 positions instead of 262,144 (about 4,096 times fewer pairs). Training and sampling become cheap, and detail is restored by the decoder. The price is some lost fine detail from the compression.
Explain classifier-free guidance and its cost. || Train the denoiser with the text condition randomly dropped, so one network gives both conditional and unconditional noise predictions. At sampling, extrapolate: \( \hat\varepsilon = \varepsilon(\varnothing) + w\,(\varepsilon(c) - \varepsilon(\varnothing)) \). A larger w improves prompt adherence but reduces diversity and can oversaturate. It needs two network evaluations per step, doubling cost unless the model is distilled for guidance.
How does cross-attention inject text into the image generation? || Image features give the queries, text-encoder output gives the keys and values. Each spatial location computes attention weights over the prompt tokens and takes a weighted sum of their value vectors, so different regions can read different words. In MMDiT, text and image tokens attend jointly in both directions.

Why, and what do you do? || LoRAs modify specific weight matrices of a particular architecture and parameterisation; SDXL is a U-Net with two text encoders, SD3.5 is an MMDiT with three, so shapes and meaning differ. practice: Use the diffusers library (or ComfyUI for visual pipelines) and start from a current open checkpoint that fits your GPU: a distilled or Medium model for 6 to 8 GB, SDXL or SD3.5 for 12 GB and more. Use half precision (fp16 or bf16), fused attention, and a fast sampler such as DPM-Solver++ or Euler with 20 to 30 steps. Keep the seed so you can reproduce an image, and change one setting at a time when tuning.

Do not expect precise text or counts from older versions; fix details with inpainting. For consistency of a subject or style, train a LoRA on 10 to 50 clean images with captions, using rank 8 to 32, and check that it does not overfit (every output looks like the training set).

Production systems add a safety checker, watermarking or metadata (C2PA) and logging. Read each model's licence before commercial use, and record the model hash and licence in your repository.

value: AlphaFold is a family of neural networks from Google DeepMind (and, for the third version, Isomorphic Labs) that predicts the three-dimensional shape of a protein from its sequence of amino acids. Why does that matter? A protein is a chain of typically 100 to 1,000 amino acids that folds into a specific 3D shape, and the shape decides what the protein does: it forms an enzyme's active site, a drug's binding pocket or a virus's spike. For fifty years, finding a shape meant growing crystals and using X-ray crystallography, or using cryo-electron microscopy or NMR; each structure took months or years of lab work and often hundreds of thousands of dollars. The sequence is cheap to read, but predicting the shape from it (the "protein folding problem") was an open research problem since the 1970s.
AlphaFold 2 (CASP14, November 2020; Nature, July 2021) reached accuracy comparable to experiments on most targets: median backbone error of about 0.96 ångström, around the width of a carbon atom, where the next best method scored 2.8 ångström. DeepMind and the European Bioinformatics Institute then released the AlphaFold Protein Structure Database, which now holds over 200 million predicted structures, close to all catalogued proteins. DeepMind reports over three million researchers in more than 190 countries using its resources. Demis Hassabis and John Jumper shared the 2024 Nobel Prize in Chemistry with David Baker (for computational protein design) for this work. AlphaFold 3 (May 2024) extended predictions to complexes of proteins with DNA, RNA, small molecules (ligands), ions and chemical modifications; as of October 2026 DeepMind's AlphaFold page lists AlphaFold 3 as the latest version, with a free AlphaFold Server for non-commercial research and code and weights available for academic use.
For the layer above, AlphaFold gives biology and drug discovery a structure for almost any target as a database lookup: scientists use it to guess function, to design experiments, to dock candidate drugs and as a starting point for protein design. It stands on three things below. JAX (L0) is the framework in which it is written, which provides automatic differentiation and compilation for accelerators. Deep learning (L1) provides the end-to-end differentiable training, with losses on 3D coordinates. Transformers and attention (L1) provide the core operation, adapted from sequences of words to alignments of protein sequences and to pairs of residues.
terms: Residue — one amino acid in the chain; a 300-residue protein has 300 residues.
MSA (multiple sequence alignment) — related sequences from other species lined up so that each column corresponds to the same position; it shows which positions change freely and which are conserved.
Co-evolution — when two positions mutate together across species because they touch in 3D and must stay compatible; the main signal AlphaFold reads from an MSA.
Pair representation — a table with one entry (a vector) for every pair of residues, holding what the model believes about their relation (distance, orientation, contact).
Evoformer — AlphaFold 2's main network: 48 blocks that exchange information between the MSA representation and the pair representation using attention.
Structure module — the part of AlphaFold 2 that turns the representations into 3D coordinates, using per-residue rigid frames (a position and a rotation).
pLDDT and PAE — per-residue confidence (0 to 100) and predicted error between pairs of residues; they tell you which parts to trust.
CASP — Critical Assessment of Structure Prediction, a blind contest held every two years in which teams predict structures that have not yet been published.
history: The folding problem was posed by Anfinsen's experiments in the 1960s, which showed that sequence alone determines shape. Levinthal noted in 1969 that a chain cannot search all conformations at random, since the number is astronomically large. The Protein Data Bank (founded 1971) collected experimentally solved structures; by 2020 it held about 170,000 entries, far fewer than the hundreds of millions of known sequences. CASP, started in 1994 by John Moult, measured progress, and for years progress was slow; the best methods reached about 40 to 60 on the GDT_TS accuracy scale (0 to 100) on hard targets.
Co-evolution gave the first break: if two positions mutate together, they probably touch. Methods such as direct coupling analysis (2011) used this, and in 2018 DeepMind's first AlphaFold used a convolutional network on co-evolution data to predict inter-residue distances and won CASP13 by a clear margin, but its accuracy was still below experiments. AlphaFold 2 (2020) replaced this pipeline by one end-to-end attention network, with a median GDT_TS of about 92 at CASP14, and the organisers judged the core problem of single-chain structure prediction solved to a large extent. The paper and the open-source code (Apache 2.0, with weights under CC BY 4.0) appeared in July 2021. The database followed, first with 350,000 structures in July 2021 and over 200 million in July 2022.
Other groups quickly built on the idea: RoseTTAFold (Baker lab, 2021), OpenFold (an open PyTorch reproduction), ESMFold (Meta, 2022, which predicts from a protein language model without searching for alignments), and AlphaFold-Multimer for complexes. AlphaFold 3 (Abramson et al., Nature, May 2024) replaced the structure module with a diffusion model over atom coordinates so that it could handle any molecule type; code for academic use was released in November 2024. Open-source rivals such as Boltz and Chai followed, because the AlphaFold 3 weights have usage limits. The reasons for the changes were scope (biology is mostly interactions, not isolated chains) and licensing pressure from the research community.
how: Follow AlphaFold 2 from input to coordinates. The input is one amino-acid sequence. The first stage is not a neural network: search large sequence databases (UniRef90, MGnify, BFD) with tools such as JackHMMER and HHblits to collect thousands of related sequences and align them into an MSA, and search structure databases for templates. This step takes minutes to hours on CPUs and is often the slowest part. The MSA carries the evolutionary evidence: columns that vary together point to contacts.
The network builds two tables. The MSA representation has one row per sequence and one column per residue, each cell a vector of 256 numbers. The pair representation has one cell for every pair of residues, a vector of 128 numbers, initialised from relative position and from the MSA. The Evoformer, 48 blocks deep, updates both. In the MSA stack, row-wise attention lets the positions within one sequence exchange information, with the pair table adding a bias to the attention scores (so what is known about pair i-j changes how i attends to j), and column-wise attention lets the same position in different species exchange information. An "outer product mean" turns the MSA information about columns i and j into an update of pair cell (i, j): this is how co-evolution reaches the pair table. In the pair stack, triangular multiplicative updates and triangular attention enforce geometric consistency. If i is close to j and j is close to k, then i cannot be far from k; every update to the edge (i, k) uses the edges (i, j) and (j, k). The attention is borrowed from the L1 transformer concept, but it is applied along rows, columns and triangles of tables instead of along a single token sequence.
The structure module reads the pair representation and the first row of the MSA and builds the backbone. Each residue gets a rigid frame, meaning an origin (the position of its alpha carbon) and an orientation. All frames start at the same place with the same orientation (a "residue gas") and are moved over 8 iterations. The key operation is Invariant Point Attention: each residue creates query, key and value points in its own local frame, these are mapped into global space, and attention weights depend on the distance between points, so the result does not change if the entire protein is rotated or shifted. After the frames are fixed, the module predicts side-chain torsion angles. The loss is the Frame Aligned Point Error (FAPE): coordinates are compared inside each residue's own frame, so mistakes in chirality and local geometry are penalised. Training also includes a masked-MSA prediction loss similar to BERT, a distance histogram loss, and a confidence loss for pLDDT.
Recycling feeds outputs back as inputs: the predicted pair distances and the final representations are given to the network again for 3 extra passes, so it refines its own answer. Training used about 170,000 structures from the PDB plus a "self-distillation" set, in which the model's own confident predictions on about 350,000 unlabelled sequences became extra training examples. Because the loss is computed on coordinates and the whole pipeline is differentiable, a gradient from a wrong atom position flows back through the structure module into the Evoformer, which is what makes the system end-to-end. The model has about 93 million parameters, small by LLM standards, and the original training took on the order of one to two weeks on 128 TPU v3 cores. JAX (L0) matters here: the code is written as pure functions (with the Haiku library), compiled by XLA, with vmap batching and efficient control over memory for the \( N^2 \) and \( N^3 \) operations.
AlphaFold 3 keeps the idea but changes the parts. The heavy MSA processing is reduced to a small module and the main trunk, the Pairformer, works mostly on the pair representation and the single representation. The structure module is replaced by a diffusion module: it starts with random atom positions and denoises them into coordinates, conditioned on the trunk output, for every atom (not only the backbone), so ligands, nucleotides and modified residues are handled in the same way. The diffusion approach also gives several samples per input, and training used cross-distillation from AlphaFold-Multimer predictions to reduce hallucinated structure in disordered regions. DeepMind reported much higher accuracy than docking tools for protein-ligand pairs on the PoseBusters benchmark.

example: Start with the co-evolution signal. Four related sequences are aligned, and we look at two columns, 12 and 87:
  seq A: position 12 = E (glutamate, negative), position 87 = K (lysine, positive)
  seq B: 12 = D (aspartate, negative),         87 = R (arginine, positive)
  seq C: 12 = E,                               87 = K
  seq D: 12 = K (positive),                    87 = E (negative)
Position 12 changes between E, D and K, and position 87 changes between K, R and E, but they never take the same charge: when one is negative, the other is positive. Such a coupled pattern suggests a salt bridge between the two side chains, which means residues 12 and 87 are probably within about 4 ångström in 3D although they are 75 positions apart in the chain. Real MSAs have thousands of rows, and the network learns these couplings automatically through the outer product mean.
Next, the triangle rule. Suppose the pair table says residues i and j are 5 Å apart and j and k are 4 Å apart. Then the distance i-k must be between |5 − 4| = 1 Å and 5 + 4 = 9 Å. If another part of the table claims i-k is 12 Å, one of the three numbers is wrong. Triangle updates let each edge look at the other two edges of every triangle that contains it, so such conflicts are resolved in favour of a consistent geometry. The cost is \( N^3 \) operations per layer: for a 300-residue protein, 300³ = 27 million triples, but for a 1,000-residue protein it is 10⁹, 37 times more, and for 3,000 residues 2.7 × 10¹⁰. This is why large complexes need large GPUs and why memory, not compute, is the limit.
Last, reading the confidence. A predicted 300-residue protein returns a pLDDT for each residue. Suppose residues 1 to 20 have pLDDT 35 and the rest around 92. Values above 90 are very high confidence (side chains are usually right), 70 to 90 confident for the backbone, 50 to 70 low, and below 50 very low, which usually means the region is intrinsically disordered, such as a floppy tail, not that the model failed. A researcher would trust the core, ignore the tail, and check the PAE plot to see whether two domains are placed correctly relative to each other. Two domains with pLDDT 95 each but a high PAE between them means the model knows each shape but not how they are arranged.
intuition: AlphaFold reads the family history of a protein: positions that always change together must be neighbours, and a geometry-aware network turns those neighbour hints into a consistent 3D shape.
The design is natural because evolution has already run a huge experiment. Every surviving protein in every species is a working solution, and the variations between relatives show which positions are constrained by their neighbours. A network that reads thousands of relatives learns which pairs are in contact. Attention is natural for this, since "which position pairs matter" is exactly what attention scores represent. The triangle rules are natural because the answer lives in 3D space, where distances must satisfy geometric laws; building these laws into the network spares it from learning them from scratch. Finally, recycling is natural because folding is an iterative refinement, and the model can check its guess against its own constraints.
mistakes: People often think AlphaFold simulates how a protein folds over time. In fact it predicts the final folded structure in one forward pass (plus recycling); it does not model the physical pathway, the energy landscape or the time-dependent motion. It says what the shape looks like, not how it got there.
People often think AlphaFold predictions are as reliable as experiments everywhere. In fact the confidence varies. Low pLDDT regions are unreliable, flexible loops and disordered regions have no single shape, and predicted structures usually show one conformation although many proteins move between states. For drug design, small errors in a binding site matter a lot.
People often think AlphaFold solved protein design or drug discovery. In fact it predicts structure from a known sequence. Designing a new protein, or showing that a molecule is a safe, effective drug, are different problems (David Baker's work, RFdiffusion, and clinical trials). AlphaFold is one important tool in those pipelines.
People often think the neural network does everything. In fact AlphaFold 2 depends on a database search for the MSA, and its accuracy falls for proteins with few relatives (orphan proteins, designed proteins, antibodies). AlphaFold 3 and ESMFold reduce this dependence, but they are still weaker without evolutionary information.
friction: Dynamics and ensembles are the biggest limit. Proteins are not static: they open, close, bind and change shape, and drugs often select a particular state. AlphaFold gives mostly one structure, and sampling methods that produce several are still being developed. Predicting the effect of a single mutation on stability or function is also poor, since the training objective rewards the shape of the sequence in the wild, not sensitivity to changes.
Accuracy on complexes and ligands is lower than on single chains. AlphaFold 3 improved this but can still place ligands wrongly, hallucinate structure in disordered regions, and fail on antibody-antigen interfaces. Experimental validation remains needed for decisions that cost money. Confidence scores can be miscalibrated for unusual inputs.
Access and licensing are issues. AlphaFold 2 is fully open, but AlphaFold 3's code and weights are limited to academic, non-commercial use; the server has daily job limits and restricts some ligands. This is why open reproductions (OpenFold, Boltz, Chai, Protenix) are active, and why pharmaceutical companies run their own versions.
Compute scales badly: attention and triangle operations grow with \( N^2 \) and \( N^3 \), so complexes of several thousand residues need very large memory, and the MSA search is a bottleneck (ColabFold with MMseqs2 makes it 40 to 60 times faster). Finally, there is a risk of over-trust: a prediction in a database looks like a measured fact, so it is easy to forget it is a model.
tradeoffs: Choose a precomputed AlphaFold database entry when the protein is a known natural sequence and you need a quick look; it is free, instant and includes confidence. Choose to run AlphaFold (or OpenFold or ColabFold) yourself when your sequence is new, mutated, or a complex, accepting the compute and the MSA search time. Choose an experimental structure (crystallography, cryo-EM) when the decision is expensive, the conformation or ligand state matters, or confidence is low; it costs months and money.
Choose AlphaFold 3 or a similar model (Boltz, Chai-1) when you need protein-ligand, protein-nucleic acid or modified residues; choose AlphaFold 2 or AlphaFold-Multimer for protein-only work when you want the permissive licence and mature tooling. Check the licence for commercial use: the AlphaFold 3 weights are restricted, while some open alternatives use permissive licences such as MIT.
Choose ESMFold or other single-sequence models when you must screen millions of sequences quickly or have no relatives to align; choose MSA-based models when accuracy matters more than speed, because the alignment gives a strong signal. Choose more recycles, more MSA depth and several random seeds for hard targets, and accept longer runs.
Choose molecular dynamics or enhanced sampling after structure prediction when the question is about motion or binding energy; the predicted static structure is the start of that work, not the answer.
interview: Explain how the Evoformer uses the MSA to infer contacts. || The MSA representation holds one vector per sequence and residue. Column-wise attention compares the same position across species and row-wise attention (with a pair bias) relates positions within a sequence. An outer product mean combines the MSA vectors at positions i and j into an update of pair cell (i, j), so co-varying columns raise the evidence for a contact. The pair representation then feeds back as a bias into the MSA attention, so each side keeps refining the other.
Why triangle updates and what is the cost? || Distances and orientations must satisfy triangle inequalities, so every edge (i, k) is updated using the edges (i, j) and (j, k) for all j. This enforces consistent geometry inside the pair table. The cost is \( O(N^3) \) per layer in compute and large activation memory in \( N^2 \), which limits very long proteins and complexes unless one uses chunking or fused kernels.
What is Invariant Point Attention and why is invariance needed? || Each residue has a local frame; queries, keys and values include 3D points expressed in that frame and mapped to global space, and attention scores use point distances. Rotating or translating the whole protein does not change the distances, so predictions do not depend on the arbitrary global coordinate system, which would otherwise have to be learned by data augmentation.
How does AlphaFold 3 differ in generating structures, and what new failure does that bring? || A diffusion module denoises atom coordinates directly, conditioned on the trunk, which handles any molecule type and gives multiple samples. The generative approach can hallucinate plausible-looking structure in regions that are disordered, so DeepMind added cross-distillation and reports confidence from sampled structures. You must check the confidence and the sample variation.
A biotech wants to use AlphaFold to prioritise 10,000 candidate binders. How do you design the workflow? || Use a fast filter first (single-sequence or a smaller model, or precomputed structures), then run the full model on the top few hundred with several seeds. Keep only candidates with high interface confidence (ipTM, low PAE across the interface), compare to known controls, validate a subset experimentally to calibrate the pipeline, and check the model licence for commercial use.
practice: First look the protein up in the AlphaFold Protein Structure Database (alphafold.ebi.ac.uk) by UniProt ID. If it is there, download the structure and read the confidence before anything else: colour by pLDDT, and open the PAE plot to see which domains are placed reliably relative to each other. Treat residues below 70 with caution, and below 50 as probably disordered.
If you need a new sequence, a mutant or a complex, use ColabFold (fast MSA search with MMseqs2, free notebooks) or the AlphaFold Server for non-commercial work, or run OpenFold, Boltz or Chai-1 locally when you need open licences or scale. Run several seeds and compare; if the models disagree, the prediction is uncertain. For complexes look at the interface confidence (ipTM) and the PAE across the interface, not only the overall score. Plan memory: a few hundred residues fit a 16 GB GPU, a few thousand need 80 GB or tricks such as chunking.
Use the structure for what it is good for: forming hypotheses on function, choosing mutations to test, finding binding pockets, and guiding experiments (for example choosing constructs for crystallisation, or fitting a model into a cryo-EM map). Do not use a single predicted structure to estimate binding energy or to claim a mechanism without testing. For drug work add docking or molecular dynamics and always validate a sample in the lab.
For learning, read the AlphaFold 2 paper's supplementary methods (Evoformer and Invariant Point Attention are described as algorithms with pseudocode), run an open reimplementation, and study how the same attention ideas look in the L1 transformer concept. Keep a record of the database release, the model version and the licence for every structure you use in a publication.
quiz: What input does AlphaFold 2 need besides the target sequence, and why? || A multiple sequence alignment of related sequences (and optionally templates), because co-evolution between positions reveals which residues are in contact.
What does a low pLDDT score on a region usually mean? || The model has low confidence in the local structure; frequently the region is intrinsically disordered or flexible, so no single shape exists. It should not be trusted as a fixed structure.
Why is the pair representation updated with triangles? || Pairwise distances must satisfy geometric consistency (triangle inequality), so each pair's information is updated from the two other edges of every triangle that contains it.
How does the cost of triangle operations scale for a protein with 1,000 versus 300 residues? || It scales with \( N^3 \), so 1,000³ / 300³ is about 37 times more triples.
When would you rather get an experimental structure than rely on AlphaFold? || When the exact conformation or ligand state matters for an expensive decision, when confidence is low, when the region is flexible, or when the protein has few relatives and the prediction is unreliable.

@@ bitcoin
value: Bitcoin and Ethereum are the two largest public blockchains. A public blockchain is a ledger (a list of transactions and balances) copied on thousands of computers run by strangers, where anyone can join, anyone can submit a transaction, and nobody is in charge, yet everyone ends up agreeing on the same history. Before Bitcoin, distributed-systems theory said agreement among unknown participants who may lie was not practical: Paxos and Raft assume a fixed, known set of members, and Byzantine protocols need to count participants to count a majority. Bitcoin (a nine-page paper by "Satoshi Nakamoto" on 31 October 2008; first block on 3 January 2009) removed the need to know the participants. It counted computing power instead of identities, using proof of work.
The two systems do different jobs. Bitcoin is a ledger of coins: a transaction moves value between keys, its scripting language is deliberately limited, and the design goal is a predictable, hard-to-change monetary system with a fixed supply of 21 million coins. Ethereum (proposed by Vitalik Buterin in 2013, launched 30 July 2015) is a ledger of accounts plus a general-purpose virtual machine: anyone can deploy a program (a smart contract) that holds funds and runs when called, and every node executes it identically. This made it the base for token standards, decentralised exchanges, stablecoins and layer-2 networks. Ethereum switched from proof of work to proof of stake in the Merge on 15 September 2022; it has since shipped Dencun (March 2024), Pectra (May 2025) and Fusaka (3 December 2025). As of late October 2026 the next fork, Glamsterdam, is listed as in development for the fourth quarter of 2026, and Bitcoin Core 31.1 is the latest release series on bitcoincore.org.
For the layer above, public chains give a shared database with strong integrity and no operator: digital assets, payments across borders, programmable escrow, and audit logs that nobody can rewrite quietly. They stand on three things below. The blockchain concept (L1) supplies the append-only replicated ledger. Proof of work and proof of stake (L2) supply the mechanism that decides who may add the next block and makes rewriting history expensive. Content addressing and Merkle trees (L2) supply the hash links and the compact commitment of a block to its transactions, which lets light clients verify payments without downloading everything.
terms: Block — a batch of transactions plus a header; the header holds the hash of the previous block, a Merkle root of the transactions, a timestamp and the proof-of-work fields.
UTXO (unspent transaction output) — Bitcoin's accounting model: a transaction destroys earlier outputs and creates new ones, like cash notes being spent and change returned; there are no account balances.
Account model — Ethereum's accounting model: each address has a balance, a transaction counter (nonce) and, for contracts, code and storage.
Proof of work (PoW) — a block is valid only if its header hash is below a target, which can only be found by trying many nonces; it costs real energy.
Proof of stake (PoS) — validators lock coins as collateral, are chosen to propose and vote on blocks, and lose part of the stake (slashing) if they cheat.
Finality — the point after which a block will not be reverted; probabilistic in Bitcoin (more confirmations, lower risk) and explicit in Ethereum (after two epochs, about 13 minutes).
Gas — Ethereum's unit of computation; each operation costs gas, and the sender pays gas used times the gas price, which bounds the work any transaction can force on the network.
Smart contract — a program stored on the chain, executed by the Ethereum Virtual Machine (EVM) when a transaction calls it.
history: Digital cash was tried before. David Chaum's eCash (1980s) relied on a central bank to prevent double spending. Adam Back's Hashcash (1997) used proof of work to fight spam, and Wei Dai's b-money and Nick Szabo's bit gold (late 1990s) proposed chains of work. The missing piece was agreement: how can strangers agree which of two conflicting payments came first? Nakamoto's answer, published during the 2008 financial crisis, was to let participants vote with computing power on a single chain of blocks, where the longest chain (more exactly, the one with most accumulated work) wins. The genesis block carried a newspaper headline about bank bailouts. The first payment, of 10 coins to Hal Finney, followed on 12 January 2009.
Bitcoin's rules have changed slowly and with conflict. SegWit (2017) fixed transaction malleability and raised capacity through a "weight" limit; a block-size war ended with the Bitcoin Cash split in 2017. Taproot (activated November 2021) added Schnorr signatures and more flexible scripts. The subsidy per block halves every 210,000 blocks (about four years): 50 coins in 2009, 25 in 2012, 12.5 in 2016, 6.25 in 2020 and 3.125 since April 2024.
Ethereum's design came from the view that Bitcoin's script was too limited. Its launch in 2015 was followed by the DAO attack in 2016, in which a contract bug drained funds and the community split the chain (Ethereum and Ethereum Classic). EIP-1559 (August 2021) introduced a base fee that is burned. After years of research on proof of stake (the Gasper protocol, combining Casper FFG finality and LMD-GHOST fork choice) the Merge in September 2022 cut energy use by about 99.9%. Later upgrades moved scaling to layer-2 rollups: Dencun (2024) added cheap "blob" data for rollups, Pectra (2025) raised the maximum stake per validator to 2,048 ETH and added smart-account features for ordinary wallets, and Fusaka (December 2025) added PeerDAS, which lets nodes check blob availability by sampling.
how: Start with Bitcoin's transaction. An output is a locked amount of coin with a script saying who can spend it, usually "a signature matching this public key hash". A transaction lists inputs (references to earlier unspent outputs, each with a signature) and new outputs. Nodes check that the signatures are valid (ECDSA or Schnorr over the secp256k1 curve), that the inputs exist and are unspent, and that outputs do not exceed inputs; the difference is the fee for the miner. Valid transactions spread through a peer-to-peer gossip network into every node's waiting pool (the mempool).
A miner collects transactions into a block. The 80-byte header contains the version, the hash of the previous header, the Merkle root of the transactions, a time, a compact difficulty target and a 32-bit nonce. The Merkle tree (L2) hashes transactions pairwise up to one root, so the header commits to every transaction and a light client can verify one payment with a proof of about \( \log_2 n \) hashes (12 hashes for 4,096 transactions) without the whole block. Mining means computing SHA-256 twice over the header and checking whether the result, as a 256-bit number, is below the target. Since the hash is effectively random, the only way is to try nonces (and then other fields, such as the coinbase transaction, when nonces run out). The chance of success per try is \( \text{target} / 2^{256} \). The network retunes the target every 2,016 blocks so that the average time stays at ten minutes: if the last period took 12 days instead of the intended 14, the target is multiplied by 12/14, making blocks harder.
Why does this agree? Each node follows a simple rule: accept valid blocks, and always build on the valid chain with the most accumulated work. Two miners may find blocks at nearly the same time, creating a temporary fork; the next block extends one branch and the other is abandoned (its transactions return to the mempool). To rewrite a payment buried z blocks deep, an attacker must redo the work for that block and every later one while the honest majority keeps extending the real chain. If the attacker has a fraction q < ½ of the hash power, the chance of ever catching up falls exponentially with z. This is the property that makes proof of work (L2) useful: it turns the lie into a physical cost, in electricity and hardware, that must be larger than the gain. Rewards (new coins plus fees) make honest mining the profitable strategy.
Ethereum has a different state and a different consensus. State is a Merkle-Patricia trie mapping addresses to account data (balance, nonce, contract code and storage); each block header commits to the state root, so any piece of state can be proved with a short Merkle proof. A transaction calls a contract; every node runs the EVM, a stack machine, step by step, charging gas for each instruction; if gas runs out the call reverts. The block's gas limit caps total work per block. Since the Merge, blocks come from proof of stake: on the order of a million validators have each locked 32 ETH or more (up to 2,048 ETH per validator since Pectra); time is divided into 12-second slots and 32-slot epochs; in each slot one validator is chosen at random to propose a block and a committee votes on it. The fork choice follows the chain with most votes (LMD-GHOST), and a second layer of votes (Casper FFG) finalises checkpoints: after two epochs (about 13 minutes) reverting the chain would cost at least one third of all staked ETH, which is destroyed. Bad behaviour is punished by slashing, which replaces the cost of electricity with the cost of capital at risk.
Throughput is low by design. Bitcoin's weight limit of 4 million units gives roughly 3 to 7 transactions per second, and Ethereum's layer 1 about 15 to 30 for simple transfers, because every node must verify everything. Scaling therefore moves work elsewhere: Bitcoin's Lightning network keeps payments off-chain and settles later, and Ethereum rollups batch thousands of transactions, post compressed data in blobs and prove correctness. The base chain becomes a court of last resort that orders and settles disputes.

example: Work out what proof of work costs. Suppose the whole network computes 10²¹ hashes per second (a plausible order of magnitude for 2025 and 2026). In ten minutes (600 seconds) it performs 6 × 10²³ hashes, and by design that is the number needed on average to find one block. The success probability per hash is therefore about 1 / (6 × 10²³) = 1.7 × 10⁻²⁴, which means the 256-bit target has about log₂(6 × 10²³) = 79 leading zero bits. A single laptop at 10⁷ hashes per second would need 6 × 10²³ / 10⁷ = 6 × 10¹⁶ seconds, about 1.9 billion years, to find a block alone. This is why mining moved to specialised chips (ASICs).
Now the difficulty rule. Suppose 2,016 blocks arrive in 12 days instead of 14, which is 8.57 minutes per block, so the network was too fast. The new target is the old target × 12 / 14 = 0.857 × old. A smaller target makes each hash succeed with only 85.7% of its earlier probability, so blocks now take 1 / 0.857 = 1.167 times longer: 8.57 × 1.167 = 10 minutes. The rule is clamped to a factor of 4 per period, so one period cannot change difficulty too fast.
Next the security of confirmations. Take an attacker with 10% of the hash power (q = 0.1) trying to reverse a payment that has z confirmations. Using the calculation in the Bitcoin paper (the attacker's progress while z blocks are found, modelled as a Poisson process, then a random walk to catch up), the success probability is 20.5% for z = 1, 5.1% for z = 2, 1.3% for z = 3 and 0.024% for z = 6. With q = 0.3 the numbers are much worse: 62.8% for z = 1, 44.6% for z = 2, 32.5% for z = 3, 13.2% for z = 6, and still 4.2% for z = 10. With q ≥ 0.5, the attacker always wins eventually. That is why exchanges require more confirmations for larger deposits, and why six confirmations (about an hour) is the convention for high-value Bitcoin payments.
Finally, Ethereum's finality economics. Suppose 34 million ETH are staked and the price is $3,000 (an illustration, not a forecast). One third of the stake is 11.3 million ETH, worth $34 billion. To finalise two conflicting blocks an attacker must make at least a third of validators sign both, and the protocol can detect this and slash them. So reverting a finalised block costs on the order of tens of billions of dollars in destroyed stake, a cost that does not depend on how long ago the attack took place, unlike a proof-of-work chain, where the cost is the rental price of hash power.
intuition: Bitcoin is a notebook that everyone copies, where adding a page requires a puzzle that costs real electricity, so rewriting old pages means redoing all the puzzles since.
The design is natural once you accept that identity is impossible to verify on an open network. If votes are cast by identities, an attacker simply makes a million identities. If votes are cast by something that cannot be faked cheaply, like computation or locked money, each vote has a price, and an attacker needs more than half of the total price of the honest participants. Linking blocks with hashes makes any past change visible to everyone and forces the attacker to redo all later blocks. Merkle trees keep the headers small, so checking is cheap while forging is expensive. Ethereum adds the next step: if the ledger can be agreed, a program running on it can be agreed too, so every node runs the same code and all see the same results.
mistakes: People often think Bitcoin transactions are anonymous. In fact they are pseudonymous and public: every payment between addresses is visible forever, and analysis can link addresses to people when coins touch an exchange. Privacy needs extra tools and discipline.
People often think miners "solve complex mathematical problems". In fact the work is a brute-force search with no mathematical insight, finding a hash with leading zeros. The work is useful only as proof that energy was spent. Nothing is computed that could not be thrown away.
People often think a transaction is final when it appears in a block. In fact a block can be orphaned by a competing chain, so a single confirmation is weak. Bitcoin finality is probabilistic and rises with every block; Ethereum has explicit finality but only after about 13 minutes, and in between the block can still change.
People often think smart contracts are legal contracts or are "smart" in the sense of intelligent. In fact they are programs that run exactly as written, including their bugs, and cannot be fixed after deployment unless designed to be upgradeable. The DAO in 2016 and many later exploits lost funds because the code did what it said, not what its authors meant.
friction: The first limit is throughput and cost. Because every full node re-executes everything, base-layer capacity is small, and fees rise sharply when demand spikes. Layer-2 solutions help, but add complexity: bridges between layers have been the target of many of the largest thefts, and rollups still rely on sequencers or committees to varying degrees.
Energy and hardware: Bitcoin's proof of work uses on the order of 100 or more terawatt-hours per year by common estimates, as much as a medium-sized country, and that is by design, since the security budget is the energy. Mining concentrates in large pools and in regions with cheap power. Ethereum proof of stake uses a tiny amount of energy, but stake is concentrated in staking services and exchanges, and liquid-staking protocols raise questions about centralisation and about whether the largest operators could coordinate.
Governance is hard. Nobody can change the rules without agreement from node operators, miners or validators and users, so Bitcoin changes slowly and sometimes splits. Software bugs are costly and irreversible; key management is entirely the user's problem, and lost keys mean lost funds, while stolen keys mean stolen funds with no appeal. Smart-contract risk includes bugs, oracle manipulation and miner or validator extractable value (MEV), where those who order transactions profit by reordering them.
Finally, regulation and speculation dominate the public view. Rules on custody, taxes, securities law and anti-money-laundering vary by country and change often. Prices are volatile, and most trading volume is speculative; real-world payments and settlement use, while growing for stablecoins, remains smaller than the attention around the technology.
tradeoffs: Choose a public chain when you need a neutral shared ledger among parties that do not trust each other or any single operator, you need censorship resistance, or the asset itself is native to the chain. Choose a normal database (possibly with a signed, append-only audit log or a Merkle-tree transparency log) when one organisation controls the data or the parties already trust a common operator: it is thousands of times faster and cheaper. Many projects that use a blockchain would work better with a database; ask who the adversary is.
Choose Bitcoin when you want the simplest, most conservative design, a limited and predictable monetary policy, and the strongest proof-of-work security record. Choose Ethereum (or an Ethereum layer 2) when you need programmable logic, tokens or composability with existing contracts. Choose a permissioned chain (Hyperledger Fabric and similar) only when participants are known and you need shared control; then the open-membership benefits disappear and a replicated database with consensus (Raft or BFT) may be enough.
Choose layer 1 for high-value settlement and final custody, accepting low throughput and higher fees. Choose a rollup for frequent, small transactions, accepting extra trust assumptions in bridges and sequencers and a longer withdrawal path. Choose to run your own node when you must verify rather than trust a provider; choose a hosted node API for convenience at the cost of trusting it and being rate-limited.
Choose more confirmations for larger payments (for Bitcoin 1 for small amounts, 6 or more for large ones; for Ethereum wait for finality for high-value transfers). You give up speed in exchange for lower reversal risk. For PoW versus PoS in design terms: PoW ties security to external energy cost and has simpler assumptions, while PoS gives faster finality and low energy use, but depends on well-designed incentives, weak-subjectivity checkpoints for new nodes, and a large and spread-out stake.
interview: How does Bitcoin prevent double spending without a central party? || Each node validates every transaction against its record of unspent outputs and rejects an input spent twice in the same chain. When two conflicting transactions exist, nodes follow the valid chain with most accumulated proof of work; the first to be buried under blocks wins and the other becomes invalid. Reversing a confirmed payment would need redoing the work of all blocks since, which needs a majority of hash power to be reliable.
Why does the probability of reversing a payment fall exponentially with confirmations, and when does it fail? || The attacker's chain must overtake the honest chain; with fraction \( q < \tfrac{1}{2} \) of the hash rate, the lead is a biased random walk and the catch-up probability is \( (q/p)^z \) for a deficit z, so each block multiplies it by \( q/p < 1 \). It fails if the attacker holds \( q \ge \tfrac{1}{2} \), or if the network is partitioned so honest nodes split their power. Selfish mining also lowers the effective threshold below 50% in some models.
Compare proof of work and proof of stake security. What does an attack cost in each? || In PoW, the attacker needs to control more hash power than the honest network for the attack period, so the cost is hardware and energy (rented or owned) and is ongoing. In PoS (Ethereum), finality requires two-thirds of stake; reverting a finalised block needs at least one third of stake to equivocate, and it can be detected and slashed, so the cost is destroyed capital. PoS has a long-range and weak-subjectivity issue for new nodes, which checkpoints address.
A Merkle proof shows a transaction is in a block. How big is it and what does a light client trust? || For n transactions the proof has about \( \log_2 n \) sibling hashes (12 × 32 bytes for 4,096 transactions) and the client recomputes the path to the root in the header. The client trusts that the header chain it follows has the most work (or the finalised checkpoint in Ethereum), so it needs only headers (80 bytes each), not full blocks. It cannot check that all transactions in the block are valid, only that one is included.
You must accept Bitcoin payments in a service. What would your design include? || Use a reputable full node or provider, derive a fresh address per invoice, store only public keys on the server (use an HSM or cold storage for spending keys), define confirmation thresholds by amount, handle reorgs by tracking transactions by ID until final, set fee estimation and replace-by-fee handling, make credits idempotent, and reconcile with the chain regularly. Consider a stablecoin or Lightning for small payments.
practice: Decide first whether you need a chain at all. If one party can run the database, use a database, perhaps with a signed append-only log or a Merkle-tree transparency log, which gives tamper evidence without consensus. If you do need a public chain, use it for what it is good at: settlement, ownership records and shared state among parties who do not trust each other, with data kept off-chain and only hashes or commitments on-chain.
When you integrate payments, run or rent a reliable node and verify rather than trust. Generate a new address for every invoice, keep spending keys in an HSM or cold storage, and never keep secret keys in application servers. Track each payment by transaction ID and state (seen, in a block, confirmed, final). Make crediting idempotent, handle reorganisations by being able to roll back a credit, and set confirmation thresholds by value. Estimate fees from the mempool, support fee bumping, and monitor for stuck transactions.
For smart contracts, treat code as irreversible: use audited libraries, keep contracts small, write tests that include adversarial cases, use formal tools or fuzzing, add pause and upgrade paths with strong governance only where needed, and limit funds at risk. Estimate gas in tests, think about front-running and MEV, and prefer pull payments to push payments. For scale, use a rollup and keep a plan for bridge failures.
To learn, read the Bitcoin paper (nine pages), then the Princeton book or Stanford CS251, then run a node and inspect blocks with a command-line tool (bitcoin-cli getblock, or an Ethereum client's JSON-RPC). Reading real transactions and Merkle proofs teaches more than any diagram.
quiz: What does a Bitcoin block header commit to? || The previous block's hash, the Merkle root of the transactions, a timestamp, the difficulty target and a nonce, so changing any transaction or earlier block changes the header hash.
How often does Bitcoin adjust difficulty and why? || Every 2,016 blocks (about two weeks), by scaling the target according to how long they took, so the average block time stays near ten minutes whatever the total hash power.
What is the difference between UTXO and the account model? || UTXO (Bitcoin) tracks unspent outputs that are consumed and created by transactions; the account model (Ethereum) keeps a balance, a nonce and for contracts code and storage per address, updated in place.
With 10²¹ hashes per second, about how many leading zero bits must a block hash have on average? || The network does 6 × 10²³ hashes in 600 seconds, so a success chance of about 1 in 6 × 10²³, which is about 2⁷⁹, or around 79 leading zero bits.
When would a normal database be a better choice than a blockchain? || When one organisation controls the data, or the parties already trust a common operator, because you then get far higher throughput, lower cost, easier changes and privacy without the cost of decentralised consensus.

@@ codingagents
value: A coding agent is a program that lets a language model work on a software project by itself. You give it a goal in plain language ("fix the failing checkout test", "migrate this service to the new logging library"). It then reads files, searches the code, edits files, runs commands such as the build and the tests, reads the output, and repeats until it believes the goal is met or it needs your decision. The two best-known terminal-based products are Claude Code (Anthropic, research preview February 2025) and Codex (OpenAI; a command-line tool and cloud agent from 2025, now also inside the ChatGPT apps). Both also exist as IDE extensions, desktop apps, web and mobile versions, and can run in continuous integration.
The change this brings is a different split of work. Before, the developer typed code and the tool completed a few lines. Now the developer specifies the task and the checks, and reviews a finished change; the agent does the typing, searching and trial and error. This works because three things became true together: models that can plan over many steps and call tools reliably, a standard way to give them tools, and test suites that tell the agent whether it is right. METR, an evaluation group, measured that the length of software tasks (in human working time) that frontier agents complete at 50% success doubled roughly every seven months in 2024 and 2025.
Coding agents stand on four concepts. The agent loop (L1) is the control structure: model call, tool call, result, repeat. Claude (L0) and GPT (L0) are the models that do the planning and write the code; Codex is tuned for OpenAI models, Claude Code for Claude models. MCP (L0) is the protocol that lets the agent use external tools and data (issue trackers, databases, browsers, design tools) through one interface instead of custom integrations. As of October 2026 Claude Code runs on the Claude 5.5 models and Codex on GPT-6.1 Sol with an optional faster mode, and both are closed products, though Codex's command-line client was released as open source in 2025.
terms: Harness — the program around the model: it holds the system prompt, defines the tools, runs them, enforces permissions, manages the context and feeds results back.
Tool call — a structured request from the model (name plus arguments, such as Bash with a command) that the harness executes.
Context window — the tokens the model can see in one request; the whole conversation, tool results and instructions must fit, so managing it is the central engineering problem.
Compaction — replacing the older part of the conversation with a model-written summary when the context gets full.
Subagent — a separate agent run with its own fresh context, given one sub-task; it returns only a short result to the main agent.
Project instruction file — a markdown file (CLAUDE.md, AGENTS.md) that is loaded at the start of every session with build commands, conventions and warnings.
Sandbox and permission mode — limits on what the agent may do without asking: which files it can write, which commands run, whether network access is on.
Hook — a deterministic script that the harness runs at a lifecycle event (before a tool call, after an edit), to enforce a rule that should not depend on the model's judgement.
history: Language models first completed code in 2021: OpenAI's Codex model (Chen et al., 2021) powered GitHub Copilot, which suggested the next lines in an editor. SWE-bench (Jimenez et al., ICLR 2024) then turned the question into "can a model fix real GitHub issues in real repositories?" using 2,294 tasks with hidden tests; at first the best systems solved a few percent. Research agents such as SWE-agent (Princeton, 2024) showed that giving the model a good interface, a shell and file viewer and editor designed for models, mattered as much as the model. Devin (Cognition, March 2024) packaged the idea as an autonomous engineer, and Aider and others offered open-source command-line versions.
In late 2024 and 2025 the models improved at long tool-using tasks, and the products arrived. Anthropic released Claude Code as a research preview with Claude 3.7 Sonnet in February 2025 and made it generally available with Claude 4 in May 2025. OpenAI released the Codex CLI in April 2025 and the cloud Codex agent in May 2025; Google released Gemini CLI in June 2025. The Model Context Protocol, published by Anthropic in November 2024, was adopted by all of them. The top scores on SWE-bench Verified (a 500-task subset checked by humans) passed 70% in 2025, so the field moved to harder, longer benchmarks and to measuring real engineering work.
Through 2026 the products grew from a terminal tool into platforms. Claude Code now runs in the terminal, VS Code, JetBrains, a desktop app and the web, supports skills, hooks, subagents, scheduled and background agents, an Agent SDK and GitHub and GitLab integration. Codex runs from the ChatGPT apps, a CLI, an IDE extension and a cloud environment, and supports AGENTS.md, subagents, skills and plugins, sandbox profiles and automatic review of approvals. In October 2026 Anthropic donated the Agent Skills format to the Agentic AI Foundation, which signals that the packaging of agent capabilities is becoming a shared standard like MCP. Why did it all happen at once? Reinforcement learning on real software tasks, with tests as rewards, made models much better at the loop itself.
how: The core is a loop. The harness starts a conversation with a system prompt that describes the tools and rules, adds the instruction files (CLAUDE.md or AGENTS.md) and your request, and calls the model. The model replies with text and possibly tool calls. Typical tools are: read a file, search by pattern (grep, glob), edit a file, write a file, run a shell command, fetch a web page, ask the user a question, and start a subagent. For each tool call the harness checks permissions, runs the tool, and appends the result as the next message. Then it calls the model again. The loop ends when the model replies without a tool call, which means it considers the work done. This is the agent concept (L1) in its simplest, most successful form: no complex planner, a capable model and good tools.
Tools define what the agent can do, so their design matters. Editing is a good example. Claude Code's edit tool asks for an exact string to replace and fails if the string is not unique, which forces the model to read the file first and avoids overwriting the wrong place. Codex uses a patch format. Both prefer small, checkable edits to rewriting whole files. The shell tool gives the agent everything a developer has: compilers, test runners, git, package managers. Search tools matter more than they seem; instead of loading the whole repository, the agent uses grep and file listings to find the few relevant files, a style called agentic search. Some products also add semantic indexes, but the main pattern is "look, then read".
MCP (L0) extends the tool set without changing the harness. An MCP server is a small program that exposes tools, data resources and prompt templates over JSON-RPC, through standard input and output locally or HTTP remotely. The agent lists the server's tools, and their descriptions and schemas join the model's tool list. A single server for GitHub, Jira, Postgres or a browser then works with Claude Code, Codex, Cursor and others; the integration cost goes from N × M to N + M. The price is context: every tool description occupies tokens, so harnesses load tool descriptions lazily or search them on demand.
Context is the scarce resource. A 1M-token window sounds large, but each turn adds file contents and command output, and quality drops when the context is cluttered. Harnesses use several methods. Prompt caching keeps the stable prefix cheap. Compaction summarises old turns when the window nears its limit. Subagents run a big search or a code review in a separate context and return a short report, so the main context stays clean. Instruction files carry knowledge that survives across sessions, and an automatic memory feature records learned facts such as build commands. Plans written to a file let work resume after compaction.
Control and safety come from permissions, sandboxes and hooks. By default the agent asks before running commands or editing files, and you can allow patterns (for example "run npm test") or switch to modes where it plans first, accepts edits, or runs without asking in an isolated environment. Operating-system sandboxes limit file and network access for shell commands. Hooks run your scripts at events, so "format after each edit" or "block writes to the migrations folder" is enforced by code and not by a request in the prompt. Checkpoints and git let you rewind. The cloud versions run the agent in a container with a copy of the repository, which is the safest place for long autonomous work.
Verification closes the loop. The most important rule is to give the agent a way to check itself: a test command, a linter, a type checker, a script that reproduces the bug. The model runs it, reads the failure and fixes the cause. Without checks, the agent can only guess whether it succeeded. This is why reinforcement learning with tests as rewards improved these models so much, and why the best advice is to invest in your tests and not in clever prompts.
The model itself was shaped for this loop, and this is where the Claude and GPT concepts contribute most. After pretraining, the labs run reinforcement learning in thousands of simulated software environments (a repository, a task, a test suite as the grader), so the model learns the habits that make the loop converge: read before editing, run the tests, look at the actual error, make a small change, and stop when the check passes. It also learns to write tool calls in the exact format the harness expects, which is why each product works best with its own lab's models. Reasoning ("thinking") is used mostly at the start of a task, to form a plan, and again after surprising results, so effort settings let you trade cost against care. Skills, a newer packaging format, add to this: a skill is a folder with instructions and optional scripts that the agent loads only when relevant, so team knowledge such as "how we cut a release" costs no context until it is needed.

example: Follow a small task: "The test test_discount_applies_once fails; fix it." Approximate token counts show how context grows. The fixed prefix (system prompt, tool definitions, instruction file) is 12,000 tokens.
Step 1: the model runs the test command. The output is 600 tokens (a stack trace saying that the discount was applied twice). Context: 12,000 + 150 (request) + 600 = about 12,750.
Step 2: it runs a search for "apply_discount" and finds 3 files. Result 300 tokens. Context 13,050.
Step 3: it reads the 220-line pricing file: 2,500 tokens. Context 15,550.
Step 4: it reads the test file: 1,200 tokens. Context 16,750. At this point the model sees that the order object calls apply_discount in both the cart total and the checkout step.
Step 5: it edits one function with an exact replacement: 400 tokens for the edit and its confirmation. Context 17,150.
Step 6: it reruns the tests: 200 tokens, all pass. It also runs the whole test suite, which prints 900 tokens with one unrelated failure that already existed (it checks with git stash and reruns to confirm). Context about 19,000.
Step 7: it summarises the change in 250 tokens and stops. Seven model calls with a context of 12,750 to 19,000 tokens each. Without caching, input tokens billed are roughly 12,750 + 13,050 + 15,550 + 16,750 + 17,150 + 17,350 + 19,000 = about 111,600. With caching the stable 12,000-token prefix is read at a small fraction of price on six of the seven calls.
Now think about errors. A single run of seven steps with 98% reliability per step succeeds with 0.98⁷ = 87%. A long migration of 40 steps at the same reliability succeeds only 0.98⁴⁰ = 45% of the time, and at 99.5% per step 82%. That is why the harness encourages checkpoints, tests after each change, and short tasks that end in a reviewable commit. Splitting a 40-step job into four independent 10-step tasks, each verified by tests, turns one fragile run into four likely ones, and errors stop at the test boundary.
Last, the subagent effect. A code review needs to read 30 files, about 60,000 tokens. Done in the main thread it adds 60,000 tokens to every later call. Done in a subagent, the main context grows only by its 500-token report, a saving of 59,500 tokens on each of the remaining calls. If 20 calls remain, that is 1.2 million input tokens avoided, and a cleaner context for the model.
intuition: A coding agent is a junior colleague with a terminal, a very fast reading speed and no memory between days, who is told exactly how to check their own work.
The design is natural because software has something most work lacks: a cheap, automatic judge. Code either compiles and passes tests or it does not. A model that can propose, act and observe the judge's verdict can improve its work in a loop, without a human in every step. The parts match the parts of human work: search tools are looking around the codebase, the shell is trying things, the instruction file is the team wiki, subagents are asking a colleague to investigate, and permissions are the manager deciding what needs sign-off. The human role moves from typing to defining goals and checks, and to reviewing.
mistakes: People often think a coding agent is just autocomplete with a chat window. In fact autocomplete predicts the next few tokens with your cursor as the only context; an agent decides what to read, runs your tests, edits many files and iterates. They need different habits: autocomplete is reviewed line by line, agents are reviewed as pull requests.
People often think a bigger context window removes the need for context management. In fact long, cluttered contexts reduce accuracy and raise cost, since every turn re-reads all of it. Good agent use keeps context small: targeted search, subagents, compaction, and clear tasks.
People often think the agent's claim that tests pass is evidence. In fact the model reports what it saw in tool output, and can misread it, skip a test, or modify the test to make it pass. Run the checks yourself in CI and review the diff, including changes to tests.
People often think the instruction file is a place for everything. In fact a long CLAUDE.md or AGENTS.md is loaded in every session and uses context; put in it the short list of commands, conventions and traps the agent cannot discover from the code, and link to details. Rules that must always hold belong in hooks and CI, not in prose.
friction: Confident mistakes are the main problem. Agents can produce plausible code that is subtly wrong, duplicate existing helpers because they did not find them, over-engineer, or "fix" a failing test by weakening it. They do not know your unwritten requirements. Review burden is real: a fast agent can produce more diff than a human can check, so the bottleneck moves to review and test quality.
Large codebases strain the loop. Searching a monorepo with millions of lines finds many false matches; the agent may not discover the right abstraction or the conventions in distant modules. Long tasks exceed the context and depend on compaction, which loses details, so progress files and small tasks matter. Non-determinism makes bugs hard to reproduce: the same prompt yields different paths.
Security needs care. An agent with a shell and your credentials is powerful. Prompt injection (instructions hidden in a web page, an issue, a dependency's README or a tool result) can make it exfiltrate secrets or run harmful commands; tool servers from MCP are third-party code. Sandboxes, narrow credentials, network limits and approval for risky commands reduce the risk but do not remove it. Supply-chain issues (the agent installing a package suggested by the model that does not exist, or is malicious) are a documented risk.
Cost and dependence also matter. Long agent sessions use millions of input tokens; subscription limits and API bills need tracking. Models and harnesses change monthly, so prompts and workflows that worked can degrade after an update. Finally, skill atrophy and onboarding are open questions: if juniors never write the first versions, how do they learn to judge them?
tradeoffs: Choose a terminal or cloud agent (Claude Code, Codex) when the task spans many files, needs commands and tests, and can be described with a clear check: migrations, bug fixes with a reproduction, test writing, dependency upgrades. Choose editor completion or inline chat when you are in the middle of writing a function and want to stay in flow; it is faster for small edits and cheaper. You give up autonomy in exchange for tighter control.
Choose local interactive mode when the task is ambiguous or risky and you want to steer; choose a background or cloud run when the task is well specified, takes more than a few minutes, and can be reviewed as a pull request. Cloud runs are isolated and parallel but have no access to your machine's state, secrets or private network unless you provide them.
Choose a stricter permission mode (ask for each command) on unfamiliar repositories and production-adjacent work; choose allow-lists or sandboxed auto-run for trusted, test-covered projects. More autonomy saves minutes per task but increases the chance and cost of an error; pair it with git checkpoints and CI.
Choose subagents for independent searches and reviews to protect context, and a single agent when steps depend closely on each other. Choose Claude or GPT models by running your own tasks: the better model on public benchmarks may not be better on your code. Choose MCP servers sparingly: each one adds tool descriptions and a new trust boundary.
interview: Describe the architecture of a coding agent and what makes it work or fail. || A loop around a model: the harness sends system prompt, tool schemas, instructions and history; the model returns tool calls; the harness checks permissions, executes them (read, search, edit, shell), and appends results. It ends when the model stops calling tools. Success depends on tool design, context management, and verification signals such as tests. Failures come from cluttered context, missing checks, and error compounding over many steps.
How would you manage context in a long refactor? || Keep the stable prefix cached; use targeted search over reading whole files; delegate broad reading and reviews to subagents; write a plan and progress notes to a file so work survives compaction; commit in small steps so state lives in git, not in the conversation; and start a fresh session for each independent chunk.
What is prompt injection in the coding-agent setting and how do you reduce the risk? || Untrusted text read by the agent (a web page, an issue comment, a README, a tool result) contains instructions that the model may follow. Reduce impact with sandboxes, minimal credentials, network allow-lists, approval for dangerous commands, hooks that block specific actions, vetting MCP servers, and treating agent output as untrusted until reviewed. You cannot rely on the model alone to refuse.
The agent says all tests pass but a bug reaches production. What do you check? || Whether the agent ran the real test command, whether it changed or skipped tests, whether tests cover the behaviour, and whether CI agrees. Review the diff for test edits, mocks that hide the problem, or weakened assertions. Then fix the process: required CI, coverage on the touched code, and a review checklist for agent-written changes.
How would you introduce coding agents to a team of 25 engineers with a large codebase? || Start with a pilot on bounded tasks (tests, migrations, bug fixes) with measured outcomes: cycle time, review time, defect rate, cost. Write shared instruction files and skills, set permission and sandbox policy, require CI and human review, restrict secrets, and train people on prompting for checks. Expand only where the metrics improve; track the review load, since the bottleneck moves there.
practice: Write a short instruction file for each repository: the exact commands to build, run one test and run the full suite; the layout of the code; conventions that are not obvious from the code; and things never to do. Keep it under a page and update it when the agent makes a repeated mistake. Put rules that must never be broken into hooks or CI.
Give every task a check. State the goal and how to verify it ("make this failing test pass, do not change the test; run the full suite at the end"). Start with plan mode for anything larger than a small change: read the plan, correct it, then let the agent execute. Keep tasks small enough to end in one reviewable commit, and ask for a commit after each step so git holds the state.
Control cost and context: use targeted prompts that name the relevant files, start a new session for an unrelated task, use subagents for broad searches and reviews, and watch the context meter. Choose the model and effort per task; use a cheaper model for mechanical edits and the strongest one for design and debugging.
Protect yourself. Run unfamiliar code in a sandbox or cloud environment, keep production credentials out of reach, allow only the commands you understand, review MCP servers like any dependency, and read the diff before merging, including test changes. Measure results: lead time, review time, escaped defects and token cost per merged change, and compare with your baseline before widening use.
For a team, standardise: shared skills and commands in the repository, an agreed permission policy, AGENTS.md so that several agents (Claude Code, Codex, Cursor) read the same instructions, and a short review checklist for agent-written changes.

value: Cursor and GitHub Copilot are code editors, or editor extensions, that have a language model built in. They sit where developers already work (a window with files, a cursor and a terminal) and use the model in three ways. Inline completion suggests the next lines, or the next edit, as you type. Chat answers questions about the open code and the whole repository. Agent mode takes a task, searches the code, edits several files, runs commands and tests, and shows you a diff to accept or reject.
The two products have different roots. GitHub Copilot started in June 2021 as a technical preview, using OpenAI's Codex model inside Visual Studio Code, and became generally available in June 2022; today it is a plugin family for many editors with chat, an agent mode and a cloud agent that can be assigned a GitHub issue, and it offers models from several vendors. Cursor (company: Anysphere, founded in 2022 by four MIT students) is a fork of Visual Studio Code rebuilt around AI. It grew very quickly; reported annual recurring revenue passed $100 million in January 2025, $1 billion by late 2025 and about $3 billion by May 2026. In 2026 it changed owner: xAI announced a right to buy it in April, SpaceX announced the $60 billion all-stock purchase in June, and Cursor said on 14 August 2026 that the acquisition had closed. Cursor says its policies do not change, and its blog now lists Grok 4.6 (12 August) and Grok 4.7 (21 September) among models introduced by the Cursor team, next to its own Composer models and models from other labs.
For the layer above, the editor-based agent is how most developers meet AI coding: it keeps the human in the loop with fast visual diffs. It stands on three things below. The agent loop (L1) is the engine of agent mode. Claude (L0) and GPT (L0) are among the models behind chat, edits and agents; developers choose per task, which is why such editors often support models from Anthropic, OpenAI, Google and others. Coding agents such as Claude Code and Codex (the neighbour concept) use the same loop in a terminal; Claude Code's documentation offers an extension that installs in Cursor, so the two styles are often combined.
terms: Tab completion — a model that predicts your next edit (often several lines, and the next cursor position), not only the next token.
Codebase index — an embedding-based search structure over your repository, built so the editor can retrieve relevant code for a question.
Embedding — a vector of numbers (for example 1,536) that represents the meaning of a text chunk; similar chunks have vectors with a high cosine similarity.
Apply model — a fast, specialised model that takes a suggested change from a big model and rewrites the file accurately, so you see an actual diff.
Agent mode — the editor runs the model in a loop with tools: search, read, edit, terminal, and optionally web and MCP tools.
Rules — project instruction files (for example .cursor/rules or AGENTS.md) that the editor adds to every request.
Cloud (background) agent — an agent that works in a remote copy of the repository, in parallel to you, and returns a branch or pull request.
Checkpoint — a saved state of the files before an agent change, so you can restore it.
history: AI completion in editors began with statistical tools (TabNine, 2018) and then neural models. GitHub Copilot (2021) showed that a code-trained language model, OpenAI's Codex (described by Chen et al., 2021), could write useful functions from comments and neighbouring code; the paper reported that Codex solved 28.8% of the HumanEval problems on the first try, and 70.2% when allowed 100 samples. Copilot Chat (2023) added conversation, and in 2024 Copilot started to offer non-OpenAI models.
Cursor appeared in 2023 on a different bet: owning the whole editor lets you show edits as diffs, track what you look at, run commands, and design the interface for model output. In 2024 it introduced multi-file edits ("Composer" mode, later agent mode), trained its own tab-completion and fast-apply models, and offered Claude and GPT models at launch. Developers widely credited Claude 3.5 Sonnet (mid-2024) with making agent-style edits reliable enough to use daily. Through 2025 the work shifted from "suggest" to "delegate": Cursor 2.0 (October 2025) added parallel agents and its own agentic coding model, Composer. Composer 2 (March 2026) was built by continuing the pretraining of an open model (Kimi K2.5) and then applying large-scale reinforcement learning; Composer 2.5 followed in May 2026. GitHub added agent mode in VS Code in early 2025 and a cloud coding agent in May 2025.
The autumn of 2026 shows where the category is going. Cursor's changelog lists Projects (10 September, beta: a coordinator agent plans a large piece of work and delegates it to implementing agents in the cloud), Rollouts and Security Review for pull requests (23 September), remote control of local agents from the phone (6 October), and an app marketplace and cloud-agent canvases (13 and 16 October). The editor is turning into an orchestration surface for many agents, and the review of their work is becoming the main task.
how: Three technical systems work together: completion, retrieval and edit application, with the agent loop on top. Start with completion. Cursor's Tab model is not a general chat model. It is a smaller model trained to predict your next edit given the file, recent changes and cursor position, so it can suggest multi-line changes, insertions in the middle of a line, and the next place to jump to. Latency is the main constraint: a suggestion that arrives after 500 ms interrupts typing, so these models are small, run on dedicated servers, reuse cached prefixes of the file, and are tuned for speed. This is a different workload from chat, which tolerates seconds.
Retrieval answers "what code should the model see?". A model cannot read a repository of 500,000 lines in each request. The editor splits files into chunks of a few hundred tokens, computes an embedding for each chunk and stores the vectors in a searchable index. Cursor's documentation describes that it keeps this index in sync by hashing files into a Merkle tree (L2 concept: content addressing), so when you edit one file only its path in the tree changes and only that file's chunks are re-embedded. At question time the editor embeds your query, finds the nearest chunks, and combines them with other signals: open files, recent edits, linter errors, git diff, and symbols you mention with @. In agent mode the model can also call search tools (grep, file listing, semantic search) and read exactly what it needs, as terminal agents do. Context assembly is therefore a mix of automatic selection and the model's own exploration.
The apply step solves a practical problem. A large model can describe an edit but may output only a snippet ("... existing code ...") or a malformed patch. Rewriting a full 500-line file token by token with a big model is slow (a 6,000-token file at 70 tokens per second takes about 85 seconds). Cursor described training a specialised fast-apply model that takes the original file and the proposed change and outputs the full new file, and using speculative decoding with the original file as the draft: since most of the output is identical to the input, many tokens are checked in parallel and accepted at once. Cursor reported speeds around 1,000 tokens per second with this approach. The user sees the diff almost at once. This is the contribution of the lower inference layer: the cost model of decoding (memory-bound, one token at a time) is turned into a parallel check.
Agent mode is the loop from the coding-agents concept inside the editor. The model receives the task, rules and retrieved context, and a set of tools: read file, search, edit, run terminal command, browse, and any MCP tools. It calls them, the editor shows each step, applies edits as diffs, and runs commands with permission rules (allow lists, or ask each time). Checkpoints let you restore the pre-edit state. Linter and compiler errors are fed back automatically, so the model corrects its own syntax and type errors. The editor setting gives agent mode some advantages over a terminal agent: it knows what files you have open, the cursor position, the diagnostics from language servers, and it can show a rich diff for review.
Models are chosen per request. The product routes between its own models (a small model for tab, a fast one for apply, Composer or Grok models for agents) and third-party models such as Claude and GPT. Cursor describes a router that selects a model for the task. Claude and GPT (L0) contribute the long-horizon planning and code quality for the hardest steps, while the in-house models make common steps fast and cheap. Cloud agents run the same loop in remote containers, with a copy of the repository, so many can run in parallel and report as pull requests. Bugbot, Security Review and Rollouts apply the loop to pull-request review and deployment monitoring. Settings and rules are layered: user rules, project rules in the repository and per-request mentions are concatenated into the prompt in a fixed order, so the same instructions reach whichever model is chosen. Privacy mode is meant to limit what is retained, so check the vendor's current terms on storage and training use; the text of each request must still be sent to be answered. For enterprises, admins can restrict which models, tools and commands are allowed, and audit logs record agent actions, which turns the editor into a managed surface and not only a personal tool.

example: Size the codebase index for a 100,000-line repository. At about 10 tokens per line the code is about 1 million tokens. With chunks of 500 tokens, that is about 2,000 chunks. Each embedding with 1,536 dimensions stored as 4-byte floats takes 6,144 bytes, so the index is 2,000 × 6 KB = about 12 MB. Searching it is a matrix product of one query vector against 2,000 vectors: about 3 million multiply-adds, microseconds on a CPU. The expensive part is creating the embeddings, 1 million tokens through an embedding model once, then only changed chunks. If you change one file in a 5,000-file repository, a Merkle tree with fan-out 2 has about log₂ 5,000 = 13 levels, so only 13 hashes along the path are recomputed to find what changed.
Now the context budget for one agent request, in tokens. System prompt and tool descriptions: 8,000. Rules files: 1,500. Open files: 6,000. Retrieved chunks: 8 × 500 = 4,000. Conversation so far: 5,000. Your request: 200. The total is 24,700 tokens, of which the first 9,500 are stable between requests and can be cached. The model then spends maybe 1,500 tokens on output. If you add 10 MCP tools with 400-token descriptions, that is 4,000 more tokens in every request, a 16% increase, so one should connect only tools that are needed.
Next the apply speed. A 6,000-token file rewritten by a large model at 70 tokens per second takes 6,000 / 70 = 86 seconds. At 1,000 tokens per second with speculative edits, 6 seconds. Why is it faster? Normal decoding produces one token per forward pass. In speculative editing, the original file's next 20 tokens are proposed as a draft and the model verifies all 20 in one forward pass; when the draft is right (most of the unchanged text), 20 tokens are accepted at once. Where the edit begins, the draft fails, the model produces its own tokens for a stretch, and then the draft is resumed. If 90% of the file is unchanged, the number of forward passes falls by up to about 10 times, matching the order of the reported speed-up.
Finally, accept rates. Suppose Tab shows 100 suggestions in an hour, you accept 25 and each accepted suggestion saves 8 seconds of typing: 200 seconds saved. If each rejected suggestion costs 1 second of distraction, 75 seconds are lost. The net gain is 125 seconds per hour, which is small; the value of an editor agent comes from the larger tasks. Measure on your own work.
intuition: The editor is a cockpit: autopilot (the agent) can fly the plane, but the pilot sees the instruments (diffs, tests, diagnostics) and can take control at any moment.
The design is natural because the editor is where the context lives. It already knows what is open, what changed, which lines have errors and what the language server says about types. A model with that information needs fewer tokens and less guessing than a model that starts from a prompt. The human is already watching this window, so diffs and one-click accept make review cheap, and fast small models can respond at typing speed. A terminal agent trades that tight loop for freedom and parallelism. Both are the same idea: a model in a loop with tools and a check.
mistakes: People often think Cursor and Copilot are only wrappers around a chat API. In fact much of the product is the system around the model: a fast completion model, a retrieval index, an apply model, diff and checkpoint tooling, and for Cursor its own agentic models. The same underlying LLM can feel very different in two products because of context selection and tools.
People often think the codebase index sends your whole code to the model. In fact an index stores embeddings of chunks for search, and only the chunks selected for a request are included in the prompt. Companies should still read the privacy mode and data retention terms, because retrieved code does leave your machine to reach the model provider.
People often think more context is always better. In fact adding many files or tools increases cost and can distract the model. Precise @-mentions, short rules and a clear task often beat dumping the repository.
People often think accepting suggestions is the same as writing code yourself. In fact accepted code still needs review, tests and understanding. Studies and surveys show a gap between the feeling of speed and measured delivery; the benefit depends on task type, codebase familiarity and review discipline.
friction: Quality limits remain. Suggestions can be subtly wrong, use APIs that do not exist, or ignore conventions in far-away files. In large monorepos, retrieval misses relevant code, and agents may duplicate helpers. Review fatigue is real: accepting many suggestions quickly can let defects through.
Dependence and change are also frictions. The product relies on third-party models whose behaviour, prices and rate limits change, and on the editor vendor's pricing (usage-based plans changed several times). Cursor is a fork of VS Code, so it must keep up with upstream changes and extension compatibility. Its ownership changed in August 2026, and teams that standardise on it should track the roadmap, terms and model availability, especially if they have procurement rules about vendors.
Security and IP policy need attention: code is sent to model providers unless you use an enterprise zero-retention arrangement; agents with terminal access can run harmful commands, be steered by prompt injection from web pages or files, or install malicious packages; rules files and MCP servers are executable influence on the agent. Enterprises need admin controls, audit logs, and policies on which models and tools are allowed.
Finally, the workflow is still evolving: many parallel agents create merge conflicts and a flood of pull requests, and the human becomes the bottleneck. Features such as Projects and Rollouts try to manage this, but evidence of net productivity gains at scale is still being gathered.
tradeoffs: Choose an editor-first tool (Cursor, Copilot in VS Code) when you work interactively, want fast visual diffs, tab completion and tight feedback while you steer. Choose a terminal or cloud agent (Claude Code, Codex) when tasks are larger, well specified and can run unattended, or when you work over SSH or in CI. Many developers use both: the editor for the daily loop, the terminal agent for big mechanical jobs. You trade tight control for autonomy.
Choose Cursor when you want the most agent-focused editor and fast-moving features, and accept a fork of VS Code and a vendor that changes plans; choose GitHub Copilot when you are already standardised on GitHub, need enterprise controls in your existing contract, and want it inside many editors (VS Code, JetBrains, Visual Studio, Neovim). The difference is mostly in integration and policy, not in the underlying model, since both offer several vendors' models.
Choose a strong frontier model for planning, debugging and multi-file design, and a small fast model for completion and mechanical edits; the cost per request differs by 10 times or more, and the editor's router or your own selection decides where to spend. Choose auto-accept only in small, test-covered tasks; choose reviewing every diff on production code.
Choose local index and strict privacy mode when code is sensitive; choose cloud agents when you need parallel work and are comfortable with repository access in a remote sandbox. You give up some convenience with stricter modes (for example, no remote embeddings can mean weaker search).
interview: How does an AI editor decide which code to show the model? || It combines signals: open files and cursor position, recent edits, diagnostics and the git diff, explicit @-mentions, retrieval from an embedding index of the repository, and in agent mode the model's own search and read tool calls. Rules files add standing instructions. The aim is a small, relevant context; more is not better.
Explain how an incremental codebase index stays in sync cheaply. || Files are hashed and arranged in a Merkle tree; comparing the root with the server's version shows whether anything changed, and walking down finds the changed files in about log n comparisons. Only those files are re-chunked and re-embedded, and unchanged chunks keep their vectors. This keeps updates cheap even in large repositories.
Why is applying an edit a separate problem from generating it, and how is it made fast? || Large models describe edits imprecisely (snippets, "rest unchanged"), and rewriting the full file token by token is slow. A specialised apply model rewrites the file from the original and the sketch, and speculative decoding uses the original file as the draft so that most tokens are verified in parallel and accepted, giving several-fold speed-ups.
What are the main security risks of agent mode in an editor and your mitigations? || Prompt injection through files, web pages or tool results; destructive or exfiltrating terminal commands; malicious dependencies; leaking code to providers. Mitigate with command allow-lists and approvals, sandboxed or cloud execution, privacy mode with zero retention, reviewed MCP servers and rules, secrets kept out of the workspace, and code review plus CI on all agent changes.
How would you measure whether an AI editor improves your team's output? || Compare matched periods or groups on lead time to merge, review time, defect and revert rates, and cost per merged change, not on suggestions accepted. Include qualitative feedback and track review load, since faster generation can shift the bottleneck. Run a pilot on bounded tasks first.
practice: Learn the three tools separately. Use Tab for local typing speed, inline edit for a change to a selected block, and agent mode for tasks across files. Use plan or ask mode first when you do not know the codebase, then switch to agent mode with a concrete goal and a check ("update the handler, run the unit tests for this module").
Give the editor good context cheaply: write a short rules file with commands and conventions (or an AGENTS.md that other tools also read), mention the exact files or symbols with @, exclude generated and vendor folders from the index (.cursorignore), and start a new chat for each unrelated task so old conversation does not crowd the window. Keep MCP tools to those you use weekly.
Set review habits. Read every diff, including tests; run the suite yourself or in CI; use checkpoints before a big agent run; and commit small steps. For sensitive code turn on privacy mode or the enterprise zero-retention plan, restrict terminal commands to an allow-list, and keep secrets out of the workspace. Treat cloud agents like contractors: give them a scoped repository, review the pull request, and cap spend.
Choose models deliberately. Try the editor's auto routing first, then pin a strong model for hard debugging or design and a cheaper one for repetitive edits, and compare on your own tasks for a week. Watch the usage and cost screen, because agent runs can consume far more than chat.
For a team, agree on which tools are approved, share rules files in the repository, and measure lead time, review time and defect rate before and after rollout.
