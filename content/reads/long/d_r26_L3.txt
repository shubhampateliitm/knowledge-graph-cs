value: A randomized algorithm makes some of its decisions by flipping coins. This sounds like a step backward, because a program that gives different answers or takes different time on each run is harder to trust. The reason it is useful is this: for many problems, a random choice gives a guarantee that no fixed, deterministic choice can give so simply. If a deterministic quicksort always picks the first element as pivot, a sorted input makes it take \( n^2 \) steps. If it picks the pivot at random, no input is bad: every input, including the sorted one, takes about \( 1.39 \times n \times \log_2 n \) comparisons on average. The adversary has to guess your coins, and cannot.
Randomization serves three goals. First, simplicity and speed: randomized quickselect finds the median in expected linear time with a few lines of code. Second, defence against bad inputs and attackers: when pivots or hash functions are chosen at random after the input is fixed, nobody can prepare a worst-case input. Third, problems where fast deterministic algorithms came late: primality testing was practical in 1976 with the Miller–Rabin test, but a deterministic polynomial algorithm (AKS) came only in 2002 and is still slower in practice.
The layer above uses this everywhere: hash tables (universal hashing), streaming sketches, cuckoo hashing, work stealing, load balancers, ASLR, and Raft's random timeouts.
Two concepts below make the analysis possible. Probability (L4) gives the language of expectation, independence and linearity of expectation, which is how we compute the average cost of a random algorithm. Concentration inequalities (L4), such as the Chernoff bound, show that the cost is almost always close to its average, so "expected n log n" becomes "n log n with very high probability" and not only on average.
terms: Las Vegas algorithm — a randomized algorithm that is always correct, but whose running time is a random variable (randomized quicksort).
Monte Carlo algorithm — a randomized algorithm with a fixed running time that may return a wrong answer with small probability (Miller–Rabin primality test).
Expected running time — the average running time over the algorithm's own random choices, for the worst input; it is not an average over inputs.
With high probability — failure probability at most \( 1/n^c \) for some constant \( c \ge 1 \), where n is the input size.
One-sided error — a Monte Carlo algorithm that can be wrong in only one direction, for example "composite" is always correct, but "prime" may be wrong.
Amplification — running a Monte Carlo algorithm several times independently to push the failure probability down exponentially.
Universal hash family — a set of hash functions such that, for a function chosen at random, any two different keys collide with probability at most 1/m.
Adversary (oblivious) — an attacker who knows the algorithm and picks the input, but does not see the random bits used during the run.
history: Random choices in computing are older than computers: Stanislaw Ulam and John von Neumann used random sampling to simulate neutron diffusion in 1946 to 1949, and the method was named Monte Carlo after the casino. Tony Hoare invented quicksort in 1960 and published it in 1961. Choosing the pivot at random became the standard way to avoid the quadratic worst case.
The modern theory starts in 1976 and 1977. Michael Rabin's "Probabilistic algorithms" (1976) showed a randomized algorithm for closest pair of points and a fast primality test. Gary Miller had a deterministic version that depended on the unproven Extended Riemann Hypothesis; Rabin removed that assumption by using randomness. Robert Solovay and Volker Strassen (1977) gave another randomized primality test. In 1977 Rusins Freivalds showed that a matrix product can be checked in \( n^2 \) time with random vectors, and Carter and Wegman introduced universal hashing (published 1977 and 1979). László Babai named the "Las Vegas" class in 1979 to contrast it with Monte Carlo.
Complexity theorists then asked whether randomness really adds power. The class BPP (problems solved in polynomial time with small two-sided error) was defined by Gill in 1977. In 1997 Impagliazzo and Wigderson showed that if some problems that need exponential time to solve exactly exist, then every randomized algorithm can be replaced by a deterministic one with only a polynomial slowdown. Most researchers now believe P = BPP, but nobody has proved it. In practice randomness is still the simplest tool.
Later milestones: skip lists (Pugh, 1990), Karger's random contraction for minimum cut (1993), the "power of two random choices" load-balancing result (Azar, Broder, Karlin and Upfal, 1994), randomized work stealing with proven bounds (Blumofe and Leiserson, 1999), and the textbook of Motwani and Raghavan (1995).
how: Every randomized algorithm has the same shape: take the normal algorithm, and at one or a few places replace "choose this element" with "choose a uniformly random element". The analysis then asks what happens, over the random choices, on a fixed worst-case input. This is the key difference from average-case analysis: we do not assume the input is random, only our own coins.
Linearity of expectation is the main tool, and it comes from the probability layer. It says that the expected value of a sum is the sum of the expected values, even when the parts are dependent. Randomized quicksort shows it clearly. Let the sorted elements be \( z_1 < z_2 < \dots < z_n \). Two elements \( z_i \) and \( z_j \) are compared at most once, and only if one of them is chosen as pivot before any element between them is chosen. Among the \( j - i + 1 \) elements from \( z_i \) to \( z_j \), each is equally likely to be the first pivot chosen, so the chance that z_i or \( z_j \) is first is \( 2 / (j - i + 1) \). Summing over all pairs gives the expected number of comparisons: \( 2n H_n - O(n) \approx 2 n \ln n \approx 1.39\, n \log_2 n \), where \( H_n \) is the n-th harmonic number. No dependence on the input order appears, so there is no bad input.
Las Vegas and Monte Carlo are related. A Las Vegas algorithm with expected time T can be turned into a Monte Carlo algorithm: run it for 2T steps and stop. By Markov's inequality (a non-negative variable is at most twice its mean with probability at least 1/2), it finishes with probability at least 1/2. In the other direction, if you can check an answer cheaply, repeat a Monte Carlo algorithm until the check passes, and you have a Las Vegas algorithm.
Amplification is the second tool. If a Monte Carlo algorithm with one-sided error fails with probability at most 1/2, then k independent runs all fail with probability at most \( 2^{-k} \). Twenty runs give a failure chance below one in a million, and the cost only grows by a factor of 20. This is why "correct with probability 1/2" is already a useful guarantee. For two-sided error (BPP), take the majority vote of k runs, and the Chernoff bound from the concentration layer shows that the probability of a wrong majority drops exponentially in k. Concentration also gives "with high probability" results for a single run: for randomized quicksort, the probability that the running time exceeds c × n log n falls faster than any polynomial in n for a suitable constant c, so one run is almost as predictable as an average.
Randomization defeats adversaries through hashing. A fixed hash function has a fixed set of colliding keys, and an attacker who learns it can send only those keys, turning O(1) lookups into O(n) (this has been done to web servers and language runtimes). In universal hashing, the function is drawn at random from a family, for example \( h(x) = ((a x + b) \bmod p) \bmod m \) with a and b chosen at random and p a prime larger than any key. For any two different keys, the collision probability is at most \( 1/m \), whatever the keys are. The expected chain length is then below \( 1 + n/m \) for every key set. SipHash, used for hash tables in Rust, Python and many Linux subsystems, is the keyed version of the same idea: a random secret key is chosen at start-up.
Random sampling turns a huge problem into a small one with a known error. A sample of about \( \ln(2/\delta) / (2\varepsilon^2) \) items estimates a proportion within ±ε with failure probability at most δ, whatever the population size (Hoeffding's inequality). Spark uses sampling to build a range partitioner: it samples keys, sorts the sample, and picks split points.
A last pattern is symmetry breaking. When machines must make the same choice at the same time, a deterministic rule makes them collide again and again. Ethernet backoff, retries with random jitter, and Raft's randomized election timeouts (150 to 300 ms in the Raft paper) use a random delay so that one machine wins first.

example: Freivalds' algorithm checks whether \( A \times B = C \) without multiplying the matrices. Multiplying two n × n matrices costs about \( n^3 \) operations by the school method, but multiplying a matrix by a vector costs only \( n^2 \). The idea: pick a random vector r with entries 0 or 1, and compare \( A \times (B \times r) \) with \( C \times r \). Both sides need only matrix-vector products.
Take A = [[1, 2], [3, 4]] and B = [[5, 6], [7, 8]]. The true product is [[19, 22], [43, 50]]. Suppose someone gives us the wrong answer C = [[19, 22], [43, 51]], with one wrong entry. There are four possible vectors r.
r = (0, 0): both sides are (0, 0). The check passes, so the error is missed.
r = (1, 0): B × r = (5, 7). A × (5, 7) = (1×5 + 2×7, 3×5 + 4×7) = (19, 43). C × r = (19, 43). They match, so the error is missed.
r = (0, 1): B × r = (6, 8). A × (6, 8) = (22, 50). C × r = (22, 51). They differ, so the error is caught.
r = (1, 1): B × r = (11, 15). A × (11, 15) = (41, 93). C × r = (41, 94). They differ, so the error is caught.
Exactly 2 of 4 vectors catch the error, so one trial misses it with probability 1/2. This matches the general theorem: if C ≠ A × B, a random 0/1 vector exposes the difference with probability at least 1/2. The error is one-sided: if the check fails, C is certainly wrong; if it passes, C is probably right.
Now amplify. With 10 independent random vectors, the chance that a wrong C passes every time is at most (1/2)^10 = 1/1024. With 30 vectors it is below one in a billion, about the chance of a hardware bit flip during the computation. For n = 1,000, the school multiplication needs about 10⁹ operations, and 30 checks need about 30 × 3 × 10⁶ ≈ 10⁸.
intuition: If you cannot tell which road is blocked, flip a coin at each fork; a blocked road can then stop you only by bad luck, and bad luck has a price you can calculate.
A deterministic algorithm is a fixed plan, and for every fixed plan there exists some input that is worst for it. An input is a fixed object, and the plan is known, so an adversary, or just an unlucky data set (sorted data, repeated keys, keys that all share the low bits), can aim at it. A randomized algorithm is a plan that is chosen after the input is fixed. The input can no longer be aimed at it, because there is no single plan. The worst case moves from "a bad input" to "a bad sequence of coin flips", and bad coin flips are rare, in a way that probability can measure.
It also shows why the guarantees are so clean. Most bad events are unions of many small, nearly independent events, and concentration says that sums of independent random variables hug their means. So a small number of random choices at the right places gives a smooth, predictable behaviour.
mistakes: People often think a randomized algorithm gives a random or unreliable answer. In fact a Las Vegas algorithm is always correct, and only its running time varies. A Monte Carlo algorithm may be wrong, but the error probability is a number you choose: after 100 independent runs of a test with error 1/2, the error is 2^(−100), far below the chance of a cosmic ray flipping a bit in your RAM.
People often think "expected O(n log n)" means "fast on average inputs". In fact the expectation is over the algorithm's own coins, and it holds for every input, including the worst one. That is the entire point. Average-case analysis, in contrast, assumes the input is random, which real data seldom is.
People often think that repeating runs only helps if the random bits are truly random. In fact the analysis needs independence between runs and a good enough source, but not perfect physical randomness. Pseudorandom generators are fine for algorithms like quicksort or Karger's min-cut. They are not fine where an attacker must not predict the bits (keys, ASLR offsets, hash seeds), and there you need a cryptographically secure generator.
People often think "with high probability" is a loose phrase. In fact it has a precise meaning (failure at most 1/n^c), and a claim without a stated probability is not a guarantee. A system that runs 10⁹ operations a day needs failure rates far lower than 10⁻⁶ per operation, so ask how many repetitions give that rate.
friction: The biggest practical cost is reproducibility. A bug that depends on a random choice may appear once in a million runs, and you cannot debug it if you cannot replay it. The usual remedy is to log or fix the seed, and to make the seed an explicit input in tests (Spark's sample() function has a seed parameter; most libraries do too). But then production behaviour and test behaviour differ.
The quality of the random source matters more than people expect. A weak generator can break the independence the analysis needs; a predictable one removes the protection against adversaries. Famous failures include a Netscape browser in 1995 that seeded its secure random numbers from the time and process ID, and a Debian OpenSSL change in 2006 to 2008 that cut the entropy of generated keys to about 32,768 possibilities. For security uses you need a cryptographically secure source from the operating system.
Finally, it is still not proved whether randomness adds power (P versus BPP). Many guarantees need only limited independence (pairwise independent hash functions), but some tail bounds need more, and that hides cost.
practice: Decide the failure budget first. For a Monte Carlo step, write down the allowed failure probability (for example 10⁻⁹), compute the repetitions k from it, and put k in the code as a constant with a comment. For Las Vegas steps, record the p99 of the running time and not only the mean.
Use randomness for load balancing: pick two random servers and send to the less loaded one. This "power of two choices" cuts the maximum queue length from about ln n / ln ln n to about ln ln n / ln 2 with n servers, and it is the default in Envoy's least-request balancer (choice count 2) and available in NGINX as `random two`. For skewed keys in Spark or Kafka, salt the hot key with a random suffix 0 … k−1, aggregate per salted key, then aggregate again without the salt.
For retries, add jitter: sleep a random time between 0 and min(cap, base × 2^attempt). Without jitter, thousands of clients that failed together retry together and fail again. Use the language's generator for the job: ThreadLocalRandom or SplittableRandom in Java for speed, SecureRandom or the operating system source for secrets and hash seeds. Never use a time-based seed for anything an attacker cares about.
In tests, print the seed on failure and allow it to be set by an environment variable, so a rare failure can be replayed. Run property-based tests with many seeds, since a randomized algorithm that passes one seed has shown very little.
tradeoffs: Choose a randomized algorithm when a deterministic one is much more complex or slower for the same guarantee, and when an occasional unlucky run is acceptable. Quickselect, universal hashing, reservoir sampling and consistent hashing with random virtual nodes are typical wins. Choose a deterministic algorithm when you need a hard worst-case time bound or exact reproducibility (real-time control, financial reconciliation, audit trails), and accept the extra code, as in median-of-medians selection, which has a larger constant factor of about 5 to 10 times.
Choose Las Vegas when a wrong answer is unacceptable and variable time is acceptable (sorting, joins, selection). Choose Monte Carlo when the time budget is hard and a tiny error is acceptable (primality testing for key generation, sketch-based counting, approximate analytics), and then fix the failure probability up front. Check that the number of repetitions needed to reach it is affordable: \( 2^{-k} \) needs only k = 40 runs for one in a trillion, but a constant-per-run success of \( 1/n^2 \) (Karger's single run) needs about \( n^2 \ln n \) runs.
Choose a cryptographically secure generator when an adversary benefits from guessing the bits (hash seeds for public-facing services, session identifiers), and a fast non-cryptographic one (xorshift, PCG, about 1 ns per number) for simulation, sampling and tests. Choose a fixed seed for tests and reproducible batch jobs, and a fresh seed on paths that face untrusted input. Whenever the seed varies, log it, so a surprising result can be replayed.
interview: Explain why randomized quicksort has expected O(n log n) time on every input. What does "expected" mean here? || The expectation is over the pivot choices, for a fixed input. Two elements are compared only if one of them is the first pivot chosen among the elements between them in sorted order, which happens with probability 2/(j−i+1). Summing over all pairs gives about 2n ln n. No input is special, because the randomness belongs to the algorithm and not to the data.
What is the difference between a Las Vegas and a Monte Carlo algorithm, and how do you convert one into the other? || Las Vegas is always correct with random running time; Monte Carlo has bounded time but a small chance of a wrong answer. Stop a Las Vegas algorithm at twice its expected time (Markov gives at least 1/2 success) to get Monte Carlo. Repeat a Monte Carlo algorithm until a cheap verifier accepts to get Las Vegas.
You have a Monte Carlo test with one-sided error 1/3. How many runs do you need for a failure probability below 10⁻⁹, and why can you multiply probabilities? || Independent runs fail together with probability \( (1/3)^k \). We need \( k \ge 9 / \log_{10}(3) \) ≈ 18.9, so 19 runs. Multiplication is valid only because the runs use independent random bits and the error is one-sided, so a single "reject" is certain.
Why does universal hashing protect a hash table against an attacker, and what stops the attacker from learning the function? || The function is drawn from a family where any two keys collide with probability at most 1/m, so for every fixed key set the expected chain length is small. The attacker picks the input before seeing the random choice, or does not see the secret seed. If the seed leaks, or the family is too weak, the protection disappears. This is why server hash tables use keyed functions such as SipHash with a per-process secret.
quiz: What is the difference between a Las Vegas and a Monte Carlo algorithm? || A Las Vegas algorithm always gives the correct answer but its running time is random. A Monte Carlo algorithm has a fixed running time but may give a wrong answer with small probability.

For every input, the chance that two elements get compared is 2/(j−i+1), which gives about 2 n ln n comparisons on average.

What decides it? || Quickselect has smaller constants and expected linear time, but a rare long run. If a p99.99 latency bound must hold with a hard guarantee, use median-of-medians. If average speed and simplicity matter and rare slow runs are tolerable, use quickselect.

value: A streaming algorithm reads a sequence of items once, in order, and keeps only a small summary in memory. The summary is called a sketch. The model fits any data that is too big to store or too fast to re-read: clicks on an ad platform, packets through a router, log lines from thousands of machines. Typical questions are "how many distinct users saw this ad?", "which 100 domains appear most often?", "what is the 99th percentile latency?" and "give me a uniform random sample of the events".
The surprising fact is how little memory is needed once you accept a small, known error. HyperLogLog counts billions of distinct items with about 12 KB and an error near 0.8%. An exact count of one billion 64-bit IDs would need at least 8 GB. A count-min sketch of 54 KB can estimate how often any key occurred, within 0.1% of the stream length, 99% of the time. Some answers are impossible without large memory: an exact distinct count provably needs memory linear in the number of distinct items. The field is the study of what can be done in sublinear space and why.
The layer above uses sketches everywhere. Databases and engines (Spark, Druid, BigQuery, Redis, Presto) offer approximate distinct counts and quantiles. Monitoring systems store latency histograms as mergeable sketches. Ad-tech systems count unique reach and frequency per campaign with them. They work because three lower concepts fit together. Hash tables and hashing (L3) map each item to a few counters or registers, spreading items evenly. Randomized algorithms (L3) let the sketch use random hash functions, so no input can be bad on purpose. Concentration inequalities (L4) turn the expected accuracy into a promise: with probability \( 1 - \delta \) the error is at most \( \varepsilon \).
terms: Stream — a sequence of items that the algorithm can read once, or a few times, in a fixed order.
Sketch — the small summary kept in memory; its size depends on the accuracy wanted, not on the stream length.
Sublinear space — memory that grows much more slowly than the stream, often logarithmically or not at all.
(ε, δ) guarantee — the answer is within error ε of the truth with probability at least \( 1 - \delta \).
Heavy hitter — an item whose frequency is above a chosen fraction of the stream, for example more than 1%.
Mergeable — two sketches built on separate parts of the data can be combined into the sketch of the whole.
Cardinality — the number of distinct items in a stream, not the total count.
Turnstile model — a stream that can both add and remove counts; the simpler cash-register model only adds.
history: Early ideas came from limited memory. Munro and Paterson (1980) studied finding the median with a few passes and little storage. Robert Morris (1978) built an approximate counter that counts up to about \( 2^{255} \) in 8 bits by incrementing only with probability \( 2^{-c} \). Philippe Flajolet and G. Nigel Martin (1983, journal version 1985) invented probabilistic counting of distinct items: hash each item and watch the rarest bit pattern, such as a long run of zeros; the longest run seen tells the size of the set. In 1982 Jayadev Misra and David Gries showed how to find all items above a frequency threshold with a few counters. Jeffrey Vitter (1985) gave reservoir sampling, a uniform sample of fixed size over a stream of unknown length.
The theory was named and organized by Noga Alon, Yossi Matias and Mario Szegedy, in "The Space Complexity of Approximating the Frequency Moments" (STOC 1996; Gödel Prize 2005). They defined the model, gave sketches for the second frequency moment, and proved lower bounds. Henzinger, Raghavan and Rajagopalan (1998) popularized the "data stream model" for web-scale data.
The 2000s made sketches practical. Greenwald and Khanna (2001) gave a deterministic quantile summary. Cormode and Muthukrishnan introduced count-min (2003 to 2005), Metwally and others the Space-Saving heavy hitters algorithm (2005), and Flajolet, Fusy, Gandouet and Meunier HyperLogLog (2007). Google's HyperLogLog++ (Heule, Nunkesser and Hall, 2013) fixed its bias at small counts. Ted Dunning's t-digest (2013) gave accurate tail quantiles, and the KLL sketch (Karnin, Lang and Liberty, 2016) reached optimal space for quantiles. Apache DataSketches, started at Yahoo and open-sourced in 2015, packaged these as a library used by Druid, Pinot and Hive.
how: The algorithm sees each item once, updates a small structure in constant time, and answers queries from the structure. Most sketches have the same skeleton: a hash function sends the item to a position, and the position holds a counter or a small register. Hashing (from the hash-table concept) is what makes items spread evenly, so that each counter sees a fair, random share of the stream.
Reservoir sampling keeps a uniform sample of k items. Keep the first k items. For item number i > k, with probability k/i replace a random slot of the reservoir with it; otherwise skip it. After n items every item is in the reservoir with probability exactly k/n. The proof is a telescoping product: item i enters with probability k/i, and survives each later step j with probability 1 − 1/j, so the product of the survival terms from i + 1 to n is i/n, and (k/i) × (i/n) = k/n. This is a pure randomized algorithm; it needs no hash and no knowledge of n.
Misra–Gries finds heavy hitters with k − 1 counters. Keep a map of at most k − 1 items to counts. When an item arrives that is in the map, add 1. If it is not in the map and there is room, add it with count 1. If it is not in the map and the map is full, subtract 1 from every counter and remove those that reach 0 (the new item is dropped). Every such step cancels k distinct items at once (the new one and k − 1 stored ones), so it can happen at most n/k times. Therefore every stored count is too low by at most n/k, and every item with true frequency above n/k is still in the map.
Count-min estimates the frequency of any key. Keep d rows of w counters, with one hash function per row. To add an item, increment one counter in each row, at the position the row's hash gives. To query, take the minimum of the d counters for the item. Collisions only add to a counter, so every counter is at least the true count, and the minimum is the least-polluted one. With \( w = \lceil e/\varepsilon \rceil \) and \( d = \lceil \ln(1/\delta) \rceil \), the estimate exceeds the truth by at most \( \varepsilon \times \text{(stream length)} \) with probability at least \( 1 - \delta \). The Markov inequality bounds one row; independent rows turn the failure probability into a product, which is the concentration idea at work.
HyperLogLog counts distinct items. Hash each item to a 64-bit value. Use the first p bits to choose one of \( m = 2^p \) registers, and in the remaining bits count the leading zeros plus one, called ρ. Each register keeps the maximum ρ it has seen. A register that saw a value with ρ = r suggests about \( 2^r \) distinct items went to it, because a run of r − 1 zeros has probability \( 2^{-r+1} \) for one item. The estimate is a harmonic mean over registers, scaled by a constant: \( E \approx \alpha_m \times m^2 / \sum_j 2^{-M[j]} \). The standard error is about \( 1.04 / \sqrt{m} \). With m = 16,384 registers of 6 bits (12 KB) it is about 0.81%. Two HyperLogLogs merge by taking the maximum of each register, which equals the HyperLogLog of the union of the streams. That makes it ideal for distributed engines.
Quantile sketches (t-digest, KLL, Greenwald–Khanna) keep a sorted, compressed list of representative values with weights. KLL keeps buffers at several levels; when a buffer is full it is sorted and every second item is promoted with double weight, so a small randomized sample of the stream stands in for the rest. The rank error is about \( \varepsilon n \). T-digest uses smaller clusters near the tails, which gives better accuracy at the 99th and 99.9th percentiles, but gives a weaker formal guarantee.
Concentration inequalities decide the sizes: Chernoff and Hoeffding bounds say how many counters or samples make the error small with the chosen probability. The whole design is: pick ε and δ, compute the size, pay that memory, and trust the bound.

example: Misra–Gries with k = 3, so at most 2 counters. The stream has 9 items: a b a c a b a d a. True counts: a = 5, b = 2, c = 1, d = 1. Any item with count above n/k = 9/3 = 3 must survive.
1. a arrives: map {a:1}. 2. b arrives: {a:1, b:1}. 3. a: {a:2, b:1}.
4. c arrives and is not in the map, and the map is full. Subtract 1 from all: a becomes 1, b becomes 0 and is removed. Map {a:1}. The item c is dropped.
5. a: {a:2}. 6. b: room is free, so {a:2, b:1}. 7. a: {a:3, b:1}.
8. d arrives, the map is full. Subtract 1 from all: {a:2}; b is removed.
9. a: {a:3}.
The final map is {a:3}. The estimate 3 is below the true count 5, by 2, which is at most n/k = 3, as promised. And a is indeed the only item that appears more than 3 times. Total memory: 2 counters for any stream length.
Now size a count-min sketch for the ad-tech case: 10 billion impressions per day, and we want each campaign's count within ε = 0.0001 (10¹⁰ × 10⁻⁴ = 10⁶ at most above the truth) with failure probability δ = 1%. Then \( w = \lceil e / 0.0001 \rceil \) = 27,183 and \( d = \lceil \ln 100 \rceil \) = 5. That is 135,915 counters; with 4 bytes each it is about 540 KB. The error bound is absolute (up to 1 million), so it is useful for campaigns with tens of millions of impressions and useless for tiny ones. This is why count-min is used for heavy hitters.
Last, HyperLogLog sizing. With p = 14 (16,384 registers) a daily unique-device count of 700 million has a standard error of 0.81%, so the answer is within about ±5.7 million, one standard deviation. Merging 24 hourly sketches takes 24 × 16,384 register comparisons. The exact alternative holds 700 million 8-byte IDs, 5.6 GB, before hash-set overhead.
intuition: Keep a postcard-sized summary of a library you cannot carry, and know exactly how wrong the postcard can be.
Why can this work at all? A question about a huge stream often has a small answer, and many items give the same evidence. Counting distinct users needs only a number, not the list of users. Hashing turns the stream into random-looking numbers, and rare patterns in random numbers (a long run of zeros, a collision in a small table) depend on how many different items there were. Random errors cancel when added (concentration), so averaging many small, independent estimates gives a sharp one. You pay not with accuracy that is unknown, but with accuracy that you chose. A sketch is also the right shape for distributed systems: it is small enough to send over the network, and mergeability means each machine can summarize its own part without coordination.
mistakes: People often think a sketch is a sample of the data. In fact a sample keeps real items; a sketch keeps hashed counters or registers from which items cannot be recovered. A reservoir sample is a sketch for a different job (representative rows), and cannot answer distinct counts reliably.
People often think the error of an approximate distinct count is like a rounding error you can ignore. In fact it is a statistical error with a known distribution, and it behaves differently from rounding: relative error stays the same at any size, but if you subtract two estimates (this week minus last week) the errors add, and the result may be mostly noise.
People often think sketches can be intersected or filtered like sets. In fact HyperLogLog merges for union exactly, but intersection can only be estimated through inclusion–exclusion, |A ∩ B| = |A| + |B| − |A ∪ B|, and the error of the result is relative to the large numbers, so small intersections are unreliable. Deletion is not supported at all by HyperLogLog.
People often think count-min estimates can be too low. In fact it never underestimates in the cash-register model, because collisions only add. It overestimates, especially for rare keys, since the error is bounded by ε times the whole stream and not by ε times the key's own count.
friction: The first limit is theoretical. Exact distinct counts, exact medians and exact frequent items need memory linear in the input in the worst case, so any sublinear algorithm must be approximate, and some questions (arbitrary joins between two streams, exact set intersection) cannot be answered well from sketches at all. Sketches also need the question to be known when the sketch is built: you can only ask what the sketch was designed for, and a new question needs a new pass over the raw data.
The guarantees have conditions. Count-min error is absolute, relative to the stream length, so it is bad for the long tail. The guarantees assume the hash functions behave randomly; weak hash functions (for example Java's hashCode on small integers) can make errors much larger than stated. Sketches are also affected by adversaries: if an attacker can see the hash function or probe the sketch, he can craft inputs that distort it.
In operations, three things hurt. First, sketches from different libraries or versions are not compatible, because the hash function, register layout and bias correction differ; storing a Redis HyperLogLog and reading it with another tool fails. Second, approximate numbers confuse users in reports: totals of parts do not equal the whole, and a repeated query may change if the sampling is random. Third, error accumulates in pipelines: summing approximate hourly counts of different groups is not the same as taking the distinct count of the union, and merging deep hierarchies of sketches needs care. Lastly, privacy: a sketch of user IDs is not anonymous. Membership can sometimes be tested, and deletion requests (for example under data-protection laws) cannot be applied to a HyperLogLog without rebuilding it from the source.
practice: Decide the error you can accept before you pick a sketch. For distinct counts, HyperLogLog with 12 KB gives 0.8%; doubling the registers lowers the error by only a factor of 1.41, so the cost grows fast. For frequencies of heavy keys, use count-min with a heap of candidates, or Space-Saving; for quantiles, use KLL or t-digest, and check the tail you need (p99.9 needs a tail-aware sketch).
Use the engine's built-in functions. In Spark, approx_count_distinct uses HyperLogLog++ with a default relative standard deviation of 5%; set rsd lower if needed. Spark's approx_percentile uses a Greenwald–Khanna style summary with an accuracy parameter (default 10,000). Spark 3.5 and later (and Databricks) also expose the DataSketches-based hll_sketch_agg and hll_union_agg functions, which let you store sketches in tables and merge them later. BigQuery has HLL_COUNT functions, Presto/Trino approx_distinct and Redis PFADD / PFCOUNT.
Store sketches, not just numbers. For a daily dashboard, save one sketch per day per dimension and merge when someone asks for a week or a month. A total over the week by adding daily distinct counts is wrong, because the same user appears on several days, while merging the sketches is correct. Keep a sample of the raw data to validate: compare the approximate and the exact count on a day, and track the relative error.
Pin the library and parameters with the data, and document them in the table schema. In tests, check that the estimate is within 3 standard errors of the exact answer for known inputs, rather than equal to it.
tradeoffs: Choose an exact count when the result drives money or a legal duty (billing, regulatory reports) and the data fits: the cost is memory and a shuffle, but the answer is auditable. Choose HyperLogLog when the count is for analysis or dashboards, the cardinality is above about a few million, and 1% error is acceptable; you give up exact numbers, deletions and good intersections for a 12 KB state that merges.
Choose count-min when you need many frequency queries and care about heavy keys; choose Misra–Gries or Space-Saving when you only need the list of the top-k with a deterministic guarantee and little memory. Count-min answers "how often did x occur?" for any x but does not list the heavy keys by itself; Space-Saving lists them but cannot answer for arbitrary keys with a tight bound.
Choose t-digest when the tails matter (latency p99 and p99.9) and the data is not adversarial, and KLL when you want a provable worst-case rank error and strict mergeability. T-digest is easy to use and very accurate at the extremes in practice, but its error bound is only empirical. DDSketch is another option for latency, with a relative error guarantee on the value.
Choose a sample (reservoir) when you will ask unknown questions later and want to run real queries on real rows; choose a sketch when the question is fixed and the volume is huge. A sample of 1 million rows supports many ad-hoc queries with error about \( 1/\sqrt{\text{sample size}} \), but cannot see rare events; a sketch sees all events but answers only its one question.
interview: Why can you not count distinct items exactly in less than linear space? || Roughly: if the algorithm uses fewer than n bits, two different sets of items must lead to the same memory state. A later item can then distinguish them, since adding it changes the distinct count for one set but not for the other, so the algorithm must give a wrong answer for one of them. A deterministic or randomized exact algorithm therefore needs Ω(n) bits in the worst case. Approximation and randomization escape this lower bound.
Explain how HyperLogLog estimates cardinality. Why does a harmonic mean appear, and how do you merge two sketches? || Each hashed item chooses a register by its first p bits, and the register keeps the maximum leading-zero count of the rest. A max of r means about 2^r items were seen. One register is noisy, because a single lucky item can raise it, so we average over m registers; the harmonic mean reduces the effect of large outliers. Merging takes the register-wise maximum, which equals the sketch of the union.
You have per-day HyperLogLog sketches for 90 days. How do you get monthly uniques, and how do you get users who visited in both January and February? || Monthly uniques: merge the daily sketches by register maximum. Users in both months: estimate by inclusion–exclusion, |Jan| + |Feb| − |Jan ∪ Feb|. The error is relative to the large numbers, so if the overlap is small the result is mostly noise. For an accurate intersection use a theta sketch (set-operation sketch) or exact data.
A count-min sketch gives a huge estimate for a rare key. What happened and how do you reduce it? || The key collided in all d rows with heavy keys, so the minimum is still high. Error is bounded by ε × stream length, not by the key's own count. Increase the width w to reduce ε, increase the depth d to reduce failure probability, or use the conservative update (increment only the minimum counters), or separate the heavy hitters into exact counters.
How would you design a service that reports p99 latency for every endpoint, per minute, across 2,000 machines? || Each machine keeps one mergeable quantile sketch (KLL, t-digest or DDSketch) per endpoint per minute and ships it, a few KB each, to an aggregator. The aggregator merges sketches across machines and reads the p99. Never average per-machine p99 values, because percentiles are not additive. Check sketch accuracy at the tail and the cost of sketches for rarely used endpoints.
quiz: What guarantee does the pair (ε, δ) express in a sketch? || With probability at least \( 1 - \delta \), the answer is within error \( \varepsilon \) of the truth (relative to the stream length or to the true value, depending on the sketch).
Why does reservoir sampling give each item the same chance k/n of being in the final sample? || Item i enters with probability k/i, then survives each later step j with probability 1 − 1/j. The product of survival terms from i + 1 to n is i/n, and (k/i) × (i/n) = k/n for every i.
Why can two HyperLogLog sketches be merged with a register-wise maximum, and what does it give? || Each register holds the maximum leading-zero count seen for its bucket, and the maximum over the union of two streams is the maximum of the two maxima. The result is exactly the sketch that would be built from the combined stream.
For a count-min sketch with ε = 0.001 and δ = 0.01, how many rows and columns are needed, and how many 4-byte counters is it? || \( w = \lceil e / 0.001 \rceil \) = 2,719 columns and \( d = \lceil \ln 100 \rceil \) = 5 rows. That is 13,595 counters, about 54 KB.
You are asked for the number of users who visited on at least one of the last 7 days. Which is correct: adding seven daily HyperLogLog estimates, or merging seven sketches? Why? || Merging. Adding counts the same user once per day on which he visited. Merging by register maximum estimates the size of the union, which is what "at least one of 7 days" means.

@@ interrupts
value: An interrupt is a signal that makes the CPU stop what it is doing, save its place, run a short piece of code called a handler, and then continue as if nothing had happened. Devices use it to say "I need attention now": a network card has received a packet, a disk has finished a read, a timer has expired, a key was pressed. Without interrupts, the CPU would have to ask every device again and again whether anything happened. This is called polling, and it wastes cycles when nothing happens and adds delay when something does.
Interrupts are the base of how an operating system stays responsive. The timer interrupt (typically 250 to 1,000 times per second in Linux, or on demand in "tickless" mode) lets the kernel take the CPU away from a program that does not give it up, and so makes preemptive multitasking possible. Device interrupts let one core serve thousands of idle sockets and disks and still react within microseconds. Exceptions, which are interrupts caused by the running instruction itself (page fault, divide by zero, system call), use the same mechanism, so the kernel handles all of them through one table of handlers.
The layer above builds on it directly. System calls enter the kernel with a trap that uses the same save-and-jump machinery. I/O models such as epoll and io_uring depend on device interrupts telling the kernel that data has arrived or a write has finished. Virtual machines must virtualize interrupts and timers for each guest. The layer below contributes the physical idea: digital logic (L3) provides an interrupt request line that a device drives high, a mask register of flip-flops that decides which lines are allowed through, and a priority encoder (a combinational circuit) that picks the most urgent pending request, so the CPU sees one vector number to act on.
terms: Interrupt request (IRQ) — a signal from a device (or a message on a bus) asking for the CPU's attention.
Handler (interrupt service routine, ISR) — the kernel function that runs in response to a particular interrupt.
Vector — a small number (0 to 255 on x86) that selects the handler in the interrupt descriptor table.
Exception — a synchronous interrupt caused by the current instruction: a fault (page fault, restartable), a trap (breakpoint, system call) or an abort.
Masking — temporarily blocking an interrupt, by a mask bit in the device controller or by clearing the CPU's interrupt-enable flag.
Top half and bottom half — the split of interrupt work: a very short handler runs with interrupts off, and the rest is deferred (softirq, tasklet, threaded handler, workqueue).
Interrupt coalescing (moderation) — the device waits for several events or a short time before raising one interrupt, so one interrupt serves many events.
IRQ affinity — the choice of which CPU cores may receive a given interrupt.
history: The idea is old. The UNIVAC 1103A is usually credited with the earliest interrupts, and the DYSEAC (completed 1954) is called the first machine to use hardware interrupts for I/O, to avoid polling loops. The motivation was economic: a machine costing millions of dollars sat idle while it waited for a slow card reader or magnetic tape. With interrupts, it could run another job during the wait. Dijkstra's THE multiprogramming system (1968) showed how a whole operating system could be organized around interrupt-driven processes and semaphores.
On the PC, the original IBM PC (1981) used the Intel 8259 programmable interrupt controller with 8 lines; the PC/AT (1984) added a second chip for 15. With one CPU, a shared line per device class was enough. Multiprocessor machines needed a better design: Intel introduced the Advanced Programmable Interrupt Controller (APIC) in the 1990s, with a local APIC per core and an I/O APIC to route lines to chosen cores. PCI 2.2 and PCI Express added Message Signaled Interrupts: instead of a wire, the device writes a small message to a special memory address, and MSI-X (PCI 3.0) allows up to 2,048 vectors per device. Multi-queue network cards use one vector per queue, so each queue can interrupt its own core. ARM systems use the Generic Interrupt Controller (GIC), and RISC-V has the PLIC and the newer AIA.
Software kept adapting to higher rates. In the early 2000s, Gigabit Ethernet made interrupt-per-packet processing impossible, and Linux added NAPI (the "new API", from Jamal Hadi Salim and others, around 2001 to 2002), which switches a busy interface to polling. Linux also added tickless kernels (NO_HZ) so that idle cores are not woken 1,000 times per second, and threaded interrupt handlers (2.6.30 and later with the real-time work) so handlers can be scheduled and prioritized. In virtual machines, hardware features such as APIC virtualization and posted interrupts let a guest receive interrupts without exits to the hypervisor.
how: The mechanism has a hardware half and a software half. Take an x86-64 machine receiving a network packet.
Step 1, signal. The network card writes the packet by DMA into a memory ring, then sends an MSI-X message to the local APIC of a chosen core, carrying a vector number such as 0x41. The APIC records the request in a 256-bit "interrupt request register". This is where digital logic matters: the request line, the mask bits and the priority logic are simple gates and flip-flops, and the hardware compares the priority of the new vector with that of the running task so that urgent requests win.
Step 2, accept. The CPU checks for pending interrupts at instruction boundaries (at retirement in an out-of-order core, so state is precise). If the interrupt-enable flag (IF) is set and the vector is not masked, it accepts. It cannot stop in the middle of an instruction, and so the delay before the handler starts is at least the length of the longest instruction in flight, plus any time interrupts were disabled.
Step 3, save and jump. The CPU switches to the kernel stack if it came from user mode, and pushes the old stack pointer, flags, code segment and instruction pointer. It looks up entry 0x41 in the interrupt descriptor table (IDT), a table of up to 256 gates set up by the kernel, loads the handler address and clears IF (for an interrupt gate). The handler's first instructions save the other registers. The hardware part alone takes on the order of a hundred cycles or more. With the handler, the return and the disturbance of caches and branch predictors, the practical cost of one interrupt is roughly 1 to 5 microseconds.
Step 4, handle. The top half does the minimum: acknowledge the device, read the cause, and schedule the rest. For a NIC, it masks that queue's interrupt and marks a poll as pending. Then it signals the APIC with an end-of-interrupt write and returns with `iretq`, which restores the saved registers and flags. Interrupts are then on again.
Step 5, bottom half. Soon afterwards, the kernel runs the deferred work with interrupts enabled, in softirq context (network receive, timers, block completions) or in a kernel thread. The NAPI poll function reads up to a budget of packets (the traditional weight is 64) from the ring, passes them up the network stack, and, when the ring is empty, unmasks the device interrupt. Under heavy load the ring never empties, so the interface stays in polling mode and takes no interrupts at all. This is how the system adapts: interrupts at low load for low latency, polling at high load for throughput.
Other mechanisms use the same path. The timer interrupt calls the scheduler, which can switch to another thread when the time slice ends. A page fault is an exception: the kernel's handler loads the page, and the instruction restarts. A system call (`syscall` instruction) is a trap with its own entry point. Non-maskable interrupts (NMI) cannot be blocked, and serve for hardware errors and profilers.
Two details of the signal matter for correctness. A level-triggered line stays asserted until the device is told to drop it; if the handler forgets to clear the cause, the interrupt fires again at once, forever. An edge-triggered signal is a single pulse, and a second event that arrives while the line is masked can be lost unless the controller remembers it. Message-signaled interrupts behave like edges and are stored in the controller's pending register, which is one reason they replaced shared wires. Shared state also needs care: data touched by both a handler and normal kernel code must be protected by a lock taken with local interrupts disabled, otherwise the handler could interrupt the lock holder on the same core and wait for the lock forever.
Interrupt delivery also needs policy. IRQ affinity (`/proc/irq/N/smp_affinity`) chooses which cores handle a vector. Spreading the receive queues of a NIC across cores uses all of them; pinning a queue's interrupt to the core that runs the consuming application improves cache locality. Coalescing (`ethtool -C rx-usecs`) trades latency for fewer interrupts. Both are knobs on top of the same hardware path.

example: Consider a 10 Gbps network interface receiving 1,500-byte frames. On the wire each frame takes 1,500 + 38 bytes of overhead = 1,538 bytes = 12,304 bits, so line rate is 10⁹ × 10 / 12,304 ≈ 812,700 frames per second.
Interrupt per packet. Assume each interrupt costs 3 microseconds of CPU time in total (entry, handler, return, cache effects). Then 812,700 × 3 µs = 2.44 seconds of CPU work per second. One core can supply only 1 second per second, so a single core would be saturated and packets would be dropped. At the extreme of 64-byte frames, line rate is about 14.88 million packets per second, and the same calculation gives 44 cores. Pure interrupt-per-packet cannot work on fast links.
Coalescing. Set the card to raise an interrupt at most every 50 µs. That is 20,000 interrupts per second, each finding about 812,700 / 20,000 ≈ 40 packets waiting. The interrupt cost is 20,000 × 3 µs = 60 ms per second, or 6% of one core. The price is delay: a packet may wait up to 50 µs before the CPU looks at it. For a bulk transfer that is irrelevant; for a trading or RPC system with 20 µs targets, it is too much.
NAPI. At 812,700 pps, the first interrupt masks the queue, and the poll loop runs repeatedly, pulling 64 packets per round. About 12,700 rounds per second handle everything, and no more interrupts occur while the ring is non-empty. The CPU still spends time on the packets themselves (perhaps 1 µs each, or 81% of a core without batching optimizations), but the 3 µs interrupt tax per packet is gone.
Timer check. A 1,000 Hz timer tick at 2 µs per tick costs 2 ms per second, or 0.2% of a core. On a 128-core machine that is 128,000 wake-ups per second if all cores tick. A tickless idle core avoids them and can stay in a deep sleep state.
intuition: A doorbell instead of opening the door every minute to see whether a visitor has arrived, but a doorbell that rings non-stop is worse than leaving the door open.
The design is natural because events arrive at times the CPU cannot predict. Polling spends work to learn that nothing happened. An interrupt spends work only when something happens, so it is cheap at low rates. But each interrupt has a fixed cost, and when events are frequent the fixed costs add up faster than the useful work. At that point the efficient design reverses: check at your own pace and process many events per visit. The best systems do both and switch by load. The save-and-jump mechanism is also natural: the CPU only needs to store its position, run another program, and restore the position, which a table of entry points and a stack make possible with very little hardware.
mistakes: People often think an interrupt handler runs on a separate thread or core. In fact it runs on the interrupted core, on the interrupted thread's kernel stack (or a dedicated interrupt stack), and the interrupted code cannot make progress until the handler returns. Long handlers therefore cause latency for whatever was running there.
People often think interrupts are always faster than polling. In fact interrupts cost more per event (a few microseconds against tens of nanoseconds for one poll step) and they win only when events are rare. At about a few hundred thousand events per second, a polling loop on a dedicated core is cheaper, which is why DPDK, SPDK and busy-polling sockets exist.
People often think the interrupt happens at the exact instruction where the signal arrived. In fact the CPU takes it at an instruction boundary, after the current instruction retires. Timing between signal and handler varies by the length of work in flight and by sections where the kernel disabled interrupts. This jitter is why general-purpose kernels give no hard real-time guarantees.
People often think an exception is a software error. In fact many exceptions are normal operation: page faults implement demand paging and copy-on-write, and system calls are deliberate traps. Only some faults (an invalid address, a divide by zero) are errors, and the kernel decides what to do with them.
friction: The first problem is cost at high rates. Besides the 1 to 5 µs direct cost, an interrupt disturbs the L1 cache and branch predictors, and on a virtual machine it can trigger a costly exit to the hypervisor unless posted-interrupt hardware support is used. An interrupt storm, caused by a faulty device or a driver bug that never clears the cause, can take a whole core, and Linux protects itself by disabling a line that fires without being handled ("nobody cared").
The second problem is latency variation. Any time interrupts are disabled (spinlocks taken with IRQs off, long handlers) delays other interrupts. The Linux real-time patches (PREEMPT_RT, merged into the mainline kernel in version 6.12, 2024) turn most handlers into threads so they can be scheduled, at the price of lower peak throughput. Handlers also cannot sleep, allocate memory freely or take sleeping locks, which makes driver code harder to write.
The third problem is placement. Interrupts land on cores that may be running something else, and moving them breaks cache locality. Good performance on servers needs deliberate IRQ affinity, receive-side scaling (hash flows to queues), and care about NUMA: a device attached to socket 0 should be served by cores on socket 0. Containers and cgroups do not isolate interrupt work well, so a noisy neighbour's network traffic can steal CPU time from other tenants on the same core.
Coalescing and NAPI reduce the problem but do not remove it; the tuning is workload-specific. Kernel-bypass stacks avoid interrupts but burn 100% of a core while waiting.
practice: Look before tuning. `cat /proc/interrupts` shows counts per core and per vector; `watch -d` on it shows which are growing. `mpstat -I SUM` and `perf stat -e irq_vectors:*` give rates; the `%soft` and `%irq` columns in `mpstat` show time in softirqs and hardirqs. If a single core shows high %soft while others are idle, receive-side load is concentrated on one queue.
For network servers: make sure the NIC has as many queues as cores that should handle traffic (`ethtool -l`), that irqbalance or manual affinity places queue vectors on the right NUMA node, and that coalescing matches your latency target (`ethtool -c`). For latency-sensitive services, lower `rx-usecs` or enable adaptive coalescing; for throughput services, raise it. Consider busy polling (`SO_BUSY_POLL`) only for services where a core can be spent for lower latency.
For real-time and low-jitter jobs, isolate cores with `isolcpus` or `nohz_full` and move interrupts away from them (`irqaffinity=` boot option). For Kafka brokers, Spark shuffle servers and storage nodes with fast NICs or NVMe, check that NVMe queues map to cores and that there is no single-core softirq bottleneck before buying hardware.
In application code you meet interrupts as latency tails, as `ksoftirqd` using CPU, or as drops in `ethtool -S` counters. In a driver or embedded program, do the minimum in the handler, never block, and defer the rest.
tradeoffs: Choose interrupts when events are rare or irregular (below roughly 100,000 per second per core) and when you want the CPU to sleep in between: the cost is 1 to 5 µs per event and some jitter. Choose polling when events are dense or latency matters at the microsecond level (above roughly 100,000 to 1,000,000 events per second, or p99 targets of a few microseconds): you spend a full core per queue at 100% utilization even when idle, and power use goes up.
Choose hybrid designs (NAPI, adaptive coalescing, io_uring with SQPOLL on demand) when load varies a lot over the day: you give up some simplicity and need tuning, but you get low latency at idle and high throughput at peak. Choose a fixed coalescing value when load is stable and predictable: simple and easy to reason about, but wrong at the extremes.
Choose to spread interrupts over all cores (irqbalance, RSS) when throughput matters. Choose to pin them to a few dedicated cores when latency-critical threads must not be disturbed: you lose capacity on those cores and must plan by NUMA node.
Choose a general-purpose kernel with default settings for most services. Choose PREEMPT_RT, isolated cores and kernel bypass only for hard latency goals, such as audio, robotics, or market data: the price is lower throughput, harder operations, and a narrower set of supported hardware.
interview: A server's CPU shows 90% usage on one core in `ksoftirqd` while other cores are idle, and packets are dropped. How do you diagnose and fix it? || The receive load is concentrated on one queue and core. Check `/proc/interrupts` and `ethtool -l/-x` for the number of queues and the RSS hash; if all flows hash to one queue (one big flow or a poor hash key), or only one queue is enabled, enable more queues and spread vectors with affinity. If a single flow dominates, use RPS/RFS or a different load split. Check `ethtool -S` for ring drops and consider larger rings and busy polling.
Why do interrupts become a bad design at high packet rates, and what exactly does NAPI do? || Each interrupt has a fixed cost of microseconds and disturbs caches. At 800,000 or more packets per second the cost exceeds one core. NAPI takes the first interrupt, masks the device's interrupt, and polls the ring in a softirq with a per-round budget until it is empty, then re-enables the interrupt. Under load there are almost no interrupts; at low load there is one per burst.
Explain what the CPU does between receiving an interrupt and executing the handler's first instruction. || It finishes the current instruction, checks that interrupts are enabled and not masked, switches to the kernel stack if needed, pushes the old stack pointer, flags, code segment and instruction pointer, reads the gate from the IDT using the vector, loads the handler address and privilege level, and clears IF for an interrupt gate. Software then saves the remaining registers.
What can you not do in an interrupt handler, and how do kernels deal with long work? || You cannot sleep, wait on a sleeping lock, or do long work, because the interrupted code and other interrupts are waiting. The handler does the minimum (acknowledge, read status, schedule), and the rest is deferred to softirqs, tasklets, workqueues or threaded handlers, which run with interrupts enabled and can be preempted.
How would you reduce interrupt jitter for a latency-critical thread on a Linux server? || Reserve cores with `isolcpus` and `nohz_full`, move all device interrupts and kernel threads to the other cores via `irqaffinity` and IRQ affinity files, disable the periodic timer tick on the isolated cores, and pin the thread there. Consider PREEMPT_RT if tail latency below tens of microseconds is required, and verify with a tool such as cyclictest.
quiz: What is the difference between an interrupt and an exception? || An interrupt is asynchronous and comes from a device or timer, at any time. An exception is synchronous: it is caused by the instruction being executed (page fault, divide by zero, system call). Both use the same table of handlers.
Why is a very short top half followed by a bottom half used in kernels? || The top half runs with interrupts masked or at high priority, so long work would delay all other interrupts and the interrupted code. The top half only acknowledges the device and schedules the rest, which then runs in softirq or thread context with interrupts enabled.
Why does an interface switch to polling under heavy load (NAPI)? || Every interrupt has a fixed cost of a few microseconds, so at high event rates the cost per packet is greater than the useful work. In polling mode one visit handles many packets and no interrupts occur, so the fixed cost is shared across a batch.
A NIC receives 400,000 packets per second and each interrupt costs 3 µs. What fraction of a core goes to interrupts with no coalescing, and with a 100 µs coalescing interval? || Without coalescing: 400,000 × 3 µs = 1.2 seconds per second, which is 120% of a core. With 100 µs coalescing: at most 10,000 interrupts per second × 3 µs = 30 ms, or 3% of a core, at a cost of up to 100 µs added latency.
When would you choose busy polling over interrupts? || When latency at the microsecond level matters or event rates are very high, and you can afford to dedicate a core that runs at 100% usage even when idle. For bursty, low-rate workloads where power and core count matter, interrupts are better.

@@ dma
value: Direct memory access (DMA) lets a device read or write main memory by itself, without the CPU moving each byte. The CPU only tells the device what to do: "write the next packet to the buffer at this address", or "read 64 KB from the buffer at that address and store it on the disk". The device does the transfer over the bus, and signals the CPU when it has finished. Without DMA, the CPU would run a loop that reads a word from the device, writes it to memory, and repeats, which is called programmed I/O.
The difference in speed is large. Reading a device register over PCIe takes roughly 0.5 to 1 microsecond, because the CPU must wait for the answer. Copying 4 KB with 4-byte reads then takes about 1,000 × 0.7 µs ≈ 700 µs, which is about 6 MB/s and uses the core fully. A DMA engine moves the same data in large bursts at several GB/s, and the CPU is free. This is the only reason a server can handle 100 Gbps of network traffic or millions of NVMe operations per second.
DMA gives the layer above its main performance features. Zero-copy I/O (sendfile, io_uring registered buffers) works because the network card can read file data straight from the page cache by DMA, so the CPU never copies it. RDMA lets a network card write into the memory of another machine, using the same descriptor idea over the network. GPUs, NVMe SSDs, network cards and accelerators all move bulk data this way. The layer below supplies the machinery: digital logic (L3) gives a DMA controller its address register, length counter and state machine, and the bus arbiter that decides which device owns the bus in each cycle, so the CPU and the device can share the memory without colliding.
terms: DMA engine (controller) — the hardware block, inside a device or on the chip, that generates memory addresses and moves data on its own.
Descriptor — a small record in memory telling the engine where a buffer is, how long it is, and flags; descriptors are arranged in a ring.
Doorbell — a write to a device register that tells it "new descriptors are ready".
Bus mastering — a device takes control of the bus and starts memory transfers itself; all PCIe devices do this.
Scatter-gather — one transfer built from many separate buffers listed in a descriptor list, so data need not be contiguous.
IOMMU — a memory-management unit for devices; it translates device addresses to physical addresses and blocks access to other memory.
Pinning — fixing a page in physical memory so it cannot be moved or swapped out while a device uses its address.
Bounce buffer — a temporary buffer in an address range the device can reach, used when the real buffer is out of reach; data is copied to or from it.
history: Early computers moved data through the CPU. In the late 1950s, the IBM 709 introduced data channels: small independent processors that ran I/O programs while the CPU kept computing. IBM System/360 (1964) made channels a standard part of mainframes. The reason was the same as for interrupts: a very expensive CPU should not wait for slow devices, and should not spend its cycles copying bytes.
Minicomputers and PCs used simpler hardware. The IBM PC (1981) used the Intel 8237 DMA controller with four channels, used for floppy disks and sound cards; it was a "third-party" design in which a shared controller moved data between a device and memory. It was slow and had limits on address range and transfer size (64 KB). With PCI (1992), devices became bus masters themselves, each with its own engine, and the shared controller faded away.
Modern designs use descriptor rings and doorbells. Network cards from the late 1990s (Intel e1000) keep a ring of receive and transmit descriptors in memory; NVMe (2011) uses pairs of submission and completion queues in host memory, with up to 65,535 I/O queues of up to 65,536 entries each. Intel's Data Direct I/O (DDIO, introduced with Xeon E5 in 2012) lets the network card write received packets directly into the processor's last-level cache instead of RAM.
Security followed. An unrestricted DMA device can read and write all memory. AMD added an IOMMU (AMD-Vi, 2007) and Intel followed with VT-d (2008); ARM has the SMMU. DMA attacks through FireWire ports were shown in practice by 2006 (Winlockpwn, by Adam Boileau), Thunderbolt later opened the same door, and the 2019 Thunderclap research by Markettos and others showed that even with an IOMMU, peripherals could attack operating systems that configure it weakly. Windows added Kernel DMA Protection (Windows 10 1803), and Linux, macOS and Windows now enable the IOMMU for external ports. GPUDirect (NVIDIA, 2010 to 2012) extended DMA to move data between a network card and a GPU directly.
how: A DMA transfer has five steps, shown here for a network card receiving packets through a ring. The same pattern is used by NVMe, GPUs and storage controllers.
Setup. The driver allocates a ring of descriptors in main memory and a set of buffers (for example 2 KB each). Each descriptor holds the bus address of one buffer, its size, and a status field. The driver tells the card, through memory-mapped registers, the ring's base address, its length, and a head and tail position. This is configuration, done once.
Posting. The driver fills descriptors with fresh empty buffers and moves the tail pointer forward, by writing it to a doorbell register on the device. This single write is the only time the CPU speaks to the device on the fast path.
Transfer. When a packet arrives, the card reads the next descriptor from the ring (a DMA read), then writes the packet bytes into the buffer (a DMA write), then writes back the status and length into the descriptor. On PCIe, each of these is a packet (TLP) with about 20 to 30 bytes of header and framing and a payload of up to the maximum payload size, usually 128 or 256 bytes, so a 1,500-byte frame becomes six to twelve write packets. The data rate is high: PCIe 4.0 offers about 2 GB/s per lane after encoding, and PCIe 5.0 about 3.9 GB/s, so a x16 slot gives about 63 GB/s on Gen 5.
Completion. The card signals the end by raising an interrupt (see the interrupts concept), usually an MSI-X message, or the driver discovers it by polling the status field. The driver walks the ring from its head, reads the descriptors marked done, hands the buffers to the network stack, and posts new ones. Batching many descriptors per interrupt is what makes the cost per packet small.
Teardown. When the buffer is no longer needed, the driver unmaps it. Mapping and unmapping are part of the DMA API in the operating system (in Linux: `dma_map_single`, `dma_map_sg`, `dma_unmap_*`, and `dma_alloc_coherent` for long-lived rings).
Several problems have to be solved for this to be correct. Addresses: the device uses bus addresses, which can differ from CPU physical addresses, and some older devices can only address the low 4 GB; the kernel then uses bounce buffers (swiotlb), at the cost of an extra copy. With an IOMMU, the device uses I/O virtual addresses (IOVA), and the IOMMU's page tables, one set per device or group, translate them. This also makes a scatter-gather list look contiguous to the device, and it stops a faulty device from writing outside its allowed buffers. Pinning: the buffer must stay in the same physical page for the whole transfer, so the kernel pins it; this is why RDMA applications must register their memory first, and why large pinned areas reduce the memory available to other uses. Coherence: x86 DMA is cache-coherent, because the memory system snoops writes from the device and updates or invalidates the CPU caches. On many ARM systems it is not, and the driver must flush or invalidate caches explicitly (`dma_sync_single_for_cpu` and `_for_device`) before and after the transfer, or the CPU will read stale data.
Sharing the memory bus needs arbitration, which is digital logic. The device (or the controller) raises a bus request, an arbiter grants one owner at a time, and the owner moves a burst of words before releasing the bus. Old DMA controllers "stole" single cycles between CPU accesses; modern PCIe devices send whole packets that the memory controller interleaves with CPU traffic. Ordering is the last piece. The card must make the packet data visible before it makes the status flag visible, and PCIe keeps writes from one device in order. On the CPU side, the driver must read the status first and only then the data, with a read barrier in between (`dma_rmb()` in Linux), because a weakly ordered processor could otherwise read the old data after seeing the new status. This is the memory-model problem again, between a CPU and a device.
Zero-copy and RDMA are the same mechanism applied further. In a `sendfile` call, the kernel builds a descriptor list that points at the pages of the file in the page cache, and the network card gathers them, so the payload is never copied by the CPU. With RDMA, the descriptor names a memory region on a remote machine, and the remote card performs the DMA write.

example: First, programmed I/O against DMA, with numbers. A device holds a 4 KB block. If the CPU reads it with 8-byte MMIO loads and each load waits 700 ns for the PCIe round trip, 4,096 / 8 = 512 loads cost 512 × 0.7 µs = 358 µs, which is 11.4 MB/s with one core fully busy. With DMA, the CPU writes one descriptor and one doorbell (about 2 to 3 µs in total), and the device moves 4 KB over a PCIe 4.0 x4 link at about 7.9 GB/s in roughly 0.5 µs plus a latency of 1 to 2 µs. The CPU is free after the doorbell.
Second, follow one packet through a receive ring of 4,096 descriptors. The driver has posted descriptors 0 to 4,095, with buffer i at address 0x10000 + i × 0x800 (2 KB each). The head is at 17. A 1,500-byte frame arrives. The card reads descriptor 17 and finds the buffer address 0x10000 + 17 × 0x800 = 0x18800. It writes 1,500 bytes there, as six 256-byte TLPs (the last one smaller), then writes length 1,500 and the "done" flag into descriptor 17. It raises an interrupt only if coalescing allows. The driver wakes, sees descriptor 17 done, passes the buffer up, allocates a new buffer for slot 17, and writes the new tail to the doorbell. If the driver is slow and the head catches the tail, the card has no buffer and drops the packet; this is counted as a ring overrun.
Third, the memory-copy budget. At 100 Gbps (12.5 GB/s), if the receive path made one CPU copy from the kernel buffer to the application buffer, memory traffic would be 12.5 GB/s read and 12.5 GB/s write, about 25 GB/s. One memory channel of DDR5-4800 provides about 38 GB/s peak, so the copy alone would use about two thirds of a memory channel, and it needs most of the copy bandwidth of one core (a single core typically copies at 5 to 15 GB/s). The DMA write that put the packet in memory is unavoidable, but every extra copy is optional, and zero-copy paths remove them.
intuition: A delivery truck unloads straight into the warehouse by following a list of shelf numbers, while the manager only signs the list and later checks that the shelves are full.
The design follows from a division of labour. The CPU is good at deciding, and bad at being a conveyor belt: each byte it moves costs a cycle of a very expensive resource, and every wait on a slow device is wasted. A device already holds the data and knows the bus protocol, so a small counter and an address register are enough to move it. What the CPU must keep is control. It decides which memory the device may touch, when to start, and when the data is valid. Descriptors and doorbells make that control cheap: one write to start, one interrupt or one read to finish, however large the transfer.
The rest of the design (pinning, IOMMU, cache maintenance) exists because the device acts on memory without the CPU's knowledge, and so the rules the CPU normally enforces (virtual memory, caching, protection) must be re-established for the device.
mistakes: People often think DMA means the CPU is not involved at all. In fact the CPU sets up each transfer (maps the buffer, writes descriptors, rings the doorbell) and handles the completion. For small transfers (a 64-byte message) this setup can cost more than copying the bytes, and small-packet performance is often limited by descriptor and doorbell overhead, not by bandwidth.
People often think DMA data is "free" for memory. In fact the data still crosses the memory bus. A DMA write consumes memory bandwidth and may evict useful lines from the CPU cache; DDIO reduces this by sending the data into cache, but a busy cache can be polluted by it. DMA saves CPU cycles, not memory traffic.
People often think a device can only reach the buffers the driver gives it. In fact, without an IOMMU, a DMA-capable device can read or write any physical address. A malicious or buggy device, or firmware on it, can take over the machine. The IOMMU limits this, but only if it is enabled and configured with strict page-level mappings.
People often think DMA buffers are normal memory that the kernel can move or swap. In fact the buffer must stay at a fixed physical address (or a fixed IOVA) until the transfer ends. Using ordinary pageable memory for a long-lived DMA target causes data corruption, which is why DMA memory is pinned or allocated from special areas.
friction: The most common problem is correctness around memory. If a driver forgets cache maintenance on a non-coherent platform, the CPU reads old data, a failure that depends on timing and appears rarely. Using a buffer after it has been unmapped, or freeing it while the device still writes, corrupts memory that now belongs to somebody else. Bugs in device firmware or drivers can write to random addresses, and without an IOMMU these cannot be contained.
Performance has its own problems. The IOMMU adds a translation step. Its IOTLB can miss, and a miss triggers a page-table walk that costs hundreds of nanoseconds; invalidating mappings after each unmap is expensive, so Linux offers a "lazy" mode that batches invalidations at the cost of a window where a device could still access an unmapped page. Studies of fast networking have measured a noticeable throughput cost from the IOMMU with small packets. Pinned memory cannot be swapped, so large registered regions (RDMA, DPDK hugepages) are taken from the system for good, and memory registration itself is slow (tens of microseconds or more per call), so applications register once and reuse.
Next, NUMA: a buffer allocated on the memory of one socket but used by a card attached to the other makes every DMA cross the inter-socket link, lowering bandwidth and adding latency. Finally, peer-to-peer DMA between devices (for example NVMe to GPU) depends on the PCIe topology, the switches and the ACS settings, and can be blocked or slow when the devices sit under different root complexes.
practice: Use zero-copy paths only where profiles show copy time: `sendfile`, `splice`, `MSG_ZEROCOPY` (worth it only for sends above roughly 10 KB, since pinning and completion notification have a cost), and registered buffers in io_uring. For small messages, the copy is cheaper than the bookkeeping.
Keep buffers close to the device: allocate on the NUMA node of the NIC or NVMe drive (`numactl`, `ethtool`, `lspci -vv` shows the node via sysfs `numa_node`). Use hugepages for DPDK and RDMA to cut IOTLB misses and registration cost. Register memory regions once at start-up and reuse them; do not register per request. Size NIC rings (`ethtool -g`) so bursts fit: a larger ring absorbs bursts and avoids drops, but a very large ring adds latency (bufferbloat) and cache pressure.
Check the IOMMU settings for your risk and workload. On servers with untrusted external devices, leave the IOMMU on in strict mode (`intel_iommu=on`, check `dmesg` for DMAR). For high-performance trusted workloads, passthrough mode (`iommu=pt`) cuts translation overhead for host devices while still allowing device assignment to VMs.
In Spark and Kafka deployments you meet DMA indirectly: cloud instance types with 100 Gbps networking and local NVMe storage get their speed from DMA, and the kernel and driver versions matter. When tuning, watch `ethtool -S` for rx_missed or rx_no_buffer counters (a sign of ring overrun) and `perf` for time in `memcpy`, which shows copies DMA could avoid.
tradeoffs: Choose DMA with interrupts for ordinary devices and moderate rates: it is simple and keeps the CPU free. Choose DMA with polling (DPDK, SPDK, io_uring SQPOLL) for rates above roughly a million operations per second or microsecond latency targets, at the price of a dedicated core that is always busy.
Choose to enable the IOMMU when devices or their firmware are not fully trusted, when you pass devices to virtual machines, or when you need to use scatter-gather with devices that have limited addressing; you pay translation latency and some throughput, and setup complexity. Choose passthrough or no IOMMU only on trusted, dedicated hardware where every percent of throughput matters.
Choose zero-copy (sendfile, registered buffers, RDMA) when payloads are large and the copy is a measurable fraction of CPU time, for example serving 100 GB/s of file data. Choose normal copying for small payloads and when data must be transformed (encryption in software, compression): zero-copy then saves nothing, and its pinning and completion bookkeeping cost more than the copy.
Choose large rings and deep NVMe queues for throughput, and small ones for latency. A queue depth of 32 to 128 usually saturates an NVMe drive; beyond that you only increase latency, because requests wait in the queue.
interview: Walk me through how a NIC delivers a packet to a user process, naming every place where data is copied or the CPU is involved. || The driver pre-posts buffers in the receive ring. The NIC DMA-writes the packet into a buffer and updates the descriptor, and raises an interrupt (or the driver polls). The kernel builds a socket buffer around it, processes the protocol layers, and on `read` copies the data to the user buffer: this is the only CPU copy on a typical path. Zero-copy receive, or kernel bypass, can remove it.
Why do DMA buffers have to be pinned, and what does an IOMMU change? || The device holds a physical or bus address, so the page must not move or be swapped out during the transfer. The IOMMU lets the device use I/O virtual addresses, translated by its own page tables; this restricts the device to its mapped buffers and allows a scattered set of pages to look contiguous. Pinning is still needed, because the translation target must stay valid.
On an ARM server, a driver sometimes shows stale data after a DMA read. What is the likely cause? || The platform's DMA is not cache-coherent, and the CPU cache holds old lines for the buffer. The driver must invalidate the cache for the buffer range after the device writes it (`dma_sync_single_for_cpu`) and clean it before the device reads it. On x86 hardware coherency hides this, which is why the bug appears only on ARM.
Why is a doorbell write needed, and why not tell the device on every descriptor? || An MMIO write crosses PCIe, costs hundreds of nanoseconds, and is uncached and ordered. Writing descriptors to memory is cheap, so the driver writes a batch and sends one doorbell with the new tail pointer. Batching amortizes the cost; the trade-off is slightly higher latency for the first packet in the batch.
What are the risks of DMA from a security standpoint, and how do you mitigate them? || A DMA-capable device can read or write any physical memory unless restricted, so a malicious device, malicious firmware, or an exposed Thunderbolt port can steal keys or modify the kernel. Mitigate with the IOMMU in strict mode, kernel DMA protection for external ports, bounce-buffering untrusted devices, and updated firmware.
quiz: What does the CPU do and what does the device do in a DMA transfer? || The CPU prepares buffers and descriptors and rings the doorbell, and handles the completion. The device's DMA engine reads descriptors and moves the data to or from memory without the CPU touching each byte.
Why does reading a 4 KB block with programmed I/O take far longer than with DMA? || Each uncached device read waits for a PCIe round trip of about 0.5 to 1 µs, and the CPU needs hundreds of them, one per 4 to 8 bytes. DMA moves the block in large bursts at GB/s with the CPU idle.
Why must the kernel flush or invalidate caches around DMA on a non-coherent system? || The device reads and writes main memory directly and does not see the CPU caches. Before the device reads, dirty lines must be written back; after the device writes, stale cached lines must be invalidated, or the CPU reads old data.
A NIC ring has 1,024 descriptors and traffic is 800,000 packets per second in bursts of 2,000 packets with no pause. What happens, and what fixes it? || The burst exceeds the ring size: after 1,024 packets the card has no free buffer and drops the rest, since the driver cannot repost fast enough. Increase the ring (up to the hardware maximum), spread flows over more queues, or make the driver faster (polling).
When is zero-copy not worth it? || For small payloads and when data must be processed by the CPU anyway. Pinning pages, building descriptors and handling completion notifications can cost more than copying a few KB.

@@ pipeline
value: Executing one instruction takes several steps: fetch it from memory, decode it, read the registers, do the arithmetic, access memory, write the result back. A simple processor does all steps for one instruction before it starts the next, so most of its hardware sits idle most of the time. Pipelining uses that idle hardware. It splits the work into stages, puts a register between the stages, and lets each stage work on a different instruction at the same time, like an assembly line. After a short start-up, one instruction finishes in every clock cycle, although each single instruction still takes five or more cycles from start to end.
The gain is throughput and clock speed. A task that takes 1000 ps in one step can be cut into five stages of about 200 ps. The clock can then run at 5 GHz instead of 1 GHz, and the machine still completes one instruction per cycle. That is a speedup of nearly 5 for the cost of some registers and control logic. Every modern processor is pipelined, from tiny microcontrollers (2 to 3 stages) to server cores (about 14 to 20 stages in the front-to-back path) and GPU cores.
The price is that instructions are not independent. The next instruction may need the result of the previous one before it is written, a branch decides which instruction comes next after the pipeline has already fetched some, and two instructions may want the same hardware. Handling these hazards is most of the design work, and its effects are what the layer above sees as "branches are expensive" and "dependent instructions are slow". The general-purpose CPU concept (L1) builds on the one-instruction-per-cycle rate that pipelining makes possible, and compilers and query engines (whole-stage code generation, vectorized loops) generate code that keeps the pipeline full.
Two lower concepts make this work. Digital logic (L3) supplies the registers (flip-flops) that sit between stages and capture each stage's result at the clock edge, and the clocking rule that the cycle must fit the slowest stage. Boolean algebra (L4) supplies the content of each stage: the instruction decoder, the register-file selectors, the adder and the forwarding comparators are all Boolean functions built from gates.
terms: Stage — one step of the pipeline (fetch, decode, execute, memory, write-back), designed to take about one clock cycle.
Pipeline register — a bank of flip-flops between two stages that holds one instruction's partial results for one cycle.
Throughput and latency — throughput is instructions finished per second; latency is the time one instruction needs from start to end. Pipelining raises throughput and does not lower latency.
CPI (cycles per instruction) — the average number of cycles per instruction; an ideal pipeline has CPI = 1.
Hazard — a situation where the next instruction cannot proceed in its normal cycle: data, control or structural.
Stall (bubble) — a cycle in which a stage does nothing useful because the pipeline waits for a hazard to clear.
Forwarding (bypassing) — sending a result directly from a later stage's register to an earlier stage that needs it, without waiting for write-back.
Misprediction penalty — the number of cycles lost when the guess about a branch was wrong and the wrongly fetched instructions are thrown away.
history: Overlapping work was used early in large machines. IBM's Stretch (1961) overlapped instruction fetch, decode and execute. The CDC 6600 (1964), designed by Seymour Cray and James Thornton, had several functional units and a scoreboard that tracked dependencies, so it could keep them busy. The Cray-1 (1976) combined deep pipelines with vector instructions.
The idea became a design principle in the 1980s with RISC. John Hennessy's MIPS project at Stanford and David Patterson's RISC project at Berkeley used simple, fixed-length instructions so that every instruction could pass through the same five stages: instruction fetch (IF), decode and register read (ID), execute (EX), memory access (MEM) and write-back (WB). The MIPS R2000 (1985) shipped this design. The Intel 486 (1989) brought a five-stage pipeline to x86, which had a harder job because its instructions have varying lengths, and the Pentium (1993) added a second pipeline so two instructions could start per cycle (superscalar).
The 1990s and early 2000s were a race for clock speed through deeper pipelines. The Pentium Pro (1995) had about 12 to 14 stages, the Pentium 4 "Willamette" (2000) 20 stages, and the Pentium 4 "Prescott" (2004) 31 stages. Longer pipelines allow higher clock speeds but make mispredicted branches and stalls more costly, and they use more power per instruction. Intel's own results showed that Prescott's gains were small and its heat large; the company changed direction to the Core microarchitecture (2006), with about 14 stages, and pipeline depth in high-performance cores has since stayed around 10 to 20 stages. Modern designs get speed from width (4 to 8 instructions per cycle) and better prediction, not from more stages.
how: The classic five-stage pipeline shows the whole mechanism. Instruction fetch (IF) reads the instruction at the program counter (PC) from the instruction cache and computes PC + 4. Decode (ID) turns the instruction bits into control signals and reads the source registers from the register file. Execute (EX) uses the arithmetic logic unit (ALU) for arithmetic, for address calculation, or for comparing a branch condition. Memory (MEM) loads or stores through the data cache. Write-back (WB) writes the result into a register. Between each pair of stages sits a pipeline register (IF/ID, ID/EX, EX/MEM, MEM/WB), which carries the instruction and its partial results into the next cycle.
The clock period must cover the slowest stage plus the register's own delay (clock-to-output time, setup time and skew). This is the contribution of digital logic: because all registers update on the same clock edge, each stage sees stable inputs for the whole cycle. In the textbook example of Patterson and Hennessy, the stages take 200, 100, 200, 200 and 100 ps. A single-cycle machine needs 800 ps per instruction. A pipelined machine has a 200 ps clock (set by the slowest stage), so it finishes one instruction per 200 ps: a speedup of 4, not 5, because the stages are not balanced. Balancing stages, and the register overhead, are what limit the ideal speedup equal to the number of stages.
Boolean algebra gives the content of the stages. The decoder is a set of Boolean functions from opcode bits to control lines (is this a load, does it write a register, does the ALU subtract). The 64-bit adder in the ALU is a tree of gates built from carry-lookahead equations. The hazard unit is a set of equality comparators on register numbers.
Data hazards happen when an instruction needs a register that an earlier, still unfinished instruction will write. In `add x1, x2, x3` followed by `sub x4, x1, x5`, the add computes x1 in EX, but the write-back comes two cycles later. Without help, the sub would read the old x1. The fix is forwarding: comparators check whether the source register of the instruction in EX equals the destination of the instruction in MEM or WB, and if so, a multiplexer takes the value from the EX/MEM or MEM/WB register instead of from the register file. A load is different: the loaded value is available only at the end of MEM, so `lw x1, 0(x2)` followed by `add x3, x1, x4` still needs one stall cycle, even with forwarding. This is the load-use hazard. Compilers try to place an independent instruction between the two.
Control hazards come from branches. The pipeline fetches the next instructions before the branch outcome is known. In the classic pipeline the branch is resolved in EX, so two wrong-path instructions are in flight, and they are flushed (turned into bubbles) if the guess was wrong. Real cores resolve branches later and fetch many instructions ahead, so the penalty is 14 to 20 cycles; this is why prediction is a separate concept. Structural hazards come from sharing hardware, for instance one memory port for both instruction fetch and data access; the classic fix is separate instruction and data caches.
Stalls and flushes are done with the same registers. To stall, the hazard unit holds the PC and the IF/ID register (they keep their old value for one cycle) and loads a "no-operation" into the ID/EX register, which creates the bubble. To flush after a misprediction, it clears the IF/ID and ID/EX registers, so the wrongly fetched instructions turn into no-operations before they can write anything. Control signals travel with the instruction: the decoder produces them once in ID, and they are carried through the later pipeline registers, for example "write the register file" is used only in WB. This is why no instruction can change architectural state before it reaches the last stage.
Exceptions need care too. When an instruction faults (page fault, divide by zero) the pipeline must behave as if all earlier instructions finished and no later one started. With several instructions in flight, the hardware tracks the age of each and squashes the younger ones.
Superscalar designs go further by duplicating stages to start 2, 4 or 8 instructions per cycle, and out-of-order designs (next concept) allow later instructions to run while earlier ones wait. Both rest on the same stage-and-register structure.

example: First, the ideal count. Run 100 instructions on a five-stage pipeline with no hazards. The first instruction takes 5 cycles, and then one finishes each cycle, so the total is 5 + 99 = 104 cycles, CPI = 1.04. An unpipelined multi-cycle machine would use 500 cycles. For one million instructions the pipelined machine needs 1,000,004 cycles.
Second, the clock. Take stage delays of 200, 100, 200, 200 and 100 ps, and a register overhead of 20 ps. The unpipelined path is 800 ps. The pipelined clock period is 200 + 20 = 220 ps. Instruction throughput rises from 1 per 800 ps to 1 per 220 ps, a speedup of 3.6, while the latency of one instruction becomes 5 × 220 = 1,100 ps, longer than before. Latency got worse; throughput got much better.
Third, the cost of hazards in a CPI budget. Suppose 25% of instructions are loads and 40% of loads are followed at once by a dependent instruction (one stall each). Suppose 15% are branches, with 90% predicted correctly, and a misprediction costs 15 cycles. CPI = 1 + 0.25 × 0.4 × 1 + 0.15 × 0.10 × 15 = 1 + 0.10 + 0.225 = 1.325. The branches cost more than twice as much as the loads, though they are fewer, because each miss is expensive. At 3 GHz this core runs 3 / 1.325 ≈ 2.26 billion instructions per second.
Now deepen the pipeline. Cut each stage in two, so the misprediction penalty grows from 15 to 30 cycles, and the clock rises not by 2 but by about 1.6 (register overhead eats the rest): from 3 GHz to 4.8 GHz. The load-use stall also doubles. CPI = 1 + 0.25 × 0.4 × 2 + 0.15 × 0.10 × 30 = 1 + 0.2 + 0.45 = 1.65. Speed = 4.8 / 1.65 ≈ 2.91 billion per second, only about 28% faster, and the dynamic power rises faster than the clock, because the clock tree and registers double and the voltage often has to go up.
intuition: A car factory does not build one car at a time from start to finish; each station does one job on a different car, and a car leaves the line every few minutes even though building one takes hours.
The design is natural because most of a processor is idle if an instruction uses one part at a time. Instruction fetch hardware waits while the ALU works, and the ALU waits while the cache is read. Giving every part something to do in every cycle is the cheapest way to use the silicon. The cost is that the line must stay in step: all stations advance together on the clock, and anything that breaks the order (a dependency, a branch) forces the line to wait or to throw away work. The speed of the machine is therefore a balance between how many stages the work can be cut into and how often the order is broken.
mistakes: People often think pipelining makes each instruction faster. In fact each instruction takes the same time or slightly longer, because of the register overhead between stages. The gain is that many instructions are in flight, which raises throughput.
People often think a deeper pipeline is always better because the clock can be faster. In fact each added stage adds register delay, raises the cost of every misprediction and flush, increases power, and makes forwarding harder. In practice the net gain turned negative beyond roughly 15 to 20 stages, which is why the Pentium 4 line was abandoned.
People often think the CPU executes instructions strictly one after another, so code order is all that matters. In fact many instructions overlap, and the order of dependencies matters: a chain where every instruction needs the previous result runs at one instruction per latency of the operation, while independent instructions overlap. Two loops with the same instruction count can differ by 3 to 4 times in speed.
People often think a stall means the whole CPU stops. In fact a stall inserts a bubble in the stages behind the hazard; the stages ahead keep going, and other work (in an out-of-order core) may continue around the bubble.
friction: Every hazard costs cycles, and they are hard to remove. Dependent chains limit the speed to the latency of the operation: a floating-point add with latency 4 in a loop that adds into one accumulator gives one add every 4 cycles, however wide the core is. Splitting into several accumulators lets the adds overlap. Loads that miss the L1 cache stall dependent instructions for 4 to 5 cycles (L1 hit latency) up to hundreds of cycles (memory), and a simple in-order pipeline cannot do anything else meanwhile.
Branches are the main limit of depth. Because the penalty is the pipeline length from fetch to the point where the branch resolves, a deeper design pays more per miss, and the cost cannot be avoided by software except by removing branches. Power and area also grow: more registers, a faster and larger clock tree (a major part of dynamic power), more forwarding paths. Clock skew and register overhead (setup and clock-to-output times, around 20 to 40 ps in practice) become a larger share of a shorter cycle, so each new stage yields less gain. Fast clocks also run into the power wall: from about 2004 clock speeds stopped rising at 3 to 5 GHz.
Complexity is a final cost. Precise exceptions, interrupts in the middle of a pipeline, self-modifying code, and instructions with variable length (x86) all interact with the pipeline. x86 processors decode instructions into simpler internal operations for exactly this reason. Pipeline timing is also the root of side-channel leaks: what an instruction does speculatively affects state that others can measure.
practice: Write code that keeps the pipeline fed. Break long dependency chains: use several accumulators in reductions, process independent elements together, and unroll loops where the compiler does not. Avoid unpredictable branches in hot loops (use arithmetic, conditional moves, or sort the data first), since each miss costs 15 to 20 cycles, about the time to do 60 to 80 simple operations on a wide core. Avoid dependent loads (pointer chasing) when you can lay data out in arrays.
Measure instead of guessing. On Linux, `perf stat` shows instructions per cycle (IPC), branch-misses and cycles; an IPC below 1 on a modern core suggests stalls from memory or branches, while 3 or 4 means the pipeline is well fed. `perf stat -e cycles,instructions,branches,branch-misses` and Intel VTune's or Linux's top-down analysis divide the lost slots into front-end bound, bad speculation, back-end bound and retiring. The top-down method tells you whether to look at code layout, branches or memory.
At the systems level, the same idea explains why engines such as Spark with whole-stage code generation fuse operators into tight loops with few branches and no virtual calls: the generated loop keeps instructions flowing, while an interpreted row-by-row pipeline with a virtual call per row stalls on indirect branches. Vectorized engines (Photon, DuckDB) process batches of values per operation to the same end. When you compare two implementations, compare instructions per cycle as well as time, because a faster algorithm that issues more stalls may still lose.
tradeoffs: Choose a short pipeline (2 to 5 stages) for microcontrollers and ultra-low-power cores, where area, energy and predictable timing matter and clock speeds are below about 500 MHz; you give up clock speed and peak performance. Choose a medium pipeline (10 to 20 stages) with strong prediction and out-of-order execution for server and phone cores that must run unpredictable code at 3 to 5 GHz; you pay with area, power and design complexity.
Choose a wider core over a deeper one when you need more speed: issuing 6 to 8 instructions per cycle raises throughput without raising the misprediction penalty, but the hardware that finds independent instructions grows faster than linearly with width. Choose a deeper pipeline only when the workload is highly predictable (streaming, vector code) and power is available, as in some GPU and DSP designs.
Choose in-order execution when power per operation matters and the workload has much parallelism available across threads (GPUs, small efficiency cores); the hardware is simple and energy per instruction low. Choose out-of-order when single-thread latency matters, since it hides the stalls an in-order pipeline suffers.
For software, choose branchless or data-parallel code when branches depend on data you cannot predict; choose simple branches when the pattern is regular, because the predictor handles them for free and the code is clearer.
interview: Why does pipelining increase throughput but not reduce latency? What limits the speedup to less than the number of stages? || Each instruction still passes through all stages, plus pipeline-register overhead, so its latency does not fall. Throughput rises because one instruction completes per cycle once the pipeline is full. Speedup is below the stage count because stages are unequal in delay (the clock follows the slowest), registers add overhead, and hazards insert bubbles.
Explain data forwarding. Why does a load followed by a dependent add still stall? || Forwarding routes a result from a later pipeline register (EX/MEM or MEM/WB) to the ALU input that needs it, selected by register-number comparators, so the consumer need not wait for write-back. A load produces its value only after the MEM stage, which is one stage too late for the next instruction's EX in the same cycle, so one bubble is unavoidable.
A loop sums 1,000,000 doubles into a single variable and runs at 4 cycles per element. How would you speed it up, and what is the limit? || The loop-carried dependency on the sum is limited by the 4-cycle add latency. Use several independent accumulators (for example 8) or SIMD, then combine at the end. The limit becomes the throughput of the floating-point units (for example 2 adds per cycle) or memory bandwidth, whichever is lower. Note that this changes the rounding order, which may be a problem for exact reproducibility.
Why did the Pentium 4 fail with a 31-stage pipeline? || The misprediction penalty and stall costs grew with depth, register overhead and clock-tree power grew too, and clock speeds hit the power wall at about 3.8 GHz. Instructions per cycle fell below those of the shorter Pentium III-derived cores, so higher clock did not give higher performance. Intel moved to the shorter Core design in 2006.
How does a pipeline handle an exception in the middle of the instruction stream, such as a page fault in the MEM stage? || The faulting instruction is marked, younger instructions in earlier stages are squashed so they have no effect, older instructions are allowed to finish, and the faulting PC is saved for the handler. This gives a precise exception: the state looks as if instructions ran one by one up to the fault. Out-of-order cores keep a reorder buffer so that commit happens in order.
quiz: Name the five classic pipeline stages in order. || Instruction fetch, decode and register read, execute, memory access, write-back.
Why is the clock period of a pipeline set by the slowest stage? || All pipeline registers capture their inputs at the same clock edge, so every stage must finish its logic within one cycle. If one stage needs 200 ps, the cycle cannot be shorter, and faster stages wait.
What is a data hazard, and how does forwarding remove most of the stalls? || A data hazard occurs when an instruction needs a result that an earlier instruction has computed but not yet written to the register file. Forwarding sends the result from the EX/MEM or MEM/WB pipeline register straight to the ALU input, saving two or three cycles.
A core has base CPI 1, 20% branches, 95% prediction accuracy and a 20-cycle misprediction penalty. What is the CPI? || CPI = 1 + 0.20 × 0.05 × 20 = 1.2. The branch penalty adds 20% to execution time.
Would you choose to double a pipeline's depth to gain clock speed? Why or why not? || Usually not. Deeper pipelines multiply the misprediction and stall penalty, register overhead means the clock rises by less than the stage count, and power rises faster than speed. Gains are larger from better prediction, wider issue and out-of-order execution.

value: A pipelined processor that runs instructions strictly in program order stops whenever one instruction has to wait. If a load misses the cache and needs 80 ns (about 300 cycles) to reach memory, every later instruction waits behind it, even instructions that have nothing to do with the load. Out-of-order execution removes this waste. The core looks ahead at a window of upcoming instructions, finds the ones whose inputs are ready, and runs them while the older ones wait. Superscalar means the core can start several instructions in the same cycle (4 to 8 in current cores). Together they find parallelism inside ordinary sequential code, with no change by the programmer.
The result must still look sequential. The program must behave as if each instruction ran completely before the next one started, including when an exception occurs. So the hardware executes out of order, but retires (commits) results in the original order, using a reorder buffer. This is the central trick: reorder freely inside, look orderly outside.
Out-of-order execution is a large part of why single-thread speed kept growing from the mid-1990s: the same binary ran faster on each new core with a bigger window and more units. It also changes how performance behaves for the layer above. The general-purpose CPU (L1) hides arithmetic and cache latency through it. Independent work runs in parallel without threads, so a loop that issues many independent loads can overlap their memory waits (memory-level parallelism), while a loop that follows a pointer chain cannot.
The lower layers contribute the structure. CPU pipelining (L3) supplies the in-order front end and the commit stage that the out-of-order engine sits between. Graph theory (L4) supplies the way to think about the window: the instructions form a data-dependency graph, a directed acyclic graph in which an edge goes from the instruction that produces a value to the one that consumes it. Any instruction whose incoming edges are all satisfied can run; the length of the longest path (the critical path) is the lower limit on the running time, whatever the width of the machine.
terms: Instruction window — the set of decoded instructions in flight, waiting to execute or to retire; its size is the ROB size.
Reorder buffer (ROB) — a queue holding all in-flight instructions in program order; instructions leave it from the head, in order, when they complete.
Register renaming — mapping each architectural register (the few names in the instruction set) to a fresh physical register, so that unrelated uses of the same name do not conflict.
Reservation station (scheduler) — a buffer where an instruction waits until all its source operands are available.
True (RAW) and false (WAR, WAW) dependencies — read-after-write is real data flow; write-after-read and write-after-write only come from reusing a register name, and renaming removes them.
Retire (commit) — the moment an instruction's result becomes architecturally visible, in program order.
Speculative execution — running instructions beyond a branch or a possible fault before it is known whether they should run; wrong work is discarded.
Memory-level parallelism (MLP) — the number of cache misses outstanding at the same time.
history: Dependency-driven execution started in the 1960s. The CDC 6600 (1964) had a scoreboard, designed by James Thornton, that let instructions run when their operands and a functional unit were free. Robert Tomasulo at IBM then designed the floating-point unit of the IBM System/360 Model 91 (1967) with reservation stations, tags that name where a value will come from, and a common data bus that broadcasts each result to all waiting instructions. This also renamed registers implicitly and was the origin of the whole family of designs.
Tomasulo's scheme had a problem: it could not make exceptions precise, because results were written out of order. The solution came in the mid-1980s. James Smith and Andrew Pleszkun (1985) described the reorder buffer for precise interrupts, and Yale Patt, Wen-mei Hwu and Michael Shebanow's HPS (1985) combined renaming, out-of-order execution and in-order commit with branch prediction. These ideas reached products slowly because they needed many transistors. The Pentium Pro (1995) was the first x86 processor to do it, translating x86 instructions into simpler micro-operations, with a 40-entry reorder buffer and three-wide issue. The Alpha 21264 (1998), MIPS R10000 (1996) and IBM POWER cores followed.
Since then the windows have grown steadily: about 224 entries in Intel Skylake (2015), 512 in Golden Cove (2021), about 320 in AMD Zen 4, and, from reverse engineering, over 600 in Apple's M1 performance cores. Widths grew as well, with decoders of 6 to 8 instructions per cycle. In 2018, the Spectre and Meltdown attacks showed that speculation leaves traces in caches that attackers can read, and the whole industry had to add mitigations that cost some performance.
how: An out-of-order core has an in-order front end, an out-of-order middle, and an in-order back end.
Front end. The core fetches several instructions per cycle (guided by the branch predictor) and decodes them into micro-operations. This is the in-order part, the same as in the simple pipeline.
Rename. Each micro-operation's source registers are looked up in a rename table that says which physical register currently holds that architectural register. The destination gets a new physical register from a free list. A core with 16 architectural registers may have 180 to 300 physical ones. After this step, false dependencies are gone: two instructions that both write "r4" write two different physical registers and need not wait for each other. Only true data flow (RAW) remains, which is the edge set of the dependency graph.
Dispatch. The renamed operation is placed in the reorder buffer (at the tail, in program order) and in a scheduler. If the operation is a load or store, it also gets an entry in the load queue or store queue. If the machine runs out of ROB entries, scheduler slots, physical registers or queue entries, the front end stalls; whichever fills first limits the window.
Issue. Every scheduler entry tracks whether its source physical registers are ready. When a producer finishes, it broadcasts its destination register tag; each waiting operation compares the tag with its sources (the wakeup step, Tomasulo's common data bus in modern form). A selection circuit then picks ready operations, oldest first, and sends them to free execution ports. A modern Intel core has about 8 to 12 ports for integer, vector, load and store operations. Independent operations run in the same cycle, up to the number of ports. This is the graph execution: each cycle, run a set of ready nodes. The length of the longest dependency chain bounds the time regardless of width.
Execute and write back. Results go to the physical register file and are forwarded to waiting operations. Loads check the store queue to see whether an older, not yet committed store wrote the same address and, if so, take the value from it (store-to-load forwarding). Because the core does not know addresses early, it predicts that a load does not depend on earlier stores, runs it, and checks later; if wrong, it flushes and repeats.
Retire. The ROB head is examined each cycle. When the oldest instructions have completed without a fault, up to 4 to 8 retire per cycle: their results become permanent, the old physical registers are returned to the free list, and stores are released to write to the cache. Because retirement follows program order, an exception is precise: everything older has retired, nothing younger has changed architectural state.
Stores are handled with extra care, because they cannot be undone. A store executes only as far as computing its address and data, and waits in the store queue. It writes to the L1 cache after it retires, and the store buffer drains in program order on x86, which is part of why x86 has the fairly strong total-store-order memory model. Loads may run early and pass older stores to other addresses, so other cores can observe a load before an earlier store; that is the one reordering x86 allows, and the memory-model concept explains it in detail.
Speculation ties this to branch prediction. The front end fetches past branches using predictions. If a branch resolves the wrong way, the core discards all younger operations in the ROB and scheduler, restores the rename table from a checkpoint, and refetches, which costs the misprediction penalty (about 15 to 20 cycles). Correct predictions let the window fill with useful future work.
Two limits shape performance. First, the window size: the core can only reorder inside its ROB, so a miss that takes 300 cycles blocks retirement when it reaches the ROB head, and the window fills up in 224 / 4 ≈ 56 cycles at 4 instructions per cycle; after that the core idles. Second, the dependency graph: a chain of dependent operations cannot be sped up by width.

example: Take this sequence, where the first load misses the cache and needs 100 cycles, a multiply needs 3 cycles, and other operations need 1.
I1: ld r1, [r8]   (miss, 100 cycles)
I2: add r2, r1, r3   (needs r1 from I1)
I3: mul r4, r5, r6   (independent)
I4: add r5, r4, 1   (needs r4 from I3; writes r5, which I3 reads)
I5: sub r4, r7, r8   (writes r4, which I3 also writes)
An in-order core runs I1, waits 100 cycles, runs I2, then I3 (3), I4 (1), I5 (1): about 106 cycles. An out-of-order core renames first. I3 writes P10 (was r4), I4 reads P10 and writes P11 (new r5), I5 writes P12 (new r4). The false dependencies (I4 overwriting r5 which I3 reads, I5 overwriting r4 which I3 writes) disappear. Now I3 and I5 run in the first cycles beside I1, I4 runs after I3 finishes at cycle 3, and everything except I2 is complete by cycle 5. I2 runs at cycle 101. The ROB holds the results; retirement waits for I1 at its head, and then I2 to I5 retire together within one or two cycles. Total: about 102 cycles, and the work after I1 was free.
The gain here is only a few cycles because the window was small. The real benefit comes with loops. Consider a loop that does `sum += a[idx[i]]` with 10 instructions per iteration, where the load misses to memory (100 cycles) and loads in different iterations are independent. The core has a 224-entry ROB and 10 line fill buffers (the limit on outstanding L1 misses). In-order: each iteration waits for its load, so 100 cycles per iteration, and 1,000 iterations take about 100,000 cycles. Out-of-order: the ROB holds 22 iterations, so the core starts 22 loads, limited by fill buffers to about 10 at once. The throughput becomes about 100 / 10 = 10 cycles per iteration, so 1,000 iterations take about 10,000 cycles. A 10 times speedup comes from memory-level parallelism. Now change the loop to `p = p->next` (pointer chasing). Each load needs the previous result, the graph is a single chain, and even a huge window gives no parallelism: 100 cycles per node in both cores.
This shows what the dependency graph means in practice: the speed is bounded by the critical path (the chain), and by the window and the number of misses the hardware can track.
intuition: A chef reads the whole order list, starts the soup while the oven heats, but plates the dishes in the order the table asked for.
The design is natural once you see that program order is only a convenient way to write down a dependency graph. The machine does not need to follow the writing order, only the graph; the extra order (names reused, one instruction per line) is accidental. So the hardware strips off the accidental part (renaming removes name conflicts), runs whatever is ready (graph execution), and then puts the visible effects back into the writing order (the reorder buffer), so the programmer's model is unchanged. The graph view also explains the limits: width helps only when the graph is wide, and window size helps only when the graph has independent parts far apart in the program. All the cleverness serves one promise: the same sequential program, the same results, faster.
mistakes: People often think the CPU executes instructions in the order of your code. In fact it executes in dependency order and only commits in program order. The compiler and the core both reorder; what you see is the sequential illusion. For one thread this is invisible, but other cores can see weaker ordering of memory operations (see the memory model concept).
People often think a wider or bigger core always runs code faster. In fact most code is limited by dependency chains, branch mispredictions and cache misses, not by width. Typical programs reach an IPC of about 1 to 2 on cores that could issue 6, and extra width only helps code with independent work.
People often think out-of-order execution hides all memory latency. In fact it hides latency only up to the window size. A miss of 300 cycles fills a 224-entry window in about 56 cycles at 4 instructions per cycle, and then the core stalls. Cache misses still dominate many workloads, and the main cure is independent misses (memory-level parallelism), prefetching and better data layout.
People often think speculation is invisible. In fact squashed instructions leave no architectural trace, but they do leave microarchitectural traces: cache lines they loaded stay in the cache. Spectre and Meltdown (disclosed in January 2018) read such traces through timing.
friction: The costs are large. An out-of-order engine spends far more area and energy on the scheduler, rename logic, ROB and wide register files than on the execution units; the cost of the wakeup and select logic grows faster than linearly with window size and width, and it must complete in one clock cycle. This is why efficiency cores in phones and servers are often in-order or small out-of-order designs, and why a big out-of-order core may use several times the energy per instruction of a small one.
Performance gains are shrinking. Wall (1991) and later studies found limited instruction-level parallelism in typical code, because of branches and true dependencies; doubling the window gives sub-linear gains (Pollack's rule of thumb says performance grows about with the square root of the complexity). Memory latency, now hundreds of cycles, is longer than any practical window can cover.
Security is a lasting problem. Spectre (variants 1 and 2) trains the branch predictor so that the victim speculatively reads a secret and uses it as a cache index, which an attacker then measures. Meltdown used the fact that Intel cores read kernel memory speculatively before the permission fault was raised at retirement. Mitigations include kernel page-table isolation (KPTI), retpolines, speculation barriers and microcode changes; they cost from a few percent to tens of percent on some system-call-heavy workloads, and newer hardware has fixes for some variants. Related attacks on speculation keep appearing, and no one has a complete solution that keeps the full performance.
Finally, the complexity makes verification hard, and the behaviour hard to predict: the same code can vary in speed by several times with alignment, branch history or store-forwarding conflicts. Performance on out-of-order cores is best measured, not predicted.
practice: Give the core independent work. In reductions use several accumulators or SIMD so the dependency chain is shorter. In loops over data, make loads independent of each other (index arrays instead of linked lists), so that many misses overlap. Batch lookups: probing a hash table for 8 keys together (interleaved, or with software prefetch) lets the core overlap 8 misses, and database engines use this technique ("group prefetching") for hash joins.
Avoid long dependent chains: pointer chasing in linked lists and trees, serial dependence through memory (store followed by a load of the same address), and division-heavy loops. Prefer arrays, B-trees with wide nodes, and layouts that put what a step needs in one cache line.
Measure with hardware counters. `perf stat` gives IPC; a top-down analysis (`perf stat --topdown`, or tools such as Intel VTune) shows the fraction of slots lost to front end, bad speculation, back-end memory and back-end core limits. If "backend memory bound" is high, look for miss counts and MLP; if "bad speculation" is high, look at branches.
Be careful with security. Do not assume an operation that was not committed has no effect when handling secrets; use constant-time code and the compiler's speculation-hardening options for sensitive code, and keep microcode and kernel mitigations on in multi-tenant environments. For data engineering, expect 2 to 3 times differences between code that exposes independent work (columnar, vectorized, batch-at-a-time) and code that processes one row through many dependent calls.
tradeoffs: Choose a big out-of-order core when single-thread latency matters and code is irregular (databases, compilers, interactive services): you pay several times more area and energy per instruction. Choose many small in-order or narrow cores when the work is highly parallel and regular (GPUs, network processing, web servers with many connections), because throughput per watt is better.
Choose a larger window when your workload has independent cache misses to overlap (analytics scans, hash probes): gains can be 2 to 10 times for memory-bound loops. Do not pay for a larger window when the code is dominated by dependent chains (pointer chasing) or branch mispredictions, where it adds nothing.
Choose to keep speculation mitigations on for multi-tenant and browser-facing systems, accepting a few percent to tens of percent in cost on affected workloads; choose to relax them only on isolated, single-tenant batch machines where all code is trusted, and document the decision.
Choose software parallelism (threads, SIMD) as well as hardware: out-of-order hardware extracts instruction-level parallelism up to a window of a few hundred instructions; threads and vectors reach parallelism the window can never see, but need programming work and may add synchronization cost.
interview: Explain register renaming. Which hazards does it remove and which does it keep? || Renaming maps each architectural destination to a new physical register, using a rename table and a free list. It removes write-after-read and write-after-write hazards, which only exist because names are reused. It keeps read-after-write, the true data flow, because a consumer must still wait for its producer's value.
Why must retirement be in order, and how does the core recover from a branch misprediction? || In-order retirement gives precise exceptions and a sequential view for the program: everything older has committed, nothing younger has. On a misprediction, the core squashes all instructions younger than the branch in the ROB and scheduler, restores the rename table from a checkpoint (or walks the ROB), frees physical registers, and refetches from the correct target.
Two loops each do 1 million loads from a 1 GB array. One uses `a[idx[i]]` with random idx; the other follows a linked list in random order. Why does one run about 5 to 10 times faster on an out-of-order core? || In the first loop the load addresses do not depend on earlier loads, so the core issues many misses at once, limited by the ROB and the line fill buffers (about 10 to 16). In the linked list, the address of the next load is the result of the previous one, so misses are serialized. The first loop is bounded by memory bandwidth and MLP, the second by latency.
How did Meltdown exploit out-of-order execution? || A user program issues a load from a kernel address. The core executes it out of order and passes the loaded value to dependent instructions, which use it to touch a cache line chosen by the secret value, before the load's permission fault is raised at retirement. The fault squashes the architectural result, but the cache line stays loaded, and the attacker finds it by timing. KPTI removes kernel mappings from user page tables.
What limits the useful size of the reorder buffer? || Cost and cycle time: the scheduler's wakeup and select logic, the register files and the ROB itself must all be searched and updated each cycle, so area and power grow faster than linearly. Benefit also shrinks, because branch mispredictions limit how far ahead correct work exists, and long memory latencies exceed any practical window.
quiz: Why does an out-of-order core retire instructions in program order? || To keep exceptions precise and the sequential illusion: when an instruction faults, all older instructions have committed and no younger ones have changed architectural state, so the handler and program can resume correctly.
What does register renaming remove, and why does it help? || It removes false dependencies (WAR and WAW) that come from reusing register names, by giving each write a new physical register. Instructions that only share a name can then run in parallel; only true data flow limits them.
A 256-entry ROB core retires 4 instructions per cycle. A load misses to memory for 300 cycles. Roughly how soon does the window fill, and what happens then? || 256 / 4 = 64 cycles. After that, the front end cannot add instructions, because the miss blocks retirement at the ROB head, and the core idles for the remaining 236 cycles or so.
In a loop with an independent L3-missing load every 10 instructions, a 224-entry ROB, and 10 fill buffers, about how many misses overlap and what limits it? || The ROB holds about 22 iterations, so up to 22 loads could be in flight, but the 10 line fill buffers limit outstanding L1 misses to about 10. Throughput is therefore about 10 times that of a core that serializes the misses.
When would you prefer an in-order core to an out-of-order one? || When energy and area per operation matter more than single-thread speed, and when parallelism comes from many threads or regular data, for example GPU lanes, small efficiency cores, microcontrollers, or hard real-time systems that need predictable timing.

value: About one instruction in five or six is a branch: an if, a loop test, a function call or return. A pipelined CPU needs to fetch the next instruction in every cycle, but a branch is resolved only several stages later, 15 to 20 cycles deep in a modern core. Waiting would waste most cycles. So the CPU guesses: it predicts whether the branch is taken and where it goes, keeps fetching and executing along the guess, and checks later. If the guess was right, nothing was lost. If it was wrong, all the work done on the wrong path is thrown away and the pipeline restarts at the right place, which costs the misprediction penalty of roughly 15 to 20 cycles, the time of 60 to 100 simple instructions on a wide core.
Modern predictors are right for 95% to 99% of branches in typical programs, and this is the reason a deep, wide pipeline is worth building at all. With a 20-cycle penalty, a branch every 6 instructions and 5% misses, a core would lose about 1 cycle for every 6 instructions, a visible fraction; at 50% misses (random data) it loses 10 cycles per 6 instructions and the core runs several times slower. This is the effect behind a famous result: summing the values above a threshold in an array runs about 6 times faster when the array is sorted first, though the code is the same.
The layer above feels this directly. Vectorized query engines replace branches by selection vectors and masks so that the data cannot cause mispredictions. The Volcano iterator model calls next() through a pointer for every row, an indirect branch that is hard to predict. General-purpose CPUs (L1) keep deep pipelines full by guessing. Two lower concepts make the guessing work. Probability (L4) supplies the idea of the saturating counter as a tiny estimate of how likely a branch is to be taken in its context. Markov chains (L4) supply the idea that the recent history of outcomes is a state from which the next outcome can be predicted: a predictor with h bits of history is an order-h Markov model learned online.
terms: Taken / not taken — a conditional branch either jumps to its target (taken) or continues with the next instruction (not taken).
Branch target buffer (BTB) — a cache that maps the address of a branch to its target address, so the fetch unit knows where to go next before decoding.
Saturating counter — a small counter (often 2 bits) that goes up when the branch is taken and down when not, but stops at its minimum and maximum; its top bit is the prediction.
Global history — a shift register holding the outcomes of the last several branches in the program, used to find correlation between branches.
gshare — a predictor that indexes a table of counters with the branch address combined (XOR) with the global history.
TAGE — a predictor with several tables indexed by different history lengths, using tags to check matches and preferring the longest matching history.
Misprediction penalty — the cycles lost because the wrong-path instructions must be flushed and fetch restarts.
Return address stack (RAS) — a small hardware stack that predicts the target of return instructions by remembering call sites.
history: Early machines used static rules, such as "backward branches are taken" (they are usually loops) and "forward branches are not taken". In 1981 James E. Smith studied dynamic prediction and introduced the table of saturating counters indexed by branch address, now called the bimodal predictor. The two-bit version tolerates a single surprise: a loop exit does not flip the next prediction.
The big step came in 1991, when Tse-Yu Yeh and Yale Patt described two-level adaptive prediction: use the pattern of recent outcomes (the history) to select a counter. Scott McFarling (1993) of DEC proposed gshare, which XORs the branch address with the global history to spread the table use, and the combining (tournament) predictor, which learns whether a bimodal or a gshare predictor is better for each branch. The Alpha 21264 (1998) used a tournament predictor. In 2001, Daniel Jiménez and Calvin Lin introduced the perceptron predictor, which learns a weighted sum of history bits and so can use much longer histories; AMD's Zen cores (2017 onward) are known to use perceptron-style prediction.
André Seznec's TAGE predictor (with Pierre Michaud, 2006, building on Michaud's PPM-like predictor of 2005) became the standard high-accuracy design: it keeps several tables with geometrically increasing history lengths (for example 5, 10, 20, 40, 80, 160 branches), each entry tagged, and takes the answer from the longest history that hits. Academic competitions (the Championship Branch Prediction workshops, since 2004) pushed accuracy up, and TAGE-like designs dominate; Intel and Apple do not publish details, but reverse engineering suggests similar ideas. Large BTBs (about 12,000 entries in Intel's Golden Cove) and separate indirect-branch and return predictors complete the front end. In 2018, Spectre showed that these predictors can be trained by an attacker, and vendors added mitigations.
how: A predictor answers three questions at fetch time, before the instruction is even decoded: is there a branch at this address, is it taken, and what is the target.
Detecting the branch and its target is the job of the branch target buffer. The fetch address indexes it; if it hits, the entry says "branch of this type, last target T". Taking the target from the BTB lets the front end fetch the next block in the very next cycle, with no decode delay. For returns, a return address stack pushes the address after each call and pops it at each return; with 16 to 32 entries it predicts returns almost perfectly. Indirect jumps (virtual calls, switch tables) use a separate predictor indexed by the address and history, as one branch can have many targets.
The direction of a conditional branch comes from tables of counters. The simplest is the two-bit saturating counter: states 0 and 1 mean "not taken" (strongly and weakly), 2 and 3 mean "taken". A taken branch adds 1, a not-taken subtracts 1, both stopping at 0 and 3. The prediction is the top bit. The counter is a small statistical estimate of P(taken) for that branch; because it needs two surprises in a row to change its mind, one odd outcome does not disturb a branch that is almost always taken. A loop that runs 10 iterations is taken 9 times and not taken once, and a two-bit counter mispredicts only the exit. A one-bit predictor would also mispredict the first iteration of the next run.
Counters indexed only by address cannot see patterns across branches. Two-level predictors add history. A global history register holds the outcomes of the last h conditional branches (for example h = 12). In gshare, the index is (branch address XOR history), so the same branch with different recent history reaches different counters, and correlations such as "if (x > 0) ... later if (x > 5)" are learned. In Markov terms, the history is the state and each counter is the learned transition: it estimates the next outcome given the last h outcomes. A longer history captures longer patterns but needs exponentially more table entries to hold all contexts, and long histories dilute the training for simple branches.
TAGE solves this trade-off. It has a base bimodal table and several tagged tables. Table i uses a history of length L_i (L_i grows geometrically) hashed with the address as the index, and stores a partial tag, a counter and a usefulness bit. At prediction time, all tables are looked up in parallel; the table with the longest history whose tag matches provides the prediction, and the next longest is kept as an alternative. On a misprediction, the predictor allocates an entry in a table with longer history, so it learns the longer context only when a shorter one failed. This is the idea of the PPM compression family: use the longest context that has been seen before.
Speed and size pull in opposite directions. A big predictor with many tables needs two or three cycles to answer, but the front end wants a new prediction every cycle. So cores use a small, fast predictor first, and a slower, more accurate one that can override it a cycle or two later; when they disagree, the front end loses a bubble of a cycle or two, which is far cheaper than a full flush. Many designs add a loop predictor (which counts iterations) and a small statistical corrector next to TAGE for branches that history cannot explain. Total predictor state is tens of kilobytes, comparable to an L1 cache, and it is read in the same cycle as the fetch.
The pipeline's flush logic uses the prediction. Each predicted branch is tagged in the reorder buffer with its guessed outcome. When the branch executes and the real outcome differs, the core squashes all younger instructions, restores the rename state from a checkpoint taken at the branch, and redirects fetch. The predictor is updated with the actual outcome, either at execution or at retirement. Because the pipeline is deep, the global history itself is updated speculatively and repaired on a flush.

example: Trace a loop branch that is taken three times and then not taken, repeating: T T T N T T T N. Start a two-bit counter at 3 (strongly taken).
Iteration 1 (T): predict taken, correct, counter stays 3. Iteration 2 (T): correct, stays 3. Iteration 3 (T): correct, stays 3. Iteration 4 (N): predict taken, wrong. The counter drops to 2. Next period, iteration 1 (T): the counter is 2, so predict taken, correct, and the counter moves up to 3. So in every period of four there is exactly one miss: accuracy is 75%. A one-bit predictor, which simply repeats the last outcome, misses twice per period (the N, and then the T after it): 50%.
Now give a predictor a 3-bit global history and a counter per history. The histories seen before each outcome are: after N T T the next is T; after T T T the next is N; after T T N the next is T; after T N T the next is T. Each of these four contexts always leads to the same outcome, so after one pass each counter has learned its answer and the predictor is right 100% of the time. 
Now the cost of a random branch. The code is `for (i = 0; i < N; i++) if (data[i] >= 128) sum += data[i];` with N = 100 million bytes drawn uniformly from 0 to 255. The branch is taken with probability 0.5, independent of history, so no predictor can do better than 50%. Per iteration the cost is about 1.5 cycles of work plus 0.5 × 15 = 7.5 cycles of penalty, about 9 cycles, so 100 million iterations at 3 GHz take 0.3 seconds. If the data is sorted, the branch is not taken for the first half and taken for the second half, so it misses only a few times, and the loop runs at about 1.5 cycles per element: 0.05 seconds. That is the factor of six. The compiler can also remove the branch, with `sum += (data[i] >= 128) ? data[i] : 0` turned into a conditional move or SIMD mask (compilers often do this at -O2 or -O3). Then sorted and unsorted data run equally fast.
intuition: A driver who knows the route turns before reading the sign, and is wrong only when the road changes.
The idea is natural because most branches are not coin flips. Loops repeat, error checks nearly always pass, and the outcome of one test often tells you about the next. Nearby outcomes have statistical structure, and a table that remembers "what happened last time in this situation" captures it cheaply. The cost of being wrong is high but fixed, and the gain from being right is large, so even a small structure that is right 95% of the time pays for itself many times. Longer memory finds subtler patterns, but memory costs area, so the best designs spend long histories only where short ones fail.
mistakes: People often think the predictor decides by looking at the data or at the condition. In fact it knows nothing about the condition; it sees only the address and the past outcomes. If the outcome depends on random data, the history carries no information and no predictor can do better than the data's own skew.
People often think a mispredicted branch just costs a few cycles. In fact the penalty equals the depth from fetch to branch resolution (15 to 20 cycles) and the lost work is bigger than that, because a wide core could have executed 4 to 6 instructions in every one of those cycles. A branch with 5% misses can be a leading cost in a hot loop.
People often think `likely()` and `__builtin_expect` train the hardware predictor. In fact they change only how the compiler lays out code (the likely path becomes the fall-through path), which helps instruction fetch. The CPU predictor still learns by its own history; on x86 there are no branch hint prefixes that modern cores honour.
People often think replacing a branch with arithmetic is always faster. In fact it is faster only when the branch is hard to predict. A well-predicted branch costs almost nothing and skips work; a branchless version always does the work of both sides and adds a data dependency. When the branch is predictable (above about 95%), keep it.
friction: Accuracy has diminishing returns, and the last few percent cost a lot of chip area. Championship predictors with 64 KB of state reach about 99% on benchmark traces, but data-dependent branches (parsing, compression, searching, interpreters, hash-table probes with chains of different length) remain at 70% to 90% or worse. Interpreters and virtual-call heavy code suffer from indirect branches whose target depends on the data.
Capacity and aliasing matter at scale. Large server programs (databases, browsers, JVMs) have far more hot branches than the tables hold; two branches that share an entry disturb each other, and a context switch or a call into the kernel pollutes the tables. Cold code, such as the first run of a function, is predicted poorly because nothing has been learned yet; this is one reason for warm-up effects in benchmarks.
Predictors also became a security problem. Spectre variant 1 trains a conditional-branch predictor so that a bounds check is "predicted" to pass for an out-of-range index, and the speculative load leaves a trace in the cache. Variant 2 poisons the indirect-branch target predictor to make the victim speculatively run an attacker-chosen gadget. Mitigations include retpolines (which replace indirect branches with a return sequence that the predictor cannot be steered through), indirect-branch prediction barriers, flushing predictors on context switches, and hardware modes (IBRS, STIBP). They cost performance, from a few percent to more on indirect-branch-heavy code. Predictor state is also a side channel by itself (BranchScope, 2018).
practice: Measure before changing. `perf stat -e branches,branch-misses ./prog` gives the miss rate; for general code, 1% to 3% is common, and a hot loop above 5% deserves a look. `perf record -e branch-misses` and `perf annotate` show which branches miss. A top-down analysis puts "bad speculation" as a fraction of pipeline slots.
Remove unpredictable branches from hot loops. Options: write the condition as arithmetic or a conditional move (`x = cond ? a : b` often compiles to cmov); use SIMD compare and mask operations; process data in a form where branches become predictable (sort or partition the data by the condition, group equal types together); use lookup tables instead of long if-else chains. Verify in the compiled output, because the compiler may or may not remove the branch. Profile-guided optimization (PGO) lets the compiler lay out code by real branch frequencies, and the JVM's JIT does this by default using runtime profiles.
In data systems, this is why vectorized engines (Photon, DuckDB, ClickHouse) evaluate predicates as a loop over a batch that writes a selection vector or bitmask without branches, and why Spark's whole-stage code generation removes per-row virtual calls: it replaces indirect calls that the predictor handles poorly with straight-line code. When writing hot code, avoid virtual dispatch and large `switch` statements inside inner loops, and prefer monomorphic call sites where one target dominates.
tradeoffs: Choose to keep a branch when it is predictable (above about 95% in one direction, or following a short pattern), because the predictor makes it nearly free and you skip work. Choose a branchless form when the outcome is data-random and the two sides are cheap (a few instructions): you do both sides' work but never pay 15 to 20 cycles. For expensive sides (a function call, a memory access), the branch is usually still better, because branchless code would perform the expensive side every time.
Choose a larger and more complex predictor in a high-performance core, where each point of accuracy saves several percent of cycles; choose a small bimodal predictor in a microcontroller or an efficiency core, where area and energy dominate and the pipeline is only 3 to 8 stages deep, so the penalty is 2 to 5 cycles anyway. The deeper the pipeline, the more accuracy is worth.
Choose sorting or partitioning the data (cost O(n log n) once) when the same data is filtered many times; it turns random branches into long runs. Do not sort for a single pass: the sort costs more than the mispredictions it saves. Choose predication in vector code (masks) when the fraction of lanes that need the expensive path is high; choose branching around the whole vector when it is rare.
Choose to accept the cost of Spectre mitigations on shared, multi-tenant hardware; consider relaxing some on dedicated machines with trusted code, after measuring. Interpreters and virtual-call heavy services see the largest slowdowns.

@@ cachelines
value: A processor does not read memory one byte at a time. Main memory is slow, about 80 to 100 ns for a random access, which is 250 to 400 cycles at 3 to 4 GHz. To hide this, the CPU keeps small, fast copies of recent data in caches, and it moves data between memory and the cache in fixed blocks called cache lines. On x86 and most ARM chips a line is 64 bytes. If your program reads one byte, the hardware fetches the whole 64-byte line that contains it. The next 63 bytes then cost almost nothing, about 1 ns from the L1 cache (4 to 5 cycles).
This one fact explains why the layout of data in memory often matters more than the algorithm. Summing a million integers in an array touches 62,500 lines and is limited by memory bandwidth. Summing a million integers in a linked list touches up to a million lines, and each load depends on the one before it, so the cost is a million memory latencies: easily 50 to 100 times slower, although both are "O(n)". Real programs gain 2 to 10 times from changes that only rearrange data.
The idea has two parts. Spatial locality: if you use an address, you will soon use its neighbours, so fetching the whole line is a good bet. Temporal locality: if you use an address, you will use it again soon, so keeping the line is a good bet. The lines are the unit of exchange between all levels of the hierarchy. The memory-hierarchy concept below this one provides the levels (L1, L2, L3, DRAM) and the rules of placement and eviction. This concept is about the unit that moves between them, and about how to make every moved byte useful.
The layer above builds on this. Columnar storage and doc values place all values of one column next to each other, so each 64-byte line holds 8 useful 8-byte values (or 16 four-byte values) for a scan, instead of one value and 56 bytes of other columns. Vectorized execution uses batches that fit in cache. Thread-per-core designs give each core its own data, so lines do not bounce between cores.
terms: Cache line (block) — the fixed-size unit, usually 64 bytes, in which data moves between memory and the caches; always aligned to its size.
Spatial locality — nearby addresses tend to be used close together in time.
Temporal locality — an address that was used tends to be used again soon.
Cache miss — the requested line is not in the cache and must be fetched from a slower level; types are compulsory (first use), capacity (cache too small) and conflict (too many lines map to the same set).
Set associativity — a line may live in any of N ways (slots) of one set chosen by address bits; an 8-way cache has 8 slots per set.
Prefetcher — hardware that guesses which lines will be needed next (sequential or strided) and fetches them early.
False sharing — two threads write different variables that sit in the same line, so the line bounces between their cores although no data is shared.
Array of structs (AoS) and struct of arrays (SoA) — two layouts: records stored one after another, or each field stored in its own array.
history: The principle of locality was named by Peter Denning in his working-set model (1968): programs use a small set of pages in any short period. Maurice Wilkes had proposed "slave memories" in 1965, a small fast store holding a copy of recently used words. The IBM System/360 Model 85 (1968) was the first commercial machine with a cache. Early caches used lines of 8 to 32 bytes. Alan Jay Smith's 1982 survey "Cache Memories" studied line size, associativity and replacement, and showed that larger lines reduce misses until the cost of moving more data outweighs the gain. As memory latency in cycles grew and DRAM bursts became efficient, lines grew to 32 bytes and then 64 bytes in the 1990s and 2000s. Some designs use 128 bytes: IBM POWER, and Apple's M-series chips, whose caches use 128-byte lines. Intel's adjacent-line prefetcher fetches lines in pairs, so effectively 128 bytes move on a miss.
Norman Jouppi (1990) introduced the victim cache and stream buffers, two ways to reduce conflict misses and to prefetch sequential lines. Hardware prefetching then became standard: next-line, stride and stream prefetchers appear in every large core. Multicore processors added a new cost: the coherence protocol (next concept in this group) works on whole lines, so false sharing became a common performance bug as multicore chips spread in the 2000s. Ulrich Drepper's "What Every Programmer Should Know About Memory" (2007) and Igor Ostrovsky's "Gallery of Processor Cache Effects" made the topic common knowledge for application programmers, and Jeff Dean's "latency numbers every programmer should know" (about 0.5 ns for L1 and 100 ns for main memory) is still quoted.
how: A cache is an array of lines organised in sets. The address of a byte is split into three fields. The offset (the low 6 bits for 64-byte lines) picks the byte inside the line. The index (the next bits) picks the set. The tag (the remaining high bits) is stored with the line and compared on lookup. A 32 KB, 8-way L1 data cache has 32768 / (64 × 8) = 64 sets, so the index is 6 bits. On a load, the cache reads all 8 tags of the set in parallel, compares them to the tag of the address, and on a match returns the bytes from the line. This is what the memory hierarchy provides; the cache line is the grain it works in.
On a miss the controller requests the whole line from the next level, evicts a victim in the set (usually the least recently used way, approximately), and fills the line. The request out to DRAM is a burst: DRAM delivers 64 bytes in one burst of 8 transfers over a 64-bit channel, so the line size matches the memory's natural burst, and the cost of the first byte (about 80 ns) is paid once for 64 bytes. This is why bandwidth for sequential access is far higher than for random access: a core can stream at 10 to 20 GB/s from DRAM, but random 8-byte loads reach perhaps 100 to 200 MB/s when they are dependent (64 bytes in 80 ns is 0.8 GB/s of line traffic, of which only 8 bytes are used).
Hardware prefetchers raise the hit rate for regular patterns. The L1 and L2 prefetchers detect a stream of ascending (or descending) lines, or a constant stride per load instruction, and request the next lines before the program asks. They keep going only within a 4 KB page, since the next physical page is unknown to the cache, so very long strides defeat them. Prefetching hides latency only when addresses are predictable. For a linked list or a tree, the next address is inside the data just loaded, so the prefetcher cannot help and the out-of-order engine cannot overlap the misses.
The levels differ in how they trade speed against hit rate. L1 is small (32 to 48 KB), 8 to 12-way, and answers in 4 to 5 cycles. L2 (about 1 to 2 MB) answers in 12 to 16 cycles, and the shared L3 (tens of MB) in 40 to 70 cycles. The line size is usually the same at every level, so a line moved down from DRAM can fill all of them, and the question for software is only how many of its bytes get used before it is evicted.
Two more effects matter. Conflict misses: addresses that differ by a multiple of (number of sets × 64) map to the same set. In the example above this period is 64 × 64 = 4 KB. A program that reads a matrix column when rows are 4 KB apart (1,024 ints) uses only one set, so only 8 of the cache's 512 lines are usable and the access thrashes, though the data would fit. Padding rows by one line removes the problem. Alignment: a value that straddles two lines needs two accesses, so compilers align types to their size, and an 8-byte field at offset 60 is a "split load".
Writes also work by lines. A store to a line not in the cache usually fetches the line first (write-allocate), changes the bytes, and marks the line dirty; it goes back to memory only when evicted. With several cores, a core must own the line exclusively before writing, which brings in the coherence protocol; the line is the unit of ownership. This is the mechanism behind false sharing: if thread A writes bytes 0 to 7 of a line and thread B writes bytes 8 to 15, the line moves back and forth between cores on every write, each transfer costing 40 to 100 ns, though the threads never touch the same variable.
Finally, the data layout decides how many bytes of each line are useful. Array of structs places the 64 bytes of a row together, so reading one field of each row uses 8 of 64 bytes (12%). Struct of arrays places each field in a separate array, so reading one field uses all 64 bytes (100%) and the prefetcher sees a clean stream. This is the idea behind columnar storage, and why databases scanning one column outrun row stores by 5 to 10 times on analytical queries.

example: Start with the address split. For the 32 KB, 8-way, 64-byte-line cache above, take address 0x12345678. The offset is the low 6 bits: 0x78 & 0x3F = 0x38 = 56. The index is the next 6 bits: (0x12345678 >> 6) & 0x3F = 0x19 = 25. The tag is the remaining bits, 0x12345. The load reads byte 56 of the line in set 25 whose tag matches. The addresses 0x12345678 and 0x12346678 (4 KB apart) share offset 56 and index 25, so they compete for the 8 ways of set 25.
Next, a stride experiment on an array of 64M ints (256 MB). Loop 1 adds up every int. Loop 2 adds up every 16th int (stride 64 bytes, one int per line). Loop 2 does 16 times fewer additions but touches every line, so it needs exactly the same memory traffic. On a typical machine, the two loops take almost the same time (both are bound by memory), which is a surprise until you count lines and not ints. Increasing the stride to 32 ints (two lines) halves the lines touched and the time roughly halves.
Now AoS against SoA. A table has 100 million rows, each a 64-byte struct with 8 eight-byte fields, and we sum one field. AoS: every row is a separate line, so the scan reads 100M × 64 B = 6.4 GB. At 20 GB/s that is 0.32 s. SoA: the field is a contiguous array of 100M × 8 B = 800 MB, read in 0.04 s. A factor of 8 from layout alone. If the query also uses two other columns, SoA reads 2.4 GB and is still 2.7 times faster, and in a columnar file with compression (say 3 to 1) it is faster again.
False sharing, with numbers. Eight threads each increment their own counter 100 million times. Case 1: the counters are in a `long[8]` array, 64 bytes, one line. Every increment needs exclusive ownership, so the line moves between cores on nearly every write: at roughly 50 ns per transfer the total is dominated by line transfers, and the run takes tens of seconds, possibly slower than one thread. Case 2: each counter is padded to its own 64-byte line (`long[8 * 8]`, using index 8 × t). Each core owns its line and increments at about 1 ns, so 100 million increments take about 0.1 to 0.3 seconds. A speedup of 50 to 100 times for one line of padding. The same effect makes naive shared statistics counters scale badly, and the reason Java's LongAdder keeps padded per-thread cells.
intuition: Groceries come in bags, not single items; plan your meals around what is in the bag you already carried home.
The reason for a line is economic. A DRAM access has a high fixed cost to open a row and find the data, and a low extra cost to read the neighbouring bytes. A cache that fetched one byte would pay the fixed cost for one byte. Fetching 64 bytes pays it once for 64. This is a good deal only if neighbours are used, which programs usually do (arrays, structs, instruction streams), and that is why locality exists as a pattern: the machine was designed to reward the access patterns programmers naturally wrote. The corollary is a simple rule for design: put things that are used together next to each other, and things that are written by different threads far apart.
mistakes: People often think a cache stores variables or objects. In fact it stores lines of 64 bytes that happen to contain them. Two unrelated variables in the same line share the fate of the line: they are loaded together, evicted together, and (with several cores) owned together.
People often think big-O decides speed on real hardware. In fact the constant for a random memory access is 50 to 100 times that of a sequential one. A linear scan of an array often beats a tree or hash lookup for sets of a few hundred to a few thousand elements, and a B-tree beats a binary tree by a large factor at equal O(log n).
People often think false sharing needs shared variables or locks. In fact the threads can use entirely separate variables with no synchronisation; the problem exists only because the hardware tracks ownership per line, not per variable. Profilers show it as high cache-miss counts or coherence misses in code that has no contention in its source.
friction: Languages hide layout. A Java `ArrayList<Integer>` holds references to boxed Integer objects: each element costs a 4 to 8 byte reference plus a 16-byte object (12-byte header, 4-byte value) at a separate address, so a scan can touch one line per element instead of 16 elements per line. Object headers, references and garbage collector moves make layout hard to control; primitive arrays, off-heap buffers, or arrays of primitives per field (SoA by hand) are the workaround, and Project Valhalla (value classes) is the long-term fix, still in development. Python is worse, with objects of 28 bytes or more for an int. 
Hardware varies too: the line is 64 bytes on x86 and most ARM servers but 128 on Apple M-series and IBM POWER, so hard-coded padding may be too small (C++17 has `std::hardware_destructive_interference_size`). Layouts optimised for one access pattern hurt another. SoA is best for scanning one field and poor for reading a whole record: it needs one line per field. AoS is the opposite. Row stores favour transactions, column stores favour analytics, and hybrid formats (PAX, Parquet row groups) compromise. Padding trades memory for speed. Cache-oblivious or blocked algorithms add code complexity and tuning to hardware sizes (L1 32 to 48 KB, L2 1 to 2 MB, L3 tens of MB), which change between machines and cloud instance types. On shared machines a noisy neighbour can also evict your lines from the shared last-level cache.
practice: Prefer arrays and contiguous structures to pointer-based ones. Use `int[]` rather than `List<Integer>`, vectors rather than linked lists, open-addressing hash tables rather than chained ones, and B-trees (nodes of 256 bytes to a few KB) rather than binary trees. Iterate in memory order: in a row-major array the inner loop must run over the last index.
Put hot data together and cold data apart. Split a record into a small hot part and a bigger cold part. Choose SoA, or a columnar format, when you scan few fields of many rows. Order struct fields by size to avoid padding, and keep frequently used fields in the first line. Keep the working set of an inner loop within L1 or L2 by blocking (tiling): to multiply 1024 × 1024 matrices of doubles, process \( B \times B \) tiles with \( 3 \times B^2 \times 8 \) bytes below 32 KB, so B around 32, and the loop can run 3 to 10 times faster than the naive order.
Avoid false sharing: give each thread's hot mutable state its own line (`alignas(64)` in C++; `@Contended` in Java, which needs `-XX:-RestrictContended` outside the JDK; padding fields in Go; or per-thread/striped counters such as `LongAdder`). Batch work per thread so shared structures are updated rarely. Measure with `perf stat -e cache-misses,cache-references,L1-dcache-load-misses`, and with `perf c2c` (cache-to-cache) on Linux, which finds contended lines and shows the addresses and the threads involved.
tradeoffs: Choose structure of arrays (columnar) when queries read a few fields from many records, as in analytics and scans; you give up cheap whole-record access and updates, which need several writes to different arrays. Choose array of structs (row layout) when you read or write whole records one at a time, as in OLTP or object-oriented code, and accept that scans of single fields waste most of every line.
Choose padding of hot fields to a full line when different threads write them often (more than thousands of writes per second per field) and measurements show contention; pay with memory (64 bytes per counter instead of 8). Do not pad rarely written data: it only reduces cache capacity.
Choose arrays with linear search up to a few hundred elements and sorted arrays with binary search up to tens of thousands, then trees or hash tables above that: contiguous data is faster at small sizes because of prefetching and line use, despite worse O(n) behaviour. Choose wide-node trees (B-trees, B+trees) over binary trees to cut the number of lines touched per lookup: for 1 billion keys a binary tree needs about 30 dependent loads, a B-tree with fan-out 128 needs about 4.

@@ coherence
value: In a multicore processor, every core has its own private caches (L1 and usually L2). If two cores read the same variable, each keeps its own copy of the 64-byte line. If one core then writes the variable, the other core's copy is old. Without a rule, the other core could keep reading the old value for ever, and shared memory would not work. Cache coherence is that rule. It is a hardware protocol that makes all copies of a line agree, so that the system behaves as if each memory address had only one up-to-date value that every core eventually sees.
Coherence is invisible to the programmer when you only ask for correctness: ordinary loads and stores to shared variables just work. Its cost is visible when you ask for speed. Every write to a line that other cores hold forces those cores to drop their copies, and the next access by them is a miss that fetches the new data from the writer's cache. This transfer takes roughly 30 to 100 ns inside one chip and 100 to 200 ns between sockets, 50 to 100 times the cost of an L1 hit. That is why a shared counter updated by 32 threads is slower than the same counter updated by one thread, why a contended lock is expensive, and why a layout that puts two threads' variables in one line hurts.
The layer above relies on this directly. Locks and atomics (L3) use coherence to make an atomic instruction effective: a core gets exclusive ownership of the line and performs the read-modify-write. Lock-free structures spin on compare-and-swap, and each failed attempt is a line transfer. General-purpose CPUs (L1) offer a single shared address space because of it, and CXL (L0) extends the idea to devices that cache host memory. The layer below gives the way to describe it: a finite automaton (L3). Each cache line in each cache is a small state machine with four states (Modified, Exclusive, Shared, Invalid) whose transitions are triggered by the core's own loads and stores and by messages from other caches. The whole protocol is the set of these machines and the messages between them.
terms: Coherence — the rule that all caches agree on the value of each memory location: writes to one address are seen by all cores in the same order.
Snooping — every cache watches (snoops) a shared bus or interconnect for requests from other caches and reacts to those that concern lines it holds.
Directory — a table, usually next to the shared L3 or memory, that records which caches hold each line, so messages go only to those caches instead of to all.
MESI states — Modified (the only copy, changed), Exclusive (the only copy, unchanged), Shared (clean, maybe several copies), Invalid (not present).
Invalidation — a message that makes other caches drop their copy of a line before one core writes it.
Read for ownership (RFO) — a request that fetches a line and takes exclusive ownership so the core can write it.
Write-back — writing a modified line to the next level or memory when it is evicted or requested by another core.
Coherence miss — a miss caused by another core's write that invalidated your copy (as distinct from capacity or conflict misses).
history: Early multiprocessors with caches had to avoid the problem. The first solutions were software-managed or write-through: every write went to memory over a shared bus, and other caches snooped the bus and invalidated their copies. This kept the rule, but the bus was saturated by writes. James Goodman's "write-once" protocol (1983) wrote through only the first write to a line and then kept it in the cache as dirty. In 1984 Mark Papamarcos and Janak Patel described the Illinois protocol, adding a state for "the only clean copy", which gives the four states of MESI and avoids a bus transaction on the common read-then-write pattern. Intel introduced MESI in the Pentium (1993), and it became the standard textbook protocol.
Directory protocols for larger machines came earlier in theory (Censier and Feautrier, 1978) and in practice with the Stanford DASH machine (1990s) and SGI Origin systems; they keep a record of sharers so that no broadcast is needed. Today, both appear in one chip. Small multicore chips use snoop-based coherence with a filter. Large chips with a mesh or ring interconnect (Intel Xeon, AMD EPYC, Arm Neoverse) use directory-like structures: Intel keeps snoop-filter information with the L3 slices, and AMD uses probe filters in its Infinity Fabric. AMD adopted MOESI, which adds an Owned state so a modified line can be shared without first writing it to memory, and Intel uses MESIF, which adds a Forward state that names one sharer to answer requests.
how: The protocol enforces two invariants for each line at any time: either one core may write it (and read it), or any number of cores may read it, never both (single-writer, multiple-reader); and every read returns the value of the most recent write. MESI does this with four states per line per cache.
In state Modified (M), this cache holds the only valid copy and it differs from memory. It can read and write without telling anyone. In Exclusive (E), this cache holds the only copy and it matches memory; it can read freely and write after a silent change to M, with no bus traffic. In Shared (S), this cache holds a clean copy and others may also hold one; it can read, but must get exclusive access before writing. In Invalid (I), the line is absent or stale.
The transitions can be listed by event. A read hit in M, E or S changes nothing. A read miss sends a read request to the interconnect. If no other cache has the line, memory (or the L3) supplies it and the line enters E. If other caches hold it in S or E, one supplies it (or memory does) and everyone ends in S. If another cache holds it in M, that cache must supply the data (and write it back to memory or L3), and both end in S. A write hit in M is silent. A write hit in E is silent and moves to M. A write hit in S sends an upgrade request (invalidate), all other copies go to I, and the writer moves to M. A write miss sends a read-for-ownership: the data arrives, all other copies are invalidated, and the writer's line is M. When another core's request arrives for a line you hold, you react according to your state: M supplies and downgrades (read) or supplies and invalidates (write); E and S drop to S (read) or I (write).
Finding the other copies is the second half of the design. In a snooping design, requests are broadcast to all caches, which is simple and gives a natural order of all writes, but traffic grows with the number of cores. In a directory design, a home node for each line records which caches share it (a bit vector of one bit per core, or a few pointers); a request goes to the directory, which sends invalidations only to the listed sharers and collects acknowledgements. The directory costs storage, for instance 64 bits per 512-bit line for 64 cores (12.5%), and adds an extra hop for each miss, but its traffic scales. Modern chips mix them: the shared L3 (which is often inclusive of, or keeps tags for, the private caches) acts as a filter, and a request for a line that no other core holds is never broadcast.
Because a core can see its own latest write before others can, stores wait in a store buffer before they reach the cache line. The write becomes globally visible only when the line is in M and the store leaves the buffer. Coherence says all cores agree on the order of writes to one address. It says nothing about how writes to different addresses are ordered with respect to each other; that is the job of the memory model, and a common confusion. Coherence guarantees that you cannot see an address go back to an old value; consistency says which combinations of values of several addresses you may observe.
Large chips store directory information next to the L3. In a mesh design, each L3 slice owns a share of all addresses (chosen by a hash of the address) and keeps, for its lines, a record of which cores' private caches may hold them. A miss goes to the home slice for that address; the slice answers from the L3 if no private cache owns the line, or forwards the request to the owner. The hop count across the mesh is why the latency of a coherence miss depends on where the two cores sit.
Atomic instructions rely on all of this. A `lock xadd` (atomic add) first obtains the line in M (an RFO if needed), and then holds it for the duration of the instruction, refusing to answer requests until done. So an atomic update by one core on a line it already owns costs about 15 to 20 cycles, while the same update on a line owned by another core costs a full transfer.

example: Trace one line x through two cores. Start with x in neither cache. (1) Core A reads x. A sends a read request, no other cache has it, memory supplies it, A's line becomes E. One request, one memory fetch. (2) Core B reads x. A's line is E, so A answers (or memory does), and both lines become S. (3) Core A writes x. A's line is S, so A sends an invalidate. B's copy goes to I, A's line goes to M. One message, no data transfer. (4) Core B reads x. B's line is I, so it is a miss. A holds M, so A sends the data to B (and writes it back to the L3 or memory), and both go to S. (5) Core B writes x. B's line is S, so B sends an invalidate; A goes to I and B goes to M. Over the five events there were three coherence transactions between the cores, and each of them cost a miss or a delay of tens of nanoseconds.
Now the cost of a shared counter. Two threads on two cores each run `counter.fetch_add(1)` 100 million times on the same atomic variable. Each increment needs the line in M, so the line moves from core to core on nearly every increment. At roughly 50 ns per transfer, 200 million increments take about 10 seconds, or 50 ns each. With a counter per thread (in separate lines), each core owns its line, an increment costs about 5 ns (an atomic) or 1 ns (a plain add), and the total is 0.1 to 0.5 seconds. With 32 threads, the shared counter gets no faster: the line can only be in one place, so the rate stays near 20 million increments per second in total, however many cores are added, while the per-thread version scales almost linearly.
Next, locks. Sixteen threads wait for a spin lock. In a naive test-and-set loop, each waiter runs an atomic exchange continuously, so the line moves between 16 cores constantly, and even the holder's release write must queue for the line. In a test-and-test-and-set lock, each waiter first reads the lock in a loop. All waiters then hold the line in S and spin in their own caches with no traffic. Only when the owner writes zero does an invalidation go out, 15 waiters miss and read, and they then try the atomic once. This reduces traffic by orders of magnitude. Queue locks such as MCS go further: each waiter spins on its own line, so a release causes one transfer to one waiter and not a herd.
intuition: Everyone keeps a photocopy of the notice board, and before anyone writes on the board, all photocopies are torn up, so no one reads an old notice.
The design is natural because the cache is a copy and the only expensive thing about copies is keeping them equal. Two cheap rules suffice: a line may be written by one cache only if all other copies are gone (single writer), and a cache that needs a line someone else changed must get it from that someone (no stale reads). Everything else is bookkeeping on how to find the other copies cheaply. Reading is free to share, since many copies of unchanged data cause no trouble, and writing is costly, because each write must remove all other copies. This is why read-mostly shared data scales well across cores and write-shared data does not.
mistakes: People often think cache coherence makes shared variables ordered and safe to use without locks. In fact coherence only guarantees agreement on the order of writes to one address. Operations on different addresses can still be observed in different orders by different cores (memory model), and a read-modify-write such as `x++` is still three steps that two cores can interleave, so atomics or locks are still needed.
People often think volatile or a memory barrier flushes caches. In fact coherence is done by hardware at all times; a barrier or a `volatile` access only orders operations and stops compiler reordering. Caches are not flushed to memory in normal code, and flushing instructions are used only for devices or persistent memory.
People often think reading shared data is free. In fact reads are free only while no one writes. A read of a line recently written by another core is a miss that costs a transfer, and a single writer that updates a hot structure frequently (for example a "last updated" timestamp that every request writes) slows all readers.
People often think more cores make atomic counters and locks scale. In fact a single contended line behaves like a serial resource: total throughput is about one operation per line-transfer time, and adding cores often makes it worse, because the waiting cores add traffic.
friction: The main cost is traffic and latency, and it grows with the number of cores and sockets. On a 2-socket server a line transfer between sockets takes 100 to 200 ns, 2 to 4 times a transfer inside one socket, so the placement of threads (NUMA) affects the cost of every shared structure. Coherence traffic uses bandwidth on the interconnect and snoop filters; a snoop filter that overflows forces extra invalidations.
Protocol complexity is the second cost. Real implementations have many transient states and races (for instance two cores writing the same line in the same cycle), and bugs here can be rare and severe. The design must also keep pace with new features: devices that cache host memory (CXL.cache), accelerators, and persistent memory all need to take part, and coherence across chiplets and across machines is much slower still.
Software patterns can defeat the hardware. False sharing, as described in the cache-line concept, is pure coherence cost. A queue with its head and tail in one line makes producer and consumer fight. Reference counts updated by every thread (for example `shared_ptr` copies) serialize on one line. Some architectures do not provide full coherence: GPUs keep their L1 caches non-coherent, and software must use explicit fences. With hundreds of cores, directories, invalidation fan-out and acknowledgement latency dominate, so large systems use coherence only inside a node and message passing between nodes.
practice: Treat each cache line as a lock that only one writer holds at a time. Keep frequently written shared data to a minimum; give each thread its own copy of counters, buffers and statistics (thread-local or per-core) and combine them rarely. In Java use `LongAdder` rather than `AtomicLong` for hot counters; in C++ use per-thread counters or `std::atomic` with relaxed ordering aggregated at the end; in Go, shard counters per P. Separate read-mostly data from write-hot data into different lines, and pad independently written fields to 64 bytes.
For locks: avoid global locks on hot paths; use test-and-test-and-set with exponential backoff, or queue locks (MCS, or the OS's futex-based mutex), and shard (lock striping) so that threads touch different lines. Prefer read-copy-update or immutable snapshots for read-heavy structures, since readers then write nothing. Keep a producer's and a consumer's indices on different lines in ring buffers (the LMAX Disruptor and most lock-free queues do this) and let each side cache the other's index to avoid reading it every time.
Measure. `perf stat -e cache-misses`, `perf c2c record/report` (which finds lines with cross-core "HITM" hits, meaning a hit on a modified line in another core's cache), and Intel VTune's "contested accesses" show coherence cost directly. Look for functions with high latency per access on a few shared addresses, and for throughput that is flat or falling as you add threads. On two-socket machines pin threads and memory to a socket (`numactl`) and shard data per socket.
tradeoffs: Choose shared-memory, coherent communication between threads when updates are rare relative to reads and when the shared data is small: it is the simplest model, and read-sharing is nearly free. Choose partitioning (each thread owns its data, communicate by messages or batches) when writes are frequent or the thread count is above about 8 to 16 per shared structure: you add code to move data between owners but remove line ping-pong, and scaling becomes close to linear.
Choose a simple spin lock with backoff for very short critical sections with few threads (two to four), where its cost is one line transfer. Choose a queue lock or a blocking mutex when many threads contend or critical sections are long; you pay a higher uncontended cost and, for blocking locks, a system call, but you avoid a herd on one line.
Choose snooping for small core counts (up to about 8 to 16 cores per domain), where broadcast is cheap and latency is lowest, and directories for larger counts, where the extra storage and hop buy scalability. Choose weaker or no hardware coherence only for accelerators, where software can manage sharing and the saved silicon and energy are used for compute.
interview: Walk through what happens in MESI when core A holds a line in S, core B also holds it in S, and A writes it. || A sends an upgrade (invalidate) request on the interconnect. B's copy is invalidated (S to I) and B acknowledges. A's line moves from S to M and the write completes. No data moves, only messages. When B later reads, it misses, and A supplies the data and both go back to S.
Why does a contended `AtomicLong` not scale to 32 cores, and what would you do about it? || Every increment needs the line in Modified state, so the line moves between cores for each operation, and the rate is bounded by the transfer time (roughly 20 million per second in total, whatever the thread count). Use per-thread or striped counters (LongAdder) and sum them when reading, trading a more expensive read for scalable writes.
Explain the difference between cache coherence and memory consistency with an example. || Coherence is about one address: all cores see writes to it in one order. Consistency is about the order of operations on different addresses as seen by other cores. Example: thread 1 writes data then flag; each address is coherent, but another core may still see flag set while data is old on a weak memory model unless there is a release/acquire pair.
What is the purpose of the Exclusive state, and why do some protocols add Owned or Forward? || E lets a core write a line it holds alone without any bus transaction (E to M is silent), which makes private data cheap. Owned (MOESI) lets a modified line be shared without writing it back to memory, with the owner supplying data. Forward (MESIF) picks one sharer to answer requests, so a clean line is not supplied by memory or by several caches at once.
When would you choose a directory over snooping, and what does it cost? || With many cores or multiple sockets, broadcasting every miss floods the interconnect. A directory records the sharers and sends messages only to them. It costs storage (about one bit per core per line, or fewer with pointers or coarse vectors) and an extra hop in latency for each miss.
quiz: What are the four MESI states, and in which can a core write without telling anyone? || Modified, Exclusive, Shared, Invalid. A core can write silently in M and in E (E moves to M); in S it must first invalidate other copies.
Why is a test-and-test-and-set lock better than a plain test-and-set lock under contention? || Plain test-and-set writes on every spin, so the line moves between all waiters continuously. With test-and-test-and-set, waiters spin reading a Shared copy with no traffic, and only the release triggers an invalidation.
Two threads each increment a shared atomic counter 100 million times at 50 ns per line transfer. About how long does it take? || 200 million increments at about 50 ns each is about 10 seconds. Per-thread counters in separate lines would take well under a second.
What does a snoop filter or directory save compared with broadcasting every request? || It records which caches may hold a line, so invalidations and data requests go only to those caches. Traffic and snoop lookups in uninvolved cores are avoided.
Does cache coherence guarantee that two writes to different variables become visible in program order on another core? || No. Coherence orders writes to the same address only. Ordering across different addresses is defined by the memory model, and weak models need fences or acquire/release operations.

@@ memmodel
value: When two threads share memory, a natural question is: if one thread writes a value, when and in what order can the other thread see it? The simple answer, "in the order of the program, immediately", is not what real machines do. A CPU keeps writes in a store buffer before they reach the cache, executes loads early, and reorders independent instructions. The compiler also moves, merges and removes memory accesses. Each of these is invisible to a single thread, but another thread can observe them. A memory model is the contract that says exactly which orderings a program may observe. It tells the programmer what is guaranteed, and tells the compiler and the CPU what they may still reorder.
Without such a contract, concurrent code would not be portable or even meaningful. A well-known example is the simple "message passing" pattern: one thread writes `data = 42; ready = 1;` and another waits for `ready == 1` and reads `data`. On a weakly ordered CPU such as ARM, the second thread can see `ready` as 1 and still read the old `data`. On x86 this exact failure cannot happen in hardware, but the compiler may still break it. Code that works on one machine can fail on another, or fail one time in a million.
The practical tool the layer above receives is a small vocabulary: atomic operations with an ordering (acquire, release, sequentially consistent), volatile in Java, and fences. Locks, lock-free data structures and the barriers inside concurrent garbage collectors are all written with it, and the consistency models of distributed systems (L2) ask the same questions across machines instead of across cores. A rule from the language models gives the programmer a simple contract: if your program has no data races, it behaves as if all threads were interleaved on a single processor.
The concept below that supports it is order theory (L4). A memory model is a statement about orders: program order inside a thread, and a happens-before relation across threads, which is a partial order (irreflexive, transitive). Whether an outcome is allowed becomes a question about whether a set of ordering edges forms a cycle, which is how formal models and tools such as herd7 decide it.
terms: Sequential consistency (SC) — the result looks as if all memory operations of all threads ran in one interleaved order that respects each thread's program order.
Data race — two threads access the same location at the same time, at least one writes, and there is no synchronization between them; in C++ this is undefined behaviour.
Happens-before — a partial order on operations: if A happens-before B, the effects of A are visible to B.
Acquire and release — a release store publishes everything the thread wrote before it; an acquire load that reads that value sees all of it.
Memory fence (barrier) — an instruction that stops certain kinds of reordering across it (mfence on x86, dmb on ARM).
Store buffer — a small queue in a core where stores wait before they go to the cache; it lets later loads pass earlier stores.
Total store order (TSO) — the model of x86 and SPARC: loads may pass earlier stores to other addresses, and nothing else is reordered.
Litmus test — a tiny multi-thread program with a listed question "can this outcome happen?", used to define and test a model.
history: Leslie Lamport defined sequential consistency in 1979 in a short paper on multiprocessors that "correctly execute multiprocess programs". It matches programmer intuition and was the first clear contract. It is also expensive: it forbids store buffers, write combining and many compiler optimisations. By the late 1980s hardware designers used weaker orderings for speed, and a series of definitions appeared: processor consistency, weak ordering (Dubois, Scheurich and Briggs, 1986), and release consistency (Gharachorloo et al., 1990). Sarita Adve and Mark Hill (1990) proved the key idea behind all later language models: if a program is free of data races, then a weak machine can behave as if it were sequentially consistent (the "DRF-SC" guarantee).
Languages needed a model of their own, because compilers reorder too. Java was first: the original model of 1995 was found to be flawed, and a new one (JSR-133, with Jeremy Manson, William Pugh and Sarita Adve) shipped with Java 5 in 2004. It fixed the broken double-checked locking idiom through volatile and final-field rules. Hans Boehm's "Threads cannot be implemented as a library" (PLDI 2005) argued that C and C++ needed a language-level model. C++11 (2011) added std::atomic and memory_order options (relaxed, acquire, release, acq_rel, seq_cst); C11 followed; Rust adopted the C++ model. Go documented its model early and revised it in 2022 (Go 1.19) after Russ Cox's analysis.
Hardware models were written down carefully only later. Peter Sewell and colleagues formalised x86-TSO in 2010. ARM's model was made simpler in ARMv8 (2017 revision), which requires "multi-copy atomic" stores (all cores see a store at the same time), while POWER still allows more. RISC-V defines the weak RVWMO model and an optional Ztso extension. Tools grew too: herd7 (Alglave and Maranget) checks litmus tests against formal models, and Linux has its own kernel memory model (2018). Apple's M-series chips even have a hardware TSO mode, used by Rosetta 2 to run x86 code correctly on ARM.
how: To see how reordering arises, follow a store through an x86 core. The core executes `x = 1`, and puts the write in its store buffer. It does not wait for the cache line to be owned (see cache coherence), because that may take 50 ns or more. The next instruction, `r1 = y`, is a load. The core runs it at once, reading y from its cache. The store to x is still in the buffer and invisible to other cores. So the core has performed the load before its own earlier store became visible: a store-to-load reordering. This is the only reordering x86 shows, plus the rule that a core always sees its own buffered stores (store-to-load forwarding). Stores leave the buffer in order, loads are not reordered with other loads, and stores are not reordered with other stores. That is total store order.
ARM, POWER and RISC-V allow much more. Loads can be satisfied out of order (speculatively, from stale cache lines that are valid until an invalidation arrives), stores can leave the buffer in a different order, and stores to different addresses can become visible to other cores in different orders. A message-passing program can therefore break: the write to `ready` can reach another core before the write to `data`.
A memory model closes the gap by naming a vocabulary and its guarantees. The vocabulary of C++, Java and the hardware has two parts: ordinary accesses, which the compiler and CPU may reorder freely (as long as one thread cannot tell), and synchronizing operations, which create order between threads. A release store on a flag means: all my earlier reads and writes complete before this store becomes visible. An acquire load of the flag means: no later read or write of mine moves before this load. If the acquire load reads the value written by the release store, the two operations synchronize, and everything before the release is visible after the acquire. A sequentially consistent atomic is stronger: all such operations form a single total order that all threads agree on.
Formally, the model is defined through relations over the operations of an execution: program order (po, within each thread), reads-from (rf, which write a read took its value from), coherence order (co, the order of writes to each location) and from-reads (fr, a read before a later write). Sequential consistency says that the union po ∪ rf ∪ co ∪ fr must be acyclic: a cycle would mean that some operation had to happen before itself. TSO removes the write-to-read edges of program order from the union, so the "both threads read 0" outcome of the store-buffering test has no cycle and is allowed. Weaker models drop more edges, and acquire/release or fences put specific edges back. Happens-before is the transitive closure of program order and the synchronizes-with edges (release to acquire, unlock to lock, thread start and join). This is order theory used directly: a partial order, and a check that adding edges does not close a cycle.
Cache coherence sits underneath this, as the previous concept explains. Coherence guarantees that all cores agree on the order of writes to one address, so a model never has to talk about stale single locations. What the model adds is the order between different addresses, which coherence does not define. A fence on a modern core mostly waits for the store buffer to drain and stops later loads from running early; it does not flush any cache.
The compiler is the second source of reordering, and the language model governs it. Without synchronization, a compiler may keep `flag` in a register and turn `while (!flag) {}` into an infinite loop, reorder two independent stores, or remove a store it thinks is dead. The DRF guarantee says: if every conflicting access is ordered by happens-before, the program behaves as in SC; if not, C++ says the behaviour is undefined, and Java says only that some limited set of outcomes is possible. To implement atomics, the compiler emits the right instructions: on x86 an acquire load or a release store is a plain `mov`, a seq_cst store is `xchg` (or `mov` plus `mfence`); on ARMv8 the same operations are `ldar` and `stlr`, which carry ordering built into the instruction.

example: Start with the store-buffering test above. Enumerate the sequentially consistent runs. Label T1's operations a1 (x = 1) and a2 (r1 = y), and T2's operations b1 (y = 1) and b2 (r2 = x). Program order requires a1 before a2 and b1 before b2. There are \( \binom{4}{2} = 6 \) interleavings. a1 a2 b1 b2 gives r1 = 0, r2 = 1. a1 b1 a2 b2 gives (1,1). a1 b1 b2 a2 gives (1,1). b1 b2 a1 a2 gives r2 = 0, r1 = 1. b1 a1 b2 a2 gives (1,1). b1 a1 a2 b2 gives (1,1). So the outcomes are (0,1), (1,0), and (1,1) four times. The pair (0,0) is impossible, because the one that reads first must come after its own store but before the other thread's store, and these demands form a cycle. On a real x86 machine a litmus-test tool reports (0,0) readily, because both stores sit in store buffers while both loads run. To forbid it, put a full fence (`mfence`) between the store and the load in each thread, or make x and y sequentially consistent atomics. The fence costs roughly 20 to 40 cycles.
Now the message-passing pattern. T1 runs `data = 42; ready = 1;` and T2 runs `while (ready == 0) {}; r = data;`. With plain variables there are two failures. First, the compiler may hoist the read of `ready` out of T2's loop, so it never ends. Second, on ARM the store to `data` may become visible after the store to `ready`, so T2 can read 0. Fix with C++ atomics: `ready.store(1, std::memory_order_release)` in T1 and `ready.load(std::memory_order_acquire)` in T2. The release guarantees that the write of `data` is ordered before the store to `ready`. The acquire guarantees that the read of `data` is ordered after the load of `ready`. When T2's load sees 1, the two synchronize, so `data == 42` is guaranteed by happens-before: write data, then release, then acquire, then read data.
The cost differs by machine. On x86, the release store and acquire load compile to plain `mov` instructions: free, because TSO already gives these orders. On ARMv8 they are `stlr` and `ldar`, a few cycles. A seq_cst store on x86 is an `xchg` of about 20 cycles, so moving a hot flag from seq_cst to release/acquire often saves that cost, and a statistics counter can use relaxed, with no ordering cost.
intuition: Each thread gossips to its neighbours through different roads; the model tells you which pieces of news can overtake which, and which roads are guaranteed to deliver in order.
Why do such rules exist? Because speed needs freedom. A strict single order for all memory operations would force every core to wait for every write to be seen by everybody before going on, and would forbid the compiler from moving most loads and stores. The weaker models give the hardware and compiler freedom and keep a small set of tools (release, acquire, fences) to restore order exactly where needed. The data-race-free rule makes the bargain simple: use these tools at every place where threads communicate, and the machine will behave as if there were no tricks at all.
mistakes: People often think that on x86 you do not need to care about memory ordering. In fact x86 allows store-to-load reordering, and, more importantly, the compiler reorders and removes accesses whatever the hardware. A plain variable used as a flag between threads is a data race in C++ and Java even on x86.
People often think `volatile` makes variables thread-safe. In Java, volatile gives acquire/release ordering and visibility, but not atomic compound operations (`count++` is still three steps). In C and C++, volatile does not give inter-thread ordering at all; it only stops the compiler from removing accesses, which is meant for hardware registers. Use std::atomic.
People often think a fence flushes the caches or makes data visible faster. In fact coherence moves data between caches at the same speed. A fence only restricts the order in which this core's operations become visible, usually by waiting for the store buffer to drain.
People often think memory ordering bugs are rare and show up as crashes. In fact they usually show up as silently wrong values, only on some CPUs, only under load, and only sometimes. They survive testing on x86 laptops and fail in production on ARM servers, which is why the move of cloud fleets from x86 to ARM (Graviton, Ampere, Apple M-series) exposed many latent bugs.
friction: Weak models are hard to reason about. Human intuition follows sequential consistency, and the allowed outcomes of even four-instruction programs surprise experts; the formal models take long papers to state. The full C++ model includes consume ordering (which no compiler implements as specified and which is effectively treated as acquire), and out-of-thin-air values: the standard has no good definition that forbids a relaxed program from inventing values from nothing, which is an open research problem that affects Java and C++ alike.
Bugs are hard to find and reproduce. A test passes millions of times and fails once in a week, on one hardware type. Tools help but do not cover everything: ThreadSanitizer finds data races dynamically in the runs it sees; jcstress (Java) and litmus7/herd7 test small patterns; model checkers such as Loom (Rust), CDSChecker and GenMC explore orderings exhaustively, but only for small code. Static proof of a lock-free algorithm in a weak model is a research task.
The performance trade-off is real: stronger orderings cost cycles and block compiler optimisations, so people are tempted to use relaxed atomics or hand-made fences for speed, and this is where most subtle bugs come from. Porting adds risk: code that is correct on x86 TSO by luck breaks on ARM, and a compiler upgrade can break code that was a data race all along. And the models differ: the Java, C++, Go and Linux kernel models are similar but not identical, so knowledge does not carry across languages without checking the rules.
practice: Follow the data-race-free rule: protect shared mutable data with a lock, or make every shared access atomic. Prefer higher-level tools (mutexes, `java.util.concurrent`, channels, queues) that include the right ordering, over hand-built synchronization. If you must write atomics, start from sequentially consistent (the default in C++ std::atomic, and Java's volatile) and relax only after measuring that it matters.
Know the common patterns. Publishing an object or flag: release store, acquire load. Reference counting: relaxed increment, release decrement with an acquire fence before the free. Statistics counter: relaxed. Spin lock: acquire on lock, release on unlock. In Java, use final fields for immutable objects (they are safely published), `volatile` for flags, `VarHandle` acquire/release modes for finer control, and never use double-checked locking without `volatile`.
Test on weak hardware. Run concurrent tests on ARM (a Graviton instance is cheap), with ThreadSanitizer enabled in CI, and with stress tests over many iterations and varying thread counts. Use jcstress for Java and Loom for Rust. When reading someone's lock-free code, ask for the happens-before argument in a comment for every atomic operation: which store synchronizes with which load.
tradeoffs: Choose locks (mutexes) when correctness and maintainability matter more than the last 20% of throughput: they carry the needed ordering, and uncontended cost is about 20 to 50 ns. Choose atomics with acquire/release for simple flags, counters and single-producer, single-consumer queues where you can write the happens-before argument in two sentences; choose lock-free structures only when profiling shows lock contention to be the bottleneck.
Choose sequentially consistent atomics when you have more than one atomic variable whose relative order matters, or when you cannot yet prove weaker ordering is enough; you pay about 10 to 20 cycles more per store on x86 and some more on ARM. Choose acquire/release when a single variable carries the synchronization (publish/consume of one flag). Choose relaxed only for values where order is irrelevant (counters, statistics) and the final value is read after a proper synchronization.
Choose a language with a strong, simple model (Java's volatile semantic, Go's channels and sync package, Rust's ownership which rules out data races in safe code) when the team is not expert in concurrency. Choose C++ atomics with explicit ordering only for performance-critical libraries written by experts.

value: The instruction set architecture (ISA) is the agreement between software and a processor. It defines the instructions the chip understands (add, load, branch), the registers a program can use, how memory addresses are formed, how the processor reports exceptions, which privilege levels exist, and what the memory model promises. It does not say how the chip is built inside. A compiler produces machine code for an ISA, and any chip that implements that ISA can run the code. That is the whole point: x86 programs from 1995 still run on a 2026 server, though the chip inside has nothing in common with the 1995 one.
The agreement splits the world into two parts that can change independently. Above it, compilers, operating systems and applications are written once per ISA. Below it, engineers are free to change the microarchitecture: pipeline depth, out-of-order windows, cache sizes, branch predictors. This split was the idea of the IBM System/360 in 1964 (one architecture, a family of machines from small to large), and it is why a CPU designer can add 10 times more transistors without breaking a single program. The price is that the ISA stays for decades, so its early choices (instruction length, number of registers, how calls work) stay in every later chip.
Today there are three families that matter. x86-64 (Intel, AMD) dominates desktops and servers. ARM (AArch64) runs almost all phones and, since Apple's M1 (2020) and cloud chips such as AWS Graviton, a growing share of laptops and servers. RISC-V is an open standard, started in 2010, used in microcontrollers and accelerators and growing in other areas. The layer above relies on the ISA in several ways. Virtual machines use hardware virtualization extensions (VT-x, AMD-V, ARM EL2) to run guests at full speed. General-purpose CPU computing (L1) is defined by it. Control-hijacking attacks (memory-safety bugs) exist because the ISA's call and return instructions keep code addresses in memory the program can overwrite.
The two lower concepts give the instruction set its physical meaning. Digital logic (L3) turns each encoded instruction into control signals: a decoder is a circuit that reads the opcode bits and raises the wires that tell the register file, the arithmetic unit and the memory port what to do. Boolean algebra (L4) is directly visible in the ISA: AND, OR, XOR and NOT instructions are Boolean functions applied to every bit of two registers, and the decoder and the adder are built from Boolean expressions.
terms: ISA (instruction set architecture) — the programmer-visible contract of a processor: instructions, registers, addressing, exceptions, memory model.
Microarchitecture — the internal design that implements an ISA (pipelines, caches, predictors); many designs can implement one ISA.
ABI (application binary interface) — the software conventions on top of an ISA: how arguments are passed, which registers a function must preserve, how structures are laid out.
RISC and CISC — reduced and complex instruction set computer: RISC uses few, simple, mostly fixed-length instructions that work on registers; CISC has many, variable-length instructions, some working directly on memory.
Load/store architecture — an ISA in which only load and store instructions touch memory, and all arithmetic works on registers.
Micro-operation (uop) — a simple internal operation into which a complex instruction is split by the hardware.
Instruction encoding — the layout of the bits of an instruction: opcode, register numbers, immediate values.
ISA extension — an optional group of instructions added later (SIMD, cryptography, matrix operations, virtualization).
history: Early computers had no stable ISA: each new machine had a new instruction set, and software was rewritten. IBM changed this with the System/360 (announced 1964), designed by Gene Amdahl, Gerrit Blaauw and Fred Brooks. They described one "architecture" implemented by six different models with a very wide range of performance, so customers could upgrade without rewriting programs. Maurice Wilkes's microprogramming (1951) made rich instruction sets practical: a small control store interpreted each complex instruction. Through the 1970s, with slow memory and weak compilers, richer instructions meant fewer fetches and easier assembly programming, giving the VAX (1977) and the Intel 8086 (1978).
In the late 1970s, studies showed that compiled programs used mostly simple instructions, and that complex ones slowed the whole machine. John Cocke's IBM 801 project (about 1975 to 1980), then Patterson and Ditzel's "The Case for the Reduced Instruction Set Computer" (1980), the Berkeley RISC I (1981) and Hennessy's Stanford MIPS (1981 to 1984) proposed small instruction sets that a pipeline can run at one instruction per cycle. Commercial RISC followed: SPARC (1987), MIPS, POWER, Alpha, and ARM (Acorn, first silicon 1985, designed by Sophie Wilson and Steve Furber), chosen for low power.
x86 survived because of software compatibility and because the Pentium Pro (1995) showed how to hide the CISC ISA: translate each x86 instruction into simple micro-operations and run those on a RISC-like out-of-order core. AMD's 64-bit extension (AMD64, 2003) beat Intel's incompatible Itanium (2001), which relied on the compiler to find parallelism (VLIW) and failed. ARM grew from phones; the 64-bit ARMv8 (AArch64, 2011) cleaned up the design. Apple's M1 (November 2020) and AWS Graviton (first chip 2018) showed that ARM could outperform x86 per watt in laptops and servers. RISC-V began at Berkeley in 2010 (Krste Asanović, David Patterson and students), and RISC-V International (founded 2015, based in Switzerland since 2020) governs the open specification.
how: An ISA specifies a machine as seen by a programmer. Take the common core, shared by all three families. There is a small set of registers (16 general-purpose registers of 64 bits in x86-64, 31 in AArch64, 32 in RISC-V), a program counter, flags or condition results, and memory addressed by byte. Instructions fall into classes: arithmetic and logic (add, and, shift), data movement (load, store, move), control flow (branch, jump, call, return), system (traps, privilege changes), and extensions (floating point, SIMD vectors, cryptography, atomics).
The main design choices are about encoding and operands. RISC ISAs have fixed-length instructions (32 bits in AArch64 and base RISC-V; RISC-V also has an optional 16-bit compressed form) and a load/store structure: arithmetic reads two registers and writes a third, and only loads and stores touch memory. Fixed length means the hardware knows where the next instruction starts without looking at the current one, so a front end can decode 6 to 8 instructions per cycle in parallel; Apple's recent cores decode 8 per cycle. Fields sit at fixed positions: in RISC-V the source registers are always bits 15 to 19 and 20 to 24, so the register file can be read while the decoder is still working. This is a direct use of digital logic: wiring bit fields straight into multiplexers.
x86 instructions are 1 to 15 bytes long. An instruction may use a memory operand, so `add [rdi], 1` loads, adds and stores in one instruction. The decoder cannot know where the next instruction begins until it has understood the length of the current one, which makes wide parallel decoding hard; x86 cores handle this with predecode that marks instruction boundaries and with a micro-op cache that stores already decoded operations (about 4,000 entries in Intel's Golden Cove), so hot loops skip the decoder. Inside, every x86 instruction is turned into one or more micro-operations; `add [rdi], 1` becomes a load, an add and a store (two internal operations for the store), and the core then executes them like a RISC machine. So the CISC/RISC difference lives mostly at the front end and in code size, and much less in the core.
Where the ISA ends, the ABI begins. A calling convention fixes how arguments and return addresses are passed. In the System V x86-64 ABI, the first six integer arguments go in rdi, rsi, rdx, rcx, r8 and r9, and `call` pushes the return address on the stack. In AArch64, the first eight go in x0 to x7, and `bl` puts the return address in the link register x30, so a function that calls nothing never writes it to memory. In RISC-V, arguments are in a0 to a7 and the return address is in ra (x1). These choices matter for speed (less memory traffic) and security (an attacker who overwrites a stack slot with a return address controls the next jump on x86; return address signing, ARM's PAC, and shadow stacks, Intel CET, are hardware additions to the ISA against this).
The ISA also defines the boundary between programs and the operating system. Privilege levels (user and kernel; on ARM, exception levels EL0 to EL3) decide which instructions a program may run. A system call is a special instruction (`syscall` on x86-64, `svc` on ARM, `ecall` on RISC-V) that raises the privilege level and jumps to a kernel entry point set by the OS; it works like the interrupt mechanism. Virtual-memory instructions and registers (the page-table base register) are part of the ISA, and so is the memory model: x86 promises total store order, ARM and RISC-V promise weaker orderings plus fence instructions.
Extensions are how an ISA grows without breaking compatibility. x86 added MMX, SSE, AVX, AVX-512 and AMX (matrix tiles) for vectors and matrices; AArch64 added NEON, SVE and SVE2 (vector length not fixed in the code), and a matrix extension; RISC-V is modular by design: a base integer set (RV32I has just 47 instructions) plus standard extensions such as M (multiply), A (atomics), F and D (floating point), C (compressed), V (vector). A chip declares which it supports, and software checks at run time (CPUID on x86). Virtualization extensions (VT-x from 2005, AMD-V 2006, ARM EL2) add a privilege level for a hypervisor, so that guest operating systems can run their privileged instructions without trapping on every one.

example: Encode one RISC-V instruction by hand: `add x5, x6, x7`, meaning x5 = x6 + x7. The R-type format has seven fields. The opcode for register-register arithmetic is 0110011. The destination register rd = 5 is 00101. The funct3 field for add is 000. The source rs1 = 6 is 00110. The source rs2 = 7 is 00111. The funct7 field for add is 0000000 (subtract uses 0100000). Place them from the top bit down: 0000000 00111 00110 000 00101 0110011. Regroup in fours: 0000 0000 0111 0011 0000 0010 1011 0011, which is 0x007302B3. The hardware decoder checks that the low 7 bits equal 0110011 (an AND of seven bits, some inverted), then funct3 and funct7 select the ALU operation. That is Boolean algebra implemented in gates, and it takes well under one clock cycle.
Compare the same work in two ISAs. The statement `counter += 1` with the counter in memory is a single x86 instruction: `add DWORD PTR [rdi], 1` is encoded as 83 07 01, 3 bytes (opcode 83 with extension 0, ModRM byte 07 selecting [rdi], immediate 01). In RISC-V (and AArch64) it takes three instructions: a load, an add of 1, a store, 12 bytes with 4-byte instructions (or about 8 bytes with 16-bit compressed forms). A naive count says x86 is denser and does more per instruction. But the x86 core splits it into a load, an add and a store internally, so the execution work is similar: the difference is in code size (a little) and decode logic (more for x86). For a function `long f(long a, long b) { return a + b; }`, x86-64 compiles to `lea rax, [rdi+rsi]; ret` (two instructions, 5 bytes), AArch64 to `add x0, x0, x1; ret` (8 bytes), and RISC-V to `add a0, a0, a1; ret` (8 bytes, or 4 with compression).
Now a migration estimate. A service moves from x86 servers to ARM (for example Graviton) at about 20% lower price per unit of compute. A pure Java or Go service needs only a new image, since the JVM and the Go compiler target both. A C++ service with AVX2 intrinsics needs a NEON version of its hot loops. Native dependencies must exist as ARM builds, and the weaker memory model may expose latent data races. A realistic project is days for managed-language services and weeks for native code with hand-tuned SIMD; on a large fleet, 20% pays for it.
intuition: A language the CPU promises to understand, whatever machinery lies beneath, so the people who write the sentences and the people who build the listener never need to meet.
The design is natural because software lasts longer than hardware. A program is expensive to write and test, and a chip is replaced every few years with a faster design. If programs depended on the chip's internals, every new chip would break every program. A narrow contract in the middle lets both sides improve. The cost is that the contract itself is hard to change: whatever the first designers promised, later designers must keep. The choice of RISC or CISC is a choice about where to put complexity: in the compiler and the number of instructions, or in the hardware decoder. Since modern chips decode anything into micro-operations, the more important question became compatibility and ecosystem.
mistakes: People often think RISC chips are always faster than CISC chips, or the reverse. In fact studies comparing x86 and ARM cores with similar designs (for example Blem and others, 2013) found that the ISA has little effect on performance and energy; the microarchitecture, the process technology and the target power budget dominate. Apple's M-series are fast because of wide out-of-order design and large caches, not only because they are ARM.
People often think modern x86 is really a CISC machine inside. In fact since the Pentium Pro (1995) it translates instructions into RISC-like micro-operations. The ISA is CISC, the core is not. The translation costs some front-end area and energy, and the micro-op cache reduces it.
People often think the ISA defines performance by instruction count. In fact performance is instructions × cycles per instruction × time per cycle, and the three trade against each other. A RISC program may use 20% to 30% more instructions than the x86 version while having a higher instructions-per-cycle rate on the same silicon.
People often think the same compiled program runs on any processor of the same brand. In fact extensions matter: a binary built with AVX-512 crashes with an illegal instruction on a CPU without it, and ARM cores differ in whether they support SVE or the newer atomics. Software chooses code at run time (feature detection) or targets a baseline.
friction: Backward compatibility is the largest cost. x86 still supports 16-bit real mode, segmentation and thousands of instructions from forty years of extensions; every new chip must implement them, and the decoder and verification effort grows. Proposals to drop old modes (such as x86S, 2023) have not reached products, while new features such as APX (more registers) keep being added, which shows how hard cleaning up is.
Switching an ecosystem takes a decade. Moving to ARM or RISC-V needs compilers, operating systems, JITs, debuggers, libraries with optimized assembly, and vendors' binary-only software. Apple solved this with Rosetta 2, which translates x86 binaries, and by controlling its whole stack; the data centre world must rebuild each dependency. Software with inline assembly or intrinsics, and anything that depends on x86 memory ordering, needs work.
Fragmentation is a risk for open ISAs. RISC-V's modularity means two chips can both be "RISC-V" and still not run the same binary; profiles (such as RVA23) and platform specifications try to fix a common baseline. Custom extensions help vendors but split software. For ARM, the licence model controls who can build what, and licence fees and legal disputes (such as the Arm and Qualcomm case) have made some companies look to RISC-V. For x86, only Intel, AMD and a few licensed partners can make chips, so the choice of suppliers is narrow.
practice: Treat the ISA as a deployment dimension. Build and publish multi-architecture container images (`docker buildx` with linux/amd64 and linux/arm64), run CI on both, and test performance on both before moving a fleet. For managed languages (JVM, Go, Python, Node) the move is usually easy; check native dependencies and JNI libraries first. In Databricks, Spark and Kafka deployments, ARM instance types (Graviton) often give 10% to 30% better price-performance for the same job; validate with your own workload, because vectorized or native engines (Photon, native libraries) may be tuned for one ISA.
When you write performance-sensitive native code, do not assume x86. Use portable intrinsics libraries or compiler vectorization first, detect features at run time (CPUID on x86, the auxiliary vector or system registers on ARM) and provide a fallback. Do not rely on x86's strong memory ordering; write code with C++ or Java atomics that are correct on the weak model. Mind alignment and endianness: x86, AArch64 and RISC-V are all little-endian in practice, but file formats and network protocols have their own byte order.
Read assembly when it matters. `objdump -d`, Compiler Explorer (godbolt.org) and `perf annotate` show what the compiler produced. Learn one RISC ISA well (RISC-V is the cleanest to learn from), and the x86 basics: it makes profiler output, crash dumps and security reports readable. When reading a stack trace or a core dump, knowing where the return address lives (stack on x86, link register on ARM and RISC-V) explains how crashes and exploits work.
tradeoffs: Choose x86-64 when you depend on binary-only software, specific AVX-512 or AMX kernels, or an existing x86 fleet and tooling, and the migration cost is higher than the saving. Choose ARM (Graviton, Ampere, Axion, Apple M) for scale-out services in managed languages, where lower price and power per core (often 20% or more) pay back a one-time porting effort, and for laptops where battery life matters.
Choose RISC-V for embedded controllers, custom accelerators and academic or sovereign projects where an open, royalty-free, extensible ISA matters more than a mature server software ecosystem; for general data-centre use in 2026 it is still early. You give up ready software and the depth of tooling.
Choose to compile for a baseline ISA (for example x86-64-v2, v3) with run-time dispatch for hot kernels, rather than for the newest extension, when the same binary must run on a mixed fleet. Choose a build per micro-architecture (-march=native) only when you control all machines: it is fastest and breaks on older or different chips.
Choose a fixed-width, simple encoding when you design an ISA or a core for high-width parallel decode and low power; choose a dense variable-length encoding when code size or instruction-cache pressure dominates (microcontrollers with RISC-V compressed or Thumb-2). Modern designs mix both: RISC-V C and Arm's Thumb-2 add short forms to a regular base.
interview: What is the difference between ISA, microarchitecture and ABI? Give an example of each. || The ISA is the hardware-software contract: instructions, registers, exceptions (AArch64, x86-64). The microarchitecture is one implementation: pipeline, caches, predictors (Apple Firestorm, Intel Golden Cove). The ABI is the software convention over the ISA: calling convention, struct layout, system call numbers (System V x86-64). A new microarchitecture keeps the ISA and ABI, and a new ABI can exist on the same ISA.
Is x86 really slower or less efficient than ARM because it is CISC? || Mostly no. Modern x86 cores decode into micro-ops and execute them like RISC cores, with a micro-op cache to avoid decode cost. The ISA affects decode width and area (variable length is harder to decode in parallel) and legacy overhead, but studies find core design, process node, and power targets matter far more. ARM's recent advantage comes largely from wide, efficient designs and mobile-focused optimisation.
Why does fixed-length encoding help a wide front end? || With fixed-length instructions, the start of every instruction in a fetch block is known, so 6 to 8 decoders can work in parallel on separate instructions with no dependence on one another. With variable length (x86), finding boundaries is a serial process, so cores use predecode bits, length prediction and a uop cache to get the same width.
You are asked to move a fleet of services from x86 to ARM. What do you check and what can go wrong? || Check runtime and language support (JVM and Go fine), native dependencies and container base images, SIMD intrinsics and inline assembly, third-party binaries, and CI for both architectures. Risks: weaker memory ordering exposing latent data races, different floating-point or undefined-behaviour results, performance differences from different cache sizes or vector widths, and tooling gaps. Canary a small share and compare latency and cost.
Why did Itanium fail while x86 survived, and what does this tell you about ISAs? || Itanium needed new compilers to find parallelism statically (VLIW/EPIC), could not run x86 software fast, and arrived late. AMD64 extended x86 compatibly. It shows that the software ecosystem and compatibility decide an ISA's survival more than technical elegance, and that hardware can hide ISA complexity through translation.
quiz: What does an ISA define, and what does it leave open? || It defines instructions, registers, addressing, exceptions and memory ordering that software can rely on. It leaves open the implementation: pipeline, caches, predictors, execution units.
Why can a CISC instruction set run well on a modern out-of-order core? || The front end decodes each complex instruction into simple micro-operations, and the core executes those like a RISC design. The micro-op cache stores them so hot code skips decoding.
Name two properties of a load/store RISC ISA that help pipelining. || Only loads and stores access memory, so arithmetic has predictable latency, and fixed-length instructions with fixed field positions make decoding and register reading simple and parallel.
How many bytes does `counter += 1` take in x86-64 (`add DWORD PTR [rdi], 1`) and in base RISC-V? || 3 bytes in x86-64 (83 07 01) and 12 bytes in base RISC-V (lw, addi, sw at 4 bytes each), or fewer with 16-bit compressed forms.
When would you choose RISC-V over ARM for a new product? || When an open, royalty-free, customizable ISA matters: embedded controllers, custom accelerators, or when licence cost and control are important. For general server software, ARM's ecosystem is far more mature.
