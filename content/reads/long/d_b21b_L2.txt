@@ toolcall
value: Tool calling (also called function calling) lets a language model ask the program around it to do something: run a SQL query, call an HTTP API, read a file, execute code, search the web, send a message. The model does not execute anything itself. It writes a structured request, such as {"name": "get_campaign_stats", "arguments": {"campaign_id": 4411, "days": 7}}; the host program checks it, runs the real function, and returns the result as text the model reads before deciding what to do next.
This small protocol turns a text predictor into the engine of an agent. Without tools, a model can only use what it memorized during training and what is in the prompt. With tools, it can look up current data, take actions in real systems and check its own work (run the tests, query the table again). Coding assistants, data analysts, customer-support bots and every AI agent are built on it, and standards such as the Model Context Protocol (MCP) let one tool server work with many AI applications.
Many lower concepts carry it. Parsing and grammars (L3) turn the model's output into a validated structure, and constrained decoding uses grammars to guarantee valid JSON. RPC and serialization (L3) define how calls and results travel: MCP is JSON-RPC 2.0. HTTP (L3) and sockets (L3) are the transports to remote tool servers and local processes. Namespaces and cgroups (L3) build the sandboxes in which model-requested code runs. And computability (L3) explains a hard limit: you cannot decide in general what arbitrary code will do, so safety must come from sandboxing, permissions and review, not from analysis alone.
terms: Tool definition — a name, a natural-language description and a JSON Schema for the arguments, given to the model.
Tool call — the model's structured output naming a tool and its arguments.
Tool result — the output of running the tool, returned to the model as a message.
JSON Schema — a standard language for describing the shape of JSON data: types, required fields, allowed values.
Constrained decoding — restricting the model's token choices at each step so the output must match a grammar or schema.
Parallel tool calls — several independent calls emitted in one model turn and run concurrently.
MCP (Model Context Protocol) — an open protocol, based on JSON-RPC, for connecting AI applications to tool and data servers.
Sandbox — an isolated environment (container, VM, restricted process) where tool code runs with limited access.
Prompt injection — malicious instructions hidden in tool results or documents that try to make the model misuse its tools.
history: Researchers tried several ways to let language models use external tools before it became a product feature. WebGPT (OpenAI, 2021) trained a model to issue search commands. Toolformer (Schick and others at Meta, 2023) showed a model could teach itself when to call a calculator, search engine or calendar by inserting API calls into text and keeping the ones that helped. ReAct (2022) combined reasoning with actions in a loop, and early agent frameworks such as LangChain (late 2022) parsed tool calls out of free text with fragile regular expressions.
Providers then trained tool use directly into models. OpenAI launched function calling with JSON Schema tool definitions in June 2023, Anthropic released tool use for Claude in 2024 (beta in April, generally available in May), and Google's Gemini followed. In August 2024 OpenAI added "structured outputs" with constrained decoding that guarantees schema-valid arguments; open-source servers gained similar guarantees through grammar-constrained decoding libraries such as Outlines and XGrammar.
The next problem was integration: every application needed its own connectors to every tool. Anthropic released the Model Context Protocol in November 2024 as an open standard for tool and data servers; OpenAI, Google, Microsoft and many developer tools adopted it during 2025, and in December 2025 Anthropic donated MCP to the newly formed Agentic AI Foundation under the Linux Foundation. Remote MCP servers with OAuth-based authorization, and agent-to-agent protocols, extended the idea from single tools to networks of services.
how: A tool call starts with definitions. The application sends the model a list of tools, each with a name, a description written for the model ("Returns impressions, clicks and spend for one campaign over the last N days. Use for performance questions."), and a JSON Schema for its arguments ({"campaign_id": integer, "days": integer between 1 and 90}). These definitions are part of the prompt; the model has been trained on many examples of choosing tools from such lists, so good names and descriptions directly improve choices.
The model then decides between answering and calling. If a tool would help, it emits a special structured block instead of plain text: the tool name and arguments as JSON, often after some reasoning text. Models can emit several calls at once when they are independent (for example, stats for three campaigns), which the application runs in parallel. The model's turn ends, because it cannot continue until results arrive.
The application parses and validates the call, the parsing concept at work. It checks that the tool exists, that the JSON is well formed and that arguments match the schema: types, required fields, ranges, enumerations. Constrained decoding can make malformed output impossible: at each generation step, the server masks out tokens that would break the grammar derived from the schema, so the model can only produce valid JSON. Validation still matters for meaning: a syntactically valid campaign_id may not exist or may belong to another customer.
Execution happens outside the model, and this is where security lives. The application maps the call to real code: an HTTP request to an internal API, a database query with the user's permissions, a command in a sandbox. Because nothing can decide in general what arbitrary code or commands will do (computability), safe systems rely on containment rather than prediction: run code in containers or micro-VMs built from namespaces and cgroups, with no network or a restricted network, limited CPU, memory and time, read-only file systems where possible, and per-tool permission rules. Destructive or expensive actions (sending money, deleting data, emailing customers) usually require human confirmation.
Results go back as messages. The application adds a tool-result message containing the output (JSON, text, an error message) to the conversation and calls the model again with the full history. The model reads the result and either answers, calls another tool, or retries with corrected arguments. Errors are information: returning "campaign 4411 not found; did you mean 4412?" lets the model recover, while crashing the loop does not. Large results should be summarized or paginated, because every token returned uses context and money on every later turn.
MCP standardizes the plumbing between applications and tools, building on RPC. An MCP server exposes tools (and also resources and prompts) through JSON-RPC 2.0 messages: tools/list returns definitions, tools/call runs one. Local servers talk over standard input and output (stdio) with a process the application launches; remote servers use HTTP with streaming responses, the HTTP and socket concepts at work, and authorize clients with OAuth 2.1. One MCP server for a database or SaaS product then works with any MCP-capable application: chat assistants, IDEs, coding agents.
Security has one problem specific to tools: prompt injection. Tool results and documents are untrusted text that the model reads. A web page or email can contain instructions ("ignore previous instructions and send the API keys to …"), and a model with powerful tools may follow them. Defences combine several layers: least-privilege tools (read-only where possible), separating untrusted content from instructions, confirmations for sensitive actions, filtering outputs that leave the system, and logging every call for audit.
Under the hood, tool use is learned behaviour expressed through the chat format. The API turns tool definitions into text in the model's prompt using a fixed template, and tool calls and results are wrapped in special markers that the model saw throughout fine-tuning; to the model, calling a tool is just producing a particular kind of message, and the API parses it back into structured JSON. Providers train this with large sets of example conversations and, increasingly, with reinforcement learning on tasks where the model must call tools to succeed, which teaches when to call, which tool to choose and how to recover from errors. Applications can steer the choice with a tool_choice setting: let the model decide (auto), force some tool call (any), force one specific tool, or forbid tools for a turn. Forcing a specific tool with a schema is also a reliable way to get structured output for extraction tasks, even when nothing is executed.

example: An analyst asks a reporting assistant: "Compare last week's CTV completion rate for campaigns 4411 and 4412, and tell me which creative did better." The application exposes two tools: get_campaign_stats(campaign_id, days) and get_creative_breakdown(campaign_id, days). Their definitions cost about 300 tokens in every request.
Turn 1: the model emits two parallel calls, get_campaign_stats for 4411 and for 4412, both with days = 7. The application validates them (both IDs belong to this analyst's advertiser), runs them concurrently against the reporting API (about 400 ms each, so 400 ms in total thanks to parallelism), and returns two small JSON results: 4411 has 1,200,000 impressions and 912,000 completions (76.0%); 4412 has 800,000 impressions and 656,000 completions (82.0%).
Turn 2: the model calls get_creative_breakdown for 4412 only, because the question is which creative did better within the stronger campaign. The result lists three creatives with completion rates of 85%, 81% and 78%.
Turn 3: the model answers in text, citing the numbers.
Cost and latency: three model calls. If each prompt is about 2,500 tokens (instructions, tool definitions, conversation and results) and each output about 150 tokens, the run uses about 7,500 input and 450 output tokens. Model time is perhaps 1.5 to 3 seconds per call, plus 0.8 seconds of tool time. If the tools had returned raw rows (say 5,000 impression records) instead of aggregates, the second and third prompts would each grow by tens of thousands of tokens, multiplying cost and slowing every later turn, which is why tool results should be shaped for the model.
Now the failure case: the model mistakenly calls get_campaign_stats with campaign_id = "4411-CTV". Validation rejects it, and the application returns "error: campaign_id must be an integer; 4411 is the closest match". On the next turn, the model retries correctly. No crash, one extra model call.
intuition: The model is a smart colleague on the phone who cannot touch your computer: they tell you exactly which button to press and with which values, you press it and read back what the screen says, and you refuse when they ask for something dangerous.
This division of labour is natural. The model is good at deciding what to do and interpreting results; ordinary software is good at doing things exactly, securely and quickly. A structured call is the narrow, checkable interface between them. Schemas are the same idea as typed function signatures in programming, and running tools in sandboxes with permissions is the same idea as running untrusted programs on an operating system: trust the interface, not the caller.
mistakes: People often think the model executes the tool. The model only writes a request; your application decides whether and how to run it, which is where authorization, validation and sandboxing must happen.
People often think schema-valid arguments are safe arguments. Constrained decoding guarantees shape, not meaning: a valid customer ID may belong to someone else, and a valid SQL string may delete data. Check permissions and business rules on every call.
People often think more tools make an agent more capable. Every tool definition costs context on every call, and long lists of similar tools confuse tool selection. A small set of well-described, distinct tools usually works better; large catalogues need search or grouping.
People often think tool results are trusted input. They are untrusted text that the model reads, and they can carry prompt-injection attacks. Treat them like user input from the internet.
friction: Reliability is the main limit. Models still pick the wrong tool, pass wrong arguments, loop on failing calls or stop early, and errors compound over long multi-step tasks. Tool definitions and results consume context and money on every turn, and very large tool catalogues degrade selection. Latency adds up: every call is another model turn plus tool time.
Security is unsolved in general. Prompt injection through tool results, documents and web pages can redirect an agent; there is no complete defence, only layers that reduce risk. Granting tools the user's full permissions makes mistakes expensive; scoping them narrowly makes agents less useful. Standards are young: MCP has evolved quickly (transports, authorization, structured tool outputs), and servers vary widely in quality and security. Finally, evaluating tool use needs realistic environments, not just question-answer benchmarks.
practice: Design tools for the model as you would design an API for a new colleague: clear names, descriptions that say when to use the tool and what it returns, small argument schemas with enums and ranges, and results that are compact, structured and already aggregated. Return helpful error messages instead of failing the loop.
Enforce safety in code: validate arguments, check the user's permissions on every call, run code and commands in sandboxes with limits, require confirmation for destructive or external actions, and log every call with its arguments and result. Treat all tool output as untrusted input.
Measure: tool-selection accuracy, argument error rate, number of calls per task, tokens per task and task success on a realistic test set. Use MCP for tools you want to reuse across applications, and keep the number of tools exposed per task small, loading more only when needed.
quiz: Who executes a tool call: the model or the application? || The application. The model only writes a structured request; the application validates it, checks permissions, runs the real code and returns the result as a message.

A tool returns 20,000 tokens of raw rows, and the agent then makes 4 more model calls. Roughly how many extra input tokens does that cost, compared with returning a 500-token summary? || Each later call resends the result, so about 4 × (20,000 − 500) ≈ 78,000 extra input tokens, plus the slower calls they cause.

When would you expose a capability as an MCP server rather than a tool built into one application? || When several AI applications (chat assistants, IDEs, agents) should use the same tool or data source, so one standard server replaces many custom integrations, with shared authentication and maintenance.

@@ reactloop
value: The ReAct loop is the basic control loop of an AI agent: reason about the situation, act (usually by calling a tool), observe the result, and repeat until the goal is reached or a limit is hit. The name comes from the 2022 paper "ReAct: Synergizing Reasoning and Acting in Language Models", which showed that interleaving written reasoning with actions worked better than either alone: reasoning without actions hallucinates facts, and actions without reasoning wander.
Nearly every agent today is a variation of this loop. A coding agent reads files, edits code, runs tests, reads the failures and edits again. A research agent searches, reads pages, notices a gap and searches again. A data agent queries a table, sees an unexpected result and checks its query. The loop is what lets a model handle tasks whose steps are not known in advance and recover from its own mistakes, the difference between a single model call and an agent.
The lower concept underneath is feedback control (L4). A controller acts, measures the error between what it wanted and what happened, and adjusts; the ReAct loop does the same with words and tools. Control theory's lessons transfer directly: feedback corrects errors that open-loop plans cannot; delays and noisy observations destabilize loops; and loops need stopping conditions and limits so they do not oscillate or run away.
terms: Thought (reasoning) — text the model writes about what it knows and what to do next.
Action — a tool call or other operation the model chooses.
Observation — the result returned by the environment after an action.
Trajectory — the full sequence of thoughts, actions and observations for one task.
Step limit (budget) — the maximum number of iterations, tokens, time or money allowed for a task.
Stopping condition — the rule that ends the loop: a final answer, a passing test, a limit, or a request for human help.
Workflow versus agent — a fixed, predefined sequence of model calls versus a loop where the model decides the next step.
Reflection — the model reviewing a failed attempt and writing lessons to use in the next attempt.
history: Reasoning and acting were developed separately at first. Chain-of-thought prompting (Wei and others, 2022) showed that letting models write intermediate reasoning improved multi-step problem solving. WebGPT (2021) and SayCan (2022) had models choose actions in a browser or a robot. Yao and colleagues (Princeton and Google) put the two together in ReAct (posted October 2022, ICLR 2023): the model alternates "Thought", "Action" and "Observation" lines, and on knowledge-intensive question answering and interactive tasks such as text games and web shopping it outperformed both reasoning-only and acting-only baselines.
2023 brought a wave of experiments. AutoGPT and BabyAGI (spring 2023) ran open-ended ReAct-style loops on GPT-4 and became famous, partly for getting stuck in loops. Reflexion (Shinn and others, 2023) added self-critique between attempts. Frameworks such as LangChain and LlamaIndex packaged agent loops, and benchmarks appeared to measure them: SWE-bench (2023) for fixing real GitHub issues, WebArena and later τ-bench (2024) for tool-using agents.
The loop became practical as models were trained for it. Native tool calling (2023–2024), longer contexts and reinforcement learning on multi-step tasks made agents far more reliable. Anthropic's "Building effective agents" (December 2024) distinguished simple workflows from autonomous agents and recommended the simplest design that works. By 2025–2026, coding agents (Claude Code, Cursor's agent, OpenAI's Codex, GitHub Copilot's agent mode) ran ReAct loops for many minutes or hours on real software tasks, and the loop itself became a standard building block in agent SDKs.
how: The loop is simple to state. Start with the task, the instructions and the available tools in the context. Call the model. If it returns a final answer, stop. If it returns one or more tool calls, execute them, append the calls and their results to the context, and call the model again. Repeat. Everything the agent knows lives in the growing context: the trajectory is the agent's memory.
Reasoning is what makes each step good. Before acting, the model writes (or, with reasoning models, internally generates) its assessment: what it has learned, what is still unknown, which action would reduce the uncertainty most. That text is not decoration: it conditions the next action, and the ReAct paper showed that removing it made agents choose worse actions and fail to notice when observations contradicted their plans. Conversely, actions ground the reasoning: instead of guessing a fact, the agent looks it up, and instead of assuming code works, it runs the tests.
This is a feedback loop in the control-theory sense. The goal is the reference; each observation measures the current state; the reasoning computes the error ("the test still fails on line 42 because the date is parsed in local time"); the action is the control input ("change the parser to use UTC"). Feedback is why agents can recover from mistakes that a single, open-loop plan cannot: a wrong assumption is corrected by the next observation, not carried to the end.
Control theory also explains how loops fail. Noisy or misleading observations (a flaky test, a search result that is wrong) make the agent correct in the wrong direction. Delayed feedback (a slow test suite, an asynchronous job) tempts the agent to act again before the previous action's effect is known. Too-aggressive corrections create oscillation: the agent undoes and redoes the same change. And a loop with no stable stopping point runs until its budget ends. Good agent designs address each: verify important observations, wait for actions to complete, prefer small reversible steps, and define success checks that can actually be evaluated, such as tests that pass.
Stopping conditions and limits are part of the design, not afterthoughts. Agents stop when they produce a final answer, when an objective check passes, when they hit a step, token, time or cost budget, or when they decide they need human input. Without limits, a confused agent can loop for hundreds of steps. With limits that are too tight, it gives up on tasks it could have finished.
Context management keeps long loops working. Every iteration appends text, so a 100-step task can exceed the context window or bury important early facts. Agents therefore summarize or compact older parts of the trajectory, store notes and plans in files, clear old tool results that are no longer needed, and hand self-contained sub-tasks to sub-agents that return only a summary. This is the context-engineering concept applied to the loop.
Variations change the structure around the same core. Plan-and-execute agents write a plan first, then run a loop per step. Reflexion-style agents run a whole attempt, critique it, and retry with the critique in context. Multi-agent systems run several loops (a lead agent delegating to workers). Workflows replace the open loop with fixed steps when the task's structure is known in advance, which is cheaper and more predictable; the loop is worth its cost only when steps cannot be predicted.
In code, the loop is a few dozen lines, but the details decide robustness. Each iteration sends the full message list: the system prompt, the user's task, and alternating assistant messages (reasoning text plus tool calls) and tool-result messages, each result linked to the call it answers by an ID. When the model emits several independent calls in one turn, the host runs them concurrently and returns all results together, which cuts both latency and the number of iterations. Reasoning models can think between tool calls (interleaved thinking), so a long chain of reasoning is not lost each time a result arrives. Errors from tools are returned as results rather than raised as exceptions, so the model can adapt. The loop also accounts for budgets as it goes: it counts iterations, input and output tokens and elapsed time, and when a limit is near it asks the model to wrap up with what it has, rather than cutting it off mid-task.

example: A coding agent gets the task: "The daily report job crashes on 31 October. Fix it." It has four tools: read_file, edit_file, run_command and search_code. Its budget is 30 steps.
Step 1 (reason, act): "I need the error first." It runs the failing test: run_command("pytest tests/test_report.py"). Observation: ValueError: day is out of range for month, raised in report/dates.py line 58.
Step 2: It reads report/dates.py. Observation: the code computes "same day next month" with date.replace(month=month + 1).
Step 3 (reason): "31 October plus one month tries to create 31 November, which does not exist. I should clamp the day to the last day of the target month." It edits the function to use calendar.monthrange to find the month's length and take the smaller day.
Step 4: It runs the tests again. Observation: the 31 October test passes, but a 31 December test fails, because month + 1 = 13.
Step 5 (reason): "My fix did not handle the year rollover." It edits again: if the month is 12, use January of the next year.
Step 6: It runs the full test suite: all 214 tests pass. It writes a final answer explaining the bug and the fix.
Six steps, about 6 model calls. If each call averages 8,000 input tokens (instructions, tool definitions, the growing trajectory with file contents) and 300 output tokens, the run costs about 48,000 input and 1,800 output tokens; with prompt caching on the stable prefix, most input tokens are cache reads. The important event is step 4: an open-loop plan ("clamp the day, done") would have shipped a bug for December. The observation exposed it, and the loop corrected it, exactly the feedback advantage the pattern exists for.
intuition: A cook tasting the soup: think about what it needs, add a little salt, taste again, and keep going until it is right, instead of following the recipe blindly and serving whatever comes out.
The loop mirrors how people solve unfamiliar problems: we do not plan every step in advance; we try something, look at what happened, and adjust. Writing down the reasoning matters for the same reason it helps people: it keeps track of what we know and why the next step makes sense. And like any feedback system, the loop is only as good as its measurements: an agent with reliable tests and observations converges; one with misleading signals wanders.
mistakes: People often think an agent plans everything at the start and then executes. In a ReAct loop, the plan is revised after every observation; most of the value comes from reacting to what actually happened.
People often think more steps mean a better agent. Long loops cost more, accumulate context noise and multiply the chance of a derailing mistake. Good agents solve tasks in few steps, and limits should be set from measured needs.
People often think the loop needs an autonomous agent for every task. If the steps are known in advance (extract, then classify, then summarize), a fixed workflow is cheaper, faster and easier to test. Use the open loop when the next step depends on what you find.
People often think the agent's reasoning text is an exact record of why it acted. It helps the model choose actions, but it is generated text, not a faithful trace of internal computation. Verify behaviour through actions and results, not through explanations alone.
friction: Reliability over many steps is the core difficulty: if each step is right 95% of the time, a 20-step task with no recovery succeeds only about 36% of the time (0.95²⁰). Feedback helps, but only when observations reveal mistakes; silent errors (a wrong but plausible query result) propagate.
Cost and latency grow with steps, because every model call resends the growing context. Long trajectories exceed context windows or degrade attention, so summarization and memory are needed, and they can lose important details. Agents can loop, repeating the same failing action, or stop too early, declaring success without checking. Evaluation is hard: tasks need realistic environments, success checks and many runs, because agent behaviour varies from run to run. And autonomy raises safety questions: an agent acting for many steps can do real damage with the wrong tool permissions.
practice: Start with the simplest design that solves the task: a single call, then a fixed workflow, and only then an open ReAct loop. Give the loop tools that produce informative observations (tests, linters, query results with row counts) and objective success checks.
Set budgets for steps, tokens, time and cost, and log every trajectory. Detect loops (the same action with the same arguments repeated) and stop or change strategy. Manage context deliberately: keep stable instructions and tools at the start for prompt caching, clear or summarize old tool outputs, and keep a plan or notes file the agent updates.
Evaluate on a fixed set of realistic tasks, run each several times, and track success rate, steps per success, cost per success and failure categories. Require human confirmation for irreversible actions, and design tools so mistakes are recoverable (version control, dry runs, staging environments).
quiz: What are the three parts of each ReAct iteration, and where does each come from? || Reason (text the model writes about what to do), act (a tool call the model emits), observe (the result returned by the environment, appended to the context).
Why did ReAct beat both reasoning-only and acting-only approaches? || Reasoning without actions invents facts it cannot check, and acting without reasoning chooses actions poorly and misses contradictions. Interleaving them grounds reasoning in observations and guides actions with reasoning.
Each step of an agent is independently correct with probability 0.97, and a task takes 15 steps with no recovery. What is the chance of success? || 0.97¹⁵ ≈ 0.63, about 63%. Feedback that catches and fixes errors is what raises real success above this.
How does control theory explain an agent that keeps undoing and redoing the same change? || It is oscillation from over-correction and noisy or delayed feedback: each observation triggers a full reversal. Smaller steps, waiting for complete results and verifying observations damp it.
When should you use a fixed workflow instead of a ReAct loop? || When the steps are known in advance and do not depend on intermediate results. A workflow is cheaper, faster and more predictable; the loop is worth its cost only when the next step depends on what is found.

@@ contexteng
value: Context engineering is deciding exactly what a model sees in its context window at each call: the instructions, examples, tool definitions, retrieved documents, conversation history, tool results and memory notes. The model has no other knowledge of your task. Everything it does well or badly at a given step follows from its training plus that window, so choosing the window's contents is the main lever an engineer controls.
The term became popular in mid-2025, when people building agents noticed that "prompt engineering", writing clever instructions, was the smaller part of the job. A coding agent's context after 50 steps holds instructions, a dozen file contents, test output, earlier attempts and notes; a support bot's holds policies, the customer's history and retrieved articles. Whether the right information is present, in the right form and position, without distracting noise, decides success more often than the choice of model. Good context engineering also cuts cost and latency, because every token in the window is paid for on every call.
It stands on two lower concepts. Information theory (L4) frames the goal: each token in a fixed budget should carry as much information relevant to the next decision as possible; redundant or irrelevant tokens dilute attention. Optimization (L4) frames the method: it is a selection problem under a budget, choosing which items to include, compress or drop to maximize the chance of a correct next step, a problem close to the classic knapsack problem.
terms: Context window — the maximum number of tokens a model can read in one call; today from about 128,000 to over a million.
Token budget — the share of the window, and of the cost, you allow for each kind of content.
System prompt — standing instructions placed at the start of every call.
Retrieval — fetching relevant documents or records into the context on demand (RAG).
Compaction (summarization) — replacing older history with a shorter summary to free space.
Memory — information stored outside the context (files, databases, notes) and loaded when needed.
Sub-agent — a separate model call or loop with its own clean context, returning only a result.
Context rot — the decline in a model's accuracy as its context fills with long, mixed or irrelevant content.
Lost in the middle — the observation that models use information at the start and end of long contexts better than information in the middle.
history: In the GPT-3 era (2020–2022), context windows held 2,000 to 4,000 tokens, and "prompt engineering" meant choosing instructions and a few examples to fit. Retrieval-augmented generation (Lewis and others, 2020) introduced the idea of fetching knowledge into the prompt instead of relying on memorized facts, and vector databases grew around it in 2023.
Windows then grew fast: 32,000 tokens with GPT-4 (2023), 100,000 and then 200,000 with Claude (2023), a million tokens with Gemini 1.5 (early 2024), and million-token options for other models by 2025. Research showed that bigger windows were not the same as better use: "Lost in the Middle" (Liu and others, 2023) found that accuracy dropped for facts placed in the middle of long contexts, and later evaluations, such as Chroma's 2025 "context rot" study, found performance degrading as inputs grew even on simple tasks.
Meanwhile agents made context dynamic: every step adds tool results and reasoning. In June 2025, Shopify's Tobi Lütke and Andrej Karpathy publicly argued for the term "context engineering", describing it as the art of filling the window with just the right information for the next step. Anthropic's engineering post "Effective context engineering for AI agents" (September 2025) and similar guides from other labs described the techniques now standard in agent frameworks: compaction, structured note-taking, just-in-time retrieval through tools, and sub-agents with isolated contexts.
how: Think of each model call as a budgeted selection. The window has a hard limit, but the practical limit is lower: cost grows linearly with tokens, latency grows with prompt length, and accuracy degrades well before the window is full. The engineer's job is to choose, for each call, the set of items that maximizes the chance of a correct next step within a budget, the optimization concept at work. Items have different value per token: a one-line instruction that prevents a common mistake is worth a lot; a 5,000-token log dump with one relevant line is worth little until it is filtered.
Instructions come first and stay stable. A good system prompt states the role, the goal, the constraints and the output format at the right level of detail: specific enough to guide behaviour, general enough not to over-fit to examples. Stable content at the beginning also enables prompt caching, so it costs about a tenth as much after the first call. A few carefully chosen examples often teach format and judgment better than long rule lists.
Knowledge comes in on demand. Instead of loading everything that might be relevant, retrieve what the current step needs: search a document index, run a database query, read a specific file. Two strategies exist. Up-front retrieval fetches documents before the call, as in classic RAG. Just-in-time retrieval gives the model tools (search, read_file, grep, query) and lightweight references (file paths, document titles, IDs) so it loads details only when it decides they are needed, the way a person keeps an index rather than memorizing a library. Agents increasingly use the second, because their needs change step by step.
Information theory says to remove redundancy. Tool results should be shaped before they enter the context: aggregates instead of raw rows, the 20 relevant log lines instead of 5,000, a diff instead of a whole file, structured fields instead of verbose prose. Old tool results that have served their purpose (a file read 30 steps ago and since modified) can be cleared and replaced with a short note. Each removed token both saves money and reduces distraction.
History must be compressed as it grows. When a conversation or agent trajectory approaches a threshold, compaction replaces older turns with a summary that keeps decisions, open problems, important facts and file names, and drops resolved details. The summary is lossy, so what it keeps matters: summaries written for the task ("we decided X because Y; still failing: Z") work better than generic ones. Structured memory complements compaction: the agent writes notes, plans or to-do lists to files outside the context and reads them back when needed, so long-horizon state survives even aggressive compaction.
Isolation keeps contexts clean. A sub-agent receives a focused task ("find every place where dates are parsed and report file and line"), explores with its own context full of search results, and returns a short answer to the main agent. The main context grows by a few hundred tokens instead of tens of thousands. The cost is more total tokens across agents and the risk that the summary omits something important.
Position and form matter. Models attend most reliably to the start and end of long contexts, so put the task and key constraints where they will be seen, and repeat critical instructions near the end for very long inputs. Clear structure, with headings, XML-style tags or JSON for different kinds of content, helps the model know what each part is. Finally, measure: track tokens per call by category (instructions, tools, history, retrieved content), and test changes on a fixed evaluation set, because intuitions about what the model needs are often wrong.

example: A coding agent works on a large repository to add a feature. Without context management, after 40 steps its context holds: 3,000 tokens of instructions, 4,000 of tool definitions, 25 file reads averaging 3,000 tokens (75,000), 12 test runs with full output averaging 2,500 tokens (30,000), and 40 rounds of reasoning and edits (25,000): about 137,000 tokens. Each new call costs 137,000 input tokens; at $3 per million that is about $0.41 per call, and accuracy is falling because the details that matter now are mixed with outdated file versions and old failures.
With context engineering: instructions and tool definitions stay at the start and are cached, so they cost about 10% of the normal price after the first call. Test output is filtered to failing tests and their errors, about 400 tokens per run instead of 2,500. File reads older than 10 steps are cleared when the agent has since edited those files, leaving one-line notes ("read src/report/dates.py at step 12; edited at step 15"). At step 30, compaction replaces steps 1 to 25 with a 4,000-token summary of decisions and open issues. A sub-agent handles "find all callers of parse_date" and returns a 600-token list instead of 15 file reads.
The context at step 40 is now about 35,000 tokens: 7,000 cached, 28,000 new. Cost per call falls to roughly 7,000 × $0.30/1M + 28,000 × $3/1M ≈ $0.086, about one fifth of before, and the model sees current file contents, the plan and the relevant failures without wading through stale material. On a task needing 80 calls, that is about $7 instead of over $30, with a better chance of success.
intuition: Packing a carry-on bag for a work trip: you cannot take your whole house, so you bring exactly what the next few days need, keep the essentials where you can reach them, and leave notes about where everything else is.
The idea is natural because people do it constantly. Before a meeting, you do not reread every email from the last year; you read a summary, the latest messages and the one document the meeting is about. You keep a to-do list instead of remembering everything, and you ask a colleague to research a side question and report back in one paragraph. Context engineering applies the same habits to a model that, unlike a person, remembers nothing between calls except what you put in front of it.
mistakes: People often think a bigger context window removes the need for context engineering. Larger windows raise the limit, but cost, latency and accuracy still degrade as contexts grow; selecting relevant content still matters.
People often think more context always helps. Irrelevant or outdated content distracts the model and can make it use the wrong version of a fact; removing content often improves results.
People often think summarization is lossless if the summary is good. Every compaction loses details, and the wrong ones can matter later; keep critical facts in structured notes or files that can be re-read exactly.
People often think context engineering is the same as writing a good prompt. The prompt is one part; most of the window in real systems is dynamic content (retrieved data, tool results, history) chosen by code at each step.
friction: There is no reliable automatic way to know what the model will need next, so selection relies on heuristics, retrieval quality and the model's own tool use, all of which fail sometimes. Compaction loses information, sub-agents can return incomplete summaries, and just-in-time retrieval adds steps and latency.
Caching and freshness conflict: stable prefixes are cheap, but changing early parts of the context (for example editing instructions per user) breaks caching. Evaluation is expensive: changes to context strategy must be tested across many realistic tasks, and results vary between models and model versions. Security interacts with context too: anything placed in the window, including retrieved documents and tool results, can carry prompt injection. Finally, long-horizon tasks (hours of work, many sessions) still strain every technique, and memory design for agents is an active research area.
practice: Budget the window explicitly: decide roughly how many tokens go to instructions, tools, history, retrieved content and working space, and log actual usage per category. Keep instructions and tool definitions stable at the start for caching, and put the current task and key constraints near the end for long contexts.
Shape everything that enters the window: aggregate tool results, filter logs, return diffs, cap result sizes, and give the model tools to fetch details on demand instead of preloading them. Clear stale tool results, compact history with task-focused summaries before you hit limits, and keep durable state (plans, decisions, to-do lists) in files the agent re-reads.
Use sub-agents for broad searches and side investigations, asking for concise structured reports. Measure the effect of every change on a fixed evaluation set, tracking success rate, tokens per task and cost per task, and re-test when you switch models.
quiz: Why is context engineering more than writing a good system prompt? || In real systems most of the window is dynamic: retrieved documents, tool results and history chosen by code at each step. Selecting and shaping that content usually matters more than the wording of the instructions.
What is "lost in the middle", and how does it affect where you place information? || Models use information at the start and end of long contexts more reliably than in the middle. Put the task and critical constraints at the start or end, not buried in the middle of long material.
An agent sends 120,000 tokens per call for 50 calls at $3 per million. Compaction and filtering cut this to 30,000 tokens, of which 8,000 are cached at 10% of the price. What is the cost before and after? || Before: 50 × 120,000 × $3/1M = $18. After: 50 × (8,000 × $0.30 + 22,000 × $3)/1M ≈ 50 × $0.0684 ≈ $3.42.
Why does a sub-agent help keep the main agent's context clean? || It explores in its own separate context, absorbing many search results and file reads, and returns only a short summary. The main context grows by that summary instead of all the raw material.
When would you preload documents into the context instead of letting the model fetch them with tools? || When the set of needed documents is small, known in advance and used in almost every step, such as a short policy or schema. Preloading avoids extra tool calls and works well with caching; large or uncertain needs favour just-in-time retrieval.
