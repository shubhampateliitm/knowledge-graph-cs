value: A constraint satisfaction problem (CSP) is a way to describe a puzzle without saying how to solve it. You list the **variables** (the things to decide), the **domain** of each variable (the values it may take), and the **constraints** (rules that limit which combinations are allowed). A solution is an assignment of one value to every variable that breaks no rule. Sudoku has 81 variables, each with domain 1 to 9, and 27 "all different" rules (9 rows, 9 columns, 9 boxes). Map colouring, timetabling, shift rosters, and "which version of each package can be installed together" all have the same shape.
The reason this idea matters is the split between **what** and **how**. Once a problem is written as a CSP, one general solver can attack it, and the solver can use the structure of the rules to avoid most of the work. The core method is simple: assign variables one at a time, use the rules to remove values that can no longer work (this is called propagation), and when a variable has no value left, go back to the most recent choice and try something else (backtracking). A good solver explores a tiny part of the search space, even though the space has \( d^n \) points for n variables with d values each.
For the layer above, this is the engine behind planning and scheduling (automated planners, factory and airline schedulers), behind placement decisions in orchestration systems (which node can host this container, given resources, affinity and anti-affinity rules), and behind dependency resolvers such as PubGrub in Dart's pub, Poetry and uv. The layers below explain why this works and where it stops: logic says what a constraint is, graph theory gives the structure that propagation runs on, SAT solvers offer a powerful way to solve the same problems by translation, and the theory of P vs NP says the general problem is hard, so every practical solver is a set of clever shortcuts.
terms: Variable — an unknown that must receive exactly one value, such as the colour of one country or the digit in one Sudoku cell.
Domain — the set of values a variable may still take; propagation makes domains smaller.
Constraint — a rule over one or more variables that says which combinations of values are allowed, for example "A ≠ B" or "all of these cells differ".
Constraint graph — a graph with one node per variable and an edge between two variables that appear in a common constraint.
Arc consistency — a state where, for every constraint between X and Y, every value in X's domain has at least one supporting value in Y's domain.
Backtracking — depth-first search that assigns one variable at a time and returns to the last choice when a dead end is reached.
Propagation — removing values from domains because of the constraints, without making any new guess.
Heuristic (MRV) — "minimum remaining values": choose next the variable with the fewest values left in its domain.
Global constraint — one constraint over many variables with a dedicated fast algorithm, such as all-different or cumulative (resource limits over time).
history: The idea of searching by trial and error with undo is old. Golomb and Baumert (1965) described "backtrack programming" as a general method, and Bitner and Reingold (1975) collected its tricks. The step that made it a field of its own was to look at the **constraints** instead of just the failed attempts. In the early 1970s David Waltz was working on a computer-vision problem: given a line drawing of blocks, decide which lines are edges of which shapes. Each junction of lines had only a few legal labellings, and removing labels that could not fit with a neighbour solved most of the drawing with almost no search. This became known as Waltz filtering. Ugo Montanari (1974) wrote the first general theory of "networks of constraints", and Alan Mackworth (1977) defined arc consistency and the algorithm AC-3, which is still the textbook method.
In the 1980s Eugene Freuder showed which structure makes a CSP easy: if the constraint graph is a tree, a solution can be found in time \( O(n d^2) \) without any backtracking. Rina Dechter and others developed ways to make a general graph "more like a tree" (cutset conditioning, tree decompositions) and the "conflict-directed backjumping" methods of Prosser (1993) which jump back to the real cause of a failure. Haralick and Elliott (1980) introduced forward checking and the "fail-first" rule (now called MRV).
Two other threads joined this field. Constraint logic programming (Jaffar and Lassez, 1987; Prolog systems with finite-domain solvers) put constraints inside a programming language. From the 2000s, SAT solvers got much faster with clause learning (CDCL), and "lazy clause generation" (Ohrimenko, Stuckey, Codish, 2009) combined CP propagation with SAT learning. This is the design of Google's OR-Tools CP-SAT, which has won many gold medals in the MiniZinc Challenge, and it is why modern practical solvers are hybrids. Dechter's book "Constraint Processing" (2003) is the standard reference.
how: A CSP solver is a loop with three parts: choose, propagate, and undo. Here is the full procedure.
Step 1: Choose a variable. Look at the variables that have no value yet and pick one by a heuristic. The best simple rule is MRV (fewest remaining values), because a variable with two choices left is most likely to fail soon, and failing early is cheap. Ties are broken by "degree": pick the variable that appears in the most constraints with unassigned variables. This is the "fail-first" principle: you want the search tree to be narrow near the root.
Step 2: Choose a value. Try values in a good order. A common rule is to try first the value that rules out the fewest values for the neighbours (least constraining value). Unlike variable choice, value choice should keep options open, because if the problem has a solution you want to find it quickly.
Step 3: Propagate. After assigning a value, use the constraints to shrink the domains of other variables. The cheapest form is **forward checking**: for each neighbour of the assigned variable, delete the values that conflict. If any domain becomes empty, this choice is a dead end, and you can stop at once instead of going deeper. A stronger form is **arc consistency** (AC-3). Keep a queue of arcs (X, Y). For each arc, remove from X's domain every value that has no supporting value in Y. If X's domain changed, put all arcs (Z, X) back in the queue, because Z's supports may be gone. Repeat until the queue is empty. The cost is \( O(e d^3) \) for e constraints and domain size d (AC-4 and later algorithms reach \( O(e d^2) \)). This is where graph theory enters: the constraint graph tells you which arcs to re-check, and the structure of the graph (tree, cycles) tells you whether propagation alone is enough. On a tree, arc consistency plus a left-to-right assignment never needs to backtrack.
Step 4: Recurse or undo. If all variables are assigned, you have a solution. If a domain is empty, undo the last assignment (restore domains from a saved copy or a trail of changes) and try the next value. If no value is left for this variable, return to the previous variable. This is plain depth-first search; its memory use is only the depth \( n \).
```python
def solve(domains, constraints):
    if all(len(d) == 1 for d in domains.values()):
        return {v: next(iter(d)) for v, d in domains.items()}
    # MRV: unassigned variable with the smallest domain
    x = min((v for v in domains if len(domains[v]) > 1),
            key=lambda v: len(domains[v]))
    for val in order_values(x, domains, constraints):
        trial = {v: set(d) for v, d in domains.items()}
        trial[x] = {val}
        if ac3(trial, constraints):        # False if a domain empties
            result = solve(trial, constraints)
            if result is not None:
                return result
    return None                            # backtrack
```
Global constraints make propagation much stronger. "All different" over a set of cells can be checked as a matching problem in a bipartite graph (Régin, 1994): if fewer values remain than variables, the constraint fails, even if each pair looks fine. Scheduling constraints such as cumulative (tasks that share a limited resource) have their own algorithms. Industrial solvers are mostly a library of such constraints.
Where does SAT fit? Any finite CSP can be written as a Boolean formula: one Boolean per (variable, value) pair, a clause saying "at least one value", clauses saying "at most one value", and one clause per forbidden combination. A CDCL SAT solver then does the search, and it learns a new clause from every failure so that the same mistake is not repeated anywhere else in the search. CP-SAT does both: it propagates with CP constraints and explains each deletion to the SAT engine, which learns from it. SAT contributes learning; CP contributes compact modelling and strong propagation for numbers and global rules.
Lastly, the hardness. Deciding if a general CSP has a solution is NP-complete (graph 3-colouring is a special case), so no known algorithm is fast on all inputs. Solvers work because real problems have structure: loose constraints, a near-tree graph, or strongly propagating rules. This is also why the same solver can be instant on one Sudoku and run for hours on a similar-sized scheduling problem.

example: Take three variables A, B, C, each with domain {1, 2, 3}, and the rules A < B and B < C. Run arc consistency. For the arc A < B: the value A = 3 has no larger B, so remove 3 from A. The value B = 1 has no smaller A, so remove 1 from B. Now A is {1, 2} and B is {2, 3}. For the arc B < C: B = 3 has no larger C, so remove it, leaving B = {2}; and C = 1 has no smaller B, so C is {2, 3}. B changed, so re-check A < B: A must be below 2, so A = {1}. Re-check B < C: C must be above 2, so C = {3}. The solution A = 1, B = 2, C = 3 is found with zero guesses. Propagation alone solved it.
Now a case that needs search: 4-queens. Put one queen in each column; the variable Qi is the row of the queen in column i. The rules are that no two share a row or a diagonal. Try Q1 = 1. Forward checking leaves Q2 in {3, 4}. Try Q2 = 3: the queen at row 3 in column 2 attacks rows 2 and 4 in column 3 by diagonal and row 3 by row, and Q1 attacks row 1 in column 3 by row. So Q3 has no value: dead end, detected right after the assignment. Try Q2 = 4: Q3 is left with only row 2. Set Q3 = 2: column 4 loses row 1 (same row as Q1), row 4 (same row as Q2), row 2 (same row as Q3), and row 3 (diagonal from Q3). Empty: dead end. No more values for Q2 or Q3, so Q1 = 1 is impossible. Try Q1 = 2: forward checking leaves Q2 = 4 only. Then Q3 can only be row 1 (rows 2 and 4 are taken, row 3 is on Q2's diagonal). Then Q4 must be row 3, and every rule holds. The solution (2, 4, 1, 3) was found after two dead ends, each cut short because a domain became empty.
intuition: Solving a CSP is like filling a crossword: each word you write removes letters from the crossing words, and when a square has no letter left you rub out your latest word.
The design is natural because mistakes are local and information is local. A rule involves only a few variables, so it can say something useful as soon as one of them is fixed. Instead of waiting until the whole assignment is complete to find a violation (the generate-and-test method), propagation moves the check forward in time to the earliest moment it can fail. Failing early at depth 3 saves the entire subtree below it, which can hold millions of leaves. The heuristics follow from the same view: decide the most constrained variable first because that is where the problem pushes back hardest, and keep value choices flexible because a good value leaves room for the rest.
mistakes: People often think backtracking means trying all possibilities and is just brute force. In fact it prunes a whole subtree whenever a partial assignment already breaks a rule, and with propagation it often prunes before any rule is broken. The gap to brute force is many orders of magnitude on typical problems.
People often think arc consistency solves a CSP. In fact it only removes values that cannot appear in any solution of a single pair of variables. Many problems stay unsolved after propagation: arc-consistent domains can still hide a contradiction that needs three or more variables to see, such as colouring a triangle with two colours. You still need search, and global constraints or stronger consistency to catch more.
People often think a better programming language or a faster machine fixes a slow CSP. In fact the running time depends mainly on the model: which variables you choose, which global constraints you use, and whether you add redundant constraints and symmetry breaking. Two models of the same problem can differ by a factor of 1000 or more, and a model that makes a constraint implicit (as an unstructured list of forbidden pairs) hides structure from the solver.
People often think NP-complete means the solver is useless. In fact it means that there is no guarantee for the worst case. Real instances usually have structure, and CP and SAT solvers routinely handle industrial problems with millions of variables. The risk is predictability: you cannot be sure that the next input, slightly different, will not be hard.
friction: The main problem is that the running time is unpredictable. Heavy-tailed behaviour is well documented: for the same instance, a randomised solver can finish in a second on one run and in an hour on another run, depending on early choices. Real solvers use random restarts with learning to fight this, and portfolio approaches that run several strategies in parallel.
Modelling is a skill and it is where most of the effort goes. A natural model may be too weak (little propagation) or too large (a variable per time slot per employee). Symmetry is another source of waste: if the n machines are identical, the solver may explore n! equivalent assignments unless you add rules that break the symmetry. Optimisation, as opposed to finding any solution, adds the question of proving that no better solution exists, which can take much longer than finding the best one.
CSP solvers also work with hard constraints only. Real planning has preferences (soft constraints), uncertainty, and data that changes while you solve. Online systems, such as a container scheduler, usually do not run a full CSP solver at all: Kubernetes filters nodes by simple predicates and then scores the survivors, because a decision must take milliseconds and always return something. Finally, explanations are not free: telling a user why no solution exists needs extra machinery (PubGrub's conflict derivations are an example of doing this carefully).
practice: Model first. Write down the variables, their domains and the constraints before you pick a tool. Use the solver's global constraints (all-different, cumulative, circuit, no-overlap) instead of long lists of pairwise rules. Add redundant constraints that are logically implied but help propagation, and break symmetries. Fix the smallest domains you can: bounded integers propagate much better than large ranges.
For practical work, start with OR-Tools CP-SAT (Python, C++, Java) for scheduling, rostering and assignment problems: it handles integers and Booleans, finds good solutions quickly and proves optimality when it can, and uses all CPU cores in parallel. MiniZinc is a modelling language that can target many solvers, good for trying different back ends. For pure Boolean problems use a SAT solver directly; for very small or very structured problems, a short handwritten backtracking program with MRV and forward checking is often enough and easier to debug.
tradeoffs: Choose a full CSP or CP-SAT solver when the rules are many and interact, a solution is valuable enough to wait seconds or minutes, and "no solution exists" is an answer you need to be sure of, for example a weekly staff roster with 200 rules or a dependency set with thousands of versions. Choose a greedy filter-and-score heuristic when each decision must take milliseconds, new requests arrive all the time, and a good-enough answer now is better than an optimal answer later, as in a container scheduler placing thousands of pods per minute. You give up the guarantee of optimality, and sometimes completeness, when you take the heuristic.
Choose CP (propagation-based search) when the problem has rich structure such as sequencing, calendars, or all-different rules, and variables with small integer domains. Choose SAT or a MIP (mixed-integer programming) solver when the problem is mostly Boolean, or mostly linear with a good LP bound, such as a transport or blending problem with costs. CP-SAT sits between the two and is a good default, but a large linear optimisation problem may still be faster in a MIP solver.
Choose stronger propagation (full arc consistency, global constraints) when the tree is large and each node is costly to explore, as in tightly constrained scheduling. Choose cheap propagation (forward checking) when nodes are cheap and the problem is loose, because the extra work per node then costs more than it saves. Choose to write your own small backtracking solver only when the problem is tiny and fixed and needs no proof of optimality; otherwise a library with restarts, learning and symmetry handling is better than rebuilding them.
interview: Why does choosing the variable with the fewest remaining values usually help? || A variable with a small domain is the most likely to run out of values, and finding that out early cuts a large subtree. It keeps the top of the search tree narrow, so a failure is found at a shallow depth. It is a heuristic, not a guarantee, and it can be fooled by problems where all domains are equal at the start.
What is the difference between forward checking and arc consistency, and when would you not use full arc consistency? || Forward checking only prunes the neighbours of the variable just assigned. Arc consistency keeps pruning the neighbours' neighbours until nothing changes, so it finds more dead ends but costs more per node. Use the cheaper form when nodes are cheap and the problem is loose, or when the domains are large and arc revision is expensive.
How would you schedule 5,000 containers on 500 nodes with affinity rules, and would you use a CSP solver? || A pure solver gives the best result but may take too long and fails badly when requests arrive continuously. Kubernetes filters nodes by hard rules (the constraint part), scores the remaining ones, and picks the best, in milliseconds per pod. Use a solver offline for re-balancing or capacity planning, where time is available and global optimality matters.
Your solver sometimes finishes in 2 seconds and sometimes runs for an hour on the same input. What do you do? || This is heavy-tailed run time caused by early bad choices. Add random restarts with clause learning, use several solver configurations in parallel, add redundant constraints and symmetry breaking, and set a time limit with the best solution found so far. Also check if the model leaves the solver blind to structure.
How is a SAT solver related to a CSP solver, and what does each do better? || A finite CSP can be encoded as SAT with one Boolean per variable-value pair. SAT solvers are strong at learning from conflicts and at pure Boolean logic. CP solvers keep the original structure, with integers and global constraints that propagate much more strongly than the encoded clauses. Hybrids such as CP-SAT take both.
quiz: What are the three ingredients of a constraint satisfaction problem? || Variables, a domain of possible values for each variable, and constraints that restrict which combinations of values are allowed.
Why does forward checking help backtracking? || After each assignment it removes the conflicting values from neighbouring variables. If a neighbour's domain becomes empty, the search knows immediately that this choice is a dead end and does not explore the subtree below it.
Why can AC-3 solve A < B, B < C over {1,2,3} with no search? || Pruning unsupported values leaves B = {2}, which forces A = {1} and C = {3}. Each removal triggers a re-check of the neighbouring arcs until nothing changes, and here this leaves exactly one value per variable.
A problem has 60 variables with 10 values each. How many complete assignments exist, and why does a solver not examine them all? || There are \( 10^{60} \) assignments. The solver prunes whole subtrees at the first violated or impossible partial assignment, and propagation removes values early, so it visits a tiny fraction, often thousands or millions of nodes.
When would you prefer a filter-and-score heuristic over a CSP solver? || When decisions are online and must take milliseconds with always an answer, such as pod placement. You accept a good but not optimal answer. Use the solver offline when time is available and optimality or proof of infeasibility matters.

value: Lossless compression makes data smaller in a way that can be undone exactly: the decompressed bytes are identical to the original. It works because real data is not random. Text repeats words, logs repeat field names, images repeat colours, and even in a file with no repeats some byte values are more common than others. A compressor finds this redundancy and writes it in fewer bits. Information theory gives the limit: the best possible average size is the entropy of the source, and no lossless method can beat it on average.
Almost every modern system uses it. Web servers send gzip or Brotli. Kafka producers compress record batches, and Parquet files compress every column page with Snappy or Zstandard (Zstd). Operating systems, backup tools, PNG images and the final stage of video codecs all depend on it. At data-centre scale, a 3x reduction means a third of the disk, a third of the network traffic, and often faster jobs, because decompressing 1 GB/s of data costs less time than reading 3 GB/s from storage that cannot deliver it.
The design has two stages that attack two different kinds of redundancy. The first stage, LZ77 matching, removes repeated strings by replacing a repeat with a pointer to an earlier copy. The second stage, entropy coding (Huffman, arithmetic coding or ANS), gives frequent symbols short codes and rare symbols long codes. The layers below supply the foundations: information theory defines the target (entropy), trees give the data structure behind Huffman codes, and hash tables make it fast to find earlier copies of a string.
terms: Entropy — the average information per symbol, \( H = -\sum p_i \log_2 p_i \) bits; the lower bound for lossless coding of a source with these probabilities.
Prefix code — a code where no codeword is the start of another, so a bit stream can be decoded without separators.
Huffman code — the best prefix code that gives each symbol a whole number of bits, built from symbol frequencies.
LZ77 — a method that replaces a repeated string with a pair (distance back, length) that points into the already seen data (the sliding window).
Sliding window — the most recent part of the data (for example 32 KB in DEFLATE) in which matches are searched.
Arithmetic coding / range coding — entropy coding that represents the whole message as one number in an interval, so symbols can cost fractions of a bit.
ANS (asymmetric numeral systems) — a newer entropy coder with the compression of arithmetic coding and the speed of table lookups.
Compression ratio — original size divided by compressed size; 3.0 means one third of the size.
Literal — a byte that is written as it is because no useful earlier match was found.
history: Claude Shannon's 1948 paper defined entropy and proved that coding can approach it. Shannon and Robert Fano each proposed a code that was good but not best. In 1951 David Huffman, then a student of Fano at MIT, was offered a choice between a final exam and a term paper on finding the most efficient binary code. He found a simple bottom-up construction and proved that it is optimal among codes with whole-bit lengths. It was published in 1952 and is still taught unchanged.
Huffman coding needs the symbol statistics in advance. Abraham Lempel and Jacob Ziv found a different path: in 1977 (LZ77) and 1978 (LZ78) they described methods that learn the structure while reading the data, with no prior statistics, and proved they approach the entropy rate for a large class of sources. Terry Welch's 1984 variant LZW became the basis of Unix compress and GIF. In 1989 Phil Katz combined LZ77 with Huffman coding in PKZIP; this became DEFLATE (RFC 1951, 1996). The gzip tool of Jean-loup Gailly and Mark Adler (1992) and the zlib library made DEFLATE nearly universal, and PNG uses it.
The next ideas were about the entropy stage. Arithmetic coding (Rissanen and Pasco, 1976) removes the whole-bit limit of Huffman but was slow and for years surrounded by patents. In 2009 Jarek Duda published asymmetric numeral systems (ANS), which reach arithmetic-coding quality at Huffman-like speed. Yann Collet released LZ4 in 2011 (very fast matching, no entropy stage), then Zstandard at Facebook (2015 to 2016, RFC 8478, updated by RFC 8878), which uses Huffman for literals and a table form of ANS (FSE) for match descriptions. Google created Snappy (2011) and Brotli (2013 to 2015, RFC 7932), which adds a built-in dictionary of common web strings.
how: Lossless compressors usually run as a pipeline: first remove repeated strings, then encode what is left with a code matched to its statistics.
Step 1: Find matches (LZ77). Read the input left to right while keeping the last W bytes (the window). At the current position, look for the longest earlier string that starts the same way. If the match is long enough (DEFLATE uses 3 bytes or more), write a pair (length, distance) instead of the bytes; otherwise write the byte as a literal. A match may overlap the current position, which is allowed and useful: "distance 3, length 9" after "abc" copies abc three times, which is how a run is encoded. Finding the longest match quickly is the job of a **hash table**: hash the next 3 or 4 bytes, and the table points to earlier positions with the same hash, kept as a chain of candidates. Fast modes (LZ4, zstd level 1) check one or two candidates; slow modes (gzip -9, zstd -19) walk long chains or use a binary tree of the window and also try "lazy matching", where the encoder looks one byte ahead to see whether a longer match starts there.
Step 2: Model the symbols. After step 1 the stream has literals, match lengths and match distances. They have very uneven frequencies, which entropy coding exploits. Shannon's bound says a symbol with probability p should cost \( \log_2(1/p) \) bits. A symbol with probability 1/2 should cost 1 bit; one with probability 1/1024 should cost 10 bits.
Step 3: Huffman coding. Count the frequency of each symbol. Put all symbols in a priority queue (a heap, from the data-structure layer). Repeatedly remove the two least frequent nodes, join them under a new node whose weight is the sum, and put it back. When one node is left, it is the root of a binary tree. A symbol's code is the path from the root (left = 0, right = 1). Frequent symbols are close to the root and get short codes. The result is a prefix code, so decoding is a walk down the tree, or a table lookup of the next 11 or so bits. In practice, codes are made canonical: only the code lengths are stored in the file header, and the decoder rebuilds the exact codes from them. The limit of Huffman is that every code length is a whole number of bits. A symbol with probability 0.9 should cost 0.15 bits but costs 1 bit. For skewed distributions this wastes a lot.
Step 4: ANS or arithmetic coding. These coders fix the fractional-bit problem. In the range ANS (rANS) form, the encoder keeps one integer state x. To encode a symbol s with frequency \( f_s \) out of a total M, and cumulative frequency \( c_s \) of the symbols before it, the new state is
\[ x' = \lfloor x / f_s \rfloor \cdot M + c_s + (x \bmod f_s) \]
Rare symbols (small \( f_s \)) grow the state a lot, which costs many bits; common symbols grow it a little. The state grows by almost exactly \( \log_2(M/f_s) \) bits per symbol, the ideal cost. When x gets too big, the encoder writes out its low bits and shrinks it again, so x fits in a machine word. The decoder runs the formula backward, and it needs only a table lookup per symbol. Zstd's FSE is the table-driven version (tANS), which avoids multiplications and divisions. Because of this, Zstd decodes at more than 1 GB/s per core while still beating DEFLATE on ratio.
Step 5: Format and framing. A real format adds block headers, checksums (a CRC or xxHash of the data), dictionary support, and a way to restart or to compress blocks in parallel. Dictionaries matter for small items: a pre-trained dictionary acts as the "earlier data" for LZ77, so 1 KB JSON messages can compress by 5x or more instead of barely at all.
The parts fit together in a clear way. Information theory says what is achievable and gives the yardstick (entropy). Trees and heaps give the Huffman construction and fast decoding. Hash tables supply cheap match finding, which is what makes LZ77 practical at hundreds of MB per second. LZ77 captures patterns in order (repeat strings); the entropy coder captures patterns in frequency (some symbols are common). The two are separate sources of savings, which is why the combination beats either alone.

example: Huffman on the string "abracadabra" (11 characters). The counts are a = 5, b = 2, r = 2, c = 1, d = 1. Plain 8-bit text needs 88 bits. Build the tree: join the two lowest, c and d, into a node of weight 2. Now the weights are a 5, b 2, r 2, cd 2. Join b and r into a node of weight 4. The weights are now a 5, cd 2, br 4. Join cd and br into 6. Finally join a (5) and 6 into the root (11). The codes are a = 0, c = 100, d = 101, b = 110, r = 111. The length is 5 × 1 + 2 × 3 + 2 × 3 + 1 × 3 + 1 × 3 = 23 bits. The entropy is about 2.04 bits per character, so the ideal is about 22.4 bits: Huffman is within 0.6 bits of it here.
Now LZ77 on "abcabcabcabc" (12 bytes). The encoder writes the literals a, b, c. At position 3 the longest earlier match starts at distance 3 and, because overlap is allowed, runs to the end: length 9. The output is three literals plus one pair (distance 3, length 9). The decoder copies one byte at a time from 3 bytes back, so the copy sees the bytes it has just written.
Now a rANS step you can check by hand. Let there be two symbols: a with frequency 3 and cumulative 0, b with frequency 1 and cumulative 3, so M = 4. Start with state x = 16. Encode a: \( \lfloor 16/3 \rfloor = 5 \), so x = 5 × 4 + 0 + (16 mod 3 = 1) = 21. Encode a again: \( \lfloor 21/3 \rfloor = 7 \), x = 7 × 4 + 0 + 0 = 28. Encode b: \( \lfloor 28/1 \rfloor = 28 \), x = 28 × 4 + 3 + 0 = 115. The state grew from 16 to 115, about 2.85 bits. The ideal cost of the message a, a, b is 2 × log₂(4/3) + log₂(4/1) = 0.83 + 2 = 2.83 bits, so the coder is almost exactly at the entropy bound. To decode, compute slot = 115 mod 4 = 3, which falls in b's range (slot 3), so the last symbol is b, and the previous state is 1 × (115 div 4) + 3 − 3 = 28. Then 28 mod 4 = 0 is in a's range (slots 0 to 2), so x = 3 × 7 + 0 = 21; then 21 mod 4 = 1 is a, x = 3 × 5 + 1 = 16. The symbols come out in reverse order, so real encoders process the input backward.
For real speeds, the Zstd project reports on the Silesia benchmark corpus (Core i7-9700K, version 1.5.7): zstd level 1 gives ratio 2.90 at 510 MB/s compression and 1,550 MB/s decompression; zlib level 1 gives 2.74 at 105 and 390 MB/s; LZ4 gives 2.10 at 675 and 3,850 MB/s. So Zstd is both smaller and several times faster than zlib, and LZ4 trades 25% of the ratio for much higher speed.
intuition: Compression is shorthand: write "see above" for a repeated passage, and use a single letter for the words you use all the time.
There are only two ways to say the same thing in fewer symbols. You can notice that something was said before and point back to it (LZ77), or you can notice that some things are said more often and give them cheaper names (entropy coding, as with Morse code, where E is a single dot). A third is not possible for all data: counting shows that there are fewer short strings than long strings, so any method that makes some inputs smaller must make others larger. Compression is therefore a bet on the data having structure, and the entropy tells you exactly how big the winnings can be.
mistakes: People often think a good compressor can shrink any file. In fact no lossless method can, because there are \( 2^n \) files of n bits but fewer than \( 2^n \) shorter ones; at least some inputs must stay the same size or grow. Compressed, encrypted or random data is incompressible, and a second round of compression usually makes it slightly larger.
People often think Huffman coding is optimal. In fact it is optimal only among codes that spend a whole number of bits per symbol. If one symbol has probability 0.99, Huffman still spends 1 bit on it, while the entropy is 0.08 bits per symbol. Arithmetic coding and ANS remove this limit.
People often think a higher compression level is always better. In fact the gain is small and the cost is large: going from zstd level 3 to level 19 might give 10% to 15% smaller output while compression becomes 20 to 50 times slower. Decompression speed stays nearly the same, so high levels suit data written once and read many times (release packages, cold storage), not hot data paths.
friction: Compression ratio, speed and memory pull in different directions, and you can only choose two. High ratios need big windows and long searches, which cost time and memory. Zstd's long-distance mode and its highest levels use tens to hundreds of MB of memory in the encoder, and the decoder needs memory for the whole window. Small data is the hardest case: a 200-byte message has no history to refer to, and the overhead of headers and tables can make the output larger than the input unless you use a shared dictionary.
Compression interacts with the rest of the system. Compressed data is harder to search and update: you must decompress a block to read one record, so formats like Parquet and ORC compress in blocks of a few hundred KB and keep an index of block positions, which limits random access. Compression and encryption have a dangerous interaction: when the attacker can add chosen text to the secret before compression, the output length leaks the secret (the CRIME and BREACH attacks on HTTPS), so the secret must not be compressed together with attacker-controlled data. Decompression can also be abused: a "zip bomb" a few KB in size may expand to many GB, so services that decompress untrusted input must limit the output size.
practice: Pick the codec by where the data lives. For data in motion on fast networks (Kafka batches, RPC), use LZ4 or Zstd at a low level (1 to 3), because speed matters and the ratio is already good. For data at rest in a lake (Parquet, ORC), Zstd at level 3 is a strong default: usually 10% to 30% smaller than Snappy for a moderate CPU cost, with fast decompression. For web assets, Brotli level 11 at build time and gzip or Brotli at a lower level for dynamic responses. For archives you write once, use the highest practical level.
Compress in blocks that match the access pattern. Batch many small records into one compressed block (Kafka does this per record batch), because compression ratio improves with size: 64 KB to 1 MB blocks are common. For many small similar objects, train a dictionary (`zstd --train`) on a sample and ship it with the data; gains of 3x to 10x on messages of 1 KB or less are typical.
tradeoffs: Choose LZ4 (or Snappy, or Zstd with a negative or fast level) when throughput matters more than size: shuffle files, hot caches, network links of 10 Gbit/s and more, where the codec must keep up with the hardware. You give up 20% to 30% in size compared with Zstd level 3. Choose Zstd at levels 3 to 9 as the general default for storage and most network use, since it is both faster and smaller than zlib at similar settings.
Choose Brotli or Zstd at the highest levels when data is compressed once and delivered many times, such as static web files or software releases, and you can pay 10 to 100 times the time for several percent smaller output. Choose gzip (DEFLATE) only for compatibility, for example with old clients, tools and file formats like PNG and ZIP; you pay in speed and ratio.
Choose entropy coding by ANS when you need arithmetic-coding efficiency at high speed, and Huffman when simplicity, hardware implementation or the lowest decoding latency matters (JPEG and DEFLATE use it). Choose no compression for data that is already compressed or encrypted, and for small data on a local fast disk where the CPU cost exceeds the savings.
interview: Why can a compressor not make every file smaller? || A counting argument: there are \( 2^n \) possible n-bit files and only \( 2^n - 1 \) bit strings that are shorter, so no mapping can shrink every input and stay reversible. A compressor wins on structured inputs and pays with small growth on random ones.
How does Huffman coding work, and when does it fall short of entropy? || Repeatedly merge the two lowest-weight nodes with a heap to build a binary tree; the path to a leaf is the symbol's code. It is optimal among whole-bit codes, but wastes up to nearly 1 bit per symbol when probabilities are not powers of 1/2, which is serious for skewed sources. ANS or arithmetic coding fix this.
Why are hash tables important in LZ77? || The encoder must find an earlier occurrence of the next few bytes at every position. A hash of the next 3 to 4 bytes indexes a table of earlier positions, so candidates are found in about constant time instead of scanning the window. Chain length and number of candidates tested set the speed versus ratio level.
You see 100 GB per hour of JSON logs on Kafka. Which codec and what changes would you make? || LZ4 or Zstd level 1 to 3 at the producer, applied to batches (raise `linger.ms` and batch size so batches are larger), since ratio improves with batch size. JSON repeats keys, so ratios of 5x to 10x are common. Check CPU on producers and consumers, and use Zstd if network or disk is the bottleneck and LZ4 if CPU is.
What is the security problem when compression is used on an HTTPS response containing a secret? || If an attacker can inject text into the same compressed stream, a correct guess of the secret compresses better and makes the response shorter, so the length leaks the secret byte by byte (CRIME, BREACH). Defences: do not compress secrets with attacker-controlled data, randomise or mask the secret, or disable compression.
quiz: What are the two stages of a typical LZ-based compressor and what does each exploit? || LZ77 matching exploits repeated strings by replacing repeats with (distance, length) pointers; entropy coding (Huffman or ANS) exploits uneven symbol frequencies by giving common symbols short codes.
Why does an overlapping match (distance 3, length 9) work in LZ77? || The decoder copies one byte at a time from earlier output, and bytes it has just produced become available as the source, so the copy repeats the pattern. This is how runs are encoded.
Why can ANS beat Huffman on a symbol with probability 0.99? || Huffman must give each symbol at least 1 whole bit, while ANS lets the state grow by about \( \log_2(1/0.99) \approx 0.014 \) bits for that symbol, which is the entropy cost.
Huffman-code the counts a:5, b:2, r:2, c:1, d:1. How many bits in total? || The code lengths are 1, 3, 3, 3, 3, giving 5 + 6 + 6 + 3 + 3 = 23 bits, against 88 bits in 8-bit text.
You have 2 TB of log data written once and read rarely, then 2 TB of shuffle data read once seconds after writing. Which codec for each? || Archive: Zstd at a high level (such as 15 to 19), because compression time is paid once and the ratio saves storage for a long time. Shuffle: LZ4 or Zstd level 1, because throughput matters and the data lives for seconds.

value: A pixel is stored as three numbers, for example (255, 128, 0). Those numbers mean nothing until two questions are answered: which physical colours do "red", "green" and "blue" refer to, and how does a number map to the amount of light? A **color space** answers the first question (the primaries and the white point). A **transfer function**, loosely called gamma, answers the second (the curve between the stored code value and the light intensity). Without both, the same file looks different on two screens, an image blends wrongly, and a gradient shows bands.
The system works because of a fact about the human eye. We have three kinds of cone cells in the retina, so any colour we can see produces three responses, and any light with the same three responses looks identical to us. Therefore three numbers are enough to describe a colour for a human, and a screen with three primaries can imitate most colours. The second fact is that vision is roughly logarithmic: we notice a change in brightness of about 1% at any level, not a fixed amount. So storing brightness with steps that are equal in light wastes codes on bright areas and leaves visible jumps in dark areas. Gamma encoding spreads the codes to match the eye.
For the layer above, this decides what a shader or an image library must do. Rendering and blending must be done on linear light (intensity proportional to photon count), and results must be encoded for the display at the end. Displays are calibrated to a standard space (sRGB, Display P3, Rec. 2020). Video codecs store luma and colour-difference channels (YCbCr) and shrink the colour channels. Browsers read ICC profiles to convert images to the screen. The layers below provide the content: human vision explains why three numbers suffice and why the encoding is non-linear, optics defines light as a spectrum that can be measured, and linear algebra turns conversion between spaces into a 3×3 matrix multiplication.
terms: Cone response (LMS) — the three signals from the long-, medium- and short-wavelength cones; they are the real basis of colour vision.
CIE XYZ — a standard space made by the CIE in 1931 from colour-matching experiments; Y is luminance (brightness), and all visible colours have non-negative X, Y, Z.
Primaries — the three base colours of a space (the exact red, green and blue it uses), given as chromaticity coordinates.
White point — the colour that equal R = G = B shows, for example D65, which is daylight at about 6500 K.
Gamut — the range of colours a space or device can show; a triangle in a chromaticity diagram for an RGB space.
Linear light — values that are proportional to the physical light power; doubling the number doubles the photons.
Transfer function (gamma) — the curve that maps linear light to the stored code value and back; sRGB uses roughly an exponent of 2.2 to 2.4.
Chroma subsampling — storing colour with less resolution than brightness, such as 4:2:0, which keeps one colour sample for each 2×2 block.
ICC profile — a file attached to an image that says which space the numbers are in and how to convert them to a standard reference.
history: The measurement of colour started with people, not devices. In the late 1920s William Wright and John Guild asked observers to match a test light by mixing three primary lights. Their results, collected by the CIE in 1931, gave the colour-matching functions and the XYZ space, which is still the base reference for all other spaces. In 1976 the CIE defined Lab (CIELAB), which tries to make equal numeric distances look equally different, so "delta E" can measure colour error.
The display side came later. A CRT screen has a natural non-linearity: light output is roughly the input voltage raised to about 2.4. Broadcast engineers realised this was useful, because pre-correcting the camera signal with the inverse curve both cancelled the CRT and, by luck, matched the eye's sensitivity, so 8 bits were enough. Rec. 709 (HDTV, 1990, revised 2015) fixed the primaries and curve for television. In 1996 HP and Microsoft proposed sRGB for the web and PCs, standardised as IEC 61966-2-1 in 1999, using Rec. 709 primaries with a D65 white and a curve close to a gamma of 2.2. For about twenty years, "RGB" on the web meant sRGB.
Wider gamuts followed. DCI-P3 was designed for cinema projectors; Apple used its primaries with the sRGB curve and a D65 white as Display P3 from 2015. Rec. 2020 (2012) set very wide primaries for UHD television. HDR required a new curve, because a gamma curve cannot cover the range up to 10,000 nits with 10 bits: Dolby's PQ curve (SMPTE ST 2084, 2014) is used in HDR10 and Dolby Vision, and the BBC and NHK designed HLG (2015). Björn Ottosson published OKLab in 2020, a simple perceptual space that web designers now use in CSS (`oklab()` and `oklch()`), because it makes gradients and colour scales behave better than HSL or Lab.
how: Four ideas make up the whole topic: how an eye turns light into numbers, how to name colours without a device (XYZ), how a device space relates to XYZ, and how a curve packs brightness into code values.
Step 1: Light to three numbers. A light has a spectrum, which is power at each wavelength from about 380 to 700 nm. Each cone type has a sensitivity curve; the long-wavelength cone peaks near 565 nm, the medium near 535 nm, and the short near 420 nm. Each cone adds up the spectrum weighted by its curve, which gives three numbers (L, M, S). Different spectra can give the same three numbers; these are called metamers, and they look identical. This is the physical fact that lets a display with only three narrow colours reproduce an orange that, in nature, is made of a smooth spectrum. The optics layer provides the spectra, and perception provides the curves.
Step 2: A device-free reference. CIE XYZ is a linear mix of cone-like responses that is chosen so that Y equals perceived brightness. A colour is a point (X, Y, Z). Dividing by the sum gives chromaticity (x, y), a 2D map of hue and saturation without brightness. An RGB space is defined by the chromaticity of its three primaries and its white point. Everything inside the triangle of the primaries is reachable with non-negative R, G, B.
Step 3: Conversion by matrix. Because XYZ and linear RGB are both linear in light, conversion is a 3×3 matrix. For sRGB (D65), the luminance row is
\[ Y = 0.2126\,R + 0.7152\,G + 0.0722\,B \]
and the other two rows are 0.4124, 0.3576, 0.1805 for X and 0.0193, 0.1192, 0.9505 for Z. To move between two RGB spaces, such as sRGB to Display P3, you apply the sRGB-to-XYZ matrix, then the inverse of the P3-to-XYZ matrix; both are linear algebra, and the two can be multiplied once into one matrix. Colours that land outside [0, 1] after the conversion are out of gamut for the target and must be clipped or mapped. This is the main job of an ICC-aware program.
Step 4: The transfer curve. The matrix only works on linear values. But stored values are not linear: sRGB encodes linear light c as
\[ C = 12.92\,c \ \text{for } c \le 0.0031308, \qquad C = 1.055\,c^{1/2.4} - 0.055 \ \text{otherwise} \]
(with a short straight segment at the dark end, so the slope is finite at zero). The curve is close to \( c^{1/2.2} \). The effect is that dark values get many codes: roughly half of the 256 codes are used for the darkest 20% of linear light. With 8 linear bits, the step from code 1 to code 2 would double the light in the shadows, which is visible banding. With gamma, each step is a few percent everywhere, near the eye's threshold. Gamma encoding is therefore a cheap form of lossy compression matched to perception, giving about the quality of 12 linear bits in 8.
Step 5: Do the arithmetic in the right domain. Any operation that mimics physics (blending, blurring, resizing, lighting, anti-aliasing) must be done on linear values: decode with the inverse curve, compute, then encode. Operations that mimic perception (gradients between colours, picking a lighter shade, measuring differences) are better done in a perceptual space such as OKLab. Graphics hardware helps: GPUs have sRGB texture formats that decode on read and encode on write at no extra cost, so a shader sees linear values.
Step 6: Video. Video compresses colour further. The RGB data is converted into luma Y′ (a weighted sum of the gamma-encoded channels) and two colour differences Cb and Cr. Since the eye resolves colour detail about half as well as brightness, 4:2:0 subsampling keeps Cb and Cr at half the width and height. That halves the data (1.5 samples per pixel instead of 3) with little visible loss. The weights and primaries are named in the stream (BT.709, BT.2020), and a player that ignores them shows washed-out or oversaturated colour.

example: Mix black and white 50:50, for example when a shader blurs a black-and-white edge or an image library halves a photo. The wrong way is to average the stored codes: (0 + 255) / 2 = 127.5, about 128. The right way is to decode, average, encode. White is linear 1.0 and black is 0.0, so the average linear light is 0.5. Encode with the sRGB curve: \( 1.055 \times 0.5^{1/2.4} - 0.055 \). Here \( 0.5^{0.4167} \approx 0.749 \), so the code is 1.055 × 0.749 − 0.055 ≈ 0.735, and 0.735 × 255 ≈ 188. The correct grey is code 188, but the naive average gives code 128. How bright is code 128 in reality? Decode it: \( ((0.5 + 0.055) / 1.055)^{2.4} \approx 0.214 \). It emits only 21% of the light of white, not 50%. This is why a downscaled photo of a striped shirt or a lamp with small bright points becomes too dark when resized in gamma space; the fault is known and still present in many tools.
Now a conversion. Take the Display P3 colour (0, 1, 0), a green that is more saturated than sRGB can show. Convert to sRGB: decode the gamma, apply the P3-to-sRGB matrix, and the result is approximately (−0.22, 1.04, −0.08) in linear sRGB. Two channels are negative (R and B), which means no combination of sRGB phosphors can show it. A browser must clip or gamut-map it, so the P3 green on an sRGB monitor is clipped to the pure sRGB green (0, 255, 0), which is duller than the original. The reverse (sRGB to P3) always fits. P3 covers roughly 25% more colours than sRGB.
Finally the memory and bandwidth side. A 4K frame is 3840 × 2160 = 8.3 million pixels. At 8 bits and 3 channels, RGB takes 24.9 MB; as 8-bit 4:2:0 YCbCr it takes 12.4 MB. At 60 frames per second the 4:2:0 stream is already 746 MB/s before any video codec starts, so chroma subsampling is the first and cheapest 2x saving.
intuition: A ruler for brightness that is dense where our eyes are sharp and sparse where they are not.
The design is natural because the standard only needs to match two physical facts: the eye has three sensors, so three numbers per colour are enough; and the eye judges ratios, so the code values should be spaced in ratios too. Everything else follows. A device-free space (XYZ) is needed so two different screens can agree, and a matrix is enough to go between spaces because light adds up linearly: the light from two sources is the sum of their spectra, and so also the sum of their XYZ values. The only non-linear step is the gamma curve, and it is applied at the edges: decode at the input, compute in linear light, encode at the output.
mistakes: People often think gamma is a monitor defect that we fix. In fact it is a deliberate coding scheme. Even though the CRT physics started it, modern flat panels emulate the curve on purpose, because it spends the 256 codes where the eye needs them. Linear 8-bit images would show banding in dark areas.
People often think RGB values describe a colour on their own. In fact (200, 100, 50) is a different colour in sRGB and in Display P3, and different again in Rec. 2020. The numbers are only meaningful with a space, a transfer curve and a white point. An image without a profile is assumed to be sRGB by browsers, which is fine for old images and wrong for a camera file in a wide gamut.
People often think that blending, scaling and lighting can be done directly on the stored pixel values. In fact those operations model the addition of light, so they must be done on linear values. Doing them on gamma-coded values darkens blends (the 128 versus 188 example), changes the look of anti-aliased text, and distorts lighting. Most engines now work in linear space for this reason.
People often think HSL or HSV are perceptual. In fact they are simple re-arrangements of RGB: a "50% lightness" yellow is much brighter than a "50% lightness" blue. For colour scales, gradients, and accessibility checks, use a perceptual space (OKLab, OKLCH, CIELAB) or compute luminance from linear values.
friction: Colour management is a chain, and any broken link ruins the result. A file may have no profile, the wrong profile, or a profile that the application ignores; a monitor may be calibrated differently from its profile; a browser, an operating system and a game may each do their own conversion. The most frequent visible failure is the double or missing gamma step, which makes an image look too dark and contrasty, or too pale. The fix is to know, at each stage, whether the values are linear or encoded and which space they are in.
Gamut mapping has no perfect answer. When a colour cannot be shown, the system must clip (keeps accuracy for in-gamut colours, but loses distinction between saturated ones), compress, or use a rendering intent chosen by a person. HDR adds another layer: a PQ signal describes absolute brightness in nits, but a TV can show 600 to 2,000 nits, so it must tone-map highlights, and every TV does it a bit differently. The same HDR video can look different across devices, and there is no single correct display.
Perceptual models are also approximations. CIELAB is not perfectly uniform, and CIEDE2000 corrects it with a complicated formula. OKLab is better in practice but is still a model for an average observer under normal viewing; colour vision differs between people (about 8% of men have some colour vision deficiency) and the appearance of a colour depends on its surroundings and the screen's brightness. Finally, precision matters: with 8-bit sRGB, repeated conversions or edits cause rounding errors and banding, so editing pipelines use 16-bit or floating-point linear buffers.
practice: Know which domain your data is in. Image files (JPEG, PNG, web CSS colours) are gamma-encoded sRGB by default. Do blending, blurring, resizing and lighting in linear light; in a game or renderer, use sRGB texture formats and sRGB framebuffers so the GPU decodes and encodes for you; in Python image code, convert with a library (for example the `colour` or `skimage` packages) instead of rewriting the formula by hand.
Tag everything. Export images with an embedded profile (sRGB for the web unless you control the whole chain). Put the colour primaries, transfer and matrix in the metadata of video you encode (`--colorprim bt709 --transfer bt709 --colormatrix bt709` in x264, for example), and check them in the player. For wide-gamut CSS, use `color(display-p3 ...)` with an sRGB fallback, and make gradients with `in oklab` or `in oklch` interpolation.
For accessibility and design systems, compute contrast from relative luminance with the Y formula on linearised values, as WCAG does (the WCAG 2.x contrast ratio uses the sRGB-to-linear step), and build colour scales in OKLCH so steps have even lightness. For machine learning on images, remember that most models are trained on gamma-encoded values; the normalisation constants belong to the encoded domain. When something looks wrong, test with a known pattern: a 50% checkerboard of black and white pixels should look like the solid grey of code 188, not 128, when viewed from far away.
tradeoffs: Choose sRGB when you target the broad web and mixed devices and want the safest result: nearly every screen and tool agrees with it, and it costs nothing. Choose Display P3 when your audience uses modern phones, laptops and monitors, and your content (photos, brand colours, video) has saturated colours that sRGB clips; you pay with the need for correct profiles and the risk of dull colours on old displays. Choose Rec. 2020 with PQ or HLG only for HDR video, where you also need 10-bit depth and a pipeline that does tone mapping.
Choose 8-bit gamma-encoded storage for final delivery, where it is compact and enough for the eye, and choose 16-bit or half-float linear buffers for editing, compositing and rendering, where several operations accumulate errors and highlights can go above 1.0. You pay about 2x to 4x the memory and bandwidth for that headroom.
Choose linear-light blending when physical correctness matters (anti-aliasing, lighting, scaling photos); choose blending in a perceptual space such as OKLab when you design the look of gradients and palettes. Choose 4:2:0 subsampling for natural video and photos, where it halves the data with little loss; choose 4:4:4 for screen content with sharp coloured text and graphics, where 4:2:0 causes colour fringes on thin lines.

@@ powerenergy
value: Every operation a chip does costs energy, and every joule ends as heat. Power is energy per second, and a chip, a server and a data centre can all handle only a fixed number of watts: the package can shed a few hundred watts of heat, a rack is fed with a fixed power budget, and a building has a fixed grid connection. Since about 2005, power has been the main limit on computing, more than the number of transistors. A modern data-centre GPU draws 700 W to 1,200 W, and a rack of them can draw more than 100 kW. At this scale, "how fast" is the same question as "how many operations per joule".
The key formula is short. The dynamic power of switching logic is roughly \( P = \alpha C V^2 f \), where \( \alpha \) is the fraction of gates that switch each cycle, C is the capacitance they charge, V is the supply voltage and f is the clock frequency. Voltage is squared, so lowering voltage is the strongest lever. Because a slower clock allows a lower voltage, a small loss of speed gives a large drop in power. This one fact explains dynamic voltage and frequency scaling (DVFS) in phones and laptops, multicore processors instead of ever faster single cores, and specialised accelerators that do more work per joule.
For the layer above, power sets what can be built. Warehouse-scale computers spend most of their cost on electricity, cooling and the power infrastructure. GPUs are limited by watts per rack, and Apple's M-series is designed around performance per watt. Matrix units with low-precision numbers (tensor cores) win because an 8-bit multiply costs a small fraction of the energy of a 32-bit one. The layers below explain the origin: the transistor is a switch that charges a capacitor each time, Moore's law and Dennard scaling tell the history of why chips got faster at constant power and then stopped, thermodynamics says every watt must leave as heat, and Landauer's principle gives the physical floor.
terms: Power — energy used per second, in watts (W); what a cooling system and a power supply must handle at each moment.
Energy — power integrated over time, in joules (J) or kilowatt-hours; what you pay for and what a battery stores.
Dynamic power — power spent charging and discharging capacitances when transistors switch, \( \alpha C V^2 f \).
Leakage (static) power — power lost when transistors are "off" but still conduct a small current; it flows even when the clock is stopped.
DVFS — dynamic voltage and frequency scaling: changing the clock and the supply voltage at run time to match the load.
Dennard scaling — the 1974 observation that if all dimensions and the voltage shrink by a factor k, a chip's power density stays constant while it gets faster.
Dark silicon — the part of a chip that cannot be powered on at the same time as the rest, because of the power or heat limit.
TDP — thermal design power: the heat the cooling system must be able to remove at sustained load.
PUE — power usage effectiveness of a data centre: total facility power divided by the power that reaches the IT equipment.
history: In 1974 Robert Dennard and colleagues at IBM described how to shrink a MOSFET. If you scale length, width, oxide thickness and voltage by 1/k, then the capacitance of each gate falls by 1/k, the delay falls by 1/k (so the frequency can rise by k), and the number of transistors in the same area rises by \( k^2 \). The power per gate falls by \( 1/k^2 \) (voltage squared times capacitance times frequency gives \( k^{-2} \cdot k^{-1} \cdot k \)), and the power per unit area stays the same. For thirty years this meant that each generation of chips was both denser and faster at the same power: Moore's law was a gift with no heat bill.
Dennard scaling stopped around 2005 to 2007. To keep making transistors faster, engineers had to lower the threshold voltage at which a transistor switches on, and subthreshold leakage grows exponentially when the threshold falls. The supply voltage then could not drop below roughly 0.7 to 1 V without making leakage dominant. Intel's Pentium 4 line, pushed to high clock speeds and about 100 W, hit the limit first: in 2004 Intel cancelled its planned 4 GHz successor and moved to multicore designs. Since then clocks have stayed at 3 to 5 GHz while transistor counts kept growing.
The consequences were drawn out in several well-known papers. Mark Horowitz and colleagues documented where energy goes (his 2014 talk "Computing's Energy Problem" showed that moving a number from DRAM costs hundreds of times more energy than adding it). Esmaeilzadeh and co-authors (ISCA 2011) projected that, at the then-expected scaling, a large share of a chip could not be powered at once and called it "dark silicon". Barroso and Hölzle (2007) argued for "energy-proportional" servers, because real servers at idle drew about half of their peak power. The industry response was specialisation: GPUs, TPUs and other accelerators that spend energy on useful arithmetic and not on control logic and caches.
how: Power and energy in a chip can be understood through four parts: where the watts come from, how the formula guides design, why the heat limit appears, and how data centres inherit it.
Step 1: Where the energy goes. A CMOS gate uses almost no current while it holds a value. When its output changes from 0 to 1, a charge \( Q = CV \) moves from the supply into the load capacitance (the wire and the next gates' inputs), and half of the energy \( CV^2 \) is lost as heat in the transistor's resistance; the rest is stored and lost when the output falls back to 0. This is the transistor-level fact: each switch event costs about \( \tfrac{1}{2} C V^2 \). With C around 0.1 to 1 fF and V near 0.7 V, one gate switch costs on the order of 10⁻¹⁷ to 10⁻¹⁶ joules. Multiply by the number of gates that switch in a cycle (\( \alpha \)) and by the cycles per second (f), and you get \( P_\text{dyn} = \alpha C V^2 f \).
Step 2: Leakage and the voltage floor. Even when nothing switches, a small current flows through "off" transistors, so \( P_\text{leak} = V \cdot I_\text{leak} \). The current depends exponentially on the threshold voltage and on temperature: a hotter chip leaks more, which makes it hotter. In a modern process, leakage can be 20% to 40% of the total power if nothing is done. Designers reduce it by power gating (cutting the supply to idle blocks), by using transistors of different thresholds, and by new transistor shapes (FinFET, gate-all-around), which control the channel better. Because leakage stops the supply voltage from falling below about 0.5 to 0.7 V, the \( V^2 \) lever has a floor.
Step 3: Using the formula. Frequency and voltage are linked: a lower voltage makes transistors switch more slowly, so the maximum clock falls roughly in proportion. When both fall by the same factor s, the power falls by about \( s^3 \), while the throughput falls by only s. The energy per operation, which is power divided by throughput, falls by \( s^2 \). This is the basis of DVFS: a phone lowers its clock and voltage when the screen is idle, and raises them for a short burst of work. It is also the basis of multicore: two cores at 0.8 of the frequency deliver 1.6 times the work of one core at the same total power or less. The opposite approach, "race to idle", runs fast and then stops the clock and power-gates everything, and it wins when leakage and the cost of keeping the rest of the system awake are large.
Step 4: Data movement dominates. The energy of arithmetic is small next to the cost of moving the operands. In a widely cited table for a 45 nm process (Horowitz, 2014), a 32-bit integer add costs about 0.1 pJ and a 32-bit floating-point multiply about 4 pJ; reading a word from a small on-chip SRAM costs about 10 pJ, and from DRAM about 1,000 to 2,000 pJ. The exact numbers change with each process, but the ratio stays large: off-chip memory costs hundreds of times the arithmetic. This is why designs concentrate on reusing data (caches, systolic arrays, tiling) and why narrow numbers help: an 8-bit multiply uses about 16 times less energy than a 32-bit one, and the operands are four times smaller to move.
Step 5: The heat limit and dark silicon. The thermodynamics layer says that all this energy leaves as heat; no computation is free of it. A chip of 800 mm² with 700 W has a heat flux of about 0.9 W/mm², near 90 W/cm², which is many times that of a kitchen hot plate. The cooling system (heat sink, fan or liquid cold plate) can only remove so much, and the junction temperature must stay below roughly 85 to 105 °C. Transistor counts still double every few years, but power per transistor no longer falls fast enough, so at a given power budget a part of the die must be idle or run slowly at any moment. Designers use that spare area for specialised units that switch only when needed (video decoders, matrix engines) instead of one big general core.
Step 6: From chip to facility. A data centre multiplies the chip's power by the number of servers, then adds cooling and power conversion. PUE measures the overhead: a PUE of 1.1 means 10% extra for cooling and losses; the best hyperscale sites report about 1.1, and the older enterprise rooms 1.5 or more. At the rack, a modern AI rack with 72 GPUs draws on the order of 120 kW, far above what air cooling can remove, so such racks use liquid cooling. The power feed, not the floor space, often limits how many racks a site can hold.
Landauer's principle sets the physical floor. Erasing one bit of information must release at least \( k_B T \ln 2 \) of heat, about \( 2.9 \times 10^{-21} \) J at room temperature. Today's gates spend roughly 10⁻¹⁷ to 10⁻¹⁶ J per switch, about 10⁴ to 10⁵ times more than that bound. So the limit comes from engineering, not from physics, for the foreseeable future, and the room for improvement is large but slow to claim.

example: A core runs at 3.0 GHz and 1.0 V and draws 20 W of dynamic power. Suppose a task needs \( 6 \times 10^9 \) cycles. At full speed it takes 2 s and uses 20 W × 2 s = 40 J. Now lower the clock to 2.0 GHz and, because the transistors can switch more slowly, lower the voltage to 0.8 V. The dynamic power is scaled by \( (0.8/1.0)^2 \times (2.0/3.0) = 0.64 \times 0.667 = 0.427 \), so 8.5 W. The task takes 3 s, so it uses 8.5 W × 3 s = 25.6 J. We lost 33% of the speed and saved 36% of the energy, and the average power fell by 57%. For a battery this is a good trade; for a latency-sensitive server request it may not be.
Now use two cores instead of one. A job that can be split evenly runs on two cores at 2.0 GHz and 0.8 V: the time is 1.5 s (half the cycles on each, at 2 GHz) instead of 2 s at full speed on one core, and the total power is 2 × 8.5 = 17 W, lower than the 20 W of the single fast core. Faster and cooler, but only if the code is parallel. If only 50% of the work can be split (Amdahl's law), the gain is much smaller.
Next, leakage changes the picture. Suppose the core also leaks 4 W whenever it is powered on, no matter the clock. At full speed: (20 + 4) × 2 s = 48 J. At the slow setting: (8.5 + 4) × 3 s = 37.5 J, still better, but the saving shrank from 36% to 22%. If leakage were 10 W, full speed would use 60 J and slow would use 55.5 J, nearly the same: slowing down only stretches the time in which leakage burns. When leakage is high, "race to idle" (finish fast, then power-gate to zero) is better. The right choice depends on the ratio of leakage to dynamic power, which is why phones have several states, and why the best setting is found by measurement.
Finally, a data-centre sum. One accelerator draws 1,000 W, and a rack holds 72 of them plus the CPUs and network, about 120 kW. With a PUE of 1.2, the facility draws 144 kW for it. Over a year (8,760 hours) that is 1,261 MWh; at 0.06 dollars per kWh, this is about 76,000 dollars of electricity per rack per year, before counting the cost of building the power and cooling to supply it. Cutting energy per token by 2x doubles what the same electrical connection can serve.
intuition: A chip is a heater that sometimes does arithmetic, and it is built to give the most arithmetic per unit of heat.
Switching a gate is like filling and emptying a small bucket. The bigger the bucket (C), the higher you lift the water (V, squared because both the charge and the push grow with V), and the more often you do it (f), the more energy you spend. Slowing down lets you lift less high, so the saving is more than the loss. Dennard scaling was lucky: smaller buckets that need less lift. When the lift could not go lower, the buckets kept getting smaller and more numerous, and the heat per area began to grow. From then on, the only way to get more work is to waste less: move data less, use fewer bits, and switch only the circuits that matter for the task.
mistakes: People often think a faster clock means a proportionally faster and hotter chip. In fact the power rises much faster than the speed because voltage must also rise with frequency near the top of the range, so power grows roughly with the cube of the frequency. A 20% higher clock at the top may cost 50% to 70% more power. That is why boost clocks last only for short bursts.
People often think the end of Moore's law means chips stopped shrinking. In fact transistor counts kept growing; what ended around 2005 was Dennard scaling, the part that kept power density constant. We still get more transistors per area, but we cannot switch all of them at full speed, which is the origin of dark silicon.
People often think lowering power always lowers the energy needed for a job. In fact if the job takes longer, the fixed costs (leakage, memory refresh, the rest of the system) accumulate for longer. There is an energy-optimal speed for each system, often in the middle of the range.
friction: The hardest limit is heat removal at the device scale. Heat flux of 100 W/cm² and rising needs liquid cooling, and the next steps (stacked dies, chips on top of each other with memory) make it worse, because the heat of the lower die must pass through the upper one. Package power delivery is a second problem: a chip drawing 1,000 W at 0.8 V draws more than 1,000 A, which causes voltage drops and needs power delivered by many small regulators close to the die.
At the system level, energy-proportionality is still not achieved: servers draw 30% to 50% of peak power when idle, so low utilisation is wasteful. Power capping, carbon-aware scheduling and the supply of grid power are now the limit for new AI data centres, sometimes more than chips. Last, efficiency gains are partly eaten by demand: cheaper compute per joule leads to more compute, so total energy can rise even while efficiency improves.
practice: Think in energy per useful result: joules per request, per token, per query, or per epoch. Measure it. On Linux servers, RAPL counters (`perf stat -e power/energy-pkg/`) report CPU package energy; for GPUs, `nvidia-smi --query-gpu=power.draw` or NVML gives watts; in a data centre use rack-level PDU metering. Compare the cost of energy with the cost of time: at 0.06 dollars per kWh, a 700 W GPU costs about 0.04 dollars per hour in electricity, but the capital and the power infrastructure are many times that.
Reduce data movement first. Improve locality, fuse operations so that intermediate results stay in cache or registers, use columnar formats and compression to read fewer bytes, and batch work so that each weight loaded is used many times. Use narrower numbers when quality allows: FP8, INT8 or lower for inference can cut energy per operation by 3x to 10x and the memory traffic by 2x to 4x.
tradeoffs: Choose a lower clock and voltage (DVFS or a power cap) when energy, battery life or the rack power budget is the limit and the work can tolerate some delay; a 20% slower setting often saves 35% to 50% of the power. Choose race-to-idle when leakage and system overheads are large, when deep sleep states are available, and when latency matters, since finishing fast and sleeping can use less total energy.
Choose many slower cores or an accelerator when the work is parallel: more units at a lower clock give more throughput per watt, but you pay in programming effort and in the part of the work that stays serial. Choose a single fast core for latency-critical, sequential code, and accept the high energy per instruction.
Choose a specialised unit (GPU, TPU, video decoder) when the workload is stable and large enough to justify the design cost: it can be 10x to 100x more energy-efficient than a general core, but it only helps for the task it was built for and may become useless when the algorithm changes. Choose general-purpose cores when the workload changes fast or is irregular.

value: A quantum algorithm is a recipe for a quantum computer that gives a correct answer to a classical question, with fewer steps than any known classical method. Two algorithms matter most. Shor's algorithm (1994) factors an integer N, and finds discrete logarithms, in time polynomial in the number of digits of N. The best known classical algorithm for factoring needs time that grows faster than any polynomial in the number of digits. Grover's algorithm (1996) searches an unsorted collection of N items for one that satisfies a test, using about \( \sqrt{N} \) tests instead of N.
These two results have very different weight. Shor's algorithm breaks RSA, Diffie-Hellman and elliptic-curve cryptography, which protect almost all web traffic, signatures and software updates. This is why governments and companies are migrating to post-quantum cryptography now: data recorded today could be decrypted later ("harvest now, decrypt later"). Grover's algorithm gives only a quadratic speed-up, which weakens symmetric ciphers and hashes by halving their bit strength (AES-128 acts like a 64-bit cipher against Grover, AES-256 like 128-bit), and it is cheap to defend against by using longer keys.
The algorithms do not try all answers in parallel and read the best one. That is the common wrong picture. They prepare a superposition, apply operations in which the amplitudes of wrong answers cancel and those of right answers add, and then measure. The layers below give the pieces: quantum computing supplies the qubits, superposition, interference and measurement; linear algebra describes states as vectors and gates as unitary matrices; Fourier analysis supplies the quantum Fourier transform that finds periods; and number theory shows why factoring reduces to finding a period. The layers above are post-quantum cryptography, which exists because of Shor, and quantum hardware, which is built to run these circuits.
terms: Qubit — a quantum bit; its state is a pair of complex amplitudes (a, b) with \( |a|^2 + |b|^2 = 1 \) for the values 0 and 1.
Superposition — a state that is a weighted sum of basis states, such as an equal mix of all n-bit strings.
Amplitude — the complex number attached to each basis state; its squared size is the probability of measuring that state.
Interference — amplitudes of different paths to the same outcome add or cancel; algorithms are designed so that wrong outcomes cancel.
Oracle — a black-box circuit that marks the answer (Grover) or computes a function (Shor's modular exponentiation) without revealing how.
Quantum Fourier transform (QFT) — the Fourier transform on the amplitudes of n qubits, built from about \( n^2 \) gates; it turns a periodic pattern into sharp peaks.
Period (order) finding — finding the smallest r > 0 such that \( a^r \equiv 1 \pmod N \).
Logical vs physical qubit — a logical qubit is protected by error correction and made from many noisy physical qubits.
BQP — the class of problems that a quantum computer solves in polynomial time with small error.
history: In 1985 David Deutsch described a universal quantum computer, and in 1992 he and Richard Jozsa gave a problem on which it is provably faster than a deterministic classical computer, though only as a toy. The first real signal came from Daniel Simon in 1994: a problem with an exponential quantum speed-up over classical randomised algorithms. Peter Shor, then at Bell Labs, read Simon's paper and saw that the same idea (use a Fourier transform to find a hidden period) could be applied to factoring. He presented the result at FOCS in 1994, and the journal version appeared in the SIAM Journal on Computing in 1997. The effect was immediate: factoring was the basis of RSA, and a new field of quantum cryptanalysis began.
Lov Grover, also at Bell Labs, published his search algorithm in 1996. In 1997 Bennett, Bernstein, Brassard and Vazirani proved that no quantum algorithm can search an unstructured list faster than about \( \sqrt{N} \), so Grover's method is optimal and the quadratic speed-up is the best one can hope for in that setting. This result is an important caution: quantum computers are not expected to solve NP-complete problems in polynomial time.
Early hardware experiments were tiny: in 2001 an IBM NMR machine factored 15 into 3 × 5 using Shor's algorithm. Since then the focus has moved to error correction and to better resource estimates. Gidney and Ekerå (2019) estimated that 2048-bit RSA could be broken in about 8 hours using 20 million noisy qubits. In May 2025 Gidney lowered the estimate to under one million noisy qubits and under a week, under stated assumptions (a square grid, 0.1% gate error, 1 microsecond cycle). In August 2024 NIST published the first post-quantum standards (FIPS 203, 204 and 205), and its draft transition plan (NIST IR 8547) proposes retiring RSA and elliptic-curve signatures and key exchange by 2035.
how: Both algorithms follow the same shape: prepare a uniform superposition, apply a structured operation that shapes the amplitudes by interference, and measure.
Step 1: The state space. From linear algebra: n qubits have \( 2^n \) basis states, so the state is a vector of \( 2^n \) complex amplitudes with total squared length 1. A gate is a unitary matrix (it keeps the length, so it can be undone). Measurement picks basis state x with probability \( |\alpha_x|^2 \). The size of the vector is why a classical computer cannot simulate more than about 50 qubits directly: 50 qubits need \( 2^{50} \) amplitudes, which is roughly 18 PB at 16 bytes each. The hope is that a quantum computer does not need to write the vector down.
Step 2: Grover's algorithm. Start with the equal superposition over all N = 2^n inputs, each with amplitude \( 1/\sqrt{N} \). Repeat two operations. The oracle flips the sign of the amplitude of the marked item. The diffusion step reflects every amplitude about the mean: new amplitude = 2 × mean − old. The marked item has a negative amplitude, so it is far below the mean, and the reflection moves it well above the mean; the other items shrink a little. Each round rotates the state vector in a two-dimensional plane by a fixed angle of about \( 2/\sqrt{N} \) radians, so after about \( (\pi/4)\sqrt{N} \) rounds the marked item has probability near 1. If you continue, the amplitude falls again, so you must stop at the right time. For N = 1,000,000 that is about 785 rounds instead of an average of 500,000 classical tests.
Step 3: Shor's reduction. To factor N, pick a random a coprime to N and ask for the order r, the smallest r with \( a^r \equiv 1 \pmod N \). This is number theory: if r is even and \( a^{r/2} \not\equiv -1 \pmod N \), then \( a^{r/2} - 1 \) and \( a^{r/2} + 1 \) share a non-trivial factor with N, and a gcd computation reveals it. For a random a, this works with probability at least 1/2, so a few tries suffice. The only hard part is finding r, and that is the quantum part.
Step 4: Finding the period. Use two registers. In the first, make an equal superposition of all x from 0 to Q − 1, where Q is a power of 2 with \( Q \ge N^2 \). Compute \( f(x) = a^x \bmod N \) into the second register using reversible modular arithmetic, which takes about \( n^3 \) gates with schoolbook multiplication for an n-bit N. Measure the second register. It collapses to one value, and the first register is left in an equal superposition of exactly those x that give that value: x₀, x₀ + r, x₀ + 2r, and so on, a comb with spacing r. Its position x₀ is random, which does not matter.
Step 5: Fourier transform and measurement. Apply the QFT to the first register. A comb with spacing r in the input becomes a comb with spacing Q/r in the output, and the random offset x₀ only changes phases, not the positions of the peaks. This is the interference step: contributions to non-multiples of Q/r cancel, and contributions to multiples add. Measuring gives a value close to \( kQ/r \) for a random k. The classical computer takes the fraction (measured value)/Q, uses the continued-fraction method to find the closest fraction with a small denominator, and reads off r (with a few retries when k and r share a factor). The Fourier layer provides this: the QFT is the Fourier transform of the amplitude vector, but costs only \( O(n^2) \) gates, while a classical FFT on the same \( 2^n \) values would cost \( n 2^n \).
Step 6: Cost and fault tolerance. The total gate count for factoring an n-bit number is polynomial, around \( n^3 \) with simple arithmetic and about \( n^2 \log n \) with fast multiplication. But real gates are noisy, so each logical qubit is built from many physical qubits with a surface code or similar. With physical error rates around 0.1% and a target failure rate very low, one logical qubit takes roughly 1,000 physical qubits. This overhead is why the resource estimates are millions of physical qubits, while today's machines have hundreds to a few thousand.

example: Factor N = 15 with a = 7. Classically, the powers of 7 modulo 15 are 7¹ = 7, 7² = 49 which is 4 mod 15, 7³ = 343 which is 13 mod 15, and 7⁴ = 2401 which is 1 mod 15 (2401 = 160 × 15 + 1). The order is r = 4, which is even. Then \( 7^{r/2} = 49 \), and 49 mod 15 = 4, which is not −1 (14), so we can use it. Compute gcd(49 − 1, 15) = gcd(48, 15) = 3, and gcd(49 + 1, 15) = gcd(50, 15) = 5. So 15 = 3 × 5. For this tiny N the quantum computer's only job was to find r = 4; for a 2048-bit N, checking powers one by one would take about \( 2^{2047} \) steps.
Now the quantum step with Q = 16. After measuring the second register, the first holds a comb such as x ∈ {2, 6, 10, 14} (spacing r = 4). The QFT of such a comb has peaks at the multiples of Q/r = 4, which are 0, 4, 8 and 12, each with probability 1/4. Suppose we measure 4. The fraction 4/16 = 1/4 has denominator 4, which is r. If we measure 8, the fraction is 1/2, giving denominator 2, a divisor of r, not r itself; we would need another run or combine results. If we measure 0 we learn nothing. So each run succeeds with probability about 1/2 here, and the cost of repetition is small.
Now Grover with N = 4 and the marked item at position 3. The start is amplitude 1/2 on each of the four items. The oracle flips the sign of the marked item: (1/2, 1/2, 1/2, −1/2). The mean is (1/2 + 1/2 + 1/2 − 1/2) / 4 = 1/4. The reflection 2 × (1/4) − a gives 0 for each unmarked item and 2 × 1/4 + 1/2 = 1 for the marked one. One round finds the answer with probability 1: \( |1|^2 = 1 \). For N = 1,000,000, the angle per round is about 0.002 rad, so reaching 90 degrees (π/2) takes about 785 rounds.
intuition: Shor's algorithm is like listening to a repeating sound to find its pitch: the quantum computer makes the sound (a comb of x values), and the Fourier transform reads its frequency.
Interference is the real resource. A quantum computer holds all inputs at once, but a measurement returns only one, at random. That is useless unless the amplitudes are arranged so that the interesting outcomes are very likely. In period finding, the structure of the function does it: paths for non-multiples of Q/r cancel exactly like waves out of phase. In search, Grover's rotations pump amplitude into one item. This also explains the limits: if a problem has no structure to exploit, as in unstructured search, interference can give only a square-root saving; if it has algebraic structure like the order of a number, the gain can be exponential.
mistakes: People often think a quantum computer tries all answers at once and picks the right one. In fact measurement gives one random outcome. The algorithm must make the correct answer far more likely than the others by interference, and this is possible only for problems with special structure. For most problems, no such speed-up is known.
People often think Shor's algorithm breaks all encryption. In fact it breaks the public-key schemes based on factoring and discrete logarithms (RSA, DH, ECDSA, ECDH). AES and SHA-256 are attacked only by Grover's quadratic speed-up, which is handled by longer keys. Lattice-based and hash-based schemes have no known quantum attack of this kind.
People often think Grover's algorithm gives a big speed-up for databases. In fact the speed-up is only quadratic, and it is optimal, so a search of 10⁹ items takes about 25,000 rounds, not a few. Each round needs the oracle as a quantum circuit, which is expensive; an index on a classical computer is much faster for real databases. Also Grover does not parallelise well: using k machines gives only a \( \sqrt{k} \) saving.
People often think it is only a matter of time before a laptop-size quantum machine breaks the internet. In fact the largest actual Shor runs factor numbers like 15 or 21, and a useful attack needs about a million physical qubits with low error for days. Progress is real (the estimate fell by 20x from 2019 to 2025), but the date of a cryptographically relevant machine is uncertain, and migration takes years, which is why it starts now.
friction: The main problem is noise. Qubits lose their state in microseconds to seconds, depending on the technology, and each gate has an error of about 0.1% to 1%. Shor's algorithm needs billions of gates in sequence, so error correction is mandatory, and it raises the qubit count and the run time by large factors. Today's devices have hundreds to a few thousand physical qubits and are far from this regime; the field is working on logical qubits that beat the error rate of physical ones.
Few algorithms have a proven large speed-up. Besides Shor's family (factoring, discrete logs, some hidden-subgroup problems) and simulation of quantum systems, the list is short, and for many claimed advantages (machine learning, optimisation) later work found classical algorithms that close the gap. Reading the input and the output also costs: loading a classical data set of N numbers into amplitudes takes about N operations, which cancels the benefit for data-heavy tasks.
Resource estimates are uncertain, so security planning must be conservative: the gap between "possible in principle" and "built" depends on engineering that cannot be forecast well. For defenders, the cost is a long and risky migration of protocols, certificates and hardware to larger keys and signatures (ML-KEM and ML-DSA are bigger than elliptic-curve keys and signatures), done before the threat exists.
practice: As an engineer you will mostly meet quantum algorithms as a reason for cryptographic change, not as a tool. Make an inventory of where you use RSA, DH and elliptic curves (TLS, SSH, code signing, JWT signing, VPNs, stored certificates). Plan migration using the post-quantum standards: ML-KEM (FIPS 203) for key exchange and ML-DSA (FIPS 204) or SLH-DSA (FIPS 205) for signatures. Many TLS libraries and browsers already offer hybrid key exchange (a classical curve combined with ML-KEM), which protects traffic recorded today.
Treat data with a long secrecy life as the first priority: anything that must stay secret for 10 to 20 years and is sent over public networks is at risk from harvest-now-decrypt-later. For symmetric cryptography, use 256-bit keys (AES-256) and at least 256-bit hashes; there is no need to replace the algorithms.
If you want to learn the algorithms by running them, use Qiskit or Cirq to simulate small circuits (up to about 25 qubits on a laptop): code Grover for N = 8 and the period finding for N = 15, and watch the amplitudes. Be sceptical of claims of near-term advantage for business problems; ask what the proven asymptotic speed-up is, what the input size is, and how the data is loaded.
tradeoffs: Choose to start the post-quantum migration now for long-lived secrets, firmware signing keys and anything that is hard to update later, because the migration takes years and the attack may come before you finish. You pay with larger keys and signatures, extra handshake bytes and some CPU. Choose to wait, while tracking standards, for short-lived session data and for systems that can be updated quickly, where a hybrid approach can be added when the libraries mature.
Choose hybrid key exchange (classical plus ML-KEM) during the transition, because it stays secure if either part is broken; you pay about 1 KB more per handshake. Choose pure post-quantum only where a policy requires it or the classical part is already retired.
Choose AES-256 over AES-128 when the data must stay secret for decades and against Grover; the cost is a small speed difference. Do not rush to change hash functions or symmetric ciphers otherwise.
Choose a classical algorithm or index for any search or optimisation task in production. Quantum algorithms with a quadratic speed-up do not pay for their overhead at realistic sizes: the error-correction cost per logical operation is so large that a square-root saving only wins for enormous problems.

value: A compiler turns each source file into a separate **object file**: machine code with holes in it. When `main.c` calls `add()` that lives in `add.c`, the compiler does not know where `add` will be, so it leaves a blank address and a note: "fill in the address of `add` here". The **linker** collects the object files and libraries, decides where every piece will sit, and fills in all the holes. The **loader** (part of the operating system, plus a user-space helper for shared libraries) then puts the finished program into a process's memory and starts it.
This split exists so that programs can be built from many parts that are compiled separately and reused. A change to one file does not force recompiling everything; a library such as libc is written once and shared. The sharing can happen at build time (static linking copies the needed code into each executable) or at run time (dynamic linking keeps the library in its own file, `libc.so.6`, and many processes map the same physical copy). Dynamic linking saves memory and disk, lets a security fix reach every program by updating one file, and enables plug-ins. It costs start-up work, version problems and an indirection on every call.
For the layers above, every toolchain ends here: C, C++, Rust and Go all produce object files and link them, and Docker image design depends on the choice. A Go binary is static and runs in an empty image; a C program with shared libraries needs those libraries inside the image. The layers below supply the machinery: virtual memory gives each process its own address space so the loader can place code at a chosen address and share pages; memory-mapped files are how the loader maps segments straight from the file; the instruction set decides what kinds of address fields and relocations exist; hash tables turn symbol names into addresses; and graph theory describes the dependencies between libraries.
terms: Object file — compiler output for one source file: machine code, data, a symbol table and relocation records, with addresses not yet fixed.
Symbol — a name for a function or variable; a file can define a symbol or refer to an undefined one that another file must supply.
Relocation — a record that says "patch this location with the final address of symbol S plus an offset".
Section vs segment — a section (`.text`, `.data`, `.bss`) is a unit for the linker; a segment is a unit for the loader, a contiguous range of the file mapped with one set of permissions.
Static library — an archive (`.a`) of object files; the linker copies only the members it needs into the executable.
Shared object — a library (`.so`) that is mapped into the process at run time and shared by many processes.
PLT / GOT — procedure linkage table and global offset table: small tables that let position-independent code call or read symbols whose addresses are known only at run time.
PIC / PIE — position-independent code, and position-independent executable; code that works at any load address, which is needed for shared libraries and for ASLR.
Dynamic linker (ld.so) — the program named in the executable (`PT_INTERP`) that loads the needed shared libraries and resolves symbols before `main` runs.
history: Early programs were written as one block with absolute addresses. As programs grew, assemblers created relocatable object code, and in the early 1960s linkers (IBM's "linkage editor" for System/360 in the mid-1960s is a well-known example) combined separate pieces. Multics in the 1960s had real dynamic linking at the level of the system: a program called a procedure by name and the system linked it at the first call.
Unix first used a simple a.out format with static linking. Shared libraries arrived on Unix in the late 1980s: SunOS 4 (1988) and System V Release 4 introduced them, and System V R4 brought the ELF format (Executable and Linkable Format), which Linux adopted in the mid-1990s when it moved from a.out. ELF is now the standard on Linux, BSDs and most embedded systems. Windows has the PE format with DLLs, and macOS has Mach-O with dylibs; the ideas are the same.
The tools improved over time. GNU ld was the standard for decades. Ian Lance Taylor's gold (2008) was faster. LLVM's lld (Rui Ueyama, 2015) and mold (Rui Ueyama, 2021) link large programs, such as a browser, in seconds instead of minutes by running in parallel. In 2006, Ulrich Drepper added a new hash table section (`DT_GNU_HASH`) with a Bloom filter in front, to speed up symbol lookup. Link-time optimisation (LTO) lets the compiler see across files at link time. Security work added position-independent executables, full RELRO and `-z now`, which some major distributions, such as Ubuntu and Fedora, now turn on by default. John Levine's book "Linkers and Loaders" (1999) and Drepper's "How to Write Shared Libraries" (2011) remain the standard references.
how: The link step has two parts: **symbol resolution** and **relocation**. Then the load step puts the result in memory.
Step 1: Compile to object files. For each source file the compiler writes machine code into sections, a symbol table, and relocation records. In `main.c` below, the call to `add` is encoded with a zero in the address field, and a relocation says: "at offset 0x14, put the address of `add`, relative to this instruction".
```bash
$ gcc -O1 -c main.c add.c
$ nm main.o
                 U add          # undefined: someone else defines it
0000000000000000 D counter      # defined here, in .data
0000000000000000 T main         # defined here, in .text
$ objdump -dr main.o
  13:  e8 00 00 00 00   call  18 <main+0x18>
          14: R_X86_64_PLT32   add-0x4
```
Step 2: Resolve symbols. The linker reads all inputs and builds a global symbol table (a hash table from name to definition). Every undefined symbol must match exactly one strong definition, or the link fails with "undefined reference" or "multiple definition". Static libraries are handled lazily: the linker opens the archive only to find members that define a symbol still undefined, and copies just those. This is why the order of libraries on the command line matters: `gcc main.o -lm` works but a library listed before the object that needs it may not. The dependency of libraries on each other forms a graph; a cycle among archives needs the group option.
Step 3: Lay out and relocate. The linker merges sections of the same kind (all `.text` together, all `.data` together), assigns each a virtual address, and then processes every relocation: it computes the final address of the target and writes it into the code. After linking, `add` has an address and the `call` instruction holds a real displacement. The ISA decides what is possible: x86-64 `call` has a 32-bit relative offset (plus or minus 2 GB), and ARM's `bl` has a 26-bit field (plus or minus 128 MB), so a linker may insert a small "veneer" or trampoline when the target is too far.
```bash
$ gcc main.o add.o -o app
$ nm app | grep -E " (main|add|counter)$"
0000000000001146 T add
0000000000004010 D counter
0000000000001129 T main
```
Step 4: The executable file. The result is an ELF file with a header, program headers that describe segments, and section headers. For the loader, only the program headers matter: typically one read-only segment (headers), one readable and executable (`.text`), one read-only (`.rodata`) and one read-write (`.data` and `.bss`). `.bss` takes no space in the file; the loader supplies zero-filled pages. If the program uses shared libraries, the file also names its interpreter (`PT_INTERP`, normally `/lib64/ld-linux-x86-64.so.2`) and lists the libraries it needs (`DT_NEEDED`).
Step 5: Load. When you run the program, the kernel's `execve` reads the program headers and maps each segment into a new address space with `mmap`: the file pages are shared with the page cache and loaded on demand by page faults, so starting a 100 MB program does not read 100 MB. If the file is a position-independent executable, the kernel picks a random base address (ASLR). If an interpreter is named, the kernel maps it too, and starts execution there, not at `main`. The dynamic linker then maps each needed library in turn (searching `RUNPATH`, `LD_LIBRARY_PATH`, the cache `/etc/ld.so.cache`, and the default directories), processes their relocations, runs their initialisers, and finally jumps to the program's entry point.
Step 6: Calls across libraries. Shared-library code must work at any address, and its code pages are read-only and shared, so it cannot hold absolute addresses. Instead, position-independent code reaches data and functions through the **GOT**, a table of pointers in a writable data page that the dynamic linker fills in. A call to `puts` goes to a small stub in the **PLT**, which jumps through the GOT slot. With *lazy binding*, the slot first points back into the PLT, which calls the resolver; the resolver looks up `puts` (through the hash table in each library), writes the real address into the GOT slot, and jumps there. Later calls go straight through. Lazy binding saves start-up work for functions never called. Some distributions (Ubuntu and Fedora, for example) now build with `-z now` (BIND_NOW), which resolves all slots at start-up and then makes the GOT read-only (full RELRO), so an attacker who finds a memory bug cannot overwrite the pointers.
```bash
$ readelf -d puts | grep -E "NEEDED|FLAGS"
 (NEEDED)  Shared library: [libc.so.6]
 (FLAGS)   BIND_NOW
$ objdump -d puts --section=.plt.sec
 1050 <puts@plt>:
   endbr64
   jmp *0x2f76(%rip)   # 3fd0 <puts@GLIBC_2.2.5>   (the GOT slot)
```
Step 7: Symbol lookup rules. The dynamic linker searches libraries in load order, and the first definition wins. This gives *interposition*: a library loaded earlier (for example through `LD_PRELOAD`) can replace `malloc` for the whole process. Symbol versioning (`GLIBC_2.34`) lets a library keep several versions of one function so old binaries keep working. Shared libraries gain from virtual memory: the code pages of `libc` exist once in RAM, mapped into hundreds of processes, while each process has private copies of the data pages once it writes to them (copy-on-write).

example: Compile two files and follow one call. File `main.c` has `int counter = 7;` and `main` returns `add(counter, 5)`. File `add.c` defines `add`. After `gcc -c`, `nm main.o` shows `U add` (undefined) and `D counter`, and `objdump -dr` shows the `call` instruction `e8 00 00 00 00` with a relocation `R_X86_64_PLT32 add-0x4` on its four address bytes. After linking, `nm app` shows `main` at 0x1129 and `add` at 0x1146. The call instruction sits at 0x113c, its address field at 0x113d, and the next instruction at 0x1141. The linker applies the rule "symbol address plus addend minus the address of the field": 0x1146 − 4 − 0x113d = 5. So the bytes become `e8 05 00 00 00`, and at run time the CPU adds 5 to the address of the next instruction (0x1141) and lands on 0x1146, which is `add`. (The commands and addresses come from a real build with gcc 13 on x86-64 Linux.) One blank became a number that depends on where both pieces ended up.
Now count the cost of sharing. A server runs 200 processes that all use `libc.so.6`, about 2 MB of code. Static linking would hold 200 copies of the used part of libc in the page cache of 200 different files, perhaps 200 × 800 KB = 160 MB. Dynamic linking holds one 2 MB copy in RAM, mapped 200 times. When a security flaw is fixed in `libc`, one package update fixes all 200; with static linking you must rebuild and redeploy every program.
Now count the start-up cost. A C++ program linking 150 shared libraries with 50,000 symbols to bind can spend tens of milliseconds in the dynamic linker before `main`: each symbol lookup is a hash search across many libraries, and each relocation touches a page. Techniques like prelinking, lazy binding, `-Bsymbolic`, hidden visibility and fewer libraries cut it. A static Go binary of 10 MB starts in a few milliseconds because it has almost nothing to resolve. For a command-line tool run thousands of times per hour, or a function that must cold start in 50 ms, this difference is visible.
Finally an image size check. A "hello" C program linked dynamically is about 16 KB, but it needs a base image that contains libc and the dynamic linker. Linked statically against musl it is tens of KB and can run in a `FROM scratch` image that contains nothing else. That is why Go and Rust services are often shipped in images below 20 MB.
intuition: A linker is a publisher that assembles chapters written separately and replaces every "see page ??" with the real page number.
The design is natural because the compiler cannot know the final address of something in another file, so it leaves a promise (a symbol and a relocation) and a later tool, which sees everything, keeps the promise. The same split repeats for shared libraries, with one more level of delay: even the linker does not know where the library will sit in memory, so the promise is kept at run time, and the PLT and GOT are the pigeonholes where each promise is stored. Each indirection is cheap, and it buys the freedom to change one part without touching the others.
mistakes: People often think the linker is part of the compiler. In fact it is a separate program that never sees source code. It works only on object files, symbol names and relocations, which is why you can link C, C++, Rust and assembly together, and why name mangling (C++) and calling conventions must agree between files.
People often think a shared library is loaded into each process's memory in full. In fact the library's code pages are mapped from the same file in the page cache and shared across all processes; only the pages a process touches are loaded, and only writable data becomes private after a write.
People often think "static" always means a fully self-contained, portable binary. In fact a binary linked statically against glibc still may need glibc's dynamic parts at run time for name lookup and locales (the `getaddrinfo` function loads NSS modules), and it may still depend on the kernel version. For a truly portable binary, link against musl, or use Go with `CGO_ENABLED=0`.
People often think dynamic linking is always slower in the steady state. In fact a call through the PLT costs one extra indirect jump, which is well predicted by the CPU and is nearly free; the real costs are at start-up and in lost cross-library inlining. LTO and static linking can win a few percent, not a factor of two.
friction: The best-known pain is dependency mismatch. "Works on my machine" often means a different version of a shared library; a binary built on a new distribution fails with `version GLIBC_2.38 not found` on an older one, because symbol versions only move forward. Containers solve it by bundling the libraries, at the price of the memory sharing and of owning the patching of every library in the image. Different programs that need different versions of the same library give "dependency hell"; Linux relies on the soname (`libfoo.so.1`) and on symbol versioning, while Nix and Flatpak avoid the problem by giving each program its own exact set.
Start-up time and security complicate the picture. Large programs with many libraries pay a bind cost at every launch, and eager binding (for security) makes it larger. The dynamic linker is also a trusted component: environment variables such as `LD_PRELOAD` and `LD_LIBRARY_PATH` change what a program loads, which is why set-user-ID programs ignore them, and why attackers who control a library path can run code. Plug-in systems face ABI stability: a change to a struct layout in a library breaks old binaries silently, and C++ makes it worse because templates and inline functions compile into the caller.
Linking at scale is a build-system cost: linking a large program with debug information can use tens of GB of memory and take minutes, which is why teams switch to lld or mold, split debug info, or use shared libraries in development and static linking in release. Link-time optimisation trades build time and memory for 5% to 15% speed in some programs. Symbol visibility is another problem: by default all global functions are exported, enlarging the symbol table and allowing accidental interposition; `-fvisibility=hidden` fixes it but needs discipline.
practice: Learn four commands: `nm` (symbols), `objdump -d` or `-dr` (code and relocations), `readelf -lSd` (segments, sections, dynamic section) and `ldd` (which libraries will be loaded; do not run it on untrusted files). When a link fails, read the exact name: "undefined reference to `foo`" means no input defines it (missing library, wrong order, or a C/C++ name mismatch, so check `extern "C"`); "multiple definition" means two strong definitions (often a function defined in a header without `inline`).
Choose the link mode deliberately. Use static linking for small tools and services you ship as a single file, and for containers where a minimal image matters (Go does this by default; Rust links its own crates statically but uses the system libc dynamically unless you target musl). Use shared libraries when many programs share a component and you need to patch it centrally. Build with PIE, full RELRO (`-Wl,-z,relro,-z,now`) and a stack protector for production; hide symbols you do not need to export.
For speed, switch to `lld` or `mold` (`-fuse-ld=mold`) for large C++ or Rust builds; check start-up with `LD_DEBUG=statistics ./app`; and measure before using `LD_BIND_NOW` or prelinking. For debugging load problems, use `LD_DEBUG=libs` to see the search path, `ldd`, and `strace -e openat` to see what is opened. When shipping binaries to other machines, build on the oldest distribution you support (or in a container with an old glibc) so the symbol versions are low.
tradeoffs: Choose static linking when you deploy to many unknown machines or minimal containers, want one file with predictable behaviour, and care about start-up time: Go services, command-line tools, sidecars. You give up shared patching (every vulnerability fix in a library means a rebuild and redeploy) and memory sharing between different programs.
Choose dynamic linking when many programs on one host use the same libraries, when the operating system vendor patches libraries centrally, or when you need plug-ins loaded at run time (`dlopen`). You pay with start-up work, the risk of version mismatch and an extra layer of environment-dependent behaviour.
Choose lazy binding when start-up time matters and the program calls only a small part of its imported functions; choose BIND_NOW with full RELRO when security matters more, since it closes the GOT-overwrite attack, at the cost of resolving everything at launch (often a few milliseconds to tens of milliseconds).
Choose link-time optimisation for release builds of performance-critical programs when you can afford longer builds and more memory; skip it in development. Choose a fast linker (lld, mold) for every developer build, since link time often dominates incremental builds.
interview: What happens between typing `./app` and the first line of `main`? || The shell calls `execve`. The kernel reads the ELF program headers, maps the segments with `mmap` into a fresh address space, picks a random base for a PIE, and maps the interpreter named by `PT_INTERP`. Control goes to `ld.so`, which maps each `DT_NEEDED` library, applies relocations, fills GOT entries (or leaves them lazy), runs constructors, and jumps to `_start`, which calls libc's start-up code and then `main`.
Explain the PLT and GOT. Why are they needed? || Shared-library code must run at any address, and its code pages are read-only and shared, so it cannot contain absolute addresses of other libraries' functions. The GOT is a table of writable pointers that the dynamic linker fills with real addresses, and the PLT is a stub that jumps through a GOT slot. With lazy binding the first call goes to the resolver, which patches the slot; later calls are one indirect jump.
Why does the order of libraries on the gcc command line matter for static libraries? || The linker processes inputs left to right and pulls a member from an archive only if it defines a symbol that is undefined at that moment. A library listed before the object that needs it is skipped, and the later reference stays undefined.
A service works in staging and fails in production with `GLIBC_2.38 not found`. Why, and what are your options? || The binary was built against a newer glibc, and symbol versions are forward-only. Options: build on the oldest supported distribution or in a container with an old glibc; link statically against musl; or ship the same base image for build and run, so build and runtime match.
Static or dynamic linking for a fleet of 500 microservices in containers? || Containers already bundle their libraries, so there is no memory sharing between images and the patching story is a rebuild either way. Static linking (or a tiny base image) gives small images, fast start and no mismatch; dynamic linking keeps the option of patching the base image's libc. For Go and Rust services, static is usually better; for C++ with many system dependencies, a pinned base image with dynamic linking is more practical.
quiz: What is a relocation? || A record in an object file that says a location must be patched with the final address of a symbol (plus an offset). The linker applies it after assigning addresses.
Why does a shared library need position-independent code? || It may be mapped at a different address in every process, and its code pages are shared read-only, so it cannot contain absolute addresses; it uses relative addressing and the GOT instead.
What does lazy binding do and what does it cost? || It leaves GOT slots unresolved until a function is first called, so unused functions cost nothing at start-up. The cost is a slower first call and a writable GOT, which is a target for attacks; full RELRO resolves everything early and makes the GOT read-only.
200 processes use a 2 MB shared library. How much RAM does the code take with dynamic linking and with static linking of the whole library? || Dynamic: about 2 MB, mapped by all processes. Static: each separate executable carries its own copy, up to 200 × 2 MB = 400 MB if every program is different (the page cache shares copies only of the same file).
When would you choose static linking for a production service? || When you want a single self-contained file for minimal container images and fast start-up, deploy to varied hosts, and can rebuild and redeploy the service whenever a dependency has a security fix.

value: When you press the power button, the computer has working hardware but nothing in RAM: the memory is empty (and not even configured yet), and the operating system is on a disk that the CPU does not yet know how to read. Booting solves this chicken-and-egg problem with a chain of small programs, each one just able to load the next, larger one. Firmware in flash memory starts the CPU and the memory and finds a bootloader; the bootloader loads the kernel and an initial RAM disk; the kernel starts its drivers, mounts the root file system and starts the first process, PID 1 (systemd on most Linux systems); and PID 1 starts everything else.
This matters to anyone who runs machines, because every cold start, every reboot after a kernel patch, every autoscaled instance and every serverless sandbox passes through it. Boot time is downtime: a server that needs 4 minutes in firmware tests before the kernel even starts costs that time at every maintenance window. A micro-VM such as Firecracker skips most of the chain and starts a Linux guest in roughly 125 ms, which is what makes per-request sandboxes possible. Boot is also the root of trust: if an attacker controls the first code that runs, nothing later can be trusted, so Secure Boot and measured boot check each stage before it runs.
The layers below explain the steps. The instruction set (ISA) defines the CPU's reset state: where it starts executing and in which mode, and how it moves from 16-bit or protected mode to 64-bit mode. Interrupts are set up early so that the kernel can handle devices and faults. File systems are what the bootloader and the kernel must read to find the kernel and the root. Processes give the final result: PID 1 is the first process, the ancestor of all others. The layers above are the Linux kernel's init code and systemd, and virtual machines, which boot virtual firmware or skip it.
terms: Firmware — the program in flash memory on the motherboard that runs first; BIOS in older machines, UEFI in modern ones.
UEFI — Unified Extensible Firmware Interface: a firmware standard with a file-based boot, drivers, and Secure Boot.
Bootloader — a small program (GRUB, systemd-boot) that loads the kernel and the initial RAM disk and passes them a command line.
initramfs — initial RAM file system: a small archive, unpacked into memory, that holds the drivers and tools needed to find and mount the real root file system.
Kernel command line — a string such as `root=UUID=... ro quiet` passed by the bootloader to tell the kernel how to find the root and how to behave.
PID 1 (init) — the first user-space process; it starts services and reaps orphaned processes. Usually systemd.
ESP — EFI System Partition: a small FAT32 partition that holds bootloaders and kernels for UEFI.
Secure Boot — a UEFI feature that runs only boot code signed by a trusted key.
Measured boot — each stage records a hash of the next stage in a TPM, so a remote party can later verify what booted.
history: Early computers loaded their first program from switches or cards. The word "bootstrap" comes from lifting yourself by your bootstraps: a few instructions that load more instructions. The IBM PC (1981) set the pattern that lasted 30 years: the CPU starts in 16-bit real mode at a fixed address near the top of the first megabyte, the ROM BIOS tests the hardware (POST), and then reads the first 512-byte sector of the boot disk into memory at 0x7C00. That sector, the Master Boot Record (MBR), holds 446 bytes of code, a table of four partitions, and the signature 0x55AA. Because 446 bytes is very small, bootloaders such as LILO (1992) and GRUB (1995) used a staged design: a tiny first stage loads a bigger second stage.
BIOS had real limits: 16-bit code, a maximum disk size of 2 TB with MBR, and no standard way to add drivers. Intel designed EFI for Itanium in the late 1990s, and in 2005 the UEFI Forum took over the specification. UEFI (version 2.0 in 2006) starts in 32- or 64-bit mode, reads files from a FAT partition, includes a driver model, and defines GPT partition tables (which allow disks beyond 2 TB). Secure Boot arrived with UEFI 2.3.1 around 2011 and became mandatory for Windows 8 hardware, which led to the `shim` loader so that Linux distributions could boot under Microsoft's keys.
On the software side, the Linux kernel gained the initramfs in the 2.6 series (from 2003) to replace the older initial RAM disk; the kernel could also start as a UEFI program directly (the EFI stub, 2012). systemd, begun by Lennart Poettering and Kay Sievers in 2010, replaced the sequential shell-script init with parallel units and dependencies; by the mid-2010s most major distributions had adopted it. On servers and phones the chain looks different: ARM systems run a ROM code, then trusted firmware stages (TF-A) and U-Boot or UEFI, and cloud micro-VMs (Firecracker, 2018) boot a kernel directly with no BIOS.
how: A boot is a relay. Each stage runs in a more capable environment than the last, and each one must find and load the next.
Step 1: Reset and firmware. When power is stable the CPU resets. Every ISA defines the reset state: on x86 the CPU starts in real mode and fetches its first instruction from the reset vector 0xFFFFFFF0, just below 4 GB, where the chipset maps the flash chip. On ARM, a small boot ROM inside the chip runs first. The firmware does the hardest early job: it initialises the memory controller (training the DRAM timing, which can take seconds on a server with a terabyte of RAM), sets up the PCIe devices, enumerates CPUs, and sets up its own interrupt tables and page tables. This is the Power-On Self-Test (POST). On servers a separate management controller (BMC) is often running before the main CPU.
Step 2: Find a boot target. With UEFI, the firmware reads a list of boot entries stored in NVRAM (for example "Linux" pointing to `\EFI\ubuntu\shimx64.efi` on the ESP), or falls back to `\EFI\BOOT\BOOTX64.EFI`. It mounts the FAT file system on the ESP (the file-system layer in action), loads that PE/COFF program into memory and runs it. With Secure Boot on, the firmware checks the signature of the program against its database of allowed keys before running it, and the shim then checks GRUB and the kernel in turn. With legacy BIOS, it loads the MBR sector instead and jumps to it.
Step 3: The bootloader. GRUB or systemd-boot reads its configuration, shows a menu if asked, then loads two files into memory: the kernel image (`vmlinuz`) and the initramfs. It builds the kernel command line and starts the kernel. Because the bootloader must read a file system before any OS driver exists, it carries its own small file-system code. On modern x86 UEFI systems the kernel can even skip the bootloader: it contains an EFI stub that makes it a valid UEFI program.
Step 4: Kernel start-up. The kernel's first code is architecture-specific. If it was entered in a simple mode, it switches the CPU into 64-bit long mode, builds its own page tables (so virtual memory is on), sets up the interrupt descriptor table and the timer, and then calls the portable start-up function (`start_kernel`). This function detects memory, initialises the scheduler, memory allocator, interrupts, and every built-in driver in a fixed order. The kernel then unpacks the initramfs into a RAM-backed file system and runs `/init` from it as the first user process.
Step 5: initramfs finds the real root. The real root file system is on a device the kernel cannot reach with built-in code alone: it may be on an NVMe disk behind a driver module, on an encrypted volume (LUKS), on LVM or RAID, or on the network (iSCSI, NFS). The initramfs holds exactly those drivers and tools. It loads the modules, asks for a passphrase if needed, assembles the volumes, mounts the real root at `/sysroot` (read-only first), and then calls `switch_root`, which replaces the RAM file system with the real one and runs the real init from it. This is why a missing driver in the initramfs gives the famous "cannot mount root" failure.
Step 6: PID 1 and user space. The init program becomes PID 1 and is never allowed to exit: if it dies, the kernel panics. systemd reads unit files, builds a dependency graph (graph theory again) from `After=`, `Requires=` and `WantedBy=`, and starts independent units in parallel until it reaches the default target (`multi-user.target` for servers, `graphical.target` for desktops). It mounts the remaining file systems from `/etc/fstab`, starts udev to create device nodes, sets the network, and starts services such as `sshd`. PID 1 also adopts orphan processes and reaps them, which is why a container that runs your program as PID 1 needs a small init (tini) to avoid zombies.
Step 7: Chain of trust. In a secured boot, each stage verifies the next one before running it: firmware verifies the shim, the shim verifies GRUB, GRUB verifies the kernel (and the kernel verifies modules). In measured boot, each stage also hashes the next stage and extends a TPM register (PCR). The final PCR values say what code actually ran. A remote server can ask the TPM to sign them ("attestation"), and a disk key can be sealed so it is released only when the PCR values match the expected ones.

example: Run `systemd-analyze` on a Linux machine and you see where time goes. A typical output on a laptop looks like this (the numbers are an example, and servers differ):
```text
$ systemd-analyze
Startup finished in 5.1s (firmware) + 1.2s (loader)
  + 2.4s (kernel) + 2.8s (initrd) + 8.3s (userspace) = 19.8s
$ systemd-analyze blame | head -3
 4.9s cloud-init.service
 2.1s NetworkManager-wait-online.service

```
Here 6.3 s of the 19.8 s passed before the kernel even started, and 8.3 s was spent by PID 1 starting services. The slowest single unit (`cloud-init`, 4.9 s) dominates user space, so the fix is to look at that unit and not at the kernel. On a big server the firmware share is much larger: a machine with 2 TB of RAM may spend 3 to 6 minutes in memory training and device tests before the bootloader appears, which is why teams prefer `kexec` (loading a new kernel directly from the running one, skipping firmware) for fast reboots in a fleet.
Now trace one failure to see the chain. After a kernel update a server drops to a prompt saying "cannot mount root" and shows `(initramfs)`. This means stages 1 to 4 worked (firmware, bootloader and kernel ran, and the initramfs started) and stage 5 failed: the initramfs could not find the root device. The usual causes are that the new initramfs was built without the storage driver, or that the `root=UUID=` on the command line no longer matches the disk. You can check by listing `ls /dev/disk/by-uuid` at the prompt and by running `lsinitramfs` on the image from a rescue system. Knowing the chain turns "the server is dead" into a small search among seven stages.
Finally a cloud example: a Firecracker micro-VM skips the firmware and the bootloader. The monitor loads the kernel at a fixed address, sets the CPU state itself, and jumps in. The kernel has virtio drivers built in, so no initramfs is needed to find a virtual disk. It reaches user space in about 125 ms (the figure stated by the Firecracker project for its reference setup), compared with 20 s or more for a physical machine. The difference is not faster hardware; it is that the stages for hardware discovery are not needed in a virtual machine whose layout is known in advance.
intuition: Boot is a relay race in which each runner can only carry the baton as far as the next, stronger runner.
The CPU on reset has no operating system, no memory it can use and no idea what a disk is. All it can do is run the first instruction at a fixed address. So the first program is tiny and lives in non-volatile memory; it only needs to wake up enough hardware to read a bigger program, which wakes up more. Each stage uses just the abilities that exist at that point, and each one hands over a better environment: the firmware brings up memory, the bootloader reads a file system, the kernel brings up virtual memory and drivers, the initramfs reaches the real root, and PID 1 brings up services. The design is forced by the chicken-and-egg order, and the only choices are how many stages and how much each one checks.
mistakes: People often think the operating system starts as soon as the machine is switched on. In fact several programs run before the kernel (the boot ROM, firmware, and the bootloader), and on servers they can take longer than the kernel and the user space together.
People often think PID 1 is just another service. In fact PID 1 is special: it is the ancestor of all processes, it adopts orphans, the kernel panics if it exits, and it ignores signals it has no handler for. A program that was not written to be init, run as PID 1 in a container, can leave zombie processes and may not respond to SIGTERM.
People often think the initramfs is a leftover that you can ignore. In fact it is what makes one kernel image work on thousands of different machines: the kernel stays generic, and the initramfs carries the drivers for this machine's disk and encryption. If it is stale or missing, the machine does not boot, even when the kernel is fine.
People often think Secure Boot protects the whole running system. In fact it checks only the early stages (firmware, loader, kernel, and signed modules). A flaw in a service or in a driver after boot is not covered, and a signed but vulnerable bootloader can be used to bypass the chain (the BootHole bug in GRUB in 2020 is an example), which is why vendors maintain revocation lists.
friction: Boot is slow and hard to debug because early failures show no output. Before the kernel has a console, you rely on beep codes, port 80 codes, a serial console or a BMC. Firmware is closed code of varying quality, differs per vendor, and is updated rarely; bugs in memory training or device initialisation cause hangs that look random. Because firmware runs with the highest privilege and persists in flash, it is a target for implants, and the update process itself is a risk (a failed flash can brick a board).
The trust chain has operational cost. Secure Boot keys and revocation lists have to be maintained; when a vulnerable bootloader is revoked, older installation media stop booting. Custom kernels and out-of-tree modules need signing, which makes development and some GPU driver installs harder. Measured boot gives strong evidence but only if someone checks the values and knows what to expect: PCR values change with every firmware or kernel update, so sealed disk keys can fail to open after a routine update.
At fleet scale, boot time and reliability interact with capacity. A rolling reboot of 10,000 servers, with 2% (200 servers) allowed down at once and 5 minutes per boot, takes 50 batches of 5 minutes, about 4 hours; halving boot time halves the window. Fast boot paths (kexec, micro-VMs, snapshot restore) are therefore a major research area. Last, the boot process grew by accretion: BIOS compatibility modes, PCI option ROMs, and the many ways of defining the root device make a large, fragile surface that few engineers know end to end.
practice: Learn to read the boot stages in the logs. Use `systemd-analyze` and `systemd-analyze blame` for timing, `systemd-analyze critical-chain` for the chain of dependent units, `journalctl -b` for logs of this boot and `journalctl -b -1` for the previous one, and `dmesg` for kernel messages. For early failures, enable a serial console (`console=ttyS0,115200`) and use the BMC's serial-over-LAN, and remove `quiet` from the kernel command line to see messages.
Keep the chain consistent after changes. After a kernel update or a change of storage or encryption, make sure the initramfs is rebuilt (`dracut`, `update-initramfs`) and the bootloader configuration is regenerated; keep the previous kernel as a fallback entry. Use UUIDs or labels, not `/dev/sdX` names, in `fstab` and `root=`, because device names can change between boots. Mount non-essential file systems with `nofail`, so one missing disk does not drop a server into emergency mode.
In clouds and containers, shorten the chain deliberately: use minimal images and a small number of services, build the drivers you need into the kernel for a micro-VM, and use `kexec` or live patching for fleet updates when the risk allows it. For containers, run a real init (`tini`, `--init` in Docker) as PID 1. For security, enable Secure Boot and measured boot on bare metal fleets, store disk keys in the TPM with the right PCR policy, and test your update procedure for PCR changes before a fleet-wide roll-out.
tradeoffs: Choose UEFI with GPT for any new machine: it supports large disks, fast boot, Secure Boot and standard tools. Choose legacy BIOS mode only for very old operating systems and hardware that cannot do UEFI, and accept the 2 TB MBR limit and the lack of Secure Boot.
Choose GRUB when you need a flexible menu, many operating systems or complex disk layouts (LVM, encrypted /boot); choose systemd-boot or a unified kernel image (kernel, initramfs and command line signed together as one UEFI file) when you want a simple, auditable chain with Secure Boot. You trade features for a smaller attack surface.
Choose a generic initramfs with many drivers when one image must boot a variety of hardware; choose a host-specific, small initramfs for fixed fleets, which boots faster and is smaller but fails if hardware changes. Choose to build critical drivers into the kernel for micro-VMs and appliances, where you know the hardware.
Choose a full reboot with firmware for kernel upgrades that need a fresh hardware state (firmware or microcode updates); choose kexec or live patching when you must keep downtime to seconds and accept that firmware is not re-run, which hides some device-reset problems.

@@ sidechannel
value: A side-channel attack steals a secret not from the program's output but from a physical or timing effect of running the program. The program may be mathematically correct and bug-free: a password check returns only "yes" or "no". Yet if the check takes 2 microseconds longer when the first letter is right, the attacker learns the password one letter at a time. The channels can be time, cache state, power draw, electromagnetic emission or sound. The common point is that computation leaves marks in shared hardware state, and someone else can read those marks.
Two families matter for software engineers. The first is **timing and cache channels**: code whose run time or memory-access pattern depends on a secret, such as a table lookup indexed by a key byte. The second is **speculative execution attacks**, shown in January 2018 as Spectre and Meltdown. Modern CPUs guess the outcome of branches and run ahead; when the guess is wrong the results are thrown away, but the cache lines that the wrong path touched stay in the cache. An attacker can steer the wrong path to read a secret and then measure the cache to recover it. This broke the isolation between processes, virtual machines and browser tabs, which many security designs had treated as solid.
The reason this belongs to the foundations layer is that the leak is created by the performance features of the lower layers: branch prediction, out-of-order execution, cache lines and the memory hierarchy are all designed to make the average case fast, and each one makes time depend on data. Probability and statistics enter on the attacker's side: one measurement is noisy, but thousands of repeated measurements are averaged until a difference of a few nanoseconds is visible. The layers above feel it as exploit mitigations (retpolines, site isolation), as the isolation limits of multi-tenant clouds and virtual machines, as browser design (coarse timers), and as the reason trusted execution environments cannot promise secrecy against a hostile host.
terms: Side channel — an information path that is not part of the program's intended interface, such as time, power, or cache state.
Timing attack — measuring how long an operation takes to infer a secret that influences its duration.
Constant-time code — code whose run time and memory accesses do not depend on secret values.
Cache side channel — learning which memory addresses a victim touched by measuring which cache lines are present (fast) or absent (slow).
Flush+Reload / Prime+Probe — two cache attack methods: evict or flush known lines, let the victim run, then time the reloads; or fill a cache set and see which lines the victim evicted.
Speculative execution — running instructions ahead of a branch or load whose outcome is not yet known, and discarding the results if the guess was wrong.
Transient execution — instructions that run speculatively and are later squashed; their architectural effects vanish but their microarchitectural effects (cache lines) remain.
Gadget — a piece of victim code that an attacker can steer to read and leak a secret during speculation.
Mitigation — a defence such as retpoline, index masking, a fence instruction, page-table isolation (KPTI) or site isolation.
history: Paul Kocher's 1996 paper "Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems" showed that the time of a modular exponentiation depends on the bits of the private key, and that an attacker who measures many operations can recover the key. In 1999 Kocher, Jaffe and Jun added power analysis on smart cards, where the current drawn by the chip shows each bit of the key. For a decade side channels were a smart-card and cryptography problem.
Cache attacks brought them to ordinary computers. Daniel Bernstein (2005) showed that the timing of AES with table lookups leaks the key over a network. Osvik, Shamir and Tromer (2006) described Prime+Probe, which recovers AES keys from another process on the same CPU. Yarom and Falkner (2014) introduced Flush+Reload, which is fast and precise when processes share memory pages. In 2015 and 2016, researchers showed cache attacks across virtual machines in public clouds. The usual advice was to make cryptographic code constant-time, and libraries slowly moved to AES-NI hardware instructions and constant-time arithmetic.
On 3 January 2018 the problem became general. Jann Horn at Google Project Zero, and independently Paul Kocher with others and a Graz University of Technology team (Lipp, Schwarz, Gruss and others), disclosed Meltdown (CVE-2017-5754) and Spectre (CVE-2017-5753 and CVE-2017-5715). Meltdown let user code read kernel memory on many Intel CPUs, by using the delay between a load and its permission check. Spectre attacked the predictors and worked on Intel, AMD and ARM. The fixes were large: kernel page-table isolation (KPTI), retpolines (a compiler technique by Paul Turner of Google), microcode updates, and changes to browsers. Many variants followed: L1TF/Foreshadow (2018), MDS/ZombieLoad (2019), Retbleed (2022), Downfall (2023) and others. The field's lesson is that the problem is structural, not a single bug.
how: A side channel needs three things: a secret-dependent effect, a shared resource that holds the effect, and a way to measure it. The pieces below show how each part works.
Step 1: Timing depends on data. Consider a naive comparison of a secret token with a guess: the loop stops at the first byte that differs. A guess whose first byte is right takes one more iteration than a guess whose first byte is wrong. The difference is a few nanoseconds, but it is systematic. The attacker sends guesses for each value of the first byte, finds the slowest, fixes it, and moves on to the second byte. This turns a search of \( 256^n \) guesses into \( 256 \times n \). Noise (network jitter of microseconds) hides a signal of nanoseconds in a single measurement, but statistics fix this: averaging N samples reduces the noise by \( \sqrt{N} \), so to see a difference \( \delta \) in noise of standard deviation \( \sigma \) the attacker needs about \( N \approx (z\sigma/\delta)^2 \) samples. With \( \sigma = 20\ \mu s \), \( \delta = 100\ ns \) and z = 3, that is \( (3 \times 200)^2 = 360{,}000 \) requests, which is feasible. Researchers (Crosby, Wallach and Riedi, 2009) showed that differences of 100 ns on a local network, and 15 to 100 microseconds over the internet, can be measured this way.
Step 2: Caches hold the trace. The memory hierarchy exists because RAM is far slower than the CPU: an L1 hit takes about 1 ns (4 cycles), an L3 hit about 10 to 15 ns, a DRAM access 80 to 100 ns. That gap, a factor of 100, is easy to measure from user space with a cycle counter. Data moves in cache lines of 64 bytes. If a victim reads `table[secret_byte]`, the line that holds that entry ends up in the cache. An attacker sharing the cache then learns which line was used. In Flush+Reload the attacker flushes a shared line (`clflush`), waits, and reloads it: a fast reload means the victim touched it. In Prime+Probe, which does not need shared memory, the attacker fills a cache set with its own lines and later checks which of them were evicted.
Step 3: Speculation makes the victim run unwanted code. To keep its pipeline full, the CPU predicts every branch and runs ahead; out-of-order execution lets later instructions start before earlier ones are finished. If the prediction was wrong, the CPU rolls back the registers and memory writes, so the program result is unaffected. But the cache is not rolled back. This is the gap Spectre uses. The attacker trains the branch predictor with many in-bounds inputs, and then supplies an out-of-bounds one. The branch is predicted "taken", and the CPU speculatively performs the secret-dependent loads before it discovers the check failed.
```c
/* Spectre variant 1: bounds check bypass */
if (x < array1_size) {              /* attacker trains: x in bounds  */
    y = array2[array1[x] * 512];    /* then x out of bounds: reads a  */
}                                   /* secret byte, touches a line    */
```
For the malicious x, `array1[x]` is a secret byte S somewhere in the victim's memory. The second load touches `array2[S * 512]`, which pulls one of 256 possible lines into the cache. The branch result arrives, the CPU squashes the work, and the program continues normally. The attacker then times a reload of each of the 256 lines of `array2`: the one that is fast reveals S. The stride 512 keeps each possible value on its own cache line and away from the hardware prefetcher. Repeating this leaks the memory at a rate of kilobytes per second.
Step 4: Variants. Spectre variant 2 poisons the indirect-branch predictor so that a victim's indirect jump speculatively goes to an attacker-chosen gadget, even across processes or into the kernel. Meltdown exploits the fact that on some CPUs the data of a load is delivered to dependent instructions before the permission check completes, so a user program can read kernel memory transiently. Later attacks (MDS) read from internal buffers (line-fill buffers, store buffers) that are shared between threads. All use the same recipe: transient access to a secret, then a cache or buffer state that carries it out.
Step 5: Defences work on each part. Against timing: write constant-time code, with no branches or memory indexes that depend on secrets, and use hardware instructions (AES-NI) and constant-time comparison functions. Against cache channels: partition the cache (Intel CAT), avoid sharing cores between tenants, and do not share memory pages between mutually distrusting parties. Against speculation: stop the speculative load (an `lfence` after the bounds check, or masking the index with `array_index_nospec`), avoid indirect branches (retpolines replace them with a construct that traps speculation in a harmless loop), flush predictors on context switches (IBPB), isolate the kernel's page tables from user mode (KPTI, at a cost of some percent on system-call-heavy workloads), and use site isolation in browsers so that pages from different origins live in different processes. Browsers also reduce the resolution of `performance.now()` and require cross-origin isolation before enabling high-resolution timers and `SharedArrayBuffer`.
Step 6: Why probability matters. A real channel is noisy: cache hits and misses vary with other activity, so the attacker repeats each trial and takes a vote or an average. This is also why adding random delays is a weak defence: noise that is 10 times larger than the signal only costs the attacker 100 times more samples, because the needed number of samples grows with the square of the noise-to-signal ratio. The signal is still there.

example: Take a password check that compares a 4-digit PIN with `strcmp` (stops at the first difference). Each correct leading digit adds about 1 ns of loop time. On a local call with measurement noise of 5 ns standard deviation, a single timing is useless, but repeating each guess 10,000 times reduces the noise of the average to 5 / √10,000 = 0.05 ns, so the 1 ns difference is clearly visible (20 standard deviations). Try digits 0 to 9 for the first position, take the slowest, and move on. The cost is 10 digits × 4 positions × 10,000 repeats = 400,000 checks, compared with 10,000 blind guesses for all PINs without the leak. For a 4-digit PIN, brute force is already cheap, but for a 32-byte random token the gap is between 256 × 32 × 1,000 = 8 million trials and \( 2^{256} \) guesses, the difference between broken and secure.
Now the Spectre numbers. A reload of one cache line costs roughly 250 cycles for a miss and 40 for a hit on a typical x86 server. To recover one byte the attacker times 256 lines: about 256 × 250 cycles = 64,000 cycles, roughly 20 microseconds at 3 GHz, and repeats the whole attack a few tens of times to make the signal clean. That is about 1 ms per byte, or around a kilobyte per second. Reading a 32-byte AES key then takes under a tenth of a second. The speed is low, but the memory attacked is small and valuable: keys, session cookies and tokens.
Finally, the cost of defences. Kernel page-table isolation adds a page-table switch to every system call and interrupt. Reported slowdowns ranged from near zero for compute-heavy jobs to several percent, and sometimes more, for I/O-heavy servers with many system calls, and newer CPUs with hardware fixes pay less. The same mitigation can therefore cost 0% on one fleet and 15% on another, so measure on your own workload.
intuition: A safe-cracker listens to the clicks: the safe never says the code, but every wheel that falls into place makes a sound.
The principle is that an implementation is a physical process, and physical processes have costs that depend on what they compute. Programs are written and verified at the level of their input and output, but security depends on everything an observer can see. Optimisations make this worse: speed-ups work by making the common case faster, and the common case is data-dependent. A cache is faster for data used recently; a predictor is faster for patterns seen before. Each of them stores a trace of the past, and a trace is information. Sharing hardware between parties that do not trust each other turns every optimisation into a possible channel.
mistakes: People often think a side channel needs a bug in the victim's code. In fact Spectre works on correct code that follows the language rules; the defect is in the contract between hardware and software. A program can be memory-safe and formally verified at the source level and still leak through the cache.
People often think you need to run on the same machine to attack. In fact remote timing attacks work over networks, and JavaScript in a web page can run Spectre-style code in a browser. Co-tenant attacks need the same physical core or cache, which is why cloud providers care about placement; but network timing needs only averaging.
People often think adding random delays defends against timing attacks. In fact the signal stays and only more samples are needed: the attacker averages over N measurements, so noise of 10 times the signal costs 100 times the samples. The reliable defence is to remove the dependency on secrets, with constant-time code.
People often think the Spectre problem was solved by the 2018 patches. In fact each patch covers one variant, and new variants have appeared every year; software mitigations for variant 1 are applied case by case to code that handles secrets, and cannot be proved complete. The design response is isolation: put secrets in a different process or core than untrusted code.
friction: There is no complete fix for speculative execution short of removing it, and that would cost a large part of CPU performance. Mitigations are partial, specific to a vendor and a generation, and they cost performance in places that vary with the workload. Each new CPU feature (new buffers, predictors, prefetchers) may open a new channel, and the hardware design is closed, so researchers find the channels by experiment. The attack surface also includes simultaneous multithreading: two threads on a core share the L1 cache, predictors and buffers, so some providers disable hyperthreading for untrusted tenants, at a cost of up to 30% of the throughput.
For service builders, the isolation boundary is the hard part. Multi-tenant clouds must assume a hostile co-tenant on the same machine, which pushes toward dedicated cores or hosts, and browsers have paid a large cost in memory for site isolation (one process per origin). Trusted execution environments (SGX, SEV, TDX) promise confidentiality against the host operator, yet repeated side-channel attacks have recovered secrets from enclaves because the host controls the shared resources.
practice: Treat any code that handles secrets as security-critical. Never compare secrets with `==` or `memcmp`; use the constant-time function of your platform (`hmac.compare_digest` in Python, `crypto.timingSafeEqual` in Node, `subtle.ConstantTimeCompare` in Go, `MessageDigest.isEqual` in Java, `CRYPTO_memcmp` in OpenSSL). Use vetted cryptographic libraries (libsodium, BoringSSL, OpenSSL) and AES-GCM or ChaCha20-Poly1305, and do not implement your own big-number or table-lookup code.
Keep your platform patched: kernel and microcode updates, hypervisor and browser updates. Check the state with `lscpu` or `cat /sys/devices/system/cpu/vulnerabilities/*`, which lists the active mitigations for each known issue. Do not disable mitigations (`mitigations=off`) on machines that run untrusted code. In the cloud, choose dedicated hosts or isolated instance types for the most sensitive workloads, and avoid running untrusted code and secrets in the same process: use separate processes or machines, because a process boundary is a much stronger defence than any in-process check.
tradeoffs: Choose strong isolation (separate processes, VMs or machines, and no hyperthread sharing) when you run mutually untrusted code and hold valuable secrets, as in a public cloud or a browser; you pay with memory, lower utilisation and higher cost. Choose cheaper sharing with software mitigations when all code on the host is yours and trusted.
Choose to keep speculation mitigations on in production by default; the cost is usually 0% to 15%, depending on the workload and the CPU generation. Choose to disable a given mitigation only on isolated, single-tenant batch machines that run only your own code, and only after measuring that the gain is large; you accept the risk that a later bug lets untrusted input reach that machine.
Choose constant-time algorithms (ChaCha20, AES-NI, X25519) over table-based implementations even when the latter are a bit faster. Choose noise and rate limiting only as an additional layer, not as the main defence, because averaging defeats them.

How do retpolines and KPTI work, and what do they cost? || KPTI removes kernel mappings from user page tables, so a speculative user-mode load cannot reach kernel data (Meltdown); it costs a page-table switch per entry and exit, with larger cost for syscall-heavy workloads. Your company runs customers' code in a multi-tenant service. What isolation do you choose after Spectre? || Treat the process and VM boundary as the real boundary. value: String matching asks a simple question: where does a short pattern P (length m) occur in a long text T (length n)? The obvious method tries every start position and compares character by character. It costs up to \( O(nm) \) comparisons, and on a repetitive input such as searching for `aaaa…ab` in `aaaa…a` it really does take that long. Searching a 1 GB log for a 100-byte string would then need up to 10¹¹ comparisons. The algorithms in this topic reach \( O(n + m) \), or less, by never repeating work: they use what a failed comparison has already told them.
Two ideas do most of the work. The **KMP** idea (Knuth, Morris, Pratt) precomputes from the pattern alone how far it can slide after a mismatch, so the text pointer never moves backwards. The **rolling hash** idea (Rabin and Karp) gives each window of the text a number that can be updated in constant time when the window moves one character, so comparing the window with the pattern costs one integer comparison. Rolling hashes then turned out to be useful far beyond searching: they find matching blocks between two versions of a file (rsync), and they cut a file into pieces at content-defined boundaries so that identical data deduplicates even after an insertion (backup tools, Git-like object stores, storage systems).
For the layers above, this is the machinery behind `grep`, text editors, intrusion detection, the delta compression in Git pack files, diff and merge in version control, phrase queries in search engines, and deduplicating backups. The layers below supply the theory: hashing (L3) shows how to make a collision-resistant fingerprint, finite automata explain KMP as a machine that has one state per matched prefix length, number theory (modular arithmetic and primes) makes the rolling hash both fast and safe from collisions, formal languages say that a pattern is a simple regular language, and dynamic programming gives the edit distance for approximate matching.
terms: Pattern and text — the short string to find (length m) and the long string to search (length n).
Border — a proper prefix of a string that is also a suffix of it; "abab" has the border "ab".
Failure function (prefix function) — for each prefix of the pattern, the length of its longest border; it tells KMP where to continue after a mismatch.
Rolling hash — a hash of a sliding window that can be updated in O(1) when the window moves by one character.
Polynomial hash — a hash that treats the string as the digits of a number in base B, modulo a large prime M.
Fingerprint — a short value that identifies a string with a very small chance of an accidental match.
Content-defined chunking (CDC) — cutting a stream into chunks where a rolling hash of the last bytes meets a condition, so cut points depend on content and not on position.
Edit distance (Levenshtein) — the minimum number of insertions, deletions and substitutions that turn one string into another.
Aho–Corasick automaton — a trie with failure links that finds many patterns in one pass over the text.
history: The first efficient search came from theory. In 1970 James Morris and Vaughan Pratt, and independently Donald Knuth working from a theorem of Stephen Cook about two-way pushdown automata, found a way to search in linear time. The three published together as "Fast Pattern Matching in Strings" in 1977. In the same year Robert Boyer and J Strother Moore published a method that compares the pattern from its end and can skip several characters at a time; on ordinary text it often looks at fewer than n characters, and for decades it was the basis of fast `grep`. Alfred Aho and Margaret Corasick (1975) built the multi-pattern automaton used by `fgrep` and by virus and intrusion scanners.
Richard Karp and Michael Rabin published their randomised algorithm in 1987. Its important idea is to compare fingerprints instead of strings, and it works naturally for many patterns of the same length and for two-dimensional matching. Later work added constant-space methods (Galil and Seiferas, 1981; the Two-Way algorithm of Crochemore and Perrin, 1991, which is used in several C libraries) and index-based search with suffix arrays and suffix trees.
For approximate matching, Vladimir Levenshtein defined the edit distance in 1965, and Wagner and Fischer (1974) gave the dynamic program that computes it in \( O(nm) \). Eugene Myers (1986) found an \( O(ND) \) algorithm for the differences between two files, where D is the number of differences; it is the default in `diff` and Git.
The rolling-hash idea moved into systems in the late 1990s. Andrew Tridgell and Paul Mackerras described rsync in 1996, using a cheap rolling checksum to find which blocks of an old file already exist in a new one. The Low-Bandwidth Network File System (Muthitacharoen, Chen and Mazières, SOSP 2001) used Rabin fingerprints to cut files at content-defined boundaries. Backup tools (restic, borg), deduplicating storage and sync services followed, with faster hashes such as the Gear hash and FastCDC (Xia et al., 2016).
how: There are three levels: exact search without repeated work, hashing for comparison, and edit distance for approximate matches.
Step 1: Why the naive method repeats work. Suppose you match `ababaca` against the text and fail at the sixth character after seeing `ababa`. The naive method restarts one position after the start of the match. But you already know the last characters of the text are `ababa`, and you know that the pattern starts with `aba`. So you can resume with three characters already matched, without looking at them again. KMP computes this fact once, from the pattern alone.
Step 2: The failure function. For each prefix of P, find the length of its longest proper border, that is, the longest prefix that is also a suffix. For `ababaca` the values are 0, 0, 1, 2, 3, 0, 1. The table is built by the same matching idea applied to the pattern against itself, in \( O(m) \) total time: a pointer k holds the current border length; on a mismatch it falls back to the failure value of k − 1, on a match it grows by 1. Finite automata give the picture: KMP is a machine with states 0 … m (the number of characters matched), and the failure function is the set of "go back" edges. A full automaton would have one edge per alphabet symbol per state; KMP stores only the failure edge and computes the rest on demand.
```python
def failure(p):
    f, k = [0] * len(p), 0
    for i in range(1, len(p)):
        while k and p[i] != p[k]:
            k = f[k - 1]          # fall back to a shorter border
        if p[i] == p[k]:
            k += 1
        f[i] = k
    return f

def kmp_search(t, p):
    f, k, hits = failure(p), 0, []
    for i, c in enumerate(t):
        while k and c != p[k]:
            k = f[k - 1]
        if c == p[k]:
            k += 1
        if k == len(p):           # full match ending at i
            hits.append(i - k + 1)
            k = f[k - 1]
    return hits
```
Step 3: Why KMP is linear. The text pointer i only moves forward. The matched length k grows by at most 1 per character and each fall-back reduces it, so the total number of fall-backs is at most n. The search takes at most 2n character comparisons, and the table at most 2m. The worst case is as good as the best case: nothing depends on how the text looks.
Step 4: Rolling hash (Rabin–Karp). Treat a string \( s_0 \dots s_{m-1} \) as a number in base B, modulo a large prime M:
\[ H(s) = \left( \sum_{i=0}^{m-1} s_i \, B^{m-1-i} \right) \bmod M \]
Moving the window one character to the right removes the first character and appends a new one, and the new hash is computed in constant time:
\[ H' = \big( (H - s_0 B^{m-1}) \cdot B + s_m \big) \bmod M \]
Slide over the text, compare each window's hash with the hash of P, and when equal, verify the actual characters to rule out a collision. The expected cost is \( O(n + m) \). Number theory makes this safe: if M is a prime near \( 2^{61} \) and B is chosen at random, two different strings of length m collide with probability at most about \( m/M \). For n = 10⁹ windows and m = 1,000 the expected number of false matches is about \( 10^9 \times 10^3 / 2.3 \times 10^{18} \approx 4 \times 10^{-7} \), and verification removes even those. The method's strength is that it works for many patterns at once (put all pattern hashes in a hash table) and in two dimensions.
Step 5: Content-defined chunking. To deduplicate files, you cut them into chunks and store each distinct chunk once. Fixed-size chunks fail: inserting one byte at the start shifts every later chunk and nothing matches. Instead, slide a rolling hash over the last 48 bytes, and declare a cut whenever the low 13 bits of the hash are zero. The chance of this at a given byte is \( 2^{-13} \), so chunks are 8 KB on average. A cut depends only on the last 48 bytes, so after an insertion the cut points re-synchronise right after the change, and all later chunks are identical to the old ones. Systems add a minimum and a maximum chunk size (for example 2 KB and 64 KB) to avoid tiny or huge chunks. Each chunk is then named by a strong hash (SHA-256) and stored once.
Step 6: rsync. The receiver has an old file and splits it into fixed blocks (say 10 KB). For each block it sends a weak rolling checksum and a strong hash. The sender slides a window over the new file one byte at a time, updating the weak checksum in O(1), and looks each value up in a hash table of the receiver's blocks. When the weak value matches, it checks the strong hash. Matching blocks are sent as references; the bytes in between are sent as literal data. The transfer is proportional to the changes, not to the file size.
Step 7: Approximate matching. When the text may contain typing errors, the question becomes edit distance. Let \( d[i][j] \) be the distance between the first i characters of A and the first j of B:
\[ d[i][j] = \min\big( d[i-1][j] + 1,\; d[i][j-1] + 1,\; d[i-1][j-1] + [A_i \ne B_j] \big) \]
The table has (m + 1)(n + 1) cells and takes \( O(mn) \) time; this is the dynamic-programming pattern: the best solution for a larger problem is built from the best solutions of smaller prefixes. Diff uses a variant on lines: the longest common subsequence of two files gives the unchanged lines, and the rest are the edits. Myers's algorithm finds it in \( O(ND) \), which is fast when the files are similar.

example: Search for `ababaca` in `ababababaca`, using the failure table [0, 0, 1, 2, 3, 0, 1]. The matched length k starts at 0. Reading a, b, a, b, a gives k = 5. The next text character is b, but the pattern wants `c` at position 5: mismatch, so k falls back to the failure value of the previous position, f[4] = 3. Then text a gives k = 5; text b mismatches again (the pattern wants c), so k = 3 and then 4; text a gives 5; text c matches, k = 6; text a gives k = 7, which is the full pattern length. The match ends at text position 10 and starts at 4. The text pointer went from 0 to 10 exactly once, with 13 character comparisons for an 11-character text; naive search would have restarted from every position.
Now the rolling hash with small numbers. The text is the digits 2 3 1 4 1 5 2, the pattern is 415, the base is 10 and the modulus is 13. The pattern hash is 415 mod 13 = 12 (13 × 31 = 403). The first window 231 has hash 231 mod 13 = 10. To move to the window 314 without re-reading three digits: remove the first digit (2 × 100 mod 13 = 2 × 9 = 18 mod 13 = 5), so 10 − 5 = 5; multiply by the base: 50; add the new digit 4: 54; mod 13 gives 54 − 52 = 2. Indeed 314 mod 13 = 2 (13 × 24 = 312). The next windows give 141 → 11, then 415 → 12, which equals the pattern hash; we compare the characters and confirm a match. One window (152) would have a hash of 9. Each step costs a few arithmetic operations, whatever the pattern length.
For edit distance, `kitten` to `sitting` needs 3 operations: substitute k with s, substitute e with i, insert g at the end; the table has 7 × 8 = 56 cells to compute.
intuition: When a search fails, the part that matched is not wasted: it is a clue to where the next match can start.
KMP says this exactly: the text you just read is also information about the pattern's own structure, so the pattern slides by the amount its borders allow. Rabin–Karp takes another view: comparing strings of length m costs m, but comparing numbers costs 1. If you can turn a window into a number that changes in constant time as the window slides, you pay for the comparison once per position. A small chance of a false alarm is acceptable, because a match can always be checked. Content-defined chunking follows from the same property: a rolling hash that looks only at nearby bytes gives cut points that depend on content, so the same content is cut in the same places.
mistakes: People often think the naive search is fine because real text rarely repeats. In fact it is usually fast on natural text, but its worst case is \( O(nm) \), and inputs with long repeated runs (DNA, logs with padded fields, binary data, adversarial input) can make it very slow. Library functions therefore use algorithms like Two-Way or hash-based filters with a guaranteed bound.
People often think a hash match means a string match. In fact equal hashes only show that the strings may be equal. Rabin–Karp compares the characters after a hash hit. A hash of a small modulus or a fixed base can be attacked: an adversary who knows the base and modulus can build many different strings with the same hash and make the search quadratic, so use a large modulus and a random base.
People often think content-defined chunking finds all duplicates. In fact it finds duplicate chunks only when the cut points agree, and a change in the middle of a chunk makes that whole chunk new. Smaller chunks find more duplicates but cost more metadata and index memory; the average chunk size is a trade-off.
friction: Exact matching is mostly solved, and the pain is elsewhere. Real text has encodings: the same character can be one or several code points, case folding depends on the language, and a byte-level search for "é" can miss the decomposed form. Regular expressions add features such as backreferences that make matching NP-hard in the worst case, and a backtracking regex engine can take exponential time on a crafted input (a "ReDoS" attack); engines based on automata, like RE2, guarantee linear time but give up some features.
Hashing brings its own failure modes. A weak or predictable hash can be attacked; polynomial hashes with a weak modulus (such as \( 2^{64} \), the natural overflow) have known collision constructions. For content-defined chunking, the data itself can be adversarial or low-entropy: long runs of zeros never trigger the cut condition, so the maximum chunk size forces cuts, and the deduplication of such data stays weak. Dedup also has privacy risks: if a service shares chunks between users, the response time or the upload size can reveal that someone else already stored a file.
practice: Use the language's library for exact search; it is already tuned (`memmem`, `str.find`, Rust's `memchr` crate, Java's `String.indexOf` with intrinsics). Reach for your own KMP or rolling hash only when you need something the library does not give: searching a stream with bounded memory, many patterns (Aho–Corasick, or RE2/Hyperscan for regex sets), or custom matching rules.
For many fixed patterns, use Aho–Corasick; for regular expressions on untrusted input, use a linear-time engine (RE2, Rust `regex`, Go `regexp`) and avoid backtracking engines. For a polynomial rolling hash, use a modulus near \( 2^{61} - 1 \) or two moduli, choose the base at random at start-up, and always verify a hit. For fuzzy matching, use a library for edit distance (`rapidfuzz`, `python-Levenshtein`) and filter candidates first, for example with n-gram indexes.
tradeoffs: Choose the library's built-in search for single exact patterns: it is tuned with SIMD and has no maintenance cost. Choose Aho–Corasick when you have hundreds or thousands of patterns and a stream to scan once; you pay with memory for the automaton (tens of bytes per state), but the scan time does not depend on the number of patterns. Choose Rabin–Karp-style hashing when patterns have equal length or when you need windows of hashes for chunking and similarity; accept the small chance of collision and the verification step.
Choose an index (inverted index, suffix array, FM-index) when you search the same large text many times: it costs several times the text size in memory, and each query then takes about \( O(m) \) time. Choose a scan when the text changes constantly or is searched once.
Choose content-defined chunking when data is edited by insertion and deletion (documents, VM images, backups), and fixed-size blocks when data changes in place (database pages, disk blocks), where fixed blocks are simpler and faster. Choose smaller chunks for more savings, larger chunks for less metadata and faster restore.
interview: Explain how KMP avoids re-reading text. What is the failure function? || For each prefix of the pattern, it stores the length of the longest proper prefix that is also a suffix. After a mismatch with k characters matched, the pattern moves so that this border lines up with the text just read, and matching resumes from the border length. Because k only grows by one per text character and each fall-back shrinks it, the total work is at most 2n comparisons.
How does a rolling hash update in O(1), and what is the risk? || Subtract the outgoing character times \( B^{m-1} \), multiply by the base B, and add the incoming character, all modulo a prime M. The risk is collisions: different windows with the same hash. Verify each hit, use a large prime and a random base so that an adversary cannot predict collisions.
Design a deduplicating backup system. How do you cut files into chunks, and why not use fixed blocks? || Use content-defined chunking: a rolling hash over the last 48 or so bytes, with a cut when the low 13 bits are zero, giving 8 KB average chunks, with minimum and maximum limits. Name chunks by SHA-256 and keep an index from hash to location. Fixed blocks fail when an insertion shifts all later bytes; content-defined cuts re-synchronise after the change, so only the changed chunks are stored again.
How does rsync transfer only the changes between two versions of a file when the receiver does not have the new file? || The receiver sends a weak rolling checksum and a strong hash for each fixed block of its old file. The sender slides a window over the new file one byte at a time with the rolling checksum, finds blocks that match at any offset, confirms them with the strong hash, and sends references for matching blocks and literal bytes for the rest.
A regex on user input takes minutes on one specially built string. What happened and what do you do? || A backtracking engine took exponential time on nested or ambiguous repetition (ReDoS). Use a linear-time automaton engine (RE2, Go regexp, Rust regex), set a timeout, limit input length, or rewrite the pattern to remove ambiguity.
quiz: What is a border of a string, and why does KMP need it? || A border is a proper prefix that is also a suffix. After a mismatch, the matched text suffix equals a pattern prefix, and the longest border tells how many characters are still matched after the shift.
Why can KMP run in at most about 2n comparisons? || The text pointer never moves back; the matched length grows by 1 per character, and each fall-back decreases it, so the number of fall-backs cannot exceed the number of increments.
With base 10 and modulus 13, window 231 has hash 10. What is the hash of the next window 314 by the rolling update? || (10 − 2 × 100 mod 13) × 10 + 4 = (10 − 5) × 10 + 4 = 54, and 54 mod 13 = 2. This equals 314 mod 13.
A cut is made when the low 13 bits of a rolling hash are zero. What is the average chunk size? || The chance per byte is \( 2^{-13} \), so the average distance between cuts is \( 2^{13} \) = 8,192 bytes, plus the effect of the minimum and maximum limits.
When would you choose an index over a scan for string search? || When the same large text is searched many times, because the one-time build cost is repaid by queries that take O(m) or O(m log n) instead of O(n). A scan is better for text that changes constantly or is searched once.

@@ binpacking
value: Bin packing is the problem of putting items of different sizes into the fewest containers of fixed capacity. A shipping company loads boxes into trucks. A cluster scheduler places containers on machines: each machine is a bin with 64 CPUs and 256 GB of memory, each container is an item with its own demand. The fewer machines are needed, the less hardware you buy, power and cool. In a large fleet a few percent of better packing is worth many millions of dollars a year, which is why this old puzzle sits behind Borg, Kubernetes, YARN and the autoscalers of every cloud.
The problem is NP-hard, so no known algorithm is both fast and always optimal on large inputs. The practical answer is simple heuristics with proven guarantees: sort the items from large to small and put each into the first bin where it fits (first-fit decreasing), which never uses more than about 22% more bins than the optimum. Real schedulers face a harder version: items have several dimensions (CPU, memory, disk, network, GPU), they arrive one at a time and cannot be reordered, and the rules add constraints (affinity, anti-affinity, zones). They work by filtering out the machines that cannot hold the item and then scoring the rest, within milliseconds.
The layers below explain why the heuristics look as they do. The theory of P vs NP says exact optimum is out of reach in general, so greedy methods are used; greedy and divide-and-conquer thinking gives the "largest first" rule and its analysis; combinatorics counts the number of ways to arrange items and gives lower bounds; and linear programming gives a relaxation, a fractional version that gives a bound on the optimum and a base for the best known methods. The layers above are the schedulers: container orchestration, Kubernetes (scoring plugins such as `MostAllocated`) and Hadoop YARN (placement of containers on NodeManagers).
terms: Bin — a container with a fixed capacity (one machine, one disk, one truck).
Item — a thing to place, with a size, or a vector of sizes in several resources.
Online vs offline — online: items arrive one by one and must be placed at once; offline: the full list is known and can be sorted first.
First-fit decreasing (FFD) — sort items from largest to smallest, put each into the first bin that has room, open a new bin if none has.
Best fit / worst fit — put the item in the bin that will have the least (best) or most (worst) space left after placing it.
Approximation ratio — the worst-case ratio between the number of bins an algorithm uses and the optimum.
Vector bin packing — bin packing where each item and bin has several dimensions, and an item fits only if it fits in every dimension.
Stranded (fragmented) resource — capacity of a machine that cannot be used because another resource on it is already full.
Filter and score — the two-phase scheduling method: first remove infeasible machines (filter), then rank the rest (score) and choose the best.
history: The one-dimensional problem was studied in the early 1970s as part of the new theory of NP-completeness. Garey and Johnson's book (1979) lists it as NP-hard in the strong sense, so even a pseudo-polynomial method cannot exist unless P = NP. The more important result for engineers was practical: in 1973 David Johnson's thesis, and the 1974 paper by Johnson, Demers, Ullman, Garey and Graham, analysed the simple heuristics and proved bounds. Next Fit uses at most twice the optimum; First Fit at most 1.7 times; first-fit decreasing about 11/9 times (the exact bound, \( \tfrac{11}{9}\,OPT + \tfrac{6}{9} \), was proved by Dósa in 2007).
A second line of work found methods that are nearly optimal in theory. Gilmore and Gomory (1961) wrote bin packing, as the cutting-stock problem, as a linear program with one column per way of filling a bin, solved by column generation. Fernandez de la Vega and Lueker (1981) gave an asymptotic approximation scheme, and Karmarkar and Karp (1982) a method that uses at most \( OPT + O(\log^2 OPT) \) bins. These are rarely run in production but show that the problem is easy in practice for large items.
The cluster era made the multi-dimensional version central. Woeginger (1997) proved that vector bin packing has no asymptotic approximation scheme unless P = NP. Google's Borg (Verma et al., EuroSys 2015) described scoring that avoids stranded resources, after finding that a worst-fit style score (E-PVM) spread work evenly but increased fragmentation, while best fit packed tightly but left no room for load spikes; a hybrid packed a few percent better. Ghodsi et al. (NSDI 2011) proposed Dominant Resource Fairness for sharing; the Tetris scheduler (Grandl et al., SIGCOMM 2014) packs by an alignment score between task demand and machine free capacity. Kubernetes (2014 onward) made filter-and-score the most widely used design.
how: The core is one decision, repeated: given an item and some bins with different free space, which bin?
Step 1: The lower bound. The total size of all items divided by the bin capacity, rounded up, is a lower bound on the number of bins. This is the simplest case of a bound from the LP relaxation. If items of total size 30 go into bins of 10, you need at least 3 bins. The gap between the best heuristic and the bound tells you how much there is to gain.
Step 2: Simple one-dimensional heuristics. Next Fit keeps one open bin and opens a new one when an item does not fit; it is simple but wasteful (up to 2× optimal). First Fit puts each item in the lowest-numbered bin that has room. Best Fit puts it in the fullest bin that still fits. The worst-case ratio for both is 1.7. All three work online. Their weakness is the order: a small item arriving early can occupy space that a later large item needs.
Step 3: Sort first (offline). First-fit decreasing places the largest items first, while there is still plenty of free space, and fills the gaps with small items at the end. The reason it works is a greedy argument: after the large items are placed, each bin can hold at most a few, and the small items, which are flexible, fill the holes. The proven guarantee is \( FFD \le \tfrac{11}{9} OPT + \tfrac{6}{9} \), and in practice it is usually within one bin of the optimum. Sorting costs \( O(n \log n) \), and finding the first bin with a search tree over remaining capacities keeps the whole algorithm at \( O(n \log n) \).
Step 4: Several resources. With CPU and memory, an item is a vector, and no sorting order is natural. Common choices: sort by the largest dimension, by the sum of normalised dimensions, or by the dominant resource share. A bin accepts an item only if every dimension fits. The new failure is **stranding**: a machine with all its CPU used and half its memory free can take no CPU-bound item, so the free memory is wasted unless some memory-heavy item arrives. A good packing mixes items whose demands are complementary, for example CPU-heavy with memory-heavy ones, so both dimensions fill together. Scores such as the dot product of the item's demand vector with the machine's free vector (Tetris) or the sum of squared leftovers favour such pairs. The same linear-algebra view (vectors, norms) appears in the LP relaxation.
Step 5: Online scheduling with filter and score. A cluster scheduler cannot sort: pods arrive one at a time, and a decision must be fast and final. Kubernetes runs two phases per pod. Filter: the nodes that fail a hard rule are removed (not enough free CPU or memory, wrong zone, a taint the pod does not tolerate, an anti-affinity rule). Score: each remaining node gets a number from several plugins, weighted and added, and the highest wins. The resource plugin `NodeResourcesFit` has strategies: `LeastAllocated` (the default; prefer emptier nodes, which spreads load and reduces hot spots), `MostAllocated` (prefer fuller nodes, which is best-fit packing and lets the autoscaler remove empty nodes), and `RequestedToCapacityRatio` (a custom curve). For large clusters, the scheduler scores only a part of the feasible nodes (an adaptive share that falls from 50% as the cluster grows, down to a minimum of 5%, and at least 100 nodes), to keep the decision fast.
```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: bin-packing
  pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: MostAllocated
        resources:
        - {name: cpu, weight: 1}
        - {name: memory, weight: 1}
```
Step 6: Reality adds layers. Schedulers pack requests (what the job asked for), not actual use, so the gap between request and usage is wasted capacity, and overcommit tries to recover it at the risk of contention. Borg and Kubernetes use priorities and preemption to evict low-priority work when a high-priority item does not fit. Packing is repeated in time: a descheduler or the autoscaler's consolidation (Karpenter, for example) moves pods to free whole nodes, which is bin packing with migration costs. Cloud autoscalers choose which machine size to add, so the bin size becomes a decision as well.
Step 7: Packing against spreading. Tight packing saves money but puts many pods on few machines, so one failure takes out many, and busy machines suffer interference. Spreading does the reverse. Production policy mixes them: pack within a zone, spread across zones and across failure domains, and keep some headroom.

example: One dimension. Bins of capacity 10 and items 6, 5, 4, 4, 3, 3, 3, 2 (total 30, so at least 3 bins). First-fit decreasing: sort (already sorted). Item 6 opens bin 1. Item 5 does not fit with 6 (11 > 10), so it opens bin 2. Item 4 fits in bin 1 (6 + 4 = 10). The next 4 does not fit in bin 1 (full) but fits in bin 2 (5 + 4 = 9). Item 3 fits in neither (bin 2 would be 12), so it opens bin 3. The next two 3s go into bin 3 (3, 6, 9). Item 2: bin 1 is full, bin 2 would be 11, bin 3 would be 11, so it opens bin 4. FFD uses 4 bins. But 6 + 4, 5 + 3 + 2, and 4 + 3 + 3 each add up to 10, so 3 bins are possible. The heuristic is 33% above optimal here, which is the worst case allowed by the bound 11/9 × 3 + 6/9 = 4. This is the reason the answer is a heuristic: finding the optimal packing means searching among a huge number of arrangements.
Now two dimensions, where stranding appears. Nodes have 8 CPUs and 32 GiB. Pod type A needs (4 CPU, 4 GiB) and type B needs (1 CPU, 12 GiB). There are 10 of each. If the scheduler first places the 10 A pods with a best-fit rule, two A pods fill a node's CPU completely (8 of 8) while using 8 of 32 GiB, so 5 nodes hold the A pods and 24 GiB is stranded on each. The 10 B pods then need 5 more nodes, because memory allows only two per node (2 × 12 = 24 ≤ 32, three would need 36) and they use only 2 of 8 CPUs. Total: 10 nodes, with the CPU of five of them mostly idle. Now place one A with two B on a node: it uses (4 + 2, 4 + 24) = (6, 28), nearly full on both. Five such nodes hold 5 A and 10 B, and the remaining 5 A fit on 3 more nodes (two per node, two on the last... 5 = 2 + 2 + 1). Total: 8 nodes, 20% fewer. The lower bound is 7 (total CPU 50 over 8, rounded up), so the mixed placement is within one node of the bound. With 1,000 nodes the same effect would save about 200 machines.
intuition: Packing a suitcase: put the big, awkward things in first, and fill the gaps with small ones.
The reason the heuristic works is that flexibility is a resource. Small items fit almost anywhere, so keep them for the end, when only gaps remain; large items have few places they can go, so place them while you still have room to choose. In several dimensions the same idea becomes: pair the items that need different things, so that none of the dimensions is exhausted while the others are idle. Hardness shows up because these local choices interact, and the best answer for one bin may ruin the next. Because of this, the problem is NP-hard, and every method accepts "good enough" in place of "best".
mistakes: People often think an NP-hard problem cannot be solved well. In fact worst cases are hard, but typical bin packing instances are easy: first-fit decreasing is within one bin of optimal on most inputs, and exact solvers with column generation prove optimality for thousands of items. NP-hardness is a statement about guarantees, not about practice.
People often think packing as tightly as possible is always the goal. In fact tight packing leaves no headroom for load spikes, increases the effect of a single machine failure, and creates interference between neighbours that share caches and memory bandwidth. Production schedulers target a utilisation below 100% and spread across failure domains.
People often think the scheduler packs actual usage. In fact it packs requests. If teams request 4 CPUs and use 1, the cluster looks full while the machines are idle. Fixing requests (right-sizing, vertical autoscaling) gives larger gains than a smarter scoring function.
People often think that the sum of free resources shows how much can still be placed. In fact free capacity can be fragmented across many nodes: 100 nodes with 2 CPUs free each have 200 free CPUs, but a pod that needs 4 CPUs cannot be placed anywhere. This is why a cluster can reject a pod while the dashboard shows half the capacity free.
friction: Online decisions are final, and the order of arrival is out of your control. No online algorithm can guarantee better than about 1.54 times the optimum in the worst case, and real arrivals are bursty: a deployment of 500 identical pods arrives at once, and a greedy choice for each pod, made without looking at the others, can leave a poor layout. Re-packing later means moving running workloads, which costs restarts, cold caches and risk, so schedulers move things only rarely.
The model is too simple in several ways. Demands are not constants: a job's real use varies over time, so peak-based packing wastes capacity and average-based packing risks overload. Resources are not independent: memory bandwidth, cache, network and disk I/O are shared and are not in the request, so two pods that fit on paper can slow each other. Constraints such as affinity, topology spread, GPUs that must sit on the same switch, and licences turn the problem into a general constraint problem (the constraint satisfaction layer again). Scoring many nodes is expensive too: for a 5,000-node cluster the scheduler samples nodes to stay inside its millisecond budget.
practice: Start from the data: measure requested versus used CPU and memory per workload, the stranded capacity per node (free memory on nodes with no free CPU, and the reverse), and the distribution of pod sizes. Right-size requests first. Then choose the scoring strategy: `LeastAllocated` for latency-sensitive services where spreading limits interference; `MostAllocated` (or a bin-packing profile) for batch and for clusters with an autoscaler that removes empty nodes.
Use several node pools matched to the shapes of your workloads (CPU-heavy, memory-heavy, GPU), so that bins have the right ratio of resources, and let the autoscaler choose instance types that fit the pending pods (`least-waste` expander in the Cluster Autoscaler, or Karpenter's consolidation). Set pod disruption budgets and topology spread constraints so that packing does not remove availability. Keep a headroom of 10% to 20% in latency-sensitive pools.
For batch systems (Spark on YARN or Kubernetes), choose container sizes that divide node sizes well: with 64 GB nodes, executors of 24 GB waste 16 GB per node, while 16 GB or 32 GB executors tile the node exactly. Check leftovers: a node with 64 GB and 16 CPUs that runs three executors of (5 CPU, 20 GB) wastes 1 CPU and 4 GB. When you need a plan offline, such as capacity planning for next quarter, write a first-fit-decreasing simulation or use an LP/CP-SAT solver on your real pod sizes; it takes a few lines and shows how many nodes you need.
tradeoffs: Choose best-fit or `MostAllocated` scoring when cost is the target and you have an autoscaler that can remove empty nodes: batch clusters, CI runners, dev environments. You pay with hot nodes, noisy neighbours, and larger impact when one node fails. Choose spreading (`LeastAllocated`, topology spread) for latency-sensitive services where tail latency and failure isolation matter more than a 10% saving in nodes.
Choose offline packing (sort and solve) when you can see the whole demand in advance: capacity planning, nightly batch assignments, reorganising a fleet. It gives results near optimal and tells you how many machines to buy. Choose online filter-and-score for live scheduling, where each decision must take milliseconds and the demand is unknown; you accept a gap to the optimum of perhaps 5% to 15% and fix it with periodic consolidation.
Choose an exact solver (MIP or CP-SAT) when the problem is small (hundreds of items), the cost of a bin is high (large GPU machines) and you can wait seconds to minutes. Choose a heuristic when there are thousands of items and decisions must be repeated. Choose more node shapes when workloads vary in their CPU-to-memory ratio, since this reduces stranding; you pay with operational complexity and more pools to keep warm.

value: PCI Express (PCIe) is the connection between the CPU and nearly everything that is not memory: GPUs, NVMe disks, network cards, accelerators. Inside a server it is the road system. A GPU doing training reads its input over PCIe, an NVMe drive delivers 7 to 14 GB/s over four PCIe lanes, and a 400 Gbit/s network card needs a Gen5 x16 slot to receive its traffic. When one of these devices is slower than it should be, the cause is often the PCIe link: negotiated at a lower speed, too few lanes, too few outstanding requests, or a shared bottleneck behind a switch.
The design is a set of point-to-point serial links called **lanes**. One lane has two wire pairs, one for each direction, and each pair carries a very fast bit stream (32 billion bits per second in Gen5) with the clock embedded in the data. Devices combine 1, 2, 4, 8 or 16 lanes (written x1 … x16) to scale bandwidth. On top of the wires, PCIe is a packet network with layers: it sends read and write requests as packets, checks them with a CRC, replays them if damaged, and uses credit-based flow control so a sender never overruns a receiver. To software it looks like the old PCI bus: devices have addresses, configuration registers and memory-mapped registers, so drivers did not need to change when the physical layer was replaced by serial links.
The layers below supply the pieces. Digital logic builds the serialisers, scramblers, state machines and FIFO buffers. Electromagnetism explains why a signal at 16 GHz on a circuit board behaves like a wave on a transmission line, with loss, reflections and crosstalk that limit the distance. Coding theory gives the line codes (8b/10b, then 128b/130b) and the CRC and error-correction codes that make a noisy channel reliable. DMA lets a device read and write main memory by itself, which is how all the bandwidth is actually used. The layers above are NVMe (its queues live in host memory and its commands are PCIe packets), CXL (it reuses the PCIe physical layer), GPUs and RDMA network cards.
terms: Lane — one pair of differential wires in each direction; a link is made of 1 to 16 lanes.
GT/s — giga-transfers per second: the raw number of bits per second on one lane (32 GT/s in Gen5), before coding overhead.
Root complex — the part of the CPU that connects the processor and memory to the PCIe fabric.
Endpoint / switch — an endpoint is a device (GPU, SSD); a switch fans out one upstream link to several downstream links.
TLP — transaction layer packet: a memory read or write, configuration access, completion or message, with a header and optional payload.
Credit — a permission, advertised by the receiver, to send a certain amount of header and data; a sender stops when its credits run out.
BAR — base address register: a register in a device that tells the system how much address space it needs for its memory-mapped registers.
Posted vs non-posted — a posted request (memory write) needs no reply; a non-posted request (memory read) needs a completion packet.
LTSSM — link training and status state machine: the procedure that detects a partner and agrees on width and speed.
history: Before PCIe, computers used shared parallel buses. Intel's PCI (1992) had 32 or 64 data wires clocked at 33 or 66 MHz, shared by all devices: the maximum was 133 MB/s for the common version, split among every card. Raising the clock was blocked by skew between the many parallel wires and by the electrical load of several devices on one bus. Intel started work on a serial replacement ("3GIO") around 2001, and PCI-SIG released PCI Express 1.0 in 2003: each device has its own dedicated serial link to a switch or to the chip set, at 2.5 GT/s per lane.
The rest of the story is a doubling of the lane rate about every three to four years. Gen2 (2007) went to 5 GT/s. Gen3 (2010) went to 8 GT/s and changed the line code from 8b/10b (20% overhead) to 128b/130b (about 1.5%), which gave twice the data rate with only 1.6 times the bit rate. Gen4 (2017) reached 16 GT/s and Gen5 (2019) 32 GT/s, where board design became hard enough that retimer chips were needed for longer traces. Gen6 (finalised in 2022) reached 64 GT/s by changing the signalling from two voltage levels (NRZ) to four (PAM4), which carries two bits per symbol, and by adding forward error correction and fixed-size 256-byte packets called FLITs. PCIe 7.0 (released in June 2025) doubles the rate to 128 GT/s, and PCIe 8.0 at 256 GT/s was announced in August 2025.
The demand came from GPUs, NVMe drives (2011 on) and fast networks. Meanwhile PCIe also spread beyond slots: CXL (2019) is a protocol for coherent memory and accelerators that runs over the PCIe physical layer, and the lane PHY design is also shared by chiplet and storage interfaces. The pattern is constant: the protocol and software model stay fixed while the physical layer gets faster.
how: PCIe has three protocol layers over the wires. Each one solves a separate problem.
Step 1: The physical layer. A lane has a transmitter and receiver in each direction, each using a differential pair: the same signal is sent on two wires with opposite polarity, and the receiver looks at the difference, so noise that hits both wires equally disappears. There is no separate clock wire per lane. The data is scrambled with a linear-feedback shift register (to avoid long runs of equal bits and to spread electromagnetic energy) and the receiver recovers the clock from the transitions in the data, with a clock data recovery (CDR) circuit. The line code guarantees enough transitions and a balanced signal: 8b/10b in Gen1 and 2 turned every 8 bits into 10 bits, and 128b/130b in Gen3 to 5 adds 2 bits to every 128. At 32 GT/s the bit time is 31 picoseconds, in which a signal travels about 5 mm on a board, so the wire must be treated as a transmission line with a controlled impedance, and its loss (skin effect and dielectric loss grow with frequency), reflections at vias and connectors, and crosstalk between neighbours all affect the eye diagram. Transmitters pre-emphasise the signal, and receivers equalise it with filters (CTLE, DFE). Gen6 uses PAM4 with FEC, because four levels have three smaller eyes.
Step 2: Link training. At power-up each side runs the LTSSM: detect a receiver on the other end, send training sequences, agree on the lane count (a x16 slot with a x8 card trains to x8), reverse lane order or swap polarity if the board needs it, start at 2.5 GT/s and negotiate upward, and tune the equalisation for each speed. The result is visible to the operating system: `lspci -vv` shows `LnkCap` (what the link can do) and `LnkSta` (what it trained to). A link that trains below its capability, such as Gen3 x4 instead of Gen4 x4, is a common cause of low performance.
Step 3: The data link layer. This layer makes the link reliable. Each TLP receives a 12-bit sequence number and a 32-bit CRC (LCRC) and is held in a replay buffer. The receiver checks the CRC and sends an ACK or NAK (small DLLPs); on a NAK or timeout the sender replays from the buffer. It also carries flow control updates. The coding-theory layer gives the CRC math; it detects all bursts up to 32 bits and almost all other errors. A raw bit error rate of 10⁻¹² means about one error every half minute per lane at 32 GT/s, which the replay hides.
Step 4: The transaction layer and credits. The software-visible unit is the TLP: Memory Read, Memory Write, Configuration Read/Write, Completion, and Message. A TLP has a header of 12 or 16 bytes and a payload of up to the negotiated maximum, typically 256 bytes (the specification allows up to 4,096). Flow control is by credits, kept separately for posted writes, non-posted requests and completions, and separately for headers and data (one data credit is 16 bytes). A receiver announces how much buffer it has; the sender subtracts credits as it sends and waits at zero; the receiver returns credits as it frees space. Because the sender never sends without credit, no packet is dropped for lack of buffer. This is a lossless design, like the link-level flow control of InfiniBand.
Step 5: The cost of a packet. Each TLP carries about 24 to 30 bytes of overhead (header, sequence number, LCRC, framing). For a 256-byte payload this gives roughly 90% efficiency, and for a 64-byte payload (one cache line) only about 70%. So the usable bandwidth is below the raw rate: Gen5 x16 is 63 GB/s per direction raw, and about 55 GB/s of useful data is typical.
Step 6: Addresses and DMA. At boot, firmware walks the bus tree and reads each device's configuration space (vendor ID, device ID, class, capabilities). Each device lists its BARs; the system assigns it a range in the physical address space. After that, a CPU store to an address in a BAR becomes a posted Memory Write TLP to the device (this is how a driver rings a doorbell), and a CPU load becomes a non-posted Memory Read, which stalls the core for the round trip, often a microsecond or more. The device in turn is a bus master: it issues reads and writes to host memory addresses itself (DMA), with the IOMMU translating and protecting those addresses. Interrupts are also writes: MSI-X is a memory write by the device to a special address. An NVMe read of 4 KB is the typical pattern: the driver writes a 64-byte command to a queue in host memory and one doorbell write to the device; the device fetches the command by DMA, reads the flash, writes 4 KB of data into host memory in TLPs of up to 256 bytes, writes a 16-byte completion entry and sends the MSI-X interrupt.
Step 7: Topology and sharing. The root complex in the CPU provides a set of lanes (a server CPU offers roughly 80 to 128 Gen5 lanes); switches expand them, with all devices below a switch sharing its upstream link. Peer-to-peer DMA lets two devices below the same switch talk without going through host memory (GPU to NIC, GPU to NVMe), which saves a copy. For GPU-to-GPU traffic, PCIe at 63 GB/s each way is slow next to NVLink on a data-centre GPU (hundreds of GB/s), which is why those GPUs have both.

example: Raw bandwidth. A Gen5 lane runs at 32 GT/s with 128b/130b coding, so the data rate is 32 × 128/130 = 31.5 Gbit/s = 3.94 GB/s per direction. A x16 link gives 63 GB/s each way, which is 126 GB/s counting both directions. With 256-byte payloads and about 28 bytes of overhead, efficiency is 256/284 = 90%, so about 57 GB/s of useful data. Compare the other generations for the same x16 slot: Gen3 about 15.8 GB/s, Gen4 about 31.5 GB/s, Gen6 about 128 GB/s (raw).
What does this mean for a GPU? To load an 80 GB model from host memory to a GPU over x16 Gen5 at 55 GB/s takes 80/55 ≈ 1.5 s. On Gen4 (about 26 GB/s) it takes about 3 s. The GPU's own memory (HBM3, around 3.35 TB/s on an H100) is about 60 times faster than the link, which is why programs copy data to the GPU once and keep it there, and why pinned memory and large transfers matter.
Now the limit of outstanding requests. A device reads host memory with 256-byte reads, and the round trip through the root complex is 1 µs. The link can carry 63 GB/s, so to fill it the device needs 63 GB/s × 1 µs = 63 KB in flight, which is about 246 reads. If the device keeps only 32 reads in flight (32 tags), its throughput is 32 × 256 B / 1 µs = 8.2 GB/s, whatever the link speed. This is the bandwidth-delay product, and it is why high-speed devices have many tags (extended 10-bit tags allow 1,024), large buffers, and why the credit pool at the receiver must be at least as large as the product of the rate and the round-trip time.
Finally, error behaviour. At a raw bit error rate of 10⁻¹² and 32 Gbit/s per lane, a lane sees an error about every 31 seconds; a x16 link sees one about every 2 seconds. Each error corrupts one TLP, the CRC catches it, and the replay costs a few hundred nanoseconds. A bad connector or too long a trace can raise the rate by orders of magnitude, so replays become frequent and throughput falls. Linux exposes these as correctable error counters in `lspci -vv` and in the AER (advanced error reporting) logs.
intuition: PCIe is a set of private lanes on a highway system: each device has its own lanes to the junction, and packets obey a strict rule that nobody enters a lane unless the exit has room.
The design is natural because a shared bus cannot go faster: more devices means more electrical load and more wires to keep in step. Point-to-point serial links remove both problems. A single pair of wires with an embedded clock has no skew between wires, so it can run very fast, and more bandwidth is added by adding lanes, which are independent. Packets and credits then put structure on top: the sender does not need to know the receiver's speed, only how much buffer it has. The price is that a simple bus read becomes a network round trip, so latency, not bandwidth, becomes the quantity to hide.
mistakes: People often think a x16 slot always gives x16 speed. In fact a link is the minimum of what both ends support and of what the board wiring provides: a x16 slot can be wired as x8 or x4 electrically, share lanes with an M.2 slot, or train at a lower generation because of signal quality. Check `LnkSta`, not the slot's size.
People often think the speed in GT/s is the data rate. In fact it counts raw bits, and coding takes a part: Gen1 and Gen2 lose 20% to 8b/10b, Gen3 to Gen5 lose about 1.5%, and packet overhead takes another 10% or so. A Gen4 x4 NVMe drive has a raw 7.9 GB/s and typically delivers 6.5 to 7 GB/s.
People often think a higher PCIe generation makes small operations faster. In fact bandwidth doubles but latency barely changes: a read round trip is dominated by the root complex, the switch hops and the device, which stay at several hundred nanoseconds to a microsecond. Small random accesses are limited by latency and by the number of outstanding requests.
People often think PCIe is only the physical slot. In fact the same protocol runs inside the chip package and on boards: NVMe on M.2, Thunderbolt tunnels PCIe over cables, and CXL uses the PCIe electrical layer. The slot is only one form.
friction: The first problem is physics. Each doubling of the rate increases loss and the sensitivity to every imperfection in the board, connector and package. Gen5 needs better board materials and often retimers (chips that re-time and re-send the signal) for traces beyond a few inches to a foot, and each retimer costs power, latency and money. PAM4 in Gen6 and later makes the signal more fragile, so the design depends on FEC. Power is also a limit: SerDes lanes at these rates take several picojoules per bit, so a x16 link at Gen5 spends several watts, and a switch with 100 lanes spends tens of watts.
Lanes are a scarce budget. A CPU has a fixed number, and every device competes. Topology matters: a GPU and an NIC under the same switch can talk directly, but if they are under different CPU sockets, traffic crosses the inter-socket link and loses bandwidth. Misplacing cards (an NVMe drive on the wrong socket) can halve performance, and operating systems expose this only through NUMA tools and `lspci -tv`.
practice: Check the link first. `lspci -vv -s <device>` shows `LnkCap` and `LnkSta`: speed (16GT/s, 32GT/s) and width (x4, x16). If `LnkSta` is lower than `LnkCap`, look at the slot wiring, riser cables, BIOS settings and the error counters. `lspci -tv` shows the tree and which devices share a switch, and `nvidia-smi topo -m` shows GPU-NIC-CPU paths. `dmesg | grep -i aer` lists corrected and uncorrected errors, and a stream of corrected errors points to a signal integrity problem.
Place devices with the topology in mind: keep a GPU and its NIC under the same switch or at least on the same socket, put NVMe drives on the socket where the application runs (pin the process with `numactl`), and count lanes before you buy a server. Use pinned (page-locked) host memory and large transfers for host-to-GPU copies, overlap copies with compute using streams, and keep data on the device. For devices you design or program, keep enough requests in flight to cover the round trip, use a maximum payload of 256 or 512 bytes where the platform supports it, and avoid MMIO reads in the fast path.
tradeoffs: Choose a wider link (x16 instead of x8) when the device can use the bandwidth and lanes are available; it adds bandwidth without new silicon, but takes lanes from other devices and costs board space. Choose a newer generation (Gen5 or Gen6) at the same width when lanes are the scarce resource, accepting the cost of better boards, retimers and more power per lane.
Choose a PCIe switch when you need more devices than the CPU has lanes, or peer-to-peer transfers between devices; you pay with latency of the order of 100 ns per hop, a shared upstream link (oversubscription) and more power. Choose to connect devices directly to the CPU when each needs its full bandwidth, as with the NVMe drives of a high-throughput database.
Choose PCIe for general attachment (storage, NICs, accelerators with modest GPU-to-GPU traffic). Choose a dedicated interconnect (NVLink, Infinity Fabric, or a network with RDMA) for GPU-to-GPU traffic in training, where hundreds of GB/s per GPU are needed. Choose CXL over plain PCIe when you need cache-coherent access to memory or memory expansion; accept latency well above local DRAM (a few hundred nanoseconds, like a remote NUMA node or worse) and a young ecosystem.
interview: What limits throughput between a device and host memory, besides the link speed? || The number of requests in flight, the round-trip latency, and the receiver's credits. Throughput is at most outstanding bytes divided by latency: 32 reads of 256 B at 1 µs give only 8 GB/s, even on a 63 GB/s link. Also the TLP overhead (about 10% at 256 B), the maximum payload size, and shared upstream links behind switches.
Explain PCIe flow control. Why is it lossless? || The receiver advertises credits for headers and data, separately for posted, non-posted and completion traffic. The sender consumes credits per packet and stops at zero; the receiver returns them with update packets when buffer space frees. Because a packet is sent only when buffer is guaranteed, there is no drop, but a slow receiver can stall a link, and head-of-line blocking can result.
Your NVMe drive does 3 GB/s but is specified at 7 GB/s. How do you investigate? || Check `LnkSta` to see if it trained at a lower speed or width (Gen3 x4 gives about 3.9 GB/s), check the slot (shared lanes, chipset vs CPU lanes), power-state and BIOS settings, AER errors, thermal throttling of the drive, and whether the test uses enough queue depth and parallel threads.
How does a driver talk to a PCIe device, and what is expensive? || It maps the BARs and writes to registers (posted writes, cheap and pipelined) and builds descriptors in host memory that the device reads by DMA. MMIO reads are expensive because they stall the CPU for a full round trip, often a microsecond. Doorbell writes are batched, and interrupts (MSI-X) are coalesced.
Why did Gen6 move from NRZ to PAM4 instead of doubling the symbol rate? || Doubling the symbol rate would double the frequency of the channel (Nyquist 32 GHz), and the board and connector loss at that frequency is too high. PAM4 sends two bits per symbol, so 64 GT/s keeps the same 16 GHz Nyquist as Gen5, at the cost of smaller eyes and a higher raw error rate, which is handled with FEC and CRC in fixed-size FLITs.
quiz: What is the useful data rate of a Gen5 x16 link in one direction, before packet overhead? || 32 GT/s × 128/130 = 31.5 Gbit/s per lane = 3.94 GB/s, times 16 lanes ≈ 63 GB/s.
Why did PCIe replace a shared parallel bus with serial point-to-point lanes? || Parallel buses are limited by skew between wires and the load of many devices on one set of wires. A serial pair with an embedded clock has no skew and each device gets its own link, so the rate can rise and bandwidth scales by adding lanes.
How does credit-based flow control prevent packet loss? || The receiver tells the sender how much buffer space it has (credits). The sender sends only when it has enough credits and gets them back when the receiver frees buffer, so the receiver is never overrun.
A device has 16 outstanding 512-byte reads and a 2 µs round trip. What is its maximum read throughput? || 16 × 512 B / 2 µs = 8,192 B per 2 µs = 4.1 GB/s, regardless of link speed.
When would you choose a PCIe switch, and what do you give up? || When there are more devices than CPU lanes or when devices need peer-to-peer transfers. You give up some latency per hop, the full bandwidth of each device if the upstream link is oversubscribed, and some power.
