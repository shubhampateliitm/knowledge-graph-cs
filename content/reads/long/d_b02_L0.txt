@@ langchain
value: Every application built on a large language model (LLM) needs the same plumbing. It must format messages, call the provider's API, stream tokens back, describe tools to the model, parse the tool calls the model returns, run those tools, feed the results back, fetch documents, and repeat until the task is done. A real product must also survive a crash halfway through, pause for a human to approve a risky step, and show engineers exactly what the model received. LangChain is an open-source library of standard interfaces and integrations for that plumbing. LangGraph, from the same company, is a runtime that runs an application as a graph of steps with saved state, so it can loop, branch, pause and resume.
Python and JavaScript developers use them to build chat assistants, retrieval-augmented generation (RAG) systems and agents; the Python package had about 164 million downloads in the 30 days before October 2026 (PyPI statistics). Many teams use only parts, such as langchain-core's model and tool helpers, or LangGraph alone.
It stands on three lower concepts. Python (L0) supplies the language and its ecosystem; LangChain turns ordinary typed Python functions into tool descriptions by reading their signatures. AI agents (L1) supply the loop that LangGraph runs: the model chooses an action, a tool runs, the result goes back to the model. Retrieval-augmented generation (L1) supplies the pipeline (load, split, embed, store, retrieve) that LangChain packages as swappable parts. Nothing on this map is built on LangChain; its "layer above" is its users' application code.
terms: Chat model — a wrapper around one provider's API with a common interface: send a list of messages, get back an AI message.
Tool — a function the model may ask to run, described by a name, a description and a JSON schema for its arguments.
Runnable — LangChain's common interface for any step, with invoke, batch, stream and async versions of each.
State — in LangGraph, a typed dictionary that every node reads and returns updates to.
Reducer — a function that says how an update is merged into a state key, for example "append to the message list" instead of "overwrite".
Super-step — one round of LangGraph execution: all ready nodes run, and their writes become visible only at the end of the round.
Checkpointer — a store (memory, SQLite, Postgres) that saves the graph state after each super-step, keyed by a thread ID.
Middleware — hooks in LangChain 1.0 agents that run before, after or around model and tool calls.
history: Harrison Chase published the first version of LangChain on PyPI on 25 October 2022, about a month before ChatGPT launched. It drew on ReAct (Yao et al., 2022), in which the model writes a thought, picks an action such as a search, reads the result, and repeats. LangChain offered ready-made "chains" (fixed sequences of prompt, model and parser) and "agents" (ReAct-style loops), and when ChatGPT made LLMs popular it became the default way to try them. The company was founded in February 2023, and its tracing product LangSmith entered beta that summer.
Growth brought criticism: many classes hid the real prompts and made simple things hard to debug. The team answered in August 2023 with the LangChain Expression Language (LCEL), in which every component is a Runnable joined with the | operator. Version 0.1 (January 2024) split the code into langchain-core (interfaces), langchain-community (third-party integrations) and partner packages such as langchain-openai, so users install only what they need.
The bigger change was LangGraph, first released in January 2024. Chains are acyclic: data flows from start to end once. Agents need cycles (call the model again after each tool), shared state, and the ability to stop and resume. LangGraph took its execution model from Google's Pregel system for graph processing (Malewicz et al., 2010), which runs in synchronized rounds.
In October 2025 LangChain 1.0 and LangGraph 1.0 shipped together, and the company announced a $125 million round at a $1.25 billion valuation, led by IVP. LangChain 1.0 rebuilt the high-level API around one function, create_agent, which runs on LangGraph, plus middleware and standard content blocks; old chains moved to a langchain-classic package. The hosted LangGraph Platform became the Deployment part of LangSmith. As of October 2026 the current releases are langchain 1.4 and langgraph 1.2, both for Python 3.10 or newer.
how: The base layer, langchain-core, defines message types (system, human, AI, tool) and the chat-model interface. A provider package such as langchain-anthropic translates that interface into the provider's HTTP API. model.invoke(messages) returns an AIMessage; model.stream(messages) yields chunks as tokens arrive. Since 1.0 every message also exposes content_blocks, a provider-neutral list of text, reasoning, image and tool-call blocks. model.bind_tools(tools) attaches tool schemas to each request, and model.with_structured_output(schema) asks for data matching a Pydantic class.
Tools show what Python contributes. You write a normal function with type hints and a docstring and add the @tool decorator. LangChain inspects the signature at runtime, builds a Pydantic model from the type hints, and converts it into the JSON schema that providers expect. When the model answers, its AIMessage carries tool_calls, each with a name, arguments and an ID. The framework validates the arguments, calls the function, and returns the result as a ToolMessage with the same ID. Python's asyncio and thread pools run independent calls at the same time; the global interpreter lock does not hurt, because almost all the time is spent waiting on the network.
The RAG concept contributes the retrieval parts. Document loaders read PDFs, web pages or tables into Document objects (text plus metadata). Text splitters cut them into chunks, for example 1,000 characters with 200 characters of overlap. Embedding and vector-store wrappers (pgvector, Pinecone, FAISS, Elasticsearch and many more) turn chunks into vectors and store them, and a retriever answers a query with the k closest chunks. Because each piece has a common interface, you can replace FAISS with Postgres without changing the rest of the program. LangChain does not make retrieval good; it makes the parts swappable so you can measure which combination is.
LCEL composes parts into fixed pipelines. prompt | model | parser builds a RunnableSequence that runs the three in order, and a dictionary of runnables becomes a RunnableParallel that runs its branches concurrently. Because every step has the same interface, the whole sequence automatically supports batch, stream and async calls. LCEL cannot cleanly express "loop until the model stops asking for tools", which is why LangGraph exists.
LangGraph runs a graph over a shared state. You declare the state as a typed dictionary and give each key a reducer; the usual messages key uses add_messages, which appends instead of replacing. Nodes are functions that receive the state and return a partial update. Edges connect nodes, and conditional edges call a function that inspects the state and names the next node. Compiling turns the graph into a Pregel-style program that runs in super-steps. In each super-step the runtime plans which nodes are triggered by channels updated in the last step, runs them in parallel, then applies all their writes through the reducers. A node never sees another node's write from the same super-step. The run ends when no node is triggered or a step limit is reached, which stops an agent that would loop forever.
Persistence makes LangGraph more than a loop. With a checkpointer, LangGraph saves a checkpoint at every super-step boundary, under the thread_id passed in the config. A checkpoint holds the state values, the next nodes to run, a pointer to its parent checkpoint, and metadata. If a node fails mid-step, the writes of the nodes that succeeded are stored as pending writes and are not re-run on resume. A node can call interrupt() to stop and wait: the state is saved, the process may even restart, and a later call with the same thread_id and a resume value continues from there. You can also replay from an older checkpoint, or fork by writing a modified state, which creates a new checkpoint and leaves the old one unchanged. In production the usual store is PostgresSaver.
create_agent packages the loop from the AI agents concept as a prebuilt graph: a model node, a tool node, and a conditional edge that goes to the tools when the last AI message contains tool calls and to the end otherwise. Middleware changes this loop without rewriting it. Node-style hooks (before_agent, before_model, after_model, after_agent) read and update state. Wrap-style hooks (wrap_model_call, wrap_tool_call) surround each call and may skip, retry or redirect it. Built-in middleware covers summarizing old messages, pausing for human approval before chosen tools, detecting personal data, falling back to another model, and limiting model calls. Every Runnable and node also emits callback events, which LangSmith or another tracer records as a tree of spans with inputs, outputs, token counts and latency.

example: Take a support agent built with create_agent. It has two tools: get_order(order_id), which calls an internal API, and search_policy(query), a retriever that returns 4 chunks of about 500 tokens each. The system prompt is 600 tokens, the two tool schemas add about 300 tokens, and the user writes 20 tokens: "Where is order 4417, and can I still return it?" Assume a model priced at $3 per million input tokens and $15 per million output tokens.
Super-step 1 runs the model node. The input is 600 + 300 + 20 = 920 tokens. The model answers with two tool calls in one message, about 60 output tokens: get_order("4417") and search_policy("return window"). The add_messages reducer appends this message, and checkpoint 1 is saved with next = tools.
Super-step 2 runs the tool node. The two calls are independent, so they run at the same time: the order API takes 80 ms and the retriever 250 ms, so the step takes about 250 ms, not 330 ms. get_order returns about 150 tokens of JSON and search_policy about 2,000 tokens. Both ToolMessages are appended, and checkpoint 2 is saved with next = model.
Super-step 3 runs the model node again. The model must see the whole history, so the input is 920 + 60 + 150 + 2,000 = 3,130 tokens. It writes a 200-token answer with no tool calls, the conditional edge goes to END, and checkpoint 3 is saved.
Cost: input is 920 + 3,130 = 4,050 tokens, so 4,050 × $3 / 1,000,000 ≈ $0.012. Output is 260 tokens, so 260 × $15 / 1,000,000 ≈ $0.004. The request costs about $0.016. Latency: if the first model call takes 0.8 s, the tools 0.25 s, and the second call 1.2 s to its first token plus 4 s to stream 200 tokens at 50 tokens per second, the user sees the first word after about 2.3 s and the full answer after about 6.3 s. The framework adds only milliseconds.
Now add a refund tool, with HumanInTheLoopMiddleware set to require approval for it. The user writes "Please refund it." The model returns a refund tool call, the middleware calls interrupt(), the state is saved, and the process can shut down. Next morning a support lead approves, which calls the graph with the same thread_id and a resume value. LangGraph loads the latest checkpoint, runs the refund tool, and continues as if there had been no pause.
intuition: LangChain is a box of standard plugs for models, tools and retrievers; LangGraph is a flowchart that saves its place after every box, so it can stop and later continue.
The design is natural once you separate two problems. The first is variety: dozens of model providers and data stores each speak their own API, and a common interface lets you swap and compare them. The second is control flow: an agent is a loop whose next step is decided at runtime, and long loops must survive failures and wait for people. Pregel's synchronized rounds solve the second problem. All writes in a round are applied together at its end, so the state between rounds is always consistent, and a consistent state is exactly what you need to save and resume from. Saving after every round turns a fragile in-memory loop into something close to a durable workflow.
mistakes: People often think LangGraph requires LangChain. In fact LangGraph is a separate package whose nodes are plain Python functions that can call a provider SDK directly. LangChain 1.0 depends on LangGraph, not the other way around.
People often think the framework makes an agent smarter or more reliable. In fact it only structures the calls. Quality comes from the model, the prompts, the tool descriptions, the retrieved context and testing. A badly described tool fails the same way with or without LangChain.
People often think checkpoints are long-term memory. In fact a checkpoint is the state of one thread (one conversation or one task run). Remembering facts across threads, such as a user's preferences, needs a separate store that you read and write on purpose.
People often think a common model interface makes switching providers free. In fact the code keeps running, but each model follows prompts and calls tools differently and prices tokens differently, so a switch still needs a re-run of your evaluation set.
friction: The most common complaint is hidden behaviour. A one-line constructor can add a system prompt, reformat messages or retry calls, and error stacks pass through many framework layers. Tracing, or at least debug logging, is close to required to see what the model actually received.
The API has changed often. From late 2022 to late 2025 the project moved through 0.0.x, 0.1, 0.2, 0.3 and 1.0 with many deprecations, and most tutorials online describe older APIs. Version 1.0 promised stability, but community integrations vary in quality, and dependency trees can be large.
Agents have costs the framework cannot remove. Each model call resends the whole history, so if 10 steps each add about 1,000 tokens, the inputs total roughly 1,000 + 2,000 + … + 10,000 = 55,000 tokens, not 10,000. Checkpoints accumulate (one per super-step per thread), so storage grows unless you prune. A step limit stops infinite loops, but an agent can waste many calls before reaching it.
Durable execution has limits too. Resuming re-runs the node that failed or was interrupted, so tools with side effects (charging a card, sending an email) must be idempotent: running them twice must have the same effect as once. The checkpoint stores state, not the outside world. Finally, many experienced teams prefer a thin custom loop around one SDK, or a smaller framework such as Pydantic AI, and build tracing and persistence themselves.
practice: Decide first whether you need an agent. If the steps are always "retrieve, then answer", write a fixed pipeline; it is cheaper, faster and easier to test. If the model must choose the steps, use create_agent, or a hand-built LangGraph graph when you need custom branches, parallel workers or several cooperating agents.
Install only langchain-core, langgraph and the provider packages you need, and pin exact versions. Turn on tracing from the first day; most bugs show up in traces as a bad prompt, a wrong tool argument or a huge tool result.
Keep tools few, with clear names, docstrings that say when to use them, and small outputs: return IDs and short summaries, not whole documents. Make side-effecting tools idempotent, for example by passing a request ID that the downstream service deduplicates. Put human approval in front of anything that spends money, deletes data or contacts customers; HumanInTheLoopMiddleware plus a Postgres checkpointer gives you this without extra infrastructure.
Use one thread ID per conversation or job. Set step and model-call limits, add summarization for long histories, and prune checkpoints on a schedule. Keep an evaluation set of 50 to 200 real questions with expected outcomes and run it on every prompt, model or version change. If your tools already exist as MCP servers, load them with langchain-mcp-adapters instead of rewriting them.
quiz: What is the difference between LangChain and LangGraph? || LangChain provides standard interfaces and integrations for models, tools and retrievers, plus create_agent. LangGraph is the runtime that executes stateful graphs with loops, checkpoints and interrupts; LangChain 1.0 agents run on it.
How does a plain Python function become a tool that a model can call? || The @tool decorator reads the function's name, docstring and type hints and builds a JSON schema. The model sees that schema; when it returns a tool call, the framework validates the arguments, runs the function and sends back a ToolMessage.
Why can LangGraph resume a run after a crash or a human pause? || It saves a checkpoint at every super-step boundary, keyed by thread_id. All writes in a super-step are applied together, so each checkpoint is a consistent state from which a later call with the same thread_id can continue.
An agent makes 4 model calls; the first input is 1,000 tokens and each step adds 2,000 tokens. How many input tokens does it use in total? || The inputs are 1,000, 3,000, 5,000 and 7,000 tokens, so 16,000 in total. Each call resends the whole history, so cost grows much faster than the number of steps.
When would you skip LangChain and write a plain loop around a provider SDK? || When you use one provider, need few integrations, and value control and fewer dependencies over ready-made parts. You then build tracing, persistence and approvals yourself.

@@ mcp
value: An AI assistant becomes useful at work when it can read your tickets, query your database and open pull requests. Before late 2024, each such connection was custom: every AI application wrote its own plug-in for every service. With M applications and N services that is M × N integrations, and most were never built. The Model Context Protocol (MCP), published by Anthropic in November 2024, turns this into M + N. A service exposes one MCP server, and any MCP-capable application (Claude, ChatGPT, Gemini, Cursor, VS Code, Microsoft Copilot, coding agents) can discover its tools and call them. By December 2025 there were more than 10,000 published MCP servers, and by July 2026 the main SDKs had close to half a billion downloads a month.
MCP stands on the AI agents concept (L1). An agent is a loop: the model reads the context, chooses a tool call, the application runs it, and the result goes back to the model. That loop needs tools that are described precisely, called reliably and authorized safely. MCP standardizes exactly that edge of the loop (discovery, invocation, results, errors, authorization) and leaves the loop, the model and the prompts to the application. The layer above it on this map is coding agents such as Claude Code and Codex, which reach GitHub, databases, browsers and internal services through this one protocol.
In December 2025 Anthropic gave MCP to the Agentic AI Foundation under the Linux Foundation, so no single vendor controls it. The current revision, dated 2026-07-28, made the protocol stateless, which changes how servers are built and deployed.
terms: Host — the AI application the user runs (chat app, IDE, coding agent); it owns the model and decides what enters its context.
Client — the connector inside the host that talks to one server.
Server — a program or service that exposes tools, resources or prompts over MCP.
Tool — a function the model may ask to run, described by a name, a description and a JSON Schema for its input.
Resource — read-only data identified by a URI (a file, a table, a document) that the application can put into context.
JSON-RPC 2.0 — a small standard for remote calls: a request has an id, a method and params; the reply has the same id and a result or an error.
Transport — how messages travel: stdio (a local subprocess) or Streamable HTTP (a remote endpoint).
Elicitation — a server asking the user, through the host, for more information or a confirmation.
Multi round-trip request (MRTR) — the 2026 pattern in which a server answers "input required" and the client retries the same request with that input.
history: MCP was announced on 25 November 2024. It was designed at Anthropic by David Soria Parra and Justin Spahr-Summers, who took the idea from the Language Server Protocol (LSP). Microsoft created LSP in 2016 for the same M × N problem between code editors and programming languages: each language ships one language server, and every editor can use it. MCP copied its choices: JSON-RPC messages, declared capabilities, and local servers started as subprocesses. The first revision (2024-11-05) defined tools, resources and prompts on the server side, sampling and roots on the client side, and stdio and HTTP transports.
Adoption came fast in 2025. The 2025-03-26 revision added OAuth 2.1 authorization for remote servers, the Streamable HTTP transport, and tool annotations such as readOnlyHint and destructiveHint. OpenAI adopted MCP in March 2025 and Google DeepMind in April. That April, Invariant Labs described "tool poisoning" (hidden instructions in tool descriptions), and security became a central topic. The 2025-06-18 revision added structured tool output, elicitation and token resource indicators. An official server registry opened in preview in September 2025. The 2025-11-25 revision added URL-mode elicitation, experimental long-running tasks and Client ID Metadata Documents for client registration. On 9 December 2025 MCP became a founding project of the Agentic AI Foundation, with Block's goose and OpenAI's AGENTS.md.
The 2026-07-28 revision answered the main operational complaint. Earlier versions opened a session with an initialize handshake and kept per-connection state, so a remote server needed sticky load balancing or shared session storage. The new revision removed sessions and the handshake, replaced server-initiated requests with multi round-trip requests, deprecated sampling, roots and logging, and moved tasks into an optional extension.
how: There are three roles. The host is the application, and it creates one client per server. A server may be a local process (a filesystem or database tool) or a remote service. The model never talks to a server directly: the host asks each server what it offers, decides what the model sees, asks the user for approval when needed, and sends the calls. This separation is the protocol's main safety boundary.
Every message is JSON-RPC 2.0 in UTF-8. A request has an id, a method such as tools/call, and params; the response carries the same id and a result or an error; a notification has no id. In the stdio transport the host starts the server as a subprocess and exchanges newline-delimited JSON over standard input and output, with logs on standard error. In Streamable HTTP each client message is a POST to one endpoint, and the reply is a single JSON object or a short server-sent-events stream that carries progress and then the result. The POST also carries the headers Mcp-Method and Mcp-Name, copied from the body, so gateways can route, rate-limit and log without parsing JSON.
Since 2026-07-28 every request is self-contained. Its _meta field carries the protocol version, the client's capabilities and its identity. A normal result has resultType "complete"; a version mismatch returns an UnsupportedProtocolVersion error, and a client may call server/discover first to learn what the server supports. Because no request depends on an earlier one, any server instance behind a plain load balancer can handle any request. A server that needs state across calls, such as a browser session or a shopping basket, returns an explicit handle (for example "bsk_a1b2c3") from one tool, and the model passes it to the next tool.
Servers offer three kinds of things. Tools are controlled by the model. tools/list returns each tool's name, description, inputSchema (JSON Schema 2020-12), and optional outputSchema and annotations. The list also carries ttlMs and cacheScope so clients can cache it, and servers should keep its order stable so the model provider's prompt cache keeps hitting. tools/call returns content blocks (text, image, audio, resource links, embedded resources), optional structuredContent matching the output schema, and isError. An error inside the tool, such as a badly formatted date, is a normal result with isError: true, so the model can read it and retry; a malformed request is a JSON-RPC protocol error instead. Resources are controlled by the application: data addressed by URIs and read with resources/read. Prompts are controlled by the user: templates the host can offer as slash commands.
Sometimes a server needs something from the user in the middle of a call. In the 2026 revision the server does not send its own request back. It answers the call with resultType "input_required", a map of inputRequests (for example an elicitation form described by a JSON Schema), and an opaque requestState. The host shows the form, then retries the same call with a new JSON-RPC id, the user's inputResponses and the same requestState. The server keeps no memory between the two calls. Because requestState passes through the client, the server must protect it with a MAC or authenticated encryption and give it a short expiry. URL-mode elicitation sends the user to a web page instead, for OAuth consent or payment, so secrets never pass through the host or the model.
Remote servers use OAuth 2.1. The server is a resource server: a request without a valid token gets 401 and a pointer to protected-resource metadata (RFC 9728), which names the authorization server. The client identifies itself with a Client ID Metadata Document (a URL that describes the client), runs the authorization-code flow with PKCE, and asks for a token bound to this server with a resource indicator (RFC 8707), so a malicious server cannot replay the user's token elsewhere. Change notifications such as "the tool list changed" travel on one opt-in subscriptions/listen stream; progress travels on the stream of its request. Optional extensions add long-running tasks (start a job, then poll tasks/get) and MCP Apps (interactive UI inside the conversation).
Inside the agent loop the pieces fit like this. At start-up the host lists tools from every server and converts them into the model provider's tool format, often prefixing names with the server name to avoid clashes. When the model emits a tool call, the host maps it back to the right client, applies its approval policy, sends tools/call, and appends the result as the tool's answer. The agent concept supplies the loop; MCP supplies a standard, discoverable, authorized way to fill its "tools" slot.

example: A developer's coding agent is connected to two MCP servers: a local Postgres server over stdio with 3 tools, and a remote code-hosting server over Streamable HTTP with 35 tools. Anthropic measured that a code-hosting server of this size costs about 26,000 tokens of tool definitions, and a five-server setup with 58 tools about 55,000 tokens. Assume our two servers cost 28,000 tokens, and input costs $3 per million tokens.
Without caching, each model call resends the 28,000 definition tokens: 28,000 × $3 / 1,000,000 = $0.084. A session with 20 model calls spends 20 × $0.084 = $1.68 on definitions alone. With prompt caching, where cached tokens cost about a tenth of the normal price, the session costs about $0.17, but only if the tool list is byte-for-byte the same in every call. That is why the 2026 spec asks servers to keep the order stable. Loading only the tools a task needs (tool search) cut Anthropic's 77,000-token example to about 8,700 tokens.
Now one call. The user asks "How many users signed up yesterday?" The model calls postgres__query with a SQL count. The host strips the prefix, treats the tool as read-only by its own policy (not by trusting the server's annotation), and writes one line to the subprocess: {"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"query","arguments":{…},"_meta":{…}}}. The server runs the query in 40 ms and writes back {"jsonrpc":"2.0","id":7,"result":{"resultType":"complete","content":[{"type":"text","text":"count: 1824"}],"isError":false}}. The local round trip adds well under a millisecond, and the model answers "1,824 sign-ups."
Next the user says "Merge pull request 912." The model calls merge_pr on the remote server. The POST carries the user's OAuth token and the headers Mcp-Method: tools/call and Mcp-Name: merge_pr. The server needs a choice, so it answers request 8 with resultType "input_required", an elicitation form "Merge method: squash or rebase?", and a requestState that is a signed blob holding the PR number, the user's identity and a 5-minute expiry. The user picks "squash". The host sends request 9: the same tool and arguments, plus inputResponses and the same requestState. A different server instance receives it, checks the signature and expiry, merges, and returns a complete result. If the network had lost request 9, the client would resend it with a new id, so the merge must be idempotent.
intuition: MCP is USB for AI tools: one plug shape, many devices, and the computer (the host) decides which device may do what.
The design is natural because it copies a solution that already worked. LSP showed that a small, typed request/response protocol with declared capabilities lets many editors share many language tools without knowing each other. MCP applies that idea to models and services. Its second insight is about control: the model holds no credentials and opens no connections. The host stands in between, so consent, approval and logging have one natural home. The 2026 move to stateless requests follows the lesson of HTTP: if each request carries everything needed to serve it, servers scale behind ordinary load balancers and failures are handled by retrying.
mistakes: People often think MCP makes a model call tools. In fact it is only a wire protocol between a host and servers. The host and model still run the agent loop and decide which tools to expose; tool calling is a model feature that existed before MCP.
People often think tool annotations such as readOnlyHint are a security guarantee. In fact the specification says clients must treat annotations as untrusted unless the server is trusted. A malicious server can label a destructive tool as read-only, so policy must live in the host.
People often think connecting more servers makes an agent more capable. In fact every tool definition uses context on every call, and models choose tools less accurately as lists grow. Ten well-chosen tools often beat fifty.
People often think an MCP server should mirror a REST API one endpoint per tool. In fact good servers are designed for a model: fewer, higher-level tools, descriptions that say when to use them, small results and error messages the model can act on.
friction: Security is the hardest problem. Tool results and descriptions are text that the model reads, so they can carry prompt injections. Simon Willison's "lethal trifecta" names the dangerous mix: access to private data, exposure to untrusted content, and a way to send data out. An agent with all three can be made to leak secrets by a poisoned web page or issue comment. Local stdio servers run with the user's permissions, and real vulnerabilities followed; CVE-2025-6514 in the mcp-remote package (CVSS 9.6, July 2025) let a malicious server run commands on the user's machine. In May 2026 the US National Security Agency published MCP security guidance, warning that gaps in design, implementation and operations had created "significant and evolving security concerns".
The protocol has also changed quickly: five revisions in under two years, and 2026-07-28 broke compatibility with the session-based design. Sampling, roots and logging are deprecated with a 12-month window, so 2025-era servers and clients must be updated. Stateless servers must authorize every handle on every call, and a broken HTTP stream now loses the in-flight request, which must be retried.
Context cost and quality remain open. Tool definitions can fill a quarter of a 200,000-token window, and the fixes (tool search, or having the model write code that calls tools, which Anthropic reported cut one task from 150,000 to 2,000 tokens) add complexity. Among more than 10,000 public servers, quality and maintenance vary widely.
practice: When you build a server, design tools around tasks, not endpoints, and say in each description when to use the tool and what it returns. Return small results, add outputSchema and structuredContent for data, and report recoverable problems with isError. Keep tools/list stable and set ttlMs. Use the official SDKs (the Python mcp package reached 2.x in 2026), target the 2026-07-28 revision, use explicit handles for state, and sign and expire every requestState. Choose stdio for tools that touch the local machine and Streamable HTTP with OAuth for shared services.
When you deploy servers for a team, keep an allow-list of approved servers and pin versions. Run local servers in containers or sandboxes with least privilege and scoped tokens. Require human approval for writes, deletions, payments and outbound messages, based on the host's own policy. Do not give one agent private data, untrusted content and an outbound channel at the same time. Put remote servers behind a gateway that uses the Mcp-Method and Mcp-Name headers for routing, rate limits and audit logs.
For the model's sake, connect only the servers a task needs, turn on prompt caching, and use tool search or deferred loading once you pass a few dozen tools. Test servers with the MCP Inspector, and keep it updated: old versions had a remote-code-execution flaw (CVE-2025-49596).
quiz: What are the three server primitives in MCP, and who controls each? || Tools are controlled by the model, which decides to call them. Resources are controlled by the application, which decides what data to load into context. Prompts are controlled by the user, who picks them, often as commands.
Why did the 2026-07-28 revision remove sessions and the initialize handshake? || Session state forced remote servers to use sticky load balancing or shared session storage. Now each request carries its version and capabilities in _meta, so any instance behind a plain load balancer can serve it, and failures are handled by retries.
How does a server ask the user a question in the middle of a tool call under the 2026 revision? || It returns resultType "input_required" with inputRequests (for example an elicitation form) and an integrity-protected requestState. The client asks the user and retries the same call with a new id, the inputResponses and the same requestState, so the server needs no memory between calls.
Your agent loads 40,000 tokens of tool definitions and makes 25 model calls at $3 per million input tokens. What do the definitions cost without caching and with a cache priced at one tenth? || Without caching, 25 × 40,000 × $3 / 1,000,000 = $3.00. With caching, about $0.30, provided the tool list stays byte-identical so the cache keeps hitting.
Why should an agent that reads untrusted web pages not also have private files and an email tool? || That is the "lethal trifecta": injected text in a page can tell the model to read private data and send it out. Removing any one of the three, or requiring human approval for the outbound step, breaks the attack.

@@ mlflow
value: Training a machine-learning model is a search. A data scientist tries dozens or hundreds of runs with different data, features, code and settings, and keeps a few. Weeks later someone asks: which data and which code produced the model in production, and was it really better than the last one? Without a record, nobody knows. Then the model must be packaged so a serving system, a batch job or another team can load it without the training notebook. MLflow is an open-source tool for exactly these jobs. It records every run (parameters, metrics, files, code version), saves models in a standard package, keeps a registry of model versions with named pointers such as "champion", and, since 2024, records traces and evaluations of LLM applications and agents.
Databricks created MLflow in 2018, and it is now a Linux Foundation project. The main Python package had about 20 million downloads in the 30 days before October 2026 and about 1.2 billion in total (PyPI statistics). On Databricks it is built in, with the model registry stored in Unity Catalog, but the open-source server runs anywhere, and other platforms such as Amazon SageMaker offer managed versions.
It stands on MLOps (L1). MLOps is the discipline of running ML like software: reproducible training, versioned artifacts, gated promotion to production, and monitoring. MLOps says what must be recorded and controlled; MLflow supplies the records, the package format and the registry that make those practices possible. It does not train models or schedule pipelines. Training libraries, orchestrators (Airflow, Databricks Jobs) and CI systems do that and call MLflow along the way. Its neighbour Feast covers the other half of the data a model needs: features, rather than models.
terms: Experiment — a named group of runs for one problem, such as "ctr-model".
Run — one execution of training or evaluation code, with its parameters, metrics, tags and artifacts.
Artifact — any file a run produces: a model, a plot, a data sample, a report.
Backend store — the database (PostgreSQL, MySQL, SQLite or MSSQL) that holds experiments, runs, metrics and registry records.
Artifact store — object storage (S3, ADLS, GCS) or a directory that holds artifact files.
Flavor — a way to save and load a model for one library (sklearn, pytorch, xgboost, transformers, langchain…).
pyfunc — the generic python_function flavor: any MLflow Python model can be loaded through it and called with predict().
Signature — the declared schema of a model's inputs and outputs, checked when the model is called.
Alias — a movable, named pointer to one version of a registered model, such as @champion.
Trace — the record of one request to an LLM application: a tree of spans with inputs, outputs, latency and token counts.
history: Matei Zaharia (the creator of Apache Spark) and Cyrielle Simeone announced MLflow on 5 June 2018 as an alpha release. The post named four problems: too many tools, experiments that are hard to track, results that are hard to reproduce, and models that are hard to deploy. Large companies had already built internal platforms for this, such as Uber's Michelangelo, Facebook's FBLearner and Google's TFX. Those platforms worked only with each company's own tools. MLflow's bet was an "open interface" design: a library that works with any ML library, any language through a REST API, and any cloud. Version 0.1 had three parts: Tracking, Projects (a format for reproducible code runs) and Models (a package format with flavors).
Version 1.0 followed in June 2019, and the Model Registry arrived with version 1.4 in October 2019, adding named, versioned models with an approval workflow. MLflow moved to the Linux Foundation in 2020. Version 2.0 (November 2022) cleaned up the APIs. As large language models spread, MLflow added flavors for transformers, OpenAI and LangChain, LLM evaluation, a gateway for model APIs, and tracing (version 2.14, June 2024). The registry's fixed stages (Staging, Production, Archived) gave way to flexible aliases and tags, and stages are now deprecated.
MLflow 3.0 (June 2025) shifted the centre from runs to models and GenAI. It added the LoggedModel, a first-class model record that links checkpoints, traces, prompts and evaluation results, plus a GenAI evaluation suite with LLM judges and a prompt registry. Releases in 2026 came about monthly: multiple workspaces (3.10), gateway budgets and pickle-free models (3.11), role-based access control (3.13), an MCP server registry (3.15) and resource permissions (3.17). As of October 2026 the current release is 3.17.
how: Tracking starts in the training code. mlflow.start_run() opens a run; log_param records a setting, log_metric(key, value, step) records a number at a training step, and log_artifact uploads a file. Autologging (for example mlflow.sklearn.autolog()) patches a library's fit function so that parameters, metrics and the model are logged without extra code. The client talks to a tracking server, a FastAPI service that exposes a REST API and the web UI. The server writes small structured records to the backend store. Metrics, for example, are rows of (run, key, value, timestamp, step). Large files go to the artifact store under a path per experiment and run. The server can proxy artifact uploads, so laptops and training jobs need no cloud credentials of their own. With no configuration at all, the client writes everything to a local mlruns directory, which suits one person but not a team.
Because runs are rows in a database, they can be searched. A filter such as "metrics.auc > 0.78 and params.max_depth = '8'" finds candidate runs, and the UI plots metrics across runs to compare them. Each run also records tags such as the Git commit, the source file and the user. You can log the training dataset as an input (for example a Delta table name and version), which turns "which data was this?" into a lookup instead of a guess.
MLflow Models is the package format. A model is a directory with an MLmodel file (YAML) at its root. The file lists the flavors the model supports, for example sklearn (how to load the pickled estimator) and python_function (how to load it through the generic interface). It also stores the signature (input and output schema), an input example, and environment files (requirements.txt, conda.yaml, python_env.yaml) for rebuilding the Python environment. Any tool that understands pyfunc can load any flavor and call predict(model_input). This is how one package serves many targets. mlflow models serve exposes a REST /invocations endpoint, a build command produces a Docker image, and mlflow.pyfunc.spark_udf turns the model into a Spark function for scoring billions of rows in batch. Most flavors save weights with pickle. Loading a pickle can run arbitrary code, so "models from code" (a Python file that defines the model) and newer pickle-free formats exist for safety.
The Model Registry adds names and versions on top. Registering a model under a name such as ctr-model creates version 1, then 2, and so on, each linked to the run or LoggedModel that produced it. Aliases are movable pointers: models:/ctr-model@champion resolves to whatever version "champion" points to now. Promotion means moving the alias, and rollback means moving it back; both are one API call, and serving code that loads by alias does not change. Tags record status such as validation_status=approved. Since MLflow 3, a LoggedModel record sits between runs and the registry: one model, such as an agent version or a training checkpoint, can collect metrics from many evaluation runs and traces from production, instead of belonging to the single run that created it. On Databricks the registry lives in Unity Catalog with three-level names (catalog.schema.model), so access control and lineage are shared with the tables the model was trained on.
For LLM applications, MLflow keeps the same records but for requests rather than training runs. Tracing is compatible with OpenTelemetry. Autologging for OpenAI, Anthropic, LangChain, LlamaIndex, DSPy and others, or the @mlflow.trace decorator, records each request as a tree of spans: the retrieval step, each model call with its prompt, tokens and latency, and each tool call. In production a lightweight mlflow-tracing package (about 95% smaller than the full package) logs asynchronously and can sample traces. Evaluation runs mlflow.genai.evaluate over a dataset of inputs and expectations, a predict function and scorers. Scorers can be plain code (exact match) or LLM judges such as Correctness and Guidelines. The results are logged as a run, so evaluations are compared exactly like training runs. A prompt registry versions prompts with aliases, the same way models are versioned.
Put together, MLflow implements the record-keeping half of MLOps. Every model in production can be traced back through an alias to a version, a run, a commit, a dataset version and its metrics. The other half, automation, comes from elsewhere: a CI job or orchestrator decides when to train, checks the metrics, and moves the alias.

example: An ad-tech team trains a click-through-rate (CTR) model with gradient-boosted trees. They run a grid search over 4 values of max_depth, 3 learning rates and 2 feature sets: 4 × 3 × 2 = 24 runs in the experiment "ctr-model". Each run logs 6 parameters, plus 2 metrics (validation log-loss and AUC) at each of 300 boosting rounds, so 2 × 300 = 600 metric rows per run and 24 × 600 = 14,400 rows in total. At roughly 100 bytes per row that is about 1.4 MB in Postgres, which is trivial. Each run also saves a 40 MB model, so the artifact store grows by 24 × 40 = 960 MB, which is why artifacts live in S3 and not in the database.
Logging cost matters too. If every metric value were a separate REST call of about 20 ms, one run would spend 600 × 20 ms = 12 s just logging. Logging both metrics of a step in one batch call halves that to 300 calls, or 6 s, and asynchronous logging takes it almost entirely off the training path.
A search for "metrics.auc > 0.775" ordered by AUC returns the best run: max_depth 8, learning rate 0.05, feature set B, AUC 0.781. The team registers its model as version 7 of ctr. The current @champion is version 6, which scored 0.774 on the same frozen hold-out set. Their CI rule says: promote if AUC improves by at least 0.005 and the p99 prediction latency stays under 10 ms. 0.781 − 0.774 = 0.007, which passes, and a latency test measures 6 ms. The CI job moves @champion from version 6 to version 7. The serving fleet loads models:/ctr@champion when it starts or refreshes, so it picks up version 7 with no code change.
Two days later, a dashboard shows that predicted CTR has drifted 15% above observed CTR for one device type. The on-call engineer moves @champion back to version 6 with one call, and the serving fleet reloads the old model. Then the team investigates. Version 7 links to run 3f2a, which records Git commit a91c, input table ads.impressions at Delta version 4412, and feature set B. Comparing it with run 1b77 (version 6) shows that feature set B added a feature computed differently for that device type. Without these records, the same investigation would start with guessing.
intuition: MLflow is a lab notebook that writes itself, plus a release desk that hands out models by name.
The design is natural because it separates what changes at different speeds. Metadata is small and queried often, so it goes in a database. Artifacts are large and written once, so they go in object storage. Models must outlive the code that made them, so they are packaged with a description of how to load them (flavors) and one common calling convention (pyfunc). Deployment needs a stable name while the thing behind it changes, so the registry uses aliases, the same idea as a DNS name or a Git branch pointing at a commit. Each part is simple; the value comes from the links between them, which let you walk from a production prediction back to the exact code, data and settings.
mistakes: People often think MLflow trains or orchestrates models. In fact it only records, packages and names them. Training happens in your libraries, and scheduling happens in an orchestrator or CI system that calls MLflow.
People often think a logged model is automatically reproducible. In fact MLflow records the Git commit and the Python environment, but not the data unless you log it. If the training table changes underneath you, the same code gives a different model. Log dataset versions, for example Delta table versions, as run inputs.
People often think the registry deploys models. In fact it only stores versions and aliases. A serving system (Databricks Model Serving, SageMaker, Kubernetes, your own service) must load the model by alias and refresh when the alias moves.
People often think it is safe to load any MLflow model. In fact most flavors use pickle, and unpickling can run arbitrary code. Load only models from trusted sources, and prefer models-from-code or pickle-free formats where possible.
friction: The open-source tracking server needs care at scale. A large organization can accumulate millions of runs and hundreds of millions of metric rows, and searches and UI pages slow down unless the database is sized, indexed and cleaned. Deleted runs stay until you run mlflow gc. Access control was weak for years: role-based access control arrived only in version 3.13 (2026), and multi-workspace support in 3.10. Before that, large companies often ran many separate servers or relied on Databricks.
Reproducing environments is imperfect. A requirements file does not capture CUDA versions, system libraries or wheels built for one platform, so a model logged on a GPU cluster may not load on a different serving image. Pickled models also break when library versions change.
pyfunc is convenient but adds overhead. Inputs are often converted to pandas DataFrames, which can cost milliseconds per call. Low-latency services frequently load the native flavor or export to a format such as ONNX instead.
For GenAI, tracing every request produces large volumes of data, so sampling and retention need decisions. LLM judges cost money and can disagree with humans, so they must be checked against human labels. Finally, some features have arrived first, or only, in managed MLflow on Databricks, so the open-source and managed versions do not always match.
practice: From the first day of a team project, point MLFLOW_TRACKING_URI at a shared server backed by Postgres and an object store, not at a local mlruns folder. Use one experiment per problem and consistent tag names (team, dataset, purpose). Turn on autologging, then add the metrics your business cares about, such as calibration error or revenue per thousand impressions.
Log what makes a run reproducible: the Git commit (automatic for scripts in a repository), dataset names and versions as inputs, and random seeds. Always log a signature and an input example with each model, so callers get clear schema errors instead of silent mistakes. Batch metric logging in tight training loops.
Use aliases, not stages, and let automation move them. A CI job should compare a candidate against the current @champion on the same frozen evaluation set and promote only when explicit thresholds pass. Keep rollback to a single alias move, and make serving reload on alias change. On Databricks, register models in Unity Catalog so the permissions and lineage of tables and models live together.
For LLM applications, add tracing early with autologging, use the lightweight tracing package and sampling in production, and build an evaluation dataset from real traces. Check LLM-judge scores against a sample of human labels before they gate releases. Schedule mlflow gc and database maintenance.
quiz: What are the backend store and the artifact store, and why are they separate? || The backend store is a database for small, structured, frequently queried records (runs, parameters, metrics, registry entries). The artifact store is object storage for large files written once (models, plots). Each data type goes where it is cheap and efficient.
How does the pyfunc flavor let one model package serve many deployment targets? || Every MLflow Python model can be loaded as python_function and called with predict(model_input), whatever library trained it. Serving tools, Docker builds and Spark UDFs only need to understand this one interface, plus the signature and environment files in the MLmodel package.
Why are aliases better than hard-coded version numbers in serving code? || Serving loads models:/name@champion, and promotion or rollback is one atomic move of the alias. The serving code never changes, and the registry records which version was champion at each time.
A run logs 3 metrics for 200 steps, one REST call per value at 15 ms each. How long does logging take, and how much with one batch call per step? || 3 × 200 = 600 calls × 15 ms = 9 s. With one batch call per step, 200 calls × 15 ms = 3 s, and asynchronous logging removes most of it from the training path.
When would you not use pyfunc to serve a model in production? || When latency is tight (for example a p99 of a few milliseconds in ad serving), because input conversion to DataFrames adds overhead. Then load the native flavor directly or export to an optimized format such as ONNX, and keep MLflow for tracking and versioning.

@@ feast
value: A model is only as good as the inputs it sees, and in production two copies of the same inputs often disagree. During training, a data scientist computes a feature such as "clicks by this device in the last 7 days" with a SQL query over the warehouse. At serving time, an engineer recomputes it in a Java service from a cache. The two versions differ slightly in windows, time zones or null handling, and the model loses accuracy for reasons nobody can see. This is training-serving skew. A second trap is leakage: if a training row is joined to the latest feature value instead of the value known at that moment, the model learns from the future and looks better offline than it will ever be online.
Feast is an open-source feature store that fixes both problems by defining each feature once and serving it two ways. Offline, it builds training sets with point-in-time correct joins over a warehouse or lakehouse. Online, it serves the latest values from a low-latency key-value store. Gojek and Google Cloud released it in January 2019. It is now a Linux Foundation AI & Data project; companies such as Affirm, Robinhood, Shopify and Cloudflare have adopted it or contributed to it, and it joined the PyTorch ecosystem in January 2026.
It stands on the feature store concept (L1), which defines the pattern: a registry of shared feature definitions, an offline store for history, an online store for the latest values, and point-in-time correctness between them. Feast is one implementation, with a particular choice: it is not a database. It reuses the systems you already run (BigQuery, Snowflake, Spark, Redis, DynamoDB, Postgres) and adds definitions, join logic, materialization jobs and a serving API on top. For the layer above (recommendation, ads ranking, fraud and, more recently, retrieval for LLM applications), it provides one name for each feature and the same value logic in training and in serving.
terms: Entity — the object a feature describes, identified by a join key such as device_id or driver_id.
Feature view — a named group of features from one data source, with its entity, schema and time-to-live.
Event timestamp — the time at which a feature value became true; it drives every point-in-time join.
TTL (time-to-live) — the maximum age of a feature value that a join may still use.
Entity dataframe — the list of (entity key, timestamp) rows, usually training events with labels, for which features are fetched.
Offline store — the system that holds feature history and runs training-set joins (BigQuery, Snowflake, Spark, DuckDB…).
Online store — a key-value store that holds only the latest value per entity (Redis, DynamoDB, Postgres…).
Materialization — the job that copies the latest feature values from the offline store into the online store.
Registry — the stored catalogue of all feature definitions, written by feast apply.
history: Feast started in 2018 at Gojek, the Indonesian ride-hailing and payments company, together with Google Cloud. Gojek's many ML teams kept rebuilding the same features in different ways. Willem Pienaar, who led Gojek's data science platform, and Tim Sell of Google announced the open-source project on 19 January 2019. The idea was not new. Uber had described Michelangelo, its internal ML platform with a shared feature store, in 2017, and other large companies had similar internal systems. Feast made the pattern available to everyone. The first version was built for Kubeflow and used Apache Beam to write batch and streaming data into both a warehouse and a serving store.
That first design ran many services on Kubernetes, which made it hard to adopt. Feast 0.10 (April 2021) rewrote it as a lightweight Python SDK and CLI. Definitions became Python files, a feature_store.yaml file selected the offline and online stores, feast apply registered the definitions, and materialization became a command or scheduled job. Most later growth came from pluggable connectors contributed by data vendors.
The project joined the Linux Foundation's AI foundation in 2020 for neutral governance. Tecton, a commercial feature-store company founded by Michelangelo's creators, was for years its biggest contributor. In February 2024 a new group of maintainers from Red Hat, Affirm and J.P. Morgan took over day-to-day leadership with a goal of reaching version 1.0 and integrating closely with Kubeflow. Since then Feast has added role-based access control (November 2024), vector search for retrieval-augmented generation (2025), a Kubernetes operator, on-demand and streaming transformations, and many new stores. Versions arrive roughly monthly; 0.67 was released in October 2026, still before 1.0, and requires Python 3.10 or newer.
how: You describe features in Python. An Entity names the join key (device_id). A data source points at a table or files and names its timestamp_field, the event timestamp, and optionally a created_timestamp column that records when a row was written. A FeatureView ties these together. It lists the entity, the feature columns with types, the source, a TTL, and online=True if the features should be served. A FeatureService groups the features one model uses, so the model asks for "ctr_model_v3" instead of a list of columns. feast apply validates the definitions and writes them to the registry, a file in object storage or a SQL database, which every training job and server reads.
Training sets come from get_historical_features(entity_df, features). The entity dataframe holds the training events: entity key, event time, and the label. For each row, Feast must find, in every feature view, the newest feature row for that entity whose event timestamp is not after the event time and not older than the TTL. The offline store does this in SQL that Feast generates for BigQuery, Snowflake, Spark and others. Logically, it joins on the entity key, keeps feature rows with feature_ts ≤ event_ts and feature_ts > event_ts − TTL, ranks them by feature_ts (and created_ts to break ties) in descending order, and keeps rank 1. This is an "as-of" join. If no feature row qualifies, the feature is null. A null tells the model "unknown", which is far better than silently copying a value from the future.
The created timestamp matters for backfills. If a bug fix rewrites last month's features today, the new rows carry old event timestamps but today's created timestamp. With filter_by_created_timestamp=True, Feast also requires created_ts ≤ event_ts. A backfilled value that did not exist at that moment then cannot leak into training.
Serving needs the opposite shape: only the latest value per entity, in milliseconds. feast materialize (or materialize-incremental, which continues from the last run) reads, for each entity key, the newest row within the time range from the offline store, and writes it into the online store. There, each entity key maps to its current feature values plus their event timestamps. The work is done by a compute engine: in-process by default, or Spark, Ray or cloud jobs for large tables. At prediction time the service calls get_online_features(feature_service, entity_rows), through the SDK or the HTTP feature server, and gets one value per feature per entity. Values older than the TTL come back as null, which is the same rule the training join applies.
Consistency comes from this symmetry. Training asks "what was the latest value no older than the TTL at time t?" for each historical t. Serving asks the same question for t = now. Both answers come from the same feature view definition over the same source table, so a model sees features computed by one piece of logic. The remaining gap is freshness: online values are only as new as the last materialization. The registry is read by every client and server and cached for a configurable time, so a new feature definition reaches running servers after that cache expires.
For fresher features, a PushSource lets a stream job (Flink, Spark Streaming, a Kafka consumer) push new values directly into the online store, and optionally into the offline store, within seconds. On-demand feature views compute features at request time from request data and stored features, for example "distance between the user's current location and the store". The same Python function runs while building the training set and while serving, so the logic is not written twice. For LLM applications, some online stores (such as Postgres with pgvector, Milvus or Elasticsearch) can also store embeddings and answer similarity searches, so one system supplies both structured features and retrieved documents.
Performance comes mostly from the online store and the serving path. A Redis lookup inside the same cluster takes well under a millisecond. In a June 2026 benchmark, the Feast team brought the Python feature server's p99 latency under 5 ms for single-row requests by tuning workers and connection pools, and under 2 ms by storing pre-computed feature vectors. Version 0.64 added data-quality monitoring, and permissions now cover who may read or change each feature view.

example: An ad platform predicts clicks per device. A daily job writes the feature view device_stats with features clicks_7d and impr_7d, entity device_id, and TTL = 2 days. For device d42 the offline table holds four rows (event timestamps at midnight UTC, written by the job at 02:00):
2026-03-01 00:00: clicks_7d = 3, impr_7d = 400. 2026-03-02 00:00: 5 and 420. 2026-03-03 00:00: 9 and 450. 2026-03-08 00:00: 2 and 300.
The entity dataframe holds three ad impressions for d42, with labels. Event A is at 2026-03-02 15:30. The newest row not after 15:30 is 03-02 00:00, which is 15.5 hours old, inside the 48-hour TTL, so A gets clicks_7d = 5 and impr_7d = 420, a recent click rate of 5 / 420 ≈ 1.19%. Event B is at 2026-03-03 09:10. It gets the 03-03 row, 9 and 450, a rate of 2.0%. Event C is at 2026-03-06 12:00. The newest row not after it is 03-03 00:00, which is 3.5 days old, beyond the TTL, so both features are null.
Compare a naive join on device_id that takes the latest row. All three events would get the 03-08 row (2 and 300), values from days in the future. For C, the model would learn that a device with few recent clicks did or did not click on 6 March, using data that did not exist yet. Offline metrics look good, and production disappoints.
There is a subtler leak too. The 03-03 row has an event timestamp of 00:00, but the job wrote it at 02:00. An impression at 01:00 on 03-03 would receive the 03-03 row in training, while in production at 01:00 that row would not yet be in the online store. Setting the created timestamp and filter_by_created_timestamp=True, or stamping rows with the time they became available, closes that gap.
Now serving. materialize-incremental runs at 03:00 each day. On 2026-03-08 it writes d42 → (2, 300, 03-08 00:00) into Redis. A request at 10:00 reads those values; they are 10 hours old and inside the TTL, which matches the training rule.
Finally, sizing. Suppose 200 million active devices, with 10 numeric features each. The raw values take 200,000,000 × 10 × 8 bytes = 16 GB. With keys, timestamps and Redis overhead, plan for about 2 to 3 times that, roughly 40 GB of memory. A daily materialization writes 200 million rows; at 100,000 writes per second it takes 2,000 s, about 33 minutes. A ranking request that scores 1 device against 50 candidate ads reads 51 keys in one pipelined call, typically about 1 ms inside the same data centre.
intuition: A feature store is a time machine with one rule: whenever you ask for a value, as of training time or as of now, you get what was known at that moment and nothing later.
The design is natural once you see that training and serving ask the same question at different times. Training asks it for millions of past moments at once, which is a large join, the kind of work warehouses are good at. Serving asks it for one moment, now, under a strict latency budget, which is a key lookup, the kind of work key-value stores are good at. Feast keeps one definition of the question and lets each kind of system answer the shape it is good at. Materialization is just a precomputed answer to the serving version of the question. The TTL makes both answers forget stale values by the same rule.
mistakes: People often think a feature store computes features. In fact Feast mainly stores, joins and serves features that your pipelines (SQL, Spark, dbt, Flink) compute. On-demand and streaming transformations exist, but most heavy computation stays in your existing data platform.
People often think "point-in-time correct" means "use the latest data". In fact it means each training row uses only values known at that row's time. That usually makes offline metrics lower, and more honest.
People often think the online and offline values are always identical. In fact the online store is only as fresh as the last materialization or push. If materialization runs daily, a model in production sees values up to a day older than training assumed, unless training simulates that lag.
People often think TTL is a cache expiry for the online store only. In fact the same TTL also limits the historical join. Set it too short and many training rows get nulls; set it too long and the model treats stale values as current.
friction: Freshness costs money and complexity. Daily batch materialization is simple but stale. Hourly runs cost more compute and load the online store. Seconds-level freshness needs a streaming pipeline that pushes values, and that pipeline must compute exactly what the batch definition computes, or skew returns through the back door.
Point-in-time joins are expensive at scale. A training set with 1 billion events joined against several feature views, each with long histories, means large sorts or window functions in the warehouse. Teams often pre-aggregate, restrict date ranges or partition carefully to keep cost and time reasonable.
Online stores are expensive for large entity counts. Hundreds of millions of keys in Redis means tens of gigabytes of memory per replica. DynamoDB or Cassandra are cheaper per gigabyte but have higher tail latency. Write bursts during materialization can also hurt read latency for live traffic.
Feast is a framework, not a managed service, so you operate the registry, the jobs, the feature server and the stores. It is still before 1.0, connectors differ in maturity, and some features (streaming transformations, vector search) are alpha or beta. Teams on Databricks or a cloud ML platform often use the built-in feature store instead and accept vendor lock-in for less operational work.
practice: Start with one or two models that clearly suffer from skew or duplicated feature code, not with a company-wide catalogue. Define entities and feature views in a Git repository, run feast apply from CI, and review feature changes like code changes.
Get timestamps right first. Every source needs an event timestamp that means "when this value became true or known". Add a created timestamp if you ever backfill. Choose TTLs from how often each feature is refreshed, for example twice the refresh interval, and check the null rate in training sets. A sudden jump in nulls usually means a broken pipeline or a TTL that is too short.
Match freshness to need. Use daily materialization for slow features such as 30-day aggregates, and push sources for features that change within a session. Simulate the serving lag in training when it matters. Use FeatureServices so each model version names its exact feature set, and record that name in the model's MLflow run for lineage.
For serving, use Redis or a similar in-memory store for p99 targets of a few milliseconds. Batch lookups for all candidates in one call, and tune the feature server's workers and connection pools before adding hardware. Monitor online values against offline values for a sample of keys every day, so skew is caught by a dashboard instead of by a revenue drop. If you already run Databricks, compare its built-in feature store with Feast before choosing; Feast's strength is portability across clouds and stores.
quiz: What two problems does a feature store such as Feast solve? || Training-serving skew, by defining each feature once and serving it from the same definition offline and online, and data leakage, by using point-in-time joins so each training row only sees feature values known at its timestamp.
How does a point-in-time join choose a feature value for one training row? || It takes feature rows for the same entity whose event timestamp is not after the row's timestamp and not older than the TTL, and picks the newest (using the created timestamp to break ties). If no row qualifies, the feature is null.
Why does Feast keep separate offline and online stores? || Training needs large historical as-of joins, which warehouses and Spark do well. Serving needs the latest value for a few keys within milliseconds, which key-value stores do well. Materialization copies the latest values from one to the other.
A feature view has TTL 1 day, with feature rows at 10:00 on 4 May and 10:00 on 6 May. What do training events at 08:00 on 5 May and 18:00 on 5 May get? || The 08:00 event gets the 4 May row, which is 22 hours old and inside the TTL. The 18:00 event finds the same row 32 hours old, beyond the TTL, so its features are null; the 6 May row is in its future and cannot be used.
When would you add a push source instead of materializing more often? || When features must reflect events within seconds or minutes, such as clicks in the current session, because frequent batch materialization becomes costly and still lags. The trade is a streaming pipeline that must compute exactly what the batch definition computes.

@@ llamacpp
value: A large language model is mostly a pile of numbers. An 8-billion-parameter model stored in 16-bit floats takes about 16 GB, and generating each token means reading all of those bytes from memory once. Datacenter GPUs have the memory and bandwidth for that; a laptop with 16 GB of RAM does not. llama.cpp, started by Georgi Gerganov in March 2023, showed that you can shrink the weights to about 4 or 5 bits each and run capable models on ordinary laptops, desktops, phones and CPUs, with hand-written kernels for each kind of hardware. Ollama, built on top of it in 2023, made this a one-command experience: ollama run downloads a model and serves it on a local HTTP API.
Local inference matters for privacy (prompts never leave the machine), offline use, cost (no per-token bill), low latency for small tasks, and experimentation with open-weight models. In July 2026 Ollama reported serving 8.9 million developers. Many desktop apps, editors and agents run local models through llama.cpp or Ollama, and its GGUF format is the standard way to share quantized open models on Hugging Face.
Three lower concepts make this work. Quantization (L2) contributes the key idea: store weights as small integers with a shared scale per block of 32 or 256 weights, cutting memory and bandwidth by 3 to 4 times with little quality loss. C and C++ (L0) contribute a dependency-free program that compiles everywhere, from a Raspberry Pi to a GPU server, and gives direct control over memory layout and SIMD instructions. LLM serving (L1) contributes the server design: request slots, continuous batching, KV-cache management and an OpenAI-compatible API, scaled down to one machine.
terms: GGUF — the single-file binary format that holds a model's tensors plus metadata (architecture, tokenizer, chat template), designed to be memory-mapped.
ggml — the C tensor library under llama.cpp; it builds a compute graph and runs it on CPU or GPU backends.
Quantization type — a block format such as Q4_0, Q4_K_M, Q8_0 or IQ2_XS, named by its approximate bits per weight.
Bits per weight (bpw) — file size in bits divided by the number of weights, including the scales; Q4_K_M is about 4.9.
Importance matrix (imatrix) — statistics from running sample text through the model, used to quantize important weights more carefully.
Prefill — processing the prompt; many tokens at once, limited by compute.
Decode — generating one token at a time; each step reads all weights, limited by memory bandwidth.
KV cache — stored attention keys and values for every past token, so they are not recomputed.
Modelfile — Ollama's recipe file: a base model (FROM) plus parameters, a prompt template and a system prompt.
history: Meta released the LLaMA models to researchers on 24 February 2023, and the weights soon spread widely. Gerganov had already written whisper.cpp, a plain C/C++ port of OpenAI's Whisper speech model, on top of his own small tensor library, ggml. On 10 March 2023 he published llama.cpp, which ran the 7-billion-parameter LLaMA with 4-bit weights on a MacBook. Within weeks people ran it on Android phones and Raspberry Pis. Until then, LLM inference assumed Python, PyTorch and an NVIDIA GPU.
The file format evolved quickly. The first format was replaced by GGJT, which allowed memory-mapping, and then by GGUF in August 2023. GGUF stores hyperparameters as typed key-value metadata, so new architectures no longer broke old files. Better quantization followed: "k-quants" in mid-2023 used super-blocks with quantized scales, and "i-quants" and importance matrices in early 2024 made 2- and 3-bit models usable. Gerganov founded ggml.ai in 2023 with pre-seed funding from Nat Friedman and Daniel Gross, and the project moved to the ggml-org GitHub organization. Hugging Face acquired ggml.ai in 2026.
Ollama was founded by Jeffrey Morgan and Michael Chiang, whose earlier company, Kitematic, Docker had bought in 2015. Its design borrows from Docker: models are pulled from a registry as layers, and a Modelfile plays the role of a Dockerfile. It added OpenAI API compatibility in February 2024, its own engine built directly on ggml in May 2025, a desktop app in July 2025, optional cloud models in September 2025, and an MLX-based engine for Apple Silicon (preview) in March 2026. Ollama 0.30 (June 2026) improved GGUF compatibility through llama.cpp and enabled Vulkan by default. In July 2026 the company announced an $88 million round led by Benchmark.
how: The pipeline starts with conversion. convert_hf_to_gguf.py reads a model from Hugging Face (safetensors weights plus tokenizer files) and writes a GGUF file in 16-bit precision. The file begins with the magic bytes "GGUF", a format version (currently 3), a tensor count and a metadata count. Then come typed key-value pairs (architecture, context length, RoPE settings, the tokenizer vocabulary and merges, the chat template) and a table of tensor names, shapes, types and offsets. The tensor data follows, aligned to a fixed boundary (general.alignment). Because of the alignment, the program can memory-map the file: the operating system maps the file into the process's address space, and tensors are used in place without copying. Loading is almost instant, pages are read on demand, and processes can share one copy in the page cache.
Next comes quantization, which is where the quantization concept pays off. llama-quantize rewrites each weight tensor in a block format. The simplest, Q4_0, takes 32 consecutive weights, finds the largest magnitude, stores one 16-bit scale d, and stores each weight as a 4-bit integer q from 0 to 15, so that w ≈ d × (q − 8). That is 2 + 16 = 18 bytes for 32 weights, or 4.5 bits per weight. Q8_0 uses 8-bit integers, so 34 bytes per 32 weights, or 8.5 bits. The k-quants group 256 weights into a super-block of eight 32-weight sub-blocks. Each sub-block has its own scale and minimum, and those are themselves quantized to 6 bits against two 16-bit super-block values. Q4_K therefore stores 256 weights in 144 bytes, again 4.5 bits, but with finer scales. The "_M" mixes keep the most sensitive tensors (parts of the attention value and feed-forward output matrices) at 6 bits, which gives Q4_K_M about 4.9 bits per weight on average. An importance matrix, computed by running sample text through the model, tells the quantizer which weights matter most, so rounding errors land on weights that matter less.
At run time, ggml builds a compute graph for each batch of tokens (embedding, then for each layer: normalization, attention, feed-forward) and a scheduler assigns graph nodes to backends. The CPU backend uses SIMD instructions (AVX2 and AVX-512 on x86, NEON dot-product instructions on ARM), and there are backends for Metal, CUDA, HIP, Vulkan, SYCL and others. With -ngl you choose how many layers go to the GPU; the rest stay in system memory. The C/C++ concept matters here: kernels work directly on the packed blocks. For a matrix-vector product, the CPU quantizes the activation vector to 8 bits once, then multiplies 4-bit weights by 8-bit activations with integer SIMD instructions and applies the scales per block. Weights are never expanded to floats in memory, so each byte read from memory carries about 3.3 times more weights than in 16-bit form.
That matters because of the two phases of inference. Prefill multiplies the weight matrices by many prompt tokens at once, so it is limited by arithmetic. Decode produces one token per step and must stream every weight from memory each time, so it is limited by memory bandwidth. A useful rule: maximum decode speed ≈ memory bandwidth ÷ bytes of weights read per token. Quantization raises this ceiling in direct proportion to the size reduction, which is why it is the central trick for local inference.
The KV cache holds attention keys and values for every past token. Its size is 2 × layers × KV heads × head dimension × bytes per value for each token, so it grows linearly with context. llama.cpp can store it in 16-bit or quantized form (q8_0, q4_0) to fit longer contexts. llama-server applies the LLM serving concept on a small scale. -np sets the number of slots (parallel conversations). The KV cache can be one unified pool shared by all slots. Continuous batching combines the next token of every active slot, plus chunks of newly arrived prompts, into one batch per step. A prompt cache reuses the stored KV of a matching prefix, so a long system prompt is processed only once. The server exposes OpenAI- and Anthropic-compatible endpoints, embeddings and metrics, plus grammar-constrained output (GBNF, JSON Schema), tool calling, speculative decoding with a small draft model, and image input.
Ollama wraps this in a Go service. ollama pull fetches a model manifest and content-addressed blobs (weights, template, parameters, license) from its registry into a local store, much as Docker pulls image layers. The server, on port 11434 and bound to localhost by default, loads a model on first request. It estimates memory to decide how many layers fit on the GPU, keeps the model loaded for a few minutes after the last request (keep_alive), and unloads it to make room for another. Models now run on Ollama's own ggml-based engine, on MLX on Apple Silicon, or through llama.cpp for broad GGUF compatibility. The engine is hidden behind one API.

example: Take Llama 3.1 8B (about 8.03 billion parameters) on a laptop with 16 GB of unified memory and 400 GB/s of memory bandwidth, typical of a high-end Apple laptop.
In 16-bit form the weights take 8.03 × 10⁹ × 2 bytes ≈ 16.1 GB (14.96 GiB). That does not fit next to the operating system and apps. Quantized to Q4_K_M at 4.89 bits per weight, they take 8.03 × 10⁹ × 4.89 / 8 ≈ 4.91 GB (4.58 GiB). The llama.cpp documentation lists exactly 4.58 GiB for this model.
Now the KV cache. The model has 32 layers, 8 key-value heads and a head dimension of 128. Per token, in 16-bit, that is 2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes = 128 KiB. An 8,192-token context needs 8,192 × 128 KiB = 1 GiB. A 32,768-token context needs 4 GiB, and with a q8_0 cache (about 8.5 bits instead of 16) about 2.1 GiB. Total for 32K context with q8_0: 4.58 + 2.1 ≈ 6.7 GiB plus some working buffers, which fits comfortably.
Decode speed. Each generated token reads all 4.91 GB of weights, so the ceiling is 400 GB/s ÷ 4.91 GB ≈ 81 tokens per second. Real systems reach perhaps 60 to 75% of it (KV cache reads, kernel overheads), so expect 50 to 60 tokens per second. The same model in 16-bit would have a ceiling of 400 ÷ 16.1 ≈ 25 tokens per second, even if memory allowed it. The llama.cpp documentation's own benchmark of this model shows the same pattern: about 72 tokens per second for Q4_K_M against 29 for F16 on the same hardware.
A desktop PC with dual-channel DDR5-5600 and no GPU has about 2 × 8 bytes × 5,600 MT/s ≈ 90 GB/s, so its ceiling is 90 ÷ 4.91 ≈ 18 tokens per second.
Finally, one Q4_0 block by hand. Suppose the 32 weights in a block range from −0.95 to +0.83. A simple encoder sets d = 0.95 / 8 ≈ 0.119, so q = round(w / d) + 8 lies between 0 and 15. A weight of 0.31 becomes round(2.6) + 8 = 11, and decodes to 0.119 × (11 − 8) = 0.357, an error of 0.047. The error in each block is bounded by half a step, d / 2 ≈ 0.06. Importance matrices and k-quant scales exist to shrink this error where it matters most.
intuition: Shrink the numbers until the model fits in ordinary memory, then make every byte read from memory count, because on a laptop memory bandwidth is the speed limit.
The design follows from one observation: during generation the processor is mostly waiting for weights to arrive from memory. If each weight takes 4.9 bits instead of 16, the same memory delivers 3.3 times more weights per second, and the model also fits in less RAM. The quality cost is small because trained weights in a block have similar sizes, so one shared scale describes them well, and most weights tolerate small rounding errors. The rest is engineering discipline: one portable C/C++ code base, one self-describing file that can be memory-mapped, and kernels that compute on packed data. Ollama adds the packaging experience developers already knew from Docker.
mistakes: People often think 4-bit quantization makes a model four times worse. In fact well-made 4- to 5-bit quantizations (Q4_K_M, Q5_K_M) usually score close to the 16-bit model on common tasks. Losses grow below about 3 bits and are larger for small models, which have less redundancy.
People often think more CPU cores mean faster generation. In fact decode is limited by memory bandwidth. Once the cores saturate it, extra threads add nothing; bandwidth and GPU offload decide speed.
People often think long contexts are free once the model fits. In fact the KV cache grows linearly. For Llama 3.1 8B, a full 128K-token context in 16-bit needs 16 GiB for the cache alone, three times the size of the quantized weights.
People often think Ollama is a separate inference engine unrelated to llama.cpp. In fact it began as a wrapper around llama.cpp. It now has its own engines, built on the same ggml library and on MLX, and it still uses llama.cpp for GGUF compatibility. They are one family with different interfaces.
friction: Local throughput is far below datacenter serving. A laptop serves one or a few users at tens of tokens per second, while a GPU server running vLLM or SGLang batches hundreds of requests. Prefill on a CPU is slow, so a 20,000-token prompt can take tens of seconds before the first token appears.
Quality depends on the quantization and the conversion. Different quantizers produce different files of the same name. Chat templates, tokenizers or RoPE settings converted wrongly cause subtle quality bugs that look like a "bad model". Very low-bit formats need a good importance matrix, and calibration text in the wrong language or domain can hurt.
New model architectures, such as new attention variants, mixture-of-experts layouts or multimodal encoders, need new code in ggml and llama.cpp. Support can lag a model release by days or weeks, and fast development means flags and defaults change often.
Defaults hide choices: Ollama picks a quantization and a context length for you, and a context smaller than the conversation silently drops early messages. Neither llama-server nor Ollama has strong built-in multi-user security. An instance bound to a public interface without a reverse proxy and authentication exposes the model, and the machine's resources, to anyone.
practice: Start with Q4_K_M. Move up to Q5_K_M, Q6_K or Q8_0 if you have memory to spare and need the last bit of quality, and use IQ formats with an importance matrix only when memory forces you below 4 bits. Prefer quantizations from the model authors, the ggml-org organization on Hugging Face, or well-known quantizers, and check the chat template.
Fit the whole model on the GPU if you can (-ngl 99 in llama.cpp; Ollama does this automatically when memory allows), since splitting between GPU and CPU drops speed toward the CPU's bandwidth. Size the context on purpose: set -c or num_ctx to what you need, compute the KV cache size (2 × layers × KV heads × head dim × bytes × tokens), and use a q8_0 KV cache to double usable context at little cost.
Measure with llama-bench on your own hardware, reporting prompt and generation tokens per second separately. For a small team, llama-server with -np 4 to 8 slots and a unified KV cache gives continuous batching and prefix reuse; put a long, stable system prompt first so its cache is reused.
Use Ollama for easy model management and a stable local API; use llama.cpp directly for full control of flags, builds and unusual hardware. Keep both on localhost or behind an authenticating reverse proxy. When load grows to many concurrent users on GPUs, move to a datacenter engine such as vLLM or SGLang and keep llama.cpp for edge and desktop use.

value: When many people use a language model at once, the cost of serving is set by how many tokens each GPU can process per second. Modern workloads waste a lot of that capacity. A chat assistant resends the whole conversation every turn. An agent resends a long system prompt, tool definitions and its history at every step. A few-shot classifier sends the same examples with every input. A basic engine runs prefill (the attention computation over the prompt) from scratch for each request, even though most of the prompt was processed a moment ago. SGLang, from the LMSYS team (December 2023), and NVIDIA's TensorRT-LLM (October 2023) are open-source serving engines built to remove this waste and to use the GPU's arithmetic as fully as possible. They compete with vLLM.
SGLang's best-known idea is RadixAttention: it keeps the KV cache of past requests in a radix tree and reuses any shared prefix automatically. It also schedules batches without GPU idle time, constrains outputs to JSON schemas cheaply, and runs very large mixture-of-experts models across many nodes, on NVIDIA, AMD, Google TPU, Intel and Huawei Ascend hardware. TensorRT-LLM is NVIDIA's engine for NVIDIA GPUs only. It focuses on hand-tuned kernels, FP8 and FP4 arithmetic on the newest GPUs, and integration with NVIDIA's Dynamo serving framework.
Both stand on two lower concepts. LLM serving (L1) supplies the core machinery: continuous batching, a paged KV cache, a scheduler that admits requests by available memory, and parallelism across GPUs. Prefix and prompt caching (L2) supplies the observation that the KV cache of a prefix depends only on that prefix, so it can be stored and reused. RadixAttention turns that observation from a manual feature ("cache this prompt") into an automatic data structure that finds and shares every common prefix.
terms: Prefill — processing the prompt to fill the KV cache; compute-bound, and it sets the time to first token.
Decode — generating one token per step for each request; memory-bandwidth-bound, and it sets the time per output token.
KV cache — stored attention keys and values for every token processed so far, needed for each later token.
Radix tree — a prefix tree whose edges hold runs of tokens, so sequences that share a beginning share a path.
Cache hit rate — the fraction of prompt tokens whose KV entries were found in the cache instead of computed.
Continuous (in-flight) batching — adding and removing requests at every decoding step instead of waiting for a whole batch to finish.
Prefill-decode disaggregation — running prefill and decode on different GPU pools and moving the KV cache between them.
Expert parallelism — spreading the experts of a mixture-of-experts model across GPUs, with tokens sent to whichever GPU holds their expert.
Constrained decoding — masking, at each step, the tokens that would break a grammar such as a JSON schema.
history: By mid-2023 the basics of LLM serving were set. Orca (2022) introduced iteration-level batching, and vLLM (2023) introduced PagedAttention, which stores the KV cache in fixed-size blocks like virtual-memory pages. LMSYS, the group from UC Berkeley and Stanford behind the Vicuna models and Chatbot Arena, saw that new programs (agents, tree-of-thought search, few-shot evaluation, multi-turn chat) issued many calls that shared prefixes. Lianmin Zheng, Ying Sheng and colleagues published "SGLang: Efficient Execution of Structured Language Model Programs" on 12 December 2023; its revised version (June 2024) reported up to 6.4 times higher throughput than existing systems, and it appeared at NeurIPS 2024. It had two halves: a small Python language for writing LLM programs (gen, fork, choices) and a runtime with RadixAttention.
The runtime soon mattered more than the language. In February 2024 LMSYS added fast JSON decoding with a compressed finite-state machine. Version 0.4 (December 2024) added a zero-overhead batch scheduler, a cache-aware load balancer and the xgrammar backend for structured output. SGLang then became a main engine for DeepSeek models. In May 2025 the team described serving DeepSeek on 96 H100 GPUs with prefill-decode disaggregation and large-scale expert parallelism. By 2026 it supported Google TPUs (July 2026) and had an AWS Trainium beta (October 2026). As of October 2026 the current release is 0.5.22, and the project is hosted by LMSYS as a non-profit open-source effort.
NVIDIA announced TensorRT-LLM in September 2023 and made it open source on 19 October 2023. It began on the TensorRT deep-learning compiler: you converted a checkpoint and built an optimized "engine" for a specific GPU, and it brought in-flight batching and FP8 on H100 to NVIDIA's stack. Development moved fully to GitHub in March 2025. NVIDIA then rebuilt it around PyTorch model definitions with custom kernels, and in 2026 removed the TensorRT engine backend, so models load directly from Hugging Face checkpoints. In 2025 NVIDIA also released Dynamo, the successor to Triton Inference Server, which orchestrates SGLang, TensorRT-LLM and vLLM workers across a cluster.
how: Start from the serving loop described in the LLM serving concept. A scheduler keeps a queue of waiting requests and a running batch. Each step it runs one forward pass that decodes one token for every running request, and it may add chunks of new prompts (prefill) to the same batch. KV memory is managed in pages, so requests can grow without large contiguous allocations, and new requests are admitted only when free pages exist.
RadixAttention changes what happens to KV pages after a request finishes. Instead of freeing them, SGLang inserts the request's full token sequence (prompt plus generated output) into a radix tree that lives in CPU memory. Each tree edge holds a run of token IDs and points to the GPU pages that hold their keys and values. In the original design a page held one token, so any prefix length can be shared. When a new request arrives, the scheduler walks the tree from the root, matching the request's tokens, and finds the longest cached prefix. Those pages are reused directly, and only the remaining suffix goes through prefill. Pages used by running requests are locked. When memory runs short, the cache evicts unlocked leaves in least-recently-used order, working inward, so popular shared prefixes near the root survive longest. Requests that branch from a common prefix (fork in the frontend, parallel samples, many users of one system prompt) share the prefix's pages in memory too, which raises the number of requests that fit in a batch.
This is where the prompt-caching concept adds value. The KV entries for a prefix depend only on the tokens of that prefix and the model weights, never on what follows. So a cached prefix is exactly correct for any request that starts with it, with no approximation. The radix tree makes "starts with" fast to test, and it lets many partial overlaps share storage.
The scheduler is also cache-aware. Among waiting requests, it prefers those with longer cached prefixes. That roughly processes the tree depth-first, finishing work on one branch while its pages are still in memory instead of jumping between branches and thrashing the cache. Since version 0.4 the scheduler also runs one batch ahead. While the GPU executes batch N, the CPU prepares batch N + 1 (tree matching, memory allocation, metadata), so the GPU does not wait for Python code between steps.
Across many servers, a router keeps an approximate radix tree of what each worker has cached. It sends each request to the worker with the best expected prefix match, balanced against load. In the v0.4 benchmark with groups of requests sharing long prefixes, this raised the cache hit rate from 20% to 75% and throughput from 82,665 to 158,596 tokens per second, about 1.9 times. NVIDIA Dynamo's KV-aware router applies the same idea to SGLang, TensorRT-LLM and vLLM fleets.
Structured output is the second pillar. A JSON schema or regular expression is compiled into a grammar automaton. At each decoding step, the engine computes which vocabulary tokens are allowed in the current state and masks the rest before sampling. The xgrammar backend precomputes most of these masks, so the cost per step is small. When the grammar forces several characters in a row (a key name such as "temperature": ), jump-forward decoding appends them at once instead of generating them one token at a time.
For very large models, SGLang combines several kinds of parallelism. Tensor parallelism splits each matrix across GPUs. DeepSeek models use multi-head latent attention with a single KV head, so tensor parallelism would copy the whole KV cache to every GPU. Data-parallel attention avoids that by giving each GPU its own requests for attention and then exchanging activations before the mixture-of-experts layers. Expert parallelism places different experts on different GPUs. Prefill-decode disaggregation runs prompt processing and token generation on separate GPU pools, so long prompts never stall decoding, and transfers the KV cache over fast networks such as RDMA. Speculative decoding (for example EAGLE) and FP8 or FP4 weights reduce per-token cost further.
TensorRT-LLM provides the same serving features (in-flight batching, a paged KV cache with block reuse for prefixes, tensor, pipeline and expert parallelism, prefill-decode disaggregation, and EAGLE, multi-token-prediction and n-gram speculation) with a different emphasis: NVIDIA's own kernels for attention, matrix multiplication and mixture-of-experts. These include FP8 on Hopper and native FP4 on Blackwell GPUs, CUDA graphs to remove launch overhead, and close tracking of each new GPU generation. Since the 2026 change it uses PyTorch as its only backend, so you start it with trtllm-serve on a Hugging Face model name and get an OpenAI-compatible API, like SGLang and vLLM.

example: An assistant serves Llama 3.1 8B on one 80 GB H100. Every request starts with the same 3,000-token prefix (system prompt, tool definitions, few-shot examples). One hundred users each have a 5-turn conversation. Each turn adds a 200-token user message and a 300-token answer.
Without prefix reuse, every turn re-prefills the whole history. For one conversation, turn 1 processes 3,000 + 200 = 3,200 tokens. Turn 2 processes 3,200 + 300 + 200 = 3,700, then 4,200, 4,700 and 5,200. That is 21,000 prefill tokens per conversation, or 2,100,000 for 100 users.
With RadixAttention, the 3,000-token prefix is computed once and then found in the tree. Each earlier turn's prompt and answer were inserted when they finished, so each new turn prefills only its 200 new tokens. That is 5 × 200 = 1,000 tokens per conversation, or 100,000 + 3,000 = 103,000 in total, about 20 times fewer.
Convert to GPU time. Prefill costs roughly 2 × parameters FLOPs per token, so 2 × 8 × 10⁹ = 1.6 × 10¹⁰ FLOPs. An H100 offers about 1,000 TFLOPS of dense BF16 at peak; assume 50% use, 5 × 10¹⁴ FLOPS. Without reuse: 2.1 × 10⁶ × 1.6 × 10¹⁰ ÷ 5 × 10¹⁴ ≈ 67 s of GPU time. With reuse: 1.03 × 10⁵ × 1.6 × 10¹⁰ ÷ 5 × 10¹⁴ ≈ 3.3 s. For a single turn-5 request, the prefill part of time to first token drops from about 5,200 × 1.6 × 10¹⁰ ÷ 5 × 10¹⁴ ≈ 0.17 s to about 0.006 s.
Memory improves as well. In 16-bit, this model's KV cache uses 128 KiB per token (2 × 32 layers × 8 KV heads × 128 dimensions × 2 bytes). If all 100 finished conversations stayed cached as separate copies, that would be 100 × 5,500 = 550,000 tokens × 128 KiB ≈ 67 GiB, which does not fit beside 16 GB of weights. With the shared prefix stored once, it is 3,000 + 100 × 2,500 = 253,000 tokens ≈ 31 GiB, which fits. When memory does run short, LRU eviction removes the leaves of idle conversations first. A user who returns after eviction pays the full prefill once more.
Finally, suppose one careless change puts the current time on the first line of the system prompt. Every request now differs from the others at token 5, the tree shares almost nothing, and the cost returns to about 2.1 million prefill tokens. Prefix caching rewards prompts whose stable parts come first.
intuition: Never compute the same prefix twice, and fuse everything else into tight GPU kernels.
A radix tree is the natural structure for this because LLM requests are sequences that are extended at the end and share beginnings, exactly the shape a prefix tree stores without duplication. The KV cache of a prefix is a pure function of that prefix, so sharing is always correct, and the only question is which prefixes to keep. LRU over leaves answers that with a simple rule: specific, old branches go first, and shared trunks stay. The rest of these engines' design follows the same economy. Overlap CPU work with GPU work, skip tokens a grammar forces, and route each request to the machine that already holds its prefix. TensorRT-LLM pursues the other half of the economy, making every arithmetic operation on NVIDIA hardware as cheap as possible.
mistakes: People often think prefix caching only helps identical prompts. In fact it helps any request that shares a beginning with an earlier one. But the match must be exact from the first token, so one changed token near the start, such as a timestamp or a user name, prevents reuse of everything after it.
People often think the fastest engine on a public benchmark will be fastest for them. In fact results depend heavily on the model, the GPU generation, prompt and output lengths, prefix sharing and the latency target. Engines leapfrog each other release by release, so benchmark with your own traffic.
People often think TensorRT-LLM still requires building a TensorRT engine for each model and GPU. In fact the engine backend was removed in 2026; PyTorch is its only backend, and it loads Hugging Face checkpoints directly.
People often think routing every request to the worker with the best cache match is always best. In fact a popular prefix can overload one worker while others sit idle. Cache-aware routers balance expected hit rate against queue length.
friction: These engines change very fast. Flags, defaults and supported models shift between minor releases, and features that appear first for one model family (for example DeepSeek's attention) may be slow to generalize. Tuning is specific to each GPU generation: FP8 kernels that are fastest on Hopper differ from FP4 paths on Blackwell, and results on AMD or TPU differ again.
Prefix caching has real limits. Hit rates depend on prompt design, and many applications put dynamic content first. Under memory pressure, eviction makes time to first token unpredictable for returning users. A cache shared across tenants can leak, through timing, whether someone else recently sent the same prefix, so providers often scope caches per customer.
Large-scale features carry operational cost. Prefill-decode disaggregation needs fast interconnects, KV transfer and a tuned ratio of prefill to decode GPUs, and that ratio changes when traffic patterns change. Expert parallelism needs all-to-all communication and suffers when some experts are much busier than others. Speculative decoding and low-precision formats can change outputs slightly, so they need evaluation, not only speed tests. TensorRT-LLM ties you to NVIDIA hardware, while SGLang's support on non-NVIDIA hardware is newer and narrower in model coverage.
practice: Choose by workload and hardware. SGLang fits workloads with heavy prefix sharing (agents, multi-turn chat, few-shot pipelines, RL rollouts) and large mixture-of-experts models. TensorRT-LLM fits teams standardized on NVIDIA that want the newest GPU features and NVIDIA support, often behind Dynamo. vLLM is the broadest default. All three expose OpenAI-compatible APIs, so keep your application engine-neutral and switch when measurements say so.
Benchmark with a replay of real traffic: prompt and output length distributions, shared-prefix structure and concurrency. Report time to first token, inter-token latency at p50 and p99, and goodput (requests that meet your latency targets), not only peak tokens per second.
Design prompts for caching. Put stable content (system prompt, tool definitions, documents) first and per-request content last. Keep tool lists in a fixed order. Monitor the cache hit rate as a first-class metric. Across several replicas, use a prefix-aware router (the SGLang router or Dynamo's KV router) instead of round-robin.
Size memory on purpose. Leave enough GPU memory for the KV pool (SGLang's --mem-fraction-static controls it), and watch for evictions and request queueing. Turn on FP8 on Hopper or FP4 on Blackwell only after an accuracy check on your evaluation set. Add speculative decoding when latency per user matters more than total throughput. Move to prefill-decode disaggregation only when long prompts measurably hurt decode latency at your scale. Pin engine versions and re-benchmark before upgrades.
quiz: What does RadixAttention store, and how does a new request use it? || It keeps the KV cache of finished requests (prompts and outputs) in a radix tree keyed by token sequences. A new request walks the tree to find its longest cached prefix, reuses those KV pages, and runs prefill only on the remaining tokens.
Why is reusing a cached prefix always exactly correct? || In a causal transformer, the keys and values of each token depend only on that token and the tokens before it. So the KV entries of a prefix are the same for every request that starts with that prefix, whatever comes after it.
Why does the cache evict leaves in LRU order rather than arbitrary entries? || Leaves are the most specific, least shared parts of the tree, while nodes near the root are shared by many requests. Evicting old leaves first frees memory with the smallest loss of future hits and keeps shared trunks such as system prompts.
Requests share a 4,000-token prefix and each adds 500 new tokens. For 1,000 requests, how many prefill tokens are needed with and without prefix reuse? || Without reuse: 1,000 × 4,500 = 4,500,000 tokens. With reuse: 4,000 once plus 1,000 × 500 = 504,000 tokens, roughly 9 times fewer.
When would you choose TensorRT-LLM over SGLang? || When you run only NVIDIA GPUs, want the newest hardware features (such as FP4 on Blackwell) and NVIDIA's support and Dynamo integration, and your workload benefits more from kernel speed than from SGLang's prefix-sharing and scheduling strengths. Benchmark both on your traffic before deciding.

@@ a2a
value: Companies now run many AI agents built by different vendors on different frameworks: a CRM vendor's sales agent, an HR platform's recruiting agent, an internal LangGraph agent, a Google ADK agent. Real work often crosses them. A recruiting agent needs a background-check vendor's agent, and a travel agent needs a hotel's booking agent. These partners are not simple tools. They take minutes or days, ask questions back, produce documents, and keep their prompts, tools and data private. Without a standard, every pair of agents needs custom glue code, and none of it handles waiting, follow-up questions or authentication the same way. Agent2Agent (A2A) is an open protocol for exactly this link. Agents publish a machine-readable "Agent Card" describing their skills, endpoints and security, and other agents send them messages, track tasks through a defined lifecycle, and receive results as artifacts, by streaming or by webhook.
Google announced A2A in April 2025 with more than 50 partners and gave it to the Linux Foundation in June 2025, when more than 100 companies supported it. Version 1.0 of the specification was released in March 2026, with official SDKs in Python, Go, Java, JavaScript, C# and Rust. It stands on the AI agents concept (L1). Each agent internally runs the agent loop of model, tools and memory. A2A deliberately treats a remote agent as opaque: only messages, tasks and artifacts cross the boundary, never its prompts, tools or internal state. For the calling agent, "ask another agent" becomes one more action in its loop, but an action that may run for hours and may need its own answers.
Its neighbour is MCP. The A2A documentation puts the split simply: MCP is vertical and deepens one agent with tools and data, while A2A is horizontal and connects agents across team and company boundaries. A typical system uses both.
terms: Agent Card — a JSON document, usually at /.well-known/agent-card.json, that describes an agent's skills, interfaces, capabilities and security requirements.
Skill — one advertised ability of an agent, with an ID, a description, tags, examples and supported input and output types.
Message — one turn of communication with a role (user or agent) and one or more parts.
Part — one piece of content in a message or artifact: text, raw bytes, a URL to a file, or structured JSON data.
Task — a stateful unit of work with an ID, a status and a lifecycle; created by the remote agent when work is more than an instant reply.
Artifact — an output produced by a task, such as a report, a file or structured data, made of parts.
Context ID — an identifier that groups related tasks and messages into one conversation.
Push notification — an HTTP POST from the remote agent to a webhook the client registered, sent when a task changes.
Protocol binding — one of the three wire formats with the same meaning: JSON-RPC 2.0 over HTTP, gRPC, or HTTP+JSON (REST).
history: Google announced A2A on 9 April 2025 at Google Cloud Next, with more than 50 technology partners, as a complement to Anthropic's Model Context Protocol. The announcement listed five design principles. Agents should collaborate as agents, not be forced to act as tools. The protocol should build on existing standards (HTTP, Server-Sent Events, JSON-RPC). It should be secure by default, with authentication schemes matching OpenAPI's. It should support long-running tasks, including hours or days with humans involved. And it should not depend on modality, so text, files, forms, audio and video are all possible.
Version 0.2 and the first SDKs followed in May and June 2025. On 23 June 2025, at Open Source Summit North America, the Linux Foundation launched the Agent2Agent Protocol Project with Google as creator and founding roles for companies including SAP, ServiceNow and Cisco, and support from more than 100 companies. Version 0.3.0 followed on 30 July 2025.
Version 1.0.0, released on 12 March 2026, was a deliberate breaking clean-up for long-term stability. A Protocol Buffers file, a2a.proto, became the normative definition, with three bindings that have equal standing: JSON-RPC, gRPC and HTTP+JSON. Methods got PascalCase names (message/send became SendMessage; tasks/resubscribe became SubscribeToTask), and a ListTasks method was added. Enums took prefixed upper-case names such as TASK_STATE_COMPLETED. Separate part types were merged into one Part type. Agent Cards gained a list of supported interfaces and optional JWS signatures, and every request gained a tenant field for multi-tenant hosting. A 1.0.1 patch followed in May 2026, and the Python SDK reached 1.0 in April 2026 and 1.2 by October 2026.
how: Discovery comes first. A client agent fetches the remote agent's card, typically GET https://agent.example.com/.well-known/agent-card.json, or reads it from a registry. The card lists the agent's name, provider and version. Its supportedInterfaces entries each give a URL, a protocol binding and a protocol version, and the client picks one it speaks. Capabilities say whether the agent supports streaming, push notifications and an extended card. securitySchemes and security say how to authenticate: API key, HTTP authentication, OAuth 2.0 (authorization code, client credentials or device code flows), OpenID Connect or mutual TLS. The card also lists default input and output media types and, most importantly, skills: what the agent can do, with examples a client model can read to decide whether to delegate. A card can carry JWS signatures over its canonical JSON form (RFC 8785), so a client can verify who issued it. An agent can publish a short public card and return a fuller extended card through GetExtendedAgentCard after authentication.
Interaction starts with SendMessage. The client sends a Message with role ROLE_USER, a unique messageId, and parts, for example a text instruction plus a data part with structured fields or a URL to a file. It can add a contextId to continue a conversation, a taskId to continue a specific task, or referenceTaskIds to build on earlier tasks. The remote agent answers in one of two ways. A Message is a direct, stateless reply for quick interactions. A Task is used for trackable work and carries an id, a contextId, a status (state, optional message, timestamp), artifacts and history.
Tasks follow a fixed state machine. TASK_STATE_SUBMITTED means the task was accepted, and TASK_STATE_WORKING means the agent is processing it. Two interrupted states pause the work: TASK_STATE_INPUT_REQUIRED (the agent needs an answer from the client) and TASK_STATE_AUTH_REQUIRED (it needs extra credentials). The client resumes by sending another message with the same taskId. Four terminal states end it: COMPLETED, FAILED, CANCELED and REJECTED. A terminal task is immutable. Any refinement ("make the report shorter") creates a new task in the same context that references the old one. That keeps every output tied to one fixed unit of work.
Results arrive in three ways, chosen for the task's length. Polling uses GetTask (and ListTasks) and is simple but wasteful for long tasks. Streaming uses SendStreamingMessage, or SubscribeToTask to attach to an existing task. Over JSON-RPC and HTTP+JSON this is a Server-Sent Events stream, and over gRPC a server stream. The stream carries the task, then statusUpdate and artifactUpdate events in order; artifacts can arrive in chunks. Push notifications suit tasks that take hours. The client registers a webhook configuration with a URL, an optional token and authentication details, and the agent POSTs each update there. The specification tells agents to validate webhook URLs against server-side request forgery, for example by rejecting localhost and private IP ranges, and tells receivers to verify the token or signature on each call.
The three bindings carry the same operations. JSON-RPC uses method names such as SendMessage and GetTask over HTTPS. gRPC uses the services in a2a.proto. HTTP+JSON maps them to paths such as POST /message:send, GET /tasks/{id} and POST /tasks/{id}:cancel. Service parameters such as the protocol version and requested extensions travel in HTTP headers or gRPC metadata. Extensions are declared in the card, can be marked as required, and add features such as citations without changing the core protocol.
Security relies on standard web machinery rather than new cryptography. Requests use TLS, and credentials are obtained outside the protocol through the schemes the card declares, often OAuth 2.0 client credentials between companies. The remote agent then authorizes each request against its own policies. The tenant field lets one deployment host many customers' agents behind one endpoint. Because each side sees only messages and artifacts, a company can offer an agent without exposing its prompts, tool access or data.
This is where the agent concept and the MCP neighbour divide the work. Inside the remote agent, the loop plans, calls its own tools (often through MCP) and decides when it needs input. A2A gives that loop a standard outside interface: a front door (the card), a ticket (the task), status updates and delivered documents. An MCP tool call is a short, structured function call. An A2A task is a long, stateful conversation with a peer that may say no, ask questions, or take a day.

example: An HR platform's recruiting agent uses a background-check vendor's agent for employment verification. The two companies have a contract, and the vendor has registered the HR platform as an OAuth client.
Step 1, discovery. The HR agent fetches https://bgcheck.example.com/.well-known/agent-card.json, about 3 KB. The card lists a skill "employment-verification" with examples, capabilities streaming: true and pushNotifications: true, an HTTP+JSON interface at https://bgcheck.example.com/a2a for protocol version 1.0, and an OAuth 2.0 client-credentials scheme. The HR agent verifies the card's JWS signature against the vendor's published key and gets a token valid for 3,600 s.
Step 2, the request. POST /message:send carries a Message with role ROLE_USER, messageId m-1, a text part ("Verify employment history for candidate 8812 from 2018 to 2025") and a data part with the candidate ID and a URL to the signed consent form. The vendor answers with Task t-91 in context c-7, state TASK_STATE_SUBMITTED. The HR agent registers a push configuration with webhook https://hr.example.com/a2a/hooks and a random 32-byte token.
Step 3, the wait. The task moves to WORKING after 40 s. Two hours later the vendor's agent cannot find one employer and moves the task to TASK_STATE_INPUT_REQUIRED with the message "No record for 'Acme Ltd' 2019 to 2021; was it registered under another name?". The push POST arrives with the token, and the HR agent checks it. The HR agent's own loop asks the recruiter, gets "Acme Labs Pvt Ltd", and sends a new message with taskId t-91 and contextId c-7. The task returns to WORKING.
Step 4, the result. After 26 hours the task becomes COMPLETED, with an artifact "verification-report" holding a data part (JSON with three verified employers) and a URL part pointing to a PDF. The HR agent receives the push notification, calls GET /tasks/t-91 to fetch the final state, stores the artifact, and closes its own step.
Why push here? Polling every 30 s for 26 hours costs 26 × 3,600 / 30 = 3,120 GetTask calls per task. With 1,000 checks in flight, that is about 3.1 million calls a day, almost all of them answering "still working". Push needs about five notifications per task, so about 5,000 calls. Holding 1,000 Server-Sent Events streams open for a day would also fight with load balancers that close idle connections after a minute or so. Streaming suits tasks that last seconds to minutes; push suits hours to days.
A week later, the recruiter asks to re-check only one employer. t-91 is terminal and immutable, so the HR agent sends a new message in context c-7 with referenceTaskIds [t-91], and the vendor creates task t-130. The audit trail keeps both tasks with their own artifacts.
intuition: MCP is how an agent uses a tool; A2A is how an agent asks another agent for help, the way one company opens a work order with a contractor.
The design is natural because it copies how organizations already cooperate. You find a contractor by their published card of services. You open a ticket with a clear request. The contractor updates its status, may come back with a question, and finally delivers documents. You never see their internal staff or tools. Agents fit this model better than the function-call model, because their work is long, uncertain and conversational. Building on HTTP, JSON-RPC, gRPC, Server-Sent Events, webhooks and OAuth means every company's existing gateways, firewalls and identity systems already understand the traffic. The immutable task with a fixed state machine gives both sides the same picture of where the work stands, which is what makes asynchronous cooperation between strangers possible.
mistakes: People often think A2A replaces MCP. In fact they solve different links. MCP connects an agent to tools and data with short, structured calls. A2A connects an agent to another autonomous agent with long-running, stateful tasks. A remote A2A agent usually uses MCP internally.
People often think an Agent Card proves an agent is trustworthy. In fact a card is self-description. A signature proves who issued the card, not that the agent behaves well. Trust still comes from contracts, allow-lists, authentication and monitoring.
People often think the remote agent's output can be passed straight into the calling agent's prompt. In fact it is untrusted input from another organization, and it can carry prompt injection. Treat artifacts like any external data: validate them, and never let them trigger actions without checks.
People often think one long streaming connection is the best way to wait for a result. In fact streams break on network changes, deploys and idle timeouts. For tasks longer than a few minutes, push notifications or occasional polling are more reliable, and a client must be able to resubscribe or call GetTask to recover.
friction: The ecosystem is young. Version 1.0 broke compatibility with 0.3 (method names, enum formats, part types, card fields), so early integrations had to be rewritten. Many agent products still support only MCP, or only their own vendor's agent-to-agent mechanisms.
Trust across organizations is mostly unsolved by the protocol itself. Who is accountable when a remote agent makes a wrong decision? How does a user's consent travel from one company's agent to another's? How are data-retention rules applied to task history? A2A gives the identity and authorization hooks, but contracts, policies and audit processes must fill them.
Security risks move to new places. Webhooks invite server-side request forgery if URLs are not validated. File URLs in parts can point anywhere. A malicious or compromised remote agent can return artifacts designed to manipulate the caller's model. And a chain of agents can turn one injection into several actions.
Operations are harder than with a single agent. A request that crosses three agents multiplies latency, cost and failure points. Tracing across company boundaries needs agreed headers and logging, and debugging a failure inside an opaque remote agent depends on the other side's support. Discovery is still fragmented: well-known URLs work when you already know the domain, but there is no single trusted global registry of agents.
practice: Use A2A when the other side is an autonomous agent owned by another team or company and the work can be long or conversational. Use MCP for tools and data sources, and plain function calls inside one codebase. Not every internal service needs to become an agent.
When you publish an agent, keep the card accurate and narrow. Give each skill a clear description and examples, so client models delegate correctly. Sign the card, serve sensitive details only on the extended card behind authentication, and declare exactly the security schemes you enforce. Return a Task for anything that takes more than a few seconds, and move it through explicit states. Use INPUT_REQUIRED to ask instead of guessing, and REJECTED to refuse out-of-scope work clearly.
When you call agents, authenticate with OAuth 2.0 client credentials or mutual TLS, scope tokens to the skills you need, and keep an allow-list of partner agents. Use a unique messageId per send, so retries can be recognized as duplicates. Prefer push notifications for long tasks; verify the token on every webhook call, and validate any URLs you are asked to fetch. Treat every artifact as untrusted input. Record contextId and taskId in your logs, propagate trace headers, set timeouts, and call CancelTask when you no longer need the work. Use the official SDKs, and pin the protocol version through the interface you select from the card.
quiz: What is an Agent Card, and what does a client learn from it? || A JSON document, usually at /.well-known/agent-card.json, that describes the agent. The client learns its skills (with examples), its endpoints and protocol bindings, its capabilities (streaming, push notifications, extended card) and how to authenticate.
When does a remote agent reply with a Message, and when with a Task? || A Message is a direct, stateless reply for quick interactions. A Task is created for trackable work that takes time, may need more input or produces artifacts, and it moves through states such as SUBMITTED, WORKING, INPUT_REQUIRED and COMPLETED.
Why are terminal tasks immutable, and how do you refine a finished result? || Immutability ties every output to one fixed unit of work, so references and audits stay reliable and nobody has to decide whether a finished task may restart. To refine, send a new message in the same context with referenceTaskIds pointing to the old task; the agent creates a new task.
A task takes 10 hours. How many GetTask calls does polling every 20 s cost, compared with about 4 push notifications? || 10 × 3,600 / 20 = 1,800 calls per task, against about 4 webhook calls with push. For 500 parallel tasks that is 900,000 polls against roughly 2,000 notifications.
Your planning agent needs a currency-conversion function and a partner's travel-booking agent. Which protocol fits each, and why? || Currency conversion is a short, stateless, structured call, so expose it as an MCP tool or plain function. Travel booking is a long, conversational task with another company's autonomous agent that may ask questions and return documents, so use A2A.
