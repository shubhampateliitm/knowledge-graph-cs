@@ allocators
value: A memory allocator is the code behind malloc and free (or new and delete, or object creation in a language runtime). A program asks for blocks of many different sizes at unpredictable times and gives them back in a different order. The allocator must find space for each request quickly, keep track of what is free, and avoid wasting memory. The operating system only hands out whole pages (usually 4 KB), so something in user space has to cut those pages into the small pieces a program needs: a 24-byte list node, a 200-byte string, a 3 MB buffer.
The allocator sits on the hot path of almost every program. A service can make millions of allocations per second, so a slow or lock-heavy allocator becomes a bottleneck, and a wasteful one decides how much RAM you pay for. This is why Redis ships with jemalloc, why Firefox and FreeBSD adopted jemalloc, why Google built tcmalloc, and why teams sometimes report double-digit improvements in throughput or memory use just by changing the allocator through an environment variable. The Linux kernel needs the same service for its own objects (inodes, sockets, network buffers), and it uses slab allocators for it.
For the layer above (language runtimes, databases, caches, the kernel), the allocator turns "give me n bytes" into a fast, mostly lock-free operation with bounded waste. The layers below supply the data structures. Trees and heaps (L3) organise free memory: buddy allocators are binary trees of blocks, and best-fit allocators keep free blocks in size-ordered trees or heaps. Queues and lists (L3) hold free blocks of one size, so that allocation is "pop the head" and free is "push the head", each in constant time.
terms: Heap — the region of address space from which dynamically allocated memory is carved; the allocator manages it.
Size class — one of a fixed set of block sizes (for example 16, 32, 48, 64 bytes); a request is rounded up to the nearest class.
Free list — a linked list of free blocks of the same size class; the link pointer is stored inside the free block itself.
Internal fragmentation — memory wasted inside an allocated block because the block is larger than the request (rounding, headers).
External fragmentation — free memory that exists in total but is split into pieces too small to satisfy a request.
Arena — a large region (or a set of regions) managed as one unit, either to reduce lock contention (one arena per thread group) or to free everything at once.
Thread cache — a small per-thread stock of free blocks, so most allocations and frees need no lock.
Slab — a run of pages cut into equal-sized slots for one kind of object; a free slot is reused for the same kind of object.
Bump allocator — an allocator that only moves a pointer forward; it cannot free single objects, only reset the whole region.
history: The first allocators were written when memory was counted in kilobytes. Donald Knuth described the classic techniques in The Art of Computer Programming, volume 1 (1968): a free list, first-fit and best-fit search, and boundary tags, which are small headers (and footers) on every block that let the allocator merge a freed block with its free neighbours in constant time. Kenneth Knowlton published the buddy system in 1965: memory is split in halves, each block has exactly one buddy, and freeing a block merges it with its buddy if that is also free.
Doug Lea's dlmalloc (around 1987, widely used through the 1990s) combined boundary tags with bins of free chunks grouped by size. Its descendant ptmalloc, by Wolfram Gloger, added multiple arenas for threads and became the malloc of GNU libc. In 1995 Paul Wilson and co-authors published a large survey of dynamic storage allocation, and in 1998 Johnstone and Wilson showed that simple policies such as address-ordered first fit and best fit cause much less fragmentation in real programs than people had feared.
Multi-core machines changed the problem: one global lock on the heap made threads wait for each other. Jeff Bonwick's slab allocator (SunOS 5.4, 1994) introduced object caches that keep initialised objects ready for reuse; he extended it with per-CPU "magazines" in 2001. Linux adopted the slab idea in the late 1990s and later added SLUB (default since 2.6.23, 2007); the older SLAB and SLOB variants were removed in recent kernels. For user space, Sanjay Ghemawat's tcmalloc at Google used per-thread caches, and Jason Evans wrote jemalloc (BSDCan 2006, FreeBSD 7, then Firefox and Facebook). Daan Leijen, Ben Zorn and Leonardo de Moura at Microsoft Research published mimalloc in 2019, using "free list sharding" to make both allocation and free fast and cache friendly. Go and Java runtimes build on the same ideas, with a garbage collector doing the freeing.
how: The core job has two halves. On allocation, find a free block big enough. On free, put the block back so it can be reused and, if possible, merged with neighbours. Everything else is a choice about how to organise the free blocks.
The classic design keeps every block preceded by a small header with its size and a flag. A free block stores list pointers in the space the program is not using. glibc on a 64-bit machine rounds each request plus an 8-byte header up to a multiple of 16 bytes, with a minimum chunk of 32 bytes. Free chunks are kept in bins: exact-size lists for small sizes, ordered lists for larger ones. When a request arrives, the allocator looks in the bin for that size, and if it is empty it splits a larger chunk. When a chunk is freed, boundary tags show whether the neighbours are free, and adjacent free chunks are coalesced into one larger chunk. Without coalescing, a long run of small frees would leave memory in thousands of useless fragments.
Modern allocators replace the single global structure with size classes and caches. A request is rounded up to a class. jemalloc uses four classes per doubling (for example 128, 160, 192, 224, 256, 320, 384 and so on), which keeps internal waste below about 20%. Go has roughly 70 classes. Each class has its own free list, so allocation is "pop one block from the list of this class", which is a few instructions. Each thread owns a cache of such lists (tcmalloc's thread cache, jemalloc's tcache, Go's per-processor mcache), so the fast path touches only memory owned by that thread and needs no lock. When the thread cache is empty it refills a batch of blocks from a shared central list under a lock; when it is too full it returns a batch. Batching is the idea that makes the design scale: the lock is taken once per many allocations, not once per allocation. glibc's own tcache (since version 2.26, 2017) works the same way for small sizes, with up to 7 blocks per size class by default.
Where do blocks come from? The allocator asks the kernel for large regions using mmap (or brk for the classic heap) and cuts them into pieces. Slab-style designs cut one run of pages into slots of a single size class and track which slots are free with a bitmap or a free list, so the allocator needs no per-block header at all. That removes the header cost and means a freed slot always fits the next request of that class, so there is no external fragmentation within a class. The price is that a page is dedicated to one size class until all its slots are free. Large requests (glibc uses a default threshold of 128 KB) bypass all of this and go directly to mmap, so that free can return the memory to the kernel at once.
Where do the lower layers help? Free lists are plain queues or stacks: constant-time push and pop at one end, and the last-freed block, which is likely still in the CPU cache, is reused first. Trees and heaps appear where order matters. A buddy allocator is a complete binary tree over memory: block sizes are powers of two, a request of n bytes is rounded up to the next power of two, and finding or merging a buddy is a matter of flipping one bit of the address, so both operations are O(log of memory size). The Linux page allocator uses this scheme. Other allocators keep free extents in a red-black tree or a heap ordered by size and address, so that "best fit" or "lowest address first" is a logarithmic search; jemalloc uses such trees and heaps to choose which extent to carve, preferring low addresses so that memory at the top becomes free and can be returned.
Returning memory is the third half of the job that is often forgotten. A thread that frees a block allocated by another thread must hand it back to the owner's structure (mimalloc does this with a lock-free list per page). Allocators also decide when to give empty pages back to the OS, with madvise or munmap. jemalloc uses decay timers (by default about ten seconds) so that a burst of freed memory is not returned and requested again a moment later. Arena (region) allocators avoid the question: they bump a pointer for each allocation and release everything together at the end of a request or a query, which is why compilers, game engines and many servers use them for short-lived data.

example: Part one: rounding and waste. A program asks for 100 bytes. With glibc, the chunk is 100 + 8 = 108 bytes, rounded up to the next multiple of 16, which is 112 bytes. The program can use 104 bytes of it. So 12 bytes of every 112 are overhead (about 11%). If the program stores 10 million such objects, the total is 1.12 GB, of which about 120 MB is overhead. A dedicated slab cache for 100-byte objects (the Linux kernel aligns object sizes to 8 bytes) needs only 104 bytes per object, so the same 10 million objects take 1.04 GB, and the saving is about 80 MB. A general class system pays the rounding but gains speed. A request of 129 bytes in a class system with classes 128 and 160 takes 160 bytes, wasting 31 bytes (19%). This is the worst case that four classes per doubling allows.
Part two: external fragmentation, step by step. Use a heap of 1,024 bytes and fixed 64-byte allocations. Allocate 16 blocks, which fills the heap exactly. Free every second block: blocks 1, 3, 5 and so on up to 15. Now 8 blocks are free, 512 bytes in total, which is half the heap. A request for 128 bytes fails: every free block is 64 bytes and none is adjacent to another free block, so nothing can be merged. The free memory is not lost, but it cannot be used for this request. A size-class allocator avoids the problem when the later requests are 64 bytes again, because the holes are exactly the right size. It does not help if later requests are all 128 bytes: the pages stay dedicated to the 64-byte class until every slot in a page is free.
intuition: A storekeeper who keeps shelves of pre-cut boxes in standard sizes, with a small tray at each counter so that the clerks rarely need to walk to the warehouse.
The design is natural because the real costs are different in each place. Searching for a block that fits exactly is slow, but rounding to a small set of sizes makes every request match a ready list. Taking a lock is slow, but taking it once for 32 blocks makes the cost small per block. Handing memory back to the OS is slow and risky, so it is done late and in bulk. Each trick turns a per-operation cost into a per-batch cost, and the price is a bounded amount of wasted memory that you can calculate in advance.
mistakes: People often think free(p) returns memory to the operating system. In fact it usually only returns the block to the allocator, which keeps the page for reuse. The process memory (RSS) that tools show may stay high after a program frees most of its data, especially when a few live objects pin pages in the middle of the heap. Only large blocks (mmap-ed ones) and pages that the allocator decides to release go back.
People often think a memory leak is the only reason memory grows. In fact fragmentation can make a program with a constant amount of live data grow over days: the live bytes are the same, but they are scattered over more pages. Long-running servers with changing request sizes show this. Comparing live bytes reported by the allocator with the resident set size tells you which problem you have.
People often think a faster allocator always helps. In fact the allocator choice matters only if the program allocates heavily, and a lower-fragmentation allocator may be slower, while a faster one may use more memory because it keeps larger caches per thread. With 200 threads, a per-thread cache of 1 MB is already 200 MB. Measure before switching.
tradeoffs: Choose a general size-class allocator with thread caches (jemalloc, tcmalloc, mimalloc) when a multi-threaded server allocates and frees many small objects and runs for days. The thread caches remove lock contention, and bounded size classes limit fragmentation. You give up some memory: caches and rounding can add roughly 10 to 20% over the exact sizes, and tuning knobs differ between libraries.
Choose the default libc allocator when allocation is not on the critical path, you need the fewest surprises across platforms, or the program is single-threaded. It is well tested and needs no extra dependency, but under many threads its per-thread arenas can hold on to memory that the process does not use (a common cause of large resident size on containers with many cores), and you may need to limit arenas with MALLOC_ARENA_MAX.
Choose an arena or bump allocator when many objects share one lifetime, such as everything allocated while handling one request, compiling one file or running one query. Allocation is a pointer increment and freeing is one reset, so it is both the fastest and the most compact choice. You give up freeing single objects: one long-lived object kept in the arena keeps the whole region alive.
friction: Fragmentation cannot be removed in general: Robson showed in 1971 that for any allocator there are request sequences that force a heap much larger than the live data, and a non-moving allocator cannot compact memory, because the program holds raw pointers. Only systems that can move objects and update references (garbage-collected runtimes with compacting collectors) can defragment, and they pay with pauses or barriers.
Multi-threading creates its own failures. Producer-consumer patterns, where one thread allocates and another frees, push blocks from one thread cache to another through the central lists, so the fast path no longer applies. Per-thread caches multiply with the number of threads and can waste memory. False sharing appears when two threads' objects land in the same 64-byte cache line.
Memory safety is mostly invisible to the allocator, and it is a security surface. Use-after-free, double free and heap overflow bugs exploit the metadata layout: classic allocators keep size fields and list pointers next to user data, so an overflow can corrupt them. Hardened allocators (scudo, glibc's safe-linking, tagged memory) add checks and randomisation at a cost of a few percent.
practice: Start from measurements. Compare the resident set size with the live bytes the program believes it holds; a large gap points at fragmentation or caching, not at a leak. Take a heap profile (jemalloc's prof, tcmalloc's heap profiler or your language's tools) before changing anything.
For a native or JVM service with heavy native allocation, try jemalloc or tcmalloc by setting LD_PRELOAD or linking it, and compare throughput, tail latency and resident memory under a realistic load for at least a few hours, because fragmentation shows slowly. For glibc, limit arenas with MALLOC_ARENA_MAX (for example 2 to 4) on machines with many cores, and consider MALLOC_TRIM_THRESHOLD_ to control when the top of the heap is returned. Redis reports fragmentation as mem_fragmentation_ratio (RSS divided by used memory); a value well above 1.5 means a lot of wasted resident memory, and Redis has an active defragmentation option.
In your own code, group objects by lifetime. Use arenas or pools for request-scoped data and avoid allocating in inner loops: reuse buffers, reserve vector capacity, and prefer a few large allocations to many small ones. In Java, watch off-heap use (direct buffers, Netty) separately from the heap. In containers, remember that the memory limit counts resident pages, so an allocator that keeps freed pages will hit the limit sooner than the program's live data suggests.
interview: Explain what happens, step by step, when a multi-threaded program calls malloc(48) and then free on the result. || The request is rounded to a size class. The thread looks in its own cache for that class; if there is a block it pops it, with no lock. If the cache is empty, it takes a batch from a central list under a lock, or carves a new run of pages from the OS. free pushes the block on the thread cache; if the cache grows beyond a limit, a batch goes back to the central list. Pages become free for the OS only when all their blocks are free and the allocator decides to release them.
Your container is killed for exceeding its memory limit, yet the heap profile shows live data far below the limit. What do you check? || Resident set size versus live bytes: fragmentation, per-thread caches and per-thread arenas retaining freed memory. Also off-heap memory (direct buffers, mmap-ed files, thread stacks). Try limiting arenas, a different allocator, or periodic trimming, and check whether allocation sizes changed over time.
Why can a non-moving allocator never fully solve fragmentation, and what do garbage-collected runtimes do differently? || The program holds raw addresses, so the allocator cannot relocate live blocks to close gaps. A copying or compacting collector knows every reference, moves live objects together and updates the references, so free space becomes contiguous. The cost is pauses or read/write barriers and extra memory for copying.
When would you build a custom allocator, and what do you risk? || When profiling shows allocation as a top cost and the lifetimes are regular (request scope, per-query, fixed-size objects). You get faster allocation and better locality. You risk memory-safety bugs, leaks that tools no longer see, loss of the library's hardening and profiling, and a maintenance burden.
quiz: What do size classes buy an allocator, and what do they cost? || A request is rounded up to a fixed size, so each class has its own free list and allocation is a constant-time pop. The cost is internal fragmentation: with four classes per doubling the waste is below about 20% per block.
Why do per-thread caches make allocation scale on many cores? || Most allocations and frees touch only the thread's own cache, so no lock is needed. The shared lock is taken only to move a whole batch of blocks to or from the central lists, so its cost is spread over many operations.

The request fails (without moving objects), which is external fragmentation.

@@ ebpf
value: eBPF lets you load a small program into the running Linux kernel and attach it to an event: a packet arriving on a network card, a system call, a function entry inside the kernel, a disk request, a timer. The program runs in the kernel at that moment, with direct access to the data, and without a reboot, a kernel module, or a change to the application being observed. Before the kernel accepts the program, a checker called the verifier proves that the program cannot crash the kernel, loop forever or read memory it should not touch.
This solves an old conflict. The kernel is the best place to see and control everything (every packet, every file open, every scheduler decision), but changing the kernel is slow and dangerous: a bug in a kernel module crashes the whole machine, and a patch takes years to reach production. User-space tools that watch the kernel from outside pay a high price, because they copy every event across the boundary. eBPF moves the code to the data and makes it safe by construction. For the layer above, this means Cilium can do load balancing and network policy for Kubernetes inside the kernel, observability tools (bpftrace, Pixie, Parca, Datadog and Grafana agents) can profile a production system with a low overhead and no code change, and security tools (Falco, Tetragon) can see and block system calls. Meta's Katran load balancer and Cloudflare's DDoS defence also run packet filters in the kernel's earliest network hook.
Three lower-layer ideas make this work. JIT compilation (L3) turns the verified bytecode into native machine instructions, so the program runs at close to the speed of kernel C code. Graph algorithms (L3) let the verifier check the program's control-flow graph: it must be a graph without unreachable code and without unbounded loops. Dataflow analysis (L3) lets the verifier track, for every register and at every instruction, which values the register may hold, so it can prove that each memory access stays in bounds.
terms: Verifier — the kernel component that analyses an eBPF program before it is loaded and rejects it unless it is proven safe.
Hook (attach point) — a place in the kernel where a program can run: XDP at the network driver, tc, kprobes, tracepoints, cgroup and security (LSM) hooks.
Map — a kernel data structure (hash, array, ring buffer and others) that eBPF programs and user-space processes use to share data and keep state.
Helper function — a function the kernel exposes to eBPF programs (read a map, get the current time, send a packet), because programs cannot call arbitrary kernel code.
XDP — eXpress Data Path, a hook in the network driver that runs a program on each packet before the kernel builds its normal packet structure.
BTF and CO-RE — type information about the running kernel (BTF) that lets a program compiled once adjust its field offsets when it loads on a different kernel version (Compile Once, Run Everywhere).
Context — the pointer a program receives on entry, which points to the event data (for example the packet bytes or the system call arguments).
Tail call — a jump from one eBPF program to another, used to split a big program into pieces, with a limit of 33 chained calls.
history: In 1992 Steven McCanne and Van Jacobson designed the BSD Packet Filter (published at USENIX in 1993) so that tcpdump could decide inside the kernel which packets to copy to user space. It was a small virtual machine with two registers, and filtering in the kernel was much faster than copying every packet. Linux adopted this "classic BPF", and in 2012 seccomp-BPF reused it to filter system calls for sandboxes.
Alexei Starovoitov (then at PLUMgrid, later at Facebook/Meta), with Daniel Borkmann, extended the design into "extended BPF": 11 64-bit registers that map well onto real CPUs, a 512-byte stack, calls to kernel helpers, maps for shared state, and a verifier. It was merged in Linux 3.18 (December 2014), with the bpf() system call as its interface. Over the following years the hooks multiplied: kprobes and tracepoints for tracing (about Linux 4.1), XDP in 4.8 (2016), cgroup hooks for container networking, BPF-based security modules (LSM) in 5.7 (2020), ring buffers in 5.8, and bounded loops in the verifier in 5.3. The 1 million instruction limit for the verifier's analysis arrived in 5.2.
Brendan Gregg at Netflix made eBPF the base of Linux performance analysis, and bpftrace (2018) gave it a short scripting language. Cilium (Isovalent, now part of Cisco) showed in 2016 and after that Kubernetes networking could skip iptables. The BTF and CO-RE work (2019 onward) removed the need to compile programs on the target machine. Meta, Google, Microsoft, Netflix and Isovalent founded the eBPF Foundation within the Linux Foundation in 2021. Microsoft ported the runtime to Windows. In 2024 (Linux 6.12) sched_ext allowed the CPU scheduler itself to be written as an eBPF program. The name "eBPF" no longer stands for anything: it is the name of the technology.
how: A program starts as restricted C (or Rust) and is compiled by LLVM or clang to eBPF bytecode, a stream of 8-byte instructions for the 11 registers. The loader calls the bpf() system call with the bytecode. The kernel then does four things: it verifies, it JIT-compiles, it attaches, and it runs the program on events.
Verification has two steps, and both are classic computer-science algorithms. First, the verifier builds the control-flow graph of the program and walks it with depth-first search. It rejects unreachable instructions, jumps out of range and, in the older rule, any back edge (a loop). Newer kernels accept loops if the verifier can prove a bound on the number of iterations, or if the program uses a helper such as bpf_loop. This is graph algorithms at work: reachability and cycle detection on the control-flow graph, which exists because every program is split into basic blocks connected by jumps.
Second, the verifier simulates the program on every path, starting at the first instruction, keeping a state for each register and each stack slot. This is a dataflow analysis, a form of abstract interpretation. For every register it records a type (pointer to the context, pointer to a map value, pointer to the stack, scalar number, possibly-NULL pointer) and, for scalars, a range: minimum and maximum, signed and unsigned, plus a "tnum" that records which individual bits are known. A branch such as "if (x > 8)" narrows the range differently on the two sides: x is at least 9 on one path and at most 8 on the other. A memory access is accepted only if, on every path that reaches it, the pointer has a known type and the offset plus size is inside the object. The result of a map lookup is "pointer or NULL", and dereferencing it before a NULL check is an error. Reading a register that was never written is an error. To keep the number of paths under control, the verifier prunes: if it reaches an instruction in a state that is a subset of one already proven safe, it stops exploring that path. A global limit of 1 million analysed instructions protects the kernel from programs that make the analysis explode.
After verification, the JIT compiler translates each bytecode instruction into native machine code for the CPU (x86-64, ARM64, RISC-V and others). Because the register set was designed to match real CPUs, the translation is nearly one to one and takes a single pass. This is the JIT idea from the lower layer in its simplest form: no profile, no deoptimisation, just a fast, safe translation of already verified code. Safety hardening is part of this step: the JIT can blind constants against JIT-spraying attacks, and the kernel enforces that the generated code pages are not writable and executable at the same time. The result is that the program runs at close to the speed of compiled kernel code, with no interpreter in the loop.
Attachment connects the program to a hook. The kernel type-checks that the program type matches the hook: a program for XDP may return actions such as XDP_PASS, XDP_DROP or XDP_TX, a tracing program only observes. Then, whenever the event happens, the kernel calls the native code with a context pointer. State lives in maps. A hash map can count events per process; an array map can hold configuration; a ring buffer sends events to user space; a per-CPU map avoids contention by giving each core its own copy. User space reads and writes the same maps through file descriptors. This is how a tool shows "top processes by syscalls" without ever copying individual events.
The safety model has a clear boundary. A program cannot call arbitrary kernel functions; it uses a fixed set of helpers, and newer "kfuncs" with type information. It cannot allocate memory freely, hold locks for long or run longer than the verifier's bound. The price of that safety is that the verifier is conservative: it proves safety by analysis, and an analysis that cannot see why code is safe says no.

example: Example one, a tool you can run. This bpftrace command counts file opens per process: bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'. bpftrace compiles the one line into an eBPF program, loads it and attaches it to the tracepoint that fires on every openat system call. Each time a process calls openat, the program reads the process name (comm), uses it as a key into a hash map and adds 1. Say a busy host makes 200,000 opens per second. The program does a few dozen instructions per event, about 100 to 300 nanoseconds including the map update, so the overhead is about 2 to 6% of one core. When you press Ctrl-C, bpftrace reads the map once and prints one line per process name. A user-space tool that traced every call with strace would stop the process on every system call and slow it down by large factors.
Example two, the verifier at work. Consider a program that looks up a counter in a map and increments it: val = bpf_map_lookup_elem(&counts, &key); *val += 1. The verifier rejects it with a message like "R0 invalid mem access 'map_value_or_null'". After the call, register R0 has the type "map value or NULL". On the path where the lookup fails, R0 is NULL, so the write would crash the kernel. The fix is the line if (!val) return 0; before the write. Now the verifier splits the state at the branch: on the path where val is zero it returns, and on the path where val is non-NULL, R0 has the type "pointer to a map value" and the write is accepted, provided the offset is inside the value size.
Now an array example with numbers. A map value is 128 bytes, an array of 16 values of 8 bytes. The program reads an index i that comes from a packet and writes arr[i]. The verifier knows i is any 32-bit number, so the access can go far out of bounds, and it rejects the program. After you add if (i >= 16) return 0;, the verifier records that i is between 0 and 15 on the fall-through path. The largest offset is 15 × 8 = 120, and 120 + 8 = 128 is inside the value, so the access is accepted. If the array had 17 slots in the check but only 16 in the map, the verifier would reject it again, because it checks the real size and not your intention. If the compiler turns your check into a form the verifier cannot follow (for example by reordering or using a 64-bit versus 32-bit comparison), the program is rejected although it is correct. Many eBPF developers spend time on exactly this problem.
intuition: Plug-ins for the kernel, where a strict inspector checks every plug-in by walking through all of its possible paths before it is allowed to run.
The design works because safety is moved from run time to load time. A language interpreter checks every memory access while running and pays on every step. The verifier checks all paths once, in advance, so the native code that runs afterwards has no checks left and still cannot go wrong. The restrictions (no unbounded loops, no free pointers, a fixed set of helpers) are what make the proof possible: a program that is allowed to do less is a program whose behaviour can be fully analysed.
mistakes: People often think eBPF programs are interpreted and slow. In fact they are translated to native machine code by the JIT on common architectures, so the cost of an event is the cost of a few dozen native instructions plus any map access. The interpreter exists only as a fallback.
People often think the verifier guarantees that a program is correct. In fact it guarantees only safety: no invalid memory access, no unbounded run time, no kernel crash. A program can still drop all your traffic, count wrongly or use a lot of CPU. The verifier says "cannot harm the kernel", not "does what you want".
People often think eBPF is only for tracing. In fact tracing was the first big use, but eBPF also forwards, filters and balances network packets (XDP, tc), enforces security policy (LSM, seccomp-like hooks), implements scheduler policy (sched_ext), and collects metrics and profiles for whole fleets. Tracing is one of several program families.
tradeoffs: Choose eBPF when you need per-event visibility or control at kernel speed on a production system, for example packet filtering at millions of packets per second per core, or low-overhead profiling of all processes. You get safety without a reboot and overhead measured in nanoseconds per event. You give up simplicity: you write restricted code, fight the verifier, and depend on kernel features that differ between versions (often 5.x or newer for modern features).
Choose a kernel module or a kernel patch when you need things that eBPF forbids: arbitrary data structures, long loops, blocking operations, or a new device driver. You gain freedom and give up safety and portability; every kernel update can break the module.
Choose user-space solutions (DPDK, libpcap, application-level metrics) when you cannot rely on a modern kernel, or when you want full control over memory and scheduling with ordinary debugging tools. DPDK polls the network card from user space and can reach very high packet rates, but it takes whole cores and bypasses the kernel stack. XDP gives a middle path: it keeps the kernel's drivers and tooling, and handles packets early.
friction: The verifier is the main source of pain. It rejects programs that are correct but whose safety it cannot prove, particularly after the compiler optimises code. Error messages are long dumps of register states. The 1 million instruction analysis limit, the 512-byte stack, the 33 tail-call limit and the limit on program size mean that big programs must be split. Debugging has no breakpoints; you print with bpf_printk or inspect maps.
Portability is hard. Kernel structures change between versions, helper functions and program types appear in specific releases, and cloud vendors ship different kernels. CO-RE helps with structure layout but not with missing features, so enterprise Linux 4.18 or 5.4 kernels may lack things that a recent kernel has.
Security is a two-sided problem. The verifier is complex code inside the kernel, and bugs in it have led to privilege escalation vulnerabilities. For this reason many distributions disable unprivileged eBPF by default and require CAP_BPF or root. Attackers also use eBPF to hide rootkits and to intercept data, so teams monitor which processes load programs. Finally, eBPF observability tools see everything on the host, including secrets in memory buffers and plain-text network data, which creates a privacy and compliance question for production use.
practice: Do not start by writing C. Start with bpftrace and the ready-made tools from the BCC and bpftrace collections (execsnoop, biolatency, tcplife, runqlat, opensnoop); they answer many production questions on their own. Learn to read the counts, histograms and latency distributions they produce, and use them on a staging host first.
When you build a program, use libbpf with CO-RE and a recent kernel (5.8 or newer gives ring buffers and CAP_BPF, and is a reasonable minimum for new work), or a framework such as Cilium's ebpf library for Go, or Aya for Rust. Keep programs small and filter early: drop uninteresting events in the kernel, aggregate in maps, and send only summaries to user space. Use per-CPU maps for counters and the ring buffer for event streams. Always handle NULL from map lookups and check every bound before using a value as an index or length.
For networking on Kubernetes, Cilium replaces kube-proxy and iptables rules, which grow linearly with the number of services, with hash-map lookups that stay constant in time. For production safety, test on the exact kernel versions you run, set limits on who may load programs, and watch the overhead of your own tools with the same tools.
interview: Why does the verifier reject loops, and how do current kernels allow some? || An unbounded loop could keep a CPU in the kernel forever, and the verifier must prove termination. It rejected all back edges at first. Now it simulates iterations and accepts a loop if it can prove a bound within the 1 million step budget, or if the program uses bpf_loop or iterators that the kernel runs with a known limit.
How does the verifier prove that a memory access is safe? || It simulates every path and tracks for each register a type and a value range (min, max, known bits). A pointer must have a known type, and offset plus size must lie inside the object on every path. Conditional branches narrow ranges, so a bounds check in the program is what makes the access provable. Lookups that can return NULL must be checked first.
Compare XDP, tc and DPDK for packet processing. || XDP runs in the driver before the kernel builds a socket buffer, so it is the cheapest place to drop or redirect, and it keeps the kernel stack for other traffic. tc runs later with more metadata and can see egress too. DPDK moves the card to user space and polls it, which is fastest for dedicated appliances but takes whole cores and loses kernel tools.
A fleet-wide eBPF profiler adds 8% CPU overhead. How do you reduce it? || Sample instead of tracing, lower the frequency, filter by process or cgroup in the kernel, aggregate in per-CPU maps rather than sending events, avoid stack-walking for every event, and batch reads from user space. Then measure the overhead again with the tool itself.
What are the main risks of letting teams load eBPF programs in production? || Verifier bugs can allow privilege escalation, a program can add latency on a hot path or lose data, a tool can see sensitive data, and programs depend on kernel version. Control with capability checks (CAP_BPF), signed or reviewed programs, an inventory of loaded programs, canary kernels and overhead budgets.
quiz: What are the two checks the verifier performs, and which lower-layer ideas do they use? || First, it walks the control-flow graph (graph algorithms, depth-first search) to reject unreachable code and unbounded loops. Second, it simulates every path to track types and value ranges per register (dataflow analysis), so each memory access is proven in bounds.
Why is the JIT step simple for eBPF compared with a JavaScript or Java JIT? || The bytecode is already verified and has no run-time types to profile. Its 11 registers match real CPUs, so each instruction translates almost one to one in a single pass, with no profiling and no deoptimisation.
A program does v = bpf_map_lookup_elem(...); *v += 1; and is rejected. Why, and what is the fix? || The lookup returns a pointer that may be NULL, so the verifier marks R0 "map value or NULL" and rejects the write. Add if (!v) return 0; so the write happens only on the non-NULL path.
A map value is 128 bytes, an array of 16 64-bit numbers. The program indexes it with i read from a packet. What check makes it accepted? || A check such as if (i >= 16) return; on the path before the access. The verifier then knows i is in 0 to 15, the largest offset is 15 × 8 = 120, and 120 + 8 = 128 fits inside the value.
When is it better to use sampling than eBPF event tracing? || When events are extremely frequent, such as every packet or scheduler switch. Sampling at about 99 Hz costs almost nothing and shows where time goes statistically; tracing every event gives exact counts but can cost several percent to tens of percent on a hot path.

@@ pagereplace
value: Demand paging means that the operating system loads a page of a program or file into RAM only when the program first touches it. Page replacement is the second half of the idea: when RAM is full and a new page is needed, the system must choose a page to throw out. Together they let a program use more memory than the machine has, start in milliseconds instead of waiting for its whole image to load, and share one RAM among many processes.
The problem is the gap in speed. A RAM access takes about 100 nanoseconds. Reading a page from an SSD takes about 100 microseconds, a thousand times more, and from a spinning disk about 5 to 10 milliseconds, around 100,000 times more. So one wrong eviction (throwing out a page that is needed again in a moment) costs as much as thousands of ordinary instructions. A good policy keeps the pages that will be used soon, which means the system can run almost at RAM speed with a RAM much smaller than the total data. A bad policy, or too little RAM, leads to thrashing: the machine spends nearly all its time moving pages and almost none running programs.
For the layer above, this machinery is the base of cache eviction (LRU, clock and their successors started here), the page cache (file pages are evicted by the same rules), and the memory limits that containers and databases live under. Two lower layers do the work. Virtual memory and paging (L3) provide the page tables, the "present" bit that causes a fault when a page is not in RAM, and the hardware "accessed" and "dirty" bits that tell the kernel which pages were used and changed. Storage devices (L3) provide the backing store: the swap area or the file from which a page returns, and their speed sets the price of every fault.
terms: Page fault — a trap raised by the CPU when a program touches a page whose page-table entry says "not present"; the kernel handles it and the instruction is retried.
Minor fault — a fault that is solved without disk I/O, for example the first touch of a zero-filled page or a file page already in the page cache.
Major fault — a fault that needs I/O, such as reading a page from swap or from a file on disk.
Frame — one page-sized slot of physical RAM; a page is loaded into a frame.
Working set — the set of pages a program uses during a recent time window; if RAM holds it, the program runs fast.
Reference bit (accessed bit) — a bit in the page-table entry that the hardware sets on every access; the kernel clears it to learn which pages are used.
Dirty page — a page changed since it was loaded; it must be written back before its frame is reused.
Thrashing — a state where the combined working sets exceed RAM and the system spends most of its time on page faults.
Belady's optimal (MIN) — the best possible policy, which evicts the page whose next use is furthest in the future; it cannot be built but gives a lower bound for comparison.
history: Demand paging was invented for the Atlas computer at the University of Manchester (operating in 1962). Its designers (Kilburn and colleagues) wanted programmers to see a large "one-level store" while the machine had a small core memory and a large drum; the hardware and a "learning program" moved pages between them on demand. The idea spread to Multics (MIT, Honeywell, GE, 1960s) and to IBM's systems.
Laszlo Belady at IBM studied replacement policies in 1966 and described the optimal policy, which later work uses as a yardstick. In 1969 Belady, Nelson and Shedler found a surprising case, now called Belady's anomaly: with FIFO replacement, giving a program more frames can cause more faults. Peter Denning's working set model (1968) explained thrashing: a program needs its recent working set in RAM to make progress, and if the system admits too many programs, none gets its working set and the useful work collapses. Corbató's Multics paging experiment (1969) described the clock algorithm as a cheap approximation of LRU. Mattson, Gecsei, Slutz and Traiger (1970) defined "stack algorithms" and showed that LRU belongs to this class and cannot show the anomaly.
Later work attacked LRU's weak spot, scans that flood the cache: LRU-K (O'Neil, O'Neil and Weikum, 1993), 2Q (1994), ARC (Megiddo and Modha, 2003) and CLOCK-Pro (2005) all add a notion of frequency or of "seen twice". Linux used a two-list design (active and inactive) for years, added detection of "refaults" (a page evicted and needed again soon) in the 2010s, added Pressure Stall Information (PSI) in 4.20 (2018) to measure memory pressure, and merged the multi-generational LRU in Linux 6.1 (2022), developed at Google by Yu Zhao for Android and ChromeOS.
how: Start with how a fault is served. A process touches an address. The CPU looks up the page table (through the TLB) and finds that the entry's present bit is 0. It raises a page fault and enters the kernel. The kernel's handler first checks that the address belongs to a region the process has mapped (a virtual memory area); if not, the process gets a segmentation fault. If the address is valid, the handler decides what kind of page it is. For an anonymous page touched for the first time, it takes a free frame, fills it with zeros and maps it. For a file-backed page it looks in the page cache; if the page is there (a minor fault) it only maps it, and otherwise it starts a read from the disk and puts the thread to sleep until the I/O finishes (a major fault). For a page that was swapped out, the page-table entry holds the location in the swap area, and the kernel reads it back. Finally the kernel updates the page table and the CPU retries the instruction, which now succeeds.
That path needs a free frame. The kernel tries to keep a small reserve: it wakes a background thread (kswapd in Linux) when free memory falls below a low watermark, and the thread reclaims pages until the high watermark is reached. If the reserve runs out, the faulting thread must reclaim pages itself, which is called direct reclaim and shows up as latency spikes. Reclaim chooses a victim page. If the page is clean and has a copy on disk (an unmodified file page), the frame is simply reused. If it is dirty, it must be written to its file or to swap first, which uses the storage device and takes time; this is why systems write dirty pages in the background before they are needed. Anonymous pages have no file, so they can only be evicted if there is swap space.
Which page should go? The best policy (MIN) evicts the page that will be used furthest in the future, but the future is unknown. Real systems use the past as a predictor, which is the principle of locality: pages used recently are likely to be used again soon. Exact LRU would need to update a list on every memory access, which is impossible because the hardware does not call the kernel on each access. So the hardware helps only a little: it sets the accessed bit in the page-table entry on any read or write. The kernel reads and clears that bit from time to time.
The clock algorithm uses exactly that bit. Frames are arranged in a circle with a hand. To find a victim, the hand moves forward. If the frame's accessed bit is 1, the algorithm clears it (a second chance) and moves on. If the bit is 0, the page was not used since the last sweep, so it is evicted. A page that is used often has its bit set again before the hand returns, so it stays. Cost per eviction is small and no work is done on memory accesses. When all bits are set the hand clears them all and evicts the first page it started at, so under heavy load clock behaves like FIFO.
Linux refines this. It keeps separate lists for anonymous and file pages, and each has an active list (recently used) and an inactive list (candidates). A new page starts on the inactive list; if it is referenced again before it is scanned, it moves to the active list. This two-step rule gives scan resistance: a big sequential read touches each page once, so those pages stay on the inactive list and are evicted quickly without pushing out the hot pages. To find whether a page was used, the kernel uses reverse mapping to locate every page-table entry that points to the frame and checks their accessed bits. It also stores a small shadow record when a page is evicted; if the page faults back in soon, the kernel knows the inactive list was too short and favours keeping more pages. The multi-generational LRU replaces the two lists with several generations of pages and finds recently used pages by walking page tables in bulk, which is cheaper than reverse-mapping page by page. The setting vm.swappiness (default 60) balances how much to evict from file pages versus anonymous pages.
Dirty pages need writeback. The kernel flushes them periodically and when a threshold of dirty memory is reached, and a process that dirties memory faster than the disk can absorb is slowed down (throttled). When no page can be freed and a process still needs memory, the out-of-memory (OOM) killer picks a process to kill. In containers, a cgroup memory limit applies the same logic inside the group: file cache is reclaimed first, and when anonymous memory exceeds the limit with no swap, a process is killed.

example: Part one: the cost of a fault. RAM access takes 100 ns. A major fault costs 8 ms on a hard disk, which is 8,000,000 ns. If a fraction p of accesses fault, the average time is \( (1 - p) \times 100 + p \times 8{,}000{,}000 \) ns. With p = 1 in 1,000 (0.1%), the average is about 0.999 × 100 + 8,000 = 8,100 ns, so the program runs 81 times slower. To lose only 10% (110 ns on average), we need \( p \times 7{,}999{,}900 \le 10 \), so \( p \le 1.25 \times 10^{e6} \): one fault in 800,000 accesses. On an NVMe SSD with 100 µs faults, the limit is \( p \le 10 / 99{,}900 \approx 10^{e4} \), one fault in 10,000 accesses. This is why locality and enough RAM matter so much.
Part two: policies on one reference string. Use 3 frames and the page references 1, 2, 3, 1, 4, 1, 2, 5, 1, 2. FIFO: 1, 2, 3 fault and fill the frames (1 2 3). Reference 1 is a hit. Reference 4 faults and evicts the oldest page, 1 (frames 2 3 4). Reference 1 faults again and evicts 2 (3 4 1). Reference 2 faults and evicts 3 (4 1 2). Reference 5 faults and evicts 4 (1 2 5). References 1 and 2 are hits. FIFO has 7 faults. It evicted page 1 just after it had been used.
LRU: after the first three faults, reference 1 is a hit and becomes the most recent (order from oldest: 2 3 1). Reference 4 faults and evicts the least recently used, 2 (3 1 4). Reference 1 is a hit (3 4 1). Reference 2 faults and evicts 3 (4 1 2). Reference 5 faults and evicts 4 (1 2 5). References 1 and 2 are hits. LRU has 6 faults. Optimal (MIN) looks ahead: at reference 4 it evicts 3, which is not used again; at reference 5 it evicts 4, never used again. Pages 1 and 2 stay and every later reference hits: 5 faults, the minimum.
Clock with the same string: frames fill with 1, 2, 3 and all reference bits are 1. Reference 1 is a hit. Reference 4 faults, all bits are 1, so the hand clears all three and returns to the first frame, evicting page 1 (the frames are 4 2 3 with bits 1 0 0). Reference 1 faults, evicts the frame at the hand that has bit 0 (page 2); reference 2 evicts 3; reference 5 evicts 4 (after a bit is cleared). Clock also gets 7 faults here, the same as FIFO. This tiny example shows the weakness: with few frames and recent bits all set, clock can lose the information that LRU keeps. On long references with a stable working set, clock tracks LRU closely.
intuition: Keep on your desk the papers you touched most recently; when the desk is full, put away the one you have not looked at for longest, and notice that a paper you just read once should not push out your daily notes.
The design is natural because the future is hidden but the past is visible and, in real programs, it predicts the future. Loops, stacks, hot data structures and nearby code all reuse the same pages. The clock algorithm is what remains when you ask for the cheapest possible record of the past, one bit per page set by the hardware for free, and the active and inactive lists add a second use to separate real reuse from one-time scans.
mistakes: People often think swap is only a disaster signal and should always be off. In fact a small amount of swap lets the kernel move pages that are never touched (idle daemons, old heap) out of RAM so that the space can be used for file cache. The disaster is heavy swap activity, meaning many major faults per second, not the existence of swap space.
People often think LRU is the best practical policy. In fact LRU is weak for scans and for loops slightly larger than memory: a loop over 101 pages with 100 frames faults on every access under LRU, because the page needed next is always the one just evicted. This is why systems add frequency (2Q, ARC) or random elements.
People often think more RAM always means fewer faults. In fact with FIFO it can increase them (Belady's anomaly), and with any policy the benefit stops once the working set fits; adding RAM beyond that only enlarges the file cache.
People often think high memory use in "free" output means a problem. In fact Linux uses spare RAM for the page cache, and those pages are easy to reclaim. What matters is the available memory, the rate of major faults, and pressure measures such as PSI.
tradeoffs: Choose to let the kernel manage caching (read files with ordinary I/O and rely on the page cache) when the workload is mixed or sequential, as in log processing, Kafka brokers or Spark scans. You get shared caching between processes, read-ahead and no code. You give up control: a large one-time scan can push out hot data, and you cannot tell the kernel exactly which pages matter.
Choose the application's own buffer pool with direct I/O (as many databases do) when the application knows its access pattern, for example B-tree index pages versus table scans. You get predictable eviction, no double caching and control over write ordering. You give up the kernel's shared cache and you must size memory carefully, since the database and the kernel can both cache the same data and waste RAM.
Choose swap enabled (with a small size, or compressed swap such as zswap and zram) for general servers and desktops. It smooths short memory spikes and lets idle memory go. Choose swap off for latency-critical processes and for JVM heaps, because a garbage-collection pass touches the whole heap and, if part of it is swapped out, a pause can grow from milliseconds to many seconds. You give up a safety margin against sudden growth, and gain predictability and quick OOM failure.
friction: Reference bits give only one bit of history, and clearing them has a cost: every clear must be coordinated with the TLB, and scanning millions of pages takes CPU time. On a machine with 512 GB of RAM there are 128 million 4 KB pages, so even a cheap per-page scan adds up. This is a main reason for huge pages (2 MB) and for the multi-generational LRU. Huge pages, however, make the unit of eviction coarse, and the kernel may have to split them first.
Thrashing and its cousin, memory pressure with slow storage, cause cliffs rather than smooth slowdown: a service at 90% of its memory limit may be fine, and at 105% it may stall completely. Containers add a surprise: the page cache is counted against the cgroup limit, so reading large files can use the limit, and tools that read only the "used" figure show a false alarm.
practice: Watch the right signals. Major faults per second (from vmstat, sar -B or /proc/vmstat), swap-in and swap-out rates, and the pressure files /proc/pressure/memory (PSI) tell you whether the machine is short of memory. Free memory does not. A system that shows high "used" and low "available" with a rising major fault rate is the one in trouble.
Size memory by working set, not by data size. For a database, check the cache hit ratio; for Kafka, make sure the page cache can hold the data that consumers read near the tail, and avoid running other memory-hungry processes on the broker. For JVM services such as Spark executors, keep swap off or swappiness low, set the container memory limit above heap plus off-heap plus overhead, and remember that Kubernetes memory limits kill the process on overrun and do not page.
Use hints when you know the pattern: posix_fadvise or madvise to say that a range will not be needed again (so a scan does not evict hot data), mlock for small latency-critical buffers, and huge pages for large, hot, long-lived heaps. Run bulk sequential jobs in their own cgroup with a memory limit, so that they cannot flush the cache of the neighbours. When a service slows down without a CPU or network cause, check for major faults first.
interview: What exactly happens on a page fault for an address that was never touched? || The CPU traps because the entry is not present. The kernel checks that the address is inside a mapped region with the right permissions, takes a free frame (reclaiming if needed), zero-fills it for anonymous memory, maps it in the page table and returns to retry the instruction. No disk I/O is needed, so it is a minor fault of about a microsecond.
Why can the OS not implement true LRU, and what does it do instead? || True LRU needs an update on every memory access, but the hardware does not trap on accesses. The hardware only sets an accessed bit in the page-table entry, so the kernel approximates LRU by sampling and clearing that bit (clock, active and inactive lists, generations).
A sequential scan of a 500 GB file evicts the hot working set of a 64 GB server. How do you prevent it? || Use scan-resistant policies, such as a two-list design that evicts single-touch pages first (Linux does this to a degree), and give the job fadvise(DONTNEED) or direct I/O. Isolate the job in a cgroup with a memory limit. Databases use midpoint insertion for the same reason.
How would you detect thrashing on a production host? || Look for a high major fault rate, constant swap-in and swap-out, high I/O wait with low CPU use, and PSI memory "full" stall time rising. Then reduce the working set (fewer processes, smaller heaps) or add memory; adding more threads makes it worse.
Why does a JVM heap behave so badly when it is partly swapped out? || A garbage-collection pass must read the whole heap, including cold objects, so every swapped-out page is a major fault during the pause. A pause of 50 ms becomes seconds, requests time out, and the load grows, which makes things worse. Production JVMs run with swap off or a very low swappiness.
quiz: What is the difference between a minor and a major page fault? || A minor fault is solved without disk I/O, for example by mapping a page that is already in RAM or zero-filling a new page; it costs about a microsecond. A major fault needs I/O from swap or a file and costs 100 µs on an SSD or milliseconds on a disk.
Why does the clock algorithm use a hand and the accessed bit instead of keeping an LRU list? || The hardware sets the accessed bit for free on every access, while updating a list would need kernel work on every access. The hand clears bits and evicts the first page whose bit is still clear, which means it was not used since the last pass.
Memory takes 100 ns and a major fault takes 8 ms. What fault rate keeps the slowdown under 10%? || Average time \( (1 - p) \times 100 + p \times 8{,}000{,}000 \le 110 \) gives \( p \le \) about \( 1.25 \times 10^{-6} \), one fault per roughly 800,000 accesses.
With 3 frames and the references 1 2 3 1 4 1 2 5 1 2, how many faults does LRU have, and how many does FIFO? || LRU has 6 faults and FIFO has 7. The optimal policy has 5.
A loop reads 101 pages repeatedly, and 100 frames are available under LRU. What happens, and what policy helps? || Every access faults, because the page needed next is always the least recently used one and has just been evicted. A policy that keeps part of the loop (random, MRU for loops, ARC or 2Q-like frequency tracking) keeps most of the pages in memory.

@@ fsjournal
value: A journaling file system makes a crash harmless. Every file operation changes several blocks on disk at once: creating a file updates a bitmap of free inodes, the new inode, the directory that lists the file, and often the directory's own inode. The disk can write only one block at a time, so a power cut in the middle leaves the structures disagreeing: a directory entry pointing to an inode that was never written, or a block marked free that a file still uses. Before journaling, the only cure was fsck, a program that reads every inode and block of the whole disk after a crash to find and repair such contradictions. On a multi-terabyte disk that takes tens of minutes or hours, and the machine is down meanwhile.
A journal turns the multi-block update into one all-or-nothing step. The file system first writes a description of the whole change to a small log area (the journal), and writes a commit mark. Only after that does it write the blocks to their real places. After a crash, recovery reads the journal, which is small and sequential, and replays the committed changes. Incomplete changes are ignored. Recovery takes seconds, whatever the size of the disk.
For the layer above (ext4, XFS, NTFS, JFS and so on), this is what lets the file system promise that its own structure is always consistent. Three lower layers contribute. Crash recovery with write-ahead logging (ARIES, L3) supplies the core idea: log first, apply later, and replay the log on restart. fsync and durability (L3) supply the ordering tools: the log must be physically on the disk before the commit mark, and the commit mark before the home-location writes; without flush commands, the disk's write cache could reorder all of this. Storage devices (L3) explain why the log works so well: a journal is written sequentially, which is much faster than many small random writes on both hard disks and SSDs.
terms: Journal (log) — a reserved area of the disk, used as a circular buffer, where changes are recorded before they are applied.
Transaction — a group of block changes that must happen together; the journal records the group between a begin mark and a commit mark.
Commit record — the final block of a transaction; once it is durable, the whole transaction counts as done.
Checkpoint — writing the logged blocks to their home locations on disk, after which the journal space can be reused.
Replay (recovery) — after a crash, reading the journal and re-applying every committed transaction.
Metadata — the file system's own structures: inodes, bitmaps, directories, indirect blocks; data blocks hold the file contents.
Write barrier (cache flush) — a command that forces the disk to write its cached data to stable media before later writes are done.
Ordered mode — a journal mode in which file data is written to disk before the metadata that refers to it is committed.
history: Early Unix file systems had no protection against crashes. The Berkeley Fast File System (McKusick et al., 1984) was faster, but it relied on writing metadata in a careful order and on fsck to repair the rest. As disks grew in the 1980s and 1990s, fsck time grew in proportion, and "the machine is checking its disks" became a major availability problem.
Logging had been developed in databases for years (the System R and ARIES work, Mohan and others, 1992). Robert Hagmann applied it to a file system in the Cedar File System at Xerox PARC (1987), logging metadata changes with group commit. IBM shipped JFS in AIX 3.1 in 1990, one of the first commercial journaling file systems. Veritas VxFS, SGI's XFS (1993-94), Microsoft's NTFS (1993) and ReiserFS (2001) followed. On Linux, Stephen Tweedie added a journaling layer to ext2 and called the result ext3 (merged in 2.4.15, 2001); the journaling code was a separate layer, JBD, that other file systems could use. ext4 (stable in Linux 2.6.28, December 2008) uses an improved version, JBD2, with checksums and larger limits.
Two alternatives arose in the same years. Soft updates (Ganger and Patt, 1994) keep metadata consistent by tracking dependencies between in-memory updates and ordering the disk writes, with no log. Copy-on-write file systems (WAFL, ZFS, Btrfs, APFS) never overwrite live blocks; they write new versions and switch a root pointer at the end. In 2005, Prabhakaran, Arpaci-Dusseau and Arpaci-Dusseau analysed ext3, ReiserFS, JFS and others, and showed how subtle the ordering rules are, with several real failure cases. In 2020 (Linux 5.10) ext4 gained "fast commits", which log compact descriptions of operations instead of whole blocks.
how: Take one operation, appending a 4 KB block of data to a file. It changes three blocks: the inode (new size and a pointer to the new block), the data bitmap (marks the block as used) and the data block itself. If only some reach the disk, the structure is damaged. Six partial results are possible: for example, the inode and the bitmap are updated but the data block is not, and the file now contains garbage; or the inode points to a block that the bitmap still calls free, and another file may get that block. A journal removes all six by adding a protocol.
The protocol has five steps. One, journal write: write a begin block (with a transaction number), copies of the changed blocks, and nothing else, into the journal. Two, journal commit: after those writes are durable, write the commit block. A flush must separate steps one and two, because the disk may reorder cached writes, and a commit mark that reaches the platter before the blocks it describes would make recovery trust a transaction that is incomplete. (Modern jbd2 can instead put a checksum in the commit block, so a torn transaction is detected without the first flush.) Three, checkpoint: write the changed blocks to their final locations. Four, free: mark the transaction as done in the journal's superblock so its space can be reused. Crashes are handled by position. Before the commit block is durable, the transaction does not exist for recovery, and the file system is exactly as it was before the operation. After the commit block is durable, recovery copies the logged blocks to their home locations, whether or not the checkpoint had started. Replaying a block twice does no harm, since it only rewrites the same bytes. This is the redo-only form of ARIES: a transaction becomes visible when it commits, and nothing written before the commit needs to be undone.
Real file systems group many operations into one transaction. ext4's JBD2 keeps one "running" transaction in memory that collects the changed metadata blocks of all operations; every 5 seconds by default (the commit interval) or when it is full, it closes the transaction and commits it. This is group commit: one sequential write and one flush serve thousands of operations. Applications that call fsync force an early commit. Because of this grouping, metadata operations are atomic as a batch, but a crash can lose the last few seconds of operations that were never committed.
The hardest question is what to do with file data. Journal mode logs data blocks too, so everything is written twice, once to the journal and once to its home; it protects data but halves write bandwidth. Ordered mode (the default in ext3 and ext4) journals only metadata, but forces the data blocks to disk before the metadata commit. If a crash occurs after the data write but before the commit, the file is as it was and the new data is unreferenced; if the commit succeeded, the data is already in place. A file never points to garbage. Writeback mode journals metadata and lets data go whenever; after a crash a file may have the right size but hold old contents from blocks that were freed by other files, which is a security problem as well as a correctness one. XFS and NTFS journal only metadata, but XFS records descriptions of the changes (smaller than a whole 4 KB block) and delays writing them, while ext4's classic journal logs whole blocks.
Space in the journal is a circular buffer. The head advances as transactions are written; the tail advances as checkpoints complete. If the journal fills before old transactions are checkpointed, new operations must wait. Journal blocks can also hold revoke records, which tell recovery that a block was freed and reused and must not be replayed from an older transaction. The journal size is chosen when the file system is created, from a few megabytes to a gigabyte or more.
The storage layer matters throughout. A single file creation touches several blocks that are far apart on the disk. Writing them in place costs several seeks, about 5 to 10 ms each on a hard disk. The journal writes them in one sequential run at about 100 to 200 MB/s. Checkpointing later can sort and merge the writes, and blocks that change many times in one interval are written to their home only once. On an SSD, sequential writes avoid small-write amplification inside the drive, and a flush is costly unless the drive has power-loss protection, which is why enterprise SSDs with capacitors make journaled workloads faster.

example: Use the append above with a journal of 4 KB blocks. The transaction is 4 blocks: TxB, the inode block (I), the bitmap block (B) and TxE: 16 KB written sequentially. In ordered mode the data block D is written to its home place first.
Case 1: the power fails after D is written but before TxE reaches the disk. On restart the journal scan sees TxB 17 without a valid TxE and ignores it. The inode still has the old size and the bitmap still says the block is free. The file system is consistent, and the append is lost, as if the program had not run.
Case 2: the power fails after TxE is durable but before I and B are checkpointed. Recovery finds a complete transaction 17, copies I and B to their home locations, and the file now has the new block, whose data (D) is already there. The system is consistent, and the append is kept.
Case 3: the power fails in the middle of the checkpoint, with I written and B not. Recovery replays transaction 17 again and writes both blocks; writing I a second time damages nothing.
Now the time saved. Suppose recovery after a crash must read the journal: 128 MB at 150 MB/s is less than one second, plus writing back the logged blocks, so a few seconds. fsck on a 4 TB disk with 50 million inodes must read the inode tables (50 million × 256 bytes = about 12.8 GB) and every directory and bitmap. At 150 MB/s the inode tables alone need 85 seconds if read sequentially, but fsck follows directories and extents with many seeks, and real runs take tens of minutes to hours. With journaling, the same machine is back in seconds.
intuition: Write a note of what you are about to rearrange before you start, so that if you are interrupted you can finish the job from the note, or know that you never began.
A change that touches many places cannot be made atomic by touching the places in order, because any order has a moment in between. The journal creates the missing atomic step: a single block, the commit record, which is either on the disk or not. Everything before it is a draft, and everything after it can be repeated safely. The idea is natural once you accept that the disk can do one thing atomically (write a sector), and you build bigger atomic actions from it by writing the description first.
mistakes: People often think a journaled file system never loses data. In fact the journal protects the file system's structure, not your data. A crash can still lose the last seconds of writes that were not committed, and in writeback mode it can expose stale data. Applications that need durability must call fsync.
People often think the journal doubles every write. In fact the default modes journal only metadata, which is a small share of the bytes. Only data=journal writes file contents twice.
People often think fsync on a file flushes just that file. In fact on ext4 an fsync forces the running transaction to commit, and in ordered mode this includes the data of other files in the same transaction. Older ext3 systems showed long stalls because one process's fsync waited for everybody's dirty data.
People often think rename is safe without anything else. In fact a crash after rename can leave a zero-length file if the data was not yet allocated and written; ext4 users saw this in 2009 with delayed allocation, and the kernel added heuristics (auto_da_alloc) for the replace-by-rename pattern. The safe pattern is to write a temporary file, fsync it, rename it, then fsync the directory.
tradeoffs: Choose ordered mode (the default) when you want file system consistency and no stale data at a small cost, which suits most servers. Choose writeback mode only when you control the stale-data risk (for example the application has its own log and checksums) and want slightly lower latency. Choose data=journal when small synchronous writes must survive and you accept half the write bandwidth.
Choose a larger journal (hundreds of MB to a few GB) for metadata-heavy workloads such as millions of small files, because a small journal fills and forces frequent checkpoints, which stalls operations. You give up some disk space, and recovery after a crash reads more data.
Choose a copy-on-write file system (ZFS, Btrfs) when you want snapshots, checksums for data and instant consistency without a journal. You give up some predictable performance: COW tends to fragment files that are rewritten in place, as databases do, and it needs free space headroom. Choose a journaled file system (ext4, XFS) when you want predictable layout and mature behaviour for large sequential I/O.
friction: Journaling depends on the hardware keeping its promises. A disk or SSD that acknowledges writes while the data is still in volatile cache, or reorders them ignoring flush commands, defeats the protocol; real devices and RAID controllers have had such bugs, and consumer drives without power-loss protection can lose recent writes. Write barriers cost performance, since each flush stalls the queue, and virtual disks and network storage may not pass flushes down properly.
The journal itself can become a bottleneck: all metadata operations commit through one log, so a metadata-heavy workload contends on the running transaction, and a full journal forces synchronous checkpoints. Logging whole 4 KB blocks to change a few bytes wastes bandwidth, which is part of why XFS logs deltas and why ext4 added fast commits.
Journaling cannot detect silent corruption. Bit rot, bad firmware and memory errors damage blocks without any crash, and a replayed journal will write a corrupt block as happily as a good one. Only checksums (in ZFS and Btrfs, and for ext4 metadata) can detect it, and repair needs redundancy. The exact guarantees also differ between file systems and modes, and POSIX says little about them, so portable programs must rely on fsync, rename and directory sync instead of file system folklore.
practice: Use the default journaling mode unless you have a measured reason to change it. For databases and queues, keep their own write-ahead log and call fsync as their documentation says; do not assume the file system's journal makes a plain write durable. For atomic file replacement, write to a temporary file in the same directory, fsync the file, rename it over the target, then fsync the directory.
Size and place the journal with the workload in mind. For metadata-heavy volumes, a larger journal helps. An external journal on a fast device (a small SSD or NVRAM) can speed up synchronous workloads on slow disks. Check that barriers and write caches are configured correctly on your storage: in the cloud, this means knowing whether a volume honours flushes, and with RAID controllers it means a battery or capacitor-backed cache.
After a crash, trust the journal replay, but still run periodic scrubs and checks on important volumes: tune2fs and e2fsck for ext4, xfs_repair for XFS. Monitor journal commit latency and fsync time as service metrics, because spikes in them often explain mysterious application stalls. For tests, practise failure injection: pull the power on a test machine, or use tools such as dm-flakey or CrashMonkey, to see what your application finds after a crash.
interview: Walk through what a journaling file system does for an operation that updates three blocks, and what recovery does after a crash at each step. || It writes begin, the three changed blocks and a commit record to the journal, with a flush before the commit. Then it checkpoints to home locations. A crash before the commit is durable means recovery ignores the transaction; after the commit it replays the logged blocks, which is safe to repeat. The state is either entirely old or entirely new.
Why is the flush between the journal blocks and the commit record needed? || Disks cache and reorder writes. If the commit record could reach stable media before the blocks it describes, a crash would leave a commit mark for a transaction with missing content, and replay would write garbage into metadata. Checksums in the commit record are an alternative way to detect a torn transaction.
What does ordered mode guarantee that writeback mode does not? || In ordered mode, data blocks are written before the metadata that references them is committed, so after a crash a file never points at blocks with stale or foreign contents. In writeback mode, the size and pointers may be committed before the data, and old data from a freed block can appear.
How is file system journaling different from database ARIES recovery? || The file system log is usually redo-only with physical block images: a transaction is not applied in place until it commits, so there is nothing to undo. ARIES allows uncommitted changes on disk (steal), so it logs undo information and has three recovery passes. NTFS is closer to ARIES than ext4.
Why might a team choose XFS or ext4 over Btrfs or ZFS for a Kafka broker or Spark local disks, or the reverse? || Journaled XFS and ext4 give predictable layout and throughput for large sequential appends and have low overhead; Kafka's log segments and Spark shuffle files fit. ZFS and Btrfs add checksums, snapshots and compression, but copy-on-write adds fragmentation and write amplification and needs tuning. The choice depends on whether data integrity features or raw predictable throughput matter more.
quiz: What problem does a journal solve, and how? || A multi-block update can be interrupted, leaving the structures inconsistent. The journal records the whole change and a commit mark first, so after a crash recovery either replays the complete transaction or ignores an incomplete one.
Why is replaying a journal transaction safe to repeat? || It only copies logged block images to fixed home locations, so doing it twice writes the same bytes again (idempotent). A crash during recovery is therefore harmless.
What is the role of fsync and write barriers in journaling? || They force data to stable media in the right order: journal blocks, then the commit record, then the in-place writes. Without them, the drive's cache could reorder writes and break the all-or-nothing property.
A 4 TB disk takes 40 minutes to fsck. With a 128 MB journal at 150 MB/s, roughly how long does replay take to read the journal, and why does it not depend on disk size? || About 128 / 150 ≈ 0.9 seconds to read it, plus writing back the logged blocks. Recovery reads only the journal, whose size is fixed, not the whole file system.
When would you choose data=journal over the default mode, and what do you pay? || When small synchronous writes must be fully protected, including data contents, and ordering matters. You pay by writing all data twice, roughly halving sustained write bandwidth.

value: A lock lets one thread at a time use shared data. It does not let a thread wait until the data is in a useful state: until a queue has an item, a buffer has space, a job has finished, a connection is ready. The simple answer is a loop that keeps checking ("spinning"), which burns a CPU core and still reacts slowly. A condition variable is the proper answer: the thread says "I will sleep until this condition may be true", the operating system takes it off the CPU, and another thread wakes it when the state changes. A monitor is the structured form of the same idea, a bundle of shared data, one lock that protects it, and condition variables that belong to it.
Almost every blocking component is built this way: producer-consumer queues, thread pools waiting for tasks, blocking I/O wrappers, barriers, futures, Java's BlockingQueue, Python's queue.Queue, Go's sync.Cond. The key promise is that waiting is cheap (a sleeping thread uses no CPU) and correct (the thread cannot miss the event between checking the condition and going to sleep).
Two lower layers carry this. Locks and atomics (L3) provide the mutex that protects the condition, and the atomic instructions that make the lock and the sleep/wake path fast: on Linux the uncontended case is one atomic operation in user space and only contended cases call into the kernel through futexes. CPU scheduling (L3) provides the sleeping itself: a waiting thread is moved from the run queue to a wait queue, uses no CPU, and when it is woken the scheduler puts it back in the run queue and decides when it runs. For the layer above, thread libraries and concurrency models (monitors are the classic shared-memory model) rely on these two pieces.
terms: Condition variable — an object with a queue of sleeping threads; threads wait on it and other threads signal it.
Mutex — a lock that allows one thread at a time into a critical section; a condition variable is always used together with one.
Predicate — the actual condition, a test on shared data such as "queue is not empty"; it is protected by the mutex, and the condition variable only carries the wake-up.
wait — atomically release the mutex and go to sleep on the condition variable; when woken, re-acquire the mutex before returning.
signal (notify) — wake one waiting thread; broadcast (notifyAll) wakes all of them.
Spurious wake-up — a return from wait although nobody signalled; allowed by POSIX and by Java.
Mesa semantics — a signal is only a hint: the woken thread must re-check the predicate. Hoare semantics — the signaller hands the lock directly to the woken thread, so the condition is guaranteed true.
Monitor — a module that bundles shared data, a lock held during every operation, and condition variables; Java's synchronized methods are monitors.
history: Edsger Dijkstra introduced semaphores in 1965 as the first general tool to make a thread wait for an event. They worked, but programmers had to place the P and V operations correctly everywhere, and one wrong place caused deadlock or a race. In 1974 C. A. R. Hoare published "Monitors: an operating system structuring concept". A monitor puts the shared data and the procedures that use it in one module, makes mutual exclusion automatic (only one thread is inside at a time), and gives threads condition variables for waiting. Per Brinch Hansen described a similar design in Concurrent Pascal (1975), with a simpler rule: signal must be the last statement of a procedure.
Hoare's original rule made the signalled thread run immediately, so that the condition was surely true. That is easy to reason about, but it forces two extra context switches. In 1980 Butler Lampson and David Redell of Xerox PARC described their experience with monitors in the Mesa language ("Experience with Processes and Monitors in Mesa"). They chose a different rule: signal only moves a waiter to the ready state, and the waiter must re-check the condition. This is cheaper, allows a broadcast, and tolerates timeouts and spurious wake-ups. Almost every system today follows Mesa.
POSIX threads (1995) offered pthread_cond_wait, pthread_cond_signal and pthread_cond_broadcast, and explicitly allowed spurious wake-ups. Java had wait/notify in every object from the first version (1996); Java 5 (2004) added Lock and Condition with several conditions per lock. C++11 added std::condition_variable and Rust has std::sync::Condvar. On Linux, futexes (fast user-space mutexes, added in kernel 2.5 and widely used with the NPTL threads library in 2003) became the base of both mutexes and condition variables: the kernel is called only when a thread must sleep or wake.
how: The pattern has three parts: a mutex, a shared state with a predicate, and a condition variable. Every correct use follows the same shape. The waiting thread locks the mutex, then tests the predicate in a while loop; if the predicate is false it calls wait, and when wait returns it tests the predicate again. The signalling thread locks the mutex, changes the state, and calls signal (it may do this before or after unlocking). The predicate lives in the shared data, and the condition variable holds no state of its own.
What does wait do? It performs three steps as one atomic action: put this thread on the condition variable's queue, release the mutex, and go to sleep. The atomicity is the heart of the design. If the thread unlocked first and then slept, a signal sent in between would find nobody on the queue and be lost, and the thread would sleep forever. A mutex plus condition variable closes this window, because the signaller must hold the mutex to change the state, and the waiter holds the mutex from the moment it tested the predicate until it is on the queue. On Linux, this is done with a futex: the waiter reads a sequence number while holding the mutex and asks the kernel to sleep only if the number is unchanged; a signaller changes the number and wakes sleepers, so a change between the check and the sleep is detected by the kernel.
When a thread is signalled, it is not running yet. The scheduler moves it from the condition variable's wait queue into the run queue, or directly to the mutex's wait queue if the mutex is held by the signaller. It runs when a CPU is free and it has re-acquired the mutex. On an idle machine the delay from signal to running is typically a few microseconds to tens of microseconds, longer if the target core is in a deep sleep state. The scheduler also decides fairness: the thread woken may not be the one that runs first.
Why must the predicate be re-checked in a loop? With Mesa semantics there are three ways in which the state may be false when wait returns. One, another thread may have run between the signal and the moment the woken thread got the mutex, and may have consumed the item (a "barging" thread). Two, a broadcast woke several waiters but only one item exists. Three, the system may wake a thread without any signal (a spurious wake-up, which can arise from how the kernel and library implement the wake on multiprocessors). A while loop handles all three at no extra cost; an if does not. Hoare semantics avoid the first two cases by handing the mutex directly to the woken thread, but at the price of extra context switches, and the remaining implementation details still make the loop the safe habit.
signal versus broadcast is a choice about who can make progress. If each state change enables exactly one waiter, and all waiters are equivalent, signal is enough and saves effort. If waiters wait for different conditions on one condition variable, or one change can enable many threads (a barrier opening, a shutdown flag), broadcast is the safe choice; the cost is the "thundering herd", where hundreds of threads wake, fight for the mutex, and all but one go back to sleep. The better remedy is to use separate condition variables for separate conditions: a bounded buffer uses notEmpty (for consumers) and notFull (for producers), so each signal wakes a thread of the right kind. With one shared variable and signal, a consumer could wake another consumer and a producer might sleep forever.
A monitor adds structure on top. In Java, every object has a monitor: a synchronized method acquires it on entry and releases it on exit, and wait, notify and notifyAll are only legal while holding it (otherwise an IllegalMonitorStateException is thrown). Each monitor has a single wait set, so Java 5's Condition objects allow several named conditions on one lock. The compiler or runtime makes the lock handling automatic, which removes the mistake of forgetting to unlock, but the predicate and loop are still the programmer's job.

example: Part one: why while and not if. A queue is empty. Consumers C1 and C2 sleep on notEmpty. At time 1, producer P locks, adds item X, signals (C1 is moved toward the mutex) and unlocks. At time 2, before C1 runs, a third consumer C3, which was not waiting, locks the mutex, sees one item, takes X, and unlocks. At time 3, C1 gets the mutex and returns from wait. The queue is empty. If C1 used if, it would go on to take from an empty queue (an exception, or garbage). With while, C1 tests again, finds the queue empty, and waits again. No item was lost and no one was wrong. With Hoare semantics, time 2 could not happen, because the mutex would pass directly from P to C1.
Part two: a lost wake-up. Suppose the consumer checks the queue without holding the mutex: it sees "empty" at time 1. At time 2 the producer adds an item and signals; nobody is on the condition queue, so the signal is dropped. At time 3 the consumer calls wait and sleeps. The item is in the queue, and the consumer sleeps until the next item arrives, which may never happen. A condition variable has no memory, unlike a semaphore (whose counter remembers a V); the state in the predicate is the memory. Holding the mutex during the test and wait makes the test and the sleep atomic with respect to the producer.
Part three: the cost of signalling. If a producer adds 1,000 items per second and signals each time, there are up to 1,000 wake-ups per second at roughly 10 µs of scheduler and context-switch work each, about 1% of one core. At 1,000,000 items per second the same rule would need 10 seconds of CPU per second, which is impossible. Fast queues therefore signal only when the queue changes from empty to non-empty, and consumers take items in batches while they are awake.
intuition: Leave your phone number with the receptionist and take a nap; they call you when your table is ready, and you look at the table to make sure it is really free before you sit down.
The design is natural because it separates two jobs. The mutex protects the facts about the world (is the queue empty?). The condition variable only moves a thread out of the CPU and back, with no facts of its own. Because the facts live under the lock and the wake-up is only a nudge, a wrong or extra nudge (spurious wake-up, a stolen item) is harmless: the thread looks again at the facts. This is also why the release-and-sleep step must be atomic: it is the only moment when the facts and the nudge could be out of step.
mistakes: People often think signal guarantees that the condition is true when the waiter resumes. In fact under Mesa semantics (nearly every real system) it only guarantees that the waiter will run at some point, and in between other threads may change the state. The loop is required.
People often think a condition variable remembers a signal. In fact a signal sent when nobody is waiting is lost. Semaphores count, condition variables do not. State must be stored in the shared variable and checked under the mutex.
People often think they can use one condition variable and signal for everything. In fact if producers and consumers share one condition variable and signal wakes the wrong type, the system can deadlock: a producer wakes another producer, finds the buffer full, and sleeps, while the consumer is never woken. Use separate variables or broadcast.
tradeoffs: Choose a condition variable with a mutex when the wait condition is a complex test on shared state (the queue is non-empty and the system is not shutting down), or when you need to wait with a timeout and to check several things. You get flexibility and low CPU use, and you must write the predicate loop correctly.
Choose a semaphore when the condition is a simple count of resources (N permits, a connection pool of 20). The counter remembers signals, so lost wake-ups cannot happen, and the code is shorter. You give up the ability to wait on arbitrary conditions and some clarity when more than counting is needed.
Choose a ready-made concurrent queue, a channel or a future (BlockingQueue, Go channels, CompletableFuture) when you are building application code. The library has already solved the loop, the shutdown and the signalling, so there is less to get wrong; you give up a little control over the exact locking and sometimes pay a small amount of extra overhead.
friction: The mutex plus condition variable is a low-level tool, and the bugs are subtle: forgetting the loop, signalling the wrong variable, changing the state without the lock, or checking the predicate in one place and modifying it in another. These bugs show up rarely and only under load, so tests often pass. Tools such as thread sanitizers and model checkers help, but cannot find all of them.
Performance has its own limits. A broadcast to many waiters causes a thundering herd. Waking a thread on another core costs microseconds, so a pipeline with many handoffs through condition variables has latency that adds up. Under contention the mutex itself becomes the bottleneck, since every signal and every wait takes it. Priority inversion can occur: a low-priority thread holds the mutex, a high-priority thread waits, and a medium thread runs; real-time systems use priority inheritance for this.
practice: Always write the standard pattern: lock, while (not predicate) wait, act, unlock. Prefer the library forms that take the predicate (std::condition_variable::wait with a lambda, Python's Condition.wait_for, Rust's Condvar::wait_while), because they contain the loop for you. Change the shared state only while holding the mutex, and keep the critical section short; do the real work after unlocking.
Use one condition variable per condition, and name them after the predicate (notEmpty, notFull, shutdown). Use signal when one waiter can proceed and all waiters are equal, and broadcast for state changes that affect many (shutdown, a barrier). Always include a way to stop: a shutdown flag that waiters test in the predicate, and a broadcast when it is set. Use timed waits (wait_for, wait_until) for operations that must give up, and use the monotonic clock, not the wall clock.
In JVM and Python code, prefer java.util.concurrent and queue.Queue over hand-written wait/notify. In Go, prefer channels, and use sync.Cond only for broadcasts to many goroutines. When a service hangs, take a thread dump: threads parked in a wait with no one able to signal point to a lost wake-up or a missed condition, and threads blocked on the mutex point to contention.
interview: Why must wait be called with the mutex held, and why does it release the mutex? || The predicate is protected by the mutex, so the test and the decision to sleep must happen under it. Wait releases the mutex atomically with going to sleep, so the signaller (which needs the mutex to change the state) can proceed, and no signal can arrive in the gap between the test and the sleep.
Explain Mesa versus Hoare semantics and what it means for your code. || Under Hoare semantics the signaller passes the lock directly to the waiter, so the predicate is true on return, but it costs extra context switches. Under Mesa semantics, used by POSIX, Java and C++, signal is a hint; the waiter becomes runnable and must re-acquire the lock and re-test in a loop, since the state may have changed.
A bounded buffer with one condition variable and signal sometimes hangs. What is the bug? || A signal may wake the wrong kind of thread: a consumer's signal wakes another consumer when a producer is needed, or the reverse. That thread finds its predicate false and sleeps again, and the signal is consumed with nobody making progress. Use two condition variables, or broadcast.
How would you implement a thread pool shutdown that does not lose or hang? || Add a shutdown flag in the shared state, test it in the wait predicate (while queue is empty and not shutdown, wait), set it under the mutex and broadcast. Workers drain the queue or exit as designed. Joining threads then returns, and no worker can sleep through the signal.
When is a condition variable the wrong tool? || When a count is enough (use a semaphore), when you would be waiting for several sources at once (use a channel with select, a future combinator or an event loop), when the wait is a few hundred nanoseconds (spin), or when a ready-made blocking queue exists.
quiz: What three things does wait do atomically? || It puts the thread on the condition variable's queue, releases the mutex, and puts the thread to sleep. When it wakes, it re-acquires the mutex before returning.
Why is the predicate tested in a while loop and not an if? || After a wake-up the state may have changed: another thread may have taken the item, a broadcast may have woken more threads than there is work, or the wake-up may have been spurious. The loop re-checks the state and sleeps again if needed.
What is a lost wake-up and how does the mutex prevent it? || A signal sent when no thread is yet waiting is dropped, so a thread that checks the condition and then sleeps may sleep forever. The mutex makes the check and the join of the queue atomic with respect to the signaller, so the signal cannot fall between the two.
A buffer holds 100 items; a producer makes 0.5 items per µs and consumers take 0.2 items per µs in total. How long until the buffer is full, starting empty, and what happens then? || The net fill rate is 0.3 items per µs, so it fills in 100 / 0.3 ≈ 333 µs. The producer then waits on notFull, which limits the rate to what the consumers can take.
Why use two condition variables in a bounded buffer instead of one with broadcast? || Two variables wake only threads that can make progress: a signal on notEmpty wakes a consumer. One variable with broadcast also works but wakes all threads, which then fight for the mutex and mostly go back to sleep.

@@ parsing
value: Parsing turns a flat string of characters into a structured tree that a program can work with. The text "price * (1 + tax)" is only 17 characters; the parser finds that it is a multiplication whose right side is a parenthesised addition. Nothing else can happen until that structure exists. A compiler cannot generate code from characters, a database cannot optimise a query from a string, a web server cannot route a request it has not split into method, path and headers, and a data pipeline cannot read a JSON record until it knows where the objects and arrays begin and end.
Parsing is therefore at the front of nearly everything: programming languages, SQL and query planners, JSON, CSV, YAML and Protobuf readers, HTTP and other network protocols, configuration files, log lines, regular expressions, the schema languages of Avro and Spark, and the constrained output of language models. It matters for speed (parsing is often the first cost of ingestion at scale) and for security (a parser that reads input differently from another parser is a classic source of attacks).
The lower layer that makes parsing a science and not a craft is formal languages and automata (L4). It says what kinds of structure can be recognised by which machines. Regular languages, recognised by finite automata, cover the flat pieces: numbers, identifiers, keywords, which is the job of the lexer. Context-free languages, recognised by pushdown automata (a finite machine with a stack), cover nested structure: balanced brackets, expressions inside expressions, blocks inside blocks. A grammar is a finite description of such a language, and a parsing algorithm is a way of running the matching automaton efficiently and building the tree as a by-product.
terms: Token — the smallest meaningful unit of text, such as a number, a name, a keyword or a punctuation mark; the lexer produces a stream of tokens.
Grammar — a set of rules that says how larger structures are built from smaller ones; for example expr → expr "+" term.
Context-free grammar (CFG) — a grammar in which each rule has one symbol on the left, so a rule applies regardless of the surrounding context; this covers most programming-language syntax.
Parse tree and AST — the parse tree shows every rule used; the abstract syntax tree (AST) keeps only the meaningful structure and drops punctuation and rule names.
Derivation — a sequence of rule applications that produces a string from the start symbol; parsing finds a derivation for the input.
Ambiguity — a grammar is ambiguous if some string has more than one parse tree, such as "1 - 2 - 3" read as (1 - 2) - 3 or as 1 - (2 - 3).
LL and LR — LL parsers read left to right and build the tree from the top down; LR parsers read left to right and build it from the bottom up by shift and reduce steps.
Lookahead — the number of upcoming tokens the parser inspects to decide which rule to use.
history: Noam Chomsky described the hierarchy of formal grammars in 1956-59 as part of linguistics: regular, context-free, context-sensitive and unrestricted languages, each needing a more powerful machine. In 1959-60 John Backus and Peter Naur used a context-free notation, now called Backus-Naur Form (BNF), to define ALGOL 60, and it became the way to specify programming languages. From then on, a language definition could be a grammar, and a compiler's front end could be derived from it.
The 1960s brought the main algorithms. Donald Knuth's 1965 paper "On the translation of languages from left to right" defined LR(k) parsing, which handles a very large class of grammars in linear time using a stack and a table. Frank DeRemer's LALR (1969-71) made the tables small enough for the memory of the time. Jay Earley (1970) gave a general algorithm for any context-free grammar, cubic in the worst case. Niklaus Wirth's Pascal compilers showed that LL grammars could be parsed by simple recursive functions (recursive descent). Vaughan Pratt's 1973 paper "Top Down Operator Precedence" gave a compact method for expressions. At Bell Labs, Stephen Johnson's yacc (1975) and Mike Lesk and Eric Schmidt's lex generated parsers and lexers from specifications; GNU bison and flex are their descendants. Terence Parr's ANTLR (from the 1990s; ANTLR 4 in 2013 with the ALL(*) algorithm) generates top-down parsers with adaptive lookahead.
In 2004 Bryan Ford introduced parsing expression grammars (PEG), where choices are ordered and the first match wins, so a grammar cannot be ambiguous; packrat parsing memoises results to give linear time. Python switched from an LL(1) parser to a PEG parser in version 3.9 (PEP 617, 2020). Meanwhile many production compilers (GCC for C++ since 3.4, Clang, Go, Rust, Roslyn) use hand-written recursive descent for control over speed and error messages. In data formats, Langdale and Lemire's simdjson (2019) used SIMD instructions to parse gigabytes of JSON per second, and tree-sitter (2018) brought incremental, error-tolerant parsing to editors.
how: Parsing has two stages. The lexer reads characters and groups them into tokens, using patterns that are regular expressions. It compiles those patterns into a finite automaton (a DFA, a table of states) and applies the rule of maximal munch: take the longest match, so "<=" is one token and not "<" then "=". Whitespace and comments are dropped here. This stage is a pure use of regular languages: a finite automaton needs no stack because tokens do not nest.
The parser reads tokens and applies the grammar. Nesting is the reason a stack is needed. A finite automaton cannot check that brackets are balanced, because it would need to count arbitrarily deep (the pumping lemma proves this). A pushdown automaton keeps a stack, and a context-free grammar is exactly what such an automaton recognises. Practical parsers use deterministic subclasses where each next step is decided by a bounded lookahead, which gives time proportional to the input length.
Top-down parsing (LL, recursive descent) starts from the start symbol and predicts which rule to use from the next token. Each grammar rule becomes a function: parseExpr calls parseTerm, which calls parseFactor. The call stack is the parser stack, and the tree is built as functions return. The method is simple to write and gives good error messages, because the code knows what it expected at each point. Its limit is left recursion. The rule expr → expr "+" term would make parseExpr call itself without consuming a token. The standard fix rewrites it as a loop: parse a term, then while the next token is "+", consume it and parse another term. Where two rules start with the same tokens, the parser uses more lookahead or factoring.
Bottom-up parsing (LR) reads tokens and pushes them on a stack (shift). When the top of the stack matches the right side of a rule, it replaces those symbols with the rule's left side (reduce). The table, built from the grammar by the generator, tells at each state whether to shift or reduce. LR handles left recursion naturally and accepts more grammars than LL, but the tables are hard to read and conflicts (shift/reduce) are hard to debug. Errors are reported with less context, which is one reason why hand-written top-down parsers dominate in mainstream compilers.
Expression parsing has its own method. Pratt parsing assigns each operator a binding power (a number for precedence and a side for associativity). A single recursive function parses a prefix expression and then, while the next operator binds more tightly than the current limit, continues with it. It handles precedence in a few lines and avoids the many levels of rules (expression, term, factor) that a pure grammar needs.
Some grammars are ambiguous or need unlimited lookahead. General algorithms (Earley, GLR, CYK) handle any context-free grammar, with cubic worst-case time, and are used for natural language and for languages like C++ that are hard to parse. PEGs trade ambiguity for ordering: a PEG tries alternatives in order and never backtracks over a choice that matched, with memoisation for speed.
After the tree exists, errors must be reported. Parsers recover by skipping tokens to a known synchronisation point (a semicolon, a closing brace), so one mistake does not produce a hundred. Rules that a context-free grammar cannot express, such as "a variable must be declared before use" or "types must match", are not checked here. They need a symbol table and are done in the semantic analysis that follows, because those properties are context-sensitive in Chomsky's hierarchy.
Data formats use the same ideas with different details. JSON is a small context-free grammar; a parser uses a stack to track nesting. Binary formats such as Protobuf and Avro avoid ambiguity by using length prefixes and varints, so a reader knows how many bytes to take and can skip unknown fields. This is how schema evolution works: a reader meets a field number it does not know and skips it by its length.
diagram:
  "2 + 3 * 4"
      | lexer (finite automaton, longest match)
      v
  [NUM 2] [+] [NUM 3] [*] [NUM 4]
      | parser (grammar + stack)
      v
  grammar:  expr   -> term  ( "+" term )*
            term   -> factor ( "*" factor )*
            factor -> NUMBER | "(" expr ")"

  parse tree / AST:           call trace of recursive descent:
          (+)                 parseExpr
         /   \                  parseTerm -> parseFactor -> 2
       2     (*)                sees "+"
            /   \               parseTerm
          3       4               parseFactor -> 3
                                  sees "*" -> parseFactor -> 4
  evaluate: 2 + (3 * 4) = 14
example: Use the grammar in the diagram. Input: 2 + 3 * 4. The lexer gives five tokens: NUM(2), +, NUM(3), *, NUM(4).
Recursive descent, step by step. parseExpr starts and calls parseTerm. parseTerm calls parseFactor, which sees NUM(2) and returns 2. parseTerm looks at the next token: it is "+", not "*", so parseTerm returns 2. Back in parseExpr the loop sees "+", consumes it, and calls parseTerm again. This parseTerm calls parseFactor, which returns 3. The next token is "*", so parseTerm consumes it, calls parseFactor (4), and builds the node (3 * 4). It returns to parseExpr, which builds (2 + (3 * 4)). The input is now used up. Evaluating the tree gives 2 + 12 = 14.
The layering of the grammar is what gives multiplication higher precedence: "*" is handled one level deeper than "+", so a product is complete before the sum sees it. Now try the ambiguous grammar expr → expr "+" expr | expr "*" expr | NUMBER. The string 2 + 3 * 4 has two trees: (2 + 3) * 4, which evaluates to 20, and 2 + (3 * 4), which evaluates to 14. The grammar does not say which is right, so a generator would report conflicts, and you would remove them by layering or by declaring precedence.
Pratt version with binding powers + = 10 and * = 20. parseExpr(0) reads 2. It sees "+" with power 10, which is more than 0, so it consumes it and calls parseExpr(10) for the right side. That call reads 3, sees "*" with power 20, more than 10, consumes it and calls parseExpr(20), which reads 4 and sees the end. The result is 3 * 4, then 2 + (3 * 4). If the input were 2 * 3 + 4, parseExpr(20) for the right side of "*" would read 3, see "+" with power 10, which is not more than 20, and stop, so the tree is (2 * 3) + 4.
intuition: Diagramming a sentence: decide which words belong together and what role each group plays, so that the meaning of the whole follows from the meaning of the parts.
The design is natural because language is built from parts inside parts. A stack is the simplest memory that follows this: open a group, push; close it, pop. Grammar rules say which groups can contain which. The parse tree is the record of that nesting, and every later step (type checking, optimisation, code generation, query planning) can walk the tree and treat each part separately, because the tree has already answered the question of what contains what.
mistakes: People often think regular expressions can parse anything text-like. In fact regular expressions cannot match nested structure such as balanced brackets, HTML tags or JSON, because a finite automaton has no stack. They are the right tool for tokens and the wrong tool for trees. (Some regex engines add recursion extensions, but then they are no longer regular expressions in the theoretical sense.)
People often think the parse tree and the abstract syntax tree are the same. In fact the parse tree has a node for every grammar rule application, including the chain expr, term, factor for a single number. The AST is the simplified tree, with just operators and operands, and it is what the next stages use.
People often think hand-written parsers are amateur and generated parsers are professional. In fact most major compilers (Clang, GCC for C++, Go, Rust, Roslyn) use hand-written recursive descent, because it gives better error messages, easier handling of context-dependent syntax and fine control over speed. Generators shine when the grammar changes often or must be shared by several tools.
People often think parsing is only a compiler topic. In fact every system that reads external input parses. Two parsers that disagree on the same bytes cause real vulnerabilities, such as HTTP request smuggling, where a proxy and a server see different request boundaries. The LangSec research programme argues that input formats should be simple enough to parse unambiguously and that parsing should be separated from processing.
tradeoffs: Choose a hand-written recursive-descent parser (with Pratt parsing for expressions) when the language is long-lived and you need good error messages, error recovery, or a context-sensitive trick; most mainstream compilers do. You give up the formal guarantee of a generator: nothing warns you about ambiguity, so you need a thorough test suite.
Choose a parser generator (ANTLR, yacc/bison, tree-sitter) when the grammar is large and evolving, or when you need the same grammar for several tools (compiler, formatter, editor). You get a declarative grammar, conflict detection and less code. You give up control of error messages, accept a build step, and sometimes accept slower parsing.
Choose a PEG or parser combinators for small languages and configuration formats, when you want to write the grammar as code quickly. Ordered choice means no ambiguity but also silent surprises: a rule that matches too early hides a later alternative, and left recursion needs special support. Choose a general parser (Earley, GLR) when the language is ambiguous or when the grammar is extended by users, and accept cubic worst-case time.
friction: Real languages resist neat grammars. C and C++ need to know whether a name is a type to parse a statement correctly, so the parser must read the symbol table, and the grammar is not purely context-free. Python and Haskell use indentation, handled in the lexer by inserting indent and dedent tokens. Ambiguities such as the dangling else are resolved by convention. Context-free parsing is not enough for many languages, which is why the front end is a pipeline and not one pass.
Error handling is hard. A parser that stops at the first error is easy to write, but users want all errors reported with a helpful message, and editors need trees for incomplete code. Recovery is heuristic, and a bad recovery produces many false errors. Incremental parsing (tree-sitter) addresses editors by reusing the old tree, but the engineering is complex.
Robustness needs care. Deeply nested input can overflow the stack of a recursive parser, so production parsers limit depth. Backtracking parsers and regular expressions can take exponential time on crafted input. Parsers in memory-unsafe languages have a long history of buffer overflows. Specifications are often incomplete, so independent parsers differ in corner cases, and attackers use the differences.
practice: Do not write a parser if a standard one exists: use a vetted JSON, XML, CSV, YAML or Protobuf library, and treat all input as hostile. Set limits on input size, nesting depth and number of fields. For a new small language, write a lexer and a recursive-descent parser with Pratt parsing for expressions; Nystrom's "Crafting Interpreters" shows the full path. Keep the AST separate from the parse tree, and attach source positions to every node so that later stages can report errors precisely.
When you use a generator, write the grammar for the language you want, resolve every conflict deliberately, and test with a corpus of valid and invalid inputs, including a fuzzer. For data pipelines, prefer binary formats with schemas (Avro, Protobuf, Parquet) over free text when the volume is large, because decoding by length prefix is much cheaper than scanning text, and choose parsers designed for speed (simdjson for JSON, vectorised CSV readers). When Spark or a database reports a syntax error, remember that the SQL text went through the same lexer and parser pipeline, and that the error position is where the grammar could no longer continue, not necessarily where the real mistake is.
interview: Why can a regular expression not validate balanced parentheses, and what can? || A finite automaton has bounded memory, so it cannot count unbounded nesting (shown by the pumping lemma). A pushdown automaton, which has a stack, recognises balanced brackets; a context-free grammar like S → ( S ) S | ε describes them. Practical parsers use a stack or the call stack.
What is left recursion, why does it break recursive descent, and how do you fix it? || A rule like expr → expr + term calls itself without consuming input, so the function recurses forever. Rewrite it as a loop (term followed by zero or more "+ term") or use an LR parser, which handles left recursion. Build the tree left-associatively inside the loop.
How does a parser enforce operator precedence and associativity? || By grammar layering (lower precedence at outer levels, higher at inner levels, left recursion or loops for left associativity) or by binding powers in a Pratt parser: continue the loop while the next operator binds tighter than the current limit, and use a slightly different limit on the right side for right associativity.
Why do many production compilers use hand-written parsers rather than yacc-style generators? || Control over error messages and recovery, handling of context-dependent constructs (C++ templates, type names), speed, and easier incremental or IDE use. The costs are no automatic ambiguity checks and more code to maintain.
Give an example where parsers disagreeing creates a security problem, and how you would reduce the risk. || HTTP request smuggling: a front proxy and a backend interpret Content-Length and Transfer-Encoding differently, so they disagree about where a request ends. Reduce the risk by rejecting ambiguous inputs, normalising at the edge, using the same parser library on both sides, and fuzzing with differential tests.
quiz: What are the two stages of parsing, and which class of formal language does each use? || The lexer turns characters into tokens using regular languages (finite automata). The parser turns tokens into a tree using context-free grammars (pushdown automata, a stack).
Why does the layered grammar expr → term ("+" term)*, term → factor ("*" factor)* give * higher precedence than +? || A product is parsed inside parseTerm, one level deeper than the sum. By the time parseExpr sees "+", the multiplication on its right side is already complete, so 2 + 3 * 4 becomes 2 + (3 * 4).
How many parse trees can 2 + 3 * 4 have under the ambiguous grammar expr → expr + expr | expr * expr | NUMBER, and what values do they give? || Two trees: (2 + 3) * 4 = 20 and 2 + (3 * 4) = 14. The grammar does not choose, so the generator reports a conflict.
A parser handles 0.4 GB/s per core and you ingest 10 TB of JSON a day. How many core-hours is that, and what does a 5 times faster parser save? || 10 TB = 10,000 GB / 0.4 GB/s = 25,000 core-seconds, about 6.9 core-hours; at 5 times the speed it takes about 1.4 core-hours, saving about 5.5 core-hours a day. The saving matters when many pipelines parse at this scale.
When would you pick a parser generator over a hand-written parser? || When the grammar is large, changes often or must be reused by several tools (compiler, formatter, editor), and error message quality matters less. A hand-written parser wins when you need the best error messages, context-sensitive handling and top speed.

@@ typesys
value: A type system is a set of rules that gives every expression in a program a type (integer, string, list of users, function from a request to a response) and rejects programs where the types do not fit together. Adding a string to a socket, calling a function with two arguments instead of three, or reading a field that does not exist are all errors that a type checker finds before the program runs, at the cost of a few seconds of compile time. The same rules also work as documentation that cannot go out of date: the type of a function says what it accepts and returns.
The value is measurable. Gao, Bird and Barr (ICSE 2017) took real bugs from open-source JavaScript projects, added type annotations, and found that Flow and TypeScript each detected about 15% of them, with bugs that had already passed tests and code review. At the strong end, Rust's ownership types remove use-after-free and data races in safe code; Google reported that memory-safety bugs fell from 76% of Android vulnerabilities in 2019 to 24% in 2024 as new code moved to memory-safe languages. For large codebases, types also make refactoring safe: change a function signature and the compiler lists every call that must change.
For the layer above, languages and runtimes use types to catch errors early, to choose the memory layout of data and to optimise (a value known to be an int needs no boxing), and data systems use the same idea for schemas: whether a new version of an Avro or Protobuf schema can read old data is a question of type compatibility. Two lower layers supply the theory. The lambda calculus (L4) is the tiny language of functions in which type systems were first defined: the typed version adds a type to every variable and a rule for every construct, and proves that well-typed programs do not get stuck. Type theory and the Curry-Howard correspondence (L4) say that types are propositions and programs are proofs of them, which explains why a function of type \( \forall a.\, a \to a \) can only return its argument, and why languages like Lean and Coq can use types to prove mathematics and program correctness.
terms: Type — a description of a set of values and of the operations that make sense on them, such as Int, String, List<User> or Int → Bool.
Static and dynamic typing — static types are checked before the program runs (compile time); dynamic types are checked while it runs, when each operation inspects its operands.
Type inference — the compiler works out types that the programmer did not write, by collecting constraints from how values are used and solving them.
Parametric polymorphism (generics) — one definition works for any type, such as a List<T> with the same code for every T.
Subtyping and variance — S is a subtype of T if a value of S can be used wherever T is expected; variance says how this carries over to List<S> versus List<T> or to function arguments and results.
Algebraic data type (ADT) — a type built from products (records, "this and that") and sums (variants, "this or that"), used with pattern matching.
Soundness — a type system is sound if a well-typed program never reaches a state the types said was impossible (the types do not lie).
Type erasure — the types are removed after checking and play no part at run time (Java generics, TypeScript, most ML).
Ownership (affine) types — types that track who may use or change a value, so that a value cannot be used after it is moved or freed (Rust).
history: Bertrand Russell introduced a theory of types in 1908 to escape his paradox about the set of all sets that do not contain themselves. Alonzo Church used types in 1940 to build the simply typed lambda calculus, which fixed the logical inconsistency of his untyped system and became the basis of typed programming. Haskell Curry (1934) and William Howard (written in 1969, published in 1980) noticed that the typing rules for these calculi are the same as the rules of natural deduction in logic. This is the Curry-Howard correspondence.
Programming languages took types in two directions. Fortran (1957) and Algol had simple types to choose machine operations. In 1978 Robin Milner, working on the ML language for a theorem prover, published "A Theory of Type Polymorphism in Programming", with an inference algorithm (Hindley-Milner, later made precise by Damas and Milner in 1982) that infers the most general type of a program without annotations, and the slogan "well-typed programs cannot go wrong". Jean-Yves Girard (1972) and John Reynolds (1974) independently discovered System F, the theory behind generics. Philip Wadler and Stephen Blott introduced type classes (1989), the basis of Haskell's overloading and Rust's traits. Barbara Liskov's substitution principle (1987) gave subtyping a precise meaning.
Industry adopted types in waves. Java (1995) made static types mainstream and added generics in 2004 (with erasure, for compatibility). Tony Hoare called his 1965 invention of the null reference a "billion dollar mistake" in 2009, which pushed languages towards option types (Kotlin, Swift, Rust). Jeremy Siek and Walid Taha described gradual typing (2006), which mixes typed and untyped code; TypeScript (2012) and Python type hints (PEP 484, 2014) apply this idea to existing dynamic languages. Rust 1.0 (2015) brought ownership types from research on linear and affine logic (Girard, 1987) into production. Benjamin Pierce's book "Types and Programming Languages" (2002) is the standard text.
how: Start with the judgement \( \Gamma \vdash e : \tau \), read "in context \( \Gamma \), expression \( e \) has type \( \tau \)". The context \( \Gamma \) lists the types of variables in scope. A type system is a set of rules for deriving such judgements, one for each kind of expression. Three rules cover the core. A variable has the type the context gives it. A function \( \lambda x{:}A.\, e \) has type \( A \to B \) if, assuming x has type A, the body e has type B. An application \( f\, a \) has type \( B \) if \( f \) has type \( A \to B \) and \( a \) has type \( A \). A type checker is a program that tries to build the derivation by walking the syntax tree from the parser; if it succeeds, the program is well-typed, and if no rule fits, it reports an error at that node.
When programmers do not write types, the compiler infers them with unification. It gives each unknown a type variable, walks the program and records constraints (this function is applied to this argument, so its type must be an arrow from the argument's type), and then solves the constraints by unification: finding the most general substitution that makes both sides equal. If two constraints cannot both hold (one says Int, the other says String), that is the type error. A key step, called let-generalisation, turns remaining variables into universally quantified ones, so a function like "twice" can be reused at many types. The result is that Hindley-Milner languages (OCaml, Haskell, Scala locals, Rust locals) need few annotations.
What do the rules guarantee? The standard theorem is type safety, proved by two lemmas. Progress: a well-typed program is either finished or can take a step; it never gets stuck on a nonsense operation. Preservation: if a well-typed program takes a step, the result has the same type. Together they show that the types predicted correctly what happens at run time. What counts as "going wrong" depends on the system: in Java it is calling a method on the wrong class, in Rust it also includes use after free and data races in safe code, in a dependently typed language it can include an out-of-range index. Escape hatches (casts, any, unsafe blocks) lead outside the guarantee.
Polymorphism comes in three forms. Parametric: List<T> works for all T, and the function body cannot look inside a T, so a function of type \( \forall a.\, \mathrm{List}\langle a\rangle \to \mathrm{List}\langle a\rangle \) can only rearrange, drop or repeat elements. This is "theorems for free" (Wadler 1989). Subtyping: if Dog is a subtype of Animal, a Dog may be used where an Animal is expected. For functions, the rule has a twist: a function from Animal to String can be used where a function from Dog to String is expected, so arguments are contravariant (the order reverses) and results are covariant. A mutable List<Dog> is not a List<Animal>, because you could then add a Cat through the second name. Ad hoc: overloading or type classes choose an implementation by type, such as one + for integers and another for floats.
Algebraic data types make illegal states impossible to write. A payment is either Card(number, expiry) or Transfer(account) or Cash; a pattern match must handle each case, and the compiler warns if one is missing. An Option<T> replaces null: a function that may return nothing has a return type that says so, and the caller must handle both cases before using the value.
Ownership types extend the idea to resources. Each value in Rust has one owner; moving it makes the old name unusable; references are either one mutable or many shared, never both at the same time. The compiler checks these rules with lifetimes. The result is freedom from use-after-free and from data races without a garbage collector, enforced as a type error.
Finally, types connect to lower and higher layers. After checking, most languages erase types. Statically typed code can be compiled to straight machine instructions (an Int add is one instruction, a field is at a known offset), whereas dynamic code needs run-time tags and checks that a JIT must remove with profiling. Dependent types go further: a type may contain values, as in Vec<Int, 3>, and the checker must evaluate expressions inside types. By Curry-Howard, constructing a value of such a type is a proof.

example: Example one, inference by hand. Take \( \text{twice} = \lambda f.\, \lambda x.\, f\,(f\, x) \). Give f the unknown type a and x the unknown type b. In the inner call f x, f is applied to x, so a must be a function type that takes b: \( a = b \to c \) for some unknown c. In the outer call f (f x), f is applied to the result of the inner call, which has type c, so \( a = c \to d \). Now we have two equations for a: \( b \to c = c \to d \). Unification compares them piece by piece: \( b = c \) and \( c = d \). All three unknowns collapse into one, call it b, and the result of twice is \( d = b \). So twice has the type \( (b \to b) \to b \to b \). It works for any b: twice (+1) 5 gives 7 and twice reverse xs returns xs. The compiler found this general type without any annotation.
Example two, variance and a hole in the rules. Java allows String[] to be used as Object[] (arrays are covariant). Consider Object[] o = new String[1]; o[0] = Integer.valueOf(1);. It compiles. At run time the array remembers that it is a String array and the write throws ArrayStoreException. The static rule was unsound, and Java has to add a run-time check on every array store to compensate. Generics fixed this for collections: List<String> is not a List<Object>, so the same mistake is a compile-time error. TypeScript arrays are also covariant and unsound by design, as a trade for convenience.
Example three, schema evolution as a type question. Version 1 of a record has fields id: long and name: string. Version 2 adds email: string with a default of "". A consumer reading with version 2 can still read old data, because the missing field takes its default (backward compatible). A consumer reading with version 1 can read new data by ignoring the extra field (forward compatible). If version 2 instead removed name without a default, old data would fail to match, which is a type error between schemas. Avro, Protobuf and Spark schema checks implement these rules, which are subtyping rules for records: a record with more fields can stand in for one with fewer (width subtyping).
intuition: Shaped holes for shaped pegs, checked before the machine starts.
The rules are natural because most errors in programs are mismatches: a value used in a way its kind does not allow. If every expression carries a small description of what it is, and each operation states what it needs, then checking reduces to comparing descriptions, which is cheap, local and compositional: the type of a whole is computed from the types of its parts. The deeper insight from Curry-Howard is that this is not an accident. Writing a function with a given type is like proving a statement, and the checker is a small proof checker; richer types state stronger facts and ask for more proof.
mistakes: People often think static typing means writing many type annotations. In fact modern inference (Hindley-Milner in ML, Haskell and Rust, local inference in Kotlin, Scala, TypeScript and C++ auto) removes most of them. Annotations remain at function boundaries, where they act as documentation.
People often think a program that type-checks is correct. In fact types rule out a class of errors, not all errors. A function with the type List<Int> → List<Int> may sort, reverse or return an empty list. Tests, properties and richer types (refinement or dependent types) cover the rest.
People often think types protect the data that enters from outside. In fact TypeScript and Java generics erase types, and a JSON body typed as User is only a claim. If the service sends a string where a number was declared, the type system does not notice at run time. Data at boundaries must be validated against a schema (zod, JSON Schema, Protobuf decoding).
tradeoffs: Choose static types with inference for long-lived code with many contributors, where refactoring and tooling (autocomplete, go-to-definition) pay back the extra rules. You gain early errors and fearless change; you give up some speed of experiment and pay in compile time and learning curve.
Choose dynamic typing for short scripts, notebooks, exploratory data work and glue code, where the cost of an error is low and the code is read by one person. You gain speed of writing. Add gradual types (Python type hints with mypy or pyright, TypeScript over JavaScript) when a script grows past a few thousand lines or a second contributor joins.
Choose structural typing (TypeScript, Go interfaces: anything with the right fields fits) when you want flexible composition across libraries; choose nominal typing (Java, Rust traits, Scala classes: types must be declared related) when you want explicit contracts and clear error messages. Structural types allow accidental compatibility, and nominal types demand more boilerplate.
friction: Expressive type systems are hard to learn: Scala implicits, Rust lifetimes, Haskell type-level extensions, TypeScript conditional types. Error messages can be long, naming the unification failure and not the programmer's mistake. Type-level programming can become its own unreadable language.
Soundness often loses to convenience. TypeScript allows any, unsound array covariance and unchecked casts; Java has unchecked casts and heap pollution through erasure; Kotlin and Scala have platform types for Java's nulls. Each hole is a place where the types stop being a guarantee, and the failure appears at run time far from the cause.
Types cannot express everything cheaply: whether a number is a valid port, a list is sorted, a lock is held. Encoding such facts is possible but costly. Checking can be slow too: Scala, Rust and C++ templates can take minutes on big projects, and features such as C++ templates and TypeScript conditional types are expensive in corner cases. Finally, types shared between services must evolve over time, which means managing schema compatibility rules.
practice: Turn on the strict settings of your language (TypeScript strict, mypy --strict for new modules, Rust's default, Kotlin non-null types) from the start, because adding strictness later is harder. Model your domain with sum types and small wrapper types: UserId and OrderId as separate types make it impossible to pass one for the other. Make illegal states unrepresentable, for example with a state enum whose variants carry only the data valid in that state.
Replace null with options, and exceptions with result types where errors are expected. Validate all external input once, at the boundary, into precise types, and pass those types inside. In data pipelines, use schemas as contracts: Avro, Protobuf or Delta schemas with compatibility checks in CI, add fields with defaults, never reuse a field number, and treat renames and type changes as breaking.
When a type error is confusing, read it from the bottom: the last line usually states the expected and actual types. Avoid any and unchecked casts, or fence them in a single module with tests. For performance code, remember that types decide layout: in the JVM, a List<Integer> boxes every number, while an int[] does not, and in Spark, typed Datasets carry encoder costs that DataFrames avoid.
interview: What is the difference between covariance and contravariance, and why is a mutable List<Dog> not a List<Animal>? || Covariance means a container of a subtype can be used as a container of the supertype; contravariance reverses the direction, as for function arguments. A mutable list that is treated as List<Animal> lets you add a Cat, which breaks the original List<Dog>. Read-only collections can be covariant (Scala's List[+A]); mutable ones must be invariant.
How does Hindley-Milner inference work, and what are its limits? || It assigns type variables, generates equality constraints from each expression, solves them by unification, and generalises at let-bindings to get polymorphic types. It finds the most general type without annotations. Its limits: it does not handle subtyping well, needs annotations for higher-rank polymorphism, and gives poor error locations when constraints conflict.
What does it mean for a type system to be sound, and give a real example where a popular language is not? || Well-typed programs never reach states the types forbid (progress and preservation). Java's covariant arrays are unsound, since String[] used as Object[] accepts an Integer and fails at run time with ArrayStoreException. TypeScript allows unsoundness deliberately with any and covariance.
How does Rust's type system prevent data races? || Ownership gives each value one owner, and borrowing allows either many shared references or one mutable reference at a time. The Send and Sync marker traits state which types can cross or be shared between threads. A program that shares mutable data between threads without a lock fails to compile.
How are schema compatibility rules like type rules? || A new schema is a subtype of the old (for readers) when it can stand in for it: adding optional fields with defaults is safe (width subtyping), removing required fields or changing a field type is not. Writer and reader schemas are compared like a type check, and Avro resolves them at read time.
quiz: What do the three core typing rules for lambda calculus say? || A variable has the type the context gives it. A function \( \lambda x{:}A.\, e \) has type \( A \to B \) if \( e \) has type \( B \) when \( x \) has type \( A \). An application \( f\, a \) has type \( B \) if \( f \) has type \( A \to B \) and \( a \) has type \( A \).
Why can a function of type \( \forall a.\, \mathrm{List}\langle a\rangle \to \mathrm{List}\langle a\rangle \) not invent new elements? || It must work for every type a, so it cannot look at or build values of an unknown type. It can only reorder, drop or repeat the elements it receives (parametricity, "theorems for free").

Validate at the boundary with a schema library or generated decoder, so invalid data is rejected before it enters typed code.
When is a dynamic language or a gradual approach a better choice than strict static types? || For short, exploratory or single-author work where speed of change matters more than long-term safety. value: An intermediate representation (IR) is the form in which a compiler keeps a program while it analyses and improves it, between the source language and the machine code. It exists because a compiler has two hard jobs at its two ends. At the front end there are many languages (C, Rust, Swift, Java, SQL expressions, tensor programs); at the back end there are many targets (x86, ARM, GPUs, WebAssembly). With a shared IR in the middle, you write N front ends and M back ends, not N × M compilers, and every optimisation is written once and works for all of them.
Static single assignment (SSA) is the most important style of IR. In SSA form every variable is assigned exactly once. When the source assigns x several times, the compiler gives each assignment a new name (x1, x2, x3). Where two paths of control meet and a variable could have come from either, a special φ (phi) function picks the right version: \( x_4 = \varphi(x_2, x_3) \) means "x2 if we came from the left branch, x3 if we came from the right". This looks like bookkeeping, but it makes one fact explicit that was hidden before: for every use of a value, there is exactly one place that defines it. Many optimisations then become simple graph walks along these definition-to-use links.
Almost every serious compiler uses it: LLVM (and so Clang, Rust, Swift, Julia), GCC (GIMPLE), HotSpot's C1 and C2, V8's optimising compilers, the Go compiler, GPU compilers, and ML compilers (XLA, MLIR, Triton, TorchInductor). The layers below supply the machinery. Graph theory (L4) describes the program as a control-flow graph and provides dominators and dominance frontiers, which tell the compiler exactly where φ functions are needed. Dataflow analysis (L3) supplies the optimisations themselves, such as constant propagation and dead-code elimination, which run faster and more precisely when SSA gives them the definition-use links directly. For the layer above, this means JIT compilers, query code generators and ML compilers can reuse the same optimiser instead of inventing their own.
terms: Basic block — a straight run of instructions with one entry at the top and one exit at the bottom, with no jumps in between.
Control-flow graph (CFG) — a directed graph whose nodes are basic blocks and whose edges are the possible jumps between them.
SSA (static single assignment) — a form of IR in which each variable name is defined by exactly one instruction in the program text.
φ (phi) function — an instruction at the start of a block that selects a value depending on which predecessor block control came from.
Dominator — block A dominates block B if every path from the entry to B passes through A.
Dominance frontier — the blocks just beyond the region that A dominates, where A's influence meets paths that do not go through A; exactly the places where A's definitions may need φ functions.
Def-use chain — the link from the single definition of a value to all the places that use it; in SSA it is built in.
Three-address code — instructions of the form \( a = b \mathbin{\text{op}} c \), with at most one operation each; the usual instruction style of an IR.
Lowering — translating from a higher-level form to a lower-level one (for example from loops to jumps, or from tensor operations to loops).
history: The first optimising compiler was the Fortran compiler of John Backus's team (1957), which already worked on an internal form of the program. Frances Allen and John Cocke (1970-76) developed control-flow analysis and the framework for global optimisation, and Gary Kildall (1973) gave a general formulation of dataflow analysis. A problem remained: classic dataflow analyses carry facts about every variable through every block, which is slow and makes many optimisations hard to write.
SSA was found at IBM Research in the late 1980s. Barry Rosen, Mark Wegman and Kenneth Zadeck, and Bowen Alpern and the same coauthors, published the key ideas at POPL 1988 (value numbering and detecting equal variables). Ron Cytron, Jeanne Ferrante, Rosen, Wegman and Zadeck (POPL 1989, journal 1991) gave the efficient algorithm to build SSA using dominance frontiers, which relies on the Lengauer-Tarjan dominator algorithm (1979). Wegman and Zadeck (1991) showed sparse conditional constant propagation on SSA, which finds constants that older methods missed. Andrew Appel (1998) pointed out that SSA is a kind of functional programming: a φ function is a function call, and a block with φ functions is a function with arguments.
Cliff Click's "sea of nodes" IR (1995) removed the fixed ordering of instructions and became the heart of HotSpot's C2 and, later, V8's TurboFan. Chris Lattner's LLVM (2002-04) put a typed SSA IR at the centre of an open compiler, and GCC added its own SSA-based middle end (Tree-SSA, GCC 4.0, 2005). Cooper, Harvey and Kennedy (2001) published a simple dominator algorithm, and Braun and colleagues (2013) a way to build SSA directly while reading the source, without dominance frontiers. In 2019-2021 Lattner and colleagues at Google created MLIR, which allows many levels of IR ("dialects") in one framework, now used by TensorFlow, IREE, and many AI compilers. In March 2025 the V8 team reported moving its optimiser from the sea of nodes to a conventional CFG-based IR (Turboshaft), because the sea of nodes was harder to debug and slower to compile.
how: The compiler first lowers the source into basic blocks of three-address instructions joined into a CFG. At this stage variables may be assigned many times. The next job is SSA construction, which has four steps. One: compute the dominator tree, the tree in which each block's parent is the closest block that dominates it. Two: compute each block's dominance frontier. Three: for every variable, take the set of blocks that assign it, and insert a φ function for that variable at every block in the dominance frontier of those blocks; because the new φ is itself a definition, repeat until nothing changes (the iterated dominance frontier). Four: rename. Walk the dominator tree from the entry, keep for every variable a stack of its current version, give each new definition a fresh number, replace each use with the current top of the stack, and fill the arguments of the φ functions in successor blocks. The result is minimal SSA. Real compilers also prune φ functions for variables that are dead at that point. In practice the number of φ functions grows about linearly with the program, though the worst case is quadratic.
In LLVM, front ends do not even try to build SSA for source variables. They emit a stack slot (alloca) for each variable, with loads and stores, and a pass called mem2reg then promotes the slots whose address is never taken into SSA registers, inserting φ nodes using the algorithm above. This keeps front ends simple. Memory itself is not in SSA form: loads, stores and calls with side effects keep their order, and extra analyses (alias analysis, MemorySSA) reason about them.
Why does SSA help optimisation? Take constant propagation. In SSA, a value is a constant if its single definition is a constant or an operation on constants, and a φ is constant if all incoming values are the same constant. The compiler keeps one fact per value, not one per variable per block, and propagates facts along def-use links; this is a sparse dataflow analysis. Sparse conditional constant propagation does this together with reachability, so a branch whose condition becomes a known constant makes the other branch unreachable and its φ inputs are ignored. Dead-code elimination is also direct: a value with no uses and no side effects can be deleted, and deleting it may leave its operands unused in turn. Common subexpression elimination (global value numbering) works because two instructions with the same operation and the same operand values compute the same result, and in SSA the operands cannot have changed in between. Copy propagation is a simple replacement. Loop optimisations find induction variables as φ cycles of the form \( i = \varphi(\text{init}, i + \text{step}) \).
SSA also makes register allocation easier, which connects to the layer above it in the pipeline. In SSA form, the interference graph of values is chordal (it has no long cycles without a shortcut), and chordal graphs can be coloured with the minimum number of colours in polynomial time. This was shown in the mid-2000s by several groups (Hack, Bouchez, Brisk). The register count of a program then equals the largest number of live values at any point, which is easy to compute.
At the end SSA must be removed, because hardware has no φ instruction. Out-of-SSA translation replaces each φ with copies at the end of each predecessor block, then removes unneeded copies by merging variables that do not interfere. Care is needed: a naive translation of two φs that swap values, or of a φ whose result is used after a loop, gives wrong code (the "swap" and "lost copy" problems, described by Briggs and colleagues in 1998).
Newer IRs adjust the details. MLIR, Swift's SIL and Cranelift use block arguments instead of φ nodes: each block has parameters and each jump passes values, which is the same idea in the shape of function calls. MLIR makes the IR open: dialects define operations at different levels (tensor, linear algebra, loops, GPU, LLVM), and the compiler lowers step by step, keeping high-level facts (this is a matrix multiply) as long as they are useful.

example: Example one: constant propagation through a branch. Source: x = 1; if (c) x = x + 2 else x = x * 3; y = x + x. In SSA (see the diagram): x1 = 1; in B1, x2 = x1 + 2; in B2, x3 = x1 * 3; in B3, x4 = φ(x2, x3) and y1 = x4 + x4. Now run constant propagation. x1 is the constant 1. Then x2 = 1 + 2 = 3, and x3 = 1 × 3 = 3. The φ has two inputs, both 3, so x4 = 3, and y1 = 3 + 3 = 6. The compiler has proved that y is 6 without knowing the condition c. Every step used one fact per value, and each fact was found by looking at the single definition. A bit-vector dataflow analysis that works per variable and per block can find the same fact, but it must store and combine sets at every block.
Example two: building SSA for a loop by hand. Source: i = 0; s = 0; while (i < n) { s = s + i; i = i + 1 }; return s. Blocks: B0 (entry, i = 0, s = 0), B1 (loop test), B2 (body), B3 (return). Edges: B0 to B1, B1 to B2, B2 to B1, B1 to B3. Variable i is defined in B0 and B2. The dominance frontier of B2 is {B1} (B2 does not dominate B1, but it reaches it through the back edge); the frontier of B0 is empty. So both i and s need a φ at B1. SSA: B0: i0 = 0; s0 = 0. B1: i1 = φ(B0: i0, B2: i2); s1 = φ(B0: s0, B2: s2); t = i1 < n; branch on t. B2: s2 = s1 + i1; i2 = i1 + 1. B3: return s1. The loop counter is now visible as a cycle: i1 → i2 → i1, with step 1 and start 0, which is what a loop optimiser looks for.
Now suppose the function returned 0 and did not use s. The values s1 and s2 use each other only: s1 is used by s2, and s2 by s1's φ. A simple "delete values with no uses" pass sees one use each and keeps them. Aggressive dead-code elimination works the other way: it marks as live everything that affects an output or side effect, and removes whatever is not marked, so the whole s cycle disappears. That is a place where the SSA graph gives a cleaner algorithm.
intuition: Rewrite a recipe so that each bowl is used for exactly one thing and labelled, making it obvious which steps depend on which.
The idea is natural because most analysis questions are about where a value came from and where it goes. When variables are reused, the answer depends on position and requires searching the control flow. If every value has one name and one definition, the answer is a pointer. The only places where the answer is not a single definition are the merge points of control flow, and the φ function names those places explicitly instead of hiding them. The program becomes a graph of values, much like a spreadsheet, and the compiler can reason about it by following arrows.
mistakes: People often think SSA means a variable can only be assigned once while the program runs. In fact it is a property of the program text. A definition inside a loop still executes on every iteration, and each execution produces a new value; the name is static, not the run-time value.
People often think a φ function is an instruction that the CPU executes. In fact it is a notation for the compiler. Before code generation, φ functions are turned into register moves on the incoming edges, or removed when both values can share a register.
People often think an IR is the same as bytecode or assembly. In fact bytecode (JVM, Python) is a compact format for storage and for an interpreter, often stack-based; compilers convert it to a graph-based SSA form to optimise. A compiler also uses several IRs in sequence: Rust goes from syntax tree to HIR, to MIR (a CFG used for borrow checking), to LLVM IR, to machine code.
People often think SSA solves all analysis problems. In fact memory, aliasing and calls are not in SSA form unless extra machinery (memory SSA, alias analysis) is built, and many of the hardest optimisations (vectorisation, loop transformations, inlining decisions) need other representations and heuristics.
tradeoffs: Choose an SSA-based IR when you plan to run many optimisation passes, because the cost of building SSA is paid once and every pass is simpler and faster. Choose a simple non-SSA or single-pass design (a template or baseline compiler, such as V8's Sparkplug or a simple JIT tier) when compile speed matters more than code quality, for example the first tier of a JIT or a language with very fast edit cycles. You give up optimisation quality, and gain compile times many times shorter.
Choose to build on LLVM when you want many targets and strong optimisation at modest effort (Rust, Swift, Julia, Clang do). You accept slow compile times, a large dependency, and changes between versions. Choose your own back end (Go moved to its own SSA back end in 1.7, in 2016) or a lighter one (Cranelift, used by Wasmtime) when compile speed or control matters more than the last 10 to 20% of speed.
Choose a CFG with φ functions or block arguments for most work; choose a graph-based IR (sea of nodes) only if the team can handle its complexity. The sea of nodes frees instructions from block order, which helps some optimisations, but it makes scheduling, debugging and cache behaviour harder, which is why V8 moved away from it.
friction: Building and removing SSA costs time and memory, and in very large functions (generated code, huge switch statements) this cost dominates compilation. Out-of-SSA translation introduces copies that must be coalesced again, and mistakes here have caused real miscompilation bugs.
Lowering loses information. Once a matrix multiplication is a nest of loops over pointers, recovering the intent is difficult; this is the main reason for multilevel IRs. Memory and undefined behaviour are another source of trouble: LLVM IR has values called undef and poison to model operations whose results are not defined, and optimisations may use the freedom to change behaviour; subtle bugs in these rules have produced wrong code in production compilers.
Stability and fragmentation are practical problems. LLVM IR changes between versions, so tools that depend on it need updates. AI hardware has produced many IRs (XLA HLO, StableHLO, TorchFX, Triton IR, vendor-specific ones) that do not interoperate cleanly, and keeping debug information and source locations through many transformations is hard. It remains an open research area to design IRs for new hardware and to prove that optimisations preserve meaning.
practice: Learn to look at IR. Compile a small C function with clang -O0 -S -emit-llvm and again with -O2 and compare: you will see alloca and loads at O0, and φ nodes and constants folded at O2. Compiler Explorer (godbolt.org) shows IR and assembly side by side for many languages. For the JVM, use javap -c to see bytecode, and -XX:+PrintCompilation and -XX:+PrintInlining to see what HotSpot compiled.
For data and ML work, treat the plan as an IR: Spark's explain(true) shows the logical and physical plans that Catalyst rewrites with rules, much as a compiler rewrites SSA, and explain codegen shows the Java code generated for a stage. In PyTorch, torch.compile captures a graph of operations (an FX graph) that TorchInductor lowers to Triton kernels; setting TORCH_LOGS to graph_code lets you read it. Write code that helps the optimiser: keep functions small and pure, avoid hidden aliasing (restrict in C, immutability in Java and Scala), prefer loops with clear induction variables, and avoid values whose address escapes without need.
interview: What problem does SSA solve, and how does it make constant propagation cheaper? || It gives every value one definition, so a use points directly to its definition. Constant propagation can then keep one fact per value and push changes along def-use links (sparse analysis), instead of keeping sets of facts for every variable at every block.
Where are φ functions placed, and why not everywhere? || At the iterated dominance frontier of the blocks that define the variable, because those are the only merge points where different definitions can meet. Putting them everywhere would bloat the code and slow every pass. Pruned SSA also omits them for variables that are dead at the merge.
Explain dominators and why compilers need them. || A dominates B if every path from entry to B goes through A. Dominators give the tree structure for SSA renaming, define natural loops (a back edge goes to a dominator), and allow safe code motion: a value defined in a dominator is available in the dominated blocks.
How does SSA help register allocation, and what does out-of-SSA translation do? || The interference graph of an SSA program is chordal, so optimal colouring is polynomial; the minimum registers equal the maximum number of simultaneously live values. Out-of-SSA replaces φ with copies on incoming edges, carefully handling swap and lost-copy cases, and coalesces copies to avoid moves.
Why might a compiler team abandon a graph-based IR like sea of nodes? || Free-floating nodes make scheduling, debugging and cache behaviour harder; effect and control chains for side effects add complexity; compile time grew. V8 reported moving to a CFG-based IR (Turboshaft) in 2025, roughly halving compile time and simplifying code.
quiz: What does a φ function do? || It selects a value at a control-flow merge depending on which predecessor block was taken, so each use still has exactly one definition. It is notation for the compiler and becomes register moves.
Why is the dominance frontier used to place φ functions? || A definition in block A is the only reaching definition inside the region A dominates. At the first blocks outside it, the dominance frontier, paths that go through A and paths that do not may merge, so a φ is needed there (and then iteratively for the new φ).
In the program x = 1; if (c) x = x + 2 else x = x * 3; y = x + x, what does constant propagation conclude? || x2 = 3 and x3 = 1 × 3 = 3, so x4 = φ(3, 3) = 3 and y = 6, whatever c is.
A function has 1,000 blocks and 500 variables. How many facts does a per-variable, per-block analysis keep, and what does a sparse SSA analysis keep if there are 5,000 values? || Up to 1,000 × 500 = 500,000 facts, against 5,000 facts for the sparse analysis, about 100 times fewer.
When would you skip SSA and use a simple single-pass or template compiler? || When compile speed matters more than code quality, such as the first tier of a JIT, or a very short-lived program, where optimisation passes would cost more time than they save.

value: A just-in-time (JIT) compiler turns a program into machine code while the program is running, and uses what it has seen so far to do a better job than a compiler that works before the program starts. A compiler that works ahead of time must produce code for every case: any type, any branch direction, any class that might be loaded later. A JIT can watch the program for a few milliseconds and learn that this call always receives a Circle, this branch is taken 99.99% of the time and this array index never goes out of range. It then compiles a fast version for exactly that behaviour, and keeps a way back if the assumption turns out to be wrong.
This is why Java, Scala, Kotlin, C#, JavaScript and Lua can run within a small factor of C for hot code, and sometimes faster, although their programs are shipped as portable bytecode or even as source text. It is also why the JVM can run Spark executors for hours at high speed, why Chrome and Node.js run JavaScript quickly, and why query engines compile an expression or a whole pipeline stage into code at run time: Spark's whole-stage code generation produces Java source, compiles it with Janino to bytecode, and lets HotSpot's JIT turn that into machine code. The eBPF subsystem uses a simple JIT to run verified programs in the Linux kernel.
Two lower layers do most of the work inside a JIT. Intermediate representation and SSA (L3) give the JIT a form in which the hot method can be optimised quickly: the bytecode is parsed into an SSA graph, and inlining, constant folding, dead-code elimination, loop optimisations and speculation guards are all passes over that graph. Register allocation (L3) maps the unlimited values of the SSA graph onto the few machine registers; because a JIT compiles while the user waits, fast JIT tiers use linear-scan allocation, which is a single pass over live intervals, not graph colouring. For the layer above, language runtimes (JVM, V8, .NET, PyPy) and code generators in data systems depend on this machinery.
terms: Interpreter — a program that executes bytecode one instruction at a time without producing machine code; slow, but starts at once.
Tiered compilation — several levels of execution: an interpreter first, then a fast compiler with little optimisation, then a slow compiler with heavy optimisation for the hottest code.
Profile — counts and observations collected while running: how often a method is called, which branch is taken, which classes appear at a call site.
Hot code — methods and loops that run often enough to be worth compiling.
Inlining — copying the body of a called method into the caller, which removes call overhead and lets the compiler optimise across the boundary.
Speculative optimisation and guard — compiling with an assumption (the receiver is a Circle) protected by a cheap run-time check, the guard.
Deoptimisation — when a guard fails, abandoning the compiled code and continuing in the interpreter, with the state rebuilt exactly as the interpreter expects.
On-stack replacement (OSR) — switching a running loop from interpreted to compiled code in the middle of execution.
Code cache — the memory area where compiled machine code is stored.
Warm-up — the period after start during which the program runs slowly because code is still interpreted or lightly compiled.
history: The idea is old. John McCarthy's Lisp (1960) compiled functions at run time, and Ken Thompson's 1968 regular expression matcher generated machine code for the pattern. Deutsch and Schiffman (1984) made Smalltalk-80 fast with "dynamic translation": the code was compiled on first use and cached. The Self language group at Stanford and Sun (Chambers, Ungar, Hölzle) invented most of the modern toolbox: polymorphic inline caches (1991), type feedback and adaptive optimisation based on run-time profiles (Hölzle and Ungar, 1994), and deoptimisation to return from optimised code to a simple state.
The Self team and a startup, Longview, built the HotSpot virtual machine, which Sun acquired in 1997; it became the default in Java 1.3 (2000). HotSpot has two compilers: C1 (the "client" compiler: fast, light optimisation) and C2 (the "server" compiler: slow, heavy optimisation, based on Cliff Click's sea-of-nodes IR). Tiered compilation, which combines them, became the default in Java 8 (2014). John Aycock's 2003 survey "A Brief History of Just-In-Time" collects the earlier work.
JavaScript made JITs a mass-market item. V8, released with Chrome in 2008, compiled JavaScript straight to machine code; it later added the optimising compilers Crankshaft (2010) and TurboFan (2015-17), the Ignition interpreter (2016), the Sparkplug baseline compiler (2021) and Maglev (2023). Other designs include tracing JITs (Dynamo, 1999; LuaJIT, Mike Pall, 2005; PyPy), which record a hot loop and compile the trace; Truffle and Graal, which derive a JIT from an interpreter by partial evaluation (Würthinger et al., 2013); and .NET's tiered compilation, on by default since .NET Core 3.0 (2019). CPython 3.13 (2024) added an experimental JIT based on "copy-and-patch" compilation (Xu and Kjolstad, 2021; PEP 744), which stitches pre-compiled machine-code templates together; it is off by default. Java's Project Leyden adds ahead-of-time caches to cut warm-up (JEP 483 in JDK 24; JEP 515 in JDK 25 stores method profiles from a training run).
how: The runtime starts in the interpreter, because compiling everything at start would waste time on code that runs once. Each method has an invocation counter and each loop has a back-edge counter. In tiered HotSpot, a method that is called a few hundred times (the default is about 200 invocations) is queued for C1; one that keeps running, after several thousand invocations or many loop iterations, is queued for C2. Compilation runs on background compiler threads, so the program keeps running (slowly) in the meantime. When compilation finishes, the new machine code is placed in the code cache and the method's entry point is switched, so the next call uses it. A long-running loop is handled by OSR, which jumps from the interpreter frame into compiled code at a loop iteration.
While in the tier that precedes C2 (tier 3), the code collects a profile: the taken and not-taken counts of each branch, the receiver classes seen at each virtual call, and the types seen at each cast and array store. This profile is the JIT's main advantage. C2 compiles with it as follows. First, it parses the bytecode into an SSA graph. Second, it optimises. Inlining comes first because it unlocks the rest: HotSpot inlines small methods (under 35 bytes of bytecode by default) and hot ones up to 325 bytes, to a depth limit. A virtual call is devirtualised in three ways: by class hierarchy analysis (if only one loaded class implements the method, call it directly), by the type profile (if the call site saw one class, test for it and inline; if two, test for both), and by final or private modifiers. After inlining, escape analysis checks whether a new object is ever visible outside the method; if not, the allocation is removed and its fields live in registers (scalar replacement). Locks on non-escaping objects are removed. Loops are unrolled, range checks are hoisted or eliminated, and simple loops are turned into SIMD instructions. Branches never taken in the profile are not compiled at all: they become uncommon traps.
Third, it allocates registers and emits machine code. C1 uses linear scan: it computes for each value the interval during which it is live, sorts the intervals by start, and walks through them once, assigning a free register and spilling the interval that ends furthest away when none is free. This takes roughly linear time, which is what a fast tier needs. C2 can afford a more thorough graph-colouring allocator because it runs only for the hottest methods.
Speculation is only safe because of deoptimisation. The compiled code contains guards: "is the receiver a Circle?", "is this index within bounds?", "is this branch the one we expected?". If a guard fails, the code jumps to an uncommon trap. For each such point the compiler has recorded how to rebuild the interpreter's view of the state (the locals, the operand stack, the position in the bytecode) from the registers and stack slots of the compiled frame. The runtime builds interpreter frames, continues in the interpreter, marks the compiled method as invalid, and lets the method collect a new profile, so that it can be recompiled with better assumptions. The compiler also records dependencies, such as "no class below Shape overrides area()"; when class loading later breaks one, every method that depends on it is deoptimised. JavaScript engines work the same way, with hidden classes (shapes) instead of Java classes: an inline cache at each property access remembers the shape, and optimised code assumes numbers are small integers or objects have a given shape.
The cost side is what makes a JIT an engineering trade-off. Compiler threads use CPU and memory (C2 can use tens of MB for one big method), compiled code occupies the code cache (240 MB by default in tiered mode), and the time before the hot code is fully optimised is the warm-up. Methods that are very large are not compiled at all by HotSpot by default (more than 8,000 bytes of bytecode), which matters for machine-generated code.

example: Take a loop that calls shape.area() on a list of one million shapes, and the loop runs 100 times, so 100 million calls. All shapes at first are Circle. Assume rough costs per iteration: the interpreter 50 ns, C1 code 10 ns, C2 code with the call inlined 2 ns (a few multiply instructions).
Timeline. The interpreter runs the first 200 calls in about 10 microseconds and queues a C1 compilation. C1 takes about a millisecond, during which the loop continues in the interpreter at 50 ns per iteration, so about 20,000 iterations. From then on the loop runs at 10 ns per iteration with profiling on. C2 is queued after a few thousand more calls. The profile says: one receiver class, Circle, at this call site. C2 compiles for about 20 milliseconds on another thread; during this time the loop runs 2 million more iterations at 10 ns. After that, the loop runs at 2 ns. The remaining 98 million iterations take 0.196 seconds. Total: about 0.02 seconds of warm-up, 0.2 seconds of fast execution, about 0.22 seconds. If everything were interpreted, 100 million × 50 ns = 5 seconds. If an ahead-of-time compiler could not prove the receiver type, the virtual call stays a call at maybe 4 ns, 0.4 seconds in total: the JIT wins because it has the profile.
Now the guard. Halfway through, at iteration 60 million, a Square appears. The compiled code has the guard if (shape.class != Circle) uncommon_trap. The guard fails once. The runtime deoptimises: it rebuilds the interpreter frame (a few microseconds to a few hundred, depending on inlining depth), marks the C2 code invalid and continues in the interpreter. The profile now shows two classes. After the thresholds are reached again and a new C2 compile of roughly 20 ms, the call site has two guards (Circle, Square) and both inlined. The cost of the shape change is roughly the compile time, a few tens of milliseconds, small against 0.2 seconds. If the program changed shape types every second, the loop would spend a large part of its time deoptimising.
Short-job case. If the whole job is only 1 million iterations, the loop runs mostly at C1 speed: about 10 to 15 ms, against about 4 ms for a precompiled version with a plain virtual call. For a serverless function that runs for 50 ms, the JIT never reaches its best code, which is why short jobs are its weak spot.
intuition: A translator who notices which phrases you use most and prepares polished, ready-made versions of those, while keeping a plain dictionary in case you say something new.
The idea is natural because programs follow the 90/10 rule: nearly all the time is spent in a tiny part of the code. Spending effort on compiling only that part, and spending it where the program tells you the behaviour is stable, gives most of the benefit for little cost. The profile turns a general problem (any type may come here) into a specific one (this type comes here), and deoptimisation makes the bet safe, because a wrong guess costs a slow moment, not a wrong answer.
mistakes: People often think JIT-compiled code is always faster than ahead-of-time compiled code. In fact a C++ or Rust program compiled with a good optimiser usually matches or beats a JIT at steady state and starts instantly. The JIT wins when run-time information (types, class hierarchy, branch frequencies) makes a real difference, and loses on startup, memory and predictability.
People often think deoptimisation means something is broken. In fact it is a normal part of the design; a program with good behaviour has a few deoptimisations early on. Many deoptimisations repeating (a "deopt storm") is a performance bug worth investigating.
People often think a benchmark that runs for 100 ms tells you how fast Java code is. In fact it mostly measures the interpreter and C1, and the result changes every run. Use a harness such as JMH, which does warm-up iterations, forks the JVM and prevents the compiler from removing the work that you are measuring.
tradeoffs: Choose JIT-based runtimes (JVM, V8, .NET) for long-running services and data processing (Spark executors, Kafka brokers, web servers), where hours of run time amortise a warm-up of seconds. You get portable binaries and peak speed close to native code. You give up fast startup and a predictable memory footprint.
Choose ahead-of-time compilation (GraalVM native image, Rust, Go, C++) for command-line tools, serverless functions and sidecars, where start time of tens of milliseconds and low memory matter more than the last 10 to 30% of peak speed. A native image starts in a few tens of milliseconds and uses a fraction of the memory, but without run-time profiles it has less aggressive optimisation (unless you give it profile-guided data), and reflection and dynamic class loading need configuration.
Choose a middle path when you want both: class-data sharing and the JDK 24/25 ahead-of-time caches, checkpoint and restore (CRaC), or warm-up requests before routing traffic. Each cuts the warm-up at the price of build-time steps and care about stale caches.
friction: Warm-up is the central complaint. Right after start or deployment, a service handles requests slowly, latency percentiles spike, and autoscaling that adds fresh instances under load adds slow instances. Compiler threads also compete with the application for CPU, which hurts in containers limited to one or two cores.
Performance is less predictable than in ahead-of-time code. It depends on the profile, which depends on the traffic: a code path first exercised with unusual input may be compiled badly. Cliffs appear when a method grows past an inlining limit (325 bytes of bytecode in HotSpot), when a call site becomes megamorphic (more than two receiver types, so it falls back to a table lookup), or when a type changes in JavaScript. The code cache can fill ("CodeCache is full. Compiler has been disabled"), and the program then falls back to the interpreter.
Memory and security also matter. Compiled code, profiles and IR use memory, so a JIT process needs more than a native one. Writable and executable pages are an attack surface, so engines flip page permissions and add hardening; some platforms (iOS for third-party apps) forbid JIT. An optimiser bug (a wrong assumption, a missing deoptimisation) gives wrong results only under certain profiles, which makes it very hard to reproduce.
practice: Measure after warm-up and under realistic load. Use JMH for microbenchmarks on the JVM. In a service, watch latency during the first minutes after a deploy; use readiness checks that wait for warm-up, a slow-start ramp of traffic in the load balancer, or synthetic warm-up requests.
Look at what the JIT does. -XX:+PrintCompilation lists what is compiled and when; -XX:+PrintInlining (with diagnostic options) shows inlining decisions; JITWatch visualises the log; JFR records compilation and deoptimisation events. In Node.js, --trace-opt and --trace-deopt show optimisation and deoptimisation. Write code that helps: keep hot methods small, keep call sites monomorphic, avoid changing object shapes in JavaScript (initialise all properties in the constructor in the same order), and avoid exceptions for control flow in hot loops.
For Spark, whole-stage code generation can produce very large methods; if one exceeds 8,000 bytes of bytecode, HotSpot does not JIT-compile it and it runs interpreted. The setting spark.sql.codegen.hugeMethodLimit (default 65535) controls when Spark gives up on codegen for a plan, and its documentation suggests 8000 on HotSpot to match this limit. To reduce start cost for short jobs, use AppCDS or the AOT cache in recent JDKs, or a native image where the framework supports it. Size the code cache and leave CPU for compiler threads on small containers.
interview: Why can a JIT sometimes beat an ahead-of-time compiler? || It has run-time facts: which classes are actually loaded, which receiver types and branches occur, and constants that were fixed at start-up. It uses them to inline virtual calls, remove dead branches and allocations, and specialise loops, with guards and deoptimisation as a safety net. An ahead-of-time compiler must be correct for every case unless profile-guided.
Explain deoptimisation. What must be saved so that execution can continue? || At each point where a guard can fail, the compiler records a map from registers and stack slots to the interpreter's locals, operand stack and bytecode position, including objects removed by escape analysis (they must be re-created). On failure the runtime rebuilds interpreter frames, continues in the interpreter, invalidates the compiled method and lets it re-profile.
What is a megamorphic call site and why does it hurt? || A call site that has seen many receiver classes (more than the inline cache or the profile can hold, two in HotSpot's inlining). The JIT cannot inline it, so it uses a virtual table or interface lookup and also loses optimisations that depend on inlining. The fix is fewer implementation classes at hot sites or restructuring the code.
Your Java service has high latency for the first five minutes after each deployment. What would you do? || Confirm it is warm-up (compilation and deoptimisation logs, JFR, GC), then reduce it: warm-up requests before traffic, gradual traffic ramp, class-data sharing or the JDK AOT cache, CRaC where available, more CPU during start for compiler threads, and make sure the code cache and tiered settings are not constraining it. Do not add instances under load without ramping.
Compare a tracing JIT, a method JIT and a template (copy-and-patch) JIT. || A method JIT compiles whole methods using profiles and inlining (HotSpot, V8). A tracing JIT records the path through a hot loop and compiles that linear trace with guards (LuaJIT, PyPy), which is simple and fast on loop-heavy code but weak on branchy code. A copy-and-patch JIT stitches pre-compiled templates, giving very fast compile and modest speed-up (CPython 3.13, experimental).
quiz: What are the main steps from a hot bytecode method to running machine code in tiered HotSpot? || Counters trigger a C1 compile; C1 code collects a profile; if the method stays hot, C2 parses it to SSA, optimises (inlining, devirtualisation, escape analysis, loops), allocates registers, emits machine code into the code cache and switches the method entry.
Why is linear-scan register allocation used in fast JIT tiers? || It makes one pass over sorted live intervals, assigns free registers and spills when needed, in roughly linear time, whereas graph colouring is slower. A fast tier must finish compiling in milliseconds.
What happens when a speculative guard fails? || The compiled code jumps to an uncommon trap; the runtime rebuilds interpreter frames from the recorded state, continues in the interpreter, invalidates the compiled code and collects a fresh profile for recompilation.

value: Functional programming builds programs from functions that behave like mathematical functions: the result depends only on the arguments, and calling the function changes nothing else in the world. Data is immutable: instead of changing a list, you make a new list. Programs are written by combining small functions with higher-order functions such as map, filter and reduce, which take other functions as arguments.
The reason this matters for an engineer is not elegance but what it allows. A function with no hidden state can be run on any machine, run twice, run in a different order, cached, or thrown away and re-run after a failure, and the answer stays the same. This is the property that distributed data processing needs. MapReduce took its two operations from Lisp. Spark's resilient distributed datasets recover a lost partition by running the same functions again on the same input (lineage). Kafka Streams, Flink and Beam describe pipelines as compositions of transformations. React describes a user interface as a function from state to a view. Declarative pipelines and materialized views treat a table as a pure function of other tables. All of these work because the functions are pure.
Two lower layers explain why this is more than a style. The lambda calculus (L4) is the tiny language in which everything is a function; it shows that functions alone are enough to compute anything, defines how a function is applied (β-reduction), and has the confluence property: for pure programs, different evaluation orders reach the same result, which is why a runtime may evaluate parts in parallel. Category theory (L4) supplies the abstract patterns that functional code reuses: a functor is anything you can map over, a monoid is an associative combine operation with a neutral element (which is exactly what a parallel reduce needs), and a monad is a way to chain steps that carry context such as "may be missing", "may fail" or "will arrive later".
terms: Pure function — a function whose result depends only on its arguments and which has no side effects (no writes, no reads of changing state, no I/O).
Immutable data — a value that cannot be changed after creation; an "update" creates a new value.
Referential transparency — an expression can be replaced by its value without changing the program's behaviour; this is what makes reasoning by substitution valid.
Higher-order function — a function that takes functions as arguments or returns a function (map, filter, fold).
Closure — a function together with the variables from its surrounding scope that it uses.
Persistent data structure — an immutable structure whose new versions share most of their memory with the old ones.
Monoid — a type with an associative operation and an identity element (numbers with + and 0, strings with concatenation and "").
Monad — a pattern for chaining computations that carry a context, through a flatMap (bind) operation; Option, List, Future and Try are examples.
Lazy evaluation — computing a value only when it is needed, as in Haskell or Spark transformations.
history: Alonzo Church's lambda calculus (1936) is the theoretical root: a language with only function definition and function application. John McCarthy's Lisp (1958; paper in 1960) was the first programming language built on it, with functions as values, recursion and garbage collection. Peter Landin's ISWIM (1966) described a family of languages with expressions in place of statements. Robin Milner's ML (1973) added type inference. In 1978 John Backus used his Turing Award lecture, "Can programming be liberated from the von Neumann style?", to argue that assignment-based programming had reached a dead end and that programs should be built by combining functions. David Turner's Miranda (1985) made lazy functional programming practical, and a committee designed Haskell (1.0 in 1990). John Hughes's "Why functional programming matters" (1989) argued that the point was modularity: higher-order functions and laziness are glue for building programs from small parts.
Several developments made the style useful beyond research. Chris Okasaki's work (thesis 1996, book 1998) showed how to build efficient immutable data structures. Phil Bagwell's hash array mapped tries (2001) became the base of Clojure's and Scala's persistent collections. Eugenio Moggi (1989-91) and Philip Wadler (1990-93) showed how monads handle effects such as I/O, state and failure in a pure language. Joe Armstrong's Erlang (1986) used immutable data and message passing for telecom systems. Scala (2004, Martin Odersky) joined functional and object-oriented programming on the JVM, and Clojure (2007, Rich Hickey) brought persistent collections to it.
Distributed data processing became the biggest customer. Dean and Ghemawat's MapReduce (OSDI 2004) was inspired by the map and reduce of Lisp; Zaharia and colleagues' Spark paper (NSDI 2012) used pure transformations and lineage for fault tolerance. Java 8 (2014) added lambdas and streams, and JavaScript, Python, C#, Kotlin, Swift and Rust all took higher-order functions, immutable values and pattern matching from this tradition.
how: The core idea is substitution. Because a pure function call can be replaced by its result, a program can be understood by rewriting, as in algebra. The lambda calculus gives the rules: a function is written \( \lambda x.\, \text{body} \), application substitutes the argument for x (β-reduction), and a function can be passed as a value. Functions of several arguments become chains of one-argument functions (currying), so \( f(a, b) \) is \( (f\ a)\ b \) and a partially applied function is a new function. A closure captures the variables around it, so a function can carry its configuration. With only these tools, loops become recursion or folds, data can be built from functions, and every control structure is a function.
Pipelines are written with a small set of higher-order functions. map applies a function to every element, filter keeps elements that satisfy a predicate, flatMap maps and flattens, and fold (reduce) combines all elements into one value with a binary operation. They replace loops with a statement of what is wanted. They also have laws that a compiler or engine may use: mapping f and then g over a list equals mapping the composition once (\( map g \circ map f = map (g \circ f) \)), so two passes can be fused into one; a filter may be moved before a map when it does not depend on the mapped value. Spark's planner relies on this kind of rewriting: it pushes filters down, merges projections and runs a chain of narrow transformations as one pass over each partition.
Category theory names the shapes behind these laws. A functor is a container with a map that obeys two laws: mapping the identity changes nothing, and mapping a composition equals composing the mappings. A monoid has an associative operation \( (a + b) + c = a + (b + c) \) and an identity element. Associativity is what lets a reduce be split: you can add up each partition separately and then add the partial results in any grouping, in a tree of depth log₂ of the number of partitions. Without associativity, the result would depend on how the data was divided. A monad adds flatMap with laws that make chaining predictable: with Option, a chain of steps stops at the first "nothing"; with Future, steps run when the previous result arrives; with List, each step can produce several results.
Immutability needs data structures that are cheap to "change". A persistent structure represents a new version by copying only the path from the root to the changed element and sharing everything else. In a balanced tree of n elements, an update copies O(log n) nodes. Clojure and Scala vectors use a trie with 32 children per node: 32⁴ is about a million, so an update in a million-element vector copies four nodes (about 128 references) instead of a million. Old versions stay valid, which gives cheap snapshots, safe sharing between threads and easy undo.
Real programs need effects: reading files, writing to a database, printing. Functional languages handle this by separating the description of an effect from its execution. In Haskell, an IO action is a value; the runtime performs it. In Scala, libraries such as cats-effect and ZIO do the same; in OCaml 5, algebraic effect handlers do it. A common architecture is a pure core (all decisions as functions on values) with a thin shell that does the I/O. Unit tests of the core then need no mocks, and the shell is small.
Finally, evaluation strategy matters. Strict languages (Scala, OCaml, Java streams within a terminal operation) evaluate arguments first; lazy ones (Haskell) only when needed. Laziness lets you write an infinite list and take ten elements, but it can hide memory use. Spark is lazy in a different way: transformations only build a plan, and an action such as count or write triggers it, which allows the whole pipeline to be optimised before any data moves. Tail calls turn recursion into loops (Scala's @tailrec checks this at compile time), because the JVM itself does not eliminate tail calls.

example: Example one: word count as a functional pipeline. Three partitions of text hold the lines "a b a", "b c" and "a c c". Step one: flatMap splits lines into words. Step two: map turns each word w into the pair (w, 1). Step three: reduceByKey adds the numbers for each key. Locally, partition 1 gives (a,2) and (b,1), partition 2 gives (b,1) and (c,1), partition 3 gives (a,1) and (c,2). After the shuffle, which brings equal keys together, a = 2 + 1 = 3, b = 1 + 1 = 2 and c = 1 + 2 = 3. Because + is associative and commutative, the answer is the same however the partitions are grouped or ordered. If the machine holding partition 2 dies, only partition 2's functions are run again on its input block. The answer does not change, since the functions have no side effects.
Example two: how impurity breaks this. Suppose the map function also increments a global counter to count the number of words. Task retries and speculative copies of slow tasks run the function again on the same data, so the counter is increased twice for those partitions. This is why Spark's documentation guarantees accumulator updates exactly once only inside actions, and why a function with hidden state is a bug in a distributed pipeline, not a style problem. The same applies to random numbers and the current time: a recomputed partition must produce the same data, so a random function needs a fixed seed.
Example three: associativity and floating point. With real numbers addition is associative, so any reduction tree gives the same sum. With floating point it is not: (0.1 + 0.2) + 0.3 gives 0.6000000000000001, while 0.1 + (0.2 + 0.3) gives 0.6. A distributed sum of doubles therefore changes in its last digits when the partitioning or shuffle order changes. For money use integers or decimals.
Example four: persistent vector update. A vector of 1,048,576 (2²⁰) elements is stored in a trie with 32 children per node and depth 4. Updating element 700,000 copies the root, two internal nodes and one leaf: four nodes of 32 references each, 128 references in all (about 1 KB). A plain array copy would move over a million references (8 MB with 8-byte references). The new vector shares all other elements with the old one, and both versions can be used at the same time.
intuition: Functions like maths formulas: the same inputs always give the same answer, and evaluating a formula never changes something somewhere else.
The idea is natural once you see what makes distributed and concurrent programs hard: shared state that changes. If nothing changes, there is nothing to lock, nothing to synchronise, no order of events to get wrong, and any piece of work can be repeated or moved. The price is that you must describe change differently, as new values and as chains of transformations, and the lambda calculus and category theory show that this loses no power: everything that can be computed can be written as functions, and the patterns for combining them are few and reusable.
mistakes: People often think functional programming means no state. In fact programs still have state; the state is made explicit and passed as values (a new state returned from each step) or kept at the edges. A functional pipeline that reads a database, calls an API and writes a file has many effects. What changes is that effects are contained and visible in the types.
People often think immutable data is always slower. In fact persistent structures give updates in O(log n) with sharing, and JVMs allocate short-lived objects cheaply. Immutable code can be slower in tight numeric loops or when a large array is rebuilt on each change, and then local mutation inside a function (still pure from the outside) is the normal answer.
People often think functional programming is the opposite of object-oriented programming. In fact the two combine well. Scala and Kotlin use classes for modules and data and functions for logic, and immutable value objects are standard advice in object-oriented design too.
tradeoffs: Choose a functional style for data transformations, business rules, parsers, and anything that needs retries, caching, parallel execution or easy testing. You gain reasoning by substitution, safe parallelism and replayability. You give up some of the speed and memory control of in-place mutation, and you ask the team to learn new idioms.
Choose imperative code with local mutation for tight inner loops, large arrays, and code that must be as fast as possible (numeric kernels, parsing hot paths, buffer handling). The best practice is to keep the mutation inside a function and keep the function pure from outside: a sort that copies the input into a local array and sorts it in place is still referentially transparent for its caller.
Choose a pure-functional effect system (cats-effect, ZIO, Haskell IO) when the program is mostly orchestration of effects with complex error handling and cancellation and the team accepts a steep learning curve; choose plain functions with exceptions or Result types and a simple shell when the team is mixed or the service is small. Effect systems give composable, testable control of retries, timeouts and resources; they cost debugging complexity and a unique vocabulary.
friction: Effects cannot be avoided, so a functional program needs a way to deal with them, and every approach has a cost. Monads and effect systems add concepts and long type signatures; stack traces from deeply composed code are hard to read. Mixing styles is common and works, but code reviews must know which parts are pure.
Performance can suffer in specific ways. Immutable updates allocate, which increases garbage collection pressure; boxing of numbers in generic collections costs memory and time (a List of Integer in Scala or Java has a pointer and an object header per number); lazy structures can leak memory when a thunk holds on to large data. Recursion needs care: without tail-call elimination a deep recursion overflows the stack, and the JVM does not eliminate tail calls itself.
Purity is a discipline, not a guarantee, in most languages. Scala, Kotlin and Java allow side effects anywhere, so a function you assumed pure may read a clock or mutate a shared object, and in Spark such functions fail under retries only in production. Floating-point arithmetic breaks associativity, which means the results of distributed reduces are not exactly reproducible. Finally, hiring and onboarding: fewer engineers are fluent in the idioms, and heavy use of abstractions such as type classes can make code hard for newcomers.
practice: In data pipelines, write transformations as pure functions of their inputs. Do not read the clock, random numbers, environment variables or external services inside a map or UDF; pass them in as columns or parameters, and fix seeds. Do not mutate shared state in a transformation; if you need counts, use the engine's accumulators or metrics, inside actions, and accept that retries can repeat them. Make operations idempotent so a rerun of a partition or a task gives the same output, and write outputs atomically (Delta Lake does this with an immutable file log).
Make your reduce operations associative with an identity element: sums, counts, max, min, set union, sketches (HyperLogLog, Bloom filters). Avoid reduce functions that are order-dependent (take-first, string building with separators). If you need an average, carry a (sum, count) pair, which is a monoid, and divide at the end. For money, use decimals or integers.
In application code, use immutable values for data that crosses threads (records, case classes, frozen dataclasses), prefer map, filter and fold or comprehensions to index loops where they read better, and keep I/O at the edges. Use Option and Result types in place of null and exceptions for expected failures. Learn the standard library of persistent collections in your language, and measure before replacing a mutable structure in a hot path. Read Hughes's paper and a good book for your language, such as Functional Programming in Scala.
interview: Why do Spark and MapReduce require functions to be pure and, for reduce, associative? || Tasks are retried and sometimes run twice (speculative execution), and lost partitions are recomputed from lineage. Pure functions give identical outputs on retries. Reduce combines partial results from partitions in arbitrary groupings and order, so the operation must be associative (and for some APIs commutative) or the result would depend on partitioning.
What is a monoid and why is it useful for distributed aggregation? || A set with an associative binary operation and an identity element. Because of associativity, each partition can be aggregated locally and the partial results merged in a tree in any grouping; the identity gives a result for empty partitions. Sum, count, max, set union and many sketches are monoids; an average is not, but (sum, count) is.
How can an immutable data structure support cheap updates? || With structural sharing: a new version copies only the path from the root to the changed node and points to the unchanged subtrees. In a balanced tree this is O(log n) nodes; Clojure and Scala vectors use 32-way tries, so an update touches only a few nodes. Old versions remain valid.
How do functional languages handle I/O and still claim purity? || By treating an effect as a value that describes an action, which is composed purely and run by the runtime at the edge (the IO monad, cats-effect, ZIO). Pure code builds the description; only the interpreter performs it. This keeps the core testable and makes effects visible in the types.
When would you not write functional code? || In performance-critical inner loops with large arrays, where in-place mutation avoids allocation; in code tightly bound to a mutable API (GPU buffers, device drivers); or when the team cannot maintain the abstractions. Even then keep mutation local and the function pure from outside.
quiz: What is referential transparency and what does it allow? || An expression can be replaced by its value without changing behaviour. It allows reasoning by substitution, caching and memoisation, running work in parallel or in a different order, and re-running a task after failure.
Why does map g ∘ map f equal map (g ∘ f), and why does an engine care? || Applying f then g to each element in two passes gives the same result as applying the composed function in one pass. The engine can fuse two passes into one, saving a pass over the data and an intermediate collection.

value: A concurrency model is a set of rules for how a program does many things at once and how those things coordinate. The problem is real and unavoidable: a server must handle thousands of requests while it waits for disks and networks, a data job must use all cores, and a user interface must stay responsive during a download. The difficulty is that when several activities touch the same data, the result depends on the exact order of their steps, and most orders are wrong. A concurrency model decides which mistakes are easy to make and which are hard.
Four families cover most practice. Shared memory with locks: threads see the same data and take turns using it (Java threads, C++, Python threads). Actors: independent entities with private state that only communicate by sending messages (Erlang, Akka, Orleans). Communicating sequential processes (CSP): lightweight processes that meet at channels (Go, Clojure core.async, occam). Async/await: a function suspends at each wait and a scheduler resumes it later, usually on one event loop (JavaScript, Python asyncio, Rust, C#). Software transactional memory and data-parallel models add further options.
For the layer above, every language runtime and framework picks one of these as its main story: Node.js is an event loop, Go is goroutines and channels, Erlang is actors, Java is threads and, since Java 21, virtual threads. Three lower layers support the choice. Logic (L4) provides the language to state and prove properties of concurrent programs: temporal logic expresses safety ("no two threads in the critical section") and liveness ("every request is eventually answered"), and process calculi give algebraic rules for message-passing programs. Formal languages and automata (L4) treat the behaviours of a concurrent program as a set of traces, a language, and model checkers explore the product of the automata to find a trace that violates a property. Condition variables and monitors (L3) are the classic shared-memory building block on which locks, queues and thread-based designs sit.
terms: Concurrency and parallelism — concurrency is structuring a program as independent activities that may overlap in time; parallelism is running them at the same instant on several cores. Concurrency can exist on one core.
Race condition — a bug where the result depends on the order in which concurrent steps happen.
Data race — two threads access the same memory at the same time, at least one writes, and there is no synchronisation; many languages define this as undefined or unspecified behaviour.
Deadlock — a state in which each activity waits for another and none can proceed.
Actor — an entity with private state and a mailbox; it handles one message at a time and may send messages, create actors or change its behaviour.
Channel — a typed queue between processes; an unbuffered channel makes sender and receiver meet (rendezvous).
Event loop — one thread that waits for events (I/O ready, timer) and runs the callback or the suspended function that handles each.
Coroutine — a function that can suspend and resume; async/await is syntax for coroutines.
Supervision — a design in which a parent process watches its children and restarts them when they fail.
history: The problem came with the first multiprogramming systems. Edsger Dijkstra's "Cooperating Sequential Processes" (1965) defined the critical-section problem and introduced semaphores. C. A. R. Hoare's monitors (1974) and Per Brinch Hansen's work packaged locks and condition variables with the data they protect. These form the shared-memory model that Java (1996) and most languages still use.
Message passing has a parallel history. Carl Hewitt, Peter Bishop and Richard Steiger proposed the actor model in 1973 for artificial intelligence research: everything is an actor, and actors communicate only by asynchronous messages. Gul Agha gave it a theory in 1986. Hoare's CSP (1978) took a different view: processes are sequential and synchronise by communicating on named channels, with a rendezvous. Robin Milner's CCS (1980) and the π-calculus (1992) built the algebra of such systems. David May's occam (1983) was a language built on CSP.
Erlang came from Ericsson's telephone switches (Joe Armstrong, Robert Virding and Mike Williams, 1986). A switch needs many thousands of simultaneous calls and must keep running when one fails, so Erlang made processes cheap, isolated and supervised ("let it crash"); it was open-sourced in 1998. Dan Kegel's "C10K problem" (1999) pointed out that thread-per-connection servers could not handle ten thousand connections, which pushed servers towards event loops (nginx, 2004; Node.js, 2009). Go (announced 2009, 1.0 in 2012) brought CSP to mainstream through goroutines and channels, and Rob Pike's talk "Concurrency is not parallelism" (2012) explained the design. Akka (2009) brought actors to the JVM.
Async/await spread from C# 5 (2012) to Python 3.5 (2015), JavaScript (ES2017), Kotlin coroutines (2018) and Rust (1.39, 2019). Bob Nystrom's essay "What Color Is Your Function?" (2015) described its main cost. Software transactional memory (Shavit and Touitou, 1995; Harris, Marlow, Peyton Jones and Herlihy, 2005 for Haskell) tried to make shared memory composable. Java's virtual threads (JEP 444, JDK 21, 2023) went back to the thread-per-task style, with cheap threads managed by the runtime, and structured concurrency (Nathaniel J. Smith, 2018; Java and Kotlin follow) ties the lifetime of child tasks to a scope.
how: Shared memory with locks. Several threads run in one address space, scheduled by the operating system. Any thread can read or write any data, so correctness depends on discipline: protect each shared variable with a lock (or use atomic instructions), always take multiple locks in the same order, and wait for conditions with condition variables. A monitor is the object-oriented form: data plus a lock plus condition variables, as in Java's synchronized methods. The language memory model (Java 5, C++11, Go) defines which writes other threads must see and when; without synchronisation, a thread may legally never see another thread's write. The strength is that it matches the hardware and gives the best performance for fine-grained sharing. The weakness is that nothing in the model prevents you from touching shared data without the lock. An OS thread costs roughly 8 MB of virtual stack on Linux by default (1 MB for Java threads), a few KB of kernel memory and microseconds to switch, which limits practical counts to thousands or tens of thousands.
Actors remove sharing. Each actor owns its state and has a mailbox, a queue of messages. The runtime takes one message at a time from the mailbox and runs the actor's handler, so inside an actor the code is sequential and needs no locks. Actors talk by sending messages to addresses; sends are asynchronous and do not wait. Messages between one sender and one receiver arrive in order, but there is no global order. Because the only coupling is the message, an actor can live on another machine (location transparency), and the same code scales out. Erlang processes weigh about 2 to 3 KB, so a node can host millions, each with its own small heap and its own garbage collection. Failure is handled by supervision: processes are linked, and a supervisor that sees a child crash restarts it from a known state. The weak points are mailboxes (usually unbounded, so there is no back-pressure unless you design it), messages that arrive out of the sequence you expected, and the loss of the simple call-and-return style: a request-reply becomes two messages and some state.
CSP is related but different. A goroutine is a lightweight process, with a stack that starts at about 2 KB and grows, scheduled by the Go runtime onto a few OS threads (an M:N scheduler). Processes communicate through channels. A send on an unbuffered channel blocks until another goroutine receives, so the send is also a synchronisation point. A buffered channel decouples them up to its capacity and gives natural back-pressure. The select statement waits on several channels at once. The rule of thumb is "do not communicate by sharing memory; share memory by communicating": ownership of a value moves with the message. Unlike actors, the channel is a first-class object that is passed around, and the processes are anonymous. In Go, ordinary threads-and-locks code is still allowed, and the race detector catches data races at test time.
Async/await targets the case in which most of the time is spent waiting for I/O. A function marked async runs until it reaches an await on an operation that is not ready; the compiler has turned the function into a state machine that saves its local variables, returns control to the event loop, and is resumed when the awaited event happens. The event loop uses the operating system's readiness interface (epoll, kqueue, io_uring) to wait for thousands of connections in one thread. There is no preemption: a task runs until it awaits, so one task that computes for a long time, or a blocking call, stalls all the others. The cost of a pending task is a small heap object, so a million of them are feasible.
A back-of-the-envelope tool decides how much concurrency is needed. Little's law says the number of requests in flight equals the arrival rate times the time each one takes. A service at 20,000 requests per second with 100 ms latency has about 2,000 requests in flight. The model decides the cost of holding them: 2,000 OS threads is feasible, 200,000 is heavy, and tasks or goroutines make both cheap.
Finally, the models can be combined. Java services use a thread pool for blocking work and an event loop for network I/O. Akka runs actors on a thread pool. Rust offers threads with ownership checks (Send and Sync types so the compiler rejects sharing mutable data across threads without a lock), async tasks, and channels. Many systems use a single-writer principle: one thread or actor owns each piece of mutable state, and others send it requests. This captures most of the benefit of each model.

example: Example one: counting interleavings. Two threads each add 1 to a shared counter that starts at 0. Each increment is three steps: load the counter into a register, add 1, store the register. Together there are 6 steps, and the number of ways to interleave two sequences of 3 steps (keeping each thread's own order) is 6! / (3! × 3!) = 20. A short enumeration shows that only 2 of the 20 give the right answer 2: the two cases where one thread finishes completely before the other begins. In the other 18, both threads load 0 before either stores, and the final value is 1: an update is lost. A race is not a rare event on a bad day; most orderings are wrong, and it is the scheduler that makes the good ones common. With three threads of three steps each, the count is 9! / (3!)³ = 1,680 interleavings, which is why testing alone cannot find races and why model checkers face "state explosion".
Now the fix in each model. With locks: lock; load; add; store; unlock. Only the two good orderings remain, and the result is always 2. With atomics: one atomic fetch-and-add instruction does the three steps indivisibly. With an actor: a counter actor owns the number and receives two "increment" messages; it handles one at a time and the final value is 2, but the callers must send messages and, to read the value, send a "get" message and wait for the reply. With CSP: a goroutine owns the counter and loops on select over an increment channel and a read channel; same result.
Example two: failures that each model keeps. Locks: thread A holds lock 1 and wants lock 2; thread B holds lock 2 and wants lock 1. Both wait forever (deadlock). Prevention: take locks in a global order. Channels: two goroutines each do an unbuffered send to the other before receiving; both block (deadlock), and Go reports "all goroutines are asleep" when it detects it. A goroutine that sends on a channel nobody will read blocks forever and leaks (goroutine leak). Actors: two actors each ask the other and wait synchronously for the answer, using the blocking "ask" pattern; they deadlock. A mailbox that grows without limit under load causes the process to run out of memory. Async: a blocking call (for example a synchronous database driver) inside an async handler freezes the event loop; with one loop thread, all connections stall.
intuition: A shared whiteboard with a few markers that people must take turns using (locks), or everyone in separate rooms passing notes through slots in the wall (actors and channels), or one clerk who goes from desk to desk whenever a desk is ready (event loop).
Each model is a choice about where the danger lies. Shared memory puts the danger in forgotten locks. Message passing moves it to the order and meaning of messages, but it removes the possibility of two parties changing the same data at once. The event loop removes parallel execution altogether to make every step between awaits atomic, and pays by requiring that nothing blocks. None of them removes the need to think about order; they only make part of the thinking local.
mistakes: People often think concurrency and parallelism are the same thing. In fact a single-threaded event loop is concurrent (it handles thousands of connections in overlapping time) but not parallel, and a data-parallel GPU kernel is parallel but has little concurrency structure. Concurrency is about structure and waiting; parallelism is about using hardware.
People often think message passing cannot have races or deadlocks. In fact it moves them: actors can deadlock on mutual requests, depend on message order that is not guaranteed, and overflow mailboxes; channels can deadlock and leak goroutines. Passing a pointer through a channel and then using it from both sides is still a data race.
People often think async/await makes code run faster or in parallel. In fact it makes waiting cheap. It does nothing for CPU-bound work, and on a single event loop a long computation blocks every other task. CPU work should go to a thread pool or process pool.
tradeoffs: Choose threads with locks (or a concurrent library: queues, concurrent maps, atomics) when you need maximum performance on shared in-memory structures, such as caches, indexes and counters, and the team has the discipline to review them. You give up safety: the compiler does not check lock use, and bugs appear under load. Prefer higher-level tools (java.util.concurrent, thread-safe queues) to raw locks.
Choose actors when you have many independent stateful entities (sessions, devices, game players, accounts), when failure isolation and restarts matter, or when the system is distributed over machines. You get isolation and a natural scaling model; you give up simple request-reply code, global ordering, and easy debugging of message flows, and you must add back-pressure yourself.
Choose CSP-style channels (Go) for pipelines and fan-out/fan-in structures inside one process, where ownership moves along the pipe. You get simple, readable code and cheap goroutines; you give up some performance compared to a well-tuned lock for tiny critical sections, and you must manage goroutine lifetimes with contexts to avoid leaks.
Choose async/await for I/O-heavy servers and clients with thousands of concurrent waits, especially in JavaScript and Python where threads are weak, or in Rust where it avoids thread stacks. You give up the simple call stack (debugging and tracing are harder), you split the ecosystem into async and blocking functions, and you must never block the loop. In Java, consider virtual threads instead: blocking style with cheap threads, no colouring, at the price of the same shared-state rules as threads.
friction: No model removes the hard problems. Ordering, partial failure, back-pressure, timeouts and cancellation remain, and they get harder when processes are on different machines, where messages can be lost, duplicated and delayed. Actors usually offer at-most-once delivery; exactly-once needs deduplication and idempotent handlers.
Debugging is difficult in all of them. Races are not reproducible; deadlocks need thread dumps; goroutine leaks and abandoned tasks need profiling; async stack traces show the event loop and not the logical caller. Structured concurrency, where the lifetime of child tasks is limited to a scope, and context cancellation reduce leaks, but they must be used consistently. Tools help (Go's race detector, ThreadSanitizer, Loom-style schedulers, TLA+ and model checkers for protocols), but the state space grows exponentially with the number of activities.
Language limits matter. Python's global interpreter lock prevents threads from running Python code in parallel in the standard build (an optional free-threaded build exists since 3.13), so CPU work needs processes. JavaScript has one thread per isolate. Memory models differ between languages and hardware, and weak orderings on ARM expose bugs that x86 hides. Finally, mixing models makes the system harder to reason about than any one of them: a lock held across an await, or blocking inside an actor, is a classic way to stall a whole service.
practice: Start with the simplest model that fits and keep shared mutable state small. Prefer immutable data and message-style hand-off between components; confine each mutable object to one thread, actor or task (the single-writer principle). Use proven concurrent collections and thread pools; do not write lock-free algorithms yourself.
Size pools by workload: for CPU-bound work, about the number of cores; for waiting work, use async I/O or virtual threads, or compute the pool size from Little's law (requests in flight = rate × latency). Bound everything: queue lengths, mailbox sizes, number of concurrent requests, timeouts on every call, so overload becomes back-pressure and errors instead of memory exhaustion. Make operations idempotent and propagate cancellation and deadlines.
When you take locks, keep critical sections short, never call unknown code or do I/O while holding a lock, and fix a global order for multiple locks. In async code, never call blocking APIs from the event loop; move them to a worker pool. In Go, give every goroutine an exit path (context cancellation or a closed channel). Test with the race detector or ThreadSanitizer in CI, run load tests, and capture thread or goroutine dumps in production incidents. For protocols and critical algorithms, write a small TLA+ or model-checker specification before the code.
interview: Compare shared-memory threads, actors, CSP and async/await. When would you pick each? || Threads with locks for fine-grained sharing and top performance; actors for many isolated stateful entities with supervision and distribution; CSP channels for pipelines and ownership hand-off within a process; async/await for I/O-bound servers with huge numbers of waits. Each prevents a different class of bugs and allows others.
Two threads increment a shared counter 1,000 times each. What can the result be and why? || Less than 2,000 in general (in theory as low as 2): an increment is load, add, store, and interleavings in which both threads load the same value lose an update. A lock or an atomic fetch-and-add makes each increment indivisible and gives exactly 2,000.
Why can a single event loop serve 100,000 connections, and what breaks it? || Waiting costs only a small heap object per connection and the OS tells the loop which sockets are ready (epoll), so one thread handles the ready ones. It breaks when a handler blocks or computes for a long time, since there is no preemption; every other connection waits. Offload CPU and blocking work to a pool.
How does Erlang's "let it crash" work, and what does it require? || Processes are isolated, share nothing and are cheap; a supervisor monitors children and restarts a failed one in a clean state according to a restart strategy. It requires that state can be rebuilt (or is stored elsewhere), that restarts are idempotent, and that messages can be lost, so protocols must handle retries.
What is function colouring, and how do virtual threads address it? || In async/await, async functions can only be awaited from async functions, so the codebase splits into two incompatible kinds. Virtual threads keep the ordinary blocking style: when a virtual thread blocks, the runtime parks it and runs another on the same OS thread, so there is no second kind of function.
quiz: What is the difference between concurrency and parallelism? || Concurrency is structuring a program as independent activities that overlap in time, even on one core. Parallelism is executing several of them at the same instant on different cores.
Why do only 2 of 20 interleavings of two three-step increments give the correct result? || Correctness requires one thread's store to happen before the other's load, which is only true when one thread completes entirely before the other starts, 2 of the 20 orderings. In the rest both read 0 and the final value is 1.
What does a buffered channel give that an unbuffered one does not? || It lets the sender continue until the buffer is full, decoupling the two sides, and a full buffer blocks the sender, which is natural back-pressure. An unbuffered channel forces a rendezvous.
A service handles 50,000 requests per second, each taking 200 ms. How many are in flight, and which models handle that cheaply? || 50,000 × 0.2 s = 10,000 requests in flight (Little's law). Goroutines, virtual threads, actors or async tasks hold that for tens of megabytes; one OS thread per request would need 10,000 threads and much more memory and switching.
Why is blocking inside an async handler dangerous, and what is the fix? || The event loop is a single thread without preemption, so a blocking call stops all other tasks. Use non-blocking APIs or move the blocking work to a worker pool and await its result.
