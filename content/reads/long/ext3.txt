@@+ llm
history: Language models are old: Shannon estimated the entropy of English by having people guess the next letter (1951), and n-gram models powered speech recognition and machine translation for decades. Neural language models began with Bengio and colleagues (2003); word2vec (2013) showed that predicting context produces useful word vectors; recurrent networks with attention improved translation (2014–2016). The transformer (2017) removed recurrence and made training highly parallel.
Then scale took over. GPT (2018) and BERT (2018) showed that pre-training on large text corpora transfers to many tasks. GPT-2 (2019) and GPT-3 (2020, 175 billion parameters) showed that bigger models trained on more data improve smoothly and can learn tasks from a few examples in the prompt. Scaling-law papers (2020, 2022) made the trade-off between parameters, data and compute predictable. InstructGPT (2022) and ChatGPT (November 2022) showed that post-training with human feedback turns a text predictor into an assistant, and the field exploded: Claude, Gemini, Llama, Mistral, Qwen, DeepSeek and others. Since 2024, the frontier has moved toward reasoning models trained with reinforcement learning to think before answering, multimodal inputs, very long contexts, tool use and agents, and toward efficiency: mixture-of-experts architectures, distillation into small models, and low-precision inference.
how: It is worth following how one token is produced inside the model, because every expensive part of serving comes from it. The token's embedding enters the first layer. In attention, it is projected into a query, key and value; its query is compared with the keys of all previous tokens (read from the KV cache), the scores become weights through a softmax, and the weighted sum of values is projected back. A residual connection adds this to the input. Then the MLP block (or, in mixture-of-experts models, the few experts chosen by a router) transforms each token independently: this is where most parameters, and much of the stored 'knowledge', live. After dozens of layers, a final projection produces a score for every token in the vocabulary.
During pre-training, all tokens of a long sequence are processed in parallel, and the loss is the average negative log-probability of each actual next token. During inference, the expensive phases are different: prefill processes the prompt in parallel and is limited by arithmetic, while decoding produces one token at a time and is limited by how fast weights and KV cache can be read from memory. This is why serving engines batch many users together, quantize weights, share prompt prefixes and use speculative decoding.
practice: For an engineer building with LLMs, a few principles go a long way. Treat the model as a component with measurable behaviour: build an evaluation set from real tasks before choosing a model or tuning prompts, and re-run it whenever anything changes. Put facts the model must use into the context (retrieval, tools, documents) rather than hoping it remembers them, and ask for answers grounded in that context. Use structured outputs (JSON schemas, constrained decoding) when another program consumes the result.
Choose the smallest model that passes your evaluations, then measure cost and latency at your expected traffic: input tokens, output tokens, prompt caching and batch processing change the bill dramatically. Keep prompts stable at the start (for caching) and variable at the end. Log inputs and outputs (with privacy controls) so failures can be reproduced. And never let untrusted text in the context authorize actions on its own; that boundary belongs in your application code.

@@+ agents
history: The idea of software agents that perceive, decide and act is old in AI research (the 'intelligent agent' framing of Russell and Norvig's textbook, 1995). Language-model agents began soon after GPT-3: WebGPT (2021) browsed the web to answer questions, SayCan (2022) connected language models to robot skills, and ReAct (2022) interleaved reasoning and tool calls. In 2023, open-source experiments like AutoGPT showed both the excitement and the fragility of long autonomous loops, while model providers added native function calling to their APIs.
From 2024, agents became practical in narrower, well-tooled domains, above all software engineering. Benchmarks like SWE-bench measured whether agents could fix real GitHub issues, and coding agents (Claude Code, Cursor's agent mode, OpenAI Codex, GitHub Copilot's agent and others) moved from demos to daily tools. The Model Context Protocol (late 2024) standardized how agents connect to tools and data, and agent-to-agent protocols followed. Reasoning models trained with reinforcement learning on long tasks made agents more reliable over many steps.
how: Real agent systems add structure around the basic loop. A harness decides which tools are available, executes them (often in a sandbox such as a container), enforces permissions (which actions need human approval), manages the context window (summarizing or dropping old steps), and stops runaway loops with limits on steps, time or cost. Many designs use a planner or orchestrator that breaks a task into parts and delegates them to sub-agents with clean, focused contexts, then combines the results. Memory outside the context window (files, notes, databases) lets work continue across sessions.
Anthropic's 'Building effective agents' essay makes a useful distinction: workflows are systems where code defines the steps and the model fills in parts (prompt chaining, routing, parallel calls, evaluator–optimizer loops), while agents let the model decide the steps. Workflows are more predictable; agents are more flexible. Most production systems use workflows where the path is known and agents only where it is not.
practice: Start with the simplest design that works: a single well-prompted model call, then a fixed workflow, and only then an autonomous agent. Give agents few, well-described tools with clear inputs and helpful error messages, because tool design matters as much as prompt design. Make every action either reversible or gated by approval, and run code in sandboxes with least-privilege credentials.
Evaluate agents on complete tasks, not single steps: measure task success, cost, time and the kinds of failures, and keep transcripts so you can see where loops went wrong. Treat all content from tools, web pages and documents as untrusted data that can contain instructions, and design permissions so that a successful prompt injection cannot do serious harm.

ref: book | Artificial Intelligence: A Modern Approach, 4th ed. | Russell & Norvig, 2020 |

@@+ attention
history: Attention was introduced for neural machine translation by Bahdanau, Cho and Bengio (2014): instead of squeezing a whole source sentence into one fixed vector, the decoder learned to look back at relevant source words for each word it produced. Luong and colleagues (2015) simplified the scoring functions. In 2017, Vaswani and colleagues at Google showed in 'Attention Is All You Need' that attention alone, without recurrence or convolution, could build the whole model: the transformer, with self-attention, multiple heads and positional encodings.
Later work changed the details rather than the idea. Rotary position embeddings (2021) improved how position is represented. Multi-query (2019) and grouped-query attention (2023) shrank the KV cache. FlashAttention (2022, with versions 2 and 3 after) made exact attention much faster by respecting the GPU memory hierarchy. Sliding-window and sparse patterns, and hybrids with state-space or linear-attention layers, aim to reduce the quadratic cost for very long contexts. DeepSeek's multi-head latent attention (2024) compressed keys and values into a small latent vector.
how: It helps to understand what attention heads actually learn. Interpretability research has found recognizable patterns: 'previous token' heads, heads that track syntax, and 'induction heads' that find an earlier occurrence of the current token and copy what followed it, a mechanism behind in-context learning. Heads in later layers combine information gathered by earlier ones, building more abstract features in the residual stream.
Attention also comes in two forms. Self-attention lets tokens in one sequence attend to each other; causal masking stops each token from seeing future tokens during training of decoder-only models. Cross-attention lets one sequence attend to another (a decoder attending to an encoder's output, or text attending to image features in some multimodal models). The arithmetic is the same; only where queries, keys and values come from differs.
practice: For practitioners, attention's cost model matters most. Prefill cost grows roughly with the square of prompt length, and KV-cache memory grows linearly with context length, number of layers and number of KV heads. So very long prompts raise both latency and cost; caching repeated prefixes, retrieving only relevant chunks, and summarizing old context are the main levers. When choosing or serving a model, check its KV-cache size per token (affected by GQA or MLA), the attention kernels available for your hardware, and how quality holds up at the context lengths you actually use, not only the maximum advertised.
ref: paper | Neural Machine Translation by Jointly Learning to Align and Translate | Bahdanau, Cho & Bengio, ICLR 2015 | https://arxiv.org/abs/1409.0473
ref: paper | In-context Learning and Induction Heads | Olsson et al. (Anthropic), 2022 | https://transformer-circuits.pub/2022/in-context-learning-and-induction-heads/index.html

@@+ gd
history: Cauchy described gradient descent in 1847 for solving systems of equations. Robbins and Monro (1951) laid the foundation for stochastic approximation, the theory behind stochastic gradient descent. The perceptron learning rule (1958) and the Widrow–Hoff rule (1960) were early forms of gradient learning. Backpropagation (1986) made gradients of multi-layer networks practical, and SGD with momentum became the workhorse of neural network training.
The deep learning era refined the optimizer. AdaGrad (2011), RMSProp (2012) and Adam (2014) adapted the step size per parameter; AdamW (2017) fixed how weight decay interacts with Adam and became the default for transformers. Learning-rate warm-up and cosine decay schedules, gradient clipping, large-batch methods (LARS, LAMB) and, more recently, optimizers like Shampoo and Muon that use more structure of the weight matrices, all aim at the same goal: faster and more stable progress per unit of compute.
how: In large-scale training, the optimizer is a significant part of memory and communication. Adam keeps two extra numbers per parameter (running averages of the gradient and of its square), so a model with 70 billion parameters needs hundreds of gigabytes just for optimizer state in FP32. Sharded data parallelism (ZeRO, FSDP) splits these states across GPUs. Mixed precision keeps master weights and optimizer state in higher precision while computing in BF16 or FP8.
The learning-rate schedule matters as much as the optimizer. A short warm-up (rising from near zero) avoids unstable early steps when Adam's statistics are still poor; then the rate decays slowly, often with a cosine shape or a 'warmup–stable–decay' schedule, so the model makes large moves early and fine adjustments later. Gradient clipping caps the size of updates to prevent rare huge gradients from destroying training. Loss spikes in large runs are often handled by rolling back to a checkpoint and skipping problematic data.
practice: When training or fine-tuning a model, tune the learning rate first: it usually matters more than any other hyperparameter, and a sweep over a few values spaced by factors of three is cheap and informative. Watch the training and validation loss curves together, and the gradient norm. Steady loss with growing gradient norm, or sudden spikes, signal instability; lower the learning rate, add warm-up or clipping, or check the data. For fine-tuning with LoRA or full updates, use much smaller learning rates than pre-training, and evaluate on held-out task data often, since overfitting a small dataset happens fast.

@@+ consensus
history: The problem was posed in the late 1970s and early 1980s. Lamport, Shostak and Pease described the Byzantine Generals problem in 1982. Fischer, Lynch and Paterson proved the FLP impossibility result in 1985. Dwork, Lynch and Stockmeyer (1988) showed consensus is possible under partial synchrony, where the network eventually behaves. Brian Oki and Barbara Liskov's Viewstamped Replication (1988) and Lamport's Paxos (submitted in 1990, published in 1998, explained again as 'Paxos Made Simple' in 2001) gave practical crash-tolerant protocols.
Industry adoption came with large-scale systems. Google's Chubby lock service (2006) used Paxos, and the paper 'Paxos Made Live' (2007) described how hard real implementation was. ZooKeeper (2008–2010) with its Zab protocol brought coordination to the Hadoop ecosystem. Raft (2014) made consensus understandable and spread into etcd (behind Kubernetes), Consul, CockroachDB, TiKV and Kafka's KRaft. Byzantine protocols (PBFT 1999, Tendermint, HotStuff) found new use in blockchains. Flexible Paxos (2016) showed that quorums for different phases only need to overlap, not be majorities, opening new trade-offs.
how: Most production systems do not run one consensus group for all data. They partition data into many ranges or shards and run a separate consensus group (often Raft) per shard: CockroachDB, TiKV and YugabyteDB do this with thousands of groups per cluster. This multiplies throughput, since each group has its own leader, and spreads leaders across machines. Cross-shard transactions then need a commit protocol on top, such as two-phase commit whose participants are themselves replicated by consensus, so the coordinator's failure no longer blocks forever.
Leases are a common optimization. A leader that holds a time-based lease (agreed with a majority) can serve reads locally without a round trip, because no other leader can exist until the lease expires. This makes reads fast but depends on bounded clock drift; if clocks misbehave, a lease can lead to stale reads. Read-index protocols (confirming leadership with a heartbeat round before serving a read) avoid the clock assumption at the cost of a round trip.
practice: Use consensus where you truly need a single agreed answer: leadership, configuration, metadata, locks and the ordering of critical writes. Keep that data small and the write rate modest, and put bulk data elsewhere. Run three nodes to tolerate one failure, five to tolerate two; more voters add latency without much benefit. Place replicas in different failure domains (racks, zones) but within low latency of each other. Use fast, dedicated disks for consensus logs, because fsync latency directly sets commit latency. And test failures deliberately, including slow disks and partial network partitions, not only clean crashes.

@@+ raft
history: Ongaro and Ousterhout designed Raft at Stanford, publishing it at USENIX ATC 2014 (where it won a best paper award) and in Ongaro's PhD thesis. They ran a user study showing that students learned Raft better than Paxos. Within a few years Raft had dozens of implementations: etcd's raft library (used by Kubernetes, CockroachDB and TiKV through ports), HashiCorp's raft (Consul, Nomad, Vault), Apache Ratis, and Kafka's own KRaft implementation, which replaced ZooKeeper entirely in Kafka 4.0.
Research and practice added refinements: pre-vote (to stop a partitioned node from disrupting the cluster with ever-higher terms when it returns), leader leases and read-index for fast reads, learners (non-voting members that catch up before joining), and joint consensus or one-at-a-time membership changes. Jepsen tests and formal TLA+ specifications found and fixed bugs in several implementations, a reminder that 'understandable' does not mean 'easy to implement'.
how: Several details are where real implementations succeed or fail. Log compaction: the log cannot grow forever, so each node periodically takes a snapshot of its state machine and discards log entries before it; a follower that is too far behind receives the snapshot instead of individual entries. Commit rule subtlety: a leader may only count replicas to commit entries from its own term; entries from earlier terms are committed indirectly when a newer entry after them commits. Ignoring this rule (illustrated in figure 8 of the paper) can lose committed data.
Performance optimizations include batching many client commands into one log append, pipelining AppendEntries without waiting for each response, and writing to the leader's disk in parallel with sending to followers. With these, a Raft group can commit tens of thousands of operations per second, limited mainly by fsync latency and network round trips.
practice: If you use a Raft-based system (etcd, Consul, Kafka KRaft controllers), watch leader changes, commit latency and disk fsync latency; frequent elections usually mean slow disks, CPU starvation or network problems, not a Raft bug. Tune election timeouts to be well above normal round-trip and fsync times. Keep etcd's database small (Kubernetes clusters suffer when it grows into gigabytes) and compact and defragment it regularly.
If you implement Raft yourself, start from the paper's figure 2, write a deterministic test harness that injects partitions, delays and crashes, and compare against a specification. Better still, use a mature library unless consensus is your product.
