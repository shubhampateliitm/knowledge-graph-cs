@@+ fdb
tradeoffs: FoundationDB or a distributed SQL database. Choose FoundationDB when you are building a database or a platform service and you want a small, very reliable, strictly serializable core that you shape with your own layer: Apple's CloudKit, Snowflake's metadata, and many internal record stores do this. Choose CockroachDB, TiDB or Spanner (see cockroach, tidb, spanner) when applications need SQL, secondary indexes, schema changes and a query optimizer out of the box. With FoundationDB you give up a ready-made query language and must write or adopt a layer; with a SQL system you give up control over data layout and pay for a heavier, less predictable stack.
Fit the 5-second, 10 MB transaction limits or not. A transaction should read and write at most about 10 MB, last under 5 seconds, and keep values under 100 KB (keys under 10 KB). Choose FoundationDB when your work is many short transactions (point reads, small range reads, small writes); typical clusters sustain hundreds of thousands of operations per second with single-digit-millisecond reads and commits in a few milliseconds inside one region. Choose a different system (Postgres, Cassandra, a lakehouse table) for long analytical scans, bulk loads, or big blobs. Splitting a long job into many small transactions is possible, but you then own the atomicity across them.
Single region or multi-region. Choose FoundationDB in one region, or across close regions with a three-region configuration where commits wait for a log server in a second data centre (adds a round trip, roughly 5 to 30 ms depending on distance), when you need strict serializability. Choose a Cassandra or DynamoDB style store (see cassandra, dynamodb) when you need active-active writes in far-apart regions and can accept eventual consistency or per-item conditions. FoundationDB has one logical write path (one sequencer), so a far-away client always pays the wide-area distance to commit; you give up local-write latency everywhere in exchange for one global order.
Optimistic conflicts or locks. FoundationDB is optimistic (see occ): nothing blocks, but a transaction that read a key someone else changed is aborted and must retry. Choose it when conflicts are rare, such as per-user or per-tenant data, where abort rates stay under a few percent. Hot keys (a global counter, a single "latest" row) turn into retry storms, so use atomic operations (ADD, MAX), split the counter over many keys, or use versionstamped keys. If your workload is a few hot rows updated by many clients, a pessimistic locking database (see postgres, mysql) behaves better.
Hardware and operations. Run FoundationDB with one storage process per SSD core, log servers on separate fast fsync disks, and at least 3 or 5 coordinators; it is designed for SSDs and does not do well on network-attached slow disks. You give up elastic cheap-disk economics in return for latency that stays flat until the disks or the single sequencer saturate (on the order of a few million commits per second at the high end).
interview: Why is FoundationDB's transaction limit 5 seconds and 10 MB, and is it a design flaw? || It follows from the design: the resolvers and storage servers keep only about 5 seconds of versions (about 5 million versions at one million per second) in memory so conflict checks and MVCC reads stay cheap. Longer transactions would need disk-based version history and much bigger resolver state. It is a deliberate trade for low latency; long work is split into many short transactions with your own idempotency or a durable workflow on top.
interview: A global counter on FoundationDB shows 40 percent aborted transactions. What do you do? || Every increment reads and writes the same key, so OCC conflicts on all concurrent writers. Use an atomic ADD mutation, which does not add a read conflict, or shard the counter over N keys and sum them on read. For exact limits (quota), shard with per-shard budgets and rebalance. Check also that you do not read the counter before adding.
interview: Which part of FoundationDB is a scaling bottleneck, and how would you notice? || The single sequencer (version assignment) and, behind it, the commit proxies and resolvers set the commit ceiling; a single process hands out versions. You see rising commit latency, proxy queue length and "ratekeeper" throttling in the status JSON. You scale proxies and resolvers (stateless, so adding them is cheap), but the sequencer's ceiling is roughly the limit of one cluster, after which you shard into more clusters at the application level.
interview: How would you build a secondary index with exactly-once consistency on FoundationDB? || Write the record and its index entry in the same transaction, since transactions span any keys. Because a single transaction is strictly serializable, readers never see an index entry without the record. The cost is a larger write set and conflicts on hot index keys; for a monotonically increasing index key (timestamps) prefix with a shard number or use versionstamps to avoid a single hot range.
interview: Why do people say FoundationDB's testing is its main advantage, and does it replace production fault testing? || The whole cluster, network and disks run in one deterministic simulator with injected failures, so a bug found once can be replayed exactly; years of simulated runs find rare orderings real tests never hit. It does not model everything (real hardware firmware bugs, kernel behaviour, operator mistakes, slow-disk gray failures), so you still run real-cluster chaos and upgrade tests. Simulation raises confidence in the logic, not in the environment.
@@+ memcached
tradeoffs: Memcached or Redis (see redis, valkey). Choose Memcached when you need a plain, very fast, multi-threaded cache of strings: it uses all cores in one process, has a simple slab allocator with predictable memory, and 1 to 2 million simple gets per second per node is normal. Choose Redis or Valkey when you need data structures (sorted sets, lists, streams), atomic scripts, persistence or replication, or pub/sub. You give up, with Memcached, any structure beyond a key and a byte blob (max item size 1 MB by default) and any durability; you give up, with Redis, some per-node throughput on large machines (the command path is mostly single-threaded; I/O threads help but do not make it a multi-core cache) and pay more memory per key for its richer encodings.
Client-side or server-side placement. Memcached servers do not know about each other, so the client picks the node by hashing; use consistent hashing (see conshash) such as ketama so that adding the ninth node to eight moves about 1/9 of keys instead of nearly all. Choose a proxy (mcrouter, twemproxy, or Redis Cluster) when you want pooling, replication of hot keys and failover handled in one place and fewer connections, and accept one more network hop (about 100 to 300 microseconds) and one more thing to run. A pure client library is the cheapest and simplest as long as you control all clients.
Cache-aside or write-through. Choose cache-aside (read cache, on a miss read the database and fill) for read-heavy data with hit rates above 90 percent, where staleness of seconds to minutes is fine; you give up freshness and risk a stampede when a hot key expires (hundreds of requests hitting the database at once), which you reduce with a short lock or lease on the miss, jittered expiry, or serving stale while one request refreshes. Choose write-through or invalidate-on-write when stale reads are costly, and accept extra write latency and the race where an old value is set after an invalidation (use versions or leases).
Memory sizing and eviction. Memcached evicts by LRU per slab class, so item size mix matters: if sizes change over time, memory may be stuck in the wrong slab class and evict while "free" memory sits idle (modern versions rebalance automatically, but check eviction counts). Size the cache for the working set, not the whole dataset; a power-law access pattern often gives 90 percent hits with 10 to 20 percent of the data. Do not use it as a primary store: any node restart or eviction loses data, and the database must always be able to carry the full load on a cold cache, or at least degrade safely.
interview: What happens to your database when a cache node dies, and how do you design for it? || Keys on that node miss, so the database sees a burst of reads, up to the node's share of total read traffic (about 1/N for N nodes, more for hot keys). Design with headroom to take that, spread keys with consistent hashing so only 1/N moves, warm replacements gradually, and use request coalescing or leases so many clients do not refill the same key. Some teams keep a small replica pool (mcrouter) for the hottest keys.
interview: Why is Memcached multi-threaded but Redis mostly single-threaded, and does it matter? || Memcached keeps only simple operations, so worker threads share a hash table with fine-grained locks and scale to many cores. Redis keeps single-threaded command execution so each command (including a Lua script or a sorted set operation) is atomic without locks, which is simpler and often fast enough on one core (hundreds of thousands of operations per second). It matters when one box has 32 cores and you want it all used for plain gets: then Memcached, or several Redis shards per box.
interview: How do you prevent a cache stampede on a hot key? || Add jitter to expiry so keys do not expire together, use a lease or lock so only one caller recomputes while others wait or get stale data, refresh in the background before expiry, and cache negative results briefly. For extremely hot keys, replicate the key under several names and randomize which one clients read.
interview: A user updates a profile and still sees the old value. What are the causes? || A race between invalidation and fill (reader fetched the old row, writer updated and deleted the cache key, then the reader set the old value), replication lag if the fill read from a replica, or a client reading from a different cache pool or TTL. Fixes: delete after commit, use versions or leases, read your own writes from the primary for a short time, and keep TTLs as a safety net.
interview: How would you cache 100 TB of data with a 1 TB cache budget? || Measure the access distribution; with a power-law pattern a 1 percent cache can reach 80 to 95 percent hits. Cache the hot working set, compress values, skip large cold objects, put a CDN in front for static content, and use a tiered flash cache for the warm layer. Check the hit rate per key class and size the database for the misses.
@@+ mlflow
tradeoffs: MLflow or a managed/commercial tracker. Choose MLflow when you want open-source tracking, a registry and model packaging that run on your own infrastructure or in Databricks, with no per-seat fee; a small team can run it on one container with Postgres and S3 for a few dollars a day. Choose Weights & Biases, Neptune or a cloud service (SageMaker, Vertex) when you need rich live dashboards, team collaboration, sweeps and hosted support, and are fine paying per seat and sending metadata out. You give up, with MLflow, polish in the UI and out-of-the-box collaboration; with a hosted tool you give up control, data residency and cost predictability.
Self-hosted server or Databricks-managed MLflow. Choose managed (Unity Catalog model registry, see unity) when you already run Databricks: access control, lineage and audit come with the platform, and you avoid operating the tracking server. Choose self-hosted when you are on another platform or want portability; then plan for a SQL backend (Postgres, not SQLite, past a few users), an artifact store (S3), authentication (MLflow has only basic auth; put it behind a proxy with SSO), and database growth, since runs with millions of logged metric points slow the UI and queries.
MLflow alone or with an orchestrator and feature store. MLflow tracks what happened and stores what was produced; it does not schedule jobs, retry them, or compute features. Choose MLflow plus Airflow or Dagster (see airflow, dagster) for pipelines, and Feast (see feast) when training and serving need the same features. Choose Kubeflow-style all-in-one platforms only when you want one opinionated system and accept its Kubernetes weight. You give up simplicity as soon as you add pieces, so add them one at a time when the pain is real (for example, when a model cannot be reproduced because the feature code changed).
How much to log. Logging every step of every run is cheap in storage (a metric point is tens of bytes) but expensive in the tracking database and in clutter. Log parameters, git commit, data version or hash, final and periodic metrics (every 10 to 100 steps, not every step for million-step jobs), and the model artifact. Autologging is quick to adopt but records what the library decides; for production models, log the data snapshot ID explicitly, because a model without its data version is not reproducible.
Registry stages or aliases. Use aliases (champion, challenger) and versions rather than old fixed stages (Staging, Production), which are deprecated, and gate promotion on automated evaluation plus a human approval for high-risk models. You give up speed of release for safety; with only a handful of models a manual approval is fine, with hundreds you need policy checks in CI.
interview: How do you make an experiment reproducible with MLflow, and what is still missing? || Log the code version (git SHA), parameters, environment (conda or pip lock, or the container digest), random seeds, and a reference to the exact data snapshot such as a Delta table version. MLflow records most of this; what is missing is the data itself, the hardware nondeterminism (GPU kernels), and any feature logic outside the repo. Without a data version, re-running later gives different results.
interview: Your MLflow tracking server is slow with 50 teams. What do you do? || Check the backing database first: indexes, row counts in metrics tables, and long queries from the UI search. Move to Postgres or MySQL with a read replica, separate artifacts to object storage with direct client access, set retention or delete old runs, reduce metric logging frequency, and run several stateless server instances behind a load balancer. If you still outgrow it, shard by team or use the platform's managed service.
interview: How does a model go from MLflow to serving, and where does it break? || The registry holds a versioned model with a flavor (sklearn, PyTorch, pyfunc); a deployment job loads the alias version into a server (MLflow serving, Databricks Model Serving, SageMaker, or your own container). It breaks on dependency mismatches (the logged environment differs from the serving image), on feature mismatch between training and serving, and on large models that need GPU serving engines like vLLM instead of the generic pyfunc wrapper.
interview: Why not store experiment results in a spreadsheet or a plain database table? || For a few runs you can. MLflow adds a standard client for many libraries, automatic artifact storage, a UI for run comparison, lineage from model to run, and a registry with permissions. The price is another service to run. I switch when more than two people run experiments or when auditability is needed, not before.
@@+ feast
tradeoffs: Feast or a managed feature store. Choose Feast when you want an open-source, cloud-neutral registry of feature definitions that pushes to the stores you already operate (Redis, DynamoDB, Bigtable, Postgres for online; Snowflake, BigQuery, or files for offline), with no extra database of its own. Choose Tecton, Databricks Feature Store or SageMaker Feature Store when you need managed streaming feature pipelines, monitoring, SLAs and support. You give up, with Feast, built-in transformation engines and streaming computation (you bring Spark, Flink or dbt, and Feast mostly moves and serves the results); with a managed store you give up portability and pay platform prices.
Do you need a feature store at all. Choose one when several models share features, when the same features are needed online with a latency target (for example under 10 to 20 ms at p99 for 100 features), and when training-serving skew has already burned you. Skip it for a single model that scores in batch: a plain table or Delta table with a version is enough, and a feature store is another system to maintain. Many teams adopt it too early; the signs it is time are duplicated feature code in two repos and a model that behaves differently online than in tests.
Online store choice. Choose Redis when you need the lowest latency (sub-millisecond reads, 1 to 3 ms with network) and can afford memory (every entity's features stay in RAM, so 100 million entities with 1 KB each is about 100 GB before overhead). Choose DynamoDB or Bigtable for large entity counts with cheaper storage and 5 to 15 ms reads, and no servers to manage. Choose Postgres only for small scale. The price of cheap storage is higher tail latency and request-based costs.
Batch materialization or streaming push. Choose scheduled materialization (offline to online every 15 minutes to a few hours) when features change slowly, like customer segments or 30-day aggregates. Choose push-based streaming ingestion (Kafka and Flink writing into the online store, see flink) when freshness of seconds matters, as with fraud or real-time bidding; you then also have to compute the same feature in batch for training, which is the point where skew reappears. Point-in-time correct joins in the offline store are the part you should never skip: joining the latest value to a past label leaks the future into training.
Python server or a compiled feature server. The Python feature server is fine for hundreds of requests per second; for thousands per second with strict tail latency, use the Go or Java server, or read the online store directly from your serving code. You give up a bit of convenience for stable p99.
interview: What is training-serving skew and how does a feature store reduce it? || Skew means the model sees different feature values in production than in training, from different code paths, different time windows, or leakage of future data. A feature store gives one definition, point-in-time joins for training, and the same values materialized for serving. It does not remove skew by itself if you compute online features in a different pipeline than offline.
interview: How do you do a point-in-time join and why does it matter? || For each training row with an entity and a timestamp, take the latest feature value at or before that timestamp (with a time-to-live limit). Without it you use values that were not yet known at the time of the label, so offline metrics look great and production performance falls. It is usually an as-of join, expensive on large tables, so partition by entity and time.
interview: Your online feature lookups have p99 of 200 ms. How do you debug? || Split the time: network, feature server, online store, and serialization. Check the number of entities times features per request (fan-out), whether reads are batched in one call, hot keys, store capacity (throttling in DynamoDB), cold connections, and the Python server overhead. Fixes: batch reads, fewer features, co-locate in the same zone, move to Redis, or bypass the server.
interview: How do you handle a feature that is late or missing at serving time? || Decide per feature: a default value (with a flag feature saying it is missing), the last known value if within a freshness limit, or fall back to a simpler model. Monitor freshness and null rates, because a silent pipeline stall causes slow quality decay with no errors.
interview: Feast versus just writing features to Redis yourself? || The Redis-only approach works for one team and one model. Feast adds a registry, a shared definition, offline retrieval with point-in-time correctness, and consistency checks, and costs another layer of learning and operation. The deciding factor is the number of consumers and the history of skew incidents.
@@+ llamacpp
tradeoffs: llama.cpp or vLLM (see vllm). Choose llama.cpp (or Ollama on top of it) when one user or a few users run a model on a laptop, workstation, phone or CPU-only box, when you want one small binary with GGUF files, or when GPU memory is short and you need to split layers between CPU and GPU. Choose vLLM or SGLang when you serve many concurrent users on datacenter GPUs: continuous batching and paged KV cache give several times the throughput (often 3 to 10 times at 32 or more parallel requests). You give up, with llama.cpp, peak multi-user throughput and some newest-model features on day one; you give up, with vLLM, the easy setup on small or non-NVIDIA hardware.
Which quantization. Choose Q4_K_M (about 4.5 to 5 bits per weight) as the default: a 7B model shrinks from about 14 GB at 16-bit to about 4.5 GB, and a 70B from 140 GB to about 40 GB, with a small quality loss (often a percent or two on benchmarks). Choose Q5_K_M or Q6_K or Q8_0 when quality on code, maths or long reasoning matters and you have the memory; choose Q3 or Q2 (IQ-quants) only when the model otherwise does not fit, and test it, because small models and reasoning tasks degrade fastest. You give up accuracy for memory, and token speed on CPU rises almost in proportion to fewer bytes read, since decoding is memory-bandwidth bound.
Ollama or raw llama.cpp. Choose Ollama for a simple pull-and-run experience, model management and an OpenAI-compatible endpoint; choose llama-server directly when you need control: context size, batch size, KV cache type (q8_0 cache halves its memory), speculative decoding, grammar-constrained output, or the latest model support. You give up the polish and automatic defaults of Ollama, which can pick a small context window that silently truncates long prompts.
CPU, Apple silicon or discrete GPU. Apple silicon with unified memory (for example 64 to 128 GB at 200 to 800 GB/s) runs 30B to 70B quantized models at roughly 10 to 40 tokens per second for one user. A desktop CPU with dual-channel DDR5 (about 80 GB/s) gives a few tokens per second on a 7B Q4 model. A 24 GB consumer GPU runs a 30B-class Q4 model at 30 to 100+ tokens per second but runs out of memory for long contexts. Prompt processing (prefill) is compute-bound and slow on CPU; for long prompts a GPU matters more than for chat. Pick by the bytes read per token divided by memory bandwidth.
Context length. KV cache grows linearly with context and layers; a 7B model at 32K context can use several GB on top of the weights. Use quantized cache or smaller contexts if you run out of memory, and do not assume the advertised window works well at the end of it.
interview: Why is token generation speed on a laptop limited by memory bandwidth and not by compute? || Each new token needs reading all the weights (or the active ones) once for a single sequence, with only a couple of multiply-adds per weight, so arithmetic intensity is very low. Speed is roughly bandwidth divided by model size in bytes, so a 4 GB Q4 model on 100 GB/s gives an upper bound of about 25 tokens per second. This is also why quantization speeds decoding.
interview: When would you not use llama.cpp for a production service? || When you need high concurrency, strict latency SLOs under load, multi-GPU tensor parallelism at scale, or a managed prefix cache across many users; vLLM, SGLang or TensorRT-LLM are better. llama.cpp is excellent for edge, embedded, private on-device and low-traffic internal tools, where the simple deployment matters more than throughput.
interview: How does quantization hurt, and how do you decide how far to go? || It adds rounding error in weights, which shows up most in small models, long chain-of-thought and rare knowledge. Measure on your own task with a held-out set and compare perplexity and task accuracy between Q8, Q5 and Q4; pick the smallest that stays within your tolerance. Also, larger model at lower bits often beats a smaller model at higher bits for the same memory, down to about 4 bits.
interview: What does it mean to offload layers to the GPU, and what is the cost? || You place N transformer layers on the GPU and the rest on CPU RAM. Each token goes through both, so speed is limited by the slow part plus transfers between them. It lets a model bigger than VRAM run, but it is often several times slower than full GPU residency; if you can, use a smaller quant so everything fits.
interview: Your Ollama chatbot forgets the start of long documents. Why? || A default context window (for example 2K to 8K tokens) truncates the prompt silently. Raise the context parameter, watch KV memory, and, for documents, use retrieval instead of stuffing everything in.
@@+ sglang
tradeoffs: SGLang or TensorRT-LLM or vLLM (see vllm). Choose SGLang when many requests share long prefixes (a system prompt, a few-shot block, a chat history, an agent loop, tree-of-thought branches) because RadixAttention reuses the cache across requests; reports show up to several times more throughput on such workloads, and it has a frontend language for structured programs. Choose TensorRT-LLM when you run NVIDIA GPUs only, the model is stable, and you will spend engineering time on compiled engines, FP8 and in-flight batching tuned per GPU: it usually gives the best tokens per second and cost per token on H100 and newer. Choose vLLM for the broadest model and hardware coverage and the largest community. You give up flexibility with TensorRT-LLM (engines are built per GPU and model shape, and builds take minutes to hours), and some of the newest-model support speed with each of the others.
Prefix caching: when it helps and when it does not. With a 2,000-token shared system prompt and 200-token user messages, a cache hit skips about 90 percent of the prefill work and cuts time to first token a lot. With unique prompts (translation of independent documents, for example), there is nothing to reuse and the radix tree only adds a little bookkeeping and memory pressure. Cache hit rate is the number to measure; if it is under about 20 percent, the feature is not your main lever and batching or quantization will matter more.
Throughput or latency. Large batch sizes raise tokens per second per GPU (cost) but increase inter-token latency. Choose high batch and chunked prefill (see chunkedprefill) for offline, batch and cost-sensitive jobs; choose smaller batches, speculative decoding (see specdecode) and prefill/decode disaggregation when you have a strict p99 on time-to-first-token and inter-token latency for interactive users. Disaggregation separates compute-bound prefill from memory-bound decode on different GPUs, which helps latency at the price of moving the KV cache across the network (tens of GB/s needed) and operating two pools.
Parallelism choice. Use tensor parallelism inside a node (NVLink, 2 to 8 GPUs) to fit a model and cut latency; use pipeline parallelism across nodes only when needed because it adds bubbles; use expert parallelism for large mixture-of-experts models such as DeepSeek, where SGLang and TensorRT-LLM have specialised kernels. You give up simplicity and pay communication costs (all-reduce per layer) for each extra dimension.
Quantization. FP8 on H100-class GPUs roughly doubles throughput over 16-bit with small quality loss and is a good default; INT4 weight-only (AWQ, GPTQ) helps when memory-bound at small batch sizes; test quality on your task before shipping.
interview: What is RadixAttention and when does it help? || It keeps the KV cache of previous requests in a radix tree keyed by token sequences, so a new request whose prompt starts with a cached prefix reuses those blocks and only computes the rest, with LRU eviction of leaves. It helps with shared system prompts, multi-turn chat, few-shot examples, and branching agent calls. It does not help when prompts are unique.
interview: Why compile with TensorRT-LLM instead of running eager PyTorch kernels? || Compilation fuses operations, picks tuned kernels for the exact GPU and shapes, and allows FP8 and graph capture, which removes launch overhead and gives higher throughput. The cost is build time, per-GPU engines, and slower support for new architectures. It pays off for a stable model at large volume.
interview: Your LLM service has good throughput but poor time-to-first-token under load. What do you change? || Prefill requests are blocking decode or queueing behind big batches. Use chunked prefill, cap the batch tokens, prioritise short prompts, add prefix caching, separate prefill and decode pools, or add replicas. Measure queue time versus compute time first.
interview: How do you decide between vLLM and SGLang for a new service? || Benchmark with real traffic traces: compare tokens per second at your target p95 latency, cache hit rate, model and quantization support, and operational maturity. If prefixes are shared heavily or you do structured generation, SGLang often wins; otherwise vLLM's wider coverage and ecosystem often decide. Treat vendor benchmarks with care, since they use friendly workloads.
interview: What breaks when you serve a 128K-token context at scale? || KV cache memory (hundreds of KB per token for large models, so tens of GB per sequence), prefill compute that grows with length, and attention cost. You reduce it with grouped-query attention, KV quantization, paged cache with offload, prefix caching, and limits on concurrency per GPU.
@@+ a2a
tradeoffs: A2A or MCP (see mcp). Choose MCP when an agent needs to call tools and read data: a function with a clear schema, called by one model that stays in control. Choose A2A when you need to hand a goal to another autonomous agent, possibly built by another team or vendor, that has its own model, tools, memory and long-running work, and that returns a task with status and artifacts. Most systems need MCP first and A2A only at organisational boundaries. You give up, with A2A, control and predictability (the remote agent decides how to do the work, may take minutes, and may ask for more input); you give up, with MCP only, the ability to delegate open-ended jobs across trust boundaries.
Multi-agent protocol or one agent with many tools. Choose a single agent with tools until its context becomes overloaded: roughly beyond 20 to 40 tools, or when roles need different permissions, models or owners. Choose separate agents over A2A when teams must deploy and change independently, or when a specialist agent (a procurement agent, a code review agent) needs its own guardrails. Each hop adds latency (seconds, since each agent runs its own model calls), cost (tokens in every agent), and failure modes, so multi-agent designs often use 3 to 10 times the tokens of a single-agent one for the same task. Use them when the separation pays for it.
Sync, streaming or push. A2A tasks can return immediately, stream updates (server-sent events), or notify by webhook when done. Choose request/response for jobs under about 30 seconds, streaming for visible progress, and push notifications for jobs of minutes to hours. You give up simplicity as you move right, because you must track task IDs, retries, and lost callbacks, and make endpoints idempotent (see idempotence).
Trust and security. An Agent Card (a JSON description at a well-known URL) advertises skills and auth requirements, but it is self-declared. Choose strong auth (OAuth 2.0, mTLS, see oauth and mtls), scoped credentials, and an allow-list of remote agents for anything touching money or customer data. Treat the remote agent's output as untrusted input: it may contain prompt injection, wrong claims or leaked data. You give up open-ended discovery in return for safety.
Standard or ad hoc. A plain HTTP API with a task endpoint is enough when you own both ends and have two or three agents. Choose A2A when there are many counterparties, you want existing client libraries and discovery, and you accept that the protocol is young (2025), with versions and features still moving.
interview: What is the difference between A2A and MCP in one answer? || MCP connects a model or agent to tools and data: stateless-ish calls with typed inputs and outputs, controlled by the caller. A2A connects agents to other agents: opaque peers that accept a task, work over time, can ask for input, and return artifacts. They are complementary; an A2A agent typically uses MCP internally to reach its own tools.
interview: How would you make an A2A call to a long-running agent reliable? || Create the task with an idempotency key, store the task ID, subscribe to updates or webhooks but also poll as a fallback, set a timeout and a cancel path, handle input-required states, and keep results as artifacts you can fetch again. Treat the webhook as a hint, not the only signal.
interview: What can go wrong when agents call agents? || Loops and runaway cost (agent A delegates to B who delegates back), error compounding (each step 90 percent reliable gives about 59 percent over five steps), context loss, prompt injection that passes through, and unclear ownership of failures. Mitigate with depth limits, budgets, tracing across hops (OpenTelemetry), strict schemas for artifacts, and human approval for risky actions.
interview: Why not just put everything behind one orchestrator agent? || You can, and it is simpler to evaluate and debug. It breaks down when ownership, deployment cadence, data access or compliance differ between teams, or when the tool and context load is too large for one prompt. Then you split along those boundaries and use a protocol at the seams.
interview: How do you test a system of cooperating agents? || Test each agent alone with fixed fixtures and a mock of the others, then run end-to-end scenarios with recorded model outputs where possible, and score outcomes with evals (see evals) on success rate, cost and latency over many runs, because results vary by run. Log the trace of every hop for replays.

tradeoffs: FFmpeg or a hardware/cloud encoder. Choose FFmpeg with software encoders (libx264, libx265, SVT-AV1) when quality per bit matters most: x264 at preset slow or medium gives clearly better compression than hardware encoders, often 20 to 40 percent fewer bits for the same quality. Choose hardware encoders (NVENC, Quick Sync, VideoToolbox, or cloud services like AWS MediaConvert) when you need many live streams or fast turnaround and can accept somewhat larger files or lower quality: one GPU can encode a dozen or more 1080p30 streams in real time where a CPU core set manages one or two at slow presets. You give up compression efficiency with hardware; you give up throughput per dollar with software.
Preset and CRF choices. CRF (constant rate factor) 18 to 23 for x264 gives visually good to acceptable quality; each +6 roughly halves the bitrate. Slower presets save 5 to 15 percent bits per step but cost 1.5 to 3 times the CPU time. For video-on-demand watched many times, spend CPU once (slow preset, two-pass or CRF with capped bitrate) because bytes are paid on every view; for a one-time internal clip or live, use fast presets. For streaming ladders use capped CRF or constrained bitrate so the player's bandwidth model works (see abr).
Codec to target. Choose H.264 for universal playback (every device and browser), HEVC when you control the devices (Apple, smart TVs) and want about 30 to 50 percent fewer bits than H.264, and AV1 for large audiences on newer hardware where bandwidth cost dominates; AV1 software encoding is roughly 5 to 20 times slower than x264 at the same quality tier. You give up compatibility and encode time for lower delivery cost, and licensing questions exist for HEVC (see codecs).
Command line, library, or a wrapper service. Choose the command-line tool in a worker queue (Kubernetes jobs, Lambda, a batch fleet) for transcoding pipelines: simple, debuggable, and each job isolated. Choose libav libraries when you embed decoding or filtering in a product and need per-frame control, accepting C API complexity and memory-management risk. Choose GStreamer when you need a long-lived, dynamic pipeline graph. For untrusted input files, run FFmpeg sandboxed with CPU, memory and time limits, since decoders have a long history of security bugs.
Chunked parallel encoding. A two-hour film can be split at keyframes into chunks, encoded on many machines, and stitched, finishing in minutes at the cost of slight rate-control inefficiency at chunk borders (a percent or two) and orchestration code.
interview: Why can't you just copy streams instead of re-encoding everything? || Stream copy (-c copy) only rewraps the compressed data in a new container, so it is fast and lossless, but you cannot change resolution, bitrate or codec, and cuts land on keyframes. Re-encoding is needed for any of those; it costs CPU and a generation of quality loss.
interview: How would you build a transcoding service for 100,000 uploads a day? || Queue jobs, probe each file, choose a ladder per content (e.g. 5 to 8 renditions), run FFmpeg workers autoscaled on spot instances, write segments to object storage, produce HLS/DASH manifests, and verify outputs with checks for duration and quality metrics such as VMAF. Handle poison files with time limits and retries, store progress for resume, and track cost per minute of video. Use hardware encoders only if throughput matters more than bitrate.
interview: What makes a video seekable or cut-accurate, and why did my trimmed clip freeze at the start? || Inter-coded frames depend on a previous keyframe (IDR), so cutting at a non-keyframe without re-encoding leaves frames that reference missing data. Place keyframes every 2 seconds (aligned across renditions for streaming), cut with re-encoding for frame accuracy, or cut on keyframes for speed.
interview: How do you measure whether an encode is good? || Use objective metrics (VMAF, SSIM, PSNR) at matched bitrates and compare curves, then check visually on difficult content (grain, fast motion, text). PSNR is the weakest at matching human opinion; VMAF is the common industry choice. Do it per content type, since averages hide failures.
interview: Live streaming through FFmpeg stutters. Where do you look? || Encoder speed below 1x real time (CPU too slow for the preset), network upload too small for the bitrate, keyframe interval mismatches with the platform, clock and audio sync issues, and buffer sizes. Lower the preset speed, use hardware encode, cap bitrate, and watch the speed= value in the log.
@@+ codecs
tradeoffs: H.264, HEVC or AV1. Choose H.264 (AVC) when the video must play everywhere: every phone, browser, TV and set-top box decodes it in hardware, encoders are mature and fast, and patent licensing is settled for most uses. Choose HEVC (H.265) when you control the playback devices (Apple devices, most smart TVs, 4K and HDR broadcast) and want roughly 30 to 50 percent fewer bits at the same quality, accepting a patchy licensing situation with several patent pools. Choose AV1 when you have a very large audience, bandwidth is your main cost, and the viewers' devices decode it (recent phones, GPUs, TV chips), because it saves about 30 percent over HEVC and 40 to 50 percent over H.264 at equal quality and is royalty-free. You give up, going up the list, encoder speed, device coverage and often battery life on software decode.
Encode cost against delivery cost. AV1 software encoding is on the order of 10 to 50 times slower than x264 medium for the best quality settings, and HEVC about 2 to 5 times slower. The extra compute pays off only when views per title are high: a video watched a million times saves bandwidth on every view, a video watched ten times does not. A common policy is H.264 for everything, plus HEVC or AV1 renditions only for titles above a view-count threshold, and storage for two or three codec ladders. You give up storage and pipeline complexity for lower delivery bytes.
Hardware or software decode. Hardware decode uses a fraction of the power (a phone can play hours of H.264 or HEVC; software AV1 on older phones drains the battery and heats it). Therefore choose the codec by your audience's hardware share, measured from player telemetry, and use capability detection (MediaCapabilities in the browser, device profile on TV apps) to pick the rendition per device. Fall back to H.264 when unsure; a failed or stuttering playback is worse than 30 percent more bytes.
Live or on-demand. For live and low latency, encoder speed and a few frames of lookahead set delay: H.264 hardware encoders handle many streams per GPU; AV1 live is now possible on newer GPUs and SVT-AV1 but at higher cost. For real-time calls, VP8/VP9/H.264 and AV1 with scalable layers are used; a long GOP and B-frames add latency, so use short GOPs and no B-frames when latency under a second matters, and pay about 10 to 20 percent in bitrate.
Licence and ecosystem. H.264 has the simplest rights position; HEVC needs checking with pools (MPEG LA/Access Advance, Velos) for large distribution of devices or content; AV1 (AOMedia) and the newer VVC (H.266) sit at the two ends of the openness and efficiency curve. VVC gives about another 30 to 40 percent but has little device support, so it matters mostly in broadcast trials.
interview: Why can a newer codec save 30 to 50 percent bits, and where does that come from? || Larger and more flexible blocks (up to 64x64 or 128x128), more intra prediction modes, better motion vectors with more references, bigger and better transforms, stronger in-loop filters and entropy coding. Each adds a few percent. The cost is a much larger search space for the encoder, so encode time rises a lot while decoding stays cheaper.
interview: A product manager says "use AV1 everywhere to save bandwidth". How do you respond? || Compute savings against cost: bytes saved times views, minus extra encode compute and storage for an additional ladder. Check the device share with hardware AV1 decode and the battery impact. Roll it out per title popularity and per device capability, with H.264 fallback, and measure rebuffering and playback failures as guardrails.
interview: What are I, P and B frames and why does the GOP structure matter for streaming? || I frames are coded alone, P frames predict from earlier frames, B frames from earlier and later frames. Longer GOPs and more B-frames compress better but make seeking and stream switching depend on keyframes. For adaptive streaming, keyframes must align at segment boundaries (commonly 2 to 6 seconds) so the player can switch renditions cleanly.
interview: What is the difference between a codec and a container? || The codec compresses the video (H.264, AV1); the container (MP4, MKV, MPEG-TS, WebM) packages the compressed video, audio, subtitles and timing together. The same codec can be in several containers; compatibility problems often come from the container, profile or level rather than the codec name.
interview: Why can a 4K stream at the same bitrate look worse on a cheaper encoder? || Rate-control and mode-decision quality differ: hardware encoders and fast presets try fewer options, so at equal bits they leave more distortion. Measure with VMAF per bitrate, and pick a preset by the quality you need per bit.
@@+ hlsdash
tradeoffs: HLS or DASH. Choose HLS when you must reach Apple devices (Safari and iOS only play HLS natively in many contexts) and want the widest player and CDN support; since CMAF fragmented MP4 is now supported by both, one set of media segments can be described by both an HLS playlist and a DASH manifest. Choose DASH when you need its richer manifest features (multi-period ad insertion, flexible timelines, wide DRM support in Android and smart TV players) and your devices play it. You give up storage and complexity if you keep two packagings, so most teams package once in CMAF and write two small manifests. For the web, the player libraries (hls.js, Shaka, dash.js) hide most of the difference.
Segment length. Choose 6 seconds for classic video on demand: fewer requests, better CDN efficiency, better compression with long GOPs. Choose 2 seconds for faster quality switching and lower startup and live delay, which costs more requests (three times as many as 6 s), more manifest updates, and about 5 to 10 percent more bitrate overhead from shorter GOPs. Live latency in classic HLS is about three segments plus encoding, so 6 s segments give 18 to 30 s behind live; 2 s gives 6 to 10 s.
Low latency. Choose LL-HLS or low-latency DASH (CMAF chunked transfer, partial segments of 200 to 500 ms) to get 2 to 5 seconds latency for sports and auctions. You give up CDN cache friendliness (more requests, blocking playlist reloads, origin load) and simplicity, and you need CDN and origin support. Choose WebRTC (see quic, tcp) for sub-second interactivity, giving up easy CDN scaling: it needs media servers and costs far more per viewer. For most live events, 6 to 10 seconds with plain segments is the cheapest, and viewers do not notice unless they watch social media in parallel.
Ladder design. Use 5 to 8 renditions, from a low (for example 240p at 300 kbps) to 1080p at 4 to 6 Mbps or 4K at 12 to 16 Mbps for H.264, with steps of about 1.5 times. Per-title or per-scene encoding makes a cartoon need much fewer bits than a sports match; per-title ladders can save 20 to 30 percent of bytes. More renditions improve fit but multiply storage and encoding cost, and splits cache hits across more files.
DRM and ads. For protected content, use CMAF with common encryption (CENC/CBCS), so one encrypted set works with FairPlay, Widevine and PlayReady, with a licence server and key rotation. For ad insertion, choose server-side ad insertion (stitching ads into the manifest) to avoid blockers and get a consistent player experience, at the cost of CDN cache fragmentation per viewer and harder client-side measurement; choose client-side insertion when you need precise beacon reporting and interactivity (see pixels).
interview: Why does HTTP-based streaming scale better than a stateful protocol like RTMP or RTSP? || Segments are plain files served by any CDN or HTTP cache, so millions of viewers hit cached copies and the origin sees only a few requests. The server is stateless and the player decides bitrate. The cost is latency from segment length.
interview: Viewers complain about 30 seconds of delay on a live sports stream. What are your options? || Shorten segments to 2 s, use LL-HLS or LL-DASH with partial segments, reduce player buffer target, shorten encoder and packager delay, and check CDN settings like origin shield and manifest TTL. Each step trades CDN efficiency and rebuffer risk for delay, so set a target (for example under 8 s) and monitor rebuffer ratio.
interview: How would the player decide which rendition to play? || It estimates throughput from recent segment downloads, tracks the buffer level, and chooses the highest rendition that fits with a safety margin; buffer-based algorithms switch up only when the buffer is healthy and down quickly when it drains. Add device limits (screen size, decoder) and avoid too frequent switching, which viewers notice.
interview: What breaks if renditions have unaligned keyframes? || The player cannot switch at segment boundaries without a glitch or a decode error, because the new rendition's segment does not start with an IDR frame at the same timestamp. Force fixed GOP boundaries and the same segment duration across renditions.
interview: How do you reduce startup time? || Start with a low-to-medium rendition, use small first segments, keep manifests small and cached, preconnect and prefetch the manifest, use a CDN near users, and make sure the first segment starts with a keyframe. Measure time to first frame, and rebuffering in the first 30 seconds.
@@+ acr
tradeoffs: Audio or video fingerprint. Choose video (screen) fingerprinting, as on smart TVs, when the device can sample pixels of the actual display and you want to recognise what is on the screen regardless of source (cable box, game console, streaming app), including ad creative; it works in silence and with muted audio. Choose audio fingerprinting when only a microphone or an audio stream is available (phones, speakers) and the target is music, shows or live broadcasts; it is cheaper to compute but fails when the sound is muted or noisy. You give up, with video, CPU and privacy sensitivity (you are sampling the screen), and with audio, coverage of muted viewing and non-audio content. Many vendors do both on TVs and combine them.
On-device matching or server matching. Choose server matching (the TV sends compact fingerprints every second or few, the cloud matches against the index of live channels and on-demand content) when the reference index is large and changes often; it needs bandwidth of a few kilobytes per second per TV and a backend that handles millions of devices (for example 10 million TVs sending every 1 to 2 seconds is millions of lookups per second at peak). Choose on-device matching when privacy rules, bandwidth or offline use matter, with a small reference set pushed to the device; you give up flexibility, because the device has limited memory and the reference must be updated all the time.
Sampling rate and latency. Sampling every second gives fast recognition (within 3 to 10 seconds of a channel change) and fine ad-level attribution, but costs 10 times the traffic and CPU of sampling every 10 seconds. For measuring who saw an ad or a program, coarse sampling is often enough for audiences; for real-time ad swap or interactive overlays, you need seconds. Pick by the use case and the TV's CPU budget, and keep the processing light so the TV experience does not get slower.
Consent and regulation. ACR is viewing data, and in the US states and the EU it is treated as sensitive or personal data: users must be told and able to opt out, and several regulators and state attorneys general have acted on TV makers about it. Choose an opt-in flow with clear text, honour opt-out and deletion requests (see privacytech), hash or tokenise device identifiers, keep retention short, and separate raw fingerprints from identity data. You give up reach (opt-in rates are often well under 100 percent) for legal safety and trust. Do not assume that hashing makes data anonymous: a household-level viewing history is identifying by itself.
Accuracy and coverage. Matching quality depends on the reference library: you must ingest live feeds from hundreds of channels in each market with seconds of delay, plus on-demand content and ads. False matches happen on similar content (a rerun, the same ad in different cuts), and gaps happen when the reference is late. Measure precision against ground truth from panel homes or set-top logs, and keep reporting a confidence level.
interview: How does ACR recognise what is on screen with no metadata from the source? || The TV computes a compact fingerprint from sampled frames (for example, small grids of brightness and edges, hashed into robust codes), sends it to a service that looks it up in an index of fingerprints of known content built from reference feeds, and returns the content ID and time offset. Because the fingerprint is robust to compression and scaling, the match works regardless of the source.
interview: Why do fingerprints need to be robust, and what breaks them? || The same content passes through different encodings, resolutions, overlays (logos, tickers), and picture settings, so the fingerprint must not change much. Heavy cropping, picture-in-picture, game consoles overlay UI and personalised ad insertion can break the match. Use multiple fingerprint features and time-aligned voting over several samples.
interview: How would you scale a matching backend to 20 million TVs? || Partition the reference index by market and time window (live content only needs recent minutes), use locality-sensitive hashing or inverted indexes over hash codes (see lsh), keep the hot index in memory, batch requests, and shard by region. Aggregate the results in a stream (Kafka and Flink) into viewing events, and keep raw fingerprints only for a short time.
interview: What are the privacy risks, and what would you build in from the start? || Viewing history is sensitive, can reveal health, religion or politics, and links to households. Build consent and opt-out into the product, minimise and expire data, separate identity from events, support deletion requests by key, restrict internal access, audit use, and avoid sensitive categories in audience segments.
interview: How do you check that ACR audience data is correct? || Compare with a reference panel (homes with known viewing), check match rate and share against published ratings for popular shows, monitor drift by channel and device model, and look for missing reference content. Report error bounds, as vendors differ.
@@+ openrtb
tradeoffs: OpenRTB bidding or a direct deal. Choose open-auction RTB when you want scale and reach across many publishers with little negotiation: you pay per impression won, accept fraud and brand-safety risk, and compete on price. Choose a private marketplace (PMP) or programmatic guaranteed deal when a premium publisher offers fixed inventory, a floor price and a seat only for chosen buyers: fewer impressions, higher price (often 20 to 100 percent higher CPMs), but better quality and certain supply. You give up volume and price efficiency; you gain transparency and fewer bad impressions. Direct, non-RTB sales add certainty but need sales effort and slow changes.
First-price or second-price, and bid shading. Exchanges moved mostly to first-price auctions (2017 to 2019), so a bidder who bids its full value pays it and loses margin. Choose bid shading (a model predicting the minimum winning price and bidding just above it) to recover 10 to 30 percent of spend; it needs win-price feedback (the notice, or exchange-provided price signals) and a model per exchange. You give up some win rate, since an aggressive shading policy loses close auctions, and you take on a model to monitor. On the sell side, floors and unified pricing rules are the controls.
Latency budget. The exchange gives bidders about 100 ms total, including the network, so the bidder's own time should be 10 to 30 ms. Choose to bid on a subset of requests (filter by geo, size, publisher, quality score) instead of all of them, because an exchange can send hundreds of thousands of queries per second to a single bidder, and 90 percent are unprofitable. Pre-compute, cache user and campaign data in memory (see cachelayer), and drop slow requests. Timeouts cost you the auction and may reduce your future traffic from the exchange (throttling by the exchange). You give up some bids to keep the p99 within the limit.
Server-side or client-side header bidding. Header bidding (publisher calls many exchanges from the page) increased competition but added page latency and many duplicate requests. Choose client-side wrappers (Prebid.js) for simplicity and cookie syncing on web; choose server-side (Prebid Server, Amazon TAM) to cut page weight and latency, and for mobile and CTV apps, giving up some match rate because user IDs are harder to sync (see cookies, identity). Supply chain transparency (ads.txt, sellers.json, SupplyChain object) is how you check who is allowed to sell.
Identity and privacy signals. The bid request carries device ID, IP, user agent, geo and consent strings (TCF in the EU, GPP for US states). Choose to respect them at the bidder: drop or coarsen the request when consent is absent. Contextual targeting, first-party IDs and clean-room matching are alternatives as third-party cookies fade. You give up targeting precision and measurable conversions; you gain compliance and durable supply.
interview: What is in an OpenRTB bid request, and what would you use to decide a bid? || The request has the impression (size, format, floor), the site or app, the device (type, OS, IP, geo, ID), the user (IDs, segments if any), regulations and consent, and supply-chain data. I would combine publisher quality, the placement, user or context signals, campaign goals and pacing to estimate the value of the impression (for example, expected click or conversion probability times its value), then bid at or below that, shaded in first-price auctions.
interview: Why is first-price bidding harder than second-price? || In second-price, bidding your true value is optimal, so no strategy is needed. In first-price you pay what you bid, so you must estimate the distribution of winning prices and bid just above the clearing price to keep surplus. That needs historical win data per exchange, publisher and context, and constant retraining.
interview: Your bidder receives 500,000 requests per second but you only win 0.5 percent. What do you do? || Filter early: reject requests that no campaign can use, using cheap tests first (geo, size, format, blocklists), then a score model on the remaining ones. Ask exchanges for traffic shaping (QPS limits by segment). Place bidders near exchange data centres to cut round trips, and track cost per request, since compute spent on losing queries is wasted.
interview: How do you handle pacing and budget in a distributed bidder? || Each bidder instance sees a part of traffic, so budget is tracked in a shared fast store with periodic synchronisation, or each instance gets a slice and rebalances every few seconds. A pacing controller adjusts bid multipliers to spend the budget evenly over time (see pacing). Small overshoot is accepted by design to avoid central locks on the hot path.
interview: How do you detect and reduce ad fraud and low-quality supply? || Use supply chain checks (ads.txt, sellers.json), IVT vendors, anomaly detection on click and conversion rates, bot-like device and IP patterns, and block or lower bids for suspect sources. Measure outcomes (conversions, viewability) by source, not only click-through, because fraud often has good-looking clicks.
@@+ pixels
tradeoffs: Client-side pixel or server-side events. Choose the classic client-side pixel (an image or script request from the browser) when you want the simplest setup and the browser context for free: IP, user agent, cookies and referrer arrive in the request. Choose server-side tracking (Conversions API, server-to-server postbacks) when ad blockers, browser privacy limits (Safari ITP capping cookies at 24 hours to 7 days) and data loss are eating your measurement: often 10 to 40 percent of browser events are lost. You give up, with server-side, the automatic browser context (you must forward IDs and consent yourself) and take on engineering work; you give up, with client-side, completeness and control over data leaving the page. Many teams send both and deduplicate with an event ID.
Image pixel or JavaScript tag. A 1x1 image request is tiny (a few hundred bytes, no code), loads even without script permissions, and is safe to put in emails and ads; but it carries only what is in the URL. A script tag can read page data, set up events and fire many pixels, but adds load time (often 50 to 300 ms per vendor) and security exposure (a third-party script runs with page privileges). Choose images for impression and open tracking; choose a tag manager with strict governance for sites, and cap the number of vendors.
Fire from the browser or from a fanout service. Firing 10 vendor pixels per ad view from the device slows the page and drains battery; firing from a server-side fanout (one request to you, which then calls vendors in parallel) lowers client cost and gives you retries and logs, but you add a service that must handle peak traffic (millions of requests per second in ad tech), and vendors see your server's IP, not the user's, unless you pass it along. Use queues and short timeouts so one slow vendor does not block others, and drop or retry according to the value of the event.
Counting accuracy. Pixel counts are never exact: ad blockers, bots, prefetching, duplicates from retries, and slow pages that the user leaves before the pixel fires. Choose to define events with deduplication keys and use a tolerance (for example, expect 2 to 5 percent discrepancy between your logs and a partner's, and investigate above 10 percent). Reconcile impression counts with exchange or ad server reports regularly. You give up exactness; you gain stable metrics if the definitions are fixed.
Identity and consent. A pixel fire links an event to a cookie, device ID or hashed email. Choose first-party cookies and server-set IDs for durability, honour consent strings and opt-outs before firing, and avoid putting plain personal data in URLs, because URLs land in logs, caches and referrer headers. Under privacy laws (GDPR, CCPA/CPRA, and others) the event itself can be personal data; a deletion request must be able to find it by key.
interview: What happens, technically, when a tracking pixel fires? || The browser makes an HTTP GET to the tracker's domain for a tiny image or script, sending cookies, IP, user agent and referrer; the server logs the request with query parameters (campaign, event type, IDs), and responds quickly with a 1x1 GIF or 204 and no body. The log is then processed into counts and joined to audiences or conversions.
interview: How would you design a pixel collection service for 1 million events per second? || Keep the request path minimal: terminate at a CDN or edge, parse the URL, write to a log or message queue (Kafka) asynchronously, and respond immediately with an empty image. Scale stateless collectors horizontally, use batching and compression, apply backpressure with bounded queues, and do enrichment, deduplication and fanout downstream. Never call a database synchronously.
interview: Your conversion counts differ 15 percent from the ad platform. How do you debug? || Compare definitions (attribution window, click versus view, time zone, event dedup), then look at loss points: blocked requests, consent filtering, bot filtering, late events, retries and double fires. Do a sample-level reconciliation by event ID. Often the gap is definitional, not a bug.
interview: What are the privacy risks of pixels and how do you limit them? || Third-party pixels let a vendor observe browsing across sites and link it to identity. Limit with consent gating, no personal data in URLs, short retention, vendor review, content security policy to restrict domains, and server-side collection with minimised fields. Support deletion by identifier.
interview: Why are pixel redirects (pixel chains) a problem? || A pixel can redirect to another vendor's pixel, which redirects again; each hop adds latency, failure chances, and uncontrolled data sharing. Set a limit on hops, use server-side fanout, and log which vendors were called.
