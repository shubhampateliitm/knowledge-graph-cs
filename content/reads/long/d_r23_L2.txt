@@ zonemaps
value: A zone map stores two numbers, the smallest and the largest value of a column, for each block of data. When a query asks for rows where the column equals 42, or lies between 10 and 20, the engine reads the two numbers first. If the range of a block cannot contain a matching row, the whole block is skipped without being read. The extra metadata is tiny: for a 128 MB block it is a few dozen bytes per column. The saving can be the whole scan, because skipping a block avoids the disk or network read, the decompression and the decoding.
This matters most for analytical tables that are huge and are filtered by a narrow condition: one day out of three years, one campaign out of ten thousand, one device group out of millions. Parquet and ORC files carry min/max statistics per row group and per page. Delta Lake and Iceberg keep per-file min/max values in their table metadata, so an engine can prune files before opening any of them. Snowflake keeps the same information for each micro-partition. PostgreSQL calls its version a BRIN index (block range index). Oracle and Netezza use the name "zone map". The idea is the same everywhere, and it is the main reason a lakehouse can answer selective queries on object storage without a classic index.
For the layer above (lakehouse tables, OLAP engines, and the clustering techniques that make skipping effective), zone maps give a cheap, always-on filter that costs almost nothing to maintain. The layer below is indexing (L3). A zone map is the coarsest possible index: instead of pointing from each key to its row, it describes a whole block by its range. That makes it a sparse index. It cannot find a row, but it can prove that a block does not contain one. That proof is all a scan needs.
terms: Zone map — a small record of statistics (at least minimum, maximum and null count) for one block of rows; also called min/max statistics or a small materialized aggregate.
Block, row group, file — the unit that gets one zone map entry; it can be a page of about 1 MB, a Parquet row group of about 128 MB, or a whole file.
Pruning (data skipping) — deciding from statistics alone that a block cannot contain matching rows, and not reading it.
Predicate — the filter condition in a query, such as event_date = '2026-10-25' or amount > 100.
Selectivity — the fraction of rows that match a predicate; a predicate that matches 0.1% of rows is highly selective.
Clustering — how well the physical order of rows follows the values of a column; well-clustered data gives narrow ranges per block.
Sparse index — an index that has one entry per block, not one entry per row.
Null count — the number of null values in a block; it lets the engine skip blocks for IS NULL or IS NOT NULL.
history: The idea is older than the name. In 1998, Guido Moerkotte published "Small Materialized Aggregates: A Light Weight Index Structure for Data Warehousing" at VLDB. He proposed storing small aggregates (min, max, sum, count) for each bucket of a table, and showed that for data that arrives roughly in order, such as sales by date, they replace a full index at a tiny fraction of the cost. A data warehouse then had disks that were slow and tables much larger than memory, so avoiding a read was worth a lot.
Commercial warehouses turned this into a product feature. Netezza (early 2000s) called it a zone map and built it automatically for every table, with no index to create or tune. Oracle Exadata added "storage indexes" that keep min/max per 1 MB region on the storage servers. Oracle 12.1.0.2 added explicit zone maps, and PostgreSQL 9.5 (2016) added BRIN indexes, which store a min/max summary per range of table pages (128 pages by default).
The big-data formats made it universal. ORC (2013) stores statistics per file, per stripe and per group of 10,000 rows. Parquet (2013) stores statistics per column chunk in each row group. Parquet 1.11 (2018 to 2019) added a page index (column index and offset index), so that a reader can skip pages inside a row group as well. When Delta Lake (2018 to 2019) and Iceberg (2018) built table formats on top of immutable files, they copied each file's min/max values into the table metadata. That step moved pruning from "open each file and look at its footer" to "look at one metadata file, then open only the files that can match". Snowflake (2014) did the same from the start with micro-partitions.
how: The mechanism has three parts: collect, store and test.
Collect. While a writer builds a block, it tracks for every column the smallest value, the largest value, and the number of nulls. This costs one comparison per value, so it adds almost nothing to the write. Strings and binary values are compared in byte order, and long values are cut short (Iceberg keeps 16 bytes by default, Delta cuts long strings as well). Truncation must stay safe. A truncated minimum is still a valid lower bound because a prefix sorts before the full string. A truncated maximum must be rounded up, for example by incrementing its last byte, otherwise the stored bound could be smaller than a real value and the engine would skip a block it should read.
Store. The statistics live at several levels. A Parquet file keeps them in its footer, for each column chunk of each row group, and optionally per page. A table format keeps them one level up, per file, in the metadata. In Iceberg each manifest entry has lower and upper bounds per column ID, and each manifest also keeps a summary of partition values, so the planner can prune whole manifests before reading their entries. In Delta Lake the add action in the transaction log carries a stats field with min, max, null count and row count for the first 32 columns by default (set by delta.dataSkippingNumIndexedCols; the choice limits the size of the log). Putting statistics in the table metadata is what makes planning cheap: the engine reads a few metadata files, not thousands of footers from object storage.
Test. For every predicate the engine asks one question for every block: can any row in this range satisfy the condition? For col = v the block is skipped when v < min or v > max. For col > v it is skipped when max ≤ v. For col BETWEEN a AND b it is skipped when max < a or min > b. For col IN (v1, v2, v3) it is skipped when none of the values is in [min, max]. For col LIKE 'abc%' the engine turns the prefix into the range ['abc', 'abd'). For IS NULL it is skipped when the null count is 0. For AND the engine skips the block if any side lets it skip; for OR it skips only if both sides do. A predicate on a function of the column, such as lower(name) = 'x', cannot be tested against the raw min and max, which is a common reason why skipping silently stops working.
The test is conservative. A zone map can prove that a block has no match, but it can never prove that a block has a match, so surviving blocks are still read and filtered row by row. The result is never wrong. It is only sometimes inefficient.
How well this works depends on one thing: how narrow the ranges are. This is where the layers below matter. Indexing (L3) gives the idea of a sparse index, and the key fact of sparse indexes is that they depend on the physical order of the data. If rows arrive sorted by event time, each file covers a short time interval and ranges barely overlap, so a query for one hour reads one or two files. If rows are in random order for a column, every file's range is nearly the whole domain, and the zone map prunes nothing. Zone maps do not create order. They exploit order that already exists, from append-time order of time-series data, from partitioning, or from sorting and clustering done on purpose (the neighbouring concept, Clustering and Z-ordering). That is why zone maps and clustering are always discussed together.
Finally, zone maps have a sibling for the case they cannot handle. Min/max cannot help with an equality lookup on a high-cardinality column that is not sorted, such as a random user ID, because every block has a wide range. For that case formats add Bloom filters (a probabilistic membership test per block), which can answer "this value is not in this block" even when the value lies between min and max.

example: Take a table of ad impressions with 3,000 files, each about 256 MB, covering 90 days. Each day has about 33 files. The table is queried with WHERE event_date = '2026-10-25' AND campaign_id = 7731.
Case 1: data is appended in time order. Each file holds rows from one day, or at most from two neighbouring days. The min/max for event_date in each file is [d, d] or [d, d+1]. For the filter date, the planner finds the roughly 33 to 66 files whose range contains that day and skips about 2,950 files. The planner read three metadata files and never opened 98% of the data. If scanning a file costs 0.5 seconds of cluster time, the scan drops from about 1,500 seconds of work to about 25.
Now the second condition, campaign_id = 7731. Inside the 33 to 66 surviving files, campaign IDs come in arrival order, so every file contains rows for all 10,000 campaigns. The range of campaign_id in each file is roughly [1, 10000]. The zone map prunes nothing here, and the engine reads all of the surviving files. This is the typical picture: zone maps give a huge win on the column that matches the write order and no win on the others.
Case 2: the same data but the pipeline writes files in random order by hash of user ID, for example after a wide shuffle. Now each file contains rows from all 90 days. Every file has event_date range [day 1, day 90]. The filter for one day cannot exclude any file, and all 3,000 files are read. The data is identical, the query is identical, and the cost is 60 times higher.
Case 3: you cluster the table by (campaign_id) inside each day. Now a file for day d holds a contiguous campaign_id range, such as [7000, 7800]. The filter for campaign 7731 on day d keeps 1 of the 33 files for that day. The total read falls from 33 files to 1. The cost of this one-time (and ongoing) reorganisation is a rewrite of the data, which is the subject of the clustering concept.
intuition: Labels on archive boxes: a box marked "invoices January to March" is never opened when you are looking for a June invoice.
The idea is natural because most queries ask a narrow question of a large collection, and a cheap summary can often prove that a part of the collection is irrelevant. To prove that something is absent, you need only a bound, not the data itself. Two numbers per block are a bound. It is also natural that the saving depends on how the boxes were filled. If someone put invoices into boxes in random order, every label would say "January to December" and the labels would be useless. The labels are only as good as the filing, and filing is something you control when you write the data.
mistakes: People often think zone maps are an index that finds rows. In fact they only rule blocks out. A block that survives may still contain no matching row, so the engine must read it and filter again. They are a filter on blocks, never a lookup of rows.
People often think that if statistics exist, skipping happens. In fact it happens only when the ranges are narrow. A column filled in random order has a range of nearly the whole domain in every file, so a table can have perfect statistics and still be scanned fully. Check the number of files read, not the existence of statistics.
People often think a Delta or Iceberg table can skip on any column. In fact statistics are collected only for some columns (the first 32 in Delta by default; Iceberg can be set per column), and long strings are truncated. A filter on a column with no statistics, or a filter that wraps the column in a function or a cast (for example cast(ts as date) = ...), cannot be pruned in the usual way.
People often think a few extreme values do no harm. In fact one outlier in a file stretches its range. If a "year" column normally holds 2026 but a bad record has 1970, every file that contains such a record now has the range [1970, 2026] and is read for every year filter. Min and max are not robust statistics, so clean outliers at ingestion.
friction: The first limit is dependence on data order. Zone maps help only if the physical layout matches the query filter. A table queried by five different columns can be well clustered for one or two of them at most. Data that arrives in the order of events (time) is the lucky case; keys such as user ID or device ID are almost never in arrival order. For those columns you need clustering, partitioning, or Bloom filters.
The second limit is the cost of keeping statistics. Statistics for hundreds of columns across millions of files make the table metadata large, and planning has to read it all. This is why Delta limits statistics to the first 32 columns by default, and why Iceberg lets you turn metrics off or truncate them for wide, rarely filtered columns. Table formats also need maintenance, because manifests with many small files make planning slow even when most files are skipped.
practice: Look at the number of files or bytes scanned, not at the query time alone. In Spark and Databricks the query profile shows files read versus files pruned. In Iceberg the scan planning metrics report skipped data files and manifests. If the pruned fraction is low for a filter that you expect to be selective, the layout is the problem, not the engine.
Put the column that most queries filter on first in the physical order. For event data this is usually the event date or an ingestion-time partition. Write files so that each file covers a narrow slice of that column: avoid wide random shuffles right before the write, or follow them with a sort. For several filter columns, use sort orders, Z-ordering or liquid clustering (see the clustering concept), and then check pruning again.
Make sure statistics exist for the columns you filter on. In Delta, move filtered columns into the first 32 columns of the schema, or set dataSkippingNumIndexedCols, and recompute statistics after changing it, because changing the property does not rewrite old statistics. In Iceberg, check write.metadata.metrics settings for wide tables. Keep filters sargable: compare the raw column to a constant, and use ranges (event_date >= '2026-10-25' AND event_date < '2026-10-26') in place of functions on the column.
Use Bloom filters for equality lookups on high-cardinality columns such as device IDs, and keep zone maps for ranges and for sorted or clustered columns. Keep file sizes healthy (256 MB to 1 GB for large tables): too many tiny files make the metadata large, and too few giant files make each range wide.
tradeoffs: Zone maps or an exact index. Choose zone maps when scans are large, the data is append-heavy and ordered or clustered on the filter column, and you can accept reading some extra blocks. Choose a B-tree or hash index when you need to find a few rows among billions with low latency (an OLTP lookup, a primary key), and you can pay for the index on every write and in memory or disk. With zone maps you give up exact row lookup; with indexes you give up cheap writes and simple maintenance.
Fine or coarse blocks. Choose finer granularity (page level, or small files of 64 to 128 MB) when selective queries dominate, because narrower blocks give narrower ranges and finer skipping. Choose coarse granularity (256 MB to 1 GB files) when the table is large and the metadata cost matters, since the number of statistics entries grows with the number of blocks. The usual middle is row-group or file-level statistics with a page index inside the file. You give up either pruning precision or metadata size.
Statistics on more columns or fewer. Choose to collect statistics on every column you filter or join on, and on nothing else; wide string and nested columns are poor candidates. Collecting all columns raises the write cost and the metadata size. Collecting too few means silently full scans. The Delta default of 32 columns is a guess, not a rule.
Zone maps, partitions or clustering. Choose partitioning when the filter column has low cardinality (dozens to a few thousand values), queries almost always filter by it, and you want to drop or move whole partitions. Choose clustering with zone maps for higher cardinality or for several columns, where partitioning would create many small files. Partitions give exact pruning and easy deletion but cause small files when over-used; clustering is flexible but needs periodic rewriting.
interview: Why can a table have correct min/max statistics on every column and still be scanned in full? || Min/max skipping works only when the ranges of different blocks are narrow and mostly disjoint. If rows are in random order for that column, every block's range is almost the whole domain, so no block can be excluded. The fix is layout (sorting, clustering, partitioning), not more statistics.
How does a zone map decide to skip a block for WHERE x BETWEEN 10 AND 20, and what happens with OR? || The block is skipped if max < 10 or min > 20, because its range does not intersect [10, 20]. For an OR of two conditions the block is skipped only if both conditions allow a skip; for AND it is skipped if either does. The test is conservative, so surviving blocks are still filtered row by row.
How would you make a query on user_id = 'abc' fast in a lakehouse table that is clustered by event_date? || Min/max on user_id is useless because each file contains many users. Options: add a Bloom filter on user_id so files without that value are skipped, cluster on user_id (possibly with date) so its ranges become narrow, or keep a separate lookup table. Pick by how often this query runs and how much extra layout and write cost you accept.
A string column has a truncated maximum value in the statistics. Why must the truncated value be rounded up? || The stored maximum must be greater than or equal to every real value. A plain prefix of the real maximum is smaller than it, so a query for the real maximum value could be wrongly skipped. Rounding up the last byte gives a valid upper bound, at the price of a slightly looser range.
Your pruning ratio dropped from 95% to 20% after a pipeline change. What do you check? || First the write path: a new shuffle, a changed partitioning, or a removed sort will widen file ranges. Then outliers or bad values that stretch ranges, new data arriving out of order (late events), a schema change that moved the column outside the indexed columns, and compaction that merged files with different ranges. Compare the min/max ranges of files before and after.
quiz: What two values does a zone map store for each block, and what extra value helps with IS NULL? || The minimum and the maximum of each column in the block; the null count lets the engine skip blocks for IS NULL or IS NOT NULL.
Why is a zone map useless on a column whose values are in random order across files? || Every file then contains values from the whole domain, so each file's [min, max] range overlaps the filter and no file can be proved irrelevant.
A table has 2,000 files, one day of data per 20 files, and is written in date order. A query filters on one day. Roughly how many files remain after pruning? || About 20 to 40 (the files whose date range contains the day, including a neighbouring day at boundaries), so about 98% of files are skipped.
Which statement is true: a surviving block definitely contains a matching row, or it may contain one? || It may contain one. Zone maps can only prove that a block has no match; surviving blocks must still be read and filtered row by row.
When would you add a Bloom filter in addition to zone maps? || For equality lookups on a high-cardinality column that is not sorted, such as a device ID, where each block's min/max range is wide but each block contains only a small fraction of the values.

@@ tieredstorage
value: Tiered storage splits a system's data into a hot tier and a cold tier, and keeps one logical view over both. In Apache Kafka the hot tier is the local disk of each broker and the cold tier is object storage such as S3. Recent log segments stay on the broker disks. Older segments are copied to the object store and deleted locally. A consumer that asks for an old offset does not notice: the broker fetches the data from the cold tier and returns it through the same fetch API.
The problem it solves is the cost and weight of retention. Without tiering, keeping 30 days of a 50 MB/s topic set with 3 replicas needs about 390 TB of broker disk (computed in the example below), and every byte lives on a machine that must be replaced, rebalanced and recovered. Brokers end up sized by disk, not by CPU or network, and adding disk means adding whole brokers. With tiering, the brokers keep only the last day or so, and the long tail sits in object storage at a fraction of the price per gigabyte, with its durability handled by the object store.
For the layer above (the distributed commit log, and analytics stores such as Pinot, ClickHouse and Elasticsearch), tiered storage makes long retention cheap and makes brokers small and fast to recover. It stands on two concepts below it. Separating storage and compute (L2) provides the pattern: the data lives in a shared, durable service that is independent of any one server, so servers become nearly stateless caches of the recent past. The memory hierarchy (L3) provides the reason it works: data access has strong locality in time. Most reads are of the newest data, so the newest data deserves the fast, expensive medium, and the long tail can sit on a slow, cheap one.
terms: Hot tier — storage that is fast and expensive per gigabyte, here the local disks of the brokers, which also benefit from the operating system page cache.
Cold tier (remote tier) — storage that is slower and cheap per gigabyte, here an object store such as S3, GCS or Azure Blob.
Log segment — a file of the Kafka partition log, closed (rolled) when it reaches a size or age limit; 1 GiB by default. Only closed segments are tiered.
Local retention — how long a segment stays on the broker disk after it has been copied to the remote tier (local.retention.ms).
Total retention — how long the data is kept in all tiers together (retention.ms); the segment is deleted from the remote tier after this.
RemoteStorageManager (RSM) — the plugin interface that copies, reads and deletes segment files in the remote store; Kafka ships no production implementation.
RemoteLogMetadataManager (RLMM) — the component that tracks which segment lives where and in what state; by default it stores this in an internal Kafka topic.
Local log start offset — the first offset still on the broker disk; offsets below it, down to the log start offset, can be read only from the remote tier.
history: The idea is old: storage hierarchies (cache, disk, tape) are as old as computing, and databases have long moved cold partitions to cheaper disks. For message logs the pressure grew in the 2010s. Kafka became the central log of many companies, and teams wanted to keep weeks or months of events, to replay for new consumers and for recovery. Disk-attached brokers made that expensive and made cluster operations slow.
Apache Pulsar approached the problem from a different design. Its storage layer, Apache BookKeeper, keeps data in ledgers, and Pulsar offloaded old ledgers to S3 and other stores from 2018. Confluent shipped a proprietary tiered storage in Confluent Platform and Confluent Cloud around 2020, and Redpanda built tiering into its broker. Elasticsearch took a similar route for search: index lifecycle management moves indices through hot, warm, cold and frozen tiers, and searchable snapshots (introduced 2020 to 2021) let the cold and frozen tiers search data that lives in an object store.
In the Kafka project, KIP-405 ("Kafka Tiered Storage") was proposed in 2020 by engineers from Uber and Confluent, among others. The design took years because it touches the core of the broker: replication, the log start offset, the transaction index, leader changes and retention all had to be taught about a second tier. Tiered storage reached early access in Kafka 3.6 (October 2023), and was declared production-ready in Kafka 3.9 (November 2024). Later releases added the ability to disable tiering on a topic and to delay uploads.
how: Kafka's version has four parts: the roll-and-copy path, the retention path, the read path and the metadata.
Roll and copy. A partition log is a sequence of segment files. Only the leader of a partition tiers data. The active segment (being written) is never copied. When a segment is closed, and its last offset is below the last stable offset (so it contains no open transaction), it becomes eligible. A background component on the broker, the RemoteLogManager, picks it up and passes it to the RemoteStorageManager plugin. The plugin uploads the segment together with its offset index, time index, transaction index, producer snapshot and leader-epoch data. When the upload succeeds, the metadata for that segment moves to a "copy finished" state. By default the upload starts right away. A topic setting (remote.copy.lag.ms and remote.copy.lag.bytes, added later) can delay it, so that the newest data is not stored twice.
Retention. A tiered topic has two retention clocks. local.retention.ms (and local.retention.bytes) says how long the data stays on broker disk, and retention.ms (and retention.bytes) says how long it stays in total. A local segment is deleted only after it has been uploaded and is older than the local limit. Segments in the remote store are deleted when they pass the total limit, by the same RemoteLogManager. If local retention is not set, Kafka uses the total retention, so no data leaves the disk early. So the cluster has two start points: the log start offset (oldest data anywhere) and the local log start offset (oldest data on disk).
Read path. A fetch request for an offset at or above the local log start offset is served from local disk, as before, often from the page cache. If the offset is below it, the broker reads from the remote tier. It looks up which remote segment holds the offset (using the metadata), reads the needed index pieces (cached on local disk), and asks the plugin for the byte range of the segment from that position. These reads run on a separate thread pool, so a slow remote read does not block fetches from local data. The response is returned to the consumer with the same protocol. The cost is latency: the first byte from an object store takes tens of milliseconds, compared with sub-millisecond for the page cache.
Replication and recovery. Followers keep replicating only the local part of the log. A new or recovering follower starts from the leader's local log start offset, not from offset 0. This is the most important operational effect: a broker that holds a few hundred gigabytes instead of many terabytes can be added, replaced or rebalanced in minutes to hours. The remote tier is shared. It does not need to be copied when partitions move between brokers.
Metadata. The system must know which segments exist remotely, their offset ranges and their state (copy started, copy finished, delete started, delete finished). The RemoteLogMetadataManager keeps this. The default implementation writes the events to an internal topic with a replication factor, and every broker reads the topic to build a local view. Because the metadata is itself in Kafka, it gets ordering and replication from the commit log.
How the lower concepts contribute. Separating storage and compute gives the cold tier its role: the object store holds durable, shared data that no broker owns, so brokers do not need to be repopulated when they change, and storage can grow without adding machines. The memory hierarchy gives the placement policy: the tail of the log is read many times soon after writing (by live consumers, through the page cache), and old segments are read rarely and mostly in long sequential scans (backfills). That access pattern is what makes a two-tier design cost-effective. Sequential scans also suit object stores well, because a large ranged GET is efficient, whereas random small reads would be expensive.
The design has known limits that follow from the mechanism. Compacted topics (which keep the latest record per key) are not supported, because compaction rewrites old segments in place, which does not fit immutable remote files. Disabling tiering needs care: the remote data must be deleted or the copy turned off first. The plugin must be provided: Kafka defines the interface, and you use an implementation for S3, GCS, Azure or HDFS from a vendor or the community. Other systems use the same pattern with different details: Elasticsearch searchable snapshots, ClickHouse storage policies with S3 disks and TTL-based moves, Pinot tiers, and Pulsar offload.

example: Take a cluster that ingests 50 MB/s in total, with replication factor 3 and 30 days of retention.
Without tiering: 50 MB/s × 86,400 s = 4.32 TB per day. Over 30 days that is 129.6 TB of unique data. With 3 replicas, brokers must hold 389 TB, and you also need free space (say 30%), so about 500 TB of provisioned disk. With 4 TB disks per broker, you need roughly 125 brokers just for storage, even if CPU and network would be satisfied by 12.
With tiering: local retention of 1 day. Brokers hold 4.32 TB × 3 replicas = 13 TB, plus 30% free: about 17 TB. That fits on a handful of brokers sized for throughput. The object store holds one copy of 129.6 TB (the store handles its own durability). At rough public list prices, block storage costs about $0.08 per GB-month and standard object storage about $0.023, so 389 TB of block storage is around $31,000 per month, against about $3,000 for 130 TB of object storage plus a small amount for 13 TB of local disk. Prices vary by region and change, but the ratio of roughly 8 to 10 is what matters. Request charges are small here: with 1 GiB segments, the cluster uploads about 4,300 segments per day, a few cents of PUT cost.
Recovery. A broker fails and its replacement must copy that broker's partitions. Without tiering (125 brokers) each broker holds about 3.1 TB. With a replication throttle of 100 MB/s, copying it takes 3,100,000 MB / 100 = 31,000 s, about 8.6 hours. With tiering, about 12 brokers hold 13 TB of local data, so each holds about 1.1 TB and the copy takes about 11,000 s, 3 hours. Moving to more, smaller brokers (for example 40 brokers with 330 GB each) brings it under 1 hour, which tiering makes affordable because disk no longer sets the broker count.
intuition: Keep this month's files on your desk and older ones in the basement archive, with an index card that says which box holds which dates.
The design is natural because log access is very uneven. Producers write only at the end, live consumers read only near the end, and the older part is read rarely and in order. A log is also immutable: closed segments never change, so copying a segment to a second place is simple and safe, and no cache invalidation is needed. Immutable, sequential, cold data is the best case for object storage. The only extra thing the system needs is an index of where each segment lives, and that index is small.
mistakes: People often think tiered storage makes Kafka's old data as fast as new data. In fact reads of tiered data have the latency profile of the object store (tens of milliseconds to first byte) and their throughput depends on the plugin, the network and the thread pool. It is built for backfills and replays, not for low-latency random reads.
People often think tiering replaces replication. In fact the active segment and recent data are still replicated across brokers, because a segment is uploaded only after it is closed. The object store makes the old data durable, but the newest data is still protected only by broker replicas.
People often think tiering is the same as moving to a diskless or object-storage-only Kafka. In fact brokers still write every record to local disk first and serve the tail from it. Tiering lowers the cost of retention and speeds recovery, but it does not remove the broker disk from the write path, and it does not reduce cross-zone replication traffic for new data.
People often think any topic can be tiered. In fact compacted topics are not supported, and the feature needs a remote storage plugin that you must choose and operate; Kafka itself ships only a test implementation.
friction: Remote reads are slower and less predictable than local reads. Throughput per partition depends on how many segment ranges the broker fetches in parallel, and a burst of backfill consumers can compete with live traffic for network and for the remote-read thread pool. Cache sizes for indexes and the choice of segment size (very large segments mean large remote reads; very small segments mean many requests and many metadata entries) need tuning.
Operations get a new failure mode: a slow or unavailable object store does not affect writes, but it does affect old reads, retention (disk fills if uploads stall and local retention cannot be applied) and the time to remove data. Disk-full alarms need to cover "upload lag", the amount of data waiting to be copied. Security and compliance questions arise too, since the data now sits in a bucket with its own access rules, encryption and deletion guarantees.
practice: Turn tiering on when disk, not CPU or network, sets your broker count, when you need retention above a few days, or when broker recovery and rebalancing take too long. Start with a pilot topic, a tested plugin for your cloud, and monitoring of copy lag and remote fetch latency.
Choose local retention to cover the reads that must be fast: usually the longest lag you expect from a live consumer plus a safety margin (often 1 to 3 days). Choose total retention from business needs, such as replay or audit windows. Keep the page cache in mind. Local retention larger than the memory available for cache does not make old data fast, it only keeps disks bigger.
Keep segment size sensible (the 1 GiB default is a good starting point). Many tiny segments slow the metadata path, while huge segments delay the first upload and increase the amount of data that exists only on local disk. Use the delayed-upload settings if the double storage of the newest data matters.
tradeoffs: Tiering or just more disk. Choose tiering when retention is long compared with the hot window (for example 30 days kept but 1 day read often) and the cost of broker disk is a large part of the bill; the saving is the ratio of disk to object-store price, often 5 to 10 times on the cold part. Choose plain disk when retention is short (under 2 to 3 days), when all of the data is read often, or when the operational cost of a plugin and a bucket is higher than the disk saving. You give up simplicity in return for lower storage cost.
Tiering or exporting to a lakehouse. Choose tiered storage when consumers need to read old data as a Kafka topic, with offsets, ordering and the same client code. Choose a connector that writes the topic to Iceberg or Delta tables when consumers are analytical, need columnar scans and SQL, and do not need Kafka semantics. Many teams do both; tiering keeps the log replayable, and the lakehouse serves analytics. Tiering gives you replay but no query engine; the lakehouse gives queries but no exact-offset replay.
Short or long local retention. Choose a short local window (hours to one day) to make brokers small and recovery fast. Choose a longer local window when late consumers regularly read several days back and need low latency, or when the object store's latency or request costs hurt. A longer window costs disk; a shorter one costs remote reads.
interview: Walk through what happens when a consumer reads offset 400 from a topic whose local log starts at offset 900. || The fetch hits the leader. The leader sees that the offset is below the local log start offset, looks up the remote segment containing it using the remote log metadata, fetches index data (cached) and then a ranged read of the segment from the remote store through the RSM plugin, on a separate thread pool, and returns the records in the normal fetch response. Latency is tens of milliseconds for the first bytes.
Why does tiering make broker recovery faster? || A new or recovering follower replicates only the leader's local part of the log, since the rest is already in the shared remote tier. With 1 day of local data instead of 30, the data per broker falls by about 30 times for the same broker count, and the time with reduced redundancy falls with it.
Why are compacted topics not supported in the first tiered storage versions? || Log compaction rewrites old segments in place to drop superseded keys, but remote segments are immutable files with metadata that points to exact offset ranges. Supporting compaction would need rewriting remote objects and updating their metadata consistently, which the first design left out.
What can go wrong if uploads to the object store fail for hours? || Segments cannot be deleted locally, because deletion requires a completed upload. Disk usage grows beyond the intended local retention and brokers can fill up. You need alerts on copy lag and enough free disk to ride out an object store outage, and perhaps a limit on how far uploads can lag.
How do you decide local retention for a topic? || Cover the slowest normal consumer lag plus a margin so that routine reads hit the local disk and page cache; use total retention for the business replay window. Check how often reads fall below the local log start offset and how long they take. If remote reads are frequent, extend local retention or fix the consumers.
quiz: What does Kafka copy to the remote tier, and when? || Closed (rolled) log segments with their indexes, once they are eligible (the last offset is below the last stable offset); the active segment is never copied.
Why can a replacement broker be ready much faster with tiered storage? || It only needs to replicate the local part of each partition log from the leader, not the whole history, because older segments are already in the shared object store.
A cluster ingests 20 MB/s with RF 3. How much broker disk is needed for 1 day of local retention? || 20 MB/s × 86,400 s = 1.73 TB per day, times 3 replicas = about 5.2 TB (plus free space), against about 155 TB for 30 days without tiering.
What are the two retention settings of a tiered topic and how do they differ? || local.retention.ms (and bytes) is how long data stays on the broker disk after upload; retention.ms (and bytes) is the total time the data is kept in all tiers, after which it is deleted from the remote store.
When is tiered storage a poor choice? || When retention is short, when most reads touch old data with low-latency needs, when you need compacted topics, or when the extra plugin and bucket operations cost more than the disk they save.

@@ zorder
value: Clustering means writing rows to files in an order that puts similar rows together. Z-ordering is a way to do this for several columns at once. If you sort a table by one column, a filter on that column reads very few files, but a filter on any other column reads all of them. Z-ordering sorts by an interleaved key built from several columns, so that rows with close values in any of those columns tend to land in the same file. Then filters on each of the columns can skip a good share of the files.
Why this matters for the layer above comes from zone maps (L2). A zone map keeps the minimum and maximum of each column for each file, and a query skips a file whose range cannot match. That only works when the ranges are narrow, and the ranges are narrow only when the data was written in a helpful order. Clustering is the act of creating that order on purpose. It is what turns "statistics exist" into "most files are skipped". Lakehouse tables (Delta Lake, Iceberg, Hudi) depend on this, because they have no row-level index: layout plus statistics is their index.
Three concepts below it do the work. Zone maps supply the skipping that rewards a good layout. Sorting (L3) supplies the machinery: sample the key, split the rows into ranges, sort each range, and write the files in order. Binary representation (L3) supplies the trick: the interleaved key is made by shuffling the bits of the column values, and for signed numbers the bit pattern must first be adjusted (the sign bit of two's complement flipped) so that numeric order equals bit order. Newer approaches, such as Databricks liquid clustering, keep the same idea but make it incremental and let you change the columns later.
terms: Clustering — arranging rows physically so that rows with similar values in chosen columns are stored near each other.
Z-order (Morton order) — an order on multi-column keys made by interleaving the bits of the column values into one number and sorting by that number.
Space-filling curve — a path through a multi-dimensional grid that visits every cell once and keeps nearby cells mostly near each other along the path; Z-order and Hilbert are examples.
Hilbert curve — a space-filling curve with better locality than Z-order, because consecutive positions are always neighbours; it costs more to compute.
Data skipping — not reading a file because its min/max statistics prove that it cannot match the filter.
Liquid clustering — Databricks' replacement for partitioning and Z-ordering on Delta tables: clustering keys are table metadata, OPTIMIZE reclusters incrementally, and the keys can be changed later.
OPTIMIZE — the command that rewrites small or badly laid out files into well laid out files of the target size.
Partitioning — splitting a table into folders by the value of a column; it prunes exactly but creates many small files when the column has many values.
history: Guy Morton described the interleaved-bit order in 1966, in an IBM report on a geodetic database, as a way to order map data so that places near each other in two dimensions stay near in one dimension. David Hilbert had published his curve in 1891 as a mathematical curiosity; later work showed that it keeps locality better. In the 1980s and 1990s, database researchers (Orenstein and Merrett in 1984, and Bayer's UB-tree in 1996) used Z-order to index multi-dimensional data with an ordinary B-tree: map each point to its Z-value and store it as a key.
In data lakes, files are immutable and there is no B-tree, so the same idea moved to the file level. Databricks introduced OPTIMIZE ... ZORDER BY for Delta tables around 2018 to 2019 and open-sourced it in Delta Lake 2.0 (2022). Iceberg added a z-order sort option to its rewrite_data_files procedure, and Hudi added Z-order and Hilbert layouts in its clustering feature. Warehouses use related ideas: Snowflake clustering keys, BigQuery clustered tables, and Redshift's interleaved sort keys.
The weaknesses of Z-ordering showed up in practice. Each OPTIMIZE ZORDER rewrites a large part of the data. You must choose the columns up front, and changing them means rewriting. It works within partitions only. Databricks announced liquid clustering in 2023 to address these points, and it is generally available for Delta tables on Databricks Runtime 15.4 LTS and later. Open-source Delta Lake added it as a preview in 3.1 and removed the feature flag in 3.2. By 2026 Databricks recommends liquid clustering for new tables and does not allow it to be combined with partitioning or ZORDER on the same table.
how: Clustering has two jobs: choose the order, and write the files in that order. The two pieces are the order function and the rewrite.
The order function. With one column, the order is simply sorting. With two columns x and y, any single order has to favour one of them. A sort by (x, y) puts all rows with the same x together, but rows with the same y are scattered across the whole table. Z-order avoids this with a different key. Write the bits of x and y, and weave them: take the top bit of x, then the top bit of y, then the second bit of x, then the second bit of y, and so on. The result is one number, the Z-value. Sorting by it has this property: the first half of the order holds all rows with a small top bit of x, then within that the top bit of y splits again. At every scale, the table is cut alternately by x and by y, so every block of the order is a compact box in the (x, y) space, not a thin stripe.
Making the key. Column values are not always small unsigned integers. The engine first converts each column to an order-preserving unsigned integer. Signed integers need their sign bit flipped, because in two's complement a negative number has a leading 1 and would otherwise sort after the positive ones. Floats need a similar transformation. Strings and skewed numbers are handled by ranking: the engine samples the data, finds quantile boundaries, and replaces each value with its rank bucket. Delta's Z-order works roughly this way, which also keeps one skewed column from using up all the bits. Then the bits of all columns are interleaved.
The rewrite. The engine reads the files to be reorganised, computes the Z-value for each row, and does a range-partitioned sort: it samples Z-values to choose boundaries, shuffles rows into ranges that match the target file size (hundreds of MB), sorts each range, and writes the files. This is the distributed external sort from the layer below, and its cost is a full read, a shuffle and a full write of the data involved. After the rewrite, each new file covers a small box of the multi-dimensional space, so its min and max for each clustered column are narrower than before. The statistics were already being collected (zone maps); clustering has only made them useful. Then queries for x = a or y = b both skip many files.
How much skipping? Suppose a table has N files and is Z-ordered on k columns of similar importance. A filter on one equality value of one column keeps about N^(1 − 1/k) files. For k = 1 that is 1 file. For k = 2 it is about √N, so 100 of 10,000 files. For k = 4 it is N^0.75, about 1,000 of 10,000 files. A sort on one column gets 1 file for that column, and all N files for any other. So Z-order trades a perfect result on one column for good results on all of them, and the benefit shrinks as you add columns. This is why Databricks says effectiveness drops with each extra column, and why liquid clustering allows at most four keys.
Liquid clustering changes the process, not the idea. The clustering keys are stored as table metadata (CLUSTER BY (col1, col2)). OPTIMIZE then reclusters incrementally: it looks at the files and rewrites only the ones that need it, such as new small files or files that overlap too much, and leaves already well-clustered files alone. Changing the keys with ALTER TABLE ... CLUSTER BY does not rewrite the data at once. New writes and later OPTIMIZE runs use the new keys, and old files are reorganised gradually (OPTIMIZE ... FULL reclusters everything). With CLUSTER BY AUTO, Databricks chooses keys from the observed query workload and changes them only when the predicted saving is larger than the clustering cost. Compared with Hive-style partitioning, clustering does not create folders, so there is no small-file problem from too many partition values and no need to guess partition granularity.
Other formats offer similar tools. Iceberg: ALTER TABLE ... WRITE ORDERED BY sets a sort order for writers, and CALL system.rewrite_data_files with strategy 'sort' and sort_order 'zorder(a,b)' rewrites files. Hudi has clustering with linear, z-order or Hilbert layouts. Warehouses hide the process: Snowflake and BigQuery recluster in the background.

example: Take the 4 x 4 grid in the diagram, where each cell is a group of rows and each file holds four cells. Compute one Z-value by hand. For the cell x = 2 (binary 10), y = 1 (binary 01), weave the bits starting with x's top bit: x1 = 1, y1 = 0, x0 = 0, y0 = 1. This gives binary 1001, which is 9, as the grid shows at column x = 2, row y = 1. Another one: x = 5 (101), y = 3 (011) in an 8 x 8 grid gives the bits 1, 0, 0, 1, 1, 1, which is binary 100111 = 39.
Sort the 16 cells by Z-value and cut them into four files of four cells. File A holds Z 0 to 3, which is the 2 x 2 box x 0 to 1, y 0 to 1. File B holds Z 4 to 7, the box x 0 to 1, y 2 to 3. Each file is a compact square, so its min and max in both columns are narrow.
Now run two queries. WHERE x = 1: only files A and B have x ranges containing 1, so two of four files are read and half are skipped. WHERE y = 1: files A and C contain y = 1 in their ranges, so again half are skipped. Compare a plain sort by x then y: files hold x = 0, x = 1, x = 2 and x = 3 columns. The query x = 1 reads one file (75% skipped), but y = 1 appears in the range of every file, so nothing is skipped. So the two layouts give 75% and 0% on one hand, and 50% and 50% on the other.
Scale it up. A table of 10,000 files with an ad-event key (campaign_id, device_group). With a sort on campaign_id, a campaign query reads about 1 file and a device_group query reads all 10,000. After Z-ordering on both, each query reads about √10,000 = 100 files, which is 1% of the table. If the queries filter on one campaign, the sort wins by 100 times, but if both kinds of query are common, Z-order cuts the worst case from 10,000 files to 100.
What does it cost? Reorganising 10 TB with a cluster that shuffles 2 GB/s takes at least 10,000 GB / 2 GB/s = 5,000 s, about 1.4 hours, plus the write. If the table receives 100 GB of new data per day, a full re-run daily is wasteful. This is where incremental clustering helps: it rewrites mostly the new 100 GB and the few files that overlap with it, and leaves the rest, so the daily cost is closer to 100 GB than to 10 TB.
intuition: Shelving books so that ones close in both topic and year end up on the same shelf, with shelves cut in squares and not in long stripes.
The idea is natural once you see that a one-dimensional order can only be a good "neighbour" map in one direction. A line cannot keep a plane's neighbours close in every direction, but it can keep them close most of the time. Interleaving bits divides space the same way a map is divided into quadrants, then each quadrant into quadrants. Because it halves x and y in turn, every contiguous piece of the order is roughly a square box. A file is a contiguous piece, so its min/max box is small in every clustered column at once. You give up the perfect order in one column and gain an acceptable order in all.
mistakes: People often think that Z-ordering sorts the table by all the listed columns, so any filter on them is fast. In fact it improves skipping on each column only partly, and each extra column dilutes the benefit (about N^(1 − 1/k) files read for k columns). Put one or two of the most selective filter columns, or at most a few, in the key.
People often think clustering replaces statistics. In fact clustering only makes the ranges narrow; the skipping still depends on min/max statistics being collected for those columns. A clustering column outside the statistics columns (the first 32 columns by default in Delta) gets no benefit, and Databricks advises against clustering on columns with no collected statistics.
People often think clustering is a one-time job. In fact new data arrives unclustered, and the layout decays. Z-ordering must be re-run (and each run rewrites a lot), while liquid clustering reclusters incrementally on OPTIMIZE. Both need to be scheduled or automated.
People often think Z-ordering and partitioning do the same thing. In fact partitioning splits a table into folders with exact pruning by one or a few low-cardinality columns, and a partition column with many values leads to tiny files. Clustering handles high-cardinality columns and several columns, but it prunes by statistics (which can be loose), not by folder, and it gives no cheap way to delete a whole partition.
friction: The cost is rewrite work. Z-ordering a large table reads, shuffles and rewrites the data. Databricks notes that it is not idempotent, but is meant to be incremental, and the time of a run is not guaranteed to fall in later runs. That compute competes with production queries, writers can conflict with the rewrite in table formats with optimistic concurrency, and the rewritten files become new files that the old snapshots do not use until vacuuming removes the old ones. Storage use rises temporarily.
The benefit has limits. It fades with more columns, with high-cardinality text keys whose statistics are truncated, and with queries that use ranges on columns that are not in the key. Low-selectivity filters (those matching a large part of the data) read most files anyway. For small tables (a few GB), clustering adds a cost without any benefit, because the data is already few files.
Choosing the key is hard. The right columns come from the real workload, and workloads change. Wrong keys waste compute for a long time. Databricks' CLUSTER BY AUTO tries to solve this by choosing keys from query history, but it needs managed tables and predictive optimization, and it still pays rewrite costs when keys change. Skewed columns are also a problem; a column with one value covering 40% of rows cannot be clustered finely on its own.
practice: Start from the queries. Collect the WHERE clauses of the 20 most expensive queries and count how often each column appears with a selective filter. Pick the one to four columns that appear most (a date or timestamp, a customer or campaign ID, a device or region). Put them in CLUSTER BY on a new Delta table. For existing tables with partitions and ZORDER, use the migration route the platform offers instead of mixing the two methods.
Small and medium tables should not be partitioned at all. For very large tables (tens of TB) with a time-based retention rule, a date partition can still help with deletion. Keep file sizes in the hundreds of MB. After clustering, measure: compare files read and bytes scanned before and after for the target queries (in the Spark UI or the query profile). If a query still reads most files, check the statistics columns and the key order.
tradeoffs: Linear sort or Z-order. Choose a plain sort when one column dominates the workload (for example event time in 90% of queries), because it gives perfect skipping on that column and costs less. Choose Z-order or Hilbert when two to four columns are filtered about equally often and no single column should be sacrificed. You give up the best case on the main column to avoid the worst case on the others.
Partitioning or clustering. Choose partitioning when one low-cardinality column (dates, a few regions) appears in nearly every query, partitions stay larger than 1 GB, and you want to drop or move whole partitions cheaply. Choose clustering when keys have many values, you need more than one key, or the access pattern may change, because changing a partition column means rewriting the table. You give up exact folder-level pruning and cheap partition drops, and gain flexibility.
Liquid clustering or manual Z-order. Choose liquid clustering for new Databricks Delta tables: incremental clustering, changeable keys and fewer tuning decisions. Choose manual Z-order when you run open-source Delta without that feature, or when you must keep an existing pipeline stable. You give up engine independence if you rely on a vendor-specific feature.
Cluster on write or cluster later. Choose clustering at write time (a sort or repartition by range before writing) when ingestion is batch and you can afford the shuffle in the pipeline. Choose a background OPTIMIZE when ingestion is streaming and latency matters; the cost is that fresh data is unclustered until the job runs.

Z-order interleaves the bits, so each file covers a compact box in (x, y) space with narrow ranges in both columns. Zone maps can then skip files for a filter on either column.
Estimate how many files a Z-ordered table reads for a single-column equality filter, with N files and k clustered columns. || About N^(1 − 1/k). For k = 2 and N = 10,000 that is 100 files; for k = 4 it is about 1,000. This shows why more columns dilute the benefit.
You have 40 columns that analysts filter on. Which do you cluster on? || Not all. For the others rely on Bloom filters, on the engine's own caching, or on materialised summary tables.
Why can clustering fail to help even after OPTIMIZE? || Statistics may be missing for the clustering column, the filter may wrap the column in a function, the filter may be unselective, files may be too few or too large, new data may be arriving unclustered, or concurrent writes keep producing small files. How is liquid clustering different from Z-order plus partitioning, operationally? || The clustering keys are metadata and can be changed without rewriting the table at once. OPTIMIZE is incremental and rewrites only what needs it, there is no partition folder structure to over-split, and it cannot be mixed with partitioning or ZORDER on the same table.
quiz: What does a Z-value of a cell (x, y) consist of? || The bits of x and y interleaved (x's top bit, y's top bit, x's next bit, and so on), sorted as one number.
Why does Z-order often beat a plain sort when queries filter on different columns? || A plain sort only narrows the first column's ranges; Z-order narrows ranges in all key columns at once, at the price of weaker skipping on any single one.
A table has 10,000 files and is Z-ordered on 2 columns. About how many files does an equality filter on one of them read? || About √10,000 = 100 files, 1% of the table.
Why must signed integers be adjusted before interleaving their bits? || In two's complement, negative numbers start with a 1 bit, so raw bits would sort them after positive numbers. Flipping the sign bit makes bit order equal numeric order.
When would you not use clustering at all? || For small tables with few files, for queries that read most of the data anyway, or for workloads whose filters change constantly; also where a partition by date with a retention rule already does the job.

@@ compaction
value: Compaction takes many small pieces of data and rewrites them as fewer, larger pieces. In a lakehouse table, a streaming job may add thousands of tiny Parquet files per day, and compaction merges them into files of a few hundred MB. In an LSM-tree database such as RocksDB or Cassandra, compaction merges sorted files and throws away old versions and deleted keys. In a search engine such as Lucene it merges index segments. The data does not change. Only its physical packaging does.
The reason to do it is that every file has a fixed cost that does not depend on its size. Opening a file on object storage takes one or two network round trips, about 20 to 50 ms each. Reading a Parquet file means reading its footer first. Listing a folder returns at most 1,000 keys per call. The table format must track every file in its metadata, and the query planner must evaluate statistics for every file. A scan of 100,000 files of 4 MB spends most of its time on these fixed costs, while a scan of 800 files of 512 MB spends most of its time reading data. Compaction moves a table from the first state to the second.
For the layer above (the lakehouse, where streaming writes meet analytical reads), compaction is the background job that makes both sides work: writers can commit small batches quickly, and readers still see a few large files. Two concepts below it explain the cost. File systems (L3) explain the per-file overhead: metadata per file (the HDFS NameNode keeps roughly 150 bytes in memory per file or block object, and object stores charge per request), and the cost of opening. Big-O analysis (L3) explains the scaling: listing, planning and opening are O(number of files), with a large constant, so reducing the file count by 100 times removes 99% of that term.
terms: Small file problem — the slowdown and metadata load that result from having many files much smaller than the ideal size.
Bin-packing — compaction that only groups small files and rewrites their rows together into files near a target size, without changing the row order.
Target file size — the size that compaction aims for, typically 128 MB to 1 GB for analytical tables.
Sorted run — a file (or set of files) whose keys are in order; LSM trees keep several runs and merge them.
Leveled compaction — an LSM strategy that keeps one non-overlapping run per level and merges data from a level into the next, giving fast reads and more rewriting.
Size-tiered compaction — an LSM strategy that waits until several files of similar size exist and merges them, giving less rewriting and more files to read.
Write amplification — the ratio of bytes physically written to bytes logically written; compaction is its main source.
Tombstone — a marker that says a key was deleted; compaction removes it, and the data it hides, once it is safe.
history: The roots are in the log-structured merge-tree. Patrick O'Neil and colleagues described the LSM-tree in 1996 as a way to turn random writes into sequential ones: collect writes in memory, flush sorted files, and merge the files in the background. Google's Bigtable (2006) made it famous, and LevelDB (2011) and RocksDB (2012, from Facebook) added leveled compaction as a standard option. Cassandra took the Bigtable design, with size-tiered compaction as its original default. Lucene's segment merging, from the early 2000s, is the same idea for search indexes: every refresh makes a small segment, and a merge policy combines them.
Hadoop gave the problem its famous name: HDFS keeps the metadata of every file in the memory of one NameNode, and MapReduce started one task per small file. The lakehouse brought the issue back at a larger scale. Table formats (Delta Lake, Iceberg, Hudi) give ACID commits on object storage, which encourages frequent small commits, especially from streaming. Databricks added OPTIMIZE for Delta tables (2018 to 2019), and then optimized writes and auto compaction to prevent small files at write time. Iceberg added the rewrite_data_files action, and Hudi has compaction for merge-on-read tables. Research continued on the LSM side: Monkey (2017) and Dostoevsky (2018), by Niv Dayan and Stratos Idreos, showed how to tune the compaction policy against a workload and introduced hybrid "lazy leveling".
how: There are two families, and they share a core pattern: read several inputs, write fewer outputs, switch readers over atomically, and delete the inputs later.
Lakehouse compaction (bin-packing). The planner lists the live data files of the table (from the transaction log or manifests), groups them by partition or cluster, and picks files that are smaller than a threshold. In Iceberg's rewrite_data_files, a file group is rewritten if it holds at least 5 files (min-input-files), or if files fall below 75% of the target size or above 180% of it. The target defaults to 512 MB (the table property write.target-file-size-bytes). In Databricks the target is chosen automatically by table size: 256 MB for tables under 2.56 TB, rising linearly to 1 GB at 10 TB and above. Executors read each group, concatenate the rows (optionally sorted or Z-ordered, see the clustering concept), and write new files near the target size. Then the engine commits one transaction that says "remove these input files, add these output files". In Delta, this commit is marked dataChange = false, so that streaming readers and change feeds know that no rows changed and do not process it again.
Atomic switch-over. Because the table formats commit by one atomic metadata change, readers never see a half-compacted table. A query that started before the commit continues to read the old files, which still exist. This is why the old files cannot be deleted at once. They stay until a separate cleanup: VACUUM in Delta (default retention 7 days) or expire_snapshots and remove_orphan_files in Iceberg. Until then storage use is up to double, and time travel to older versions still works.
Prevention at write time. The best compaction is the one you avoid. Optimized writes shuffle data before writing so that each task writes one properly sized file instead of every task writing a tiny file for every partition. Auto compaction runs a small compaction job right after a write, in the same cluster, when a partition has too many small files (Databricks uses 128 MB as its target when this feature is set to true). Longer trigger intervals in streaming also help: one batch per minute makes 1,440 commits per day, one per ten minutes makes 144.
LSM compaction. An LSM tree flushes its in-memory table as a new sorted file at level 0. These files overlap each other in key range, so a read may need to check all of them. Leveled compaction (the RocksDB default) triggers when level 0 has 4 files (level0_file_num_compaction_trigger) or when a level exceeds its size budget, which grows by a factor of 10 per level. It picks a file at level L, finds the overlapping files at level L+1, merges them like merge-sort, drops overwritten values and tombstones, and writes new non-overlapping files at level L+1. With a fanout of 10, each byte is rewritten up to about 10 times for each level it passes, so write amplification is often 10 to 30 in practice. Size-tiered compaction (Cassandra's original default) waits for 4 files of similar size and merges them into one bigger file. It rewrites each byte only about once per tier, so writes are cheaper, but reads must check more files and space use can spike to double during a big merge. Lucene's TieredMergePolicy aims for around 10 segments per tier and merged segments up to 5 GB.
What the lower concepts contribute. File systems supply the cost model: opening a file, reading its footer, and tracking its metadata are per-file costs, and an atomic rename or an atomic metadata commit is what lets compaction swap files without readers noticing. Big-O supplies the argument for the target size. Per-scan overhead is roughly (number of files × fixed cost) + (bytes ÷ throughput). Making files bigger shrinks the first term, until it is smaller than the second. Beyond about 1 GB there is little more to gain, and larger files reduce parallelism and make each rewrite more expensive.
Concurrency. A compaction job races with writers. Appends are harmless, because they add files and do not touch the inputs. Row-level updates or deletes of the same input files make the compaction commit fail validation, and one job must retry. Deletion vectors and row-level concurrency in Delta reduce such conflicts, and Iceberg's partial-progress option commits groups of rewrites separately, so a conflict loses one group and not the whole job.

example: A streaming job writes to a Delta table every minute. Each micro-batch has 8 shuffle partitions, so it creates 8 files of about 4 MB each (32 MB per minute). The table is partitioned by date, so one day holds 1,440 batches × 8 = 11,520 files and 46 GB.
A dashboard query scans the last 7 days: 80,640 files, 322 GB. Assume each file costs about 40 ms of fixed overhead (two round trips to S3 for the footer and the first data), and the cluster has 200 cores. Fixed overhead is 80,640 × 40 ms = 3,226 core-seconds, or about 16 seconds of wall-clock time across 200 cores. The data itself, at about 100 MB/s per core, needs 322,000 MB ÷ 100 = 3,220 core-seconds. So half of the work is overhead. The query planner must also read 80,640 file entries from the transaction log, and Spark creates thousands of tasks, which costs time for scheduling.
Now compact to the target size of 512 MB: 322 GB becomes about 630 files. Fixed overhead drops to 630 × 40 ms = 25 core-seconds. The scan now costs 3,245 core-seconds in place of 6,446, which is a 2 times speed-up on the whole query, and the overhead term shrank by 130 times. Pure scan speed is not the only gain: statistics are more useful, and the metadata is 100 times smaller.
The price: compaction reads 322 GB and writes 322 GB, which is 644,000 MB. At 100 MB/s per core, that is about 6,440 core-seconds. This equals the saving from about two full scans, so if the table is read more than a couple of times after compaction, compaction pays for itself. Old, cold partitions need to be compacted only once, while the hot partition, where new files keep arriving, is the one to compact repeatedly, and compacting a partition that is still being written is wasteful. A common schedule is to compact yesterday's partition once, after it closes.
intuition: Tidy many small piles of paper into a few well-sorted binders, throwing away the crossed-out pages as you go.
The design is natural because file systems and object stores charge per file and per request, while the useful work is per byte. Writers want to write fast and often, in small units. Readers want to read in big units. A background process that translates between the two is the simplest answer: accept small writes now and pay to rearrange them later, when the data is cold and the rewrite can be done once for many readers. LSM trees do this for sorted keys, lakehouses for scan files.
mistakes: People often think compaction changes the data. In fact it rewrites the same rows into different files; the table contents are identical before and after. That is why table formats mark such commits as not changing data, so that downstream streams and change feeds ignore them.
People often think bigger files are always better. In fact above roughly 1 GB the gain is small, parallelism falls (a 10 GB file is read by one task unless the format splits it into row groups), and each rewrite costs more. Too large files also make updates and clustering more expensive.
People often think compaction frees space at once. In fact the old files stay until VACUUM or snapshot expiry, so storage use rises first. Time travel and long-running queries depend on those files.
People often confuse file compaction with Kafka log compaction. In fact Kafka log compaction keeps the latest record per key in a topic and drops older ones, which changes the content of the log, while lakehouse compaction keeps all rows and only repackages them.
friction: Compaction is write amplification by design. Each byte is read and rewritten, which costs compute and I/O, and in an LSM tree it competes with foreground reads and writes. When compaction falls behind, level 0 grows, reads slow down, and the database starts to throttle or stop writes (a write stall). Tuning means balancing three costs: write amplification, read amplification (how many files a read must check) and space amplification (how much extra data is stored).
In table formats the practical problems are scheduling and conflicts. A compaction that runs while updates or deletes touch the same files fails its commit, and a job that always loses the race never finishes. Compacting a partition that is still receiving data wastes work, and compacting too rarely leaves readers with the problem. Downstream incremental readers must also ignore compaction commits, and cleanup (VACUUM, snapshot expiry) is a separate task that is easy to forget.
practice: Prevent first. Avoid writing many tiny files: repartition or coalesce before the write, turn on optimized writes and auto compaction where your platform offers them, use trigger intervals that match your latency needs, and avoid partitioning by columns with many values (daily partitions are usually the finest sensible level for a table below a few TB). A partition that holds less than 1 GB is probably too fine.
Then schedule compaction. For streaming tables, run it on a timer (hourly or daily) for the partitions that are no longer being written, using the platform's automatic option where available (for example predictive optimization on Databricks). Set a target file size of 256 MB to 1 GB. In Iceberg, run rewrite_data_files with a size filter, then expire_snapshots and remove_orphan_files. In Delta, run OPTIMIZE, and VACUUM only with a retention longer than your longest-running query or time-travel need.
Monitor the file count and average file size per table, the percentage of files under 25% of target, and the time spent in planning and listing. Alert when the small-file ratio rises. For LSM stores, watch pending compaction bytes, level 0 file count and write stalls, and pick the policy by workload: leveled for read-heavy, size-tiered or universal for write-heavy. Keep compaction jobs on separate resources from latency-sensitive queries if you can.
tradeoffs: Compact often or rarely. Choose frequent compaction (hourly, or auto compaction after each write) when queries on fresh data are latency-sensitive and the hot partitions are small; the cost is repeated rewrites of the same data. Choose rare compaction (daily, after a partition closes) when freshness of file layout is less important, because you rewrite each byte only once. You give up either compute or read speed.
Leveled or size-tiered LSM compaction. Choose leveled when reads and space matter (point lookups, limited disk, read-heavy workloads), accepting write amplification of 10 or more. Choose size-tiered when writes dominate and you can afford extra files and up to double the space during merges. Hybrid policies such as lazy leveling sit in between.
Compact at write time or in the background. Choose write-time techniques (optimized writes, bigger batches) when you control the writers; they avoid most small files at the cost of a shuffle and some latency. Choose background compaction when many independent writers or streams produce the files, and when you want writes to be as fast as possible.
interview: Why do many small files hurt a query engine, even if the total bytes are the same? || Each file costs fixed work: listing, a footer read, a metadata entry in the log, planning and a task or at least a scheduling slot. How can compaction run while queries and writers use the table? || The rewritten files are new; the commit is an atomic metadata change that swaps inputs for outputs, so readers see either the old or the new set. Old files remain until cleanup, so running queries are safe. Writers that only append do not conflict; updates or deletes of the same files cause a conflict that must be retried.
Your Delta table has 200 files per streaming batch. What do you change first? || Reduce the number of files being written: fewer shuffle partitions or an optimized write, a longer trigger interval, and check over-partitioning. value: A schema describes the fields and types of a record. Schema evolution is the discipline and the machinery that let a schema change over time while the systems that write and read the data keep working. The change might be adding a field, renaming a column, or widening an int to a long. The hard part is that you cannot upgrade everything at once. Producers and consumers are deployed by different teams on different days, and stored data (Kafka topics with weeks of retention, Parquet files from three years ago) was written under old schemas and must still be readable.
The concept gives two answers. The first is a set of compatibility rules: backward compatible means a reader on the new schema can read data written with the old one; forward compatible means a reader on the old schema can read data written with the new one; full means both. The second is the mechanism that applies the rules when data is decoded: Avro resolves the writer's schema against the reader's schema, Protobuf skips unknown field numbers, and table formats such as Iceberg track columns by ID, so a rename does not break old files.
For the layer above, this is what keeps teams decoupled. Avro and Protobuf (L0) are the formats with built-in evolution rules. A schema registry (L0) checks every new schema against the earlier ones and rejects a break before it reaches production. The lakehouse (L1) lets columns be added, renamed or widened without rewriting petabytes. Data contracts and data mesh (L1) make a schema a promise between teams. Two concepts below it carry the logic. Type systems (L3) turn compatibility into a type-checking question: can every value the writer can produce be accepted by the reader? Parsing (L3) explains how a decoder reads bytes using a schema, and so what a decoder can do when the bytes and the schema disagree.
terms: Writer schema — the schema that was used to encode a piece of data; Avro needs it to decode.
Reader schema — the schema that the consuming application expects.
Backward compatible — a reader using the new schema can read data written with the previous schema (for example, a new field has a default value).
Forward compatible — a reader using the previous schema can read data written with the new schema (for example, it ignores fields it does not know).
Full compatible — both backward and forward compatible; the safest and the most restrictive.
Transitive — checked against all earlier versions, not only the latest one.
Field ID — a number that identifies a column permanently (Iceberg, Parquet field_id, Protobuf field number), so renames do not change identity.
Schema registry — a service that stores schema versions, assigns IDs and enforces a compatibility mode when new versions are registered.
history: The problem is as old as stored data. Early formats such as CSV had no schema, and relational databases solved it with ALTER TABLE, which rewrites or locks the table. Distributed systems made it harder, because the readers and writers are separate programs. Google developed Protocol Buffers in the early 2000s for internal RPC and storage, and the central rule was set early: fields are identified by number, not by name, so old and new code can exchange messages as long as the numbers keep their meaning (published as open source in 2008).
Apache Avro (2009, Doug Cutting, in the Hadoop project) took a different approach. Avro data carries no field tags, which makes it compact. In return the reader must have the writer's schema, and resolution rules in the specification define how to match it to the reader's schema. Confluent's Schema Registry (around 2014 to 2015) turned this into an operating practice for Kafka: the producer registers a schema, each message carries a 4-byte schema ID, and the registry rejects incompatible changes according to a configured mode.
Column stores and table formats brought the issue to analytical data. Early Hive and Parquet matched columns by name or by position, so a rename or a drop followed by an add could silently return wrong data. Iceberg (2018) assigned every column a unique ID and matched files by ID. Delta Lake added column mapping, which separates logical names from physical names in the files, and type widening for selected type changes.
how: Schema evolution works in three layers: the rules, the identity of fields, and the enforcement.
The rules. Compatibility is a relation between a writer schema W and a reader schema R. Think of each schema as the type of the data. Reading is safe when every value allowed by W can be handled by R. That is a subtyping check, with one twist: it depends on the direction. Adding an optional field is backward compatible: a new reader (R with the extra field) reads old data (W without it) by filling a default. It is also forward compatible if old readers ignore unknown fields. Removing a field with a default is backward compatible in the opposite sense. Adding a required field with no default breaks backward compatibility, because the new reader has nothing to put in the field when it reads old data. Changing a type is allowed only along safe promotions (Avro: int to long, float or double; long to float or double; float to double; string and bytes to each other; Iceberg: int to long, float to double, and decimal precision growth with the same scale). Everything else (string to int, narrowing, reordering enums) is a break. The type-system view gives the logic: a reader may accept more than the writer produces, and a writer may produce less than the reader accepts.
Confluent's compatibility modes state the rules as policies. BACKWARD (the default) lets you delete fields and add optional ones, and says to upgrade consumers first. FORWARD lets you add fields and delete optional ones, and says to upgrade producers first. FULL allows only adding or deleting optional fields, and allows any order. The _TRANSITIVE variants check against every earlier version, which you need when old data stays readable for a long time, such as in a lakehouse.
Identity of fields. The rules need a way to say which field in W corresponds to which field in R. The formats choose different keys. Protobuf uses the field number written on the wire, so names can change but numbers can never be reused for another meaning (reserved lists protect retired numbers and names). Avro matches by name (with aliases to support renames) and needs the writer schema at decode time, as the binary data has no tags. Iceberg matches by field ID, which is stored with the column in the table schema and in Parquet files, so rename, reorder and add are metadata-only, and a dropped column is not revived by a later column with the same name because the new one has a new ID. Delta matches by name by default, and column mapping mode (name or id) adds an indirection so that renames and drops are metadata-only.
How decoding applies the rules. Here parsing matters. Avro decoding is a parse driven by a grammar built from the schema: for each field, the decoder reads a value of the next type. When the writer and reader schemas differ, the decoder follows the writer's schema to consume the bytes, and the reader's schema to decide what to keep. Writer fields the reader does not have are read and thrown away. Reader fields the writer did not have are filled from defaults. If a reader field has no default, the parse fails. Protobuf's tag-length-value layout lets a decoder skip an unknown field without knowing its meaning, because each tag carries the wire type and the length. That is how forward compatibility works there, with no registry at all.
Enforcement. Rules are only useful if they are checked at the right moment. A schema registry checks when a producer registers a new version, and rejects the registration if it breaks the mode. Table formats check on write: Delta enforces the table schema and fails a write with extra or mismatched columns, unless you explicitly set mergeSchema or run ALTER TABLE; Iceberg updates the schema through API calls that record a new schema version with the same IDs. CI checks in the schema repository can run the same compatibility test before any deploy. Data contracts add semantic checks (units, allowed values) that no format can enforce by itself.

example: Start with an Avro record User version 1 with two fields, id (long) and name (string). Encode id = 7 and name = "Ann". Avro writes integers as zigzag varints: 7 becomes 14 = 0x0E. The string is a length (3 becomes 6 = 0x06) followed by the bytes 41 6E 6E. The record is five bytes: 0E 06 41 6E 6E. It has no field names or tags. Without the schema it cannot be decoded.
Now a new version 2 adds a field email (string, default ""). A consumer upgraded to version 2 reads old bytes. The registry told it the writer schema (version 1), so it reads id = 7 and name = "Ann", sees that email is not in the writer schema, and fills the default. This is backward compatible, and it works because of the default. If the field had no default, the registry in BACKWARD mode would have rejected version 2.
The other direction: a new producer writes version 2 data with the email. A consumer still on version 1 gets the writer schema (version 2), reads the email string, and drops it because its own schema has no such field. This is forward compatible for free in Avro, because deleting an unknown field is always allowed during resolution. Because both hold, adding an optional field with a default is FULL compatible.
Now three bad changes. Rename name to full_name in version 2 with no alias: the reader looks for full_name in the old bytes, finds no field, and has no default, so the parse fails. Adding the alias "name" to the new field fixes it. Change id from long to string: no promotion exists, so it fails. Add a required field with no default: new readers cannot read old data.
Finally the table side. An Iceberg table has columns id (ID 1), name (ID 2), email (ID 3). You run ALTER TABLE RENAME COLUMN name TO full_name. Only the schema JSON changes; ID 2 is the same, so every old Parquet file is read correctly with no rewrite. You drop email, and later add a different column also called email. It receives ID 4. Old files contain column ID 3 only, so the new email reads as null for old rows, and the dropped values are not exposed. With name-based matching, the new email would have picked up the old data, which is a silent data error.
intuition: Adding a new box to a form without making the old, filled-in forms invalid.
The design is natural because change and stability pull in different directions, and compatibility is a way to get both. If readers accept a bit more than writers produce (extra optional fields, wider numbers) and writers never take away what readers depend on, then each side can move on its own timeline. Giving fields a permanent identity (a number or an ID) is the same idea as giving files names that never get reused. The rules are about trust: two programs that never meet agree on a contract of what can change and what cannot.
mistakes: People often think that a schema registry guarantees safe evolution. In fact it checks structure only (fields, types, defaults). It cannot detect that "amount" changed from dollars to cents, or that a status code gained a new meaning. These semantic changes pass every check and still break consumers.
People often think backward and forward compatibility are the same, or that one implies the other. In fact they are different directions and need different upgrade orders: backward means upgrade consumers first, forward means upgrade producers first. Choosing the wrong mode for your deployment order causes outages when versions overlap.
People often think a rename is a harmless change. In fact it is a delete plus an add unless the format tracks identity: Avro needs aliases, Protobuf JSON output changes the name, and name-matched Parquet readers return nulls. Only ID-based formats (Iceberg, Delta column mapping) make a rename safe.
People often think checking against the latest version is enough. In fact consumers may read data written under any earlier version, for example when replaying a topic or querying an old partition. Use transitive modes where data lives long, because a chain of individually safe steps can still produce a version that cannot read the oldest data.
friction: Compatibility checks cover structure and miss meaning. A column that changes meaning, units, time zone or enum semantics is the most common real incident, and it needs data contracts, tests on real data and communication between owners. Many teams also lack enforcement: schemas live in code reviews and not in a registry or in CI, and breaking changes reach production.
Real breaking changes still happen and need a migration process, such as expand and contract. First add the new field and write both, then migrate every reader, and then stop writing the old field and remove it once retention has expired. That takes weeks and needs a way to find all consumers. For streams with long retention or for lakehouse tables with years of data, you may need to rewrite or backfill.
Formats differ, so cross-system pipelines hit mismatches. A rule that is safe in Avro (type promotion) may not be safe in Parquet readers that expect the old type, in a JSON sink, or in a downstream SQL view. Wide tables with hundreds of columns and nested types produce complex changes. Type widening can also break downstream code that assumed 32-bit integers.
practice: Treat every shared schema as an API. Put it in version control, run a compatibility check in CI, and register it in a schema registry with a mode that matches your deployment order. Default to FULL_TRANSITIVE or BACKWARD_TRANSITIVE for data that is retained for a long time, and BACKWARD if you can always upgrade consumers first.
Make safe changes by habit. Add optional fields with defaults; never reuse a Protobuf field number; reserve removed ones; do not change a field's type except by supported promotions; make new enum values safe by giving readers an unknown or default value. For renames in Avro use aliases, and in lakehouse tables use ID-based or column-mapped renames. For anything else, use expand and contract with dual writes and a migration window.
In lakehouse tables, enable column mapping in Delta if you expect renames and drops, and prefer Iceberg's ID-based evolution. Keep schema changes explicit (ALTER TABLE), and avoid leaving automatic schema merging on for production writes, because a typo in a column name becomes a new column. For Parquet written outside table formats, read with an explicit schema.
tradeoffs: Backward or forward compatibility. Choose BACKWARD when you control consumers and can upgrade them before producers (typical for data warehouses and replayable topics, where new readers must read old data). Choose FORWARD when producers must change first and many old consumers cannot be upgraded soon. Choose FULL when both orders occur. The stricter the mode, the fewer changes you can make; the looser it is, the more coordination you need.
Transitive or latest-only checks. Choose transitive when retention is long or consumers may replay from the start, since a new schema must read everything still stored. Choose latest-only when retention is short (days) and every consumer reads recent data. Transitive checks block more changes, and they protect old data.
Avro, Protobuf or JSON. Choose Avro for data pipelines and analytics where compactness and a registry are fine and schemas are always available at read time. Choose Protobuf when you also need RPC, many languages and field-number evolution that works without any registry. Choose JSON (with a JSON Schema) when humans read the messages and size matters less. You give up compactness or tooling.
Name-based or ID-based tables. Choose ID-based tables (Iceberg, Delta with column mapping) when you expect renames, drops and years of history. Choose simple name-based tables for short-lived, rarely changed data where the added metadata is not worth it. The cost of ID-based tables is a more complex format and a protocol upgrade (in Delta, an older reader or writer may lose access).
interview: What is the difference between backward and forward compatibility, and which upgrade order does each imply? || Backward: new readers can read old data, so upgrade consumers first. Forward: old readers can read new data, so upgrade producers first. Full does both and allows any order. The point is to match the mode to the deployment order you actually have.
How does Avro read data written with a different schema? || The decoder gets both schemas. It parses the bytes using the writer's schema, because the bytes have no tags, then maps fields to the reader's schema by name (or alias). Missing reader fields take defaults, extra writer fields are skipped, and promotions are applied. A reader field with no default and no writer field is an error.
Why are renames safe in Iceberg but risky elsewhere? || Iceberg identifies columns by permanent IDs stored in the schema and Parquet files, so a rename only changes a name in the metadata. Name-matched formats see a rename as a delete and an add, so old data reads as null or fails.
A team replays a 30-day Kafka topic into a new consumer after three schema changes. What compatibility mode should have been used? || A transitive mode (BACKWARD_TRANSITIVE or FULL_TRANSITIVE), because the new consumer must read data written under every version in the retention window, and checking against the latest version only does not guarantee that.
How would you remove a field used by many consumers? || Use expand and contract: mark it deprecated, make it optional with a default if needed, stop producers from filling it after consumers no longer read it, verify with usage data, and only then remove it from the schema; for Protobuf reserve the number. In table formats drop the column as metadata and keep old files.
quiz: Is adding a required field without a default backward compatible? || No. A new reader meets old data that lacks the field and has no value to put there, so reading fails.
Why does Protobuf stay compatible when you rename a field but not when you reuse its number? || The wire format identifies fields by number only, so names do not matter in binary, but a reused number is decoded with the new meaning, which corrupts old data.
An Iceberg column "email" (ID 3) is dropped and a new "email" is added. What ID does the new one get and what do old rows show? || A new ID (4), and old rows show null because their files contain only ID 3; the old values are not exposed.
Avro writer v1 bytes are 0E 06 41 6E 6E. What are the fields? || id = 7 (zigzag 0x0E = 14 means 7) and name = "Ann" (length byte 0x06 means 3, then A n n).
When would you choose FULL_TRANSITIVE over BACKWARD? || When producers and consumers upgrade in any order, or when long retention means readers must handle data from every earlier version and older readers must handle new data.

@@ rowlineage
value: Row lineage gives each row in a table a stable identity and a stamp that says which table version last changed it. With those two facts, an engine can answer "which rows were inserted, updated or deleted since version N?" by reading only the data that changed, without comparing two full copies of the table. This is the base for incremental pipelines: a downstream table or materialized view can process only the delta and not recompute everything.
Table formats built on immutable files have a natural difficulty here. A table is a set of files, and an UPDATE does not change a row in place. It writes a new file that contains a copy of the row (copy-on-write), or a delete marker plus a new row (merge-on-read). To a reader the old row has vanished and a new row has appeared, and nothing says that they are the same row. Before row lineage, engines found changes by diffing file lists (which tells you which files changed, not which rows), by writing a separate change log, or by trusting a business key and a timestamp column.
For the layer above, row lineage is the engine of change data capture on lakehouse tables (CDC, L1) and of incremental refresh in declarative pipelines and materialized views (L1). Iceberg (L0) v3 specifies it as two row fields, and Delta Lake (L0) provides row tracking and a separate change data feed. Two concepts below it explain it. MVCC (L2) provides the model: a version number is stamped on each row version, as in multi-version databases, so "what is visible at version N" and "what changed after N" are comparisons on that stamp. Indexing (L3) provides the use of the stable ID: it works like a primary key for the table's history, a handle that lets two snapshots be joined row by row.
terms: Row ID — a number that identifies a row across table versions, even when the row is moved to another file or updated.
Sequence number — Iceberg's counter that increases with each commit; every data file records the sequence number of the commit that added it.
Last-updated sequence number — the sequence number of the commit that most recently inserted or modified the row.
Row commit version — Delta's name for the same idea: the table version in which the row was last inserted or updated.
Change data feed (CDF) — a stream of row-level changes (insert, update before and after, delete) that a table can expose to readers.
Pre-image and post-image — the values of an updated row before and after the update.
Inheritance — a way of storing a value once at a higher level (file or manifest) so that rows get it at read time instead of storing it in every row.
Copy-on-write and merge-on-read — two ways to implement an update on immutable files: rewrite the file, or write a delete marker and a new row.
history: Two older ideas lead here. Databases have long stamped rows with versions: PostgreSQL stores a creating and a deleting transaction ID on every row version, and Oracle uses system change numbers. Replication systems (MySQL binlog, Debezium reading logs) emit change events with keys. Both ideas answer "what changed" for row-store databases, because the engine owns the log.
Lakehouse formats started without this. Delta Lake (2019) had a transaction log of added and removed files, so one could see which files changed between versions but not which rows. Databricks then added the change data feed (2021; open-source Delta 2.0, 2022), which writes explicit change records for updates and deletes. Iceberg (2018) kept snapshots with sequence numbers (from spec v2) and offered a changelog view in Spark that reconstructs changes from added and deleted files and delete files.
The newer step is to put identity into the table itself. Delta introduced row tracking as a table feature (writer feature "rowTracking") with row IDs and commit versions. The Iceberg community added row lineage to the v3 table spec, together with deletion vectors, a variant type and default values, and Databricks supports Iceberg v3 row tracking from Databricks Runtime 18.0. The motivation in both cases is the rise of incremental processing: materialized views, streaming tables and dbt-style incremental models all want the changed rows, and they want them without a full scan.
how: There are two ways to get row-level changes from a table format. The first is to store identity and a version stamp for each row (row lineage). The second is to write explicit change records when the change happens (a change feed). The first is cheap to store and flexible to read. The second is faster to read and heavier to write.
Row lineage in Iceberg v3. Every row has two logical fields: _row_id, a unique long for the row within the table, and _last_updated_sequence_number, the sequence number of the commit that last inserted or modified it. The clever part is that these are mostly not stored. When a writer adds new rows, it writes null for both, or omits the columns. The values are assigned by inheritance when the data is read. The sequence number comes from the manifest entry of the data file. The row ID is the data file's first_row_id plus the row's position in the file. The first_row_id of a file comes from the manifest's first_row_id, which comes from the snapshot's first-row-id, which is set from the table's next-row-id field at commit time. Because everything is resolved at commit, the writer can prepare files before knowing the final values, and a retried commit does not require rewriting data files.
When a row is updated, the rule is: if the row moves to a new file, its existing _row_id is copied into the new file, so the identity persists. If the write modified the row, _last_updated_sequence_number is set to null, so that the new commit's number is inherited. If the row was only copied, for example during compaction or an unrelated update to the same file, the old sequence number is copied unchanged. Equality deletes are an exception: because the engine does not read the old rows, it cannot know their IDs, so such updates are treated as a delete plus a brand new row. The next-row-id counter is advanced by the number of rows in the files that got a range, so IDs are unique but not necessarily dense. A table upgraded to v3 starts with next-row-id = 0, and snapshots from before the upgrade have no row IDs.
Delta Lake row tracking. The protocol defines two kinds of IDs. A fresh row ID is the default generated ID: the file's baseRowId plus the row position. It uniquely names a row in one table version, but changes whenever the row is rewritten into another file. A stable row ID survives updates and copies. It is stored in a hidden materialized column in the data file when the writer needs to preserve it, and falls back to the default generated value when that column is null. Row commit versions work the same way, with a defaultRowCommitVersion on the file's add action and an optional materialized column. Applications can read these as the metadata columns _metadata.row_id and _metadata.row_commit_version. The feature is turned on with the table property delta.enableRowTracking, and the high-water mark of assigned IDs is kept in a domainMetadata entry. Enabling it needs writer protocol version 7 and the rowTracking feature, so older writers cannot write to the table, though readers are not affected.
Reading changes. Given two versions A and B, the reader selects rows whose last-updated stamp is greater than A's (and at most B's). A row in that set whose ID did not exist at A, which means its ID is at or beyond the table's next-row-id at A, is an insert. A row whose ID existed before A is an update, and its pre-image can be found by joining the earlier version on the row ID. Deletes cannot be found from the rows that remain, because a deleted row is gone. They need a comparison of the IDs present at A and B, or the delete files and deletion vectors of the commits in between. This is the main difference to a change feed.
Delta's change data feed. When delta.enableChangeDataFeed is true, the engine records changes as it writes. For commits such as appends or whole-file deletes, it can derive the changes from the added and removed files. For UPDATE, DELETE and MERGE, it writes extra files in a _change_data folder, with each row tagged with _change_type (insert, update_preimage, update_postimage, delete), _commit_version and _commit_timestamp. A reader asks for versions 10 to 20 (table_changes in SQL, or the readChangeFeed option) and gets these rows directly, in an explicit form that downstream consumers (CDC sinks, incremental pipelines) can apply without any join. The price is extra write work and extra files.
How the lower concepts contribute. MVCC supplies the stamp: every row version knows the commit that produced it, so visibility at a version and the difference between two versions are range checks on that stamp, in the way a multi-version database decides which tuple a transaction sees. Indexing supplies the identity: a stable ID is a key. Without it, two snapshots cannot be matched row for row, and any diff needs a business key chosen by the user, which may not be unique or stable. With it, an engine can use ordinary join and group-by operations on the history.

example: Follow the diagram with an Iceberg v3 table that has next-row-id = 1000. Commit S5 (sequence number 5) appends file A with three rows. The snapshot's first-row-id is 1000, so the rows get IDs 1000, 1001 and 1002 by inheritance, each with last-updated sequence number 5. The table's next-row-id becomes 1003.
Commit S6 (sequence number 6) runs UPDATE ... WHERE id = 1001 with copy-on-write. The engine writes a new file A' containing all three rows and removes A. Rows 1000 and 1002 are only copied: their IDs and their stamp 5 are written into A' unchanged. Row 1001 is modified: its ID is copied, but its stamp is set to null, so it inherits 6. In this simplified example the new file reserves a range of 3 IDs from the counter, so next-row-id becomes 1006 (the exact count depends on how the writer lays out manifests). IDs 1003 to 1005 are never used by any row, which is allowed because IDs are unique, not dense.
Commit S7 (sequence number 7) appends file B with two rows. Their first row ID is 1006, so they are rows 1006 and 1007, both with stamp 7. The counter is now 1008.
Now an incremental job asks for changes after S5. It filters rows with last_updated_sequence_number > 5 and reads only the files that can contain them. It gets three rows: 1001 (stamp 6), 1006 and 1007 (stamp 7). To classify them, it uses the next-row-id at S5, which is 1003. A row ID below that existed already, so 1001 is an update. IDs at or above it are new, so 1006 and 1007 are inserts. To find the deletes, it takes the set of IDs at S5 {1000, 1001, 1002} and subtracts the IDs at S7 {1000, 1001, 1002, 1006, 1007}, which is empty, so nothing was deleted.
intuition: Every row gets a passport with an entry stamp, so you can list exactly who arrived or changed since last Tuesday.
The idea is natural because the missing piece in an immutable-file table is identity across time. Files come and go, but a row is a logical thing, and a logical thing needs a name that does not change when it moves. Once rows have names and a version stamp, "what changed" is a simple filter on the stamp, in the same way that an incremental backup uses a modification time. The hard engineering is to keep the names and stamps nearly free, and inheritance does that: values are computed from where the row sits until the row is rewritten.
mistakes: People often think row lineage is the same as a change data feed. In fact lineage records identity and a version stamp, and the changes are derived at read time. A change feed writes explicit change records at write time. Lineage cannot directly show deleted rows or the pre-image of an update, whereas a feed contains both.
People often think a row ID is a business key or a primary key. In fact it is an internal identifier of the engine. It is not meaningful outside the table, may not be dense, and is not guaranteed to survive operations that the writer treats as delete plus insert (such as updates through equality deletes, or a table copy).
People often think that any compaction or rewrite keeps lineage. In fact the stable ID survives only if the writer preserves it. In Delta, default generated row IDs are reassigned when rows move, and stable IDs survive only through materialized columns. In Iceberg, a writer must copy the existing _row_id into the new file. An engine that does not support the feature can produce rows without valid lineage.
friction: The first limit is engine support. Row lineage is new in Iceberg (spec v3), and engines implement it at different speeds, so a reader that does not understand v3 cannot read the table at all. In Delta, enabling row tracking is a protocol change that older writers cannot follow. Check every tool that touches the table (Spark versions, Trino, Flink, catalogs, BI tools) before upgrading.
The second limit is correctness around edge cases: deletes are not visible in the remaining rows, equality-delete updates lose lineage, tables copied or restored from a backup may have row IDs that no longer match consumers' expectations, and branching in Iceberg assigns disjoint ID ranges per branch. Incremental consumers must also track which version they processed last, and that bookmark can be lost if snapshots expire. A consumer that falls behind retention has to do a full refresh.
practice: Decide what the consumer needs. If it needs explicit insert/update/delete events with before and after values (CDC into another database, audit), use a change feed (Delta CDF, or Iceberg's changelog view). If it needs only "which rows changed so I can recompute", row lineage and a version filter are enough and cheaper to store.
Turn the feature on early for tables that will feed incremental pipelines, since it applies only to future changes. Test your engines first: write, update, compact and read with all the tools that touch the table, and verify that row IDs and stamps survive compaction and merges. Keep snapshot retention longer than the slowest consumer's lag, and store the last processed version in the consumer (or use the platform's checkpoint). Add a fallback to a full refresh if the bookmark has expired.
tradeoffs: Row lineage or a change feed. Choose lineage when many consumers read at different times and you want low write overhead (the stamp is nearly free) and flexible queries over any version range. Choose a change feed when consumers need explicit before and after images and deletes with no joins, and you accept extra write cost and a limited history. You give up read simplicity with lineage, and write cost with a feed.
Lineage or a business key and timestamp. Choose lineage when the table has no reliable key or no trustworthy update timestamp, or when updates may arrive from many writers. Choose a business key plus updated_at column when you control the source, all writers set it correctly, and you need engine independence; it works on any format today. The risk is clock errors, late updates and missing deletes.
Incremental or full recompute. Choose incremental processing when changes are a small fraction of the table (below about 5 to 10 percent per run), consumers can tolerate occasional full refresh, and the logic is easy to maintain incrementally. Choose full recompute when the changed fraction is large, when the logic is not incremental (global ranks, complex joins) or when correctness is more important than cost.

@@ deliverysem
value: Delivery guarantees describe what a messaging or streaming system promises about a message when something fails. There are three classic levels. At-most-once means a message is delivered zero or one times: it may be lost, but never duplicated. At-least-once means one or more times: it is never lost, but it may be duplicated. Exactly-once means the effect happens one time. The third level cannot be had for free, because over an unreliable network a sender can never know whether a missing acknowledgement means "the message was lost" or "the message arrived and the reply was lost".
This matters in every pipeline that moves events between services: ad impressions and clicks, billing events, orders, sensor readings. Each failure (a crashed consumer, a timeout, a restarted broker) forces a choice. Retry and risk a duplicate, or give up and risk a loss. Counting impressions twice overbills advertisers; dropping them underbills the business. Knowing which of the two your pipeline does, at each hop, is the first step to making the final result correct.
For the layer above (message queues and publish-subscribe systems, and the share groups that add queue semantics to Kafka), delivery guarantees are the contract that consumers code against. The layer below is TCP (L3). TCP shows the mechanism that creates the problem: a sender keeps a message until it gets an acknowledgement, and retransmits when the acknowledgement does not arrive. If the data arrived and only the acknowledgement was lost, the retransmission is a duplicate. TCP hides this inside one connection with sequence numbers. Once an application retries on a new connection, or a message crosses a queue, nothing deduplicates it unless the application adds its own identifiers.
terms: At-most-once — each message is delivered zero or one times; failures can lose messages.
At-least-once — each message is delivered one or more times; failures can duplicate messages.
Exactly-once — the effect of each message happens once, in spite of failures and retries; usually built from at-least-once delivery plus idempotence or transactions.
Acknowledgement (ack) — a reply from the receiver saying the message was received or processed.
Offset commit — the consumer's record of how far it has read in a log, so it can resume after a restart.
Idempotent operation — an operation that gives the same result when applied once or many times, such as "set balance to 50" (and unlike "add 10").
Deduplication — recognising and dropping a message that was already processed, usually by an ID.
Zombie — an old instance of a producer or consumer that was presumed dead but is still running and still writing.
history: The theory is older than any messaging product. The Two Generals Problem (Akkoyunlu, Ekanadham and Huber, 1975; named by Jim Gray in 1978) shows that two parties communicating over an unreliable link cannot reach certain agreement about a message. In 1984, Saltzer, Reed and Clark's "End-to-end arguments in system design" argued that reliability must in the end be checked by the endpoints of an application, and not left to the network in the middle. Both ideas explain why per-hop reliability does not give end-to-end exactly-once.
Message queue products in the 1990s and 2000s (IBM MQ, JMS, RabbitMQ, SQS in 2004) standardised acknowledgements and redelivery, which means at-least-once by default, with a visibility timeout or an unacked message returning to the queue. Pat Helland's "Idempotence Is Not a Medical Condition" (ACM Queue, 2012) made the practical case: since duplicates cannot be avoided, design operations that tolerate them.
Kafka (2011) began with at-least-once delivery and, in its early years, said that exactly-once was not possible without cooperation from the destination. In 2017 (Kafka 0.11, KIP-98) it added idempotent producers and transactions, which together provide exactly-once within Kafka. Kafka Streams followed with exactly-once processing (and the improved "exactly_once_v2" mode in 3.0), idempotence became the producer default in Kafka 3.0 (2021), and Flink (2017 onward) paired its checkpoints with two-phase commit sinks for end-to-end exactly-once. Amazon SQS FIFO queues (2016) added a deduplication window of five minutes. The consistent lesson of these years: exactly-once is a property of a whole pipeline, and it is built, not given.
how: The core of every guarantee is a rule about the order of two actions: doing the work, and recording that the work is done. A failure can strike between them, and which side is recorded first decides whether you lose or duplicate.
At-most-once. Record first, work second. A consumer reads a message, commits its offset (or acks it), and only then processes it. If it crashes after the commit and before the work finishes, on restart it continues after the message, and the message is lost. A producer is at-most-once when it sends and never retries (acks=0 or no retry). This is simple and fast, and suitable for data where an occasional loss is cheaper than any duplicate, such as sampled metrics or logs.
At-least-once. Work first, record second. The consumer processes the message, and commits the offset afterwards. A crash between the two repeats the work after a restart. A producer is at-least-once when it retries until it receives an acknowledgement: if the first send succeeded and only the ack was lost, the retry writes a second copy. Most systems default to this level, because losing data is usually considered worse than duplicating it. The consumer side is where the duplicate does its damage, so consumers must be written to tolerate it.
Exactly-once effects. There are two ways to turn at-least-once into an exactly-once effect. The first is idempotence: make the repeated action harmless. Writing a row with a key by upsert, setting a value rather than incrementing it, or including a unique message ID and ignoring IDs already seen. Kafka's idempotent producer does this inside the broker. Each producer gets a producer ID, and each batch to a partition carries a sequence number. The broker keeps the last few sequence numbers (it accepts up to 5 in-flight requests per connection with idempotence on) and rejects a repeated one. Retries then cannot duplicate, and order is preserved. This works for one producer session and one partition; it does not protect against a producer that restarts with a new ID or against duplicates created further down.
The second way is atomic commit of the work and the progress together. Kafka transactions let a read-process-write loop write output records to several partitions and the consumer's input offsets in one atomic transaction. A transactional.id identifies the producer across restarts, and an epoch fences zombies: when a new instance registers, the broker rejects writes from the old one. Consumers set isolation.level=read_committed, so they only see records of committed transactions (the broker writes commit or abort markers in the log). The input offset and the output are then either both visible or neither is. This gives exactly-once for Kafka-to-Kafka pipelines. Kafka Streams exposes it as processing.guarantee=exactly_once_v2.
Beyond Kafka. For a sink outside Kafka, the same pattern appears with a different form. Flink takes a checkpoint (a consistent snapshot of operator state and source offsets). Sinks that support two-phase commit write data in an open transaction, pre-commit when the checkpoint barrier arrives, and commit once the whole checkpoint is complete. After a failure, Flink restores the last checkpoint, replays the source from the saved offsets, and aborts uncommitted transactions. Spark Structured Streaming records the offsets of each micro-batch in a write-ahead log before processing, and gets exactly-once with a sink that treats the batch ID as an idempotency key (Delta's idempotent writes use an application ID and version). Where the sink is a plain database, an upsert keyed by event ID, or a table of processed IDs updated in the same transaction as the effect, achieves the same.
How the layer below shapes this. TCP explains why the failure window exists: acknowledgements are separate messages that can be lost, so the sender can never be sure. It also shows the standard fix, sequence numbers: TCP drops duplicate segments by sequence number within a connection. The messaging layers copy the idea at the application level (producer ID plus sequence number in Kafka, MessageDeduplicationId in SQS FIFO). The end-to-end argument adds the limit: the dedup must be done where the effect happens, because a reliable hop does not stop a duplicate created by an application retry.

example: A consumer reads batches of 10 messages (offsets 100 to 109) from a topic, writes each to a database, and then needs to record progress.
Option A, commit first: the consumer commits offset 110 and then starts writing. It writes 4 messages (100 to 103) and crashes. After the restart it resumes at 110. Messages 104 to 109 were never written: 6 are lost. This is at-most-once.
Option B, commit last: the consumer writes all 10 messages and then commits 110. Suppose it crashes after writing 7 (100 to 106), before the commit. After the restart it resumes at 100 and writes all 10 again. Messages 100 to 106 now exist twice: 7 duplicates, 0 lost. This is at-least-once.
Option C, at-least-once with an idempotent sink: the database table has a primary key event_id, and the consumer uses an upsert (INSERT ... ON CONFLICT DO UPDATE). The replay in option B rewrites rows 100 to 106 with identical values, and the table ends with exactly 10 rows. The effect is exactly-once, although the delivery was at-least-once.
Option D, atomic: the consumer writes the rows and the offset in the same database transaction (storing the offset in the database), or uses a Kafka transaction when the sink is another topic. A crash rolls back both, and the restart repeats the batch from the beginning, once.
Money. An ad pipeline processes 1 billion impressions per day. Suppose 0.1% are duplicated by retries. That is 1 million duplicate events. At a $5 CPM, each impression is worth $0.005, so 1 million duplicates equal $5,000 per day, or about $1.8 million per year, billed twice to advertisers or reported incorrectly. The fix is deduplication on an impression ID. To hold the IDs of 24 hours, 1 billion IDs at 16 bytes need 16 GB for raw bytes (roughly 40 to 50 GB in a hash set with overhead), which is affordable in a keyed state store or a table. A Bloom filter would use under 2 GB, but with a 1% false-positive rate it would drop 1% of real impressions as "seen already", which is a loss and not acceptable for billing.
intuition: Did you tick the task off the list before you did it, or after? Before means a crash can lose the task, after means a crash can repeat it.
The design follows from one fact: two things cannot be done atomically over a network without extra machinery. One thing is the work and the other is the record of the work, and a crash can fall between them. You pick which mistake you prefer. Then, if you cannot accept either, you either make the work safe to repeat (idempotence) or you make the work and the record one thing (a transaction). All the exactly-once systems are one of these two tricks, wearing different clothes.
mistakes: People often think exactly-once delivery is a setting that you switch on. In fact it is an end-to-end property that holds only if every hop cooperates: an idempotent or transactional producer, a read-committed consumer, and a sink that is idempotent or part of the transaction. A side effect that is not covered, such as sending an email or calling an external API, can still happen twice.
People often think at-least-once is bad and at-most-once is safe. In fact each is right for a different loss. A payment pipeline cannot lose events, so it takes at-least-once plus deduplication. A noisy metrics stream can accept some loss to avoid the complexity and latency of acknowledgements.
People often think Kafka's idempotent producer removes all duplicates. In fact it removes duplicates caused by retries in one producer session to one partition. If the application itself resends data after a restart (a new producer ID), or if the upstream source produces duplicates, the broker cannot tell. You need transactions with a stable transactional.id or an application-level ID.
People often think auto-commit of consumer offsets is "exactly once". In fact the Kafka consumer's default auto-commit commits offsets on a timer (every 5 seconds). A crash can then lose messages that were committed but not processed, or repeat messages that were processed but not yet committed, depending on timing. Without careful handling, it should be treated as at-least-once at best.
friction: Exactly-once has a cost. Transactions add latency (a commit round trip and waiting for markers), reduce throughput somewhat, and a consumer reading read_committed must wait behind the oldest open transaction (the last stable offset), so one slow producer holds back everyone. Two-phase-commit sinks hold transactions open between checkpoints, so end-to-end latency becomes at least the checkpoint interval.
Duplicate handling needs state. A deduplicating consumer must remember IDs for as long as duplicates can arrive, which can mean tens of GB per day, expiration rules, and the question of what happens when a duplicate arrives after its ID has expired. Queues such as SQS FIFO have short windows (five minutes), so a duplicate after the window is not caught.
Effects outside the system defeat guarantees. Calls to external APIs, emails, payments through a third party, and non-transactional databases need idempotency keys from the external service, and not all of them offer them. Ordering can also change under retries and partition rebalances, and a consumer-group rebalance can make two consumers process the same message for a short time.
practice: Decide, for each hop, which loss you prefer: duplicate or drop. Default to at-least-once plus idempotent consumers. Give every event a unique ID at the source (a UUID or a deterministic hash of the key fields), carry it through the pipeline, and use it for upserts, MERGE statements and deduplication windows. In lakehouse tables, MERGE INTO on the event ID, or a dropDuplicates with a watermark in Structured Streaming, handles replays.
In Kafka, keep the idempotent producer on (default since 3.0), use acks=all and a sensible delivery.timeout.ms, and set min.insync.replicas so that an acknowledged write is durable. For consumers, disable auto-commit when processing has side effects, commit after processing (commitSync or commitAsync with care), and handle rebalances by committing before partitions are revoked. Use transactions and read_committed for Kafka-to-Kafka pipelines, and exactly_once_v2 in Kafka Streams. For non-Kafka sinks, use a transactional sink, the outbox pattern (write the event in the same database transaction as the state change, then publish from the outbox), or idempotent writes. Test the failure paths by killing consumers between processing and commit, and reconcile source and sink counts every day.
tradeoffs: At-most-once or at-least-once. Choose at-most-once when the data is statistical, loss of a small fraction does not change decisions, and you want lowest latency and no deduplication state (telemetry, sampled logs). Choose at-least-once when each event matters (billing, orders, user actions) and you can handle duplicates downstream. You give up completeness in one and simplicity in the other.
Idempotent sink or Kafka transactions. Choose an idempotent sink (upserts keyed by event ID) when the destination supports it cheaply: it is simple, has no coordinator and works across any system. Choose transactions (or two-phase commit sinks) when outputs are appends without natural keys, when you must see all of a batch or none of it, or when the destination is Kafka. You give up latency and some throughput with transactions, and you give up generality with idempotent sinks.
Deduplication window size. Choose a window longer than the longest delay and replay you expect (a day or more for streaming with retries), because a duplicate that arrives after its ID has expired is processed again. A longer window costs memory or storage in proportion. Choose a short window (minutes) only when retries happen quickly and a late duplicate is acceptable.
interview: Why can't a system guarantee exactly-once delivery over an unreliable network? || Because the sender cannot tell a lost message from a lost acknowledgement. If it retries, it may duplicate; if it does not, it may lose. Practical systems give at-least-once delivery and obtain exactly-once effects with idempotent operations or atomic commits of the effect and the progress.
How does Kafka's idempotent producer prevent duplicates, and what are its limits? || Each producer has an ID, and every batch to a partition carries a sequence number. The broker accepts the next expected number and rejects repeats, so retries do not duplicate and order is kept. It covers one producer session and one partition; a restarted producer with a new ID or duplicates created upstream are not covered.
Explain how a Kafka transactional consumer-process-producer loop achieves exactly-once. || The producer writes outputs and the consumed offsets to the offsets topic in one transaction, identified by a stable transactional.id; the epoch fences zombie instances. Commit or abort markers make records visible only to read_committed consumers. After a crash the transaction is aborted and the batch is reprocessed, so output and progress are atomic.
Your consumer has a rebalance during processing. How can this produce duplicates and how do you handle it? || Partitions can move to another consumer before the first has committed its progress, so the new owner reprocesses messages. Commit offsets in the rebalance listener before partitions are revoked, keep processing idempotent, and use cooperative rebalancing and short poll loops. With transactions, the epoch fences the old owner.
How would you deduplicate 1 billion events a day with a 24-hour window? || Keep a keyed state or table of event IDs with a TTL of 24 hours (about 16 GB raw, more with overhead), or use an upsert/MERGE on the event ID in the sink. A probabilistic filter is not safe for billing because false positives drop real events; it can be used only as a fast pre-check before an exact lookup.
quiz: Which order of actions gives at-least-once for a consumer? || Process the message first and commit the offset afterwards; a crash between the two repeats the work after a restart.
Why does a lost acknowledgement cause a duplicate? || The sender cannot tell that the message arrived, so after a timeout it sends the message again, and the receiver stores or processes it a second time.
An ad pipeline has 500 million events per day and 0.2% duplicates. How many duplicates per day? || 500,000,000 × 0.002 = 1,000,000 duplicates per day.
What do transactional.id and the epoch do in Kafka transactions? || The transactional.id identifies a producer across restarts, and the epoch increases when a new instance starts, so the broker can fence off (reject) writes from an older zombie instance.
Why is a Bloom filter a poor choice for billing deduplication? || A Bloom filter has false positives, so it would mark some new events as already seen and drop them, causing silent loss; it can serve only as a pre-check before an exact lookup.

@@ backpressure
value: Backpressure is a way for a slow part of a system to tell the fast part in front of it to slow down. When a producer sends data faster than a consumer can handle it, the extra data has to go somewhere. It can pile up in memory until the process dies, it can be dropped, or the producer can be made to wait. Backpressure is the third choice: the pressure from the slow stage travels backwards through the pipeline until it reaches the source, and the source sends only as fast as the slowest stage can accept.
Every data system has this problem because stages never run at exactly the same speed, and speeds change: a garbage-collection pause, a slow database write, a hot key, a traffic spike. Without a control, the first symptom is growing queues and rising latency, and the final symptom is an out-of-memory crash or a flood of timeouts and retries that makes everything worse. Stream processors (Flink, Spark, Kafka Streams), message queues, HTTP services and reactive libraries all contain some form of this control.
For the layer above (message queues, where prefetch limits and bounded queues protect consumers, and stream processing, where slow operators must slow their sources), backpressure is what turns a pipeline of independent stages into a system that stays stable under load. Two concepts below it supply the parts. TCP (L3) is the original example: the receiver advertises a window of how much data it can accept, and the sender may not exceed it. The same idea (a credit) is reused at higher layers. Queues and ring buffers (L3) supply the bounded buffer: a fixed-size queue between two stages, which makes "full" an observable event that can block, reject or signal the producer.
terms: Backpressure — a signal or mechanism by which a slow consumer limits the rate of a faster producer.
Bounded buffer — a queue with a fixed capacity; when it is full the producer must wait, drop or fail.
Credit-based flow control — the receiver gives the sender a number of credits (free buffers); the sender sends only as many units as it has credits.
Pull-based consumption — the consumer asks for data when it is ready, so the producer cannot overrun it (Kafka consumers fetch; they are not pushed to).
Load shedding — deliberately dropping or rejecting some work when the system is overloaded, to protect the rest.
Lag — how far a consumer is behind the head of a log, measured in messages or time.
Little's law — in a stable system, the average number of items inside equals the arrival rate times the average time each item spends there.
Head-of-line blocking — one slow item at the front of a queue delays every item behind it.
history: Flow control is as old as networks. TCP's sliding window was in the first TCP specifications of the late 1970s, and Van Jacobson's congestion control work (1988) added a second limit that reacts to network loss. The receiver window (flow control) protects the receiver, and the congestion window protects the network. These two ideas were the first working backpressure systems, and every later design borrows from them.
Unix pipes gave programmers the bounded buffer in 1973: a pipe holds a fixed amount of data (64 KB on Linux today), and a writer blocks when it is full. This is why `producer | consumer` shell pipelines never run out of memory. Message brokers added prefetch limits and acknowledgements (AMQP, 2000s). In the streaming era, early systems often left operators to guess limits. Spark Streaming 1.5 (2015) added a rate controller based on a PID controller (spark.streaming.backpressure.enabled).
The Reactive Streams initiative (2013 to 2015, from Netflix, Lightbend, Pivotal and others) defined a small standard for asynchronous streams with non-blocking backpressure: a subscriber calls request(n), and the publisher sends no more than n items. It became part of Java 9 as the Flow API (JEP 266, 2017). Apache Flink introduced credit-based flow control in version 1.5 (2018), replacing a design where a blocked receiver also blocked other streams that shared the same TCP connection. Flink 1.14 (2021) added buffer debloating, which tunes the amount of data in flight to about one second of work. Large-scale outage analysis since then (for example the work on "metastable failures", 2021) has shown that overload plus retries is a leading cause of long outages, which makes backpressure and load shedding a design concern for the whole service, not only for the data path.
how: Backpressure needs three things: a limit on how much work is in flight, a way to observe that the limit is reached, and a way to pass that fact upstream. Different systems choose different forms of each.
The bounded buffer. The simplest form is a queue of fixed size between two stages. When the consumer is slow, the queue fills. A full queue makes the producer's put() call block (in-process), or fail (return an error), or drop. Blocking is a backpressure by itself: the producer thread stops, so it stops producing. If that producer is itself a consumer of an upstream queue, its input queue then fills, and the pressure moves one stage up, and so on to the source. The queue size is a design decision. Little's law says that the delay added by a full queue is its size divided by the consumer rate. A buffer of 1,000 items and a consumer rate of 8,000 per second adds at most 125 ms.
Window and credit protocols. When the stages are on different machines, blocking a thread is not enough. The receiver must tell the sender how much it can accept. TCP does this with the receive window carried in every acknowledgement: the sender can have at most that many unacknowledged bytes in flight, and a window of 0 stops it completely. HTTP/2 repeats the idea per stream and per connection, with WINDOW_UPDATE frames and an initial window of 65,535 bytes. Flink uses credits. The network buffers are 32 KB segments. Each input channel keeps a few exclusive buffers (2 by default) and can borrow floating buffers from a shared pool. The receiver tells the sender its credit, equal to the number of free buffers. The sender sends only while it has credit, and also tells the receiver how much data it has queued (its backlog) so that the receiver can ask for more floating buffers. When an operator is slow, its input buffers fill, credit falls to zero, the upstream task's output buffers fill, and its own processing thread blocks when it cannot get an output buffer. Backpressure then reaches the source task, which stops reading from Kafka. Credits are per channel, so one slow channel does not stop the other channels that share the TCP connection.
Pull-based consumption. In a pull model the consumer decides when to read. A Kafka consumer calls poll() and receives at most max.poll.records records; if it is slow, it simply polls less often, and the data waits safely in the broker log. Here the log is the buffer, and the broker is the place where pressure becomes lag. Spark Structured Streaming also pulls: options such as maxOffsetsPerTrigger or maxFilesPerTrigger bound the size of each micro-batch, so a backlog is worked off at a controlled speed. Reactive Streams is a pull/push hybrid: the demand signal request(n) travels upstream, and data flows downstream only up to that demand.
Rate controllers. Some systems measure and adjust. Spark's old DStream backpressure tracks batch processing time and sets the maximum rate for the next batch so that processing keeps up with arrival (a PID controller). Flink's buffer debloating measures throughput and sizes the in-flight buffers so that roughly one second of data is queued. Kafka brokers enforce quotas by byte rate per client: when a client exceeds its quota, the broker delays its response (and tells it with throttle_time_ms), so the client slows down without errors.
When pressure cannot propagate. Some sources cannot be slowed down: user requests arriving over HTTP, or ad bid requests that must be answered within about 100 ms. For these, the system must shed load: reject early with a 429 or 503, answer "no bid", sample, or drop the oldest or lowest-priority work. This is backpressure's last resort, and it is a business decision (what is the cheapest thing to drop?). Another option is to put a durable log (Kafka) between the uncontrollable source and the slow processor, which converts pressure into lag. Lag can be watched and cleared later.
What the lower layers add. TCP shows that a receiver window is enough to make a whole network stable, and it shows the danger as well: when a receiver stops reading, a sender can be blocked completely. Queues and ring buffers give the means: a bounded ring buffer has a fixed cost, makes overflow explicit, and is cheap to check, so every stage can ask "is there room?" in constant time.

example: A pipeline has a source that produces 10,000 messages per second (1 KB each) and a consumer that can handle 8,000 per second.
Unbounded queue. The queue grows by 2,000 messages per second, which is 2 MB/s, or 7.2 GB per hour. On a process with an 8 GB heap, memory is gone in roughly an hour, and garbage collection pauses before that make the consumer even slower, which accelerates the collapse. Latency grows steadily as well. After 30 minutes the queue holds 3.6 million messages, and a new message waits 3,600,000 / 8,000 = 450 seconds, 7.5 minutes, before it is processed. Users see old data and timeouts, and retries add more load.
Bounded queue of 1,000 messages with blocking. The producer blocks whenever the queue is full. Throughput is 8,000 messages per second, equal to the consumer's rate, and no memory grows. The waiting time of a message is at most 1,000 / 8,000 = 125 ms. The 2,000 messages per second that the source wanted to send are not lost: if the source is a Kafka topic, they stay in the log, and the consumer lag grows by 2,000 messages per second (7.2 million per hour) while the log sits safely on disk. If the source is an HTTP client, it sees slow responses or errors and should back off.
Add stages. With three stages that can handle 12,000, 5,000 and 8,000 per second, the slowest sets the throughput at 5,000. The queue before the 5,000 stage fills first; its upstream stage blocks; its upstream queue fills; and the source is held back to 5,000 per second. The 8,000 stage runs at 62% of its capacity, which is fine. Queueing theory explains why you do not want it near 100%: in a simple M/M/1 queue the mean wait in units of service time is ρ/(1 − ρ), which is 4 at 80% utilisation, 9 at 90%, and 99 at 99%. Latency grows sharply near saturation, so a bounded queue and load shedding keep the pipeline in the good part of the curve.
Load shedding. A bidder gets 50,000 requests per second and each must be answered in 100 ms. A worker pool handles 40,000 per second. Queuing the extra 10,000 per second would deliver answers after the deadline, so they would be worthless. The right action is to reject the excess immediately, at the edge, with a fast "no bid", and to prefer to drop the cheapest or lowest-value requests.
intuition: A traffic light on a highway on-ramp: let cars in only as fast as the road ahead can take them.
The design is natural because the other choices are worse. A queue between two stages is a promise to hold data that nobody is ready for. If the promise has no limit, it is a promise the machine cannot keep. If the promise is limited, then the only questions are what to do when the limit is reached, and who must be told. Telling the producer is the cheapest and most precise answer, since the producer is the one who can stop. The approach is also self-adjusting: the pipeline runs at the speed of its slowest part, without a central controller, because each stage only needs to know whether the next one has room.
mistakes: People often think a bigger buffer solves overload. In fact a bigger buffer only delays the failure and adds latency. If the average arrival rate exceeds the average service rate, any finite buffer fills eventually, and a larger one means the delay (size divided by service rate) is larger when it does. Buffers help with bursts, not with sustained overload.
People often think backpressure is the same as dropping data or rate limiting. In fact backpressure slows the producer without losing data (the producer waits), rate limiting caps a rate regardless of the consumer's state, and load shedding drops data. They are used together: backpressure where the source can wait, shedding where it cannot.
People often think Kafka consumers need backpressure handling. In fact Kafka's pull model already provides it: a slow consumer reads less, and the data stays in the log, which is why the right metric is consumer lag. The remaining problems are in the processing after the poll (for example, a large poll batch that takes longer than max.poll.interval.ms causes a rebalance).
friction: Backpressure propagates, and the propagation is itself a risk. A slow sink (a database under load) can stall a whole job and all its upstream sources, and a single slow partition or hot key can hold back the whole stage. Diagnosing it takes work: the slow stage is the one that is busy at 100% and has full input buffers, while all stages upstream show high back-pressured time. Flink reports busyTimeMsPerSecond, idleTimeMsPerSecond and backPressuredTimeMsPerSecond per task for this reason.
Backpressure interacts with other mechanisms. In Flink, checkpoint barriers travel in the same buffers as data, so under backpressure a barrier waits behind queued records and checkpoints become slow or time out. Unaligned checkpoints and buffer debloating exist to reduce this. Timeouts and retries make it worse: if a stalled client retries, load increases exactly when the system is weakest (a retry storm). Cyclic dataflows can deadlock when every buffer on the cycle is full.
Not everything can be slowed down. Real-time sources, user traffic and sensor feeds cannot wait, so some data is dropped or delayed, and deciding what is a product decision. A durable buffer in front of the processor turns the problem into a lag you must watch and a catch-up capacity you must pay for. The lag also means results are late, which may break downstream deadlines.
practice: Make every queue bounded and decide, in advance, what happens when it is full: block, reject with an error, or drop (and which items). Search for hidden unbounded queues: thread-pool work queues, async client buffers, in-memory batch lists, and log appenders.
For streaming jobs, size the system for the peak sustained rate, not the average, and watch the metrics that show pressure: consumer lag, queue depth, back-pressured time, and end-to-end latency. In Flink, find the bottleneck as the first task that is busy while its upstream tasks are back-pressured, then fix the cause (a hot key, a slow external call, too little parallelism) rather than raising buffers. Use async I/O with a bounded number of in-flight requests for external lookups, and enable buffer debloating if checkpoints are slow under load.
For Spark Structured Streaming, bound the work per micro-batch with maxOffsetsPerTrigger or maxFilesPerTrigger, so that a backlog drains at a steady rate. On Kafka, control consumers with max.poll.records, fetch sizes and pause()/resume(), and use quotas to keep a noisy client from harming others. For services, set concurrency limits and timeouts, return 429 or 503 early when saturated, use exponential backoff with jitter on clients, and cap retries with a budget. For real-time bidding or similar deadline systems, shed at the edge before the work is queued.
tradeoffs: Block, drop or buffer. Choose blocking (true backpressure) when the producer can wait, data must not be lost and delay is acceptable (batch and stream jobs reading from a log). Choose dropping or shedding when data has a deadline or lower value after it (real-time bidding, live telemetry) and late work is worthless. Choose a larger durable buffer (Kafka) when you need to absorb bursts for minutes to hours and can afford storage and the lag. You give up latency, completeness or money respectively.
Small or large buffers. Choose small buffers (tens to thousands of items, or about one second of data) when you want low latency and a fast backpressure signal. Choose larger buffers when the workload is bursty and throughput matters more than latency, and when you can accept longer delays and more memory. Large buffers also hide problems for longer.
Push, pull or credit-based. Choose pull when the consumer is a batch-like worker that reads from a durable log: it is simple and safe. Choose credits (Flink-like) or request(n) for continuous low-latency streams between processes, where you want the sender to be fast but never ahead of the receiver. Choose plain push with shedding at the very edge where the sender is uncontrollable. Credits cost protocol complexity and a round trip of signalling.
interview: What happens in a streaming pipeline when one operator slows down, and how does the system react? || Its input buffers fill, so its upstream sender runs out of credit and its own output buffers fill. The upstream operator blocks, and the effect repeats up to the source, which reads less from Kafka. The pipeline runs at the speed of the slowest stage, and the data waits in the log as lag.
Why is an unbounded in-memory queue between stages dangerous even if average rates are balanced? || Bursts, pauses and variable service times make the queue grow without a bound, so latency rises and memory is exhausted. By Little's law the delay equals queue length over service rate, so a long queue means stale data. A bound turns this into a visible, controlled signal.
How does Flink's credit-based flow control improve on relying on TCP's window alone? || TCP's window is per connection, and Flink multiplexes many logical channels on one connection, so a full receiver for one channel would block the others. Credits are per channel, based on free buffers, so only the slow channel stops, and the sender can also announce its backlog so the receiver allocates floating buffers.
A checkpoint times out under heavy load. What is the likely link to backpressure and what options do you have? || Barriers travel behind data in the same buffers, so with full buffers a barrier is delayed and alignment takes long. Options: remove the bottleneck, enable unaligned checkpoints and buffer debloating, reduce parallelism imbalance and data skew, and tune the checkpoint timeout.
How would you protect an ad bidder from overload? || Bound the in-flight work, use a short queue with a deadline check so that stale requests are dropped, shed excess at the edge with a fast no-bid, prefer high-value traffic, use concurrency limits that adapt to latency, and expose metrics on shed rate. Queuing past the deadline wastes work.
quiz: What are the three things a backpressure scheme needs? || A limit on in-flight work (a bounded buffer or window), a way to observe that the limit is reached, and a way to pass that signal upstream to the producer.
Why does a bounded queue keep latency bounded? || A message waits at most the queue size divided by the consumer rate, so a 1,000-item queue with an 8,000/s consumer adds at most 125 ms.
A source sends 10,000 msg/s into a consumer that handles 8,000 msg/s with an unbounded queue of 1 KB messages. How fast does memory grow? || 2,000 messages per second, which is 2 MB/s or about 7.2 GB per hour.
In an M/M/1 queue, how does mean waiting time change from 90% to 99% utilisation? || The wait in service-time units is ρ/(1 − ρ): about 9 at 90% and 99 at 99%, so latency grows by roughly 11 times for a 9-point rise in load.
When is load shedding better than backpressure? || When the source cannot wait and the work has a deadline, such as real-time bids or user requests; late work is worthless, so it is better to reject early than to queue.

@@ watermarks
value: Events do not arrive in the order in which they happened. A phone sends a click at 9:04:50, but it loses signal and the click reaches the server at 9:09. A stream processor that wants to count "clicks per 5-minute window of event time" must decide when the window 9:00 to 9:05 is complete and its count can be emitted. It cannot wait forever, because it never knows whether another late event is on the way. A watermark is the system's answer. It is a moving timestamp W with the meaning: "I believe I have now seen all events with event time earlier than W." When W passes the end of a window, the window is closed and its result is emitted.
Watermarks make a trade between completeness and latency. A watermark that is too cautious (it assumes events can be very late) keeps windows open for long and delays results. A watermark that is too bold closes windows early, and events that arrive afterwards are late: they are dropped, put aside, or used to correct an earlier result. No setting is right for all data, because the watermark is a guess about a process that nobody controls: networks, mobile devices, retries, clock drift.
For the layer above (stream processing, where windows, joins and timers in event time all depend on it), the watermark is the only notion of "time has passed" that is based on the data and not on the wall clock. The concepts below explain why it is hard and how it is set. Distributed systems theory (L3) explains that there is no global clock and no instant way to know what other nodes have sent, so completeness can only be estimated. Statistics (L4) provides the estimation: a good lateness bound is a quantile of the observed delay between event time and arrival time.
terms: Event time — the time at which an event happened, as recorded in the event itself (for example by the phone).
Processing time — the time at which the stream processor sees the event; depends on delays and load.
Watermark — a timestamp W flowing through the stream with the claim that no events with event time earlier than W are expected anymore.
Out-of-orderness bound — the maximum lateness assumed by a heuristic watermark: watermark = highest event time seen minus this bound.
Late event — an event that arrives after the watermark has passed its event time.
Allowed lateness — extra time after the watermark passes a window's end during which late events still update the window result.
Side output — a separate stream that receives events that are too late to be included.
Idle source — an input partition that sends no events, and so sends no watermark advance, which can hold the watermark of the whole job back.
history: The problem was recognised in database research on data streams in the early 2000s. Systems such as Aurora and STREAM talked about out-of-order arrival and heartbeats, which are signals that say "no earlier timestamp will come". The practical form came from Google. In MillWheel (VLDB 2013), the stream system behind Google's production pipelines, each computation tracked a "low watermark" for its data: a lower bound on the timestamps of events that could still arrive, computed from the oldest pending work in all upstream stages and from the sources. Computations used it to know when it was safe to emit results.
The Dataflow Model paper (Akidau et al., VLDB 2015) generalised this into a model that separates four questions: what is computed, where in event time (windows), when in processing time results are emitted (triggers, including watermarks), and how refinements relate (accumulation modes). It also named the key distinction: a perfect watermark is possible only if you know everything about the source, and in all other cases the watermark is a heuristic. Tyler Akidau's "Streaming 101 and 102" posts (2015 and 2016) and the book "Streaming Systems" (2018) made these ideas the standard vocabulary.
The open-source engines followed: Apache Flink treated event time and watermarks as a core feature from its early versions (2015), and Apache Beam (2016) is the open-source form of the Dataflow Model. Spark added watermarking to Structured Streaming in Spark 2.1 (2017). Kafka Streams has a related but simpler design that uses record timestamps and a "grace period" for late records.
how: A watermark system has three parts: how watermarks are produced at sources, how they flow and combine through the dataflow, and what operators do with them.
Production at the source. Each event carries an event time. A source (or a watermark generator placed after it) estimates the watermark. The most common heuristic is the bounded-out-of-orderness rule: W = (highest event time seen so far) − B, where B is the chosen bound. In Flink this is WatermarkStrategy.forBoundedOutOfOrderness(Duration), and the watermark is emitted periodically (every 200 ms by default), not for every event. Spark Structured Streaming uses the same rule, written as withWatermark("eventTime", "10 minutes"). If the source has a known order, the watermark can be exact: a file whose records are sorted, or a Kafka partition with a monotone timestamp, gives a perfect watermark equal to the last event time.
Propagation. Watermarks travel through the dataflow along with the data. A rule keeps them correct: an operator's output watermark is the minimum of its input watermarks (and cannot pass the timestamp of any state it still holds). If a stage has four input channels at watermarks 9:05, 9:07, 9:02 and 9:06, its watermark is 9:02, because the slowest input could still send events up to that point. Flink applies this per source partition: each Kafka partition produces its own watermark, and the task takes the minimum over the partitions it reads. Spark Structured Streaming instead tracks one maximum event time per stream, and with several input streams uses the minimum of their watermarks by default. A partition that receives no events does not advance its watermark and can hold the minimum back for the whole job. Flink's withIdleness(Duration) marks such an input idle after a timeout and leaves it out of the minimum, so the other inputs can move time forward.
Use in operators. An event-time window [start, end) fires when the watermark reaches end. A timer registered for time T fires when the watermark reaches T. A stream-stream join with a time condition can drop state older than the watermark. In Spark, watermarks let the engine remove state for old windows, and in append output mode a window result is emitted only after the watermark passes its end. In Flink, window state is kept until the watermark passes end plus allowed lateness, and then cleaned up.
Late data. An event with event time earlier than the current watermark is late. The options are: drop it (the default in many engines), send it to a side output for separate handling, or, if it is within the allowed lateness, update the window and emit a new, corrected result (a "late firing"). Dataflow/Beam express these choices as triggers (early firing, on-time firing, late firing) with an accumulation mode (discarding, accumulating or retracting). The choice decides whether downstream consumers see a single final answer or a series of corrections.
Choosing the bound. This is where statistics enters. Measure the lateness of real events, which is arrival time minus event time, over some days, and look at the percentiles. If p99 is 10 s, p99.9 is 90 s and p99.99 is 20 minutes, a bound of 2 minutes closes windows 2 minutes late and treats about 0.1% of events as late. A bound of 20 minutes makes only 0.01% late but delays every result by 20 minutes. There is no free value, and the long tail (devices offline for hours) decides the cost. A common design is to use a modest bound for fast, approximate results, and to correct the tail with a batch job or with late-data updates.
Why completeness can only be estimated. Distributed systems theory says that without a global clock and without bounds on message delay, an observer cannot know that nothing more is coming. The watermark is therefore a hypothesis, derived from assumptions about delay. Mobile and TV devices make it clearer: their clocks can be wrong, they buffer events while offline, and they send in bursts when they reconnect. Event times from devices need validation against server time, or one device with a clock set to 2030 will push a max-based watermark far into the future and cause every normal event to look late.

example: Use the diagram. The job counts events in tumbling windows of 5 minutes, using event time and a watermark with a bound of 2 minutes.
Event e1 has event time 9:01:10 and goes into the window [9:00, 9:05). The highest event time seen is 9:01:10, so the watermark is 8:59:10. Event e2 (9:04:50) goes in the same window and moves the watermark to 9:02:50. Event e3 has event time 9:03:20 but arrives after e2. It is out of order, but the watermark (9:02:50) is still earlier than its event time, so it is accepted into the window. This is what the bound is for.
Event e4 (9:06:05) belongs to the next window [9:05, 9:10). It raises the watermark to 9:04:05, which is still before 9:05:00, so the first window stays open. Event e5 (9:07:30) moves the watermark to 9:05:30. The watermark is now at or after the window end, so the engine fires window [9:00, 9:05) with the count 3 (e1, e2, e3) and can drop its state. The result was emitted at roughly the moment the stream reached 9:07:30 in event time, about 2.5 minutes after the window end: that gap is the price of the 2-minute bound.
Now e6 arrives with event time 9:04:10. It belongs to the closed window, and its event time is before the watermark 9:05:30. It is late. With default settings it is dropped, and the emitted count 3 stays wrong by one. With 1 minute of allowed lateness (so cleanup happens when the watermark passes 9:06:00), the engine would still hold the window state, would add e6, and would emit a corrected count of 4. With a side output, e6 goes to a separate stream that a batch job can use to fix the totals.
Now size the bound from data. A CTV pipeline measures lateness (arrival minus event time) over a week: p50 2 s, p99 40 s, p99.9 3 minutes, p99.99 45 minutes. A bound of 3 minutes marks about 0.1% of events late. At 1 billion events per day, that is about 1 million late events per day. If a window result is useful only within 5 minutes, the 3-minute bound spends most of that budget; a bound of 1 minute (between p99 and p99.9, about 0.5% late) gives faster results and sends more corrections to the batch path. Then compute what a late event costs: if each late event is worth $0.005 of billing, 1 million per day is $5,000, and a nightly batch reconciliation is the right tool for the tail, not a 45-minute watermark.
intuition: "I will publish the 9:00 to 9:05 count when I am fairly sure nobody is still mailing in a 9:04 receipt."
The idea is natural because the alternatives are worse. Wall-clock time does not measure the data: a delay in the network changes the results. Waiting for certainty is impossible, because you can never prove that no late event exists. So you need a rule that says "after this point I will assume the past is complete", and a way to handle the exceptions. The watermark packages that rule as a number that moves through the pipeline like any other piece of data, so that every operator shares one idea of how far time has advanced.
mistakes: People often think a watermark guarantees that no late data will arrive. In fact it is a heuristic assumption. Events with event time before the watermark can and do arrive. The watermark only fixes the moment when the system stops waiting and decides what to do with them.
People often think the watermark is based on the wall clock. In fact it is derived from event times in the data (highest event time minus the bound), so it advances only when data arrives. If the stream stops, the watermark stops, and the last windows never fire unless the system injects idle handling or a final watermark.
People often think a bigger out-of-orderness bound is always safer. In fact it only moves the trade: every window result is delayed by the bound, and state grows because windows stay open. The right bound comes from measured lateness percentiles and the latency the consumer needs.
People often think one slow or bad source affects only itself. In fact the watermark of an operator is the minimum over inputs, so one idle or slow partition holds everything back, and a single event with a far-future timestamp can push a max-based watermark so far ahead that normal data becomes late. Validate timestamps and use idleness detection.
friction: Watermarks are heuristics, and tuning them is a continuous job. Distribution of lateness changes with releases, outages and traffic patterns, and a bound that was right last month may drop data today. You need metrics: the lateness distribution, the count of late and dropped events, the lag between the watermark and wall-clock time, and the age of the oldest open window.
Correctness is split between the stream path and a repair path. Events later than any practical bound exist (a TV that was off for a week), so exact results need either a long allowed lateness with large state, or a batch correction (a lambda-like pattern or a re-aggregation of the affected days). Output semantics also matter: a pipeline that emits corrections (updates) needs sinks that can apply upserts or retractions, while an append-only sink needs the final answer once.
Watermarks interact with the rest of the system. They depend on every source and stage doing its part: a stage that buffers events or holds state must hold the watermark back, or downstream results are wrong. Joins across streams use the minimum of the two watermarks, so a slow stream slows both. In Spark, a watermark is computed from the previous batch, so the effect of an event is seen one trigger later. Different engines also define watermark semantics differently (per-partition minimum in Flink, global maximum in Spark), which makes porting a job a source of surprise.
practice: Use event time whenever results must be reproducible and independent of delays, which is true for most analytics. Make sure each event carries a trustworthy timestamp, and clamp or reject values far in the future or past. Decide the bound from measured data: collect arrival-minus-event-time percentiles, choose the bound that covers p99 to p99.9 and meets the latency need, and send the rest to a side output or a correction job.
Set up idleness handling for sources with uneven traffic (withIdleness in Flink, or fewer partitions than keys), and watch for stuck watermarks. In Flink, assign watermarks per Kafka partition, in the source, so that ordering inside a partition is used. In Spark, remember that the threshold is the maximum lateness the engine promises to handle; later data may or may not be dropped, so do not rely on dropping for correctness. Use a modest allowed lateness to get corrected results for the common slightly-late events, only if your sink can handle updates.
Monitor: watermark lag (wall clock minus watermark), late-event counts and rate, the number of open windows, and state size. Alert when the watermark stops advancing. Test with replayed data that includes disorder (shuffle a day of events within a few minutes and with a long tail) and compare results with a batch computation of the same data.
tradeoffs: Small or large out-of-orderness bound. Choose a small bound (seconds to a minute) when freshness matters (dashboards, alerting, real-time bidding feedback) and you can fix the late tail with another path. Choose a large bound (minutes to hours) when completeness matters (billing, reporting) and the consumer can wait. You give up completeness or latency; the percentile table of your own data decides the point.
Event time or processing time. Choose event time when results must not depend on delays and replays must give the same numbers. Choose processing time when you only need an operational view of what the system saw in the last minute, for monitoring or rate limits, and want no watermark machinery. Processing time is simpler and cheap, and its results change when the pipeline is slow.
Drop, side output or update late events. Choose dropping when late data is rare or does not matter. Choose a side output when a batch job can repair totals later. Choose updating windows (allowed lateness) when consumers can accept corrections, and you can afford to keep window state longer. Updates cost state and need idempotent or upsert sinks.
Heuristic or perfect watermarks. Choose perfect watermarks when the source gives order guarantees (a sorted file, a single ordered log per key) because you can then close windows exactly. Choose heuristic watermarks in all other cases, and check them against data. A perfect watermark costs ordering constraints on the source; a heuristic costs occasional wrong results.
interview: What is a watermark and what exactly does it promise? || It is a timestamp flowing in the stream that says the system does not expect events with earlier event time. It is a heuristic, not a guarantee: late events can still arrive. It lets operators close event-time windows and clean up state at a chosen moment, trading completeness against latency.
How is the watermark computed in a job with four Kafka partitions, and what can go wrong? || Each partition has its own watermark (highest event time minus the bound), and the operator takes the minimum over partitions. An idle or slow partition holds back the minimum and stops all windows from firing, unless the idle partition is excluded with idleness detection. A bad far-future timestamp can push a partition's watermark too far ahead.

Send the remaining tail to a side output and repair it in batch. Revisit the choice when the lateness distribution changes.
What happens to an event that arrives after its window has fired, and what are the options? || It is late. The engine can drop it, route it to a side output, or, within allowed lateness, update the window and emit a corrected result. The choice depends on whether the sink supports updates and how much state you can keep.
Why can Spark's and Flink's watermarks behave differently on the same data? || Flink computes watermarks per source partition and takes the minimum, so a slow partition delays windows but its data is not dropped. Spark Structured Streaming uses the highest event time seen across the stream minus the threshold, so events from a slow partition can fall behind the watermark and be dropped.

@@ windowing
value: A stream has no end, so you cannot ask "what is the total?" You can only ask "what is the total for this slice?" Windowing cuts an unbounded stream into finite groups, called windows, so that aggregates such as counts, sums and distinct counts are defined. "Clicks per minute", "impressions per campaign in the last hour" and "events per user session" are all window questions. A window is a rule that assigns each event to one or more groups, together with a rule for when the group's result is emitted.
The three common shapes answer different questions. Tumbling windows are fixed-size and do not overlap (every 5 minutes), and give a clean time series. Sliding (hopping) windows overlap (the last 5 minutes, updated every minute), and give smooth rolling metrics. Session windows have no fixed size: they group events from the same key that follow each other with gaps shorter than a limit, and a long gap closes the session. Windows can use event time (when the event happened) or processing time (when the system saw it). Event-time windows give reproducible answers but need watermarks to know when to close.
For the layer above (stream processing, where windows are the standard tool for aggregation, joins and deduplication), windowing turns an infinite log into a sequence of small, finite batch problems, so that familiar operations apply. The layer below is queues and buffers (L3). A window is a buffer of events (or of partial results) grouped by time, and efficient implementations use ring buffers of per-slice partial aggregates, so that a sliding window can add new data and drop expired data in constant time per step. The neighbouring concept, event time and watermarks, decides when each window is complete.
terms: Window — a finite group of events defined by time (or count) over an unbounded stream.
Tumbling window — fixed-size, non-overlapping windows; each event is in exactly one.
Sliding (hopping) window — fixed-size windows that start every "slide" interval; with size 5 min and slide 1 min, each event is in 5 windows.
Session window — a window per key that extends while events keep arriving within a gap, and closes after a gap of inactivity.
Trigger — the rule that decides when a window's result is emitted (at the watermark, early, at each event, periodically).
Pane — a slice of time that sliding windows share; a window is the combination of several panes.
Accumulation mode — how later firings relate to earlier ones: discard the old result, accumulate on top of it, or retract the old value and emit a new one.
Allowed lateness — how long after the watermark passes the window end that late events can still change the window.
history: Windows are as old as stream query languages. The CQL language of the STREAM project at Stanford (2003) defined time-based and count-based sliding windows over streams, and systems such as Aurora and Borealis had windowed operators. These systems assumed that events arrived in order, so a window closed when a later timestamp appeared.
The efficiency of sliding windows became a research topic of its own. Li, Maier, Tufte, Papadimos and Tucker's "No Pane, No Gain" (SIGMOD Record, 2005) showed that overlapping windows can share work by splitting time into panes: compute one partial aggregate per pane, and build each window from the partial results. Later work (two-stacks, slicing systems such as Scotty) extended the idea to non-invertible aggregates such as max.
The modern definitions come from Google's Dataflow Model (VLDB 2015), which treated windowing as an independent part of the model (the question "where in event time?") separate from triggering ("when in processing time?"). It added session windows as a first-class kind, with merging, and defined triggers and accumulation modes to handle out-of-order data. Apache Flink (event-time windows with assigners, triggers and evictors), Apache Beam, Kafka Streams (windows with grace periods) and Spark Structured Streaming (the window() function from 2.0, and session_window() from 3.2) implement the same set. Flink SQL later added window table-valued functions (TUMBLE, HOP and CUMULATE) that make windows a part of the SQL language.
how: A windowing operator has four jobs: assign each event to windows, keep state per window, decide when to fire, and clean up.
Assignment. For tumbling windows with size S, the window of an event with timestamp t starts at t − (t mod S) (plus an offset if the windows should be aligned to something other than the epoch). The event belongs to exactly one window. For sliding windows with size S and slide D, the event belongs to ceil(S / D) windows: with a 1 hour window sliding every 1 minute, each event is in 60 windows. For session windows with gap G, each event first creates its own window [t, t + G). The operator then merges overlapping windows of the same key: two events 20 minutes apart with G = 30 minutes produce [t1, t1 + 30) and [t2, t2 + 30), which overlap and merge into [t1, t2 + 30). Session windows therefore need a merge step and cannot be assigned independently of other events.
State. The simplest implementation buffers every event of every open window and computes the result at the end. It is flexible but costly: sliding windows copy each event into many windows. The better way is incremental aggregation: keep an accumulator per window (sum, count, a sketch) and update it as each event arrives. The state per window is then a few bytes, whatever the number of events. For sliding windows, panes cut the cost further: keep one accumulator per slice of length D, and compute each window by combining S / D pane accumulators. For invertible aggregates (sum, count) the window result can be updated by adding the new pane and subtracting the expired one. For non-invertible ones (max, distinct count) the operator merges the panes again, or uses a structure such as two stacks. Mergeable sketches (HyperLogLog for distinct counts, t-digest for quantiles) fit this model well. The pane buffer is naturally a ring buffer of S / D slots, in which the oldest slot is overwritten as time moves forward. That is the contribution of the queue and buffer concepts below.
Firing. A trigger decides when to emit. The default for event-time windows is "when the watermark passes the window end". Other triggers fire early (every minute while the window is still open, to give speculative results), per element, per count, or after late data. The Dataflow Model combines these: for example, "an early firing each minute, an on-time firing at the watermark, and a late firing for each late event within an hour". Each firing produces a pane of output, and the accumulation mode says how the panes relate. In discarding mode each firing contains only new data since the last one. In accumulating mode each firing contains the full window so far, and a downstream consumer replaces its old value. In retracting mode the system sends a retraction of the earlier value, followed by the new one, which is needed when later stages aggregate again.
Cleanup. State for a window must be dropped at some point, or it grows without bound. The rule is: remove it when the watermark passes window end plus allowed lateness. Events that arrive after that are late and are dropped or sent to a side output. This is the connection to watermarks: windows give the events a place, and the watermark decides when the place can be closed.
Event time or processing time. Processing-time windows group events by the clock of the machine that sees them. They need no watermark and fire on timers, and they are cheap. Their results depend on delays, restarts and replays, so the same input can give different outputs. Event-time windows give the same result however the data is delayed and replayed, at the price of watermarks, late-data handling and extra state.
Keys and parallelism. Windows are normally per key (per campaign, per user), so the stream is first partitioned by key and each worker holds the windows of its keys. A hot key puts its state and work on one worker, which is a typical performance problem. Pre-aggregating before the shuffle reduces both the traffic and the skew.

example: Tumbling first. Impressions arrive with event times, and you count per campaign in tumbling 5-minute windows. An impression at 09:04:50 is in [09:00, 09:05). An impression at 09:05:01 is in [09:05, 09:10). Each campaign has one accumulator (a count) per open window. With 10,000 active campaigns and about 2 windows open per campaign (the current one and the one waiting for the watermark), the state is 20,000 counters, a few hundred KB.
Sliding next. The business asks for "impressions in the last hour, updated every minute" per campaign. The window size is 60 minutes and the slide is 1 minute, so each event belongs to 60 windows. A naive operator that adds the event to 60 accumulators does 60 updates per event. At 100,000 events per second that is 6 million updates per second. With panes, each event updates one 1-minute pane (100,000 updates per second), and once per minute for each campaign the operator sums 60 pane counts (or adds the newest and subtracts the oldest): 10,000 campaigns × 60 additions = 600,000 per minute, which is 10,000 per second. Total work falls from 6.0 million to about 0.11 million operations per second, about 55 times less. State per campaign is 60 counters of 8 bytes, which is 480 bytes, or 4.8 MB for all campaigns. For unique users per campaign, each pane holds a HyperLogLog sketch of about 1 to 12 KB, and the window merges 60 sketches. A sketch cannot be subtracted, so the operator re-merges all 60 panes each minute.
Session windows. A user has events at 10:00 and 10:25, and the gap is 30 minutes. The first event creates [10:00, 10:30); the second creates [10:25, 10:55). They overlap, so they merge into [10:00, 10:55). An event at 11:10 creates [11:10, 11:40), which is separate. So there are two sessions with 2 and 1 events. Now a late event with time 10:50 arrives (within allowed lateness). Its window [10:50, 11:20) overlaps both the first session (until 10:55) and the second session (starting 11:10). The three merge into one session [10:00, 11:40) with 4 events. A result that was emitted earlier for two sessions is now wrong, so the system must retract the old results and emit the merged one. This shows why session windows and late data need accumulation modes.
intuition: Cutting a never-ending ribbon into pieces you can measure, and deciding when each piece is finished.
The idea is natural because every aggregate needs a finite set, and the most natural way to make a finite set from a timeline is to take an interval. Tumbling windows are the calendar (this minute, this hour). Sliding windows are a moving magnifying glass. Session windows follow the behaviour of a user, not the calendar: they let the data decide where the pieces end. The efficiency trick is also natural: overlapping windows share most of their content, so you split time into small pieces, summarise each one once, and build windows from summaries.
mistakes: People often think a sliding window stores a separate copy of the data for every window. In fact a good implementation shares work through panes and incremental aggregates, so the cost per event is closer to one update than to S / D updates. Systems that buffer raw events per window do multiply state, and that is a reason to use incremental aggregation functions.
People often think that windows are assigned by the order in which events arrive. In fact event-time windows are assigned by the timestamp in the event, so an event that arrives late goes into an older window, and results for that window can still change until the watermark closes it.
People often think session windows are just tumbling windows with a big size. In fact their boundaries depend on the data, they are per key, and they merge as events arrive. They need more state and a merge step, and a single late event can join two sessions into one.
People often think daily windows are simple. In fact a "day" depends on a time zone. In a local time zone, days with a daylight-saving change have 23 or 25 hours, and a window aligned to UTC does not match a business day in another zone. Choose the zone on purpose and align windows with an offset where needed.
friction: Sliding windows multiply cost. Without pane sharing, state and updates grow by S / D. Even with it, a long window with a short slide and many keys creates a large number of results: 1 million keys × one result per minute is 1 million rows per minute to write. Session windows keep one window object per key and per open session, with merging work, so a high-cardinality key (for example a device ID) with long gaps leads to very large state.
Correctness depends on watermarks and lateness decisions. A window that fires early gives speculative results that can change, and consumers must handle updates or retractions. Late data either changes old results or is dropped, so there is always a trade between freshness, completeness and state size. Triggers and accumulation modes are powerful and easy to get wrong. A trigger that fires on every element of a large window floods downstream systems.
Windows interact with the other parts of the system. Count windows and global windows have no natural end and need custom triggers and eviction to avoid unbounded state. Time-zone and calendar windows (month, with different lengths) need care. Windows also need to be consistent across restarts: state is saved in checkpoints, and changes to window size or type usually require starting from scratch.
practice: Start from the question: do you need a fixed time series (tumbling), a rolling metric (sliding) or user behaviour (session)? Prefer tumbling windows whenever possible: they are the cheapest and the simplest. If you need a rolling value, consider tumbling windows with a small size and compute the rolling total in the query layer. Use event time unless you only need operational monitoring.
Always use incremental aggregation (reduce or aggregate functions in Flink, built-in aggregates in Spark), and avoid process functions that buffer all events of the window unless you need them. For distinct counts and quantiles, use mergeable sketches (HyperLogLog, t-digest) so that panes combine. Keep keys at a sensible cardinality, and pre-aggregate before the shuffle for hot keys.
Set the watermark and allowed lateness together with the window: the window state lives for size + lateness, so a 1-hour window with 10 minutes of lateness holds state for 70 minutes. Decide how results are consumed: append-only sinks need the final result only (fire at the watermark); upserting sinks can accept early and late firings keyed by window start. Include the window start and end in the output key.
Watch the number of open windows and the state size, the window fire latency, and the late-event rate. Test with out-of-order replays and check the totals against a batch computation. Choose time zones and window alignment explicitly, and keep them in the job's documentation.
tradeoffs: Tumbling or sliding windows. Choose tumbling when you need a time series of independent buckets (hourly counts, billing periods): the cost is one update per event. Choose sliding when the consumer needs a smooth rolling value (the last 15 minutes, updated every minute) and you accept S / D times more results, or pane-based state. You give up smoothness with tumbling, and cost with sliding.
Windows in the stream engine or in the query layer. Choose stream windows when results are needed within seconds, or when downstream actions depend on them (alerts, bidding). Choose small tumbling windows in the stream and rolling aggregation at query time (in the warehouse) when the rolling result is only read in dashboards, since the query can combine buckets cheaply. You give up latency or add query cost.
Session windows or fixed windows with a user key. Choose session windows when the real unit is user activity (visits, watch sessions) and the gap is well defined. Choose fixed windows per user (hourly activity) when the session logic is unclear or events are very late, since sessions can merge unpredictably and are expensive. You give up the natural unit and gain stability.

Sliding with size S and slide D: ceil(S / D) windows per event. Session: windows are created per event with the gap and merged, so an event ends in one merged session per key, and boundaries depend on the data.
How do you make a 1-hour window that slides every minute cheap? || Use panes: keep one partial aggregate per minute and build the window from 60 panes. For invertible aggregates add the new pane and subtract the expired one; for others re-merge or use two stacks. Use mergeable sketches for distinct counts. State and work then scale with the number of panes, not events times windows.

A result emitted earlier for the separate sessions becomes wrong, so the system needs allowed lateness, retraction or update semantics in the sink, and state for closed sessions must be kept until the lateness expires.

How do windows relate to watermarks and state cleanup? || A window fires when the watermark passes its end, and its state is removed once the watermark passes end plus allowed lateness. Without watermarks, event-time windows cannot be closed, and state would grow without bound.

value: A distributed snapshot is a picture of a whole running distributed computation: the state inside every process and every message in flight, taken at moments that fit together into one consistent whole, without stopping the computation. It matters because a distributed job has no single place where "the state" lives. A streaming job may have 200 parallel tasks on 30 machines, each holding counters, windows and join buffers, with records moving between them. If one machine fails, you need to restart the job from a state that all tasks agree on. Restoring each task from its own latest save would give a mix of moments: one task would have counted a record, and the task that sent it would not remember sending it.
Stream processors use snapshots as their fault-tolerance mechanism. Flink calls them checkpoints. Every few minutes the job saves all operator state and the position in each input (for example, Kafka offsets) to durable storage. After a failure it restores the last complete snapshot, rewinds the sources to the saved positions and replays. The result is as if the failure had not happened. The same mechanism provides consistent backups, supports pausing and moving a job (a savepoint), and underpins exactly-once results when sinks cooperate.
For the layer above (stream processing, and declarative pipelines whose streaming tables keep their progress in checkpoints), snapshots turn a collection of fragile stateful tasks into one fault-tolerant program. Two concepts below carry it. Distributed systems theory (L3) provides the model and the algorithm: a consistent global state, defined by what a cut across the processes may contain, and the marker algorithm of Chandy and Lamport that records one without a global clock or a pause. File systems (L3) provide the durable place for the result: a snapshot is a set of files on a distributed file system or object store, and it counts only once its metadata file has been written atomically.
terms: Global state — the combination of the local states of all processes and the messages in transit on all channels.
Consistent cut — a global state in which, for every message that has been received, the send is also included; it could have happened in a real execution.
Marker (barrier) — a special message that flows through the channels with the data and tells a process "take your snapshot now".
Channel state — the messages that were sent before the sender's snapshot but not yet received at the receiver's snapshot; they must be recorded or replayed.
Barrier alignment — waiting for the barrier on all input channels of an operator before snapshotting, and holding back records on channels where it has already arrived.
Unaligned checkpoint — a variant where the barrier overtakes the buffered records, which are saved as part of the snapshot, so alignment does not delay it.
Savepoint — a snapshot triggered by a person, kept for planned restarts, upgrades or migration, and not deleted automatically.
Incremental checkpoint — a snapshot that uploads only the state files that changed since the previous one.
history: In 1985, K. Mani Chandy and Leslie Lamport published "Distributed Snapshots: Determining Global States of Distributed Systems" (ACM Transactions on Computer Systems). The problem sounds simple and was hard: how can one process find out what the whole system looks like, when there is no shared clock and messages take unknown time? Their answer was the marker rule, and a proof that the recorded state, though it may never have existed as an instant in the real execution, is a state the system could have been in, and so is good enough to detect stable properties such as deadlock or termination, and to restart from.
For decades the idea lived in textbooks and in checkpoint-and-rollback research for scientific computing. It came back with large-scale dataflow. Apache Flink (from the Stratosphere research project, 2014) needed fault tolerance with low overhead for stateful streaming, and in 2015 Carbone, Fóra, Ewen, Haridi and Tzoumas published "Lightweight Asynchronous Snapshots for Distributed Dataflows" (Asynchronous Barrier Snapshotting, ABS). They noted that in an acyclic dataflow with replayable sources, one need not record channel state at all, if barriers are aligned. This made snapshots cheap: just the operator state plus the source offsets. Spark Structured Streaming (2016) took a different route, with synchronous micro-batches and a write-ahead log of offsets. Later work attacked the cost of large state: incremental checkpoints with RocksDB (Flink 1.3, 2017), unaligned checkpoints for backpressured jobs (Flink 1.11, 2020), and log-based "changelog" checkpoints (introduced in Flink 1.15, 2022).
how: There are four steps in a snapshot: start, propagate, capture, and complete. Then there is recovery.
The Chandy–Lamport algorithm. Assume the processes are connected by channels that deliver messages in order and without loss. Any process can start a snapshot. It records its own state, and then sends a marker on every one of its outgoing channels. Another process P, when it receives a marker on channel C for the first time, records its own state, marks channel C as empty (everything before the marker on C is already part of P's state), and starts recording the messages that arrive on its other incoming channels. It also sends markers on its outgoing channels. For each other incoming channel, P keeps recording until the marker arrives there; the messages recorded in between are the channel's state, because they were sent before the sender took its snapshot and not yet received when P took its own. When markers have arrived on all channels, P is finished. The union of all recorded process and channel states is the snapshot. The invariants are what make it consistent: no message is recorded as received without having been sent, and no message is lost between the sender's state and the receiver's state.
Flink's barrier snapshotting. The coordinator (the JobManager) triggers checkpoint n at a regular interval. Each source records its current position (for Kafka, the offsets of the partitions) and injects a barrier numbered n into its output, in line with the data. An operator with several inputs waits until it has seen barrier n on every input. While waiting, it keeps processing the channels where the barrier has not yet arrived but must not process records from channels where it has, since those records belong to the next epoch. They stay buffered. This is alignment. When all barriers have arrived, the operator snapshots its state, forwards the barrier to its outputs and resumes. Because the barrier separates "before n" from "after n" on every path, the state of all operators reflects exactly the records before the barriers, and no channel state is needed.
Writing the state. Saving gigabytes of state must not stop processing. With the RocksDB state backend, the operator does a short synchronous step (it takes a consistent view of the database files, which are immutable SST files, so this is a cheap hard link or file list), and then uploads in the background while processing continues. An incremental checkpoint uploads only the SST files that are new since the last checkpoint, and refers to older files that are already stored. This is where file systems and object stores matter. The files are written to durable shared storage, and the checkpoint is complete only after every task has acknowledged and the coordinator has written a small metadata file that lists all pieces. A reader (a recovering job) uses a checkpoint only if its metadata exists, so a half-written snapshot is ignored.
Unaligned checkpoints. When a job is backpressured, buffers are full, and a barrier may wait behind seconds or minutes of queued records. An unaligned checkpoint lets the barrier jump ahead: the operator snapshots at once, and saves the records that were queued between the barrier and the front of the queue as channel state. This is the original Chandy–Lamport idea of recording in-flight messages, used where it pays off. It makes checkpoints fast under load but larger, since they include buffers.
Recovery. When a task fails, the coordinator picks the latest completed checkpoint, restarts the tasks (all of the job, or the affected region), loads each operator's state from the files, and tells the sources to start from the saved positions. Records after the checkpoint are read and processed again, so the state ends up as it would have been. With a replayable source (Kafka, files), no input is lost. For results written to the outside, the system needs idempotent or transactional sinks. Two-phase commit sinks pre-commit when the barrier passes and commit when the coordinator confirms that the checkpoint is complete, so each output appears exactly once.
Spark's alternative. Structured Streaming does not use barriers. A driver divides the input into micro-batches, writes the planned offsets of the next batch to a write-ahead log in the checkpoint directory, runs the batch, writes the new state-store version and then a commit record. A batch boundary is a natural consistent cut, because the whole cluster finishes batch n before starting n+1. Restart reads the log and either re-runs the last uncommitted batch (same offsets, so the same data) or continues. It is simpler and gives higher latency than continuous snapshotting.
What the lower layers contribute. Distributed systems theory supplies the definition of consistency (the consistent cut), the marker rule that achieves it without a global clock, and the knowledge of what can go wrong: non-FIFO channels, lost messages and failures during the snapshot. File systems supply durability and atomic publication: write the pieces, then publish the metadata in one atomic step, and keep old checkpoints until a newer one is complete.

example: A Flink job reads two Kafka partitions, A and B, and counts events per key in one keyed operator. Checkpoint 7 is triggered. Source A has read up to offset 120 when the barrier is injected, and source B up to offset 95. Both write these numbers into the checkpoint. The sources put barrier 7 into their streams.
The counting operator receives barrier 7 from B first. It must not mix records from after the barrier into the state that belongs to checkpoint 7, so it blocks channel B and buffers the records that follow on it, while continuing to process records from channel A, which are still before its barrier (A's offsets 118, 119, 120). When barrier 7 arrives from A, alignment is complete. The state now contains exactly the effect of A's records up to 120 and B's up to 95. Say key X has count 40 and key Y has count 25. The operator uploads its state (in the background), passes barrier 7 to the sink, unblocks channel B and processes the buffered records.
Thirty more records are processed. Then a machine fails. Recovery loads checkpoint 7: X = 40, Y = 25, and resets the sources to A = 121 and B = 96. The 30 records are read and processed again, and counts end where they would have without the failure. If the sink is a two-phase-commit sink, the output written for those 30 records after checkpoint 7 was in an uncommitted transaction. It is aborted at recovery, and written again, so the external table sees each result once.
Now cost. Assume 500 GB of state in total, with an interval of 5 minutes. A full checkpoint would upload 500 GB each time. If the cluster can upload 1 GB/s to S3, it takes 500 s, which is longer than the interval: checkpoints would overlap and the job would always be checkpointing. With incremental RocksDB checkpoints, if 3% of the state changes between checkpoints, the upload is 15 GB, which takes about 15 s. Recovery is different: it must load the state again. At 20 TaskManagers reading 100 MB/s each (2 GB/s in total), 500 GB takes 250 s, about 4 minutes, plus replay of up to 5 minutes of input at catch-up speed. So the checkpoint interval is also a recovery-time and a replay-volume decision.
intuition: Take a group photo of a dance without stopping the music: each dancer freezes their pose in the picture as the photographer's signal reaches them, and the photographer also notes who was mid-air.
The idea is natural once consistency is defined by causality and not by clock time. A picture is consistent if it never shows an effect without its cause: no message received that was never sent. A marker is a boundary drawn through the flow of the data itself. Everything before the marker on a path is in the picture, and everything after it is not. As the marker travels along every channel, it cuts the system into a "before" and an "after" that agree everywhere. Nothing needs to stop, because the cut follows the data, not the clock.
mistakes: People often think a snapshot is the state of the system at one instant. In fact there may never have been a real moment with exactly that state. The guarantee is weaker and enough: the recorded state is one that the system could have passed through, and restarting from it gives a valid execution.
People often think checkpointing makes output exactly-once by itself. In fact checkpoints restore internal state and rewind the sources, so records after the checkpoint are processed again, and any output sent to the outside in the meantime would be duplicated. End-to-end exactly-once needs idempotent or two-phase-commit sinks.
People often think checkpoints and savepoints are the same. In fact checkpoints are automatic, made for failure recovery, and managed by the system (they can be deleted when newer ones exist). Savepoints are triggered by a person for planned operations like upgrades, and are kept. Changing the job's code or operator identities can make a checkpoint unusable, so use stable operator IDs.
friction: State size is the main cost. Large state makes full snapshots too slow and expensive, and recovery time includes loading all state back. Incremental checkpoints reduce the upload, but they make restore and cleanup more complex (the chain of referenced files), and they depend on the state backend. The changelog approach reduces the time of each checkpoint further, but it writes the changes twice.
Latency and backpressure interact with barriers. Alignment delays records and slows the job, in particular with skewed or backpressured channels. A barrier stuck in a long queue makes a checkpoint time out (10 minutes by default in Flink), and repeated failures can stop the job. Unaligned checkpoints help but increase checkpoint size and make some features less compatible. Checkpoint intervals trade overhead against replay time on failure.
Exactly-once to the outside needs cooperation from sinks, which is not always possible: sinks must support transactions or idempotent writes, and two-phase commit sinks hold their transactions open for a checkpoint interval, which delays the visibility of results. Failure during the commit phase needs careful recovery.
practice: Enable checkpointing on every stateful streaming job, with the interval chosen from the recovery requirement: for example 1 to 5 minutes for most jobs. Store checkpoints in durable shared storage (S3, GCS, HDFS) in a location with a retention policy. Set a minimum pause between checkpoints so that the job is not always checkpointing, a timeout, and a limit for tolerated failed checkpoints.
For large state, use the RocksDB state backend with incremental checkpoints, local recovery if disks allow it, and enough network and storage bandwidth. Watch the checkpoint duration, size, alignment time and the number of failed checkpoints. If alignment time is large, fix the cause (backpressure, skew), and consider unaligned checkpoints and buffer debloating. Assign explicit operator IDs (uid in Flink) so that you can change the job and restore from a savepoint, and take a savepoint before every deployment.
tradeoffs: Frequent or infrequent checkpoints. Choose a short interval (seconds to one minute) when the replay after failure must be small, for example low-latency pipelines with 2PC sinks, and accept overhead and more load on storage. Choose a long interval (5 to 15 minutes) for large state where each checkpoint is expensive, and accept longer replay and slower output visibility with transactional sinks.
Aligned or unaligned checkpoints. Choose aligned (the default) when the job is not usually backpressured and you want small snapshots and the simplest behaviour. Choose unaligned when backpressure makes alignment slow enough to break checkpoint timeouts, and you can pay for larger checkpoints that contain in-flight data.
Full or incremental checkpoints. Choose incremental with RocksDB when state is large (tens of GB and above) and changes slowly between checkpoints; the upload cost depends on changes, not on total state. Choose full snapshots when state is small, or when you want simpler restore and cleanup. Incremental ones cost restore complexity.
Continuous snapshots or micro-batches. Choose Flink-style barrier snapshots when you need low latency (milliseconds to seconds), event-time processing and large keyed state. Choose Spark-style micro-batches when seconds of latency are acceptable and you value the simpler model, batch-like recovery and unified code with batch jobs. You give up latency in micro-batches, and simplicity in continuous operators.
interview: Explain how a consistent global snapshot is taken without stopping the system. || A marker is sent through channels. A process that gets its first marker records its local state and forwards markers; for each other input it records messages until the marker arrives there. The recorded states plus recorded channel messages form a consistent cut: no message is received without being sent. No global clock or pause is needed.
Why does Flink not need to record channel state in aligned checkpoints? || The sources are replayable and the dataflow is acyclic, and the barrier is aligned: an operator blocks channels that already delivered the barrier until all channels have it. So all records before the barrier are in the state and all after it are not, and nothing in flight needs saving. Unaligned checkpoints give this up and save in-flight data.
A checkpoint takes longer than the interval and the job slows down. What do you check? || State size and whether checkpoints are incremental, storage and network throughput, alignment time caused by backpressure or skew, and the timeout setting. Options: incremental checkpoints, unaligned checkpoints or buffer debloating, a longer interval, more parallelism, and removing the bottleneck operator.
How do checkpoints give end-to-end exactly-once into an external system? || The sink writes into an open transaction, pre-commits on the barrier, and commits only after the coordinator reports that the whole checkpoint completed. On failure, uncommitted transactions are aborted and the data is replayed from the checkpoint, so each result is committed once. Idempotent writes are the alternative.
Compare Flink checkpoints and Spark Structured Streaming checkpoints. || Flink takes asynchronous barrier snapshots of operator state and source positions while the job runs continuously. Spark logs the offsets of each micro-batch before processing and commits the state version and a commit record after it; the batch boundary is the consistent cut. Flink gives lower latency, and Spark has a simpler model.
quiz: Who proposed the marker-based snapshot algorithm and when? || K. Mani Chandy and Leslie Lamport, in 1985.
What does a Flink checkpoint contain? || The state of every operator and the position in every source (for example Kafka offsets), written to durable storage, with a metadata file written last to mark it complete.
Why does an operator buffer records on a channel after the barrier arrives there? || Those records belong to the next checkpoint epoch; processing them before the barrier arrives on the other inputs would put them in the wrong snapshot. This is alignment.
A job has 400 GB of state and checkpoints every 5 minutes at 1 GB/s upload. Can full checkpoints keep up? || No: 400 GB / 1 GB/s = 400 s, longer than 300 s. Incremental checkpoints that upload only changes (say 3% = 12 GB, about 12 s) can.
When would you choose unaligned checkpoints? || When backpressure delays barriers so that aligned checkpoints time out; unaligned ones let the barrier overtake queued records, at the cost of larger checkpoints that include in-flight data.
