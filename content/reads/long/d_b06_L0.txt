@@ neo4j
value: Neo4j is the most widely used graph database. It stores data as nodes (things, such as people or devices) and relationships (typed, directed connections between two nodes), and both can carry properties. Its main promise is that multi-hop questions, such as "friends of friends who bought X" or "which accounts share a phone number with a known fraud account, within three steps", run fast and are easy to write in its query language, Cypher.
The problem it solves is the join. In a relational database, a relationship is a foreign key, and following it means a join: an index lookup for every hop. One or two hops are fine. Five hops, or "any number of hops until you reach X", become slow queries that are hard to write and hard for the optimizer to plan. Neo4j stores each relationship as its own record with direct pointers to its two nodes and to the neighbouring relationships of each node. Following a connection is then a pointer dereference, not a search. This is called index-free adjacency.
Neo4j is the concrete engine for the L1 idea of a graph database (graphdb): it takes the model "relationships are stored data, not computed joins" and turns it into store files, a page cache, a query planner and a cluster. Teams use it for fraud rings, identity resolution, recommendation, IT dependency maps, access-control graphs and knowledge graphs for retrieval-augmented generation (GraphRAG). As of October 2026 the current release is 2026.09, with 5.26 as the long-term-support line.
terms: Node — an entity in the graph; it can have zero or more labels and a set of properties.
Label — a tag on a node, such as :Person or :Account, used to group nodes and to define indexes and constraints.
Relationship — a directed, typed connection between exactly two nodes, such as (:Person)-[:FRIEND]->(:Person); it can have properties.
Index-free adjacency — each node or relationship record points directly to its connected records, so a traversal follows stored pointers instead of looking up an index.
Cypher — Neo4j's declarative query language; patterns look like ASCII art, such as (a)-[:FRIEND]->(b).
GQL — the ISO standard graph query language (ISO/IEC 39075, published April 2024), strongly based on Cypher.
Dense node (supernode) — a node with a very large number of relationships, such as a celebrity account; it needs special storage to stay fast.
Page cache — Neo4j's own in-memory cache of store-file pages.
history: The idea started in 2000. Emil Eifrem, Johan Svensson and Peter Neubauer were building a content management system in Sweden and found their data, full of connections, painful to model in relational tables; Eifrem later described sketching the property graph model on a napkin during a flight. They built an embedded Java graph engine for their own use, and in 2007 founded Neo Technology in Sweden to develop it as an open-source product, Neo4j. Version 1.0 came in 2010.
Early Neo4j was used through a Java API. In 2011 the team introduced Cypher, a declarative language whose patterns look like the diagrams people draw on whiteboards. Neo4j 2.0 (2013) added labels and schema indexes, which let Cypher find starting nodes quickly. In 2015 Neo4j started the openCypher project so other vendors could implement the language; several did, and Cypher became the main input to the ISO GQL standard, published in April 2024 as ISO/IEC 39075.
Scaling and operations came next. Neo4j 3.0 (2016) added the Bolt binary protocol, and 3.1 (2016) introduced Causal Clustering based on the Raft consensus protocol. Neo4j 4.0 (2020) allowed many databases per server and Fabric queries across databases. Neo4j 5 (2022) automated cluster placement. In 2023 Neo4j added a vector index for embeddings and previewed a new "block" store format, which became the default for Enterprise databases in 5.22 (2024).
In 2025 Neo4j moved to calendar versioning (2025.01 in February 2025), added Cypher 25 as a new language version with GQL features (2025.06, July 2025), and announced Infinigraph (September 2025), an architecture that shards property data across a cluster for graphs above 100 TB. The Community Edition remains GPLv3; Enterprise is commercial, and the managed cloud service is called Aura.
how: Start with what the L1 concept graphdb contributes: the property-graph model and the rule that a relationship is a stored object with its own identity. Neo4j's job is to make that rule fast on real hardware. In the classic record format (used through Neo4j 4.x and still the Community default under the name "aligned"), every kind of object lives in its own store file of fixed-size records. A node record is about 15 bytes; a relationship record is about 34 bytes; a property record is about 41 bytes. The record's ID is its position in the file, so the record with ID r starts at byte r × record size. Finding a record by ID is arithmetic, not a search.
The pointers inside the records do the real work. A node record holds the ID of its first relationship and its first property, plus inline label bits. A relationship record holds its start node ID, end node ID, type, first property ID, and four more IDs: the previous and next relationship in the start node's chain, and the previous and next relationship in the end node's chain. So every node owns a doubly linked list of its relationships, and each relationship sits in two lists at once, one for each end. To expand from a node, Neo4j reads the node record, jumps to the first relationship, checks its type and direction, and follows the "next" pointer for this node until the chain ends. The cost of one hop is proportional to the number of relationships of that node, not to the size of the whole graph. That is index-free adjacency.
A plain chain is slow for a dense node: to find the 20 :WORKS_AT relationships of a node that also has 2 million :FOLLOWS relationships, you would walk all of them. So once a node has more than a threshold of relationships (50 by default), Neo4j inserts relationship group records: one chain per relationship type and direction. A query that asks for one type then walks only that chain.
The newer block format (default in Enterprise since 5.22) keeps the same logical pointers but improves locality. A small node gets one 128-byte block holding its labels, properties and up to about five relationships, so one page read brings most of what a query needs. Larger nodes use bigger records, and very dense nodes get a per-node B+ tree of relationships. Neo4j reported that block format was about 40% faster than record format when the graph fit in memory and about 70% faster when only a third of it did. The block format also raises the node limit from 2^35 (about 34 billion) to 2^48.
Around the store sit the usual database parts. Neo4j has its own page cache, outside the Java heap, that maps 8 KB pages of the store files; it should be large enough to hold the hot part of the store, because a traversal that misses the cache turns each pointer hop into a random disk read. Every write goes first to a transaction log (a write-ahead log) and is applied to the store files at checkpoints. Transactions are ACID with read-committed isolation and write locks; deadlocks are detected and one transaction is aborted. Indexes still exist, and they matter: range, text, point, full-text (Lucene) and vector (HNSW) indexes find the starting nodes of a query, for example the Person with email = x. Index-free adjacency only removes indexes from the hops after that.
Cypher is compiled like SQL. A query such as MATCH (a:Person {email: $e})-[:FRIEND]->()-[:FRIEND]->(fof) RETURN DISTINCT fof is parsed and turned into a plan by a cost-based planner that uses statistics (nodes per label, relationships per type). The plan picks a starting point (usually an index seek), then chains Expand operators that walk relationship chains, plus Filter, Distinct and Aggregation operators. Enterprise adds pipelined and parallel runtimes that run operators in tight loops or across several cores.
For availability, a Neo4j cluster runs a Raft group per database among the primary servers. The leader orders writes, and a write commits when a majority of primaries have it in their logs. Secondary servers copy the log asynchronously and serve reads. Clients pass bookmarks, tokens that mark the last transaction they saw, so a later read on another server waits until that server has caught up (read-your-writes). The whole graph is copied to every primary; it is not split. Splitting needs Fabric or composite databases (the application decides which part lives where) or Infinigraph, which keeps the topology together and spreads property data across members. For whole-graph analytics such as PageRank, the Graph Data Science library copies the graph into a compact in-memory projection and runs parallel algorithms on it.

example: Take a social graph with 10 million people and an average of 100 friends each. Each friendship is stored once, so there are 10,000,000 × 100 / 2 = 500 million FRIEND relationships. In the record format, node records need 10,000,000 × 15 B = 150 MB, and relationship records need 500,000,000 × 34 B = 17 GB. With one or two property records per person (name, email), add roughly 0.4–0.8 GB. To keep traversals in memory, the page cache should be about 18–20 GB, plus room for indexes.
Query: friends of friends of Alice. Step 1: an index seek on email finds Alice's node. Step 2: walk her chain of 100 relationship records. Step 3: for each of the 100 friends, read the friend's node record and walk their 100 relationships: 100 × 101 = 10,100 records. In total, about 10,200 record reads. At roughly 1 µs each inside the page cache (pointer chase plus operator overhead), the query takes about 10 ms. If the store does not fit and each read becomes a random SSD read of about 100 µs, it takes about 1 second. Page cache size matters more than any other setting.
Now compare a well-indexed relational design: a table friendships(person_id, friend_id) with 1 billion rows (both directions) and a B-tree index on (person_id, friend_id). Hop 1 is one index seek; with about 500 keys per page, the tree has 4 levels, and the 100 friend IDs sit together in one leaf page. Hop 2 is 100 more seeks, about 400 page touches. That is not slow. At depth 2, a good relational schema is within a small constant factor of Neo4j. The difference grows with depth and with the planner's choices. At depth 3 there are 100³ = 1,000,000 paths: Neo4j does about a million pointer hops (about 1 second), while the relational plan does 10,000 index seeks and builds a join result of a million rows, and many optimizers switch to hash joins that scan large parts of the table.
At depth 4 there are 100⁴ = 100 million paths, but only 10 million people exist, so most paths revisit the same people. Neither system should enumerate all paths. A breadth-first search with a visited set reads each person's chain at most once, which bounds the work by the size of the graph; in Cypher, use shortestPath or DISTINCT between hops. The lesson: index-free adjacency makes each hop cheap, but the number of paths still grows as degree to the power of depth.
intuition: A city where every house has a signpost to each neighbour's front door: to visit friends of friends you walk from door to door, instead of looking up every address in the city directory.
The design is natural once you see which work repeats. In a relational database, the connection between two rows is recomputed at query time, every time, by searching an index. In a graph-heavy workload the same connections are followed millions of times a day and change rarely. Neo4j pays at write time, by storing the connection as a record and linking it into two chains, so that reads pay nothing to find it. This is the same trade as any index or materialized view: precompute what is read often. Fixed-size records make "find record r" a multiplication, and the linked chains make "next neighbour" one more read. The rest, from the page cache to Raft, exists to keep those cheap reads in memory, safe and replicated.
mistakes: People often think index-free adjacency means Neo4j uses no indexes. In fact every query must first find its starting nodes, and that uses ordinary indexes (range, text, full-text, vector) or a label scan. Without an index on the lookup property, MATCH (p:Person {email: $e}) scans every Person node.
People often think a graph database makes deep traversals cheap at any depth. In fact the cost is proportional to the paths explored, which grows like degree^depth. Pointer hops make each step cheaper than a join, but six unbounded hops in a dense graph can still touch millions or billions of records.
People often think Neo4j clusters spread a large graph across machines. In fact a standard cluster copies the whole database to every primary for fault tolerance and read scaling. Write throughput is limited by one leader per database, and graph size by one machine's disk and memory, unless you use Fabric or composite databases, or Infinigraph.
People often think Neo4j is the right tool for whole-graph analytics such as PageRank on billions of edges. In fact the transactional engine is built for local traversals from a few starting points. Whole-graph algorithms belong in the Graph Data Science library's in-memory projections, or in Spark GraphFrames or similar engines.
friction: Partitioning a graph is the hardest open problem. A good partition keeps connected nodes on the same machine, but real graphs (social, web, fraud) have no clean cuts, and any cut turns cheap pointer hops into network round trips of about 0.5 ms each, roughly 500 times slower than a hop in memory. This is why Neo4j for years scaled up instead of out, and why Infinigraph shards properties while keeping the topology together. Very large graphs therefore need large machines: a few billion relationships means hundreds of gigabytes of page cache.
Supernodes still hurt. A node with millions of relationships makes writes to it contend on locks and makes any traversal through it explode. Relationship groups and the block format's per-node B+ trees help when you filter by type, but a model where everything connects through one "Country: India" node is a design problem, not a storage problem.
Bulk loading and bulk updates are slow through transactions, so large imports use the offline neo4j-admin import tool, which writes store files directly. Read-committed isolation allows anomalies such as lost updates unless you take explicit locks. Cypher and GQL are not yet identical: Cypher 25 adds GQL features, but Cypher 5 remains the default language version, so teams must choose and test. Finally, the Community Edition lacks clustering, the faster runtimes and the block format's default status, so many production features require the commercial Enterprise license or Aura.
practice: Use Neo4j when the core queries are about connections of variable or unknown depth: fraud rings, identity graphs, dependency impact ("what breaks if this service fails?"), permissions inheritance, and knowledge graphs for GraphRAG. If your queries are mostly aggregations over many rows, keep them in a columnar warehouse and export only the connected part to Neo4j.
Model for traversal. Make the things you hop through into relationships with specific types (:BOUGHT, :SHARES_DEVICE) rather than generic ones, because the type is how dense nodes and the planner prune work. Avoid hubs that connect everything; split them by time or category (for example, one node per day instead of one :Day node for all events).
Size the page cache to hold the whole store if you can (check the store size on disk and add 20–30% for growth), and keep the Java heap for query execution. Always look at the query plan with EXPLAIN and PROFILE: check that the plan starts with an index seek and that "db hits" grow as you expect. Bound variable-length patterns ([*1..4], not [*]) and use DISTINCT between hops. Use the LOAD CSV or neo4j-admin import tools for large loads, and batch writes in transactions of 10,000 to 50,000 changes. For new Enterprise databases, use the block format; for analytics, project the graph into the Graph Data Science library rather than running whole-graph Cypher.
quiz: What does a Neo4j relationship record point to, and why does that make traversal fast? || Its start and end nodes, its first property, and the previous and next relationships in both nodes' chains. Each hop is one read at a computed offset, not an index search.
Why does Neo4j still need indexes if it has index-free adjacency? || Index-free adjacency only helps after the query has a starting node. Finding the start, such as the Person with a given email, needs a normal index or a label scan.
How does Neo4j avoid walking millions of relationships of a supernode to find a few of one type? || Above a threshold (50 relationships by default) it keeps one chain per type and direction (relationship group records); the block format can use a per-node B+ tree. A query for one type walks only that chain.
A graph has 10 million nodes with average degree 100. Roughly how many paths does a 3-hop pattern from one node explore, and how long might that take in memory at 1 µs per hop? || About 100³ = 1,000,000 paths, so roughly 1 second. With a visited set or DISTINCT between hops, many duplicates are pruned, because only 10 million distinct nodes exist.
Your team has 50 billion edges and wants daily PageRank plus 3-hop fraud checks in under 50 ms. How would you split the work? || Run PageRank in a batch engine (Spark or Graph Data Science projections) and write scores back as properties. Serve the 3-hop checks from Neo4j on the subgraph they need, or shard with Fabric or Infinigraph, since one page cache cannot hold 50 billion edges.

@@ pgvector
value: pgvector is a PostgreSQL extension that adds a vector column type, distance operators and approximate nearest-neighbour indexes. With it, embeddings live in the same table as the rest of your data, and a similarity search is an ordinary SQL query: SELECT id FROM docs WHERE tenant_id = 42 ORDER BY embedding <=> $1 LIMIT 10. You get SQL filters, joins, transactions, backups, replication and access control for free, because Postgres already has them.
The problem it solves is the second database. When teams started building retrieval-augmented generation (RAG), semantic search and recommendation features in 2022–2023, the default advice was to add a dedicated vector database. That means a second system to run, a pipeline to keep it in sync with the source of truth, and a separate permission model. For a large share of applications (up to tens of millions of vectors, moderate query rates), pgvector removes that second system. Every major managed Postgres service (AWS RDS and Aurora, Google Cloud SQL and AlloyDB, Azure, Supabase, Neon) ships it.
pgvector stands on two lower concepts. From PostgreSQL (postgres) it takes the extension API (custom types, operators and index access methods), the buffer manager, the write-ahead log, MVCC and the query planner. From vector search (vectorsearch, L1) it takes the algorithms: the HNSW graph index, the IVF cluster index, distance metrics, and the recall-versus-speed trade-off that every approximate index makes. pgvector's real contribution is the glue: it fits those algorithms into Postgres's 8 KB pages, its crash recovery and its planner.
terms: Embedding — a list of numbers (for example 1,536 floats) produced by a model, where similar items get nearby vectors.
vector(n) — pgvector's column type for n 32-bit floats; it costs 4 × n + 8 bytes per value.
halfvec, bit, sparsevec — compact types: 16-bit floats, single bits, and vectors that store only non-zero elements.
Distance operator — <-> (Euclidean, L2), <#> (negative inner product), <=> (cosine distance), <+> (L1); <~> and <%> for bits.
HNSW — Hierarchical Navigable Small World: a layered graph of vectors; search walks greedily toward the query.
IVFFlat — an inverted-file index: k-means splits vectors into lists; a query scans only the nearest lists.
Recall — the fraction of the true k nearest neighbours that an approximate search returns.
ef_search — the size of HNSW's candidate list at query time (default 40); larger means higher recall and slower queries.
Iterative index scan — a pgvector 0.8 feature that keeps reading the index when filters remove too many candidates.
history: Andrew Kane, a prolific author of open-source data libraries, released pgvector 0.1.0 in April 2021. It had one type, three distance functions and one index, IVFFlat, chosen because it was simple to build inside Postgres's index framework. For two years it was a niche tool. Then embedding APIs and ChatGPT (late 2022) made RAG mainstream, and many teams realised they already had a Postgres database. Managed providers added pgvector during 2023, and it became the most common way to try vector search.
Releases followed the demand. Version 0.4.0 (January 2023) raised the maximum dimensions to 16,000 for storage (2,000 for indexes). Version 0.5.0 (August 2023) added HNSW, which gave much better recall for the same speed than IVFFlat and did not need training data at build time. Version 0.6.0 (January 2024) made HNSW builds parallel, which cut build times by large factors. Version 0.7.0 (April 2024) added halfvec, sparsevec, bit indexing and functions such as binary_quantize, so large collections could be indexed in less memory. Version 0.8.0 (October 2024) added iterative index scans and better cost estimates for filtered queries, the most common complaint from production users. The 0.8.x line has continued with Postgres 18 support (0.8.1, September 2025) and many fixes; 0.8.6 was released in July 2026.
An ecosystem grew around it. Timescale (now TigerData) released pgvectorscale in June 2024, adding a DiskANN-style index that keeps most of the graph on SSD. Others, such as VectorChord, add quantized IVF indexes. pgvector remains the base type that these extensions build on.
how: The extension starts with a data type. A vector(1536) value is stored as a small header plus 1,536 four-byte floats, 6,152 bytes in total. Postgres stores large values out of line through TOAST (The Oversized-Attribute Storage Technique) when a row exceeds about 2 KB, so the main table row holds a pointer and the vector lives in a side table. Distance functions are written in C and compiled with SIMD instructions where the CPU supports them, so comparing two 1,536-dimension vectors costs well under a microsecond once the data is in memory.
Exact search needs no index. ORDER BY embedding <-> $q LIMIT 10 makes Postgres compute the distance for every row and keep the best 10. This gives perfect recall and is fine for tens of thousands of rows, or for a few thousand rows left after a selective WHERE clause that uses a B-tree index. For millions of rows, it reads gigabytes per query.
Approximate search uses Postgres's index access method API, the same API that B-tree, GiST and GIN use. pgvector registers two methods, hnsw and ivfflat, and operator classes that tie each one to a distance (vector_l2_ops, vector_ip_ops, vector_cosine_ops). The key Postgres feature is the ordering operator: like a GiST index for geographic "nearest" queries, a pgvector index scan returns rows in approximately increasing distance, and the executor stops as soon as LIMIT is satisfied. The index must be built with the same operator class as the query's operator, or the planner will not use it.
The HNSW algorithm comes straight from the vectorsearch concept. Each vector becomes a graph node with up to m neighbours per layer (default m = 16, and 2 × m on the bottom layer). Higher layers contain exponentially fewer nodes, like express lanes. A search enters at the top, moves greedily to the neighbour closest to the query, drops a layer, and repeats; on the bottom layer it keeps a candidate list of size ef_search (default 40) and returns the best ones. Build quality is set by ef_construction (default 64). In pgvector, these nodes and neighbour lists are stored in ordinary 8 KB index pages, so the index is crash-safe through the write-ahead log, replicated to standbys, and cached in shared buffers. One element must fit in one page, which explains the indexing limits: 2,000 dimensions × 4 bytes for vector, 4,000 × 2 bytes for halfvec, 64,000 bits for bit, each about 8,000 bytes. A fast build needs the whole graph in maintenance_work_mem; if it does not fit, the build continues on disk, much more slowly.
IVFFlat is simpler. At build time it runs k-means on a sample of the rows to find lists centroids (rule of thumb: rows / 1,000 up to 1 million rows, \( \sqrt{\text{rows}} \) above that), then puts every vector in the list of its nearest centroid. A query compares the query vector with all centroids, then scans the ivfflat.probes nearest lists (default 1; \( \sqrt{\text{lists}} \) is a good start). It builds faster and uses less memory than HNSW, but its recall is lower at the same speed, and the centroids are fixed: if the data drifts after the build, recall drops until you rebuild.
Postgres concepts also shape correctness. The index stores heap tuple IDs, so after the index produces candidates, Postgres fetches each row, checks MVCC visibility (is this version visible to my transaction?) and applies the WHERE clause. That gives transactional consistency (a vector inserted in a committed transaction is searchable at once), but it also means filters run after the index. With ef_search = 40 and a filter that matches 10% of rows, only about 4 rows survive on average. pgvector 0.8's iterative scans fix the worst case: with hnsw.iterative_scan = relaxed_order, the scan keeps exploring the graph until enough rows pass or hnsw.max_scan_tuples (default 20,000) is reached. Deletes and updates leave dead tuples that VACUUM must remove from the graph and repair around, which is slower for HNSW than for a B-tree.
Memory can be cut with quantization. A halfvec column or an expression index such as (embedding::halfvec(1536)) halves the size. An index on binary_quantize(embedding)::bit(1536) keeps one bit per dimension, 32 times smaller, and you re-rank the top candidates with the full vectors in a second step.

example: A SaaS product stores 10 million document chunks with 1,536-dimension embeddings. Size the data first. One vector(1536) is 4 × 1,536 + 8 = 6,152 bytes, so the vectors alone take 10,000,000 × 6,152 B ≈ 61.5 GB. An HNSW index stores each vector again plus up to 32 neighbour IDs (6 bytes each) on the bottom layer, about 6.4 KB per element. Because one element nearly fills an 8 KB page, the index is roughly 65–80 GB. To keep queries fast, table and index together want around 130–140 GB of RAM in shared buffers and the OS cache.
Now the query cost. With ef_search = 40, an HNSW search typically computes distances for roughly a thousand vectors. If they are in memory, each costs about 1–2 µs (fetch 6 KB, then about 1,536 multiply-adds with SIMD), so the search takes about 1–2 ms. If they are not in memory, each visited element can become a random SSD read of about 100 µs, and the same search takes about 100 ms. Exact search, for comparison, reads all 61.5 GB per query; even at 10 GB/s that is about 6 seconds.
Cut the memory. Switch the index to halfvec: 2 × 1,536 + 8 = 3,080 bytes per vector, so the index falls to about 35 GB, with almost no recall loss for typical text embeddings. Or build a binary-quantized index: 1,536 bits = 192 bytes per vector, plus about 192 bytes of neighbour IDs, so about 4 GB in total. Search it for the top 100 by Hamming distance, then re-rank those 100 with the full vectors: 100 × 6 KB = 600 KB of extra reads per query.
Then the filter. Tenant 42 owns 1% of the rows. Without iterative scans, the index returns about 40 candidates, of which 1% pass, so 0.4 rows on average: the query asked for 10 and gets almost nothing. To find 10 matching rows, the scan must examine about 10 / 0.01 = 1,000 candidates; with iterative scans it does this automatically, well under the 20,000 limit. For a tenant with 0.01% of rows, the scan needs about 100,000 candidates and hits the limit. Here the better plan is exact search on that tenant's 1,000 rows through a B-tree on tenant_id (1,000 × 6 KB = 6 MB read, a few milliseconds), or list partitioning by tenant so each tenant has its own small index.
intuition: Instead of buying a new warehouse for one new kind of item, add a special shelf to the warehouse you already run, with its own fast way to find "the items most like this one".
The design is natural because the hard parts of a database are not the similarity search. Durability, replication, backups, access control, transactions and a query language took Postgres decades to get right, and a vector index needs every one of them. HNSW and IVF are, at their core, just data structures over pages: nodes with neighbour lists, or lists of vectors grouped by a centroid. Postgres was designed from the start to let extensions add new types and new index structures through stable APIs. So pgvector only had to write the algorithms and fit them into pages; everything else came with the host. The cost is that the algorithms must live with the host's rules, such as filtering after the index scan and 8 KB pages.
mistakes: People often think pgvector search is exact. In fact HNSW and IVFFlat are approximate: a query may miss some true nearest neighbours, and the recall depends on ef_search, probes, the data and the filters. Measure recall against an exact query on a sample.
People often think adding WHERE clauses makes vector queries faster and still correct. In fact the approximate index produces candidates before the filter runs. A selective filter can return fewer rows than LIMIT, or only far neighbours, unless you enable iterative scans, use partial indexes or partitions, or let the planner choose exact search on a small filtered set.
People often think the index is used for any distance. In fact an index built with vector_l2_ops serves only the <-> operator. A query with <=> (cosine) ignores it and falls back to a full scan. For normalized embeddings (length 1), inner product, cosine and L2 give the same ranking, so pick one operator and use it everywhere.
People often think an IVFFlat index stays good forever. In fact its centroids come from the data at build time. If you build it on an empty or small table, or the data distribution changes, recall drops; rebuild it, or use HNSW, which updates its graph on every insert.
friction: Memory is the main limit. HNSW is fast only when the graph is in RAM, and a 1,536-dimension index costs about 6.4 KB per row, so 100 million rows need several hundred gigabytes. Quantization helps, but the base table still holds the full vectors. One Postgres primary handles all writes, so very large collections or very high write rates need sharding (Citus, application-level partitioning) or a dedicated distributed vector database.
Builds are heavy. An HNSW build for tens of millions of rows can take hours, wants maintenance_work_mem as large as the graph, and competes with production traffic for CPU and I/O. Parallel builds help, but they use shared memory too (a Docker container needs a large enough --shm-size). Updates and deletes leave dead entries; VACUUM on an HNSW index is slow because it must repair neighbour links.
Filtered search is still the hardest problem. Iterative scans fix the "too few rows" case, but the planner's cost estimates for vector queries are rough, and the TOAST storage of vectors makes sequential scans look cheaper than they are. Hybrid search (keywords plus vectors) needs you to combine Postgres full-text search and vector results yourself, for example with reciprocal rank fusion in SQL. Finally, pgvector lacks some features that dedicated systems have, such as GPU indexes, built-in multi-vector ranking, and automatic tiering of cold vectors to object storage.
practice: Start with pgvector if your vectors relate to data you already keep in Postgres and the collection is below roughly 10–50 million vectors per database. Use HNSW by default; use IVFFlat only when build time or memory is the main constraint and the data is static. Create IVFFlat indexes after loading data, never on an empty table.
Choose one distance and match it everywhere: normalized embeddings with cosine (<=> and vector_cosine_ops) is the common choice. Store the embedding model name and version in a column so you can re-embed in the background later. Consider halfvec for the column or the index from the start; it halves memory with very little recall loss.
For loads, insert with COPY in bulk, then build the index with high maintenance_work_mem and max_parallel_maintenance_workers. For queries, set hnsw.ef_search per query or per transaction (SET LOCAL): 40 for speed, 100–200 for higher recall. If you filter, enable hnsw.iterative_scan = relaxed_order, add B-tree indexes on filter columns, and partition by tenant when tenants are large. Use EXPLAIN ANALYZE to check that the index is used.
Measure recall regularly: run 100 real queries with exact search (SET enable_indexscan = off in a test session) and compare with the indexed results. Watch index size, cache hit rate and VACUUM progress. When you outgrow one machine, look at pgvectorscale for disk-based indexes or at a distributed vector database, but move only when measurements show the need.
quiz: Which two lower concepts does pgvector combine, and what does each provide? || PostgreSQL provides types, operators, the index access method API, pages, WAL, MVCC and the planner. Vector search provides the HNSW and IVF algorithms, the distance metrics and the recall-versus-speed trade-off.
Why can a filtered query such as WHERE tenant_id = 42 ORDER BY embedding <=> $q LIMIT 10 return fewer than 10 rows? || The index returns about ef_search candidates in distance order, and Postgres applies the filter after fetching them. If few candidates belong to tenant 42, most are discarded; iterative scans fix this by fetching more candidates.
Why are vector indexes limited to 2,000 dimensions but halfvec indexes to 4,000? || An index element must fit in one 8 KB Postgres page. 2,000 × 4-byte floats and 4,000 × 2-byte halves both come to about 8,000 bytes.
You have 5 million 768-dimension vectors. Roughly how large is the vector data, and how much would a binary-quantized index need? || 4 × 768 + 8 = 3,080 bytes per vector, so about 15.4 GB. Binary quantization stores 768 bits = 96 bytes per vector, about 0.5 GB plus overhead, followed by re-ranking with full vectors.
When would you move from pgvector to a dedicated vector database such as Milvus? || When the collection needs more memory or write throughput than one Postgres primary can give (hundreds of millions of vectors or more), or when you need GPU indexes, tiered storage or very high query rates. Below that, one database is simpler to keep consistent and secure.

@@ milvus
value: Milvus is an open-source, distributed vector database built for collections from millions to tens of billions of embeddings. You define a collection with a schema (a primary key, one or more vector fields, scalar fields such as price or region, and JSON metadata), insert rows, and ask for the k nearest vectors to a query vector, optionally with a filter such as region == "IN" and in_stock == true. It is used for semantic search, RAG, image and video search, deduplication and, very often, candidate retrieval in recommender systems.
The problem it solves is scale with freshness. A single-machine vector index such as Faiss or hnswlib is fast, but it is a library: it does not take writes from many clients, survive crashes, replicate, filter by metadata, delete rows, or grow past one machine's memory. Milvus wraps these libraries in a database that does all of that, and splits the work across many machines so that ingestion, index building and search scale independently.
It stands on two lower concepts. Vector search (vectorsearch, L1) gives it the core algorithms: HNSW graphs, IVF clustering, product and scalar quantization, DiskANN for SSDs, and GPU indexes, each with its own recall, speed and memory profile. Recommender systems (recsys, L1) give it the workload that shaped much of its design: a two-tower model turns a user into a vector, and the database must return the top few hundred or thousand items from hundreds of millions, thousands of times per second, while new items appear every minute and filters exclude out-of-stock or blocked items. Milvus is maintained by Zilliz, which also sells a managed version (Zilliz Cloud), and it is a graduated project of the LF AI & Data Foundation. As of October 2026 the current major version is 3.0.
terms: Collection — a table of rows with a fixed schema: primary key, vector fields and scalar fields.
Shard — a split of a collection's write stream; each shard has its own write-ahead log channel.
Segment — a chunk of a shard's rows (up to 1 GB by default); the unit of storage, indexing, loading and search.
Growing segment — a segment that still receives new rows; it lives in memory on a streaming node and is searchable at once.
Sealed segment — a full, immutable segment; it gets a vector index and is loaded by query nodes from object storage.
Write-ahead log (WAL) — the ordered, durable log of all inserts and deletes; in Milvus it is the backbone that every component reads.
Knowhere — Milvus's vector execution engine, which wraps Faiss, hnswlib, DiskANN and GPU libraries behind one interface.
Consistency level — Strong, Bounded (default), Session or Eventually: how recent the data must be before a search runs.
Partition key — a scalar field that Milvus uses to group rows, so a filtered search can skip whole groups of segments.
history: Zilliz was founded in 2017; its founder and CEO is Charles Xie. Its team released Milvus as open source in October 2019. The first versions were essentially a server around Faiss with GPU support, aimed at image and video search. Milvus joined the LF AI Foundation as an incubation project in January 2020 and graduated in June 2021. The SIGMOD 2021 paper "Milvus: A Purpose-Built Vector Data Management System" (Jianguo Wang and colleagues) described this generation: heterogeneous CPU and GPU execution, strategies for combining vector search with attribute filters, multi-vector queries, and an LSM-style way to handle a stream of inserts.
The 1.x design could not scale out easily, so the team rewrote it. Milvus 2.0 (January 2022) was cloud-native: stateless compute nodes, a message queue (Pulsar or Kafka) as the log, object storage for data, and etcd for metadata. The design is described in "Manu: A Cloud Native Vector Database Management System" (Guo and colleagues, PVLDB 2022), whose main idea is "log as data": writers publish to the log, and every reader subscribes to it independently.
Then the features followed the market. Milvus 2.3 (2023) added GPU indexes built with NVIDIA's libraries, including the CAGRA graph index. Milvus 2.4 (2024) added sparse vectors, multi-vector and hybrid search. Milvus 2.5 (late 2024) added built-in full-text search with BM25. Milvus 2.6 (June 2025) replaced the external message queue with Woodpecker, a log that writes directly to object storage, added streaming nodes, 1-bit RaBitQ quantization, int8 HNSW and tiered storage. Milvus 3.0 (July 2026) is "lake-native": external collections index data that stays in Lance, Iceberg, Parquet or Vortex files, with a new storage engine (Loon), snapshots and a Spark connector.
how: Milvus separates four layers. Proxies are stateless entry points: they check requests, assign rows to shards (by hashing the primary key), and merge results. A single active coordinator is the control plane: it keeps the schema and segment map in etcd, hands out timestamps, assigns shards to streaming nodes and segments to query nodes, and schedules compaction and index builds. Worker nodes do the work: streaming nodes own the write path and the newest data, query nodes search sealed data, and data nodes build indexes and compact segments. Storage sits under all of them: etcd for metadata, the WAL (Woodpecker since 2.6, or Kafka or Pulsar), and object storage (S3, MinIO, GCS, Azure Blob) for everything else. Because the durable state is in the log and object storage, compute nodes can be added, removed or restarted without moving data.
A write works like this. The proxy gets a timestamp from the coordinator's timestamp oracle (a hybrid of wall-clock time and a counter, so every operation has a global order) and appends the row to its shard's WAL. Once the log has it, the write is durable and acknowledged. The streaming node that owns the shard applies the row to a growing segment in memory, where it is searchable immediately, by brute force or a light interim index. The streaming node also flushes the growing data to object storage as columnar binlogs, one file per field. When a segment reaches its size limit (1 GB by default) or stays idle for about 10 minutes, it is sealed. A data node then builds the vector index for the sealed segment, plus scalar indexes, and writes the index files to object storage. Query nodes load the new index and the coordinator swaps it in for the growing data. Each segment also keeps a Bloom filter of its primary keys, so a delete or upsert can quickly find which segments might hold the key.
Deletes never modify a sealed segment, because sealed segments are immutable files. A delete is a log entry (primary key and timestamp). Query nodes keep a per-segment bitmap of deleted rows and skip them, and compaction later rewrites segments without the deleted rows. This is the same idea as an LSM tree: append, mark, and clean up in the background. It also means heavy deletes slow searches until compaction runs.
A search fans out and merges. The proxy sends it to each shard's leader, which searches its growing data and asks query nodes to search the sealed segments of that shard. Each segment is searched independently with its own index, by Knowhere, which calls the right library (hnswlib-style HNSW, Faiss IVF, DiskANN or a GPU index). Filters are evaluated first into a bitset of allowed rows, and the index skips disallowed rows during traversal; when the filter keeps very few rows, brute force on those rows is better and the engine can choose it. Each segment returns its own top k; the query node merges its segments, the shard leader merges query nodes, and the proxy merges shards. Because the global top k must be inside the union of the local top k lists, this merge is exact relative to what the segment indexes return.
Freshness is controlled by timestamps. Each search carries a guarantee timestamp, and a node does not run it until it has applied the log up to that time. With Strong, the guarantee is "now", so the search waits for all earlier writes. With Bounded staleness, the default, it is slightly in the past (a few seconds), so the search rarely waits. Session uses the client's own last write, so you always see your own inserts. Eventually skips the check.
The recsys workload explains several features. Partition keys let a query for one region or category touch only the segments of that group. Range search and grouping search return diverse candidates instead of 1,000 near-duplicates. Multiple replicas of the loaded segments spread query load, because retrieval traffic is read-heavy. Hybrid search runs a dense vector search and a sparse or BM25 search and fuses the two ranked lists with reciprocal rank fusion or weights, which suits RAG as well. Index choice is per field: HNSW (fast, high memory), IVF_FLAT, IVF_SQ8 or IVF_RABITQ (less memory), DISKANN (graph on SSD, compressed codes in RAM), or GPU_CAGRA (high throughput on GPUs).

example: An e-commerce company retrieves candidates for its recommender. It has 100 million items, each with a 768-dimension float32 embedding, and the ranking model wants the top 1,000 candidates per request at 2,000 requests per second.
Size the data. One vector is 768 × 4 = 3,072 bytes, so the raw vectors take 100,000,000 × 3,072 B ≈ 307 GB. With HNSW (M = 16, so up to 32 neighbours of 4 bytes each on the bottom layer), add about 13 GB of graph: roughly 320 GB of RAM per replica. With IVF_SQ8 (one byte per dimension) the index needs 768 B per vector, about 77 GB. With IVF_RABITQ (one bit per dimension, 96 B) it needs about 10 GB, and a refine step re-ranks the best candidates with higher-precision vectors. The team picks IVF_SQ8 with two replicas: about 154 GB of query-node memory instead of 640 GB.
Count the segments. At 1 GB per segment and about 3 KB per row (plus a little for scalar fields), one segment holds roughly 300,000 items, so the collection has about 330 sealed segments. A search runs on every segment and each returns its own top 1,000, so the proxy merges up to 330 × 1,000 = 330,000 candidates into the final 1,000. This merge is cheap (a heap of size 1,000), but the per-segment search is not: if one segment search costs about 0.3 ms of CPU, one request costs 330 × 0.3 ≈ 100 ms of CPU. At 2,000 requests per second that is 200 CPU-seconds per second, so about 200 cores, or 7 machines with 32 cores, before replicas for failure.
Now add a partition key. Every request is for one of 10 countries, and the team makes country the partition key. Milvus groups each country's rows into its own segments, so a request touches about 33 segments instead of 330. CPU per request falls to about 10 ms, and the cluster needs about 20 cores for the same load. This is the biggest single tuning lever in the example.
Finally, freshness. A new product is inserted at 10:00:00. It is in the WAL within milliseconds and in a growing segment almost at once. A Bounded search at 10:00:01 may not see it yet; a Session search from the same client, or a Strong search, will. The growing segment seals when it reaches 1 GB or after about 10 minutes idle, and a data node builds its index in roughly a minute. Until then, new items are searched by brute force inside the growing segment, which is fine because it holds at most a few hundred thousand rows.
intuition: A library that never edits a shelf: new books go onto a small open cart that anyone can browse, full carts become sealed shelves with their own catalogue, and a search asks every relevant shelf for its best matches and merges the answers.
The design is natural because vector indexes hate change. An HNSW graph or IVF clustering is expensive to build and awkward to update, so Milvus never updates one: it builds an index once per immutable segment and handles new data and deletes beside it. This is the LSM-tree idea applied to vector indexes. Once segments are immutable files in object storage, the rest follows: any query node can load any segment, the log is the single source of truth for order and recovery, and ingestion, indexing and search can scale separately because they never share mutable state.
mistakes: People often think Milvus results are exact because it is a database. In fact every index except FLAT is approximate, and recall depends on the index type, its parameters (ef, nprobe), quantization and filters. Measure recall against FLAT on a sample of real queries.
People often think a row is searchable only after its index is built. In fact it is searchable as soon as it reaches a growing segment. Whether a given search sees it depends on the consistency level: the default Bounded level can miss writes from the last few seconds, while Session or Strong will not.
People often think more, smaller segments make search faster through parallelism. In fact each segment is searched separately, and HNSW or IVF search cost grows slowly with segment size. Many small segments multiply the per-segment overhead. Compaction, larger segments and partition keys reduce the number of segments each query touches.
People often think deletes free memory and speed up search at once. In fact deletes only mark rows in a bitmap. The rows stay in sealed segments, and are still visited and then discarded, until compaction rewrites the segment.
friction: Operating a distributed Milvus is real work. A cluster has proxies, a coordinator, streaming, query and data nodes, etcd and object storage, usually on Kubernetes. Version 2.6 removed the need for Kafka or Pulsar, but etcd health, object storage latency and node memory still need monitoring. For small collections, Milvus Lite (embedded) or Standalone (one process) are simpler, and pgvector may be simpler still.
Memory is the main cost. Loaded segments must normally sit in query-node RAM, and HNSW on full-precision vectors costs more than the raw data. Quantization (SQ8, RaBitQ), DiskANN, mmap and tiered storage reduce RAM, but each moves cost into recall loss or SSD latency. Index parameters interact with data, filters and top k in ways that only benchmarks reveal.
Filtered search is better than in many systems but not solved. Very selective filters make graph indexes walk many disallowed nodes; very broad filters are cheap. The planner's choice between index search and brute force uses estimates that can be wrong. Large top k (thousands) hurts graph indexes and favours IVF.
Consistency is weaker than in a transactional database. There are no multi-row transactions, Bounded staleness is the default, and an upsert is a delete plus an insert. Deletes and updates cost compaction work. Finally, a change of embedding model means re-embedding and re-indexing the whole collection, typically into a new collection that you switch to with an alias.
practice: Start by estimating memory: number of vectors × bytes per vector for your chosen index, times the number of replicas. Pick the index from the constraint: HNSW when RAM is plentiful and latency matters most, IVF_SQ8 or IVF_RABITQ with refine when memory dominates, DISKANN when the data is far larger than RAM and NVMe is available, GPU_CAGRA for very high query rates or fast builds.
Design the schema for filtering. Choose a partition key for the filter that almost every query uses (tenant, country, category), and add scalar indexes on other frequent filter fields. Use the JSON field for flexible metadata, but index the paths you filter on. Keep vectors and their metadata in one collection so filters run inside the search.
Choose consistency per query: Bounded for most traffic, Session for "user just uploaded this and expects to find it", Strong only for tests or rare checks. Use bulk insert from Parquet files in object storage for large loads instead of millions of single inserts, and let compaction finish before benchmarking.
Treat recall as a monitored metric: keep a set of queries with exact (FLAT) answers and re-check after any change of index, parameters or data size. For model upgrades, write into a new collection and switch an alias when it is ready. If your data already lives in Iceberg, Lance or Parquet, look at 3.0's external collections before copying it.

@@ pinecone
value: Pinecone is a managed vector database offered only as a cloud service. You create an index, send records (an ID, a dense or sparse vector, and metadata such as {"tenant": "acme", "year": 2026}), and query for the most similar records with optional metadata filters. You never choose machines, shards or index parameters. In its serverless mode you pay for what you store and for the reads and writes you make, and the service scales up and down without any action from you.
The problem it solves is operating vector search. An open-source engine such as Milvus or an extension such as pgvector gives you the algorithms, but you still have to size memory, choose and tune indexes, rebuild them, replicate, upgrade and watch them at 3 a.m. Pinecone sells the result instead of the parts. This made it the default first choice for many retrieval-augmented generation (RAG) prototypes in 2023, and it is still used in production for semantic search, recommendation candidates and agent memory. As of October 2026 it reports more than 10,000 customers.
It stands on two lower concepts. Vector search (vectorsearch, L1) gives it the algorithms: exact scans, hashing-based sketches, product quantization and IVF clustering, and the recall-versus-cost trade-off they share. Recommender systems (recsys, L1) give it a core workload: candidate retrieval, where a user or query vector must find a few hundred similar items among millions within tens of milliseconds, with filters for availability or eligibility. Pinecone's own contribution is the storage design that makes this cheap on shared cloud infrastructure: immutable index files on object storage, organized like an LSM tree, with compute that loads them on demand.
terms: Index — the top-level container for records, with a fixed vector dimension and distance metric (cosine, dot product or Euclidean).
Namespace — a hard partition inside an index; every read and write targets exactly one namespace, and each is stored and indexed separately.
Record — an ID, a dense vector and/or a sparse vector, and filterable metadata (up to 40 KB).
Serverless (on-demand) — the default mode: storage on object storage, shared compute, billing per read unit, write unit and GB stored.
Slab — an immutable file holding a batch of records, its vector index, compressed vectors and metadata bitmaps.
Memtable — the in-memory buffer of the newest writes, searched by exact scan until it is flushed into a slab.
LSN — log sequence number: the position of a write in the namespace's log, used to check whether a query already reflects it.
Read unit (RU) — the billing unit for queries; a query costs about 1 RU per GB of the namespace it searches (minimum 0.25).
Dedicated Read Nodes (DRN) — reserved query capacity billed by the hour instead of per read unit.
history: Edo Liberty founded Pinecone in 2019. He had led Amazon AI Labs, which built algorithms for Amazon SageMaker, and before that worked at Yahoo Research on large-scale similarity search and sketching algorithms. His bet was that embeddings would become a basic data type that needed its own managed database. Pinecone launched its managed vector database in 2021. That first version was pod-based: you chose a pod type (storage-optimized or performance-optimized), a number of pods and replicas, and Pinecone ran the index on those fixed machines.
The RAG boom of 2023 brought huge demand from teams building on ChatGPT-style models, and frameworks such as LangChain made Pinecone a default example. In April 2023 it raised a $100 million Series B led by Andreessen Horowitz at a $750 million valuation. Pod-based indexes, however, were expensive for the typical customer: many small or bursty workloads paying for always-on machines.
So Pinecone rebuilt the system. In January 2024 it announced Pinecone Serverless, which separates reads, writes and storage and keeps data on object storage; it claimed cost reductions of 10× to 100× for typical workloads. Serverless became generally available on AWS in May 2024 and later on Google Cloud and Azure; pods are now a legacy option. The company then added hosted embedding and reranking models, sparse indexes for keyword-style search, and Pinecone Assistant, a managed RAG service.
In September 2025 Ash Ashutosh, a storage-industry founder (Actifio), became CEO, and Liberty became Chief Scientist. A November 2025 engineering article described the slab architecture publicly. In 2026 Pinecone made Dedicated Read Nodes generally available (April), released Bring Your Own Cloud for enterprise customers on AWS, Google Cloud and Azure (August), and made full-text search with BM25 and a Documents API generally available (September).
how: The system has a global control plane and regional data planes. The control plane manages projects, indexes, users and billing. The data plane serves reads and writes inside one cloud region, and its write path and read path are separate services that scale independently, so a burst of writes does not slow queries. Every request carries an API key, and an API gateway routes it to the right plane and region. The namespace is the unit of everything below: each namespace has its own log positions, its own memtable and its own set of slabs, so a query never touches another namespace's files.
A write is cheap and fast because almost nothing happens before the acknowledgment. The data plane appends the write to a log on object storage, assigns it an LSN in its namespace, and returns success, typically in under 100 ms. Everything else is asynchronous. An index builder, assigned to the namespace through a consistent-hash ring, reads the log in batches, applies writes to an in-memory memtable of up to about 10,000 records, and periodically flushes the memtable to object storage as a new immutable L0 slab. Updates and deletes are recorded as new versions and tombstones (markers that hide older versions), not as changes to old files. This is the LSM-tree pattern: the log gives durability and order, the memtable gives freshness, and immutable files make storage simple and cacheable.
Compaction keeps the number of files small. About ten L0 slabs (up to 10,000 records each) merge into an L1 slab of about 100,000 records; about ten L1 slabs merge into an L2 slab of about 1 million; Dedicated Read Nodes add an L3 level above that. Compaction also drops versions hidden by tombstones. The goal is to keep a namespace at about 20 slabs or fewer, so a query does not have to open hundreds of files.
Here is where the vectorsearch concept enters, with a twist: the index type depends on the slab size. The memtable is searched by exact brute force, which is fast for 10,000 vectors. Small slabs use a SimHash-style sketch (random rotation, then one sign bit per coordinate), cheap to build and good enough to shortlist candidates. Medium slabs use PQFS, a fast-scan form of product quantization that compresses vectors into short codes and compares codes with lookup tables. Large slabs use IVF: vectors are clustered, each cluster holds compressed codes, and a query scans only the clusters nearest to it. Pinecone does not use HNSW. The reason is economic: graph indexes are expensive to build and must sit in RAM, while quantized IVF files are compact, can be built once at compaction time, and can be cached on local SSD. Expensive indexing is spent only on data that has survived long enough to be compacted.
A query fans out and merges. The query router checks limits, finds the slabs of the target namespace, and sends the query to query executors, while it also scans the memtable. Executors keep slabs cached in memory or on local SSD; a slab that has not been used for a while must first be fetched from object storage, which makes the first query to a cold namespace slower. Each executor searches its slabs and returns a partial top k; the router merges them with the memtable results, removes stale versions and duplicates, and returns the best matches. Metadata filters use roaring bitmaps (compressed sets of row numbers) built for every metadata field in each slab. For selective filters Pinecone filters before the vector scan, and for broad filters it filters during the scan. It never filters after the scan, so a filter does not cut the result list short.
Freshness is eventual. A query reports x-pinecone-max-indexed-lsn, the highest LSN it reflects; if that is at least the LSN your write returned, the query saw your write. Usually this takes seconds.
Pricing follows the architecture. Storage is billed per GB-month of records. Writes cost write units, about 1 WU per KB written. A serverless query costs 1 RU per GB of the namespace searched, because the work and cache footprint of a query grow with the number of slabs it must scan. Dedicated Read Nodes instead reserve executors with the namespace's slabs always loaded, billed per hour and scaled by adding replicas, for steady high query rates.

example: A B2B SaaS company builds RAG search over its customers' documents: 10 million chunks, 1,536-dimension embeddings, about 500 bytes of metadata and a 36-byte ID per record. Prices below are the Standard plan list prices in October 2026 (storage $0.33 per GB-month, about $16 per million read units, about $4 per million write units); check them before you plan.
Storage. One record is 1,536 × 4 = 6,144 bytes of vector plus about 536 bytes of ID and metadata, so about 6.7 KB. Ten million records are about 67 GB, which costs 67 × $0.33 ≈ $22 per month. Storage is cheap.
Initial load. Batches of 100 records are about 670 KB each, so about 670 WUs per batch (well above the 5 WU minimum per request). Ten million records are about 67 million WUs, about $270, once.
Reads, design A: one namespace for everything, with a metadata filter tenant = X. The namespace is 67 GB, so every query costs about 67 RUs, whatever the filter or top k. At a steady 50 queries per second, that is 50 × 86,400 = 4.32 million queries per day, × 67 = about 289 million RUs per day, or about $4,600 per day: roughly $140,000 per month.
Reads, design B: one namespace per customer. There are 1,000 customers, averaging 10,000 chunks (67 MB) each. A query to a 67 MB namespace costs the minimum 0.25 RU. The same 4.32 million queries per day cost about 1.08 million RUs, about $17 per day or $520 per month. The largest customer, with 500,000 chunks (3.4 GB), pays about 3.4 RUs per query, still small.
The two designs store the same bytes and return the same answers, but they differ in read cost by about 270×. The reason is mechanical: a query scans the slabs of one namespace, so the work, and the bill, follow namespace size, not filter selectivity. Design B also gives isolation for free, because one tenant's query cannot touch another's data.
If design A were unavoidable (for example, a public search over all documents at 500 queries per second), on-demand reads would cost about $46,000 per day. That is the point where Dedicated Read Nodes, billed per node-hour regardless of query count, become the cheaper choice.
intuition: A self-storage warehouse that also answers questions: you hand over boxes and leave, workers sort them into ever-larger labelled crates in the back, and when you ask for "the ten boxes most like this one", they open only the crates of your unit.
The design is natural once you accept two facts about cloud hardware. Object storage is cheap, durable and nearly unlimited, but slow; local RAM and SSD are fast, but expensive and tied to one machine. An LSM design uses both well: writes become immutable files on object storage, and compute caches only the files that queries actually touch. Most customers have many small namespaces that are idle most of the time, so shared executors serving cached slabs cost far less than a fixed server per customer. Choosing the index per slab size follows the same logic: never spend expensive indexing work on data that is small, new or about to be merged.
mistakes: People often think serverless pricing means you pay mainly for storage. In fact storage is usually the small part; each query costs RUs in proportion to the size of the namespace it searches, so a large shared namespace with steady traffic can cost thousands of dollars per day.
People often think a filter makes a query on a big namespace cheap. In fact the filter speeds up the scan, but the RU cost depends on namespace size, not on how many records match. Put tenants or other hard partitions into separate namespaces.
People often think a successful upsert is immediately searchable. In fact Pinecone is eventually consistent: the write is logged first and indexed shortly after. If you need read-your-writes, compare the write's LSN with the query's max indexed LSN, or retry.
People often think Pinecone runs HNSW like most vector databases. In fact it uses brute force for the memtable, a sign-bit sketch for small slabs, quantized codes for medium slabs and IVF for large ones, chosen automatically. You cannot tune these indexes, so you tune recall through top k, reranking and data design instead.
friction: You give up control. The service is closed source, you cannot choose the index type or its parameters, and you cannot inspect why a result was missed. Recall is high in Pinecone's published tests, but you can only measure it yourself, by comparing with exact search on an export of your data.
Cost is hard to predict for read-heavy workloads, because RUs scale with namespace size times query count. Dedicated Read Nodes fix the per-query cost, but bring back capacity planning. Since 2026, egress is metered too. A namespace that has been idle can be slow on its first queries while slabs are fetched from object storage.
There are hard limits: dense vectors up to 20,000 dimensions, 40 KB of filterable metadata per record, upserts of 1,000 records or 2 MB per request, top k up to 10,000, at most 10,000 values in an $in filter, and per-namespace request-rate limits. Queries cannot span namespaces, so cross-tenant search needs one query per namespace. There are no transactions or joins: your source of truth lives elsewhere, and keeping Pinecone in sync with it, including deletes, is your pipeline's job.
Finally, data leaves your environment unless you pay for Bring Your Own Cloud, which matters for regulated data, and you depend on one vendor's roadmap and pricing.
practice: Design namespaces first. Use one namespace per tenant, per user, or per other hard partition that every query names; it cuts read cost, speeds queries and gives isolation. Use metadata filters for soft conditions inside a namespace (document type, date range, language). Keep metadata small and filterable, and keep the full text or large payloads in your own store, keyed by record ID.
Load in batches (up to 1,000 records or 2 MB per request), or use bulk import from object storage for large loads. Store the embedding model name and version in metadata, and re-embed into a new namespace or index when you change models; namespace aliases (2026) let you switch with no code change. Delete explicitly when source data is deleted: Pinecone will not know otherwise.
Estimate cost before you launch: GB stored, writes per day, and, most importantly, queries per day × GB per namespace. If a single large namespace has a steady high query rate, compare the on-demand bill with Dedicated Read Nodes. Use hybrid search (dense plus sparse or full-text) and a reranker for user-facing RAG, since pure dense search misses exact names and codes. Measure recall on a held-out set of queries with known answers, and if you need read-your-writes, check LSNs rather than adding sleeps. If you need the data to stay in your cloud account, or you outgrow the pricing, compare BYOC with self-hosted Milvus or pgvector.
quiz: What is a slab in Pinecone, and why is it immutable? || A slab is a file on object storage holding a batch of records with their vector index, compressed vectors and metadata bitmaps. @@ tidb
value: TiDB is an open-source distributed SQL database from PingCAP. It speaks the MySQL protocol, so most MySQL drivers, ORMs and tools work with it, but it stores data across many machines, replicates every piece with Raft, scales by adding nodes, and survives the loss of a machine without losing committed data. Its second promise is HTAP (hybrid transactional and analytical processing): the same database serves small, fast transactions and large analytical queries on fresh data, without an ETL pipeline to a separate warehouse.
The problem it solves is the sharded MySQL. Many companies, especially in fast-growing Chinese and Southeast Asian internet businesses where PingCAP started, ran hundreds of MySQL instances split by user ID or by table, with the routing logic in the application. Cross-shard transactions, resharding and analytics across shards were painful. TiDB replaces that with one logical database. It is used for order systems, payments, user accounts, SaaS metadata and real-time dashboards, often at tens of terabytes.
It stands on two L1 concepts. Distributed SQL (newsql) gives it the core design: SQL on top of a transactional key-value store split into ranges, each range replicated by consensus, with distributed transactions that keep ACID across ranges. HTAP (htap) gives it the second half: TiFlash, a columnar replica of chosen tables, kept up to date from the same replication log, so the optimizer can send scans and aggregations to columns and point lookups to rows. As of October 2026, 8.5 is the current long-term-support line for self-managed TiDB (8.5.8, August 2026), and TiDB Cloud runs a newer object-storage-based architecture called TiDB X.
terms: TiDB server — the stateless SQL layer: it parses, optimizes and executes queries and holds no data.
TiKV — the distributed transactional key-value store that holds rows and indexes; it uses RocksDB on each node.
Region — a contiguous range of keys (256 MiB by default in recent versions) and the unit of replication and movement.
PD (Placement Driver) — the cluster brain: it stores the Region map, balances Regions and issues global timestamps.
TSO (timestamp oracle) — PD's service that hands out strictly increasing timestamps used as transaction start and commit times.
Percolator — Google's 2010 protocol for distributed transactions on a key-value store, using a primary lock and two phases.
TiFlash — the columnar storage engine; it holds Raft learner replicas of chosen tables for analytics.
Raft learner — a replica that receives the Raft log but does not vote and does not count toward the write quorum.
MPP — massively parallel processing: TiFlash nodes exchange data among themselves to run joins and aggregations in parallel.
history: PingCAP was founded in Beijing in 2015 by Max Liu (Liu Qi), Ed Huang (Huang Dongxu) and Cui Qiu, engineers who had worked together on Redis infrastructure at Wandou Labs and written Codis, an open-source Redis clustering system. They took the design of Google's Spanner and F1 papers (2012–2013), a SQL layer over a globally replicated key-value store, and rebuilt it without Google's special hardware: Spanner uses atomic clocks and GPS (TrueTime), while TiDB uses a central timestamp service. They chose Raft (2014) over Paxos because it was easier to implement correctly, and wrote TiKV in Rust, one of the first large Rust systems in production.
TiDB 1.0 became generally available in October 2017. TiKV joined the Cloud Native Computing Foundation in 2018 and graduated in September 2020, so it is also used without TiDB. TiDB 3.0 (2019) added pessimistic transactions, which behave more like MySQL under contention. TiDB 4.0 (2020) introduced TiFlash, and the VLDB 2020 paper "TiDB: A Raft-based HTAP Database" (Huang and colleagues) explained the key idea: a columnar replica fed by Raft learners. In its tests, adding analytical clients reduced transactional throughput by at most about 10%, and replication lag to TiFlash usually stayed below one second. TiDB 5.0 (2021) added the MPP engine and faster commits (async commit and one-phase commit). TiFlash became open source in 2022.
Later releases focused on operations and the cloud: resource control for many tenants in one cluster (7.x), long-term-support lines 7.5, 8.1 (May 2024) and 8.5 (December 2024), and TiDB Cloud's serverless tiers. In October 2025 PingCAP announced TiDB X, which keeps the SQL and Raft design but makes object storage such as Amazon S3 the source of truth, with local caches, one LSM tree per Region, and separate compute pools for compaction, DDL and loading.
how: Start with the newsql idea: map SQL onto ordered key-value pairs. The TiDB server encodes each row as a key t{table_id}_r{row_id} with the column values as the value, and each secondary index entry as a key t{table_id}_i{index_id}{indexed values} pointing to the row ID. Because TiKV keeps keys sorted, all rows of a table are adjacent, an index range scan is a key range scan, and a primary-key lookup is a point get. Each key also carries a version (a timestamp), and newer versions sort first; this is MVCC, which lets readers see a consistent snapshot while writers create new versions.
TiKV splits the sorted key space into Regions. When a Region grows past its limit (256 MiB by default in recent versions; 96 MiB in older ones), it splits in two; small neighbours merge. Each Region is replicated, three copies by default, on different TiKV nodes, and each Region's replicas form their own Raft group. So a cluster runs thousands of small Raft groups ("Multi-Raft"), not one big one. A write goes to the Region's leader, which appends it to its Raft log, sends it to followers, and applies it to RocksDB once a majority (2 of 3) has stored it. PD watches Region sizes and load, and moves replicas and leaders between nodes to balance them; adding a node simply gives PD a new place to move Regions to.
Transactions span Regions with a Percolator-style protocol, using PD's TSO as the global clock. A transaction gets a start timestamp, reads the snapshot at that time, and buffers its writes in the TiDB server. At commit, it picks one key as the primary. Phase one, prewrite: it writes every changed key with a lock that points to the primary, failing if another transaction committed a newer version since the start timestamp. Phase two: it gets a commit timestamp and commits the primary key by replacing its lock with a commit record; at that moment the whole transaction is committed. The other keys are cleaned up afterwards, and a reader that meets a leftover lock checks the primary to learn the outcome. Async commit removes one round trip by treating the transaction as committed once all prewrites succeed, and one-phase commit skips the protocol for transactions that touch a single Region. The default mode is pessimistic: DML statements take locks as they run, as in MySQL, instead of failing at commit. The isolation level is snapshot isolation, which TiDB calls repeatable read.
The SQL layer is a cost-based optimizer and a distributed executor. It pushes filters, projections, limits and partial aggregations down to TiKV's coprocessor, so each Region returns only what is needed. Because TiDB servers are stateless, you scale SQL processing by adding servers behind a load balancer.
Now the htap part. For a table you mark with ALTER TABLE orders SET TIFLASH REPLICA 1, each of its Regions gets an extra replica on a TiFlash node, joined to the Region's Raft group as a learner. The learner receives the same log as the followers, but it does not vote and the leader does not wait for it, so TiFlash adds almost no latency to transactions and its failure does not block writes. TiFlash decodes the log entries into rows, drops prewrites that were rolled back, and periodically converts batches of rows into columns. Its DeltaTree engine keeps recent changes in a delta layer, indexed by a B+ tree, and older data in a stable columnar layer, merging them in the background.
Reads on TiFlash are still consistent. Before a query reads a Region, the learner asks the leader for its current commit index (a read index), waits until it has applied the log up to that point, and then reads the snapshot at the query's start timestamp. So an analytical query sees every transaction committed before it started, usually after a wait of milliseconds. The optimizer chooses per table, from cost estimates, whether to read TiKV rows (best for point lookups and selective indexes) or TiFlash columns (best for scans and aggregations), and can use both in one query. For big joins and aggregations, the MPP mode splits the work across TiFlash nodes, which shuffle data among themselves like a small Spark cluster.

example: An online marketplace keeps 1 billion order rows of about 200 bytes each in TiDB: about 200 GB per copy, 600 GB with three TiKV replicas, before RocksDB compression. With 256 MiB Regions, the table has about 200 GB / 0.25 GB = 800 Regions, so 2,400 Region replicas spread over, say, 6 TiKV nodes: about 400 per node, each with its own small Raft group.
A transaction: "insert an order and decrement stock". Assume TiDB, PD and TiKV are in one data centre with 0.5 ms round trips, and that one Raft write (leader plus one follower writing to disk) takes about 1.5 ms. Classic two-phase commit costs: get start timestamp (0.5 ms), prewrite both keys in parallel (one Raft write, about 1.5 ms), get commit timestamp (0.5 ms), commit the primary (another Raft write, about 1.5 ms). That is about 4 ms, against roughly 1 ms for a single MySQL server. Async commit drops the second Raft write from the client's wait: about 2.5 ms. If both keys were in one Region, one-phase commit would need just one Raft write. Now spread the three replicas over three cloud regions 30 ms apart: every Raft write needs at least one 30 ms round trip, so commits take 30–70 ms. Distributed consensus pays network distance on every commit.
An analytical query: total sales per country for the last 90 days, which touch about 300 million rows. On TiKV, each row is read whole, about 200 bytes, so the scan reads about 60 GB and decodes MVCC versions. At about 0.5 GB/s per node across 6 nodes, that is about 20 seconds, and it competes with the order traffic on the same disks and CPUs. On TiFlash, the query reads only three columns: country (about 2 bytes), amount (8 bytes) and created_at (8 bytes), so 18 bytes per row, about 5.4 GB, and columnar compression of 3–5× brings that to roughly 1–2 GB. Two TiFlash nodes scanning at about 2 GB/s each finish in under a second, on separate machines.
Freshness: an order committed at 12:00:00.000 reaches the TiFlash learner a few hundred milliseconds later. A dashboard query that starts at 12:00:00.100 asks for a read index, waits until the learner catches up, and then includes the order. The cost of freshness is a short wait, never a wrong answer.
intuition: One ledger, written once, delivered to two clerks: one files each entry by customer for quick lookups, the other copies the same entries into column-by-column summary sheets for reports, and both agree on what the ledger said at any moment.
The design is natural because replication already exists. A distributed database must send every change to other machines for durability. TiDB notices that the replication log is a complete, ordered description of every change, so a columnar replica is just one more subscriber that stores the data differently. Making it a non-voting learner keeps analytics off the transaction's critical path, and the read-index check makes it consistent anyway. On the transactional side, splitting data into many small Regions, each with its own Raft group, turns the hard problem "replicate a big database" into many easy problems that PD can move around freely.
mistakes: People often think TiDB is MySQL with sharding added. In fact it is a different engine with the MySQL protocol. Some MySQL features behave differently or are missing (for example, auto-increment IDs are unique but not consecutive across servers), and latency per transaction is higher. Test your application, not just your SQL syntax.
People often think TiFlash replicas are eventually consistent copies like a reporting replica. In fact a TiFlash read waits for its learner to catch up to the leader's commit index and reads the snapshot at the query's timestamp, so it sees the same data a TiKV read would.
People often think adding nodes makes every transaction faster. In fact adding nodes adds capacity, not speed. Each commit still needs timestamps from PD and Raft round trips, so single-transaction latency stays around a few milliseconds in one data centre, and much more across regions.
People often think auto-increment or timestamp primary keys are fine. In fact sequential keys send every insert to the last Region, so one TiKV node takes all writes (a hotspot). Use AUTO_RANDOM, SHARD_ROW_ID_BITS or another key that spreads writes.
friction: There are many parts to run: TiDB servers, PD, TiKV, TiFlash, plus tools for backup, change data capture (TiCDC) and migration (DM). Kubernetes (TiDB Operator) or TiDB Cloud make this easier, but upgrades, capacity planning and Region-level debugging still need specialist knowledge.
Latency is the price of distribution. Every transaction pays PD and Raft round trips, so latency-sensitive workloads that fit on one MySQL server are faster there. PD's timestamp service runs in one place, so in multi-region deployments, servers far from the PD leader pay a long round trip per transaction. Hot Regions, from sequential keys or one very popular row, are the most common production problem.
Large transactions are limited by memory in the TiDB server and by the size of prewrite batches, so huge updates should be split into batches. Analytics on TiFlash costs extra storage and nodes for each replicated table, and the MPP engine is good for joins and aggregations on fresh data but is not a full data warehouse or lakehouse for petabytes of history.
MySQL compatibility is broad but not complete: stored procedures, triggers and some functions and isolation behaviours differ. Finally, classic TiDB and the TiDB X architecture used by TiDB Cloud are diverging, so check which one a feature or benchmark refers to.
practice: Choose TiDB when one MySQL server is no longer enough for your data or write rate, you want SQL transactions across that data, and you want analytics on fresh data without a separate pipeline. If your data fits on one MySQL or Postgres server with replicas, stay there.
Design keys to spread writes: use AUTO_RANDOM for primary keys of insert-heavy tables, or pre-split Regions before a big load. Keep transactions small (thousands of rows, not millions), and batch large updates. Keep the default pessimistic mode for MySQL-like behaviour under contention.
Add TiFlash replicas only for tables that analytical queries actually scan, and check the plan with EXPLAIN: look for the TiFlash (mpp[tiflash]) tasks. You can force the choice per session or query when the optimizer guesses wrong. Use resource control to keep reports from starving the transaction workload, and put TiFlash on separate nodes.
Monitor the TiDB Dashboard's key visualizer to find hotspots, and watch PD leader placement, Raft write latency, and TiFlash replication lag. For multiple regions, place PD leaders and Raft leaders near the writers with placement rules, and accept higher commit latency for cross-region durability. Use TiCDC to stream changes into Kafka or a lakehouse when you need history beyond what TiFlash should hold.

@@ scylla
value: ScyllaDB is a wide-column database that is compatible with Apache Cassandra: the same data model, the same CQL query language and wire protocol, the same drivers and a compatible file format. It also offers a DynamoDB-compatible API called Alternator. What it changes is the engine. Cassandra runs on the Java virtual machine with thread pools, locks and a garbage collector. ScyllaDB is written in C++ on the Seastar framework, with one thread pinned to each CPU core, each thread owning its own slice of the data, memory and network connections, and no locks between them.
The problem it solves is cost and tail latency at high throughput. A large Cassandra deployment often needs many nodes, and its p99 latency suffers from garbage-collection pauses and from threads competing for locks and caches. Moving the same workload to ScyllaDB typically needs fewer, larger nodes, and the latency is steadier. Discord's 2023 migration is the best public example: its message store went from 177 Cassandra nodes to 72 ScyllaDB nodes, and p99 read latency for historical messages fell from 40–125 ms to about 15 ms.
It stands on two lower concepts. From the L1 concept nosql (distributed key-value and wide-column stores) it takes Cassandra's design: partitions placed by consistent hashing, tunable consistency with leaderless replication, and log-structured storage. From the L2 concept shardpercore (thread-per-core, shared-nothing) it takes the execution model: each core is an independent server, cores communicate by passing messages, and the software manages its own memory, cache and I/O instead of relying on the operating system. The layer above, applications that need millions of small reads and writes per second with predictable latency (messaging, ad tech, IoT, feature stores, fraud detection), gets the Cassandra model at a lower cost per operation. As of October 2026, the current release is ScyllaDB 2026.3, under a source-available license.
terms: Partition key — the column(s) hashed to decide which nodes store a row; all rows with the same partition key form one partition.
Clustering key — the column(s) that sort rows inside a partition, so range reads within a partition are sequential.
Shard — in ScyllaDB, one CPU core with its own thread, memory, data and queues; not a separate server.
Seastar — the open-source C++ framework of futures, per-core reactors and message passing that ScyllaDB is built on.
Shard-aware driver — a client driver that computes which core owns a partition and sends the request straight to that core.
Tablet — a small range of a table's partitions that ScyllaDB can move between nodes and cores independently.
SSTable — an immutable sorted file on disk; memtables are flushed into SSTables, and compaction merges them.
Consistency level — how many replicas must answer, such as ONE, QUORUM (2 of 3) or ALL.
Tail latency — the slowest requests, such as the 99th percentile (p99), which users of large fan-out systems feel most.
history: Avi Kivity and Dor Laor, who had led the development of the KVM hypervisor, founded Cloudius Systems in Israel to build OSv, an operating system for cloud virtual machines. To make applications fast on it, they wrote Seastar, a C++ framework for asynchronous, per-core programming. In late 2014 they decided that the most valuable target for Seastar was a database, and picked Cassandra, which was popular but known for heavy hardware use and latency spikes. They kept its protocol, data model and file format, so existing users could switch without rewriting applications. ScyllaDB was released as open source under the AGPL in September 2015, reached 1.0 in 2016, and the company renamed itself ScyllaDB.
Later versions added features beyond Cassandra. Workload prioritization lets operational and analytical traffic share a cluster with separate CPU and I/O shares. Alternator added the DynamoDB API. Change data capture, incremental compaction and lightweight transactions followed. In 2023 and 2024 ScyllaDB moved schema and topology management onto the Raft consensus protocol, ending the "one topology change at a time" rule inherited from Cassandra's gossip, and introduced tablets (version 6.0, 2024), which replace Cassandra's fixed token ranges with small, movable ranges. Tablets are now the default for new keyspaces.
In December 2024 the company announced that it would stop publishing an AGPL open-source edition: 6.2 was the last one. Starting with 2025.1 (2025), there is one release stream under a source-available license, with a free tier for smaller deployments. Releases are now named by year and number (2025.1 to 2025.4, then 2026.1 to 2026.3). Recent versions added vector search and full-text search.
how: The execution model comes from shardpercore. At start, ScyllaDB starts one thread per core and pins it there. It takes almost all of the machine's memory up front and divides it evenly: on a 32-core server with 256 GB, each shard owns about 7–8 GB. Each shard runs a reactor, an event loop that polls for network and disk events and runs small tasks written as futures (callbacks chained with .then()). A shard never blocks: a disk read returns a future and the shard runs other work until the data arrives. When a shard needs something another shard owns, it sends a message through a lock-free queue between the two cores and gets a future back. There are no mutexes on the data path, no context switches between threads, and no cache lines bouncing between cores, which on modern CPUs cost tens to hundreds of nanoseconds each time.
Data is partitioned twice. Across the cluster, the nosql design applies: the partition key is hashed with Murmur3 to a token, and the token decides which nodes hold replicas (three, for replication factor 3). Inside a node, the same partition belongs to exactly one shard. With tablets, the cluster keeps a Raft-replicated map from token ranges (tablets) to replicas, where each replica names both a node and a shard. A shard-aware driver keeps a connection to every shard of every node, computes the owner, and sends each request directly to that core. If a request arrives at the wrong shard, the receiving shard forwards it with a message, which costs a little extra CPU but stays correct.
The write path is Cassandra's LSM design, done per shard. A write is appended to the shard's commit log (a write-ahead log for durability), applied to the shard's memtable in memory, and acknowledged. Full memtables are flushed into immutable SSTables, and background compaction merges SSTables to drop overwritten and deleted data. Reads merge the memtable with the relevant SSTables, using Bloom filters and partition indexes to skip files. A coordinator replica sends each request to the replicas required by the consistency level; with QUORUM and three replicas, two must answer.
Compatibility is a design constraint, not an afterthought. ScyllaDB speaks the CQL binary protocol, so Cassandra drivers work; it reads and writes SSTables in Cassandra's format, so data can be loaded from Cassandra; and it keeps the same replication strategies, consistency levels, Paxos-based lightweight transactions and repair. Because it is written in C++ with explicit memory management, there is no garbage collector and so no stop-the-world pauses. C++ is also what makes the per-core memory, the custom allocator and the direct I/O path possible, since a JVM controls its own heap, threads and file access.
ScyllaDB replaces the operating system's caching and scheduling with its own. It does not use the Linux page cache: SSTables are read with direct I/O, and a row cache inside each shard keeps recently used rows in their parsed form, so a cache hit needs no parsing or copying. Memtables and cache use a log-structured memory allocator that can compact memory to avoid fragmentation, which a general allocator cannot do. A user-space I/O scheduler, calibrated at install time by a tool that measures the disk's real throughput and latency, keeps the disk just busy enough and divides its capacity between classes (queries, commit log, compaction, streaming) by shares. A CPU scheduler does the same for tasks. Controllers adjust compaction shares to the backlog: compaction runs faster when there is debt and slower when queries need the capacity. This is how ScyllaDB keeps compaction from causing the latency spikes that are common in LSM stores.
Elasticity comes from tablets and Raft. Each table is split into many tablets, and tablets are split or merged as the table grows or shrinks. A background load balancer moves tablets between shards and nodes by streaming whole SSTables, so a new node starts taking traffic as soon as its first tablets arrive, and several nodes can be added at once because topology changes are serialized through Raft rather than gossip. With Cassandra's older token-range design, adding a node meant streaming a large fixed share of data and then running a cleanup on every other node.

example: A messaging service stores messages in a table partitioned by (channel_id, bucket), where bucket is a 10-day time window, and clustered by message_id. It runs ScyllaDB on nodes with 32 vCPUs, 256 GB of RAM and 7.5 TB of NVMe SSD, with replication factor 3.
Per node: suppose 2 cores are left for network interrupts, so 30 shards. Each shard owns about 256 GB × 0.9 / 30 ≈ 7.7 GB of memory for memtables and cache, and, if the node holds 4.5 TB, about 4.5 TB / 30 = 150 GB of data.
Throughput budget: suppose a cached single-row read costs about 20 µs of CPU on its shard. One shard can then serve about 1 s / 20 µs = 50,000 reads per second, and 30 shards about 1.5 million per node. Reads that miss the cache also need one or two NVMe reads of about 100 µs each, but the shard does other work while it waits, so they cost latency more than CPU.
Cluster size: the service needs 3 million reads per second at consistency ONE plus 500,000 writes per second. Each write goes to 3 replicas, so the cluster does 1.5 million replica writes per second. If a write also costs about 20 µs of CPU, total CPU is 3,000,000 × 20 µs + 1,500,000 × 20 µs = 90 core-seconds per second, about 90 shards, or 3 nodes. Storage decides the rest: 9 TB of data × 3 replicas = 27 TB. With 50% CPU headroom for compaction, repairs and peaks, plan for 6 nodes, each holding about 4.5 TB, 60% of its disk, which leaves room for compaction.
Now the hot partition. A popular channel receives 200,000 reads per second for its current bucket. That partition lives on exactly one shard on each of its 3 replicas. Even if reads are spread perfectly across the 3 replicas, that is about 67,000 reads per second per shard, above the 50,000 that one core can serve. Adding nodes does not help, because the partition cannot be split across cores. The fixes are in the data model and the application: smaller buckets (split the hot partition), a cache or request coalescing in front of the database (Discord's Rust data services merge identical concurrent reads into one query), or both. Shard-per-core makes the normal case very efficient, and it makes the limit of a single hot key very visible.
Tail latency, finally: a JVM-based node with a 200 ms garbage-collection pause adds 200 ms to every request it holds. A user page that fans out to 20 partitions has a high chance of meeting at least one slow node. ScyllaDB has no garbage collector, so this source of p99 spikes disappears; the remaining tail comes from disk, compaction and network, which its schedulers control.
intuition: A restaurant kitchen where each cook has a private station, ingredients and orders, and passes notes to other cooks instead of sharing knives and fighting over the stove.
The design is natural once you see where time goes in a modern server. CPUs have become much faster, and NVMe disks and 25–100 Gb networks deliver millions of operations per second, but locks, context switches and shared caches have not become cheaper. When many threads share data, a large part of each request is spent coordinating rather than working. A database partition is already a natural unit of independence, so ScyllaDB extends partitioning from machines down to cores: each core becomes a small, single-threaded server that needs no locks. Taking over memory, caching and I/O scheduling follows from the same idea. The operating system manages resources for general programs, while the database knows exactly which rows matter, which I/O is urgent, and which work can wait.
mistakes: People often think ScyllaDB removes Cassandra's data-modeling rules. In fact it keeps the same model: queries must name the partition key, there are no joins, secondary indexes and materialized views have costs, and large or hot partitions hurt. A schema that is bad on Cassandra is bad on ScyllaDB, only faster.
People often think adding nodes fixes any overload. In fact a single hot partition is served by one shard on each replica, so it is limited to what about three cores can do. Only splitting the partition or caching in front of it helps.
People often think shard-per-core means one core per node handles all requests and the rest wait. In fact every core is a full server for its own partitions; with shard-aware drivers, requests go straight to the owning core, and all cores work in parallel.
People often think ScyllaDB is still open source under the AGPL. In fact the last AGPL release was 6.2 (2024); since 2025.1, ScyllaDB is source-available, with a free tier and paid licenses for larger clusters. Check the license terms before you plan a large deployment.
friction: The licensing change is the biggest non-technical friction. Teams that chose ScyllaDB as an open-source database must either accept the source-available terms, pay, stay on old AGPL versions without fixes, or move to Cassandra (which in version 5.0 also improved performance) or another system.
Technically, ScyllaDB inherits every limit of the Cassandra model: query-driven denormalized tables, eventual consistency by default, lightweight transactions that need extra round trips, tombstones from deletes that slow reads until compaction, and repair that must run to keep replicas in sync. Shard-per-core adds its own: a hot partition is limited to one core per replica, and a skewed workload leaves some cores busy while others idle.
ScyllaDB also needs the right hardware and settings to show its advantage: fast NVMe disks, enough cores, the setup scripts that tune interrupts and CPU pinning, and preferably no noisy neighbours. On small virtual machines or with slow network disks, the gains shrink. Compatibility with Cassandra is high but not total: some newer Cassandra features do not exist in ScyllaDB, and some ScyllaDB features do not exist in Cassandra, so a later move back is not automatic. The ecosystem of tools, managed services and community knowledge is smaller than Cassandra's.
practice: Consider ScyllaDB when you have a Cassandra-style workload (high-volume reads and writes by key, with predictable access patterns) and either a large Cassandra bill or a p99 latency problem. Model the data as for Cassandra: one table per query pattern, partition keys that spread load, partitions that stay below roughly 100 MB, and time buckets for growing data such as messages or events.
Always use a shard-aware (and tablet-aware) driver; without it, many requests land on the wrong core and must be forwarded. Use prepared statements and token-aware load balancing. Choose consistency levels deliberately: LOCAL_QUORUM for reads and writes when you need read-your-writes inside one data centre, ONE for high-volume reads that can tolerate a little staleness.
Run the provided setup and I/O calibration tools on every node, use local NVMe, and keep nodes uniform so tablets and shards balance. Watch per-shard metrics, not only node averages: one shard at 100% CPU while others sit at 30% points to a hot partition. Use workload prioritization to keep batch or analytical jobs from hurting online traffic. Keep repairs scheduled (ScyllaDB Manager), and design deletes carefully to avoid tombstone-heavy partitions. Finally, read the current license terms, and test a migration with your own data and query mix, because published speed-ups depend heavily on hardware and workload.

value: FoundationDB is a distributed, ordered key-value store with ACID transactions that are strictly serializable: every transaction behaves as if all transactions ran one at a time, in an order that matches real time. Keys and values are byte strings, keys are sorted, and a transaction can read and write any keys anywhere in the cluster. That is the whole interface. Richer data models (tables, documents, records with secondary indexes, queues, graphs) are built on top as "layers", libraries that map them onto sorted keys.
The problem it solves is the hardest part of a distributed database, done once and done correctly. Many systems in the 2000s gave up transactions to scale (the NoSQL trade-off), and application teams then had to deal with partial failures and inconsistent indexes themselves. FoundationDB keeps full transactions and scales out by splitting the work into separate roles. It is used where correctness matters more than features: Apple's CloudKit stores data for its users on it through the Record Layer, and Snowflake keeps its metadata catalog in it.
It stands on two lower concepts. From newsql (distributed SQL and transactional stores, L1) it takes the core goal and techniques: data split into key ranges across machines, a global ordering of transactions, multi-version concurrency control, and replication that survives failures. FoundationDB is the rare system in that family that stops at key-value transactions and leaves SQL to layers. From dst (deterministic simulation testing, L2) it takes its development method: the real database code runs inside a single-threaded simulator that controls time, network and disks, injects failures, and can replay any failing run exactly. That method is the reason engineers trust the system. As of October 2026, the stable release line is 7.3, with 7.4 and 8.0 in development.
terms: Strict serializability — transactions appear to run one at a time, in an order consistent with when they actually committed.
Read version — the version (logical timestamp) at which a transaction reads a consistent snapshot of the database.
Commit version — the version the sequencer gives a committing transaction; it defines its place in the global order.
Optimistic concurrency control (OCC) — transactions run without locks and are checked for conflicts only at commit; conflicting ones abort and retry.
Sequencer — the single process that hands out read and commit versions, about one million versions per second.
Resolver — a process that checks committing transactions for read-write conflicts within its key range.
Log server — a process that stores committed mutations durably, in order, until storage servers have applied them.
Storage server — a process that holds key ranges, keeps recent versions in memory and serves reads.
Layer — a library that implements a data model (tables, documents, indexes) on top of the ordered key-value API.
Flow — FoundationDB's actor-based extension of C++, which makes all concurrency deterministic under simulation.
history: Dave Rosenthal, Dave Scherer and Nick Lavezzo, who had worked together at the analytics company Visual Sciences, started FoundationDB in 2009. Their unusual first step was to build the testing tool before the database. They created Flow, a language that adds actors and async/await-style concurrency to C++, so that the entire system could run in a deterministic simulator. Early in the project, fault injection found two independent bugs in Apache ZooKeeper, which they had planned to use, so they wrote their own Paxos implementation instead.
FoundationDB 1.0 became generally available in August 2013. At the time it was a rare combination: a NoSQL-style scalable store with full ACID transactions. Will Wilson's 2014 Strange Loop talk "Testing Distributed Systems w/ Deterministic Simulation" made its testing approach famous. In March 2015 Apple acquired the company and removed the downloads, which left its users stranded. Inside Apple it became a foundation for iCloud services.
In April 2018 Apple released FoundationDB as open source under the Apache 2.0 license. Layers followed: a MongoDB-compatible Document Layer (2018), and the Record Layer (paper at SIGMOD 2019), which provides schemas, secondary indexes and queries, and lets CloudKit run billions of small logical databases in shared clusters. The SIGMOD 2021 paper "FoundationDB: A Distributed Unbundled Transactional Key Value Store" (Zhou and colleagues) described the architecture and its production results. Version 7 split the proxy role into read-version proxies and commit proxies and added new storage engines (Redwood, a faster B-tree, and RocksDB). Several former FoundationDB engineers later founded Antithesis, which offers deterministic simulation testing for other software.
how: The architecture is "unbundled": each job of a transactional database runs in its own kind of process, and each kind scales or recovers separately. A small group of coordinators runs Paxos to store the cluster's configuration and elect a cluster controller. The cluster controller recruits the other roles. The transaction system has one sequencer, several proxies and several resolvers, and keeps no durable state. The log system is a set of log servers that store committed mutations durably. The storage system is many storage servers, each holding some key ranges; together they act like one distributed B-tree. A data distributor moves and splits key ranges to balance load, and a ratekeeper slows new transactions when storage servers fall behind.
A transaction starts by asking a proxy for a read version. The proxy batches requests from many clients and asks the sequencer for the latest committed version, so every transaction sees everything committed before it started; this is the "strict" part of strict serializability. The client then reads directly from storage servers at that version. Each storage server keeps the last 5 seconds of versions in memory on top of its on-disk B-tree (a modified SQLite B-tree in the classic ssd engine), so it can serve any snapshot in that window. Writes are not sent anywhere yet; the client library buffers them along with the key ranges it read (read conflict ranges) and wrote (write conflict ranges).
Commit is where the newsql machinery runs. The client sends its writes and conflict ranges to a commit proxy. The proxy batches transactions and gets a commit version from the sequencer. It sends each transaction's conflict ranges to the resolvers responsible for those keys. A resolver remembers which key ranges were written by recently committed transactions, at which versions. If any key that this transaction read was written by another transaction with a version after this transaction's read version, the transaction conflicts and is aborted; the client library retries it automatically. Otherwise the proxy sends the mutations, tagged by the storage servers that will need them, to the log servers, and every log replica must make them durable on disk before the proxy reports success. Storage servers pull mutations from the log servers asynchronously and apply them. There are no locks anywhere: OCC replaces them, which is efficient when conflicts are rare (0.73% in the paper's production cluster) and painful when they are not.
The 5-second window explains the best-known limit. Versions advance about one million per second, and resolvers and storage servers keep only about 5 seconds of history, so a transaction whose read version is older than that fails with transaction_too_old. Transactions are also limited to 10 MB of affected data, keys to 10 KB and values to 100 KB. These limits keep the in-memory parts of the system small and fast.
Recovery is simple because the transaction system is stateless. If the sequencer, a proxy, a resolver or a log server fails, FoundationDB does not repair it; it replaces the whole transaction system. The cluster controller recruits a new sequencer, which locks the old log servers, finds the last version that was durably logged, recruits new proxies, resolvers and logs, and starts a new generation from that version. In the paper's production traces, the median recovery took about 3 seconds and the 90th percentile about 5 seconds. Storage server failures are handled differently: the data distributor re-replicates their key ranges from other copies while the cluster keeps running.
Now the dst half. All FoundationDB code is written in Flow, whose actors compile to callbacks on a single-threaded event loop. In production the loop talks to the real network and disks. In simulation the same code runs a whole cluster of simulated machines inside one process, with simulated network, disks and clocks, driven by one random seed. The simulator injects faults much more often than reality does: machine, rack and data-centre failures, network partitions, clogged connections, slow and full disks, reboots and processes that come back after being declared dead. Code paths also contain hooks that randomly choose unusual but legal behaviour (a timeout that fires early, a buffer that is always tiny). Test workloads check invariants; for example, the "cycle" test arranges keys in a ring and runs transactions that must keep the ring intact, so any isolation bug breaks it. Because everything is deterministic, a failing seed reproduces the bug exactly, as often as needed. Tens of thousands of simulations run every night.

example: An online shop keeps stock counts in FoundationDB. Key ("stock", item 42) holds 10. Two clients, A and B, each try to reserve one unit. Assume, as in the paper's production cluster, that a read takes about 1 ms and a commit about 22 ms on average.
Step 1. A and B both get read version 7,000,000. Both read stock = 10 and buffer the write stock = 9. Each records a read conflict range covering ("stock", 42).
Step 2. A commits first and gets commit version 7,020,000. The resolver sees that nothing has written ("stock", 42) between 7,000,000 and 7,020,000, so A succeeds and the log servers store stock = 9 at version 7,020,000.
Step 3. B commits and gets commit version 7,021,000. The resolver checks B's read range and finds a write to ("stock", 42) at 7,020,000, which is after B's read version 7,000,000. B aborts. The client library retries: new read version 7,022,000, reads 9, writes 8, and commits. The final value is 8, which is correct. Without the conflict check, both would have written 9 and one reservation would be lost.
Now the cost of contention. Each attempt takes about 1 + 22 = 23 ms from read version to commit. Suppose 50 clients hammer this one item continuously. Within any 23 ms window, roughly one transaction on that key can commit, and every other one that read before it must retry. So the item supports only about 1,000 / 23 ≈ 40 reservations per second, and most of the work is wasted retries. Two fixes follow from the mechanism. First, use an atomic operation: FoundationDB's atomic add sends "add −1" as a mutation that the storage servers apply later, so the client never reads the value, the transaction has no read conflict, and many clients can decrement in the same batch. You lose the ability to check "stock > 0" inside the same transaction, so a separate check is needed. Second, split the hot key: store the stock in 10 keys of 1 unit each (or 10 buckets), and let each client pick a random bucket. Conflicts now happen only within a bucket, so throughput rises about 10 times.
The 5-second limit in numbers: versions advance about 1,000,000 per second, so after 5 seconds the read version 7,000,000 is about 5,000,000 versions old. A batch job that reads 100,000 keys one by one at 1 ms each would need 100 seconds and fail with transaction_too_old. Split it into many small transactions, or read ranges in parallel, and keep each transaction to a few hundred milliseconds.
intuition: A bank with one ticket machine that stamps every transaction with a number, one clerk who checks that nothing you looked at changed while you were deciding, and a vault of ledgers that only accepts entries in stamped order.
The design is natural because it separates what must be ordered from what can be spread out. Ordering needs one place, the sequencer, but handing out numbers is so cheap that one process can do it millions of times per second. Conflict checking needs only recent history, so it fits in memory and can be split by key range. Durability needs disks and replication, so it goes to log servers, and serving data needs many machines, so it goes to storage servers. Each role is simple enough to reason about alone. The simulator is the other half of the idea: a distributed system has too many interleavings of messages and failures for people to imagine, so you let a machine explore them, deterministically, until rare bugs become common and reproducible.
mistakes: People often think FoundationDB is a SQL database. In fact its native interface is only ordered keys and values with transactions. SQL, documents or records come from layers, which you must choose, build or maintain; the Record Layer is the most complete one.
People often think FoundationDB transactions use locks and therefore wait under contention. In fact they are optimistic. Conflicting transactions abort and retry, so a hot key wastes work instead of queueing. Atomic operations, versionstamps and splitting hot keys are the tools for contention.
People often think the 5-second limit is a configuration default that you can raise. In fact it reflects how much version history the resolvers and storage servers keep in memory. Long-running work must be split into many transactions, using a key-range cursor or snapshot reads where a conflict check is not needed.
People often think deterministic simulation proves the system correct. In fact it finds bugs in the scenarios it explores; it is very good, not a proof. It also tests only code that runs inside the simulator, so client applications and layers need their own testing.
friction: The limits shape every design: transactions of at most 5 seconds and 10 MB, keys of 10 KB and values of 100 KB. Large objects must be split across keys, and long analytics must run as many small transactions or outside FoundationDB. Optimistic concurrency punishes hot keys, and the documentation also notes a limit of roughly 100,000 reads per second for a single hot key with triple replication.
Commit latency is not tiny. Every commit visits the sequencer, the resolvers and every log replica's disk, so commits take a few milliseconds in a good cluster and more under load (the paper's production cluster averaged about 22 ms). The design favours throughput and correctness over the lowest single-transaction latency.
The layers are your responsibility. Beyond the Record Layer, few layers are maintained, so most teams write their own mapping, indexes and schema migrations, which is where many application bugs live. There is no user-level access control inside the database: any client that can connect can read and write every key, so network isolation and an access-control layer are required.
Operating it also needs knowledge. Choosing processes per machine and roles, storage engines and redundancy modes, and reading its status output takes experience, and the public community is small compared with Postgres or Cassandra. The documentation describes testing up to about 500 processes and 100 TB of data; larger clusters may scale less than linearly.
practice: Use FoundationDB when you need a correct, scalable, transactional foundation and are willing to build or adopt a layer: metadata stores, catalogs, multi-tenant record stores, queues and schedulers, or the storage engine of a larger system. If you just need SQL, use a distributed SQL database built for that.
Learn the key-encoding tools first: the tuple layer (order-preserving encoding of typed values into bytes), subspaces (key prefixes per data type) and the directory layer (short prefixes for long names). Design keys so that data read together is adjacent, and so that writes spread across ranges rather than all hitting the end of one range.
Keep transactions short and small: aim for well under one second and under 1 MB. Make transaction code idempotent, because the client library retries it on conflicts and on some failures where the outcome is unknown. Use atomic operations for counters and versionstamps for ordered logs and queues, and use snapshot reads when you do not need a read to cause conflicts. Watch the conflict rate and the ratekeeper's throttling; both explain most performance surprises.
Run with triple redundancy and at least five machines in one data centre, use SSDs, and keep coordinators on separate machines. For a deeper understanding, read the SIGMOD 2021 paper and watch Will Wilson's simulation talk; if you build distributed systems yourself, consider writing them so they can run deterministically under a simulator from day one.
quiz: What are the main roles in a FoundationDB cluster? || Coordinators and the cluster controller (control), the sequencer, proxies and resolvers (transaction system), log servers (durability) and storage servers (data). The data distributor and ratekeeper balance data and control load.
How does FoundationDB detect that a transaction must abort? || The resolver compares the transaction's read conflict ranges with the writes of transactions that committed after its read version. If any key it read was written in that interval, the transaction aborts and the client retries it.
Why can FoundationDB recover from a failed proxy, resolver or log server in a few seconds? || The transaction system keeps no durable state apart from the logs. Recovery replaces the whole transaction system with a new generation that starts from the last durable log version, which took a median of about 3 seconds in production.
Fifty clients update one counter with read-modify-write, and each transaction takes about 25 ms. Roughly how many succeed per second, and how would you fix it? || About 1,000 / 25 = 40 per second, because overlapping transactions conflict and retry. Use an atomic add, which creates no read conflict, or split the counter into several keys and sum them on read.
Why did the FoundationDB team build the simulator before the database, and what does that cost? || Rare interleavings of failures cannot be found or reproduced reliably on real clusters, while a deterministic simulator finds them often and replays them exactly. The cost is that all code must use Flow and avoid any source of nondeterminism, such as real threads, clocks or unsimulated I/O.

@@ memcached
value: Memcached is a distributed in-memory cache with a deliberately small design. Each server is an independent process that keeps key–value pairs in RAM, supports a handful of commands (get, set, add, delete, increment, compare-and-swap) and evicts the least recently used items when memory is full. Servers do not know about each other: there is no replication, no persistence and no cluster protocol. The client library decides which server holds a key by hashing the key, so a fleet of 100 servers behaves like one large shared memory.
The problem it solves is database read load. Web pages read the same rows again and again: user profiles, friend lists, rendered fragments, results of expensive queries. Serving them from RAM takes a fraction of a millisecond, while a database query takes milliseconds and costs far more hardware per request. Memcached became the standard cache tier of the web in the 2000s, used by LiveJournal, Facebook, Wikipedia, YouTube, Twitter and many others. Facebook's deployment, described in a 2013 paper, served billions of requests per second and stored trillions of items. It is still widely used in 2026, directly and through managed services such as AWS ElastiCache; the current release line is 1.6 (1.6.45, July 2026).
It stands on the L1 concept cachelayer, the idea of a caching tier, and is its classic implementation. From that concept it takes the cache-aside pattern (read the cache, on a miss read the database and fill the cache), the arithmetic that hit rate decides database load, and the hard problems of staleness and thundering herds. Memcached's choice is to solve only the simplest part inside the server, a fast hash table with eviction, and to leave distribution, consistency and failure handling to clients and surrounding tools. The layer above, web and API services, gets microsecond reads and a database that only sees the misses.
terms: Cache-aside — the application reads the cache first; on a miss it reads the database and writes the result into the cache.
Slab allocator — memcached's memory manager: 1 MB pages are split into fixed-size chunks, one slab class per chunk size.
Slab class — a group of chunks of one size; sizes grow by a factor of 1.25 by default.
LRU — least recently used eviction; memcached keeps one segmented LRU (HOT, WARM, COLD) per slab class.
TTL — time to live; an expiry time set with each item, after which it is treated as missing.
Consistent hashing — mapping keys to servers on a hash ring so that adding or removing one server moves only that server's share of keys.
Lease — a token given to one client on a miss, so only it may fill the key; it prevents stale sets and thundering herds.
Thundering herd — many clients missing on the same hot key at once and all querying the database.
CAS — compare-and-swap: a set that succeeds only if the item has not changed since the client read it.
history: Brad Fitzpatrick wrote memcached in 2003 for LiveJournal, his blogging site, whose MySQL databases could not keep up with page views. The first version was written in Perl; Anatoly Vorobey soon rewrote it in C. The design followed from LiveJournal's situation: many web servers, each with spare RAM, and data that was expensive to compute but fine to lose. Pooling that RAM into one cache was the key idea; the memcached site's own example is that 50 web servers with 64 MB each give 3.2 GB of shared cache instead of 64 MB of duplicated cache.
Memcached spread quickly because it was simple, fast and had clients for every language. Last.fm's "ketama" library (2007) popularized consistent hashing for memcached clients, so adding a server no longer invalidated most of the cache. Facebook became the largest user and contributed heavily: it made the server multi-threaded with finer locks, used UDP for gets, and built mcrouter, a routing proxy it open-sourced in 2014. The NSDI 2013 paper "Scaling Memcache at Facebook" (Nishtala and colleagues) is the standard account of running a cache at that scale: leases, invalidation from the database commit log, regional pools, a "gutter" pool for failures and cold-cluster warm-up.
The server itself kept improving under its long-time maintainer, dormando. Version 1.5.0 (2017) made a segmented LRU and a background crawler for expired items the default. The 1.6 series (from 2020) added extstore, which keeps keys in RAM and moves large values to flash; the meta protocol, a more flexible command set that supports features like stale-while-revalidate; TLS; and, from 1.6.23, a built-in proxy configured in Lua. Meanwhile Redis, with richer data structures and persistence, took over many new caching use cases, but memcached remains common where a plain, very efficient cache is all that is needed.
how: Start with one server. Memcached keeps a hash table that maps each key to an item stored in memory. The table grows by doubling when it holds more than about 1.5 items per bucket, and a background thread moves buckets gradually so lookups never stop. Get, set and delete are constant-time operations: hash the key, follow the bucket's chain, compare keys. Several worker threads (four by default) each run their own event loop over their own client connections, and they share the hash table using fine-grained locks. This is why one server can handle 200,000 or more requests per second on ordinary hardware, with sub-millisecond latency. Commands travel over a simple text protocol (or the binary and newer meta protocols) on TCP, or on UDP for gets. CAS gives optimistic concurrency: a gets returns a 64-bit version number with the value, and a later cas command succeeds only if the item still has that number.
Memory is managed by a slab allocator, not by malloc for each item. At start, memcached reserves the memory you give it (-m) and hands it out in 1 MB pages. Each page is assigned to a slab class and cut into equal chunks: for example 96, 120, 152, 192 bytes and so on, each about 1.25 times the previous one, up to 1 MB. An item (a header of about 50 bytes, the key and the value) goes into the smallest chunk that fits it. This avoids fragmentation and makes allocation and freeing very fast, but it wastes the unused end of each chunk, on average around 10%, and up to about 20% when items sit just above a class boundary. Because a page belongs to one class, a change in item sizes over time can leave memory stuck in the wrong classes; a background "slab automove" process moves free pages between classes to correct this.
Each slab class has its own LRU, split since 1.5.0 into HOT, WARM and COLD queues with separate locks. New items enter HOT. Items that are read again move to WARM, which protects frequently used items from being pushed out by one-time reads or scans. Eviction happens from the tail of COLD. Hits do not move items under a lock on every read, which was the old design's bottleneck; a background maintainer thread does the moving. Expired items are freed lazily, when a get finds them, or by the LRU crawler, which walks the queues and reclaims them before they waste memory.
Distribution happens entirely in the client. The client library hashes the key and picks a server. With simple modulo hashing (hash(key) mod N), changing N remaps almost every key, which empties the cache. With consistent hashing, each server is placed at many points on a ring of hash values, a key goes to the first server point after its own hash, and removing one server moves only that server's keys to its neighbours. Clients send multi-gets in parallel to all servers involved, which is efficient but means a page's latency is the slowest of those servers. Large deployments put a proxy between clients and servers, such as mcrouter or memcached's built-in proxy, to manage pools, replicate hot pools, fail over and route by key prefix.
Now what the cachelayer concept contributes, and what memcached leaves to you. Hit rate decides everything: with a 99% hit rate, the database sees 1% of reads; at 95%, it sees five times as many. Consistency is the application's job. The usual rule is "update the database, then delete the cache key", never "set the cache key", because two concurrent writers can otherwise leave an old value in the cache. Facebook added two mechanisms on top. Leases: on a miss, the server gives one client a token, and only a set with a valid token is accepted, so a late set from a slow reader cannot overwrite a newer delete; other clients that miss during the same short window are told to wait and retry, which stops thundering herds. Invalidation from the commit log: a daemon reads the database's committed changes and sends deletes to every cache cluster, so every write path invalidates the cache, including ones the application forgot.

example: A social app serves 1,000,000 profile reads per second. Each profile is a 1,024-byte value with a 30-byte key. The database can safely serve 50,000 reads per second.
Hit rate needed. Database load = miss rate × 1,000,000. At a 95% hit rate the database sees 50,000 reads per second, exactly its limit, with no headroom. At 99% it sees 10,000. So the target is about 99%.
Memory. There are 200 million active profiles, and the app needs most of them cached to reach 99%. One item is about 50 + 30 + 1,024 ≈ 1,104 bytes, and it lands in the next slab class up, roughly 1,184 bytes, so each item costs about 1.2 KB. That gives 200,000,000 × 1.2 KB ≈ 240 GB. With 20 servers of 16 GB of cache each (320 GB), there is room for growth and for fragmentation. Each server handles 1,000,000 / 20 = 50,000 requests per second, well below what one server can do.
A server fails. With consistent hashing, its 1/20 of the keys (5%) now map to other servers, where they are missing. For the next minutes, the miss rate rises from 1% to about 1% + 5% = 6%, so the database sees about 60,000 reads per second, above its 50,000 limit. This is why Facebook sent such requests to a small "gutter" pool (about 1% of its servers) instead: the failed server's keys warm up in the gutter, and the database sees only the first miss for each key. With modulo hashing it would be far worse. Going from hash mod 20 to hash mod 19 keeps only about 5% of keys on their old server, so 95% of reads miss, and the database would receive about 950,000 reads per second and collapse.
A hot key. A celebrity's profile gets 20,000 reads per second. When she edits it, the app deletes the key. If the database query takes 5 ms, about 20,000 × 0.005 = 100 requests miss before anyone refills the cache, and all 100 query the database for the same row. With leases, the first miss gets the token and queries the database; the other 99 wait a few milliseconds and retry the cache. The database sees one query instead of 100. Facebook reported that leases cut the peak database query rate for a set of hot keys from 17,000 to 1,300 per second.
intuition: A row of identical coat-check counters where every ticket number tells you which counter to go to; the counters never talk to each other, and if one closes, only its coats are lost.
The design is natural because a cache is allowed to forget. Data in a cache is a copy, so losing it is a performance problem, not a correctness problem. That permission removes the expensive parts of a database: no disk writes, no replication protocol, no consensus, no recovery. What remains is a hash table and an eviction policy, which can be made very fast. Putting the routing in the client follows from the same thinking: if servers never coordinate, you can add more of them without limit, and the only shared knowledge is the list of servers and the hash function. Everything that is hard, such as consistency with the database, hot keys and failures, is pushed to the edges, where the application knows what each piece of data means.
mistakes: People often think a cache can be filled by writing the new value on every database write. In fact concurrent writers and readers can then leave an old value in the cache for its whole TTL. Delete the key after the database write, and use leases or CAS when stale sets matter.
People often think memcached's memory limit equals the amount of data it stores. In fact slab chunks waste part of their space, each item carries about 50 bytes of header, and the hash table and connections take a few percent more. Plan for 10–25% overhead, more if item sizes vary widely.
People often think losing one cache server is harmless because "it is only a cache". In fact the database is sized for the misses at normal hit rates. A sudden drop in hit rate, from a failure, a restart, a rehash or a deploy that changes key names, can overload the database and cause an outage.
People often think memcached and Redis are interchangeable. In fact memcached is a multi-threaded, memory-efficient key–value cache with no persistence or data structures, while Redis offers lists, sets, sorted sets, scripting, persistence and replication. For a plain cache of blobs at very high throughput, memcached is simpler; when you need structures or durability, Redis or Valkey fits better.
friction: Consistency with the source of truth is entirely the application's problem. Races between reads that fill the cache and writes that invalidate it can leave stale data for a full TTL, and multi-region deployments need extra machinery (Facebook's remote markers) to avoid serving data older than replication lag. There is no way to invalidate "all keys for user 42" except by tracking keys yourself or putting a version number into key names.
Failures are handled outside the server. Without replication, a lost server is a cold spot that the database must absorb, and a restart loses everything (the warm restart feature can keep memory across a planned restart). Hot keys are limited by one server's capacity unless a proxy replicates them. Multi-gets that fan out across many servers suffer from the slowest server and from incast, many responses arriving at one client at once.
Memory efficiency has limits. Slab classes waste space when item sizes vary, and the slab automover reacts slowly to shifts. Items above 1 MB need a larger configured item size, which increases waste. The text protocol and default setups have no authentication; UDP was abused for large reflection attacks in 2018, which is why it is disabled by default. Finally, the ecosystem has moved toward Redis and Valkey for new projects, so fewer libraries add memcached-specific features such as the meta protocol.
practice: Use memcached for what it does best: a high-throughput cache of serialized objects, rendered fragments and query results, where the source of truth is elsewhere and losing an item only costs a recomputation. Use cache-aside with a TTL on every item, add random jitter to TTLs so keys do not expire together, and invalidate by deleting after database writes. For data that changes often, invalidate from the database's change stream (binlog or CDC) rather than from application code.
Size from the hit-rate target: estimate the working set, multiply by item size plus about 50 bytes, add 20% for slab overhead, and check that the database survives the loss of the largest server or a whole availability zone of cache. Use a client with consistent hashing (ketama-style), keep server lists identical on all clients, and prefer a proxy (mcrouter or the built-in proxy) once you have many pools or need replicated hot pools and failover.
Protect hot keys with leases or the meta protocol's stale-while-revalidate flags, and coalesce identical concurrent misses in the application. Monitor hit rate per key prefix, evictions, evicted-but-never-fetched items, slab class memory, connections and latency. Never expose memcached to the internet: bind to private interfaces, keep UDP off unless you need it, and use TLS and SASL where supported. Consider extstore when values are large (above about 512 bytes), the working set is much larger than RAM and the network has spare capacity.
quiz: Why do memcached servers not need to talk to each other? || The client hashes each key to choose one server, so every key has exactly one home and no server needs to know about the others. There is no replication or persistence to coordinate, because cached data can be recomputed from the database.
How does the slab allocator avoid fragmentation, and what does it cost? || It divides memory into 1 MB pages cut into fixed-size chunks per slab class, so items are placed in pre-sized chunks and freed chunks are reused exactly. The cost is unused space inside each chunk and memory stuck in classes whose item sizes are no longer common.
How do Facebook's leases prevent stale sets and thundering herds? || On a miss, the server gives one client a token; a set without a valid token, or after the key was deleted, is rejected, so a slow reader cannot write old data. Other clients that miss during the token window wait and retry instead of querying the database.
A cache tier serves 400,000 reads per second at a 98% hit rate, spread over 16 servers. One server fails, using consistent hashing. Roughly how many database reads per second follow? || Normally misses are 2% × 400,000 = 8,000 per second. The failed server's 1/16 (about 6%) of keys now miss as well: about 25,000 more, so roughly 33,000 database reads per second until those keys are cached again.
You need a cache for session objects that must survive a cache server restart and support per-user lists. Memcached or Redis? || Redis (or Valkey), because it has persistence, replication and list or hash data structures. Memcached would lose sessions on restart and can only store opaque values, so you would rebuild those features in the application.
