@@ ipc
value: Every process on a modern operating system lives in its own private virtual address space. A pointer in process A means nothing in process B, and a bug or a crash in A cannot overwrite B's memory. This isolation is the reason one bad program does not take down the machine. But isolation has a cost: real systems are made of many cooperating processes (a shell pipeline, a web server and its workers, a database and its clients, a container runtime and its CLI), and they must exchange data and events. Inter-process communication (IPC) is the set of kernel-provided channels that let isolated processes talk anyway.
The kernel offers a few channels with different shapes. A **pipe** is a one-way byte stream with a small buffer in the kernel. A **Unix domain socket** is a two-way channel that can carry either a byte stream or discrete messages, and can even pass open file descriptors from one process to another. **Shared memory** maps the same physical pages into two address spaces, so one process writes and the other reads with no copy at all. A **signal** is not a data channel; it is a tiny asynchronous notification ("please stop", "a child died", "you wrote to a closed pipe") delivered to a process like a software interrupt.
For the layer above, these channels are the glue. The Unix idea of small programs joined by pipes became the pipes-and-filters architecture. Docker's command-line tool talks to the Docker daemon over a Unix socket. A Kubernetes pod shuts down gracefully because the kubelet sends SIGTERM and the application handles it. Databases such as PostgreSQL use shared memory for their buffer cache across worker processes. The layers below make all of this possible: processes (L3) define what needs separating, system calls (L3) are the only door through which a process may ask the kernel for a channel, virtual memory (L3) is what makes shared memory work, and interrupts (L3) are the model behind signals.
terms: Pipe — a kernel buffer with a read end and a write end; bytes written at one end come out of the other in the same order.
FIFO (named pipe) — a pipe that has a name in the file system, so unrelated processes can open it.
Unix domain socket — a socket whose address is a file path on the same machine; it avoids the network stack and supports passing file descriptors.
File descriptor — a small integer that a process uses to refer to an open kernel object such as a file, pipe or socket.
Shared memory — a region of physical memory mapped into the address spaces of two or more processes.
Signal — a short asynchronous notification sent to a process, identified by a number such as SIGTERM (15) or SIGKILL (9).
Signal handler — a function in the process that the kernel runs when a signal arrives, interrupting normal execution.
Backpressure — the effect that a full pipe makes the writer wait, so a fast producer is slowed down to the speed of its consumer.
history: The pipe is older than Unix itself as an idea. In 1964 Doug McIlroy wrote a memo at Bell Labs saying programs should be connected "like garden hose", screwing in another segment when you need to massage data in a new way. For years it stayed an idea. In 1972 and 1973 McIlroy pushed Ken Thompson to implement it, and Thompson added the `pipe()` system call and the shell `|` syntax in a single night in early 1973, for Unix Version 3. The effect was large: Unix programs were rewritten to read standard input and write standard output so they could be chained. This is where the "do one thing well" tool culture came from.
Signals appeared in the very first versions of Unix in the early 1970s, as a simple way to kill or interrupt a process. They were unreliable at first: a handler was reset after each signal, and signals could be lost. BSD (4.2BSD, 1983) fixed this with reliable signals and also introduced the socket API, including Unix domain sockets, which became the standard local message channel. In the same period AT&T's System V Unix added its own IPC set (message queues, semaphores, shared memory) in 1983, usually called "System V IPC". Its API used numeric keys and was awkward, so POSIX later defined a cleaner family (`shm_open`, `sem_open`, `mq_open`) in the 1990s.
POSIX.1 (1988 onward) standardised signal semantics, and POSIX real-time extensions (1993) added queued signals with data. Linux later added file-descriptor based tools that fit into event loops: `signalfd` (2007), `eventfd` (2007) and `memfd_create` (2014), plus `pipe2` and `splice` for moving data between pipes and files without copying through user space. On the desktop and in services, D-Bus (2002 onward) built a structured message bus on top of Unix sockets, and in the container era the Docker socket and container runtime sockets became the control plane for whole fleets.
how: The kernel owns all IPC objects, so every channel starts with a system call. A process cannot reach into another process, but it can ask the kernel to create an object and hand out file descriptors or mappings to it. This is the first contribution from the layer below: **system calls** are the single controlled gate through which isolated processes get any shared object. `pipe(fds)` returns two descriptors, `fds[0]` to read and `fds[1]` to write. `socketpair()` and `socket(AF_UNIX, ...)` create sockets. `shm_open()` plus `mmap()` creates a shared mapping. `kill(pid, sig)` sends a signal.
Pipes. A pipe is a ring buffer inside the kernel. On Linux it holds 16 pages, so 64 KiB by default (it can be changed with `fcntl(F_SETPIPE_SZ)`). `write()` copies bytes from the caller's memory into the buffer. `read()` copies bytes out. If the buffer is full, `write()` blocks until a reader makes room; if the buffer is empty, `read()` blocks until a writer adds data. This blocking is the backpressure that keeps `producer | consumer` from using unbounded memory. If all readers close their end, a write fails with the error EPIPE and the kernel also sends SIGPIPE, which by default kills the writer; this is why `yes | head -1` ends cleanly. If all writers close their end, `read()` returns 0, which means end of file. POSIX guarantees that a write of at most `PIPE_BUF` bytes (4096 on Linux) is atomic, so several writers can share one pipe without their small messages interleaving. Larger writes may be split and mixed.
A pipe is a byte stream: it has no message boundaries. Two writes of 10 bytes can be read as one read of 20 bytes. If you need messages, you must add framing yourself (a length prefix, or a delimiter such as a newline), or use a socket type that keeps boundaries. A unidirectional pipe is created by a parent before `fork()`, so only related processes can share it. A FIFO, made by `mkfifo`, gives the pipe a path name so unrelated processes can open it.
Unix domain sockets. These behave like network sockets but skip IP, TCP and the network card. Data is copied between socket buffers inside the kernel, with no checksums, no routing and no congestion control. `SOCK_STREAM` gives a reliable byte stream, `SOCK_DGRAM` and `SOCK_SEQPACKET` keep message boundaries. They have two features pipes lack. First, they are bidirectional. Second, they can carry **ancillary data**: with `sendmsg()` and the `SCM_RIGHTS` option, a process can send an open file descriptor to another process, and the receiver gets its own descriptor pointing to the same kernel object. This is how a privileged process opens a file or port and passes it to an unprivileged worker. The receiver can also ask who the peer is (`SO_PEERCRED` returns the peer's process id, user id and group id), so a daemon can authorise a client by identity. The Docker daemon listens on `/var/run/docker.sock` for this reason, and permission to open that file is permission to control Docker.
Shared memory. Here the contribution comes from **virtual memory**. Each process has its own page table that maps virtual pages to physical frames. When two processes call `mmap()` on the same shared object (a file under `/dev/shm`, or an anonymous `memfd`), the kernel puts the same physical frames into both page tables, possibly at different virtual addresses. A store by one process is then visible to the other as soon as the CPU cache coherence protocol propagates it, and no system call is needed for the data transfer itself. This is the fastest IPC: no copy, no kernel involvement per message. The price is that the kernel no longer helps with coordination. The two processes must agree on a layout and synchronise with atomic operations, a futex-based mutex or semaphore (`pthread_mutex_t` with the process-shared attribute), or a lock-free ring buffer. Pointers inside the region must be offsets, not raw addresses, because the region may be mapped at different addresses in different processes.
Signals. When `kill(pid, SIGTERM)` runs, the kernel marks the signal as pending for the target process. The delivery model comes from **interrupts**: just like a hardware interrupt stops the CPU and runs a handler, a signal is delivered when the target is next about to return to user mode (from a system call, or from a timer interrupt that preempted it). If the process has a handler, the kernel builds a small frame on the user stack and runs the handler, then returns to the interrupted code through a special system call (`sigreturn`). If it has none, the default action runs: terminate, ignore, stop or dump core. Two signals cannot be caught or ignored: SIGKILL (9) and SIGSTOP. Because a handler can run between any two instructions of the main program, it may only call **async-signal-safe** functions (`write`, `_exit` and a short list of others, not `malloc` or `printf`). The classic safe pattern is that the handler only sets a flag or writes one byte into a pipe (the "self-pipe trick"), and the main loop does the real work. Standard signals do not queue: five SIGCHLD signals that arrive while one is pending may be seen as one, so a handler must loop with `waitpid(WNOHANG)`.
Graceful shutdown ties these pieces together. When Kubernetes deletes a pod, the kubelet sends SIGTERM to the main process of each container and waits for `terminationGracePeriodSeconds` (30 seconds by default). If the process is still alive, it sends SIGKILL, which cannot be caught. A service that handles SIGTERM can stop accepting connections, finish in-flight requests and flush buffers. A frequent trap is that in a container the main process is PID 1, and the kernel gives PID 1 no default signal actions: a SIGTERM without an installed handler is ignored. This is why many images use a tiny init such as `tini`.

example: Take the shell command `ls | wc -l`. The shell does the following. It calls `pipe(fds)` and gets, say, `fds[0] = 3` (read end) and `fds[1] = 4` (write end). It calls `fork()` twice. In the first child (which will become `ls`) it calls `dup2(4, 1)`, which makes file descriptor 1 (standard output) refer to the pipe's write end, then closes 3 and 4 and calls `exec("ls")`. In the second child (`wc`) it calls `dup2(3, 0)` so standard input is the pipe's read end, closes 3 and 4, and runs `exec("wc", "-l")`. The parent closes both ends. This last step matters. If the write end stays open anywhere (even in the parent), `wc` never sees end of file, because the kernel only reports EOF when no writer remains, and the pipeline hangs.
Now `ls` prints 200 file names of about 20 bytes each, 4,000 bytes in total. That fits inside the 64 KiB buffer, so `ls` may finish before `wc` has read anything. If `ls` produced 10 MB instead, it would fill the buffer after 64 KiB and block; each time `wc` reads, space frees up and `ls` continues. Neither program knows about the other: they only use `read` and `write` on descriptors 0 and 1.
Next a cost comparison. Process A must give process B a 1 GB array. Through a pipe the bytes are copied twice (A to kernel, kernel to B). At roughly 5 to 10 GB/s per core that is about 2 GB of copying, 0.2 to 0.4 seconds, plus about 16,000 system calls each way (one per 64 KiB chunk). With shared memory, A writes the data once into the mapped region and B reads it in place, so both copies and all those calls disappear. For 100-byte messages the picture flips: a pipe costs one system call per side, a few microseconds round trip, while a shared ring buffer needs careful design and a way to wake a sleeping reader.
intuition: Processes are people in separate sealed rooms; the kernel is the building manager who provides a pipe in the wall, a mail slot, a shared whiteboard seen through two windows, or a buzzer.
Isolation and communication look like opposites, but they are one design. Because processes cannot touch each other directly, every channel must be created by someone both sides trust, which is the kernel. The kernel can then choose the right trade-off for each need. A pipe copies data but gives ordering and backpressure for free. A socket adds two-way messages and identity. Shared memory removes the copy but makes the programmer responsible for safety, which is the same trade-off as between a message-passing design and a shared-state design everywhere else in computing. Signals are a different kind of thing: no data, only attention. They are cheap because they reuse the machinery the CPU already has for interrupts.
mistakes: People often think shared memory is always the fastest way to communicate. In fact it is the fastest way to move large amounts of data, but not always to deliver a message. A reader that has to be woken up still needs a system call (a futex or an eventfd), and spinning wastes a core. For small, infrequent messages a socket or pipe is simpler and fast enough.
People often think `SIGKILL` and `SIGTERM` are the same with different names. In fact SIGTERM asks the process to stop and can be caught, so the process can clean up. SIGKILL is carried out by the kernel and the process never runs any code in response: no flush, no lock release, no child cleanup. Locks held in shared memory by a killed process stay locked unless you use robust mutexes.
People often think a pipe keeps message boundaries. In fact it is a byte stream: one `read()` may return half a message or two messages. Add framing (a length prefix) and treat short reads as normal.
tradeoffs: Choose a pipe when you have two related processes and a one-way stream, such as a shell pipeline or a parent reading a child's output. You get ordering, backpressure and automatic end-of-file for free. You give up message boundaries, two-way flow and unrelated peers. Choose a Unix domain socket when you need a long-lived local service with many clients, two-way messages, client identity or descriptor passing; this is why Docker, containerd, systemd and X11 use them. You pay a little more per message than a pipe and have to manage connections.
Choose shared memory when throughput matters and the payload is large or the same data is read by many processes: a database buffer cache, a video frame passed from a decoder to a renderer, a feature table shared by worker processes. The deciding numbers are copy cost (about 0.1 s per GB) and message rate (above roughly 100,000 messages per second a system call per message becomes the bottleneck). You give up the kernel's help: you must design the layout, the locking and crash recovery yourself, and a bug can corrupt the data of every process that maps the region. Choose message passing (pipes or sockets) when processes may crash independently and you want the failure to stay inside one process.
friction: The first problem is the sharp edges of signals. Handlers run at arbitrary points, so shared data structures can be half-updated; the list of async-signal-safe functions is short; signals interrupt system calls (`EINTR`) so every blocking call needs a retry loop; and signal dispositions are inherited across `fork` and `exec` in ways that surprise people. Multithreaded programs add the question of which thread receives a process-directed signal. Many modern programs avoid handlers and use `signalfd` or a dedicated signal-handling thread.
Shared memory moves all correctness work to the programmer. On ARM and POWER a writer that stores data and then sets a ready flag needs a release barrier, or the reader may see the flag first. A process that dies holding a lock leaves it locked unless the mutex is robust (`EOWNERDEAD`). Every process that maps the region can read and write all of it.
practice: Use pipes for simple parent-child streaming and always close the ends you do not use in each process. Set pipes and sockets to non-blocking mode and use `poll`, `epoll` or your language's event loop when you handle more than one channel, and treat short reads and writes as normal. Add framing to byte streams: a 4-byte length prefix followed by the payload is the simplest choice.
For services, use a Unix domain socket and set the file permissions or use `SO_PEERCRED` to decide who may connect; prefer it over TCP on localhost, since access can be controlled with ordinary file permissions. For shared memory, create it with `memfd_create` or `shm_open`, size it with `ftruncate`, use offsets instead of pointers, put an explicit version and size in a header, use atomics with acquire/release ordering for the ready flags, and use robust, process-shared mutexes if you lock. Tools such as `lsof`, `ss -x` (Unix sockets), `ipcs` (System V objects), `ls /dev/shm` and `strace -f` show what channels exist and where a program is blocked.
Handle SIGTERM in every long-running service with a tiny handler. In containers use the exec form of `CMD`, add `tini` or `--init`, and set `terminationGracePeriodSeconds` longer than your longest in-flight request. Use signals for control only, and prefer `signalfd` in event loops.
interview: A service in Kubernetes drops requests during every deploy. How do you debug it from the IPC and signal side? || Check that the app receives SIGTERM: with shell-form `CMD` the shell is PID 1 and may not forward it, and PID 1 ignores signals without a handler. Then check the handler stops the listener, drains in-flight requests and exits before `terminationGracePeriodSeconds`. Also consider the race between endpoint removal and SIGTERM: add a short preStop sleep so load balancers stop sending traffic before the app closes its listener.
Why does `producer | head -1` terminate the producer and what happens if SIGPIPE is ignored? || When `head` exits, the read end closes; the next `write()` by the producer finds no readers and the kernel sends SIGPIPE, whose default action kills the producer. If SIGPIPE is ignored (as in many runtimes), `write` returns EPIPE and the program must handle that error itself, otherwise it keeps working for nothing or logs errors.
Why can a process not catch SIGKILL, and what does that imply for correctness? || The kernel needs a way to remove a process that is stuck or hostile, so SIGKILL is carried out in the kernel with no user code involved. Therefore no cleanup code runs. Correctness must not depend on a clean shutdown: use write-ahead logs or atomic renames, lease-based locks that expire, and robust mutexes.
When would you pass a file descriptor over a Unix socket? || When a privileged process should do the sensitive step (open a restricted file, bind port 80) and hand the result to a sandboxed worker. It also enables zero-downtime restarts: the old process passes its listening socket to the new one.
quiz: What are the two guarantees that make a pipe safe for a fast producer and a slow consumer? || The buffer is bounded (64 KiB by default on Linux), and `write()` blocks when it is full. This backpressure stops the producer from using unbounded memory, and bytes always arrive in order.
Why does shared memory need no system call per message, and what must the programmer do instead? || The kernel maps the same physical frames into both page tables, so a normal store by one process is visible to the other. The programmer must provide synchronisation (atomics, futex-based locks) and a layout that uses offsets instead of pointers.
Why is a SIGTERM sent to a container's main process sometimes ignored? || The main process is PID 1, and the kernel gives PID 1 no default signal actions, so an unhandled SIGTERM does nothing. The app must install a handler, or the container must run an init such as `tini`; with a shell-form entrypoint the signal may also go to `sh` instead of the app.
A pipe write of 3,000 bytes and another of 3,000 bytes come from two processes on the same pipe. Can they interleave? What if each is 10,000 bytes? || The 3,000-byte writes are below `PIPE_BUF` (4096 on Linux), so each is atomic and they cannot interleave. The 10,000-byte writes may be split, so their pieces can mix.
You must send 50-byte control messages 10 times a second between two local daemons that may crash independently. Pipe, socket or shared memory? || A Unix domain socket (or `SOCK_SEQPACKET`), because the rate is tiny, message boundaries and two-way flow are useful, and a crash of one side shows up as a closed connection. Shared memory would add locking and recovery complexity for no gain.

@@ rtsched
value: A real-time system is one where the answer must arrive before a deadline, and a correct answer that arrives late is a wrong answer. An airbag controller, a flight-control loop, a pacemaker, an audio driver and an engine-control unit all work this way. "Real-time" does not mean fast. It means **predictable**: the worst case is bounded and known in advance. A system that averages 1 ms but sometimes takes 80 ms is not real-time; a system that always takes between 4 and 5 ms may be.
Ordinary CPU scheduling optimises throughput and fairness. It asks "how do I share the CPU so that everyone makes progress and the machine stays busy?" Real-time scheduling asks a harder question: "given tasks that each need C milliseconds of CPU every T milliseconds, in what order must I run them, and can I prove, before the system ships, that no deadline is ever missed?" The answer is a small set of ideas: assign fixed priorities by rate (rate-monotonic scheduling), or always run the task with the nearest deadline (earliest deadline first, EDF), test schedulability with a utilisation bound or a response-time calculation, and prevent a low-priority task that holds a lock from blocking a high-priority task for an unbounded time (priority inheritance).
The layer above uses this directly: embedded control loops in cars and aircraft, and the PREEMPT_RT patch set, which became part of mainline Linux in version 6.12 (November 2024) so that Linux can serve robotics, industrial control and audio. The layers below supply the parts. CPU scheduling (L3) gives the dispatcher, the ready queue and preemption. Locks and atomics (L3) are the source of the priority inversion problem. Queueing theory (L4) gives the idea of utilisation as the fraction of time a server is busy, and the warning that waiting time explodes as utilisation approaches 1. Proofs and induction (L4) turn "it seems to work in tests" into "it provably meets every deadline".
terms: Task (job) — a piece of work released at some time that needs a known amount of CPU time and must finish before its deadline.
Period (T) — the time between two releases of a periodic task; the deadline is usually the end of the period.
Worst-case execution time (C) — the longest CPU time one job can need; real-time analysis uses this, not the average.
Utilisation (U) — the sum of C/T over all tasks; the fraction of CPU time the task set demands.
Hard and soft real-time — hard means a missed deadline is a failure (an airbag); soft means a late result only lowers quality (a video frame).
Preemption — the scheduler stops a running task to run a more urgent one.
Priority inversion — a high-priority task is made to wait for a lower-priority one, for example because the low-priority task holds a lock.
Priority inheritance — while a low-priority task holds a lock that a high-priority task wants, it temporarily runs at the high priority.
Schedulable — a task set is schedulable under an algorithm if every job always meets its deadline.
history: The foundation is the 1973 paper "Scheduling Algorithms for Multiprogramming in a Hard-Real-Time Environment" by C. L. Liu and James Layland, written with the NASA Apollo-era problem of scheduling flight software in mind. They studied periodic tasks on one processor and proved two results. Giving the highest priority to the task with the shortest period (rate-monotonic scheduling, RM) is the best possible fixed-priority rule. And running the job with the earliest absolute deadline (EDF) can use 100% of the CPU. Michael Dertouzos proved the optimality of EDF in 1974 for the more general case.
The next problem was locks. In the 1980s and 1990s, real systems found that the clean theory broke when tasks shared data. Lui Sha, Ragunathan Rajkumar and John Lehoczky published "Priority Inheritance Protocols: An Approach to Real-Time Synchronization" in 1990, with the basic priority inheritance protocol and the priority ceiling protocol, which also prevents deadlock and bounds blocking to one critical section. The problem became famous in July 1997 when the Mars Pathfinder lander kept resetting its computer on Mars. A low-priority meteorological task held a shared bus lock, a medium-priority task preempted it, and the high-priority bus management task waited so long that a watchdog timer reset the system. Engineers at JPL found the cause by reproducing it on the ground and fixed it by enabling the priority inheritance option in the VxWorks mutex, uploading the change to the spacecraft.
Later work widened the model: response-time analysis (Joseph and Pandya 1986, Audsley and others 1993) made fixed-priority tests exact; multiprocessor scheduling and mixed-criticality systems came in the 2000s; and Linux gained real-time classes. `SCHED_FIFO` and `SCHED_RR` have been in Linux since the early days, `SCHED_DEADLINE` (EDF with a constant-bandwidth server) was merged in Linux 3.14 in 2014, and the long-running PREEMPT_RT patches, started by Ingo Molnar and Thomas Gleixner around 2004 to 2005, were fully merged in Linux 6.12.
how: Start with the task model. Each periodic task i has a worst-case execution time C_i and a period T_i, and its deadline is the end of its period. The utilisation of one task is C_i/T_i and the total is \( U = \sum_i C_i / T_i \). Utilisation above 1 is impossible on one CPU. The question is how close to 1 you can get with a given scheduling rule.
Rate-monotonic scheduling. Give each task a fixed priority, and give higher priority to tasks with shorter periods. A preemptive scheduler always runs the highest-priority ready task. This is just ordinary priority scheduling from the CPU-scheduling concept, with a rule for choosing the numbers. Liu and Layland proved that RM is optimal among fixed-priority rules: if any fixed-priority assignment can meet all deadlines, RM can. They also gave a sufficient test. A set of n tasks is schedulable under RM if
\[ U \le n\left(2^{1/n} - 1\right) \]
For one task the bound is 1.0, for two it is 0.828, for three 0.780, and as n grows it falls to \( \ln 2 \approx 0.693 \). The proof, which is where **proofs and induction** enter, uses the "critical instant": the worst case for a task is when it is released at the same moment as all higher-priority tasks, so it is enough to check that one moment. The bound is sufficient, not necessary: many task sets above it are still schedulable, and the exact test is response-time analysis. For task i, start with \( R = C_i \) and iterate
\[ R_i^{(k+1)} = C_i + \sum_{j \in hp(i)} \left\lceil \frac{R_i^{(k)}}{T_j} \right\rceil C_j \]
until the value stops changing; the task is schedulable if the fixed point is at most its deadline. The sum counts how many times each higher-priority task can interrupt during the window. This is an application of the **queueing** idea of load: delay for a low-priority task is its own work plus the work of all those who may cut in front.
Earliest deadline first. At every scheduling point, run the ready job whose absolute deadline is nearest. Priorities are now dynamic: they change from job to job. For independent periodic tasks with deadline equal to period on one CPU, EDF is schedulable if and only if \( U \le 1 \), and EDF is optimal among all algorithms. So EDF can use the whole CPU where RM can guarantee only about 69 to 83% for small sets in the worst case. The cost is behaviour under overload: when U exceeds 1 under RM, the lowest-priority tasks miss deadlines and the important ones keep running; under EDF, one overrun can make many tasks miss their deadlines in a chain (a "domino effect"). EDF is also harder to implement in a priority-indexed kernel, and it needs a budget mechanism so that a task that exceeds its declared C cannot steal time from the others. Linux's `SCHED_DEADLINE` handles this with a constant-bandwidth server: each task declares (runtime, deadline, period), the kernel does admission control (it refuses a new task if the total bandwidth would exceed capacity), and a task that uses up its runtime is throttled until the next period.
Priority inversion and inheritance. The analysis above assumed independent tasks. Real tasks share data protected by locks (from **locks and atomics**). Suppose low-priority L holds a mutex. High-priority H becomes ready, preempts L, tries to take the mutex and blocks. Now medium-priority M becomes ready. M does not need the mutex, and it has higher priority than L, so it preempts L. L cannot run to release the lock, so H waits for as long as M runs, and M's running time is unrelated to H's critical section. H is blocked for an unbounded time, even though H has higher priority than M. That is **unbounded priority inversion**. Priority inheritance repairs it: when H blocks on a lock held by L, L is temporarily raised to H's priority. M can no longer preempt L, L finishes the critical section, releases the lock, drops back to its own priority, and H runs. The blocking H suffers is now bounded by the length of one critical section. Inheritance must be transitive: if L is itself blocked on a lock held by Q, then Q inherits too. The priority ceiling protocol goes further: each lock has a ceiling equal to the highest priority of any task that ever uses it, and a task can only take a lock if its priority is above the ceilings of all locks currently held by others. This makes deadlock impossible and limits blocking to a single critical section.
Putting it together gives the response-time formula with blocking: \( R_i = C_i + B_i + \) interference, where \( B_i \) is the longest critical section by a lower-priority task on a lock that i or a higher-priority task uses. In Linux, mutexes with priority inheritance are `rt_mutex` and the `PTHREAD_PRIO_INHERIT` mutex attribute (implemented with the PI futex). The PREEMPT_RT configuration also makes the kernel itself preemptible: most spinlocks become sleeping `rt_mutex` locks with priority inheritance, interrupt handlers run as schedulable kernel threads, and long non-preemptible regions are removed, so that the worst-case latency for a high-priority thread drops from many milliseconds to tens or hundreds of microseconds on suitable hardware.

example: Take two periodic tasks: T1 with C = 2 and period 5, and T2 with C = 4 and period 7. Utilisation is 2/5 + 4/7 = 0.400 + 0.571 = 0.971. The RM bound for n = 2 is 0.828, so the test fails. Check by simulation. Under RM, T1 has the higher priority (shorter period). At time 0 both are released. T1 runs 0 to 2. T2 runs 2 to 5 and has done 3 of its 4 units. At time 5, T1 is released again and preempts: T1 runs 5 to 7. At time 7, T2's deadline arrives with 1 unit still missing. T2 misses its deadline. Under EDF the same set works. At time 0 the deadlines are 5 (T1) and 7 (T2), so T1 runs 0 to 2, then T2 runs 2 to 5 (3 units). At time 5, T1's new job has deadline 10 and T2's job has deadline 7, so T2 continues 5 to 6 and finishes with 1 unit of slack. Then T1 runs 6 to 8, meeting its deadline of 10. Because U = 0.971 is at most 1, EDF is guaranteed to succeed.
Now a response-time example where the bound is exceeded but RM still works. Three tasks: A with C = 1, T = 4; B with C = 2, T = 6; C with C = 3, T = 12. Utilisation is 0.250 + 0.333 + 0.250 = 0.833, above the n = 3 bound of 0.780. Priorities by period: A, then B, then C. For A: R = 1. For B: start 2, then 2 + ⌈2/4⌉ × 1 = 3, then 2 + ⌈3/4⌉ × 1 = 3, so R = 3 ≤ 6. For C: start 3. Then 3 + ⌈3/4⌉×1 + ⌈3/6⌉×2 = 3 + 1 + 2 = 6. Then 3 + ⌈6/4⌉×1 + ⌈6/6⌉×2 = 3 + 2 + 2 = 7. Then 3 + ⌈7/4⌉ + ⌈7/6⌉×2 = 3 + 2 + 4 = 9. Then 3 + ⌈9/4⌉ + ⌈9/6⌉×2 = 3 + 3 + 4 = 10. Then 3 + ⌈10/4⌉ + ⌈10/6⌉×2 = 3 + 3 + 4 = 10. It has converged: R = 10 ≤ 12. All deadlines are met, even though the utilisation test said "not guaranteed".
intuition: A hospital emergency room ranks patients by urgency, not arrival time, and a doctor holding the only key to the supply cabinet must hurry when the critical patient is waiting for it.
Deadlines are promises, and a promise can only be checked if you know the worst case. Rate-monotonic scheduling is natural because a task that must run often has less room to wait, so it gets the priority. EDF is natural because the job that will expire soonest should go first, which is the same logic as a queue at a counter ordered by closing time. Priority inheritance is natural because the only reason the low-priority task is in the way is that the high-priority task needs it; lending the priority makes the delay as short as the work really requires. The schedulability tests are proofs by worst case: if the hardest alignment of jobs still works, every other alignment works too.
mistakes: People often think real-time means fast. In fact it means bounded and predictable. A system with a 10 ms worst case that never exceeds it is real-time; a system with a 0.1 ms average and an occasional 50 ms garbage-collection pause is not, for a 5 ms deadline.
People often think priority inversion needs a bug in the code. In fact it follows from correct use of locks together with fixed priorities; the Mars Pathfinder code was correct in the logic sense. Inversion is a property of the scheduling policy, so it must be handled by the policy: inheritance or ceilings.
People often think a utilisation under 100% is always safe. In fact the guarantee depends on the algorithm: under RM the simple bound is only about 69% for large task sets (exact analysis often allows 85 to 90%, and harmonic periods allow 100%), and real overheads such as context switches and interrupts eat into EDF's 100% too.
tradeoffs: Choose fixed priorities (RM or deadline-monotonic) when the system must behave predictably under overload, when the OS offers only priority-based scheduling (FreeRTOS, VxWorks, Zephyr and Linux `SCHED_FIFO` all do), or when certification tools expect it. You accept a lower guaranteed utilisation, around 69% by the simple bound and up to 100% only when periods are harmonic. Choose EDF (`SCHED_DEADLINE` on Linux) when you need to use the CPU close to full capacity, when tasks have deadlines shorter or different from their periods, or when you want admission control and budget enforcement per task. You accept domino effects under overload, weaker tooling and more work to prove worst cases.
Choose priority inheritance when tasks share locks and you want the simplest fix: it is built into `rt_mutex`, PI futexes and VxWorks mutexes, and it works without knowing in advance which tasks use which lock. Choose priority ceiling when you can list all users of every lock at design time and you need deadlock freedom and a blocking bound of exactly one critical section; you give up flexibility, because adding a task may change the ceilings. The best choice is often to avoid shared locks in the high-priority path at all, using lock-free queues or message passing between tasks.
friction: The hardest step is not the scheduling algorithm but finding the worst-case execution time C. Modern CPUs have caches, branch predictors, pipelines and shared memory buses, so the time of a code path depends on history and on what the other cores are doing. Measured maximums are not safe bounds; static analysis tools give safe but pessimistic ones. On multicore chips, interference through shared caches and memory bandwidth can make a task several times slower than when it runs alone, which is why safety-critical systems often disable cores or partition resources.
Sources of unbounded delay also hide in software. A page fault, a memory allocation (`malloc` can call into the kernel), garbage collection, a logging call that blocks on a disk, or a shared lock in a library can each break a deadline. Real-time code locks its memory (`mlockall`), preallocates everything and avoids blocking calls in the critical loop. Finally, the theory assumes accurate periods and declared budgets; real jobs overrun, arrive with jitter and form chains across several tasks and machines, which makes end-to-end deadlines harder than the single-task analysis suggests.
practice: Start from the requirement: the deadline, its consequence if missed (hard or soft), and the measured worst-case latency you must beat. Keep the real-time part small. Put the control loop in a thread with a fixed priority, and keep everything else (logging, networking, UI) at lower priority or in other processes.
On Linux, use `SCHED_FIFO` or `SCHED_DEADLINE` through `sched_setscheduler` or `chrt`, lock memory with `mlockall(MCL_CURRENT | MCL_FUTURE)`, pre-fault the stack and heap, use `PTHREAD_PRIO_INHERIT` on mutexes shared with lower-priority threads, pin the thread with `sched_setaffinity` and isolate its core (`isolcpus`, `nohz_full`). Run the PREEMPT_RT kernel for single-digit to tens of microseconds typical jitter, and measure with `cyclictest` under heavy load for hours: the worst case, not the average, is what counts. Use the kernel's RT throttling limits (`sched_rt_runtime_us`) carefully; a runaway `SCHED_FIFO` thread can lock up a machine.
In an RTOS such as FreeRTOS or Zephyr, assign priorities by period, keep interrupt handlers short and defer work to tasks, and use mutexes with priority inheritance (FreeRTOS mutexes have it; binary semaphores do not). Add a watchdog, and log deadline misses so that you learn about overload before the field does. In ad-tech and data systems you rarely meet hard deadlines, but the same ideas appear as latency SLOs, bounded queues, admission control and designing for the tail, not the mean.

Why is it not used everywhere? || Under overload it fails unpredictably (many jobs miss deadlines), the kernel needs a more complex data structure and budget enforcement, safety tooling is built for fixed priorities, and real overheads reduce the usable capacity. Fixed priorities degrade gracefully: the most important tasks keep meeting deadlines.

@@ checksums
value: Hardware and networks are not perfect. A bit flips in a memory chip, a cable picks up noise, a disk sector decays, a buggy driver writes the wrong buffer. If nothing checks, the damaged bytes flow on as if they were good, and the error appears days later as a crashed parser or a wrong number in a report. A checksum is the cheapest defence: compute a short value from the data, store or send it next to the data, and recompute it when the data is read. If the two values differ, the data was damaged and must not be trusted.
The family has three levels. Simple sums, such as the TCP/IP ones'-complement sum, cost almost nothing but miss some common errors. Cyclic redundancy checks (CRCs) treat the data as a polynomial and keep the remainder of a division; they give mathematical guarantees against bursts of bit errors and are cheap in hardware, which is why every Ethernet frame ends with a CRC-32. Cryptographic hashes such as SHA-256 detect even deliberate tampering, but cost more. A checksum answers "was this damaged by accident?"; it does not answer "did an attacker change it?".
For the layer above, checksums are the way storage and network systems stay honest. Ethernet drops frames with a bad CRC. Kafka brokers and clients verify a CRC32C on each record batch. ext4 and Btrfs checksum metadata, ZFS checksums every block, and Parquet pages can carry a CRC. Backups are only useful if they are verified. The layers below give the machinery: binary (L3) gives the bit patterns and carry rules, finite fields (L4) explain why a CRC is division of polynomials over GF(2), and coding theory (L4) tells you exactly which errors a given code is guaranteed to catch.
terms: Checksum — a short value computed from data and stored or sent with it, used to detect accidental corruption.
CRC (cyclic redundancy check) — a checksum equal to the remainder of dividing the data, seen as a polynomial over GF(2), by a fixed generator polynomial.
Generator polynomial — the fixed divisor of a CRC; its choice decides which errors are caught (for example CRC-32 or CRC-32C).
GF(2) — the field with two elements, 0 and 1, where addition is XOR and there are no carries.
Burst error — a run of consecutive damaged bits, typical of noise on a link or a damaged disk region.
Hamming distance — the number of bit positions in which two code words differ; a code with distance d detects any d − 1 bit errors.
Ones'-complement sum — adding 16-bit words and wrapping any carry-out back into the low bits; used by the IP, TCP and UDP checksums.
Collision — two different inputs with the same checksum; for a w-bit checksum, random damage collides with probability about 2^−w.
history: The idea of a parity bit goes back to the early telegraph and punched-card era. Richard Hamming built the first practical error-detecting and correcting codes at Bell Labs in 1947 to 1950, after he grew tired of weekend batch jobs that failed on a single card-reader error. In 1961, W. Wesley Peterson and D. T. Brown published "Cyclic Codes for Error Detection", which showed how a shift register could compute the remainder of a polynomial division cheaply in hardware. This is the origin of the CRC.
Networking took up both families. The Internet checksum is a simple 16-bit ones'-complement sum, defined in the IP and TCP specifications of 1981 and explained in RFC 1071 (1988); it was chosen because it was fast on the small machines of the day and byte-order independent. Ethernet, standardised in 1983 to 1985, uses a 32-bit CRC with polynomial 0x04C11DB7 as its frame check sequence; the same polynomial appears in zlib, gzip, PNG and ZIP. Peter Fletcher published a cheaper two-sum checksum in 1982 and Mark Adler's Adler-32 followed in the 1990s.
Better polynomials and faster software came later. Guy Castagnoli and colleagues published a family of better 32-bit polynomials in 1993; the one with polynomial 0x1EDC6F41 (CRC-32C) was adopted by iSCSI and SCTP, and Intel added a hardware `CRC32` instruction for it in SSE4.2 with the Nehalem processors in 2008. Koopman and Chakravarty analysed polynomial choice in 2004, and Intel researchers showed around 2005 how to compute a CRC several bytes at a time ("slicing-by-8"). Today CRC32C is the default in systems that care about throughput: Kafka (record format v2, 2017), ext4 metadata checksums, Btrfs and many databases. (Parquet page checksums use the older CRC-32 polynomial, the same as gzip.) Fast non-cryptographic hashes such as xxHash (2012) are used where only accident detection is needed and the goal is raw speed. A 2000 SIGCOMM paper by Jonathan Stone and Craig Partridge, "When the CRC and TCP Checksum Disagree", showed from real traces that roughly 1 in 30,000 packets failed the TCP checksum even though link-level CRCs had passed, which supported the end-to-end view that data must also be checked at the endpoints.
how: Begin with the simplest checksum. A parity bit is the XOR of all data bits. It detects any odd number of flipped bits and misses every even number. A byte-sum checksum adds all bytes modulo 256; it detects many single-byte errors but is blind to reordered bytes, because addition does not care about order. The Internet checksum adds the data as 16-bit words and folds any carry out of bit 16 back into the low end, then stores the complement of the result. The receiver adds everything including the checksum and expects all ones. It is fast and incremental (you can update it when one field changes, as routers do when decrementing the TTL), but it cannot see swapped 16-bit words or two errors that cancel (one bit up in a column, one bit down in the same column of another word).
A CRC does better by using **finite-field** arithmetic. Treat the message bits as the coefficients of a polynomial over GF(2). For example the bits 1101 are \( x^3 + x^2 + 1 \). In GF(2), addition and subtraction are both XOR, so there are no carries. Choose a fixed generator polynomial \( G(x) \) of degree r. To compute the r-bit CRC of message \( M(x) \), shift the message left by r bits (multiply by \( x^r \)) and take the remainder of division by G:
\[ \text{CRC}(M) = \left( M(x) \cdot x^{r} \right) \bmod G(x) \]
The sender transmits the message followed by the CRC, which is the same as sending a polynomial that is exactly divisible by G. The receiver divides what it received by G; a nonzero remainder means damage. In hardware, the division is a shift register with XOR gates at the positions of the polynomial's terms, processing one bit per clock. In software, you precompute a 256-entry table so that one byte is processed per step (`crc = table[(crc ^ byte) & 0xFF] ^ (crc >> 8)`), and fast libraries use slicing-by-8 or the carry-less multiply instructions (PCLMULQDQ) to reach many gigabytes per second per core. CRC32C on x86 with the `CRC32` instruction reaches roughly 10 GB/s or more per core when three streams are interleaved.
The guarantees come from **coding theory**, and they are exact, not statistical. Let the error be the polynomial E(x) (bits flipped at the positions of its terms). The receiver's remainder is \( E(x) \bmod G(x) \), so an error is missed exactly when G divides E. From this: every burst error of length up to r bits is detected (a nonzero polynomial of degree less than r cannot be divisible by G of degree r); every single-bit error is detected if G has at least two terms; every odd number of bit errors is detected if \( (x+1) \) divides G (CRC-32's polynomial does not have this property, but many 16-bit ones do); and any error pattern up to a certain weight is detected within a given message length, depending on the polynomial's Hamming distance at that length. A random error not covered by these guarantees is missed with probability about \( 2^{-r} \), which is 1 in 4.3 billion for a 32-bit CRC. The choice of polynomial matters: CRC-32C was found by computer search for good Hamming distance at the message sizes common in networks and storage (hundreds to thousands of bytes), and it does better there than the Ethernet polynomial.
Two properties set the limit of use. First, a CRC is **linear**: \( \text{CRC}(a \oplus b) = \text{CRC}(a) \oplus \text{CRC}(b) \oplus \text{CRC}(0) \). This helps (you can combine and update CRCs of pieces), but it means an attacker can modify data and fix the CRC without knowing any secret, so a CRC is useless against an adversary. Second, a w-bit checksum has only \( 2^w \) values, so over trillions of blocks a few collisions are expected; this is why backup and deduplication systems that must be sure use SHA-256, not CRC32.
Where the checksum is placed also matters. A checksum stored next to its data, in the same block, cannot detect a block written to the wrong place, or a lost write that left an old but self-consistent block. ZFS and Btrfs store each block's checksum in its parent pointer, so a read verifies not only "the bytes are intact" but "these are the bytes the parent expects", and the checks form a Merkle tree up to the root. Kafka puts the CRC32C in the batch header, covering everything after it (attributes, offsets, timestamps and records), so a consumer or broker can verify the batch end to end before using it.

example: Work a small CRC by hand. Use the generator \( G = x^3 + x + 1 \), written as bits 1011, so r = 3. The message is 1101011 (7 bits). Append three zeros to get 1101011000. Now divide using XOR, from left to right. Whenever the current leading bit is 1, XOR the divisor 1011 into the four bits starting there; when it is 0, move on. Step 1: at bit 0, 1101 XOR 1011 = 0110, so the string becomes 0110011000. Step 2: at bit 1, 1100 XOR 1011 = 0111, giving 0011111000. Step 3: at bit 2, 1111 XOR 1011 = 0100, giving 0001001000. Step 4: at bit 3, 1001 XOR 1011 = 0010, giving 0000010000. Step 5: bit 4 is 0, so skip it; at bit 5, 1000 XOR 1011 = 0011, giving 0000000110. The remainder is the last three bits: 110. The sender transmits the message followed by the CRC, 1101011110.
Check at the receiver. Dividing 1101011110 by 1011 gives remainder 000, so it is accepted. Flip one bit in the message part, giving 1101111110: the remainder is 111, nonzero, so the error is detected. Flip a bit inside the CRC part, giving 1101011010: the remainder is 100, also nonzero. Any burst of 3 or fewer consecutive flipped bits is guaranteed to be caught, because it is a polynomial of degree below 3 and cannot be divisible by G. Errors that are exact multiples of G, such as the pattern 1011 placed anywhere in the message, pass unnoticed; with a 3-bit CRC about 1 random error pattern in 8 does this.
Now the scale. Random damage that evades a 32-bit CRC has probability about \( 2^{-32} \approx 2.3 \times 10^{-10} \) per damaged batch. A Kafka cluster that handles 10 million batches a day and sees one damaged batch per 100 million has about 0.1 damaged batches a day, or 36 a year; the chance that any of them goes undetected is about \( 36 \times 2.3 \times 10^{-10} \), under one in a hundred million. For the 16-bit TCP checksum the escape chance is 1 in 65,536. If 1 packet in 30,000 arrives damaged (the Stone and Partridge figure), a server that receives a billion packets sees about 33,000 bad ones, and about 0.5 of them slip past TCP silently. Across a large fleet this happens regularly, which is why data stores add their own checksums above TCP.
intuition: A check digit on a credit card number, but strong enough that the way the data is usually damaged (a short burst, one flipped bit) always changes the digit.
The CRC is natural once you see division with remainder. If the sender makes the whole word exactly divisible by G, then any damage that is itself not divisible by G leaves a visible remainder. Choosing G with the right structure makes the common damage patterns, short bursts and few-bit errors, provably non-divisible. Using GF(2) arithmetic means no carries, so the computation is a shift register in a few gates. The checksum is a compromise: just enough redundancy (32 bits) to catch almost everything accidental, at almost no cost.
mistakes: People often think a CRC protects data from tampering. In fact it is linear and has no secret, so anyone can change the data and compute a matching CRC. For tampering use an HMAC or a signature; for accidental damage a CRC is enough.
People often think a good checksum makes a 1-in-4-billion collision impossible. In fact it is only unlikely per event. At the scale of petabytes and billions of blocks, collisions happen, and deduplication systems must either compare bytes or use a 256-bit cryptographic hash.
People often think that if TCP has a checksum and Ethernet has a CRC, application-level checksums are redundant. In fact each layer protects only one hop or one segment, and corruption also arises inside routers, NIC buffers, memory and disks, after the lower check passed. Checksums must be end to end, from where the data is created to where it is used.
People often think all CRC-32 are the same. In fact the polynomial matters: CRC-32 (Ethernet, zlib) and CRC-32C (Castagnoli, iSCSI, Kafka, ext4) give different values and different error guarantees. Mixing them is a common cause of "checksum mismatch" bugs when two systems meet.
tradeoffs: Choose a CRC when the threat is accidental damage and you need speed: a 32-bit CRC32C costs a small fraction of a CPU cycle per byte with hardware support and catches all short bursts and all few-bit errors in typical block sizes. Choose a cryptographic hash (SHA-256, BLAKE3) when an adversary may change the data, when you use the value as an identity for deduplication or content addressing, or when a false match would be catastrophic; you pay roughly 5 to 20 times the CPU per byte (BLAKE3 and SHA extensions narrow the gap), and 32 bytes of storage instead of 4.
Choose a non-cryptographic hash such as xxHash when you need a fast fingerprint for hash tables, change detection or sharding and do not need the burst-error guarantees of a CRC; xxHash is faster than software CRC but gives no mathematical guarantee for specific error shapes. Choose a simple sum (the Internet checksum, Fletcher) only when you need the lowest possible cost or incremental updates, as in packet headers, and accept that it is much weaker. Choose to put the checksum in the parent (ZFS style) when you must catch misdirected or lost writes; choose it in the block header when you want simple self-verifying blocks, and add a sequence number or block address inside the checksummed range to cover misdirection.
Checksum granularity is another decision. A checksum per 4 KiB block costs 0.1% overhead for 4 bytes and localises the damage; a single checksum for a 1 GB file is cheap but means any error invalidates the whole file and you cannot say where it is. Systems such as HDFS use a checksum per 512 bytes of data for this reason. Finally, choose whether to repair or only detect: detection needs 32 bits per block, repair needs replicas or erasure codes, and that is a different cost.
friction: A checksum detects; it does not correct. After a mismatch the system needs a second copy, a retransmission, or a parity-based repair, and many designs have no such path, so they can only fail loudly. Checksums also cover only what they are asked to cover. A CRC computed after a bug corrupted the data in memory will faithfully certify the corrupted data. Silent data corruption inside CPUs and memory (large fleets report faulty CPU cores that return wrong results without errors) cannot be caught by a checksum computed on the same faulty machine.
There are performance and compatibility costs too. Verifying on every read adds CPU, which is why some systems allow it to be turned off (and then only a periodic scrub finds the damage). Computing the CRC of data that is read through zero-copy paths, such as `sendfile`, means touching the bytes that the zero-copy path tried not to touch; Kafka avoids this by storing the CRC with the batch and letting consumers verify it. The polynomial, bit order, initial value and final XOR all vary between "CRC-32" implementations, so two correct libraries can disagree. Finally, a 32-bit check gives 1-in-4-billion odds, which is plenty for one packet but marginal for exabyte-scale stores, where a stronger hash is justified.
practice: Always verify checksums on data that crossed a boundary: network, disk, tape, another team's service. Keep the checksum with the data and compute it as early as possible (at the producer) and verify as late as possible (at the final consumer). Use CRC32C where a hardware instruction exists (all modern x86 and ARM), and use a library that uses it. Include the length, the block address or a sequence number in what you check so that misplaced data is also caught.
In storage systems, run periodic scrubs (ZFS `scrub`, Btrfs `scrub`, HDFS block scanner) so that damage is found while a good replica still exists. Enable checksum options where they are off by default, for example Parquet page checksums on write and verification on read, and turn on end-to-end verification in object storage uploads (S3 supports CRC32C, SHA-256 and others as additional checksums). In Kafka leave `check.crcs` on for consumers. When a mismatch appears, treat it as a hardware or software fault to investigate, not as noise: log the data location, retry from another replica, and look for a bad NIC, memory or disk. Never use a CRC for passwords, signatures, or any security decision.
interview: Why is a CRC better than a sum for detecting errors on a link? || A CRC is polynomial division over GF(2), so it catches every burst up to its length and every odd-weight error for suitable polynomials, and it is sensitive to order. A sum ignores order and misses errors that cancel in a column. A CRC also has the same small hardware cost as a shift register.
TCP already has a checksum and Ethernet a CRC. Why does Kafka add CRC32C to each record batch? || Those checks cover one hop or one segment and are verified and then dropped. Corruption can still happen in a router, NIC, memory or on disk after they passed, and the data is stored for days. A checksum made at the producer and verified at the final consumer covers the whole path, including the broker's disk.
A teammate proposes using CRC32 as the identity of files for deduplication. What is wrong? || Only 2^32 values, so with 100 million files a collision is almost certain (birthday bound near 77,000 items for 50%). It is also not collision resistant against an adversary. Use SHA-256 or BLAKE3, or compare bytes after a hash match.
How does ZFS detect a lost write or a misdirected write that an in-block checksum would miss? || It stores each block's checksum in its parent block pointer, so a read checks the data against what the parent says it should be. An old block that is self-consistent, or a block written to the wrong address, fails the check, and the checksums form a Merkle tree up to the root.
Your service sees a CRC mismatch once per billion reads. What do you do? || Treat it as real: identify the replica and path, re-read from another copy and repair, then correlate with a host, disk or NIC to find failing hardware. Add scrubbing so damage is found early, and verify that the CRC variant and byte order match across all components.
quiz: What does a receiver compute to check a CRC, and what does a nonzero result mean? || It divides the received message plus CRC by the generator polynomial over GF(2). A nonzero remainder means the data was changed in a way that is not a multiple of the polynomial, so it is corrupted.
Why does an r-bit CRC detect every burst error of length up to r? || A burst of length at most r is a nonzero polynomial of degree less than r. A polynomial of lower degree than G cannot be a multiple of G, so the remainder is nonzero.
Why is the Internet checksum unable to see two swapped 16-bit words? || It is a sum, and addition is commutative, so the order of the words does not change the total. A CRC depends on the position of every bit, so a swap changes the remainder.
A 32-bit checksum is used on 1 million damaged blocks with random damage. About how many go unnoticed? || Each escapes with probability about 2^−32 ≈ 2.3 × 10^−10, so about 0.0002 blocks, which means almost certainly none.
When must you use SHA-256 instead of CRC32C? || When someone may deliberately alter the data (a CRC is linear and forgeable), or when the value is used as an identity (deduplication, content addressing) where a collision would cause wrong data to be served.

@@ routingalgo
value: A router has several outgoing links and receives packets for millions of destinations. For each destination it must know which link is the best next hop. A small network could be configured by hand, but the Internet changes all the time: links fail, cost changes, new networks appear. Routing algorithms are the distributed procedures by which routers learn the shape of the network and compute, on their own and within seconds, a forwarding table that leads every packet toward its destination without loops.
There are two classic families, and they differ in what routers share. In **distance-vector** routing, each router tells its neighbours only a summary: "I can reach destination D at cost 7." Each router combines the summaries from its neighbours with the cost of the link to each, and keeps the cheapest. It never sees the whole map. In **link-state** routing, each router floods a description of its own links to every router in the area. Every router then holds the same complete map and runs a shortest-path algorithm on it locally. BGP, which joins the networks of the Internet, is a third variant, called path-vector, that is built from distance-vector ideas but keeps the full list of networks along each path so that it can enforce policy and avoid loops.
For the layer above, these protocols fill the routing tables that IP forwarding uses (OSPF and IS-IS inside a company or an ISP, BGP between them, and BGP inside many data-center fabrics). The layers below supply the mathematics. The network is a weighted graph (graph theory, L4), and the two families are the two classic shortest-path algorithms from graph algorithms (L3): Dijkstra's algorithm for link-state and the Bellman–Ford algorithm for distance-vector. What makes routing hard is that those algorithms normally run on one computer with the whole graph in memory, while here they run spread across thousands of routers that only talk to neighbours, with messages that can be lost and a graph that keeps changing.
terms: Routing table — the list a router consults to choose the next hop and outgoing link for each destination prefix.
Metric (cost) — the number assigned to a link or path, such as hop count, delay or inverse bandwidth; the algorithm minimises its sum.
Distance vector — the list of (destination, cost) pairs that a router advertises to its neighbours.
Link-state advertisement (LSA) — a message describing a router's links and their costs, flooded to all routers in the area.
Flooding — forwarding a message to all neighbours except the one it came from, so that it reaches every router.
Convergence — the state in which all routers have consistent tables and no further changes occur; convergence time is how long this takes after a change.
Count to infinity — the distance-vector failure in which routers keep raising their cost to an unreachable destination step by step because each trusts the other's old information.
Path vector — a distance-vector variant that advertises the whole list of networks on the path, as BGP does.
history: The first ARPANET (1969) used a distance-vector style algorithm based on the Bellman–Ford method, which computes shortest paths using only information from neighbours. It was simple and light, and it worked on the first four to dozens of nodes. But it converged slowly, it reacted to changes in queue length too eagerly and caused oscillations, and the count-to-infinity problem made it slow to recover from failures. In 1979 the ARPANET switched to a new algorithm, described by John McQuillan, Ira Richer and Eric Rosen in 1980, in which every node floods its own link states and computes shortest paths itself with a Dijkstra-style algorithm. This was the first link-state protocol. Radia Perlman's 1983 paper on fault-tolerant broadcast of routing information made flooding robust with sequence numbers and ages.
Distance-vector survived in smaller networks. The Routing Information Protocol (RIP) came from the Xerox PARC and BSD "routed" programs and was specified in RFC 1058 in 1988 (RIPv2 in RFC 1723, 1994). Link-state spread through the 1980s and 1990s: IS-IS was designed at DEC and standardised by ISO in the early 1990s (ISO 10589), and the Internet's OSPF version 2 was specified in RFC 1247 in 1991 and its current form, RFC 2328, in 1998. John Moy led the OSPF work.
Between networks, a different need appeared: not shortest path but policy. The Border Gateway Protocol (RFC 1105 in 1989; version 4 in RFC 1654 in 1994, now RFC 4271) uses a path-vector design so that each network can choose paths by business rules. Cisco's EIGRP (1990s) built a loop-free distance-vector protocol using the DUAL algorithm of J. J. Garcia-Luna-Aceves (1993). In the 2010s large data centers, such as Facebook's and Microsoft's, began to run BGP as the only routing protocol inside the fabric, described in RFC 7938 (2016), partly because of its simplicity and policy control. Link-state ideas also moved into software-defined networks, where a central controller holds the map.
how: Both families compute the same kind of answer: for each destination, the minimum-cost path. Let us look at how each does it with only local actions.
Distance-vector. Each router keeps a table of the best known cost to each destination and the neighbour (next hop) that gives it. Periodically, and whenever its table changes, it sends its whole vector to its neighbours. When router X hears from neighbour N that N can reach D at cost c, X computes \( c + \text{cost}(X, N) \) and compares it to its current entry. If it is lower, X adopts it and records N as the next hop. This is the distributed form of the Bellman–Ford equation:
\[ d_X(D) = \min_{N \in \text{neighbours}(X)} \left( \text{cost}(X, N) + d_N(D) \right) \]
Starting from knowing only the directly connected networks, news travels one hop per exchange. After at most as many rounds as the longest path (the network diameter, in hops), all tables are correct, provided nothing changes. This relies on the **graph algorithm** Bellman–Ford, which tolerates arbitrary edge weights and needs only local relaxations, which is why it distributes so naturally. The cost per router is low: memory proportional to the number of destinations, and no need to understand the topology.
The weakness is how bad news travels. If a link fails and the only path to D was through it, a router that did not use the failed path may still advertise a route to D via the router that has just lost it. The two routers then keep improving each other's stale information, adding a link cost each time. This is **count to infinity**. In a chain A–B–C, if C's link to D fails, B hears from A "I can reach D at cost 3" (that path actually goes through B and C), so B thinks cost 4 via A, then A thinks 5 via B, and so on. RIP stops this by defining infinity as 16, so a lost destination is declared unreachable after about 16 steps, which can take minutes with 30-second update timers. Fixes include **split horizon** (do not advertise a route back to the neighbour you learned it from), **poison reverse** (advertise it back with infinite cost), and triggered updates. These solve two-router loops but not all loops. EIGRP's DUAL algorithm guarantees loop freedom by only switching to a neighbour whose reported distance is lower than your own best known cost.
Link-state. Each router discovers its neighbours with periodic hello packets (OSPF default: every 10 seconds on broadcast links, with a neighbour declared dead after 40 seconds; faster with BFD). It then builds an LSA listing its neighbours and link costs, stamped with a sequence number, and **floods** it: each router that receives a new LSA stores it, and forwards it out of all other interfaces. An older or duplicate LSA (by sequence number) is discarded, so flooding stops after reaching everyone. When all routers have the same set of LSAs (the link-state database), each has the same graph and runs Dijkstra's shortest-path-first algorithm from itself to compute a tree of best paths and fill its table. With a binary heap this costs \( O((V + E)\log V) \), which is milliseconds for hundreds of routers.
Because each router computes from the same map, loops can only occur briefly while different routers have different versions of the map. A failure is detected by missed hellos, a new LSA is flooded in a time dominated by propagation and processing (tens to hundreds of milliseconds), and every router recomputes in parallel. Convergence in well-tuned networks is well below a second, much faster than classic distance-vector. The cost is that every router stores the full database and recomputes on each change. To keep this manageable OSPF divides a network into **areas** connected by a backbone area 0; routers inside an area know only summaries of other areas. IS-IS uses levels in the same spirit. The size limit is typically a few hundred routers per area and a few thousand overall.
Path-vector (the step to BGP). Instead of a cost, each advertisement carries the list of autonomous systems (AS numbers) it has crossed. A router that sees its own AS number in the list discards the route, so loops are impossible by construction, and count to infinity cannot occur. Routers pick among paths using policy first (prefer customers over peers over providers) and path length later.

  Distance-vector (Bellman-Ford): neighbours exchange summaries

example: Take the graph with four routers A, B, C, D and link costs A–B = 1, B–C = 1, A–C = 5, C–D = 2. We compute A's table both ways.
Link-state with Dijkstra, run at A. Step 1: set distance A = 0 and all others infinite. Step 2: relax A's links: B = 1, C = 5. Step 3: pick the closest unfinished node, B (1). Relax B's links: via B, C costs 1 + 1 = 2, better than 5, so C = 2. Step 4: pick C (2). Relax C's links: D = 2 + 2 = 4. Step 5: pick D (4); nothing more to improve. A's table: B via B, cost 1; C via B, cost 2; D via B, cost 4. Every router can do this because each holds the same four-node map after the LSAs were flooded: each of the four routers sent one LSA, flooded over 3 links, so a few messages per link, about a dozen messages in all.
Distance-vector with Bellman–Ford, round by round. Round 0: each router knows only its own links. A knows B = 1, C = 5. D knows C = 2. Round 1: A hears from B that B reaches C at 1, so A's C cost becomes 1 + 1 = 2 (via B), better than 5. A also hears from C that D is at 2, so D = 5 + 2 = 7 via C. Round 2: A hears from B that B now reaches D at cost 3 (B learned D from C in round 1), so D = 1 + 3 = 4 via B, better than 7. After two rounds A has the same table as Dijkstra produced: B = 1, C = 2, D = 4, all via B. The number of rounds needed is roughly the number of hops on the longest best path.
Failure. Link C–D goes down. With link-state, C floods a new LSA; within roughly 50 to 200 ms every router has it and recomputes; D is unreachable and removed everywhere. With distance-vector in this small graph: B had D = 3 via C. B now loses that path, but if B hears from A "D = 4" (A's route goes through B, but A does not say so), B sets D = 1 + 4 = 5 via A. A, hearing B's new value 5, sets D = 6, and so on. Split horizon stops this case: A would not advertise D to B because A learned D from B.
intuition: Link-state is every traveller carrying a full map and planning their own route; distance-vector is asking each neighbouring town how far the destination is, and trusting them.
Routing is the shortest-path problem under a constraint: no one sees the whole graph at once, and the graph changes while you solve it. Distance-vector accepts that constraint fully and trades speed and correctness under failure for tiny state. Link-state removes the constraint by spending messages and memory to copy the map to everyone, after which the problem is just an ordinary algorithm. Path-vector adds a memory of the path so a route can recognise itself and refuse to loop. The three designs are the same idea (shortest paths) at different points on the line between "share a summary" and "share everything".
mistakes: People often think link-state is just "better" than distance-vector. In fact it converges faster and avoids count to infinity, but every router needs the full topology, more memory and CPU, and careful area design. For small networks and for policy-driven inter-domain routing, distance-vector and path-vector ideas are simpler and fit better.
People often think routers use the path with the fewest hops. In fact the metric is configurable. RIP counts hops (maximum 15), but OSPF's default cost is derived from link bandwidth, and BGP picks by policy before it looks at path length. Shortest in hops can be a slow, congested link.
People often think BGP finds the best path. In fact BGP finds a path that the local policy prefers. Business relations, local preference and filters outrank shortest AS path, and the result can be longer, unstable or wrong, as route leaks and hijacks show.
tradeoffs: Choose link-state (OSPF or IS-IS) for a network under one administration of tens to a few thousand routers, where you need convergence in well under a second and a clear view of topology for traffic engineering. You pay with memory for the database, CPU for each SPF run, flooding load during instability, and the work of designing areas. Choose distance-vector (RIP, EIGRP) for a small network where simplicity matters, or when the equipment only supports it. RIP's 15-hop limit and slow convergence rule it out for anything large; EIGRP converges fast but was long proprietary.
Choose BGP (path-vector) between organisations, where policy matters more than shortest path and where hundreds of thousands of prefixes (the global table holds roughly a million IPv4 routes) must be carried. Choose BGP inside a large data-center fabric when you want one protocol, simple per-link configuration and fine control of paths (RFC 7938), and accept that its convergence is slower than a link-state protocol unless it is tuned. Choose a central controller computing paths (software-defined networking) when you control all devices and want global optimisation, as Google does in its wide-area network; you give up the autonomy and failure independence of distributed routing and must make the controller highly available.
friction: The core problem is the cost of change. A link that flaps up and down makes every router recompute and, in BGP, can spread across the world; route flap damping and rate limits exist because of it. Convergence is never instant: during it, packets may be lost in black holes or circle in transient loops. Large networks need hierarchy (areas, levels, route summarisation), which hides detail and can make paths less than optimal.
Security is weak by design. Routing protocols mostly trust their neighbours. A wrong LSA or a false BGP advertisement can redirect or drop traffic for a whole network; the 2008 Pakistan Telecom incident that took YouTube offline for about two hours, and many route leaks since then, show it. RPKI and route origin validation are slowly being deployed to fix BGP origin hijacks, but a full path validation is not widely used.
Metrics are simplistic. Cost based on static link bandwidth ignores load, so routing alone cannot balance traffic; equal-cost multipath helps only for exactly equal costs. Load-based metrics were tried in the ARPANET and caused oscillation. Traffic engineering, segment routing and central controllers exist to put traffic on paths these protocols would not choose.
practice: Run OSPF or IS-IS as the interior protocol in a network you control, keep areas small (tens of routers per area is comfortable, a few hundred is a practical maximum), summarise at area borders, and use point-to-point links so that no designated-router election is needed. Set link costs deliberately so that traffic follows the paths you intend, tune BFD for fast failure detection, and enable authentication on adjacencies.
At the edge, filter what you accept and announce: limit the number of prefixes per peer, drop private and too-specific prefixes, and publish route objects and RPKI ROAs so that others can validate you. In data centers, follow RFC 7938 for BGP design: one private AS per rack or per tier, ECMP across equal paths, and short timers. When you debug, look at the routing table (`ip route`, `show ip route`), the protocol database (`show ip ospf database`), and `traceroute` to see the real path; most routing incidents come from a wrong cost, a filtered prefix or a flapping link. If you write a simulator or a service-mesh control plane, remember the same ideas: a registry that holds the full topology (link-state style) is easier to reason about than gossip of summaries.
interview: Why does distance-vector suffer from count to infinity but link-state does not? || In distance-vector a router trusts a neighbour's summary, which may depend on the router's own old route, so they keep raising each other's cost. In link-state each router has the same complete map from flooded LSAs and computes paths itself, so there is no second-hand information to trust; loops appear only briefly while maps differ.
How do split horizon and poison reverse work, and when do they fail? || Split horizon stops a router advertising a route back to the neighbour it came from; poison reverse advertises it back with infinite cost. They break two-node loops but not loops that involve three or more routers. Triggered updates, hold-down timers or DUAL's loop-free conditions are needed for those.
What happens inside OSPF when a link fails, step by step? || Hellos stop or BFD signals, the adjacency goes down, the router originates a new LSA with a higher sequence number and floods it. Each router updates its database, waits a short SPF delay, runs Dijkstra and updates the forwarding table. Well-tuned networks finish in a few hundred milliseconds.
Why is BGP called path-vector and why does it use the AS path? || Each advertisement carries the list of AS numbers traversed. A router drops any route containing its own AS, which prevents loops without a global map, and the path lets operators apply policy such as preferring customers over providers.
Would you use link-state or BGP for a 2,000-switch Clos data-center fabric? || Many large operators use BGP (RFC 7938): one protocol, simple configuration, policy to drain devices, and good fit for ECMP in a regular topology. Link-state works too, and gives faster convergence and a full view, but floods to all 2,000 nodes on each change, so area or hierarchy design is needed.
quiz: What equation does a distance-vector router apply, and which algorithm is it? || d_X(D) = min over neighbours N of (cost(X,N) + d_N(D)). It is the distributed form of the Bellman–Ford algorithm.
Why must an LSA carry a sequence number? || So routers can tell new from old copies during flooding. An older or duplicate LSA is discarded, which stops the flood and prevents stale information from replacing newer.
In a chain A–B–C with all link costs 1 and D beyond C, the C–D link fails. Why can B end up counting upward? || A still advertises a route to D that goes through B and C, and B accepts it as a new path via A. B and A then keep adding 1 to each other's stale value until a limit such as RIP's 16 stops it.
Using the example graph (A–B 1, B–C 1, A–C 5, C–D 2), what is the cost from A to D and the next hop? || 4, via B (A–B–C–D = 1 + 1 + 2). The direct A–C link of cost 5 gives 5 + 2 = 7, which is worse.
You manage a 40-router campus network and a 3-site WAN. What do you pick for each? || OSPF or IS-IS (single area or a few areas) inside the campus for fast convergence and a clear map; for the WAN, OSPF/IS-IS if all sites are under your control, or BGP if you connect to carriers and need policy control over which links carry which traffic.

value: A large data center holds tens of thousands of servers that must talk to each other: a search query fans out to hundreds of machines, a Spark shuffle sends data from every executor to every other, a GPU training job exchanges gradients among thousands of accelerators. The old design for a campus network was a tree: servers hang off access switches, those off aggregation switches, those off a few big core routers. In a tree, every path between two distant servers goes through the same top-level boxes. Those boxes must be the largest and most expensive in the building, and they still become the bottleneck, because the traffic between racks is far larger than the traffic leaving the building.
The modern answer is to build the network from many identical, cheap, small switches wired in layers so that there are many parallel paths between any two servers. In a leaf–spine network (a two-layer Clos network), each server connects to a "leaf" switch at the top of its rack, and each leaf connects to every "spine" switch. Any two servers on different racks are exactly two switch hops apart, and there are as many equal-length paths as there are spines. Capacity grows by adding spines and leaves, not by buying a bigger box. Traffic is spread over the parallel paths by equal-cost multipath routing (ECMP), which hashes the header fields of each flow to pick a path.
For the layer above, this is what makes warehouse-scale computing and the cloud possible: a rack can be placed anywhere, and bandwidth between any two servers is roughly the same, so schedulers need not care about locality as much. It also carries RDMA traffic (RoCE) for GPU clusters. The layers below supply the pieces: Ethernet switching (L3) gives the forwarding hardware, IP routing (L3) gives the way modern fabrics route every hop, graph theory (L4) supplies the Clos and fat-tree topologies with many disjoint paths, and hashing (L3) is how ECMP assigns flows to paths without any per-flow state.
terms: Clos network — a multistage switching network, invented by Charles Clos in 1953, in which each stage connects to every switch of the next stage so that many paths exist.
Leaf–spine — a two-tier Clos network: leaf switches face servers, spine switches interconnect the leaves; every leaf connects to every spine.
Fat-tree — a Clos-based topology built from identical k-port switches in pods, with full bandwidth between all servers.
Bisection bandwidth — the total bandwidth across the narrowest cut that divides the network into two equal halves; the worst-case capacity for all-to-all traffic.
Oversubscription — the ratio of the bandwidth below a switch (to servers) to the bandwidth above it (to the rest of the network); 1:1 means no oversubscription.
ECMP (equal-cost multipath) — spreading traffic across all equal-cost next hops, choosing per flow by hashing.
Flow (5-tuple) — a connection identified by source and destination IP address, source and destination port and protocol.
Elephant and mouse flows — a few large, long-lived flows carry most of the bytes; many small short flows carry few.
history: The idea is much older than computers on racks. In 1953 Charles Clos at Bell Labs designed a multistage switching network for telephone exchanges so that a call could be connected without a giant crossbar of N × N crosspoints; with three stages of small crossbars, the number of crosspoints grows much more slowly than N². The same structure was later used in parallel computers. Charles Leiserson proposed the fat-tree for supercomputers in 1985, a tree whose links get thicker toward the root so that the top does not become a bottleneck.
Data centers got there in the late 2000s. Network switches then were expensive, and big Ethernet and IP core routers cost many times more per port than commodity switches. In 2008, Mohammad Al-Fares, Alexander Loukissas and Amin Vahdat at UC San Diego published "A Scalable, Commodity Data Center Network Architecture" (SIGCOMM 2008), which showed how to build a fat-tree from identical commodity switches so that any server could talk to any other at full line rate. Microsoft's VL2 (2009) and others followed. Google described its own multi-generation fabrics, culminating in "Jupiter Rising" (SIGCOMM 2015): 1.3 petabits per second of bisection bandwidth, enough for each of 100,000 servers to send at 10 Gb/s, built from merchant-silicon switch chips. Facebook published its data center fabric in 2014, built from small "pods" and four "spine planes",.
The 2010s brought two more changes. Operators moved from layer 2 switching to routing every hop with IP, often with BGP as the only protocol (RFC 7938, 2016). And since about 2018 the arrival of GPU clusters has pushed designs toward large, nearly non-blocking fabrics with 400 Gb/s or 800 Gb/s links and RDMA over Converged Ethernet (RoCE) or InfiniBand. Google's later Jupiter paper (SIGCOMM 2022) replaced the spine layer with optical circuit switches that can be reconfigured, to allow upgrades without taking the network down.
how: Start with the building block. A switch has k ports, each at a speed such as 100 Gb/s. A leaf–spine network uses a layer of leaf switches and a layer of spine switches. Each leaf uses some ports for servers (down) and the rest for spines (up). If a leaf has 64 ports, 32 down and 32 up, then it connects to 32 spines with one link each. Each spine has 64 ports and so can connect to 64 leaves. Total servers: 64 leaves × 32 servers = 2,048. Every server has the same capacity to every other, because the bandwidth up from each leaf (32 links) equals the bandwidth down (32 links): the oversubscription is 1:1. The general limit of a two-tier network with k-port switches is k²/2 servers. For more, add a third tier.
The fat-tree extends this with pods. With k-port switches (k even), a pod holds k/2 edge (leaf) switches and k/2 aggregation switches. Each edge switch has k/2 server ports and k/2 uplinks, one to each aggregation switch in the pod. There are (k/2)² core switches, and each aggregation switch connects to k/2 of them. The network supports \( k^3/4 \) servers. With k = 48 that is 27,648 servers from identical 48-port switches, with 576 core switches. This is where **graph theory** enters: the topology is a graph with many edge-disjoint paths between any two vertices, and the bisection bandwidth is the min-cut. Between two servers in different pods there are (k/2)² distinct shortest paths, each of six links (five switches). Capacity is high because every layer has as much bandwidth as the layer below it; the network is "rearrangeably non-blocking".
Forwarding. In the modern design, every switch is a router. A server's address belongs to a subnet on its leaf. Each leaf and spine learns routes with a routing protocol (BGP in most large fabrics, or OSPF/IS-IS). For a destination on another rack, the leaf has not one best next hop but many equal-cost next hops, one per spine. This is the contribution of **IP routing**: a routed fabric has no spanning tree to block links, so all links carry traffic and failures are handled by ordinary route convergence. Classical layer-2 Ethernet networks use a spanning tree that disables redundant links, which would waste exactly what a Clos network offers. Where a layer-2 domain is needed across racks (for virtual machines), overlay protocols such as VXLAN tunnel Ethernet frames over the routed IP fabric.
ECMP chooses among the equal-cost next hops. A switch computes a hash of the 5-tuple of each packet (source IP, destination IP, protocol, source port, destination port) and uses the hash modulo the number of next hops to choose a link. This is **hashing** used for load balancing: all packets of one flow hash to the same link, so they take the same path and arrive in order (TCP reacts badly to reordering), and different flows spread roughly evenly, with no state in the switch. Hardware does this at line rate with a CRC-like function over the header bytes.
The weakness is that hashing balances flows, not bytes. If two elephant flows hash to the same uplink, that link is overloaded while others sit idle, and neither flow gets full speed. With few large flows the law of large numbers does not help. Mitigations are: more entropy (use the source port, which also lets a host change the path by changing the port or the IPv6 flow label), splitting large transfers into many parallel connections, flowlet switching (re-hash after a pause in a flow, so reordering is safe), per-packet spraying with reordering handled at the receiver (used in some AI fabrics), and adaptive routing in switches that senses congestion. Another approach is centralised traffic engineering that assigns flows to paths.
Failures show the benefit of the design. If one spine or one link fails, a leaf loses 1 of its 32 uplinks, so it loses about 3% of its capacity, and ECMP shifts the flows to the other 31 within the routing convergence time (hundreds of milliseconds with BFD and fast BGP timers). In the old tree design, losing a core router could halve the cross-building bandwidth.

example: Take a leaf–spine network with 4 spines and 4 leaves, each link 100 Gb/s, and 8 servers per leaf. Let us compute things you can check with a pen.
Capacity first. Each leaf has 8 × 100 = 800 Gb/s of server-facing capacity and 4 × 100 = 400 Gb/s of uplink capacity (one link to each spine). The oversubscription is 800:400 = 2:1. Under all-to-all load where every server sends at full speed to servers on other racks, each server could get only 50 Gb/s. To make the fabric non-blocking, use 8 spines (8 uplinks per leaf, 1:1). The number of servers is then 4 × 8 = 32; the bisection bandwidth is the total capacity of the links cut when the leaves are split into two halves: 2 leaves × 8 uplinks × 100 Gb/s on each side = 1.6 Tb/s, equal to the 16 servers on one side sending 100 Gb/s each.
Now ECMP collisions. In the 4-spine network, suppose four elephant flows (each wants 100 Gb/s) leave one leaf, and each is hashed independently onto one of the 4 uplinks. The chance that they land on four different uplinks is 4!/4⁴ = 24/256 ≈ 9.4%. In the other 90.6% of cases at least two share an uplink, and each of those flows gets at most 50 Gb/s. With 8 flows on 8 uplinks, the chance of a perfect spread is 8!/8⁸ ≈ 0.24%, so a collision is almost certain. Many small flows behave better: with 1,000 flows of equal size hashed over 4 links, each link gets 250 ± about 14 flows (standard deviation \( \sqrt{1000 \times 0.25 \times 0.75} \approx 13.7 \)), under 6% imbalance.
Scale-out. A fat-tree built from 64-port switches (k = 64) supports 64³/4 = 65,536 servers with (64/2)² = 1,024 core switches, all from the same switch. A two-tier network from the same switch holds 64²/2 = 2,048 servers. This is the reason large operators go to three tiers: each added tier multiplies the size by k/2 = 32, at the price of two more hops and more links.
Failure. In the 32-server, 8-spine network, one spine fails. Each leaf loses one of 8 uplinks, so capacity falls by 12.5% and ECMP moves the flows onto the other seven; no server loses connectivity.
intuition: Instead of one huge highway interchange, a city grid of many ordinary streets: no single street matters much, and any trip has many equally good routes.
The design is natural because of a simple fact: cheap, identical parts are far cheaper per unit of capacity than a few big special parts, and parallelism is the way to turn many small parts into one big capacity. A Clos network is the structure in which parallel parts are always used in a balanced way, and the graph has so many disjoint paths that no single failure matters. ECMP hashing is natural for the same reason as in a hash table: with no coordination, hashing spreads items evenly in expectation, and each item stays in its place. Only the elephant flows break this, because the law of large numbers needs many items.
mistakes: People often think a Clos fabric has unlimited bandwidth between any two servers. In fact it has full bandwidth only if it is built at 1:1 oversubscription, and many real fabrics are 2:1 or 3:1 at the leaf to save cost. The bandwidth guarantee also holds only for traffic that is spread well over the paths.
People often think ECMP balances load evenly. In fact it balances the number of flows in expectation, not the bytes. Two elephant flows on the same link are enough to cause a hotspot, and a hash that ignores some header bits can make all flows from one pair of hosts take one path.
People often think the network is flat, so placement does not matter. In fact the path between two servers in one rack takes one switch hop, in the same pod three, and between pods five (in a fat-tree), with different latencies (roughly 1 µs to a few µs added), and rack-level failures or oversubscription still make locality useful.
tradeoffs: Choose a two-tier leaf–spine fabric when the server count is within k²/2 of your switch radix (about 2,000 servers with 64 ports, 8,000 with 128 ports), because it has the lowest latency (two switch hops between racks), the fewest devices and the simplest operation. Choose three tiers (fat-tree, or leaf–spine–superspine) when you need tens of thousands of servers or more; you give up one more hop of latency and a larger number of links and optics, which is the main cost of the network.
Choose 1:1 oversubscription for GPU training fabrics and for storage or shuffle-heavy clusters where traffic is all-to-all and the network is the bottleneck; the network is already a large share of the cluster cost. Choose 2:1 to 4:1 for general-purpose web or batch clusters where most traffic stays in a rack or a pod and servers rarely use full line rate; you save half or more of the spine capacity but you must keep the heavy-traffic jobs inside a pod.
Choose plain ECMP when flows are many and small, which is typical for web services. Choose flowlet switching, adaptive routing or per-packet spraying when a few large flows dominate, as in AI training with collective operations, accepting more complex switch features or receivers that handle reordering. Choose BGP as the fabric protocol for simplicity and policy at scale, and link-state if you need the fastest convergence or a global view.
friction: The biggest limit is the cost and power of the network itself. Cables and optical transceivers dominate: a 27,000-server fat-tree has hundreds of thousands of links, each needing two transceivers, and the optics fail more often than switches. Cabling errors are a major source of outages, and miswired links can be hard to find. The physical layout (cables from every rack to every spine) also limits how a data center building can be shaped.
Congestion control remains hard. ECMP collisions waste capacity, and incast (many senders to one receiver, as in a shuffle) overflows shallow switch buffers, causing drops and TCP timeouts. Solutions such as DCTCP (using ECN marks), priority flow control and RoCE congestion control (DCQCN) exist, but lossless Ethernet with priority flow control can create head-of-line blocking and even deadlocks, so large RoCE fabrics need careful design. Gray failures, such as a link that drops 1% of packets without going down, are hard to detect and cost a lot because TCP reacts badly, so operators run constant probing to find them.
practice: When you design or use a data-center network, start with the traffic matrix: how many servers, what fraction of traffic stays in a rack, how heavy cross-rack flows are. Size switch radix and oversubscription from that, with the formula servers = k²/2 for two tiers and k³/4 for three. Plan for incremental growth by adding spine capacity before you need it, and keep every device type identical so spares are interchangeable.
As an application engineer, remember that bandwidth between racks is large but not free: put chatty services and the shards of one query in the same pod when you can, keep the number of parallel connections high so that ECMP can spread them, and use different source ports for different bulk transfers. Measure with `iperf3` across many connections and `traceroute` or Paris-traceroute to see the ECMP paths. Watch retransmission counts, switch drops and ECN marks, because a 1% loss on one link can slow a distributed job far more than the average suggests. For Spark or Kafka clusters on a cloud network, understand the placement groups, availability zones and cross-zone costs: the fabric is fast inside a zone, but the traffic between zones is billed and slower.

value: When you build a system in layers, you must decide at which layer each function lives: reliable delivery, ordering, duplicate removal, encryption, compression. The end-to-end argument gives a rule for this decision. It says that a function can be implemented completely and correctly only with knowledge that exists at the endpoints of the communication, the applications that actually produce and use the data. A lower layer may offer the function as a help, but it cannot make the function unnecessary at the endpoints, so the endpoints must do it anyway. The lower layer is then justified only as a performance optimisation, and only if its cost is acceptable for all users.
The classic example is copying a file between two computers. The network can provide reliable, ordered delivery of packets. Yet the file can still arrive damaged: the disk read may return bad data, the sending program may have a bug, a memory error may hit the buffer, a router may corrupt a packet after its link-level check, or the receiving disk may write the wrong block. Only the two endpoints can check the thing the user cares about: "the file I wrote equals the file you read". So the endpoint must verify the whole file, for example by comparing a checksum of the file at both ends, and retry the whole transfer if it fails. Once you do that, a perfectly reliable network gives no correctness gain. It can only make the transfer faster by reducing how often the retry is needed.
This rule shapes the Internet itself. IP is a simple "best effort" service that may drop, duplicate or reorder packets; TCP at the hosts builds reliability; the routers stay simple and fast. It also shapes the design of every modern data pipeline: idempotency keys sent by the client, end-to-end checksums in storage, exactly-once results that depend on the sink. The layers below supply the logic. Proofs (L4) explain what kind of statement this is: an argument about which guarantees can be given from where, much like an impossibility result. Reductionism and abstraction (L5) explain layering itself, the idea of hiding a part behind an interface, and the end-to-end argument says where that hiding leaks: you cannot hide a correctness requirement from the endpoints.
terms: Endpoint — the application at either end of a communication; it knows what the data means and what counts as correct.
Layer — a part of a system that offers a service to the layer above and hides how it is done.
Best-effort service — a service that tries to deliver but gives no guarantee, such as IP packets.
Fate sharing — the design rule that state needed by a connection should be kept in the endpoints that use it, so it is lost only when those endpoints fail.
Idempotent operation — an operation that has the same effect whether it is done once or many times.
Performance enhancement — a feature in a lower layer that does not remove the need for the endpoint check, but reduces its cost.
Acknowledgement (ACK) — a message from the receiver saying that data arrived; an ACK from a lower layer says only that the lower layer got it, not that the application used it.
Middlebox — a device in the network path, such as a firewall, NAT or proxy, that looks at or changes traffic.
history: The argument was published in 1981 as "End-to-End Arguments in System Design" by Jerome Saltzer, David Reed and David Clark at MIT, at the Second International Conference on Distributed Computing Systems. A revised version appeared in ACM Transactions on Computer Systems in November 1984, and that is the version usually cited. It grew out of the authors' experience with early Internet protocols and with MIT systems.
The paper described several examples: reliable file transfer, delivery guarantees ("the message arrived" does not mean "the user acted on it"), secure transmission (encryption in the network helps, but the endpoints need to authenticate each other), duplicate message suppression, FIFO message delivery, and transaction management. The authors also described real cases in which data was damaged inside gateways or hosts after the link-level checks had passed, so only an end-to-end check could find the damage.
The argument became a guide for the Internet's architecture. David Clark's 1988 paper "The Design Philosophy of the DARPA Internet Protocols" explained why TCP/IP put reliability in the hosts and kept the gateways simple, and why fate sharing mattered for survival of the network under attack or failure. In 2001, Marjory Blumenthal and David Clark wrote "Rethinking the Design of the Internet: The End-to-End Arguments vs. the Brave New World", about how firewalls, NATs, content distribution networks and commercial pressure were wearing the principle away. In data systems, the same idea reappeared in Pat Helland's writing on idempotence and "life beyond distributed transactions" (2007), in the idempotent producer of Kafka (2017) and in the "exactly-once" debates of the stream-processing community.
how: Start from a chain. An application at host A sends data to an application at host B through layers: the application, a transport protocol, the network, links, and physical hardware. Each layer can fail in its own way, and each can add a check or a retry. The question is where to put the check that really decides correctness.
Step 1: define what correct means. Correct is a property of the application: "the file on B equals the file on A", "the payment was applied exactly once", "the user's browser rendered what the server sent". A lower layer does not know this. A network link knows only about frames, TCP only about bytes of a stream, and a message queue only about messages. This is the contribution of **abstraction** (the L5 concept of reductionism and layered abstraction): each layer exposes a simple interface and hides details, which makes systems manageable, but also means that a lower layer cannot see the application's definition of success.
Step 2: list the places where the data can be damaged or lost. Between the two applications there are many: the sending program's buffer, the library, the operating system, the NIC, each link, each router's memory and queues, the receiving NIC, the receiving operating system, the application, the disk. A check at one lower layer covers only the part below it. If you add a reliable layer at the link and another at the transport, there is still the portion above the check and the portion where the data passes between layers (for example from the NIC's memory into the kernel).
Step 3: the only check that covers all of them is one that spans the whole path from the creation of the data to its final use. This is the end-to-end check, performed by the applications: a checksum or hash of the whole object, a sequence number or unique ID in the message, an application-level acknowledgement that confirms the action. Here the **proof-style** reasoning enters: the claim is an argument by cases. For any function F implemented at a lower layer, if the endpoints need F to be correct against failures that the lower layer cannot see, the endpoints must implement F themselves. Therefore the lower-layer implementation is redundant for correctness. This is like an impossibility argument of the form "you cannot get property P from below".
Step 4: decide whether to put anything in the lower layer at all. The answer depends on cost and benefit. A lower-layer feature can still be valuable as a performance enhancement when it is cheap and helps most users. Link-level retransmission on a lossy wireless link is the standard example. A WiFi frame is lost perhaps 10% of the time; if only TCP repairs it, each loss costs a timeout of at least tens of milliseconds and TCP also thinks the network is congested and slows down. Retrying at the link in a millisecond is far faster. But the endpoints still run TCP's checks, because the link-level retry does not protect against the other failures. The test is: does the lower-layer feature reduce the frequency of end-to-end retries enough to pay for itself, and does it harm applications that do not need it? A guarantee that every user must pay for, even those who do not want it, is suspect. For example, forcing a strict reliable-ordered delivery inside the network would delay real-time voice, which prefers to skip a lost packet rather than wait for it.
Step 5: use the result in design. In the Internet, IP is best effort and TCP provides reliability at the hosts. The hosts keep the connection state (fate sharing), so a router restart loses no connection. In applications, the pattern is: assume messages may be duplicated, delayed or lost, and give each request an idempotency key so the server can drop repeats. In storage, store a checksum with each object and verify when it is read. In stream processing, "exactly once" is achieved by combining at-least-once delivery with deduplication or atomic commits at the sink, that is, the endpoint takes part. In security, TLS from the client to the server is the end-to-end choice; link encryption (such as WiFi or VPN) protects one hop but the data is exposed at each intermediate system.

example: A company copies a 2 GB log file every night from server A to server B. The transfer uses TCP over a network where every link has a CRC. Why can the file still arrive damaged, and what should the endpoints do?
Look at the failure rates. Suppose, as an assumed figure for illustration, that the chance a packet is damaged in a way that passes the link CRC and TCP's 16-bit checksum is 1 in 10 billion. The file has 2 GB / 1,460 bytes ≈ 1.4 million packets, so one transfer has about 1.4 × 10⁶ / 10¹⁰ = 0.014% chance of an undetected corruption. That is small, but 100 files a night for a year is 36,500 transfers, which gives about 5 corrupted files. Add sources that no network layer sees: a memory error on A (large fleet studies find correctable memory errors on a noticeable share of servers every year), a bug in the sending application, a failed disk write on B. Each is rare; together they are not.
The end-to-end fix is cheap. After the copy, B computes the SHA-256 of the file as stored on disk (not of the received buffer) and compares it with the SHA-256 that A computed from the original. This takes about 2 GB / 500 MB/s = 4 seconds of CPU on each side. If the values differ, the job copies the file again. Now the probability of an undetected error is about \( 2^{-256} \), which is zero in practice, and no property of the network matters for correctness. A better network (or TCP retransmission) matters only for speed: if the network corrupts nothing, the check passes the first time; if it corrupts a lot, you retry many times and the job becomes slow. This is exactly the paper's performance argument.
A second example: a payment API. A client calls `POST /charge` and the connection times out. The client does not know whether the server charged the card. TCP's acknowledgement says only that bytes were received by the server's kernel, not that the charge happened. A "reliable" HTTP layer or message queue cannot decide whether to retry, because only the application knows if a second charge is acceptable. The end-to-end design: the client generates an idempotency key `K` (a UUID) once and sends it with every attempt. The server stores `K` with the result of the first charge, in the same database transaction as the charge. If the same `K` arrives again, the server returns the stored result instead of charging again. Now retries are safe, any number of times. The client's retry plus the server's deduplication together give "exactly once" effect; neither the network nor a queue could have provided it alone.
intuition: Mailing a valuable item: the postal service tracking number is useful, but only the recipient opening the box and checking the contents can confirm that what arrived is what you sent.
The principle is natural because of one fact: correctness is defined at the ends. Any middle part sees only a slice of the path, so it can reduce failures but cannot certify success. Once the ends have to certify success anyway, the middle can be kept simple, and simple middles are cheaper, faster, and easier to upgrade. The Internet grew because routers carried packets and nothing else, and every new application (the web, video, voice, peer-to-peer) could be built at the edges without asking anyone in the middle for permission. The argument is therefore not only about correctness; it is also about where change is cheap.
mistakes: People often think the end-to-end argument says lower layers should do nothing. In fact it allows and even encourages performance enhancements, such as link-level retransmission on lossy wireless or TCP offload in a NIC. It only says they cannot replace the endpoint check, and that their value must be judged by cost and benefit.
People often think TCP gives reliable delivery to the application. In fact TCP gives a reliable byte stream between two kernels. A reset, a crash after the data was ACKed but before the application processed it, a timeout, or a bug leaves the application without knowing what happened. Application-level acknowledgements and idempotency are still needed.
People often think "exactly-once delivery" can be provided by a broker or a network. In fact the broker cannot know whether the consumer's side effect happened. What systems provide is at-least-once delivery plus idempotent or transactional processing at the sink, which gives exactly-once effect. The end-to-end argument is the reason.
People often think the argument is an absolute law. In fact the authors presented it as an argument to use with judgment. Today's networks have middleboxes, NATs, load balancers and CDNs that break pure end-to-end behaviour, and sometimes the lower layer is the best place for a function, for example congestion control in switches (ECN) or encryption in a data-center link (MACsec) where the cost of doing it at every application would be high.
tradeoffs: Choose the end-to-end check when a failure would be costly and the lower layers cannot see it: file integrity, payments, backups, data pipelines. The price is some CPU, an ID per request and a retry path, typically small compared to the cost of silent corruption. Choose a lower-layer help when the same failure is frequent and local, and fixing it at the endpoint would be slow: link-level ARQ on WiFi or cellular, forward error correction on a satellite link, hardware checksum offload. You accept a more complex lower layer, and the risk that people start to rely on it for correctness.
Choose to keep the network simple (best effort) when you want the freedom to build new applications at the edges and many different needs (reliable files, real-time voice, loss-tolerant video) share the same network. Choose a smarter network (QoS, in-network processing, deep packet inspection, a service mesh sidecar) when you control both ends and the benefit is operational: observability, policy, retries, mutual TLS. You pay with lost transparency, a new place for bugs, and a layer that cannot see correctness anyway; a mesh retry of a non-idempotent call can double a charge.
friction: The argument is easy to state and easy to forget, because lower-layer guarantees feel convincing. "The queue is durable", "the network is reliable", "the database has transactions" all hide the same fact: they cover a part of the path. Teams repeatedly discover the gap in production, as duplicate charges, lost updates, or files that pass transfer but fail on read.
The argument also has costs and limits. End-to-end checks mean every application must implement idempotency and integrity, which is work, and libraries do it unevenly. Checks at the ends tell you that something is wrong but not where; localisation needs extra tools such as per-hop checksums or tracing. And for some functions, the endpoint does not have enough information. Congestion control is the standard case: a host can only guess the load in the middle of the network from losses and delays, while a router knows its own queue, so explicit signals (ECN, in-network telemetry) put some of the function back in the middle.
practice: For every operation that crosses a boundary (network call, queue, file copy, database write by another service), ask: what does correct mean here, who can check it, and what happens if the operation is repeated or lost? Give every write request a client-generated idempotency key and make the server store it with the result in the same transaction. Verify data with a checksum or hash stored at creation time, and verify it at the final use, not at an intermediate hop. Do not treat an acknowledgement from a lower layer as proof of the effect you care about.
In data pipelines, combine at-least-once delivery with idempotent sinks (upserts by key, partition overwrite, transactional commits that include the offset) to get exactly-once effect. Keep timeouts and retries at the caller with exponential backoff and jitter, and retry only operations that are idempotent or protected by a key. Use checksums in storage formats (Parquet page CRCs, Kafka batch CRC32C) and end-to-end verification when copying data between systems, for example comparing row counts and hashes of partitions after a migration. When you add a feature in the middle (a proxy, a mesh retry policy, a cache), write down which end-to-end check still protects the user and what the feature changes for performance, not for correctness.

value: Threads that share memory need to coordinate. The usual tool is a lock, but locks have well-known costs: a thread that holds a lock can be descheduled, crash or be delayed by a page fault, and then every other thread waits behind it. Lock-free and wait-free programming tries to avoid this by using atomic hardware instructions directly. Maurice Herlihy's 1991 paper "Wait-Free Synchronization" asked a sharp question about these instructions: which ones are powerful enough, and which are not? The answer divides the instructions into a strict ladder, and it explains why every modern CPU has compare-and-swap (CAS) or its equivalent.
Two terms set the goal. An operation is **wait-free** if every thread that calls it finishes in a bounded number of its own steps, no matter how slow or stopped the other threads are. It is **lock-free** if, at any time, at least one thread makes progress, though an unlucky thread may retry forever. Wait-freedom is the strongest form: no lock, no starvation, no dependence on the scheduler. Herlihy measured the power of an atomic object by its **consensus number**: the largest number of threads for which the object, together with ordinary registers, can solve consensus, the problem of getting threads to agree on one value that one of them proposed. Plain reads and writes have consensus number 1. Test-and-set, fetch-and-add, swap, queues and stacks have number 2. CAS has number infinity.
Why does this matter for the layer above? Consensus is the key to building shared objects. Herlihy proved that with an object of consensus number n you can build a wait-free version of any shared object for n threads, and with CAS you can do it for any number of threads. So the lock-free queues in the JVM and Linux, and the atomic instructions in every CPU, rest on this result. The layers below supply three things. Computability (L3) provides the style of argument: like the halting problem and the FLP result, this is an impossibility theorem, proved by showing that no algorithm can exist. Proofs (L4) provide the valency argument used for the impossibility. And locks and atomics (L3) provide the practical background: the instructions, their cost and the problems of locks that motivate the question.
terms: Wait-free — every operation completes in a bounded number of the calling thread's own steps, whatever other threads do.
Lock-free — some thread always makes progress in a finite number of steps, but an individual thread may starve.
Obstruction-free — a thread that runs alone for long enough finishes; it is the weakest of the three.
Consensus — n threads each propose a value and all must decide the same value, which was proposed by one of them, in a wait-free way.
Consensus number — the largest n for which an object (plus registers) can solve wait-free consensus among n threads; infinity if there is no limit.
Compare-and-swap (CAS) — an atomic instruction that sets a memory word to a new value only if it still holds an expected value, and tells whether it succeeded.
Register — a memory word with atomic read and write only.
Valency — in the impossibility proof, the set of decisions still possible from a given state of the system; a state is bivalent if both outcomes remain possible.
history: Concurrent programming started with locks and semaphores (Dijkstra, 1965), and the first work on non-blocking algorithms was practical. IBM added compare-and-swap to the System/370 in the early 1970s, and R. Kent Treiber described a lock-free stack in 1986. In the theory of distributed systems, the 1985 FLP result of Fischer, Lynch and Paterson showed that agreement is impossible in an asynchronous message-passing system if even one process may crash. This was a warning that coordination under failures is hard in a precise sense.
In 1987 Michael Loui and Hosame Abu-Amara, and independently Danny Dolev, Cynthia Dwork and Larry Stockmeyer, proved a related result for shared memory: consensus for two processes cannot be solved wait-free with only atomic read/write registers. Maurice Herlihy turned this into a general theory in "Wait-Free Synchronization", published in ACM Transactions on Programming Languages and Systems in January 1991. He defined the consensus number, placed a number of standard primitives on the ladder, and proved the universality of consensus: any object with consensus number n can implement any other object wait-free for n threads. The paper was written when machines offered mixed primitives, and it argued that a machine designer should provide universal ones.
Practical consequences followed quickly. Michael and Scott published their lock-free queue (1996), based on CAS, and it became the model for the Java `ConcurrentLinkedQueue`. The Java `java.util.concurrent` package (2004, from Doug Lea's work) put CAS-based atomics and non-blocking collections into a mainstream language. Intel, ARM and others kept CAS or load-linked/store-conditional (LL/SC) as the basic atomic, and ARMv8.1-A added single-instruction CAS and other atomics for better scaling. Wait-free data structures remained hard to build efficiently until Kogan and Petrank (2011) and Yang and Mellor-Crummey (2016) showed wait-free queues with speed close to lock-free ones. Herlihy and Shavit's book "The Art of Multiprocessor Programming" (2008, revised 2020) made the theory the standard teaching text.
how: Start with the problem: wait-free consensus. Each of n threads has an input value. A protocol must make every thread decide a value (termination, in a bounded number of its own steps), all decisions must be equal (agreement), and the decision must be one of the inputs (validity). The protocol may use shared objects, and any thread may be arbitrarily slow or may stop. This looks like a toy problem, but Herlihy showed that it is the right measure of power.
Registers cannot solve it for two threads. The proof uses a **valency** argument, the same style as the impossibility proofs in **computability**. Suppose a protocol for threads A and B exists using only read/write registers. With A proposing 0 and B proposing 1, the outcome is not yet decided: the state is bivalent (both decisions are still possible). Keep choosing steps that stay bivalent. Because the protocol must terminate, you reach a critical state: a bivalent state where A's next step `a` leads to a state from which only 0 can be decided (0-valent) and B's next step `b` leads to a 1-valent state. Now look at what `a` and `b` touch. Case 1: one of them is a read, say `a`. A read leaves memory unchanged, so the state after `b` and the state after `a` then `b` look the same to B; B running alone from either must decide the same, yet one state is 1-valent and the other is 0-valent. Case 2: they write different registers. Then the order does not matter, both orders give the same state, but that state would be both 0-valent and 1-valent. Case 3: they write the same register. If A writes then B writes, B's value overwrites A's, so B running alone cannot tell this state from the state where only B wrote. Same contradiction. So no such protocol exists, and registers have consensus number 1. The proof only uses the fact that a thread can be stopped at any time, which is what "wait-free" demands.
Test-and-set (TAS) reaches level 2. TAS atomically sets a flag to 1 and returns the old value. For two threads, each first writes its input into its own register, then calls TAS. The thread that sees 0 won: it decides its own input. The thread that sees 1 lost: it decides the input of the other thread, which it reads from the other's register (the winner wrote it before its TAS). Both agree and both finish in a bounded number of steps. The same works for fetch-and-add, swap, queues and stacks (the first to dequeue a marked item wins). But no object at level 2 can solve consensus for three threads: a similar valency argument shows that with three threads, the result of a TAS cannot separate the two threads that lost. Herlihy showed that an atomic assignment to m registers reaches level 2m − 2, so the ladder has rungs everywhere between.
Compare-and-swap reaches infinity. All threads share a word `winner` initialised to a special empty value. To decide, a thread does `CAS(&winner, EMPTY, myinput)` and then reads `winner`. Exactly one CAS succeeds, because the others see a non-empty value; every thread then returns the same word. This takes two steps, whatever the number of threads. The same holds for LL/SC. This is why hardware designers provide CAS or LL/SC: nothing weaker can build all objects.
Why consensus is universal. Herlihy's **universal construction** builds any object, such as a queue, a counter or a hash map, from consensus objects. Think of the object as a sequential specification, and keep a log (a linked list) of all operations in the order they take effect. To apply an operation, a thread announces it in a shared array, then tries to append a cell to the log. All threads that compete to append the next cell use a consensus object to agree which one wins. The state of the object is the result of replaying the log from the start. Since all threads see the same log, the object is linearizable (each operation looks as though it happens instantly at one point). To make it wait-free and not only lock-free, threads help: when appending, a thread picks the announced operation of the thread whose turn it is (by cell number modulo n), not its own, so any announced operation is chosen within n rounds. This makes every operation finish in a bounded number of the caller's own steps. The construction is slow in practice, but it proves that nothing is lost by having only CAS.
The resulting ladder is a strict hierarchy. An object at level k cannot implement an object at a higher level for more than k threads, in a wait-free manner, however clever the algorithm is. That is why a lock-free queue can be built from CAS but not from loads and stores alone, and why a CPU that has only atomic reads and writes cannot support wait-free queues for three threads.

example: First a concrete use of CAS: a lock-free counter and a lock-free stack. The counter loop reads the value, computes the new value and tries CAS; if another thread changed it, the CAS fails and the loop retries.
```c
void push(node **top, node *n) {
    node *old;
    do {
        old = atomic_load(top);
        n->next = old;
    } while (!atomic_compare_exchange_weak(top, &old, n));
}
```
Each failed CAS means that another thread succeeded in the meantime, so the system as a whole progresses: this is lock-free. But a single thread can lose the race again and again, so it is not wait-free. With 8 threads pushing constantly, a thread may retry many times; the expected number of retries grows with contention. A wait-free counter is available with hardware fetch-and-add (`lock xadd` on x86): it completes in one step for every thread, so it is wait-free on that hardware. This is a practical difference: use fetch-and-add for counters and CAS for pointer structures.
Now the consensus examples with a pen. Two threads A and B, inputs 5 and 9. Using TAS: A writes prop[A]=5, B writes prop[B]=9. Suppose B calls TAS first and gets 0, so B decides 9. A calls TAS and gets 1, so A reads prop[B] = 9 and decides 9. Both decide 9 and agree. Had A won, both would decide 5. Check that this is wait-free: even if B is suspended right after its TAS, A decides in 3 steps, and if A is suspended, B finishes alone in 3 steps. Now try three threads, A, B and C. TAS gives one winner, but a loser (say A) sees only "1". It cannot tell if B or C won, because both B and C could have run TAS before it. It must read prop[B] or prop[C], and if it guesses wrong the threads decide differently. That is the intuition for why TAS has consensus number 2. With CAS and three threads: `CAS(&winner, EMPTY, input)`; all three then read winner. The first CAS wins, and all return its value, including A, B and C in any order.
A failure case: the ABA problem. Thread 1 reads the stack top as node X and is suspended. Meanwhile other threads pop X, pop Y, free X and push a new node that happens to reuse X's address. Thread 1 resumes and its CAS(top, X, X->next) succeeds because the address matches, but `X->next` is stale, so the stack is corrupted. CAS compares values, not history. Fixes: attach a version counter to the pointer so that the CAS checks both (double-width CAS or a tagged pointer), use hazard pointers or epoch-based reclamation so that memory is not reused while a thread may read it, or use a garbage-collected language where freed addresses are not reused (in Java, ABA on references to nodes is much less common).
intuition: Atomic instructions are like tools for agreeing on a winner; a notice board anyone can write to is not enough, because a late writer can erase the earlier note, but a "first stamp wins" machine is.
The result is natural once you see that every shared object, to be useful, must in the end decide an order among competing operations: who goes first. Reads and writes give no way to decide: whoever writes last erases the evidence of who wrote first, so a stopped thread can never learn the order from memory alone. CAS records the winner permanently, in one atomic step, so everyone can read the same answer. The hierarchy therefore measures how many competing threads an instruction can keep from erasing each other. It is the same idea as the impossibility results of distributed systems, with crashes replaced by arbitrarily slow threads.
mistakes: People often think lock-free means wait-free. In fact lock-free guarantees that the system as a whole progresses, but individual threads can starve forever under contention. Wait-free guarantees progress for each thread. Wait-free algorithms are rarer, more complex and often slower on average.
People often think lock-free code is always faster than locks. In fact under low contention a well-implemented lock is cheap, and under high contention both suffer: CAS loops waste work and bounce cache lines between cores. Lock-free gives you no deadlock and robustness against a stalled thread; it does not give speed for free.
People often think CAS solves everything because it is universal. In fact universal means "possible", not "practical". The universal construction is slow, and real structures (queues, hash maps) use carefully designed algorithms with extra problems such as ABA and memory reclamation.
tradeoffs: Choose locks (a plain mutex) when the critical section is short and contention is low or moderate, when the code must be easy to read and verify, and when thread delays are not a correctness issue. This is the right default for most application code. Choose lock-free structures (CAS loops) when a stalled or preempted thread must not block others: in interrupt handlers, in real-time or signal-safe code, in the allocator or scheduler, and in high-contention queues in a runtime. You accept harder code, ABA and reclamation bugs, and no guarantee of fairness.
Choose wait-free algorithms when you need a hard bound on every operation, such as real-time control or a latency-critical path with a strict tail target. Examples: fetch-and-add counters, single-producer single-consumer ring buffers, and some queues built on fetch-and-add. You pay with complexity and often some average speed. For most problems, choose the simplest primitive that is strong enough: a single `fetch_add` is wait-free and beats a CAS loop; a SPSC ring buffer needs only loads and stores with memory ordering.
friction: The theory assumes an idealised model: atomic objects, arbitrary delays, no memory model issues. Real machines add weak memory ordering (on ARM a CAS may need acquire/release semantics to order other accesses), cache-coherence traffic, and false sharing. A CAS on a highly contended word can cost hundreds of nanoseconds and scales poorly beyond a socket. Wait-free algorithms often use helping, which means that threads do other threads' work and that can waste time under contention.
Memory reclamation is the practical killer of lock-free code. When a node is removed, you cannot free it while another thread may still hold a pointer to it. Hazard pointers, epoch-based reclamation and reference counting each cost something and each have their own failure modes (an epoch scheme is blocked by one stalled thread, which reintroduces blocking). Correctness is also very hard to establish: such algorithms need proofs of linearizability, and published algorithms have contained bugs for years.
practice: In application code, use the library's concurrent types rather than writing CAS loops: `AtomicLong`, `LongAdder`, `ConcurrentHashMap` and `ConcurrentLinkedQueue` in Java; `std::atomic`, and tested queues such as the Disruptor or `crossbeam` in Rust. Use `LongAdder` or per-thread counters for hot counters, because they avoid contention rather than only surviving it. Prefer a single-writer design: one thread owns each piece of mutable state, and others send it messages.
If you must write a lock-free structure, first write the sequential specification, then the CAS loop, think about ABA and reclamation before you start, and test with a stress test and a model checker or a tool such as ThreadSanitizer, Loom (Rust) or `jcstress` (Java). Choose memory orderings deliberately: `acquire` on a load that guards data, `release` on the store that publishes it, `seq_cst` only when you cannot reason about it otherwise. Measure with real core counts; lock-free code that is fast with 4 threads can collapse with 64.

value: Two people who have never met want to talk privately over a network that anyone can read. To encrypt, they need a shared secret key. But how can they agree on a secret if every message between them is public? Before 1976 the only answer was to carry the key in advance by courier, or to share it through a trusted party. That does not scale to a world where your browser must set up a secure session with a server it has never seen before, in a fraction of a second. Diffie–Hellman (DH) key exchange solves exactly this problem: two parties exchange public messages and both end up with the same secret key, which an eavesdropper who saw every message cannot compute.
The mechanism is a one-way street in arithmetic. Fix a public number g and a modulus p. Alice picks a secret number a and sends \( g^a \bmod p \). Bob picks a secret b and sends \( g^b \bmod p \). Alice raises Bob's value to her secret and Bob raises Alice's to his, and both get \( g^{ab} \bmod p \). Computing \( g^a \bmod p \) from a is fast, but recovering a from \( g^a \bmod p \), the discrete logarithm problem, is believed to be very hard for well-chosen groups. An eavesdropper sees g, p and the two public values, but not a or b.
For the layer above, DH is the engine of secure channels. TLS 1.3 (the protocol under HTTPS) uses an ephemeral elliptic-curve DH exchange in every handshake. SSH, WireGuard, Signal and many VPNs do the same. The ephemeral choice gives **forward secrecy**: even if a server's long-term key is stolen later, recorded sessions stay secret. The layers below supply the mathematics. Number theory and modular arithmetic (L4) give the group of integers modulo p and the fast exponentiation algorithm. Finite fields and elliptic curves (L4) give the groups used in modern versions, with much smaller keys for the same security. Public-key cryptography (L3) gives the frame: DH was the first public-key idea, and the other pieces (signatures, authentication) are needed to make it safe.
terms: Public-key cryptography — cryptography in which each party has a public value, shared with everyone, and a private value, kept secret.
Modular exponentiation — computing \( g^x \bmod p \); fast to do even for numbers of thousands of bits.
Discrete logarithm problem (DLP) — given g, p and \( y = g^x \bmod p \), find x; believed to be hard in suitable groups.
Generator (g) — a number whose powers cover a large subgroup of the integers modulo p.
Ephemeral key — a key pair made fresh for one session and then thrown away.
Forward secrecy — the property that stealing long-term keys later does not reveal past session keys.
Man-in-the-middle (MITM) attack — an attacker who sits between the two parties and runs a separate exchange with each.
Key derivation function (KDF) — a function such as HKDF that turns the raw shared secret into one or more uniformly random keys.
history: In the early 1970s secure communication meant shared secret keys, and the "key distribution problem" was the main obstacle for banks and governments. Ralph Merkle, a student at Berkeley, proposed "Merkle puzzles" in 1974: one party sends many weak puzzles, the other solves one at random, and the solved puzzle tells the first party which key was picked. It worked, but the cost grew with the square of the security level.
Whitfield Diffie and Martin Hellman at Stanford found a much better way. Their paper "New Directions in Cryptography" (IEEE Transactions on Information Theory, November 1976) introduced the idea of public-key cryptography and the exponentiation-based key exchange. Merkle is often named with them; the method is also called Diffie–Hellman–Merkle. In 1977 Rivest, Shamir and Adleman added RSA, which gave both encryption and signatures. Diffie and Hellman received the ACM Turing Award in 2015. It later became public that Malcolm Williamson at GCHQ had found the same exchange in 1974, inside secret work that began with James Ellis and Clifford Cocks; this was declassified in 1997.
Practice came with the Internet. SSL (1995) and TLS (1999) had DH modes, but for years most HTTPS sessions used RSA to transport the key, which gives no forward secrecy. Elliptic-curve DH came from Neal Koblitz and Victor Miller (independently, 1985); Daniel Bernstein's Curve25519 (2006) made a fast, safe-by-design curve that became X25519 in RFC 7748 (2016). The 2013 Snowden documents increased the push for forward secrecy, and in 2015 the "Logjam" attack showed that many servers used weak or shared 1024-bit DH primes, and that the older "export-grade" 512-bit mode could be forced by a downgrade. TLS 1.3 (RFC 8446, 2018) removed RSA key transport and static DH, so every full handshake uses ephemeral (EC)DH. Since 2023, because a future quantum computer running Shor's algorithm would break DH, systems have been adding hybrid exchanges: Signal's PQXDH (2023) and the X25519 plus ML-KEM key shares in TLS, deployed by major browsers and CDNs from 2024.
how: Setup. Choose a large prime p and a generator g. The integers modulo p, excluding 0, form a group under multiplication; g generates a subgroup of large prime order q. Everyone can use the same public (p, g). This is where **number theory** matters: the structure of the group, Fermat's little theorem (\( g^{p-1} \equiv 1 \bmod p \)) and the properties of prime-order subgroups decide the security.
The exchange, step by step. Step 1: Alice picks a random secret a from 1 to q − 1 and computes her public value \( A = g^a \bmod p \). Bob picks b and computes \( B = g^b \bmod p \). Step 2: they send A and B over the open channel. Step 3: Alice computes \( s = B^a \bmod p \) and Bob computes \( s = A^b \bmod p \). Both equal \( g^{ab} \bmod p \), because exponents multiply and multiplication is commutative:
\[ (g^b)^a = g^{ab} = (g^a)^b \pmod p \]
Step 4: both feed s into a key derivation function (for example HKDF with SHA-256), together with the transcript of the handshake, to get the actual encryption keys. The raw s is not uniformly random bits, so it should never be used as a key directly.
Computing \( g^a \bmod p \) with a 2,048-bit exponent is done with square-and-multiply, in about 2,000 squarings and up to 2,000 multiplications of 2,048-bit numbers: fast, around a millisecond. The inverse problem, finding a from A, has no known fast algorithm in a well-chosen group. The best attack on integers modulo a prime is the number field sieve, which runs in sub-exponential time. That is why integer DH needs 2,048 bits or more for about 112 bits of security, and 3,072 bits for 128 bits.
Elliptic curves. The same exchange works in any group where exponentiation is easy and discrete logarithms are hard. The **elliptic-curve** version takes the group of points on a curve over a finite field. The "multiplication" of the group is point addition and "g^a" becomes the scalar multiplication \( a \cdot G \), adding the base point G to itself a times (done fast by double-and-add). Alice sends \( A = aG \), Bob sends \( B = bG \), and the shared secret is \( abG \). For well-chosen curves there is no sub-exponential attack: the best known attacks take about \( \sqrt{q} \) steps, so a 256-bit curve gives about 128 bits of security. A 256-bit key replaces a 3,072-bit key, and computing X25519 takes tens of microseconds on a modern core. This is the contribution of **finite fields and elliptic curves**: the same protocol, 12 times smaller keys, and much faster.
Curve details matter. X25519 works on the curve Curve25519 over the field of integers modulo \( 2^{255} - 19 \). The group has a cofactor of 8, meaning a few points lie in small subgroups; the scalar is "clamped" (the low three bits cleared, the top bit set) so the result always lies in the large prime-order subgroup. X25519 also uses only the x-coordinate and a constant-time ladder, so it is hard to implement incorrectly.
What DH does not do: it provides no authentication. If Mallory sits in the middle, she can run one exchange with Alice and another with Bob, read and re-encrypt everything, and neither side knows. DH only guarantees that the key is shared with whoever sent the other public value. **Public-key cryptography** completes the picture with signatures or certificates: in TLS the server signs the handshake transcript, including its DH public value, with the key in its certificate, so the client knows the DH value came from the real server. Signal-like protocols authenticate with long-term identity keys inside X3DH or PQXDH; WireGuard authenticates with pre-shared static public keys inside the Noise framework.
Ephemeral versus static. In ephemeral DH (DHE or ECDHE) each side makes a fresh a or b for every session and deletes it afterward. Even if an attacker records the traffic and later steals the server's certificate key, the session secrets cannot be recomputed, because the ephemeral secrets no longer exist. This is forward secrecy. Static DH reuses a key pair, which loses this property.
Finally, validation. The receiver must check that a received public value is valid: for integer DH that it is in the range 2 to p − 2 and in the right subgroup; for elliptic curves that the point lies on the curve and is not of small order. Skipping these checks allows small-subgroup and invalid-curve attacks that leak bits of the private key.

example: Use the tiny numbers p = 23 and g = 5. Alice chooses a = 6 and Bob chooses b = 15 (kept secret). Alice computes \( A = 5^6 \bmod 23 \). The powers of 5 modulo 23 are 5, 2, 10, 4, 20, 8, so \( 5^6 = 8 \) and A = 8. Bob computes \( B = 5^{15} \bmod 23 = 19 \). They exchange 8 and 19. Alice computes \( 19^6 \bmod 23 \): \( 19^2 = 361 \equiv 16 \), \( 19^4 \equiv 16^2 = 256 \equiv 3 \), \( 19^6 = 19^4 \cdot 19^2 \equiv 3 \cdot 16 = 48 \equiv 2 \). Bob computes \( 8^{15} \bmod 23 = 2 \). Both have the shared secret 2.
Eve knows 23, 5, 8 and 19. To find the secret she must find a with \( 5^a \equiv 8 \bmod 23 \). With such a small modulus she simply lists the powers (5, 2, 10, 4, 20, 8) and finds a = 6, then computes \( 19^6 \equiv 2 \). With a 2,048-bit modulus the list would have about \( 2^{2000} \) entries, and even the sub-exponential sieve algorithm needs far more work than any attacker has. The scale matters: the work to break 1,024-bit DH is within the reach of a very large organisation (the Logjam paper estimated it for a nation state, with a heavy precomputation per prime), but not for 2,048 bits.
Now the man-in-the-middle. Mallory picks m = 3 and computes \( M = 5^3 \bmod 23 = 10 \). She intercepts A = 8 and B = 19 and sends the value 10 to both Alice and Bob. Alice computes \( 10^6 \bmod 23 = 6 \); Bob computes \( 10^{15} \bmod 23 = 5 \). Mallory computes \( 8^3 \bmod 23 = 6 \) (matches Alice) and \( 19^3 \bmod 23 = 5 \) (matches Bob). Alice and Bob each believe they share a key with the other, but they share different keys with Mallory, who reads and re-encrypts everything. Only authentication, such as Bob signing his value, prevents this.
intuition: Mixing paint: each person adds a secret colour to a shared base and sends the mix; adding your own secret colour to the other's mix gives the same final colour, but un-mixing the first step is practically impossible.
The idea is natural because of an asymmetry in arithmetic: some operations are easy to do and very hard to undo. Exponentiation in a modular group is easy to compute and, as far as anyone knows, infeasible to reverse. The order of operations does not matter, \( (g^a)^b = (g^b)^a \), so each side can combine its own secret with the other's public value and arrive at the same result. The public values reveal nothing usable, because getting the secret out of them is the hard problem. Security does not come from hiding the algorithm; it comes from the gap between the work for the parties (milliseconds) and for the attacker (longer than the age of the universe).
mistakes: People often think Diffie–Hellman encrypts data. In fact it only produces a shared secret. The data is then encrypted with a symmetric cipher (AES-GCM or ChaCha20-Poly1305) using keys derived from that secret, which is much faster.
People often think DH protects against active attackers. In fact plain DH is secure only against a passive eavesdropper. Without authentication a man in the middle can impersonate either side. Certificates, signatures or known public keys supply the authentication.
People often think the shared secret can be used directly as a key. In fact it is a group element with structure, not uniformly random bits. It should go through a KDF (HKDF) that also binds the handshake transcript and the context.
People often think a bigger prime is the only thing that matters. In fact the choice of group matters as much. Weak or reused primes (the Logjam finding of a few common 1,024-bit primes), subgroups of small order and unchecked public values all reduce security, which is why standards such as RFC 7919 define vetted groups and why X25519 is designed to resist misuse.
tradeoffs: Choose ECDH on X25519 (or P-256 when a compliance rule requires NIST curves) for almost all new designs: 32-byte public values, about 128-bit security, roughly 50 microseconds per operation, and a design that is hard to misuse. Choose finite-field DH (the RFC 7919 groups, 2048 bits at minimum) only for compatibility with old systems; you pay about 12 times larger messages and much slower computation. Choose a hybrid X25519 plus ML-KEM key exchange now for data that must stay secret for 10 years or more, since an adversary can record traffic today and decrypt it when a quantum computer exists; you pay about 1 KB more per handshake and a little CPU, and you rely on both algorithms: it stays safe if either one is not broken.
Choose ephemeral keys (ECDHE) wherever you can: it costs one extra scalar multiplication per handshake and gives forward secrecy. Choose static DH or a long-term key only for very restricted cases such as non-interactive encryption to a recipient (where an ephemeral key on the sender's side is combined with the recipient's static key, as in HPKE) or when a protocol cannot do a round trip. Choose a full authenticated protocol (TLS 1.3, Noise, Signal's X3DH) rather than building one from DH yourself: the hard part is not the exchange but authentication, key derivation, replay and downgrade protection.
friction: DH is not secure by itself, and most failures come from the way it is used, not from the mathematics. Missing authentication, no validation of received values, reuse of random numbers, small or shared groups, and implementations that leak the secret through timing have all caused real breaks. The random number generator for the secret a matters as much as the maths: a predictable a makes the shared secret predictable.
The quantum threat is the large open issue. A cryptographically relevant quantum computer does not exist today, but traffic recorded now could be decrypted later ("harvest now, decrypt later"), so migration to post-quantum or hybrid exchanges is under way and carries costs: bigger handshakes (about 2.3 KB of key shares in total for the ML-KEM-768 hybrid), compatibility problems with middleboxes that choke on large ClientHello messages, and less experience with the new algorithms than with a 20-year-old curve.
practice: Do not write your own key exchange. Use TLS 1.3 for client–server traffic, SSH or WireGuard for tunnels, and a library with a high-level interface (libsodium `crypto_kx` or `crypto_box`, Go `crypto/ecdh`, Java `KeyAgreement` with X25519, Python `cryptography` library's `X25519PrivateKey`) for other cases. Always derive keys with HKDF from the shared secret and the transcript, never use the raw value, and use a different key for each direction.
When you configure servers, disable TLS 1.0 to 1.2 cipher suites that use plain RSA key transport or static DH; prefer ECDHE with X25519 or P-256, and enable the hybrid post-quantum groups if your TLS library supports them. Use certificates from a trusted CA, or pin the peer's public key when you control both sides, so that the exchange is authenticated. Generate secrets from the operating system's CSPRNG, and never reuse an ephemeral key. To check a server, `openssl s_client -connect host:443` shows the negotiated group (for example X25519), and tools like `testssl.sh` or SSL Labs flag weak groups. For learning, implement the p = 23 toy example and then X25519 on top of a bignum library, and read RFC 7748 for the details.
interview: Why is plain Diffie–Hellman vulnerable to a man-in-the-middle attack, and how does TLS fix it? || DH gives a shared key with whoever sent the other value, but does not say who that is. An active attacker can run separate exchanges with both sides. In TLS 1.3 the server signs the handshake transcript (including its DH value) with the private key of its certificate, and the client verifies the signature against a trusted CA chain, so the DH value is tied to the server's identity.
What is forward secrecy and why does ephemeral DH give it, but RSA key transport does not? || With RSA transport, the client encrypts the session key under the server's long-term key; stealing that key later decrypts all recorded sessions. With ephemeral DH the session secret comes from random values that are deleted after the handshake, so a later key theft reveals nothing about past sessions.
Why are elliptic-curve keys so much smaller than finite-field DH keys for the same security? || The best attack on integer discrete logarithm (number field sieve) is sub-exponential, so the modulus must be large (3,072 bits for 128-bit security). For well-chosen elliptic curves only generic attacks work, which take about the square root of the group size, so 256 bits are enough.
What could go wrong if the receiver does not validate the peer's public value? || In finite-field DH, a value of 1, p − 1 or an element of a small subgroup forces the shared secret into a tiny set. On curves, a point of small order or on a different curve (invalid-curve attack) can leak the private key bit by bit through repeated handshakes. Receivers must check range, subgroup or on-curve conditions; X25519 handles most via clamping.
How would you prepare a TLS service for quantum computers without waiting for standards to settle? || Enable the hybrid group X25519MLKEM768 so that the session key depends on both X25519 and ML-KEM, test with clients and middleboxes for large ClientHello problems, and keep classical groups as fallback. Authentication (certificates) can follow later, because it only needs to be secure at the time of the handshake.
quiz: Write the two computations that give both parties the same secret in Diffie–Hellman. || Alice computes (g^b)^a mod p and Bob computes (g^a)^b mod p. Both equal g^(ab) mod p.

Why must the shared secret go through a KDF? || It is a group element, not uniformly random bits, and may have structure. A KDF such as HKDF turns it, with the handshake transcript as context, into independent uniformly random keys for each purpose and direction.
Why does TLS 1.3 only allow ephemeral key exchange? || Ephemeral (EC)DH gives forward secrecy: session keys cannot be recovered from a stolen long-term key. TLS 1.3 therefore removed RSA key transport and static DH.
You need confidentiality for medical records that must stay secret for 25 years. What do you add to X25519? || A post-quantum KEM in a hybrid exchange (for example X25519 plus ML-KEM-768), because an adversary can record traffic now and decrypt it later when a quantum computer can run Shor's algorithm; the hybrid stays secure if either component holds.

@@ fuzzing
value: Most bugs are found by the inputs that the author did not think of. A programmer writes tests for the cases in their head: a normal file, an empty file, a file with one obvious error. The bugs that become security holes live elsewhere: a length field that is too large, a string that contains a zero byte in the middle, a nesting depth of 10,000, two flags that are never set together in practice. Fuzzing attacks this gap with brute force. It generates a huge number of unusual inputs, runs the program on each one, and watches for a crash, a hang, a memory error or a broken rule. Property-based testing is the same idea with a different aim: instead of looking for crashes only, you state a rule that must always hold ("decoding an encoded value gives back the original") and the tool searches for an input that breaks it.
Two ideas turn this from a lottery into an effective method. The first is **feedback**: a modern fuzzer measures which parts of the code each input reached, keeps the inputs that reached something new, and mutates them to go further. This lets it discover, step by step, inputs that pass a checksum, a magic header or a parser stage that random bytes would never pass. The second is **shrinking**: when a random test fails, the failing input is often large and confusing, so the tool repeatedly simplifies it while it still fails, ending with a small case you can read, such as a list with one element.
For the layer above, fuzzing is now a standard part of how serious software is built and secured. Google's OSS-Fuzz runs fuzzers continuously on open-source projects and has found many thousands of bugs, including well over ten thousand security vulnerabilities. Browsers, kernels, compilers, image libraries and cryptography libraries are fuzzed all the time. Continuous integration runs property tests on every commit. Deterministic simulation testing of distributed systems is fuzzing of fault schedules. The layers below supply the ingredients: pseudorandom generators (L3) produce the inputs from a seed so that every failure can be replayed, finite automata (L3) describe the coverage graph and the grammars that structure-aware generators follow, and logic (L4) is the language in which a property, a statement of the form "for all inputs x, P(x) holds", is written.
terms: Fuzzing — running a program on automatically generated or mutated inputs to find crashes and other failures.
Coverage-guided fuzzing — fuzzing that uses code-coverage feedback to decide which inputs to keep and mutate.
Corpus — the set of interesting inputs the fuzzer has saved; it is the fuzzer's memory.
Mutation — a small random change to an existing input, such as flipping a bit, changing a byte or splicing two inputs.
Oracle — the check that decides whether a run is a failure: a crash, a sanitizer report, a failed assertion or a violated property.
Property-based testing — testing by stating a rule that must hold for all inputs and letting a tool generate many inputs to look for a violation.
Shrinking — automatically reducing a failing input to a simpler one that still fails.
Sanitizer — a compiler-inserted check (such as AddressSanitizer) that turns silent memory errors into immediate crashes with a report.
history: In the autumn of 1988, Barton Miller, a professor at the University of Wisconsin, was logged into a Unix machine over a dial-up line during a thunderstorm. Line noise put random characters into his commands, and programs crashed. He asked a class to write a tool that sends random input to Unix utilities. The result, the 1990 paper "An Empirical Study of the Reliability of UNIX Utilities" (Miller, Fredriksen and So), reported that roughly a quarter to a third of the tested utilities crashed or hung. The word "fuzz" came from that project. The studies were repeated in 1995 and later for Windows and macOS, with similar results.
Property-based testing grew separately in functional programming. Koen Claessen and John Hughes published QuickCheck for Haskell in 2000 (ICFP): you write properties as functions, and the library generates random inputs and, later, shrinks counterexamples. Versions followed in Erlang, Scala, Python (Hypothesis, by David MacIver, from 2013), Rust, Java and many more languages. Kyle Kingsbury's Jepsen (2013 onward) applies the same idea to distributed databases, running random operations while injecting network partitions and checking the history for consistency violations.
The big change in fuzzing came with feedback. Michał Zalewski's American Fuzzy Lop (AFL, released around 2013 to 2014) instrumented programs to record the branches they take, and used a genetic-style loop to grow a corpus. It found bugs in nearly every popular parser it touched. LLVM's libFuzzer (about 2015) runs the fuzzer inside the process for speed, and honggfuzz, Google's syzkaller (for the Linux kernel, 2015) and AFL++ (a community fork, published in 2020) followed. OSS-Fuzz launched in December 2016 to run these tools at scale for open source. Research added symbolic and concolic execution (KLEE, SAGE), grammar-based and structure-aware fuzzing, and, more recently, language models that write fuzz targets.
how: Start with the simplest version: blind (black-box) fuzzing. Generate random bytes, feed them to the program, and look for a crash. This finds shallow bugs quickly, but it has a deep weakness. Real programs check their input in stages: first a magic number, then a header, then a checksum, then the body. Random bytes fail at the first stage almost every time, so the code behind it is never tested. If the program starts with a four-byte magic number, a blind fuzzer needs about \( 256^4 \approx 4.3 \) billion tries on average to pass that one check.
Coverage-guided fuzzing fixes this with feedback. The compiler inserts a small piece of code at every branch (edge between basic blocks). Each run updates a shared bitmap (64 KiB in AFL) that records which edges were taken and roughly how many times. The fuzzer keeps a queue of inputs. It repeats a loop: pick an input from the queue, mutate it, run the program, and look at the bitmap. If the run took an edge never seen before, the mutated input is new and interesting, so it is added to the queue. If not, it is thrown away. The queue is thus a growing set of inputs that together reach more and more of the program. Now the four-byte magic number takes only about \( 4 \times 128 = 512 \) tries on average, because each correct byte opens a new edge and is saved, and the next byte is searched separately.
Mutations are cheap and varied: flip single bits, flip bytes, add or subtract small numbers, replace bytes with "interesting values" (0, 1, 255, 65535, \( 2^{31}-1 \), −1, which tend to trigger overflow bugs), delete or duplicate blocks, insert dictionary tokens (keywords of the format), and splice two queue entries together. All of this depends on **pseudorandom generators**: the fuzzer is driven by a seeded generator, which makes runs reproducible, and every failing input is saved as a file so you can replay it exactly. Speed is essential. A fuzzer that forks the process once per input reaches thousands of executions per second per core; in-process fuzzers (libFuzzer) reach tens of thousands to hundreds of thousands, because they avoid process creation and call the target function in a loop.
The oracle decides what counts as a bug. A plain crash (segmentation fault) is the easiest. But many memory errors do not crash: reading one byte past a buffer usually succeeds silently. Sanitizers solve this: AddressSanitizer adds checks around every allocation and every memory access, so an out-of-bounds read or a use-after-free aborts at once; UndefinedBehaviorSanitizer catches integer overflow and similar; MemorySanitizer finds reads of uninitialised memory. A fuzz target can also contain assertions or compare two implementations (differential fuzzing: a new parser against an old one, or compression followed by decompression must give the original). The more precise the oracle, the more bugs found.
Structure matters for inputs that have a grammar. A byte mutator will break a JSON or SQL input into garbage most of the time, so the parser rejects it early. **Finite automata** and grammars help here: a grammar-based fuzzer generates inputs by walking a grammar, so every input is syntactically valid and reaches the deeper logic; coverage itself can be seen as visiting edges of the program's control-flow graph, which is an automaton over execution. Structure-aware tools (libprotobuf-mutator, Grammarinator) mutate the parsed tree and then serialise it.
Property-based testing uses the same machinery with a richer oracle, and this is where **logic** enters. A property is a universally quantified statement, \( \forall x.\; P(x) \), for example "for all lists xs, `sort(xs)` is ordered and has the same elements as xs". The tool has generators for types (integers, lists, records, trees), which can be combined and filtered, and it runs the property on hundreds or thousands of generated values. If a value falsifies it, the tool shrinks: it tries smaller candidates (shorter lists, smaller numbers, simpler structures) and keeps any that still fail, until no simplification works. A 500-element failing list typically shrinks to one or two elements. Stateful testing extends this to sequences of operations on a system, compared with a simple model. Hypothesis also remembers failing examples in a database so they are replayed first.
Typical properties are: a round trip (`decode(encode(x)) == x`), an invariant (the balance is never negative), idempotence (`normalize(normalize(x)) == normalize(x)`), equivalence to a simple model (the fast implementation matches the slow obvious one), and "does not crash".

example: The first example is coverage guidance on a tiny program.
```c
int parse(const unsigned char *d, int n) {
    if (n < 4) return 0;
    if (d[0] != 'F') return 0;
    if (d[1] != 'U') return 0;
    if (d[2] != 'Z') return 0;
    if (d[3] == 'Z') abort();     /* the bug */
    return 1;
}
```
A blind fuzzer must produce the four bytes "FUZZ" at once: about \( 256^4 \approx 4.3 \times 10^9 \) tries. At 100,000 executions per second this is about 12 hours. A coverage-guided fuzzer starts from the empty or random input. After a few hundred tries it produces an input whose first byte is 'F'; this reaches a new edge (the second `if`), so it is saved. Mutating that input finds 'U' as the second byte after about 256 tries, again saved. The same for 'Z' and then the final 'Z'. The total is about \( 4 \times 256 \approx 1000 \) executions, and the crash is found in well under a second. The numbers show the idea: feedback turns a product of probabilities into a sum.
The second example is a property test in Python with Hypothesis. A developer writes a function that merges two sorted lists and has a subtle bug.
```python
from hypothesis import given, strategies as st

def merge(a, b):
    out, i, j = [], 0, 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    return out + a[i:]            # bug: forgets b[j:]

@given(st.lists(st.integers()), st.lists(st.integers()))
def test_merge(a, b):
    a, b = sorted(a), sorted(b)
    assert merge(a, b) == sorted(a + b)
```
Hand-written examples where the first list holds the largest value, such as `merge([5, 6], [1, 2])`, pass, because then the leftover is in `a`. Hypothesis finds a failing case within a few dozen generated examples and shrinks it to the smallest possible failure: `a = []`, `b = [0]` (we ran this example with Hypothesis 6 and it reports exactly this). That tiny counterexample points straight to the cause: when `a` runs out first, the remainder of `b` is dropped. The fix is `return out + a[i:] + b[j:]`.
intuition: A tireless intern who tries every odd thing on your program and keeps a notebook of the tries that opened a new door; a property test asks the intern to also report the shortest way to reproduce each failure.
Fuzzing works because bugs hide in rare corners of the input space, and a machine can visit rare corners at a rate no human can. Feedback makes the visiting efficient: instead of searching a huge space blindly, the fuzzer searches in small steps, each guided by a measurable sign of progress (a new branch). Shrinking works for a human reason: a bug is understood from a small example, so the tool should always end with the smallest one. And properties work because they separate "what must be true" from "which examples we thought of".
mistakes: People often think fuzzing is random testing and so finds only shallow bugs. In fact coverage guidance, dictionaries, grammars and sanitizers let modern fuzzers reach deep states; they have found bugs in code that was well reviewed and well tested for years.
People often think that if a fuzzer runs for a long time without finding anything, the code is safe. In fact fuzzing can show the presence of bugs, not their absence. Coverage plateaus, and a bug behind a rare condition (a specific checksum, a long sequence of state changes) may stay out of reach. Treat the coverage report as the measure of what was tested.
People often think a fuzzer only finds crashes. In fact it finds whatever the oracle can detect. With sanitizers it finds silent memory errors, with assertions it finds logic errors, and with differential or round-trip checks it finds wrong answers. Without an oracle, a fuzzer cannot see a bug that does not crash.
tradeoffs: Choose coverage-guided fuzzing for code that parses untrusted input and is written in a memory-unsafe language: image and video decoders, network protocols, file formats, compilers. You pay for writing a fuzz target (a function that takes bytes) and for CPU time, which is cheap compared with a security incident. Choose property-based testing for logic with clear rules: serialisation, data structures, parsers with round trips, business invariants, and algorithms with a simple model. You pay for the effort to write good generators and properties, and for flaky-looking failures that need seeds to replay.
Choose grammar-aware or structure-aware fuzzing when inputs have a strict syntax (SQL, JSON, protobuf, programming languages) and plain mutation spends most of its time on rejected inputs; you pay for the grammar or the mutator. Choose a plain byte mutator with a seed corpus and a dictionary when the format is binary and loose. Choose long-running continuous fuzzing (OSS-Fuzz style) for libraries that many people depend on, and a short time-boxed fuzz run (a minute or two) in CI as a regression check for ordinary services.
friction: The main difficulty is the oracle and the setup, not the engine. A fuzz target needs to be deterministic, fast and stateless: no network, no clock, no global state that leaks between runs, or the fuzzer cannot reproduce or learn from a run. Hard stages (checksums, encryption, compressed data) block progress unless you disable them in a fuzzing build or give the fuzzer a way past. Large programs need many targets and a well-chosen seed corpus.
Triage is also a real cost. A fuzzer can produce thousands of crashes that are really a handful of bugs, so deduplication by stack trace and bucketing are needed, and the findings still need a human to judge severity. Flaky failures from concurrency or timing are hard to replay. For property-based testing, writing generators that produce realistic, valid data (a consistent set of related records) is difficult, and the value of the test depends entirely on how well the generator covers interesting cases.
practice: Start with the code that parses untrusted input. Write a fuzz target of ten lines (in libFuzzer: `int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)`; in Go `go test -fuzz`; in Rust `cargo fuzz`; in Python or Java Atheris or Jazzer), build it with sanitizers, give it a seed corpus of a few real files and a dictionary of format keywords, and run it on a spare core for a day. Save the corpus, run it as a regression test on every commit, and register the project with OSS-Fuzz if it is open source.
For logic, add property tests with Hypothesis, QuickCheck, jqwik, fast-check or `proptest`. Begin with round trips, invariants and comparison with a slow, obviously correct model. Keep the generators small and shaped like real data, log the seed on failure, and keep failing examples as plain regression tests. In data engineering, properties are a good fit for transformations: "the output row count equals the input count after the dedupe key is applied", "re-running a job gives the same output (idempotence)", "the total of the parts equals the total of the whole". For distributed systems, use fault-injection and simulation (Jepsen, deterministic simulation) that generate random schedules of operations and failures.
interview: Why does coverage guidance find bugs that blind random testing cannot? || Programs check input in stages. Blind testing must satisfy all stages at once, so its chance is the product of the stage probabilities. With coverage feedback, passing one stage is detected as a new edge and the input is saved, so the next stage is searched separately: the cost becomes a sum, not a product.
What is shrinking and why does it matter? || After a failure, the tool tries simpler variants of the input (shorter, smaller, simpler) and keeps those that still fail until it reaches a minimal case. A 3-element counterexample is readable and points to the cause; a random 5,000-element one is not. Integrated shrinking in Hypothesis works on the generation choices, so shrunk values still respect the constraints.
You have a fast new JSON parser and a slow trusted one. How would you test the new one? || Differential fuzzing and a property: for any input bytes, both parsers accept or reject the same inputs and produce the same tree. Use a structure-aware generator (valid JSON with mutations) plus raw bytes, run with sanitizers, and keep the corpus. Known deliberate differences must be listed as exceptions.
Your fuzzer stopped finding new coverage after two days. What do you do? || Check the coverage report for blocked stages (checksums, magic values, compressed or encrypted data) and fix the target or disable them in a fuzzing build; add seeds and a dictionary; make the generator structure-aware; split a big target into smaller ones; or use a directed or symbolic approach for the stuck branches.
quiz: What is the role of the coverage bitmap in a coverage-guided fuzzer? || It records which program edges a run took. If a mutated input took an edge not seen before, it is added to the corpus so future mutations start from it.
Why do sanitizers matter for fuzzing C and C++ programs? || Many memory errors (out-of-bounds read, use after free) do not crash, so a plain fuzzer cannot see them. AddressSanitizer and similar tools make them abort with a report, turning silent bugs into findable ones.
A program checks a 4-byte magic value. Roughly how many tries does a blind fuzzer need on average, and how many does a coverage-guided one? || Blind: about 256^4 ≈ 4.3 billion. Coverage-guided: about 4 × 128 ≈ 500 to 1,000 because each correct byte opens a new edge and is saved.
Name three useful kinds of property for property-based tests. || Round trip (decode(encode(x)) == x), idempotence (f(f(x)) == f(x)), and agreement with a simple model; also invariants such as "balance never negative" or "output is sorted and a permutation of the input".
When would you choose formal verification over fuzzing? || When a single bug is unacceptable and the code is small and critical, such as a cryptographic primitive, a kernel component or a protocol core. Fuzzing gives evidence of the absence of bugs it can reach, and a proof gives a guarantee, at a much higher effort.

@@ hoare
value: A test shows that a program works on the inputs you tried. A proof shows that it works on all inputs. Hoare logic is the simplest way to turn a program into something that can be proved. You write down what must be true before a piece of code runs (the precondition) and what the code guarantees afterward (the postcondition), and you use a small set of rules, one per kind of statement, to check that the code really moves from one to the other. The result is written as a triple \( \{P\}\; C\; \{Q\} \): if P holds before command C runs, and C finishes, then Q holds afterward.
The hardest part of a proof is loops, because a loop may run a million times and you cannot follow each step. Hoare logic handles this with a **loop invariant**: a statement that is true before the loop, stays true after every pass through the body, and so is still true when the loop exits. Together with the exit condition it gives the postcondition. Finding the right invariant is the same skill as finding the right induction hypothesis in a mathematical proof, and it is also the best way to understand what a loop is for.
For the layer above, this is the basis of formal verification tools. Dafny, Why3, SPARK Ada, Frama-C and Verus for Rust let you write preconditions, postconditions and invariants next to the code. The tool turns them into logical formulas, called verification conditions, and hands them to an SMT solver that proves them or finds a counterexample. The layers below give the parts. Logic (L4) provides the language of assertions: propositional and first-order formulas with quantifiers. Proofs and induction (L4) provide the pattern of loop invariants. Formal semantics (L4) explains what the rules mean: Hoare's rules are an axiomatic semantics, a definition of a language through what can be proved about its programs. SAT and SMT solvers (L3) do the heavy lifting of checking the generated formulas automatically.
terms: Precondition — a condition that must hold when a piece of code starts; the caller promises it.
Postcondition — a condition that the code guarantees when it finishes, if the precondition held.
Hoare triple — the statement {P} C {Q}: if P holds before C and C terminates, then Q holds afterward.
Loop invariant — a condition that holds before a loop, is preserved by each iteration of the body, and therefore holds after the loop ends.
Weakest precondition — for a command C and a postcondition Q, the most general condition wp(C, Q) that guarantees Q after C.
Verification condition — a logical formula, generated from the annotated program, that must be proved valid for the program to be correct.
Partial and total correctness — partial correctness says the postcondition holds if the code terminates; total correctness also proves termination.
Variant (ranking function) — a quantity, such as the number of remaining items, that is a non-negative integer and strictly decreases with every loop pass, so the loop must stop.
history: The idea that programs can be proved correct is from the 1960s, when software errors were already costly. Robert Floyd's 1967 paper "Assigning Meanings to Programs" attached assertions to the edges of a flowchart and showed how to prove that a flowchart satisfies them. In October 1969, Tony Hoare published "An Axiomatic Basis for Computer Programming" in Communications of the ACM, which turned Floyd's idea into a logic for program text: axioms and inference rules for assignment, sequence, conditional and while-loops. The notation {P} C {Q} is named after him. 
Edsger Dijkstra took the idea in a constructive direction. In 1975 and 1976 he introduced weakest preconditions and "predicate transformers", so that the postcondition drives the design of the program: you derive the code from what it must achieve. His book "A Discipline of Programming" (1976) showed programs developed together with their proofs. David Gries's "The Science of Programming" (1981) taught this to a generation of students. In the 1980s and 1990s, the work extended to pointers and heap memory: John Reynolds, Peter O'Hearn and others developed separation logic (around 2000 to 2002), which can state that two pieces of memory are disjoint and so lets proofs about one data structure ignore the rest.
Automation made it practical. SMT solvers such as Simplify, Z3 (2008) and CVC went from research tools to engines that could check thousands of verification conditions in seconds. Tools followed: Spec# and then Dafny (K. Rustan M. Leino, Microsoft Research, from about 2008), Why3 (Inria), SPARK Ada for safety-critical software, Frama-C with ACSL annotations for C, and Verus (2023) for Rust. Large verified systems showed that the approach scales to real software: the seL4 microkernel proof of functional correctness (2009), the CompCert verified C compiler (Xavier Leroy), and verified components inside industrial systems.
how: Begin with the triple. \( \{P\}\; C\; \{Q\} \) says: start in any state satisfying P, run C, and if C terminates, the final state satisfies Q. Hoare's rules say how to prove such a triple for each kind of statement. The proof has the same shape as the program, which is why the method is called compositional: you prove each part, then combine.
Assignment. The assignment axiom works backward: \( \{Q[E/x]\}\; x := E\; \{Q\} \). To know that Q holds for x after the assignment, Q must hold for E before it, so replace x by E in Q. Example: to get \( x > 5 \) after `x := x + 1`, you need \( x + 1 > 5 \) before, which is \( x > 4 \). This backward rule is the reason Dijkstra's weakest precondition style is natural: wp(x := E, Q) is exactly Q with E substituted for x.
Sequence. If \( \{P\}\; C_1\; \{R\} \) and \( \{R\}\; C_2\; \{Q\} \) hold, then \( \{P\}\; C_1; C_2\; \{Q\} \) holds. The middle assertion R is the glue. Working backward, you start from Q, compute the weakest precondition of the last statement, then of the one before, and so on.
Conditional. For `if B then C1 else C2`, prove \( \{P \wedge B\}\; C_1\; \{Q\} \) and \( \{P \wedge \neg B\}\; C_2\; \{Q\} \). Each branch gets the knowledge of which way the test went.
Consequence. If \( P' \Rightarrow P \), \( \{P\}\; C\; \{Q\} \) and \( Q \Rightarrow Q' \), then \( \{P'\}\; C\; \{Q'\} \). You may always strengthen the precondition and weaken the postcondition. This is the rule that connects the program proof to ordinary mathematics: the implications \( P' \Rightarrow P \) are plain logic facts that need proof, and this is where **logic** is used.
While loop. The central rule is
\[ \frac{\{I \wedge B\}\; C\; \{I\}}{\{I\}\;\textbf{while } B \textbf{ do } C\;\{I \wedge \neg B\}} \]
If the body C preserves the invariant I whenever the loop test B is true, then after the loop, the invariant still holds and the test is false. This is **induction**: the base case is that I holds on entry, the step is that one pass preserves I, and the conclusion holds after any number of passes. Choosing I is the creative step. A good invariant says what the loop has done so far, and it becomes the postcondition when the loop condition fails. For total correctness you add a variant: an integer expression V with \( V \ge 0 \) when I holds and V strictly decreasing in each pass; then the loop cannot run forever.
From proof rules to tools. A verifier does not ask you to write every intermediate assertion. You write the contract (pre- and postconditions) of each function and the invariant of each loop. The tool then works backward, computing weakest preconditions through the straight-line code, and produces verification conditions of the form "the stated precondition implies the computed weakest precondition", with quantifiers over array elements and so on. These formulas go to an **SMT solver** (Z3 is the most widely used), which decides them automatically for many theories: linear arithmetic, bit-vectors, arrays, uninterpreted functions. If it proves the formula, the code meets its contract. If not, it often returns a counterexample, an input that shows the failure, or it times out. The solver needs only the contract of a called function, not its body, so large programs are verified function by function.
What the rules mean. They are an **axiomatic semantics**: they define a command by what can be proved about it. They are justified by comparing them with an operational semantics, which defines how states change when the program runs; the rules are sound if every provable triple is true for every execution. Soundness is proved once for the logic, so individual program proofs can trust it.
Pointers need more. With aliasing, an assignment through one pointer may change what another pointer sees, and plain Hoare logic breaks down. Separation logic adds the connective \( P * Q \), meaning P and Q describe disjoint parts of memory, and a frame rule that lets a proof ignore the memory a command does not touch. Rust verifiers such as Verus and Creusot use the language's ownership rules to reduce this burden.

example: Prove that this program computes the sum \( 0 + 1 + \dots + (n-1) = n(n-1)/2 \).
```text
{ n >= 0 }
s := 0; i := 0;
while i < n do
    s := s + i;
    i := i + 1
{ s = n(n-1)/2 }
```
Step 1: choose the invariant. After i passes, s holds the sum of 0 to i − 1, which is i(i − 1)/2. So \( I \equiv (s = i(i-1)/2) \wedge (0 \le i \le n) \). Step 2: initialisation. Before the loop, `s := 0; i := 0` gives s = 0 and i = 0. Check I: 0 = 0·(−1)/2 = 0, and 0 ≤ 0 ≤ n holds because n ≥ 0. Good. Step 3: preservation. Assume I and the test i < n. The body is `s := s + i; i := i + 1`. Work backward from I with the assignment rule. Replace i by i + 1 in I: \( s = (i+1)i/2 \) and \( 0 \le i+1 \le n \). Then replace s by s + i: \( s + i = (i+1)i/2 \). Now check that I and i < n imply this. From \( s = i(i-1)/2 \), we get \( s + i = i(i-1)/2 + i = (i^2 - i + 2i)/2 = i(i+1)/2 \). Correct. And \( 0 \le i < n \) gives \( 0 \le i + 1 \le n \). Good. Step 4: exit. On exit, I holds and the test is false, so \( i \ge n \). With \( i \le n \) from I we get \( i = n \), so \( s = n(n-1)/2 \). That is the postcondition. Step 5: termination. The variant \( n - i \) is at least 0 under I and drops by 1 each pass, so the loop ends after exactly n passes.
In Dafny, the same proof is written as annotations on the code, and the tool checks it in a fraction of a second.
```text
method SumTo(n: int) returns (s: int)
  requires n >= 0
  ensures 2 * s == n * (n - 1)
{
  s := 0;
  var i := 0;
  while i < n
    invariant 0 <= i <= n
    invariant 2 * s == i * (i - 1)
    decreases n - i
  {
    s := s + i;
    i := i + 1;
  }
}
```
Here is a case where a proof revealed a real surprise. Binary search was proved correct by hand in Jon Bentley's "Programming Pearls" (1986) and appeared in textbooks. The midpoint was computed as `(low + high) / 2`. The proofs assume mathematical integers. With 32-bit integers, `low + high` overflows for arrays larger than \( 2^{30} \) elements, giving a negative index. Joshua Bloch described this in 2006 as a bug found in the Java library. A verifier that models machine integers (bit-vectors or bounded ranges) flags it at once: the precondition `low + high <= INT_MAX` cannot be proved. The fix is `low + (high - low) / 2`. The lesson is that a proof is only about the model: it is valuable exactly as far as the model of integers, memory and time matches the machine.
intuition: A bridge inspector does not drive every possible truck over the bridge; she proves that every beam carries its load and that the loads add up.
The method is natural because a program is a chain of small steps, and a proof of a chain needs only a statement at each link: what is true here, and why the next step keeps it true. A loop is a chain of unknown length, so we need one statement that survives every link, the invariant. If you can state what remains true during a loop, you have understood the loop. That is why even people who never use a verifier find invariants useful: they turn "I think it works" into a claim that can be checked line by line, in a code review or by a machine.
mistakes: People often think Hoare logic proves that a program is correct. In fact it proves that the program meets a specification. If the specification is wrong or incomplete (a sort that returns a sorted list of the wrong elements), the proof is useless. Writing a good specification is often harder than writing the code.
People often think a verified program cannot have bugs. In fact verification covers the properties you stated, on the model you assumed. Integer overflow, a compiler bug, hardware faults, or a missing property can still cause failures. The seL4 team is explicit about what its proof assumes about the compiler and hardware.
People often think partial correctness is enough. In fact `while true do skip` satisfies every postcondition, because it never terminates, so the triple says nothing. Total correctness requires a variant. For services that must respond, termination matters.
tradeoffs: Choose testing and fuzzing for most software: you get good evidence for little effort, and bugs in the specification are found by running things. Choose deductive verification (Dafny, SPARK, Verus, Frama-C) for small, critical, stable components where a bug is very costly and the specification is crisp: cryptographic primitives, allocators, parsers of untrusted input, consensus cores, safety kernels. You pay with a large effort; for seL4 the proof is roughly 20 lines for each line of C, and engineers need training.
Choose lightweight formal methods (types, refinement types, assertions checked at run time, bounded model checking) when you want part of the guarantee at a small cost; they prove less but are cheap. Choose model checking (TLA+, Alloy) when the risk is in the design of a concurrent or distributed protocol rather than in the code. Choose interactive proof assistants (Coq/Rocq, Isabelle, Lean) when your property is beyond what SMT can decide automatically and you need the strongest guarantee, at the price of expert effort.
friction: The main cost is human effort and proof maintenance. Specifications are as large as code and must be updated when the code changes. Automated proofs can be brittle: a small change in the code or the solver version can make a proof that worked time out, because SMT solvers rely on heuristics for quantifiers. Projects measure proof stability, and developers add hints, lemmas and triggers to guide the solver.
There is also a gap between the verified model and the running system. Real languages have undefined behaviour and wrapping integers, so a verifier must model them exactly, and the verifier, solver, compiler and hardware remain in the trusted base. Even so, verified components now ship in browsers, cloud systems and aircraft; engineers at Amazon have described using Dafny to verify parts of their authorization logic.
Some programs are hard to specify at all: user interfaces, machine-learning components, floating-point numerics, and anything whose correctness is a matter of taste. Concurrency adds interleavings, which need more machinery (rely-guarantee, concurrent separation logic, Iris). The trusted base is also real: the verifier, the solver, the compiler, the operating system and the hardware are assumed correct.
practice: You do not need a verifier to benefit. Write the precondition and postcondition of every non-trivial function as comments or assertions. For every loop, write down the invariant in one line before you write the body, and check it in three places: it holds on entry, the body preserves it, and with the exit condition it gives the result. Use `assert` in code to check invariants in tests, and add a variant when termination is not obvious. In code review, ask for the invariant of each tricky loop.
To try verification, start with Dafny: install it, write `SumTo` as above, then verify a binary search, a sorting routine and a small data structure such as a stack with a ring buffer. Read verification errors carefully: they usually name the failing assertion, and the fix is a missing invariant. For Rust, try Verus or Creusot; for C, Frama-C/WP with ACSL; for safety-critical Ada, SPARK. Keep specifications small and stable, prove properties that matter (no out-of-bounds access, no overflow, functional correctness of key functions), and use tests and fuzzing for the rest. In data engineering, think of invariants for pipelines: "every input row ends in exactly one output partition", "the sum of the parts equals the total", and check them at run time.
interview: What is a loop invariant and how do you find one? || A condition that holds before the loop, is preserved by each iteration, and with the negated loop test implies the postcondition. Why does the assignment rule work backward? || To guarantee Q after `x := E`, Q must hold of the value E before, so the precondition is Q with E substituted for x. Working backward from the postcondition gives a mechanical way to compute weakest preconditions without guessing intermediate states.
What is the difference between partial and total correctness and how do you prove termination? || Partial correctness: if the program terminates the postcondition holds. Total correctness also shows termination. You pick a variant, an integer expression that is non-negative and strictly decreases each iteration (or each recursive call), such as n − i; Dafny checks it with `decreases`.
How does a tool like Dafny use an SMT solver? || It converts the annotated program into verification conditions using weakest preconditions and sends each to Z3. If the formula is valid, the assertion holds; if not, the solver returns a counterexample or times out. Loop invariants and function contracts cut the program into pieces that the solver can reason about independently.

@@ lexing
value: A compiler, an interpreter, a SQL engine and a JSON parser all begin with a stream of characters: `if (count >= 10) { return "done"; }`. Before any grammar can be applied, this text must be cut into the pieces that mean something: the keyword `if`, the parenthesis, the identifier `count`, the operator `>=` (one symbol, not two), the number `10`, and the string `"done"`. Each piece is a **token**. Lexical analysis, also called lexing or scanning, is the first phase of language processing: it reads characters and produces tokens, throwing away whitespace and comments on the way.
The reason to make this a separate phase is simplicity and speed. Tokens have a simple structure, a regular one: an identifier is a letter followed by letters and digits, a number is a run of digits, an operator is a fixed string. Such patterns can be written as regular expressions and recognised by a finite automaton that reads each character once and keeps only a small state. That makes lexing fast, often hundreds of megabytes per second, and it relieves the parser (the next phase) from dealing with characters, spaces and comments. The parser then works on a few dozen kinds of tokens instead of thousands of characters.
For the layer above, lexers are inside the parsers of every language, query engine and configuration format: `lex` and `flex` generate them, `re2c` generates very fast ones, and the scanners in Go, Rust, V8 and Clang are written by hand. The layers below supply the theory. Finite automata (L3) give the machine: the token rules become a deterministic finite automaton (DFA), and running it is a table lookup per character. Formal languages and automata (L4) explain why this works: each token class is a regular language, regular expressions and finite automata describe the same class of languages, and there is a mechanical conversion between them. Unicode and UTF-8 (L3) decide what a "character" is: source text arrives as bytes that must be decoded, and identifiers, spaces and line breaks are defined over Unicode code points.
terms: Token — a unit of the language with a kind and, usually, the text it came from, such as (IDENTIFIER, "count") or (NUMBER, "10").
Lexeme — the actual character sequence in the source that matches a token pattern.
Regular expression — a compact notation for a set of strings built from characters, alternation (a|b), concatenation and repetition (a*).
DFA (deterministic finite automaton) — a machine with a finite set of states that moves to exactly one next state for each input character.
NFA (nondeterministic finite automaton) — a finite automaton that may have several possible moves for a character, or moves without reading a character; every NFA can be converted to a DFA.
Maximal munch (longest match) — the rule that the lexer takes the longest prefix of the remaining input that matches some token pattern.
Lookahead — reading characters beyond the end of the current token to decide where it ends.
Scanner generator — a tool, such as lex, flex or re2c, that turns a list of token patterns into the code of a lexer.
history: The mathematics comes first. Stephen Kleene described "regular events" in 1951 while modelling neural networks, and in 1959 Michael Rabin and Dana Scott formalised finite automata and showed that nondeterministic ones are no more powerful than deterministic ones; the conversion is the subset construction. In 1968, Ken Thompson published "Regular Expression Search Algorithm" in Communications of the ACM, describing how to compile a regular expression to machine code for a fast search, and he used the same ideas in the editor QED and later in `grep`. The Thompson construction, which builds an NFA from a regular expression piece by piece, is still the textbook method.
Early compilers wrote scanners by hand, and the work was repetitive. In 1975, Mike Lesk and Eric Schmidt at Bell Labs wrote Lex, which took a file of regular expressions with actions in C and generated a scanner; it was designed to work together with Steve Johnson's parser generator Yacc (1975). Vern Paxson wrote the faster, free reimplementation flex in 1987, which remains in wide use. The "Dragon Book" (Aho, Sethi and Ullman, 1986; second edition 2006 with Lam) made this the standard way to teach compilers.
Later practice moved in two directions. Generators got better at speed: re2c (Peter Bumbulis and Donald Cowan, 1993) generates code where each state is a piece of direct code, with no table lookup, and is faster than table-driven scanners. At the same time, most production compilers use hand-written lexers, for better error messages, for speed and because real languages are not purely regular: Python must track indentation, Go inserts semicolons at line ends, JavaScript must decide whether `/` begins a regular expression or is a division, and C must know whether a name is a type. The Unicode era added a new duty: following the identifier rules of Unicode Standard Annex 31, lexers decide which code points may start or continue an identifier, and in 2021 the "Trojan Source" paper showed that invisible bidirectional control characters in comments and strings can make code display differently from how a compiler reads it.
how: Step 1: decode the input. A source file is bytes. The lexer first decodes them (usually from UTF-8) into code points, rejecting invalid sequences, and may skip a byte-order mark. This is where **Unicode and UTF-8** matter: UTF-8 is self-synchronising, so a lexer can scan bytes directly and treat bytes of 0x80 and above as parts of identifiers or strings without decoding each code point, and all ASCII delimiters (quote, newline, brace) are single bytes that cannot appear inside a longer multi-byte character. Line and column numbers for error messages are counted at this stage, and the position of each token is recorded.
Step 2: describe the tokens as patterns. Each token class is a regular expression. For example, `ID = [A-Za-z_][A-Za-z0-9_]*`, `NUM = [0-9]+(\.[0-9]+)?`, `GE = ">="`, `GT = ">"`, `IF = "if"`, and `WS = [ \t\n]+`. A token class is a regular language, which is the content of **formal language theory** here: regular languages are closed under union, so all the token patterns together are one big regular expression `IF | ID | NUM | GE | GT | WS | ...`, and one automaton can recognise any token.
Step 3: compile the patterns into an automaton. Each regular expression becomes an NFA using Thompson's construction: a character is two states joined by an edge, alternation adds a split, repetition adds a loop, and "empty" (epsilon) edges join the pieces. The NFA for the union has one start state and one accepting state for each token class. Simulating an NFA means tracking a set of states, which is slower. So the generator converts it to a DFA using the subset construction: each DFA state stands for a set of NFA states. The DFA has one move per character, so the scanner reads each character once and never backs up inside the automaton. In the worst case the DFA can have exponentially more states than the NFA, but for token patterns of real languages it has tens to a few hundred states. A final minimisation step (Hopcroft's algorithm) merges states that behave the same. This is the contribution of **finite automata**: a precise machine model with a mechanical way to build, run and shrink it.
Step 4: run the DFA with maximal munch. The generated code stores the DFA as a table `next[state][char]` (or compresses it, since most entries go to the same dead state), and a table of which states accept which token class. To read a token at position p, the scanner starts in the start state and loops: read a character, move to the next state; whenever the new state is accepting, remember the position and the token class (the "last accept"); stop when the automaton enters the dead state (no way to continue) or the input ends. Then it emits the token for the last accept, moves the input position to just after that token, and starts again. This is **maximal munch**: the lexer takes the longest possible match. It is why `>=` is one token and not `>` followed by `=`, why `iffy` is an identifier and not `if` followed by `fy`, and why `x+++y` is read as `x ++ + y` in C.
When two patterns match the same longest text, a tie-break is needed: the rule listed first wins. This is how keywords work if they are written as patterns: `IF = "if"` before `ID` makes `if` a keyword, while `iffy` is longer under ID. Many scanners instead match everything as an identifier and then look the lexeme up in a hash table of keywords; this gives a smaller DFA.
Step 5: handle what is not regular. Some tokens need memory beyond a finite state. Nested comments (`/* a /* b */ c */`) need a counter. Python's indentation is converted into INDENT and DEDENT tokens by comparing each line's indentation with a stack. Go's lexer inserts a semicolon after a line's last token if that token is an identifier, literal, `return`, `)` and a few others. In C the lexer needs to know whether a name was declared by `typedef`, a feedback from the parser known as the "lexer hack". String interpolation (`"a ${b + "c"} d"`) and JavaScript's regular expression versus division are handled with modes: the parser or lexer keeps a stack of modes and the same character is scanned by different rules in different modes. The standard tool for this is "start conditions" in flex, or hand-written code.

example: Lex the text `if x1>=10` using the rules above (IF before ID, whitespace skipped). At position 0 the scanner is in S0. It reads 'i' and moves to the ID state (accepting; last accept = ID, length 1). It reads 'f' and stays in ID (length 2). It reads a space: no move, so the scanner stops. The longest match is `if` with length 2. Both IF and ID accept it, and IF is listed first, so the token is IF. If the text were `iffy`, the scanner would have read four letters before stopping, and the longest match is ID. Next, whitespace is matched and discarded. At `x1` the scanner reads 'x' (ID), then '1' (still ID, since digits may continue an identifier), then '>' where there is no move from ID, so it emits ID("x1"). At '>' the scanner moves to the GT state (accepting, length 1); it reads '=', moves to GE (accepting, length 2); it reads '1', which has no move from GE, so it emits GE for `>=`, not GT. Finally '1' and '0' take the scanner through NUM; the end of input stops it and NUM("10") is emitted. Total work: 9 characters and about 12 table lookups, since the character that ends a token is looked at once more to start the next one.
Now backing up. Take the rules `AB = "ab"`, `ABCD = "abcd"`, `ANY = .` and the input `abcx`. The scanner reads 'a', 'b' (accepting AB, last accept at length 2), 'c' (still alive, heading to ABCD but not accepting), then 'x' (dead). It falls back to the last accept: it emits AB for `ab` and resets the position to 2, having read 4 characters to emit a token of length 2. Then `c` and `x` are tokens of ANY. This rescanning is the price of maximal munch. In the worst case it becomes quadratic: with the rules `A = "a"` and `AAB = "a*b"` (zero or more a followed by b), the input `aaaa...a` (n letters, no b) makes the scanner run to the end for each token and then fall back, so it reads about n + (n−1) + … + 1 = n²/2 characters. For n = 100,000 that is 5 billion steps. Real languages avoid this by design (no token pattern needs long lookahead), and flex can warn about it.
intuition: Reading a sentence as a series of words by looking for the longest valid word at each spot, using only a small notebook to remember where you are inside the word.
The design is natural because of a mismatch in difficulty. Cutting text into words needs almost no memory: while inside an identifier you only need to know that you are inside it. Understanding the structure of sentences needs much more (nesting, matching brackets). Giving each job to the right machine (a finite automaton for words, a stack-based parser for structure) makes each part simple, fast and independently testable. Maximal munch is natural too: if "ifx" could be read as `if` and `x`, then no variable name could ever start with a keyword; the longest-match rule matches what people expect from written text.
mistakes: People often think lexing is trivial and can be done by splitting on whitespace. In fact tokens are not separated by spaces: `a+b>=c` has no spaces, strings can contain spaces, and comments hide tokens. A lexer must follow the patterns, not the spaces.
People often think a regular expression library is a good lexer. In fact a backtracking regex engine tries each pattern one at a time, can take exponential time on some inputs, and does not by itself apply maximal munch over all token types. A DFA built from all patterns reads each character once and gives linear time.
People often think the lexer decides what the program means. In fact it knows nothing about grammar, types or scope. It cannot tell whether `a * b;` in C is a multiplication or a declaration of a pointer; that needs a symbol table and is solved by the parser or by the "lexer hack".
People often think that using a lexer means you cannot parse languages with indentation, nested comments or string interpolation. In fact those just need a little extra state beside the DFA: a stack of indentation levels, a nesting counter, or a stack of lexer modes. The finite automaton does the regular part, and ordinary code does the rest.
tradeoffs: Choose a generated lexer (flex, re2c, ANTLR's lexer, `logos` in Rust) when the token set is large or changes often and you want a specification that is easy to read and test; re2c gives the fastest generated code, flex the most familiar workflow. You pay with a build step and less control over error messages. Choose a hand-written lexer when you need the best speed, precise error recovery, context-sensitive rules (Python-style indentation, interpolation, regex literals) or incremental re-lexing in an editor, as in Go, Rust, Clang, V8 and most IDE-oriented compilers. You pay with more code and more risk of small mistakes.
Choose a separate lexing phase when the language has a clear token level and you want a fast, simple parser. Choose a scannerless parser (PEG or GLR that works directly on characters) when the token level is ambiguous or context-dependent in ways that make lexing awkward, as in languages that embed other languages, or in some template and markup formats; you pay with slower parsing and less sharing of the token level between tools.
friction: Real languages are not strictly regular at the lexical level, and the exceptions cause most of the work: context-sensitive tokens (`>>` in C++ templates, which is the end of two template argument lists in `vector<vector<int>>`, was a problem until C++11), regular expression versus division in JavaScript, raw strings and nested comments in Rust, heredocs in shell and Ruby. The lexer and parser often need to talk to each other, which breaks the clean separation.
Error handling is a second source of difficulty. A lexer must say precisely what is wrong ("unterminated string starting at line 12") and recover so that later errors are still reported. A single unclosed quote can turn the rest of the file into one giant string, producing confusing messages far away from the cause.
Unicode and security are third. Identifiers that look the same but are different (a Cyrillic "а" and a Latin "a"), invisible characters, bidirectional text controls and normalisation forms can make code behave differently from how it looks. Compilers now warn about or reject some of these. Finally, performance in editors is a concern: a language server must re-lex a file on every keystroke, so lexers often support restarting from a known state at the start of a line rather than from the beginning of the file.
practice: If your language is small and regular, write the token patterns first as a table (name, regex, whether to skip) and use a generator or a small DFA built from it. If you write a lexer by hand, structure it as a function `next_token()` that skips trivia, looks at one character to choose a branch, consumes the longest valid run, and returns (kind, start, end). Store tokens as offsets into the source instead of copying text. Track line starts so that you can convert offsets to line and column only when needed. Test it with strings of tricky cases (`>=`, `>>=`, `1..2`, `1.e3`, an unterminated string, a file that ends inside a comment) and with fuzzing.
In data work, you lex whenever you write a parser for SQL snippets, log lines, configuration or expression languages. Prefer an existing grammar and tool (ANTLR, tree-sitter, Lark, the JSON parser in your runtime) to a hand-made regex; log parsing with a careful DFA-based tool is far faster than a chain of backtracking regexes. Use linear-time regex engines (RE2, Rust `regex`) for untrusted input, to avoid catastrophic backtracking.
interview: Why is a DFA built from all token patterns better than trying each regex in turn? || The DFA reads each input character once and runs in linear time, finding the longest match across all patterns together. Trying patterns one by one rescans the text for each pattern, and a backtracking regex engine can take exponential time on some inputs.
Explain maximal munch and how ties between rules are broken. || The lexer takes the longest prefix that matches any token pattern; it tracks the last accepting state and falls back to it if the automaton dies. If two rules match the same longest text, the rule listed first wins, so keywords are placed before identifiers.
How do you lex a language with significant indentation, such as Python? || The lexer keeps a stack of indentation levels. At the start of each logical line it compares the indentation with the top of the stack: greater pushes it and emits INDENT; smaller pops until it matches, emitting a DEDENT for each pop, and an inconsistent level is an error. Blank lines, comments and lines inside brackets are ignored for indentation.
Why can't a pure regular-expression lexer handle nested comments? || Matching nesting depth needs unbounded counting, which a finite automaton cannot do; the language of balanced comments is not regular. The lexer adds a counter (or enters a comment mode and tracks depth) outside the DFA.
quiz: What does the lexer produce and what does it discard? || It produces a stream of tokens (kind, text, position). It discards whitespace and, in most compilers, comments.
Why are token patterns written as regular expressions and recognised by a DFA? || Tokens are regular languages, which need only finite memory. Regular expressions convert to NFAs and then DFAs, which read each character once with a table lookup.
With the rules `ab`, `abcd`, `.` and input `abcx`, what tokens are produced? || `ab`, then `c`, then `x`. The scanner reads up to `abc` looking for `abcd`, fails at `x`, and falls back to the last accepting position (after `ab`).
For the input `a>=b`, why is the result three tokens and not four? || Maximal munch reads `>=` as one token because that match is longer than `>` alone. The tokens are `a`, `>=`, `b`.
When would you write a lexer by hand instead of using flex? || When you need precise error recovery and messages, context-sensitive rules (indentation, interpolation, regex literals), incremental re-lexing for an editor, or maximum speed; production compilers such as Go's, Rust's and V8 do this.
