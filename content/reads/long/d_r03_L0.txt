@@ terraform
value: Terraform is a tool that turns a text description of infrastructure into real infrastructure. You write files that say "I want a network, three subnets, a database and a Kubernetes cluster". Terraform looks at what already exists, works out the difference, and calls the cloud APIs to create, change or delete only what is needed. The same files can be reviewed in a pull request, stored in Git, and applied again to build an identical copy in another account or region.
The problem it solves is the gap between clicking in a cloud console and running a production system. A console change leaves no record, cannot be reviewed, and cannot be repeated exactly. A shell script that calls cloud APIs can create things, but it does not know what already exists, so running it twice may fail or create duplicates. Terraform is declarative: you describe the end state, and it computes the steps. It also knows the order. A subnet needs its network first, and an instance needs its subnet first, so Terraform builds a dependency graph and creates things in a safe order, in parallel where possible.
For the layer above, Terraform is the common way teams create everything else on this map: the VPC and IAM roles under a Databricks workspace, the S3 buckets for a data lake, the EKS or GKE cluster that runs Kubernetes, the DNS records in front of NGINX. It stands on two lower ideas. Go (L0) gives it a single static binary that runs on any laptop or CI runner and lets it walk the graph with many concurrent goroutines. Infrastructure as code (L1) gives it the idea itself: infrastructure is data that is versioned, reviewed, tested and repeatable. OpenTofu is the community fork of Terraform created after the 2023 licence change, and almost everything here applies to both.
terms: Resource — one infrastructure object that Terraform manages, such as an aws_s3_bucket or a google_compute_instance.
Provider — a plugin that knows how to talk to one API (AWS, Azure, Kubernetes, Datadog) and turns resource changes into API calls.
State — a JSON file that records which real objects Terraform created for each resource in the configuration, with their current attributes.
Plan — the list of creates, updates and deletes that Terraform computes by comparing configuration, state and the real world; nothing changes until you apply it.
Module — a reusable folder of Terraform files with inputs and outputs, used like a function.
Backend — the place where state is stored and locked, for example an S3 bucket, so a team shares one copy.
Drift — a difference between what the state says and what really exists, usually caused by a manual change.
HCL — HashiCorp Configuration Language, the declarative syntax of Terraform files (.tf).
history: Mitchell Hashimoto and Armon Dadgar founded HashiCorp in 2012 and released Terraform in July 2014. At that time AWS had hundreds of services and most teams managed them by hand or with scripts. Configuration tools such as Chef and Puppet managed what runs inside a server; AWS CloudFormation (2011) described infrastructure, but only for AWS. Terraform's idea was one language and one workflow for many clouds, with a plugin per API. Version 1.0 came in June 2021, after years of 0.x releases and a promise of compatibility from then on.
The first big technical step was the provider plugin model. Providers are separate programs that talk to Terraform core over gRPC, so a new provider can be written without changing core, and thousands exist in the public registry. The next steps added safety and structure: remote state with locking, modules, the "moved" and "import" blocks for refactoring without destroying things, and a built-in test command (1.6, 2023).
In August 2023 HashiCorp changed the licence of future Terraform versions from the open Mozilla Public License to the Business Source License (BSL), which forbids using the code to build a competing product. Many companies and the community answered with a fork, first called OpenTF and then OpenTofu, placed under the Linux Foundation and released as generally available in January 2024. OpenTofu entered the CNCF sandbox in April 2025. IBM announced in 2024 that it would buy HashiCorp, and the purchase completed in early 2025. As of October 2026, Terraform's latest release is 1.16.x and OpenTofu keeps its own release line with features such as state encryption.
how: Terraform works in a loop of four steps: read configuration, read state, compute a plan, apply the plan.
First it parses the .tf files written in HCL. Each resource block has a type, a name and arguments, for example type aws_subnet, name "a", with a vpc_id argument that refers to aws_vpc.main.id. A reference like that is the source of the dependency graph: Terraform scans all expressions, and every reference becomes an edge. The result is a directed acyclic graph (DAG) of resources, variables, data sources and providers. Here the lower concept does real work. A DAG is what lets Terraform know that the subnet cannot exist before the network, and it also shows which resources are independent and can be handled at the same time. Go goroutines walk this graph, by default with up to 10 operations in parallel (the -parallelism flag changes it).
Second, Terraform loads the state. State is a JSON document that maps each resource address in the configuration (for example aws_subnet.a) to the real object (its cloud ID and all its attributes as last seen). It has a serial number, which increases on every change, and a lineage ID, which detects when two unrelated state files are mixed up. State is needed because the cloud API alone cannot tell Terraform which of the 400 subnets in an account belong to this configuration. For a team, state lives in a remote backend. The common one is an S3 bucket, and the lock prevents two people from applying at once. Older setups used a DynamoDB table for the lock; newer Terraform and OpenTofu versions can lock with a lock file in S3 itself, which uses S3's conditional writes (the S3 concept on this map).
Third, plan. Terraform refreshes state by asking each provider to read the real object, so it sees drift. Then, for each resource, it asks the provider to compute the planned change between the old state and the new configuration. The provider's schema marks some arguments as "force new". If you change one of those, such as the availability zone of a subnet, the object cannot be modified, so the plan shows a replace: destroy and create again. The plan prints + for create, ~ for update in place, - for destroy and -/+ for replace. A replace of a resource also forces a change of everything that depends on its changed attributes, which is why one innocent edit can produce a long plan, and why you must read it.
Fourth, apply. Terraform walks the graph again. Creates and updates go from dependencies to dependents. Destroys go in the reverse direction: the instance first, the network last. For each node, core sends the planned change to the provider plugin over gRPC. The provider calls the cloud API, waits until the object is ready (often by polling), and returns the new attributes. Core writes them into state after each resource, so a failure halfway leaves a partial but correct state that the next run continues from.
The provider plugin protocol, based on gRPC and Protobuf, is what lets thousands of providers be developed by different teams in Go. Terraform core knows nothing about AWS. It only knows the generic operations: validate, plan, apply, read, import. The cloud (L0) concept is what Terraform ultimately controls: nearly every cloud resource is an API object with create, read, update and delete operations, which maps cleanly onto Terraform's model.
Data sources and repetition add flexibility. A data source reads an existing object (for example the latest AMI ID, or a VPC created by another team) without managing it. The count and for_each arguments create several copies of a resource from a list or a map. With for_each, each copy gets a stable address based on its key (aws_subnet.a["eu-1a"]), so removing one key removes only that copy. With count, the address is a number, so removing an item from the middle of a list shifts all later items and can cause unwanted replacements. This detail of how addresses map to state entries explains many surprising plans.
Modules package a set of resources behind inputs and outputs. Workspaces or separate state files per environment keep dev and prod apart. The import command or import blocks attach an existing object to a resource address, so a console-built system can be brought under management slowly. Recent versions add ephemeral values so secrets used during apply are not written to state, and OpenTofu adds optional state encryption.

example: Take a small configuration with four resources: a VPC, a subnet, a security group and one instance. The subnet and the security group each refer to the VPC. The instance refers to both the subnet and the security group. The graph has three levels: the VPC alone, then the subnet and the security group, then the instance.
First run, empty state. Terraform plans "4 to add". With parallelism 10, it creates the VPC first. When it finishes (a few seconds), it starts the subnet and the security group at the same moment. When both are done, it creates the instance, which takes roughly 20 to 40 seconds because the provider waits for the instance to reach the running state. State now holds four entries with their real IDs.
Second run, you change the instance type from t3.micro to t3.large. The provider knows that the instance type can be changed in place after a stop and start, so the plan says "1 to change". Nothing else is touched. If you instead change the AMI (the machine image), the schema marks it as force-new, and the plan says "1 to add, 1 to destroy" for the same resource, shown as -/+. The old instance is destroyed and a new one is created, and anything that stored data on its local disk is lost. This is the kind of line to read carefully in a review.
Third run, someone deletes the security group in the console. At plan time Terraform refreshes and finds that the group no longer exists. The state is updated, and the plan shows "1 to add" for the security group and "1 to change" for the instance, because its security group attachment changed. After apply, the real world again matches the files. If, on the other hand, someone adds an inbound rule in the console, the provider sees an extra rule and the plan removes it. That is the benefit of declarative control and the cause of many surprises for people who do not know the rule is managed.
Finally, destroy. Terraform walks the graph backwards: instance first, then subnet and group in parallel, then the VPC. If it tried to delete the VPC first, the cloud API would refuse because the VPC is not empty. The graph is what prevents this.
intuition: A blueprint, an inventory and a builder who only does the difference: compare what you want with what exists, and do only the work that closes the gap.
The design is natural because infrastructure is a set of objects with dependencies, and the hard part of managing it is order and memory. Order is solved by the graph: if A refers to B, B comes first. Memory is solved by state: Terraform must remember which objects are its own, otherwise it cannot tell what to change or delete. Everything else is convenience on top: providers hide API details, modules reuse patterns, and plans give you a chance to look before you act. The idea is the same as in a build system like make: declare targets and dependencies, and let the tool compute the minimum work.
mistakes: People often think Terraform configuration is the source of truth. In fact the state file is what Terraform trusts about which real objects it owns. If you lose the state, Terraform thinks nothing exists and plans to create everything again, which fails or creates duplicates. Back up state, and keep it in a versioned, locked remote backend.
People often think terraform plan is a perfect preview. In fact a plan is computed against the state and a refresh at one moment. Values that are only known after creation (generated IDs, IP addresses) show as "known after apply", and the real apply can still fail because of quotas, permissions or API errors. Apply the saved plan file (terraform apply plan.out) in CI so that what was reviewed is what runs.
People often think Terraform is a configuration tool like Ansible. In fact it manages the lifecycle of cloud objects through APIs, not the software inside servers. It can create the instance and its security group, but installing and tuning software on the instance belongs to images, containers or a configuration tool.
People often think secrets are safe because variables are marked sensitive. In fact "sensitive" only hides a value from the console output. The value is still written in plain text to the state file, so the backend needs encryption and strict access control, or you should use ephemeral values or an external secret store.
friction: State is the main weak point. It must be shared, locked and protected, and it often contains secrets in clear text. A corrupted or lost state is a serious incident. Manual changes cause drift, and a team that mixes console edits with Terraform will see plans that try to revert them. The refresh step calls the API for every resource, so a configuration with thousands of resources can take many minutes just to plan, and hit API rate limits.
Large monolithic configurations are risky because one apply touches too much, one lock blocks everyone, and the blast radius of a mistake is large. Teams split configurations by environment, region and ownership (network, data platform, applications), and then pass values between them through outputs and remote state data sources, which creates its own dependency problem. Refactoring is hard: renaming a resource makes Terraform think the old one should be destroyed and a new one created, unless you add a "moved" block.
The language is declarative and deliberately limited. Loops, conditionals and dynamic blocks are possible but awkward, and complex logic leads to unreadable configurations. Some people move to general-purpose languages (Pulumi, for example) at the price of more power and less predictability. Some changes cannot be done in place and force destroy-and-create. Finally, the licence split is a real decision: Terraform is BSL, and OpenTofu is MPL and community governed, and the two are diverging in features, so provider and module compatibility must be checked.
practice: Keep state remote, versioned, encrypted and locked. For AWS, an S3 bucket with versioning and server-side encryption is the usual choice. Use one state file per environment and per ownership boundary, and keep each one small enough that a plan finishes in a minute or two. Avoid sharing one huge state between teams.
Pin versions of Terraform and of every provider with required_version and required_providers, and commit the lock file (.terraform.lock.hcl). A provider upgrade can change plans in surprising ways. Run fmt, validate and a linter such as tflint in CI, and run plan on every pull request and post its output as a comment. Apply only from CI, from the reviewed plan, with a role that has limited rights.
Read every plan, and look for -/+ and destroy lines first. Protect critical resources (databases, buckets with data) with lifecycle { prevent_destroy = true }. Use "moved" blocks for refactoring and import blocks to adopt existing resources. Prefer small, focused modules with few inputs, and avoid deep module nesting. Do not put secrets in variables if you can use a secret manager reference or ephemeral values. Detect drift with a scheduled plan, and decide for each drift whether to change the code or revert the real object. Finally, decide Terraform or OpenTofu on purpose, based on licence, feature needs and support, not by habit.
tradeoffs: Choose Terraform or OpenTofu when you manage resources from several providers (cloud, Kubernetes, DNS, Datadog, Databricks) and want one workflow; choose the cloud's own tool (CloudFormation, Bicep) when you are fully on one cloud and want the provider to manage state and rollback for you. The cost of the multi-cloud tool is that you own the state; the cost of the native tool is lock-in and a smaller ecosystem.
Choose Terraform when you want vendor support, HCP Terraform features and the newest HashiCorp releases; choose OpenTofu when the BSL licence is a legal problem for your product, when you want features such as state encryption, or when you prefer community governance. Both read nearly the same language today, but they are diverging, so switching later costs more the longer you wait.
Choose a declarative HCL tool when infrastructure is mostly static resources and reviewers must read the plan. Choose a general-purpose language tool (Pulumi, CDK) when you need loops and abstractions over many similar resources and your team prefers tests in a normal language. You give up the simple, uniform syntax, and plans become harder for non-experts to review.
Choose many small states when teams must deploy independently and the blast radius must be small; choose one larger state when resources change together and cross-state dependencies would be a burden. Splitting costs wiring (outputs, data sources), and merging costs lock contention and slow plans. A useful rule is to split when plans take more than a few minutes or when two teams wait for the same lock.
Choose Terraform for infrastructure and Kubernetes manifests managed by GitOps tools (Argo CD, Flux) for what runs inside the cluster. Using Terraform for every Kubernetes object works, but its plan model fits poorly with fields controllers change after creation.
interview: Why does Terraform need a state file? Could it just query the cloud? || A cloud account holds many objects, and the API does not say which belong to this configuration. State maps each resource address to a real ID, so Terraform can tell what to update or delete. It also stores attributes that are not easy to query and supports metadata such as dependencies. Without it, Terraform could only create things, not manage them. Refresh keeps state aligned with reality.
Two engineers run apply at the same time on the same state. What happens, and how do you prevent it? || Without locking, both read the same state, both change the cloud, and the last write overwrites the other's state, leaving orphaned or untracked objects. A backend with locking (S3 with a lock file or DynamoDB, or HCP Terraform) lets only one run hold the lock. Also run applies from a single CI queue.
A plan shows -/+ on a production database. What do you do? || Stop and find which argument forced the replacement, for example an engine version, a name or a subnet group. Check whether the change can be made in place or with a parameter. Protect it with prevent_destroy, take a snapshot, and plan a migration if replacement is really needed. Never apply a replace of stateful data without a backup and a review.
How would you refactor a resource name or move it into a module without destroying it? || Add a moved block (or use terraform state mv) from the old address to the new one. Terraform then updates state and shows no create or destroy. Run plan and confirm it reports zero changes before applying.
How do you handle drift and secrets in state? || Detect drift with a scheduled plan in CI and decide per case whether to fix the code or the world. For secrets, encrypt and restrict the backend, avoid writing secrets to state by using ephemeral values or secret-manager references, and rotate anything that was ever stored in clear text.
Why is a huge single state a problem, and how do you split it? || Plans take long because every resource is refreshed, one lock blocks everybody, and one mistake can affect everything. Split by environment and ownership (network, data, apps), expose values through outputs and remote-state data sources or a parameter store, and keep each state small.
quiz: What does the Terraform state file contain, and why is it needed? || It maps each resource in the configuration to the real object (its ID and attributes). Terraform needs it to know which cloud objects it owns, so it can compute updates and deletes instead of only creating.
Why does Terraform destroy resources in the reverse order of creation? || The dependency graph says the instance needs the subnet, and the subnet needs the network. Deleting the network first would fail because it still contains the other objects, so dependents are removed first.
You change an argument that is marked "force new" on a resource with 3 dependents. What does the plan show and what is the risk? || It shows -/+ (destroy and create) for that resource, and possibly updates or replacements for the dependents whose references change. The risk is data loss or downtime for stateful resources, so read the plan before applying.
A configuration has 6 independent resources, each taking 30 seconds to create, and default parallelism of 10. About how long does apply take? || About 30 seconds, because all six can run at the same time; if they were chained by dependencies it would take 6 × 30 = 180 seconds.
When would you pick OpenTofu over Terraform? || When the BSL licence is a legal or business problem, when you want open governance or features such as state encryption, or when you do not want to depend on one vendor. Pick Terraform if you rely on HashiCorp or IBM support and the HCP Terraform service.

@@ linux
value: Linux is the operating system kernel that sits between your programs and the hardware. A program never talks to a disk, a network card or a CPU core directly. It asks the kernel, and the kernel shares the machine among all programs: it decides which thread runs on which core, which process gets which pages of memory, how bytes are cached and written to disks, and how packets move through the network. Linux does this for almost every server in the cloud, every Android phone, most network equipment and every machine on the TOP500 supercomputer list.
This is why every data system on this map depends on it. Kafka relies on the page cache and sequential disk writes. Spark executors are Linux processes with memory limits set by cgroups. Docker and Kubernetes are mostly a convenient interface to Linux namespaces and cgroups. NGINX and Envoy are fast because of epoll. Cilium moves networking into eBPF programs inside the kernel. If you understand what the kernel does with a read call, a memory allocation or a TCP packet, you can explain many performance problems that look mysterious at the application level.
The kernel is written mostly in C, with some assembly for each CPU architecture and, since version 6.1, a growing amount of Rust for new drivers. It runs on x86 and ARM (and RISC-V and others) by keeping a small architecture-specific layer below a large portable core. It provides the processes, virtual memory, scheduling, file systems, system calls, namespaces, I/O interfaces, eBPF and allocators described in the lower layers of this map. This read shows how they fit together into one working system, and which settings matter when you run data systems on it. As of October 2026, the current stable kernel series is 7.2.
terms: Kernel space and user space — the kernel runs with full hardware privileges; applications run with limited privileges and must ask the kernel for anything that touches hardware or other processes.
System call — the controlled entry from a program into the kernel, such as read, write, mmap, clone or epoll_wait.
Page cache — kernel memory that holds recently read or written file data, so repeated reads do not go to disk.
Namespace — a kernel feature that gives a group of processes their own view of a resource such as process IDs, network interfaces or mount points.
cgroup — a kernel feature that limits and accounts for the CPU, memory, I/O and process count of a group of processes.
eBPF — a way to load small verified programs into the kernel and run them at hooks for networking, tracing and security.
Loadable module — a piece of kernel code (often a device driver) that can be added to a running kernel.
OOM killer — the kernel routine that kills a process when memory is exhausted and nothing can be reclaimed.
history: Linus Torvalds, a student at the University of Helsinki, announced on 25 August 1991 that he was writing "a free operating system (just a hobby, won't be big and professional)". Version 0.01 came in September 1991. He wrote it because MINIX was only for teaching and the GNU system had no working kernel yet. In 1992 he moved the licence to GPL version 2, which is still the licence today. Combined with the GNU tools, it became a complete free system, which is why you will see the names Linux and GNU/Linux.
The kernel grew by being practical. Version 1.0 appeared in 1994, 2.0 in 1996 added multiprocessor support, and 2.6 in 2003 brought a scalable scheduler, the new epoll interface for many connections, and the model of frequent releases that is still used: a new release every nine to ten weeks, with a two-week merge window and release candidates. In 2005, after a dispute about a source control tool, Torvalds wrote Git in a few weeks to manage the kernel's own development.
Many of the features on this map arrived in the kernel step by step. Mount namespaces came in 2002 and the other namespaces over the next ten years; cgroups were added in 2008 by engineers at Google; KVM, which turns Linux into a hypervisor, came in 2007; the Completely Fair Scheduler replaced the older scheduler in 2007; and extended BPF (eBPF) was added in 2014 by Alexei Starovoitov. cgroup version 2 (2016) cleaned up the resource model. io_uring, by Jens Axboe, came in 5.1 in 2019, and EEVDF replaced CFS in version 6.6 in 2023. Rust support entered in 6.1 (2022), and sched_ext, which lets eBPF programs define a scheduler, entered in 6.12 (2024).
Linux won on servers because it was free, it could be changed, and companies could share the cost of improving it. Today thousands of developers from hundreds of companies contribute to each release, and drivers make up the largest part of tens of millions of lines of code.
how: The kernel's job can be described as four things: protect, share, hide and connect.
Protection starts in the CPU. Processors have privilege levels (ring 0 and ring 3 on x86, exception levels on ARM). User programs run at the low level. When a program needs the kernel, it executes a special instruction (syscall on x86-64, svc on ARM64), the CPU switches to kernel mode and jumps to a fixed entry point. The system call interface (the syscalls concept) is therefore the only door, and it is narrow: several hundred calls, with arguments checked on entry. A trivial call costs from about a hundred nanoseconds to a microsecond depending on the CPU and on security mitigations. This is cheap but not free, which is why high-performance code batches work, and why io_uring lets a program submit many operations with one call or none.
Sharing the CPU is the job of the scheduler (CPU scheduling). Each CPU core has a run queue of runnable threads. Since version 6.6, the EEVDF scheduler gives each thread a fair share by weight and picks, among the threads that are owed time, the one with the earliest virtual deadline, which improves latency for short tasks. Timer interrupts, a thousand or so per second per core in typical settings, let the kernel preempt a running thread. A context switch between threads costs roughly one to several microseconds including lost cache warmth. The scheduler also balances load among cores and tries to keep a thread near its cached data and memory (NUMA).
Memory (virtual memory and paging) is the part that surprises people most. Every process sees its own flat address space. The CPU translates virtual addresses to physical ones with page tables, in units of 4 KiB pages (and larger huge pages), using a hardware cache called the TLB. The kernel creates the tables, and a page is only given physical memory when it is first touched: the first access causes a page fault, the kernel finds or allocates a free page, fills it (zeros, file data, or data from swap) and resumes the program. A minor fault, which only needs a free page, costs around a microsecond; a major fault that reads from storage costs the storage latency, about 100 microseconds on NVMe and milliseconds on disks. fork creates a child with copy-on-write: both share the same pages until one writes. The kernel's own allocators (memory allocators) serve its internal needs: the buddy allocator hands out runs of pages, and the slab allocator carves small fixed-size objects such as inodes and socket buffers from them.
Files go through the virtual file system (VFS). The read system call enters VFS, which calls the specific file system (ext4, XFS, Btrfs, which map files to blocks and use journals or copy-on-write to survive crashes). The result is cached in the page cache. A cached read is a memory copy at several GB/s; a miss goes through the block layer to the device driver, and the kernel reads ahead (128 KB by default) when it sees sequential access. Writes normally go into the cache and are written back later, so a program is only sure its data is on disk after fsync. All memory not used by programs is used as page cache, which is why free memory looks low on a healthy server.
Networking receives packets from the network card with interrupts and polling (NAPI), passes them through the protocol layers (IP, TCP), keeps per-connection state, and wakes the thread waiting on the socket. For many connections, I/O models matter: epoll lets one thread wait on tens of thousands of sockets and be told which are ready, and io_uring has submission and completion rings shared with user space for asynchronous file and network operations.
Isolation and limits come from namespaces and cgroups (namespaces and cgroups). A namespace changes what a process can see (its own PID 1, its own network stack, its own root file system). A cgroup changes how much it can use: cpu.max, memory.max, io.max and pids.max. A container is simply a process started inside a set of namespaces and cgroups, which is why containers start in milliseconds and share the host kernel, unlike virtual machines. With KVM (virtualization), the same kernel can also act as a hypervisor, using CPU hardware support to run entire guest kernels.
Finally eBPF lets you extend the kernel safely at run time. A verifier checks that a small program terminates and cannot read arbitrary memory, a JIT compiles it, and it attaches to a hook (a packet arriving, a system call, a function entry). It stores data in maps shared with user space. This is the base of Cilium, of many profilers and tracers, and of security tools. Linux is monolithic: all these parts run in one address space for speed, with loadable modules adding drivers without a reboot, at the cost that a bug in a driver can crash the whole machine.

example: Two examples with numbers show the kernel at work.
First, a read. A Spark executor reads a 1 MB block from a local file on an NVMe disk. The read call enters the kernel, VFS finds the file's pages in the page cache. Case 1, the data is not cached. The default read-ahead window is 128 KB, so the kernel issues a sequence of reads of 128 KB (the window grows as it sees a sequential pattern). Each NVMe read takes roughly 80 to 100 microseconds, so the 1 MB takes about 8 requests in a sequence, or around 0.3 to 0.8 ms in total when some run in parallel. The kernel then copies the data into the user buffer. Case 2, the same read a second later, now hits the page cache. The cost is only a memory copy: 1 MB at about 10 GB/s is around 100 microseconds, and the disk is not touched. This is the reason why a Kafka broker with 64 GB of RAM serves consumers that are close to the head of the log without any disk reads, and why a restart that empties the cache (a cold broker) is slow for a while.
Second, a CPU limit. A container is started with a limit of 2 CPUs. Kubernetes writes cpu.max = "200000 100000" in the cgroup: the group may use 200 ms of CPU time in every 100 ms period. The application has 8 busy threads on a 16-core node. In each period the 8 threads together burn 8 × 25 ms = 200 ms of CPU in the first 25 ms of wall-clock time. The budget is then exhausted, and the kernel throttles the whole group for the remaining 75 ms. A request that needs 30 ms of CPU may therefore take 100 ms or more, even though the node's CPUs are mostly idle and average utilization shows only 20% of the node. The counters nr_throttled and throttled_usec in cpu.stat show this directly. The fix is to give more CPU limit, use fewer threads, or remove the limit and rely on requests. This kind of tail-latency problem cannot be understood without knowing how the scheduler and cgroup accounting work.
intuition: Linux is the referee and the landlord: it decides who plays when, who gets which rooms, and nobody enters a room without the keys it hands out.
The design is natural once you see the conflict it solves. Programs want the whole machine to themselves. The hardware is shared and fragile. The cheapest solution is to give each program the illusion of a private machine, a private address space, a private view of files, a private CPU timeline, and to keep one trusted piece of code, the kernel, that creates the illusion and enforces the rules. The CPU's privilege levels and the MMU make the rules enforceable in hardware. Namespaces and cgroups are the same illusion extended: not just a private address space, but a private network and process tree, with a budget. Containers are therefore not a new technology but a new way to use old kernel mechanisms.
mistakes: People often think a container is a small virtual machine. In fact a container is an ordinary Linux process (or group) started inside namespaces and cgroups, and it shares the host kernel. There is no guest kernel, which is why startup is fast, and also why a kernel bug or a kernel setting affects every container on the node.
People often think free memory should be high and that low "free" memory means a problem. In fact Linux uses spare memory for the page cache, so free memory goes close to zero on a healthy file-heavy server, such as a Kafka broker. Look at "available" memory, which counts reclaimable cache, and at major page faults, swap activity and OOM kills.
People often think a write call means the data is on disk. In fact write copies data into the page cache and returns. The kernel flushes it later, and a power loss before that loses it. Only fsync (or opening with O_DSYNC, or direct I/O with the right flags) gives a durability guarantee, which is why databases and Kafka configure flush behavior with care.
People often think a CPU limit is a safe, harmless way to share a node. In fact the limit is enforced as a quota per 100 ms period, so a multithreaded process can be throttled in bursts and see large latency spikes while the CPU looks idle. CPU requests (shares) are a fairer tool for sharing, and limits should be set with the throttling counters in hand.
People often think a newer kernel is always faster. In fact an upgrade changes the scheduler, the memory manager, the TCP stack and drivers. It often improves things, but you must test your workload, because defaults and behavior change.
friction: Defaults are made for general use, not for a particular data system. Many things need tuning: vm.swappiness, dirty page ratios (vm.dirty_ratio and dirty_background_ratio), transparent huge pages (which can cause latency spikes in databases), the open file descriptor limit (ulimit -n), vm.max_map_count (needed for Elasticsearch and others), the I/O scheduler for each device, network buffer sizes and TCP settings. Kernel parameters that were right for one workload can hurt another.
Observability is hard because the kernel is a large system with no single dashboard. You need perf, ftrace, and eBPF tools to see where time goes, plus the knowledge to interpret them. The monolithic design means a faulty driver or module can crash the machine; the kernel has no memory safety in its C code, and a large share of security vulnerabilities come from that, which is the main reason for the slow introduction of Rust. The huge number of drivers and options also makes the kernel hard to harden, and mitigations for CPU vulnerabilities (Spectre and similar) have added cost to system calls and context switches.
The pace of change is another cost. A new release appears every nine or ten weeks. Long-term support (LTS) series, such as 6.12 and 6.18 at the time of writing, receive fixes for years, but features such as new eBPF helpers, io_uring operations or cgroup behavior vary between versions, so a fleet with mixed kernels produces mixed results. Container platforms and tools like Cilium therefore document a minimum kernel. Finally, the kernel's resource limits are not always precise: the OOM killer chooses victims by heuristics, memory accounting in cgroups does not cover everything, and I/O isolation is weaker than CPU isolation.
practice: Know your kernel version and pin it per fleet. Use a distribution kernel with long-term support, and upgrade deliberately with a canary group. Keep a small, written list of the sysctls you change, with the reason and a measured result for each.
For data systems, a typical baseline is: set swappiness low (1 to 10) for databases and brokers, so the kernel keeps program memory and drops cache first; disable or set transparent huge pages to madvise for latency-sensitive databases; raise file descriptor limits (hundreds of thousands for brokers and proxies) and vm.max_map_count; choose none or mq-deadline as the I/O scheduler for NVMe; and set dirty page limits so write-back is smooth rather than bursty. Leave room for the page cache: a broker or a database that uses all RAM as heap leaves the page cache with nothing.
For containers, read the cgroup files directly (cpu.stat, memory.current, memory.events, io.stat). Watch nr_throttled, OOM events and PSI (pressure stall information, in /proc/pressure), which tells you what share of time tasks waited for CPU, memory or I/O. Treat memory limits as hard walls and size the JVM heap below them, leaving room for off-heap memory and page cache.
For diagnosis, learn a small set of tools: top and vmstat for the first look, iostat and pidstat for devices and processes, ss for sockets, perf for CPU profiles, strace for system calls, and bpftrace or BCC for custom questions. Brendan Gregg's USE method (utilization, saturation, errors for each resource) gives a simple order. Always change one setting at a time and measure. Write the kernel version and the settings into your runbooks.
tradeoffs: Choose a general-purpose distribution kernel (Ubuntu, Debian, RHEL and relatives) when you want security fixes, support contracts and predictable behavior; choose a recent mainline or a custom-built kernel when you need a specific feature (new eBPF or io_uring capability, a driver, a scheduler) and can afford your own testing and patching. The price of the first is old features; the price of the second is that you own the regressions.
Choose containers when you want fast start (milliseconds), density (many per host) and a shared kernel; choose virtual machines (KVM, Firecracker) when tenants do not trust each other or need different kernels. A container gives up isolation strength, since a kernel flaw can cross the boundary; a VM costs memory and some start time, but offers a much stronger boundary. Sandboxes such as gVisor or Kata sit in between with extra cost.
Choose buffered I/O with the page cache for most workloads, since the kernel's caching and read-ahead are good and you get sharing between processes for free. Choose direct I/O (O_DIRECT) when you run your own cache and want to avoid double caching and unpredictable write-back, as many databases do, at the cost of doing alignment, read-ahead and scheduling yourself.
Choose epoll with a few threads when you have thousands of mostly idle connections; choose io_uring when you do many small file or network operations and the system call cost shows in profiles, and when your kernel version and security policy allow it (some environments restrict io_uring because of past vulnerabilities). Choose plain blocking threads when the connection count is small and simplicity matters.
Choose CPU limits when you need hard isolation between tenants or predictable billing; choose requests only (no limits) when you value low latency and can accept that a busy neighbour may use idle CPU. You give up either burst capacity and tail latency, or strict fairness.
interview: What exactly happens when a process calls read() on a file, from user space to disk and back? || The syscall switches to kernel mode, VFS finds the file's inode and calls the file system. The kernel checks the page cache; on a hit it copies the data to the user buffer. On a miss it issues block I/O (with read-ahead) through the block layer and driver, sleeps the thread until the interrupt, fills the cache, and then copies the data and returns. The thread is runnable again via the scheduler.
A service in a container with a 2-CPU limit shows high p99 latency while node CPU is 20% used. What do you check? || CFS bandwidth throttling. Read cpu.stat for nr_throttled and throttled_usec, compare thread count to the quota (cpu.max), and look at PSI. Fix by raising the limit, reducing parallel threads or removing the limit and using requests only. Also check the runtime's own CPU detection, such as the JVM's use of container limits.
Why does a Kafka broker need free RAM that it does not use itself? || Kafka relies on the OS page cache: recent log segments are served from memory, and writes are appended sequentially in cache before write-back. A large JVM heap takes memory away from the cache, so consumer reads fall back to disk. Keep the heap modest (a few GB to about 6 GB) and let the rest be cache.
What does the OOM killer do in a cgroup-limited container, and how is it different from a node-wide OOM? || When a cgroup reaches memory.max and cannot reclaim, the kernel kills a process inside that cgroup (the container is OOM-killed), leaving the node healthy. A node-wide OOM happens when the whole machine is out of memory and the kernel picks a victim by oom_score across all processes, which can hit unrelated services.
Why is a context switch expensive, and how do you reduce them? || Direct cost is saving and restoring registers and entering the scheduler, a microsecond or so. The indirect cost is lost CPU cache and TLB state, which is larger. Reduce switches with fewer threads than cores, event loops, CPU pinning, batching, and avoiding lock contention that makes threads sleep and wake.
Why can eBPF programs run in the kernel safely, and what are the limits? || The verifier checks the program before loading: bounded loops, no invalid memory access, allowed helper calls, valid types. The JIT then compiles it. Limits are the program size and complexity, restricted helpers, and the fact that it needs a recent kernel and privileges; the verifier can also reject valid programs it cannot prove safe.
quiz: What is the difference between user space and kernel space, and how does a program move between them? || The kernel runs with full hardware privilege and user programs with limited privilege. A program enters the kernel through a system call instruction, which makes the CPU switch to kernel mode and jump to a fixed entry point; it returns to user mode when the call finishes.
Why does a healthy Linux file server show almost no free memory? || The kernel uses all memory that programs do not need as page cache for file data. That memory is reclaimed instantly when programs need it, so "available" memory, not "free", shows the real headroom.
How do namespaces and cgroups together make a container? || Namespaces give the process group its own view of PIDs, network, mounts and so on; cgroups limit and account for its CPU, memory and I/O. A container is just such a process group plus a root file system image, sharing the host kernel.
A container has cpu.max = 150000 100000 and runs 6 busy threads. About how long are threads running in each 100 ms period before throttling? || The quota is 150 ms of CPU per 100 ms period. With 6 threads burning in parallel, the quota is used up in 150 / 6 = 25 ms, so the group runs for 25 ms and is paused for about 75 ms.
When would you choose O_DIRECT instead of the page cache? || When the application has its own cache and wants to avoid double caching and unpredictable write-back, as many databases do. The price is that you must align buffers, handle read-ahead and ordering yourself, and lose sharing between processes.

@@ nginx
value: NGINX (pronounced "engine-x") is a web server and reverse proxy. It sits at the edge of a system, accepts connections from browsers and clients, and either serves files directly or forwards requests to application servers behind it. It also terminates TLS, balances load across several backends, caches responses and applies limits. A single NGINX server can hold tens of thousands of open connections and push several gigabits per second of traffic with a few worker processes and modest memory.
It was built to solve the C10K problem: how to serve ten thousand concurrent connections on one machine. The older design, used by Apache's classic mode, gave each connection its own process or thread. A thread costs memory for its stack, and the scheduler has to switch among thousands of them, most of which are only waiting for a slow client. NGINX uses an event loop instead. A small number of workers, usually one per CPU core, each watch thousands of sockets with epoll, and work only on the sockets that are ready. An idle connection costs a small structure in memory, not a thread.
For the layer above, NGINX provides the practical form of three ideas on this map. Load balancing (L1) is its upstream module, which spreads requests across servers with round robin, least connections or hashing, and removes failing servers. The API gateway (L1) pattern is its server and location blocks: terminate TLS, route by host and path, authenticate, rate limit, rewrite. Web architecture (L1) is the role it plays in most web stacks: serve static files fast, and shield slow application servers from slow clients. NGINX Ingress controllers also made it the default way to expose Kubernetes services for many years, although the community ingress-nginx project was retired in March 2026.
terms: C10K problem — the challenge, named by Dan Kegel in 1999, of serving ten thousand concurrent connections on one server.
Event loop — a loop that waits for readiness events on many sockets and runs a small piece of code for each one, without blocking.
epoll — the Linux system call interface that tells a program which of many file descriptors are ready for reading or writing.
Master and worker processes — the master reads the configuration and manages workers; the workers handle all connections.
Reverse proxy — a server that accepts requests from clients and forwards them to other servers, hiding those servers from the client.
Upstream — a group of backend servers that NGINX forwards requests to and balances across.
Keep-alive — keeping a TCP connection open for several requests, to avoid the cost of new TCP and TLS handshakes.
sendfile — a system call that copies file data to a socket inside the kernel, without passing it through user space.
history: Igor Sysoev, a Russian system administrator working for the portal Rambler, started writing NGINX in 2002 because Apache could not cope with the traffic of busy Russian sites. The first public release was on 4 October 2004. Dan Kegel's essay "The C10K problem" (1999) had described the problem and listed the answers, and Linux got epoll in the 2.5/2.6 kernels in 2002 to 2003. NGINX was among the first servers to be designed around these answers from the start.
It spread through the 2000s as the front of busy sites, because it was fast, small and stable, and because the configuration was short. Sysoev and two co-founders started Nginx, Inc. in 2011 to offer support and a commercial version (NGINX Plus), with extra features such as an API for changing upstreams without a reload, active health checks and a dashboard. HTTP/2 support came in 2015, dynamic modules in 2016, and HTTP/3 over QUIC in 2023. F5 bought the company in 2019 for about 670 million dollars.
Two splits came later. In 2024 Maxim Dounin, one of the longest-serving core developers, left and started a fork called freenginx after a disagreement with F5 over project policy. In Kubernetes, the community ingress-nginx controller, which many clusters used to receive traffic, announced its retirement in November 2025: no more releases or security fixes after March 2026, with Gateway API and other controllers recommended instead. F5 maintains its own, different NGINX Ingress Controller and NGINX Gateway Fabric. As of October 2026 the mainline version of NGINX itself is 1.31.x.
how: NGINX runs as one master process and several worker processes. The master reads and validates the configuration, opens the listening sockets, starts the workers, and handles signals. The workers do all real work. A common setting is worker_processes auto, which starts one worker per CPU core. Each worker is single-threaded and runs its own event loop. Because there is no sharing of connection state between workers, there are almost no locks, and each worker keeps its data close to its CPU core's cache.
Inside a worker the loop is simple. The worker calls epoll_wait, which returns a list of sockets that are ready. For each, NGINX runs a small step of a state machine: read some bytes, parse the request, pick a handler, write some bytes. Nothing blocks. If a client is slow, the socket is simply not in the ready list. This is where the Linux concept does its work: epoll scales with the number of ready sockets, not the number of watched sockets, while older select and poll scan every socket on each call. Because each connection is a small structure (a few kilobytes of memory with buffers allocated on demand from per-request memory pools), a worker can hold tens of thousands of connections. The cost model is also different: a thread-per-connection server needs at least one stack (the default reserved stack is 8 MB of address space on Linux, with tens of kilobytes resident) and a share of scheduler time for every client, even idle ones.
Requests pass through phases. After reading the request header, NGINX finds the matching server block (by listen port and Host header) and then the matching location block (exact match, longest prefix, or regular expression). A set of phases runs in a fixed order: rewrite, access (authentication, allow and deny), content generation (static file, proxy_pass, FastCGI) and logging. Modules hook into phases. Most modules are compiled in, and since 1.9.11 some can be loaded dynamically.
For static files, NGINX uses sendfile, which lets the kernel copy file data from the page cache to the network socket without moving it through user space, and it can use tcp_nopush to fill packets. Blocking operations that cannot be made asynchronous, such as reading a file that is not cached, can use a thread pool so that the event loop is not stuck.
As a reverse proxy, the proxy_pass directive forwards the request to an upstream group. This is the load balancing concept in practice. The default method is weighted round robin; least_conn sends each request to the server with the fewest active connections; ip_hash or hash with a key (a cookie, a URI) gives stickiness; random with two choices picks the lesser loaded of two random servers. Passive health checks mark a server as failed after max_fails errors within fail_timeout, and then skip it for that time; NGINX Plus adds active checks. With keepalive in the upstream block, NGINX keeps a pool of idle connections to the backends, so it saves the connection setup on every request. NGINX also buffers: it reads the whole response from a fast backend and then sends it to a slow client at the client's speed, so that a precious application thread is released quickly. This one feature is why putting NGINX in front of a slow application server often improves the application's capacity.
As an API gateway (the API gateway concept), the same configuration terminates TLS (with session resumption, OCSP stapling and HTTP/2), routes by host and path, checks credentials by calling an auth service (auth_request) or validating a token, limits rates (limit_req uses a leaky bucket kept in shared memory; limit_conn limits concurrent connections) and rewrites headers. The proxy cache stores responses on disk, with an index of keys in a shared memory zone, honors Cache-Control, and can serve stale content when a backend fails.
Reloading is graceful. On a reload signal, the master checks the new configuration, starts new workers with it, and tells the old workers to stop accepting new connections and exit when their existing connections end. Traffic is not dropped. This is the main limit: the configuration is static and changes need a reload, which is why dynamic environments with changing backends fit NGINX less well than Envoy, which receives configuration through an API.

example: Take a small shop site on one machine with 4 CPU cores, with the configuration written in words. Worker_processes auto gives 4 workers. A server block listens on 443 with TLS, and a location "/static/" serves files from disk. A location "/api/" has proxy_pass to an upstream group of three application servers with keepalive 32 and least_conn.
A browser opens a connection and requests /static/logo.png. The kernel puts the connection in the accept queue, and one worker accepts it. The worker completes the TLS handshake (it does a few steps without blocking, each time returning to the loop), parses the request, matches the location, and calls sendfile. A 40 KB file is copied from the page cache to the socket in one call. The whole request uses on the order of tens of microseconds of CPU time. At that cost, one core can serve roughly tens of thousands of such requests per second, and the network or TLS usually limits first.
Now a request to /api/orders from a slow mobile client on a 1 Mbit/s link. The application server produces a 250 KB response in 20 ms. A direct connection would keep the application thread busy for 250 KB × 8 / 1 Mbit/s = 2 seconds while sending to the client. With NGINX in between, the application sends the 250 KB to NGINX over the fast local network in a few milliseconds and moves on. NGINX holds the response in its buffers and delivers it to the client for the 2 seconds, using one small connection structure instead of one application thread. If the application server has 200 threads, it can handle 200 / 0.02 = 10,000 such requests per second when it is not held back by slow clients, but only 200 / 2 = 100 per second if every thread waits for the slow client. The proxy buffering gives a 100 times improvement in this case.
Least-connections balancing then picks among three servers whose active connections are 12, 4 and 9, and sends the request to the second one. If one server fails three times within 10 seconds and the settings are max_fails=3 fail_timeout=10s, NGINX takes it out for the next 10 seconds and sends traffic to the other two. Finally, to roll out a new configuration, an engineer changes the file, runs nginx -t to check it, and sends reload. The 4 old workers finish their requests and exit, the 4 new workers take new connections, and no client sees an error.
intuition: One waiter for a whole restaurant who only goes to a table when the guests are ready to order, instead of one waiter standing by each table.
Most of the time in a network server is spent waiting: for a client to send, for a backend to answer, for a disk. A design that gives every waiting connection a thread pays for the waiting with memory and scheduling. An event loop pays only when something is ready. Add the observation that proxying and static serving need very little CPU per request, and the single-threaded worker per core is natural: no locks, no context switches, and the cores stay busy with real work.
mistakes: People often think NGINX is faster because it is written in C. In fact the language helps a little, but the main gain is the architecture: an event loop with non-blocking I/O means that waiting costs almost nothing. Code that blocks inside a worker (a slow DNS lookup, a blocking module, a disk read without thread pool) stalls thousands of connections at once.
People often think more worker processes than CPU cores gives more throughput. In fact each worker is a full event loop, and extra workers on the same cores only add context switches. One per core is the usual setting, and the number of connections is set by worker_connections and the file descriptor limit, not by the number of workers.
People often think a reload restarts NGINX and drops connections. In fact the master starts new workers with the new configuration and lets the old ones finish their connections. A restart (stopping the master) does drop them. Long-lived connections such as WebSockets can keep old workers alive for a long time, which can surprise people.
People often think NGINX balances load as well as a service mesh proxy. In fact open-source NGINX has passive health checks only, no dynamic endpoint API, and basic algorithms. When upstream addresses come from DNS, NGINX resolves the name when it loads the configuration, unless you use a variable and a resolver, so changed addresses can go unnoticed.
friction: The configuration language is compact but has sharp edges. The meaning of location matching, the inheritance rules for directives such as proxy_set_header or add_header (a directive defined in an inner block silently replaces the ones from the outer block), and the behavior of "if" inside location blocks are well-known traps. A small error can send traffic to the wrong place or expose a file path. Testing configuration with nginx -t catches syntax errors, not meaning.
Dynamic environments are a weak point. Open-source NGINX needs a file change and reload to change upstreams, which means orchestration around it. Reloads with thousands of long-lived connections create two sets of workers for a while, which uses more memory. Observability is basic: the stub status page and logs are available, and richer metrics need NGINX Plus or an exporter. There is no built-in distributed tracing or service discovery comparable to Envoy's.
Under high load the limits are the usual Linux ones: file descriptors, ephemeral ports when proxying (about 28,000 default ports per destination address and port), the accept queue, and TLS handshake CPU. A request body or header attack (slowloris) needs timeouts and limits. Finally, ecosystem risk is a real friction: the retirement of the community ingress-nginx, the split with freenginx, and a commercial/open-source line within F5 mean you must choose which NGINX distribution and controller you depend on, and watch their security support.
practice: Set worker_processes auto, and raise worker_connections and the process file descriptor limit (worker_rlimit_nofile) to match your expected connections, counting both the client and the upstream side for every proxied request. Enable keepalive to upstreams (keepalive with proxy_http_version 1.1 and an empty Connection header), and keepalive to clients with a sensible timeout. Turn on sendfile, tcp_nopush and gzip or brotli for text.
Set timeouts and limits on purpose: client_header_timeout, client_body_timeout, proxy_connect_timeout, proxy_read_timeout, client_max_body_size, and limit_req for abusive clients. Use proxy_next_upstream carefully, because retrying a non-idempotent POST can create duplicates. Log the upstream response time ($upstream_response_time) next to the request time ($request_time), so you can see whether the slowness is the backend, NGINX or the client.
Terminate TLS with modern settings (TLS 1.2 and 1.3, session resumption, OCSP stapling) and consider HTTP/2 or HTTP/3 to clients while using HTTP/1.1 with keepalive to backends. Keep configuration in version control, check it in CI with nginx -t, and reload rather than restart. If you run in Kubernetes, do not start a new project on the retired community ingress-nginx; look at Gateway API implementations (including Envoy-based ones) or a maintained controller. Use NGINX where its strengths show: static content, caching, TLS termination, a simple edge or API front with stable backends.
tradeoffs: Choose NGINX when the topology is stable, the configuration is managed as files, and you want a small, fast edge for static content, caching and a handful of upstreams; choose Envoy when backends change constantly, you need dynamic configuration through xDS, rich per-request metrics, retries with budgets, and L7 features such as gRPC-aware routing. You give up simplicity and a short learning curve with Envoy, and you give up dynamic control with NGINX.
Choose NGINX or HAProxy for pure load balancing at high connection counts. HAProxy has stronger load balancing features (active health checks, rich stick tables, detailed stats) in its open version; NGINX is stronger as a web server and cache, and many teams already know its configuration. Choose one by what else the box has to do, not by benchmark numbers, which are close for typical loads.
Choose open-source NGINX when you can script reloads and accept passive health checks; choose NGINX Plus when you need runtime upstream changes, active checks and support, at a licence price. Choose a managed cloud load balancer (such as an application load balancer) when you do not want to operate the edge at all, at the cost of per-hour and per-request fees and fewer features.
Choose NGINX as a TLS terminator and cache in front of an application when most requests can be served from cache or static files; choose to skip the extra hop when requests are dynamic, latency-sensitive and already pass through a mesh or a cloud load balancer, since each proxy adds some hundreds of microseconds and one more thing to operate.
interview: Why can NGINX handle 10,000 connections with a handful of processes while a thread-per-connection server struggles? || It uses a non-blocking event loop with epoll, so each worker waits on all its sockets at once and runs only for ready ones. An idle connection costs a few KB of structures, not a thread stack and scheduler share. The server spends CPU on useful work rather than on switching between mostly idle threads.
A slow application behind NGINX has p99 latency spikes; where do you look? || Compare $request_time with $upstream_response_time in the access log to separate backend time from client and proxy time. Check upstream keepalive (new connections per request), proxy buffering, worker connection and file descriptor limits, the accept queue, and whether a blocking operation stalls a worker. Then look at the backend itself.
What happens during an NGINX reload, and when can it still cause trouble? || The master validates the new config, starts new workers, and old workers stop accepting and exit after their connections finish. No connection is dropped, but long-lived connections (WebSockets, streaming) keep old workers alive and double the memory for a long time. Frequent reloads under many connections can also cause CPU spikes.
How would you rate limit per client, and what are the failure modes? || limit_req_zone keyed on the client IP (or a header or API key) with a rate and burst, using a leaky bucket in shared memory. Failure modes: many clients behind one NAT or proxy share an IP, so use the real client address from a trusted header; the zone size must hold the keys; and per-worker counters share memory but not across multiple NGINX servers, so a global limit needs a shared store.
How does NGINX pick an upstream and handle a failing one? || The method is round robin by default, or least_conn, hash or random two choices. Passive checks count errors and timeouts, and after max_fails within fail_timeout the server is removed for that time. Retries (proxy_next_upstream) move to another server for idempotent requests. Active health checks need NGINX Plus or an external tool.
Why might you choose Envoy over NGINX for a microservice platform? || Envoy takes endpoints, routes, clusters and certificates dynamically through xDS without reloads. It offers outlier detection, retry budgets, circuit breakers, gRPC and HTTP/2 end to end, and detailed stats and tracing out of the box. NGINX is simpler and good at static, caching and stable topologies.
quiz: What was the C10K problem, and how did NGINX address it? || It was the problem of serving 10,000 concurrent connections on one machine. NGINX uses a few worker processes, each running an epoll event loop with non-blocking I/O, so idle connections cost little memory and no threads.
Why does putting NGINX in front of an application server help with slow clients? || NGINX buffers the application's response quickly over the fast local connection and then sends it to the slow client at the client's pace. The application thread is released sooner and can serve other requests.
Why does one worker per CPU core make sense? || Each worker is a single-threaded event loop that can use a core fully. More workers than cores only adds context switches, while fewer leaves cores idle. The number of connections is set by worker_connections, not by the number of workers.
An application has 100 threads and each request takes 50 ms of work, but a slow client keeps a thread for 1 s without a proxy buffer. What is the throughput in each case? || With a buffering proxy the thread is busy 50 ms, so 100 / 0.05 = 2,000 requests per second. Without it each request holds the thread for about 1.05 s, so about 100 / 1.05 ≈ 95 requests per second, roughly twenty times less.
When would you choose NGINX Plus or Envoy rather than open-source NGINX? || When upstream servers change often and you need runtime updates without reloads, active health checks and richer metrics. Choose NGINX Plus if you want to keep NGINX with support; choose Envoy if you want a fully API-driven proxy, for example in a service mesh.

@@ envoy
value: Envoy is a proxy that sits next to a service, or at the edge of a system, and handles the network traffic for it. It understands TCP, TLS, HTTP/1.1, HTTP/2, HTTP/3 and gRPC. For every connection it can balance load across endpoints, retry failed requests, set timeouts, eject sick hosts, encrypt traffic with mutual TLS, and report detailed metrics, logs and traces. Its key property is that its configuration is not a file you edit: it is a set of live APIs, called xDS, that a control plane can change while traffic flows.
It was built at Lyft to solve a problem of microservices. When dozens of services are written in several languages, every team has to implement retries, timeouts, load balancing, TLS and metrics in its own client library, with its own bugs, and when a request is slow, nobody can see why. Envoy moves all of this out of the application into a separate process on the same host. The application talks to localhost, and Envoy does the hard parts of talking to the network. The same logic then works for every language and can be upgraded without changing application code.
For the layer above, Envoy is the data plane of the service mesh (L1): the sidecar proxy that Istio and others run beside each workload, receiving its configuration from a control plane through xDS. It also acts as an edge or gateway proxy (Envoy Gateway, Contour, Emissary, and Cilium's L7 features all use it). From load balancing (L1) it takes the algorithms and health logic, and applies them per request rather than per connection. From security architecture (L1) it takes the ideas of workload identity, mutual TLS and least privilege, and enforces them in the network path with certificates and authorization filters. It is written in modern C++ for predictable latency and memory use, which is why it can add a few hundred microseconds to a request, not milliseconds.
terms: xDS — the family of gRPC/REST APIs (listener, route, cluster, endpoint and secret discovery) through which a control plane configures Envoy at run time.
Listener — a port and address where Envoy accepts connections, with a chain of filters that process them.
Cluster — a named group of upstream endpoints that Envoy can send traffic to, with a load balancing policy.
Filter — a pluggable processing step in a connection or request path, such as TLS inspection, rate limiting, authentication or routing.
Sidecar — a proxy that runs beside each application instance and handles all of its network traffic.
Data plane and control plane — the data plane forwards traffic (Envoy); the control plane decides the configuration and pushes it (istiod, Envoy Gateway).
Outlier detection — passive health checking that removes an endpoint from the pool after it returns errors.
Circuit breaker — a limit on connections, pending requests or retries to a cluster, so that overload fails fast instead of piling up.
history: Matt Klein, an engineer at Lyft, started Envoy in 2015 and Lyft open-sourced it in September 2016. Lyft had grown from a monolith to many services in Python, PHP and Go, and its engineers could not tell, when a call failed, whether the cause was the network, the client library or the service. Klein's design goal was that the network should be transparent to applications and that problems should be easy to find. The first version already had the main features: an out-of-process proxy, HTTP/2 and gRPC support, rich stats, distributed tracing and dynamic configuration.
Adoption was fast. In 2017 Google, IBM and Lyft announced Istio, which put Envoy beside every pod, and Envoy joined the CNCF. It became the third project to graduate from the CNCF, in November 2018, after Kubernetes and Prometheus. Meanwhile the configuration protocol evolved from a simple REST/JSON API (v1) to gRPC streams and Protobuf (v2, then v3), and became a standard: gRPC clients with xDS support can use the same control planes without a proxy at all.
Over the years the project added HTTP/3 and QUIC, a WebAssembly extension model, dozens of filters, and a growing set of gateway projects built on it, including Envoy Gateway, the Kubernetes Gateway API implementation of the Envoy project. Cloud providers have built managed mesh and load balancing products on it too. As of October 2026 the current release line is 1.39. Releases come every quarter, and old lines go out of support after a short time, so users need a process to upgrade.
how: Envoy is built around four ideas: listeners with filter chains, clusters with load balancing, dynamic configuration, and a threading model without locks on the hot path.
A listener binds a port. When a connection arrives, Envoy runs listener filters (for example a TLS inspector that sniffs the server name), picks a filter chain, and runs network filters in order. The most important network filter for HTTP is the HTTP connection manager. It decodes HTTP/1.1, HTTP/2 or HTTP/3 into streams and runs a chain of HTTP filters on each request: authentication (JWT), external authorization, rate limiting, fault injection, Lua or Wasm code, and finally the router filter. The router matches the request by host, path, headers or other conditions (the route table), and then picks a cluster. Because Envoy works at the request level (L7), a long-lived HTTP/2 or gRPC connection can carry requests that go to many different backends. A plain TCP load balancer cannot do this. Other network filters proxy raw TCP, or speak protocols like Redis, MongoDB or Postgres.
A cluster is a group of endpoints. Envoy finds them from static config, DNS, or EDS (endpoint discovery service) pushed by the control plane. For the cluster, Envoy applies the load balancing logic (load balancing concept): round robin, least request (by default it picks two random hosts and sends the request to the one with fewer active requests, which is called power of two choices), ring hash and Maglev for consistent hashing, or random. It also runs active health checks (periodic probes) and outlier detection: after a set number of consecutive 5xx responses (the default is 5), a host is ejected for a base time (30 seconds by default) that grows with each ejection, with a cap on how many hosts can be ejected at once (10% by default). A panic threshold (50% by default) says that if too many hosts are unhealthy, Envoy ignores health status and spreads traffic across all, because sending everything to the few "healthy" hosts would kill them. Retries have limits: the number of retries, a timeout per try, and a retry budget, so that retries do not multiply the load during an incident. Circuit breakers cap concurrent connections, pending requests, requests and retries per cluster (1024 each and 3 retries by default), so that a slow backend causes fast failures rather than an unbounded queue.
Security (the security architecture concept) is built into the connection path. A cluster can require upstream TLS and a listener downstream TLS, and for mutual TLS both sides present certificates. The certificates and keys are delivered by SDS (secret discovery service), so they can be rotated without a restart; in a mesh they carry a workload identity, such as a SPIFFE ID, which the other side checks. Filters enforce authorization based on that identity, so that a rule can say "only the checkout service may call the payment service". Envoy itself becomes an enforcement point, and it must be protected as one.
Dynamic configuration is the defining feature. The control plane exposes xDS over gRPC streams. Envoy opens a stream, says what it already has, and the server sends updates for listeners (LDS), routes (RDS), clusters (CDS), endpoints (EDS) and secrets (SDS). ADS (aggregated discovery service) puts all of them on one stream so the server can order them: a new cluster must exist before a route that points to it, or requests would fail in the gap. The delta variant sends only changes, which matters in a mesh with thousands of endpoints that change often. Envoy applies the update without dropping connections: old connections drain while new ones use the new configuration.
The threading model avoids locks. A main thread handles xDS, admin, stats flushing and process management. Worker threads (by default one per hardware thread) each run their own event loop (epoll on Linux, via libevent) and own their connections for life. All workers accept on the same listening socket (using SO_REUSEPORT or a shared file descriptor). When the main thread receives a configuration update, it builds the new immutable configuration and posts it to every worker through thread-local slots, in a read-copy-update style, so workers never take a lock to read config. Hot restart lets a new Envoy process take over the listening sockets and share stats with the old one during an upgrade.
Finally, observability is part of the data path: every request updates counters, gauges and histograms per cluster and route, access logs are configurable, and trace headers are generated and propagated so that the proxy appears in a distributed trace. An admin interface shows clusters, health, config dumps and stats. Written in C++ (the cpp concept), Envoy uses its own memory-conscious buffer and arena types, avoids copies, and uses compile-time extension registration to keep the core small while allowing hundreds of extensions.

example: A request goes through Envoy in an Istio mesh. A "checkout" pod calls http://orders/api/v1/items. Traffic is redirected to its sidecar Envoy. The route for the host "orders" selects the cluster "orders", which currently has three endpoints from EDS: A with 12 active requests, B with 3 and C with 7.
With least request using two random choices, Envoy picks two hosts, for example A and C, compares 12 with 7 and chooses C. In other cases it might pick B and A, and choose B. Over time, the busiest host is selected only when it is drawn together with an even busier one, so load evens out without Envoy needing a global view or a lock. This is much more even than simple round robin when requests have very different durations.
The retry policy says: retry on 5xx, num_retries 2, per_try_timeout 2 s, overall timeout 5 s. The first try goes to C and returns 503 after 100 ms. Envoy retries on a different host (host selection can avoid hosts already tried), and picks B, which answers in 40 ms. The caller sees one successful response in about 140 ms. If all tries had failed, the worst case is bounded by the overall timeout of 5 s, and not by 3 × 2 s plus delays, because the overall timeout caps the total. A retry budget of, say, 20% of active requests keeps retries from creating a storm: if the backend is fully down, no more than about one in five extra requests is added.
Now host C starts failing. After 5 consecutive 5xx responses it is ejected for 30 seconds. The cluster has 3 hosts, and the default maximum ejection is 10%, but at least one host can always be ejected, so C leaves the pool. Traffic goes to A and B. After 30 seconds C returns to the pool, and if it fails again the second ejection lasts 60 seconds. Meanwhile the stats show upstream_rq_5xx, upstream_rq_retry and outlier_detection.ejections_active, so an engineer sees the effect immediately.
Finally, the control plane adds a fourth endpoint D after a scale-up. It sends an EDS update over the open gRPC stream. Within a second or so every sidecar adds D to its cluster, with no restart and no dropped connection. With 2,000 sidecars, istiod pushes this one small change to all of them, which is why delta xDS and limiting what each sidecar needs to know matter at scale.
intuition: A smart translator and traffic officer standing next to every service: the service speaks plainly to the officer, and the officer handles the road, the retries and the rules.
The design is natural because networking problems are the same for every service, and they are better solved once, outside the application, where they can be observed and changed by operators rather than application teams. Making the proxy configurable through an API, rather than a file, follows from the fact that in a dynamic cluster the set of services and endpoints changes every minute. The control plane knows what should be true; the proxy enforces it where the packets are.
mistakes: People often think Envoy is a service mesh. In fact Envoy is only the data plane proxy. A mesh also needs a control plane (such as Istio) that watches the cluster, issues certificates and writes xDS configuration. Running Envoy alone gives you a proxy with a very long static config file.
People often think Envoy is a replacement for every use of NGINX. In fact Envoy is excellent for dynamic L7 routing, but for serving static files or as a simple caching web server NGINX is simpler. Envoy's configuration is verbose, and it is meant to be generated.
People often think retries only improve reliability. In fact retries multiply load. If each of three layers retries twice, one failing call can create up to 27 attempts at the bottom service. Use retry budgets, retry only idempotent requests and on safe conditions, and keep retries at one layer.
People often think connection-level load balancing is enough for gRPC. In fact gRPC uses long-lived HTTP/2 connections that carry many requests, so an L4 balancer pins all traffic of a client to one backend. An L7 proxy such as Envoy balances each request.
People often think the sidecar is free. In fact each sidecar holds the whole configuration it receives (all clusters and endpoints by default), uses tens of MB of memory and some CPU, and adds two proxy hops to every call in a mesh. Scoping configuration to what each workload needs is a basic optimization.
friction: Configuration is large and deeply nested. A full Envoy config in YAML runs to thousands of lines, and one misplaced field can silently change behavior. That is the reason it is nearly always driven by a control plane, and debugging means reading config dumps and understanding how the control plane translated a simple policy into listeners, routes and clusters.
Resource cost is a real concern. In an Istio sidecar deployment, a proxy can use around 0.2 vCPU and 60 MB of memory for 1,000 requests per second, according to Istio's published tests, multiplied by every pod. Every request goes through two proxies (client side and server side), each adding some hundreds of microseconds to a few milliseconds depending on the filters. This is the cost that pushed projects toward node-level proxies (Istio ambient mode, Cilium).
Operational friction includes a fast release cadence with short support windows, so a platform team must upgrade regularly; security fixes in HTTP parsing or filters appear often. Debugging failures such as a 503 with response flags (UF, UH, NR, UC) requires knowing Envoy's vocabulary. Resource tuning (connection limits, buffer sizes, the number of worker threads, overload manager) is needed at scale. Because Envoy is an extensible platform, custom filters in C++ or Wasm are possible, but they are costly to maintain and can crash or slow the data plane.
practice: Do not write raw Envoy YAML for a fleet. Use a control plane or a Gateway API controller (Istio, Envoy Gateway, Contour) and learn how to read what it generates. The commands you need are the admin endpoints (/config_dump, /clusters, /stats) or istioctl proxy-config. Check response flags in access logs when you see a 503.
Set timeouts on every route, and keep a hierarchy: the caller's timeout must be longer than the sum of what it waits for. Set retries only for idempotent requests, with per-try timeouts and a retry budget. Keep outlier detection on with reasonable thresholds, and set circuit breaker limits so that an overloaded backend sheds load. For gRPC, use HTTP/2 end to end and let Envoy balance per request.
Scope the configuration each sidecar receives (in Istio, with the Sidecar resource or namespace isolation), because in a large mesh the size of the configuration, not the traffic, can dominate memory and push time. Watch xDS push latency and rejected updates (NACKs). Use the stats that matter: upstream_rq_time histograms, upstream_cx_overflow and upstream_rq_pending_overflow for circuit breaker hits, and health and ejection counts.
Plan for upgrades: pin a version, test with real traffic, and upgrade often, because security fixes arrive in every quarter. Prefer an Envoy build from a distribution that publishes security advisories (Istio, Envoy Gateway). Consider whether you need Envoy at all: for a small system with a few services, a library, a cloud load balancer or NGINX may be enough.
tradeoffs: Choose Envoy (usually through a mesh or gateway) when you have many services, need uniform mTLS, retries, traffic splitting and telemetry across languages, and can run a control plane; choose client libraries or a simple load balancer when you have a handful of services in one language. Envoy gives uniformity and operator control; it costs memory, CPU, latency and operational skill.
Choose sidecar Envoy when you need per-workload L7 policy and strong isolation per pod; choose node-level or shared proxies (ambient mode, Cilium) when sidecar overhead across thousands of pods is too high and L4 identity plus selective L7 is enough. The shared proxy lowers cost but changes the failure domain, because one proxy failure affects every pod on the node.
Choose Envoy at the edge (as an API gateway) when you want dynamic routes, gRPC and HTTP/3, and Kubernetes Gateway API; choose NGINX at the edge when static content, caching and a file-based configuration are enough. Choose a managed cloud load balancer when you do not want to operate the edge, at the price of fewer features and per-request fees.
Choose filters written in Wasm or Lua for small custom logic that must run on every request, and accept the extra CPU and the maintenance; choose to do that logic in an application or a dedicated service (using ext_authz or ext_proc to call out) when it is complex or changes often, and accept an extra network hop.
interview: Why does Envoy use xDS instead of a configuration file, and how does an update reach the data path without dropping traffic? || In a dynamic cluster endpoints and routes change constantly, so a file and reload do not scale. The control plane streams typed updates over gRPC. The main thread builds a new immutable config and posts it to the worker threads through thread-local slots; existing connections drain on the old config while new ones use the new one. ADS orders updates so dependencies exist first.
Explain how Envoy's threading model avoids lock contention. || Each worker thread runs its own event loop and owns its connections for their whole life, so connection state is not shared. Shared configuration is immutable and distributed to threads with thread-local storage, updated by the main thread posting a new version. Stats use per-thread counters aggregated by the main thread.
You see many 503s with the response flag UH, then UF. What does that suggest? || UH means no healthy upstream hosts, and UF means upstream connection failure. Together they suggest the endpoints are failing connections and were ejected or marked unhealthy, possibly leading to panic mode or no available hosts. Check endpoints, outlier ejections, health checks, readiness of pods, and the network path or mTLS settings.
A service calls another with 3 retries at each of 3 layers. What can go wrong, and how do you prevent it? || Retries multiply: up to 4 × 4 × 4 = 64 attempts reach the bottom service during an outage, turning a partial failure into overload (a retry storm). Retry at one layer, use retry budgets and per-try timeouts, make calls idempotent, and use circuit breakers and outlier detection.
Why is L7 balancing needed for gRPC? || gRPC multiplexes many requests on a few long-lived HTTP/2 connections. An L4 balancer chooses a backend per connection, so one client sends everything to one backend. An L7 proxy sees individual requests and balances each of them across endpoints.
What does least-request with two random choices do better than round robin? || It uses the actual number of active requests, so slow or busy hosts get fewer new requests, and it needs only a sample of two, not global state. Round robin ignores load and works badly when requests vary in cost or hosts differ in speed.

@@ grpc
value: gRPC is a framework for calling functions on another machine as if they were local. You describe a service in a Protocol Buffers file: the methods, and the fields of each request and response. A compiler generates client and server code in your language (Java, Go, Python, C++ and many more). The client calls a typed method; the framework turns the arguments into compact bytes, sends them over an HTTP/2 connection, runs the method on the server, and returns the typed result. It also supports streaming in one or both directions, deadlines, cancellation and metadata such as authentication tokens.
The problem it solves is the cost and the fragility of service-to-service communication. With JSON over HTTP/1.1, every team writes parsing code by hand, field names and types are only documented, a typo is found at run time, and each message repeats field names as text. With a shared schema and generated code, the contract is checked at compile time, messages are several times smaller and faster to parse, and every language gets the same behavior for timeouts, errors and streaming. In a system with hundreds of services, that consistency is the main benefit.
For the layer above, gRPC is the standard way that microservices (L1) call each other in many large systems. It is also used inside infrastructure tools on this map: Kubernetes components talk to etcd and to container runtimes over gRPC, Envoy receives its configuration by xDS over gRPC streams, Terraform core talks to providers over gRPC, and OpenTelemetry's OTLP protocol can run over gRPC. It stands on remote procedure calls and serialization (L3), which supplies the idea of a call that crosses the network and the Protobuf wire format, and on HTTP/2, which supplies multiplexed streams over one connection. Its origin is Stubby, the internal RPC system that Google had used for about a decade before gRPC was open-sourced in 2015.
terms: Protocol Buffers (Protobuf) — a schema language and a compact binary format for structured messages; each field has a number that identifies it on the wire.
Service definition — a .proto file that lists RPC methods with their request and response message types.
Stub — the generated client object; calling a method on it sends a request to the server.
Unary and streaming RPC — unary is one request and one response; server streaming, client streaming and bidirectional streaming send many messages in one or both directions.
HTTP/2 stream — an independent, ordered sequence of frames inside one HTTP/2 connection; many streams share the connection at once.
Deadline — an absolute time limit for a call, which is sent to the server and propagated to downstream calls.
Status code — one of 17 standard results (OK, DEADLINE_EXCEEDED, UNAVAILABLE, and others), returned in HTTP/2 trailers.
Channel — the client-side object that manages connections, name resolution and load balancing to a target.
history: Google had built an internal RPC system called Stubby in the early 2000s. All its services used it, and it handled an enormous number of calls per second. It was tied to Google's infrastructure, so it could not be released. When the company wanted a standard for open systems and mobile apps, it started again, using the new standard HTTP/2 (finalized in 2015, built on Google's own SPDY) as the transport. gRPC was announced and open-sourced in February 2015, reached version 1.0 in August 2016, and joined the Cloud Native Computing Foundation in 2017.
The adoption path followed the move to microservices and containers. Square, Netflix, Cisco, CoreOS (etcd v3, 2016) and others used it early. Kubernetes adopted it for the container runtime interface and storage interface, and Envoy chose gRPC for xDS. Language support grew to more than ten languages, with a C core (used by C++, Python, Ruby, PHP, C#) and separate native implementations for Go and Java.
The main gap was the browser, which cannot control HTTP/2 frames and trailers directly. gRPC-Web (2018) solved this with a modified protocol and a proxy. Later projects such as Connect (by Buf) offer a protocol that works in browsers and with gRPC. Another development is gRPC with xDS: clients load balance by talking to a control plane directly, without a sidecar proxy ("proxyless" gRPC). Protocol Buffers itself dates from Google in the early 2000s and was open-sourced in 2008.
how: A gRPC call has three layers: the contract (Protobuf), the message encoding (also Protobuf), and the transport (HTTP/2).
The contract is a .proto file. For example, a service OrderService has a method GetOrder(GetOrderRequest) returns (Order). Each message lists fields with a type and a number: int64 id = 1; string name = 2. The compiler protoc, with a gRPC plugin, generates classes for messages and a client stub and server base class. A server developer implements the method. A client developer calls it through the stub. Here the RPC concept from L3 does its work: the stub hides the network behind a function call, and the compiler guarantees that both sides agree on types.
The encoding is Protobuf's wire format. Each field is written as a key and a value. The key is (field number << 3) | wire type, as a varint, so the field names never go on the wire. Integers use varints: 7 bits of data per byte, with the high bit set when more bytes follow, so small numbers take one byte. Strings and nested messages are written with a length prefix. Fields with default values can be left out entirely. This is why a message is usually 3 to 10 times smaller than the same data in JSON and parses much faster, with no string matching. Schema evolution rules make it safe to change a contract: you may add new fields with new numbers, readers skip unknown fields, and you must never reuse or change the type of an existing number.
The transport is HTTP/2. A call is one HTTP/2 stream on a long-lived TCP connection. The client sends HEADERS with :method POST, :path /package.OrderService/GetOrder, content-type application/grpc, te trailers and optionally grpc-timeout, then DATA frames. Each message is framed with 5 bytes: one byte for compression flag and four bytes for the length, followed by the Protobuf bytes. The server answers with HEADERS, DATA frames with messages, and then trailers carrying grpc-status and grpc-message. Using trailers for status is what allows a stream of responses to fail in the middle with a proper error. HTTP/2 headers are compressed with HPACK, so the repeated path and content type of later calls cost only a few bytes. Many calls run at once as separate streams on the same connection, which avoids head-of-line blocking at the HTTP level and the cost of opening a new TCP and TLS connection per call. Flow control works per stream and per connection, with a default window of 64 KB that gRPC implementations grow automatically by measuring bandwidth and delay.
The four call types are different patterns of messages on one stream. Unary is request then response. Server streaming sends many responses, for example a stream of events. Client streaming sends many requests and gets one reply, for example an upload. Bidirectional streaming lets both sides send independently, for chat or telemetry. Streaming is possible because HTTP/2 streams are full-duplex.
Deadlines and cancellation are first-class. The client sets a deadline, which is sent as grpc-timeout. The server sees the remaining time and, when it calls another service, passes the deadline on, so the whole chain stops when the time is over. If the client cancels, a RST_STREAM frame tells the server to stop work. This is what makes timeouts work across a chain of microservices (the microservices concept): each hop knows how much time is left.
Load balancing is where HTTP/2 changes the rules. Because one connection carries many requests for a long time, a classic layer-4 balancer, which decides per connection, sends all calls from a client to a single backend. There are two answers. Client-side balancing: the channel resolves a name (through DNS or xDS) to many addresses, opens a subchannel to each, and picks one per call with round_robin or another policy. Or a layer-7 proxy such as Envoy terminates HTTP/2 and distributes each request. Keepalive pings detect dead connections, and servers can send GOAWAY so clients reconnect and spread over new instances.
Security uses TLS on the channel and per-call credentials such as tokens in metadata. Interceptors (middleware) on both sides add logging, metrics, tracing and authentication. Health checking and reflection are standard services. Errors use the standard status codes, and richer details can be attached as Protobuf messages.

example: Define a message with two fields: int64 id = 1 and string name = 2. We send id = 150 and name = "hi".
Encode the first field. The key is (1 << 3) | 0 = 8, wire type 0 meaning varint, so the first byte is 0x08. The value 150 in binary is 1001 0110. Varints store the low 7 bits first: the low 7 bits are 001 0110 (22), and the remaining bit is 1. The first byte sets the high bit to say "more follows": 1001 0110 = 0x96. The second byte is 0000 0001 = 0x01. So field 1 is the three bytes 08 96 01.
Encode the second field. The key is (2 << 3) | 2 = 18 = 0x12, wire type 2 meaning length-delimited. Then the length 2 (0x02), then the bytes of "hi" (0x68 0x69). So field 2 is 12 02 68 69, four bytes. The whole message is 7 bytes: 08 96 01 12 02 68 69.
The same data in JSON is {"id":150,"name":"hi"}, which is 22 bytes, more than three times larger, and the receiver must parse numbers from text and match key names. In gRPC, the message gets a 5-byte prefix: 00 00 00 00 07 (not compressed, length 7), so 12 bytes go into HTTP/2 DATA frames. The headers of the first call (path, content type, user agent) may cost 100 bytes or so. With HPACK, the second call on the same connection sends the same headers in a handful of bytes, since the table already holds them. So 1,000 calls per second of this small message use around 1,000 × (12 + about 15) bytes, roughly 27 KB/s of payload and headers, plus HTTP/2 and TLS framing. The same calls over HTTP/1.1 with JSON would send hundreds of bytes of headers for each request.
Now a load balancing scenario. A client has one channel to "orders.internal:443". If a layer-4 balancer is in front of 3 backends, the client opens one connection and all calls go to the backend that accepted it, so after a scale-up from 3 to 6 backends, the new three get nothing from existing clients. With client-side round_robin and DNS or xDS returning 6 addresses, the channel opens 6 subchannels and alternates calls over them: each backend gets 1/6 of the calls. If a backend fails, the subchannel goes to a transient failure state and is skipped.
intuition: A phone call with a printed phrase book: both sides hold the same typed contract, so what travels on the line is only numbers and short codes.
The design is natural because two programs that talk a lot should agree on the meaning once, at build time, instead of describing it in every message. The schema moves names and types out of the message, so the message gets small. HTTP/2 moves the cost of connections out of the call, so the call is cheap. Generated code moves the work of serialization out of the programmer's hands, so a remote call looks like a local one, with the difference that you must still plan for failure, delay and deadlines.
mistakes: People often think gRPC makes a remote call as safe as a local call. In fact the network still fails, delays and duplicates. Every call needs a deadline, and a retry policy only for idempotent methods. The "looks like a function" interface is convenient, not a guarantee.
People often think gRPC is always faster than REST with JSON. In fact the gain comes from smaller messages, cheaper parsing and connection reuse, and it matters when messages are small and numerous. For large payloads, slow backends or simple low-traffic APIs, the difference is small, and the cost is harder debugging and weaker browser support.
People often think a layer-4 load balancer is enough for gRPC. In fact a connection-level balancer pins a long-lived HTTP/2 connection, and so all its calls, to one backend. You need client-side balancing or an L7 proxy that understands HTTP/2.
People often think you can change a .proto file freely. In fact field numbers are the identity of a field on the wire. Reusing a number for another meaning, or changing its type, silently corrupts data for old readers or writers. Add new numbers, mark old ones as reserved, and never reuse them.
People often think gRPC works directly from browsers. In fact browser JavaScript cannot read HTTP/2 trailers or control framing, so you need gRPC-Web with a proxy, or a protocol such as Connect that is designed for browsers.
friction: Debugging is harder than with JSON and curl. Messages are binary, so you need tools such as grpcurl, server reflection, or a proxy that decodes Protobuf, and logs of payloads need schema-aware formatting. Contracts need discipline: a shared repository of .proto files, a linter and a breaking-change detector (such as buf) in CI, or you will break clients without noticing.
HTTP/2 brings its own problems. One TCP connection means that packet loss blocks all streams on it (head-of-line blocking at the TCP level), which hurts on lossy mobile networks; HTTP/3 would fix this, but gRPC over HTTP/3 is not yet a standard option. Long-lived connections complicate load balancing, rolling deployments (clients must reconnect after GOAWAY) and idle timeouts in middle boxes. Default limits, such as the 4 MB maximum message size in several implementations, surprise people who send large payloads; streaming or chunking is the answer. Proxies and gateways in the path must support HTTP/2 end to end and trailers, which not all do.
Browser and public API use needs gRPC-Web, a Connect protocol, or a REST translation layer (such as gRPC-Gateway or Envoy's transcoder). Streaming adds hard problems: back pressure, ordering, partial failure and resuming. Finally, the generated code adds build complexity in every language, and version mismatches between protoc, plugins and runtime libraries are a frequent annoyance.
practice: Always set a deadline on the client, and propagate the incoming deadline downstream. Choose a retry policy with care: retries only on UNAVAILABLE (and maybe a few others) for idempotent methods, with exponential backoff and a budget. Return the right status code, such as INVALID_ARGUMENT, NOT_FOUND or FAILED_PRECONDITION, rather than UNKNOWN for everything, so clients and dashboards can react correctly.
Design the schema for the future. Use a separate request and response message for each method, even if they are empty today, so you can add fields later. Keep field numbers 1 to 15 for common fields (they take one byte for the key). Reserve removed numbers and names. Use enums with a zero value of UNSPECIFIED. Run a breaking-change check in CI.
For load balancing, use headless Services plus round_robin client-side balancing, or put Envoy, a mesh or a cloud L7 load balancer in front. Enable keepalive pings with sensible intervals, and set a maximum connection age on servers so that clients rebalance after deploys. Use interceptors for metrics, tracing (OpenTelemetry) and authentication, and expose the standard health service for Kubernetes probes.
Watch message sizes and use streaming for large or unbounded data. Compress only when payloads are large and CPU is available. For browsers and external partners, offer a REST or Connect endpoint generated from the same proto. Keep a tool like grpcurl, plus reflection in non-production environments, to explore services quickly.
tradeoffs: Choose gRPC for internal service-to-service calls when you control both sides, care about latency and bandwidth, and want typed contracts and streaming; choose REST with JSON for public APIs, browser clients and partners, where readability, caching and tooling matter more than efficiency. The price of gRPC is a build step, binary debugging and weaker HTTP caching; the price of REST is larger messages and informal contracts.
Choose gRPC over a message queue such as Kafka when the caller needs an answer now and a result; choose a queue when work can be asynchronous, you need buffering, replay or fan-out to many consumers, or the receiver may be down. gRPC streaming is not a durable log: when a connection breaks, the data in flight is gone.
Choose client-side load balancing when you want the lowest latency and no extra hop and can manage the client library versions; choose a proxy or mesh (Envoy, Istio) when you want uniform policy, many languages and central control, at the cost of an extra hop and more infrastructure. Proxyless gRPC with xDS gives a middle path with a control plane but no sidecar.
Choose Protobuf when schema evolution and compactness matter; choose JSON when humans read the messages, and Avro or others when your data ecosystem (such as Kafka with a schema registry) is built around them. Choose bidirectional streaming only when you need independent flows in both directions; plain unary calls are easier to retry, balance and observe.
interview: Why does gRPC need special load balancing, and what are the options? || HTTP/2 multiplexes many calls on one long-lived connection, so an L4 balancer that decides per connection sends all calls from a client to one backend. Options: client-side balancing with a resolver (DNS or xDS) and round_robin over subchannels, an L7 proxy such as Envoy that balances per request, or a lookaside balancer. Also use max connection age and GOAWAY to rebalance after deploys.
How do deadlines work across a chain of services A to B to C? || A sets a deadline, sent as grpc-timeout. B sees the remaining time and uses it as the deadline for its call to C, so the whole chain stops when time is up. If A cancels, an RST_STREAM travels and servers should stop work. Without propagation, C may keep working for a caller that is already gone.
How does Protobuf make messages small, and how do you evolve a schema safely? || Field names are replaced by numbers, integers use varints, defaults are omitted, and strings are length-prefixed. For evolution, add fields with new numbers, never change a field's type or reuse a number, reserve removed ones, and rely on readers skipping unknown fields. Use a breaking-change linter in CI.
A gRPC service sees UNAVAILABLE spikes during every deployment. What do you check? || Whether servers drain: send GOAWAY and finish in-flight calls before exit, with readiness probes removing the pod first. Check client retry settings, keepalive and idle timeouts, connection age, DNS or xDS refresh time, and whether the proxy in front supports graceful HTTP/2 drain.
When is gRPC a poor choice? || For browser-facing or public APIs, where gRPC-Web or REST is easier; when you need HTTP caching or easy debugging with curl; for asynchronous, durable workloads where a queue is better; and on lossy networks where TCP head-of-line blocking hurts all streams.
What is the retry risk with gRPC, and how do you limit it? || Retrying non-idempotent calls can duplicate effects such as double payments, and retries at several layers multiply load. Retry only idempotent methods or use idempotency keys, retry only on safe codes like UNAVAILABLE, use backoff and retry budgets (throttling), and keep retries at one layer.
quiz: What do the 5 bytes before each gRPC message mean? || One byte says whether the message is compressed, and four bytes give its length. They let the receiver split a stream of DATA frames into messages.
Why is a gRPC message usually smaller than JSON? || Field names are replaced by small numbers shared through the schema, integers use variable-length encoding, and default values can be omitted. No quotes, braces or repeated key names are sent.
Why do all calls of one client go to a single backend behind an L4 balancer? || The client uses one long-lived HTTP/2 connection for all calls, and an L4 balancer picks a backend only when the connection is made. Per-request balancing needs a client-side policy or an L7 proxy.

When would you choose REST/JSON instead of gRPC for a new API? || When clients are browsers or external partners, when you want easy debugging, HTTP caching and wide tooling, or when traffic is low enough that efficiency does not matter. Use gRPC inside your platform where you control both sides.

@@ prometheus
value: Prometheus is a monitoring system that keeps numbers over time. Every few seconds it visits each service you run, reads a page of current metric values (requests served, errors, queue length, memory used), and stores them with a timestamp in its own time-series database. You then ask questions in its query language, PromQL, such as "what is the error rate per service over the last 5 minutes?", and you write alert rules that fire when an answer crosses a limit. It became the standard metrics system for Kubernetes and cloud-native systems because it fits their shape: many small, short-lived, constantly changing instances.
Two ideas make it different from older tools. First, the data model: a metric is a name plus labels, for example http_requests_total{service="orders", status="500"}. Every unique set of labels is its own time series, so you can slice and add up by any label at query time without deciding in advance. Second, the pull model: Prometheus fetches metrics from targets over HTTP, and it finds targets by asking Kubernetes or a cloud API. A target that does not answer is visibly down (the built-in up metric becomes 0), so monitoring and discovery are one mechanism.
It stands on observability (L1), where metrics are one of three signals beside logs and traces: metrics are cheap, aggregated and good for alerting and trends, while logs and traces explain individual events. It stands on Go (L0), which gave it a single static binary with good concurrency for scraping thousands of targets. For the layer above, Prometheus is what dashboards (Grafana), alerting (Alertmanager, PagerDuty), autoscaling (Kubernetes custom metrics) and SLO tracking are built on. A single server stores everything locally and does not scale out by itself; systems such as Thanos, Cortex and Mimir add long-term storage and horizontal scale.
terms: Time series — a sequence of (timestamp, value) pairs for one metric with one exact set of labels.
Label — a key-value pair attached to a metric (such as pod="orders-7f9") that splits it into separate series.
Scrape — one HTTP request from Prometheus to a target's /metrics endpoint to read all its current values.
Counter, gauge, histogram — a counter only goes up (requests); a gauge goes up and down (memory); a histogram counts observations in buckets (latency).
PromQL — the query language for selecting series, computing rates and aggregating by labels.
Cardinality — the number of distinct time series; it is the number of label combinations, and it controls memory use.
Alertmanager — a separate service that receives alerts from Prometheus, groups, deduplicates, silences and routes them to people.
Remote write — a protocol to stream samples from Prometheus to another long-term storage system.
history: Prometheus began at SoundCloud in 2012. The company had moved to many small services, and its existing tools (StatsD and Graphite) could not slice data by many dimensions or query it flexibly. Matt Proud and Julius Volz, who had worked at Google, built a system inspired by Borgmon, Google's internal monitoring system for Borg, which is described in the "Practical Alerting from Time-Series Data" chapter of the Google SRE book. Borgmon's ideas were: time series with labels, collection by scraping, and rules that compute new series.
Prometheus was released as open source in 2012, announced more widely in early 2015, and joined the CNCF in 2016 as its second project after Kubernetes. It graduated in August 2018. Version 1.0 appeared in 2016. Version 2.0 (November 2017) replaced the storage engine with a new time-series database written by Fabian Reinartz, with blocks, a write-ahead log and an inverted index, which brought better compression and made high churn (Kubernetes pods that come and go) practical. The compression is based on the Gorilla paper from Facebook (2015), using delta-of-delta timestamps and XOR-encoded floating point values.
Around the core grew an ecosystem: exporters for systems that do not expose metrics (node_exporter for Linux hosts), client libraries in many languages, the OpenMetrics text format, Grafana for dashboards, and long-term storage projects (Thanos from Improbable, Cortex from Weaveworks and Grafana Labs, and Mimir, 2022). Prometheus 3.0 was released on 14 November 2024, the first major version in seven years, with a new UI, UTF-8 metric and label names, native OpenTelemetry (OTLP) ingestion, and Remote Write 2.0. As of October 2026 the current release is 3.14, and 3.13 is a long-term-support line.
how: Prometheus is a loop of discover, scrape, store, evaluate and query.
Discovery. The server has a list of scrape jobs. For each one, service discovery finds targets: Kubernetes (pods, services, endpoints), cloud APIs (EC2, GCE, Azure), Consul, DNS or static lists. Relabeling rules then filter the targets and turn discovery metadata into labels (the namespace, pod name, app label). This is how a new pod starts being monitored without anyone editing configuration.
Scrape. At each interval (the default is one minute, and 15 or 30 seconds is common) a scrape worker sends an HTTP GET to the target's /metrics page. The response is plain text, one line per series, for example http_requests_total{method="GET",code="200"} 1027. The target does not store history; it only exposes current values, which are kept in memory by a client library. Prometheus attaches the scrape time as the timestamp, adds target labels (job, instance), and appends the samples. It also records synthetic series: up (1 if the scrape worked) and scrape_duration_seconds. Because Prometheus initiates the scrape, it knows immediately when a target stops answering.
Storage. Each sample is a 64-bit timestamp (in milliseconds) and a 64-bit float. Incoming samples go first into the head block in memory and are also appended to a write-ahead log on disk for crash recovery. Samples of one series are grouped in chunks of about 120 samples, compressed with the Gorilla scheme: timestamps are stored as the difference of differences (with regular scrapes this is almost always zero, and takes one bit), and values are XORed with the previous value (an unchanged value is a single bit, and slowly changing values share many bits). The result is roughly 1 to 2 bytes per sample on average, compared with 16 bytes raw. Every two hours the head is written to disk as an immutable block that contains chunks, an index and metadata. The index is an inverted index: for each label pair (such as job="api") it keeps a sorted list of series IDs (a postings list), and a query for several labels intersects these lists quickly. Background compaction merges small blocks into larger ones, and old blocks are deleted after the retention period (15 days by default).
Query. PromQL selects series by label matchers, works on instant vectors (one value per series at a time) and range vectors (a window of samples per series), and applies functions and aggregations. The central function is rate(): rate(http_requests_total[5m]) takes the samples of a counter over 5 minutes, handles counter resets when a process restarts, and returns the average per-second increase. sum by (service) (...) then adds series that share a label value. histogram_quantile(0.99, ...) estimates a percentile from histogram buckets. Because queries are evaluated against label indexes and compressed chunks, a query over thousands of series and a few hours returns in milliseconds to seconds.
Rules and alerts. The server evaluates recording rules (which precompute expensive expressions into new series) and alerting rules at a fixed interval. An alert rule has an expression, a "for" duration (the condition must hold that long before firing, to avoid flapping), and labels and annotations. Firing alerts are sent to Alertmanager, which groups related alerts, removes duplicates, applies silences and inhibition rules, and routes to receivers such as PagerDuty, Slack or email. This split keeps the decision of what is wrong in Prometheus and who to notify in Alertmanager.
Metric types and staleness. A counter is one number that only increases; a client library keeps it in memory and resets it to zero when the process restarts, which is why rate() must handle resets. A gauge is a number that can go up and down, such as memory in use. A histogram is not one series but many: one counter per bucket (the _bucket series, each with an "le" label for the upper bound), plus _sum and _count. Because buckets are cumulative counters, they can be added across pods and across time, and histogram_quantile() then finds the bucket where the wanted percentile falls and interpolates inside it. When a series stops appearing in scrapes (a pod was deleted), Prometheus writes a special stale marker, so queries stop returning the old value after one scrape interval instead of carrying it forward for five minutes.
Scale and extension. One Prometheus server is a single process with local disk. It scales vertically, to a few million active series on a large machine. For high availability, teams run two identical servers scraping the same targets. For global views and long retention, they use remote write to Mimir, Thanos (which uploads blocks to object storage such as S3) or Cortex-like systems. The observability concept explains why this design is chosen: metrics are small aggregated numbers, cheap enough to keep for months, while per-request detail belongs to logs and traces.

example: Take a service "orders" with 20 pods. Each pod exposes http_requests_total with labels method (5 values), status class (4 values: 2xx, 3xx, 4xx, 5xx) and handler (50 values). Each pod creates up to 5 × 4 × 50 = 1,000 series, though in practice many combinations never happen. Say 600 do. With 20 pods, that is 12,000 series. A latency histogram with 12 buckets per handler, method and status class would add 12 more series for each combination, so about 144,000 more. So one service already has about 150,000 series. Prometheus holds the active series in memory, at roughly 2 to 4 KB each, so this one service costs about 450 MB of RAM. This is the kind of arithmetic you do before adding a label.
Now the storage arithmetic. Suppose the server holds 1,000,000 active series and scrapes every 15 seconds. That is 1,000,000 / 15 ≈ 66,700 samples per second. Per day: 66,700 × 86,400 ≈ 5.76 billion samples. At about 1.5 bytes per sample, that is about 8.6 GB per day, and 15 days of retention needs about 130 GB of disk. Raw, at 16 bytes per sample, it would be 92 GB per day, about ten times more. This is why the Gorilla compression matters.
Next, a query. The counter shows the values 1000 at t=0, 1150 at t=15 s, 1300 at t=30 s, and so on, increasing by 150 every 15 seconds. rate(http_requests_total[1m]) looks at the samples in the last minute, (about four of them), computes the increase divided by the time span, and returns about 150 / 15 = 10 requests per second. If the pod restarts and the counter falls from 2,200 to 40, rate() sees the drop, treats it as a reset, and adds the missing increase instead of reporting a large negative number. Rule of thumb: use a range of at least four times the scrape interval so that the window always contains enough samples.
Finally, an alert: the expression sum(rate(http_requests_total{status="5xx"}[5m])) / sum(rate(http_requests_total[5m])) > 0.05 with for: 10m. If the error ratio is above 5% for ten minutes, the alert fires and goes to Alertmanager. If another alert for the same service also fires, Alertmanager groups them into one notification.
intuition: A meter reader who walks the same route every fifteen seconds, writes each number in a ledger with the time, and can later tell you how fast each meter is turning.
The pull design is natural for dynamic systems because the party with the best knowledge of what exists is the discovery system, not the application. The monitored service only exposes its current state; it has no knowledge of the monitoring system, so it cannot overload it or break when it is down. Labels make the data model natural for the same reason: the questions you will ask during an incident are not known in advance, so you keep dimensions and aggregate at query time. Counters, which only increase, make aggregation and loss tolerant: if a scrape is missed, the next value still carries the total, so the rate is still right.
mistakes: People often think Prometheus is a long-term data warehouse. In fact the local storage is designed for recent operational data (days to weeks) on one node. It is not replicated or horizontally scalable. For months or years, and for global views, you need remote write to Thanos, Mimir or a similar system.
People often think it is fine to add any label, such as user_id or request_id. In fact each distinct value creates a new time series with its own memory and index cost. A label with a million values multiplies the series count a million times, and the server runs out of memory. Per-request detail belongs in logs and traces.
People often think pull is better than push, or the other way around, in all cases. In fact pull makes discovery and health visible and is simple for long-running services, but it is awkward for short-lived batch jobs that finish before the next scrape. Those use the Pushgateway or write results at the end, and other systems (including OpenTelemetry's OTLP push) fit other cases.
People often think averages of a metric are enough. In fact an average hides the tail. Use histograms and histogram_quantile for latency, and know that the percentile is estimated from bucket boundaries, so it is only as accurate as the buckets you chose. Averaging percentiles from different instances is mathematically wrong; aggregate the buckets first.
People often think rate() gives exact per-second values. In fact it is an estimate over a window, extrapolated to the window edges, and it can be slightly off or jumpy when samples are sparse. For alerts, use windows long enough for several samples.
friction: Cardinality is the main operational limit. Memory for the head grows with the number of active series, and the churn caused by short-lived pods (new label values every deploy) adds to index size. A bad label can take down the monitoring system just when you need it, so teams set limits per scrape (sample_limit, label_limit) and review new metrics.
A single server has no clustering. High availability means two independent servers with duplicated data, and alert rules evaluated twice and deduplicated by Alertmanager. Long retention, global queries across clusters, and multi-tenancy need extra systems, each with its own storage, compaction and cost. Queries over long ranges and many series can be slow and memory-hungry, and recording rules are needed to keep dashboards fast.
Semantics need care. Counters reset, gauges sampled at intervals miss spikes between scrapes, and histogram buckets must be chosen before you know the data (native histograms, introduced in version 2.40 and still experimental when 3.0 launched, aim to remove this problem). PromQL has a learning curve, with subtle rules about staleness, offsets and vector matching. The pull model needs network reachability from Prometheus to every target, which is hard across firewalls and clusters. Finally, alert design is a human problem: too many alerts cause fatigue, and Prometheus gives the tools but not the judgment.
practice: Name metrics well: use base units (seconds, bytes), a _total suffix for counters, and a prefix per subsystem. Pick labels with a small, bounded set of values. Before adding a label, estimate the series count as the product of its values; before adding a histogram, remember it multiplies series by the number of buckets.
Instrument with the four golden signals (latency, traffic, errors, saturation) for services, and the USE method (utilization, saturation, errors) for resources. Use histograms for latency with buckets around your SLO thresholds. Use the client libraries rather than hand-written text, and expose a /metrics endpoint on a separate port from the public one.
Alert on symptoms that users feel (error ratio, latency SLO burn rate) rather than every cause (CPU at 80%). Use "for" durations, multi-window burn-rate alerts, and route by severity with Alertmanager. Every alert needs a runbook link. Use recording rules for expensive queries used by dashboards and alerts, and name them with the level:metric:operation convention.
For scale, set a retention that matches disk, monitor Prometheus itself (prometheus_tsdb_head_series, scrape duration, WAL size, rule evaluation time), and set sample limits. For Kubernetes, use kube-state-metrics and node_exporter, and the Prometheus Operator (ServiceMonitor objects) for configuration. For retention beyond weeks, use Thanos or Mimir with object storage, and keep Prometheus as the local collector. When you need OpenTelemetry metrics, Prometheus 3 can ingest OTLP directly, or you can use the OpenTelemetry Collector to export in Prometheus format.
tradeoffs: Choose Prometheus when your systems are dynamic services that you can scrape, you want a flexible label model and strong alerting, and a few million active series per server are enough; choose a managed metrics service (Amazon Managed Prometheus, Datadog, Grafana Cloud) when you do not want to run storage and scaling yourself, and accept per-series or per-sample prices. The price of running your own is operations; the price of managed is cost, and sometimes limits on labels.
Choose pull when targets are long-running and discoverable, and you want automatic detection of down targets; choose push (Pushgateway, OTLP or remote write from an agent) for short-lived jobs, devices behind NAT, or when firewall rules prevent inbound scraping. Push gives up the free "is it alive" signal; pull gives up reach.
Choose Prometheus with Thanos or Mimir when you need long retention, a global view and high availability; choose plain Prometheus when one cluster and weeks of retention are enough. Each added layer brings object storage cost, more components and more things that can fail, but keeps the same PromQL.
Choose metrics for alerting, trends and capacity planning, because they cost bytes per sample regardless of traffic; choose logs or traces for explaining a single request, since they cost bytes per event and grow with traffic. Many teams use metrics to find the problem, traces to locate it, and logs to explain it, with OpenTelemetry tying the three together.
Choose VictoriaMetrics or a similar engine when Prometheus memory per series is a bottleneck and you want cheaper storage with the same query model; choose the original when you want the reference behavior and the widest ecosystem support.
interview: Why does Prometheus use a pull model, and when does that break down? || Pull lets the server own discovery, scrape timing and health: an unreachable target shows up=0, and services need no knowledge of the monitor. It breaks for short-lived jobs that end before a scrape, for targets behind NAT or firewalls, and for very large fleets where the server needs network access to everything. Use the Pushgateway for batch jobs, or agents with remote write.
A Prometheus server runs out of memory after a deploy. How do you investigate? || Look at prometheus_tsdb_head_series and its growth rate. Find the top metrics and labels by series count (the TSDB status page or topk(count by (__name__))). A new label with high cardinality, or pod churn creating new series with each deploy, is the usual cause. Drop or relabel the label, add sample limits, and move detail into logs and traces.
How does Prometheus store samples so compactly? || Samples of a series are grouped in chunks. Timestamps use delta-of-delta encoding, which is zero for regular scrapes and costs about a bit; values are XORed with the previous value, so unchanged or similar values need few bits. The result is roughly 1 to 2 bytes per sample instead of 16. Data is held in a head block with a write-ahead log, then flushed into immutable two-hour blocks.
What is the difference between rate() and irate(), and which do you use for alerting? || rate() averages the per-second increase over the whole window; irate() uses only the last two samples, so it shows spikes but is noisy. Use rate() with a window of at least four scrape intervals for alerts and most dashboards, and irate() only for zoomed-in views of fast-moving counters.
How do you compute a 99th percentile latency across 50 pods? || Use histograms: histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))). Sum the buckets across pods first, and then take the quantile. Averaging each pod's 99th percentile is wrong. Accuracy depends on bucket boundaries, so place buckets near the SLO limit.
How would you design monitoring for 30 clusters with a year of retention? || One Prometheus (or agent mode) per cluster for scraping and local alerting, remote write or Thanos sidecars to a central store (Mimir or Thanos with object storage) for long retention and global queries, with downsampling or recording rules to control cost. Keep critical alerts evaluated locally, so they work even if the central store is down. Enforce cardinality limits per tenant.
quiz: What makes up a time series in Prometheus? || A metric name plus a specific set of label values, with a sequence of timestamped samples. Changing any label value creates a different series.
Why does a high-cardinality label such as user_id hurt Prometheus? || Each distinct value is a separate series that needs memory in the head block and entries in the index. A million values means a million series, which can exhaust memory and slow queries.
How does Prometheus compress timestamps and values? || Timestamps are stored as delta-of-delta, which is almost always zero for regular scrapes. Float values are XORed with the previous value, so equal or similar values use very few bits. This is the Gorilla scheme and gives about 1 to 2 bytes per sample.
A server has 2 million active series scraped every 30 s with 1.5 bytes per sample. How much disk does one day need? || Samples per second = 2,000,000 / 30 ≈ 66,700. Per day: 66,700 × 86,400 ≈ 5.76 billion samples × 1.5 bytes ≈ 8.6 GB per day.
When would you choose push instead of Prometheus's usual pull? || For short-lived batch jobs that end before a scrape, for devices behind NAT or firewalls, or when an agent forwards data to a central store using remote write or OTLP. Pull is better for long-running, discoverable services.

@@ otel
value: OpenTelemetry (OTel) is a vendor-neutral standard and a set of tools for producing and moving telemetry: traces, metrics and logs. Your code, or an agent attached to it, creates telemetry through one API. A Collector process receives it, processes it, and sends it to whichever back end you choose (Jaeger, Tempo, Prometheus, Datadog, Honeycomb, and others) using one wire protocol, OTLP. You instrument once, and you can change the back end later without touching application code.
The problem it solves is lock-in and fragmentation. Before OTel, each monitoring vendor had its own agent and library, and open-source projects had two competing standards for traces (OpenTracing and OpenCensus). Changing vendor meant re-instrumenting every service. Worse, in a system of many services a trace only works if every service passes the same trace identifiers to the next one, so mixed standards broke traces at the boundaries. OTel defines the identifiers, the propagation format (W3C Trace Context), the names of attributes (semantic conventions such as http.request.method), the SDKs, and the protocol. Every service speaks the same language about "what happened during this request".
It stands on observability (L1). Observability says that to understand a running system from outside you need several kinds of evidence: metrics for trends and alerts, logs for detailed events, and traces for the path of one request through many services. OTel is the standard way to produce all three and to link them: a log line and a metric exemplar can carry the trace ID of the request that caused them. For the layer above, OTel is what dashboards, tracing back ends, anomaly detection, and cost-control tools consume. The project graduated in the CNCF in May 2026 and is one of the most active projects in the foundation.
terms: Trace and span — a trace is the record of one request across services; it is a tree of spans, and each span is one timed operation with a name, attributes and a parent.
Context propagation — passing the trace ID and parent span ID from one service to the next, usually in HTTP headers or message headers.
W3C Trace Context — the standard traceparent header that carries trace ID, parent span ID and flags between services.
OTLP — the OpenTelemetry Protocol, a Protobuf-based format for traces, metrics and logs, sent over gRPC (port 4317) or HTTP (port 4318).
Collector — a standalone service that receives telemetry, processes it (batching, filtering, sampling) and exports it to one or more back ends.
Instrumentation — code that creates telemetry: written by hand with the API, or added automatically by an agent or library hook.
Sampling — deciding which traces to keep, because keeping all of them is too expensive.
Semantic conventions — agreed names and meanings for attributes, such as service.name, http.response.status_code and db.system.
history: Distributed tracing started inside companies. Google described Dapper in 2010, a system that followed requests across thousands of services with low overhead and sampling. Twitter's Zipkin (2012) and Uber's Jaeger (2015) were open-source followers. A shared API was needed so that libraries could be instrumented once, and OpenTracing (2016, CNCF) provided one for traces only. Google and Microsoft then created OpenCensus (2018) with both traces and metrics and a different design. For two years, library authors had to choose between two standards.
In May 2019 the two communities announced they would merge into OpenTelemetry. The goal was to take the API of OpenTracing, the libraries and collector ideas of OpenCensus, and add a complete specification, a wire protocol and a Collector. It joined the CNCF as a sandbox project in 2019. In the following years, the tracing specification reached 1.0 in 2021, metrics stabilized after, and logs were added as a third signal by building on existing logging libraries rather than replacing them. The W3C Trace Context specification became a W3C Recommendation in 2020, so propagation is also a web standard.
OTel grew into one of the busiest CNCF projects, with SDKs in a dozen or more languages, automatic instrumentation for popular frameworks, a Collector with hundreds of components, and support from almost every observability vendor. The CNCF announced its graduation on 21 May 2026. Newer work includes continuous profiling as a fourth signal (in early public alpha at the time of writing), eBPF-based automatic instrumentation for compiled languages such as Go, and a push for the semantic conventions to become stable across areas such as HTTP, databases and messaging.
how: OTel has four parts that work together: the API and SDK, the data model, context propagation, and the Collector with OTLP.
The API and SDK are separate on purpose. Library authors depend only on the API, a small set of interfaces such as Tracer, Meter and Logger. With no SDK installed, the API calls do nothing at almost zero cost. The application owner adds the SDK, which implements the API, and configures it: which exporter, which sampler, which resource attributes (service.name, the pod, the version). This split means a library like an HTTP client or a database driver can be instrumented once without forcing any telemetry choice on its users. In many languages there is also automatic instrumentation: the Java agent rewrites bytecode at startup, Python and Node.js patch libraries, and eBPF-based tools attach to compiled programs, so that common frameworks produce spans without code changes.
The data model for traces is a span. A span has a 16-byte trace ID (shared by all spans of the request), an 8-byte span ID, the parent's span ID, a name, a kind (server, client, producer, consumer or internal), start and end times with nanosecond resolution, attributes (key-value pairs), events (timestamped notes, such as an exception), links to other traces, and a status. A trace is the tree built from the parent links. Metrics are instruments: counters, up-down counters, histograms and gauges, with attributes as dimensions, and a choice of cumulative or delta temporality when exported. Exemplars attach a trace ID to a metric data point, so you can jump from a latency spike to an example trace. Logs use a log record with severity, body, attributes, and the trace ID and span ID of the active span, so logs can be joined with traces.
Context propagation is what turns separate spans into a trace. When service A calls service B over HTTP, the SDK injects a header traceparent with four parts: version, trace ID, parent span ID and flags, for example 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01. Service B extracts it, and starts its server span with the same trace ID and with A's span as parent. The same is done in message queues (headers in Kafka records) and between threads inside a process through a context object. A second header, baggage, can carry user-defined key-value pairs across the whole request. If any hop fails to propagate, the trace breaks into pieces, which is the most common instrumentation problem.
Metrics are aggregated inside the SDK, not sent one event at a time. When code calls counter.add(1, attributes), the SDK adds the value to an in-memory accumulator for that attribute set, and a periodic reader (every 60 seconds by default in most SDKs) exports the totals. With cumulative temporality the exported value is the running total since start, which suits Prometheus. With delta temporality it is the change since the last export, which suits back ends that sum values themselves. Views let the application owner rename instruments, drop attributes that would explode cardinality, or change histogram buckets, without touching library code. This is the same design idea as the API and SDK split: the library author records what happened, and the application owner decides what is kept.
Sampling controls cost. Head sampling decides at the start of the trace, for example keep 1%, and the decision is passed along in the trace flags so all services agree (the ParentBased sampler). It is cheap but blind: it throws away an interesting slow or failed trace with the same probability as a boring one. Tail sampling waits until the trace is complete and then decides, for example keep all errors, all traces slower than one second, and 1% of the rest. This needs a Collector tier that receives all spans of a trace in one place, so a load-balancing exporter routes by trace ID.
The Collector is a pipeline of receivers (OTLP, Prometheus scrape, Jaeger, Kafka, host metrics), processors (batch, memory_limiter, attributes, filter, tail_sampling, resource detection) and exporters (OTLP, Prometheus remote write, vendor back ends, Kafka, files). It is deployed as an agent beside each node or pod (a DaemonSet or sidecar) for local buffering and enrichment, and as a gateway tier for heavy processing such as tail sampling and routing. OTLP is the glue: a Protobuf schema carried over gRPC or HTTP, so the efficient encoding comes from the same serialization ideas as gRPC itself. The observability concept explains why the signals are kept in one standard: the three kinds of evidence are far more useful when they share identifiers, resource attributes and time, so that an engineer can move from an alert to a trace to a log line in a few clicks.

example: A request enters the checkout service, which calls orders over HTTP, which calls payments over gRPC, which runs one SQL query. Each service creates a server span, plus a client span for each outgoing call, so a request makes roughly 4 server spans, 3 client spans and perhaps a few internal ones: about 10 to 12 spans.
Propagation first. The checkout service has no incoming trace header, so it creates a new trace ID, 0af7651916cd43dd8448eb211c80319c, and a span ID, say b7ad6b7169203331. When it calls orders, it injects traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01, where 01 means "sampled". The orders service extracts it and creates its own server span with a new span ID and the parent b7ad6b7169203331. In the trace view, the spans form a tree with times: checkout 180 ms in total, orders 150 ms, payments 120 ms, and the SQL query 95 ms. Reading the tree, you can see at once that 95 of the 180 ms went to one query.
Now cost. Suppose the system serves 10,000 requests per second, each trace has 12 spans, and each span is about 500 bytes in OTLP. One trace is about 6 KB, so keeping everything means 10,000 × 6 KB = 60 MB per second, which is about 5.2 TB per day. Head sampling at 1% reduces this to about 52 GB per day, but it also drops 99% of the rare slow or failing requests that you want to see. A tail sampling policy keeps all traces with an error or a duration over 1 s and 1% of the others. If 0.5% of requests are errors or slow, the kept volume is about 1.5% of the traffic: roughly 78 GB per day, and every interesting trace is present. The price is that the Collector gateway must buffer all spans of a trace for a decision window, such as 30 seconds. At 60 MB/s, that is 1.8 GB of memory for one window, split across the gateway instances.
Finally, metrics and logs. The same SDK records an http.server.request.duration histogram with attributes for route and status. When a request is slow, an exemplar stores its trace ID in the bucket. A log line written inside the span automatically gets trace_id and span_id fields. In the back end, an engineer sees a latency alert from the metric, clicks the exemplar to open the trace, finds the slow SQL span, and filters logs by that trace ID to read the database error.
intuition: A luggage tag that stays on the bag through every airport: each handler writes a line on the same tag, so at the end you can read the whole journey.
The idea is natural once you see that no single service knows the whole story of a request, and no vendor can see inside code it does not control. The only way to rebuild the story is to attach a small identifier to the request itself and let every service record what it did under that identifier. Standardizing the identifier, the header and the record format turns observability from a product feature into a shared infrastructure, like HTTP for the web. The API and SDK split follows the same logic: the part that everyone must agree on is tiny and stable, and the part that varies (where data goes) is a plug-in.
mistakes: People often think OpenTelemetry is a monitoring product or a back end. In fact it produces, carries and processes telemetry, but it does not store or display it. You still need a trace store, a metrics store and a log store, and a user interface.
People often think auto-instrumentation gives complete traces. In fact it covers the libraries it knows, and the context must also cross your own thread pools, queues and custom protocols. Gaps in propagation split traces into pieces. Business-specific spans and attributes still need manual instrumentation.
People often think we can keep every trace and sample later. In fact the volume of spans is the largest cost in observability, often larger than the cost of the systems being observed. Plan sampling from the start, and know the trade-off between head sampling (cheap, blind) and tail sampling (informed, needs a stateful Collector tier).
People often think OTel replaces Prometheus. In fact they overlap but differ. OTel defines how metrics are produced and sent, and Prometheus is a storage and query system with its own data model and pull-based collection. Many systems use OTel SDKs and the Collector to feed Prometheus, which itself can accept OTLP since version 3.0.
People often think attribute names do not matter. In fact semantic conventions are what lets different services, libraries and vendors agree. If one team writes http.status and another http.response.status_code, dashboards and queries must handle both, and the benefit of a standard is lost.
friction: Overhead and cost are the first problems. Instrumentation adds CPU and memory to every service, mostly for creating spans and for exporting them in batches. Telemetry volume grows with traffic and with the number of services, and storing and querying it can cost more than the application. Cardinality in metrics attributes has the same limits as in Prometheus.
The project is large and moves fast. The specification, SDKs and semantic conventions are at different stability levels: traces are stable, but individual language SDKs, some signals in them, and many semantic conventions are still changing, and attribute names have been renamed between versions. Upgrading SDKs and the Collector regularly is necessary, and the Collector's contrib distribution has hundreds of components of varying quality, so building a custom distribution (with the builder tool) is common.
Operations are demanding. Tail sampling needs a stateful Collector tier with routing by trace ID, memory limits and careful sizing; a restart can lose buffered traces. Backpressure and failure handling (what happens when the back end is slow) must be designed: queues, retries and dropping policy. Auto-instrumentation can conflict with other agents, and manual instrumentation requires discipline across teams. Finally, the three signals are not equally mature, and linking them in practice depends on back-end support and consistent resource attributes.
practice: Start with the Collector. Run an agent Collector on each node or as a sidecar for batching and enrichment (Kubernetes metadata), and a gateway tier for tail sampling and routing. Always set the memory_limiter and batch processors. Use OTLP everywhere between SDKs and Collectors, and keep exporter-specific logic in the Collector so applications never change when you change the back end.
Set resource attributes consistently: service.name, service.namespace, service.version, deployment.environment. Without them, data from different services cannot be grouped or compared. Use the standard semantic conventions and add business attributes (customer tier, order type) with care for cardinality and privacy; never put personal data or secrets in attributes.
Begin with auto-instrumentation for the main frameworks, then add manual spans around business operations and external calls that matter. Make sure context propagates across async boundaries and messaging. Test propagation with a trace that crosses every service type you own. Choose sampling on purpose: ParentBased with a ratio for head sampling at the edge, and tail sampling in a gateway for errors and slow traces, with a measured budget in GB per day.
Monitor the telemetry pipeline itself: Collector queue size, dropped spans, export failures and SDK export errors. Use metrics with exemplars and logs with trace IDs, so engineers can move between signals. Pin SDK and Collector versions, upgrade on a schedule, and read release notes for semantic convention changes. When cost grows, drop low-value spans and attributes in the Collector before they are stored.
tradeoffs: Choose OpenTelemetry when you want to avoid being locked to a vendor, you run many languages and services, and you want one way to instrument traces, metrics and logs; choose a vendor's own agent when you have a small system, want the fastest start and deepest vendor-specific features, and accept that moving later means re-instrumenting. The OTel route costs more setup and operational work (Collectors, sampling), and buys portability.
Choose head sampling when you need a simple, low-cost and predictable volume, and the traffic is high enough that a 1% sample still shows patterns; choose tail sampling when errors and slow requests are rare and must not be lost, at the cost of a stateful Collector tier, extra memory and added delay before a trace is available. Many systems combine both: a low head rate at the edge plus rules that always keep errors.
Choose auto-instrumentation to cover many services quickly with no code change, at the price of generic spans, some overhead and less control; choose manual instrumentation for key business flows where you want meaningful names and attributes, at the price of developer effort and the risk of inconsistency.
Choose an agent Collector per node when you want low latency to the app, local buffering, and metadata enrichment; choose sending directly from the SDK to the gateway when the environment is simple or serverless, and accept less buffering and more load on the SDK. Choose Prometheus scraping for infrastructure metrics you already expose, and OTLP push for application metrics and for environments where scraping is difficult.

value: The public cloud is a way to rent computing instead of owning it. Amazon Web Services (AWS), Microsoft Azure and Google Cloud Platform (GCP) run very large data centres and sell their capacity through APIs: virtual machines by the second, storage by the gigabyte-month, networks, databases, queues, machine learning, and hundreds of other services. You call an API and a thousand servers appear in minutes. When you are done, you delete them and stop paying. The three providers hold most of the market, roughly a third for AWS, a fifth for Azure and a tenth or so for Google, with many smaller providers.
This changed the economics of building systems. Before, you estimated peak demand, ordered hardware months ahead, paid for it up front, and left it idle most of the time. Now capital cost becomes running cost, capacity follows demand, and a team of five can use the same database, queue and global network that a large company builds with hundreds of people. The cost is that you pay a margin for the service, depend on one provider's APIs, and must learn a new set of failure modes and a new bill.
For the layer above, the cloud is the ground that almost everything else on this map stands on. Databricks clusters are virtual machines in your cloud account, and its data lives in object storage. Snowflake, BigQuery and Redshift are managed warehouses built on cloud storage and compute. Kubernetes usually runs on cloud VMs, and Terraform exists to manage cloud resources. The cloud concept (L1) supplies the idea of elastic, metered, API-driven infrastructure; this read describes how the three real providers implement it. It also draws on virtualization (to cut servers into VMs), the data lake (cheap durable storage), serverless (compute that scales to zero), the CDN (edge caching sold as a service) and security architecture (identity on every call).
terms: Region — a geographic area (such as Mumbai or Frankfurt) containing several data centres that the provider operates together.
Availability zone (AZ) — one or more data centres in a region with independent power, cooling and network, so a failure in one zone does not take down the others.
VPC — a virtual private network that you define inside a cloud, with your own address ranges, subnets and routing rules.
IAM — identity and access management: the system of users, roles and policies that decides whether each API call is allowed.
Instance — a virtual machine of a chosen size (vCPUs, memory, network) rented by the second or hour.
Egress — data leaving the provider's network to the internet or another region; the provider charges for it.
Shared responsibility — the provider secures the physical systems and the platform; the customer secures its own data, configuration and identities.
Spot instance — spare capacity sold at a deep discount (often 60 to 90% less) that the provider can take back on short notice.
history: Amazon built its own infrastructure for retail and found that each team spent months on the same undifferentiated work: servers, storage, networking. In 2006 it began to sell the pieces. Amazon S3 launched on 14 March 2006 with storage at 15 cents per gigabyte-month, and EC2 (virtual machines) followed in a limited beta in August 2006. The idea was that developers would pay by use and call everything with an API. The Berkeley paper "Above the Clouds" (2009) explained why this would last: the illusion of infinite capacity, no up-front commitment, and payment for use by the hour.
Others followed. Google App Engine appeared in 2008 as a platform for web apps, and Compute Engine (virtual machines) became generally available in 2013. Microsoft announced Windows Azure in 2008 and made it generally available in 2010; it grew quickly after it added Linux, open-source tools and the enterprise customers who already used Microsoft software. By the mid-2010s, the cloud had become the default for new startups. Then large enterprises, banks and governments followed, helped by compliance programs, private connectivity and hybrid products.
Technology kept changing the foundation. AWS introduced the Nitro system in 2017: small dedicated cards that take over networking, storage and management from the host, so almost all CPU goes to customers and the hypervisor is minimal. Firecracker (2018), a lightweight virtual machine monitor on KVM, made it possible to start isolated micro-VMs in about a hundred milliseconds, which is the base of AWS Lambda. Containers and Kubernetes became managed services (EKS, GKE, AKS). Data platforms moved to object storage and separated compute from storage. The 2020s brought custom chips (Graviton, TPUs, Trainium), GPU capacity for AI as the scarcest resource, and a debate about cost, which led some companies to move parts of their workloads back to their own hardware.
how: A cloud is a stack of layers that each hide the one below, exposed through APIs and metered.
At the bottom are regions and availability zones. A region contains typically three or more zones, each one or several data centres with separate power and network, connected by fast private fibre. Latency inside a zone is a fraction of a millisecond, and between zones in a region roughly one to two milliseconds. This structure is the basis of high availability: if you spread an application over three zones, the loss of one zone leaves two-thirds of the capacity. Zones are close enough for synchronous replication, and regions are far apart for disaster recovery and data residency rules.
Servers are cut into virtual machines by a hypervisor (virtualization). In AWS, Nitro cards run the virtual network, the virtual disks and the encryption, and a thin KVM-based hypervisor schedules vCPUs; Google also uses KVM, and Azure uses Hyper-V. Hardware virtualization support in CPUs lets guest code run at nearly native speed, and memory is isolated by page tables. A "vCPU" is usually one hardware thread. Customers pick an instance type, such as 8 vCPUs and 32 GB of memory, and a scheduler in the provider's control plane places it on a server with free capacity within seconds. Dedicated hosts and bare metal types exist for those who need them.
Networking is software-defined. Each customer defines a VPC with address ranges, subnets in zones, route tables, gateways and firewalls (security groups). The provider's network encapsulates customer packets and maps virtual addresses to physical hosts, so thousands of customers can use the same private address ranges without seeing each other. Load balancers, NAT gateways, private links and transit gateways are services built on this. The same fabric carries traffic between zones and regions, and each crossing has a price.
Storage comes in three kinds. Block storage (EBS, Persistent Disk) is a network-attached virtual disk for a single VM, replicated inside a zone. File storage offers shared file systems. Object storage (S3, Cloud Storage, Blob) holds immutable objects in huge flat namespaces, replicated across zones at very low cost per byte; it is the foundation of the data lake concept, where raw files are kept cheaply and read by many engines. Managed databases, queues, caches and warehouses are built on these primitives and sold as services with backups, patching and failover included.
Elastic and event-driven compute extends the model. Autoscaling groups add and remove VMs by load. Serverless (the serverless concept) goes further: you upload a function or a container, and the provider runs it on demand, scales it from zero to thousands of concurrent instances, and bills per request and per millisecond. The price is cold starts and limits on duration and memory. Content delivery networks (the CDN concept) put caches in hundreds of edge locations close to users and are sold as a service in front of storage or applications.
Security and identity are present in every call. Each API request is signed with credentials, and IAM evaluates policies: by default everything is denied, an explicit deny always wins, and permissions are attached to roles that machines assume temporarily, so no long-lived keys are needed. The security architecture concept explains the principle of least privilege that this serves. The shared responsibility model divides the work: the provider secures the facilities, hardware and hypervisor, and the customer secures the configuration, network rules, identities and data. Most cloud breaches come from the customer side, such as a public bucket or an over-broad role.
Sharing many customers on the same machines needs rules. Quotas cap how many vCPUs, addresses or API calls an account can use, so one customer cannot drain the pool. Rate limits protect the control plane. Network and disk limits are enforced per instance, which is why a small instance has a low network bandwidth and a "burstable" instance has credits. The provider places VMs across racks and zones to limit the effect of one failure, and it overbooks some resources (for example, CPU time on small instances) because customers rarely all use their full share at once. These choices explain behaviours that surprise newcomers: throttled API calls, a disk that is slower than its list speed after a burst, and "insufficient capacity" errors for a rare instance type in one zone.
Finally, the control plane and the bill. Every resource is created through a control plane API (the console, CLI and Terraform all call it), recorded, and metered. Billing is by usage: instance seconds, GB-months, requests, and data transferred. Pricing models include on-demand, reserved or savings plans (a one- or three-year commitment for 30 to 70% off), and spot. Knowing which meter each design touches is a core skill.

example: Three small calculations show how the cloud changes decisions. The prices are rounded and for the US East region of AWS; they differ by region and change over time, so treat them as the right order of magnitude.
First, elasticity. A nightly Spark job needs 100 machines for 2 hours. At roughly 0.40 dollars per instance-hour on demand, one night costs 100 × 2 × 0.40 = 80 dollars, or about 29,000 dollars per year. Keeping those 100 machines running all day and all year would cost 100 × 8,760 × 0.40 = 350,400 dollars. With spot instances at a 70% discount the nightly job costs about 24 dollars. Owning the machines would need hardware for the peak, and idle capacity for the other 22 hours. This is the main economic argument for the cloud: pay for hours used, not for peak capacity.
Second, the opposite case. A steady database server that runs 24 hours a day on a machine with a list price of 1.00 dollar per hour costs 8,760 dollars per year on demand. With a three-year commitment at around 50% off it costs about 4,400 dollars. Compare this with buying a comparable server for a few thousand dollars, plus power, space, spare parts and people. For flat, predictable loads at large scale, owning can be cheaper, which is why some companies repatriate stable workloads. The cloud wins when load varies, when speed matters, and when operations staff is expensive.
Third, the hidden meter. A Kafka cluster in three zones with replication factor 3 receives 100 MB/s. The leader receives each byte, and two followers in other zones copy it, so replication sends about 200 MB/s across zones. At 0.01 dollars per GB in each direction, which is 0.02 dollars per GB for a round trip, the cost is 200 MB/s × 86,400 s = 17.3 TB per day, or 17,300 GB × 0.02 = about 346 dollars per day, or about 126,000 dollars per year, before counting producers and consumers that also cross zones. Egress to the internet is worse: moving 100 TB out at roughly 0.09 dollars per GB (lower at high volumes) costs up to about 9,000 dollars. Designs that keep traffic inside a zone, compress data, or put consumers next to data save real money.
intuition: Electricity from the grid instead of a generator in your basement: you pay for what you draw, someone else keeps the power station running, and you must still be careful what you plug in.
The cloud is natural because computing resources are fungible and most demand is uneven. A provider that serves millions of customers can pool servers, so peaks of one customer fill the valleys of another, and it can buy hardware and build networks at a scale that no single customer can. Exposing everything as an API with metering is then logical: if resources are pooled and billed by use, they must be created and destroyed by programs. Many properties that look like product features, such as automation, elasticity and infrastructure as code, follow directly from this one step.
mistakes: People often think the cloud is always cheaper. In fact it is cheaper for variable, uncertain or fast-growing demand and for small teams, but a steady large workload on on-demand prices can cost several times more than owned hardware. Cost depends on commitments, architecture and attention to the meters.
People often think the cloud provider secures everything. In fact it secures the infrastructure, and you secure what you build on it. Public storage buckets, open security groups, leaked keys and over-privileged roles are customer-side failures and the most common cause of cloud breaches.
People often think multiple availability zones protect against all outages. In fact zones protect against failures of a data centre, but many outages come from regional services, control planes or shared dependencies (DNS, identity, a regional database). Disaster recovery for such events needs multiple regions, with the cost and complexity that this implies.
People often think using managed services means no lock-in if the API looks standard. In fact data gravity (egress fees and the time to move petabytes), proprietary features and operational habits create lock-in even when the API is similar. Lock-in can still be a good trade, but it should be chosen knowingly.
People often think "scale to zero" and "unlimited scale" are free of limits. In fact accounts have quotas (vCPUs, IPs, API rates), and at large scale you can hit capacity limits for a specific instance type or GPU in a zone.
friction: Cost control is the most common pain. Bills have thousands of line items, and the expensive ones are often surprising: cross-zone traffic, NAT gateway processing, egress, idle volumes and snapshots, over-provisioned instances, and log or metric ingestion. Without tagging, budgets, alerts and a team that owns cost (FinOps), spending grows quietly.
Complexity and lock-in follow. Each provider has hundreds of services with their own names, limits and failure modes, and the IAM system alone takes months to learn. Managed services reduce operations but tie you to one API, and moving a data platform between clouds means redesigning networking, identity and data movement. Multi-cloud sounds like freedom, but it multiplies the work and usually reduces use of the best features of each.
Reliability is shared and sometimes outside your control. Large regional outages in the past (for example in AWS us-east-1) affected thousands of services at once, because many control planes and customer systems depend on a few regions. Noisy neighbours, throttled APIs, quota limits and capacity shortages (GPUs especially) can break scaling plans. Performance is less predictable than on dedicated hardware: network-attached disks have variable latency, and instance types with "burst" credits slow down when credits are used up.
Finally, governance and sovereignty matter. Data residency laws, audit needs and government access rules shape where you can put data, and shared responsibility confuses teams when something goes wrong. Skills are also a cost: engineers must understand networking, IAM and the provider's services, not only code.
practice: Treat the account structure as part of the design: separate accounts or projects for production, development and shared services, with central logging and guardrails (service control policies or organization policies). Create all resources through Terraform or similar, never by hand, and tag everything with owner, team and cost center.
Use roles, not long-lived keys. Give each workload the narrowest role that works, use short-lived credentials, turn on logging of all API activity (CloudTrail or equivalent), and block public access on storage by default. Encrypt data at rest and in transit, and manage keys in the provider's key service.
Design for the meters. Keep chatty traffic inside one zone when you can, use VPC endpoints or private links for storage traffic instead of NAT gateways, compress data, and place compute where the data is. Choose purchase models by workload: on-demand for experiments, savings plans or reservations for the steady base (cover 60 to 80% of the baseline, not the peak), and spot for fault-tolerant batch work such as Spark executors with retries.
Plan for failure explicitly. Spread across zones, use health checks and autoscaling, test restores from backups, and decide the recovery time and recovery point you need before choosing multi-region. Set budgets and anomaly alerts, review the bill monthly, and delete idle resources. For data platforms, prefer object storage as the system of record, separate compute from storage, and keep clusters ephemeral.
tradeoffs: Choose the public cloud when demand is variable or uncertain, time to market matters, or you need global reach and managed services; choose your own data centres or colocation when load is large and steady (hundreds of servers at high utilization for years), you have the staff, or regulation requires it. The cloud buys speed and elasticity and charges a margin; owning buys lower unit cost and charges in capital, lead time and operations.
Choose managed services (a managed database, Kafka, or warehouse) when your team is small or the service is not your differentiator, because patching, backups and failover are included; choose self-managed on VMs or Kubernetes when you need deep tuning, a special version, or lower unit cost at scale and have people to run it. Managed saves people and costs money and flexibility.
Choose a single provider when you want speed and depth of integration; choose multi-cloud only for clear reasons, such as regulation, acquisition, best-of-breed capability (for example, a specific AI service) or negotiating power. Multi-cloud means the lowest common denominator, duplicate skills and more egress.
Choose one region with multiple zones when a few minutes of downtime on a rare regional event is acceptable; choose multi-region active-passive when you need recovery within an hour at moderate cost; choose active-active only when the business loss justifies the complexity of data replication and conflict handling. Each step multiplies cost and engineering effort.
Choose serverless for spiky or low-volume workloads and glue code, with scale to zero; choose containers or VMs for steady load, long-running work, or when per-request pricing exceeds the cost of a continuously running instance. A common break-even is a function that is busy more than a quarter to a third of the time.
interview: Why is cross-AZ traffic a design concern, and how would you reduce it? || It is billed per GB in each direction and adds around a millisecond of latency. Systems with replication (Kafka, databases) and chatty microservices can create large flows. Reduce it with zone-aware routing and consumer-follows-leader or rack-aware fetching, keeping traffic inside a zone where possible, compression and batching, and by sizing replication to the actual durability needs.
How do you decide between on-demand, savings plans and spot for a data platform? || Use savings plans or reservations for the steady baseline (the always-on services and the minimum cluster), on-demand for the variable part that is not fault-tolerant, and spot for fault-tolerant batch executors with retries and checkpoints, with diversification across instance types and zones. Measure utilization and commit to 60 to 80% of the stable base.
An application is highly available across three zones. What failures can still take it down? || A regional failure, a control plane or identity outage, a shared dependency (DNS, a regional database or message service), a bad deployment or configuration that is replicated everywhere, quota exhaustion, a certificate expiry, and human error. Zones only cover the loss of a data centre.
Explain IAM evaluation and how you would apply least privilege. || Requests are denied by default. The engine collects the applicable policies (identity, resource, boundaries, organization rules), an explicit deny wins, and otherwise an explicit allow is needed. Apply least privilege with roles per workload, short-lived credentials, scoped resources and conditions, analysis of access logs to remove unused permissions, and guardrails at the organization level.
What are the arguments for and against repatriating a workload from the cloud? || For: steady, predictable and large workloads where owned hardware is cheaper, high egress or storage bills, and performance needs. Against: lost elasticity, capital outlay, operations staff, hardware lead times, missing managed services, and the cost of migration. Decide with total cost of ownership over several years, including people, and keep elastic parts in the cloud.
Why does a data lake on object storage change the architecture of a data platform? || Object storage is cheap, durable and shared, so compute can be separated from storage: clusters start when needed, scale independently, and read the same files, and can be shut down without losing data. The costs are higher latency than local disks, request charges, and the need for table formats to provide transactions.
quiz: What is the difference between a region and an availability zone? || A region is a geographic area with several independent zones. A zone is one or more data centres with separate power and network. Spreading across zones protects against data centre failure; across regions, against regional events.
Why do Nitro-style cards matter for a cloud provider? || They offload networking, storage and management from the host CPU to dedicated hardware, so nearly all CPU goes to customer VMs, isolation is stronger, and the hypervisor can stay very small.
What does "explicit deny wins" mean in IAM? || If any applicable policy denies an action, the request is refused even if other policies allow it. With no allow, the default is also deny.
A Kafka cluster replicates 50 MB/s to two followers in other zones at 0.01 dollars per GB each way. What is the cost per day of replication traffic? || The cross-zone volume is 2 × 50 = 100 MB/s, or about 8.64 TB per day. At 0.02 dollars per GB for both directions, that is about 8,640 GB × 0.02 ≈ 173 dollars per day.
When would you choose spot instances, and when not? || For fault-tolerant, restartable work such as batch Spark tasks, CI jobs or stateless workers, where an interruption costs a retry. Not for databases, single points of failure, or jobs that cannot checkpoint.

value: Amazon S3 (Simple Storage Service) stores objects: files of any size, from zero bytes to 50 TB, each identified by a key (a name such as logs/2026/10/26/part-0001.parquet) inside a bucket. You write an object with an HTTP PUT, read it with GET, list keys with LIST, and delete it. You do not mount it, you do not manage disks, and you do not plan capacity. It holds hundreds of trillions of objects for millions of customers, is designed for 99.999999999% (eleven nines) durability, and is billed by the gigabyte-month, per request and per gigabyte of data leaving AWS.
S3 became the default place to put data because of three properties together. It is cheap: S3 Standard costs roughly 2.3 cents per gigabyte-month, and colder classes cost much less. It is durable and available without any work from you, because the data is spread over many devices and at least three availability zones. And it is shared: any number of machines can read the same objects at the same time, from any service. This last property allowed a major change in data architecture. Compute (Spark clusters, query engines) can be started, stopped and resized independently of storage, because the data is not on the cluster's disks.
For the layer above, S3 is the base of the data lake (L1) and of the lakehouse. Table formats such as Delta Lake and Apache Iceberg add transactions, schemas and versions on top of plain files in S3. Databricks, Spark, Trino, Snowflake external tables and Athena read the same Parquet files. Backups, logs, machine learning datasets and model weights live there too. It stands on the cloud (L0), which provides regions, zones, identity and the billing model; on the cloud computing idea (L1) of rented, elastic services; and on the data lake concept, which is the use that made S3 central. Its API has become a de facto standard that many other stores copy (MinIO, Ceph, Cloudflare R2, Google Cloud Storage's compatibility mode).
terms: Object — a blob of bytes plus metadata, stored and addressed as a whole; it cannot be modified in place, only replaced.
Bucket — a named container for objects in one region; bucket names are globally unique.
Key — the full name of an object in a bucket; a flat string, where "/" is only a convention that tools show as folders.
Prefix — the leading part of a key, used for listing and for spreading load.
Multipart upload — uploading a large object as many parts in parallel and then completing it into one object.
Erasure coding — splitting data into k data pieces plus m parity pieces so that any k pieces rebuild it, using less space than full copies.
Strong read-after-write consistency — after a successful write, any following read or list sees the new data; S3 has provided this for all operations since December 2020.
Storage class — a price and availability tier (Standard, Infrequent Access, Glacier tiers, Express One Zone) chosen per object or by lifecycle rules.
history: S3 launched on 14 March 2006 as one of the first AWS services, with a simple promise: store any amount of data, get it back at any time, pay about 15 cents per gigabyte-month. The API had a handful of operations (PUT, GET, DELETE, LIST) over HTTP. It was meant for web application assets, and almost immediately it was used for backups and for storing data of every kind. Prices fell many times; Standard is now roughly 2.3 cents per gigabyte-month in the main US region, and archive classes cost a small fraction of a cent.
The early S3 had eventual consistency for some operations. A new object could be read at once, but an overwrite or delete could briefly show old data, and listings could miss recent keys. This caused real problems for big data: Hadoop and Spark jobs that wrote files and then listed a directory sometimes missed files, and tools such as EMRFS consistent view and S3Guard were built to work around it. On 1 December 2020 AWS made S3 strongly consistent for all operations, at no extra cost, which removed a whole class of workarounds.
Later changes served the data lake. Multi-region and lifecycle features arrived early; S3 Select and Intelligent-Tiering followed. In 2023 AWS launched S3 Express One Zone, a single-zone class for latency-sensitive workloads with single-digit-millisecond access. In August 2024 S3 added conditional writes (If-None-Match, and later If-Match), which let a client create an object only if it does not already exist; this gives table formats the compare-and-swap primitive they need to commit safely. In December 2024 AWS launched S3 Tables, a managed Apache Iceberg table service with automatic compaction. In December 2025 the maximum object size was raised from 5 TB to 50 TB. Inside, the storage layer was rewritten; AWS described ShardStore, the per-disk storage engine in Rust, which is checked with lightweight formal methods (a SOSP 2021 paper).
how: S3 looks like a simple key-value map, and the engineering is in making that map durable, consistent, fast and huge.
Requests come in over HTTPS to a regional endpoint. A front-end fleet authenticates each request with signed credentials (IAM, from the cloud concept), checks bucket policies, and routes it to the right internal services. Internally, S3 is made of hundreds of microservices. Two systems are central: an index (metadata) subsystem that maps each (bucket, key) to the location of the data, and a storage subsystem that holds the bytes. Keys are kept in sorted order, which is what makes LIST by prefix possible. Because the index is partitioned by key ranges, S3 splits hot ranges automatically; AWS documents that each prefix supports at least 3,500 write and 5,500 read requests per second, and you can have as many prefixes as you want.
For durability, an object is not stored once. When you PUT an object, S3 stores it redundantly across at least three availability zones (except One Zone classes). In his 2023 article on running S3, Andy Warfield described the basic method as erasure coding: an object is cut into k data shards plus m parity shards (Reed-Solomon is the classic example), and any k of the k+m shards are enough to rebuild it. With, for example, 5 data shards and 4 parity shards the storage overhead is 1.8 times the data, compared with 3 times for three full copies, and the system survives the loss of any 4 shards. Shards sit on different drives, racks and zones. A continuous background process audits shards, detects bit errors and failed drives, and rebuilds missing pieces before more failures accumulate. This is the cloud concept at work: a very large number of cheap disks (millions of them), made reliable by software.
For performance, the main challenge is heat. A hard disk can do only about 120 random operations per second, and a single popular object can overload the disks that hold it. S3 spreads each customer's objects over a huge number of drives, so that even one large bursty workload spreads across a very big set, and aggregation of many customers smooths the demand. Replication of hot data and request routing away from busy devices reduce stragglers, which would otherwise dominate tail latency.
Consistency is the hardest part of the index. For strong read-after-write, every read of metadata must see the latest committed write. AWS described the 2020 change (Werner Vogels, 2021) as a cache coherence protocol for the metadata caches. The replication logic tracks the order of operations for each object, and a component called the witness is told about every change. On a read, the cache asks the witness whether its copy is stale. If it is current, it is served from the cache; if it is stale, it is invalidated and read again from the persistence tier. There was no extra cost and no loss of performance, and a LIST right after a PUT sees the new key. S3 still does not offer transactions across keys or atomic rename: each object operation is atomic on its own, nothing more.
Large objects use multipart upload. The client starts an upload, sends parts of at least 5 MiB (the last one may be smaller), in parallel and with individual retries, and then completes it; S3 assembles the object atomically. A single PUT is limited to 5 GB, a multipart upload has up to 10,000 parts, and the maximum object is 50 TB. Downloads use range GETs, so a client can fetch many ranges in parallel; one HTTP connection typically moves about 90 MB/s, so high throughput comes from parallel connections. The first-byte latency for S3 Standard is tens of milliseconds, which is the central cost for small objects.
On top of these primitives sit management features: versioning (keeping old versions after overwrite or delete), lifecycle rules (move to colder classes or expire), replication across buckets and regions, event notifications, access points and encryption (server-side with AWS-managed or customer keys). Conditional writes add the missing atomic step: a client sends If-None-Match: * with a PUT, and S3 creates the object only if the key does not exist. Table formats use this to commit. Delta Lake writes the next log file, such as _delta_log/00000000000000000123.json, and needs exactly one writer to win; Apache Iceberg commits by atomically swapping a pointer in a catalog. S3 Tables and S3 Express One Zone move further toward table and low-latency workloads.

example: Take a 1 TB dataset of Parquet files that a Spark job scans once a day, and compare two ways to store it.
Layout 1: 8,192 files of 128 MB each. Listing needs 9 LIST calls (1,000 keys per call). A scan makes about 8,192 GET requests (or a few more with range reads), and S3 charges roughly 0.0004 dollars per 1,000 GET requests, which is 8.2 requests-thousand × 0.0004 ≈ 0.003 dollars. Reading one 128 MB file with one connection at about 90 MB/s takes about 1.4 seconds, plus a first-byte latency of perhaps 30 ms, which is 2% overhead. With 200 task slots in parallel, the whole terabyte is read in 8,192 / 200 × 1.4 s ≈ 57 to 60 seconds, at an aggregate rate of about 18 GB/s.
Layout 2: 1,048,576 files of 1 MB each (a streaming job that writes small files). Listing needs about 1,050 LIST calls, which are sequential unless you list by prefix in parallel. A scan needs 1,048,576 GETs: 0.0004 × 1,048.6 ≈ 0.42 dollars per scan, about 128 times more than layout 1. Each 1 MB file takes about 11 ms to transfer at 90 MB/s, but also has 30 ms of first-byte latency, so latency is 73% of the time per file. With the same 200 slots, the scan takes 1,048,576 / 200 × 41 ms ≈ 215 seconds, almost four times slower, and a task's time is dominated by waiting. This is the small-files problem, and it is why Delta and Iceberg have compaction jobs (OPTIMIZE) and why S3 Tables offers automatic compaction.
Now the storage bill. 1 TB in S3 Standard costs about 1,024 GB × 0.023 = 24 dollars per month. 100 TB costs about 2,400 dollars per month (the real price is slightly lower for large volumes). Moving the same cold data to a colder class such as Glacier Instant Retrieval at about 0.4 cents per GB-month would cost around 400 dollars, but retrieval and minimum-duration fees apply. Reading 100 TB out of AWS to the internet would cost around 9,000 dollars, while reading it from EC2 in the same region costs nothing for transfer. That is why compute is placed in the same region as the data.
Finally, a rename. Spark writes output to a temporary directory and then "renames" it to the final path. On a file system this is one atomic metadata change. On S3 there is no rename: it is a copy followed by a delete of each object. Renaming a directory of 10,000 files means 10,000 COPY and 10,000 DELETE calls, which takes minutes and is not atomic. This is why S3-specific committers (the S3A magic and staging committers) and table formats that commit with a single small metadata file were created.
intuition: A giant warehouse where every box has a unique label: you can store or fetch any box, any number of workers can do it at once, but you cannot repack a box, you must replace it.
The design is natural when you accept two limits. First, objects are immutable and addressed by name, so there is no need to coordinate partial updates or locks, and data can be replicated and moved freely. Second, a flat key space sorted by name is enough to build everything else, because any structure (folders, tables, versions) can be added above it with naming conventions and metadata files. Giving up in-place update, rename and POSIX semantics is what allows the system to grow to exabytes with simple, uniform behaviour. The rest of the data stack, from Parquet to Iceberg, is designed around this deal.
mistakes: People often think S3 is a file system with folders. In fact it is a flat key-value store. A "folder" is a shared key prefix, "renaming a folder" means copying and deleting every object, and listing a "directory" is a prefix search over sorted keys.
People often think S3 is eventually consistent. This was true of some operations before December 2020, and many tools and articles still describe it. Today reads, lists and overwrites are strongly consistent. What S3 still lacks is multi-object transactions: two writes to different keys are not atomic together.
People often think eleven nines of durability means the data can never be lost. In fact it is a design target for the probability of losing an object through hardware failure; it says nothing about you deleting data by mistake, a bad lifecycle rule, a compromised credential, or a software bug. Use versioning, object lock, replication to another account or region, and backups for those risks.
People often think S3 throughput is limited per bucket. In fact request rates are per prefix and the index scales out automatically, so spreading keys across prefixes and reading with many parallel connections gives very high aggregate throughput. The limit you hit more often is the throughput of a single connection and the request overhead of small files.
People often think the cheapest storage class is always the cheapest choice. In fact colder classes charge for retrieval, minimum storage durations (30 to 180 days or more) and per-object overheads, so for small or frequently read objects, they can cost more than Standard.
friction: Latency per request is the main cost. Every GET has a first-byte latency of tens of milliseconds, unlike local disk or memory, so workloads with many small files or random reads are slow and expensive. Remedies are larger files, columnar formats with footers and range reads, caching (local SSD caches, Alluxio-like layers), prefetching, and S3 Express One Zone for latency-sensitive data at a higher per-GB price.
The API lacks features that file systems have. There is no rename, no append, no partial update, and no multi-object atomicity. Listing is slow (1,000 keys per call and sequential) and billed as a request, and listing a bucket with billions of objects is a project in itself (use S3 Inventory instead). Atomic commit across files must be built above S3 with table formats and conditional writes.
Cost has several meters that surprise people: requests (PUT is ten times more expensive than GET), data transfer out of AWS or between regions, small-object overhead, retrieval fees and minimum durations in colder classes, versioning that keeps every old version, and incomplete multipart uploads that hide parts that you still pay for. There are also operational risks: public-bucket misconfigurations, compromised credentials, accidental deletes, and a regional outage that makes data unavailable. Finally the "S3-compatible" label of other systems often hides differences in consistency, conditional writes, listing and performance, so each must be tested.
practice: Design file layout for the engine. Aim for Parquet files of 128 MB to 1 GB for analytics, compact small files regularly (OPTIMIZE in Delta, rewrite_data_files in Iceberg), and partition by columns that queries filter on, without creating millions of tiny partitions. Use columnar formats so that readers fetch only needed column chunks with range reads.
Co-locate compute and data in the same region, and use gateway VPC endpoints for S3 so traffic stays on the AWS network and avoids NAT gateway charges. Use multiple parallel connections for large transfers (the AWS CRT-based clients and the Transfer Manager do this), and use random or hashed key prefixes only if you really exceed per-prefix limits. Use multipart upload for anything over 100 MB, and add a lifecycle rule to abort incomplete multipart uploads after a few days.
Protect the data. Turn on Block Public Access at the account level, enable default encryption, use bucket policies with least privilege and IAM roles rather than keys, enable versioning and, for critical data, object lock and cross-account replication. Log access with CloudTrail data events when audit matters. Use lifecycle rules and Intelligent-Tiering to move cold data to cheaper classes, and S3 Inventory and Storage Lens to see what you have and what it costs.
For lakehouse writes, use a table format (Delta or Iceberg) rather than raw files, and make sure your engine uses the S3 committer or conditional-write support appropriate for it. Avoid rename-based commit protocols, avoid listing large directories in hot paths, and test the behavior of any S3-compatible store before relying on it.
tradeoffs: Choose S3 (object storage) for data that is written once and read many times by many machines: lakes, logs, backups, model files. Choose block storage (EBS) or local NVMe for databases, low-latency random I/O and anything that needs in-place updates; a Kafka broker or a RocksDB instance needs fast local disks. S3 gives you durability, sharing and low price per byte; you give up latency, mutation and file-system semantics.
Choose S3 Standard for data read often; choose Standard-Infrequent Access or Intelligent-Tiering when access is unpredictable or falls after weeks; choose Glacier classes for archives read rarely, when you can accept retrieval fees, minimum durations and (for deep archive) hours of delay. Choose S3 Express One Zone when you need single-digit-millisecond latency and high request rates, for example for ML training data or shuffle, and accept single-zone availability and a higher price per GB.
Choose large files (hundreds of MB) when scan throughput matters, and smaller files only when data must be available within seconds of arrival; compaction is the bridge between them. Smaller files cost more per scan; larger files make updates and deletes more expensive, because a change rewrites a bigger unit.
Choose a table format with a catalog (Iceberg, Delta) over raw Parquet in S3 when several writers, deletes, schema changes or time travel matter; choose raw files with partitioned paths when data is append-only, written by one job, and read by simple tools. The table format costs metadata maintenance and a learning curve; raw files cost you correctness when something goes wrong.
Choose S3 over a self-hosted S3-compatible store (MinIO, Ceph) when you want no operations and the highest durability; choose self-hosted when data must stay on-premises, egress costs dominate, or you have steady, very large volumes and the staff to run it, and accept that you own durability, upgrades and performance tuning.
interview: How does S3 achieve eleven nines of durability, and what does that number not cover? || Objects are stored with redundancy (erasure coding or replication) over many drives and at least three availability zones, with continuous scrubbing and repair of lost shards, so the chance of losing enough pieces at once is tiny. It does not cover logical errors such as deletes, bad lifecycle rules, credential compromise or corruption caused by your own software; use versioning, object lock and cross-account replication.
Why is there no rename in S3, and what breaks because of that? || Objects are immutable and the namespace is a flat sorted key space with no directory inodes, so a rename means copy then delete for each key, which is slow, costs requests and is not atomic. Commit protocols that rely on rename (Hadoop FileOutputCommitter) are slow and unsafe on S3, so S3A committers and table formats commit with a single metadata write instead.
What changed in December 2020 and why did it matter for Spark and Hive? || S3 became strongly consistent for reads, lists and overwrites. Before that, a list right after writing could miss files, and jobs could read stale data, so workarounds such as S3Guard and EMRFS consistent view were needed. Now listings are reliable, although there are still no multi-object transactions.
How do conditional writes help Delta Lake or Iceberg commits? || A table commit must succeed for only one of several concurrent writers. With If-None-Match, a writer creates the next log file only if it does not exist; the loser gets a failure and retries. Before this, S3 had no atomic put-if-absent, and Delta needed an external lock service such as DynamoDB for multi-cluster writes. Iceberg uses an atomic pointer swap in its catalog.
A Spark job reading S3 is slow, and the S3 request bill is high. What do you check first? || The number and size of files: many small files cause many GETs with high first-byte latency. Check listing time, whether partitioning is too fine, and whether files can be compacted to 128 MB or more. Then check parallelism, columnar pruning and range reads, and whether compute is in the same region.
When would you not use S3 as the primary store? || For low-latency random reads and writes, for workloads needing in-place updates or POSIX semantics, and for very small objects at very high request rates where request cost dominates. Use local SSD, EBS, a database or a cache, and use S3 as the durable, shared tier behind them.
quiz: What does strong read-after-write consistency mean for S3? || After a successful PUT or DELETE, any later GET or LIST sees the result. Since December 2020 S3 provides this for all operations, though it still does not offer multi-object transactions.
Why is a rename in S3 expensive and not atomic? || Objects cannot be moved, so a rename copies each object to a new key and then deletes the old one. Each step is a separate request, and a failure in the middle leaves a partial result.
How does erasure coding save space compared with three copies? || It splits the object into k data and m parity shards, and any k shards rebuild it. With 5 data and 4 parity shards the overhead is 9/5 = 1.8 times, versus 3 times for three copies, while tolerating the loss of 4 shards.
A scan reads 1 TB as 1 MB files, with 30 ms first-byte latency and 90 MB/s throughput per request, using 100 parallel readers. Roughly how long does it take? || Each file takes about 30 + 11 ≈ 41 ms. There are about 1,048,576 files, so 1,048,576 / 100 × 41 ms ≈ 430 seconds. With 128 MB files, the same data takes about 8,192 / 100 × 1.45 s ≈ 119 seconds.
When would you choose S3 Express One Zone over S3 Standard? || When you need single-digit-millisecond latency and very high request rates for frequently accessed data, such as ML training, shuffle or interactive queries, and you can accept storage in only one availability zone and a higher price per GB.

@@ istio
value: Istio is a service mesh for Kubernetes. It puts a proxy (Envoy) next to every workload and manages all of those proxies from one control plane. Without changing application code, it then gives every service-to-service call encryption with mutual TLS, a cryptographic identity for each workload, rules about who may call whom, retries, timeouts, traffic splitting for canary releases, and metrics, logs and traces for every request. You write a few Kubernetes resources, and Istio turns them into configuration for hundreds or thousands of proxies.
The problem it solves is the cost of doing these things inside applications. With microservices, each team would need to implement TLS, certificate rotation, retries, timeouts and telemetry in every language and every service, and keep them consistent. Security and reliability rules would depend on 200 teams doing the right thing. Istio moves the policy into the platform: the platform team sets "all traffic in the mesh must use mTLS" or "send 5% of requests to version 2", and it applies to every service the same way, and can be audited in one place.
It stands on three lower concepts. The service mesh pattern (L1) is the idea of a data plane of proxies controlled by a control plane. Mutual TLS (L2) is how Istio proves identity and encrypts traffic: each workload gets a short-lived certificate, and both sides of a connection check each other. Envoy (L0) is the data plane, the proxy that actually handles packets and requests; Istio's own job is to compute Envoy configuration and push it through xDS. In 2024 Istio also made its "ambient mode" generally available, a design without a sidecar in each pod, which responds to the main criticism of the first design: resource cost.
terms: Control plane — the part that decides configuration and identity; in Istio it is the istiod process.
Data plane — the proxies that handle traffic; Envoy sidecars, or the ztunnel and waypoint proxies in ambient mode.
Sidecar — an Envoy container injected into each pod that intercepts all of the pod's incoming and outgoing traffic.
Workload identity — a certificate that names a workload, such as spiffe://cluster.local/ns/shop/sa/orders, issued automatically and rotated.
VirtualService and DestinationRule — Istio resources that define routing (weights, retries, timeouts) and per-destination policy (load balancing, circuit breaking, mTLS mode).
AuthorizationPolicy — a resource that allows or denies requests based on identity, namespace, method, path and other fields.
ztunnel — in ambient mode, a small per-node proxy (written in Rust) that provides L4 mTLS, identity and basic authorization for all pods on the node.
Waypoint proxy — in ambient mode, an optional Envoy deployment per namespace or service that provides L7 features such as routing and HTTP authorization.
history: Istio was announced in May 2017 by Google, IBM and Lyft, with Lyft contributing Envoy. It followed an earlier pattern at Google and large internet companies, where a proxy and a policy system handled all service traffic. Kubernetes was winning, microservices were growing, and teams wanted traffic management and security as platform features. Version 1.0 came in July 2018.
The first architecture had several separate components: Pilot (configuration and service discovery for the proxies), Citadel (certificate authority), Galley (configuration validation) and Mixer (a policy and telemetry service that every proxy called for each request). Mixer proved too slow and costly because it added a network call to the request path, so telemetry moved into the proxies themselves. In version 1.5 (March 2020) the control plane components were merged into a single binary, istiod, which made installing and operating Istio much simpler. Istio entered the CNCF in 2022 and graduated in July 2023.
The long-running criticism was the sidecar model: one proxy per pod meant a lot of memory and CPU, pod startup order problems, the need to restart pods to upgrade the proxy, and an extra hop for every call. In 2022 the Istio project announced ambient mode, which splits the data plane into a shared L4 node proxy (ztunnel) and optional L7 waypoint proxies, and reached general availability in version 1.24 in November 2024. Sidecar mode remains fully supported. As of October 2026, the current release line is 1.31.
how: Istio is a control plane that watches Kubernetes, computes configuration, and pushes it to Envoy proxies, plus a way to put those proxies into the traffic path.
In sidecar mode the proxy is placed with a mutating admission webhook. When a pod is created in a namespace labelled for injection, istiod's webhook adds an Envoy container (with a small helper called pilot-agent) and an init step, or a CNI plugin, that sets iptables rules inside the pod's network namespace. These rules redirect all outbound traffic to Envoy on port 15001 and all inbound traffic to Envoy on port 15006. The application does not change: it still connects to orders:8080, and the kernel quietly sends the packets to the local proxy. Here Linux namespaces and netfilter do the real work, which is why a mesh is not magic. Ambient mode avoids per-pod changes by redirecting traffic of the pod to the node's ztunnel.
The control plane, istiod, holds three jobs. First, it is a configuration server. It watches the Kubernetes API for Services, Endpoints, Pods and Istio resources, builds an internal model, and translates it to Envoy configuration (listeners, routes, clusters and endpoints). It then pushes updates to every proxy over xDS, a gRPC stream. A VirtualService with a 90/10 split becomes weighted clusters in an Envoy route. Second, it is a certificate authority. A proxy's agent creates a key pair, sends a certificate signing request with its Kubernetes service account token, and istiod verifies the token and returns a short-lived certificate (24 hours by default) with the identity spiffe://cluster.local/ns/<namespace>/sa/<service-account>. The agent hands the certificate to Envoy through SDS and renews it before it expires, with no pod restart. Third, it validates configuration, so a bad resource is rejected early.
Mutual TLS then works like this. When the orders sidecar calls payments, it sees from the cluster configuration that the destination supports Istio mTLS, and opens a TLS connection in which both sides show certificates signed by the mesh CA. Each side learns the other's SPIFFE identity from the certificate. The PeerAuthentication policy sets the mode: PERMISSIVE accepts both plain text and mTLS (useful during migration) and STRICT accepts only mTLS. An AuthorizationPolicy is then evaluated with the verified identity: for example, allow only principals ending in sa/orders to call POST /charge on payments. Because identity comes from a certificate and not from an IP address, the rule stays valid when pods move.
Traffic management uses the same machinery. Retries, timeouts, fault injection, circuit breaking and outlier detection, traffic mirroring and weighted routing are Envoy features (see the Envoy concept) selected by Istio resources. Gateways at the edge of the mesh are also Envoy deployments, configured through the Kubernetes Gateway API or Istio's Gateway resource. Telemetry is generated by the proxies: request counts, latencies and sizes labelled by source and destination workload (scraped by Prometheus), access logs, and trace spans that join into OpenTelemetry or Zipkin-style traces if the application forwards trace headers.
Failure behaviour follows from the split between control plane and data plane. Proxies keep running with the last configuration they received if istiod is unreachable, so traffic continues; what stops is change, not service. Endpoints are the exception: the proxy learns about new or removed pods only through istiod, so a long control plane outage slowly makes the endpoint lists stale, and calls to removed pods fail until Envoy's own health logic ejects them. Certificates last 24 hours by default, which limits how long a stolen certificate is useful and how long an outage of the certificate authority can be tolerated. The mesh also needs to know about the outside world: a ServiceEntry describes an external host, and by default Istio lets mesh traffic leave to unknown hosts, which can be tightened by setting the outbound traffic policy to registry-only.
Ambient mode changes where the proxies run. The ztunnel runs on each node as a DaemonSet. It captures traffic from pods in the ambient mesh, and for each connection it authenticates both ends and wraps the traffic in mTLS, using a tunnel protocol called HBONE (an HTTP/2 CONNECT tunnel on port 15008). This gives L4 identity, encryption, and TCP-level authorization and metrics for every pod with a tiny footprint. When a service needs L7 behaviour (HTTP routing, retries, header or path authorization), you deploy a waypoint, an Envoy proxy managed per namespace or per service account and configured with Gateway API resources. Traffic to such a service goes from ztunnel to the waypoint and on to the destination. Because waypoints are shared and scaled separately from applications, a 1,000-pod namespace does not need 1,000 Envoy copies. In Istio's published test at 1,000 requests per second, a sidecar used about 0.20 vCPU and 60 MB, a waypoint 0.25 vCPU and 60 MB, and a node's ztunnel about 0.06 vCPU and 12 MB.

example: Take a namespace "shop" with 200 pods, each with a sidecar. A team deploys a new version of the payments service, v2, next to v1 and wants a canary.
First, security. The platform team applies a PeerAuthentication in STRICT mode for namespace shop. Now any plain-text connection to a pod in shop is rejected. The orders pod calls payments; the two sidecars exchange certificates, and the payments proxy sees the caller's identity spiffe://cluster.local/ns/shop/sa/orders. An AuthorizationPolicy on payments allows only that principal, for POST on /charge. A request from the reporting service, whose identity is sa/reporting, gets 403 from the payments sidecar before it reaches the application.
Second, the canary. A VirtualService for payments sends 95% of requests to subset v1 and 5% to subset v2 (subsets are defined in a DestinationRule by pod labels). At 400 requests per second to payments, v2 gets about 20 requests per second. The dashboard shows the 5xx ratio per version, from sidecar metrics. If v2 has an error ratio of 2% against 0.05% for v1, v2 produces 0.4 errors per second from only 20 requests per second, a ratio 40 times higher, and the team sees the difference within a minute. They move the split to 25%, 50% and 100%, or back to 0 in one apply, with no deploy. The rollback needs seconds, since it is an xDS push to the proxies.
Third, the cost. With sidecars, 200 pods × 60 MB ≈ 12 GB of memory and 200 × 0.2 ≈ 40 vCPU at 1,000 requests per second each (the test figure; less at lower traffic, though the memory stays). If the pods run on 20 nodes, the ambient design needs 20 ztunnels at about 12 MB each (240 MB) and perhaps 0.06 vCPU each, plus a handful of waypoints for the services that need L7 rules, for example 3 waypoints × 60 MB. That is more than an order of magnitude less memory for the same mTLS coverage. In exchange, the L4 path loses some L7 features unless a waypoint is added, and failures of a node's ztunnel affect all pods on that node.
Fourth, the push. A rolling update of orders changes the endpoint list. istiod computes the change and sends an incremental EDS update to the sidecars that talk to orders. With 2,000 proxies, a careless configuration where every sidecar knows every service in the cluster makes each push large. The Sidecar resource, which limits a workload's view to the namespaces it calls, can cut the configuration size and memory by an order of magnitude.
intuition: A building's security desk and phone exchange: every call between rooms goes through a trained operator who checks ID, applies the rules, records the call, and can reroute it, and the people in the rooms never need to know how.
The idea is natural because the rules of communication between services are the same everywhere, but applications are written by many teams in many languages. The only place that sees every call is the network path, so putting a programmable proxy there lets one team set policy for all. Separating control plane from data plane follows from scale: policy is decided in one place, and enforced locally, fast, at each hop. Ambient mode applies the same logic to cost: encryption and identity are needed for every packet, but heavy L7 processing is only needed for some services, so the shared, cheap layer should be separate from the optional, expensive one.
mistakes: People often think Istio is a proxy. In fact the proxy is Envoy. Istio is mainly the control plane: it watches Kubernetes, issues identities, converts high-level rules to Envoy configuration and keeps all proxies updated. It also includes the injection and ambient components.
People often think that enabling a mesh makes the whole system secure. In fact mTLS protects traffic between mesh workloads and gives identity, but authorization policies are what restrict who may call what; with the default settings, any workload in the mesh can call any other. It also does not protect against a compromised application, nor traffic to destinations outside the mesh.
People often think a mesh needs no changes in the application. In fact it needs little, but not nothing. Applications must forward trace headers for traces to connect. Retries at the mesh and in the application multiply load. Some protocols, server-first protocols and long-lived connections need care, and applications that start before the sidecar is ready can fail on startup.
People often think ambient mode is just a cheaper sidecar. In fact it is a different architecture with different trade-offs: the L4 and L7 functions are split into two components, identity is held by the node-level ztunnel on behalf of each pod, and the failure and security boundaries change. It is generally available, but some features (multi-cluster support, for example, was still on the roadmap at GA) lagged behind sidecar mode, so check the current feature status.
friction: Operating a mesh is an engineering commitment. Istio adds a control plane to upgrade and monitor, a proxy in every request path, and many custom resources with subtle interactions between them. When a request fails, the cause might be in the application, in the sidecar configuration, in a policy, in mTLS mode, in the control plane push, or in the network. Debugging needs istioctl, Envoy admin output and knowledge of both Istio and Envoy.
Resource use is significant in sidecar mode: tens of megabytes and a fraction of a CPU per pod, growing with the size of the configuration each proxy holds, and each call crosses two proxies, adding latency of the order of a millisecond or less at the median, more at the tail. Sidecar upgrades require pod restarts, and startup and shutdown ordering between the application and the proxy needs care (recent Kubernetes versions with native sidecar containers help). The control plane can become a bottleneck at large scale: configuration pushes to thousands of proxies need scoping and enough istiod replicas.
Ambient mode reduces cost but is newer, with a smaller body of production experience, a different failure model (a node-level component carries traffic for many pods) and gaps in some features and platforms. Finally, many teams adopt a mesh for mTLS alone and end up carrying the whole complexity, when a smaller solution (Cilium encryption, a simple library, or cloud-native features) would have been enough.
practice: Start with a clear reason: mTLS and identity for compliance, canary and traffic control, or uniform telemetry. Adopt step by step. Install in PERMISSIVE mode, add workloads namespace by namespace, check with the telemetry that traffic uses mTLS, then move to STRICT. Prefer the ambient profile for new installs when L4 identity and encryption are the main goals, and add waypoints only for the services that need L7 policy.
Keep the configuration small. Use the Sidecar resource (or ambient's naturally smaller footprint) to limit what each proxy knows, set resource requests and limits for proxies from measurements, and run at least two or three istiod replicas. Use revision-based upgrades (a canary control plane) and test upgrades in a staging mesh. Set timeouts and a small number of retries in the mesh, and remove duplicate retries from applications.
Write default-deny authorization (an empty AuthorizationPolicy in the namespace) and then allow specific identities. Use the Kubernetes Gateway API for ingress and for waypoints where possible. Make sure applications propagate trace headers, and send mesh metrics to Prometheus and traces to your OpenTelemetry pipeline. Learn the debugging commands: istioctl proxy-status, istioctl proxy-config, istioctl analyze, and the Envoy access log response flags. Keep an exit plan: know how to remove the mesh from a namespace without an outage.
tradeoffs: Choose a service mesh (Istio) when you have many services owned by many teams, you need uniform mTLS, authorization and traffic control, and a platform team to run it; choose application libraries or a simple ingress and network policies when you have a few services, one language, and no strict identity requirements. The mesh gives consistency and central control; it costs resources, complexity and a new failure surface.
Choose sidecar mode when you need strong per-pod L7 policy everywhere, per-workload proxy tuning, or features not yet in ambient mode, and you can pay the memory and the restarts; choose ambient mode when most services only need mTLS, identity and L4 policy, cost matters at scale, and you want to avoid restarting pods to upgrade the data plane. Ambient trades some isolation granularity and maturity for lower cost.
Choose Istio when you want the richest L7 feature set and an Envoy-based ecosystem; choose Cilium service mesh or a kernel-level approach when you want to reuse the CNI, avoid proxies for L4 and need only basic L7 features; choose Linkerd when you want a lighter, simpler mesh with its own Rust proxy. Each choice sets how much you control against how much you operate.
Choose mesh-level retries and timeouts for consistent defaults across languages; choose application-level logic when the retry decision depends on business meaning (idempotency, partial results). Doing both without a plan multiplies retries and creates storms.
Choose mTLS in a mesh when you want identity-based security that survives pod movement and IP changes; choose network-level encryption (WireGuard or IPsec in the CNI) when you only need encryption between nodes and not workload identity.
interview: What does istiod do, and what happens to traffic if it goes down? || It serves xDS configuration to proxies, acts as the certificate authority, and injects sidecars via webhook. Running proxies keep their last configuration and certificates, so existing traffic continues. New pods cannot be injected or get certificates, configuration changes and endpoint updates stop propagating, and certificates expire after their 24 hours if renewal never succeeds.
Walk through how a request from A to B is intercepted and secured in sidecar mode. || iptables rules in A's pod redirect the outbound connection to A's Envoy (port 15001). Envoy applies routing from RDS/CDS, picks an endpoint of B, and opens an mTLS connection with A's workload certificate. B's Envoy (inbound redirect to 15006) verifies the certificate and identity, evaluates AuthorizationPolicy, and forwards to the app on localhost. Both proxies emit metrics and spans.
What is the difference between PERMISSIVE and STRICT mTLS, and how do you migrate safely? || PERMISSIVE accepts both plain text and mTLS; STRICT accepts only mTLS. Migrate by installing with PERMISSIVE, enrolling workloads gradually, verifying with telemetry that all traffic is mTLS (including from jobs and non-mesh clients), then switching namespaces to STRICT, with a rollback path.
Why was ambient mode created, and what do you lose by using it? || Sidecars cost memory, CPU and operational pain (pod restarts, ordering, per-pod proxies). Ambient moves L4 mTLS and identity into a shared per-node ztunnel and puts L7 features in optional waypoints. You lose the strict per-pod proxy boundary, you have a node-level shared failure domain, and some features may still lag behind sidecar mode.
Istiod pushes are slow and sidecars use a lot of memory in a 3,000-pod cluster. What do you do? || Every sidecar holds the config of the whole mesh by default. Use the Sidecar resource and exportTo to limit visibility, scale istiod, debounce pushes, check for churny resources, and consider ambient mode. Monitor push time and the size of configuration.
How would you implement a canary with automatic rollback? || Use two subsets or two Deployments with labels, a VirtualService for weights, and metrics (5xx ratio, latency) per version from the mesh telemetry. A progressive-delivery controller (Argo Rollouts or Flagger) adjusts the weights and rolls back when an SLO check fails. Keep session stickiness and database compatibility in mind.

@@ cilium
value: Cilium is a networking and security layer for Kubernetes that runs inside the Linux kernel. When a pod sends a packet, Cilium's eBPF programs, attached to the network path in the kernel, decide where it goes, which backend a Service address points to, whether a policy allows it, and what to record about it. It gives pods their network connections (it is a CNI plugin), replaces kube-proxy for Service load balancing, enforces network policy by workload identity rather than by IP address, encrypts traffic between nodes, and shows who talks to whom with a flow-visibility tool called Hubble.
The problem it solves comes from how Kubernetes networking was first built. Service routing used iptables, a firewall tool whose rules are a long list checked one after another, and policies were written as IP addresses in a world where pods get new IP addresses every few minutes. In a large cluster, the rule list becomes thousands of lines, every change rewrites the whole table, and packet processing time grows with the number of Services. IP-based rules also say nothing about what a pod is. Cilium instead uses hash tables in the kernel (O(1) lookups) and gives each group of pods a numeric security identity derived from its labels, so a rule can say "pods labelled app=web may reach pods labelled app=db on TCP 5432".
It stands on the Linux kernel (L0) and on eBPF (L3): without the kernel's ability to load verified programs at network hooks, Cilium would have to run in user space or use iptables. It stands on containers (L1), because it connects the network namespaces of pods; on security architecture (L1), because it enforces identity-based, least-privilege network rules; and on the service mesh idea (L1), because it can provide mesh features such as mutual authentication and L7 policy without a sidecar in each pod. Cisco bought Isovalent, the company behind Cilium, in 2024, and Cilium graduated from the CNCF in 2023. It is the default or an offered network layer in several managed Kubernetes services.
terms: CNI — the Container Network Interface, the plugin API that Kubernetes calls to give each pod a network interface and an IP address.
eBPF program — a small program that the kernel verifies and runs at a hook, such as a packet arriving on a network interface.
BPF map — a kernel data structure (hash table, array, LRU) shared between eBPF programs and user space, used for services, connections and policy.
Security identity — a number assigned to a set of pods with the same labels; policy is written and enforced in terms of identities.
XDP — eXpress Data Path, a hook in the network driver that runs a program on a packet before the kernel allocates memory for it.
tc hook — a hook in the kernel's traffic control layer, where Cilium attaches programs to each pod's virtual network interface.
Hubble — Cilium's observability layer that reads flow events from eBPF and shows connections, drops and DNS or HTTP details.
kube-proxy replacement — Cilium doing Service load balancing in eBPF, so the kube-proxy component and its iptables rules are not needed.
history: The ideas behind Cilium began when Thomas Graf, a Linux kernel networking developer, saw that containers needed a new kind of network layer. Around 2015, Graf and other kernel networking developers started Cilium to use BPF for container networking and security. They also helped drive the extension of BPF into "eBPF", which Alexei Starovoitov had added to the kernel in 2014, with maps, many more hooks, a verifier and a JIT compiler. The company Isovalent was founded around Cilium in 2017.
Kubernetes was growing, and its default networking had two weak points: kube-proxy with iptables, and IP-based NetworkPolicy. Cilium offered identity-based policy first, then replaced kube-proxy (socket-level load balancing and XDP/tc-based NodePorts), then added observability (Hubble, 2019), multi-cluster connectivity (Cluster Mesh), BGP, encryption with WireGuard, and service mesh features. Tetragon, an eBPF-based runtime security tool, was open-sourced in 2022. Cilium joined the CNCF in 2021 and graduated in October 2023.
Adoption followed. Google chose Cilium for GKE Dataplane V2, Microsoft offers Azure CNI powered by Cilium on AKS, and many companies run it on EKS and on-premises. Cisco announced the acquisition of Isovalent in December 2023 and completed it in 2024. As of October 2026, the current stable release is 1.20. Cilium's documentation lists Linux 5.10 or newer as the recommended kernel, with some features needing newer versions.
how: Cilium has user-space parts that decide and kernel parts that act. The agent on each node (a DaemonSet) watches the Kubernetes API, computes what the node needs, compiles and loads eBPF programs, and fills BPF maps. After that, packets are handled in the kernel without involving the agent. This is the use of the Linux concept and the eBPF concept: eBPF gives safe, fast programs at hooks, and the kernel's verifier, JIT and maps make them practical.
Connecting a pod. When a pod starts, the CNI plugin creates a pair of virtual interfaces (veth), puts one end into the pod's network namespace (the namespaces concept) and the other in the host. The Cilium agent allocates an IP, assigns a security identity from the pod's labels, and attaches eBPF programs at the tc ingress hook of the host-side interface. Every packet leaving the pod hits that program first.
Identity and policy. All pods with the same relevant labels share one numeric identity, say 12345 for app=web and 23456 for app=db. A policy such as "web may reach db on TCP 5432" becomes an entry in a BPF policy map keyed by (identity, port, protocol). When a packet leaves a pod, the program looks up the destination IP in an "ipcache" map to find the destination's identity, then looks up the policy map; the result is allow or drop. If the packet crosses nodes in an overlay tunnel, the sender can put the source identity in the tunnel header (VXLAN or Geneve), so the receiver does not need to look it up. Policy is thus enforced by who the workload is and not by an address that changes when pods restart. For L7 rules (HTTP method and path, DNS names, gRPC), the traffic is sent to an Envoy proxy that Cilium runs on the node, and the decision is made there; plain L3/L4 rules never leave the kernel. This is how Cilium gives some service mesh features (the service mesh concept) without a sidecar in each pod.
Service load balancing. In kube-proxy's iptables mode, each Service becomes a chain of rules, and for each Service with several endpoints, a set of rules chooses one at random with a probability. A packet to a ClusterIP is compared with the Service rules one by one until it matches, so lookup cost grows linearly with the number of Services. Updating rules means rewriting large parts of the table, which can take seconds or longer in big clusters, during which changes lag. Cilium puts Services in BPF hash maps: a lookup by (IP, port, protocol) finds the Service, and a second map holds its backends. For the common case of a pod connecting to a Service, Cilium attaches programs to the cgroup socket hooks (connect, sendmsg, recvmsg). When the application calls connect() to the ClusterIP, the program changes the destination to a chosen backend address before any packet exists. The pod and the network only ever see the backend IP; no per-packet translation (DNAT) or connection tracking entry for it is needed. For traffic from outside (NodePort, LoadBalancer), programs at XDP or tc do the lookup, using Maglev consistent hashing so that backend choices stay stable when backends change, and can forward directly (direct server return).
Datapath and routing. Packets between pods on the same node can be redirected straight to the other pod's veth with helper functions such as bpf_redirect_peer, skipping much of the host's networking stack, which lowers latency and CPU. Between nodes, Cilium uses either an overlay (VXLAN or Geneve) or native routing in the underlying network (including cloud routing or BGP). Optional features are implemented in the same way: transparent encryption with WireGuard or IPsec, bandwidth limits using the Earliest Departure Time model, and a host firewall.
Observability. Because every packet passes through eBPF programs, Cilium can emit events for each flow: source and destination identity, verdict (forwarded, dropped by policy), and for L7 traffic the HTTP or DNS details. Hubble collects these from each node into a per-node buffer and a relay that provides a cluster-wide view, with a CLI and a UI. A policy drop that would take hours to debug with iptables logs becomes a one-line answer: "web to db port 5433 dropped by policy".

example: Take a cluster with 5,000 Services and 20,000 pods. A "web" pod calls the "db" Service at 10.96.0.50:5432, which has 3 backend pods.
The iptables way first. The packet is checked against the KUBE-SERVICES chain, a long list with at least a few rules per Service. In the worst case it passes thousands of rules before a match, on the order of tens of microseconds in total per new connection, and a lot of CPU when new connections are frequent. Then a rule with a probability picks one of the three backends (1/3, then 1/2, then the rest), and DNAT rewrites the destination, with an entry in the connection tracking table. When a Service gains an endpoint, kube-proxy must regenerate rules; with tens of thousands of rules, a sync can take several seconds and use noticeable CPU, and new endpoints are not reachable until it finishes.
The Cilium way. The application calls connect() to 10.96.0.50:5432. The cgroup program looks up that address in the service map (one hash lookup, the same cost with 50 or with 50,000 Services), selects backend 10.0.1.17 using the backend map, and rewrites the socket's destination before the SYN is sent. The packet leaves the pod already addressed to the real backend. At the veth, the tc program looks up the destination in ipcache, gets identity 23456, and checks the policy map for the key (12345, TCP, 5432). The entry exists, so the packet is allowed. If the backend is on the same node, it is redirected directly to the other pod's interface. Adding a fourth backend means inserting one entry in a BPF map, which takes microseconds and does not disturb the other entries.
Now a policy change. A developer applies a CiliumNetworkPolicy saying that db accepts TCP 5432 only from pods with the label app=web. The agent computes the identities that match, and inserts keys into db's policy map. Another pod, with label app=batch (identity 34567), tries to connect: the lookup of (34567, TCP, 5432) finds nothing, and the packet is dropped and logged. Hubble shows the drop with both identities and the policy verdict within a second. No IP list needs updating when pods restart or scale.
Finally an L7 rule: allow web to call GET /api/orders on the "orders" service but not DELETE. The L3/L4 part is still checked in the kernel. Traffic that matches an L7 rule is redirected to the node-local Envoy, which parses the HTTP request and applies the rule. This costs more per request than the in-kernel path, so L7 rules should be used where they are needed.
intuition: Instead of a doorman reading a long, ever-changing list of addresses, give every visitor a badge at the entrance and put a lock that reads the badge on each door.
The design is natural because the kernel already sees every packet, and the information needed to decide (who is the sender, which Service is this, is it allowed) can be kept in a few hash tables that are cheap to look up and cheap to update. iptables was designed for firewalls with a few hundred static rules; Kubernetes has thousands of rules that change constantly. Using identities makes policy follow the workload, not its address. And because the code runs in the kernel at the point of the decision, no packet needs to make a detour through a user-space proxy unless it truly needs application-level inspection.
mistakes: People often think Cilium is a service mesh like Istio. In fact the core of Cilium is a CNI with network policy and load balancing in eBPF. It can offer some mesh features (mutual authentication, L7 policy and routing through per-node Envoy), but it is not a drop-in copy of Istio, and its L7 feature set is smaller.
People often think eBPF means no overhead and no proxy. In fact L3/L4 processing in eBPF is very cheap, but any L7 inspection (HTTP rules, gRPC routing) still needs a proxy, so Cilium sends that traffic to Envoy. The saving is that there is one proxy per node, not one per pod, and only for traffic that needs it.
People often think replacing kube-proxy is only a speed optimization. In fact it also changes behaviour: client source IP preservation, direct server return, session affinity, graceful backend termination and debugging tools all differ. Test those on your workloads before switching.
People often think IP-based and identity-based policy are equivalent. In fact identity follows the labels, so a restarted pod with a new IP keeps its permissions, and a pod whose labels change loses them at once. The labels must therefore be protected: whoever can change labels can change what a pod is allowed to do.
People often think any Linux kernel will do. In fact many Cilium features need specific kernel versions and configuration options, and the base requirement is Linux 5.10 or newer for current releases, so old node images and some managed distributions limit what is available.
friction: Cilium puts a complex piece of software in the critical path of all pod traffic. A bug in a program, a map that fills up (a full conntrack or policy map drops packets), a failed agent upgrade or a verifier problem can affect connectivity, and the failure messages come from the kernel rather than from friendly logs. Debugging needs the cilium and hubble CLIs, bpftool, and an understanding of maps, hooks and identities, not only of kubectl.
The dependency on the kernel is real. Features are tied to kernel versions (for example IPv6 BIG TCP needs 5.19, IPv4 BIG TCP needs 6.3 and netkit devices need 6.8), the verifier limits program size and complexity, and kernels from some distributions backport features unevenly. Upgrades of nodes and of Cilium must be coordinated, and Cilium's own release cadence is fast, with several minor versions supported at a time.
Operational and ecosystem questions follow. Overlay networking adds encapsulation overhead (about 50 bytes per packet for VXLAN), and native routing needs support from the underlying network. Identity-based policy depends on label hygiene, and the number of identities can grow in clusters with very varied labels. L7 features, service mesh mode and some mutual authentication features are younger and have less field experience than the datapath. Finally, a large part of the project's development is led by one company, now part of Cisco, which some organizations weigh when they plan long-term support, although it is a CNCF graduated project with a broad community.
practice: Choose the mode with the kernel in mind. Check that your node images run Linux 5.10 or newer (a recent LTS kernel is better), enable kube-proxy replacement on new clusters, and use native routing where your cloud or network allows it, since it avoids encapsulation. Use the cloud's recommended integration (for example the Cilium-powered dataplane of your managed Kubernetes) if you want vendor support.
Start policy in observation mode. Turn on Hubble, watch the flows, and write CiliumNetworkPolicy rules from what you see. Then adopt default deny per namespace, with explicit allows for DNS and for the required paths. Use identity-based selectors and namespaces, keep labels under control (restrict who may set the labels used in policy), and add L7 rules only where the benefit justifies the cost of the proxy.
Watch the health of the datapath: agent status, BPF map pressure (cilium-dbg status, metrics for map entries), drops by reason, endpoint regeneration times, and kernel logs. Size conntrack and policy maps for peak load. Test upgrades one node pool at a time, with the supported version skew, and keep the agent's resource requests realistic. Use Cluster Mesh when you need cross-cluster Services and policy, WireGuard for node-to-node encryption, and Tetragon when you want process-level runtime visibility.
For a service mesh, decide what you need. If you only need mutual authentication, identity policy and basic L7, Cilium's sidecar-free approach is simpler; if you need rich L7 traffic management, retries and a large ecosystem, use Istio (possibly ambient mode) and let Cilium handle the CNI and L3/L4 policy underneath.
tradeoffs: Choose Cilium when your clusters are large or fast-changing, you want identity-based policy and flow visibility, and you control a recent kernel; choose a simpler CNI (the cloud provider's native CNI, Calico in iptables mode, Flannel) when the cluster is small, the requirements are basic, or the nodes run old kernels. Cilium buys speed, scale and visibility, and costs complexity and kernel dependence.
Choose Cilium's kube-proxy replacement when Service counts or churn make iptables slow, or you want features such as Maglev and direct server return; stay with kube-proxy (now with an nftables backend) when the cluster is modest and you value the simplicity of well-known tools. The gain is mostly visible above thousands of Services.
Choose native routing when the network can route pod IPs (cloud routes, BGP) and you want the lowest overhead; choose an overlay (VXLAN or Geneve) when you cannot change the underlying network, and accept encapsulation overhead and reduced MTU.
Choose Cilium for a sidecar-free mesh when L4 identity, mutual authentication and simple L7 rules are enough; choose Istio when you need advanced traffic management, a larger policy model and a mature L7 ecosystem. Istio ambient mode also drops sidecars, so the real question is feature depth against the number of components you want to operate.
Choose WireGuard transparent encryption for simple node-to-node protection; choose mTLS with workload identity (mesh) when compliance requires per-workload authentication, accepting that it costs more CPU and operations.
interview: Why is kube-proxy in iptables mode a scaling problem, and how does Cilium avoid it? || iptables evaluates rules linearly, so lookup time grows with the number of Services and endpoints, and each update rewrites large parts of the rule set, which is slow and holds locks. Cilium keeps Services and backends in BPF hash maps with constant-time lookups and updates individual entries, and at connect() time it can pick the backend at the socket layer so that no per-packet NAT is needed.
How does identity-based policy work in Cilium, and what are the risks? || Pods with the same labels get one numeric identity. The datapath finds the destination identity with an ipcache lookup (or reads the source identity from tunnel metadata) and checks a policy map keyed by identity, port and protocol. Policy follows pods across IP changes. The risk is label governance: whoever can set labels can change a pod's permissions.
A pod cannot reach a Service after enabling a default-deny policy. How do you debug it? || Use Hubble to observe flows between the two identities and see the drop reason. Check for missing allows for DNS (kube-dns), the right selectors and namespaces, whether the policy is applied to ingress or egress, and endpoint policy state with the cilium CLI. Then add the needed rule and confirm in Hubble.
Where does Cilium still use a proxy, and why? || For L7 rules and L7 routing (HTTP paths, gRPC, DNS-aware policy and some mesh features), traffic is redirected to a node-local Envoy, because parsing application protocols is too complex and stateful for an in-kernel program. L3/L4 stay in eBPF. So the cost of L7 is paid only where the policy requires it.
What kernel and operational dependencies come with Cilium? || It needs a recent kernel (5.10 or newer for current releases) with the right BPF options; some features need newer kernels. Programs must pass the verifier, maps need correct sizing, and node and Cilium upgrades must be coordinated. Debugging requires bpftool and Cilium tools, not just iptables knowledge.
Compare Cilium service mesh and Istio ambient mode. || Both avoid per-pod sidecars. Cilium implements identity, L3/L4 policy and encryption in the eBPF datapath and uses a per-node Envoy for L7. Istio ambient uses a per-node ztunnel for L4 mTLS with HBONE and Envoy waypoints for L7. Istio has the richer L7 and traffic API and ecosystem; Cilium integrates with the CNI and can enforce policy in the kernel.
quiz: What is a security identity in Cilium? || A number assigned to all pods with the same relevant labels. Policy rules are stored and enforced in terms of identities, so they stay valid when pod IPs change.
Why does socket-level load balancing avoid per-packet NAT? || A cgroup hook rewrites the destination of the connect() call from the Service IP to a backend IP before any packet is created, so the pod and the network only ever see the backend address.
Which traffic does Cilium send to Envoy? || Traffic that matches L7 policy or L7 routing rules (such as HTTP method and path). L3 and L4 decisions are made entirely by eBPF programs in the kernel.
A cluster has 10,000 Services. Compare the lookup cost of finding a Service in an iptables chain versus a BPF hash map. || A linear chain may check up to thousands of rules per new connection, so cost is O(n), and updates rewrite many rules. A hash map lookup is O(1), about the same cost with 10 or 10,000 Services, and an update changes one entry.
When would you not choose Cilium? || When nodes run old kernels, the cluster is small with basic needs, or the team cannot operate eBPF-based networking. A cloud-native CNI or a simpler plugin is then easier to run and to debug.
