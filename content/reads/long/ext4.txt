@@+ replication
history: Replication is as old as reliable computing. Tandem's NonStop systems (1970s) paired processes and disks so a failure would not stop a bank's transactions. Database replication spread in the 1980s and 1990s, mostly as primary–backup log shipping. Research in that period formalized what replicas can guarantee: state machine replication (Lamport, Schneider), Viewstamped Replication (1988), Paxos (1989/1998), and later chain replication (2004), which gives strong consistency with high throughput by passing writes down a chain.
The web era added a different school. Amazon's Dynamo (2007) chose leaderless replication with quorums and eventual consistency for availability, and Cassandra and Riak followed. Google's Bigtable relied on a replicated file system, then Spanner (2012) made synchronous, globally replicated transactions practical with Paxos and TrueTime. Kafka (2013) brought leader–follower replication with an in-sync replica set to streaming. Today most systems mix both schools: consensus for metadata, and leader–follower or quorum replication for bulk data.
how: The key design choice is when a write counts as done. Synchronous replication waits for replicas before acknowledging, so a failover loses nothing, but every write pays the slowest replica's latency. Asynchronous replication acknowledges immediately and ships changes later, so writes are fast, but a failover can lose the last few seconds. Semi-synchronous designs wait for one replica, or for a quorum. Kafka's acks=all with min.insync.replicas=2 is semi-synchronous over a dynamic set of healthy replicas.
What is replicated also matters. Physical replication ships storage-level changes (PostgreSQL WAL records, page writes), which is exact and efficient but ties replicas to the same version and layout. Logical replication ships row-level changes (inserts, updates, deletes), which allows different versions, selective tables and feeding other systems, as change data capture does. Statement replication ships SQL statements, which breaks on non-deterministic functions and is rarely used now.
Failover is where replication systems are tested. The new leader must have every acknowledged write; the old leader must be stopped from accepting writes (fencing, epochs, terms); clients must find the new leader; and replicas that diverged must truncate their extra entries. Automating this safely usually requires consensus, which is why systems like Patroni (for PostgreSQL) use etcd, and Kafka uses its KRaft controllers.
practice: Write down three numbers for any replicated system you run: the recovery point objective (how much data you can lose), the recovery time objective (how long you can be down) and the read-staleness you can tolerate. Then check that your replication mode and settings actually meet them, and test failover on a schedule rather than during an incident.
Monitor replication lag in time, not only in bytes. Route reads that must see a user's own writes to the leader, or use read-your-writes techniques (session tokens, waiting for a replica to reach a given log position). Place replicas in separate failure domains, and remember that replicas protect against hardware failure, not against bad writes: you still need backups and point-in-time recovery for mistakes and corruption.
ref: paper | Chain Replication for Supporting High Throughput and Availability | van Renesse & Schneider, OSDI 2004 |
ref: docs | PostgreSQL: High Availability, Load Balancing, and Replication | PostgreSQL | https://www.postgresql.org/docs/current/high-availability.html

@@+ partitioning
history: Partitioning large data across machines goes back to parallel database research in the 1980s: Gamma (DeWitt and colleagues) and Teradata hashed tables across nodes so each processor scanned only its share. The web era made it unavoidable. Consistent hashing (Karger and colleagues, 1997) let caches add and remove nodes without reshuffling everything, and became the core of Dynamo, Cassandra and many caches. Bigtable (2006) used range partitioning into tablets that split and move automatically, a design followed by HBase, Spanner, CockroachDB and TiKV.
Streaming and analytics then made partitioning visible to users. Kafka exposed partitions directly as the unit of ordering and parallelism. MapReduce and Spark made the shuffle (repartitioning by key) the central cost of distributed computation. Data lakes partitioned files into directories by date and other columns, and lakehouses later added clustering so that layout could adapt without fixed directory schemes.
how: Three questions define a partitioning scheme. What is the key? It should spread load evenly and keep together the data that is used together (all of a user's events, all of a tenant's rows). How are keys mapped to partitions? Hashing spreads keys evenly but destroys order, so range queries touch every partition; range partitioning keeps order and makes scans efficient but risks hot spots at the end of the key space (for example, time-ordered keys all landing on the newest partition). How are partitions mapped to machines, and how do they move? Fixed partition counts with many partitions per machine (Kafka, Elasticsearch shards, Cassandra virtual nodes) make rebalancing a matter of moving whole partitions; dynamic splitting (Bigtable, CockroachDB) splits ranges as they grow.
Secondary indexes add a further choice. Local indexes (each partition indexes its own data) make writes cheap but force reads by the indexed field to query every partition (scatter–gather). Global indexes (partitioned by the indexed field) make those reads targeted but turn each write into a distributed update.
practice: Choose partition keys from the access pattern, not the data model. For Kafka and Pinot, use the key that downstream joins and aggregations group by, so related events stay together and no reshuffle is needed. Estimate the hottest key: if one customer or device can produce a large share of traffic, add a salt or a sub-key, accepting that per-key ordering then becomes per-sub-key ordering.
Size partition counts for growth: changing them later is disruptive in Kafka (key-to-partition mapping changes) and costly in Elasticsearch (reindex or split). Watch for skew continuously: per-partition throughput, size and lag reveal hot keys long before they cause outages. In Spark and lakehouse tables, partition coarsely (by date, perhaps tenant) and use clustering for the rest, because too many small partitions are as harmful as too few.
ref: paper | Gamma: A High Performance Dataflow Database Machine | DeWitt et al., VLDB 1986 |
ref: paper | Bigtable: A Distributed Storage System for Structured Data | Chang et al., OSDI 2006 |

@@+ lsm
history: Patrick O'Neil and colleagues published the log-structured merge-tree in 1996, motivated by workloads with far more inserts than reads, on disks where random writes were expensive. Earlier, Rosenblum and Ousterhout's log-structured file system (1991) had shown the power of turning all writes into sequential appends. Google's Bigtable (2006) brought the design to large-scale storage with memtables and SSTables; LevelDB (2011) open-sourced a compact version, and Facebook forked it as RocksDB (2012), adding many compaction strategies and tuning options.
RocksDB became the default embedded storage engine for distributed systems: Kafka Streams and Flink state, CockroachDB (until it built Pebble, a Go reimplementation), TiKV, MyRocks for MySQL at Facebook, and many others. Research since then (Monkey, Dostoevsky, WiscKey and others) has focused on tuning the trade-off between read, write and space amplification, separating large values from keys, and adapting to flash and NVMe devices.
how: The heart of LSM performance is the amplification trade-off. Write amplification is how many times each byte is rewritten by compaction; read amplification is how many files a lookup must check; space amplification is how much extra space obsolete versions take. Leveled compaction (each level about 10× larger, with non-overlapping files per level) keeps reads and space low but rewrites data many times. Tiered (universal) compaction merges whole runs less often, cutting write amplification but leaving more overlapping files to search. Bloom filters per file and a block cache make most point lookups touch at most one file on disk.
Deletes are writes too: a delete inserts a tombstone that hides older values until compaction drops both, which is why delete-heavy workloads can slow down range scans until compaction catches up. Range scans must merge iterators over the memtable and every level, so they are more expensive than in a B-tree.
practice: Tune an LSM engine around your dominant workload. For write-heavy ingestion, allow larger memtables and consider tiered compaction; for read-heavy point lookups, use leveled compaction, enough Bloom-filter bits per key (about 10 for roughly 1% false positives) and a generous block cache. Watch compaction debt (pending compaction bytes) and write stalls, which are the usual cause of sudden latency spikes.
Give compaction enough disk bandwidth headroom, prefer fast NVMe for hot levels, and avoid workloads that delete large ranges key by key; use range deletes or time-based partitioning instead. In stream processors that keep state in RocksDB (Flink, Kafka Streams), keep state bounded with time-to-live and watch state size per task, since it directly affects checkpoint and recovery time.
ref: paper | WiscKey: Separating Keys from Values in SSD-conscious Storage | Lu et al., FAST 2016 |
ref: docs | RocksDB Tuning Guide | RocksDB wiki | https://github.com/facebook/rocksdb/wiki/RocksDB-Tuning-Guide

@@+ btree
history: Rudolf Bayer and Edward McCreight invented the B-tree at Boeing Research Labs in 1970 (published 1972), to index large files on disks where each read fetched a whole block. Douglas Comer's 1979 survey called it 'ubiquitous', which it still is. The B+tree variant, with all values in the leaves and leaves linked for range scans, became the standard index in IBM's System R and nearly every relational database since.
Later work adapted the design to concurrency and new hardware. Lehman and Yao's B-link trees (1981) allowed concurrent access with minimal locking. Write-optimized variants (fractal trees, Bε-trees) buffer updates in internal nodes. In-memory and latch-free versions (the Bw-tree in Microsoft's Hekaton, 2013) and cache-conscious layouts responded to multicore CPUs and RAM-resident data. On flash, copy-on-write B-trees (as in LMDB and Btrfs) avoid in-place updates. Despite LSM trees' rise for write-heavy workloads, B-trees remain the default for transactional databases: PostgreSQL, MySQL InnoDB, SQLite, Oracle and SQL Server.
how: Fan-out explains why B-trees are so fast. With 8 KB pages and keys of a few dozen bytes, each internal node holds hundreds of children, so a tree over a billion rows is only three or four levels deep, and the top levels stay cached in memory. A point lookup typically needs one or two actual disk reads. Splits and merges keep every leaf at the same depth, and leaves are kept at least half full.
Concurrency control is the hard part. Readers and writers coordinate with short-lived latches on pages; 'latch crabbing' holds a parent's latch only until it is clear the child will not split. Crash safety comes from the write-ahead log, which records page changes so that a half-finished split can be redone or undone during recovery. Clustered indexes (InnoDB) store rows in the primary-key B-tree itself; heap-organized tables (PostgreSQL) keep rows separately and point to them from every index.
practice: Index for your queries: put equality columns first and range columns last in composite indexes, and include extra columns (covering indexes) when they let a query skip the table entirely. Avoid random primary keys in clustered-index databases like InnoDB, which cause page splits across the whole tree; time-ordered IDs (for example UUIDv7) keep inserts at the right edge.
Watch index bloat and fill factors on update-heavy tables, rebuild or reindex when needed, and drop unused indexes, since every index slows every write. When an index exists but is not used, read the query plan: type mismatches, functions on the column and low selectivity are the usual causes.
ref: paper | The Ubiquitous B-Tree | Douglas Comer, ACM Computing Surveys 1979 |
ref: paper | Efficient Locking for Concurrent Operations on B-Trees | Lehman & Yao, ACM TODS 1981 |

@@+ mvcc
history: Multi-version concurrency control was described by David Reed in his 1978 MIT thesis and formalized by Bernstein and Goodman in the early 1980s. Commercial systems adopted it from the 1980s: InterBase and Oracle (with rollback segments that rebuild old versions) were early, and PostgreSQL adopted MVCC in 1999. Snapshot isolation was defined in Berenson and colleagues' 1995 critique of SQL isolation levels, which also showed that it permits write skew.
The 2000s and 2010s fixed and extended it. Serializable Snapshot Isolation (Cahill, Röhm and Fekete, 2008) detects the dangerous patterns of read–write dependencies and aborts one transaction, making snapshot isolation serializable; PostgreSQL implemented it in 9.1 (2011). Distributed databases (Spanner, CockroachDB, TiDB) use MVCC with timestamps from TrueTime, hybrid logical clocks or a timestamp oracle. Lakehouse formats apply the same idea at file granularity: each commit is a new table version, and readers see a consistent snapshot.
how: Implementations differ mainly in where old versions live and how they are found. Append-only storage (PostgreSQL) writes each new version as a new tuple in the table and links versions; old versions stay in the table until vacuum removes them. Delta storage (Oracle, MySQL InnoDB) updates rows in place and keeps the previous values in an undo log, rebuilding old versions on demand for readers that need them. Time-travel storage keeps old versions in a separate area. Each choice trades write cost, read cost for old snapshots and cleanup work differently.
Garbage collection is the other half. A version can be removed only when no active transaction might still need it, so the oldest running transaction sets the horizon. Long-running transactions, idle sessions holding snapshots and abandoned replication slots stop cleanup for the whole database, which is the most common cause of MVCC bloat.
practice: Keep transactions short, and never leave sessions 'idle in transaction'. Monitor the age of the oldest snapshot and the dead-tuple counts (in PostgreSQL, pg_stat_activity and pg_stat_user_tables), and alert well before transaction-ID wraparound becomes a risk.
Choose the isolation level deliberately. Snapshot isolation (REPEATABLE READ in PostgreSQL) is enough for most reads; for business rules that span rows (only one on-call doctor, no overbooking), use SERIALIZABLE and retry on serialization failures, or enforce the rule with explicit locks or constraints. In lakehouse tables, the same thinking applies: old table versions are kept for time travel until vacuum or snapshot expiry, so set retention to balance recoverability against storage cost.
ref: paper | Serializable Isolation for Snapshot Databases | Cahill, Röhm & Fekete, SIGMOD 2008 |
ref: paper | An Empirical Evaluation of In-Memory Multi-Version Concurrency Control | Wu, Arulraj, Lin, Xian & Pavlo, VLDB 2017 |

@@+ columnar
history: Storing tables by column dates back to the 1970s (Cantor in Sweden, TAXIR for biology data), and Copeland and Khoshafian's decomposition storage model (1985) analysed it formally. Sybase IQ commercialized it in the 1990s for data warehouses. The modern wave began in 2005 with C-Store (Stonebraker and colleagues, commercialized as Vertica) and MonetDB/X100 (commercialized as Vectorwise), which showed order-of-magnitude gains on analytic queries from columnar storage, compression and vectorized execution together.
Google's Dremel (2010) brought columnar storage to nested data at web scale, and its encoding of repeated and optional fields inspired Apache Parquet (2013, from Twitter and Cloudera); Apache ORC came from the Hive community the same year. Apache Arrow (2016) standardized a columnar format in memory, so tools could exchange data without conversion. Today almost every analytic system, from Snowflake and BigQuery to DuckDB, ClickHouse, Pinot and every lakehouse, stores data in columns.
how: Parquet shows the typical layout. A file is split into row groups (often 128 MB or so); within each row group, each column is stored as a column chunk, split into pages. Each page is encoded (dictionary, run-length, bit-packing, delta) and then optionally compressed (Snappy, Zstd). The file footer holds the schema and statistics (min, max, null count) for every column chunk, so readers can skip row groups. Nested data uses repetition and definition levels to record where lists start and which optional fields are missing.
Execution engines take advantage of the layout in memory too. Arrow arrays store values contiguously with a separate validity bitmap for nulls, so loops over a column are branch-free and SIMD-friendly. Late materialization keeps working on compressed or encoded columns and builds full rows only for the final results. Some engines even evaluate filters directly on dictionary codes or run-length runs without decoding.
practice: Write columnar files with enough rows per row group and file (hundreds of MB) to get good compression and few requests per query; tiny files and tiny row groups destroy the benefits. Sort or cluster data on common filter columns before writing, so min/max statistics become selective. Choose Zstd for a good balance of size and speed on cold data, and Snappy or LZ4 where decompression speed matters most.
Select only the columns you need: SELECT * on a wide table throws away the main advantage. For frequently updated data, remember that columnar files are immutable; use table formats with deletion vectors or merge-on-read, and compact regularly.
ref: spec | Apache Parquet file format | Apache Parquet | https://parquet.apache.org/docs/file-format/
ref: spec | Arrow Columnar Format | Apache Arrow | https://arrow.apache.org/docs/format/Columnar.html
