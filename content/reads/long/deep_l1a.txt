@@ cdc
value: Change data capture turns every committed change in a database (each insert, update and delete) into an ordered stream of events that other systems can consume. It is the reliable way to keep search indexes, caches, analytics tables, lakehouses and other services in sync with an operational database, without dual writes from application code and without nightly bulk copies.
The value is freshness with correctness. Because CDC reads the database's own commit log, it sees exactly what was committed, in commit order, including deletes, and it does not add load from repeated queries. It also decouples teams: the service that owns the database does not need to know who consumes its changes.
history: Databases have always had internal logs for recovery and replication; for decades, integrating data meant periodic batch extracts (ETL) or triggers that wrote changes into shadow tables. Commercial log-based replication tools (Oracle GoldenGate, founded 1995; IBM InfoSphere) brought CDC to enterprises. The open-source wave came with Kafka: LinkedIn's Databus (2012) streamed changes from Oracle and MySQL, and Red Hat's Debezium (2016) built CDC connectors for MySQL, PostgreSQL, MongoDB and others on Kafka Connect.
PostgreSQL's logical decoding (9.4, 2014) made it possible to read row changes from the WAL in a pluggable format. Cloud services added managed CDC (AWS DMS, Google Datastream, Fivetran and Airbyte connectors), and lakehouse formats added the reverse direction: table change feeds (Delta's change data feed, Iceberg's row lineage) so that downstream tables can be updated incrementally.
how: A CDC connector attaches to the database's replication interface: the MySQL binlog in row format, PostgreSQL logical replication slots with the pgoutput plugin, MongoDB change streams, SQL Server's change tables. It usually begins with a consistent snapshot of existing rows, then switches to streaming changes from the log position recorded at the snapshot, so nothing is missed or duplicated. Each change event carries the operation type, the before and after images of the row (where available), the source position (log sequence number or binlog offset) and the transaction ID.
Events are published to Kafka, typically one topic per table, keyed by primary key so that all changes to a row stay in order in one partition. The connector stores its log position (in Kafka Connect offsets) so it can resume after restarts; processing is at least once, so consumers must be idempotent or deduplicate by position. Schema changes are captured and versioned through a schema registry. Downstream, consumers apply events as upserts and deletes to targets (search indexes, caches, Delta or Iceberg tables via MERGE), often compacting topics so the latest value per key is kept.
The layers below make this possible: the write-ahead log (Layer 2) is the source; log compaction and partitioning (Layer 2) organize the stream; idempotence (Layer 2) makes replays safe; and transactions and recovery (Layer 3) define what 'committed' means.
intuition: Instead of photocopying the whole filing cabinet every night, read the clerk's diary of every change as it is written, and replay it wherever a copy is needed.
friction: Replication slots and binlog retention must be monitored: if a CDC consumer stops, PostgreSQL keeps WAL for its slot and disks fill up. Initial snapshots of large tables are slow and must be coordinated with streaming. Schema changes (renames, type changes) can break consumers; exposing internal table structures as events couples downstream teams to the database design, which is why many teams prefer the outbox pattern for public events.
Ordering is per key, not global, so cross-table consistency (an order and its line items) needs transaction metadata or careful design. Deletes need tombstones that downstream systems handle correctly. And at-least-once delivery means duplicates after restarts.
practice: Monitor replication lag and log retention on the source (replication slot size in PostgreSQL, binlog retention in MySQL) and alert before disks are at risk. Key topics by primary key and use compacted topics for current-state consumers. Register schemas with compatibility rules, and treat breaking schema changes as coordinated migrations.
For events other teams depend on, publish deliberate domain events via an outbox table rather than raw table changes. Make every consumer idempotent (upserts keyed by primary key, with the source log position used to ignore stale updates), and test recovery: stop a consumer for an hour and confirm it catches up correctly.

@@ llmserving
value: LLM serving is the engineering of running large language models for many users at acceptable latency and cost. Training happens once; inference runs every time anyone uses the model, so for most companies serving costs dominate. A good serving stack can deliver several times more tokens per GPU than a naive one, which directly decides product margins and how responsive applications feel.
Serving systems (vLLM, SGLang, TensorRT-LLM, Hugging Face TGI, llama.cpp, and the internal stacks of model providers) also decide what features are cheap: long contexts, prompt caching, structured output, many fine-tuned adapters on one base model, and agent workloads that resend long histories.
history: Early transformer serving reused general model servers (TensorFlow Serving, NVIDIA Triton Inference Server) with static batching. As models grew to tens and hundreds of billions of parameters, specialized systems appeared: FasterTransformer (NVIDIA), DeepSpeed-Inference, and Orca (2022), which introduced iteration-level (continuous) batching. vLLM (2023) introduced PagedAttention and quickly became the most widely used open-source server; SGLang (2023–2024) added RadixAttention for prefix sharing and fast structured generation; TensorRT-LLM optimized kernels for NVIDIA hardware.
From 2024 the focus shifted to long contexts, speculative decoding, FP8 and FP4 quantization, mixture-of-experts serving with expert parallelism, chunked prefill and disaggregated prefill/decode clusters, and KV-cache offloading to CPU memory and SSDs. Reasoning models and agents, which generate and resend many more tokens per task, made efficiency even more important.
how: Inference has two phases. Prefill processes the whole prompt in parallel and produces the first token; it is compute-bound and sets time to first token. Decode generates one token per step per request, reading all model weights and the request's KV cache from GPU memory each step; it is memory-bandwidth-bound and sets time per output token. The serving engine's job is to keep the GPU's arithmetic busy despite decode's low arithmetic intensity, mainly by batching many requests together.
The core techniques work as a set. Continuous batching adds and removes requests at every step. PagedAttention stores each request's KV cache in fixed-size blocks, avoiding fragmentation so more requests fit. Prefix caching reuses KV blocks for shared prompt prefixes (system prompts, documents, conversation history). Chunked prefill and disaggregation stop long prompts from stalling decodes. Quantization (FP8 or INT4 weights, FP8 KV cache) cuts memory and bandwidth. Speculative decoding drafts several tokens cheaply and verifies them in one pass. Large models are split across GPUs with tensor and pipeline parallelism, and MoE models spread experts across GPUs.
A scheduler sits on top: it admits requests based on available KV-cache memory, prioritizes, preempts (swapping or recomputing the cache of evicted requests) and routes requests to replicas, ideally to the one that already holds a matching prefix. Metrics that matter are time to first token, inter-token latency, throughput (tokens per second per GPU) and goodput (requests that meet latency targets).
intuition: A restaurant kitchen where each dish needs one quick step per minute for a long time: you make money only by cooking many dishes side by side, keeping the counters (GPU memory) tidy, and reusing prep work that several orders share.
friction: Latency and throughput pull against each other: bigger batches raise throughput but slow each user. KV-cache memory limits concurrency, especially with long contexts. Workloads are unpredictable (prompt and output lengths vary by orders of magnitude), making capacity planning and autoscaling hard, and GPU cold starts (loading tens of gigabytes of weights) are slow.
Quantization and speculative decoding can change outputs subtly; cache-aware routing conflicts with simple load balancing; and every new model architecture (new attention variants, MoE layouts) needs new kernels before it runs efficiently.
practice: Define service-level objectives first (for example, p95 time to first token under 1 s and inter-token latency under 50 ms), then load-test with realistic prompt and output length distributions, measuring goodput rather than peak throughput. Put stable content at the start of prompts so prefix caching works, and route requests by prefix where possible.
Start with a mature engine (vLLM, SGLang or TensorRT-LLM), enable FP8 where accuracy holds, and tune maximum batch size and chunked prefill for your latency targets. Track cost per million tokens by model and feature, and use smaller or distilled models for the traffic that does not need the largest one.

@@ rag
value: Retrieval-augmented generation gives a language model the right information at the moment it answers: relevant passages from documents, tickets, code, knowledge bases or databases are retrieved and placed into the prompt. It lets models answer questions about private and fresh data they were never trained on, with citations, and it is usually far cheaper and safer than fine-tuning a model on that data.
RAG is the backbone of enterprise assistants, support bots, internal search, coding assistants that read a repository, and agents that look things up before acting. Its quality depends less on the language model than on retrieval: if the right passage is not retrieved, the model cannot use it.
history: Open-domain question answering combined retrieval and reading long before LLMs (DrQA, 2017). Dense passage retrieval (DPR, 2020) showed that learned embeddings could beat keyword search for finding answer passages. The 2020 paper by Lewis and colleagues named retrieval-augmented generation, training a retriever and generator together. With ChatGPT (2022) and long-context models, RAG became the default architecture for 'chat with your data', and vector databases boomed.
Practice then matured: hybrid search combining BM25 and embeddings, re-ranking with cross-encoders, better chunking, query rewriting, evaluation frameworks, and 'agentic RAG' where the model decides what to search for, iteratively. Long-context models (hundreds of thousands to millions of tokens) reduced but did not remove the need for retrieval, because cost, latency and accuracy still favour putting only the relevant parts in context.
how: Indexing: documents are cleaned, split into chunks (by structure such as headings, or by length with overlap), enriched with metadata (source, date, permissions), embedded with an embedding model and stored in a vector index (HNSW or IVF), often alongside a keyword index. Retrieval: the user's question (possibly rewritten or expanded by the model) is embedded and used for approximate nearest-neighbour search, combined with BM25 keyword search and metadata filters; results are merged (for example with reciprocal rank fusion) and re-ranked by a cross-encoder that reads query and passage together. Generation: the top passages are placed in the prompt with instructions to answer from them and cite sources.
Each step relies on lower layers: embeddings and contrastive learning (Layer 2) for meaning, ANN search over small-world graphs (Layers 2 and 4) for speed, BM25 and inverted indexes (Layer 2) for exact terms, and context engineering (Layer 2) for packing the right information into a limited window.
intuition: An open-book exam: the model is a capable student, retrieval decides which pages of the book are open in front of it.
friction: Retrieval misses are silent: the model may answer confidently from the wrong passage or from its own memory. Chunking splits context that belongs together; tables, PDFs and code need special handling. Permissions must be enforced at retrieval time so users never see documents they cannot access. Indexes drift as documents change, and embedding-model upgrades require re-embedding everything.
Evaluation is hard: you need to measure retrieval quality (recall of the right passages) and answer quality (faithfulness to sources, completeness) separately. Retrieved text can carry prompt-injection attacks. And long-context models tempt teams to skip retrieval, which raises costs and often lowers accuracy.
practice: Build an evaluation set first: real questions with the passages that answer them. Measure retrieval recall at k before tuning prompts. Use hybrid search (BM25 plus vectors) and a re-ranker; they fix most retrieval failures cheaply. Chunk by document structure, keep titles and section headings with each chunk, and store metadata for filtering and citation.
Enforce access control in the retrieval query, not after generation. Ask the model to cite passage IDs and check that citations exist. Log retrieved passages with each answer so failures can be debugged, and re-index incrementally from change feeds rather than full rebuilds.

@@ dl
value: Deep learning trains neural networks with many layers to learn representations directly from raw data (pixels, audio, text, clicks) instead of relying on hand-designed features. Since 2012 it has transformed computer vision, speech recognition, translation, recommendation, protein structure prediction and, through large language models, software itself.
Its value is generality and scaling: the same few ingredients (layers of linear transforms and non-linearities, a loss, gradient descent, lots of data and compute) work across domains, and performance keeps improving predictably as data, parameters and compute grow.
history: Neural networks are old: the McCulloch–Pitts neuron (1943), Rosenblatt's perceptron (1958), and backpropagation popularized in 1986. Convolutional networks read handwritten digits in the late 1980s and 1990s (LeCun). But for decades they lost to other methods because data and compute were scarce and deep networks were hard to train. Around 2006, Hinton and others revived deep networks with pre-training tricks; in 2012 AlexNet, trained on GPUs with ImageNet's million labelled images, cut the image-recognition error rate dramatically and started the deep-learning era.
A rapid sequence of ideas followed: ReLU activations, dropout, batch normalization (2015), residual networks with over 100 layers (2015), attention and the transformer (2017), self-supervised pre-training (BERT, GPT, 2018), diffusion models (2020), and scaling laws (2020). Hinton, LeCun and Bengio received the 2018 Turing Award; Hinton shared the 2024 Nobel Prize in Physics with John Hopfield, and Hassabis and Jumper shared the 2024 Chemistry prize for AlphaFold.
how: A network is a composition of layers, each computing a linear transformation followed by a non-linear function; with enough layers and units it can approximate very complex functions. Architectures add structure suited to the data: convolutions share weights across positions in images; recurrence or attention models sequences; graph networks model relations. Training defines a loss on outputs, computes gradients of the loss with respect to every weight by backpropagation (reverse-mode automatic differentiation), and updates weights with stochastic gradient descent variants such as AdamW, over mini-batches of data.
Several techniques make deep training work in practice: careful initialization, normalization layers, residual connections (so gradients flow through many layers), regularization (weight decay, dropout, data augmentation), learning-rate schedules, mixed precision on tensor cores, and parallelism across many GPUs (data, tensor, pipeline and expert parallelism with all-reduce). Frameworks (PyTorch, JAX) and compilers handle gradients and kernels automatically.
The lower layers carry the whole stack: linear algebra and calculus (Layer 4) are the mathematics; probability and information theory (Layer 4) define losses; GPUs, HBM and interconnects (Layer 3) make the arithmetic affordable; and the analogy with biological neurons (Layer 5) inspired the field but explains little of how it works.
intuition: Stack many simple adjustable filters, show them millions of examples, and nudge every knob slightly in the direction that reduces the error; useful internal features emerge because they help reduce that error.
friction: Deep learning needs large datasets and expensive compute, and models can fail unpredictably outside their training distribution. They are hard to interpret, vulnerable to adversarial inputs, and can absorb biases in data. Training is sensitive to hyperparameters and infrastructure failures, and theory still does not fully explain why huge over-parameterized networks generalize so well. For small tabular datasets, simpler models such as gradient-boosted trees often still win.
practice: Start with a strong baseline (a pre-trained model or a well-known architecture) and fine-tune rather than training from scratch. Get the data pipeline and evaluation right before tuning models: clean labels, proper train/validation/test splits by time or entity, and metrics that match the product goal. Tune the learning rate first, monitor training and validation curves, and watch for leakage.
Use mixed precision and the largest batch that fits, profile GPU utilization, and checkpoint often. For production, measure latency and cost as carefully as accuracy, and monitor input distributions to detect drift.

@@ vectorsearch
value: Vector search finds the items whose embeddings are closest to a query embedding: semantically similar documents, products, images, users or code. It powers retrieval for RAG, recommendation candidate generation, deduplication, image and audio search, and fraud or anomaly detection by similarity.
Its value is search by meaning rather than by exact words or values, at scale: billions of vectors searched in milliseconds. It has become a standard feature of databases and search engines (PostgreSQL with pgvector, Elasticsearch and OpenSearch, Redis, ClickHouse, Pinot) as well as dedicated vector databases (Milvus, Pinecone, Weaviate, Qdrant).
history: Nearest-neighbour search is an old problem: k-d trees (1975) work in low dimensions but degrade in high ones (the curse of dimensionality). Locality-sensitive hashing (1998) gave the first strong approximate methods. Product quantization (Jégou and colleagues, 2011) compressed vectors so large collections fit in memory. Graph-based methods, especially HNSW (Malkov and Yashunin, 2016), became the standard for high recall at low latency. Facebook's FAISS library (2017) made these methods widely available on CPUs and GPUs; Microsoft's DiskANN (2019) extended graph search to SSDs for billion-scale indexes.
The 2020s embedding boom (sentence embeddings, CLIP, LLM embedding models) and RAG created a market for vector databases, followed by vector support in mainstream databases. Recent work focuses on filtered search, hybrid lexical–semantic ranking, quantization to 1–4 bits per dimension, and GPU-accelerated indexing.
how: Items are embedded into vectors (typically 384–4,096 dimensions). Similarity is measured by cosine similarity, dot product or Euclidean distance. Exact search compares the query with every vector, which is fine for thousands but too slow for millions. Approximate indexes trade a little recall for big speed-ups. HNSW builds a multi-layer proximity graph; search starts at the top layer and greedily moves toward the query, descending layers for finer search, controlled by parameters such as M (links per node) and efSearch (candidate list size). IVF clusters vectors with k-means and searches only the nearest clusters (nprobe). Product and scalar quantization compress vectors (for example 32× smaller), often with re-ranking of top candidates using full-precision vectors.
Production systems add metadata filtering (pre-filtering, post-filtering, or filter-aware graph traversal), sharding with scatter–gather, replication, incremental updates and deletes, and hybrid ranking with keyword search. The lower layers explain the design: metric spaces and random-graph theory (Layer 4) explain why greedy graph search works; clustering and quantization (Layer 2) compress; the memory hierarchy (Layer 3) decides whether an index must be in RAM or can live on SSD.
intuition: To find the most similar item among billions, ask a well-connected neighbour who points you closer, repeat a few dozen times, and you arrive near the best match without visiting most of the city.
friction: Recall is approximate and can silently degrade as data changes, filters become selective or parameters drift. HNSW indexes use a lot of memory and are slow to build; deletes leave holes that need rebuilds. Combining vector similarity with strict filters (tenant, permissions, date) is hard to do both fast and accurately. Embedding models change, forcing re-embedding of the whole corpus, and vectors from different models are not comparable. Pure vector search also misses exact matches (names, codes, IDs) that keyword search finds easily.
practice: Measure recall against exact search on a sample of real queries whenever you change index parameters or data volume. Use hybrid search for user-facing retrieval. Quantize to save memory, but re-rank the top candidates with full-precision vectors. Store the embedding model's name and version with every vector, and plan re-embedding as a background migration.
Before adding a separate vector database, check whether your existing database or search engine (pgvector, Elasticsearch, Redis) meets the scale and latency needs; fewer systems mean simpler permissions and consistency.
