@@ numerical
value: Numerical analysis is the study of how to compute continuous mathematics with finite, approximate numbers, and how to know how wrong the answer is. A computer cannot store most real numbers exactly. It stores the nearest floating-point number, and every addition, multiplication and division rounds again. Numerical analysis tells you when these tiny errors stay tiny, and when they grow until the answer is garbage.
The subject matters because the failure is silent. A program that sums a billion numbers, solves a linear system, computes a softmax, or trains a network in 16-bit precision does not crash when the error becomes large. It returns a number that looks normal. In 1991 a Patriot missile battery in Dhahran lost track of a target because its clock counted time in tenths of a second, and 0.1 cannot be stored exactly in binary. After about 100 hours of uptime the accumulated error was roughly a third of a second, enough to miss the target by hundreds of metres. The arithmetic was correct; the number representation was not.
For the layer above, floating-point numbers (L3) give the machine format and its rounding rules, and numerical analysis gives the theory that says how to use that format safely. Calculus (L4) gives the exact objects we want to approximate: derivatives, integrals, solutions of equations, minima. Numerical analysis is the bridge between the two: it asks how close a finite computation gets to the calculus answer, and at what cost.
terms: Machine epsilon — the gap between 1 and the next larger floating-point number; about 2.2 × 10⁻¹⁶ for 64-bit doubles and 1.2 × 10⁻⁷ for 32-bit floats.
Unit roundoff (u) — the largest relative error from rounding one number to its nearest float; half of machine epsilon, about 1.1 × 10⁻¹⁶ for doubles.
Forward error — the difference between the computed answer and the true answer.
Backward error — the size of the change to the input that would make the computed answer exactly correct; small backward error means the algorithm solved a nearby problem.
Condition number — how much a problem magnifies relative input changes into relative output changes; it is a property of the problem, not of the algorithm.
Stability — an algorithm is stable if it does not make errors much worse than the conditioning of the problem already forces.
Catastrophic cancellation — subtracting two nearly equal numbers, which erases the leading digits they share and leaves only the noisy low digits.
Truncation error — the error from replacing an infinite process by a finite one (a Taylor series cut short, a step size that is not zero), as opposed to rounding error.
history: Numerical computing is older than computers. Gauss and Newton designed methods for hand calculation, and a human "computer" knew that digits were lost at each step. The modern theory began when machines appeared. In 1947 John von Neumann and Herman Goldstine analysed rounding errors in Gaussian elimination and feared that errors would grow exponentially with matrix size, which would make large systems unsolvable. Alan Turing, in his 1948 paper on rounding errors in matrix processes, introduced the condition number and looked at the problem more carefully.
The key step came from James Wilkinson, who worked with Turing at the National Physical Laboratory in the UK. In the early 1960s he introduced backward error analysis: instead of asking how far the answer is from the truth, ask which slightly different problem the computer answered exactly. He showed that Gaussian elimination with row pivoting is backward stable in practice, which explained why it works. His book "Rounding Errors in Algebraic Processes" (1963) is the foundation of the field. Kahan's compensated summation (1965) showed that a few extra operations remove most of the error in a long sum.
Two engineering efforts turned theory into shared tools. The BLAS (1979) defined standard vector and matrix kernels, and LINPACK, EISPACK and then LAPACK (1992) packaged stable algorithms. IEEE 754 (1985), led by William Kahan, standardised floating-point formats and rounding so the same program gave the same answer on different machines; it was revised in 2008 and 2019. In the deep-learning era the questions returned: mixed-precision training (Micikevicius et al., 2017), bfloat16 on Google TPUs, and 8-bit formats (FP8, 2022) all ask how much precision a computation needs.
how: Every numerical computation has three sources of error. First, input error: the data itself is measured or stored approximately. Second, truncation error: the method replaces an exact limit with a finite step, such as the slope (f(x+h) − f(x))/h in place of f'(x). Third, rounding error: each arithmetic result is rounded to a float. The basic rule of floating-point arithmetic is that each operation returns the exact result times (1 + δ) with |δ| ≤ u. That is the only fact the analysis needs. It gives a model in which an algorithm with N operations has accumulated at most about N·u relative error in the worst case, and often about √N·u because errors partly cancel.
Conditioning comes next, and it separates a hard problem from a bad algorithm. If the output changes by a factor κ more than the input in relative terms, then even a perfect algorithm that only rounds the input to u cannot do better than relative error κ·u. For solving Ax = b, κ(A) = σ_max / σ_min, the ratio of the largest to the smallest singular value (from linear algebra). A rule of thumb: you lose about log₁₀ κ decimal digits. Doubles carry about 16 digits, so a system with κ = 10¹⁰ leaves about 6 trustworthy digits, and κ near 10¹⁶ leaves none. Conditioning is a fact about the problem; you cannot fix it by coding better, only by reformulating the problem.
Stability is the algorithm's part. An algorithm is backward stable if the computed answer is the exact answer for an input that differs from the true input by only a few multiples of u. Then forward error ≲ κ × backward error, so a stable algorithm on a well-conditioned problem is accurate, and on an ill-conditioned problem it is as accurate as the problem allows. Unstable algorithms lose much more than the conditioning requires. A classic case is the normal equations AᵀAx = Aᵀb for least squares: forming AᵀA squares the condition number, so κ = 10⁸ becomes 10¹⁶ and all the digits are gone. A QR factorization solves the same problem with condition number κ and keeps them.
Many practical tricks are stability repairs. Avoid subtracting nearly equal quantities: rewrite 1 − cos x as 2 sin²(x/2), and compute the roots of a quadratic with the formula that adds numbers of equal sign. Softmax is exp(zᵢ)/Σ exp(zⱼ); exp(1000) overflows in 64 bits, but subtracting the maximum z first gives the identical ratio with no overflow, and the log-sum-exp form log Σ exp(zⱼ) = m + log Σ exp(zⱼ − m) does the same for logs. Sums are made safer by sorting, pairwise (tree) summation with error about log N · u, or Kahan summation, which keeps a running correction term c = (t − sum) − y and gives an error bound independent of N.
Calculus supplies the targets and the error estimates. A Taylor expansion shows that the forward difference has truncation error about h·f''/2 while rounding error grows like u/h, so there is a best step near √u ≈ 10⁻⁸ for doubles, and shrinking h further makes things worse. Newton's method, built on the derivative, converges quadratically near a root (the number of correct digits roughly doubles each step), and this makes it self-correcting: an iterative method forgets earlier rounding errors, because each step starts again from the current estimate. That is why iterative methods such as conjugate gradient (Hestenes and Stiefel, 1952) are favoured for huge sparse systems: their cost per step is one matrix-vector product, and their speed depends on κ, roughly through the factor (√κ − 1)/(√κ + 1) per iteration.
Finally, parallel and low-precision hardware changes the picture. Floating-point addition is not associative, so summing in a different order, as a GPU reduction with a different thread count does, gives a different last digit. Mixed-precision training keeps the weights and the accumulations in 32 bits while multiplying in 16 or 8 bits, and scales the loss so that small gradients do not underflow to zero. The principle is the same as in Wilkinson's work: spend precision where errors accumulate, and save it where they do not.

example: Example 1, cancellation. Compute f(x) = (1 − cos x) / x² for x = 10⁻⁸. The true value is very close to 1/2, because 1 − cos x ≈ x²/2 for small x. In double precision, cos(10⁻⁸) = 1 − 5 × 10⁻¹⁷ rounds to exactly 1.0, since 5 × 10⁻¹⁷ is below the rounding spacing near 1 (about 1.1 × 10⁻¹⁶). So 1 − cos x = 0 and the program prints 0. The relative error is 100%. The cause is the subtraction, not the cosine: the cosine was correct to 16 digits, but all 16 digits were the shared leading "0.99999999...". Now use the identity 1 − cos x = 2 sin²(x/2). Then f(x) = 2 sin²(x/2) / x². Here sin(5 × 10⁻⁹) ≈ 5 × 10⁻⁹ is computed with full relative accuracy, squaring and dividing do not cancel anything, and the answer is 0.5 to about 16 digits. Same mathematics, different algorithm: the first was unstable, the second stable.
Example 2, accumulation. Add the number 1.0 to a 32-bit float counter 20 million times. A float has a 24-bit significand, so it holds every integer exactly only up to 2²⁴ = 16,777,216. At that value the spacing between floats becomes 2, so adding 1 gives 16,777,217, which is exactly halfway between two floats and rounds back to 16,777,216. The counter stops at about 16.8 million and the sum never reaches 20 million. Fixes: accumulate in 64 bits (exact for integers up to 2⁵³ ≈ 9 × 10¹⁵), or sum in pairs (a tree), or use Kahan summation. This is the reason GPU kernels that multiply in FP16 or FP8 still accumulate in FP32.
Example 3, conditioning. A 2 × 2 system with matrix [[1, 1], [1, 1.0000001]] has singular values near 2 and 5 × 10⁻⁸, so κ ≈ 4 × 10⁷. A relative input perturbation of 10⁻¹⁶ (just storing the numbers) can change the solution by about 4 × 10⁷ × 10⁻¹⁶ = 4 × 10⁻⁹. Losing about 7 or 8 digits is unavoidable for any algorithm. A well-written solver returns about 8 correct digits and no better. If your result only has 3 correct digits, the algorithm is losing something extra.
intuition: Arithmetic with slightly blurry numbers: some questions keep the blur small, some stretch it, and some ways of asking the same question stretch it more than others.
Think of measuring a table with a ruler marked in millimetres. Adding the lengths of ten tables keeps the error small. Computing the thickness of a sheet of paper by subtracting two table lengths cannot work, because the answer is smaller than the blur. Numerical analysis is the habit of asking, before computing, how much blur the question stretches (conditioning) and how much the method adds (stability). Backward error analysis makes this natural: a result that is the exact answer to a question slightly different from yours is as good as your own input, which was already blurry.
mistakes: People often think rounding errors are random noise that averages out. In fact they are deterministic and often systematic. The same sum repeated gives the same error, and the stalled 32-bit counter loses every increment, not half of them. Random-walk behaviour (error about √N · u) is common but not guaranteed, and worst cases are real.
People often think more precision is the cure for a wrong answer. In fact a better formula often does more than a wider type. Switching from float to double buys 9 digits but costs twice the memory and bandwidth. An unstable algorithm can burn those digits too, for example a variance computed as E[x²] − E[x]² on data with a large mean and a small spread can give a negative variance even in double precision.
People often think an ill-conditioned answer means the algorithm is buggy. In fact conditioning belongs to the problem. If tiny input changes really change the answer a lot, such as fitting a degree-20 polynomial to equally spaced points, no algorithm fixes it; you must change the problem (lower degree, regularization, a better basis).
People often think a == b is a sensible test for floats, or that 0.1 + 0.2 == 0.3 is a language bug. In fact 0.1 has no finite binary expansion, so the stored value is a nearby number, and the sum 0.30000000000000004 differs from the stored 0.3 by one unit in the last place. Compare with a tolerance suited to the scale, and prefer integer cents for money.
tradeoffs: Choose a direct method (LU, QR, Cholesky) when the matrix is dense and not too large (up to roughly 10⁴ to 10⁵ rows on one machine) and you want an answer with a known backward-stable error bound. Choose an iterative method (conjugate gradient, GMRES) when the matrix is sparse or only available as a matrix-vector product, and when a good preconditioner keeps the iteration count small. You give up predictable cost: the iteration count depends on the conditioning, and a poor preconditioner can make it very slow.
Choose double precision when you do not know where errors will accumulate: scientific code, financial aggregates, long reductions, anything that subtracts large close numbers. Choose single or half precision (FP32, BF16, FP16, FP8) when throughput and memory dominate and the computation is tolerant: neural network matrix multiplications are typically 2 to 16 times faster at lower precision on modern accelerators. You give up range (FP16 overflows above 65,504) or digits (BF16 has about 2 to 3 decimal digits), so keep accumulators and optimizer state in FP32.
Choose Kahan or pairwise summation when a long sum matters and order may vary; pairwise summation is almost free and cuts error from N·u to about log N · u. Choose a plain loop when the sum is short or the data is non-negative and the tolerance is loose. Choose exact arithmetic (integers, rationals, decimal types) when correctness is legal or discrete, such as money and counts; you pay in speed and in the need to avoid division.
Choose bitwise reproducibility (fixed reduction order, single-thread or deterministic kernels) when you must compare runs, debug, or audit results; you give up some parallel speed. Choose fast, non-deterministic reductions when the result only needs to be correct to a tolerance, as in most training.
friction: Floating-point reproducibility is hard. The same code can give different last digits on different hardware, compilers or thread counts, because addition is not associative and compilers may fuse a multiply and an add into one rounding (FMA). Debugging a "different result" often means proving that both are within tolerance, which needs an error bound that you rarely have.
Error bounds are usually worst-case and pessimistic, by a factor that grows with N, so practice and theory can disagree: Gaussian elimination can lose 2ⁿ⁻¹ in a contrived growth case, but almost never does. Conversely, a test on easy data proves little. Ill-conditioning shows up on real data that a unit test did not include.
Low precision makes the margin small. With BF16, relative rounding error is about 0.4% per operation, so layer norms, softmax, attention scores and loss sums are sensitive. Training with FP8 and FP4 needs per-block scaling factors, loss scaling and careful choice of which operations stay in higher precision, and research on stable recipes is still active. Finally, tools are limited: there is no cheap way to certify the accuracy of a general program, and interval arithmetic or automatic error analysis tools exist but often overestimate by large factors.
practice: Before computing, ask three questions. What is the condition number of this question? Which subtractions of nearly equal numbers are in my formula? Where do sums get long? Then use library routines (BLAS, LAPACK, NumPy, SciPy, cuBLAS) rather than writing loops, because they encode stable algorithms and tuned kernels.
Use these standard rewrites: log-sum-exp with the maximum subtracted; log1p(x) and expm1(x) in place of log(1+x) and exp(x) − 1 for small x; hypot(x, y) in place of sqrt(x² + y²); the "two-pass" or Welford algorithm for variance; QR or SVD in place of normal equations for least squares; solving Ax = b with a factorization instead of forming A⁻¹. In data pipelines, sum money in integers, accumulate averages in doubles, and use Spark's or Databricks' decimal types when exactness is required; remember that a parallel sum can differ in the last digits between runs.
For machine learning, keep a master copy of weights in FP32, use loss scaling with FP16, prefer BF16 for its wider range, and watch for NaN and Inf as early alarms. To test an algorithm, compare against a higher-precision run (for example, 128-bit or arbitrary precision with mpmath) on difficult inputs, and perturb inputs by tiny random amounts to see how the output moves. To study the subject, start with Trefethen and Bau for linear algebra, then Higham for the floating-point model and stability proofs.

Stability is a property of the algorithm: whether it adds more error than the conditioning forces. A stable algorithm on a well-conditioned problem is accurate.

@@ tensoralg
value: Tensor algebra is the arithmetic of multi-dimensional arrays: how to add them, stretch them to matching shapes, reshape them, and combine them by multiplying and summing over chosen axes. A vector has one axis, a matrix has two, and a tensor has any number. In machine learning a batch of text is a tensor of shape (batch, sequence, features), and attention adds a heads axis. Almost every operation in a neural network is a tensor operation, and almost every bug in one is a shape or axis mistake.
The central idea is the contraction: take two arrays that share an index, multiply matching entries and sum over that index. Matrix multiplication is the simplest contraction. Dot products, batched matrix multiplies, convolutions written as matrix products, attention scores and even a sum over one axis are all contractions. One compact notation, Einstein summation (einsum), describes all of them in one line. This gives frameworks such as NumPy, PyTorch, JAX and TensorFlow a single abstraction to optimise.
For the layer above, this is what GPUs and tensor cores (L3) execute. Linear algebra (L4) supplies the base case: matrix multiplication, rank, and the SVD. Tensor algebra generalises them to more axes. A GPU's thousands of threads (SIMT) work well on tensors because each output entry of a contraction is an independent sum, and tensor cores are fixed-size matrix-multiply units that large contractions are cut into. Understanding tensors lets you predict cost (floating-point operations and memory traffic) before you run anything.
terms: Tensor (in machine learning) — a multi-dimensional array of numbers with a fixed shape; mathematicians use "tensor" for a stricter object that transforms in a defined way under a change of basis.
Rank or order — the number of axes (indices) of a tensor; a scalar has 0, a vector 1, a matrix 2. Do not confuse it with matrix rank.
Shape — the list of axis lengths, for example (32, 128, 768).
Contraction — multiplying two tensors and summing over one or more shared indices; it reduces the total number of axes.
Einsum — Einstein summation notation: a string such as "ij,jk->ik" naming each axis of the inputs and outputs; any index missing from the output is summed.
Broadcasting — the rule that lets arrays of different shapes combine by virtually repeating size-1 axes.
Stride — the number of elements to skip in memory to move one step along an axis; it describes the memory layout.
View — a tensor that shares memory with another and differs only in shape and strides (reshape, transpose, slice), so no data is copied.
history: The word "tensor" comes from nineteenth-century physics, where it described stresses and strains in materials. Gregorio Ricci-Curbastro and Tullio Levi-Civita developed tensor calculus around 1900, and Albert Einstein used it for general relativity. In 1916 he noticed that when an index appears twice in a product it is always summed, and he dropped the summation sign. This "Einstein convention" is the origin of einsum.
In computing, multi-dimensional arrays appeared early. APL (Kenneth Iverson, 1960s) made whole-array operations and shape rules the core of the language, and Fortran arrays and MATLAB carried the idea into scientific computing. NumPy (2006, from Travis Oliphant's work merging Numeric and Numarray) brought n-dimensional arrays, broadcasting and strides to Python, and added an einsum function around 2011. Deep-learning frameworks (Theano, Torch, TensorFlow, PyTorch, JAX) made the tensor the central object, and added automatic differentiation of every tensor operation.
Two parallel threads matter for efficiency. Tensor decompositions were studied in statistics and chemometrics (Hitchcock 1927; Tucker 1966; Carroll and Chang 1970) long before deep learning, and Oseledets introduced the tensor-train form in 2011. And contraction order became an engineering problem: libraries such as opt_einsum (Smith and Gray, 2018) pick a cheap order for chains of contractions. In 2017 the Transformer paper wrote attention as exactly two batched contractions, and since 2021 low-rank updates such as LoRA have used the rank idea to cut the cost of adapting large models.
how: Start with the data layout. A tensor of shape (2, 3, 4) is stored in one flat block of 24 numbers. In the usual row-major layout, the strides (in elements) are (12, 4, 1): moving one step along the last axis moves 1 element, along the middle axis 4, along the first 12. Element [i, j, k] sits at offset 12i + 4j + k. This is the part linear algebra does not need to say and a GPU needs to know. A transpose does not move data; it permutes the strides, creating a view. After a transpose the tensor is non-contiguous: walking along its last axis jumps through memory, and many kernels first copy it into a contiguous layout.
Element-wise operations act position by position. When shapes differ, broadcasting applies. Align the shapes from the right; each pair of axis lengths must be equal or one of them must be 1, and a size-1 axis is treated as if it were repeated. So a (32, 128, 768) activation plus a (768,) bias works, because the bias is aligned to the last axis and repeated 32 × 128 times without being copied. Broadcasting is the reason bias, scaling and masking are cheap, and also a common bug: a (32, 1) column plus a (32,) row quietly becomes a (32, 32) matrix.
Reductions sum, average or take the maximum over one or more axes. They are the simplest contractions: summing over axis j of A[i, j] is the contraction of A with a vector of ones. Contractions are the general case. Given C[i,k] = Σⱼ A[i,j]·B[j,k], einsum writes "ij,jk->ik". The rule has no special cases: indices that appear in an input but not in the output are summed; indices that appear in the output are kept; an index repeated across inputs is multiplied. "ii->" is the trace, "bij,bjk->bik" is a batched matrix multiply, and "bhqd,bhkd->bhqk" are the attention scores of a Transformer: queries Q and keys K share the feature index d, which is summed, while batch b and head h are kept. The next contraction, "bhqk,bhkd->bhqd", mixes the values V by the attention weights.
Cost follows directly from the notation. A contraction costs about 2 × the product of the sizes of all distinct indices in the expression (one multiply and one add for each combination). For the attention scores with b = 2, h = 8, q = k = 1024, d = 64 the cost is 2 × 2 × 8 × 1024 × 1024 × 64 ≈ 2.1 billion floating-point operations. The output has b × h × q × k = 16.8 million entries, about 34 MB in 16-bit numbers. This is why attention memory grows with the square of the sequence length, and why fused kernels (FlashAttention) avoid writing that intermediate to memory.
For chains of contractions the order matters a great deal, because contraction is associative in value but not in cost. For three matrices A (100 × 10), B (10 × 100), C (100 × 10), computing (AB)C costs 100·10·100 + 100·100·10 = 200,000 multiplications, while A(BC) costs 10·100·10 + 100·10·10 = 20,000. Finding the best order for a general network is NP-hard, but heuristics are good enough for the sizes in practice, which is what opt_einsum and compilers such as XLA do. Linear algebra contributes the key tools beneath all this: matrix multiplication as the base kernel, rank and the SVD as the way to compress. A matrix W of size d × d can be replaced by a product BA with B (d × r) and A (r × d), where r is small; the number of parameters falls from d² to 2dr. This is the idea behind LoRA and, in higher order, behind CP, Tucker and tensor-train decompositions.
Finally, hardware turns contractions into tiles. A tensor core multiplies small fixed-size blocks (for example 16 × 16 matrices) in one instruction. The compiler reshapes a big contraction into a batched matrix multiplication, by permuting the axes so that kept indices from each input are grouped, flattening groups into rows and columns, and tiling those into blocks that fit registers and shared memory. Each output tile is an independent sum, which is why thousands of GPU threads can work at once without coordination.

example: Compute C = einsum("ij,jk->ik", A, B) by hand with A = [[1, 2, 3], [4, 5, 6]] (shape 2 × 3) and B = [[1, 0], [0, 1], [2, 1]] (shape 3 × 2). The index j has length 3 and is summed. C[0,0] = 1·1 + 2·0 + 3·2 = 7. C[0,1] = 1·0 + 2·1 + 3·1 = 5. C[1,0] = 4·1 + 5·0 + 6·2 = 16. C[1,1] = 4·0 + 5·1 + 6·1 = 11. So C = [[7, 5], [16, 11]]. The cost is 2 × (2 × 2 × 3) = 24 operations, which matches "2 × the product of all index sizes".
Now count a realistic case: a Transformer layer with batch 32, sequence 512, model width 1024, and a feed-forward expansion to 4096. The first feed-forward contraction is "bsd,df->bsf". The cost is 2 × 32 × 512 × 1024 × 4096 ≈ 1.37 × 10¹¹ operations, or 137 GFLOP, for one layer and one pass. On a GPU that sustains about 200 teraflops in 16-bit matrix math, this takes about 0.7 milliseconds, if the data feeds the cores. The weight matrix is 1024 × 4096 = 4.2 million numbers, 8.4 MB in 16 bits, and the activation input is 32 × 512 × 1024 = 16.8 million numbers (33.5 MB). The arithmetic intensity (operations per byte moved) is high, so this contraction is compute-bound, while the softmax and layer-norm steps in between are memory-bound.
Finally a shape check. Suppose you compute scores = einsum("bqd,bkd->bqk", Q, K) but K has shape (b, d, k) because it was transposed earlier. The einsum fails if lengths mismatch, but if d = k = 64 it runs and silently computes the wrong thing. Naming axes in einsum, and asserting shapes at function boundaries, catches this.
intuition: A tensor is a box of numbers with labelled directions; einsum is a precise recipe saying which directions to line up, multiply and sum, and which to keep.
Matrix multiplication already has this form: rows of the first matrix are matched with columns of the second along one shared direction. Higher-order tensors just have more directions. The index notation works because the operations are local: each output entry depends on a sum over a few matched indices, and nothing else. That locality is exactly what hardware needs. Every output entry is independent, so work can be cut into tiles, and the cost is visible in the notation before the code runs.
mistakes: People often think a tensor is just a matrix with extra dimensions, so the maths is a straight extension. In fact the extra axes bring new questions that matrices do not have: which axes to contract, in which order, and how the data is laid out. Even rank is different: matrix rank is a computable number, but finding the rank of a tensor is NP-hard (Håstad 1990).
People often think transpose and reshape are cheap everywhere. In fact they are cheap only as views. A reshape of a non-contiguous tensor must copy data, and a transposed tensor may make later kernels read memory with a large stride, which can slow them by several times.
People often think broadcasting copies the data. In fact it does not: it uses a stride of 0 along the repeated axis, so the memory is reused. The cost is in the output, which is full size. Broadcasting is also the source of silent errors when two shapes happen to be compatible by accident.
People often think the multiplication order of a chain does not matter because the result is the same. In fact the result is the same but the cost can differ by orders of magnitude, as the 200,000 versus 20,000 example shows. Floating-point results also differ slightly with the order.
tradeoffs: Choose einsum when the operation is unusual, involves several axes, or readability matters: attention variants, multi-linear layers, physics-style calculations. The notation documents the shapes, and optimised backends such as opt_einsum or a compiler find a good order. Choose a named op (matmul, bmm, conv) when one exists, because it maps directly to a tuned library kernel such as cuBLAS or cuDNN; a hand-written einsum may fall back to slower paths in some frameworks.
Choose contiguous layouts and fused kernels when memory bandwidth is the limit, which it is for most element-wise and normalisation steps (these do very few operations per byte). Choose to keep views and delay copies when the tensor is used once. You give up some predictability about when memory is copied.
Choose a low-rank factorisation (LoRA-style, or SVD truncation) when a weight matrix is large and the update or the model is known to have low effective rank: a rank-16 update of a 4096 × 4096 weight needs 131,072 parameters instead of about 16.8 million, under 1%. Choose full-rank training when quality matters more than memory and compute, because low rank limits what the update can express.
Choose a fixed shape (static shapes) when you compile for an accelerator (XLA, TPU, CUDA graphs), because the compiler can plan memory and fuse operations. Choose dynamic shapes when sequence lengths vary a lot, with padding or bucketing to limit waste. Dynamic shapes cost recompilation or padding overhead; static shapes waste compute on padding.
friction: Shape bugs are among the most common errors in machine-learning code, and they are often silent: broadcasting makes a wrong program run and produce plausible numbers. Frameworks catch mismatched lengths but not mismatched meanings. Most code still uses positional axes (axis 0, 1, 2) rather than named ones, so the meaning of each axis lives in comments.
Memory traffic, not arithmetic, is often the limit. Attention scores need b × h × L² entries, so doubling the sequence length quadruples this term. Intermediate tensors dominate training memory because they are kept for the backward pass. Layout choices (channels-first or channels-last, padding to multiples of 8 or 16 for tensor cores) can change speed by large factors and are not visible in the maths.
Higher-order maths is harder than the matrix case. Most tensor problems, including computing rank, the best low-rank approximation, and many decompositions, are NP-hard in general (Hillar and Lim, 2013). Unlike matrices, a best low-rank approximation may not exist. Practical methods (alternating least squares) have no global guarantees. The word "tensor" is also used loosely: ML tensors are arrays and have no transformation law, while physics tensors do.
practice: Write down the shape of every tensor at every step, in comments or assertions. Use einsum for anything with more than one non-trivial axis and name the indices meaningfully (b batch, s sequence, h head, d feature). Libraries such as einops add readable reshaping, and checkers (jaxtyping, torchtyping) put shapes into type hints.
Estimate cost before running: FLOPs are about 2 × the product of all index sizes, and bytes are about the sizes of inputs plus outputs times bytes per number. If FLOPs per byte is high (matrix multiplies), you are compute-bound; if low (element-wise, softmax), you are bandwidth-bound and should fuse operations or use lower precision storage. Check with a profiler rather than trusting the estimate.
Watch layout: call .contiguous() or reshape deliberately, avoid repeated transposes inside loops, and pad dimensions to multiples of 8 (or 64) so tensor cores can be used. Prefer batched operations over Python loops, since each Python-level call has a fixed overhead of microseconds. For contraction chains, use opt_einsum or torch.einsum with optimisation turned on, and look at the chosen path. To study: work Rocktäschel's einsum examples, implement attention in four lines of einsum, and read the d2l.ai chapters on tensors and linear algebra.

@@ metricspaces
value: A metric space is a set of objects together with a distance function that behaves the way distance should. Once you have chosen a distance, a large part of machine learning and search becomes the same question: which points are near this one? Nearest-neighbour search, clustering, recommendation, duplicate detection, anomaly detection and retrieval for language models all ask it. The answer depends heavily on which distance you chose, so this choice is a modelling decision, not a detail.
The formal definition is short, and the value is in what it guarantees. A distance d(x, y) must be non-negative, zero only when x = y, symmetric, and must obey the triangle inequality: d(x, z) ≤ d(x, y) + d(y, z). The last rule is the useful one. If you know that a point is far from y, and that y is close to x, then you know something about x without measuring it. Search indexes use this to skip most of the data.
For the layer above, embeddings (L2) place text, images and users as vectors, and their meaning is read through a distance. Approximate nearest-neighbour indexes (HNSW, IVF), contrastive training (CLIP), k-means and perceptual hashing all rest on it. Linear algebra (L4) gives the common distances as norms of vector differences. Set theory (L4) gives the idea of a function on pairs of elements, so strings, sets and graphs can be metric spaces too. The Johnson–Lindenstrauss lemma (L4) shows that in Euclidean space the distances between a finite set of points survive when the vectors are projected to far fewer dimensions.
terms: Metric — a function d(x, y) that is non-negative, zero only for identical points, symmetric, and satisfies the triangle inequality.
Norm — a length function ‖v‖ on vectors; a norm gives a metric by d(x, y) = ‖x − y‖.
Lp norm — ‖v‖ₚ = (Σ|vᵢ|ᵖ)^(1/p); p = 1 is Manhattan, p = 2 is Euclidean, p = ∞ is the largest absolute coordinate.
Cosine similarity — (x · y) / (‖x‖ ‖y‖), the cosine of the angle between two vectors; it ignores their lengths.
Hamming distance — the number of positions in which two equal-length strings (often bit strings) differ.
Jaccard distance — 1 − |A ∩ B| / |A ∪ B| for two sets.
Edit (Levenshtein) distance — the least number of insertions, deletions and substitutions that turns one string into another.
Concentration of distances — in high dimensions, the nearest and farthest points from a query have almost the same distance.
history: Maurice Fréchet introduced abstract metric spaces in his 1906 doctoral thesis. His goal was to study convergence and continuity for objects that are not numbers, such as functions and curves, by keeping only the notion of distance. Felix Hausdorff built general topology on this base in 1914. For the next sixty years metric spaces were a tool of analysis.
Computing brought them back as a practical subject. Hamming (1950) defined the distance between bit strings to study error-correcting codes, and Levenshtein (1965) defined edit distance for strings. Salton's vector space model (1970s) represented documents as vectors and compared them with cosine similarity, which made information retrieval a geometry problem. In the 1990s, search over metric spaces became a field (metric trees such as the vantage-point tree, Uhlmann 1991 and Yianilos 1993; M-trees, Ciaccia, Patella and Zezula 1997).
A warning arrived with the paper by Beyer, Goldstein, Ramakrishnan and Shaft (ICDT 1999), "When Is 'Nearest Neighbor' Meaningful?", which showed that under broad conditions, as dimension grows, the ratio between the farthest and nearest distances tends to 1. Locality-sensitive hashing (Indyk and Motwani, 1998) answered with approximate search. In the 2010s, neural embeddings (word2vec, 2013) made distances meaningful again by learning the space itself, and the 2020s vector databases built indexes (HNSW, 2016; IVF-PQ) around inner product, cosine and Euclidean distance.
how: The four metric axioms say what "distance" must mean. Non-negativity and identity say d(x, y) ≥ 0 with equality only when x = y. Symmetry says the distance is the same in both directions. The triangle inequality says that going through a third point never shortens the trip. Each axiom is a promise to algorithms. Symmetry lets an index store each pair once. The triangle inequality lets a search prune: if you know d(q, p) for a pivot p and the stored d(p, x), then d(q, x) ≥ |d(q, p) − d(p, x)|, so x can be ruled out without computing d(q, x) when this lower bound already exceeds the best distance found.
Vectors give a family of metrics through linear algebra. For x, y ∈ ℝⁿ, the Lp distance is (Σ|xᵢ − yᵢ|ᵖ)^(1/p). L2 is the straight-line distance, and is natural when directions are interchangeable (rotating all points leaves it unchanged). L1 sums coordinate differences, is more robust to a single large outlier coordinate, and suits sparse features. L∞ is the largest single difference; adversarial-robustness work bounds image perturbations by it, for example 8/255 per pixel. The unit ball of L1 is a diamond, that of L2 a circle (a sphere in higher dimensions), and that of L∞ a square (a cube). L1 adds the coordinate differences linearly, L2 weights large differences more through squaring, and L∞ keeps only the largest one. In a finite number of dimensions all Lp norms are equivalent up to a factor depending on n (‖x‖∞ ≤ ‖x‖₂ ≤ √n ‖x‖∞), so which one you pick changes rankings but not the notion of convergence.
Cosine similarity is the most used measure for embeddings, but it is not a metric as written. Cosine distance 1 − cos θ can violate the triangle inequality. The angle θ itself (angular distance) is a metric. A useful fact: if both vectors are scaled to length 1, then ‖x − y‖² = 2 − 2 cos θ, so Euclidean distance, cosine similarity and dot product all give the same ranking. For vectors of different lengths they disagree, and the choice means something: dot product rewards long vectors, cosine ignores length, and Euclidean penalises both a difference in direction and in length.
Other objects have their own metrics. Hamming distance on bit strings supports perceptual hashes: a 64-bit hash of an image changes in few bits after resizing or mild compression, so images within a small Hamming distance are treated as near-duplicates. Jaccard distance on sets measures overlap and is estimated cheaply by MinHash signatures. Edit distance on strings is computed by dynamic programming in O(mn) time. Wasserstein distance compares distributions by the cost of moving mass. Not every useful dissimilarity is a metric: KL divergence is not symmetric and does not satisfy the triangle inequality, and maximum inner product search (MIPS) uses a score that is not a distance at all. Algorithms that rely on the triangle inequality then need a transformation, or use graph indexes that work heuristically.
Distances become useful through the questions built on them. Nearest-neighbour search asks for the k points with the smallest d(q, x). Brute force computes all n distances and costs O(n·d). Clustering asks for groups with small internal distances: k-means alternates between assigning each point to its nearest centre and moving each centre to the mean of its points, which reduces the sum of squared Euclidean distances at every step. Contrastive learning turns the same idea around and trains the embedding itself, so that matching pairs end up with a small distance and non-matching pairs with a large one.
High dimension changes geometry in ways that low-dimensional intuition misses. The volume of a unit ball inside the cube [−1, 1]ⁿ shrinks toward zero as n grows: for n = 10 it is about 0.25% of the cube. Almost all the volume of a cube sits near its corners and a thin shell near the surface. For random points, distances concentrate: the ratio of the farthest to the nearest distance tends to 1, and two random unit vectors have cosine near 0, with spread about 1/√n, so they are almost orthogonal. When distances concentrate, "nearest" loses meaning for unstructured data. Real embeddings are not random: they lie close to a low-dimensional structure (a manifold), so nearest neighbours remain meaningful, and the Johnson–Lindenstrauss lemma shows that for n points, about log n / ε² dimensions are enough to keep all distances within a factor 1 ± ε, whatever the original dimension.

example: Take the query q = (1, 1) and two candidates, x = (10, 10) and y = (1, 0). The Euclidean distances are d(q, x) = √(9² + 9²) = √162 ≈ 12.7 and d(q, y) = √(0² + 1²) = 1, so y is the nearest. The cosine similarities are cos(q, x) = (10 + 10) / (√2 × √200) = 20 / 20 = 1.0 and cos(q, y) = 1 / (√2 × 1) ≈ 0.71, so x is the nearest, because x points in exactly the same direction as q. The dot products are 20 and 1, so x wins again. The three measures give two different answers. In a product-recommendation setting, a user with a long vector (a heavy user) could dominate by dot product while cosine would focus on taste direction. Normalise first if you want direction only.
Next, a pruning example. Suppose you store distances from every point to a pivot p, and the query has d(q, p) = 10. The best match found so far is at distance 3. For a stored point x with d(p, x) = 20, the triangle inequality gives d(q, x) ≥ |10 − 20| = 10 > 3, so x is skipped without being compared. This is how vantage-point trees and pivot-based indexes cut work in low or moderate dimensions.
Last, a concentration example. Draw 1,000 random points uniformly in a unit cube of dimension 2 and pick one as the query. The nearest of the others is typically about 0.016 away, and the farthest is about 1.0, so the ratio of farthest to nearest is about 60 or more. In dimension 1,000, the typical distance between two random points is about √(1000/6) ≈ 12.9, with a spread of only about 0.25 (the variances of the 1,000 coordinate terms add up, but their sum grows only like √n while the mean grows like n), so the farthest-to-nearest ratio is about 1.1. Every point looks about equally far. That is why a vector search over raw high-dimensional random-like features gives poor answers, and why embeddings that organise the data into structure are needed.
intuition: Define what "close" means, and many problems become "find the nearest".
A metric is a promise about the structure of closeness, and the triangle inequality is its most useful clause: nearness spreads. If a is close to b and b is close to c, then a is not far from c. An index can use that to give up on large regions of the data without looking at them. Different distances are different opinions about what matters: Euclidean cares about size and direction, cosine only about direction, Hamming about the count of differing features, Jaccard about shared members. Choosing among them is choosing what your system treats as "the same".
mistakes: People often think cosine distance is a metric. In fact 1 − cos θ can violate the triangle inequality; the angle arccos(cos θ) satisfies it. This matters for pivot-based indexes, which assume the inequality holds. For unit vectors you can use Euclidean distance instead, which is a metric and gives the same ranking.
People often think cosine, Euclidean and dot product give the same neighbours. In fact they agree only when vectors have the same length. If lengths differ, the example above shows opposite rankings. Check whether your embedding model was trained with normalisation, and use the distance it was trained for.
People often think the curse of dimensionality means high-dimensional search is hopeless. In fact it applies to data that fills the space in an unstructured way. Real data has low intrinsic dimension (images and sentences lie near much smaller structures), so neighbours are meaningful and indexes like HNSW work well, even though raw dimension is 768 or 1536.
People often think a smaller distance in embedding space always means more similar for the user. In fact distance only reflects what the training objective rewarded. An embedding trained for topic similarity will say "I love this" and "I hate this" are close, because they are about the same thing.
tradeoffs: Choose Euclidean (L2) distance when magnitudes carry meaning (physical measurements, k-means on standardised features) and rotation invariance is natural. Choose cosine similarity when only direction matters (text and image embeddings, tf-idf vectors) or when vector length reflects something unrelated to meaning such as document length. You give up information about magnitude with cosine; with L2 a long document and a short one on the same topic look far apart.
Choose L1 when features are sparse or you want robustness to a few large coordinate errors; choose L2 when errors are small and independent. Choose L∞ only when the worst coordinate is what matters, such as a per-pixel bound in adversarial robustness testing.
Choose a true metric with exact pruning (vantage-point tree, ball tree, k-d tree) when the dimension is low (roughly under 20) or the intrinsic dimension is low, and exactness is required. Choose approximate indexes (HNSW, IVF-PQ, LSH) when the dimension is in the hundreds, the dataset has millions to billions of vectors, and a recall of 95% to 99% is enough. You give up guarantees: you cannot be sure the true nearest neighbour was returned, and tuning recall against latency becomes part of operations.
Choose to learn the distance (a metric-learning or contrastive objective, as in CLIP) when hand-picked distances on raw features do not match what users consider similar and you have labelled pairs. You give up simplicity and take on the cost of training, and when the model changes, every stored vector must be recomputed.
friction: The right distance is task-dependent and rarely obvious. There is no test that tells you which metric is correct without data on what "similar" means; you have to evaluate retrieval quality on labelled examples. Metrics also assume that every feature is on a comparable scale, so unscaled features (age in years next to income in rupees) let the largest-scale feature decide everything.
High dimension makes exact search expensive: brute force costs O(n·d) per query, and for 100 million vectors of 768 floats that is about 77 billion multiply-adds, plus 300 GB of memory. Exact tree indexes degrade to a linear scan above a few dozen dimensions. Approximate indexes trade recall for speed, with behaviour that depends on data distribution, and they handle updates and deletions poorly.
Metric assumptions break in practice. Maximum inner product search, asymmetric similarity (query and document encoders are different), and learned scores do not obey the triangle inequality. Distances computed in an embedding space also drift when the model is retrained, so old and new vectors cannot be compared. Finally, hubness is a known effect: in high dimensions a few points become the nearest neighbour of a very large number of queries, distorting results.
practice: Start by writing down what "similar" should mean for the user, then pick the distance that encodes it. For text and image embeddings, use the distance the model was trained with, usually cosine or dot product on normalised vectors; if you normalise at write time, a dot product is cheaper and gives cosine. For numeric features, standardise each column first, or use Mahalanobis distance to account for correlations. For sets (user segments, shingled documents) use Jaccard with MinHash, and for bit hashes use Hamming distance with a threshold found from labelled duplicates.
Measure quality, not just speed. Build a small labelled set of query and relevant-result pairs, and compute recall@k for your index against exact brute force on a sample. When using HNSW or IVF, tune the parameters (efSearch, nprobe) against that recall. For ad tech, similar ideas appear in lookalike audiences and device or household matching, where the distance between feature vectors or hash signatures decides which users are treated as alike.

@@ lp
value: Linear programming (LP) is the problem of choosing numbers to make one linear quantity as large or as small as possible, while a set of linear limits is respected. "Spend the budget across campaigns to maximise expected conversions, with no campaign above its daily cap and no more than 100% of each impression's capacity sold" is a linear program. So are blending, routing, scheduling, network flow, transport and assignment problems. It is the best-understood kind of constrained optimisation: solvers handle millions of variables reliably, and the answer comes with a proof.
The proof is the second half of the topic, and it is called duality. Every LP that maximises has a twin LP that minimises, built from the same numbers, and at the optimum the two have the same value. A feasible dual solution is an upper bound on the primal, so if you can show a primal answer and a dual answer with equal values, you have a certificate that no better answer exists. The dual variables also have a meaning: each one is the price of its constraint, how much the best value would rise if that limit were relaxed by one unit.
For the layer above, this is the engine under max-flow and matching (where max-flow min-cut is LP duality), under the training problem of support vector machines (solved through its dual), and under budget pacing in advertising, where the dual variables become the bid multipliers that keep spending on schedule. Query optimisers and cluster schedulers use LP relaxations too. Linear algebra (L4) gives the language: constraints are Ax ≤ b and the objective is cᵀx. Optimisation (L4) gives the setting of constrained problems and Lagrange multipliers, and set theory (L4) gives the feasible region as an intersection of half-spaces, which is a convex polytope.
terms: Objective — the linear function cᵀx to be maximised or minimised.
Constraint — a linear inequality or equality such as aᵀx ≤ b that the solution must satisfy.
Feasible region — the set of all x that satisfy every constraint; for an LP it is a convex polytope (a flat-faced solid).
Vertex (extreme point) — a corner of the polytope; if an LP has an optimum, at least one vertex is optimal.
Simplex method — an algorithm that moves from vertex to adjacent vertex, improving the objective each time, until no neighbour is better.
Interior-point method — an algorithm that moves through the inside of the polytope along a smooth path towards the optimum.
Dual problem — the companion LP with one variable per primal constraint and one constraint per primal variable.
Shadow price — the dual variable of a constraint: the rate at which the optimal value changes when that constraint's right-hand side changes.
Complementary slackness — at the optimum, a constraint with positive price must be tight, and a slack constraint has price zero.
history: Linear programming was invented several times. Leonid Kantorovich, a Soviet mathematician, formulated production-planning problems as LPs and described a solution method in 1939, but his work was not widely known in the West. George Dantzig, working for the US Air Force on planning problems, formulated the general problem and in 1947 invented the simplex method. John von Neumann, when Dantzig described the problem to him, saw at once the link to his own game theory and described duality. David Gale, Harold Kuhn and Albert Tucker published the first rigorous proof of the duality theorem in 1951.
The big theoretical question was speed. In 1972 Klee and Minty built a cube-like polytope on which the simplex method with the usual pivot rule visits all 2ⁿ vertices, so its worst case is exponential. Yet in practice it takes a small multiple of the number of constraints in steps. Khachiyan's ellipsoid method (1979) proved LP solvable in polynomial time, but it was slow in practice. Narendra Karmarkar's interior-point method (1984) was both polynomial and fast, and started a decade of work that made interior-point codes standard. Spielman and Teng (2001) explained the gap with smoothed analysis: under tiny random noise on the data, simplex takes polynomial time on average. Whether a strongly polynomial algorithm for LP exists (time depending only on the number of variables and constraints, not on the size of the numbers) is still open.
Modern solvers (Gurobi, CPLEX, HiGHS, Google's GLOP and PDLP) combine simplex, interior point and, since about 2021, first-order methods such as PDLP that use only matrix-vector products and scale to billions of nonzeros. Integer programming, which adds whole-number requirements, became practical through branch-and-cut, which uses LP at every step.
how: Write the problem in a standard form: maximise cᵀx subject to Ax ≤ b and x ≥ 0. Each row of A is one constraint, and each constraint cuts the space with a flat boundary, keeping one side. The feasible region is the intersection of these half-spaces, a convex polytope. Because the objective is linear, its level sets are parallel flat sheets, and sliding the sheet in the direction of improvement stops at the last point of the polytope it touches. That is a vertex (or a whole face, if the sheet is parallel to a face). So you only need to search vertices: a finite set, but exponentially large.
The simplex method searches smartly. Add a slack variable to each inequality so it becomes an equality: aᵀx + s = b with s ≥ 0. A vertex then corresponds to a basis, a choice of m variables (m = number of constraints) that are allowed to be non-zero, with the rest fixed at 0, found by solving an m × m linear system. This is the part linear algebra supplies. A pivot swaps one variable into the basis and one out, which moves to an adjacent vertex. The reduced cost of each non-basic variable says how much the objective changes if it enters; if none is positive, the vertex is optimal. Each pivot is one row operation on a tableau, as in Gaussian elimination. Simplex can cycle on degenerate vertices (where more than the minimum number of constraints are tight), which rules such as Bland's prevent.
Interior-point methods take another route. Replace each constraint x ≥ 0 by a barrier term −μ Σ ln xᵢ in the objective, which becomes infinite at the boundary, and solve the smooth problem for a decreasing sequence of μ. The solutions form the central path, which ends at the optimum. Each step solves one linear system with Newton's method (a use of calculus), and 20 to 100 steps are typical regardless of size. A step costs more than a simplex pivot, but there are far fewer steps, so interior-point methods usually win on very large problems, while simplex is better for re-solving after a small change.
Duality is the central structure. For the primal "maximise cᵀx subject to Ax ≤ b, x ≥ 0", the dual is "minimise bᵀy subject to Aᵀy ≥ c, y ≥ 0". Weak duality is one line. For feasible x and y, cᵀx ≤ (Aᵀy)ᵀx = yᵀ(Ax) ≤ yᵀb. Every dual-feasible y therefore bounds every primal-feasible x from above. Strong duality says that if either problem has an optimum, both do and the optimal values are equal. This gives a certificate: if you present x and y with cᵀx = bᵀy, nobody needs to trust your solver. Complementary slackness adds the structure at the optimum: if a constraint is not tight, its dual variable is 0, and if a dual constraint is not tight, the matching primal variable is 0.
Prices explain why duality is useful in applications. A dual variable yⱼ is the value of one more unit of resource j. In a budget problem, it is the marginal conversions per extra rupee of budget, and it tells you where to spend or raise a cap. In ad pacing, the dual variable of each campaign's budget constraint acts as a multiplier: an impression is given to the campaign that maximises value − λ × cost, and adjusting λ over time keeps spend on target. The same duality gives max-flow min-cut (the dual of a flow LP is a cut LP), and the support vector machine's dual form (which depends on the data only through inner products, enabling kernels).
Finally, integers. Many real decisions are yes/no or counts: open a data centre or not, run a job on one machine. Requiring x to be an integer makes the problem NP-hard in general. The standard approach, branch and bound, solves the LP relaxation (drop the integer requirement), which gives an upper bound; if the solution has a fractional value, say x = 2.5, split into two subproblems x ≤ 2 and x ≥ 3, and prune any branch whose LP bound is worse than the best integer solution found. For some structures the LP is automatically integral: if the constraint matrix is totally unimodular, as for bipartite matching and flows, the vertices are integer and plain LP solves the combinatorial problem.

example: Solve the small problem in the diagram: maximise 3x + 2y subject to x + y ≤ 4, x + 3y ≤ 9, x ≤ 3, x ≥ 0, y ≥ 0. The feasible region has five corners. Evaluate the objective at each. (0, 0) gives 0. (3, 0) gives 9. (3, 1), where x = 3 meets x + y = 4, gives 9 + 2 = 11. (1.5, 2.5), where x + y = 4 meets x + 3y = 9, gives 4.5 + 5 = 9.5. (0, 3) gives 6. The best corner is (3, 1) with value 11. Check that (3, 1) is feasible: 3 + 1 = 4 ≤ 4, 3 + 3 = 6 ≤ 9, 3 ≤ 3. The constraints x + y ≤ 4 and x ≤ 3 are tight; x + 3y ≤ 9 has slack 3.
Now prove that 11 is optimal using the dual, without checking corners. The dual is: minimise 4y₁ + 9y₂ + 3y₃ subject to y₁ + y₂ + y₃ ≥ 3 (the column of x), y₁ + 3y₂ ≥ 2 (the column of y), and y ≥ 0. Complementary slackness says the slack constraint x + 3y ≤ 9 must have price y₂ = 0. Then y₁ ≥ 2 from the second dual constraint; take y₁ = 2, and then y₃ = 3 − 2 = 1 from the first. This dual solution is feasible and its value is 4·2 + 9·0 + 3·1 = 11. By weak duality no primal point can exceed 11, so (3, 1) is optimal. The certificate is the pair of equal numbers.
The prices say what each limit is worth. y₁ = 2: if the cap x + y ≤ 4 becomes 4.1, the new optimum is (3, 1.1) with value 9 + 2.2 = 11.2, a gain of 0.2 for 0.1 of extra capacity, which is 2 per unit. y₃ = 1: if x ≤ 3.1, the optimum is (3.1, 0.9) with value 9.3 + 1.8 = 11.1, a gain of 1 per unit. The price of the slack constraint is 0: more room on x + 3y ≤ 9 changes nothing. These prices hold for small changes, until another constraint becomes tight.
Scale gives a sense of the algorithms. A real pacing problem might have 10⁶ impression groups and 10⁴ campaigns, with about 10⁷ nonzero entries in A. A dense tableau would be impossible, but sparse interior-point or first-order solvers handle it in minutes, and the dual variables (10⁴ numbers) are the output that serving systems actually use.
intuition: Find the highest corner of a many-sided crystal; the dual proves no point is higher by pricing each face.
Imagine a solid with flat faces, and a rule that says "higher is better" in one direction. You walk along its edges, always uphill, and stop at a corner where every edge leads down. Because the solid is convex, a corner that is higher than all its neighbours is higher than everything. The dual is a different view of the same solid: each face has a price, and a set of prices whose combined effect gives an upper bound on the height anywhere. When the cheapest bound meets the best corner, both searches are done, and the prices are the proof.
mistakes: People often think the optimum of an LP can be in the middle of the region. In fact, if the objective is not constant, an optimum is always on the boundary and at least one is at a vertex, because a linear function has no interior maximum. Ties happen when the objective is parallel to a face, and then a whole face is optimal.
People often think the simplex method is slow because its worst case is exponential. In fact the Klee–Minty cases are rare constructions; on real problems simplex needs a modest multiple of the number of constraints in pivots, and smoothed analysis (Spielman and Teng) explains why. Commercial solvers still rely on it heavily.
People often think dual variables are only a mathematical device. In fact they are prices with direct meaning: the marginal value of each constraint, which is what a planner needs to decide where to add capacity. They also drive algorithms such as pacing, where the multiplier is the control variable.
People often think that if LP is easy, integer programming is only a little harder. In fact adding integrality makes the problem NP-hard. The LP relaxation gives a bound, and for most problems the gap between the LP and integer optimum can be large, so good formulations (tight relaxations) matter more than fast solvers.
tradeoffs: Choose simplex when the problem is small to medium (up to a few hundred thousand variables), when you re-solve after small changes (warm start from the previous basis works well), or when you need a vertex solution with a clear basis for sensitivity analysis. Choose an interior-point method for large sparse problems solved once, where it usually needs 20 to 100 iterations. You give up warm starting, and the solution lies in the middle of an optimal face unless you run a crossover step to a vertex.
Choose a first-order method (PDLP-style) when the problem has hundreds of millions to billions of nonzeros and only moderate accuracy (1e-4 relative) is needed, since it needs only matrix-vector products and parallelises well on GPUs or clusters. You give up high-accuracy answers and exact bases. Choose the dual or a decomposition (Dantzig–Wolfe, Lagrangian) when the problem is mostly independent blocks tied by a few coupling constraints, such as many campaigns sharing a few global budgets; you pay with iteration and convergence tuning.
Choose LP over a heuristic when you need a guaranteed optimum and a certificate, or sensitivity (prices); choose a greedy or heuristic method when the data is too large, the answer is needed in milliseconds, or the structure is so simple (sorting by value per cost) that a closed form exists. Choose integer programming when decisions are truly discrete and the problem size is modest; choose rounding an LP relaxation or a heuristic when the optimum is not needed exactly and you can tolerate a few per cent gap, which is common in large scheduling and allocation.
friction: Real problems are often not linear. Diminishing returns, risk terms and interaction effects are curved, so you approximate by linearising, by piecewise-linear pieces, or you move to convex programming (quadratic, second-order cone), which loses some speed. Integer requirements make problems NP-hard; solving them uses LP as a subroutine many times, and solve times vary from seconds to days with little warning.
Numerics matter. Coefficients that differ by many orders of magnitude (for example 1e-6 next to 1e6) cause poor scaling, and solvers can return slightly infeasible or slightly suboptimal answers within a tolerance of about 1e-6 to 1e-9. Degenerate problems, where many constraints are tight at one vertex, make simplex stall. The data is uncertain: the optimum is sensitive to small changes in coefficients, and a plan optimal for the forecast can be bad for the actual traffic, which motivates robust and stochastic formulations that are larger.
Formulation is the hard human part. A correct model of an ad-allocation or scheduling problem needs the right variables, constraints and objective; a wrong constraint gives an answer that satisfies the model and is useless. The open theory question, a strongly polynomial algorithm for LP, also remains unsolved, and the exact reason simplex is so fast was only explained in average and smoothed senses.
practice: Formulate before you code: write the decision variables, the objective, and each constraint in words, then as a linear expression. Check units and scale (cost in rupees against counts in millions, rescale to keep coefficients within a few orders of magnitude). Use a modelling layer (SciPy linprog, PuLP, CVXPY, OR-Tools, Pyomo) over a solver such as HiGHS (open source) or Gurobi and CPLEX (commercial), and read the status: optimal, infeasible, unbounded.
Always look at the duals and slacks, not only the primal answer. Duals tell you which constraints bind and what relaxing them is worth; an infeasible model can be diagnosed with an irreducible infeasible subset. For repeated problems (daily pacing), warm start from the last solution. For very large allocation problems, consider the dual-based approach: solve for a small vector of multipliers λ, and then assign each impression by a simple local rule value − λ × cost, which is how many ad systems implement budget constraints at serving time.

value: The Johnson–Lindenstrauss (JL) lemma says that a set of n points in a space of any dimension can be mapped into about (log n)/ε² dimensions so that every pairwise distance changes by at most a factor 1 ± ε. The map is not clever. Multiply every point by a random matrix. The target dimension depends on the number of points and the accuracy you want, and not at all on the original dimension. A million points in a million dimensions can be squeezed to roughly ten thousand dimensions with 10% distortion, and a billion-dimensional sparse feature space can be reduced the same way.
This matters because almost every algorithm on vectors costs time and memory proportional to the dimension. Nearest-neighbour search, clustering, regression on a large feature set, and similarity joins all get cheaper if the vectors are shorter. The lemma says there is a price to pay and states it exactly: you lose accuracy in distances by a controlled ε, and nothing else about the geometry is promised. It is a rare case in which dimension reduction comes with a proof and needs no training data.
For the layer above, locality-sensitive hashing for cosine similarity is built on random projections: the sign of a random projection is a one-bit hash. Approximate nearest-neighbour systems reduce dimension or compress vectors before indexing. Sketching in data systems, such as feature hashing and compressed sensing, rests on the same idea. For the layers below, probability (L4) lets us choose the matrix at random and speak of success with high probability. Linear algebra (L4) supplies the matrix and the notion of a projection. Concentration inequalities (L4) are the proof: they say that the squared length of a randomly projected vector is very close to its expected value, and a union bound over all pairs finishes the argument. Metric spaces (L4) describe what is preserved, namely Euclidean distances.
terms: Embedding (distortion) — a map f that keeps distances within a factor: (1 − ε)‖x − y‖ ≤ ‖f(x) − f(y)‖ ≤ (1 + ε)‖x − y‖.
ε (epsilon) — the allowed relative error in distances, for example 0.1 for 10%.
Random projection — multiplying vectors by a random k × d matrix to get k-dimensional vectors.
Gaussian matrix — a matrix whose entries are independent normal random numbers, here with variance 1/k.
Concentration of measure — the fact that a function of many independent random inputs, like a sum of squares, stays very close to its mean.
Union bound — the probability that any of several events happens is at most the sum of their probabilities.
Sparse JL transform — a projection matrix with only a few non-zero entries per column, which makes the projection fast.
SimHash — a locality-sensitive hash that uses the sign of a random projection to give one bit per projection.
history: William Johnson and Joram Lindenstrauss proved the lemma in 1984 in a paper about extending Lipschitz maps into Hilbert space, which is a question in functional analysis. It was not written for computers. The statement they proved was that n points in Euclidean space map into dimension O(log n / ε²) with distortion 1 + ε.
The lemma entered computer science in the 1990s, when Indyk and Motwani (1998) used random projections in approximate nearest-neighbour search and Linial, London and Rabinovich (1995) used embeddings to study graph metrics. Dasgupta and Gupta (2003) gave a short, elementary proof with explicit constants, which is the version taught today. Achlioptas (2003) showed that the Gaussian matrix could be replaced by one with entries +1 or −1, or by a sparse matrix with entries +1, 0, −1 with probabilities 1/6, 2/3, 1/6, which is easy to compute in a database, with the same guarantee.
Later work attacked speed and optimality. Ailon and Chazelle (2006) built the fast JL transform, which applies a random sign flip, a fast Fourier-type transform and a sparse projection, reducing the cost of one projection from O(dk) to about O(d log d). Kane and Nelson (2014) gave sparse constructions with only about ε⁻¹ log n non-zeros per column. Larsen and Nelson (2017) proved that the dimension k = Θ(ε⁻² log n) cannot be improved for any embedding into Euclidean space, linear or not, over a wide range of ε, so the lemma is tight. Charikar's SimHash (2002) turned the idea into a hash for cosine similarity.
how: Take n points x₁ … xₙ in ℝᵈ. Choose k, and build a k × d matrix R whose entries are independent normal random numbers with mean 0 and variance 1/k. Map each point to f(x) = Rx. The variance 1/k is chosen so that lengths are preserved on average. That is the whole algorithm; it needs no knowledge of the data.
The proof has three steps. First, linearity. The distance between f(x) and f(y) is ‖R(x − y)‖, so we only need to show that R preserves the length of one fixed vector v = x − y. Scale v to length 1. This is where linear algebra helps: a linear map turns a statement about pairs of points into a statement about single vectors.
Second, the key calculation. Each coordinate of Rv is Σⱼ Rᵢⱼ vⱼ, a sum of independent normal variables, and so it is itself normal, with variance (1/k) Σ vⱼ² = 1/k, whatever the direction of v. So ‖Rv‖² = Σᵢ (Rv)ᵢ² is a sum of k independent squared normals, each with mean 1/k, which makes the mean of the sum exactly 1 = ‖v‖². This uses probability: the rotational symmetry of Gaussian vectors means that every direction behaves the same. The sum has a chi-squared distribution divided by k. Its spread is small: its standard deviation is √(2/k).
Third, concentration. A chi-squared variable is tightly concentrated around its mean. A Chernoff-style bound (concentration inequalities) gives P(|‖Rv‖² − 1| > ε) ≤ 2·exp(−k(ε²/2 − ε³/3)/2), which falls off exponentially in k. For a fixed pair, the probability of a distortion larger than ε is therefore tiny once k is a few multiples of 1/ε². Finally the union bound: there are n(n − 1)/2 pairs, so the total failure probability is at most that number times the per-pair failure. Choosing k so that the per-pair probability is about 1/n² or smaller, which needs k of order (log n)/ε², makes the chance that any pair fails small. The Dasgupta–Gupta version states that k ≥ 4 ln n / (ε²/2 − ε³/3) suffices to make all pairs preserved with positive probability (at least 1/n), and the probability can be raised by a small increase in k or by repeating.
The estimate is also unbiased: because E‖Rv‖² = ‖v‖² exactly, the projection neither shrinks nor stretches distances on average, and the error is symmetric noise that averages out when you combine many pairs. Inner products survive as well. By the polarisation identity, ⟨x, y⟩ = (‖x + y‖² − ‖x − y‖²) / 4, so preserving the lengths of x + y and x − y preserves the inner product up to an additive error of about ε‖x‖‖y‖. This is why models and similarity scores built on dot products can run on projected sketches. The error is additive, so inner products that are small compared with the norms (nearly orthogonal vectors) are not recovered with good relative accuracy.
Notice what the proof does not use: the original dimension d never appears. The reason is rotational symmetry. A random Gaussian projection treats all directions alike, so a vector in a million dimensions loses no more length information than one in a hundred. The log n dependence comes only from the union bound. If you only care about preserving the distance from one query to the n data points, a similar argument applies with n pairs.
Practical variants change the matrix, not the idea. A ±1 matrix, or a sparse one with two thirds zeros, replaces Gaussian numbers and cuts the work by three times or more. A sparse JL transform with s non-zeros per column costs O(s·nnz(x)) per vector and works well on sparse inputs such as text, where nnz(x) is much smaller than d. Feature hashing (the "hashing trick") is a very sparse JL transform with one ±1 entry per column. The fast JL transform handles dense vectors in O(d log d). SimHash keeps only the sign of each projected coordinate: for two vectors with angle θ, the probability that a random hyperplane separates them is θ/π, so the fraction of different bits between two hash codes estimates the angle, and thus the cosine similarity.
Note the limits on what is preserved. JL preserves Euclidean (L2) distances between a finite set of points fixed before the matrix is drawn. It does not preserve L1 distances well (Brinkman and Charikar 2005 showed that no analogue exists), it does not preserve distances to points chosen after seeing the matrix, and to preserve all distances in a whole subspace of dimension r, you need about r/ε² dimensions, not log n/ε².

example: Compute the Dasgupta–Gupta dimension for n = 1,000,000 points. Take ε = 0.1. Then ε²/2 − ε³/3 = 0.005 − 0.000333 = 0.004667. The natural logarithm of a million is ln(10⁶) = 13.816. So k ≥ 4 × 13.816 / 0.004667 = 55.26 / 0.004667 ≈ 11,841. Points in 10⁶ dimensions, or 10⁹, are mapped into about 11,841 dimensions and every pairwise distance stays within 10% of its true value. For ε = 0.2: ε²/2 − ε³/3 = 0.02 − 0.002667 = 0.017333, and k ≥ 55.26 / 0.017333 ≈ 3,188. Halving the allowed error multiplies k by about 3.7 (close to 4, the 1/ε² law). These numbers are conservative. In practice, much smaller k often works, and 200 to 1,000 dimensions are usual for embeddings.
Now check the claim on a tiny case by hand. Let v = (3, 4), with ‖v‖ = 5, and project to k = 1 dimension with R = (r₁, r₂), r drawn from N(0, 1). Then Rv = 3r₁ + 4r₂, which is normal with variance 9 + 16 = 25, so |Rv| has typical size 5 = ‖v‖, matching the claim (Rv)² has mean ‖v‖². But with k = 1 the spread is huge: (Rv)²/25 is a squared standard normal, which equals 1 only on average and has standard deviation √2 ≈ 1.41. With k = 100 projections, the average of 100 such squares has standard deviation √(2/100) = 0.14, so the length is within about 7% (one standard deviation of the length is about half that of the square). With k = 10,000 the standard deviation of the squared length falls to 0.014. This is the concentration at work.
Then see what it buys in search. Suppose you have 10⁷ document vectors in 3,072 dimensions, and brute-force search takes 3,072 multiply-adds per comparison. Projecting to k = 384 cuts each comparison eightfold, and the memory from 123 GB to 15 GB in 32-bit floats. The cost: distances have a relative error of about √(2/384) ≈ 7% (one standard deviation) on squared lengths, so you retrieve a candidate list from the projected vectors, say the best 200, and re-rank it with the full vectors. This candidate-and-rerank pattern is common in vector search.
intuition: A random shadow of a high-dimensional object keeps its proportions surprisingly well, if the shadow has enough dimensions.
In high dimensions there is a great deal of room, but every single direction is a sum of many small contributions. A random direction picks up a little of every coordinate, so its measurement of a vector is an average over all of them, and averages are stable. A few hundred such independent averages are enough to reconstruct the length of any given vector accurately. The only thing that needs more of them is the number of vectors you must handle at once, and that grows only as the logarithm, because each added measurement multiplies the failure chances by a constant factor smaller than one.
mistakes: People often think JL compresses data like PCA does, by finding the important directions. In fact JL does not look at the data. PCA finds the directions of largest variance and can give better approximations of the data on a specific dataset, but needs computation and has no guarantee for all pairs. JL gives a distance guarantee for any data, at the cost of using more dimensions.
People often think the target dimension depends on the original dimension. In fact it depends only on n and ε. That is the surprise of the lemma. Going from 10⁶ to 10⁹ original dimensions changes nothing.
People often think JL keeps all structure, such as angles and nearest neighbours exactly. In fact it keeps pairwise Euclidean distances within 1 ± ε, which keeps angles and inner products approximately (additive error about ε times the norms). A true nearest neighbour whose distance is only 1% smaller than the second nearest can swap places when ε = 10%.
People often think random projection works with k as small as the final answer you want. In fact the 1/ε² law is harsh. For 1% accuracy you need 100 times more dimensions than for 10%, and for tiny n the constants matter more than the log term.
tradeoffs: Choose a random projection when you cannot or do not want to look at the data: streaming data, data that changes daily, many datasets with the same pipeline, or when a worst-case distance guarantee is needed. It costs one matrix multiply and gives an unbiased estimate of squared distances. Choose PCA or a trained embedding when a fixed dataset is available and quality matters more than guarantees; PCA usually reaches the same accuracy with several times fewer dimensions on correlated data, but costs a decomposition and has to be redone as the data drifts.
Choose a dense Gaussian matrix when d is moderate (up to thousands), accuracy matters, and the cost of O(kd) per vector is acceptable. Choose a sparse or ±1 matrix when d is large and the input is sparse; it costs less and gives practically the same error. Choose the fast JL transform when vectors are dense and d is large (tens of thousands or more), so O(d log d) beats O(kd). You give up simplicity, and the constants hide the gain at small d.
Choose a sign-only projection (SimHash) when you need compact binary codes and fast Hamming comparison: 64 to 256 bits per vector, comparisons by XOR and popcount. You give up precision, because each bit carries one bit of information, and you need many more bits than floats for the same accuracy. Choose to keep the real-valued projection when the accuracy is needed for ranking.
Choose to project and then re-rank with the original vectors when the dimension reduction is only a filter; choose to project and use the result directly when a distortion of ε is acceptable end to end, as in clustering or linear models over sketched features.
friction: The 1/ε² dependence is the main cost, and the bound is tight (Larsen and Nelson), so no cleverer embedding gives a better worst case. For ε = 0.05, the Dasgupta–Gupta formula gives k above 40,000 for a million points. Many practical systems accept ε around 0.2 to 0.3 and compensate with re-ranking.
The lemma is about Euclidean distance only and for a fixed set. It gives no promise for L1, for the maximum norm, for new points drawn after the matrix is chosen (these are covered with "oblivious subspace embeddings" which cost more), or for tasks such as classification where the labels matter. It also does not give nearest-neighbour recall directly, because recall depends on how close the competing distances are.
Implementation has its own friction. A dense random matrix of size k × d can be larger than the data itself (12,000 × 10⁶ numbers is 48 GB in float32), so it must be generated from a seed on the fly or replaced by a sparse or structured one. Results depend on the random draw, so pipelines must fix seeds to be reproducible. For trained models, learned projections and quantisation (product quantisation) often beat random ones on a specific dataset, which is why JL is more often a tool for analysis and sketching than the final compression in production vector search.
practice: Use JL when you need to shrink vectors without training, or to reason about what is possible. Before using a random projection, compute the dimension bound with your n and ε (scikit-learn provides johnson_lindenstrauss_min_dim) and compare it to the empirical error: draw random pairs, compute true and projected distances, and plot the ratio. Treat the bound as an upper estimate; empirical tests on your own data usually allow a smaller k.
For sparse high-dimensional features (text, categorical IDs), use feature hashing, which is a very sparse JL transform and needs no vocabulary. For dense embeddings in vector search, use projection or product quantisation as a first-stage filter and re-rank with full precision vectors. For binary codes use SimHash with 64 to 256 bits, and measure the Hamming recall against exact cosine neighbours.
Fix the seed, store the matrix or the seed with the data, and apply the same projection to queries and documents. If the model or data changes, remember that the projections of old and new vectors are only comparable if the same matrix is used. @@ convexity
value: Convexity is the property that makes optimisation reliable, and Jensen's inequality is its most useful consequence in probability. A function is convex when its graph is bowl-shaped: the straight line between any two points on the graph lies on or above it. A bowl has no false bottoms. Any point where you cannot go downhill locally is the global minimum, so a simple method that walks downhill is guaranteed to find the best answer and to know when it has.
For the layer above, this is why linear and logistic regression, support vector machines, LASSO and many scheduling and allocation problems can be trained or solved to a certified optimum with no tuning of initial guesses. Solvers for convex problems come with convergence rates and stopping criteria. Deep networks are not convex, and training them is a different and less certain art, but convex ideas still decide what can be analysed: the loss at the last layer, the Hessian near a minimum, and the shape of regularisers are all studied with convex tools.
The second half is Jensen's inequality: for a convex function f and a random variable X, f(E[X]) ≤ E[f(X)]. The function of the average is at most the average of the function. Applied to the logarithm, which is concave, it reverses: log E[X] ≥ E[log X]. That single step produces the evidence lower bound (ELBO) used in variational autoencoders, the guarantee that the EM algorithm improves the likelihood at every iteration, and Gibbs' inequality (KL divergence is never negative) in information theory. Calculus (L4) supplies the test, through the second derivative or Hessian, and set theory (L4) supplies the idea of a convex set, which contains the whole segment between any two of its points.
terms: Convex set — a set that contains the straight segment between any two of its points.
Convex function — a function f with f(θx + (1 − θ)y) ≤ θf(x) + (1 − θ)f(y) for all x, y and 0 ≤ θ ≤ 1; its graph lies below every chord.
Concave function — a function whose negative is convex; its graph is cap-shaped.
Hessian — the matrix of second derivatives of f; f is convex exactly when the Hessian is positive semidefinite everywhere (all eigenvalues ≥ 0).
Strong convexity — convexity with a guaranteed curvature: the Hessian has all eigenvalues at least μ > 0, so the function curves up at least as fast as a parabola.
Smoothness (L) — the gradient changes at most at rate L; the Hessian has all eigenvalues at most L.
Jensen's inequality — for convex f, f(E[X]) ≤ E[f(X)].
KKT conditions — the conditions for optimality in constrained problems: stationarity, feasibility, non-negative multipliers and complementary slackness; sufficient for optimality when the problem is convex.
history: Convexity is old geometry. Archimedes used it for the circumference of the circle, and Minkowski built a theory of convex bodies in the 1890s. Johan Jensen, a Danish engineer who did mathematics in his spare time, published the inequality that bears his name in 1906 in Acta Mathematica, in a paper on convex functions and means. Earlier special cases include the arithmetic–geometric mean inequality, which follows from it with the logarithm.
Optimisation turned convexity into a method. Fenchel and then Rockafellar (Convex Analysis, 1970) built the duality theory. The simplex method of Dantzig (1947) solved a convex case, linear programs, and the KKT conditions (Karush 1939; Kuhn and Tucker 1951) described optimality for smooth constrained problems. A major step came in 1984 with Karmarkar's interior-point method for linear programs, and in 1994 Nesterov and Nemirovski showed that interior-point methods solve a very wide class of convex problems in polynomial time. After this, "convex" came to mean "solvable". Rockafellar summed it up: the great watershed in optimisation is not between linear and nonlinear, but between convexity and non-convexity.
For machine learning, convexity gave the first generation of reliable methods: support vector machines (Cortes and Vapnik 1995), LASSO (Tibshirani 1996), and logistic regression solved by Newton-type methods. Dempster, Laird and Rubin (1977) proved that EM never decreases the likelihood, using Jensen. Compressed sensing (Candès, Romberg, Tao and Donoho, 2004–2006) showed that a convex L1 problem recovers sparse signals exactly under conditions. Variational autoencoders (Kingma and Welling, 2013) trained deep generative models with a Jensen-based bound.
how: Start with the definition and the first tests. A function f is convex when, for any two points x and y and any weight θ between 0 and 1, f(θx + (1 − θ)y) ≤ θf(x) + (1 − θ)f(y). In one dimension this is the same as f'' ≥ 0, so f(x) = x² (f'' = 2) and eˣ are convex, while log x (f'' = −1/x²) is concave. In many dimensions the test is that the Hessian matrix is positive semidefinite, which is the linear algebra statement that all its eigenvalues are non-negative, so that the function curves upwards in every direction. A first-order version is useful: f is convex if and only if f(y) ≥ f(x) + ∇f(x)ᵀ(y − x) for all x and y, meaning that the tangent plane at any point lies under the graph.
The central theorem is that a local minimum of a convex function is a global minimum. The proof is short. Suppose x is a local minimum and some y has f(y) < f(x). Along the segment from x to y, convexity gives f(x + t(y − x)) ≤ (1 − t)f(x) + t f(y) < f(x) for every t in (0, 1]. For small t this point is arbitrarily close to x, so x was not a local minimum, which is a contradiction. In the smooth case there is a stronger statement: the gradient is zero at x if and only if x is a global minimum. So the stopping rule "the gradient is nearly zero" is a certificate, which is not available for non-convex problems.
Convexity is preserved by many operations, which is how you recognise it in practice. A non-negative sum of convex functions is convex. The maximum of convex functions is convex. A convex function of a linear map, f(Ax + b), is convex. Norms are convex. The log-sum-exp function log Σ exp(zᵢ) is convex. From these rules: squared error ‖Xw − y‖² is convex in w (a convex function of a linear map); the logistic loss log(1 + exp(−y wᵀx)) is convex in w; the hinge loss max(0, 1 − y wᵀx) is convex; and softmax cross-entropy, which equals log-sum-exp(z) minus a linear term, is convex in the logits z. Adding a regulariser λ‖w‖² makes the whole function strongly convex, which has the extra benefit of a unique minimiser.
Convexity also gives speed guarantees for gradient descent. Let f be convex and L-smooth. Gradient descent with step size 1/L satisfies f(xₜ) − f* ≤ L‖x₀ − x*‖² / (2t), so the error falls like 1/t. If f is also μ-strongly convex, the error shrinks by a constant factor about (1 − μ/L) per step, which is linear (geometric) convergence. The ratio L/μ is the condition number, the same quantity that governs rounding error in numerical analysis. A long narrow valley (large L/μ) makes gradient descent zigzag; momentum, preconditioning and Newton steps reduce the effect. Calculus supplies all of this: the Hessian describes the curvature, and Taylor's theorem links the curvature to the progress per step.
Jensen's inequality is convexity applied to expectations. Treat the expectation as a weighted average with weights equal to probabilities; then f(Σ pᵢxᵢ) ≤ Σ pᵢ f(xᵢ) is the definition of convexity extended from two points to any number, and to integrals. A useful reading: the gap E[f(X)] − f(E[X]) is zero when X is constant and positive when X varies. For f(x) = x², the gap is exactly the variance. This is why variance is non-negative, and why risk-averse (concave) utility functions pay less for a gamble than for its average.
The three big uses follow. First, for the concave logarithm, E[log X] ≤ log E[X]. In a latent variable model, log p(x) = log Σ_z q(z) · p(x, z)/q(z) ≥ Σ_z q(z) log (p(x, z)/q(z)) for any distribution q. The right side is the ELBO; it is a lower bound on the log-likelihood, tight when q equals the posterior. EM alternates between choosing the q that makes the bound tight (the E step) and maximising the bound over the parameters (the M step), and each step cannot decrease log p(x). A VAE maximises the same bound with neural networks for q and p. Second, Gibbs' inequality: KL(p‖q) = E_p[−log(q/p)] ≥ −log E_p[q/p] = −log 1 = 0, so the KL divergence is never negative, and cross-entropy is at least entropy. Third, many bounds in learning theory use Jensen to move an expectation inside a convex function.

example: Check Jensen with numbers. Let X take the value 1 or 4, each with probability 1/2. Then E[X] = 2.5. For the convex function f(x) = x², f(E[X]) = 2.5² = 6.25 and E[f(X)] = (1 + 16)/2 = 8.5. So 6.25 ≤ 8.5, and the gap, 2.25, is the variance of X: E[X²] − (E[X])² = 8.5 − 6.25. For the concave function ln, ln(2.5) ≈ 0.916 and E[ln X] = (ln 1 + ln 4)/2 = (0 + 1.386)/2 = 0.693, so E[ln X] ≤ ln E[X], in the reverse direction. The arithmetic–geometric mean inequality follows: taking X = a or b with equal probability, ln((a + b)/2) ≥ (ln a + ln b)/2, so (a + b)/2 ≥ √(ab). With a = 1 and b = 9: 5 ≥ 3.
Next, gradient descent on a convex quadratic. Let f(x, y) = ½(x² + 100y²). Its Hessian is diag(1, 100), so μ = 1, L = 100, and the condition number is 100. Gradient descent with step 1/L = 0.01 updates x ← x − 0.01x = 0.99x, and y ← y − 0.01·100y = 0. So y reaches the minimum in one step, but x shrinks by only 1% per step. To reduce x by a factor 10⁶ you need ln(10⁻⁶)/ln(0.99) ≈ 1,375 steps. The slowest direction (smallest curvature) sets the speed, and this is what the factor (1 − μ/L) says. Newton's method, which divides each direction by its curvature, solves this problem in one step.
Now see the benefit in training. For logistic regression, the loss for one example is log(1 + e^(−m)) with margin m = y·wᵀx. Its second derivative in m is σ(m)(1 − σ(m)), which is between 0 and 1/4, so it is convex and 1/4-smooth in the margin. The sum over the dataset is convex in w. Full-batch gradient descent with a suitable step goes to the global minimum from any start; two runs from different random starts give the same model, up to numerical error. For a two-layer neural network with the same logistic loss, the loss as a function of the weights is not convex, and different starts can give different models with different test error.
intuition: In a bowl-shaped valley, walking downhill always leads to the bottom.
Convexity means that mixing never hurts: a blend of two points is never worse than the blend of their values. That one property rules out the traps. A false bottom would be a point lower than its neighbours but higher than somewhere far away, and a chord from that point to the lower place would have to pass above the graph, which a convex function forbids. Jensen's inequality is the same property seen through averages: averaging inputs before applying a bowl gives a lower result than averaging the outputs, and the difference measures how spread out the inputs were.
mistakes: People often think a convex function has a unique minimum. In fact convex functions can have a flat bottom with many minimisers (the function max(0, |x| − 1) is zero on [−1, 1]), or no minimum (eˣ). Strict or strong convexity gives uniqueness.
People often think convex means that gradient descent is fast. In fact convexity guarantees convergence, not speed. The rate depends on the condition number L/μ; an ill-conditioned convex problem can need millions of steps. Convex also does not mean smooth: the hinge loss and L1 norm have kinks and need subgradients.
People often think deep learning does not need convexity. In fact the guarantees of convex optimisation do not apply to deep networks, but convex tools describe the pieces: the cross-entropy loss is convex in the logits, the Hessian near a minimum is analysed with the same eigenvalue tools, and many theoretical results use convex proxies. Also, large networks have shown that non-convex landscapes can be benign: most local minima that gradient methods reach have similar loss.
People often think Jensen's inequality says E[f(X)] is "about" f(E[X]). In fact the gap can be large and has a direction. Plugging the average into a convex function underestimates the average of the function; this is the source of a common bias, for example estimating E[1/X] by 1/E[X], or E[exp(error)] by exp(E[error]).
tradeoffs: Choose a convex formulation when you can express the task that way: you get a global optimum, no dependence on initialisation, a stopping criterion and often a dual with a certificate. Choose a non-convex model (deep networks, mixture models, matrix factorisation) when the extra expressiveness is needed for accuracy; you give up guarantees, and results depend on initialisation, learning rate and luck, so you run several seeds.
Choose a convex relaxation when the true problem is hard (for example, minimising the number of non-zeros, which is NP-hard) and a convex surrogate such as the L1 norm has theory behind it. It is fast and has guarantees under conditions such as incoherence, but the relaxed optimum can differ from the true optimum, and the gap may be large on real data. Choose the original non-convex form with a heuristic when the relaxation is known to be loose.
Choose first-order methods (gradient descent, SGD, accelerated methods) for large convex problems with millions of parameters, where each step costs O(n) and moderate accuracy is enough. Choose second-order methods (Newton, L-BFGS, interior point) when the dimension is up to thousands to a few hundred thousand and you want high accuracy in tens of iterations; a Newton step costs O(d³) for a dense Hessian, and you give up scalability.
Choose a strongly convex regulariser (L2) when the problem is ill-conditioned or has several solutions: it adds μ = 2λ to the curvature and fixes the solution, at the cost of some bias. Choose L1 when you want sparsity, accepting a kink and a slower subgradient or proximal method.
friction: Most interesting problems are not convex: neural networks, clustering, mixture models, matrix factorisation, and any model with a hidden structure. For them gradient descent finds a stationary point that may be a poor local minimum or a saddle, and theory gives few guarantees. Recognising whether a problem is convex is also not automatic; disciplined convex programming (CVXPY) checks it by rules, and a problem that is convex but written in a non-recognised form is rejected.
Convex does not mean cheap. Interior-point methods need O(d³) per step; a semidefinite program with a million variables is out of reach. Convergence rates degrade with ill-conditioning, and the constants L and μ are rarely known, so step sizes are tuned by hand or by line search. Stochastic gradients add noise, and exact convergence needs a decreasing step size.
Relaxations can be loose. The LP relaxation of an integer program can have an integrality gap of a factor of two or more, and the semidefinite relaxation of some problems gives answers with no practical value. Finally, Jensen-based bounds are only as good as their gap: the ELBO is tight only if the approximate posterior q matches the true posterior, and VAEs with a limited q family can give a loose bound and biased models.
practice: When you meet an optimisation problem, ask first whether it is convex. Check the standard building blocks: linear maps, norms, squared error, log-sum-exp, max and non-negative sums are convex; products, differences and compositions in the wrong order usually are not. For small problems write it in CVXPY, which verifies convexity by rules and calls a solver; for large problems use gradient-based methods in your library with a step size from a line search or an adaptive method such as Adam.
Add L2 regularisation to make a convex problem strongly convex and well-posed, and scale features so the condition number is moderate: standardising the columns of the data matrix often reduces thousands of iterations to tens. Use the gradient norm and the duality gap as stopping criteria, instead of a fixed number of iterations. For non-convex training, use convex ideas as diagnostics: look at the loss in the last layer, check the Hessian's largest eigenvalue to choose a stable learning rate (stable steps need a step size below 2/L), and use several random starts.
For Jensen, remember its direction when you transform estimates. When a quantity is estimated with noise and then passed through a convex function, the result is biased upwards; log-transformed data gives a geometric mean below the arithmetic mean. To study, work through chapters 2 to 5 of Boyd and Vandenberghe, and the Stanford CS229 notes on EM, where Jensen is used step by step.
quiz: Why is a local minimum of a convex function also global? || If some y had lower value, then along the segment from x to y convexity gives f(x + t(y − x)) ≤ (1 − t)f(x) + t f(y) < f(x) for all small t > 0, so points arbitrarily near x would be lower, which contradicts x being a local minimum.
State Jensen's inequality and its direction for the logarithm. || For convex f, f(E[X]) ≤ E[f(X)]. The logarithm is concave, so the direction reverses: log E[X] ≥ E[log X]. This gives the ELBO as a lower bound on the log-likelihood.
For f(x, y) = ½(x² + 100y²), what step size makes gradient descent safe, and how many steps does it need to cut x by 10⁶? || A step of 1/L = 0.01. Then x ← 0.99x, and ln(10⁻⁶)/ln(0.99) ≈ 1,375 steps, because the smallest curvature (1) sets the speed, while y finishes in one step.
Why is the logistic regression loss convex in the weights, but the loss of a two-layer network is not? || Logistic loss is a convex function (log-sum-exp type) of a linear function of w, and convexity is preserved under that composition and under sums. In a two-layer network, w enters the output through a product of weights and a nonlinearity, so the composition is no longer convex.
You can either train a convex SVM or a deep network for a tabular task. When is the convex choice better? || When data is limited or reproducibility and guarantees matter, because the SVM gives a unique, repeatable optimum with a certificate and little tuning. The deep network is better when the data is large and the structure rich, at the cost of seeds, tuning and no global guarantee.

@@ combinatorics
value: Combinatorics is the mathematics of counting: how many ways can things be chosen, ordered, split or combined, without listing them. The answer decides many engineering questions. How big is the search space? How many different inputs can a hash function receive before two collide? How many servers must agree so that two decisions cannot contradict each other? How many comparisons must any sorting algorithm make? In each case a counting argument gives a hard number that no implementation can beat.
Counting is powerful because it works on whole families of cases at once, and often shows that something is impossible. There are 2ⁿ bit strings of length n but only 2ⁿ − 1 strings that are shorter, so no lossless compressor can shrink every input. There are n! orderings of n items but a comparison gives only one bit, so a comparison sort needs at least log₂(n!) ≈ n log₂ n comparisons. These are lower bounds that hold for every program, written or not.
For the layer above, consensus, quorums and Byzantine fault tolerance rest on one counting fact: two large enough subsets of a group must overlap. Sorting lower bounds, the birthday bound for collisions, and the size of data cubes (the star-tree index) all come from counting. Set theory (L4) gives the objects being counted: subsets, ordered tuples and functions. From thermodynamics (L5) comes the surprising link that Boltzmann's entropy S = k log W is the logarithm of a count of arrangements, W, which is the same quantity that Shannon later used to define information.
terms: Rule of sum — if a task can be done in a ways or in b different ways that cannot overlap, there are a + b ways.
Rule of product — if a task has a choices at step one and b choices at step two for each of them, there are a × b ways.
Permutation — an ordering of items; n distinct items have n! = n × (n − 1) × … × 1 orderings.
Combination C(n, k) — the number of ways to choose k items from n when order does not matter: n! / (k! (n − k)!).
Pigeonhole principle — if more than n items are placed in n boxes, some box holds at least two.
Inclusion–exclusion — a way to count a union by adding the sizes of the sets, subtracting the pairwise overlaps, adding back the triple overlaps, and so on.
Recurrence — an equation that defines a count in terms of smaller counts, such as C(n, k) = C(n − 1, k − 1) + C(n − 1, k).
Generating function — a power series whose coefficients are the counts you want, so that algebra on the series solves counting problems.
history: Counting problems are ancient. Indian mathematicians such as Pingala (around the third or second century BCE) counted the patterns of short and long syllables in verse, and Halayudha (tenth century) described the triangle of binomial coefficients; Chinese and Persian mathematicians also knew it centuries before Pascal. In Europe, the modern theory began with the 1654 letters between Blaise Pascal and Pierre de Fermat about dividing the stakes of an interrupted game, which started probability and combinatorics together. Jacob Bernoulli's "Ars Conjectandi" (1713) gathered the rules of counting.
In the 18th and 19th centuries Euler counted partitions and derangements, and De Moivre and Stirling found formulas for large factorials. Stirling's approximation, n! ≈ √(2πn)(n/e)ⁿ, made it possible to reason about huge counts. Cayley (1889) showed that there are nⁿ⁻² labelled trees on n vertices. Frank Ramsey (1930) proved that complete disorder is impossible in large enough structures, which started extremal combinatorics, and Paul Erdős added the probabilistic method (1947): to show that an object exists, show that a random one has the property with positive probability.
Computer science made counting a daily tool. Knuth's "The Art of Computer Programming" (from 1968) analysed algorithms by counting operations. Valiant (1979) showed that counting solutions is a harder question than finding one by defining the class #P, where computing the permanent of a matrix is complete. Flajolet and Sedgewick's "Analytic Combinatorics" (2009) gave generating functions a systematic role in the analysis of algorithms, and the same counting ideas now appear in quorum systems, hashing and the design of data structures.
how: Two rules cover most counting. The rule of product says that independent choices multiply. A password of 8 characters from 62 letters and digits has 62⁸ ≈ 2.18 × 10¹⁴ possibilities. The rule of sum says that disjoint cases add. From these come permutations: n distinct items can be ordered in n × (n − 1) × … × 1 = n! ways, since each position has one fewer choice. Choosing an ordered list of k from n gives n!/(n − k)!. If order does not matter, each unordered group of k was counted k! times, so the number of combinations is C(n, k) = n!/(k!(n − k)!). For example, C(52, 5) = 2,598,960 poker hands. The binomial theorem, (a + b)ⁿ = Σ C(n, k) aᵏ bⁿ⁻ᵏ, gives Σ C(n, k) = 2ⁿ, the number of subsets of an n-element set, which is why n binary features give 2ⁿ combinations.
Counting a union uses inclusion–exclusion. For sets A, B and C, |A ∪ B ∪ C| = |A| + |B| + |C| − |A∩B| − |A∩C| − |B∩C| + |A∩B∩C|. Adding the sets counts every overlap too many times, subtracting the pairs removes too much for triple overlaps, and adding the triple corrects it. The same pattern extends to any number of sets with alternating signs. It is the exact answer to questions such as "how many distinct users are in at least one of three audience segments?", which is relevant to audience-size estimates in ad tech where segments overlap.
The pigeonhole principle is the simplest and most useful non-constructive tool. If you hash more than m keys into m buckets, some bucket has two keys, so collisions are not a defect of a particular hash function but a certainty of counting. A stronger form says that with N items in m boxes, some box holds at least ⌈N/m⌉. The same principle proves that no lossless compression algorithm can shrink all inputs: there are 2ⁿ inputs of n bits and only 2ⁿ − 1 outputs shorter than n bits, so at least two inputs would share one output or at least one input cannot get shorter.
Overlap counting is the basis of quorums. If a set A has a members and a set B has b members, both drawn from a group of N, then |A ∩ B| ≥ a + b − N. When a + b > N this is at least 1, so any two such sets share a member. With N = 5 replicas, a write quorum W = 3 and a read quorum R = 3 satisfy R + W = 6 > 5, so every read quorum includes at least one replica that saw the latest write. That is the rule R + W > N from replicated storage. Consensus protocols use majorities (any two majorities of the same group overlap), and Byzantine fault tolerance takes N = 3f + 1 nodes with quorums of 2f + 1: two quorums overlap in at least 2(2f + 1) − (3f + 1) = f + 1 nodes, and since at most f are faulty, the overlap contains at least one honest node. These guarantees need no clever protocol detail: they follow from set theory and counting.
Large counts need estimates. Stirling's approximation gives ln n! ≈ n ln n − n + ½ ln(2πn), which is how the sorting lower bound log₂(n!) ≈ n log₂ n − 1.44n comes about. Binomial coefficients satisfy (n/k)ᵏ ≤ C(n, k) ≤ (en/k)ᵏ, and more precisely log₂ C(n, pn) ≈ n·H(p), where H(p) = −p log₂ p − (1 − p) log₂(1 − p) is the entropy function. This is the link to information theory and to Boltzmann: a physical system with W equally likely arrangements has entropy k ln W, and counting arrangements of n symbols with given frequencies gives Shannon's entropy per symbol, the number of bits needed to name one arrangement.
Recurrences and generating functions count structured objects. The Pascal recurrence C(n, k) = C(n − 1, k − 1) + C(n − 1, k) says: a k-subset either contains the last element or does not. This gives a dynamic-programming table with O(nk) entries, which avoids the huge factorials. Counting binary trees with n nodes gives the Catalan numbers (1, 1, 2, 5, 14, 42, …), and the number of ways to partition a set of n items into groups is the Bell number (B₅ = 52, B₁₀ = 115,975).

example: Example 1, inclusion–exclusion for audience segments. Three segments overlap: A has 100 users, B has 80, C has 60. The pairs share |A∩B| = 30, |A∩C| = 20, |B∩C| = 10, and 5 users are in all three. The number of distinct users is 100 + 80 + 60 − 30 − 20 − 10 + 5 = 240 − 60 + 5 = 185. If you just added the sizes you would claim 240 users, 55 too many. Check by regions: only-triple 5; A and B only 25; A and C only 15; B and C only 5; A only 100 − 25 − 15 − 5 = 55; B only 80 − 25 − 5 − 5 = 45; C only 60 − 15 − 5 − 5 = 35. Sum: 5 + 25 + 15 + 5 + 55 + 45 + 35 = 185. ✓.
Example 2, the sorting lower bound. A comparison sort must tell apart n! possible orderings, and each comparison has two outcomes, so a decision tree of depth h has at most 2ʰ leaves. We need 2ʰ ≥ n!, so h ≥ log₂(n!). For n = 1,000,000, log₂(n!) ≈ n log₂ n − 1.4427n = 19.93 × 10⁶ − 1.44 × 10⁶ ≈ 18.5 million comparisons. Merge sort uses about n log₂ n − n ≈ 19 million, so it is within 3% of the best possible. No comparison-based algorithm can do better, however clever; radix sort avoids the bound only by using more than comparisons (it looks at the digits of the keys).
Example 3, collisions by pairs. A hash function maps keys to a 32-bit space, which has 2³² ≈ 4.29 × 10⁹ values. The number of pairs among n keys is n(n − 1)/2, and each pair collides with probability 2⁻³². The expected number of colliding pairs is about n²/2³³. This reaches 1 when n ≈ √(2³³) ≈ 92,682, and the probability that any collision exists reaches 50% at about 1.1774 × 2¹⁶ ≈ 77,000 keys. With a 64-bit hash the same point is near 5 × 10⁹ keys. Pairs grow like n², so collisions come much sooner than the size of the space suggests.
Example 4, quorum overlap with numbers. In a five-node cluster, how many ways are there to choose a write quorum of 3? C(5, 3) = 10. Any two of them overlap in at least 3 + 3 − 5 = 1 node. In a Byzantine system with f = 1, N = 4 and quorums of 3: two quorums overlap in at least 3 + 3 − 4 = 2 nodes; at most one is faulty, so at least one is honest.
intuition: Counting without listing.
Many problems ask "how many" and you can answer without visiting each case if you can build the cases from independent choices, or remove overlaps with a formula. The central skill is to find a description of the objects that makes the structure visible: choices that multiply, cases that add, or a bijection with something easier to count. Many impossibility results then become one line: more objects than labels, so labels repeat.
mistakes: People often think a hash collision means the hash function is poor. In fact collisions are forced by the pigeonhole principle whenever there are more possible keys than hash values, and the birthday effect makes the first collision arrive after about √(size of the space) keys, not after the whole space is used.
People often think that "choose k from n" and "arrange k from n" are the same count. In fact order changes the count by k!: choosing 3 of 5 people for a committee gives C(5, 3) = 10, while assigning them to three named roles gives 5 × 4 × 3 = 60.
People often think inclusion–exclusion is only for small cases. In fact it is exact for any number of sets, but it has 2ᵏ − 1 terms for k sets, so it is expensive for many sets. Sketches such as HyperLogLog and MinHash estimate unions of many sets without it.
People often think a large count means a hard problem. In fact the opposite can hold: the number of spanning trees of a graph is huge but computed by a determinant (Kirchhoff's matrix-tree theorem), while the number of perfect matchings of a general graph is #P-complete even though finding one is easy. The difficulty depends on structure, not on size.
tradeoffs: Choose an exact count (a closed formula, dynamic programming over a recurrence, or inclusion–exclusion) when the structure allows it and the numbers fit: exact answers are needed for correctness arguments such as quorum sizes and for small exact tests. Choose an estimate (Stirling's approximation, the entropy form of binomials, or Monte Carlo sampling) when the count is astronomically large or only its order of magnitude is needed, such as 2¹²⁸ possible keys. You give up exactness; in return the calculation becomes feasible and shows how the count scales.
Choose a counting argument (lower bound) when you want to know whether a goal is possible at all, before building: a compressor for all files, a sort faster than n log n by comparison, a hash without collisions. Choose experiments when the counting argument is loose or only gives a worst case, such as the actual collision rate of a given hash on your data. You give up a tight, practical number.
Choose majorities (N = 2f + 1) when the failures are crashes, and the quorum overlap argument needs only one surviving member. Choose N = 3f + 1 with quorums of 2f + 1 when failures can be arbitrary (Byzantine), because the overlap must contain an honest node. You pay with 50% more machines and an extra round of messages.
Choose exhaustive search when the space is below roughly 10⁹ to 10¹⁰ states and you can enumerate them quickly; choose pruning, dynamic programming or sampling when counting shows the space is far larger, as for 30 binary features (2³⁰ ≈ 10⁹ combinations) or 20 columns in a data cube (about 10⁶ cuboids).
friction: Numbers grow explosively. The factorial 20! is already 2.4 × 10¹⁸, close to the limit of a 64-bit integer, and 52! ≈ 8 × 10⁶⁷ exceeds any hardware counter. Exhaustive search, brute-force testing of all combinations, and computing all subsets of dimensions are impossible beyond small sizes. The combinatorial explosion is the reason for heuristics, sampling and approximate algorithms in so many systems.
Exact counting is often intractable. Counting satisfying assignments, perfect matchings in general graphs, or linear extensions of a partial order is #P-complete, harder than the corresponding decision problem. Approximate counting by random sampling (Markov chains) has guarantees only for some problems.
Counting arguments also give lower bounds without telling you how to reach them, and they say nothing about distributions. The birthday bound assumes a uniformly random hash; real data and weak hash functions collide earlier. Counting subsets assumes independence of choices, which fails for dependent constraints. Finally, error-prone details abound: off-by-one in "at least" and "at most", double counting when cases overlap, and treating ordered and unordered cases alike. A small brute-force check on tiny inputs is the standard defence.
practice: Before building, count. How many keys? How many pairs? How many subsets of dimensions? A few lines of arithmetic often show that an approach is infeasible (a cube over 40 dimensions has 2⁴⁰ ≈ 10¹² cuboids) or that a risk is real (a 32-bit ID space gives collisions after tens of thousands of IDs). Use the birthday formula n²/(2M) for expected collisions with n items in a space of size M, and use 64 or 128 bits when the number of items is large.
For distributed systems, state the quorum condition as an inequality: R + W > N for reads and writes, 2W > N so two writes overlap, and N ≥ 3f + 1 for Byzantine faults. Check it by counting overlap, a + b − N. For test design, count the combinations (parameters multiply), and use pairwise or t-wise testing when the full product is too large: pairwise covering arrays reduce thousands of combinations to dozens.
When sizes are huge, compute logarithms (lgamma in most libraries) rather than factorials, and use C(n, k) via the multiplicative formula or Pascal's recurrence in a table to avoid overflow. To study, read the first chapters of Lehman, Leighton and Meyer (free), then Concrete Mathematics for generating functions, and practise by writing a brute-force counter for each formula you learn and comparing results for n up to 10.

@@ graphtheory
value: A graph is a set of points (vertices) and a set of links between them (edges). That simple structure describes an astonishing amount of computing: the web and the internet, a road map, a social network, a build system's dependencies, a database's foreign keys, the call graph of a program, the state machine of a protocol, the identity graph that links a household's devices. Once you see a problem as a graph, you can use a body of results that already says what is possible, how fast, and what is provably hard.
The value is in the vocabulary and the theorems. A path is a route, a cycle is a way back to the start, a tree is a connected graph with no cycles, a DAG (directed acyclic graph) is a set of dependencies that can be put in a valid order. "Can job A run before job B?" becomes "is there a path?". "Will these transactions deadlock?" becomes "does the wait-for graph have a cycle?". "Which machines are cut off if this switch fails?" becomes "which vertices become disconnected?". Theorems tell you which of these are quick to answer (linear time) and which are hard (NP-complete).
For the layer above, routing protocols compute shortest paths over a graph of networks, DNS and file systems are trees, garbage collectors find reachable objects in the object graph, compilers colour interference graphs to assign registers, and transaction schedulers test conflict graphs for cycles. Set theory (L4) gives the definition: a graph is a pair (V, E) of a set of vertices and a set of pairs of them. Proofs and induction (L4) give the way results are established: most graph theorems are proved by removing a vertex or edge and applying induction, or by assuming the opposite and finding a contradiction.
terms: Vertex and edge — a vertex (node) is an object; an edge is a link between two vertices, directed (one-way) or undirected.
Degree — the number of edges at a vertex; in a directed graph, in-degree counts incoming edges and out-degree counts outgoing edges.
Path and cycle — a path is a sequence of vertices joined by edges; a cycle is a path that returns to its start.
Connected component — a maximal set of vertices that can all reach each other.
Tree — a connected graph with no cycles; a tree on n vertices has exactly n − 1 edges.
DAG — a directed graph with no directed cycle; it has a topological order, an ordering of vertices in which every edge points forward.
Bipartite graph — a graph whose vertices split into two groups with every edge going between the groups; equivalent to having no odd cycle.
Graph colouring — assigning colours to vertices so that no edge joins two vertices of the same colour.
history: Graph theory began in 1736, when Leonhard Euler solved the puzzle of the seven bridges of Königsberg: can you walk through the city crossing each bridge exactly once? He replaced the map by four vertices (land masses) and seven edges (bridges) and noticed that only the number of bridges at each land mass mattered. A walk that uses every edge once needs at most two vertices of odd degree. All four land masses had an odd number of bridges (3, 3, 3 and 5), so no such walk exists. This was the first time a problem was solved by dropping everything except structure.
In the nineteenth century, Kirchhoff (1847) used graphs for electrical circuits and counted spanning trees, Cayley (1857) counted trees to enumerate chemical compounds, and the four colour question (can every map be coloured with four colours?) was posed in 1852. The proof by Appel and Haken (1976) was the first major theorem proved with a computer, checking nearly two thousand cases. Kuratowski (1930) characterised planar graphs, and Hall (1935) gave the condition for a perfect matching. The first textbook, by Dénes Kőnig, appeared in 1936.
Computers changed the questions from "does it exist?" to "how fast can we find it?". Ford and Fulkerson (1956) gave the max-flow min-cut theorem, Dijkstra (1959) shortest paths, Kahn (1962) topological sorting, and Tarjan and Hopcroft (1970s) linear-time algorithms for depth-first search, connected components and planarity. Karp (1972) showed that Hamiltonian cycle, graph colouring and clique are NP-complete. Page and Brin's PageRank (1998) used the eigenvector of the web graph, and Robertson and Seymour's graph minors theory (1983–2004) became the deepest structural result of the field. Today's graph systems handle billions of vertices.
how: Choose how to store the graph. An adjacency matrix is a V × V table with a 1 where an edge exists. It answers "is there an edge from u to v?" in O(1), but it costs V² memory: for a million vertices that is 10¹² cells (125 GB as bits), which is absurd for a sparse graph. An adjacency list stores, for each vertex, the list of its neighbours. It uses O(V + E) memory and lets you scan the neighbours of a vertex in time proportional to its degree. Real graphs are sparse (the average degree is tens or hundreds, far below V), so lists, or their compressed form CSR (compressed sparse row), are the standard.
Traversal is the basic operation. Breadth-first search (BFS) explores vertices in rings of increasing distance from a start vertex using a queue; it finds shortest paths in unweighted graphs and runs in O(V + E). Depth-first search (DFS) goes as deep as possible before backing up, using a stack or recursion; it also runs in O(V + E) and reveals structure: during DFS an edge that points back to a vertex still on the stack proves a cycle, and the order in which vertices finish gives a topological order of a DAG and the strongly connected components (Tarjan, 1972). Almost every graph algorithm is a traversal with a small piece of bookkeeping.
Directed acyclic graphs are the language of dependencies. Kahn's algorithm builds a topological order: count the in-degree of each vertex, put all vertices with in-degree 0 in a queue, repeatedly remove one, output it, and decrease the in-degree of its successors, adding any that reach 0. If all vertices are output, the order is valid. If some are never output, they lie on or behind a cycle, which is exactly the diagnosis a build system or a workflow scheduler needs. The longest path in a weighted DAG, computed by processing vertices in topological order, is the critical path that sets the minimum completion time of a project.
Weighted graphs bring shortest paths. Dijkstra's algorithm grows a set of settled vertices, always settling the unsettled vertex with the smallest tentative distance, using a priority queue; it runs in O((V + E) log V) and needs non-negative weights. Bellman–Ford handles negative weights in O(VE) and detects negative cycles. Routing protocols such as OSPF run Dijkstra over the network graph, and BGP uses path-vector rules over the graph of autonomous systems, choosing by policy and not only by length.
Connectivity has a special tool for streams of edges. Union-find (disjoint-set union) keeps each connected component as a small tree of parent pointers. Adding an edge (u, v) means finding the roots of u and v and linking them if they differ. With path compression and union by size, each operation costs almost constant time (the inverse Ackermann function, below 5 for any input that fits in a universe). It is the usual tool for incremental questions such as "are these two devices in the same household?" and it is the core of Kruskal's spanning tree algorithm. It cannot handle edge deletions, which is why dynamic connectivity is a harder research problem.
Several structural theorems drive design. The handshake lemma says the sum of degrees equals twice the number of edges, since each edge adds 1 to two degrees; so the number of odd-degree vertices is always even (induction and counting). A tree on n vertices has n − 1 edges, which is why a spanning tree (a tree touching all vertices) is the cheapest way to keep a network connected, found by Kruskal's or Prim's algorithm. Max-flow min-cut says the largest amount of flow from s to t equals the capacity of the smallest set of edges whose removal separates them, which is the same statement as linear programming duality. A graph is 2-colourable (bipartite) if and only if it has no odd cycle; but deciding whether three colours suffice is NP-complete, and register allocation is a colouring problem for this reason.
Spectral methods link graphs to linear algebra. The adjacency matrix A and the Laplacian L = D − A (D is the diagonal matrix of degrees) have eigenvalues that reveal structure: the number of zero eigenvalues of L equals the number of connected components, and the eigenvector of the second smallest eigenvalue (Fiedler vector) suggests a good way to cut the graph into two pieces. PageRank is the stationary distribution of a random walk on the web graph, found by power iteration.

example: Take the job graph in the diagram. Edges: ingest → clean, ingest → dedupe, clean → join, dedupe → join, join → report. Durations: ingest 2 h, clean 3 h, dedupe 1 h, join 4 h, report 1 h. In-degrees: ingest 0, clean 1, dedupe 1, join 2, report 1. Kahn's algorithm: the queue starts as [ingest]. Remove ingest, output it; clean and dedupe drop to in-degree 0 and join the queue. Remove clean: join drops to 1. Remove dedupe: join drops to 0 and is queued. Remove join: report drops to 0. Remove report. The order is ingest, clean, dedupe, join, report: all 5 vertices appear, so the graph is a DAG.
Now compute the earliest finish time of each job, going in this order. ingest: 2. clean: 2 + 3 = 5. dedupe: 2 + 1 = 3. join must wait for both inputs: start at max(5, 3) = 5, finish at 9. report: 9 + 1 = 10. The whole pipeline needs 10 hours, set by the critical path ingest → clean → join → report. Shortening dedupe does nothing, and shortening clean by one hour saves one hour. This is how workflow schedulers find the jobs that matter.
Next, add the edge report → ingest (a "feedback" dependency). In-degree of ingest becomes 1, so no vertex has in-degree 0, and Kahn's algorithm outputs nothing: the whole graph is on a cycle. DFS would find the back edge from report to ingest. The scheduler can report the cycle ingest → clean → join → report → ingest, which is precisely the information the user needs.
Last, Königsberg by degrees. Land masses have 3, 3, 3 and 5 bridges. The sum is 14 = 2 × 7 bridges, as the handshake lemma requires. A walk using every edge once can have at most two odd-degree vertices (the start and the end), but here there are four, so no such walk exists. Euler's theorem also tells you the reverse: a connected graph with 0 or 2 odd vertices has such a walk, and it can be found in linear time. Finding a walk that visits every vertex once (a Hamiltonian path) looks similar, but it is NP-complete.
intuition: Dots and lines, and the surprising number of questions they answer.
A graph keeps only what matters about relations: who is connected to whom. That makes it a common language across fields. Because it forgets all else, any algorithm for graphs applies to every problem that can be expressed that way, and any proof of hardness transfers too. Local rules (an edge, a neighbour) build global properties (a path, a cycle, a component), and most graph algorithms are ways of following local links patiently until the global answer appears.
mistakes: People often think a tree and a DAG are the same. In fact a tree is a connected, undirected graph with no cycles, while a DAG is a directed graph with no directed cycles. A DAG can have many paths from one vertex to another (a diamond: join with two inputs), which a tree never has.
People often think a graph with few edges is cheap to store as a matrix. In fact an adjacency matrix costs V² regardless of E. Use adjacency lists or CSR for sparse graphs, and a matrix only for dense graphs or small V where constant-time edge checks matter.
People often think finding a shortest path and finding a longest path are equally hard. In fact shortest paths in graphs with non-negative weights take near-linear time, while longest simple path in a general graph is NP-hard (it includes Hamiltonian path). In a DAG, however, longest path is easy, because the topological order removes the cycles.
People often think that shortest path means fewest edges. In fact that holds only for unweighted graphs (BFS). With weights you need Dijkstra or Bellman–Ford, and in routing, the metric may be a policy-based preference and not a distance at all.
People often think "no cycle found" means "no deadlock possible". In fact a wait-for graph shows only the waits that exist now. A cycle check finds deadlocks that have already occurred; prevention needs an ordering of lock acquisition so a cycle can never form.
tradeoffs: Choose an adjacency list (or CSR) when the graph is sparse (E near V or a small multiple), which is nearly always for real data; it supports fast neighbour scans and uses O(V + E) memory. Choose an adjacency matrix when the graph is dense, V is a few thousand or less, or you want algebra on it (matrix products count paths); you pay V² memory and lose on sparse data.
Choose BFS when you need the fewest hops, the shortest path in an unweighted graph, or levels; its queue can hold a whole frontier, which can be a large part of the graph. Choose DFS when you need structure (cycles, topological order, components, bridges) with small memory O(depth); it does not give shortest paths. Choose Dijkstra for non-negative weights and Bellman–Ford only when negative weights exist; use A* with a good heuristic when you have one target and a distance estimate.
Choose an in-memory graph library (NetworkX for experiments, igraph or a CSR in C++ for speed) when the graph fits in memory, which means up to roughly a billion edges on a large machine. Choose a distributed graph framework (GraphX, Pregel-style systems) or a graph database when the graph exceeds memory or needs multi-hop queries on live data. You pay with communication costs, because graph algorithms have poor locality: each hop can touch another machine, and iterations must synchronise.
Choose exact algorithms for problems in P (shortest path, matching, flow, connectivity). Choose heuristics or approximation for NP-hard ones (colouring, clique, travelling salesman, longest path): greedy colouring in register allocation, approximation algorithms with provable ratios, or ILP solvers for modest sizes. You give up optimality guarantees but keep tractable run time.
friction: Many graph problems are NP-hard: Hamiltonian cycle, colouring with three or more colours, clique, minimum vertex cover, travelling salesman. For these, no known algorithm is fast in the worst case, and systems rely on heuristics. Even polynomial problems become expensive at web scale: a dense all-pairs shortest path computation needs V² output, impossible for a billion vertices.
Real graphs are skewed. Degree distributions follow power laws: a few hubs have millions of neighbours while most vertices have a handful. This breaks load balancing in distributed systems (a hub's partition becomes a hot spot), makes the number of two-hop neighbours explode (friends of friends), and slows BFS because a single level can contain most of the graph. Graph algorithms also have irregular memory access, which wastes cache and GPU bandwidth: following a pointer is a cache miss.
Graphs change. Maintaining connectivity or shortest paths under edge insertions and deletions is much harder than computing them once. Identity graphs in ad tech are noisy: a wrong edge (two households linked by a shared IP address) merges components and spreads the error, so thresholds and edge confidence matter. Finally, the model itself loses information: edges between two things say nothing about the type or strength of a relation unless you add labels and weights, and hypergraphs or property graphs are then needed.
practice: Say what the vertices and edges mean, whether edges are directed or weighted, and how big V and E are. Then pick the right standard algorithm before inventing anything. Dependencies: topological sort. Reachability and components: BFS, DFS or union-find (disjoint sets), which handles an incremental stream of edges in nearly constant time per edge. Cheapest connection: minimum spanning tree. Routing: Dijkstra. Assignment: bipartite matching or max-flow. Importance: PageRank.
Check the graph first: count vertices, edges, components, the degree distribution, and whether it is acyclic. For identity or user graphs, plot the component size distribution; a giant component of millions of nodes usually signals a bad merge rule. Use CSR for static graphs, and avoid pointer-based node objects for large graphs. For pipelines on Spark or Databricks, use GraphFrames or iterative joins for connected components, and expect many iterations on long-diameter graphs.
In workflow and build systems, validate that the dependency graph is a DAG at definition time and report the cycle path in the error. In databases, detect deadlock with a wait-for graph and choose a victim. To study, work through Easley and Kleinberg for networks, West for theory, and implement BFS, DFS, Kahn and Dijkstra yourself once on a graph of a few thousand nodes.

@@ ordertheory
value: Order theory studies the ways things can be ranked when not everything has to be comparable. In a total order, such as the integers, any two items can be compared. In a partial order, some pairs are simply incomparable: two sets that each contain something the other lacks, two events on different machines with no message between them, two versions of a file edited separately. Distributed systems, compilers and databases are full of such situations, and order theory gives the precise language to reason about them.
The idea with the most practical force is the lattice. A lattice is a partial order in which every two elements have a least upper bound, called their join: the smallest thing that is above both. If the states of replicas form such a structure, and every update moves a state upward, then merging two replicas by taking their join is safe. The join does not depend on the order of arrival (it is commutative and associative) and does not mind duplicates (it is idempotent). Replicas that have seen the same updates end in the same state, without a coordinator. This is the mathematical core of CRDTs.
For the layer above, the happened-before relation behind Lamport clocks and vector clocks is a partial order, and the clocks are ways of representing it. CRDTs use joins to converge. Dataflow analysis in compilers lets facts climb a lattice until they stop changing. Concurrency control and isolation levels ask for an order: a schedule is serialisable if there is one total order of transactions consistent with the partial order of their conflicts. Set theory (L4) supplies the base: an order is a relation, that is, a set of pairs, with three properties, and a lattice is built on it.
terms: Partial order — a relation ≤ on a set that is reflexive (a ≤ a), antisymmetric (a ≤ b and b ≤ a imply a = b) and transitive (a ≤ b and b ≤ c imply a ≤ c).
Comparable and incomparable — a and b are comparable if a ≤ b or b ≤ a; otherwise they are incomparable (concurrent, in a distributed system).
Chain and antichain — a chain is a set of pairwise comparable elements; an antichain is a set of pairwise incomparable elements.
Join (least upper bound) — the smallest element that is above both a and b, written a ∨ b.
Meet (greatest lower bound) — the largest element that is below both, written a ∧ b.
Lattice — a partial order in which every pair has both a join and a meet; a join-semilattice only needs joins.
Monotone function — a function f with a ≤ b implying f(a) ≤ f(b); it never reverses order.
Fixed point — a value x with f(x) = x; iterating a monotone function on a lattice of finite height reaches one.
Linear extension — a total order that agrees with a given partial order; a topological order is one.
history: Order and lattice ideas came out of nineteenth-century algebra and logic. Richard Dedekind (1890s) studied the structure of ideals and subgroups under "meet" and "join". George Boole's algebra of logic is a lattice, with AND as meet and OR as join. Garrett Birkhoff gave the subject its modern form in the 1930s and wrote "Lattice Theory" (1940), including the representation theorem for finite distributive lattices.
Alfred Tarski proved in 1955 that every monotone function on a complete lattice has a fixed point (the Knaster–Tarski theorem). Dana Scott used complete partial orders in the early 1970s to give meaning to recursive programs: the meaning of a recursive definition is the least fixed point of a monotone function. Gary Kildall (1973) saw that compiler optimisations could be run as iteration on a lattice of facts, and Patrick and Radhia Cousot (1977) built abstract interpretation on the same structure, adding widening to handle lattices of infinite height.
Distributed computing arrived at the same structure from a different side. Leslie Lamport (1978) defined the happened-before partial order on events, and Colin Fidge and Friedemann Mattern (1988) independently devised vector clocks to represent it. Bernadette Charron-Bost (1991) proved that this representation needs one counter per process. Shapiro, Preguiça, Baquero and Zawirski (2011) named CRDTs and showed that semilattice states with monotone updates converge. Hellerstein and Alvaro's CALM principle (conjectured 2010, proved by Ameloot, Neven and Van den Bussche in 2011) says that programs which are monotone need no coordination to be consistent. Delta-state CRDTs (Almeida, Shoker and Baquero, 2015–2018) made them efficient to send.
how: A partial order is any relation with three properties: a ≤ a; if a ≤ b and b ≤ a then a = b; if a ≤ b and b ≤ c then a ≤ c. The integers with ≤ give a total order. The more typical example is a set of sets ordered by inclusion: {1} and {2} are both below {1, 2} but are not comparable to each other. Another is divisibility on positive integers: 4 and 6 are incomparable, while 2 divides both. A Hasse diagram draws only the "immediate above" links, so it shows the shape. Elements with no comparison are the reason why order theory is needed: a total order is just a sorted list, but a partial order can have a width.
Joins and meets turn the order into algebra. In the divisibility order, the join of 4 and 6 (the smallest number divisible by both) is their least common multiple, 12, and the meet is their greatest common divisor, 2. In the subset order, the join is union and the meet is intersection. The key equivalence is that join is a binary operation with three algebraic laws: commutative (a ∨ b = b ∨ a), associative ((a ∨ b) ∨ c = a ∨ (b ∨ c)) and idempotent (a ∨ a = a). Conversely, any operation with these three laws defines an order by saying a ≤ b exactly when a ∨ b = b. So "a semilattice" and "a merge operation with the three laws" are the same object seen in two ways.
CRDTs use this directly. A state-based CRDT has a state space that is a join-semilattice, update operations that only move the state up (they are inflationary), and a merge function that is the join. Why do the three laws matter? A network may deliver the same state twice (idempotence), may deliver states in a different order on different replicas (commutativity), and replicas may merge in different groupings (associativity). With these laws, any replicas that have received the same set of updates, in any order and with any duplicates, reach exactly the same state. This is strong eventual consistency, obtained from mathematics and not from a protocol. The grow-only counter is the standard example: the state is a vector with one counter per replica, a replica increments only its own entry, merge takes the maximum in each position, and the value is the sum.
Vector clocks show the order itself. Give each of n processes a counter. Each event increments its process's entry, and each message carries the sender's vector; a receiver takes the entry-wise maximum with it and then increments its own. Compare two vectors V and W: V ≤ W if every entry of V is at most the entry of W. If V ≤ W (and they differ), the first event happened before the second; if neither V ≤ W nor W ≤ V, the events are concurrent. The set of vectors under entry-wise ≤ is a lattice with join = entry-wise maximum, which is exactly the merge when a message arrives. Lamport clocks are a single number and give a total order that extends happened-before, but cannot detect concurrency: from L(a) < L(b) you cannot conclude that a happened before b.
Dataflow analysis uses the same structure on programs. Take constant propagation. For each variable the facts form a small lattice: ⊥ (no information yet), then each specific constant, then ⊤ ("not a constant"). Each program statement has a transfer function that maps facts before to facts after, and these functions are monotone. At a point where two branches merge, the facts are combined by join: if one branch has x = 1 and the other x = 2, the join is ⊤. The analysis starts from ⊥ and repeatedly applies the transfer functions until nothing changes. Because the lattice has finite height (each variable can rise at most twice, ⊥ → constant → ⊤) and the functions are monotone, the iteration must stop, and by the Knaster–Tarski and Kleene theorems it stops at the least fixed point. With v variables and p program points, the number of changes is bounded by about 2vp, which proves termination. For infinite lattices, such as intervals [low, high], widening jumps ahead to guarantee that the climb ends.
Serialisability and isolation reduce to linear extensions. Two transactions conflict if they access the same item and at least one writes. Put an edge from T1 to T2 if T1's conflicting operation comes first. The schedule is conflict-serialisable exactly when this graph has no cycle, which means the partial order of conflicts has a linear extension: a total order of transactions that respects it. Two-phase locking and timestamp ordering are ways to make the system create only schedules that have such an extension. Memory models also talk in these terms: they define which orderings of reads and writes by different threads are allowed, which is a partial order of events with extra rules.

example: Example 1, merging counters. Three replicas A, B and C each keep a vector of three counts, and each increments only its own slot. After some activity, A holds (3, 0, 0), B holds (0, 2, 0) and C holds (0, 0, 4). A merges with B and gets the entry-wise maximum (3, 2, 0). Then A merges with C and gets (3, 2, 4), and the counter's value is 3 + 2 + 4 = 9. Now change the delivery: C sends its state to B first, giving (0, 2, 4); then B sends to A, giving (3, 2, 4); then A receives C's state a second time, a duplicate: max with (0, 0, 4) leaves (3, 2, 4). All delivery orders reach (3, 2, 4). Compare a naive design where replicas send increments and the receiver adds them: a duplicated message of "+4" would give 13, and a lost one gives 5. Taking the maximum is idempotent; adding is not.
Example 2, vector clocks. Process P1 has V = (2, 1, 0) and process P2 has W = (1, 2, 0). Is V ≤ W? The first entry 2 > 1, so no. Is W ≤ V? The second entry 2 > 1, so no. The events are concurrent: each saw something the other did not. A store like Dynamo or Riak that sees two writes with these clocks must keep both as siblings. The join (2, 2, 0) is the clock of a merged version, which is above both. If instead W were (3, 1, 0), then V ≤ W and the second write supersedes the first, so the older one can be discarded.
Example 3, constant propagation. Program: if c then x = 1 else x = 2; y = x + 1. At the merge point, the fact for x is join(1, 2) = ⊤, so x is not a constant and y = x + 1 is also ⊤. If both branches set x = 1, the join is 1 and y = 2, which the compiler can fold into a constant. Each variable's fact can change at most twice (⊥ to a constant to ⊤), so with 10 variables, at most 20 changes per program point, which is why the analysis terminates quickly.
intuition: Not everything can be ranked, but any two things may have a smallest thing above both.
Think of version histories. Two people edit the same document separately. Neither version is "later" than the other, but there is a smallest version that contains both sets of changes. If every system agrees on how to combine versions in this way, and combining is harmless to repeat, then the order in which news travels no longer matters. The same picture explains compilers: facts about a program only become less specific as paths merge, and a process that only moves up in a finite structure has to end.
mistakes: People often think a partial order is a total order with some ties. In fact incomparable elements are not equal; they carry different information. Treating concurrent events as ordered (by a timestamp) hides a conflict; keeping it visible is the whole point of vector clocks.
People often think Lamport timestamps can detect concurrency. In fact if a happened before b then L(a) < L(b), but the reverse does not hold: L(a) < L(b) can occur with a and b concurrent. Only vector clocks (or similar) characterise the order exactly.
People often think any merge function makes a CRDT. In fact the merge must be commutative, associative and idempotent, and updates must be inflationary. A "merge" that adds counts, or overwrites by arrival order, breaks convergence under duplicates and reordering.
People often think a lattice means there must be a smallest and a largest element. In fact a lattice only needs a join and a meet for every pair. A bounded lattice has a bottom and a top; unbounded ones, like the set of all finite subsets of the integers under union, are also lattices. Convergence needs only that the join exists.
People often think CRDTs remove all conflicts. In fact they guarantee that replicas agree, not that the agreed result is what a user wanted. A set where one user adds an item and another removes it must pick a rule (add wins, remove wins), and the result may surprise people.
tradeoffs: Choose a CRDT (a lattice-based design) when availability and low latency matter more than a single global order, for example collaborative editing, shopping carts, counters that tolerate temporary divergence, or offline-first mobile data. You give up the ability to enforce invariants that need coordination: a CRDT counter cannot guarantee that a balance never goes below zero. Choose consensus (Raft, Paxos) when you need a single agreed order, uniqueness, or invariants across replicas; you pay with latency of a round trip to a majority and unavailability without a quorum.
Choose state-based CRDTs when messages may be lost, duplicated or reordered and states are small; they are the simplest to reason about. Choose operation-based CRDTs when the state is large and each operation is small, but you need a delivery layer that is reliable and ordered by causality, with no duplicates. Choose delta-state CRDTs to get both: you send only the changes since the last merge, and they are still joins, so duplication is harmless.
Choose vector clocks when you need to detect concurrency exactly and the number of writers is small (tens). Choose version vectors per key with dotted version vectors to limit growth, or hybrid logical clocks (a physical time plus a counter) when you need timestamps close to wall-clock time and can accept that concurrency is not detected. Choose Lamport clocks when only a consistent total order is needed and concurrency detection is not.
Choose a precise abstract domain (the full constant lattice, or octagons) in compile-time analysis when the code is critical and time allows; choose a coarse one (signs, or intervals with widening) when the analysis must be fast on a huge code base. Precision costs a taller lattice, more iterations and more memory per fact.
friction: Lattices must be designed with care. Deletion is the hard case, since every update must go up. Removing an element needs a tombstone (a marker that the item was removed) or a more complex structure such as an observed-remove set, and tombstones accumulate until a garbage-collection protocol, which itself needs coordination, discards them. Metadata growth is a real cost: a vector clock with one entry per client grows with the number of clients, and Charron-Bost showed that you cannot represent the happened-before order in fewer than n entries for n processes.
Semantics are limited. Convergence does not mean intent is preserved. Text editing CRDTs must choose how to interleave concurrent inserts at the same position, and different designs give different results. Monotone structures cannot express operations that need to see everything ("is the set empty?", "what is the total?") safely before coordination, which is the content of the CALM theorem: non-monotone questions need coordination.
Order theory itself has hard computational problems. Counting the linear extensions of a partial order is #P-complete (Brightwell and Winkler, 1991). The width of a partial order (the largest antichain, which by Dilworth's theorem equals the minimum number of chains covering it) measures how much true concurrency there is, and large width means more states to explore in model checking. In dataflow analysis, precise analyses may be expensive, and the iteration order matters for speed, though not for the result.
practice: When you design a replicated data type, write down the state, the order on states, the update operations and the merge, and check the three laws and the inflationary property with a property test: generate random states, merge in random order with duplicates, and assert equality. Start from known building blocks: grow-only set, grow-only counter, max register, last-writer-wins register (timestamp plus replica ID as tie-break, which gives a total order), two-phase set, and observed-remove set. Use a library such as Automerge, Yjs or Riak's data types instead of writing text CRDTs yourself.
In stores with causal versions, interpret vector clocks correctly: discard a version only if its clock is strictly below another; keep concurrent ones as siblings and merge them with a defined rule. Prune clocks by bounding the number of entries only if you accept false conflicts. When designing pipelines, ask whether an operation is monotone: adding facts is, retracting them is not, and monotone pipelines can run without coordination, as in streaming systems that handle late data by adding more.
For compilers and static analysis, define the lattice and transfer functions first, check monotonicity, and look at the height to bound the iterations; process basic blocks in reverse postorder to converge faster. To study, read the first three chapters of Davey and Priestley, the CRDT paper by Shapiro et al., and the lecture notes on dataflow analysis in Stanford CS243.
quiz: What three properties must a CRDT merge have, and what failure does each one prevent? || Commutative: replicas that receive updates in different orders still agree. Associative: different groupings of merges give the same result. Idempotent: a duplicated message does no harm.
What is the join of 4 and 6 in the divisibility order, and what is the meet? || The join is the least common multiple, 12, and the meet is the greatest common divisor, 2. 4 and 6 themselves are incomparable.
How do you decide from vector clocks (2, 1, 0) and (1, 2, 0) whether one event happened before the other? || Compare entry by entry. Neither is at most the other (2 > 1 in the first entry for one direction, 2 > 1 in the second entry for the other), so the events are concurrent. Their join is (2, 2, 0).
Why does constant propagation terminate on a lattice with ⊥, constants and ⊤? || Transfer functions are monotone and each variable's fact can rise at most twice (⊥ to a constant to ⊤), so the total number of changes is bounded (about 2 × variables × program points) and the iteration reaches a fixed point.
When would you choose consensus over a CRDT? || When you must enforce an invariant or a single order, such as a unique username or a balance that cannot go negative. CRDTs stay available during partitions but cannot prevent concurrent updates that jointly break such invariants.

@@ codingtheory
value: Coding theory answers a basic question about unreliable storage and communication: how much extra data must you add to a message so that the original can be recovered after some of it is damaged or lost? The answer is not "copy it three times". Cleverly structured redundancy can repair many errors with far less overhead. A 64-bit word in server memory carries 8 extra bits and can repair any single flipped bit and detect any two. A cloud object store can lose three of nine fragments and still rebuild the data with 1.5 times the storage, where plain replication would need 3 times.
The theory has two halves. The first is a limit: Shannon proved in 1948 that for every noisy channel there is a capacity, and that reliable communication is possible at any rate below it and impossible above it. The second is construction: Hamming, Reed–Solomon, BCH, LDPC, turbo and polar codes are ways to get close to that limit with fast encoding and decoding. CRCs, by contrast, only detect errors, which is cheaper and often enough.
For the layer above, ECC memory, SSDs, hard disks, QR codes, CDs, Wi-Fi, 5G, deep-space links and erasure-coded storage (HDFS, S3-like systems, RAID 6) are all applications. Information theory (L4) supplies the limit and the vocabulary of entropy and capacity. Finite fields (L4) supply the arithmetic: Reed–Solomon codes treat data as polynomials over a field such as GF(256), where bytes can be added, multiplied and divided without overflow. Thermal noise and signal-to-noise (L5) explain why channels make errors at all, and set the capacity formula that the codes aim at. Even UTF-8, a variable-length code designed so a reader can resynchronise after a damaged byte, borrows the idea.
terms: Codeword — a valid encoded block of n symbols; the code is the set of all valid codewords.
Rate — k/n, the fraction of a codeword that carries data; a rate-2/3 code adds 50% redundancy.
Hamming distance — the number of positions where two words differ.
Minimum distance (d) — the smallest Hamming distance between two different codewords; it decides how many errors a code can detect (d − 1) and correct (⌊(d − 1)/2⌋).
Parity check — an extra bit equal to the XOR of a chosen group of data bits.
Syndrome — the pattern of failed parity checks on a received word; for a single error it points to the position of the error.
Erasure — a symbol known to be lost, as opposed to an error, whose position is unknown; erasures are twice as cheap to repair.
MDS code — a code that reaches the best possible distance d = n − k + 1, such as Reed–Solomon; any k of the n symbols suffice to rebuild the data.
Channel capacity — the highest rate at which information can be sent with an error probability that goes to zero.
history: Claude Shannon's 1948 paper "A Mathematical Theory of Communication" proved that a noisy channel has a capacity C and that codes exist with rate below C and arbitrarily small error. He did not show how to build them. The proof was an existence argument using random codes, and the search for practical codes that approach the limit lasted for more than forty years.
Richard Hamming, working at Bell Labs on relay computers in the late 1940s, was frustrated that a single error stopped a weekend batch job. He designed codes that find and fix the error, and published them in 1950. Marcel Golay (1949) found a perfect code that was used on the Voyager spacecraft. Irving Reed and Gustave Solomon (1960) published codes over larger alphabets, where each symbol is a byte, which are excellent for burst errors; Berlekamp (1968) and Massey (1969) gave an efficient decoder. Reed–Solomon codes went on to CDs (the CIRC scheme, early 1980s), QR codes, DVDs, deep-space probes and RAID 6.
Robert Gallager invented LDPC (low-density parity-check) codes in his 1960 thesis, but computers were too weak and the idea was set aside. In 1993 Berrou, Glavieux and Thitimajshima announced turbo codes, which came within a fraction of a decibel of Shannon's limit and surprised the field. MacKay and Neal (1996) rediscovered LDPC codes and showed they were as good. Erdal Arıkan (2009) invented polar codes, the first with a proof of reaching capacity with efficient encoding and decoding. 5G uses LDPC for data channels and polar codes for control channels; modern SSDs use LDPC with soft information read from the flash cells; cloud storage uses Reed–Solomon and locally repairable codes (Huang et al. for Azure, 2012).
how: Start with the simplest idea: add a parity bit. Append one bit that makes the number of 1s even. Any single flipped bit makes the count odd, so you detect the error, but you do not know which bit it was. The minimum distance of this code is 2, which detects 1 error and corrects none. To correct, you need distance 3: if every pair of codewords differs in at least 3 positions, then a word with one error is within distance 1 of exactly one codeword and distance 2 or more from every other, so you decode to the nearest codeword. In general, distance d corrects ⌊(d − 1)/2⌋ errors, or d − 1 erasures. This is the geometric picture: codewords are points in a space of words, with Hamming distance as the metric, and decoding rounds to the nearest point.
Hamming's (7,4) code puts 4 data bits and 3 parity bits in 7 positions numbered 1 to 7. The parity bits go at positions 1, 2 and 4 (powers of two). Parity bit p₁ checks positions whose binary number has a 1 in the last place (1, 3, 5, 7); p₂ checks positions with a 1 in the middle (2, 3, 6, 7); p₄ checks positions with a 1 in the first place (4, 5, 6, 7). Every position from 1 to 7 is covered by a different non-empty set of checks, so when one bit flips, the pattern of failed checks, read as a binary number, is the position of the flipped bit. That number is the syndrome. All of this is linear algebra over GF(2): the code is the set of vectors x with Hx = 0, where H is the 3 × 7 parity-check matrix whose columns are the numbers 1 to 7 in binary, and the syndrome is Hr for the received word r. Adding one more overall parity bit gives the SECDED code (single error correction, double error detection) used in ECC memory: 8 check bits protect 64 data bits, a 12.5% overhead.
For burst errors and erasures, one uses algebra over larger fields. A Reed–Solomon code over GF(q) takes k data symbols as the coefficients of a polynomial p of degree less than k, and sends the values p(a₁), …, p(aₙ) at n distinct points. Any k of the n values determine the polynomial uniquely (interpolation, as a polynomial of degree k − 1 has at most k − 1 roots), so the data can be rebuilt from any k symbols: this is the MDS property, and the distance is n − k + 1, the best possible. With n − k erasures known, you interpolate from what remains. With errors in unknown places, the decoder (Berlekamp–Massey, or the Welch–Berlekamp method) finds up to (n − k)/2 wrong symbols. Finite fields are essential: GF(256) lets every byte be a field element, and the arithmetic of addition (XOR) and multiplication (table lookups or carry-less multiply instructions) is exact and never overflows. Classic parameters are RS(255, 223), correcting 16 byte errors, used by NASA.
Shannon's limit shows what is possible. For the binary symmetric channel that flips each bit with probability p, the capacity is C = 1 − H(p), where H(p) = −p log₂ p − (1 − p) log₂(1 − p). If p = 0.11, then H(p) ≈ 0.5 and C ≈ 0.5: at best one useful bit per two sent. For a Gaussian channel with bandwidth B and signal-to-noise ratio S/N, C = B log₂(1 + S/N), where the noise comes from thermal noise physics. The codes ask how closely a practical, decodable code can approach this. Hamming-style algebraic codes with short blocks are far from capacity; LDPC and turbo codes use long blocks (thousands of bits), a sparse parity-check matrix, and iterative decoding by belief propagation, in which bits and checks exchange probability estimates along the edges of a graph until they agree. Polar codes use a recursive transformation that polarises channels into perfectly good and perfectly bad ones. They reach within a fraction of a decibel of capacity.
Error detection is simpler. A CRC treats the message as a polynomial over GF(2), divides it by a fixed generator polynomial and appends the remainder. The receiver divides again; a non-zero remainder means corruption. A CRC-32 detects all burst errors up to 32 bits and all but about 1 in 4.3 billion random corruptions, but cannot correct. Real systems layer them: an SSD uses LDPC to correct, a CRC to detect what ECC missed, and checksums at higher levels.
Erasure coding in storage uses Reed–Solomon over bytes. With RS(6, 3), the data is split into 6 blocks and 3 parity blocks are computed, giving 9 blocks on 9 different machines or racks. Any 6 of the 9 rebuild the data, so three failures are tolerated with 1.5 times the storage, against 4 copies (4 times) for the same tolerance by replication. The price is repair traffic: rebuilding one lost block reads 6 blocks, so locally repairable codes add extra local parities to reduce this.

example: Encode the data bits d₁d₂d₃d₄ = 1 0 1 1 with Hamming (7,4). p₁ covers positions 1, 3, 5, 7, which hold p₁, d₁, d₂, d₄ = ?, 1, 0, 1, so for even parity p₁ = 1 ⊕ 0 ⊕ 1 = 0. p₂ covers positions 2, 3, 6, 7: p₂, d₁, d₃, d₄ = ?, 1, 1, 1, so p₂ = 1 ⊕ 1 ⊕ 1 = 1. p₄ covers positions 4, 5, 6, 7: p₄, d₂, d₃, d₄ = ?, 0, 1, 1, so p₄ = 0 ⊕ 1 ⊕ 1 = 0. The codeword in positions 1 to 7 is p₁ p₂ d₁ p₄ d₂ d₃ d₄ = 0 1 1 0 0 1 1.
Now flip position 6 in transit, so we receive 0 1 1 0 0 0 1. Recompute the checks. Check 1 (positions 1, 3, 5, 7): 0 ⊕ 1 ⊕ 0 ⊕ 1 = 0, passes. Check 2 (positions 2, 3, 6, 7): 1 ⊕ 1 ⊕ 0 ⊕ 1 = 1, fails. Check 4 (positions 4, 5, 6, 7): 0 ⊕ 0 ⊕ 0 ⊕ 1 = 1, fails. Reading the checks as a binary number with check 4 as the most significant bit gives 1 1 0 = 6. The error is at position 6. Flip it back and the data is 1 0 1 1. Three bits of overhead (75% extra) protect four bits. That is a heavy cost for short words; longer codes are cheaper: Hamming (127, 120) uses 7 check bits for 120 data bits, 5.8%.
Reed–Solomon example with a tiny field. Use arithmetic modulo 7 (a field with 7 elements, the numbers 0 to 6). Let the data be (2, 3), the polynomial p(x) = 2 + 3x, so k = 2. Send the values at x = 1, 2, 3, 4: p(1) = 5, p(2) = 8 mod 7 = 1, p(3) = 11 mod 7 = 4, p(4) = 14 mod 7 = 0. So the codeword is (5, 1, 4, 0), with n = 4 and distance n − k + 1 = 3. Suppose the second and fourth symbols are erased. You have p(1) = 5 and p(3) = 4. A line through (1, 5) and (3, 4) has slope (4 − 5)/(3 − 1) = −1/2. In mod 7, 2⁻¹ = 4, so the slope is −4 = 3. Then p(x) = 5 + 3(x − 1) = 2 + 3x. That recovers (2, 3). Any 2 of the 4 values work, since two points fix a line.
intuition: Add carefully chosen extra information so the original can be rebuilt from damaged copies.
Think of the words of a language that is deliberately spelled so that no two valid words are close together. If a few letters are garbled, the garbled word is still nearer to the intended word than to any other, so you can say which word was meant. Coding theory builds such a vocabulary in a space of bit strings. The best vocabularies come from algebra: a polynomial of degree k − 1 is fixed by any k of its points, so n points carry the information redundantly and evenly, and no particular k of them is special.
mistakes: People often think redundancy means repetition. In fact repetition is the least efficient code: repeating each bit three times has rate 1/3 and corrects one error per bit. A Hamming (7,4) code corrects one error per 7 bits at rate 4/7, and LDPC codes at rate 0.8 correct many errors per block at far lower overhead.
People often think error correction and error detection are the same feature. In fact detecting needs distance d − 1 and correcting needs about d/2, so a code with a given overhead detects twice as many errors as it corrects. CRC detects; ECC corrects. Systems often use both, and treating a CRC pass as proof of correct data after ECC has "corrected" it ignores miscorrection.
People often think erasure coding is the same as RAID or replication. In fact RAID 5 and 6 are special cases (one or two parity blocks), and general Reed–Solomon allows any number of parity blocks. Replication is the trivial code with k = 1; erasure coding gives the same fault tolerance at half or less of the storage, at the cost of CPU and repair traffic.
People often think Shannon's theorem tells how to build the code. In fact it proves that good codes exist, using random codes that are impossible to decode efficiently. The practical part, building codes that are close to capacity and fast to decode, took 45 years, from 1948 to the turbo codes of 1993.
tradeoffs: Choose replication when data is hot, small, read often, and you value fast repair and simple reads; each read touches one copy, and repair is a copy of one block. Choose erasure coding when data is large and mostly cold, and storage cost dominates: RS(10, 4) costs 1.4 times against 3 times for replication. You give up read latency in degraded mode (reconstruction contacts k nodes), repair bandwidth (rebuilding one block reads k blocks), and simplicity.
Choose a wide code (large k, such as RS(20, 4)) to lower storage overhead further; choose a narrow code or a locally repairable code (LRC) to lower repair cost and the number of nodes involved in each repair. A locally repairable code adds a few local parities so that a single failure is repaired from, for example, 6 blocks instead of 12, at slightly more storage. You choose between space and repair traffic.
Choose algebraic codes (Hamming, BCH, Reed–Solomon) when blocks are short, latency must be small, decoding must be simple and deterministic, or erasures are the main error, as in memory and storage. Choose LDPC or polar codes when the channel is noisy, long blocks are acceptable and you need to operate near Shannon's limit, as in wireless links and flash memory; the price is iterative decoders with higher latency and complexity, and more careful engineering of the error floor.
Choose a CRC alone when you only need to detect corruption and can retransmit (TCP/IP and Ethernet frames, file formats); choose forward error correction when retransmission is slow or impossible (deep space, broadcast, storage at rest). Choose hard-decision decoding when the receiver sees only bits; choose soft-decision decoding when it also sees how confident each bit is (SSD read voltages), which gains 1 to 2 dB or a large reduction in errors at the cost of more data reads.
friction: Redundancy costs space, bandwidth and energy, and the best codes cost compute. Decoders for LDPC and turbo codes run many iterations and need dedicated hardware in phones and SSD controllers. The code must match the error pattern: a code designed for independent random bit flips fails on bursts unless interleaving spreads them out, and a code for erasures does not help with silent corruption unless it is combined with checksums to turn errors into erasures.
Theory is asymptotic. Capacity-approaching performance needs very long blocks, but long blocks mean delay (bad for voice and control channels) and large decoders. Short-block codes, which 5G control channels and IoT need, are still an active research area. Error floors, where performance stops improving as the signal improves, appear in LDPC codes because of rare structures in the graph, and are hard to find by simulation.
In storage, correlated failures break the assumption of independent errors: a rack, a power domain, or a bad firmware version fails many blocks together, so placement across failure domains matters as much as the code. Silent data corruption in CPUs and memory, which produces wrong values without any error flag, is not stopped by storage ECC and has been reported at large scale by cloud operators. Finally, decoding errors (miscorrection beyond the correction radius) can look like valid data, which is why systems layer a CRC or hash above ECC.
practice: Match the code to the failure model. For bit flips in memory, use SECDED ECC, and turn on scrubbing, which reads memory periodically to correct errors before they accumulate into uncorrectable pairs. For disks and objects, use checksums on every block to detect, and erasure coding or replication across failure domains to repair. For networks, use a CRC for detection plus retransmission, and forward error correction only where latency or one-way links forbid retransmission.
For erasure coding, decide k and the number of parities from the target durability and the failure domains (a rack-aware layout with at least n domains), measure repair time (it sets the window in which a second failure can occur), and benchmark the encoding library: modern implementations such as Intel ISA-L use SIMD finite-field multiplication and reach several GB per second per core. Keep small objects replicated or packed together, because splitting a 1 MB object into 10 blocks makes the metadata and seek cost dominate.
To study, work the Hamming (7,4) example with a parity-check matrix in Python, then implement Reed–Solomon over GF(256) using log and antilog tables, and compare with a library such as reedsolo. Then read MacKay for the probabilistic view and the HDFS erasure coding documentation for the engineering side.

In Hamming (7,4), why does the pattern of failed parity checks give the position of the flipped bit? || Each position from 1 to 7 is covered by a different non-empty subset of the three checks, namely those matching the 1-bits of its binary number. A single flip makes exactly the checks covering that position fail, so the failed pattern read as a binary number is the position.
Why can a Reed–Solomon code with k data symbols and n total symbols rebuild the data from any k symbols? || The data are the coefficients of a polynomial of degree less than k. A polynomial of degree k − 1 is determined by its values at any k distinct points, so any k received symbols fix the polynomial by interpolation.
A system stores 100 PB of data. How much raw storage does 3-way replication need compared with RS(10, 4), and how many failures does each tolerate? || Replication needs 300 PB and tolerates 2 lost copies. RS(10, 4) needs 100 × 14/10 = 140 PB and tolerates 4 lost blocks per stripe.
When would you choose replication over erasure coding for stored data? || For small, hot, frequently read objects where read latency and fast, cheap repair matter more than storage cost. Erasure coding suits large, cold data where the 2x storage saving is worth slower degraded reads and heavier repair traffic.

value: Kolmogorov complexity measures the information in one single object, such as a file, a string or a dataset, as the length of the shortest program that prints it. A string of a million zeros has a tiny complexity, because "print 0 a million times" is a short program. A million random coin flips has a complexity of about a million bits, because no program is much shorter than the data itself. This gives a precise meaning to the words "pattern", "structure" and "randomness" without assuming a probability distribution.
The idea explains several things engineers meet in practice. It shows why random or encrypted data cannot be compressed, why a good compressor is also a good predictor, and why a simple model that fits the data well is more believable than a complicated one (a formal Occam's razor). It also sets a hard limit: complexity cannot be computed by any program. You can always find a short description, and never prove that no shorter one exists.
For the layer above, encoding and compression use description length as their measure of success, and learning theory uses it to bound generalisation: a hypothesis that is short to describe cannot have fitted noise by luck. Information theory (L4) gives the link in expectation: for data drawn from a distribution, the average Kolmogorov complexity is close to the Shannon entropy. The Church–Turing thesis (L5) provides the definition of "program", through a universal Turing machine that can run any other. Occam's razor (L5) is the philosophical principle that the formal definition makes precise. The recent idea that "language modelling is compression" is a statement in this framework.
terms: Kolmogorov complexity K(x) — the length, in bits, of the shortest program that makes a fixed universal computer print x and stop.
Universal Turing machine — a machine that reads a program and runs it, so it can simulate any other machine.
Invariance theorem — changing the universal machine changes K(x) by at most a constant that does not depend on x.
Incompressible (random) string — a string x of length n with K(x) ≥ n − c for a small constant c.
Conditional complexity K(x | y) — the length of the shortest program that prints x when it is given y as input.
Computable and uncomputable — a function is computable if some program calculates it for every input and halts; K is not.
Minimum description length (MDL) — a principle: prefer the model that minimises the length of the model plus the length of the data described with the model's help.
Normalized compression distance — a practical distance between two files based on how well they compress together, using a real compressor in place of K.
history: Three people discovered the idea independently. Ray Solomonoff, in 1960 and 1964, proposed a universal way to predict sequences by giving each program a prior weight of 2 to the power minus its length. Andrey Kolmogorov, the founder of modern probability, published his definition in 1965, as part of a program to ground information and randomness without probability. Gregory Chaitin, then a teenager, published the same notion in 1966 and 1969. The result is often called Solomonoff–Kolmogorov–Chaitin complexity.
The next step made the theory clean. Leonid Levin (1970s) and Chaitin introduced prefix-free programs, which gave complexities that behave well under addition and are tied directly to probability. Per Martin-Löf (1966) defined randomness through statistical tests, and Levin and Schnorr showed that a sequence is random in his sense exactly when its prefix complexity is close to its length. Chaitin defined the halting probability Ω, a real number whose bits are random and encode answers to unsolved problems, and showed through it that mathematics has limits like Gödel's, now stated as information.
Practical work took the idea in two directions. Jorma Rissanen (1978) turned it into the minimum description length principle for model selection. Cilibrasi and Vitányi (2005) used real compressors such as gzip in the normalised compression distance to cluster music, languages and genomes without features. The textbook by Li and Vitányi (first edition 1993) collects the theory. In 2023–2024 the connection became widely discussed again: Delétang et al. (ICLR 2024) showed that large language models are strong general-purpose compressors, when their predictions are fed to an arithmetic coder.
how: Fix a universal programming language, say a particular universal Turing machine U. Define K(x) as the length of the shortest program p such that U(p) prints x and halts. The choice of language matters only up to a constant. If V is another universal machine, there is a program (an interpreter or simulator of V, written for U) of fixed length c that translates V-programs into U-programs. Therefore K_U(x) ≤ K_V(x) + c for all x, and symmetrically. This invariance theorem is what makes K meaningful: for long strings, an additive constant of a few hundred or thousand bits is small, and the Turing machine of the Church–Turing thesis represents "any computation" so the definition does not depend on one language's accident.
Two quick facts bound K from above and below. Upper bound: K(x) ≤ |x| + c, because the program "print this literal string" works for every x. A string with a pattern gets a much shorter program: "print 0 n times" has length about log₂ n + c, so K(0ⁿ) ≈ log₂ n. Lower bound by counting: there are only 2ⁿ − 1 programs shorter than n bits, but 2ⁿ strings of length n, so at least one string of each length is incompressible. More strongly, fewer than a fraction 2^−c of the strings of length n can be compressed by c bits or more, because there are fewer than 2^(n−c) programs shorter than n − c bits to describe them. So most strings are nearly incompressible, and the strings that look like patterns are a tiny minority. This is the counting argument from combinatorics applied to programs, and it is why no compressor shrinks all inputs.
K is not computable, and the proof is a version of the Berry paradox ("the smallest number not definable in under twenty words"). Suppose a program could compute K(x) for any x. Then write a program Q that, given N, searches strings in order and prints the first one with K(x) > N. Q has length about log₂ N + c, because only N must be written down. But Q prints a string whose complexity is more than N. For large N we have log₂ N + c < N, so a program shorter than N prints a string of complexity above N, a contradiction. Hence no program computes K. The same fact is related to the halting problem: knowing K would let you decide halting, because you could search for the shortest programs and see which stop. A stronger result by Chaitin says that a formal system with a certain complexity cannot prove any statement of the form K(x) > L for L much larger than the complexity of the system itself.
Even so, K can be bounded from above by any real compressor. If gzip compresses x to m bytes, then K(x) ≤ 8m + (size of the decompressor) + c, so every compression result is an upper bound on K, and better compressors give tighter bounds. This is the usage in practice: complexity is the ideal that compressors approximate. The relation to Shannon's entropy is exact in expectation. For strings drawn independently from a distribution P, the expected K(x) is within a small additive term of the Shannon entropy of the strings, so the average case of Kolmogorov complexity recovers information theory, while K speaks about an individual string and needs no distribution. Shannon's source coding theorem says that the best average code length is the entropy; Kolmogorov says that the best code for one string is its K, and the two agree on the average.
Prediction and compression are two sides of the same coin. If a model assigns probability P(x) to a string, an arithmetic coder can write x in about −log₂ P(x) bits. So the better the predictor, the shorter the code. Solomonoff's universal prior gives each program of length ℓ a weight 2^−ℓ and predicts the next symbol by averaging over all programs consistent with the past. It is the most general possible predictor, and it is uncomputable, but its error is bounded: for any computable source, the total expected squared prediction error of the universal predictor over the whole infinite sequence is bounded by a constant proportional to K(source). Practical learners approximate this by restricting to a family of models and using MDL. In learning theory the same idea yields Occam bounds: with m training examples, a hypothesis described by L bits has a generalisation error at most about (L ln 2 + ln(1/δ)) / m (for a consistent hypothesis), so shorter descriptions generalise better.
The Delétang et al. paper turns this around. They fed the probabilities of large language models to an arithmetic coder and measured the compressed size. Chinchilla 70B, trained mostly on text, compressed ImageNet patches to 43.4% of their raw size and LibriSpeech audio to 16.4%, against 58.5% for PNG and 30.3% for FLAC. A model that predicts well compresses well, and a general model compresses data of kinds it was not trained on. A caveat belongs here: such a comparison counts only the compressed data, not the size of the model, which holds tens of billions of parameters. Under Kolmogorov's definition the model is part of the program.

example: Take two strings of 1,000 bits each. String A is "01" repeated 500 times. A short program prints it: a loop of 500 repetitions of "01", which needs only the number 500 (about 9 bits) plus the loop code, say 100 to 200 bits in total in a typical language. So K(A) is a small fraction of 1,000. String B is the outcome of 1,000 fair coin flips. By counting, at most 2^(1000−10) programs are shorter than 990 bits, out of 2^1000 strings, so the fraction of strings that can be shortened by 10 bits or more is under 2^−10, about 0.1%. B is almost certainly incompressible: K(B) ≈ 1,000 bits.
Check with a real compressor. Run gzip on one megabyte of zeros: it produces about 1 KB, because deflate's best ratio is about 1000:1. Run it on one megabyte of random bytes: the output is slightly larger than the input (by a fraction of a per cent), as there is no pattern to find. Run it on the first million digits of π written as text: you get roughly 40 to 50% of the size (digits carry log₂ 10 ≈ 3.32 bits each, stored in 8-bit characters, so the best a digit-by-digit code can do is about 41.5% of the size). Yet K of those digits is a few hundred bytes: the program that generates π. The compressor is an upper bound that is far from K, because it cannot discover the formula. This also shows the key warning: apparent randomness is not true randomness. Digits of π pass statistical tests and are still highly compressible in the Kolmogorov sense.
Now the uncomputability argument with numbers. Assume K is computable. Define Q(N): "find the first string x, in order of length, with K(x) > N, and print it". Writing Q needs a fixed program body of, say, 500 bits plus the number N in about log₂ N bits. Take N = 10,000. Then Q(10,000) has length about 500 + 14 = 514 bits and prints a string whose complexity is above 10,000. But K of that string is at most the length of Q(10,000), which is 514. A string cannot have complexity both above 10,000 and at most 514. So the assumption that K is computable is false.
intuition: A pattern is anything that lets you describe data more briefly than listing it.
Imagine telling a friend over a phone how to reproduce a picture. For a picture of stripes you can say "alternate black and white, 100 times", and the call is short. For a picture of television static you can only read out every pixel. The length of the shortest possible message is the information in the picture. What makes the definition fair is that your friend's decoder can be any computer: two different decoders differ only by the cost of explaining one to the other, which is a fixed amount, not growing with the picture.
mistakes: People often think Kolmogorov complexity can be computed, or measured with a compressor. In fact it cannot be computed by any program, and a compressor gives only an upper bound. A file that gzip cannot shrink may still have a very short description (the digits of π, the output of a random-number generator with a known seed).
People often think a random-looking string is complex in the Kolmogorov sense, so noise is "rich information". In fact noise has high complexity because it has no pattern, but it carries no useful structure. Real structure is measured by other quantities, such as sophistication and logical depth, which are low for both simple patterns and pure noise and high for things like a biological genome or a compiled program.
People often think the choice of programming language makes K meaningless. In fact the invariance theorem bounds the difference by a constant independent of x. The constant can be large for short strings (so K of a 20-byte string is not meaningful), but for long data the relative effect disappears.
People often think Kolmogorov complexity and Shannon entropy are the same thing. In fact entropy is a property of a probability distribution and averages over outcomes, while K belongs to one string. They agree on average, but a single string can have much lower K than the entropy of the distribution it came from (the digits of π).
tradeoffs: Choose Kolmogorov-style reasoning when you need a principled argument about limits: why a compressor cannot beat a bound, why random data is incompressible, why a model of a given size cannot explain an unbounded amount of data. It is a tool for proofs and intuition, not for computation. Choose Shannon entropy and a probabilistic model when you have a distribution and want numbers you can compute: expected code length, cross-entropy of a model, bits per character.
Choose practical compression (gzip, zstd, a trained model plus arithmetic coding) when you want an upper bound on the information in data. General compressors need no training and decode quickly, so use them for logs and files. Use a learned model when the data has structure a generic compressor cannot see (text, images, telemetry with a known schema), accepting that you must count the model's size and the compute for each byte (large models are millions of times slower than zstd).
Choose MDL or Bayesian model selection with a penalty on model size when you must pick among models of different complexity and have limited data. Choose cross-validation when data is plentiful and you can measure held-out performance directly, which usually works better in practice and needs no coding scheme. MDL gives theory and a way to compare models without a held-out set, but results depend on how the parameters are encoded.
Choose normalised compression distance for a quick, feature-free similarity of whole files or sequences (malware families, text languages) when you have no better representation; accept its sensitivity to compressor window sizes and its quadratic cost over many files. Choose learned embeddings when you have enough data to train them.
friction: The main limit is that K is uncomputable, and no algorithm can even give increasingly accurate lower bounds that are certified. All practical measures are upper bounds, and you cannot know how far from the truth they are. The additive constant from the choice of machine is invisible in theory but can exceed the size of small objects, so the theory says little about short strings.
The theory also does not tell you which pattern to look for. A sequence from a simple pseudo-random generator has a tiny K and passes every statistical test you try; to find the short program you must guess the generator. Search for short programs is itself hard: time-bounded versions (Levin's Kt complexity) are computable but expensive, and the minimum circuit size problem, a cousin of the question, is not known to be solvable in polynomial time.
Links to deep learning are suggestive, not exact. Compression bounds for neural networks (the size of the compressed weights plus the data given the model) can be computed and give non-vacuous generalisation bounds for some networks, but they are loose. The claim "prediction is compression" is exact for a fixed model and an arithmetic coder, but it ignores the cost of the model and the compute. Solomonoff induction is the optimal predictor and cannot be run; approximations such as AIXI-style agents are far from practical. Finally, K ignores time: a short program may take longer than the age of the universe to run, so computational depth and resource-bounded versions matter for engineering.
practice: Use the idea as a diagnostic. If a dataset compresses to a few per cent of its size, it is highly redundant, and a better schema, columnar encoding or deduplication will save storage: this is why Parquet's dictionary and run-length encodings work so well on low-cardinality columns. If a column does not compress at all, it is either random (hashes, encrypted values, UUIDs) or already compressed; do not spend CPU on compressing it again.
Use compressors as quick tests. Compress a sample with zstd at a few levels and compare with a domain-specific method to see how much structure is left. Compress two files together versus separately to estimate their shared information, as in the normalised compression distance: NCD(x, y) = (C(xy) − min(C(x), C(y))) / max(C(x), C(y)). Treat the result as an indication, since the compressor's window size limits what it can see.
In modelling, think in terms of total description length: prefer simpler models when the fit is similar, use regularisation as a price on model bits, and check generalisation on held-out data. When someone claims that a model "understands" structure because it compresses well, ask what the compressed size includes. To study, read the first chapters of Li and Vitányi, then Grünwald's tutorial on MDL, and the Delétang et al. paper for the link to language models.
