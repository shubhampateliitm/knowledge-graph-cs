@@ pytorch
value: PyTorch is a Python library for building and training neural networks. It gives you three things. First, tensors: n-dimensional arrays that live in CPU or GPU memory. Second, automatic differentiation: it computes the gradient of any calculation you write, so you never derive backpropagation by hand. Third, a large set of fast operations (matrix multiplies, convolutions, attention, reductions) that run as GPU kernels. Facebook AI Research (now Meta) started it in 2016 and released it in January 2017. Since September 2022 it is governed by the PyTorch Foundation, part of the Linux Foundation. In October 2026 the current release is 2.14 (September 2026), and new releases now arrive roughly every two months.
Its defining choice is eager execution. When Python reaches a line such as y = x @ w, the multiply runs at once and y is a real tensor that you can print, inspect in a debugger or use in an if statement. Earlier frameworks, mainly TensorFlow 1, asked you to build a graph first and run it later in a session. PyTorch made research code shorter and much easier to debug, and researchers moved to it quickly. Today most open models, including Llama and Stable Diffusion, are developed in PyTorch and released as PyTorch code and weights.
For the layer above, PyTorch is the common base: Hugging Face Transformers defines its models as PyTorch modules, vLLM runs model weights through PyTorch, and Llama and Stable Diffusion ship as PyTorch checkpoints. The layers below supply the pieces. Python makes a model just a program. CUDA supplies the GPU kernels (cuBLAS for matrix math, cuDNN for convolutions) that do the arithmetic. Deep learning supplies the method (backpropagation plus gradient descent) that PyTorch exists to express. Recommender systems, computer vision and NLP are the workloads that shaped its features: huge embedding tables, convolutions, attention. ML compilers supply torch.compile.
terms: Tensor — an n-dimensional array with a data type (such as float32 or bfloat16) and a device (CPU or one GPU).
Stride — how many elements to skip in memory to move one step along a dimension; strides let views share memory.
Eager execution — each operation runs as soon as Python reaches it and returns a real result.
Autograd — the engine that records operations during the forward pass and replays them in reverse to compute gradients.
grad_fn — the backward node attached to a tensor made by a differentiable operation; these nodes form the graph backward() walks.
Dispatcher — the C++ layer that routes each operation to the right kernel by device, data type and gradient needs.
torch.compile — the PyTorch 2 compiler entry point; it captures Python code into graphs and generates fused kernels.
Graph break — a point where the compiler cannot capture code, so that part runs as normal Python.
FSDP — Fully Sharded Data Parallel; it splits weights, gradients and optimizer state across GPUs.
history: PyTorch grew out of Torch, a numerical library written in C with a Lua front end. Ronan Collobert, Samy Bengio and Johnny Mariéthoz started Torch in 2002, and Torch7 (2011) was used at Facebook, Twitter and DeepMind. Lua was a small community, and the machine-learning world had moved to Python and NumPy. At the same time, Chainer (Preferred Networks, 2015) showed a different idea called "define-by-run": build the graph for gradients while the code runs, instead of declaring it first. Harvard's autograd package did the same for NumPy.
At Facebook AI Research, Adam Paszke (then an intern), Sam Gross, Soumith Chintala and Gregory Chanan combined these ideas: Torch's fast C and CUDA back end, a Python front end, and a define-by-run autograd. The first public release was in January 2017. Researchers adopted it fast because a model was simply a Python class and a bug could be found with print or pdb. By 2019, analyses of conference papers showed PyTorch ahead of TensorFlow in most research venues, and in January 2020 OpenAI announced it was standardizing on PyTorch.
Production needs pushed the next steps. PyTorch 1.0 (December 2018) merged Caffe2, Facebook's production framework, and added TorchScript for running models without Python. In September 2022 Meta moved the project to the new PyTorch Foundation. PyTorch 2.0 (March 2023) added torch.compile; the ASPLOS 2024 paper reports geometric-mean speedups of 2.27× for inference and 1.41× for training on an NVIDIA A100 across more than 180 models. In 2025 the foundation became an umbrella for related projects (vLLM and DeepSpeed joined in May, Ray later that year). In 2026 TorchScript's deprecation warnings became visible (2.14), with torch.export as its replacement.
how: Start with the tensor. A tensor is a small header that points to a block of memory called the storage. The header holds the sizes (for example 4 × 3), the strides (3 and 1: move 3 elements for the next row, 1 for the next column), an offset, a data type and a device. Many operations only change the header. Transposing the 4 × 3 matrix gives sizes 3 × 4 and strides 1 and 3 over the same memory, with no copy. This is why some operations need .contiguous(): a kernel that expects packed rows must first copy a strided view.
Next, follow one operation. When Python runs z = x * y, the call crosses into C++ and reaches the dispatcher, which calls a chain of handlers chosen by keys on the inputs. If an input needs gradients, the Autograd handler runs first and records what happened. Then the device handler runs the real kernel. This is where CUDA adds its value: PyTorch calls cuBLAS for matrix multiplies, cuDNN for convolutions and its own kernels for elementwise work, and launches them on a CUDA stream. Launching is asynchronous: the CPU queues the kernel and moves to the next Python line, often several kernels ahead of the GPU. Python and the dispatcher cost a few microseconds per operation. For a matrix multiply that takes milliseconds this does not matter; for thousands of tiny operations it dominates.
Autograd is the core idea taken from deep learning: training needs the gradient of a loss with respect to every parameter, and backpropagation computes it with the chain rule. PyTorch builds the graph for that during the forward pass. Each operation on a tensor that requires gradients creates a node (the output's grad_fn) and saves what its backward rule needs. A multiply z = x * y saves x and y, because \( \partial z/\partial x = y \) and \( \partial z/\partial y = x \). When you call loss.backward(), the engine starts at the loss with gradient 1, walks the nodes in reverse topological order, and at each node multiplies the incoming gradient by the local derivative (a vector-Jacobian product). Gradients that reach the same tensor by two paths are added. At the leaves (the parameters) the results accumulate in .grad. Then the graph is freed. The next iteration builds a new graph, so a model can use Python loops and if statements whose path changes from one input to the next. This is where Python adds its value: control flow is just Python.
An nn.Module is a Python class that owns parameters (leaf tensors with requires_grad=True) and defines forward(). An optimizer such as AdamW reads each .grad and updates the parameter in place, keeping two extra state tensors per parameter. Training memory therefore has four parts: weights, gradients, optimizer state, and activations saved by autograd, which grow with batch size and sequence length. Activation checkpointing keeps only some activations and recomputes the rest during backward. Asking the CUDA driver for memory is slow and can stall the GPU, so PyTorch uses a caching allocator: freed blocks return to PyTorch's own pools and are reused. This is why nvidia-smi often shows a GPU as nearly full when live tensors are much smaller. The three big workloads each left specific features: recommender systems brought EmbeddingBag and sharded embedding tables (TorchRec), computer vision brought cuDNN convolutions in the channels-last layout, and NLP brought fused attention (scaled_dot_product_attention and FlexAttention).
torch.compile is where ML compilers add their value. TorchDynamo uses a CPython hook (PEP 523) to see each Python function's bytecode before it runs. It traces the tensor operations into an FX graph and records guards: checks on shapes, data types and Python values that must hold for the graph to be reused. If a guard fails, it compiles again. If it meets code it cannot trace, such as printing a tensor's value, it inserts a graph break, runs that part as normal Python, and starts a new graph. AOTAutograd then traces the backward pass ahead of time, so both directions are optimized. TorchInductor, the default back end, fuses chains of elementwise and reduction operations into single kernels written in Triton for GPUs (C++ with OpenMP for CPUs), and can replay the whole sequence as a CUDA graph to remove launch overhead. Fusion matters because most operations other than matrix multiplies are limited by memory bandwidth: one fused kernel reads the input once instead of once per operation.
Scaling out uses torch.distributed with NCCL, NVIDIA's library for collective communication between GPUs. DistributedDataParallel (DDP) keeps a full model copy on each GPU and averages gradients with an all-reduce, in buckets of about 25 MB that start while backward is still running, so communication overlaps compute. FSDP shards parameters, gradients and optimizer state: before each layer runs, it all-gathers that layer's weights, and after backward it reduce-scatters the gradients. DTensor adds tensor parallelism. For deployment, torch.export captures a whole program into one graph with no graph breaks allowed; AOTInductor compiles it for servers, and ExecuTorch runs it on phones.

example: Start with a tiny model you can check with a pen: one weight and one bias. Let x = 2.0, w = 3.0, b = 1.0 and target t = 10.0. Forward: y = w × x + b = 7.0, and the loss is \( (y - t)^2 \) = (−3)² = 9.0. Autograd recorded three nodes: a multiply, an add and a squared difference. Backward starts at the loss with gradient 1. The squared-difference node gives \( \partial L/\partial y = 2 \times (y - t) \) = −6. The add node passes −6 unchanged to both inputs, so b.grad = −6. The multiply node multiplies by the other input: w.grad = −6 × x = −12. Note that it needed x, which is why autograd saved it. With plain gradient descent and learning rate 0.01: w becomes 3 − 0.01 × (−12) = 3.12, and b becomes 1 − 0.01 × (−6) = 1.06. The new prediction is 3.12 × 2 + 1.06 = 7.30, and the loss falls from 9.0 to (7.30 − 10)² = 7.29. In PyTorch this is six lines, and the gradients printed by w.grad and b.grad are exactly −12 and −6.
Now a memory budget. You want to fine-tune a 7-billion-parameter model with AdamW in mixed precision. A common layout costs about 16 bytes per parameter: 2 bytes of bf16 weights, 2 bytes of bf16 gradients, 4 bytes of fp32 master weights, and 8 bytes for AdamW's two fp32 state tensors. That is 7 × 10⁹ × 16 = 112 GB before any activations, which does not fit on one 80 GB H100, so DDP fails. FSDP across 8 GPUs gives each one about 112 / 8 = 14 GB of state, plus one gathered layer at a time and the activations. The cost is communication: weights are all-gathered for forward and again for backward, and gradients are reduce-scattered, roughly 1.5 times the traffic of DDP.
Finally, why fusion helps. Take a tensor of 100 million fp32 values (400 MB) and apply three elementwise operations: add a bias, apply GELU, multiply by a scale. Eager mode runs three kernels; each reads 400 MB and writes 400 MB, so 2.4 GB moves through memory. On an H100 with about 3.3 TB/s of bandwidth, that is about 0.73 ms. Inductor fuses them into one kernel that reads and writes 400 MB once: 0.8 GB, about 0.24 ms, three times faster. The matrix multiplies in the same model would not speed up this way, because cuBLAS is already near peak; this is why whole-model gains are usually well below 3×.
intuition: PyTorch is a calculator that keeps a receipt of every step, so it can later read the receipt backwards and tell you how much each input affected the total.
The design feels natural because it follows how people already write math code. You write the forward computation as a normal program, and the program's actual run is the graph: no second language, no separate build step. Backpropagation only needs to know which operations happened, in which order, on which values, and the tape records exactly that. Speed comes from the fact that almost all the time is spent inside a few big kernels written by GPU experts, so the thin Python layer on top costs little. When it does cost too much, torch.compile removes it without changing how models are written.
mistakes: People often think PyTorch is slow because Python is slow. In fact the heavy arithmetic runs in C++ and CUDA kernels, and Python only issues calls. Python overhead matters only when a model runs many tiny operations, and torch.compile and CUDA graphs remove most of it.
People often time GPU code with time.time() around a line and get very small numbers. In fact kernel launches are asynchronous, so the line returns before the GPU finishes. Call torch.cuda.synchronize() before reading the clock, or use CUDA events or the PyTorch profiler.
People often think model.eval() turns off gradient tracking. In fact it only switches layers such as dropout and batch normalization to inference behaviour. To stop autograd from recording and saving activations, wrap inference in torch.inference_mode() or torch.no_grad().
People often think torch.compile always makes code faster. In fact graph breaks split the model into small graphs, changing shapes can trigger repeated recompilation, and the first call can take tens of seconds or minutes. Models dominated by large matrix multiplies gain little. Check with torch._dynamo.explain or TORCH_LOGS before relying on it.
friction: GPU memory is the most common pain. Out-of-memory errors come from activations that grow with batch size and sequence length, from fragmentation in the caching allocator, and from tensors kept alive by mistake (for example, adding a loss tensor to a Python list keeps its whole graph). Diagnosing them needs memory snapshots and some knowledge of the allocator.
The compiler stack is complex. Graph breaks, guard failures and dynamic shapes cause silent slowdowns or recompilation storms, and a bug can sit in any of Dynamo, AOTAutograd or Inductor. Error messages from generated Triton code are hard to read. torch.compile on the newest Python version often arrives later than the wheels: in 2.14, Python 3.15 wheels exist but torch.compile raises an error on 3.15.
Distributed training at scale needs careful configuration. Choosing between DDP, FSDP, tensor parallel and pipeline parallel, setting bucket sizes, and recovering when one GPU among thousands fails are hard problems; NCCL hangs are notoriously difficult to debug. The 2.14 work on fault-tolerant process groups addresses this, but it is new.
Deployment without Python has been a moving target: TorchScript is deprecated, and torch.export plus AOTInductor and ExecuTorch are the replacements, still maturing for models with data-dependent control flow. Packaging is also heavy: wheels are built per CUDA version, and matching PyTorch, CUDA, drivers and libraries such as torchvision causes real friction. Finally, many GPU kernels are not deterministic by default, so two runs can differ slightly.
practice: Get the model correct in eager mode first, then add torch.compile around the model or the training step and measure. Use bf16 autocast on modern GPUs, and torch.nn.functional.scaled_dot_product_attention rather than hand-written attention, so PyTorch can pick a FlashAttention-style kernel. Wrap inference in torch.inference_mode().
Keep the GPU fed. Use DataLoader with several workers and pin_memory=True, avoid .item(), .cpu() and printing tensors inside the training loop (each one forces a synchronization), and check GPU utilization with the PyTorch profiler, not with nvidia-smi alone. For memory problems, record a memory snapshot (torch.cuda.memory._record_memory_history) and look at what holds memory at the peak. Try the allocator setting expandable_segments:True when fragmentation is the cause.
For scale, start with DDP when the model, gradients and optimizer state fit on one GPU, and move to FSDP (the fully_shard API) when they do not. Add tensor parallelism only for very large models on fast interconnects. Save checkpoints with torch.distributed.checkpoint so they can be loaded on a different number of GPUs. For serving LLMs, do not run model.generate in a loop; use an engine such as vLLM, which runs on PyTorch but manages batching and the KV cache. Pin exact versions of torch and CUDA in your environment, and read the release notes for deprecations before upgrading, because releases now come about every two months.
quiz: What does a PyTorch tensor store besides the numbers? || A header with sizes, strides, an offset, a data type and a device. Strides let views such as transposes share memory without copying.
Why can a PyTorch model use Python if statements and loops that change from input to input? || Autograd builds the backward graph during each forward run, recording only what actually happened. The graph is rebuilt every iteration, so it always matches the path the code took.
Why does torch.compile speed up a chain of elementwise operations more than a large matrix multiply? || Elementwise operations are limited by memory bandwidth, so fusing them cuts memory traffic. A large matrix multiply already runs near peak compute in cuBLAS.
A 13-billion-parameter model is trained with AdamW in mixed precision at about 16 bytes per parameter. How much state per GPU with FSDP on 8 GPUs? || 13 × 10⁹ × 16 = 208 GB in total, so about 26 GB per GPU, plus activations and one gathered layer at a time.
When would you choose FSDP over DDP, and what do you pay? || FSDP when weights, gradients and optimizer state do not fit on one GPU. You pay extra communication (all-gathers of weights plus reduce-scatters of gradients) and more configuration; when the model fits, DDP is simpler and usually faster.

@@ tensorflow
value: TensorFlow is Google's open-source framework for machine learning, released in November 2015. Its central idea is the dataflow graph: a computation is described as a graph of operations (nodes) connected by tensors (edges), and a runtime places that graph on CPUs, GPUs or TPUs, optimizes it, and runs it. Because the whole computation is known as data, TensorFlow can split it across many machines, compile it with XLA, save it to a file, and run that file later on a server, a phone or in a browser, without the Python code that created it.
That last property made TensorFlow the first deep-learning framework built for production at Google scale. Around the core grew a full toolkit: Keras for defining and training models, tf.data for input pipelines, TensorFlow Serving for model servers, TFX for production pipelines, TensorFlow Lite (renamed LiteRT in 2024) for phones and embedded devices, and TensorFlow.js for the browser. Search ranking, ads, recommendations and translation at Google ran on it, as did many systems outside Google. In research, PyTorch and JAX have largely replaced it since about 2020, and Google's own frontier models are trained with JAX. TensorFlow is still maintained, but releases have slowed: 2.19 (March 2025), 2.20 (August 2025) and 2.21 (March 2026), the current version in October 2026.
For the layer above, TensorFlow's graph is the deployable artifact. The layers below explain its design. Deep learning (L1) supplies the models and backpropagation; TensorFlow computes gradients by adding gradient operations to the graph. CUDA supplies the GPU kernels (cuDNN for convolutions, cuBLAS for matrix multiplies). ML compilers (L2), in the form of XLA, turn graphs into fused machine code and are the only way to run on TPUs. Recommender systems, computer vision and NLP shaped its features: parameter servers and embedding APIs for huge sparse models, LiteRT for vision on phones, and the first BERT release in 2018.
terms: Dataflow graph — a graph whose nodes are operations and whose edges carry tensors; a node can run as soon as its inputs are ready.
Op and kernel — an op is an abstract operation such as MatMul; a kernel is its implementation for one device type (CPU, GPU, TPU).
Session — the TF1 object that executed a graph; you asked it to compute certain outputs and fed it input values.
tf.function — the TF2 decorator that traces a Python function into a graph and runs the graph on later calls.
Tracing — running the Python function once with symbolic tensors to record which ops it creates.
AutoGraph — the converter that rewrites Python if, for and while statements on tensors into graph control-flow ops.
Grappler — TensorFlow's default graph optimizer (constant folding, pruning, layout changes, fusion).
XLA — Accelerated Linear Algebra, a compiler that turns graphs into fused kernels for CPUs, GPUs and TPUs.
SavedModel — the on-disk format holding graphs (as signatures) plus variable values, loadable without Python.
history: TensorFlow replaced DistBelief, Google Brain's first system, described by Jeff Dean and colleagues in "Large Scale Distributed Deep Networks" (NIPS 2012). DistBelief trained huge networks over thousands of CPU cores with parameter servers, but its layers were fixed C++ classes, so researchers could not easily try new ideas. TensorFlow, released on 9 November 2015 under the Apache 2.0 licence, generalized it: any computation built from ops, with state held in variables, running on any device. The OSDI 2016 paper by Martín Abadi and colleagues described the design. In May 2016 Google revealed the TPU, its own accelerator, which TensorFlow targeted from the start.
TensorFlow 1.0 arrived in February 2017 with an experimental XLA compiler. TensorFlow Serving (2016), TFX (KDD 2017 paper), TensorFlow Lite (2017) and TensorFlow.js (2018) covered production, mobile and web. In 2018 Google released BERT in TensorFlow, and for a few years TF was the default for both industry and research.
The problem was usability. TF1 code built a graph with placeholders and then executed it with session.run, so a Python print showed a symbolic tensor rather than a value, and errors appeared far from the line that caused them. PyTorch's eager style attracted researchers quickly. Google answered with eager execution (preview in late 2017) and TensorFlow 2.0 (30 September 2019): eager by default, tf.function to get graphs back, and Keras as the main API. The migration was large and split the community, and research moved mostly to PyTorch.
Later changes moved pieces out. XLA became part of the multi-company OpenXLA project (2022–2023). Keras 3 (November 2023) became multi-backend, running on TensorFlow, JAX or PyTorch, and became the default tf.keras in TF 2.16 (2024). TensorFlow Lite was renamed LiteRT in September 2024; TF 2.20 (2025) started deprecating tf.lite in favour of the separate LiteRT repository. TF 2.21 (March 2026) dropped Python 3.9.
how: Everything starts with the graph. An op such as MatMul or Conv2D has typed inputs and outputs and one or more kernels, one per device type. A tf.Variable holds state (weights) that survives between executions, and ops such as AssignAdd change it. Because the graph is data, the runtime can see the whole computation before running any of it. That is the source of every TensorFlow advantage: it can decide where each op runs, remove unused parts, merge ops, and save the result.
In TensorFlow 1 you built this graph explicitly. A placeholder stood for input data, and session.run(fetches, feed_dict) computed only the part of the graph needed for the requested outputs. In TensorFlow 2 code runs eagerly by default, and tf.function brings the graph back. The first time you call a decorated function, TensorFlow traces it: it runs the Python body with symbolic tensors that have only a shape and a data type, and records every op created into a FuncGraph. AutoGraph rewrites Python control flow that depends on tensor values into graph ops: an if becomes tf.cond, a while becomes tf.while_loop. The traced graph is cached under a key made of the argument types and shapes and the values of any plain Python arguments. Later calls with a matching key skip Python entirely and run the cached graph. A new key triggers a new trace. Python side effects, such as print or appending to a list, happen only while tracing, not on each call.
Gradients follow the same split. In eager code, tf.GradientTape records operations as they run, like PyTorch's tape, and tape.gradient walks them in reverse. Inside a graph, TensorFlow adds gradient ops to the graph itself, using a registered gradient function for each op type; the backward pass becomes more graph that can be optimized like the forward pass. This is backpropagation from deep learning expressed as graph rewriting.
Before running, the graph is optimized and placed. Grappler applies passes such as constant folding (computing parts that do not depend on inputs), pruning of unused nodes, common subexpression elimination, layout changes (for example NHWC to NCHW, which cuDNN prefers on GPUs), and remapping of patterns such as Conv2D followed by BiasAdd and ReLU into one fused op. The placer assigns each op to a device. When an edge crosses devices or machines, the graph is cut and a Send/Recv pair is inserted, so one graph can span many GPUs and hosts. The executor then runs ops as soon as their inputs are ready, using thread pools, so independent branches run in parallel. On NVIDIA GPUs, kernels come from CUDA libraries: cuDNN for convolutions and cuBLAS for matrix multiplies, launched on CUDA streams.
XLA is the compiler path. With jit_compile=True on a tf.function, or always on TPUs, TensorFlow lowers the graph to XLA's HLO, a small set of about a hundred primitive operations with static shapes. XLA then fuses chains of elementwise ops and reductions into single kernels, assigns memory layouts, reuses buffers, and generates machine code (through LLVM for CPUs and NVIDIA GPUs, and a dedicated back end for TPUs). Static shapes are the price: each new input shape means a new compilation, so variable-length inputs are usually padded to a few fixed sizes. XLA is the main thing JAX and TensorFlow share.
Around the core sit data and distribution. tf.data builds input pipelines from stages such as read, map (decode, augment), shuffle, batch and prefetch; stages run in parallel on CPU threads, and AUTOTUNE picks the parallelism. tf.distribute strategies spread training: MirroredStrategy copies the model to every GPU on one machine and all-reduces gradients; MultiWorkerMirroredStrategy does the same across machines; TPUStrategy targets TPU pods; ParameterServerStrategy keeps variables on parameter-server tasks, the DistBelief design that suits recommender models with embedding tables too big for one worker.
Deployment is where the graph pays off. tf.saved_model.save writes the traced graphs (as named signatures such as serving_default) and the variable values. TensorFlow Serving, a C++ server, loads SavedModels from a versioned directory, swaps in new versions without downtime, and batches incoming requests on the server so the GPU sees larger batches. The LiteRT converter turns a model into a compact FlatBuffer file, usually with 8-bit quantization, and runs it on phones through delegates for mobile GPUs and NPUs; computer-vision models such as MobileNet were its first main use. For NLP, the same SavedModel path served BERT-style encoders, with text preprocessing ops inside the graph. Keras sits above all of this: you define layers and call model.fit, and Keras builds the tf.function training step for you.

example: First, tracing. You write a tf.function f(x, scale) and call it four times. Call 1: x is a float32 tensor of shape [32, 10], scale is the Python number 2.0. There is no cached graph, so TensorFlow traces: trace count 1. Call 2: same shape and dtype, scale = 2.0 again. The key matches, so it runs the cached graph with no Python: still 1 trace. Call 3: x has shape [16, 10]. The shape differs, so it traces again: 2 traces. Call 4: shape [32, 10] but scale = 3.0. Plain Python values are part of the key, so it traces a third time. In a training loop that passes the step number as a Python int, this means one trace per step, each taking tens to hundreds of milliseconds, and the "fast graph" becomes slower than eager code. The fix is to pass scale as a tensor (tf.constant(3.0)) and give an input_signature with shape [None, 10], so one graph serves every batch size.
Second, an input pipeline. A GPU training step takes 50 ms per batch of 256 images. Decoding and augmenting 256 JPEG images takes 200 ms on one CPU core. Without parallelism the GPU waits 200 ms per step, so it is busy only 50 / (200 + 50) = 20% of the time. With dataset.map(decode, num_parallel_calls=8), preprocessing takes about 200 / 8 = 25 ms per batch. With .prefetch(2), the next batch is prepared while the GPU trains on the current one, so each step costs max(50, 25) = 50 ms and the GPU is busy almost 100% of the time: five times faster training without touching the model.
Third, serving. A ranking model in TensorFlow Serving takes 4 ms of GPU time for a batch of 1 and 10 ms for a batch of 32, because the GPU has spare parallel capacity. Serving one request at a time gives at most 1,000 / 4 = 250 requests per second. With server-side batching (max_batch_size = 32, batch_timeout_micros = 2,000), a full batch of 32 every 10 ms gives up to 32 × 100 = 3,200 requests per second, almost 13 times more. The cost is latency: a request may wait up to 2 ms for its batch to fill, then 10 ms to compute, so about 12 ms instead of 4 ms. Choosing the timeout is choosing a point on that latency and throughput curve.
intuition: TensorFlow is a factory blueprint: you design the whole production line on paper first, and because the blueprint exists, it can be optimized, split across buildings, and rebuilt in another city.
This is natural for a company that runs models in production at huge scale. If you only experiment, eager code is easiest, because you see each value immediately. But if you train across thousands of machines and then serve billions of predictions on servers, phones and browsers, you want one description of the computation that is independent of the Python process that wrote it. A graph is that description. Placement, partitioning, fusion and serialization all become graph rewrites, which is why the same SavedModel can run in TF Serving, LiteRT or the browser. TensorFlow 2 keeps this property but hides it: you write eager code for clarity and add tf.function where you want the blueprint.
mistakes: People often think TensorFlow 2 removed graphs. In fact tf.function, Keras model.fit and SavedModel all build and use graphs; TF2 only made eager mode the default for writing and debugging. Most production performance still comes from graphs.
People often expect Python code inside a tf.function to run on every call. In fact Python runs only while tracing. A print statement prints once, a Python counter increments once per trace, and random numbers from Python's random module are frozen into the graph. Use tf.print, tf.Variable and tf.random inside graphs.
People often think XLA is always on. In fact on CPUs and GPUs it is opt-in (jit_compile=True or auto-clustering settings); only TPU programs always go through XLA. Turning it on can speed up models with many small ops, but it can also slow them down when shapes keep changing and force recompilation.
People often treat Keras and TensorFlow as the same thing. In fact Keras 3 is a separate, multi-backend library that also runs on JAX and PyTorch. Since TF 2.16, tf.keras means Keras 3, and old Keras 2 code needs the tf_keras package, which surprises teams during upgrades.
friction: The TF1 to TF2 transition left a long tail: old tutorials, tf.compat.v1 code, removed tf.contrib modules and estimators that still exist in production systems. Keras 3 created a second migration for code that depended on Keras 2 internals.
Graph mode is harder to debug than eager code. Errors refer to graph nodes and symbolic shapes such as (None, 128), not to your variables, and retracing problems are silent: the code is correct, only slow. Static shapes for XLA and TPUs force padding and bucketing for variable-length data.
Installation and hardware support are a constant cost. Each TensorFlow release is built for specific CUDA and cuDNN versions, native Windows GPU support ended after TF 2.10 (2022), so Windows users need WSL2, and the TF Addons project ended development in 2024.
The biggest friction is momentum. New model architectures, research code and libraries arrive first, or only, in PyTorch. Hugging Face Transformers dropped TensorFlow in version 5 (January 2026), mobile deployment is moving to the separate LiteRT project, and the slower release cadence (one release in the year to October 2026) signals reduced investment. Teams choosing TensorFlow today are mostly choosing it for existing systems, TF Serving and TFX pipelines, or TPU workflows that predate JAX.
practice: If you maintain TensorFlow systems, keep them healthy rather than rewriting them in a hurry. Put the training step and the serving function under tf.function with an explicit input_signature (use None for the batch dimension), and watch for retracing warnings in the logs. Build input pipelines with tf.data using num_parallel_calls=tf.data.AUTOTUNE, cache after expensive steps that do not change, and end with prefetch. Profile with the TensorBoard profiler (installed separately since TF 2.21) to see whether time goes to input, host or device.
For serving, export SavedModels with clear signatures, test them by loading in a fresh process, and tune TF Serving's batching parameters against your latency target. For phones, use the LiteRT converter with post-training int8 quantization and check accuracy on a validation set after conversion. Try jit_compile=True on the training step and keep it only if it helps.
For new projects, the realistic choices in 2026 are PyTorch for most work, JAX for TPU-heavy or very large-scale training, and Keras 3 if you want a TensorFlow-like high-level API that can switch backends. If you plan a migration, move the model definition to Keras 3 first, because that lets you change backends with little code change. Pin TensorFlow, CUDA and Python versions together, because each TF release supports only specific combinations.

@@ jax
value: JAX is a Python library from Google that looks like NumPy but adds composable function transformations. You write an ordinary function on arrays, and JAX gives you new functions from it: jax.grad returns its gradient, jax.jit compiles it with XLA, jax.vmap makes it work on a whole batch, and sharding annotations spread it across many GPUs or TPUs. Transformations nest freely, so jit(vmap(grad(f))) is a compiled function that computes per-example gradients for a batch. JAX was first released in December 2018. In October 2026 the current version is 0.12 (released 19 October 2026); it is still below 1.0 and ships a new minor version about every three months.
JAX exists because research at very large scale needs two things that pull against each other: the freedom to write any new idea as plain code, and whole-program compilation so that thousands of accelerators run that idea efficiently. JAX resolves this by requiring functions to be pure (no hidden state, no side effects). A pure function can be traced into a small, exact intermediate form, and that form can be differentiated, batched, compiled and partitioned by mechanical rules. Google DeepMind trains Gemini with JAX on TPUs, AlphaFold 2 and 3 are implemented in JAX, and many groups outside Google use it for large language models and scientific computing.
The layers below supply the pieces. Python supplies the language in which the user writes functions, and its dynamic objects make tracing possible: JAX passes special tracer objects through normal Python code and records what happens to them. Deep learning (L1) supplies the main workload and the reason gradients matter: training is gradient descent on a loss, and grad delivers that gradient. ML compilers (L2), in the form of XLA, supply the back end that fuses operations, plans memory and generates code for CPUs, GPUs and TPUs. For the layer above, AlphaFold and similar systems get a compact, compiled, multi-device program from short scientific code.
terms: Pure function — a function whose output depends only on its inputs and which changes nothing outside itself.
Tracer — a stand-in object that JAX passes through your function to record operations instead of computing values.
Abstract value — what a tracer knows about an array: its shape and data type, not its numbers.
jaxpr — JAX's intermediate representation: a short, typed list of primitive operations recorded by tracing.
Primitive — one of JAX's fixed set of basic operations (add, dot_general, exp, reduce_sum); every transformation has a rule for each.
Transformation — an interpreter that reads a jaxpr and produces a new function: grad, jit, vmap, and others.
PRNG key — an explicit array that holds random-number state; you split keys instead of using a hidden global seed.
Pytree — a nested structure of lists, tuples and dicts whose leaves are arrays; transformations accept and return pytrees.
Sharding — a description of how an array is split across a mesh of devices, for example by rows over 8 GPUs.
history: JAX grew from Autograd, a Harvard library by Dougal Maclaurin, David Duvenaud, Matthew Johnson and Ryan Adams (around 2014–2015) that differentiated ordinary NumPy code by tracing it. Autograd was elegant but slow: it ran on the CPU, one NumPy call at a time. At Google, Johnson and Maclaurin joined Roy Frostig, Chris Leary, Peter Hawkins, James Bradbury and others to connect the same tracing idea to XLA, the compiler Google had built for TensorFlow and TPUs. The SysML 2018 paper "Compiling machine learning programs via high-level tracing" (Frostig, Johnson and Leary) described the design, and the code was open-sourced in December 2018.
Adoption grew fastest where TPUs and scale mattered. DeepMind moved much of its research to JAX around 2020 and built libraries on it (Haiku for networks, Optax for optimizers). AlphaFold 2 (2021) was published as JAX code. Google Brain built Flax, and later large models such as PaLM were trained with JAX on the Pathways system. Gemini (from December 2023) continued this, and AlphaFold 3 (2024) is also JAX.
The API kept evolving because sharding was hard. Early JAX had pmap, which ran one copy of a function per device. jax.Array (version 0.4.1, December 2022) unified all arrays, single-device or sharded, into one type, so jit could partition computations automatically from sharding annotations. shard_map added explicit per-device code for cases where automatic partitioning is not good enough. In 2025 JAX added an explicit-sharding mode, where shardings are part of an array's type, and moved its partitioner to Shardy, built with the OpenXLA community. Pallas (2023 onward) added a way to write custom GPU and TPU kernels from JAX. The neural-network library Flax added a new, more object-oriented API called NNX (2024), which its documentation now recommends for new users.
how: Everything starts with tracing. When you call jit(f)(x), JAX does not run f on x's numbers. It replaces x with a tracer that carries an abstract value, for example "float32 array of shape [32, 512]", and runs the Python code of f. Each jax.numpy call on a tracer does not compute anything; it appends a primitive operation to a list and returns a new tracer with the output's shape and type. Python's dynamic typing is what makes this work: f cannot tell a tracer from an array. When f returns, JAX has a jaxpr: a small, typed program of primitives with no Python in it. Python control flow runs during tracing, so a Python for loop over a fixed range is unrolled into the jaxpr, and an if on a Python value picks one branch. An if on a traced value cannot work, because its value is unknown; you use lax.cond or lax.while_loop, which become primitives themselves.
Each transformation is an interpreter over jaxprs, and each primitive carries one rule per transformation. This is why they compose: grad of a jaxpr is another jaxpr, which vmap can transform again, and jit can compile the result. The design is small: one fixed set of primitives, each with a few rules, covers all of jax.numpy, jax.lax and jax.scipy.
grad is where deep learning's need is met. JAX first builds the forward-mode derivative (JVP, Jacobian-vector product) using each primitive's JVP rule: for \( y = \sin(x) \), the tangent is \( \cos(x) \) times the input tangent. It then linearizes, keeping only the linear part, and transposes that linear program to run backwards. The transposed program is the vector-Jacobian product, which is reverse-mode differentiation (backpropagation). Each linear primitive has a transpose rule; for example, the transpose of "multiply by matrix W" is "multiply by \( W^\top \)". So JAX derives reverse mode from forward mode plus transposition, instead of writing two separate systems. You can also mix them: jax.hessian is forward-over-reverse, and jacfwd and jacrev give full Jacobians.
vmap uses batching rules. It adds a batch dimension to every array and asks each primitive how to handle it. A dot of two vectors with a batch axis on one side becomes a matrix-vector product; an elementwise add just broadcasts. The result is one batched program with a few large operations, not a Python loop over examples. This is how per-example gradients, ensembles of models, and Monte Carlo samples are written as single-example code.
jit is where ML compilers add their value. JAX lowers the jaxpr to StableHLO, an operation set shared with XLA, and XLA compiles it: fusing chains of elementwise ops and reductions into single kernels, choosing memory layouts, reusing buffers, and generating machine code for the device. Compiled code is cached by the input shapes, data types and any static arguments; a new shape compiles again, so shapes should be few and fixed. Execution is asynchronous: a jitted call returns a future-like array at once, and Python continues while the device works, until something needs the actual values.
Sharding scales the same program to many devices. You create a Mesh, a named grid of devices such as 8 GPUs named "data", and attach a NamedSharding with a PartitionSpec to arrays, for example P("data", None): split rows across the "data" axis and keep columns whole. jit reads these annotations, propagates shardings to every intermediate value, and inserts the needed collective operations (all-reduce, all-gather, reduce-scatter) between devices. This is the GSPMD approach: you write the program for one big logical device and the compiler partitions it. When you need exact control, shard_map lets you write the per-device program and its collectives yourself. Multi-host training runs the same Python program on every host, each driving its local devices.
Purity explains the remaining rules. Randomness is explicit: key = jax.random.key(0), and key1, key2 = jax.random.split(key) gives independent streams, so the same key always gives the same numbers on any device. Arrays are immutable; x.at[i].set(v) returns a new array, and XLA usually turns it into an in-place update. Model parameters are pytrees passed into functions and returned from them, rather than attributes changed in place. Libraries hide some of this: Flax (NNX) gives modules that look like PyTorch's, Optax gives optimizers as pure update functions, and Orbax saves checkpoints.

example: Take the loss from the diagram: \( f(w) = (w \cdot x - y)^2 \). Let w = [1, 1], x = [1, 2] and y = 5. Forward: w · x = 1 + 2 = 3, residual r = 3 − 5 = −2, loss = 4. The gradient with respect to w is \( 2 \times r \times x \) = 2 × (−2) × [1, 2] = [−4, −8]. jax.grad(f)(w, x, y) returns exactly this. Inside, JAX traced three primitives (dot, subtract, square). The JVP rule of square gives 2r, the subtract passes it through, and the transpose of the dot "w · x" with respect to w is "multiply by x", which produces the vector.
Now three training examples: (x = [1, 2], y = 5), (x = [0, 1], y = 0) and (x = [1, 0], y = 1). For the second: w · x = 1, r = 1, gradient 2 × 1 × [0, 1] = [0, 2]. For the third: w · x = 1, r = 0, gradient [0, 0]. jax.vmap(jax.grad(f), in_axes=(None, 0, 0)) maps over x and y but not w, and returns the 3 × 2 array [[−4, −8], [0, 2], [0, 0]] in one call. The batching rule turned three vector dot products into one matrix-vector product. Per-example gradients like these are what differentially private training needs: each row is clipped to a maximum length before averaging. Averaging without clipping gives [−4/3, −2].
Now scale it. A batch of 1,024 examples is placed on 8 devices with sharding P("data"), so each device holds 1,024 / 8 = 128 rows, and the model's 1 billion bf16 parameters (2 GB) are replicated on every device. jit compiles one program: each device computes gradients for its 128 rows, then XLA inserts an all-reduce to sum them. A ring all-reduce sends about 2 × (N − 1) / N times the data per device: 2 × 7/8 × 2 GB = 3.5 GB. At an assumed 100 GB/s of device-to-device bandwidth, that is 35 ms per step, which XLA tries to overlap with the backward computation. If memory is tight, change one annotation and shard the parameters too (P("data") on the weights, the FSDP pattern). XLA then all-gathers each weight before use and reduce-scatters gradients, and each device stores only 2 GB / 8 = 250 MB of weights. The model code itself does not change.
intuition: JAX is a set of lenses for functions: write a function once, then look at it through grad, vmap or jit and get a new function each time.
This works because a pure function is just a mathematical object, and math already has these operations. Differentiation, mapping over a batch, and compiling are all ways of producing a new function from an old one. If a function hides state or side effects, these transformations cannot be defined cleanly, because the result depends on things outside the inputs. By requiring purity, JAX can trace a function into a small exact program and apply mechanical rules, one per primitive, to produce new programs. Composition comes for free: each transformation takes a jaxpr and gives a jaxpr. The same idea makes sharding natural. Because the whole program is known before it runs, the compiler can decide where every piece of every array lives and which messages to send, instead of the user writing that by hand.
mistakes: People often think jit runs the Python function on every call. In fact Python runs only while tracing, once per new shape, type or static argument. A print inside a jitted function prints tracers, once; use jax.debug.print to see runtime values.
People often think JAX is mainly a neural-network library like PyTorch. In fact JAX itself has no layers, optimizers or data loaders. It is a numerical library with transformations; Flax, Optax, Orbax and Grain (or Equinox) provide the neural-network pieces, and choosing them is part of using JAX.
People often reuse the same random key twice and expect different numbers. In fact the same key always gives the same numbers, by design. Split the key for every new use, and pass keys into functions explicitly.
People often expect jit to speed up any code. In fact the first call pays compilation time (seconds, sometimes minutes for large models), every new input shape compiles again, and Python control flow on traced values fails. Jit pays off for functions called many times with stable shapes, which is the normal case for a training step.
friction: The functional style has real costs. Changing a model means threading parameters, optimizer state and random keys through every function, and code that relies on in-place mutation must be rewritten. Errors such as ConcretizationTypeError, raised when Python needs a traced value, confuse newcomers, and debugging compiled code needs special tools (jax.debug, disabling jit).
Static shapes are another cost. Variable-length inputs (text, graphs, ragged batches) need padding and bucketing, or each new length triggers a compilation. Compile time for large models can be minutes, and the compilation cache must be managed to avoid paying it on every restart.
The ecosystem is smaller and more fragmented than PyTorch's. There are several neural-network libraries (Flax Linen, Flax NNX, Haiku in maintenance mode, Equinox), most new open models are released first in PyTorch, and Hugging Face Transformers dropped its Flax models in version 5 (January 2026). GPU support is good, but TPUs remain JAX's strongest platform, and GPU performance for new attention variants often depends on custom kernels written in Pallas or on cuDNN integrations.
API change is frequent. JAX is still at 0.x with releases about every three months, sharding APIs moved several times (pmap, pjit, jax.Array, shard_map, explicit sharding), and deprecated functions are removed on a schedule, so upgrading large codebases takes planned effort.
practice: Write the training step as one pure function, step(params, opt_state, batch, key) returning new params, new opt_state and metrics, and apply jax.jit to it. Mark arguments that change the program's structure (such as a config object) as static, and keep input shapes fixed by padding batches to a few sizes. Use donate_argnums for params and optimizer state so XLA can reuse their buffers in place, which roughly halves their memory during updates.
Use jax.debug.print and jax.debug.breakpoint inside compiled code, run once with jax.disable_jit() when logic is wrong, and inspect what was traced with jax.make_jaxpr. Profile with jax.profiler and view the trace in Perfetto or TensorBoard to see whether time goes to compute, collectives or host work. Enable the persistent compilation cache so restarts do not recompile.
For scale, start from a reference such as MaxText (LLMs) or the Flax examples rather than writing sharding from scratch. Define a Mesh with named axes (for example "data" and "model"), annotate parameters and batches with NamedSharding, and check with jax.debug.visualize_array_sharding that arrays are laid out as you intend. Use shard_map only where automatic partitioning makes poor choices. Checkpoint with Orbax, which saves sharded arrays in parallel. Choose JAX when you train on TPUs, need transformations such as per-example gradients or higher-order derivatives, or want one program to scale from one device to thousands; choose PyTorch when you depend on the widest set of open models and tools.

value: Hugging Face Transformers is the standard Python library for using pretrained models. It contains the code for more than 400 model architectures (BERT, Llama, Qwen, Mistral, Whisper, ViT and many more), the tokenizers and image processors that prepare their inputs, and one common API to load any of them by name from the Hugging Face Hub. A single call such as AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct") downloads the configuration and weights, builds the right PyTorch model class, and loads the weights onto your GPUs. In late 2025 it was installed more than 3 million times a day, and in October 2026 the current version is 5.20. Version 5 (January 2026) made PyTorch its only back end and dropped TensorFlow and Flax.
It exists because pretrained models changed how machine learning is done. Since about 2018, most NLP work, and later vision and speech work, starts from a large model trained by someone else and adapts it. That only works if the model's code, its exact tokenizer and its weights travel together and load the same way everywhere. Before Transformers, each paper had its own repository, framework and loading script. Transformers made "a model" a shareable unit: a Hub repository with config.json, tokenizer files and weight files, which millions of model repositories now follow. The Hub (about 3 million models by August 2026, by Hugging Face's own count) is to models roughly what GitHub is to code.
The layers below supply what the library packages. PyTorch supplies the tensors, autograd and GPU kernels; every model class is a PyTorch nn.Module. Deep learning supplies the training methods (fine-tuning, mixed precision) that the Trainer wraps. Transformers and LLMs (L1) supply the architectures themselves: attention layers, decoder stacks, the KV cache used during generation. NLP supplies the tasks and the tokenization methods (subword vocabularies such as BPE and WordPiece). For serving engines above it, Transformers is the reference definition of each model: vLLM and SGLang can run Transformers model code as a back end, so a new architecture becomes usable in them quickly.
terms: Hub — Hugging Face's hosting service for model, dataset and app repositories, versioned like Git.
Checkpoint — one set of trained weights plus its config and tokenizer, stored in a Hub repository.
config.json — the file that names the architecture (model_type) and its sizes: layers, hidden size, heads, vocabulary.
Auto classes — AutoConfig, AutoTokenizer and AutoModel*, which read config.json and pick the right concrete class.
Tokenizer — the component that turns text into integer token IDs and back, using a learned subword vocabulary.
BPE — byte-pair encoding: a subword method that starts from characters or bytes and repeatedly merges the most frequent adjacent pair.
safetensors — a weight file format with a small JSON header and raw tensor bytes; it can be memory-mapped and cannot run code.
Chat template — a Jinja template stored with the tokenizer that turns a list of chat messages into the exact prompt string the model was trained on.
LoRA — low-rank adaptation: fine-tuning by training two small matrices per weight instead of the full weight.
history: Hugging Face was founded in 2016 in New York by Clément Delangue, Julien Chaumond and Thomas Wolf, first as a chatbot app. In October 2018 Google released BERT in TensorFlow. Within weeks, in November 2018, the team published pytorch-pretrained-BERT: a PyTorch reimplementation that loaded Google's converted weights and reproduced its results. Researchers wanted BERT in PyTorch, and the package spread fast. As OpenAI's GPT and GPT-2, XLNet and others appeared, the team added them behind the same interface, renamed the package pytorch-transformers (July 2019) and then transformers (version 2.0, September 2019), with TensorFlow 2 support added.
The design was described in the EMNLP 2020 demo paper "Transformers: State-of-the-Art Natural Language Processing" by Wolf and colleagues. Version 4 (November 2020) became the long-lived API. Around it, Hugging Face built a set of libraries: tokenizers (fast tokenization in Rust, 2019–2020), datasets (memory-mapped Arrow tables), accelerate (device placement and distributed training), PEFT (LoRA and other adapters), TRL (reinforcement learning from human feedback and preference tuning), and safetensors (2022), created because the older PyTorch .bin format used Python's pickle, which can run arbitrary code when a file is loaded.
The Hub grew with open models. Llama (2023) and its successors, Mistral, Qwen, DeepSeek and Gemma were all published there, together with thousands of fine-tuned variants each. In August 2024 Hugging Face acquired XetHub, and in 2025 the Hub moved from Git LFS to Xet storage, which deduplicates at the level of byte chunks, so a new checkpoint that differs slightly from the old one uploads only the changed parts. Text Generation Inference, Hugging Face's own server, moved to maintenance mode; the project now recommends vLLM and SGLang, which use Transformers model definitions.
Version 5 (release candidate December 2025, final release 26 January 2026) was the first major version in five years. It dropped TensorFlow and Flax, made the Rust tokenizers the single tokenization back end, centralized attention implementations, and added an OpenAI-compatible transformers serve command with continuous batching. Minor releases now come every few weeks.
how: A Hub repository is the unit of distribution. For a typical language model it contains config.json (architecture name and sizes), generation_config.json (default sampling settings), tokenizer.json and tokenizer_config.json (vocabulary, merges, special tokens and the chat template), and the weights as one or more .safetensors files with an index file that maps each tensor name to its shard. Every file is versioned: a revision is a Git commit hash, so you can pin exactly what you load. The local cache mirrors this: a blobs folder holds each file once, named by its content hash, a snapshots folder holds one directory of links per commit, and a refs folder maps names such as "main" to commits. Two revisions that share a 5 GB shard therefore store it once. At the top of the API, pipeline("text-generation", model=...) wraps all of the steps below (tokenize, run the model, decode) in one call for quick use.
Loading follows a fixed path. from_pretrained first asks the huggingface_hub client to resolve the name and revision and download the files into a local cache (by default ~/.cache/huggingface/hub), where files are stored once by content and shared between revisions. AutoConfig reads model_type from config.json, for example "llama", and creates a LlamaConfig. AutoModelForCausalLM maps that config to LlamaForCausalLM and builds the model on PyTorch's "meta" device, which allocates no memory, so building an 8-billion-parameter model is instant. Then the weights are loaded. A safetensors file starts with an 8-byte length, then a JSON header listing each tensor's name, data type, shape and byte offsets, then raw bytes. The loader memory-maps the file, so the operating system reads pages from disk only when they are needed, and copies each tensor into its parameter in the requested data type. With device_map="auto", the accelerate library fills each GPU in turn with whole layers, then places the rest in CPU memory or on disk. Quantization configurations (bitsandbytes, GPTQ, AWQ, torchao) are applied at this stage, converting weights to 8-bit or 4-bit as they load.
The model code itself is plain PyTorch. Each architecture lives in a modeling file (for example modeling_llama.py) that defines the embedding, the decoder layers, attention, the MLP and the output head as nn.Module classes. The library deliberately repeats code across models, the "one model, one file" rule, so that a researcher can read and change one model without following layers of abstraction. Version 5 keeps that readability but generates these files from shorter "modular" definitions that inherit from existing models, and it routes attention through one interface that can pick PyTorch's scaled_dot_product_attention, FlashAttention or FlexAttention. Here the LLM layer and PyTorch meet directly: the attention layer is the transformer block from the papers, and it runs on PyTorch's kernels.
Tokenization is where NLP methods enter. The tokenizers library, written in Rust, runs a fixed pipeline: normalization (for example Unicode normalization), pre-tokenization (splitting on spaces or bytes), the subword model (BPE, WordPiece or Unigram) that maps pieces to IDs, and post-processing that adds special tokens such as a beginning-of-text marker. It also records offsets, so each token can be traced back to its characters. For chat models, apply_chat_template renders a list of messages into the exact string format used in training, with role markers and special tokens. A wrong template is one of the most common reasons a model "works badly".
Generation is a loop around the model. model.generate runs one forward pass over the prompt (prefill), stores the attention keys and values in a cache object, and then repeatedly runs a forward pass on just the newest token, reading the cache. Each step produces logits for the next token; logits processors apply temperature, top-k, top-p and repetition penalties; a token is chosen by greedy choice or sampling; and the loop stops at an end token or max_new_tokens. This is correct and flexible, but each call handles one fixed batch. Production servers instead batch many users continuously and manage cache memory in pages, which is why vLLM and SGLang exist.
Training uses the same objects, and here deep learning supplies the recipe. The Trainer class wraps a PyTorch training loop with mixed precision, gradient accumulation, checkpointing, logging and evaluation, and uses accelerate to run on one GPU or many (DDP, FSDP or DeepSpeed). PEFT adds adapters such as LoRA to chosen layers, so only a small number of new parameters train while the original weights stay frozen. TRL builds on this for supervised fine-tuning and preference or reinforcement methods such as DPO and GRPO.

example: Start with tokenization, using a toy BPE vocabulary. The learned merges, in order, are (l, o) → "lo", (lo, w) → "low", (e, r) → "er". Encode the word "lower". Start from characters: l o w e r. Apply the first merge: lo w e r. Apply the second: low e r. Apply the third: low er. The result is two tokens, "low" and "er", which the vocabulary maps to two IDs. A word never seen in training, such as "slower", still encodes: s low er, three tokens. Real vocabularies have tens of thousands of merges (Llama 3's vocabulary has 128,256 tokens), and English text averages roughly 4 characters per token, which is why cost and context limits are counted in tokens.
Now load a model. Llama 3.1 8B's config.json says 32 layers, hidden size 4,096, 32 attention heads, 8 key-value heads of dimension 128, and a vocabulary of 128,256. It has about 8.0 billion parameters. In bf16 (2 bytes each) that is about 16 GB, stored as four safetensors shards of roughly 5, 5, 4.9 and 1.2 GB. On one 24 GB GPU the weights fit, leaving about 8 GB. How much context does that buy? The KV cache per token is 2 (keys and values) × 32 layers × 8 heads × 128 dimensions × 2 bytes = 131,072 bytes, which is 128 KB. So 8 GB holds about 8 × 1,024 × 1,024 / 128 = 65,536 tokens of cache in total, for example 8 conversations of 8,192 tokens, minus space for activations. Load the same model in 4-bit and the weights shrink to roughly 5 GB, leaving room for more than twice as much cache, at some cost in quality.
Finally, fine-tune it with LoRA of rank 16 on the attention projections q_proj and v_proj. q_proj is 4,096 × 4,096; LoRA adds A (16 × 4,096) and B (4,096 × 16), so 131,072 new parameters. Because of grouped-query attention, v_proj is 4,096 × 1,024; LoRA adds 16 × 4,096 + 1,024 × 16 = 81,920. Per layer that is 212,992; over 32 layers, about 6.8 million trainable parameters, roughly 0.085% of the model. The adapter file is about 13.6 MB in bf16, and the gradients and AdamW state for it take only around 100 MB, so a single GPU that holds the frozen base model can fine-tune it.
intuition: Transformers is a shared shipping standard for models: every container (Hub repository) has the same labels (config, tokenizer, weights), so any crane (from_pretrained) can unload any container onto any ship (your hardware).
The design is natural because a pretrained model is useless without three things that must match exactly: the architecture code, the tokenizer, and the weights. Storing them together, versioned, and loading them through one function removes the most common failure, a mismatch between them. Reading the class from config.json means the caller does not need to know which architecture it is loading. Building on the meta device and memory-mapping safetensors means that loading cost is just copying bytes, and the copy can go straight to the right GPU. Keeping each model's code explicit, even with repetition, matches how researchers work: they read one model, change it, and publish the variant to the Hub, where the next person loads it the same way.
mistakes: People often think model.generate is a good way to serve many users. In fact it processes one fixed batch at a time and allocates the KV cache simply, so GPU utilization under real traffic is low. Use vLLM or SGLang for serving; they can run the same Transformers model definitions.
People often think a model on the Hub is safe and ready because it is popular. In fact quality, licence and safety vary widely. Weights in the old pickle format, or repositories that require trust_remote_code=True, can run arbitrary code on your machine. Prefer safetensors, read the licence and model card, and pin a revision hash.
People often build prompts for chat models by joining strings by hand. In fact each model was trained on one specific format with special tokens, and small differences (a missing end-of-turn token, an extra space) reduce quality. Use tokenizer.apply_chat_template.
People often think from_pretrained always loads the same thing. In fact without a revision it loads the latest commit of the repository, which the owner can change at any time. Pin a commit hash in production, and keep your own copy of critical weights.
friction: The API surface is huge: hundreds of model classes, many task heads, and several companion libraries, each with its own options. Parameters change between versions, and version 5 removed many deprecated arguments, the TensorFlow and Flax classes, and the "slow" Python tokenizers, so upgrading older code takes work. Minor releases every few weeks mean frequent small breaking changes in less-used paths.
Performance is not the library's main goal. The explicit modeling code favours readability over speed, so production inference needs dedicated engines, and the built-in continuous batching of transformers serve is newer and less tuned than vLLM or SGLang. Training very large models needs careful configuration of FSDP or DeepSpeed through accelerate, and memory errors often come from defaults such as full-precision loading or an oversized cache.
The Hub raises its own problems. Licences range from Apache 2.0 to custom licences with usage limits, and gated models need access approval. Many repositories have incomplete model cards, wrong chat templates or wrong generation defaults. Supply-chain risk is real: malicious pickle files and remote code have been found on public hubs. Large downloads (an 8B model is 16 GB; a 400B model is hundreds of gigabytes) need caching, mirrors and disk planning, and the cache grows silently on shared machines.
practice: Pin everything: the library version, and a commit hash for each model you load (revision="..."). Load in the training data type, usually torch_dtype=torch.bfloat16, with device_map="auto" when the model does not fit on one GPU, and choose attn_implementation (sdpa or flash_attention_2) explicitly. Prefer safetensors and avoid trust_remote_code unless you have read the code.
Use apply_chat_template for every chat model and check the rendered prompt once by printing it. For fine-tuning, start with LoRA or QLoRA through PEFT before full fine-tuning; it needs far less memory and produces small adapter files that you can keep per task. Use TRL for supervised fine-tuning and preference tuning instead of writing those loops yourself. Evaluate on your own held-out data, not only public benchmarks.
For serving, export the fine-tuned model (merging LoRA into the base if needed) and run it in vLLM or SGLang, which read Hub repositories directly. Set HF_HOME to a large shared disk, run a mirror or proxy cache for clusters so hundreds of nodes do not download the same 16 GB, and use the hf CLI to pre-download models during image builds. In regulated settings, copy approved models into a private Hub organization or internal storage, and record the licence and revision with each deployed model.

@@ sklearn
value: scikit-learn is the standard Python library for classic machine learning: linear and logistic regression, decision trees and random forests, gradient boosting, support vector machines, k-means and other clustering, principal component analysis, nearest neighbours, and the preprocessing, model-selection and evaluation tools around them. Its central contribution is not any single algorithm but one consistent interface: every model is an estimator with fit, and then predict or transform, so you can swap a random forest for a logistic regression by changing one line. In October 2026 the current version is 1.9.1 (September 2026), with a new minor release about every six months.
It exists because most practical machine learning is not deep learning. Fraud scores, churn models, demand forecasts, A/B test analysis, lead scoring and many ad-tech models work on tables of a few thousand to a few million rows, where a well-validated linear model or tree ensemble is accurate, fast to train, cheap to serve and easy to explain. The hard part is rarely the algorithm. It is preprocessing, honest evaluation and avoiding leakage of test information into training. scikit-learn turned the textbook workflow (split data, fit on training data, tune with cross-validation, score on held-out data) into objects that make the correct workflow the easy one.
It stands on one concept, machine learning (L1), and contributes its software form. Machine learning supplies the methods (least squares, maximum likelihood, tree induction, margin maximization, clustering objectives) and, just as important, the evaluation methodology: generalization error, the bias–variance trade-off, and cross-validation as an estimate of performance on unseen data. scikit-learn encodes both: the algorithms as estimators, and the methodology as Pipeline, cross_validate and GridSearchCV. Under the hood it relies on NumPy and SciPy for arrays, linear algebra and sparse matrices, and on Cython for tight loops. Many other libraries (XGBoost, LightGBM, imbalanced-learn, skops, sklearn-onnx) follow its API so they plug into the same tools.
terms: Estimator — any object with a fit method that learns from data; its hyperparameters are set in the constructor.
Transformer — an estimator with transform, which turns X into a new X (for example scaling or encoding); not related to the neural-network transformer.
Predictor — an estimator with predict (and often predict_proba or decision_function).
Fitted attribute — a value learned by fit, named with a trailing underscore, such as coef_ or mean_.
Pipeline — a chain of transformers ending in an estimator, which behaves as one estimator.
ColumnTransformer — a transformer that applies different preprocessing to different columns, such as scaling numbers and one-hot encoding categories.
Cross-validation — splitting training data into k folds, training on k − 1 and scoring on the remaining one, k times, to estimate performance on unseen data.
Data leakage — information from the evaluation data reaching the training step, which makes scores look better than reality.
Hyperparameter — a setting chosen before training (such as tree depth or regularization strength C), not learned from data.
history: scikit-learn began in 2007 as a Google Summer of Code project by David Cournapeau, called scikits.learn: a "SciKit", meaning an add-on toolkit for SciPy. Matthieu Brucher continued work on it during his thesis. In 2010, researchers at INRIA in France (Fabian Pedregosa, Gaël Varoquaux, Alexandre Gramfort and Vincent Michel) took over leadership, and the first public release (0.1) came out in February 2010. They needed reliable machine-learning tools for neuroimaging research, and they valued consistent APIs, documentation and tests over adding algorithms quickly.
The 2011 JMLR paper "Scikit-learn: Machine Learning in Python" by Pedregosa and colleagues became one of the most cited software papers in machine learning. The 2013 paper by Buitinck and colleagues, "API design for machine learning software", explained the design rules: estimators, transformers and predictors with uniform methods, hyperparameters in the constructor, learned state in attributes ending with an underscore, and composition through pipelines and meta-estimators.
The library then grew slowly and deliberately. It has a strict inclusion rule: a new algorithm must be well established before it is added; the project's rule of thumb is at least three years since publication, 200 or more citations, and wide use. Version 0.21 (2019) added HistGradientBoostingClassifier and Regressor, histogram-based boosting inspired by LightGBM, so users could get fast boosting without extra libraries. Version 1.0 (September 2021) marked API stability, and later versions added pandas output (set_output, 1.2), native categorical support in histogram boosting, and metadata routing. In early 2024 the INRIA team moved to Probabl, an INRIA spin-off company that now funds much of the development. Version 1.8 (December 2025) expanded experimental GPU support through the Python Array API standard, so some estimators accept PyTorch or CuPy arrays and compute on the GPU, and shipped free-threaded wheels for Python 3.14. Version 1.9 (June 2026) added experimental callbacks such as progress bars during fit.
how: The estimator contract is simple and strict. The constructor only stores hyperparameters, with no validation and no work, so LogisticRegression(C=0.1) is just a description. fit(X, y) checks the inputs, learns, stores learned values as attributes with a trailing underscore (coef_, intercept_, classes_), and returns self. predict(X) or transform(X) uses only those attributes. Because every hyperparameter is a constructor argument, get_params and set_params can read and change any of them by name, and clone(estimator) can build a fresh, unfitted copy with the same settings. These three facts are what make composition work: a search tool can clone a model, change its parameters, fit it on a fold and score it, without knowing what kind of model it is.
Data has one shape: X is a two-dimensional array with one row per sample and one column per feature, and y is one value (or one row) per sample. X can be a NumPy array, a SciPy sparse matrix (useful for text features, where most values are zero), or a pandas DataFrame, and set_output(transform="pandas") keeps column names through transformations.
Pipeline chains steps. Pipeline([("scale", StandardScaler()), ("clf", LogisticRegression())]) is itself an estimator. Its fit calls fit_transform on each transformer in order, passing the result to the next, and then fit on the final estimator. Its predict calls transform on each step, using what was learned during fit, and then predict. ColumnTransformer runs different transformers on different column groups and joins their outputs side by side, so a single object can impute and scale numeric columns and one-hot encode categorical ones. The point is not convenience only. When a pipeline is evaluated by cross-validation, every preprocessing step is fitted inside each training fold, so the test fold never influences scaling statistics, category lists or selected features.
Model selection is machine learning's evaluation methodology turned into code, built from the same pieces. A splitter (KFold, StratifiedKFold, GroupKFold, TimeSeriesSplit) produces index pairs of training and test rows. cross_validate clones the estimator for each split, fits it on the training rows, and scores it on the test rows. GridSearchCV and RandomizedSearchCV do this for every candidate set of hyperparameters, then refit the best candidate on all the training data and expose it as best_estimator_. HalvingGridSearchCV saves time by training all candidates on small samples and giving more data only to the best ones. Fits are independent, so they run in parallel through joblib, set with n_jobs. The same clone-and-fit idea powers meta-estimators, which wrap other estimators: BaggingClassifier fits clones on bootstrap samples, StackingClassifier fits a second model on the cross-validated predictions of several first-level models, OneVsRestClassifier fits one binary clone per class, and CalibratedClassifierCV fits clones and then learns a mapping from their scores to calibrated probabilities.
Speed comes from the layers underneath. Linear algebra (least squares, PCA, Ridge) calls LAPACK and BLAS through NumPy and SciPy, which use optimized libraries such as OpenBLAS or MKL with many threads. Iterative solvers such as L-BFGS come from SciPy. Code that must loop over samples or tree nodes is written in Cython, compiled to C, with OpenMP threads where possible. Decision trees, for example, are grown in Cython: for each node, each candidate feature's values are sorted, every split point is scanned while class counts are updated incrementally, and the split with the largest decrease in impurity (Gini or entropy for classification, squared error for regression) is kept. HistGradientBoosting first bins each feature into at most 255 bins, then builds histograms of gradients per bin with OpenMP threads, which makes split finding cost proportional to the number of bins rather than the number of rows. Support vector machines wrap the C++ libraries libsvm and liblinear.
Two recent mechanisms change where computation runs. With array_api_dispatch=True, estimators that support the Array API standard use the namespace of the input arrays, so a PyTorch tensor on a GPU is processed with PyTorch operations on that GPU; in 1.8 this covers estimators such as Ridge, StandardScaler and GaussianMixture and many metrics, but not trees or most of the library. With free-threaded Python, joblib can use threads instead of processes, which avoids copying data between processes. Fitted models are usually saved with pickle or joblib; skops offers a safer format, and sklearn-onnx converts many pipelines to ONNX for serving outside Python.

example: Start with what fit and transform store. A training column has the values 2, 4, 6 and 8. StandardScaler.fit computes mean_ = 5 and the standard deviation: the squared distances from the mean are 9, 1, 1 and 9, their average is 5, so scale_ = √5 ≈ 2.236. transform maps each value x to \( (x - 5) / 2.236 \), giving −1.34, −0.45, 0.45 and 1.34. A test value of 10 later becomes (10 − 5) / 2.236 ≈ 2.24, using the training statistics. If you had fitted the scaler on training and test data together, the mean would have moved toward the test data. In this case that is a small leak, but the same pattern with feature selection is a large one.
Here is that large one, a classic example from The Elements of Statistical Learning (section 7.10.2). There are 50 samples, two equally sized classes, and 5,000 features of pure noise, so no model can beat 50% error. The wrong procedure: choose the 100 features most correlated with the labels using all 50 samples, then cross-validate a 1-nearest-neighbour classifier on those 100 features. The book reports an average cross-validation error of about 3%, a completely false result, because the features were chosen by looking at the test folds' labels. The right procedure puts SelectKBest(k=100) and the classifier in one Pipeline and cross-validates the pipeline, so selection happens again inside every training fold. The cross-validation error then comes out near the true 50%.
Now the cost of a search. You tune a pipeline over C ∈ {0.01, 0.1, 1, 10} and two choices of class_weight, which is 4 × 2 = 8 candidates. With 5-fold cross-validation that is 8 × 5 = 40 fits, plus 1 final refit on all the training data: 41 fits. If each fit takes 3 seconds, one core needs about 123 seconds; with n_jobs=8 the 40 search fits run 8 at a time, so 5 rounds of 3 seconds plus the refit, about 18 seconds. Add a third hyperparameter with 5 values and you have 200 fits; this multiplication is why RandomizedSearchCV or successive halving is the better default for more than two or three hyperparameters.
intuition: scikit-learn is a toolbox where every tool has the same handle: whether you pick up a scaler, a tree or a clustering method, you hold it the same way, so you can build machines out of them.
The design is natural because the machine-learning workflow really is the same across algorithms. Every method learns something from training data and then applies it to new data; the only differences are what is learned and how. Making "learn" (fit) and "apply" (predict or transform) the universal verbs separates the two phases cleanly, and storing learned values apart from settings makes it obvious what came from the data. Once every piece obeys this contract, the methodology itself becomes code: a pipeline is just another estimator, and cross-validation and grid search are functions that clone, fit and score any estimator. The safe workflow stops being a discipline you must remember and becomes the default shape of the code.
mistakes: People often scale, impute or select features on the whole dataset and then cross-validate. In fact this leaks test information into training, and the scores are too optimistic, sometimes wildly so. Put every preprocessing step in a Pipeline and cross-validate the pipeline.
People often trust the default hyperparameters as if they were tuned. In fact defaults are reasonable starting points, not good values for your data. LogisticRegression applies L2 regularization with C = 1 by default, which matters a lot when features are not scaled, and a RandomForest with default depth can overfit small, noisy datasets.
People often think scikit-learn cannot handle large data at all. In fact it works well up to millions of rows on one machine, especially with sparse inputs, HistGradientBoosting, SGDClassifier, and estimators with partial_fit for data that arrives in chunks. What it does not do is distribute training across a cluster or use GPUs for most estimators.
People often split time-ordered or grouped data randomly. In fact random KFold lets the model see the future, or the same user, in training, which inflates scores. Use TimeSeriesSplit for time order and GroupKFold when rows from the same user, device or session must stay together.
friction: scikit-learn runs on one machine and mostly on CPUs. GPU support through the Array API covers only some estimators and is experimental; tree models, SVMs and most of the library stay on the CPU. For data that does not fit in memory, or for distributed training, you need other tools (Spark MLlib, Dask-ML, Ray, or XGBoost and LightGBM with their own distributed modes).
It is not a deep-learning library. Its neural-network classes (MLPClassifier) are small and CPU-only, and are useful only for teaching or tiny problems. It also does not cover gradient boosting at the very high end: XGBoost, LightGBM and CatBoost usually train faster on large data and offer more options, although HistGradientBoosting is close for many tasks.
The conservative inclusion policy means new methods arrive late or never; you will find them in companion libraries instead. Persistence is fragile: a pickled model is tied to the scikit-learn version that created it, may break or silently change after an upgrade, and pickle files can run code when loaded, so they must come from trusted sources. Finally, serving a scikit-learn pipeline at low latency in a non-Python service needs conversion (for example to ONNX) or a Python serving layer, and each step's Python overhead adds up when you predict one row at a time.
practice: Build everything as one Pipeline (ColumnTransformer for per-column preprocessing, then the model) and use it for cross-validation, tuning, saving and serving, so training and serving use exactly the same transformations. Choose the splitter that matches how the model will be used: StratifiedKFold for imbalanced classes, GroupKFold for users or devices, TimeSeriesSplit for anything predicted forward in time. Keep a final test set that no search ever touches.
Start with a strong, simple baseline: a regularized linear model on scaled features and HistGradientBoosting on raw features. Compare them with cross-validated scores and their spread across folds, not one number. Use RandomizedSearchCV or HalvingRandomSearchCV for more than a few hyperparameters, and set n_jobs to use your cores. For classifiers whose probabilities drive decisions (bids, risk thresholds), check calibration and use CalibratedClassifierCV if needed; 1.8 added temperature scaling for multiclass problems.
For production, record the scikit-learn version with each saved model and reload it only with the same version; consider skops for safer files or ONNX for serving outside Python. Use set_output(transform="pandas") to keep feature names, which makes debugging and feature-importance analysis much easier. Move to XGBoost or LightGBM when data grows to tens of millions of rows or when you need distributed or GPU training; both accept the same fit and predict calls inside scikit-learn pipelines.

@@ xgboost
value: XGBoost is an open-source library for gradient-boosted decision trees. It builds a model as a sum of many small trees, added one at a time, where each new tree is fitted to correct the errors of all the trees before it. Tianqi Chen started it in 2014 at the University of Washington, and it became famous by winning machine-learning competitions: the KDD 2016 paper reports that 17 of the 29 winning solutions published on Kaggle's blog in 2015 used it. In October 2026 the current release is 3.4.1 (August 2026). It runs from Python, R, Java/Scala (including Spark), C++ and other languages, on CPUs and NVIDIA GPUs, on one machine or across a cluster.
Boosted trees remain the best default for many problems on tabular data: rows of records with numeric and categorical columns, such as click-through prediction, fraud detection, credit risk, demand forecasting and search ranking. They need little preprocessing (no scaling, missing values handled natively), train in minutes on millions of rows, and capture non-linear effects and interactions between features automatically. Studies such as Grinsztajn and colleagues (NeurIPS 2022) found that tree ensembles still match or beat deep networks on typical medium-sized tabular benchmarks. XGBoost, LightGBM and CatBoost are the three main libraries, and they share most ideas.
It stands on machine learning (L1), and takes several things from it. Decision trees (CART) give the weak learner: a piecewise-constant function that splits the feature space one feature at a time. Boosting, in Jerome Friedman's 2001 formulation, gives the training method: gradient descent in the space of functions, where each tree is one step. Regularization gives control of overfitting, here as explicit penalties on the number of leaves and the size of leaf values. XGBoost added a second-order (Newton) approximation of the loss and the systems engineering (histograms, sparse data handling, parallel and distributed training) that made boosting fast on very large data.
terms: Decision tree — a model that routes each row through yes/no questions on single features ("age < 30?") to a leaf value.
Boosting — building a strong model as a sum of weak models, each trained to fix the remaining errors.
Margin — the sum of all trees' leaf values for a row, before a link function such as the sigmoid.
Gradient g — the first derivative of the loss with respect to the current prediction, for one row.
Hessian h — the second derivative of the loss with respect to the current prediction (its curvature).
Gain — the reduction in the regularized objective that a candidate split would give.
Learning rate (eta) — a factor below 1 that shrinks each new tree's contribution, so many trees share the work.
Histogram method — bucketing each feature into at most a few hundred bins, so split search scans bins.
min_child_weight — the minimum sum of hessians allowed in a child node; it blocks splits that create tiny, noisy leaves.
history: Boosting began as a theoretical question: can many weak learners, each only slightly better than chance, be combined into a strong one? Robert Schapire showed in 1990 that they can, and Yoav Freund and Schapire's AdaBoost (1995–1997) made it practical by re-weighting the examples that earlier models got wrong. Friedman, Hastie and Tibshirani (2000) explained AdaBoost as fitting an additive model to a particular loss, and Friedman's "Greedy Function Approximation: A Gradient Boosting Machine" (Annals of Statistics, 2001) generalized it: for any differentiable loss, fit each new tree to the negative gradient of the loss at the current predictions. His stochastic gradient boosting (2002) added row subsampling. These methods became standard in R (gbm) and scikit-learn, but were slow on large data.
Tianqi Chen, then a PhD student at the University of Washington working with Carlos Guestrin, started XGBoost ("eXtreme Gradient Boosting") in 2014 as part of the DMLC (Distributed Machine Learning Community) projects. It became known through the 2014 Kaggle Higgs Boson challenge and spread quickly through competitions. The 2016 KDD paper "XGBoost: A Scalable Tree Boosting System" described its main ideas: a regularized objective with second-order gradients, a weighted quantile sketch for approximate splits, sparsity-aware split finding, and cache-aware, out-of-core computation.
Competition followed. Microsoft's LightGBM (NeurIPS 2017) used histograms and leaf-wise tree growth to train much faster, and Yandex's CatBoost (2017–2018) handled categorical features with ordered target statistics. XGBoost adopted these ideas: the hist method and GPU training (from about 2017), optional leaf-wise growth, native categorical splits, and in version 2.0 (September 2023) hist as the default with one device parameter for CPU or GPU. Version 3.0 (February 2025) made external-memory training practical, including on GPUs using NVLink-C2C to reach host memory, so datasets of terabytes can be trained. Version 3.4 (August 2026) made multi-output trees, where one tree predicts several targets with vector-valued leaves, feature-complete but still experimental.
how: Training follows Friedman's gradient boosting from machine learning, with CART-style trees as the weak learner: one tree per round. After t − 1 rounds, each row i has a current margin \( \hat{y}_i \), the sum of the previous trees' outputs (starting from a base score). Round t adds a tree \( f_t \), so the new margin is \( \hat{y}_i + \eta f_t(x_i) \). XGBoost chooses \( f_t \) to minimize the regularized objective: the sum over rows of the loss \( l(y_i, \hat{y}_i + f_t(x_i)) \), plus a penalty \( \Omega(f_t) = \gamma T + \tfrac{1}{2}\lambda \sum_j w_j^2 \), where T is the number of leaves, \( w_j \) are the leaf values, \( \gamma \) charges a fixed cost per leaf, and \( \lambda \) shrinks leaf values toward zero.
The key step is a second-order Taylor expansion of the loss around the current margin. For each row, compute \( g_i \) (the gradient) and \( h_i \) (the hessian) of the loss with respect to \( \hat{y}_i \). Then the loss after adding the tree is approximately a constant + \( \sum_i [\,g_i f(x_i) + \tfrac{1}{2} h_i f(x_i)^2\,] \). A tree gives every row in leaf j the same value \( w_j \), so group the rows by leaf: let \( G_j \) be the sum of g over rows in leaf j and \( H_j \) the sum of h. The objective becomes \( \sum \) over leaves of \( [\,G_j w_j + \tfrac{1}{2}(H_j + \lambda) w_j^2\,] + \gamma T \). Each leaf is a simple quadratic in \( w_j \), minimized at \( w_j^* = -G_j / (H_j + \lambda) \), and the minimum value is \( -\tfrac{1}{2} G_j^2 / (H_j + \lambda) \). This is a Newton step: the gradient says which way to move, the hessian says how far.
That formula scores any tree structure, so it also scores any split. Splitting a node with sums \( (G, H) \) into left and right children with sums \( (G_L, H_L) \) and \( (G_R, H_R) \) changes the objective by
\[ \text{Gain} = \frac{1}{2}\left[\frac{G_L^2}{H_L + \lambda} + \frac{G_R^2}{H_R + \lambda} - \frac{G^2}{H + \lambda}\right] - \gamma \]
The tree is grown greedily: for each node, try candidate splits on every feature, keep the one with the largest gain, and stop when no split has positive gain, the maximum depth is reached (default 6), or a child would have a hessian sum below min_child_weight. Because only g and h enter these formulas, any twice-differentiable loss works the same way: squared error (\( g = \hat{y} - y \), \( h = 1 \)), logistic loss for classification (\( g = p - y \), \( h = p(1 - p) \), where p is the sigmoid of the margin), Poisson, Tweedie, and ranking losses such as LambdaMART's.
Finding splits efficiently is the systems part. The exact method sorts each feature once and scans every distinct value, which is precise but slow and memory-heavy. The hist method, the default since 2.0, first quantizes each feature into at most max_bin bins (default 256) using quantiles, so each value becomes a one-byte bin index. To evaluate a node, it builds a histogram per feature: for each bin, the sums of g and h of the node's rows that fall into it. Scanning a feature's bins from left to right gives G_L and H_L for every possible threshold, with G_R = G − G_L. Two tricks make this fast. Building histograms is one pass over the node's rows, which suits CPUs with many threads and GPUs very well. And a parent's histogram minus the smaller child's histogram gives the larger child's histogram for free, so only the smaller child is scanned.
Missing values and sparse data are handled inside the split search. For each candidate split, XGBoost tries sending all rows with a missing value to the left child and then to the right child, and keeps the better direction as that node's default. Rows that have no entry for a feature (in sparse one-hot data, most of them) are never touched while building that feature's histogram, so cost grows with the number of non-zero values, not with rows times features. Native categorical support splits a node by partitioning the categories into two groups, chosen by sorting categories by their gradient statistics.
Several controls fight overfitting: the learning rate η (default 0.3; smaller needs more rounds but generalizes better), subsample and colsample_bytree (random fractions of rows and features per tree), the penalties λ, α and γ, and early stopping on a validation metric. For distributed training, each worker builds histograms for its slice of the rows and the workers sum them with an all-reduce, so every worker picks the same split; this runs on Spark, Dask, Ray and multiple GPUs. Prediction walks each row through every tree and adds the leaf values.

example: Take four rows with one feature x = 1, 2, 3, 4 and labels y = 0, 0, 1, 1, with logistic loss. Use λ = 1, γ = 0, η = 0.3, and set min_child_weight = 0 for this tiny example (the default of 1 would forbid children this small, which is exactly its purpose). The base margin is 0, so every row has p = sigmoid(0) = 0.5. Gradients are \( g = p - y \): 0.5, 0.5, −0.5, −0.5. Hessians are \( h = p(1 - p) \) = 0.25 for every row. At the root, G = 0 and H = 1.0.
Try the split x < 2.5. Left gets rows 1 and 2: G_L = 1.0, H_L = 0.5. Right gets rows 3 and 4: G_R = −1.0, H_R = 0.5. Gain = ½ × [1.0² / 1.5 + (−1.0)² / 1.5 − 0² / 2.0] = ½ × [0.667 + 0.667] = 0.667. Now try x < 1.5. Left is row 1 only: G_L = 0.5, H_L = 0.25. Right is rows 2 to 4: G_R = 0.5 − 1.0 = −0.5, H_R = 0.75. Gain = ½ × [0.25 / 1.25 + 0.25 / 1.75] = ½ × [0.200 + 0.143] = 0.171. The first split wins, as it should, since it separates the classes.
Leaf values: left \( w = -G_L / (H_L + \lambda) \) = −1.0 / 1.5 = −0.667; right w = +0.667. After shrinking by η = 0.3, the tree adds −0.2 to rows 1 and 2 and +0.2 to rows 3 and 4. New probabilities: sigmoid(−0.2) = 0.450 and sigmoid(0.2) = 0.550, both now closer to their labels. The log loss per row falls from −ln(0.5) = 0.693 to −ln(0.55) = 0.598. In round 2, the gradients are 0.45, 0.45, −0.45, −0.45 and the hessians are 0.45 × 0.55 = 0.2475, so the next tree makes a slightly smaller correction. Each round repeats this until the validation loss stops improving.
Now a realistic size. A click-through model has 50 million rows and 300 features: as float32, 50 × 10⁶ × 300 × 4 bytes = 60 GB. With the hist method each value becomes a bin index of about one byte, so about 15 GB, which fits on one 80 GB GPU. Per tree level, histogram building touches each value once (at most 15 billion updates, halved by the subtraction trick), while the split scan costs only 300 × 256 = 76,800 candidates per node. With 500 trees of depth 8, prediction is 4,000 node visits per row, a few microseconds.
intuition: Boosting is like a team of junior analysts working in sequence: each one studies only the errors left by everyone before, explains a small part of them, and passes the rest on.
The design is natural once you see training as descent. Gradient descent on a neural network moves the weights a little in the direction that reduces the loss. Gradient boosting does the same with the predictions themselves: the gradient for each row says which way its prediction should move, and a small tree is the simplest function that moves similar rows the same way. The hessian adds a sense of scale: where the loss is very curved (rows already predicted confidently), take smaller steps; where it is flat, take bigger ones. Trees fit this role because they ignore feature scaling, route missing values, and capture interactions by nesting splits; many shallow, shrunk trees average out the noise one deep tree would memorize.
mistakes: People often think more trees always overfit, or always help. In fact, with a small learning rate, validation error usually falls and then flattens; it rises only slowly after the best point. Use early stopping on a validation set to choose the number of trees instead of guessing.
People often one-hot encode or scale every feature before XGBoost. In fact trees are not affected by scaling, and for high-cardinality categories (thousands of values) one-hot encoding creates many sparse columns and weak splits. Use native categorical support (enable_categorical=True with pandas category columns) or target statistics computed inside cross-validation.
People often read feature importance ("gain" or "weight") as the causal effect of a feature. In fact importance shows how much the model used a feature, which is biased toward features with many split points and splits credit between correlated features. Use SHAP values (pred_contribs=True) for per-prediction explanations, and experiments for causal questions.
People often expect a boosted model to follow a trend beyond the training data. In fact each leaf predicts a constant, so for any input beyond the training range the prediction is flat. A demand model trained on prices from 10 to 50 predicts the same for 80 as for 50, which matters for time trends and growth.
friction: Boosted trees need good features. They do not learn from raw images, audio or long text, and they cannot share information across rows the way sequence or graph models can, so a lot of the work moves into feature engineering and aggregation pipelines, which must be identical in training and serving.
Tuning has many interacting knobs (learning rate, depth, min_child_weight, subsampling, regularization, number of trees), and the best values depend on the data. Training is sequential across rounds, so one model cannot use more parallelism than one tree's histogram building allows; thousands of rounds on huge data still take hours.
Models drift. The trees memorize the feature distribution of the training period, cannot extrapolate, and do not update online, so systems such as ad bidding or fraud detection retrain daily or weekly and must monitor calibration and feature drift. Probability outputs from boosting are often miscalibrated, especially with class re-weighting, and need a calibration step when they drive bids or thresholds.
Operational details also bite: distributed training on Spark needs careful partitioning and memory settings, and GPU builds must match the CUDA version (the 3.4 wheels default to CUDA 13; CUDA 12 needs a separate package).
practice: Start with tree_method="hist" (the default), device="cuda" if you have a GPU, a learning rate of 0.05 to 0.1, max_depth of 6 to 8, subsample and colsample_bytree around 0.8, and early_stopping_rounds of about 50 on a validation set that follows the same split logic as production (for example, the most recent days for time-ordered data). Then tune depth, min_child_weight and regularization with a random or Bayesian search, using cross-validation or a time-based validation scheme.
Load data with QuantileDMatrix (or its external-memory version for data larger than memory) so it is quantized once and uses about a byte per value. Use native missing-value handling: leave missing values as NaN instead of filling them with zeros, which the model would treat as real values. Mark categorical columns explicitly. For ranking problems, use rank:ndcg with query groups, and for click models set the objective to binary:logistic and check calibration on held-out data.
Explain and monitor the model: compute SHAP values for a sample of predictions, track feature distributions and calibration over time, and set a retraining schedule. Save models in the JSON or UBJSON format, which is stable across versions, and record the library version. In Spark pipelines use the xgboost.spark estimators, in Python use the scikit-learn API inside a Pipeline, and for serving in other languages consider exporting to ONNX or using the C API or a dedicated tree-inference library.

@@ vllm
value: vLLM is an open-source engine for serving large language models: it loads a model onto one or more GPUs and answers many users' requests at once, through an OpenAI-compatible HTTP API or a Python library. It came out of UC Berkeley's Sky Computing Lab in June 2023 and is the most widely used open-source LLM server. Its founding idea, PagedAttention, manages the GPU memory that holds each request's attention state (the KV cache) the way an operating system manages RAM: in small fixed-size pages, allocated on demand. Its launch blog reported up to 24 times the throughput of Hugging Face Transformers and up to 3.5 times that of Hugging Face's TGI server.
The problem it solves is cost. Generating text is a loop of decode steps, and each step reads all the model weights to produce one token per request. Serving one user at a time leaves most of the GPU idle; serving hundreds at once shares each weight read across all of them. How many requests fit is decided by KV-cache memory, and earlier systems reserved a contiguous buffer per request for the longest possible output, wasting 60–80% of it. vLLM wastes under 4%, so several times more requests run together on the same hardware.
In October 2026 the current release is 0.32.0 (18 October 2026), with releases about every two weeks. Since version 0.11 (October 2025) only the redesigned V1 engine remains. The project has been hosted by the PyTorch Foundation since May 2025, has more than 2,000 contributors, and runs on NVIDIA and AMD GPUs, Google TPUs, Intel and AWS accelerators. In January 2026 Ion Stoica, Woosuk Kwon and other maintainers founded Inferact, which raised $150 million to build a commercial service on vLLM. It stands on three concepts. PyTorch supplies the model definitions, weight loading, torch.compile and the distributed runtime. CUDA supplies the custom kernels: paged attention, quantized matrix multiplies, fused mixture-of-experts layers and sampling. LLM serving (L1) supplies the problem itself: prefill versus decode, batching, latency targets and goodput.
terms: KV cache — the stored attention keys and values for every token a request has processed, so each new token needs only its own computation.
Block (page) — a fixed-size chunk of KV cache holding the keys and values of 16 tokens by default.
Block table — a per-request list mapping its logical blocks (tokens 0–15, 16–31, …) to physical block numbers in GPU memory.
Prefill — processing the whole prompt in one pass; it is compute-heavy and sets time to first token.
Decode — generating one token per request per step; it is limited by memory bandwidth and sets time per output token.
Continuous batching — adding and removing requests at every step instead of waiting for a whole batch to finish.
Token budget — the maximum number of tokens the scheduler sends through the model in one step (max_num_batched_tokens).
Prefix caching — reusing KV blocks of an identical prompt prefix, found by hashing block contents.
Preemption — evicting a running request's KV blocks when memory runs out, then recomputing them later.
history: Before vLLM, LLM serving reused ideas from general model servers. NVIDIA's FasterTransformer had fast kernels but static batches. Orca (OSDI 2022, Seoul National University and FriendliAI) introduced iteration-level scheduling, the idea behind continuous batching: decide the batch again at every decoding step. But KV-cache memory was still allocated as one contiguous block per request, sized for the maximum length.
Woosuk Kwon, Zhuohan Li and colleagues in Ion Stoica's group at Berkeley saw that this was the same problem operating systems solved decades ago with virtual memory and paging. They built vLLM with PagedAttention and used it from mid-April 2023 to serve LMSYS's Vicuna chatbot and Chatbot Arena, handling an average of 30,000 requests a day and cutting the GPUs needed by half. The code was released on 20 June 2023, and the SOSP 2023 paper, "Efficient Memory Management for Large Language Model Serving with PagedAttention", reported 2–4 times the throughput of FasterTransformer and Orca at the same latency.
Adoption was fast because vLLM supported each new open model (Llama 2, Mistral, Mixtral, Qwen, DeepSeek) quickly. During 2024 it added chunked prefill, automatic prefix caching, speculative decoding, FP8 quantization, many LoRA adapters per server, and multimodal models. Contributors came from Anyscale, Neural Magic (acquired by Red Hat in early 2025), IBM, NVIDIA, AMD, Google and others.
Growth exposed CPU overhead and complexity in the original design, so the team rebuilt the core. The V1 engine (alpha in January 2025, default from 0.8 in March 2025) unified prefill and decode scheduling, moved tokenization and detokenization out of the main loop, and enabled prefix caching by default; the team reported up to 1.7 times the throughput of V0, mostly from lower CPU overhead. vLLM joined the PyTorch Foundation in May 2025, the Kubernetes-based llm-d project (launched by Red Hat, Google, IBM and others in May 2025) adopted it as its engine, and V0 was removed in October 2025.
how: Start with memory. At startup vLLM loads the weights, runs a test forward pass at the maximum batch size to measure peak activation memory, and then turns the rest of the allowed GPU memory into a pool of KV blocks. The allowed share is gpu_memory_utilization (default 0.9). For each block, the pool holds the keys and values of 16 tokens for every layer. The startup log prints the KV-cache size in tokens and the resulting maximum concurrency at full context length.
PagedAttention is how requests use the pool. Each request has a block table. When it starts, it gets just enough blocks for its prompt; each time its last block fills during decoding, it gets one more free block from anywhere in the pool. Physical blocks need not be next to each other, exactly as virtual pages in an operating system map to scattered physical frames. The only waste is the unfilled part of each request's last block, fewer than 16 token slots. The attention kernel is rewritten to follow the block table: for each query, it walks the request's blocks, loads their keys and values from wherever they are, and computes attention block by block. Blocks also carry reference counts. When several requests share a block (the same prompt prefix, or several samples from one prompt), they point to the same physical block, and a block is copied only when one of them needs to write into it (copy-on-write). The launch blog reported memory savings of up to 55% for parallel sampling and beam search from this sharing.
The scheduler runs once per step, and it is where the LLM-serving trade-off between throughput and latency is decided. In V1 there is no separate prefill phase: every request simply has some tokens that still need computing, and the scheduler fills a token budget. Running requests in decode each take one token (more with speculative decoding). The rest of the budget goes to prompt tokens of waiting or partially prefilled requests, in chunks, so a 30,000-token prompt is processed over several steps instead of blocking everyone's next token for a whole second. A new request is admitted only if enough free blocks exist. If decoding requests run out of blocks, the scheduler preempts the most recently admitted request: it frees that request's blocks and later recomputes them from its tokens. Finished requests leave at once and their blocks return to the pool, which is continuous batching.
Prefix caching makes repeated prompts cheap. Every full block gets a hash computed from its parent block's hash, its own 16 token IDs, and any extra keys (such as a LoRA adapter or image hashes). A new request looks up its blocks' hashes in order; every match is reused without computation, and prefill starts at the first miss. Freed blocks stay in the pool in least-recently-used order with their hashes, so a popular system prompt stays cached until memory is needed. Because the hash chain starts at the first token, only an identical prefix can match.
Execution is PyTorch plus custom CUDA work. vLLM has its own implementations of most popular architectures, written as PyTorch modules with vLLM's layers, and it can also run Hugging Face Transformers model code as a fallback. The model is compiled with torch.compile and captured into piecewise CUDA graphs, so a decode step launches a few graphs instead of thousands of separate kernels. Attention runs on selectable back ends (FlashAttention, FlashInfer, Triton and others) that understand block tables. Custom kernels implement quantized matrix multiplies (FP8, INT4 formats such as AWQ and GPTQ, and FP4 on Blackwell), fused mixture-of-experts layers, sampling, and a fast all-reduce. The engine core runs in its own process and talks to the API server over ZeroMQ, so tokenization, detokenization and streaming responses run in parallel with the GPU loop. A persistent batch keeps input tensors on the GPU and applies only per-step changes.
Scaling uses several kinds of parallelism. Tensor parallelism splits every layer's matrices across GPUs in one machine and all-reduces after each layer, so it needs fast links such as NVLink. Pipeline parallelism places groups of layers on different machines. For mixture-of-experts models such as DeepSeek, data parallelism for attention combined with expert parallelism spreads experts across many GPUs. Disaggregated serving runs prefill and decode on separate instances and moves KV blocks between them through connectors such as NIXL or LMCache. Around this sit speculative decoding (a small draft model, EAGLE heads, n-gram matching or the model's own multi-token prediction proposes several tokens, and one forward pass verifies them), structured output (grammar-based token masks that force valid JSON), and many LoRA adapters served on one base model.

example: Serve Llama 3.1 8B in bf16 on one 80 GB H100. The weights take about 16 GB. With gpu_memory_utilization = 0.9, vLLM may use 72 GB; after weights and about 4 GB for activations and CUDA graphs, roughly 52 GB remains for the KV pool. The model has 32 layers and 8 KV heads of dimension 128, so one token's cache is 2 × 32 × 8 × 128 × 2 bytes = 128 KB, and one 16-token block is 2 MB. The pool holds about 52 GB / 2 MB ≈ 26,600 blocks, roughly 426,000 tokens.
Compare allocation schemes for a workload whose requests average 1,000 prompt tokens and 300 output tokens, with max_model_len = 8,192. Reserving the maximum per request costs 8,192 × 128 KB = 1 GB each, so only 52 requests fit, and most of each reservation is never used. With paging, a 1,300-token request needs ⌈1,300 / 16⌉ = 82 blocks = 164 MB, with only 12 unused slots in its last block. Now about 52 GB / 164 MB ≈ 320 requests fit at once, six times more.
Why concurrency matters: a decode step must read every weight once, whatever the batch size. At about 3.3 TB/s of memory bandwidth, reading 16 GB takes at least 4.8 ms. With one request, that is about 200 tokens per second in total. With 256 requests of about 1,300 cached tokens each, each step also reads their KV cache: 256 × 1,300 × 128 KB ≈ 41 GB. The step then takes roughly (16 + 41) GB / 3.3 TB/s ≈ 17 ms and produces 256 tokens: about 15,000 tokens per second, 75 times more from the same GPU. Each user now sees about 1 / 0.017 ≈ 58 tokens per second instead of 200. That trade, much more total throughput for somewhat slower individual streams, is the central tuning decision in serving.
Finally, prefix caching. If every request starts with the same 2,048-token system prompt, those 128 blocks (256 MB) are stored once and shared, instead of once per request, and each new request skips 2,048 tokens of prefill. If prefill runs at around 20,000 tokens per second for this model on this GPU, that removes about 0.1 seconds from every time to first token, and frees that compute for other requests.
intuition: vLLM treats GPU memory like a well-run hotel: instead of reserving an entire floor for each guest in case their family arrives, it hands out one room at a time, anywhere in the building, and keeps a register of who is in which room.
The design is natural once you see that the KV cache behaves like process memory. Each request grows by one token at a time, nobody knows in advance how long it will grow, requests start and end constantly, and some share identical beginnings. Operating systems met the same pattern long ago and answered with fixed-size pages, a page table per process, on-demand allocation, shared pages with reference counts and copy-on-write. Applying that answer removes fragmentation, so the batch can grow until compute or bandwidth, not wasted memory, is the limit. Once memory is paged, the rest follows: the scheduler can admit, pause and resume requests at block granularity, and identical prefixes become identical blocks found by hashing.
mistakes: People often think PagedAttention makes the attention computation itself faster. In fact its gain is memory: less waste means larger batches, and larger batches mean higher throughput. Reading scattered blocks can be slightly slower per token than reading one contiguous buffer; the batch-size gain is far larger.
People often see that vLLM uses 90% of GPU memory while idle and conclude something is wrong. In fact it preallocates that share (gpu_memory_utilization) as the KV pool at startup. To run two engines on one GPU, or to leave room for other work, lower this value for each engine.
People often think raising max_num_seqs or max_num_batched_tokens always increases useful throughput. In fact past a certain point steps get longer, inter-token latency rises, and preemptions force KV recomputation, which wastes GPU time. Tune these against your latency targets and measure goodput, the requests that meet them.
People often expect prefix caching to reuse any repeated text. In fact it matches only an identical prefix from the first token, in whole 16-token blocks. A timestamp or user name at the start of the prompt makes every request a cache miss.
friction: Tuning is a real cost. Throughput and latency depend on the model, GPU, prompt and output lengths, and settings such as max_num_seqs, max_num_batched_tokens, tensor_parallel_size, quantization and the attention back end. The defaults are reasonable, but reaching good goodput needs load testing with realistic traffic.
Support is uneven. New model architectures, attention variants and quantization formats need new code and kernels, and support often arrives first and runs fastest on NVIDIA GPUs; other hardware works through separate back ends or plugins whose feature sets lag. With a release about every two weeks, flags, defaults and internal APIs change often, so upgrades need testing.
Startup is slow for large models: loading tens or hundreds of gigabytes of weights, running torch.compile and capturing CUDA graphs can take minutes, which hurts autoscaling and cold starts. Caching compiled artifacts and using fast storage help but do not remove the problem.
Long contexts stay expensive. KV memory grows linearly with tokens, so a few 128,000-token requests can fill a GPU, forcing smaller batches, preemptions, KV quantization or offloading to CPU memory. Running across many machines (disaggregated prefill, expert parallelism, KV transfer) adds network and operational complexity, and outputs are not bit-for-bit reproducible by default, because batch composition changes the floating-point order of operations.
practice: Start simple: vllm serve with the model name, a max_model_len no larger than your application needs, and the default settings. Read the startup log for KV-cache size and maximum concurrency, and if concurrency is low, reduce max_model_len, use FP8 weights or an FP8 KV cache (on GPUs that support it, after checking accuracy), or add GPUs with tensor parallelism inside one NVLink machine.
Benchmark before tuning, using vllm bench serve or your own load generator with your real distribution of prompt and output lengths. Set targets first (for example p95 time to first token under 1 second and inter-token latency under 50 ms), then adjust max_num_seqs and max_num_batched_tokens to maximize requests meeting them. Watch the Prometheus metrics: running and waiting requests, KV-cache usage, preemptions, prefix-cache hit rate, time to first token and inter-token latency. Rising preemptions mean memory is the bottleneck.
Design prompts for the cache: put fixed content (system prompt, tool definitions, shared documents) first and variable content last, and route requests that share prefixes to the same replica (llm-d and other prefix-aware routers do this). Use speculative decoding when you serve few concurrent users and care about per-user speed, since it uses spare compute; at high concurrency it helps less. Pin the vLLM version and model revision in production, keep a regression benchmark, and upgrade deliberately.
quiz: What problem does PagedAttention solve, and how? || It removes KV-cache memory waste from reserving one contiguous, maximum-size buffer per request. It stores each request's cache in fixed 16-token blocks allocated on demand anywhere in GPU memory, tracked by a per-request block table.
Why does fitting more concurrent requests raise decode throughput so much? || Each decode step reads all model weights whatever the batch size, and decode is limited by memory bandwidth. A larger batch shares that read across more requests until KV reads or compute become the limit.
How does vLLM find a reusable prompt prefix? || Each full block is identified by a hash of its parent block's hash and its own token IDs (plus extra keys such as the LoRA adapter). A new request looks up its block hashes in order and reuses every match, starting prefill at the first miss.
A model needs 64 KB of KV cache per token and the KV pool is 40 GB. How many 16-token blocks fit, and how many 2,000-token requests can run at once? || A block is 16 × 64 KB = 1 MB, so about 40,960 blocks fit. A 2,000-token request needs 125 blocks, so about 327 requests fit at once.
A chat product has a 3,000-token system prompt and strict per-user latency targets. What would you use and watch? || Put the system prompt first so prefix caching shares it, keep chunked prefill so long prompts do not stall decodes, and try speculative decoding if concurrency is low. Watch prefix-cache hit rate, preemptions and p95 inter-token latency.
