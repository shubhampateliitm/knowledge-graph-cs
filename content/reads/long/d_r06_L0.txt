@@ avro
value: Avro and Protocol Buffers (Protobuf) are two ways to turn a structured record into a small block of bytes and back, using a schema that both sides agree on. JSON would send the field names with every record, as text. A schema-based format sends only the values, in a compact binary form. For a record with an id, a name and an optional email, the JSON text is about 34 bytes, while the Avro encoding is 6 bytes and the Protobuf encoding is 7 bytes. When a Kafka cluster carries billions of messages a day, that difference is a real part of the network, disk and cost.
Size is only half of the reason. The other half is change. A record format lives for years, and producers and consumers are deployed at different times by different teams. Both formats solve this with rules: a field can be added or removed, and old and new code can still read each other's data, as long as the rules are followed. Avro does this by comparing a writer schema with a reader schema. Protobuf does it by giving every field a permanent number. These rules are what the L2 concept schema evolution describes; Avro and Protobuf are the products that make it concrete.
For the layer above, Avro is the default message format of many Kafka deployments and the format of the manifest files in Apache Iceberg and of data in older Hadoop pipelines. Protobuf is the standard format of gRPC services and is very common on Kafka as well. Two lower concepts give them their value. Schema evolution (L2) provides the compatibility rules: which changes are safe, and in which direction. Remote procedure calls and serialization (L3) provide the basic problem both formats solve: turning in-memory objects into bytes that another process, perhaps in another language, can read. A schema registry (a separate L0 concept) then stores the schemas so the bytes do not need to carry them.
terms: Schema — a formal description of a record: its field names, types and order. In Avro it is a JSON document; in Protobuf it is a .proto file.
Writer schema and reader schema — the schema used when the data was written, and the schema the reading program expects. Avro resolves one against the other at read time.
Field number (tag) — in Protobuf, the permanent integer that identifies a field on the wire. The name is never sent.
Varint — a way to write an integer in 1 to 10 bytes, using 7 bits of the number per byte; small numbers take one byte.
Zigzag encoding — a trick that maps signed integers to unsigned ones (0, −1, 1, −2 become 0, 1, 2, 3) so that small negative numbers also take one byte as a varint.
Union — in Avro, a field that can hold one of several types, written as a list such as ["null", "string"]; this is how optional fields are expressed.
Backward compatible — new readers can read old data. Forward compatible — old readers can read new data. Full compatibility means both.
Object container file — an Avro file that stores the schema once in its header, then many records in compressed blocks separated by sync markers.
history: Protocol Buffers came first. Google built them for internal use in the early 2000s, because XML was too big and too slow for the messages its servers exchanged all day. Google released them as open source in July 2008 (this is the "proto2" language). Proto3, a simpler version, came in 2016 and became the language used by gRPC, which Google released in 2015.
Avro was started by Doug Cutting, the creator of Hadoop, and announced in 2009 as a Hadoop subproject. The reason was practical. Hadoop used its own Writable classes for data, which worked only in Java, and Protobuf and Thrift needed code generation and a fixed number for every field. Cutting wanted a format that was language neutral, that stored its schema next to the data, and that worked well with dynamic languages where generating code is awkward. Avro became a top-level Apache project in 2010. Its schemas are written in JSON, so any language with a JSON parser can read them.
The next step came from Kafka. LinkedIn used Avro for its event data, and the engineers who built Kafka found that the schema could not travel with every message, since that would remove the size benefit. Confluent, a company formed by the Kafka creators, released a schema registry in 2014 so that a message carries only a small schema ID. Over the following years Confluent added Protobuf and JSON Schema support to the registry (in 2020), and Protobuf became a common Kafka format too.
Avro found a second life in the lakehouse. When Iceberg was designed at Netflix, its manifest lists and manifest files were defined as Avro files, because Avro keeps the schema in the file and handles schema evolution well. Hudi also writes Avro blocks into its log files. So today Avro is both a streaming format (row by row) and a metadata format inside table formats, while analytical data itself is stored in columnar formats such as Parquet.
how: Start with the problem that both formats solve: a program has an object in memory, with fields of different types, and must produce a byte array that another program can read. The layer below (serialization and remote procedure calls) says that both sides need to agree on the layout. The simplest agreement is a schema. Once the schema is shared, the bytes do not need to describe themselves.
Avro takes this to the extreme. A record is written as its field values one after another, in the order the schema lists them, with no field names, no tags and no separators. An int or long is written as a zigzag varint: the value is mapped with (n << 1) XOR (n >> 63), then written 7 bits at a time, with the high bit of each byte saying "more bytes follow". So 3 becomes 6, which is one byte, 0x06; −1 becomes 1; 300 becomes 600, which is two bytes, 0xD8 0x04. A string is a length (as a long) followed by UTF-8 bytes. A boolean is one byte. A float is 4 bytes and a double is 8 bytes. An array is written as blocks, each with a count and its items, ending with a block of count zero. A union is written as the index of the chosen branch (a long) and then the value, so a null in ["null", "string"] costs one byte. A null by itself costs zero bytes.
Because the bytes carry no names, a reader cannot decode them without a schema, and it must use the exact schema the writer used, or a schema it can resolve against it. This is Avro's central rule. When the reader has its own schema (the reader schema) and knows the writer schema, Avro performs schema resolution. Fields are matched by name (or by alias). A field that exists in the writer but not in the reader is read and discarded. A field that exists in the reader but not in the writer takes its default value, and if it has no default, resolution fails. Some types may be promoted: int can be read as long, float or double, and string and bytes can be read as each other. Reader and writer can therefore differ in many ways and still work. This is exactly the compatibility behaviour that schema evolution (L2) requires: adding a field with a default is backward compatible; removing a field that has a default is forward compatible; renaming a field needs an alias.
Where does the writer schema come from? Avro has three answers. In a file (object container file) the schema is stored once in the header, followed by blocks of records with a 16-byte random sync marker between them, so a big file can be split and processed in parallel, and each block can be compressed (deflate, Snappy, zstandard and others). In a single message, the "single-object encoding" puts a two-byte marker and an 8-byte fingerprint of the schema in front of the data, and the receiver looks the schema up by that fingerprint. In Kafka the common answer is the Confluent wire format: a zero "magic" byte, a 4-byte schema ID from the schema registry, and then the Avro bytes. The registry holds the full schema, so each message pays only five bytes of overhead.
Protobuf makes the opposite choice. Every field has a number in the .proto file, and each value is written with a tag: (field_number << 3) | wire_type, as a varint. The wire type says how to read the value: 0 for a varint, 1 for 8 fixed bytes, 2 for a length-delimited value (strings, bytes, nested messages) and 5 for 4 fixed bytes. The reader does not need the writer schema to find where each value ends, because the tag tells it the wire type. If the reader sees a field number it does not know, it can skip the value, and recent versions keep the unknown bytes and write them back. Fields can come in any order, and a field with its default value can be left out (in proto3, a plain field set to 0 or empty is not written at all). So adding a new field with a new number is safe, and removing one is safe if the number is never reused. The cost is one or more extra bytes per field for the tag.
Both formats generate code. Protobuf's compiler (protoc) creates classes in Java, C++, Go, Python and many other languages from the .proto file, and gRPC adds service stubs on top. Avro can generate classes too, but it also has a "generic" mode: a program can read data using just the schema, as maps and lists, which is useful for tools such as Kafka Connect, Spark and Flink that process many different schemas. Avro also defines its own RPC protocol and an IDL, though in practice this is rarely used compared with gRPC.
In summary: Avro keeps the format minimal and moves the cost into schema management (you must always find the writer schema). Protobuf keeps the data self-skippable and moves the cost into permanent field numbers (you must never change the meaning of a number). The compatibility rules from schema evolution tell you which changes are safe for each.

  +------+------+---+---+---+------+

  +------+------+------+------+---+---+---+

   field1        field2
   varint        bytes

  JSON text                                  34 bytes
  {"id":3,"name":"Ann","email":null}

  Kafka message with a schema registry:
  [0x00][schema ID: 4 bytes][ Avro bytes ... ]
example: Use this schema for version 1 of a user event: record User with fields id (long) and name (string). Take the user id=3, name="Ann". Avro writes the id first. The long 3 is zigzag-mapped to 6, which fits in one byte, 0x06. Then the string: its length 3 is mapped to 6, so 0x06, followed by the UTF-8 bytes 0x41 0x6E 0x6E. Total: 5 bytes. The same event as JSON is {"id":3,"name":"Ann"}, 21 bytes.
Now the team adds an optional email. Version 2 of the schema adds the field email with type ["null", "string"] and default null. The new record id=3, name="Ann", email=null is written as the same 5 bytes plus one byte 0x00 for the union branch "null". Six bytes in total.
Check the compatibility with a pen. Case 1: a new consumer (reader schema v2) reads an old message (written with v1). The bytes have only id and name. The resolver sees that email is missing in the writer schema, uses the reader default null, and succeeds. This is backward compatibility. Case 2: an old consumer (reader v1) reads a new message (written with v2). The resolver reads id and name, sees that email exists in the writer but not in the reader, reads the union branch and the value, and discards it. This is forward compatibility. Because the new field has a default, the change is fully compatible, and a registry set to FULL would accept it.
Now a bad change. Version 3 adds a field country of type string with no default. Case 1 now fails: a v3 reader reading v1 data has no value to put in country. A registry with BACKWARD compatibility rejects this schema at registration time, before any producer can use it. That is the whole point of putting the check there.
Next, the Protobuf view of version 2. The .proto file has int64 id = 1; string name = 2; and now string email = 3. An old reader that gets field 3 does not know the number and skips it by its wire type (2, length-delimited), so no code change is needed. If someone later deletes email and, a year later, adds a different field as number 3 with an int type, old data with a string in field 3 would be decoded as garbage or fail. This is why the rule is: write reserved 3; when you remove a field, so the compiler stops anyone from reusing the number.
Finally, the cost at scale. Suppose a Kafka topic receives 50,000 events per second and each event is 300 bytes as JSON. That is 15 MB/s, or about 1.3 TB per day, before replication. If Avro cuts each event to roughly 90 bytes (names removed, numbers as varints, timestamps as 8-byte longs instead of ISO strings), the same stream is 4.5 MB/s, about 390 GB per day. With replication factor 3 and 7 days of retention, you save roughly 19 TB of disk. The exact ratio depends on the data, and text-heavy events shrink much less than numeric ones, but a 2× to 4× reduction is typical.
intuition: Two people who have the same form in front of them can talk in short numbers ("box 3: yes") instead of full sentences, as long as they both have the same version of the form.
Everything in the design follows from one choice: where does the description of the data live? JSON puts it inside every message, which is simple and wasteful. Avro puts it in a schema that is stored once, in a file header or a registry, and the message is only values. Protobuf splits the difference: the message carries a small number per field, which is enough to skip fields it does not understand. So Avro gives the smallest bytes and needs a schema lookup at read time. Protobuf gives slightly larger bytes and can always be partly read. Both are natural answers to the same question, and the compatibility rules are the contract that makes the choice safe over years.
mistakes: People often think Avro data is self-describing like JSON. In fact the bytes of a single Avro record contain no names or types at all. Only the object container file (which stores the schema in its header) is self-describing. For a Kafka message you must find the writer schema, normally by the ID in the first five bytes. If the registry is lost, the data cannot be decoded.
People often think Avro and Protobuf are interchangeable because both use schemas. In fact their evolution models differ. Avro resolves names and defaults between two schemas at read time, so a rename needs an alias and a removed field needs a default. Protobuf identifies fields only by number, so a rename is free (the name is not on the wire), but changing a number or reusing a removed one corrupts data silently. Always follow the rules of the format you use.
People often think that adding a field is always safe. In fact it is safe only in the right direction. In Avro, a new field without a default breaks backward compatibility. In Protobuf, changing the type of an existing field number (for example int32 to string) breaks every reader, and some type changes (int32 to int64) are compatible only in some languages.
People often think Protobuf "optional" and "required" work the same in all versions. In fact proto3 originally removed field presence for plain scalars, so a field set to 0 could not be told apart from a missing field; "optional" was added back in 2020 to restore presence tracking. Proto2 "required" fields are considered harmful because they can never be removed safely.
People often think that smaller bytes always mean faster processing. In fact both formats must still be decoded into objects, and a varint decode takes more CPU than reading a fixed-width integer. Formats designed for zero-copy reading, such as FlatBuffers or Cap'n Proto, trade size for speed. For analytical queries over many rows, a columnar file such as Parquet beats both row formats.
tradeoffs: Choose Avro when the data flows through Kafka, Hadoop-era tools, Spark or Flink, and you want the smallest messages plus a schema registry that enforces compatibility. Avro's generic reader (no code generation) makes it easy to build tools that handle many schemas. You give up self-skipping: a reader without the writer schema cannot decode anything, and every consumer depends on the registry being available.
Choose Protobuf when the same schema is also used for gRPC service calls, when many programming languages need generated and typed classes, or when you want readers to survive unknown fields without a registry lookup. Messages are a little larger than Avro (a tag byte per field), and the numbering discipline is strict. For Kafka, Confluent's registry supports Protobuf, so the choice rests more on your ecosystem than on the broker.
Choose JSON (with JSON Schema if you need rules) when humans and browsers read the data directly, volumes are small (below a few thousand messages a second), and being able to run curl and read the answer matters more than a 3× size cost. Choose a columnar format (Parquet, ORC) instead when the main access is analytical scans: Avro and Protobuf are row formats, and reading one column still requires decoding the whole row.
Choose strict compatibility (FULL or FULL_TRANSITIVE) when many independent teams consume a topic and you cannot control deployment order. Choose BACKWARD (the Confluent default) when you can always upgrade consumers before producers. Stricter rules give safer evolution and fewer allowed changes; teams that need to remove or retype fields will have to create a new topic or a new subject version and migrate.
friction: The hardest problems are not in the bytes but in the organization. Someone must own each schema, review changes and decide the compatibility mode. Without process, teams find out about a breaking change when a consumer crashes at 3 a.m. Tools such as a registry with enforced checks and CI jobs that test every schema change against the previous version are the usual answer.
Avro has some sharp corners. Unions are awkward: a nullable field is a two-branch union, a default must match the first branch of the union (so ["null","string"] with default null works, but ["string","null"] with default null does not), and generated code for unions can be unfriendly. Logical types (dates, decimals, UUIDs, timestamps) are stored as annotations on a base type, and different language libraries have supported them to different degrees. Schema resolution costs CPU when reader and writer schemas differ, and good libraries cache the resolver per schema pair.
Protobuf has its own traps. Map and repeated fields have no ordering guarantees across languages in all cases; the default-value behaviour of proto3 makes "not set" and "zero" look the same unless you use optional or wrapper types; and the binary encoding is not canonical, so two correct encoders can produce different bytes for the same message, which breaks naive hashing and comparison. Large messages (above a few megabytes) are not designed for streaming, because the parser needs the whole message.
Finally, neither format helps with the meaning of data. A change from "amount in dollars" to "amount in cents" keeps the type long and passes every compatibility check, yet breaks every consumer. Schema compatibility is a check on structure, not on semantics.
practice: Pick one format per platform and stay with it. Typical choice: Avro with a registry for Kafka event streams, Protobuf for service-to-service calls with gRPC, Parquet for analytical storage. Mixing formats on one topic is possible but costs tooling.
Write schemas for evolution from day one. In Avro, give every field that might ever be removed a default, make optional fields unions with null (null first) and default null, and use aliases for renames. Prefer adding new fields over changing old ones. In Protobuf, never change or reuse a field number, mark removed numbers and names as reserved, avoid required, and use optional or wrapper types when you must tell "zero" from "not set". Use enums with an explicit zero value such as UNKNOWN, since new enum values will arrive at old readers.
Automate the check. Put the schemas in a repository, run a compatibility check in CI against the registry (or with a tool such as buf for Protobuf), and let the registry enforce the same mode at registration time. Pick the compatibility mode from your deployment reality: if consumers can lag producers, you need FORWARD or FULL; if you may replay old data from a topic with long retention, you need BACKWARD_TRANSITIVE or FULL_TRANSITIVE, so every old version stays readable.
Keep events small and flat: use IDs and facts, not whole nested objects, and avoid putting large blobs in messages. Compress batches at the Kafka producer level (zstd or lz4), since Avro and Protobuf remove field names but not repeated values. For lake storage, write Avro only for row-oriented staging or metadata; convert to Parquet for analytics. Test with real old data: replay a sample of last month's messages against the new schema before you deploy it.
interview: Why can Avro omit field names and tags, and what does it cost? || Because the reader always has the writer's schema (from the file header or a registry ID) and decodes fields in schema order, so names are redundant. The cost is that bytes cannot be decoded without the right schema, so the registry or file header becomes a hard dependency, and any mismatch decodes garbage or fails.
A producer adds a required field to an Avro schema and the registry accepts it, but consumers crash. What happened and how do you prevent it? || The compatibility mode was probably NONE, or FORWARD only, so a field without a default was allowed; consumers on the old schema or replaying old data cannot fill it. Prevent it with BACKWARD or FULL (transitive if old data is replayed), defaults on every new field, and a CI check against the registry before merge.
Explain how Protobuf lets an old reader accept a message from a newer writer. || Each value is preceded by a tag containing the field number and a wire type. An old reader finds a number it does not know and uses the wire type to know how many bytes to skip (varint, fixed, length-delimited). Modern versions also keep the unknown bytes so that re-serialization does not lose them.
When would you pick Protobuf over Avro for Kafka, and when the reverse? || Protobuf if the same message types are used in gRPC and you want typed classes in many languages. Avro if the data goes to Spark, Flink, Hadoop tools or Iceberg-style pipelines, where generic (code-free) reading and the container file format matter. Either way, use a registry.
How would you handle a semantic change, such as an amount moving from dollars to cents, when compatibility checks pass? || Do not change the meaning of an existing field. Add a new field (amount_cents) and deprecate the old one, run both for a period while consumers migrate, and then stop writing the old one. For a hard break, create a new topic or new schema subject version and migrate with a dual-write or a conversion job.
quiz: What is the Avro encoding of the long 3 and why does it take only one byte? || Zigzag maps 3 to 6, and a varint writes 6 in one byte (0x06) because the value fits in 7 bits. Small numbers of either sign take one byte.
Why does a Protobuf reader survive an unknown field while an Avro reader needs the writer schema? || Protobuf puts the field number and wire type in front of every value, so unknown values can be skipped by length. Avro writes no tags, so the reader needs the writer schema to know how to decode each value.
A topic has Avro schema v1 with fields id and name. A producer registers v2 that adds email as a plain string with no default. Which compatibility modes accept it? || Only FORWARD (and NONE). Old readers ignore the new field, but new readers cannot read old data because email has no default, so BACKWARD and FULL reject it.
A Kafka event averages 300 bytes as JSON and 90 bytes as Avro, at 50,000 events per second. How much data do you save per day before replication? || The difference is 210 bytes × 50,000 = 10.5 MB/s, about 907 GB per day. That is roughly 0.9 TB per day of network and disk, multiplied by the replication factor in the cluster.
Why not store analytical data as Avro files instead of Parquet? || Avro is a row format, so a query that needs two columns must still read and decode every column of every row, and it has no per-column statistics or dictionary encoding. Parquet lets the engine read only the needed columns and skip row groups.

@@ schemareg
value: A schema registry is a small service that stores the schemas of the messages in a streaming system, gives each schema a number, and refuses any new schema that would break the programs already reading the data. The best known one is Confluent Schema Registry, created for Apache Kafka in 2014. Without it, a team that renames a field in its producer can crash every consumer of a topic at the next deployment, and often the first sign is an error in someone else's dashboard.
The registry solves two separate problems with one mechanism. First, a compact format such as Avro cannot be decoded without its schema, and sending the schema with each message would remove the size benefit. So each message carries only a 4-byte schema ID, and the receiver asks the registry for the schema once and remembers it. Second, someone has to decide whether a change is safe. The registry runs a compatibility check at registration time: before any producer can use the new schema, the registry compares it with the earlier versions under a rule such as BACKWARD or FULL, and answers with an error if the change is unsafe. The check happens early and in one place, not in production at 3 a.m.
For the layer above (Kafka Connect, ksqlDB, Flink and Spark jobs, data catalogs, and "data contract" practices between teams), the registry is the place where the shape of every stream is written down and versioned. Two lower concepts matter. Schema evolution (L2) provides the compatibility rules the registry implements: which changes are safe and in which direction. Apache Kafka (L0) provides the transport and also the storage: the registry keeps its own data in a compacted Kafka topic, and its IDs travel inside Kafka messages. Avro, Protobuf and JSON Schema supply the schema languages it understands.
terms: Subject — the name under which a series of schema versions is stored; by default it is the topic name plus "-key" or "-value", for example orders-value.
Version — the sequence number of a schema inside one subject (1, 2, 3, …). Registering an identical schema again returns the existing one.
Schema ID — a global integer that the registry assigns to each distinct schema; this is the number written inside every message.
Compatibility mode — the rule used when a new version is registered: BACKWARD, FORWARD, FULL, their TRANSITIVE variants, or NONE.
Transitive — the new schema is checked against all earlier versions of the subject, not only the latest.
Magic byte — the first byte of a message in the Confluent wire format, always 0, which tells the deserializer that a schema ID follows.
Subject naming strategy — the rule that maps a message to a subject: by topic, by record type name, or by both.
Data contract — a schema plus extra rules and metadata (ownership, quality rules, tags) that producers promise to follow and consumers can depend on.
history: Kafka was created at LinkedIn around 2010 as a way to move event data between systems. LinkedIn used Avro for its events and found that a central place for schemas was necessary, because the producers and consumers belonged to many different teams. Confluent was founded in 2014 by Kafka's creators (Jay Kreps, Neha Narkhede and Jun Rao), and its open-source Schema Registry, with a REST API, was one of the first products around Kafka. The idea of a schema ID in front of the message payload became the standard "Confluent wire format".
The first versions supported only Avro. The registry stored its state in a Kafka topic named _schemas, which let it avoid a separate database. In 2018 Confluent changed its licence for several components, and the registry moved to the Confluent Community License, which is free to use but not an open-source licence, because it forbids offering the software as a competing managed service. This pushed other groups to write compatible alternatives: Karapace (from Aiven) and Apicurio Registry (from Red Hat) are open source, Redpanda built a compatible registry into its broker, and AWS offers Glue Schema Registry for Kafka and Kinesis users.
In 2020, with Confluent Platform 5.5, the registry added Protobuf and JSON Schema as first-class formats, because many companies standardized on Protobuf for gRPC and wanted one schema story. Later releases added schema references (one schema importing another), schema linking between clusters, and, from 2023, data contracts: rules for field-level encryption, validation and migration, written next to the schema.
Over the same period the idea spread beyond Kafka. Table formats and catalogs (Iceberg, Unity Catalog) store schemas with the table, and API tools keep schemas for HTTP services. A schema registry is the streaming version of a more general idea: a versioned, checked, central description of data shapes.
how: Start with what Kafka gives. A Kafka topic is a log of byte arrays. The broker does not know or care what the bytes mean. Therefore the meaning must come from somewhere else, and a registry is that somewhere else. The registry is a separate HTTP service (several instances for availability). Its state is a log in a Kafka topic called _schemas, with one partition and log compaction, so it has a single total order of all changes. Every instance reads this topic and keeps the full set of schemas in memory. One instance is elected the primary, and only the primary writes to the topic; other instances forward write requests to it. Reads are served by any instance.
Registration works like this. The producer's serializer takes a message and finds its subject name using the naming strategy. With the default TopicNameStrategy, a value written to the topic orders gets the subject orders-value. The serializer sends the schema text to the registry (POST /subjects/orders-value/versions). The registry normalizes the schema, checks whether the same schema already exists in the subject (if so, it returns the existing ID), and otherwise runs the compatibility check. For Avro this uses Avro's own resolution rules, run in the direction the mode requires; for Protobuf and JSON Schema the registry has its own rule sets. If the check passes, the registry assigns the next version number in the subject and a global schema ID (the same schema text in two subjects gets the same ID), and writes it to the _schemas topic. If the check fails, it returns HTTP 409 with a message that says what is incompatible.
Then the serializer writes the message. The Confluent wire format is: one byte 0 (the magic byte), then the 4-byte schema ID in big-endian order, then the payload, for example Avro bytes. For Protobuf there is one more small section after the ID, listing which message type inside the file is used. The overhead is 5 bytes per message. The serializer caches the schema-to-ID mapping, so the registry is called once per schema per client, not once per message.
The consumer does the reverse. The deserializer reads the first byte, checks that it is 0, reads the 4-byte ID, and looks it up in a local cache. On a miss it calls the registry (GET /schemas/ids/{id}) and caches the answer forever, since an ID never changes meaning. Then it decodes the payload using that writer schema, and, for Avro, resolves it against the reader schema the application uses. After a short warm-up, the registry is out of the data path. This is why it can serve many thousands of clients from a few instances, and why a short registry outage does not stop running producers and consumers, but does stop new ones from starting and new schemas from being registered.
Now the compatibility modes, which are the heart of the product. The definitions are always about a new schema compared with the older ones, and "reader" and "writer" are as in Avro. BACKWARD (the default): consumers using the new schema can read data written with the previous schema. Allowed changes: delete fields, add fields with defaults. Upgrade consumers first. FORWARD: consumers using the previous schema can read data written with the new schema. Allowed: add fields, delete fields that had defaults. Upgrade producers first. FULL: both directions. Allowed: add or delete only fields that have defaults; the order of upgrades does not matter. Each has a TRANSITIVE variant that compares with every earlier version, not only the last. NONE disables the check. Choosing the mode is choosing which party is allowed to move first, which is why the schema evolution concept (L2) is the foundation here.
Subjects can have their own mode that overrides the global one, and there are administrative modes: READONLY (no new schemas) and IMPORT (used when migrating schemas from another registry while keeping their IDs). In production, clients should be set not to register schemas automatically (auto.register.schemas=false) and use the latest registered version, so that only a controlled CI step registers schemas, and an application bug cannot create a new version.
Newer features build on the same base. Schema references let a schema import another subject's schema. Data contracts add rules, such as "this field must match a regular expression", "encrypt this tagged field", or "move records from major version 1 to 2 with a migration expression". Broker-side schema validation (a commercial feature in Confluent Server) lets the broker reject messages whose schema ID is not valid for the topic, which closes the gap that a plain Kafka broker accepts any bytes.

example: Take a topic orders with subject orders-value and compatibility BACKWARD. Version 1 is a record with two fields, id (long) and amount (double). The producer registers it, and the registry returns schema ID 1. Every message now begins with the five bytes 00 00 00 00 01.
The team wants to record the currency. Version 2 adds currency (string) with default "USD". The producer registers it. The registry checks that a reader with schema 2 can read data written with schema 1: the field currency is missing in the old data, and it has a default, so the check passes. Version 2 gets schema ID 2, and new messages start with 00 00 00 00 02. Old messages in the topic, which start with ID 1, are still readable by new consumers, which fetch schema 1 from the registry and resolve it against schema 2, filling currency with "USD".
A developer then proposes version 3 that adds region (string) with no default. The registry compares version 3 as reader with version 2 as writer. Old data has no region, the reader needs a value, and no default exists, so the check fails. The registry returns HTTP 409 and the message "Schema being registered is incompatible with an earlier schema". The change never reaches production. The developer fixes it by adding a default of "unknown", and registration succeeds as version 3 with ID 3.
Now see why transitive matters. Suppose the team instead proposes version 3 as: currency without its default (it becomes required). Non-transitive BACKWARD checks version 3 against version 2 only. Every message written with version 2 contains currency, so version 3 can read all of them, and the check passes. But the topic still holds version 1 messages (retention is 30 days), and version 3 cannot read them, because they have no currency and there is no default. A consumer that replays the topic from the start will fail on the first old message. With BACKWARD_TRANSITIVE the registry compares with versions 1 and 2, finds the problem, and rejects the change.
Last, the numbers. A producer sends 20,000 messages per second. The overhead from the schema ID is 5 bytes × 20,000 = 100 KB/s, about 8.6 GB per day, which is small. Without a registry, if each message carried a 400-byte JSON schema, it would be 8 MB/s, about 690 GB per day. Registry traffic is tiny: one POST per producer start and one GET per consumer per schema. A cluster with 500 consumers and 50 schemas sees at most a few tens of thousands of requests at a mass restart, then nearly nothing.
intuition: A contract office for data: you cannot start sending a new kind of message until the office has checked that it will not break the people who already receive the old kind.
The design works because it separates two things that change at different speeds. Messages are sent millions of times, so they must carry almost nothing. Schemas change a few times a month, so they can live in a central place and be checked carefully. The ID is a short pointer that joins the fast path and the slow path. Because an ID always refers to the same schema, caches never need invalidation. And because the check happens when a schema is registered, the cost of mistakes is moved from runtime, where they are expensive and hard to trace, to review time, where they are cheap.
mistakes: People often think the registry sits in the path of every message. In fact clients cache schemas by ID, so the registry is called only when a client sees a new schema. A short outage hurts only new clients and new schema registrations. But the registry must still be highly available, because a cold start of a large consumer group needs it.
People often think the Kafka broker enforces the schema. In fact the broker stores bytes and checks nothing. Enforcement happens in the client serializer and in the registry's registration check. A producer that does not use the registry serializer can write anything to the topic. Only broker-side validation (commercial) or strict access control closes this gap.
People often think "compatible" means "the application keeps working". In fact the check only covers structure. Changing the meaning of a field, such as dollars to cents, passes every mode. Compatibility modes also depend on the direction: BACKWARD does not protect old consumers from new producers; FORWARD does. Teams that choose BACKWARD but deploy producers first will see consumer failures.
People often think each topic has one schema. In fact a topic can hold several record types (with RecordNameStrategy or TopicRecordNameStrategy), which is common for event sourcing where one topic carries all events of an entity. Compatibility is then checked per record type, not per topic.
People often think the schema ID is a version number. In fact the ID is global across the registry, while the version is per subject. The same schema text registered under two subjects gets one ID but may be version 1 in one and version 5 in the other.
tradeoffs: Choose BACKWARD compatibility when you control deployment order and consumers are upgraded before producers, or when you replay old data often and want new code to read all of it (use the transitive form with long retention). Choose FORWARD when many unknown consumers exist and producers must be upgraded first, as in an event platform. Choose FULL (transitive) when many teams deploy independently with no order. The cost of strictness is that you can only add and remove fields that have defaults, and a real breaking change needs a new subject or topic.
Choose a managed registry (Confluent Cloud, AWS Glue, Redpanda) when you do not want to run another critical, highly available service and the licence terms and cost fit; choose a self-hosted open-source one (Karapace, Apicurio) when you need the Apache 2.0 licence, want to run it near your own brokers, or need extra backends (Apicurio can store schemas in SQL). Choose Confluent's own registry when you use its other features: data contracts, schema linking, broker-side validation. Check API compatibility of the alternative with your clients before you commit, since all of them implement the Confluent REST API but differ at the edges.
Choose auto-registration (clients register schemas on first use) for development and prototypes, where speed matters. Choose registration in CI, with auto.register.schemas=false and use.latest.version=true, in production, where a schema change should be a reviewed event. The cost is a deployment step and a dependency between your pipeline and the registry.
Choose a registry-less design (embedded schemas in Avro files, or JSON with no schema) only for a small system with one team, where the overhead of another service and the discipline it forces are bigger than the risk. Once there are more than a handful of producers, shared topics or long retention, the registry pays for itself.
friction: The registry is one more critical service. If it is down, new producers and consumers cannot start, and deployments that register schemas fail. It needs several instances, monitoring, backups of the _schemas topic and careful handling of the primary election. Because it stores its state in a single-partition Kafka topic, it has a hard ceiling on writes, which is rarely reached but means that auto-registration of thousands of generated schemas is a bad idea.
Schema IDs are tied to one registry. If you migrate to another registry, or mirror a topic to another cluster, the IDs inside the messages must still resolve, so you need IMPORT mode or schema linking to keep the same IDs. Many cross-cluster replication incidents come from message bytes that point to IDs the target registry does not have.
The licensing situation is a real strategic issue. Confluent's registry is source-available, not open source, and the alternatives follow the Confluent API with small differences, such as how they treat references, normalization or contexts. Organizations that want to avoid lock-in need to test their client libraries against the alternative.
The deeper difficulty is organizational. A registry makes breaking changes visible, but it does not decide who owns a schema, who is told when it changes, or how long a deprecated field stays. Compatibility checks are also limited to structure: they cannot see unit changes, new null patterns, or changed business meaning. Data contracts with rules and ownership metadata try to fill this gap, but they add more things to maintain.
practice: Decide four things before you create the first topic: the format (Avro or Protobuf), the naming strategy (TopicNameStrategy is the simple default; use RecordNameStrategy for multi-type topics), the global compatibility mode (BACKWARD or FULL is typical; use the transitive variant if you keep data for a long time or replay), and who is allowed to register schemas. Set the global mode explicitly instead of relying on the default, and set it per subject when a topic differs.
Put schemas in a Git repository next to the producer code. In CI, call the registry's compatibility endpoint (POST /compatibility/subjects/{subject}/versions/latest) for each changed schema, and fail the build on an error. Register the schema in the deploy pipeline, not inside the running application. Keep field defaults on everything that might be added or removed. Use a dedicated service account with write access for the pipeline and read-only access for everyone else.
Run the registry with at least two or three instances behind a load balancer, with the _schemas topic at replication factor 3 and min.insync.replicas of 2, and monitor the instance count, request latency and the primary. Back up the schemas, for example by exporting them regularly through the REST API. When you mirror topics between clusters, plan for the schema IDs from day one: use schema linking, or import the schemas with the same IDs.
For debugging, learn to read the first five bytes of a message. If a consumer fails with an error about an unknown magic byte, the producer did not use the registry serializer. If it fails with "schema not found", the ID points to a schema the registry does not have, which usually means a different registry or environment. Treat schema changes like database migrations: small, reviewed, and reversible by a following change, never edited in place.
interview: Why is the schema ID stored in the message rather than the schema name or version? || The ID is global and immutable: it always means exactly one schema text, so consumers can cache it forever without invalidation. A name or version is ambiguous without the subject, and a "latest" lookup could change between write and read. A 4-byte ID keeps the per-message cost to 5 bytes.
What happens to running producers and consumers if the registry goes down for ten minutes? || Running clients keep working because they have cached the schemas they use. What fails is anything that needs a lookup: new consumers or restarts, producers that register a new schema, and consumers that meet an unseen ID. So the effect is on deployments and scaling, not on steady-state traffic.
Explain BACKWARD vs FORWARD vs FULL in terms of who must upgrade first. || BACKWARD means new consumers can read old data, so upgrade consumers first, then producers. FORWARD means old consumers can read new data, so upgrade producers first. FULL allows either order, at the price of only allowing changes to fields that have defaults.
A consumer group replays a topic from offset 0 and fails halfway on a deserialization error, though the registry accepted every schema. How can that happen? || The subject used a non-transitive mode, so each version was checked only against its predecessor, and a later schema is not compatible with the oldest messages. The fix is to use a transitive mode, retain a compatible read path, or write a one-time migration, and in future check changes against all versions.
How would you migrate a Kafka topic with Avro data from one registry vendor to another? || Preserve the schema IDs, because they are inside the messages. Export subjects with their versions and IDs, import them into the target in IMPORT mode (or use schema linking), verify with a sample consumer, then switch the clients' registry URL. Never re-register schemas freshly, as that would assign new IDs.
quiz: What are the five bytes at the start of a Confluent-format message? || One magic byte with value 0, followed by the 4-byte big-endian schema ID that identifies the writer schema in the registry.
Why can clients cache a schema by ID forever? || Because an ID is assigned once and always refers to the same schema text; the registry never changes it. So there is nothing to invalidate.
A subject has BACKWARD compatibility. Which change is rejected: adding a field with a default, deleting a field, or adding a field with no default? || Adding a field with no default. A new reader cannot fill that field when reading old data. Adding with a default and deleting a field are both allowed under BACKWARD.
A producer sends 20,000 messages per second. How many bytes per day does the schema-ID overhead use? || 5 bytes × 20,000 × 86,400 seconds ≈ 8.6 GB per day, which is small compared with embedding a schema in each message.
You run a company-wide event bus with many independent teams and 30 days of retention. Which mode would you set and what do you give up? || FULL_TRANSITIVE: any version can read and be read by any other, so deployment order does not matter and replays are safe. @@ iceberg
value: Apache Iceberg is an open table format: a specification for keeping a table, with a schema, partitions, snapshots and transactions, in a set of immutable files on cheap object storage such as Amazon S3. The data lives in Parquet files. Iceberg adds a tree of small metadata files that says exactly which data files belong to the table at each moment. Because the list of files is explicit, an engine does not have to list directories on S3 (slow, and once not even consistent), and two engines can read and write the same table safely.
The problem it solves was real at Netflix, where it started in 2017. With Hive-style tables, a table was a directory tree and a partition was a sub-directory. A query had to list the directories to find files. A job that rewrote a partition could be seen half done by a reader. Changing the partitioning meant rewriting the whole table. Renaming a column could silently point to the wrong data. Iceberg replaces "a table is whatever files are in this directory" with "a table is whatever the current snapshot says", and a commit becomes one atomic swap of a pointer.
For the layer above (Spark, Flink, Trino, Snowflake, BigQuery, Athena, DuckDB and many more), Iceberg is the common table layer that lets different engines share one copy of the data. This is why it became the neutral standard of the open lakehouse. Four lower concepts matter. Parquet supplies the columnar data files, and its column statistics are copied into Iceberg's manifests so that planning can skip files without opening them. S3 supplies cheap, durable, immutable objects, and its lack of atomic multi-file operations is exactly the gap Iceberg fills. The lakehouse idea (L1) defines the goal: warehouse-like transactions and schemas on lake storage. Row lineage (L2), added in format version 3, gives each row an identity and a last-changed marker so engines can compute change feeds.
terms: Snapshot — the complete state of a table at one commit: a pointer to a manifest list. Each commit creates a new snapshot; old ones stay until they are expired.
Metadata file — a JSON file (metadata.json) holding the table's schema, partition specs, snapshot list and properties. A new one is written for every commit.
Manifest list — an Avro file that lists the manifests of one snapshot, with partition-range summaries for each manifest.
Manifest — an Avro file that lists data files (or delete files) with their partition values, row counts and per-column statistics.
Catalog — the service that stores the name of each table and a pointer to its current metadata file; it makes the commit atomic.
Hidden partitioning — partition values are computed from a column by a transform such as day(ts) or bucket(16, id), so users filter on the original column and never name a partition column.
Delete file and deletion vector — a file that marks rows of a data file as deleted without rewriting it; format v3 uses a compact bitmap called a deletion vector.
Compaction — a maintenance job that rewrites many small data files into fewer large ones.
history: Ryan Blue and Dan Weeks started Iceberg at Netflix in 2017. Netflix kept very large tables on S3 with Hive metadata, and they hit several limits: partition listings that took minutes, correctness problems when S3 listings were eventually consistent (S3 became strongly consistent only in December 2020), and no safe way to change a table. Netflix donated the project to the Apache Software Foundation in 2018. It became a top-level project in May 2020.
Two other projects were born from the same pain. Delta Lake (Databricks, 2019) solved it with a transaction log. Apache Hudi (Uber, open-sourced 2017) solved it with a timeline and record-level indexes for upserts. Iceberg's design choice was different from both: a tree of immutable snapshots with a strict written specification, independent of any engine. Having a specification, not only an implementation, let many vendors write compatible readers. Version 1 covered large analytic tables, version 2 (2022) added row-level deletes, and version 3 was adopted in 2025.
Adoption turned from slow to fast around 2022–2024. AWS Athena and Glue, Snowflake, Google BigQuery and Dremio added support; Cloudera, Starburst and others built around it. In June 2024 Databricks bought Tabular, the company that Blue, Weeks and Jason Reid founded to commercialize Iceberg, a sign that even the Delta Lake vendor saw Iceberg as the neutral format. Snowflake donated the Polaris catalog to the Apache Software Foundation in 2024, and the Iceberg REST catalog specification became the common way for engines to talk to catalogs. Amazon launched S3 Tables, which manages Iceberg tables inside S3, in December 2024.
Version 3 of the specification, finished in 2025, added deletion vectors (taken from Delta Lake's idea), row lineage, default column values, a VARIANT type for semi-structured data, geometry and geography types, nanosecond timestamps, and multi-argument partition transforms. Version 4 is under discussion; its aim is to cut the cost of metadata, especially for small and frequent commits.
how: Think of the table as a tree with the catalog at the top. The catalog stores one fact per table: the location of the current metadata.json. That file contains the table schema, the list of partition specs, the list of snapshots, and which snapshot is current. Each snapshot points to one manifest list. The manifest list names the manifests that make up the snapshot, and for each manifest it keeps a summary: the lowest and highest value of each partition field among its files, and how many files were added or deleted. Each manifest lists data files. For every data file it stores the path, the format, the partition values, the record count, the file size, and for each column the null count, value count and lower and upper bounds. Manifests and manifest lists are Avro files, because Avro keeps its schema in the file and evolves well.
Reading a table is a planning step before any data is read. The engine asks the catalog for the current metadata file and picks a snapshot (the latest, or an older one for time travel). It reads the manifest list and uses the partition summaries to drop whole manifests that cannot match the query's filter. It then reads the remaining manifests and applies the filter to each file's partition values and column bounds, which drops files that cannot match. Only then does it open the surviving Parquet files, where Parquet's own row-group statistics skip more data. Nothing in this path lists a directory. The cost of planning depends on the size of the metadata that matches the query, not on the number of files in the table.
Writing is optimistic and atomic. A writer creates new data files first. It then writes new manifests for the files it added or removed, a new manifest list that reuses all unchanged manifests, and a new metadata.json that adds a snapshot and sets it as current. Nothing is visible yet. The last step is the commit: ask the catalog to change the pointer from the old metadata file to the new one, but only if it still equals the old one (compare-and-swap). If another writer committed first, the swap fails. The writer then re-reads the new state, checks whether its changes conflict (for example, both rewrote the same file), and if not, it re-applies its change on top and tries again. This gives snapshot or serializable isolation without locks. The immutability of files in object storage (S3 supplies this) is what makes it safe: a file never changes after being written, so a reader holding an old snapshot is never disturbed, and the failure of a writer leaves only orphan files that no snapshot refers to.
Column identity is another important piece. Iceberg gives each column a unique integer field ID stored in the schema and, via Parquet field IDs, in the data files. Queries and statistics refer to IDs, never to names or positions. So renaming a column changes only the schema metadata, dropping a column and adding a new one with the same name gives a different ID and no stale data appears, and reordering is free. Type promotion (int to long, float to double, widening decimals) is also safe. This is the schema evolution idea of the L2 layer, implemented at the table level.
Hidden partitioning uses the same principle. The table stores a partition spec made of transforms on source columns: identity, year, month, day, hour, bucket(N), truncate(W). A query that filters on ts is translated by the engine into a filter on day(ts) automatically. Because each manifest records which spec its files were written with, the table can change from monthly to daily partitioning without rewriting old data: old files keep the old spec, new files use the new one, and planning handles both.
Row-level changes work with delete files. In format v2, a position delete file lists (data file, row position) pairs, and an equality delete file lists key values to delete. Readers merge the deletes with the data files at read time, and sequence numbers decide which deletes apply to which data. This makes updates cheap to write and more expensive to read, until compaction applies the deletes. Format v3 replaces position deletes with deletion vectors, a bitmap of deleted rows per data file stored in a Puffin file, which is faster to read and write. Row lineage gives each row an ID computed from the file's first row ID plus the row's position, and a last-updated sequence number, so a consumer can ask "which rows changed between snapshot A and B".
Maintenance is part of the design. Each commit adds a snapshot and some metadata files, and frequent small writes create many small data files. Jobs for expiring old snapshots, rewriting data files (compaction), rewriting manifests, and deleting orphan files keep the table healthy. Catalogs (REST catalog servers, AWS Glue, Hive Metastore, JDBC, Nessie, Polaris, Unity Catalog) differ in what they offer, but all must provide the atomic pointer swap.

example: A table orders on S3 has 200,000 Parquet files grouped into 1,000 manifests, partitioned by day(order_ts) over about two years, with roughly 280 files per day. A query asks for orders on one day, 2026-07-04, with amount > 5000.
Planning with Hive-style listing would call S3 LIST for the partition directory tree. Each LIST returns at most 1,000 keys, so even for one day the engine must find the right directory first; for a full-table scan it would need 200 sequential calls of about 50–100 ms, roughly 10 to 20 seconds of listing before a single byte of data is read.
With Iceberg, the engine reads the current metadata.json (a few hundred KB), then the manifest list, which has 1,000 entries, each with a lower and upper partition bound. Manifests are mostly organized by date, so only about 1 manifest has a range that contains 2026-07-04. The engine reads that one manifest, which lists about 200 files. For each file it checks the day value: 280 files match the day, and of those it checks the amount upper bound. Suppose 30 of the files have max(amount) above 5000. The engine plans exactly 30 file scans. Metadata I/O was about three small reads, a few tens of milliseconds each, and the data read is 30 files instead of 200,000.
Now a commit. Two jobs run at the same time. Job A appends 5 files, and Job B appends 7 files. Both read metadata v42. A writes v43 and swaps the catalog pointer from v42 to v43: success. B tries to swap from v42 to v43 and fails, since the pointer is now v43. B reloads v43, sees that A only added files that B does not touch, and builds v44 containing both sets of files on top of v43, then swaps v43 to v44 successfully. If instead A had compacted (deleted and rewrote) files that B was also deleting, B would see a conflict and fail, and the job would have to retry from the start.
Finally, the cost of evolution. The team decides to change from day(order_ts) to hour(order_ts) because daily partitions have grown to 40 GB. They run ALTER TABLE ... SET PARTITION SPEC (hour). Nothing is rewritten: the metadata gets spec 1, old manifests keep spec 0, and new data files use spec 1. A query on a day touches both layouts and is planned correctly. In a Hive table, the same change would be a full table rewrite of 8 TB, or a new table with a migration.
intuition: Instead of asking the warehouse what is on its shelves by walking through every aisle, keep a signed, dated inventory book and replace the whole book atomically.
The design is natural once you accept three facts about object storage: files are cheap and immutable, listing is slow, and there is no multi-file transaction. Given immutability, the cheapest way to make a change atomic is to write everything new first and then flip one pointer. Given slow listing, the table must store its own file list. Given the file list, adding statistics next to each file is almost free and makes planning smarter than listing. A tree of metadata, with summaries at each level, is the usual way to keep such a list searchable at any size. Iceberg is, in effect, a small database index built from files.
mistakes: People often think Iceberg is a storage engine or a file format. In fact it is a metadata specification over files that other formats (Parquet, ORC, Avro) store. Iceberg does not run as a service, and it does not execute queries. Engines and catalogs do the work.
People often think Iceberg has no need for a catalog because the metadata files are on S3. In fact the catalog is essential: the single pointer swap is what makes commits atomic, and without a catalog that supports compare-and-swap, concurrent writers can overwrite each other. File-based "Hadoop catalogs" are unsafe on S3 for this reason, and S3's conditional writes (2024) only partly change this.
People often think time travel means free history. In fact each snapshot keeps old data files alive, so storage grows until you expire snapshots, and expiring them ends time travel to those points. The same applies to deleted data: until old snapshots expire, "deleted" rows are still on disk, which matters for privacy requests such as deletion obligations.
People often think all engines support all Iceberg features equally. In fact support depends on engine and version. Row-level deletes, v3 features such as deletion vectors and VARIANT, branching and write support differ between Spark, Flink, Trino, Snowflake and others. Read the compatibility matrix before choosing a feature.
People often think Iceberg removes the need for small-file management. In fact it makes small files more visible: every micro-batch commit adds files and metadata, and without compaction both planning and reads slow down.
tradeoffs: Choose Iceberg when several engines (for example Spark for ETL, Trino or Snowflake for queries, Flink for streaming) must share the same tables, when you want to avoid being tied to one vendor, or when you need hidden partitioning and partition evolution on very large tables. You accept that you must run or rent a catalog, schedule maintenance jobs, and track the differences in engine support.
Choose Delta Lake when your platform is Databricks or Spark-centric and you want the tightest integration and the most mature streaming and MERGE performance there; modern Delta can also expose Iceberg metadata (UniForm), so the two are converging. Choose Hudi when the workload is dominated by high-rate record-level upserts and change data capture with indexes and incremental pulls, and you can accept a narrower ecosystem. The decision is mostly about engines and update patterns, not about file layout, since all three store Parquet.
Choose merge-on-read (delete files or deletion vectors) when writes are frequent and small and the table is read less often than it is written, for example CDC from a database. Choose copy-on-write when the table is read heavily and updates are batched, so readers pay no merge cost. Merge-on-read gives you fast commits (seconds) and slower reads until compaction; copy-on-write gives the reverse, with write amplification of a whole file per updated row.
Choose a managed catalog (Glue, Unity, Polaris-based services, S3 Tables, Snowflake) when you want governance and maintenance handled for you and accept the lock-in around the catalog. Choose an open REST catalog that you run yourself (Polaris, Lakekeeper, Nessie) when portability matters more than operations effort. Whichever you pick, the catalog is now a strategic dependency, because it holds the pointer to your data.
Choose frequent small commits (streaming) only with automatic compaction, or accept that metadata and small files will grow. A common compromise is commits every 1 to 5 minutes, not every few seconds, plus a rewrite job every hour or day.
friction: The catalog is the biggest operational and strategic issue. A catalog must offer atomic commits, access control and ideally credential vending. Moving between catalogs is possible (the metadata is just files), but the catalog features around permissions, lineage and maintenance do not move with it. The REST catalog specification narrows this gap, and not every vendor implements all of it.
Metadata and small files grow with every commit. A table written by a streaming job every 10 seconds creates 8,640 snapshots per day, each with manifests; without expiring snapshots, rewriting manifests and compacting data files, planning gets slower and storage costs rise. Equality deletes, produced by streaming upserts, force readers to apply many delete files and can make reads much slower until compaction. Deletion vectors in v3 reduce this for position deletes, but engine support is still catching up.
There are limits at the edges. Commit rate: because each commit swaps one pointer and retries on conflict, a table written by many concurrent writers can spend most of its time in retries; the practical rate is about one commit per second per table, less with big manifests. Cross-table transactions are not part of the format, though some catalogs are adding multi-table commits. Fine-grained row and column security is not in the table format at all; it must come from the catalog and the engines.
Finally, the pace of change is high. Spec v3 is new, v4 is in design, and the same feature can behave differently on different engine versions. Treat versions as part of the operational plan: pin the format version of production tables, test upgrades on copies, and remember that a table written in a newer format version cannot be read by an older client.
practice: Start with decisions that are hard to reverse. Choose the catalog first, and prefer one that implements the REST catalog specification, so that engines can change without changing the table location. Use format version 2 or 3 depending on the weakest engine in your stack. Partition with the coarsest useful transform (day or hour of an event time, or bucket on a high-cardinality join key), because over-partitioning produces tiny files. Target data files of 128 to 512 MB, and manifests that group files by the partition column you filter on.
Schedule maintenance as part of the table's definition. A usual set: compact small files daily or hourly with the rewrite_data_files procedure (bin-pack, or sort when queries filter on certain columns); rewrite_manifests when planning slows; expire_snapshots weekly, keeping at least the number of days of time travel you promise; remove_orphan_files with a safety age of at least 3 days, so you do not delete files from running writes. Set write.target-file-size-bytes and write distribution modes so that writers produce reasonably sized files without a shuffle explosion.
For streaming writes (Flink or Spark Structured Streaming), commit every 1–5 minutes, use upsert mode only when you need it, and monitor the number of delete files and the data-file count per partition. For batch updates (MERGE INTO), look at whether copy-on-write or merge-on-read fits the table's read-write ratio, and set it per operation with write.delete.mode, write.update.mode and write.merge.mode.
Use the metadata tables to see what is happening: SELECT * FROM table.snapshots, .manifests, .files, .partitions and .history show file counts, sizes and statistics with plain SQL. Use branches and tags for audit or write-audit-publish workflows. Control access through the catalog, not through bucket permissions alone, and with credential vending so users never hold long-lived cloud keys. When you must delete personal data, remember to expire snapshots and remove the old files afterwards, or the data stays on disk.
interview: Explain how Iceberg makes a multi-file commit atomic on S3, which has no multi-object transactions. || Writers create new immutable data files, manifests, a manifest list and a new metadata.json, none of which are visible. The commit is a single compare-and-swap in the catalog from the old metadata pointer to the new one. Readers see either the old or the new snapshot, never a mix. If the swap fails, the writer reloads, checks for conflicts, and retries.
A table has 500,000 files and queries on one day are slow to plan. What do you check? || Whether manifests are organized by the filter column (rewrite_manifests with the partition sort), the number of manifests and their size, whether the manifest-list partition summaries can prune, whether stats are collected for the filter columns, and metadata caching on the engine. Also check small files and lots of delete files, which add to planning.
Why does Iceberg use field IDs instead of column names, and what does that make safe? || Names can be reused or changed; IDs are unique and permanent. Rename is a metadata change, a dropped-and-re-added column of the same name is a different column and shows no stale data, and reordering is free. It makes full schema evolution safe without rewriting files.
A streaming job commits every 10 seconds and queries are getting slower every week. Diagnose and fix. || It creates thousands of snapshots, manifests and small files per day, and equality deletes pile up. Fix: commit less often (1–5 minutes), run compaction and manifest rewrite jobs, expire snapshots on a schedule, and switch to deletion vectors or merge-on-read with regular compaction.
Compare Iceberg and Delta Lake commit protocols. When do the differences matter? || Delta appends a numbered JSON action to a log (with periodic Parquet checkpoints) and relies on atomic put-if-absent of the next log file; Iceberg swaps a catalog pointer to a new snapshot tree. Both give optimistic concurrency. The differences matter with multi-engine access, catalog dependence, and storage that lacks put-if-absent; feature sets (deletion vectors, row tracking) are converging.
quiz: What are the four levels between the catalog and the data files in Iceberg? || The catalog points to metadata.json, which points to a snapshot's manifest list, which points to manifests, which list the data files.
Why does a rename of a column not break an Iceberg table? || Columns are identified by unique, permanent field IDs, not by names. A rename changes only the name in the schema, and the data files and statistics still match by ID.
Two writers both start from metadata v42 and commit. What happens to the second one? || Its compare-and-swap fails because the pointer is now v43. It reloads v43, checks that its changes do not conflict, rebuilds its metadata on top of v43 as v44, and swaps again. If there is a conflict, the commit fails.
A table is partitioned by day with 280 files per day, 30 of which could contain amount > 5000. How many data files does the planner open for that day's query, and which metadata decides it? || 30 files. The manifest list prunes to the right manifest, and the per-file column bounds (upper bound of amount) in the manifest remove the other 250.
Your streaming CDC job has slow reads after weeks of operation. Would you choose copy-on-write or merge-on-read, and what maintenance do you add? || Merge-on-read (delete files or deletion vectors) suits frequent small CDC writes, but the reader must apply deletes, so schedule regular compaction (rewrite_data_files) that applies them, plus manifest rewrites and snapshot expiry.

@@ hudi
value: Apache Hudi is a table format and a set of table services for data lakes, built around one hard job: applying a constant stream of inserts, updates and deletes to huge tables made of immutable Parquet files, and letting downstream jobs read only what changed. Its name stands for Hadoop Upserts, Deletes and Incrementals. It began at Uber in 2016, where trip records in the data lake had to be updated within minutes, not once a day.
The problem is simple to state. Files on HDFS or S3 cannot be edited in place. To change one row in a 120 MB Parquet file, you must write a new file. If you do not know which file holds the row, you must scan everything. Hudi answers both parts. It keeps an index that maps each record key to the group of files that holds it, so an update goes straight to the right place. And it offers two ways to write the change: rewrite the file immediately (copy-on-write) or append the change to a small log and merge later (merge-on-read).
For the layer above (Spark and Flink ingestion jobs, change data capture from databases, incremental ETL, Presto/Trino and Athena queries), Hudi turns a lake into something close to a database that receives change streams. Two lower concepts matter. Parquet supplies the columnar base files, and Hudi relies on Parquet's footer for statistics and Bloom filters of record keys. The lakehouse idea (L1) is the goal: transactions, schemas and indexes over files in object storage. Hudi's differentiator in this family is that it treats the record, not the file or the snapshot, as the unit it manages. Compare Iceberg, which is built around snapshot metadata, and Delta Lake, which is built around a transaction log.
terms: Record key — the unique key of a row (such as trip_id), used by the index to find the file group that holds the row.
Precombine (ordering) field — a column such as an update timestamp used to pick the latest version when several versions of one key arrive together.
File group and file slice — a file group is all versions of a set of records over time, identified by a file ID; a file slice is one version of it: a base Parquet file plus the log files written after it.
Copy-on-write (COW) — an update rewrites the whole base file with the changes merged in; readers just read Parquet.
Merge-on-read (MOR) — an update is appended to a log file next to the base file; readers merge base and logs, and compaction later folds the logs into a new base file.
Timeline — the ordered record of all actions on the table (commit, delta commit, compaction, clean, rollback), stored in the .hoodie folder.
Index — the structure that maps a record key to its file group (Bloom filter index, bucket index, record-level index and others).
Table services — background jobs that keep a table healthy: compaction, clustering, cleaning and archival.
history: Vinoth Chandar and Prasanna Rajaperumal built the first version at Uber in 2016, under the name Hoodie. Uber kept its trip data in MySQL-like databases and wanted the analytics tables on Hadoop to be fresh. The usual approach, a full re-import every day, meant data that was 24 hours old and a large load on the databases. They needed updates at minute-level latency on top of HDFS, and they also needed downstream jobs to process only the changed rows ("incremental processing"), which became the central idea of the design.
Uber open-sourced Hudi in 2017. It entered the Apache Incubator in January 2019 and became a top-level Apache project in 2020. Its early users were companies with change-data-capture workloads: Uber, Robinhood, Walmart, ByteDance and others. Delta Lake (2019) and Iceberg (2018 as an Apache project) followed with the same goal of transactions over lake files but different priorities. Hudi stayed strongest where upsert rate, indexes and streaming ingestion mattered.
Hudi 0.x releases added the metadata table (an internal Hudi table that stores file listings, column statistics and Bloom filters so that queries do not list directories), clustering, multi-writer concurrency, a Flink writer and the record-level index. Version 1.0, released in January 2025, was a deep redesign: a new LSM-style timeline, non-blocking concurrency control, secondary and expression indexes, partial updates and the idea of Hudi as a "transactional database for the data lake". Version 1.1 made the table format layer pluggable, and 1.2 added unstructured types (VECTOR, VARIANT, BLOB) and read and write support for the Lance file format.
By the mid-2020s the lakehouse formats converged in features, and Iceberg gathered the broadest engine support. Apache XTable, a project that translates metadata between Hudi, Delta and Iceberg, grew out of this. Hudi's role became more specialised: very high-throughput record-level upserts, streaming ingestion with Flink or Spark, and incremental data pipelines.
how: Start with the layout. A Hudi table is a directory (on S3 or HDFS) that contains partition folders with data and a .hoodie folder with metadata. Inside a partition, each file group holds the history of a fixed set of record keys. A file group consists of file slices. Each slice has one base file (Parquet) and, for MOR tables, zero or more log files with changes made after the base file was written. Each record in the Parquet file carries extra metadata columns such as _hoodie_commit_time, _hoodie_record_key and _hoodie_file_name. The columnar layout and statistics of Parquet make base files fast to scan; Hudi adds the keys and commit times on top.
A write begins with tagging. The writer receives a batch of records, each with a key and a partition path. First, it removes duplicates inside the batch, using the precombine field to keep the latest version of each key. Then it asks the index: for each key, which file group (if any) already contains it? Keys found are updates and go to that file group. Keys not found are inserts, and Hudi packs them into new file groups or into small existing file groups, sized to a target such as 120 MB, which is how Hudi controls file sizes automatically. The default Bloom index stores a Bloom filter and the min/max key range of each base file in its Parquet footer. For each incoming key, Hudi checks key ranges first, then Bloom filters, and finally the actual file only for candidates. Bloom filters (an L0-adjacent idea built on hashing and probability) make "is this key possibly in that file?" cheap, so most files are never opened. Other indexes trade memory for speed: the bucket index uses a hash of the key, so there is no lookup at all but the bucket count is fixed; the record-level index stores every key's location in the metadata table; and the Flink state index keeps the mapping inside Flink state.
Then the write itself. In copy-on-write, each affected file group gets a new base file: Hudi reads the old file, merges the updated records, and writes a new file slice as Parquet. The cost is write amplification, as a change of a few rows rewrites a whole file, but readers need nothing special. In merge-on-read, the updates are appended to a log file in the file group as Avro (or Parquet) data blocks, plus delete blocks for deleted keys. The write is cheap and fast. A snapshot query must read the base file and merge the log files for the latest state. A read-optimized query reads only base files and is faster but sees only data as of the last compaction.
Everything is recorded on the timeline. An action goes through states: requested, inflight, completed. The completed instant is a file in .hoodie. A reader finds the latest completed instants, and a write is atomic because it becomes visible only when its completed marker file appears (object stores and file systems provide atomic file creation). Rollbacks remove the partial work of failed writes. Since version 1.0, the timeline is stored as an LSM-style structure with completion time, which scales to millions of instants and supports reads in completion order.
Table services keep the tables healthy and can run inline with the writer, asynchronously in the same job, or as separate jobs. Compaction merges log files into a new base file for MOR tables. Clustering rewrites small files into larger ones and can sort them by query columns, improving data skipping. Cleaning deletes old file slices that no query needs (by commit count or by age). Archival moves old timeline entries aside. The metadata table, itself a Hudi MOR table, stores file listings, column statistics and indexes so that reading and planning avoid listing storage.
Concurrency has two layers. Between writers, Hudi uses optimistic concurrency control with a lock provider (ZooKeeper, a Hive metastore, DynamoDB, or since 1.1 a lock file in storage on S3 or GCS): writers detect conflicts at commit time on overlapping file groups. Between a writer and table services such as compaction, it uses MVCC, so that readers and compaction see consistent file slices. Non-blocking concurrency control (1.0) lets several writers append to the same file group in MOR tables without locks and resolves the order at read or compaction time, using the record's ordering field.
Incremental queries are Hudi's special feature. Because every record has its commit time, a consumer can ask "give me all records changed after commit time T". The engine reads only the file slices touched by commits after T, which is a small part of the table. Since 0.13 there is also a change data capture mode that returns before and after images of rows. This makes a Hudi table a source for the next stage of a pipeline, so that a chain of tables is updated incrementally and not rebuilt in full.

example: Take a trips table with 2 billion rows in daily partitions. About 10,000 base files of 120 MB each are in the last 30 days, and the table is about 1.2 TB for those days. Every 5 minutes a CDC feed delivers 100,000 changed trip records: 10% are new trips and 90% are updates to trips from the last 30 days. Each record is about 500 bytes, so a batch carries about 50 MB.
First the index step. Suppose the Bloom index is used. Each base file holds about 1.2 million records. Hudi first compares the 90,000 update keys with the min and max key range of each file. If trip IDs are random, ranges overlap and do not help, so Bloom filters decide. A Bloom filter with a 1% false-positive rate means that for each key about 1% of the 10,000 files, around 100 files, are wrongly suggested. So Hudi must open the candidate files to confirm, which is a lot of reads. This is why ordered keys (for example IDs that start with a timestamp) work much better with the Bloom index: key ranges prune files well. With random keys, the record-level index or the bucket index is the better choice, since lookup becomes one hash or one point read.
Now the cost of the write, assuming the updates are spread across 3,000 of the 10,000 file groups. With copy-on-write, Hudi rewrites 3,000 files of 120 MB, which is 360 GB of writing every 5 minutes to change 50 MB. That is a write amplification of more than 7,000 times and impossible to sustain. Copy-on-write fits this workload only when updates are concentrated in a few files, or batches are large and rare, for example hourly. With merge-on-read, Hudi appends the updates to log files of the 3,000 file groups: roughly 50 MB plus overhead in total, written in a few seconds. Readers doing a snapshot query merge the logs on the fly, which costs more CPU. A compaction job runs, say, every hour or after N delta commits, and rewrites the file slices that have many log blocks, paying the 360 GB cost once per hour instead of every 5 minutes, and only for the file groups that really changed enough.
Then the incremental read. A downstream job last processed commit 20260710093000. It asks for changes after that time. Hudi finds the commits since then on the timeline (12 commits in the last hour) and reads only the file slices touched by them. It returns about 600 MB of changed records, instead of scanning 1.2 TB. The job updates its own aggregate table from only those changes. This is the main saving of an incremental pipeline: the work is proportional to the change, not to the table.
intuition: A bookkeeper who keeps a card index of where every account is filed and a small pile of "new entries" beside each file, and tidies up the piles when it is quiet.
The design is natural because an upsert is two problems: find the record, and apply the change cheaply. Finding needs an index, as in any database. Applying cheaply on immutable files needs a log, as in a log-structured store, and that is what a MOR log file is. Compaction is the usual price of a log: someone has to merge it later. Hudi simply treats the lake table as a log-structured database with a Parquet-based base layer, and then exposes the log of changes (by commit time) to downstream jobs as a stream. Everything else, such as the timeline, file sizing and cleaning, is housekeeping for that idea.
mistakes: People often think Hudi, Iceberg and Delta Lake differ mainly in file format. In fact all three store data as Parquet. They differ in how they track files and handle change: Hudi has record-level indexes and a built-in set of table services, Iceberg has a snapshot tree and a catalog pointer, Delta has a transaction log.
People often think merge-on-read is always better for updates. In fact it moves cost from writers to readers and to compaction. If compaction falls behind, log files accumulate and snapshot queries slow down, sometimes by several times. Copy-on-write is the better choice for tables that are read much more than they are written.
People often think the index is optional or free. In fact index choice decides write throughput. A Bloom index on random keys opens many files; a global index across all partitions needs more memory; the bucket index needs a bucket count that is hard to change. Bad indexing is the most common cause of slow Hudi ingestion.
People often think Hudi only works with Spark. In fact it has Flink, Presto/Trino, Hive, Athena, StarRocks and other readers, but the richest write support and table services are in Spark and Flink, and many other engines read only. Check what your query engine can read before you choose.
People often think a Hudi table needs no operations once created. In fact compaction, clustering, cleaning and lock configuration all need tuning, and failing to clean means storage grows without bound.
tradeoffs: Choose Hudi when the main workload is high-rate upserts or deletes by key, such as CDC from operational databases, and when downstream jobs can use incremental pulls. Choose Iceberg when the main need is broad multi-engine access and a neutral table standard, and your updates are moderate and batch-like. Choose Delta Lake when your platform is Databricks and you want the tightest integration. What you give up with Hudi is ecosystem breadth and simplicity: more configuration, fewer engines.
Choose copy-on-write when read performance and simplicity matter more than write latency, and updates touch a small share of files. Choose merge-on-read when updates are frequent, spread across many files, and freshness of minutes is required; accept that you must run compaction and that snapshot queries cost more until it runs. Provide a read-optimized view when some consumers can accept data that is as old as the last compaction.
Choose the Bloom index when record keys are ordered or when update batches are small and mostly hit recent files. Choose the bucket index when the key space is large and uniform and you can fix the bucket count (it avoids lookups). Choose the record-level index (or Flink state index for Flink writers) when keys are random and tables are very large; you pay metadata table storage and index maintenance. A global index (unique keys across partitions) costs more but is required if a record can move between partitions.
Choose inline table services for small tables and simple jobs, so there is no extra scheduling. Choose asynchronous or separate table-service jobs for high-throughput pipelines, so compaction does not block ingestion; the price is more moving parts, and lock-provider setup if services and writers run at the same time.
friction: Hudi has many configuration options, and good performance depends on setting them well: index type, file size targets, compaction triggers, clustering strategy, cleaning policy and lock provider. Defaults are acceptable for demos but often not for large tables. Teams need someone who understands the system, or a managed service (Onehouse, or the Hudi support in AWS EMR, Glue and other platforms).
Engine support is narrower than Iceberg's. Many warehouses and query engines read Iceberg and Delta natively, while Hudi support is usually read-only, and sometimes limited to COW or read-optimized views. Metadata translation tools such as Apache XTable can expose a Hudi table as Iceberg or Delta, at the cost of keeping two sets of metadata in sync.
There are performance risks from the design itself. MOR tables with lagging compaction slow down reads. A badly chosen index slows down writes by opening thousands of files. The metadata table adds its own storage and maintenance and can become a point of contention at high commit rates. Multi-writer concurrency needs an external lock provider, except the newer storage-based lock, and a lock failure can stall ingestion.
The ecosystem has also moved. Both Iceberg and Delta now have deletion vectors and row-level change tracking, which removes some of the advantage Hudi once had in upserts, and community momentum is larger around Iceberg. Hudi's answer is to stay strong where it leads (indexes, streaming upserts, incremental processing) and to interoperate, but a new project must weigh the smaller community and the risk of fewer integrations over time.
practice: Decide the key and the ordering field first. A good record key is unique, stable and, if possible, ordered by time or prefixed by a time component, so the Bloom index can prune by key range. Pick the precombine field that really decides which version is latest (an update timestamp or a log sequence number), and not the processing time. Choose the partition path by a column that does not change for a record (such as trip creation date), otherwise you need a global index.
Choose the table type from the read-write profile: COW for batch-updated, heavily read tables; MOR for streaming CDC and frequent updates. For MOR, set compaction to run every few delta commits or by log-file size, run it asynchronously, and watch the number of log files per file group. Set the target base file size (about 120 to 512 MB) and let Hudi's small-file handling pack inserts into existing small files. Run clustering to sort by columns used in filters and to merge small files.
Set the cleaning policy to keep as many commits as your slowest reader or longest incremental pull needs, with a safety margin. If a consumer falls behind the cleaning window, it can no longer pull incrementally and must read the full table. For multi-writer setups, configure a lock provider (DynamoDB, ZooKeeper, Hive metastore or the storage-based lock) and prefer non-blocking concurrency control for MOR writers that rarely touch the same keys.
For ingestion use the Hudi Streamer utility or Flink. Monitor commit duration, number of file groups touched per commit, index lookup time, number of pending compactions and bytes per commit. Test failure cases: kill a writer during a commit and verify that rollback leaves the table consistent. Use Hudi's CLI and the timeline to inspect states. If other teams need Iceberg or Delta readers, expose the table through XTable or the supported sync tools instead of copying the data.
interview: Why does Hudi need an index when Iceberg and Delta do not? || Hudi's main operation is an upsert by key, which must find the file group that already holds the key. Iceberg and Delta usually handle updates through MERGE INTO, which scans or prunes files with column statistics, or through delete files; they do not keep a key-to-file map. Hudi's index avoids scanning and lets update cost depend on batch size.
When would merge-on-read make a table slower than copy-on-write overall? || When compaction cannot keep up, snapshot reads must merge many log blocks per file group, and the read cost grows with the number of logs. It also loses when the table is read far more than written, since each read pays the merge cost that copy-on-write pays once at write time.
How does Hudi guarantee that a failed writer does not leave a visible partial commit? || Data files are written first under an inflight instant. The commit becomes visible only when the completed instant file is written to the timeline, which is an atomic file creation. A rollback later removes the leftover files of any instant that never completed.
Two Flink jobs write to the same MOR table. How do you avoid corrupt or lost updates? || Use a lock provider with optimistic concurrency, so conflicting commits on the same file groups are detected and one fails. For jobs that mostly write different keys, use non-blocking concurrency control: both append log files, and ordering fields settle the winner at read or compaction time.
A consumer reads incrementally from a Hudi table and gets an error about missing commits. What happened? || The cleaner removed file slices (and the timeline archived commits) that the consumer still needed because the consumer fell behind the retention window. Fix by lengthening cleaner retention beyond the longest expected lag, and have the consumer fall back to a full snapshot read and restart the incremental checkpoint.
quiz: What do the letters of Hudi stand for? || Hadoop Upserts, Deletes and Incrementals.
Why is a Bloom filter useful in Hudi's default index? || For an incoming key it tells cheaply which base files might contain it, with no false negatives, so Hudi opens only those candidate files and not all of them.
What is the difference between a file group and a file slice? || A file group is all versions of a set of records over time (one file ID). A file slice is one version of that group: a base Parquet file plus the log files written after it.
A batch of 50 MB of updates touches 3,000 file groups of 120 MB. How much does copy-on-write write, and how does merge-on-read compare? || Copy-on-write rewrites 3,000 × 120 MB = 360 GB; merge-on-read appends about 50 MB of log blocks plus small overhead and pays the merge cost later, at compaction or read time.
You run CDC with random UUID keys on a 5 TB table. Which table type and index do you choose, and why? || Merge-on-read, so frequent small updates stay cheap, and a record-level index or bucket index instead of Bloom, because random keys give Bloom filters no key-range pruning and would open many files.

@@ parquet
value: Apache Parquet is a file format that stores a table column by column, with each column encoded and compressed on its own, and with summary statistics written on each block so that readers can skip data they do not need. It is the default storage format of the analytics world. Spark, Trino, Snowflake, BigQuery, DuckDB, pandas and Polars all read and write it, and the table formats Iceberg, Delta Lake and Hudi store their data in Parquet files.
The reason is the shape of analytical queries. A typical question touches few columns of a wide table, for example "sum of amount by country" over 200 columns and 10 billion rows. A row format such as CSV, JSON or Avro stores each row together, so the engine must read and parse all 200 columns to use two of them. A columnar format keeps the values of one column together on disk. The engine reads only the two columns it needs, which can be 1% of the bytes. Values in one column are also alike (the same type, often the same few values), so they compress very well: a column of country codes, sorted, can shrink by 100× or more. Typical Parquet files are 3 to 10 times smaller than the same data as CSV or JSON, and scans are often 10 to 100 times faster.
For the layer above (Spark, Trino, Delta, Iceberg, Hudi, machine-learning training sets), Parquet is the common language for data at rest. Its lower concept is the OLAP idea (L1): analytics means scans and aggregations over a few columns of many rows, so storage should be columnar, and the format should help the engine avoid reading data. Parquet contributes the concrete mechanism: a layout of row groups, column chunks and pages, a menu of encodings, and statistics in a footer. It also brings the record-shredding idea from Google's Dremel paper, which lets nested data (lists, structs) be stored in flat columns.
terms: Row group — a horizontal slice of the table (for example 1 million rows or about 128 MB) that holds one column chunk for every column; the unit of parallel reading and of skipping.
Column chunk — all values of one column within one row group, stored contiguously.
Page — the smallest unit inside a column chunk (about 1 MB by default in the Java library); each page is encoded and compressed separately.
Footer — metadata at the end of the file: the schema, the location of every column chunk, the encodings used, and the statistics.
Dictionary encoding — replacing repeated values by small integer codes, with one dictionary of the distinct values stored once per chunk.
Run-length encoding (RLE) — storing a repeated value once together with how many times it repeats; Parquet uses a hybrid of RLE and bit-packing.
Definition and repetition levels — small integers stored next to values of nested columns; they record where nulls occur and where a list starts a new element, so nested records can be rebuilt.
Predicate pushdown — using min/max statistics (and Bloom filters) to skip row groups or pages that cannot satisfy a filter, before reading their data.
history: The idea of columnar storage is old. In 2005 the C-Store paper described a column-oriented database, and Vertica, MonetDB and others built products. For Hadoop, the first columnar formats were RCFile (Facebook, 2009–2011) and Trevni, a columnar variant of Avro. In 2010 Google published the Dremel paper, which showed how to store nested records (protocol buffers) in columns using repetition and definition levels and run interactive queries over them.
Parquet was born in 2012–2013 from a collaboration between Twitter and Cloudera. Julien Le Dem at Twitter wanted a Dremel-style format for Twitter's nested protocol buffer and Thrift data, while Nong Li and Marcel Kornacker at Cloudera were building a columnar format for their Impala query engine. They combined the work, and the first release was in 2013. The name comes from parquet flooring, a pattern of blocks laid in columns. Parquet joined the Apache Incubator in 2013 and became a top-level project in 2015.
Adoption grew with Spark, which made Parquet its default format around 2015, and with cloud object stores, where reading only the needed byte ranges of a file is a big saving. The format kept growing: the page index (column and offset indexes) was added so that readers can skip pages inside a column chunk; split-block Bloom filters were added for equality filters; modular encryption allowed per-column keys; and new encodings such as DELTA_BINARY_PACKED and BYTE_STREAM_SPLIT improved sizes for integers and floating-point values.
In the last years the community added logical types for modern workloads: a VARIANT type for semi-structured JSON-like data and GEOMETRY and GEOGRAPHY types for spatial data, both also adopted by Iceberg v3. At the same time a new generation of formats (Lance, Vortex, Nimble and others) has appeared, aimed at random access, wide tables with thousands of columns and machine-learning data, areas where Parquet's footer-heavy design is not ideal. Parquet remains the default because every engine already reads it.
how: A Parquet file begins and ends with the four bytes PAR1. After the first magic number come the row groups, one after another. At the end of the file is the footer, which contains the file metadata serialized with Thrift, then a 4-byte footer length, then PAR1 again. A reader first reads the last 8 bytes, learns the length of the footer, reads the footer in one request, and now knows everything about the file without scanning it. This is an important point for object stores such as S3: opening a file costs one or two range requests, and then the reader asks only for the byte ranges of the column chunks it needs.
Inside a row group there is one column chunk per column, stored one after the other. Inside a column chunk are pages: possibly one dictionary page, then data pages. A data page holds the values for a range of rows (typically about 1 MB before compression, or 20,000 values), along with the definition and repetition levels for nested or nullable columns. This layering, file to row group to column chunk to page, serves three goals. Row groups allow parallel work: each Spark task or Trino split reads one or more row groups. Column chunks allow column pruning: only the chunks of requested columns are read. Pages allow fine skipping and incremental decoding: a reader decodes a page at a time.
Encoding comes before compression. For each column chunk the writer picks an encoding based on the data. Dictionary encoding is the default for most types: while writing, the writer builds a dictionary of distinct values; each value becomes an index, and the indices are written with the RLE/bit-packing hybrid, using only as many bits as the dictionary needs (8 bits for up to 256 distinct values, for example). If the dictionary becomes too big (the default limit is about 1 MB), the writer falls back to plain encoding for the later pages. For sorted integers and timestamps, DELTA_BINARY_PACKED stores differences between neighbours in small bit widths. For strings without a good dictionary, DELTA_LENGTH_BYTE_ARRAY and DELTA_BYTE_ARRAY store lengths separately and prefixes shared with the previous value. For floats, BYTE_STREAM_SPLIT regroups the bytes of all values by byte position, which makes later compression much more effective.
After encoding, each page is compressed with a general-purpose codec chosen per column: Snappy (fast, moderate ratio), LZ4, Zstandard (better ratio, still fast; the usual modern choice) or Gzip (slow, high ratio). The important idea is that encoding makes the data much more regular (small integers, runs, deltas), so a compressor then works on easy input. A column that is sorted and low in cardinality may compress by a factor of 100; a column of random identifiers hardly shrinks.
Nested data uses the Dremel approach. A schema with optional, required and repeated fields is flattened into leaf columns. For each value, Parquet stores two small integers. The definition level says how many of the optional or repeated ancestors are actually present (so a null at any level can be told apart from a value). The repetition level says at which repeated ancestor the value starts a new element, so the reader knows where one list ends and the next begins. These levels are stored in RLE, and they are often tiny. With them, a reader can rebuild each original record from its leaf columns without any pointers.
Statistics make skipping possible. For every column chunk the footer stores the minimum, the maximum, the null count and (optionally) the distinct count. For a filter such as country = 'IN', the engine compares 'IN' with the min and max of each row group and discards groups whose range excludes it. The page index goes one level deeper: a ColumnIndex holds the min and max of each page, and an OffsetIndex holds the byte position and row range of each page, so a reader can read only the pages that may match, and can align pages across columns by row number. Bloom filters (the split-block kind, which are cache-friendly) can be stored per column chunk for high-cardinality columns where min/max is useless, such as user IDs; they let the reader say "this value is definitely not in this row group".
These statistics are only useful when the data is clustered. If every row group contains every country, min and max cover everything and nothing is skipped. This is why writers sort or cluster data by commonly filtered columns (and why table formats offer sorting and Z-order options). It is also why row group size matters: smaller groups give tighter statistics but more footer metadata and more small reads. A common practice is row groups of 128 MB to 1 GB for object stores, and files of at least 128 MB to 1 GB.

example: Take a table events with 100 million rows and three columns: user_id (64-bit integer), country (two-letter code, 200 distinct values) and amount (64-bit float). As CSV, a row like 8123456789,IN,129.50 takes about 24 bytes, so the file is about 2.4 GB.
Parquet writes it with 100 row groups of 1 million rows. The country column per row group: PLAIN storage of a two-letter string costs 4 bytes of length plus 2 bytes of text, so 6 bytes per value, 6 MB per chunk. Dictionary encoding stores up to 200 strings once (about 1.2 KB) and an 8-bit index per row, so 1 MB per chunk, before further tricks. If the table is sorted by country, each row group contains one or two countries, the indices form long runs, and RLE reduces the chunk to a few hundred bytes. Compression then adds almost nothing, because the chunk is already tiny. The amount column holds floats with two decimals, so it compresses less, say from 8 MB to 6 MB with Zstandard. The user_id column of random 64-bit numbers barely compresses, about 8 MB. The whole file is then about 100 × (0 + 6 + 8) MB, which is about 1.4 GB, and a smarter layout (user_id sorted within groups and delta-encoded) would cut it further.
Now the query SELECT sum(amount) WHERE country = 'IN'. The reader fetches the footer (a few hundred KB for 100 row groups and 3 columns). The table is sorted by country, so only the 1 or 2 row groups whose min and max include 'IN' qualify; the other 98 are skipped without a single read. For those 2 groups the reader fetches two column chunks each, country and amount, and never touches user_id. The bytes read are about 2 × (0.0005 + 6) MB = 12 MB, instead of the 2.4 GB that CSV would need, a reduction of about 200×. If the table were not sorted by country, every row group would have min 'AE' and max 'ZA', no group could be skipped, and the query would read the country and amount chunks of all 100 groups: 100 × 6 MB ≈ 600 MB, still four times less than CSV but 50 times more than the sorted layout. Layout matters as much as format.
A nested example. A record has a field tags, which is a repeated string. The records are [a, b], [] and [c]. In the leaf column tags there are three entries for the values a, b and c, plus one null entry that marks the empty list in the second record. The repetition levels are 0, 1, 0, 0 (0 means a new record starts, 1 means another element of the same list) and the definition levels are 1, 1, 0, 1 (1 means a value is present, 0 means the list is empty). From these two short arrays and the values a, b, c the reader rebuilds all three records exactly.
intuition: A library that shelves each topic of every book in its own aisle, labels each shelf with the range of what it holds, and keeps a catalog by the door.
Analytics asks narrow questions of wide, huge tables, so the layout should follow the question, not the record. Putting a column's values next to each other makes them cheap to read in bulk, easy to compress and easy to process with vector instructions. Cutting the data into row groups with summaries makes "skip it" the cheapest operation a reader can do. And putting the catalog (the footer) at the end lets a writer produce the file in one streaming pass: it only needs to know the offsets after the data has been written.
mistakes: People often think Parquet is a database or a table format. In fact it is a single immutable file format. It has no transactions, no concept of a table made of many files, and no way to update a row in place. Table formats such as Iceberg and Delta add those on top of Parquet files.
People often think Parquet always makes data smaller and faster. In fact the benefit depends on the data and the layout. Very small files have footer overhead that dominates; unsorted data has useless statistics; and reading all columns of every row (for example for a row-by-row export) is slower than reading a row format.
People often think row group skipping works automatically for any filter. In fact it works only for columns where min and max are selective, which requires clustering. A filter on a random ID column skips nothing without a Bloom filter. A filter on an expression, like lower(name) = 'x', cannot use statistics at all.
People often think compression codec is the main lever for size. In fact encoding and sorting usually matter more: sorted, low-cardinality columns shrink by orders of magnitude through dictionary and RLE even before compression. Changing from Snappy to Zstandard typically gains 10–30%.
People often think "schema on read" means Parquet files can be read with any schema. In fact the schema is stored in the file and engines match columns by name or by field ID. Renaming a column in the files is not safe unless the reader is told, and different engines have historically differed in how they treat things like timestamps (INT96 versus INT64 with a logical type) and decimal types.
tradeoffs: Choose Parquet when the access pattern is analytical scans over a few columns of many rows, and you need the broadest engine support. Choose ORC when you live in a Hive-centred stack, where its built-in indexes and ACID support were designed, and Parquet where you need Spark, Trino, Snowflake, DuckDB and the table formats to share files. Choose Avro or Protobuf for record-at-a-time streams and Kafka, where you read whole records; choose Parquet for what you store afterwards.
Choose large row groups (128 MB to 1 GB) and files (256 MB to 1 GB) on object stores, where each request has a fixed cost of tens of milliseconds, and the statistics overhead is small relative to the data. Choose smaller row groups (16–64 MB) when the data is highly selective and clustered, when a reader has limited memory per task, or when many fine-grained skips pay off. The cost of large groups is memory pressure in writers (a whole row group is buffered) and less precise skipping.
Choose dictionary encoding (default) for columns with fewer than a few hundred thousand distinct values per row group; disable it for columns like UUIDs, where the dictionary grows as big as the data and falls back anyway. Choose Zstandard (level 1 to 3) for storage that is read often and cares about size; choose Snappy or LZ4 when CPU is the bottleneck; avoid Gzip except for cold archives.
Choose newer formats (Lance, Vortex, Nimble) only for specific needs, such as fast random access to single rows, thousands of columns, or vector-heavy ML data. You give up the universal compatibility that makes Parquet the safe default.
friction: Parquet files are immutable, so any update means writing a new file. Deleting one row from a 1 GB file means rewriting it, or using a table format with delete files or deletion vectors. Streaming writers must buffer a full row group before writing, or produce many small files, so the freshness of data and the file size are in direct tension.
The footer design has costs. The reader must parse the whole footer to open a file, and for wide tables (thousands of columns) or files with thousands of row groups this metadata can be many megabytes and take tens of milliseconds to parse. Thrift decoding of the footer is slow for ML-style tables with 10,000 columns; this is a main reason for new formats. Page indexes and Bloom filters add more bytes to read.
Interoperability gets complicated. The format has many encodings, versions and logical types, and writers differ on which they use by default. Old readers cannot read new encodings; INT96 timestamps (a legacy Impala/Spark type) are deprecated but still around; nested types are handled differently across engines; and Spark, Hive and Impala once disagreed on timestamp time zone semantics. Test files with all the readers you rely on before adopting a new feature.
Performance depends on settings that engines hide: row group size, page size, dictionary limits, compression codec and sort order. Defaults are tuned for the average case, not for your table. And statistics only help when the data is clustered, so writers often need a sort or a Z-order/clustering step, which costs compute.
practice: Treat file layout as part of the schema. Write files of 256 MB to 1 GB, with row groups of 128 MB or more on object storage. Sort data by the columns you filter on most, lowest-cardinality first, within each file or table partition. Partition coarsely (by day, for example) so files are not tiny. Compact small files regularly, because a table of 100,000 files of 1 MB reads much slower than 100 files of 1 GB.
Inspect before tuning. Use parquet-tools, DuckDB (SELECT * FROM parquet_metadata('file.parquet')), or PyArrow's metadata API to see row group count, sizes, encodings and min/max values. If min and max overlap across row groups for your filter column, fix clustering. If the dictionary falls back to PLAIN for a column, look at its cardinality. Check that string columns are not stored as BINARY without the UTF8 annotation, because engines may refuse to filter them with statistics.
Use Zstandard for most data (level 3 is a good default in Spark and Arrow), and enable Bloom filters only on high-cardinality columns used in equality filters, such as user_id or device_id (Spark: parquet.bloom.filter.enabled#column). Avoid very wide, deeply nested schemas when you can; flatten what you filter on. Use INT64 with a TIMESTAMP logical type for time, and decimals for money, not floats.
For streaming into the lake, accept that you will write small files and schedule compaction, or let a table format do it. Use schema evolution through the table format (field IDs) and not by renaming columns in raw files. For long-term archives, record the version of the writer and test that a different engine can read the files, because the archive will outlive today's tools.
interview: Explain how a Parquet reader answers SELECT sum(amount) WHERE country = 'IN' on S3 reading as little as possible. || Read the last 8 bytes to find the footer, read the footer, and use per-row-group min/max of country (and page indexes or Bloom filters if present) to select row groups and pages. Then issue range reads for only the country and amount column chunks of those groups. The result depends on the data being clustered by country.
Why is the footer at the end of the file, and what is the cost? || The writer streams row groups out in one pass and only knows the offsets and statistics after writing them, so the metadata goes last. The cost is that a reader must first fetch the tail and parse the whole footer, which hurts for wide tables with thousands of columns and for tiny files.
Why do definition and repetition levels exist, and what would you do without them? || They let nested and nullable data be stored as flat columns while being rebuildable into records; definition levels mark which levels are null, repetition levels mark list boundaries. Without them, you would store nested records as one blob or as pointers, losing column pruning and vectorized reading for inner fields.
Queries on a user_id equality filter scan the whole table even though the table is in Parquet. Why, and what are your options? || User IDs are random, so every row group's min and max cover the whole range, and statistics cannot skip. Options: cluster or sort by user_id, add Bloom filters for the column, partition or bucket by a hash of user_id in the table format, or use an index or a different store for point lookups.
How would you update 1,000 rows in a 10 TB Parquet table? || Parquet files are immutable, so you rewrite the affected files, or use a table format with delete files or deletion vectors (Iceberg, Delta, Hudi) to record the change and compact later. The cost depends on how many files contain the rows: clustering by the update key limits the rewrite to few files.
quiz: What are the four layers of a Parquet file from top to bottom? || File, row groups, column chunks, pages; plus the footer at the end holding the schema and statistics.
Why does dictionary encoding followed by RLE shrink a sorted country column so much? || The country values become small integer codes, and in sorted data the same code repeats in long runs. RLE stores each run as one code and one count, so millions of rows reduce to a few hundred bytes.
A 100-row-group file is sorted by country. How many row groups does a filter on one country read, and why? || Usually one or two, because the min/max statistics in the footer show that only those groups include that country, so the others are skipped without being read.
A table has 10,000 files of 1 MB each and queries are slow though the data is small. What is the likely cause and the fix? || Per-file costs (a request, a footer read and parse, task scheduling) dominate. Compact into files of at least 128 MB to 1 GB, so there are about 10–100 files, and the fixed cost is paid fewer times.
Would you pick Parquet for storing Kafka messages that are consumed one record at a time? || No. A row format such as Avro or Protobuf is better for record-at-a-time streams. Parquet suits the later analytical storage, where queries read a few columns of many rows.

value: Apache ORC (Optimized Row Columnar) is a columnar file format for analytics, created in 2013 for Apache Hive by engineers at Hortonworks and Facebook. Like Parquet, it stores each column separately, compresses it with type-aware encodings, and keeps statistics so that readers can skip data. Unlike Parquet, it was designed together with Hive, so it also carries lightweight indexes inside the file, optional Bloom filters, and a layout for Hive's ACID tables. It is still widely used in Hive and Trino-based warehouses and is one of the three file formats that Iceberg can store.
The problem it solved was concrete. Hive in 2012 stored tables in RCFile, a column-grouped format with little compression and no way to skip data. A Hive query over a large table still read most of the file, and the cost was in disk reads and CPU for parsing. ORC reduced both. Facebook reported file sizes much smaller than RCFile and large speedups on its warehouse queries, because the format stores integers and strings with specialised encodings and lets the reader skip groups of 10,000 rows using an index.
For the layer above (Hive, Spark, Trino, Presto, Flink, Impala and the Iceberg table format), ORC is a file format option for the data files. It stands on the OLAP idea (L1): analytic queries read few columns of many rows, so columns should be stored and decoded separately, and statistics should let the engine avoid I/O. ORC's version of that idea differs from Parquet in structure (stripes with embedded indexes, not row groups with footer statistics), in how it stores nested data (separate length and presence streams, not definition and repetition levels), and in its ACID support. The result is comparable size and speed on most workloads, so the choice between them is mostly decided by the ecosystem.
terms: Stripe — a horizontal slice of the file (default 64 MB) that contains index data, column data and a stripe footer; it is the unit of parallel reading.
Stream — a sequence of bytes inside a stripe that holds one kind of data for one column, such as the values, the "present" bits for nulls, the lengths of strings, or the dictionary.
Row index — a set of entries, one per 10,000 rows by default, giving each column's statistics for that group and the positions in the streams where decoding can start.
Index stride — the number of rows between row-index entries (10,000 by default); it is the finest unit the reader can skip.
File footer and postscript — metadata at the end of the file: the schema, stripe locations, file-level statistics, and a small postscript that gives the compression type and the footer length.
Run-length encoding v2 — ORC's integer encoding, which chooses per block between four sub-encodings (short repeat, direct, patched base, delta).
SearchArgument (SARG) — the form of a filter that the engine passes to the ORC reader so it can test it against statistics and Bloom filters.
ACID base and delta files — Hive's way of storing updates to a table as new ORC files next to a base file, with row identifiers that let readers merge them.
history: Hive was created at Facebook in 2007–2008 to give analysts an SQL interface over Hadoop. Its first file formats were plain text and SequenceFile, and then RCFile (2009–2011), which stored data in column groups but was weak at compression and had no indexes. Facebook and Hortonworks, a company formed in 2011 by the Yahoo Hadoop team, worked on a better format. Owen O'Malley, one of the first Hadoop developers, led the design at Hortonworks. ORC was introduced with Hive 0.11 in 2013 and became a top-level Apache project in 2015, separate from Hive, with its own C++ and Java readers.
Parquet appeared in the same year from Twitter and Cloudera, so the Hadoop ecosystem had two similar formats from two camps. Hortonworks and Hive favoured ORC, while Cloudera, Impala and later Spark favoured Parquet. Meta (Facebook) kept a fork called DWRF for its own Presto-based warehouse, with extra features such as flat maps. In Hive 3 (2018) the ACID tables, which store updates and deletes as ORC delta files, became the default for managed tables.
After 2015 Parquet gained ground, mainly because Spark made it its default and because cloud data warehouses adopted it. ORC stayed strong inside Hive and in Trino installations with Hive heritage. The Iceberg table format supports Parquet, ORC and Avro data files, so ORC keeps a place in modern lakehouses. The ORC project continues to release versions with new compression codecs (zstd), better Bloom filters and support for newer data types, though at a lower pace of change than Parquet.
how: An ORC file has three parts: the body (a sequence of stripes), the file footer, and a postscript. The last byte of the file gives the length of the postscript. The postscript says which compression is used and how long the footer is. The footer lists the schema, the position of each stripe, row counts and statistics for the whole file. A reader therefore starts at the end, like a Parquet reader, and learns the layout with one or two reads.
Each stripe is self-contained and has three areas. The index data area holds the row index: for every column and every group of 10,000 rows, the minimum, maximum, sum (for numbers), count and null information, together with positions that say where in each stream the decoder must start to read that group. An optional Bloom filter for each group can be stored in the same area. The row data area holds the actual column data, as streams. The stripe footer lists the streams and the encoding of each column in this stripe. Stripe size is 64 MB by default and is often raised to 256 MB in Hive deployments, so that a stripe is a large, sequential read from HDFS or an object store.
The schema is a tree of types: primitives, and the compound types struct, list, map and union. Every node in the tree is a column with its own streams, which is simpler than Parquet's levels. A nullable column gets a PRESENT stream of bits that marks which rows have a value, and the DATA stream stores only the non-null values. A list or map column gets a LENGTH stream with the number of children for each row, and its children are separate columns. To read a struct field inside a list, the reader reads the list's lengths and the child column; it does not read other fields of the struct. This layout is easy to vectorize, because a reader can decode a whole batch of values from a stream into an array.
Encodings are chosen per column per stripe. Integers use run-length encoding version 2, which picks for each block of up to 512 values the best of four modes: SHORT_REPEAT for a few identical values, DIRECT for bit-packed values, PATCHED_BASE for mostly small values with a few outliers (the outliers are stored separately as patches), and DELTA for sorted or evenly stepped values. Strings use either dictionary encoding or direct encoding, and the writer decides per stripe: if the number of distinct values is small compared with the number of rows (by default below about 80% of the row count), it uses a dictionary; otherwise it writes the strings with their lengths. After encoding, each stream is compressed in chunks (default 256 KB) with zlib, Snappy, LZ4 or Zstandard, so a reader can decompress a chunk independently, which is how the row index can point into the middle of a stream.
Reading uses three levels of skipping. First, file-level and stripe-level statistics are compared with the filter, and stripes that cannot match are skipped. Second, within a surviving stripe, the reader loads the row index for the filtered columns and tests each 10,000-row group's min and max, or its Bloom filter, and skips groups that cannot match. Third, for the groups that remain, it uses the stored stream positions to jump straight to the first byte of the group, decompresses only the needed chunks, and decodes. The row index inside the stripe makes this second step cheap, because it is read together with the stripe data, instead of in a different place.
Hive ACID is built on top. A transactional table is a directory with a base directory (all rows as of some transaction) and delta directories (inserts, updates, deletes from later transactions). Each ORC file has hidden columns: operation type, original transaction ID, bucket, row ID and current transaction ID. A reader merges base and delta files by row ID, skipping deleted or superseded rows. A compactor rewrites deltas into a new base, as in a log-structured design. This is the same family of ideas as merge-on-read in Hudi and delete files in Iceberg, and it came earlier.

example: A table of 1 billion log rows has a column user_id (64-bit), and the file is split into stripes of about 2 million rows (64 MB). That makes 500 stripes. The user_id values are random, so each stripe has a min near 0 and a max near the top of the range. The query is SELECT * FROM logs WHERE user_id = 8123456789.
Without Bloom filters, the stripe statistics and the row index all contain the full range, and nothing can be skipped. The reader decodes all 1 billion user_id values, which is 8 GB before compression. Now enable Bloom filters on user_id with the default false-positive probability of 5%. With 10,000 rows per group, a Bloom filter needs about \( 1.44 \times \log_2(20) \approx 6.2 \) bits per key, so about 62,000 bits or 7.8 KB per group. A stripe has 200 groups, so the Bloom filters cost about 1.55 MB per stripe, which is 2.4% of the 64 MB stripe: a small price.
In each stripe the reader loads the user_id row index and Bloom filters (1.55 MB) and checks all 200 groups. Only the group that really contains the value (at most one, if the ID is unique) and about 5% of the other groups give a false positive: 0.05 × 199 ≈ 10. So the reader decodes about 11 groups × 10,000 rows = 110,000 rows from the stripe, instead of 2 million. That is 5.5% of the decode work. But this is true of every stripe, because the stripe-level statistics cannot exclude any of them. Over 500 stripes the reader still loads 500 × 1.55 MB = 775 MB of Bloom filters, and decodes about 5.5% × 8 GB = 440 MB of user_id data. Compare it with 8 GB: the saving is a factor of about 6.5 in bytes, which sounds modest.
To do better, sort the data by user_id inside the table. Now each stripe holds a narrow range of IDs, and the stripe statistics alone exclude 499 of the 500 stripes. The reader loads one stripe's index, finds one group via min/max, and decodes 10,000 rows. This changes the cost from "hundreds of MB" to "a few MB" and shows again that skipping works because of clustering, and Bloom filters are the fallback when you cannot cluster by that column.
A small encoding example: the integer sequence 7, 7, 7, 7, 7 is stored by RLE v2 SHORT_REPEAT mode as a header byte plus one value, 2 bytes instead of 40; the sequence 1000, 1010, 1020, 1030 is stored in DELTA mode as base 1000, delta 10 and a count, again a few bytes. This is why timestamps and IDs in ORC often cost well under 2 bytes per value.
intuition: A warehouse where each aisle (stripe) has its own small inventory list attached to the front, so you can decide what to fetch without leaving the aisle.
ORC differs from Parquet by putting index data next to the data it describes, inside each stripe, and by giving each node of a nested schema its own streams. The first choice means one big sequential read gets both the index and the data; the second means a decoder never needs to rebuild structure from levels. Both choices come from being designed with a query engine (Hive) in mind that processes data in batches and wants predictable, sequential I/O on HDFS. The cost of choices designed around one engine is that other engines have to adopt them later.
mistakes: People often think ORC is obsolete. In fact it is actively maintained, well supported by Hive, Trino and Spark, and an official data file format in Iceberg. It is less common in new stacks, but not unsupported.
People often think ORC compresses much better than Parquet (or the reverse). In fact the sizes are close and depend on data, encoder settings and compression codec. Published comparisons differ by workload, and the difference is often within 10 to 20%. Test with your own data.
People often think Bloom filters make every filter fast. In fact they help equality filters on high-cardinality columns where min and max cannot skip, and they cost space and write time. They do nothing for range filters, and they are not needed for sorted columns.
People often think the stripe is the same as a Parquet row group. In fact a stripe contains its own indexes and footer and is meant to be read in one large I/O, while a Parquet row group has its statistics in the file footer. The two play similar roles but are laid out differently.
People often think ACID tables in Hive are a property of ORC. In fact ORC only provides the file format and hidden columns; the transactions, compaction and locking are Hive's metastore and compactor. Other formats could carry the same idea, as table formats now do.
tradeoffs: Choose ORC when your data platform is built on Hive with ACID tables, when the main engines are Hive and Trino, or when you already have large ORC datasets and the conversion cost is high. Choose Parquet when you want the widest support across Spark, Snowflake, BigQuery, DuckDB, pandas and the major table formats, which now default to it. What you give up with ORC is breadth: some tools read it poorly or not at all.
Choose smaller stripes (32–64 MB) when memory per writer task is limited or when you need finer skipping; choose larger stripes (256 MB) for sequential scans on HDFS or object stores, where each stripe read should be a big request. Large stripes need more writer memory, because the writer buffers the whole stripe before flushing it.
Choose Bloom filters for equality lookups on high-cardinality columns that you cannot sort by (user IDs, device IDs), and accept 2–5% extra size. Choose sorting (or bucketing and sorting) instead when the same column is also used in joins and range filters, since clustering makes min/max useful and costs no space.
Choose Zstandard for new data when read cost and size matter, Snappy or LZ4 when CPU time matters most. Choose Hive ACID only when you need SQL updates and deletes inside a Hive-centred platform; for new lakehouse tables, a table format such as Iceberg is usually simpler and works with more engines.
friction: The main problem of ORC is ecosystem reach. Most new engines implement Parquet first, and some read ORC through older or less-tuned code paths. Python and Rust libraries for ORC are less mature than for Parquet. Cloud warehouses commonly ingest Parquet more smoothly. Teams that adopt ORC today usually have a reason from the past, in the form of existing Hive tables.
The format has also some technical limits. Stripes are large and buffered in memory by the writer, so writers with many partitions open at once (dynamic partitioning in Hive) can run out of memory, which is a known failure mode. Small files hurt as in all columnar formats, because each file has a postscript, footer and at least one stripe. ORC files with many columns have large indexes per stripe, and with a Bloom filter on many columns the write cost grows.
Evolution of schema is limited to what the engine implements: ORC files carry column names and, in newer versions, an optional Iceberg-style column ID attribute, so renames need the table layer to map names. Hive ACID tables have their own pain: many small delta directories degrade reads until compaction runs, the compactor must be monitored, and the metastore tables that track transactions can become a bottleneck at high rates.
Finally, ORC has less activity in new feature design than Parquet, which has the larger community. Features such as a standard semi-structured type and geospatial types arrived in the Parquet world first. For a long-lived platform, the risk is slow convergence with the rest of the ecosystem, not a technical failure.
practice: If you run Hive or Trino on HDFS or object storage with existing ORC data, keep it and tune it rather than convert. Set the stripe size to 128–256 MB for large tables, keep the default 10,000-row index stride unless profiling says otherwise, and use Zstandard or Snappy compression. Write data sorted by the columns that queries filter on, because the stripe and row-index statistics then skip most of the file.
Enable Bloom filters (orc.bloom.filter.columns) for high-cardinality equality columns that you cannot sort by, with a false-positive probability of 0.01 to 0.05 (orc.bloom.filter.fpp). Check that the engine really pushes the filter down: in Hive set hive.optimize.index.filter=true, in Spark spark.sql.orc.filterPushdown=true, and look at the query plan for the pushed predicate. In Trino, use the ORC reader statistics in EXPLAIN ANALYZE to see how many stripes and row groups were skipped.
For ACID tables, schedule compaction (minor compaction merges delta files, major compaction rewrites into a new base) and monitor the number of delta directories per partition. Avoid many concurrent small writers. Use orcfiledump (java -jar orc-tools) to look at a file's stripes, encodings and statistics when queries are slow: it shows whether stripes are well sized and whether statistics are selective.
For a new platform, choose Parquet unless Hive ACID or a Trino-on-Hive stack argues for ORC. If you use Iceberg, the choice is per table through write.format.default, and mixing is allowed; but keep one format per table to simplify tuning. When you migrate from ORC to Parquet, do it through the table format (rewrite data files) and validate row counts and checksums on a sample before dropping the old files.
interview: How does ORC skip data inside a stripe, and how does this differ from Parquet? || ORC stores a row index inside each stripe with min/max/sum/count and stream positions for every 10,000 rows, plus optional Bloom filters, so the reader can test groups and seek directly to those that match. Parquet keeps column-chunk statistics in the footer, and finer page-level skipping came later with the page index.
Why does ORC need less machinery than Parquet for nested data? || It gives each node of the type tree its own streams (a PRESENT stream for nulls, a LENGTH stream for lists and maps), so structure is explicit. Parquet flattens nested fields into leaf columns and rebuilds records from repetition and definition levels.
An ORC table has a Bloom filter on user_id but the query still reads all stripes. Why? || Stripe-level statistics cannot exclude any stripe because IDs are random, so every stripe's row index and Bloom filters must still be loaded. The Bloom filter removes most 10,000-row groups inside each stripe, but not the per-stripe cost. Sorting or bucketing by user_id is what skips whole stripes.
How do Hive ACID tables apply an UPDATE on ORC files, and what keeps reads fast? || The update is written as a delete event plus an insert in a new delta directory with row IDs; readers merge base and delta files by row ID. A compactor periodically folds deltas into a new base file, and without it the number of delta files grows and reads slow down.
You inherit a 500 TB ORC warehouse and a team wants everything in Parquet. How do you decide and migrate? || Measure first: take a sample of tables, convert, and compare size, query time and engine support, since gains are often under 20%. If the reason is engine reach or table-format adoption, migrate incrementally through Iceberg by rewriting data files table by table, validate counts, and keep ORC where Hive ACID is used.
quiz: What is the default number of rows between row-index entries in ORC? || 10,000 rows (the index stride); it is the smallest unit the reader can skip.
Why are ORC streams compressed in chunks? || So a reader can decompress a chunk independently. The row index stores positions that point into the middle of a stream, and chunking lets the reader start at the right chunk instead of decompressing from the beginning.
A stripe holds 2 million rows in 200 groups, with a 5% false-positive Bloom filter. About how many groups are decoded for an equality filter on a unique key? || One true match plus about 0.05 × 199 ≈ 10 false positives, so about 11 groups, which is 5.5% of the stripe.
You sort a 500-stripe ORC table by user_id and query one ID. How many stripes are read, and why? || About one, because each stripe now covers a narrow ID range and the stripe statistics exclude the other 499.
Your company must choose between ORC and Parquet for a new Spark, Trino and Snowflake lakehouse. Which, and what would change your answer? || Parquet, for the broadest support, including Iceberg and Delta defaults. The answer changes if the platform is Hive-centred with ACID tables and large existing ORC data.

@@ arrow
value: Apache Arrow is a specification for how to lay out a table in memory, column by column, so that different programs, written in different languages, can share the same bytes without converting them. It also comes with libraries (C++, Java, Rust, Go, Python, JavaScript, C# and more) that build, move and compute on data in that layout. Before Arrow, each tool kept its own in-memory representation: pandas used NumPy arrays and Python objects, Spark used JVM objects or its own binary rows, databases used their own pages. Moving data between them meant serializing to bytes, copying and parsing again, and that conversion often cost more than the actual computation.
Arrow makes the in-memory format a shared standard, in the way that Parquet is a shared standard on disk. A column of one million 32-bit integers is a validity bitmap plus a contiguous 4 MB buffer, aligned for vector instructions. Any library that knows the specification can read that buffer directly. Two processes on one machine can share it through shared memory or a memory-mapped file with no copying, and two libraries in one process can pass a pointer to it through a small C interface. Between machines, Arrow's IPC format and Flight protocol send the same buffers over the network with almost no encoding work.
For the layer above (pandas and Polars, DuckDB, Spark's Python integration, Ray, data warehouses' client drivers, machine learning data loaders), Arrow removes the conversion cost between steps of a data pipeline. Its lower concept is the OLAP idea (L1): analytical computing works on columns, and columnar memory is what lets CPUs process many values per instruction (SIMD) and keeps caches full of useful data. Arrow takes the columnar idea that Parquet uses for disk and applies it to RAM, where the goals are different: not the smallest size, but fast random access and direct computation.
terms: Array — a sequence of values of one type, stored in a few contiguous buffers; the in-memory form of a column.
Validity bitmap — one bit per slot that says whether the value is present (1) or null (0); this is how Arrow stores nulls without a special value.
Buffer — a contiguous block of memory (values, offsets or bitmap); arrays are made of buffers, and buffers are shared, not copied.
Offsets buffer — for variable-length data such as strings, an array of positions where each value starts in a separate data buffer.
Record batch — a group of equal-length arrays (the columns) with a schema; the unit that is sent over IPC and Flight.
IPC format — Arrow's serialization for record batches: the schema, then batches, written so that the receiver can use the bytes in place.
C Data Interface — a tiny C struct definition (ArrowSchema and ArrowArray) that lets two libraries in one process exchange arrays by passing pointers, with no copy and no shared code.
Flight and ADBC — Flight is a gRPC-based protocol for moving Arrow batches between services; ADBC (Arrow Database Connectivity) is a database client API that returns results as Arrow batches.
history: Wes McKinney created pandas in 2008, and by 2015 he saw its limits: pandas stored strings as Python objects, copied data often, and needed several times the data size in memory. In the same period, Jacques Nadeau, who led Apache Drill, had built an in-memory columnar format called ValueVectors. Others at Impala, Spark, Kudu, Parquet and Cassandra faced the same cost of converting data between systems. In 2015–2016 they agreed to define one format. Arrow was announced in February 2016 as a top-level Apache project, with the Drill code as a starting point and committers from about a dozen existing projects, a fast route for an open standard to be accepted.
The early years built the specification, the C++ and Java libraries and the Python bindings (PyArrow), and a file format, Feather, for saving data frames quickly. In 2017 McKinney's blog post "Apache Arrow and the '10 Things I Hate About pandas'" explained the problems that Arrow should solve in pandas. Spark 2.3 (2018) used Arrow to speed up the transfer of data between the JVM and Python workers, which turned vectorized Python UDFs from a curiosity into a normal tool.
Then the ecosystem grew in layers. The Arrow Flight RPC protocol (2018–2019) moved data between services at network speed; Flight SQL (2022) added a SQL client protocol. The C Data Interface (2020) allowed in-process sharing across libraries and languages, which is how DuckDB, Polars, Velox and many Python packages exchange data. ADBC (2022–2023) offered a driver API that returns Arrow, so that clients do not decode rows only to rebuild columns. Compute engines built on Arrow appeared: DataFusion (Rust), Acero (C++), and the Polars library. The specification grew new types: dictionary arrays, run-end encoded arrays, and "string view" arrays, a layout for strings used by DuckDB and Velox, adopted into the format in 2023–2024.
The project is still active: version 26.0.0 was released on 9 October 2026, with new releases every few months. Arrow also changed pandas: pandas 2.0 (2023) added Arrow-backed data types, and Arrow strings are now a common choice for text columns. Its role is infrastructure: most users never write "Arrow" in their code, but their tools use it underneath.
how: The layout rules are the core of Arrow, and they are simple. Each array has a logical type and a physical layout made of buffers. A fixed-width type such as int32 or float64 has a validity bitmap and a values buffer with the values packed one after the other. Value i lives at byte i × width, so access by position is a multiplication and a load. A boolean array packs one bit per value. Null slots keep their position in the values buffer (with unspecified content), which is why access stays position-based, and the bitmap says which slots to ignore.
Variable-length types use offsets. A string array has a validity bitmap, an offsets buffer of n + 1 integers (32-bit, or 64-bit for the "large" variants), and one data buffer of UTF-8 bytes. The string i is the bytes from offsets[i] to offsets[i+1]. A list array has offsets into a child array, and a struct array holds one child array per field, all of the same length. Nested data is therefore a tree of flat arrays, which gives the same columnar benefits as flat data. Dictionary arrays store integer codes plus a dictionary, like Parquet's dictionary encoding but kept in memory in that form so engines can compute on codes directly. Run-end encoded arrays store runs. The newer string view type uses 16-byte entries that hold short strings inline and point to long ones, which makes comparisons and filtering of short strings much faster.
Memory is allocated in aligned buffers. The specification requires 8-byte alignment and recommends 64 bytes, which matches the cache line size and the width of vector instructions (AVX-512), and padding to multiples of 64 bytes. The aim is that compute kernels can process data with SIMD instructions without alignment checks, and that arrays can be sliced without copying: a slice is an offset and length on the same buffers. These properties are why Arrow is called "zero-copy": a sub-array or a filtered view shares memory with the original.
A record batch groups arrays of equal length plus a schema; a table is a list of batches (chunks) that share a schema, so a large table can be built from many batches without copying. For moving data, the IPC stream format writes the schema as a message, then each batch as a metadata message (written in FlatBuffers) followed by the raw buffers, aligned. The receiver reads the message and then sets its arrays directly onto the received bytes. The IPC file format adds a footer with batch positions, so a reader can memory-map the file and jump to any batch; opening a 10 GB Arrow file this way takes microseconds, as nothing is parsed. Feather v2 is this file format.
Process boundaries are crossed in three ways. In the same process, two libraries use the C Data Interface: one passes a pointer to a struct of pointers, with a release callback for ownership, so a DuckDB query can scan a Polars or PyArrow table and return a result as Arrow without copying a byte. Between processes on a machine, shared memory or memory-mapped IPC files give the same effect. Between machines, Flight sends batches over gRPC streams in parallel from many endpoints; because the wire format equals the memory format, the cost is mostly the network, not the CPU. ADBC drivers for databases such as PostgreSQL, SQLite, Snowflake and BigQuery return results in this form.
On top of the format, the libraries provide compute kernels: vectorized functions for filtering, sorting, hashing, arithmetic, string operations and aggregation that run over whole arrays with SIMD, and handle the validity bitmap in bulk. Query engines (DataFusion, Acero, DuckDB's Arrow scans, Velox) build plans on these. Arrow also reads and writes Parquet, CSV, JSON and ORC, so a common route is Parquet on disk to Arrow in memory: the Parquet reader decodes pages directly into Arrow buffers, which is faster than going through any row-based intermediate form.
Types are described by a schema that lists field names, logical types and nullability, and the same schema travels with every IPC stream and every C Data Interface call. The type system is richer than a database's: besides integers, floats, decimals, dates, times, timestamps with units and time zones, strings and binary, it has lists, fixed-size lists (used for embeddings), structs, maps, unions and dictionaries. Extension types let a library attach its own meaning to a standard storage type, for example a UUID stored as 16 fixed bytes or a geometry stored as binary, without changing the physical layout. Memory comes from pools that track allocations, so a program can see how many bytes its arrays use, which is how Arrow-based tools detect hidden copies and leaks.

example: Take a column of four 32-bit integers with a null in the second slot: [1, null, 3, 4]. Arrow stores a validity bitmap with one bit per slot, least significant bit first. Slot 0 is valid, slot 1 is null, slots 2 and 3 are valid, so the bits from slot 0 to 3 are 1, 0, 1, 1, which as a byte is 0b00001101 = 13. The values buffer holds four 4-byte integers, 16 bytes; slot 1 contains an unspecified value that nobody reads. The padded size of the two buffers is 64 bytes for the bitmap and 64 bytes for the values.
Now the string column ["ab", null, "cde"]. The data buffer holds the bytes abcde, 5 bytes. The offsets buffer holds four integers: 0, 2, 2, 5. String 0 is data[0:2] = "ab", string 1 (null) is the empty range [2:2] and is marked invalid in the bitmap, string 2 is data[2:5] = "cde". To get the length of string i you subtract two neighbours, and to slice the array from slot 1 you only change the start offset and length; no data is copied.
Now the cost comparison, with rough numbers. A data scientist has a Spark DataFrame with 10 million rows and 20 numeric columns, 1.6 GB of data, and calls toPandas(). The older path collected rows to the driver as Java objects, pickled them, and built Python objects: for 10 million rows this took well over a minute and used several times the data size in memory. With Arrow enabled, Spark converts each partition to Arrow record batches in the JVM, sends the bytes to the driver, and PyArrow turns the buffers into NumPy-compatible arrays with little or no copy. The conversion is limited by memory bandwidth and network; for 1.6 GB a few seconds is typical. The difference of 10 to 50 times is the main reason Arrow became widely used.
A second example is in-process sharing. A Polars DataFrame of 100 million rows (800 MB per numeric column) is passed to DuckDB with duckdb.sql("SELECT ... FROM df"). DuckDB reads the Arrow arrays through the C Data Interface, so no copy is made, and it can start executing at once. If both tools had their own formats, the 800 MB would have to be converted first, costing about as much time as a scan, and doubling the memory.
A third example is a Flight call. A service holds a 5 GB table as Arrow batches on 5 nodes. A client calls GetFlightInfo, receives 5 endpoints, and opens 5 parallel streams. Each stream carries 1 GB over a 10 Gb/s link at about 1 GB/s, so the whole table arrives in roughly 1–2 seconds, with nearly no decoding on the client; JDBC would send the same data row by row and parse it, usually at a few tens of MB/s per connection.
intuition: A shared shipping container standard: because every ship, truck and crane uses the same box, nothing needs to be unpacked and repacked at each port.
Conversion cost between systems grows with the square of the number of systems: each pair needs its own translator. A single shared memory layout reduces it to one format per system. The layout is chosen to be good for computation, not for compactness: fixed-width slots for direct indexing, offsets for variable data, a bitmap for nulls, 64-byte alignment for the hardware. A format that is good for the CPU is a good lowest common denominator, because every engine wants to compute on it, and the cost of agreeing on it is paid once.
mistakes: People often think Arrow is a file format that competes with Parquet. In fact Arrow is an in-memory format (and a way to move it); Parquet is a compressed on-disk format. They work together: a Parquet reader decodes pages into Arrow arrays. The Arrow IPC (Feather) file exists, but it is uncompressed or lightly compressed and is meant for fast local exchange, not for long-term analytics storage.
People often think "zero-copy" means free. In fact it means no copy of the data when you hand over buffers, but you may still pay to produce the Arrow arrays in the first place (decoding Parquet, converting from Python objects) or when a library does not support a layout and converts. Strings with nulls, nested types or non-standard types can cause hidden copies, so check with memory profiling.
People often think Arrow arrays can be updated in place like NumPy arrays. In fact Arrow arrays are treated as immutable: buffers are shared among slices and consumers, so changes would be visible to others. To "change" a value you build a new array. This is a design choice that makes sharing safe, and is a cost for workloads that update elements often.
People often think Arrow replaces databases or compute engines. In fact it is a data layout and a toolkit. It has compute kernels and some engines (DataFusion, Acero), but its main value is that other engines can interoperate.
People often think Arrow makes data smaller. In fact it usually makes it larger than Parquet, and it can be larger than compact row formats for sparse data, because it favours speed over size. A 1 GB Parquet file can need 3 to 10 GB in Arrow memory.
tradeoffs: Choose Arrow (as the in-memory or interchange format) when many steps of a pipeline, written in different tools or languages, pass large tables to each other, and the conversion cost shows in profiles. Choose to stay with a tool's native format when everything runs inside one engine that already has its own optimized layout; the benefit then is only at the edges.
Choose Arrow Flight or ADBC when clients read large results (hundreds of MB or more) from a service or database: they remove the row-by-row decoding of JDBC/ODBC and allow parallel streams. Choose JDBC/ODBC for small results and for the widest compatibility; the cost of the old drivers matters little at 10,000 rows. Flight needs a server that speaks it and gRPC-friendly networks; ADBC drivers exist for fewer databases than JDBC.
Choose IPC files (Feather v2) for scratch data and fast hand-off between processes on one machine, where memory-mapping gives instant reads. Choose Parquet for anything stored for days or more or moved over a network, where its compression (3–10× smaller) is worth the decoding time. A common rule: Parquet at rest, Arrow in flight and in memory.
Choose dictionary or string-view layouts when the data has many repeated or short strings and the engine supports them; they save memory and speed up filters. The cost is that not all consumers support every layout, and an unsupported type forces a conversion at the boundary.
friction: Arrow is a layout, not an agreement on semantics. Two libraries may support different subsets of types, handle time zones, decimals or nested nulls differently, or lag behind the specification (for example in string view or run-end support). The C Data Interface carries the type description, but the consumer must know what to do with it. Version mismatches between PyArrow, pandas, DuckDB and Polars are a regular source of errors in Python environments.
Memory is a real cost. Arrow's layout is uncompressed, and a table that is 2 GB in Parquet can take 10 GB in memory. Large strings and nested data have extra overhead from offsets and validity bitmaps. Because arrays are immutable, repeated small updates create new arrays, and long pipelines can hold several copies alive at once unless references are dropped.
Ownership across language boundaries is hard. The C Data Interface uses release callbacks, and a bug in lifetime management (releasing a buffer while another library still points to it) gives crashes that are difficult to debug. The ecosystem has also a wide surface: many libraries (C++, Rust arrow-rs, Go, Java, C#) implement the format separately, with different completeness and speed. A feature in the C++ library may take months to reach another.
Last, Arrow does not solve storage or distribution. It does not decide how data is partitioned, how updates are applied or how queries are planned. It lowers the cost of moving data between components, but pipelines still need table formats, catalogs and engines.
practice: Use Arrow where data crosses a boundary. In Python, read Parquet with PyArrow or Polars, hand data to DuckDB or Spark through Arrow (spark.sql.execution.arrow.pyspark.enabled=true for toPandas and pandas UDFs), and avoid converting to Python lists or row dictionaries in between. If you must use pandas, use Arrow-backed dtypes for strings, so you avoid Python objects and save memory.
Process big data in batches, not whole tables. Read record batches (for example 64,000 rows) from Parquet or Flight, compute on them, and release them; this keeps memory low and still gives vectorized speed. Prefer compute kernels (pyarrow.compute, Polars expressions, DuckDB SQL) to Python loops, which defeat the purpose of the layout. Use memory-mapped IPC files for large data that several local processes read.
For services that return data to analysts, offer an Arrow Flight (SQL) endpoint or ADBC driver next to JDBC. In Java, use the Arrow allocators carefully: close every vector and allocator, and run tests with memory-leak checks, because off-heap memory is outside the garbage collector. In Rust, arrow-rs and DataFusion are a good base for new engines; in C++, link against the shared library so that different packages use the same version.
Pin versions and test interoperability: when you upgrade PyArrow, run your pipeline tests against pandas, Polars and DuckDB versions you use. Keep Parquet as the long-term storage format, and treat Arrow IPC files as a cache. Profile memory (for example, pa.total_allocated_bytes()) to see hidden copies, and check the schema when passing data between tools, particularly timestamps (unit and time zone), decimals and large versus normal strings.
interview: Why can two libraries share an Arrow array with zero copies? || The layout is fully specified: a type, a validity bitmap and a set of buffers with known meaning and alignment. A library can wrap those buffers directly. In one process the C Data Interface passes pointers and a release callback, so no serialization or copy is needed, and ownership is handled by the callback.
How does Arrow store a nullable string column, and how do you read element i? || A validity bitmap, an offsets buffer of n + 1 integers and a data buffer of UTF-8 bytes. Check bit i of the bitmap; if valid, the value is data[offsets[i] : offsets[i+1]]. Slicing only changes the start and length.
Why is Arrow bigger than Parquet and why is that acceptable? || Arrow uses no compression or heavy encoding so that every value can be addressed by position and processed with SIMD without decoding. The extra memory buys speed in computation. For storage and network, where bytes cost more than CPU, you use Parquet or Arrow with light compression.
A Python service returns 5 million rows over JDBC and is slow. How would you improve it? || Profile first. Typically the cost is row-wise decoding and Python object creation. Switch to an Arrow-based path (an ADBC driver or a Flight SQL endpoint), fetch record batches in parallel, and keep the data in Arrow or Polars without converting to Python objects. Expect a large speedup for big results and no change for small ones.
What are the risks of sharing Arrow data between a JVM library and a native library in one process? || Lifetime and ownership: off-heap buffers are released by whoever owns them, and a premature release or a double release crashes the process. Also, type support can differ, and version mismatches can cause subtle errors. Use the C Data Interface release callbacks correctly and test with leak detectors.
quiz: What are the buffers of an Arrow string array? || A validity bitmap, an offsets buffer with n + 1 integers, and a data buffer with the concatenated UTF-8 bytes.
Why is Arrow called "zero-copy" for slices? || A slice is just an offset and a length over the same buffers, so no data moves. This works because buffers are immutable and shared.
The int32 column [1, null, 3, 4] is stored. What is the validity bitmap byte and how large is the values buffer? || The bits from slot 0 are 1, 0, 1, 1, so the byte is 0b00001101 = 13. The values buffer is 4 × 4 = 16 bytes (before padding), and the null slot's bytes are ignored.
A table is 2 GB as Parquet and 8 GB in Arrow memory. You have 16 GB. What do you do to process it? || Read it in record batches (or a few row groups at a time), filter and project columns early so only what you need is in memory, and use a streaming or out-of-core engine such as DuckDB or Polars lazy mode, instead of loading the whole table.
When should you not use Arrow Flight or ADBC instead of JDBC? || When results are small (thousands of rows), the database or tool has no mature driver, or the network blocks gRPC. JDBC is simpler and universally supported, and its decoding cost does not matter at that size.

@@ unity
value: Unity Catalog is a governance layer for data and AI assets. It gives every table, view, file volume, machine-learning model and function a three-part name (catalog.schema.object), keeps one central list of who may do what with each of them, records where data came from (lineage) and who touched it (audit), and hands out short-lived storage credentials so that users and engines never hold permanent cloud keys. Databricks introduced it in 2021 and made it generally available in 2022. In June 2024 Databricks open-sourced it under the Linux Foundation's LF AI & Data Foundation, so there is now a managed version inside Databricks and an open-source server.
The problem is that a lakehouse is only files in object storage, and file systems have a weak security model. Cloud storage permissions work on buckets and paths, not on tables, columns or rows. Each workspace or cluster once had its own Hive metastore with its own permissions, so the same table could be visible in one place and invisible in another, and a person who could read the files could ignore every table-level rule. Unity Catalog moves the decision point: the catalog, not the file system, decides who reads what, and the catalog is the only holder of the keys to the storage.
For the layer above (Databricks workspaces, Spark, SQL warehouses, Delta Sharing, machine learning registries, and external engines such as Trino, DuckDB or Flink through its APIs), Unity Catalog is the single front door to data. It stands on the L1 idea of a data catalog and governance layer: a catalog maps names to data, schemas and permissions. Unity Catalog adds a strict hierarchy, one account-wide metastore per region, a privilege model with inheritance, and credential vending. Open tables in Delta or Iceberg format remain the storage layer underneath, and the catalog stores only metadata and policy.
terms: Metastore — the top-level container of Unity Catalog metadata for an account and region; workspaces are attached to one metastore.
Catalog, schema, table — the three levels of the namespace (catalog.schema.table); catalogs usually represent an environment or domain, schemas a project or team.
Securable — any object that can have permissions: catalog, schema, table, view, volume, function, model, storage credential, external location, share.
Privilege and grant — a right such as SELECT or MODIFY given to a user, group or service principal on a securable; privileges on a catalog or schema apply to everything inside it.
Managed and external table — a managed table has its files stored and lifecycle-managed by the catalog; an external table points at files that already exist in a location the catalog knows.
Storage credential and external location — a stored cloud identity (such as an IAM role) and a path in object storage that it may access; together they let the catalog reach the data.
Credential vending — the catalog issues a temporary, narrowly scoped token for one table's storage path, for a short time, after it has checked the caller's permissions.
Row filter and column mask — a function attached to a table that hides rows or masks values based on who is querying.
history: Hive's metastore (2008) was the first widely used catalog for Hadoop tables, but it had weak security. Databricks customers ran many workspaces, each with its own metastore and its own table permissions, and used cloud IAM rules and cluster-level settings to approximate governance. This was hard to audit and easy to bypass. At the Data + AI Summit in 2021, Databricks announced Unity Catalog as a unified governance layer. It reached general availability in 2022, and from late 2023 Databricks enabled it by default for new workspaces.
The scope widened with each release. Unity Catalog added column-level lineage, system tables for audit and billing, volumes for non-tabular files, registered models for MLflow, row filters and column masks, Lakehouse Federation (querying external databases through foreign catalogs), and Delta Sharing for sharing data with other organizations. Attribute-based access control, based on tags, was added later so that policies can be written once and applied to many tables.
In June 2024 Databricks open-sourced the catalog and donated it to LF AI & Data. The same year, the Iceberg ecosystem moved toward the REST catalog specification and Snowflake donated the Polaris catalog to Apache, which made catalogs a visible strategic battleground after the table formats had converged. Unity Catalog responded by exposing Iceberg tables through an Iceberg REST endpoint and supporting Iceberg as a managed table format. The open-source server has continued to release frequently (the 0.5.x line in mid-2026), adding a catalog-managed Delta API, credential vending for several clouds, and a credential-scoped file system in its Spark connector.
how: The architecture has three parts: the catalog service, the engines and the cloud storage. The catalog service holds metadata in a database: the hierarchy of objects, their schemas, locations, properties, permissions, and (in the managed product) lineage and audit records. Engines never use the permission model of the cloud storage directly. They talk to the catalog over an API. Cloud storage holds the data files and trusts only the identities that the catalog controls.
Name resolution is the first step. When a user runs SELECT * FROM prod.sales.orders, the engine sends the three-part name and the user's identity to the catalog. The catalog finds the object and checks privileges. Privileges are inherited down the hierarchy: SELECT granted on a schema applies to all current and future tables in it, and USE CATALOG and USE SCHEMA are needed on the parents to see the path at all. Groups from the identity provider are used to grant to many people at once. The resolution result contains the table's format, schema and storage location.
Then comes credential vending, the key mechanism. For managed tables and registered external locations, the catalog holds a long-lived cloud identity, for example an IAM role in AWS, a managed identity in Azure or a service account in GCP. After approving a request, it asks the cloud for a temporary credential scoped to exactly that table's path and the needed access (read or read-write), such as an AWS STS token with a path-restricted policy, an Azure SAS token or a Google downscoped token, and returns it to the engine. The credential lives for a short time, typically up to an hour, and can read nothing else. The engine then reads Parquet files directly from object storage with that credential, so the catalog is not in the data path and does not become a bandwidth bottleneck. Users never receive or manage cloud keys, which also means that revoking a permission in the catalog takes effect at the next credential request.
Fine-grained controls need a trusted engine. Row filters and column masks are functions defined in the catalog and attached to a table. In Databricks, the compute is trusted: it applies the filter or mask inside the query engine, and the cluster is arranged so that users cannot run code that reads the raw files. For an external engine that receives a raw storage credential, the catalog cannot force it to apply the filter. So external access to tables with row filters or masks is typically restricted, or limited to engines that are trusted or that go through a controlled service. This is the main architectural limit of credential vending, and it applies to every catalog that uses it.
Lineage and audit come from the engine's side. In the managed product, the compute reports which tables and columns each query or job reads and writes, and the catalog stores these edges as a graph, down to column level. Audit logs and system tables record each access. Both are queryable with SQL, so governance reports use the same tools as the data.
Storage is organised by two more objects. A storage credential wraps a cloud identity, and an external location binds one path in object storage to one credential. A catalog or schema can also have a managed storage location, which is where the files of managed tables are placed in directories named by IDs, not by table names. The catalog checks that external locations do not overlap, because two overlapping paths would give two different permission answers for the same file. Volumes use the same machinery for files that are not tables (images, model files, CSV drops): a volume is a governed directory with a three-part name, and access to /Volumes/prod/sales/raw/file.csv goes through the same privilege check and credential vending as a table. Models and functions are securables in the same hierarchy, so the same GRANT syntax governs them. Since Delta and Iceberg keep their own transaction metadata next to the data, the catalog does not need to track every file; it tracks the table and its location, and, for catalog-managed tables, it can also take part in the commit so that it knows the latest table version.
Open interfaces make the catalog usable from other tools. The open-source server exposes a REST API for catalogs, schemas, tables, volumes, functions and models, plus credential vending endpoints. For tables, it can present Delta tables to Iceberg readers through the Iceberg REST catalog interface, and it supports Delta Sharing. Engines such as Spark (through a connector), Trino, DuckDB and others can resolve names and obtain credentials through these APIs, so one catalog can govern the data across tools, as far as each tool implements the API.

example: A company has a catalog prod with a schema sales and a managed table orders. Alice, an analyst, belongs to the group analysts. The administrator runs three statements: GRANT USE CATALOG ON CATALOG prod TO analysts; GRANT USE SCHEMA ON SCHEMA prod.sales TO analysts; GRANT SELECT ON TABLE prod.sales.orders TO analysts. Alice has no cloud account keys and no direct access to the storage bucket.
Alice runs SELECT order_id, amount FROM prod.sales.orders WHERE region = 'EU'. Her engine sends the name and her identity to Unity Catalog. The catalog checks the three privileges (catalog, schema, table), finds the table location s3://lake/prod/orders, and asks AWS STS for a token whose policy allows only s3:GetObject (and ListBucket) on that prefix, expiring in about an hour. The engine reads the Delta transaction log and the Parquet files with this token. The audit table records: alice, SELECT, prod.sales.orders, time, and the lineage graph records the columns read.
Now a row filter. The administrator defines a function that returns true when the row's region is in the user's allowed regions, and attaches it to the table as a row filter. Alice, who is in the group eu_analysts, sees only EU rows even if she writes no WHERE clause. A column mask on customer_email returns a hash for everyone outside the group pii_readers. The compute engine applies both inside the query plan, so Alice cannot bypass them with a different query.
Next, take revocation. The administrator runs REVOKE SELECT ON TABLE prod.sales.orders FROM analysts. Queries that start after this fail at name resolution. A query that started a few minutes earlier still holds a token and can read until it ends or the token expires (up to the token lifetime). This is a design cost: revocation is immediate for new requests and bounded by the token lifetime for running ones.
A scale example. A company has 8 workspaces, 60,000 tables and 2,000 users. With per-workspace Hive metastores, an auditor must check 8 permission sets, and moving a project from one workspace to another breaks access. With one Unity Catalog metastore, the same question is one SQL query on the system tables ("who can read prod.sales.orders and who read it last month?"), and moving a project means attaching the catalog to another workspace. Migrating from the old metastore is a project of weeks to months: upgrade tables with SYNC or deep clone, change three-part names in code, replace cluster-level credentials with storage credentials and external locations, and test jobs.
intuition: A front desk for all data: it knows where everything is, checks your badge, and hands out a temporary key for exactly one room.
The design is natural because storage is dumb and engines are many. If each engine enforces permissions, you need to trust and update every engine, and users can always read the files themselves. If the catalog owns the only keys and gives out narrow, short-lived copies, then every engine has to ask the same place, the rules live in one location, and "who accessed what" has a single source of truth. The catalog stays small and fast because it handles only metadata and tokens, while the heavy data traffic goes directly between engines and storage.
mistakes: People often think Unity Catalog is a metastore in the old Hive sense only. In fact it replaces the Hive metastore's single job (names to locations) and adds security, lineage, audit, sharing, model and file governance. It is closer to a control plane for data than to a table index.
People often think the open-source and the Databricks versions are the same. In fact the managed product has more: the full governance model, lineage, system tables, attribute-based policies and many integrations. The open-source server implements the core API, credential vending and a growing set of features, but you need to check each feature against the release you run.
People often think the catalog enforces everything for every engine. In fact enforcement of row filters and column masks needs a trusted engine. An engine that receives a raw storage credential can read whole files. For untrusted or external engines the practical options are to deny access to filtered tables or to route access through a service that enforces policy.
People often think credential vending makes revocation instant. In fact it makes it instant for new requests only; tokens already issued stay valid until they expire. For highly sensitive data, use short token lifetimes and be aware of this window.
People often think moving to Unity Catalog is only a configuration change. In fact names change from two-part (database.table) to three-part, legacy table types and cluster access modes need migration, and external locations must not overlap. Jobs, dashboards and permissions all need review.
tradeoffs: Choose the managed Unity Catalog when your lakehouse runs mainly on Databricks and you want governance, lineage and audit without building them; the cost is dependence on the vendor's platform, though the data stays in open formats. Choose an open-source catalog (Unity Catalog OSS, Apache Polaris, Nessie, Lakekeeper) when you run many engines and want to own the metadata layer or avoid license fees; the cost is that you operate it, and features such as lineage and fine-grained policy are less complete.
Choose Unity Catalog or another REST catalog over the Hive Metastore for new projects: you get real permissions, credential vending and atomic table commits via the table format. Keep the Hive Metastore only for legacy engines that cannot talk to anything else. The cost of migration is moderate for tables and high for the many jobs that hard-code two-part names and cluster credentials.
Choose managed tables when you want the platform to manage file layout, cleanup and optimization, and you can accept that files live in the catalog's storage root. Choose external tables when other systems also write or read the files directly, or when data already exists and must stay in place. Managed tables give the catalog more control (and features); external tables give you more freedom and more responsibility.
Choose a single metastore per region with catalogs per environment (dev, staging, prod) for simple governance; choose several metastores or workspaces only for hard isolation requirements, such as separate legal entities. More metastores make cross-team sharing harder, and sharing then needs Delta Sharing or federation.
Choose to expose tables to external engines through the Iceberg REST interface when the readers are not Databricks engines; you gain openness, but fine-grained filters may not be enforceable there, so keep the sensitive tables restricted.
friction: The open-source and managed versions diverge, and a feature in the documentation of one may not exist in the other. Teams that want portability must test their workflow against the open-source server. The catalog is also now a critical dependency: if it is unavailable, new queries cannot resolve names or get credentials, so availability and latency of the catalog service matter for every job.
Migration is the day-to-day pain. Hive-metastore-era tables, mounts, cluster-scoped credentials and notebooks that access paths directly (dbfs:/mnt/...) must be converted to catalog objects and volumes. Overlapping external locations are not allowed, which forces a cleanup of storage layout. Large estates need tooling and many weeks of testing.
Multi-engine governance depends on each engine. Row filters, masks and attribute-based policies are only as strong as the weakest engine that gets credentials. Engines differ in their support for the catalog's APIs, for Iceberg versus Delta, and for credential refresh during long jobs. Permissions can also become complicated: with inheritance, groups, ownership and defaults, answering "why can this user read this table?" may need tooling.
Finally, governance is only as good as the process. Catalog structure (what is a catalog, what is a schema), naming, ownership and tags need agreement across teams. A catalog can enforce the rules it is given, but it does not decide them, and many projects fail from an unclear ownership model, not from the product.
practice: Design the namespace first. A common pattern is one catalog per environment and domain (prod_sales, dev_sales) and schemas per data product or layer (bronze, silver, gold). Make groups, not users, the unit of grants, and grant at the schema level for simplicity. Give each catalog an owner team, and use tags (PII, owner, retention) so that policies and audits can select by tag.
Move storage access to the catalog. Create storage credentials and external locations for your buckets, register each path once (no overlaps), remove broad cluster-level instance profiles and mounts, and use volumes for files that are not tables. Prefer managed tables for new data so the platform handles layout and cleanup; use external tables for data shared with other systems.
Adopt fine-grained controls where they matter: row filters and column masks for personal data, tag-based policies to avoid per-table work, and dynamic views as a fallback. Test these as a non-privileged user, and check what external engines can see. Use system tables for audit: write a standing query for "who read the PII-tagged tables this week" and review it. Use lineage to find the owners of downstream tables before changing a column.
For migration from the Hive metastore, inventory tables and dependencies, use the SYNC command or deep clone for tables, convert code to three-part names, migrate jobs in batches, and keep the legacy catalog read-only until the end. For multi-engine setups, test each engine against the catalog's REST API, check token refresh in long jobs, and decide explicitly which tables external engines may see.

@@ hms
value: The Hive Metastore (HMS) is a service that stores the metadata of tables: their names, columns and types, file formats, storage locations and partitions. It began as part of Apache Hive in 2008, and it became the shared catalog of the Hadoop world, used not only by Hive but also by Spark, Presto and Trino, Impala, Flink and later the first lakehouse systems. When an engine reads a table called logs, it asks the metastore what the table is: where its files are, how to decode them, and which partition directories hold the data that a filter needs.
The problem it solved is basic. Files in HDFS have no meaning by themselves. A directory full of text or ORC files is not a table until someone says what the columns are, how the rows are encoded and which part of the path is a partition value. Before Hive, every MapReduce job carried this knowledge in its own code. Hive put it in one service, backed by a relational database, so that SQL users could write SELECT * FROM logs WHERE dt = '2026-07-04' without knowing paths, and so that many tools could share definitions.
For the layer above (Hive itself, Spark SQL, Trino's Hive and Iceberg connectors, Impala, AWS Glue's compatible API), HMS is the glue between a table name and a set of files. It stands on the L1 idea of a data catalog: map names to data, schemas and permissions. HMS implements the first two well and the third only weakly. It is now labelled legacy, because modern catalogs add what it lacks: real access control, atomic commits across files, credential handling and open REST APIs. Yet it is still everywhere, because so many engines and so much data depend on it.
terms: Metastore service — the network server (Thrift API, usually port 9083) that engines call to read and change table metadata.
Backing database — the relational database (MySQL, PostgreSQL, Oracle or SQL Server) where the metastore keeps all its data in tables.
Storage descriptor — the part of a table or partition definition that says where the files are, which input and output format and which SerDe read them, and the columns.
SerDe — serializer/deserializer, the class that turns bytes in a file into rows and back, for example the ORC, Parquet or JSON SerDe.
Partition — a subset of a table identified by values of partition columns (for example dt='2026-07-04'), stored in its own directory and listed in the metastore.
Managed and external table — a managed table's data is owned by Hive and deleted with the table; an external table only points at data owned by someone else.
Partition pruning — using a filter on partition columns to ask the metastore only for matching partitions, so the engine lists only those directories.
Table statistics — row counts, sizes and column statistics stored in the metastore, which query optimizers use to plan joins.
history: Facebook created Hive in 2007 and open-sourced it in 2008, to let analysts run SQL on Hadoop instead of writing MapReduce jobs. SQL needs a schema, so Hive stored table definitions in a relational database, first an embedded Derby database for tests and MySQL for production. The code that managed this metadata became the metastore. It had a Thrift interface from the start, which let other programs (not only the Hive client) talk to it.
Because the metastore was independent of Hive's query engine, other engines adopted it. Facebook's Presto (2013) used it through its Hive connector, Cloudera's Impala (2012) and Spark SQL (2014) read table definitions from it. By the mid-2010s the Hive Metastore was the de facto catalog of the Hadoop ecosystem, in the same way that a single shared schema registry or DNS serves many programs. Amazon's AWS Glue Data Catalog (2017) implemented a compatible API, so that EMR, Athena and Redshift Spectrum could use the same model in the cloud.
In Hive 3.0 (2018) the metastore became a standalone project component that can be released and deployed without the rest of Hive, which acknowledged its role as shared infrastructure. Table formats then used it as their catalog: Iceberg's Hive catalog, and Delta and Hudi through sync tools, keep a pointer to the table's current metadata in the metastore.
The limits became visible as data moved to object storage and tables grew to hundreds of thousands of partitions. Since about 2020, new catalogs have been designed to replace it: AWS Glue, Project Nessie (git-like versions), Apache Polaris and other Iceberg REST catalogs, and Unity Catalog. The Iceberg REST specification is a direct response to HMS's tie to Thrift and a relational database. HMS remains in production in a large number of companies, and the Hive project continues to maintain it.
how: HMS has three layers: a Thrift API, a service that implements it, and the relational database. The API offers calls such as get_table, get_partitions_by_filter, create_table, add_partitions, alter_table and drop_database. A client (an engine's catalog connector) opens a connection to the service and calls these methods. The service translates calls into SQL against the backing database using an object-relational layer (DataNucleus in Hive's implementation), and sometimes direct SQL for speed.
The data model is a set of normalized tables in the backing database. DBS holds databases; TBLS holds tables with owner, type (managed or external) and parameters; SDS holds storage descriptors with location, input format and output format; COLUMNS_V2 holds columns; SERDES holds SerDe classes and parameters; PARTITIONS and PARTITION_KEY_VALS hold each partition's values, and each partition has its own storage descriptor. Table and column statistics are stored in separate tables, and ACID tables use more tables for transactions, locks and compaction. A single partition thus takes rows in several tables (roughly five to ten). A table with 1 million partitions is therefore roughly 5 to 10 million rows in the backing database, a reasonable load for MySQL or PostgreSQL, but a heavy one for each query that asks for many partitions.
Reading a table works like this. The engine calls get_table("logs") and gets the schema, the SerDe and the base location. If the table is partitioned, the engine passes the partition filter to get_partitions_by_filter, for example dt = '2026-07-04'. The service turns the filter into a SQL query on the partition tables (pushed down when the filter is on partition columns of simple types) and returns only the matching partitions, each with its location. This is partition pruning, and it is the one metastore feature that scales the planning of queries on huge tables. The engine then lists the files in each returned location on HDFS or S3 and reads them. The metastore does not know the individual files; it knows directories. Listing remains the job of the file system, which is slow on object stores. Statistics, if present, come from the metastore and help the optimizer.
Writing is metadata only. When a job creates a new partition directory, someone must register it: Hive does this at the end of INSERT; for external tables written by other systems, the user runs MSCK REPAIR TABLE (which scans the directories and adds missing partitions) or ALTER TABLE ADD PARTITION. The metastore does not move or check files. It trusts the registration, so a partition can exist in the metastore with no files, or files can exist with no partition.
There are no atomic multi-file commits in the model. A job writes files into a directory and then registers it; a reader who looks in between can see half the files. Hive ACID tables add transactions for managed ORC tables: the metastore keeps a transaction manager with locks and a table of open transactions, and writers produce base and delta directories with a protocol that readers follow. For other uses, the metastore offers table-level locks, which table formats use as their commit mechanism: Iceberg's Hive catalog takes an HMS lock, writes a new metadata file, then updates the table property metadata_location in the metastore from the old to the new value. That update is the atomic pointer swap (protected by the lock).
Deployment has three common modes. In embedded mode, the metastore runs inside the Hive process with a local Derby database, used for tests only. In local mode, the service is in the client process but the database is remote. In remote mode, which is the production setting, one or more metastore service instances run on their own and clients connect over Thrift; the database is the single source of truth, usually with a primary and a replica. The service is stateless, so scaling it means adding instances, but all of them hit one database.
Security in the metastore is minimal. Hive offers storage-based authorization (permissions follow the file system's permissions) and SQL-standard grants, and Apache Ranger can add policies for Hive. But the metastore does not hand out credentials, so an engine with read access to the files can read them regardless of table-level policy. This is the largest conceptual difference from Unity Catalog and other newer catalogs.

example: A company stores web logs as ORC files under s3://lake/logs/, with a directory per day and hour: dt=2026-07-04/hr=13/. The table is partitioned by dt and hr. The table has existed for 3 years, so it has 3 × 365 × 24 = 26,280 partitions. Each is one row group in the metastore tables, with a few supporting rows.
An analyst runs SELECT count(*) FROM logs WHERE dt = '2026-07-04' AND hr = 13. The engine calls get_partitions_by_filter with the predicate. The metastore executes a SQL query like SELECT ... FROM PARTITIONS JOIN PARTITION_KEY_VALS ... WHERE key = 'dt' AND value = '2026-07-04' ..., which uses an index, returns one partition in a few milliseconds, and the engine lists one directory with, say, 40 files. Planning takes well under a second. Without the filter on partition columns, the engine would receive all 26,280 partitions (several MB of Thrift data) and list 26,280 directories on S3, which at 50–100 ms per list call run in parallel would still take many seconds to minutes.
Now make the table worse. Add a third partition column, country, with 200 values. The partition count becomes 26,280 × 200 = 5.3 million. The backing database now has tens of millions of rows for this one table. A query with a filter on dt and hr only (not on country) asks for 200 partitions, still fine. But a query over a month asks for 30 × 24 × 200 = 144,000 partitions; the service must build and serialize a large response, the engine must hold it in memory and list 144,000 directories, and the metastore's database is under load for everyone else. This is the typical failure: dashboards that previously ran in seconds begin to time out because planning, not execution, is the bottleneck. The usual fixes are to coarsen partitioning (drop hr or country), to move to a table format such as Iceberg that stores file lists in manifests and prunes without the metastore, or to enable partition projection (in Athena/Glue) so that partitions are computed from the filter.
Next, an incorrect state. A producer writes a new directory dt=2026-07-06/ on S3 but does not register it. The table query for that day returns zero rows without any error. Running MSCK REPAIR TABLE logs scans the table location (26,000 directories) and adds the missing partition. On S3 that scan can take minutes, which is why teams register partitions explicitly at write time.
Finally, the Iceberg use. An Iceberg table registered in HMS has one property, metadata_location, pointing to s3://lake/ice/orders/metadata/00042-abc.metadata.json. A commit acquires an HMS lock on the table, writes 00043-def.metadata.json, checks that the property still equals the 00042 path, updates it to 00043, and releases the lock. HMS here is only a pointer store; all the file-level information is in Iceberg's own metadata, which avoids the partition explosion problem completely.
intuition: The phone book of a data lake: it tells you where each table lives and how to read it, but it does not check that anyone is home.
HMS works because the minimum needed to treat files as tables is small: a name, a schema, a decoder and a location. Putting that in a relational database is natural, since the data is small, structured and needs transactions and indexes for lookups by name and by partition value. The weakness is also in the model: a partition is a directory, the unit of metadata is the directory, and the metastore does not know about files or changes inside the directory. When tables grow to millions of partitions or need atomic multi-file updates, the model reaches its edge, which is why the following generation tracks files, not directories.
mistakes: People often think the Hive Metastore requires Hive. In fact it runs as an independent service, and Spark, Trino, Impala, Flink and many others use it without Hive's query engine. Since Hive 3.0 it can be deployed alone.
People often think the metastore stores table data or knows about every file. In fact it stores metadata at the level of tables and partitions (directories). Files are discovered by listing storage at query time. That is a major reason why planning on object stores can be slow and why a table can have stale or missing partitions.
People often think the metastore gives you table-level security. In fact it stores some grants, but it never controls storage access. Any engine or user that can read the files can read the data. Real enforcement needs file-system permissions, Ranger or a catalog with credential vending.
People often think MSCK REPAIR TABLE is a normal way to keep partitions current. In fact it scans the whole table location, which is slow and expensive on object stores; it is a repair tool. Use explicit ALTER TABLE ADD PARTITION, partition projection or a table format instead.
People often think moving to Iceberg or Delta removes the need for any catalog. In fact those formats still need a catalog to find the current table metadata and to make commits atomic. HMS can serve this role, but only as a pointer store, and newer REST catalogs fit it better.
tradeoffs: Choose the Hive Metastore when you must support many existing engines and tools (Hive, Impala, older Spark, Presto) that only know its Thrift API, or when you have thousands of tables and jobs whose names and locations are registered there. It is stable and widely understood. You give up fine-grained access control, scalable partition handling and atomic commits.
Choose a REST catalog (Polaris, Unity Catalog, Lakekeeper, Nessie, or a managed one) for new Iceberg or Delta lakehouses. You gain credential vending, access control, a protocol that does not depend on Thrift or JDBC, and multi-engine access. The cost is migration: table registrations, jobs that use two-part names and tools that expect HMS must be updated.
Choose AWS Glue Data Catalog when you run on AWS and want a managed, HMS-compatible catalog without operating a database. You give up portability (some features are Glue-specific) and accept its limits on API rates and partition counts. Choose a self-hosted HMS when you need full control, run on-premise or multi-cloud, or require specific Hive features; you then own the database, its backup and its tuning.
Choose coarse partitions (day, not hour; no high-cardinality columns) if you stay with HMS, aiming for fewer than roughly 100,000 partitions per table. Choose to leave partitioning to the table format (hidden partitioning with file-level pruning) if you can move to Iceberg. Choose partition projection in Athena or Trino-like engines for very regular partition schemes such as dates, and you avoid storing them at all.
friction: The partition model is the biggest limit. Each partition is a row set in the backing database, and every query that touches many partitions pays to fetch and transfer them. Beyond a few hundred thousand partitions per table, planning times grow into minutes, the database becomes a shared bottleneck, and memory in the service and in clients is stressed. Tuning (direct SQL, batching, indexes, connection pools) postpones the problem but does not remove it.
There are no atomic multi-file operations, no versioning and no isolation. Readers can see half-written directories; a failed job can leave unregistered or empty partitions; two writers can race. Table formats solve this for data files, but HMS itself is only a pointer store and a lock manager, and locks can be left behind by crashed clients.
The service depends on a relational database, with its backups, failover, upgrades and schema migrations. Version upgrades of Hive change the metastore schema and need careful migration. High availability means several service instances but a single database cluster. Cross-region or multi-cloud use is awkward.
Governance is thin. There are no credential vending, no lineage, no tagging and no audit as a first-class feature, so teams add Ranger, Atlas or external catalogs on top. The result is a stack of tools, each with its own metadata. This is the reason why migration paths to modern catalogs exist, typically with a sync step that registers Hive tables in the new catalog while jobs are moved over.
practice: If you operate an HMS, treat the backing database as production infrastructure: use PostgreSQL or MySQL with replication, regular backups and monitored query latency, and index the partition tables as the Hive schema scripts do. Run at least two stateless service instances behind a load balancer, tune the connection pool, and set limits on the number of partitions a single call may fetch, to protect it from runaway queries.
Design partitions with care. Partition by low-cardinality columns that queries filter on (usually a date), avoid more than one or two partition columns, and keep the count per table below about 100,000. Register partitions explicitly when data is written, not with MSCK REPAIR. For external tables on object stores, make sure the data layout and the partition registration happen in a defined order: write files first, then register the partition, so readers never see a partition without data.
Prefer a table format for new data. For existing Hive tables, convert them in place to Iceberg with the migration procedures (snapshot or migrate) and register them in a REST catalog; the Hive tables then stop being limited by partition counts. Keep HMS as a compatibility layer for legacy engines if you must, but make the new catalog the system of record.
When migrating to Unity Catalog, Glue, Polaris or Nessie, inventory tables, partitions and locations first; test on one domain; move the permissions model deliberately, since HMS grants do not map one to one; and run old and new catalogs side by side until jobs have moved. Monitor the metastore's top slow calls (get_partitions is usually first) and fix the queries and the layouts that cause them.
interview: What exactly does the Hive Metastore store, and what does it not store? || Databases, tables, columns, SerDes, storage locations, partitions (values and directories), statistics, and transaction and lock state for ACID tables. It does not store individual files, data, or enforce storage access, so file discovery is done by listing storage and security by other tools.
Why do tables with millions of partitions make queries slow even when little data is read? || Planning must fetch the matching partitions from the backing database, serialize them and list their directories on storage. The cost grows with the number of partitions returned, not with data read. Fix by coarsening partitions, using a table format with file-level metadata, or partition projection.
How does Iceberg use HMS, and what does HMS contribute to atomicity? || HMS stores the table entry with a metadata_location property. A commit takes an HMS lock, writes a new metadata file, and updates the property from the old to the new path if it still equals the old one. This pointer swap is the atomic step; all file-level information lives in Iceberg's own metadata.
What are the security limits of HMS-based governance, and how do modern catalogs address them? || HMS does not control file access, so anyone with storage permissions bypasses table rules. Modern catalogs hold the storage keys and issue short-lived, path-scoped credentials after checking permissions, with central audit and policies.
How would you migrate 5,000 Hive tables to an Iceberg REST catalog with minimal downtime? || Inventory and classify tables, convert in place with Iceberg's snapshot (for testing) and migrate procedures, register them in the new catalog, update engine configs and job names per domain, keep HMS read-only for rollback, validate counts and permissions, and retire HMS after a quiet period.
quiz: What is the main structural difference between a Hive Metastore partition and an Iceberg manifest entry? || A partition is a directory registered in the metastore, and files are found by listing it. An Iceberg manifest lists individual data files with statistics, so no listing is needed and pruning is at file level.
Why is HMS usually backed by MySQL or PostgreSQL rather than something distributed? || The metadata is small and relational, and the service needs transactions, indexes and simple queries by name and partition value. A single well-run relational database handles this for most workloads.
A table is partitioned by dt, hr and country (200 values) over 3 years. How many partitions does it have? || 3 × 365 × 24 × 200 = 5,256,000 partitions, which is far beyond what an HMS handles comfortably for planning.
A job wrote files to a new dt directory but queries return zero rows for that day. What happened and what is the quick and the right fix? || The partition was not registered in the metastore. Quick fix: ALTER TABLE ADD PARTITION or MSCK REPAIR TABLE. Right fix: register partitions at write time, or use a table format that tracks files.
Why can a user with table SELECT revoked in HMS-based Ranger still read the data? || HMS and Ranger policies apply only through engines that honour them. The files in HDFS or S3 are still readable by anyone with storage permissions or an engine that does not check the policy, because HMS does not control storage access.

@@ browser
value: A web browser is a program that fetches documents and programs from servers anywhere on the internet and runs them safely on your machine. It turns HTML, CSS and JavaScript into pixels and interaction: it downloads the bytes, parses them into a tree of objects (the DOM), works out the style and position of every box, paints the result, and runs JavaScript that can change the tree at any time. It does this inside a security sandbox, so that code from a site you have never visited cannot read your files or the data of another site.
Three facts make the browser unusual. It is the only runtime that nearly every connected person already has installed, on every kind of device. It runs code from untrusted parties by default, so isolation is part of its core design. And it is a real-time system on top of a single-threaded programming model: JavaScript, style, layout and paint share one main thread, and the user expects a response within about 100 ms and a smooth frame every 16.7 ms (at 60 frames per second). Most of the performance work in web development is about respecting that budget.
For the layer above (React and other UI frameworks, web apps, ad tech tags and pixels, video players, browser-based tools like notebooks), the browser is the platform. Three lower concepts give it its shape. JavaScript and V8 (L0) provide the engine that parses, compiles and runs scripts, with a just-in-time compiler and a garbage collector; the browser adds the DOM, events and timers around it. Web architecture (L1) provides the network side: URLs, HTTP and its caching, TLS, CDNs and the request-response model that delivers resources. Web security (L3) provides the rules that make running foreign code acceptable: the same-origin policy, Content Security Policy, cookie rules and process sandboxing.
terms: DOM (Document Object Model) — the tree of objects that represents the page in memory; JavaScript reads and changes the page by changing this tree.
CSSOM and computed style — the parsed style rules, and the final values (size, colour, display) that apply to each element after the cascade is resolved.
Layout (reflow) — the step that computes the size and position of every box from the styles, the content and the window size.
Paint and composite — paint records what each layer looks like as drawing commands; compositing combines layers on the GPU into the final frame.
Main thread and event loop — the single thread that runs JavaScript, style, layout and most of paint, taking tasks one at a time from queues.
Critical rendering path — the chain of work from the first bytes of HTML to the first pixels: HTML, CSS, blocking scripts, layout and paint.
Origin — the triple scheme, host and port (for example https://example.com:443); the unit of trust in the same-origin policy.
Site isolation — a design in which pages from different sites run in different operating-system processes, so a compromised page cannot read another site's memory.
history: Tim Berners-Lee wrote the first browser, WorldWideWeb in 1990 at CERN (later renamed Nexus), together with the first web server. The big step was Mosaic (1993), written at the NCSA by Marc Andreessen and Eric Bina, which showed images inline and was easy to install. Andreessen then co-founded Netscape, whose Navigator (1994) dominated for a time. Microsoft answered with Internet Explorer (1995) and bundled it with Windows, leading to the browser wars and to a lawsuit. In 1995 Brendan Eich created JavaScript at Netscape in about ten days; CSS followed in 1996.
After IE reached over 90% share around 2002–2003, innovation slowed. Mozilla's Firefox (2004) revived competition, Apple's Safari (2003) built WebKit from the KDE engine KHTML, and in 2004 browser vendors founded the WHATWG to continue HTML as a living standard because the W3C had moved toward XML. A key step in this period was specifying the HTML parsing algorithm in detail, including error recovery, so that all browsers build the same DOM from the same broken HTML.
Google Chrome, released in September 2008, changed several things at once. It used one operating-system process per tab, so that a crash or a hang stayed local. It shipped V8, a JavaScript engine that compiled JavaScript to machine code, making scripts many times faster and making large web applications possible. It also set a pace of frequent automatic updates. Google forked WebKit to make Blink in 2013, and Microsoft moved Edge to Chromium in 2020. By the 2020s, Chromium-based browsers together hold roughly two thirds of the market, Safari (WebKit) is dominant on Apple devices, and Firefox (Gecko) is the main independent engine along with new efforts such as Ladybird.
Security and privacy have shaped later years. Spectre (2018) showed that a page's code could read memory across a process through CPU timing, so Chrome turned on site isolation by default in 2018. Safari and Firefox now block third-party cookies by default. Chrome planned to remove them, but in 2025 Google decided to keep them without a new consent prompt and began retiring most of its Privacy Sandbox APIs, so cross-site tracking and measurement for advertising still depends on browser differences. Meanwhile Chrome's rendering pipeline was rebuilt (the project called RenderingNG), WebAssembly (2017) and WebGPU added near-native compute, and Core Web Vitals (2020) made user-visible speed a measured quality.
how: Start with navigation. The user types a URL. The browser process (the one with the address bar and UI) parses it, checks its caches, resolves the host name with DNS, opens a TCP connection (or QUIC for HTTP/3), performs a TLS handshake, and sends an HTTP request. Web architecture (L1) matters here: HTTP caching headers (Cache-Control, ETag), connection reuse, HTTP/2 multiplexing and CDNs decide whether this takes 20 ms or 800 ms. When the first response bytes arrive, the browser hands them to a renderer process chosen for that site.
The renderer parses HTML as a stream. A tokenizer turns bytes into tags, and a tree builder turns them into DOM nodes, following the specified error-recovery algorithm. While the parser works, a lightweight preload scanner looks ahead for resources such as images, scripts and stylesheets so downloads start early. CSS is parsed into style rules. A classic script tag without async or defer blocks the parser: the parser must stop, fetch and run the script, because it might call document.write. Stylesheets block rendering, since painting before styles are known would show a flash of wrong content, and scripts that come after a stylesheet wait for it, because the script may ask for computed styles. These blocking rules define the critical rendering path.
Next is style. For each element, the engine finds all matching rules, resolves the cascade (origin, specificity, order), inheritance and relative units, and produces its computed style. Then layout builds a tree of boxes and computes geometry using the CSS formatting models (block, inline, flexbox, grid, tables). A change to a width can ripple through the tree, which is why layout is among the most expensive steps. After layout, paint walks the tree and produces display lists (drawing commands) for each layer. Layers are then rasterized into tiles of pixels, now usually on the GPU, and the compositor thread combines layers with transforms and opacity into a frame. Properties like transform and opacity can be changed on the compositor thread without touching layout or paint, which is why they are the preferred way to animate.
JavaScript runs on the main thread in the engine (V8 in Chromium, JavaScriptCore in Safari, SpiderMonkey in Firefox). The engine parses the code, runs it first in a bytecode interpreter, and compiles hot functions with an optimizing JIT. The browser supplies the host environment: the DOM API, timers, fetch, events, storage. All of this is driven by an event loop. The loop picks a task from a queue (a click, a timer, a network response), runs it to completion, then runs all microtasks (promise callbacks), and finally, if a frame is due, runs animation callbacks (requestAnimationFrame), style, layout and paint. A task that runs for 200 ms blocks everything else on the page for 200 ms, including input and painting. That is why the browser's rule is: never block the main thread. Web Workers run JavaScript on other threads without DOM access, and communicate by messages, and Service Workers sit between the page and the network.
Security is built into every layer. The same-origin policy says a script from one origin cannot read the responses or the DOM of another origin; cross-origin requests may be sent but their results are hidden unless the server opts in through CORS headers. Cookies are attached by rules (domain, path, Secure, HttpOnly, SameSite). Content Security Policy lets a site limit where scripts can come from, which limits the damage of injected code. Renderers run in a sandbox with no direct access to files or the network: they must ask the privileged browser process, which checks. With site isolation, a renderer process only holds documents of one site, with cross-site iframes placed in separate processes, so even a memory-reading bug cannot reach other sites' data. These security measures come from the web security layer (L3) and are enforced by this multi-process architecture.
After the first frame, the page lives by invalidation. When a script changes a node, adds a class or resizes the window, the engine does not redo everything. It marks the affected nodes as dirty (needing style recalculation, layout or paint) and does the work only at the next rendering opportunity, usually once per frame. Several changes in the same task are therefore merged into one update. This lazy scheme is what makes repeated DOM writes cheap, and what makes a read of layout-dependent values (offsetWidth, getBoundingClientRect) expensive when something is dirty: the engine must stop and compute the layout at once to give a correct answer. Frameworks such as React rely on this behaviour: they collect many changes, then write them to the DOM in one batch, and the browser turns them into one layout and one paint.
The process model in Chromium looks like this: one browser process, one GPU process, a network service, and many renderer processes, each in a sandbox. Costs are memory (each renderer carries its own copy of the engine, perhaps 50–200 MB) and inter-process messaging, which is the price of isolation and stability.

example: Follow a simple page load with round-trip time (RTT) of 50 ms to the server. The HTML is 50 KB, one stylesheet is 30 KB, one script is 200 KB and is loaded with defer.
Time 0: the user presses Enter. DNS lookup takes about 20 ms if not cached. TCP handshake needs one RTT, 50 ms. TLS 1.3 needs one more RTT, 50 ms. The request goes out and the first byte of HTML comes back one RTT later, 50 ms, plus the server's time of, say, 30 ms. So first byte arrives at roughly 200 ms. The 50 KB HTML arrives within the next 20–30 ms. The preload scanner sees the stylesheet and the deferred script in the first chunk and starts both downloads at once, each taking about one RTT plus transfer: another 70–100 ms. At about 300 ms the CSS is ready; the DOM is complete; style and layout of a small page take around 5–10 ms; the first paint is at roughly 310 ms. The deferred script runs after parsing and takes, say, 40 ms to compile and run, in the main thread; if the user clicks at 320 ms, the response waits until the script is done. That wait is the kind of delay measured by Interaction to Next Paint (INP), where a value under 200 ms counts as good.
Now see what changes if the script is a normal blocking script placed before the content: the parser stops at the script tag and waits for it to download (100 ms) and run (40 ms). First paint moves from about 310 ms to about 450 ms. Putting the script at the end, or adding defer, restores the earlier paint. This is the practical meaning of the critical rendering path.
A second example is a long task. A click handler sorts 100,000 rows in JavaScript and takes 180 ms. At 60 Hz, the frame budget is 16.7 ms, so about 10 frames are missed; the page appears frozen. The user presses a button during this time and the press is only handled after the loop finishes, giving an interaction delay near 180 ms plus rendering. Splitting the work into 10 chunks of 18 ms with scheduling in between, or moving the sort to a Web Worker, keeps the page responsive. The total work is the same, but the page can paint between chunks.
A third example is layout thrashing. A loop sets element.style.width and then reads element.offsetWidth for each of 1,000 elements. Every read forces the browser to run layout immediately so that it can return a correct value; with 1,000 reads between 1,000 writes, layout runs 1,000 times. If one layout of this page costs 0.5 ms, the loop takes 500 ms. Reading all widths first, then writing all of them, triggers layout once, about 0.5 ms. The 1,000-fold gap comes from the rule that the browser delays layout until needed, and reads that need fresh layout cancel the delay.
intuition: A document viewer that grew into an operating system for applications, with a security guard at every door.
Browsers work because a few fixed ideas fit together. A document is a tree, so everything (parsing, styling, scripting, accessibility) is an operation on a tree. Scripts change the tree and the browser re-renders only what changed. A single main thread removes the need for locks in page scripts, at the price of a strict rule about not blocking. And since code arrives from strangers, trust is based on origin and enforced by process boundaries, not on promises. Most advice on web performance and security is a consequence of these ideas.
mistakes: People often think JavaScript runs in parallel on many threads. In fact page JavaScript runs on one main thread; concurrency comes from the event loop (tasks interleaved) and from workers with separate memory and message passing. A long task blocks painting and input.
People often think the browser draws the page after it has downloaded everything. In fact it renders progressively: it parses HTML as it arrives and can paint before the page has finished loading. But CSS and synchronous scripts block this progress, which is why their placement matters.
People often think the same-origin policy stops cross-site requests from being sent. In fact it stops a page from reading the response (and some other interactions). A cross-site form post or image request is still sent, with cookies depending on SameSite rules. This is why CSRF protection is needed, and why the policy is not a firewall.
People often think the DOM is slow so you must avoid touching it. In fact reading and writing individual nodes is fast. What is slow is forcing layout and paint repeatedly, or changing very large trees. Batching reads and writes and using compositor-friendly properties solves most cases.
People often think all browsers are the same engine. In fact the three major engines (Blink, WebKit, Gecko) differ in features, bugs, release speed and privacy defaults. Safari on iOS must use WebKit (with regional exceptions), which affects what web apps can do there.
tradeoffs: Choose a server-rendered or static HTML page when content matters most and interaction is light: it delivers the first paint after one round trip and works without JavaScript. Choose a client-rendered application when interaction is rich and state lives on the client; you pay in download size, JavaScript execution time on low-end phones (a 1 MB script can take 1–3 seconds to parse and run on a mid-range phone) and slower first paint. Many sites mix the two with server rendering plus hydration.
Choose a single-process page with workers for compute-heavy tasks when you need a responsive UI and work above 50 ms: workers use extra cores but cannot touch the DOM, and data crosses by copy or transfer. Choose WebAssembly when you have numeric or legacy code that needs predictable speed; choose JavaScript when the code is mostly DOM and I/O, where Wasm gives no gain.
Choose strong isolation features (site isolation, COOP/COEP headers, CSP, SameSite=Lax or Strict cookies, Secure and HttpOnly) for sites with authenticated data. The costs are more work in integration: third-party widgets, embeds and cross-origin resources need explicit permissions. Choose looser settings only for public content with no sensitive state.
Choose to depend on third-party scripts (analytics, ads, tag managers) knowing each runs with full page privileges, adds network requests and main-thread time, and may be blocked by users and browsers. For ad tech, choose first-party measurement and server-side events where possible, as third-party cookie availability differs between browsers and can change.
friction: The main thread is the bottleneck. Heavy JavaScript, large DOMs (over about 1,500 nodes is a common warning), expensive styles and forced layouts compete for the same thread, and low-end devices make everything slower by several times. The metrics are Largest Contentful Paint (good: under 2.5 s), Interaction to Next Paint (under 200 ms) and Cumulative Layout Shift (under 0.1), and many sites fail them on real phones.
Compatibility and fragmentation cost time. Features arrive at different speeds in Chromium, WebKit and Gecko, so developers rely on feature detection, polyfills and testing across browsers. Safari on iOS has its own limits. Standards processes are slow and political, and a feature shipped by one vendor first (a "Chrome-only" API) may never be adopted by others.
Security is a moving target. Cross-site tracking, cookie rules, storage partitioning, fingerprinting defences and consent rules change how analytics, attribution and advertising work, and the details differ between browsers and change between versions. Spectre-class attacks forced costly changes (process isolation, restrictions on shared memory and timers). Extensions and third-party scripts remain a source of risk.
The platform is also large. A modern browser engine has tens of millions of lines of code, and the specification is huge; building a new engine is a decade-long project, which concentrates power in few vendors. Memory use is high because of process isolation, and long-lived tabs with leaks grow until they are discarded.
practice: Measure on real conditions: use Lighthouse for lab tests, the Performance panel in DevTools for traces, and field data (Chrome User Experience Report, or your own RUM with the web-vitals library) because lab results differ from low-end phones on slow networks. Test with CPU throttling of 4× and a slow 4G profile, which approximate a mid-range phone.
Keep the critical path short. Inline or preload only critical CSS, serve the rest asynchronously; use defer or type="module" for scripts; compress with Brotli; use HTTP/2 or HTTP/3 and a CDN; set long Cache-Control for fingerprinted assets; use preconnect for important third-party origins. Size images, use modern formats, and set width and height to prevent layout shifts. Lazy-load below-the-fold images and iframes.
Protect the main thread. Break up tasks longer than 50 ms (the threshold for a long task) with scheduler.yield() or setTimeout; move heavy computation to workers; debounce input handlers; avoid forced layout by batching reads before writes; animate transform and opacity only; use content-visibility and virtualization for long lists. Watch third-party tags: audit them regularly and load them after the main content or through a worker-based tag approach.
Set security headers by default: Content-Security-Policy (start in report-only mode), Strict-Transport-Security, X-Content-Type-Options, a Referrer-Policy, Cross-Origin-Opener-Policy where useful, and cookies with Secure, HttpOnly and SameSite. Treat any user-supplied string as text and not as HTML. For advertising and measurement, design for browsers with no third-party cookies, with first-party identifiers, server-side collection and consent, and test in Safari and Firefox, not only in Chrome.
interview: Walk through what happens between pressing Enter on a URL and seeing the first pixels. Where can it be slow? || DNS, TCP and TLS handshakes (each about one RTT), HTTP request and first byte, HTML parsing with preload scanner, CSS fetch and parse (render-blocking), blocking scripts, style, layout, paint and composite. Slowness comes from network round trips, big blocking CSS or JavaScript, and long main-thread tasks. Caching, CDN, HTTP/3, and preload shorten the path.
Why does a long JavaScript task freeze the page, and how do you fix it? || JavaScript, style, layout and most painting share the main thread, and the event loop runs one task to completion. While it runs, no input is handled and no frame is painted. Fix by splitting work into chunks that yield, moving computation to a Web Worker, or reducing the work (virtualized lists, memoization).
Explain the same-origin policy and what CORS changes. || A script can only read data from its own origin (scheme, host, port); cross-origin responses are blocked from being read, though requests may be sent. CORS lets a server opt in by sending headers that say which origins may read the response, with a preflight for non-simple requests. It is a relaxation controlled by the server, not by the page.
What is site isolation and why was it introduced? || Each site runs in its own sandboxed renderer process, with cross-site iframes in separate processes. It was introduced by default in 2018 after Spectre showed that a page could read other memory in the same process through speculative execution timing, so process boundaries became the only reliable barrier.
A page has good server response time but a poor INP on phones. How do you investigate? || Record a Performance trace with CPU throttling, look for long tasks around interactions, identify the handlers, framework re-renders or third-party scripts responsible, and check input delay, processing time and presentation delay. Fix by yielding, reducing work in handlers, deferring non-critical scripts, and using workers.
quiz: Why does a script without defer or async delay the first paint? || The parser must stop, download and run the script before it continues, since the script may change the document. Everything after it waits.
Which browser properties can be animated without layout or paint, and why? || Transform and opacity. They are applied by the compositor thread on already-rasterized layers, so the main thread is not involved.
A click handler takes 180 ms at 60 frames per second. About how many frames are missed? || 180 / 16.7 ≈ 10 or 11 frames, during which the page cannot update or respond to input.
A loop writes style.width and then reads offsetWidth for 1,000 elements, and one layout costs 0.5 ms. How long does it take and how do you fix it? || Each read forces a layout, so 1,000 × 0.5 ms = 500 ms. Read all values first and then write all, so layout runs once for about 0.5 ms.
When would you prefer a server-rendered page to a client-rendered application? || When content and first-paint speed matter more than rich client interaction, when users have slow devices, or when search and sharing matter. You avoid large JavaScript costs and get content after one round trip.

@@ react
value: React is a JavaScript library for building user interfaces from components. Instead of telling the browser step by step what to change ("find this node, set its text, add that class"), you write a function that describes what the screen should look like for the current data. When the data changes, React calls the function again, compares the new description with the previous one, and applies only the differences to the page. The rule of thumb is UI = f(state).
The problem it addressed was the growth of state in web applications. Around 2010–2012, large pages with many pieces of changing data (Facebook's notifications, chat and news feed) were built with manual DOM updates or two-way data binding. Every event handler had to know which parts of the page to change, and the number of possible interactions between parts grew faster than the code. Bugs appeared as stale or inconsistent screens. React removed the update logic: you write only the rendering from state, and the library works out the changes. This makes a screen a pure function of data, which is easy to reason about, test and reuse as components.
For the layer above (Next.js and other frameworks, React Native apps, design systems, dashboards and ad-tech consoles), React is the most widely used UI library on the web. Three lower concepts shape it. The browser (L0) provides the DOM, the event system, and the layout and paint pipeline that React must drive efficiently; React's batching of DOM writes exists because forced layout and repeated paints are the costs the browser imposes. JavaScript and V8 (L0) run component functions and allocate the element objects that describe the UI, so allocation rate and garbage collection matter. Web architecture (L1) provides the client-server model: bundles delivered over HTTP, server-rendered HTML, hydration, streaming, and the newer server components.
terms: Component — a function that takes props (inputs) and returns elements describing a piece of UI; components can contain other components.
Element — a small plain object that describes what to render ({type: 'div', props: {...}}); creating one does not touch the DOM.
JSX — a syntax extension that lets you write elements as tags in JavaScript; a compiler turns it into function calls that create element objects.
State and props — state is data a component remembers between renders (set with useState); props are values passed in from the parent. Changing state schedules a re-render.
Reconciliation — the algorithm that compares the new element tree with the previous one and decides which DOM nodes to create, update or remove.
Fiber — React's internal data structure for a unit of work, one per component instance, which holds state, links to the parent, child and sibling, and the priority of pending updates.
Hook — a function such as useState, useEffect or useMemo that lets a component keep state or run side effects; hooks are called in the same order on every render.
Hydration — attaching React's event handling and state to HTML that was already rendered on the server.
history: React was created by Jordan Walke, an engineer at Facebook, who was influenced by XHP, a PHP extension that let Facebook write HTML as typed components on the server. An early prototype called FaxJS appeared around 2011. React was used in Facebook's News Feed in 2011 and in Instagram after Facebook bought it in 2012. It was open-sourced in May 2013 at JSConf US. The first reaction was doubtful: mixing markup into JavaScript (JSX) looked like a step backward to many developers. Over the next two years the idea of "describe the UI, don't mutate it" proved itself, and the criticism faded.
React Native (2015) applied the same model to iOS and Android: components render native views instead of DOM nodes. In 2015 Redux and then many state libraries appeared around React. React 16 (2017) replaced the core algorithm with Fiber, a rewrite that made rendering interruptible, and introduced error boundaries. Hooks, released in React 16.8 in February 2019, let function components hold state and effects, replacing most class components.
React 18 (March 2022) shipped concurrent rendering: the library could prepare a new screen in the background, interrupt it for urgent input, and keep the old screen visible. It added automatic batching, transitions, and streaming server rendering with Suspense. React 19 (December 2024) brought Actions for form handling and async state, new hooks (use, useActionState, useOptimistic) and stable support for Server Components inside frameworks. React 19.1 (March 2025) and 19.2 (October 2025, adding Activity and useEffectEvent) followed, and React Compiler 1.0 (October 2025) stabilised automatic memoization, which removes most hand-written useMemo and useCallback. React 19.3 was released in September 2026.
Governance changed too. In October 2025 Meta announced that React would move to a new React Foundation under the Linux Foundation, which launched in February 2026, with members from several large companies. Security also became visible: in December 2025 a critical remote code execution flaw in the React Server Components protocol was found and fixed in patched releases of 19.0, 19.1 and 19.2, a reminder that moving rendering to the server moves attack surface to the server.
how: A React program is a tree of components. A component is a function. For example, function Counter({start}) { const [n, setN] = useState(start); return <button onClick={() => setN(n + 1)}>{n}</button>; }. The JSX is compiled to a call such as jsx('button', {onClick: ..., children: n}), which returns an element: a plain JavaScript object with a type, props and key. An element is only a description. This is where JavaScript (V8) supplies the machinery: creating objects is cheap, and the runtime's garbage collector reclaims the old elements after each render.
Rendering is a phase that computes the next element tree. React starts at the root, calls each component function with its props, and collects the elements returned. If an element's type is another component, React calls it too, recursively. This phase must be pure: it may not change the DOM or outside variables. Purity is what allows React to run it twice, pause it, throw it away, or run it in the background.
Reconciliation compares the new tree with the previous one. Comparing two arbitrary trees optimally costs \( O(n^3) \), which is too slow, so React uses two heuristics that make it \( O(n) \). First, elements of different types produce different trees: if a div becomes a span, or component A becomes component B, the old subtree is destroyed and the new one is built. Second, in a list of children, a key identifies each child across renders, so that a reordered or inserted item is matched with its previous version and keeps its state and DOM node. Without keys, React compares by position, which can mix up state when an item is inserted at the front. Where the type and position (or key) match, React keeps the instance and compares props, then recurses to the children.
Fiber is the data structure that carries out this work. Each component instance has a fiber node with fields for its type, its props and state, pointers to the parent (return), first child and next sibling, and a bit mask of pending work (lanes). React keeps two trees, the current one (what is on screen) and a work-in-progress tree it is building, and swaps them when the work is done. The render phase is a loop that processes one fiber at a time and can check, after each unit, whether a more urgent update has arrived or whether it has used its time slice of about 5 ms; if so it yields to the browser so that input and painting can proceed. This turns rendering into cooperative work on the browser's single main thread: React does not make the browser faster, but it cuts its work into pieces that fit between frames.
State is stored in the fiber, not in the function. useState returns the current value for this component instance and a setter. Hooks are kept in a linked list on the fiber, in call order, which is why hooks must be called in the same order on each render (no hooks inside conditions or loops). Calling the setter does not change the variable at once: it enqueues an update on the fiber with a priority lane, and schedules a render. Since React 18 several updates in the same event are batched into one render. Updates marked as transitions (startTransition) get a low-priority lane, so a typing event renders first and an expensive list filter later, and can be abandoned if new input arrives.
The commit phase applies the result. When the render phase has finished for a lane, React walks the list of fibers that changed and performs all DOM mutations in one synchronous pass (create nodes, set attributes, insert, remove), which the browser then lays out and paints once. After mutation it runs layout effects (useLayoutEffect), which can measure the DOM before paint, and later passive effects (useEffect), which run after paint for subscriptions, fetches and logging. Event handlers are attached through a single listener at the root and dispatched by React. The commit phase cannot be interrupted, because a half-updated DOM would be visible; this is the reason why all the work that can be paused is placed in the render phase.
By default, when a component re-renders, all its children re-render too, because React cannot know whether they depend on anything that changed. A component can skip this if its props are identical (React.memo), if its output is memoized (useMemo), or, with the React Compiler, automatically, since the compiler analyses the code and adds the memoization. Re-rendering is not the same as updating the DOM: a re-render calls functions and compares elements, and only real differences cause DOM writes.
On the server, React can render the same components to an HTML string or stream (renderToPipeableStream), so that the browser shows content before any JavaScript has loaded. In the browser, hydrateRoot attaches handlers to the existing HTML and reuses it if it matches what the client would render. Server Components extend this idea: components that run only on the server, can read databases directly, and send their output to the client as a serialized description (the RSC payload); only components marked "use client" ship JavaScript to the browser. This depends on the web architecture layer, as frameworks decide the routing, caching and streaming of these payloads.

example: A list shows 3 items [A, B, C], each rendered as <li key={id}> with a text input inside. The user types "x" into the input of B, so B's input state is "x". Then the app removes A from the data. Without keys, React compares by position: new list [B, C] against old [A, B, C]. Position 0 now holds B's data but the old instance of A with its state, position 1 gets C's data with B's instance (which has the typed "x"), and position 2 is removed. The input with "x" now appears in C's row, a classic bug. With key={id}, React matches by key: B keeps its instance and state, C keeps its instance, and only A's node is removed from the DOM. One DOM removal, no wrong state.
Now the cost of rendering. A page has a parent with 1,000 child components, each costing about 5 microseconds to run its function and diff its few elements. When the parent's state changes (for example, a text field it owns), React re-renders all 1,000 children: roughly 1,000 × 5 µs = 5 ms of JavaScript, well under a 16.7 ms frame. The diff finds that nothing in the children changed, so there are zero DOM writes. At 10,000 children it would be 50 ms, which blocks the frame and makes typing feel slow. The remedies are, in order: keep the state close to where it is used so fewer components depend on it, memoize the children (React.memo or the compiler), and virtualize the list so only the 30 visible rows exist.
A concurrency example. The user types in a search box that filters 20,000 products. Filtering and rendering the list takes 120 ms. If each keystroke updates the input and the list in one urgent render, typing lags by 120 ms per key. If the list update is marked as a transition (startTransition(() => setQuery(q))), React renders the input immediately (a few ms), starts the list render in the background in small slices, and discards it if the next key arrives before it is finished. The input stays responsive. The total work is the same, or less, because abandoned renders never commit, but the order and interruptibility change the user experience.
A server example: a product page with a 300 KB JavaScript bundle. Client-only rendering shows a blank page until the bundle downloads (about 1 second on a mid-range phone on 4G), parses and runs (0.5 s), and then fetches data (another round trip of 200 ms). Server rendering sends the HTML in the first response, so content is visible at about 300 ms; the page becomes interactive after hydration, at about 1.5 s. Server Components can reduce the bundle: a 100 KB Markdown library used only to render product descriptions stays on the server and never reaches the client.
intuition: A painter who, each time the scene changes, repaints a fresh sketch of the whole picture, compares it with the last sketch, and touches up only the places that differ.
The design is natural because comparing is cheaper than tracking. To keep the screen right, you can either record every possible change and its effect (error-prone, as the number of combinations grows) or recompute the whole description and compare it (simple, always correct). Recomputing is affordable because the description is small compared with the real DOM, and the comparison is linear with a few sensible assumptions. The expensive thing, touching the browser's layout and paint, happens only for the differences. React's later work (Fiber, concurrency, the compiler) all aims to keep this simple model while making it fit into the browser's 16.7 ms frame.
mistakes: People often think the virtual DOM makes React faster than the real DOM. In fact it is extra work on top of the DOM. Hand-written targeted DOM updates are faster than any diff. What the virtual DOM gives is simplicity and correctness at acceptable cost. Libraries such as Svelte and Solid avoid it by compiling updates or tracking fine-grained dependencies.
People often think a re-render means the DOM is updated. In fact a re-render is React calling your function and comparing elements; the DOM is touched only where the result differs. Re-rendering is cheap unless components are heavy or the tree is huge.
People often think setState changes the variable immediately. In fact it schedules an update. Inside the same event handler, the state variable still has the old value (the closure captured it), and several calls are batched. To compute from the previous value, use the updater form, setN(n => n + 1).
People often think useEffect is the same as a lifecycle method such as componentDidMount. In fact an effect is a synchronisation between React state and something outside React, and it re-runs whenever its dependencies change. Using effects to derive state from other state causes extra renders and bugs; compute during render instead.
People often think React includes routing, data fetching and a build system. In fact React is a rendering library. Frameworks such as Next.js, React Router (Remix) and Expo add routing, data loading, server rendering and bundling, and decide how Server Components are used.
tradeoffs: Choose React when you need a large ecosystem, many hiring candidates, shared code with React Native, and a component model for complex, stateful interfaces. Choose a lighter or compile-time framework (Svelte, Solid, Preact) when bundle size and update speed on low-end devices matter more than ecosystem; you give up libraries and talent pool. Choose plain server-rendered HTML with small scripts for content sites and simple forms, where React's runtime (about 40–50 KB gzip for react-dom) buys little.
Choose a framework (Next.js, React Router, Expo) over a hand-built React app for anything with routing, server rendering and data loading, since the framework solves these in an integrated way. The price is framework lock-in and fast-changing conventions. Choose a client-only single-page app for internal tools behind a login, where SEO and first paint matter less and simplicity is a gain.
Choose Server Components when much of the page is read-only data and heavy libraries, and you can run a server runtime; they cut client JavaScript and allow direct data access. You pay in a more complex mental model (which code runs where), constraints on what can be passed across the boundary, and a larger security surface on the server. Choose client components for everything that needs state, effects or browser APIs.
Choose local component state first, then context or a small store (Zustand, Redux Toolkit, Jotai) only when many distant components need the same data, and use a data-fetching library (TanStack Query, SWR, or the framework's loader) for server state. Putting everything into one global store makes every change a potential wide re-render.
friction: Unnecessary re-renders are the standard performance problem. A change high in the tree re-renders everything below by default, and a context value that changes on every render re-renders all consumers. Profiling with React DevTools is needed to find the hot components, and manual memoization is error-prone. The compiler helps, but only for code that follows the rules of React (pure render, no mutation of props or state).
The model has sharp rules that surprise beginners: hooks order, stale closures in effects, dependency arrays, strict-mode double rendering in development to expose impurity, and the need to treat state as immutable. Effects are easy to misuse. Concurrent features add subtle cases: renders can run more than once and be discarded, so side effects in render are bugs.
The ecosystem changes fast. State management, data fetching, styling, routing and now server components have each gone through several waves, and a project's choices age quickly. Upgrades across majors (class components to hooks, 17 to 18, 18 to 19) cost time. Server-side features increase the security surface: the December 2025 vulnerability in the Server Components protocol showed that a flaw in the framework layer can be remote code execution on the server.
Performance on the client is bounded by JavaScript. Large bundles, hydration of big pages (the browser repeats the rendering work to attach handlers) and many components on low-end phones lead to slow interaction. Partial and selective hydration, islands and Server Components all try to reduce this cost, at the price of more architectural complexity.
practice: Design state first. Keep state as local as possible, derive values during render instead of storing them, lift state up only when two siblings need it, and keep server data in a data-fetching library, not in a global store. Give list items stable keys from your data (database IDs), never array indexes for lists that change order. Treat props and state as immutable: create new objects and arrays instead of changing them.
Measure before optimizing. Use the React DevTools Profiler to see which components render and why, and the browser's Performance panel for long tasks. Fix the biggest wins first: move state down, split a large component so that a frequently changing piece does not re-render the rest, virtualize long lists (TanStack Virtual, react-window), and lazy-load routes and heavy components (React.lazy with Suspense). Enable the React Compiler on new code, and remove manual memoization only after testing.
Use effects sparingly: for subscriptions, timers and syncing with non-React systems, always with a cleanup function and an honest dependency array (the ESLint rule react-hooks/exhaustive-deps helps). For data fetching, use the framework or a library, not hand-written effects, to get caching, deduplication and cancellation. Use transitions (startTransition, useDeferredValue) for expensive updates triggered by typing.
Run React in StrictMode in development, use TypeScript for props, and test components by behaviour with React Testing Library. For server rendering, set up streaming and Suspense boundaries so that slow parts do not block the fast ones; keep secrets on the server, validate everything that crosses the client-server boundary, and keep the framework and React versions patched, because server components extend the attack surface.
interview: Explain reconciliation and why keys matter. || React compares the new element tree with the previous one using two heuristics: elements of different types produce different subtrees, and keys identify items in a list across renders. Matching types and keys keep the instance and state and update props; mismatches unmount and mount. Without stable keys, state is attached to positions and can move to the wrong item when the list changes.
What does Fiber make possible that the old stack reconciler could not? || The old algorithm recursed through the whole tree in one uninterruptible call. Fiber represents work as a linked structure processed one unit at a time, so React can pause, resume, prioritise and discard rendering work. That enables time slicing, transitions, Suspense and concurrent rendering, while the commit to the DOM stays synchronous.
A parent state change makes a page with 5,000 components lag. How do you diagnose and fix it? || Profile with the React DevTools Profiler to see which components render and why, and use the browser trace for long tasks. Move the state down or split components so fewer render, memoize stable children (or enable the compiler), virtualize large lists, and check for unstable props or context values that defeat memoization.
Why must hooks be called in the same order on every render, and how are they stored? || Hook state lives in a linked list on the component's fiber, indexed by call order, not by name. If the order changes between renders, a call would read another hook's state. So hooks cannot be inside conditions or loops.
When would you choose Server Components, and what are the risks? || When pages are mostly read-only data with heavy dependencies and you want less client JavaScript and direct data access. The risks are a more complex model of what runs where, restrictions on props crossing the boundary, caching confusion, and a larger server-side attack surface, as shown by the 2025 protocol vulnerability.
quiz: What does a React component return, and does creating it touch the DOM? || It returns elements, plain objects that describe the UI. Creating them does not touch the DOM; only the commit phase does.
Why is the render phase interruptible but the commit phase not? || Render only computes a new tree in memory, so it can be paused or discarded safely. Commit changes the real DOM, and a half-applied change would be visible to the user.
A list [A, B, C] loses A. With keys, how many DOM nodes are removed and does B keep its state? || One node (A's) is removed; B and C keep their instances and state because they are matched by key.
A parent re-renders 1,000 children at 5 microseconds each. How long does it take, and is it a problem? || About 5 ms of JavaScript, which fits within a 16.7 ms frame. It becomes a problem at around 3,000 or more such components, or when each child is heavier.
Why is calling setN(n + 1) twice in one handler not the same as adding 2, and how do you get 2? || Both calls use the same captured value of n, so the result is n + 1. Use the updater form setN(x => x + 1) twice, which uses the latest queued value, to get n + 2.

value: Git is a version control system: a tool that records the history of a set of files as a chain of snapshots, so that you can see what changed, go back to any earlier state, work on several lines of development at once, and merge them again. Linus Torvalds wrote it in April 2005 for the Linux kernel. Today almost every software project uses it, and every copy of a repository (a clone) holds the full history, so there is no single server that everything depends on.
Underneath, Git is much simpler than its command line suggests. It is a content-addressed object store: a key-value database where the key of each object is the hash of its content. Four kinds of objects are enough: blobs (file contents), trees (directories), commits (snapshots with a message and parent links) and tags. Because the key comes from the content, two identical files are stored once, an object can never change without changing its name, and a single commit hash identifies the entire history behind it. Branches are only small files that contain a commit hash.
For the layer above (GitHub and GitLab, code review, release pipelines, GitOps, infrastructure as code, and the daily workflow of every engineer), Git is the source of truth for code and configuration. Three lower concepts shape it. Version control (L1) provides the model: history as a graph of snapshots, with branching and merging as first-class operations. C (L0) is the language Git is written in, chosen for speed and direct control of files and memory; the plan to add Rust is under way. CI/CD (L1) sits on top: every push or merge can trigger builds and tests, and a commit hash is the identity of what was built and deployed.
terms: Blob — an object that stores the bytes of one file, with no name; its ID is the hash of a short header plus the content.
Tree — an object that lists the entries of one directory: for each entry a mode, a name and the ID of a blob or a sub-tree.
Commit — an object that points to one tree (the snapshot), zero or more parent commits, the author and committer, a time and a message.
Ref — a name, such as refs/heads/main or a tag, that holds a commit ID; HEAD says which ref (or commit) is checked out.
Index (staging area) — a file that lists the paths and blob IDs that will go into the next commit; git add updates it.
DAG (directed acyclic graph) — the shape of the history: commits point to their parents, never in a cycle, and merges have two parents.
Packfile — a compact file that stores many objects together, using delta compression between similar objects, plus an index for lookup.
Merge base — the nearest common ancestor of two commits, the starting point of a three-way merge.
history: Until 2005 the Linux kernel used BitKeeper, a proprietary distributed version control system, with a free licence for the kernel community. In April 2005 the arrangement ended after a dispute, since Andrew Tridgell had reverse-engineered the BitKeeper protocol. Torvalds had no free tool that met his needs, so he started Git on 3 April 2005. His goals were speed, a simple design, strong support for thousands of parallel branches, a fully distributed model and the ability to handle a project as large as the kernel. Within days Git could manage its own source, and within about two weeks the kernel itself was managed with it. Junio Hamano took over as maintainer in July 2005 and still leads the project.
A similar tool, Mercurial, appeared in the same month. The two competed for some years, but Git won, helped by its speed, by its strong branching, and by GitHub (founded 2008), which added pull requests and a social layer around it. Subversion, the centralized system that most projects used before, declined sharply.
The design has been extended without being replaced. Packfiles (2005–2006) made storage compact. Shallow and partial clones, sparse checkout, the commit-graph file and multi-pack indexes (2018–2019) made huge repositories practical. Microsoft's work on a Windows repository of about 300 GB led to the VFS for Git and then to these features inside Git itself, with the Scalar tool. Protocol v2 (2018) reduced the cost of fetch. SSH signing of commits (2021) made signatures easier. The default merge strategy changed to ort in 2.34 (2021), which is faster and handles renames better.
The hash is the most visible long-term change. In 2017 researchers at Google and CWI found the first practical SHA-1 collision (SHAttered). Git added collision detection, and in 2020 (Git 2.29) added experimental repositories that use SHA-256 for object IDs. Git's own planning document for version 3.0 lists the changes the project intends to make: SHA-256 as the default for new repositories, the reftable format for storing refs, main as the default branch name, and Rust as a required part of the build, with steps that start in the 2.5x releases. No release date for 3.0 has been set.
how: Everything starts with the object database in the .git directory. To store a file, Git forms a header "blob <size>" followed by a zero byte and then the content, takes the SHA-1 hash of that, and uses it as the name. The object is compressed with zlib and written to .git/objects/ab/cdef..., where the first two hex digits form the directory. For the text hello followed by a newline, the object is "blob 6\0hello\n" and its ID is ce013625030ba8dba906f756967f9e9ca394464a. Every machine in the world computes the same ID for the same bytes. This is what "content-addressed" means, and it gives deduplication and integrity for free: if a bit changes on disk, the hash no longer matches.
A tree object stores a directory as a sorted list of entries, each with a file mode (100644 for a normal file, 100755 for executable, 040000 for a directory, 120000 for a symlink), a name and the hash of the child object. The name is stored in the tree, not in the blob, so a renamed file keeps its blob and only the tree changes. A tree is itself hashed, so its ID depends on all the names and IDs below it. This makes the repository a Merkle tree: if two root trees have the same ID, the two snapshots are identical down to the last byte. Comparing two snapshots is fast, because any subtree with the same ID can be skipped without looking inside.
A commit object records the ID of the root tree, the IDs of its parents, the author and committer with timestamps, and the message. Its own ID is the hash of all of this, including the parent IDs. So a commit ID identifies not only the snapshot but the entire history leading to it: changing an old commit changes its ID, and therefore the ID of every later commit. This is why history is tamper-evident, and why "rewriting history" (rebase, amend) creates new commits with new IDs instead of editing the old ones. A commit is a snapshot, not a diff; diffs are computed on request by comparing two trees. The set of commits forms a directed acyclic graph.
Names for commits are refs: files in .git/refs/heads (branches), refs/tags and refs/remotes, each holding one commit ID. HEAD is normally a symbolic ref that says "ref: refs/heads/main". Creating a branch writes one 41-byte file, which is why branching is nearly free. Making a commit builds trees from the index, writes the commit object and moves the current branch ref to the new commit. The index file is the staging area: a sorted list of paths with blob IDs, modes and file-system metadata (size and modification time), which Git also uses to detect quickly which working files changed, without hashing all of them.
Storage grows by two mechanisms. New objects are first written as loose files. Then git gc (or the server on push) packs them: a packfile stores objects one after another, and for objects that are similar, such as successive versions of a file, it stores one in full and the others as deltas (copy and insert instructions) against it. Git chooses delta bases by sorting objects by type, name and size and looking for good matches inside a window, not just by history. An index file next to the pack holds a fan-out table and sorted IDs, so a lookup of an ID is a binary search. Typical packs are 5 to 10 times smaller than the loose objects, and this is how repositories with decades of history fit on a laptop.
Merging uses the graph. To merge branch B into A, Git finds the merge base (the nearest common ancestor), and does a three-way merge of three trees: base, A and B. For each path, if only one side changed it, take that change; if both changed it identically, take it once; if both changed it differently, run a line-based three-way merge, and report a conflict where the changes overlap. Renames are not recorded; they are detected during merge by comparing content similarity of added and removed files. If A is an ancestor of B, the merge is a fast-forward: the ref just moves. Rebase replays commits one by one onto another base, creating new commits.
Distribution is a graph exchange. When you fetch, the client and server compare their refs, then negotiate by exchanging commit IDs they have ("have") and want ("want") until the server knows the smallest set of objects the client lacks. It builds a pack of just those objects, often with deltas against what the client has, and sends it. Push is the reverse. Because objects are immutable and named by hash, this works safely over any transport (HTTPS, SSH), and a remote is just another repository. CI/CD systems rely on this: a webhook on push tells the pipeline which commit ID to check out and build, and the build records that ID, so any artifact can be traced back to an exact source tree.

example: Make a repository, with the author and committer "Ann <ann@example.com>" and both dates fixed to 2026-01-01T00:00:00Z, so the hashes are reproducible (commit signing off). Create a.txt with the text hello, and src/m.py with print(1). Run git add and git commit -m first. Git creates five objects. Blob ce01362... holds hello (the same ID you get anywhere, and the same as the example in the diagram). Blob b917a72... holds print(1). Tree 8afc95e... lists m.py for the folder src. Tree c91d713... is the root and lists a.txt and src. Commit dad3e29340a1... points to tree c91d713 and has no parent. The branch file .git/refs/heads/main (or master) contains that commit ID. The command git count-objects shows 5 objects.
Now change a.txt to hello world and commit as second at 2026-01-02. Git creates three new objects: a blob for the new content (3b18e51...), a new root tree (1ff1a4e...) which lists the new blob and the same src tree 8afc95e, and a new commit (54ea4c6...) whose parent is dad3e29. The directory src did not change, so its tree and blob are reused, and the object count rises from 5 to 8, not to 10. This shows why branching and committing are cheap: a commit stores only what is new.
See the effect on storage. Take a file of 1.08 MB (15,000 lines of random text) committed in two versions that differ in one line. As loose objects, each version is compressed alone, about 0.64 MB each, 1.29 MB total. After git gc, the pack holds the first version in full (about 630 KB for the whole pack) and the second as a delta of a few hundred bytes. Storing 1,000 versions of that file with small edits would cost roughly 0.6 MB plus 1,000 small deltas, not 640 MB.
Now a merge. History: C1 on main; branch feature starts at C1 with F1 and F2; main gets M1. The merge base is C1. The three trees are the tree of C1 (base), the tree of M1 (ours) and the tree of F2 (theirs). If F2 changed util.py only and M1 changed app.py only, the result takes both changes with no conflict, and the merge commit has two parents (M1 and F2). If both changed the same line of app.py differently, Git writes conflict markers and waits for a human.
Finally, integrity: if someone changes one byte in an old file on a server, the blob hash no longer matches, so git fsck detects the damage; if someone replaces an old commit with another, the new commit has another ID, and everyone who has the old ID can see that the history differs. Signed tags or commits (GPG or SSH) add proof of who made the change.
intuition: A Merkle tree of snapshots: if the top hash matches, everything below it matches.
The design is natural once you choose to name data by its content. Then identical data is stored once, a name is a proof of content, and history is a chain of hashes that cannot be altered unseen. Everything else follows. Snapshots, not diffs, make any version cheap to read. Immutable objects make copying, caching and distributing safe, so every clone can be a full peer. Branches are just movable labels on an immutable graph, so they cost almost nothing, and the graph gives merge a precise definition through the common ancestor. The complexity users meet is mostly in the command line over this small, clean model.
mistakes: People often think Git stores the differences between versions. In fact each commit refers to a full snapshot (a tree). Deltas are used only inside packfiles as a compression detail, and they are chosen by similarity, not by commit order.
People often think a branch is a copy of the code or a separate line with its own history. In fact a branch is a 41-byte file that holds one commit ID. The history belongs to the commits, and any number of branches can point into the same graph.
People often think rebase and amend change commits. In fact commits are immutable; these commands create new commits with new IDs and move the branch name. The old commits still exist (visible through git reflog) until garbage collection removes them. Rewriting commits that others have already pulled forces them to reconcile two histories.
People often think git tracks file renames. In fact Git stores no rename information; it infers a rename by comparing similar content when you diff or merge. This usually works but fails for heavily edited or very small files.
People often think deleting a file or a secret from the latest commit removes it from the repository. In fact every earlier commit still holds it, and every clone has it. Removing a leaked secret needs history rewriting (git filter-repo) on all copies and, above all, rotating the secret.
tradeoffs: Choose merge commits when you want to keep the true history of parallel work, and every merge is a visible event; choose rebase (or squash merge) when you want a linear, readable history on the main branch. Rebase rewrites commits, so it is safe only on commits that nobody else has based work on; merge keeps everything, but histories become branchy. Most teams use squash merges for feature branches and merge commits for long-lived branches.
Choose trunk-based development (short-lived branches, merge to main at least daily, feature flags) when you have good CI and want fast integration; choose long-lived release branches (Git Flow style) when you must support several released versions at once. The cost of long-lived branches is merge pain that grows with the time apart, often more than linearly.
Choose a monorepo (one repository for many projects) when you want atomic cross-project changes, shared tooling and one version of dependencies; choose many repositories when teams are independent and want separate access control, release cycles and small clones. Monorepos at large scale need partial clone, sparse checkout, the commit-graph and tooling (a build system with caching), and above some size (hundreds of GB), custom systems such as Google's Piper or Meta's Sapling.
Choose Git LFS or an artifact store for large binary files (models, video, datasets) because Git stores every version of every blob and clones carry all history; choose plain Git for text and source. LFS keeps pointers in Git and the files on a server, at the cost of an extra service and a weaker offline story. For datasets and models, many teams use data-versioning tools or table formats instead.
Choose SHA-256 repositories only when your hosting, CI and tools support them, which is not yet universal; keep SHA-1 (with collision detection) for compatibility until the ecosystem is ready.
friction: The command-line interface is the best-known problem. Commands grew over years, names and options are inconsistent (checkout used to do three different things, now split into switch and restore), and the model of working tree, index and repository confuses newcomers. Mistakes feel dangerous even though most can be undone with the reflog; data loss does happen with reset --hard on uncommitted work or with forced pushes.
Large repositories and large files are a real limit. A clone downloads all history by default, a repository with millions of files makes git status slow unless a file-system monitor is used, and a binary file changed often bloats the history permanently, because Git cannot forget old blobs without rewriting history. Partial clone, sparse checkout and Scalar help, but need setup and server support.
Merge conflicts remain a human problem. Git merges text lines and knows nothing about the meaning of code, so it can produce a clean merge that is semantically broken (two branches each change one side of an API), or conflicts in generated files and lock files. CI on the merge result and merge queues reduce the risk but add process.
Access control and secrets are outside Git's model. Anyone who can clone can read all history, there is no per-directory permission, and a secret committed once is in every clone. Also the hash transition is slow: SHA-256 repositories do not interoperate with SHA-1 ones without conversion, and hosting services and tools are only slowly adding support. Git 3.0 will bring breaking changes to defaults, which tools and scripts need to be ready for.
practice: Commit small, coherent changes with messages that explain why, not only what: a short summary line (about 50 characters), a blank line, and a body. Use branches for each piece of work and keep them short. Review diffs before committing with git diff --staged, and use git add -p to stage parts of files. Never commit secrets, build output or large binaries; use .gitignore, secret scanning and pre-commit hooks.
Learn the recovery tools. git reflog shows where HEAD and branches have been, so most mistakes (a bad reset, a lost commit after rebase) can be undone by checking out the old hash. git restore and git switch replace the overloaded checkout. git bisect finds the commit that introduced a bug by binary search over history: about log2(n) test runs, so 10 runs for 1,000 commits. git blame and git log -S show who changed a line and when a string appeared.
Set a clear team policy: protected main branch, required reviews and passing CI, squash or rebase merge, and a merge queue if the team is large. Use signed commits or tags for releases, and tag versions so that deployments point to exact commit IDs. In CI, check out by commit ID, use shallow clones (--depth=1) or partial clones to save time, and cache dependencies. For GitOps, treat the Git repository as the desired state of infrastructure and let a controller apply it.
For big repositories, enable the commit-graph and multi-pack index (git maintenance start does this), use git clone --filter=blob:none for developer machines, sparse checkout for sub-trees, and fsmonitor for large working trees. Keep large files in LFS or outside Git. Prune with git gc occasionally on servers, and avoid force-pushing shared branches; use --force-with-lease when you must.
interview: Explain what a Git commit really is and why the commit hash identifies the whole history. || A commit is an object that stores a pointer to a root tree (the snapshot), the parent commit IDs, author, committer, timestamp and message. Its ID is the hash of all of that, including the parents' IDs. Therefore any change in an ancestor changes every descendant's ID: the hash is a Merkle chain over the history.
Why are branches cheap in Git but expensive in some older systems? || A branch is a tiny file with one commit ID; creating it copies nothing. Snapshots share unchanged trees and blobs by hash, so a new commit stores only changed objects. Older centralized systems often copied directories or tracked per-file histories on the server.
What happens when you run git rebase main on a feature branch, and when is it dangerous? || Git finds the commits on the feature branch not in main, replays each onto the tip of main, making new commits with new IDs, and moves the branch. It is dangerous when others have already based work on the old commits, since their history diverges and a force push will overwrite their reference; use it on private branches.
How does Git keep repositories small despite storing full snapshots? || Identical content is stored once by hash. Trees are shared between commits for unchanged directories. And packfiles use delta compression, storing similar objects (like versions of one file) as small diffs against a base, plus zlib compression, usually shrinking storage by an order of magnitude.
Your monorepo clone takes 40 minutes and git status takes 20 seconds. What do you do? || Use partial clone (--filter=blob:none) and shallow or sparse checkout so only needed data is fetched; enable the commit-graph, multi-pack index and fsmonitor with untracked cache; run git maintenance; remove large binaries from history or move them to LFS; and consider splitting repositories if boundaries are clear.
quiz: What are Git's four object types and what does each store? || Blob (file contents), tree (a directory's entries with names and child IDs), commit (a tree ID, parent IDs, author and message), and tag (a named, optionally signed pointer to an object).
Why does changing an old commit change all later commits' hashes? || A commit's hash covers its parent's hash, so the new ID of the changed commit becomes part of the next commit's content, and so on down the chain.
A repository has 5 objects after the first commit. After changing one file in the root directory and committing, how many objects does it have and why? || 8: a new blob for the file, a new root tree, and a new commit. The unchanged sub-directory tree and the other blob are reused.

value: Jupyter is an interactive computing environment in which you write code in small pieces called cells, run each cell in a live process, and see the result (numbers, tables, charts, text) right below the cell. The cells, their outputs and the explanatory text are saved together in one document called a notebook. This turns programming into a conversation with the data: run a query, look at the result, change one line, run again, without starting a program from the beginning each time.
Two ideas make it work. First, a notebook does not run code itself. It is a web page (or an editor window) that talks to a separate program, the kernel, which holds the live state of a language interpreter such as Python. Variables you create in one cell are still there in the next cell, because the kernel keeps running. Second, the format is general: the same notebook interface can talk to kernels for Python, R, Julia, Scala, SQL and many other languages. The name Jupyter comes from Julia, Python and R.
For the layer above (data exploration, machine learning experiments, teaching, reports, and managed notebooks on Databricks, Google Colab, SageMaker and VS Code), Jupyter is the standard way to work with data. Two lower concepts matter. Python (L0) supplies the default kernel, IPython: a Python interpreter extended with magics, rich display and history. Interpreters and bytecode virtual machines (L3) supply the idea that makes a persistent session possible: an interpreter that compiles each piece of code to bytecode and runs it in a long-lived global namespace, so that state survives from one execution to the next.
terms: Notebook — a document (an .ipynb file, stored as JSON) containing an ordered list of cells with their outputs.
Cell — one unit of the notebook: a code cell (executed by the kernel), a Markdown cell (formatted text) or a raw cell.
Kernel — the separate process that executes code and keeps variables and imports alive between cells; restarting it clears all state.
Jupyter server — the web server that serves the notebook interface, stores files and starts, stops and connects to kernels.
Messaging protocol — the set of JSON messages (execute_request, stream, display_data, execute_reply and others) that front ends and kernels exchange, carried over ZeroMQ sockets or WebSockets.
MIME bundle — a dictionary that offers one output in several formats (text/plain, text/html, image/png), so that each front end chooses the richest one it can show.
Execution count — the number shown in brackets next to a code cell, counting how many cells the kernel has run; it records the order of execution, which may differ from the order on the page.
Magic command — a special IPython command such as %timeit or %%sql that is not Python syntax but is handled by the kernel.
history: Fernando Pérez, a physics PhD student, started IPython in late 2001 as a better interactive shell for Python, with a famous first version of only about 260 lines. He wanted a tool that matched the workflow of scientists, who explore data step by step. The idea of a notebook document with code, results and text was older: Mathematica had it since 1988, and Maple and Sage had their own forms. IPython brought it to open-source scientific Python.
The web-based IPython Notebook appeared in 2011 (IPython 0.12), built by Pérez, Brian Granger and Min Ragan-Kelley and others, using ZeroMQ to separate the browser interface from the kernel. This architecture made it easy to attach other languages. In 2014 the language-independent parts were split into Project Jupyter, a non-profit open-source project, while IPython kept the Python kernel and shell. Funding from the Sloan and Moore foundations supported the work. The project received the ACM Software System Award in 2017.
JupyterLab (stable version 1.0 in 2019, 3.0 in 2021, 4.0 in 2023) replaced the single-document interface with a full workspace of panels, file browser, terminals and extensions. The classic Notebook interface was rebuilt on JupyterLab components as Notebook 7 (2023). Meanwhile the format became an industry standard: Google Colab (2017), AWS SageMaker, Azure and Databricks offer notebooks, and VS Code and PyCharm open .ipynb files natively. JupyterHub (2015) serves notebooks to many users, for classes and companies.
Recent years added real-time collaboration (using CRDTs, so that several people edit one notebook), AI assistants, and alternatives that fix known weaknesses: reactive notebooks such as marimo (2023) re-run dependent cells automatically and store notebooks as plain Python files. The core idea, a live kernel behind a document of cells, has not changed.
how: A running Jupyter session has three parts: the front end in your browser, the Jupyter server, and the kernel. The browser shows the notebook as cells. When you press Shift+Enter on a code cell, the front end sends the cell's text as an execute_request message over a WebSocket to the server. The server forwards it to the kernel, which is a separate process started from a kernel specification (a small JSON file that says which command to run, for example python -m ipykernel_launcher). Because the kernel is a separate process, a crash or an infinite loop in your code does not take down the web page, and you can interrupt or restart it.
Between the server and the kernel the protocol uses several ZeroMQ sockets. The shell socket carries execute requests and replies. The IOPub socket is a broadcast channel on which the kernel publishes everything that happens: status changes (busy, idle), printed text, results, errors and rich output, so all connected front ends see the same output. The stdin socket handles input() calls. The control socket carries urgent commands such as shutdown and interrupt, and a heartbeat socket checks that the kernel is alive. Every message is a JSON object with a header (id, type, session, time), a parent header (which request this answers), metadata and content, signed with an HMAC key from the connection file, so that other local users cannot send code to your kernel.
Inside the kernel, the interpreter layer does the work. IPython takes the cell text and first applies its own transformations: magics (a line starting with %), shell escapes (!ls), and help syntax (name?). The result is Python source, which IPython parses into an abstract syntax tree. All statements run in exec mode, but the last expression of the cell is treated specially: its value is evaluated and displayed, which is why typing df at the end of a cell shows a table. The compiled code object (bytecode) is executed in the kernel's user namespace, one dictionary of global names that lives as long as the kernel. This is the interpreter concept from L3: compile to bytecode and run it on a virtual machine, with a long-lived global environment. It explains why the second cell can use variables from the first, why deleting a cell does not delete its variables, and why restarting the kernel removes everything.
Output is richer than text. When the last expression returns an object, IPython asks it for a representation using methods like _repr_html_, _repr_png_ or _repr_latex_, and sends a MIME bundle with all available forms. A pandas DataFrame offers HTML, a Matplotlib figure offers PNG, and a plain object offers text. The front end picks the best format it supports: the browser shows the HTML table or the image, a terminal shows text. Printed text goes to the stream message type, errors come back with a traceback, and display_data messages can update an output in place, for progress bars and live charts.
The notebook file keeps all of this. The .ipynb format (nbformat version 4) is a JSON document with notebook metadata (kernel name, language) and a list of cells. Each code cell has its source, its execution_count and its outputs, where each output holds the MIME bundle: images are stored as base64 text inside the JSON. This means the file contains both the code and the results of one particular run. It makes notebooks easy to share and view (GitHub renders them), and it also makes them awkward to diff and review, since outputs and execution counts change every time.
Around the core there is a large tool chain. nbconvert turns notebooks into HTML, PDF or scripts. Papermill runs a notebook with parameters, from a scheduler, and saves the executed copy, which is how many teams run notebooks as batch jobs. Jupytext keeps a plain-text pair (a .py file) for each notebook so that version control and code review work. nbdime does notebook-aware diff and merge. JupyterHub starts a server per user, often in containers on Kubernetes, with authentication and resource limits. Kernels can also run remotely, for instance attached to a Spark cluster through PySpark or Spark Connect, so the notebook is a thin client for heavy computation.

Finally the shell channel returns execute_reply with status ok. All of this typically takes a few milliseconds of protocol overhead plus the real compute time of the groupby.
Now the hidden state problem. She notices that the totals look too large and re-runs cell 3 twice while debugging. The kernel multiplied amount by 100 three times in total, so amount is now 1,000,000 times its original value, and cell 2 (if re-run) shows totals 10,000 times higher than after the first run. The notebook page still shows cell 3 once, with execution count [5], and nothing on the page tells her it ran three times. If she saves the notebook and sends it to a colleague, "Run All" from top to bottom gives a different (correct) result than her saved outputs. The only trustworthy check is: restart the kernel and run all cells in order. If a notebook does not pass this test, its outputs are not reproducible.
A size example. The notebook has 40 Matplotlib charts, each a PNG of about 60 KB. In the .ipynb file each image is base64 text, which is about 4/3 larger: 80 KB. So the file is about 3.2 MB, of which the code is probably under 20 KB. Re-running the notebook changes every image's bytes and the execution counts, so git diff shows megabytes of change even if the code is the same. Teams solve this with nbstripout (remove outputs before commit), Jupytext (commit a .py pair), or nbdime for readable diffs.
A production example. A nightly report notebook takes a parameter run_date. A scheduler calls papermill report.ipynb out/report_2026-07-04.ipynb -p run_date 2026-07-04. Papermill starts a kernel, injects a cell with the parameter, runs all cells, and writes the executed copy with outputs. If cell 7 fails, the output notebook contains the traceback at that cell, which makes debugging easy: open the failed notebook and see exactly where it stopped, with the variables' printed values.
intuition: A lab notebook that can run its own experiments: you write a note, run a step, paste the result next to it, and the apparatus stays on the bench between steps.
The design is natural because exploration is iterative and expensive to restart. Loading a dataset may take a minute; a model may take an hour. A live process that keeps state turns each next step into a small edit instead of a full rerun. Separating the kernel from the interface makes the system language-neutral and robust. And storing code, results and text together makes the document a record of reasoning, not only of code. The same properties explain its main weakness: the state is invisible, and the order of execution is the user's responsibility.
mistakes: People often think a notebook is a program that runs from top to bottom. In fact it is a record of cells run in the order the user chose, against a stateful kernel. The page order and the execution order can differ, so the file does not guarantee the results shown.
People often think a notebook runs in the browser. In fact the browser only shows the interface. The code runs in the kernel process on the server or on your machine, with its memory, files and credentials. Any notebook that you open and run has the same power as any program you run; opening an untrusted notebook and executing it is a security risk, and notebooks from others show their HTML and JavaScript outputs only after they are trusted.
People often think the outputs in a notebook are the current results. In fact they are stored from whenever the cell last ran, possibly with older code or data. Looking at a shared notebook without re-running it can mislead.
People often think Jupyter is for Python only. In fact the protocol is language-independent; there are kernels for R, Julia, Scala, Java, SQL, Bash and dozens of others. Python is the default only because IPython was the first kernel.
People often think notebooks and production code are opposites. In fact notebooks are an excellent place for exploration and a poor place for long-lived logic. The usual path is to explore in a notebook, move reusable functions into modules with tests, and keep the notebook as a thin driver or report.
tradeoffs: Choose a notebook for exploration, teaching, communication of results and one-off analysis, where fast feedback and visible output matter more than strict structure. Choose scripts or modules with tests and a scheduler for anything that must run repeatedly, be reviewed in detail, or be maintained by several people. Notebooks are weak at code reuse, testing and review; scripts lack the immediate view of intermediate results.
Choose classic Jupyter (JupyterLab or Notebook 7) when you need open standards, many kernels, extensions and the ability to self-host. Choose a managed notebook product (Databricks, Colab, SageMaker, Hex, Deepnote) when you want zero setup, attached compute, access control and collaboration, and you accept some vendor-specific features and data lock-in. Choose VS Code notebooks when you want a full editor, debugger and Git integration next to the notebook.
Choose a reactive notebook (marimo, Observable) when hidden state is the main problem and you value reproducibility: cells form a dependency graph and re-run automatically, and files are plain code. You give up the Jupyter ecosystem and some tools that expect .ipynb.
Choose to run kernels near the data (on the cluster, in the cloud region of the warehouse) instead of on a laptop when datasets exceed a few GB, because transferring data is slower than moving the notebook. The cost is the remote environment: dependency management, credentials, idle-cost control (auto-shutdown) and security.
Choose papermill-style notebook execution for parameterised reports when the audience wants a notebook output and the team is small; choose a proper workflow (Airflow, Dagster, Databricks Jobs running Python files) when you need retries, dependencies, testing and clear ownership.
friction: Hidden state is the central problem. Out-of-order execution, deleted cells whose variables live on, and re-run cells that change data in place make results depend on the history of the session, not just on the visible code. Studies of public notebooks have found that a large share cannot be re-run to the same result, and the usual advice is to restart and run all before sharing.
Version control and review are awkward. The JSON format mixes code, outputs and metadata; images inflate file size; diffs are unreadable; merge conflicts in JSON are painful. Tools help (nbdime, jupytext, nbstripout, GitHub's rendering), but each is an extra step to adopt, and team habits matter more than tools.
Engineering practice suffers. Notebooks encourage global variables, long cells, copy-and-paste instead of functions, and weak testing. Dependencies are often undocumented: a notebook says import torch but not which version. Turning a notebook into a reliable pipeline takes work: parameters, configuration, logging, error handling, and a pinned environment.
Operational issues also appear. A notebook server gives the user a shell on the machine, so authentication, network exposure and isolation matter; an open Jupyter server on the internet is a well-known way to get compromised. Kernels hold memory (a 20 GB DataFrame stays in RAM until it is deleted), idle servers cost money, and multi-user installations need resource limits and cleanup. Large outputs (a table of a million rows) can freeze the browser.
practice: Treat the notebook as a lab notebook, not as a product. Keep cells small and focused; put reusable code into a Python module (imported with autoreload during development), and test that module. Before sharing or committing, restart the kernel and run all cells from the top; if it fails or the results change, fix it. Put imports and configuration in the first cell and parameters in one clearly marked cell.
Make notebooks reviewable. Strip outputs before committing (nbstripout as a pre-commit hook) or pair each notebook with a .py file using Jupytext, and review the text file. Use nbdime for diffs when needed. Record the environment: a requirements or environment file with pinned versions, or a container image, so that a colleague gets the same libraries. Never put secrets in cells; read them from environment variables or a secret manager.
For production use, parameterise with papermill or move the logic into scripts and call them from a scheduler. Keep the executed notebook as a run artifact for debugging. In Databricks or Spark setups, connect through Spark Connect or the platform's notebook, use sampling for exploration (df.limit(1000).toPandas()) and avoid collecting large results to the driver, since toPandas on a billion rows will run out of memory.
Secure the deployment: bind to localhost or sit behind an authenticating proxy, use tokens or SSO, run JupyterHub with per-user containers and resource limits, and shut down idle kernels automatically. Learn the useful commands: %timeit and %prun for timing, %who to list variables, %debug after an exception, and %load_ext autoreload with %autoreload 2 to pick up edits to modules without restarting.
interview: How does the Jupyter architecture separate the interface from execution, and why is that useful? || The browser front end talks to a server, which talks to a kernel process through a messaging protocol (ZeroMQ channels: shell, IOPub, stdin, control, heartbeat). The separation allows many languages to plug in as kernels, remote kernels on big machines, several front ends viewing one kernel, and crashes or interrupts without losing the interface.
What is the hidden-state problem and how do you make a notebook reproducible? || Cells run in any order against a persistent namespace, so results depend on session history that is not visible in the file. Make it reproducible by restarting the kernel and running all cells top to bottom, pinning the environment, avoiding in-place mutation across cells, and putting logic in modules or using a reactive notebook.
How would you put a notebook into a production schedule, and when would you refuse? || Parameterise it with papermill, run it on a scheduler with a pinned image, store the executed notebook as an artifact, and add alerts on failure. Refuse (or refactor) when the logic is business-critical, needs tests, retries or complex dependencies, which belong in versioned modules run by a workflow engine.
What security risks does a Jupyter server create and how do you reduce them? || It executes arbitrary code with the server user's permissions, so an exposed or weakly authenticated server gives a remote shell. Reduce risk by token or SSO authentication, localhost or a proxy with TLS, per-user containers with minimal credentials and network policy, not trusting notebooks from unknown sources, and idle shutdown.
A colleague's notebook uses 40 GB RAM on a shared server. How do you find and fix the cause? || Look at the kernel's variables (%whos, memory profiler) for large DataFrames and copies kept in cells and in the output history (the Out dictionary stores results). Delete variables, avoid keeping the entire history of outputs, process in chunks, push work down to Spark or the database, and set per-user memory limits.
quiz: What are the three main parts of a running Jupyter session? || The browser front end, the Jupyter server, and the kernel process that runs the code.
Why does a variable still exist after you delete the cell that created it? || The kernel's namespace keeps it alive; deleting the cell only removes text from the document. Only restarting the kernel (or del) removes the variable.
A notebook has 40 PNG charts of 60 KB each. About how large is the .ipynb file, and why? || About 3.2 MB, because images are stored as base64 text which is about 4/3 of the binary size (80 KB each), plus a little for the code.
A cell that multiplies a column by 100 is run three times. By what factor is the column scaled and how do you find the problem? || By 100³ = 1,000,000. The page does not show repeats; you detect it by restarting the kernel and running all cells in order, and by checking execution counts.
When would you choose a reactive notebook or a script instead of Jupyter? || When reproducibility and review matter more than free-form exploration: a reactive notebook re-runs dependent cells and stores plain Python files, and scripts or modules with tests suit repeated or production work.
