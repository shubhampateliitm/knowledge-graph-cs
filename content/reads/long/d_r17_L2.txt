@@ antientropy
value: In a leaderless database such as Dynamo, Cassandra or Riak, every write goes to several replicas (copies) of the data, and no single node decides the order of writes. This design stays available when machines fail. But it has a cost: a replica can miss a write because it was down, because a network link dropped the message, or because the client gave up waiting. After that, the three copies of a key are no longer the same. Left alone, they would drift further apart and different readers would see different answers for ever.
Read repair, hinted handoff and anti-entropy are three layers of defence against this drift. Hinted handoff handles the short outage: another node keeps the missed write and delivers it when the failed node returns. Read repair handles the hot data: when a read finds replicas that disagree, it fixes them right then. Anti-entropy handles everything else: a background process compares replicas and copies whatever differs, so even data that nobody reads, and writes whose hints were lost, eventually converge. Together they give "eventual consistency" a concrete meaning: not "maybe, some day", but "within a repair cycle you control".
The layers below make the background comparison cheap. A Merkle tree (L2, content addressing) lets two replicas compare millions of rows by exchanging a few hashes and then walking down only the branches that differ. A cryptographic or at least well-mixed hash function (L3) turns a whole range of rows into a short fingerprint, so that equal data is proven equal without sending it. For the layer above, distributed key-value and wide-column databases (L1), this is what turns "replicas might diverge" into "replicas are repaired on a schedule".
terms: Replica — one of several copies of the same data, each on a different node.
Anti-entropy — a background process that compares replicas and copies the differences, so they converge. "Entropy" here means disorder between copies.
Read repair — fixing stale replicas as a side effect of a client read that noticed a mismatch.
Hinted handoff — when a replica is down, another node stores the write with a "hint" naming the target, and sends it when the target is back.
Merkle tree — a tree of hashes: each leaf hashes a slice of the data, each parent hashes its children, so the root summarizes everything.
Tombstone — a marker that records a delete, so the delete can be copied to other replicas like any other write.
Sloppy quorum — counting a write as successful when stand-in nodes outside the usual replica set accept it, as in Dynamo.
gc_grace_seconds — the Cassandra setting for how long a tombstone is kept before it may be purged; the default is 10 days.
history: The word "anti-entropy" comes from Demers and colleagues at Xerox PARC, who wrote "Epidemic Algorithms for Replicated Database Maintenance" (1987). They had a real problem: the Clearinghouse name service kept copies of its database on many servers, and the copies disagreed. Their answer was gossip. Each server regularly picks a random partner and the two compare and merge their data, in the way a rumour or a virus spreads. They showed that this converges quickly and with high probability, without any central coordinator.
The second ingredient is older than most people think. Ralph Merkle patented hash trees in 1979 and published the best-known account in 1987. He wanted to verify a large set of data, or a set of digital signatures, with one short value.
Amazon put the two together in Dynamo (DeCandia and others, SOSP 2007). Dynamo was built for the shopping cart, where being unable to accept a write was worse than a brief disagreement. The paper describes sloppy quorums with hinted handoff for short failures, and Merkle trees for "anti-entropy to keep replicas synchronized" after longer ones. Each Dynamo node keeps a separate Merkle tree per key range it hosts, so two nodes can compare just the range they share.
The open-source descendants copied the design. Cassandra (Facebook, 2008, then Apache) has `nodetool repair`, hinted handoff and read repair. Riak added "active anti-entropy", which keeps its hash trees on disk and updates them as writes arrive, so no full scan is needed to build them. ScyllaDB changed repair to work on row level and added a managed repair service. Over time Cassandra also added incremental repair (version 2.1), which only compares data written since the last repair, and version 4.0 fixed many repair bugs. A community tool called Cassandra Reaper schedules repairs in small pieces.
how: There are three mechanisms, working at three different time scales.
First, hinted handoff. A coordinator node sends a write to all replicas of the key (for example three). If one replica is marked down, the coordinator, or in Dynamo a stand-in node, stores the write locally together with a hint: "this belongs to node C". A background task checks for C regularly. When C is back, the hints are replayed in order. In Cassandra the hints are only kept for a limited time, three hours by default (`max_hint_window`). If a node is down longer than that, hints stop accumulating, and the node must be repaired by the next mechanism instead. Hints are a performance optimization, not a guarantee: the coordinator itself can crash and lose them.
Second, read repair. When a client reads at consistency level QUORUM, the coordinator asks one replica for the full data and the others only for a digest (a hash of their version). If the digests match, the coordinator returns the data. If not, it fetches the full data from all of them, picks the winner (in Cassandra, the value with the newest timestamp; in Dynamo and Riak, the version with a causally newer vector clock, or all siblings if they are concurrent), returns it to the client, and writes it to the replicas that were behind. This is cheap because the read already paid for contacting the replicas. But it only repairs keys that people read, so cold data stays broken.
Third, Merkle-tree anti-entropy. Each replica scans its data for a token range and builds a tree. The data is divided into a fixed number of leaf ranges by key hash. Each leaf stores a hash of all rows in its range, and each inner node stores a hash of its two children. The depth is limited, so a leaf covers many rows. Two replicas now exchange their trees. First they compare the roots: if equal, the whole range is identical and the work is finished. If not, they compare the two children, and recurse only into children whose hashes differ. At a differing leaf, they exchange the actual rows in that leaf range and merge them, again using timestamps or vector clocks. If a few rows differ, only a few paths are walked, and only a few leaf ranges are streamed. Here the hash function (L3) is doing the real work: a good hash makes it almost impossible for two different ranges to share a fingerprint by accident, so "hashes equal" can be trusted to mean "data equal".
Two details make this work in a live system. First, both replicas must hash the same rows in the same order with the same ranges, otherwise equal data gives different hashes. So the coordinator of the repair fixes the token range and the tree layout, and each replica builds its tree from a consistent snapshot of its data (in Cassandra this is a "validation compaction", a read-only pass that looks like a compaction but writes nothing). Second, the hash covers not only values but also timestamps and tombstones. A replica that holds a newer version, or a delete marker the other lacks, therefore shows a different hash, and the repair copies the winning version in the right direction: each side may be behind on different rows, so the exchange goes both ways.
The cost is in building the tree. Hashing requires reading every row of the range, so a repair is a full scan of the data on disk, run on every replica, and then a network exchange. This is why repair is heavy, and why systems build the trees in the background with throttling. Riak avoids it by updating persistent trees on every write. Incremental repair avoids it by marking data as "repaired" and only hashing the unrepaired part next time.
Last, deletes. A delete is written as a tombstone, because a replica that was offline must learn about the delete. A tombstone cannot be kept for ever, so it is purged after `gc_grace_seconds`. If a replica missed the delete and no repair reached it before the tombstone was purged on the others, then the old value is the only copy left, and it spreads back as if new. This "zombie" data is the main reason the rule "run a full repair on every node within gc_grace_seconds" exists.

example: Take a table with 3 replicas (A, B, C) and one token range holding 1,000,000 rows. Suppose a Merkle tree has 2^15 = 32,768 leaves, so each leaf covers about 30 rows. Node C was down for 20 minutes, so it missed 500 writes. The hint window is three hours, so A's hints would normally replay and fix C. But suppose node A, which held the hints, was replaced after a disk failure, so the hints are gone. C is now missing 500 rows, spread over, say, 480 different leaf ranges.
Without anti-entropy, a read at consistency ONE that hits C returns old data for those rows. A read at QUORUM would notice the digest mismatch and repair the row, but only for rows somebody reads.
Now run a repair. A and C each scan their 1,000,000 rows, hash them, and build trees. This costs one pass over the data, perhaps a few seconds to minutes depending on disk speed and throttling. They compare roots (different), then walk down. The number of hash comparisons is about 2 per level for each differing path, and 480 differing leaves out of 32,768 means several thousand comparisons (the top nine levels are shared, and each of the 480 paths then needs about six more levels), instead of 1,000,000 row comparisons. Then they stream 480 leaf ranges x 30 rows = about 14,400 rows, not 1,000,000. Only the 500 truly missing rows matter, but the repair sends about 29 times more than needed, because the leaf is the smallest unit. A deeper tree would send less but cost more memory.
Compare the alternative: if only one row differed, one path of 15 levels would be walked, so about 30 hash comparisons and one leaf of 30 rows would be streamed. If the replicas differed in all rows, the tree gives no benefit, and the cost is a full copy plus the cost of building the trees. The benefit depends on "mostly equal".
Finally, the delete case. A row was deleted at time T, and C was down. With `gc_grace_seconds` of 10 days, the tombstone lives on A and B until day 10. If a repair runs on day 5, C gets the tombstone and everything is fine. If no repair runs before day 10, A and B purge the tombstone, and when C returns and is read or repaired, its old copy of the row is the newest data anyone has. The deleted row returns.
intuition: Two librarians compare one summary card per shelf, and walk to a shelf only when the cards differ.
The design is natural once you see that copies are almost always equal. Checking every item is wasteful when 99.9% match. A hash is a way to ask "are these two big things the same?" with a very small message, and a tree of hashes lets you ask that question about the whole, then about halves, then quarters, so you find the few differences in a number of steps equal to the depth of the tree. The three mechanisms are the same idea at three speeds: hints fix what you know you missed, read repair fixes what you happen to touch, and the Merkle tree finds what you did not know you missed.
mistakes: People often think a repair compares the actual data on each replica. In fact it compares hashes first and moves data only for leaves that differ, which is why a repair on healthy replicas sends almost no data. But it still has to read all the data to compute the hashes, so it is cheap on the network and expensive on the disk.
People often think hinted handoff makes writes durable. In fact a hint is stored on one node, for a limited time, and does not count toward the write quorum at consistency levels such as QUORUM. If the node holding the hints fails, or the target stays down past the hint window, the write is only on the other replicas until a repair runs.
People often think read repair keeps replicas consistent, so repair jobs are optional. In fact read repair only touches keys that are read, and often only a sample. Cold keys, and keys deleted and never read again, stay different. Only a regular full repair covers all data, and skipping it risks zombie rows once tombstones are purged.
People often think anti-entropy makes the database strongly consistent. In fact it gives convergence after the fact, usually within minutes to days, not read-your-writes. If you need a read to see a write immediately, you use quorum reads and writes (R + W > N), and even that is not full linearizability in Dynamo-style systems.
People often think a Merkle tree must be rebuilt from scratch for each repair. In fact this is true for the simplest design (Cassandra's classic one), but not for all. Riak keeps hash trees on disk and updates them when data changes, and incremental repair limits hashing to new data.
friction: Repair is the most operationally painful part of a leaderless database. A full repair reads all data on all replicas. On a cluster with tens of terabytes per node, this can take days, uses disk and network bandwidth that user queries also need, and may overlap with compaction. Teams therefore schedule repairs in small token slices (Cassandra Reaper), throttle them, and watch their duration, because the repair must finish inside the tombstone grace period or deleted data can come back.
The tree has limited resolution. Because the tree has a fixed number of leaves, a table with billions of rows has leaves holding thousands of rows each. One differing row then causes a whole leaf to be streamed. This is called "over-streaming" and it can move many times more data than needed, particularly after a long outage where small differences are spread everywhere.
Time and clocks matter. Cassandra picks the winner by timestamp, so clock skew between clients or nodes can decide which write survives, and a repair can happily copy the wrong value everywhere. Dynamo-style systems with vector clocks avoid this but pass conflicts to the application.
Finally, there are corner cases around correctness: repair streams data while writes continue, so replicas that were equal when the tree was built may already differ; a node that is repaired while another is down can only compare with the available replicas; and bugs in incremental repair have caused data to be marked "repaired" when it was not. Many operators still run a full repair now and then as a safety net.
practice: Treat repair as a scheduled job, not an emergency action. For Cassandra, run it on every node within gc_grace_seconds (default 10 days), commonly once a week. Use a scheduler such as Cassandra Reaper, or the managed repair in your platform, to repair token subranges in small slices, so one failure does not lose hours of work, and so the load is spread. Prefer incremental repair where your version supports it well, and run a full repair occasionally to check.
Never lower gc_grace_seconds without a repair plan. If you reduce it to save disk space (tombstones pile up in delete-heavy tables), you shrink the window in which repair must complete. Also avoid designs that need many deletes; a queue stored in a wide-column table is the classic cause of tombstone trouble. Time-to-live (TTL) data with time-window compaction is easier to repair and purge.
Pick the consistency levels so that read repair has less to do. QUORUM writes and QUORUM reads (with replication factor 3) already ensure that every read sees the latest acknowledged write. After a node has been down longer than the hint window, run repair on it before it serves reads, or rebuild it fully. When you replace a node, stream its data from the others instead of relying on hints.
Measure. Track repair duration per table, the amount of data streamed per repair (if it is large each time, a node is probably dropping writes or hints), pending hints, and dropped mutations. A node that needs a lot of repair every week has a cause: overload, a flaky network, or a clock problem. If your database offers continuous automatic repair, use it; if not, add alerts when the last successful repair is older than the grace period.
tradeoffs: Choose to rely on hinted handoff and read repair alone only when data is short-lived or you can tolerate rare permanent differences, for example a cache of recomputable data. The gain is zero scheduled load. The loss is that cold keys and long outages are never repaired, and deletes can come back.
Choose scheduled Merkle-tree repair when data lives for months and must be correct. The gain is a bounded convergence time and safe deletes. The cost is a full disk scan per replica per cycle, which on a node with 2 TB of hot data can take hours and compete with queries.
Choose incremental repair over full repair when your data is mostly immutable and large. It hashes only the part written since the last repair, so a weekly job costs a fraction. You give up some simplicity: it depends on correct tracking of what is "repaired", and a bug or a missed step can leave data unrepaired without a visible sign.
Choose a deeper Merkle tree or smaller token slices when over-streaming is your problem, and a shallower one when memory or tree-exchange time is. A tree with 2^15 leaves takes tens of kilobytes per range; doubling the depth doubles the memory but halves the data per leaf.
Choose a leader-based system (Raft, a primary with replicas) when you do not want to operate repair at all. All writes go through one log, so replicas cannot silently diverge. You pay with write availability during a leader election and with lower write scalability, which is exactly what leaderless systems were built to avoid.
interview: Why can two replicas differ in a database that accepted every write successfully? || A write at consistency QUORUM only needs a majority to acknowledge, so the third replica can miss it (it was down, partitioned or slow). Sloppy quorums and dropped hints make this worse. The system accepted the write correctly, but the copies are now different, and a mechanism must make them converge.
Walk me through how two replicas find their differences without sending all their data. || Each builds a Merkle tree over the same key range, with each leaf hashing a fixed sub-range. They compare the roots; if they match, stop. Otherwise they compare children and descend only into subtrees whose hashes differ. At differing leaves, they exchange the actual rows and merge by timestamp or vector clock. The messages are about twice the tree depth per difference, not proportional to the number of rows.
Why is repair expensive even when the replicas are nearly identical? || Building the tree needs a hash over every row of the range, which means reading all the data from disk on each replica. The network cost is small, but the disk and CPU cost is the full data size. Persistent trees (Riak) or incremental repair reduce this.
What is a zombie row, and how do you prevent it? || A deleted row that comes back. A delete is a tombstone, which is purged after gc_grace_seconds. If a replica missed the delete and was not repaired before the purge, its old value becomes the only evidence and gets copied back. Prevention: complete a repair on every node within gc_grace_seconds, and do not lower it carelessly.
Your Cassandra cluster has 3 nodes, RF=3, and one node was down for 5 hours. What do you do when it returns? || The 3-hour hint window has passed, so hints are incomplete. Run a repair on that node (or let it stream/bootstrap fresh data) before trusting it for reads at low consistency levels. Reads at QUORUM would still be correct because read repair and the other two replicas answer.
Why not make replicas converge by always reading from all of them? || Reading all replicas on every read raises latency to the slowest node and fails when one is down, which defeats availability. It also only fixes data being read. Background anti-entropy moves the repair work off the request path and covers cold data.
quiz: What three mechanisms keep replicas converging in a Dynamo-style database, and which one covers data nobody reads? || Hinted handoff (short outages), read repair (keys that are read) and Merkle-tree anti-entropy. Only the Merkle-tree repair finds differences in data nobody reads.
Why does the comparison walk down the tree instead of comparing all leaves? || If a parent hash matches, everything beneath it is equal, so the whole subtree can be skipped. Only branches with different hashes are explored, so the work is about proportional to the number of differences times the tree depth.
Why must a Cassandra repair finish within gc_grace_seconds? || Tombstones are purged after that time. If a replica missed a delete and has not been repaired by then, the other replicas no longer remember the delete, and the old value is copied back.
A range has 1,000,000 rows and a tree of 2^15 leaves. One row differs. Roughly how many rows are streamed and how many hashes compared? || About 1,000,000 / 32,768 = roughly 30 rows are streamed (the whole leaf), and about 2 x 15 = 30 hash comparisons are made on the way down.
When would you prefer incremental repair over full repair, and what do you risk? || Prefer incremental when data is large and mostly written once, because it only hashes unrepaired data and costs far less per cycle. The risk is that mistakes in tracking "repaired" data leave real differences unnoticed, so run a full repair now and then.

@@ outbox
value: Many services must do two things after a business event: save the new state in their own database, and tell the rest of the system by sending a message, for example to Kafka. These are two different systems, and no transaction covers both. If the service saves and then crashes before sending, other services never learn about the order. If it sends first and then the save fails, other services react to something that never happened. This is the dual-write problem, and retries do not fix it, because the crash can happen between any two lines of code.
The transactional outbox removes the second write. In the same local database transaction that changes the business tables, the service inserts the event as a row in an outbox table. Either both rows commit or neither does. A separate relay then reads the outbox and publishes each row to the broker, retrying until it succeeds. Change data capture (CDC) is the clean way to build that relay: it reads the database's own commit log, so no polling query is needed and no committed row can be missed. A saga then covers the next level up: a business workflow that spans several services, each with its own database, where no single transaction exists. Each step has a compensating step that undoes it, and events drive the workflow forward or backward.
The layers below carry the weight. ACID transactions (L3) give the one guarantee the pattern needs: the state change and the event row are atomic and durable in one database. The write-ahead log (L2) is both why the database can recover to a consistent point and the source that CDC tools read to see every committed change in commit order. For the layer above, microservices (L1) get reliable event publication without distributed transactions, and durable execution engines (L1) offer the same workflow idea, sagas, as a managed service.
terms: Dual write — updating two systems (a database and a broker) in one code path, with no atomicity between them.
Outbox table — a table in the service's own database that holds events waiting to be published.
Relay (message relay) — the process that reads outbox rows and publishes them to the broker.
Change data capture (CDC) — reading a database's commit log to turn each committed change into an event.
Replication slot — a PostgreSQL object that remembers how far a CDC reader has read, so the database keeps the log until it is consumed.
Idempotent consumer — a receiver that can process the same message twice with the same result as processing it once.
Saga — a workflow made of local transactions in several services, where each step has a compensating action in case a later step fails.
Compensating action — a new business operation that semantically undoes an earlier step, such as a refund after a charge.
history: The saga idea is older than microservices. Hector Garcia-Molina and Kenneth Salem published "Sagas" at SIGMOD in 1987. They were worried about long-lived transactions in a single database: holding locks for hours blocks everyone. Their answer was to break the long transaction into a sequence of short ones, T1 ... Tn, each paired with a compensating transaction C1 ... Cn. If step k fails, the system runs C(k-1) ... C1 to reach an acceptable state. It does not restore the exact old state; it restores a state the business accepts.
The outbox pattern grew in the 2000s and early 2010s as large systems moved to message queues and later to services with one database each. Pat Helland's "Life Beyond Distributed Transactions" (2007) argued that at scale you give up distributed transactions and use entities that talk by messages, made safe by idempotence and by remembering what you have already processed. Chris Richardson's "Microservices Patterns" (2018) and his site microservices.io gave names to "Transactional outbox", "Polling publisher", "Transaction log tailing" and "Saga".
CDC tools made the log-tailing form practical. LinkedIn built Databus (2012), and Debezium, started at Red Hat by Randall Hauch in 2015, added connectors for MySQL, PostgreSQL, MongoDB and others on top of Kafka Connect. Debezium added an "outbox event router" transformation that turns outbox rows into properly keyed and routed Kafka messages. The saga side moved from hand-written code to frameworks (Eventuate, Axon) and then to workflow engines such as Temporal and AWS Step Functions, which keep the workflow state durable for you.
how: Start with the write path. The service opens a database transaction, updates its tables (for example `orders` set to PLACED), and inserts a row into `outbox` with columns such as `id`, `aggregate_type`, `aggregate_id`, `event_type`, `payload` (often JSON or Avro) and `created_at`. It commits. Because of ACID atomicity, a crash before the commit leaves neither change, and a crash after leaves both. The service never talks to Kafka in this transaction, so a broker outage cannot fail user requests.
Now the relay. There are two designs. The first is a polling publisher: a loop runs `SELECT ... FROM outbox WHERE published = false ORDER BY id LIMIT 100`, sends the rows to Kafka, waits for acknowledgement, and marks them published (or deletes them). It is simple, but it adds query load and has a subtle bug. Auto-increment ids are assigned at insert time, not commit time. Transaction A can get id 5 and commit after transaction B, which got id 6. A poller that has read up to id 6 will never see id 5. Fixes are to poll by a monotonic commit marker, to use a small delay, or to avoid polling.
The second design is log tailing with CDC. A tool such as Debezium connects to the database as a replication client. On PostgreSQL it uses logical decoding through a replication slot and a plug-in (pgoutput); on MySQL it reads the binlog in row format. The database writes every committed change to its log in commit order, which is the write-ahead log (L2) at work, and the connector turns the inserts on the outbox table into Kafka messages. Because the log is already ordered and durable, the relay needs no polling and cannot miss a committed row. It stores its position (the log sequence number or binlog offset) so that after a restart it resumes where it stopped. A neat detail: the row can be inserted and deleted in the same transaction, because the log keeps the insert. The table then stays empty, and only the log carries the events.
Delivery is at least once. The relay may publish a message, crash before saving its position, and publish it again after restart. So each message carries a unique id, and each consumer records the ids it has processed (an "inbox" table, updated in the same transaction as the consumer's own change) or makes its operation naturally idempotent, such as "set status to SHIPPED". Ordering is kept per aggregate by using the aggregate id as the Kafka message key: all events of one order go to one partition, in log order.
A saga uses this machinery to coordinate several services. In choreography, each service reacts to events and emits new ones: OrderPlaced causes the payment service to charge and emit PaymentCompleted, which causes the inventory service to reserve stock, and so on. In orchestration, a central coordinator (or a workflow engine) keeps the state machine and sends commands to each service. If a step fails, say inventory has no stock, the saga runs compensating actions in reverse order: refund the payment, cancel the order. Compensations must also be idempotent and must be retried until they succeed, because there is no one to roll back for them. Between the steps, other users can see the intermediate state: sagas lack isolation. Designers handle that with "semantic locks" (an order in state PENDING), commutative updates, or re-reading before acting.
The ordering of steps in a saga follows a simple rule. Put steps that can be compensated first, then one "pivot" step, which is the point of no return, and after it only steps that are guaranteed to succeed when retried. In an order flow, "reserve stock" and "authorize payment" can be cancelled, so they come early; "ship the parcel" cannot be cancelled by software, so it comes last. The orchestrator stores its state (which step is done, which are pending, which are compensated) in a table, written in the same transaction as the next command it puts in its own outbox. This is the outbox pattern used again: the saga's progress and the message that drives it are atomic. Each command is sent with a saga id and a step number, so a duplicate command is recognized and ignored by the participant.

example: An order service handles 500 orders per second. Each order writes one row to `orders` and one to `outbox` in one transaction. Take order 9001. The service commits at time t. CDC reads the commit from the PostgreSQL WAL within about 50 ms and writes an `OrderPlaced` message, keyed by `order-9001`, to the Kafka topic. The payment service consumes it.
Now a crash. The relay publishes the message for order 9001, then its machine dies before it records the new log position. After restart, it resumes from the last saved position and publishes order 9001 again. The payment service receives the same `event_id` twice. Its inbox table has a unique index on `event_id`. In one transaction it tries to insert the id; the second insert fails on the unique key, so the charge is skipped. The customer is charged once. Without the inbox the card would be charged twice, so at-least-once delivery requires an idempotent consumer.
Now the saga. Step 1: orders creates order 9001 in state PENDING. Step 2: payment charges 40 dollars and emits `PaymentCompleted`. Step 3: inventory finds that the item is out of stock and emits `StockRejected`. The orchestrator now runs compensations in reverse. It sends `RefundPayment` (idempotent, keyed by the payment id) and then sets the order to CANCELLED. During the few hundred milliseconds between step 2 and the refund, the customer's bank shows a pending charge, an intermediate state that a database transaction would never expose. The business accepts that, and the UI shows "processing" for the order.
Last, the operational numbers. At 500 events per second, each of about 1 KB, the outbox produces roughly 0.5 MB/s of log data. If the relay is down for one hour, the database must keep about 1.8 GB of extra WAL, because the replication slot blocks the log from being recycled. With a 100 GB disk and an unnoticed outage of two days, that is 86 GB, and the database could run out of space. So the lag of the slot must be monitored and alarmed.
intuition: Write the letter in the same notebook entry as the decision, so the postal worker who reads the notebook can never miss it.
The pattern works because it reduces a problem of two systems to a problem of one. A single database can make two changes atomically. Once the event is safely written, sending it is only a matter of retrying until it succeeds, and a retry is safe if the receiver is idempotent. The saga extends the same way: if you cannot make a long business process atomic, make every step safe to retry and give it a defined way back.
mistakes: People often think the outbox gives exactly-once delivery. In fact it gives at-least-once publication, so duplicates are normal after crashes and rebalances. Exactly-once effects come from idempotent consumers, not from the relay.
People often think a polling publisher with an auto-increment id is as correct as CDC. In fact ids are assigned before commit, so a long transaction can commit later than transactions with higher ids, and a poller can skip it for ever. Log-based CDC reads in commit order and avoids this.
People often think a saga is a distributed transaction with rollback. In fact it has no rollback and no isolation. Other readers can see the intermediate states, and a compensation is a new business action (a refund), not an erasing of the past. Some steps cannot be undone at all (an email sent), so they must go last or be designed as pivots.
People often think writing to Kafka after the database commit, with a retry, is good enough. In fact if the process dies after the commit and before the send, the event is lost with no record that it was owed. Only a durable record in the same transaction closes this gap.
People often think CDC is free. In fact an idle replication slot makes PostgreSQL keep WAL on disk without limit unless `max_slot_wal_keep_size` is set, and many outages have come from a forgotten slot.
friction: The outbox adds a table, a relay and a monitoring burden to each service. Every event is written twice (outbox row, then broker), and CDC adds latency of tens to hundreds of milliseconds. The relay is a single point to operate: if it stops, no events flow even though the database is healthy, so you must alert on lag between the commit time and the publish time.
Schema is a contract problem. If CDC publishes changes of the business tables directly, any column rename leaks into every consumer. The outbox table exists to separate the internal model from the public event, but then the team must version payloads and keep old consumers working.
Sagas are hard to reason about. The state of one business operation is spread over many services and topics, failures can occur in compensations too, and testing every failure order is difficult. Without isolation, anomalies like lost updates and dirty reads appear at the business level. Timeouts are needed for every step, because a lost message otherwise leaves a saga stuck. Debugging needs a correlation id on every event and a way to see the whole saga's state, which is a main reason teams adopt orchestrators or durable execution engines.
Ordering across aggregates is not guaranteed: events for order 1 and order 2 may be interleaved in any way across partitions. Consumers that need a global order need other designs. Finally, the outbox only helps the service that owns the database. It does not make a consumer's action on a third system atomic with its own state, so the same pattern (inbox, idempotence) is needed there.
practice: Use the outbox whenever a state change in a database must reliably cause a message. Keep the outbox row small and stable: an event id (a UUID), an aggregate id, an event type, a version, and a payload that is a public contract rather than a copy of internal tables. Use the aggregate id as the broker key for per-entity ordering.
Prefer log-based CDC (for example Debezium with its outbox event router) when you can run Kafka Connect, and the polling publisher when you cannot or the volume is low (under a few hundred events per second). If you poll, query in small batches, index the "unpublished" column, and delete or archive rows regularly, otherwise the table grows and the scan slows. For PostgreSQL, set `max_slot_wal_keep_size`, alert on slot lag, and drop slots of dead connectors. For MySQL, keep binlog retention longer than your worst relay outage.
Make every consumer idempotent. Add a processed-events table keyed by event id, updated in the same transaction as the consumer's state change, and expire old rows after your maximum redelivery window. Use natural idempotency where you can ("set X to Y" rather than "add 1 to X").
For sagas, start with the simplest form that works: orchestration with a state machine row in a table for a few steps, or a workflow engine if the flow has timers, retries and many branches. Write down the compensation for every step before coding it, put steps that cannot be undone last, give every step a timeout, and make compensations retry until they succeed. Put a saga id on every event and log line, and expose the saga's current state in an admin screen.
tradeoffs: Choose log-based CDC for the relay when you already run Kafka Connect, need low latency (tens of ms) and have high volume; choose a polling publisher when the volume is small (hundreds of events per second at most), the team has no CDC operations experience, and a delay of 1 second is fine. You give up latency and database load with polling, and simplicity with CDC.
Choose an outbox table (explicit events) over CDC on the business tables when other teams consume the events or the schema will change. You pay one more insert per transaction and some storage; you gain a stable contract. Choose raw table CDC only for internal replication to a warehouse, where the consumer wants the raw rows.
Choose orchestration over choreography when the saga has more than about three or four steps, needs timeouts, or must be visible to operators. You give up some service autonomy (the orchestrator knows the flow). Choose choreography for two or three steps where each service already reacts to events, and you want no central component.
Choose a saga over a distributed transaction (two-phase commit) when services are owned by different teams, the participants are not all XA-capable, or locks held across services would hurt availability. You give up isolation and simple rollback. Choose two-phase commit only inside one organization and one technology where blocking on a coordinator failure is acceptable.
Choose a durable execution engine (Temporal, Step Functions) over hand-written sagas when flows are long-running and have many failure paths. You give up some freedom in code structure and add a platform to operate, and you gain persisted state and retries without writing the plumbing.
interview: Explain the dual-write problem and how the outbox fixes it. || Writing to a database and a broker are two separate operations, and a crash between them leaves one done and one not. The outbox writes the event as a row in the same local transaction as the state change, so they are atomic. A relay then publishes outbox rows and retries until it succeeds, making delivery at-least-once.
Why is a polling publisher with auto-increment ids unsafe, and how would you fix it? || Ids are assigned at insert, not commit, so a transaction with a lower id can commit after one with a higher id and the poller, having moved past that id, never sees it. Fixes: use log-based CDC, which reads in commit order; or poll with a safety lag and a "not yet published" flag rather than a high-water id.
You get duplicate events downstream. Where did they come from and what do you do? || The relay is at-least-once: it can publish and crash before saving its position, and the broker or consumer may also redeliver. Make consumers idempotent with an inbox table keyed by event id, updated in the same transaction as the effect, or use naturally idempotent operations.
A Debezium connector for PostgreSQL has been down for a day and the database disk is nearly full. What happened? || The replication slot keeps WAL until the connector confirms it has read it. With the connector down, WAL piles up. Restart the connector or drop the slot if the data is not needed, then set max_slot_wal_keep_size and alert on slot lag to prevent a repeat.
How do sagas handle failure, and what do they not give you? || Each step has a compensating action, run in reverse order when a later step fails; compensations must be idempotent and retried. Sagas give eventual atomicity but no isolation: other transactions see intermediate states, so you need semantic locks like a PENDING state and careful design.
When would you use two-phase commit instead of a saga? || Inside one organization, with participants that support XA, short transactions and where a coordinator failure that blocks locks is acceptable. For cross-team services, long flows and high availability needs, a saga with outbox is the usual choice.
quiz: What problem does the transactional outbox solve? || The dual-write problem: updating a database and publishing a message so that both happen or neither does. The event is stored in the same local transaction as the state change, and published afterwards by a relay.
Why does the relay give at-least-once rather than exactly-once delivery? || It may publish a message and crash before recording that it did, so after restart it publishes the same message again. Consumers must therefore deduplicate or be idempotent.
What does CDC read, and why does that make it safe for the relay? || It reads the database's commit log (WAL or binlog), which records every committed change in commit order. So no committed outbox row can be missed and the order is kept, unlike polling by id.

An orchestrator holds the state machine in one place, handles timeouts and compensations, and can be inspected, at the cost of some coupling to the orchestrator.

@@ pbft
value: Most replicated systems in a data centre, such as Raft clusters, assume that a machine either works or crashes. They trust every message they receive. That assumption fails when a node can be hacked, when a bug corrupts its memory, or when the nodes belong to different organizations that do not trust each other. Such a node can send different answers to different peers, vote twice, or lie about what it has seen. This is called a Byzantine fault, after the Byzantine Generals problem of Lamport, Shostak and Pease (1982).
Byzantine fault tolerance (BFT) is the ability of a replicated service to keep agreeing on one sequence of operations, and to answer clients correctly, even when up to f of its replicas behave arbitrarily. Practical BFT, or PBFT (Castro and Liskov, 1999), showed that this can be done on an ordinary network that may delay and lose messages, and at a speed close to an unreplicated server. It needs n = 3f + 1 replicas to tolerate f faulty ones: four replicas for one traitor, seven for two. Crash-fault protocols such as Raft need only 2f + 1.
The layers below give the exact reason for these numbers. Distributed systems theory (L3) supplies the failure model (arbitrary faults), the network model (partial synchrony, because no deterministic protocol can guarantee both safety and liveness in a fully asynchronous system, the FLP result) and the notion of a state machine replicated by agreeing on an operation log. Combinatorics (L4) supplies the counting argument: with 3f + 1 replicas, any two groups of 2f + 1 overlap in at least f + 1 replicas, and at least one of those is honest. For the layer above, blockchains (L1) use descendants of PBFT (Tendermint, HotStuff and its variants) to give transactions final, irreversible confirmation when the set of validators is known.
terms: Byzantine fault — a fault in which a node may behave in any way, including lying, sending conflicting messages and colluding with other faulty nodes.
Replica — one server that holds a copy of the service state and runs the protocol.
f — the maximum number of faulty replicas the system must tolerate; n = 3f + 1 is the number of replicas.
Quorum — a group of replicas large enough that any two such groups overlap; in PBFT it has 2f + 1 members.
Primary — the replica in the current view that assigns a sequence number to each client request; the others are backups.
View — a period during which one replica is primary; a view change replaces a primary that is slow or faulty.
Partial synchrony — the model in which the network may behave badly for a while but eventually delivers messages within some unknown bound; it is the model in which PBFT stays live.
Equivocation — sending different messages to different peers for the same step, the main trick of a Byzantine node.
history: Leslie Lamport, Robert Shostak and Marshall Pease introduced the problem in "Reaching Agreement in the Presence of Faults" (1980) and told it as a story in "The Byzantine Generals Problem" (1982). Generals camp around a city and must agree on attack or retreat by messengers, but some generals are traitors. They proved that with oral (unsigned) messages, agreement needs more than two thirds of the generals to be loyal: \( n \ge 3f + 1 \). With unforgeable signatures, their second protocol can tolerate any number of traitors, but only in a synchronous system with bounded message delays.
For almost twenty years this stayed mostly theory. The known algorithms needed synchronous networks, exchanged huge numbers of messages, or used expensive public-key signatures on every message. Fischer, Lynch and Paterson (1985) also proved that no deterministic protocol can guarantee agreement in a fully asynchronous network if even one node can crash. Dwork, Lynch and Stockmeyer (1988) showed the way out: partial synchrony, where safety never depends on timing and liveness depends on timing only eventually.
Miguel Castro and Barbara Liskov at MIT published "Practical Byzantine Fault Tolerance" at OSDI in 1999. Their key moves were to keep safety independent of timing, to use fast message authentication codes (MACs) for the normal case instead of signatures, and to cut the number of message steps to three. They built a replicated NFS file service, BFS, which was only about 3% slower than standard unreplicated NFS in their tests. A 2002 follow-up (Castro and Liskov, TOCS) added proactive recovery.
Interest returned with blockchains. Tendermint (Kwon, 2014; Buchman, Kwon and Milosevic, 2018) adapted PBFT to a chain of blocks with rotating proposers. HotStuff (Yin, Malkhi, Reiter, Gueta and Abraham, PODC 2019) made the leader's communication linear in n, and was the base of Facebook's Libra/Diem consensus. Ethereum's Casper FFG (2017) uses a similar two-thirds vote for finality. Today, nearly every proof-of-stake chain and many permissioned ledgers run a descendant of PBFT.
how: PBFT runs a replicated state machine. All n = 3f + 1 replicas start in the same state, execute the same operations in the same order, and so stay identical, provided they agree on the order. One replica is the primary of the current view (for view v it is replica v mod n). It orders requests. The other replicas are backups, who check the primary rather than trust it.
Normal case, in five steps. First, the client sends its request to the primary. Second, in the pre-prepare phase, the primary assigns a sequence number s and sends (view, s, request digest) to all backups. Third, in the prepare phase, each backup that accepts the proposal (it checks the view, that it has not accepted a different request for the same view and s, and the digest) sends a prepare message to all other replicas. A replica becomes "prepared" for (v, s, request) when it holds the pre-prepare and 2f matching prepares from different replicas. At that point, a quorum of at least 2f + 1 replicas (counting the primary) agrees on which request has number s in view v. Fourth, in the commit phase, a prepared replica sends a commit message to all. When it has 2f + 1 matching commits (its own included), it is "committed-local" and executes the request after all lower sequence numbers. Fifth, each replica sends its reply to the client, which waits for f + 1 identical replies from different replicas. Since at most f are faulty, at least one of those f + 1 is honest, so the answer is correct.
Why 3f + 1, and why two phases of voting? The counting argument comes from combinatorics (L4). A request needs to be acknowledged by 2f + 1 replicas. Among them, f may be faulty and f + 1 honest. Why can we not wait for more? Because f replicas may never answer, so the most we can wait for without risking liveness is n − f = 2f + 1. Why is 2f + 1 enough for safety? Two quorums of 2f + 1 out of 3f + 1 share at least 2(2f + 1) − (3f + 1) = f + 1 members. At most f of them are faulty, so at least one honest replica is in both. That honest replica never signs two different requests for the same view and sequence number, so two conflicting requests cannot both be prepared. The prepare phase thus guarantees that within one view, replicas agree on the order. The commit phase guarantees the result survives a view change: a replica commits only when it knows that 2f + 1 replicas are prepared, so any later view will find evidence of the request among its own quorum.
View change. Each backup starts a timer when it receives a request. If the request is not executed before the timer fires, the backup suspects the primary and moves to view v + 1: it stops accepting messages for view v and sends a view-change message containing its prepared requests (with proof) and its last stable checkpoint. The new primary, replica (v + 1) mod n, waits for 2f + 1 view-change messages, then computes which sequence numbers were prepared in earlier views and re-proposes them with a new-view message. This is where signatures are used, since these messages must be forwarded and checked by third parties. Backups also double the timer for each successive view change, so that after a period of bad network the system eventually finds a view with a working primary, which gives liveness under partial synchrony.
Checkpoints and garbage collection. The log cannot grow without limit, so every K requests (for example, 100) replicas compute a digest of their state and broadcast it. When 2f + 1 replicas have the same digest, the checkpoint is stable, and older messages may be discarded. A slow or recovering replica fetches state from others and verifies it by the digest.
The cost: each of the prepare and commit phases is an all-to-all exchange, so one request costs about \( 2n^2 \) messages. That is why PBFT works well for 4 to about 20 replicas but badly for hundreds. HotStuff reduces this by routing votes through the leader and having it broadcast a combined certificate, so the cost is linear, at the price of an extra phase and of the leader being the bandwidth bottleneck. Tendermint takes a related approach with rotating leaders.

example: Take n = 4 replicas, so f = 1: R0 (primary), R1, R2 and R3. Suppose R3 is Byzantine. A client sends the request "transfer 10 from A to B".
R0 gives it sequence number 7 in view 0 and sends PRE-PREPARE(0, 7, digest d) to R1, R2 and R3. Each backup checks the message and broadcasts PREPARE(0, 7, d). R3 is faulty and broadcasts a PREPARE with a wrong digest d' instead. Now count at R1. It holds the pre-prepare, its own prepare for d, and the prepare for d from R2. That is 2f = 2 matching prepares, so R1 is prepared. R3's wrong prepare does not match and is ignored. R2 is prepared in the same way. R0 does not send a prepare (its pre-prepare counts), but it receives matching prepares from R1 and R2, so it is prepared too.
The three prepared replicas broadcast COMMIT(0, 7, d). Each of R0, R1 and R2 now holds 3 matching commits, which is 2f + 1, so each executes the transfer and replies to the client. R3 replies "transfer 1000". The client needs f + 1 = 2 identical replies. It gets three for "transfer 10" and one for "transfer 1000", and accepts the first. One liar changed nothing.
Now suppose the primary R0 is the Byzantine one. It sends digest d to R1 and R2 and digest d' to R3. R1 and R2 prepare for d and match each other, so both become prepared for d. R3 holds a pre-prepare for d' but sees prepares for d, so it never becomes prepared. R0 may now withhold its commit, so only R1 and R2 send commits and nobody reaches 3. The request stalls. The backups' timers fire and they start a view change to view 1 with primary R1. Their view-change messages carry the proof that R1 and R2 prepared d at number 7. The new primary must re-propose d at number 7, since the 2f + 1 = 3 view-change messages it collects must include at least one of those two honest replicas (3 + 2 > 4). No replica ever executes d' at sequence 7. Safety held, and liveness returned through the view change.
Message count: for n = 4, one request costs 1 (request) + 3 (pre-prepare) + 3 × 3 = 9 (prepare) + 4 × 3 = 12 (commit) + 4 (reply) = 29 messages. For n = 100, the prepare and commit phases alone cost about 2 × 100 × 99 ≈ 19,800 messages.
intuition: Generals who might include traitors can still agree, if each one waits to hear that two thirds of the group saw the same order.
The design is natural once you see what a liar can do: tell different people different things. The only defence is to ask others what they were told, which is why the prepare phase is all-to-all. A traitor cannot fool everyone if each honest replica acts only after enough others confirm the same thing. The numbers come from counting: you can wait only for \( n - f \) answers, because f may stay silent; and among those answers up to f may be lies, so you need the honest majority inside the quorum to outvote them. Solving \( n - f \ge 2f + 1 \) gives \( n = 3f + 1 \).
mistakes: People often think BFT needs only a simple majority. In fact a majority of 2f + 1 out of 2f + 1 is not enough, because a liar can be counted in two different majorities and tell each a different story. The extra f replicas buy the guarantee that any two quorums share an honest member.
People often think BFT protects against bugs that every replica shares. In fact all replicas run the same code, so a bug that exists in all of them fails all of them together. BFT protects only against independent faults. Real deployments use different implementations or different operating systems to reduce common faults, which is expensive.
People often think PBFT solves the Sybil problem and works with open membership. In fact PBFT needs a fixed, known set of n replicas, since a quorum counts identities. If an attacker can create many identities, it passes the one third limit with ease. Open networks need a way to make identities costly, such as proof of work or proof of stake.
People often think a Byzantine protocol with signatures needs fewer replicas, so \( 2f + 1 \) is possible. In fact signatures help only in the synchronous model. In the partially synchronous model that real networks need, the lower bound for agreement is still \( n \ge 3f + 1 \), with or without signatures.
People often think that PBFT is always much slower than Raft. In fact in the 1999 tests the replicated file service was close to the plain one, because MACs are cheap and the extra message rounds were on a fast local network. The real difference is message count growing as \( n^2 \) and the larger n.
friction: The quadratic message pattern limits the group size. PBFT-style protocols are comfortable with 4 to 20 replicas and become costly beyond a few dozen, which is why blockchains with hundreds of validators use linear variants (HotStuff), aggregate signatures, or committees sampled from a larger set.
The one-third threshold is a hard line. With 3f + 1 replicas, if f + 1 are faulty, safety may be lost. For a proof-of-stake chain this threshold is counted in stake, not machines, so a group holding a third of the stake can stop the chain, and one holding two thirds can rewrite it. Operators must also avoid shared failure causes: if several validators run on one cloud provider or one software version, they are not independent.
Liveness depends on timers. Setting them too short causes needless view changes; too long, and a faulty primary stalls the system. A malicious primary can delay requests up to just under the timeout, slowing the service without being removed. Later protocols (Aardvark, 2009; Prime, 2008; RBFT) were designed to bound the damage of such performance attacks.
Operational cost: you need 3f + 1 machines, key management, and protection of keys; recovery of a replica that lost state needs state transfer from others with verification; and reconfiguring the membership is hard. And most data-centre services do not face malicious replicas, so they take the cheaper 2f + 1 crash model, and handle corruption by checksums and signed data. BFT tends to appear where the operators are independent: blockchains, cross-organization ledgers, and some safety-critical systems such as aircraft control and space systems.
practice: Choose the failure model first. If all nodes are run by one team, in one trust domain, use Raft or Paxos with checksums, and encrypt and authenticate traffic. Use BFT only if nodes are run by parties who do not fully trust each other, or if the cost of a compromised node is catastrophic.
If you need BFT, do not write your own protocol. Use a mature implementation such as CometBFT (the Tendermint successor in the Cosmos ecosystem), a HotStuff-family library from a production chain, or the BFT ordering service in your ledger platform. Plan membership carefully: choose n = 3f + 1 for the failures you must survive (4 for one, 7 for two, 10 for three), spread the nodes across operators, clouds and implementations, and keep the keys in hardware security modules.
Test with faults on purpose. Simulate equivocating, silent and slow nodes, partitions, and primaries that delay messages. Deterministic simulation (see the neighbouring concept) is a good way to explore these cases. Monitor the view-change rate, the commit latency percentiles and the number of nodes lagging: frequent view changes mean a bad primary or a bad network.
To study the topic, read the PBFT paper, then the Castro thesis for details, then the HotStuff paper to see how linear communication is obtained. Work the n = 4 example by hand, including a Byzantine primary. Then compare with Raft: list what each Raft step trusts and see which of those trusts PBFT must replace with a vote.
tradeoffs: Choose crash-fault consensus (Raft, Paxos, \( 2f + 1 \) replicas) when all nodes are in one trust domain, such as a database cluster you operate. Choose BFT (\( 3f + 1 \) replicas) when nodes belong to different organizations or a compromised node is a real threat. BFT costs you 50% more machines for the same f (4 instead of 3 for f = 1), more messages (\( n^2 \) against n), and signature or MAC verification on every message.
Choose PBFT-style all-to-all voting for small groups (up to about 20) where latency matters: it commits in three message delays and has no single bandwidth bottleneck. Choose HotStuff-style linear voting when n is in the hundreds: the leader sends and receives O(n) messages, but each decision takes more phases (often 3 rounds plus pipelining), and the leader's bandwidth becomes the limit.
Choose BFT with a fixed validator set (permissioned, or proof of stake with known validators) when you want fast, final confirmation in seconds. Choose proof of work when membership must be open and anonymous and you can accept probabilistic finality (about an hour for Bitcoin's six blocks) and large energy use.
Choose MACs for the normal path when you want speed, because they are orders of magnitude cheaper to compute than public-key signatures. Choose signatures when messages must be forwarded and proven to third parties, as in view changes and in blockchains, where a vote must be verifiable by anyone. Aggregate signatures (BLS) let you combine hundreds of votes into one, at a higher computation cost.
interview: Why does BFT need \( 3f + 1 \) replicas when crash-fault consensus needs only \( 2f + 1 \)? || A crash-faulty node is silent but never lies, so a majority of \( 2f + 1 \) overlaps in a correct node. A Byzantine node can also vote for conflicting values. Because up to f replicas may not answer, a quorum can only be \( n - f \). It must also contain \( f + 1 \) honest members to outvote f liars, and overlap with any other quorum in at least one honest node, which gives \( n - f \ge 2f + 1 \), or \( n \ge 3f + 1 \).
Walk through the three phases of PBFT and say what each one guarantees. || Pre-prepare: the primary proposes an order for a request. Prepare: replicas broadcast that they accepted it; 2f matching prepares plus the pre-prepare make a request prepared, so within a view no two requests can share a sequence number. Commit: replicas broadcast that they are prepared; 2f + 1 commits make it committed, which guarantees that the request survives a view change.
What happens if the primary is faulty and how does the system recover? || A faulty primary might send conflicting proposals or nothing. Backups time out, stop accepting messages for the old view and send view-change messages with proof of what they prepared. The new primary collects 2f + 1 of them, re-proposes the prepared requests and starts the new view. Timers grow with each failed view change to ensure eventual liveness.
What are PBFT's scaling limits and how do modern protocols address them? || Prepare and commit are all-to-all, so messages grow as \( n^2 \). It works for a few to a few dozen replicas. HotStuff routes votes through the leader and uses threshold or aggregate signatures to get linear communication, and pipelines phases; Tendermint-style rotating leaders spread the load. Sharding or committees reduce n per decision.
Why can't Raft simply be used in a blockchain with mutually distrusting validators? || Raft trusts that the leader and followers follow the protocol. A malicious leader could send different entries to different followers or fake a quorum; a malicious follower could claim to have entries it lacks. Without signatures and 2f + 1 votes from n = 3f + 1, safety fails.
How does BFT relate to proof of work, and why not use PBFT for Bitcoin? || PBFT needs a fixed known membership to count quorums, and is limited to small n. Bitcoin has open membership, so identities are free to forge; proof of work ties voting power to computation instead of identities and scales to thousands of nodes, but gives only probabilistic finality.
quiz: How many replicas does PBFT need to tolerate 2 Byzantine replicas, and what quorum size is used? || n = 3 × 2 + 1 = 7 replicas; quorums of 2f + 1 = 5.

value: Classical Byzantine agreement (the previous concept) counts votes from a fixed, known list of replicas. That is useless on the open internet, where anyone can start a million fake identities for free. This attack is called a Sybil attack. If voting power is "one identity, one vote", an attacker simply makes more identities than there are honest users.
Proof of work (PoW) and proof of stake (PoS) fix this by tying voting power to something that cannot be forged cheaply. In PoW, the scarce thing is computation: to add a block, you must find a number that makes the block's hash small, which takes a huge number of attempts, and the chain with the most accumulated work wins. In PoS, the scarce thing is money held at risk: validators lock up coins, are chosen to propose and vote on blocks in proportion to their stake, and lose part of it if they cheat. In both, rewriting history costs real resources, so an attack is expensive, and honest behaviour is the profitable choice.
The layers below supply the machinery. Cryptographic hash functions (L3) make the puzzle: a hash cannot be reversed or shortcut, so the only way to find a good one is brute force, and anybody can verify the answer with a single hash. Probability (L4) explains why finding a block is a lottery where your chance equals your share of the total power, and why the chance of rewriting k confirmed blocks falls exponentially. Game theory (L4) is the reason the design holds: rewards and penalties are set so that following the rules pays more than attacking. For the layers above, Bitcoin and Ethereum (L0) are the two big deployments, and blockchains (L1) in general use one of these two ways of picking who may write the next block.
terms: Sybil attack — creating many fake identities to gain more influence than you deserve in a system that counts identities.
Nonce — a number that the miner changes on each attempt so that the block hash changes.
Target (difficulty) — the threshold below which a block hash must fall; the smaller it is, the more attempts are needed.
Cumulative work — the sum of the expected work behind every block in a chain; nodes follow the chain with the most.
Confirmation — one more block built on top of a transaction's block; each makes reversal harder.
Validator — in proof of stake, a participant who has locked up coins and can propose and vote on blocks.
Slashing — the destruction of part of a validator's stake as a penalty for provably breaking the rules.
Finality — the point after which a block cannot be reverted unless a large part of the stake is destroyed (PoS) or, in PoW, becomes practically irreversible with growing probability.
history: The idea of a costly puzzle comes from fighting spam. Cynthia Dwork and Moni Naor proposed in 1992 that an email sender should compute a moderately hard function for each message, so that bulk spam becomes expensive. Adam Back's Hashcash (1997, described fully in 2002) used partial hash collisions as the puzzle. Hal Finney's reusable proofs of work (2004) and the b-money and bit gold proposals of Wei Dai and Nick Szabo tried to make such work into money, but none solved double spending without a trusted party.
Satoshi Nakamoto's Bitcoin paper (October 2008) combined four things: a hash-linked chain of blocks, Hashcash-style puzzles to choose who writes the next block, the rule "follow the chain with the most work", and a block reward that pays miners in the new currency. The network started in January 2009. It solved a problem that PBFT could not: agreement in a network with unknown, changing, anonymous participants. John Douceur had named the Sybil problem in 2002 and claimed it could not be solved without a central authority. Proof of work solves it economically, not by identity.
Problems appeared quickly. Miners moved from CPUs to GPUs, then to custom chips (ASICs) from 2013, and to pools that share rewards. Eyal and Sirer (2014) showed "selfish mining": a miner holding well under half of the power can gain extra reward by hiding blocks. Energy use grew to the scale of a medium country.
Proof of stake was suggested on the Bitcoin forum in 2011, and Peercoin (2012) shipped a first version. Ouroboros (Kiayias and others, 2017) gave the first provably secure design, Algorand (Gilad and others, 2016–2017) used random committees, and Ethereum's Casper FFG (Buterin and Griffith, 2017) combined stake with PBFT-style voting. Ethereum switched from PoW to PoS on 15 September 2022 ("the Merge"), cutting its energy use by about 99.9%, according to the Ethereum Foundation.
how: Proof of work, step by step. A miner collects pending transactions and builds a block header. The header contains the hash of the previous block, a Merkle root (a hash summary) of the transactions, a timestamp, the target and a nonce. The miner computes SHA-256 twice over the header and reads the result as a 256-bit number. If the number is below the target, the block is valid. If not, the miner changes the nonce and tries again. A good hash behaves like a random number, so each attempt succeeds with probability target / 2^256, independent of all previous attempts. There is no shortcut except trying. Verification costs one hash, so every node can check a block in microseconds.
The network keeps the average block time near 10 minutes with a feedback rule. Every 2,016 blocks (about two weeks), nodes compare the real time taken with the intended two weeks and scale the target by that ratio (limited to a factor of 4). If miners join and total hash power doubles, blocks come twice as fast until the next adjustment, then difficulty doubles.
Fork choice: each node follows the valid chain with the most cumulative work (not simply the longest). If two miners find a block at almost the same moment, the network briefly has two tips. The next block makes one chain heavier, and the other is dropped (its transactions return to the pool). So a transaction is never final in a mathematical sense; it becomes less and less likely to be reversed. With an attacker who controls a share q of the hash power, and honest share \( p = 1 - q \), the chance that the attacker ever catches up from z blocks behind falls as \( (q/p)^z \) when \( q < p \). Nakamoto's more careful calculation gives, for q = 0.1 and z = 6 confirmations, about 0.024%. For q = 0.3, it is 13% at z = 6 and about 4% at z = 10. At \( q \ge 0.5 \), the attacker catches up with certainty, which is why this is called the 51% attack.
Incentives: the first miner to find a block gets a block subsidy (3.125 BTC after the April 2024 halving; it halves every 210,000 blocks) plus transaction fees. Costs are hardware and electricity. A rational miner follows the rules, because a block that other nodes reject earns nothing, and an attack that rewrites history would also destroy the value of the coins the attacker is rewarded in. This is the game-theory (L4) argument.
Proof of stake, step by step (Ethereum as the example). To join, a validator deposits 32 ETH into a contract (since 2025 up to 2,048 ETH may be held by one validator). Time is divided into slots of 12 seconds, and 32 slots form an epoch (6.4 minutes). For each slot, a pseudo-random process (RANDAO) picks one validator to propose a block, and chooses committees of other validators to attest (vote) on it. The chance to be picked is proportional to stake. The fork-choice rule (LMD-GHOST) follows the branch with the most recent attestations. Finality comes from Casper FFG: in each epoch validators vote to link a checkpoint to the next one; when two thirds of the total stake votes for a link, the checkpoint is "justified", and once the next one is justified too, the first is "finalized". That takes about two epochs, roughly 13 minutes.
The safety of PoS comes from slashing, not from burnt energy. Two provable offences are punished: voting for two different blocks in the same slot, and "surround" votes that contradict earlier votes. The evidence is published on-chain, a slasher takes a reward, and the offender loses at least part of the 32 ETH and is ejected. To make two conflicting checkpoints final, an attacker needs two thirds of the stake to vote for both, so at least one third of the stake must break the slashing rules and be destroyed. This is called accountable safety. If more than a third of validators go offline, the "inactivity leak" slowly drains their stake until the remaining two thirds can finalize again.
PoS has its own attacks, which the design answers. "Nothing at stake": voting on every fork is free, unless double votes are slashed. "Long-range attack": someone buys old keys cheaply and rewrites history from far back; clients defend with weak subjectivity, trusting a recent checkpoint obtained from a trusted source when they first sync.

example: First, why solo mining is hopeless. Suppose the whole network does about 10^20 hashes per second (a round figure; it has been of this order in recent years) and a block is found every 600 seconds on average. A miner with a fast graphics card or older chip at 1 GH/s (10^9 hashes per second) has a share of 10^9 / 10^20 = 10^-11. Its expected time to find a block is 600 s / 10^-11 = 6 x 10^13 seconds, which is about 1.9 million years. This is why miners join pools and are paid for partial work in proportion to their hash rate: the same expected income, with a small steady stream instead of a lottery.
Second, a toy puzzle. Let the target be "the first 16 bits of the hash are zero", so each attempt succeeds with probability 1/65,536. On average a miner needs 65,536 attempts. At 1,000 attempts per second this takes about 65 seconds, but in a given run the time varies a lot (the time is roughly exponential, so there is a 37% chance it takes longer than the average). Adding one more zero bit halves the success chance and doubles the expected work. Bitcoin's real target needs roughly 2^76 attempts per block, 2^60 times more than the toy.
Third, the double-spend race. An attacker holding q = 30% of the hash power pays a merchant, waits for z = 6 confirmations, receives the goods, and then tries to rewrite the chain with a secret fork that excludes the payment. While the honest network found 6 blocks, the attacker found some number k by chance. From there, the attacker needs to catch up: from d blocks behind, the chance is (0.3/0.7)^d. Summing over the possible k gives the 13% in the earlier table. With q = 10%, the same attack succeeds in about 0.024% of tries. The merchant therefore waits for more confirmations for larger payments: the cost of waiting grows linearly, while the risk falls exponentially.
Fourth, the cost of a PoS attack. Suppose a chain has 30 million ETH staked. To finalize two conflicting blocks, an attacker would need to control two thirds of it for both votes, and at least one third (10 million ETH) must sign contradicting votes. All of that part is slashable. At a price of 2,000 dollars per ETH (an assumed figure for illustration), the attack costs at least 20 billion dollars in destroyed stake, with no hardware to resell. A PoW attacker would need to rent or buy more than half of the hash power, but could in principle reuse the hardware afterwards.
intuition: Voting rights by burnt electricity (work) or by money put at risk (stake), so fake identities gain nothing.
The idea is natural once you ask what cannot be faked on the internet. Names and IP addresses cost nothing. Computation and money do cost something, and everyone can check that they were spent. By making the right to write a block depend on one of these, the number of identities no longer matters, only the total resources behind them. Work is proved by a hash anyone can recompute, and stake is proved by a record in the ledger itself. Then the rules make cheating a loss: either it wastes the work, or it burns the stake.
mistakes: People often think miners solve a complicated mathematical problem. In fact the puzzle is plain brute force: change a number, hash, compare. It has no value except as proof that the work was done. The "difficulty" is only how small the target is.
People often think that the longest chain wins. In fact nodes follow the chain with the most cumulative work. A shorter chain with harder blocks beats a longer chain of easy blocks, which matters when difficulty changes.
People often think a transaction in Bitcoin is final after one confirmation. In fact finality is only probabilistic: each extra block lowers the reversal chance exponentially, and the number of confirmations you need depends on the value at risk and the attacker's possible share. Exchanges use from 3 to 100 or more depending on the chain.
People often think proof of stake means the rich control everything and nothing is at risk. In fact stake is at risk: slashing destroys it, and an attacker would need a third of all stake (to break finality) or more, which also destroys the value of what they hold. But concentration is a real concern: pools and exchanges that hold large shares of stake are points of influence.
People often think PoW and PoS agree on one history in the way PBFT does. In fact PoW has no fixed set of voters and gives only eventual agreement, while PoS chains such as Ethereum combine a stake-weighted voting set with PBFT-like finality. They are cousins of PBFT, using cost to decide who the voters are.
friction: Proof of work spends energy as its security budget. Estimates for Bitcoin are of the order of 100 to 200 terawatt-hours a year, similar to a medium-sized country. This is not an accident: security equals what an attacker would have to spend, so it cannot fall without the chain becoming cheaper to attack. As the block subsidy halves every four years, fees must pay for security, and whether they will is an open question. PoW throughput is low (Bitcoin about 7 transactions per second, a block every 10 minutes), and small PoW chains with rentable hash power have suffered real 51% attacks (for example Ethereum Classic in 2019 and 2020).
Mining concentrates in pools and in the places with cheap power, and ASIC production is held by a few firms. A few pools often control a large share of the hash rate, although individual miners can switch pools.
Proof of stake removes the energy cost but brings other problems. Wealth earns more stake, so there is a tendency toward concentration, and staking services (liquid staking) can hold a large share of the network. Safety depends on social agreement about checkpoints for new nodes (weak subjectivity). Protocols are more complex, with many edge cases (reorg attacks, MEV, validator key management). Penalties for software bugs can slash honest validators. Finality can stall if over a third of stake is offline or split. And in both systems, there is a trade-off between decentralization, security and throughput that remains open.
practice: As an engineer you rarely write the consensus layer, but you must understand it to integrate with it. Treat on-chain data as probabilistic until final. For a PoW chain, decide the confirmation depth from the value at risk: a small payment may accept 1 to 3 blocks, a large transfer 6 or more. For Ethereum, use the "finalized" block tag (about 13 minutes) for anything you cannot reverse, and "safe" or "latest" only for low-risk reads. Be ready for reorganizations: keep your own database keyed by block hash, and roll back and replay when the chain reorganizes.
If you run validators, protect the signing keys; never run the same key on two machines, because the double vote is slashable. Use a client diversity strategy (more than one execution and consensus client) so a bug in one does not slash you, and monitor attestation performance and missed slots.
When you design a system, ask what the participants are. If membership is known and small, use classical BFT or a crash-fault protocol; it is faster, final and uses less energy. Use PoW or PoS only when membership is open and no one is trusted.
To study the topic, read the Bitcoin paper (nine pages), then the textbook by Narayanan and others, which has the full incentive analysis; for PoS, read the Ethereum proof-of-stake documentation and the Gasper paper (Buterin and others, 2020) that describes combining Casper FFG with LMD-GHOST. Try the probability calculation for the attacker's catch-up yourself with a short script.
tradeoffs: Choose proof of work when you want the simplest security argument and a chain that anyone can join without holding any coins, and you can pay for the security with energy and accept slow, probabilistic finality (about an hour for six Bitcoin blocks). You give up energy efficiency, throughput and fast confirmation.
Choose proof of stake when you want fast finality (Ethereum about 13 minutes, other chains seconds), low energy use (about 99.9% less) and punishments you can prove. You give up the simple "nothing but a hash" trust model: you need a way for new nodes to find a recent trusted checkpoint, a more complicated protocol, and you accept that the early distribution of coins decides who holds the stake.
Choose classical BFT with a known validator set when participants are known organizations. It gives instant finality and thousands of transactions per second at small n, but is limited to a few dozen to a few hundred nodes and needs an admission process. Choose PoW or PoS only when you need open membership.
Choose a large number of confirmations when the payment is large or the chain is small. A chain with 1% of Bitcoin's hash power can be attacked by renting power for hours, so its exchanges ask for hundreds of confirmations. Choose few confirmations only for low-value payments on a chain with a large hash rate.
Choose to rely on a layer-2 or a centralized database when you need thousands of transactions per second at low fee. You give up the direct security guarantee of the base chain, or in the second case decentralization altogether.

value: The worst bugs in distributed systems appear only when several unlikely events line up: a node crashes during a disk flush, a message is delayed behind a newer one, and a timeout fires at the wrong moment. Ordinary tests almost never produce these orderings. When production does produce one, the log is incomplete, the timing is gone, and the bug cannot be reproduced. Teams then spend weeks guessing.
Deterministic simulation testing (DST) attacks the problem at its root. The whole system, with every node, the network and the disks, runs inside one single-threaded program. Every source of randomness and timing (the clock, the random number generator, thread scheduling, message delivery, disk behaviour) is replaced by a simulated version driven by one seed number. A test is a seed. The simulator injects crashes, slow disks, dropped and reordered messages and partitions, runs a workload, and checks invariants such as "no acknowledged write is ever lost". If an invariant breaks, the seed is the bug report: the same seed replays the exact same events, as often as you like, in a debugger.
Three ideas from lower layers make this work. Distributed systems theory (L3) says what to simulate: the failure model of crashes, message delay, loss, duplication and partitions, and the invariants (safety properties) that must hold in every execution. Monte Carlo methods (L4) say why random schedules are enough: if a bug appears with probability p in one random run, then N independent runs find it with probability 1 − (1 − p)^N, and you can buy N cheaply. For the layer above, FoundationDB and TigerBeetle (L0), distributed SQL databases (L1) and CI/CD pipelines (L1) use it to find bugs that unit tests, integration tests and even chaos testing in real time do not.
terms: Seed — the number that initializes the random generator; with the same code and seed, a simulation replays exactly.
Determinism — the property that the same inputs always produce the same sequence of events and outputs.
Simulated time — a virtual clock that jumps to the next scheduled event, so hours of system time pass in seconds.
Fault injection — deliberately causing failures (crashes, slow or corrupt disks, lost or delayed messages, partitions) during a test.
Invariant — a rule that must be true at all times or at the end (for example, "reads never see an older value after a newer one").
BUGGIFY — FoundationDB's macro that, only in simulation, makes code take unlikely paths such as extra delays, small buffers or injected errors.
Workload — the random mix of client operations that the simulator runs against the system.
Deterministic hypervisor — a virtual machine monitor that makes any software deterministic by controlling all its sources of non-determinism; the basis of Antithesis.
history: The idea has roots in model checking and in older work on record-and-replay debugging, but its modern form comes from FoundationDB, a distributed transactional key-value database started around 2009–2010. The founders decided to build the test system before the database. They first wrote a deterministic simulator in which a whole cluster runs in a single thread, then wrote the database to run inside it. To do that they built Flow, a C++ extension that adds actors and futures (a form of cooperative multitasking) and compiles to ordinary C++. All network and disk calls go through interfaces that have a real version and a simulated one.
Will Wilson presented the method at Strange Loop in 2014 in the talk "Testing Distributed Systems w/ Deterministic Simulation". FoundationDB was acquired by Apple in 2015, taken off the market, and open-sourced in 2018. The 2021 SIGMOD paper "FoundationDB: A Distributed Unbundled Transactional Key Value Store" describes simulation as the reason the team could add features fast with few production bugs. Its former engineers have said that customers reported very few bugs over its history.
Others had been working from the other side, with real-time fault injection. Netflix's Chaos Monkey (2011) killed instances in production. Kyle Kingsbury's Jepsen (from 2013) tests real databases on real machines with real partitions and checks the recorded histories. These tools find real bugs, but they are not repeatable, and they are slow, since a test takes real time.
After 2018 the method spread. TigerBeetle, a financial database written in Zig, built the VOPR (Viewstamped Operation Replicator), a simulator that runs the whole cluster with injected disk and network faults, and runs it on many cores continuously. Will Wilson and other former FoundationDB engineers later founded Antithesis. It runs unmodified software inside a deterministic hypervisor, so teams do not have to redesign their code. In Rust, libraries such as madsim and Tokio's turmoil offer simulated networks and time. Amazon, Dropbox and others have described using simulation or model-based tests for storage systems.
how: First, remove all non-determinism from the program. A normal program depends on many hidden inputs: the wall-clock time, random numbers, the order in which threads run, the arrival order of network packets, disk latency, memory addresses (when a hash map is ordered by pointer) and the iteration order of unordered collections. To make a run repeatable, each of these must be either removed or controlled by the seed. The system is therefore written against interfaces: `now()`, `random()`, `send(msg)`, `read(file)`, `write(file)`. In production they call the operating system. In simulation they call the simulator. The simulator runs everything in a single thread with cooperative scheduling, so there is no race that depends on the CPU's timing. The scheduler picks the next task using the seeded random generator.
Second, simulate the world. A simulated network keeps a queue of messages, each with a delivery time chosen from a distribution; it may drop, duplicate, delay or reorder them, and it can cut links between groups of machines (a partition) or clog a link for a while. A simulated disk can be slow, can fail a write, can lose data that was not flushed (to model a power cut), or can return corrupted bytes. A simulated machine can be killed and restarted, keeping only what it had flushed to disk. Time is virtual: when every task is waiting, the simulator advances the clock straight to the next scheduled event. A cluster that sits idle for ten simulated minutes finishes that wait in microseconds, so the simulator can run many hours of system time per second of real time.
Third, run a workload and check invariants. A workload generator issues random client operations (reads, writes, transactions) while a "chaos" component injects faults at random moments. Checkers run during and after the test. For a database these include: committed data is never lost, transactions are serializable (a checker looks at the history), replicas converge, and the system recovers and makes progress once faults stop (a liveness check). Each check is an executable form of the invariants from distributed systems theory. Assertions inside the code also fire when internal states are impossible.
Fourth, make rare paths common. FoundationDB's BUGGIFY macro marks places in the code where a rare thing may happen: a very small buffer, a long delay, a forced error return, a skipped optimization. In production the macro does nothing. In simulation, each BUGGIFY site is randomly enabled for a whole run, with a small probability, so some runs have a very different "personality" from others. This is related to swarm testing (Groce and others, 2012): turn random features on and off per run, because a mix of all features at once often hides bugs that a subset exposes.
Fifth, search the seed space. Each run is cheap, so a cluster of machines runs millions of seeds per night, with the system version under test. This is the Monte Carlo step (L4). If a bug appears with probability p per run, then with N runs the chance of seeing it at least once is \( 1 - (1 - p)^N \), which is about \( 1 - e^{-pN} \). A bug that appears once in ten million runs is found with 99.995% probability by one hundred million runs. When a run fails, the seed and the code version are saved. The developer re-runs it with the same seed on a laptop, with a debugger, adds logging, and the bug appears at exactly the same event each time. After the fix, the same seed is added to the regression suite, and it must pass.
A note on structure: the simulator and the system under test share one process, so the "network" between nodes is just a function call that puts a message into a priority queue ordered by simulated delivery time. A node is an object with its own state and its own simulated disk. "Killing" a node means discarding its in-memory state and keeping only the bytes that had been flushed to its simulated disk, which is exactly what a power cut does. "Restarting" it runs the recovery code on those bytes. This makes the hardest code paths, crash recovery and partial writes, run thousands of times per second instead of once a quarter.
Sixth, handle code you cannot rewrite. A deterministic hypervisor (Antithesis) runs the whole system, with its operating system, in a virtual machine whose every source of non-determinism (time, interrupts, I/O, scheduling) is controlled and recorded, and it injects faults from outside. It costs more per run but needs no changes to the program, and works with third-party databases and mixed languages.

example: A team builds a three-node replicated log. Invariant: once a client gets "committed" for an entry, every later leader must contain that entry. They run seeds in parallel on 1,000 cores. Each core does about 10 simulated runs per second, so the cluster does 10,000 runs per second.
Seed 77192 fails at simulated time 9.1 s. The saved trace says: at 3.2 s the workload writes entry 42 to leader n1; n1 sends it to n2 and n3; n2 acknowledges at 3.25 s and n1 reports "committed" to the client (a majority of two). At 3.3 s the injector kills n1. At 3.31 s it clogs the link from n2 to n3 for 5 seconds, so n3 never gets entry 42 in that window. At 3.4 s n3 times out and wins an election in term 2, because n2 votes for it. A bug in the vote check compares only the term numbers and not the log length, so n2 grants the vote although n3's log is shorter. At 4 s the new leader accepts a new entry as position 42 and overwrites the committed one. The checker at 9.1 s sees that a client was told entry 42 was committed, but it is gone. The invariant is broken.
The developer runs seed 77192 on a laptop with a debugger. The same events occur at the same moments. She sets a breakpoint at the vote handler at simulated time 3.4 s, sees the missing log-length comparison, adds it, and runs the seed again: it passes. She adds seed 77192 to the regression list.
How rare was it? Suppose the bug needs a kill, a clog and a timeout inside one window of 100 ms, and it appears in one of ten million random runs (\( p = 10^{-7} \)). A real-time test that runs once a day would need about 10 million days, roughly 27,000 years, to hit it once on average. The simulator makes 10,000 runs per second, or 8.6 × 10^8 per day, so it expects to see the bug about 86 times per day. With N = 5 × 10^7 runs (about 83 minutes), the chance of at least one hit is \( 1 - e^{-5} \), or 99.3%.
Compare a real-time test on real machines: each run takes minutes, the same schedule almost never repeats, and when the bug shows up in a log, the exact timing is lost. That is the gap the simulator closes.
intuition: A flight simulator for your database: crash it a million ways safely, and rewind any crash to watch it again.
The idea is natural once you notice that most of a distributed system's trouble comes from timing and failure, and that both are just inputs. If you control the inputs with one seed, an execution becomes a number you can store, send to a colleague and replay. The hard problem of reproducing a race turns into the easy problem of reusing a number. Because time is virtual and runs are cheap, you can afford the thousands of CPU years that real-time testing would need.
mistakes: People often think DST is the same as chaos engineering or Jepsen. In fact those tools break real systems in real time, so they are not repeatable and they are slow. DST runs a model of the world in virtual time, and every failure can be replayed. The two are complementary: simulation finds logic bugs early, real-world tests check the real kernel, network and hardware.
People often think the simulator tests everything about the system. In fact it tests the code you run inside it against the faults you modelled. A bug in the real network card driver, a quirk of the filesystem's fsync, or a failure kind nobody thought to model is invisible. Teams therefore keep some tests on real hardware for this reason.
People often think that determinism needs only a fixed random seed. In fact any other hidden input also breaks it: the wall clock, thread timing, memory addresses used as hash keys, floating-point differences across CPUs, reading environment variables, or a library that starts its own threads. One such leak makes a failing seed unrepeatable, and teams therefore check determinism by running each seed twice and comparing the trace.
People often think random testing is not systematic and so is weak. In fact a coverage argument works well here: with cheap runs, 10^8 or more random schedules sample the space of interleavings far more widely than humans can write by hand, and swarm-style variation of features makes the distribution broad. It is not a proof, but it finds bugs that a proof of a model would not (code bugs, not design bugs).
People often think you can add DST to any existing system next week. In fact the system must route all I/O, time and randomness through interfaces. That is easy at the start and costly later. Antithesis-style hypervisors lower the cost, but give less control over the internals.
friction: The largest cost is design discipline. All code that touches time, threads, network or disk must go through the simulation layer, from the first day. Mixed code with third-party libraries is hard: a library that spawns threads, reads the clock or uses random numbers directly will break determinism, and so you must wrap, replace or avoid it. Languages with a hidden runtime scheduler (Go, JVM, async runtimes) need special care, replacement runtimes or a hypervisor.
Fidelity is a limit. A simulated disk or network is a model. If it never loses a write after an fsync, or never reorders in the way the real filesystem does, bugs in that area remain. Models need updating with each production incident: every real failure should become a new fault in the simulator.
Checkers are work. Finding a bug needs an invariant that notices it. Writing a serializability checker, or a model of the expected state to compare with, is real effort, and a weak checker gives a green result that means little. Also, liveness bugs ("the system never makes progress again") are harder to detect than safety bugs, because they need timeouts and judgement about what "stuck" means.
There are also coverage and speed issues. The search is random, so some deep states are reached rarely; guided methods (coverage-guided fuzzing, as in Antithesis) help but add complexity. Simulated runs are slower than the real system per simulated operation, because a whole cluster shares one thread, and so performance bugs and multi-threaded data races inside one node are not found by the single-threaded simulation. Finally, a passing seed list creates false confidence if the workloads and faults stay narrow.
practice: If you are building a new distributed system or storage engine, design for simulation from the first commit. Put time, randomness, network and disk behind small interfaces. Make the core logic single-threaded or cooperative (state machines driven by events), with real threads only at the edges. Avoid hash maps ordered by address, avoid global singletons that read the environment, and never call the clock directly.
Start with a small simulator: a network with random delay, drop and partition, a disk that can crash and lose unsynced data, a clock, and a workload with an invariant checker. Run it on thousands of seeds in CI, and in a larger batch overnight. Print the seed at the start of every failure. Run each failing seed twice and compare the traces to detect leaks of non-determinism. Put every fixed seed in the regression set.
Use assertions liberally inside the code, because the simulator will find a path to violate them. Use a BUGGIFY-like switch to make rare conditions common, such as tiny buffers, short timeouts, and forced retries. Randomize configuration (cluster size, timeouts, batch sizes) per seed to widen the search. Track coverage: log which fault types and code branches were hit, and add faults when a branch has never been reached.
For existing systems, consider a deterministic hypervisor service, or the simulation libraries for your language (madsim and turmoil for Rust). Keep real-world testing as well: Jepsen-style tests and chaos experiments catch what the model leaves out. Add each production incident to the simulator as a new fault.
To study, watch Will Wilson's 2014 talk, read the FoundationDB paper's testing section, and read the TigerBeetle write-ups on the VOPR. Then build a toy: three nodes, a simulated network and one invariant, and run 100,000 seeds against a deliberately buggy protocol.
tradeoffs: Choose deterministic simulation when you are building a new system where correctness is critical (databases, consensus, storage, payments) and you can design for it from the start. You pay for an engineering discipline and a simulator, and you get reproducible bugs and years of test time per day. Choose conventional integration tests and Jepsen-style runs when you inherit a large system that cannot be restructured; you lose repeatability and speed.
Choose DST over TLA+ or other model checking when you need to test the real implementation. A model checker explores a model of the design exhaustively but small (a few nodes and steps), and cannot tell whether the code matches the model. DST explores the actual code on large clusters but only samples the space. Use TLA+ for the design of subtle protocols and DST for the implementation, if you have both skills.
Choose a language-level or library simulator (Flow-style actors, madsim, turmoil) when you control the code. It is fast: many runs per core per second. Choose a deterministic hypervisor when you must test existing code in many languages with third-party dependencies; it is slower per run and gives coarser control, but needs no code changes.
Choose more seeds with short runs to find shallow bugs cheaply, and fewer, longer runs with heavy fault injection to find deep ones that need a long history, such as bugs after many compactions. Budget both, using the failure data to tune it.
Choose to also keep real-hardware and chaos tests. They cost more per bug and are not repeatable, but they test the parts of the world your simulator only imitates.
interview: What makes a simulation run deterministic, and what usually breaks determinism? || All inputs that vary between runs (time, random numbers, thread scheduling, network and disk events) come from one seeded generator through interfaces, and everything runs in one thread. Hidden inputs break it: wall-clock reads, multi-threaded libraries, pointer-ordered maps, uninitialized memory, floating-point differences. Detect leaks by running each seed twice and comparing traces.
How does DST find bugs that only occur once in ten million executions? || Runs are cheap and use virtual time, so a cluster can run millions of seeds per night. If the bug has probability p per run, N runs hit it with probability 1 − (1 − p)^N; with p = 10^-7 and N = 5 × 10^7 that is about 99%. BUGGIFY and per-run feature randomization make rare states more common.
How is DST different from Jepsen or Chaos Monkey? || Those inject faults into real systems in real time; a run takes minutes and cannot be replayed exactly. DST injects faults into a simulated environment, so runs are fast and any failure replays from its seed. Jepsen tests the real stack, DST tests the logic far more deeply; teams combine them.
You have a large Java service built on many libraries. Can you apply DST? || Hard to do in-process because of threads, timers and library randomness. Options: a deterministic hypervisor that controls non-determinism from outside; or isolating the core state machine behind interfaces and simulating just that part. Expect partial coverage and a lot of integration work.
What are the main limits of the approach? || It only finds bugs under the faults and invariants you modelled, so fidelity of the disk and network model matters, and weak checkers pass buggy code. It does not find multi-threaded races (single-threaded), and it is expensive to retrofit. Liveness bugs are harder to detect than safety bugs.
How would you test a Raft implementation with DST? || Run 3 to 5 nodes in a simulator with random message delay, loss, duplication and partitions, plus crashes with lost unsynced writes. Check election safety, log matching, leader completeness and that committed entries survive. Check liveness by healing faults and expecting progress within a bound. Save the seed of any failure.
quiz: What does the seed control in a deterministic simulation? || Every source of non-determinism: random choices, scheduling, message delays and drops, disk faults, crash timing and the workload. The same seed and code give the same run.
Why can a simulator run hours of system time in seconds? || Time is virtual. When all tasks are waiting, the simulator jumps the clock straight to the next scheduled event instead of really waiting.
A bug appears in 1 of 10^7 random runs. About how many runs give a 99% chance to find it? || N such that \( 1 - e^{-N/10^7} = 0.99 \), so \( N \approx 4.6 \times 10^7 \) runs.
Why does BUGGIFY only act in simulation? || It makes code take unlikely paths (delays, errors, tiny buffers) to expose rare bugs. In production that would hurt performance and behaviour, so the macro is a no-op there.
Your team must choose between a TLA+ model and a simulator for a new replication protocol. What do you do? || Use TLA+ to check the design with exhaustive search on small configurations, then DST to check the real implementation at larger scale with faults. TLA+ cannot show the code matches, and DST cannot prove the design in all cases.

value: A service that must survive machine crashes needs several copies of its state, and the copies must apply the same operations in the same order. A simple way to get this is primary-backup replication: one replica (the primary) receives all requests, puts them in order, and sends them to the others. The hard part is what happens when the primary fails. The backups must choose a new primary, and the new primary must not lose any operation that a client has already been told succeeded. It must also not let two replicas both believe they are the primary.
Viewstamped Replication (VR), by Brian Oki and Barbara Liskov (1988), is one of the first complete answers. Time is divided into numbered views. In each view, one replica is primary, chosen by a fixed rule from the view number. The primary orders requests, and an operation commits when a majority of replicas have stored it. When the primary seems dead, the replicas move to the next view, and the new primary rebuilds the log from a majority before it accepts requests. With 2f + 1 replicas the service survives f crashes. It stays consistent even when the network delays or loses messages, and it makes progress whenever a majority can talk.
The layers below supply the parts. Quorums (L2) give the safety argument: any commit quorum (f + 1 replicas) and any view-change quorum (f + 1 replicas) share at least one replica, so the new primary always meets a replica that holds every committed operation. Leader election and leases (L2) supply the idea of a single primary at a time and failure detection by timeouts. The write-ahead log (L2) is the ordered operation log that backups append to and replay. For the layers above, Raft's leader, terms and log matching follow VR closely, and consensus (L2) in practice is often taught through VR, Paxos and Raft as three views of one design.
terms: Replica — one server holding a copy of the service state and the operation log.
View — a numbered period during which one replica is primary; the view number only grows.
Primary — the replica of the current view that orders client requests; its index is the view number modulo the number of replicas.
Op-number — the position of an operation in the log; the primary assigns the next one to each request.
Commit-number — the highest op-number known to be committed, meaning stored by a majority and safe to execute.
View change — the protocol that replaces the primary and rebuilds the log for the new view.
Viewstamp — the pair (view number, op-number), which orders operations across views.
Client table — a record, kept by replicas, of each client's latest request number and reply, so that retries are not executed twice.
history: Brian Oki's MIT thesis and the PODC 1988 paper "Viewstamped Replication: A New Primary Copy Method to Support Highly-Available Distributed Systems" (Oki and Liskov) were written for Argus, a language for distributed programs with transactions, built in Barbara Liskov's group. Earlier primary-copy schemes could lose data or split in two when the primary failed. Oki and Liskov added "views" and "viewstamps": a view change makes sure the group agrees on one history before it continues, and the viewstamp tells which replica knows the most. A related system, the Harp file system (Liskov and others, SOSP 1991), used the idea in practice, with replicas that kept data in memory protected by uninterruptible power supplies.
At nearly the same time Leslie Lamport devised Paxos (written in 1989, published in 1998 after long delay), which solves the same problem with a different presentation. For years, people believed VR and Paxos were separate. Later work showed that Multi-Paxos with a stable leader and VR are the same idea in different words. Industry systems such as Google's Chubby and Spanner use Paxos, and ZooKeeper's Zab is a closely related design.
In 2012 Barbara Liskov and James Cowling published "Viewstamped Replication Revisited". It describes the protocol without the Argus transaction setting, gives the full set of messages, and adds recovery from crashes without relying on disk writes, and reconfiguration (changing the set of replicas). Diego Ongaro and John Ousterhout's Raft (2014) states that it is closely related to VR and credits it, while it makes the problem easier to teach with strong leader and terms. TigerBeetle, a financial database, uses VR as its replication protocol, together with the protocol-aware recovery ideas of Alagappan and others (FAST 2018).
how: The system has n = 2f + 1 replicas, numbered 0 to n − 1 in a fixed configuration. Each replica keeps: the current view number, its status (normal, view-change or recovering), the op-number of the latest operation in its log, the log itself (operations in order), the commit-number, and a client table. In view v, the primary is replica v mod n, a rule that every replica can compute alone, so no vote is needed to choose a primary.
Normal operation, four messages in the common case. A client sends REQUEST(op, client id, request number) to the primary. The primary checks the client table (a retry of an old request returns the saved reply), assigns the next op-number, appends the request to its log, and sends PREPARE(view, op, op-number, commit-number) to all backups. A backup accepts the PREPARE only if it is in the same view and has already accepted all earlier op-numbers (otherwise it waits or fetches the missing entries). It appends the operation and answers PREPAREOK(view, op-number). When the primary has PREPAREOK from f backups (so f + 1 replicas, counting itself, hold the operation), the operation is committed: the primary executes it, updates the client table, and replies to the client. The commit-number in later PREPARE messages (or in an idle COMMIT message) tells backups which operations they may now execute. Backups execute operations only in order and only up to the commit-number.
Failure detection is by timeout. A backup that hears nothing from the primary (no PREPARE and no COMMIT, which the primary sends regularly) concludes that the primary may be dead and starts a view change. This is the leader-election idea from the lower layer: assume the leader is gone after a silence, but never assume the old leader has stopped, since it could just be slow. Safety must not depend on the guess being right.
View change. The replica increases its view number to v + 1, sets its status to view-change, and sends STARTVIEWCHANGE(v + 1) to all. When a replica has received f such messages from others for the same view (plus its own), it knows a majority wants to leave the old view. It then sends DOVIEWCHANGE(v + 1, log, last normal view, op-number, commit-number) to the new primary, replica (v + 1) mod n. The new primary waits for f + 1 DOVIEWCHANGE messages (its own included). Then it builds the new log: from the messages with the highest "last normal view", it takes the log with the largest op-number. It sets its commit-number to the largest one reported and sends STARTVIEW(v + 1, log, op-number, commit-number) to everyone. Backups replace their logs, send PREPAREOK for any uncommitted operations, and resume normal operation. A replica accepts no messages from old views once it has moved on, so an old primary that wakes up is ignored and cannot commit anything.
Why is this safe? Counting from combinatorics (L4) and quorums (L2): a committed operation is stored on at least f + 1 replicas. The view change collects logs from f + 1 replicas. Any two groups of f + 1 out of 2f + 1 overlap in at least one replica. So at least one log in the view change contains every committed operation, and the "highest last normal view, then longest log" rule picks a log that has them. The new primary may also keep operations that were prepared but not committed. That is fine, because the client has not been told they succeeded, and keeping them is safe too.
Recovery and reconfiguration. A replica that crashes and restarts sends RECOVERY with a random nonce. It waits for f + 1 answers, including one from the primary of the latest view, and rebuilds its state from them; the nonce prevents it from using old answers. This means VR can run without writing to disk on every operation, using replication in memory as the form of durability, as long as fewer than a majority fail at once. If all replicas can lose power at the same time, disk writes are needed. For reconfiguration, a special client request moves the group to a new epoch with a new set of replicas, so that machines can be added and removed.

example: Take three replicas R0, R1 and R2 (f = 1) in view 0, so R0 is primary. Clients have submitted five operations. R0 has sent PREPARE for each, and for operation 5 only R1 received it. R1 stored it and sent PREPAREOK. R0 received that single PREPAREOK, so with itself it has f + 1 = 2 copies. It declares operation 5 committed, executes it and replies to the client. Then R0 crashes before sending any later message.
State now: R1 has operations 1 to 5 (commit-number 4, since it has not yet been told that 5 committed). R2 has operations 1 to 4 (it never got the PREPARE for 5). The client has already been told that operation 5 succeeded.
R1 and R2 each wait for a PREPARE or COMMIT message and time out after, say, 500 ms. Both move to view 1. The primary of view 1 is replica 1 mod 3 = R1. R2 sends DOVIEWCHANGE(view 1, log of 4 operations, last normal view 0, op-number 4, commit-number 4) to R1. R1 counts its own DOVIEWCHANGE (log of 5 operations, last normal view 0, op-number 5). That makes f + 1 = 2 messages. Both have last normal view 0, so R1 picks the largest op-number, which is 5 from its own log. It sends STARTVIEW(1, 5 operations, op-number 5, commit-number 5) to R2. R2 appends operation 5. The committed operation survived, as it must.
Check the other possible outcome. If R2 had been the new primary, it would have received R1's DOVIEWCHANGE with 5 operations, and R2's own with 4; the rule picks the longer log again. The only way to lose operation 5 would be a view-change quorum that does not contain R1 or R0. But any two groups of 2 out of 3 replicas overlap, and the commit quorum was {R0, R1}. The view-change quorum {R1, R2} shares R1.
Now count the cost. Normal case: 1 request, 2 PREPARE (one per backup), 2 PREPAREOK, 1 reply: 6 messages, and 4 message delays from client to reply. The view change took one STARTVIEWCHANGE broadcast from each live replica, one DOVIEWCHANGE from R2 and one STARTVIEW from R1, about three message delays after the 500 ms timeout. For n = 5 (f = 2) the primary needs 2 PREPAREOK of 4 backups, and a view change needs 3 DOVIEWCHANGE messages. In both cases the messages grow linearly with n, not quadratically, because only the primary talks to everyone in the normal case.
intuition: A meeting with a chair who numbers every decision; if the chair disappears, the next person in line collects everyone's notes, adopts the most complete record and carries on.
The design is natural because it separates two jobs. In the normal case, a single primary makes ordering easy: no conflicts, one place to number requests. When the primary fails, the group must be certain that nothing already promised to a client is lost. Majorities always overlap, so asking a majority for their notes is guaranteed to reach someone who remembers every committed decision. Numbering the views stops an old chair from returning and causing confusion, since everyone ignores messages from earlier views.
mistakes: People often think VR and Paxos or Raft are very different algorithms. In fact all three use a majority quorum, one ordering leader per period, and the same overlap argument. VR calls the period a view, Raft calls it a term. They differ mostly in how the new leader is chosen (VR: fixed rotation by view number; Raft: a vote with a log-freshness check) and in how the new leader gets the log (VR: it fetches from the quorum; Raft: it must already be the most up to date).
People often think a replica that sees a timeout can safely say that the primary is dead. In fact timeouts only suggest a failure, since the primary may be slow or cut off. VR is safe even when the guess is wrong: the old primary cannot get PREPAREOK from a majority in the old view once a majority has moved on, so it cannot commit anything.
People often think the new primary takes the log of the most replicas, or the log with the highest op-number. In fact it takes the log from the highest "last normal view" first, and only then the longest. A replica may hold a long log from an old view that was never committed, and a shorter log from a newer view must win over it.
People often think VR needs to write to disk on every operation. In fact the 2012 version keeps durability by replication in memory and recovers a crashed replica from the others. Disk is needed only to survive failures of a majority at once, such as a full power loss.
People often think 2f + 1 replicas tolerate f Byzantine replicas. In fact VR assumes crash faults only. A replica that lies about its log can make the group lose committed operations. Byzantine tolerance requires 3f + 1 replicas and signed messages (the PBFT concept).
friction: As with every leader-based protocol, all writes pass through one primary. Its CPU and network limit throughput, and while it is being replaced the service accepts no writes, usually for at least the timeout plus a few message delays. Choosing the timeout is a trade-off: too short causes needless view changes under load, too long extends the outage.
The view change moves whole logs. In the paper's simple form, each DOVIEWCHANGE carries the full log, which can be huge. Practical versions send only the part after the last known commit-number, use checkpoints and state transfer to bring a far-behind replica up to date, and truncate the log regularly. The details of log truncation and state transfer are where many implementations go wrong.
Fewer production libraries exist than for Raft or Paxos, and fewer teaching materials and test suites. Recovery without disk is subtle: if too many replicas restart at once, or a replica restarts and forgets that it has promised something, safety can break. The 2012 paper's recovery protocol handles single failures, but whole-cluster power loss needs disk writes, and disk faults (a corrupted log entry) need more care than the simple crash model; protocol-aware recovery was developed for this. Also, VR does not by itself give read performance: reads that must be linearizable either go through the log or need a lease on the primary, which again depends on clock behaviour.
practice: If you need a replicated state machine, use a mature library or service rather than writing VR yourself: etcd or Consul (Raft), ZooKeeper (Zab), or a managed service. VR is mostly valuable as knowledge, because it explains Raft and Paxos from a clear angle. If you do implement it, follow the 2012 paper message by message, and test with simulated failures: dropped, delayed and duplicated messages, crashes at every step, and partitions that isolate the primary.
Choose n = 2f + 1 to match your failure budget: 3 replicas for one crash, 5 for two. Spread replicas across failure domains (racks, zones), because the quorum argument assumes independent failures. Put the log on separate disks if you persist it, and fsync before replying if you want to survive a power loss of the whole group.
Pick the timeout from the network round trip and the load, several heartbeat intervals, well above the normal message delay, and add jitter. Monitor view-change counts, commit latency and the lag of each backup. A rising view-change rate is a sign of overload or network trouble.
Use the client table. Every request needs a unique (client id, request number) so that retries after a timeout do not execute twice, which is the usual source of duplicate-effect bugs in replicated services.
To study, read "Viewstamped Replication Revisited" next to the Raft paper and make a table that maps each VR message to its Raft counterpart. Then compare how each protocol picks the new leader and brings its log up to date.
tradeoffs: Choose VR-style rotation of the primary by view number when you want a simple, vote-free leader choice and a clear log-transfer step. You give up the chance to prefer the healthiest node, and a dead replica whose turn comes still costs one timeout. Choose Raft's randomized elections when you want the leader to be the node with the most complete log, so that no log needs to move, and when you want strong library support.
Choose protocols with in-memory durability (VR Revisited) only when the machines have independent power and failures are not correlated, and you value low write latency (no fsync, often saving 0.1 to several milliseconds per write). Choose synchronous disk writes when losing the whole group at once is not acceptable, as with a database of record.
Choose a leader-based replicated log (VR, Raft, Multi-Paxos) when you need a single ordering of operations and linearizable reads, at the cost of a leader bottleneck and a pause on failure. Choose a leaderless design (quorum reads and writes, anti-entropy) when availability under partitions matters more than a single order.
Choose a larger group (5 instead of 3) when you need to tolerate two failures or want maintenance without risk; it costs four more messages per request and slightly higher latency, since the primary waits for the second-fastest of four backups instead of the faster of two. Choose 3 when latency and cost matter more than the added safety.
Choose crash-fault VR over BFT when all replicas are in one trust domain. It needs 2f + 1 machines instead of 3f + 1 and linear instead of quadratic messages.
interview: Explain how VR commits an operation in the normal case. || The client sends the request to the primary, which assigns the next op-number, appends it to its log and sends PREPARE to the backups. Each backup that has all earlier entries appends and replies PREPAREOK. When the primary has f replies (f + 1 copies including itself), the operation is committed; it executes, replies to the client, and later tells backups the new commit-number.
How does VR make sure a new primary does not lose a committed operation? || A committed operation is stored on f + 1 of 2f + 1 replicas. The new primary collects logs from f + 1 replicas, and any two such groups overlap, so at least one log contains it. The primary chooses the log with the highest last-normal-view and, among those, the largest op-number, which contains all committed operations.
How is VR's view change different from a Raft election? || In VR the next primary is fixed by the view number (v mod n) and gathers logs from a majority, then picks the best one. In Raft, a candidate asks for votes and each voter grants a vote only if the candidate's log is at least as up to date as its own, so the winner already has all committed entries and no logs move. Both rely on majority overlap.
What happens if the old primary is only slow and comes back later? || Replicas have moved to a higher view and ignore messages from the old view. The old primary cannot get PREPAREOK from a majority in the old view, so it cannot commit anything. When it sees a higher view number, it steps down and catches up by state transfer.
How can VR run without disk writes, and what is the risk? || Durability comes from f + 1 in-memory copies; a restarted replica recovers by asking a majority (including the primary of the latest view) for state, using a nonce so replies are fresh. If a majority of replicas fail at once, as in a total power loss, the data is gone, so those environments need disk persistence.
Why does a duplicate request not run twice? || The client table stores the latest request number and reply for each client. The primary checks it before assigning an op-number, and returns the saved reply to a retry, so a client may safely re-send after a timeout.
quiz: How many replicas does VR need to tolerate 2 crashes, and how many must hold an operation before it commits? || n = 2f + 1 = 5 replicas; an operation commits once f + 1 = 3 replicas (the primary and 2 backups) hold it.
Who is the primary of view 7 in a group of 5 replicas? || Replica 7 mod 5 = 2, so replica 2.
Why must a view-change quorum overlap every commit quorum? || Both have f + 1 members out of 2f + 1, so they share at least one replica. That replica's log contains the committed operation, so the new primary will see it.
In a view change, replica A has a log of 9 entries from last normal view 2, and replica B has a log of 7 entries from last normal view 3. Which log does the new primary choose? || B's log, because the highest last normal view comes first. The log from view 3 may contain entries that committed after view 2; A's extra entries were never committed in view 3.
When would you choose Raft over a hand-written VR? || Almost always in production: Raft has well-tested libraries, clear documentation and tooling, and an equivalent design. Use VR when its in-memory recovery or its fixed rotation suits a specific system, or to understand the design.

value: A large language model is mostly a pile of numbers (weights). A model with 70 billion weights stored as 16-bit floats takes 140 GB, more than one GPU holds. Worse, when the model generates text one token at a time, the GPU must read every weight from memory for each token, and reading memory, not arithmetic, is the bottleneck. On an H100 with about 3.35 TB/s of memory bandwidth, reading 140 GB takes about 42 ms, so the speed limit is about 24 tokens per second for one user, however fast the arithmetic units are.
Quantization stores each number with fewer bits: 8, 4 or even fewer instead of 16. A weight is mapped to one of a small set of levels, plus a scale factor that says how big a step is. At 4 bits the same 70B model needs about 36 GB, fits on one GPU, and its bandwidth-limited speed limit becomes roughly four times higher. The price is rounding error, and the whole craft is choosing the mapping so that this error does not change the model's answers. Today 8-bit and 4-bit weights are the usual way to serve open models, and the same idea shrinks the KV cache (the memory of earlier tokens), activations during training and vectors in search indexes.
The layers below set the terms. Floating-point numbers (L3) explain what is being thrown away: a 16-bit float has a sign, an exponent that sets the range and a mantissa that sets the precision, and quantization replaces this with fewer, evenly spaced levels (integers) or smaller floats such as FP8 and FP4. Tensor cores and systolic arrays (L3) explain why the saving is also computed faster: modern GPUs have matrix units that run 8-bit and 4-bit multiplications at two to four times the rate of 16-bit. For the layers above, transformers and LLMs (L1), LLM serving (L1), vector search (L1) and local runtimes such as llama.cpp (L0) all depend on it to fit models into memory and meet latency targets.
terms: Quantization — mapping real numbers to a small set of discrete levels, stored as low-bit integers or small floats.
Scale (step size) — the real-number value of one integer step; the real weight is approximately integer × scale.
Zero point — an integer offset used in asymmetric quantization so that the range need not be centred on zero.
Group size — the number of consecutive weights that share one scale, for example 32 or 128; smaller groups mean less error and more overhead.
Outlier — a value far larger than its neighbours; one outlier forces a large scale and ruins the precision of the rest.
PTQ (post-training quantization) — quantizing a finished model, usually with a small calibration set.
QAT (quantization-aware training) — training or fine-tuning while simulating rounding, so the model adapts to it.
Calibration data — a few hundred sample inputs used to measure activation ranges or the effect of rounding.
history: Quantization is old in signal processing; in machine learning it began as an efficiency tool for small networks. Courbariaux and others (BinaryConnect, 2015) and Rastegari and others (XNOR-Net, 2016) trained networks with 1-bit weights. Jacob and others at Google (CVPR 2018) described the 8-bit integer scheme with scale and zero point and quantization-aware training that later became the standard in mobile inference (TensorFlow Lite). QAT relies on the straight-through estimator (Bengio and others, 2013): rounding has zero gradient almost everywhere, so the backward pass pretends rounding is the identity.
Large language models changed the problem. In 2022, Dettmers and others found in LLM.int8() that beyond about 6.7 billion parameters, a few hidden dimensions carry huge activation values (outliers, with magnitude up to about 20 times larger than typical values), and that plain 8-bit rounding of activations breaks the model. They kept the outlier dimensions in 16-bit and quantized the rest. SmoothQuant (Xiao and others, 2022) moved the difficulty from activations to weights by rescaling channels. GPTQ (Frantar and others, 2022) quantized weights to 3 or 4 bits one layer at a time, using second-order information to adjust the remaining weights after each rounding, and could process a 175-billion-parameter model in a few GPU-hours. AWQ (Lin and others, 2023) observed that about 1% of weight channels matter most, as seen from the activations, and protected them by scaling.
In 2023, QLoRA (Dettmers and others) combined a 4-bit "NormalFloat" format with low-rank adapters, so a 65B model could be fine-tuned on one 48 GB GPU. In the same year, the llama.cpp project introduced the GGUF format with block-wise "k-quants" that made 4-bit models run on laptops. On the hardware side, NVIDIA's Hopper GPUs added FP8 (2022), and Blackwell GPUs added FP4 formats (MXFP4 from the Open Compute Project and NVIDIA's NVFP4), where small blocks share an 8-bit scale. By 2025, open-weight models such as OpenAI's gpt-oss were released with 4-bit (MXFP4) weights for the expert layers.
how: The basic scheme is affine quantization. Given a block of real values x, choose a scale s and, if needed, a zero point z. The stored integer is \( q = \text{clamp}(\text{round}(x / s) + z, q_{\min}, q_{\max}) \). The approximate real value is \( \hat{x} = s \times (q - z) \). In symmetric quantization \( z = 0 \) and the range is centred on zero: for signed b-bit integers q runs from \( -(2^{b-1} - 1) \) to \( 2^{b-1} - 1 \), and \( s = \max|x| / (2^{b-1} - 1) \). For 4 bits that gives integers from −7 to 7; for 8 bits, −127 to 127. The maximum rounding error for each value is \( s / 2 \).
The key design choice is how many values share a scale (granularity). One scale per whole tensor is cheap but fragile, because one outlier sets the scale for millions of values. One scale per output channel is better. Modern 4-bit schemes use groups of 32 to 128 consecutive weights, each with its own 16-bit or 8-bit scale. A group of 128 with a 16-bit scale adds 16/128 = 0.125 bits per weight, so "4-bit" really costs about 4.1 bits. Smaller groups cut error but increase this overhead and the cost of dequantization.
Post-training quantization works on a trained model. The simplest method, round-to-nearest, just applies the formula, and is fine at 8 bits and usually acceptable at 4 bits for large models. Smarter methods look at the effect on the layer's output. GPTQ takes a layer's weight matrix W and a sample of its inputs X, and quantizes the columns one by one; after rounding a column, it adjusts the not-yet-quantized columns to cancel the error on the layer's output, using the inverse of the Hessian (the second-derivative matrix of the layer's squared error, XXᵀ). AWQ multiplies the important channels (those with large activations) by a factor before quantization, which makes them effectively use finer steps, and divides the activations by the same factor, so the output is unchanged. These methods need only a few hundred calibration samples and minutes to hours of GPU time.
Weights, activations and the KV cache have different difficulty. Weights are fixed and well behaved, so weight-only quantization (W4A16: 4-bit weights, 16-bit activations) is the most common. The GPU loads 4-bit weights, converts them to 16-bit inside the kernel (dequantization), and multiplies in 16-bit. This saves bandwidth (the bottleneck in token generation) but not arithmetic. Quantizing activations too (W8A8, or FP8) lets tensor cores run the multiplication in low precision, which is what speeds up the compute-bound phase, but activations contain outliers and change with every input, so they need dynamic scales or smoothing. The KV cache can be stored in 8-bit (FP8 or INT8) to double the context or batch size that fits in memory.
How the saving reaches the hardware depends on packing and kernels. Two 4-bit values are packed into one byte, so a row of weights is a dense array of bytes. A fused kernel loads a tile of packed weights from memory into registers, unpacks the nibbles with shifts and masks, multiplies them by the group scale to get 16-bit values, and feeds them to the tensor cores together with the activations, all without writing the unpacked weights back to memory. Only the packed bytes cross the memory bus. This is the reason a good 4-bit kernel (such as Marlin or the kernels in llama.cpp) can approach the byte-ratio speedup, and a naive implementation that dequantizes the whole matrix to memory first is no faster than FP16.
Quantization-aware training goes further. During training, the forward pass includes the quantize-then-dequantize step ("fake quantization") so the loss sees the rounding error, and the backward pass uses the straight-through estimator. The weights learn to sit where rounding hurts least. QAT gives better accuracy than PTQ at 4 bits and below but needs training compute and data.
Finally, hardware formats. FP8 comes in E4M3 (4 exponent bits, 3 mantissa bits, more precision) and E5M2 (more range). FP4 (E2M1) has only 16 values, so it is used with a shared scale for each block of 16 or 32 values: NVFP4 uses 16-element blocks with an FP8 scale and a per-tensor scale, MXFP4 uses 32-element blocks with a power-of-two scale. Floating-point formats put more levels near zero, which suits weights that follow a bell curve.

example: Take eight weights: 0.12, −0.50, 0.33, 1.20, −0.07, 0.80, −1.00, 0.02. Quantize them to signed 4 bits (integers −7 to 7). The largest magnitude is 1.20, so s = 1.20 / 7 = 0.1714. Divide each weight by s and round: 0.12 gives 0.70, which rounds to 1; −0.50 gives −2.92, which rounds to −3; 0.33 gives 1.93, so 2; 1.20 gives 7; −0.07 gives −0.41, so 0; 0.80 gives 4.67, so 5; −1.00 gives −5.83, so −6; 0.02 gives 0.12, so 0. Stored: 1, −3, 2, 7, 0, 5, −6, 0. To dequantize, multiply by s: 0.171, −0.514, 0.343, 1.200, 0, 0.857, −1.029, 0. The errors are 0.051, 0.014, 0.013, 0, 0.070, 0.057, 0.029 and 0.020, all at most s / 2 = 0.086. That is a relative error of several percent per weight, but the errors point in random directions, and a dot product of thousands of such weights averages most of them out.
Now add one outlier, 12.0, to the group. The scale becomes 12 / 7 = 1.714, and the grid is now 0, ±1.714, ±3.43, and so on. Every ordinary weight is smaller than half a step (0.857) except 1.20 and −1.00, which round to ±1 (that is ±1.714). All of the others become 0. The group has lost nearly all information except the outlier. This is why outliers are the main problem, and why groups, channel-wise scaling (AWQ, SmoothQuant) and keeping outlier channels in high precision (LLM.int8()) exist.
Now the system effect. A 70-billion-parameter model has the following weight sizes: in FP16, 140 GB; in INT8, 70 GB; in 4-bit with groups of 128, about 36 GB (70 × 4.125 / 8). On one H100 with 3.35 TB/s of bandwidth, reading all weights once per token gives an upper limit of about 24 tokens per second at FP16 (it does not fit on one 80 GB GPU in any case), 48 at INT8, and 93 at 4 bits, for a single sequence. With batching, the weights are read once per step for all sequences, so the real gain is that more sequences fit in the freed memory. The limits are upper bounds; real systems reach 60–80% of them. On the accuracy side, 8-bit weight quantization of large models is normally indistinguishable in benchmarks, and good 4-bit methods usually lose a small fraction of a point on perplexity and a little more on hard reasoning tasks.
intuition: Describe each number with fewer digits; for most purposes the picture stays the same.
The method works because neural networks are redundant and noisy. A weight's exact value rarely matters; what matters is the combined effect of thousands of weights on an output. Rounding errors are small and random, so they largely cancel in the sums. The trouble comes only from a few values that dominate (outliers), and almost all the effort in quantization research is about finding them and giving them special treatment. The saving is real because decoding is limited by how many bytes cross the memory bus, so fewer bytes mean more tokens per second.
mistakes: People often think a 4-bit model is 4 times faster than a 16-bit one. In fact the gain depends on where the bottleneck is. Weight-only quantization speeds up the memory-bound decode step by up to the ratio of bytes, but gives nothing in the compute-bound prefill step, where dequantization even adds work. Real speedups are usually 1.5 to 3 times.
People often think quantization error is uniform across the model. In fact a few layers, a few channels and a few tokens (for example the first token, which many models use as an attention sink) are much more sensitive. Good methods keep the embedding, the output head or the sensitive layers at higher precision.
People often think lower is always better, so 2-bit is just twice as good as 4-bit. In fact quality falls fast below 4 bits for weights: perplexity loss is small at 8, small at 4, noticeable at 3 and large at 2 for ordinary methods. Special methods (vector quantization, rotation-based methods, QAT) reduce the loss but cost complexity and speed.
People often think perplexity or a single benchmark shows the quantized model is as good. In fact perplexity changes little, while long-context, multi-step reasoning, code and low-resource-language tasks can degrade more. Evaluate on your own task.
People often think quantization and compression by pruning or distillation are the same. In fact quantization keeps every weight and shrinks the representation; pruning removes weights; distillation trains a smaller model. They combine well, but each has different failure modes.
friction: Accuracy loss grows quickly below 4 bits, especially for small models (which have less redundancy), long contexts and tasks needing exact reasoning or exact recall. Activation quantization is much harder than weight quantization because of outliers. Different layers, models and tasks respond differently, so a recipe that works on one model may not on the next.
Kernels and hardware support are uneven. A 4-bit format only helps if there is a fast kernel that unpacks it in registers and feeds the tensor cores. Formats like GPTQ, AWQ, GGUF and FP4 each need their own kernels, and some run well only on certain GPUs or for certain batch sizes: at large batch sizes, dequantization adds work and the benefit shrinks. Native low-precision tensor core formats (FP8 on Hopper, FP4 on Blackwell) are newer and need matching software.
Calibration and tooling add risk. PTQ methods depend on the calibration data: a set unlike the real traffic can give misleading ranges. Quantized checkpoints from third parties vary in quality, and a quantized model should be tested against the original on your own prompts before use. Quantization also interacts with fine-tuning, long context (the KV cache error accumulates over many tokens) and speculative decoding, whose draft and target models should match in behaviour.
Finally, there is an open research frontier: training in low precision from scratch (FP8 and FP4 pre-training), lower-bit weights with learned codebooks, and methods that handle outliers by rotating the weights (Hadamard transforms) so that no single channel dominates.
practice: Start from the memory budget. Compute weight bytes (parameters × bits / 8, plus about 3% for scales) and add the KV cache for your batch and context. If the model fits at 8 bits and speed is enough, use 8 bits: it is almost lossless. If you need to double the capacity or the speed, go to 4-bit weights with a well-supported method, such as AWQ or GPTQ with group size 128 for GPU serving, or a Q4_K_M GGUF file for llama.cpp on a laptop.
Prefer weight-only 4-bit for latency-bound serving with small batches, and FP8 weights and activations for high-throughput serving on Hopper or newer GPUs, where tensor cores run FP8 at twice the FP16 rate. Quantize the KV cache to FP8 when memory limits batch size. Keep the embedding table, the final output layer and normalization in higher precision unless measured otherwise.
Always compare with the original model on your own evaluation set: accuracy on key tasks, long-context behaviour, tool calling and any language you serve. Look at outputs, not only perplexity. Check throughput on your own hardware, at your own batch sizes. A 4-bit model that is slower than the 8-bit model because of poor kernels is a common surprise.
For training or fine-tuning, use QLoRA (4-bit frozen base plus 16-bit adapters) to fine-tune big models on small hardware, and QAT when you must deploy at 4 bits or lower and PTQ is not good enough. For vector search indexes, scalar quantization (8-bit) is the safe first step, with product quantization when memory still limits you.
To study, quantize a small model by hand with the formula above, measure the error per group size, then use a library (bitsandbytes, AutoAWQ, llama.cpp quantize) and compare perplexity and speed.
tradeoffs: Choose 8-bit (INT8 or FP8) when you want a nearly lossless 2× memory saving with simple tooling. Choose 4-bit weights when memory or bandwidth limits you: it gives roughly 4× smaller weights and up to 3× faster decoding, and costs a small accuracy loss that you must measure. Choose 3-bit or 2-bit only for large models with no better option, and expect clear quality loss.
Choose weight-only quantization (W4A16) for interactive serving with small batches, where decoding is memory-bound. Choose weight-and-activation quantization (W8A8, FP8) for big batches or prefill-heavy loads, where compute is the limit; it needs outlier handling and hardware support, but speeds up arithmetic too.
Choose post-training quantization when you have a finished model and little time: minutes to hours, no training data. Choose quantization-aware training when the target precision is very low or the accuracy loss must be minimal; it costs training compute and a training pipeline.
Choose small groups (32) and 16-bit scales when quality matters most, and larger groups (128 or per-channel) when overhead and kernel speed matter. The difference is about 0.1 bit per weight and a small change in accuracy.
Choose to leave quantization out when the model is small (under about 3B parameters, where redundancy is low and memory is not an issue), or when exact numerical behaviour matters, for example in scientific code.

value: Modern AI turns text, images, products and users into embeddings: lists of a few hundred numbers (a vector) such that similar things have nearby vectors. To use them, you must answer one question again and again: given a query vector, which stored vectors are closest? Doing it exactly means comparing the query with every stored vector. With 100 million vectors of 768 numbers, one query needs about 77 billion multiplications and reads about 300 GB of memory. That takes seconds on one machine, and a search service must answer in tens of milliseconds, for thousands of queries per second.
Approximate nearest neighbour (ANN) search gives up a little accuracy for a large saving. It builds an index that lets the search look at a tiny fraction of the vectors, for example 0.01%, and still return most of the true nearest neighbours. The usual quality measure is recall@k: the fraction of the true top k that the search returns. A good system reaches 95 to 99% recall at a small fraction of the cost of exact search. The two main families are graph indexes (HNSW, DiskANN), which walk from point to point toward the query, and cluster indexes (IVF), which divide the space into regions and search only the closest ones. Both are usually combined with compression (product quantization) so that vectors fit in memory.
The layers below explain each part. Graph algorithms (L3) provide greedy search and beam search over a proximity graph. Queues (L3) provide the two priority queues (heaps) that hold the candidates still to explore and the best results found. Geometry and metric spaces (L4) define distance (Euclidean, cosine, inner product) and the triangle inequality that makes "close to a close point" mean something. Random and small-world graphs (L4) explain why a graph with a few long links gives short paths from anywhere to anywhere. Locality-sensitive hashing (L2) was the first ANN family with guarantees, and random projections (L4) shrink dimensions. For the layer above, vector search (L1), RAG (L1) and recommender systems (L1) use ANN to find relevant passages and candidate items among millions in milliseconds.
terms: Embedding — a vector of numbers produced by a model so that similar items have nearby vectors.
Recall@k — the share of the true k nearest neighbours that the approximate search returns.
Proximity graph — a graph whose nodes are vectors and whose edges join vectors that are close to each other.
HNSW — Hierarchical Navigable Small World: a stack of proximity graphs, sparse at the top and dense at the bottom.
IVF — Inverted File index: k-means clusters the vectors, and each cluster keeps a list of its members.
Product quantization (PQ) — compressing a vector into a few bytes by splitting it into parts and replacing each part with the index of its nearest centroid.
efSearch / nprobe — the search-time knobs: how many candidates the graph search keeps, or how many clusters the IVF search visits.
Curse of dimensionality — in high dimensions, distances between points become similar and space-splitting trees stop working.
history: Exact methods came first. The k-d tree (Bentley, 1975) splits space with axis-aligned cuts and works well in 2 to about 10 dimensions. In high dimensions it degrades to a linear scan, because a query ball touches nearly every cell. This is the curse of dimensionality. In 1998 Indyk and Motwani introduced locality-sensitive hashing (LSH), which hashes vectors so that near ones collide with high probability, and gave the first provable sublinear-time approximate search in high dimensions.
Graph methods grew from an observation about networks. Watts and Strogatz (1998) showed that a few random shortcuts turn a regular lattice into a "small world" with very short paths, and Kleinberg (2000) showed that if shortcuts follow the right distance-dependent pattern, a purely local greedy walk finds short paths. This is how letters pass between people in the "six degrees" experiments, and the same property is observed in real networks and brains. Malkov and colleagues applied it to search: Navigable Small World graphs (2012–2014), then HNSW (Malkov and Yashunin, arXiv 2016, TPAMI 2018), which added layers so that search starts with long hops and ends with short ones.
For compression, Jégou, Douze and Schmid (TPAMI 2011) introduced product quantization and IVF-PQ, which let a billion vectors fit in tens of GB. Facebook released Faiss (2017, Johnson, Douze and Jégou, "Billion-scale similarity search with GPUs"), which became the standard library. Google published ScaNN (Guo and others, 2020) with a quantization loss tuned for inner-product search. Microsoft's DiskANN (Subramanya and others, NeurIPS 2019) stored the graph on SSD and a compressed copy in memory, so a billion points fit on one machine with 64 GB of RAM. ANN-Benchmarks (Aumüller, Bernhardsson and Faithfull) gave a common way to compare methods. After 2022, the rise of RAG made vector databases (Milvus, Qdrant, Weaviate, pgvector, OpenSearch and others) common, and almost all of them use HNSW or IVF at their core.
how: HNSW builds a layered graph. Each vector is assigned a top layer at random with an exponentially decaying chance: layer \( l = \lfloor -\ln(u) \times m_L \rfloor \) where u is uniform in (0, 1) and \( m_L = 1 / \ln(M) \). With M = 16, about 1 in 16 nodes reaches layer 1, 1 in 256 reaches layer 2, and so on, like the levels of a skip list. Every node is on layer 0, which holds the whole dataset. Each node keeps up to M links per layer (2M on layer 0) to near neighbours.
Search starts at the entry point on the top layer. On each upper layer it does a greedy walk: look at the links of the current node, move to the neighbour closest to the query, repeat until no neighbour is closer. Then it drops one layer, keeping the same node, and continues. The upper layers have few nodes and long links, so a few hops cover large distances, like moving from a continent to a city. On layer 0 the search switches to a beam search with width efSearch. It keeps a min-heap of candidates (closest first) and a max-heap of the best efSearch results so far. It pops the closest candidate, computes distances to its unvisited neighbours, and pushes the neighbours that beat the worst current result. It stops when the closest candidate is farther than the worst result. The answer is the top k of the results. Raising efSearch widens the beam, raises recall and costs time. A typical query computes a few hundred to a few thousand distances in a graph with millions or billions of nodes.
Insertion uses the same search. A new vector searches for its neighbours with a beam of width efConstruction (often 100 to 400), then links to M of them. The choice of which neighbours to keep matters: a heuristic selects candidates that are close to the new point and not closer to an already selected neighbour than to the point itself. That keeps links in different directions, which preserves the long links that make navigation work and avoids clusters that trap the walk.
IVF takes the other route. Run k-means on the vectors to find nlist centroids (a common choice is a few times √N). Each vector goes to the list of its nearest centroid. To search, compute the distance from the query to all centroids, pick the nprobe closest, and scan only their lists. If nlist = 16,384 and N = 100 million, each list has about 6,100 vectors, and nprobe = 16 scans about 98,000 vectors, 0.1% of the data. The risk is that the true neighbour sits in a cluster that was not probed, which is why recall depends on nprobe.
Product quantization makes vectors small and distances fast. Split a vector of d = 768 numbers into m = 96 parts of 8 numbers. For each part, train 256 centroids by k-means on the dataset. Replace each part by the 8-bit id of its nearest centroid. The vector now takes 96 bytes instead of 3,072 bytes (32 times smaller). To compare a query with a stored code, build a table once per query: for each of the 96 parts, the distance from the query part to each of the 256 centroids (96 × 256 entries). The distance to any stored vector is then the sum of 96 table lookups, with no multiplication. This is called asymmetric distance computation. The price is quantization error, so systems often fetch the top few hundred candidates and re-rank them with the full-precision vectors.
Whatever the index, quality is measured the same way. Take a sample of queries, compute their exact nearest neighbours by brute force, run the approximate search, and compute recall@k. Then plot recall against queries per second while changing efSearch or nprobe. This recall-versus-speed curve, not the algorithm name, is what you compare. The distance function is part of the index: most embeddings are compared by cosine similarity, which equals the inner product after the vectors are normalized to length 1, and Euclidean distance on normalized vectors gives the same ranking.
Real systems mix these ideas. IVF-PQ (Faiss) is the classic memory-efficient design. DiskANN builds a single-layer graph (Vamana) with long-range links chosen by a pruning rule, keeps the full vectors and the graph on SSD, keeps PQ codes in memory for fast approximate steps, and reads only the nodes it visits from disk (a few dozen SSD reads per query), then re-ranks with the exact vectors.

example: Sizing first. A search service holds N = 100 million embeddings with d = 768 dimensions in 32-bit floats. The raw data is 100e6 × 768 × 4 bytes = 307 GB. An exact scan per query costs 100e6 × 768 ≈ 77 billion multiply-adds and reads all 307 GB. Even at 100 GB/s of memory bandwidth that is 3 seconds per query.
Option one is HNSW with M = 16. Each node keeps its vector (3,072 bytes) and about 2M = 32 links of 4 bytes on layer 0 (128 bytes) plus a small amount on upper layers. The index is about 3.2 KB per vector, around 320 GB. It needs a big-memory machine. A query with efSearch = 100 visits roughly 1,500 to 3,000 nodes, so about 2 million multiply-adds and, since each visited node is a random memory access of around 100 ns, roughly 0.2 to 0.4 ms of memory stalls. Recall@10 of 95 to 99% is typical for such settings on embedding data.
Option two is IVF-PQ. With nlist = 16,384, m = 96 and 8-bit codes, the codes take 100e6 × 96 bytes = 9.6 GB, small enough for one commodity server. A query computes 16,384 centroid distances (12.6 million multiply-adds), builds the 96 × 256 table, then scans nprobe = 16 lists: 98,000 codes × 96 lookups = 9.4 million table lookups. The cost is a few milliseconds. Recall@10 may be 80 to 90% on the compressed distances. Re-ranking the top 200 candidates with full vectors read from SSD (200 reads) raises it to the mid 90s.
Now trace a tiny HNSW query. Take three layers and a query Q. The entry point A on layer 2 has distance 9.0 to Q. Its only neighbour F has distance 7.5, so move to F. F has no closer neighbour, so drop to layer 1 at F. F's neighbours are C (5.2) and G (6.0); C is closest, so move to C. C's neighbours are B (5.8) and E (3.1); move to E. No closer neighbour on layer 1, so drop to layer 0 at E. Now beam search with ef = 3: E (3.1) is expanded first, and its neighbours H (2.4), I (2.9) and J (4.0) are evaluated. The results are {H, I, E}. The closest candidate, H, is expanded and finds M (2.0) and N (3.5), so the results become {M, H, I}. M is expanded next and has no unvisited neighbour that beats the worst result (2.9). I (2.9) is expanded and also adds nothing. The next closest candidate is now N at 3.5, which is farther than the worst result (2.9), so the search stops. Total distance computations: about 12 instead of the full dataset. In a real graph, with millions of nodes, the walk takes tens of hops and a few thousand distance computations.
Finally, the knob. Doubling efSearch from 100 to 200 might raise recall@10 from 96% to 98.5% and double latency. That non-linear curve (recall rising slowly while cost rises linearly) is why you set efSearch from a recall target measured on your own data.
intuition: To find the nearest café, ask locals who each point you closer, instead of measuring the distance to every café in the city.
The graph works because of two properties together. Nearby points are linked, so a walk can always make small progress toward the target. A few long links, and the layers that carry them, make the number of hops grow like the logarithm of the dataset, not like its size. The cluster approach works on the opposite idea: if the data forms groups, the neighbours of a query are almost always in the few groups whose centres are closest, so you can ignore the rest. Both bet that real data has structure, which embeddings do.
mistakes: People often think ANN returns the exact answer faster. In fact it returns an answer that is usually right, and sometimes misses a true neighbour. Recall is a number you choose and measure, and it can fall silently when data changes.
People often think HNSW is always the best choice. In fact it needs the whole graph and all vectors in RAM (or fast memory), takes a long time to build (minutes to hours for hundreds of millions of vectors), and is awkward to update. IVF-PQ or DiskANN win when memory or cost is the limit.
People often think more dimensions or a better embedding always help search quality at no cost. In fact the cost per distance grows with d, the memory grows with d, and in very high dimensions distances concentrate and neighbours become less meaningful. Many systems reduce dimensions or quantize embeddings (for example to 256 dimensions or to 8 bits) with only a small recall loss.
People often think vector search with metadata filters works the same as plain search. In fact a filter such as "category = shoes and price < 50" can disconnect the graph or empty the probed clusters. Post-filtering (search first, filter after) returns fewer than k results when the filter is selective, and pre-filtering needs a different algorithm or a fallback to brute force.
People often think the distance function does not matter. In fact the index is built for one metric. Cosine, Euclidean and inner product differ, and maximum inner product search is not a true metric (it breaks the triangle inequality); the usual fix is to normalize vectors so cosine and inner product give the same order.
friction: HNSW memory use is high (vectors plus links, a few KB each) and does not shrink easily. Build time is long and hard to parallelize without losing quality. Updates are the biggest weakness: inserts are fine, but deletes leave holes that hurt graph connectivity, so systems mark deleted nodes and rebuild periodically (or use special repair procedures as in FreshDiskANN). Concurrent insert and search need careful locking.
Recall is a moving target. The same index gives different recall on different queries; hard queries (far from the data, or in dense clusters) fare worse than average, and the 95% recall may hide a poor tail. Data drift (new kinds of documents, a new embedding model) changes the structure, so recall must be monitored with a held-out set of queries with exact answers. Changing the embedding model means re-embedding and re-indexing everything.
Filtered and hybrid search is still unsolved in general. Filters of different selectivity need different strategies (pre-filter, post-filter, filtered graph traversal, partitioned indexes), and combining vector scores with keyword scores (from an inverted index) needs fusion methods such as reciprocal rank fusion, plus tuning. Sharding adds another loss: each shard returns its local top k, and the merge needs a larger k per shard. Finally, latency is dominated by random memory or SSD access, not arithmetic, so speed depends on cache behaviour and the storage hardware, and the benchmarks that ignore this mislead.
practice: Start by measuring what you need. Build a test set of a few thousand queries with exact nearest neighbours (computed by brute force on a sample or on GPU), then choose the index by recall at your latency target, not by name. For up to a few million vectors, a flat (exact) index on a GPU or a single HNSW index is simplest. For tens to hundreds of millions, use HNSW if memory allows, IVF-PQ or DiskANN if not.
Typical HNSW settings are M = 16 to 32, efConstruction = 200 to 400, and efSearch between 50 and 500 set from the recall curve. For IVF, set nlist near \( 4 \times \sqrt{N} \) to \( 16 \times \sqrt{N} \), train it on a sample of 30 to 100 vectors per centroid, and tune nprobe for recall. For PQ, use \( m = d / 4 \) or \( d / 8 \) parts with 8 bits, or a larger scalar quantization (8-bit) when quality matters more than size. Always re-rank a shortlist with the full vectors when you compress.
Normalize embeddings when the model expects cosine similarity. Keep the embedding model version in the index metadata. Plan updates: batch rebuilds for mostly static data, or a small mutable index plus a big immutable one merged on a schedule. For filters, test the real filters at their real selectivities, and use the engine's built-in filtered search where possible.
Monitor recall in production with a shadow exact search on a sample of queries, plus latency percentiles and memory. Re-check recall after every index change, data load or model change.
tradeoffs: Choose HNSW when the index fits in RAM, you want the best recall-versus-latency curve and updates are mostly inserts. You pay for 2 to 10 times more memory than compressed schemes and slow builds. Choose IVF-PQ when memory dominates cost: it is 10 to 30 times smaller, builds quickly, and supports GPUs, but has lower recall unless you re-rank, and needs training and re-training when data shifts.
Choose DiskANN-style SSD indexes when the dataset has billions of vectors and you cannot afford the RAM. You get a few milliseconds of latency at a fraction of the cost and give up some speed and tuning simplicity: a query costs several SSD reads, and throughput depends on SSD IOPS.
Choose a flat exact index up to about a million vectors, or when you need 100% recall: a GPU can scan 1 million vectors of 768 dimensions in a millisecond or two. You give up scaling beyond that.
Choose a higher efSearch or nprobe when the cost of a miss is high (legal, medical, deduplication). Choose a lower one when results are re-ranked afterwards by a stronger model, and only need candidates; RAG pipelines often fetch 50 to 200 candidates and re-rank to the top 5.
Choose LSH only for very large streaming sets with simple memory limits, or for near-duplicate detection (with MinHash). For dense embeddings, graph and cluster methods usually give far better recall per unit of cost.
interview: How does HNSW find neighbours in logarithmic-like time? || It stacks proximity graphs: a sparse top layer with long links and denser lower layers. A search takes greedy hops on the top layers to reach the right region quickly, then does a beam search of width efSearch on the dense bottom layer. Because of the small-world structure, the number of hops grows roughly with the logarithm of N, and only a few thousand distances are computed.
Explain IVF-PQ and why it uses so little memory. || IVF clusters vectors with k-means and searches only the nprobe nearest clusters. PQ splits each vector into m parts and stores the id of the nearest centroid for each, so a 768-dimensional float vector becomes about 96 bytes. Distances to codes are summed from a per-query lookup table, with no multiplication. Re-ranking with full vectors recovers accuracy.
Your recall dropped from 97% to 90% after a data load. What do you look at? || Distribution drift or a change in the embedding model; a filter that changes the effective graph; deletions and updates that degraded the graph; clusters in IVF that have become unbalanced and need retraining; or parameters (efSearch, nprobe) that were tuned to old data. Compare against exact search on a held-out query set.
How do you handle filtered vector search with a very selective filter? || Post-filtering returns too few results, because most candidates fail the filter. Options: pre-filter and brute-force scan the small matching set; use a filter-aware graph traversal that continues until k matches are found; partition the index by the filter field. Choose by the selectivity: below a few thousand matches, brute force wins.
When would you pick DiskANN over HNSW? || When the dataset is too large for RAM (hundreds of millions to billions of vectors). DiskANN keeps compressed codes in memory and the graph and full vectors on SSD, so it serves a billion vectors on one machine with a few milliseconds latency, while HNSW would need terabytes of RAM.
Why is exact search sometimes the right answer? || For small sets (up to about a million vectors) or when 100% recall matters, a GPU or vectorized brute force is fast, simple, always correct and has no index to build or maintain. Approximate indexes add recall risk and operational cost that are not worth it below a certain scale.
quiz: What does recall@10 of 95% mean? || On average, 9.5 of the true 10 nearest neighbours appear in the ten results the approximate search returns.
Why are HNSW's layers built with exponentially decreasing probability? || It makes each higher layer a sparser sample (about 1/M of the layer below), like a skip list, so long hops on top layers cover large distances and the number of hops grows with log N.
With nlist = 4,096 and 40 million vectors, how many vectors does an IVF query with nprobe = 8 scan, roughly? || Each list has about 40,000,000 / 4,096 ≈ 9,800 vectors, so 8 lists have about 78,000 vectors, around 0.2% of the data.
A 1,024-dimensional float vector is compressed with PQ into 64 parts of 8 bits. How many bytes, and what is the compression ratio? || 64 bytes, versus 4,096 bytes for the float vector: 64 times smaller.
You have 500,000 embeddings and need exact results with no operational complexity. What do you do? || Use a flat exact search (a matrix multiplication on CPU or GPU). 500,000 × 768 is small, a scan takes milliseconds, and there is no index to build, tune or monitor.

@@ parallelism
value: A large model cannot be trained or served on one GPU, for two reasons. First, memory: with the common Adam optimizer in mixed precision, training needs about 16 bytes per parameter (weights, gradients, master weights and two optimizer moments), so a 70-billion-parameter model needs about 1.1 TB, and one GPU has 80 GB. Second, time: training such a model takes on the order of 10^24 floating-point operations, which one GPU would need hundreds of years to do. The only answer is to spread the work over many GPUs, and the question is how to cut the job into pieces.
There are three basic cuts. Data parallelism copies the whole model to each GPU and gives each a different slice of the batch. Tensor parallelism cuts each large matrix multiplication into pieces that run on different GPUs. Pipeline parallelism puts different layers on different GPUs and streams small batches through them like an assembly line. Sharded data parallelism (ZeRO and FSDP) is a fourth cut that stores each GPU's slice of the weights and optimizer state but still behaves like data parallelism. Training a frontier model combines them, for example 8-way tensor parallelism inside a server, 16-way pipeline across servers, and data parallelism across the rest of the cluster. Serving large models uses tensor, pipeline and expert parallelism too.
The layers below decide what is possible. RDMA, NVLink and InfiniBand (L3) set the cost of moving data between GPUs: about 450 GB/s per direction inside a server over NVLink on H100, but only about 50 GB/s per GPU between servers over 400 Gb/s InfiniBand. This difference decides which cut goes where. Linear algebra (L4) shows how a matrix product can be split into blocks so that the pieces are independent, or summed afterwards. Amdahl's law (L4) is the reminder that any part that does not parallelize, such as waiting for communication or pipeline idle time, limits the speed-up however many GPUs you add. For the layers above, deep learning (L1) and HPC collective communication (L1) are built on these cuts.
terms: Data parallelism (DP) — every GPU holds a full model copy and processes a different part of the batch; gradients are averaged across GPUs.
Tensor parallelism (TP) — one layer's matrices are split across GPUs, which compute pieces of the same product together.
Pipeline parallelism (PP) — consecutive groups of layers (stages) run on different GPUs, and micro-batches flow through them.
Micro-batch — a small slice of the batch that moves through the pipeline as a unit.
Pipeline bubble — idle time at the start and end of a step when some stages have nothing to do.
ZeRO / FSDP — sharding of optimizer states, gradients and parameters across data-parallel GPUs, gathering what is needed just in time.
Expert parallelism — placing the experts of a mixture-of-experts layer on different GPUs and routing tokens to them.
MFU (model FLOPs utilization) — the share of the hardware's peak arithmetic that goes into useful model computation.
history: Data parallelism is the oldest. Training on many machines with a parameter server was described by Dean and others (DistBelief, 2012). Goyal and others (Facebook, 2017) showed that ImageNet could be trained in one hour with a batch of 8,192 images on 256 GPUs, using a linear scaling rule for the learning rate with a warm-up. After that, synchronous data parallelism with all-reduce became the default, and Horovod (2018) and PyTorch DistributedDataParallel made it easy.
Models then outgrew a single GPU's memory. Pipeline ideas came first in GPipe (Huang and others, Google, 2018), which splits the batch into micro-batches to keep stages busy, and PipeDream (Narayanan and others, 2019), which interleaves forward and backward passes. In 2019, Shoeybi and others at NVIDIA published Megatron-LM, which splits the matrices of a Transformer layer across GPUs with only a few communication points, and trained an 8.3-billion-parameter model. In 2020, Rajbhandari and others at Microsoft published ZeRO, which removes the redundancy in data parallelism by sharding the states; PyTorch added a similar design as FSDP (2021–2022). Narayanan and others (SC 2021) combined tensor, pipeline and data parallelism in Megatron-LM to train a trillion-parameter model on 3,072 GPUs at about half of peak throughput.
Newer variants followed. Mixture-of-experts models (GShard 2020, Switch Transformer 2021) added expert parallelism with all-to-all communication. Long sequences led to sequence and context parallelism, including Ring Attention (Liu and others, 2023). The Llama 3 report (Meta, 2024) describes training a 405-billion-parameter model on up to 16,000 H100 GPUs with four combined dimensions (tensor, context, pipeline, data) and about 38 to 43% model FLOPs utilization, and notes that hardware failures interrupted the job on average roughly every three hours. In 2025, the Hugging Face "Ultra-Scale Playbook" and DeepSeek-V3 (which used expert parallelism, a custom pipeline schedule and FP8) added documented practice.
how: Take a model with Ψ parameters. With mixed precision and Adam, each parameter needs 2 bytes for the 16-bit weight, 2 for the gradient, 4 for the 32-bit master weight, and 8 for the two Adam moments: 16Ψ bytes, plus activations. The strategies differ in how they share this memory and how much they communicate.
Data parallelism (DP). Each of d GPUs holds all 16Ψ bytes and processes a micro-slice of the global batch. After the backward pass, each has its own gradients. An all-reduce (the next concept) averages them so that every GPU applies the same update and stays identical. The communication per step is about 2Ψ values per GPU for a ring all-reduce, independent of d, and can be overlapped with the backward pass because gradients of late layers are ready first. DP scales throughput almost linearly but does not reduce memory per GPU.
Sharded DP (ZeRO and FSDP). ZeRO stage 1 shards only the optimizer states over the d GPUs (the biggest part, 12Ψ of 16Ψ). Stage 2 also shards the gradients (reduce-scatter instead of all-reduce). Stage 3, which FSDP implements, also shards the parameters: before computing a layer, the GPUs all-gather its full weights, use them, and free them; in the backward pass they gather again. Memory per GPU falls toward 16Ψ/d. The communication grows to about 3Ψ per step (a 50% increase over DP), and it can be hidden behind compute if the layers are large enough.
Tensor parallelism (TP). Megatron-LM splits a Transformer layer so that only one all-reduce is needed per block. A feed-forward block computes \( Z = \text{GeLU}(XA)\,B \). Split A by columns across t GPUs: each computes its columns of X·A, and since GeLU acts element by element, each applies it to its own part with no communication. Split B by rows: each GPU multiplies its part of the activation by its rows of B, giving a partial result of the full output shape. The true output is the sum of the partial results, which one all-reduce computes. The attention block is split by heads in the same way. That is two all-reduces per layer in the forward pass and two in the backward pass, each of the size of the layer's activations. This traffic is large and on the critical path, so TP is used only inside a server, over NVLink, usually with t = 2, 4 or 8.
Pipeline parallelism (PP). Split the L layers into p stages of L/p layers, one stage per GPU group. The global batch is cut into m micro-batches. Stage 1 runs micro-batch 1 and passes the activations to stage 2, then starts micro-batch 2, and so on. Only the activations at the stage boundary cross the network (a point-to-point send), which is small and tolerates the slower inter-server links. But at the start of a step the later stages wait for the first micro-batch to reach them, and at the end the early stages wait for the last backward pass. This idle time is the bubble, a fraction (p − 1)/(m + p − 1) of the step. With p = 8 stages and m = 8 micro-batches, 47% of the time is idle. With m = 32, it is 18%. The 1F1B schedule (one forward, one backward in turn) limits how many activations are stored, and interleaved schedules (each GPU holds several small stages) cut the bubble further at the price of more communication.
Other cuts. Expert parallelism sends each token to the GPUs that hold its chosen experts and back, using all-to-all communication. Sequence or context parallelism splits the sequence dimension, so very long inputs fit in memory; attention then needs key and value blocks from the other GPUs, which ring attention passes around a ring while computing.
Putting them together ("3D parallelism"). A rule of thumb follows the network. Put TP inside a node, where bandwidth is highest. Put PP across nodes, since it sends little data. Put DP (with ZeRO-1 or FSDP) across the remaining GPUs. The total number of GPUs is t × p × d. The model fits when the 16Ψ bytes shared across t × p GPUs (or all of t × p × d with FSDP) plus activations fit in one GPU's memory.

  Typical placement:  TP inside a server (NVLink), PP across servers,
                      DP/FSDP across the remaining replicas
example: First, a small numeric tensor-parallel example. Let X = [1, 2], A be a 2x4 matrix with rows [1, 0, 2, 1] and [0, 1, 1, 3], and B be a 4x1 matrix with entries [1, 1, 2, 1]. Then X·A = [1, 2, 4, 7], and the output Z = 1·1 + 2·1 + 4·2 + 7·1 = 18. With two GPUs, GPU0 gets the first two columns of A, so it computes [1, 2]; GPU1 gets the last two columns and computes [4, 7]. No communication was needed. Now split B by rows: GPU0 holds rows [1, 1] and computes 1·1 + 2·1 = 3; GPU1 holds [2, 1] and computes 4·2 + 7·1 = 15. An all-reduce adds 3 + 15 = 18, the right answer. A non-linear function between the two matrix products, like GeLU, acts on each element separately, so it also needs no communication.
Second, a sizing for a 70-billion-parameter model on 64 GPUs with 80 GB each. The states need 16 × 70e9 bytes = 1.12 TB. Choose TP = 8 (one server), PP = 4 and DP = 2, which gives 8 × 4 × 2 = 64 GPUs. Each model replica uses 32 GPUs, so each GPU holds 1.12 TB / 32 = 35 GB of states, leaving about 45 GB for activations. The pipeline bubble with m = 32 micro-batches and p = 4 stages is 3/35 = 8.6%.
Third, the tensor-parallel cost. Take the hidden size h = 8,192, sequence length s = 4,096, one sequence per micro-batch, and 16-bit values. The activation tensor is 4,096 × 8,192 × 2 bytes = 67 MB. A ring all-reduce across 8 GPUs moves 2 × 7/8 × 67 MB = 117 MB per GPU, which takes 0.26 ms at 450 GB/s. A stage has 80/4 = 20 layers, with 4 all-reduces per layer in forward and backward, so 80 all-reduces, about 21 ms per micro-batch. The computation for one micro-batch on one GPU is 6 × 70e9 × 4,096 / 32 = 5.4e13 floating-point operations, which takes about 134 ms at an effective 400 TFLOPS. TP communication is therefore about 16% of the compute time if it is not overlapped. If TP were spread over the slower 50 GB/s network, the same traffic would take about 190 ms and more than double the step time, which is why TP stays inside the server.
Fourth, the ZeRO saving. For a 7.5-billion-parameter model on 64 data-parallel GPUs, plain DP needs 120 GB per GPU, which does not fit. ZeRO stage 1 needs 2Ψ + 2Ψ + 12Ψ/64 = 4Ψ + 0.19Ψ = about 31 GB. Stage 3 needs 16Ψ/64 = 1.9 GB of states. The price of stage 3 is the extra all-gather of the weights at every layer.
intuition: Split a big job by customers (data), by steps (pipeline), or by cutting each task in pieces (tensor).
The right cut depends on what is scarce. Data parallelism needs the least cleverness but copies everything. Pipeline cuts need little bandwidth but leave idle gaps. Tensor cuts keep every GPU busy but chat constantly. So put the chattiest cut on the fastest wires, and the quietest cut on the slowest wires. Almost every large training configuration is this one idea, applied to the shape of the network.
The three cuts also map onto three different costs. Data parallelism costs memory, because every GPU holds a full copy. Tensor parallelism costs bandwidth, because the GPUs must exchange partial results inside every layer. Pipeline parallelism costs idle time, because stages wait for each other at the start and end of a step. Sharding (ZeRO, FSDP) turns the memory cost into a bandwidth cost. Once you see each cut as a way to pay one cost instead of another, the choices stop looking arbitrary.
mistakes: People often think adding GPUs makes training proportionally faster. In fact each added GPU brings communication, and every part that does not overlap with compute is a serial fraction (Amdahl). Real jobs reach 35 to 55% of the peak arithmetic of the hardware, and efficiency falls as the cluster grows.
People often think model parallelism is a way to make small models faster. In fact it exists to fit models that do not fit on one GPU. A model that fits on one GPU is almost always trained faster by data parallelism alone, because it has the least communication.
People often think pipeline parallelism wastes only a small amount. In fact the bubble is (p − 1)/(m + p − 1), so a deep pipeline with few micro-batches idles a large part of the time. You need many micro-batches (at least 4 times the number of stages), which in turn needs a large global batch.
People often think FSDP and ZeRO-3 are the same as tensor parallelism because both shard weights. In fact they shard storage only: before use, the full layer is gathered on every GPU, so each GPU still computes whole layers on its own data. Tensor parallelism shards the computation itself, so each GPU computes part of every layer.
People often think the parallelism choice is only about speed. In fact it also changes the maths: DP with larger batches changes the optimal learning rate and can hurt generalization past a critical batch size, and pipeline schedules can use stale weights in some designs (PipeDream), so the choice affects convergence.
friction: Communication is the main cost. Between servers, bandwidth is about 9 times lower than inside a server, and latency is 10 times higher, so the topology of the network (rails, switches, oversubscription) shapes the best configuration. Large clusters need topology-aware placement of ranks.
Load imbalance and bubbles waste time. Pipeline stages must have equal work, but the first stage has the embedding, the last has the loss, and MoE layers vary by routing. Stragglers matter, because the step ends only when the slowest GPU finishes. Memory is also uneven: with 1F1B the first stage holds the most activations.
Failures are routine at scale. A synchronous job stops when any of its thousands of GPUs fails. Llama 3's report counted hundreds of interruptions in 54 days, most caused by hardware, so frequent checkpoints, fast restart and automatic detection of bad nodes are part of the design. Activation recomputation (checkpointing) trades about 30% more compute for large memory savings and is almost always used.
Complexity is a cost too. The configuration space (t, p, d, micro-batch size, number of micro-batches, ZeRO stage, recomputation) is large, the best choice depends on model shape and hardware, and bugs from wrong sharding are silent: the loss simply looks slightly worse. Frameworks (Megatron-LM, DeepSpeed, PyTorch FSDP, JAX with XLA sharding) automate part of it, but tuning is still manual work.
practice: Start with the simplest strategy that fits. If the model and activations fit on one GPU, use plain DDP. If only the optimizer state does not fit, use FSDP or ZeRO-1/2. If a single layer is still too large, or you need to keep the per-GPU batch small, add tensor parallelism inside the server. Add pipeline parallelism only when the model must span several servers and the network is slow.
Compute memory first: 16 bytes per parameter for Adam in mixed precision, plus activations (which grow with batch × sequence × layers), then divide by the shard factor. Use activation recomputation when memory is tight. Choose the number of micro-batches at least 4 times the number of pipeline stages. Keep TP within one server, usually 8 or fewer, and use sequence parallelism with TP to shard the activations of the non-matrix operations.
Measure MFU. A well-tuned dense-model job reaches 40 to 55%; if you see 15%, look for exposed communication, small micro-batches, data loading stalls or stragglers. Profile with the framework's tools, check that all-reduce and compute overlap in the timeline, and test the network with an all-reduce benchmark before long runs (NCCL tests).
Plan for failures: checkpoint every 10 to 30 minutes to fast storage, keep spare nodes, and test restart. For serving, tensor parallelism cuts latency for big models, pipeline parallelism raises throughput when latency is not critical, and expert parallelism fits MoE models. To learn, read the Ultra-Scale Playbook, then reproduce the small TP example above in PyTorch on two GPUs, and look at the Megatron-LM code for the column- and row-parallel linear layers.
tradeoffs: Choose data parallelism (with DDP) when the model and its optimizer state fit on one GPU. It has the simplest code and nearly linear scaling; the cost is a full copy of the model per GPU and a global batch that grows with the GPU count.
Choose FSDP or ZeRO-3 when memory is the problem but you want a simple programming model and your layers are big enough to hide the extra all-gathers. You pay about 50% more communication than DP. Choose tensor parallelism when single layers are too large or per-GPU latency matters, and the GPUs share a fast link (NVLink). You give up scaling beyond about 8 GPUs per group, because of the per-layer all-reduces.
Choose pipeline parallelism when the model spans several servers connected by slower links. You gain low-volume communication and give up 10 to 20% of the time to the bubble, plus tuning of stages and micro-batches. Choose more micro-batches to shrink the bubble, if the batch size allows; a bigger micro-batch count costs optimizer-step flexibility and activation memory.
Choose expert parallelism for mixture-of-experts models, where parameters are many but each token uses few. It cuts compute per token and brings all-to-all traffic that stresses the network, plus load-balance problems among experts.
Choose context parallelism when the sequence is so long that the activations or attention do not fit (for example 128K tokens). The cost is key-value exchange between GPUs for every attention layer. Choose recomputation when memory is the limit and you can spend about one third more compute.

@@ allreduce
value: In data-parallel training, every GPU computes gradients on its own slice of the data. Before anyone updates the weights, all gradients must be combined, usually summed or averaged, and every GPU must receive the same result. This operation is all-reduce: each of N workers starts with its own array, and each ends with the element-wise sum of all N arrays. For a 7-billion-parameter model with 16-bit gradients, each array is 14 GB, and this happens at every training step, once every few seconds, for weeks.
How all-reduce is done decides how well training scales. The obvious method sends all arrays to one node, which adds them and sends the answer back. That node's network link must carry N − 1 arrays in and N − 1 out, so the time grows with N and one link is the bottleneck. Ring all-reduce arranges the workers in a circle and cuts the array into N chunks. Each worker sends only about two arrays' worth of data in total, whatever N is, and every link in the ring is busy at the same time. Tree-based and hierarchical algorithms reduce the number of steps for very large clusters or small messages. In practice a library (NCCL for NVIDIA GPUs, RCCL for AMD, MPI in HPC) chooses an algorithm that fits the topology.
The layers below set the rules. RDMA, NVLink and InfiniBand (L3) provide the links and the way data moves between GPUs without involving the CPU, with a fast path inside a server and a slower one between servers. Graph algorithms (L3) give the ring and tree layouts: choosing the order of GPUs so that each hop uses a different physical link and no link is shared is a graph-embedding problem. For the layers above, deep learning (L1) uses all-reduce for gradient synchronization, and HPC collectives (L1) generalize it to a family of operations (reduce-scatter, all-gather, all-to-all) that tensor and sharded parallelism use too.
terms: Collective operation — a communication step involving all workers in a group, such as broadcast, reduce, all-reduce or all-gather.
Reduce-scatter — each worker ends with one chunk of the summed result, and the chunks are spread over the workers.
All-gather — each worker starts with one chunk and ends with all chunks concatenated.
Ring — an arrangement where worker i sends only to worker i + 1 and receives from worker i − 1 (mod N).
Bus bandwidth — the data rate the algorithm effectively achieves per link, defined so that results are comparable across N; for all-reduce it is 2(N − 1)/N × size / time.
Latency term (α) — the fixed start-up cost of each message, a few microseconds, which dominates small messages.
Bandwidth term (β) — the time per byte, the inverse of the link speed, which dominates large messages.
NCCL — NVIDIA Collective Communications Library, the standard implementation for GPU clusters.
history: Collective operations come from message-passing in high-performance computing. The MPI standard (1994) defined reduce, broadcast and all-reduce. Researchers studied which algorithms are best for which message sizes. Thakur, Rabenseifner and Gropp (2005) showed that for large messages the best all-reduce is a reduce-scatter followed by an all-gather, using either recursive halving and doubling or a ring, and that trees and recursive doubling are better for small messages. Patarasuk and Yuan (2009) proved the ring algorithm is bandwidth-optimal on a cluster with one link per node.
Deep learning brought the problem to a new scale. Early GPU training in 2012–2015 used parameter servers (DistBelief), which are like the naive method with several central nodes. In 2017, Andrew Gibiansky at Baidu wrote an influential blog post, "Bringing HPC Techniques to Deep Learning", explaining ring all-reduce for gradients, and the Baidu ring-allreduce library followed. Uber's Horovod (Sergeev and Del Balso, 2018) packaged it for TensorFlow, then PyTorch. NVIDIA's NCCL library, first released in the middle of the 2010s, gradually added NVLink-aware rings, multi-node support, and, in version 2.4 (2019), "double binary trees", based on a Sanders, Speck and Träff (2009) design, that give logarithmic latency with full bandwidth.
Hardware took on more of the work. Mellanox (now NVIDIA) added SHARP, which sums data inside the InfiniBand switches. NVSwitch in H100 systems supports reductions inside the switch ("NVLink SHARP"). Frameworks changed too: PyTorch DDP groups gradients into buckets (25 MB by default) and starts all-reduce as soon as a bucket is ready, so communication overlaps with the backward pass. As models grew, sharded training added reduce-scatter and all-gather as separate operations, so all-reduce is now one member of a family rather than the only one.
how: Count what must be moved. Each of N workers has an array of S bytes. After all-reduce, each needs the sum of all N arrays. A lower bound on the traffic: each worker must receive information from all others, which is at least S × (N − 1)/N bytes in, and the sum must also be spread back out, so about 2S(N − 1)/N bytes through each worker's link. Ring all-reduce meets this bound.
Step one is the cut. Each worker splits its array into N equal chunks, numbered 0 to N − 1. Workers form a ring.
Phase one is reduce-scatter, N − 1 steps. In step s, every worker i sends one chunk to its right neighbour and receives one chunk from its left neighbour at the same time, then adds the received chunk to its own copy of that chunk. The chunk number rotates so that each partial sum travels around the ring collecting contributions. After N − 1 steps, each worker holds one chunk that contains the full sum of that chunk from all N workers (worker i holds chunk i + 1, mod N). All links were busy in every step, each carrying S/N bytes.
Phase two is all-gather, N − 1 steps. Now each worker passes the finished chunk it holds to the right, and keeps the ones it receives, again each step sending S/N bytes. After N − 1 steps, every worker holds all N finished chunks, which is the full summed array.
Cost. The total sent per worker is \( 2(N - 1) \times S/N \), close to \( 2S \) for large N. The time is
\[ T = 2(N - 1) \times \left(\alpha + \frac{S}{N B}\right) \]
where \( \alpha \) is the per-message latency and B the link bandwidth. The bandwidth part, \( 2(N - 1)S/(N B) \), is nearly independent of N, which is the key property: you can add workers without making the large-message time longer. The latency part, \( 2(N - 1)\alpha \), grows linearly with N. For N = 1,024 and α = 5 µs, it is about 10 ms, which is much larger than the transfer time of a small message. That is why rings are good for large messages and small clusters, and poor for small messages at large scale.
Trees fix the latency. In a binary tree reduce, workers pair up, add, and pass the result up; after \( \log_2 N \) levels the root has the sum, and a broadcast down the tree returns it. That takes \( 2\log_2 N \) steps instead of \( 2(N - 1) \). A single tree has a problem, though: internal nodes receive from two children and send to one parent, so half the nodes (the leaves) use only one direction of their links. NCCL's double binary tree builds two trees in which leaves of one are internal nodes of the other and sends half the data over each, so all links are used in both directions. It gives full bandwidth with logarithmic latency.
Real clusters are hierarchical. Inside a server, 8 GPUs are connected by NVLink and NVSwitch at about 450 GB/s per direction. Between servers, each GPU has its own network card, usually 400 Gb/s (about 50 GB/s). A hierarchical all-reduce first reduces inside each server, then all-reduces across servers (each GPU's network card handles one slice), then broadcasts inside the server. Because the slow network only carries 1/8 of the data per card in parallel, the cluster uses all its network cards at once. NCCL chooses ring, tree or other algorithms and the number of channels at run time, depending on the message size and the topology it detects.
A useful fact for sharded training: all-reduce is exactly reduce-scatter followed by all-gather. That is why sharded data parallelism (ZeRO, FSDP) can keep the same gradient traffic as plain data parallelism. It runs the reduce-scatter after the backward pass, applies the optimizer update to its own shard only, and runs the all-gather on the updated weights. The same two building blocks, used separately, also appear inside tensor parallelism and sequence parallelism, so implementations expose them as first-class operations.
Overlap hides the cost. The backward pass produces gradients layer by layer, from the last layer to the first. As soon as a bucket of gradients is complete, the framework starts its all-reduce on a separate stream while the GPU keeps computing earlier layers. If the all-reduce for the bucket takes less time than the remaining backward compute, communication is completely hidden. The communication that cannot be hidden, mostly the first layers' gradients, shows up as step time.

example: Take 4 workers G0 to G3, each with a 4-chunk vector. G0 has [1, 2, 3, 4], G1 has [10, 20, 30, 40], G2 has [100, 200, 300, 400], G3 has [1000, 2000, 3000, 4000]. The expected result on all workers is [1111, 2222, 3333, 4444].
Reduce-scatter, step 1: in step s, worker i sends chunk (i − s) mod 4 to worker i + 1. So G0 sends chunk 0 (value 1) to G1, G1 sends chunk 1 (20) to G2, G2 sends chunk 2 (300) to G3, and G3 sends chunk 3 (4000) to G0. Each receiver adds: G1's chunk 0 becomes 10 + 1 = 11, G2's chunk 1 becomes 200 + 20 = 220, G3's chunk 2 becomes 3000 + 300 = 3300, G0's chunk 3 becomes 4 + 4000 = 4004. Step 2: G0 sends chunk 3 (4004) to G1, making 40 + 4004 = 4044; G1 sends chunk 0 (11) to G2, making 111; G2 sends chunk 1 (220) to G3, making 2220; G3 sends chunk 2 (3300) to G0, making 3303. Step 3: G0 sends chunk 2 (3303) to G1 and gets 3333; G1 sends chunk 3 (4044) to G2 and gets 4444; G2 sends chunk 0 (111) to G3 and gets 1111; G3 sends chunk 1 (2220) to G0 and gets 2222. Now G0 owns the final chunk 1 (2222), G1 owns chunk 2 (3333), G2 owns chunk 3 (4444) and G3 owns chunk 0 (1111). Each owner has added contributions from all four workers.
All-gather: in three more steps, each worker forwards the finished chunk it knows to the right. After step 3, all four workers hold [1111, 2222, 3333, 4444]. We sent 6 steps × 1 chunk = 6 chunks, or 1.5 times the array size per worker, compared with 3 arrays in and 3 out at the root in the naive method.
Now real numbers. The gradients of a 7B-parameter model in 16 bits are S = 14 GB. In a server with 8 GPUs and 450 GB/s links, ring all-reduce moves 2 × 7/8 × 14 GB = 24.5 GB per GPU, which takes 24.5 / 450 = 54 ms at full link speed. Real libraries reach 70 to 85% of that, so call it 65 to 75 ms. The naive method sends 7 × 14 GB = 98 GB into one GPU and then 98 GB out: about 0.44 s at 450 GB/s, 8 times slower. Across 128 servers with 8 GPUs each, using the hierarchical method, each GPU's network card handles a 1/8 slice, 1.75 GB, so the inter-server step moves 2 × (127/128) × 1.75 GB = 3.5 GB per card, about 70 ms at 50 GB/s. That is still large next to a backward pass of a few hundred ms, which is why overlap matters and why sharded methods and gradient compression are studied.
Last, latency. A small all-reduce of S = 1 MB on N = 1,024 GPUs by ring takes 2 × 1,023 × 5 µs = 10 ms of latency, while a tree takes 2 × 10 × 5 µs = 0.1 ms. For tiny messages (a loss value, a norm), use the tree.
intuition: Pass partial sums around a circle until everyone holds the total.
Ring all-reduce is natural because it uses every wire at the same time. In the naive method one worker does all the work while the others wait, and that one worker's link is the bottleneck. In the ring, each worker takes responsibility for 1/N of the data, so the work is shared equally, and each worker only ever talks to two neighbours, so no link is overloaded. It is the same idea as a bucket line passing water: every person does a small, equal job all the time.
mistakes: People often think all-reduce time grows with the number of GPUs. In fact the bandwidth part of ring all-reduce is almost constant in N, about 2S/B. Only the latency part grows, so for large messages doubling the GPUs barely changes the time, and for small messages it does.
People often think the ring is always the best algorithm. In fact it is best for large messages on a small number of links. For small messages or many nodes, the 2(N − 1) steps of latency dominate, and trees, recursive doubling or hierarchical schemes are better. NCCL picks automatically but can pick wrongly on unusual topologies.
People often think a faster GPU always means faster training. In fact if communication is not overlapped, a faster GPU spends the same time waiting for the network, and scaling efficiency falls. At large scale the inter-server network often sets the pace.
People often think all-reduce averages are exact like a single-GPU sum. In fact floating-point addition is not associative, so a different order of additions gives slightly different results, and the result can differ between runs or between algorithms. Training tolerates this, but bit-exact reproducibility needs fixed algorithms and settings.
People often think all workers can proceed independently. In fact all-reduce is synchronous: it completes only when every worker joins. One slow or failed worker blocks all others, and a mismatch (one GPU calling a different collective) causes a hang, not an error.
friction: The synchronous nature is the main limitation. The slowest worker sets the pace, so stragglers (a throttled GPU, a bad link, noisy neighbours) slow the whole job, and a failure stops it. At thousands of GPUs, such events occur every few hours, so jobs need monitoring, timeouts and fast restarts.
Network topology matters a lot. Bandwidth between servers is about one ninth of that within a server, so the algorithm must use the hierarchy, and the physical layout (which GPUs share a switch, rail-optimized networks, oversubscription) can change the performance by a factor of two or more. Congestion from other jobs sharing the fabric causes variance.
Overlap is hard to perfect. The first layers' gradients arrive last, so some communication is always exposed at the end of the backward pass; small buckets increase latency overhead, and large buckets delay the start. Memory for communication buffers, and the compute cores that NCCL kernels use on the GPU, compete with the model's own work.
Numerical issues remain: summing 16-bit gradients over thousands of workers loses precision, so reductions are often done in 32-bit or with careful ordering, which doubles traffic. Gradient compression (quantization, sparsification) can cut communication but can hurt convergence, and it is rarely used in large LLM training. Finally, debugging hangs in collectives is difficult, because all ranks must call the same operation in the same order, and one rank taking another path leaves the others waiting for ever.
practice: Use the framework's built-in data parallelism (PyTorch DDP or FSDP, JAX pjit) and NCCL, and do not write your own collectives. Make sure the process groups match the hardware: keep tensor-parallel groups inside a server and data-parallel groups across servers, so the large all-reduces use the right wires.
Before a long run, benchmark with the NCCL tests (all_reduce_perf) over a range of sizes. Check that the bus bandwidth is close to the link rating (for example roughly 350 GB/s or more inside an H100 server, and close to the NIC's line rate across servers), and that results are the same on all nodes. A node with a weak link shows up as a slow outlier. Set NCCL environment variables only after measuring, and log the NCCL topology and algorithm choices (NCCL_DEBUG=INFO).
Tune overlap: keep DDP bucket sizes near 25 to 100 MB, make sure gradient computation and communication run on different streams, and check in the profiler timeline that all-reduce kernels overlap with backward kernels. For sharded training, prefetch the next layer's all-gather. Reduce traffic by using bf16 gradients when stable, and reduce-scatter instead of all-reduce when using ZeRO or FSDP.
Plan for hangs: set collective timeouts, use a watchdog that dumps the state of all ranks, and checkpoint regularly. To learn the idea, implement ring all-reduce with simulated workers (as in the example) and then count steps and bytes for N = 8 and 64; then compare with the tree.
tradeoffs: Choose ring all-reduce for large messages (tens of MB and more) inside a server or a small group, where latency is small compared with transfer time. It is bandwidth-optimal and simple. Choose a tree (double binary tree) for small and medium messages or hundreds to thousands of workers, where 2(N − 1) latency steps would dominate; you pay a little in bandwidth efficiency, depending on the implementation.
Choose hierarchical all-reduce on multi-server clusters: reduce inside the server over NVLink, then across servers over the network. It uses the fast links for most of the data. The cost is added complexity and an extra pass inside the server. Choose in-network reduction (SHARP, NVLink SHARP) when your switches support it: it halves the data each GPU sends and cuts latency, but depends on hardware and software support.
Choose to overlap communication with the backward pass whenever you can, even at the cost of more memory for buffers and buckets. Choose bigger buckets for bandwidth efficiency and smaller buckets for earlier overlap; 25 to 100 MB is a normal range.
Choose lower-precision gradients (bf16 or FP8) to halve or quarter traffic when training is stable, and 32-bit when accuracy of the sum matters. Choose gradient compression only when the network is much slower than usual (cross-datacenter or slow Ethernet), because it adds computation and may change convergence.
Choose asynchronous or local-SGD style methods (workers synchronize every H steps, as in DiLoCo) when the network is slow or unreliable, at the cost of weaker convergence guarantees; choose synchronous all-reduce when you have a fast fabric and want well-understood behaviour.
interview: Derive the communication volume of ring all-reduce per worker. || Reduce-scatter takes N − 1 steps, each sending a chunk of S/N bytes; all-gather takes another N − 1 steps with the same chunk size. Total per worker: 2(N − 1)S/N, which approaches 2S and does not grow with N. This matches the lower bound for any all-reduce algorithm on links of fixed bandwidth.
Why does a naive parameter-server or root-based approach not scale? || The root must receive N − 1 arrays and send N − 1 back through its single link, so time grows linearly with N and that link is the bottleneck while others are idle. The ring spreads the load evenly so every link is used.
When is a tree better than a ring? || When messages are small or N is large. A ring has \( 2(N - 1) \) sequential steps, each paying latency \( \alpha \), whereas a tree has about \( 2\log_2 N \) steps. NCCL's double binary tree also uses both directions of every link, which recovers full bandwidth.
How does all-reduce work on a cluster of 8-GPU servers with a slow inter-server network? || Hierarchically: reduce-scatter inside each server over NVLink, all-reduce between servers where each GPU's NIC handles a 1/8 slice in parallel, then all-gather inside each server. The slow network sees only a fraction of the data, and all NICs work at once.
Training scales well to 64 GPUs but poorly to 1,024. What do you check? || Exposed communication (is overlap working, are buckets right-sized), algorithm choice (ring versus tree at this message size), network topology and oversubscription, stragglers, and whether the global batch size is too small so that each GPU has too little compute per step. Run the NCCL tests at the target scale.
Why can all-reduce results differ between runs, and does it matter? || Floating-point addition is not associative, and the order of additions depends on the algorithm, the number of channels and timing. Differences are tiny and training tolerates them, but exact reproducibility needs a fixed algorithm and deterministic settings, with some speed cost.
quiz: What do the two phases of ring all-reduce do? || Reduce-scatter: after N − 1 steps each worker holds one fully summed chunk. All-gather: after N − 1 more steps every worker holds all summed chunks.
How much data does each worker send in ring all-reduce of an array of size S across N workers? || 2(N − 1)/N × S, which is close to 2S for large N.
For 8 GPUs, a 4 GB gradient and 450 GB/s links, what is the ideal ring all-reduce time? || 2 × 7/8 × 4 GB = 7 GB per GPU, so 7/450 s ≈ 15.6 ms.
Why does ring all-reduce get slower for tiny messages on thousands of GPUs? || It takes \( 2(N - 1) \) sequential steps, each costing the fixed message latency, so for N = 1,024 and 5 µs per step that is about 10 ms, far more than the data transfer time. A tree needs only about \( 2\log_2 N \) steps.
You see the step time barely improve when moving from 128 to 256 GPUs with the same global batch size. What are two likely causes? || The per-GPU compute shrinks while the communication per step stays the same, so communication becomes a larger share (Amdahl). Also the inter-server network or latency steps may be the bottleneck. Raise the global batch or overlap and reorganize communication.

value: Training a neural network is mostly matrix multiplication, and the speed of a matrix multiplication depends on the number format. On an NVIDIA A100, 32-bit floating-point arithmetic runs at about 19.5 trillion operations per second (TFLOPS), while 16-bit arithmetic on the tensor cores runs at about 312 TFLOPS, roughly 16 times faster. Half-size numbers also mean half the memory traffic for weights, activations and gradients in flight. So running the heavy arithmetic in 16-bit, and in 8-bit on newer chips, is a large win.
But a plain switch to 16 bits breaks training. A 16-bit float has only about 3 decimal digits of precision, so a small update added to a larger weight can vanish. Its range is narrow (FP16 cannot represent anything below about 6 × 10^-8 or above 65,504), so small gradients become zero and large values overflow. Mixed precision is the set of techniques that keeps the speed and avoids these failures: do the bulk of the work in a low-precision format, but keep the numbers that must stay accurate (a master copy of the weights, the accumulation of sums, the loss, the normalization statistics) in 32 bits.
The layers below explain both halves. Floating-point numbers (L3) tell you what each format can represent: a sign, an exponent that sets the range, and a mantissa that sets the precision, and how rounding errors behave when you add numbers of very different size. Tensor cores (L3) are the hardware that makes low precision fast: they multiply small matrices of 16-bit or 8-bit values and add the products into a 32-bit accumulator in one operation. For the layers above, deep learning (L1) and GPU computing (L1) rely on it to get large models trained in weeks instead of years.
terms: FP32 — 32-bit floating point: 1 sign bit, 8 exponent bits, 23 mantissa bits; range up to about 3.4 × 10^38 and about 7 decimal digits.
FP16 — 16-bit float with 5 exponent bits and 10 mantissa bits; more precision than BF16 but a narrow range (maximum 65,504).
BF16 (bfloat16) — 16-bit float with 8 exponent bits and 7 mantissa bits; the same range as FP32 but only about 2 to 3 decimal digits.
FP8 (E4M3, E5M2) — 8-bit floats; E4M3 has more precision (maximum 448), E5M2 more range (maximum 57,344).
Master weights — a 32-bit copy of the weights that receives the optimizer updates.
Loss scaling — multiplying the loss by a large factor before the backward pass so that small gradients stay representable in FP16; the gradients are divided by the same factor before the update.
Accumulator — the register in which products are summed; tensor cores keep it in 32 bits even when the inputs are 16 or 8 bits.
Autocast — a framework feature that picks the precision of each operation automatically.
history: Early work asked how few bits neural networks need. Gupta and others (2015) showed that 16-bit fixed-point arithmetic with stochastic rounding can train small networks. Courbariaux and others (2014) studied low-precision multiplications. For years, however, GPUs ran FP32 at full speed and gave no reward for lower precision, so almost everyone trained in FP32.
In 2017, NVIDIA's Volta V100 introduced tensor cores, which run FP16 matrix multiplications at 8 times the FP32 rate. The same year, Micikevicius and others (NVIDIA and Baidu) published "Mixed Precision Training" (ICLR 2018). They proposed three techniques: keep an FP32 master copy of the weights, accumulate products in FP32, and scale the loss so that small gradients do not underflow. With these, models in many domains trained to the same accuracy as FP32 at about half the memory traffic and much higher speed.
Google's TPUs took another route. They used bfloat16, a format Google Brain introduced for TPU v2 (2017–2018) that keeps FP32's 8-bit exponent and cuts the mantissa to 7 bits. Since the range matches FP32, no loss scaling is needed. NVIDIA added BF16 and TF32 (a format with FP32's range and 10 mantissa bits) with the A100 in 2020. BF16 became the default for training large language models, while FP16 stayed common in inference.
The next step was 8 bits. Micikevicius and others (NVIDIA, Arm, Intel, 2022) proposed the two FP8 formats, E4M3 and E5M2, and NVIDIA's H100 (2022) offered FP8 tensor cores at twice the BF16 rate, with the Transformer Engine library managing the scaling. DeepSeek-V3 (December 2024) reported a large model trained mostly in FP8 with fine-grained scaling, with loss within about 0.25% of BF16 training. NVIDIA's Blackwell GPUs (2024–2025) added block-scaled formats (MXFP8, and 4-bit MXFP4 and NVFP4), which are now used in inference and under study for training.
how: Take the standard recipe with FP16 (the BF16 variant is simpler, see below). It has four parts.
First, master weights. The optimizer keeps an FP32 copy of every weight. Before each forward pass, the weights are cast to FP16 and used for the computation. The reason is in the update step: a weight near 1.0 changes by an amount like learning rate × gradient, perhaps 10^-4. The gap between neighbouring FP16 numbers near 1.0 is 2^-10, about 0.001, so adding 10^-4 changes nothing, and the update is lost. In FP32 the gap is about 10^-7, so the update survives. Many small updates add up to large changes over a training run, and without the master copy they would all be rounded away.
Second, low-precision compute with high-precision accumulation. The forward and backward matrix multiplications run on tensor cores with FP16 inputs. Each core multiplies and adds into an FP32 accumulator, so a dot product over thousands of elements does not lose accuracy. This matters: if you add numbers one at a time in FP16, the running total stalls. Adding 1.0 repeatedly in FP16 stops at 2,048, because at that size the gap between numbers is 2 and adding 1 rounds back down. The result is written back in FP16 to save memory traffic.
Third, loss scaling (needed for FP16 only). Gradients are often tiny; many fall below 6 × 10^-8, the smallest FP16 value, and become zero. The fix is to multiply the loss by a scale S (for example 2^16 = 65,536) before the backward pass. By the chain rule every gradient is also multiplied by S, which moves the whole distribution up into the representable range. After the backward pass, the gradients are divided by S (in FP32) before the optimizer step. Dynamic loss scaling adjusts S automatically: if any gradient overflows to infinity or NaN, skip the step and halve S; if 2,000 steps pass without overflow, double S. PyTorch's GradScaler does this.
Fourth, keep sensitive operations in FP32. Reductions over many elements (sums for softmax, layer normalization statistics, the loss), exponentials and some element-wise functions are numerically fragile, so frameworks run them in FP32 even inside autocast. Embeddings and the final logits are often kept in higher precision. Matrix multiplications and convolutions, which are 90% or more of the arithmetic, go to the tensor cores in low precision.
In code, this is automated. A framework feature such as PyTorch autocast keeps a table of operations: matrix multiplications and convolutions are cast to the low-precision type, while softmax, normalization and loss functions are cast up to FP32. Inputs are converted at the boundary of each operation, so the model code stays unchanged. The cast itself is cheap, but it is memory traffic, so fused kernels that read low precision and write low precision directly are preferred.
BF16 simplifies this. Because it has the same exponent range as FP32, gradients do not underflow and activations do not overflow, so loss scaling is unnecessary. The cost is a coarser mantissa: 7 bits means a relative rounding error of about 0.4% per operation, so master weights and FP32 accumulation are still needed. Most LLM training today uses BF16 with FP32 master weights and FP32 optimizer states.
FP8 training keeps the same structure but needs finer scaling. Each tensor (or each small block of values) gets its own scale factor chosen from the largest absolute value seen recently (amax), so its values fill the narrow FP8 range. NVIDIA's Transformer Engine uses per-tensor scales with a history of recent amax values. DeepSeek-V3 uses scales per 1 × 128 tile for activations and per 128 × 128 block for weights, and adds partial sums to a full-precision accumulator every 128 elements because the tensor core's internal accumulation in FP8 mode keeps limited precision. Master weights, optimizer states and sensitive operations (embeddings, attention softmax, normalization) stay in BF16 or FP32.
Memory arithmetic needs care. In mixed precision with Adam, each parameter costs 2 bytes (16-bit weight) + 2 bytes (16-bit gradient) + 4 bytes (FP32 master) + 8 bytes (two FP32 Adam moments) = 16 bytes. Pure FP32 training costs 4 + 4 + 8 = 16 bytes too. So mixed precision does not shrink the weights-and-optimizer memory; it shrinks the activations (which are stored in 16-bit), the memory traffic and the communication volume (gradients are sent in 16-bit), and it multiplies arithmetic speed.

example: Three small experiments with real FP16 numbers show why each rule exists.
First, a lost update. A weight is 1.0, and the optimizer wants to add 0.0001. The gap between FP16 numbers near 1.0 is 2^-10 = 0.000977. Half a gap is 0.00049, and the update (0.0001) is smaller than that, so 1.0 + 0.0001 rounds back to 1.0. In BF16 the gap near 1.0 is 2^-7 = 0.0078, so the loss is even worse. In FP32, the gap is 1.2 × 10^-7, and the weight becomes 1.0001. This is why the master weights are FP32. Over 1,000 steps of the same small update, FP32 reaches 1.1, and FP16 stays at 1.0.
Second, accumulation. Add 1.0 five thousand times. In FP32 the sum is 5,000. In FP16 it stops at 2,048: at that value the gap between numbers is 2.0, so 2,048 + 1 is a tie that rounds back to 2,048, and every later addition changes nothing. A dot product of 5,000 terms in FP16 would be badly wrong. Tensor cores avoid this by using an FP32 accumulator.
Third, loss scaling. A gradient value is 3 × 10^-8. FP16's smallest positive number is about 6 × 10^-8 (a subnormal), so 3 × 10^-8 rounds to 0 or 6 × 10^-8, a 100% error. Multiply the loss by 65,536 and the gradient becomes 3 × 10^-8 × 65,536 = 0.00197, which FP16 stores with a good relative accuracy (above the normal minimum of 6.1 × 10^-5). After the backward pass, divide by 65,536 in FP32 to get back 3 × 10^-8. If instead some gradient reaches 70,000 after scaling, it exceeds 65,504 and becomes infinity. The scaler sees the inf, skips this step, and halves the scale to 32,768. After 2,000 clean steps it tries 65,536 again.
Now the speed picture on an A100: FP32 (without TF32) 19.5 TFLOPS, TF32 156, BF16 312. On an H100 SXM: BF16 about 989 TFLOPS dense and FP8 about 1,979. A large model typically reaches 40 to 55% of the peak, so BF16 training runs at roughly 130 to 170 TFLOPS per A100 against 19.5 for FP32. Switching from FP32 to BF16 speeds a transformer up by roughly 5 to 10 times in practice. The step from BF16 to FP8 on H100 gives a smaller gain, 1.3 to 1.6 times, since attention, normalization, communication and the casts between formats stay in higher precision (Amdahl's law again).
intuition: Do rough work with a pencil, but keep the final ledger in ink.
The idea is natural when you notice that two kinds of numbers behave differently. Products inside a matrix multiplication are many and noisy, and their errors average out, so rough numbers are fine. The running totals and the weights are few, accumulate small changes over millions of steps, and any systematic rounding loss builds up. So you spend precision only where errors would pile up and save it everywhere else. The 32-bit accumulator and the master weights are the ink; the 16-bit and 8-bit products are the pencil.
mistakes: People often think mixed precision halves the memory of the whole training state. In fact with Adam the weights, gradients and optimizer states cost 16 bytes per parameter either way. It halves the activations and the traffic, not the persistent state. Memory for the state is reduced by sharding (ZeRO, FSDP), not by mixed precision.
People often think BF16 is just a less accurate FP16. In fact they trade differently: FP16 has more precision and little range, BF16 has the full FP32 range and little precision. For training, range matters more (no overflow or underflow, no loss scaling), which is why BF16 became the default. For inference of trained weights, FP16's precision is sometimes better.
People often think all operations can run in low precision. In fact softmax, normalization, loss functions and large reductions can lose accuracy or overflow in 16 bits, and are kept in FP32. Frameworks keep lists of such operations. Turning autocast off for a layer is a common debugging step.
People often think loss scaling changes the training mathematically. In fact it is exactly undone before the update (gradients are divided by the same scale in FP32), so the updates are the same as without it, apart from the avoided underflow. A skipped step due to overflow is the only visible effect, and it is rare.
People often think FP8 is just BF16 with fewer bits. In fact it has only 3 or 2 mantissa bits, so it needs a scale factor for every tensor or block, careful choice of format per tensor (E4M3 for weights and activations, E5M2 for gradients in NVIDIA's recipe), and master copies in higher precision. Without those, training diverges or degrades.
friction: Numerical problems are hard to see. A model that trains with a slightly higher loss, or diverges after 50,000 steps, may be suffering from rounding, not from a bug in the code. Typical causes are overflow in attention logits, a softmax or normalization running in the wrong precision, an optimizer state in 16 bits, or large outlier activations. Teams therefore monitor the maximum absolute values of activations and gradients, and the fraction of skipped steps, and compare early training curves against a higher-precision run.
Hardware and software support is uneven. BF16 needs an Ampere or newer NVIDIA GPU (or a TPU); FP8 needs Hopper or newer; FP4 needs Blackwell. Libraries and kernels differ in which operations support which format, and a missing fast kernel can make a low-precision model slower than a higher-precision one. Non-determinism from different accumulation orders makes bit-exact reproduction difficult.
FP8 and lower add overhead and risk. Scale factors must be computed (an extra pass to find the maximum), values are cast between formats, and communication of FP8 gradients is rarely safe, so gains are smaller than the raw 2× in arithmetic speed. Stability of long runs is still a research subject: small formats may behave well for 100,000 steps and fail later. Also, evaluation and serving may use a different precision from training, and the mismatch can change results slightly.
practice: In PyTorch, use `torch.autocast` with `dtype=torch.bfloat16` on Ampere or newer GPUs, and keep the model parameters and optimizer in FP32 (autocast casts on the fly) or use FSDP with a mixed precision policy that keeps FP32 master weights. On older GPUs (V100, T4) use FP16 with `GradScaler`. Do not use FP16 for large transformers if BF16 is available.
Start from the default autocast policy, which already keeps softmax, layer norm and loss functions in FP32. If the loss shows NaNs or spikes: check the scaler's scale (a scale that keeps falling means repeated overflow), find the first layer where activations become inf (use hooks or anomaly detection), and move that operation to FP32. Keep the final projection and the loss in FP32 if logits are large. Use gradient clipping in FP32.
Try FP8 only when your model is large enough that matrix multiplications dominate (hidden size of 4,096 or more), your GPUs support it, and you can compare against a BF16 baseline for a few thousand steps. Use a library that manages scaling (Transformer Engine, or the framework's FP8 recipes), keep attention and normalization in BF16, and monitor the loss gap relative to BF16; a gap below about 0.5% over time is a reasonable target.
Measure model FLOPs utilization before and after. If speed does not improve, the model may be memory-bound or limited by communication or the data loader, and extra precision tricks will not help. Keep a BF16 or FP32 reference run for debugging, and log the scale, the number of skipped steps and gradient norms in every run. To study, reproduce the three experiments in the example with NumPy float16, then train a small transformer with and without autocast and compare memory and speed.
tradeoffs: Choose BF16 mixed precision for training any large model on Ampere/TPU or newer hardware. It gives most of the speed-up with the least tuning and no loss scaling. You give up some mantissa precision, and need FP32 master weights and accumulation. Choose FP16 with loss scaling only on hardware without BF16 or where you want the extra precision for inference. You accept the work of dynamic scaling and the risk of overflow.
Choose FP8 when you train very large models on Hopper or Blackwell, and arithmetic and memory traffic are the bottleneck. Expect 1.3 to 1.6 times higher throughput than BF16, and spend engineering time on scaling and monitoring; you accept small quality risk and software complexity. Do not use FP8 for small models, where overhead dominates and the gain is small.
Choose TF32 (a one-line setting on Ampere and newer) when you cannot change code and want a speed-up of several times over FP32; it gives FP32-like range with reduced precision in matrix multiplications. Choose full FP32 for numerically sensitive science, small models, or when debugging.
Choose per-tensor scaling for simplicity and per-block (tile) scaling for stability. Block scaling costs more bookkeeping and a more complex kernel but handles outliers inside a tensor, which matters at 8 bits and below.
Choose FP32 for the optimizer states and master weights when stability matters most (it is the default). Choose BF16 optimizer states to save memory only after testing on your own model; some groups report no loss in quality, others see degradation in long runs.
interview: Why do we need FP32 master weights in mixed precision training? || Weight updates are small compared with the weights. The FP32 copy accumulates the small updates faithfully, and the low-precision copy is made by casting for the forward and backward passes.
How does loss scaling work and why is it not needed for BF16? || FP16 cannot represent gradients below about 6 × 10^-8, so small gradients become zero. Multiplying the loss by S scales all gradients by S through the chain rule, moving them into range; they are divided by S in FP32 before the update. BF16 has the same exponent range as FP32, so gradients do not underflow and no scaling is needed.
Does mixed precision reduce the memory needed for weights and optimizer state? || Not in the standard recipe. With Adam it takes 2 + 2 + 4 + 8 = 16 bytes per parameter, the same as FP32 training (4 + 4 + 8). It reduces activation memory and bandwidth. To reduce the state itself, shard it (ZeRO, FSDP) or use low-precision optimizer states.
A training run produces NaNs after 20,000 steps in BF16. Gains are 1.3 to 1.6 times in practice, with more risk and monitoring.

Multiplying 16-bit numbers is exact enough, but the sum needs the extra bits of an FP32 accumulator.
