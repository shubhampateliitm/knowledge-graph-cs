@@ queryopt
value: SQL says what result you want, not how to compute it. A query optimizer is the part of a database or query engine that turns the "what" into a "how": an execution plan with a join order, a join algorithm for each join, an access method for each table, and a place to apply each filter. The same query can have thousands or millions of correct plans, and their costs can differ by factors of 1,000 or more. A join of a 10-million-row fact table with two small tables can take seconds if the filters run first, and hours if the engine builds a huge intermediate result before filtering.
Every serious SQL system relies on one: PostgreSQL, SQL Server, Oracle, MySQL, Spark SQL (the Catalyst optimizer), Databricks, Snowflake, Trino, BigQuery. For an analytics engineer it explains why adding a filter can make a query faster, why stale statistics make a nightly job suddenly slow, and why a hint such as BROADCAST sometimes helps. For the layer above (data warehouses and distributed SQL engines) the optimizer is what makes declarative SQL practical: users write simple queries on a star schema and the engine chooses the join tree, the join types and the data movement across machines.
The layers below supply the three ingredients. Relational algebra (L3) gives the equivalences: the optimizer may rewrite a plan into another plan only if the algebra proves the result is the same, for example by moving a filter below a join. Dynamic programming (L3) gives a way to search the huge plan space by building the best plan for every subset of tables from the best plans of smaller subsets. Statistics and estimation (L4) give the numbers: histograms and distinct counts let the optimizer guess how many rows each step produces, and these guesses decide which plan looks cheapest. P versus NP (L3) explains why the search cannot be perfect for large queries, and linear programming (L4) appears at the edges, in size bounds and in resource allocation.
terms: Logical plan — a tree of relational operators (scan, filter, project, join, aggregate) that says what to compute but not how.
Physical plan — a logical plan where each operator has been given an algorithm, for example hash join or sort-merge join, and each table an access method.
Cardinality — the number of rows an operator produces; cardinality estimation is the guess made before running.
Selectivity — the fraction of rows that pass a predicate, a number between 0 and 1.
Histogram — a summary of a column's values as buckets with counts, used to estimate selectivity.
Cost model — a formula that turns estimated row counts into a number (CPU, I/O and network work) so that plans can be compared.
Memo — a data structure that stores equivalent sub-plans in groups, so a search never explores the same sub-plan twice.
Join order — the sequence in which tables are combined; since joins can be reordered, it changes the size of every intermediate result.
history: In 1970 Edgar Codd proposed the relational model, and with it the idea that users should not choose access paths. Someone had to choose them for the user. IBM's System R project (1974 to 1979) built the first working optimizer, described in "Access Path Selection in a Relational Database Management System" by Patricia Selinger and colleagues (SIGMOD 1979). Its main ideas are still the base of most optimizers: estimate costs from statistics, search with dynamic programming over subsets of tables, keep only the cheapest plan for each subset and each "interesting order" (a sort order that helps later), and mostly consider left-deep join trees.
In the late 1980s and 1990s researchers wanted optimizers that were easier to extend with new operators. Goetz Graefe built the Exodus and Volcano optimizer generators (1987 and 1993) and then Cascades (1995), a top-down search over a memo with rules and "physical properties" such as sort order and data distribution. Cascades-style optimizers are used in SQL Server, Greenplum's Orca, CockroachDB, TiDB and Apache Calcite, which many open-source engines embed. Ibaraki and Kameda (1984) had already shown that finding the best order for a join is NP-hard in general, so practical systems add heuristics.
Cardinality estimation stayed the weak point. In "How Good Are Query Optimizers, Really?" (VLDB 2015), Viktor Leis and colleagues built the Join Order Benchmark, 113 queries over the real IMDB data, and showed that estimation errors, not the cost model or the search algorithm, cause most bad plans in five major systems. Since then, work has gone in two directions: better estimators (including learned models) and runtime adaptation, which Spark added as adaptive query execution in version 3.0 (2020).
how: An optimizer works in stages. First the SQL text is parsed and analyzed (names are resolved against the catalog) into a logical plan. Second, rule-based rewrites apply transformations that are almost always good. They come straight from relational algebra: push filters below joins (see predicate pushdown), remove columns that are never used, fold constants, merge adjacent projections, and turn subqueries into joins. A selection on one table's column commutes with a join on another table, so the rewrite never changes the answer. In Spark these rules are the Catalyst batches, applied repeatedly until the plan stops changing.
Third comes the cost-based part, where the real choices are made. For each base table the optimizer lists access methods (full scan, index scan, partition-pruned scan) and estimates their cost. Then it chooses a join order. The System R method is dynamic programming over subsets: for every subset S of the tables, store the cheapest plan that joins exactly S. A plan for S is built by taking a split of S into two smaller subsets A and B, whose best plans are already known, and joining them with the cheapest algorithm. For 10 tables there are 2^10 = 1,024 subsets, which is easy. Without the restriction to left-deep trees, the number of possible join trees with cross products allowed is (2(n−1))!/(n−1)!, about 17.6 billion for n = 10, but dynamic programming never lists them one by one; it only compares splits of each subset. For a clique-shaped query graph the work grows like 3^n, so around 15 to 20 tables exact search becomes too slow.
Here statistics matter. To cost a join the optimizer must know how many rows come out. It stores, per column, the number of distinct values, the minimum and maximum, the null fraction, and often a histogram. A predicate such as price > 100 is estimated from the histogram; an equi-join A.x = B.y is estimated as \( |A| \times |B| / \max(\text{distinct}(x), \text{distinct}(y)) \). When predicates on several columns are combined, most systems assume they are independent and multiply the selectivities. This assumption is the biggest source of error, because real columns are correlated (city and state, brand and product type).
Because join ordering is NP-hard in general (this is where P versus NP enters), real systems limit the search. PostgreSQL uses exact dynamic programming up to geqo_threshold = 12 tables and switches to a genetic algorithm above that; it also stops reordering explicit JOIN syntax after join_collapse_limit = 8 items. Spark's cost-based join reorder, which is off by default (spark.sql.cbo.enabled and spark.sql.cbo.joinReorder.enabled), uses dynamic programming up to 12 tables. Other systems use greedy methods that join the pair giving the smallest result next.
The cost model then adds up estimated work. A common simplified form is: cost = rows read × cost per row + rows shuffled × network cost + rows built into hash tables × memory cost. The physical choices follow from the estimates: a broadcast join if one side is below a size threshold (Spark default 10 MB), otherwise a shuffle hash or sort-merge join; an index if the predicate is selective, a scan if not. A data movement choice, such as which side to repartition, is part of the same search in distributed engines, and Cascades-style optimizers handle it by treating data distribution as a required physical property.
Linear programming appears at the edge of this machinery. The AGM bound of Atserias, Grohe and Marx (2008) gives a worst-case upper bound on a join's output size by solving a small linear program over the query's join graph; it motivated worst-case optimal join algorithms. Optimizers that schedule work across a cluster also treat resource allocation as an LP. It is a tool for bounds and allocation, not the core of join ordering.
One more idea from System R is the interesting order. The cheapest plan for a subset is not always the best one to keep: a slightly more expensive plan whose output is already sorted on the join key may let the next join use a sort-merge join without sorting again, or may satisfy an ORDER BY at no extra cost. So the optimizer keeps the cheapest plan for each subset and also the cheapest plan for each useful sort order or data distribution. The same trick, called physical properties in Cascades, is how distributed engines decide whether a repartition step is needed.
Finally, adaptive execution corrects the plan after the first stages run and the real sizes are known (see adaptive query execution).

example: Take a fact table F with 10 million rows and two dimension tables: D1 (stores) with 1,000 rows and D2 (products) with 100,000 rows. F has a store_id and a product_id, and each F row matches exactly one store and one product. The query joins all three and filters stores with a condition that keeps 10% of them (100 stores) and products with a condition that keeps 1% (1,000 products).
Estimate the sizes. F joined with the filtered stores keeps about 10% of F: 1,000,000 rows. F joined with the filtered products keeps 1%: 100,000 rows. All three together, assuming the two filters are independent, keep 10% × 1% of F: 10,000 rows.
Now compare the two left-deep orders by the size of the intermediate result (the first join's output). Order A is (F ⋈ D1) ⋈ D2, with an intermediate of 1,000,000 rows. Order B is (F ⋈ D2) ⋈ D1, with an intermediate of 100,000 rows. Both end with 10,000 rows, but order B pushes ten times fewer rows through the second join. The dynamic programming table holds exactly this: best({F,D1}) = 1,000,000 rows, best({F,D2}) = 100,000 rows, and for the full set it takes the cheaper of the two splits, so it picks B. The third possibility, joining D1 with D2 first, is a cross product of 100 × 1,000 = 100,000 rows; most optimizers skip such plans unless no other plan exists.
Now suppose the independence assumption is wrong. If the products that pass the filter are sold only in a few stores, the real final result may be 100,000 rows, not 10,000, and the real intermediate in order A may be different too. A classic case: for a table of people, city = 'Bengaluru' has selectivity 1/500 and state = 'Karnataka' has 1/30. The optimizer multiplies them to get 1/15,000, but every Bengaluru row is also a Karnataka row, so the truth is 1/500, which is 30 times more rows than estimated. After three or four joins such errors multiply, and a plan chosen for "tiny" inputs (say a nested loop or a broadcast of a table believed to be 5 MB but really 5 GB) can fail badly. This is the situation adaptive execution is built for.
intuition: Planning a road trip: the destination is fixed, but the route you choose decides how long it takes, and your estimate of the traffic decides which route you choose.
The design is natural because of one fact: joins are commutative and associative, so the same result can be reached in many orders, and the orders differ greatly in how much data they carry along the way. Relational algebra says which rewrites are safe, so the optimizer can explore freely. The search space is large but built from small repeated pieces (best plans for subsets), which is exactly the shape dynamic programming handles. The only thing the optimizer cannot get from logic is the size of the intermediate results, so it estimates them from statistics. Everything that goes wrong in practice is a wrong estimate, a search that was cut short, or a cost model that ignores something real, such as skew.
mistakes: People often think the optimizer finds the best plan. In fact it finds the cheapest plan according to its estimates, using a heuristic search above a size limit. If the estimates are wrong, the "best" plan can be far from the real best. Leis et al. found that perfect cardinalities made even simple cost models choose good plans.
People often think the order of tables in the FROM clause or the order of joins in the SQL text controls execution. In fact a cost-based optimizer reorders inner joins freely. The text order matters only for outer joins (which are not always reorderable), when a reorder limit such as join_collapse_limit is hit, or when the engine has no statistics and falls back to the written order.
People often think a better cost model is the main fix for slow queries. In fact the model is usually good enough; the row-count estimates are the problem. A 30× error in rows changes a plan far more than a 20% error in the cost of reading a page.
People often think statistics are only for huge tables. In fact stale or missing statistics hurt most after a bulk load, when the optimizer thinks a table of 500 million rows has 0 rows and picks a nested loop or a broadcast. Run ANALYZE (or the engine's equivalent) after large changes.
tradeoffs: Choose rule-based rewrites alone when the rules are always beneficial (filter pushdown, column pruning, constant folding), because they cost almost nothing and need no statistics. Add a cost-based search when the choice depends on data size: join order, join algorithm, index versus scan. The price is the need for good statistics; Spark leaves cost-based join reorder off by default, since it needs column statistics that many tables do not have.
Choose exact dynamic programming for queries up to about 10 to 12 joined tables, where planning takes milliseconds to a second; choose greedy or randomized search beyond that, accepting a plan that may be 2 to 10 times worse than optimal in return for planning time that stays bounded. For a dashboard query that runs every second, planning time counts as part of latency; for a nightly 3-hour job, spending 5 seconds on planning is cheap.
Choose a static plan with high-quality statistics for predictable, repeated workloads, where a stable plan is itself a feature. Choose adaptive execution when sizes are hard to estimate (data behind several joins, new tables, skewed keys): you give up some plan stability, because the plan can change between runs.
Choose hints and manual join order only where you know something the optimizer cannot (a table is always small in production, a key is always skewed). Hints are brittle: when the data changes, the forced plan can become wrong while the optimizer would have adapted. Prefer fixing statistics first, then hints, and write down why each hint exists.
friction: Cardinality estimation is the central unsolved problem. Independence assumptions, uniform-distribution assumptions inside histogram buckets, and join-key correlation make errors grow with every join; Leis et al. saw errors growing exponentially with the number of joins. Learned estimators (neural networks, sampling-based methods) reduce average error but add training cost, drift as data changes, and are hard to debug; as of 2026 most production optimizers still use histograms plus independence with a few corrections such as multi-column statistics.
Statistics themselves are a cost. Computing exact distinct counts on a 10 TB table is expensive, so engines sample or use sketches such as HyperLogLog, and then the numbers are approximate. In lakehouse systems, statistics must be kept fresh as files are added; files written by other tools may carry none.
Optimization time and plan stability also hurt. A tiny change in a statistic can flip a join order and turn a 5-second query into a 5-minute one, the so-called plan regression. Databases respond with plan baselines, hints and query stores that pin a known-good plan. In distributed engines the cost model must also guess network and skew effects, which are much harder to predict than local CPU or disk cost. Finally, user-defined functions and complex expressions are black boxes: the optimizer usually uses a fixed default guess for their selectivity.
practice: Read plans before tuning. Use EXPLAIN (and EXPLAIN ANALYZE in PostgreSQL, or the Spark UI SQL tab) and compare estimated rows with actual rows at each node. The first node where they differ by more than about 10 times is usually where the plan went wrong.
Keep statistics fresh: run ANALYZE after bulk loads and large deletes; in Spark and Databricks use ANALYZE TABLE ... COMPUTE STATISTICS FOR COLUMNS on join and filter columns of large tables if you enable cost-based optimization. Keep join keys the same type on both sides, because an implicit cast on a column often blocks both statistics use and filter pushdown.
Help the optimizer with structure: filter early on partition columns, avoid wrapping filtered columns in functions, and model star schemas with small dimension tables so that broadcast joins apply. When you see a bad plan, try in this order: refresh statistics, add multi-column statistics or extended statistics where the engine supports them, rewrite the query (for example, pre-aggregate before a join), enable adaptive execution, and only then add a hint. In Spark, set spark.sql.adaptive.enabled to true (already the default since 3.2) and review the autoBroadcastJoinThreshold against your cluster memory.
quiz: What is the difference between a logical plan and a physical plan? || A logical plan is a tree of relational operators that says what to compute. A physical plan picks an algorithm for every operator (for example hash join, index scan) and is what the engine actually runs.
Why can a filter be moved below a join without changing the result? || Relational algebra shows that a selection on one input's columns commutes with the join, since the filter only removes rows from that input and the join matches the remaining rows the same way. Doing it early shrinks the join input.
In the example, why does order (F ⋈ D2) ⋈ D1 win over (F ⋈ D1) ⋈ D2? || The first join produces 100,000 rows instead of 1,000,000, so the second join handles ten times less data, while the final result of 10,000 rows is the same.
An optimizer multiplies selectivities 1/500 (city) and 1/30 (state) for fully correlated columns. By what factor does it underestimate the rows? || It estimates 1/15,000, while the truth is 1/500, so it underestimates by a factor of 30. After several joins such errors multiply.
When would you set a manual join hint instead of trusting the optimizer? || When you know a fact the statistics cannot show (for example a table is always tiny in production, or a key is heavily skewed) and fixing the statistics has failed. Write down why, because the hint can become wrong when the data changes.
interview: Why is join ordering hard, and how do optimizers cope? || The number of join trees grows super-exponentially (about 17.6 billion bushy trees for 10 tables) and finding the optimum is NP-hard in general. Optimizers use dynamic programming over subsets (about 2^n subproblems) for roughly 10 to 12 tables, then fall back to greedy or genetic search, and prune plans with cross products.
Your query got 50 times slower after last night's load. What do you check? || Compare the EXPLAIN plan with an old one and look at estimated versus actual rows. A bulk load often leaves stale statistics, so the optimizer thinks a table is small and picks a nested loop or a broadcast. Refresh statistics, check for skew in new data, and check whether a pinned plan or hint still fits.
Why do cardinality errors get worse with more joins, and what can a system do about it? || Estimates of the join output multiply the errors of the inputs, and independence assumptions are wrong for correlated columns, so the error compounds. Remedies: multi-column statistics, sampling at planning time, learned estimators, and adaptive execution that replans with real sizes between stages.
Why not always use a cost-based optimizer with a very detailed cost model? || The model is rarely the weak point; the inputs (row counts) are. A detailed model fed with wrong row counts gives confident wrong plans. Better statistics and runtime feedback help more.
How is a Cascades-style optimizer different from System R dynamic programming? || System R builds plans bottom-up over table subsets, mostly for left-deep trees. Cascades searches top-down over a memo of equivalent expression groups, applies transformation and implementation rules on demand, and tracks physical properties (sort order, data distribution), so new operators and rules are easy to add and unpromising branches can be pruned.

@@ pushdown
value: The cheapest row to process is the row you never read. Predicate pushdown moves a filter as close to the data as possible: below joins in the plan, into the table scan, and finally into the file reader or the remote database, so that rows which fail the filter are skipped before they are decoded, moved over the network or joined. Projection pushdown does the same for columns: only the columns the query needs are read. Together they decide how many bytes leave storage, and in a lakehouse that is usually the largest part of the cost of a query.
Who uses it: every engine that reads from separate storage. Spark, Trino, Presto, Hive and Databricks push filters into Parquet and ORC readers. Delta Lake and Iceberg use file-level statistics to skip whole files. JDBC connectors send a WHERE clause to PostgreSQL or MySQL instead of pulling the whole table. A query on a 73 TB event table with a date filter and two columns can end up reading a few gigabytes. The layer above, distributed SQL engines, depends on this: a scan that cannot skip anything makes the whole cluster pay for data it will throw away.
The only lower concept it needs is relational algebra (L3). Algebra proves that a selection can slide down through a join, a projection or a union without changing the answer, as long as the predicate only mentions columns of the side it moves to. Without that proof, an optimizer would not be allowed to touch the order of filters and joins. Everything else in this read is about how far down a proven-safe filter can travel, and which layer of the stack is able to understand it.
terms: Predicate — a condition that is true or false for a row, such as country = 'IN' or price > 100.
Selection and projection — selection keeps rows that satisfy a predicate; projection keeps only chosen columns.
Partition pruning — skipping whole directories or partitions (for example date=2026-10-01) because their key value cannot satisfy the predicate.
Row group — a block of rows inside a Parquet file (often 128 MB), stored column by column, with min, max and null count for each column.
Data skipping — using per-file or per-block statistics to avoid reading blocks that cannot contain matching rows.
Sargable — a predicate shape that an index or statistic can use directly, for example col = 5; a predicate such as UPPER(col) = 'A' is not sargable on col.
Dynamic partition pruning — a runtime filter built from the small side of a join and applied to the large table's scan to skip partitions.
Federated pushdown — sending filters, projections or aggregates to an external system, such as a database, so that it does the work.
history: Pushing selections down is one of the oldest ideas in query processing. Early relational systems in the 1970s, including System R and Ingres, used the algebra rule that a selection commutes with a join, and textbook optimizers teach it as the first heuristic: "do selections as early as possible". The reason was the cost of disk reads and the size of intermediate results.
The idea became more important when data moved to columnar files and to storage that is separate from compute. Columnar formats such as ORC (2013) and Parquet (2013, from Twitter and Cloudera) store min and max values per column per block, so a reader can skip blocks without decoding them. Parquet added a page index (column index and offset index, in parquet-mr 1.11, 2019) for skipping individual pages, and Bloom filters per column chunk (1.12, 2021) for equality predicates on high-cardinality columns.
On the engine side, Spark SQL's Catalyst optimizer (2015) made pushdown a standard rule and introduced the data source API, where a connector can report which filters it can handle. Spark 3.0 (2020) added dynamic partition pruning, which builds a filter at run time from a join's small side, a technique used earlier in data warehouses under the names semi-join reduction and runtime filtering. Spark 3.2 and later (DataSource V2) also pushes aggregates, limits and top-N to sources that support it. Lakehouse table formats (Delta Lake, Iceberg, Hudi) moved the statistics into the table metadata, so that skipping happens before any data file is opened.
how: Pushdown happens in three places, and each one needs a different kind of knowledge.
First, in the logical plan. The optimizer applies algebra rules. For a filter on top of a join, a conjunct (one AND-ed part) that mentions only columns of the left input moves into the left input: \( \sigma_p(R \bowtie S) = \sigma_p(R) \bowtie S \) when p uses only R's columns. A conjunct that mentions both sides stays above the join. Through a projection the filter moves down after substituting expressions. Through an aggregation it can move only if it uses grouping keys; a filter on SUM(x) must wait for the sum. Through a window function it can move only if it uses the partition keys. Non-deterministic expressions such as rand() are not moved, because evaluating them earlier changes which rows pass. The optimizer also infers new predicates: from a.id = b.id and a.id = 5 it derives b.id = 5, which can then be pushed into b's scan. Outer joins need care. For a LEFT JOIN, a WHERE predicate on the left (preserved) side can be pushed to the left input; a WHERE predicate on the right side removes the null-extended rows, so the optimizer first turns the join into an inner join and then pushes it; but a predicate written in the ON clause on the left side cannot be pushed, because it must not remove left rows. Projection pushdown works the same way: the optimizer computes the set of columns each operator needs (including the join keys and the columns of later filters) and trims every scan.
Second, in the scan. The data source receives the pushed filters and projected columns. For a partitioned table, a filter on the partition column is evaluated against directory names or the table's metadata, and non-matching partitions are never listed. For a table format such as Delta or Iceberg, per-file statistics (min, max, null count per column; Delta keeps them for the first 32 columns by default) are checked against the predicate, and files whose range cannot contain a match are dropped from the scan plan. This is cheap because it only reads metadata. The test is conservative: it may keep a file that has no match, but it never drops a file that has one.
Third, in the file reader. A Parquet reader reads the footer, then for each row group compares the filter with the stored min and max of the column. A row group with ts between 10:00 and 10:05 cannot satisfy ts > 11:00, so it is skipped without being fetched. If a page index exists, it skips pages inside the surviving groups. If a Bloom filter exists (see the Bloom filter concept) and the predicate is an equality, it rules out groups where min and max alone would not help, such as a user ID that falls inside the range of the group but is not in it. Only the requested column chunks are read, using byte-range requests (on object storage, separate GET requests with a Range header). The surviving rows are decoded and the filter is applied again row by row, because skipping is only an approximation and exact rows still have to be checked.
The contract between the engine and the source matters. In Spark's data source API, the engine offers the source a list of filters; the source accepts those it can evaluate and hands back the rest, and the engine keeps a Filter operator above the scan for anything that was not fully handled. This is why a plan can show a filter both as pushed and as a residual filter above the scan: the pushed one is a hint to skip data, and the residual one guarantees correctness. A source may also accept a filter only approximately (as row-group skipping does), and then the engine must still apply the exact filter. Because of this split, pushdown can never make a result wrong, only slower if the source ignores it.
Federated pushdown follows the same pattern against a database: the connector translates the filter to SQL and the database uses its own indexes.
The deciding factor is how the data is laid out. Min and max statistics only help if values are clustered: if every row group contains users from all countries, no group can be skipped. Sorting or clustering data by commonly filtered columns (Z-order or liquid clustering on Databricks, sort order in Iceberg) makes the ranges narrow.

example: Take an events table in Parquet, partitioned by date, with 365 partitions of 200 GB each (73 TB in total) and 100 columns of roughly equal size. The query is: SELECT campaign_id, COUNT(*) FROM events WHERE event_date = '2026-10-01' AND country = 'IN' GROUP BY campaign_id. The numbers below assume equal column widths and that the data is clustered by country within each day; they are for illustration.
Without any pushdown, the engine reads all 73 TB, decodes it, and filters at the top. At a cluster read speed of 20 GB/s that is about an hour.
Partition pruning: event_date is the partition column, so only one directory matches. Bytes to read: 200 GB. That is a reduction of 365 times, using only directory names.
Projection pushdown: the query needs 2 columns, campaign_id and country (event_date is known from the partition path and needs no read). So 2 of 100 columns: 200 GB × 2/100 = 4 GB.
Row-group skipping: suppose the day's data is written sorted by country and India is 5% of rows. The row groups containing only other countries have min and max that exclude 'IN'. About 5% of groups survive, plus one or two boundary groups: 4 GB × 5% = 0.2 GB, roughly 200 MB.
Result: 200 MB read instead of 73 TB, a reduction of roughly 365,000 times, and the query finishes in a second or two. If instead the data were not clustered by country, each row group would contain India rows, no group could be skipped, and you would read the full 4 GB: still much better than 73 TB, but 20 times worse than the clustered layout. Now add a trap: write the filter as WHERE CAST(event_date AS STRING) = '2026-10-01'. The cast hides the partition column from the pruning rule in some engines, and the scan can drop back to 73 TB. Checking the scan node in EXPLAIN (it lists PartitionFilters and PushedFilters in Spark) is how you find this.
intuition: Ask the warehouse to send only the red shirts in size M, rather than shipping everything to your house and sorting there.
Moving work to where the data lives is natural because moving data is the expensive part. Every layer of the stack knows something that the layer above does not: the plan knows the query, the table format knows file ranges, the Parquet footer knows block ranges, the database knows its indexes. Pushdown hands the question to the lowest layer that can answer it cheaply, and each layer passes down only what it can prove safe. Algebra provides the proof, so no layer needs to trust the others.
mistakes: People often think pushdown changes the query result or makes it approximate. In fact it only changes where the filter runs. Skipping by min and max is conservative (it may read extra blocks, never fewer than needed), and the exact filter still runs on the rows that are read.
People often think that if a WHERE clause exists, it is automatically pushed to storage. In fact the filter must be expressed in a form the source understands. Calls to user-defined functions, casts on the column side, expressions such as col + 1 > 10, or string functions are often not pushed. Rewrite them as col > 9 or compare the column with a constant of the same type.
People often think that min and max statistics always skip a lot. In fact they work only for clustered data. Random or high-cardinality columns such as a user ID have min and max spanning the whole range in every file, so nothing is skipped unless the data is sorted by that column or a Bloom filter is used.
People often think a filter on the right side of a LEFT JOIN is pushed below the join the same way as on the left. In fact the semantics differ: a filter in the ON clause on the preserved side cannot be pushed, and a WHERE filter on the null-supplied side converts the join to an inner join first. Putting a condition in ON versus WHERE can change both the result and the plan.
tradeoffs: Choose to rely on automatic pushdown and good file layout when your filters are on a few well-known columns (date, tenant, country). Choose to add explicit partitioning or clustering only for columns that most queries filter on. Partitioning by a high-cardinality column, such as user ID, creates millions of tiny files, and listing and opening them costs more than the scan saved; a rule of thumb is to keep partitions at least about 1 GB and files at 128 MB to 1 GB.
Choose partition pruning when a column has tens to thousands of values and is filtered in nearly every query; choose clustering (sorting, Z-order, liquid clustering) for columns with many values, where partitions would be too small. You give up write speed and some storage efficiency, because the writer must sort or rewrite files, and the clustering decays as new data arrives until you run an optimize job.
Choose Parquet Bloom filters for equality lookups on high-cardinality columns that are not sorted (device ID, user ID). Choose min/max alone for range filters on sorted columns. A Bloom filter adds file size (about 10 bits per distinct value in the row group at a 1% error rate) and does nothing for range predicates.
Choose pushing work to a remote database when the database has an index that makes the filter cheap and the result is small. Choose to pull the data into the engine when the database is a fragile production system: a pushed query can run a heavy scan on it. You trade lower data transfer for load on the source.
friction: Pushdown depends on every layer cooperating. A connector that does not implement filter or aggregate pushdown makes the engine read everything; different engines support different predicate forms; a type mismatch (comparing an integer column to a string literal) can disable the pushdown silently. Reading the plan is the only reliable check.
Statistics can be missing or wrong. Delta and Iceberg keep column statistics for a limited number of columns, so a filter on column 40 may not benefit; files written by tools that skip statistics cannot be skipped. Long string columns may store truncated min and max values, which weakens skipping. After updates and merges, files overlap again, and skipping gets worse until the table is compacted and re-clustered.
Some semantics resist pushdown: non-deterministic functions, filters that depend on aggregate results, correlated subqueries, and predicates above outer joins. Pushed filters can also have a cost: evaluating a heavy predicate in the scan can slow the reader if it is not selective, and in a remote database a pushed predicate may force a full table scan there. Dynamic filters add planning complexity and only pay off when the build side is small and selective; otherwise the runtime filter is just extra work.
practice: Check the plan, not the SQL. In Spark, look at the scan node for PartitionFilters, PushedFilters and ReadSchema; in Trino, look at the table scan constraints in EXPLAIN. Confirm that the filter you expect appears there, and compare "rows read" with "rows output" in the metrics.
Write predicates in a sargable form: compare the raw column with constants of the same type, filter on the partition column directly (event_date = '2026-10-01', not CAST or DATE_FORMAT on it), and avoid UDFs in filters. Select only the columns you need instead of SELECT *; with columnar files this is often the biggest saving.
Lay out data for your common filters: partition on a low-cardinality column used in most queries (usually date), cluster within it on one or two high-value columns, and keep file sizes healthy by compacting small files regularly. Use Bloom filters on columns used in equality lookups. In Spark, keep spark.sql.parquet.filterPushdown enabled (it is by default) and keep dynamic partition pruning on for star-schema joins. When joining a big fact table to a filtered dimension table, check that the dimension filter reaches the fact scan as a dynamic filter.
Finally, watch the join side: put selective filters in the query so that they can be pushed before the join, but do not move conditions from WHERE to ON (or the opposite) in outer joins without checking the result.
quiz: What condition must a filter satisfy to be pushed below a join through the algebra rule? || It must refer only to columns of the one input it moves into, for example \( \sigma_p(R \bowtie S) = \sigma_p(R) \bowtie S \) when p uses only R's columns. A filter that mentions both sides must stay above the join.
Why does min/max skipping fail on a randomly ordered user_id column? || Each row group contains user IDs spread over the whole range, so every group's min and max include the searched value and none can be skipped. Sorting by user_id or adding a Bloom filter fixes it.
A 73 TB table has 365 equal date partitions and 100 equal columns. A query filters one date and reads 2 columns. How much data is read after partition and column pruning? || One partition is 200 GB, and 2 of 100 columns is 2%, so about 4 GB, before any row-group skipping.
Why is a WHERE filter on the right table of a LEFT JOIN handled differently from one on the left? || A right-side WHERE filter removes null-extended rows, so the join effectively becomes an inner join and the filter can then be pushed. A left-side filter in the ON clause cannot be pushed because it must not remove left rows from the output.
Should you partition an events table by user_id so that user lookups are fast? || No. Millions of partitions create millions of tiny files, and metadata and file-open costs exceed the savings. Partition by date, then cluster or Bloom-filter on user_id.
interview: Explain the difference between partition pruning, file skipping and row-group skipping. Where does each get its information? || Partition pruning uses directory names or table metadata and drops whole partitions. File skipping uses per-file min, max and null-count statistics in the table format's metadata (Delta log, Iceberg manifests). Row-group skipping uses the Parquet footer, and page index or Bloom filters, after the file is opened. Each is conservative and cheaper than the next level down.
A query is slower after you added a CAST around a filter column. Why? || The cast makes the predicate non-sargable: the engine cannot compare the raw column with statistics or partition values, so pruning and skipping may be lost and the scan reads much more data. Compare the plan's PushedFilters and PartitionFilters before and after, and cast the constant instead of the column.
What is dynamic partition pruning and when does it help? || It builds a filter at run time from the filtered small side of a join and applies it to the large table's scan, so only partitions with matching keys are read. It helps star-schema queries where the filter is on the dimension table and the fact table is partitioned by the join key. It does not help if the dimension side is large or not selective.
Why can pushing a predicate to a remote database be a bad idea? || The database may not have an index for it, so it performs a full scan on a production system, or it may evaluate the predicate with different semantics (collation, null handling, time zones). Pushing saves network transfer but moves load and risk to the source.
How would you design file layout so that a user-ID lookup on a 50 TB Delta table is fast? || Cluster data by user ID (Z-order or liquid clustering) so each file covers a narrow ID range, give the column statistics (it must be within the indexed columns), and optionally add Bloom filters; compact small files. Then the lookup skips nearly all files using metadata alone.

@@ joins
value: A join combines rows from two tables whose key values match: each order with its customer, each ad impression with its campaign, each device with its household. In analytical queries the joins are usually the most expensive step, because the naive way to match two tables of a million rows each compares a trillion pairs. Join algorithms are the methods that avoid this. A hash join gets the cost down to roughly one pass over each input, a sort-merge join does the same by sorting, and in a cluster a broadcast join avoids moving the big table at all.
Every SQL engine has several of these algorithms, and the optimizer picks one for each join from table sizes, sort order, available memory and the cluster layout. For a data engineer the choice shows up directly in the Spark UI as BroadcastHashJoin, ShuffledHashJoin or SortMergeJoin, and it often decides whether a job takes two minutes or two hours. The layers above rely on it: batch processing, distributed SQL (MPP) engines and dimensional models all depend on star joins between a big fact table and small dimension tables being cheap.
Three lower concepts supply the machinery. Hashing and hash tables (L3) give the build-and-probe step: put one side in a hash table and look up each row of the other side in constant expected time. Sorting and external merge sort (L3) give the sort-merge join and the way to handle data larger than memory. Big-O complexity (L3) explains why the choice matters: O(n × m) for nested loops, O(n + m) for hash join, and O(n log n + m log m) for sort-merge. In a cluster, the joins also depend on the shuffle (the repartitioning step) to bring matching keys to the same machine.
terms: Equi-join — a join whose condition is equality on keys (a.id = b.id); hash and sort-merge joins need this form.
Build side and probe side — in a hash join, the input put into the hash table (usually the smaller) and the input scanned against it.
Nested loop join — compares every row of one input with every row of the other; works for any condition.
Broadcast join — copies the small table to every worker so the large table never moves.
Shuffle hash join — repartitions both inputs by join key, then runs a local hash join in each partition.
Sort-merge join — sorts both inputs by key and walks through them together like a zipper.
Grace hash join — a hash join for inputs larger than memory: first split both inputs into partitions on disk by hash, then join partition pairs one at a time.
Join skew — a few very frequent keys that send most rows to one partition and make one task much slower than the others.
history: Joins were the central cost problem of relational systems from the start. IBM's System R (1970s) used nested-loop and sort-merge joins (Blasgen and Eswaran, 1977 compared them) because memory was tiny and disks were slow. Hash joins appeared in the early 1980s: the Grace database machine in Japan (Kitsuregawa and others, 1983) partitioned both inputs by hash so that each piece fit in memory, and DeWitt and colleagues (1984) added the hybrid hash join, which keeps the first partition in memory instead of writing it out. Shapiro's 1986 paper compared the methods as main memory grew and showed that hash joins win when memory is at least about the square root of the table size in pages.
In the 1990s and 2000s CPU caches became the limit. Boncz, Manegold and Kersten (VLDB 1999) described radix partitioning to make each partition fit in the cache, and later work asked whether hash or sort-merge is faster on multicore machines (Balkesen and others, 2013; Schuh, Chen and Dittrich, 2016, found that well-tuned partitioned hash joins did best in most cases). With MapReduce (2004) and Hadoop, joins became distributed: reduce-side joins sent both tables through the shuffle, and map-side joins copied a small table to every mapper, which is the ancestor of the broadcast join.
Spark SQL (2015) made the choice automatic with a size threshold for broadcast joins, and Spark 3.0 (2020) added runtime switching through adaptive query execution. Another line of theory, worst-case optimal joins (Ngo, Porat, Ré and Rudra, 2012; the leapfrog triejoin of Veldhuizen, 2014), handles cyclic queries such as triangle counting, where any plan made of pairwise joins can produce huge intermediate results.
how: Start with the simplest method. A nested loop join runs two loops: for each row r of R, scan all rows of S and emit matches. Cost is |R| × |S| comparisons. It looks bad, but it is the only method for conditions that are not equality (a.ts BETWEEN b.start AND b.end) and it is fine when one side is tiny. With an index on S's key, the inner loop becomes an index lookup of O(log |S|) per outer row, an index nested loop join, which is the right choice when R is small and S is large and indexed (an OLTP-style lookup).
A hash join works in two phases. Build: scan the smaller input and insert each row into a hash table keyed by the join key. Probe: scan the larger input, hash each row's key, and look for matches in the table. Cost is one pass over each input, O(|R| + |S|), plus memory for the build side (roughly the size of the smaller table plus 20 to 50 percent overhead). This is where hashing contributes: good hash functions spread keys evenly over buckets, so each probe touches only a few entries. If the build side does not fit in memory, the Grace/hybrid variant partitions both inputs by hash of the key into P files on disk, so that rows with the same key land in the same pair of files; then each pair is joined in memory. The cost rises to about three passes over the data (read, write partitions, read again), which is still linear.
A sort-merge join sorts both inputs by key, then keeps one pointer in each and advances the pointer with the smaller key; when keys are equal, it emits the cross product of the equal-key groups. Cost is the sort, O(n log n), plus one linear merge. Sorting is where the external merge sort concept pays off: if the inputs are larger than memory, sorted runs are written to disk and merged. It is slower than hash join in general, but it has advantages: the output is sorted (useful for a following ORDER BY, GROUP BY or another merge join on the same key), it handles any data size with predictable memory, it is robust to skewed keys inside a task, and it needs no hash table in memory.
The algorithms must also handle join types. For an inner join, only matched pairs are output. For a left outer join, the hash join must remember which probe rows found no match and emit them with nulls; if the preserved side is the build side, the table must also track which build entries were never matched and emit those at the end. A semi join (keep rows of R that have any match in S) needs only one existence check per row and does not multiply rows when S has duplicates; an anti join (keep rows with no match) is the same test, inverted. Duplicate keys matter for cost: if a key appears 1,000 times in each input, an equi-join produces 1,000,000 rows for that key, so output size can be far larger than either input.
In a distributed engine there is one more question: where do matching rows meet? There are three answers. In a broadcast hash join, the small table is sent to every worker, which builds a hash table in memory and probes it with its local part of the big table. The big table is never shuffled. In a shuffle hash join, both inputs are repartitioned by hash of the join key so that matching keys land on the same worker, then each worker builds and probes locally. In a shuffle sort-merge join, both inputs are repartitioned the same way, and each worker sorts and merges. Spark prefers sort-merge for large inputs by default (spark.sql.join.preferSortMergeJoin is true), because it can spill gracefully to disk, and uses broadcast when one side is below spark.sql.autoBroadcastJoinThreshold (10 MB by default) or has a BROADCAST hint. If the tables are already bucketed by the join key and have the same number of buckets, or are partitioned compatibly (storage-partitioned join), the shuffle can be skipped entirely.
Choosing is the optimizer's job (see query optimization): it compares estimated sizes with the thresholds. Adaptive execution re-checks this at run time and can turn a sort-merge join into a broadcast join once the real size is known. Skewed keys are handled by splitting the oversized partition into several tasks and replicating the matching rows from the other side.

example: First a small example you can follow with a pen. R has rows (key, value): (1,a), (2,b), (2,c), (4,d). S has rows: (2,x), (3,y), (4,z), (4,w). We want R joined with S on key.
Hash join, building on R: the hash table is {1: [a], 2: [b, c], 4: [d]}. Probe with S in order. Key 2 finds [b, c], so emit (2,b,x) and (2,c,x). Key 3 finds nothing. Key 4 finds [d], so emit (4,d,z) and (4,d,w). Four output rows, and each S row was looked up once.
Sort-merge join: R is already sorted by key (1, 2, 2, 4) and so is S (2, 3, 4, 4). Pointers start at R[1] and S[2]. Since 1 < 2, advance R. Now both are 2: emit the product of the group {b, c} and {x}, giving two rows, and move past the group. Now R is at 4 and S at 3. Since 4 > 3, advance S. Both are 4: emit {d} × {z, w}, two rows. The same four rows came out, in key order.
Now a cluster decision. An impressions table has 200 GB, a campaign table has 200 MB, and the cluster has 100 executors. Broadcast: the 200 MB table is sent to each executor, about 100 × 200 MB = 20 GB of network traffic (less with Spark's peer-to-peer broadcast), and the 200 GB table is not moved. Shuffle: nearly all of 200 GB + 0.2 GB must cross the network, since each row moves to the executor that owns its key hash (about 99% with 100 executors). So broadcast moves roughly 10 times less data here, and it also avoids sorting 200 GB. If the small table were 2 GB, broadcast would move 200 GB, the same as the shuffle, and each executor would need more than 2 GB of memory for the hash table, so shuffle becomes the better choice. The break-even rule is: broadcast when small × workers is clearly less than big + small, and the small table fits comfortably in each executor's memory.
Finally, skew. Suppose 40% of the impressions have campaign_id = 0 (a default value). In a shuffle join, all those rows go to one partition. If the other 60% is spread over 199 partitions at 0.3% each, the one partition has about 130 times more data than a typical one, and the stage finishes only when this one task does. Adaptive execution splits this partition into several sub-partitions, each joined with a copy of the matching rows of the other side.
intuition: Matching name tags at a conference: look up each guest in a prepared directory (hash), or line up both groups alphabetically and walk along together (merge).
The design is natural because matching is a search problem, and there are only a few ways to search: compare everything (nested loop), build a lookup structure (hash), or sort so that equal items are neighbours (merge). Each is the best when one resource is plentiful: memory favours hashing, sorted order or disk favours merging, and a tiny side favours copying it everywhere. In a cluster, the same three ideas appear again, with network traffic as the main cost.
mistakes: People often think a hash join is always faster than a sort-merge join. In fact hash join is faster when the build side fits in memory, but with a large build side it must spill to disk, and sort-merge with already sorted or bucketed inputs can win. Spark prefers sort-merge by default for stability, not for speed.
People often think a broadcast join is always better when one table is "small". In fact the broadcast table must be collected on the driver, sent to all executors and built into a hash table in each of them. A table of 1 GB on disk can expand to several GB in memory, and broadcasting it to 500 executors costs 500 GB of traffic; failures with out-of-memory on the driver are common. Spark also refuses to broadcast tables over 8 GB.
People often think the join order in SQL text is the join order that executes. In fact the optimizer reorders inner joins and chooses the algorithm and the build side from size estimates, so a wrong estimate gives a wrong algorithm even when the SQL looks sensible.
People often think that joins with a skewed key are slow because of the join algorithm. In fact the problem is the partitioning: all rows of one key must meet in one task for a shuffle join, no matter which local algorithm is used. Fixes act on distribution (salting, splitting, broadcasting the other side), not on the local algorithm.
tradeoffs: Choose a broadcast hash join when one side is small, say under a few hundred MB, and the other is large: it removes the shuffle of the large side and is immune to skew on the large side. You pay with memory on every executor and a risk of failure if the size estimate is wrong; keep the threshold well below executor memory per task.
Choose a shuffle sort-merge join when both sides are large (tens of GB or more): memory use is bounded because sorting spills to disk, and the output is sorted. You pay for sorting both sides, which can cost more CPU than hashing. Choose a shuffle hash join when one side is several times smaller than the other (Spark requires roughly 3 times, or a hint), but still too big to broadcast, and the partitions of the build side fit in memory; you give up the safe spilling of sort-merge.
Choose bucketing, storage-partitioned joins or co-partitioned tables when the same two big tables are joined repeatedly on the same key (daily jobs joining events to a user table). You pay at write time (bucketed writes are slower and need the same bucket count and key) and lose flexibility, but you save the shuffle on every read.
friction: Joins are where distributed jobs fail. Skew is the best known problem: one hot key makes one task run for hours, and automatic skew handling works only for some join types and not for every key pattern. Out-of-memory errors from broadcast or hash tables are common when the optimizer's estimate is too low. Spills to disk make hash joins several times slower, and a too-high number of partitions creates many small tasks and overhead.
Estimates are the other source of pain. If statistics are missing, a table on object storage may be estimated by its file size, which is compressed and says little about the in-memory size. Joining after a filter or an aggregation makes estimation harder. Null keys also surprise people: nulls never match in an equi-join, but they can all hash to the same partition and cause skew.
Some joins do not fit the standard algorithms. Non-equi joins (range conditions) fall back to nested loops, which can be a cartesian product of billions of pairs. Cyclic multiway joins can produce intermediate results far larger than the output, which is the motivation for worst-case optimal joins; these are in research systems and a few engines but not in mainstream Spark.
practice: Read the join node in the plan first. In the Spark UI, check which join was chosen, the size of each side, the number of output rows and the spill metrics. If a join that should be a broadcast is a sort-merge, check statistics and the threshold; if a broadcast fails, lower the threshold or remove the hint.
Make small tables small before joining: select only needed columns and filter first, because the broadcast decision is made on the size after pruning. Use the BROADCAST hint only for tables that are small by construction (dimension tables), and prefer fixing statistics over adding many hints. Join on keys of the same type and avoid functions on the key.
For skew, turn on adaptive skew handling (spark.sql.adaptive.skewJoin.enabled, default true), then look at the key distribution: filter out null and default keys and handle them separately (join the rare real keys, treat the default key as a special case), or salt the hot keys. For repeated joins of the same big tables, bucket both by the join key. For very large joins, reduce the data first: a pre-aggregation, a semi-join with a Bloom filter (Spark 3.3 runtime filters), or a dynamic partition filter from the small side, before the shuffle starts.
quiz: What are the two phases of a hash join and which input is used for each? || Build: insert the smaller input into a hash table by join key. Probe: scan the larger input and look up each key in the table. Cost is about one pass over each input.
Why does a Grace hash join partition both inputs by the same hash function? || Rows with equal keys must land in the same partition number on both sides, so each partition pair can be joined independently in memory, without looking at any other partition.
A 200 GB table is joined to a 200 MB table on 100 executors. Roughly how much network data does broadcast move compared with shuffle? || Broadcast moves about 100 × 200 MB = 20 GB. Shuffle moves nearly the whole 200 GB. So broadcast moves about 10 times less here.
Why is a sort-merge join sometimes preferred even though hash join needs fewer operations? || Sorting spills to disk with bounded memory, so it works at any size without out-of-memory errors; its output is sorted for later operators; and it is already cheap if the inputs are pre-sorted or bucketed.
You must join two 5 TB tables every day on user_id. How can you avoid paying the shuffle every time? || Write both tables bucketed (or clustered) by user_id with the same number of buckets, so the join can run with no shuffle. The cost moves to write time and to keeping the layout consistent.
interview: How does Spark choose a join strategy, and how can you override it? || It checks hints first (BROADCAST, MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL, in that precedence), then picks a broadcast join if a side is below the broadcast threshold, then shuffle hash if configured and one side is much smaller, then sort-merge for equi-joins, and a broadcast nested loop or cartesian join otherwise. Hints are not guaranteed if the join type does not support the strategy.
A join stage has 199 tasks finishing in a minute and one running for an hour. What is wrong and what do you do? || This is key skew: one key (often null or a default value) sends most rows to one task. Check the key histogram; enable adaptive skew join, filter or isolate the hot key, salt it, or broadcast the smaller side if it is small enough.
Why can a hash join be much slower than expected even when the optimizer is right about the algorithm? || The hash table may not fit in memory and spill, or have poor cache locality (random access into a large table, one cache miss per probe), or the key hashes badly. Partitioned/radix joins and smaller build sides help.
Explain a case where a nested loop join is the right plan. || When the condition is not equality (range or inequality joins), or when the outer side has a handful of rows and the inner side has an index, so index nested loop does a few lookups instead of scanning or building anything.
Why do worst-case optimal joins exist, and when do they matter? || A sequence of pairwise joins on a cyclic query, such as triangles in a graph, can build an intermediate result much larger than the final answer. Worst-case optimal algorithms process one attribute at a time and keep the work within the AGM bound of the output size. They matter for graph-like and multiway cyclic queries, not for ordinary star joins.

@@ shuffle
value: Many computations need all rows with the same key in one place: a join needs every order next to its customer, a group-by needs every row of a group on one machine, a sort needs ranges of keys on different machines in order. But the data starts spread across hundreds of machines in whatever order it was stored. The shuffle is the step that fixes this: every machine splits its data by key, sends each piece to the machine that owns that key, and each machine collects its pieces from all the others. It is an all-to-all exchange over the network.
It is the most expensive and the most failure-prone step in Spark, MapReduce, Flink and distributed SQL engines. Everything else in a job is local and streams through memory; the shuffle writes to disk, uses the network, and makes every downstream task wait for all upstream tasks. In the Spark UI, an "Exchange" node in the SQL plan or a stage boundary in the DAG is a shuffle. When a job is slow, the cause is often a shuffle that is too big, too skewed, or split into the wrong number of pieces.
Four lower concepts do the work. Hashing (L3) decides which receiver owns a key: partition = hash(key) mod R, so equal keys always meet. Sorting (L3) is used on the map side to group records by destination and, for sort-based operations, by key inside each destination. File systems (L3) give the local disk where each task's output is written, with sequential appends and an index of offsets, so that the output survives a retry of a reader. TCP (L3) carries the data between machines, with its flow control and retransmission, and its limits shape the design (many small connections, many small transfers, and congestion when thousands of senders reply at once).
terms: Map side and reduce side — the producer tasks that write partitioned output (map) and the consumer tasks that fetch their part of it (reduce); in Spark, the stage before and after the shuffle.
Partitioner — the rule that maps a record's key to one of R reduce partitions, usually hash(key) mod R, or range boundaries for sorting.
Shuffle block — the piece of a map task's output that is destined for one reduce partition; there are M × R blocks for M map tasks and R reduce tasks.
Spill — writing in-memory data to disk when the task runs out of execution memory, then merging the pieces later.
Combiner (map-side combine) — partial aggregation on the map side before the shuffle, so fewer records are sent (for example, summing counts per key within one task).
External shuffle service — a long-lived process on each machine that serves shuffle files, so they remain available after the executor that wrote them has gone.
Skew — a few keys carrying far more data than others, so a few reduce tasks receive most of the shuffle.
Push-based shuffle — an optimization in which map tasks push blocks to a merger on the reducer's side, so reducers read a few large merged files instead of many small blocks.
history: Shuffle appears in the MapReduce paper by Dean and Ghemawat (OSDI 2004). Map outputs were partitioned by hash, sorted by key, written to the mapper's local disk, and fetched by reducers over HTTP; a combiner function could pre-aggregate. This sort-and-merge design was robust and simple, and Hadoop kept it for years.
Spark (2012) initially used a hash-based shuffle in which each map task wrote one file per reduce partition. With M map tasks and R reducers this made M × R files, and the file-system overhead and random disk reads became a bottleneck; a "consolidation" option reduced this to cores × R files. In Spark 1.2 (December 2014) the default became sort-based shuffle: each map task writes one data file sorted by partition id plus one index file, so there are 2 × M files. Project Tungsten (2015) added an unsafe writer that sorts serialized records in binary form without creating objects.
Large clusters exposed more limits. Facebook's Riffle (EuroSys 2018) merged many small map outputs on each machine before reducers fetched them. LinkedIn's Magnet (VLDB 2020) pushed blocks to remote mergers, and a version of it went into Spark 3.2 (2021) for YARN. Other systems moved shuffle data off the compute nodes into dedicated services: Facebook's Cosco, and the open-source Apache Celeborn and Uniffle, which are used in Spark and Flink to make shuffle data survive node loss and to avoid local-disk limits. Adaptive query execution (Spark 3.0, 2020) added run-time control of the number of partitions and splitting of skewed ones.
how: A shuffle has a write phase and a read phase, separated by a barrier: no reducer starts reading until the map stage that feeds it is complete (Spark's default, for batch).
Write phase. Each map task processes its input partition and, for every output record, computes the destination partition id with the partitioner. For a hash partitioner this is hash(key) mod R (Spark SQL uses a Murmur3 hash of the exchange columns); for a sort it is a range found by sampling the key distribution first, so that partition 0 gets the smallest keys and so on. If a combiner applies (a sum, count, min, max), records with the same key are merged in an in-memory hash map before being written, which can shrink the data by a large factor when keys repeat. Records are buffered in memory. When the buffer is full (execution memory is limited), it is sorted by partition id, and by key if the operation needs sorted output, and spilled to disk as a sorted run. At the end of the task the runs are merged into one data file, in partition order, together with an index file that stores the byte offset of each partition. This is where sorting is used: an external merge sort whose first sort key is the partition id. Spark has a shortcut, the bypass writer, when there is no combiner and R is at most 200 (spark.shuffle.sort.bypassMergeThreshold): it writes R small files and concatenates them, skipping the sort. Data is serialized and usually compressed (LZ4 by default) before it is written, because disk and network are the cost.
The files are written on the local disk of the executor machine (file systems at work). Sequential appends are fast, and the index lets any reader jump to its partition with one seek. Because the files are on disk, a retry or a later reader does not need the map task to run again, unless the machine is lost.
Read phase. Each reduce task asks the scheduler where the map outputs for its partition live, then sends fetch requests for its block from every map output: R reducers each contact up to M mappers, so the cluster handles up to M × R fetches. Requests are grouped per remote machine and sent over TCP, with limits on the data in flight (Spark's spark.reducer.maxSizeInFlight defaults to 48 MB) so that one task does not flood the network or its own memory. Blocks that are local are read from disk directly. The reducer merges the blocks it receives: for an aggregation it inserts them into a hash map (or sorts and merges, for a sort-merge join or a sort), spilling if memory runs out.
The reduce side differs by operation. For a group-by, the reducer builds a hash map from key to running aggregate and merges the incoming partial aggregates into it. For a sort, it merges the incoming blocks, which are already sorted within each map output, with a k-way merge. For a sort-merge join, it sorts or merges both inputs' blocks by key and walks them together. In each case, the shuffle only delivers the right rows to the right task; the local algorithm then does the actual work.
Failure handling. Shuffle files live on the map side's disk. If a machine dies, its map outputs are lost, a reducer gets a fetch failure, and the scheduler re-runs the lost map tasks, which may trigger a cascade if those tasks themselves depended on earlier lost shuffles. An external shuffle service lets files outlive the executor process, which is what makes dynamic allocation (removing idle executors) possible.
The network part, TCP, shapes the cost: thousands of reducers fetching from the same mapper at once can overload its network link and cause packet loss and timeouts (called incast), and small fetches waste round trips. So engines batch requests, limit in-flight data and reuse connections.
Tuning knobs act on the number of partitions R: too few and each reduce task gets a huge partition, spills, and may run out of memory; too many and the M × R blocks are tiny, with scheduling and fetch overhead dominating. Adaptive query execution measures actual partition sizes after the map stage and merges small adjacent partitions up to a target size (64 MB by default), or splits a skewed partition.

example: A job aggregates 1 TB of compressed shuffle data. Suppose it has M = 10,000 map tasks and R partitions. Spark SQL's default is 200 partitions (spark.sql.shuffle.partitions).
With R = 200, each reducer gets 1 TB / 200 = 5 GB. That does not fit in the memory of a typical task (a few GB per core), so every reducer spills heavily, the stage is slow, and tasks may fail with out-of-memory errors. The number of blocks is 10,000 × 200 = 2 million, each averaging 500 KB.
With R = 10,000, each reducer gets 100 MB, which fits in memory. The blocks are now 10,000 × 10,000 = 100 million, each averaging 10 KB. Each reducer must make 10,000 fetches for 100 MB of data. At roughly a millisecond per request that is about 10 seconds of per-request overhead per reducer before the data time, and the map-side index files must serve 100 million small reads.
The middle choice is R = 2,000: 500 MB per reducer, 20 million blocks averaging 50 KB. With adaptive execution you can start with a large R (say 10,000) and let the engine merge small neighbours until each partition is near the advisory size of 64 MB, so the final number follows the data size.
Now the combiner. A job counts events per campaign with 100 map tasks. Each task reads 1 million events, but only 5,000 distinct campaigns appear inside it. Without a combiner each task shuffles 1 million records, 100 million in total. With a map-side combine each task shuffles at most 5,000 records, 200 times fewer, 500,000 in total. This is the difference between reduceByKey and groupByKey in the RDD API, and Spark SQL's partial HashAggregate does it automatically for aggregates that can be merged.
Last, a skew check: if one campaign has 30% of all events, 30% of the map outputs go to one reducer. With R = 10,000 and a mean partition of 100 MB, that reducer receives about 300 GB if the total is 1 TB. No setting of R fixes this; the combiner (if it applies), splitting the key (salting) or AQE's skew handling does.
intuition: Every clerk sorts their pile of papers into labelled bins by the first letter; then the clerk for each letter walks around and collects that letter's bin from everyone.
The design follows from one constraint: a single machine cannot see all rows of a key unless someone sends them. The cheapest scheme that works for any data is to agree on a rule (hash of the key) that every sender can compute locally, without talking to the others, so that all rows with the same key go to the same place. Writing the pieces to disk first decouples the two sides: the senders finish and the receivers can fetch later, retry, or use another copy. The cost is that data is written once and read once across the network, and that every receiver needs a piece from every sender.
mistakes: People often think a shuffle is a network copy only. In fact it is also serialization, compression, sorting, a disk write, a network transfer, a disk read and often a second sort or hash build on the reduce side. Disk and CPU are usually as important as the network.
People often think more partitions always means more parallelism and so faster jobs. In fact the number of fetch blocks grows as M × R. Past a point, per-task overhead and tiny blocks dominate, and the cluster is busy with metadata instead of data. Aim for partitions of about 100 to 200 MB after compression, or let adaptive execution coalesce them.
People often think a shuffle happens in every Spark job. In fact narrow operations (map, filter, projection, a join against a broadcast table, a join of already co-partitioned data) need no shuffle. Wide operations (group-by, distinct, repartition, most joins, sort) do. Removing a shuffle is the best speed-up.
People often think skew can be fixed by increasing the number of partitions. In fact all records of one key go to one partition by definition. More partitions spread the other keys thinner but the hot key's partition stays as big as before.
tradeoffs: Choose a hash partitioner when you need equal keys together and do not need order (joins, group-bys, distinct); choose a range partitioner when you need globally sorted output or range queries, accepting an extra pass to sample the keys, and a risk of uneven ranges if the sample is not representative.
Choose a small number of large partitions when the data is small or the job is memory-light, so that fixed overhead per task stays low; choose many smaller partitions when the data is large or each record is heavy, so that each task fits in memory. A good working range is 100 to 200 MB per partition, which for 1 TB means 5,000 to 10,000 partitions; adaptive coalescing lets you set the upper bound and let the engine trim it.
Choose the classic local-disk shuffle with an external shuffle service for clusters with fixed machines and reliable disks: it is simple and has no extra component. Choose a remote or push-based shuffle service (Magnet-style push, Celeborn, Uniffle) when you have thousands of tasks per stage, spot or preemptible machines, or machines with little local disk; you gain stability and fewer small reads, and you pay in an additional system to run and in extra network and storage cost.
Choose to avoid the shuffle when you can: broadcast the small side of a join, bucket tables by the common key, pre-aggregate before the shuffle, or filter earlier. You give up some flexibility and sometimes memory, but a removed shuffle is both faster and safer than a tuned one.
friction: The shuffle is an all-to-all pattern, so cost grows with cluster size: M × R blocks, many connections, and a barrier that makes the whole stage wait for its slowest task. Stragglers (slow machines, skewed partitions) therefore decide the job time. Spilling to disk makes each pass several times slower than memory, and a reduce task that cannot fit its data in memory may fail after hours of work.
Failures are expensive. Loss of one machine loses its map outputs, forcing recomputation of those tasks, and if upstream shuffles were also stored there, the recomputation can cascade. Long jobs on spot instances may spend more time recomputing than computing. Remote shuffle services reduce this but add their own failure modes and cost.
Small files and small blocks are a quiet limit: with tens of thousands of tasks on each side, the number of blocks reaches billions, and random reads of a few kilobytes are slow on hard disks and still costly on SSDs because of request counts. The network can also be a limit, especially for the cross-rack traffic of all-to-all patterns, and in cloud settings where network bandwidth per instance is capped.
practice: Find the shuffles first. In the Spark UI look at stages with large "Shuffle Read" and "Shuffle Write", spill (memory and disk), and a long tail between the median and maximum task duration; in the SQL tab, look for Exchange nodes. Count how many your query has and ask if any can be removed.
Reduce data before the shuffle: filter and select only the needed columns early, use aggregations that combine on the map side (in SQL it is automatic; in RDDs use reduceByKey or aggregateByKey, not groupByKey), and use a broadcast join for small tables. Keep serialized records small and prefer columnar formats and built-in types over objects.
Set the number of partitions from the data: aim for 100 to 200 MB per partition; keep adaptive execution on (it is on by default since Spark 3.2) and give it a larger initial partition count if the shuffle is big, because it can merge but not split other than skewed ones. Watch for skew in the task duration histogram and fix it at the source: handle null and default keys separately, salt a hot key, or let AQE split it.
For clusters with unstable nodes, use an external shuffle service or a remote shuffle service so that executors can be lost without losing shuffle data, and keep shuffle data on local SSDs, not network disks.

value: A query optimizer plans before it runs, using statistics that are often old, missing or wrong. If it believes a filtered table has 2 GB when it has 6 MB, it picks a slow join and a poor number of partitions, and nothing can correct that while the query runs. Adaptive query execution (AQE) changes this: the engine runs the query in stages, measures the real size of each stage's output, and re-plans the rest of the query with the facts instead of the guesses.
In Spark this is a framework that has existed since version 3.0 (2020) and has been on by default since 3.2. It does three main things. It coalesces many small shuffle partitions into fewer, right-sized ones. It switches a planned sort-merge join to a broadcast join (or to a shuffled hash join) when one side turns out small. And it splits a skewed partition into several tasks so one slow task does not hold the whole stage. Similar ideas appear in Oracle (adaptive plans), SQL Server (adaptive joins) and other engines.
For the layer above (distributed SQL and lakehouse engines), AQE turns tuning from a static, per-query chore into a runtime property: the same query can run well on today's small partition and on next month's large one, and a default of 200 shuffle partitions is no longer a trap. Two lower concepts make it work. Statistics and estimation (L4) are not the guess this time but exact measurements: bytes and rows per partition from the finished stage. Relational algebra (L3) guarantees that the remaining plan can be rewritten (a different join type, fewer partitions) without changing the answer. The shuffle supplies the natural place to stop and look: the barrier between two stages, where all data is already materialized.
terms: Query stage — a piece of the plan that ends at a shuffle or broadcast boundary; AQE runs stages from the leaves up and treats each finished stage as a source of exact statistics.
Materialization — a stage has finished and its output (shuffle files) exists, so its size is known.
Map output statistics — the byte size (and row count) of each reduce partition, reported by the finished map tasks to the driver.
Coalescing — merging adjacent small shuffle partitions into one reduce task, to avoid thousands of tiny tasks.
Advisory partition size — the target size for a partition after coalescing or splitting (64 MB by default in Spark).
Skew join optimization — splitting an oversized partition into several smaller tasks and giving each a copy of the matching partition from the other join side.
Local shuffle reader — a reader that reads shuffle files on the same machine without going over the network, used after a sort-merge join becomes a broadcast join.
Re-optimization — running the optimizer again on the unfinished part of the plan after new statistics arrive.
history: Fixing plans at run time is an old idea, because the weakness of estimates was known from the 1970s. Kabra and DeWitt (SIGMOD 1998) proposed mid-query re-optimization: collect statistics during execution and, if they differ greatly from the estimates, stop and re-plan. Eddies (Avnur and Hellerstein, SIGMOD 2000) went further and routed each tuple adaptively between operators. IBM DB2's progressive optimization (Markl and others, 2004) placed checkpoints in the plan that validated cardinalities and triggered re-planning. Deshpande, Ives and Raman surveyed the field in "Adaptive Query Processing" (2007). Commercial databases used limited forms: Oracle 12c adaptive plans (2013) and SQL Server 2017 adaptive joins.
Distributed batch engines suited the idea well because they already materialize data between stages. Early prototypes of adaptive execution appeared in the Spark 2.x era, and the framework was rebuilt for Spark 3.0 (June 2020) on top of the Catalyst optimizer, with coalescing, join conversion and skew handling. It was enabled by default in 3.2.0 (October 2021), which added the local shuffle reader fixes, dynamic join selection and more rules. Spark 3.3 and later added further options (for example, forcing skew optimization and optimizing skew in rebalance).
how: Without AQE, Spark creates the whole physical plan before it starts. With AQE, the plan is wrapped in an adaptive plan node and is built and run in rounds.
Round 1: the planner splits the plan at every exchange (shuffle) and broadcast into query stages. It starts all stages that do not depend on other stages (the leaves) and waits for them to finish. When a map stage finishes, its tasks have reported the exact size of every output partition to the driver. This is the map output statistics, which is a measured, not estimated, value of bytes and rows.
Round 2: the driver takes those exact sizes, plugs them into the logical plan as statistics for the finished part, runs the optimizer rules again on the rest, and creates a new physical plan for the remaining stages. Then it launches the next ready stages and repeats. The final plan is stitched together from stages that were chosen with the best knowledge available at each point.
Three rules do most of the work.
Coalescing shuffle partitions. The user sets a high initial count (the default is spark.sql.shuffle.partitions = 200; you can set a larger initial number with spark.sql.adaptive.coalescePartitions.initialPartitionNum). After the map stage, AQE reads the sizes and merges adjacent partitions until each has about the advisory size of 64 MB. Merging adjacent partitions is safe for a hash shuffle, since any group of hash buckets is still a valid partitioning, as long as all inputs of a join are merged the same way. By default Spark also tries to keep enough parallelism (parallelismFirst is true since 3.2): the target is limited so that the cluster is not left idle, with a floor of 1 MB. Because the merge only joins neighbours and reads several small blocks inside one task, the data does not move again: a reduce task simply fetches a range of partitions instead of one, which is why coalescing costs almost nothing.
Join conversion. If one side of a planned sort-merge join turns out below the broadcast threshold (spark.sql.autoBroadcastJoinThreshold, 10 MB by default, or spark.sql.adaptive.autoBroadcastJoinThreshold if set), AQE rewrites the join to a broadcast hash join. This is legal because the join type and condition are unchanged; only the algorithm differs, which relational algebra and the physical join family allow. The big side's shuffle has already been done, so there is no saving of that network step, but AQE uses a local shuffle reader to read the data without more network transfer, and it skips the sort that the sort-merge join would have done. A related rule can also choose a shuffled hash join if all partitions are small enough. Another rule removes work: if a stage returns zero rows, joins or filters over it can be replaced by an empty result.
Skew join. After both join inputs have been shuffled, AQE looks at the partition sizes. A partition is skewed if it is larger than the skewedPartitionFactor (5.0) times the median partition size and also larger than the skewedPartitionThresholdInBytes (256 MB). A skewed partition is split into several sub-partitions by dividing its map outputs into ranges, each about the typical partition size. The matching partition from the other side is read in full by each sub-task, which is a replication cost. The result is the same as the original join, because the union of the pieces covers the whole partition. This works for sort-merge joins (and, in later versions, shuffled hash joins) and only on the side that is allowed to be split for the join type: for a left outer join only the left side can be split, and for a full outer join not at all.
Each new plan is compared with the old one by a cost evaluator before it is accepted. Spark's default evaluator simply counts the shuffles in the plan, so a rewrite that would add a shuffle is rejected (a setting such as forceOptimizeSkewedJoin can override this for skew), which keeps AQE from making a plan worse while trying to improve it. Stages whose output is already computed are reused, not re-run, and identical exchanges inside one query can be shared.
The framework has limits by construction. It acts only at stage boundaries, so a plan with no shuffle gets no benefit. It cannot undo work already done.

example: A query joins a 500 GB events table to a campaigns table with a filter, then groups by campaign. The campaigns table has no column statistics, so the optimizer estimates the filtered result at 2 GB: far above the 10 MB broadcast limit. It plans a sort-merge join with 2,000 shuffle partitions (the user raised spark.sql.shuffle.partitions for the big join).
Without AQE: both tables are shuffled and sorted by key. The 500 GB side is shuffled into 2,000 partitions of about 250 MB. The campaigns side, whose real size is 6 MB, becomes 2,000 partitions of 3 KB each, so most tasks handle almost nothing on that side. Then, the join output is shuffled again for the group-by into the same 2,000 partitions, where the true aggregated data is only 40 MB in total: 2,000 tasks of 20 KB each, all with scheduling overhead of tens of milliseconds, and thousands of tiny output files if the result is written.
With AQE: the stage that scans and filters campaigns finishes first and reports a total of 6 MB. AQE sees 6 MB < 10 MB and changes the join to a broadcast hash join. The events side has already been shuffled, so the local shuffle reader reads its partitions locally and skips the sort. Then the group-by's shuffle stage runs and reports 40 MB of data in 2,000 partitions of 20 KB. Coalescing merges them: 40 MB with a floor of 1 MB per partition gives roughly 40 tasks (with parallelism-first, the target is min(64 MB, max(total / parallelism, 1 MB))), so the final stage has dozens of tasks, not 2,000.
Now skew: suppose the events join key has one hot value. After the shuffle, the median partition is 250 MB and one partition is 6 GB. The test: 6 GB > 256 MB, and 6 GB > 5 × 250 MB = 1.25 GB, so it is skewed. AQE splits it into about 6 GB / 250 MB = 24 sub-tasks. Each sub-task reads one slice of the hot partition and the matching rows of the other side. The stage's longest task falls from the time to process 6 GB to the time for about 250 MB, a speedup of up to 24 times for that straggler, while the other side's matching data is read 24 times (a small cost if that side is small).
intuition: Re-planning the route at each rest stop, using the real traffic you just saw instead of the forecast you made at home.
The idea is natural because the weakest input to an optimizer is the estimate, and the engine's own stage barrier produces the exact answer for free: when a stage ends, its output size is known. Deciding later, with real numbers, is cheaper and safer than building ever better predictions. The price is that you can decide only where the plan pauses, so the first stage always runs on the original guess.
mistakes: People often think AQE replaces statistics and the cost-based optimizer. In fact it works on top of them. The first stages, the join order and the choice of scans are still planned from estimates; AQE only corrects decisions that come after a shuffle or broadcast.
People often think AQE makes tuning shuffle partitions unnecessary. In fact it can only merge partitions (and split skewed ones). If you start with too few partitions, nothing splits them; so set a generous initial number and let AQE coalesce.
People often think a join switched to broadcast by AQE is as good as a planned broadcast join. In fact the big side has already been shuffled when AQE decides, so you have paid for the shuffle write and the stage barrier. The gain is mostly from skipping the sort and the network fetch. Fix the statistics or add a hint if you know the table is small.
People often think AQE fixes all skew. In fact it handles skew only in shuffle joins and only after the shuffle; skew inside a group-by with one hot key, skew in a scan, or a skewed key in the non-splittable side of an outer join remain.
tradeoffs: Choose AQE on (the default) for batch SQL and DataFrame jobs where table sizes vary, statistics are missing, or data grows over time: the cost is small and it removes the worst failure patterns (200 default partitions, a wrong join type, one huge straggler). Choose to switch it off or to pin a plan only for tiny interactive queries where the extra planning rounds are noticeable, or when you need a fully predictable plan for debugging.
Choose a high initial partition number with coalescing when data size changes day to day; choose a fixed, hand-tuned number when the size is known and stable and you want to avoid the extra planning and the many-small-blocks shuffle that a very high initial number creates (every extra partition adds shuffle blocks, which cost the M × R pattern).
Choose to rely on AQE's broadcast conversion when you do not know the size of a filtered table; choose an explicit BROADCAST hint, or fix the statistics, when you do know it. Planning the broadcast up front avoids the already-paid shuffle of the big side. The hint is brittle if the table later grows, so AQE is the safer default.
Choose AQE skew handling for moderate skew, where one partition is about 5 to 50 times the median; choose manual salting, isolating the hot key, or a broadcast of the other side when a single key carries a large share of the data, because replicating the other side to many sub-tasks can cost more than it saves.
friction: AQE can act only at stage boundaries. A query with a single scan and aggregation, or one that contains a long chain of narrow operators, gets little. The first stage is planned entirely from estimates, and every stage boundary is a synchronization barrier, so AQE cannot fix a plan that reads far too much data in the first scan; this is the job of statistics, pushdown and partitioning.
It adds planning rounds and complexity. The final plan is known only after the query runs, so EXPLAIN before running shows an "initial plan" that may differ from what ran; you need the Spark UI (or EXPLAIN FORMATTED after the run) to see the final plan. Plans can differ between runs as data changes, which makes comparing performance harder and surprises people who expect fixed plans. Rules sometimes conflict: coalescing wants fewer partitions while skew handling wants more tasks, and a parallelism setting can silently stop coalescing.
There are also correctness-neutral but cost-relevant limits. Conversion to broadcast can cause out-of-memory errors in the driver or executors if the measured size is small on disk but large in memory. Skew splitting replicates data from the other side. And the optimization covers only some operators: it does not handle skew in aggregations, it cannot switch join order after the first stage in the general case, and it does not apply to streaming queries.
practice: Leave AQE on (it is the default since Spark 3.2; check spark.sql.adaptive.enabled on older clusters). Then set the initial number of shuffle partitions high enough for your largest jobs (spark.sql.adaptive.coalescePartitions.initialPartitionNum) and let AQE reduce it; tune spark.sql.adaptive.advisoryPartitionSizeInBytes if you want bigger or smaller output tasks (64 MB is a reasonable value; use 128 to 256 MB for large jobs to produce fewer files).
Read the final plan in the Spark UI: the SQL tab shows an "AQE" plan with final and initial versions, and the nodes "AQEShuffleRead" marked coalesced or skewed. Look for "number of coalesced partitions", "skewed partitions" and "local" labels to confirm that AQE acted. If a join you expected to be broadcast is still a sort-merge, check the measured size and the thresholds.
For skew, keep spark.sql.adaptive.skewJoin.enabled on and tune skewedPartitionFactor and skewedPartitionThresholdInBytes if your partition sizes are small or large relative to defaults; if a join key has a null or default value with most of the rows, treat it separately in the query. Keep table statistics fresh anyway; AQE helps after the first stage, and good statistics help the first one.
When writing output, remember that coalescing also reduces the number of output files from a shuffle, which usually helps downstream readers; if you need exact file counts, use an explicit repartition or rebalance.
quiz: What information does AQE collect, and where does it come from? || The exact size (bytes and rows) of every reduce partition, reported by the finished map tasks of a shuffle stage to the driver. It is a measurement, not an estimate.
Why is it safe for AQE to change a sort-merge join into a broadcast join? || Both compute the same join result for the same condition and type; only the algorithm differs. Relational algebra and the join semantics are unchanged, so the answer is the same.
A partition has median size 250 MB and one partition is 6 GB. Is it skewed under the defaults, and about how many pieces will it split into? || Yes: it exceeds 256 MB and also 5 × 250 MB = 1.25 GB. Splitting aims at roughly the typical partition size, so about 6 GB / 250 MB = 24 pieces.
Why does AQE not help when you start with too few shuffle partitions? || It can merge small partitions and split skewed ones, but it does not generally increase the number of partitions of an ordinary shuffle. So start high and let it coalesce.
When would you prefer a planned BROADCAST hint to AQE's runtime conversion? || When you know a table is small. A planned broadcast avoids the shuffle and sort of the big side; with AQE conversion that shuffle has already been done. Prefer AQE when the size is uncertain or changes.
interview: Describe how AQE works internally and where it can and cannot change a plan. || The plan is cut into query stages at exchanges. Stages run bottom-up; finished stages report exact partition sizes. The driver re-optimizes the remaining logical plan with those statistics and builds a new physical plan, applying rules such as coalescing, join conversion and skew splitting. It can only act at stage boundaries after materialization; it cannot change scans, earlier stages, or plans without a shuffle.
Your job writes 2,000 tiny output files after a shuffle. How does AQE help, and what else can you do? || Coalescing merges small shuffle partitions, so fewer reduce tasks write fewer files. You can raise the advisory size, use repartition or rebalance before the write, or run a compaction (OPTIMIZE for Delta) afterwards.
Why does the "parallelism first" setting matter? || With it on (the default since 3.2), the target partition size is capped so that the number of tasks does not fall below the cluster's parallelism, with a floor of 1 MB, so the advisory 64 MB may be ignored and a small shuffle may not be coalesced much. Turn it off if you want partitions close to the advisory size.
A skew join in AQE still takes hours on one task. What could be going on? || The skew may be in a side or join type that cannot be split (the preserved side of an outer join, or a full outer join), in a group-by rather than a join, or inside a single key so large that even replicating the other side to many pieces cannot help. Isolate the key, salt it, or restructure the query.
Compare AQE with mid-query re-optimization from the research literature. || Both measure real statistics during execution and re-plan. Classic approaches checkpointed anywhere in a pipelined plan and might discard work; Spark AQE re-plans only at natural materialization points (shuffle and broadcast), where the data is already written, which keeps it simple and cheap but limits where it can act.

@@ volcano
value: After the optimizer has chosen a plan, something must run it. The Volcano model, also called the iterator model, is the simplest and most widely used answer. Every operator in the plan (scan, filter, join, aggregate, sort) is an object with three methods: open(), next() and close(). To get the result, the engine calls next() on the root operator. The root calls next() on its child, which calls next() on its own child, down to the scan. Each call returns one row, which travels back up the tree. The consumer pulls rows, and the producers never run ahead of it.
The value of this design is composability. Any operator can be plugged on top of any other, because they all speak the same three-method language. Adding a new operator does not require changing the others. Pipelines run without storing intermediate results: a row can go from the scan through a filter and a projection to the client without ever being written down. A LIMIT 10 stops the whole tree after ten rows because nobody asks for more. PostgreSQL, MySQL, SQLite and many older engines still execute queries this way, and it is the baseline against which vectorized and compiled engines (the neighbouring concepts) are measured.
Two lower concepts matter. Relational algebra (L3) provides the operator set: each Volcano operator is the executable form of one algebra operation, so the optimizer's plan tree is already the execution tree. Branch prediction (L3) explains the cost: a call to next() per row per operator is an indirect (virtual) call, and the work inside is a long chain of data-dependent branches, which a CPU predicts poorly. On modern hardware this overhead, not the disk, is often what limits in-memory query speed. The layer above (distributed SQL engines) uses the same iterator idea inside each worker and adds an exchange operator to move rows between workers.
terms: Operator — a node of the plan tree that implements one relational operation (scan, filter, project, join, aggregate, sort).
Iterator interface — the three methods open() (prepare), next() (return the next row or end-of-input) and close() (release resources) that every operator implements.
Pull-based execution — the consumer asks the producer for each row; control flow goes from the root of the tree down to the leaves.
Pipelined operator — an operator that can emit a row as soon as it receives a row (filter, projection, a probe side of a hash join).
Blocking operator (pipeline breaker) — an operator that must consume all or part of its input before it can emit anything, such as sort, hash aggregate or the build side of a hash join.
Virtual call — a function call whose target is found at run time from a table of function pointers; it cannot be inlined and relies on the CPU's indirect branch predictor.
Exchange operator — Volcano's operator for parallelism; it moves rows between processes and partitions them, so the other operators do not need to know about parallelism.
Tuple-at-a-time — processing a single row at a time through the whole operator chain, as opposed to a batch of values.
history: The idea of a standard open-next-close interface was already used in the first relational systems of the 1970s (System R and Ingres had similar iterator-style executors). Goetz Graefe made it a clean, general design in the Volcano project, described in "Volcano: An Extensible and Parallel Query Evaluation System" (IEEE TKDE, 1994; an earlier paper on parallelism appeared at SIGMOD 1990). His goal was extensibility: researchers should be able to add operators and data types without rebuilding the engine. The paper also introduced the exchange operator, a single place where parallelism lives, so that the same operators run on one core or many processes.
For two decades this was how almost every database executed queries, because disks were slow and the interpretation overhead hid behind I/O. In the 2000s, memory grew and queries became CPU-bound. The MonetDB/X100 paper by Boncz, Zukowski and Nes (CIDR 2005) showed that a tuple-at-a-time engine spent most cycles on interpretation, and proposed passing vectors of about a thousand values between operators. Neumann (VLDB 2011) showed another route in HyPer: compile each pipeline of the plan to machine code with LLVM, so the whole pipeline becomes one tight loop. Kersten and colleagues (VLDB 2018) compared the two approaches carefully and found both far faster than Volcano and similar to each other.
Industry followed. Spark 2.0 (2016) added whole-stage code generation that fuses operators into one Java method. DuckDB, ClickHouse and Databricks Photon use vectorized execution (Photon is described in a SIGMOD 2022 paper). PostgreSQL added optional LLVM-based JIT compilation of expressions in version 11 (2018), but its executor is still Volcano style.
how: Each operator implements open(), next() and close(). Here is the logic of a filter in plain words: open() calls child.open(). next() loops: row = child.next(); if row is end-of-input, return end-of-input; if the predicate is true for the row, return it; otherwise go back and ask for another row. close() calls child.close(). A scan operator has the same shape, but next() reads a row from a page of the table and returns it. A projection computes new columns from the row it receives. All of them look the same from outside, so a plan is just a tree of such objects, and the whole query runs by repeatedly calling next() on the root until it reports end-of-input.
Blocking operators change the timing. A hash aggregate must see all its input before it can return any group, so in open() (or on its first next()) it pulls all rows from its child, updates a hash table keyed by the grouping columns, and only then starts returning groups one by one. A sort does the same with an external merge sort (using spilled runs on disk if the input is too large). A hash join first builds a hash table from its build child, then streams the probe child through it: for each probe row, next() returns the matches. These are the pipeline breakers; between two of them, rows flow one by one through pipelined operators with no storage in between. Pipeline breakers are also the places where memory is used, and where plans spill to disk.
Some details of the contract matter in practice. Most implementations return a pointer to a row buffer that the operator owns and will overwrite on the next call, so a parent that wants to keep a row (for a hash table or a sort run) must copy it. The same operator tree can be restarted: a nested loop join calls rescan or open() on its inner child once per outer row, which is cheap for an index lookup but disastrous for a full scan, and is why a node with many loops in an EXPLAIN output deserves attention. Memory is managed per operator, with a budget for each blocking operator; when it is exceeded, the operator writes sorted runs or hash partitions to disk and continues, still presenting the same next() interface to its parent. Expressions such as a + b * 2 are usually evaluated by a small interpreter walking an expression tree for every row, which adds a second layer of per-row overhead inside each operator.
Parallelism comes from the exchange operator. It looks like any other operator from above (it has next()), but internally it runs its child subtree in other processes or threads, partitions their output rows (by hash, by range, round robin or broadcast), and passes them through queues to consuming processes. Operators above and below do not change. This is the same idea as the shuffle in distributed engines: there it is the one place where data crosses the network.
The cost shows when you count what happens per row. Each next() call is an indirect function call: the CPU must load the function pointer and jump, and it can predict the target only if the call site always goes to the same function. Generic engine code calls child.next() from many operators through the same instruction, so targets vary, and branch prediction (L3) has a hard time. A mispredicted branch costs on the order of 15 to 20 cycles. Inside each operator there are also data-dependent branches (does this row pass the predicate?) that mispredict when the filter passes about half of the rows. Because the interpreter works on one row, the CPU cannot use SIMD instructions, cannot keep values in registers across operators (each row goes through memory as a tuple), and cannot inline or optimize across operators. The instruction cache also suffers because code of every operator in the pipeline is executed for every row.
The result: for in-memory data, a Volcano engine often needs tens of CPU cycles per row per operator for tiny work, where a compiled or vectorized loop uses one to a few cycles per value. The fixes keep the plan and change the unit of work. Vectorized engines make next() return a batch (for example 1,000 to 2,000 values per column), so the call overhead is spread over the whole batch and inner loops run over arrays with SIMD. Compiled engines remove the interface completely by generating one loop per pipeline.

example: Follow a tiny query by hand: SELECT dept, SUM(sal) FROM emp WHERE sal > 50 GROUP BY dept. The table emp has three rows: (a, dept 10, sal 40), (b, dept 10, sal 60), (c, dept 20, sal 70). The plan is Aggregate over Filter over Scan.
The client asks the Aggregate for its first row. The Aggregate is blocking, so it loops on Filter.next(). Filter.next() calls Scan.next(), which returns row a. The predicate sal > 50 is false, so the Filter calls Scan.next() again and gets row b, which passes. It returns b. The Aggregate puts dept 10 in its hash table with sum 60. It calls Filter.next() again; the Filter pulls row c from the Scan, which passes, and the Aggregate adds dept 20 with sum 70. It calls Filter.next() once more; the Scan has no rows left and reports end-of-input, and the Filter passes that up. Now the Aggregate returns (10, 60), and on the next call (20, 70). Count the calls: Scan.next() was called 4 times (3 rows and the end) and Filter.next() 4 times, so 8 calls for 3 input rows.
Now scale it. A table has 100 million rows and the pipeline is Scan, Filter, Project, Aggregate (3 operators below the aggregate). That is about 300 million next() calls. If each call and the associated tuple handling costs a rough 10 ns (a conservative figure for a tuple-at-a-time engine on a 3 GHz core), the interpretation overhead alone is 3 seconds of one core, before any real work is counted. A vectorized engine with batches of 1,024 rows makes 100 million / 1,024, about 98,000 calls per operator, so about 300,000 calls in total: overhead is under a millisecond. The actual work is a tight loop over arrays, at roughly 1 to 2 ns per value per operator, so 100 million values through three operators take 0.3 to 0.6 seconds on one core, about 5 to 10 times faster than the row-at-a-time number. These are rough, illustrative numbers; measured gains on real queries range from 3 to 10 times or more (the X100 paper reported gains of about an order of magnitude on TPC-H query 1).
Also notice what the pull design gave for free: if the query had LIMIT 1, the client stops after the first row, and the Scan would not read the other rows. A push design must add explicit signals to achieve this.
intuition: A bucket brigade: each person asks the one behind them for the next bucket, one bucket at a time.
The design is natural because it mirrors the plan tree: each node is a small machine with one job and one rule, "give me your next row". It needs no memory for intermediate results and no global schedule, and any tree can be built from any pieces. The price is the same as the bucket brigade's: every single bucket needs a handoff, and handoffs are slow compared to the work in each bucket once the data is in memory.
mistakes: People often think the Volcano model is obsolete. In fact it is still how PostgreSQL, MySQL and many other engines run queries, and it is a good fit for OLTP (few rows per query), for clarity and for extensibility. Only large analytical scans over in-memory data make its per-row overhead dominant.
People often think vectorized execution is a different algorithm. In fact it is the same plan and often the same pull interface, but next() returns a batch of rows (a column vector) instead of one row. The change reduces call overhead and allows SIMD.
People often think the slowness comes from function calls only. In fact function calls are one part. The bigger losses come from no cross-operator optimization (values go through memory instead of registers), poor instruction-cache use, branch mispredictions in data-dependent filters, and no SIMD.
People often think "pull" means the data is fetched lazily from disk. In fact pull is about control flow between operators: the consumer asks for rows. Whether the scan reads from disk or from memory is a separate matter, handled by buffering and prefetching.
tradeoffs: Choose the Volcano (tuple-at-a-time) model when queries touch few rows (OLTP point lookups and short transactions), when the engine must be easy to extend, debug and reason about, or when the team is small. The per-row overhead of 10 to 50 ns does not matter when a query handles 100 rows; the simplicity does.
Choose vectorized execution (batches of 1,000 to 2,000 values) when queries scan millions to billions of rows in memory or from columnar files and the CPU is the limit. You keep the interpreter's flexibility (no compile step, easy profiling, good for many operators and types) and get most of the speedup, but you must write operators as tight loops over arrays and handle selection vectors (which rows in the batch are still alive).
Choose compiled execution (generate code per pipeline) when queries are heavy and repeated, so that compile time (tens to hundreds of milliseconds with LLVM, longer for Java) is repaid, and you want the best raw speed for complex expressions. You give up debuggability and fast startup, and take on a compiler as a dependency. For short queries, adaptive engines interpret first and compile only hot pipelines.
Choose a pull model when early termination (LIMIT, EXISTS) and simple control flow matter; choose a push model (producers call consumers) when you want to compile pipelines into loops and share work between consumers. Either way you pay in complexity somewhere: pull gets simple code and slow rows, push gets fast loops and trickier control for limits and joins.
friction: The main limit is CPU efficiency. Per-row virtual calls, per-row branches and per-row memory traffic make Volcano 5 to 50 times slower than vectorized or compiled engines on in-memory analytical scans. The gap grows as storage gets faster (NVMe, memory), since the interpretation cost stays constant while I/O cost drops.
It is also single-threaded in its basic form. Parallelism needs the exchange operator or morsel-driven parallelism (Leis and others, SIGMOD 2014), which divides work in small chunks over threads and also fixes load imbalance, a weakness of static exchange partitioning. Blocking operators need memory, and the iterator interface gives no direct way to share memory budgets between them, so engines add memory managers and spilling.
Modern hardware features such as SIMD, prefetching and wide caches are hard to use from tuple-at-a-time code. Moving to vectors or compilation needs a rewrite of operators, expressions and often of the storage layer to deliver data in columns, which is why legacy row stores change slowly. Finally, debugging a pull tree is easy, but profiling is harder because time is spread across thousands of small calls with no single hot loop.
practice: When reading a query plan, think in pipelines: find the blocking operators (sort, hash aggregate, hash join build) and see which operators stream between them. Memory use and spills happen at the breakers; row-by-row CPU cost happens in the streams.
If you run an OLTP or mixed workload on PostgreSQL or MySQL, the iterator model is fine; focus on indexes and plans, not on executor internals. For analytics, prefer engines with vectorized or compiled execution (DuckDB, ClickHouse, Photon on Databricks, Spark with whole-stage codegen, Velox-based engines) and make sure you use their fast path: columnar formats like Parquet, built-in functions rather than UDFs (a Python UDF forces a row-at-a-time boundary), and types that the engine handles natively.
In Spark, check that the plan nodes show "WholeStageCodegen" (the operators fused into one function) or that Photon is active in the Databricks plan; operators outside codegen, such as some UDFs or complex types, run row at a time. In PostgreSQL, EXPLAIN (ANALYZE) shows per-node actual rows and loops; a node that is called many times (loops) in a nested loop join is the Volcano re-scan pattern, and often a sign for an index. If you build your own engine, start with the iterator model for clarity, make the batch size a parameter early, and keep the operator interface compatible with batches.

Why does a LIMIT 10 query finish early in a pull-based engine? || The root only calls next() ten times; each call pulls just enough rows from the child operators, so the scan is never asked for the rest. Nothing runs ahead of the consumer.
Why is tuple-at-a-time execution slow on in-memory data, beyond the cost of the call itself? || Each row goes through memory between operators, the CPU cannot inline or use SIMD across them, data-dependent branches mispredict, and the code of all operators competes for the instruction cache.

interview: Why do vectorized and compiled engines beat Volcano, and which would you pick for a new engine? || They remove per-row interpretation: vectorized amortizes calls over batches and enables SIMD, compiled fuses a pipeline into one loop with values in registers. Vectorized is easier to build, debug and profile, supports adaptive execution and has no compile latency; compiled can be faster on complex expressions but costs compile time and complexity. Most new engines choose vectorized; some add JIT for expressions.
What is a pipeline breaker, and why does it matter for memory? || An operator that must consume (part of) its input before producing output: sort, hash aggregate, hash join build side. It holds state in memory, so it needs a memory budget and spilling to disk; between breakers, rows stream through without being stored.
How does Volcano's exchange operator relate to the shuffle in Spark? || Exchange is the single operator that hides parallelism: it partitions rows by hash, range or broadcast and sends them to other processes. Spark's Exchange node is the same idea across machines, with data written to disk and fetched over the network.
How does a hash join work in the iterator model, and which child is the pipeline breaker? || On open(), the join pulls all rows from the build child and builds a hash table (the breaker). Then each next() pulls probe rows one by one, looks them up and returns matches. The probe side streams without being stored.
What is morsel-driven parallelism and why does it improve on the exchange operator? || The work is divided into small chunks (morsels) that worker threads take dynamically, using NUMA-local memory. Unlike static exchange partitioning, it balances load automatically and adapts the degree of parallelism at run time without separate processes.

@@ qlearning
value: Imagine an agent that acts in a world, sees a reward after some actions, and has no model of how the world works. It must learn what to do from experience alone. Q-learning does this by learning a table or function Q(s, a): the total future reward the agent expects if it takes action a in state s and then behaves as well as possible. Once Q is known, the policy is trivial: in each state, pick the action with the highest Q.
The learning rule is one line. After each step, move the old estimate a little toward "the reward I just got plus the discounted best value I expect from the next state". The agent never needs to know the transition probabilities, and it can learn the best policy even while it behaves differently (it explores). In 2015 DeepMind replaced the table with a neural network and trained a single design, the Deep Q-Network (DQN), to play 49 Atari 2600 games from raw screen pixels at a level comparable to a professional human games tester. That result started the modern wave of deep reinforcement learning.
Three lower concepts carry the weight. Markov decision processes and the Bellman equations (L4) define what Q should be: the unique fixed point of the Bellman optimality equation, and the reason that "reward plus best next value" is the right target. Gradient descent (L2) lets DQN fit Q with a neural network when there are far too many states for a table (an Atari frame has more possible images than atoms in the universe). Sampling (L2) is used in experience replay: random mini-batches drawn from stored past steps break the strong correlation between consecutive frames. The layer above, reinforcement learning, treats value-based learning like this as one of its two main families, beside policy gradients.
terms: State, action, reward — what the agent observes, what it can do, and the number it receives after acting; the goal is to maximize the sum of rewards over time.
Discount factor γ — a number between 0 and 1 (often 0.99) that makes a reward t steps in the future worth γ^t of its face value; it keeps sums finite and prefers sooner rewards.
Q-value Q(s, a) — expected discounted future reward from taking action a in state s and then following the best policy afterwards.
Temporal-difference (TD) error — the difference between the current estimate and a better one made of one real reward plus the estimate of the next state: \( r + \gamma \max Q(s', a') - Q(s, a) \).
Off-policy — learning about one policy (the greedy, best one) while following another (an exploring one).
ε-greedy — an exploration rule: with probability ε take a random action, otherwise take the action with the highest Q.
Experience replay — a buffer of past transitions (s, a, r, s′) from which random mini-batches are drawn for training.
Target network — a slowly updated copy of the Q-network, used to compute the learning target, so that the target does not move with every step.
history: Reinforcement learning grew from animal-learning theory and optimal control. Richard Bellman's dynamic programming (1950s) gave the equations for optimal behaviour when the model is known. Richard Sutton's temporal-difference learning (1988) showed how to learn value estimates from experience by bootstrapping, using the estimate of the next state in place of the full future return. Chris Watkins introduced Q-learning in his 1989 Cambridge PhD thesis, and Watkins and Dayan proved its convergence in 1992 for the tabular case, if every state-action pair is visited again and again and step sizes shrink suitably.
Combining Q-learning with function approximation was hard. Baird (1995) built small counterexamples where it diverges, and Sutton and Barto's book later named the combination of bootstrapping, off-policy learning and function approximation the "deadly triad". Gerald Tesauro's TD-Gammon (1992 to 1995) learned backgammon with a neural network and TD learning, but similar attempts on other problems often failed. Riedmiller's Neural Fitted Q iteration (2005) was an early stable batch approach.
Mnih and colleagues at DeepMind published the first DQN results in 2013 (an NIPS workshop paper) and in Nature on 25 February 2015. They made it work with two ideas: experience replay (from Lin, 1992) and a separate target network, plus tricks such as clipping rewards and stacking four frames. Improvements followed quickly: Double DQN (van Hasselt, Guez and Silver, 2016) against overestimation, prioritized replay (Schaul and others, 2016), dueling networks (Wang and others, 2016), distributional methods (Bellemare and others, 2017), and Rainbow (Hessel and others, 2018), which combined six of them. Later work moved to actor-critic and policy-gradient methods for continuous control and for language models, but Q-learning remains the base of value-based RL.
how: The table version first. Keep a number Q(s, a) for every state-action pair, initialized to 0. The agent observes state s, picks an action a (ε-greedy: usually the best, sometimes random), receives reward r and the next state s′. Then it applies the update:
\[ Q(s, a) \leftarrow Q(s, a) + \alpha \left[ r + \gamma \max_{a'} Q(s', a') - Q(s, a) \right] \]
The learning rate \( \alpha \) (for example 0.1) controls how far each step moves the estimate. If the episode ended at s′, the max term is 0. The bracket is the TD error: the gap between what the table said and a slightly better estimate made from one real step of experience.
Why does this converge to the right answer? The Bellman optimality equation says the true Q* satisfies \( Q^*(s, a) = \mathbb{E}[\, r + \gamma \max Q^*(s', a') \,] \). Value iteration, which applies this equation as an update with a known model, is a contraction (each pass shrinks the distance to Q* by a factor \( \gamma \)), so it converges. Q-learning is the same iteration done by sampling: each real step is one noisy sample of the right-hand side, and averaging samples with a shrinking step size converges to the fixed point (the stochastic approximation argument of Robbins and Monro). This is the contribution of the MDP and Bellman layer.
The method is off-policy: the target uses max over next actions, whatever action the agent will actually take. So the agent can explore freely and still learn the values of the greedy policy. SARSA, its on-policy cousin, uses the action actually taken next, and so learns the value of the exploring policy. Off-policy learning also means old data stay useful, which allows replay.
With images there are too many states for a table, so DQN represents Q(s, ·) by a convolutional network with parameters θ: the input is the last four 84×84 grayscale frames, and the output is one Q-value for each of the (up to 18) actions. Training minimizes the squared TD error: \( L(\theta) = \mathbb{E}\big[ \big( r + \gamma \max_{a'} Q(s', a'; \theta^-) - Q(s, a; \theta) \big)^2 \big] \), by gradient descent (RMSProp in the paper) on mini-batches of 32 transitions. The target \( r + \gamma \max Q(s', a'; \theta^-) \) is treated as a constant label, not differentiated; this is a semi-gradient method.
Two additions make this stable. Experience replay stores the last million transitions and trains on random samples. Without it, consecutive frames are nearly identical, the network overfits to the current moment, and the data distribution shifts as the policy changes. Random sampling (L2 sampling) makes the mini-batches closer to independent and reuses each experience many times. The target network θ⁻ is a copy of θ that is refreshed only every 10,000 steps in the original DQN. Without it, the target moves each time the network is updated, so the network chases its own tail, and the deadly triad can make values blow up.
One full DQN step looks like this. The agent feeds the current four-frame state to the network, chooses an action by ε-greedy, sends it to the game, and receives the reward and the next frame. It stores (s, a, r, s′, done) in the buffer. Then it draws 32 random transitions, computes the targets with the target network (using just r for terminal transitions), computes the loss on the online network's outputs for the actions that were taken, and makes one gradient step. Every 10,000 steps it copies θ into θ⁻. Learning starts only after the buffer holds some initial data (50,000 frames in the paper), so that the first batches are not all from the same few moments. Exploration matters for convergence: the tabular proof needs every state-action pair to be tried again and again, which ε-greedy provides, and the ε decay moves the agent from exploring to exploiting.
Other practical details of DQN: ε is annealed from 1.0 to 0.1 over the first million frames, rewards are clipped to [−1, 1] so one learning rate fits all games, the agent chooses an action every 4th frame, and each game is trained for tens of millions of frames.
The known weakness is overestimation. Taking a max over noisy estimates is biased upward, because the max of noisy numbers is larger than the max of the true values. Double DQN reduces this by choosing the best next action with the online network and evaluating it with the target network.

example: A corridor has four cells in a row: s0, s1, s2 and a goal cell. The agent can move left or right. Reaching the goal gives reward 1 and ends the episode; all other steps give 0. Use γ = 0.9 and α = 0.5, with all Q-values starting at 0. Only the "right" action matters for this example.
Episode 1 starts at s2 and moves right into the goal: r = 1, the episode ends, so the target is 1. Q(s2, right) = 0 + 0.5 × (1 − 0) = 0.5.
Episode 2 starts at s1 and moves right to s2 with r = 0. The target is 0 + 0.9 × max Q(s2, ·) = 0.9 × 0.5 = 0.45. Q(s1, right) = 0 + 0.5 × (0.45 − 0) = 0.225. Then from s2 the agent moves right again: Q(s2, right) = 0.5 + 0.5 × (1 − 0.5) = 0.75.
Episode 3 starts at s0 and moves right to s1: target = 0.9 × 0.225 = 0.2025, so Q(s0, right) = 0.5 × 0.2025 ≈ 0.10. The reward information has moved one cell back per pass, like water flowing backward from the goal. After many episodes the values approach the true ones: Q*(s2, right) = 1, Q*(s1, right) = 0.9 × 1 = 0.9, and Q*(s0, right) = 0.81. The optimal policy is read off by choosing, in each state, the action with the largest Q.
Now overestimation with numbers. Suppose an agent has 10 actions whose true value is 0 in some state, but its estimates have independent noise with standard deviation 1. The expected maximum of 10 such estimates is about +1.5, not 0. Q-learning uses this maximum as the target, so the next state looks about 1.5 better than it is, and the error is passed back to earlier states with each update. Double DQN selects the action with one set of estimates and evaluates it with another, whose noise is independent, so the expected value of the chosen action is close to 0.
intuition: Keep a score for every move in every position, and each time you see where a move actually led, nudge its score toward what you saw.
This works because of one fact about good decisions: the value of a move equals the immediate reward plus the value of the best position it leads to. That is a statement about neighbours only, so it can be learned from single steps, without waiting for the end of the game and without understanding the whole world. Each update makes the score a bit more consistent with its neighbours, and consistency spreads from rewards backward through the states, like a rumour spreading from the goal.
mistakes: People often think Q-learning learns the policy the agent actually follows. In fact it learns the value of the greedy policy, whatever the agent does (that is what off-policy means). The agent may be exploring, or even replaying someone else's data, and the Q-values still estimate the best behaviour.
People often think DQN is just Q-learning with a bigger table. In fact Q-learning with a neural network is unstable and can diverge; replay and the target network are what make it work. Remove either and the Atari results degrade sharply.
People often think a higher Q-value always means a better action. In fact the value is an estimate that can be biased upward by the max operator and noisy data, especially for rarely visited actions. High Q for an action that was never tried much is often an error, not a discovery.
People often think Q-learning needs a model of the environment. In fact it is model-free: it learns only from sampled transitions. The price is data: it needs many more experiences than planning with a known model.
tradeoffs: Choose Q-learning (value-based, off-policy) when the action set is small and discrete, experience is expensive and you want to reuse it (replay, logged data). Choose policy gradient or actor-critic methods when actions are continuous or very many (robot torques, bid prices as a continuous number), or when a stochastic policy is needed. You give up the simple "argmax" policy and sample efficiency; you gain the ability to act in continuous spaces.
Choose tabular Q-learning when the state space is small, say under a million state-action pairs: it has convergence guarantees and is easy to debug. Choose DQN-style function approximation when states are high-dimensional (images, long feature vectors); you lose the guarantees and need the stabilizers, a large buffer (memory for a million frames is several GB) and tuning of learning rate, target update interval and ε schedule.
Choose a small replay buffer and fast target updates when the environment changes (non-stationary) and old data go stale; choose a large buffer and slow target updates when the environment is stable and stability matters more. A larger buffer uses more memory and keeps outdated policies' data longer.
Choose off-policy value learning on logged data only with care. Standard Q-learning on a fixed log overestimates actions that the log rarely contains, so use offline methods that penalize unseen actions (such as conservative Q-learning, Kumar and others, 2020), or fall back to a contextual bandit if there is no long-term effect from actions.
friction: The deadly triad (bootstrapping, off-policy data and function approximation) means there is no general convergence guarantee for DQN; training can oscillate or diverge, and results vary strongly between random seeds. The max operator causes overestimation. Learning with sparse rewards (no feedback for long stretches) is slow because the signal must travel back one step at a time; games such as Montezuma's Revenge needed extra exploration methods.
Sample efficiency is poor: the original DQN trained on about 50 million frames per game, which is days of game time at human speed, where a person learns the same game in minutes. Exploration with ε-greedy is blind; it wastes steps on random moves and cannot plan deep exploration. Continuous actions break the max: finding max over a′ needs an optimization at every step, so DDPG, TD3 or SAC use an actor network instead.
Practical issues add up. Hyperparameters (learning rate, ε schedule, buffer size, target update period) matter greatly. Reward design is delicate, because the agent maximizes exactly what you wrote. Generalization is weak: a DQN trained on one game level can fail on a slightly changed one. And in real systems (such as bidding, recommendation, or control), you rarely can explore freely, so safe exploration and offline evaluation become the main work.
practice: Start small. Implement tabular Q-learning on a grid world first and watch the Q-table converge; then try DQN on CartPole with a library (Stable-Baselines3, CleanRL, or RLlib). Check that the learning curve rises over several random seeds, not one lucky run.
For DQN use the standard recipe: a replay buffer of 100,000 to 1 million items, mini-batches of 32 to 128, a target network updated every 1,000 to 10,000 steps (or a soft update with a small rate such as 0.005), ε decaying from 1 to 0.05 or 0.1, a Huber loss in place of squared error, gradient clipping, and Double DQN. These small changes matter more than the network size.
Log the average Q-value and the TD loss during training. If Q-values grow without bound or far above the maximum possible return, you have overestimation or divergence. Check the reward scale (clip or normalize), and make sure terminal states are treated correctly (no bootstrapping after the end of an episode).
Before using RL on a business problem, ask if a simpler model fits. If actions do not change future states (choosing a creative for an ad impression), a contextual bandit does the job with much less data. Use RL when decisions have long-term effects, such as budget pacing across a day or sequential bid strategies, and when you have a simulator or a safe way to explore.

Why is Q-learning called off-policy? || The target uses the maximum over next actions, which is the greedy policy's value, no matter which action the agent actually takes. So it learns the best policy while following an exploring one.
What two ideas make DQN stable, and what does each fix? || Experience replay breaks the correlation between consecutive samples and reuses data. The target network keeps the learning target fixed for many steps, so the network does not chase a target that moves with every update.
In the corridor example with γ = 0.9, what are the true values Q*(s2, right), Q*(s1, right) and Q*(s0, right)? || 1, 0.9 and 0.81. Each step away from the goal multiplies the value by γ.
You have a stream of logged ad impressions and clicks, where each decision does not change the next state. Would you use DQN? || Probably not. If actions do not affect future states, the problem is a contextual bandit, which needs less data and avoids bootstrapping instability. DQN fits only when actions have long-term effects.
interview: Why can Q-learning with a neural network diverge, and how does DQN address it? || It combines bootstrapping, off-policy learning and function approximation (the deadly triad), so errors feed back through the target and generalize wrongly across states. DQN uses a replay buffer to decorrelate data, a target network to freeze the target for many steps, reward clipping to bound gradients, and often Huber loss and gradient clipping.
What is the overestimation bias in Q-learning, and how does Double DQN reduce it? || The max over noisy estimates is biased upward, and bootstrapping propagates it. Double DQN selects the next action with the online network and evaluates it with the target network, so selection noise and evaluation noise are independent and the bias is much smaller.
Compare Q-learning with SARSA. On a cliff-walking task SARSA learns a safer path away from the cliff, because it accounts for random exploratory steps; Q-learning learns the shortest path and falls off during exploration.
Why is Q-learning hard to use for continuous actions, and what do people use instead? || The target needs max over actions, which is an optimization problem at every step for continuous actions. Actor-critic methods (DDPG, TD3, SAC) learn a separate actor network that outputs the action, trained to increase the critic's Q-value.
You want to use RL to tune bid prices. What risks would you check before training on live traffic? || Exploration costs real money, so use a simulator or offline data first and check for distribution shift. Reward hacking (maximizing clicks at ruinous cost), non-stationary auctions, delayed feedback, and constraints such as budgets must be modelled. @@ policygrad
value: Q-learning learns how good each action is and then picks the best one. Policy-gradient methods skip the middle step: they represent the policy itself, a function that gives the probability of each action in each state, and improve its parameters directly by gradient ascent on the expected total reward. If an action led to a better result than expected, make it more likely; if it led to a worse one, make it less likely. That is the whole idea, and the mathematics shows it is exactly the gradient of the quantity you want to maximize.
This approach has practical advantages. It works with continuous actions (a robot's joint torques) because the policy can output the parameters of a probability distribution. It can learn a truly random policy, which matters in games with hidden information. It is simple to attach to a neural network. And it is the family of methods behind RL for language models: Proximal Policy Optimization (PPO) was the algorithm in the RLHF stage of InstructGPT and many chat models, and Group Relative Policy Optimization (GRPO) is used to train reasoning models on tasks with checkable answers, such as maths and code.
Three lower concepts carry it. Markov decision processes (L4) define the objective: the expected discounted return of a policy in an MDP. Probability (L4) provides the key identity: the gradient of an expectation can be written as an expectation of a gradient of a log-probability, which can be estimated from sampled trajectories without knowing how the world works. Gradient descent (L2), used here as gradient ascent, with optimizers such as Adam, turns that estimate into parameter updates of a neural network. The layers above are reinforcement learning in general and RLHF, which applies PPO-style updates to a language model.
terms: Policy π(a|s) — the probability that the agent takes action a in state s; in deep RL it is the output of a neural network with parameters \( \theta \).
Return G — the sum of discounted rewards from a time step to the end of the episode.
Trajectory — one sampled sequence of states, actions and rewards from running the policy.
Baseline — a number subtracted from the return (often the value of the state) to reduce the variance of the gradient estimate without changing its average.
Advantage A(s, a) — how much better action a was than the average action in state s: Q(s, a) − V(s).
Actor-critic — a method with two parts: the actor (the policy) and the critic (a learned value function that supplies baselines or advantages).
Importance ratio r(θ) — \( \pi_{\text{new}}(a \mid s) / \pi_{\text{old}}(a \mid s) \), the factor that reweights data collected by an older policy.
KL divergence — a measure of how different two probability distributions are; used to keep the new policy close to a reference.
history: Ronald Williams proposed REINFORCE in 1992, the first general policy-gradient algorithm: sample an episode, then increase the log-probability of each action in proportion to the return that followed. Sutton, McAllester, Singh and Mansour proved the policy gradient theorem for function approximation in 1999, showing that the gradient can be computed without differentiating the environment. Actor-critic methods, which learn a value function to reduce variance, go back to the 1980s (Barto, Sutton and Anderson) and were refined in the following decades.
Deep learning made the approach practical, but stability was the problem: one step that is too large can destroy the policy, and the data collected afterwards is then bad. John Schulman and colleagues introduced Trust Region Policy Optimization (TRPO, ICML 2015), which limits each update by a KL-divergence constraint, and Generalized Advantage Estimation (GAE, 2015) to balance bias and variance. Asynchronous advantage actor-critic (A3C, Mnih and others, 2016) showed that parallel workers train stable policies. In 2017 Schulman and colleagues published PPO, which replaced the constraint by a simple clipped objective that needs only first-order gradient descent, and PPO became the default algorithm in many projects, including OpenAI Five and the RLHF of InstructGPT (Ouyang and others, 2022).
For language models, the critic is costly: it is another model as large as the policy. DeepSeekMath (Shao and others, 2024) introduced GRPO, which drops the critic and uses the average reward of a group of sampled answers to the same prompt as the baseline. GRPO and related methods (RLOO, DAPO and others) were used in the "reasoning model" wave of 2025, including DeepSeek-R1, with rewards from automatic checkers instead of human preference models.
how: Write the policy as \( \pi_\theta(a \mid s) \). Run it to collect trajectories \( \tau = (s_0, a_0, r_0, s_1, \dots) \). The objective is \( J(\theta) = \mathbb{E}[\, G(\tau) \,] \), the expected return. The difficulty: the return depends on θ through the actions taken, and sampling an action is not differentiable. The log-derivative trick solves this. Since \( \nabla \pi = \pi \cdot \nabla \log \pi \), the gradient becomes
\[ \nabla J(\theta) = \mathbb{E}\Big[ \sum_t \nabla_\theta \log \pi_\theta(a_t \mid s_t) \cdot G_t \Big] \]
The environment's dynamics (the transition probabilities) appear in the trajectory probability but do not depend on θ, so their gradients vanish, and the formula holds without any model of the world. This is the policy gradient theorem, and it comes from probability (L4) in the plainest way: the expectation can be estimated by averaging over sampled trajectories.
In words: for each action taken, compute the gradient of its log-probability (the direction that makes this action more likely), multiply it by how good the outcome was, and average. Actions followed by a high return are pushed up; actions followed by a low return are pushed down. REINFORCE does exactly this and then takes a gradient step with an optimizer such as Adam (gradient descent, L2, on the negative objective).
The estimate has high variance: the return mixes the effect of this action with luck from everything else. The standard fix is a baseline \( b(s) \). Replacing \( G_t \) by \( G_t - b(s_t) \) leaves the expected gradient unchanged (because \( \mathbb{E}[\nabla \log \pi] \) is zero) but can cut the variance greatly. With \( b(s) = V(s) \) the multiplier becomes the advantage, how much better this action was than the average action. In actor-critic methods a second network, the critic, learns \( V(s) \) by regression on observed returns. GAE combines multi-step returns with a decay parameter \( \lambda \) (commonly 0.95) to trade bias against variance.
A complete training loop for PPO has a fixed rhythm. First, collect a batch of experience with the current policy (for example 2,048 steps from 8 parallel environments), storing the action probabilities that were used. Second, use the critic to compute advantages with GAE: the one-step error is \( \delta_t = r_t + \gamma V(s_{t+1}) - V(s_t) \), and the advantage is a decaying sum of these errors, \( \sum_k (\gamma\lambda)^k \delta_{t+k} \). With \( \lambda = 0 \) it uses only the one-step error (low variance, more bias from the critic); with \( \lambda = 1 \) it equals the full return minus the baseline (no critic bias, high variance). Third, normalize the advantages to mean 0 and standard deviation 1 within the batch, and run the clipped update for several epochs. Fourth, throw the batch away and repeat. For language models the ratio r is computed per token, and the loss is averaged over the tokens of the batch.
Plain policy gradients are on-policy: the gradient formula holds for data from the current policy, so each batch is used for one step and then discarded. PPO makes the data usable for several steps. It uses the importance ratio \( r(\theta) = \pi_\theta(a \mid s) / \pi_{\text{old}}(a \mid s) \) and maximizes
\[ L = \mathbb{E}\big[ \min\big( r A,\ \mathrm{clip}(r, 1 - \varepsilon, 1 + \varepsilon) A \big) \big] \]
with \( \varepsilon \) about 0.2. If the advantage is positive, the objective stops rewarding increases of r above \( 1 + \varepsilon \); if it is negative, it stops rewarding decreases below \( 1 - \varepsilon \). So the policy gets no incentive to move far from the old one on this batch. This lets PPO run several epochs (commonly 3 to 10) of minibatch updates on one batch, a cheap approximation of a trust region. A typical PPO loss adds a value-function loss and a small entropy bonus to keep exploring.
For language models, the "state" is the prompt plus the tokens so far, the "action" is the next token, and the reward comes at the end of the response, from a learned reward model (RLHF) or from a checker (such as unit tests or an answer match). A penalty on the KL divergence from a reference model (the supervised starting point) is added to the reward, so the model does not drift into text that fools the reward. PPO needs four large models: policy, reference, reward model and critic. GRPO removes the critic. For each prompt it samples a group of G answers, scores them, and defines each answer's advantage as (reward − group mean) / group standard deviation. All tokens of an answer share that advantage, and the PPO-style clipped objective is used on top.

example: Take a policy with two actions, A and B, and logits θ = (0, 0), so the probabilities are (0.5, 0.5) (softmax of the logits). For a softmax policy, the gradient of log π(a) with respect to the logit of action i is \( \mathbf{1}[i = a] - \pi_i \). Suppose action A pays reward 1 and action B pays 0, and we use a baseline b = 0.5, the expected reward. Use learning rate 1.0.
Sample action A: reward 1, advantage = 1 − 0.5 = +0.5. The update to logit A is 0.5 × (1 − 0.5) = +0.25 and to logit B is 0.5 × (0 − 0.5) = −0.25. The logits become (0.25, −0.25), and \( \pi(A) = 1 / (1 + e^{-0.5}) \approx 0.62 \). Sample action B instead: reward 0, advantage −0.5. The update to logit B is −0.5 × (1 − 0.5) = −0.25 and to logit A is −0.5 × (0 − 0.5) = +0.25. Same result. Both samples move the policy toward A. Without a baseline, sampling B would give no update at all, and sampling A would give (+0.5, −0.5) to the two logits. The average over many samples is the same (+0.25, −0.25), but single steps are noisier.
Now why a baseline matters. If the rewards were 11 for A and 10 for B, with no baseline each sample would push its own action up in proportion to 10 or 11, while the real difference between the actions is only 1, so the useful signal is buried in noise. Subtracting b = 10.5 gives advantages ±0.5 and the clean update above.
PPO clipping with ε = 0.2: suppose the new policy now gives an action probability 1.5 times the old one (r = 1.5) and the advantage is +2. The unclipped term is 1.5 × 2 = 3; the clipped term is clip(1.5, 0.8, 1.2) × 2 = 2.4; the min is 2.4, a constant, so its gradient is zero: this sample no longer pushes r higher. If the advantage were −2, the unclipped term is −3 and the clipped is −2.4; the min is −3, which still has a gradient and pulls r back down. Clipping thus acts only in the direction that would move the policy too far.
Last, GRPO for a language model. For one prompt, sample G = 4 answers and score them with a checker: rewards (1, 0, 0, 1). Mean 0.5, standard deviation 0.5, so the advantages are (+1, −1, −1, +1). The two correct answers get all their tokens pushed up, the two wrong ones pushed down. If only one answer in four is correct, rewards (1, 0, 0, 0): mean 0.25, standard deviation about 0.43, advantages (+1.73, −0.58, −0.58, −0.58), so a rare success is strongly rewarded. If all four are correct or all wrong, all advantages are 0 and the prompt teaches nothing.
intuition: Do more of what worked better than expected, and less of what worked worse than expected.
The design is natural because the one thing we can always do is try things and see the results. The log-derivative trick shows that "make the actions that preceded high rewards more likely" is not only a heuristic; it is the true gradient of the expected reward. The baseline is simply a comparison: judge an action against the typical outcome, not against zero. The clip says: do not trust one batch of experience enough to change much.
mistakes: People often think policy gradient needs a model of the environment. In fact the gradient only needs the log-probabilities of the policy's own actions and the observed returns. The transition probabilities drop out of the formula.
People often think a baseline changes what the algorithm learns. In fact it does not change the expected gradient; it only lowers its variance. A baseline that depends on the action, however, would add bias unless it is corrected.
People often think PPO's clipping is a hard constraint on the policy change. In fact it is a modification of the objective that removes the incentive to move beyond the clip range on the sampled actions; the policy can still drift beyond it through other actions or many updates, and implementation details (advantage normalization, value clipping, learning-rate schedule) strongly affect results.
People often think RLHF reward means the model is learning human values. In fact the model optimizes the score of a reward model or a checker, which is only a proxy. Pushed hard, it finds answers that score high without being good (reward hacking), which is why the KL penalty and early stopping exist.
tradeoffs: Choose policy gradient or actor-critic methods when actions are continuous or numerous, when a stochastic policy is needed, or when you fine-tune a generative model whose output is a sequence. Choose Q-learning when actions are few and discrete and sample efficiency is the priority, because off-policy value learning reuses data. You give up reuse of old data with policy gradients, and you gain a direct, stable improvement of the behaviour you care about.
Choose PPO when you want a robust default: a clipped objective, several epochs per batch, and plenty of public implementations. Choose TRPO only when you need a more principled constraint and can afford second-order computations. Choose newer off-policy actor-critic methods (SAC, TD3) for continuous control with expensive data, such as robots; you pay in more tuning and less stable learning.
Choose a learned critic (PPO) when rewards arrive at many time steps and credit assignment inside long episodes matters; choose a group baseline (GRPO) for LLM tasks with one reward per answer, where a critic would cost another full-size model and is hard to train. With GRPO you need several samples per prompt (commonly 4 to 64), which raises generation cost, and prompts where all samples agree give no signal.
Choose a learned reward model when the goal is hard to define (helpfulness, style) and humans can compare answers; choose a verifiable reward (tests pass, answer matches) when one exists, because it is cheaper and harder to game. You trade breadth for reliability: verifiable rewards cover only tasks that can be checked.
friction: Variance and sample cost are the main problems: policy gradients need many trajectories, and on-policy methods throw data away after each update. Long episodes make credit assignment hard: with a single reward at the end of a 1,000-token answer, it is unclear which token deserved credit. Training is sensitive to implementation details; two correct implementations of PPO can differ greatly in result, and hyperparameters (learning rate, clip range, batch size, advantage normalization) interact.
For language models, extra problems appear. Reward hacking and reward model over-optimization are common: the policy finds quirks that score high but are poor outputs (very long answers, flattery, special formatting). The KL penalty coefficient is hard to set. Entropy collapse is a risk: the policy becomes deterministic too early and stops exploring. Generation is the costly part, so RL training is bound by inference throughput, and PPO needs memory for four models. Rare rewards (a task the model almost never solves) give no gradient signal at all.
practice: Start from a tested implementation (Stable-Baselines3, CleanRL, TRL or similar libraries for language models) before writing your own. For classic control, use PPO with advantage normalization, GAE with λ about 0.95, γ about 0.99, learning rate around 3e-4, clip range 0.2, 4 to 10 epochs per batch, and watch the policy entropy and approximate KL between old and new policies. If the KL spikes, lower the learning rate or the number of epochs.
Log more than reward: mean episode return, entropy, value loss, explained variance of the critic, KL to the old policy and, for language models, KL to the reference model and the response length. A reward that rises while length or KL explode is usually reward hacking.
For language models, use a good supervised starting policy, keep a reference model for the KL penalty, normalize advantages within groups, filter prompts whose samples all get the same reward, and evaluate on held-out checks that are not part of the training reward. Prefer a verifiable reward when you can define one. If the problem is only to choose among a few options with immediate feedback (ad creatives, for example), a bandit is simpler than any policy-gradient method.
quiz: What does the policy gradient theorem say, in words? || The gradient of expected return equals the expected value of (gradient of the log-probability of each action) times (the return that followed). No model of the environment's dynamics is needed.
Why does subtracting a baseline not bias the gradient, and what does it change? || The expected value of \( \nabla \log \pi \) over actions is zero, so a baseline that does not depend on the action adds nothing in expectation. It reduces variance, which makes learning faster and more stable.
In PPO with ε = 0.2, ratio r = 1.5 and advantage +2, what is the objective value and its gradient? || min(1.5 × 2, 1.2 × 2) = min(3, 2.4) = 2.4. The clipped term is constant in r, so the gradient is zero: this sample no longer pushes the policy further.
GRPO samples 4 answers with rewards (1, 0, 0, 0). What are the advantages? || Mean 0.25, standard deviation about 0.433. Advantages: (1 − 0.25)/0.433 ≈ +1.73 for the correct answer and (0 − 0.25)/0.433 ≈ −0.58 for each wrong one.
Why would you choose GRPO over PPO for training a large language model on math problems with an answer checker? || GRPO needs no critic model, which saves a second model of the policy's size, and with a single end-of-answer reward the group average is a good baseline. The cost is multiple samples per prompt, and no signal on prompts where all samples agree.
interview: Derive the policy gradient and explain why the environment model is not needed. || Write \( J = \mathbb{E}_\tau[G(\tau)] \); \( \nabla J = \int G\, \nabla p_\theta(\tau) = \int G\, p_\theta \nabla \log p_\theta = \mathbb{E}[G\, \nabla \log p_\theta(\tau)] \). The log of the trajectory probability is a sum of log initial-state, log transition and log policy terms; only the policy terms depend on θ, so the transitions drop out. We estimate the expectation by sampling.
What problems does PPO solve compared with vanilla policy gradient and TRPO? || Vanilla policy gradient can take destructive steps and uses each batch once. TRPO limits the step with a KL constraint but needs second-order computation. PPO replaces the constraint with a clipped surrogate objective optimized by first-order methods, allowing several epochs per batch with simple code.
In RLHF with PPO, why is there a KL penalty and what happens if it is too small or too large? || It keeps the policy near the reference model so the policy does not exploit weaknesses in the reward model. Too small: reward hacking and degenerate text. Too large: the policy barely moves and the reward does not improve.
Why does GRPO normalize rewards inside each group, and when does it fail? || The group mean acts as a baseline and the standard deviation scales the advantage, so prompts of different difficulty give comparable updates. It fails to give signal when all samples have the same reward, and standard-deviation scaling can overweight prompts that are very easy or very hard.
How would you tell if your RL run is reward hacking? || Reward rises while quality measures on held-out checks do not, response length or formatting changes strangely, KL from the reference grows quickly, or manual samples show exploits. Use independent evaluations, cap length, and stop or adjust the KL coefficient.

@@ mcts
value: Some decisions are too big to search completely. In Go there are about 250 legal moves per turn and games last about 150 turns, so the tree of possible futures is far beyond any computer. Chess programs of the 1990s used alpha-beta search with a hand-written evaluation of positions, but nobody could write a good evaluation function for Go. Monte Carlo tree search (MCTS) takes another route: it grows a search tree gradually, spends most of its effort on the moves that look best, and judges a position by playing it out to the end many times and counting the results.
The algorithm needs only two things: a way to simulate the game (the rules) and a way to say who won. It can stop at any time and return its best move so far, so more thinking time simply gives a better answer. Combined with deep neural networks, it produced AlphaGo, which beat the Go champion Lee Sedol 4 to 1 in March 2016, and AlphaZero, which learned Go, chess and shogi from self-play alone. The same pattern, a search guided by a learned policy and value, is explored today for reasoning in language models and for planning in robotics and logistics.
Three lower concepts supply the parts. Monte Carlo methods (L4) give the evaluation: the average result of random playouts is an unbiased estimate of how good a position is, with error shrinking as \( 1/\sqrt{n} \). Trees (L3) give the data structure: a tree of positions whose nodes store visit counts and value sums, and which grows unevenly toward the promising lines. Multi-armed bandits (L2) give the selection rule: at each node, choosing which child to try next is a bandit problem, and the UCB rule balances using good moves against testing uncertain ones. The layer above, reinforcement learning, uses MCTS as a planning step that improves a policy beyond what the raw network knows.
terms: Simulation (rollout, playout) — playing a game from a position to the end, with random or fast simple moves, and recording who won.
Node statistics — for each tree node, N (the number of visits) and W (the sum of results), so the mean value is \( Q = W / N \).
UCT (upper confidence bound for trees) — the selection rule \( Q + c\sqrt{\ln N_{\text{parent}} / N_{\text{child}}} \): mean value plus a bonus that is large for rarely visited children.
Selection, expansion, simulation, backpropagation — the four phases of one MCTS iteration.
PUCT — a UCT variant used in AlphaGo and AlphaZero, in which a neural network's prior probability P for a move scales the exploration bonus.
Policy network and value network — neural networks that give prior move probabilities and an estimate of the winning chance of a position; AlphaZero uses one network with two outputs.
Self-play — the program plays against itself to generate training data; the search results are the training targets.
Transposition — different move orders reaching the same position, which a search may merge into one node.
history: Monte Carlo ideas in games began with Brügmann's 1993 Go program, which used random playouts, and with Bruce Abramson's 1990 work on expected-outcome evaluation. Real progress came in 2006. Rémi Coulom built the Go program Crazy Stone, which grew a tree with selective backups, and in the same year Levente Kocsis and Csaba Szepesvári published "Bandit based Monte-Carlo Planning", which proposed UCT: use the UCB1 rule from bandit theory (Auer, Cesa-Bianchi and Fischer, 2002) in every node, and proved that it converges to the optimal move. The name "Monte Carlo tree search" was proposed by Chaslot and others in 2008. Programs such as MoGo and Zen reached strong amateur level on 19×19 Go during the following years, which was far better than before but far from professional play.
DeepMind changed this. AlphaGo (Silver and others, Nature 2016) used a policy network trained on human games and then by self-play to guide the tree toward plausible moves, a value network to judge positions without playing them out, and fast rollouts mixed in. In October 2015 it beat the European champion Fan Hui 5 to 0 and in March 2016 Lee Sedol 4 to 1. AlphaGo Zero (Nature, October 2017) removed all human data and the rollouts: a single network trained by self-play, with MCTS as the policy-improvement step. AlphaZero (arXiv December 2017; Science 2018) used the same method for chess and shogi. MuZero (2019, Nature 2020) added a learned model, so the tree is searched in a learned latent space and no rule engine is needed.
how: The tree starts with one node, the current position. Each node stores visit count N and total value W for the player who moved into it. One MCTS iteration has four steps.
Selection. Start at the root and repeatedly move to the child with the highest score until you reach a node that has an untried move or is a leaf. The score is the bandit rule UCT: \( Q + c \sqrt{\ln N_{\text{parent}} / N_{\text{child}}} \), where \( Q = W / N \) is the average result so far and c is an exploration constant (about 1.4, or tuned). The first term favours moves that have worked; the second grows for moves that have been visited little, so every move eventually gets a chance. This is the UCB rule from multi-armed bandits applied at every node, and it is the reason the search keeps its regret small: it wastes few visits on bad moves.
Expansion. Add one new child node for an untried move at the selected leaf.
Simulation (evaluation). Estimate the value of the new node. In classic MCTS, play random (or lightly guided) moves from there to the end of the game and record the result: win 1, loss 0. This is the Monte Carlo part (L4): the mean over many random playouts estimates the winning chance, and the standard error of that mean falls as \( 1/\sqrt{n} \). In AlphaGo Zero style, skip the playout and ask the value network for an estimate of the winning probability.
Backpropagation. Walk back up the path from the new node to the root, adding 1 to every N and adding the result to every W (flipping the sign at each level, because what is good for one player is bad for the other).
After thousands of iterations, the move to play is the root child with the most visits (more robust than the highest average, since visits reflect both value and confidence). Part of the tree is reused for the next move.
AlphaZero changes two things. First, the selection rule is PUCT: \( \text{score} = Q + c_{\text{puct}} \cdot P \cdot \sqrt{\sum N} / (1 + N) \), where P is the prior probability given by the policy head of the network. A move the network thinks is promising gets a large bonus even before it is visited, so the search concentrates on a handful of plausible moves instead of all 250. Second, each leaf is evaluated by the value head, not by random play, and the network is trained on the outcome: the policy head learns to predict the root's visit distribution (the search's improved policy), and the value head learns the final game result. So the search teaches the network, and the better network makes the search stronger: a loop of policy improvement (search) and policy evaluation (the game result). Dirichlet noise is added to the prior at the root during self-play to keep exploring. At about 800 to 1,600 simulations per move, a game of 200 moves needs more than 100,000 network evaluations, which is why training used thousands of TPUs.
What does the search guarantee? Kocsis and Szepesvári proved that with UCT the probability of choosing a suboptimal move at the root goes to zero as the number of simulations grows, and that the estimated values converge to the minimax values of the game. The convergence is slow in the worst case (the number of simulations can grow very fast with depth), so the practical strength comes from the speed of the first thousands of simulations and from good priors, not from the limit. The search handles terminal positions simply: if the rules say the game is over in a node, its result is exact and no playout is needed. In self-play, the move actually played is sampled from the visit counts in proportion to \( N^{1/\tau} \) in the first moves of a game (with temperature \( \tau = 1 \), for variety), and then chosen greedily, so openings differ from game to game while later play is strong.
The tree grows asymmetrically: good lines get deep, poor ones stay shallow. Memory is one node per simulation, so 10,000 simulations per move means about 10,000 nodes, which is small. Parallel search needs care: many threads may select the same path, so "virtual loss" temporarily penalizes a node while one thread is working on it.

example: Take the root with three candidate moves and 10 simulations so far. Results are recorded as win = 1, loss = 0. Move A has N = 5 and W = 3.5, so Q = 0.70. Move B has N = 3, W = 1.2, Q = 0.40. Move C has N = 2, W = 1.0, Q = 0.50. Use UCT with c = 1 and ln 10 ≈ 2.303.
Scores: A = 0.70 + √(2.303 / 5) = 0.70 + 0.68 = 1.38. B = 0.40 + √(2.303 / 3) = 0.40 + 0.88 = 1.28. C = 0.50 + √(2.303 / 2) = 0.50 + 1.07 = 1.57. The search selects C, although A has the best average, because C has been tried only twice and its true value is still uncertain. Suppose the simulation from C's new child is a win. Backpropagation updates C to N = 3, W = 2.0 (Q = 0.67) and the root to N = 11. In the next iteration the bonus term for C drops, and A or C may lead, depending on the results.
Now PUCT with a prior. The network gives priors P = 0.5, 0.3 and 0.2 to three moves X, Y and Z. After 53 total visits, X has N = 40 with Q = 0.55, Y has N = 10 with Q = 0.50, and Z has N = 3 with Q = 0.20. With c_puct = 1.5 and √53 ≈ 7.28, the scores are: X = 0.55 + 1.5 × 0.5 × 7.28 / 41 = 0.55 + 0.13 = 0.68. Y = 0.50 + 1.5 × 0.3 × 7.28 / 11 = 0.50 + 0.30 = 0.80. Z = 0.20 + 1.5 × 0.2 × 7.28 / 4 = 0.20 + 0.55 = 0.75. The next visit goes to Y: a move with decent value, a reasonable prior and few visits. X has the best value and the highest prior, but it has already received most visits, so its bonus is small.
Last, a cost check. A chess or Go game of 200 moves with 800 simulations per move needs 160,000 network evaluations for one game. At 5 ms per evaluation on one accelerator that is 800 seconds for one game on a single device, which is why self-play runs on thousands of devices in parallel; and why, for deployment, the number of simulations is set from the time budget.
intuition: Think ahead mostly along the lines that look good, but keep checking a few that have not been tried much, and trust what the playouts tell you.
The design is natural because it turns a search problem into a sequence of cheap bets. Averaging random outcomes gives a value estimate without any knowledge of the game. The bandit rule decides where an extra look is worth the most: it moves effort toward moves that are good and toward moves that are uncertain, and away from moves that are clearly bad. The tree remembers what was learned, so later iterations build on earlier ones. Add a network that supplies the priors and the evaluation, and the search needs far fewer simulations to reach the same strength.
mistakes: People often think MCTS is random play. In fact the random playouts are only the evaluation step. The selection step is a careful bandit rule, and the tree concentrates the effort. In AlphaZero there are no random playouts at all.
People often think AlphaGo's strength came from the neural network alone. In fact the network without search is a good but much weaker player; the search adds a large amount of strength. The networks and the search improve each other.
People often think the move with the highest average value should be played. In fact a move with a high average and few visits may be luck. Visit count is the more robust choice, since UCT sends visits to moves that stay good.
People often think MCTS works for any decision problem. In fact it needs a fast simulator (or a learned model), a clear end or a value function, and a manageable branching factor. It struggles with hidden information (poker needs different methods, or tricks such as determinization), with continuous or huge action spaces, and with rewards that are hard to define.
tradeoffs: Choose MCTS when you have a simulator or exact rules, decisions are sequential, and no good hand-written evaluation function exists (Go, many board games, planning problems). Choose alpha-beta search with a handcrafted or learned evaluation when the game is tactical, has a small branching factor and strong evaluation functions (classical chess engines such as Stockfish used alpha-beta, later with a neural evaluation); you gain exact depth-first pruning, and give up the ability to work without an evaluation.
Choose random rollouts when you have no network and cheap rules; choose a learned value (and policy prior) when rollouts are noisy or too long. Rollouts cost many steps per evaluation and have high variance in long games; a network evaluation costs one forward pass (milliseconds) but needs training data and may have blind spots that the search can exploit.
Choose more simulations per move when time allows and the position is critical; choose fewer when latency is tight. Strength grows roughly logarithmically with simulations: doubling the budget gives a smaller and smaller gain, so a budget of 800 can be close to 1,600 in practice.
Choose model-based search (MuZero style) when the environment's rules are unknown or too slow, and accept the cost of training the model and the risk that errors in the model mislead the search. Choose model-free policy learning (policy gradient) when no planning is needed and decisions must be made in a few microseconds.
friction: MCTS needs a simulator and many simulations per decision; in the real world, a simulator is usually the missing piece. Each decision costs thousands of evaluations, so latency and compute are significant, and the training loop of AlphaZero used a very large amount of hardware.
The method also struggles in several settings. Games with hidden information break the assumptions (the tree must be built over beliefs, as in information-set MCTS). Large or continuous action spaces need progressive widening or sampled actions. Sparse and late rewards give noisy playout results. Tactical positions where one forced sequence decides the game can be missed, because MCTS averages results and a single refutation can be hidden under many good outcomes; AlphaGo's single loss to Lee Sedol (game 4) is often attributed to such a gap. Self-play can also settle into narrow styles and be exploited by adversarial opponents, as studies of superhuman Go programs have shown.
For language models, tree search over reasoning steps has been explored (Tree of Thoughts, reasoning with a world model, process reward models), but defining a step, a reliable value function and a cheap simulator is hard, and some groups reported that MCTS did not scale well for their reasoning training, relying instead on long chains of thought trained by policy gradient. Search at inference time remains an active research area.
practice: Start with a clear problem statement: do you have an exact simulator, a bounded number of moves, and a reward at the end? If yes, plain UCT is a few dozen lines: a Node class with children, N and W; a selection loop; a rollout function; and backup. Test it on tic-tac-toe or Connect Four, where you can compare with an exact solver.
Tune the exploration constant c on your reward scale (rewards in [0, 1] suggest 0.7 to 1.4), use the most visited child as the final move, and reuse the subtree between moves. Add domain knowledge in rollouts (cheap heuristics beat uniform random play) and consider RAVE or progressive bias as long as no network is available. Use virtual loss if you parallelize.
For neural-guided search, use PUCT with a policy prior, keep c_puct near 1 to 2, add Dirichlet noise at the root during training only, and batch network evaluations across many simultaneous searches to keep the accelerator busy. Open-source projects such as KataGo and Leela Zero, and the AlphaZero tutorials in Python, show the full loop.
Outside games, MCTS has been used for planning in compilers (choosing optimization sequences), chemical synthesis planning and program synthesis, where a cheap simulator exists. Check that a simpler optimizer (beam search, bandit, or an evolutionary method) does not give the same result with less machinery.

interview: Explain why UCT balances exploration and exploitation, and how it relates to bandits. || Each node faces a bandit problem: which child to try. UCB1 picks the child with the highest upper confidence bound on its value, which gives logarithmic regret in the bandit setting. UCT applies it recursively, with the caveat that child values are non-stationary because the subtrees below keep changing.
What is the role of the policy and value networks in AlphaZero, and what are they trained on? || The policy head gives priors that focus the search on plausible moves; the value head replaces rollouts. How would you parallelize MCTS across threads or machines? || Run several simulations at once with shared tree statistics and virtual loss, so threads do not all follow the same path; or run independent trees and merge root statistics (root parallelism). What are the failure modes of MCTS in a real-world planning problem such as warehouse routing? || The simulator may be slow or wrong, rewards may be sparse or delayed, branching may be huge or continuous, and the horizon long. Use a learned model carefully, restrict actions, add heuristics for rollouts, and compare with simpler optimization methods such as integer programming or local search.

@@ bandits
value: Many decisions repeat: which of five ad creatives to show, which headline to use, which recommended item to put first, which price to try. You do not know which option is best, and you only learn about an option by using it. Every time you try a weaker option to learn more, you lose some reward; every time you stick to the option that looks best, you risk missing a better one that looked bad by chance. This is the explore-exploit trade-off, and the multi-armed bandit is its cleanest form: K options ("arms"), each with an unknown reward rate, and one choice per round.
Bandit algorithms give a rule for this choice that provably loses little. The loss is measured by regret: the reward you would have collected by always playing the best arm, minus what you collected. A fixed A/B test splits traffic evenly until it ends, so its regret grows linearly during the test. Good bandit algorithms have regret that grows only like log T, because they send less and less traffic to arms that are clearly worse. This is why bandits sit inside ad tech (creative and bid selection), recommender systems (trying new items), experimentation platforms, and as the decision rule inside Monte Carlo tree search.
The layers below supply the three parts. Probability (L4) provides the model of each arm's rewards, such as a Bernoulli click with unknown rate p, and the idea of drawing samples from a distribution. Bayesian inference (L4) provides the belief update: with a Beta prior, each click or non-click moves the posterior of an arm by simple counting, and Thompson sampling acts on the posterior. Statistics and estimation (L4) provide the confidence bounds: how uncertain an average is after n trials, which UCB uses to decide how much optimism an arm deserves.
terms: Arm — one option you can choose; each arm gives a random reward drawn from its own unknown distribution.
Regret — the expected reward lost compared with always choosing the best arm; the main measure of a bandit algorithm.
Exploration and exploitation — exploring means choosing an arm to learn about it; exploiting means choosing the arm that currently looks best.
ε-greedy — with probability ε pick a random arm, otherwise pick the arm with the highest average reward.
UCB (upper confidence bound) — pick the arm whose average plus an uncertainty bonus is highest, so that rarely tried arms are given the benefit of the doubt.
Thompson sampling — keep a probability distribution over each arm's reward rate, draw one sample from each, and play the arm with the highest sample.
Beta distribution — a distribution on [0, 1] used as the belief about a click rate; after s clicks and f non-clicks from a Beta(1, 1) start it becomes Beta(1 + s, 1 + f).
Contextual bandit — a bandit in which each round has features (user, page, device) and the best arm depends on them.
history: The problem was posed by William R. Thompson in 1933, in a paper on how to allocate patients between two medical treatments as evidence accumulates; he proposed the sampling rule now named after him. Herbert Robbins formalized the multi-armed bandit in 1952. The name comes from slot machines ("one-armed bandits"). Gittins (1979) found an optimal index policy for the discounted Bayesian version, elegant but hard to compute in practice. Lai and Robbins (1985) proved a lower bound: any reasonable algorithm must suffer regret that grows at least like log T, with a precise constant given by the KL divergence between the arms' reward distributions.
Auer, Cesa-Bianchi and Fischer (2002) gave UCB1, a simple algorithm with a finite-time logarithmic regret bound, and EXP3 for adversarial rewards. Thompson sampling was largely forgotten until around 2010, when Scott's work on Bayesian bandits for web experiments and the empirical study by Chapelle and Li (NeurIPS 2011) showed it often beat UCB in practice; Agrawal and Goyal (2012) and Kaufmann and others (2012) then proved it reaches the Lai-Robbins bound.
The web made bandits a daily tool. Li, Chu, Langford and Schapire (WWW 2010) introduced LinUCB, a contextual bandit for personalized news article selection at Yahoo!, and showed how to evaluate such policies offline from logged data. Large platforms use bandits for ad creative selection, recommendation carousels, notification timing and artwork choice, and Google Analytics Content Experiments (2013) offered bandit-based tests. Research has since extended them to delayed feedback, non-stationary rewards, and combinatorial choices (rankings).
how: Model each arm i as giving a reward with unknown mean \( \mu_i \). At each round t the algorithm picks an arm, sees its reward, and updates. The three main strategies differ only in how they pick.
ε-greedy: keep the average reward of each arm. With probability \( 1 - \varepsilon \) play the arm with the highest average; with probability ε play a random arm. It is simple, but it keeps exploring at the same rate forever and wastes the exploration on arms that are already known to be bad, so its regret grows linearly (ε times the average gap per round) unless ε is decreased over time.
UCB (UCB1): play the arm with the largest value of \( \text{mean}_i + \sqrt{2 \ln t / n_i} \), where \( n_i \) is the number of times arm i has been played. The second term is a confidence radius from statistics (Hoeffding's inequality): it is large when n_i is small and shrinks as an arm is played, but grows slowly with ln t for arms that are not played, so they eventually get another turn. This is "optimism in the face of uncertainty": assume each arm is as good as it plausibly could be. The regret bound is on the order of \( \sum_i (\ln T) / \Delta_i \) over suboptimal arms, where \( \Delta_i \) is the gap to the best arm.
Thompson sampling: keep a posterior distribution for each arm. For a click rate use a Beta distribution: start from Beta(1, 1) (uniform), and after s clicks and f non-clicks the posterior is Beta(1 + s, 1 + f) by Bayes' rule. Each round, draw one random sample from each arm's posterior and play the arm with the highest sample. An arm with a wide posterior (few trials) produces widely varying samples and is often chosen when its sample is high; an arm with a narrow posterior and a low mean is almost never chosen. Exploration is thus proportional to the probability that the arm is the best, which is exactly what is needed. It needs no tuning constant, handles delayed or batched updates naturally (just keep drawing from the current posterior), and extends to other reward distributions with their conjugate priors.
Why does the UCB bonus work? After n plays, Hoeffding's inequality says the true mean lies within \( \sqrt{\ln(1/\delta) / 2n} \) of the sample mean with probability at least \( 1 - \delta \). UCB sets δ so that the bound holds for all arms and rounds with high probability. Then a suboptimal arm can only be chosen when its optimistic estimate beats the best arm's, and that requires its bonus to be at least about half its gap \( \Delta_i \), which happens only while \( n_i \) is smaller than about \( 8 \ln T / \Delta_i^2 \). So each bad arm is played about \( (\ln T)/\Delta_i^2 \) times, costing \( \Delta_i \) each, and the sum gives the logarithmic regret. The same counting explains the practical rule: halving a gap makes the arm four times as expensive to rule out. Thompson sampling reaches the same order by a different argument: the probability that a bad arm's sample exceeds the best arm's decays quickly as its posterior narrows.
Contextual bandits add features x. LinUCB assumes the expected reward is linear in features, \( \mu(x, a) = \theta_a^\top x \), maintains ridge-regression estimates of θ_a with a covariance matrix, and adds a bonus proportional to \( \sqrt{x^\top A^{-1} x} \), the uncertainty for this particular context. Linear Thompson sampling samples θ from its Gaussian posterior. Neural contextual bandits use a network for the reward model, with dropout or ensembles for uncertainty.
All of these are judged by regret. For K arms and horizon T, good stochastic algorithms have regret \( O(\sum_i \ln T / \Delta_i) \), and no algorithm can do better than order \( \ln T \) in the worst case for a fixed set of arms (Lai-Robbins). For adversarial rewards, EXP3 achieves \( O(\sqrt{K T \ln K}) \), which is the price of making no assumptions.
Practical systems also need an update loop: log the arm shown, the context and the reward; update counts or posteriors in batches (every few minutes is enough at web scale); serve decisions from the current posterior. Keep a small share of traffic on a uniform or fixed policy, because it is the only source of unbiased data for later offline analysis.

example: Three creatives have true click-through rates of 2.0%, 2.5% and 3.0%, unknown to us. We serve 1 million impressions. Always showing the best would give 30,000 clicks.
Option 1, a fixed A/B/C test with equal thirds for the whole time: the average rate is 2.5%, so 25,000 clicks. Regret: 5,000 clicks.
Option 2, a classic test followed by exploitation: test with equal split for the first 100,000 impressions (regret about 100,000 × 0.5% = 500 clicks), then show the winner. If the test picked the 3.0% creative, the total regret is about 500. But the test must be large enough to separate 2.5% from 3.0%; with 33,000 impressions per arm the standard error of each rate is about 0.09 percentage points, so the 0.5-point gap is about 4 standard errors and the winner is usually right; with a shorter test, the wrong creative may be chosen for the remaining 900,000 impressions, costing up to 4,500 clicks.
Option 3, Thompson sampling or UCB with logarithmic regret. The asymptotic Lai-Robbins formula gives regret ≈ \( \sum_i \Delta_i \ln T / \mathrm{KL}(p_i, p^*) \). For the 2.0% arm: Δ = 0.01, KL(0.02, 0.03) ≈ 0.00194, giving 0.01 × 13.8 / 0.00194 ≈ 71 clicks. For the 2.5% arm: Δ = 0.005, KL ≈ 0.000455, giving about 152 clicks. Total about 220 clicks, roughly 20 times less than a fixed test, in the best case; real algorithms have extra constant terms, but the order is a few hundred clicks.
Now a Thompson step. Arm A has 10 clicks and 190 non-clicks: Beta(11, 191), mean 5.4%. Arm B has 3 clicks and 37 non-clicks: Beta(4, 38), mean 9.5% but wide. Draw one sample from each. Simulating many such pairs, B's sample is higher about 80% of the time, so B gets most of the next impressions, even though only 40 observations back it. If B then gets 3 clicks in 40 more views, Beta(7, 75) has mean 8.5%, and as its estimate falls toward A's, its share falls too. Contrast with UCB1: with rewards in [0, 1] the bonus is √(2 ln 1000 / 600) = 0.15 for an arm with 600 plays but √(2 ln 1000 / 40) = 0.59 for one with 40 plays. For click rates around 5%, such bonuses dwarf the differences between arms, so plain UCB1 over-explores in ad problems; use tuned or KL-based variants, or Thompson sampling.
intuition: Several slot machines in a casino: spend most coins on the one that seems best, but keep testing the ones you know little about, because a lucky first impression can mislead you.
The design is natural because uncertainty is the real reason to explore. An arm you know well needs no more tests; an arm you know poorly may be much better than it looks. UCB turns this into a number (an optimistic estimate) and Thompson sampling turns it into a random choice whose probability equals the chance of being best. Both automatically stop wasting trials as evidence builds up, and that is why regret grows only logarithmically.
mistakes: People often think a bandit is just a faster A/B test. In fact it optimizes a different goal. A/B testing estimates effects with controlled error; a bandit maximizes reward during the experiment. Because bandit traffic is uneven and adaptive, the data are poor for clean effect-size and p-value estimates, especially for losing arms that got little traffic.
People often think exploration is waste. In fact it is the investment that finds the best option. Without exploration, a greedy policy can lock on an inferior arm forever after an unlucky start, and its regret grows linearly.
People often think the best arm is a fixed fact. In fact in web and ad systems the best arm changes with time of day, season, audience and fatigue. A bandit that assumes fixed rewards will go stale unless you discount old data or use a sliding window.
People often think more arms is harmless. In fact regret grows with the number of arms, because each needs some tests. With 1,000 creatives and little traffic, a plain bandit takes very long; use contexts, shared structure (features of the creative) or a smaller candidate set.
tradeoffs: Choose Thompson sampling as the default for click and conversion problems: it has no constant to tune, performs well empirically, and works with batch updates and delay. Choose UCB when you need a deterministic, auditable choice and a proven bound, accepting that it can over-explore with small rates unless tuned. Choose ε-greedy only for a first version or when you cannot maintain posteriors, and expect to pay for the constant exploration (with ε = 0.1, 10% of traffic is always spent randomly).
Choose a bandit when the goal is to maximize reward during the test, when options are many or short-lived (headlines, daily deals), and when the cost of showing a weak option is real. Choose a classic A/B test when you need a reliable estimate of the effect size, a decision that will be reviewed, or protection against hidden confounders; you give up some reward during the test. Many teams run a bandit for allocation and a small fixed holdout for measurement.
Choose a contextual bandit when the best choice clearly depends on the user or situation and you have thousands of events per context; choose a context-free bandit with a few segments when data are thin, because a rich model learns slowly and may reduce reward at first. A contextual model needs careful offline evaluation (inverse propensity weighting or doubly robust estimators) before launch.
Choose a bandit rather than full reinforcement learning when your choice affects only the immediate reward. If actions change the user's future state (a recommendation that shapes later behaviour, budget pacing through the day), you are in sequential decision territory where Q-learning or policy gradients may be needed, at much higher data cost.
friction: Real feedback is delayed. A conversion may come hours or days after the impression, and a bandit that treats "no conversion yet" as failure will punish slow-converting arms. Delayed-feedback models, or using a faster proxy reward, are needed. Rewards also change over time, so old data must be down-weighted; discounted or sliding-window variants help but add a tuning parameter.
Inference is harder. Because arm choice depends on past rewards, standard estimates of arm means are biased and confidence intervals are invalid unless handled with specific methods (such as inverse-propensity weighting or anytime-valid inference). A bandit may starve an arm whose early results were unlucky. Interference between arms (users see several creatives, creatives compete for the same budget or inventory) breaks the independence assumption.
Systems problems are real too: you need to log the probability with which each arm was chosen (propensity) to evaluate policies later; serving decisions must be fast (milliseconds); and updates from distributed servers must be merged without delay. Safety constraints (never show a certain ad to a certain user, brand safety, pacing and budget limits) make the plain bandit model too simple, and constrained bandits and budgeted bandits exist but are more complex.
practice: Define the reward carefully: a click, a conversion, revenue per impression. Choose one that arrives quickly and that you actually care about, and write down how you handle delayed conversions. Start with Thompson sampling with Beta priors for binary rewards (use a weak, informative prior such as Beta(1, 1) or one based on the average rate), or Gaussian posteriors for continuous rewards.
Always log the context, the chosen arm, the probability of choosing it and the reward. Keep a small exploration floor (for example 5% of traffic chosen uniformly at random) so that new arms get data and so that you have unbiased samples for offline evaluation. Add new arms with a prior that matches the typical rate, or with a short forced warm-up.
Handle non-stationarity: use a discount factor on old counts (for example multiply counts by 0.99 per day) or a sliding window; monitor each arm's rate over time. Watch for seasonal patterns and time-of-day effects by including them as context. Evaluate contextual policies offline with inverse propensity scoring or doubly robust estimators before putting them live, and compare them to a simple non-contextual baseline.
Finally, keep measurement separate from optimization: hold out a fixed share (say 5 to 10%) on a control arm for reporting lifts, and run a classic A/B test when a decision needs strong evidence. For ad tech uses such as creative selection or bid shading, start with the bandit on one small decision before moving to anything with long-term effects.
quiz: What is regret in a bandit problem, and what growth rate is achievable? || Regret is the reward lost compared with always playing the best arm. Good algorithms achieve regret that grows only like ln T (logarithmic), and no algorithm can do better in general (Lai-Robbins lower bound). A fixed even split has linear regret.
How does Thompson sampling choose an arm? || It draws one sample from each arm's posterior distribution over its reward rate and plays the arm with the highest draw. Arms with uncertain beliefs sometimes draw high samples, so they get explored in proportion to the chance that they are best.
An arm has 4 clicks and 36 non-clicks. With a Beta(1, 1) prior, what is its posterior and mean? || Beta(1 + 4, 1 + 36) = Beta(5, 37). The mean is 5 / 42 ≈ 11.9%.
Three creatives with CTRs 2.0%, 2.5% and 3.0% get 1 million impressions. What is the regret of an even three-way split compared with always showing the best? || The average CTR is 2.5%, giving 25,000 clicks versus 30,000 for the best, so regret is 5,000 clicks.
When should you prefer a classic A/B test to a bandit? || When you need an unbiased estimate of the effect size for a decision that will be reviewed, when the cost of showing a weaker option during the test is small, or when interference and long-term effects make adaptive allocation risky.
interview: Compare ε-greedy, UCB and Thompson sampling. When does each fail? || ε-greedy explores at a constant rate, so regret is linear unless ε decays; it is simple. UCB is deterministic with a log-regret proof but can over-explore with low rates because the bonus is large compared with the gaps. Thompson sampling needs a model and a posterior, but explores adaptively and performs well in practice; it can fail with a badly misspecified prior or model, or with heavy delayed feedback if handled naively.
Why is a bandit's data a problem for estimating the effect of each arm, and what can you do? || Arm selection depends on past outcomes, so the arm means are biased, losing arms get little data and standard errors are wrong. Log propensities and use inverse-propensity weighting, keep a fixed-probability holdout, or use methods designed for adaptive data (anytime-valid confidence sequences).
You run a bandit on ad creatives and conversions arrive up to 3 days late. What goes wrong and how do you fix it? || Recent impressions show no conversion yet, so recent arms look worse and new arms are penalized. Fixes: model the delay distribution and treat recent impressions as censored, use a faster proxy such as clicks or add-to-cart, or update only with impressions old enough for the conversion window.
How would you evaluate a new contextual bandit policy offline before launch? || Use logged data from a randomized policy with recorded propensities. Compute inverse-propensity-scored or doubly robust estimates of the new policy's reward, check the variance and effective sample size, and look for context-action pairs that the log never explored. Then launch gradually against a control.
Where do bandits appear inside other algorithms? || Monte Carlo tree search uses UCB to choose the child to explore in each node; hyperparameter search (successive halving, Hyperband) allocates budget like a bandit; and the exploration in recommender systems and adaptive experiments is a bandit.

@@ invindex
value: To find the documents that contain the words "kafka" and "partition", the obvious method is to read every document and check. For a billion documents that takes minutes or hours, and every query repeats the work. An inverted index does the work once, in advance. It stores, for each distinct term, a sorted list of the IDs of the documents that contain it (a posting list). A query then looks up the lists of its terms and combines them: intersect two lists for AND, merge them for OR. The cost depends on the length of the lists, not on the size of the collection.
The name "inverted" is historical: a normal ("forward") index maps a document to its words; this one inverts the mapping, from word to documents. It is the core data structure of search engines (Lucene, Elasticsearch, OpenSearch, Solr), of web search, of log and observability tools, and of the equality filters in many analytical databases such as Apache Pinot and Druid, where the "term" is a column value and the list is the set of rows that have it.
For the layer above (search engines, real-time analytics), the inverted index turns filtering and text matching into cheap operations on sorted integers. Four lower concepts make it work. Sorting (L3) keeps posting lists in document-ID order, so two lists can be intersected by a linear merge, and builds the index by merging sorted runs. Trees and tries (L3) organize the dictionary of terms for fast lookup and prefix search. Hashing (L3) lets the indexer collect postings in memory as documents arrive. Suffix arrays (L2) cover what word-based indexes cannot: matching arbitrary substrings, or searching DNA, where there are no words.
terms: Term — a normalized unit of text that is indexed, usually a lowercased and stemmed word.
Posting list (postings) — the sorted list of document IDs for one term, often with extra data per entry.
Term frequency (tf) and document frequency (df) — tf is how often a term appears in one document; df is how many documents contain the term.
Positional index — an index whose postings also store the positions of the term in each document, which enables phrase queries.
Term dictionary — the sorted structure that maps each term to the location of its posting list.
Segment — an immutable, self-contained piece of an index; new documents create new segments, which are merged in the background.
Skip pointers — extra entries in a posting list that allow jumping forward over many IDs when intersecting with a short list.
BM25 — the standard ranking formula that scores a document for a query from tf, df and document length.
history: Indexes of this kind are older than computers: concordances of the Bible and the book index at the back of a printed book map words to places. In the 1950s and 1960s information-retrieval pioneers such as Hans Peter Luhn and Gerard Salton (the SMART system at Cornell, from the 1960s) built the first automatic text indexes and the vector-space ranking models used with them. For the first decades of the web, search engines of the 1990s (AltaVista, then Google, 1998) used inverted indexes sharded over many machines.
The key engineering steps were about size and speed. Compression of posting lists using gaps between document IDs (Elias, Golomb and variable-byte codes) made indexes small enough to fit in memory or cache (Witten, Moffat and Bell, "Managing Gigabytes", 1994). Google's 1998 paper by Brin and Page described the web index as barrels of inverted lists, and large engines soon sharded such indexes over many machines. Ranking moved from tf-idf to BM25, developed by Robertson and colleagues in the 1990s at City University London and the Okapi system; it became Lucene's default in version 6 (2016).
Doug Cutting created Lucene in 1999, and it became the basis of Solr (2004), Elasticsearch (2010) and OpenSearch. Later Lucene versions added the finite-state-transducer term dictionary (Lucene 4, 2012), the immutable-segment design with background merges, and block-based compression. Recent work includes SIMD-friendly integer compression (Lemire and Boytsov, 2015), Roaring bitmaps for dense lists (Chambi, Lemire and others, 2016) and dynamic pruning algorithms such as WAND and block-max WAND (Broder and others, 2003; Ding and Suel, 2011), which Lucene 8 (2019) adopted to return top-k results without scoring every match.
how: Building the index has four steps. First, analysis: each document's text is split into tokens (words) and normalized: lowercase, strip accents, optionally remove stop words ("the", "of") and reduce words to stems ("partitions" to "partition"). The same analysis must be applied to queries. Second, the indexer collects postings in memory, using a hash map from term to a growing list of (document ID, term frequency, positions). Third, when memory is full or after a refresh interval, the in-memory data are sorted by term and written to disk as an immutable segment: a term dictionary, posting lists, and per-document data. Fourth, a merge policy combines small segments into larger ones in the background, as external merge sort does with sorted runs.
Posting lists are stored in sorted document-ID order. In Lucene they are split into blocks of 128 IDs, each block stored as the differences (gaps) between consecutive IDs, packed with the smallest number of bits that fits the largest gap in the block; this frame-of-reference encoding can be decoded with SIMD instructions at billions of integers per second. A small header per block holds its last ID, and a skip structure above the blocks (one level every 128 IDs, another every 32 blocks) lets a reader jump forward without decoding the skipped blocks. The reason for gaps: the IDs in a long list are close together, so the gaps are small numbers needing 2 to 8 bits instead of 32.
The term dictionary maps each term to its posting list. It must support exact lookup, prefix search (for autocomplete and wildcard queries) and range search over sorted terms. Terms are sorted, so a binary search works, but real systems use a trie-like structure: Lucene stores terms in sorted blocks and keeps an index over their prefixes as a finite-state transducer (FST), a compact automaton that shares both prefixes and suffixes. The structure fits in memory even for hundreds of millions of terms, and it gives the location of the block to read from disk.
Query processing for a conjunction (kafka AND partition) fetches both lists and intersects them. The efficient way is to start from the shortest list and, for each ID in it, ask the longer list to advance to that ID, using skip data to jump over large ranges. The cost is then close to (length of the short list) × (a small cost per jump) rather than the sum of lengths. For OR, the lists are merged. For NOT, the second list is subtracted. Phrase queries ("partition leader") first intersect the lists, then check positions in the survivors: the positions of "leader" must be exactly one more than those of "partition". Wildcards use the dictionary: expand prefix* into the matching terms and union their lists. Substring search ("*art*") cannot use a word dictionary efficiently, which is where n-gram indexes or suffix arrays come in.
Ranking uses statistics stored in the index. BM25 gives a document a score for each query term: \( \text{idf}(\text{term}) \times \text{tf}\,(k_1 + 1) / (\text{tf} + k_1 (1 - b + b \cdot \text{length}/\text{avg\_length})) \), with common defaults k1 = 1.2 and b = 0.75. Rare terms (high idf) count more, repeated terms count with diminishing return, and long documents are normalized. To return the top 10 out of millions of matches, engines use dynamic pruning (WAND, block-max WAND): each list stores an upper bound on the score it can add, and documents that cannot beat the current tenth-best score are skipped without full scoring.
Updates are handled by immutability. A new document goes into a new small segment. A delete only sets a bit in a per-segment "live documents" bitmap, and the space is reclaimed when segments merge. An update is a delete plus an insert. Searches read all segments and combine their results. Elasticsearch makes new documents searchable after a refresh, one second by default, which creates a new segment each time, and background merges keep the segment count small.
In a cluster, the index is usually split by document: each shard holds a full inverted index for a subset of documents; a query goes to all shards (scatter), each returns its local top-k, and a coordinator merges them (gather). OLAP engines such as Pinot apply the same structure to column values, storing for each value a compressed bitmap (Roaring) of row IDs, so a filter such as country = 'IN' AND device = 'tv' is a bitwise AND of two bitmaps.

Now sizes. A collection has 1 billion documents. The word "kafka" appears in 2 million of them. Stored as 4-byte integers the list needs 8 MB. The average gap is 1,000,000,000 / 2,000,000 = 500, so most gaps fit in about 9 or 10 bits; with block packing the list takes about 2,000,000 × 10 bits = 2.5 MB, three times smaller. For a very common term in 50 million documents the average gap is 20 and needs about 5 bits, so 50 million × 5 bits = 31 MB instead of 200 MB, over six times smaller.
Skipping: intersect "kafka" (2 million IDs) with a rare term of 1,000 IDs. A plain merge walks about 2,001,000 entries. With skip data in blocks of 128, for each of the 1,000 IDs the reader jumps to the right block and decodes at most one block of 128 IDs: about 1,000 × 128 = 128,000 entries at most, and usually much less, so at least 15 times fewer. The shorter the short list, the larger the gain.
intuition: The index at the back of a book: instead of reading every page to find a word, look the word up and go straight to the pages.
The idea is natural because queries are about words, but documents are stored as sequences of words; the cost of that mismatch is paid once at indexing time, in return for cheap queries. Keeping every list sorted makes combining lists a single pass, like merging two sorted decks of cards. The numbers inside the lists are small gaps, which compress well, so the index stays small enough to keep hot parts in memory.
mistakes: People often think an inverted index finds documents "similar" in meaning. In fact it matches terms that were produced by analysis. Synonyms, typos and paraphrases are not found unless you add expansion, fuzzy matching, or a vector index. This is the reason for hybrid search, which combines BM25 results with approximate nearest-neighbour results from embeddings.
People often think the index makes every query fast. In fact the cost follows the lists touched. A query on a very common term ("the", or a status code present in 40% of the rows) has to walk or intersect enormous lists, and ranking all matches can be slower than a column scan. Stop words, pruning and filters first on selective terms help.
People often think updating an index is like updating a database row. In fact segments are immutable: updates and deletes are new data plus marks, and the real cleanup comes with merges. Frequent small updates therefore create many segments and merge work, and deleted documents still occupy space until merged.
People often think that more shards always give faster search. In fact each shard has its own index and each query visits all of them. Too many small shards add overhead for the coordinator and per-shard fixed cost, and relevance statistics (idf) become uneven.
tradeoffs: Choose an inverted index when queries are about specific terms or values, equality and text filters dominate, and you need results in milliseconds on large collections. Choose a column scan with min/max statistics and partition pruning (see predicate pushdown) when filters are on ranges or low-cardinality columns, queries are few and heavy, and you do not want the write cost and storage of an index; a scan of compressed columns at several GB/s per core is often good enough up to billions of rows.
Choose positional postings when you need phrase and proximity queries; choose docs-and-frequencies only when you rank by terms without phrases. Positions typically make the index two to three times larger, in return for exact phrase matching. For substring or wildcard-in-the-middle queries choose n-gram indexing (bigger index, fast) or a scan (no extra index, slow); suffix arrays suit fixed collections like genomes or code corpora where updates are rare.
Choose near-real-time refresh (1 second) when users expect new data fast, and a longer refresh (30 seconds or more) for bulk indexing: each refresh makes a new segment, so frequent refresh means more small segments, more merge work and slower queries. Choose fewer, larger segments for read-heavy data (force-merge when data is no longer written) and more tolerance of small segments for write-heavy data.
Choose BM25 with inverted lists when exact keyword relevance is needed and explainability matters; choose vector search when meaning matters more than exact words; choose both (hybrid with rank fusion) when you can pay for two indexes, since each one fails on queries the other handles well. In analytical engines, choose inverted bitmaps on columns with moderate cardinality that are filtered by equality, and skip them for columns that are rarely filtered.
friction: Write cost and freshness are the main limits. Building and merging segments costs CPU and I/O; indexing often runs at tens of thousands of small documents per second per node, and a merge rewrites data several times (write amplification). Deleted and updated documents waste space until merged. Heavy update workloads (counters, frequently changing fields) suit an inverted index badly, because each change is a delete plus a new document.
Memory and size matter too. The term dictionary and caches want RAM; high-cardinality fields (unique IDs, free-text IP addresses) create huge dictionaries without helping queries. Long posting lists make common-term queries slow. Positional data and stored fields increase size.
Semantics are limited: the index sees tokens, so analysis choices (stemming, language, tokenization of product codes and emails) decide what can be found, and changing the analyzer requires a full reindex. Relevance in a sharded cluster depends on per-shard statistics. Finally, an inverted index offers no joins, little aggregation support beyond doc values, and limited transactions, which is why teams that use Elasticsearch for filtering and counting often move heavy aggregations to a columnar OLAP engine.
practice: Design the analysis chain first: language-specific tokenizers, lowercase, stemming or lemmatization where appropriate, synonyms at query time rather than index time when possible. Test with real queries and look at the actual tokens (the _analyze API in Elasticsearch). Index only the fields you need to search, and use keyword (exact) fields, not text fields, for IDs, enums and values used in filters and aggregations.
Control the write path: batch writes (bulk API), raise the refresh interval during large loads, avoid frequent single-document updates, and use time-based indices or partitions so that old data stays in large, merged, read-only segments and can be dropped as a unit. Keep shard sizes in a healthy range (often tens of GB per shard) and avoid thousands of tiny shards.
Know the cost of queries: filters (cached, no scoring) are cheaper than scored queries; put the most selective term first in your head, even though the engine reorders; avoid leading wildcards and regular expressions on large fields; paginate with search_after instead of deep from/size. Measure with the engine's profile tools.
When using an OLAP engine such as Pinot or Druid in place of a search engine, keep the inverted index for the equality filters and drop what is not carried over: full-text relevance ranking and rich analyzers may be limited or need a separate text index. For semantic search, add a vector index and combine it with keyword results using reciprocal rank fusion, rather than replacing the inverted index.
quiz: What does an inverted index store, and why is it faster than scanning documents? || For each term, a sorted list of the IDs of documents containing it. A query reads only the lists of its terms and combines them, so cost depends on list lengths, not on the total size of the collection.
Why are posting lists kept sorted by document ID, and why are they stored as gaps? || Sorted lists can be intersected in one linear pass and skipped through. Storing differences between consecutive IDs gives small numbers that need only a few bits, so lists compress well.
Intersect [2, 5, 9, 14] with [1, 5, 14, 20]. What is the result, and how does the algorithm proceed? || [5, 14]. Keep a pointer in each list; advance the pointer with the smaller value; when the values are equal, output the ID and advance both.
A term appears in 50 million of 1 billion documents. About how large is its posting list with 4-byte IDs and with about 5 bits per gap? || 4 bytes × 50 million = 200 MB raw. With about 5 bits per ID: 50 million × 5 bits ≈ 31 MB, more than six times smaller.
When would you choose a column scan with pruning over an inverted index? || When filters are on ranges or low-cardinality columns, writes are heavy, queries are few and aggregate-heavy, or storage and index maintenance cost matter more than latency. A compressed column scan with min/max skipping is often fast enough and has no index to maintain.
interview: How does a search engine handle a phrase query, and what does it cost in index size? || It intersects the posting lists of the words, then checks stored positions in the surviving documents for consecutive positions. A positional index is typically two to three times larger than one with only document IDs and frequencies, but it makes phrase and proximity queries exact.
Why are index segments immutable, and what are the consequences? || Immutability allows compressed, sequential, lock-free structures, easy caching and cheap concurrent reads. Consequences: updates and deletes are new data plus delete bits; background merges reclaim space and cause write amplification; refresh creates many small segments if done too often.
How do engines return the top 10 results without scoring every matching document? || With dynamic pruning such as WAND and block-max WAND: each list or block keeps an upper bound on its score contribution, and documents whose bound cannot beat the current tenth-best score are skipped. Results are exact for the scoring function but need far fewer score computations.
How would you shard a search index, and what problems appear? || Usually by document: each shard has a full index for its subset, queries go to all shards and results are merged. Problems: every query touches every shard (tail latency), idf statistics differ across shards unless collected globally, and too many small shards add overhead. Sharding by term makes single-term queries cheap but gives load imbalance and expensive multi-term intersection across the network.
Where does an inverted index fall short, and what do you combine it with? || It matches tokens, not meaning, so synonyms, typos and paraphrases are missed; it supports little aggregation and no joins. Combine with vector search (hybrid retrieval with rank fusion), a columnar OLAP engine for aggregations, or n-gram and suffix structures for substring search.
