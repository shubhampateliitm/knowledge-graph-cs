@@ multitenancy
value: Multi-tenancy means that one running system serves many customers (called tenants) at the same time, and each tenant sees it as if it were their own. A tenant can be a paying company in a SaaS product, a team inside your company that shares a data platform, or an advertiser in an ad system. The reason to share is cost and effort. If you run one separate copy of the system per customer, you pay for idle machines 24 hours a day, you deploy and monitor thousands of copies, and every new version must roll out thousands of times. If you run one shared system, the fixed costs are paid once and a new version is deployed once.
Sharing creates three hard problems, and the whole topic is about solving them. First, isolation of data: tenant A must never read or change tenant B's data, even when the code has a bug. Second, isolation of performance: if tenant A sends ten times its usual traffic, tenant B must not become slow (this is the "noisy neighbour" problem). Third, accounting: you must know how much each tenant uses, so that you can bill, limit and plan capacity.
The layers below give the building blocks. Namespaces and cgroups (L3, nscgroups) let the operating system give each tenant's processes a private view of the machine and a hard cap on CPU, memory and disk I/O. Rate limiting with token buckets (L2, ratelimit) caps the request rate of each tenant, so that a burst from one tenant is rejected or delayed instead of consuming shared capacity. Partitioning (L2, partitioning) places each tenant's data in its own range, shard or table, so that tenant data is physically separated, can be moved as a unit, and is cheap to find. Kubernetes (L0) packages these ideas as namespaces, resource quotas and network policies.
terms: Tenant — one customer, organisation or team that uses the shared system and owns a separate set of data.
Noisy neighbour — a tenant whose heavy use slows down other tenants that share the same resources.
Silo model — each tenant gets its own dedicated stack, database or cluster; strong isolation, high cost.
Pool model — all tenants share the same stack and tables, and a tenant ID on each row tells them apart; low cost, weak default isolation.
Bridge (hybrid) model — small tenants share a pool and large or sensitive tenants get a silo.
Row-level security (RLS) — a database feature that adds a filter such as tenant_id = current tenant to every query automatically.
Blast radius — the number of tenants affected when one component fails or one tenant misbehaves.
Cell-based architecture — splitting the whole system into many identical independent copies (cells), each serving a fixed subset of tenants.
Control plane / data plane — the control plane creates, configures and meters tenants; the data plane serves their traffic.
history: Multi-tenancy is as old as shared computers. Time-sharing systems of the 1960s (CTSS, Multics) let many users share one machine and had to protect users from each other with memory protection and accounts. The word has a more specific meaning for software: one program instance serving many customers.
Salesforce, founded in 1999, made this the business model of software-as-a-service. It ran one shared database for all customers, put an organisation ID on every row, and stored customer-specific fields as metadata rather than as real columns. Weissman and Bobrowski described this design in their SIGMOD 2009 paper on the Force.com platform. In parallel, Aulbach and colleagues (SIGMOD 2008) compared the ways to map many tenants' schemas onto shared tables, and measured the trade-off between sharing and customisation.
Cloud computing made isolation a first-class infrastructure topic. Virtual machines (Xen, 2003) and then containers (Linux namespaces and cgroups, merged into the kernel between 2002 and 2008, and Docker in 2013) gave cheaper isolation. Amazon's own services became multi-tenant at huge scale, and papers such as the DynamoDB paper (USENIX ATC 2022) explain how per-partition admission control keeps one customer's traffic from harming another's. AWS Lambda and Fargate went further and run each customer's code in a Firecracker micro-VM (NSDI 2020), because a shared kernel was not an acceptable security boundary for untrusted code. The AWS SaaS Lens and the Microsoft multitenant architecture guide later gave the silo, pool and bridge vocabulary that teams use today.
how: A multi-tenant system must do four things on every request: know who the tenant is, restrict data to that tenant, restrict resources to that tenant's share, and record what was used.
Step 1 is tenant identity. The tenant is identified once, at the edge of the system, from a signed token (for example a claim in a JWT), a hostname such as acme.example.com, or an API key. The tenant ID is then put in a request context that travels through every service, queue message and log line. The rule that prevents most leaks is simple: the tenant ID comes from the verified token, never from a field in the request body.
Step 2 is data isolation, and here the three models differ. In the pool model, all tenants share the same tables and every table has a tenant_id column. The primary key becomes (tenant_id, id) and the main indexes start with tenant_id, so that one tenant's rows are stored next to each other in the B-tree. In the schema-per-tenant model each tenant has its own set of tables inside one database. In the silo model each tenant has its own database or cluster. The more you separate, the stronger the isolation and the easier it is to restore one tenant from backup or to give a customer their own encryption key, but the more objects you must create, migrate and monitor. A database with 5,000 tenants times 50 tables has 250,000 tables, and schema migrations, catalog size and backup tools start to suffer.
In the pool model, the safest way to enforce the tenant filter is to put it in the database, not in application code. PostgreSQL row-level security does this with a policy such as USING (tenant_id = current_setting('app.tenant_id')::uuid). The application sets app.tenant_id at the start of each transaction, and the database then adds the filter to every SELECT, UPDATE and DELETE and checks it on every INSERT. A forgotten WHERE clause in one query can no longer leak data. Two details matter: table owners bypass RLS unless FORCE ROW LEVEL SECURITY is set, and with a connection pooler in transaction mode the setting must be applied inside each transaction (SET LOCAL), or one tenant's ID can stay on a connection reused by another.
Step 3 is compute isolation. Namespaces give each tenant's process its own view of process IDs, network interfaces and mounted file systems. Control groups (cgroups) then cap what the process may consume: in cgroup v2, cpu.max sets a CPU quota per period, memory.max sets a hard memory limit (the process is killed if it exceeds it), and io.max limits disk bandwidth. Kubernetes turns these into per-pod limits and per-namespace ResourceQuota objects. Remember that containers share the host kernel, so they isolate resources well but isolate hostile code only moderately; for untrusted code, use micro-VMs or separate nodes.
Step 4 is fairness at the request level, and this is where rate limiting comes in. A token bucket gives each tenant a bucket that fills at a steady rate r (for example 100 tokens per second) up to a capacity b (the allowed burst, for example 200). Each request removes one token (or more for expensive requests). If the bucket is empty, the request is rejected with HTTP 429 or placed in a queue. This guarantees that a tenant can never use more than r on average and b in one burst. Real systems layer limits: per tenant, per API, per user inside the tenant, and a global limit. Better systems also use weighted fair queuing or per-tenant concurrency limits (bulkheads), so that one slow tenant cannot fill all worker threads, and shed load first from the tenants that exceed their share.
Step 5 is placement. Because the tenant ID is the natural partition key (partitioning), data can be sharded by tenant: a directory table maps tenant to shard, and a tenant can be moved to another shard when it grows. A very large tenant gets its own shard or silo (the bridge model). A cell-based design repeats the whole stack in several cells and routes each tenant to one cell, so a failure or a bad deployment hits only the tenants in that cell.
Step 6 is metering. Every metric, log and trace carries the tenant ID, so you can compute cost per tenant and find the noisy neighbour in minutes. Take care with cardinality: a metric label with 100,000 distinct tenant values can overload a metrics system, so use per-tenant logs and sampled traces for the long tail and per-tenant metrics for the top tenants.

example: Take a SaaS product with 5,000 tenants on one PostgreSQL primary. Most tenants are small (about 100,000 rows each), but one whale tenant has 200 million rows, which is about 30% of all rows. The server can sustain 2,000 requests per second (req/s) at an acceptable latency.
Data design. Use the pool model with tenant_id as the first column of the primary key and of every index, plus row-level security. A query for one tenant now reads a narrow range of the index. Table partitions by hash of tenant_id (say 64 partitions) keep each index small. The whale is moved to its own database (the bridge model), because its 200 million rows would dominate maintenance and one bad query from it could slow the pool. Moving a tenant is possible because every row carries tenant_id: copy rows where tenant_id = whale, switch the directory entry, and delete the old rows.
Rate limits. Give normal tenants a bucket with r = 10 req/s and b = 50, and the whale r = 400 and b = 1,000. The sum of all limits (about 5,000 × 10 = 50,000 req/s) is far above the 2,000 req/s capacity. That is intended: tenants are rarely all busy at once, and the limits only cap the worst case for a single tenant. So there is also a global protection: when total load goes above, say, 85% of capacity, the system rejects requests first from tenants that are above their fair share.
Why this matters, with numbers. Suppose a faulty client at tenant A starts to send 1,500 req/s while all other tenants together send 300 req/s. Without limits, utilisation of the shared server goes to 1,800 / 2,000 = 90%. In a simple queueing model the average waiting time grows roughly like 1 / (1 − utilisation) times the service time: at 90% this is 10 times the service time, and tail latency is worse. With A capped at r = 10 req/s (the tenant's bucket), utilisation is about 310 / 2,000 = 15.5%, the factor is about 1.2, and the other tenants do not notice. Tenant A receives 429 responses and sees the problem in its own logs. The cost of the protection is a few hundred nanoseconds per request to update a counter, usually kept in memory on the gateway or in a fast shared store such as Redis.
Failure check. A developer writes a new report query and forgets the tenant filter. Without RLS, it returns all tenants' rows to one customer: a data breach. With RLS, the database appends tenant_id = 'T42' automatically and the query returns only T42's rows. The bug is still a bug, but it is no longer an incident.
intuition: An apartment building: one shared structure and shared pipes, private locked apartments, and house rules so that one neighbour's party does not keep everybody awake.
The design is natural because sharing and isolation pull in opposite directions, and each layer lets you choose where to cut. The more you share, the cheaper the system, but the more a single bug, load spike or attacker can reach. The more you separate, the safer, but the more copies you operate. Multi-tenancy is therefore not one technique but a dial, and the right setting is different for each tenant: the free-tier user gets a shared row in a shared table, the bank gets its own database. What makes the dial workable is that every mechanism (a tenant ID on rows, a quota per tenant, a cap per cgroup) is a small, cheap, local rule that is enforced by the layer closest to the resource, not by trust in every developer.
mistakes: People often think multi-tenancy is only about data security. In fact performance isolation is usually the more frequent problem. Data leaks need a bug; noisy neighbours need only a successful customer. A system that is secure but lets one batch job slow everyone will still lose customers.
People often think that a tenant_id column and a WHERE clause are enough. In fact one missed filter in one query leaks data, and code review cannot catch every case over years. Put the filter into the database with row-level security or into a single data-access layer, add automated tests that run each endpoint as tenant A and try to read tenant B's data, and apply the principle of least privilege to database roles.
People often think containers give the same isolation as virtual machines. In fact containers share one kernel, so a kernel bug can break the boundary, and cgroups limit CPU and memory but not every shared resource (the page cache, the last-level CPU cache and the network card can still be contended). For hostile or customer-supplied code use micro-VMs (Firecracker) or sandboxes such as gVisor.
People often think a rate limit per tenant makes capacity planning unnecessary. In fact limits only bound each tenant's worst case. If many tenants burst together (for example at the start of the business day in one time zone), total demand can still exceed capacity, so you also need a global limit, load shedding and headroom.
friction: The main cost of sharing is a larger blast radius. One bad deployment, one bad query plan, one schema migration or one corrupted shared index can hit every tenant at once. Cells and gradual rollouts (a few tenants first) reduce this but add routing logic and operational work.
Per-tenant customisation fights with a shared schema. Custom fields, custom workflows and per-tenant versions of the product force either wide sparse tables, generic key-value or JSON columns (hard to index and validate) or a metadata layer, which is what Salesforce built. Schema migrations are another pain: in schema-per-tenant or database-per-tenant designs a migration must run thousands of times, some will fail, and tenants end up on different versions.
Data lifecycle is harder than it looks. Deleting one tenant completely (including backups, logs, search indexes and caches) or restoring one tenant to last Tuesday is easy in a silo and difficult in a pool, where backups contain everybody. Regulations such as GDPR and contracts may demand data residency per tenant, per-tenant encryption keys, or audit trails of every access.
Fairness itself has no single correct definition. Equal shares waste capacity when some tenants are idle; strict quotas reject work while the machine is half empty; a priority for paying customers raises the question of what the free tier is promised. Metering has costs too: tenant labels on metrics create very high cardinality, and shared resources such as cache and network are hard to charge to one tenant exactly.
practice: Choose isolation per risk and per revenue. A common plan is pool for the long tail of small tenants, silo or dedicated shard for the largest and most regulated ones, and the ability to move a tenant from one to the other without downtime. Design this move from day one: every row has tenant_id and every identifier is unique per tenant or globally.
Enforce the tenant boundary in one place. Use row-level security or a mandatory data-access layer, take the tenant from the verified token, and write a test that runs the whole API as two tenants and checks that no response from tenant A contains tenant B's data. Add tenant_id to the primary key and to the leading column of indexes so that tenant queries are range scans.
Protect shared resources with layered limits: token buckets per tenant and per API at the gateway, concurrency limits per tenant for expensive operations (exports, reports, imports), separate queues or worker pools for batch work, and a global load-shedding rule. In Kubernetes, give every tenant namespace a ResourceQuota and LimitRange, add NetworkPolicy rules, and run untrusted workloads in sandboxed runtimes on separate node pools. Return clear 429 responses with a Retry-After header so that clients can back off.
Measure per tenant: requests, errors, latency percentiles for the top tenants, storage, CPU-seconds and egress. Use this for billing, for finding the noisy neighbour quickly, and for deciding which tenant should move to its own shard. Roll out changes gradually, a small cell or a few internal tenants first. In a data platform such as Databricks, the same ideas appear as workspaces or catalogs per team, cluster policies, and per-team budgets and tags for cost attribution.
tradeoffs: Choose the pool model (shared tables with tenant_id) when you have thousands of small tenants, each using little, and per-tenant revenue is low. One database with a few hundred thousand rows per tenant is far cheaper than thousands of separate databases. You give up strong default isolation, easy per-tenant restore and per-tenant schema versions, so you must add row-level security, tests and good limits.
Choose the silo model (a database or cluster per tenant) when tenants are few and large, pay enough to cover dedicated infrastructure, have contractual or regulatory demands (own encryption keys, data residency, audit), or have very different load. Expect the infrastructure bill and the operational work to grow roughly linearly with the number of tenants, and plan automation for provisioning, upgrades and monitoring before you pass a few dozen silos.
Choose the bridge model when the tenant size distribution is skewed, which it almost always is: a few tenants produce most of the load. Keep the long tail pooled and give the top 1% their own shard. The price is two code paths and a tenant-move procedure that must be tested.
Choose containers with cgroups for isolating your own services and trusted teams, where density and startup time matter. Choose micro-VMs or separate nodes when tenants run their own code or when a compromise of one tenant would be a legal risk. You pay in memory overhead (tens of MB per micro-VM), slower start and lower density.
Choose hard quotas when you need predictable guarantees and billing, and soft limits with borrowing when utilisation matters more. Hard caps waste idle capacity; borrowing allows bursts but needs a mechanism to take capacity back quickly, and it can surprise tenants who saw good performance only because others were idle.
interview: How would you design tenant isolation for a SaaS database with 10,000 tenants where a few tenants are 1,000 times bigger than the median? || Use a bridge model: pooled tables keyed by (tenant_id, id) with row-level security for the long tail, and dedicated shards for the largest tenants, with a tenant directory that maps tenant to shard and a tested online move procedure. Rate-limit per tenant, track usage per tenant, and promote a tenant to its own shard when its share of load or size crosses a threshold.
A tenant says it was slow for 20 minutes yesterday. How do you find out whether a noisy neighbour caused it? || Check per-tenant request rate, CPU-seconds, queue time and database locks or slow queries for the same window on the shared component the tenant used. Compare the top consumers to their limits and look for a tenant that was above its usual by a large factor. This only works if tenant ID is on every metric, log and trace, so say that you would add it first.
Why is a WHERE tenant_id = ? clause in every query not good enough, and what would you do instead? || It depends on every developer and every query being correct for years, and one miss is a data breach. Enforce it below the application: row-level security with the tenant ID set from the verified token, restricted database roles, and automated cross-tenant tests that must fail to read other tenants' data.
Your token-bucket limiter runs on 20 gateway nodes. How do you apply a limit of 100 req/s per tenant? || Either keep the counter in a shared store (Redis) with an atomic update per request, which adds a network hop, or give each node a share of the tokens (100 / 20 = 5 req/s) and rebalance by actual traffic. The second is cheaper but inaccurate when traffic is uneven. Accept a small overshoot for speed; exactness is rarely worth a synchronous call on the hot path.
What are the failure modes of cell-based architecture? || A cell limits blast radius, but you need a router that is itself highly available and simple, a way to move tenants between cells, and cross-cell features (global search, admin, billing) that must read from many cells. Cells can become imbalanced, and a bad deploy to all cells at once removes the benefit, so roll out cell by cell.
How would you add per-tenant encryption keys, and what does it cost? || Wrap each tenant's data key with a key in a key management service; store the wrapped key with the tenant and cache the unwrapped key in memory for a short time. It enables per-tenant revocation and crypto-shredding for deletion, and costs extra key-service calls, cache logic, and complexity for search or analytics that must read across tenants.
quiz: What is the difference between the silo, pool and bridge models? || Silo gives each tenant dedicated infrastructure, pool shares everything and separates tenants only by a tenant ID, and bridge mixes both: small tenants pooled, large or sensitive tenants in silos.
Why does a token bucket protect other tenants from a noisy neighbour? || Each tenant's bucket refills at a fixed rate r and holds at most b tokens, so the tenant can never send more than about r requests per second on average, plus one burst of b. Excess requests are rejected or delayed before they reach the shared resource.
Why is row-level security safer than adding a tenant filter in application code? || The database applies the filter to every query automatically, using the tenant ID set for the session, so a forgotten WHERE clause cannot leak rows. The filter lives in one place and is checked on writes as well.
A server handles 2,000 req/s. Other tenants send 300 req/s in total. One tenant starts sending 1,500 req/s. What is the utilisation with and without a limit of 10 req/s on that tenant? || Without a limit: 1,800 / 2,000 = 90%, where queueing delay is about 10 times the service time. With the limit: about 310 / 2,000 = 15.5%, where the delay factor is only about 1.2.
When would you move a tenant from the pool to its own shard? || When its size or load starts to dominate the pool (for example it is above 10% of the rows or requests), when its queries hurt others, or when contract and regulation require dedicated storage or keys. The cost is a second code path and a move procedure you must test.

@@ durableexec
value: Durable execution lets you write a long process as ordinary code (a function with if-statements, loops and function calls) and have the platform guarantee that the function runs to the end, even if the machine crashes, the deployment restarts, or the process has to wait for 30 days. The function does not lose its place. Its local variables, its position in the code and the results of everything it already did are recovered automatically.
The problem it solves is the multi-step business process. An order must charge a card, reserve stock, ask a warehouse to ship, wait for a delivery event and send an email. Each step calls another service that can be slow or down, and the whole thing can take minutes or weeks. Without durable execution, each team builds the same machinery by hand: a status column, a queue, a retry loop, a cron job that finds stuck rows, and a state machine whose transitions are spread over many files. Bugs in this machinery cause double charges and lost orders. With durable execution, the machinery is the platform's job and your code reads like a normal story: charge, reserve, ship, sleep, email.
It is built on three lower ideas. The write-ahead log (L2, wal) is the core: the engine appends every step, its input and its result to a durable event history before moving on, in the same way a database logs a change before applying it. Idempotence (L2, idempotence) is what makes retries safe: a step may be executed more than once (the worker may crash after doing the work but before recording it), so each side effect must have the same final effect if it runs twice. Outbox and sagas (L2, outbox) handle failure of the business process itself: when step 4 fails for good, the compensating actions (refund, release stock) for steps 1 to 3 are run, because there is no distributed rollback across services. The same idea powers Temporal (L0) and, at the level above, general workflow orchestration (workflow). It is also the natural runtime for long-running AI agents, whose steps are slow, costly and non-repeatable.
terms: Workflow — the durable function that describes the whole process; its code must be deterministic.
Activity — a single step with side effects (call an API, write to a database); it can fail and is retried.
Event history — the append-only log of everything that happened in one workflow run; it is the source of truth.
Replay — re-running the workflow function from the start against the recorded history to rebuild its state.
Determinism — given the same history, the code must make the same decisions in the same order.
Worker — a stateless process that runs workflow and activity code and polls a task queue for work.
Timer — a durable wait (for example 30 days) stored as a record, not as a sleeping thread.
Compensation — an action that undoes the effect of an earlier completed step (a refund undoes a charge).
Continue-as-new — closing a long workflow run and starting a fresh one with the current state, to keep the history small.
history: The ideas are old. Business process management systems of the 1990s and 2000s (BPEL, jBPM) stored process state in a database, but forced people to model processes in XML or diagrams. Garcia-Molina and Salem proposed sagas in 1987 for long transactions that cannot hold locks: a chain of local transactions, each with a compensating one. Event sourcing, where state is rebuilt from a log of events, became popular in the 2000s.
Amazon launched Simple Workflow Service (SWF) in 2012, with workers that poll for decisions, but programmers still wrote a decider by hand. Later, at Uber, Maxim Fateev and Samar Abbas built Cadence, which Uber released as open source in 2017. Cadence's new idea was to let the programmer write the workflow as normal code in Go or Java and to recover it by replaying the code against the history. Microsoft's Durable Task Framework and Azure Durable Functions (2017–2018) used the same replay approach, with orchestrator functions. Fateev and Abbas forked Cadence in 2019 as Temporal, which became the best-known open-source implementation.
After 2022 the idea spread beyond dedicated servers. Restate (2023) puts a journal in front of ordinary services and handlers. DBOS (2023, by Michael Stonebraker, Matei Zaharia and others) stores checkpoints in your own Postgres database, using a library. AWS Step Functions (2016) offers a managed state machine in JSON, and in December 2025 AWS added Lambda durable functions, which use checkpoint and replay inside Lambda. The reason for the growth is practical: microservices turned every business operation into a distributed one, and long-running AI agents need exactly this guarantee.
how: A durable execution system has a server (the engine) and workers. The server stores the event history of every workflow run in a database and keeps task queues. Workers hold your code. The server never runs your code; it only records events and hands out tasks.
Start of a run. A client asks the server to start a workflow with an ID and input. The server appends the first event, WorkflowExecutionStarted, and puts a workflow task on the task queue. A worker picks it up and runs the workflow function from the first line.
Calling an activity. When the code calls an activity (for example chargeCard(order)), the SDK does not run it inline. It creates a command, "schedule activity chargeCard with this input", and the workflow function waits at that point. The worker sends the commands back to the server, which appends ActivityTaskScheduled to the history (this is the write-ahead log step: the intent is durable before anything happens) and puts an activity task on a queue. Some worker, perhaps a different one, runs the activity, which can call any API. When it finishes, the server appends ActivityTaskCompleted with the result and creates a new workflow task so that the workflow can continue.
Replay. To continue, a worker needs the workflow function to be at the right line with the right variables. It gets this by running the function again from the start, but with the history in hand. When the code reaches chargeCard, the SDK looks at the history, finds that this call already has an ActivityTaskCompleted event, and returns the recorded result at once without scheduling anything. The function then proceeds to the next call. When the code gets past the last recorded event, replay ends and the next call produces a new command. So the history acts as a script of already decided facts, and the code re-derives its own state from it. If the worker crashes, any other worker can do this from the same history. Workers keep recently used workflows in memory and receive follow-up tasks on a sticky queue, so full replay happens mainly after a crash, a cache eviction or a long wait.
Determinism. Replay works only if the code makes the same calls in the same order each time it sees the same history. If a replayed run reaches a different command than the one recorded at that position, the SDK raises a non-determinism error and refuses to continue. So workflow code may not read the real clock, generate random numbers, use unordered map iteration for decisions, start its own threads or call the network directly. The SDK provides replacements: workflow.now() reads a timestamp recorded in the history, a "side effect" API records a random value once, and every real interaction goes into an activity.
Time, signals and waiting. A call such as sleep(30 days) creates a timer: TimerStarted is appended and the worker may forget the workflow entirely. Thirty days later the server appends TimerFired and schedules a workflow task. Nothing holds a thread or memory in between, so millions of sleeping workflows are cheap. Signals (messages sent to a running workflow, for example "customer cancelled") and queries (reads of its state) are also events in the history.
Retries and idempotence. Activities have a retry policy (exponential backoff, maximum attempts) and several timeouts, including a heartbeat timeout for long activities. The guarantee is at-least-once for activities and effectively-once for workflow code. An activity can succeed on a payment API and the worker can die before the result is recorded; the retry then calls the payment API again. The fix is idempotence: pass a key that is the same on each attempt, such as workflow ID plus activity ID, and let the payment service deduplicate. This is why outbox and idempotence patterns remain necessary.
Failure of the business process. Because there is no global rollback, the workflow itself is the saga coordinator. A common pattern is to keep a list of compensations and, in a catch block, run them in reverse order; each compensation is itself an activity with retries. Since this is ordinary code in a durable function, the saga survives crashes, which is the main reason to use durable execution for sagas.
Limits. The history is stored in a database and replayed, so it must stay bounded. Temporal terminates a run whose history goes over 51,200 events and logs warnings from 10,240 events. Long-lived or looping workflows therefore call continue-as-new, which closes the run and starts a new one with the carried state. Deploying new code is the other hard part: running instances replay old histories on new code, so changing the order of activity calls breaks them. Teams use versioning APIs (patching) or pin old runs to old worker versions until they finish.

     sleep(3d)    -> history says "fired"   -> return
     email(...)   -> beyond the history    -> NEW command to server
example: Take an order workflow with four steps: charge the card (activity A), reserve stock (B), ship (C), wait 3 days and send a survey email (D). If shipping fails permanently, the workflow must refund and release stock.
Normal run. Events: 1 WorkflowStarted, 2 A scheduled, 3 A started, 4 A completed, 5 B scheduled, 6 B started, 7 B completed, 8 C scheduled, 9 C started, 10 C completed, 11 TimerStarted(3 days), 12 TimerFired, 13 D scheduled, 14 D started, 15 D completed, 16 WorkflowCompleted. That is 16 events for a four-step workflow, roughly 3 events per activity. Each event is a database write on the server, so each step costs a few to tens of milliseconds, more than a plain function call. This is fine for orchestration, and not fine for a loop of a million tiny operations.
Crash during the run. The worker dies after event 4 (A completed) and before B's result is recorded. Another worker receives the workflow task and the history events 1 to 5. It runs the function from the top. At A, history has the result, so it is returned instantly; no second charge. At B, the history has only "scheduled", so the SDK waits for the activity result, and the activity is dispatched again if its timeout passes. Suppose B had actually reserved the stock before the worker died. The second attempt calls the stock service again with the idempotency key "W1-B"; the service sees the key and returns the first reservation. The effect happens once.
Failure and saga. C fails five times with the retry policy and gives up. The workflow code catches the error, then calls the compensations in reverse order: release stock (key "W1-B-undo"), refund the card (key "W1-A-undo"). Both are activities, so they are retried until they succeed, even over a deploy or a crash. The workflow ends as failed-but-compensated, and the history shows exactly which steps ran.
History growth. A different workflow processes a 100,000-item batch with one activity per item. At about 3 events per item this needs 300,000 events, six times the 51,200 limit. The fix is to process 5,000 items per run (15,000 events), then call continue-as-new with the next offset. A run's replay cost then stays at 15,000 events, which takes milliseconds to a few seconds, not minutes.
intuition: Save the game at every checkpoint and, after a crash, replay your recorded moves instead of playing them again.
The design is natural because it combines two old, simple facts. A log can rebuild any state if the state changes are deterministic functions of the log, and a program is exactly such a function when it has no hidden inputs. So if you capture every input from the outside world (activity results, timer firings, messages) and fix the order, the program's whole state, including its place in the code, is a function of that list. You do not need to save the stack or the heap. You save the facts and re-run the thinking. This is cheap because thinking is fast and the world is slow: replaying 1,000 recorded steps takes milliseconds, while repeating one real payment call is dangerous.
mistakes: People often think durable execution gives exactly-once execution of everything. In fact only the workflow logic is effectively once. Activities are at-least-once, because a crash can happen after the work and before the record. You still need idempotency keys or deduplication in every external side effect.
People often think replay means the activities are run again. In fact replay never calls activities that already have a recorded result; it only re-executes the workflow code, which is pure orchestration, and feeds it the recorded results.
People often think a workflow is just a cron job or a queue with retries. In fact a queue retries one message; a workflow keeps the state of a whole multi-step process, including timers of days, waiting for external signals, parallel branches and compensations, and it makes that state survive restarts without a hand-written state table.
People often think any code can go in the workflow function. In fact workflow code must be deterministic and must not call the network, read the clock directly or depend on the order of unordered collections. A change as small as reordering two activity calls can break running instances, which is a non-determinism error at replay.
People often think durable execution is free of cost. In fact each step is a durable write and a queue hop, so throughput per workflow is limited, and the engine and its database become a critical dependency that must be operated or paid for.
friction: Versioning is the hardest daily problem. A workflow may run for months, and during this time you deploy new code. Old runs replay with the new code, so every change to the order or number of calls is a possible break. Teams must use patch markers or worker versioning, keep old code alive until old runs end, and test replays against saved production histories. This makes the code less free to refactor than normal code.
The programming model has sharp edges. Determinism rules are easy to violate by accident (a library call that uses the clock, a map iteration, a log statement that reads a variable). Debugging means reading histories. Data in the history is stored and replayed, so large payloads are expensive; the usual advice is to pass references (an object-store key), not blobs, and to encrypt sensitive payloads with a codec.
Scale limits apply. The history size is bounded (51,200 events in Temporal), a single workflow is a serial thread of decisions, and hot workflows with many signals can become a bottleneck. The persistence layer (Cassandra, MySQL or PostgreSQL for Temporal) needs capacity planning, and an outage of the engine stops all workflows at once; hosted services trade this for cost. There is also lock-in: Temporal, Step Functions, Azure Durable Functions and Restate have different programming models, so switching is a rewrite.
Finally, durable execution does not remove distributed-systems design. You must still choose timeouts, define what is retryable, design compensations that are themselves idempotent, and handle the cases where a compensation cannot undo reality (an email already sent, money already paid out).
practice: Put all side effects into activities and keep workflow code as plain orchestration. Give every activity a stable idempotency key (workflow ID plus a step name) and make the downstream service honour it. Set explicit timeouts (start-to-close for every activity; a heartbeat timeout for long ones) and a retry policy that stops retrying on non-retryable errors such as validation failures.
Keep histories small. Pass IDs and references, not documents. Process large loops in batches and call continue-as-new at a fixed size, well under the limit (for example at 10,000 events). Use child workflows to split a large fan-out into several histories. Watch the number of events per run and the replay time as metrics.
Plan versioning from the first day. Use the SDK's patching or versioning API for any change that touches the order of commands in a live workflow, run replay tests against recorded histories in CI, and avoid long-lived runs when a short run plus a stored state would do. Keep a human-readable workflow ID (order-123) so that duplicate starts are rejected and so that signals can find the run.
Choose the tool for the job. Use a durable execution engine for money, fulfilment, onboarding, data-pipeline control flow that needs human approval, and long-running AI agent loops where each step is expensive and must not repeat. Use a plain queue for independent single-step jobs, and a scheduler such as Airflow for periodic batch DAGs with data-aware scheduling. For a small team without operations capacity, consider a managed service (Temporal Cloud, Step Functions) or a library that uses your own database (DBOS).
tradeoffs: Choose replay-based durable execution (Temporal, Azure Durable Functions, Lambda durable functions) when the process logic is complex (branches, loops, waits for signals, compensations) and you want it in normal code that developers can test. You give up freedom to refactor, because determinism and versioning rules apply, and you must run or buy the engine.
Choose a declarative state machine (AWS Step Functions) when the flow is simple, mostly calls to AWS services, and you want visual inspection and no worker fleet. You give up code-level expressiveness, and the price per state transition on Standard workflows (charged per transition) grows quickly for high-volume or loop-heavy flows. Step Functions Standard can run up to a year; Express workflows are for short, high-rate flows.
Choose a library that checkpoints into your own database (DBOS) or a lightweight journal (Restate) when you want fewer moving parts and your volume is moderate. You depend on your database's throughput and give up the strong separation, queues and tooling of a dedicated engine.
Choose a plain queue with retries and an idempotent consumer when each job is one step. It is cheaper by a large factor in latency and money, and simpler to operate. Choose a sagas-by-hand design with outbox only when you cannot adopt an engine and the number of steps is small; the cost is that the state machine and recovery jobs are yours to write and test forever.
Choose how long a single run may live. Short runs that store the state externally are easier to deploy and version; very long runs are convenient but each deployment risks breaking replays of old histories.
interview: Explain how a workflow resumes after the worker crashes in the middle of the run. || The server holds the event history. Another worker gets the next workflow task with that history and re-runs the workflow function from the start. Each activity call that already has a completed event returns the recorded result without executing, so the code reaches the same point with the same variables. Past the end of the history, the code creates new commands.
Why must workflow code be deterministic, and what happens if it is not? || Replay matches the commands the code issues against the commands in the history, position by position. If the code takes a different branch (because of a clock, a random number or a changed code path), the commands differ and the SDK raises a non-determinism error. The run cannot be trusted to continue, so it fails or blocks until fixed.
An activity charges a card, and the worker dies before reporting success. How do you avoid a double charge? || The engine will retry the activity, so the charge call must be idempotent: send an idempotency key that is stable across attempts, such as workflow ID plus activity ID, and let the payment provider return the first result for a repeated key. Optionally, check the payment state at the start of the activity.
How do you deploy a code change while 100,000 workflows are running? || Changes that alter the sequence of commands break replay for old runs. Use the patching or versioning API to branch on a version marker recorded in the history, or route old runs to old worker builds (worker versioning) until they finish. Test with replay of saved production histories in CI, and prefer short runs where possible.
Why not just use a queue and a status column in a database? || You can for one or two steps. For a long process you must handle timers, retries per step, parallel branches, cancellation, compensation and recovery from partial failures, and you end up writing a workflow engine, usually with hidden bugs. Durable execution gives these as tested primitives, at the cost of an extra system and its programming rules.
What limits the throughput of a single workflow and of the whole system? || One workflow is a serial chain of decisions, each step costs a durable write and a task hop (milliseconds to tens of milliseconds), and its history is bounded (51,200 events in Temporal). The whole system scales by the number of independent workflows, limited by the database and the task-queue partitions. Use batches, child workflows and continue-as-new to stay inside the limits.
quiz: What are the two kinds of code in a durable execution system, and which one must be deterministic? || Workflow code, which orchestrates and must be deterministic, and activities, which do side effects and may be retried. Only the workflow code is replayed.
Why does replay not call a completed activity again? || The history already contains the activity's completed event and result. The SDK matches the call in the code to that event and returns the stored result at once.
Why are activities at-least-once and not exactly-once? || A worker can finish the work and crash before the result is recorded, so the engine cannot know whether it happened and retries it. The side effect must be idempotent.
A workflow makes 3 events per activity and the history limit is 51,200 events. About how many activities can one run perform, and what do you do for 100,000? || About 17,000 activities (51,200 / 3). For 100,000 items, split the work into runs of a few thousand items each and use continue-as-new, or use child workflows.
When would you choose AWS Step Functions over a code-based engine such as Temporal? || When the flow is simple, mostly integrates AWS services, and benefits from a visual state machine and no workers to run. Choose Temporal when you need complex logic in code, long histories of decisions, or portability, and can operate or buy the engine.

value: Version control is a system that records every change made to a set of files, who made it, when and why, and lets you go back to any earlier state. It solves a very basic problem of teamwork: two people edit the same code at the same time, something breaks on Friday, and nobody can say what changed since Thursday. With version control you can compare any two states, undo a bad change, work on several ideas in parallel on branches, and combine the work of many people with a defined merge procedure.
Almost all professional software lives in a version control system today, and the use has widened: infrastructure definitions (Terraform), pipeline code, notebooks, configuration, documentation, and increasingly data and models. The history is not only a backup. It is the shared record that code review, blame, bisecting a bug, audits and release engineering all read.
The layers below give it its shape. Content addressing and Merkle trees (L2, merkle) are the core data structure: every file version, directory and commit is stored under the hash of its content, and a commit's hash includes its parents' hashes. This makes history tamper-evident, makes identical content stored only once, and makes synchronising two repositories a question of which hashes are missing. Software engineering principles (L3, swe) supply the reason for the workflow: small changes, reviewed and integrated often, reduce risk. CI/CD (L1, cicd) sits on the other side of the commit: a push triggers builds, tests and deployment, so the commit becomes the unit of delivery. Git (L0) is the dominant implementation, and platforms such as GitHub and GitLab add pull requests and automation around it.
terms: Repository — the complete store of a project's files and history.
Commit — a snapshot of the whole project at one moment, with a message, an author and a pointer to its parent commit(s).
Blob, tree — in Git, a blob stores the bytes of one file, and a tree stores a directory listing that points to blobs and other trees.
Branch — a movable name that points to one commit; creating one costs almost nothing.
Merge — combining the changes of two lines of history into one new commit that has two parents.
Rebase — replaying your commits on top of another commit, which creates new commits with new hashes.
Merge base — the closest common ancestor of two commits; it is the reference point for a three-way merge.
Distributed version control — every developer has a full copy of the history, so most operations work offline.
Monorepo — one repository that holds many projects of a company.
Pull request — a request on a hosting platform to merge a branch, combined with review and automated checks.
history: The first tools stored changes to single files. SCCS (Bell Labs, 1972) and RCS (Walter Tichy, 1982) kept deltas per file and locked a file while someone edited it. CVS (Dick Grune's scripts in 1986, then a full tool around 1990) allowed concurrent edits with a central server, and Subversion (2000) fixed CVS's weakest points, such as no atomic commits and no tracking of renames. All of these were centralised: one server held the history.
The shift to distributed systems came from large open-source projects. The Linux kernel used the proprietary BitKeeper from 2002. In April 2005 the free licence was withdrawn, and Linus Torvalds started Git, with the explicit goals of speed, a distributed design, and strong protection against corruption. Git hosted its own source within days, and the kernel moved to it within weeks. Mercurial, written by Olivia Mackall, started in the same month with similar ideas. Git's design used content-addressed objects, which made it fast and simple at its core.
GitHub (2008) turned Git into a social platform with forks and pull requests, and GitLab and Bitbucket followed. This is why Git is now close to universal for software. At the same time very large companies met limits and built their own systems: Google's Piper, a single repository with about two billion lines of code in about nine million source files (CACM 2016), Meta's Sapling (open-sourced in 2022), and Microsoft's work on VFS for Git and Scalar to run Git on the huge Windows repository. Recent Git versions include features for scale, such as partial clone, sparse checkout, a commit-graph file and file system monitors. Newer front ends such as Jujutsu (jj) use Git as the storage layer and give a different workflow.
how: Git's model is small. It has a key-value store in which the key is a hash of the value, and a few kinds of value.
Objects. A blob holds the bytes of a file. A tree holds a list of entries, each with a mode, a name and the hash of a blob or a subtree. A commit holds the hash of one root tree (the snapshot of the whole project), the hashes of its parent commits, the author and committer with time stamps, and the message. The name of each object is the SHA-1 of its type, its length and its content. For example, a blob containing the text "hello" and a newline always has the ID ce013625030ba8dba906f756967f9e9ca394464a, in every repository in the world. This is the Merkle-tree idea: the hash of a tree depends on the hashes of its children, and the hash of a commit depends on its tree and its parents. If you change one byte in one file, the blob hash changes, so the hashes of all trees above it change, so the commit hash changes, and so do all later commits.
Snapshots, not diffs. Each commit points to a complete tree. This looks wasteful, but unchanged files and directories are the same objects, referenced again, so a commit that changes one file at depth three creates only the new blob, three new trees along the path to the root, and the commit: five small objects, however many thousand files the project has. Git computes diffs on demand by comparing two trees. For disk space it later packs objects into packfiles, where similar objects are stored as deltas against each other, and a pack for a large history is usually many times smaller than the loose objects.
History as a graph. Commits point to their parents, so history is a directed acyclic graph (DAG). A normal commit has one parent, a merge commit has two or more, and the first commit has none. Branches and tags are only refs: small files that contain a commit hash. A branch is a ref that moves forward when you commit. HEAD says which branch is checked out. Creating a branch writes about 41 bytes, which is why Git encourages branching.
The index. Between your working directory and the next commit there is the index (staging area), a sorted list of paths with blob hashes. git add writes blobs and updates the index; git commit turns the index into a tree and creates the commit. This allows partial commits and makes status checks fast.
Merging. To merge branch B into A, Git finds the merge base, the nearest common ancestor in the DAG. It then does a three-way merge for each file: compare the base with A's version and with B's version. If only one side changed a region, take that change. If both changed the same region in different ways, Git marks a conflict and asks a human. A merge with a clean result produces a commit with two parents. A fast-forward happens when A is simply an ancestor of B and the ref just moves. Rebase takes your commits one by one and re-applies them on a new base. The content changes may be the same, but each commit gets a new parent, so a new hash, which is why rewriting published history causes trouble for others.
Sync. Because objects are immutable and named by content, synchronisation is simple. A fetch asks the other side which commits it has, computes the objects that are missing, and transfers them as a pack. A push does the reverse and then asks to move a ref; the server accepts it only if it is a fast-forward (unless forced). No locking is needed, because adding objects never conflicts. Only the movement of refs needs coordination.
Around the repository. A hosting platform adds access control, pull requests, code review and branch protection, and calls webhooks on every push. This is where CI/CD (cicd) connects: a push or merge triggers a pipeline that builds and tests the commit, and a green result is a condition for merging. The commit hash is a precise identifier of what was built and deployed, and a signed commit or tag adds provenance for supply-chain security.

example: Make a repository with a file greeting.txt of three lines: "Hello", "World", "Bye". Commit A holds this. Branch main then gets commit B, which changes line 1 to "Hello there". A second line of work, branch feature, starts from A and adds commit C which changes line 3 to "Goodbye". Now merge feature into main.
Find the merge base: it is A, the last commit both share. Three-way compare for each line, using A as the reference. Line 1: A has "Hello", main has "Hello there", feature has "Hello". Only main changed it, so take "Hello there". Line 2: nobody changed it. Line 3: A has "Bye", main has "Bye", feature has "Goodbye". Only feature changed it, so take "Goodbye". The merged file is "Hello there", "World", "Goodbye", and Git creates merge commit M with parents B and C and no human help. If both sides had changed line 1 differently, the file would contain conflict markers between the two versions, and you would edit it and commit the result.
Count the objects. Suppose the repository has 1,000 files in 50 directories at depth two, and you change one file. Git writes one new blob, one new tree for the file's directory, one new root tree (and a middle tree if there are three levels) and one commit: about four or five objects, each tens or hundreds of bytes before compression. The other 999 files are not copied. With a 40-character SHA-1 name (20 bytes in binary form), the cost of the pointers is tiny compared with the content. A history of 100,000 commits of a source tree with 20,000 files is held in a few hundred megabytes to a few gigabytes after packing, which is why a full clone is practical for most projects.
Tamper-evidence in numbers. A commit ID, say 9f3c..., is a hash of the tree ID and the parent IDs. If someone alters the file in commit B after the fact, B's ID changes, so C's recorded parent no longer matches, and so on up to the branch tip. Everyone who has the old tip hash can see that history was rewritten. Signing the tip commit or tag with a key therefore protects the whole history.
Bisecting a bug. A bug exists in the version of 1,024 commits ago and not in the version before. Binary search with git bisect needs log₂(1,024) = 10 test runs to find the commit that introduced it, if each commit is buildable. This is one reason small, self-contained commits are valuable.
intuition: An undo history for a whole team, in which every save point is named by a fingerprint of its content and of all that came before it.
The design is natural because it separates what is stored from how it is named. If a name is the fingerprint of the content, then the same content has the same name everywhere, and nothing needs a central authority to assign IDs. Copying becomes safe, since a copy can be verified, and merging two histories is reduced to a graph question: find the common ancestor and combine the differences. Snapshots as immutable objects make everything else, branches, tags, sync, cheap pointers.
mistakes: People often think Git stores diffs between versions. In fact it stores full snapshots as objects, and the packfile compresses similar objects with deltas only as an optimisation that may choose any pair of objects. The mental model of snapshots explains why branching and checkout are fast.
People often think a branch is a copy of the code. In fact a branch is a pointer to one commit, about 41 bytes. Creating a thousand branches costs almost nothing, and the cost of branching is in merging later, not in creating.
People often think git rebase and git merge produce the same history. In fact merge keeps the true graph and adds a merge commit, while rebase creates new commits with new hashes and a straight line. Rebasing commits that others already pulled forces them to reconcile two versions of the same work. Rebase your own unpublished work; do not rewrite shared branches.
People often think deleting a file or a secret from the latest commit removes it. In fact the old blob is still in history and in every clone. A leaked key must be revoked first; removing it from history needs a rewrite tool (git filter-repo) and everyone must re-clone, and even then forks and caches may keep it.
People often think version control is only for source code, and that large binary files do not matter. In fact every version of every binary is kept forever in a Git repository, so a 100 MB file edited 50 times can add several GB to every clone. Use Git LFS or an artifact store for big binaries and data.
friction: Merging remains the weak spot. Textual merge knows nothing about meaning, so it can produce a file that merges cleanly but does not compile or behaves wrongly, and conflicts in generated files, lock files or notebooks are painful. The longer a branch lives, the larger the conflict; this is one reason for trunk-based development and merge queues.
Scale is the second limit. A normal Git clone copies all history, and some commands (status, blame, log on a path) scale with the number of files or commits. A repository with millions of files or hundreds of gigabytes needs partial clone (fetch blobs on demand), sparse checkout (only some directories), a commit-graph file, filesystem monitors, or a different system such as Piper or Sapling. Monorepos also need a build system (Bazel, Buck) that knows what to rebuild, and code-ownership rules.
The data model has limits. Git is poor for large binary files and for data that is not text. It does not track renames explicitly (it guesses them from similarity), and it has no file-level locking for unmergeable files. SHA-1 is no longer collision-safe: the SHAttered attack (2017) produced two different PDF files with the same SHA-1. Git added detection of such attacks and has a SHA-256 object format, but SHA-1 remains the default and most tools assume it.
Last, history quality depends on people. Large noisy commits, messages like "fix", and force-pushes to shared branches make history useless for the tools that depend on it, such as bisect, blame and review.
practice: Keep commits small, focused and buildable, with a message that explains why. A good commit message has a short summary line and a body that gives the reason. This makes review faster and bisecting possible. Prefer short-lived branches that merge into the main branch within a day or two, with feature flags to hide unfinished work, as in trunk-based development; the DORA research links this to high delivery performance.
Protect the main branch: require pull-request review and passing CI checks, use a merge queue to test merges in order, and disable force-push on shared branches. Use CODEOWNERS files so that the right people review changes to sensitive paths. Choose one merge policy for the team (merge commits, squash or rebase) and write it down.
Keep the repository healthy. Do not commit secrets; add secret scanning in CI and a pre-commit hook, and treat any leaked secret as compromised. Keep generated files and large binaries out (use .gitignore, LFS or an artifact store). Sign tags or commits for releases when supply-chain security matters. Use git bisect, git blame and git log -S to understand history, and git reflog to recover lost commits (it keeps old ref positions for about 90 days by default).
For data and infrastructure, apply the same discipline: Terraform and pipeline definitions in Git with review, notebooks stripped of outputs, and, for data, use table versions (Delta and Iceberg time travel) or tools such as lakeFS that give branch-like workflows on data.
tradeoffs: Choose a distributed system like Git when developers work offline or in many time zones, when forks and open collaboration matter, and when history must be cheap to branch. You give up simple central controls (such as per-file locking and fine-grained permissions) and you take on a learning curve in the command set.
Choose trunk-based development with short branches when you have good automated tests and deploy often (see cicd); integration problems are found within hours. Choose long-lived release branches when you must maintain several shipped versions (for example an operating system or an on-premises product). You pay with backports and merge work in proportion to the number of branches.
Choose a monorepo when many projects share code and you want atomic cross-project changes and one version of each dependency. It needs investment in tooling (build, search, code ownership, partial checkout), and a single bad change can break many teams. Choose many repositories when teams are independent and have clear interfaces, at the price of versioned dependencies and harder cross-repo refactors.
Choose merge commits when you want the true history and easy revert of a whole feature; choose squash merges when you want one clean commit per pull request and do not care about intermediate commits; choose rebase when you want a linear history and the branch is private. Each loses something: merges give a busier graph, squashes lose the detail, rebases rewrite hashes.
Choose Git LFS or an artifact registry for files above a few MB that change often, and keep the repository small; you give up the guarantee that a clone alone contains everything.

What are the risks of SHA-1 in Git, and how is Git protected? || SHA-1 collisions have been demonstrated (SHAttered, 2017), so an attacker could in theory craft two objects with one ID. Git uses a hardened SHA-1 that detects known collision attack patterns, and it supports a SHA-256 repository format. Signed commits and tags add authenticity on top.
When would you not use rebase? || On branches that others have already pulled, and when the exact original history is needed for audit. Rebase rewrites commit IDs, so collaborators end up with duplicate commits and painful merges, and signed commits become invalid.
quiz: What are the four object types in Git, and what does a commit contain? || Blob, tree, commit and tag. A commit contains the hash of a root tree, the hashes of its parent commits, author and committer information and a message.
Why does changing one byte in a file change the ID of the commit that contains it? || The blob hash changes, which changes the hash of every tree on the path to the root, which changes the root tree hash stored in the commit, and the commit ID is a hash of that content and its parents.
What is the merge base and why is it needed? || It is the nearest common ancestor of the two commits being merged. A three-way merge compares each side with it to see who changed what; without a base, any difference would look like a conflict.
A repository has 1,000 files and you change one in a subdirectory of depth 2. About how many new objects does the commit create? || About 4 or 5: one new blob, one new tree for the subdirectory, one new root tree (more if the path is deeper), and the commit itself.
Why might a team choose squash merges, and what do they lose? || Squash gives one clean commit per pull request, a simple, linear main branch, and easy revert of a whole change. The team loses the individual commits and their messages, which makes bisecting and archaeology less precise.

value: Continuous integration (CI) means that every developer merges their work into a shared main line many times a day, and each merge is checked automatically by a build and a set of tests. Continuous delivery (CD) goes one step further: every change that passes the checks is packaged and can be released to production by pressing a button, and in continuous deployment it is released with no human step. The goal is to make releasing boring. If releasing is rare, each release carries hundreds of changes, and when something breaks nobody knows which change caused it.
The reasoning is about batch size. A small change is easy to review, easy to test, easy to understand when it fails, and easy to roll back. A large change is none of these. CI/CD is the machinery that makes small changes cheap: instead of a person running tests and copying files to servers, a pipeline does it in minutes, the same way every time. The DORA research programme (Forsgren, Humble and Kim, "Accelerate", 2018) found that teams with short lead times, frequent deployments, low change-failure rates and fast recovery are also the teams with better business results, and that CI/CD practices predict these outcomes.
Several lower layers give the pipeline its strength. Software engineering principles (L3, swe) supply the basic idea: short feedback loops and small batches reduce risk and cost of defects found late. Version control (L1, vcs) supplies the trigger and the identity: a commit hash names exactly what is being built. Deterministic simulation testing (L2, dst) supplies a way to test distributed systems inside CI: a whole cluster, with its network and clock, is simulated in one process driven by a random seed, so rare failure interleavings can be explored by the million and any failure can be replayed exactly. Git (L0) hosts the code and calls the pipeline, and at the top the pipeline deploys onto platforms like Kubernetes.
terms: Pipeline — an automated sequence of stages (build, test, package, deploy) triggered by a change.
Artifact — the immutable output of a build, such as a container image or a package, identified by a version or a digest.
Test pyramid — the advice to have many fast unit tests, fewer integration tests and very few end-to-end tests.
Flaky test — a test that sometimes passes and sometimes fails on the same code.
Canary release — sending a new version to a small share of traffic first and promoting it only if the metrics stay healthy.
Blue-green deployment — running the new version next to the old one and switching traffic at once, keeping the old one for fast rollback.
Feature flag — a runtime switch that turns code on or off without a deployment.
Trunk-based development — everyone integrates into one main branch in small steps, with branches that live for hours or a day or two.
DORA metrics — four measures of delivery performance: deployment frequency, lead time for changes, change failure rate and time to restore service.
Merge queue — a service that tests each pull request on top of the latest main branch before merging it, one after the other or in batches.
history: The idea that integration should be frequent comes from the 1990s, when teams found that merging for the first time just before a release ("integration hell") was the most painful phase. Extreme Programming (Kent Beck, 1999) made "integrate several times a day, with all tests passing" a core practice, and Martin Fowler and Matthew Foemmel wrote the influential article "Continuous Integration" in 2000. ThoughtWorks released CruiseControl in 2001, one of the first CI servers. Hudson (Kohsuke Kawaguchi, 2005) was forked as Jenkins in 2011 after a dispute with Oracle, and Jenkins became the standard open-source server.
Delivery followed. In 2009 John Allspaw and Paul Hammond of Flickr described "10+ deploys per day" at the Velocity conference, which showed that frequent deployment could be safer, not riskier. Jez Humble and David Farley's book "Continuous Delivery" (2010) defined the deployment pipeline as the single path from commit to production. The DevOps movement and the DORA research (reports from 2014, the book "Accelerate" in 2018) measured the effect. Hosted CI services appeared (Travis CI and CircleCI, 2011), and GitHub Actions, announced in 2018 and generally available in November 2019, put pipelines next to the code. Container images, Kubernetes and GitOps tools (Argo CD, Flux) made deployment declarative; Bazel (open source in 2015) made large builds fast and reproducible.
For distributed systems, ordinary tests were not enough. The FoundationDB team built a deterministic simulator before the database itself (Will Wilson described it at Strange Loop 2014), and later systems such as TigerBeetle followed with simulators that run in CI continuously. Chaos engineering (Netflix, around 2010–2011) tests failures in production-like conditions.
how: A pipeline is a program that runs on every change. A typical one has these stages.
Trigger. A push or a pull request calls a webhook from the version control platform (vcs). The runner checks out the exact commit, so the result is tied to a hash. For pull requests, good setups test the result of merging into the latest main branch, not just the branch alone, because a branch that is green alone can break main. A merge queue does this for each change in order.
Build. The code is compiled and dependencies are fetched in a clean, preferably containerised environment. Reproducibility matters here: pinned dependency versions, a lock file, and a build cache so that unchanged parts are not rebuilt. A tool like Bazel hashes every input of each build step, which means that if the hash is unchanged the cached result is reused. The output is an immutable artifact, for example a container image tagged with the commit hash and recorded by digest, and it is built once. The same artifact is then promoted through all environments, so what you tested is what you deploy.
Test. Tests run in layers, ordered by speed and scope. Unit tests (milliseconds each) check functions in isolation. Integration tests start real dependencies, such as a database in a container, and check that components work together. End-to-end tests drive the whole system, are slow and fragile, and should be few (the test pyramid). Static analysis, linters, type checks, dependency scanning and secret scanning run alongside. Test sets are sharded over many machines so that total time stays near ten minutes. Google's testing guidance groups tests by size (small, medium, large) by resources used, and keeps most tests small.
Distributed systems. Tests of a cluster face a problem: the bug appears only in one rare ordering of messages, crashes and timeouts. Deterministic simulation testing (dst) removes the sources of nondeterminism, namely real threads, real clocks and real networks, and runs the system under a scheduler controlled by a seeded pseudo-random generator that also injects faults (dropped messages, slow disks, node crashes). A failing run is reproduced exactly by running the same seed again. Because a simulated hour can take seconds, a nightly CI job can run the equivalent of years of cluster time. Property-based tests, fuzzing and chaos tests add other angles.
Deliver. The artifact is deployed to a staging environment and checked with smoke tests, then to production. The deployment strategy limits damage. A rolling update replaces instances a few at a time. Blue-green switches all traffic at once and keeps the old environment for instant rollback. A canary sends, for example, 1% of traffic to the new version, compares error rate and latency with the old version for some minutes, then moves to 10%, 50% and 100%, or rolls back automatically. Feature flags separate deployment (code is in production) from release (users see it), so a risky feature can be enabled for 1% of users and switched off in seconds without a new deployment.
Database changes need extra care. Use the expand-contract pattern: first add the new column in a backward-compatible way, deploy code that writes to both, migrate data, switch reads, and only later remove the old column. This lets old and new code run at the same time, which is needed for canary and rollback.
Pipelines as code and runners. The pipeline is described in a file in the repository (a YAML file for GitHub Actions or GitLab CI, a Jenkinsfile, or a Bazel and Buildkite configuration), so it is versioned, reviewed and changed together with the code. A scheduler gives each job to a runner: a fresh virtual machine or container that is created for the job and destroyed after it. Fresh runners avoid the hidden state that makes builds pass on one machine and fail on another. Jobs with no dependency between them run in parallel, and a dependency graph decides the order of the others, so the length of the slowest chain (the critical path), not the sum of all jobs, sets the feedback time. Caching of dependencies and build outputs, keyed by a hash of the inputs, is the biggest single saving, often turning a 20-minute build into a few minutes.
Feedback and measurement. Results are reported on the pull request. The pipeline records timing, failure and flake rates, and the team tracks the four DORA metrics. Security belongs in the pipeline: short-lived credentials via OIDC instead of long-lived secrets, signed artifacts, and provenance records (the SLSA framework) so that production runs only what the pipeline built.

example: A team of 20 developers opens about 100 pull requests per day. Their pipeline takes 12 minutes: 4 for build, 3 for unit tests and 5 for integration tests. They keep 300 tests that run on every pull request.
Flaky tests, with arithmetic. Suppose that 5 of the 300 tests are flaky, and each of them fails at random on 10% of runs even when the code is correct. A run has a false failure if at least one of them fails: 1 − 0.9⁵ ≈ 41%. Four runs in ten are red for no reason. Developers then press "re-run" without reading the failure, and later they also ignore real failures. If 30 tests were flaky, the chance would be 1 − 0.9³⁰ ≈ 96%. Google reported that almost 16% of its tests had some flakiness and about 1.5% of all test runs reported a flaky result, and that about 84% of pass-to-fail transitions involved a flaky test (Google Testing Blog, 2016). The fix is to measure the flake rate per test, quarantine the worst automatically, and fix or delete them.
Batch size, with arithmetic. Suppose each change has a 5% chance of containing a defect that production will reveal. If you deploy once per change, a failure points to one change, and you roll back one change. If you deploy weekly with 50 changes, the chance that at least one is bad is 1 − 0.95⁵⁰ ≈ 92%. When it fails, you must find which of 50 changes is guilty. A binary search takes about log₂(50) ≈ 6 rounds of deploy and test, which is hours. So frequent small deployments do not cause more failures per change; they make each failure cheap to find and fix. This is the quantitative reason behind "deploy small and often".
Canary, with numbers. Deploy v2 to 1% of traffic, 1,000 requests per second in total, so 10 req/s go to v2. After 5 minutes v2 has served 3,000 requests. If the baseline error rate is 0.1% (about 3 errors expected) and v2 shows 60 errors (2%), an automatic analysis flags the difference and rolls back. The damage was 60 failed requests, not 3% of an hour of full traffic. The canary needs enough requests to detect a difference: at very low traffic you need a longer time or a synthetic load.
Lead time. Merge at 10:00, pipeline 12 minutes, canary 30 minutes, full rollout at 10:45. Lead time for the change is under an hour, which is well under one day, the level DORA research associates with its best-performing teams.
intuition: Many small, tested steps are safer than one big leap, because after each step you can see the ground.
The design is natural because errors are cheapest to fix when the change that caused them is fresh and small. The pipeline moves the check next to the moment of writing: seconds for a compile error, minutes for a test, an hour for a bad deploy. It also replaces human memory with a script, and a script that runs on every change is a test of the release process itself, so release day stops being special.
mistakes: People often think CI means having a CI server. In fact CI is a practice: integrating into the shared main line at least daily. A team that has Jenkins but keeps feature branches for weeks is not doing CI, however many builds it runs.
People often think continuous delivery means deploying every commit to production automatically. In fact continuous delivery means every commit could be deployed, and the decision to release can be manual. Continuous deployment is the variant with no human step. Many regulated teams do the first and not the second.
People often think more tests mean a safer pipeline. In fact slow or flaky tests reduce safety, because developers stop trusting or waiting for them. A smaller set of fast, reliable tests that run on every change gives better protection than a huge suite that runs once a night.
People often think passing tests prove the system correct. In fact tests show only that the cases you wrote pass. Distributed systems fail in orderings that nobody wrote a test for, which is why simulation, fuzzing, property-based tests, canaries and monitoring are all needed.
People often think rollback is always available. In fact code can be rolled back by redeploying the old artifact, but data cannot: a migration that dropped a column or a message already sent cannot be undone. Rollback needs backward-compatible changes (expand-contract) and feature flags.
friction: Flaky tests are the most common reason that teams lose trust in CI. Causes include shared state, time dependence, order dependence, real network calls and race conditions. They are expensive: each false failure costs a rerun of the whole pipeline, and a team with a 40% spurious failure rate spends much of its time waiting.
Speed is the second problem. A pipeline that takes 40 minutes makes developers batch their changes, which brings back large batches. Remedies are caching, incremental builds, test sharding, running only affected tests, and a hierarchy of fast checks first. Build cost also grows: large CI bills are common, and in-house runners need capacity planning.
Some things are hard to test in a pipeline: data and machine-learning systems (the input data changes, outputs are statistical), infrastructure (a Terraform plan can only be fully verified by applying it), performance (noisy shared machines) and distributed protocols (rare interleavings). Each needs special practice: data quality checks, shadow runs, performance baselines on dedicated machines, simulation.
The pipeline itself is a high-value target. It holds credentials and can ship code to production, so a compromise of CI is a compromise of production (supply-chain attacks). It needs least-privilege short-lived credentials, protected branches, reviewed pipeline definitions and signed artifacts. Finally, the human side matters: ownership of broken builds, on-call for the pipeline, and a rule that a broken main branch is fixed or reverted first.
practice: Keep main always releasable. Run fast checks (build, lint, unit tests) on every pull request within about 10 minutes, and a merge queue so that the tested state is the merged state. Treat a red main branch as an incident: revert first, investigate later.
Build once and promote the same immutable artifact through environments. Keep environment differences in configuration, not in code. Deploy with a canary or a gradual rollout, automatic metric checks and one-command rollback. Use feature flags for risky or large features, and remove old flags quickly because they create their own debt. Apply the expand-contract pattern for schema changes.
Manage tests as a portfolio: many small tests, a modest number of integration tests with real dependencies in containers, a handful of end-to-end checks of the critical paths. Track flake rate per test and quarantine automatically. For distributed systems and storage engines, add deterministic simulation or at least randomised fault-injection tests with reproducible seeds, and run them for long periods outside the pull-request path.
Measure the four DORA metrics: deployment frequency, lead time for changes, change failure rate, and time to restore service. Use them to find the slowest stage, not to compare people. Secure the pipeline: OIDC-based short-lived credentials, pinned and scanned dependencies, secret scanning, signed artifacts and provenance. For data platforms, apply the same practice to pipeline code: tests on sample data, schema checks, jobs deployed from version control (for example Databricks asset bundles) and promoted dev to staging to production.
tradeoffs: Choose trunk-based development with short-lived branches when your tests are fast and trustworthy and you deploy often; choose longer release branches only when you must support several shipped versions. Long branches cost merge pain that grows faster than linearly with their age.
Choose continuous deployment (every green commit goes to production) when you have strong automated tests, canaries and fast rollback, and the cost of a bad change is small. Choose continuous delivery with a manual release gate when regulation, contracts or the cost of failure (payments, medical, safety) demand a human or a change window. You give up some speed; keep the pipeline automated so the gate is a button, not a project.
Choose many fast unit tests when logic is local and the system is simple. Choose more integration and contract tests when most bugs are at service boundaries, as in microservices. End-to-end tests give the highest confidence per test and the highest cost and flake rate, so keep them for critical paths only.
Choose canary or gradual rollout when traffic is high enough to detect problems quickly and metrics are good. Choose blue-green when you need an instant switch and can afford double capacity for a short time. Choose feature flags for decoupling release from deployment, accepting extra code paths and the need to clean up.
Choose deterministic simulation when you build a distributed or stateful system where a rare race would be catastrophic (databases, consensus, storage). It needs an engineering investment up front: all I/O and time must go through an abstraction you can simulate. For an ordinary web service, standard integration tests and canaries give most of the value at a much lower cost.
Choose a hosted CI service for a small team to avoid operating runners; choose self-hosted runners when builds are large, need special hardware, or must stay inside your network. Hosted means per-minute cost and less control; self-hosted means capacity planning and security work.

value: A data lake is a large, cheap store in which an organisation keeps its data in raw or lightly processed form, as plain files: logs, events, database exports, images, documents. Nothing has to be modelled in advance. You write first and decide how to read later (schema-on-read). Many different engines (Spark, Trino, Presto, Athena, Python notebooks, machine-learning jobs) can then read the same files without copying them.
The problem it solved was cost and rigidity. A traditional warehouse required you to design tables, clean the data and load it before anyone could query it, and it charged warehouse prices for storage on specialised hardware. Web companies in the 2000s produced terabytes of clicks and logs per day, much of whose value was unknown at the time. Keeping everything in files on cheap disks, first in HDFS and then in cloud object storage, cost a small fraction of a warehouse, and it kept the option to answer questions that nobody had asked yet. In an ad-tech system, for example, every bid request, impression and viewership event can be kept for a year or more, and reprocessed when a new attribution method is invented.
Three lower ideas make the lake work. Separating storage from compute (L2, sepstorage) means that the files live in object storage, which is always on and cheap, and compute clusters are started when needed and thrown away; any number of engines can read the same data at once. Erasure coding (L2, erasurecoding) is how object stores keep data durable at low cost: instead of keeping three full copies (200% extra space), they split each object into data and parity fragments, for example 10 data plus 4 parity fragments (40% extra), and survive the loss of several disks or even a whole data centre. Partitioning (L2, partitioning) lays out files in directories by date or key, so that a query reads only the directories it needs. The products built on it are HDFS, Amazon S3 and the big cloud platforms (cloud); the lakehouse is its successor, which adds tables and transactions.
terms: Object storage — a service that stores immutable blobs under flat keys and gives them over HTTP (S3, GCS, Azure Blob), with no real directories.
Schema-on-read — the structure of data is applied when it is read, not when it is written.
Schema-on-write — data must fit a defined table structure before it is stored; the warehouse approach.
Parquet — an open columnar file format that stores each column of a group of rows together, with compression and statistics.
Partition — a subset of a dataset kept in its own directory, such as dt=2026-10-25, so queries can skip the rest.
Catalog (metastore) — a service that maps table names to file locations, schemas and partitions (Hive Metastore, AWS Glue).
Data swamp — a lake where files have no owner, schema or quality control, so nobody can trust or find anything.
Small-file problem — the slowdown that comes from having millions of tiny files instead of fewer large ones.
Medallion layers — a naming convention for zones: bronze (raw), silver (cleaned), gold (curated for use).
history: James Dixon, then the CTO of Pentaho, used the term "data lake" in a 2010 blog post. He contrasted a data mart, which is like bottled water that is cleaned and packaged for easy use, with a lake, which holds the data in its natural state and from which many users can take samples in their own way.
The technical roots are earlier. Google's GFS and MapReduce papers (2003, 2004) showed how to store and process huge files on cheap machines. Hadoop (2006) and its file system HDFS made this available to everyone, and Hive (Facebook, 2007–2008) put SQL tables on top of files. In March 2006 Amazon launched S3, and by the mid-2010s object stores were cheaper, more durable and easier to run than HDFS clusters. Parquet (2013) and ORC gave open columnar formats, which made scans over files fast enough for analytics. Presto (Facebook, 2012) and Spark (2014 as a top-level project) read directly from object storage.
By the late 2010s many companies had a lake with petabytes and little trust in it: files with unknown schemas, no owner, half-written outputs after failed jobs, no way to update or delete a row. This was called the data swamp. Table formats added transactions on top of the files: Apache Hudi (Uber, 2016–2017), Apache Iceberg (Netflix, 2017–2018) and Delta Lake (Databricks, 2019). The Lakehouse paper (Armbrust et al., CIDR 2021) described the combined design. Amazon S3 also changed under the lake: since December 2020 it gives strong read-after-write consistency, and in 2024 it added conditional writes, which table formats can use to commit safely.
how: A lake is a storage layer, a layout convention, a catalog and a set of engines.
Storage. Files are objects in an object store. An object is written whole and never modified in place; to change data you write a new object. Names are flat keys such as events/dt=2026-10-25/hour=13/part-0007.parquet. The slashes are only part of the name, so a "directory" does not exist, a listing is a prefix search, and a "rename" is a copy followed by a delete, which is neither fast nor atomic. A list call returns at most 1,000 keys, and S3 supports roughly 3,500 write and 5,500 read requests per second for each prefix. The first byte of a GET takes tens of milliseconds, against about 100 microseconds for a local NVMe disk, but throughput scales with parallelism, so engines fetch many byte ranges at once.
Durability and cost. Behind the interface the store keeps each object in several data centres using replication or erasure coding (the layer below). Object stores quote 11 nines (99.999999999%) of annual durability. The storage price is roughly $23 per terabyte-month for the standard tier of S3 in a main US region, against roughly $80 per terabyte-month for a general-purpose SSD volume, and colder tiers cost much less. The cheapness comes from erasure coding and from the lack of POSIX features: no in-place updates, no locks, no directories.
Formats. Raw data arrives as JSON, CSV, Avro or logs. A pipeline converts it to Parquet. A Parquet file is divided into row groups (often 128 MB or so), and inside each group every column is stored together, compressed and dictionary-encoded, with min/max statistics in the footer. An engine reads the footer first (one small request), keeps only the columns the query needs (column pruning) and skips row groups whose statistics cannot match the filter (predicate pushdown). JSON converted to Parquet is commonly 5 to 10 times smaller.
Layout and partitioning. Data is arranged in a path scheme, usually by date, so that a query with a filter on date reads only some directories. This is partition pruning (partitioning). The designer picks partition columns with a moderate number of values: too few and queries read too much, too many and files become tiny. The goal is files of about 128 MB to 1 GB.
Catalog. A metastore records for each table its location, schema, format and list of partitions. Engines ask the catalog for the file list, then read the files directly. Without a catalog, every user needs to know paths and formats by heart. Access control and lineage are attached to catalog objects (Unity Catalog, Glue and Lake Formation, and others).
Compute. Engines such as Spark, Trino, Athena and BigQuery external tables start as stateless clusters, read the needed byte ranges, and write results back as new files. Because the data is in shared storage (sepstorage), a team can start a 500-core cluster for an hour, and a second team can query the same files with another engine at the same time. Storage and compute scale and are billed separately.
A query, step by step. The engine receives SQL, asks the catalog for the table's location, schema and partitions, and removes the partitions that the filter excludes. It then lists the remaining prefixes, which costs one list call per 1,000 files, and splits the files into tasks of about 128 MB. Each task reads the Parquet footer, decides which row groups and columns it needs, and issues parallel range reads. Decompression and filtering happen on the compute nodes, so the network between storage and compute (often 10 to 100 Gbit/s per node) is the main limit for scan speed. Intermediate results move between workers in a shuffle, and the final result is returned or written back as new files. Nothing in this path needs a server that owns the data, which is why compute can be added or removed freely, and also why every query pays the cost of listing and footers again unless a metadata layer or cache remembers them.
Missing guarantees. A plain lake has no atomic commit across files. A Spark job that writes 200 files can fail after 120, leaving a partial result visible. Readers can see half of an overwrite. You cannot update or delete one row without rewriting the file that holds it, which is a problem for privacy deletion requests. These gaps are what table formats such as Delta, Iceberg and Hudi fix with a transaction log, and with them the lake turns into a lakehouse.

example: An ad-tech company logs about 2 TB per day of raw JSON events: impressions, clicks and viewership. It stores them in a lake on S3.
Step 1, landing. A streaming job writes JSON files every minute for each of 200 Kafka partitions. That makes 200 × 1,440 = 288,000 files per day, each about 2 TB / 288,000 ≈ 7 MB. This is the small-file problem. A query over 30 days would have to open 8.6 million files, and listing alone needs 8,600 list calls, with a GET of tens of milliseconds for every file. It would be slow even on a big cluster.
Step 2, compaction and conversion. A nightly job reads the day's JSON and writes Parquet. If Parquet is 5 times smaller, the day shrinks to about 400 GB. Target file size is 256 MB, so the day becomes about 1,600 files, partitioned as dt=2026-10-25/hour=13. That is 180 times fewer files, and each is large enough for a long sequential read.
Step 3, query. An analyst asks: clicks for campaign 77 yesterday. The catalog tells the engine that the table has partition column dt. Partition pruning picks one day out of 365: 1/365 of the data, or about 400 GB. Column pruning reads only 3 columns out of 40, so roughly 400 GB × 3/40 = 30 GB. Row-group statistics on campaign_id skip most of what is left if the data was sorted or clustered by campaign. A 100-core cluster reading at about 50 MB/s per core can read 30 GB in 30 GB / 5 GB/s = 6 seconds, plus planning. Without pruning the same query would read 2 TB × 365 days of raw JSON, around 730 TB, which would take hours and cost real money.
Step 4, cost. One year of Parquet is 400 GB × 365 ≈ 146 TB, which at about $23 per TB-month is about $3,400 per month. Three-way replicated local disks in a self-run HDFS cluster would need 438 TB of raw disk plus servers, network and people. The comparison is why most new lakes use object storage.
Step 5, deletion request. A user asks for deletion under privacy law. In a plain lake you must find every file that contains that user (the lake has no index), rewrite those files without the user's rows and replace them. If you cannot find them, you scan everything. This is the main reason to adopt a table format.
intuition: A huge, cheap warehouse where you can put anything on the shelf now and decide later how to use it, as long as you label the shelves.
The design is natural because writing is easy and reading is hard. At write time you often do not know what questions will be asked, so the cheapest thing is to store faithfully and defer decisions. Object storage gives an almost unlimited flat space with very high durability, the file formats carry just enough structure (columns, statistics) for fast scans, and compute is rented only while a question is being answered. The price of deferring decisions is that someone must eventually decide, and a lake without an owner, a catalog and a contract is a swamp.
mistakes: People often think a data lake replaces the data warehouse. In fact a raw lake lacks transactions, curated models and fast, predictable BI queries. It stores the data; someone still has to clean and model it. That is why teams add warehouse layers or move to a lakehouse.
People often think a lake is a folder you can dump anything into with no design. In fact without a catalog, naming rules, owners and quality checks it becomes a swamp within a year or two. "Schema-on-read" moves the work, it does not remove it: every reader has to understand the schema, and they may all understand it differently.
People often think object storage behaves like a file system. In fact it has no atomic rename, no directories, and no append. Code written for HDFS that relies on rename for commits can produce duplicate or partial data on object storage unless a committer or table format handles it.
People often think more partitions always make queries faster. In fact too many partitions (for example partitioning by user ID) create millions of tiny files and a huge partition list for the catalog, which slows planning and reads. Partition by a low-cardinality column such as date, and use sorting or clustering inside files for the rest.
People often think the lake is cheap, so cost is not a problem. In fact storage is cheap but scanning is not: queries that read whole tables, requests on millions of small objects, cross-region transfer and unneeded copies can cost more than the stored data.
friction: The central problem is reliability without transactions. Failed jobs leave partial output, concurrent writers can overwrite each other, readers see inconsistent states, and there is no way to update a row cheaply. Table formats solve this, but they add a layer (a log, a catalog, maintenance jobs for compaction and expiry) that must be run well.
Metadata is the second. Listing millions of objects is slow, the small-file problem damages query planning, and the catalog may become a bottleneck. HDFS has a related limit, because the NameNode keeps all file metadata in memory (roughly 150 bytes per file or block), so hundreds of millions of files strain it. Governance is the third: who owns this dataset, which columns hold personal data, who may read them, when must they be deleted, and how do you know that a dashboard number came from a trusted source? Lineage, access control and data quality tests have to be built in.
Performance is the fourth. A GET to object storage has tens of milliseconds of latency, so interactive query speed depends on caching (local SSD caches), large files, and good layout. Warehouses with tuned internal storage can still be faster for repeated dashboard queries. Finally, costs surprise teams: egress between regions or clouds, millions of LIST and GET requests, and forgotten copies of data.
practice: Treat every dataset as a product with a minimum contract: a catalog entry, an owner, a schema, a partition scheme, a retention period and a data classification. Use open columnar formats (Parquet) for everything past the raw zone, and a table format (Delta or Iceberg) for any table that is updated, merged or deleted from. Organise zones (bronze, silver, gold) and restrict write access to the raw zone.
Control file sizes: aim for 128 MB to 1 GB per file, compact small files regularly (OPTIMIZE or equivalent jobs), and avoid writing one file per micro-batch per partition. Partition by date, or a similar low-cardinality column, so that each partition holds at least a few GB; cluster or sort inside files for other filters (Z-order, liquid clustering, sorting keys).
Control cost and risk. Set lifecycle rules to move old raw data to colder tiers and delete what the retention policy allows; monitor request counts and scan bytes; turn on object versioning and protect against accidental deletion. Keep a map of where personal data lives, so that deletion and access requests can be honoured, and encrypt buckets with managed keys. Expose curated tables, not raw paths, to most users, and test data quality (null rates, duplicates, row counts) in the pipeline that produces each table.
tradeoffs: Choose a data lake (raw files in object storage) when you have large volumes of varied data, unknown future uses, and ML or batch workloads that read big ranges. You give up transactions, fast row updates and predictable BI latency, and you accept the work of governance.
Choose a warehouse when the main use is SQL reporting on well-understood, modelled data, with many concurrent dashboard users and a need for predictable performance. You give up cheap storage for raw and unstructured data, and you pay for proprietary storage and compute; you must model before you load.
Choose a lakehouse (a lake with a table format such as Delta or Iceberg) when you need both: open storage, ACID updates and deletes, time travel, and BI-quality SQL, at lake cost. You take on the operational work of compaction, vacuum and catalog management.
Choose object storage over HDFS for a new platform unless you need very low latency or data locality: object storage costs less per terabyte, is durable without running disks, and separates compute. You give up rename semantics and low per-request latency, and you must tune for many parallel reads. Choose HDFS or local SSD caching when workloads re-read the same hot data thousands of times.
Choose coarse partitions (day, or day and hour) and large files when scans dominate. Choose finer layouts only when queries nearly always filter on that key, and accept the small-file cost, which compaction jobs must repay.
interview: What is the difference between a data lake and a data warehouse, and why did lakehouses appear? || A warehouse stores curated, modelled data in managed columnar storage with transactions and fast SQL; a lake stores raw open-format files cheaply in object storage with schema-on-read. Lakes had no transactions, updates or governance, and warehouses were costly and closed. Lakehouses add a transactional table layer over open files to get both.
Why is S3 rename a problem for big data jobs? || There is no rename. It is a copy then delete, which is slow for large objects and not atomic, so a job that commits by renaming temporary files to final names can leave partial or duplicate output on failure. Use committers designed for object stores or a table format with an atomic log commit.
You have 50 million small files in a table and queries are slow. What do you do? || Compact them into files of about 256 MB to 1 GB with an OPTIMIZE-like job, fix the writer so that it does not produce so many files (larger batches, repartition before write, auto-compaction), and revisit the partition scheme. Check catalog and listing costs, and set up regular maintenance.
How do you delete one user's data from a petabyte lake? || Without a table format you must find all files that contain the user (often impossible without an index) and rewrite them. With a table format use a DELETE with a predicate, which rewrites only the affected files, then expire old snapshots and vacuum so that old files are actually removed. Keep a record of where personal data is stored and use keys such as hashed IDs to find it quickly.
How does the lake get its low cost, and what does it give up? || Erasure-coded object storage has about 1.3 to 1.5 times storage overhead against 3 times for replication, and storage is decoupled from compute so you pay for compute only while queries run. It gives up in-place updates, rename, POSIX semantics and low per-request latency.
How would you decide the partitioning of a new events table? || Look at the dominant filters in queries and at data volume. Usually partition by date (maybe hour for very high volume), keep partitions at several GB at least, and use clustering or sorting for other columns. Avoid high-cardinality partition keys, which produce millions of tiny files.
quiz: What is schema-on-read? || The structure of the data is applied when the data is read, so raw data can be stored without a predefined table design. Each reader interprets the data at query time.
Why is object storage cheaper than three-way replication on disks? || Erasure coding stores data and parity fragments (for example 10 + 4), giving about 40% overhead instead of 200%, and storage is shared by many customers without running compute servers.
What is the small-file problem and what causes it? || Many tiny files make listing and opening costly: each file needs a request with tens of milliseconds of latency and metadata to track. It is caused by frequent micro-batch writes, too many partitions and too many writers.
A day of data is 2 TB of JSON. It becomes Parquet 5 times smaller, and a query touches 3 of 40 columns on one day. About how much data does it read? || The day is about 400 GB in Parquet. Reading 3 of 40 columns reads about 400 × 3/40 = 30 GB, before row-group skipping.
When would you prefer a warehouse or a lakehouse over a plain data lake? || When users need reliable updates and deletes, consistent reads, governed tables and fast SQL for dashboards. A plain lake suits raw landing and ML reads, but it lacks transactions and curation.

@@ warehouse
value: A data warehouse is a database built to answer questions about the business, not to run it. It holds integrated, cleaned, historical data from many operational systems (orders, billing, ad delivery, support), arranged so that analysts can ask questions such as "revenue by product category by month for the last three years" and get an answer in seconds. It exists because the two kinds of work do not fit together. A transactional database (OLTP) handles many small reads and writes on a few rows and must stay fast for customers. An analytical query reads millions or billions of rows and a few columns. Run on the same system, the analytical query slows down the customer, and the OLTP schema (normalised across dozens of tables) is awkward for analysis.
So a warehouse copies data out of the operational systems, reshapes it, and stores it for reading. Its users are analysts, BI dashboards, finance, data scientists and increasingly machine-learning and AI applications. Its value for the layer above is a single place where numbers agree: one definition of "active user" or "revenue", one history, one access policy.
Five lower ideas explain how it is fast and affordable. Columnar storage (L2, columnar) means a query reads only the columns it uses and compresses each column well. Separating storage from compute (L2, sepstorage) keeps the data in cheap shared object storage and lets you add or remove compute clusters for each workload. Query optimisation (L2, queryopt) uses table statistics to choose join order and join method, which can change a query's cost by factors of 100 or more. SQL (L3, sql) is the common language that every BI tool speaks. Dimensional modelling (L1, dimmodel) gives the usual shape of the data, the star schema, which fits both how people think and how the engine joins. Snowflake, BigQuery and Redshift (L0) are the main managed products.
terms: Fact table — a very large table that records events or measurements (one row per sale or per ad impression), with keys to dimensions and numeric measures.
Dimension table — a smaller table that describes the context of facts (product, customer, date, store); it is used to filter and group.
Star schema — a fact table in the centre, joined to denormalised dimension tables around it.
Grain — the exact meaning of one row in a fact table, for example "one line item of one order".
ETL / ELT — extract, transform, load: transform before loading (ETL), or load first and transform inside the warehouse with SQL (ELT).
Slowly changing dimension (SCD) — a method to keep history when a dimension attribute changes; type 2 adds a new row with valid-from and valid-to dates.
MPP — massively parallel processing: many nodes each scan and process a slice of the data at the same time.
Zone map — min and max values stored for each block of data, used to skip blocks that cannot match a filter.
Materialized view — a query result stored and kept up to date, so repeated questions are answered without recomputing.
Semantic layer — a shared definition of metrics and dimensions that dashboards and tools reuse.
history: Business reporting on separate copies of data began in the 1980s, when companies saw that running reports on production systems hurt them. Teradata (founded 1979, first systems in 1984) built parallel database machines for this. Bill Inmon's "Building the Data Warehouse" (1992) defined the warehouse as subject-oriented, integrated, time-variant and non-volatile, and recommended a central normalised store feeding departmental marts. Ralph Kimball's "The Data Warehouse Toolkit" (1996) took the other route: build dimensional marts first, joined by shared (conformed) dimensions. The two ideas are still debated; most teams use a mix. E. F. Codd's 1993 paper gave the name OLAP to multi-dimensional analysis.
The 2000s brought speed through new storage design. Column stores such as the C-Store research prototype (Stonebraker et al., VLDB 2005) and its product Vertica, and MonetDB/X100 with vectorised execution (2005), showed that reading columns in batches was an order of magnitude faster than row-by-row. Appliance vendors (Netezza, Greenplum, Aster) used MPP clusters. Hadoop (2006) offered cheap scale-out but slow, batch-style SQL.
The cloud then changed the economics. Google described Dremel in 2010 and launched BigQuery (available in 2011), which scans columns across thousands of machines and bills per use. Amazon announced Redshift in 2012 and made it available in 2013, based on a licensed ParAccel engine. Snowflake, founded 2012 and widely available from 2015, described its design in a SIGMOD 2016 paper: storage in S3, compute in independent "virtual warehouses", and one metadata service. From about 2020 the lakehouse approach (Databricks SQL, with the Photon engine) and open table formats (Iceberg, Delta) brought warehouse-style SQL to files in object storage, and the warehouses began to read the same open formats. The two kinds of product are converging.
how: Follow the data from source to dashboard.
Load. Data arrives from operational databases (by change data capture or nightly extracts), event streams, SaaS tools and files. It is first copied to a staging area as it is. Then it is transformed into the warehouse model. In the older ETL style, a separate engine transforms the data before loading. In the ELT style, which cloud warehouses made practical, raw data is loaded first and the transformation is SQL running inside the warehouse (tools such as dbt manage these as version-controlled models with tests). Typical layers are raw, cleaned and conformed, and marts.
Model. In a star schema (dimmodel), the central fact table has one row per event at a declared grain, plus foreign keys and numeric measures; dimension tables are wide and denormalised, with attributes such as product name, brand and category in one table. Denormalising dimensions means fewer joins and easy-to-read queries. When a dimension attribute changes (a product moves to another category), slowly changing dimension type 2 closes the old row and adds a new row, so old sales still show the old category. Conformed dimensions, shared by several facts, let you compare sales with returns or with ad spend on the same date and product.
Store. Each table is stored column by column, in blocks of rows. A column block holds values of one type, so it compresses well with dictionary encoding, run-length encoding and delta encoding, often by 3 to 10 times. Each block keeps zone-map statistics (min and max). Data is usually clustered or sorted by a key such as date, so a filter on date skips most blocks. Files are immutable. Snowflake calls its units micro-partitions (tens to hundreds of megabytes of data), and updates write new files and change metadata, which also gives time travel and cheap copies.
Execute. A query is parsed, and the cost-based optimiser (queryopt) uses statistics (row counts, distinct counts, histograms) to choose a plan. It pushes filters down to the scan, picks the join order (usually filtering the most selective dimension first), and picks the join method. If a dimension is small, the engine broadcasts it to every node, and each node joins its slice of the fact table locally with a hash join. If both sides are large, both are shuffled across the network by the join key, which is far more expensive. Aggregation is done in two steps: each node computes partial sums for its slice, then a final step merges them. Vectorised execution processes thousands of values per call in tight loops, which uses CPU caches and SIMD instructions well.
Separate storage and compute. In Snowflake, BigQuery and Redshift RA3, persistent data sits in object storage (sepstorage), and compute nodes cache hot blocks on local SSD. You can run a large cluster for the nightly load, a small one for dashboards and another for a data science team on the same data, and none of them slows the others. Compute can be suspended when idle. Billing follows either compute time (Snowflake credits, Redshift node hours or serverless units) or bytes scanned (BigQuery on-demand), and BigQuery also offers reserved slots.
Updates and consistency. Warehouses are not built for single-row updates, but they do support MERGE, UPDATE and DELETE. Because files are immutable, an update rewrites the affected blocks as new files and then switches the table metadata to the new file list in one atomic step. Readers that started earlier keep seeing the old list (snapshot isolation), so a long dashboard query never sees half of a load. The same mechanism gives time travel: the old file list is kept for a retention period (one day by default for some products, up to 90 days in others), so you can query the table as it was yesterday or undo a bad load. The cost is write amplification, since changing one row rewrites a whole block, which is why batch loads of many rows are much cheaper than many small updates.
Serve. Result caching returns the same answer immediately when the query and data are unchanged. Materialized views precompute frequent aggregations. Workload management queues and limits queries so that one analyst cannot starve a dashboard. Row and column policies and masking control who sees what, and data sharing lets other accounts query your tables without copying. A semantic layer defines metrics once, so the finance dashboard and the product dashboard show the same revenue.

example: A retailer has a star schema. fact_sales has 10 billion rows, one per order line, with 20 columns, about 100 bytes per row in row format. Dimensions are dim_date (4,000 rows), dim_product (100,000 rows, with category) and dim_store (2,000 rows). History covers three years (12 quarters).
The question. Revenue by product category for the third quarter of 2026:
SELECT p.category, SUM(f.amount) FROM fact_sales f JOIN dim_product p ON f.product_key = p.product_key JOIN dim_date d ON f.date_key = d.date_key WHERE d.quarter = '2026-Q3' GROUP BY p.category.
Row store cost. Reading 10 billion rows of 100 bytes means scanning about 1 TB, whatever the question. At 2 GB/s on one machine that is 500 seconds.
Columnar cost. The query needs three columns: date_key (4 bytes), product_key (4 bytes) and amount (8 bytes), 16 bytes per row, so 10 billion × 16 B = 160 GB uncompressed. With a typical 4 times compression it is about 40 GB. The table is clustered by date, and zone maps skip all blocks outside Q3. One quarter out of 12 is about 1/12, so the scan is about 40 GB / 12 ≈ 3.3 GB. That is 300 times less data than 1 TB.
Parallel execution. On 20 nodes each node scans about 165 MB, which takes well under a second at 1 GB/s per node. The optimiser sees that dim_date filtered to Q3 has only 92 rows and dim_product has 100,000 rows, about 5 MB with its columns. It broadcasts both to every node (5 MB × 20 nodes = 100 MB of network traffic in total), and each node joins locally. If it had shuffled the fact table by product_key instead, it would move several GB across the network. Each node then keeps partial sums for the few hundred categories and sends only those few hundred rows to the final step. The answer arrives in about a second.
History kept correct. In the second quarter a product moved from category "Toys" to "Games". With slowly changing dimension type 2, dim_product now has two rows for the product: key 501 (Toys, valid until June 30) and key 982 (Games, valid from July 1). New sales use key 982, so Q3 revenue is under Games and Q1 revenue is still under Toys, which is what the business wants to report.
Cost control. On a bytes-scanned plan, the query bills for about 3.3 GB, not for the 160 GB column data or the 1 TB row data. A SELECT * version over the same quarter would read all 20 columns: about 1 TB of rows, roughly 250 GB after 4 times compression, and about 21 GB for one quarter, six times more bytes for the same date filter. This is why partitioning, clustering and avoiding SELECT * are the main cost rules.
intuition: A well-organised archive, filed so that the common questions can be answered by opening only a few drawers.
The design is natural once you see that analytical questions touch few columns of many rows and almost never change old data. So you store by column, compress heavily, sort by time, and skip what cannot match. Because the facts are the same everywhere, you describe them once in dimensions that all facts share, so numbers agree. Because compute is only needed while someone asks, you keep data in cheap shared storage and rent compute by the second.
mistakes: People often think a warehouse is just a big copy of the production database. In fact its schema is redesigned for questions (facts and dimensions, one history), it stores columns, and it has loads and checks. A copy of OLTP tables with joins across 30 tables is slow, hard to understand and gives different answers in different dashboards.
People often think a warehouse is fast because it uses a lot of hardware. In fact most of the speed comes from reading less: columns, compression, zone maps and partition pruning. Hardware helps after that. A badly written query that scans everything is still expensive on a big cluster.
People often think warehouses and lakes are opposite, so you must choose one. In fact they overlap more every year: warehouses read open table formats such as Iceberg, and lakehouses offer warehouse SQL. The real choices are about governance, workload, cost and openness.
People often think normalisation is always better, as in OLTP. In fact a warehouse denormalises dimensions on purpose. Updates are rare and batch, so update anomalies matter little, and fewer joins make queries simpler and faster.
People often think ELT means no modelling is needed since SQL can transform anything later. In fact without agreed grains, keys and metric definitions, a warehouse becomes a pile of inconsistent tables. Raw loading is easy; the value is in the modelled layer.
friction: Cost is the first problem. Pay-per-scan or pay-per-second pricing makes mistakes expensive: a dashboard that refreshes every minute on a large table, an unbounded exploratory query, or a cluster left running can double a bill. You need budgets, query tagging by team, and weekly review of the most expensive queries.
Latency of data is the second. Most pipelines are batch or micro-batch, so data may be minutes to hours old, and streaming ingestion adds complexity. Point lookups and many small updates are weak; a warehouse is not an OLTP system, and a high rate of single-row writes is slow or costly. Schema change is the third: a change in a source system breaks pipelines and downstream models, and without contracts and tests the break is found by a user.
Proprietary storage creates lock-in. Moving petabytes out of one vendor to another is slow and costly, and SQL dialects differ. Open table formats reduce this. Governance is hard at scale: personal data in many tables, access rules per column and row, deletion requests, and lineage from dashboard back to source. Finally, concurrency and workload mix need care. Many dashboard users, big nightly transforms and ad-hoc queries compete unless you separate them into different compute clusters or queues, and a semantic layer is needed so that definitions of metrics do not drift.
practice: Model for the questions people ask. Declare the grain of each fact table, use surrogate keys, make dimensions wide and descriptive, and keep conformed dimensions shared. Use SCD type 2 where history of attributes matters. Write the metric definitions once, in code or a semantic layer, and review changes.
Keep transformation logic in version control with tests (dbt or declarative pipelines): uniqueness and not-null tests on keys, accepted values, row-count and freshness checks, and reconciliation against the source. Run models incrementally for large tables, not full refreshes.
Control cost. Partition or cluster big tables by the column most queries filter on (usually date). Select only needed columns. Use materialized views or summary tables for dashboards that run the same query often. Use separate compute for loads, dashboards and ad-hoc work, auto-suspend idle compute, and set budgets, query timeouts and per-team tags. Review the top 20 queries by cost every week.
Plan for openness and safety: prefer open table formats when the choice exists, and apply row and column security, masking of personal data and audit logs. Monitor freshness and failures, and tell users when data is late. Keep the warehouse out of the path of customer-facing latency; if an application needs data from it in milliseconds, serve it from a cache or a serving store.
tradeoffs: Choose a managed cloud warehouse (Snowflake, BigQuery, Redshift) when your workload is SQL analytics and BI, you want minimal operations, and you accept usage-based pricing. You give up control over storage and engine internals, and you accept lock-in unless you use open formats.
Choose a lakehouse (Databricks, or engines on Iceberg or Delta) when you also have large raw data, data science and machine learning on the same data, and a need for open files. You take on more engineering of layout, maintenance and governance, in return for flexibility and lower storage cost.
Choose dimensional models (star schemas) for BI and shared metrics, where readability and join speed matter. Choose wide, flat tables (one big table) when one tool reads one use case and you want the simplest and fastest queries; you give up reuse and consistency across use cases. Choose a Data Vault or Inmon-style central model when many sources change often and auditability matters more than query convenience, and add marts on top.
Choose on-demand (pay per byte scanned) pricing for spiky and small use, and reserved capacity or provisioned compute for steady, heavy use. On-demand makes bad queries a direct cost; reservation makes cost predictable but wastes money when idle.
Choose ELT (load raw first, transform in the warehouse) when the warehouse is elastic and your team knows SQL, so you can reprocess history by changing code. Choose ETL when data must be filtered or masked before it enters the warehouse, for privacy reasons or to save loading cost.
interview: Why is a columnar warehouse so much faster than a row store for analytics? || Queries read a few columns of many rows. Columnar layout reads only those columns, compresses similar values together (often 3 to 10 times), skips blocks with min/max statistics, and processes values in vectors. So the I/O and CPU per query drop by large factors, typically 10 to 100 times for wide tables.
How does a warehouse join a 10-billion-row fact table with a 100,000-row dimension table? || The optimiser broadcasts the small dimension to every node, and each node builds a hash table and joins its local slice of the fact table. No fact rows move across the network. For two large tables it must shuffle both by the join key, or use co-located distribution keys to avoid the shuffle.
What does separating storage and compute give, and what does it cost? || Independent scaling and isolation of workloads, pay-for-use compute, cheap durable storage and easy data sharing. It costs cold-cache reads from remote storage, which are slower than local disks, so engines add SSD caching, and data movement over the network between layers.
A dashboard that used to cost $50 per day now costs $800. How do you investigate? || Look at query history by user, tag and bytes scanned or credits used. Find the query or model that changed: a lost partition filter, a SELECT *, a new full refresh, a join that explodes, or a refresh interval that was shortened. Fix with pruning, clustering or a materialized view, and set a budget alert.
Kimball or Inmon, and what would you do in a company with 30 source systems? || It depends on goals. I would land raw data, build a cleaned, integrated layer with stable keys (Inmon- or Data Vault-like) so that sources can change without breaking everything, and expose dimensional marts (Kimball) for BI. The deciding factors are the speed of source change, audit needs and the number of consumers.
How do you handle a dimension attribute that changes over time? || Decide if reports need the old or the new value. SCD type 1 overwrites, which loses history. Type 2 adds a new row with valid-from and valid-to dates and a new surrogate key, so facts keep pointing to the version in force at the time. The costs are more rows and queries that must choose the right version for an as-of question.
quiz: What are a fact table and a dimension table? || A fact table holds events or measurements, one row per event at a declared grain, with keys and numeric measures. A dimension table holds descriptive context such as product or customer, used to filter and group.
Why do zone maps speed up queries on a table clustered by date? || Each block stores the min and max of its date values, so the engine can skip every block whose range does not overlap the filter without reading it.
Why is a broadcast join cheap for a star schema query? || The dimension table is small, so sending a copy to every node costs little network traffic, and each node joins its own slice of the huge fact table locally with no shuffle of fact rows.
A table has 10 billion rows. A query needs 3 columns of 16 bytes per row total and compresses 4 times. About how much data does a full scan read, and what if a filter keeps 1/12 of the blocks? || 10 billion × 16 B = 160 GB, about 40 GB compressed. With 1/12 of blocks, about 3.3 GB.
When would you choose ELT over ETL? || When the warehouse is elastic and cheap enough to hold raw data and run SQL transforms, so that logic is easy to change and history can be reprocessed. Choose ETL when sensitive data must be removed or masked before loading.

@@ oltp
value: OLTP stands for online transaction processing. It is the kind of database work that runs the daily life of a business: place an order, move money between accounts, book a seat, update a profile, record that an ad impression was served. Each operation touches a handful of rows, takes a few milliseconds, and there may be thousands of them per second from thousands of users at the same time. The defining demand is not speed alone but correctness under concurrency and failure. Two people must not buy the last seat. A transfer must not take money from one account and lose it before adding it to another. After a power cut, every confirmed order must still be there.
The tool that gives these guarantees is the transaction: a group of reads and writes that behave as one unit with the ACID properties. Atomicity means all or nothing. Consistency means the data satisfies its rules (keys, constraints) before and after. Isolation means concurrent transactions do not see each other's half-finished work. Durability means a committed change survives crashes. Almost every business application depends on this, which is why PostgreSQL, MySQL (InnoDB), SQL Server, Oracle and SQLite remain central after fifty years.
Seven lower ideas make it work. The relational model and SQL (L3, relmodel and sql) give tables, keys and a declarative language. Normalisation (L3, normalization) stores each fact once, so one update changes one place. B-tree indexes (L2, btree) find a row among a billion in about four page reads. MVCC (L2, mvcc) lets readers see a consistent snapshot without blocking writers. The write-ahead log (L2, wal) makes a commit durable with one sequential write. Two-phase commit (L2, twopc) extends atomicity across several shards or databases. On top of OLTP sit the database products (postgres, mysql, sqlite) and, for analytics, the neighbouring OLAP systems, which make the opposite trade.
terms: Transaction — a group of operations that succeed or fail together, between BEGIN and COMMIT or ROLLBACK.
ACID — atomicity, consistency, isolation, durability: the four guarantees of a transaction.
Isolation level — how much of other transactions' work you can see: read committed, repeatable read (snapshot) or serializable.
Write-ahead log (WAL) — an append-only file in which every change is recorded before the data pages are changed.
Buffer pool — the memory cache of table and index pages that the database manages itself.
Lock — a claim on a row or table that stops conflicting concurrent changes.
MVCC — multi-version concurrency control: keep several versions of a row so readers use an old snapshot while writers create new versions.
Hot row — a row that many transactions try to update, so they queue one after the other.
Deadlock — two transactions each wait for a lock held by the other; the database aborts one.
Group commit — flushing the log commit records of many transactions with one disk sync.
history: Online transaction processing began with reservation systems. SABRE, built by IBM and American Airlines in the early 1960s, let agents sell seats from terminals and was among the first large systems to do this. IBM's IMS (1968) and later CICS gave banks and airlines transaction monitors. In 1970 Edgar Codd proposed the relational model, and System R at IBM Research (1974–1979) proved that a declarative language (SQL) could be as efficient as hand-written access paths. Oracle (1979) and DB2 (1983) commercialised the idea.
The theory of transactions came from Jim Gray. His papers and the Tandem report "The Transaction Concept: Virtues and Limitations" (1981) set out the idea, and Theo Haerder and Andreas Reuter coined the acronym ACID in 1983. The ARIES recovery algorithm (Mohan et al., 1992) defined how a database uses the log to recover after a crash, and it is the basis of most engines. To compare systems, the Transaction Processing Performance Council was founded in 1988; TPC-A (1989) and the order-entry benchmark TPC-C (1992) measured OLTP for decades.
The open-source databases MySQL (1995) and PostgreSQL (1996) carried OLTP to the web, and InnoDB (Heikki Tuuri) became the default MySQL engine in 2010. Postgres added serializable snapshot isolation in version 9.1 (2011). Scale-out arrived with Google's Spanner (2012), which combined Paxos replication, two-phase commit and synchronised clocks to give global transactions, and then CockroachDB, TiDB and YugabyteDB. In the cloud, Amazon Aurora (announced in 2014; SIGMOD 2017 paper) moved the redo log into a distributed storage service, and newer systems (Neon, AlloyDB, and Databricks' Lakebase after its 2025 Neon acquisition) separate storage from compute in a Postgres-compatible form.
how: Follow one transaction through a typical engine such as PostgreSQL or InnoDB.
Arrival and planning. A client takes a connection (from a pool, since each connection costs memory and a process or thread). The SQL text is parsed, and the planner picks an access path using statistics: for a lookup by primary key it chooses the index. Plans for repeated statements are cached.
Finding rows. Tables and indexes are stored in fixed-size pages (8 KB in Postgres, 16 KB in InnoDB). A B+tree index has a high fan-out, since one page holds hundreds of keys. With a fan-out of about 300, three levels address 300³ = 27 million rows and four levels about 8 billion. The root and upper levels stay in the buffer pool, so a lookup usually costs zero or one disk read. A buffer pool hit ratio of 99% or more is normal for a well-sized OLTP database, which is why the working set must fit in memory. A row is returned in tens to hundreds of microseconds when it is cached.
Isolation by MVCC. In MVCC, an update does not overwrite the row in place for readers. Postgres writes a new row version, marked with the transaction IDs that created and deleted it, and InnoDB keeps old versions in an undo log. A transaction takes a snapshot, the set of transactions that were committed at that moment, and sees only the versions visible to it. Readers therefore do not block writers, and writers do not block readers. Two writers on the same row do conflict: the second waits for the first to commit (a row lock) and then either proceeds or fails, depending on the isolation level. Read committed takes a new snapshot for each statement. Repeatable read (snapshot isolation) keeps one snapshot for the whole transaction. Serializable adds detection of dangerous patterns (SSI in Postgres) or more locks (SQL Server, InnoDB) so that the result equals some one-after-another order. A deadlock detector aborts one victim when waits form a cycle.
Durability by WAL. A change is first made to the page in the buffer pool, and a redo record describing it is appended to the WAL buffer. The page is not written to disk yet. At COMMIT the database writes a commit record and forces the log to disk (fsync), and only then tells the client "committed". This is one sequential append, which is much cheaper than writing many scattered data pages. The dirty pages are written later in the background and at checkpoints. After a crash, recovery starts at the last checkpoint, replays the log to redo committed work and undoes unfinished transactions (ARIES). Group commit makes this efficient: while one fsync is in progress, other commits queue their records, and the next fsync covers all of them.
Consistency by schema. Constraints (primary key, unique, foreign key, not null, check) are enforced inside the transaction, and normalisation puts each fact in one place, so an invariant such as "every order line belongs to an order" holds at every commit. The database refuses a transaction that would break it.
Replication. The WAL is also the replication stream: replicas receive log records and replay them. Asynchronous replication has lag and can lose the last transactions at failover; synchronous replication waits for a replica to confirm before committing, which adds one network round trip (about 0.5 to 2 ms inside a region) and protects against loss.
Scale-out and two-phase commit. One machine can handle tens of thousands of simple transactions per second, and reads can be spread over replicas. Beyond this, data is sharded by a key. A transaction that touches two shards needs two-phase commit (twopc): the coordinator asks all shards to prepare (each forces a prepare record to its log and promises to commit), and then tells all to commit. This costs two log forces and two network round trips, and a failed coordinator can leave shards waiting. So well-designed sharding keeps most transactions within one shard, for example by sharding on customer ID.

example: Take a bank transfer of 100 from account A (balance 500) to account B (balance 200), run in one transaction:
BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 'A'; UPDATE accounts SET balance = balance + 100 WHERE id = 'B'; COMMIT;
Execution. The first UPDATE finds row A through the primary key B+tree (three page reads, probably all cached), takes a row lock on A, creates a new version with balance 400, and appends a redo record to the WAL. The second UPDATE does the same for B, giving 300. Both new versions are invisible to other transactions until commit, so a concurrent report reads 500 and 200 (a total of 700, correct). At COMMIT the log gets a commit record and is forced to disk. If the fsync takes 0.2 ms, the transaction is durable after about 0.2 ms plus a few tens of microseconds of CPU. The locks are released, and the new versions become visible together: atomicity.
Crash. Suppose the machine loses power after the commit record is on disk but before the data pages are flushed. After restart, recovery reads the log from the last checkpoint, sees the commit record for this transaction, and replays both changes: A is 400 and B is 300. If the crash had come before the commit record reached disk, recovery would find no commit record and would discard the work: neither account changes. Money is never lost or created.
Group commit and throughput. If every commit needed its own 0.2 ms fsync, one log could do at most 1 / 0.0002 = 5,000 commits per second. With group commit, 50 transactions share one fsync, so the ceiling is about 250,000 commits per second, and CPU becomes the limit instead. On cloud network disks an fsync may take 1 ms, so the single-commit ceiling is 1,000 per second and group commit matters even more.
Hot row. Now suppose every transaction also updates one row, "total_transferred", to keep a running total. Each transaction holds that row lock until it commits, about 1 ms including the log sync. The row can serve at most about 1,000 updates per second, however many cores you have, and others queue behind the lock. The fix is to avoid the shared counter: shard it into 16 rows and sum them when reading, or compute the total later from the transactions.
Lost update. Two sessions read A's balance (500) in separate transactions, compute 500 − 100 in application code and write 400. The second write overwrites the first: one withdrawal is lost, and the balance is 400 instead of 300. Avoid it with UPDATE balance = balance - 100 (the database does the read and the write under a lock), with SELECT ... FOR UPDATE, or with serializable isolation and a retry on conflict.
intuition: A busy cash register: many quick transactions, each of which must be exactly right, and each recorded in the receipt roll before the customer leaves.
The design follows from one constraint: correctness must not depend on luck. The log gives a single, ordered, durable truth, and everything else (pages, indexes, replicas) is a faster view of that truth which can be rebuilt from it. Versions let readers and writers pass each other without waiting. Constraints and normalisation make the rules of the business live in the database, where every program is forced to obey them.
mistakes: People often think ACID means a transaction cannot see anything wrong under any setting. In fact most databases default to read committed or repeatable read, not serializable, and anomalies such as lost updates, write skew and non-repeatable reads remain possible. Know your isolation level and design for it.
People often think a commit writes the data to the table files. In fact it writes only the log. The table pages are written later. Durability comes from the log reaching stable storage, which is why disk sync settings (fsync, synchronous_commit) matter so much for both safety and speed.
People often think adding more indexes always makes the database faster. In fact each index must be updated on every insert and update, makes writes slower and takes memory. Index what your frequent queries need, and drop unused indexes.
People often think NoSQL is needed for scale and OLTP databases do not scale. In fact one well-tuned relational server handles tens of thousands of transactions per second and terabytes of data, and replicas scale reads. Sharding is needed much later than people think, and it complicates transactions.
People often think a long-running transaction is harmless if it only reads. In fact an open transaction pins old row versions, so the database cannot clean them (vacuum in Postgres, purge in InnoDB), tables and indexes bloat, and replicas may be delayed.
friction: Scaling writes beyond one machine is the hard limit. Replicas multiply reads, but all writes go through one primary. Sharding splits the writes, but then cross-shard transactions need two-phase commit, which costs latency and can block, and joins and secondary indexes across shards become expensive. Distributed SQL systems hide this but pay in commit latency (cross-region round trips of tens to hundreds of milliseconds).
Contention is the second limit. Hot rows, hot index pages (an auto-increment key where all inserts hit the last page) and long transactions turn a fast database into a queue. Anomalies are the third: isolation levels are subtle, retries are required on serialisation failures and deadlocks, and many applications have latent bugs that appear only under load.
Operations are heavy: schema changes on large tables can lock them for a long time, connection counts are limited (each connection costs MBs of memory), failover can lose or duplicate work, and vacuum and bloat need care in Postgres. Analytics on OLTP databases is the last friction. A long scan hurts latency for customers through cache pollution, I/O and held versions, which led to replicas, change-data-capture to a warehouse or lakehouse, and HTAP systems.
practice: Keep transactions short and few: do no network calls or user waits inside a transaction, and touch as few rows as you can, in a consistent order to reduce deadlocks. Retry on deadlock and serialisation errors with a limit and backoff. Use the database to enforce rules: primary and unique keys, foreign keys, check constraints. Do atomic updates in SQL (balance = balance - 100) instead of read-modify-write in the application.
Design indexes from the actual queries. Put the equality columns first in a composite index, use covering indexes for hot reads, and check plans with EXPLAIN. Avoid hot spots: sequences that put all inserts on one page may need random or time-bucketed keys, and counters should be sharded. Use a connection pool (PgBouncer or the application's pool) with a size close to the number of cores times a small factor, since too many active connections reduce throughput.
Size memory so the working set fits in the buffer pool, put the WAL on a fast, durable device, and keep synchronous_commit on for data you cannot lose. Monitor lock waits, replication lag, long transactions, dead tuples and cache hit rate. Take backups with point-in-time recovery from the WAL, and test restores. Move analytics off the primary with read replicas or change data capture into a warehouse or lakehouse, and use online schema change tools for big tables. Plan sharding on a key that keeps most transactions inside one shard.
tradeoffs: Choose a single relational primary with replicas when your data fits one machine's disk and memory budget (up to several TB) and writes are below tens of thousands per second. You get full ACID, simple operations, and rich SQL. You give up unlimited write scale and have a single failure domain for writes, which replicas and automatic failover only partly address.
Choose sharding (Vitess, Citus, application-level) when write throughput or data size exceeds one node and most transactions touch one key's data. You give up cross-shard joins and cheap transactions, and you take on resharding work. Choose distributed SQL (Spanner, CockroachDB, TiDB) when you need horizontal scale with transactions and multi-region availability, and can pay commit latency in the tens of milliseconds and the cost of more nodes.
Choose snapshot isolation (repeatable read) when you want good concurrency and can reason about write skew, using explicit locks for the few critical paths. Choose serializable when correctness is subtle and the code is hard to analyse; you pay in retries and some throughput, but you get simpler reasoning.
Choose synchronous replication when losing a committed transaction is unacceptable (payments), accepting extra commit latency and reduced availability if replicas fail. Choose asynchronous replication when low latency matters more and a few seconds of loss at failover is acceptable.
Choose normalised schemas for the system of record, to keep facts consistent. Choose selective denormalisation (copied columns, summary tables) for hot reads when a join is a measured bottleneck, and accept the work of keeping copies correct. Choose a key-value or document store instead of OLTP SQL when access is only by key at very high scale and you can live without joins and multi-row transactions.
interview: Explain what happens, step by step, when a transaction commits, and why it is durable. || Changes are applied to pages in memory and described by redo records in the write-ahead log. At commit, the commit record is appended and the log is flushed to stable storage with fsync, then the client is acknowledged. Data pages are written later. After a crash, recovery replays the log from the last checkpoint, redoing committed work and discarding uncommitted work.
How does MVCC let readers and writers work without blocking each other, and what does it cost? || Writers create new versions of rows, and readers use a snapshot that sees only versions committed at snapshot time. No read locks are needed. The cost is extra storage for old versions, cleanup work (vacuum, purge), bloat when long transactions pin old versions, and the need to resolve write-write conflicts.
Two requests withdraw from the same account at the same time and the balance is wrong. What happened and how do you fix it? || A lost update from read-modify-write in application code under read committed or snapshot isolation: both read the same balance, and one write overwrote the other. Fix with an atomic UPDATE balance = balance - x with a check, SELECT FOR UPDATE, a version column with optimistic retry, or serializable isolation with retries.
Your primary Postgres is at 80% CPU and writes are growing 3x a year. What are your options? || First tune: queries, indexes, connection pooling, batching, and move reads and reporting to replicas. Then vertical scale, then partitioning of hot tables, and caching. Next, shard by tenant or customer key (Citus, Vitess) or move to distributed SQL. Check for hot rows and unnecessary writes before adding hardware.
Why is two-phase commit avoided in high-scale designs, and what do you do instead? || It needs two log forces and two round trips per transaction, holds locks across the network, and blocks if the coordinator fails. Designers choose a sharding key that keeps transactions local, or use sagas, outbox and idempotent steps for cross-service workflows, accepting eventual consistency.
How would you do analytics without hurting the OLTP database? || Use read replicas for light reports, change data capture into a warehouse or lakehouse for heavy analysis, and HTAP engines when freshness within seconds is essential. Set limits (statement timeout, resource groups) on replicas so reports cannot hold back vacuum or replication.
quiz: What do the four letters of ACID stand for? || Atomicity, consistency, isolation and durability: all-or-nothing, rules preserved, concurrent transactions do not interfere, and committed data survives crashes.
Why does a commit only need to write the log and not the data pages? || The log contains enough information to redo the change after a crash. One sequential log write is cheap and durable, while the scattered data page writes can happen later in the background.
Why do readers not block writers under MVCC? || Writers create new versions of rows. Readers use a snapshot of committed versions, so they read old versions and need no lock that a writer would conflict with.
An fsync takes 0.5 ms. What is the commit rate ceiling without group commit, and with 25 commits per fsync? || Without it, 1 / 0.0005 = 2,000 commits per second. With 25 per fsync, about 50,000 commits per second.
When would you choose serializable isolation over snapshot isolation? || When the correctness rules involve several rows and write skew is possible (for example "at least one doctor on call"), and you prefer to let the database detect conflicts and retry rather than add explicit locks. The cost is more aborts and some throughput.

@@ htap
value: HTAP stands for hybrid transactional/analytical processing. An HTAP database accepts the small, fast writes of an OLTP system and also answers large analytical queries about the same data, a few seconds after the data was written, without a separate warehouse and without a pipeline in between.
The usual setup has two systems. Orders and payments go into an OLTP database. A pipeline (nightly batch, or change data capture) copies them to a warehouse or lakehouse, where analysts query them. This works, but it has costs: the analytical copy is minutes to hours old, the pipeline can break or drift out of sync, you pay to store and operate two systems, and numbers in the application can differ from numbers in the dashboard. Some questions cannot wait for the pipeline: Is this card payment fraudulent given everything this card did in the last ten minutes? Which products are about to go out of stock? What is the live revenue by region right now? An HTAP system answers these where the data is written.
Two lower ideas make this possible. Columnar storage (L2, columnar) gives analytics what it needs: a scan of a few columns over millions of rows at memory speed. It does not suit transactions, so HTAP keeps a column-oriented copy of the data next to the row-oriented store that transactions use. MVCC (L2, mvcc) provides one timeline for both: every transaction commits at a version, and an analytical query reads a snapshot at some version, so the row and column copies can be read consistently at the same logical time, without locks that would stop writers. At the product level, TiDB with TiFlash, MySQL HeatWave, SingleStore, SAP HANA, Oracle Database In-Memory and SQL Server columnstore are all HTAP designs, with different ways of keeping the two layouts together.
terms: Row store — data stored row by row, so one whole record is read or written with one access; good for OLTP.
Column store — data stored column by column, so a query reads only the columns it needs and compresses well; good for OLAP.
Delta store (delta/main) — a small, write-friendly area that collects recent changes; it is merged periodically into the large read-optimised main store.
Columnar replica — a copy of a table in column format, kept up to date from the transaction log of the row store.
Learner (Raft) — a replica that receives the log but does not vote in elections, so it cannot slow down commits.
Freshness (staleness) — how old the data seen by an analytical query is compared with the latest commit.
Resource isolation — keeping analytical work from using the CPU, memory bandwidth, cache and I/O that transactions need.
Snapshot — a consistent view of the database as of one point in the commit order.
Workload-aware optimiser — a query planner that chooses between the row store and column store for each table in a query.
history: The idea that one system could do both is old, but for decades hardware made it impractical, and OLTP and OLAP were separated in the 1990s (see the warehouse). In 2009 Hasso Plattner of SAP argued in a SIGMOD paper that a single in-memory column database could serve both kinds of work, since memory had become large and cheap, and SAP HANA (announced in 2010) was built on this. Oracle Database In-Memory (2014) added an in-memory column copy of tables next to the row format, and SQL Server added updatable columnstore indexes (2012–2014) and real-time operational analytics (2016).
Research showed how to separate the two workloads without copies of the whole machine. The HyPer system (Kemper and Neumann, ICDE 2011) used the operating system's fork call: an analytical query ran in a forked child process that saw a virtual-memory snapshot of the database, copied lazily, while the parent kept running transactions. The CH-benCHmark (Cole et al., 2011) combined TPC-C transactions with TPC-H-like queries on the same data to measure such systems.
The name was introduced by Gartner in 2014 (Pezzini and colleagues). From about 2015 a new family appeared that keeps a distributed row store and adds a replicated column store: TiDB with TiFlash (the VLDB 2020 paper, "TiDB: A Raft-based HTAP Database"), MemSQL (renamed SingleStore in 2020) with its universal storage that combines row and column formats, MySQL HeatWave (announced 2020), and Google AlloyDB with a columnar engine (2022). Surveys (Özcan et al., SIGMOD 2017; Li and Zhang, SIGMOD 2022 tutorial) classify the designs. Cloud vendors also offer "zero-ETL" links from OLTP to the warehouse, which shorten the pipeline but still keep two systems.
how: There are three ways to build an HTAP system, and each answers the same two questions: where does the column copy live, and how does it stay consistent with the row data?
Design 1: one engine, two formats in the same node. In SAP HANA the main store is columnar and compressed, and writes go to a small delta store, which is row-like and fast to append. A query reads main plus delta and applies MVCC visibility to the rows. When the delta grows past a threshold, a background merge creates a new main. SingleStore works in a similar way, with an in-memory row store as the write buffer and a columnar store of immutable segments, merged in the background. Oracle In-Memory keeps the normal row format on disk and buffer cache, adds an in-memory columnar copy of chosen tables, and marks changed rows in a side journal so that queries correct for them. SQL Server keeps a clustered columnstore with a delta rowstore for fresh rows.
Design 2: a row store and a separate columnar replica fed by the log. In TiDB, data is stored in TiKV, a distributed row store using multiple Raft groups, each holding a range of rows ("region"). TiFlash nodes join each region's Raft group as learners: they receive the same replicated log but do not vote, so they cannot slow down a commit. The log entries are converted into columns and stored in a delta layer and a stable layer. A read on TiFlash first asks the region leader for its current commit position (a read index) and waits until the replica has applied the log up to it, so the answer is a consistent snapshot at that moment, as fresh as the leader; the price is waiting time when the replica lags. The optimiser can choose per table, and per query, between TiKV and TiFlash, or use both in a single plan, for example a point lookup from TiKV joined to a big aggregation from TiFlash. Because TiFlash runs on other machines, a heavy query takes CPU and I/O from the analytical nodes, not from the transactional nodes. MySQL HeatWave follows the same idea with a different mechanism: InnoDB stays the source of truth, and changes are streamed to a separate in-memory columnar cluster, which executes the heavy parts of eligible queries.
Design 3: snapshots from the operating system. HyPer lets the transaction engine run in the main process, and each analytical query forks a child with a copy-on-write snapshot. Only pages that transactions modify are copied. This gives snapshot consistency without versions in the table, but it ties both workloads to one machine's memory.
The role of MVCC. In every design, a consistent read needs a version. Each transaction gets a commit timestamp (or log position). The analytical query picks a read timestamp and sees every change with a smaller timestamp and none with a larger one. The row store and the column store use the same number, so a query that joins both sees one world. If the column copy is behind the read timestamp, the system either waits (TiFlash), applies a correction from the log or delta (Oracle, HANA), or reads the row store for the missing rows.
The role of columnar storage. In the column copy, a query scanning 3 of 40 columns reads about 7% of the bytes, compresses them (often 4 times or more), skips blocks by min/max statistics and uses vectorised execution. That gives the 10 to 100 times speedup that makes analytics practical, and the row store could not offer it.
Resource isolation. HTAP only works if analytics do not hurt transactions. The main tools are separate nodes for the columnar replica (TiFlash, HeatWave), resource groups with CPU and memory limits, admission control, and routing heavy queries to followers. Without them, a scan on the same cores and memory bus as the transactions can raise OLTP tail latency severalfold.

example: An online shop has an orders table with 500 million rows, 300 bytes per row (150 GB), and 40 columns. The application inserts about 5,000 orders per second at peak. Two reads matter. The fraud check, at order time, needs this card's orders in the last ten minutes: an index lookup returning about 5 rows, 1 to 2 ms. The business dashboard needs revenue by category by hour for the last 24 hours. At the peak rate that would be 5,000 × 86,400 = 432 million rows, but the average day is lower, say 100 million rows, and the query needs only 3 of the 40 columns.
Separate warehouse. A pipeline copies new rows every 15 minutes. The dashboard is up to 15 minutes old, plus load time. The fraud check cannot use the warehouse. Two systems must be run, and totals sometimes disagree after pipeline failures.
Row store only. The dashboard query on the OLTP database scans 100 million rows × 300 bytes = 30 GB of pages, evicts hot pages from the buffer pool and competes for I/O. Transaction latency, which was 5 ms at the 99th percentile, may rise to 40 ms during the scan. This is the reason for the split in the first place.
HTAP with a columnar replica on separate nodes. The same 100 million rows, 3 columns of 16 bytes in total, are 1.6 GB raw, and about 400 MB after 4 times compression. With zone maps on the order time the engine reads only the last day. Eight analytical nodes scan this in well under a second. The row store is not touched, so the fraud check stays at 1 to 2 ms. The data is seconds old, because the replica applies the log continuously, and a consistent read waits for the replica to catch up to the leader's position, typically a small fraction of a second.
Delta and merge arithmetic (for a delta/main design). Inserts add 5,000 rows per second to the delta store. If the delta is merged when it holds 5 million rows, a merge occurs every 5,000,000 / 5,000 = 1,000 seconds, about 17 minutes. Reading the delta costs 5 million rows × 16 bytes = 80 MB per query, small compared with the main store. If merges fell behind and the delta grew to 500 million rows, every query would scan 8 GB of unsorted, poorly compressed delta, and analytical speed would collapse. Tuning merge frequency is therefore a core operational task.
The copy does not disappear. Note what HTAP does and does not save: the column copy still takes storage, here about 38 GB if all 40 columns are copied and compressed 4 times (150 GB / 4). It is created, updated and kept consistent by the system automatically.
intuition: One set of facts, shelved in two ways: by record for the people at the till, and by category for the people counting stock.
The design is natural because transactions and analytics differ in layout, not in facts. A row layout is fastest to write a whole record; a column layout is fastest to read one attribute across millions of records. Rather than argue about one layout, keep both and let one source of truth, the commit log with its version numbers, update them. The log is the thread that ties the two copies, and the version number tells a reader exactly which moment it sees.
mistakes: People often think HTAP removes the need for a data warehouse or lakehouse. In fact it removes the pipeline for fresh, moderate-size analysis on operational data. A warehouse still serves years of history, data from many sources, heavy batch jobs, machine learning and cheap storage.
People often think HTAP means no copy of the data. In fact most designs keep a second, columnar copy. What changes is that the system maintains it and offers consistent reads across both copies.
People often think that because the data is in one system, analytics cannot slow down transactions. In fact if both run on the same CPU, memory bandwidth, cache and disk, they interfere strongly. Good HTAP isolates analytics on separate nodes or resource groups, and you must test it under a mixed load.
People often think the column copy is always up to date. In fact freshness depends on the design: some wait for the log to be applied to give a fully consistent read, some allow bounded staleness, and a busy or failing replica can lag. Measure freshness; do not assume it.
People often think HTAP is just a marketing word for "a database with an analytic add-on". In fact the hard part is real: a shared timeline of versions across two storage formats, an optimiser that picks the right format, and resource isolation. The weaker products differ a lot in how much of this they really provide.
friction: Interference is the first problem. Even with separate nodes, the log shipping, columnar conversion and merging cost CPU and network, and a very busy write load can make the columnar replica lag. On a single node, analytic scans compete with transactions for cache and memory bandwidth, and benchmarks that show HTAP success usually use modest analytic load.
The second problem is cost. Two layouts mean extra storage and extra memory (many designs hold the column copy in RAM, which is expensive), and extra nodes for the column side. Compared with a warehouse on object storage, HTAP storage is expensive for long history, so most systems apply HTAP only to recent or hot tables.
Third, the optimiser and the workload are hard. Choosing the format per table, estimating costs across two engines, and avoiding plans that read a huge delta need good statistics. Analytical queries need large joins and shuffles, and HTAP systems from the OLTP side have less mature distributed execution than warehouses. Fourth, features can lag: not all SQL, data types or indexes work on the column copy, and schema changes must be applied to both.
Finally, it is a young and uneven field. The products differ a lot in guarantees (consistent reads or bounded staleness), in what they scale to, and in lock-in. Many organisations judge that a clean pipeline into a lakehouse is simpler and cheaper to operate, and use HTAP only for the specific low-latency paths that need it.
practice: Define freshness and scale first. If the analytic question must see data within seconds of commit, and the data involved is a recent window of gigabytes to a few terabytes, HTAP is a good fit; if it needs years of history, many sources or heavy transformations, use a lakehouse or warehouse fed by change data capture, and keep the OLTP system lean.
Check isolation. Run a mixed benchmark with your real queries and your real write rate, and watch the p99 latency of transactions while analytics run. Prefer designs that place the column copy on separate nodes, or use resource groups with hard limits. Set statement timeouts and memory limits for analytic users.
Choose which tables get a column copy. Replicate only the tables the analytic queries need (in TiDB you set the number of TiFlash replicas per table; in HeatWave you load chosen tables into the cluster), and watch memory use. Measure replication lag or the time of the consistent-read wait, and alert on it. Keep schema changes in a tested order so that both copies stay in step.
Use the optimiser's hints sparingly and check query plans: confirm that the analytical queries run on the column engine and the point lookups on the row engine. Keep an exit route: store your data in standard SQL tables, and keep the ability to feed a lakehouse for the long history, since HTAP products differ and migrations are hard.
tradeoffs: Choose HTAP when you need analytics on fresh operational data within seconds, the data window is moderate, and you want one SQL interface and consistent numbers (fraud checks, live dashboards, operational reporting inside an application). You give up some cost efficiency, a mature ecosystem of BI and ML tools, and some freedom to choose engines.
Choose OLTP plus CDC into a lakehouse or warehouse when freshness of minutes is acceptable, analytic work is heavy or involves many sources, and you need long history and cheap storage. You give up second-level freshness and take on a pipeline, but each system does one job well and can scale and fail on its own.
Choose a separate columnar replica on other nodes (TiFlash, HeatWave) when isolation of transactional latency is the priority; you pay for extra nodes and replication traffic. Choose a same-node dual format (Oracle In-Memory, SQL Server columnstore) when the analytic load is light, you want no extra hardware, and the data fits in memory; you risk interference and are limited by one machine.
Choose strict consistent reads on the column copy when results must match the row store exactly (financial views), accepting waits when the replica lags. Choose bounded staleness (a few seconds old) when latency and throughput of analytics matter more than the very last transaction.
Choose a pure OLAP engine fed by streaming (Pinot, ClickHouse, Druid) when you need sub-second analytical queries at very high rates on append-only events and do not need transactional updates. You give up updates, joins on mutable data and a single system of record.
interview: Why can't an OLTP row store simply run analytics well, and what does HTAP add? || Row layout reads whole records, so a scan of 3 columns reads all 40, with no compression or vectorisation, and it competes with transactions for cache and I/O. HTAP adds a column-oriented copy, kept in sync from the transaction log with version numbers for consistent reads, plus an optimiser to route queries and isolation of resources.
How does TiDB give a consistent read on TiFlash if the replica is asynchronous? || TiFlash is a Raft learner that receives the log. For a read, it asks the region leader for the current read index and waits until it has applied the log up to that index, then reads a snapshot at the read timestamp. The result is consistent and as fresh as the leader, at the price of extra waiting when the replica lags.
Explain a delta/main design and its main operational risk. || Writes go to a small write-optimised delta, reads combine main and delta, and a background merge folds the delta into the compressed main. If merges fall behind, the delta grows and every query scans a large, unsorted, poorly compressed region, so analytic latency rises sharply. You monitor delta size and merge duration.
How would you test whether an HTAP database fits your workload? || Replay real traffic: your write rate and your analytic queries together, then measure transaction p99 latency, analytic latency, freshness (commit to visible on the column side), and resource use. Use the CH-benCHmark as a baseline, but trust your own workload. Test failure cases such as replica lag and node loss.
When would you refuse to use HTAP and use a lakehouse with CDC? || When analytics need long history, many sources, heavy batch transformation or machine learning, when minute-level freshness is enough, or when cost matters most. Then CDC into a lakehouse isolates the OLTP system completely and uses cheap object storage.
What problem does MVCC solve in an HTAP system that locking would not? || Long analytical scans would hold locks and block writers, or be blocked by them. With MVCC the scan reads a snapshot at a timestamp and does not take locks, and the same timestamp is valid on both the row and the column copy, so a query that touches both sees consistent data.
quiz: What does HTAP stand for, and what two workloads does it combine? || Hybrid transactional/analytical processing. It combines OLTP (small, fast, correct reads and writes) and OLAP (large scans and aggregations) on the same data.
Why does a columnar copy make analytics faster? || Queries read only needed columns, similar values compress well, min/max statistics skip blocks, and vectorised execution processes many values per instruction.
How does a Raft learner help isolate analytics from transactions? || It receives the replicated log but does not vote, so commits do not wait for it, and it runs on separate machines, so scans do not use the transactional nodes' CPU or I/O.
A delta store receives 2,000 rows per second and is merged every 4 million rows. How often is the merge, and how large is the delta scan at 16 bytes per row? || 4,000,000 / 2,000 = 2,000 seconds, about 33 minutes. A full delta of 4 million rows × 16 B is 64 MB per scan.
When is a pipeline to a lakehouse a better choice than HTAP? || When analytics need long history or many sources, when freshness of minutes is acceptable, when workloads are heavy, or when cost per terabyte is the main concern.

value: Web architecture is the way a web application is put together from a browser, a network path and a set of servers. A user types an address or taps a link; the browser finds the server, opens a secure connection, sends an HTTP request, and receives HTML, JSON or a stream back; then it draws the page and runs code. Behind the server there is usually a chain of machines: a content delivery network (CDN), a load balancer, a reverse proxy, application servers, caches and databases. It is the most widely used distributed system in the world, and every web product, from a news site to an ad-serving endpoint, sits on this shape.
The architecture exists to solve a handful of problems at once. Many users must be served by many machines, so servers are made stateless and put behind load balancers. Distance costs time, since light in fibre needs about 1 ms for each 100 km of round trip, so content is cached close to users. Pages are shown on devices of very different power, so work is split between server and client. And the network is hostile, so everything is encrypted and checked. Each of these choices is a trade-off between latency, cost, freshness and complexity, and web architecture is the art of choosing them for a given product.
Eight lower concepts do the work. HTTP (L3, http) defines requests, methods, status codes, headers and caching rules. DNS (L3, dns) turns names into addresses and can steer a user to a nearby server. TLS (L3, tls) encrypts the connection and proves the server's identity. The layered network model (L3, osi) explains that an HTTP message rides on TCP or QUIC, on IP, on links, so each layer adds its own round trips. Unicode and UTF-8 (L3, unicode) let one page carry any language. The event loop (L2, eventloop) lets one server thread serve thousands of connections, as NGINX and Node.js do. Cache eviction (L2, eviction) decides what stays in the browser, CDN and server caches. Virtual DOM diffing (L2, virtualdom) lets UI libraries update only the changed parts of a page. At the top, NGINX, FastAPI, the browser and React are the pieces you actually run.
terms: Client–server — the browser (client) asks, the server answers; the server does not start the conversation.
Stateless — the server keeps no memory of earlier requests; each request carries all that is needed (a cookie or token).
Reverse proxy / load balancer — a server in front of the application servers that terminates TLS, spreads requests and can cache.
CDN — a worldwide network of caching servers (edge nodes) that answer from a place near the user.
SSR / CSR / SSG — server-side rendering builds HTML on the server for each request; client-side rendering builds it in the browser with JavaScript; static site generation builds it at deploy time.
Hydration — attaching JavaScript behaviour to HTML that the server already sent.
REST — an API style where resources have URLs and are handled with standard HTTP methods, statelessly and cacheably.
Cache-Control / ETag — HTTP headers that say how long a response may be reused and how to check if it is still valid.
Round trip (RTT) — the time for a message to reach the other side and a reply to come back; the basic unit of web latency.
Core Web Vitals — Google's measures of page experience: loading (LCP), responsiveness (INP) and layout stability (CLS).
history: Tim Berners-Lee proposed the web at CERN in March 1989 and, with Robert Cailliau, built the first browser and server in 1990. HTTP/0.9, HTML and URLs were public by 1991. Mosaic (1993) and Netscape (1994) brought graphics and the public; Apache (1995) became the standard server. The early web was simple: a browser asks for a file, the server returns it. Dynamic pages followed (CGI, then PHP), and the LAMP stack (Linux, Apache, MySQL, PHP) powered the first generation of sites. HTTP/1.1 (1997) added persistent connections and virtual hosting.
Scale and interactivity changed the design. Dan Kegel's "C10K problem" (1999) asked how a server could serve ten thousand connections, which led to event-driven servers: NGINX (2004) and Node.js (2009). The term AJAX (2005, after Google Maps and Gmail) described pages that fetch data in the background, and single-page applications grew from it. Roy Fielding's PhD thesis (2000) described REST as the style that made the web scale; GraphQL was open-sourced in 2015. React (2013) brought the virtual DOM and component model, and Next.js (2016) brought back server-side rendering as a framework feature. React Server Components became stable with React 19 at the end of 2024.
The transport was rebuilt too. HTTP/2 (2015) added multiplexing of many requests over one connection. TLS 1.3 (RFC 8446, 2018) cut the handshake to one round trip. QUIC (RFC 9000, 2021) moved transport to UDP with built-in encryption, and HTTP/3 (RFC 9114, 2022) runs on it. CDNs (Akamai from 1998, then Cloudflare, Fastly and the cloud providers) moved from caching images to running code at the edge.
how: Follow one page view from the click to the pixels.
Step 1, cache check and DNS. The browser first looks in its own HTTP cache. A stored response with a valid Cache-Control: max-age is used with no network at all. If it is stale but has an ETag, the browser sends a conditional request, and the server can answer 304 Not Modified with no body. Otherwise, the browser resolves the hostname (dns): its resolver asks a recursive resolver, which answers from cache or walks from the root servers to the authoritative servers. An uncached lookup takes roughly 20 to 100 ms; a cached one almost nothing, and the record's TTL controls how long answers live. Large sites make DNS or anycast routing return the address of a nearby edge.
Step 2, connection. TCP needs one round trip (SYN, SYN-ACK, ACK). TLS 1.3 needs one more, in which the server proves its identity with a certificate and both sides derive session keys; resumed connections can send data at once (0-RTT). With HTTP/3, QUIC combines transport and TLS in a single round trip. The browser reuses one connection for many requests. The network layers (osi) mean that each of these steps is a conversation across several routers, and the speed of light sets a floor: Bengaluru to a data centre in Virginia is about 13,000 km, so a round trip cannot be less than roughly 130 ms and is typically 200 to 250 ms.
Step 3, edge, load balancer and proxy. The request reaches the CDN edge. If the object is cached (static files, images, even API responses with Cache-Control headers), the edge answers in a few milliseconds. Otherwise, it goes to the origin over a warm connection. At the origin a load balancer picks a healthy server (round robin, least connections). A reverse proxy such as NGINX terminates TLS, compresses responses, serves static files and forwards dynamic requests. NGINX uses an event loop (eventloop): a few worker processes wait on thousands of sockets with epoll, and never block on a slow client, so one machine can hold tens of thousands of idle connections.
Step 4, the application. A stateless application server (FastAPI, Express, Spring) parses the request, checks the session cookie or token, and calls other services: first a cache (Redis or Memcached, with an eviction policy such as LRU to bound memory), then the database. It returns HTML, JSON or a stream. Because the server keeps no state in memory between requests, any server can handle any request, and capacity grows by adding servers. State lives in the database, in a shared cache, or in the client (a cookie holding a session ID, or a signed token).
Step 5, the browser draws. The browser parses HTML into the DOM and CSS into the CSSOM, combines them into a render tree, computes layout and paints. JavaScript can block the parser unless it is marked async or defer. The preload scanner reads ahead to find CSS, scripts and images early. The text is decoded as UTF-8 (unicode), declared in the Content-Type header, which is ASCII-compatible and handles every script. Largest Contentful Paint is the moment the main content appears.
Step 6, where rendering happens. In server-side rendering the server sends complete HTML, so the user sees content after the first response; JavaScript then hydrates it. In client-side rendering the server sends a small HTML shell and a JavaScript bundle; the browser runs it, calls an API, and builds the page, so content waits for more round trips and device CPU. Static generation builds HTML at deploy time and serves it from the CDN. Modern frameworks mix these per route, stream HTML in chunks, and use server components to keep code on the server. On updates, UI libraries keep a virtual DOM, a tree of plain objects: after a state change they build a new tree, compare it with the old one with a fast heuristic algorithm, and apply only the differences to the real DOM, because touching the real DOM triggers expensive layout.
Step 7, further requests and security. The page triggers more requests for scripts, styles, images and API calls, which HTTP/2 or HTTP/3 multiplexes on one connection. The browser enforces the same-origin policy: scripts from one site cannot read another site's responses unless the server allows it with CORS headers. Servers defend against cross-site scripting (escaping output, Content-Security-Policy) and request forgery (SameSite cookies, tokens), and use HTTPS everywhere with HSTS.
Step 8, API style. REST treats everything as a resource with a URL and uses GET (safe, cacheable), PUT and DELETE (idempotent) and POST (not idempotent). Statelessness and cacheability follow Fielding's constraints. GraphQL lets the client ask for exactly the fields it needs in one request, gRPC suits internal service calls, and WebSockets or server-sent events carry push updates.

example: A shopper in Bengaluru opens a product page. The origin is in Virginia, round trip 220 ms. A CDN edge in Mumbai has a round trip of 20 ms to the shopper and is connected to the origin over a warm connection. The server needs 100 ms to build the page. The shopper uses a mid-range phone on a 10 Mbit/s connection.
Without a CDN, with server-side rendering. TCP: 1 RTT = 220 ms. TLS 1.3: 1 RTT = 220 ms. Request and first byte: 1 RTT + 100 ms server time = 320 ms. Total to the first byte of HTML: 760 ms. Then the HTML refers to a CSS file and a script: with HTTP/2 on the same connection they come in one more round trip, 220 ms plus transfer. Content appears at about 1.0 to 1.2 seconds. Most of this is distance, not computation: 4 round trips × 220 ms = 880 ms of waiting.
With a CDN edge and cached assets. TCP + TLS to the edge: 2 × 20 = 40 ms. The HTML is dynamic, so the edge forwards it to the origin: 20 ms for the request and reply between the shopper and the edge, 220 ms on the warm connection to the origin, and 100 ms server time, so about 340 ms. With 40 ms for the handshake this gives about 380 ms. The CSS and JavaScript come from the edge cache in 20 ms. The page shows content at about 420 to 450 ms. The handshake cost fell from 440 ms to 40 ms, and the static files cost almost nothing. If the HTML is also cacheable for 60 seconds (for example a product page that changes rarely), the edge answers in about 5 ms and the first byte comes after about 40 + 20 + 5 = 65 ms.
Client-side rendering instead. The HTML shell arrives quickly (it is static). The browser then downloads a 300 KB (gzipped) JavaScript bundle: at 10 Mbit/s that is 300 × 8 / 10,000 = 0.24 s of transfer alone. Parsing and running the bundle on a mid-range phone can take hundreds of milliseconds more. Only then does the code call the API for product data (one more round trip, 220 ms to the origin plus 100 ms server time) and draw the page. The chain is shell → script → API → render. The shopper sees a blank or skeleton page for about 1 to 1.5 seconds longer than with server-side rendering. This is the reason many frameworks render the first view on the server and hydrate afterwards.
Scale check. The product page is requested 5,000 times per second. If the HTML is cached at the edge for 60 seconds, the origin sees about one request per edge location per minute (say 200 locations: about 3 requests per second), not 5,000. The origin's load is reduced by a factor of more than 1,000, which is the main reason that CDNs exist. The price is that a price change can appear up to 60 seconds late unless the edge cache is purged.
intuition: Every page is a conversation of short requests and answers, and the best conversations are the ones that are answered by someone nearby.
The design follows the physics and the economics. Distance cannot be reduced, only avoided: so the answers are copied close to users, and the number of round trips is cut by reusing connections and combining handshakes. Servers are kept free of memory about users so that any machine can answer, which makes growth a matter of adding machines. Standard methods, headers and status codes mean that proxies, caches and browsers made by different people can all do the right thing without knowing the application.
mistakes: People often think a fast server means a fast website. In fact for most users the time is dominated by network round trips and by work in the browser. A server that answers in 20 ms is still slow if the page needs six sequential round trips to a far-away origin, or 2 MB of JavaScript to run.
People often think stateless means no state. In fact the application still has state; it is just stored somewhere that all servers can reach (a database, a cache) or sent by the client in each request (a cookie or token). Stateless servers can be added or removed freely, which is why it matters.
People often think a single-page application is always better because it feels modern. In fact client-side rendering delays first content, depends on device power, and is harder for search engines and for slow networks. It is right for highly interactive tools behind a login, and often wrong for content pages.
People often think HTTPS is only a security feature with a speed cost. In fact with TLS 1.3 and session resumption the extra cost is small, and HTTP/2 and HTTP/3, which browsers use only over HTTPS, usually make pages faster than plain HTTP/1.1.
People often think caching is simple. In fact the hard part is invalidation and correctness: serving personalised content from a shared cache, forgetting the Vary header, or caching an error page can show one user's data to another or keep a bug alive for hours. Use cache keys, short TTLs, and versioned file names for static assets.
friction: Latency is the first limit, because round trips add up and you cannot beat the speed of light. Every redirect, every sequential dependency (HTML, then script, then API call) and every third-party script costs more. The second limit is the browser itself: the main thread is single-threaded, so large JavaScript bundles delay interaction, and a mid-range phone is five to ten times slower than a laptop. Core Web Vitals make this visible: a good experience is Largest Contentful Paint within 2.5 seconds, Interaction to Next Paint within 200 ms and Cumulative Layout Shift below 0.1.
State and consistency are the third. Stateless servers push state to shared stores, caches create stale data, and several tabs and devices see different versions. Security is the fourth: XSS, CSRF, injection, misconfigured CORS, leaked tokens and supply-chain attacks through npm packages are the usual causes of breaches, and the browser is an untrusted environment. Fifth, the stack changes fast: frameworks, rendering models and build tools change every few years, and server components, edge runtimes and streaming add complexity and lock-in. Finally, observability is hard because one page view crosses a browser, a CDN, several services and databases, and needs tracing with a shared request ID and real-user monitoring to see what users actually experience.
practice: Start from the user's critical path and count round trips. Use HTTP/2 or HTTP/3 and TLS 1.3, keep connections warm, put static assets on a CDN with long cache lifetimes and content-hashed file names, compress with Brotli or gzip, and size images properly. Reduce redirects and third-party scripts. Send the first content from the server (server rendering, static generation or streaming) and load JavaScript only for what the page needs.
Make application servers stateless and put them behind a load balancer with health checks. Keep sessions in a signed cookie or a shared store, and use timeouts, retries with backoff and circuit breakers for calls to other services. Cache at several levels with explicit Cache-Control headers, use stale-while-revalidate for content that may be a little old, and plan invalidation before you cache. Design APIs around resources, use correct status codes, make PUT and DELETE idempotent, support idempotency keys for POST, version the API, and paginate lists.
Secure by default: HTTPS and HSTS, cookies with Secure, HttpOnly and SameSite, a Content-Security-Policy, output escaping, input validation, rate limits, and dependency scanning. Measure real users (Core Web Vitals from the field, not only lab tests), trace requests end to end, and set performance budgets in CI so that a heavy dependency fails the build.
tradeoffs: Choose server-side rendering or static generation when first-load speed, search visibility and low-end devices matter (content, e-commerce, marketing pages). You pay with server cost, more complex caching and the work of hydration. Choose client-side rendering when the page is a rich application behind a login, where users stay for a long time and interactions matter more than first paint. You pay with bigger bundles and a slower start.
Choose a CDN and long cache lifetimes when content is the same for many users and changes rarely; origin load falls by orders of magnitude. Choose short TTLs, purging or no shared caching for personalised or fast-changing data. You give up freshness or pay for invalidation machinery.
Choose server-side sessions (a session ID in a cookie with data in Redis) when you need instant revocation and small cookies. Choose signed tokens such as JWTs when many independent services must verify identity without a shared store; you give up easy revocation and must keep tokens short-lived.
Choose REST when resources are simple, caching matters and many clients are external. Choose GraphQL when many clients need different shapes of data and over-fetching or many round trips hurt, accepting harder caching and query-cost control. Choose gRPC for internal service-to-service calls where speed and typed contracts matter, not for browsers directly.
Choose HTTP/3 where users are on mobile or lossy networks and connection migration and no head-of-line blocking help; keep HTTP/2 as the fallback. Choose a monolith behind a load balancer first and split into services only when team or scaling pressure demands it, since each service boundary adds latency and failure modes.
interview: What happens between typing a URL and seeing a page? Where does the time go? || Cache check, DNS lookup, TCP and TLS handshakes (1 RTT each, or 1 total with QUIC), request through CDN, load balancer and proxy to a stateless app server, then database or cache. The browser then parses HTML, fetches CSS, JS and images, builds DOM and render tree, lays out and paints. Time goes mostly to round trips over distance, server time, and JavaScript work on the device; a good answer gives numbers.
How would you cut page load time for users far from your servers? || Move content closer: CDN for static and cacheable responses, edge termination of TLS with warm connections to the origin, HTTP/3, fewer sequential requests (inline critical CSS, preload, avoid redirects), server-rendered first view, regional deployments for dynamic data, and measure real-user metrics by region.
Why should web servers be stateless, and where does the state go? || Any server can handle any request, so you add or remove servers freely, deploy without losing sessions and recover from failures. State moves to the database, a shared cache such as Redis, or the client in a cookie or signed token. The cost is an extra lookup per request and the need to secure client-held state.
How do you design caching for a page with personalised and public parts? || Split them. Serve the public shell and assets from the CDN with long TTLs. Fetch personalised data through a separate request with Cache-Control: private or no-store, or assemble it at the edge. Use Vary correctly and cache keys, and never put user data into a shared cache entry. Plan invalidation for the public part.
What is the difference between SSR, CSR and SSG, and how do you choose? || SSR builds HTML per request on the server, CSR builds it in the browser from JS and API calls, SSG builds at deploy time. Choose by freshness needs, personalisation, first-load performance, SEO and server cost: SSG for content that rarely changes, SSR for dynamic and SEO-sensitive pages, CSR for app-like interfaces behind a login. Most frameworks allow a mix per route.
How does CORS work and why does it exist? || The same-origin policy stops a page from reading responses from another origin, to protect user data. CORS lets a server opt in with Access-Control-Allow-Origin headers, and the browser sends a preflight OPTIONS request for non-simple requests. It protects users in the browser, not the server, since other clients can send any request.
quiz: Why are TCP and TLS handshakes a latency problem, and how did HTTP/3 help? || Each needs a round trip before data flows, so at 200 ms RTT the setup alone costs about 400 ms. HTTP/3 over QUIC combines transport and encryption setup into one round trip, and can resume with none.
What does a CDN gain you for a page that is requested 5,000 times per second and cached for 60 seconds at 200 edge locations? || The origin sees about 200 requests per minute, around 3 per second, instead of 5,000: a reduction of more than 1,000 times, and users get answers from nearby. The price is up to 60 seconds of staleness.
Why can a single-page application show a blank screen longer than a server-rendered page? || It must download and run JavaScript and then call an API before it can draw, which adds round trips, transfer time and CPU work on the device. A server-rendered page includes the content in the first response.
A user in a city 13,000 km from the server loads a page that needs TCP, TLS 1.3 and one request. What is the minimum time to the first byte at the speed of light in fibre (about 200,000 km/s)? || One RTT is about 2 × 13,000 / 200,000 = 0.13 s, so three round trips take at least about 390 ms, before any server time. Real paths are longer, so 600 ms or more is common.
When would you pick JWTs over server-side sessions? || When several independent services must authenticate requests without a shared session store, and you can live with short token lifetimes and harder revocation. Choose sessions when immediate revocation and small tokens matter.
