@@ druid
value: Apache Druid is a database for one kind of question: "over this time range, filtered by these dimensions, what are the totals?" It answers such questions over billions of events in well under a second, while new events are still arriving from a stream such as Kafka. Typical uses are dashboards that customers click on (ad campaign reports, network monitoring, product analytics), where hundreds of people run small aggregate queries at the same time and expect each answer in about 100 milliseconds.
A general data warehouse can answer the same SQL, but usually in seconds, on data that is minutes or hours old. Druid gets its speed by fixing the shape of the data in advance. Every row has a timestamp, data is cut into files by time, each column is stored separately with its own dictionary and index, and rows can be pre-aggregated ("rolled up") while they are ingested. A query then touches only the time slices it asks for, only the columns it needs, and inside those columns only the rows that match its filter.
Druid stands on two L1 ideas. OLAP analytics gives it columnar storage and the habit of answering aggregations by scanning compressed columns instead of reading whole rows. Real-time analytics gives it the goal and the shape of the ingestion path: events are queryable seconds after they arrive, not after a nightly batch. For the layer above (BI tools such as Apache Superset, customer-facing analytics products, alerting systems), Druid turns "group and sum a billion events" into an interactive operation. Its closest relatives are Apache Pinot and ClickHouse, and choosing between them is a common design decision in ad tech.
terms: Segment — an immutable file holding all rows for one time interval (or one shard of it), stored column by column; usually 300–700 MB and about 5 million rows.
Datasource — Druid's name for a table; it is a set of segments.
Rollup — pre-aggregating rows at ingestion time: rows with the same truncated timestamp and the same dimension values become one row with summed metrics.
Dimension and metric — a dimension is a column you filter and group by (country, campaign); a metric is a column you aggregate (count, revenue).
Bitmap index — for each distinct value of a dimension, a bitmap with one bit per row, set to 1 where the row has that value.
Deep storage — durable object storage (S3, HDFS, GCS) that keeps the master copy of every segment; query servers keep cached copies.
Historical — a server process that loads segments from deep storage onto local disk and answers queries over them.
Broker — the process that receives a query, finds the segments it needs, sends sub-queries to the servers holding them, and merges the results.
Supervisor — a long-running controller that manages streaming ingestion tasks, for example one per group of Kafka partitions.
history: Druid was started in 2011 at Metamarkets, a San Francisco start-up that sold analytics for programmatic advertising. The product needed interactive drill-downs over billions of ad events. Over a year the team tried relational databases (Greenplum, Infobright, MySQL) and HBase, and none gave both the scale and the speed. Eric Tschetter, the first full-time employee, wrote a short design proposal by email in February 2011, and Druid replaced the HBase cluster in April 2011, about eight weeks later. His blog post "Introducing Druid: Real-Time Analytics at a Billion Rows Per Second" (2011) described the design. Fangjin Yang, Gian Merlino and Vadim Ogievetsky were among the early builders.
Druid was open-sourced under the GPL in October 2012 and moved to the Apache License in February 2015. The SIGMOD 2014 paper "Druid: A Real-time Analytical Data Store" (Yang, Tschetter, Léauté, Ray, Merlino and Ganguli) described the node types, segments and the real-time path. In 2015 Yang, Merlino and Ogievetsky founded Imply to build a commercial Druid platform, and Snap acquired Metamarkets in 2017. Druid entered the Apache Incubator on 28 February 2018 and became a top-level Apache project on 18 December 2019.
The 2020s changed what Druid can do beyond simple aggregates. Version numbering jumped from 0.23 to 24.0 in 2022, when the multi-stage query (MSQ) engine arrived: a distributed, shuffle-based engine that runs SQL INSERT and REPLACE for batch ingestion. Druid 27 (August 2023) added asynchronous queries straight from deep storage. Druid 32 (February 2025) added projections, which are pre-aggregated views stored inside each segment, and later releases developed Dart, an interactive mode of the multi-stage engine for heavier queries and joins. Druid 38.0 (October 2026) supports Java 25, drops Java 17, and removes the old ZooKeeper-based way of announcing segments in favour of HTTP.
how: Every Druid row has a primary timestamp column, __time. At ingestion, rows are grouped by a segment granularity (for example one hour) into segments. Inside a segment, data is stored as columns, which is the core lesson of OLAP analytics: a query that sums revenue by country reads only the country, revenue and __time columns, not the other 40 columns of each event. Each string dimension is dictionary-encoded: the distinct values are sorted and numbered, and the column stores small integer IDs, compressed in blocks. For each distinct value there is also a bitmap index (Roaring bitmaps by default) marking the rows that hold it. Numeric columns are stored as compressed arrays (LZ4 by default). A filter such as campaign = 'c42' AND country IN ('IN','US') becomes a dictionary lookup and a few bitwise AND and OR operations on bitmaps, which yields exactly the matching row numbers before any data column is read.
Rollup is optional but central. If you set a query granularity of one minute, Druid truncates each timestamp to the minute and merges all rows that share the minute and every dimension value, summing the metrics. Ad and telemetry data often shrink 10 to 100 times this way. The price is that individual raw events are gone. Counts of distinct users cannot be summed, so Druid stores sketches instead (HyperLogLog or Apache DataSketches theta sketches), which can be merged and give approximate distinct counts with a known error, often around 1–2%.
Segments are immutable and versioned. A segment's identity is datasource + interval + version + partition number. To correct a day of data, a batch job writes new segments for that day with a higher version; when they are all published, the "timeline" switches queries to them in one step and the old ones are later removed. This is multi-version concurrency control at the file level. It gives atomic replacement without locks on readers, but it also means that changing one row means rewriting its whole segment.
The cluster is split into roles. Master processes: the Coordinator decides which Historicals hold which segments, keeps the requested number of replicas and balances load; the Overlord accepts ingestion tasks and assigns them to MiddleManagers (or Indexers). Data processes: Historicals serve published segments; ingestion tasks serve fresh data. Query processes: Brokers plan and merge; an optional Router forwards requests. Three external dependencies hold the state: deep storage keeps every segment, a SQL metadata store (PostgreSQL or MySQL) keeps the list of published segments and ingestion state, and ZooKeeper is still used for leader election in classic deployments. Historicals download segments from deep storage to local disk and read them through memory-mapped files, so the operating system page cache keeps hot segments in RAM. Because deep storage holds the master copy, a lost Historical costs only a re-download, not data loss.
The streaming path is where real-time analytics enters. A Kafka (or Kinesis) supervisor starts tasks that each read a set of partitions. A task keeps incoming rows in an in-memory index that is queryable immediately, so an event is visible to queries a few seconds after it reaches Kafka. Periodically the task persists small on-disk pieces, and at the end of its run (one hour by default) it merges them into final segments, pushes them to deep storage, and commits the segment list and the Kafka offsets to the metadata store in one database transaction. Because data and offsets are committed together, a crashed task restarts from the last committed offsets without loss or duplicates: this is how Druid gets exactly-once ingestion from Kafka. The Coordinator then asks Historicals to load the new segments, and the task stops serving them once they are loaded.
A query arrives at a Broker as Druid SQL (parsed and planned with Apache Calcite) or as native JSON. The Broker uses the time filter to pick only the segments whose intervals overlap the query, then sends one sub-query per segment to the servers holding them, real-time tasks included. Each server scans its segments in parallel, one segment per processing thread, and returns partial aggregates; the Broker merges them. Per-segment results can be cached, so a dashboard that refreshes every minute recomputes only the newest segments. For heavier work (large joins, big group-bys, ingestion with SQL) the multi-stage engine splits the query into stages connected by shuffles, much like Spark.

example: An ad server logs 1,000,000,000 impressions per day, about 11,600 per second. Each event has a timestamp, country, device type, campaign ID, publisher ID, user ID and price. The dashboard question is "spend by country for campaign c42 over the last 7 days".
Step 1, rollup. Set query granularity to one minute and keep four dimensions: country, device type, campaign and publisher. Keep user ID only inside a theta sketch for distinct users. Each minute has about 694,000 events (10⁹ / 1,440). Suppose those events contain about 40,000 distinct combinations of the four dimensions. Then each minute becomes 40,000 rows, and a day becomes 1,440 × 40,000 = 57.6 million rows. The rollup ratio is 1,000 / 57.6 ≈ 17 times fewer rows.
Step 2, segments. With hourly segment granularity, each segment holds 57.6 million / 24 = 2.4 million rows, a little under the 5 million that Druid suggests. Seven days is 7 × 24 = 168 segments, holding 7 × 57.6 million ≈ 403 million rows in total.
Step 3, pruning by time. The Broker selects only those 168 segments. Older months are never touched.
Step 4, bitmap filter. Suppose campaign c42 is 0.5% of rows, so each segment has 2.4 million × 0.005 = 12,000 matching rows. The Historical looks up "c42" in the campaign dictionary, takes its bitmap, and gets the 12,000 row numbers directly. Stored as a Roaring bitmap with 16-bit entries, that is about 12,000 × 2 bytes = 24 KB, instead of 2.4 million bits (300 KB) as a plain bitmap. It then reads the country ID and the price for just those rows.
Step 5, parallel scan. The cluster has 8 Historicals with 16 processing threads each, so 128 threads. The 168 segments need two rounds at most (168 / 128 ≈ 1.3). Scanning 12,000 rows of two compressed columns takes on the order of a few milliseconds, so the Historical work is roughly 10 ms, and the Broker merges 168 small partial results (about 200 countries each). The answer arrives in well under 100 ms, assuming the segments are already cached on local disk or in memory.
Count the rows actually touched: 168 × 12,000 ≈ 2.0 million. The raw week had 7 billion events. Rollup removed a factor of 17 and the bitmap removed a factor of 200, so the query reads about 3,500 times fewer rows than a full scan of raw data. That ratio, not raw CPU speed, is the source of Druid's latency.
intuition: Druid is a library that shelves its books by date, keeps a card index for every subject, and has already written summaries of each day's pages.
Most questions about events have the same shape: a time window, a few filters, a few groupings, and sums or counts. Druid makes each part of that shape cheap. The time window is cheap because files are cut by time. The filters are cheap because every dimension value already has a list of matching rows. The groupings and sums are cheap because columns are small integers next to each other in memory, and rollup has already merged rows that would have been grouped together anyway. Once you accept that the questions will have this shape, every design choice follows. The cost appears only when a question does not have this shape, such as "show me this one raw event" or "join these two large tables".
mistakes: People often think Druid is a general data warehouse that happens to be fast. In fact it is optimized for filtered aggregations on time-partitioned data. Large joins, frequent updates and wide row lookups are possible in newer versions but are much slower than the aggregate path, and a warehouse or lakehouse is usually the better home for that work.
People often think rollup is free compression. In fact it permanently drops the raw events and any column not listed as a dimension. If you later need a new dimension, or per-user detail, you must re-ingest from the raw source, so keep the raw events somewhere else (for example in a data lake).
People often think Druid's results are always exact. In fact distinct counts use sketches, and the native topN query is approximate by design: each segment returns only its local top values (at least 1,000 by default), so a value that is small in every segment but large in total can be ranked wrongly. Use groupBy with ORDER BY and LIMIT when exact ranking matters.
People often think more Historicals will fix any slow query. In fact a query that touches thousands of small segments is slow because of per-segment overhead. Compaction into fewer segments of roughly 5 million rows usually helps more than extra servers.
friction: Druid has many moving parts. A production cluster runs Coordinators, Overlords, Brokers, Routers, Historicals and MiddleManagers, plus deep storage, a metadata database and (in classic setups) ZooKeeper. Each has its own memory settings, and mistakes show up as slow queries or stuck ingestion. Managed offerings (Imply) and Kubernetes operators reduce this, but the operational surface is still larger than a single-binary system such as ClickHouse.
Updates are coarse. Because segments are immutable, correcting or deleting a few rows means rewriting the segments for that interval. Streaming upserts by primary key, which Pinot supports directly, are not Druid's strength. Late-arriving events create extra small segments for old intervals, which then need compaction. Privacy deletion requests (for example deleting one user's data) are expensive for the same reason.
Schema decisions made at ingestion are hard to undo. Rollup granularity, the dimension list, and which columns have indexes are fixed in the segments. High-cardinality dimensions such as user ID or URL create one bitmap per value, which grows segments and slows ingestion; such columns often should be sketches, or left out of the index.
Joins have improved (broadcast joins with lookup tables, shuffle joins in the multi-stage engine) but remain weaker than in warehouses, and Brokers merging very large group-by results can run out of memory. Choosing between Druid, Pinot and ClickHouse is hard, because benchmarks depend on data shape and most are run by vendors.
practice: Design the datasource around the dashboard queries, not around the raw events. List the filters and group-bys that users really run, make those the dimensions, choose the coarsest query granularity the product accepts (one minute or one hour is common), and measure the rollup ratio with a sample before going to production. Use theta or HLL sketches for distinct counts, and keep raw events in your lake so you can re-ingest when the schema changes.
Size segments to about 5 million rows (300–700 MB) and run automatic compaction to merge the small segments that streaming and late data produce. Set retention and load rules per tier: for example, keep the last 30 days on fast Historicals with two replicas, keep older data on a cheaper tier with one replica, and query very old data from deep storage with asynchronous queries.
For Kafka ingestion, set the task count to match the number of Kafka partitions you need in parallel, watch consumer lag, and alert on failed task publishing, because that is where data freshness breaks. Use the per-segment cache for dashboards that refresh often, and set query priorities or laning so one heavy report cannot block many small queries. Monitor query time per segment and segments scanned per query; they show whether the problem is data layout or capacity. For frequent upserts, wide joins or ad hoc analysis of raw data, use a warehouse or lakehouse beside Druid.
quiz: What do deep storage and the metadata store each hold in Druid? || Deep storage holds the durable master copy of every segment. The metadata store (PostgreSQL or MySQL) records which segments are published and stores ingestion state such as Kafka offsets.
How does a bitmap index let Druid answer a filter before reading any data column? || Each dimension value has a bitmap of the rows that contain it. Druid finds the value in the column dictionary, takes its bitmap, and combines bitmaps with AND and OR. The result is exactly the matching rows, so only those rows are read from the other columns.
How does Druid get exactly-once ingestion from Kafka? || An ingestion task publishes its finished segments and the Kafka offsets it has read in a single transaction in the metadata store. If the task crashes before the commit, a new task restarts from the last committed offsets, so no event is lost or counted twice.
Raw data has 2 billion events per day; with one-minute rollup each minute has 50,000 distinct dimension combinations. How many rows per day remain, and what is the rollup ratio? || 1,440 minutes × 50,000 = 72 million rows per day. The ratio is 2,000 million / 72 million ≈ 28 times fewer rows.
A product needs frequent per-user corrections and deletions plus sub-second dashboards. Why might you pick Pinot or a warehouse over Druid? || Druid segments are immutable, so each correction rewrites whole time intervals, which is costly when it happens often. Pinot supports primary-key upserts on real-time tables, and a warehouse or lakehouse handles row-level changes naturally, at the cost of slower queries.

@@ clickhouse
value: ClickHouse is an open-source columnar database for analytical queries: counting, filtering and grouping billions of rows in a fraction of a second. It started as the engine behind Yandex.Metrica, a web analytics service, and the name means "clickstream data warehouse". Today it runs observability platforms (logs, traces, metrics), product and ad analytics, financial data, and the backends of many SaaS dashboards. It is a single C++ binary that can run on a laptop, on a cluster of hundreds of servers, or as ClickHouse Cloud.
The problem it solves is the gap between batch warehouses and key-value stores. A warehouse such as Snowflake or Spark SQL can aggregate a billion rows, but usually in seconds and with batch loading. A key-value store answers point lookups fast but cannot aggregate. ClickHouse accepts a steady stream of inserts, makes each insert visible as soon as it is written, and answers aggregations in tens of milliseconds by reading only the columns and the row ranges a query needs, compressed, with every CPU core.
It stands on three concepts. OLAP analytics gives the columnar layout, compression and scan-oriented execution. Real-time analytics gives the goal of fresh data and low-latency queries, and with it the design of frequent inserts merged later in the background. C and C++ give direct control over memory layout, no garbage-collection pauses, templates that generate specialized code for each data type, and SIMD instructions; much of ClickHouse's speed comes from code that a managed runtime would make hard to write. For the layer above (Grafana, Superset, observability tools, user-facing analytics APIs), ClickHouse is the store that turns raw events into interactive charts.
terms: Part — an immutable directory of files created by one insert (or one merge), holding rows sorted by the table's sorting key, one file per column.
Sorting key (ORDER BY) — the columns by which rows inside every part are sorted; it decides which queries can skip data.
Granule — a block of 8,192 consecutive rows (by default), the smallest unit ClickHouse reads.
Sparse primary index — an in-memory array with one entry per granule: the key values of the granule's first row.
Mark — for one column and one granule, the byte offset of that granule inside the column's compressed file.
Merge — a background job that combines several parts of the same partition into one larger sorted part.
Mutation — an ALTER TABLE UPDATE or DELETE that rewrites the affected columns of whole parts in the background.
Materialized view — in ClickHouse, an insert trigger: each new block written to a source table is transformed by a query and appended to a target table.
ClickHouse Keeper — a Raft-based coordination service, compatible with the ZooKeeper protocol, that holds replication logs and metadata.
history: Alexey Milovidov began ClickHouse at Yandex in 2009 as a filter-and-aggregate engine for web log data. Yandex.Metrica, then one of the largest web analytics services in the world, wanted to build reports on the fly from raw clicks instead of storing pre-computed aggregates, which could not answer new questions. ClickHouse went into production for Metrica around 2012 and was open-sourced under the Apache 2.0 license in June 2016.
Adoption grew quickly because it was easy to run (one binary, no Hadoop) and fast on commodity hardware; Cloudflare, Uber and many observability companies built on it. In September 2021, ClickHouse Inc. was spun out of Yandex as an independent US company, with Milovidov as CTO and Aaron Katz as CEO. ClickHouse Cloud became generally available in December 2022. Its storage engine, SharedMergeTree, keeps all parts in object storage and lets stateless compute nodes share them.
The VLDB 2024 paper "ClickHouse - Lightning Fast Analytics for Everyone" (Schulze, Schreiber, Yatsishin, Dahimene and Milovidov) described the architecture for the first time in academic form. Recent work has filled old gaps: a native JSON type, a vector similarity index (generally available in 25.8), automatic join reordering (25.9), a text index for full-text search (beta in 25.12), and lightweight UPDATE with patch parts (25.7), which made standard SQL updates practical. The company raised $350 million at a $6.35 billion valuation in May 2025 and $400 million at a $15 billion valuation in January 2026. ClickHouse ships a release every month and long-term-support releases twice a year; 26.9 (September 2026) made the default compression size-aware, using ZSTD(3) for parts of 100 MB or more and LZ4 for smaller ones.
how: The main storage engine is the MergeTree family. A table declares a sorting key (ORDER BY), an optional partition key (often the month), and optional TTL rules. When an INSERT arrives with, say, 100,000 rows, the server sorts that block by the sorting key in memory and writes it as a new part. In the common "wide" format a part has one compressed data file per column, one marks file per column, a primary index file, a small min/max index for the partition key, a row count and checksums. Nothing is updated in place. The insert is visible to queries as soon as the part is committed, so there is no refresh delay, which is the real-time analytics side of the design.
Inside each column file, rows are grouped into granules of 8,192 rows (adaptive, so that very wide rows make smaller granules), and several granules are compressed together into blocks of roughly 64 KB to 1 MB with LZ4 or ZSTD. Columns can also have special codecs: Delta and DoubleDelta for timestamps and counters, Gorilla for floating-point metrics, and LowCardinality, which stores a dictionary and small integer codes for string columns with few distinct values. Because similar values sit next to each other, and are sorted by the key, compression ratios of 5 to 20 times are normal for event data.
The primary index is sparse: it stores only the key of the first row of each granule. One billion rows make about 122,000 granules, so the index fits in a few megabytes of RAM. A query with a condition on a prefix of the sorting key does a binary search on this index to find the range of granules that can contain matching rows, then uses the marks to seek directly to those granules in each needed column file. This is the most important tuning decision in ClickHouse: the sorting key decides which queries read 0.1% of the data and which read 100%. Secondary "skip indexes" (min/max, set, Bloom filter, n-gram Bloom filter, text index) store a small summary per group of granules and let the engine skip groups that cannot match on columns that are not in the key. Recent versions also cache which granule ranges matched a WHERE condition, so a repeated dashboard filter skips the index work.
Many small parts would make every query open many files, so background threads merge parts of the same partition. Because every part is already sorted, a merge is a k-way merge sort, like compaction in an LSM tree. Part names record the merge history: 202610_1_5_2 means partition 202610, insert blocks 1 to 5, merge level 2. Merges stop at a size limit (150 GB by default). Merges are also where special engines do their work. ReplacingMergeTree keeps only the newest version of rows with the same key. SummingMergeTree and AggregatingMergeTree combine rows with the same key into sums or partial aggregate states. TTL merges delete old rows or move them to cheaper disks. The important consequence is that deduplication and pre-aggregation are eventual: until a merge happens, a query may see two versions of a row, unless it uses the FINAL modifier or aggregates correctly.
Changes to existing data have three paths. A classic mutation (ALTER TABLE ... UPDATE or DELETE) rewrites the affected columns of every affected part in the background, which is heavy. Lightweight DELETE marks rows as deleted with a hidden mask column that queries filter out. Lightweight UPDATE (since 25.7) writes small "patch parts" that contain only the changed rows and columns; queries apply patches while reading, and later merges fold them into the original parts. It is designed for changing up to roughly 10% of a table, with about 40 bytes of overhead per updated row.
Query execution is vectorized: operators process blocks of columns (tens of thousands of values at a time) instead of one row at a time, which keeps data in CPU caches and lets loops use SIMD. This is where C++ matters. Aggregation picks one of more than 30 hash table variants generated from one template, depending on key type and size; for example, a key of one byte uses a direct lookup array, and string keys use a special string hash table. Kernels are compiled for several instruction sets (SSE 4.2, AVX2, AVX-512) and chosen at runtime. Expressions can be compiled with LLVM. A single query uses all cores of a server by splitting the granule ranges among threads.
Scale-out is explicit. A Distributed table sends a query to one replica of every shard and merges partial results. ReplicatedMergeTree tables replicate by writing each new part to a shared log in ClickHouse Keeper (a C++ Raft implementation that replaced ZooKeeper); other replicas fetch the part. Replication is asynchronous, so replicas are eventually consistent unless you require an insert quorum. Streams arrive through table engines such as Kafka, usually with a materialized view that moves each consumed block into a MergeTree table.

example: A SaaS analytics product stores page views in one table with 10 billion rows. Columns include site_id (UInt32), event_date (Date), user_id (UInt64), url (String) and duration_ms (UInt32), plus 30 more. The sorting key is (site_id, event_date). A customer dashboard asks: "unique users and average duration for site 42 over the last 7 days".
Step 1, index size. Granules: 10,000,000,000 / 8,192 ≈ 1.22 million. Each index entry holds a UInt32 and a Date, 4 + 2 = 6 bytes, so the primary index is about 1.22 million × 6 ≈ 7.3 MB, which stays in memory.
Step 2, finding the rows. Site 42 has 0.1% of all rows, 10 million rows, stored next to each other because site_id is first in the key. They cover about one year of data, so 7 days is about 7 / 365 × 10 million ≈ 192,000 rows. Binary search over 1.22 million entries takes about log₂(1.22 million) ≈ 20 comparisons. The matching rows fill 192,000 / 8,192 ≈ 23.4 granules; with partial granules at both ends, the engine reads about 25 granules, roughly 205,000 rows.
Step 3, bytes read. The query needs user_id (8 bytes) and duration_ms (4 bytes): 205,000 × 12 bytes ≈ 2.5 MB uncompressed. With 4× compression, about 0.6 MB comes from disk or the page cache. That takes well under 10 ms even on a network disk, and computing uniq and avg over 205,000 values is a few milliseconds of CPU.
Step 4, the counterfactual. With a sorting key of (event_date) only, site 42's rows would be spread through every granule of those 7 days. Seven days hold about 7 / 365 × 10 billion ≈ 192 million rows, so the engine would read about 2.3 GB of the two columns instead of 2.5 MB, roughly 900 times more. A full scan without any useful key would read 10 billion × 12 bytes = 120 GB. The same query, the same hardware, three very different costs: only the sorting key changed.
Step 5, the insert side. The product receives 50,000 events per second. If each event were its own INSERT, ClickHouse would create 50,000 parts per second, and the "too many parts" limits (inserts slow down above 1,000 active parts in a partition and fail above 3,000) would be hit within a second. Batching for one second gives one part of 50,000 rows per second, which background merges handle easily. Asynchronous inserts do this batching on the server for clients that cannot batch.
intuition: ClickHouse is a well-sorted archive with a thin table of contents: find the right drawer quickly, open only the folders you need, and read them with every hand you have.
The design is natural once you see that analytical speed comes from not reading data rather than from reading it quickly. Sorting by the key puts related rows together, so a filter becomes a contiguous range. A sparse index of one entry per 8,192 rows is small enough to keep in memory and still precise enough to skip almost everything. Columnar files mean that a query touching 2 of 35 columns reads 2 files. Immutable parts make inserts cheap, because writing a new sorted file is easier than updating an old one, and the cost of tidying up is moved to background merges where nobody waits for it. Finally, once the data to read is small, vectorized C++ code makes the remaining work fast.
mistakes: People often think the primary key in ClickHouse is a unique constraint, as in PostgreSQL. In fact it is only the sort order and the sparse index. Two rows can have the same key; uniqueness, if needed, comes eventually from ReplacingMergeTree merges or explicitly with FINAL or a GROUP BY in the query.
People often think many small inserts are fine because each one is fast. In fact every insert creates a part, and too many parts slow queries and eventually make inserts fail. Batch to thousands or hundreds of thousands of rows per insert, or use asynchronous inserts.
People often think ReplacingMergeTree or SummingMergeTree gives correct results immediately. In fact rows are combined only when merges happen, which may be minutes later or never for some parts. Queries must be written to tolerate duplicates (for example argMax by version, or sum in the query) or use FINAL, which costs extra work.
People often think a skip index works like a B-tree index. In fact it only lets ClickHouse skip groups of granules whose summary cannot match. If the values you filter on are spread across all granules, a skip index skips nothing and only adds cost; the sorting key is the real index.
friction: The sorting key is chosen at table creation and cannot be changed freely later. A table serves well the queries that filter on a prefix of its key, and poorly the others. Teams handle this with projections (a second, hidden sort order inside each part) or materialized views into differently sorted tables, both of which cost storage and insert work.
Joins were historically the weak point. The default hash join builds the right-hand table in memory, so a large right side can exceed memory. Newer versions add join reordering, grace hash joins that spill to disk, and better planning, but a star schema with many large joins is still more natural in a warehouse. Many teams denormalize into wide tables, or use dictionaries (in-memory lookup tables) for small dimensions.
Updates and deletes are better than before but still not free. Patch parts add read cost until merges absorb them, mutations rewrite whole parts, and deleted data really disappears only after merges. Consistency across replicas is eventual by default; reading your own write requires routing to the same replica or settings such as select_sequential_consistency.
Operations at scale need care: shard rebalancing is mostly manual in self-managed clusters, Keeper must be run reliably, and per-query memory limits need tuning. ClickHouse Cloud removes much of this with SharedMergeTree.
practice: Choose the sorting key from the most common filters, from low to high cardinality, for example (tenant_id, event_type, toStartOfHour(timestamp)). Keep the partition key coarse (usually a month or a day); thousands of partitions create thousands of small parts. Use LowCardinality(String) for strings with fewer than about 10,000 distinct values, Delta or DoubleDelta codecs for timestamps and counters, and ZSTD for large cold columns.
Batch inserts to at least thousands of rows and about one insert per second per table, or enable async_insert. Watch system.parts and system.merges: a growing number of active parts per partition is the first sign of trouble. For streams, use the Kafka engine or ClickPipes with a materialized view, and make consumers idempotent, because replicated inserts deduplicate by block hash only for retries of the same block.
For dashboards, pre-aggregate with a materialized view into an AggregatingMergeTree table and query it with the -Merge combinators (sumMerge, uniqMerge). Use EXPLAIN indexes = 1 to see how many granules a query really reads; the ratio of selected granules to total granules is the best single health number for a table. Use FINAL only where needed. Prefer lightweight UPDATE for small corrections and partition drops for bulk deletes, which are instant. Test on a copy of real data, because ClickHouse performance depends more on data shape than on hardware.
quiz: What is a granule in ClickHouse, and what does the primary index store for it? || A granule is a group of 8,192 consecutive rows by default, the smallest unit ClickHouse reads. The sparse primary index stores the sorting-key values of the first row of each granule.
Why do background merges exist, and what do ReplacingMergeTree and AggregatingMergeTree do during them? || Every insert creates a new sorted part, so merges combine small parts into large ones to keep the number of files low. During merges, ReplacingMergeTree keeps only the newest row per key, and AggregatingMergeTree combines rows with the same key into partial aggregate states.
How does the sorting key decide how much data a filtered query reads? || Rows are stored in key order, so a filter on a key prefix maps to a contiguous range of granules found by binary search on the sparse index. A filter on a column not at the front of the key matches rows spread across many granules, so far more data must be read.
A table has 4 billion rows and the default granule size. About how many index entries are there, and how big is the index if each key entry is 12 bytes? || 4,000,000,000 / 8,192 ≈ 488,000 entries. At 12 bytes each, the index is about 5.9 MB.
When would you choose ClickHouse over Druid, and when the other way round? || ClickHouse fits when you want one simple binary, flexible SQL, wide tables, and raw events kept unaggregated, for example observability. Druid fits when you want tight Kafka integration with exactly-once ingestion, automatic tiering of time-partitioned segments, and many small concurrent dashboard queries on rolled-up data, accepting more node types to operate.

@@ lucene
value: Apache Lucene is a Java library for building search: you give it documents, and it lets you find the ones that match a query and rank them by relevance in milliseconds, even across hundreds of millions of documents. It is not a server. It has no network API, no cluster and no replication. It is the engine inside products that add those things: Elasticsearch, OpenSearch and Apache Solr run one Lucene index per shard.
The problem it solves is old and simple to state. Scanning every document for every query is far too slow, and a database B-tree index on a text column cannot answer "documents that contain these words, best matches first". Lucene builds an inverted index, the data structure behind every search engine: for each word, the sorted list of documents that contain it. Over 25 years it has grown to index much more than text: numbers and geographic points in BKD trees, columnar "doc values" for sorting and aggregation, and dense vectors in HNSW graphs for semantic search.
Lucene stands on three concepts. The search engine concept (L1) gives the model: analyze text into terms, keep posting lists, and rank with a relevance formula such as BM25. The JVM (L0) gives a portable runtime with a JIT compiler that turns Lucene's tight loops over integer arrays into fast machine code, and recent Java versions give it SIMD through the Vector API and safe access to native memory. Memory-mapped files (L3) let Lucene read its immutable index files as if they were arrays in memory, leaving caching to the operating system's page cache instead of the Java heap. For the layer above, Lucene is the reason Elasticsearch and OpenSearch can treat a shard as a black box that indexes and searches.
terms: Document and field — a document is a set of named fields (title, body, price); each field can be indexed, stored, or kept as doc values.
Analyzer — the pipeline that turns field text into terms: a tokenizer splits text, filters lowercase, remove stop words or stem ("running" to "run").
Term — one analyzed token in one field, such as body:shoe; the unit of the inverted index.
Posting list — for one term, the sorted list of document IDs that contain it, with optional frequencies and positions.
Segment — a self-contained, immutable mini-index written once; an index is a list of segments.
Doc values — a column-oriented copy of a field's values, one entry per document, used for sorting, faceting and aggregations.
BM25 — the default scoring formula; it rewards rare terms, rewards repeated terms with diminishing returns, and penalizes long documents.
Commit and refresh — a commit makes segments durable with fsync; a near-real-time refresh makes new segments searchable without that cost.
FST — finite state transducer, a compact automaton that maps term prefixes to positions in the terms dictionary.
history: Doug Cutting wrote Lucene in Java in his spare time in the late 1990s, after working on search at Xerox PARC, Excite and Apple, and it is usually dated to 1999. He named it after his wife's middle name. It was first distributed through SourceForge, joined the Apache Jakarta project in September 2001, and became a top-level Apache project in February 2005. Cutting later built Nutch, a web crawler on Lucene, from which Hadoop grew.
Servers were built around the library. Solr was created at CNET by Yonik Seeley in 2004, donated to Apache in 2006, and merged with the Lucene project in 2010. Shay Banon released Elasticsearch in 2010, built around distributed Lucene shards with a JSON API. These products pushed Lucene toward faster indexing, near-real-time search and analytics.
The internals changed several times. Lucene 4.0 (2012) introduced pluggable codecs, doc values and terms indexes stored as FSTs, work led largely by Michael McCandless and Robert Muir. Lucene 6.0 (2016) made BM25 the default similarity, replacing classic TF-IDF, and added points, numeric and geo fields indexed with BKD trees. Lucene 8.0 (2019) added block-max WAND, which skips blocks of documents that cannot reach the top results. Lucene 9.0 (2021) added vector search with HNSW graphs. Lucene 10.0 (October 2024) requires Java 21 and uses its newer APIs for memory mapping and I/O. The 10.x line has focused on speed and vectors: filtered vector search (10.2, 2025), vectorized lexical scoring (10.3, 2025), 1- to 8-bit quantized vectors (10.4, 2026) and methods for combining BM25 and vector scores (10.5, June 2026). The latest release is 10.5.2 (October 2026).
how: Indexing starts with analysis. For each document, each text field passes through an analyzer that produces a stream of terms with positions: "Red Running Shoes" becomes red(0), run(1), shoe(2). The IndexWriter adds these terms to in-memory buffers, one per indexing thread. When the buffer reaches its size limit (16 MB by default) or the application asks, the buffer is flushed as a new segment. A segment is never modified afterwards. This one decision shapes the rest of Lucene: writes are sequential, files can be cached and memory-mapped without locking, and many readers can search a segment while new segments are being written.
Inside a segment, each indexed field has a terms dictionary, sorted by term, stored in blocks on disk, with a small FST in front that maps term prefixes to the right block. For each term the dictionary points to its posting list. Posting lists store document IDs in increasing order as deltas (gaps between IDs), packed into fixed-size blocks with just enough bits per value, so a frequent term costs only a few bits per document. Frequencies and positions sit in separate files, so a query that needs no phrase matching never reads positions. Skip data and "impacts" (the best possible score in each block) let a search jump over whole blocks. Besides the inverted index, a segment can hold stored fields (the original document, compressed with LZ4 or DEFLATE), doc values (columnar data for sorting and aggregations), BKD trees for numeric and geo ranges, and an HNSW graph for each vector field.
Deletes are also handled without changing segments. Deleting a document sets its bit in a "live docs" bitset for that segment, and searches skip it. An update is a delete plus an add. Over time an index accumulates many segments and many deleted documents, so a merge policy runs background merges: the default TieredMergePolicy merges about ten segments of similar size into one, drops deleted documents, and avoids creating segments larger than 5 GB. Merging is a sequential read and write, close to how compaction works in an LSM tree. For vectors, merging must rebuild or extend the HNSW graph, which is the most expensive part of merging in vector-heavy indexes.
Search runs over all segments of a point-in-time reader. The query is rewritten into basic parts, and for each segment Lucene creates a scorer that walks the posting lists. A conjunction (red AND shoe) is a leapfrog: take the current document of the shortest list, ask the other list to advance to that ID or the next larger one, and repeat. A disjunction uses a priority queue of iterators. Each matching document gets a score, and a heap keeps the top k. The search engine concept supplies the scoring model; BM25 computes, for each query term t in document d, IDF(t) × f × (k1 + 1) / (f + k1 × (1 − b + b × dl / avgdl)), where f is the term frequency, dl the document length, avgdl the average length, k1 = 1.2 and b = 0.75. IDF is ln(1 + (N − n + 0.5) / (n + 0.5)) for N documents of which n contain the term. Block-max WAND and MaxScore use the per-block maximum scores to skip blocks that cannot beat the current k-th best score, which often avoids scoring most matching documents.
The JVM contributes more than portability. Lucene's hot loops decode blocks of integers, intersect lists and compute scores; the JIT compiler inlines and unrolls them, and the Java Vector API (used by Lucene when available) runs vector distance and decoding with SIMD instructions. Lucene keeps most data off the Java heap, so the garbage collector does not have to scan gigabytes of index.
Memory-mapped files are how that is possible. The default MMapDirectory maps each segment file into the process's virtual address space; on Java 21 this uses the Foreign Function and Memory API rather than the older ByteBuffer workaround. Reading index data is then a memory access. If the page is in the operating system's page cache it costs nanoseconds; if not, the kernel reads it from disk. Immutability is what makes this safe: a mapped file never changes under a reader. The practical rule that follows is that a Lucene server needs free RAM outside the Java heap, because the page cache is Lucene's real cache.
Near-real-time search connects writing and reading. After a flush, an application can open a new reader that includes the new segments without a commit, which takes milliseconds. A commit, which calls fsync on new files and writes a new segments_N file listing the live segments, is what makes data durable; it is much more expensive and done less often. Elasticsearch and OpenSearch build on this: a "refresh" (every second by default) opens a new near-real-time reader, and their own transaction log provides durability between commits.

example: Start with posting compression. Suppose the term "shoe" appears in documents 1000, 1003, 1010, 1011 and 1040. Lucene stores the first ID and then the gaps: 1000, 3, 7, 1, 29. In a block where all gaps are below 64, each needs only 6 bits. A block of 128 gaps then takes 128 × 6 = 768 bits = 96 bytes, compared with 128 × 4 = 512 bytes as plain 32-bit integers. That is more than 5 times smaller, and decoding a block is a simple, vectorizable loop.
Now scoring. An index has N = 1,000,000 product documents with an average length of avgdl = 100 terms. The query is "red shoes", analyzed to red and shoe. The term red appears in n = 50,000 documents and shoe in n = 2,000.
Step 1, IDF. For red: ln(1 + (1,000,000 − 50,000 + 0.5) / (50,000 + 0.5)) = ln(1 + 19.0) = ln(20.0) ≈ 3.00. For shoe: ln(1 + 998,000.5 / 2,000.5) = ln(499.9) ≈ 6.21. The rarer word is worth about twice as much.
Step 2, document A has 50 terms and contains red once and shoe twice. Its length factor is \( K = k_1 \times (1 - b + b \times \text{dl} / \text{avgdl}) \) = 1.2 × (0.25 + 0.75 × 0.5) = 1.2 × 0.625 = 0.75. For red: 1 × 2.2 / (1 + 0.75) = 1.257. For shoe: 2 × 2.2 / (2 + 0.75) = 1.600. Score = 3.00 × 1.257 + 6.21 × 1.600 ≈ 3.77 + 9.94 = 13.71.
Step 3, document B has 200 terms and contains red three times and shoe once. K = 1.2 × (0.25 + 0.75 × 2) = 1.2 × 1.75 = 2.1. For red: 3 × 2.2 / (3 + 2.1) = 1.294. For shoe: 1 × 2.2 / (1 + 2.1) = 0.710. Score = 3.00 × 1.294 + 6.21 × 0.710 ≈ 3.88 + 4.41 = 8.29.
Document A wins, 13.71 against 8.29. Three effects explain it: the rare term shoe dominates; three mentions of red count only a little more than one (term frequency saturates); and B's long text lowers each match. Since Lucene 8, the (k1 + 1) factor is left out of the numerator because it multiplies every score by the same constant and does not change the ranking.
Finally, memory. A 60 GB index on a server with 64 GB of RAM and a 16 GB Java heap leaves about 48 GB for the page cache, so most of the index can stay in memory. With a 48 GB heap only about 16 GB would remain, and searches would read from disk much more often, even though the process "has more memory".
intuition: Lucene is the index at the back of a book, written in small booklets that are never edited, only stapled together into bigger ones later.
The design follows from two observations. First, text search is about the words, not the documents, so you invert the data: for each word, keep the list of places it appears, sorted, so that combining words is merging sorted lists. Second, rewriting a sorted, compressed index in place for each new document would be very slow, but writing a new small index is cheap. So new data goes into new segments, and merging, which is a fast sequential operation, slowly turns many small segments into a few large ones. Immutability then gives everything else for free: safe concurrent readers, simple caching through the page cache, and easy snapshots, because a set of segment files is a consistent view of the index.
mistakes: People often think Lucene is a search server. In fact it is a library inside your process. Sharding, replication, a REST API, security and cluster management all come from systems built on it, such as Elasticsearch, OpenSearch and Solr.
People often think an update changes a document in place. In fact every update deletes the old document (a bit in the live docs) and indexes a new one in a new segment. Frequent updates of large documents cost full re-analysis and create merge work.
People often think a bigger Java heap makes Lucene faster. In fact index data is read through memory-mapped files and cached by the operating system outside the heap. A heap that takes most of the RAM starves the page cache and makes searches slower.
People often think a document is searchable as soon as it is added. In fact it becomes visible only after a flush and a new near-real-time reader (a refresh), and durable only after a commit. Elasticsearch hides part of this with its one-second refresh and its own transaction log.
People often think BM25 scores are comparable across queries or indexes. In fact they depend on collection statistics (N, document frequencies, average length), so a score of 13 means nothing outside one query on one index.
friction: Being a library, Lucene leaves everything distributed to the products on top. Statistics are per index, so in a sharded system each shard computes IDF from its own documents, which can change rankings slightly across shards.
Merging is a constant cost. It uses disk bandwidth and CPU in the background, can temporarily need extra disk space for the new segment, and competes with searches. Too few merges leave many small segments and slow searches; aggressive merging wastes I/O. Indexes with many deletes keep paying for dead documents until merges remove them.
Vector search is the fastest-changing area. HNSW graphs are built per segment, so a search visits a graph in every segment, and merging must rebuild or extend graphs, which is slow and memory-hungry at large scale. Quantization (8, 4, 2 and 1 bit) has reduced memory a lot, but specialized vector databases can still be faster for pure vector workloads, while Lucene's advantage is combining vectors with filters and keyword search in one engine.
Relevance is hard to get right: BM25 is a default, and boosts, synonyms and language analysis need tuning per domain. Changing an analyzer requires re-indexing every document, because terms are fixed at write time.
practice: If you use Lucene directly, reuse one IndexWriter per index, give it a larger RAM buffer (for example 256 MB) for bulk loads, and use a SearcherManager to refresh readers on a schedule instead of opening a new reader per query. Commit at intervals that match your durability needs, not after every document. Use MMapDirectory, which is the default on 64-bit systems, and leave at least half of the machine's RAM for the page cache.
Design fields deliberately: index only the fields you search, enable doc values only on fields you sort or aggregate, and store only what you must return. Use keyword (not analyzed) fields for IDs and exact filters, and put filters in non-scoring filter clauses so they can be cached and do not affect scores. Test analyzers with real queries before indexing large data, because changing them later means re-indexing.
For scale, prefer fewer, larger segments for read-heavy indexes (force-merge only indexes that no longer change), and watch the deleted-document ratio. For vector search, choose quantized formats to cut memory, and test recall against brute-force results on a sample, since HNSW is approximate. In Elasticsearch or OpenSearch, the same Lucene rules apply per shard: shard sizes of roughly 10 to 50 GB, enough page cache, and refresh intervals longer than one second for bulk indexing.
quiz: What does a Lucene segment contain, and why is it never modified after it is written? || A segment holds a terms dictionary with posting lists, plus optional stored fields, doc values, BKD points and HNSW vectors. It is immutable so that writes are sequential, readers need no locks, files can be memory-mapped and cached safely, and a set of segments forms a consistent snapshot.
How does Lucene delete and update documents without changing segments? || A delete sets the document's bit in the segment's live-docs bitset, and searches skip it. An update is a delete plus an add of the new version in a new segment; merges later remove deleted documents for real.
Why does block-max WAND speed up top-k search? || Each block of a posting list records the highest score any document in it can reach. If the sum of these maxima for a block cannot beat the current k-th best score, Lucene skips the whole block without decoding or scoring it.
With N = 1,000,000 documents, what is the BM25 IDF of a term that appears in 1,000 documents? || ln(1 + (1,000,000 − 1,000 + 0.5) / (1,000 + 0.5)) = ln(1 + 998.5) = ln(999.5) ≈ 6.91.
A search server has 64 GB of RAM and a 50 GB index. Should you give the JVM a 48 GB heap? || No. Lucene reads index files through memory mapping, so the operating system page cache is its main cache. A heap of about 16 GB or less leaves most of the RAM to cache the index, which usually gives faster and more stable searches than a large heap.

@@ opensearch
value: OpenSearch is a distributed search and analytics engine: it stores JSON documents, indexes every field, and answers full-text, filter, aggregation and vector queries over billions of documents through a REST API. It is the Apache-2.0-licensed fork of Elasticsearch 7.10 and Kibana, started by AWS in 2021 after Elastic changed its license, and it is now governed by the OpenSearch Software Foundation under the Linux Foundation. Amazon OpenSearch Service, Aiven, Instaclustr and many self-managed clusters run it.
Teams use it for three different jobs. The first is search in applications: product catalogues, documents, help centres. The second is observability: logs, traces and metrics from thousands of services, searched and charted in OpenSearch Dashboards. The third, growing fastest, is vector and hybrid search for semantic retrieval and retrieval-augmented generation (RAG), where keyword relevance and embedding similarity are combined in one query. Each job needs the same core: shard data across machines, keep copies for safety, index new data within about a second, and run one query on every shard in parallel.
OpenSearch stands on four concepts. Apache Lucene (L0) does the real indexing and searching: every shard is a full Lucene index with segments, posting lists, doc values, BKD trees and HNSW graphs. The search engine concept (L1) gives inverted-index retrieval and BM25 ranking. Vector search (L1) gives approximate nearest-neighbour search over embeddings, which OpenSearch provides through its k-NN plugin with the Faiss and Lucene engines. Observability (L1) gives the log, metric and trace use case that drives much of its feature work: ingestion pipelines, index lifecycle policies, the Piped Processing Language (PPL), and trace and service views. What OpenSearch itself adds is the distributed layer: cluster membership, shard placement, replication, durability, routing, query fan-out and result merging.
terms: Index — a named collection of documents with a mapping (schema); physically split into shards.
Shard — one Lucene index holding part of an index's documents; a primary shard takes writes, replica shards are copies.
Mapping — the schema of an index: for each field, its type (text, keyword, date, knn_vector) and how it is analyzed.
Cluster manager — the elected node that owns the cluster state (indexes, mappings, shard locations); called "master" before version 2.0.
Translog — a per-shard write-ahead log that makes acknowledged writes durable between Lucene commits.
Refresh — opening a new Lucene near-real-time reader so recent writes become searchable; every 1 second by default.
Segment replication — replicas copy finished Lucene segment files from the primary instead of re-indexing each document.
k-NN plugin — the plugin that adds the knn_vector field and approximate nearest-neighbour search using the Faiss or Lucene engines.
ISM — Index State Management, policies that roll over, shrink, move to cheaper storage and delete indexes as they age.
history: Shay Banon released Elasticsearch in 2010 as a distributed, JSON-over-HTTP server around Lucene, and Elastic built Kibana, Logstash and Beats around it. AWS launched Amazon Elasticsearch Service in 2015, based on the open-source code. In January 2021 Elastic announced that, from version 7.11, Elasticsearch and Kibana would no longer be Apache-licensed but dual-licensed under the Server Side Public License (SSPL) and the Elastic License, both of which restrict offering the software as a managed service. In April 2021 AWS announced OpenSearch, a fork of the last Apache-licensed versions (Elasticsearch 7.10.2 and Kibana 7.10.2), merged with the Open Distro for Elasticsearch plugins it had been building since 2019 (security, alerting, SQL, anomaly detection, k-NN). OpenSearch 1.0 became generally available on 12 July 2021, and the AWS service was renamed Amazon OpenSearch Service.
The 2.x line, starting with 2.0 on 26 May 2022, moved to Lucene 9, renamed "master" to "cluster manager", and added segment replication and searchable snapshots (both generally available in 2.7, 2023), remote-backed storage on object stores, neural search with embedding models, and hybrid search. In September 2024 AWS moved the project to the new OpenSearch Software Foundation under the Linux Foundation, so that governance no longer depended on one company. Also in 2024, Elastic added the AGPL as a third license option, so Elasticsearch is open source again, though under a copyleft license.
OpenSearch 3.0 (6 May 2025) moved to Lucene 10 and Java 21, replaced the Java Security Manager, and added pull-based ingestion from Kafka and Kinesis and gRPC APIs. Later 3.x releases added GPU-accelerated vector index builds (3.1), Apache Calcite as the PPL engine (3.3), the first long-term support release (3.6, April 2026), native Prometheus and PromQL support (3.7), and more vector quantization options; the latest release is 3.9 (29 September 2026). The NMSLIB vector engine was deprecated in 2.19, leaving Faiss (the default) and Lucene.
how: A cluster is a set of nodes with roles. Cluster-manager-eligible nodes elect one leader that owns the cluster state: which indexes exist, their mappings, and which node holds each shard copy. Data nodes hold shards and do the indexing and searching. Coordinating nodes receive requests and fan them out; ingest nodes run pipelines that transform documents before indexing; ML nodes run embedding and other models. An index is created with a fixed number of primary shards and a number of replicas. A document goes to shard = hash(_routing) mod number_of_primary_shards, where _routing is the document ID unless you set it. Because of that formula, the primary shard count cannot simply be changed later; you must split, shrink or re-index.
The write path is where OpenSearch adds durability around Lucene. A coordinating node forwards an indexing request to the primary shard. The primary indexes the document into its Lucene IndexWriter (an in-memory buffer) and appends the operation to the shard's translog, which is fsynced before the request is acknowledged by default. The operation is then sent to replicas. In classic document replication every replica re-indexes the document, so a cluster with one replica does the analysis and indexing work twice. With segment replication, only the primary indexes; replicas copy the finished segment files after each refresh, which saves CPU at the cost of replicas lagging slightly behind. With remote-backed storage, segments and translog are also uploaded to object storage such as S3, so data survives even if all copies on local disks are lost.
Freshness and durability are separate steps, inherited from Lucene's near-real-time model. A refresh, every second by default, turns the in-memory buffer into a new searchable segment. A flush, done less often, performs a Lucene commit (fsync of segment files) and trims the translog. If a node crashes, the shard recovers from the last commit plus a replay of the translog. Background merges inside Lucene combine small segments created by frequent refreshes.
Search uses two phases. In the query phase, the coordinating node sends the query to one copy (primary or replica) of every shard, choosing copies on nodes that have recently answered fastest (adaptive replica selection). Each shard runs it on its Lucene index and returns only the IDs and scores of its local top k results (say 10). The coordinator merges these lists into the global top k; this costs little, because it merges a few short sorted lists rather than raw data. In the fetch phase it asks the relevant shards for the full documents. Aggregations work the same way: each shard computes partial results, such as counts per term, and the coordinator combines them. A terms aggregation is therefore approximate when values are spread unevenly, because each shard returns only its top shard_size buckets. Scores also use per-shard statistics unless you ask for a global pre-query (dfs_query_then_fetch).
Vector search is a plugin layer on Lucene's model. A knn_vector field stores embeddings. With the Faiss engine, each segment gets a native Faiss index (HNSW or IVF, optionally with product or scalar quantization) built through JNI and loaded into memory outside the Java heap; with the Lucene engine, the HNSW graph lives in the Lucene segment. A query searches the graph of every segment of every shard, keeps the best candidates, and the coordinator merges them. Filters can be applied before or during the graph walk. Hybrid queries run a BM25 query and a vector query, normalize each score list (min-max, L2 or z-score) or combine ranks with reciprocal rank fusion, and merge them in a search pipeline. Quantization trades recall for memory: 16-bit, 8-bit, and binary encodings reduce memory up to 32 times, with optional rescoring against full-precision vectors stored on disk.
The observability side is mostly about lifecycle and query languages. Logs arrive through Data Prepper, Fluent Bit or OpenTelemetry collectors into time-based indexes (one per day, or rollover by size). ISM policies roll an index over at, for example, 50 GB, force-merge it when it stops receiving writes, move it to cheaper warm or cold storage, and delete it after the retention period. PPL lets users write pipe-style queries such as "source = logs | where status >= 500 | stats count() by service", now planned by Apache Calcite, and Dashboards provides Discover, trace views and service maps.

example: A company keeps 30 days of application logs and wants semantic search over 10 million support articles in the same cluster.
Step 1, log storage. Services produce 500 GB of raw JSON logs per day. Indexed size depends on mappings; assume the index on disk is 1.1 times the raw size, so 550 GB of primary data per day. With one replica that is 1.1 TB per day, and 30 days is 33 TB. OpenSearch stops allocating shards to a disk above 85% use by default (the low watermark), so plan for 33 / 0.85 ≈ 39 TB, plus room for merges.
Step 2, shards. A common target is 30 to 50 GB per shard. One day of 550 GB at about 40 GB per shard needs 550 / 40 ≈ 14 primary shards, or 28 shard copies with the replica. Thirty daily indexes give 30 × 28 = 840 shards. On 6 data nodes with 8 TB disk each (48 TB), each node holds 140 shards and about 6.5 TB. A frequently cited limit is about 25 shards per GB of Java heap; with a 31 GB heap that is roughly 775 shards per node, so 140 is safe. If the team had used 5 primaries per day for a 10 GB-per-day index instead, shards would be tiny and the count would grow without any benefit.
Step 3, routing. A log line with ID "abc" goes to shard hash("abc") mod 14. If hash("abc") mod 14 = 9, it lands on primary 9 of that day's index. Doubling to 28 primaries tomorrow is easy, because tomorrow is a new index; changing today's index would need a split or re-index.
Step 4, vector memory. The 10 million articles have 768-dimension float embeddings, indexed with Faiss HNSW and M = 16. The plugin's estimate is 1.1 × (4 × 768 + 8 × 16) = 1.1 × 3,200 = 3,520 bytes per vector, so 10,000,000 × 3,520 ≈ 35 GB, or 70 GB with one replica. This memory lives outside the Java heap, and by default the plugin may use at most half of the remaining RAM. On 64 GB nodes with a 31 GB heap, each node offers about 16 GB for vectors, so 70 GB needs about 5 nodes just for the graphs.
Step 5, quantization. With 8-bit scalar quantization each vector takes 768 bytes instead of 3,072: 1.1 × (768 + 128) ≈ 986 bytes, about 9.9 GB, or 20 GB with the replica. With binary quantization (1 bit per dimension, 96 bytes) it is 1.1 × (96 + 128) ≈ 246 bytes, about 2.5 GB, and full-precision vectors on disk are used to rescore the top candidates. The trade is recall: measure recall at 10 against exact search on a sample before choosing.
intuition: OpenSearch is a library of identical card catalogues, one per room: a clerk at the front sends each question to every room and merges the best answers they send back.
The design is natural because search work splits cleanly. Documents are independent, so you can put any document in any shard; a query is just "ask every shard, then merge the top results", and merging sorted lists of 10 is cheap. Lucene already makes each shard fast and consistent on one machine, so the distributed layer only has to decide where shards live, keep copies, and survive failures. The translog adds durability without slowing every write to a Lucene commit, and the one-second refresh is the compromise that makes data "almost immediately" searchable without creating a new segment for every document. Vectors fit the same pattern: each shard returns its nearest neighbours, and the coordinator keeps the best.
mistakes: People often think OpenSearch and Elasticsearch are still the same product. In fact they have diverged for five years. APIs are similar for basic indexing and search, but plugins, security, vector features, query languages and client libraries differ, and newer Elasticsearch clients may reject OpenSearch clusters. Test a migration as a real migration.
People often think more shards always mean more parallelism. In fact each shard has fixed costs in heap, file handles and cluster-state size, and a query must visit every shard. Thousands of tiny shards make a cluster slow and unstable; shards of tens of gigabytes are usually better.
People often think an acknowledged write is immediately searchable. In fact it becomes searchable only after the next refresh (up to one second by default), although a get by ID can read it from the translog. Tests that write and then search at once will sometimes fail.
People often think vector search runs inside the Java heap. In fact Faiss graphs are native memory, limited by a circuit breaker to a share of the RAM left after the heap. Sizing only the heap leads to out-of-memory errors or evicted graphs and slow queries.
friction: Operating a large cluster takes skill. Shard counts, heap size, disk watermarks, refresh intervals and mapping explosions (thousands of dynamically created fields) are common causes of trouble. A hot shard, one that receives much more traffic than others because of routing or a popular tenant, can slow the whole cluster. The cluster state is held in memory on every node, so very large numbers of indexes or fields make updates to it slow.
Resharding is coarse. The primary count is fixed per index, so growth is handled by new indexes, rollover or split operations, all of which need planning. Deep pagination is expensive because each shard must return from + size results; use search_after or point-in-time instead.
Aggregations are approximate in places (terms buckets across shards, cardinality with HyperLogLog), and joins are not really supported; OpenSearch is not a warehouse. Storing months of logs on hot nodes is expensive, so most teams add warm and cold tiers, searchable snapshots or a separate lake, which adds complexity.
Vector search at scale is memory-heavy and rebuild-heavy: merges must rebuild graphs, which uses CPU and can cause latency spikes, which is why GPU index builds and quantization arrived. Finally, the Elasticsearch split costs the ecosystem: tools, tutorials and Stack Overflow answers often target Elasticsearch, and the details no longer match.
practice: Plan shards from data size: aim for 10 to 50 GB per shard (smaller for search-heavy indexes, larger for logs), and use rollover with ISM so that each index has a sensible size and old indexes can be deleted cheaply. Give the JVM at most half of the node's RAM and no more than about 31 GB, so that compressed object pointers stay enabled and the page cache and vector graphs have room.
Define mappings explicitly. Use keyword fields for IDs and exact filters, text fields only where you need full-text search, and turn off dynamic mapping for log sources that can create unbounded field names. For bulk loads, use the _bulk API with requests of a few megabytes, raise refresh_interval to 30 seconds or disable it during the load, and set replicas to 0 until the load ends. Consider segment replication for write-heavy indexes, and remote-backed storage when you want durability from object storage.
For vectors, start with Faiss HNSW, estimate memory with 1.1 × (4 × d + 8 × M) bytes per vector, and try 8-bit or binary quantization with rescoring if memory is the limit. Measure recall against exact search on a sample, and use hybrid search with score normalization or RRF when exact keywords matter, such as product codes. Monitor search latency percentiles, rejected thread-pool tasks, JVM heap, disk use and k-NN memory; set slow logs. When choosing between OpenSearch and Elasticsearch, compare the specific features you need, the managed service, and the license, rather than general benchmarks.
quiz: Why does OpenSearch exist as a separate project from Elasticsearch? || In 2021 Elastic moved Elasticsearch and Kibana from the Apache 2.0 license to SSPL and the Elastic License from version 7.11. AWS forked the last Apache-licensed version, 7.10.2, to keep an Apache-licensed engine, and the project now belongs to the OpenSearch Software Foundation under the Linux Foundation.
What do the translog and the refresh each provide, and why are they separate? || The translog is a write-ahead log that makes acknowledged writes durable between expensive Lucene commits. The refresh opens a new near-real-time Lucene reader so recent writes become searchable. Separating them lets writes be both safe and visible quickly without an fsync-heavy commit every second.
How does a search on an index with 5 primary shards and size 10 produce the global top 10? || The coordinating node sends the query to one copy of each of the 5 shards. Each returns the IDs and scores of its local top 10, the coordinator merges the 50 results into the global top 10, and then fetches those 10 documents from their shards.
Using the formula \( 1.1 \times (4 \times d + 8 \times M) \) bytes per vector, how much memory do 2 million 1,024-dimension vectors need with M = 16 and one replica? || Per vector: 1.1 × (4,096 + 128) = 1.1 × 4,224 ≈ 4,646 bytes. For 2 million vectors that is about 9.3 GB, and about 18.6 GB with one replica.
When would you choose segment replication over document replication? || When indexing CPU is the bottleneck, because only the primary analyzes and indexes documents and replicas copy finished segments. The cost is that replicas lag slightly behind the primary and more segment data crosses the network, so document replication fits better when replicas must be as fresh as possible.

@@ snowflake
value: Snowflake is a data warehouse sold as a cloud service. You load data, write SQL, and pay for storage and for the seconds your compute runs; there are no servers, indexes, vacuums or file layouts to manage. Its central design choice is to separate storage from compute. All table data lives once, in the cloud provider's object storage, and any number of independent compute clusters ("virtual warehouses") can read it at the same time. The finance team's month-end reports, the data science team's feature jobs and a customer-facing dashboard can each run on their own warehouse, against the same tables, without slowing each other down.
Before Snowflake, a warehouse was usually a fixed cluster (Teradata, Netezza, the first Redshift) in which storage and compute grew together. To get more concurrency you bought a bigger cluster and moved data into it; heavy loading jobs competed with reports; and an idle cluster at night still cost money. Snowflake turned those trade-offs into knobs: warehouse size for the speed of one query, number of clusters for concurrency, and auto-suspend so idle compute costs nothing. Features that were hard in fixed clusters, such as instant copies of a table (zero-copy cloning), querying the table as it was yesterday (Time Travel), and sharing live tables with another company without copying them, follow almost directly from the same design.
Snowflake stands on four concepts. AWS, GCP and Azure (L0) provide the object stores (S3, Google Cloud Storage, Azure Blob) where data lives and the virtual machines that compute runs on. Cloud computing (L1) provides the economic model of elastic, rented capacity, which makes per-second billing and start-in-seconds warehouses possible. Distributed SQL, or MPP (L1), gives the execution model: one query is split across the nodes of a warehouse, which scan, join and aggregate in parallel. The data warehouse concept (L1) gives columnar storage, SQL, star schemas and the analytics workload. For the layer above (dbt projects, BI tools such as Tableau and Power BI, reverse-ETL and ML pipelines), Snowflake is the SQL engine and the governed store.
terms: Micro-partition — an immutable file of 50–500 MB of uncompressed rows (much smaller compressed), stored column by column, the unit of storage and pruning.
Virtual warehouse — a named compute cluster with a T-shirt size; it reads micro-partitions, caches them on local SSD, and bills credits only while running.
Credit — Snowflake's unit of compute billing; an X-Small warehouse uses 1 credit per hour, and each size up doubles it.
Cloud services layer — the always-on control layer: authentication, metadata, query compilation and optimization, transactions and access control.
Pruning — skipping micro-partitions whose stored min/max values show they cannot match a filter.
Clustering key — the columns by which Snowflake keeps related rows in the same micro-partitions, maintained by a background service.
Time Travel — querying or restoring a table as it was at an earlier time, up to 1 day by default and up to 90 days on Enterprise edition.
Zero-copy clone — a new table, schema or database that points to the same micro-partitions as the original until either side changes.
Multi-cluster warehouse — a warehouse that adds identical clusters when queries queue, for concurrency rather than single-query speed.
history: Snowflake was founded in July 2012 by Benoît Dageville and Thierry Cruanes, two architects of Oracle's query engine, and Marcin Żukowski, co-founder of Vectorwise, a vectorized columnar engine from CWI Amsterdam. Their starting point was that the cloud changed the basic economics: object storage was cheap, durable and effectively unlimited, and compute could be rented by the second. A warehouse designed for the cloud from the start, instead of a fixed cluster moved onto cloud machines, could separate the two. The first product launched on AWS in June 2015, followed by Azure in 2018 and Google Cloud in 2019–2020.
The SIGMOD 2016 paper "The Snowflake Elastic Data Warehouse" (Dageville and many co-authors) described the three layers, micro-partitions, pruning, and how semi-structured JSON is stored in a VARIANT type with automatic columnar sub-columns. A 2020 NSDI paper, "Building An Elastic Query Engine on Disaggregated Storage" (Vuppalapati et al.), analysed millions of production queries and described the local caching and work-stealing that keep disaggregated storage fast.
Snowflake's IPO in September 2020 was the largest software IPO at the time. Bob Muglia led the company from 2014 to 2019, Frank Slootman from 2019 to 2024, and Sridhar Ramaswamy since February 2024. The 2020s moved Snowflake from "warehouse" toward "data platform": Snowpark for Python and Java code (2021–2022), hybrid tables for transactional rows, Apache Iceberg tables (generally available in 2024) and the open-sourced Polaris catalog, now Apache Polaris. In 2025 it released Gen2 standard warehouses on newer hardware, acquired Crunchy Data to offer managed PostgreSQL, and previewed Adaptive Compute, which removes warehouse sizing. Snowflake Postgres became generally available in February 2026, and Adaptive Compute is now generally available too.
how: The storage layer holds every table as a set of immutable micro-partitions in object storage. When you load data, Snowflake cuts it into micro-partitions of 50–500 MB uncompressed in arrival order, stores each column separately inside the file, and compresses it. For every micro-partition and every column, the cloud services layer records metadata: minimum and maximum value, number of distinct values, number of nulls. This metadata lives in a transactional key-value store (FoundationDB), not in the files, so the optimizer can use it before any data is read. The cloud object store contributes durability (eleven nines on S3) and unlimited capacity, but its latency is tens of milliseconds per request, so Snowflake must avoid reading what it does not need and cache what it reads.
A query starts in the cloud services layer, which parses it, checks access rights and optimizes it. Pruning happens here: for WHERE order_date = '2026-10-01', the optimizer reads the min/max metadata of every micro-partition of the table and keeps only the files whose range contains that date. If data arrived in date order, one day of a three-year table touches about 1/1,095 of the files; if dates are scattered randomly, it may touch all of them. That is why clustering matters. Snowflake measures "clustering depth", the number of overlapping micro-partitions for a value, and its automatic clustering service rewrites micro-partitions in the background to reduce it, billed as serverless compute. The services layer also keeps a result cache: an identical query on unchanged data within 24 hours returns the stored result without running a warehouse.
The plan then runs on a virtual warehouse, and this is where MPP comes in. A warehouse is a group of machines; the plan's operators (scan, filter, hash join, aggregate) run on all of them, and the micro-partition files to scan are spread across the nodes. Execution is columnar, vectorized and push-based: batches of column values flow from operator to operator. Joins and group-bys redistribute rows between nodes by hashing the key, as in any MPP engine, and small tables are broadcast instead. Nodes that finish early can steal scan work from slow ones. Each node caches the files it reads on local SSD, so a warehouse that runs similar queries repeatedly reads mostly from local disk instead of S3. Suspending a warehouse loses this cache, which is one of the real costs of aggressive auto-suspend.
Warehouse sizing follows cloud computing's elastic model. Sizes go from X-Small (1 credit per hour) to 6X-Large (512 credits per hour), doubling at each step. Doubling the size roughly doubles the resources, so a query that scales well runs in about half the time for the same total cost. Billing is per second, with a 60-second minimum each time a warehouse starts. Auto-suspend stops a warehouse after an idle period, and auto-resume starts it in seconds when a query arrives, so compute exists only when it is needed. A multi-cluster warehouse adds clusters when queries start to queue and removes them when the queue empties: it solves concurrency, not single-query speed. Adaptive Compute goes further: you set an upper performance level, and Snowflake sizes resources per query from a shared pool. The cloud services layer is billed only when its daily use exceeds 10% of the warehouse use.
Transactions use multi-version concurrency control on immutable files. An UPDATE, DELETE or MERGE does not change files; it writes new micro-partitions for the affected rows and commits a new table version in the metadata store, which lists the files that make up the table. Readers see a consistent snapshot. Old versions remain for the Time Travel period, so "SELECT ... AT (OFFSET => -3600)" reads the file list from an hour ago, and UNDROP restores a dropped table. After Time Travel, a 7-day Fail-safe period keeps data recoverable by Snowflake support. A clone copies only metadata: the new table points at the same files, and new files are written only when one side changes. Data sharing works the same way across accounts: the provider grants access to the metadata, and the consumer reads the same files with its own warehouse and pays for its own compute.
Beyond its own format, Snowflake can store tables as Apache Iceberg (Parquet files plus Iceberg metadata in your own bucket), so other engines such as Spark or Trino can read them, and can read Iceberg tables managed by external catalogs. Semi-structured data goes into VARIANT columns, where Snowflake extracts frequently used paths into hidden typed columns so they prune and compress like normal columns.

example: A retail company has a sales table of 3 years: 6 billion rows, 40 columns, 2 TB compressed. A dashboard asks for revenue by region for one month.
Step 1, number of files. Micro-partitions are stored compressed, often around 16 MB each. 2 TB / 16 MB = 2,000,000 MB / 16 MB = 125,000 micro-partitions, each holding about 6 billion / 125,000 = 48,000 rows.
Step 2, pruning. The data was loaded day by day, so order_date is naturally clustered. One month is about 1/36 of three years, so pruning keeps about 125,000 / 36 ≈ 3,500 files. If the table had been loaded in random date order, almost every file would contain some date from that month and almost nothing would be pruned.
Step 3, column pruning. The query needs 3 columns (order_date, region, amount) of 40. If columns are roughly equal in size, it reads 3/40 of each file: 3,500 × 16 MB × 3/40 ≈ 4.2 GB, instead of 2 TB. That is about 475 times less data.
Step 4, compute. On a Medium warehouse (4 credits per hour), suppose the query takes 20 seconds. Its compute cost is 4 × 20 / 3,600 ≈ 0.022 credits; at an example price of $3 per credit, about 7 cents.
Step 5, the idle-time trap. The dashboard refreshes every 5 minutes, all day. With the default auto-suspend of 10 minutes, the warehouse never becomes idle long enough to suspend, so it bills 24 hours × 4 credits = 96 credits per day, about $288 per day or $8,600 per month, for less than two hours of real work. With auto-suspend set to 60 seconds, each 5-minute cycle bills 20 seconds of work plus 60 seconds of idle time, 80 seconds in total. That gives 288 cycles × 80 s = 23,040 s = 6.4 hours, or 6.4 × 4 = 25.6 credits per day, about $77 per day. The price is a cold SSD cache on each resume, which may make each query a little slower.
Step 6, better still: the result cache. If the underlying table changes only once an hour, 11 of every 12 refreshes return the cached result with no warehouse at all, cutting compute by more than 90%.
intuition: Snowflake is a shared pantry with rented kitchens: the food is stored once, every team rents its own kitchen by the second, and nobody waits for someone else's stove.
The design is natural once you take the cloud's prices seriously. Object storage is cheap and durable but slow per request; compute is expensive per hour but can be created and destroyed in seconds. So keep one copy of the data in the cheap durable place, keep enough metadata in a fast database to know which files matter, and bring compute to the data only when a query needs it. Immutability ties it together: files that never change can be cached on any node, shared with any account, kept for Time Travel, and pointed at by a clone, all without copying or locking. The cost model then becomes simple to reason about: you pay once for bytes stored, and separately for seconds of compute, so the question "how fast should this be?" turns into "how many credits per hour am I willing to spend?".
mistakes: People often think a bigger warehouse always costs more. In fact cost is credits per hour times hours. A query that scales well finishes in about half the time on a warehouse twice as large, so its cost stays about the same while it finishes faster. Bigger warehouses waste money only on queries that do not parallelize, or when idle time dominates.
People often think multi-cluster warehouses make single queries faster. In fact they add identical clusters to serve more queries at once. To make one heavy query faster, increase the size, not the number of clusters.
People often think Snowflake needs no physical design. In fact pruning depends entirely on how rows are spread across micro-partitions. Large tables filtered on a column that does not follow load order need a clustering key or a different load order, and automatic clustering itself costs credits.
People often think Time Travel is a backup. In fact it is limited to at most 90 days, and Fail-safe is recoverable only through Snowflake support. Accidental damage that is noticed late, or an account-level problem, needs separate replication or exports.
friction: Cost is the main friction, and it comes from idle time and from features that run in the background: warehouses that never suspend, multi-cluster warehouses that scale out for a queue of small queries, automatic clustering, materialized view maintenance, search optimization, serverless tasks and AI functions all spend credits. Without resource monitors, budgets and tagging, monthly bills are hard to explain and easy to grow.
Control is limited by design. You cannot choose join algorithms, inspect the hardware, or tune memory per operator; the query profile is the main tool. Spilling to local disk and then to remote storage, when a join or sort exceeds memory, can make a query many times slower, and the fix is usually a larger warehouse or a rewritten query.
The native storage format is proprietary. Other engines cannot read native tables directly, so lock-in is real unless you use Iceberg tables, which in turn have their own feature differences. Point lookups and many small updates are slow compared with an OLTP database, because every change writes new micro-partitions; hybrid tables and Snowflake Postgres exist because the core engine is not an operational store. Very fresh data (seconds) needs Snowpipe Streaming or dynamic tables, and still has more latency than a real-time OLAP engine such as Druid or ClickHouse. Finally, cloud-provider egress charges apply when data leaves the region.
practice: Separate workloads by warehouse: loading, transformation (dbt), BI and data science each get their own, sized for their queries, so that costs can be attributed and one workload cannot starve another. Set auto-suspend to 60 seconds for bursty workloads and longer only where a warm cache clearly pays for itself. Put resource monitors and budgets on every warehouse, and tag queries and warehouses by team.
Make pruning work. Load large tables in the order of their main filter (usually time), check clustering with SYSTEM$CLUSTERING_INFORMATION, and add a clustering key only to large tables (over about 1 TB) with selective filters on another column. Avoid wrapping filter columns in functions that defeat pruning, and avoid SELECT *. Read the query profile for "partitions scanned versus total", spilling, and exploding joins; these three explain most slow queries.
Use Time Travel and zero-copy clones for safe development: clone production into a dev database in seconds and test transformations against it. Use secure data sharing instead of file exports when another account needs live data. Choose Iceberg tables when other engines must read the same data or when an open format is a requirement. Review the most expensive queries and warehouses every week, using the ACCOUNT_USAGE views such as QUERY_HISTORY and WAREHOUSE_METERING_HISTORY.

@@ bigquery
value: Google BigQuery is a serverless data warehouse. You never create a cluster: you load or stream data into tables, run SQL, and Google decides at query time how many workers to use, possibly thousands. You pay either per byte your queries scan (on-demand) or per "slot-hour" of reserved or autoscaled compute (editions), plus storage. A query over terabytes usually finishes in seconds to a minute, and the same SQL works for a 10 MB table and a 10 PB table.
This matters because the hardest part of running a warehouse is often not SQL but capacity: sizing clusters, choosing node types, handling the Monday-morning peak and paying for idle machines at night. BigQuery moves that problem to Google, which can pool spare capacity across many customers. The price is a different set of trade-offs: little control over execution, and a cost model in which a careless query can scan, and bill, far more data than needed.
BigQuery stands on four concepts. AWS, GCP and Azure (L0) supply the hardware platform, here Google Cloud's internal systems: Colossus (the distributed file system that stores table data), Borg (the cluster manager that runs the workers) and Jupiter (the data-centre network, fast enough that reading data from remote storage is not a bottleneck). Cloud computing (L1) supplies the elastic, pooled capacity that makes per-query allocation and per-second billing possible. Distributed SQL, or MPP (L1), supplies the execution model of splitting one query into stages that run on many workers in parallel. The data warehouse concept (L1) supplies columnar storage, SQL and the analytics workload. For the layer above (Looker and other BI tools, dbt projects, ML pipelines in Vertex AI, ad-hoc analysts), BigQuery is the place where data is stored, governed and queried with no infrastructure to run.
terms: Dremel — Google's internal interactive query engine, the execution engine behind BigQuery.
Slot — BigQuery's unit of compute: a share of CPU, memory and network that runs part of a query; queries use many slots at once.
Capacitor — BigQuery's columnar file format for table data, stored on Colossus.
Shuffle — the step that redistributes intermediate rows between query stages; BigQuery keeps it in a separate, in-memory distributed service.
On-demand pricing — paying per TiB of data read by each query, with the first 1 TiB per month free.
Editions — the capacity-based pricing model (Standard, Enterprise, Enterprise Plus): you pay per slot-hour for reserved or autoscaled slots.
Partitioned table — a table split by a date, timestamp or integer column (or by ingestion time), so filters on that column skip whole partitions.
Clustered table — a table whose rows are sorted within storage blocks by up to four columns, so filters on them skip blocks.
Logical and physical bytes — logical bytes are the uncompressed size used for on-demand billing; physical bytes are the compressed size on disk, one of two storage billing options.
history: Dremel began in 2006 as a "20 percent" project by Andrey Gubarev at Google. Engineers needed to explore huge datasets (web crawl data, logs, ads data) interactively, and MapReduce jobs took minutes to hours. Dremel ran SQL-like queries over nested data in seconds, using a columnar format and a tree of servers that pushed work down to many leaves. The VLDB 2010 paper "Dremel: Interactive Analysis of Web-Scale Datasets" by Melnik, Gubarev, Long, Romer, Shivakumar, Tolton and Vassilakis described it. Its method for storing nested records in columns, with "repetition levels" and "definition levels", was later adopted by Apache Parquet.
BigQuery, the public service built on Dremel, was announced at Google I/O in May 2010 and opened to general use in 2011–2012. Inside Google the architecture kept changing, as described in "Dremel: A Decade of Interactive SQL Analysis at Web Scale" (VLDB 2020). Dremel moved onto shared Borg clusters in 2009 and from local disks to the distributed file system (GFS, then Colossus), which separated storage from compute. A disaggregated shuffle came in 2012, and in 2014 the team settled on an in-memory shuffle service, which cut shuffle latency about 10 times, allowed shuffles about 10 times larger, and reduced resource cost by over 20%. Capacitor replaced the original columnar format from 2014. Standard SQL (now GoogleSQL) replaced the old SQL dialect from 2016; use of legacy SQL has been restricted since June 2026.
Commercial features followed: BigQuery ML for training models with SQL (2018), BigQuery Omni for querying data in AWS and Azure (2020), and in 2023 the editions pricing model, with the on-demand price raised from $5 to $6.25 per TiB. Recent years focused on open formats, speed and AI. BigQuery-managed Apache Iceberg tables became generally available in June 2025; the "advanced runtime", an improved vectorized execution engine, became generally available in September 2025 and the default for all projects in March 2026; BigLake was renamed Google Cloud Lakehouse in April 2026; and fluid scaling, per-second autoscaling with no minimum, became generally available in June 2026.
how: Table data is stored in Capacitor files on Colossus, column by column, compressed, and replicated across zones of a region. Each column is encoded with dictionaries and run-length encoding where useful, and rows inside files may be reordered to compress better; the Dremel team reported 17% average savings from reordering alone. Metadata records each file's partition and the ranges of clustered columns, so the planner can skip files before reading them. Because Colossus serves data to any machine over Jupiter's very high-bandwidth network, any worker in the region can read any part of any table. This is the cloud layer's main contribution: storage that is shared, durable and fast enough to read remotely, so compute does not need to own data.
A query is parsed and optimized into a plan of stages, a directed acyclic graph (DAG) of distributed SQL steps. The first stages scan: each worker reads a slice of the needed columns from Colossus, applies filters, and computes partial aggregates or partial join inputs. It writes its output, partitioned by a key, to the shuffle tier, a separate in-memory service. The next stage's workers each read one partition from the shuffle, finish aggregations or joins, and write to the next shuffle. The last stage produces the result. This is MPP, but with a twist: because intermediate data lives in the shuffle service rather than on the workers, a stage can be re-run, its workers changed, or its parallelism adjusted without losing data. The original Dremel described this as a fixed "serving tree" (root, intermediate servers, leaves); the modern engine keeps the tree idea for aggregations but runs general DAGs.
Execution is dynamic. The scheduler hands out slots to stages as they become ready, and each stage can grow or shrink its number of workers. If one side of a join turns out to be small, the plan switches from a shuffle (hash) join to a broadcast join at runtime. History-based optimizations, on by default since 2025, reuse statistics from earlier runs of similar queries to choose better plans. Slow workers (stragglers) can have their work split and given to others. Many queries from many customers share the same pool, and the fair scheduler divides slots among them; this is the cloud computing idea of pooled, elastic capacity applied inside one service.
Pricing follows two models. On-demand charges $6.25 per TiB of logical bytes read from the columns a query references, after the first 1 TiB per month, with a minimum of 10 MB per table. Only the columns you select count, and partition and clustering pruning reduce the bill; a LIMIT clause does not, because the scan still reads the columns. With editions, you buy slots: a baseline that is always on, plus autoscaling up to a maximum, billed per slot-hour ($0.04 Standard, $0.06 Enterprise, $0.10 Enterprise Plus in US regions, less with one- or three-year commitments). Under editions, queries cost slot time rather than bytes, so a scan-heavy but simple query can be cheap and a light but CPU-heavy query can be expensive. Results of identical queries on unchanged data are cached for 24 hours at no charge.
Data layout is the user's main lever. Partitioning by a date column creates one partition per day (or hour, month or year), and a filter on that column means the other partitions are never read and never billed. Clustering sorts data within partitions by up to four columns and lets BigQuery skip storage blocks whose value ranges do not match; BigQuery re-clusters in the background at no charge as new data arrives. For clustered tables, the dry-run estimate is an upper bound, and the bill reflects the blocks actually skipped.
Writes go through the Storage Write API (or older streaming inserts and batch load jobs). Streamed rows are written first to a write-optimized store, are queryable within seconds, and are later converted to Capacitor files in the background. The Write API supports exactly-once delivery by tracking offsets per stream. Data Manipulation Language (UPDATE, DELETE, MERGE) rewrites the affected files, and every change is kept for time travel (two to seven days, seven by default), followed by a seven-day fail-safe period. In the other direction, the Storage Read API lets external engines such as Spark read table data directly, in parallel streams of Arrow or Avro rows, without running a SQL query.

example: An ad platform keeps 3 years of impression events in one table: 1,095 daily partitions and 60 TiB of logical data across 80 columns. A customer dashboard runs "SELECT SUM(revenue) FROM events WHERE event_date >= last 30 days AND advertiser_id = 'A17'", 10,000 times a month. The three referenced columns (event_date, advertiser_id, revenue) hold 6 TiB in total.
Case A, no pruning. If the date filter is written in a way that cannot prune (for example on a column the table is not partitioned by), the query reads all 6 TiB of the three columns. On-demand cost per run: 6 × $6.25 = $37.50. Per month: 10,000 × $37.50 = $375,000.
Case B, partition pruning. With the table partitioned by event_date, 30 of 1,095 partitions are read: 6 TiB × 30 / 1,095 ≈ 0.164 TiB, about 168 GiB. Cost per run: 0.164 × $6.25 ≈ $1.03. Per month: about $10,300.
Case C, clustering. With the table also clustered by advertiser_id, rows of A17 sit in a few blocks of each partition. If A17 is 0.5% of rows and boundary blocks bring the read to about 2% of each partition, the query reads 0.164 TiB × 0.02 ≈ 0.0033 TiB, about 3.4 GiB. Cost per run: about $0.02. Per month: about $205. The SQL is the same in all three cases; only the table design changed, and the bill fell by a factor of about 1,800.
Case D, capacity pricing. Instead of on-demand, the team could buy 200 baseline slots on Enterprise edition: 200 slots × 730 hours × $0.06 = $8,760 per month, for all queries of the project. That is cheaper than case B but far more expensive than case C. Capacity pricing pays off when many queries scan a lot of data, and on-demand pays off when good layout keeps scans small.
Storage. The 60 TiB of logical data is 61,440 GiB; at about $0.023 per GiB-month for active logical storage, that is about $1,400 per month (long-term storage after 90 days without changes is cheaper). If the data compresses 6 times, the physical size is about 10 TiB, or 10,240 GiB at about $0.04 per GiB-month, about $410 per month. Physical billing wins when the compression ratio is above about 0.04 / 0.023 ≈ 1.7, but it also charges for bytes kept for time travel and fail-safe, so tables with heavy updates gain less.
intuition: BigQuery is a public library with ten thousand readers on call: you hand in a question, they each read one shelf and pass notes back, and you pay either for the shelves read or for the readers' time.
The design is natural at Google's scale. If you own enormous, shared storage and a network fast enough to read from it anywhere, there is no reason to tie data to particular machines. Then compute can be treated as a pool, given to whichever query needs it now and taken back a second later. Pulling the shuffle out of the workers into its own memory service is the same idea applied again: once intermediate data does not belong to a worker, workers become interchangeable, and the engine can change its plan while the query runs. For the user, the result is that capacity planning disappears, and the remaining job is to make queries read as little as possible.
mistakes: People often think LIMIT makes a query cheaper on on-demand pricing. In fact the bill counts the bytes of the referenced columns that are scanned, and LIMIT only cuts the result. To scan less, select fewer columns and filter on partition and clustering columns.
People often think serverless means no tuning. In fact partitioning, clustering, column choice and query shape decide cost and speed. A dashboard over an unpartitioned table can cost thousands of times more than the same dashboard over a well-designed one.
People often think SELECT * on a big table is harmless because results are previewed. In fact a query that references all columns is billed for all of them, even if you look at ten rows. Use the table preview, or select only the columns you need.
People often think slots are machines. In fact a slot is an abstract unit of compute shared by Google's scheduler; a query's slot count changes stage by stage, and many queries share slots. Reserving 100 slots does not give you 100 dedicated servers.
friction: Cost control is the main friction. On-demand pricing makes every analyst's query a spending decision, and one bad query on a petabyte table costs thousands of dollars. Teams must set per-user or per-project byte quotas, require partition filters on large tables, and watch the INFORMATION_SCHEMA.JOBS view. Capacity pricing brings a different problem: choosing baselines, autoscaling limits and commitments, and accepting slower queries when slots are scarce.
Control is limited. You cannot pick machine types, force a join algorithm in most cases, or keep data in memory on purpose; the query plan and execution graph in the console are the main tools. Very low-latency workloads (tens of milliseconds, high concurrency) fit better in BI Engine, a cache, or a real-time OLAP store than in core BigQuery, whose overhead per query is typically hundreds of milliseconds or more.
Row-level changes are relatively expensive: UPDATE, DELETE and MERGE rewrite files and are subject to DML concurrency limits, so BigQuery is not a transactional database. Streaming has its own costs and quotas. Data and compute are tied to a region, so cross-region joins need copies or replication, and moving data out of Google Cloud costs egress. Proprietary storage creates lock-in, which open Iceberg tables now reduce. Finally, recent features arrive quickly and some are tied to specific editions, so the same SQL may behave or bill differently across projects.
practice: Design every large table with partitioning on the main time column and clustering on the most common filter columns (up to four, the most selective or most often filtered first). Set "require partition filter" on large partitioned tables, and set partition expiration for data you do not need forever. Always dry-run large queries to see bytes processed before running them, and set maximum bytes billed on scheduled and ad-hoc queries.
Choose the pricing model from your workload, not from habit. Look at INFORMATION_SCHEMA.JOBS for total bytes scanned and total slot-milliseconds per month, and compare on-demand cost with slot cost; many companies use editions for production pipelines and on-demand for light exploratory projects. With editions, start with a small baseline and autoscaling, and use reservations and assignments to separate ETL from dashboards.
Pre-aggregate expensive dashboard queries with materialized views or scheduled summary tables, and use BI Engine for sub-second dashboards on small hot tables. Prefer the Storage Write API for streaming, with batching and exactly-once offsets where duplicates matter. For storage, compare logical and physical billing per dataset using the TABLE_STORAGE view; switch to physical when compression is high and updates are few. Use Iceberg managed tables when other engines such as Spark need to read and write the same data.

@@ redshift
value: Amazon Redshift is AWS's managed data warehouse: a massively parallel (MPP), columnar SQL database that runs analytics over terabytes to petabytes. It comes in two forms. Provisioned clusters are a fixed number of nodes you choose and pay for by the hour. Redshift Serverless sizes compute automatically in "RPUs" and bills only while queries run. Both speak a PostgreSQL-like SQL dialect, so most BI tools, ETL tools and drivers connect to it unchanged.
When it launched in 2013, Redshift changed who could have a data warehouse. Teradata, Netezza and Oracle Exadata required large up-front purchases; Redshift could be started in minutes, at a price per terabyte far below the appliances. Many companies built their first real warehouse on it, and it remains common in organizations whose data already lives in AWS: in S3, in Aurora and DynamoDB, in Kinesis and MSK streams.
Redshift stands on four concepts. AWS (L0) supplies the EC2 machines it runs on and S3, which holds its backups and, since RA3 nodes, the master copy of the data itself. Cloud computing (L1) supplies rented, resizable capacity, which made the warehouse a service rather than a purchase, and later serverless billing. Distributed SQL, or MPP (L1), gives the core design: rows are spread across nodes and slices, and every query runs in parallel on all of them, with data moved between nodes only when a join or aggregation needs it. The data warehouse concept (L1) gives columnar storage, compression, star schemas and the analytical workload. The main thing to understand about Redshift, compared with Snowflake or BigQuery, is that it exposes more of the MPP machinery to the user: distribution keys, sort keys and workload queues are yours to choose, and those choices decide performance.
terms: Leader node — the node that accepts connections, parses and optimizes SQL, compiles the plan into code, and coordinates the compute nodes.
Compute node and slice — compute nodes store data and run the plan; each is divided into slices, each with its own share of memory, CPU and data.
Distribution style — how rows of a table are spread across slices: KEY (by hash of a column), EVEN (round robin), ALL (full copy on every node) or AUTO.
Sort key — the column order in which rows are stored on disk; it makes zone maps effective for range filters.
Zone map — the minimum and maximum value of each 1 MB block of a column, kept in memory, used to skip blocks.
RA3 and Redshift Managed Storage (RMS) — the node family whose data lives durably in S3, with local SSDs acting as a cache.
RPU — Redshift Processing Unit, the serverless unit of capacity, with 16 GB of memory each.
Workload management (WLM) — the queues, memory shares and priorities that decide which queries run at once.
Concurrency scaling — temporary extra clusters that AWS adds to absorb bursts of queries.
history: AWS announced Redshift at its first re:Invent conference in November 2012 and made it generally available in February 2013. Instead of writing an engine from scratch, AWS licensed technology from ParAccel, a company that had built an MPP columnar database, and put a front end derived from PostgreSQL 8.0.2 on it. That is why PostgreSQL drivers work, and also why many PostgreSQL features (some data types, indexes, triggers) do not. AWS advertised costs of under $1,000 per terabyte per year with reserved nodes, a fraction of appliance prices. A 2015 SIGMOD paper, "Amazon Redshift and the Case for Simpler Data Warehouses", explained that the goal was not a new database technique but removing the cost and effort of buying and running one.
The first generations coupled storage and compute: data lived on the nodes' local disks, so more data meant more nodes. Over the next years AWS removed limits one by one. Redshift Spectrum (2017) queried files in S3 with a separate fleet. Concurrency scaling (2019) added transient clusters for bursts. RA3 nodes (December 2019) moved the master copy of data to Redshift Managed Storage on S3, with local SSDs as a cache, so storage and compute could finally grow separately. Data sharing let several clusters read the same data without copying. Redshift Serverless became generally available in July 2022. The SIGMOD 2022 paper "Amazon Redshift Re-invented" (Armenatzoglou et al.) described this evolution: code generation and a compilation service, managed storage, AQUA (a hardware-accelerated scan layer), and machine-learning-based "autonomics" that choose sort keys, distribution and vacuuming automatically.
Recent work has focused on integration and less tuning: zero-ETL replication from Aurora, RDS and DynamoDB (from 2023), streaming ingestion from Kinesis and Kafka, writes from multiple warehouses through data sharing, AI-driven scaling for Serverless, multidimensional data layout (MDDL) sort keys that adapt to query filters (September 2025), and UPDATE, DELETE and MERGE on Apache Iceberg tables (March 2026). Python UDFs reached end of support after June 30, 2026, in favour of Lambda UDFs.
how: A cluster has one leader node and several compute nodes, and each compute node is split into slices (for example 4 slices on an ra3.4xlarge). When you load a table, each row is assigned to a slice by its distribution style. With DISTSTYLE KEY, the slice is chosen by hashing the distribution column, so all rows with the same customer_id are on the same slice. With EVEN, rows go round robin. With ALL, every node gets a full copy, which suits small dimension tables. AUTO lets Redshift choose and change the style as the table grows. This is MPP in its classic shared-nothing form: each slice owns a part of the data, and a query is fast when every slice can do its share of the work alone.
Within a slice, each column is stored in 1 MB blocks, compressed with an encoding chosen per column (AZ64 for numbers and dates, ZSTD or LZO for text, run-length and delta encodings, dictionary encodings for low-cardinality values). Rows are kept in sort key order. For every block, Redshift keeps a zone map, the block's minimum and maximum value, in memory. A filter such as sale_date >= '2026-09-01' checks the zone maps and reads only blocks whose range overlaps the filter. If the table is sorted by sale_date, the matching blocks are a small contiguous set; if not, almost every block overlaps and nothing is skipped. New rows are appended to an unsorted region, which is why sorting maintenance (VACUUM SORT, now mostly automatic) still exists.
The leader node parses and optimizes each query, then generates C++ code for the plan's segments and compiles it to machine code. Compiled code avoids the overhead of interpreting operators row by row. Compilation takes time, so Redshift caches compiled objects and uses a compilation service outside the cluster, so most queries reuse code compiled earlier. The compute nodes execute the plan in parallel, slice by slice, and the leader combines the final results. Execution is late-materializing: a scan first evaluates filters on the filter columns, and only for surviving rows reads the other columns the query needs.
Joins show why distribution matters. If two tables are distributed on their join column, matching rows are already on the same slice, and the join runs locally with no network traffic (EXPLAIN shows DS_DIST_NONE). Otherwise Redshift must move data: broadcast the smaller table to every node (DS_BCAST_INNER), redistribute one side by the join key (DS_DIST_INNER or DS_DIST_OUTER), or redistribute both (DS_DIST_BOTH). Moving tens of gigabytes across the network for every query is the most common cause of slow Redshift queries. A typical star schema distributes the large fact table and its largest dimension on the same key, and uses DISTSTYLE ALL for small dimensions.
RA3 nodes add the cloud storage layer. The master copy of every block lives in Redshift Managed Storage, backed by S3, and the local SSDs hold a cache of hot blocks, managed by access frequency. A cluster can therefore hold far more data than its local disks, and snapshots are cheap because data is already in S3. Data sharing builds on this: a consumer cluster or serverless workgroup can read the producer's tables live, using its own compute, and recent versions allow several warehouses to write to shared databases.
Elasticity comes in several forms, each from the cloud computing toolbox. Elastic resize changes the number of nodes in minutes. Concurrency scaling adds temporary clusters when queries queue; each cluster earns one free hour of it per day. Workload management divides memory and concurrency between queues and gives short queries a fast lane. Redshift Serverless hides nodes entirely: a workgroup has a base capacity from 4 to 512 RPUs (1,024 in some regions), scales up for heavy queries, and bills per RPU-second (about $0.375 per RPU-hour in US East) with a 60-second minimum.
Changes follow a delete-and-append model. A DELETE marks rows as deleted; an UPDATE marks the old row deleted and appends a new one. Space is reclaimed and order restored by VACUUM, which now runs automatically in the background, and ANALYZE keeps optimizer statistics fresh, also mostly automatic. Transactions are serializable. Spectrum and Iceberg support extend queries to open files in S3, and zero-ETL integrations replicate operational databases into Redshift tables within seconds to minutes without pipelines.

example: A retailer has a fact table sales with 6 billion rows over 3 years and a customers dimension with 50 million rows. The cluster has 4 ra3.4xlarge nodes, 16 slices in total. The report is "revenue by customer segment for last month".
Step 1, zone maps. The amount column is 6 billion × 8 bytes = 48 GB uncompressed; with 3× compression about 16 GB, or 16,000 blocks of 1 MB. If sales is sorted by sale_date, one month is about 1/36 of the table, so the query reads about 16,000 / 36 ≈ 445 blocks of that column instead of 16,000. The same happens for the other two columns the query needs (customer_id and sale_date). After this filter, about 6 billion / 36 ≈ 167 million fact rows remain.
Step 2, a collocated join. If both sales and customers use DISTKEY customer_id, each slice holds about 167 million / 16 ≈ 10.4 million of last month's fact rows and about 50 million / 16 ≈ 3.1 million customers, and every fact row's customer is on the same slice. Each slice builds a hash table of its 3.1 million customers and probes it with its 10.4 million fact rows. No data crosses the network.
Step 3, the wrong key. Suppose instead sales uses DISTSTYLE EVEN. Now a fact row's customer is usually on another node. Redshift can redistribute the 167 million filtered fact rows by customer_id: at about 20 bytes per row (customer_id, amount, sale_date) that is about 3.3 GB, and with 4 nodes about three quarters of it, 2.5 GB, crosses the network. Or it can broadcast the customers table: 50 million rows × about 28 bytes (customer_id and segment) ≈ 1.4 GB copied to each of the 4 nodes. Either way the query moves gigabytes before it can join, and that movement, plus the extra memory for hash tables, can turn a 5-second query into a 30-second one. Running the same report many times a day multiplies the cost.
Step 4, cost. Four ra3.4xlarge nodes at about $3.26 per hour each cost $13.04 per hour, about $9,500 per month if they run all the time (730 hours), plus managed storage at about $0.024 per GB-month. If the warehouse is busy only 6 hours a day, Redshift Serverless with a 32-RPU base costs 32 × $0.375 = $12 per hour while running, so about 6 × 30 × $12 = $2,160 per month. For an always-busy warehouse, provisioned nodes with reserved pricing usually win; for bursty use, serverless wins.
intuition: Redshift is a warehouse with many loading docks: if each order's items are already stored at the same dock as its customer file, every dock works alone; if not, forklifts must carry boxes across the building first.
That picture explains the design. An MPP system is fast when the work splits into independent pieces, and in a warehouse the expensive pieces are joins and aggregations on keys. Putting rows with the same key on the same slice turns a distributed join into many small local joins. Sorting by the main filter column, and keeping a tiny min/max summary per block, turns a filter into skipping most of the disk. Compiling the plan to native code removes interpreter overhead from the remaining work. Every later change, from managed storage on S3 to serverless, keeps this core and removes the parts of operations that customers found hardest. What stays with the user is the one decision the engine cannot easily guess: which keys the important queries join and filter on.
mistakes: People often think distribution keys only affect storage balance. In fact they decide whether joins run locally or move data across the network. A key with good balance but the wrong join column can make every query slower; check EXPLAIN for DS_BCAST and DS_DIST steps.
People often think Redshift is PostgreSQL, because the protocol and much of the syntax are the same. In fact it is a different engine: no general indexes, no foreign-key enforcement, different data types and functions, and very different performance rules. Advice written for PostgreSQL often does not apply.
People often think adding nodes fixes a slow query. In fact a query that broadcasts a large table, or that skews most rows onto one slice because of a bad distribution key, stays slow or gets worse. Fix data movement and skew first.
People often think Serverless means no design work. In fact sort keys and distribution still matter, because the same engine runs underneath; Serverless removes node sizing, not table design.
friction: Tuning is the classic friction. Distribution and sort keys must match the main queries, and when workloads change, the keys must change too, which rewrites tables. Automatic table optimization, AUTO distribution and MDDL sort keys reduce this, but they act on observed workloads and may lag behind new ones. Skew, when one slice holds much more data than others, makes the whole query wait for that slice.
Concurrency has limits. Each query reserves memory from a queue, and many small queries can wait behind a few large ones. Concurrency scaling and Serverless help, but they add cost, and concurrency scaling does not cover every kind of query.
Updates and deletes are expensive: they leave deleted rows and unsorted regions behind until VACUUM runs, and frequent small updates fit poorly. Redshift is also not a low-latency serving store; very high-concurrency dashboards may need caching or a real-time OLAP engine.
The provisioned model ties cost to node hours, so idle clusters cost money unless you pause them, while the serverless model makes cost depend on RPU-seconds, which is harder to predict for heavy workloads. Feature differences between provisioned and serverless, and between Redshift's SQL and PostgreSQL, still surprise teams. Finally, choosing between Redshift, Snowflake, BigQuery and a lakehouse such as Databricks is often decided less by speed than by where data already lives and which ecosystem a team knows.
practice: Start with AUTO distribution and AUTO sort keys, then measure. For the biggest fact table, choose a DISTKEY that is both well balanced and the most common join column, and give its biggest dimension the same key; use DISTSTYLE ALL for small dimensions (up to a few million rows). Use the main time column as the leading sort key for event and fact tables, or let MDDL sort keys adapt to filters.
Read EXPLAIN plans and the SVL and SYS system views for data movement (DS_BCAST_INNER, DS_DIST_BOTH), skew, and disk-based (spilled) steps. Keep column encodings at their defaults (AZ64 and ZSTD), and avoid very wide VARCHAR columns, which waste memory during queries.
Load with COPY from S3 in parallel, using many files of similar size (at least one per slice, ideally a multiple of the slice count), not with single-row INSERTs. Use auto WLM with query priorities, turn on short query acceleration, and enable concurrency scaling for read-heavy peaks with a usage limit. Pause provisioned clusters that are idle at night, or move bursty workloads to Serverless with a base capacity and maximum RPU limit. Use data sharing to separate ETL and BI compute, zero-ETL for operational sources, and Spectrum or Iceberg tables for cold or shared lake data.
quiz: What do the leader node and the compute nodes each do in Redshift? || The leader node accepts connections, parses and optimizes queries, generates and compiles code, and coordinates execution. The compute nodes, split into slices, store the data and execute the compiled plan in parallel on their own slices.
Why does a collocated join avoid network traffic? || If both tables are distributed by hashing the join column, rows with the same key land on the same slice. Each slice can then join its own rows locally, so no rows need to be broadcast or redistributed between nodes.
How do zone maps and sort keys work together? || A zone map stores the minimum and maximum value of each 1 MB block of a column. When rows are stored sorted by that column, a range filter overlaps only a few blocks, so Redshift reads only those; without sorting, most blocks overlap and little is skipped.
A Serverless workgroup runs at 64 RPUs for 3 hours per day at $0.375 per RPU-hour. What is the monthly compute cost for 30 days? || 64 × $0.375 = $24 per hour. 24 × 3 hours × 30 days = $2,160 per month.
A small 20,000-row dimension is joined to a large fact table in most queries. Which distribution style would you choose and why? || DISTSTYLE ALL, so every node has a full copy of the dimension and joins with the fact table run locally regardless of the fact table's distribution. The cost is extra storage and slower loads for the copies, which is small for a 20,000-row table.

@@ airflow
value: Apache Airflow is the most widely used open-source orchestrator for data pipelines. You write a pipeline as a Python file that defines a DAG (directed acyclic graph) of tasks: "wait for the export, then extract, then run two transformations in parallel, then load, then notify". Airflow runs each DAG on its schedule or when upstream data changes, starts tasks only when their dependencies have succeeded, retries failures, lets you re-run history (backfill), and shows every run and every log line in a web UI.
The problem is coordination, not computation. A data platform has hundreds of jobs: Spark jobs on Databricks, SQL in Snowflake or BigQuery, dbt runs, file transfers, API calls, ML training. Each depends on others, each can fail, and each must run at the right time for the right date. Cron can start a script at 02:00 but knows nothing about dependencies, retries or history. Airflow keeps that knowledge in a database and a scheduler, so "did yesterday's revenue pipeline finish, and if not, which task failed and why?" has one answer.
Airflow stands on two concepts. Python (L0) is the authoring language: a DAG is ordinary Python code, so pipelines can be generated in loops, share libraries, and use any Python package, and the huge ecosystem of operators and provider packages (AWS, GCP, Databricks, Snowflake, Kafka, Slack and about a hundred more) exists because writing a Python integration is easy. Workflow orchestration (L1) is the model: a DAG of tasks with dependencies, schedules, retries, state tracking and backfills. For the layer above (data engineering teams, analytics engineers using dbt, ML teams), Airflow is the control plane that turns many independent jobs into a reliable daily process. Its important limit is that it orchestrates work done elsewhere; it is not the place to process the data itself.
terms: DAG — a pipeline: a set of tasks and the dependencies between them, with no cycles, plus a schedule.
Task and operator — a task is one step in a DAG; an operator is the class that defines what the step does (run SQL, submit a Spark job, call an API).
DAG run and task instance — one execution of a DAG for one logical date, and one execution of one task within it; each has a state stored in the metadata database.
Scheduler — the process that creates DAG runs, checks dependencies and sends ready task instances to the executor.
Executor — the component that decides where tasks run: locally, on Celery workers, as Kubernetes pods, or on remote edge workers.
Logical date and data interval — the timestamp a run represents and, for interval timetables, the period of data it covers.
XCom — a small value passed from one task to another through Airflow, such as a file path or a row count.
Deferrable operator — an operator that releases its worker slot while it waits, handing the wait to an asynchronous triggerer process.
Asset — a named piece of data (a table, a file path); DAGs can be scheduled to run when an asset is updated.
history: Maxime Beauchemin started Airflow at Airbnb in October 2014. Airbnb's data team had many Hive and other batch jobs whose dependencies lived in people's heads and in cron files. Earlier tools (Oozie, Luigi) defined workflows in XML or had weak scheduling and UIs. Airflow's choice was "configuration as code": DAGs written in Python, a scheduler that understood dates and backfills, and a rich UI. It was open-sourced in June 2015, entered the Apache Incubator in March 2016, and became a top-level Apache project in January 2019. Beauchemin, who also created Apache Superset, described the wider shift in his 2017 essay "The Rise of the Data Engineer".
Airflow 2.0 (December 2020) fixed the biggest operational pain: the scheduler became highly available, with several schedulers sharing work through database row locks, and became much faster. It also added the TaskFlow API (tasks as decorated Python functions passing data through XCom), a stable REST API, and split integrations into separately versioned provider packages. Later 2.x releases added deferrable operators and the triggerer (2.2), dynamic task mapping, which creates tasks at runtime from data (2.3), and data-aware scheduling with datasets (2.4). Managed services appeared: Google Cloud Composer (2018), Amazon MWAA (2020) and Astronomer's Astro.
Airflow 3.0 (22 April 2025) was the largest redesign. Tasks no longer access the metadata database directly; they talk to a Task Execution API through a Task SDK, so workers can run in remote or untrusted environments, and an Edge Executor runs tasks at remote sites. DAG versioning records how a DAG's structure changed over time, datasets became assets with an @asset decorator, backfills became scheduler-managed runs, a separate DAG processor parses files, and a new React UI replaced the old Flask one. Defaults changed too: catchup is off, and cron schedules use trigger semantics. Later releases added human-in-the-loop tasks and deadline alerts (3.1, September 2025), asset partitions and experimental multi-team deployments (3.2, April 2026), and a task state store, pluggable retry policies and experimental Java and Go task SDKs (3.3, July 2026). The latest stable release is 3.3.2 (September 2026).
how: An Airflow 3 deployment has six parts. The metadata database (PostgreSQL or MySQL) stores every DAG, DAG run, task instance and its state. The DAG processor reads DAG files from "DAG bundles" (a folder or a Git repository), executes the Python to build each DAG object, and stores a serialized version in the database. The scheduler reads those serialized DAGs and drives runs. The API server serves the UI, the public REST API and the Task Execution API. Workers run tasks. The triggerer runs asynchronous waits for deferred tasks. Because DAG files are executed during parsing, slow top-level code in a DAG file slows every parse.
Python's role is visible here. A DAG is defined by Python objects: with DAG("daily_sales", schedule="0 2 * * *") as dag, extract >> [transform_a, transform_b] >> load. The >> operator is Python operator overloading that records an edge. Because it is code, a DAG can be generated from a list of 50 tables in a loop, tested with pytest, and reviewed in pull requests. The cost is that the scheduler must execute that code to know what the DAG is, and that DAG files can import heavy libraries by accident.
The scheduler loop is the workflow orchestration concept in action. On each loop it does three jobs. First, for each active DAG, it asks the DAG's timetable whether a new run is due; with a cron schedule in Airflow 3, a run for 02:00 is created at 02:00, while interval timetables create the run for an interval after the interval ends. Second, for each running DAG run, it evaluates every task whose upstream tasks are finished: by default a task is ready when all upstream tasks succeeded (the "all_success" trigger rule), but rules like "one_failed" or "none_failed" allow other patterns. Third, it checks limits (the DAG's max active runs and tasks, pool slots that cap access to shared systems, overall parallelism) and priority weights, then marks the chosen task instances as queued and gives them to the executor. Several schedulers can run at once; they claim rows with SELECT ... FOR UPDATE SKIP LOCKED so that each task instance is scheduled exactly once.
The executor decides where a queued task runs. The LocalExecutor runs tasks as processes on the scheduler machine. The CeleryExecutor puts tasks on a message broker (Redis or RabbitMQ) for a pool of long-lived workers. The KubernetesExecutor starts one pod per task, which isolates dependencies and scales to zero but adds pod start-up time of several seconds or more. The EdgeExecutor sends tasks to workers in other sites over HTTP. On the worker, the Task SDK runs the operator's execute method, sends heartbeats, writes logs, and reports the final state through the Task Execution API. If a task fails and has retries left, it moves to "up_for_retry" and is scheduled again after retry_delay, optionally with exponential backoff.
Waiting is a large part of orchestration: waiting for a file, for a partner's API, for a Spark job to finish. A classic sensor occupies a worker slot while it polls. A deferrable operator instead "defers": it hands an asynchronous trigger to the triggerer process and frees its slot. One triggerer, built on Python's asyncio, can watch thousands of such waits; when a trigger fires, the task resumes on a worker. Data passing is deliberately limited: XComs are for small values stored in the database (or in object storage through a custom backend). Large data should stay in S3, a warehouse or a lakehouse, with only references passed between tasks.
Time handling is the subtle part. Each DAG run has a logical date. With interval timetables (and in Airflow 2 by default), a daily run labelled 2026-10-25 covers the data from 2026-10-25 00:00 to 2026-10-26 00:00 and starts after that interval ends, so a task can safely process "its" day. Backfill creates runs for past logical dates, and templated values such as {{ ds }} let one task definition process any date. This only works if tasks are idempotent: running a task twice for the same date must produce the same result, for example by overwriting a partition instead of appending to it.
Assets add a data-driven trigger on top of time. A task can declare that it produces an asset, and another DAG can be scheduled on that asset, so it runs when the asset is updated instead of at a fixed hour. Since 3.2, asset partitions let a downstream DAG run only for the partition (for example the date) that changed.

example: The DAG daily_sales has schedule "0 2 * * *" (02:00 UTC). Its tasks are wait_export (a deferrable sensor that checks every 5 minutes), extract (10 minutes), transform_orders (20 minutes) and transform_refunds (8 minutes) in parallel, then load (6 minutes). The task transform_orders has retries=3, retry_delay of 5 minutes and exponential backoff.
Step 1, a normal day. The run is created at 02:00. The partner's file arrives at 02:37, and the trigger's next check at 02:40 sees it. Extract runs 02:40–02:50. Both transforms start at 02:50; the pipeline must wait for the slower one, so the critical path is 20 minutes, to 03:10. Load runs 03:10–03:16. Queueing between tasks adds a few seconds each. While wait_export waited, it held no worker slot.
Step 2, a failure. transform_orders fails after 12 minutes, at 03:02, because a warehouse connection dropped. It goes to up_for_retry and is retried about 5 minutes later, at 03:07; a second failure would wait about 10 minutes, and a third about 20, because the delay doubles. The retry succeeds at 03:27, and load runs 03:27–03:33. transform_refunds finished at 02:58 and is not re-run. A deadline alert set for 04:00 does not fire.
Step 3, capacity. The company has 300 DAGs with an average of 25 tasks each, all daily: 7,500 task instances per day. Most DAGs start between 01:00 and 03:00, so about 4,500 task instances run in those 2 hours, with an average task length of 6 minutes. That is 4,500 × 6 = 27,000 task-minutes of work in 120 minutes, so on average 27,000 / 120 = 225 tasks must run at once. A Celery deployment with 10 workers of 16 slots has 160 slots, so tasks queue and pipelines finish late. The options are to add workers (for example 15 × 16 = 240 slots), to spread schedules across the night, or to move long waits to deferrable operators.
Step 4, why deferral matters. If 200 of those tasks were classic sensors waiting on average 40 minutes each, they would hold 200 worker slots for 40 minutes doing almost nothing, 8,000 slot-minutes, which is more than the whole 160-slot cluster can give in 50 minutes. As deferrable operators, all 200 waits live in one triggerer process, and the slots stay free for real work.
intuition: Airflow is a railway timetable with a signal box: it knows which trains leave when, which must wait for which, and what to do when one is late, but it does not carry any passengers itself.
The design follows from what pipelines have in common. Almost every data job is "run this step, for this date, after those steps, and retry if it fails". Once you write that down as a graph, everything else is bookkeeping: store the state of each step for each date in a database, loop over the graph to find steps whose parents are done, and give those to workers. Writing the graph in Python means engineers use the tools they already know (functions, loops, tests, code review). Keeping data out of Airflow and passing only references keeps the orchestrator small and lets each job use the right engine for its work. And because every state change is a row in a database, the UI, alerts, backfills and audits all read the same truth.
mistakes: People often think Airflow should process data inside tasks. In fact it is designed to orchestrate: heavy pandas work or large data in XComs overloads workers and the metadata database. Push the computation to Spark, a warehouse or a container, and let Airflow start it and wait for it.
People often think a daily DAG run labelled with a date runs on that date. With interval timetables (and Airflow 2's default), the run labelled 2026-10-25 covers that day and starts after it ends, on 2026-10-26. Airflow 3's default cron behaviour labels runs with their trigger time instead; know which timetable your DAG uses before you write date logic.
People often think top-level code in a DAG file runs once. In fact the DAG processor executes the whole file on every parse, often every 30 seconds or more often, so database calls or API requests at module level run thousands of times a day and slow parsing for everyone.
People often think retries make pipelines safe. In fact a retry is safe only if the task is idempotent. A task that appends rows will duplicate them on retry; tasks should overwrite partitions, use MERGE, or check what already exists.
friction: The metadata database and the scheduler are the bottlenecks of a large deployment. Thousands of DAGs and hundreds of thousands of task instances per day need a well-sized PostgreSQL, tuned scheduler settings (parsing intervals, loop sizes) and cleanup of old rows. Task start-up latency is seconds, not milliseconds, so Airflow suits jobs of minutes and hours, not streams of tiny events.
Data dependencies are weaker than in asset-first tools. Classic Airflow knows that task B runs after task A, not that table B is derived from table A, so lineage needs extra tools (OpenLineage) and asset declarations. Testing DAGs locally requires an Airflow environment; dependency conflicts between DAGs that share workers are common, which pushes teams toward KubernetesPodOperator or virtualenv tasks.
The Airflow 2 to 3 migration has real work: tasks that read the metadata database directly, removed features (SubDAGs, SLAs, pickling), changed defaults for catchup and cron timetables, and import paths that moved to airflow.sdk. Dynamic DAGs generated from external metadata can be hard to debug, and the UI becomes slow when a DAG has thousands of mapped tasks. Security and multi-tenancy are also hard: in Airflow 2 every worker needed database credentials, and although Airflow 3 removes that, teams sharing one deployment still share connections, variables and executors unless they adopt the experimental multi-team mode or run separate deployments. Finally, Airflow's age means many tutorials and Stack Overflow answers describe Airflow 1 or 2 behaviour.
practice: Keep DAG files light: no network calls or heavy imports at module level, and put shared logic in a Python package that DAGs import. Make every task idempotent and parameterized by the logical date or the data interval, so retries and backfills are safe. Pass only small values through XCom, and keep data in object storage or the warehouse.
Use deferrable operators for anything that waits (file sensors, external job status), and pools to cap concurrent load on shared systems such as a database that allows 20 connections. Set retries with exponential backoff for flaky external systems, plus execution timeouts so a hung task fails instead of blocking a run forever, and deadline alerts for pipelines with business deadlines.
Choose the executor from your needs: Celery for many short tasks with low latency, Kubernetes for isolation and varied dependencies, or a mix with the multiple-executor setting. Monitor scheduler loop time, DAG parse time, queued-task counts and pool usage; spreading schedules away from midnight often fixes "everything is late" without new hardware. Start new deployments on Airflow 3, use the airflow.sdk imports and the TaskFlow API, and consider asset-based scheduling between teams so that a downstream DAG runs when its input is ready rather than at a guessed hour. Test DAGs in CI by importing every file (DagBag) and checking for import errors and cycles.
quiz: What are the main components of an Airflow 3 deployment? || The metadata database, the DAG processor (parses DAG files), the scheduler (creates runs and queues ready tasks), the executor and workers (run tasks), the API server (UI, REST and Task Execution API), and the triggerer (asynchronous waits for deferred tasks).
How does the scheduler decide that a task instance can run? || It checks that the DAG run is active, that upstream tasks are in states allowed by the task's trigger rule (by default, all succeeded), and that concurrency limits, pool slots and priorities allow it. Then it marks the task as queued and hands it to the executor.
Why do deferrable operators save resources compared with classic sensors? || A classic sensor holds a worker slot for the whole wait. A deferrable operator hands its wait to the triggerer, which runs many asynchronous waits in one process, and frees the worker slot until the condition is met.
A deployment runs 3,000 task instances in a 90-minute window, each lasting 4 minutes on average. How many worker slots are needed on average? || 3,000 × 4 = 12,000 task-minutes of work. Divided by 90 minutes that is about 133 tasks at once, so at least about 133 slots, plus headroom for peaks.
When would you choose Dagster or Temporal instead of Airflow? || Dagster fits when you want the orchestrator to understand data assets, lineage, partitions and freshness directly. Temporal fits long-running, event-driven business processes in application code that need durable state, signals and timers over days or months. Airflow fits scheduled batch pipelines across many external systems with a large provider ecosystem.

@@ dagster
value: Dagster is an open-source data orchestrator built around data assets rather than tasks. Instead of saying "run step A, then step B at 02:00", you declare the things that should exist (a table of cleaned events, a daily sessions table, a trained model, a dashboard) and, for each one, the Python function that computes it from its upstream assets. Dagster derives the dependency graph from those declarations, decides what needs to run, runs it, and records every materialization: when the asset was last built, from which code version, with which metadata and with which quality checks.
This matters because the questions people ask about a data platform are about data, not jobs: "Is the revenue table fresh?", "Which dashboards use this column?", "Which partitions of last quarter are missing?", "If I change this model, what must be rebuilt?". A task-based orchestrator such as Airflow can answer them only indirectly, through naming conventions and extra lineage tools. Dagster stores the answers as first-class state, so the UI shows a catalog of assets with lineage, freshness and history, and automation can be expressed per asset ("rebuild this when any upstream changes, but at most once per hour").
Dagster stands on two concepts. Python (L0) is both the implementation language and the authoring model: an asset is a decorated Python function, dependencies come from function parameters, and resources (database clients, API keys) are injected like ordinary objects, so pipelines can be tested with pytest and type-checked. Workflow orchestration (L1) gives the runtime machinery: a dependency graph, schedules and sensors, runs, retries, concurrency limits and backfills. Dagster's addition is to put a data model on top of that machinery. For the layer above (analytics engineers using dbt, ML engineers, platform teams serving many data teams), Dagster is the control plane and the catalog in one place.
terms: Asset — a persistent object such as a table, file or model, declared in code with the function that produces it; also called a software-defined asset.
Materialization — one execution of an asset's function that produces or updates the asset, recorded as an event with metadata.
Asset graph — the directed acyclic graph of assets and their dependencies, derived from the asset definitions.
Partition — a slice of an asset, such as one day or one customer, that can be materialized, tracked and backfilled on its own.
Asset check — a data-quality test attached to an asset (no nulls, row count in range); blocking checks stop downstream assets.
Resource — a configurable object injected into assets, such as a Snowflake connection or an S3 client, swapped between test and production.
IO manager — a resource that stores an asset function's return value and loads it for downstream assets.
Declarative Automation — per-asset rules (AutomationCondition) that say when an asset should be materialized, evaluated continuously by Dagster.
Code location — a separately deployed Python environment holding a set of definitions, loaded by Dagster over gRPC.
history: Nick Schrock, a co-creator of GraphQL at Facebook, founded Elementl (now Dagster Labs) in 2018 to build Dagster. The first releases on PyPI date from mid-2018. His starting observation was that data pipelines were rarely developed like software: they were hard to test locally, their inputs and outputs were untyped, and orchestrators knew nothing about the data they produced. Early Dagster (0.x, 2019–2020) centred on "solids", typed computations with declared inputs and outputs, later renamed "ops", with an emphasis on local development and testing.
The decisive step came in 2021, when Dagster introduced software-defined assets as an experimental API: instead of wiring ops into a graph, you declared assets and let Dagster build the graph. The idea fitted the way dbt users already thought (each model is a table that depends on other tables), and Dagster's dbt integration turned every dbt model into an asset with lineage. Dagster 1.0 (August 2022) made assets the recommended way to build pipelines. The hosted product Dagster Cloud, later renamed Dagster+, offered serverless and hybrid deployments.
Later versions deepened the asset model. Version 1.8 (August 2024) introduced Declarative Automation with AutomationCondition, replacing the earlier auto-materialize policies, and 1.9 (November 2024) made it stable. Components, reusable YAML- or Python-configured building blocks, and the dg command-line tool arrived in 2025 and became generally available in 1.12 (October 2025). Version 1.13 (April 2026) added partitioned asset checks, virtual assets for views that need no materialization, more integration components and AI-assisted development tooling. The latest release in October 2026 is 1.13.26.
how: A Dagster project exposes a Definitions object containing assets, asset checks, jobs, schedules, sensors and resources. An asset is written as a function: @asset def sessions(raw_events): ... returns sessions computed from raw_events. Python's function signature is the dependency declaration: the parameter name raw_events refers to the upstream asset of that name, and Dagster's IO manager loads it before the call. Assets that do their work elsewhere (run SQL in Snowflake, trigger a Databricks job, run dbt) declare dependencies with deps=[...] and return metadata (row counts, schema, a preview) instead of data. Because these are ordinary functions and objects, a test can call sessions() with a small DataFrame and a fake resource, without any orchestrator running.
When Dagster loads the definitions, it builds the asset graph, which is a DAG in exactly the sense of workflow orchestration. A job or a selection, such as "sessions and everything downstream", is a subgraph of that graph. To execute it, Dagster creates a run and compiles the selection into an execution plan of steps, one or more per asset, ordered by dependencies. A run launcher starts a run worker (a process, a Docker container or a Kubernetes pod), and an executor inside it runs the steps, in one process, in parallel processes, or as one pod per step. Retries, timeouts and concurrency limits (for example at most 5 steps that query the warehouse at once, across all runs) are standard orchestration features applied per step or per asset.
Every step writes structured events to the event log in Dagster's storage (PostgreSQL in production): step started, materialization with metadata, check result, failure with stack trace. The asset catalog is built from these events. That is the core difference from a task orchestrator: the latest materialization of each asset (and of each partition), its code version and its upstream data versions are queryable state, so Dagster can tell whether an asset is missing, stale because an upstream asset changed, or stale because its code changed.
Partitions bring time and other dimensions into the graph. An asset can be partitioned daily, hourly, by a static list (regions), by a dynamic list (customers added at runtime), or by two dimensions at once. Each partition is materialized and tracked separately, and partition mappings describe how partitions relate across assets: a weekly asset depends on seven daily partitions, a daily asset on the same day of its parent, or on the previous day for rolling windows. A backfill is then a request such as "materialize sessions for these 90 days", and Dagster launches the runs, respecting each asset's backfill policy (one run per partition or one run per range).
Automation has three layers. Schedules launch selections on a cron. Sensors run a small Python function every 30 seconds or so and launch runs when an external condition is true, such as a new file in S3. Declarative Automation attaches a condition to each asset: AutomationCondition.eager() means "materialize when an upstream partition is updated and none of my dependencies are missing or in progress"; on_cron("0 6 * * *") means "materialize once after 06:00 when all upstream data for the period has arrived"; on_missing() fills in partitions that should exist. A daemon evaluates these conditions on every tick using the event log, so the decision is based on data state rather than on the clock alone. Asset checks run after or alongside materializations; a failed blocking check stops downstream automation from consuming bad data.
Deployment separates the control plane from user code. The webserver (UI and GraphQL API) and the daemon (schedules, sensors, automation, run queue, backfills) are long-running services. User code lives in code locations, each a Python environment that serves its definitions over gRPC, so two teams can use different library versions and redeploy independently. In Dagster+, Dagster Labs runs the control plane, and an agent inside your own cloud account launches runs, so data does not leave your infrastructure.
Integrations map other systems into the asset graph. The dbt integration reads dbt's manifest, makes each model an asset with the right dependencies, and runs selected models through dbt; Fivetran, Airbyte and Sling syncs become source assets; Tableau, Looker and Power BI dashboards become downstream assets. The result is one lineage graph from ingestion to dashboard, even when Dagster runs only part of the work.

example: A team has three assets. raw_events is partitioned daily and loaded from S3 (3 minutes per partition). sessions is partitioned daily and computed from the same day of raw_events (6 minutes per partition). weekly_report is partitioned weekly and depends on the seven daily partitions of sessions in its week (4 minutes per partition).
Step 1, a backfill. The team adds the pipeline and wants 90 days of history, which covers about 13 weeks. Dagster's request is 90 raw_events partitions, 90 sessions partitions and 13 weekly_report partitions: 193 materializations. Total work is 90 × 3 + 90 × 6 + 13 × 4 = 270 + 540 + 52 = 862 minutes. With a concurrency limit of 10 steps at once, the lower bound on wall-clock time is 862 / 10 ≈ 86 minutes; in practice it is a little longer because a week's report must wait for its seventh day.
Step 2, automation. sessions has AutomationCondition.eager(), and weekly_report has on_cron for Monday 06:00. On Tuesday the partner's file for Monday is late; raw_events for that day materializes at 05:10. On the next daemon tick, Dagster sees that sessions for that day has a newer upstream materialization and requests it; it finishes at 05:16. No schedule had to be moved, because the trigger is the data. The weekly report for the previous week was built on Monday at 06:00, after the cron tick, because all seven of its sessions partitions existed by then; if one had been missing, the condition would have waited for it.
Step 3, a failure and a check. sessions for 2026-10-23 fails because of a schema change. The partition grid shows exactly one red cell. The weekly report for that week does not run, because one of its dependencies is missing. The team fixes the code and re-materializes only that partition, 6 minutes of work, and automation then builds the dependent weekly report, 4 more minutes.
Step 4, a code change. The team changes the sessionization rule and bumps the code version of sessions. Dagster now marks all 90 sessions partitions and the 13 weekly reports as stale for code reasons, while raw_events stays current. Re-running exactly the stale set costs 90 × 6 + 13 × 4 = 592 minutes of work, instead of 862 for the whole pipeline. In a task-based orchestrator, the team would have to work out that set by hand.
intuition: Airflow gives you a list of chores and a clock; Dagster gives you a picture of the house as it should be and tells you which rooms are out of date.
The asset model is natural because a data pipeline exists only to produce data. Tasks are just the means; what users depend on is that the tables are present, correct and fresh. Once you declare the assets and their dependencies, many hard questions become graph questions: what is downstream of this table (a traversal), what must re-run after a fix (the stale set), when should this run (when its inputs change). The event log makes the state real: because every materialization is recorded with versions, the orchestrator can reason about data, not guess from task names. Making assets plain Python functions keeps the cost of this model low for engineers, who can test them like any other code.
mistakes: People often think assets mean Dagster must move or store the data. In fact an asset can be computed entirely in Snowflake, Spark or dbt, with the function only starting the work and returning metadata. IO managers are optional and most useful for small Python-computed data.
People often think Dagster has no tasks or jobs. In fact assets run as steps (ops) inside runs, and jobs, schedules and sensors still exist. Dagster also supports plain op-based jobs for work that does not produce an asset, such as sending a report or calling an API.
People often think Declarative Automation replaces all schedules. In fact the conditions are evaluated on daemon ticks and need a sensible starting point, such as source assets that are observed or a cron condition at the edge of the graph. Eager conditions on a large graph can also trigger more runs than expected; start with cron-based conditions at the leaves and use eager only where low latency matters.
People often think switching from Airflow is a quick port. In fact the value comes from remodelling pipelines as assets with partitions and checks. Translating Airflow tasks one-to-one into ops keeps the old model and gains little; Dagster's Airflow integration (airlift) lets teams observe and migrate gradually.
friction: The ecosystem is smaller than Airflow's. Airflow has more provider packages, more managed offerings (MWAA, Cloud Composer, Astronomer), more engineers who know it and more answers online. Dagster's integrations cover the modern data stack well (dbt, Snowflake, Databricks, Fivetran, BI tools), but unusual systems may need custom resources.
The asset model asks for design work. Teams must decide the grain of assets and partitions, define partition mappings, and keep code versions meaningful; badly chosen partitions (for example one per customer for 100,000 customers) produce huge numbers of runs and a slow UI. Dynamic partitions and multi-dimensional partitions add power but also complexity.
Operational limits appear at scale. The daemon evaluates automation conditions for every asset and partition on every tick, which can become slow with many thousands of assets and long partition histories. The event log grows quickly and needs retention policies. Each run has start-up overhead (launching a process or pod and loading code), so very many tiny runs are inefficient; batching partitions with backfill policies helps.
The project moves fast. APIs have been renamed and deprecated several times (solids to ops, auto-materialize policies to Declarative Automation, source assets to asset specs, new Components and dg tooling), so upgrades need attention and older blog posts may mislead. Finally, much of the polish (branch deployments, insights, alerting) is in the commercial Dagster+, which is a factor in self-hosted versus managed decisions.
practice: Model assets at the grain people care about: one asset per table or file that someone queries, not one per transformation step. Partition by time when data arrives by time, and keep partition counts reasonable (days or hours for years of data, not minutes). Give heavy assets backfill policies that process ranges in one run, so a 365-day backfill does not launch 365 pods.
Keep compute where it belongs. Let Snowflake, Databricks or dbt do the heavy work, and use Dagster assets to start it and record metadata. Put connections in resources, configured per environment, so local tests use DuckDB or fakes and production uses the real systems. Add asset checks for the properties downstream users rely on (uniqueness, freshness, row counts), and make critical ones blocking.
For automation, start with cron-based conditions on leaf assets and eager conditions only where freshness matters; watch the automation evaluation history in the UI to see why something ran or did not. Use concurrency pools to protect shared systems. Organize large projects into code locations per team, use Components and dg for repeated patterns, and use the dbt integration so dbt models appear in the same lineage graph. Set event log and run retention from the start.
quiz: What is a software-defined asset? || It is a declaration in code of a persistent data object, such as a table or model, together with the function that computes it and the upstream assets it depends on. Dagster builds the dependency graph from these declarations and records each materialization of the asset.
How does Dagster know that an asset is stale? || It keeps, in the event log, the latest materialization of each asset and partition with its code version and the versions of the upstream data it used. If an upstream asset has a newer materialization, or the asset's code version changed, the asset is marked stale.
How do partition mappings help a weekly asset that depends on a daily asset? || The mapping states that each weekly partition depends on the seven daily partitions of its week. Dagster can then wait until all seven exist, show exactly which ones are missing, and backfill or re-run only the affected weeks.
A backfill covers 60 daily partitions of two assets taking 5 and 8 minutes per partition, with 6 steps allowed at once. What is the lower bound on wall-clock time? || Total work is 60 × 5 + 60 × 8 = 300 + 480 = 780 minutes. With 6 steps in parallel the lower bound is 780 / 6 = 130 minutes.
When is Airflow a better choice than Dagster? || When pipelines are mostly scheduled tasks across many external systems that Airflow's large provider ecosystem already covers, when the team already knows Airflow well, or when a widely available managed service is required. Dagster is better when lineage, partitions, freshness and data quality of assets are the main concern.

@@ dbt
value: dbt ("data build tool") turns SQL transformations inside a warehouse into a software project. Each model is a file containing one SELECT statement. dbt wraps it in the DDL needed to create a view or table, works out the order in which models must be built from the ref() calls between them, runs them in that order in the warehouse, and then runs tests on the results. The whole project lives in Git, with code review, environments (development, CI, production), generated documentation and lineage.
Before dbt, warehouse transformations were usually stored procedures, scripts in a scheduler, or logic hidden inside BI tools. They were hard to test, hard to review and hard to change safely, and nobody could see which table fed which. dbt made a new role, the "analytics engineer", possible: someone who writes SQL but works like a software engineer, with modules, tests, version control and continuous integration. It is now the most common way to build models in Snowflake, BigQuery, Databricks, Redshift, Postgres and DuckDB, and it is often scheduled by an orchestrator such as Airflow or Dagster.
dbt stands on five concepts. Workflow orchestration (L1) gives the idea of running steps in dependency order with selection and retries; dbt is an orchestrator specialised for SQL models inside one warehouse. DAG scheduling (L2) gives the algorithm: the ref() calls form a directed acyclic graph that dbt sorts topologically and runs with a fixed number of parallel threads. Declarative pipelines and materialized views (L1) give the model of declaring what a table should contain (a SELECT) and letting the tool decide how to create or update it. Dimensional modelling (L1) gives what most dbt projects build: staging models, then fact and dimension tables in a star schema, with snapshots for slowly changing dimensions. Train/validation/test splits (L2) give the habit of validating results before anyone uses them: dbt's data tests and unit tests check each model before downstream models and dashboards consume it, much as a model is checked on held-out data before it is trusted.
terms: Model — a SQL (or Python) file with one SELECT; dbt materializes it as a view, table, incremental table, materialized view or ephemeral CTE.
ref() — a Jinja function that refers to another model; it returns the right schema-qualified name for the current environment and records a dependency edge.
source() — like ref(), but for raw tables loaded by other tools; declared in YAML, with optional freshness checks.
Materialization — the strategy dbt uses to build a model: view, table, incremental, ephemeral or materialized_view.
Incremental model — a table that dbt updates by processing only new or changed rows, using merge, append, delete+insert, insert_overwrite or microbatch strategies.
Data test — a query that returns rows that violate an assumption (duplicates, nulls, broken relationships); the test fails if any rows come back.
Manifest — the JSON file describing every node in the project and its dependencies, produced when dbt parses the project.
Jinja and macros — the templating language dbt uses to generate SQL, and reusable template functions written in it.
Snapshot — a table that records changes to a source over time, as type 2 slowly changing dimension rows with valid_from and valid_to columns.
history: dbt began in 2016 at RJMetrics, a Philadelphia analytics company, where Tristan Handy, Drew Banin and Connor McArthur wanted a better way to transform data inside the new cloud warehouses, especially Amazon Redshift. Cheap, fast warehouses made "ELT" possible: load raw data first, then transform it with SQL inside the warehouse, instead of transforming it in a separate ETL tool. The first versions appeared on PyPI in March 2016. Handy founded Fishtown Analytics, a consultancy that used and developed dbt; the company launched the hosted dbt Cloud and was renamed dbt Labs in 2021. dbt Core 1.0, the first version with stability guarantees, was released on 3 December 2021.
The 1.x line added features one release at a time: model contracts and versions (1.5, 2023), a semantic layer built on MetricFlow after dbt Labs acquired Transform (2023), unit tests with mocked inputs (1.8, May 2024), the microbatch incremental strategy for large event tables (1.9, December 2024), and later Iceberg catalog support and user-defined functions (1.10 and 1.11, 2025).
The biggest change was the engine. In January 2025 dbt Labs acquired SDF Labs, whose Rust-based tool could parse and type-check SQL in many dialects. In May 2025 it announced the dbt Fusion engine, a rewrite in Rust that understands the SQL it compiles, so it can catch errors, compute column-level lineage and power editor features without running queries. In October 2025 Fivetran and dbt Labs announced an all-stock merger, completed on 1 June 2026, with George Fraser as CEO and Tristan Handy as President. The same day, dbt Core v2 was released as an alpha: the Fusion runtime, open-sourced under Apache 2.0 in the dbt-core repository. By October 2026, v2 (in release candidates for the pure open-source build, and as the Fusion binary distribution) is the recommended default, while the Python 1.x line, at 1.12, is still maintained.
how: A dbt project is a folder of SQL, YAML and Jinja. A model file such as models/marts/fct_orders.sql contains a SELECT that refers to other models with {{ ref('stg_orders') }} and to raw tables with {{ source('shop', 'orders') }}. When dbt parses the project, it renders the Jinja enough to find every ref() and source() call, and builds a graph whose nodes are models, sources, seeds, snapshots and tests. That graph is written to manifest.json. Because the project can only declare dependencies this way, dbt always knows the full lineage, and a reference to a model that does not exist is an error before any SQL runs.
Running the graph is DAG scheduling. dbt sorts the nodes topologically and keeps a pool of worker threads (for example 8). A node starts as soon as all its parents have succeeded and a thread is free, so independent staging models run in parallel while a mart waits for its inputs. Node selection uses graph operators: --select fct_orders+ means "this model and everything downstream", +fct_orders means "and everything upstream", and state:modified+ compares the current manifest with one saved from production to select only changed models and their children. If a model fails, its descendants are skipped, and dbt retry can resume from the failure point.
Each model is compiled into SQL for the target environment. ref('stg_orders') becomes, for example, analytics.dbt_prod.stg_orders in production and analytics.dbt_alice.stg_orders in Alice's development schema, so every developer can build the whole project in isolation. The materialization then wraps the SELECT. A view becomes CREATE VIEW AS SELECT; a table becomes CREATE TABLE AS SELECT, usually into a temporary name followed by a swap; an ephemeral model is inlined as a common table expression into the models that use it. This is the declarative pipeline idea: the model states what the table contains, and the materialization decides how to produce it.
Incremental models are where dbt does the most work and where mistakes hide. The model contains a filter inside {% if is_incremental() %}, for example "where updated_at > (select max(updated_at) from {{ this }})", which applies only when the target table already exists. dbt runs the SELECT with the filter into a temporary relation and then applies the strategy: MERGE on a unique_key (update existing rows, insert new ones), append, delete+insert, or replacing whole partitions (insert_overwrite). The microbatch strategy splits work into time batches (for example one day each) based on an event-time column, runs each batch independently, and can retry or backfill single batches. A full refresh rebuilds the table from scratch when logic changes.
Testing applies the validation idea at every node. A data test such as unique on order_id compiles to a query like "select order_id from fct_orders group by order_id having count(*) > 1"; if it returns rows, the test fails. Built-in tests cover unique, not_null, accepted_values and relationships (every foreign key exists in the parent), and packages add many more. dbt build interleaves models and tests in graph order, so a failed test on a staging model stops downstream models from being built on bad data. Unit tests check transformation logic itself: they give a model fixed input rows and compare its output with expected rows, without touching production data.
Dimensional modelling shapes most projects. Staging models clean and rename one source table each; intermediate models combine them; mart models expose fact tables (orders, events) and dimension tables (customers, products) in a star schema. Snapshots implement type 2 slowly changing dimensions: on each run, dbt compares the current source rows with the snapshot and closes changed rows (setting valid_to) while inserting new versions. Model contracts enforce column names and types, and versions let a mart change its shape while consumers migrate.
The v2 engine changes the compiler, not the language. It parses the Jinja and also the resulting SQL into a typed logical plan for the target dialect, so it can report a misspelt column or a type mismatch before sending anything to the warehouse, trace a column through every model, and parse very large projects much faster than the Python engine. Artifacts can be written as Parquet and queried directly. In both engines, each run also writes run_results.json (status and timing per node), and docs generation writes catalog.json (column types read from the warehouse); with the manifest, these artifacts feed the documentation site, lineage tools and orchestrators such as Dagster, which turns each dbt model into an asset.

example: A shop's raw orders table has 500 million rows and grows by about 2 million rows per day. The model fct_orders joins orders to customers and is used by every revenue dashboard. The warehouse is Snowflake on a Medium warehouse (4 credits per hour).
Step 1, the DAG. The project has stg_orders and stg_customers (views), dim_customers (table), fct_orders and mart_revenue_daily. dbt's order is: stg_orders and stg_customers in parallel, then dim_customers, then fct_orders, then mart_revenue_daily. Tests on dim_customers run before fct_orders starts, so a duplicate customer key stops the build before it can double revenue.
Step 2, full table versus incremental. As a plain table, fct_orders rebuilds all 500 million rows daily; suppose that takes 12 minutes, which is 4 × 12 / 60 = 0.8 credits per day, or about 292 credits per year. As an incremental model with a 3-day lookback (updated_at > max(updated_at) − 3 days), each run processes about 3 × 2 million = 6 million rows and merges them on order_id; suppose 1.5 minutes, which is 0.1 credits per day, about 37 credits per year. The incremental model is 8 times cheaper.
Step 3, the hidden bug. Suppose the filter had been written on order_date instead: order_date > max(order_date). About 0.5% of orders reach the warehouse two days late, with an order_date that is already older than the table's maximum. Each day, 2 million × 0.005 = 10,000 late orders are never inserted. After 30 days, 300,000 orders are missing and revenue is understated, while every run reports success. The lookback window, or the microbatch strategy with a lookback setting, fixes this; a test that compares daily row counts with the source would have caught it.
Step 4, a test. The unique test on order_id runs "select order_id from fct_orders group by order_id having count(*) > 1". If a merge without unique_key had appended updated rows, this query returns, say, 4,200 duplicate IDs, the test fails, and mart_revenue_daily is skipped instead of publishing wrong numbers.
Step 5, continuous integration. The project has 800 models. A pull request changes 3 of them, which have 25 downstream models. In CI, dbt build --select state:modified+ with deferral to production builds 3 + 25 = 28 models in a temporary schema, reading unchanged parents from production. That is 28 instead of 800 models, about 3.5% of a full build.
intuition: dbt treats the warehouse like a compiler target: you write small, named SELECT statements, and dbt links them into a program, runs it in the right order and checks the output.
The design is natural because SQL already describes results declaratively; what was missing was everything around it. A SELECT says what a table should contain, so the only extra information needed is how to store it (the materialization) and what it depends on (ref). From that, the graph, the order, the parallelism, the documentation and the lineage all follow mechanically. Tests are just more SELECTs that should return nothing. Environments are just different schemas for the same code. By adding very little to SQL, dbt gave analysts the main tools of software engineering, and that is why it spread so widely. The warehouse does what it is good at, set-based computation, and dbt does only what the warehouse cannot: remember the structure of the whole project.
mistakes: People often think dbt moves or processes data itself. In fact dbt only generates SQL and sends it to the warehouse; all computation and storage happen there. Performance and cost depend on the warehouse, the SQL and the materializations chosen.
People often think dbt is an orchestrator that replaces Airflow or Dagster. In fact dbt orders and runs models within one project, but it does not schedule across systems, wait for upstream loads, or run non-SQL steps; teams usually call dbt from an orchestrator or from dbt's own hosted scheduler.
People often think incremental models are always correct if they run without errors. In fact the incremental filter decides which rows are seen, and late-arriving or updated rows outside the filter are silently missed. Use a lookback window or microbatch, a unique key, and periodic full refreshes or reconciliation tests.
People often think more Jinja makes a project more maintainable. In fact heavy macro logic makes SQL hard to read and debug, because the code you see is not the code that runs. Use macros for real repetition and keep models as plain SQL where possible.
friction: Large projects strain the tool. Projects with thousands of models were slow to parse with the Python engine, and the DAG becomes hard to navigate without strict naming and folder conventions. The v2 engine addresses parse speed, but migrating requires fixing deprecated patterns, and some adapters and packages move to v2 at different speeds.
Incremental logic is the most common source of silent data errors: wrong filters, missing unique keys, schema changes in an incremental table (handled by on_schema_change settings), and different merge semantics across warehouses. Testing helps only if the right tests exist; many projects have hundreds of not_null tests and no test of business totals.
Jinja is powerful but blurs the line between code and template, and errors in compiled SQL point to generated text, not to the source. Running every test on every build can cost as much warehouse time as the models themselves, so teams must choose test severity and scope. Cross-project dependencies (dbt Mesh) and the semantic layer add capability but also more concepts.
The licensing and company landscape has also shifted: the Python Core under Apache 2.0, a Rust engine whose open part is Apache 2.0 and whose binary distribution has a separate license, some features behind a free login, and the merger with Fivetran. Teams should know which distribution they run and which features depend on dbt's platform.
practice: Structure the project in layers: staging models that map one-to-one to source tables (renaming, casting, light cleaning), intermediate models for joins and logic, and marts for facts and dimensions. Use source() for every raw table with freshness checks, and ref() for everything else; never hard-code table names. Keep one model per business concept, with a primary key that has unique and not_null tests.
Make incremental models safe: always set unique_key for merges, add a lookback window for late data or use microbatch with an event-time column, and schedule a periodic full refresh or a reconciliation test against the source. Add a few tests of business meaning (daily revenue within an expected range, row counts matching the source) rather than only column-level tests, and set severity so that warnings do not block builds.
In CI, build only modified models and their children with state:modified+ and --defer, in a temporary schema. Use dbt build rather than separate run and test steps, so tests guard downstream models. Generate docs and publish lineage so analysts can see where columns come from. Watch model run times in run_results.json and move the slowest tables to incremental, clustered or partitioned designs. If you start a new project in 2026, try the v2 engine for its faster parsing and SQL checks, and pin versions of dbt and packages so upgrades are deliberate.
quiz: What does the ref() function do? || It returns the fully qualified name of another model for the current environment, such as a production or development schema, and records a dependency edge in dbt's graph. dbt uses these edges to build models in the correct order and to draw lineage.
How does dbt decide which models can run in parallel? || It builds a DAG from ref() and source() calls and sorts it topologically. A model starts when all its parents have succeeded and one of the configured threads is free, so models without dependencies between them run at the same time.
Why can an incremental model miss rows even though every run succeeds? || The incremental filter, such as order_date greater than the current maximum, decides which source rows are processed. Rows that arrive late with older values, or are updated outside the filter window, are never selected, so they are silently missing unless a lookback window, microbatch or full refresh covers them.
A source table grows by 1.5 million rows per day and an incremental model uses a 4-day lookback. About how many rows does each run process, and how does that compare with a 300-million-row full rebuild? || About 4 × 1.5 million = 6 million rows per run, which is 2% of the 300 million rows a full rebuild would process.
When would you choose a view, a table or an incremental model in dbt? || A view for light logic over small data, since it costs nothing to build but recomputes on every query. A table when queries are frequent and a full rebuild is affordable. An incremental model when the table is large and grows by appends or bounded updates, accepting more complex logic and the risk of missed rows.

@@ temporal
value: Temporal is a platform for durable execution. You write a business process as ordinary code, in Go, Java, Python, TypeScript, .NET, PHP, Ruby or Rust: charge the card, reserve stock, wait up to seven days for the shipping event, send the email, refund if anything fails. Temporal makes that code survive process crashes, deploys, machine failures and outages lasting hours. If the machine running it dies in the middle of a seven-day wait, another machine continues the same function at the same line, with the same local variables, as if nothing happened.
The problem it solves is the reliability of multi-step processes that span services and time. Without it, teams build these flows from queues, cron jobs, database status columns, retry tables and timeouts scattered across services. Every step needs code for "what if we crash here?", and the overall process is visible nowhere. Temporal moves that state machine into the platform: the progress of each workflow is stored as an event history, retries and timers are built in, and the code reads as the process it implements. It is used for payments and money movement, order fulfilment, infrastructure provisioning, data and ML pipelines, and, increasingly since 2024, for AI agents whose long chains of model and tool calls must not lose progress.
Temporal stands on two concepts. Durable execution (L1) is the core idea: record the result of every step in a durable log, and rebuild the program's state after a failure by replaying the log rather than by saving memory snapshots. Workflow orchestration (L1) gives the surrounding model: steps with dependencies, retries with backoff, timeouts, timers and visibility into running processes. Compared with Airflow, which schedules DAGs of batch tasks, Temporal orchestrates long-lived, event-driven processes written as imperative code, where each workflow instance may be a single order or a single customer.
terms: Workflow — a function that defines the process; its code must be deterministic, because it is replayed.
Activity — a function that performs one side effect (an API call, a database write), with its own timeouts and retry policy; activities may run more than once.
Event history — the append-only list of everything that happened in one workflow execution (started, activity scheduled, activity completed, timer fired, signal received).
Worker — a process you run that hosts workflow and activity code and polls the Temporal Service for tasks.
Task queue — a named queue through which the service dispatches workflow tasks and activity tasks to workers.
Replay — re-running workflow code from the beginning against its event history to rebuild its state, without re-executing completed activities.
Signal, query and update — ways for outside code to send data into a running workflow, read its state, or send data and wait for a validated result.
Continue-As-New — ending a workflow run and starting a fresh run with the same workflow ID and a new, empty history, to keep histories small.
Namespace — a unit of isolation in a Temporal Service, with its own workflows, retention period and access rules.
history: The ideas behind Temporal came from two engineers. Maxim Fateev led the architecture of Amazon Simple Workflow Service (SWF), launched in 2012, which recorded workflow progress as a history of events. Samar Abbas worked at Microsoft on the Durable Task Framework, which later became the basis of Azure Durable Functions and used replay of an orchestration's history to rebuild its state. At Uber they built Cadence to coordinate Uber's many long-running processes, and Uber open-sourced it in 2017.
In 2019 Fateev and Abbas founded Temporal Technologies and forked Cadence as Temporal. The fork changed the wire protocol to gRPC with Protocol Buffers, reworked security and multi-tenancy, and invested heavily in SDKs for more languages. Temporal Server 1.0 was released in 2020, and the hosted Temporal Cloud followed. Later additions included Schedules (a durable replacement for cron), Update (synchronous request-response into a workflow) and Nexus (calls between workflows across namespaces and teams). In 2026 Worker Versioning, which routes workflows to specific worker builds, became generally available (March), task queue priority and fairness followed (May), the Rust SDK and standalone activities became generally available (September), and Serverless Workers for AWS Lambda and Google Cloud Run entered public preview.
Adoption grew with microservices and then with AI agents, which are long chains of slow, failure-prone calls. Users have included Netflix, Snap, Stripe, Datadog and HashiCorp. The company raised a $300 million Series D in February 2026 and a $550 million Series E in September 2026 at a reported valuation of $12.55 billion. The Temporal Server is open source under the MIT license, and the SDKs are released frequently; the Python SDK reached version 1.34 in September 2026.
how: A Temporal deployment has two halves. The Temporal Service (self-hosted or Temporal Cloud) stores state and dispatches work. Workers are your processes, which contain your workflow and activity code. Workers never receive pushed calls; they long-poll task queues on the service, so they can run anywhere that can reach it, and you scale them like any stateless service. The service itself has a Frontend (the gRPC API), a History service that owns workflow state, a Matching service that manages task queues, and an internal worker service. State lives in a database: Cassandra, PostgreSQL or MySQL, with SQLite for development, plus a visibility store (Elasticsearch, OpenSearch or SQL) for listing and searching workflows.
Durable execution is implemented through the event history. When a workflow starts, the History service writes WorkflowExecutionStarted and schedules a workflow task. A worker picks it up and runs the workflow function until the code cannot continue: it wants to call an activity, start a timer, or wait for a signal. At that point the SDK sends back commands (for example ScheduleActivityTask for ChargeCard) and the service appends them to the history as events. The activity is dispatched through its task queue to an activity worker, which calls the payment API and returns the result; the service records ActivityTaskCompleted with the result and schedules a new workflow task. The workflow code then continues from where it stopped. Every decision and every result is in the history before anything that depends on it happens.
Recovery is replay. If the worker holding a workflow crashes, or evicts it from its cache, any other worker can take the next workflow task. It downloads the event history and runs the workflow function from the beginning. When the code asks to call ChargeCard, the SDK does not send a new command; it finds ActivityTaskCompleted in the history and returns the recorded result immediately. The code runs through all completed steps in milliseconds, its local variables are rebuilt exactly, and it reaches the point where the history ends; from there it runs normally. This is why workflow code must be deterministic: given the same history, it must make the same calls in the same order. Reading the clock, generating random numbers, iterating over unordered maps or calling the network directly in workflow code would produce different decisions on replay, so the SDKs provide deterministic replacements (workflow time, workflow random, side-effect APIs) and detect mismatches as non-determinism errors. Normally, workers keep recent workflows in a "sticky" cache and receive their next tasks on a worker-specific queue, so full replay happens only after failures or evictions.
Workflow orchestration features are built from the same events. Retries belong to activities: by default an activity is retried with exponential backoff starting at 1 second, doubling each time, capped at 100 seconds, with no limit on attempts, until it succeeds or a timeout or non-retryable error stops it. Timeouts limit a single attempt (start-to-close), the whole activity including retries (schedule-to-close), and time between heartbeats for long activities. Timers are durable: workflow.sleep(30 days) writes a TimerStarted event, and the service fires it 30 days later even if every worker has been restarted many times since. Signals and updates append events that the workflow reacts to. Child workflows and Nexus operations compose workflows across services and teams.
Scale comes from sharding. Each workflow execution is assigned, by a hash of its namespace and workflow ID, to one of a fixed number of history shards, chosen when the cluster is created (for example 512 or more) and not changeable later. Each shard is owned by one History host at a time, which serializes all updates to its workflows and writes them to the database with conditional writes, so two hosts cannot update the same workflow concurrently. Millions of workflows can be open at once, mostly as rows in the database waiting for a timer or a signal, costing no CPU.
Limits keep the replay model practical. A single workflow's event history is capped at 51,200 events or 50 MB, with warnings at 10,240 events or 10 MB, and a workflow can have at most 2,000 pending activities by default. Long-running workflows (a subscription that lasts years, an entity that loops forever) periodically call Continue-As-New, passing their state as input to a fresh run with an empty history. Completed workflows are kept for a namespace's retention period and then deleted or archived.
Changing code under running workflows is the hardest part. If you deploy a new version that calls activities in a different order, replaying an old history fails. Temporal offers two tools: patching (a versioned branch in the code, such as if workflow.patched("v2"), which old executions skip and new ones take) and Worker Versioning, where each worker build has an ID and workflows stay pinned to the build that started them, or are moved to a new build at a safe point.

example: An order workflow does four things: charge the card, reserve stock, wait up to 7 days for a "shipped" signal, then send a confirmation email. The history below is simplified, but the event numbers are realistic.
Step 1, the first steps. Events 1–4 start the workflow and complete its first workflow task, which issues the ChargeCard command. Events 5–7 record ChargeCard: scheduled, started, completed with result ch_91. Events 8–10 are the next workflow task, which issues ReserveStock; events 11–13 record it. Events 14–16 are the next workflow task, which starts a 7-day timer as event 17. The workflow now waits. It uses no worker thread; it is a row in the database.
Step 2, a crash and a deploy. On day 1, worker A is killed during a routine deploy. On day 2 the warehouse system sends the signal "shipped", recorded as event 18, and a new workflow task is scheduled. Worker B has never seen this workflow. It loads 18 events and replays the code: the call to ChargeCard returns ch_91 from event 7 without calling the payment API, ReserveStock returns from event 13, the wait sees the signal from event 18, and the code continues to SendEmail. Replaying 18 events takes a few milliseconds. The customer is charged exactly once.
Step 3, a flaky email service. SendEmail fails. With the default retry policy, attempts are separated by 1, 2, 4, 8, 16, 32 and 64 seconds, then 100 seconds each. If the service recovers after 10 failed attempts, the total waiting time is 1 + 2 + 4 + 8 + 16 + 32 + 64 + 100 + 100 + 100 = 427 seconds, about 7 minutes. The email activity must be idempotent (for example by passing an idempotency key), because an attempt can succeed at the email provider but time out before reporting success, and then run again.
Step 4, a history that grows. A different workflow monitors a device by calling a CheckStatus activity every 10 seconds in a loop. Each iteration adds about 11 events: three for the activity, three for the workflow task that follows, two for the timer, and three for the next workflow task. The warning at 10,240 events arrives after about 10,240 / 11 ≈ 930 iterations, which is about 930 × 10 s ≈ 2.6 hours. The hard limit of 51,200 events is reached after about 4,650 iterations, about 13 hours. So this workflow must call Continue-As-New, for example every 500 iterations (about 80 minutes), carrying its state into a fresh run.
Step 5, shards. With 512 history shards on 8 History hosts, each host owns 64 shards. If one host fails, another takes over its 64 shards from the database, and their workflows pause only briefly.
intuition: Temporal works like a careful cook with a recipe and a notebook: every finished step is written down, and if the cook is replaced, the new cook reads the notebook, skips what is already done, and continues from the next line.
The idea is natural because programs already describe processes well; what they lack is memory that outlives the process. Saving a full memory snapshot after every step would be large and fragile, but the state of a deterministic program is completely defined by its code plus the inputs it received. So Temporal records only the inputs from the outside world, which are activity results, signals, timer firings and time, and rebuilds everything else by re-running the code. This is event sourcing applied to a program's execution. The determinism rule, which seems strict at first, is simply the price of being able to rebuild state from inputs.
mistakes: People often think Temporal makes every step run exactly once. In fact the workflow's logic advances exactly once, but activities are executed at least once: a worker can perform the side effect and crash before reporting it. Activities that change external systems must be idempotent or use idempotency keys.
People often think workflow code can do anything ordinary code can. In fact workflow code is replayed, so it must not call the network, read the system clock, use random numbers or depend on unordered iteration directly. All I/O goes into activities, and the SDK's deterministic APIs replace time and randomness.
People often think Temporal is a message queue or a faster cron. In fact it stores the full state and history of every process and drives it forward. It has higher per-step overhead than a queue (each step is several persisted events), and it is meant for business processes, not for moving millions of messages per second.
People often think a workflow can run forever without care. In fact each run's history is limited to 51,200 events or 50 MB, and large histories make replay slow. Long-running and looping workflows must use Continue-As-New, and large payloads should be stored elsewhere with only references in the history.
friction: Determinism and versioning are the main friction. Every change to workflow code must be safe for executions that started weeks or months ago; patch branches accumulate in the code, Worker Versioning needs old builds kept alive until their workflows finish, and replay tests add work.
The service is critical infrastructure. Self-hosting means operating the History, Matching and Frontend services, a Cassandra or SQL database sized for the write rate, a visibility store, and the shard count, which is fixed at creation and is hard to change. Many teams choose Temporal Cloud for this reason, which turns the cost into a per-action price.
Each workflow step costs several database writes and round trips, so latency per step is typically tens of milliseconds, and very fine-grained workflows (thousands of tiny activities) are expensive in both latency and money. Payload limits (a few megabytes per message) and history limits push large data out to object storage.
The programming model takes time to learn (workflows versus activities, timeouts, cancellation, time-skipping tests), and a non-determinism error after a deploy can stop thousands of workflows at once. Finally, Temporal overlaps with other tools (Airflow for batch DAGs, AWS Step Functions, queues with sagas), and choosing it is a commitment of every service that participates.
practice: Put all I/O in activities and keep workflow code pure: orchestration logic, branching, waiting, and calls to activities, child workflows and timers. Give every activity a start-to-close timeout, and a heartbeat timeout for long activities that report progress, and make every activity idempotent, for example by passing the workflow ID and step name as an idempotency key to external APIs.
Choose workflow IDs from business keys (order-881, customer-42) so that duplicate starts are rejected and signals can find the right workflow. Pass small payloads; store large data in S3 or a database and pass references. For loops and long-lived entities, call Continue-As-New well before the history warning, for example every few thousand events.
Plan versioning before the first production deploy: use Worker Versioning or patching, keep old worker builds running while their workflows finish, and run replay tests in CI against histories downloaded from production. Use separate task queues for activities with different resource needs (CPU-heavy work, rate-limited APIs) and scale workers per queue; watch schedule-to-start latency, which shows when workers are too few. Use Schedules instead of cron for recurring work, signals and updates for human approvals and external events, and the visibility API to search running workflows by custom attributes such as customer ID or status.
quiz: What is stored in a workflow's event history, and why is that enough to recover the workflow? || It stores every event of the execution: start, scheduled and completed activities with their results, timers, signals and other inputs. Because workflow code is deterministic, re-running it against these recorded inputs rebuilds exactly the same state, so a new worker can continue from the end of the history.
Why must workflow code be deterministic, and how do SDKs help? || Workflow code is replayed after failures, and replay must produce the same commands in the same order as the original run. SDKs provide deterministic replacements for time, randomness and side effects, and report a non-determinism error when replay differs from the history.
Why do activities need to be idempotent even though Temporal retries them reliably? || Activities run at least once: a worker can complete the external side effect and then crash or time out before Temporal records the result, so the activity runs again. Idempotency keys or checks make the repeated execution harmless.
A looping workflow adds about 12 events per iteration and runs one iteration every 30 seconds. About when does it reach the 10,240-event warning? || After about 10,240 / 12 ≈ 853 iterations, which is about 853 × 30 s ≈ 25,600 s, roughly 7 hours. It should call Continue-As-New before that.
When would you choose Temporal over Airflow? || When the process is long-running, event-driven and per entity, such as one workflow per order or payment, with waits for signals, human approvals and timers over days, written as application code. Airflow fits scheduled batch pipelines of data tasks with a fixed DAG and a large ecosystem of data integrations.
