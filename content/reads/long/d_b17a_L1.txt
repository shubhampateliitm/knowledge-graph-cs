@@ medallion
value: The medallion architecture organizes lakehouse tables into layers of increasing refinement. Bronze tables hold data as it arrived from sources, appended and kept. Silver tables hold cleaned, deduplicated, typed and conformed data, one trustworthy version of each entity or event. Gold tables hold data shaped for specific uses: dashboards, reports, machine-learning features, exports to partners. Each layer is computed from the one before it.
The value is not the three names but the contracts between them. Bronze guarantees "we kept everything, exactly as received", so any later mistake can be fixed by recomputing. Silver guarantees "this is the clean, agreed version", so analysts do not each write their own cleaning logic. Gold guarantees "this table answers this question at this grain and freshness", so consumers know what they are getting. With these contracts, a data platform with hundreds of pipelines stays understandable, debuggable and re-runnable. That is why Databricks and most lakehouse reference architectures recommend it, and why Delta Lake, Iceberg and Spark projects (including ad-tech platforms processing billions of events a day) are usually laid out this way.
Three lower concepts make it work. Idempotence (L2) lets every layer be rebuilt from the layer below without double-counting or side effects. DAG scheduling (L2) runs bronze, silver and gold jobs in dependency order with retries. Declarative pipelines and materialized views (L1) let teams describe each layer's tables as queries over the previous layer and let the engine keep them up to date incrementally.
terms: Bronze — raw, append-only tables that copy source data as received, plus ingestion metadata.
Silver — cleaned and conformed tables: deduplicated, typed, validated, joined to reference data.
Gold — consumer-specific tables: aggregates, dimensional models, features, exports.
Grain — what one row of a table represents, such as one impression or one campaign-day.
Reprocessing (backfill) — recomputing a layer for past data after a bug fix or logic change.
Quarantine — a separate table for rows that fail quality checks, kept for inspection instead of being silently dropped.
Data quality expectation — a declared rule on a table (for example "event_time is not null") with an action: warn, drop the row, or fail the pipeline.
Change data feed — a table's record of inserted, updated and deleted rows, used to update the next layer incrementally.
history: The idea of staged data is as old as data warehousing. Classic warehouses in the 1990s used a staging area (raw extracts), an integration layer (cleaned, often normalized, Bill Inmon's enterprise data warehouse) and presentation data marts (Ralph Kimball's star schemas). Hadoop-era data lakes in the 2010s used similar zones, often called raw, cleansed and curated, but many lakes became "data swamps": raw files with no clear contracts, no transactions and no quality checks.
The lakehouse made layered designs reliable. Delta Lake (2019) added ACID transactions, schema enforcement and time travel to files on object storage, so each layer could be a proper table that is updated atomically and rebuilt safely. Databricks popularized the bronze, silver and gold names around 2019–2020 in its documentation, training and customer projects, and Delta Live Tables (announced 2021, now Lakeflow Declarative Pipelines) made the pattern declarative, with expectations and automatic dependency management. Iceberg and Hudi users adopted the same structure, and by the mid-2020s "medallion" had become the default vocabulary for lakehouse pipelines, including in Microsoft Fabric's documentation.
how: Bronze is about capture. Ingestion jobs read from Kafka topics, CDC streams (for example Debezium change events from operational databases), files landing in object storage, or partner APIs, and append records to bronze tables with minimal transformation: perhaps parsing the envelope, but keeping the original payload. Every row gets metadata: ingestion time, source file or Kafka offset, batch ID. Bronze is append-only, so it is cheap to write and safe to replay, and retention is set by how far back you may need to recompute (often months, sometimes forever on cheap storage). The key property is replayability: if silver logic was wrong for three weeks, you fix the code and recompute silver from bronze.
Silver is about correctness. Jobs read bronze and apply the rules everyone should share: parse and type fields, normalize time zones and units, drop or quarantine malformed rows, deduplicate (events retried by clients, CDC replays), apply late-arriving updates, join reference data (map device models to categories, IPs to regions), and conform keys so the same customer or campaign has one ID everywhere. Deduplication is where idempotence matters most: silver writes are usually MERGE operations keyed by a stable event or entity ID, so reprocessing the same bronze data twice produces the same silver table, not duplicates.
Gold is about use. Each gold table has an owner, a grain and a freshness target. Typical gold tables are dimensional models (fact and dimension tables for BI), daily aggregates (impressions and spend per campaign per day), feature tables for ML, and export tables in a partner's format. Gold tables are deliberately specific: one dashboard's needs should not force a change that breaks another consumer, so it is normal to have several gold tables derived from the same silver data.
DAG scheduling ties the layers together. Each table is a node, and each dependency an edge: bronze_impressions → silver_impressions → gold_campaign_daily. A scheduler (Airflow, Dagster, Databricks Jobs) or a declarative pipeline engine runs nodes in topological order, in parallel where possible, retries failures, and records which data versions were used. Because every node is idempotent, a failed run can simply be re-run, and a backfill is the same job run for older partitions.
Incremental processing keeps costs down. Reprocessing all history every hour would be far too expensive for billions of rows, so each layer processes only new data: streaming reads of bronze (Structured Streaming with checkpoints), Delta change data feed or Iceberg incremental reads from silver into gold, and materialized views that the engine refreshes incrementally when the query allows it. This is where declarative pipelines add value: you declare "gold_campaign_daily is this aggregation over silver_impressions", and the engine works out whether it can update only the changed day partitions or must recompute.
Quality checks sit at the boundaries. Expectations on silver tables (keys not null, timestamps within a sane range, enum values valid, row counts within expected bounds) either drop and quarantine bad rows or stop the pipeline before bad data reaches gold. Gold tables add business checks: totals reconcile with source systems, no campaign spends more than its budget, yesterday's numbers did not change by more than a threshold without a known reason. Lineage, recorded by the catalog (for example Unity Catalog), shows which gold tables depend on which bronze sources, so the impact of a bad source can be traced in minutes.
Layers also map naturally to physical design and access control. Bronze tables are partitioned by ingestion date, because they are written by arrival and replayed by time range; silver and gold tables are partitioned or clustered by the columns people filter on (event date, advertiser, campaign), using features such as Delta liquid clustering or Iceberg sort orders so that queries skip most files. Deletion vectors and MERGE make row-level fixes cheap without rewriting whole files. Permissions usually tighten toward the source: bronze often contains raw personal identifiers and is readable only by the platform team; silver exposes conformed and possibly pseudonymized data to engineers; gold is shared broadly with analysts and partners. In a catalog such as Unity Catalog this becomes three schemas with different grants, which also makes audits simpler. The storage cost of the layers is real but predictable: if bronze is 1× the compressed source size, silver is often 0.8–1× and gold a few percent, so the whole medallion costs roughly twice the raw data, which is usually small compared with compute.

example: An ad platform receives impression events from CTV apps through Kafka: about 2 billion events a day, roughly 300 bytes each as JSON, so about 600 GB a day raw. Bronze stores them as compressed Parquet in a Delta table partitioned by ingestion date: about 60 to 80 GB a day after compression. Keeping 180 days of bronze costs about 12 TB of object storage, which is cheap compared with the compute that would be needed to re-ingest from sources that no longer exist.
Silver job: every 5 minutes, a streaming job reads new bronze rows, parses them, converts timestamps to UTC, drops events with missing device IDs into a quarantine table (typically 0.1 to 0.5% of events), maps app bundle IDs to publishers, and MERGEs into silver_impressions keyed by impression_id. Client retries make about 1% of events duplicates; the MERGE removes them, so a day of silver has about 1.98 billion rows.
Gold job: an hourly materialized view gold_campaign_daily aggregates silver_impressions by date, campaign and device type: about 50,000 campaigns × 4 device types ≈ 200,000 rows a day, small enough for dashboards to query directly. Because the view only reads changed date partitions through the change feed, each refresh processes the last hour's data plus late arrivals rather than the whole table.
Now the failure case. On 3 October a bug in an SDK release sends device_type as "ctv " with a trailing space for 12 days, so silver classifies those impressions as unknown devices, and gold under-reports CTV impressions by 18%. The fix: add trimming to the silver parsing code, then rerun the silver job for ingestion dates 3 to 14 October from bronze. Because silver uses MERGE by impression_id, rerunning cannot create duplicates. The gold view sees changed silver partitions through the change feed and recomputes those 12 days. Total recompute: 12 days × about 70 GB of bronze, a few hours on a modest cluster, and no source system had to resend anything. Without bronze, the 12 days of correct device types would have been lost.
intuition: Water treatment: raw water is stored, filtered water is made from it, and drinking water is bottled for each customer; if a filter was broken, you go back to the stored raw water and filter it again.
The pattern feels natural because it separates three questions people otherwise mix up: did we keep what we received, is it correct, and is it shaped for this use? Each question gets its own layer with its own owner and checks. The most important layer is the least glamorous: bronze is insurance. It costs storage, which is cheap, and saves you from the one mistake that cannot be fixed later, throwing away the original data.
mistakes: People often think medallion means exactly three copies of every table. The names describe roles, not a required count. Some sources go straight from bronze to a gold aggregate; some silver layers have several steps. The point is the contracts between layers, not the number of hops.
People often think bronze can be skipped if sources are reliable. Sources change formats, drop fields and cannot resend old data. Without an append-only raw copy, a logic bug in cleaning becomes permanent data loss.
People often think silver is "just cleaning" and can be done separately by each team. Divergent cleaning logic is how two dashboards end up with different numbers for the same metric. Shared rules for deduplication, time zones and key conformance belong in one silver layer.
People often think gold tables should serve every consumer. A single all-purpose gold table becomes a bottleneck where every change breaks someone. Consumer-specific gold tables with owners and documented grain are easier to change safely.
friction: Layers multiply storage and compute: three or more copies of large datasets, plus the jobs that maintain them. Latency adds up across layers, and the strict "always go through silver" rule can make a simple fresh metric slower than necessary. Gold layers tend to sprawl, with hundreds of tables whose owners have moved on and whose consumers nobody knows; without a catalog, lineage and regular clean-up, the lakehouse becomes a swamp again.
Medallion is a naming convention, not a quality guarantee: a silver table without tests or contracts is just another table. Schema changes in sources ripple through all layers. Deletion obligations (GDPR, DPDP Act, California's Delete Act) are harder with append-only bronze copies, because personal data must be found and removed in every layer, including history kept for replay. Finally, incremental processing has limits: some transformations (window functions over long histories, global deduplication, some joins) force large recomputes.
practice: Keep bronze append-only with ingestion metadata (source, offset or file, load time) and enough retention to replay realistic bug windows. Make every silver write idempotent with MERGE by a stable key, and put expectations on silver tables that quarantine rather than silently drop bad rows. Give every gold table an owner, a documented grain and a freshness target, and register all tables in a catalog with lineage.
Process incrementally: streaming or change-feed reads between layers, materialized views with incremental refresh where supported, and partitioning by date so backfills touch only affected partitions. Plan deletions across layers from the start: keep personal identifiers in identifiable columns, use deletion vectors or MERGE deletes, and apply suppression lists during replays. Review gold tables quarterly and delete the ones nobody reads.
quiz: What guarantee does each medallion layer give? || Bronze: everything was kept as received, so you can replay. Silver: one clean, deduplicated, conformed version of each entity or event. Gold: a table shaped for a specific use, with a known grain, owner and freshness.
Why should silver writes use MERGE by a stable event ID? || So that reprocessing the same bronze data, after a failure or a backfill, produces the same silver rows instead of duplicates. That makes the job idempotent and safe to re-run.
Bronze holds 70 GB of compressed data per day, and a parsing bug affected 15 days. How much bronze data must be reprocessed, and why is this possible at all? || About 15 × 70 = 1,050 GB, roughly 1 TB. It is possible because bronze kept the original events; without it, the affected days could not be corrected.
Why can strict medallion layering hurt a fresh operational metric? || Each layer adds processing delay (micro-batches, refresh schedules), so forcing a simple real-time count through bronze, silver and gold can add minutes. A direct streaming path or a real-time store may fit better, as long as it is reconciled with gold later.
A team wants one gold table that serves finance, the ads dashboard and an ML model. What would you suggest? || Separate gold tables per consumer, derived from the same silver data, each with its own grain, owner and freshness. Shared definitions belong in silver or a semantic layer, so changes for one consumer do not break the others.

@@ declpipelines
value: In a declarative pipeline you describe which tables should exist and how each is derived from others, and the engine decides how to build and maintain them. Instead of writing a job that reads table A, writes table B, then triggers another job, and adding schedules, retries, checkpoints and dependency logic by hand, you write "B is this query over A; C is this query over B". The engine builds the dependency graph, runs everything in the right order, processes only what changed when it can, recovers from failures and checks data quality rules.
This changes the unit of work from "job" to "dataset". Data engineers spend most of their time on the meaning of tables, not on orchestration plumbing, and the same definition can run as a batch refresh or as a continuously updated stream. Spark 4.1 added this to open-source Spark as Spark Declarative Pipelines, contributed by Databricks from its Delta Live Tables (now Lakeflow Declarative Pipelines). dbt applies the same idea to SQL warehouses, and streaming databases such as Materialize and Feldera, and Flink's materialized tables, push it to continuous incremental maintenance.
Several lower concepts make it possible. DAG scheduling (L2) orders the declared tables and runs them in parallel where they are independent. Row lineage and change feeds (L2) tell the engine which upstream rows changed, so it can update only affected results. Distributed snapshots and checkpoints (L2) let streaming tables resume exactly where they stopped. Idempotence (L2) makes every refresh safe to re-run. And the style is inspired by functional programming (L3): each table is a pure function of its inputs, so the engine can reorder, cache and recompute freely.
terms: Dataset — a named table or view that the pipeline maintains.
Flow — the computation that writes into a dataset, usually a query over other datasets.
Streaming table — a dataset fed incrementally from append-only sources; each new input row is processed once.
Materialized view — a dataset whose contents always equal the result of its query, refreshed fully or incrementally.
Incremental view maintenance (IVM) — updating a materialized view using only the changes to its inputs.
Dependency graph — the DAG of datasets and the flows between them, built by reading the declarations.
Expectation — a data-quality rule on a dataset, with an action for violating rows: keep and log, drop, or fail.
Dry run — validating all declarations and the graph (missing tables, cycles, schema errors) without processing data.
Full refresh — recomputing a dataset from scratch instead of incrementally.
history: Databases have had declarative derived data for a long time. Views (1970s) are named queries, and materialized views store a view's result for fast reads. Research on maintaining them incrementally began in the 1980s; Gupta and Mumick's 1995 survey summarized the techniques, and commercial databases (Oracle, then others) shipped materialized views with incremental "fast refresh" for some query shapes in the late 1990s. Spreadsheets brought the same model to everyone: cells defined by formulas, recalculated when inputs change.
Big data pipelines went the other way at first: Hadoop and early Spark pipelines were imperative jobs glued together by schedulers such as Oozie and Airflow (2015). dbt (2016) brought declarations back for analytics engineers: each model is a SELECT statement, dependencies come from references between models, and dbt builds them in order, with tests. On the streaming side, Differential Dataflow (McSherry and others, 2013) and the companies built on it (Materialize, founded 2019) showed that complex SQL views, including joins, could be maintained incrementally with low latency; DBSP (Budiu and others, 2023, behind Feldera) gave a general algebra for incremental computation.
Databricks announced Delta Live Tables in 2021 (generally available in 2022), combining declared streaming tables and materialized views, expectations and automatic orchestration on Delta Lake; it was renamed Lakeflow Declarative Pipelines in 2025, and Databricks contributed the core to Apache Spark, where it shipped as Spark Declarative Pipelines in Spark 4.1. Flink added materialized tables, and Snowflake dynamic tables and BigQuery materialized views offer similar features inside warehouses.
how: Writing a pipeline means writing declarations. In Spark Declarative Pipelines, a Python function decorated as a materialized view or table returns a DataFrame, or a SQL file contains statements such as CREATE STREAMING TABLE silver_events AS SELECT … FROM STREAM bronze_events and CREATE MATERIALIZED VIEW gold_daily AS SELECT date, campaign_id, count(*) … GROUP BY …. A pipeline specification lists the source files, the catalog and schema, and settings. Nothing runs when the code is loaded; the functions are only registered.
The engine then builds the dependency graph, the DAG-scheduling concept at work. It analyses each query to find which datasets it reads, which gives the edges of the DAG. A dry run checks the whole graph: every referenced dataset exists, there are no cycles, schemas are compatible. Problems that would otherwise appear at 3 a.m. halfway through a run are caught in seconds in CI. During a run, datasets execute in topological order, independent branches run in parallel, and each flow is retried on failure.
Streaming tables process each input row once. They read append-only sources (Kafka, Auto Loader files, a bronze Delta table read as a stream) and keep their progress in checkpoints: which offsets or file versions have been processed, plus any operator state such as aggregation buffers or deduplication keys. This is the distributed-snapshot concept: after a failure, the flow restarts from the last checkpoint and reprocesses at most the last incomplete micro-batch, and idempotent or transactional writes make that safe. Streaming tables are ideal for bronze and silver layers, where data only grows.
Materialized views promise more: their content must equal the full result of their query at refresh time, even when inputs are updated or deleted. The simple way is full recomputation. The efficient way is incremental view maintenance, using the row-lineage concept: the engine reads the change feed of each input (rows inserted, updated, deleted since the last refresh) and computes the change to the output. For a filter or projection, the change is just the filtered changes. For SUM or COUNT grouped by a key, it adds and subtracts deltas for affected groups. For a join, it joins the changes of one side with the current state of the other. Engines inspect each query to decide whether an incremental plan exists; queries with non-deterministic functions, some window functions or complex nested aggregations fall back to full recomputation, and good engines report which strategy they chose.
Data quality is declared next to the data. An expectation such as valid_event_time: event_time IS NOT NULL AND event_time > '2020-01-01' can keep violating rows but record metrics, drop them, or fail the update. The engine collects pass and fail counts per expectation per run, so data quality becomes a time series you can monitor rather than an assumption.
Because each dataset is a function of its inputs, the engine can do things that are risky in hand-written jobs: re-run any dataset safely, run a full refresh of one table and everything downstream, change compute size without code changes, and track lineage automatically. This is the functional-programming inspiration paying off: no hidden state outside the declared inputs and checkpoints means the system can reason about the whole pipeline.
Pipelines also have execution modes. In triggered mode, an update runs once (on a schedule or after upstream data lands), processes everything new, and stops, so compute is paid only during the run. In continuous mode, streaming flows keep running with low latency, at the cost of always-on compute. Several flows can write into one streaming table: for example, one flow per regional Kafka topic appending into a single bronze table, or a one-time backfill flow that loads historical files into the same table the live flow feeds. Because the engine knows the whole graph, it can also choose the cluster size and parallelism per update, and serverless versions scale compute up for a backfill and down for small incremental runs. All of this would be custom code in a hand-written job: here it is configuration on top of the same declarations.

example: A pipeline has three datasets. bronze_impressions is a streaming table reading a Kafka topic with about 25,000 events per second. silver_impressions is a streaming table that parses, deduplicates and drops events without a device ID. gold_campaign_daily is a materialized view: SELECT date, campaign_id, count(*) AS impressions, sum(cost) AS spend FROM silver_impressions GROUP BY date, campaign_id.
Each hourly run first does a dry run of the graph, then updates bronze with the last hour's 90 million events, then silver, then gold. The expectation "device_id IS NOT NULL" drops 0.2% of events, 180,000 rows, and records the count. Silver now has about 89.8 million new rows.
For gold, the engine checks whether the query can be maintained incrementally. SUM and COUNT grouped by date and campaign_id can: it reads silver's changes (89.8 million inserted rows), aggregates them into about 40,000 (date, campaign_id) groups, and merges those deltas into the existing view, adding counts and spends to matching rows. The gold table has 50,000 campaigns × 400 days ≈ 20 million rows, but the refresh touches only about 40,000 of them. Compare the cost: a full recompute would aggregate 400 days × about 2 billion rows = 800 billion rows; the incremental refresh aggregates 90 million. That is roughly 9,000 times less input.
Now a change that breaks incrementality. An analyst edits gold to add "rank of the campaign by spend within its advertiser for that day", a window function. The engine cannot express the change to ranks as a simple delta, so it switches that view to full recomputation and reports this in the refresh details. The team notices the run time jump from 3 minutes to 70 minutes, moves the ranking into a small separate view computed from gold_campaign_daily (20 million rows instead of 800 billion), and incremental refresh comes back.
intuition: A spreadsheet for tables: you write the formula for each table once, and when inputs change, only the cells that depend on them are recalculated.
Declarative pipelines feel natural for the same reason SQL does: you say what result you want, and a planner with more information than you decides how to get it. Dependency order, retries and checkpoints are mechanical, so a machine should handle them. Incremental maintenance is how an accountant updates totals: add today's receipts to yesterday's balance instead of re-adding the whole year. The engine just applies that idea systematically, and tells you when a formula makes it impossible.
mistakes: People often think "declarative" means the engine will always refresh incrementally. Many queries cannot be maintained incrementally, and the engine silently or explicitly falls back to full recomputation. Check the refresh strategy for expensive views.
People often think materialized views and streaming tables are interchangeable. A streaming table processes each new input row once and does not reprocess history when its logic changes or inputs are updated; a materialized view always reflects the full query result. Use streaming tables for append-only ingestion and materialized views for results that must stay correct when inputs change.
People often think declarative pipelines replace all orchestration. They manage dependencies between datasets inside a pipeline; tasks such as calling an external API, sending files to partners or coordinating several pipelines still need a general scheduler.
People often think expectations that drop rows make data clean. Dropped rows are lost from downstream results; if a source suddenly drops 30% of rows, totals fall quietly. Monitor expectation metrics and alert on unusual drop rates.
friction: Incremental view maintenance covers common shapes (filters, projections, grouped sums and counts, many joins) but not everything, and the rules differ by engine and version, which makes performance hard to predict. Debugging is harder when the engine decides execution: you inspect plans and refresh logs instead of your own code. Features and syntax differ across Spark Declarative Pipelines, Lakeflow, dbt, Materialize, Snowflake dynamic tables and Flink, so pipelines are not easily portable.
Changing a streaming table's logic does not reprocess history; correcting past data needs an explicit full refresh, which may be expensive or impossible if the source retained too little data. Large pipelines with hundreds of datasets can have long planning times, and a single failing dataset can block everything downstream. Finally, the declarative model fits deterministic data transformations; side effects, external calls and non-deterministic functions do not fit it well.
practice: Declare datasets with clear inputs and one responsibility each; keep heavy logic in silver and simple aggregations in gold so incremental refresh stays possible. Use streaming tables for append-only ingestion and materialized views for results that must stay consistent with changing inputs.
Run dry runs in CI for every change. Put expectations on every silver dataset, choose drop versus fail deliberately, and alert on expectation metrics. After deploying a new or changed materialized view, check the refresh details to confirm the incremental strategy, and watch run times for sudden jumps that indicate a fallback to full recomputation.
Plan for history changes: know how to full-refresh a table and everything downstream, how long sources retain data, and how much a full refresh costs. Keep non-dataset tasks (exports, notifications) in a general orchestrator that triggers the pipeline.
quiz: What is the difference between a streaming table and a materialized view? || A streaming table processes each new input row once and appends results, which suits append-only sources. A materialized view always equals its query's full result and is refreshed, incrementally or fully, when inputs change.
How can an engine refresh SUM(cost) GROUP BY campaign_id incrementally? || It reads the input's change feed, aggregates only the inserted, updated or deleted rows into per-campaign deltas, and adds or subtracts those deltas in the stored result.
A gold view aggregates 300 days × 1 billion rows, and each refresh brings 50 million new rows. Roughly how much less input does an incremental refresh read than a full one? || 300 billion rows versus 50 million rows, about 6,000 times less.
Why does a dry run catch problems that hand-written jobs often hit only in production? || It builds and validates the whole dependency graph from the declarations (missing tables, cycles, schema mismatches) before any data is processed, so errors appear in CI, not halfway through a nightly run.
A team adds a window function to a large materialized view and refresh time jumps 20×. What happened, and what would you do? || The window function made incremental maintenance impossible, so the engine fell back to full recomputation. Move the window computation into a separate, smaller view built on the aggregated result, so the large view stays incremental.

@@ lambdakappa
value: Lambda and Kappa are two answers to one question: how do you give users results that are both fresh (seconds old) and correct (complete, deduplicated, recomputable when logic changes)? In the early 2010s, stream processors were fast but unreliable, and batch systems were reliable but slow. The Lambda architecture, described by Nathan Marz around 2011, ran both: a batch layer that periodically recomputed accurate results from all data, and a speed layer that produced approximate results for recent data, merged at query time. The Kappa architecture, proposed by Jay Kreps in 2014, argued that one streaming system is enough if the input is kept in a replayable log: to fix or change logic, run a new version of the stream job from the beginning of the log and switch over when it catches up.
The debate shaped modern data platforms. Kafka's long retention, exactly-once stream processing (Flink, Kafka Streams, Spark Structured Streaming) and lakehouse tables that serve both streaming and batch reads all grew from the Kappa argument, while the Lambda insight, keep raw data and be able to recompute, survives in the medallion bronze layer. For engineers, these two patterns are the vocabulary for deciding how fresh and how correct each output needs to be, and what that costs.
They stand on two lower concepts. The log (L2, the write-ahead-log idea made public by Kafka) makes reprocessing possible: data kept in order with offsets can be read again from any point. Idempotence (L2) makes reprocessing safe: running the same computation over the same data must not double-count, whether in a batch recompute or a stream replay.
terms: Batch layer — a system that recomputes results from the complete master dataset, accurately but with hours of delay.
Speed layer — a stream processor that updates results for recent data with seconds of delay, possibly approximately.
Serving layer — the store that answers queries by combining batch views and real-time views.
Master dataset — the immutable, append-only record of all raw events, the source of truth for recomputation.
Replay (reprocessing) — reading a retained log again from an earlier offset to recompute results with new logic.
Event time versus processing time — when an event happened versus when the system processed it.
Retention — how long a log or table keeps data, which bounds how far back you can replay.
Backfill — recomputing outputs for a past period.
history: In 2011 Nathan Marz, then at BackType and soon at Twitter, created Apache Storm, one of the first widely used stream processors. Storm offered at-least-once processing without built-in state or exactly-once guarantees, so real-time counts could drift. In his blog post "How to beat the CAP theorem" (October 2011) and later the book "Big Data" (with James Warren, 2015), Marz described the Lambda architecture: keep an immutable master dataset of all events, compute batch views with Hadoop from scratch every few hours, cover the gap with Storm, and merge both in a serving database. Human mistakes and stream errors would be corrected automatically by the next batch run.
Engineers quickly felt the cost: every piece of logic written twice, in MapReduce and in Storm, with different APIs and subtle differences in results. Jay Kreps, co-creator of Kafka at LinkedIn, published "Questioning the Lambda Architecture" in 2014. He proposed using Kafka's retained, partitioned log as the master dataset and a single stream-processing code path; reprocessing meant starting a second instance of the job from offset zero, writing to a new output table, and switching readers when it caught up. Around the same time Google's MillWheel (2013) and Dataflow model (2015) showed that streaming systems could be correct, with exactly-once state and event-time windows, and Apache Flink (2014–2015) brought those ideas to open source.
By the late 2010s, Kafka Streams and Flink provided exactly-once stateful processing, Spark Structured Streaming (2016) unified batch and streaming APIs, and lakehouse formats let streaming jobs write tables that batch jobs read. Most platforms now use hybrids: streaming ingestion into lakehouse tables, streaming or incremental transformations, and batch backfills over the same tables with the same code.
how: Lambda has three layers. All incoming events are appended to the master dataset (in the original design, files on HDFS). The batch layer periodically runs a job over the entire master dataset, say every 6 hours, producing batch views: for example, total impressions per campaign up to the last batch cutoff. Because the job recomputes from scratch from immutable data, it is simple and self-correcting: if yesterday's logic had a bug, the next run with fixed code produces correct numbers. The speed layer processes only events newer than the last batch cutoff, incrementally updating real-time views. The serving layer answers queries by combining both: batch_view(campaign) + realtime_view(campaign since cutoff). When a new batch run completes, the corresponding real-time data is discarded.
The weakness is in the speed layer and the duplication. The same business logic (deduplication rules, attribution windows, currency conversion) must be implemented in two frameworks and kept consistent. When the results differ, users see numbers jump when batch views replace real-time ones, and engineers debug two code bases. The speed layer may also be approximate (at-least-once processing, no handling of late events), which is acceptable only because the batch layer overwrites it.
Kappa removes the batch layer by making the stream reliable and replayable. All events go into a log with long retention, such as a Kafka topic kept for 30 days or more, or with tiered storage for much longer. One stream job computes results continuously and writes them to an output table. To change logic, deploy version 2 of the job reading the log from the earliest offset (or from the oldest offset still relevant), writing to a new output table. Version 2 processes history much faster than real time, because it reads from storage at full speed, until it catches up with the head of the log. Then readers switch to the new table and version 1 is stopped. This is the log concept at work: offsets make every replay deterministic and resumable.
Correctness in Kappa depends on the stream processor. It needs exactly-once state (checkpointed snapshots of operator state together with input offsets), event-time processing with watermarks so late events land in the right windows, and idempotent or transactional sinks so that restarts do not double-write. Idempotence is the bridge: whether the job reprocesses one micro-batch after a crash or all of history after a logic change, the same input must produce the same output.
Modern hybrids combine the ideas. Events land in a bronze lakehouse table through a streaming job; silver and gold layers are maintained by streaming or incremental jobs; and backfills reuse the same code in batch mode over the same tables, because engines such as Spark and Flink run one API in both modes. The lakehouse table becomes the long-term replayable log, cheaper than keeping years in Kafka. Real-time OLAP stores often use a Lambda-like hybrid internally: real-time segments from Kafka and offline segments rebuilt in batch, with a time boundary deciding which to query.
The practical choice comes down to replay cost and logic complexity. Replaying 30 days of a 100,000-events-per-second stream means reading about 260 billion events; at a replay throughput of 2 million events per second, that takes about 36 hours. If logic changes weekly, that is fine; if business users need corrected numbers in an hour, a batch recompute over partitioned lakehouse tables may be faster and cheaper.
Cut-over is where Kappa reprocessing usually goes wrong, so it deserves care. While version 2 catches up, compare its output with version 1 on overlapping periods: row counts, sums of key measures and a sample of individual records, per hour or per day. Differences should be explained by the intended logic change, nothing else. Watermarks and allowed lateness must be the same as in production, or the replayed job will close windows differently. Any external side effects (sending emails, calling partner APIs, charging customers) must be disabled in the replaying job, or keyed with idempotency keys, because the replay would otherwise repeat them for every historical event. Finally, readers should switch by changing a pointer, such as a view definition or table alias, so that rollback is one more pointer change.

example: An ad platform needs campaign spend per hour, visible to advertisers within a minute, and correct to the cent for billing.
Lambda version: Storm counts spend per campaign per hour as events arrive, writing to a key-value store. A Hadoop job runs every 6 hours over all raw events since the start of the month, applies fraud filtering (which needs 2 hours of data to decide) and writes exact totals. At 14:00, the dashboard shows exact batch totals up to 12:00 plus Storm's counts from 12:00 to 14:00. At 18:30 the next batch completes and replaces the 12:00–18:00 real-time numbers; because Storm did not apply fraud filtering, advertisers see their spend drop by about 3% for those hours. Two teams maintain two implementations of the spend rules, and a mismatch in currency rounding causes a support ticket every week.
Kappa version: one Flink job reads the impressions topic (50,000 events per second, retained for 35 days), applies the same fraud rules with event-time windows and a 2-hour allowed lateness, and writes hourly spend per campaign to a table using transactional commits. Advertisers see provisional numbers within a minute, and they are updated (not replaced by another system) when late or fraudulent events are resolved.
In March, the fraud rules change. Version 2 of the job starts from the offset of 1 March, 25 days ago. The backlog is 25 × 86,400 × 50,000 ≈ 108 billion events. With enough parallelism to process 1.5 million events per second, the replay takes about 20 hours, while version 1 keeps serving. When version 2 catches up, reports switch to its table. One code path, one set of rules, and the cost is a day of extra compute plus enough log retention to cover the replay window.
intuition: Lambda keeps a fast rough draft and a slow clean copy, then staples them together; Kappa keeps the original recording and, when you want a better edit, simply plays the recording again through the new editor.
Both follow from one principle: never lose the raw events, because they are the only way to fix mistakes. Lambda trusts batch for correctness because, in 2011, streams could not be trusted. Kappa notices that if the stream processor becomes trustworthy and the log is kept, the batch system is just a slow, separate way of doing the same thing. Today's hybrids pick per output: replay from the log when it is short, recompute from lakehouse tables when the history is long.
mistakes: People often think Kappa means "no batch processing ever". It means one code path and replay from a log; that replay is itself a high-throughput catch-up run, and many teams run the same streaming code in batch mode over lakehouse tables for backfills.
People often think Lambda is obsolete. Its central lesson, keep immutable raw data and be able to recompute, is now standard practice, and some systems (real-time OLAP stores with offline segments) still merge fresh and corrected data at query time.
People often think a replayable log makes reprocessing free. Replay needs retention long enough for the history you want, enough compute to catch up quickly, space for a parallel output table, and a cut-over plan. For years of history, the cost can be very large.
People often think stream results will match batch results automatically. Late events, deduplication windows, time zones and non-deterministic code make them differ unless event-time semantics, idempotent sinks and deterministic logic are designed in.
friction: Lambda's double implementation is expensive and error-prone, and users see numbers change when batch views replace real-time ones. Kappa's costs are long log retention (expensive in Kafka unless tiered storage is used), replay time and compute for large histories, and the difficulty of running two versions side by side, including external side effects that must not happen twice.
Stateful streaming jobs with large state (deduplication over days, joins over long windows) are slow to rebuild from scratch. Schema evolution in a long-retained log means version 2 must read every historical format. And many correctness needs (billing reconciliation, fraud decisions that arrive days later, regulatory corrections) still fit batch thinking better, which is why pure Kappa is rare and most organizations run a hybrid that must be documented carefully.
practice: Keep the raw events immutable and replayable: in Kafka with tiered storage for short horizons, and in bronze lakehouse tables for long ones. Prefer one code path that can run in streaming and batch modes (Spark, Flink, Beam) over two separate implementations.
Design for reprocessing from the start: deterministic logic, event-time windows with explicit lateness, idempotent or transactional sinks, versioned output tables, and a documented cut-over procedure. Estimate replay time (events in window ÷ replay throughput) before promising how fast a logic change can be applied.
Label results by their state, provisional or final, and reconcile streaming outputs against batch recomputations on a schedule; disagreement beyond a small threshold is a bug, not noise. Choose per output: dashboards may accept provisional numbers; billing should use reconciled, final ones.
quiz: What problem was the Lambda architecture designed to solve? || Getting results that are both fresh and correct when stream processors were unreliable: a batch layer recomputed accurate views, a speed layer covered recent data approximately, and a serving layer merged them.
How does Kappa apply a change in processing logic? || It runs a new version of the stream job from an earlier offset of the retained log into a new output table, lets it catch up to the present, then switches readers and stops the old version.
A stream has 20,000 events per second, and you must replay 30 days with a job that processes 800,000 events per second. How long does the replay take? || 30 × 86,400 × 20,000 ≈ 51.8 billion events; at 800,000 per second that is about 64,800 seconds, roughly 18 hours.
Why does idempotence matter for both architectures? || Batch recomputations and stream replays process the same events again. Without idempotent or transactional writes, every rerun, crash recovery or replay would double-count results.
When would you choose to backfill from lakehouse tables in batch rather than replay a Kafka log? || When the history is long (months or years), log retention is short or expensive, or corrected results are needed quickly. Partitioned lakehouse tables can be recomputed in parallel with the same logic, more cheaply than replaying a long log.

@@ dimmodel
value: Dimensional modelling organizes analytical data around two kinds of tables. Fact tables record measurements of business events at a declared grain: one row per ad impression, per order line, per daily account balance. Dimension tables describe the context of those events: date, campaign, advertiser, device, product, customer, region. Facts hold keys pointing to dimensions, and the picture of a large fact table in the middle with dimensions around it gives the name "star schema".
The model matches how people ask analytical questions: "measure something, sliced and filtered by some context". Total spend by advertiser and month; impressions by device type for campaigns in a region; conversion rate by creative format. In a star schema those questions are always the same shape of query, a fact table joined to a few dimensions, filtered, grouped and summed. That makes data easy to understand for analysts, easy to generate for BI tools, and fast for columnar engines, which are optimized for exactly this pattern. Most warehouses and lakehouse gold layers, most dbt projects and most semantic layers are built this way.
It stands on three lower concepts. The relational model (L3) supplies tables, keys and joins. Normalization (L3) is deliberately relaxed: dimensions are denormalized into wide, redundant tables so queries need fewer joins and humans see all attributes in one place. Join algorithms (L2) make star joins fast: a huge fact table joined to small dimensions is exactly the case where engines broadcast the dimensions and use hash joins, or push dimension filters into the fact scan.
terms: Fact table — a table of measurements of business events, with foreign keys to dimensions.
Dimension table — a table of descriptive attributes used to filter and group facts.
Grain — the precise meaning of one fact row, declared before anything else.
Measure — a numeric fact; additive (sums across all dimensions), semi-additive (sums across some, like account balances not across time) or non-additive (ratios, distinct counts).
Surrogate key — a meaningless integer key for a dimension row, independent of source system IDs.
Slowly changing dimension (SCD) — a technique for attributes that change over time; type 1 overwrites, type 2 adds a new row with validity dates.
Conformed dimension — a dimension shared across fact tables with the same keys and meanings, so metrics from different facts can be combined.
Star schema versus snowflake schema — denormalized dimensions versus dimensions split into normalized sub-tables.
history: Relational databases in the 1970s and 1980s were designed for transactions, with highly normalized schemas that are excellent for updates but awkward for analysis: a simple sales report could need ten joins. Decision support systems needed a different shape. Bill Inmon, often called the father of data warehousing, described in "Building the Data Warehouse" (1992) a central, normalized, integrated enterprise warehouse feeding departmental data marts.
Ralph Kimball took a different approach in "The Data Warehouse Toolkit" (1996): model each business process directly as facts and dimensions, build conformed dimensions so marts fit together (the "bus architecture"), and optimize for usability and query speed. The book catalogued techniques still used today: grain declaration, surrogate keys, slowly changing dimensions types 1 to 3 (later extended), periodic snapshot and accumulating snapshot fact tables, factless fact tables, and junk and degenerate dimensions. The "Inmon versus Kimball" debate ran through the 1990s and 2000s; in practice Kimball's star schemas won the presentation layer. Data Vault (Dan Linstedt, around 2000) later offered another integration-layer style.
Columnar warehouses (Vertica, Redshift, BigQuery, Snowflake) and then lakehouses changed the economics: storage became cheap and scans fast, so wide denormalized "one big table" designs became popular, especially for real-time OLAP stores with limited join support. Yet dbt (2016), semantic layers and BI tools kept the star schema as the default contract between data engineers and analysts, and the third edition of Kimball's book (with Margy Ross, 2013) remains a standard reference.
how: Design starts with a business process and its grain. For ad delivery, the process is "an ad was shown", and the grain might be "one row per impression". Declaring the grain first prevents the most common modelling errors: mixing daily totals and individual events in one table, or double-counting when a row means different things in different contexts. Then choose dimensions (everything that describes the event: date, time of day, campaign, creative, advertiser, publisher app, device, household, region) and measures (cost, duration watched, a completion flag).
Dimension tables are wide and denormalized. A campaign dimension might hold campaign name, objective, start and end dates, budget, advertiser name, advertiser industry, agency and sales region, all in one row, even though advertiser data repeats for every campaign of that advertiser. This deliberately breaks normalization: it wastes some storage in a small table but saves joins and makes the table readable. Each dimension row gets a surrogate key, a small integer, so facts store compact keys and the model is insulated from source systems changing their IDs.
History in dimensions needs a decision. If a campaign moves from the North region to the West region, should last month's impressions report under North or West? A type 1 dimension overwrites the attribute, so all history reports under West. A type 2 dimension closes the old row (valid_to = change date) and inserts a new row with a new surrogate key; facts loaded before the change point to the old row and report under North, facts after it point to the new row. Most "why did last quarter's numbers change?" questions come from choosing the wrong type.
Fact tables are long and narrow: a few integer keys and numeric measures per row, billions of rows. Three common types exist. Transaction facts record individual events (impressions, orders). Periodic snapshots record the state at regular intervals (daily account balance, daily campaign budget remaining). Accumulating snapshots track a process with milestones (order placed, shipped, delivered), updating the row as milestones happen. Measures must be classified by additivity. Cost is additive. A daily balance is semi-additive: you can sum across accounts but not across days. Click-through rate and unique reach are non-additive: summing daily reach double-counts people seen on several days, so reach needs distinct counting at query time or mergeable sketches such as HyperLogLog stored in the fact table.
Conformed dimensions connect processes. If the impressions fact and the conversions fact both use the same campaign and date dimensions with the same keys, a report can combine impressions and conversions by campaign and month, a "drill-across" query, and the numbers line up. Kimball's bus matrix is simply a table of business processes (rows) against shared dimensions (columns), used to plan which dimensions must be conformed.
The query engine is where join algorithms add value. A typical star query filters dimensions (advertiser industry = 'automotive', date in October), joins them to the fact table, groups by a few attributes and sums measures. Engines broadcast the small filtered dimensions to every worker, build hash tables on them and stream the fact table through, so the big table is never shuffled. Better still, dynamic partition pruning and runtime filters take the set of qualifying dimension keys and push it into the fact scan, skipping files and row groups that cannot match. Columnar storage means the fact scan reads only the key and measure columns needed.
In lakehouses the same model is built with dbt or declarative pipelines: dimension tables as merge-maintained Delta or Iceberg tables (SCD type 2 implemented with MERGE), fact tables partitioned by date and clustered by common filters, and a semantic layer defining metrics once (spend, impressions, reach, CTR) on top of the star schema.

example: An ad platform builds a star schema for impressions. Grain: one row per impression. The fact table stores date_key (4 bytes), campaign_key (4), device_key (2), app_key (4), household_key (8), cost in micro-units (8), seconds watched (2) and a completed flag (1): about 33 bytes uncompressed per row, often under 10 bytes after columnar compression. At 2 billion impressions a day, that is roughly 66 GB a day raw, about 15 to 20 GB compressed.
Dimensions are small: 50,000 campaigns, 300 device models, 20,000 apps, 3,650 dates. The campaign dimension, with 40 attributes per row, is about 50,000 × 500 bytes = 25 MB.
Query: "October spend and completion rate by advertiser for automotive campaigns on CTV". The engine filters dim_campaign to automotive campaigns (2,100 rows), dim_device to CTV (60 rows) and dim_date to October (31 rows). It broadcasts these small sets to all workers and pushes their keys into the fact scan as runtime filters. The fact table is partitioned by date, so only 31 daily partitions are read, about 62 billion rows; of these, perhaps 8% match the campaign and device filters. Reading 4 columns of 62 billion rows with good compression is a few hundred GB of scanning, which a large cluster finishes in tens of seconds; a pre-aggregated gold table at the grain (date, campaign, device_type) would answer the same question from about 6 million rows in under a second.
Now the reach trap. The team adds a daily_reach measure (distinct households per campaign per day) to a daily aggregate and a dashboard sums it over October: 4.2 million. But many households saw the campaign on several days; the true distinct October reach is 1.6 million. Reach is non-additive. The fix is to store a HyperLogLog sketch of household keys per campaign per day (a few kilobytes each) and merge sketches over any date range: merged sketches estimate October reach as 1.6 million within about 1%.
Finally an SCD example. Campaign 4411 moves from the North sales region to West on 15 October. With type 2, dim_campaign has two rows for 4411: key 9001 (North, valid until 14 October) and key 9876 (West, from 15 October). Impressions before the 15th carry key 9001; after, key 9876. October spend by region correctly splits between North and West, and September's report does not change next month.
intuition: Every business question is "measure something, sliced by some context", so put the measurements in the middle and the context around them, like a star.
The design follows how people already think about reports: columns of numbers and rows of descriptions. Denormalized dimensions read like a well-labelled index card, and a fact row is a receipt with a few codes on it. Declaring the grain is like agreeing on the unit before adding numbers. Most failures of analytics, numbers that disagree or change unexpectedly, come from skipping one of these simple agreements, not from slow queries.
mistakes: People often think star schemas are obsolete because columnar engines can scan one big wide table. Wide tables are fast to query but hard to maintain: changing a campaign's name means rewriting billions of rows, and every consumer copies its own version. Stars keep descriptive data in one place and are often flattened into wide tables only for specific serving uses.
People often think every numeric column can be summed. Distinct counts (reach, unique users), ratios (CTR, completion rate) and snapshots (balances) give wrong answers when summed across days or groups. Store their components (numerators, denominators, sketches) instead.
People often think slowly changing dimensions are an edge case. Attributes change all the time (regions, categories, owners), and the type 1 versus type 2 choice decides whether historical reports change. It must be decided per attribute.
People often think the grain can be decided later. Mixing grains in one table, or joining facts at different grains without care, causes double-counting that is very hard to detect after the fact.
friction: Dimensional models need upfront agreement on grain, definitions and conformed dimensions across teams, which is organizationally hard and slows the first deliveries. Type 2 dimensions, late-arriving facts (an impression arriving after its campaign's attributes changed) and late-arriving dimensions (a fact referencing a campaign not yet loaded) require careful handling.
At very large scale, star joins on the fly may be too slow for interactive dashboards, so teams add aggregate tables and wide serving tables, which must be kept consistent. Many-to-many relationships (a household with several demographic segments, an impression attributed to several conversions) do not fit the simple star and need bridge tables. Real-time OLAP stores often support joins poorly, pushing teams to denormalize at ingestion. And a star schema alone does not guarantee consistent metrics; different dashboards can still compute "CTR" differently unless a semantic layer defines it once.
practice: Start every fact table by writing its grain in one sentence, and refuse to mix grains. Build conformed dimensions for the entities shared across processes (date, campaign, advertiser, device, household) and reuse them everywhere. Decide SCD type per attribute, implement type 2 with surrogate keys and validity dates, and test that historical reports stay stable.
Classify every measure by additivity. Store sums and counts for ratios, and HyperLogLog or similar sketches for distinct counts such as reach. Partition fact tables by date, cluster by the most common filters, and let the engine broadcast dimensions and push runtime filters into fact scans.
Add pre-aggregated gold tables at coarser grains for heavily used dashboards, generated from the base facts so they agree. Define metrics once in a semantic layer or in dbt metrics, and document each table's grain, owner and freshness in the catalog.
quiz: What is the grain of a fact table, and why declare it first? || The exact meaning of one row, such as "one impression". Declaring it first prevents mixing levels of detail and the double-counting that follows.
Why are dimensions deliberately denormalized? || A wide dimension keeps all descriptive attributes in one table, so queries need fewer joins and people can read it easily. The redundancy costs little because dimensions are small compared with facts.
Daily reach for a campaign is 100,000, 120,000 and 90,000 on three days. Can total reach for the three days be 310,000? What is the range? || Not necessarily; reach is non-additive. It lies between 120,000 (if every viewer on the other days was already counted) and 310,000 (if no household repeated). Merged sketches or distinct counting give the real value.
A campaign changes sales region mid-month. How do type 1 and type 2 dimensions report that month? || Type 1 overwrites the attribute, so the whole month and all history appear under the new region. Type 2 adds a new dimension row with a new key, so impressions before the change stay under the old region and later ones go to the new region.
When would you flatten a star schema into one wide table? || For a specific serving use where joins are slow or unsupported, such as a real-time OLAP store or a heavily used dashboard. Generate the wide table from the star so the star remains the single source of truth.
