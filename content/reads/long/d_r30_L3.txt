@@ relmodel
value: The relational model says that all data in a database is a set of tables, and that you get data out by describing the result you want, not by describing the steps to find it. A table is a "relation": a set of rows (tuples) with named, typed columns (attributes). Rows are found by their values, never by their position or by a pointer. This one decision is why a query written in 1985 can still run today on a database with completely different storage, indexes and hardware.
The problem Codd was solving in 1970 was that programs were tied to the physical layout of the data. In the hierarchical and network databases of that time (IBM IMS, CODASYL), an application walked pointers from record to record. If the storage layout changed, for example a new index or a different record order, application code broke. The relational model introduced data independence: the logical view (tables and constraints) is separate from the physical layer (files, indexes, partitions, compression). The system, not the programmer, chooses the access path.
For the layers above, this is the foundation of nearly everything with a schema. OLTP databases (PostgreSQL, MySQL) store related tables joined by keys. Dimensional models (Kimball star schemas) are relational tables with a special shape. Spark SQL, Databricks, Pinot, Snowflake and BigQuery all present data as relations, even though underneath they use columnar files on object storage. The layers below make the model precise. Set theory gives the definition (a relation is a set of tuples, so there are no duplicate rows and no row order). The notion of a mathematical relation gives the table its meaning (a subset of a product of domains) and gives keys their meaning (a function from key to the rest of the row). Logic gives queries their meaning: a query is a formula, and the answer is every tuple that makes the formula true.
terms: Relation — a set of tuples that all have the same attributes; in practice, a table.
Tuple — one row: a fixed set of values, one per attribute.
Attribute and domain — a named column, and the set of values it is allowed to hold (integer, date, text).
Schema and instance — the schema is the table's structure and rules (names, types, constraints); the instance is the rows stored right now.
Key — a minimal set of attributes whose values identify at most one tuple; the primary key is the key chosen as the main identifier.
Foreign key — attributes in one relation that must match a key value in another relation; this is how tables are linked.
Data independence — the ability to change the physical storage (indexes, file format, partitioning) without changing queries (physical independence) or to change the logical schema without breaking all applications (logical independence).
Relational calculus — a way to write a query as a logical formula that describes the wanted tuples, with no order of steps.
Closure — the result of every query operator is again a relation, so operators can be chained without limit.
history: Edgar F. "Ted" Codd was a mathematician working at IBM's San Jose research laboratory. In June 1970 he published "A Relational Model of Data for Large Shared Data Banks" in Communications of the ACM. An earlier IBM research report (1969) had a first version. His argument was simple and forceful: store data as relations, use predicate logic to query it, and keep the user away from the physical layout. In 1972 he showed that relational algebra and a restricted form of relational calculus have the same expressive power, a result now called Codd's theorem. This gave the model a solid theoretical base: a query language could be both easy to state (calculus) and easy to execute (algebra).
IBM management at first preferred to protect its IMS business. Two projects proved the idea in practice. System R at IBM San Jose (from 1973, running to about 1979) built a full relational system with the SEQUEL language, a cost-based optimizer and transactions. INGRES at UC Berkeley (Michael Stonebraker and Eugene Wong, from 1973) did the same with the QUEL language. Larry Ellison's company (later Oracle) shipped a commercial SQL product in 1979, and IBM followed with SQL/DS (1981) and DB2 (1983). Codd received the ACM Turing Award in 1981. He also published a list of rules for what counts as a truly relational system (the 12 rules, 1985) because vendors used the word loosely.
The model has been declared dead many times and has come back each time. Object databases (1980s), XML databases (2000s) and the NoSQL wave (2009 to 2015) each promised to replace tables. Stonebraker and Hellerstein (2005) and Stonebraker and Pavlo (2024) argue that each challenger failed or added a relational interface, such as SQL on Hadoop, SQL on Cassandra, or joins in document stores.
how: Start with domains and relations. A domain is a set of allowed values, for example the integers, or the set of valid country codes. A relation schema R(A₁, …, Aₙ) names n attributes, each with a domain. An instance of R is a finite set of tuples, and each tuple assigns one value from the right domain to each attribute. Because an instance is a set, two facts follow at once. First, there are no duplicate tuples. Second, there is no row order and no column order that carries meaning. This is where set theory contributes: the definition is exact, so the operations on relations (union, difference, product) inherit their meaning from set operations. Real SQL tables are relaxed: they are bags (duplicates allowed) and can be sorted, but the model underneath stays the set.
Next come keys. A superkey is a set of attributes that never has the same values in two different tuples. A candidate key is a superkey that cannot be made smaller. One candidate key is chosen as the primary key. Seen as mathematics, a key means that the relation is a function from key values to the remaining attribute values; this is the contribution of the "relations and functions" concept. A foreign key is a constraint that says every value in attributes F of relation R must also appear as a key value in relation S. This is an inclusion dependency, and it replaces pointers: instead of "this order record points to that customer record", the order stores the customer id, and the database checks that such a customer exists. References are by value, so rows can be moved, copied, sorted and partitioned freely.
Integrity constraints are the logical part of the schema. A primary key, a unique constraint, a NOT NULL, a CHECK (amount > 0) and a foreign key are each a sentence in first-order logic that must be true for every instance. For example, a key on customer_id means: for all tuples t1 and t2, if t1.customer_id = t2.customer_id then t1 = t2. The database rejects any change that would make a sentence false. This is the contribution of logic to the model, and it is why constraints can be checked automatically and reasoned about (for example, by an optimizer that removes a join because a foreign key guarantees the match).
Queries are also logic. In relational calculus a query is written as {t | φ(t)}: all tuples t for which the formula φ is true. For example, {c.name | Customer(c) ∧ c.city = 'Bengaluru' ∧ ∃o (Order(o) ∧ o.cid = c.id ∧ o.amount > 1000)}. The formula says what is true of the answer. Nothing in it says which table to read first or whether to use an index. The same query can be written as a tree of operators in relational algebra (select, project, join), which says how to compute the answer in some valid way. Codd's theorem says that these two forms describe the same set of queries (when the calculus is restricted to "safe" formulas whose answers are finite). That equivalence is the bridge from a declarative idea to an executable plan.
Because the user states only the result, the system is free to choose how. This is the job of the optimizer: it takes one logical query, enumerates equivalent plans using algebraic rules, estimates the cost of each from statistics, and runs the cheapest. Storage can be a B-tree, a column store with zone maps, or Parquet files in object storage, and the query text stays the same. The closure property supports this: every operator takes relations and returns a relation, so plans can be nested and rewritten piece by piece, and a view (a saved query) can be used anywhere a table can be used.
The model also makes choices that matter later. It assumes a closed world: a fact that is not in the database is taken to be false. It allows a NULL marker for missing information, which Codd added later and which forces three-valued logic (true, false, unknown). And it separates identity from location: the pure model has no object identifiers, only values.

  Physical (hidden): hash join? index on Order.cid? Parquet files?
example: Use the two tables in the diagram. Customer has three tuples and Order has three tuples. The question is: "Which customers in Bengaluru have placed an order above 1000?"
In calculus, we write the condition: a customer c qualifies if c.city is 'Bengaluru' and there exists an order o with o.cid = c.id and o.amount > 1000. Check each customer. Asha (id 1) is in Bengaluru, and order 10 has cid 1 and amount 1500, so she qualifies. Ravi is in Pune, so he fails the city test. Meera (id 3) is in Bengaluru, but her only order, 12, has amount 900, which is not above 1000, so she fails. The answer is the one-tuple relation {Asha}. Notice that the answer is a relation too, with a single attribute name.
Now see data independence at work. Suppose Order has 50 million rows and Customer has 2 million. The database may run this query in several ways. Plan A scans all of Order, keeps rows with amount > 1000 (say 1% remain, 500,000 rows), then looks up each matching customer by primary key and checks the city. Plan B first finds customers in Bengaluru (say 5%, which is 100,000 customers) and, for each, uses an index on Order.cid to find orders. Plan C hashes the 100,000 Bengaluru customers into memory and streams Order once against it. The cost differs by orders of magnitude, but the result is the same set. The person who wrote the query does not choose, and does not need to change the query if someone adds an index on Order.cid tomorrow or moves Order to Parquet files.
Now see constraints at work. The foreign key on cid says no order can name a customer that does not exist. If a program tries to insert (13, 99, 200) and no customer has id 99, the database rejects the insert. Every query can then assume that the join Order to Customer loses no order rows. An optimizer can use this fact: if a query joins Order to Customer but uses no Customer column, it may drop the join completely.
intuition: A well-kept ledger where you can ask any question by describing the entries you want, and the clerk decides which shelves to open.
The model is natural because it matches how people already state facts: "customer 1 is named Asha and lives in Bengaluru". A table is a list of such statements with the same shape. Queries then become questions about these statements, which is exactly what logic is for. Because the answer to a logical question does not depend on how the statements are stored, storage is free to change. That is the whole trick: pick an abstraction (sets of facts) that is simple enough to reason about mathematically and rich enough to say most things, and then let the machine do the work of finding the data.
mistakes: People often think "relational" means tables are related to each other through foreign keys. In fact "relation" is the mathematical word for the table itself (a subset of a product of domains). Foreign keys are one kind of constraint between relations, not the reason for the name.
People often think the relational model is the same as SQL. In fact SQL departs from the model in several ways: it allows duplicate rows, keeps row order in results, has NULL with three-valued logic, and lets tables exist without keys. Codd and C. J. Date criticised these differences for decades.
People often think the model is about the row-store layout on disk. In fact it is purely logical. A column store, a Parquet file, and a distributed Spark DataFrame all implement the same relational idea with different physical layouts, and that freedom is the point of data independence.
People often think NoSQL disproved the model. In fact NoSQL systems mostly dropped features (joins, multi-row transactions, fixed schema) to scale or to ship faster, and many later added them back. The remaining real limit is that deep nested or graph-shaped data fits a flat relation awkwardly, which is a modelling cost, not a refutation.
tradeoffs: Choose a strict relational schema with constraints when data is shared by many applications and correctness matters more than speed of change, for example orders, payments, and billing. Keys and foreign keys catch whole classes of bugs at write time, and the cost is that a schema change needs a migration. Choose a flexible document or JSON column when records vary a lot in shape and are mostly read as a whole, accepting that the database can no longer check or optimize inside the document.
Choose normalized tables (one fact in one place) for the system of record that takes writes, and denormalized wide tables for analytics where a query reads a few columns from billions of rows. Normalized data needs joins on read; denormalized data needs pipelines that keep copies consistent on write. In a lakehouse, a common compromise is to keep a normalized layer for correctness and publish denormalized tables from it.
Choose enforced constraints (foreign keys in the database) for transactional systems, and informational constraints for large analytical tables. Delta and Databricks, for example, allow primary and foreign keys that are not enforced and are only hints for the optimizer and for people; enforcing a foreign key on a table with 50 billion rows would cost a lookup per insert. You give up the safety net and must test the data in the pipeline instead.
friction: The best-known problem is the impedance mismatch: application code works with nested objects and lists, while the model wants flat tables in normal form. Mapping an order with line items, addresses and tags to five tables, and back, is tedious and slow, and object-relational mappers hide cost and produce surprising queries (for example the N+1 query problem, where one list query triggers one more query per row).
Schemas are strict. This protects data, but early in a product's life, when fields change weekly, it slows development. In large organizations, a schema change on a table with billions of rows needs careful migration, and consumers of that table must be coordinated. Systems such as Delta, Iceberg and Parquet use schema evolution rules to soften this, but breaking changes still need agreement.
Joins are the weak point at scale. A join between two large tables on a distributed system needs a shuffle: both sides are re-partitioned over the network by the join key. This is the main cost in Spark jobs, and the main reason people denormalize. The model says nothing about how to partition data, so physical design (partition keys, clustering, co-location) is left to people.
NULL and bags cause real confusion. A comparison with NULL gives "unknown", and a row filtered with WHERE x <> 5 silently drops rows where x is NULL. SQL's bag semantics also break some of the clean algebraic laws. Finally, the model cannot easily express recursion and graph traversal (reachability, bill of materials); SQL added recursive queries in 1999, but they are awkward and often slow compared with dedicated graph engines.
practice: Start every schema design by writing down the facts and the keys: what identifies each thing, and what depends on it. Give each table a primary key, even if the system does not enforce it. Prefer a stable surrogate key (a generated id) when the natural key can change, but also keep a unique constraint on the natural key.
Use foreign keys, NOT NULL, CHECK and UNIQUE constraints in transactional databases; they are cheap compared with the cost of finding bad data later. In analytical tables where constraints are not enforced, add data-quality tests in the pipeline (uniqueness of the key, no orphan foreign keys, not-null on required columns) and run them on every load.
Keep the logical and physical design separate in your thinking. Write the query to say what you want; then use the plan (EXPLAIN) to see how the engine runs it, and change the physical side (indexes, partitioning, clustering, file layout, statistics) when the plan is poor. Avoid putting physical knowledge into the query (such as forcing join order with hints) unless you have measured it.
quiz: Why is a relation described as a set, and what two consequences follow? || A relation is a set of tuples, so there are no duplicate tuples and no meaningful order of rows or columns. Real SQL tables relax this (bags, ORDER BY) but the model underneath is a set.
What is data independence, and how does the relational model achieve it? || It means queries do not depend on physical storage. The user states the result in terms of tables and values, and the system picks the access path (index, scan, join algorithm) using the logical-to-physical separation and the algebraic equivalence of plans.
Why do relational systems use foreign keys instead of pointers? || A foreign key refers to a row by value, which stays valid when rows move, are sorted, partitioned or copied. A pointer ties the program to a physical location. The database can also check the value against the key of the other table.
Table Order has 50 million rows, 1% have amount > 1000, and 5% of 2 million customers are in Bengaluru. How many Order rows and customers does each filter keep, and why might the optimizer filter customers first? || 500,000 Order rows and 100,000 customers. The customer side is smaller, so building a hash table from it and streaming Order, or using an index on Order.cid, can read less data. Statistics let the optimizer compare these plans.
When would you not enforce a foreign key in the database? || When the table is very large or loaded in bulk and the check would cost a lookup per row, such as an analytical lakehouse table. Then you keep the key as documentation or an optimizer hint and verify it in the pipeline with data tests.
interview: Codd's model says queries are declarative. What makes it possible for the system to choose a plan? || Closure and algebraic equivalence. Every operator maps relations to relations, and laws such as pushing selections below joins and reordering joins keep the result the same. The optimizer enumerates equivalent trees and picks the cheapest by estimated cost, so the query text does not fix the plan.
Why is SQL not truly relational, and what breaks because of it? || SQL has bags, NULL with three-valued logic, and tables without keys. Duplicates break some set laws (for example, UNION versus UNION ALL), and NULL makes NOT IN and outer-join filters behave unexpectedly. Optimizers must be careful with rewrites that are valid for sets but not for bags.
You have an orders table with a customer_id column but no foreign key. What can go wrong, and what would you do in a Delta table that cannot enforce it? || Orders can reference customers that do not exist, so joins silently drop rows or analytics miscount. In Delta, I would declare the informational constraint, add a pipeline test for orphan rows on each load, and quarantine bad records instead of failing silently.
Why did NoSQL systems drop joins, and why did many bring them back? || Joins across partitions need network shuffles and coordination, so early NoSQL systems avoided them to scale writes and keep latency predictable. Users still needed to combine data, so they pushed joins into application code, which was slower and error-prone; so systems added SQL and joins again.

@@ relalgebra
value: Relational algebra is a small set of operators that take tables and return tables: select (filter rows), project (pick columns), join (combine tables), union, difference, and a few more. Because every operator returns a table, operators can be nested into a tree, and any query you can state in the relational model is such a tree. This tree is the plan that a database actually runs: Postgres, Spark, DuckDB and Databricks all show you a query plan whose nodes are algebra operators (Filter, Project, Join, Aggregate, Union).
Algebra exists because a declarative language such as SQL says what you want, but a machine needs steps. Algebra is the middle layer. It is precise enough to execute, and it has laws (like arithmetic has laws) that say which rearrangements give the same result. These laws are the entire reason query optimizers can work. An optimizer does not guess: it applies rewrites that are proven to preserve the answer, such as moving a filter below a join, and then chooses the cheapest of the equivalent forms.
The layers below supply the meaning. Set theory defines the operators: union, intersection and difference are exactly the set operations, and join is built from the Cartesian product of sets. Logic defines the selection conditions: a predicate such as city = 'Bengaluru' AND amount > 1000 is a formula in propositional and first-order logic, and the laws for combining predicates (De Morgan, distribution) are the laws of logic. The layers above use the algebra directly: SQL is compiled into it, predicate pushdown and join reordering are its laws applied, adaptive query execution rewrites the unfinished part of a plan with valid algebraic changes, and the Volcano iterator model implements each operator as a small piece of code that pulls rows from its children.
terms: Selection σ — keeps the rows that satisfy a condition; \( \sigma_{\text{amount} > 1000}(\text{Order}) \).
Projection π — keeps only the named columns (and, in set algebra, removes duplicate rows); \( \pi_{\text{name}}(\text{Customer}) \).
Join ⋈ — combines rows from two relations that satisfy a condition; the natural join matches columns with equal names.
Cartesian product × — every row of one relation paired with every row of the other; n × m rows.
Union, difference — set operations on two relations with the same columns: rows in either, or rows in the first but not the second.
Rename ρ — gives a new name to a relation or a column, so that expressions can refer to the same table twice.
Semi-join and anti-join — keep the rows of the left relation that do have (semi) or do not have (anti) a match on the right; they are EXISTS and NOT EXISTS.
Set versus bag semantics — in a set no duplicate rows exist; in a bag (SQL's default) duplicates are kept and counted.
Equivalence rule — a law saying two algebra expressions always return the same relation, for example \( \sigma_p(R \bowtie S) = \sigma_p(R) \bowtie S \) when \( p \) uses only R's columns.
history: Codd's 1970 paper already defined the main operations on relations: projection, join, union and others, under different names. In 1972 he published "Relational Completeness of Data Base Sublanguages" and defined a clear set of operators: select, project, product, union, difference (plus join and division as derived operators), and a relational calculus. He proved that the algebra and the safe calculus can express exactly the same queries. A language that can express everything the algebra can is called relationally complete, and this became the yardstick for query languages.
Through the 1970s, systems used the algebra in two ways. For users, it was one of the notations for queries (Codd also proposed the calculus-based language ALPHA). For implementers, it was an internal form. The System R team at IBM did not give users the algebra; they gave them SEQUEL/SQL and translated it into a tree of operations. Selinger and colleagues' 1979 paper "Access Path Selection in a Relational Database Management System" described the first cost-based optimizer, which enumerated join orders over such trees and chose the cheapest, and it is still the base of most optimizers.
Later work extended the algebra to match real systems. Klug (1982) added aggregation. Researchers studied bag semantics, because SQL keeps duplicates; the textbook of Garcia-Molina, Ullman and Widom uses bags as the default. Aho and Ullman (1979) showed that the basic algebra cannot express transitive closure (reachability), which is why SQL needed recursive queries (SQL:1999) and why datalog is a stronger language. Rewrite-based optimizer frameworks such as Graefe's Volcano and Cascades (1990s) made the equivalence rules into data, so that new rules can be added without rewriting the optimizer. Spark's Catalyst (2015) applies the same idea, with rules written as pattern matches in Scala.
how: The core has five operators that cannot be built from each other: selection σ, projection π, Cartesian product ×, union ∪ and difference −, plus rename ρ. Everything else is derived. Intersection is \( R - (R - S) \). A theta-join \( R \bowtie_\theta S \) is \( \sigma_\theta(R \times S) \), but an engine never builds the product; it uses a join algorithm (hash join, sort-merge join, nested loops with an index). A natural join matches equally named columns and then drops the duplicate columns. Division ("customers who bought all products") is built from product, projection and difference. An anti-join, \( R \triangleright S \), keeps rows of R with no match in S, and corresponds to NOT EXISTS. Set theory is doing the work here: each operator is a set operation, and the identities between them (\( R \cup S = S \cup R \), \( R \cap (S \cup T) = (R \cap S) \cup (R \cap T) \)) are the identities of sets.
Real systems add extended operators. Grouping and aggregation γ[keys; sum(x)] partitions the rows by key and reduces each group. Duplicate elimination δ turns a bag into a set. Sort τ and limit have no place in pure algebra (relations are unordered) but every engine needs them. Outer joins keep unmatched rows and fill with NULL. Window functions and recursion add more. In SQL the data are bags, so each operator has a bag definition: UNION ALL adds multiplicities, UNION also removes duplicates, and a projection does not remove duplicates unless DISTINCT is written.
The value of the algebra is its laws, because laws justify rewrites. The important ones are these. Selections can be split and reordered: \( \sigma_{p \land q}(R) = \sigma_p(\sigma_q(R)) \). A selection can move below a join when it only uses columns of one side: \( \sigma_p(R \bowtie S) = \sigma_p(R) \bowtie S \). This is the law behind predicate pushdown. Projections can be pushed down too, as long as the join columns are kept (this is column pruning, which saves a lot of I/O in a column store). Joins are commutative and associative: \( R \bowtie S = S \bowtie R \) and \( (R \bowtie S) \bowtie T = R \bowtie (S \bowtie T) \), so the engine may pick any join order. Selections distribute over union. Logic gives the laws that apply inside predicates: De Morgan, and the fact that \( p \land \text{true} = p \), which lets the optimizer simplify conditions before it uses them.
Join reordering shows why this matters. For three tables, there are many valid trees. Because (R ⋈ S) ⋈ T and R ⋈ (S ⋈ T) give the same result, the optimizer can compare the sizes of the intermediate results and choose the order that keeps them small. The number of possible orders grows very fast (for n tables there are (2n−2)!/(n−1)! ordered binary trees, which is about 17 billion for 10 tables), so engines use dynamic programming over subsets with pruning, or heuristics, and they depend on size estimates. The estimates come from statistics: a selection with selectivity s keeps s × |R| rows; an equi-join of R and S on a key keeps about |R| × |S| / max(distinct values) rows. If the estimate is wrong, the "best" order can be very bad, which is why adaptive execution corrects plans using the real sizes seen at run time.
The last piece is execution. A plan is a tree; the engine runs it by letting each operator produce rows for its parent. In the Volcano model, each operator offers a next() call that pulls one row from its children, so Filter, Project and Join are small reusable pieces. In vectorized and compiled engines the same tree is evaluated batch by batch or compiled into one loop. The semantics stay those of the algebra, and the engine is free to change everything else.
diagram:
  SELECT c.name FROM Customer c JOIN Orders o ON o.cid = c.id
  WHERE c.city = 'Bengaluru' AND o.amount > 1000

  Naive plan (as written)               Rewritten plan (laws applied)

      pi[name]                              pi[name]
         |                                     |
   sigma[city and amount]                join[id = cid]
         |                                /          \
    join[id = cid]            sigma[city=Blr]   sigma[amount>1000]
      /        \                    |                 |
  Customer    Orders            Customer           Orders
  (2M rows)  (50M rows)        (2M -> 100k)       (50M -> 500k)

  Join input: 2M x 50M pairs possible    Join input: 100k + 500k rows
  Law used: sigma[p](R join S) = sigma[p](R) join S   (p uses only R)
example: Take Customer with 2,000,000 rows, of which 5% live in Bengaluru, and Orders with 50,000,000 rows, of which 1% have amount above 1000. The query asks for the names of Bengaluru customers with an order above 1000, the same query as in the diagram.
As written, the plan has a single filter on top of a join. If an engine executed it literally, it would join 2 million customers to 50 million orders first (an equi-join output of about 50 million rows, since each order has one customer), then filter. That means shuffling or hashing 52 million input rows and building a 50-million-row intermediate result.
Apply the law \( \sigma_{p \land q}(R \bowtie S) = \sigma_p(R) \bowtie \sigma_q(S) \), valid because city belongs only to Customer and amount only to Orders. Now the filter on Customer keeps 5% of 2,000,000 = 100,000 rows, and the filter on Orders keeps 1% of 50,000,000 = 500,000 rows. The join now reads 600,000 rows instead of 52,000,000, which is about 87 times less input. If both tables are Parquet files, the filters can also be pushed into the scan, so many row groups are skipped using min/max statistics. Add the projection law: the join needs only id, name for Customer and cid for Orders, so the scan reads three columns, not all the columns of both tables.
Last, estimate the join output. Assume order customers are spread evenly, so each of the 100,000 Bengaluru customers has about 25 orders (50M / 2M), of which 1% pass the amount test, which is 0.25 per customer on average. The join returns roughly 100,000 × 25 × 0.01 = 25,000 rows. Because the filter on amount is independent of the customer in this model, you can check it the other way: 500,000 filtered orders × 5% Bengaluru = 25,000. Both routes agree, and this is how an optimizer estimates the size of intermediate results. In real data these filters are often correlated (high-value customers cluster in some cities), and then the estimate is wrong; this is a standard failure mode.
intuition: Arithmetic for tables: a few operations, combined freely, with laws that tell you which rearrangements keep the answer unchanged.
Arithmetic gives us a similar freedom: because a × (b + c) = a × b + a × c, we may compute whichever side is cheaper. The same holds for tables. Once the operators are few, closed (they return tables) and lawful, a query becomes an expression that can be rearranged by simple rules. The optimizer is just a search among equal expressions for the cheapest one, and the laws are guaranteed by the set theory and logic underneath.
mistakes: People often think the algebra is a language you must learn to use a database. In fact most engineers never write it. It is the internal form: EXPLAIN shows it. Learning to read the plan is the practical skill.
People often think SQL clauses run in the order they are written. In fact the logical order is FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT; the algebra plan expresses this order, and the optimizer is allowed to execute differently as long as the answer is the same.
People often think pushing a filter down is always a safe rewrite. In fact it is valid for inner joins, but for an outer join, moving a filter on the null-producing side below the join changes the result, because the unmatched rows that the outer join would have kept with NULLs are removed early. Bag semantics and NULLs also break some set-based laws, so engines must check each rewrite's conditions.
People often think relational algebra can express any query on tables. In fact it cannot express recursion such as "all ancestors of a person" (transitive closure), nor counting without the extended aggregate operator. Recursive CTEs and Datalog go beyond it.
tradeoffs: Choose to rely on the optimizer's rewrites (write plain SQL, let the engine reorder) when statistics are fresh and the query shape is common. Choose to take control (hints, query splitting into staged tables, explicit join order) when estimates are wrong by more than about 10 times, for example after heavy skew or correlated filters. You give up simplicity and portability, and your hint may be wrong when the data changes.
Choose set semantics (DISTINCT, UNION) when you need uniqueness and the data are small or already sorted; choose bag semantics (UNION ALL, no DISTINCT) when duplicates are acceptable or impossible. Removing duplicates needs a sort or a hash over all rows, which can cost more than the rest of the query on billions of rows.
Choose a hash join when one side fits in memory (the small side builds, the large side probes) and the join is an equality; choose a sort-merge join when inputs are already sorted or too large for memory and you need range or sorted output; choose a broadcast join in a cluster when one side is smaller than a few hundred megabytes, so the large side is not shuffled. You give up memory in the first and last cases, and sorting time in the second.
Choose left-deep join trees (a chain, the classic search space) for fast planning with many tables; choose bushy trees when branches are independent and can run in parallel, accepting a much larger search space.
friction: The algebra is clean, but SQL is not. SQL uses bags, so the neat equivalences of set algebra hold only in modified form. NULL means "unknown", and its three-valued logic breaks laws such as \( p \lor \lnot p = \text{true} \), so some rewrites that a logician would accept are wrong in SQL (for example, x NOT IN (1, NULL) can never be true). Outer joins are not associative in general, which limits join reordering, and every engine has to carry a list of conditions for each rewrite.
Cost estimation is the weak point, not the algebra. The laws give the set of valid plans, but choosing among them needs the size of intermediate results, and these sizes are estimated from histograms and distinct-value counts that assume independence between columns. Real data is skewed and correlated, so estimates can be wrong by orders of magnitude after three or four joins. Research on "learned" cardinality estimation and runtime re-planning (adaptive query execution in Spark) are partial answers.
The search space is huge. Joining 20 tables has more plans than any engine can enumerate, so engines cut the search with heuristics, limits (Postgres switches to a genetic search at 12 relations by default, geqo_threshold) and plan caching. Finally, the pure algebra has no model of ordering, windows, recursion, user-defined functions or nested data, and each extension needs its own rules, so the clean theory covers only part of what a real optimizer does.
practice: Learn to read plans. Run EXPLAIN (Postgres, Spark, Databricks, DuckDB) and look for the operators of the algebra: scans with pushed filters, projections, joins with their type, aggregates. Check that filters appear next to the scans, not above the joins, and that only the needed columns are read. In Spark, compare the logical plan, the optimized logical plan and the physical plan (EXPLAIN EXTENDED) to see which rules fired.
Write queries so that the laws can apply. Keep predicates simple and on raw columns (WHERE order_date >= '2026-01-01', not WHERE year(order_date) >= 2026 with a function that hides the column from statistics and pruning). Avoid non-deterministic functions and UDFs inside filters, because they stop pushdown. Prefer EXISTS or a semi-join to a join followed by DISTINCT when you only need to know whether a match exists.
Keep statistics current (ANALYZE in Postgres, ANALYZE TABLE in Spark, automatic statistics in Delta/Unity Catalog) so that the estimated sizes are close. When a plan is wrong, check the estimated row counts at each node against the actual row counts first. That points to the bad statistic, and often a single extra column statistic, a rewrite of a correlated predicate, or a staged table fixes it.
Know the join types your engine offers: Spark has inner, left/right/full outer, left semi, left anti and cross joins, and uses a different physical join (broadcast hash, shuffle hash, sort-merge) for each case depending on sizes.

value: SQL (Structured Query Language) is the language in which you describe the table you want, and the database works out how to produce it. You write SELECT … FROM … WHERE …; you do not write loops, you do not choose indexes, and you do not say which table to read first. SQL has been the main interface to data for about 45 years. Analysts, applications, BI tools and now many machines (ORMs, AI agents) generate it, and nearly every data system speaks it: PostgreSQL, MySQL, Oracle, Spark SQL, Databricks, Snowflake, BigQuery, Pinot, DuckDB, and even stream processors such as Flink SQL and ksqlDB.
The reason this matters is that SQL separates the question from the execution. One query text can run on a laptop over a CSV file or on a 1,000-node cluster over petabytes. The same skill, the same dashboards and the same code move between systems, and the engine can get faster underneath you. Every attempt to replace SQL (QUEL, Hadoop MapReduce code, Pig, NoSQL query APIs) ended with the replacement adding a SQL layer, because declarative queries are much shorter than hand-written dataflow and are safe to optimize.
Three layers below make SQL work. Parsing and grammars turn the text into a syntax tree: a lexer cuts the text into tokens, and a context-free grammar defines which token sequences are valid queries. Relational algebra gives the tree its meaning and its executable form: after parsing and name resolution, the query becomes a tree of select, project, join and aggregate operators. Logic gives the WHERE clause its meaning: a condition is a formula, and a subquery with EXISTS is a quantifier. The layers above rely on SQL as their contract: OLTP applications read and write with it, data warehouses and distributed SQL engines (MPP) are built to run it fast.
terms: Declarative — describes the result wanted, not the steps to compute it.
DDL, DML, DQL — data definition (CREATE TABLE), data manipulation (INSERT, UPDATE, DELETE, MERGE) and data query (SELECT) statements.
Parse tree / AST — the tree built from the query text; the planner turns it into a logical plan.
Logical plan and physical plan — the logical plan is a tree of algebra operators; the physical plan picks algorithms (hash join, index scan) for each operator.
CTE (common table expression) — a named subquery introduced with WITH, used to build a query in readable steps; WITH RECURSIVE allows loops.
Window function — computes a value over a set of related rows without collapsing them, such as rank() OVER (PARTITION BY user ORDER BY ts).
NULL and three-valued logic — NULL means unknown; a comparison with NULL is neither true nor false but unknown, and WHERE keeps only rows where the condition is true.
Dialect — a vendor's variant of SQL; the ISO/ANSI standard is only a common core.
history: In 1970 Codd published the relational model, but he proposed mathematical languages (algebra and calculus). At IBM San Jose, Donald Chamberlin and Raymond Boyce designed a friendlier language. They first built SQUARE and then SEQUEL ("Structured English Query Language", 1974), meant for non-mathematicians. The name was shortened to SQL because of a trademark problem. It was implemented in System R (1974 to 1979), which also proved that a cost-based optimizer can match hand-tuned navigation code.
Commercial products followed fast. Relational Software, later Oracle, shipped Oracle V2 in 1979, before IBM's own products (SQL/DS in 1981, DB2 in 1983). ANSI standardized SQL in 1986 and ISO in 1987. The big step was SQL-92, which fixed a large common core (joins syntax, isolation levels, types). SQL:1999 added recursive queries, triggers and user types; SQL:2003 added window functions and MERGE; SQL:2011 added temporal tables; SQL:2016 added JSON functions; SQL:2023 added property graph queries (SQL/PGQ) and more JSON support. Vendors adopt these at different speeds, so dialect differences remain.
The 2000s said SQL could not scale, and the NoSQL and MapReduce movement followed. By about 2010 the direction reversed: Hive (2008) put SQL on Hadoop, Spark SQL (2014 to 2015) brought a Catalyst optimizer, Google published Dremel (2010) and Spanner's SQL, and Snowflake, BigQuery and Databricks SQL made SQL the default for the cloud. In 2024 Google proposed a pipe syntax (FROM … |> WHERE … |> AGGREGATE …) to fix the reading order of SQL; BigQuery supports it and Spark 4.0 added it.
how: Execution of a SQL statement has fixed stages. First, the lexer splits the text into tokens (keywords, names, numbers, strings). The parser applies the SQL grammar and builds an abstract syntax tree. Postgres uses a Bison grammar, and Spark uses an ANTLR grammar. This is where parsing and grammars contribute: the grammar defines which strings are queries at all, and the parser reports errors at the exact token. Second, the analyzer (binder) resolves names against the catalog: which table does "orders" mean, what type is "amount", does the column exist, and which function is meant. It also checks types and inserts casts. Under ANSI mode a bad cast raises an error; with older permissive modes it may produce NULL.
Third, the tree becomes a logical plan, a tree of relational-algebra operators. This is the key translation. FROM and JOIN become scans and joins, WHERE becomes a selection σ, GROUP BY becomes an aggregation γ, SELECT becomes a projection π, DISTINCT removes duplicates, ORDER BY sorts, LIMIT cuts. The order is not the written order: SQL's logical evaluation order is FROM, WHERE, GROUP BY, HAVING, window functions, SELECT, DISTINCT, ORDER BY, LIMIT. This explains why a column alias defined in SELECT cannot be used in WHERE (WHERE runs earlier), but can be used in ORDER BY (which runs later). Subqueries and CTEs become nested or shared sub-plans; the optimizer usually "unnests" a correlated subquery into a join.
Fourth, the optimizer rewrites the logical plan with algebra laws (push filters and projections down, prune unused columns, fold constants, reorder joins using statistics), then chooses physical algorithms and picks the lowest estimated cost. Fifth, the executor runs the physical plan, usually with iterators or vectorized batches. Logic comes in at the semantic level. WHERE is a first-order formula: AND, OR, NOT, comparison, IN, EXISTS (an existential quantifier) and NOT EXISTS (a negated quantifier). Everything the user writes with those words has a logical meaning that the optimizer may transform, such as turning IN (subquery) into a semi-join.
SQL's semantics have two parts that differ from the clean algebra. First, tables are bags: duplicates are allowed, and DISTINCT or UNION removes them on request. Second, NULL. Any comparison with NULL gives UNKNOWN, AND, OR and NOT follow three-valued truth tables (UNKNOWN AND FALSE is FALSE, UNKNOWN OR TRUE is TRUE), and WHERE and HAVING keep only rows that evaluate to TRUE. So WHERE x <> 5 drops rows with x NULL, and x = NULL is never true; you must write x IS NULL. Aggregates such as SUM and AVG skip NULLs, while COUNT(*) counts rows and COUNT(x) counts non-NULL values.
Beyond a single SELECT, SQL has a few features that give it power. Joins (inner, outer, semi, anti, cross, lateral) combine tables. Window functions compute running totals, ranks and moving averages without collapsing rows. CTEs make a long query readable, and WITH RECURSIVE does graph walks and hierarchies. Set operators (UNION, INTERSECT, EXCEPT) combine results. MERGE applies a set of inserts, updates and deletes from a source table in one statement, which is the basis of upserts and change-data-capture loads in Delta and Iceberg. Transactions (BEGIN, COMMIT) group statements into ACID units.
Two practical mechanisms sit around this pipeline. Prepared statements split parsing from execution: the server parses and plans a query with placeholders once, then runs it many times with different values. This saves planning time (often a fraction of a millisecond to several milliseconds per query) and, more importantly, stops SQL injection, because values are never parsed as SQL text. Plan caching has a cost, though: a plan built for one parameter value (a rare city) may be poor for another (a common city), a problem known as parameter sniffing. In distributed engines the physical plan is also split into stages that exchange data (shuffles), and the engine may compile each stage into one tight loop of generated code, as Spark's whole-stage code generation does, so that the abstract operator tree costs almost nothing at run time.

example: Take two tables: orders(id, cid, amount) with 50 million rows and customers(id, city) with 2 million rows. Query: "top five cities by number of orders above 1000".
SELECT c.city, COUNT(*) AS n FROM orders o JOIN customers c ON o.cid = c.id WHERE o.amount > 1000 GROUP BY c.city ORDER BY n DESC LIMIT 5;
Follow the stages. The parser builds the tree. The analyzer checks that o.amount is a numeric column and that c.city exists. The logical plan is Limit(Sort(Aggregate(Filter(Join(orders, customers))))). The optimizer applies two laws. The filter amount > 1000 involves only orders, so it moves below the join and, in Parquet, into the file scan. If 1% of orders pass, 500,000 rows reach the join instead of 50 million. Column pruning means the scan reads only cid and amount from orders and only id and city from customers. Since customers is small (2 million rows, maybe 60 MB for two columns), it is broadcast to every worker and a hash table is built in memory. Orders are streamed and probed, with no shuffle of the large side. Then a partial aggregate counts per city on each worker, and a final aggregate merges the counts: only a few thousand cities, so the network cost is tiny. Sort and limit become a top-5 operation (a heap), and no full sort of the cities is needed.
Now the NULL trap, with small numbers. Suppose customers has 1,000 rows, and 10 of them have city = NULL. The query SELECT COUNT(*) FROM customers WHERE city <> 'Pune' returns the number of customers whose city is known and not Pune: the 10 NULL rows are excluded, even though "not Pune" feels true for them. And SELECT * FROM orders WHERE cid NOT IN (SELECT id FROM customers_blocked) returns zero rows if even one id in customers_blocked is NULL, because the comparison with that NULL is UNKNOWN for every cid that is not otherwise matched. The safe form is NOT EXISTS (SELECT 1 FROM customers_blocked b WHERE b.id = o.cid). Both effects follow directly from three-valued logic and from WHERE keeping only TRUE.
intuition: A precise question written in a formal language, which the database answers by whatever method it finds cheapest.
SQL is natural because asking is easier than instructing. The hardest part of data work is knowing the best route (which index, which join order), and that depends on data sizes that change every day. If the programmer fixes the route, the program becomes wrong as the data grows. If the programmer states only the result, the engine can choose a new route as the data changes. This is the same idea as a compiler that chooses instructions: you state meaning, the machine picks the means. The grammar lets people write the meaning in a language close to English, the algebra gives it an exact form, and logic tells both sides what it means.
mistakes: People often think SQL is executed in the order it is written. In fact the logical order starts with FROM and ends with LIMIT, and the physical order is chosen by the optimizer. That is why WHERE cannot see SELECT aliases, and why filters are applied before grouping (WHERE) or after (HAVING).
People often think two logically equal queries have equal cost. In fact the optimizer cannot always see they are equal; a correlated subquery, a function on an indexed column, or an OR across columns can block rewrites and change cost by 100 times or more. Look at the plan.
People often think NULL behaves like zero or an empty string. In fact it means unknown, so NULL = NULL is unknown (not true), and NOT IN with NULLs returns nothing. Count and sum also treat NULL in different ways.
People often think SQL is just for data analysts and not a real programming language. In fact it is Turing-complete with recursive CTEs and has a deep standard; but it is a poor fit for control flow, testing and modularity, which is why people wrap it with dbt, stored procedures and Python.
People often think a faster query comes from writing "clever" SQL. In fact the largest gains usually come from data layout (partitioning, clustering, statistics, indexes), not from rewriting the text, because the optimizer already does the usual rewrites.
tradeoffs: Choose SQL when the task is filtering, joining and aggregating structured data and you want the engine to optimize. Choose a general-purpose language (Python, Scala, Java) when the logic needs custom algorithms, iterative loops, complex parsing or machine learning. A common split is SQL for the heavy data movement and code for logic the engine cannot express, accepting that user-defined functions in Python are opaque to the optimizer and can be 10 to 100 times slower than built-in functions.
Choose a CTE for readability and a temporary table or materialized intermediate when a sub-result is used many times or has a very bad estimate. Some engines inline CTEs and compute them once per reference; materialization costs a write but gives the planner real statistics and a stable plan. Choose a view for reuse of logic, and a materialized view when reads are frequent and the data changes slowly, accepting the refresh cost and staleness.
Choose ANSI-strict behavior (errors on invalid casts and overflow, as in Spark 4.0 defaults) for correctness and early failure; choose permissive behavior (NULL on bad input) only when you must keep old pipelines running, accepting silent data errors. Choose portable standard SQL when you expect to change engines, and vendor extensions (QUALIFY, MERGE variants, arrays, higher-order functions) when productivity matters more than portability.
Choose a stored procedure or a database function for logic that must stay next to the data and be transactional; choose application code when you need version control, tests and observability. You trade latency and atomicity for maintainability.
friction: The semantics are odd in places: three-valued logic, duplicates, implicit casts, different NULL ordering and string comparison rules across engines. The same query can return different results in two systems (integer division, collation, time zone handling, how overflow is treated).
Composition is weak. A SELECT has a fixed clause order that reads inside-out, so long analytic queries become nested subqueries and CTE chains hundreds of lines long. SQL has no standard functions as first-class modules, no standard testing and no real package system. dbt, SQLMesh and stored templates (Jinja) exist mostly to repair this, and pipe syntax is a language-level attempt.
Performance is indirect. You cannot see the plan from the text, and a small change in data or statistics can flip a plan from seconds to hours. SQL gives no way to state a physical intention, so people use hints, which are vendor-specific and brittle. Dialect differences also make migrations expensive: window syntax, date functions, quoting, string functions, and semantics of MERGE differ.
Finally, SQL is awkward for graphs, deep nesting, time series with irregular intervals, and iterative algorithms. SQL:2023 adds graph pattern queries and recursion exists, but specialised engines or code often fit better.
practice: Learn to read EXPLAIN output for your engine and make it a habit before shipping any query over a large table. Check that filters are pushed to the scan, that only needed columns are read, that the join type is sensible, and that estimated and actual rows are close.
Write for the optimizer. Filter on raw columns and avoid functions on them in WHERE. Select only the columns you need; SELECT * on a columnar table reads everything. Use explicit column lists in INSERT. Use EXISTS for existence checks, and NOT EXISTS rather than NOT IN. Qualify every column with its table alias. Prefer UNION ALL to UNION unless you need duplicate removal, because UNION adds a distinct step.
Be careful with NULL in every join and filter: decide what a NULL key should do, and test it. Use COALESCE and IS NOT DISTINCT FROM when needed. Be careful with time zones, and store timestamps in UTC with explicit types.
Structure large queries as CTEs with clear names, and check them one at a time. In a lakehouse, test changes with a small partition first. In Spark and Databricks, set ANSI mode on (default in Spark 4.0) so that wrong casts fail instead of producing NULL. Use dbt or a similar tool to add tests (unique, not null, relationships) and version control to your SQL. Finally, collect statistics and keep your data layout aligned to the filters people use, because that is where most speed comes from.

@@ normalization
value: Normalization is a method for designing tables so that each fact is stored in exactly one place. If a customer's city is written in 40 order rows, then moving house means 40 updates; miss one and the database now holds two answers to "where does this customer live?" Normalization removes that risk by splitting the data into tables, using rules based on which columns determine which other columns (functional dependencies). The rules give a ladder of normal forms: first (1NF), second (2NF), third (3NF) and Boyce–Codd (BCNF), and higher forms for rarer cases.
The reason it matters is that duplicated facts cause three "anomalies". An update anomaly: change one copy and forget another. An insertion anomaly: you cannot record a new product until someone orders it, because the row needs an order. A deletion anomaly: deleting the last order of a customer also deletes everything you knew about that customer. A normalized design makes these impossible by construction: the key constraints of the database enforce the facts, and no application code has to remember to keep copies equal.
The layers below give the method its precision. Relations and functions supply the central idea: a functional dependency \( X \to Y \) says that \( Y \) is a function of \( X \), so any two rows with the same X have the same Y. Logic supplies the reasoning: a dependency is a first-order sentence, and the question "does this set of dependencies imply that one?" has a sound and complete set of rules (Armstrong's axioms). The layers above use the result in two directions. OLTP systems follow normalized schemas for correctness under many writers. Dimensional modelling (Kimball star schemas) and lakehouse wide tables deliberately undo normalization for read speed, and knowing exactly what you give up is the skill.
terms: Functional dependency (FD) — \( X \to Y \) means that whenever two rows agree on the columns \( X \), they also agree on the columns \( Y \); for example customer_id → customer_city.
Superkey and candidate key — a superkey is a set of columns that determines all columns; a candidate key is a superkey with no unnecessary column.
Prime attribute — a column that belongs to at least one candidate key.
Attribute closure X⁺ — the set of all columns that X determines, directly or through a chain of dependencies.
Anomaly — a bad effect of duplicated data: update, insertion or deletion inconsistency.
Lossless decomposition — splitting a table into two so that joining the parts gives back exactly the original rows, with no extra and no missing rows.
Dependency preservation — after a split, every original dependency can still be checked inside a single table, without a join.
Normal form — a rule on the dependencies of a table: 1NF atomic values; 2NF no column depends on part of a key; 3NF no column depends on a non-key column; BCNF every determinant is a key.
Denormalization — deliberately storing redundant data, for example copying a customer's city into each order, to avoid a join.
history: Codd introduced first normal form in his 1970 paper: relations should have atomic values, with no tables inside cells. In 1971 he published "Further Normalization of the Data Base Relational Model", which defined second and third normal forms using functional dependencies. His goal was to remove bad insert, update and delete behavior. In 1974 Codd and Raymond Boyce gave a stricter third form, now called Boyce–Codd normal form. In the same year William Armstrong published the axioms that let one derive all the dependencies implied by a given set.
Theory then grew in the late 1970s. Philip Bernstein (1976) gave an algorithm that synthesizes a 3NF schema that preserves dependencies. Ronald Fagin defined multivalued dependencies and fourth normal form (1977), and join dependencies with fifth normal form (1979), which cover cases where independent facts about the same key are stored together. Beeri and Bernstein (1979) studied the computing cost of these problems, and others showed that some design problems are hard (finding all candidate keys of a schema can take exponential time in the worst case). The informal slogan "every non-key column depends on the key, the whole key, and nothing but the key" comes from William Kent (1983). Date, Darwen and Lorentzos later proposed a sixth normal form for temporal data, which is used in anchor modelling and some data vault designs.
In the 1990s, data warehousing pushed in the other direction. Ralph Kimball and Bill Inmon described schemas for analysis in which dimensions are denormalized on purpose. Later, NoSQL stores and columnar lakehouses encouraged wide, nested tables. Today normalization is mostly used to design the system-of-record layer, and denormalization is used to publish derived layers for reads.
how: Everything starts with functional dependencies, which come from the real rules of the business, not from the data. If every order has one customer, then order_id → customer_id. You cannot prove an FD from a sample of rows; you can only disprove it by finding two rows that break it. Armstrong's axioms give three rules: reflexivity (if \( Y \) is part of \( X \) then \( X \to Y \)), augmentation (if \( X \to Y \) then \( XZ \to YZ \)) and transitivity (if \( X \to Y \) and \( Y \to Z \) then \( X \to Z \)). They are sound (they derive only true dependencies) and complete (they derive all implied ones); this is a proof in logic, and it is what allows a program to reason about a schema. The practical tool is attribute closure: start with \( X^{+} = X \) and repeat "if some FD \( A \to B \) has \( A \) inside \( X^{+} \), add B" until nothing changes. If \( X^{+} \) contains all columns, \( X \) is a superkey.
With these tools the normal forms are checks. 1NF: every cell holds one atomic value, so no comma-separated lists and no repeating column groups (phone1, phone2, phone3). 2NF: no non-key column depends on only part of a composite key; the order line (order_id, product_id) must not store product_name, because product_id alone determines it. 3NF: for each dependency \( X \to A \), either \( X \) is a superkey or \( A \) is a prime attribute; informally, no non-key column depends on another non-key column (customer_name depends on customer_id, not on the order key). BCNF: for each non-trivial dependency \( X \to A \), \( X \) must be a superkey, with no exception for prime attributes. BCNF is stricter than 3NF only when a schema has overlapping candidate keys.
To normalize, find the dependencies, compute the keys, and decompose any table that has a violating dependency \( X \to Y \) into two tables: one with \( X \cup Y \) and one with the rest plus \( X \). This is lossless when the shared columns \( X \) form a key of at least one part (Heath's theorem): the join of the parts returns exactly the original rows, because \( X \) is a function and so cannot multiply rows incorrectly. Repeating until no table violates BCNF gives a lossless BCNF design. But BCNF decomposition may lose dependency preservation: a rule that once lived in one table now spans two, and checking it needs a join. 3NF synthesis (Bernstein) always gives a design that is lossless and keeps every dependency in some table, which is why 3NF is the usual practical target and BCNF the strict one.
Higher forms handle other redundancy. A multivalued dependency (MVD) X ↠ Y says that, for a given X, the set of Y values is independent of the other columns. If an employee has several skills and several languages, storing (employee, skill, language) forces the cross-product of skills and languages, which is huge and error-prone. 4NF splits the two independent lists into two tables. 5NF handles join dependencies, where a table can be rebuilt only from three or more projections. These cases are rare in business data but show up in many-to-many modelling.
Normalization also changes how constraints work. Once each fact lives in one table, the key and the foreign key do the checking: the database refuses an order for a customer that does not exist and refuses a second row for the same key. The cost moves to read time: to see an order with the customer's name and the product's name, the query must join. That is the price of correctness, and with good indexes on keys, a join of a few tables costs little on a transactional system.
Denormalization is the controlled reverse. You copy a column into another table (customer_city into the order) or flatten a star into one wide table, and you accept the duplicated fact. The result is faster reads, as no join is needed, and slower or riskier writes. In warehouses, the copies are rebuilt from the normalized source by a pipeline, so they cannot drift for long.

example: Start with a flat table of order lines. Suppose it has 100 million rows, with columns order_id, customer_id, customer_name, customer_city, product_id, product_name, qty. The business rules are: order_id → customer_id; customer_id → customer_name, customer_city; product_id → product_name; and (order_id, product_id) → qty.
Find the key by closure. Take {order_id, product_id}. order_id gives customer_id; customer_id gives name and city; product_id gives product_name; the pair gives qty. The closure is every column, so the pair is a key, and it is minimal because order_id alone misses product_name and qty, and product_id alone misses everything about the order. So the table has partial dependencies (customer_id depends only on order_id; product_name only on product_id), which violates 2NF, and a transitive dependency (city depends on customer_id, a non-key column), which violates 3NF.
See the anomalies with numbers. A customer has placed 50 orders with 4 lines each, which is 200 rows. When the customer moves, 200 rows need an update, and if a batch job changes 199, the table says the customer lives in two cities. If the company adds a new product, it cannot be stored until someone orders it. If the only order of a customer is cancelled, the customer's name and city vanish. Storage is also wasteful: the customer's name and city (say 40 bytes) repeat in all 200 rows, 8 KB for one customer, and over 100 million rows it is about 4 GB for the repeated customer fields alone, against around 20 MB if the 500,000 customers were stored once.
Now decompose by the dependencies. Customer(customer_id, name, city) has 500,000 rows. Product(product_id, product_name) has maybe 200,000 rows. Orders(order_id, customer_id) has 25 million rows if each order has 4 lines. OrderLine(order_id, product_id, qty) has 100 million rows. Each fact is stored once; moving house is one row update. The decomposition is lossless: joining OrderLine to Orders to Customer to Product returns the original 100 million rows exactly.
Last, the case where BCNF costs something. Address(street, city, zip) has the rules (street, city) → zip and zip → city. The keys are (street, city) and (street, zip). The rule zip → city breaks BCNF, since zip is not a key. Splitting into ZipCity(zip, city) and StreetZip(street, zip) is lossless, and a zip now maps to one city. But the first rule, "a street in a city has one zip", cannot be checked in either table alone, so the database can no longer enforce it with a key. The 3NF form keeps the original table and tolerates the repeated city. This is the standard example of the BCNF versus 3NF trade-off.
intuition: Write each fact on one index card and file it under the thing it describes, so there is only ever one card to correct.
A functional dependency says that one thing decides another. If a thing decides another and you store both together in a row that is about something else, you repeat the decided value every time the deciding value repeats. Normalization is simply the rule: put each deciding thing in its own table and refer to it by key. The mathematics is natural because a function has exactly one output for each input, and storing a function's table in two places is how contradictions arise.
mistakes: People often think normalization is about making many small tables. In fact its aim is to remove redundant facts. A table with many columns can be perfectly normalized, and a design split into many tables can still repeat facts.
People often think a higher normal form is always better. In fact each step trades update safety for read cost, and beyond 3NF or BCNF the gains are small for most business data. Denormalized read-optimized layers are a normal, intended part of analytics platforms.
People often think you can discover functional dependencies from the data. In fact the data can only show that an FD does not hold; whether it must hold is a business rule. A column that happens to be unique in today's sample is not a key.
People often think 3NF and BCNF are the same. In fact they differ when candidate keys overlap, and BCNF can lose the ability to enforce a rule inside one table, as the street, city, zip example shows.
People often think a surrogate id column (auto-increment) makes a table normalized. In fact it only adds a key; the dependencies between the other columns still need to be checked.
tradeoffs: Choose a normalized (3NF) design for the system of record that receives many concurrent writes from many applications: orders, accounts, inventory. You get one place to correct each fact and constraints that enforce rules; you give up some read speed, because queries join. Choose denormalized wide tables for reporting and dashboards that read a few columns from billions of rows, where a join per query would cost far more than storage, and accept that a pipeline must refresh the copies.
Choose 3NF over BCNF when you want every rule to be enforceable by a key inside one table, and accept a little redundancy. Choose BCNF when the redundancy is harmful and the lost rule can be checked in another way (a trigger, an application check, or a materialized join). Choose to stop at 3NF in most business schemas and to look at 4NF only when you see lists of independent values stored together.
Choose a star schema (a fact table plus denormalized dimensions) for analytics that people explore with BI tools: it gives simple joins and good compression on columnar storage. Choose a snowflake (normalized dimensions) when a dimension is very large or changes often, and you want one update to fix it, accepting extra joins. Choose nested or JSON columns when the child records are always read with the parent and never queried alone; you give up independent constraints and easy joins.
Choose a slowly changing dimension design (keep history of changes with valid-from and valid-to dates) when reports must show the customer's city as it was at the time of the order; choose to overwrite when only the current value matters. History is itself a form of controlled redundancy.
friction: Finding the right dependencies is a business task, and teams disagree about the rules. A wrong assumption (for example, that a customer has one address) is built into keys, and changing it later means migrations on large tables. Real data also has exceptions that the neat theory ignores: NULLs break the logic of dependencies (is NULL equal to NULL for the purpose of an FD?), and historical data often violates the rules that the application now claims.
Normalized schemas produce joins, and joins are the most expensive operation in distributed query engines, because they need a shuffle. That is why analytics platforms are built on the opposite principle, and why data engineers must maintain denormalized copies and keep them correct. Redundancy returns, together with the anomalies: a customer dimension copied into five wide tables can again disagree with itself unless a single pipeline owns the copy.
The algorithms are also costly in theory: deciding whether a schema is in BCNF is easy given the keys, but finding all keys, testing 3NF in general, and finding a minimum cover can need exponential time in the number of columns in the worst case. Schemas with hundreds of columns need tooling and judgment, not hand-derivation. Last, normalization says nothing about performance for a given workload, about time (history), or about semi-structured data, so it is only one input to schema design.
practice: Before drawing tables, list the business rules as dependencies in plain words: "an order belongs to one customer", "a product has one name", "a customer has one current city". Find the keys. Then check each table against the rules in the order 2NF, 3NF, BCNF, and split where a non-key column depends on something that is not the full key.
For transactional databases, aim at 3NF, declare keys and foreign keys, and denormalize only for a measured reason (a query that is too slow even with good indexes). When you copy a column on purpose, write down which table owns the truth and how the copy is refreshed.
For analytics in a lakehouse, keep a normalized layer close to the source (bronze and silver) and publish denormalized, query-friendly tables (gold) from it. Make dimensions wide and facts narrow, put the filter columns that people use on the fact or in a small dimension that can be broadcast, and use surrogate keys for dimensions so history can be tracked.
Test the dependencies as data quality rules: check that the key is unique, that foreign keys have no orphans, and that columns that should be functions of a key really are (count distinct city per customer_id equals 1). Run these checks on every load, because lakehouse tables often do not enforce them.
quiz: What does the functional dependency customer_id → city mean, and can a data sample prove it? || Any two rows with the same customer_id must have the same city. A sample can disprove it (two rows that differ) but never prove it; it is a business rule.
Why does storing customer_city in every order line cause anomalies? || The same fact is repeated in many rows, so an update can change some copies and miss others (update anomaly), a new customer cannot exist without an order (insertion), and deleting the last order loses the customer (deletion).
What is the difference between 3NF and BCNF, and which one can lose a dependency? || 3NF allows a dependency \( X \to A \) if \( A \) is a prime attribute even when \( X \) is not a key; BCNF requires \( X \) to be a superkey. BCNF decomposition may lose dependency preservation, while 3NF synthesis always keeps it.
A flat table has 100 million rows and each customer appears in 200 rows on average, with 40 bytes of customer fields. How much storage is spent on repeated customer fields, versus normalized? || 100M × 40 B = 4 GB repeated, against 500,000 customers × 40 B = 20 MB stored once (100M / 200 = 500,000 customers), roughly 200 times less.
Why do star schemas denormalize deliberately, and what do they give up? || A columnar warehouse reads a few columns of a huge fact table, and joining to small, wide dimensions is cheap, so denormalized dimensions make queries simple and fast. They give up single-place updates and must be refreshed by a pipeline.
interview: You inherit a 200-column table in a lakehouse with many repeated customer attributes. How do you decide whether to normalize it? || Check which dependencies hold (customer_id determines the attributes), measure the redundancy and the update pattern, and look at how it is read. If it is a source of truth with writes, split out a customer table; if it is a read-optimized gold table, keep it wide but build it from a normalized source and test consistency.
Explain a lossless decomposition and give the test for it. || Splitting R into R1 and R2 is lossless if joining them returns exactly R. The test: the common columns R1 ∩ R2 must determine all of R1 or all of R2 (be a key of one part). Otherwise the join creates spurious rows.
When is BCNF decomposition a bad idea? || When it breaks dependency preservation, so a business rule needs a join to be enforced, as with (street, city) → zip. Then you keep 3NF and accept limited redundancy, or enforce the rule another way.
What is a slowly changing dimension and why is it a form of denormalization? || It stores historical versions of dimension rows (type 2, with valid-from and valid-to) so facts link to the version that was true at the time. This duplicates attributes across versions on purpose, to answer point-in-time questions that a single current row cannot.
How does normalization interact with distributed joins? || A normalized schema needs joins across tables, which in a distributed engine means shuffling or broadcasting data. If one side is small it can be broadcast, but large-to-large joins are costly, so analytics schemas denormalize or co-locate by join key to avoid the shuffle.

value: An ACID transaction is a group of reads and writes that the database treats as one indivisible step. Atomicity: all of it happens or none of it does. Consistency: the data moves from one valid state to another valid state. Isolation: concurrent transactions do not see each other's half-finished work. Durability: once the database says "committed", the result survives a crash or power loss. Together, they let an application programmer write "debit A, credit B" as simple code and trust that no crash, no other user and no retry can leave the money half-moved.
Without these guarantees, every application would need its own recovery code. After a crash, a program would have to find out which of its ten writes reached the disk, and under concurrency it would have to avoid reading data that another program is in the middle of changing. ACID moves this hard work into the database once, where it is done carefully and tested for decades. That is the main reason relational databases became the system of record for money, orders, inventory and identity.
Two lower concepts do the real work. Crash recovery (a write-ahead log plus the ARIES algorithm) provides atomicity and durability: the log records every change before it reaches the data pages, so after a crash the database can redo committed work and undo unfinished work. Isolation levels, implemented by concurrency control (locks or multiple versions), provide the "I": they define exactly which interleavings of concurrent transactions are allowed to be visible. The layers above build on ACID: two-phase commit stretches atomic commit over many machines, exactly-once stream processing commits output and progress together, optimistic concurrency validates at commit, and the outbox pattern commits a business change and an outgoing event in one local transaction. Delta Lake and Iceberg brought ACID to files in object storage.
terms: Transaction — a sequence of operations that the database treats as a unit, ended by COMMIT (keep) or ROLLBACK (undo).
Atomicity — either every change of the transaction becomes visible, or none does, even after a crash.
Consistency — the transaction takes the database from one state that satisfies all declared rules (keys, foreign keys, checks) to another one.
Isolation — each transaction behaves as if it ran alone, to the degree allowed by the chosen isolation level.
Durability — after commit is acknowledged, the changes survive crashes of the process, the machine or the power.
Write-ahead log (WAL) — an append-only file of change records that must be on durable storage before the changed data pages are.
Serializable — the strongest isolation: the result is equal to some one-at-a-time order of the transactions.
Anomaly — a result that no one-at-a-time order could produce, such as a dirty read, lost update or write skew.
Group commit — flushing the log once for many transactions that commit at about the same time.
history: Jim Gray developed the idea of the transaction at IBM Research and Tandem in the 1970s while working on System R and on fault-tolerant systems. His 1981 paper "The Transaction Concept: Virtues and Limitations" explained why a unit of work with all-or-nothing behavior simplifies programs. In 1976 Eswaran, Gray, Lorie and Traiger showed that two-phase locking gives serializable schedules, and Gray's lock granularity work made fine-grained locking practical.
The name ACID comes from Theo Härder and Andreas Reuter, "Principles of Transaction-Oriented Database Recovery" (ACM Computing Surveys, 1983). They organized the properties and also classified recovery techniques by how they treat the buffer pool (steal or not, force or not). Gray and Reuter's book "Transaction Processing: Concepts and Techniques" (1992) became the standard reference, and Gray received the Turing Award in 1998. The ARIES paper (Mohan et al., 1992) gave the recovery algorithm used by most commercial databases.
Isolation is where history is messiest. The SQL-92 standard defined four levels (read uncommitted, read committed, repeatable read, serializable) by three forbidden phenomena. In 1995 Berenson, Bernstein, Gray, Melton, O'Neil and O'Neil published "A Critique of ANSI SQL Isolation Levels", showing that these definitions were ambiguous and incomplete, and describing snapshot isolation and anomalies such as lost update and write skew. Snapshot isolation (versions, not locks) became popular in Oracle and PostgreSQL, and in 2008 and 2012 researchers (Cahill et al.; Ports and Grittner) made serializable execution practical on top of it. PostgreSQL 9.1 (2011) shipped serializable snapshot isolation.
The 2010s brought doubt and then return. NoSQL systems gave up transactions for scale and availability, and the CAP discussion made ACID seem old. Google Spanner (2012) and later CockroachDB, TiDB, YugabyteDB and Aurora DSQL showed distributed ACID is feasible. Since 2017 to 2019, Delta Lake, Apache Iceberg and Apache Hudi gave ACID commits to tables made of Parquet files on object storage.
how: Atomicity and durability rest on the write-ahead log. Every change first creates a log record that holds the transaction id, the page, and the old and new values (or enough information to redo and undo). The rule is that the log record must reach durable storage before the changed data page does, and all log records of a transaction must be durable before COMMIT is acknowledged. The data pages themselves can stay in memory and be written later in any order. This is the "steal, no-force" policy: uncommitted pages may be written to disk (steal), and committed pages need not be (no-force). It is fast because a commit needs only one sequential log write, not many random page writes. After a crash, the recovery algorithm replays the log to redo committed work and undoes the work of transactions that did not commit. Atomicity therefore means "if there is no commit record, undo it"; durability means "if there is a commit record on disk, redo it". The cost is the flush: an fsync to an SSD takes roughly 50 microseconds to 1 millisecond, and to a cloud network disk 1 to 5 milliseconds or more. Group commit batches many transactions into one flush, so thousands of commits per second share a few flushes.
Isolation rests on concurrency control. The simplest form is locking: a transaction takes shared locks to read and exclusive locks to write, and (in strict two-phase locking) holds them until commit. This gives serializability but makes readers and writers wait for each other. Multi-version concurrency control (MVCC) keeps old versions of each row with the ids of the transactions that created and replaced them. A reader looks at a snapshot, the versions committed when it started (or when each statement started), so it never waits for writers. Snapshot isolation prevents dirty reads, non-repeatable reads and (in most implementations) phantoms. But it allows write skew: two transactions each read an overlapping set, each write a different row, and together break a rule that neither one broke alone. Serializable snapshot isolation adds tracking of read-write dependencies and aborts one transaction when a dangerous pattern appears.
Isolation levels are a menu. Read committed: you only see committed data, but two reads in one transaction may differ. Repeatable read (or snapshot): all reads in the transaction see the same snapshot. Serializable: the outcome equals some serial order. The defaults differ and surprise people: PostgreSQL, Oracle and SQL Server default to read committed (SQL Server's optional snapshot is off by default), MySQL InnoDB to repeatable read (which is implemented with gap locks and differs from the Postgres version), CockroachDB and Spanner to serializable or stronger. Weaker levels perform better and cause fewer aborts, but they allow anomalies, and many real bugs (double-spent balances, oversold stock) come from these.
Consistency is the odd letter. The database enforces the rules you declare: primary keys, unique constraints, foreign keys, NOT NULL and CHECK. A transaction that would violate one is aborted. But a rule such as "total debits equal total credits" or "an on-call doctor must always exist" is the application's invariant. The database helps (with isolation and constraints), but it cannot know what you mean. In that sense atomicity, isolation and durability are properties of the database, and consistency is a property of the application running on top.
In distributed settings these pieces must be coordinated. A transaction touching two shards needs two-phase commit: all participants first log a "prepared" vote, then a coordinator logs the decision, then everyone commits. Each participant keeps the prepared state across crashes through its own recovery log. This costs extra round trips and holds locks during the protocol. In lakehouse formats, the equivalent of the log is a transaction log of file additions and removals: a writer stages new data files, then atomically publishes one new log entry (a put-if-absent of the next version number). Readers use the last committed version. Concurrent writers use optimistic concurrency: if another commit touched the same files, the later writer fails or retries.

example: Follow a transfer of 5,000 rupees. Account A holds 12,000 and B holds 3,000. The transaction runs: read A, write A = 7,000, read B, write B = 8,000, commit.
Atomicity and durability. The log gets three records: L1 (T1 changed A from 12,000 to 7,000), L2 (T1 changed B from 3,000 to 8,000) and L3 (T1 commit). Suppose the machine loses power after L2 reaches the disk but before L3. On restart, recovery finds T1 with no commit record, so it undoes L2 and L1 using the old values: A is 12,000 and B is 3,000, as if the transfer never began. Suppose instead power fails right after L3 is flushed but before the data pages were written. Recovery finds the commit record and redoes L1 and L2, so A is 7,000 and B is 8,000. In both cases the total remains 15,000. Cost: one log flush at commit. If a flush takes 0.5 ms and each commit flushes alone, the limit is about 2,000 commits per second. With group commit, if 100 transactions arrive during one flush, they share it, and the limit becomes about 200,000 per second (limited by CPU and other things).
Isolation. Add a second transaction T2 that reads both balances to compute a total. Under read committed, T2 sees only committed data, but each statement gets a fresh view. If T2 reads A before T1 commits (12,000) and reads B after T1 commits (8,000), it reports 20,000, a total that never existed. Under snapshot isolation or serializable, both reads come from one snapshot and the total is 15,000.
Write skew. A hospital rule says at least one doctor must stay on call. Two doctors, Asha and Ravi, are both on call. Each transaction checks "count of on-call doctors ≥ 2" (true), then sets its own doctor off call. Under snapshot isolation both succeed, because they write different rows, and nobody is on call. Under serializable isolation one of them is aborted and retried, and the retry sees count = 1 and refuses. The lesson: snapshot isolation is not serializable, and the fix is either the serializable level or an explicit lock (SELECT … FOR UPDATE on the shared rows).
intuition: A bank transfer either moves the money completely or not at all, even if the power fails midway, and no one sees the money in the air between the two accounts.
The design is natural once you see that a program's crash cannot be avoided, but its effects can be made reversible. A log records intentions before actions, so the database can always decide afterwards whether to finish or to undo. Isolation applies the same idea to other users: pretend the transactions ran one at a time, and allow reordering only when it cannot be seen. ACID is a promise that the world looks simple, and the log, the locks and the versions are how the database keeps that promise.
mistakes: People often think ACID means the database is always correct. In fact the database only guarantees what you declared and the level you chose. At read committed, a read-modify-write on a balance can lose an update unless you use SELECT … FOR UPDATE, an atomic UPDATE balance = balance - x, or a higher level.
People often think "serializable" is the default. In fact the common defaults are read committed (PostgreSQL, Oracle, SQL Server) and repeatable read (MySQL InnoDB). Serializable costs more aborts or waiting, so you must ask for it.
People often think the C in ACID is something the database provides. In fact consistency depends on the application's invariants; the database enforces declared constraints and relies on A, I and D to keep them safe. Many engineers consider it the weakest-defined of the four.
People often think a committed transaction is on disk. In fact it is only durable if the log was flushed (fsync) to stable storage, or replicated to enough machines. Settings such as synchronous_commit = off in Postgres or innodb_flush_log_at_trx_commit = 2 in MySQL trade the last moments of commits for speed.
tradeoffs: Choose serializable isolation when invariants span several rows (balances, inventory, uniqueness checks without a unique index) and you can afford retries; expect abort rates that rise with contention. Choose read committed or snapshot isolation when transactions are short, rows are independent, and you protect critical updates explicitly (atomic increments, row locks, unique constraints). You gain throughput and fewer aborts, and you accept that you must reason about anomalies.
Choose synchronous durability (flush before ack) for money, orders and identity; choose asynchronous commit or batched flush when you can lose the last few hundred milliseconds of writes (click logs, metrics, caches). The gap can be 10 to 100 times in commit rate on a single disk, but the data lost in a crash is real.
Choose a single-node ACID database while it fits: a modern server handles tens of thousands of transactions per second and tens of terabytes. Choose a distributed SQL database (Spanner, CockroachDB, Aurora DSQL) when you need ACID across regions or more write throughput than one machine, and accept commit latencies of tens of milliseconds because of consensus and cross-region round trips. Choose sagas or the outbox pattern when you cross service boundaries and cannot hold one transaction, giving up isolation and accepting compensations.
Choose lakehouse ACID (Delta, Iceberg) for table-level atomic commits on object storage, with optimistic concurrency, accepting that commits cost hundreds of milliseconds and that many small concurrent writers to the same files will conflict.
friction: Coordination costs performance. Locks serialize hot rows: if each transaction holds a lock on one hot row for 2 ms, that row can handle at most about 500 updates per second, whatever the hardware. Optimistic and snapshot schemes avoid waiting but abort under contention, and every abort wastes the work done. The log flush puts a floor under commit latency, and across machines, two-phase commit adds round trips and can block participants when the coordinator fails.
Weak defaults produce real bugs. Lost updates, write skew and phantom reads appear in production in ways that are hard to reproduce, because they depend on timing. Research by Bailis and others has shown that many applications relying on default isolation levels are exposed to such anomalies. Frameworks that retry transactions on conflict must also make sure the transaction body is safe to run twice, with no external side effects (emails, API calls) inside it.
Durability is only as good as the lower layers. An fsync that returns success on a disk with a volatile write cache, or a cloud volume with weak guarantees, gives false safety; storage errors after fsync have caused data loss in real databases, and PostgreSQL changed its behavior in 2018 to treat fsync failure as fatal. Long transactions are another cost: they hold locks or old versions (MVCC bloat, vacuum delays), and they block recovery checkpoints.
Last, the guarantees are local to one database. When a business operation touches a database, a queue and an external API, no ACID transaction covers all of them, so you need idempotency, retries, outboxes and reconciliation to reach the same safety.
practice: Know your database's default isolation level and what anomalies it permits. For any read-modify-write, use an atomic statement (UPDATE … SET x = x + 1), a conditional update (WHERE version = ?), or SELECT … FOR UPDATE; do not read in the application and write back without protection. For invariants over several rows, use serializable or lock a parent row that represents the invariant.
Keep transactions short and put no network calls, user waits or large computations inside them. Retry transactions that abort with serialization or deadlock errors, with backoff, and make the whole body idempotent. Add unique constraints and foreign keys, because they are the cheapest and strongest consistency tools you have.
For durability, understand your commit settings and your storage: does an acknowledged commit mean a flushed log, or a replica in another zone? Test with a real power-loss or kill -9 test, and monitor replication lag and fsync latency. Use group commit and batching in your own writers instead of turning durability off.
On the lakehouse, use Delta or Iceberg commits for atomic table updates, design writers to touch disjoint partitions or files so that optimistic concurrency rarely conflicts, and choose the isolation level that the format offers for your operation (Delta's default is WriteSerializable, with Serializable available; Iceberg lets you set serializable or snapshot isolation for deletes, updates and merges). Expect conflicts and retry them.
quiz: Which part of ACID depends on the application, and why? || Consistency. The database enforces declared constraints, but an invariant such as "at least one doctor on call" is known only to the application; the database protects it only through isolation and constraints that you set up.
Why does write-ahead logging make a commit fast and still safe? || A commit needs only one sequential log flush, not random writes of data pages, which can be written later. The log has enough information to redo committed changes and undo uncommitted ones after a crash.
Why does snapshot isolation allow write skew? || Each transaction reads from its own snapshot and writes a different row, so there is no write-write conflict to detect, yet together they violate an invariant that depends on both rows. Serializable snapshot isolation or explicit locking prevents it.

@@ ccontrol
value: Concurrency control is the part of a database that lets many transactions run at the same time and still gives answers as if they had run one after another. Without it, two clients adding to the same balance can overwrite each other, and a report can read half of a transfer. With it, the application writes simple code, and the database decides which operations may overlap, which must wait, and which must be cancelled and retried.
The goal has a precise name: serializability. A concurrent execution (a schedule) is serializable if its result is the same as some serial order of the same transactions. There are three families of methods to reach it. Pessimistic methods (two-phase locking) take locks first, so conflicts are prevented by waiting. Optimistic methods (OCC) run without locks and check at commit whether a conflict happened, so conflicts are handled by aborting and retrying. Multi-version methods (MVCC) keep old versions of data so that readers never wait for writers. Each choice decides how a system behaves under contention, and you see the result in throughput graphs, deadlock logs and retry rates.
The layers below supply the mathematics. Order theory describes what a schedule is: each transaction fixes a partial order of its operations, a schedule is a total order that respects all of them, and "equivalent to a serial order" means there is a consistent ordering of whole transactions (a linear extension). Timestamps and lock sequences are ways to impose such an order. Graph theory gives the checking tools: the precedence graph of a schedule has an edge for each conflict, and the schedule is conflict-serializable exactly when this graph has no cycle; the wait-for graph finds deadlocks by looking for cycles too. Deadlock theory explains why locking can get stuck and how to detect or avoid it. The layers above build on these ideas: MVCC and optimistic concurrency are specializations, and the lakehouse commit protocols (Delta, Iceberg) are optimistic concurrency over files.
terms: Schedule — an interleaving of the operations of several transactions, in the order they actually happen.
Conflict — two operations from different transactions on the same item, at least one of them a write; their order matters.
Serializable — a schedule whose effect equals that of some serial (one at a time) execution.
Precedence graph — a graph with a node per transaction and an edge \( T_i \to T_j \) when an operation of \( T_i \) conflicts with, and comes before, one of \( T_j \).
Two-phase locking (2PL) — a rule: a transaction takes locks in a growing phase and, once it releases any lock, takes no more.
Strict 2PL — 2PL where exclusive locks are held until commit or abort, so no one reads uncommitted data.
Shared and exclusive locks — a shared (S) lock allows reading and can be held by many; an exclusive (X) lock allows writing and is held by one.
Wait-for graph — a graph with an edge \( T_i \to T_j \) when \( T_i \) waits for a lock held by \( T_j \); a cycle means deadlock.
Optimistic concurrency control (OCC) — run without locks, then validate at commit that nothing you read or wrote was changed by others; abort if it was.
Timestamp ordering — give each transaction a timestamp and reject operations that arrive in an order that disagrees with the timestamps.
history: Concurrency control grew out of the first multi-user databases in the 1970s. In 1976 Eswaran, Gray, Lorie and Traiger published "The Notions of Consistency and Predicate Locks in a Database System", which defined serializability as the correctness criterion for concurrent transactions and showed that two-phase locking guarantees it. Gray and his colleagues added granularity of locks (lock a table, a page or a row, with intention locks to make this efficient), which is why databases can lock rows cheaply today. Papadimitriou (1979) formalized serializability and the graph test; Bernstein, Hadzilacos and Goodman's 1987 textbook collected the theory.
Alternatives appeared soon. Timestamp ordering and multi-version schemes came from Reed's 1978 thesis at MIT, which is the first full description of multi-version concurrency control. Rosenkrantz, Stearns and Lewis (1978) gave the wait-die and wound-wait schemes to prevent deadlock using timestamps. In 1981 H. T. Kung and John Robinson published "On Optimistic Methods for Concurrency Control", arguing that when conflicts are rare, locks are wasted work and it is better to validate at the end.
The next waves followed hardware. Snapshot isolation (Berenson et al., 1995) became the default in Oracle and PostgreSQL, because it lets readers avoid locks. The 2010s brought many-core machines and in-memory databases: Hekaton (SQL Server's in-memory engine), HyPer and Silo introduced lock-free or optimistic designs for short transactions. Thomson and colleagues' Calvin (2012) orders transactions first and then runs them deterministically, to avoid distributed commit. Yu, Bobba, Pavlo, Devadas and Stonebraker (VLDB 2014) simulated 1,000 cores and showed that every classic scheme hits a wall for different reasons. Today the same ideas run at the level of files in lakehouses, where optimistic commit is the standard.
how: Start with conflicts. Two operations conflict if they come from different transactions, touch the same item and at least one is a write: read-write, write-read and write-write. Non-conflicting operations can be swapped without changing the result; conflicting ones cannot. A schedule is conflict-serializable if it can be turned into a serial schedule by swapping only non-conflicting neighbors. The test is graph theory: build the precedence graph, with an edge \( T_i \to T_j \) for each conflicting pair where \( T_i \) comes first. If the graph has no cycle, a topological order of the nodes is an equivalent serial order. If there is a cycle, no serial order explains the schedule. This test is a proof tool; databases do not build the graph at run time (except serializable snapshot isolation), they use protocols that guarantee it stays acyclic.
Two-phase locking is the classic protocol. Before reading an item, a transaction takes a shared lock; before writing, an exclusive lock. A shared lock is compatible with other shared locks only. The rule: once a transaction releases a lock, it may not take a new one. So there is a growing phase and then a shrinking phase. This guarantees conflict-serializability: the order in which transactions pass their "lock point" (the moment they hold all their locks) is a valid serial order. Practical systems use strict 2PL, holding exclusive locks until commit, since releasing early lets another transaction read data that may later be rolled back, which causes cascading aborts. Hierarchical locking adds intention locks (IS, IX) on tables so that a table lock and a row lock can coexist cheaply. Phantoms, new rows that match a range predicate, are blocked with range or next-key locks on index ranges, as InnoDB does.
Locks produce deadlock: T1 holds A and waits for B while T2 holds B and waits for A. The deadlock concept supplies the four conditions (mutual exclusion, hold and wait, no preemption, circular wait), and databases attack the last one. Detection builds the wait-for graph and looks for a cycle, either each time a transaction blocks or after a timeout (PostgreSQL waits deadlock_timeout, 1 second by default, before it checks). One transaction in the cycle, the victim, is aborted. Prevention uses timestamps: in wait-die an older transaction may wait for a younger one but a younger one that would wait for an older one is aborted ("dies"); in wound-wait an older transaction aborts ("wounds") the younger one. Both keep the wait graph acyclic, by ordering transactions by age, which is order theory used directly.
Timestamp ordering needs no locks. Each transaction gets a timestamp when it starts, and each item remembers the largest timestamp that read it and the largest that wrote it. A read by T is rejected if T's timestamp is older than the item's write timestamp, because T would read a value from its future. A write by T is rejected if a younger transaction has already read or written the item. Rejected transactions restart with a new timestamp. The schedule is equivalent to the serial order of timestamps by construction.
Optimistic concurrency control has three phases. Read: the transaction reads data and writes only into a private workspace. Validate: at commit, check that no transaction that committed since it started wrote anything it read (backward validation). Write: if valid, publish the writes atomically; if not, abort and retry. No locks are held while the transaction thinks, so there is no deadlock and no waiting, and the work is wasted only when validation fails. The same pattern runs in Delta and Iceberg: a writer reads the table version, stages new files, then commits only if no conflicting commit appeared since.
MVCC keeps several versions of each row, each tagged with the transaction that created and the one that deleted it. A reader picks the versions visible to its snapshot, so reads never block writes and writes never block reads; only write-write conflicts need coordination (a lock on the row in PostgreSQL, "first committer wins" in other systems). Snapshot isolation by itself is weaker than serializable (it allows write skew). Serializable snapshot isolation adds detection of dangerous read-write dependency patterns and aborts one transaction when needed.

example: Take two transactions on accounts A and B, both starting at 100. T1 does: A = A + 10, then B = B × 2. T2 does: A = A × 2, then B = B + 10. Run serially, T1 then T2 gives A = 220, B = 210. T2 then T1 gives A = 210, B = 220. These are the only two correct answers.
Now run the schedule in the diagram. T1 writes A = 110. T2 reads A = 110 and writes A = 220. T2 reads B = 100 and writes B = 110. T1 reads B = 110 and writes B = 220. The result is A = 220, B = 220, which matches neither serial result. The precedence graph shows why: on A, T1's write comes before T2's read, so T1 must be first; on B, T2's write comes before T1's read, so T2 must be first. That is a cycle, so no serial order explains the schedule.
Now strict 2PL. T1 locks A exclusively before reading it. T2 asks for A and waits. T1 locks B, finishes both updates (A = 110, B = 200), commits and releases both locks. T2 then runs on those values and ends with A = 220, B = 210, equal to the serial order T1 then T2. Deadlock arises if T2 instead starts with B: T1 holds A, T2 holds B, T1 asks for B and waits, T2 asks for A and waits. The wait-for graph has the cycle T1 → T2 → T1. The detector aborts the younger transaction (T2), which releases B; T1 finishes; T2 retries.
Now throughput numbers. If every transaction updates one hot row (a global counter) and holds its lock for 1 ms until commit, the row allows at most 1,000 transactions per second, whether the machine has 4 cores or 64. With optimistic control the same workload would let all 64 run in parallel and 63 of 64 would fail validation each round, so the useful rate is also about one commit per round. The fix for both is to remove the hot spot: shard the counter into 16 rows, or use an atomic increment.
Last, an optimistic lakehouse case. Two Spark jobs each run MERGE on a Delta table of 1,000 partitions. Job 1 touches partitions 1 to 10, Job 2 touches partitions 500 to 510. Both read table version 41, stage new files, and try to commit version 42. Job 1 wins. Job 2 sees that version 42 changed files in partitions that it did not read or write, so validation passes, and it commits as version 43. If Job 2 had also touched partition 5, it would fail with a concurrent modification error and have to retry. This is why partitioning writers by disjoint ranges matters.
intuition: Traffic rules for transactions: stop signs (locks), number tickets (timestamps), or "drive on and check at the end" (optimistic).
The problem is that conflicting operations have a hidden order, and you need all conflicts to point the same way, with no cycles. Locks make later arrivals wait so the order is set early. Timestamps decide the order in advance and reject those who break it. Optimism lets everyone run and removes the ones that conflicted. All three keep the precedence graph acyclic; they differ only in when they pay: before the work (waiting), during the work (rejection), or after the work (abort).
mistakes: People often think two-phase locking means two lock requests. In fact the two phases are a growing phase (acquire only) and a shrinking phase (release only). Strictness (holding exclusive locks until commit) is a separate, stronger rule that real systems add.
People often think optimistic is always faster because it avoids locks. In fact it is faster only when conflicts are rare. Under heavy contention, many transactions do full work and then abort, wasting CPU, and throughput can collapse below the locking version.
People often think MVCC means no locks and no conflicts. In fact MVCC removes read-write blocking, but concurrent writers to the same row still conflict, and snapshot isolation still allows write skew. Old versions also need cleaning (vacuum or compaction).
People often think deadlocks are a sign of a database bug. In fact they are a normal outcome of locking, caused by two transactions taking the same locks in different order. Databases detect them and abort one; the application should retry, and should access rows in a consistent order to reduce them.
tradeoffs: Choose pessimistic locking (strict 2PL, SELECT … FOR UPDATE) when conflicts are likely, transactions are short, and aborting is expensive, such as inventory counts for popular items. You give up concurrency while waiting and accept deadlocks. Choose optimistic validation when conflicts are rare (say under about 5 percent of transactions), the work between read and commit is long, or locks are impossible, as with files on object storage. You give up work on each abort.
Choose MVCC with snapshot isolation for mixed workloads with many readers, because reads never block, and long reports can run beside updates. Choose serializable (locking or SSI) when the invariants span rows and anomalies are unacceptable, and accept lower throughput or a higher abort rate (often 2 to 10 times more aborts under contention).
Choose deadlock detection (a periodic wait-for graph search) when waits are frequent and aborting late is acceptable; choose timeouts for simplicity in distributed systems, where building a global graph is hard, accepting that slow transactions are cancelled falsely. Choose wait-die or wound-wait when you need a simple rule without a graph, accepting extra aborts of transactions that would not have deadlocked.
Choose coarse locks (table or partition) when transactions touch most of the data and you want low overhead; choose fine locks (row) when transactions touch few rows, accepting the memory and CPU cost of tracking many locks. Choose deterministic ordering (Calvin-style) for workloads that touch many partitions and where a global order can be agreed once, and give up interactive transactions, since all reads and writes must be known up front.
friction: Hot spots decide everything. A single counter, a single "latest" row or a table with an auto-increment key at the end of an index can limit a whole system, and none of the families of methods fixes that without schema or workload change. Under heavy contention, locking suffers from lock thrashing (many transactions waiting while holding other locks), and optimistic schemes suffer from abort storms.
Deadlocks and retries are hard to test. The bug appears only when timings line up, and application code often forgets to retry or to make the body idempotent. Long transactions are risky in every scheme: they hold locks, delay vacuum in MVCC systems, and are more likely to fail validation.
Many-core machines expose shared structures: the lock table, the timestamp counter and the log become bottlenecks. The 2014 study by Yu and colleagues found that each classic algorithm stops scaling before 1,000 cores because of a different bottleneck (lock thrashing, timestamp allocation, or copy costs), and no algorithm won everywhere. Distributed transactions make everything worse: a lock held during a network round trip of 1 to 100 ms turns a hot row into a very hard limit.
Finally, the theory describes single-item reads and writes. Real workloads use predicates (phantoms), secondary indexes, foreign keys and triggers, each needing special care, and many databases deviate from textbook definitions in their isolation levels, so you must read the documentation of your actual system.
practice: Find out what your database uses: PostgreSQL uses MVCC with row locks for writers, MySQL InnoDB uses MVCC for reads with next-key locks for writers, SQL Server defaults to locking for read committed, Spanner uses locking with timestamps, and Delta and Iceberg use optimistic commits. Know the default isolation level and the error you get on conflict (deadlock detected, serialization failure, concurrent modification).
Reduce the conflict window. Keep transactions short, touch rows in a fixed order (for example by primary key), take the strongest lock you will need first (SELECT … FOR UPDATE rather than read then upgrade), and avoid user interaction inside a transaction. Move hot counters to sharded rows or to a stream. Use atomic statements such as UPDATE … SET n = n + 1 instead of read, compute, write.
Always retry on serialization failures and deadlocks, with limited retries, backoff and jitter. Make the transaction safe to run again: no external side effects before commit.
In lakehouses, partition and cluster so that concurrent writers touch disjoint files, run compaction and MERGE jobs on separate partitions or schedules, add explicit predicates to MERGE conditions so conflict detection can see they are disjoint, and monitor concurrent-modification exceptions as a signal. Measure lock waits and deadlocks (pg_stat_activity, pg_locks, the InnoDB status output) before you change isolation levels.

@@ recovery
value: Crash recovery is what a database does when it starts again after a failure, so that the data is in a correct state: every transaction that was committed is fully there, and every transaction that was not committed has left no trace. The machine may have lost power in the middle of writing a page, or between two updates of one transaction. Recovery uses a log, an append-only record of every change, to repair the files. It is the mechanism behind two letters of ACID, atomicity and durability.
The problem it solves comes from a conflict in speed. A database wants to keep hot pages in memory and write them to disk lazily, because writing a page for each change would be far too slow. But memory is lost in a crash. Recovery lets the database be lazy with data pages and strict with a small sequential log. On commit, only the log must be flushed. The pages can follow later, and if the crash comes first, the log has enough information to rebuild them. The same log-replay idea is the base of replication (a replica replays the primary's log), point-in-time restore, and change data capture.
Two lower concepts matter most. fsync and durability give the log its meaning: the rule "log first" works only if the system can force bytes to stable storage and know that they are there; if fsync lies or fails, the log is not a promise. Proofs and induction give the correctness argument: ARIES is correct because of invariants stated over log sequence numbers (every page records the LSN of the last change applied to it, and the log is totally ordered), and one proves by induction that replaying the log from any checkpoint produces the same state as the crashed system, even if recovery itself crashes again. The layers above reuse this: two-phase commit participants log their votes to finish the protocol after a restart, exactly-once processing rolls back to a checkpoint and replays, and file-system journaling is the same pattern for metadata.
terms: Write-ahead logging (WAL) — the rule that a log record describing a change must be durable before the changed data page is written to disk.
LSN (log sequence number) — an increasing number that identifies each log record; each page stores the LSN of the last record applied to it.
Redo and undo — redo re-applies a change that may not have reached disk; undo reverses a change of a transaction that did not commit.
Steal and no-force — steal lets the buffer manager write dirty pages of uncommitted transactions to disk; no-force means a commit need not write the data pages, only the log.
Checkpoint — a log record that summarizes the state at some moment (active transactions and dirty pages) so recovery can start close to the crash, not at the beginning of the log.
Dirty page table and transaction table — recovery's two work lists: which pages may be out of date on disk (with the first LSN that dirtied them, recLSN), and which transactions were active.
Compensation log record (CLR) — a log record written when an undo is performed, so that undo itself is logged and is never repeated.
Torn page — a page that was only partly written when the crash came, because the disk's atomic write unit is smaller than the page.
Fuzzy checkpoint — a checkpoint taken while transactions keep running, without flushing all dirty pages first.
history: Early systems (System R, 1970s) used shadow paging for atomicity: write new versions of pages elsewhere and switch a pointer at commit. It was simple but scattered data on disk and made concurrent transactions hard. The industry moved to logging. Jim Gray's 1978 notes described write-ahead logging, and Härder and Reuter's 1983 survey classified recovery methods by two buffer policies, steal versus no-steal and force versus no-force. The best performance and flexibility came from steal and no-force, which required both undo and redo information in the log.
Through the 1980s, IBM researchers at Almaden (C. Mohan, Don Haderle, Bruce Lindsay, Hamid Pirahesh and Peter Schwarz) developed ARIES for DB2 and other IBM products. The paper "ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging" appeared in ACM TODS in 1992. It joined three ideas: write-ahead logging, repeating history during redo (redo everything, including the work of transactions that will be rolled back), and logging the undo (compensation records). Together, they allow row-level locking, fuzzy checkpoints and partial rollbacks. ARIES, or close relatives, run in DB2, SQL Server, Oracle (with different details), InnoDB and many research systems.
Not every database follows ARIES. PostgreSQL's WAL replays redo records only; it needs no undo phase because MVCC keeps old row versions and aborted transactions are simply invisible. Log-structured designs (LSM trees in RocksDB and Cassandra) use a WAL to rebuild the in-memory table and have no pages to undo. Since 2010, new work addresses fast storage and the cloud: Aurora (2017) pushes redo log processing into the storage layer, so that recovery is spread over many storage nodes, and non-volatile memory designs reduce or remove log flush cost.
how: During normal operation the engine does four things for each change. It finds the page in the buffer pool. It writes a log record that holds the LSN, the transaction id, the page id, a pointer to that transaction's previous log record (prevLSN), and the change in a form that allows both undo and redo (usually "physiological": physical to one page, logical inside the page). It applies the change to the page and stores the record's LSN in the page header (pageLSN). And it keeps the transaction table (one row for each active transaction with its last LSN) and the dirty page table (each dirty page with recLSN, the first LSN that made it dirty). The key rule, the WAL rule, is that before the buffer manager writes a dirty page to disk, the log must be flushed up to that page's pageLSN. The other rule is that at commit the log is flushed up to the commit record; only then is success reported. Fsync is what makes "flushed" true.
Because the log is flushed at commit and the pages are written lazily, two bad things can exist at a crash. Some committed changes exist only in the log (pages were not written), so they must be redone. Some uncommitted changes exist on disk (the buffer manager stole a page), so they must be undone. Checkpoints keep the amount of work small. A fuzzy checkpoint writes a begin record and an end record containing copies of the transaction table and dirty page table, while work continues, and stores the begin LSN at a known place. It does not force all dirty pages, which would stall the system, so pages are written by a background process.
Recovery after a crash has three passes. Analysis: start at the last checkpoint and scan the log forward to the end. Rebuild the transaction table and dirty page table: a new log record for a page adds it to the dirty page table if absent (with recLSN equal to that record's LSN), a commit or end record updates the transaction status. At the end, you know which transactions were active at the crash (the losers) and the smallest recLSN in the dirty page table, which is where redo must start. Redo: scan forward from that smallest recLSN and re-apply every logged change, for winners and losers alike (repeating history). For each record, skip it if the page is not in the dirty page table, or its recLSN is greater than the record's LSN, or the page on disk already has pageLSN ≥ this record's LSN. Otherwise read the page, re-apply the change and set pageLSN. This check makes redo idempotent: running recovery twice does no harm. After redo, the database is exactly in the state it had at the moment of the crash, including the effects of the losers.
Undo: roll back every loser. Take the last LSN of each loser, and repeatedly process the largest LSN of all, undoing that change, and writing a compensation log record (CLR) that describes the undo and carries an undoNextLSN pointing to the next record of that transaction still to undo. When a transaction has nothing left to undo, write an end record. CLRs are redo-only: they are re-applied by redo but never undone. So if the system crashes during recovery, the next recovery repeats history including the CLRs, and the undo continues where it stopped; the amount of work does not grow with repeated crashes. This is the proof-by-induction part: the invariant "pageLSN tells exactly which log prefix is reflected in a page" holds after each step.
The details around this matter in practice. Torn pages: if a disk writes 4 KB atomically and a database page is 8 KB or 16 KB, a crash can leave half a page, and no log replay can fix a page whose base is garbage. PostgreSQL writes the full page image into the WAL the first time a page is modified after each checkpoint (full_page_writes), and InnoDB uses a doublewrite buffer. Checkpoint frequency trades recovery time against write load: frequent checkpoints shorten the log to replay but flush more pages. Logs are also archived and shipped to replicas, so the same stream serves recovery, replication and point-in-time restore.

example: Use the log in the diagram. Transactions T1, T2 and T3 update pages P5, P3, P7. The log has records 10 to 80, and the system crashes after record 80. T1 committed at 60, and its commit record was flushed; T2 and T3 had not committed.
Analysis. The last checkpoint's end record (LSN 40) says that T1 (last LSN 10) and T2 (last LSN 20) were active, and that P5 (recLSN 10) and P3 (recLSN 20) were dirty. Scanning forward: record 50 updates T1's last LSN to 50; 60 marks T1 as committed; 70 adds T3 (last LSN 70) and adds P7 to the dirty page table with recLSN 70; 80 updates T2's last LSN to 80. The losers are T2 and T3. The smallest recLSN is 10, so redo starts there.
Redo. Scan from LSN 10. For record 10 (P5): the disk copy of P5 has pageLSN 0, which is less than 10, so redo the change. Suppose P3 was already flushed after record 20, so its pageLSN is 20; record 20 is skipped, but record 50 (pageLSN 20 < 50) is redone. Records 70 and 80 are redone as well, even though they belong to losers. When redo ends, memory holds the exact state at the crash.
Undo. The to-undo set has 80 (T2) and 70 (T3). Take the largest, 80: undo T2's change to P5, write CLR 90 whose undoNextLSN is 20 (T2's previous record). Next largest is 70: undo T3's change to P7, write CLR 100, and since T3 has no earlier record, write its end record. Then 20: undo T2's change to P3, write CLR 110 and the end record for T2. Now only T1's changes remain. If the machine crashes again during undo, say after CLR 90, the next analysis sees the CLR, redo re-applies it, and undo continues with the record named by its undoNextLSN (20), skipping 80 which is already undone.
Cost. Suppose the system writes 20 MB/s of WAL with checkpoints every 5 minutes. The log since the last checkpoint is up to 6 GB. If replay runs at about 100 MB/s, redo takes around a minute. Halving the checkpoint interval halves the worst-case replay but doubles checkpoint I/O pressure. With group commit, a commit costs one log flush: 0.1 ms on an NVMe drive with power-loss protection, or a few milliseconds on a network volume.
intuition: Keep a diary of every change before you make it; after a disaster, replay the diary to rebuild the room, then reverse the entries that were never finalized.
The idea is natural because it splits a hard problem into two easy ones. Writing a small log sequentially is cheap and can be made reliable. Once the log is safe, the big data files do not need to be safe at every moment: any mess in them can be repaired from the log. "Repeat history, then undo the losers" gives one simple state to reason about: the exact state at the crash. From that state, rolling back a transaction after a crash is the same operation as rolling it back during normal work.
mistakes: People often think the database writes data pages to disk at commit. In fact it writes only the log (no-force). The data pages are written later by the background writer and at checkpoints, and a crash before that is repaired by redo.
People often think recovery only redoes committed work. In fact ARIES repeats history for all transactions first, then undoes the losers. This makes pages consistent with the log and allows row-level locking, at the price of replaying some work that is then undone.
People often think a checkpoint writes everything to disk and stops the system. In fact a fuzzy checkpoint runs while transactions continue and only records which pages are dirty; flushing is done gradually. The checkpoint's purpose is to bound the log that recovery must scan.
People often think fsync success always means the data is safe. In fact it depends on the disk's write cache, the file system and the cloud volume; fsync errors have also been mishandled: in 2018 it was found that PostgreSQL could retry after a failed fsync and lose data silently, which led to treating such failures as fatal.
tradeoffs: Choose frequent checkpoints (every 1 to 5 minutes, small max WAL size) when fast restart matters more than throughput, for example for a primary that must come back quickly. Choose infrequent checkpoints (15 to 30 minutes, large WAL) for write-heavy workloads, where fewer dirty page flushes and fewer full-page images save I/O; you give up longer replay after a crash, and more disk for logs.
Choose synchronous commit (flush before ack) when losing an acknowledged transaction is not acceptable; choose asynchronous commit when the loss of the last 100 to 500 ms of data is acceptable and you need much higher commit rate. The gain is large on slow disks (often 5 to 50 times), but the loss is real.
Choose undo plus redo logging with steal and no-force (ARIES) for general OLTP, where large transactions and memory pressure are normal; choose redo-only designs when MVCC keeps old versions (PostgreSQL) or the whole working set is in memory (many in-memory engines), which avoids undo logic but requires version cleanup (vacuum). Choose shadow paging or copy-on-write trees (LMDB, some file systems) when you want simple crash safety and cheap snapshots, accepting write amplification and weaker concurrency.
Choose physical logging (page images, large logs but simple) or logical logging (small logs, but replay depends on the state of the page) according to need; physiological logging is the common compromise. In the cloud, choose to ship the log to a distributed storage service (Aurora style) if you want fast recovery and replicas, accepting the dependence on that service.
friction: Recovery is subtle. The ARIES paper is more than 60 pages, and implementations must cover partial page writes, nested top actions (structure changes of indexes that must not be undone), savepoints, index and space-allocation logging, and recovery of recovery. Bugs here lose data rarely but catastrophically, and crash paths are difficult to test because they only run after a failure; tools such as fault injection, Jepsen-style tests and deterministic simulation try to explore them.
Recovery time grows with log size since the checkpoint and with replay speed. Many engines replay with one thread, so a busy primary can write faster than recovery can read, and a crash can mean minutes of downtime. Parallel redo by page helps, and standbys keep the log applied continuously for fast failover.
The logging itself adds write amplification: each change is written to the log and later to the page, and in some systems also to a doublewrite area and to replicas. The log is also a serial point: all transactions append to one stream, which limits throughput on very fast hardware, and group commit adds a small waiting time to every commit.
Finally, the guarantee depends on the hardware and OS telling the truth. Disks with volatile caches, controllers that ignore flush, file systems that reorder metadata, and cloud storage with weaker semantics all break the WAL rule silently, and the failure is found only after a crash.
practice: Understand your database's recovery settings. For PostgreSQL: checkpoint_timeout (default 5 minutes), max_wal_size, synchronous_commit, full_page_writes (keep it on unless your storage guarantees atomic page writes). For MySQL InnoDB: innodb_flush_log_at_trx_commit = 1 for full durability, innodb_redo_log_capacity, doublewrite. Know what an acknowledged commit means: log flushed locally, or replicated to another zone.
Test recovery, not just backup. Kill the database process and the machine during load (kill -9, power-cut tests on a test host, or storage fault injection), and measure restart time. Alert on checkpoint duration, WAL generation rate, replication lag and fsync latency. Keep backups and archived WAL, since the log is also what lets you restore to a point in time after an operator error.
When you build systems with your own durable state (a queue, a state store), follow the same recipe: append to a log, fsync before you acknowledge, checkpoint state periodically, and replay the log tail on restart. Make replay idempotent with sequence numbers, as pageLSN does. Kafka, Flink checkpoints and RocksDB's WAL are variations of the same design.
For lakehouse tables the transaction log plays this role at table level: a commit is a single atomic log entry, and a failed job leaves stray files that are invisible because no log entry names them. Clean them with VACUUM or orphan-file removal, not by hand.
quiz: What does the write-ahead logging rule require? || A log record describing a change must be on durable storage before the changed data page is written, and all of a transaction's log records must be flushed before its commit is acknowledged.
Why does ARIES redo the work of transactions that will be rolled back? || Repeating history brings every page to the exact state at the crash, so undo can run as normal rollback using logged information. This also supports fine-grained locking and makes recovery simple to reason about.
What is the purpose of compensation log records? || They log each undo step with a pointer to the next record to undo. Because CLRs are redone but never undone, a crash during recovery resumes undo where it stopped and the work stays bounded.
Checkpoints every 5 minutes with 20 MB/s of WAL, and replay at 100 MB/s. What is the worst-case redo time? || About 5 × 60 × 20 = 6,000 MB of log, so roughly 60 seconds of replay (plus analysis and undo).
When would you relax synchronous commit, and what exactly do you risk? || For data that is cheap to lose or recompute (metrics, click events) when commit rate matters. You risk losing the last few hundred milliseconds of acknowledged transactions after a crash, but not corruption, because the log order is kept.
interview: Walk through what happens on restart after a crash in ARIES. || Analysis scans from the last checkpoint to rebuild the active transaction table and dirty page table. Redo starts at the smallest recLSN and re-applies every logged change whose page has a lower pageLSN. Undo rolls back the losers from the largest LSN down, writing CLRs. After that the database is consistent and can accept new work.
Why is redo idempotent, and why does it matter? || Each page stores the LSN of the last change applied, and redo skips records whose LSN is not higher. Running recovery twice, or crashing during recovery, then gives the same result, which is essential because recovery can itself be interrupted.
How does PostgreSQL's recovery differ from ARIES? || PostgreSQL replays WAL redo records and has no undo pass, since MVCC leaves old versions in the heap and aborted transactions are marked invisible. Torn pages are handled with full-page images in the WAL after each checkpoint. The cost moves to vacuum.
A cloud database restarts and takes 10 minutes to recover. How do you shorten it? || Check log volume since the checkpoint and replay speed. Checkpoint more often, limit max WAL size, use parallel redo if available, make sure a hot standby can take over, and check that fsync and disk throughput are not the bottleneck. Aurora-style designs push redo into the storage layer.
What can go wrong if fsync lies or fails, and how do you defend against it? || The WAL rule is silently broken, so committed data may vanish or pages may be corrupt after a crash. Defend with hardware that honors flush (power-loss protection), fatal handling of fsync errors, checksums on pages and log records, replicas in separate failure domains, and crash tests.

@@ indexing
value: An index is an extra data structure, kept beside a table, that lets the database find rows by value without reading the whole table. A table of 100 million rows may take 5 seconds to scan; with an index on the right column, the same lookup reads a handful of pages and takes about a millisecond. The price is paid on writes: every insert, update or delete must also change each index, and each index takes disk and memory space.
This trade is the main lever of database performance. Most slow queries are queries that read far more data than they return, and most fixes either add an index that matches the query, change the query so an existing index applies, or remove an index that only slows writes. The idea is not limited to relational databases. A search engine is mostly an inverted index. A time-series store is mostly a time-ordered index with block summaries. A Parquet file carries min/max statistics per row group, which is a tiny index. A vector database is an index for nearest-neighbour search. Kafka's segment files have a sparse offset index; a Delta table has a deletion vector that indexes deleted row positions.
Two lower concepts supply the classic structures. Trees give the B-tree and B+ tree: a balanced, wide, sorted tree whose height grows with the logarithm of the table size, so any key is found in 3 to 5 page reads, and whose sorted leaves give range scans and ordering for free. Hashing gives the hash index: a key is hashed to a bucket and found in about one read, but with no order, so it supports equality only. Almost every other index type is a variation: bitmaps, inverted lists, LSM trees, R-trees, zone maps and Bloom filters answer other questions with the same pattern of a small structure that points to the big data.
terms: Index — a structure that maps column values to the locations of matching rows.
B+ tree — a balanced tree with many keys per node; internal nodes route the search and leaf nodes hold all keys in sorted order, linked for range scans.
Fanout — the number of children of a node; with 8 KB pages and small keys it is a few hundred, so trees stay very shallow.
Clustered index — an index whose leaves hold the whole row, so the table is stored in index order (InnoDB's primary key); a secondary index stores a pointer or the primary key.
Covering index — an index that contains every column the query needs, so the table need not be read (an index-only scan).
Composite index — an index on several columns, sorted by the first, then the second, and so on; the leftmost-prefix rule says it helps queries that constrain a leading part of its columns.
Selectivity — the fraction of rows that match a condition; a low fraction (few matches) is what makes an index useful.
Cardinality — the number of distinct values in a column.
Sequential scan — reading the whole table in order; cheap per row, and best when most rows are needed.
history: Early file systems used the Indexed Sequential Access Method (ISAM): a static index over a sorted file, which degrades as inserts pile up in overflow areas. In 1970, Rudolf Bayer and Edward McCreight at Boeing invented the B-tree, a tree that stays balanced under inserts and deletes by splitting and merging pages, and published it in Acta Informatica in 1972 ("Organization and Maintenance of Large Ordered Indexes"). Douglas Comer's 1979 survey "The Ubiquitous B-Tree" described the B+ tree variant, with data only in the leaves, that nearly all databases use. When Codd's relational model arrived, System R (1970s) added B-tree indexes, and the optimizer learned to choose between scans and index paths (Selinger et al., 1979).
Other families followed the data they had to serve. Hash indexes and extendible hashing (Fagin et al., 1979) gave constant-time equality lookup. Guttman's R-tree (1984) indexed rectangles and geographic data. Inverted indexes, first used in information retrieval, became the core of search engines (Lucene, 1999; Elasticsearch, 2010). Bitmap indexes arrived for low-cardinality columns in data warehouses in the 1990s. In 1996 O'Neil and colleagues proposed the log-structured merge tree (LSM) to index write-heavy data; it powers Bigtable (2006), Cassandra, RocksDB and many others.
The warehouse and lakehouse era changed the question. When data sits in immutable columnar files on object storage, maintaining a B-tree per column is unrealistic. Instead of exact indexes, systems keep cheap summaries: zone maps (min and max per block, from Netezza in the 2000s and now in Parquet and Delta), Bloom filters per file, partition pruning, data clustering (Z-order, Hilbert curves, Databricks liquid clustering) and sorted layouts. More recently, approximate nearest-neighbour indexes (HNSW, 2016; IVF and product quantization) added vector search to databases and lake engines.
how: Consider the B+ tree first, since it is the default index in PostgreSQL, MySQL InnoDB, Oracle and SQL Server. The database stores the index in fixed-size pages (8 KB in PostgreSQL, 16 KB in InnoDB). A leaf page holds a sorted list of (key, pointer) entries, and leaf pages are linked to their neighbours. An internal page holds separator keys and pointers to child pages. To find a key, start at the root, pick the child whose key range contains the key, and repeat until a leaf. The cost is one page read per level. This is where trees contribute: because each page holds hundreds of entries, the height h of a tree with N entries and fanout f is about log_f(N). With f = 300, a root with 300 children, each with 300 children, each with 300 leaf pages, gives 27 million leaf pages. Each leaf page holds about 300 entries, so four levels hold about 8 billion entries. So even a table of billions of rows needs 4 or 5 levels, and since the top levels are used by every query they stay in memory, so a lookup costs about 1 or 2 disk reads.
Inserts keep the tree balanced. A new entry goes into the right leaf; if the leaf is full, it splits into two half-full leaves and a new separator key goes up to the parent, which may split in turn. The tree grows only at the root, so all leaves stay at the same depth. Deletes may leave pages sparse, and some systems merge them. Sequential keys (auto-increment ids, timestamps) fill the rightmost leaf and keep pages dense; random keys (random UUIDs) hit random leaves, split pages often, and cause more cache misses and write amplification.
A secondary index stores the indexed column(s) and a pointer to the row. In PostgreSQL the pointer is the physical tuple location in the heap; in InnoDB the leaf stores the primary key value, and a lookup through a secondary index then walks the primary (clustered) index a second time. If the index contains all columns the query needs (covering), the second step is skipped; PostgreSQL also needs its visibility map to be current to answer from the index alone. A range query on a B+ tree finds the first key and then walks the linked leaves in order, which is sequential reading. That same order serves ORDER BY and merge joins without a sort.
Composite indexes sort by the first column, then the second within equal first values. An index on (user_id, created_at) serves "user_id = 5" and "user_id = 5 AND created_at > X ORDER BY created_at", where the matching entries are adjacent and already sorted. It does not serve "created_at > X" alone, because those entries are spread over all users. Put equality columns first and the range or sort column last; among equality columns, put the more selective one first only if it also serves other queries. Partial indexes (WHERE active) and expression indexes (lower(email)) index only what queries use.
The hash index maps hash(key) to a bucket, with overflow handling and splitting (linear or extendible hashing) as data grows. Equality takes about one page read, but ranges and ordering are impossible, and many systems prefer the B-tree because it does nearly as well on equality. Hash is more common inside the engine, for hash joins and in-memory indexes. The inverted index maps each term to a sorted list of document ids (postings) and answers "which documents contain these words" by intersecting lists. A bitmap index keeps one bit-vector per distinct value, and answers AND and OR of low-cardinality filters by bitwise operations (in the warehouse style, e.g. region = 'EU' AND status = 'open'). LSM trees buffer writes in memory and merge sorted files in the background, making inserts cheap (sequential) and reads check several levels, helped by Bloom filters. Spatial and vector indexes organize points so that a nearby search visits a small part of the data.
The optimizer decides whether to use an index. It estimates selectivity from statistics (histograms, distinct counts) and compares costs: an index scan costs a few page reads for the tree plus a random read per matching row; a sequential scan costs one cheap sequential read of the whole table. As a rule of thumb, an index helps when the query touches a small fraction of rows (often under 1 to 5 percent, higher on SSDs, where random reads are cheap) and loses when it touches a large fraction. A "bitmap scan" in PostgreSQL sits between: it collects row locations from the index, sorts them by page, and then reads pages in order.

example: A table events(id, user_id, created_at, payload) has 100 million rows, about 100 bytes each, so the table is 10 GB. The common query is: WHERE user_id = 5 AND created_at >= '2026-09-01' ORDER BY created_at DESC LIMIT 20.
Without an index, the database scans the table. At about 2 GB/s of sequential read, 10 GB takes around 5 seconds, plus filtering. Each query reads everything to return 20 rows.
Add an index on user_id only. Each leaf entry holds an 8-byte key, a 6- to 8-byte pointer and some overhead, say 24 bytes; 100 million entries is about 2.4 GB, so with pages at about 70 percent full, roughly 3.4 GB. An 8 KB page holds about 300 entries, so the leaves number about 425,000 pages. The tree has 4 levels: a root, about 5 pages, about 1,400 pages, and the 425,000 leaves. Everything above the leaves is only about 12 MB, so it stays in memory, and finding the first entry costs about 1 disk read. Suppose user 5 has 2,000 events. The query finds them via the index (a few reads), fetches 2,000 heap rows (random reads, many on different pages, say 2,000 × 100 µs = 200 ms if not cached), filters by date and sorts. Much better than 5 seconds, but not good.
Now add a composite index on (user_id, created_at). The database descends to the first entry for user 5 with the newest date (scanning the index backward), and reads 20 entries in order. The sort and the date filter disappear. Cost: 2 to 3 index page reads plus 20 heap fetches, about 20 × 100 µs = 2 ms cold, much less when cached. That is about 2,500 times faster than the scan. If the select list was only (user_id, created_at, id), adding id as an included column makes the index covering, and the 20 heap fetches vanish: roughly 0.3 ms.
Count the cost on the write side. Each insert now also inserts into the composite index. If the table had 5 indexes, one logical insert means 6 B-tree insertions (the heap plus 5 indexes), each possibly dirtying a different page. At 20,000 inserts per second that is 120,000 index operations per second, and the index pages and their WAL must be written too. An index that no query uses is pure loss: in PostgreSQL, pg_stat_user_indexes.idx_scan = 0 over a few weeks marks one that you can drop.
Last, the lakehouse version. The same table in Delta on Parquet has no B-tree. A query for user 5 uses file statistics: if the table is clustered by user_id (Z-order or liquid clustering), each file covers a narrow range of users, and min/max statistics let the engine skip all but a few files out of thousands. Delta collects statistics on the first 32 columns by default, so putting filter columns early (or setting the property) matters. Bloom filters per file help with the remaining equality lookups on high-cardinality columns.
intuition: The index at the back of a book: a small sorted list that tells you which pages to open, so you do not read the whole book.
The index works because looking up is cheaper than reading, if the lookup structure is small, sorted and shaped for the question. A sorted structure lets you halve the search space at each step; a wide tree makes each step a single disk read; a hash makes one jump. The cost is that you must keep the structure in step with the data, which is why every index is a bet that reads will be more frequent or more valuable than the extra write work.
mistakes: People often think adding more indexes always makes a database faster. In fact each index slows every insert and update, uses memory that could cache data, and gives the optimizer more plans to choose from. Indexes that no query uses are pure cost.
People often think an index is used whenever the column appears in WHERE. In fact the optimizer ignores it when the filter matches a large share of rows, when the column is wrapped in a function (WHERE lower(email) = … with no expression index), when types mismatch (a string compared with a number), when a LIKE pattern starts with a wildcard, or when the leading column of a composite index is not constrained.
People often think the order of columns in a composite index does not matter. In fact it decides which queries the index can serve, because the index is sorted by the first column first. An index on (a, b) does not help a query on b alone.
People often think a B-tree is a binary tree. In fact it is a wide tree with hundreds of children per node, designed so that each node is one disk page. A binary tree of 100 million keys would be about 27 levels deep, each a separate page read.
tradeoffs: Choose a B+ tree when you need equality, ranges and ordering and the table is read far more than written. Choose an LSM tree when writes dominate (ingest of 100,000 or more rows per second), accepting slower point reads (several levels to check, helped by Bloom filters) and extra background compaction work, with write amplification of 10 to 30 times.
Choose a hash index or a key-value layout when you only need exact-match lookups and the keys are random; give up ranges and ordering. Choose a covering index when one hot query needs a few columns, to avoid heap fetches, and accept a larger index and slower writes. Choose a partial index when queries always filter on a small subset (status = 'open') to shrink the index by 10 times or more.
Choose an inverted index for text search and filters over many tags; choose a bitmap index for low-cardinality columns in read-mostly analytical tables; avoid bitmap indexes on tables with frequent updates, since changes lock large bit ranges. Choose summaries (zone maps, Bloom filters, partition pruning) with a clustered layout for lakehouse tables, since they cost nothing to maintain on immutable files, and accept that they skip files rather than find rows.
friction: Every index is a duplicate of data that must be kept consistent, so index maintenance is a large share of write cost, WAL volume and replication lag. Index bloat accumulates from updates and deletes (pages half empty), so indexes must be rebuilt (REINDEX, or online rebuild), and large rebuilds take hours and need extra space.
Choosing indexes is a design problem with no perfect answer: the best set depends on the query mix, which changes over time. Automatic advisors exist (Oracle, SQL Server, some cloud services), but they can over-recommend, and they cannot see future queries. The optimizer can also choose badly when statistics are stale or when column values are correlated, picking an index scan that reads half the table randomly.
Indexes are poor for low-selectivity filters and for analytic queries that scan most of a table: there a column store with compression and zone maps beats any B-tree. B-trees also assume that random reads are the expensive part and that pages are fixed size; on modern NVMe, many-core machines and in-memory databases, latch contention at the root and cache misses dominate, which pushes toward other designs (Bw-trees, adaptive radix trees, learned indexes).
practice: Design indexes from queries, not from tables. List the ten most frequent and ten slowest queries, and look at their filters, joins and sort order. Create composite indexes with equality columns first, then the range or sort column. Use EXPLAIN (ANALYZE) to confirm that the index is chosen and to compare estimated with actual row counts; do not trust a guess.
Check cost on the write side. Measure insert and update latency before and after, and watch index size. Drop indexes that are duplicates (an index on (a) is redundant if (a, b) exists) or unused, using the usage statistics of your database after a full business cycle (a month, to include reports).
Write predicates so the index applies: compare the column directly with a constant of the same type, avoid functions on the indexed column (use an expression index, or rewrite the range), and avoid leading wildcards. Use keyset pagination (WHERE (created_at, id) < (?, ?) ORDER BY … LIMIT) instead of large OFFSET values, which read and discard all skipped rows. Prefer time-ordered keys. Keep statistics current with ANALYZE.
For a lakehouse, choose partition columns with low cardinality that appear in most filters (a date), cluster inside partitions on the high-cardinality filter columns (Z-order or liquid clustering), keep files at a healthy size (hundreds of megabytes) by compaction, and add Bloom filters only for equality lookups on high-cardinality columns that clustering cannot help. For search and vector workloads, use the engine built for them (Elasticsearch, Pinot, a vector index) and decide how the index is fed and how stale it may be.

value: Distributed systems theory is the study of what several computers connected by a network can and cannot achieve, when messages can be delayed or lost and machines can crash. It gives you two things. First, a vocabulary of models: what exactly do we assume about timing, failures and links? Second, a set of proofs: given those assumptions, this problem is solvable (and here is the cost), or it is impossible (and here is the proof). Knowing the impossible results saves years. Nobody should try to build a protocol that always reaches agreement in a fully asynchronous network with a crash, because it has been proven that none exists.
The reason this matters in daily engineering is that every distributed system lives inside such a model, whether its authors say so or not. A Kafka cluster that elects a controller, a database that replicates with Raft, a stream job that restarts from a checkpoint: each of them makes assumptions such as "a majority of nodes stay up", "clocks drift by less than a few hundred milliseconds" or "a node that does not answer within 10 seconds is dead". Theory tells you which of these assumptions the safety of the system depends on, and which only affect availability. When an incident happens, "two leaders at once" or "the cluster froze", the explanation usually lies in an assumption that did not hold.
The layers below supply the proof tools. Logic is how impossibility is proved: FLP is an argument about all possible algorithms, built from indistinguishability (a process cannot tell a slow peer from a dead one) and from statements about sequences of states. Probability lets randomized protocols escape some impossibility results, and gives the arithmetic for quorum availability. Game theory models participants who deviate on purpose: Byzantine nodes as adversaries, and rational nodes with incentives in blockchains. The layers above are the protocols and guarantees that these results shape: consensus, Paxos, Raft, ZAB, replication and in-sync replicas, CAP and PACELC, consistency models, logical clocks, CRDTs, watermarks, distributed snapshots and RPC semantics.
terms: System model — the assumptions about timing (synchronous, asynchronous, partially synchronous), failures and links under which an algorithm is claimed to work.
Crash-stop, crash-recovery, omission, Byzantine — failure types: a node halts for good; halts and may restart with its disk; loses some messages; or behaves arbitrarily, even maliciously.
Synchronous, asynchronous, partially synchronous — message delay and process speed have a known bound; have no bound; or have a bound that holds eventually but is unknown.
Safety and liveness — safety means nothing bad ever happens (no two different decisions); liveness means something good eventually happens (a decision is made).
Consensus — the problem of getting all correct nodes to agree on one value, where the value was proposed by some node.
Failure detector — a module that gives each node a (possibly wrong) list of suspected crashed nodes; completeness and accuracy describe how wrong it may be.
Quorum — a subset of nodes large enough that any two quorums overlap; a majority is the usual choice.
Indistinguishability — the core proof tool: a node cannot tell two executions apart because it saw the same messages, so it must act the same in both.
Happened-before — the partial order of events defined by local order and by message send and receive; there is no global clock.
history: The first results are about communication. In 1975 Akkoyunlu, Ekanadham and Huber described a problem of agreeing over an unreliable link, and Jim Gray called it the "two generals" problem in 1978. Two generals on opposite hills must attack at the same time; their only messengers may be captured. No finite exchange of messages makes both sure that the other will attack. Leslie Lamport's 1978 paper "Time, Clocks, and the Ordering of Events in a Distributed System" showed that without a global clock, the right notion is the happened-before order, and that logical clocks can capture it. In 1980 and 1982, Pease, Shostak and Lamport introduced Byzantine failures, in which a node may lie, and proved that agreement needs more than two-thirds of the nodes to be honest (\( n \ge 3f + 1 \) for oral messages).
In 1985 Michael Fischer, Nancy Lynch and Michael Paterson proved the FLP result: in a fully asynchronous system, no deterministic algorithm can guarantee consensus if even one process may crash. The paper won the Dijkstra Prize in 2001. The response over the next decade was to change the model, not to give up. Ben-Or (1983) showed that randomness gives termination with probability 1. Dwork, Lynch and Stockmeyer (1988) defined partial synchrony: the system is asynchronous for a while but eventually behaves well, and consensus becomes solvable. Chandra and Toueg (1996) defined failure detectors and showed that an eventually-correct one (◇S) is enough to solve consensus when a majority of nodes is correct; with Hadzilacos they showed that even the weaker ◇W is the minimum needed. This made "timeouts" a formal object. Lamport's Paxos (written 1989 to 1990, published 1998) was the protocol that fits this model: it is always safe and makes progress when the network becomes stable enough.
The theory then moved into practice. Lamport and Alpern and Schneider formalized safety and liveness (1977, 1985), and TLA+ made specification and model checking usable in companies. Brewer's conjecture (2000) and Gilbert and Lynch's proof (2002) became the CAP theorem. Castro and Liskov's PBFT (1999) made Byzantine tolerance practical, and blockchains from 2008 made it popular. Raft (2014) packaged consensus for understandability. Since about 2015, Jepsen tests have found real violations in widely used databases, and the "gray failure" work (Huang et al., HotOS 2017) showed that real components are often partly broken in ways no clean crash model captures.
how: Every result starts with a model, three choices at a time. Timing: synchronous (every message arrives within a known bound \( \Delta \) and processes take steps at a known rate), asynchronous (no bound at all), or partially synchronous (a bound exists but is unknown, or holds only after some unknown time). Failures: crash-stop, crash-recovery (the node comes back with its stable storage), omission, or Byzantine. Links: reliable (every message sent between correct nodes is delivered), fair-loss (it is delivered if you retry forever), or arbitrary. The same problem can be easy in one model and impossible in another, so the first question about any protocol is "in which model is it correct?"
Properties are split into safety and liveness. A safety property can be violated in a finite prefix of an execution: "two nodes never decide different values." A liveness property can only be violated by an infinite execution: "every proposal is eventually decided." Every property is the intersection of a safety and a liveness property (Alpern and Schneider). This split organizes the whole field. FLP says: in the asynchronous model with a crash, you cannot have both safety and liveness for consensus. Practical protocols keep safety always and give up liveness when the model is violated. If the network is bad, Raft or Paxos may stop answering, but will not return two different answers.
Why does FLP hold? The proof is short. Call a configuration (the state of all processes plus the messages in transit) 0-valent if every possible continuation decides 0, 1-valent if all decide 1, and bivalent if both outcomes are still possible. Step one: some initial configuration is bivalent. Arrange initial configurations in a chain where neighbours differ in one process's input; the first is all 0 (must decide 0), the last is all 1 (must decide 1), so somewhere a 0-valent configuration sits next to a 1-valent one, differing in process p. If p crashes at the start, the others cannot tell the two configurations apart, so they must decide the same value in both, a contradiction. So one of them is bivalent. Step two: from any bivalent configuration, and any pending message m, the adversary can find a way to deliver m and still end in a bivalent configuration. So the adversary can deliver every message eventually (a fair schedule), and the system still never decides. The proof uses only the fact that a slow process and a crashed process look the same. This is logic at work: an argument about all algorithms at once.
How do real systems escape? They change the model. Partial synchrony: use timeouts as failure detectors. A node that does not hear from the leader for a timeout starts an election. The timeout can be wrong (a slow leader is suspected) and that costs liveness for a while but never safety, because quorum intersection protects it: any two majorities share a node, so two leaders cannot both get a majority in the same term. Randomization: Raft picks random election timeouts (the paper suggests 150 to 300 ms) so that candidates rarely collide, and uses probability to make livelock vanishingly unlikely. Probability supplies the argument that a split vote repeats with exponentially decreasing chance. A third way is to strengthen the model with hardware: Google's Spanner uses GPS and atomic clocks (TrueTime) to bound clock uncertainty to a few milliseconds, which turns time into a usable tool.
The failure model sets the cost. For crash failures with partial synchrony, consensus needs \( n \ge 2f + 1 \) nodes to tolerate \( f \) crashes (a majority quorum). For Byzantine failures, \( n \ge 3f + 1 \), and quorums must intersect in at least one honest node, so they are larger (\( 2f + 1 \) of \( 3f + 1 \)) and the messages are more numerous (PBFT uses a quadratic number of messages per decision). In the synchronous crash model, agreement needs \( f + 1 \) rounds in the worst case. Game theory enters when nodes do not follow the protocol on purpose: blockchain designs assume a fraction of participants is Byzantine or rational, and use incentives (rewards and penalties) to make honest behavior the best strategy.
Finally, theory also gives tools for time. With no global clock, Lamport clocks give a number to every event that respects causality (if a happened before b, then clock(a) < clock(b)). Vector clocks are stronger: they let you tell whether two events are ordered or concurrent. Distributed snapshots (Chandy–Lamport) record a consistent global state without stopping the system. Event time and watermarks in stream processing are practical estimates of "how late can data be", because the system can only estimate, not know.

example: First, the two generals. General A sends a message "attack at dawn". It may be lost. A cannot attack unless B confirms, so B sends an acknowledgement. That may be lost too. So A sends an acknowledgement of the acknowledgement, and so on. Suppose some protocol finishes after k messages, and the last message is essential. The sender of that last message cannot know whether it arrived. If it was not essential, drop it and get a shorter protocol with the same guarantee. By induction on k, no finite protocol makes both generals certain. If each message is lost with probability 0.1, one message arrives with probability 90%, and all three messages of a three-step exchange with 0.9³ ≈ 73%. More messages raise confidence but never make it certain. TCP's connection close has the same limit, which is why it uses timeouts.
Second, a quorum calculation. A cluster has 5 nodes using majority quorums (3 of 5), so it tolerates \( f = 2 \) crashes. If a partition splits it into 3 and 2, the side with 3 can elect a leader and commit entries; the side with 2 cannot reach a majority, so it stops accepting writes, and no divergence happens. That is the safety-over-liveness choice. Availability under independent failures: if each node is up 99.9% of the time, then 3 nodes with majority 2 are available with probability \( p^3 + 3p^2(1 - p) \) ≈ 99.9997%, and 5 nodes with majority 3 reach about 99.999999% (the failure probability is about \( 10 \times (0.001)^3 = 10^{-8} \)). Real failures are correlated (same rack, same bad deploy), so the true number is much lower; that is a limit of the model, not of the arithmetic.
Third, a timeout. A Raft follower waits a random time between 150 and 300 ms for a heartbeat from the leader. If a network pause of 400 ms occurs, followers time out, a new election starts, and a new term begins. The old leader, when it wakes up, sees the higher term and steps down. Safety held throughout, because the old leader's writes needed acknowledgement from a majority, and any two majorities overlap. What was lost was liveness for a few hundred milliseconds. If you set the timeout to 10 ms in a cloud network with 50 ms spikes, the cluster would elect new leaders constantly and make little progress, even though no node ever crashed. This is how a theory result becomes a tuning rule.
intuition: Physics for networks: first learn the laws you cannot break, then design inside them.
The central fact is that a node knows only what messages it has received. Silence can mean death, delay or loss, and no node can tell them apart without more assumptions. Every impossibility result is a precise version of this. Every algorithm is a way to act safely under this doubt: ask a majority so any two answers overlap, number your attempts so old ones lose, and treat time-outs as hints that can cost speed but never correctness.
mistakes: People often think FLP says consensus is impossible. In fact it says no deterministic algorithm can guarantee termination in a fully asynchronous system with a crash. With timeouts (partial synchrony), randomization or failure detectors, consensus works in practice, and protocols stay safe even when they cannot make progress.
People often think a timeout tells you that a node is dead. In fact it only tells you that no message arrived in time. The node may be slow, paused (garbage collection, a stalled VM), or cut off by the network. Designs that treat a timeout as proof (two nodes both acting as leader) cause split-brain.
People often think CAP means you can only have two of consistency, availability and partition tolerance. In fact partitions are not optional in a real network, so the choice is what to give up during a partition, and CAP says nothing about normal operation, where latency versus consistency is the real trade (PACELC).
People often think Byzantine fault tolerance is needed for ordinary data centers. In fact most systems assume crash faults because they trust their own software, which is much cheaper (2f + 1 nodes, not 3f + 1, and linear messages). Byzantine protocols are for settings with distrust, such as blockchains, or where bugs and corruption must be masked.
People often think network failures are rare and clean. In fact partial partitions (A reaches B and C, but B cannot reach C), asymmetric links and slow nodes are common. Studies of cloud outages and Jepsen reports repeatedly find that systems that assumed a clean failure model lose data in them.
tradeoffs: Choose a crash-fault model with majority quorums (2f + 1) for services inside your own data center or cloud account. Choose Byzantine tolerance (3f + 1) only when participants do not trust each other, or when hardware or software faults may produce arbitrary outputs and the cost of a wrong answer is huge. You pay about 50 percent more nodes, many more messages and much more complex code.
Choose a longer failure-detection timeout (seconds) when false suspicion is expensive, for example leader changes that trigger large state transfers. Choose a shorter timeout (hundreds of milliseconds) when fast failover matters more than occasional unnecessary elections. Whatever you choose, keep it above the 99.9th percentile of heartbeat delay, including GC pauses, or you will create failures yourself.
Choose to stay safe and stop (a CP-style design) when wrong answers cost more than downtime: money, inventory, leader election. Choose to stay available and reconcile later (an AP-style design with CRDTs, last-writer-wins or application merges) when users prefer a possibly stale answer to an error: shopping carts, presence, counters. You give up either uptime in a partition or simplicity of reasoning.
Choose stronger time assumptions (hardware clocks, bounded drift as in Spanner) if you need external consistency across regions, accepting hardware cost and a wait of a few milliseconds per commit; choose logical clocks or version vectors when you cannot trust wall clocks and can live with partial order.
friction: Proofs apply to models, and models simplify. Real components fail partially: a disk gets slow but not dead, a NIC drops 1 percent of packets, a process stalls for 30 seconds in a GC pause, a clock jumps after an NTP step. These "gray failures" make some nodes look healthy to one observer and dead to another, and break the assumption that failure detection is simple. Many production outages involve exactly such a case that the theoretical crash model ignores.
Bridging proof and code is hard. A protocol proved correct on paper can be implemented wrongly, and Paxos is famously "simple to state and hard to implement": multi-decree variants, membership changes, log compaction and disk corruption are all outside the basic proof. Testing finds bugs only in the interleavings it happens to try. Formal methods (TLA+, Ivy, Verdi, model checking) and deterministic simulation help, but need effort and skill.
The results are also pessimistic in a way that is not always useful. FLP says a bad schedule exists, but real networks are not adversarial, and the probability of hitting it is tiny. At the same time, the theory says little about performance: it tells you what is possible, not what is fast. The cost of a consensus round (one or two network round trips, plus a disk flush) is the real limit on write latency, and across regions that means 50 to 200 ms.
practice: When you design or review a distributed component, write the model down: what failures are tolerated (how many nodes, which kinds), what timing is assumed, and what the system does when the assumption fails. Ask of every timeout, lease and heartbeat: what is the worst case if this is wrong? Ask of every "exactly one" (one leader, one writer, one owner): what stops two from existing when a node is paused? Fencing tokens (a number that increases with each leader term and is checked by the storage) are the standard answer.
Prefer proven protocols and libraries (Raft implementations, ZooKeeper, etcd, Kafka's KRaft controller, a managed consensus service) to your own. Use idempotent operations and unique request ids so that retries after an unknown outcome are safe, because an RPC timeout means "I do not know", not "it failed".
Test failures on purpose: network partitions, partial partitions, slow disks, paused processes, clock jumps. Use Jepsen-style tests, chaos experiments and, for protocols you write, TLA+ models and deterministic simulation. Monitor the signals that betray bad assumptions: leader changes per hour, replication lag, clock offset, heartbeat latency tails.

value: A process is a running program together with everything the operating system keeps for it: its own virtual address space, its open files, its permissions, its current register values and its place in the scheduler. The central idea is isolation. Each process sees its own private memory and cannot read or write the memory of another process, so a bug, a crash or a malicious program in one process cannot corrupt another. The kernel sits in between and decides who runs, who gets memory and who may touch which file.
This is what makes a shared computer usable. A laptop or a server runs hundreds of processes at the same time: a database, a web server, a monitoring agent, a shell. If one of them crashes with a segmentation fault, the kernel removes that process and the others continue. If one leaks memory, the kernel can kill only that process (the out-of-memory killer). Process boundaries are also the unit of security (a user id, a set of capabilities), of resource accounting (CPU time, memory), and of failure. Many architectures use processes on purpose for this reason: PostgreSQL runs one process per connection, Chrome one process per site, and nginx a set of worker processes.
Two lower concepts make the process possible. Virtual memory and paging give each process its own address space: the CPU translates each virtual address with a page table that belongs to the process, so two processes can both use address 0x7fff0000 and reach different physical memory. This also provides lazy allocation and copy-on-write, which make creating a process cheap. CPU scheduling shares the cores among the runnable processes: a timer interrupt lets the kernel take the CPU back after a time slice, so a process that loops forever cannot freeze the machine. The layers above build on the process: namespaces and cgroups turn processes into containers by limiting what they can see and use, and the Linux kernel is, at its core, the manager of processes and threads.
terms: Process — a program in execution with its own address space, file descriptor table, credentials and at least one thread of control.
Address space — the range of virtual addresses a process can use; the page table maps these to physical memory.
Process control block (PCB) — the kernel's record of a process: id, state, registers, memory map, open files, credentials (task_struct in Linux).
Context switch — saving one process's CPU state and loading another's so the CPU can run a different process.
fork and exec — fork creates a child as a copy of the parent; exec replaces the current program image with a new program.
Copy-on-write (COW) — after fork, parent and child share the same physical pages, marked read-only; a page is copied only when one of them writes to it.
File descriptor — a small integer, local to a process, that names an open file, pipe or socket.
Zombie process — a process that has exited but whose exit status has not yet been collected by its parent with wait().
System call — the controlled entry from user mode into the kernel, used to ask for services such as read, write, fork and mmap.
IPC (inter-process communication) — ways for processes to exchange data: pipes, sockets, shared memory, signals, files.
history: Early computers ran one program at a time. Time-sharing systems of the 1960s (CTSS at MIT, then Multics, a joint project of MIT, Bell Labs and General Electric) needed to protect users from each other, and so they defined the process as the unit that owns an address space and is scheduled. When Bell Labs withdrew from Multics, Ken Thompson and Dennis Ritchie built Unix (from 1969) with a deliberately small design. Their 1974 CACM paper "The UNIX Time-Sharing System" described processes created by fork, programs loaded by exec, and communication by pipes, a combination that made the shell easy to write: a command is a process, and a pipeline connects them. The idea of fork goes back to earlier systems such as Project Genie (1960s) and Conway's 1963 work.
Over the next decades the model grew more careful. Hardware memory protection and virtual memory became universal. BSD added sockets and job control. System V and POSIX standardized the interfaces (1988 onward). Linux (1991) implemented processes and threads as one kind of object, a task, created with the clone system call, with flags that decide what is shared. Windows NT chose a different creation call (CreateProcess starts a new program directly, with no fork) and Mach chose tasks and threads. In 2007, Linux 2.6.23 introduced the Completely Fair Scheduler, and in 2023 Linux 6.6 replaced it with EEVDF (earliest eligible virtual deadline first), which changed how the next process is picked.
The security and cloud era added new questions. The Meltdown and Spectre attacks (2018) showed that hardware speculation can leak data across the boundary between processes and the kernel, which led to costly fixes such as kernel page-table isolation. Containers (cgroups in 2007, namespaces in the 2000s, Docker in 2013) reused the process as the unit of packaging. Researchers, in the HotOS 2019 paper "A fork() in the road", argued that fork is now a poor primitive for large multi-threaded programs, and that posix_spawn-like designs should be preferred.
how: The kernel represents each process with a process control block, called task_struct in Linux. It holds the process id (pid), the parent id, the state, scheduling data, the saved CPU registers when the process is not running, a pointer to the memory descriptor (the page-table root and the list of mapped regions), the table of open file descriptors, the credentials (user and group ids, capabilities), signal handlers and resource limits. The states are roughly: runnable (ready, waiting for a CPU), running, sleeping (blocked on I/O, a lock or a timer) and exited (zombie until the parent collects it). The scheduler, the second layer below, keeps the runnable processes in a per-core structure (a red-black tree ordered by virtual deadline or runtime in Linux) and picks the next one when a time slice ends, when the running process blocks, or when a higher-priority process wakes up.
The address space is the key resource. A typical Linux process has: the program's code (text, read-only and shared among processes running the same binary), read-only data, initialized data, zero-initialized data (bss), the heap (grows up through brk or mmap), memory-mapped regions for shared libraries and files, and the stack (grows down). The addresses are virtual. A page table, one per process, maps 4 KB pages to physical frames, or marks them as absent. This is where virtual memory contributes: the hardware (the memory management unit) checks the table on every access, so a process can reach only the pages the kernel has mapped for it, and the kernel can map a page on first touch (demand paging), share it, swap it out, or mark it read-only for copy-on-write. A process accessing an unmapped address gets a page fault, and if the kernel agrees the access is invalid, a SIGSEGV signal ends the process.
Creating a process in Unix takes two steps. fork() makes a child that is a copy of the parent: the same code, the same open files, a copy of the page tables. It does not copy the memory itself. Both processes' page tables point to the same physical pages, which are marked read-only; the first write by either side causes a page fault, and the kernel allocates a new page, copies the 4 KB, and lets the write continue. This copy-on-write makes fork cost proportional to the size of the page tables (about 8 bytes per 4 KB page, roughly 2 MB of page-table entries per gigabyte), not to the size of the data. The child then usually calls exec(), which throws away the copied address space and loads a new program. The parent calls wait() to collect the child's exit status. The split into two calls is flexible: between fork and exec the child can rearrange its own file descriptors (redirect output, connect a pipe), which is how a shell builds pipelines.
Context switching moves the CPU between processes. On a timer interrupt, a blocking system call or an I/O completion, the kernel saves the registers of the current process in its PCB, picks the next runnable process, switches the page-table pointer to the new process's table, and restores its registers. The direct cost is a few microseconds. The indirect cost is larger: the new process finds the CPU caches and the TLB (the cache of address translations) full of the old process's data, so it runs slowly for a while. Hardware tags such as PCID avoid a full TLB flush, but cold caches remain. This is why a process that switches 10,000 times a second spends 5 percent or more of its time on switching and cache refill.
Processes cooperate through explicit channels, since memory is not shared by default. A pipe is a kernel buffer (64 KB by default on Linux) with a read end and a write end; the writer blocks if it is full and the reader blocks if it is empty. Sockets work within a machine (Unix domain sockets) or across machines. Shared memory maps the same physical pages into two address spaces, the fastest path, but then the processes need locks. Signals deliver small notifications (SIGTERM asks to stop, SIGKILL cannot be caught). Each of these costs a system call and usually a copy, which is why a message between processes costs microseconds, compared with nanoseconds for a function call.
Last, resource control. The kernel enforces limits per process (open files, stack size, number of processes), and cgroups apply them to groups: a memory limit, a CPU quota, an I/O weight. Namespaces change what a process sees: its own pid numbering, network stack, mount points and hostname. A container is a process (or a tree of processes) started in a new set of namespaces under a cgroup, with no hypervisor. The first process in a container becomes pid 1 there and must reap zombie children.

example: Take the pipeline ls | wc -l typed in a shell. The shell is process 100. It first calls pipe(), which gives two file descriptors, say 3 (read end) and 4 (write end). It calls fork() twice. In the first child (pid 101) it calls dup2(4, 1), so that file descriptor 1 (standard output) now refers to the pipe, closes 3 and 4, and calls exec("ls"). The process image is replaced by ls, but the file descriptor table survives exec, so ls writes into the pipe without knowing it. In the second child (pid 102), dup2(3, 0) makes standard input read from the pipe, and exec("wc", "-l") counts the lines. The shell closes its own copies of the pipe, so that wc sees end-of-file when ls exits, and then waits for both children. The whole structure is only fork, exec, pipe, dup2 and wait. That is the reason Unix processes compose so well.
Now a number-based case: Redis snapshots. A Redis server holds 10 GB of data in memory, which is 10 GB / 4 KB ≈ 2.6 million pages. To save a snapshot, it calls fork(). The kernel copies the page tables: 2.6 million entries of 8 bytes is about 20 MB, which takes some milliseconds to tens of milliseconds, and during that time the parent is blocked. After fork, the child walks its view of memory (frozen at the moment of fork) and writes it to disk, while the parent keeps serving writes. Each time the parent modifies a page for the first time, the kernel copies the 4 KB page (a few microseconds). If the snapshot takes 60 seconds and the workload modifies 20 percent of the pages, 0.2 × 10 GB = 2 GB of extra memory is used. If the machine had only 4 GB free, the kernel runs out of memory and the out-of-memory killer may stop Redis. That is why operators leave memory headroom for copy-on-write and why very large Redis instances are tricky to snapshot.
intuition: Each program lives in its own apartment with its own key, and the kernel is the building manager who owns the master key, the water meter and the walls.
The design is natural because a computer has a few shared things (CPU time, memory, disk) and many programs that cannot all be trusted. Giving each program a private address space makes mistakes local. Letting the kernel hand out the CPU in slices makes sharing fair. Everything else, such as fork, pipes and signals, is just the minimum set of doors between apartments.
mistakes: People often think fork copies all the memory of the parent. In fact it copies only the page tables and shares the pages copy-on-write. The cost shows up later, as page faults when either side writes, and as extra memory use.
People often think a process and a program are the same thing. In fact a program is a file on disk; a process is a running instance with state. One program can run as many processes, and one process can load different programs over its life with exec.
People often think killing a parent kills its children. In fact children keep running and are adopted by pid 1 (or the nearest subreaper). A child that exits when its parent never calls wait() stays as a zombie, which uses a pid and a small kernel record. In containers, a pid 1 that does not reap children leaks zombies.
People often think processes are fully isolated. In fact they share the kernel, the CPU caches, the disk and the network, so they can interfere through contention, and speculative-execution attacks (Spectre) and the Rowhammer memory effect have crossed process boundaries. A container is a process with a restricted view, not a virtual machine.
tradeoffs: Choose processes (one per request or per worker) when isolation and fault containment matter more than the per-unit cost: a crashing worker takes down only itself, memory leaks are bounded by restart, and security boundaries are clear. This is the model of PostgreSQL, nginx workers and browsers. You give up memory (each process has its own heap and page tables) and fast sharing.
Choose threads in one process when tasks need to share a lot of data at low cost and you trust the code; you give up fault isolation. Choose an event loop in one or a few processes when you have very many mostly-idle connections (tens of thousands), accepting more complex code. A pool of 100 to 500 database connection processes is usual; beyond that, put a connection pooler (PgBouncer) in front, because each PostgreSQL backend takes several megabytes and costs scheduler time.
Choose fork for short setup (a snapshot, a pre-fork server whose workers share loaded code and data copy-on-write), and posix_spawn, vfork or a launcher process for starting many unrelated programs from a large multi-threaded parent, because fork must copy page tables and is unsafe with threads (only the calling thread survives in the child, and locks held by other threads stay locked).
Choose a container (namespaces and cgroups) when you want lightweight isolation with a shared kernel and very fast start (milliseconds); choose a virtual machine or a microVM (Firecracker), or a user-space kernel sandbox (gVisor), when the workloads are mutually untrusted, accepting extra memory, boot time of 100 ms to seconds, and some overhead.
friction: Creating and switching processes is expensive compared with threads or tasks: a new process needs page tables, a kernel stack and a task_struct, and the first minutes of its life run with cold caches. A system with 100,000 processes spends noticeable time in the scheduler and the memory manager. Per-process memory overhead (page tables, libraries loaded separately, a private heap) wastes RAM when thousands of processes each hold a copy of the same data.
Communication between processes is slow and awkward: every message crosses the kernel and usually copies data, and shared memory requires its own synchronization and is easy to get wrong. Serialization to move data adds more cost, which is why microservices on one machine pay a high price for what would be function calls.
Isolation is not perfect. Processes share a kernel with a large attack surface, shared CPU caches and memory buses. Side channels such as Spectre and Meltdown cost a few percent to tens of percent in performance to mitigate. Resource limits are incomplete: memory pressure from one process can slow others through the page cache, and the OOM killer picks victims that may be innocent.
practice: Know the process model of every component you run. How many processes does it start, which ones are workers, what happens when one dies, who restarts it (systemd, Kubernetes, a supervisor)? Set limits deliberately: ulimit -n for open files (the common default of 1,024 is too low for a busy server), memory limits in cgroups, and process count limits.
Use top, ps, pidstat and /proc/<pid>/status to see state, memory (resident versus virtual), context switches (voluntary ones mean waiting on I/O; involuntary ones mean CPU competition) and open files. Look at the count of runnable processes against cores (the load average) and at CPU steal in virtual machines. Use strace to see what system calls a hung process is making, and perf for where CPU time goes.
In containers, run a small init (tini, or the container runtime's --init) as pid 1 so that signals are forwarded and zombies are reaped, and handle SIGTERM for clean shutdown, because Kubernetes sends SIGTERM and after the grace period (30 seconds by default) SIGKILL. Set memory limits and requests honestly; a limit lower than the real peak means the OOM killer will end the process.
For services that fork (Redis, pre-fork servers), keep memory headroom for copy-on-write, disable transparent huge pages where the database vendor advises it (huge pages make copy-on-write copy 2 MB at a time), and avoid forking from a big multi-threaded process; use posix_spawn or a small helper to start other programs. Prefer a few well-sized worker processes (about one per core for CPU-bound work) over many.
quiz: What does fork() copy, and what does it share? || It copies the page tables, the file descriptor table and the process state, but shares the physical memory pages copy-on-write. Pages are duplicated only when one side writes.
Why does a shell call fork and exec as two separate steps? || Between them the child can change its own file descriptors (redirect output, connect a pipe, change directory) before the new program starts. That makes pipelines and redirection simple and keeps exec itself small.
What is a zombie process and how is it removed? || It is a process that has exited but whose parent has not yet called wait() to read its exit status, so its small kernel record remains. It disappears when the parent waits, or when the parent exits and pid 1 adopts and reaps it.
A Redis instance has 10 GB in memory and forks for a snapshot. About how large are the page tables copied, and how much extra memory is used if 20% of pages change during the snapshot? || 10 GB / 4 KB ≈ 2.6 million pages × 8 bytes ≈ 20 MB of page-table entries. The 20% of changed pages are copied, so about 2 GB of extra memory.
When would you choose processes over threads for a server? || When you want fault isolation and clear security boundaries, and the units of work share little state: for example one process per client connection or per browser site. You pay in memory and communication cost.
interview: Explain what happens, step by step, when you type ls | wc -l in a shell. || The shell creates a pipe, forks twice, and in each child uses dup2 to connect standard output or input to the pipe ends, closes extra descriptors and calls exec for ls and wc. The kernel loads each program into a fresh address space, the children run concurrently, ls writes into the pipe buffer, wc reads it, and the shell waits for both and collects their exit statuses.
Why can fork be a problem in a large multi-threaded program, and what are the alternatives? || fork copies page tables for the whole heap, costing time and memory, and only the calling thread exists in the child, so locks held by other threads stay locked and can deadlock the child. Use posix_spawn, vfork followed by exec, or a small helper process, and restrict the child to async-signal-safe calls before exec.
What exactly does a context switch cost, and how would you tell that a server suffers from too many of them? || Direct cost is saving and restoring registers and switching page tables, a few microseconds; the larger cost is cold caches and TLB afterwards. Symptoms are a high rate of involuntary context switches (pidstat -w, vmstat cs), high system CPU time and a run queue much longer than the core count.
What is the difference between a container and a virtual machine in terms of processes and isolation? || A container is a set of ordinary processes in separate namespaces under cgroup limits, all sharing the host kernel, so it starts in milliseconds but depends on the kernel for isolation. A VM runs its own kernel on virtualized hardware, with stronger isolation and more overhead.
A service is killed with exit code 137 in Kubernetes. What happened and what do you check? || 137 is 128 plus signal 9 (SIGKILL), commonly from the OOM killer when the container exceeded its memory limit, or from a liveness failure or grace-period timeout. Check the container's memory working set versus its limit, the OOMKilled reason in the pod status, and the memory growth of the process, including copy-on-write after fork.

value: A thread is one path of execution inside a process. All threads of a process share the same memory (heap, global variables, code) and the same open files, but each thread has its own stack, its own CPU registers and its own place in the program. The kernel schedules threads, not whole processes, onto CPU cores. So a process with eight threads can use eight cores at once, and a server thread that waits for the disk does not stop the other threads from working.
Threads exist because two needs pull in different directions. Programs need parallelism, to use many cores, and concurrency, to keep working while some task waits for the network or disk. Separate processes can do this, but they do not share memory, so cooperating through them is slow and clumsy. Threads give cooperation by shared memory: one thread can build a data structure and another can read it at once, with no copy. This is why web servers, databases, JVM and Spark executors, and browsers are built from many threads.
The price is that shared memory makes every program a possible race. If two threads change the same variable without coordination, the result depends on timing, and bugs appear once in a million runs. The layers below supply the tools. CPU scheduling decides which threads run on which cores and when they sleep. Locks and atomics give mutual exclusion and indivisible updates, so a group of operations on shared data appears to happen at once. Condition variables and monitors let one thread wait until another has changed the state it needs, which is how producers and consumers hand work to each other without spinning. The layers above build on threads: language runtimes map their own threads or virtual threads onto operating-system threads, event loops try to avoid threads, and work stealing balances load over one worker thread per core.
terms: Thread — a schedulable flow of control with its own stack and registers, sharing the memory of its process.
Stack — the per-thread memory for function calls and local variables; typically 1 to 8 MB of reserved address space per thread.
Data race — two threads access the same memory, at least one writes, and nothing orders them; the program's behavior is then undefined or unpredictable.
Mutex (lock) — an object that only one thread can hold at a time; others wait until it is released.
Atomic operation — a read-modify-write (such as compare-and-swap or fetch-and-add) that the hardware performs as one indivisible step.
Condition variable — a queue where a thread sleeps until another thread signals that a condition may now be true; it is always used together with a mutex.
Thread pool — a fixed set of worker threads that take tasks from a queue, to avoid creating a thread per task.
Memory model — the rules that say when a write by one thread becomes visible to another, given compiler and CPU reordering.
Virtual thread (green thread, goroutine) — a thread managed by a language runtime, not the kernel, many of which share a few kernel threads.
history: Time-sharing systems of the 1960s had processes only, and in the 1980s researchers added "lightweight processes" to share an address space: the Mach operating system had threads, and SunOS got lightweight processes in 1990. The POSIX standard for threads (pthreads, IEEE 1003.1c, 1995) gave Unix programs a common interface, Windows NT had kernel threads from 1993, and Java (1995) put threads into a mainstream language. Linux first had LinuxThreads (Xavier Leroy, 1996), built on the clone system call, with known flaws. In 2003 the Native POSIX Thread Library (NPTL), by Ulrich Drepper and Ingo Molnar, together with the futex mechanism (Franke and Russell, 2002), made thread creation and locking fast enough for servers with tens of thousands of threads.
Two arguments shaped the next decades. The first is hardware: around 2005, single-core speed stopped rising, and Herb Sutter's essay "The Free Lunch Is Over" told programmers that performance would now come only from concurrency. The second is difficulty. John Ousterhout's 1996 talk "Why Threads Are a Bad Idea (for most purposes)" argued that threads with locks are too hard for most programmers, and that event-driven code is simpler. Edward Lee's 2006 essay "The Problem with Threads" argued that shared-memory threads are unpredictable by nature. The C10K problem (Dan Kegel, 1999) led to epoll-based event loops in nginx and Node.js, which serve tens of thousands of connections with one thread.
Meanwhile languages made rules for memory. The Java Memory Model (JSR-133, 2004) and the C++11 memory model (2011) defined when a write is visible and what a data race means. Newer designs reduce the pain: Go (2009) made goroutines cheap and encouraged channels, Rust (1.0 in 2015) uses ownership and the Send and Sync traits to reject data races at compile time, Java 21 (2023) shipped virtual threads (JEP 444) and Java 24 (2025) removed most of their pinning problems around synchronized (JEP 491). Python's free-threaded build, which removes the global interpreter lock, was experimental in 3.13 and officially supported but optional in 3.14 (PEP 779).
how: In Linux, a thread is a task that shares things with its creator. The clone system call takes flags: CLONE_VM shares the address space, CLONE_FILES shares the file descriptors, CLONE_SIGHAND shares signal handlers, and CLONE_THREAD puts the new task in the same thread group. A process is simply a task created without these flags. Each thread has its own kernel stack, its own saved registers and its own scheduling entity. This is where scheduling contributes: the kernel's run queues hold threads, so each thread competes for CPU time individually, and a process with 8 runnable threads can occupy 8 cores. A thread-to-thread context switch inside one process is cheaper than a process switch because the page table does not change and the TLB need not be flushed, typically 1 to 2 microseconds.
The memory layout is simple: one address space, many stacks. Each thread's stack is a reserved region (8 MB by default for pthreads on Linux with glibc; 1 MB by default for Java threads on 64-bit Linux). Only the touched pages become real memory, so 10,000 threads reserve about 10 GB of address space but may use only a few hundred MB, plus a kernel stack (16 KB) each. Thread-local storage gives each thread its own copies of selected variables. Everything else (heap, globals) is shared, and that is the source of both the power and the danger.
Shared memory needs rules. A data race is a pair of unordered accesses to one location with at least one write. Modern compilers and CPUs reorder and cache memory operations, so without synchronization one thread may never see another's write, or see writes in a different order. A memory model defines when it is safe: a write before releasing a lock is visible to any thread that later acquires the same lock (a happens-before relation). Locks and atomics supply these guarantees. A mutex gives mutual exclusion: the code between lock and unlock runs in one thread at a time. An atomic compare-and-swap lets a thread update a single word without a lock: "set X to new if it is still old." In Linux the mutex is built on the futex: lock and unlock are an atomic operation in user space when uncontended (about 20 nanoseconds), and only a contended lock calls the kernel to sleep and wake (microseconds).
Condition variables solve waiting. A consumer thread that needs an item must wait until a producer adds one. Spinning wastes a core. Instead the consumer holds the mutex, checks a condition in a loop (while queue is empty: wait(cv, mutex)), and wait atomically releases the mutex and puts the thread to sleep. The producer takes the mutex, adds the item, and calls signal. The sleeping thread wakes, re-acquires the mutex and re-checks the condition. The loop is needed because wakeups can be spurious, and because another consumer may have taken the item first. A monitor bundles the data, the mutex and the condition variables into one unit, as Java's synchronized, wait and notify do.
Threads are managed in pools because creating one costs on the order of 10 to 100 microseconds and its stack memory. A thread pool keeps N workers and a queue of tasks. Sizing follows a simple model: for CPU-bound work, one thread per core; for work that waits, the number is about cores × (1 + wait time / compute time). With 8 cores and tasks that wait 9 ms for every 1 ms of compute, about 80 threads keep all cores busy. More threads only add switching and memory.
Because kernel threads are heavy, runtimes build lighter ones on top. Go multiplexes goroutines (starting stacks of a few KB, growing on demand) over a small set of kernel threads with a scheduler that steals work between per-core queues. Java virtual threads are scheduled by the JVM onto a few carrier threads; when a virtual thread blocks on I/O, it is unmounted and the carrier runs another. Async/await in Rust, Python and JavaScript compile tasks into state machines that an event loop runs. All of them keep the same discipline: when your code waits, give the core to someone else, and when your code shares memory, synchronize.
Two performance effects matter. Amdahl's law: if a fraction \( s \) of the work is serial, speedup on \( N \) cores is at most \( 1 / (s + (1 - s)/N) \); with s = 10 percent and 8 cores, it is 1 / (0.1 + 0.9 / 8) ≈ 4.7, and it can never exceed 10. False sharing: two threads writing to different variables that sit on the same 64-byte cache line force the line to bounce between cores, which can make code several times slower. Padding hot variables onto separate cache lines fixes it.

example: Start with the lost update. Two threads each run counter++ one million times on a shared integer. At machine level, counter++ is three steps: load the value into a register, add 1, store it back. If thread A loads 5, thread B loads 5, A stores 6, and B stores 6, two increments produced one. The final value is somewhere between 1,000,000 and 2,000,000, usually far below 2,000,000, and different on each run. Fix 1: protect with a mutex, lock before and unlock after each increment; correct, and about 20 ns per uncontended operation, but under heavy contention each lock operation can cost hundreds of nanoseconds, since threads sleep and wake. Fix 2: an atomic fetch-and-add, a single hardware instruction, about 5 to 20 ns uncontended, correct without a lock. Fix 3: each thread counts in its own local variable (padded to its own cache line) and the totals are added at the end; this has no sharing and is the fastest. The lesson is to share less.
Now a bounded queue between one producer and one consumer, capacity 100. The producer takes the mutex, and while the queue has 100 items it calls wait(notFull, mutex), which releases the mutex and sleeps. The consumer takes an item and signals notFull. The producer wakes, re-takes the mutex, and re-checks the condition in the loop: if another producer took the free slot first, it waits again. With the loop, correctness does not depend on who wakes first. Throughput is limited by the mutex, around 10 to 50 million queue operations per second for a single queue on modern hardware without contention, far less with many threads on one lock.
Finally, the pool size. A service has 8 cores and each request spends 1 ms of CPU and 9 ms waiting on a database. One thread per core would use 8 / 10 ms = 800 requests per second at best, with each core idle 90 percent of the time. With 80 threads, the cores are kept busy, and the capacity is about 8 cores / 1 ms = 8,000 requests per second, 10 times more, provided the database can serve 8,000 queries per second. Each extra thread costs memory (1 MB reserved stack) and scheduling time, so 80 is cheap but 8,000 threads would waste time. If the code were async or used virtual threads, the same throughput needs far fewer kernel threads.
intuition: Several cooks in one kitchen: much faster together, as long as they agree who uses the knife and who waits for the oven.
The thread is natural because a program often has more than one thing it could do, and the machine has more than one place to do it. Sharing memory makes cooperation cheap, like cooks sharing one counter and one pantry, but it also means any two cooks can reach for the same thing at the same moment. Locks, atomics and condition variables are the kitchen rules: one cook at a time at the knife, a bell to call when the oven is ready, and a habit of looking again after you are called.
mistakes: People often think more threads always mean more speed. In fact the speedup is bounded by the number of cores and the serial part of the work (Amdahl's law). Beyond that, extra threads add context switches, lock contention and memory use, and can make the program slower.
People often think a data race is harmless if it is "only a counter". In fact the language models treat a data race as undefined or unpredictable behavior: values can be torn, stale or reordered by the compiler and CPU. Use atomics or locks even for flags and counters.
People often think volatile makes a variable safe for threads. In fact in Java, volatile gives visibility and ordering for one variable but does not make count++ atomic, and in C and C++ volatile gives no thread safety at all; use atomic types.
People often think condition variables can be used with an if instead of a while. In fact a thread can wake without its condition being true (spurious wakeups, or another thread took the item), so the condition must be rechecked in a loop.
People often think virtual threads or goroutines make shared-state bugs disappear. In fact they make threads cheap, not safe. The same races and deadlocks occur, and a blocking call that pins a carrier thread (for example some native calls) can still stall many virtual threads.
tradeoffs: Choose kernel threads with a pool when work is CPU-bound or uses blocking libraries, and size the pool near the core count (CPU work) or cores × (1 + wait/compute) (blocking work). You give up scalability past a few thousand threads because of stack memory and scheduling cost. Choose virtual threads or goroutines when you have tens of thousands of concurrent blocking tasks (one per connection) and want simple straight-line code; you give up some control over scheduling and must avoid pinning and long CPU loops on carriers.
Choose an event loop (Node.js, Netty, async Rust) when you handle many mostly-idle connections and the work per event is small; one thread per core avoids locks on shared state. You give up simple stack traces and straightforward code, and any blocking call or long computation stalls every task on that loop. Choose separate processes when isolation or the lack of a safe shared-memory model matters, such as Python before free-threading, or untrusted plugins.
Choose a mutex when the critical section is more than a few instructions or may block; choose atomics or lock-free structures for single counters, flags and simple queues, accepting that lock-free code is hard to get right. Choose a coarse lock first and split it only after measuring contention, because fine-grained locking multiplies the chances of deadlock. Choose message passing (channels, queues, actors) over shared state when ownership can be handed off, giving up some copying cost for fewer races.
friction: Concurrency bugs depend on timing, so they pass tests and fail in production. Data races, deadlocks (two locks acquired in opposite orders), lost wakeups, priority inversion and visibility problems are hard to reproduce, and debugging changes the timing. Tools help: ThreadSanitizer, Go's race detector, Java's JFR and lock profiling, and Rust's compile-time checks. But they find only races that actually occur in the run.
Locks do not compose. Two correct, thread-safe classes combined may deadlock, and holding a lock while calling unknown code (a callback) is a common source of deadlock. Contention limits scaling: a single hot lock turns a 64-core machine into a one-core machine. Cache effects such as false sharing and cache-line bouncing cost more than the lock itself.
Threads cost memory and scheduling. Each kernel thread has a stack and kernel structures, so 100,000 threads is hard; the context-switch rate rises with the thread count, and a run queue much longer than the core count hurts latency. Language runtimes add their own hazards: the Python GIL until 3.13 serialized CPU-bound threads, JVM garbage collection pauses all threads at safepoints, and virtual-thread pinning can quietly reduce a program to a few carriers.
practice: Do not create threads by hand; use an executor or pool with a bounded queue, so overload shows up as rejected or delayed work and not as out-of-memory. Name your threads, because thread dumps (jstack, py-spy, gdb) and profilers show names. Size pools by workload: CPU-bound pools at about the core count, blocking pools by measured wait time, and separate pools for slow external calls so they cannot starve fast ones.
Share as little as possible. Prefer immutable objects, thread confinement, and concurrent data structures from the standard library (ConcurrentHashMap, queues, LongAdder for counters). When you must lock, keep critical sections short, never call unknown code or do I/O while holding a lock, acquire multiple locks in one global order, and always use try/finally (or RAII) to unlock. Always wait on a condition in a while loop.
Test and observe. Run tests under ThreadSanitizer or the race detector; stress with more threads than cores to widen the interleavings; use timeouts on all blocking calls so a deadlock surfaces as an error. In production, watch thread counts, queue depths, lock wait time, context switches per second and CPU run-queue length, and take thread dumps when latency spikes.
On the JVM, consider virtual threads for I/O-heavy request handling on Java 21 and later, and keep CPU-bound parallel work on a bounded pool. In Python, use processes or native extensions for CPU-bound work, threads or asyncio for I/O, and evaluate the free-threaded build only after checking that your dependencies support it. In Spark, remember that an executor runs many task threads in one JVM sharing memory, so non-thread-safe static objects and shared mutable state in your code are a common source of rare bugs.
quiz: What do threads in one process share, and what does each have of its own? || They share the address space (heap, globals, code) and open files. Each has its own stack, registers, program counter and thread-local storage.
Why must a condition variable wait be inside a while loop? || A thread can wake spuriously, or another thread can consume the state change first. Rechecking the condition in a loop makes the code correct whoever wakes first.
Why is a thread-to-thread context switch within a process cheaper than between processes? || The address space is the same, so the page table is not switched and the TLB need not be flushed. Only registers and the stack pointer change, so there are fewer cache and TLB misses afterwards.
Tasks spend 1 ms on CPU and 9 ms waiting on I/O, on an 8-core machine. How many threads keep the cores busy, and what throughput results? || About 8 × (1 + 9/1) = 80 threads. Throughput is about 8 cores / 1 ms = 8,000 requests per second, if the backend can keep up.
When would you prefer an event loop or virtual threads over a pool of kernel threads? || When you have many thousands of mostly-waiting connections: thread stacks and context switches become costly, while event loops and virtual threads multiplex them over a few kernel threads cheaply.
interview: Two threads increment a shared counter and the total is wrong. Explain why, and give three fixes with their costs. || counter++ is load, add, store, so updates interleave and one is lost. Fixes: a mutex (correct, tens of ns uncontended, slow when contended), an atomic fetch-and-add (single instruction, a few to tens of ns, still bounces a cache line), and per-thread counters merged at the end (no sharing, fastest, needs a merge step).
How does a Linux futex-based mutex work, and why is it fast in the common case? || The lock word is changed with an atomic compare-and-swap in user space; if it succeeds there is no system call. Only if the lock is held does the thread call futex wait to sleep, and unlock calls futex wake only if waiters exist. So the uncontended path costs about as much as one atomic operation.
What is false sharing and how do you find and fix it? || Two threads write different variables that share a 64-byte cache line, so the line bounces between cores and throughput collapses though there is no logical sharing. Detect it with perf c2c or by seeing poor scaling of per-thread counters. Fix it by padding or aligning hot fields to separate cache lines.
Your Java service creates a thread per request and falls over at 20,000 concurrent requests. What do you change? || Move to a bounded executor or virtual threads (Java 21+) so the blocking tasks do not need a kernel thread each, bound concurrency with a semaphore or queue, and keep CPU-heavy work on a separate pool. Check for pinning from synchronized blocks around I/O on Java versions before 24.
Why did Ousterhout argue threads are a bad idea, and what is still true today? || Threads with locks are hard to reason about, easy to deadlock, and not needed for most I/O-driven programs, which event loops handle with simpler code. It remains true that shared mutable state is error-prone, which is why modern practice favors immutability, message passing, structured concurrency and compile-time checks.
