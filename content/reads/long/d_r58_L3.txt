value: A parser turns a flat list of tokens into a tree that shows how the pieces belong together. The text `1 + 2 * 3` is five tokens in a row. The program needs to know that `2 * 3` is grouped first, so the tree has `+` at the top, `1` on its left, and a `*` node on its right. A parsing algorithm is a systematic procedure that finds this tree for any input that follows the grammar, in time proportional to the input length, and that reports a precise error when the input does not follow it.
Every language tool needs one: compilers, interpreters, SQL engines, JSON and YAML readers, configuration systems, editors that highlight code, linters and formatters. The two big families are different in how they think. A top-down parser (recursive descent, LL, Pratt) starts from the goal "I expect a statement" and predicts which rule to use by looking at the next token. A bottom-up parser (LR and its relatives LALR and SLR) reads tokens, pushes them on a stack, and when the top of the stack matches the right side of a rule, it replaces those symbols with the rule's left side.
This concept gives the layers above their front doors. The interpreter chapter uses recursive descent and Pratt parsing for its own front end. The SQL engines in PostgreSQL and MySQL use bottom-up parsers generated by Bison. The layers below make the algorithms precise: formal language theory (L4) says which grammars can be parsed deterministically and how fast, the lexer (L3) supplies the tokens, finite automata (L3) are the engine inside an LR parser, and trees (L3) are what comes out.
terms: Token — one unit produced by the lexer, such as a number, an identifier, or the symbol `+`; the parser never looks at raw characters.
Grammar — a set of rules such as `expr -> expr + term` that define which token sequences are valid.
Parse tree (syntax tree) — the tree that shows which rules were used to derive the input; internal nodes are rules, leaves are tokens.
Lookahead — how many upcoming tokens the parser may inspect before it decides; LL(1) and LR(1) use one.
Recursive descent — a top-down parser written as one function per grammar rule, where functions call each other as the rules do.
Shift and reduce — the two main moves of a bottom-up parser: shift pushes the next token on the stack; reduce replaces the symbols at the top that match a rule's right side with the rule's left side.
Conflict — a state where a table-driven parser has two legal moves (shift/reduce or reduce/reduce) and the grammar does not say which; it means the grammar is ambiguous or needs more lookahead.
Binding power — a number attached to an operator in a Pratt parser; higher means the operator holds its operands more tightly.
history: The first parsers were found by hand for each language. In the 1950s and early 1960s, compiler writers had trouble with operator precedence in languages such as FORTRAN and ALGOL 60. The ALGOL 60 report (1960) described syntax with a grammar notation (Backus–Naur form), which made it natural to ask for an algorithm that works for any grammar of a class. Floyd's operator precedence parsing (1963) was an early bottom-up method.
Donald Knuth's 1965 paper "On the translation of languages from left to right" defined LR(k) parsing and proved that LR(k) grammars are exactly the ones a deterministic pushdown automaton can parse. Canonical LR tables were too large for the memory of the time, so Frank DeRemer's 1969 MIT thesis introduced SLR and LALR, which merge states and give tables that are close to the size of the grammar. LL(k) came from Lewis and Stearns (1968) and from Rosenkrantz and Stearns (1970). Earley (1970) gave a method for any context-free grammar that runs in cubic time in the worst case and quadratic or linear time for easy grammars.
Stephen Johnson wrote yacc at Bell Labs around 1975; it generated LALR(1) parsers from a grammar file, and its descendant Bison is still used (PostgreSQL's `gram.y` is a Bison grammar). Vaughan Pratt published "Top Down Operator Precedence" in 1973, a short method for expressions that was almost forgotten until it was rediscovered by Douglas Crockford (for JSLint, 2007) and by many writers of hand-made parsers since. Terence Parr's ANTLR moved from LL(k) to LL(*) and then to the adaptive ALL(*) algorithm (2014). Bryan Ford's parsing expression grammars and packrat parsing (2002–2004) offered a different, ordered-choice model. Python's CPython switched to a PEG parser in version 3.9 (PEP 617). Masaru Tomita's GLR (1985) explores all possible parses in parallel; it is used for ambiguous languages such as C++ in some tools and in tree-sitter's design for editors.
how: Both families solve the same problem: given a grammar and a token stream, find a derivation. They differ in the order in which they build the tree.
Top-down: recursive descent. Write one function per nonterminal. The function for `expr` looks at the next token, decides which rule applies, and calls the functions for the symbols of that rule, consuming tokens as it matches terminals. For the grammar `stmt -> "if" expr "then" stmt | "while" expr "do" stmt | ID "=" expr`, the function `parse_stmt` peeks at one token: `if`, `while`, or an identifier tells it which branch to take. This is an LL(1) decision: Left-to-right scan, Leftmost derivation, one token of lookahead. The call stack of the program is the parse stack, so the tree builds itself as function calls return. Error messages are easy to customize because the code knows exactly what it was expecting.
For a grammar to work with one-token prediction, the choices must be separable. The standard test uses two sets. FIRST(A) is the set of tokens that can begin a string derived from A. FOLLOW(A) is the set of tokens that can come right after A. A grammar is LL(1) when, for each nonterminal with several rules, the FIRST sets of the rules do not overlap (and, for rules that can derive the empty string, they do not overlap with FOLLOW). Two things break this. Left recursion, such as `expr -> expr + term`, makes `parse_expr` call itself with no token consumed, so it loops forever; the fix is to rewrite it as a loop: `expr -> term ("+" term)*`. Common prefixes, such as two rules that both start with `ID`, need left factoring. ANTLR's LL(*) and ALL(*) relax these limits by looking ahead as far as needed with a small automaton, and ALL(*) also accepts direct left recursion by rewriting it internally.
Top-down: Pratt parsing. Expressions with many operator levels (C has about 15) are awkward to write as one rule per level. Pratt's method uses one function and a table. Every operator gets a left binding power and a right binding power. The function `parse_expr(min_bp)` first parses a prefix item (a number, a name, a unary minus, or a parenthesized expression), then loops: look at the next operator; if its left binding power is lower than `min_bp`, stop; otherwise consume it and parse the right operand with the operator's right binding power. Left-associative operators have a right binding power slightly higher than the left; right-associative ones (like `^` or `=`) have it slightly lower. Adding an operator means adding a table row, not a new function.
Bottom-up: LR. An LR parser keeps a stack of states and two tables. The ACTION table says, for the current state and the next token, whether to shift (push the token and go to a new state), reduce by rule number r (pop as many entries as the right side has symbols, then push the left side), accept, or report an error. The GOTO table says which state to enter after a reduce. The key insight is that the set of possible "viable prefixes" (the stack contents that can still lead to a valid parse) forms a regular language. That is where finite automata add their value: a deterministic finite automaton over grammar symbols, whose states are sets of "items" such as `expr -> expr + . term` (the dot marks how much of the rule has been seen), tells the parser in which state it is. The parser is a finite automaton plus a stack, which is exactly a pushdown automaton. Because it decides at the end of a rule, after it has seen the whole right side, LR parsers handle left recursion naturally and accept a larger set of grammars than LL(k).
The family has several members, all using the same machine but different table builders. LR(0) uses no lookahead, SLR(1) uses FOLLOW sets to decide reductions, LALR(1) merges canonical LR(1) states that have the same core and so keeps tables small, and canonical LR(1) keeps full lookahead and has the largest tables. Bison and yacc build LALR(1). When a table cell would have two entries, Bison reports a conflict. The famous example is the dangling else: for `if a then if b then x else y`, the parser can reduce the inner `if` before the `else` or shift the `else`. Parser generators resolve a shift/reduce conflict in favor of shift by default, which matches the usual meaning (the `else` belongs to the nearest `if`), and precedence declarations (`%left '+'`, `%left '*'`) resolve expression conflicts.
The trees layer matters at each reduce: a reduce step creates a tree node whose children are the popped entries. The tree is built from the leaves upward in LR and from the root downward in LL. The lexer layer matters because both algorithms read from a token stream; most parsers need one token of lookahead, and a few languages need the parser to feed information back to the lexer (C's typedef names, for example).

example: Take the expression `1 - 2 - 3 * 4` and parse it with a small Pratt parser. Binding powers: `-` has (left 10, right 11); `*` has (left 20, right 21). Higher numbers bind tighter, and the right number being larger than the left makes the operator left-associative.
```python
def parse_expr(toks, min_bp=0):
    lhs = next(toks)                 # a number (prefix item)
    while True:
        op = peek(toks)
        if op is None: break
        lbp, rbp = BP[op]            # {'-': (10, 11), '*': (20, 21)}
        if lbp < min_bp: break
        next(toks)                   # consume the operator
        rhs = parse_expr(toks, rbp)
        lhs = (op, lhs, rhs)
    return lhs
```
Step 1: call `parse_expr(min_bp=0)`. Read `1` as lhs. Peek `-`: lbp 10 is not below 0, so consume it and call `parse_expr(11)` for the right side.
Step 2: inside, lhs = `2`. Peek `-`: lbp 10 is below min_bp 11, so stop and return `2`. This is what makes subtraction left-associative: the inner call refuses to take the second `-`. Back in the outer call, lhs = `(-, 1, 2)`.
Step 3: the outer loop peeks the second `-`: lbp 10 is not below 0, so consume it and call `parse_expr(11)`. Inside, lhs = `3`. Peek `*`: lbp 20 is not below 11, so consume it and call `parse_expr(21)`, which reads `4`, sees the end, and returns `4`. The call builds `(*, 3, 4)` and returns it.
Step 4: the outer call builds `(-, (-, 1, 2), (*, 3, 4))`. The tree is `((1 - 2) - (3 * 4))`, which evaluates to -13. Each token was read once, and the work was linear in the input length.
Now the same input in an LR parser built from the grammar in the diagram. The parser shifts `1`, reduces it to `E`, shifts `-`, shifts `2`, and then looks at the next token `-`. In the state holding `E - T .`, the table says: on `-` or `$`, reduce `E -> E - T`; on `*`, shift. That table entry is how precedence lives in the grammar structure itself: `T` is lower in the grammar, so `*` groups before `-`. The parser would shift `*` when it sees it after `3`, and only reduce the `-` rule at the end. The result is the same tree. The table for this small grammar has only a dozen or so states; the tables for the full SQL grammars in database systems have thousands.
intuition: A top-down parser is a reader who knows what kind of sentence to expect and checks that the words fit; a bottom-up parser is a reader who collects words until a phrase is complete, and then names it.
Both approaches work because the grammar is a promise that the text has structure. The top-down reader uses the next word to guess the structure early, so it needs a grammar where the first word is enough to choose. The bottom-up reader delays the choice until it has seen the whole phrase, so it can accept grammars where the first word is not enough. This is why LR covers more languages than LL: it makes its decision later, with more information. The price of waiting is that the machinery (tables, states, conflicts) is harder for a person to hold in the head, and that is why people often write the easier top-down code by hand.
mistakes: People often think a parser checks that the program is correct. In fact the parser checks only structure (the shape of the code). Whether a variable exists, whether types match and whether a function is called with the right number of arguments are checked later, in semantic analysis. Languages such as C++ blur this line, because the meaning of `a * b;` depends on whether `a` is a type, so the parser needs symbol information.
People often think LR parsers are more powerful in every way, so all serious compilers must use them. In fact the common big compilers (GCC, Clang, Go, rustc) use hand-written recursive descent. They choose it for error messages, for easy special cases and context-dependent rules, for speed, and for easy debugging with ordinary tools. LR is excellent when the grammar is stable and you want a proof that it is unambiguous.
People often think recursive descent cannot handle left recursion at all, or operator precedence cleanly. In fact the standard fix is to turn recursion into a loop (`term ("+" term)*`), and Pratt parsing handles any number of precedence levels with a table of binding powers. The left-recursion problem is only for the naive translation of the grammar.
People often think an ambiguous grammar is just an inconvenience. In fact it means one input has two different trees, and so two meanings. A table-driven generator reports it as a conflict. Do not silence conflicts by trusting the default choice without checking: the default may hide a real design mistake, and a grammar with hundreds of silenced conflicts is very hard to maintain.
friction: Grammar design is the hard part, not the algorithm. Real languages are not neatly context-free. C needs to know if a name is a typedef; C++ templates make `a < b > c` ambiguous without symbol information; Python and Haskell use indentation, which the lexer must turn into indent and dedent tokens; many languages have rules like "a newline ends a statement unless the line is clearly unfinished". Each of these bends the pure model and pushes work into the lexer or into hand-written hacks.
Error handling is a large share of the effort. A table-driven parser knows only that no action exists for the current state and token. Good messages ("expected `)` before `;`") and good recovery (skipping to the next safe token and continuing, so that one mistake does not produce a hundred follow-up errors) need design on top of the algorithm. Tools for IDEs also need incremental parsing, where an edit re-parses only the changed part of the file, and they need to work on broken, half-typed code. Tree-sitter exists for this reason: it is a GLR-based incremental parser that always returns a tree, with error nodes where the code is broken.
practice: For a new language or a configuration format, start with a hand-written recursive-descent parser with a Pratt loop for expressions. It is about 300 to 1,000 lines, easy to test and gives you full control of errors. Write the grammar down first in a notation such as EBNF so you keep it consistent. Limit recursion depth on outside input with a counter (100 to 1,000), because ten thousand open brackets can overflow the call stack. Fuzz the parser with random and mutated inputs, because parsers are a main source of crashes and security bugs when they receive untrusted text.
Use a generator (ANTLR, Bison, Lemon, tree-sitter, or a parser-combinator library) when the grammar is large, changes often, or must be shared by several tools. Read the conflict report every time and keep it at zero, or at a small number that you have explained in comments. In Bison, run with `-Wcounterexamples` (available in recent versions) to see an example input that causes each conflict.
tradeoffs: Choose hand-written recursive descent (with Pratt for expressions) when you control the language, care about error messages, and expect context-dependent rules. You give up a machine-checked guarantee that the grammar is unambiguous, and the grammar lives in code rather than in one file.
Choose an LALR or LR generator (Bison, Lemon) when the grammar is large and stable, such as SQL, and you want the generator to prove there are no hidden ambiguities. You give up flexible error recovery and accept occasional contortions of the grammar to avoid conflicts. Choose ANTLR (ALL(*)) when you want a generator but also want to write natural grammars with left recursion and long lookahead; you pay with a runtime library and slower worst-case behavior than a tight LR table.
Choose a PEG or parser combinators when you want a quick grammar written close to the code and the language has little ambiguity. You give up the "unambiguous by construction" property: ordered choice silently picks the first match, and left recursion needs special support. Choose tree-sitter or another incremental, error-tolerant parser when the consumer is an editor: you accept a grammar written for approximate structure rather than for a compiler's exact acceptance.
quiz: What is the difference between a shift and a reduce in an LR parser? || Shift pushes the next input token onto the stack and moves to a new state. Reduce pops the symbols that match the right side of a rule and pushes the rule's left-side symbol, building one tree node. Together they build the tree from the leaves upward.
Why does a naive recursive-descent function for `expr -> expr + term` loop forever, and how do you fix it? || The function calls itself first, before consuming any token, so it recurses without progress. Rewrite the rule as `expr -> term ("+" term)*` and implement the repetition with a loop, building the left-associative tree inside the loop.
Why can LR(1) parse some grammars that LL(1) cannot? || An LR parser delays its decision until the whole right side of a rule has been seen, so it uses more context. An LL(1) parser must pick the rule from only the next token, before it has read any of the phrase. Every LL(k) grammar is also LR(k), but not the reverse.
In a Pratt parser, `-` has binding powers (10, 11) and `^` has (15, 14). How are `a - b - c` and `a ^ b ^ c` grouped? || `a - b - c` groups as `(a - b) - c` because the right power 11 is above the left power 10, so the inner call refuses the second `-`. `a ^ b ^ c` groups as `a ^ (b ^ c)` because the right power 14 is below the left power 15, so the inner call takes the second `^`.
A team must pick a parser approach for a new SQL-like query language that will change every month and needs good error messages for users. What would you choose, and why? || Hand-written recursive descent with a Pratt expression parser. Frequent changes are easy to make in code, error messages and recovery are fully controlled, and no generator conflicts have to be resolved. If the language later stabilizes and must be shared by several tools, a grammar file with a generator becomes attractive.
interview: Explain how an LR parser decides between shift and reduce, and what a conflict means. || The parser is in a state, which is a set of grammar items that could be in progress, and it looks at the next token. The ACTION table gives shift or reduce for that pair. A conflict means two actions are possible: the grammar is ambiguous (for example the dangling else) or needs more lookahead than the method uses. You fix it by rewriting the grammar, by precedence declarations, or by using a more powerful method.
Why do most production compilers use hand-written recursive descent rather than a generated LR parser? || Better and more specific error messages and recovery, easy handling of context-sensitive parts (C typedefs, C++ templates, Go's semicolon rules), better speed through simple code, and no dependency on a generator. They accept the loss of a mechanical proof that the grammar is unambiguous and cover it with tests and a written grammar.
How would you make a recursive-descent parser safe against hostile input? || Bound recursion depth with a counter, bound the input size and token count, avoid backtracking that can take exponential time (or use memoization), keep every loop advancing by at least one token, and fuzz the parser. Return errors instead of panicking, and test with deeply nested, very long and malformed inputs.
How would you parse code in an editor while the user is typing? || Use an error-tolerant, incremental parser such as tree-sitter: re-parse only the edited region and keep error nodes for broken parts, so a tree always exists for highlighting and navigation.

value: Most of the time in numeric and data-processing programs is spent inside loops, and the speed of a loop depends less on how many operations it performs than on the order in which it touches memory. A modern core can do several arithmetic operations per cycle, but a read that goes all the way to main memory costs roughly 80 to 100 nanoseconds, hundreds of cycles. Loop optimization changes the shape of a loop nest (the order of the loops, the size of the pieces, which loops are merged) so that data is reused while it is still in cache, and so that consecutive iterations can run together as the lanes of one SIMD instruction.
The key condition is that the answer must not change. A compiler may reorder iterations only if it can prove that no iteration depends on a result produced by an iteration that would now run later. That proof is called dependence analysis, and it is what separates a safe transformation from a bug. The transformations are classical: interchange, tiling (blocking), fusion, fission, unrolling and vectorization.
For the layers above, this is where performance of compiled numeric code comes from. A blocked matrix multiplication (GEMM) is a triple loop that has been tiled, unrolled and vectorized by hand or by a tool. ML compilers such as XLA, TVM and Triton tile and fuse tensor loops. Vectorized query engines rely on the compiler to turn simple loops over columns into SIMD code. LLVM contains the vectorizer and the unroller used by Clang, Rust and Swift. Below, dataflow analysis supplies the dependence proofs, cache lines explain why the order matters, SIMD supplies the hardware to target, and linear algebra gives the polyhedral model a way to describe loop nests as integer matrices.
terms: Loop nest — loops placed inside other loops, such as the three loops of a matrix multiplication.
Iteration space — the set of all index tuples (i, j, k) that the loop nest visits, seen as points on an integer grid.
Dependence — a pair of iterations where one must run before the other because one writes a memory location that the other reads or writes.
Distance vector — the difference between the index tuples of the two dependent iterations, for example (0, 1) when iteration (i, j) feeds (i, j+1).
Tiling (blocking) — splitting loops into small blocks so that the data used by one block fits in a cache level and is reused before it is evicted.
Vectorization — running several consecutive iterations at once as lanes of one SIMD instruction, for example 8 floats in a 256-bit AVX register.
Unrolling — repeating the loop body several times per pass, to cut loop overhead and expose more independent work.
Loop fusion — merging two loops over the same range into one, so that data produced by the first is consumed while it is still in cache.
history: Loop transformations began with vector supercomputers. The Cray-1 (1976) could run a vector instruction over 64 elements, but only if the compiler found loops it could turn into such instructions. Ken Kennedy, Randy Allen and others at Rice built the PFC system, and the paper "Automatic translation of Fortran programs to vector form" (Allen and Kennedy, 1987) set out the theory of dependence-based loop distribution and vectorization. Utpal Banerjee's dependence tests (1970s and 1980s) gave the arithmetic that decides whether two array references can touch the same element.
In the late 1980s, caches replaced vector registers as the main performance problem. Michael Wolfe described iteration-space tiling (1987–1989). Monica Lam, Edward Rothberg and Michael Wolf (1991) showed that blocked matrix multiplication could lose its benefit because of cache conflicts, and gave guidance for choosing block sizes. Steve Carr, Kathryn McKinley and others studied loop interchange and fusion for memory locality.
The next theoretical step was the polyhedral model. Paul Feautrier (1988–1992) modeled loop nests with affine bounds and subscripts as integer polyhedra, so that a transformation becomes a matrix and a legality check becomes a linear programming question. This led to tools such as PLuTo (Bondhugula et al., PLDI 2008), GCC's Graphite and LLVM's Polly. In 2013, Halide (Ragan-Kelley et al.) took a different route: the programmer writes the algorithm and a separate schedule that says how loops should be tiled, fused and vectorized. This separation of what and how was adopted by TVM (2018) and, in spirit, by Triton and MLIR's affine dialects. Meanwhile, SIMD ISAs grew from MMX (1997) and SSE through AVX2 (2013) and AVX-512 (2016–2017), and ARM added NEON and SVE, making automatic vectorization a central compiler feature. LLVM's loop vectorizer was enabled by default in 2013.
how: Everything starts with the dependence question. Take two statements in a loop that access the same array element. If neither one writes it, order does not matter. If one writes it, then their order does (a true dependence: write then read; an anti dependence: read then write; an output dependence: write then write). For a loop nest, the compiler computes for each pair a distance or direction vector. In `for i: for j: A[i][j] = A[i-1][j+1] + 1`, iteration (i, j) reads what iteration (i-1, j+1) wrote, so the distance vector is (1, -1). Dataflow analysis supplies the facts that make this precise: which pointers can alias, which values are loop-invariant, what the induction variables are. If two arrays may alias and the compiler cannot prove they do not, it must assume a dependence. This is why `restrict` in C, `noalias` in LLVM and Rust's guarantee that two `&mut` do not overlap, are performance features.
Legality rule: a transformation is legal if every dependence still goes from an earlier iteration to a later one after the change. For interchange of two loops, swap the entries of every distance vector; the result must still be lexicographically positive (its first non-zero entry must be positive). (1, -1) swaps to (-1, 1), which is negative, so this nest cannot be interchanged. Vectors like (0, 1) or (1, 0) can.
Locality, step one: interchange. Memory is a line of bytes, and the cache loads 64-byte lines. A row-major array `A[i][j]` stores `A[i][j]` and `A[i][j+1]` next to each other. A loop whose inner index runs along a row uses all 8 doubles of each line it loads. A loop whose inner index runs down a column touches a new line on each iteration and, if the column is longer than the cache can hold, loads the same line again later. Swapping the loops, when legal, turns stride-N access into stride-1 access. Cache lines are the layer below that explains why this matters so much.
Locality, step two: tiling. Interchange fixes a single array, but in matrix multiplication one array has to be walked in a bad order whichever way you choose. Tiling breaks each loop into an outer loop over blocks and an inner loop within a block. With block size T, the program works on a T by T tile of each matrix at a time; the three tiles take 3 x T x T x 8 bytes. If that is below the size of the L1 cache (commonly 32 or 48 KB), then every element in a tile is loaded once and used T times. The number of memory accesses to slower levels drops by about a factor of T. Choosing T is a hardware question: tiles for L1, then larger tiles for L2 and L3, which is the multi-level structure of high-performance GEMM.
Fusion and fission. Two loops that go over the same range and share data (`B[i] = f(A[i])` followed by `C[i] = g(B[i])`) can be fused so that `B[i]` is used while still in a register, and the temporary array disappears. This is the main optimization in ML compilers, where it removes whole round trips to memory. Fission does the reverse when a loop body mixes a part that vectorizes with a part that does not.
Vectorization. If the iterations are independent (or their dependences go only in ways SIMD can respect), the compiler packs W consecutive iterations into one vector instruction, where W is the number of lanes: 4 doubles or 8 floats for AVX2, double that for AVX-512. It handles the leftover iterations with a scalar epilogue, or with masked operations. Three things often block it: possible aliasing, a loop-carried dependence with distance smaller than W, and floating-point reductions. A sum `s += a[i]` in floats is not associative, so splitting it into 8 partial sums changes the rounding. The compiler will not do it unless you permit it with `-ffast-math` or `#pragma omp simd reduction(+:s)`. The compiler also uses a cost model to decide if the vector version is worth it, since short loops, gathers and unaligned or strided accesses can cost more than they save.
Unrolling. Repeating the body 4 or 8 times removes branch and counter overhead and gives the out-of-order core several independent chains to run at once. This matters for the reduction case: a single accumulator makes every addition wait for the previous one (about 4 cycles of latency each); four accumulators let four additions run in flight. The price is bigger code and more register pressure.
Polyhedral compilers do these steps in one framework: write each statement's iteration domain as inequalities, find a schedule (an affine function from iteration to time) that satisfies all dependences, and choose the one that maximizes locality and parallelism with linear programming; then generate the loops from the new schedule. This is where linear algebra pays: a transformation is multiplication of the index vector by a unimodular matrix, and a skew, an interchange or a reversal are all such matrices.

          B is walked down a column (stride N*8 bytes): a new cache
          line is touched on every k

  Tiled (T = 32):  three tiles are in L1 at the same time

    C tile (32x32)  +=  A tile (32x32)  x  B tile (32x32)

         j-tile            k-tile             j-tile
      +--+--+--+        +--+--+--+        +--+--+--+
   i  |  |C |  |      i |  |  |A |      k |  |B |  |
      +--+--+--+        +--+--+--+        +--+--+--+

  loops:  for ii (tiles of i)
            for jj (tiles of j)
              for kk (tiles of k)
                for i, j, k inside the tile (32 x 32 x 32 steps)

  3 tiles x 32 x 32 x 8 bytes = 24 KB   -> fits in a 32 KB L1 cache
  each loaded element is reused 32 times before it leaves the cache
example: Multiply two 1024 x 1024 matrices of doubles in C, stored in row-major order. Each matrix is 1024 x 1024 x 8 bytes = 8 MB. The L1 data cache holds 32 KB, and L2 holds about 1 MB, so no matrix fits in either level. The loop has 1024^3 = about 1.07 billion multiply-add steps.
```c
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)
    for (k = 0; k < N; k++)
      C[i][j] += A[i][k] * B[k][j];
```
Step 1: look at the access pattern of the inner loop over k. `A[i][k]` moves along a row, stride 8 bytes: good. `B[k][j]` moves down a column, stride 1024 x 8 = 8 KB: each access lands on a new cache line, and the line holds 7 other doubles that we will not need until a later j. Over the whole inner loop, 1024 lines are touched for B (64 KB), and by the next j they are probably gone from L1. So almost every B access misses L1. In practice this naive code runs at a small fraction of peak: often about 1 to 2 GFLOP/s on one core, while the same core can do tens of GFLOP/s with AVX2.
Step 2: interchange j and k to get the order i, k, j. Now the inner loop over j has `C[i][j]` and `B[k][j]` both moving along a row (stride 8 bytes) and `A[i][k]` constant, so it can be kept in a register. Is the interchange legal? The only dependence is the accumulation into `C[i][j]` across k, with distance vector (0, 0, 1) in (i, j, k) order; swapped to (i, k, j) it is (0, 1, 0), still positive. So it is legal, up to floating-point reordering of additions within one element, which stays in the same order here. Now every access is stride 1, the inner loop is vectorizable (8 floats or 4 doubles at a time), and typical speed rises several times, to roughly 5 to 10 GFLOP/s.
Step 3: tile with T = 32. The three 32 x 32 tiles take 24 KB and fit in L1. For each tile triple the code does 32^3 = 32,768 multiply-adds on 3 x 1,024 = 3,072 elements, which is about 10 operations per element loaded, compared with about 1 in the untiled version once the data has fallen out of cache. With unrolling and AVX2 fused multiply-add (a vector unit that does 4 doubles x 2 operations per instruction, often 2 per cycle), a tuned kernel reaches 30 or more GFLOP/s on one core at 3 GHz, and libraries such as OpenBLAS or MKL reach most of peak by adding register blocking and packing of tiles into contiguous memory. The takeaway: the arithmetic count never changed. Only the order did.
intuition: Reading a book in the right order: instead of walking across the library for every sentence, you bring a small stack of books to your desk and finish everything that needs them.
Memory is organized in blocks (cache lines) and levels (L1, L2, L3, DRAM) of growing size and cost. A loop nest is an order in which a very large set of small operations is carried out. Many orders give the same answer, because addition and multiplication of independent terms can be done in any sequence. Loop optimization is just the choice of one good order among many equal ones, and the dependence rule says which orders are really equal. Vector instructions are the same idea in a different place: if neighboring iterations are independent, the hardware may do them together.
mistakes: People often think the compiler will fix any badly ordered loop. In fact compilers do interchange and vectorize simple cases, but they are held back by possible aliasing, function calls in the body, unknown trip counts and floating-point rules. A tiled matrix multiplication written naively is rarely produced automatically by GCC or Clang at -O3; high-performance code is either hand-tiled, uses a library, or goes through a scheduling tool like Halide, Polly or TVM.
People often think fewer instructions means faster code. In fact the cost of a loop is often set by cache misses and not by the instruction count. The tiled matrix multiplication executes slightly more instructions than the naive one (extra loops and bounds) yet runs ten or more times faster.
People often think -ffast-math or reduction pragmas are harmless switches for speed. In fact they allow the compiler to reassociate floating-point additions, and the result changes in the last bits (and can change much more for ill-conditioned sums). Use them only when you have decided that small differences are acceptable, and check that results stay within tolerance.
friction: Dependence analysis is undecidable in general and conservative in practice. Pointers, indirect indexing (`A[idx[i]]`), non-affine subscripts and function calls make the compiler assume a dependence, so it does nothing. Sparse and graph workloads, where the access pattern depends on the data, mostly cannot be tiled or vectorized by a compiler at all.
Every machine wants different parameters. The best tile size depends on cache sizes and associativity; the best unroll factor depends on latency and the number of registers; the best vector width depends on the instruction set and on whether wide vectors reduce the core clock. Auto-tuners (ATLAS, FFTW's planner, TVM's search) measure on the real machine because models are not accurate enough. Portable performance remains an unsolved problem, which is why libraries still ship hand-written kernels for each architecture.
practice: Measure first. Profile with `perf stat` to see cache misses and instructions per cycle, and use a tool such as `perf record`, VTune or Instruments to find the one or two loops that really matter. Many programs have a single hot loop nest; the rest does not deserve attention.
Help the compiler. Use simple loops with a trip count that is clear, contiguous arrays (struct-of-arrays rather than array-of-structs), `const` and `restrict` or `noalias` where valid, and no function calls with side effects in the body. Ask the compiler to explain itself: Clang's `-Rpass=loop-vectorize`, `-Rpass-missed=loop-vectorize` and `-Rpass-analysis=loop-vectorize`; GCC's `-fopt-info-vec-missed`. Read the reason it gives, such as "cannot prove aliasing" or "unsafe dependence", and fix that.
If the compiler will not do it, do not start by writing assembly. First try a library (BLAS, LAPACK, Eigen, NumPy, a columnar engine's built-in kernels), which is tuned per chip. Then try a pragma (`#pragma omp simd`, `#pragma clang loop vectorize(enable)`), and compiler-friendly intrinsics only for the hottest kernel. For tensor code, use a framework compiler (`torch.compile`, XLA) or a scheduling language (Halide, TVM) where tiling and fusion are parameters you can tune without rewriting the algorithm.
tradeoffs: Choose a vendor library (BLAS, MKL, cuBLAS, or the built-in kernels of your engine) when the operation is standard (matrix multiplication, FFT, convolution, sorting). Experts have tuned tiles and register blocking per chip, and you will not match them in a week. You give up flexibility for odd shapes or fused operations.
Choose compiler auto-vectorization with hints when the loop is simple, regular and in your own code, and you want portable code that follows each new instruction set after a compiler upgrade. You give up guarantees: a harmless edit can silently turn vectorization off, so keep a benchmark and check remarks in CI for the critical loop.
Choose explicit intrinsics or a portable SIMD library (std::simd, Highway, Rust's `std::simd`) when the loop is the product's bottleneck and the compiler cannot find the structure (shuffles, saturating arithmetic, custom bit operations). You give up readability and you must write one path per instruction set, with runtime dispatch.
Choose a scheduling language or ML compiler (Halide, TVM, Triton, XLA) when you have many tensor operators and shapes and need fusion across operators. You pay with a build pipeline, tuning time (minutes to hours of search) and a harder debugging story. For one fixed kernel, hand tuning may still win by 10 to 20 percent.
quiz: Why does swapping the loops of a nest sometimes make it much faster without changing the result? || The new order walks arrays along their memory layout (stride 1), so each 64-byte cache line is fully used before it is evicted, and hardware prefetchers work. The result stays the same only if no dependence reverses direction, which is checked with distance vectors.
A nest has a dependence with distance vector (1, -1). Can the two loops be interchanged? || No. Swapping gives (-1, 1), whose first non-zero entry is negative: the dependent iteration would run before the one it depends on. The loops can be interchanged only after some other transformation (such as skewing) makes the vector positive.
Why will a compiler not vectorize `for (i...) s += a[i];` for floats by default? || Floating-point addition is not associative. Vectorizing needs several partial sums that are added at the end, which changes the order and so the rounding of the result. It is allowed only with `-ffast-math` or an explicit reduction pragma.
You tile a matrix multiplication of doubles with T x T tiles. What is the largest T such that three tiles fit in a 32 KB L1 cache? || 3 x T x T x 8 bytes <= 32,768 gives T^2 <= 1,365, so T <= 36. In practice T = 32 or less is used, leaving room for other data and avoiding conflict misses.
A colleague wants to hand-write AVX2 intrinsics for a loop that is only 2% of runtime. What do you say? || Do not. At best it saves 2% x (1 - 1/speedup) of total time, a tiny gain, and it adds code that only works on one instruction set. First check whether the compiler vectorizes it with remarks, and spend effort on loops that dominate the profile.
interview: How does a compiler decide if it may reorder or vectorize the iterations of a loop? || It runs dependence analysis: for every pair of accesses to the same array where one is a write, it asks whether two different iterations can touch the same element, using subscript tests and alias information. If it finds no dependence, or only dependences that the new order preserves (distance vectors stay lexicographically positive, or the distance is at least the vector width), it may transform the loop. Unknown aliasing is treated as a dependence.
Explain loop tiling and how you would choose the tile size. || Tiling splits loops into blocks so that the data of one block fits in a cache level and is reused many times before eviction. Choose T so the working set (for matrix multiplication, 3 T^2 elements) fits in the target level with room to spare, typically 50 to 70 percent of the cache to avoid conflict misses; use nested tiles for L1, L2 and L3, or autotune on the real machine.
A loop that was vectorized last month is now slow after a refactor. How do you find out why? || Compile with optimization remarks (`-Rpass-missed=loop-vectorize` in Clang, `-fopt-info-vec-missed` in GCC) to see the reason: new possible aliasing, a function call that is no longer inlined, a changed data type or a conditional. Then inspect the assembly for vector instructions, and compare perf counters (instructions per cycle, cache misses) between versions.
Why do ML compilers care so much about fusion, even more than about vectorization? || Elementwise operators (add, multiply, activation) do very little arithmetic per byte moved, so they are limited by memory bandwidth. Running each as a separate loop writes and re-reads the whole tensor; fusing them into one loop keeps the intermediate in registers, which can cut memory traffic by the number of fused operators.

@@ closures
value: A program must decide what a name means. If a function uses a variable `rate` that is not its own parameter, which `rate` does it see? Lexical scope gives a simple answer: the one you find by reading the source text outward from the use, through the enclosing blocks and functions, until a definition appears. You can answer this by looking at the code, without running it.
A closure is what makes lexical scope work when functions are values. A function can be returned, stored in a list, or passed to another thread. By then the code that created it may have finished and its local variables should be gone. A closure fixes this: the function value is a pair, the code plus a pointer to the environment (the table of variables) in which the function was created. When the function runs later, its free variables (names that are not its own parameters or locals) are looked up in that saved environment.
The layers above depend on this. Callbacks, event handlers, promise continuations, decorators, iterators and `map`/`filter` with a custom body are all closures. Functional programming builds on them: a function that returns a function, and partial application, are closures. Interpreters implement environments directly, and compilers for JavaScript (V8), Python and Lua must decide where captured variables live. The layers below explain the cost: the lambda calculus defines the meaning (a closure is a lambda term plus an environment), the call stack explains why captured variables cannot stay in a frame that is popped, and garbage collection explains how the heap copy is freed when nothing refers to the closure.
terms: Free variable — a name used inside a function that is neither a parameter nor declared inside it; it comes from an enclosing scope.
Lexical (static) scope — a name is resolved by the structure of the source text, so it is fixed when the program is written, not when it runs.
Dynamic scope — a name is resolved through the chain of callers at run time; early Lisps and some shells use it, and almost no modern language does for ordinary variables.
Environment — a mapping from names to values (or to memory locations), usually a chain of frames, one per scope, linked to the enclosing one.
Closure — a function value together with the environment it captured; calling it uses that environment.
Capture by reference — the closure shares the variable itself, so changes made inside are seen outside and the other way round.
Capture by value — the closure takes a copy of the value when it is created, so later changes to the original are not seen.
Upvalue — the Lua and Lua-like name for a captured variable; it points to the stack slot while the variable is alive and moves to the heap when the scope ends.
history: The problem appeared with the first Lisp, in 1958. McCarthy's `eval` looked up variables in the environment of the caller, which is dynamic scope. When a function was passed as an argument or returned as a result (the "funarg problem", described by Joel Moses in 1970), variables could be found in the wrong environment, and results were surprising.
Peter Landin, in "The mechanical evaluation of expressions" (1964), introduced the SECD machine and the term closure for a lambda expression packaged with its environment. This gave an exact way to evaluate lambda calculus with static scope. ALGOL 60 had lexical scope for nested blocks but did not allow functions to escape their blocks. Scheme (Sussman and Steele, 1975) made lexically scoped first-class functions the core of a language, and the textbook "Structure and Interpretation of Computer Programs" (Abelson and Sussman, 1985) taught the environment model of evaluation to a generation of programmers. Common Lisp (1984) chose lexical scope as default, with optional dynamic variables.
Closures spread to mainstream languages slowly. JavaScript (1995) had them from the start, borrowed from Scheme, which is why callbacks became the main style of browser programming. Python gained nested scopes in version 2.2 (2001), and the `nonlocal` keyword to assign to an outer variable in Python 3 (PEP 3104, 2006). C# added anonymous methods (2005) and lambdas (2007); C++ lambdas came in C++11 (2011); Java lambdas in Java 8 (2014). Implementation techniques were refined in parallel: flat closures (Cardelli, 1984), the work of Dybvig and others on Scheme compilers, and Lua's upvalues, described in "The implementation of Lua 5.0" (2005). Rust (1.0 in 2015) put captures into the type system, with three closure traits that say how a closure uses what it captured. Go 1.22 (February 2024) changed loops so that each iteration has its own copy of the loop variable, removing a frequent closure bug.
how: Start with how a language without closures finds variables. Each function call creates a frame on the call stack holding its parameters and locals. When the function returns, the frame is popped and its memory is reused. This works as long as no value outlives the call. A closure breaks that rule: an inner function may be used after the outer call has returned, and it still needs the outer function's variables. The call stack layer, which allocates and frees frames in strict last-in, first-out order, cannot keep them. So the variables that a closure captures must live somewhere else, and that is the heap.
The environment model. At run time an environment is a chain of frames. Each frame maps names to values and has a link to its parent frame (the lexically enclosing one). Looking up `x` means searching the current frame, then its parent, and so on. A function value created in a frame stores a pointer to that frame. Calling the function creates a new frame for its parameters whose parent is the saved frame, not the caller's frame. That single rule (the parent of a call frame is where the function was defined) is the whole difference between lexical and dynamic scope.
Real implementations avoid walking chains. A compiler knows from the source text, before running, how many scopes out each name is, so it can resolve each variable to a fixed (depth, index) pair or to a stack slot. It also finds out which variables are actually captured by an inner function. Only those need to live on the heap. In V8, a captured variable is stored in a `Context` object on the heap, linked to the context of the enclosing scope; variables not captured stay in registers or on the stack. In CPython, a captured variable is turned into a cell object: the outer function and the inner function both hold a reference to the same cell, and the closure keeps the cells in the function's `__closure__` tuple. In Lua, an inner function refers to a captured local through an upvalue that points at the stack slot while the outer function is running; when that function returns, the upvalue is "closed", meaning the value is copied into the upvalue object itself.
Two designs for the closure object. In a linked environment, the closure holds one pointer to the parent frame and shares everything in it, which is cheap to create but keeps alive every variable in the chain, including ones the closure never uses. In a flat closure, the compiler copies just the needed free variables into the closure object (code pointer plus an array of captured values or cells). Creation costs a little more, lookup is a single indexed load, and nothing extra is retained. Most modern compilers use flat closures, with cells or boxes for variables that are assigned after capture, so that all closures that share the variable see the update.
By value or by reference. If a captured variable is never assigned after initialization, copying it is the same as sharing it, and the compiler can store the value directly. If it is assigned, a shared box is needed, or the language forbids the change. Java requires captured locals to be final or effectively final, which is why it needs no boxes. C++ lets the programmer choose in the capture list (`[=]` copies, `[&]` refers to the original stack variable, which is dangerous if the lambda outlives it). Rust makes the choice by how the closure uses the variable: a closure that only reads borrows it (`Fn`), one that changes it borrows it mutably (`FnMut`), one that moves it out is callable once (`FnOnce`), and the `move` keyword forces ownership transfer, which is needed to send a closure to another thread. Python, JavaScript and Go capture variables, not values, by reference.
Garbage collection supplies the last piece. The captured frame or cells are ordinary heap objects. They live as long as some reachable closure points to them and are reclaimed by the collector afterwards. The same fact is the main source of leaks: a long-lived closure, such as an event listener, keeps everything it captured alive.

example: Consider a counter factory in Python and trace the memory by hand.
```python
def make_counter():
    n = 0
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

a = make_counter()
b = make_counter()
print(a(), a(), b())     # 1 2 1
```
Step 1: `make_counter()` is called for `a`. A frame is created with `n = 0`. The compiler already knows that `inc` uses `n` from the enclosing function, so `n` is stored in a cell object on the heap, and the frame holds a reference to the cell. The inner function object `inc` is created with `__closure__` pointing to a tuple containing that cell. The function returns `inc`, the frame disappears, and the cell stays alive because the closure refers to it.
Step 2: the second call creates a new frame, a new cell with its own `n = 0`, and a new closure `b`. The code of `inc` is the same in both closures; only the cells differ. This is why `a` and `b` have independent state while sharing one compiled function.
Step 3: `a()` runs. `n += 1` reads the cell (0), writes 1 back, returns 1. The second `a()` returns 2. `b()` reads its own cell and returns 1. You can check with `a.__closure__[0].cell_contents`, which is 2 at this point.
Now the classic loop problem in JavaScript, with an important difference between `var` and `let`.
```js
var fs = [];
for (var i = 0; i < 3; i++) { fs.push(() => i); }
console.log(fs.map(f => f()));   // [3, 3, 3]
```
With `var`, there is one variable `i` for the whole function. All three arrow functions capture that same variable, and the loop leaves it at 3, so all three return 3. If you write `for (let i = 0; ...)`, the language creates a fresh binding of `i` for each iteration (ES2015 rule), each closure captures its own, and the result is `[0, 1, 2]`. Go had the same trap until Go 1.22, and Python still has it: a list of lambdas created in a loop that use the loop variable all see its final value, unless you bind it as a default argument (`lambda i=i: i`).
intuition: A closure is a function that carries a small backpack with the variables it needs from the place where it was born.
Lexical scope matches how people read code: to understand a name, you look up the page, not at who called the function. For that reading to stay true when a function travels, the function must take its birthplace with it. That is all a closure is. The stack cannot hold the backpack because the stack is for calls, which end, and the backpack belongs to a function value, which may live much longer, so the backpack goes on the heap and the garbage collector decides when it is no longer needed.
mistakes: People often think a closure copies the values of the outer variables. In fact in most languages (Python, JavaScript, Go, Lua, Scheme) it captures the variables themselves, so changes are visible both ways. Copy semantics belong to some languages and to explicit choices, such as C++ `[=]` or Rust `move` for values that are `Copy`.
People often think a closure keeps only what it uses. In fact that depends on the implementation. A flat closure keeps just the used variables, but a closure implemented with a pointer to a whole environment can keep large unused objects alive. Engines have in some cases retained unused variables of an enclosing scope when another closure in the same scope used them (V8 shares one context among all closures of a scope), which is a known source of memory leaks.
People often think lexical scope and dynamic scope only differ in obscure cases. In fact they give different results whenever a function is called from a context with a different binding of the same name. Dynamic scope makes a function's meaning depend on its callers, which breaks local reasoning and makes refactoring unsafe. Modern languages keep dynamic scope only in special forms (Emacs Lisp special variables, shell environment variables).
friction: Hidden lifetimes cause leaks and surprises. A listener that captures a large object keeps it alive until the listener is removed, and in a garbage-collected language no tool shows this unless you take a heap snapshot. In languages without a garbage collector, the cost is made visible and sometimes painful: C++ lambdas capturing by reference crash with a dangling reference when they outlive the stack frame, and Rust makes you state ownership (`move`, `Arc`, `Rc`) before it compiles.
Performance has costs that are easy to forget. Creating a closure usually allocates an object, and each captured mutable variable needs a heap cell, so a closure created in a hot loop can generate garbage. Calling a closure is an indirect call through a code pointer, which prevents inlining unless the compiler can see which function it is. Escape analysis in JIT compilers (V8, HotSpot) can remove the allocation when the closure does not escape, but this is not guaranteed.
Finally, closures hurt debugging and serialization. A closure cannot be written to disk or sent over a network in a simple way, because its environment is a graph of pointers and its code is a pointer. Systems such as Spark have to serialize closures to ship them to executors (Java serialization of the closure and everything it captures), which fails with "Task not serializable" when the closure captures a non-serializable object such as a database connection, and wastes bandwidth when it captures a large object by accident.
practice: When a closure behaves strangely, ask two questions: which variable does each name refer to, and when does the variable's value get read. Print or inspect the captured variables (`fn.__closure__` and `cell_contents` in Python, the "Closure" scope in Chrome DevTools). In a loop that creates callbacks, bind the loop value explicitly: `let` in JavaScript, a default argument or `functools.partial` in Python, a local copy (`i := i`) in Go before 1.22.
Keep what you capture small. Capture the one field you need and not a whole large object (`const id = request.id` before creating the callback), and always unregister listeners and timers when the owner is destroyed. For Spark, never use a field of the enclosing class inside a lambda passed to `map`, because referring to `this.field` captures all of `this`; copy it into a local `val` first, and use broadcast variables for large read-only data.
Use closures where they simplify code: callbacks, sorting keys, retry wrappers, decorators, lazy values, and small stateful helpers such as counters, memoizers and rate limiters. When the state becomes complex, or must be inspected, serialized or tested separately, switch to a class with explicit fields.
tradeoffs: Choose capture by reference (the default in Python, JavaScript and Go) when closures are meant to share and update state, such as counters, accumulators and callbacks that report progress. You give up predictability: the value seen is the value at call time, which causes the loop bug and data races.
Choose capture by value or move (C++ `[=]`, Rust `move`, Java effectively-final) when a closure will outlive its creator or run on another thread. You give up the ability to mutate shared state through the closure and may need explicit shared containers (`AtomicInteger`, `Arc<Mutex<T>>`), but the lifetime is clear and no dangling references are possible.
Choose a closure over a class when the behavior is one small function with a little state and is used in one place. Choose a class (or a named function with explicit parameters) when the state is large, must be inspected, serialized, tested alone or shared across modules; closures make this harder because the state is hidden.
Choose explicit parameters over captured variables for code that runs on remote workers (Spark, Dask, Ray). Passing data as arguments or broadcasting it avoids serializing an accidental object graph, at the cost of more verbose code.

The closure object holds a code pointer and references to those cells (flat closure) or to the enclosing context (linked environment).

value: When you write `shape.area()`, the compiler often cannot know which `area` will run. The variable `shape` may hold a circle in one call and a square in the next, and each class has its own code. Dynamic dispatch means that the choice is made at run time, from the actual type of the object, and not at compile time from the declared type. This is the mechanism behind object-oriented polymorphism, interfaces, traits and virtual methods.
The simple version of the problem is cost. The decision has to be fast, because programs make billions of method calls. Statically typed languages solve it with a small table of function pointers per class (the vtable): the call becomes "load the table pointer from the object, load the function pointer from a fixed slot, jump". Dynamic languages cannot use fixed slots because an object can gain methods at any time, so they use hash tables, and then use inline caches to remember the answer at each call site.
The layers above are everywhere. Design patterns such as Strategy and Observer are calls through an interface. The JVM's `invokevirtual` and `invokeinterface`, C++ virtual functions, Go interface values, Rust `dyn Trait` and V8's property lookups are all implementations of this idea. JIT compilers use run-time information to turn dynamic calls back into direct calls and inline them. The layers below supply the parts: type systems define which methods a call may reach (subtyping), the call stack and calling conventions define what an indirect call is at machine level, hash tables are the lookup structure in dynamic languages, and type theory gives the formal account of subtype polymorphism.
terms: Virtual method — a method whose implementation is chosen by the object's run-time class, not by the type of the variable.
vtable — an array of function pointers, one per virtual method, built once per class; objects hold a pointer to their class's table.
vptr — the hidden pointer stored at the start of an object (in C++) that points to its class's vtable.
Static (early) binding — choosing the function at compile time; used for non-virtual and final methods.
Call site — one place in the code where a call is made; an inline cache is attached to each call site.
Inline cache (IC) — a small record at a call site of the last type seen and the method found for it, so a repeat of the same type skips the lookup.
Monomorphic, polymorphic, megamorphic — a call site that has seen one type, a few types (often up to 2 to 4), or many types.
Devirtualization — replacing a virtual call with a direct call, because the compiler proved or guessed the exact type.
history: Simula 67, by Ole-Johan Dahl and Kristen Nygaard, introduced classes, objects and virtual procedures, and so the first dynamic dispatch. Smalltalk (Alan Kay's group at Xerox PARC, 1970s) made every operation a message send whose receiver decides the method. This was elegant but slow: each send looked up the method name in the class, then in its superclass, and so on, using a dictionary.
Peter Deutsch and Allan Schiffman, in "Efficient implementation of the Smalltalk-80 system" (POPL 1984), introduced the inline cache. They noticed that at most call sites the receiver is nearly always the same class, so the compiled code can contain a direct call to the method found last time, guarded by a check of the receiver's class. In the 1980s and 1990s, the C++ community fixed the vtable layout: Bjarne Stroustrup's cfront compiler used vtables from the beginning, and the Itanium C++ ABI (from 1999, still used by GCC and Clang on all platforms except Windows) standardized the layout, including multiple inheritance.
The Self project (Xerox PARC, then Stanford and Sun; David Ungar, Craig Chambers, Urs Hölzle) pushed this further. Hölzle, Chambers and Ungar's "Optimizing dynamically-typed object-oriented languages with polymorphic inline caches" (ECOOP 1991) added caches that hold several types at one call site. Self also used hidden classes (maps), type feedback and speculative inlining with deoptimization, and these ideas moved into HotSpot (Hölzle and others, 1990s) and V8 (2008). Meanwhile, Java's interface calls (`invokeinterface`) needed extra machinery because a class can implement many interfaces, and Go (2009) and Rust (2015) chose fat pointers: a reference to an interface or trait object carries two words, a data pointer and a table pointer, so objects need no hidden header at all. In 2018, the Spectre attacks made indirect branches a security issue and added a new cost, the retpoline, to virtual calls in kernels and some systems code.
how: Virtual call in C++. Each class with virtual methods gets one vtable in read-only memory. The table lists the addresses of the class's implementations in a fixed order; a derived class copies the base class's table, replaces the slots it overrides and appends new ones. So `area` is slot 0 in `Shape`, `Circle` and `Square` alike. Each object begins with the vptr, set by the constructor. The call `p->area()` compiles to a few instructions: load `[p]` (the vptr), load `[vptr + 0*8]` (the function pointer), and `call` that address. Two dependent loads and one indirect jump replace one direct jump. The calling convention is unchanged: `p` is passed as the hidden `this` argument in the first register. Because both loads hit the cache in the common case, the call itself costs only a few cycles more than a direct call.
Where dispatch really costs. An indirect call is predicted by the CPU's branch target predictor, which remembers recent targets for each call instruction (and uses history of earlier branches). If the same call site keeps going to the same target, prediction is almost perfect. If the target changes unpredictably, each wrong guess flushes the pipeline, roughly 15 to 20 cycles. The larger cost is hidden: the compiler cannot inline a function it cannot name, and inlining is what lets optimization see through the call (constants, dead code, vectorization). That is why devirtualization is the key goal of optimizing compilers.
Multiple inheritance and interfaces. With several base classes, an object holds several vptrs, one for each base subobject, and a call through the second base adjusts `this` by a fixed offset using a small thunk. In Java, an interface method has no fixed slot across all classes that implement it, so `invokeinterface` goes through an itable: the class has a table per implemented interface, and the call finds the right table (by search, or with the help of a cache) and then indexes into it. In Go, an interface value is two words: a pointer to an itab (interface table, listing the concrete type and the function pointers for this interface-type pair) and a data pointer. The runtime builds the itab the first time a concrete type is converted to an interface, and keeps it in a hash table; after that, calling a method is "load the function pointer from the itab, call it". In Rust, `&dyn Trait` is a pair of a data pointer and a vtable pointer; the vtable also contains the destructor, size and alignment of the concrete type. Generic code (`T: Trait`) instead is monomorphized: one copy of the function for each concrete type and direct calls, with no table at all.
Dynamic languages and inline caches. In JavaScript, `obj.area()` first needs to find the property `area` on `obj`, and objects are not fixed layouts. V8 gives every object a hidden class (called a map) that describes its property names and their offsets; objects built in the same way share the map. The first time a call site runs, it does a full lookup (through the map, the prototype chain and possibly a dictionary: a hash table). It then stores the map and the result in the call site's feedback slot. The next time, the code checks whether the receiver's map equals the cached one; if so, it loads the property from a known offset or jumps to the known function, with no hashing. This is the monomorphic state. If another map arrives, the cache grows to a polymorphic state holding up to four maps; beyond that it becomes megamorphic and falls back to a global stub cache keyed by map and name, which is several times slower. Python (3.11 and later) does the same with its specializing adaptive interpreter, which rewrites bytecodes such as `LOAD_ATTR` into specialized forms guarded by the type version.
Type feedback and JIT devirtualization. The inline cache also records what types have been seen. When the JIT compiler (V8's TurboFan, HotSpot's C2) compiles a hot function, it reads this profile. If a call site has been monomorphic, the compiler inserts a guard ("is the receiver's class `Circle`?") and a direct call, which it can inline; on a guard failure the code deoptimizes, returning to the interpreter and recompiling. HotSpot also uses class hierarchy analysis: if only one loaded class implements a method, the call is direct, and if a new class is loaded later that overrides it, the compiled code is invalidated. For two common types, a bimorphic inline (two guards) is done. Beyond that, the compiler leaves a real virtual call. Ahead-of-time compilers use the same idea from profile data (profile-guided optimization) or from `final` and `sealed` markers.
The type systems layer gives the rules. Subtyping says that a `Circle` may be used where a `Shape` is expected, and that an override must have a compatible signature (accept at least the same arguments, return at most the same type). Dispatch is how that rule is carried out at run time. Hash tables are the fallback for languages where the set of methods changes, and the speed of their lookup (hundreds of cycles including hashing and probing) is why inline caches exist. The call stack layer defines how arguments and return addresses flow, so an indirect call differs from a direct call only in where the target address comes from.

example: Take a base class `Shape` with `virtual double area()` and two subclasses, `Circle` (field `r`) and `Square` (field `s`). On a 64-bit machine, a `Circle` object is 16 bytes: 8 for the vptr and 8 for `r`. There are two vtables in the binary, each with 2 slots (area and perimeter), so 16 bytes each. A loop sums the area of 10 million shapes held as `Shape*` in a vector.
Step 1: for each element, the code loads the pointer `p`, then `[p]` (vptr), then `[vptr]` (function address), then calls. The two loads of the vptr and slot are almost always cache hits for the vtable (it is tiny), but loading `p` and the object touches 16 bytes of the heap per shape, which is where memory time goes.
Step 2: suppose the shapes are in random order, 50% circles and 50% squares. The call site has two targets and the CPU cannot predict which, so roughly half of the calls (modern predictors use history, but random data has none) are mispredicted. At about 15 cycles per miss, that is about 7 cycles extra per call on average, or roughly 2 ns at 3.5 GHz, which is 20 ms for 10 million shapes for the misprediction alone.
Step 3: sort the vector by type, or keep two separate vectors. Now the branch is predictable for long runs, and the misprediction cost almost disappears. In a database engine this is the idea behind processing columns of one type in a batch: the dispatch happens once per batch of 1,000 or more values, not once per value.
Step 4: in Java, if only `Circle` is loaded when the method is compiled, the JIT compiles `shape.area()` as a direct, inlined call guarded by class hierarchy analysis. When a `Square` class is loaded later, HotSpot invalidates that compiled code, and the next compilation uses a type profile. If the profile shows 99% circles, it inlines `Circle.area` behind a guard and leaves a virtual call for the rest, so the common path has no dispatch cost at all.
intuition: A dispatch table is a menu card kept by each kind of object, where the position of each dish is the same on every card, so a call is one look-up by position and not a search by name.
Dispatch is natural because the caller knows what it wants (`area`) but not who will do it, while the object knows how. The vtable makes "what" into a number (a slot) that is the same for every subclass, and "how" into a pointer stored in each class's own table. The inline cache applies a second observation: programs are repetitive, and the same call site tends to see the same type again and again, so the result of the last lookup is usually the right one. A guess guarded by a cheap check turns an expensive general mechanism into a cheap special case.
mistakes: People often think virtual calls are slow because of the table lookup. In fact the two loads usually hit the L1 cache and cost a few cycles. The real costs are lost inlining and, when targets vary, branch misprediction. A virtual call to a tiny getter is expensive because it cannot be inlined, not because of the lookup.
People often think dynamic dispatch needs object-oriented classes. In fact it is the idea of calling through a pointer chosen by data. C programs do it with structs of function pointers (the Linux kernel's `file_operations`), Go has no inheritance but has interface calls, and Rust trait objects and C++ function objects use the same pattern.
People often think a JIT makes every call fast. In fact the JIT is fast only when the call site is stable. A megamorphic site, for example one generic helper called with ten different object shapes in a serializer, loses inline caching and inlining. Keeping object shapes consistent (same properties added in the same order) is a real performance concern in JavaScript.
friction: The deepest cost is the barrier to optimization: virtual calls separate the caller from the callee, so a compiler cannot propagate constants, remove dead code or vectorize across the call. A loop calling a virtual method per element can be 5 to 50 times slower than the same work as an inlined loop. This is why query engines moved from a virtual `next()` per row (the Volcano model) to batches or generated code.
Branch prediction is also a source of unpredictable performance, and a security problem. Spectre variant 2 showed that an attacker can train the indirect-branch predictor to make the CPU speculatively run chosen code. The defenses (retpolines, indirect branch restricted speculation) make indirect calls slower, sometimes by tens of cycles, so kernels and hardened systems try hard to turn indirect calls into direct ones.
practice: Do not remove abstraction on a guess. First profile and find whether a virtual call is in a hot loop. If it is, bring the dispatch outside the loop: handle a batch of items of one type per call, sort or partition items by type, or use a template/generic parameter so the compiler can monomorphize the loop body.
Mark classes and methods `final` (or `sealed`, or use a private implementation) when they are not designed for extension. In Java, the JVM already devirtualizes many cases, but `final` documents the intent. In C++, use `final` on classes and `override` on overrides, and prefer templates or `std::variant` with `std::visit` for a closed set of types known at compile time; the variant stores the type as a small integer and uses a switch, which is cheaper than a virtual call and keeps the data inline.
In JavaScript, write functions that see objects of one shape: create objects with all properties in the constructor in the same order, avoid `delete`, and do not change types of properties. Check with `node --allow-natives-syntax` and `%HasFastProperties`, or the Chrome performance profile's deoptimization events. In Python 3.11+, keep attribute access on stable classes and avoid assigning new attributes outside `__init__`.
tradeoffs: Choose virtual dispatch (interfaces, traits objects) when the set of types is open and extended by other code, such as plugins, storage back ends or user-defined handlers. You give up inlining and pay an 8-byte pointer per object or per reference, but you gain separate compilation and extension without changing existing code.
Choose static dispatch (templates, generics, monomorphization, `final`) when the types are known at compile time and the call is in a hot path. You give up compile time and binary size (each type gets its own copy of the code, which can multiply code size) and the ability to add types at run time.
Choose a closed sum type (`enum` in Rust, `std::variant`, sealed classes with pattern matching) when the set of variants is fixed and you add operations more often than types. You give up easy extension by new types, but get a switch that the compiler checks for completeness and that predicts well.
For dynamic languages, choose stable object shapes and a small number of types per call site to keep inline caches monomorphic. If the data is irregular by nature, accept the slower megamorphic path or move that hot kernel to a typed language or a vectorized library.

value: Two ideas that look separate are closely connected. Parametric polymorphism lets one function work for many types with one definition and one proof of safety: `length : List<T> -> int` works for any `T` because it never looks inside the elements. Type inference lets the compiler find the types itself, so you can write `let double = fun x -> x * 2` and the compiler works out `int -> int` without annotations. Together they give static typing with little of its paperwork: the compiler checks everything before the program runs, and you write types mostly at the boundaries.
The classic algorithm is Hindley–Milner (HM). Every unknown type gets a type variable; each use of an expression adds equations ("this argument must have the type the function expects"); and unification, an algorithm that solves such equations, finds the most general type that satisfies them all. The result is principal: it is the most general type the expression can have, so no other valid type is more useful.
For the layers above, this is the typing story of ML, OCaml and Haskell, and the base for the local inference found in Rust (`let v = Vec::new()` with the element type decided by a later `push`), Scala, Swift, Kotlin and TypeScript, and for generics in Java, C++, Go and Rust. The layers below supply the foundations: the lambda calculus (L4) is the language that HM is defined on, type theory (L4) says what a type and a typing judgment are, a type system (L3) is what inference reconstructs, and logic programming (L3) shares unification, the matching procedure at the center of both Prolog and type inference.
terms: Type variable — a placeholder for a type that is not yet known, written 'a, b or t1.
Unification — finding a substitution of types for type variables that makes two type expressions equal, for example `a -> int` and `bool -> c` unify with a = bool and c = int.
Most general unifier (mgu) — the simplest such substitution; every other solution is an instance of it.
Type scheme — a type with universally quantified variables, written `∀a. a -> a`; each use picks a fresh instance.
Generalization and instantiation — turning free type variables of a let-bound definition into quantified ones (generalization), and replacing the quantified ones by fresh variables at each use (instantiation).
Principal type — the most general type of an expression; HM always finds it when a type exists.
Monomorphization — compiling a generic function once for each concrete type used, so each copy has direct, specialized code.
Type erasure — compiling a generic function once, forgetting the type arguments, so one copy of the code serves all types.
history: Haskell Curry and Robert Feys studied type assignment for combinatory logic in the 1950s. J. Roger Hindley (1969) proved that every typable term has a principal type scheme. Robin Milner independently built the same system for the language ML, which he designed as the metalanguage for the LCF theorem prover at Edinburgh in the 1970s. His paper "A theory of type polymorphism in programming" (1978) presented Algorithm W and showed that "well-typed programs cannot go wrong": a type-checked program never applies an operation to the wrong kind of value. Luis Damas and Milner (POPL 1982) proved that the algorithm is complete, finding a principal type whenever one exists. The unification procedure comes from John Alan Robinson's resolution paper (1965), written for theorem proving, which is why Prolog and type inference share the same core.
In the 1980s and 1990s, the ideas were extended. Philip Wadler and Stephen Blott (1989) added type classes to give overloading on top of inference, implemented with dictionary passing, and this became the base of Haskell. Hindley–Milner was shown to be DEXPTIME-complete in the worst case (Kfoury, Tiuryn and Urzyczyn; Mairson, 1990): contrived programs have types whose size is exponential in the program text, but ordinary programs are checked in near-linear time. Full inference for the more powerful System F (explicit polymorphism of arbitrary rank) was proved undecidable by Joe Wells in 1994, so languages must stop short of it or ask for annotations.
Mainstream languages adopted the ideas in pieces. Java 5 (2004) added generics, designed by Gilad Bracha, Martin Odersky, Wadler and others, implemented by type erasure to stay compatible with old bytecode. C# 2.0 (2005) chose reified generics in the runtime. C++ templates (1990s) were instantiated per use, with argument deduction for functions, and `auto` (C++11) added local inference. Scala (2004) and later Kotlin, Swift and TypeScript use local or bidirectional inference because pure HM does not combine well with subtyping and overloading. Rust (1.0 in 2015) uses HM-style inference inside function bodies plus traits and monomorphization. Go added generics in version 1.18 (March 2022), with type-argument inference and an implementation that mixes both strategies.
how: The algorithm in outline. Walk the syntax tree of the expression. Give every variable and every unknown sub-expression a fresh type variable. At each node, emit an equation that its parts must satisfy: for an application `f e`, the type of `f` must equal "type of e -> some result type r"; for `if c then a else b`, `c` must be `bool` and the types of `a` and `b` must be equal; for a literal `3`, the type is `int`. Solve all equations by unification. Substitute the solution back to get the type. If two equations conflict, such as `int = bool`, the program has a type error.
Unification. To unify two types: if one is a variable, bind it to the other (after the occurs check, which refuses to bind `a` to a type that contains `a`, since `a = a -> b` would be an infinite type). If both are the same constructor, such as `->` or `List`, unify the arguments pairwise. Otherwise fail. Implemented with a union-find structure (the trees and disjoint sets layer), this runs in almost linear time. The substitutions compose, and the result is the most general one, which is what gives principal types. The same procedure matches Prolog terms, which is why the logic programming concept is a close relative.
Let-polymorphism, the heart of HM. Consider `let id = fun x -> x in (id 1, id true)`. The type of `id` is `a -> a` for a type variable `a` that nothing constrains. If `a` stayed a single unknown variable, the first use would force `a = int` and the second `a = bool`, a conflict. HM solves this at `let`: after inferring the type of the bound expression, it generalizes all type variables that are not mentioned in the surrounding environment, giving the scheme `∀a. a -> a`. Each use of `id` then instantiates the scheme with fresh variables. A lambda-bound variable, in contrast, gets a plain monomorphic type, so `(fun id -> (id 1, id true))` is rejected. This split gives enough polymorphism to be useful while keeping inference decidable. The type theory layer says why the limit is there: allowing a lambda-bound argument to be polymorphic needs higher-rank types, whose inference is undecidable.
Typeclasses and traits as constraints. In Haskell and Rust, a function such as `sum` needs `+`, so its type is `∀a. Num a => [a] -> a`. Inference collects such constraints along with equations and either solves them from known instances or keeps them in the type. The constraint is turned into a hidden argument: in Haskell, a dictionary (a record of the methods of the class) is passed at run time; in Rust, the compiler picks the implementation at compile time.
Implementing generic code: two ways. After type checking, the compiler still has to produce machine code for a function that works for any `T`. Monomorphization makes a separate copy of the function for each concrete `T` it is used with (Rust, C++ templates, Swift sometimes, and MLton for Standard ML). Each copy is as fast as hand-written code for that type, the compiler can inline and vectorize, and there is no boxing; the cost is larger code and longer compile times. Type erasure (Java, and OCaml and Haskell by uniform representation) produces one copy that treats all values uniformly, usually as pointers, so a `List<Integer>` holds pointers to boxed integers; the code is small and compilation fast, but primitives are boxed and the run time cannot see the type argument (Java cannot write `new T()` or `x instanceof List<String>`). A middle way is dictionary passing: one copy of the code receives a hidden table of operations (size, equality, method pointers). Go 1.18 groups types by "GC shape" (the same memory layout, for example all pointer types) and compiles one copy per shape, passing a dictionary for the rest. Swift and the .NET runtime also mix: .NET compiles one copy for all reference types and one for each value type.
Local inference and subtyping. Languages with subtyping, overloading and implicit conversions cannot use plain unification, because `a <: b` is an inequality, not an equation, and the solution is often not unique. Instead they use bidirectional checking: types flow down from annotations (`val xs: List[Int] = List()` tells `List()` to be `List[Int]`) and up from literals and function results. Function signatures are annotated, bodies are inferred. Rust works this way and still uses unification variables inside a function body; TypeScript infers variable types from initializers and contextual types from where a lambda is passed. This gives most of the benefit of inference with predictable behavior.

example: Infer the type of `fun f -> fun x -> f (f x)` (apply a function twice), following the diagram. We give `f` the type variable A and `x` the type variable B. The inner application `f x` has a result type C, so A must equal `B -> C`. The outer application `f (f x)` applies `f` to an argument of type C and gets a result type D, so A must also equal `C -> D`. Unify `B -> C` with `C -> D`: both are function types, so unify arguments (B = C) and results (C = D). Now all three variables are one variable, called b, and A = `b -> b`. The type of the whole function is `(b -> b) -> b -> b`, generalized to `∀b. (b -> b) -> b -> b`. Nobody wrote an annotation. Test: `twice (fun n -> n + 1) 5` instantiates b = int and gives 7; `twice not true` instantiates b = bool.
A tiny unifier is short enough to read. Types are either a string (a variable such as `'a`) or a tuple `(name, args...)` such as `('->', 'a', 'int')`.
```python
def walk(t, s):                      # follow variable bindings in s
    while isinstance(t, str) and t in s:
        t = s[t]
    return t

def occurs(v, t, s):
    t = walk(t, s)
    if isinstance(t, str): return v == t
    return any(occurs(v, a, s) for a in t[1:])

def unify(a, b, s):                  # s: dict var -> type, updated
    a, b = walk(a, s), walk(b, s)
    if a == b: return
    if isinstance(a, str) and a.startswith("'"):
        if occurs(a, b, s): raise TypeError("infinite type")
        s[a] = b
    elif isinstance(b, str) and b.startswith("'"):
        unify(b, a, s)
    elif (isinstance(a, tuple) and isinstance(b, tuple)
          and a[0] == b[0] and len(a) == len(b)):
        for x, y in zip(a[1:], b[1:]): unify(x, y, s)
    else:
        raise TypeError(f"cannot unify {a} with {b}")
```
Calling `unify(('->', "'b", "'c"), ('->', "'c", "'d"), s)` binds `'b` to `'c` and `'c` to `'d`, exactly the steps above. A full inferencer adds an environment, fresh variable generation, and generalization at `let`, in about 100 lines.
Now a failing case: `fun x -> x x`. Give x the variable A. The application `x x` needs A = `A -> R`. The occurs check finds A inside `A -> R`, so unification fails with "infinite type", and the program is rejected. This is why self-application, the heart of the untyped lambda calculus' fixed-point combinators, needs special support (recursive types or a built-in `fix`) in typed languages.
intuition: Type inference is solving a small system of equations: the program tells you how pieces must fit, and you find the types that make all pieces fit at once.
The design is natural because a type annotation is mostly redundant. In `x + 1`, the use already says that `x` is a number. Instead of asking the programmer to repeat what the code states, the compiler writes down what each use demands and solves. Polymorphism follows from the same view: a definition that places no demands on a value (it only passes it around, like `id` or `length`) leaves its type variable free, and free variables can be filled in differently at each use. Generalizing at `let` captures exactly that.
mistakes: People often think type inference means the language is dynamically typed. In fact the types are all there and checked at compile time; the compiler found them itself. An inferred program has the same safety as an annotated one, and in OCaml or Haskell you can print the inferred types and should usually write them as documentation for top-level functions.
People often think generics are the same thing as templates. In fact a C++ template is checked only after it is instantiated with concrete types (so errors appear at the use site, often as long messages), while a Rust or Java generic is checked once against its declared bounds. Both can be implemented by monomorphization, but the checking model differs.
People often think Java generics exist at run time. In fact because of erasure, `List<String>` and `List<Integer>` are the same class at run time; the type arguments are checked by the compiler and then removed. That is why you cannot create a generic array `new T[n]`, why generics cannot hold `int` directly (they hold boxed `Integer`), and why `instanceof List<String>` is rejected.
People often think monomorphization is always faster. In fact it makes each copy fast but multiplies code. A generic function used with 50 types is compiled 50 times; large instruction footprints can evict code from the instruction cache and slow the program, and compile times can grow noticeably. Some Rust crates and C++ libraries add `dyn` or type-erased wrappers specifically to limit this.
friction: Error messages are the main user cost. Unification is order-dependent: the compiler may notice a conflict far from the mistake, in a place that was actually correct. An error like "expected int, found string" at line 80 may come from a wrong call at line 12 that fixed a type variable early. Good compilers (Elm, Rust) work hard on explaining, but the underlying algorithm gives no direct notion of "which expression is to blame".
The value restriction. Allowing generalization of any `let` is unsound when mutation exists. `let r = ref []` in ML would have type `∀a. a list ref`, and then `r := [1]` followed by `(hd !r) ^ "x"` would use the same cell as both an int list and a string list. ML therefore generalizes only syntactic values (functions, constants), and an expression such as `ref []` gets a weak type `'_a list ref` that is fixed by its first use. This surprises newcomers.
Inference interacts badly with the features mainstream languages want: subtyping, overloading, implicit conversions, default arguments, higher-rank polymorphism and dependent types all make the constraint problem harder or undecidable. That is why Rust requires full signatures on functions, Scala 3 and TypeScript limit what they infer, and why Swift's type checker could take exponential time on some expressions that mix literals and overloaded operators, a known source of "expression too complex" errors.
practice: Annotate public functions even in languages that infer them. The annotation is documentation, it turns a confusing error deep in a function into a clear error at the boundary, and it prevents accidental changes to your API. Let local variables and lambdas be inferred. In Rust, write the function signature in full and let the body infer; use the turbofish `collect::<Vec<_>>()` or an annotation when the compiler asks "type annotations needed".
Read type errors from the first one, and treat later errors as possibly caused by it. When a message is confusing, add an annotation on a sub-expression to give the compiler a firm fact; the real mismatch then moves closer to its cause. In OCaml, print inferred types with the editor or `ocamlfind ocamlopt -i`; in Haskell, ask GHCi with `:t`.
Choose generics with bounds (`T: Ord`, `T extends Comparable<T>`), because the bound states exactly which operations the function needs. Keep generic functions small and push type-specific work into traits or interfaces, so monomorphized code stays small; check binary size with `cargo bloat` if it matters. In Java, remember erasure: pass a `Class<T>` or a `Supplier<T>` if you need the type at run time. In TypeScript, enable `strict` so that inference does not fall back to `any`.
For learning, implement the unifier above and extend it to a mini-ML with `let`. It is a small project that explains many error messages you will see for the rest of your career.
tradeoffs: Choose full HM inference (OCaml, Haskell, Elm, Standard ML) when you control the language, favor correctness and concise code, and can live without subtyping and ad-hoc overloading. You get principal types and few annotations; you give up easy overloading and implicit conversions, and you must live with confusing errors at times.
Choose local, bidirectional inference with required signatures (Rust, Scala, Swift, Kotlin, TypeScript, Go) when the language has subtyping, overloading or traits and the code is read by many people. You give up writing no types at all, but get predictable checking, readable boundaries and better error messages.
Choose monomorphization when the generic code is performance-critical and the number of type instances is small, such as numeric kernels, collections of primitives and serialization hot paths. You pay with binary size and compile time. Choose erasure or dictionary passing when there are many instantiations, code size matters, or you need separate compilation and plugin-style loading; you pay with boxing, indirect calls and less inlining.
quiz: What does unification do, and what does the occurs check prevent? || Unification finds a substitution for type variables that makes two types equal (it fails if no such substitution exists). The occurs check refuses to bind a variable to a type that contains it, which would make an infinite type such as `a = a -> b`; this is why `fun x -> x x` is rejected.
Why can `let id = fun x -> x in (id 1, id true)` be typed, but `(fun id -> (id 1, id true)) (fun x -> x)` cannot? || A `let`-bound name is generalized to `∀a. a -> a`, and each use instantiates fresh variables, so one use can be `int` and another `bool`. A lambda-bound parameter has one monomorphic type, so the two uses would force `int = bool`.
What is the inferred type of `fun f -> fun x -> f (f x)`, and which equations give it? || `(b -> b) -> b -> b`. With f : A and x : B, `f x` gives A = B -> C, and `f (f x)` gives A = C -> D. Unifying them gives B = C = D, so A = b -> b.
A Java list `List<Integer>` of one million numbers is compared with an `int[]` of the same numbers. Roughly how do they differ in memory, and why? || The `int[]` takes about 4 MB. The list holds 1 million references (4 to 8 bytes each) to separate `Integer` objects of about 16 bytes each, so roughly 20 to 24 MB, plus pointer chasing. Erasure forces generic containers to hold objects, so primitives are boxed.
You are designing a new language with subtyping and method overloading. Why not just use Hindley–Milner for everything? || Subtyping turns type equations into inequalities and overloading makes them ambiguous, so unification no longer finds a unique most general type, and inference can become undecidable or very slow. A common design is local bidirectional inference with explicit function signatures.
interview: Walk through how Hindley–Milner infers the type of `let compose f g x = f (g x)`. || Assign f : A, g : B, x : C. The application `g x` gives B = C -> D. The application `f (g x)` gives A = D -> E. The result type of the function is E. So the type is `(D -> E) -> (C -> D) -> C -> E`, and all three variables are generalized at the `let`. Each step is an equation, solved by unification.
Why does Rust require full type signatures on functions when it can infer so much inside them? || Signatures are the contract between functions; requiring them keeps inference local, so error messages point to the right place and a change inside a body cannot silently change the public API. It also makes separate compilation and trait resolution tractable, since inference needs to see only one function body at a time.
Compare monomorphization and type erasure on performance, binary size and compile time. When would you pick each? || Monomorphization: fastest code (direct calls, inlining, no boxing), but code size and compile time grow with the number of instantiations. Erasure: one copy, small and quick to compile, but boxing and indirect calls. Pick monomorphization for hot, small, widely used generics with few instantiations, and erasure or dictionaries for large generic code with many instantiations or when you need a stable binary interface.
What is the value restriction and why does it exist? || In languages with mutable references, generalizing the type of `ref []` to `∀a. a list ref` is unsound because one cell would be used at several types. The restriction generalizes only syntactic values, so non-values get weak, monomorphic type variables resolved by their first use.
How does Go 1.18 implement generics, and what trade-off does it make? || It uses GC shape stenciling with dictionaries: types that have the same underlying memory shape (for example all pointers) share one compiled copy, and a dictionary passed as a hidden argument gives type-specific operations. This limits code growth compared with full monomorphization, at the price of some indirect calls and less inlining than a per-type copy.

value: In most programming you tell the computer how to compute an answer. In logic programming you tell it what is true and ask what follows. You write facts (`parent(alice, bob).`) and rules (`ancestor(X, Y) :- parent(X, Z), ancestor(Z, Y).`, read "X is an ancestor of Y if X is a parent of some Z who is an ancestor of Y"), and then you ask questions (`?- ancestor(alice, W).`). The system finds every value of `W` that makes the question true. The search procedure is part of the language, not of your program.
Two engines grew from this idea. Prolog answers a query by working backward from it: it unifies the question with the head of a rule, replaces it by the rule's body, and tries again, backtracking when a branch fails. Datalog, the restricted and cleaner relative, works forward: it applies the rules to the known facts to produce new facts, and repeats until nothing new appears. Datalog always terminates and gives one well-defined answer; Prolog is more expressive and can loop forever.
Datalog is the version that is widely useful in industry today. Program analysis tools (CodeQL, Doop, Soufflé) express questions such as "which values can reach this call?" as recursive rules over a database of program facts. Policy engines use it (Open Policy Agent's Rego is Datalog-inspired). Recursive queries in SQL (`WITH RECURSIVE`) are Datalog inside a relational engine. Knowledge graphs apply rules to triples in the same way. The layers below explain why it works: first-order logic (L4) supplies the clauses and the meaning of "follows", relational algebra (L3) supplies the data model and the join, and order theory (L4) proves that the forward process reaches a unique least fixed point.
terms: Fact — a statement that is always true, such as `edge(1, 2).`; in database terms, a row.
Rule (Horn clause) — a statement `head :- body1, body2.` meaning the head is true if all body goals are true; the comma means "and".
Query (goal) — a question such as `?- path(1, X).`; the answers are the bindings of the variables that make it true.
Unification — finding values for variables that make two terms identical; for example `parent(X, bob)` and `parent(alice, Y)` unify with X = alice and Y = bob.
Backtracking — when a choice leads to failure, undo it and try the next alternative.
Fixed point — a set of facts that no rule can extend; Datalog evaluation stops when it reaches one.
Semi-naive evaluation — a bottom-up strategy that joins only the facts that are new since the last round, instead of all facts.
Stratified negation — allowing `not p(X)` in rules provided the rules can be ordered in layers so that `p` is fully computed before it is negated.
history: The roots are in logic and theorem proving. In 1965, John Alan Robinson published the resolution principle and the unification algorithm, which showed how a machine can prove statements in first-order logic by one uniform rule. Robert Kowalski, working with Alain Colmerauer's group at Marseille, saw that a restricted form (Horn clauses with SLD resolution) can be read both as logic and as a procedure: "predicate logic as programming language" (1974). Colmerauer and Philippe Roussel implemented the first Prolog in 1972, for natural-language processing in French. David H. D. Warren's compiler for DEC-10 Prolog (1977) and the Warren Abstract Machine (1983) made Prolog fast enough to be practical.
In the 1980s, Prolog became the symbol of the Japanese Fifth Generation Computer Systems project (1982–1992), which aimed at logic-based parallel machines, and which did not reach its larger goals. At the same time database researchers took the clean subset: Datalog is Prolog without function symbols and without the order-dependent features, so every program terminates. The theory of efficient evaluation grew quickly: semi-naive evaluation, and the magic sets transformation (Bancilhon, Maier, Sagiv and Ullman, 1986), which rewrites a program so that bottom-up evaluation only computes facts relevant to a specific query.
Datalog fell out of fashion in the 1990s as object databases and then SQL took the attention, and came back in the 2000s. Bravenboer and Smaragdakis's Doop (OOPSLA 2009) showed that points-to analysis for Java could be written in a few hundred Datalog rules. Soufflé (Oracle Labs and University of Sydney, 2016) compiles Datalog to parallel C++ and analyzes programs with hundreds of millions of facts. Semmle, founded by Oege de Moor, built the QL language (an object-oriented Datalog) for code search; GitHub bought Semmle in 2019 and runs it as CodeQL. SQL:1999 added recursive common table expressions, which gave relational systems the core of Datalog's recursion. Datomic (2012) uses Datalog as its query language, and the Open Policy Agent project (2016) built the Rego policy language on Datalog ideas.
how: Start with the rules. A clause has a head and a body. In `path(X, Z) :- path(X, Y), edge(Y, Z).`, the variables are universally quantified: for all X, Y, Z, if the body is true then the head is true. The first-order logic layer gives this meaning, and Horn clauses (at most one positive literal) are the fragment for which a simple and efficient proof procedure exists.
Top-down, Prolog. To answer a goal, Prolog looks through the rules in the order they are written. It tries to unify the goal with a rule's head; if that works, the variable bindings are applied and the goals of the body become new goals, solved left to right. If a goal fails, the system backtracks to the most recent choice point and tries the next rule. Each success returns one answer, and asking for more resumes backtracking. This depth-first search is the SLD resolution strategy. It uses little memory (a stack of choice points) and is easy to follow, but it has well-known traps. The order of rules and goals matters. A left-recursive rule such as `path(X, Z) :- path(X, Y), edge(Y, Z).` placed first sends the search into an infinite loop. The cut (`!`) prunes choice points for efficiency, but it makes the program's meaning depend on order and ruins the logical reading. Most Prolog systems also skip the occurs check for speed, so unification can build circular terms.
Bottom-up, Datalog. Datalog avoids those problems by starting from the facts. Take the set of known facts. For every rule, find all ways to satisfy the body using the current facts (this is a join), and add the head instances that result. Repeat until a round adds nothing. Rules without function symbols (Datalog has only constants and variables) can only produce facts made of constants already present, so the number of possible facts is finite and the process must stop. The answer does not depend on the order of rules or goals.
Why the result is unique. Define a function T that takes a set of facts and returns it plus everything one rule application can derive. T is monotone: more input facts never remove output facts. The sets of facts, ordered by inclusion, form a lattice, and the Knaster–Tarski theorem (the order theory layer) says that a monotone function on a finite lattice has a least fixed point, which is reached by starting from the base facts and applying T repeatedly. That least fixed point is the meaning of the program. It is also the set of facts that logically follow from the program, and no extra fact is added that the rules do not force.
Relational algebra is the engine. Each rule body is a conjunctive query: a join of the relations in the body, followed by a projection onto the head variables. `path(X, Z) :- path(X, Y), edge(Y, Z)` is `π_{X,Z}(path ⋈_{Y} edge)`. Datalog is therefore relational algebra plus recursion, and everything a database knows about joins applies: hash joins, indexes on join columns, join ordering, and parallelism by partitioning facts. Soufflé uses specialized B-trees and compiles every rule into a loop nest in C++.
Semi-naive evaluation. The naive loop recomputes all joins every round, even though most derived facts are old. Semi-naive evaluation keeps a delta, the facts new in the last round. For a rule with one recursive body atom, it joins the delta of that atom with the other relations. For rules with two recursive atoms, `path(X,Z) :- path(X,Y), path(Y,Z)`, it uses two versions of the join, each with one delta. Each derivation is then made about once, instead of once in every later round.
Negation and aggregation. Plain Datalog is monotone, so it cannot say "not". Stratified negation orders the rules into layers: compute a predicate completely, then use `not` on it in a later layer. A program like `p(X) :- not p(X)` has no sensible meaning and is rejected. Aggregates (`count`, `sum`, `min`) have a similar restriction when used in recursion; some systems allow `min` and `max` in recursion (for shortest paths) if the values keep improving in one direction.
Goal-directed evaluation. If you want only `path(1, X)`, computing the whole closure for all start nodes is wasteful. The magic sets transformation adds helper predicates that record which calls are relevant, so bottom-up evaluation behaves like top-down: it explores only facts reachable from the query. Tabling (SLG resolution, used in XSB Prolog) does the same from the top-down side, memoizing subgoals, which makes left recursion terminate.
Unification also appears in type inference: the type inferencer for ML-style languages uses the same algorithm to match type terms, which is the link to the previous concept on type inference.

```text

path(X, Z) :- path(X, Y), edge(Y, Z).
```

Step 1: round 0 applies the first rule. `path` gets the four edge pairs: (1,2), (2,3), (3,4), (2,5). All four are new, so delta0 has 4 facts.
Step 2: round 1 applies the second rule to the delta only. (1,2) joined with `edge(2, Z)` gives Z = 3 and Z = 5, so we derive (1,3) and (1,5). (2,3) joined with `edge(3, Z)` gives (2,4). Step 3: round 2 joins delta1 with edges. (1,3) with `edge(3,4)` gives (1,4). (1,5) and (2,4) give nothing. Delta2 = {(1,4)}.

```sql
WITH RECURSIVE path(x, y) AS (
  SELECT src, dst FROM edge
  UNION
  SELECT p.x, e.dst FROM path p JOIN edge e ON p.y = e.src
)
SELECT * FROM path WHERE x = 1;
```
`UNION` (not `UNION ALL`) removes duplicates, which is what makes the iteration stop on graphs with cycles. The database runs the recursive part repeatedly on the rows added in the previous step, which is semi-naive evaluation. Now scale the idea: a program-analysis rule `varPointsTo(V, H) :- assign(V, W), varPointsTo(W, H).` over 50 million `assign` facts is the same recursion, and Soufflé evaluates it with indexes in minutes on a multicore machine.
Contrast with Prolog on a cyclic graph: if we add `edge(5, 2)`, the Datalog evaluation still stops (the closure just grows to include the cycle, and duplicates are dropped), while a naive Prolog definition of `path` can loop forever, because it keeps revisiting 2, 5, 2, 5, and has no memory of what it has seen.
intuition: Datalog is a spreadsheet for facts: you write the rules once, and the system keeps filling in the table until no rule can add another row.
The idea is natural because many questions are reachability in disguise: who can reach what, what depends on what, which values flow where. A rule says one step; recursion says "any number of steps". Because the rules only add facts and never remove them, the order in which you apply them cannot change the final answer, and the process must stop when the supply of possible facts is finite. That gives the pleasant property that the program is a specification: you can read it, reorder it, and the engine is free to choose how to run it.
mistakes: People often think logic programming is the same as Prolog. In fact Prolog is one execution strategy, depth-first with cut and side effects, which is why it can loop and why its meaning depends on rule order. Datalog, answer set programming and constraint logic programming use other strategies with different guarantees.
People often think Datalog is just a toy version of SQL. In fact it is more expressive in the main direction that matters: arbitrary recursion with mutually recursive predicates is natural, and SQL recursion is more awkward and limited (one recursive term, restrictions on aggregation). Many SQL engines implement recursion only as linear recursion with a working table.
People often think a Datalog query always gives the answers quickly because it terminates. In fact termination only means that the process ends. The number of derived facts can be huge (the transitive closure of a graph with n nodes can have n² pairs; a 1 million node graph can yield up to 10¹² pairs), and rule order and join order can change run time by orders of magnitude.
People often think negation is just `NOT` and works anywhere. In fact negation in recursion can be self-contradictory (`p :- not p`), and the theory needs stratification or well-founded semantics to give it a meaning. Check that your engine accepts the program, and do not rely on negation to mean "not yet derived".
friction: Prolog's gap between the logical reading and the actual behavior is the main practical problem. A clean-looking program can loop, run in exponential time, or give different answers when two goals are swapped, and to make it fast you add cuts that reduce the logic to ordinary imperative code with strange syntax. This is the main reason Prolog is now used for narrow tasks (parsing, rule systems, teaching, symbolic AI prototypes) and not as a general language.
Datalog has the opposite limits. It is deliberately weak: no function symbols means no arithmetic on structures, no building lists, and limited numeric computation (most engines add arithmetic and aggregates as extensions, and with them termination is no longer guaranteed). Data complexity is polynomial (PTIME-complete), but combined complexity, measured in program size too, is EXPTIME-complete, so a program with many variables per rule can be expensive.
practice: Use Datalog thinking when your problem is a graph with rules about it: dependency closure, access-control inheritance, lineage ("which downstream tables does this column feed?"), reachability, "who can reach this resource?", and static analysis. If the data is in a warehouse, a recursive CTE gives you the basics without a new system; remember to deduplicate with `UNION`, to cap depth (a `depth` column and `WHERE depth < 20`) against runaway cycles, and to push filters into the base case (start from the node you care about instead of computing all pairs and filtering at the end).
For program analysis or large rule sets, use Soufflé or CodeQL. Write relations with typed columns, put the most selective relation first in a rule body, give join-order hints if the planner picks badly, and profile with the tool's own profiler. Keep the set of facts small by extracting only what you need from the source (for code analysis, extract per-function facts rather than every token). value: Time is not the only resource a computation uses. A program also needs memory, and memory differs from time in one important way: it can be reused. A step that has been done cannot be done again for free, but a cell that was used can be erased and used for something else. Space complexity asks how many cells a computation needs as a function of the input size n, and it groups problems into classes by the answer: logarithmic space (L), polynomial space (PSPACE), exponential space, and so on.
This view explains problems that time-based classes describe badly. Playing a generalized game perfectly, checking that a system never violates a temporal property, and finding a plan for a robot are all problems where the number of possible situations is exponential, so exploring all of them takes exponential time. But the search is a depth-first walk over a tree of polynomial depth, and each step needs only the current position, so the memory stays polynomial. Such problems sit in PSPACE, and the hardest of them are PSPACE-complete.
For the layers above, this is the vocabulary for hardness results: classical AI planning is PSPACE-complete, and model checking of LTL formulas is PSPACE-complete, so no one should expect a fast general algorithm for either. The layers below make the theory precise. The Turing machine (L3) defines space as the number of tape cells visited. P versus NP (L3) shows that PSPACE sits above NP, with the question of whether they are equal still open. Computability (L3) supplies diagonalization, the technique of the hierarchy theorems, and asymptotic analysis (L4) defines classes by growth rate such as polynomial.
terms: Space complexity — the number of tape cells (bits of memory) a machine uses as a function of the input length n; the input itself is usually not counted.
L (LOGSPACE) — problems solved by a deterministic machine that uses O(log n) cells of working memory, enough for a few pointers into the input.
PSPACE — problems solved by a deterministic machine that uses a polynomial number of cells, such as n² or n³.
NPSPACE — the same with a nondeterministic machine; Savitch's theorem shows it equals PSPACE.
Configuration — a complete snapshot of a machine: its state, head positions and tape contents; the configuration graph has one node per snapshot and one edge per step.
Space-constructible function — a bound s(n) that a machine can itself compute and mark off using s(n) cells; the hierarchy theorem needs it.
PSPACE-complete — a problem in PSPACE to which every PSPACE problem can be reduced in polynomial time; a fast solution for one would put all of PSPACE in P.
TQBF — true quantified Boolean formula: given a formula with alternating "for all" and "there exists" quantifiers over Boolean variables, is it true? The canonical PSPACE-complete problem.
history: In 1965, Juris Hartmanis and Richard Stearns founded complexity theory with "On the computational complexity of algorithms", defining time classes and proving a hierarchy: more time solves strictly more problems. Stearns, Hartmanis and Philip Lewis ("Hierarchies of memory limited computations", 1965) did the same for space. The space result is cleaner than the time one: any asymptotically larger space bound solves more problems, with no logarithmic gap.
Walter Savitch proved in 1970 that nondeterministic space s can be simulated in deterministic space s², which means that the guessing power of nondeterminism costs at most a square in memory. This is very different from time, where the best known simulation of nondeterminism is exponential and the cost is the P versus NP question. In 1973, Larry Stockmeyer and Albert Meyer proved that TQBF is PSPACE-complete, and with it that deciding whether two regular expressions are equivalent is PSPACE-complete, giving the class its first natural complete problems. The same decade, Even and Tarjan (1976) showed that generalized Hex is PSPACE-complete, and Lichtenstein and Sipser (1980) that Go on an n by n board is PSPACE-hard; Robson (1983) showed that Go with Japanese ko rules is EXPTIME-complete, and Fraenkel and Lichtenstein (1981) that generalized chess is EXPTIME-complete.
In 1987–88, Neil Immerman and Róbert Szelepcsényi independently proved that nondeterministic space is closed under complement (NL = coNL), solving a problem open since the 1960s with a surprising "inductive counting" argument. The same question for NP and coNP remains open. Later applications connected PSPACE to practical verification: Sistla and Clarke (1985) proved that model checking of linear temporal logic is PSPACE-complete, and Bylander (1994) that propositional STRIPS planning is PSPACE-complete. Game puzzles followed: Culberson (1997) showed Sokoban is PSPACE-complete, and Flake and Baum (2002) did the same for Rush Hour.
how: How space is counted. A Turing machine has a read-only input tape and one or more work tapes. Space is the number of work-tape cells ever used. Leaving the input out of the count lets us talk about sublinear space such as O(log n), which is enough for a counter or a pointer into the input. The tape layer gives the ruler; nothing else about a real computer is needed.
Two basic relations link space and time. First, a machine that runs t steps can touch at most t cells, so time bounds space: DTIME(t) is inside DSPACE(t). Second, a machine that uses s cells can be in at most 2^{O(s)} different configurations (each cell holds one of a few symbols, and the head can be in s places), and a machine that halts never repeats a configuration, so it runs for at most 2^{O(s)} steps. This gives the chain L ⊆ NL ⊆ P ⊆ NP ⊆ PSPACE ⊆ EXPTIME. NP is inside PSPACE because a machine can try all 2^n certificates one after another, reusing the same n cells. That is the concrete meaning of "space can be reused". Whether any of the inclusions after L is strict is unknown, but the hierarchy theorems below prove that L ≠ PSPACE and that P ≠ EXPTIME, so at least one is strict.
The space hierarchy theorem. If s₂(n) grows faster than s₁(n) (formally s₁(n) = o(s₂(n))) and s₂ is space-constructible, then some problem is solvable in space s₂ but not in s₁. The proof uses diagonalization, the technique from computability. Build a machine D that, on input ⟨M⟩, simulates M on its own description using at most s₂(n) cells, and does the opposite of what M does; if the simulation would exceed the bound, D gives up and rejects. D differs from every machine that runs within space s₁, because for large inputs D has enough room to simulate it. Since the simulation has only a constant factor of overhead in space, there is no log factor as in the time hierarchy theorem.
Savitch's theorem. A nondeterministic machine with space s(n) ≥ log n has at most N = 2^{O(s)} configurations, and its computation is a path in the configuration graph from the start configuration to an accepting one. Savitch defines a recursive question CANREACH(u, v, k): "can the machine go from configuration u to configuration v in at most 2^k steps?" For k = 0, check directly whether v follows from u in zero or one step. Otherwise, try every configuration w as a midpoint and ask CANREACH(u, w, k−1) and CANREACH(w, v, k−1). The key trick: the two halves run one after the other, and the same memory is reused for both. The depth of the recursion is k = O(s), because paths longer than N steps are not needed. Each level stores three configurations of O(s) bits. The total is O(s) × O(s) = O(s²) bits:
\[ \text{NSPACE}(s(n)) \subseteq \text{DSPACE}(s(n)^2) \]
Consequences: PSPACE equals NPSPACE (a square of a polynomial is a polynomial), and the question "does nondeterminism help for space?" has a fairly small answer, unlike for time. The price is time: at every level there are N choices for the midpoint, and two recursive calls, so the running time is N^{O(s)}, which is 2^{O(s²)}. Savitch's algorithm is a memory-saving device, not a practical one.
Complete problems and the game view. TQBF asks whether a formula such as ∀x₁ ∃x₂ ∀x₃ … φ(x₁, …, x_n) is true. Evaluate it by recursion: to decide ∀x ψ, evaluate ψ with x = 0 and with x = 1 and require both; to decide ∃x ψ, require at least one. The recursion goes n levels deep and each level keeps one bit, so the algorithm uses O(n) space (plus the space to evaluate φ), yet takes 2^n time because it explores the whole tree. This is a game: the ∃ player picks values to make the formula true, the ∀ player picks values to make it false, and the formula is true when ∃ has a winning strategy. Any two-player game with a polynomial number of moves per play fits this form, which is why generalized games are PSPACE-complete. A depth-first search of the game tree needs memory only for the current line of play.
The reduction idea. To show a problem Q is PSPACE-hard, translate TQBF into Q: build, in polynomial time, an instance of Q whose answer equals that of the formula. For Generalized Geography, for example, the graph is built so that each quantifier becomes a choice of a player at a gadget. For the upper bound (Q in PSPACE) show a polynomial-depth recursion. The Turing machine layer enters again here: a generic argument says a PSPACE machine's computation can be written as a formula whose size is polynomial, using the recursive midpoint idea of Savitch to keep the formula short.

example: Evaluate the TQBF  ∀x ∃y (x ∨ y) ∧ (¬x ∨ ¬y)  by hand. The formula says: for every value of x there is a value of y such that exactly one of them is true (an exclusive or). Use the recursion. To decide ∀x, we must succeed for x = 0 and for x = 1.
Case x = 0: decide ∃y of (0 ∨ y) ∧ (1 ∨ ¬y). Try y = 0: (0 ∨ 0) is false, so the whole formula is false. Try y = 1: (0 ∨ 1) = true and (1 ∨ 0) = true, so the formula is true. The ∃ succeeds. The memory is cleared and reused for the next case.
Case x = 1: decide ∃y of (1 ∨ y) ∧ (0 ∨ ¬y). Try y = 0: (1 ∨ 0) = true and (0 ∨ 1) = true, so it is true. The ∃ succeeds. Both cases succeeded, so the ∀ succeeds, and the TQBF is true. At no point did we store more than the current values of x and y and the position in the recursion.
Scale it. With n = 100 variables, the full tree has 2^100, about 10^30 leaves, which no computer can visit. But the stack holds 100 bits of assignment and a few counters, well under one kilobyte. This is the signature of PSPACE: impossible in time, easy in memory.
Now Savitch's recursion in code, for a graph given as a function `edge(u, v)` on N nodes:
```python
def reach(u, v, k):          # path from u to v of length <= 2**k ?
    if k == 0:
        return u == v or edge(u, v)
    for w in range(N):       # try every midpoint
        if reach(u, w, k - 1) and reach(w, v, k - 1):
            return True
    return False

# call: reach(start, goal, ceil(log2(N)))
```
Take N = 2^40 configurations (a machine with about 40 cells of memory). The recursion depth is 40. Each level stores u, v, w and k, about 3 x 40 + 6 = 126 bits. The total is about 40 x 126 = 5,040 bits, under 1 KB, while a direct breadth-first search would have to remember up to 2^40 nodes, about 1 terabit even at one bit per node. The cost is time: each level tries all N midpoints, so the running time is about N^40, astronomically large. Savitch trades time for space as far as it can go.
intuition: Space is a whiteboard that can be erased; time is a clock that only moves forward.
This is why the two resources behave differently. A long computation can reuse a small whiteboard again and again, so exponentially many steps fit in polynomial space, and a search tree of exponential size can be explored while remembering only one path. Nondeterminism, the ability to guess, costs little when you can erase: to simulate all guesses you try them one after another in the same memory, and Savitch's midpoint trick shows how to do it with only a square of the space. In time, the same trick of trying every guess costs a factor that is exponential and cannot be erased.
mistakes: People often think PSPACE means "problems that need a lot of memory". In fact PSPACE problems use only polynomial memory, which is a modest amount; they are called hard because the time they seem to need is exponential. Having small memory and huge running time is the typical shape.
People often think space and time are two names for the same cost. In fact they are linked in one direction only: time t gives space at most t, and space s gives time at most 2^{O(s)}. A problem may need little space and enormous time (TQBF), which is why PSPACE is believed to be larger than P.
People often think NP-complete and PSPACE-complete are about equally hard. In fact PSPACE contains NP, and PSPACE-complete problems are believed to be strictly harder: a polynomial-size certificate is not enough to check a winning strategy, since the strategy must answer every possible opponent move. If P = PSPACE, then P = NP, but the reverse is not known to hold.
People often think "chess is PSPACE-complete" is a fact about real chess. In fact complexity classes describe how cost grows with input size. Real chess on 8 by 8 has a fixed size, so it is a finite problem, solvable in principle by a table; the theorems concern n by n generalizations, where the growth is the point.
friction: The big open questions are all still open. We do not know whether L = NL, whether P = PSPACE, or even whether P = NP, which would be a weaker statement than P = PSPACE. The best separations come from the hierarchy theorems, which are non-constructive diagonal arguments. After 50 years we know that L ≠ PSPACE but not how to prove that any particular natural problem like TQBF is outside P.
Worst-case classification can also mislead in practice. SAT is NP-complete, yet modern solvers handle millions of variables on industrial formulas; TQBF is PSPACE-complete, and QBF solvers handle only much smaller instances, though real planning and verification problems often have structure that makes them easy. A hardness result says nothing about your instance, and a solver may work well for years until an instance with the wrong structure arrives.
practice: Use PSPACE as a warning label. When you see that a task includes alternation ("for all inputs, there exists a plan such that ...", an adversary, or a game), or that it asks to analyze all executions of a succinctly described system, suspect PSPACE-hardness before looking for a polynomial algorithm. Examples: classical planning with a compactly described state space, equivalence of two regular expressions or two NFAs, LTL model checking against a formula, reachability in a system given by a program rather than an explicit graph, and generalized puzzles and games.
When you meet such a problem, switch the goal from exact worst-case solution to a practical technique. Use a SAT or SMT solver, a QBF solver or a bounded search (limit depth k), a symbolic representation (BDDs) so that sets of states are stored compactly, heuristics (A* with a good estimate), abstraction, or decomposition. Planners and model checkers are engineered around exactly this: the state space is exponential, but a good heuristic or compact encoding makes realistic instances tractable.
Memory-bounded search is the engineering form of the space idea. Depth-first search and iterative deepening (IDA*) use memory proportional to the depth, and trade time for space by recomputation. The same trade-off appears in training large neural networks (activation checkpointing recomputes values instead of storing them), in databases (external merge sort), and in streaming algorithms (small sketches of a huge input). When you size a system, ask which resource is the real limit, and whether trading one for the other helps.
tradeoffs: Choose to design for small space (streaming, depth-first, recomputation) when memory, not time, is the scarce resource, such as an embedded device, a huge data stream, or a model whose activations do not fit on the GPU. You give up time: activation checkpointing in training typically adds roughly a third to the step time, and Savitch-style recursion adds far more.
Choose to spend memory to save time (memoization, tables, indexes) when memory is cheap relative to time, as in dynamic programming or caches. You give up the ability to handle inputs whose tables exceed RAM, and a table that no longer fits can be slower than recomputing it.
Choose an exact solver (SAT, SMT, QBF, model checker) when the instance is moderate and a proof is needed. Choose a heuristic or bounded search when instances are large and an approximate or best-effort answer is acceptable. In both cases a PSPACE-hardness result tells you not to promise a worst-case guarantee.

value: Many real systems must decide now, with the future unknown. A cache must evict a page before it knows which page will be asked for next. An autoscaler must decide whether to keep an idle server for another minute without knowing if a request will arrive. A buyer must decide whether to rent a machine for another day or to buy it, without knowing how long the job will last. Algorithms that make each decision using only the past are called online algorithms. The opposite, an offline algorithm, sees the whole input first.
Competitive analysis is the tool for judging them. It does not ask for the average case, which needs a model of the input. It asks: for every possible input sequence, how much worse is the online algorithm than an algorithm that knew the whole sequence in advance (the optimum, OPT)? If the online cost is never more than c times the optimal cost (plus a constant), the algorithm is c-competitive, and c is a guarantee that holds without any assumption about the input. The ski-rental rule "rent until you have spent the price of buying, then buy" is 2-competitive. LRU caching with k pages is k-competitive.
For the layers above: cache eviction policies (LRU, FIFO, and randomized variants) are analyzed this way, and the result explains why LRU is a sound default. Autoscaling and keep-alive decisions are rent-or-buy decisions. Ad systems that must assign each arriving impression to an advertiser with a budget are online matching problems, with a 1 − 1/e guarantee. Bandit algorithms are online decisions with regret, a close cousin. The layers below supply the tools: amortized analysis (L3) gives the potential-function method for proofs, probability (L4) shows how randomness beats every deterministic strategy, and game theory (L4) provides the view of an adversary who picks the worst input after seeing your strategy.
terms: Online algorithm — an algorithm that receives its input piece by piece and must make an irrevocable decision for each piece before seeing the next.
Offline optimum (OPT) — the cost of the best possible solution when the whole sequence is known in advance.
Competitive ratio — the smallest c such that, for every input sequence σ, ALG(σ) ≤ c · OPT(σ) + b, where b is a constant that does not depend on σ.
Adversary — an imagined opponent who chooses the input sequence to make the algorithm look as bad as possible; an oblivious adversary fixes the sequence before the algorithm's random choices, an adaptive one reacts to them.
Paging — the problem of managing a cache with k slots: on each request for a page not in the cache (a fault), load it and, if the cache is full, evict another page.
Ski rental — the basic rent-or-buy problem: renting costs 1 per day, buying costs B once; you do not know how many days you will ski.
Belady's algorithm (MIN) — the optimal offline paging rule: evict the page whose next request is furthest in the future.
Regret — the difference between the total cost of an online algorithm and the cost of the best fixed choice in hindsight; used for online learning.
history: Offline optimal paging was solved by László Belády in 1966: evict the page that will not be used for the longest time. It is optimal but needs the future, so it is only a benchmark. For online strategies, practical systems used LRU and FIFO, backed by experience rather than proof.
Daniel Sleator and Robert Tarjan's 1985 paper "Amortized efficiency of list update and paging rules" turned this into a theory. They compared online algorithms with the offline optimum on worst-case sequences, proved that LRU and FIFO are k-competitive for paging, and that no deterministic algorithm can do better than k. They also showed that the move-to-front rule for self-organizing lists is 2-competitive. Their proofs used potential functions, the same tool as amortized analysis. The name "competitive" was used by Karlin, Manasse, Rudolph and Sleator in 1988, who also studied ski rental and the snoopy caching problem. Manasse, McGeoch and Sleator (1988) introduced the k-server problem, which generalizes paging, and posed the k-server conjecture (a k-competitive algorithm exists in every metric space), still open in general after Koutsoupias and Papadimitriou proved a (2k−1)-competitive bound in 1995.
Randomization gave sharper results. Fiat, Karp, Luby, McGeoch, Sleator and Young (1991) showed that a randomized "marking" algorithm is about 2H_k-competitive (H_k is the k-th harmonic number, close to ln k) against an oblivious adversary, so the factor falls from k to about log k. Karlin, Manasse, McGeoch and Owicki (1994) found the optimal randomized ski-rental ratio, e/(e−1) ≈ 1.58. Karp, Vazirani and Vazirani (1990) gave the Ranking algorithm for online bipartite matching, which achieves 1 − 1/e ≈ 0.63 of the optimal matching, and Mehta, Saberi, Vazirani and Vazirani (2007) extended it to the AdWords problem with budgets, the situation in search and display advertising.
A criticism followed: worst-case ratios can be too pessimistic. LRU is only k-competitive in theory but is very close to optimal on real traces, because real requests have locality. This led to refinements: resource augmentation (give the online algorithm a larger cache), access-graph models, and "beyond worst case" analysis. Later, learning-augmented algorithms (Lykouris and Vassilvitskii, 2018) combined a machine-learned prediction of the future with a guarantee: follow the prediction when it is good, and stay within a constant of the competitive bound when it is wrong.
how: Definition. Let σ be a request sequence. ALG(σ) is the online algorithm's cost and OPT(σ) the cost of the best offline solution. The algorithm is c-competitive if ALG(σ) ≤ c · OPT(σ) + b for all σ. Proving a bound has two halves: an upper bound (an argument that the algorithm never loses by more than c) and a lower bound (a sequence, built by the adversary, that forces any online algorithm to lose by at least c). The game theory layer gives the model: the algorithm and the adversary play a zero-sum game, the adversary moves with full knowledge of the algorithm's rules, and the competitive ratio is the value of the game.
Ski rental. Renting costs 1 per day; buying costs B. If the season lasts d days, OPT pays min(d, B). The break-even rule: rent for B − 1 days, and buy on day B if the season is still on. If d < B, cost is d, which equals OPT. If d ≥ B, cost is (B − 1) + B = 2B − 1 against OPT = B, a ratio of 2 − 1/B, below 2. No deterministic rule does better: any rule that buys on day t is beaten by an adversary who ends the season on that day or just before (buy early and the season is a single day, buy late and the adversary stops right after the purchase). Randomization helps: choose the purchase day from a distribution that puts more weight on later days, and the expected ratio against an oblivious adversary falls to e/(e−1) ≈ 1.58 for large B. Probability is the layer that quantifies this: the algorithm hides its decision from the adversary, who can no longer aim at it.
Paging. A cache holds k pages. If the requested page is present (a hit) there is no cost; otherwise a fault costs 1. Belady's rule is optimal offline. Online, LRU evicts the least recently used page. The proof that LRU is k-competitive uses phases. Split the sequence into maximal blocks that contain k distinct pages each. In one phase, LRU can fault at most k times: once a page has been loaded in the phase, it is among the k most recently used distinct pages for the rest of the phase, so it cannot be evicted before the phase ends. And OPT must fault at least once per phase (with a small correction for the first). Look at the first request of a phase, page p, followed by the k−1 other distinct pages requested in the phase and then the first request of the next phase: these are k distinct pages that differ from p, and the cache holds p and only k−1 other pages, so at least one of them must be missing and cause a fault. So LRU ≤ k × OPT + k. FIFO and many others satisfy the same bound; the proof works for any algorithm that does not evict a page loaded in the current phase (called a marking algorithm).
The lower bound for any deterministic algorithm uses an adversary with k+1 pages in total: always request the one page that the algorithm does not have in its cache, so the algorithm faults on every request. Meanwhile, OPT with Belady's rule, when it faults, evicts the page that will be requested last among the k other cached pages, so it faults at most once in k requests. The ratio is at least k.
Resource augmentation. Sleator and Tarjan also compared LRU with a cache of size k against OPT with a smaller cache of size h ≤ k. LRU's cost is at most k/(k−h+1) times OPT's. If LRU has twice the memory of OPT, k = 2h, the ratio is about 2, no longer growing with the cache size. This is one reason why real LRU caches work well: a modest amount of extra memory makes the worst case mild.
Randomized paging. The marking algorithm works in phases. At the start of a phase, all pages in the cache are unmarked. On each request, the requested page is marked. On a fault, evict a page chosen uniformly at random among the unmarked pages. An analysis of the expected number of faults per phase gives 2H_k, about 2 ln k: for k = 1000 pages that is about 14, not 1000. The best possible randomized ratio is H_k. This beats every deterministic rule because the adversary cannot know which unmarked page will go.
Potential functions and amortization. For algorithms such as move-to-front, there is no clean phase structure, and the proof defines a potential Φ that measures the difference between the algorithm's state and OPT's state (for list update, the number of pairs of items ordered differently). Each request's online cost, plus the change in Φ, is shown to be at most c times OPT's cost for that request. Summed over the sequence, the potential telescopes and the competitive bound follows. This is the same bookkeeping as in amortized analysis.

example: First, ski rental with numbers that look like cloud pricing. Suppose a reserved server costs the equivalent of 100 days of on-demand use (B = 100 days), and you do not know how long a project will need the server. Rule: use on-demand for 99 days; if the project is still running on day 100, reserve. Case 1: the project ends after 40 days. You paid 40, OPT paid 40. Case 2: the project ends after 100 days. You paid 99 + 100 = 199, OPT would have paid 100 by reserving at the start. Ratio 1.99. Case 3: the project runs for 3 years: you paid 199, OPT paid 100, again 1.99. Whatever the project length, you never pay more than about twice the optimum. A rule that bought at day 1 would have a ratio of 100 for a one-day project; a rule that never buys would have a ratio of about 11 for a three-year project (1,095 days against 100).
Now paging with k = 3 and the request sequence 1 2 3 4 repeated six times. Follow LRU. Requests 1, 2, 3 fault (cold cache), and the cache holds {1,2,3}. Request 4 faults and evicts 1 (the least recently used), so the cache holds {2,3,4}. Request 1 faults and evicts 2, then request 2 faults and evicts 3, and so on. Every request faults: 24 faults in 24 requests. Belady's rule on the same sequence: it faults on 1, 2, 3 and 4 (evicting 3, the page used furthest in the future), then hits twice, faults once, hits twice, and so on, about one fault per three requests. A simulation gives 10 faults in 24 requests. The ratio is 24/10 = 2.4, and it tends to 3 = k as the sequence is repeated more times.
Finally, the keep-warm decision in autoscaling. An idle container costs 1 unit per minute to keep, and a cold start costs 30 units (in latency and CPU). Rule: keep an idle container for 30 minutes, then shut it down. If a request arrives at minute 10, you paid 10 and OPT paid 10 (keeping was right). If the next request arrives at minute 31 or later, you paid 30 (waiting) + 30 (cold start) = 60 while OPT paid 30 (shut down immediately and take the cold start): ratio 2. Same as ski rental, because it is ski rental.
intuition: You must commit to each choice before seeing what comes next, so the best you can ask is not to be right, but never to be too wrong compared with someone who could see the future.
The factor of 2 in ski rental has a simple reason. Waiting until you have paid the buy price is the natural moment to act: until then, buying might still turn out to be a waste, and after it, renting would have been. At the break-even moment you have spent exactly what buying would have cost. The adversary can make you wrong only once, and what you lose by being wrong is at most what you have already spent, so the total is bounded by a factor of 2. Competitive analysis turns this idea into a method: find the point where the cost of waiting equals the cost of acting, and act there.
mistakes: People often think a high competitive ratio means the algorithm is bad in practice. In fact the ratio is the worst case over all sequences, including adversarial ones that real workloads never produce. LRU is k-competitive and performs within a few percent of optimal on typical traces, because real requests have locality that the adversary lacks.
People often think competitive analysis is the same as average-case analysis. In fact it is the opposite choice: it makes no assumption about the input and gives a guarantee that holds on every sequence, at the price of pessimism. Average-case analysis assumes a distribution and can be wrong if the workload changes.
People often think randomization always helps. In fact it helps against an oblivious adversary, who commits to the sequence in advance. An adaptive adversary that sees the algorithm's random choices can make randomization useless for some problems. For paging, randomized algorithms do not beat k against adaptive online adversaries.
friction: The model is pessimistic and often too coarse. Many problems with a large worst-case ratio are easy in practice, and the worst-case ratio does not rank algorithms well: LRU and FIFO have the same ratio k, but LRU is usually clearly better on real workloads. This has pushed research toward refined measures (access graphs, locality of reference, smoothed analysis, learning-augmented models) that fit what we see in production.
It also ignores much of what makes systems hard. The classical model has unit costs and a single objective, but real caches have variable object sizes, different fetch costs, concurrent clients, admission control and write costs. Weighted and size-aware variants exist, with weaker or messier guarantees. Competitive ratios say nothing about latency tails, fairness among clients or the cost of the algorithm's own bookkeeping.
practice: Whenever a system decides "keep or drop" or "commit or wait" with an unknown future, look for the ski-rental structure: a recurring cost of waiting and a one-time cost of acting. Set the threshold at the point where waiting has cost as much as acting would. You then have a policy that never loses more than a factor of 2 to the best hindsight choice. Examples: keep a connection or container warm for as long as a cold start costs; buy a reserved or committed-use contract once the on-demand bill for that workload has reached the contract price; spill to disk after memory use has cost as much as the spill; spin on a lock for as long as a context switch would cost, then block (spin-then-block).
For caches, use LRU or an LRU variant as the default, because its worst case is bounded and its typical case is good. Protect it against scans (a ring buffer or a separate segment for sequential access, or an adaptive policy such as ARC or a TinyLFU admission filter) and size it with the resource-augmentation insight in mind: a cache that is a small multiple of the hot set is far better than one that is just equal to it. Measure hit ratio on real traces, and replay them offline against Belady's rule to see how much room is left; if the gap is 3 percent, stop tuning.
Use predictions with safety. If you have a forecast of load, use it to pre-scale or pre-warm, but keep a reactive fallback rule with a known worst-case bound, and compare the two. In ad delivery, pacing and budget allocation are online problems: use a conservative bound (for example, a fraction of the remaining budget per interval) so that a bad forecast cannot exhaust a budget in the first hour.
tradeoffs: Choose a deterministic break-even rule when you want a simple, auditable policy with a clear worst-case guarantee (2 for rent-or-buy). You give up the better expected performance of a tuned or randomized rule, and an observant adversary or a periodic workload can hit the worst case every time.
Choose a prediction-based policy (a forecast, a learned model, historical traces) when the workload is stable and you have data. You give up the worst-case guarantee unless you wrap it in a fallback, as in learning-augmented algorithms, and you take on the cost of keeping the model correct.
Choose a randomized rule when the workload could be adversarial or accidentally periodic, as when a scan hits LRU's worst case. You give up reproducibility and easy debugging (two runs differ), and the guarantee holds in expectation, so a single run can be unlucky.
Choose more resources over a smarter policy when the ratio depends on the size gap: LRU with twice the cache of the optimal policy is within about 2 of it. You pay for the memory, but the guarantee no longer depends on the cache size, and this is often cheaper than engineering a policy.
quiz: What does it mean for an online algorithm to be c-competitive? || For every input sequence σ, its cost is at most c times the cost of the best offline solution for σ, plus a constant. It is a worst-case guarantee that needs no assumption about the input.
Why is break-even ski rental (rent until you have paid B, then buy) 2-competitive, and why can no deterministic rule do better? || If the season is shorter than B you pay exactly the optimum; otherwise you pay about B in rent plus B to buy, which is twice OPT = B. Any fixed purchase day can be punished by an adversary who ends the season right after you buy, or who keeps it going if you wait longer.
Why does LRU fault at most k times per phase while OPT faults at least once per phase? || A phase contains k distinct pages, and a page loaded in the phase stays among the k most recently used distinct pages for the rest of the phase, so LRU loads each page at most once. The first request of a phase, the k−1 other distinct pages and the first request of the next phase give k distinct pages other than the page OPT just served, and OPT has room for only k−1 of them, so it faults at least once.
A cache has k = 4 and the sequence 1 2 3 4 5 repeats 100 times (500 requests). How many faults does LRU make, and roughly how many does OPT make? || LRU faults on every request: 500. Belady's rule faults about once for every k = 4 requests after the start, so about 125 plus the first few cold faults, roughly 130. The ratio is close to 4.
Your team can reserve capacity for 70% of the on-demand price for a full year (reserved cost = 0.7 × 365 days of on-demand). A new service's lifetime is unknown. What simple rule do you apply, and what does it guarantee? || Pay on-demand until the cumulative on-demand spend equals the cost of reserving (about 256 days of use), then reserve. By the ski-rental argument, you never pay more than about twice what you would have paid with perfect knowledge. A forecast of the service's life can improve this, but the rule is a safe fallback.
interview: Explain competitive analysis and why you would use it instead of average-case analysis for a cache or autoscaler. || It bounds the ratio between the online cost and the offline optimum on every input, so the guarantee does not depend on a workload model that may be wrong or may change. For caches and autoscalers the workload is bursty and unknown, so a worst-case bound protects against surprises. The cost is pessimism: the bound may be far from typical performance.
Prove that LRU is k-competitive, or give the idea of the proof. || Split the sequence into phases of k distinct pages. In a phase, LRU faults at most once per distinct page, so at most k times. OPT must fault at least once per phase, because the first request of a phase together with the pages of the next k−1 distinct requests exceed its cache. Hence LRU ≤ k · OPT + k.
Why can no deterministic paging algorithm beat k, and how does randomization change this? || The adversary uses k+1 pages and always requests the one missing from the cache, so the algorithm faults every time, while OPT faults at most once per k requests. A randomized algorithm (marking with a random unmarked page evicted) hides its choice from an oblivious adversary and achieves about 2 ln k expected competitive ratio.
How does online bipartite matching relate to ad allocation, and what guarantee exists? || Impressions arrive one at a time and must be assigned to an advertiser (with a budget) immediately. The Ranking algorithm for matching and its AdWords extension (balancing by the fraction of budget left) achieve a competitive ratio of 1 − 1/e ≈ 0.63 against the optimal offline allocation, and no online algorithm does better in the worst case.

value: Many signals are easier to understand as a sum of pure waves of different frequencies than as a list of samples over time. The discrete Fourier transform (DFT) converts n samples from the time domain into n numbers that say how much of each frequency is present. Done directly from the definition, it takes n² multiplications, about a trillion for one million samples. The fast Fourier transform (FFT) computes exactly the same result in about n log₂ n operations, around 20 million for one million samples, a saving of roughly 50,000 times.
That change is the difference between impossible and routine. Audio and speech systems compute thousands of FFTs per second to build spectrograms. Wi-Fi, 4G and 5G radios use OFDM, where the transmitter runs an inverse FFT to build each symbol and the receiver runs an FFT to read it. Image and video codecs use close relatives (the discrete cosine transform). Many scientific simulations, MRI reconstruction and radar depend on it. And because multiplying in the frequency domain is the same as convolving in the time domain, the FFT multiplies huge polynomials and integers in O(n log n) and speeds up large convolutions in signal processing and in neural networks.
For the layers above, the FFT is a building block. Fourier analysis (L4) says what the transform means and why it is useful; linear algebra (L4) shows the DFT is multiplication by a special matrix and the FFT is a factorization of that matrix; divide and conquer (L3) is the technique that produces the speed; and recurrences (L4) give the cost, T(n) = 2T(n/2) + O(n) = O(n log n).
terms: DFT — the discrete Fourier transform: for samples x₀ … x_{n−1}, the outputs \( X_k = \sum_{j=0}^{n-1} x_j \, e^{-2\pi i jk/n} \) for k = 0 … n−1.
Frequency bin — output index k; it measures the strength of the wave that completes k cycles over the n samples.
Root of unity — a complex number ω with ωⁿ = 1; here \( \omega_n = e^{-2\pi i/n} \), and its powers are n evenly spaced points on the unit circle.
Butterfly — the small operation that combines two values a and b into a + ωb and a − ωb; the FFT is built from n/2 · log₂ n butterflies.
Twiddle factor — the root of unity ω^k multiplied in a butterfly.
Radix — the number of parts a transform is split into at each step; radix-2 splits into 2, radix-4 into 4.
Bit reversal — the permutation that orders the inputs of an in-place radix-2 FFT, where the element at index i goes to the index whose binary digits are i's digits reversed.
Convolution theorem — the Fourier transform of a convolution of two signals is the pointwise product of their transforms.
history: The idea is much older than computers. Carl Friedrich Gauss used a divide-and-conquer method for computing trigonometric series to compute asteroid orbits around 1805, and did not publish it. Several authors found variants later, including Danielson and Lanczos (1942), who used it for X-ray crystallography.
The modern algorithm came from a practical need. In 1963, Richard Garwin, an IBM physicist advising the US President's Science Advisory Committee, wanted a fast way to detect underground nuclear tests from seismic data. John Tukey sketched the method for Garwin, and James Cooley at IBM wrote the program. Cooley and Tukey's paper "An algorithm for the machine calculation of complex Fourier series" appeared in 1965 and was widely used within months. Because it was published openly, it spread within months and the Fourier transform became a routine computing tool.
Further steps made it faster and wider. Rader (1968) and Bluestein (1970) gave methods for lengths that are prime or have large prime factors. Split-radix variants (1984) reduced the operation count. FFTW, written by Matteo Frigo and Steven Johnson at MIT (the paper appeared in 1998), introduced a planner that tries different ways of splitting a transform on the actual machine and picks the fastest, with small hand-generated code pieces called codelets. GPU libraries such as cuFFT apply the same ideas to thousands of threads. In 2019, David Harvey and Joris van der Hoeven proved that integers of n bits can be multiplied in O(n log n) time, using FFTs in many dimensions, completing the line of work that began with Schönhage and Strassen (1971), who first used the FFT for big-integer multiplication in O(n log n log log n).
how: The DFT as a matrix. Write the outputs as X = F x, where F is the n by n matrix with entries \( F_{jk} = \omega^{jk} \) and \( \omega = e^{-2\pi i/n} \). Multiplying a vector by a general n by n matrix costs n² operations. Linear algebra tells us that this matrix is special: its entries come from powers of one number, and those powers repeat. Since ωⁿ = 1, we have \( \omega^{m} = \omega^{m \bmod n} \), and also \( \omega^{n/2} = -1 \). The FFT exploits this redundancy.
The split. Suppose n is even. Separate the input into even-indexed samples (x₀, x₂, x₄, …) and odd-indexed samples (x₁, x₃, x₅, …). The sum for X_k can be split in two:
\[ X_k = \sum_{m=0}^{n/2-1} x_{2m}\,\omega_n^{2mk} \;+\; \omega_n^{k} \sum_{m=0}^{n/2-1} x_{2m+1}\,\omega_n^{2mk} \]
Because \( \omega_n^2 = \omega_{n/2} \), each sum is itself a DFT of size n/2, one of the even samples (call it E_k) and one of the odd samples (O_k). So \( X_k = E_k + \omega_n^{k} O_k \). The E and O transforms have period n/2 in k, so for the second half of the outputs, k + n/2, the same E_k and O_k are used, and \( \omega_n^{k+n/2} = -\omega_n^{k} \) gives \( X_{k+n/2} = E_k - \omega_n^{k} O_k \). One pair of half-size results produces two outputs with one multiplication and two additions: the butterfly.
The recursion. The cost T(n) of a transform of size n is two transforms of size n/2 plus n/2 butterflies for the combination, so T(n) = 2T(n/2) + O(n). The recurrences layer solves this: there are log₂ n levels, each level does O(n) work, so T(n) = O(n log n). Counting exactly: (n/2) log₂ n complex multiplications and n log₂ n complex additions. This is divide and conquer in its clearest form, where the combine step is cheap because the structure of the roots of unity makes half of the work shared.
Iterative form and bit reversal. The recursion can be run in place without function calls. Reorder the input by bit reversal (index 110 in binary goes to 011), then do log₂ n passes. In pass s, combine blocks of size 2^{s−1} into blocks of size 2^s, using butterflies with the appropriate twiddle factors. Each pass reads and writes all n values. A good implementation arranges these passes to use caches well (the cache-oblivious recursive form of FFTW, or Stockham autosort schemes that avoid the bit-reversal permutation), since for large n the transform is limited by memory bandwidth more than by arithmetic.
Other sizes. If n has other factors, split by those: radix-4 takes four quarter-size transforms and has fewer multiplications and memory passes than radix-2. The mixed-radix method handles n = 2^a 3^b 5^c. For prime n, Rader's algorithm turns the transform into a cyclic convolution of length n−1, and Bluestein's algorithm turns any size into a convolution that is computed with power-of-two FFTs, at about 3 times the cost. So every size runs in O(n log n).
Inverse and convolution. The inverse transform is the same algorithm with ω replaced by its conjugate and a final division by n. The convolution theorem says that the cyclic convolution of two sequences a and b equals IFFT(FFT(a) · FFT(b)), where the product is pointwise. Direct convolution costs O(n²); the FFT route costs three transforms, O(n log n). To multiply polynomials p and q of degree d, pad both to size at least 2d+1 (so the cyclic wrap-around does not mix terms), transform, multiply pointwise, inverse-transform. Coefficients of the product are the convolution of the coefficient lists. The same trick multiplies big integers, treating digits as coefficients.
Precision. A floating-point FFT has error growing roughly like ε log n, which is better than the direct sum's error growth, so it is accurate in practice. For exact integer work, number-theoretic transforms replace complex roots of unity with roots of unity modulo a prime (for example 998,244,353 = 119 · 2²³ + 1), avoiding rounding altogether.

example: Compute the 4-point DFT of x = (1, 2, 3, 4) in both ways. Here \( \omega = e^{-2\pi i/4} = -i \), so ω⁰ = 1, ω¹ = −i, ω² = −1, ω³ = i.
Direct definition: X₀ = 1 + 2 + 3 + 4 = 10. X₁ = 1 + 2(−i) + 3(−1) + 4(i) = 1 − 2i − 3 + 4i = −2 + 2i. X₂ = 1 + 2(−1) + 3(1) + 4(−1) = −2. X₃ = 1 + 2(i) + 3(−1) + 4(−i) = −2 − 2i. That is 16 multiplications by roots of unity (many trivial) for n = 4.
FFT: Step 1: split into even samples (x₀, x₂) = (1, 3) and odd samples (x₁, x₃) = (2, 4). Step 2: two-point DFTs. For the even part, E₀ = 1 + 3 = 4 and E₁ = 1 − 3 = −2. For the odd part, O₀ = 2 + 4 = 6 and O₁ = 2 − 4 = −2. Step 3: combine with twiddle factors ω₄⁰ = 1 and ω₄¹ = −i. X₀ = E₀ + O₀ = 10. X₂ = E₀ − O₀ = −2. X₁ = E₁ + (−i)·O₁ = −2 + (−i)(−2) = −2 + 2i. X₃ = E₁ − (−i)·O₁ = −2 − 2i. Same numbers, and the only non-trivial multiplication was one by −i.
Now the scale. For n = 2²⁰ = 1,048,576, the direct method needs n² ≈ 1.1 × 10¹² complex multiplications. The FFT needs (n/2) log₂ n = 524,288 × 20 ≈ 1.05 × 10⁷. At one billion complex multiplications per second, that is about 18 minutes against about 10 ms. A tuned library on a modern CPU core does a million-point FFT in somewhere between a few and a few tens of milliseconds, since memory traffic matters as well.
Last, multiply two polynomials. p(t) = 1 + 2t and q(t) = 3 + 4t. The product has degree 2, so 3 coefficients; pad to length 4. Transform (1, 2, 0, 0) and (3, 4, 0, 0), multiply the 4 pairs of values, and inverse-transform to get (3, 10, 8, 0), meaning 3 + 10t + 8t². Check: (1 + 2t)(3 + 4t) = 3 + 4t + 6t + 8t² = 3 + 10t + 8t². For polynomials with a million coefficients, direct multiplication needs 10¹² steps and the FFT route needs a few times 10⁷.
intuition: To combine many waves quickly, notice that the transform of the whole signal is built from the transforms of its two halves, and the same few rotations are reused again and again.
The DFT matrix is highly repetitive: its n² entries are only n different numbers (the powers of ω). The even and odd halves each see a DFT of half the size, and the second half of the output costs almost nothing because it is the first half with a sign flipped. Repeating this split for log₂ n levels removes the repeated work. The same idea of exploiting symmetry to factor a dense matrix into a product of sparse matrices, each with few non-zeros, appears in many fast transforms.
mistakes: People often think the FFT is an approximation of the DFT. In fact it is the same transform computed in a different order. The outputs are identical in exact arithmetic; only floating-point rounding differs, and it is usually smaller than in a naive sum.
People often think the FFT works only for lengths that are powers of two. In fact the plain radix-2 form needs that, but mixed-radix, Rader and Bluestein algorithms give O(n log n) for every n. Libraries still run faster at sizes with small prime factors (2, 3, 5, 7), so padding to a nice size is a common speed trick.
People often think the FFT gives exact frequencies of a real signal. In fact the DFT assumes the n samples are one period of a repeating signal. If a sine wave does not fit a whole number of periods in the window, its energy leaks into neighboring bins (spectral leakage). Window functions (Hann, Hamming) reduce the leakage, at the cost of a wider main peak. Also, frequencies above half the sampling rate fold back as lower frequencies (aliasing), and no FFT can undo that.
friction: The FFT is often limited by memory, not arithmetic. It performs only about 5 n log₂ n floating-point operations on n values, a ratio of a few operations per byte loaded for each pass, so large transforms run at a small fraction of peak compute. Cache-friendly decompositions, such as the four-step or six-step algorithm that arranges the data as a matrix, transposes, and runs many small FFTs that fit in cache, matter more than counting multiplications. On GPUs the same holds, with shared memory playing the role of the cache.
Distributed FFTs are communication-bound. A transform of data spread across many nodes needs an all-to-all transpose, where every node sends a piece to every other node, and the network, not the processors, decides the speed. This is the main bottleneck in large simulations, and the reason algorithms with less communication are an active research field.
Finally, the theory has a gap. The O(n log n) bound is not known to be optimal: no one has proved that a general DFT needs more than linear time, while the best known lower bounds under restricted models are Ω(n log n).
practice: Never write your own FFT for production. Use a tuned library: FFTW or Intel MKL on CPUs, cuFFT or rocFFT on GPUs, `numpy.fft` or `scipy.fft` (backed by pocketfft) in Python, and `torch.fft` in PyTorch. Create a plan once and reuse it for many transforms of the same size, since planning (searching the fastest strategy) can cost more than a single execution. Choose sizes that factor into small primes, or pad the input; for convolution, pad to at least len(a) + len(b) − 1 to avoid wrap-around.
Use the real-to-complex transforms (`rfft` in NumPy) for real signals. They give n/2 + 1 outputs and about double the speed. For long signals, process in overlapping chunks (overlap-add or overlap-save) so that the FFT sizes stay cache-friendly and memory use stays bounded. For a spectrogram, apply a window to each frame, choose the hop size (often half or a quarter of the frame), and keep the frame size at a power of two such as 512 or 1,024 samples at 16 kHz (32 or 64 ms).
tradeoffs: Choose the FFT route for convolution and correlation when both signals are long (kernels beyond roughly 64 taps, or sequences of thousands of samples). Choose direct convolution when one signal is short, because FFT needs padding and several passes through memory. Choose Winograd or specialized small kernels for the 3 by 3 convolutions of deep networks.
Choose a power-of-two size with zero padding when speed matters and the exact length does not; you waste up to 2 times the length in the worst case. Choose a mixed-radix or Bluestein transform when the length is fixed by the problem (for example 1,000 samples per second of data) and padding would change the meaning.
Choose floating-point FFT for signal processing and approximate results; choose a number-theoretic transform for exact integer or polynomial arithmetic (cryptography, big numbers, error-correcting codes), at the cost of working modulo a special prime and giving up the frequency interpretation.
quiz: What is the key observation that turns the O(n²) DFT into an O(n log n) algorithm? || A DFT of size n can be split into a DFT of the even-indexed samples and a DFT of the odd-indexed samples, each of size n/2, and the full result is combined as E_k + ω^k O_k and E_k − ω^k O_k using n/2 butterflies. Repeating the split log₂ n times gives T(n) = 2T(n/2) + O(n) = O(n log n).
Why does one pair of half-size values give two outputs, X_k and X_{k+n/2}? || The half-size transforms E and O repeat with period n/2, and ω^{k+n/2} = −ω^k. So the same E_k and O_k give X_k = E_k + ω^k O_k and X_{k+n/2} = E_k − ω^k O_k with one multiplication.
How is polynomial multiplication done with the FFT, and why is padding needed? || Transform both coefficient lists, multiply the results point by point, and inverse-transform. The transform computes a cyclic convolution, so both lists must be padded to length at least the degree of the product plus one; otherwise the high coefficients wrap around and add to the low ones.
For n = 1,024, roughly how many complex multiplications does a direct DFT need compared with a radix-2 FFT? || Direct: n² = 1,048,576. FFT: (n/2) log₂ n = 512 × 10 = 5,120, about 200 times fewer (fewer still when trivial multiplications by ±1 and ±i are skipped).
A teammate wants to filter audio with a 21-tap FIR filter by transforming each 1,024-sample block with an FFT. Is that a good idea? || Probably not. A 21-tap filter costs 21 multiply-adds per sample directly, about 21,000 per block, whereas FFT-based filtering needs three transforms and padding; the FFT route pays off only for much longer filters (roughly above 64 to 100 taps, depending on hardware).
interview: Derive the radix-2 FFT and state its complexity. || Split the sum into even and odd indexed terms, which gives two DFTs of size n/2: X_k = E_k + ω^k O_k and X_{k+n/2} = E_k − ω^k O_k. The cost satisfies T(n) = 2T(n/2) + Θ(n), so T(n) = Θ(n log n): about (n/2) log₂ n complex multiplications. The structure is a divide-and-conquer recursion that shares work through the symmetry of roots of unity.
How would you multiply two large integers or polynomials in O(n log n), and what are the pitfalls? || Treat the digits or coefficients as sequences, pad to a power of two at least as long as the product, take FFTs, multiply pointwise, take the inverse FFT, round, and propagate carries. Pitfalls: floating-point rounding when the numbers are large (use small digit chunks or a number-theoretic transform), and cyclic wrap-around if padding is too short.
Why is a large FFT usually memory-bound, and how do libraries cope? || It does only a few operations per element per pass, and every pass touches all n values, so cache misses dominate. Libraries restructure the computation (recursive cache-oblivious order, the four-step algorithm with transposes, Stockham auto-sort), use SIMD, and pick the best plan by measurement at run time.
What causes spectral leakage and aliasing, and how are they handled? || Leakage: the DFT assumes the window is periodic, so a sine that does not complete a whole number of periods has discontinuities at the edges and spreads across bins; use a window function. Aliasing: frequencies above half the sampling rate fold into lower bins during sampling; use an anti-aliasing low-pass filter before sampling, because it cannot be fixed afterwards.

@@ workspan
value: How fast will a program run if you give it 8, 64 or 4,000 processors? The answer is not in the number of operations alone. Two numbers describe a parallel algorithm well. The work T₁ is the total number of operations, the time on one processor. The span T∞ is the length of the longest chain of operations that must run one after another, the time on an unlimited number of processors. A sum of one million numbers has work of about 10⁶ and, if done as a tree of additions, span of about 20.
These two numbers give hard limits and a good estimate. No machine with p processors can finish before T₁/p (the work must be shared out) or before T∞ (the chain cannot be shortened). And a greedy scheduler, one that never leaves a processor idle when work is ready, finishes within T₁/p + T∞, so it is never more than twice the best possible time. Work and span turn "is this parallel?" into arithmetic: parallelism = T₁/T∞ tells you how many processors can be kept busy.
For the layers above this is the design language. A work-stealing runtime (Cilk, Rayon, Java's ForkJoin, Tokio, TBB) is the scheduler that achieves the bound. GPU kernels such as reduce and scan are designed to have tiny span. MapReduce and Spark stages are low-span patterns: map has span 1, and the shuffle plus reduce make the tree. Pipeline bubbles in model training are a span cost. The layers below supply the tools: big-O (L3) is how both numbers are expressed, graph theory (L4) provides the DAG whose longest path is the span, and Amdahl's law (L4) is the same idea with the span as the serial fraction.
terms: Work (T₁) — the total number of operations of the computation; the running time on a single processor.
Span (T∞) — the length of the longest dependency chain, also called the critical path or depth; the running time with unlimited processors.
Parallelism — the ratio T₁/T∞, the largest speedup any number of processors could give.
Computation DAG — a directed acyclic graph with a node for each small step and an edge for each dependency; work is the number of nodes and span is the longest path.
Strand — a sequence of steps with no parallel split inside it, drawn as one node or chain in the DAG.
Fork-join — a model where a task spawns subtasks that run in parallel (fork) and waits for them to finish (join).
Greedy scheduler — a scheduler that never leaves a processor idle while a ready step exists.
Speedup and linear speedup — speedup is T₁/T_p; it is linear when it grows in proportion to p.
Grain size — the size of the smallest task worth running in parallel; below it, scheduling costs more than the task.
history: Early parallel computers in the 1970s and 1980s led to theoretical models of parallel machines. The PRAM (parallel random-access machine, Fortune and Wyllie, 1978) imagined many processors sharing one memory with no cost for access, and was used to design algorithms in terms of time and number of processors. It was clean but did not match real machines.
Two results from scheduling theory gave the bounds we use. Ronald Graham (1966, 1969) analyzed list scheduling and showed that a greedy schedule is within a factor 2 of optimal. Richard Brent (1974) proved that a computation with work T₁ and span T∞ can be run on p processors in time at most T₁/p + T∞ (more exactly (T₁ − T∞)/p + T∞) with a simple simulation of the circuit level by level. Eager, Zahorjan and Lazowska (1989) used similar reasoning for speedup bounds.
The practical turn came with the language Cilk at MIT, led by Charles Leiserson, in the 1990s. Cilk (Blumofe, Joerg, Kuszmaul, Leiserson, Randall and Zhou, 1995; Cilk-5 by Frigo, Leiserson and Randall, PLDI 1998) added two keywords, `spawn` and `sync`, to C, so programmers wrote ordinary recursive code and the runtime scheduled it. Robert Blumofe and Leiserson (FOCS 1994, JACM 1999) proved that randomized work stealing runs a fully strict computation in expected time T₁/p + O(T∞), within a constant of the greedy bound and with provably small communication. Guy Blelloch's work on the NESL language and on the scan (prefix sum) primitive (1990) showed that many problems have low-span algorithms, and introduced the work-depth framework used in textbooks. The idea reached mainstream through Intel TBB (2006), OpenMP tasks (3.0, 2008), Java's ForkJoin framework (Java 7, 2011, by Doug Lea), Rust's Rayon (2015) and many GPU kernel libraries.
how: The model. Think of a program run as a DAG. Each node is a step that takes one unit of time; each edge is a dependency, "this step needs the result of that step". Sequential code is a chain. A fork creates two branches that can run in parallel, and a join merges them. The graph theory layer gives the vocabulary: work T₁ is the number of nodes; span T∞ is the number of nodes on the longest path. For a sum of n numbers computed by a balanced tree of additions, T₁ = n − 1 and T∞ = ⌈log₂ n⌉. For a loop that adds the numbers one by one into a single accumulator, T₁ is the same, but T∞ = n − 1: every addition depends on the previous one.
Two lower bounds. With p processors, each does at most one step per time unit, so the time is at least T₁/p (the work law). And no schedule can beat the longest chain, so the time is at least T∞ (the span law). Together, T_p ≥ max(T₁/p, T∞). The speedup T₁/T_p can never exceed p, and can never exceed the parallelism T₁/T∞. This is Amdahl's law seen in more detail: if a fraction f of the work is serial, the span is at least f·T₁, so the speedup is at most 1/f. The span captures every kind of serial constraint, not only a single serial section.
The upper bound. A greedy scheduler runs, at each time step, as many ready steps as there are free processors (up to p). Count the time steps in two kinds. A complete step has p ready steps, so p units of work are done; there are at most T₁/p complete steps. An incomplete step has fewer than p ready steps, so it runs all of them; each such step reduces the length of the remaining longest path by one, so there are at most T∞ incomplete steps. Hence T_p ≤ T₁/p + T∞. Since the lower bound is max(T₁/p, T∞) and the upper bound is the sum of the same two numbers, the greedy time is within a factor of 2 of optimal. When p is much smaller than the parallelism (T₁/T∞ ≫ p, called parallel slackness), the T₁/p term dominates and the speedup is nearly linear.
Making the schedule real: work stealing. A central queue of ready tasks becomes a bottleneck, so runtimes use work stealing. Each worker thread has its own double-ended queue (deque) of tasks. A worker pushes and pops tasks at one end (the bottom), so it runs depth-first, just like a sequential program, which keeps locality and memory use small. When its deque is empty, the worker becomes a thief and takes a task from the other end (the top) of a random victim's deque. The oldest tasks are usually the biggest (closest to the root of the recursion), so one steal moves a large chunk of work. The number of steals is O(p · T∞) in expectation, so the cost of communication is bounded by the span, not by the work. This is how the runtime approaches T₁/p + O(T∞).
Designing algorithms for low span. The usual tools: (1) divide and conquer with independent halves (fork-join), which gives a recursion tree whose depth is the span; (2) tree reductions, which replace a chain of dependent additions by a tree; (3) parallel prefix (scan), which computes all running sums with work O(n) and span O(log n) by an up-sweep and a down-sweep over a tree (Blelloch's scan); (4) parallel merge, so that merge sort has span polylogarithmic and not linear. With a sequential merge, merge sort has span Θ(n), because the top-level merge touches all elements one by one and parallelism is only about log n; with the textbook parallel merge the span is Θ(log³ n). (5) Avoid shared mutable state; if two tasks write the same location they either race or must be ordered, and the order adds to the span.
Work efficiency and grain size. A parallel algorithm is work-efficient if its work is the same as the best sequential algorithm, up to a constant. Parallel prefix sum has work O(n), as the sequential one. An algorithm with lower span but much more work (for example computing all pairs to find a maximum in constant span with n² work) is rarely useful, because with p ≪ n² processors the T₁/p term is large. In practice each task has overhead (creating it, queueing it, a possible steal), commonly tens to hundreds of nanoseconds, so tasks must do enough work to pay for it. Standard practice is a sequential cutoff: parallel recursion until subproblems have, say, 1,000 to 10,000 elements, then plain sequential code. The model assumes unit costs and free communication, so it says nothing about memory bandwidth, cache misses or synchronization costs, which are the real limits on large machines.

example: Sum one million numbers on p = 8 processors using a tree reduction with a sequential cutoff. Work T₁ ≈ 10⁶ additions. Span T∞ ≈ log₂(10⁶) ≈ 20 additions, plus the cost of splitting. Lower bound: max(10⁶/8, 20) = 125,000. Upper bound (greedy): 125,000 + 20 = 125,020. So the time is about 125,000 additions, a speedup of almost 8. The span is irrelevant here. On p = 10,000 processors, the work term is 100 and the span is 20, so the time is between 100 and 120 and the speedup is about 8,300 to 10,000: the span now matters. Parallelism is 10⁶/20 = 50,000, so with 50,000 processors we would run at the span limit of 20, but more processors would give nothing.
Compare the chain version, where every addition waits for the previous one. T₁ = 10⁶, T∞ = 10⁶. Parallelism is 1. No number of processors helps. This is the same total work, but the dependency structure removes all parallelism, and this is what the span measures.
Now the parallel prefix sum (scan), which looks sequential: output[i] = sum of input[0..i−1]. Take the input (3, 1, 7, 0, 4, 1, 6, 3), n = 8. Up-sweep (reduce on a tree, keeping partial sums in place): level 1 adds neighbors, giving partial sums 4 (3+1), 7 (7+0), 5 (4+1), 9 (6+3); level 2 adds pairs of these, giving 11 and 14; level 3 gives the total 25. Down-sweep: put 0 at the root, then at each node pass down the value from above to the left child and (the value from above + the left child's old sum) to the right child. The result is the exclusive prefix sums (0, 3, 4, 11, 11, 15, 16, 22). Work: 7 additions up and 7 down, O(n). Span: 3 levels up and 3 down, 2 log₂ n. For n = 10⁶: work about 2 × 10⁶ operations and span about 40. Scan is the building block of stream compaction, radix sort, and many GPU algorithms.
The code for a fork-join sum shows the shape (Python-like pseudocode with `spawn` and `sync`):
```text
def psum(a, lo, hi):
    if hi - lo <= 4096:              # sequential cutoff (grain size)
        return sum(a[lo:hi])
    mid = (lo + hi) // 2
    left = spawn psum(a, lo, mid)    # may run on another worker
    right = psum(a, mid, hi)         # runs here
    sync                             # wait for the spawned task
    return left + right
```
For n = 10⁶ and a cutoff of 4,096, the recursion ends in about 256 leaf tasks of roughly 4,000 elements, each costing about 4 microseconds of arithmetic. A task-creation overhead of 100 ns is 2.5 percent of that, which is why the cutoff is chosen as it is. The span is the longest path through the recursion: about 8 levels of splitting, one leaf of 4,096 additions, and 8 levels of combining, so roughly 4,110 operations, far from the work of 10⁶. The parallelism is about 240.
intuition: Work is how much total effort the job needs; span is how long the longest chain of waiting is; with enough hands the job takes as long as the longest chain, and with few hands as long as the total effort divided by the hands.
The model works because of one simple fact: a processor with nothing ready to do is wasted, and a greedy scheduler wastes a processor only when the program itself has little parallelism at that moment. Each such moment shortens the critical path by one. So the total time is the work spread over p processors, plus at most one extra step for each step on the critical path.
mistakes: People often think more processors always help. In fact the speedup is capped by the parallelism T₁/T∞. A program with work 10⁹ and span 10⁶ has parallelism 1,000, and 10,000 processors give a speedup of about 1,000 at most, not 10,000.
People often think a parallel algorithm should minimize span at any cost. In fact an algorithm with lower span but much more work is usually worse on real machines, where p is far smaller than the parallelism. Work efficiency matters first; then reduce span until the parallelism is a few times larger than the number of processors.
People often think the model predicts exact run times. In fact it ignores memory bandwidth, cache effects, synchronization cost and load imbalance. A task graph with perfect parallelism can still run at one quarter of the predicted speed because eight threads share one memory channel. The model tells you the best shape of the algorithm; measurement tells you the speed.
friction: Real machines are not the model. Communication is not free: moving data between sockets or nodes costs far more than an arithmetic step, and in distributed systems a shuffle or all-reduce moves data over a network with latency measured in microseconds to milliseconds. The work-span model counts operations and says nothing about bytes moved. Extensions add the cost of cache misses (parallel cache-oblivious analysis) or communication (the LogP and BSP models), but they are harder to use.
Scheduling overhead and imbalance matter. Tasks have a cost, steals have a cost, and irregular work (graph algorithms, sparse data, skewed keys) can leave one worker with a huge task while others wait. In Spark, a single key with 50 percent of the data makes the span of the stage equal to half the work: one task does half the job. The fix is at the algorithm level (salting keys, splitting the skewed key, two-phase aggregation).
practice: Before parallelizing, write down the work and span of your algorithm, on paper, in big-O terms. If the parallelism T₁/T∞ is below your core count times a few, restructure first. Typical fixes: replace a sequential accumulation by a tree reduction (every parallel framework has `reduce`, with an associative operator), replace a sequential scan by a parallel prefix, and replace "append to a shared list" by "each task builds its own result, then combine".
Use a library that implements work stealing and do not manage threads by hand: Rayon (`par_iter`, `join`) in Rust, ForkJoinPool and parallel streams in Java, TBB in C++, OpenMP tasks, Go's runtime scheduler for goroutines. Choose a grain size by measurement: try cutoffs from 100 to 100,000 elements and plot the time. Aim for tasks that take at least 10 to 100 microseconds so that overhead stays under a few percent.
Check scaling honestly. Run with 1, 2, 4, 8 threads and compute the speedup T₁/T_p. If it flattens early, look in this order: lock contention or shared atomic counters (span), memory bandwidth, false sharing between threads that write nearby addresses, load imbalance, and the sequential parts (input parsing, final merges). In data systems, a Spark stage's span is its slowest task, so compare the maximum and median task time in the Spark UI before adding executors, and prefer `treeAggregate` or two-phase aggregation to collecting everything on one node.
tradeoffs: Choose a work-efficient algorithm with moderate span (parallelism of a few times the core count) over a minimum-span algorithm that does much more work, when p is in the tens or hundreds. You give up asymptotic elegance; you gain real speedup, because the T₁/p term dominates on real hardware.
Choose to minimize span when p is very large (thousands of GPU threads, large clusters) and the extra work is a small factor. At that scale, the work term shrinks and the critical path decides the time, so a scan or a tree reduction beats a simple chain even if it costs 2 times the arithmetic.
Choose dynamic scheduling (work stealing) for irregular and recursive work, since it balances automatically and gives provable bounds. Choose static partitioning (equal chunks, one per thread) for regular loops with uniform cost and good locality, because it has no scheduling overhead and predictable placement; you give up balance if the cost per item varies.

interview: Explain work and span and why they predict scalability better than "the fraction of serial code". || Work is total operations, span is the longest chain of dependent operations. How does work stealing achieve the T₁/p + O(T∞) bound? || Each worker runs its own tasks depth-first from its deque, which keeps locality. Diagnose with hardware counters and by varying thread count and grain size.

value: Many important problems have far too many possible answers to try them all: the order in which a delivery van visits 100 stops (about 10¹⁵⁵ distinct tours), the placement of millions of cells on a chip, the assignment of 5,000 containers to 300 machines, a timetable for a university. Exact methods exist for some of them, but they can take unbounded time. Local search takes a different path. Start from any valid solution, define a small set of changes that give "neighboring" solutions (swap two stops, move one container), and keep moving to a better neighbor. It always has a valid answer, it can be stopped at any time, and it often gives a very good solution in seconds.
The weakness is that greedy improvement stops at a local optimum: a solution with no better neighbor, which may be far worse than the best solution overall. Simulated annealing fixes this with one rule. A move that makes the solution worse by Δ is accepted with probability e^{−Δ/T}, where T is a "temperature" that starts high and is lowered slowly. At high T the search wanders freely and escapes poor valleys; as T falls it becomes greedy and settles into a deep one.
For the layers above, local search is the engine inside many practical solvers: vehicle routing in Google OR-Tools, timetabling, chip placement, and the rebalancers that improve the placement of workloads or shards by many small moves. Genetic algorithms are local search carried out on a population. The layers below explain it: optimization (L4) frames the problem as minimizing a cost over a space; Markov chains (L4) show that annealing is a random walk over solutions with a known long-run distribution; and thermodynamics (L5) is the source of the acceptance rule and the cooling idea.
terms: Solution space (search space) — the set of all candidate solutions, such as all orderings of the stops.
Objective (cost, energy) — the number to minimize, such as the length of the tour.
Neighborhood — the set of solutions reachable from the current one by one small move; its definition is the main design choice.
Local optimum — a solution with no neighbor that is better; a global optimum is the best solution overall.
Move and delta — a move changes the solution a little; the delta is the change in cost, which should be computed without evaluating the whole solution again.
Temperature (T) — a parameter that sets how willing the search is to accept worse moves; high means very willing.
Cooling schedule — the rule by which T is lowered over time, for example T ← 0.995 · T after each step.
Metropolis rule — accept an improving move always, and a worsening move with probability e^{−Δ/T}.
history: Simple hill climbing is as old as optimization. For the traveling salesman problem, Georges Croes (1958) described the 2-opt move: remove two edges of the tour and reconnect the pieces the other way, which reverses a segment. Shen Lin and Brian Kernighan (1973) generalized it to variable-depth moves, and their heuristic (later improved by Helsgaun's LKH) found tours within a few percent of optimal on large instances.
The annealing idea came from physics. In 1953, Nicholas Metropolis, Arianna and Marshall Rosenbluth, Augusta and Edward Teller published an algorithm to sample the states of a system of particles at a fixed temperature, where a random change is accepted with probability e^{−ΔE/kT} if it raises the energy. In 1983, Scott Kirkpatrick, Daniel Gelatt and Mario Vecchi at IBM published "Optimization by simulated annealing" in Science, noticing that the same procedure, with a slowly falling temperature, solves hard optimization problems; they applied it to the placement of circuit components and wiring. Vladimír Černý had found the same method independently in 1985 for the traveling salesman. Stuart and Donald Geman (1984) proved convergence for annealing in image restoration with a logarithmic cooling schedule, and Bruce Hajek (1988) gave the exact condition: with T_k = c / ln(k+1), annealing converges to a global optimum if c is at least the height of the deepest "valley" that is not a global minimum. That schedule is far too slow to use, so practical annealing uses faster cooling and loses the guarantee.
Many variants followed. Tabu search (Fred Glover, 1986) forbids returning to recently visited solutions, using memory to get out of local optima. Iterated local search, guided local search and variable neighborhood search shake or reshape the problem when stuck. Large neighborhood search (Paul Shaw, 1998) destroys a large part of the solution and rebuilds it with an exact or greedy method; it is widely used in vehicle routing and scheduling. Genetic algorithms (Holland, 1975) keep a population and recombine solutions. Practical tools such as TimberWolf (Sechen and Sangiovanni-Vincentelli, 1985) for chip placement, and OR-Tools' routing solver, which combines first-solution heuristics with local search and metaheuristics, bring these methods to production.
how: The basic local search loop has four parts: a representation of a solution, an objective function, a neighborhood, and a rule for choosing the next solution. Hill climbing evaluates the neighbors and moves to the best (steepest descent) or to the first improving one (first improvement); it stops when none improves, at a local optimum. The optimization layer supplies the language: the problem is minimizing f(x) over a discrete set, and local search is descent on a landscape whose "downhill" is defined by the neighborhood, not by a derivative.
The neighborhood is the key design decision. For a tour, 2-opt (reverse a segment) has about n²/2 neighbors; for scheduling, swap two jobs or move one job; for bin packing or container placement, move one item to another bin or swap two items. A good neighborhood has three properties: moves are cheap to evaluate (a delta in O(1) or O(log n), such as the 2-opt change d(a,c) + d(b,d) − d(a,b) − d(c,d), which looks at four distances instead of recomputing the length of the whole tour), moves keep the solution valid, and any solution can be reached from any other through a sequence of moves (so the search can in principle go anywhere).
Why local optima exist. The landscape of a hard problem has many valleys. A hill climber falls into the nearest one and stays. Restarting from random solutions many times (random restarts) samples many valleys and keeps the best, which works if valleys are shallow and plentiful. Annealing tries to do better by letting one run escape valleys.
Simulated annealing. Pick a random neighbor y of the current solution x. Compute Δ = f(y) − f(x). If Δ ≤ 0, accept. Otherwise accept with probability e^{−Δ/T}, and reject otherwise. After each step (or each batch of steps) lower T. The number is important: at T = 100 a move that worsens the cost by 10 is accepted with probability e^{−0.1} ≈ 0.90; at T = 20 with 0.61; at T = 5 with 0.14; at T = 2 with 0.0067; at T = 1 with 0.000045. So early in the run almost anything is accepted and the search explores; late in the run only improvements and tiny worsenings are accepted, which is greedy descent with a little noise. The scale of T must match the scale of typical Δ, and a common way to choose the starting T is to pick it so that about 50 to 80 percent of worsening moves are accepted at first.
Why it is correct: the Markov chain view. The sequence of solutions is a Markov chain: the next state depends only on the current one. At a fixed temperature T, with a symmetric proposal of neighbors, the Metropolis rule satisfies detailed balance with respect to the Boltzmann distribution π_T(x) ∝ e^{−f(x)/T}. If the chain is irreducible (any solution reachable from any other), it converges to that distribution. At high T the distribution is nearly uniform, so the chain explores everywhere. As T → 0 the probability concentrates on the global minima. Annealing moves T slowly enough that the chain stays near the distribution for the current T, which pushes it toward the minima. This gives the theory the Markov chain layer provides, including Hajek's theorem on logarithmic cooling. From thermodynamics comes the physical picture: a metal cooled slowly forms a regular low-energy crystal, while one cooled quickly (quenched) freezes into a disordered state with defects, the equivalent of a local optimum.
Practical cooling. The common schedule is geometric: T_{k+1} = α T_k with α between 0.95 and 0.999, applied after a fixed number of moves at each temperature, from a T₀ where most moves are accepted to a final T where almost none are. Total run time sets the quality: doubling the number of steps gives a modest improvement in the final cost, and more time always helps, which makes annealing easy to tune against a time budget. Many implementations keep the best solution seen so far, since the current solution at the end may not be the best of the run. Reheating, restarts from the best solution, and adaptive schedules that change T according to the acceptance rate are common improvements.

example: First a tiny TSP. Four cities at A(0,0), B(4,0), C(0,3), D(4,3). Start with the tour A-B-C-D-A. Its length is AB 4 + BC 5 + CD 4 + DA 5 = 18. Try the 2-opt move that removes edges (B,C) and (D,A) and reconnects with (B,D) and (C,A): the new tour is A-B-D-C-A. The delta is the new edges minus the old edges: (BD 3 + CA 3) − (BC 5 + DA 5) = 6 − 10 = −4. The new length is 14, which is the optimal tour (a rectangle). The delta was computed from four distances, not from the whole tour.
Next, the same idea at a size where it matters. In a small experiment with 100 random cities in a unit square and 2-opt moves, on three different random instances, A random tour had length about 53 to 57. Hill climbing with 2-opt (accept only improvements, 400,000 random proposals) ended at about 8.6 to 9.2. Simulated annealing with the same moves and the same number of proposals, with T falling geometrically from 0.3 to 0.001, ended at about 8.2 to 8.5, which is roughly 5 to 8 percent shorter. The improvement is modest in relative terms, but the shape is typical: local search removes about 85 percent of the excess in a fraction of a second, and annealing buys the next few percent by paying more time. (These numbers come from one small experiment on random instances, not from a benchmark.)
The core of the annealing loop is short:
```python
import math, random

def anneal(tour, dist, T0, T1, steps):
    n, T = len(tour), T0
    cool = (T1 / T0) ** (1.0 / steps)         # geometric cooling
    cost_now = cost(tour, dist)       # full tour length, computed once
    best, best_cost = tour[:], cost_now
    for _ in range(steps):
        i, j = sorted(random.sample(range(1, n), 2))
        a, b = tour[i-1], tour[i]
        c, d = tour[j], tour[(j+1) % n]
        delta = dist[a][c] + dist[b][d] - dist[a][b] - dist[c][d]
        if delta < 0 or random.random() < math.exp(-delta / T):
            tour[i:j+1] = reversed(tour[i:j+1])
            cost_now += delta
            if cost_now < best_cost:
                best, best_cost = tour[:], cost_now
        T *= cool
    return best, best_cost
```
The reversal costs O(n) in this version; production code uses a doubly linked list or a balanced structure to make a move cheaper, or chooses segments of limited length. The acceptance test and the cooling are the whole of annealing.
Last, a systems example. A rebalancer has 300 machines and 5,000 containers, each with CPU and memory demand. The cost is the sum over machines of (load − average)², plus a penalty for overload. The move is "move one container to another machine"; the delta involves only two machines, so it is O(1). A greedy rebalancer makes moves that improve the cost and stops, usually at a decent state. Adding annealing, or restricting to a small number of moves per hour because each move costs a restart, are both easy extensions, since only the cost function and the move set change.
intuition: Rolling a ball downhill gets it stuck in the first valley; shaking the whole landscape at the start, and less and less as time goes on, lets the ball hop out of shallow valleys and settle in a deep one.
The idea is natural because worse moves are sometimes the only way to a better place, but they must become rarer as the search learns where the good region is. The Boltzmann acceptance rule gives a clear dial for that, and a neat rule: small worsenings are accepted often, and large ones rarely, so the search climbs over low hills easily and over high hills only when it is hot.
mistakes: People often think simulated annealing finds the global optimum. In fact it is a heuristic. The convergence theorem needs cooling so slow (logarithmic in time) that it is worse than exhaustive search, so real runs give good solutions with no guarantee of optimality.
People often think the temperature is a physical quantity that can be set by looking at the system. In fact it is a scale in the units of your cost function. A T of 1 is cold for costs in thousands and hot for costs in millionths. Choose the starting value from the typical size of Δ (accept 50 to 80 percent of worsening moves at the start) and the final value so that almost none are accepted.
People often think a bigger neighborhood is always better. In fact a bigger neighborhood has better local optima but costs more per step; a tiny neighborhood is fast but gets stuck in poor optima. The right size depends on the cost per evaluation, and the best results often come from a mix of cheap and large moves, as in variable neighborhood search and large neighborhood search.
People often think local search needs no care about validity. In fact most practical difficulty is in constraints. If a move can break a constraint (a capacity, a time window), you either avoid such moves, repair the solution afterwards, or add a penalty to the cost; a penalty weight that is too small gives invalid answers and one that is too big blocks all useful moves.
friction: There is no guarantee of quality, and it is hard to know how far you are from the optimum. Without a lower bound (from an exact method, linear programming relaxation or a dual bound) you cannot say whether 8.3 is 1 percent or 10 percent above optimal. In practice teams compare against a baseline, run longer, or run several seeds and look at the spread.
Time per move dominates. Long runs need cheap deltas. A move that requires recomputing the full cost, or a data structure update that costs O(n), reduces the number of moves per second from millions to thousands and ruins the quality. Much of the engineering in serious solvers goes into incremental evaluation and fast move generation.
practice: Start with the simplest thing: a valid starting solution from a greedy rule, a neighborhood with O(1) deltas, and hill climbing with random restarts. Measure the objective. Only then add annealing, which usually needs a few lines: an acceptance test and a cooling schedule. Keep the cost function and the move generator separate from the search loop, so that you can swap methods.
Always compute deltas incrementally and test them: after every thousand moves in a debug build, recompute the full cost and check that it equals the running total. Wrong deltas are the most common bug and silently produce plausible, wrong results. Keep the best solution seen, and make runs repeatable with a seed.
Choose the schedule from the data. Sample random moves at the start to find the typical positive Δ, set T₀ so that about 60 percent are accepted, and set the final T near 1 percent of the smallest meaningful cost difference. Use a time budget: set the number of steps from the time you have, and compute the cooling factor from it, as in the code above. Plot the cost and the acceptance rate against time; if the cost is still falling steeply at the end, you need more time or slower cooling.
tradeoffs: Choose plain hill climbing with random restarts when the landscape is simple, evaluations are very cheap, and you want a baseline in an hour of work. You give up the ability to escape deep local optima, and gain simplicity and speed.
Choose simulated annealing when the landscape has many local optima, moves are cheap, and you have a time budget of seconds to hours. You give up predictability and must tune the schedule; you gain a method that is easy to implement and that improves steadily with time.
Choose tabu search or large neighborhood search when annealing's random moves waste time, as in tightly constrained routing and scheduling, where a good move needs a lot of structure. You give up simplicity and take on a more complex implementation and memory; you gain stronger results on difficult instances.
Choose an exact solver (MIP, CP-SAT) when instances are small enough to solve to optimality, when a proof or bound is needed (money, safety, contracts), or when constraints are complex. Choose local search when instances are huge, the time limit is strict, or "within 3 percent of the best known" is good enough.
quiz: What is a local optimum, and why does hill climbing get stuck there? || A local optimum is a solution with no better neighbor under the chosen move set. Hill climbing accepts only improving moves, so once it reaches one, every move makes the solution worse and the search stops, even if a much better solution exists elsewhere.
What is the Metropolis acceptance rule, and what does the temperature control? || Accept an improving move always; accept a move that worsens the cost by Δ with probability e^{−Δ/T}. The temperature sets how likely worsening moves are: high T accepts almost everything (exploration), low T accepts almost nothing (greedy descent).
Why does simulated annealing converge to the Boltzmann distribution, and why does that help? || At fixed T, the Metropolis rule satisfies detailed balance for π(x) ∝ e^{−f(x)/T}, so an irreducible chain converges to it. As T falls, this distribution concentrates on low-cost, eventually globally optimal, solutions, so slow cooling moves the chain toward them.
At T = 5, how likely is a move that worsens the cost by 10, and by 1? What happens at T = 0.5? || e^{−10/5} = e^{−2} ≈ 0.135, and e^{−1/5} = e^{−0.2} ≈ 0.82. At T = 0.5: e^{−20} ≈ 2 × 10⁻⁹ for Δ = 10, and e^{−2} ≈ 0.135 for Δ = 1, so only tiny worsenings are still accepted and the search is nearly greedy.
You must rebalance 5,000 containers over 300 machines nightly within 10 minutes, and a plain greedy pass leaves uneven loads. How would you improve it? || Use local search with the move "relocate one container" (O(1) delta on two machines), add annealing or restarts with a time budget, penalize overload in the cost, limit the number of moves because each costs real work, keep the best solution, and compare with a lower bound such as the average load to see how much room is left.
interview: When would you use local search or simulated annealing instead of an exact solver? || When the problem is NP-hard and large, the time budget is fixed, near-optimal is good enough, the cost is awkward to write for a solver, or you need an answer at any time. Use an exact solver when instances are small, optimality or a bound matters, or constraints are intricate.
How do you design the neighborhood and the cost evaluation for a new problem? || Pick small moves that keep the solution valid, connect the whole search space, and have an O(1) or O(log n) delta, then verify the deltas against full recomputation. Add larger moves or a destroy-and-repair move for diversity, and put constraint violations into the cost with tuned weights if infeasible intermediate states help.
Explain why simulated annealing is a Markov chain and what the theory guarantees. || The next state depends only on the current state, through the proposal and acceptance probabilities. At fixed T the stationary distribution is the Boltzmann distribution. With a logarithmic cooling schedule T_k = c/ln(k+1), where c is at least the depth of the deepest non-global valley (Hajek), it converges to a global optimum, but the schedule is too slow for practice, so in practice it is a heuristic.
How is a rebalancer in a cluster scheduler related to local search? || It treats a placement as a solution, a "move one task or shard" action as a neighbor, and a balance and cost function as the objective, and applies improving moves until none remain or a move budget is used. Differences from textbook local search are real move costs, live constraints (affinity, capacity, failure domains) and the need to avoid oscillation.
