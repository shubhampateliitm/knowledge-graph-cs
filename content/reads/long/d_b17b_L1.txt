@@ batchproc
value: Batch processing runs one large computation over a fixed, finite dataset: yesterday's ad impressions, last month's orders, a full table export. The input does not change while the job runs, and the job ends when the input is used up. ETL, daily reports, billing, machine-learning training sets, backfills and table maintenance are all batch jobs, and together they are still the largest workload on most data platforms.
The problem it solves is size. One day of impression logs for a large ad platform can be 4 TB of compressed Parquet. A single machine reading at about 500 MB/s needs more than two hours just to scan that, before any join. A batch engine splits the input into thousands of pieces and runs the same code on each piece on hundreds of machines at once, so the scan takes minutes. Because the input is fixed, the result is a pure function of the input: a failed piece can be re-run, a wrong result can be recomputed after a bug fix, and two runs give the same answer.
For the layer above (Spark, Hadoop MapReduce, Flink in batch mode, Beam, Ray Data, Dask, Hive), batch processing supplies the execution model: a job is a graph of stages, and each stage is many identical tasks over partitions of the data. The layers below make it work. DAG scheduling (L2) runs stages in dependency order. The shuffle (L2) regroups data by key between stages. Join algorithms (L2) combine large datasets across machines. Lineage-based recovery (L2) recomputes lost pieces instead of copying everything. Speculative execution (L2) cuts the tail of slow tasks. Amdahl's and Gustafson's laws (L4) say how much speed-up more machines can buy.
terms: Bounded dataset — input with a known end, such as one day's partition; the job finishes when it has read all of it.
Partition (split) — one piece of the input, often about 128 MB, processed by one task.
Task — the same code applied to one partition on one executor core (a slot).
Stage — a group of tasks that run without exchanging data; shuffles separate stages.
Wave — one round of tasks filling all slots; 10,000 tasks on 1,000 slots run in about 10 waves.
Shuffle — the all-to-all exchange that sends every record to the task responsible for its key.
Straggler — a task that runs much slower than its peers and delays the end of its stage.
Data skew — uneven distribution of records over keys, so one task gets far more data than the others.
history: Batch is how computing began. In the 1950s and 1960s, payroll and billing jobs ran on mainframes from punched cards and tape, and IBM's OS/360 (1964) used Job Control Language to say which programs ran on which datasets. Operators ran the jobs overnight and reran them if they failed.
Web-scale data broke the single-machine model. In 2004 Jeffrey Dean and Sanjay Ghemawat published "MapReduce: Simplified Data Processing on Large Clusters". Users wrote a map function and a reduce function; the runtime handled partitioning, scheduling, shuffling and machine failures on thousands of cheap servers. Their example sorted 1 TB on about 1,800 machines in 891 seconds. Doug Cutting and Mike Cafarella's open-source clone became Hadoop at Yahoo in 2006. Microsoft's Dryad (2007) generalized the fixed map-then-reduce shape to any directed acyclic graph of stages.
Raw map and reduce code was slow to write, so higher-level tools followed: Pig (Yahoo, 2008), Hive (Facebook, 2009, SQL over Hadoop) and FlumeJava (Google, 2010), which optimized whole pipelines. Then came Spark, started by Matei Zaharia at UC Berkeley. Its Resilient Distributed Datasets paper (NSDI 2012, best paper) kept intermediate data in memory and rebuilt lost data from lineage instead of writing every step to replicated disk. In 2014 Spark sorted 100 TB in 23 minutes on 206 machines; the previous Hadoop record was 72 minutes on 2,100 machines. Google's Dataflow model paper (2015) treated batch as the bounded case of stream processing, an idea carried into Apache Beam and Flink.
Today most batch work runs on Spark (4.2.0 was released in July 2026), cloud warehouses and lakehouse SQL engines, triggered by orchestrators such as Airflow, Dagster or Databricks Jobs.
how: A batch job starts as a program: SQL, a DataFrame pipeline, or explicit map and reduce functions. The engine turns it into a plan of operators and splits the input into partitions. For Parquet files in object storage, a partition is usually about 128 MB (Spark's default for spark.sql.files.maxPartitionBytes), so a 4 TB input becomes about 32,000 partitions and 32,000 tasks.
DAG scheduling (L2) decides the order of work. Narrow operators (filter, project, map, a lookup in a broadcast table) need only one input partition to produce one output partition, so the engine chains them inside one task: read, filter, project and partially aggregate, with nothing written in between. Wide operators (group by key, join on a key, distinct, global sort) need records from all partitions, so they force a stage boundary. The engine builds a directed acyclic graph of stages and starts a stage only when its parents have finished. Inside a stage, tasks are independent, so the scheduler places them on free slots, preferring machines that already hold the data, and runs them in waves.
The shuffle (L2) connects stages and is usually the most expensive step. Each upstream (map) task computes hash(key) mod R for every record, where R is the number of downstream partitions, and writes its records into R buckets in one sorted file on local disk. Each downstream (reduce) task then fetches its bucket from every map task: M map tasks and R reduce tasks mean M × R transfers. Partial aggregation (a combiner) sums values per key inside each map task first, so "count impressions per campaign" may shuffle gigabytes instead of terabytes. A reducer whose data does not fit in memory sorts, spills to disk and merges the spilled runs, as in an external sort.
Join algorithms (L2) decide how two datasets meet. If one side is small (Spark's default broadcast threshold is 10 MB, often raised to a few hundred MB), every task gets a full copy and joins its partition locally with a hash table, so the big side is never shuffled. If both sides are large, both are shuffled by the join key, and each reduce task runs a sort-merge join or a shuffle hash join on its key range. The choice changes network traffic by orders of magnitude.
Lineage-based recovery (L2) handles failures without replicating every step. The engine remembers, for every partition, which parent partitions and which function produced it. If an executor dies, the scheduler re-runs only the tasks whose outputs were lost, from their inputs. Hadoop MapReduce instead wrote every job's output to HDFS with three replicas: safe, but slow for multi-step pipelines. Lineage is correct only if tasks are deterministic. A task that uses unseeded random numbers, the current time, or the arrival order of records can produce different data when recomputed. Long lineage chains, as in iterative algorithms, are cut with checkpoints.
Speculative execution (L2) handles stragglers. On hundreds of machines a few are always slow: a failing disk, a noisy neighbour, a long garbage-collection pause. A stage ends only when its last task ends, so the scheduler launches a backup copy of unusually slow tasks and keeps whichever finishes first. In the MapReduce paper, turning backup tasks off made the 1 TB sort 44% slower (1,283 seconds instead of 891). In Spark 4 this is spark.speculation, off by default; when on, a task is copied once 90% of its stage is done and it has run three times longer than the median. Retries and backups create duplicate attempts, so only one attempt per task is committed, and the job's output is published in one atomic step. With Delta Lake or Iceberg that step is one transaction, so overwriting the partition date=2026-10-25 twice leaves the same table: the job is idempotent.
Amdahl's law (L4) limits all of this. If a fraction s of the run time is serial, the speed-up on N machines is at most 1 / (s + (1 − s)/N). Serial parts are easy to miss: listing millions of files on the driver, planning, the commit, and above all the largest task of a skewed stage, which more machines cannot split. Gustafson's law explains why batch still scales in practice: we usually want ten times more data in the same nightly window, not the same job faster, and the parallel part grows with the data while the serial part stays roughly fixed.

example: A nightly job builds impressions per campaign, device type and hour for one day. The input is 4 TB of Parquet, about 4,194,000 MB. With 128 MB partitions, stage 1 has 4,194,000 / 128 ≈ 32,768 tasks. The cluster has 100 executors with 8 cores, so 800 slots, and the stage needs 32,768 / 800 ≈ 41 waves. At about 20 seconds per task (read, decompress, filter, partially aggregate), stage 1 takes 41 × 20 = 820 seconds, roughly 14 minutes.
Partial aggregation shrinks the shuffle to about 40 GB, or 400 MB per executor, which takes seconds on a 10 Gbit/s network (about 1.25 GB/s). Stage 2 merges partial counts in 400 tasks and broadcasts a 20 MB campaign table; it takes about a minute.
Add the serial parts: 2 minutes to list files and plan, 1 minute to commit. The job takes about 2 + 14 + 1 + 1 = 18 minutes. Doubling the cluster halves only the parallel 15 minutes: 2 + 7.5 + 1 = 10.5 minutes, a speed-up of 18 / 10.5 ≈ 1.7, not 2. The serial fraction is 3 / 18 ≈ 17%, so by Amdahl's law no cluster can make this job more than about 6 times faster.
A second job joins the raw impressions with a 300 GB device-to-household table on device_id, so both sides are shuffled. With 2,000 reduce partitions the average task gets (4,000 + 300) / 2,000 ≈ 2.2 GB. But 5% of impressions have device_id = "unknown", and they all hash to one partition: 0.05 × 4,000 = 200 GB in one task. At about 100 MB/s, that task runs 2,000 seconds (33 minutes) while the others take about 20 seconds. Speculation cannot help: a copy of a 200 GB task is just as slow. The fixes are to filter unknown IDs before the join, to "salt" the hot key into sub-keys, or to let adaptive execution split partitions larger than 256 MB and more than 5 times the median (Spark's defaults).
Now an executor dies during stage 2 of the first job. It held the shuffle files of about 32,768 / 100 ≈ 328 map tasks. Reducers fail to fetch those blocks, and the scheduler re-runs only those 328 tasks: less than one wave, about 20 seconds. Without lineage, the safe choice would be to restart the whole 18-minute job.
intuition: Close the shop, count all the stock at once with many people, then reopen: simple and thorough, but the numbers are only as fresh as the last count.
A fixed input removes the hardest problems of distributed computing. Nothing changes under your feet, so there is no coordination with writers and no question of which version of the data a task saw. Every piece of work becomes a pure function from input partitions to output partitions, and pure functions can run anywhere, in any order the graph allows, as often as needed. That is why failure handling is just "do it again" and slow machines can simply be raced. Machines must cooperate only at shuffles, which is why almost all cost and tuning effort goes there.
mistakes: People often think streaming has made batch obsolete. In fact billing, finance, reporting and training-data jobs are still mostly batch, because a bounded input gives exact, reproducible answers and cheap reruns. Streaming systems also need batch-style reprocessing when their logic changes.
People often think that doubling the cluster halves the run time. In fact planning, file listing, commits, shuffle overhead and the largest skewed task do not shrink with more machines. Amdahl's law caps the gain, and in a skewed job more machines may change nothing.
People often think retries make any job safe. They are safe only when tasks are deterministic and output is committed atomically. A task that writes rows into an external database, calls a partner API or uses unseeded randomness repeats or changes those effects when it is retried or speculated.
People often think speculative execution fixes skew. It does not. Speculation helps when the machine is slow; skew means the task itself has too much data, and a copy of it is equally slow.
friction: Latency is the basic cost. A daily job means data up to a day old, and an hourly job can lag by more than an hour once queueing, retries and upstream dependencies are counted. Minute-level freshness needs micro-batches or streaming.
Recomputing everything is wasteful. A job that rereads 90 days to add one new day spends almost all its compute on unchanged data. Incremental processing (new partitions only, MERGE, change data feeds, incrementally refreshed materialized views) fixes this, but updates and deletes in old data make it harder to get right.
"Fixed input" is often a fiction. Events arrive late and upstream jobs rerun, so a partition that was complete at 02:00 gets more rows at 06:00. Pipelines need explicit rules for lateness and completeness, or they publish numbers that change silently.
Shuffles, skew and small files dominate tuning. Millions of tiny files make listing cost more than the work. One hot key turns a 15-minute job into a 2-hour one. These problems grow with the data, so a job that was fine last quarter can fail next quarter with no code change. Finally, a job can succeed while producing wrong output; without data-quality checks, that is worse than failing.
practice: Make every job idempotent for a time window: replace the partition or table version for date=2026-10-25 in one atomic commit, so a retry or backfill never doubles data. Give jobs a date-range parameter, so a backfill is the same job run for older dates.
Process incrementally where the logic allows (new partitions only, or a change data feed merged into the target on a stable key), and keep a full-recompute path for when logic changes.
Aim for partitions of roughly 100 to 200 MB, compact small files, and keep adaptive query execution on (the default since Spark 3.2) so the engine can coalesce tiny shuffle partitions and split skewed ones. Broadcast small dimension tables explicitly when the optimizer's size estimate is wrong.
Read the stage view in the Spark UI before resizing the cluster. A large gap between the maximum and median task time or input means skew; uniformly slow tasks mean too little parallelism or heavy spill. Enable speculation on shared or spot clusters, where slow machines are common, but only with a safe output committer or a table format.
Keep side effects out of tasks: write a table, then load it into operational systems in a separate, idempotent step. Track freshness, completeness (row counts against the source) and cost per run as first-class metrics, and alert on them.
quiz: What makes a dataset "bounded", and why does that make batch jobs easy to retry? || A bounded dataset has a known end and does not change during the run. The output is then a pure function of the input, so a failed task or job can be re-run and gives the same result.
Why does a group-by on a key create a stage boundary, while a filter does not? || A filter needs only the records of one partition, so it runs inside the same task. A group-by needs all records with the same key from every partition, so the data must be shuffled before the next step can start.
How does lineage recover a lost partition, and what must be true of tasks for this to be correct? || The engine knows which parent partitions and function produced each partition, and re-runs only the tasks needed to rebuild it. Tasks must be deterministic, or the rebuilt partition may differ from the one other tasks already used.
A job reads 2 TB in 128 MB partitions on 400 slots, and each task takes 15 seconds. About how long does the first stage take? || About 2,097,152 MB / 128 = 16,384 tasks, so 16,384 / 400 ≈ 41 waves, and 41 × 15 s ≈ 615 s, roughly 10 minutes.
One task in a stage has 50 times the median input. Should you enable speculation, add machines, or something else? || Neither speculation nor more machines helps, because the task itself has too much data. Change the partitioning: filter or isolate the hot key, salt it into sub-keys, or let adaptive execution split the skewed partition.

@@ mpp
value: A distributed SQL engine of the MPP (massively parallel processing) kind takes one SQL query and runs it on many machines at once, so that a query over terabytes answers in seconds. It is the engine inside data warehouses and lakehouse SQL: Spark SQL, Trino, Snowflake, BigQuery, Redshift, Databricks SQL with Photon, and Hive on Tez or Spark.
The problem is size plus latency. A dashboard query might scan 400 GB, join three tables and group the result. One server needs minutes, and the hash table for a large join may not fit in its memory. Fifty servers each scan one fiftieth of the data and send each other only the rows they need. Unlike a batch job, a user is waiting, so the engine plans in milliseconds, streams data between steps, and serves many queries at once.
The lower layers each add a piece. SQL (L3) is declarative: it says what result is wanted, not how to compute it, so the engine is free to choose the plan. Query optimization (L2) picks join orders, join types and data distribution from statistics. Predicate pushdown (L2) applies filters and column selection at the scan, so most bytes are never read. Join algorithms (L2) and the shuffle (L2) let matching rows meet on the same worker. The Volcano iterator model (L2) gives a uniform operator interface, and its exchange operator hides parallelism from the other operators. Vectorized execution (L2) and whole-stage code generation (L2) make each core fast. Adaptive query execution (L2) corrects the plan with real sizes measured while the query runs.
terms: Coordinator — the node that parses, plans and schedules a query and returns the result (the driver in Spark, the leader node in Redshift).
Worker — a node that scans data and runs operators on its share of the rows.
Fragment (stage) — a piece of the plan that runs on many workers in parallel between two exchanges.
Exchange — the operator that moves rows between fragments: repartition by hash, broadcast to all, or gather to one.
Broadcast join — copy the small table to every worker and join locally; the big table does not move.
Repartition (shuffle) join — hash both tables on the join key so equal keys land on the same worker.
Partial and final aggregation — each worker pre-aggregates its rows; only the small partial results are exchanged and merged.
Cardinality estimate — the optimizer's guess of how many rows an operator will produce; plans are only as good as these guesses.
Shared-nothing — each node has its own CPU, memory and disk, and nodes cooperate only by sending messages.
history: Parallel databases came long before "big data". Teradata, founded in 1979, shipped its first parallel system in 1984. University projects defined the techniques: the Grace hash join from the University of Tokyo (1983) and the Gamma database machine of David DeWitt's group at Wisconsin (mid-1980s), which partitioned tables across nodes by hash and ran every relational operator in parallel. Michael Stonebraker's "The Case for Shared Nothing" (1986) argued that independent nodes connected by a network scale better than nodes sharing memory or disks. Goetz Graefe's Volcano system (1990) introduced the exchange operator, which let ordinary single-node operators run in parallel without being rewritten. DeWitt and Jim Gray's 1992 article "Parallel Database Systems: The Future of High Performance Database Systems" predicted that shared-nothing designs would win, and they did.
In the 2000s, MPP moved to commodity hardware and columnar storage: Netezza, Greenplum, Vertica (from the C-Store research project, 2005), Aster and ParAccel. MonetDB/X100 (2005) showed vectorized execution, and HyPer (2011) showed compiled query plans; most modern engines use one of the two. Big-data systems then brought SQL to files: Google's Dremel paper (2010), offered publicly as BigQuery; Impala (Cloudera, 2012); Presto (Facebook, created 2012, open-sourced 2013, its main fork renamed Trino in December 2020); and Spark SQL with its Catalyst optimizer (2015). Amazon Redshift (2012) was built on ParAccel technology. Snowflake (paper at SIGMOD 2016) separated storage from compute: data lives in object storage, and independent compute clusters read it. Databricks Photon (2022) and Meta's Velox (2022) are vectorized C++ engines that run inside larger systems, while DuckDB and DataFusion brought the same techniques to a single machine.
how: The coordinator first parses the SQL text and binds names to tables and columns using the catalog. The result is a logical plan: a tree of relational operators such as scan, filter, project, join and aggregate. Because SQL (L3) describes only the result, any plan that computes the same relation is allowed, and the rest of the pipeline is about choosing a good one.
Query optimization (L2) rewrites the logical plan. Rule-based rewrites push filters below joins, remove unused columns, fold constants and turn correlated subqueries into joins. Cost-based optimization then chooses the join order and the join methods. It uses statistics (row counts, distinct values, null fractions, sometimes histograms) to estimate the size of every intermediate result and searches for the plan with the lowest estimated cost, an approach that goes back to System R (Selinger et al., 1979). Join order matters because intermediate results can differ by factors of a thousand: joining the two most selective tables first keeps every later step small.
Predicate pushdown (L2) moves work into the scan. A filter on the partition column (date = '2026-10-25') prunes whole directories, so only one partition out of 365 is listed. Columnar files such as Parquet store minimum and maximum values for each row group, so the scan skips row groups whose range cannot match. Only the referenced columns are read, which for a 40-column table may cut bytes by 90%. Pushdown often removes more work than all the parallelism adds.
Next the planner decides how data is distributed for each join and aggregation, and inserts exchanges. For a join of a small table S with a large table L on N workers, broadcasting S moves about N × |S| bytes and needs a hash table of S in every worker's memory; repartitioning moves about |S| + |L| bytes. Join algorithms (L2) then run locally: usually a hash join (build a hash table on the smaller input, probe it with the larger one), or a sort-merge join when inputs are already sorted or too large for memory. Repartitioning works because two rows can match only if their keys are equal, and equal keys hash to the same worker, so every match meets somewhere and no match is missed. Aggregations are split in two: each worker computes partial sums and counts for its rows, the partial rows are repartitioned by the group-by key, and a final aggregation merges them. This works for any associative function (SUM, COUNT, MIN, MAX; AVG as SUM and COUNT), and for COUNT DISTINCT engines often offer HyperLogLog sketches instead.
The Volcano iterator model (L2) defines how operators connect: each operator offers open, next and close, and pulls rows from its children. The exchange operator fits this interface. Below it, producer threads or machines run copies of a plan fragment and send rows into network buffers; above it, consumers call next as if reading from a local child. The other operators never know they are running in parallel, which is why one set of operators serves both single-node and distributed plans. The exchanges cut the plan into fragments (stages), and the coordinator assigns input splits (file chunks or row groups) to workers. Here engines differ. Trino streams pages of rows through in-memory exchanges, so all fragments run at once and results start flowing quickly, but a worker failure fails the whole query unless its fault-tolerant mode spools exchange data to storage. Spark SQL writes shuffle files at each exchange, which adds latency but lets it re-run only the lost tasks.
Per-core speed matters as much as the number of cores, because doubling CPU efficiency is like doubling the cluster. Vectorized execution (L2) processes batches of a few thousand values held in columnar arrays, so each operator runs a tight loop that the CPU can pipeline and the compiler can turn into SIMD instructions; Photon, Velox, Snowflake and BigQuery work this way. Whole-stage code generation (L2), used by Spark SQL and HyPer, fuses a chain of operators into one compiled function, so a row stays in CPU registers from scan to aggregation instead of passing through virtual next calls.
Plans are built from estimates, and estimates are often wrong, especially after several joins and filters on correlated columns. Adaptive query execution (L2) uses the real sizes measured when an exchange finishes: Spark switches a planned sort-merge join to a broadcast join when one side turns out small, merges many tiny shuffle partitions, and splits skewed ones. Dynamic filtering (runtime filters) adds another correction: once the small side of a join is built, its set of keys, or a Bloom filter of them, is sent to the scan of the large side, which can then skip rows and whole files that cannot match.
Finally, storage architecture shapes the engine. Classic MPP systems (Teradata, early Redshift) were shared-nothing with data on local disks, so adding nodes meant redistributing data. Snowflake, BigQuery, Databricks and Redshift's RA3 nodes keep data in object storage and cache hot data on local SSDs, so compute can be resized or duplicated in minutes. The price is that a cold scan reads over the network, which makes pruning and caching even more important.

example: An analyst runs: total cost per advertiser for the last 7 days, only for devices in India. Tables: impressions (one year, 200 TB, partitioned by date, 40 columns), campaigns (50 MB), devices (2 billion rows, 200 GB). The cluster has 50 workers; each scans about 1 GB/s and has a 10 Gbit/s link (about 1.25 GB/s).
Pushdown first. Partition pruning keeps 7 of 365 days: 200 TB × 7 / 365 ≈ 3.8 TB. The query needs 4 of 40 columns (campaign_id, device_id, cost, date), roughly 10% of the bytes, so the scan reads about 385 GB. At 50 GB/s for the whole cluster, that is about 8 seconds. Without pushdown, reading 200 TB would take more than an hour.
Join with campaigns. Broadcasting it moves 50 workers × 50 MB = 2.5 GB. Repartitioning would move 385 GB of impressions. Broadcast is the obvious choice.
Join with devices. The filter country = 'IN' keeps 20% of devices, 400 million IDs; at 8 bytes per ID that is about 3.2 GB. Broadcasting costs 50 × 3.2 = 160 GB of network in total, and each worker receives 3.2 GB in about 2.6 seconds, overlapping with its scan. Repartitioning costs 385 + 3.2 ≈ 388 GB. Broadcast wins on 50 workers, if a 3.2 GB hash table (several GB more with overhead) fits in each worker's memory. On 150 workers the answer flips: broadcasting costs 150 × 3.2 = 480 GB, more than the 388 GB of repartitioning. The best plan depends on the cluster size, not only on the tables.
Dynamic filtering helps further. After the device hash table is built, a Bloom filter of the Indian device IDs is pushed into the impressions scan, and 80% of impression rows are dropped before the join. Only about 77 GB of rows reach the join operators.
Aggregation. There are 5,000 advertisers. Each worker's partial aggregation produces at most 5,000 rows, so the exchange moves 50 × 5,000 = 250,000 small rows instead of billions. The final aggregation finishes in milliseconds. The query returns in about 10 seconds, and almost all of that is the scan.
Now suppose statistics are stale and the optimizer believes devices has 20 million rows. It may choose a different join order or underestimate memory, and some workers spill to disk or fail. Fresh statistics, or adaptive execution that sees the real size at runtime, prevent this.
intuition: Divide one big question into many identical small questions about slices of the data, answer them in parallel, and send each partial answer to the one place that combines it.
This works because relational operators decompose cleanly. Filters and projections look at one row at a time, so any slice can be processed anywhere. Associative aggregates can be computed in pieces and merged. Equi-joins can be split by key, because rows with different keys never match; hashing both sides on the key guarantees that every pair that could match meets on the same worker. The engine therefore needs only one new operator, the exchange, to turn a single-machine plan into a parallel one. The rest of the design is about moving as few bytes as possible: filter at the scan, pre-aggregate before the network, broadcast small things, and repartition only what must meet.
mistakes: People often think that more workers always make a query faster. In fact each query pays fixed costs for planning, scheduling and coordination, often tens to hundreds of milliseconds, and very small queries can run faster on one node. Broadcast costs also grow with the number of workers.
People often think the optimizer finds the best plan. It finds the plan that is cheapest under its estimates, and estimates after several joins are often wrong by factors of 10 to 1,000. Leis and colleagues showed this on real queries in 2015. That is why runtime adaptation and fresh statistics matter.
People often think separating storage from compute makes data layout irrelevant. In fact the scan still decides most of the cost: partitioning, clustering, file sizes and column pruning decide how many bytes cross the network from object storage.
People often confuse MPP analytic engines with distributed SQL databases such as Spanner or CockroachDB. MPP engines are built for large scans and aggregations by a few users at a time; distributed SQL databases are built for many small transactions per second with strict consistency. They solve different problems.
friction: Shuffles and skew dominate cost. A repartition moves every qualifying row across the network, and if one key holds 10% of the rows, one worker does 10% of the work while the others wait. Engines can split skewed partitions, but only when they detect the skew.
Estimates fail silently. Correlated columns (city and country), user-defined functions and stale statistics produce plans that are wrong by orders of magnitude, and the symptom is a query that is fast one day and slow the next with no code change.
Memory is the hard limit for joins and aggregations. Hash tables that do not fit must spill to disk, which can make a query ten times slower, and many concurrent queries compete for the same memory. Warehouses therefore add admission control, queues and multiple clusters for concurrency, which raises cost.
Fault tolerance and latency pull in opposite directions. Streaming pipelines are fast, but a failure late in a long query wastes all its work; materialized stages survive failures but add I/O to every query.
Costs are hard to predict. Pay-per-byte-scanned pricing punishes a missing filter, and elastic clusters make it easy to spend a lot quickly. Federated queries across different systems add another layer: a cross-source join may pull a whole remote table across the network because the source cannot run the join itself.
practice: Lay out large tables for pruning: partition by date or another coarse filter column, and cluster or sort within partitions on frequent filter and join keys (Z-ordering or liquid clustering in Delta, sort keys in Redshift, clustering keys in Snowflake). Keep files in the hundreds of megabytes.
Keep statistics fresh (ANALYZE TABLE, or the engine's automatic statistics) after large loads, and read EXPLAIN plans for slow queries. Check which joins are broadcast and which are repartitioned, and compare estimated with actual row counts in the query profile; a large gap points to the problem.
Select only the columns you need, filter on partition columns directly (not through functions that hide them from the planner), and prefer built-in SQL functions over user-defined functions, which block pushdown and vectorization. Use approximate functions (approx_count_distinct, HyperLogLog sketches) when exact distinct counts are not required.
For dashboards with many users, pre-aggregate into gold tables or materialized views, so each query scans megabytes instead of terabytes. For Spark SQL keep adaptive execution on; for Trino, push filters down to the connectors and avoid joining two large tables from different sources. Watch the slowest task of each stage: if it reads far more data than the median, you have skew.
quiz: What does the exchange operator do, and why is it important for parallel query engines? || It moves rows between plan fragments by repartitioning, broadcasting or gathering them. Because it has the same interface as any other operator, single-node operators can run in parallel without being rewritten.
Why is hash-partitioning both inputs on the join key enough to compute an equi-join in parallel? || Rows can match only if their keys are equal, and equal keys hash to the same worker. So every matching pair meets on exactly one worker, which joins its share locally.
How does two-phase aggregation reduce network traffic? || Each worker first aggregates its own rows, producing at most one row per group. Only these partial rows are repartitioned by group key and merged, instead of every raw row.
A 2 GB table joins a 500 GB table on 100 workers. Broadcast or repartition, and does the answer change on 300 workers? || Broadcast moves about 100 × 2 = 200 GB, repartition about 502 GB, so broadcast wins if 2 GB fits in memory. On 300 workers broadcast moves 600 GB, so repartition becomes cheaper.
When would you prefer an engine that materializes shuffle data over one that streams it? || For long, expensive queries or ETL on large or unreliable clusters, because a failure re-runs only the lost tasks. For short interactive queries, streaming exchanges give lower latency and a failure costs only a cheap restart.
