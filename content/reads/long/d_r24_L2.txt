@@ statefulops
value: A stateless stream operator looks at one event and produces output from that event alone: parse a JSON line, drop a bad record, add a field. Most useful questions are not like that. "How many impressions has this device seen today?", "Has this event ID already been processed?", "Which click belongs to which earlier ad request?" and "What is the latest feature vector for this user?" all need the operator to remember something from earlier events. A stateful operator is an operator that keeps this memory between events, one separate piece of memory per key (a device ID, a user ID, a session ID).
The hard part is not keeping a number in a variable. The hard part is that streams never stop and machines do fail. The state must be large enough to hold billions of keys, fast enough to read and update at hundreds of thousands of events per second, split across many parallel tasks, and still correct after a crash, a deployment or a change in parallelism. Stateful operators solve this with four ideas: partition the state by key so each task owns a slice, keep that slice in local memory or in an embedded store such as RocksDB, back it up with periodic checkpoints (or a changelog) to durable storage, and expire it with time-to-live rules and watermarks.
For the layer above, stream processing (the L1 concept that engines such as Flink, Kafka Streams and Spark Structured Streaming implement), this is what turns a pipe of events into aggregates, joins, deduplication and sessionisation with exactly-once results. Two lower layers do the real work. Hashing and hash tables (L3) decide which task owns which key and give the O(1) per-key lookup. File systems (L3) provide the local disk files where state larger than memory lives, and the durable files, on a distributed file system or object store, that checkpoints are written to.
terms: Keyed state — state that is scoped to one key; an operator sees and updates only the state of the key of the event it is processing.
Key group — the smallest unit of state that can move between tasks; the key space is hashed into a fixed number of key groups, and each task owns a range of them.
State backend — the component that stores and accesses the state, for example Java heap objects or an embedded RocksDB database on local disk.
Checkpoint — a consistent snapshot of all operator state plus the input positions, written to durable storage so the job can restart from it.
Barrier — a marker record injected into the stream; when an operator receives it, it knows that all earlier events are already in its state, and it takes its snapshot.
Changelog — an ordered log of every state update, stored for example in a compacted Kafka topic, from which state can be rebuilt by replaying.
State TTL — time-to-live; an expiry time after which a state entry is deleted automatically.
Watermark — a marker that says "no event with an older event time will arrive any more"; it lets operators close windows and drop the state of finished windows.
Rescaling — changing the number of parallel tasks, which requires redistributing the state among them.
history: Early stream systems of the 2000s (Aurora, Borealis, STREAM) already had windows and joins, but kept the state in the memory of one machine or replicated it fully. When Storm arrived in 2011, they pushed state out to the application: Storm's early topologies were stateless, and users kept counters in Redis or Cassandra themselves, which meant extra network hops and weak guarantees after failures.
The next step was to treat state as a first-class part of the engine. Spark Streaming (2013) kept state as RDDs and recovered it by recomputation and checkpointing. Apache Flink, which grew from the Stratosphere research project at TU Berlin and became a top-level Apache project in 2014, made keyed state the central idea. Its 2015 paper by Carbone and others, "Lightweight Asynchronous Snapshots for Distributed Dataflows", adapted the Chandy–Lamport snapshot algorithm (1985) to dataflows by injecting barriers into the stream, so a consistent snapshot can be taken without stopping the job. Flink's embedded RocksDB backend (2016) removed the limit that state must fit in memory, and the 2017 VLDB paper "State Management in Apache Flink" describes the design.
Kafka Streams (2016) chose a different durability path: local RocksDB stores backed by compacted changelog topics in Kafka, so there is no separate snapshot step. Spark Structured Streaming added its own state store, with a RocksDB-based provider from Spark 3.2 (2021), and Spark 4.0 added a new API, transformWithState, for arbitrary stateful logic with timers and TTL. The latest research direction is disaggregated state: Flink 2.0 (2025) introduced the ForSt backend and asynchronous state access, so that state lives on remote storage instead of the local disk of each task. The reason is the same in every step: state grew from megabytes to terabytes, and recovery time became the main problem.
how: Take a job that counts impressions per device. The input is partitioned by key: every event passes through a hash function of the device ID, and the result decides which parallel task receives it. This is the first thing hashing contributes. In Flink the key is hashed into one of maxParallelism key groups (at least 128 by default, up to 32,768), and key group g belongs to task floor(g × parallelism / maxParallelism). Because all events for one key always reach the same task, that task can keep the key's state locally and never needs a lock or a network call. The number of key groups is fixed for the life of the state, which is why it is chosen once and written into every checkpoint.
Inside the task, the state backend is the second contribution of hashing and file systems. The simplest backend is a hash table on the Java heap: a map from key to value, with O(1) access, about 100 ns per operation, and a size limit equal to memory. Java objects are also large, often two to three times the raw data, and large heaps cause long garbage-collection pauses. The alternative is RocksDB, an LSM-tree database embedded in the task. It stores each key and value as serialised bytes, in memory tables that are flushed to immutable sorted files (SST files) on the local disk, and merges them in the background. This uses the file system exactly as it likes to be used: sequential appends, big immutable files, and the operating system page cache. State can then be as large as the disk. The price is serialisation on every access and a few microseconds per operation; Flink's documentation says RocksDB is about an order of magnitude slower than the heap backend. Also, RocksDB sorts keys as bytes, not by hash, so the key group number is stored as a prefix of every key, which makes each key group a contiguous range of the files.
Durability is the third part. A task can crash, and its local disk is lost with it, so state must be copied somewhere safe. Flink does this with checkpoints. Every few seconds or minutes, the source operators record their input position (a Kafka offset, for example) and insert a barrier into each stream. When an operator has received the barrier on all its inputs, it knows that its state reflects exactly the events before the barrier, so it snapshots its state and forwards the barrier. The snapshot is written asynchronously to a durable file system or object store, such as S3, so processing continues. With RocksDB, incremental checkpoints upload only the SST files created since the last checkpoint, because SST files never change after they are written. On failure, the job restarts from the last completed checkpoint: state is downloaded, inputs rewind to the recorded offsets, and every event is reflected in the state exactly once. Kafka Streams reaches the same goal differently: every update to a local store is also written to a changelog topic, which is compacted so it keeps only the latest value per key; on restart the store is rebuilt by replaying it, and standby replicas keep a warm copy on another instance.
State cannot grow forever. Two mechanisms remove it. A time-to-live setting deletes entries that were not touched for a given period; in RocksDB the cleanup is done cheaply inside background compaction. Watermarks do the same for windows and joins: when the watermark passes the end of a window plus the allowed lateness, the window's result is emitted and its state is deleted. Without one of these, a deduplication operator keeps every ID it has ever seen.
Rescaling is the last piece. To change parallelism from 20 to 32, the engine stops the job (usually through a savepoint, a checkpoint that the user triggers and keeps), and redistributes whole key groups to the new tasks. It never rehashes individual keys, which would require reading all state. The key group is the unit of movement. This is why max parallelism must be set high enough from the start: it caps how far the job can ever scale out.

example: A pipeline reads ad impressions from Kafka. Each event has a device ID and an event ID. The job does two things: it drops events whose ID was already seen in the last 24 hours (deduplication), and it counts impressions per device per day. There are about 100 million active devices, and the job runs with parallelism 20 and max parallelism 128.
First, key assignment. 128 key groups are spread over 20 tasks, so each task gets 6 or 7 key groups (8 tasks get 7 and 12 tasks get 6, which adds to 128). Device d1 hashes to key group 45, so it goes to task floor(45 × 20 / 128) = floor(7.03) = 7. Every event of d1 goes to task 7 and no other task ever sees d1.
Second, state size. The count state per device is a key (16 bytes) plus a counter (8 bytes) plus RocksDB overhead, say about 50 bytes in total. For 100 million devices that is roughly 5 GB, or 250 MB per task. On the Java heap, with one boxed Long and one String per entry, the same data would be roughly 3 times larger and would put heavy pressure on the garbage collector. The deduplication state is larger: if 500 million event IDs arrive per day, with 16 bytes per ID plus overhead of about 20 bytes, that is about 18 GB, or 0.9 GB per task. A 24-hour TTL deletes each ID one day after it was written, so the size stays flat.
Third, checkpointing. A checkpoint runs every 60 seconds. A full snapshot would upload about 23 GB each time. With incremental checkpoints, suppose the job writes about 150 MB of new SST files per minute across all tasks, so each checkpoint uploads about 150 MB, which is more than 100 times less. Barriers pass through in a few hundred milliseconds if the job is not back-pressured.
Fourth, a failure. Task 7 dies at second 45 of a checkpoint interval. The job restarts from the last completed checkpoint. Task 7's replacement downloads about 1.1 GB of its state (counts plus dedup) at, say, 100 MB/s, so it needs roughly 11 seconds, then opens RocksDB. Kafka offsets rewind to the checkpoint, and the up to 45 seconds of events are read again. Their updates are applied to the restored state, which had not yet seen them, so each event is counted once. Output sinks need transactions or idempotent writes to avoid duplicated output; that is the job of delivery guarantees, not of the state.
intuition: A clerk who keeps a ledger for his own set of customers, makes a photocopy of the whole ledger every few minutes, and can hand a whole customer drawer to a new clerk without reading it.
The design is natural because of one fact: events for different keys are independent. If all updates for a key arrive at one place, in order, then that place can hold the key's state privately, with no locks and no distributed transactions. Parallelism becomes simple partitioning. The only hard problem left is failure, and the snapshot idea answers it: because the barrier marks a clean cut through the stream, state plus input position together are consistent, and replay from that point gives the same result. The key group is a small, fixed unit that makes both recovery and rescaling cheap, because you move or restore drawers, not individual papers.
mistakes: People often think a stream processor keeps state in an external database such as Redis. In fact the engines keep it inside the task, next to the code. Local access takes nanoseconds to microseconds, not a network round trip of about 0.5 ms or more, and the engine can snapshot it consistently with the input position. An external store is possible but then you lose exactly-once between state and input unless you design it carefully.
People often think a checkpoint is a backup that you can restore to a different version of the code. In fact a checkpoint is tied to the job structure and the state serialisers. Changing the type of a field, removing an operator without a stable ID, or changing max parallelism can make the state unreadable. Planned upgrades use savepoints, stable operator IDs and state schema evolution (Avro or Protobuf-based serialisers).
People often think more parallelism always helps with large state. In fact a skewed key (one device with millions of events) lands in one key group on one task, so adding tasks does not help. Parallelism is also capped by max parallelism.
People often think TTL makes expired data disappear at the exact second. In fact cleanup is lazy: entries are removed during compaction, on read, or in snapshots, so the state can be larger than the live data, and an expired entry may still occupy disk for a while.
friction: State size drives everything. Checkpoint time, recovery time, disk cost and rescaling time all grow with it. A job with 2 TB of state and a 100 MB/s per-task download can need many minutes to recover, during which the pipeline is behind and must catch up. Incremental checkpoints reduce upload size but not restore size, and RocksDB compaction can rewrite the same data many times (write amplification of 10 or more is common), which uses disk bandwidth and CPU at unpredictable moments.
Back-pressure interacts with checkpointing. Barriers travel with the data, so a slow operator delays the barrier, and long checkpoints cause timeouts. Unaligned checkpoints (Flink 1.11 and later) let barriers overtake buffered data, at the cost of larger checkpoints, because the in-flight buffers are saved too.
Schema evolution is hard, because state is serialised data that outlives the code that wrote it, sometimes for years. Changing a class can make a restore fail. Skew and hot keys make one task hold more state and take more traffic than others. Event-time logic is subtle: a late event that arrives after its state expired is dropped or gives a wrong result. Observability is poor, since the state is a binary store inside a running job; tools such as Flink's State Processor API and Spark 4's state data source exist, but they work offline. Disaggregated state (ForSt) attacks the size problem by keeping state on remote storage, trading higher access latency for fast recovery and elastic scaling.
practice: Choose the key carefully: it decides parallelism, skew and state size. Prefer a high-cardinality key with an even event rate. For a hot key, add a salt (key + random 0..N) and combine partial results in a second stage.
Set max parallelism explicitly and generously at the first deployment (for example 1,024 or 4,096 for a job that may grow), because changing it later breaks state restore. Give every stateful operator a stable ID (uid in Flink). Use RocksDB with incremental checkpoints once state passes a few GB per task, give it managed memory, and put its local directory on fast local SSD, not on network storage. Set TTL on every state entry that has a natural lifetime; deduplication and join state without TTL is the most common cause of a slowly growing, eventually failing job.
Tune the checkpoint interval against recovery: a shorter interval means less replay after a failure but more load; one to five minutes is typical. Keep checkpoints on a durable store with enough bandwidth, and monitor checkpoint duration, size and alignment time as first-class metrics. Test restore from a checkpoint and a savepoint regularly, including after a code change. Use schema-evolving serialisers such as Avro or Protobuf for state, not Java serialisation. In Kafka Streams, set num.standby.replicas to 1 or more if restore time matters, and watch the changelog topics' size. Before adding state at all, ask whether a stateless design with a lookup in an external store is enough; each stateful operator is something you must operate, upgrade and recover.
tradeoffs: Choose the heap state backend when state per task is small (under roughly 1 to 2 GB), latency per event matters, and you can afford the garbage collection tuning. Choose RocksDB when state is larger than memory, when you need incremental checkpoints, or when you want predictable pauses. You give up about 5 to 10 times in per-access speed and gain size and stability. Choose disaggregated state (ForSt in Flink 2.0) when state is in the multi-terabyte range and fast recovery and elastic scaling matter more than the lowest per-access latency; you give up local-disk speed and depend on a remote store.
Choose Flink-style checkpoints plus savepoints when you want exactly-once state with the engine controlling snapshots and a full-job restore; choose the Kafka Streams changelog model when you already run Kafka, want a library instead of a cluster, and accept that every update is written twice (local store and changelog). Checkpoints cost periodic bursts of upload; changelogs cost constant extra write traffic, and restore time depends on the changelog length (compaction helps).
Choose external state (Redis, Cassandra, DynamoDB) when state must be read by other services, or when it is too large and too cold to be kept per task; choose embedded state when it is only used by the stream job and you need exactly-once. With external state you give up the consistent snapshot with the input, and add about a millisecond per lookup, unless you batch or cache.
interview: How does a stream engine make keyed state exactly-once after a crash? || It combines a consistent snapshot with replayable input. Barriers flow with the data, each operator snapshots its state when the barrier arrives, and sources record their offsets. After a failure, the job restores the snapshot and rewinds the inputs to those offsets, so each event affects the state exactly once. Exactly-once output to external systems additionally needs transactional or idempotent sinks.
Why does Flink use key groups instead of assigning keys directly to tasks? || If keys were hashed straight to tasks, changing parallelism would move keys unpredictably and every key would have to be re-read and rehashed. With a fixed number of key groups, a task owns a contiguous range, and rescaling moves whole ranges as files. The cost is that max parallelism is fixed once state exists.
A stateful job slows down over days and then fails with out-of-disk errors. What do you check? || First, whether any state has no TTL or watermark cleanup, such as dedup sets or join buffers. Then key cardinality growth, skew (one task holding much more state), and RocksDB compaction falling behind or write amplification. Also check checkpoint retention.
Why is a state backend on the heap often a poor choice for tens of GB per task? || Java objects have large overhead and the garbage collector must scan or move them, so pauses of seconds appear. Long pauses cause missed heartbeats, timeouts and restarts. RocksDB keeps data off-heap as bytes, so GC cost does not grow with state size.
How would you handle a hot key that overloads one task? || Add a salt to split the key into N sub-keys, aggregate partially in the first stage, and merge in a second stage keyed by the original key. This works for associative aggregates such as counts and sums. It does not work when the logic needs all events of one key in order.
quiz: What is a key group and why does it exist? || A key group is a fixed bucket of the hashed key space. Each task owns a range of key groups, and rescaling moves whole key groups, so keys never need to be rehashed individually.
Why can the stream engine take a consistent snapshot without stopping the job? || Barriers in the data stream mark a clean cut. When an operator receives a barrier on all its inputs, its state reflects exactly the events before the barrier, so it can snapshot asynchronously while later events continue to flow.
Why are incremental checkpoints possible with RocksDB? || RocksDB writes immutable SST files. A checkpoint only has to upload the files created since the previous one, plus references to files already in the durable store.
A job has 100 million keys at 50 bytes of state each and parallelism 20. How much state does each task hold, and how long does restoring one task take at 100 MB/s? || Total state is about 5 GB, so about 250 MB per task. Downloading it takes about 2.5 seconds, plus time to open RocksDB.
When would you choose the Kafka Streams changelog design over snapshot checkpoints? || When you already run Kafka, want to deploy a library without a separate cluster, and accept writing every update twice. Restore is by replaying the compacted changelog, and standby replicas shorten it.

@@ logcompaction
value: A normal Kafka topic forgets by time or size: after seven days, or after 100 GB, the oldest segments are deleted. That is right for events ("a click happened"), but wrong for state ("the current address of user 42"). For state, what you want to keep is not the last week of messages but the latest message for each key, however old it is. Log compaction is the topic setting (cleanup.policy=compact) that does this. A background cleaner rewrites old segments and drops every record that has a newer record with the same key. The topic then holds at least the last value of every key, so its size is bounded by the number of distinct keys, not by the number of writes.
This turns a log into a table that can be rebuilt. A new consumer, or a crashed one, reads the topic from the beginning and ends up with the current value of every key, and then continues to follow changes. Kafka uses this for its own metadata: the __consumer_offsets topic stores one committed offset per group, topic and partition, and Kafka Connect keeps its configuration and offsets in compacted topics. Kafka Streams uses compacted changelog topics to rebuild its local state stores, and teams use compacted topics for change data capture (CDC) tables, configuration and reference data.
For the layer above, the distributed commit log (L1), compaction is what lets one log serve both as a stream of changes and as a durable table, the "stream-table duality". Three lower concepts make it work. Hashing and hash tables (L3) give the cleaner its offset map, a compact table from key hash to the latest offset. File systems (L3) give it immutable segment files that can be rewritten sequentially and swapped in by an atomic rename. The LSM tree (L2) gives the idea itself: do not update in place, append new versions, and merge away old versions later in the background. Kafka's version differs in one important way, which the how section explains.
terms: Compacted topic — a topic with cleanup.policy=compact, where the cleaner keeps at least the latest record for each key.
Segment — one file of the partition log; the log is a sequence of segments, and only the last one (the active segment) is being written.
Head and tail — the tail is the part of the log that was already cleaned and has no duplicate keys; the head (the dirty part) is newer and may still contain old versions.
Dirty ratio — the size of the head divided by the size of the whole log; the cleaner starts when it passes min.cleanable.dirty.ratio (default 0.5).
Offset map — the cleaner's in-memory hash table from key hash to the highest offset of that key in the head.
Tombstone — a record with a key and a null value; it means "delete this key", and it is itself removed later.
delete.retention.ms — how long a tombstone is kept after cleaning (default 24 hours), so that slow readers can still see the delete.
Compaction lag — min.compaction.lag.ms and max.compaction.lag.ms set the shortest and the longest time a record may stay uncompacted.
history: The idea comes from LinkedIn, where Kafka was built in 2010 to move activity and database changes between systems. Jay Kreps and colleagues noticed that many consumers did not want the full history of a database table's changes; they wanted the current state, and a way to catch up quickly. Jay Kreps' 2013 essay "The Log: What every software engineer should know about real-time data's unifying abstraction" describes this view, in which a table and a changelog are two views of the same thing. The work was tracked as KAFKA-631 from 2012, and compaction shipped in Kafka 0.8.1 in 2014.
The first big user was Kafka itself. Consumer offsets used to be stored in ZooKeeper, which could not handle the write rate of large groups. Kafka 0.8.2 (2015) added a compacted internal topic, __consumer_offsets, which gave a scalable store with no new storage system: each commit overwrites the previous one for the same key. The transaction coordinator later used the same trick for its state. Kafka Streams (2016) made the pattern a public programming model: a KTable is a changelog topic read as a table, and every local state store is backed by a compacted topic. Later changes added control over timing: a minimum compaction lag, so readers near the head are guaranteed to see every record (KIP-58), and a maximum lag, so low-traffic partitions are not left uncleaned for a long time (KIP-354). The overall design has stayed stable for more than ten years.
how: A Kafka partition is a directory of segment files, each holding a range of offsets, written only at the end. Compaction divides the log into two parts. The tail is the already cleaned part: it has at most one record per key. The head is everything written since the last cleaning, and it may contain many versions of each key. The active segment, the one being written, is never cleaned. Offsets are never changed or reused, so a compacted log has gaps: if the records at offsets 36 and 37 are removed, a read starting at 36 simply returns the record at 38.
The log cleaner is a small pool of background threads (one thread by default). Each thread repeatedly picks the partition whose dirty ratio is highest, provided it is above min.cleanable.dirty.ratio (0.5 by default) or a record has waited longer than max.compaction.lag.ms. Then it works in two passes. In the first pass it reads the head and builds the offset map: for each record it stores the hash of the key (a 16-byte MD5 hash) and the offset, 24 bytes per entry, so later records overwrite earlier ones and the map ends with the latest offset of every key. This is where hash tables contribute. The map is bounded by log.cleaner.dedupe.buffer.size (128 MiB by default, shared by all cleaner threads), which holds roughly five million keys. If the head has more distinct keys than fit, the cleaner cleans only a prefix of the head in this round and continues in the next.
In the second pass the cleaner copies the log, oldest segment first, from the beginning of the tail to the end of the cleaned region. For every record it looks up the key in the map. If the map holds a higher offset for that key, a newer version exists and the record is dropped. Otherwise it is copied. The output goes to new files with a .cleaned suffix; small segments are grouped so that the result is not many tiny files. When a group is complete, the cleaner renames it to .swap and then replaces the old segments with it, and deletes the old files. A crash at any moment leaves either the old files or a recoverable swap file, so the log is never inconsistent. This is where file systems contribute: sequential reads and writes, immutable files, and atomic rename. Consumers keep reading during all of this; cleaning is throttled by log.cleaner.io.max.bytes.per.second so it does not starve producers, and it needs only about one extra segment of free space, not a copy of the whole log.
Why a hash map, and not a merge as in an LSM tree? An LSM tree stores sorted runs, so merging two runs is a streaming merge of sorted keys and needs very little memory. A Kafka log is ordered by offset, not by key, and consumers rely on that order, so Kafka cannot sort it. To find duplicates in an unsorted file, you need a lookup table of the keys, and that is the offset map. This is the cost of compaction: memory proportional to the number of distinct keys in the head. The benefit is that the order of surviving records is preserved exactly.
Deletes use tombstones. A producer writes a record with the key and a null value. The cleaner treats it like any other newer version, so it removes older records of that key. The tombstone itself must stay for a while: a consumer that read the old value earlier needs to see the delete. So the cleaner keeps the tombstone until delete.retention.ms (24 hours by default) has passed since the segment was cleaned, and only then removes it. A consumer that rebuilds its table from offset 0 sees every tombstone if it reaches the head of the log within that time. If it takes longer, it may miss the delete and keep a key that no longer exists.
The guarantees follow. A consumer that stays near the head sees every message. A consumer that reads from the start sees at least the final value of every key, in the original order. Ordering holds per key, and so per partition. Two further rules matter: records without a key are not allowed in a compacted topic, and a topic can use cleanup.policy=compact,delete to also apply time-based deletion.

example: Take a topic user-profile with 10 million distinct user IDs. Each record is about 1 KB. Producers write 5,000 updates per second, spread evenly over the users.
First, what retention would cost. The write rate is 5,000 × 1 KB = 5 MB/s, which is about 430 GB per day. With time-based retention of 7 days, the topic would hold 3 TB, and a consumer that wants the current profiles would have to read all 3 TB. With compaction, the long-term size is bounded by the distinct keys: 10 million × 1 KB = 10 GB. The cleaner starts when the dirty ratio is 0.5, so the log can reach about 20 GB (10 GB clean tail plus 10 GB of dirty head) before it is cleaned, still 150 times smaller than 3 TB. A new consumer that reads 10 to 20 GB at 200 MB/s rebuilds the table in 50 to 100 seconds.
Second, the cleaner's memory. The dirty head of 10 GB is 10 million records, written in about 2,000 seconds at 5 MB/s. Drawing 10 million times from 10 million users hits about 63% of them, so the head has roughly 6.3 million distinct keys. The offset map needs 6.3 million × 24 bytes, about 150 MB, but the default buffer is 128 MiB (about 5.6 million keys). The cleaner then cleans the head in two rounds. If it keeps falling behind, raise log.cleaner.dedupe.buffer.size to 256 MiB or add cleaner threads.
Third, a small trace. Using the diagram's nine records, the map after the first pass says A→8, B→4, C→6, D→7. The copy pass keeps offsets 4, 6, 7 and 8 and drops 0, 1, 2, 3, 5. Offset 4 is a tombstone for B. A consumer that starts at offset 0 receives 4, 6, 7, 8 and ends up with C=2, D=1, A=4 and a delete of B. A consumer that was at offset 5 before the cleaning and continues from 5 receives 6, 7, 8, because offsets did not change.
Fourth, the tombstone trap. A service keeps a local copy of the table in its own database and applies the topic incrementally. It is offline for 3 days. During that time user 7 is deleted: the tombstone is written, the old records are cleaned, and after 24 hours the tombstone is removed too. When the service restarts, it never sees the delete, because the log no longer says anything about user 7, and the stale row stays. A service that rebuilds from offset 0 is safe; one that resumes with old state must return within delete.retention.ms.
intuition: An address book where you cross out old addresses and keep only the newest one per person, but the page numbers never change.
The design is natural once you see that most readers of a keyed stream ask "what is true now?", not "what happened?". If only the last value matters, older values for the same key are dead weight, and removing them cannot change the answer. Doing this in the background, in files that are never modified in place, keeps writes fast and cheap. Keeping offsets fixed means that every consumer position stays valid. And since the log stays ordered, the compacted log is still a log, just a shorter one. The tombstone is the one place where the shortcut needs care, because "absence" cannot be sent over a stream as a message.
mistakes: People often think a compacted topic always contains exactly one record per key. In fact it contains at least the latest record per key. The head and the active segment can hold many versions, and cleaning is lazy. Consumers must handle seeing several versions of a key, applying them in order.
People often think compaction deletes data immediately when you write a tombstone, for example to meet a privacy request. In fact the old values stay on disk until the cleaner reaches those segments, and the tombstone stays for another day by default. A low-traffic partition may not roll its active segment for days (segment.ms defaults to 7 days), so nothing is cleaned. Use segment.ms and max.compaction.lag.ms to bound this time.
People often think a compacted topic is an event history. In fact it throws away history by design. If you need every event (audit, replay of business logic), use a normal topic with time retention, or store both: events in one topic, current state in a compacted one.
People often think compaction is the same as the LSM-tree merge. In fact it has the same goal but a different method. An LSM tree merges sorted runs using little memory. Kafka cannot sort its log, so it builds a hash map of keys, and the memory depends on the number of distinct keys in the head.
friction: Compaction is lazy and costs I/O. The cleaner reads and rewrites the log, and for a topic where nearly every key is rewritten often, it can write several times the topic's size per day. Throttle it, and give it enough memory for the offset map, or it falls behind and the topic grows. The cleaner thread can also die: a corrupt segment or an unexpected error marks the partition as uncleanable. This has been reported for the busy __consumer_offsets topic, which then grew without limit. Monitor the uncleanable-partitions-count and max-clean-time-secs metrics.
Visibility rules are subtle. A consumer may read records that are about to be removed, and consumers that lag see only the compacted log, so you cannot rely on seeing every intermediate value. Tombstone retention is a hidden deadline for any consumer that keeps long-lived state. Deletes of keys that never existed, and the null-value convention, mean that a "null" payload can never be a real value. There is no secondary index, no point lookup, and no query: to read one key you must consume the whole partition, so compacted topics are loaded into a store (a KTable, a database) and read from there. Finally, the set of live keys needs space: a topic with billions of small keys still costs real disk and a very long bootstrap read, and key skew creates hot partitions.
practice: Use compaction when the topic is a changelog of keyed state: CDC from a database table, a user profile or feature topic, configuration, a Kafka Streams store. Choose the key to be the entity ID, always set it, and use a tombstone to delete. Keep records of one entity in one topic, since compaction only compares keys within a partition.
Tune three things. For a low-volume topic, lower segment.ms (for example to one hour) so segments roll and become eligible; for a topic where freshness matters, set max.compaction.lag.ms to bound how long duplicates survive. For a topic where you need consumers near the head to see every update, set min.compaction.lag.ms. Raise min.cleanable.dirty.ratio to 0.7 or more to save I/O at the cost of more disk, or lower it (0.1 to 0.2) to keep the topic small at the cost of more rewriting. Size log.cleaner.dedupe.buffer.size from the number of distinct keys: about 24 bytes per key, divided by the load factor, and increase log.cleaner.threads if the cleaner falls behind.
Set delete.retention.ms longer than the longest time a consumer can be offline and still resume with old state, or force such consumers to rebuild from the beginning. Watch the cleaner metrics and the topic's size against the expected number of keys. If the topic is much bigger, the cleaner is behind or the key design is wrong. For GDPR-style deletions, write the tombstone, then verify compaction, and remember copies in other systems. Do not use compaction for a topic you also want to replay as an event history.
tradeoffs: Choose compact when consumers need the current state per key and bootstrap time matters: 10 GB to read instead of 3 TB. Choose delete (time or size retention) when every event matters, such as clickstream and audit data. You give up history with the first and unbounded growth with the second. Choose compact,delete when you want the latest value per key but also a hard limit on age, for example to drop keys not updated for 30 days.
Choose a low min.cleanable.dirty.ratio (0.1 to 0.2) when disk is expensive or bootstrap time must be short; it keeps the log near its minimum size but rewrites data more often, spending I/O. Choose a high ratio (0.7 to 0.9) for very large topics where rewriting hurts and extra disk is cheap. At 0.5, the log can be up to twice its minimum size.
Choose a long delete.retention.ms (days) when consumers may be offline for long periods and must see deletes; choose the default 24 hours or shorter when deleted keys are numerous and tombstones themselves take space. Choose a compacted topic as the changelog of a stream processor when you want state that is rebuilt by replay; choose periodic snapshots to object storage when the state is huge and the replay time of a changelog (minutes to hours) is too long.
interview: How does the log cleaner find which records to remove in an unsorted log? || It scans the dirty head and builds an offset map from key hash to the highest offset (24 bytes per entry). Then it copies the log from the oldest segment, keeping a record only if no higher offset exists for its key. Memory is proportional to the number of distinct keys in the head.
Why are offsets preserved in a compacted topic, and what would break otherwise? || Consumers store offsets as their position, and the commit log is the source of truth for ordering. If compaction renumbered records, committed offsets and replicas would point to wrong records. Preserved offsets mean gaps, and a read at a removed offset returns the next surviving record.
A consumer rebuilds a table from a compacted topic but sometimes keeps users that were deleted. What is the likely cause? || It missed the tombstone: the tombstone was removed after delete.retention.ms before the consumer reached it, for example after a long pause. The consumer must read the log to the head within that window, or rebuild its state from scratch.
Why might a compacted topic keep growing even though there are few distinct keys? || The cleaner may be behind or dead (uncleanable partition, too little offset-map memory, throttling), the dirty ratio threshold may be high, or the active segment is huge because segment.ms is long and traffic is low. Check cleaner metrics and the segment settings.
How does compaction relate to Kafka Streams state stores? || Each local store (RocksDB) writes every update to a compacted changelog topic. On failure or migration, the new owner replays the changelog to rebuild the store, which has one record per key after compaction. Standby replicas keep a warm copy, so restore is short.
quiz: What does Kafka guarantee about the latest record for each key in a compacted topic? || The cleaner never removes the latest record for a key, so a reader from the start sees at least the final value of every key, in the original order, and offsets never change.
Why does the cleaner need a hash map of keys, when an LSM tree needs none? || An LSM tree merges sorted runs, so duplicates are adjacent. A Kafka log is ordered by offset, not by key, so to find newer versions of a key the cleaner needs a lookup table from key to latest offset.
Why is the active segment never compacted, and what is the practical result for a low-traffic topic? || The active segment is still being written, so it cannot be rewritten safely. A low-traffic topic may not roll its segment (segment.ms default 7 days), so old duplicates remain until the segment rolls.
With the default 128 MiB buffer and 24 bytes per key, about how many distinct keys can one cleaning round cover, and how much memory does a head with 20 million distinct keys need? || About 5.6 million keys in one round (134,217,728 / 24). Twenty million keys need 480 MB, so the cleaner needs several rounds or a larger buffer.
When would you use cleanup.policy=compact,delete instead of only compact? || When you need the latest value per key but also a maximum age, for example dropping entities that were not updated in 30 days, or limiting how long deleted data can remain.

@@ consumergroups
value: A Kafka topic is split into partitions, and a partition is read in order. Two different needs appear on top of this. Sometimes many workers must share the reading of a topic so that each message is handled once, to scale out. Sometimes several independent applications must each see every message, for example billing, search indexing and analytics. Older messaging systems offered two separate models for these needs, the queue and publish–subscribe. A consumer group gives both with one rule: inside a group, each partition is read by exactly one member; different groups do not affect each other, and each keeps its own position in the log.
So adding consumers to a group spreads the partitions over them (scale-out). Starting a second group gives a second full copy of the stream (fan-out). The group also gives fault tolerance: if a member dies, its partitions move to the survivors, which continue from the last committed offset. The work of keeping this assignment correct while machines join, leave and fail is called rebalancing, and it is the most visible operational pain of Kafka consumers.
For the layer above, publish–subscribe (L1) gets its fan-out and load sharing from this. Three lower concepts supply the pieces. Partitioning (L2) provides the unit of assignment and also the upper limit of parallelism: a group with more members than partitions leaves the extra members idle. Leader election and leases (L2) provide the coordinator, a broker that is the leader of one partition of the internal offsets topic, and the heartbeat-and-timeout idea, which is a lease: a member owns its partitions only as long as it renews its membership. Distributed systems theory (L3) explains why this is hard: you cannot tell a dead consumer from a slow one, so the group uses timeouts, and it must fence the "zombie" that comes back after being declared dead, using generation numbers.
terms: Group coordinator — the broker that manages one group: it tracks members, runs rebalances and stores the group's committed offsets.
Rebalance — the process of reassigning partitions among the members of a group after a change.
Committed offset — the position, stored per group and partition, from which a group continues after a restart or a rebalance.
Heartbeat — a small periodic message from a member to the coordinator that says "I am alive"; if heartbeats stop, the member is removed.
Generation (member epoch) — a number that increases at each rebalance; requests carrying an old number are rejected, which fences zombie members.
Assignor — the algorithm that decides which member gets which partitions (range, round-robin, sticky, uniform).
Lag — the log end offset minus the group's committed offset: how far behind the group is.
Static membership — a member keeps a fixed group.instance.id so a quick restart does not cause a rebalance.
history: The first Kafka consumers (LinkedIn, 2010–2011) kept group state in ZooKeeper. Each consumer watched ZooKeeper, and when anything changed, every consumer computed the new assignment on its own and tried to claim partitions. This caused herd effects, with many clients hitting ZooKeeper at once, and sometimes disagreement between clients about who owned what. Kafka 0.9 (November 2015) introduced the new consumer with a group coordinator on the brokers, and the JoinGroup and SyncGroup requests: the coordinator manages membership, one member (the group leader) computes the assignment on the client side, and the coordinator distributes it. Offsets moved to the compacted __consumer_offsets topic.
Later fixes targeted the pain of rebalancing. KIP-62 (Kafka 0.10.1, 2016) moved heartbeats to a background thread and added max.poll.interval.ms, so a slow processing loop was no longer confused with a dead process. KIP-345 (Kafka 2.3, 2019) added static membership. KIP-429 (Kafka 2.4, 2019) added cooperative incremental rebalancing, where members keep partitions that do not move. KIP-735 (Kafka 3.0) raised the default session timeout from 10 to 45 seconds. Then KIP-848 redesigned the protocol so that the broker computes the assignment and members reconcile step by step, with no group-wide barrier. It became generally available in Kafka 4.0 (March 2025). Kafka Streams has its own version of this idea (KIP-1071), made generally available, with a limited feature set, in Kafka 4.2. Share groups (KIP-932) add queue semantics on top of the same group machinery.
how: A consumer starts by sending FindCoordinator. The coordinator for a group is found by hashing the group.id onto one of the partitions of __consumer_offsets (50 by default); the broker that leads that partition is the coordinator. This is leader election at work: the coordinator is not elected separately, it is whichever broker leads that partition, and if it fails, the new partition leader becomes the coordinator and reloads the group state by reading the log. The same topic also stores the committed offsets of the group, keyed by (group, topic, partition), and it is a compacted topic (see log compaction), so it keeps only the latest commit for each key.
In the classic protocol, a member sends JoinGroup with the list of topics it subscribes to. The coordinator waits until all known members have joined (or a timeout), increments the generation, picks one member as leader and sends it the full member list and subscriptions. The leader runs the assignor locally and sends the result back in SyncGroup; the coordinator hands each member its part. Built-in assignors are range (per topic, contiguous ranges), round-robin, sticky (keeps the old assignment where possible) and cooperative-sticky. After that, each member polls its partitions. A background thread sends heartbeats every 3 seconds (heartbeat.interval.ms); if the coordinator hears nothing for 45 seconds (session.timeout.ms), it removes the member. Separately, if the application does not call poll() within max.poll.interval.ms (5 minutes), the client leaves the group, because the processing loop looks stuck. Every commit carries the generation number, so a zombie that wakes up after a rebalance and tries to commit is rejected.
The choice of assignor matters. The range assignor sorts partitions of each topic and gives each member a contiguous range, so partition 0 of topic A and partition 0 of topic B go to the same member; this is needed for joins between co-partitioned topics, but it can load the first members more when topics have few partitions. Round-robin spreads all partitions evenly. Sticky tries to keep the old owner of each partition and moves as few as possible, which matters when a member holds local state or caches per partition. The cost of an assignment is not the computation, which takes milliseconds, but the pause while members revoke and re-fetch.
A rebalance is triggered when a member joins, leaves or times out, or when the subscribed topics change (a new partition, or a regex subscription matching a new topic). In the original "eager" mode, every member first revokes all its partitions, then rejoins, then receives a new assignment. For the whole time, nobody consumes: a stop-the-world pause for the entire group. Cooperative rebalancing uses two rounds: first the group agrees on what moves, and only the partitions that must change owner are revoked; the others continue to be consumed. Static membership avoids the rebalance altogether for short restarts: the member keeps its identity and partitions until the session timeout expires.
The new protocol (KIP-848) removes the barrier. A member joins and stays alive with a single ConsumerGroupHeartbeat request. The coordinator keeps a group epoch that increases when membership or subscriptions change, computes the target assignment on the broker with a server-side assignor (uniform or range, both sticky), and each member converges to it on its own. The rules are simple: a partition is first revoked from its old owner and only then given to the new one, and a single heartbeat response never does both. Members do not stop partitions they keep. Heartbeat and session timing are controlled by the broker (group.consumer.heartbeat.interval.ms of 5 seconds and group.consumer.session.timeout.ms of 45 seconds by default). A consumer opts in with group.protocol=consumer; in Kafka 4.2 the default client setting is still classic, so existing applications must change it. Moving assignment to the broker means that assignor bugs are fixed by upgrading brokers, not every client.
Finally, offsets. A consumer commits the position it has processed to the coordinator, either automatically (enable.auto.commit, every 5 seconds by default) or by code. The delivery guarantee depends on the order: commit after processing gives at-least-once (a crash replays some messages); commit before gives at-most-once (a crash loses some). Different groups store separate offsets for the same partition, which is why they do not interfere. Lag is simply the log end offset minus the group's committed offset, and it is the main health metric.

example: A topic orders has 6 partitions and receives 6,000 messages per second, so each partition gets 1,000 per second. Each consumer instance can process at most 3,000 messages per second. A group "billing" has 3 members, C1, C2 and C3, with 2 partitions each. Each member handles 2,000 messages per second, which is 67% of its capacity. Auto commit is on, every 5 seconds.
Now C3 crashes (the machine is lost). The coordinator waits for the session timeout of 45 seconds. During this time, partitions P4 and P5 have no reader, and lag grows by 2,000 × 45 = 90,000 messages. When the timeout expires, the rebalance starts. With the classic eager protocol, C1 and C2 first stop all consumption, rejoin and receive a new assignment, which takes several seconds; in this time their own partitions also build lag. Afterwards C1 and C2 have 3 partitions each, which is 3,000 messages per second, exactly their capacity. The lag of 90,000 plus the lag from the pause never shrinks, because there is no spare capacity. This is the lesson: a group must be sized for N−1 members, or it cannot recover from a single loss. Compare a group of 6 members, one partition each, 1,000 messages per second per member. When one dies, the outage lag is 1,000 × 45 = 45,000 messages. One survivor takes the extra partition and runs at 2,000 per second, which is 67% of its capacity, so it has 1,000 per second spare and clears the 45,000 backlog in about 45 seconds.
What about duplicates? C3 had processed some messages since its last auto commit. Worst case it crashed just before the next commit, so up to 5 s × 2,000 = 10,000 messages were processed but not committed. The new owners of P4 and P5 restart from the last committed offset and process these 10,000 again. The application must be idempotent, or use transactions, or commit more often.
Scaling the other way: with 6 partitions, adding a 7th consumer does nothing, because only 6 partitions exist and one member would be idle. To go beyond 6 you must add partitions (which changes the key-to-partition mapping for keyed data) or use share groups. Lastly, static membership: if C1 is restarted for a deployment in 20 seconds and has group.instance.id set, the coordinator waits, C1 returns, and no rebalance happens. Without it, the restart causes two rebalances: one when C1 leaves and one when it comes back.
intuition: A team splitting a pile of mailbags so each bag has one sorter, and a notebook that records for each team how far into each bag they are; another team can sort the same mail independently with its own notebook.
The design is natural because the partition is already an ordered, independent unit. If two workers read the same partition, they would break the order and need coordination for every message. If each partition has exactly one reader, ordering and a simple offset are enough. Coordination then happens rarely, only when the set of readers changes, and not per message. The price is that the assignment must be agreed on by everyone, and the mechanism to agree (leases, generations, a coordinator) is the same as in any distributed system.
mistakes: People often think that adding consumers always increases throughput. In fact parallelism is capped by the number of partitions. A group with 12 members on 6 partitions has 6 idle members.
People often think a rebalance only moves the partitions of the failed member. In fact, in the classic eager protocol, all members give up all partitions and the whole group pauses; only cooperative rebalancing and the KIP-848 protocol move just the needed partitions.
People often think a slow consumer is harmless. In fact if it does not call poll() within max.poll.interval.ms, it is treated as failed and removed, which triggers a rebalance; the same messages are then reprocessed by another member, which can make the load worse and cause a rebalance storm.
People often think the new protocol (KIP-848) is on automatically in Kafka 4.0. In fact the brokers support it, but the client must set group.protocol=consumer, and the default remains classic. Some client features, such as client-side custom assignors, work differently.
People often think auto commit means "exactly the messages I processed". In fact it commits the position returned by the last poll at a timer, which may be before or after processing finished, so a crash can lose or repeat messages.
friction: Rebalances are the main operational pain. Each one pauses at least part of the group, and a group with large local state (for example Kafka Streams stores) may spend minutes rebuilding state after partitions move. Long GC pauses, slow processing and rolling deployments cause rebalances, and in the classic protocol a rebalance can trigger another one: while consumers are busy joining, they miss poll deadlines. Cooperative rebalancing needs two rounds, so it takes longer in total even though fewer partitions pause.
Throughput is capped by the partition count, and the order of keys limits what you can change; adding partitions later breaks the key-to-partition mapping. The one-reader-per-partition rule also causes head-of-line blocking: one slow message blocks all later messages of that partition. Lag can be uneven when a few partitions are hot. The group state is also a single point of attention: a broker holding a coordinator that fails over needs time to reload the state, and the offsets topic needs care (replication factor, compaction health).
Delivery guarantees are not built in: exactly-once needs transactions or idempotent processing in the application. The new protocol removes much of this pain, but it is recent, still opt-in on clients, and some custom assignor use cases are not yet covered. Many tools and client libraries in other languages lag behind the Java client.
practice: Choose the number of partitions from the peak parallelism you will ever need, with room to grow, because it cannot easily go down and changing it later affects keyed ordering. Size the group for N−1 members. Keep processing in the poll loop short, or hand work to a thread pool but commit only when the work is done. Keep max.poll.records small enough that one batch finishes well inside max.poll.interval.ms.
Use static membership (group.instance.id) and a session timeout longer than your typical restart time for stateful or slow-starting consumers. Use the cooperative-sticky assignor on classic clients, or try group.protocol=consumer on clients and brokers that support it, after testing. Handle onPartitionsRevoked by committing offsets and flushing state. Make processing idempotent, and commit offsets after processing, usually with manual commits. For exactly-once pipelines, use transactions and read_committed.
Monitor lag per partition (not only the sum), rebalance rate and duration, and the time since the last poll. Alert on a rising lag, not only on a high one. Use different group.ids for different applications and never share a group.id between unrelated services, because they would split the partitions. If you need many workers on few partitions, or per-message acknowledgement and retries, look at share groups instead.
tradeoffs: Choose exclusive partition assignment (consumer groups) when you need ordering per key and simple at-least-once processing with checkpointed offsets, as in stream processing, CDC and stateful consumers. Choose share groups when the work is independent jobs, order does not matter, and you want more workers than partitions or per-record retries. You give up ordering and simple offset commits with share groups, and parallelism above the partition count with consumer groups.
Choose the classic protocol with cooperative-sticky when your clients are old or you depend on custom assignors; choose the KIP-848 protocol for large groups, frequent deployments, or when rebalance pauses hurt, since it removes the group-wide barrier and moves logic to the broker. You give up some client-side control with the new protocol.
Choose a short session timeout (6 to 10 seconds) when fast failure detection matters more than stability; choose the default 45 seconds or longer when GC pauses and network blips are common, because every false failure costs a rebalance. Choose static membership when restarts are short and the group has expensive state; you give up fast reaction to a real failure, since the member's partitions wait until the session timeout.
Choose more partitions for more parallelism and headroom; choose fewer when partitions are costly (more files, more replication traffic, more rebalance work, longer recovery after a broker failure). A common range is tens, not thousands, per topic.
interview: Why can't two consumers in the same group read the same partition? || It would break ordering and force per-message coordination. With one reader per partition, a single offset describes progress, and coordination is only needed when membership changes. Share groups relax this by locking individual records instead.
What happens when a consumer is slow but alive? || If it keeps heartbeating but does not call poll() within max.poll.interval.ms, the client leaves the group and a rebalance starts. Its partitions are reassigned, uncommitted work is repeated, and a later commit from it is rejected by the generation check. Fix it by shortening batches, lowering max.poll.records, or raising the interval.
How does the group avoid a zombie consumer that was declared dead and comes back? || Each rebalance increases the generation (member epoch). Commits and heartbeats carry it, and the coordinator rejects old ones, so the zombie cannot commit offsets for partitions it no longer owns.
Compare eager, cooperative and KIP-848 rebalancing. || Eager revokes everything and pauses the whole group. Cooperative revokes only partitions that move, but needs two rounds and still has a group-wide join barrier. KIP-848 has the broker compute a target assignment and members reconcile independently, revoking before assigning, so unaffected members keep consuming.
Your group has 6 partitions and lag grows. How do you decide what to do? || First check whether consumers are the limit (CPU, downstream calls, processing time per record) or the partition cap. If members are below the cap and busy, add members up to 6. If at the cap, increase partitions (accepting key remapping), speed up processing, batch downstream calls, or use share groups for order-free work.
Why do offsets for consumer groups live in a compacted Kafka topic? || Each commit overwrites the previous one for the same (group, topic, partition) key, so only the latest matters. A compacted topic is replicated, bounded in size by the number of keys, and replayable by a new coordinator after failover.
quiz: How many members of one group can actively read a topic with 8 partitions? || At most 8. Each partition is assigned to exactly one member, so additional members stay idle.
Why does the generation number matter? || It fences old members. After a rebalance, requests from a member with an old generation are rejected, so a zombie cannot commit offsets or keep consuming partitions that now belong to someone else.
What is the difference between how cooperative rebalancing and the eager protocol treat partitions that do not move? || Eager revokes all partitions from all members and stops consumption; cooperative revokes only partitions that change owner, so other partitions keep being consumed.
A group of 3 consumers handles 6,000 msg/s with 3,000 msg/s capacity each. One consumer dies. What happens to lag? || The remaining two need 3,000 msg/s each, exactly their capacity, so the backlog built during the outage never drains. The group needs spare capacity, for example 4 members.
When should you pick KIP-848 over the classic protocol with cooperative-sticky? || When groups are large or deployments frequent and rebalance pauses or complexity hurt, and your clients and brokers support it. The broker computes assignment and there is no group-wide barrier, but you must opt in and may lose custom client-side assignors.

@@ sharegroups
value: A consumer group gives each partition to one consumer. This is perfect for ordered stream processing, but it is a poor fit for a work queue. Imagine a topic with 6 partitions and jobs that take two seconds each, such as sending emails or calling a slow API. At most 6 consumers can work at the same time, however many machines you own. One slow job holds up every job behind it in the same partition. And you can only move the offset forward, so you cannot say "job 17 failed, retry it later, but I finished job 18". Teams solved this by running a separate queue system (RabbitMQ, SQS), by over-partitioning topics, or by adding libraries on top of the consumer.
Share groups (KIP-932, "Queues for Kafka") put queue behaviour inside Kafka. Many consumers in one share group may read the same partition at the same time. The broker hands each record to one consumer under a time-limited lock, and the consumer acknowledges each record separately: ACCEPT when done, RELEASE to give it back for another try, REJECT when it can never be processed. If the consumer does nothing, the lock expires and the record becomes available again, with a delivery count that goes up. After a limit (5 by default) the record is archived as failed. The log itself does not change: records stay in the topic in order, and ordinary consumer groups can still read the same topic.
The idea builds on three lower concepts. Consumer groups (L2) supply the membership machinery: share group members join through a coordinator, send heartbeats, and are removed when they stop, but they are not given exclusive partitions. Delivery guarantees (L2) supply the model: each record is delivered at least once, acknowledged individually, and its delivery attempts are counted. Leader election and leases (L2) supply two things: the broker that leads a partition also owns the share state of that partition, so there is one authority for who holds which record, and the acquisition lock is a lease, a right that expires unless it is renewed. Share groups appeared as early access in Kafka 4.0 (March 2025), as preview in 4.1, and were declared production-ready in Kafka 4.2 (February 2026).
terms: Share group — a group of consumers that cooperatively read the same partitions; records, not partitions, are the unit of assignment.
Acquisition lock — a time-limited claim by one consumer on one delivered record; the default is 30 seconds.
Acknowledgement — the consumer's answer for a record: ACCEPT (done), RELEASE (retry elsewhere), REJECT (do not retry), and since Kafka 4.2 RENEW (extend the lock).
Delivery count — how many times a record has been handed out; at the limit (5 by default) the record is archived instead of delivered again.
Share-partition — the state a share group keeps for one topic partition: which offsets are available, acquired, acknowledged or archived.
In-flight window — the offsets between the share-partition start offset and end offset; its size is capped (2,000 records by default).
Share coordinator — the broker component that saves share-partition state durably, in the internal topic __share_group_state.
Archived — a record that will not be delivered again, because it was rejected, reached the delivery limit or is before the start offset.
history: Kafka has always had two ways to scale reading: more partitions, or more groups. For jobs, neither is natural. Users built queues on top of Kafka with tricks: many partitions (thousands) with one consumer thread each; libraries such as Confluent's Parallel Consumer, which tracks individual acknowledgements on the client and commits only the contiguous prefix; or dead-letter topics written by the application. Others left Kafka for RabbitMQ, SQS or Pulsar (whose "shared" subscription mode has long offered individual acknowledgement) for work-queue jobs.
KIP-932 was proposed to bring this inside the broker, so that one platform could serve streams and queues. The design reuses the log: the log stays an immutable, ordered, shared record of events, and a new layer on the broker tracks the delivery state of records for each share group. It reached early access in 4.0 (March 2025) and preview in 4.1, with a first set of improvements and fixes in each release. Kafka 4.2 (February 2026) called it production-ready and added a RENEW acknowledgement (KIP-1222), share-partition lag metrics (KIP-1226), a choice between a soft and a strict limit on records per fetch (KIP-1206), and adaptive batching in the coordinators (KIP-1224). Features still missing in 4.2 include a built-in dead-letter topic for share groups: the 4.2 release notes mention dead-letter support only for Kafka Streams.
how: The broker side has two parts. The first is group management. A share consumer joins with a ShareGroupHeartbeat request, similar to the new consumer protocol of KIP-848. The group coordinator tracks members, session timeouts (45 seconds by default) and subscriptions, but it does not hand out partitions to individual members for exclusive use. A share group can have up to 200 members by default, and the number of members is not tied to the number of partitions. This is what consumer groups contribute, and what share groups change: the group is a membership and liveness mechanism, not an exclusive partition assignment.
The second part is the share-partition, which lives on the broker that leads the topic partition. It keeps a window of offsets between two pointers. The share-partition start offset (SPSO) marks the first record that is not yet finished. The share-partition end offset (SPEO) marks the last record that has been handed out. Between them, each record has a state: Available, Acquired (locked to one consumer), or Acknowledged; everything before the SPSO is Archived. A new share group starts at the latest offset by default, controlled by share.auto.offset.reset. Because the partition leader is the only one that hands out records, no two consumers can acquire the same record at the same time; the same leader election that decides partition leadership decides who owns the share state.
When a consumer fetches, the leader selects the next Available records, marks them Acquired for this consumer with a lock that expires after group.share.record.lock.duration.ms (30 seconds by default), increments their delivery count, and returns them as batches. The number of records in the window is capped by group.share.partition.max.record.locks (2,000 by default), so a slow group cannot make the broker track unlimited state. The consumer processes the records and acknowledges each one. In the default implicit mode (share.acknowledgement.mode=implicit), all records returned by a poll are accepted when the next poll or commit is called; in explicit mode the application calls acknowledge() for each record with ACCEPT, RELEASE or REJECT. ACCEPT moves the record to Acknowledged. RELEASE moves it back to Available, and another consumer, or the same one, will get it with a higher delivery count. REJECT archives it, for records that can never succeed. RENEW extends the lock for a long-running record, so a slow but healthy job does not lose it.
When a lock expires without an acknowledgement, which happens when the consumer crashed, was too slow or lost its session, the record returns to Available. Each acquisition adds one to its delivery count. If a record has been delivered the maximum number of times (group.share.delivery.count.limit, 5 by default), the next failure archives it instead of releasing it, so poison messages do not circulate forever. The count is approximate: it is updated by the leader, and a leader change or a crash could repeat a delivery. Delivery is therefore at-least-once, and consumers must be idempotent.
The SPSO moves forward over the contiguous prefix of records that are Acknowledged or Archived. A stuck record at the front keeps the SPSO behind it while later records are processed, which is why the in-flight window is capped. The state itself must survive broker failure. The share coordinator writes snapshots and updates of each share-partition's state to the internal topic __share_group_state (50 partitions by default), and the state is protected by epochs (a state epoch and the partition leader epoch), the same fencing idea as elsewhere in Kafka, so a deposed leader cannot overwrite newer state. A new leader reads the state and continues.
Acknowledgements are sent together with the next fetch request or a commit, so one round trip can carry many of them. The cost on the broker is therefore related to the number of records in flight, not to the number of requests. Finally, ordering and reading rules. Records within a batch are handed out in offset order, but across consumers and across retries there is no ordering guarantee: a released record comes back after later ones have been processed. Share consumers can read in read_committed mode (the default is read_uncommitted), which hides records of open or aborted transactions. And since the topic is an ordinary topic, a consumer group and a share group can read it side by side.

example: A topic jobs has 3 partitions. Each record is a job that takes 2 seconds on average. First, the consumer-group version: at most 3 consumers work in parallel, so throughput is 3 / 2 = 1.5 jobs per second, even if you have 12 machines. A job that hangs for 60 seconds blocks everything behind it in its partition.
Now the share-group version with 12 workers, each processing one record at a time. All 12 can read from the 3 partitions at the same time. Throughput is up to 12 / 2 = 6 jobs per second, four times higher, and no partition is blocked by a single slow job.
Follow one partition. Offsets 0 to 9 are in the log, nothing is acknowledged, and SPSO is 0. Worker W1 fetches and acquires offsets 0 to 4 with locks of 30 seconds; W2 acquires 5 to 9. Delivery counts are 1. W1 finishes 0, 1 and 2 and sends ACCEPT. Offset 3 hits a temporary error (a downstream timeout), so W1 sends RELEASE: offset 3 is Available again with count 1. Offset 4 never gets an answer, because W1 crashes. W2 accepts 5 to 9 within 10 seconds. The SPSO now sits at 3, because offset 3 is not finished.
W3 fetches and gets offset 3, count 2. It succeeds, and ACCEPT moves it forward. After 30 seconds the lock on offset 4 expires, and it becomes Available with count 1 (it was delivered once). W4 acquires it with count 2 and accepts. Now offsets 0 to 9 are all Acknowledged and SPSO jumps to 10. If offset 4 were a poison message that fails every time, it would be delivered 5 times: after the fifth failed attempt it is archived. The worst case is 5 × 30 s = 150 s if it fails by lock expiry each time, or about 5 × 2 s = 10 s if the worker releases it after each failed attempt.
A sizing check on the locks. A single-threaded worker takes 2 s per record and the lock lasts 30 s, so it can safely hold about 15 records. If the application fetches 500 records in one poll, only about the first 15 are processed in time; the rest expire at 30 s, become Available, and are delivered to others, so the same job runs twice. The fix is to fetch small batches (about 5 to 10 here), use RENEW for slow records, or raise the lock duration. Finally, the window: with 3 partitions and 2,000 locks each, at most 6,000 records can be in flight at once, which is much larger than 12 workers need.
intuition: A ticket counter on top of a ledger: the ledger keeps every entry in order, but any free clerk can take the next ticket, and a ticket not returned in 30 seconds goes back to the counter.
The design is natural because it separates two things Kafka had joined: storage and delivery state. The log is cheap, ordered and immutable, and it is good at being a record. Who is working on which record is a different kind of state, changing all the time, and a log offset alone cannot express it, because an offset says "everything before this is done" and nothing about records out of order. By tracking state per record in a small window next to the log, the broker lets many workers share a partition, while the data stays a normal Kafka topic that other groups can read in order.
mistakes: People often think share groups replace consumer groups. In fact they are for a different job. Consumer groups keep ordering per partition and give simple offset-based replay and stream processing. Share groups give up ordering for parallelism and per-record retries.
People often think share groups give exactly-once processing, because every record is acknowledged. In fact delivery is at-least-once. A lock can expire while a slow consumer still works, and the record is then handed to someone else. Consumers must be idempotent.
People often think a share group has a committed offset like a consumer group. In fact it has a share-partition window with a state per record. The SPSO moves only when a contiguous prefix is finished, and a record stuck at the front holds the SPSO back.
People often think the delivery limit makes a dead-letter queue. In fact after the limit the record is only archived, which means the group skips it. Nothing is copied to another topic in 4.2, so the application must catch failures and write its own dead-letter record before it sends REJECT or ACCEPT.
friction: There is no ordering guarantee, so share groups cannot serve keyed state or any logic where event order matters. Redelivery means duplicates. There is no built-in dead-letter topic yet, and no per-record delay or backoff before a retry: a released record is available immediately, which can cause a tight retry loop against a failing dependency. Applications must build their own backoff.
Tuning is subtle. The lock duration, batch size and processing time must fit together: too short and records are processed twice, too long and a crashed worker's records are stuck for a long time. The in-flight cap means a stuck record at the front lets the window fill, and after 2,000 further records are handed out, no new records are delivered for that partition until the window moves. Delivery counts are approximate. Share groups add load on the brokers: the share-partition leader keeps per-record state in memory, and the share coordinator writes state updates to an internal topic, so a high rate of small acknowledgements costs more than an offset commit every few seconds. Batching of acknowledgements and the adaptive linger in 4.2 reduce this, but not fully.
The ecosystem is new. Client libraries outside Java, connectors, monitoring tools and operational know-how follow slowly. Compared with mature queue systems, features such as priority, delayed delivery, per-message TTL and a built-in dead-letter queue are missing. Clusters with fewer than 3 brokers need extra settings for the internal share-state topic.
practice: Use share groups for independent jobs: sending notifications, calling external APIs, image or document processing, fan-out of tasks created by a producer, where you want more workers than partitions and a failed job should not block the others. Keep consumer groups for streams, aggregations and anything keyed or ordered.
Make processing idempotent, with a stable record ID in a database unique key or a deduplication table. Choose the lock duration as a few times your normal processing time per batch, and set the batch size so that batch time fits inside it; use RENEW for the rare long jobs. Choose explicit acknowledgement mode if you want per-record control: ACCEPT on success, RELEASE for transient errors, REJECT for permanent ones. Before you REJECT, write the failed record and the error to your own dead-letter topic. Add delay with an application-level retry topic if a failing downstream needs backoff.
Watch the new lag metrics (KIP-1226), the number of in-flight records per share-partition, the delivery count distribution, and the time between acquisition and acknowledgement. Alert when records reach the delivery limit. Test failure paths: kill a worker mid-batch and confirm the records come back after the lock time. Start from the latest offset or from the earliest with share.auto.offset.reset, depending on whether the group should process history. Run the same topic with a consumer group for audit or replay if you need an ordered view.
tradeoffs: Choose a consumer group when order per key, replay from any offset and checkpointed state matter; choose a share group when records are independent jobs and you need more workers than partitions or per-record retry. You give up ordering and cheap offset-based replay with the share group, and parallelism above the partition count with the consumer group.
Choose share groups on Kafka when you already run Kafka and want to avoid a second system (one set of security, monitoring and retention rules), and when throughput is high. Choose a dedicated queue (SQS, RabbitMQ, Pulsar) when you need delayed delivery, priorities, per-message TTL, a built-in dead-letter queue, or a fully managed service with no cluster to run. You give up those features on Kafka, and on the dedicated queue you give up the shared log, replay and the unified platform.
Choose a short lock (10 to 30 seconds) when jobs are short and fast recovery from a crashed worker matters; choose a long lock (minutes) with RENEW for jobs that take long and where double processing is expensive. A short lock risks duplicates; a long lock delays retries after a crash.
interview: What problem do share groups solve that consumer groups cannot? || In a consumer group, parallelism is capped by the partition count and a slow record blocks its partition; progress is a single offset. Share groups lock individual records and acknowledge them one by one, so any number of workers can share a partition and a failed record can be retried without blocking others.
How does a share group avoid giving the same record to two consumers? || The leader of the topic partition owns the share-partition state. When it hands out a record, it marks it Acquired with a lock and an expiry, and it will not hand it out again until the lock is released, acknowledged or expired. State is persisted by the share coordinator and fenced with epochs.
What are the delivery guarantees, and what must the application do? || At-least-once with an approximate delivery count. A lock may expire while work continues, or a leader may change, so a record can be processed twice. The application needs idempotent processing, and its own dead-letter handling, because the broker only archives records at the delivery limit.
How would you handle a poison message? || Let the delivery count limit stop it, but handle it earlier: catch permanent errors, write the record to a dead-letter topic yourself, then REJECT. Alert on records near the limit. Remember that a stuck record at the front holds back the SPSO and fills the in-flight window.
Why not simply add partitions to a consumer group? || Partitions are costly (files, replication, recovery time, rebalance work), changing the count remaps keys, and it does not remove head-of-line blocking or allow per-record retry. It also requires planning for the peak parallelism ahead of time.
How do you choose lock duration and batch size? || The lock must be longer than the time to process one whole fetched batch, with margin, or records are processed twice. With 2 s jobs and 30 s locks, a batch of about 10 is safe. Use RENEW for long jobs and raise the lock only if retries after a crash can wait.
quiz: How does a share group differ from a consumer group in assigning work? || A consumer group assigns whole partitions to single members. A share group lets many members read the same partition, with each record locked to one member and acknowledged individually.
What happens if a consumer acquires a record and then crashes? || Its acquisition lock expires after about 30 seconds by default. The record becomes Available again, its delivery count already includes the failed attempt, and another consumer will receive it.
Why must consumers of a share group be idempotent? || Delivery is at-least-once: locks can expire during slow processing and leaders can change, so the same record may be delivered and processed more than once.
Jobs take 3 seconds each and the lock is 30 seconds. How many records can a single-threaded worker safely hold at once? || About 10 (30 / 3), and fewer to keep a margin. A bigger batch means the last records expire and are delivered to another worker as well.
When would you choose a dedicated queue such as SQS instead of Kafka share groups? || When you need delayed delivery, priorities, message TTL or a built-in dead-letter queue, or you want a managed service and have no need for the shared log and replay.

@@ virtualdom
value: A web page is a tree of elements, the DOM (Document Object Model). Changing it by hand is error-prone: to show a new message in a chat you must find the right node, create a child, set its text, update the unread counter, hide the empty-state banner, and keep all of this consistent when five different events can change the same screen. The number of possible transitions between screens grows much faster than the number of screens. Virtual DOM diffing removes the problem by changing what the programmer writes. You write a function from state to a complete description of the UI, as if you were building the page from scratch every time. The library keeps the previous description, compares it with the new one, and changes only the real DOM nodes that differ.
This is the basis of declarative UIs such as React, Preact and Vue. The programmer says what the screen should look like for the current state; the library finds out how to get there. It also gives a second benefit that matters as much as speed: because the description is plain data in memory, it can be built on a server, built in pieces, paused, thrown away, tested without a browser, or applied to something other than HTML, such as native mobile views (React Native).
Trees (L3) provide the structure and the algorithm. The UI description is a tree of lightweight element objects, the DOM is a tree, and the library walks the two trees together, depth first, collecting a list of differences. The exact solution of this problem, tree edit distance, costs O(n³) for a tree of n nodes, which is far too slow for a page with thousands of elements. React replaces it with two assumptions that hold in nearly all interfaces, and the cost falls to O(n). Everything else in the idea, the keys, the component boundaries and the commit step, is built around those two assumptions.
terms: Virtual DOM — a lightweight tree of plain JavaScript objects that describes what the UI should look like; it is not the browser's DOM.
Element — one node of the virtual tree: a type (such as "div" or a component function), its props and its children.
Reconciliation — the process of comparing the new element tree with the previous one and deciding what to create, update, move or remove.
Diffing — the comparison step itself; it produces a list of changes.
Commit — the step that applies the list of changes to the real DOM; in React it runs synchronously, in one go.
Key — a stable identifier that the programmer gives to each child in a list, so the library can match children between renders even if they move.
Component — a function (or class) that takes props and state and returns elements; its state is attached to its position in the tree.
Fiber — React's internal data structure (since React 16) that represents one unit of work in the tree, so that rendering can be split, paused and resumed.
history: Before 2013, there were two main ways to build dynamic pages. The first was to change the DOM directly, with jQuery-style code, which becomes hard to keep consistent as an application grows. The second was templates (Handlebars, Mustache, Backbone views) that render a new HTML string and replace a whole section with innerHTML. That is simple, but the browser then rebuilds all nodes, and the user loses focus, scroll position and text typed into inputs. Facebook faced this in its News Feed and chat, and also in Instagram.
Jordan Walke at Facebook built a prototype in which components describe the whole UI and a library updates the DOM efficiently, first used in Facebook's feed (2011) and Instagram (2012). Facebook presented React publicly at JSConf US in May 2013 and open-sourced it. At first many developers disliked mixing markup (JSX) with code, but the model spread quickly. Other libraries used the same idea: Elm's virtual-dom, Mithril, Snabbdom (2015, whose design Vue 2 adopted), Preact and Inferno.
The algorithm had to be fast, and the theory said it could not be exact. Tree edit distance was studied from the 1970s; Zhang and Shasha gave a practical algorithm in 1989, and Demaine and others in 2007 showed O(n³) is the best known worst-case bound. React's team chose heuristics that give O(n). In 2017, React 16 shipped Fiber, a rewrite of the reconciler as a linked structure that lets rendering be interrupted; it led to concurrent rendering in React 18 (March 2022). Meanwhile critics pointed out that the diff is overhead that a compiler can avoid: Svelte (Rich Harris, 2016 and later, with an essay "Virtual DOM is pure overhead" in 2018) compiles components into direct DOM updates, Solid uses fine-grained signals, and Vue 3 (2020) uses its compiler to mark static parts so the diff can skip them. React answered with the React Compiler, released as version 1.0 in October 2025, which adds memoization automatically at build time so that fewer components re-render.
how: Start with a component, a function from props and state to elements. An element is a plain object such as {type: "li", props: {className: "row"}, children: ["Buy milk"]}. Calling the component produces a tree of such objects. This is cheap: it creates JavaScript objects, no DOM node, no layout, no painting. The library keeps the tree from the last render (React keeps two, a current tree and a work-in-progress tree, and swaps them when the update is committed). When state changes, it calls the components again (the render phase) and gets a new tree. Then it compares the two.
The comparison walks both trees from the root down, one level at a time, under two rules. Rule one: elements of different types produce different trees. If the old element at this position was a div and the new one is a span, or a different component, the library does not try to find similarities; it removes the old subtree (and its state) and builds the new subtree from scratch. Rule two: for lists of children, the programmer can give a key; children with the same key are assumed to be the same thing. These two rules make the problem linear. The exact algorithm would need to compare every node of one tree with every node of the other, and find the cheapest mapping. React only compares nodes at the same position in the same parent, or with the same key in the same list, so each node is visited once. This is what trees contribute: the recursive structure of the problem, in which a mismatch at the top removes the need to compare anything below it.
When two elements have the same type, the library keeps the existing DOM node and compares the props. For a DOM element, it updates only the attributes and style properties that changed, and then recurses into the children. For a component element, the same instance is kept, so its state survives. The library updates its props, calls it again, and compares the new result with the old one. This is why state in React belongs to a position in the tree: the same component type at the same place keeps its state, a different type or a different key at that place starts fresh.
Lists need care. Without keys, the library compares children by index. If a new item is inserted at the front of a list of 100 rows, every row is now compared with its predecessor's data, and nearly all of them are updated; worse, any component state (a half-typed input) stays at the index and now appears to belong to a different item. With keys, the library builds a map from key to old child (a hash table), finds that 100 old children still exist, and creates only the one new row. Keys must be unique among siblings and stable across renders; ids from the data are right, array indices are right only for lists that never reorder, and random keys defeat the purpose, because every render creates new keys and so recreates every node.
The diff does not touch the DOM; it produces a list of effects (insert this node, set this attribute, remove that node). The commit phase applies them in one batch. This split is what Fiber exploits. The render phase, which calls components and diffs, only reads and builds in-memory data; it can be paused, resumed, prioritised, or discarded, for example if the user types again before the last update has finished. The commit phase mutates the DOM and cannot be interrupted, so the page never shows a half-finished state. Updates from event handlers are also batched, so several setState calls lead to one render. The cost model is therefore: render cost proportional to the number of components that re-render (all components below the one whose state changed, unless they are memoized), diff cost proportional to the size of the trees compared, and DOM cost proportional to the number of actual changes. Because DOM changes trigger style recalculation, layout and painting, which are the expensive parts, minimizing them is the point. Memoization (React.memo, useMemo, and now the compiler) cuts the first two costs by skipping subtrees whose inputs did not change.

example: A to-do list has 1,000 rows. Each row is a component with a checkbox, a label and a delete button. The user ticks one checkbox.
First, the work. State lives in the list component, which re-renders. It calls the row component 1,000 times and produces a tree of about 1,000 rows × 4 elements = 4,000 element objects. The diff compares them with the old 4,000 elements by key. 3,999 of them are equal; one checkbox has checked changed from false to true. The effect list has one item: set the checked property of one DOM input. Roughly, producing and comparing several thousand small objects takes on the order of a millisecond or a few in a modern browser, and one DOM property update costs far less than rebuilding 1,000 rows (which would also lose focus). If the rows are wrapped in React.memo and their props are the same, React skips 999 of the 1,000 render calls entirely, leaving one row to render and diff.
Second, the order problem. The list is [Milk, Bread, Rice]. The user adds "Eggs" at the top. With index keys, the old children are at 0, 1, 2 and the new ones at 0, 1, 2, 3. Position 0 (was Milk) is now Eggs: update its text. Position 1 (was Bread) is now Milk: update. Position 2 (was Rice) is now Bread: update. Position 3 is new (Rice): insert. That is three updates and one insert. With keys milk, bread, rice, and egg, the diff finds that three keys are unchanged and egg is new: one insert. For a list of 1,000 items, index keys would give 1,000 updates and one insert, instead of one insert.
Third, the bug that keys prevent. Each row has a text input for a note. The user types "ask for 2 liters" in the Milk row, then adds Eggs at the top. With index keys, the input state belongs to position 0, so the text "ask for 2 liters" now appears in the Eggs row, while the Milk row has an empty input. With keys, the input's state moves with the Milk row. This is not a speed issue but a correctness issue, which is why the key rule is more important than it first looks.
Finally, the type rule. If a panel renders <Form /> when the user is logged out and <Profile /> when logged in, switching destroys the whole old subtree and builds a new one. This is correct (the two are different things), but if you wrapped a stable subtree in a div in one branch and a section in the other, you would accidentally reset its state. To force a reset deliberately, change the key.
intuition: Compare the new blueprint with the old one, and send the workers to renovate only the rooms that changed.
The idea is natural because it moves the hard part to the cheap side. Thinking about "what changed" is hard for people, because the number of cases explodes; thinking about "what should it look like now" is easy. Computers are good at the comparison, and comparing two small in-memory trees is much cheaper than the slow operations the browser performs (layout and paint) when the real tree changes. The two heuristics are natural because user interfaces rarely move a large subtree to a different place and rarely replace a div with a table having the same contents, so a node's position and type are good evidence of identity.
mistakes: People often think the virtual DOM is faster than the real DOM. In fact it is extra work on top of the DOM: it must create the new tree and diff it before any DOM update. It is fast enough, and much faster than naive re-rendering, but a hand-written or compiler-generated minimal update can be faster. Its real benefits are simplicity of the programming model and control over when work happens.
People often think React compares the whole old and new trees to find the minimum number of changes. In fact it uses heuristics. It does not detect that a subtree moved to a different parent; it destroys and rebuilds it. The result is correct but may not be minimal.
People often think "re-render" means the DOM is rebuilt. In fact re-rendering means calling the component function and producing elements. Most re-renders end with no DOM change at all. The cost is CPU time for calling components and diffing, which can be large for big trees, and that is why memoization exists.
People often think array indices are fine as keys. In fact they are fine only for static lists. When items are inserted, removed or reordered, the index key matches the wrong items, which causes extra DOM work and, more seriously, state and input values that stay at a position and show up in the wrong item.
friction: The diff has a cost even when nothing changes. Every state change re-renders a whole subtree by default, so a state held too high in the tree makes a large part of the page re-render on every keystroke. Developers then add memoization by hand (React.memo, useMemo, useCallback), which is easy to get wrong: a new object or function created in each render breaks the equality check and silently removes the benefit. The React Compiler automates much of this, but not all patterns can be optimized, and it adds a build step.
The heuristics can fail. Components that look alike but have different types are destroyed and rebuilt; unstable keys cause rebuilds; subtrees that move between parents lose their state. Very large lists need windowing (render only visible rows), because even a perfect diff of 100,000 rows is too slow and the DOM itself becomes too heavy. Animations and fine-grained updates (a counter changing 60 times per second) are costly when each tick goes through render and diff; libraries then bypass React and write to the DOM directly.
Memory is also used: the library holds the old and new trees (and, in React, a work-in-progress and a current fiber tree). Server rendering and hydration need the server and client trees to match exactly. And the model competes with alternatives that avoid the diff: Svelte's compile-time updates, Solid's and Vue's reactivity (signals), Lit's template updates. They do less work per update in common cases, but give up the simple "re-run everything" model, and some need a compiler or special syntax.
practice: Give every item in a list a stable key from your data (a database id), never the index for lists that can change, and never a random value. Keep state as low in the tree as possible, so that a change re-renders a small subtree. Do not define components inside other components, because each render creates a new component type and so destroys the subtree's state. Keep render functions pure: no mutation, no network calls, no random numbers, because React may call them more than once, or discard the result.
Measure before optimizing. Use the React DevTools Profiler to see which components render and why. Common fixes, in order: move state down, split a component, memoize an expensive child with React.memo with stable props, window long lists, debounce high-frequency input. If you use the React Compiler, check which components it skips, and keep code simple enough for it to analyze. For lists with expensive rows, memoize the row, not the list.
tradeoffs: Choose a virtual DOM framework (React, Preact, Vue) when you want a simple model, a large ecosystem and the ability to render on the server, in native views or in tests, and when your screens are not extremely update-heavy. You give up some raw update speed and pay for diffing and memoization work. Choose a compile-time or signal-based framework (Svelte, Solid) when you need small bundles, frequent fine-grained updates, or the lowest CPU on weak devices; you give up part of the ecosystem and some flexibility of "just JavaScript".
Choose keys from stable ids when the list changes; choose index keys only for static lists that never reorder, filter or insert. The cost of a wrong choice is not only speed but wrong state.
Choose to keep state high when many components need it and it changes rarely; choose to keep it low or local (or use an external store with selectors) when it changes often, because every change re-renders the owner's subtree. Choose memoization when a subtree is expensive (hundreds of elements or heavy computation) and its props are stable; skip it for cheap components, because the comparison costs time and memory too.
Choose list windowing (react-window and similar) once a list passes a few hundred rows with complex content; below that, the simple full list is easier to build and test.
interview: Why is general tree diffing O(n³), and how does React get O(n)? || The exact minimum edit script between two ordered trees needs to consider mappings between all node pairs, which costs O(n³) in the best known algorithm. React assumes elements of different types give different trees, and that keys identify stable children. Then it compares only nodes at the same position or key, visiting each node once.
Why do keys matter, and what goes wrong with index keys? || Keys let the library match children between renders even if their order changes. With index keys, an insertion at the front shifts every item, so each position is updated, and component state such as an input value remains at the position and ends up on the wrong item.
Is the virtual DOM faster than direct DOM updates? || No. It adds work, and a hand-optimized direct update is faster. It is fast enough, and it makes updates predictable. Its value is the declarative model, batching, and the ability to separate rendering from applying, which enables concurrent rendering and other hosts.
What does Fiber change, and why does it need the virtual tree to be a data structure? || Fiber represents the render work as a linked structure that can be paused, resumed and prioritised, so a long render does not block input. This works because the render phase only builds in-memory data and never touches the DOM; only the commit phase mutates the DOM, in one uninterruptible step.
A list of 5,000 rows is slow on every keystroke in a search box above it. How do you find and fix it? || Profile to see that the whole list re-renders on every keystroke because the query state sits above it. Move the input state down or separate it, memoize the rows with stable props, defer the filtered list update, and window the list so only visible rows are in the DOM.
quiz: What are the two assumptions that make React's diffing O(n)? || Elements of different types produce different trees, so the library does not look inside them; and keys identify which children are stable across renders, so only same-position or same-key children are compared.
Why is state in a component lost when the element type at its position changes? || State belongs to a position in the tree. When the type at that position is different, the library treats it as a different thing, removes the old subtree with its state and mounts a new one.
Why is it correct to say that "re-rendering" is not the same as "updating the DOM"? || Re-rendering calls component functions to build a new virtual tree. The diff then finds changes, and only those are applied to the DOM. Many re-renders produce no DOM change.
A list of 1,000 items gets a new item at the front. How many DOM operations occur with index keys versus stable keys? || With index keys, about 1,000 text or attribute updates and 1 insert, since every position now holds different data. With stable keys, 1 insert.
When would you choose Svelte or Solid over React? || When bundle size, CPU cost per update or very frequent fine-grained updates matter most, and you can accept a smaller ecosystem and compile-time or signal-based reactivity instead of the re-render-and-diff model.
