@@ flink
value: Apache Flink is the reference engine for stateful stream processing: computations that run continuously over unbounded data, keep large amounts of state (counts, joins, sessions, model features) and still produce correct results after failures. Where Spark grew from batch toward streaming, Flink was designed stream-first, processing each record as it arrives with low latency and treating batch as a bounded stream.
Its value shows up wherever freshness and correctness both matter: fraud detection that must react in milliseconds, real-time ad pacing and frequency capping, streaming ETL into lakehouses, real-time feature pipelines for machine learning, and event-driven applications that keep state per user or device. Alibaba, Uber, Netflix, LinkedIn, Pinterest and many ad-tech companies run it at large scale, and most cloud providers offer it as a managed service.
history: Flink began as the Stratosphere research project at TU Berlin and other German universities (2009–2014), entered the Apache incubator in 2014 and became a top-level project that December. Its founders started data Artisans (later Ververica, acquired by Alibaba in 2019). Key ideas arrived early: lightweight asynchronous barrier snapshots (Carbone and colleagues, 2015) for exactly-once state, and full support for event time and watermarks following Google's Dataflow model. Flink SQL and the Table API made it accessible beyond Java and Scala developers.
Flink 2.0 (March 2025) was the first major version in nine years. It introduced disaggregated state management, storing state primarily in remote object storage (through the ForSt state backend) with local caching, so that rescaling and recovery no longer require copying large state between machines. It also removed the old DataSet API, deepened SQL support with materialized tables, and added better integration with lakehouse formats such as Apache Paimon and Iceberg. The 2.x line has continued since.
how: A Flink job is a dataflow graph of operators running as parallel tasks across TaskManagers, coordinated by a JobManager. Sources (usually Kafka partitions) feed records through transformations; keyed operations (keyBy) partition the stream by key so that each key's state lives in exactly one parallel task. State is held in a state backend: on the JVM heap for small state, or in an embedded RocksDB instance (or ForSt in Flink 2) for state far larger than memory.
Fault tolerance comes from checkpoints. The JobManager periodically injects barriers into the sources; each operator snapshots its state when barriers from all its inputs have arrived (aligned) or as they pass (unaligned checkpoints, which avoid waiting under backpressure). Snapshots are written asynchronously and incrementally to durable storage, together with source offsets. On failure, all operators restore the last completed checkpoint and sources rewind. Transactional sinks (Kafka transactions, two-phase commit to files or lakehouse tables) make output exactly-once by committing only when a checkpoint completes. Savepoints are manually triggered checkpoints used for upgrades and migrations.
Time handling follows the Dataflow model: each record carries an event timestamp; watermarks flow through the graph saying 'no more records older than T are expected'; windows (tumbling, sliding, session) fire when the watermark passes their end, with allowed lateness and side outputs for stragglers. Backpressure is handled by credit-based flow control between tasks, so slow operators slow down their upstream instead of exhausting memory.
The layers below explain each choice. The commit log (Kafka) gives replayable, partitioned input. The Chandy–Lamport snapshot algorithm (Layer 2, from distributed systems theory) gives consistent checkpoints without stopping the world. LSM trees (RocksDB) give cheap writes for state updates. Hash partitioning gives each key a single owner. The JVM and its garbage collector shape memory management, which is why Flink manages much of its memory off-heap.
intuition: Picture a factory line where every workstation keeps its own ledger for the items it handles. Every few seconds a marker travels down the belt; when a station sees it, it photocopies its ledger and files it in the archive. If the factory loses power, every station restores the ledger from the same marker and the belt rewinds to that point, so nothing is counted twice or missed.
friction: Stateful streaming is operationally demanding. State size drives checkpoint duration, recovery time and storage cost; poorly bounded state (no time-to-live, unbounded joins) grows until jobs fail. Changing a job that holds state requires compatible state schemas and savepoints, and rescaling keyed state is slow with local state backends (the main problem Flink 2's disaggregated state targets). Backpressure, checkpoint timeouts and data skew are the usual sources of incidents.
Event-time semantics are powerful but subtle: watermark strategies trade latency against completeness, idle partitions can stall watermarks, and late data needs explicit handling. Exactly-once output depends on every sink supporting transactions or idempotent writes. Finally, Flink competes with simpler options: Kafka Streams for application-embedded processing, Spark Structured Streaming for teams already on Spark, and streaming databases for SQL-only use cases.
practice: Start every job design with three decisions: the key (which determines state ownership and parallelism), the time semantics (event time with an explicit lateness budget, or processing time), and the state bound (window length or time-to-live for every piece of state). Use RocksDB (or disaggregated state in Flink 2) for anything beyond small state, with incremental checkpoints.
Watch checkpoint duration and size, backpressure per operator, consumer lag at sources and watermark lag. Take a savepoint before every deployment, and test restoring from it. Keep parallelism at or below the number of source partitions for Kafka sources, and handle hot keys with pre-aggregation or salting. For lakehouse sinks, commit on checkpoint and size checkpoints so files are not too small, and schedule compaction.

@@ databricks
value: Databricks packages the lakehouse into a managed platform: Spark for compute, Delta Lake for tables, Photon for fast SQL, Unity Catalog for governance, plus notebooks, job orchestration, SQL warehouses, streaming pipelines and machine-learning tooling, all running on the customer's cloud account and storage. Its value is that a data team can ingest, transform, govern, analyse and model data in one place, on open formats, without building and operating each piece.
For organizations migrating from Hadoop or a classic warehouse, Databricks often becomes the central data platform: raw events land in bronze tables, pipelines refine them to silver and gold, analysts query them through SQL warehouses and BI tools, and data scientists train and serve models on the same governed data. The trade-off is a commercial platform with its own pricing model (Databricks Units on top of cloud costs) and features that go beyond the open-source projects it is built on.
history: Databricks was founded in 2013 by the creators of Apache Spark at UC Berkeley's AMPLab, including Matei Zaharia, Ali Ghodsi, Ion Stoica and Reynold Xin. The early product was hosted Spark notebooks. Delta Lake (developed from 2017, open-sourced 2019) added reliable tables on cloud storage; MLflow (2018) added experiment tracking; the 2021 lakehouse paper named the architecture the company was selling. Photon, a vectorized query engine written in C++, was described in a SIGMOD 2022 paper.
Later years added governance and AI. Unity Catalog (2021, open-sourced in 2024) became the central catalog for tables, files, models and permissions across workspaces. Databricks acquired MosaicML (2023) for model training, Tabular (2024, founded by Apache Iceberg's creators) to bridge Delta and Iceberg, and Neon (2025) for serverless PostgreSQL. Delta Live Tables evolved into Lakeflow Declarative Pipelines, and its declarative pipeline engine was contributed to Apache Spark 4.1. Serverless compute for notebooks, jobs and SQL removed much of cluster management.
how: The architecture separates a control plane (run by Databricks: the web UI, job scheduler, Unity Catalog service, notebooks) from the compute plane (clusters or serverless compute that read and write data in cloud object storage). Data stays in the customer's storage in open formats, mostly Delta Lake tables of Parquet files.
Query execution has two engines. Classic Spark executes on the JVM with Catalyst optimization and code generation. Photon takes over supported operators (scans, filters, joins, aggregations) and runs them as vectorized C++ code over columnar batches, which avoids JVM overheads and uses SIMD; the planner decides operator by operator, falling back to Spark for unsupported ones. Delta adds data skipping with file statistics, liquid clustering for layout, deletion vectors for cheaper updates, and predictive optimization (automatic OPTIMIZE and VACUUM).
Unity Catalog provides a three-level namespace (catalog.schema.table), fine-grained access control down to rows and columns, lineage across notebooks and jobs, and credential vending so that compute receives short-lived storage credentials only for what it may access. Lakeflow (Connect for ingestion, Declarative Pipelines for transformation, Jobs for orchestration) covers the pipeline lifecycle; Mosaic AI covers model training, serving and evaluation.
intuition: Databricks is a fully equipped kitchen installed in your own building: you own the pantry (cloud storage, open formats), they supply and maintain the appliances (engines, catalog, schedulers), and they charge by how long the stoves are on.
friction: Cost visibility and control are the main friction: compute charges come from both the cloud provider and Databricks, and serverless, Photon and different SKUs price differently, so attributing cost to teams and pipelines needs tagging, system tables and dashboards. Performance still depends on data layout, file sizes and query patterns; a managed platform does not prevent small-file problems or skewed joins.
Lock-in is subtler than with a proprietary warehouse, because data stays in Delta and Parquet, but much of the value (Photon, Unity Catalog features, Lakeflow, predictive optimization) is proprietary or ahead of the open-source versions. Interoperability with Iceberg-based engines improved with UniForm and the Tabular acquisition, but cross-engine governance remains complex. Migrations from Hadoop or other warehouses also require rethinking pipelines, not just moving them.
practice: Govern from the start: put every table in Unity Catalog, grant access through groups, and avoid direct storage paths. Tag clusters, jobs and warehouses with team and pipeline names, and build cost dashboards from the system billing tables; review the top spenders monthly. Prefer job clusters or serverless over long-running all-purpose clusters for scheduled work.
For performance, enable liquid clustering on large tables with selective filters, keep predictive optimization or scheduled OPTIMIZE and VACUUM running, use Photon-enabled compute for SQL-heavy workloads, and check query profiles for spills, skew and scanned bytes. Build pipelines declaratively where possible, so retries, dependencies and incremental processing are handled by the engine rather than custom code.

@@ delta
value: Delta Lake turns a directory of Parquet files in cloud object storage into a reliable database table: atomic commits, consistent snapshots for readers, schema enforcement and evolution, time travel to earlier versions, and efficient updates, deletes and merges. Before it, data lakes had no transactions; a failed job could leave half-written data, concurrent writers could corrupt tables, and listing millions of files was slow.
Its value is getting warehouse guarantees on cheap, open storage that many engines can read. It is the default table format on Databricks and is supported by Spark, Flink, Trino, DuckDB, Snowflake, BigQuery and others, through the Delta Kernel libraries and the open protocol.
history: Databricks engineers built Delta in 2017 after seeing customers struggle with unreliable data lakes, open-sourced it in April 2019, and moved it to the Linux Foundation later that year. The 2020 VLDB paper described the design. Delta 2.0 (2022) open-sourced features that had been Databricks-only, such as Z-ordering and change data feed. Delta 3.0 (2023) introduced UniForm, which writes Iceberg (and Hudi) metadata alongside the Delta log so other engines can read the same files, and Delta Kernel, a library for building connectors.
Delta 4.0 (2025) brought the VARIANT type for semi-structured data, catalog-managed tables (a foundation for multi-table transactions), Delta Connect for Spark Connect clients, type widening and further kernel features; the 4.x line continued with 4.1 and 4.2 (April 2026). Liquid clustering, deletion vectors and row tracking turned Delta from a copy-on-write format into one that supports cheap row-level changes.
how: A Delta table is a directory of data files plus a _delta_log directory. Each commit writes a new JSON file numbered 000…N.json containing actions: add file (with path, partition values and column statistics), remove file, change metadata (schema, configuration), protocol (required reader and writer features) and commit information. Every 10 or so commits (configurable), a Parquet checkpoint summarizes the table state, so readers do not replay the entire log. The current version is the highest committed number.
Writers use optimistic concurrency. A writer reads the latest version, does its work by writing new data files, then attempts to create the next log file using a put-if-absent operation (natively on some storage systems, or through a coordination service or catalog where object stores lack it). If another writer took that number first, the writer checks whether the other commit conflicts with what it read and wrote (for example, both changed the same files); if not, it retries with the next number, otherwise it fails. Readers simply pick a version and read exactly the files it lists, giving snapshot isolation.
Row-level changes use either copy-on-write (rewrite each affected file without the deleted or updated rows) or deletion vectors (a Roaring bitmap per file marking deleted row positions, merged at read time), which make deletes and merges much cheaper. Data skipping uses per-file min/max statistics; liquid clustering keeps files clustered on chosen columns incrementally. VACUUM deletes files no longer referenced by any version within the retention period; time travel works only within that period.
intuition: A ledger of index cards for a filing cabinet: each card says 'add these folders, remove those'. Readers pick a card number and see exactly that state of the cabinet. Two clerks who try to write the same card number at once discover it, and the loser checks whether their changes clash before taking the next number.
friction: Commit throughput is limited because every commit is a write to object storage and conflicts cause retries; high-frequency small writes (for example, from many streaming jobs into one table) need batching or partitioning by writer. Small files accumulate from streaming and need compaction. Protocol upgrades (enabling deletion vectors, column mapping, liquid clustering) can make tables unreadable by older clients and are often irreversible.
Multi-table transactions are only now emerging through catalog-managed tables. Interoperability with Iceberg via UniForm works but with limitations on features and write paths. And Delta's richest features often appear first in Databricks, so open-source users must check which version and engine support each table feature.
practice: Enable features deliberately and check reader compatibility first, especially when other engines or older Spark versions read the table. Use liquid clustering instead of fine-grained partitioning for new large tables; keep partitioning, if any, coarse. Run OPTIMIZE and VACUUM regularly (or enable predictive optimization), and set log and file retention to match your time-travel and recovery needs.
Design writers to avoid conflicts: partition streaming writers by key range or date, batch small commits, and use MERGE with conditions that touch as few files as possible. Use the change data feed or row tracking to drive incremental downstream processing instead of full rescans, and DESCRIBE HISTORY to audit and debug changes.

@@ redis
value: Redis is an in-memory data structure server: strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLogs, geospatial indexes and, more recently, JSON and vector sets, all reachable over the network with sub-millisecond latency. It is the default choice for caching, session storage, rate limiting, leaderboards, queues, distributed locks, real-time counters and feature serving.
Its value is speed with the right shapes of data. Instead of serializing objects into a key–value blob, applications use atomic operations on rich structures: increment a counter, add to a sorted set with a score, pop from a list, update a HyperLogLog. Each operation is simple, fast and atomic, which makes many concurrency problems disappear.
history: Salvatore Sanfilippo (antirez) wrote Redis in 2009 to speed up a real-time web analytics product, and it spread quickly through the web and startup world. Persistence (RDB snapshots and the append-only file), replication, Lua scripting, Sentinel for failover (2012), Redis Cluster for sharding (2015), modules (2016) and streams (2018) followed. Redis Labs (later Redis Ltd.) became the main sponsor.
Licensing became the big story. In March 2024 Redis moved from the BSD license to dual source-available licenses (RSALv2 and SSPLv1). The Linux Foundation forked the last BSD version as Valkey, backed by AWS, Google, Oracle and others; Valkey 8 added multi-threaded I/O improvements. In May 2025, with Redis 8, Redis added the AGPLv3 as an open-source option, and antirez, who had returned, contributed the vector set data type. Redis 8 also folded previously separate modules (JSON, query engine, time series, probabilistic structures) into the main distribution.
how: Redis keeps the whole dataset in memory and executes commands one at a time on a main thread driven by an event loop (epoll on Linux). Single-threaded execution means every command is atomic without locks and latency is very predictable for small operations. Since Redis 6, separate I/O threads can read and parse requests and write responses, while command execution stays single-threaded; Valkey extends this further. Data structures are tuned for memory: small hashes, lists and sorted sets use compact encodings (listpacks) and switch to hash tables and skip lists as they grow.
Persistence has two options, often combined. RDB snapshots fork the process; the child writes a compact snapshot while the parent keeps serving, relying on copy-on-write virtual memory. The append-only file logs every write command and can fsync every second (losing at most about a second of writes) or on every write (slower); it is periodically rewritten to stay compact. Replication is asynchronous: replicas receive a stream of commands and can lag. Redis Cluster splits the key space into 16,384 hash slots spread across primaries, each with replicas; clients route commands by key, and multi-key operations work only when all keys hash to the same slot (forced with hash tags).
The lower layers explain the trade-offs. The event loop (Layer 2) and epoll (Layer 3) give one thread high throughput. Hash tables, skip lists and HyperLogLog (Layers 2–3) are the data structures. Copy-on-write fork depends on virtual memory (Layer 3). Asynchronous replication means a failover can lose acknowledged writes, a CAP-style choice for availability and latency.
intuition: A very fast clerk at a single counter who keeps everything on the desk in neatly organized trays; because only one request is handled at a time, nothing is ever half-updated, and because everything is on the desk, nothing takes long.
friction: Memory is the limit and the cost: datasets must fit in RAM (with replicas doubling or tripling it), and fork-based snapshots can need up to twice the memory under heavy writes. One slow command (a large KEYS, a huge sorted-set range, a long Lua script) blocks every other client. Asynchronous replication means acknowledged writes can be lost on failover, so Redis is a poor primary store for data that must never be lost.
Redis Cluster limits multi-key operations and transactions to one slot, and resharding needs care. Distributed locks built on Redis (Redlock) are debated, because clock and pause assumptions can break mutual exclusion without fencing tokens. And the licensing split means teams must choose between Redis (AGPL, source-available or commercial) and Valkey (BSD), whose features are gradually diverging.
practice: Use Redis for what it is best at: caches with time-to-live, counters, rate limits, leaderboards, short-lived queues and fast lookups, with the source of truth elsewhere. Set maxmemory and an eviction policy explicitly, and monitor memory fragmentation, evictions and replication lag. Avoid O(N) commands on large keys in production (use SCAN instead of KEYS, paginate ranges), and keep values small.
For persistence, choose AOF with fsync every second if you need durability within a second, and leave memory headroom for fork-based rewrites and snapshots. In clusters, design keys so that data used together shares a hash tag. If you need locks for correctness (not just efficiency), use fencing tokens or a consensus-based store such as etcd instead.

@@ jvm
value: The Java Virtual Machine runs bytecode from Java, Scala, Kotlin and other languages on any operating system and CPU, with a just-in-time compiler that makes long-running programs very fast and a garbage collector that manages memory automatically. Much of the data infrastructure in this map runs on it: Kafka, Spark, Flink, Elasticsearch, Cassandra, Hadoop, Pinot, Trino and ZooKeeper.
Its value for these systems is a combination of portability, mature tooling (profilers, debuggers, monitoring through JMX and Java Flight Recorder), a huge library ecosystem and performance close to native code for steady workloads. Its costs (garbage-collection pauses, memory overhead, warm-up time) are why many of those systems also use off-heap memory, native code (Photon, RocksDB) or careful tuning.
history: Sun Microsystems released Java in 1995 with the slogan 'write once, run anywhere': programs compiled to bytecode for a virtual machine rather than for a specific CPU. Early JVMs were interpreters and slow; the HotSpot JVM (1999), based on research from the Self language, introduced adaptive JIT compilation that profiles hot code and compiles it aggressively. Java became dominant in enterprise software and then in big data, as Hadoop (2006) and later Kafka, Spark and others chose it or Scala.
Oracle acquired Sun in 2010; OpenJDK became the reference implementation, and since 2017 Java has shipped a release every six months with a long-term-support release every two years (Java 21 in 2023, Java 25 in September 2025). Recent major features include the G1 collector as default (Java 9), ZGC for sub-millisecond pauses (production in Java 15, generational in Java 21), virtual threads (Project Loom, Java 21), records and pattern matching, and ongoing work on value types (Project Valhalla) and faster start-up (Project Leyden). GraalVM added a new JIT and ahead-of-time native images.
how: Source code is compiled to bytecode in .class files. The JVM loads and verifies classes, then starts executing bytecode with an interpreter while profiling which methods and branches are hot. Tiered compilation first compiles hot methods quickly with C1, then recompiles the hottest with C2 using profile data: inlining, escape analysis (allocating objects on the stack or removing them), loop optimizations and speculative devirtualization. If a speculation proves wrong, the JVM deoptimizes back to the interpreter.
Memory is a managed heap. Objects are allocated quickly by bumping a pointer in thread-local buffers. Generational collectors exploit the fact that most objects die young: G1 divides the heap into regions and collects those with the most garbage within a pause-time goal; ZGC and Shenandoah do most work concurrently, using load barriers and relocating objects while the application runs. Threads map one-to-one onto OS threads, except virtual threads, which the JVM schedules onto a small pool of carrier threads, making millions of blocking tasks cheap.
The layers below show up directly: JIT compilation and SSA-based optimization (Layer 3), garbage collection theory (Layer 3), memory models (the Java Memory Model, 2004, defines what concurrent code may observe), and the CPU's caches and branch predictors, which the JIT's code layout tries to please.
intuition: A translator who starts by reading your speech aloud line by line, notices which paragraphs you repeat most, and quietly prepares polished translations of those; meanwhile a cleaner tidies the room, mostly sweeping up the papers you dropped a moment ago.
friction: Garbage-collection pauses and CPU overhead still matter for latency-sensitive systems; large heaps with older collectors can pause for seconds. Object headers and pointers make Java data structures memory-hungry, which is why Spark, Kafka and Flink use binary formats and off-heap memory. Warm-up means peak speed arrives only after the JIT has profiled the workload, a problem for short jobs and serverless functions.
Containers add pitfalls: memory limits must leave room beyond the heap (metaspace, thread stacks, direct buffers, native libraries), or the out-of-memory killer ends the process. Tuning flags have changed across versions, and advice from older blogs is often wrong for current JVMs.
practice: Run supported long-term-support versions (21 or 25) to get better collectors and container awareness. Size the heap explicitly, leaving 25–40% of container memory for non-heap use, and monitor GC pause times, allocation rate and heap after collection rather than just heap usage. Use G1 as the default; switch to generational ZGC for latency-sensitive services with large heaps.
Profile before tuning: Java Flight Recorder and async-profiler show CPU, allocation and lock hot spots with low overhead. Reduce allocation in hot paths, prefer primitive arrays and binary formats for large data, and use virtual threads for I/O-bound services instead of large thread pools.

@@ nvgpu
value: NVIDIA's data-centre GPUs (Hopper H100 and H200, Blackwell B200 and GB200, and the Rubin generation entering production in 2026) are the main machines on which modern AI is trained and served. Their value is enormous parallel arithmetic, especially low-precision matrix multiplication in tensor cores, fed by stacked high-bandwidth memory and connected by NVLink into rack-scale systems that behave like one large accelerator.
Together with the CUDA software stack (cuBLAS, cuDNN, NCCL, TensorRT and the CUDA programming model), this hardware made NVIDIA the dominant supplier of AI compute; capacity, power and cost of these GPUs now shape what models can be built and how much inference costs.
history: NVIDIA built graphics processors from the 1990s. CUDA (2007) opened GPUs to general-purpose computing, and researchers soon found them far faster than CPUs for neural networks; AlexNet (2012) was trained on two consumer GPUs. Data-centre generations followed: Kepler, Pascal (P100, 2016, with HBM2 and NVLink), Volta (V100, 2017, introducing tensor cores), Ampere (A100, 2020, with TF32, BF16 and structured sparsity) and Hopper (H100, 2022, with a Transformer Engine using FP8).
Blackwell (B200 and the GB200 NVL72 rack, shipping in volume from late 2024 and 2025) joined two large dies in one package, added FP4 support and connected 72 GPUs in one NVLink domain. Rubin, announced for 2026 with HBM4 memory, continues the yearly cadence. Competition comes from AMD's Instinct GPUs, Google's TPUs, AWS Trainium and other accelerators, but the CUDA ecosystem remains a strong moat.
how: A GPU contains many streaming multiprocessors (132 on an H100 SXM), each running thousands of threads in groups of 32 (warps) that execute the same instruction (SIMT). Each multiprocessor has tensor cores that multiply small matrix tiles in one operation, in formats from FP64 down to FP8 (Hopper) and FP4 (Blackwell), plus a large register file and fast shared memory. An H100 offers roughly 1,000 dense FP16/BF16 TFLOP/s and about 2,000 in FP8, with 80 GB of HBM3 at about 3.35 TB/s; Blackwell B200 roughly doubles compute per GPU and offers about 8 TB/s from 192 GB of HBM3e.
Because arithmetic is so fast relative to memory, the key to performance is arithmetic intensity: kernels must reuse data from registers and shared memory many times per byte fetched from HBM (the reason for FlashAttention and operator fusion). Across GPUs, NVLink and NVSwitch give hundreds of GB/s to TB/s per GPU within a server or rack, and InfiniBand or Ethernet with RDMA connect racks; NCCL implements all-reduce and other collectives over this fabric for distributed training.
The lower layers are visible everywhere: tensor cores are systolic-style matrix units (Layer 3), HBM stacks DRAM dies with through-silicon vias (Layer 5), FP8 and FP4 depend on floating-point formats (Layer 3), and power and cooling (often over 1 kW per GPU, liquid-cooled racks over 100 kW) are thermodynamics (Layer 5).
intuition: Thousands of tiny calculators working in lockstep, so fast that the real challenge is bringing them numbers quickly enough; most of the engineering is about keeping data close and reusing it.
friction: Supply, price and power are the biggest constraints: leading GPUs are expensive and were scarce for years, and data centres are limited by electricity and cooling. Peak FLOPs are rarely reached; real utilization (model FLOPs utilization) of 30–50% in training is good, and inference is often memory-bound. Large clusters suffer frequent hardware failures, so training needs fast checkpointing and restart.
Software lock-in to CUDA makes switching vendors costly, though PyTorch, Triton and compilers are reducing this. Low-precision formats (FP8, FP4) need careful scaling to avoid accuracy loss. Export controls also restrict where the most advanced chips can be sold.
practice: Measure before buying more GPUs: profile utilization, memory bandwidth and communication time (Nsight Systems, PyTorch profiler). For training, use mixed precision (BF16, FP8 where supported), fused kernels (FlashAttention, compiled graphs) and the right parallelism for your model size. For inference, maximize batch size within latency targets, quantize weights and the KV cache, and choose GPUs by memory capacity and bandwidth as much as by FLOPs.
Treat GPU capacity as a scarce shared resource: schedule jobs with queues and quotas, track cost per experiment, and plan for failures with frequent checkpoints.
