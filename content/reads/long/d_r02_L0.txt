@@ applem
value: Apple M-series is a family of chips that Apple designs for its Mac computers and iPads, starting with the M1 in November 2020. Each chip is a system on a chip (SoC): CPU cores, GPU cores, a neural engine, media engines and the memory controllers sit on one piece of silicon, and the memory chips sit in the same package. All of them use one pool of memory, called unified memory. The M1 was the first time an ARM-based chip beat the best x86 laptop chips at the same time on speed and on battery life, and it did this in a fanless MacBook Air.
For an engineer, the important idea is not "ARM is faster". It is that the chip is built around the memory system and the power budget, not around the clock speed. The CPU, the GPU and the neural engine read the same bytes in the same memory, so a program does not copy a tensor or a texture from "CPU memory" to "GPU memory" over a slow link. A 128 GB Mac can hold a large language model in memory that a 24 GB desktop graphics card cannot. At the same time the cores spend little energy per instruction, so a laptop runs a long time on its battery.
The layers below make this possible. The ARM instruction set (armisa, L0) gives instructions of fixed length that are easy to decode in parallel. General-purpose CPU design (cpucomp, L1) supplies the out-of-order, superscalar core that Apple builds very wide. DRAM (dram, L3) supplies LPDDR memory placed next to the chip with a wide bus. The instruction-set concept (isa, L3) is the contract that lets old software run, either natively or translated. The lithium-ion battery (liion, L5) sets the energy budget that all of these choices serve. Who uses it: every Mac since 2023, all iPads with an M chip, and developers who run Spark jobs, Docker containers and local AI models on their laptops.
terms: SoC (system on a chip) — one chip that holds the CPU, GPU, neural engine and other blocks together, instead of separate chips on a board.
Unified memory — one physical pool of memory that the CPU, GPU and neural engine all address directly, so no copy between "host" and "device" memory is needed.
Performance core and efficiency core — a big, fast core for heavy work and a small, low-power core for background work; the operating system chooses which one runs a thread.
Out-of-order execution — the core runs instructions in a different order from the program when they do not depend on each other, to keep its units busy.
Reorder buffer (ROB) — the list of instructions that are in flight in an out-of-order core; a bigger ROB lets the core look further ahead for independent work.
Memory bandwidth — how many bytes per second the memory can deliver to the chip; for the M5 Max it is about 614 GB/s.
Neural Engine — a fixed block that does low-precision matrix math for machine-learning models using little power.
Rosetta 2 — Apple's translator that converts x86-64 programs to ARM instructions so old Mac programs keep running.
Architecture license — a contract with Arm that lets a company design its own cores that run the ARM instruction set, instead of using Arm's designs.
history: Apple has designed its own processors since the iPhone 4 (A4, 2010), after buying the chip team P.A. Semi in 2008 and Intrinsity in 2010. The A6 (2012) was the first Apple-designed core. The A7 (2013) was the first 64-bit ARM chip in a phone, and it surprised the industry because it arrived years before competitors expected it. Each year after that the core grew wider and faster, led by Johny Srouji's silicon group. By 2018 the iPad chips were close to laptop speed.
Apple announced the move of the Mac from Intel to its own chips at WWDC in June 2020. It was the third change of Mac processor family (Motorola 68k to PowerPC in 1994, PowerPC to Intel in 2006). The reasons were practical. Intel's manufacturing had stalled for several years, so its laptop chips were stuck on the same process node. Apple already had a better core and a better schedule. Owning the chip also allowed Apple to design the whole device around it: the memory, the power controller, the operating system's scheduler and the media hardware.
The M1 was announced on 10 November 2020. It had 16 billion transistors, was built by TSMC on a 5 nm process, and had 4 performance cores, 4 efficiency cores, a GPU with 7 or 8 cores, a 16-core Neural Engine and about 68 GB/s of LPDDR4X memory bandwidth. Reviewers found that a fanless Air matched or beat many fan-cooled x86 laptops. M1 Pro and M1 Max followed in October 2021 (up to about 400 GB/s). M1 Ultra (2022) joined two Max dies with a silicon bridge called UltraFusion. M2 came in 2022, M3 in 2023 on a 3 nm process with a new GPU design, and M4 in 2024. The M5 arrived on 15 October 2025 on TSMC's third-generation 3 nm process, and M5 Pro and M5 Max followed on 3 March 2026. They use what Apple calls Fusion Architecture: two 3 nm dies joined into one SoC by advanced packaging.
how: Start with the instruction set. Apple's cores run AArch64, the 64-bit mode of the ARM architecture (see armisa). Every instruction is exactly 4 bytes, so the decoder knows where each instruction starts without looking at the previous one. On x86 an instruction is 1 to 15 bytes, so finding the boundaries is a serial problem and the decoders are large and costly. Because Apple's decode is cheap, the Firestorm core of the M1 decoded 8 instructions per cycle, while x86 cores of that time decoded about 4. This is the first thing the ISA layer (isa, L3) contributes: a simple contract makes a wide front end affordable.
Behind the decoder is a very large out-of-order engine, the general-purpose CPU design from cpucomp. The M1 performance core has a reorder buffer of roughly 600 entries, a 128 KB first-level data cache (x86 cores then had 32 to 48 KB) and a 12 MB L2 cache shared by the four performance cores. A wide core with a big window finds more independent instructions in ordinary code, so it gets more work done per clock. Apple chose to run at about 3.2 GHz, not 5 GHz. Power grows faster than linearly with frequency, because a higher clock needs a higher voltage. A core that does more per cycle at a lower clock wins in work per joule.
The second idea is heterogeneous cores. The M1 has four efficiency cores that use a fraction of the power of the performance cores. macOS gives every thread a quality-of-service class. Background threads such as indexing or backup run on the efficiency cores. Interactive and heavy work runs on the performance cores. The chip finishes light tasks at very low power, and the battery (liion, L5) lasts longer. The MacBook Air M1 has a 49.9 Wh battery and Apple rates it for about 15 hours of web use, which is an average draw of roughly 3 to 4 W for the whole machine.
The third idea is unified memory, which is where dram (L3) matters most. The memory chips are LPDDR (low-power DRAM) mounted in the same package as the SoC, not in sockets on the board. Short wires let the bus be very wide: 128 bits on the M1 and M5 base, 256 bits on a Pro, and 512 bits on a Max, giving 68 GB/s on the M1, 153.6 GB/s on the M5, 307 GB/s on the M5 Pro and 614 GB/s on the M5 Max. A normal desktop with two channels of DDR5 gives about 90 GB/s. All the blocks (CPU clusters, GPU, Neural Engine, display and media engines) connect to this memory through a shared fabric and a large system-level cache. Because there is one address space, a buffer that the CPU wrote can be read by the GPU with no copy. On a PC with a discrete graphics card, the same data must cross PCIe at about 32 to 64 GB/s and be duplicated in two memories.
The fourth idea is the compatibility layer. Rosetta 2 translates x86-64 programs to ARM code ahead of time when an app is first installed or launched, and translates just-in-time code on the fly. One hardware detail makes it fast: x86 guarantees a strong memory order (total store ordering, TSO) and ARM by default does not. Apple added a mode in the hardware that gives TSO order for translated threads, so the translator does not need to insert many memory barriers. Translated programs often run at 70 to 80 percent of native speed.
The GPU and the Neural Engine use the same memory for different kinds of work. The GPU is a tile-based design that is efficient for graphics and general parallel compute through Metal. The Neural Engine is a fixed block for low-precision matrix math, rated at 11 trillion operations per second on the M1 and 42 on the M5, and it uses far less power than the GPU for the models it supports. Since the M5, each GPU core also has a Neural Accelerator, a matrix unit inside the core, which speeds up large language model work on the GPU itself. All three see the same tensors in memory, so the framework (Core ML, MLX, PyTorch) can choose the block that fits each layer.
Finally, the chips grow by composition. The Max chip adds more GPU cores and memory channels to the Pro design. The Ultra (M1 Ultra, M2 Ultra, M3 Ultra) joined two Max dies with a bridge of about 2.5 TB/s so that software sees one chip. M5 Pro and Max use two dies in the Fusion design. This lets Apple reach 128 GB (M5 Max) or, on the M3 Ultra, 512 GB of unified memory with up to about 800 GB/s, in one machine.

example: Question: how fast can a Mac generate text with a large language model, and why does it depend on memory? Take an M5 Max with 128 GB of unified memory and a model with 70 billion parameters stored at 4 bits per weight. The weights take 70 billion x 0.5 byte = 35 GB (plus a few GB for the key-value cache), so the model fits in memory with room to spare. A 24 GB discrete graphics card cannot hold it at all, and would have to split the model between GPU and system memory over PCIe.
Now estimate the speed. To produce one token, the GPU must read every weight once. That is 35 GB of reads per token. The memory bandwidth of the M5 Max is about 614 GB/s. The upper bound on the speed is 614 / 35, about 17 tokens per second. In practice you reach perhaps 60 to 80 percent of the bound, so 10 to 14 tokens per second. The compute of the GPU is not the limit here. The limit is how fast bytes arrive. This is why Apple puts so much into the width of the memory bus, and why the Max chip has twice the bandwidth of the Pro chip and four times the base chip (153.6 GB/s, which would give only about 4 tokens per second on the same model, if it fitted).
Now a second example, about energy. A MacBook Air M1 has a 49.9 Wh battery. If the whole machine draws 3.5 W while you browse, the battery lasts 49.9 / 3.5, about 14 hours. A typical x86 thin laptop of 2020 drew 8 to 10 W in the same task, so it lasted 5 to 7 hours with a similar battery. The chip itself is not the whole difference, but the wide, low-clock core and the efficiency cores explain most of the CPU part.
A third example is a developer matter. You build a Docker image on an M-series Mac with the default settings. It is a linux/arm64 image. You push it to a Kubernetes cluster that runs x86 nodes, and the pod fails with "exec format error". The fix is to build for both platforms with docker buildx build --platform linux/amd64,linux/arm64, or to run the cluster on ARM nodes such as AWS Graviton, which also cost less per unit of compute.
intuition: A kitchen where the cook, the oven and the pantry share one counter, so nobody carries ingredients from room to room.
Most of the energy and time in a computer goes into moving data, not into the arithmetic. If you design the CPU, the GPU and the memory together, you can shorten the distance between them, make the road wider, and remove the copies. A wide core at a low clock does more work for each joule, and a small core handles light work without waking the big one. None of these ideas is new. What was new in 2020 was that one company controlled the instruction set licence, the core design, the memory system, the operating system and the compilers, so it could tune all of them at once.
mistakes: People often think the M1 is fast simply because ARM is a better instruction set than x86. In fact the ISA matters less than the core design. Apple's advantage comes from a very wide core, big caches, a large reorder buffer, a modern process node and on-package memory. ARM's fixed-length instructions make a wide decoder cheaper, but x86 cores from AMD and Intel have narrowed the gap since 2020.
People often think unified memory means the GPU is slow because it shares memory with the CPU. In fact the bandwidth is high (up to 614 GB/s on the M5 Max, and about 800 GB/s on the M3 Ultra), and the gain from removing copies is large. The real limit is that the bandwidth is lower than the 1 to 3 TB/s of high-end data-centre GPUs with HBM, so Apple chips are strong for capacity and efficiency, not for peak training speed.
People often think Apple uses ARM's own processor designs. In fact Apple holds an architecture license and designs its own cores from scratch. They only share the instruction set with ARM's Cortex cores, and they are very different inside.
People often think a Mac with an M chip cannot run x86 software. In fact Rosetta 2 translates most Mac apps, and Docker Desktop and other virtual machine tools can run linux/amd64 containers through emulation. This is slower than native, and some low-level tools, such as kernel extensions and some virtualization products, do not work.
tradeoffs: Choose an M-series Mac as a developer laptop when you work with Spark local mode, Docker, IDEs and local models, and battery life and noise matter. You give up some compatibility. Production is usually x86 Linux, so you must build multi-platform images and watch for native libraries that have no arm64 build. Choose an x86 laptop when your daily tools depend on x86-only software, Windows-only drivers or CUDA. You give up battery life and often get more noise and heat.
Choose a Mac with large unified memory for running or fine-tuning mid-size models (up to roughly 70 to 200 billion parameters at 4-bit) on one machine, when you value capacity and a single quiet box. Choose a discrete NVIDIA GPU or a cloud instance when you need the highest throughput or training speed: an H100 has about 3.35 TB/s of HBM bandwidth, five times the M5 Max, and the CUDA software stack. You pay more power, money and setup. A Mac is cheap per GB of fast memory compared with a data-centre GPU, but slow per token compared with it.
Choose the larger memory option when you buy, because unified memory cannot be upgraded later and the price step is high (often several hundred dollars per 16 or 32 GB). Choose the smaller option only if the machine is for light work. For a team fleet, buying one tier above today's need is cheaper than replacing the machine in two years.
Choose Apple silicon servers only inside Apple's own services (Apple runs its Private Cloud Compute on its own chips). For a general data centre, choose x86 or ARM server chips (AWS Graviton, Ampere, NVIDIA Grace): they have more cores per socket, ECC memory, PCIe lanes and sockets for large memory. You cannot buy an M-series chip as a rack server.
friction: Memory and storage are fixed at purchase. The memory is in the package, so you cannot add RAM later, and Apple charges a high price for upgrades. If the logic board fails, repair usually means replacing the board. The GPU is strong, but the software world of machine learning is built on CUDA. On a Mac you use Metal, the MLX framework or the PyTorch MPS backend, and many research projects and kernels (FlashAttention variants, custom CUDA ops) are missing or slower.
The chip is closed. Apple does not publish the microarchitecture, the GPU instruction set or full documentation. Linux support exists only because the Asahi Linux project reverse-engineered the hardware, and features such as some GPU functions and the Neural Engine lag behind. Virtualization is limited: you can run arm64 Linux guests well, but you cannot run macOS in more than two virtual machines at once on the same Mac, and you cannot boot x86 guests natively.
Scaling has limits. Bandwidth does not grow without cost: a 512-bit bus needs many LPDDR packages and a large die, and joining dies with bridges adds latency between halves. The Ultra chips give 2x the cores, but software may see uneven speed-ups. The chips also depend on TSMC's newest process nodes, so supply is tied to one manufacturer, and each new node is more expensive per transistor. Finally, the thin-laptop power budget caps sustained GPU work: under a long load the clock drops.
practice: For daily engineering work on an M-series Mac, set Docker to build multi-platform images (docker buildx with --platform linux/amd64,linux/arm64) and test the one that production uses. Prefer arm64 base images, and check that native wheels (NumPy, pyarrow, grpc, snappy, JNI libraries) exist for arm64. Apple's chips run the JVM well, and recent JDK builds for aarch64 are fully supported, so Spark local mode and Gradle builds are fast. If production can run on Graviton, your laptop and your servers now share one architecture, and many teams save about 20 percent in cost for the same work.
Size memory for the work: a quick rule for local models is that a 4-bit model needs about 0.5 GB per billion parameters, plus 10 to 20 percent for the cache. Tokens per second is bounded by bandwidth divided by model size, so a higher-tier chip (Max) is much faster than a base chip even when both can fit the model. Use Activity Monitor to watch "memory pressure", not only "memory used": when pressure turns red, macOS is compressing and swapping, and speed falls sharply.
Use Metal (MPS) for PyTorch and MLX for Apple-specific model work, but do training at scale on NVIDIA or AMD GPUs in the cloud. Do not benchmark by peak numbers: test your own workload, because a mix of single-thread latency, memory bandwidth and sustained thermal limits decides the real speed. If you manage a fleet, track which engineers still use Intel Macs (no new macOS updates after the current generation) and which CI runners are arm64 versus x86.
quiz: What does "unified memory" mean in an M-series chip? || The CPU, GPU and Neural Engine all use the same physical pool of memory and the same address space, so data does not need to be copied between separate CPU and GPU memories.
Why can the M1 decode 8 instructions per cycle while x86 cores of 2020 decoded about 4? || AArch64 instructions are all 4 bytes, so each decoder can start at a known position without waiting for the previous instruction's length. x86 instructions have a length of 1 to 15 bytes, so finding boundaries is serial and wide decoders are expensive in area and power.
An M5 Max has 614 GB/s of memory bandwidth. A model takes 35 GB in memory. What is the rough upper bound on tokens per second? || Each token reads all the weights once, so the bound is 614 / 35, about 17 tokens per second. In practice about 60 to 80 percent of that is reached.
Why does Rosetta 2 run translated programs fast, and what hardware feature helps? || It translates x86-64 code to ARM ahead of time (and uses just-in-time translation for dynamic code). Apple's chips also have a hardware mode with x86-style total store ordering, so the translator does not need to add many memory barriers.
You need to train a 70B-parameter model from scratch. Do you choose a 128 GB Mac or a cluster of NVIDIA GPUs, and why? || The cluster of GPUs. Training needs far more compute and memory bandwidth (HBM at 3 TB/s or more per GPU), fast interconnects and the CUDA ecosystem. A Mac is good for inference and small fine-tuning, where capacity and efficiency matter more.
interview: Why did Apple's core design reach higher performance per watt than Intel's at the same time? || Apple used a very wide core (8-wide decode, ROB of about 600 entries, large L1 and L2 caches) at a lower clock, on a leading process node (5 nm versus Intel's 10 nm class). Energy rises faster than linearly with frequency and voltage, so more work per cycle at a lower clock saves energy. Fixed-length instructions made the wide decoder affordable, and efficiency cores handle light work.
What are the costs of putting memory in the package? || You cannot upgrade or replace it, the maximum capacity is limited by what fits in the package (128 GB for the M5 Max, 512 GB for the M3 Ultra), and the price is high. In return you get short wires, a wide bus and low power. It is a good trade for laptops but a poor one for general servers, which need sockets, ECC and terabytes of RAM.
You deploy a Docker image built on a developer's M-series laptop and the pod crashes on start. What happened and how do you prevent it? || The image was built for linux/arm64 and the node is linux/amd64 ("exec format error"). Build multi-platform images in CI with buildx and a manifest list, pin the platform in the Dockerfile or the deploy spec, and test on the production architecture, or move the cluster to ARM nodes.
Why is an M-series Mac good for local LLM inference but weak for training large models? || Inference is limited by memory capacity and bandwidth, and unified memory gives large capacity at 150 to 800 GB/s. Training needs much higher compute, 3 TB/s HBM, fast multi-GPU links and the CUDA/ROCm libraries, which Apple chips do not match.
How does Apple scale from M5 to Max to Ultra, and what limits it? || It adds GPU cores and memory channels per die (128-bit, 256-bit, 512-bit buses), then joins dies with a high-bandwidth bridge (Ultra, Fusion). Limits are die area and yield, the cost of many LPDDR packages, latency between dies, software that does not scale across dies, and thermal limits in a laptop body.

@@ armisa
value: ARM is a family of instruction sets for processors, and also the company (Arm Holdings) that owns them. The instruction set is the contract between software and a processor: it says which instructions exist, how many registers there are and how memory behaves. ARM chose a simple, regular contract (a RISC design), and it does not sell chips. It licenses the contract, and optionally ready-made core designs, to other companies, who build the chips. That is why ARM is in almost every phone, in most embedded devices, in all Apple devices, and, more and more, in cloud servers.
The practical value for an engineer is this: the same software contract is implemented by very different chips, from a small controller that costs a few cents and uses milliwatts to a 192-core server chip. A program compiled for 64-bit ARM (AArch64) runs on a phone, on a Mac with an M-series chip (applem), on an AWS Graviton server, on an NVIDIA Grace CPU and on a Raspberry Pi. In servers, ARM chips often give more work per watt and per dollar than x86, so for a large fleet the instruction set becomes a cost decision, not only a technical detail.
The layers below explain what is special. The instruction-set concept (isa, L3) tells us what a contract of this kind must define, and the RISC idea of a load/store design is the reason ARM instructions are simple to decode. General-purpose CPU design (cpucomp, L1) is what each licensee builds on top of the contract: pipelines, out-of-order engines, caches and branch predictors. ARM supplies the contract and a menu of designs; the licensee decides how fast, how large and how efficient the core will be. Linux (linux, L0) and Apple's chips (applem, L0) are built on it, and both show the same lesson: a stable contract lets a whole software ecosystem move to new hardware.
terms: ISA (instruction set architecture) — the list of instructions, registers and rules that software can rely on, independent of how a chip implements them.
RISC (reduced instruction set computer) — a design with few, simple, regular instructions that each do one small step.
Load/store architecture — arithmetic works only on registers; memory is touched only by separate load and store instructions.
AArch64 — the 64-bit execution state of ARMv8 and later, with 31 general registers and fixed 4-byte instructions.
Architecture license — a contract that lets a company design its own cores that run the ARM ISA (Apple, Qualcomm and Nvidia have one).
Core license — a contract to use a ready-made Arm core design, such as Cortex or Neoverse, in your own chip.
Neoverse — Arm's family of core designs for servers and infrastructure (N, V and E series).
Weak memory model — a rule set that lets the hardware reorder memory operations, so programs need barriers or acquire/release operations to order them.
NEON and SVE — ARM's vector instructions: NEON works on fixed 128-bit vectors, and SVE works on vectors whose length (128 to 2048 bits) is chosen by the hardware.
history: The design began at Acorn Computers in Cambridge, England. Sophie Wilson and Steve Furber started the project in October 1983 because the chips they could buy were too slow for the computer they wanted to build. They had read papers from Berkeley and Stanford on RISC, and had seen that a small team could build a processor. The first ARM1 silicon ran correctly on 26 April 1985. The ARM2 powered the Acorn Archimedes in 1987, and its design was so small and low in power that it ran from a modest supply.
In 1990, Acorn, Apple (which wanted a processor for the Newton) and VLSI Technology formed Advanced RISC Machines Ltd. The company made a choice that defined its history: it would not make chips. It would license designs, and take a royalty on every chip sold. The ARM7TDMI (1994) added Thumb, a 16-bit compressed encoding, and became the core of countless phones and music players. Arm Holdings listed in London and on Nasdaq in 1998.
The mobile phone boom made ARM the default. In 2007 the iPhone used an ARM chip, and Android followed. ARMv7 (2005 onward) split the line into Cortex-A (applications), Cortex-R (real time) and Cortex-M (microcontrollers). In October 2011 ARM announced ARMv8-A with AArch64, a new 64-bit instruction set that dropped many old features. Apple shipped the first 64-bit ARM phone chip, the A7, in 2013. In 2018 Arm introduced the Neoverse line for servers, and AWS announced its first Graviton chip in the same year. Graviton2 (2019, Neoverse N1, 64 cores) was the point when cloud users took ARM seriously. Fujitsu's A64FX, an ARM chip with 512-bit SVE vectors, powered Fugaku, the fastest supercomputer in the world from 2020 to 2022.
Two business events also matter. SoftBank bought Arm in 2016. In September 2020, NVIDIA agreed to buy Arm for about 40 billion US dollars, but regulators in several countries objected and the deal was dropped in February 2022. Arm returned to the public market with an initial public offering on Nasdaq in September 2023. ARMv9-A was announced in March 2021, with SVE2 vectors and security features such as memory tagging and confidential compute. Today the main server chips are AWS Graviton (the fifth generation, announced in December 2025, uses Neoverse V3 cores and has 192 cores), Google Axion, Microsoft Cobalt, Ampere and NVIDIA Grace.
how: The ARM instruction set is a load/store design. An arithmetic instruction names registers only. ADD X0, X1, X2 means "add the 64-bit values in X1 and X2 and put the result in X0". To use a value in memory, you first run a load such as LDR X1, [X3, #8] ("read 8 bytes from the address X3 + 8 into X1"), and later a store to write back. This is the core RISC idea from isa (L3). It keeps each instruction simple and uniform. The hardware does not need an instruction that reads memory, adds, and writes memory in one step, so the pipeline has fewer special cases.
In AArch64, every instruction is exactly 32 bits (4 bytes). Fields have fixed places, so the decoder can read the register numbers and the operation at the same time. For example, ADD X0, X1, X2 is the 32-bit word 0x8B020020. The top bits select 64-bit add; the fields Rm = 2, Rn = 1 and Rd = 0 are each 5 bits wide, and 5 bits give 32 possible registers (31 general registers X0 to X30, and a 32nd code that means the stack pointer or the zero register, depending on the instruction). The decoder does not need to find where an instruction ends. A wide core can decode 8 instructions from a 32-byte window in parallel (the Apple M1 does this). On x86, instructions are 1 to 15 bytes long, so boundaries must be found first. This is why fixed length helps wide cores (see x86).
AArch64 removed several old features that made hardware hard. There is no general conditional execution of every instruction (the old 32-bit ARM had it). Instead there are compare-and-branch instructions and conditional select instructions such as CSEL, which pick between two registers without a branch. The flags register is set only by instructions that ask for it (ADDS, SUBS), so the out-of-order engine can rename and reorder flag use easily. Addressing modes are limited but useful: a base register plus an immediate, a scaled register, or pre- and post-increment forms that help loops.
The memory model is weak. On x86, stores become visible in program order (total store ordering), and a few barriers are enough. On ARM, the hardware may reorder loads and stores, so one thread can see another thread's writes in a different order. Software must use acquire/release instructions (LDAR and STLR), explicit barriers (DMB), or the atomic operations that language runtimes provide. ARMv8.1 added Large System Extensions (LSE): single-instruction atomics such as compare-and-swap (CAS) and atomic add (LDADD). The older method, load-exclusive and store-exclusive pairs, can fail under heavy contention. This matters for servers: a program with many threads updating a shared counter runs much better with LSE atomics.
Vector and matrix work is done by NEON (128-bit registers, present on all ARMv8-A cores) and, on bigger cores, SVE and SVE2. SVE code is written without knowing the vector length. A loop uses predicate registers to handle the tail, so the same binary runs on a core with 128-bit vectors and on one with 512-bit vectors. This is the ARM answer to the many AVX versions on x86. ARMv9 adds SME, a matrix extension that is important for machine learning on the CPU.
The privileged part of the contract is small and clear. AArch64 has four exception levels: EL0 for applications, EL1 for the operating system kernel, EL2 for the hypervisor and EL3 for secure firmware. A system call is an SVC instruction that moves the core from EL0 to EL1, and the kernel (see linux) returns with ERET. Virtual memory uses page tables with a choice of 4 KB, 16 KB or 64 KB pages; Apple chips use 16 KB, and some server distributions use 64 KB pages, which reduces TLB misses but wastes memory for small mappings. Interrupts go through a standard controller (the GIC), so one kernel image with a device tree can boot on many different boards. This is a second reason why the ecosystem works: the parts of the contract that an operating system needs are standard, not only the user instructions.
The business model is also part of how it works. Arm sells two kinds of license. With a core license (Cortex, Neoverse), a company gets a finished design and builds a chip with it; it chooses the number of cores, caches, memory controllers and the foundry (see cpucomp for what such a design contains). With an architecture license (Apple, Qualcomm, NVIDIA), a company designs its own core that must pass Arm's compatibility tests. The result is a market with many implementations of one contract: Cortex-X for fast phone cores, Apple's Firestorm for laptops, Neoverse V3 for servers. Because they all run the same ISA, Linux (linux, L0) runs on all of them with the same kernel source, and one compiled arm64 binary or container image runs on all of them. The chips differ in speed and power but not in software.

example: Take a small loop that sums an array of 64-bit integers on ARM. The pointer is in X1, the count is in X2, and the sum is in X0. The code is: loop: LDR X3, [X1], #8 (load one value and add 8 to the pointer); ADD X0, X0, X3 (add it to the sum); SUBS X2, X2, #1 (subtract one from the count and set flags); B.NE loop (branch back if the result is not zero). Four instructions, each 4 bytes, so the loop is 16 bytes. Every instruction does one thing. The load is the only one that touches memory. A core with a good branch predictor and out-of-order engine will overlap many iterations.
Now a memory-order example, which is where programmers meet the ARM difference. Thread A writes data = 42, then sets flag = 1. Thread B waits until flag is 1, then reads data. On x86 this works with plain stores, because stores are not reordered with other stores. On ARM the hardware may make flag = 1 visible before data = 42. Thread B might see flag set and read an old data. The fix is to write flag with release semantics (STLR) and read it with acquire semantics (LDAR). In Java you use volatile, in C++ std::atomic with memory_order_release and acquire, and the compiler emits the right instructions. Old code that relied on x86 behaviour by accident (for example a hand-made spin lock with plain variables) can fail only on ARM, and only sometimes, which is a rare and difficult bug.
Finally, a migration example. A team runs 400 c-class x86 instances with a JVM service. They test the same jar on Graviton instances. The Java bytecode needs no change. They must check native libraries: Netty, Snappy, zstd-jni and RocksDB-JNI all have aarch64 builds, but a small vendor library does not, and the build fails at startup. They run a load test, find that one Graviton instance with the same number of vCPUs handles a similar request rate at a lower price per hour, and move the fleet in stages: 10 percent, 50 percent, 100 percent, with the x86 pool kept for rollback. The savings are real only if the test on their own workload confirms them.
intuition: A small, tidy language where every sentence has the same shape, so the reader (the processor) needs very little work to understand it.
The design is natural because simple, regular instructions can be decoded and scheduled cheaply, and cheap decoding means the chip spends its power on useful work. The licensing is natural for the same reason from the business side: a contract that does not change lets hundreds of companies build chips for it, and lets software run on all of them. The weak memory model follows the same logic. By promising less, the hardware can reorder more freely and use less power, and the cost moves to the compiler and the programmer, who ask for order only where it is needed.
mistakes: People often think ARM chips are always slower than x86 chips because they are "mobile". In fact ARM is a contract, not a speed. Apple M-series and Neoverse V-series cores are among the fastest in the world per core. Speed depends on the implementation (width, caches, clock, memory), not on the instruction set.
People often think ARM is a chip that Arm Holdings makes and sells. In fact Arm licenses designs and the instruction set, and other companies make the chips. This is why you can buy ARM chips from Apple, Qualcomm, Ampere, AWS, Google and NVIDIA that are all quite different.
People often think code that works on x86 will work on ARM after a recompile. In fact, most code does, but code with data races that happened to work under x86's stronger memory order can break. Hand-written assembly, SIMD intrinsics for AVX, and native dependencies without arm64 builds also need work.
People often think RISC means fewer instructions and a smaller chip, and that this is the reason for the efficiency. In fact modern ARM has hundreds of instructions. The key point is regularity: fixed length, load/store, few special cases. This makes decoding and scheduling cheaper. The "reduced" in the name is about complexity per instruction.
tradeoffs: Choose ARM servers (Graviton, Axion, Cobalt, Ampere) for horizontally scaled, stateless services, JVM and Go workloads, web serving, data processing and containers, when your languages and dependencies are portable and you pay a cloud bill measured in thousands of instances. Cloud vendors price them lower, and each core often does the same work in less power. You give up some portability: you must build arm64 images, test native libraries, and keep x86 for any component that has no arm64 build.
Choose x86 when you depend on closed-source binaries, on AVX-512 or other x86-specific optimized code, on Windows server software, or on a vendor image that is only available for x86. Choose x86 also when you need the broadest hardware choice, for example very large memory (several terabytes per socket) or the highest single-thread clock. You pay more per unit of work in many cloud price lists, and often more power.
Choose an architecture license only if you can fund a design team for years: Apple, Qualcomm and NVIDIA do so because their volume and control over the product repay the cost. Choose a core license (Neoverse, Cortex) if you want a competitive chip in two to three years with a team of tens or hundreds, accepting that your core will match, not exceed, Arm's own design. Choose RISC-V instead (see riscv) if a license fee, a closed roadmap or export rules are the main problem, and you can accept a younger software ecosystem.
Choose a multi-architecture build (a manifest list with amd64 and arm64) as the default for container images. It costs extra CI time, and it lets you move workloads between architectures when prices or supply change.
friction: Software must be built for ARM. Most open-source software now has arm64 builds, but long tails remain: older proprietary agents, drivers, security tools, some Python wheels, and some JNI libraries. Binary-only vendors may not support ARM at all. Emulation (QEMU, Rosetta) works for development but is 2 to 10 times slower, and is not suitable for production.
The memory model is a cause of rare bugs. Lock-free code that was tested only on x86 may fail on ARM, often under load and not in tests. Tools such as ThreadSanitizer and the memory model of your language help, but they do not replace testing on ARM hardware. Performance is also uneven between implementations: a Cortex-A55 and a Neoverse V3 are both ARM, but they differ in speed by a large factor, and the vector length, cache sizes and memory systems vary. Do not assume that an arm64 benchmark from one vendor applies to another.
There are business risks. Arm is a single company that controls the architecture and the royalty rates. Licensees have fought with it: Arm and Qualcomm went to court over the license for the Nuvia core design, which shows that a license is a legal and strategic dependency. Finally, there is no single "ARM server standard" as complete as the x86 PC platform. Server boot, firmware and device description (SBSA, SBBR with UEFI and ACPI) have improved a lot, but edge cases still exist on smaller vendors' boards.
practice: Build and publish multi-architecture images by default: docker buildx build --platform linux/amd64,linux/arm64, with a manifest list so each node pulls the right one. Test on real ARM hardware in CI, not only under emulation. For the JVM, current OpenJDK builds for aarch64 are mature; check native dependencies (Netty, Snappy, zstd, RocksDB, TensorFlow or PyTorch wheels) before you move. In Python, prefer wheels with manylinux aarch64 tags.
Move in stages. Pick a stateless service, run it on a small number of ARM instances behind the same load balancer, compare p50 and p99 latency, CPU use and cost per request, then expand. Many teams find that ARM wins on cost per request, but the margin depends on your code, so measure. Watch for code that depends on x86: AVX intrinsics (use portable libraries or add NEON paths), inline assembly, and spin locks with plain variables.
For concurrent code, use the language's atomics and locks and do not rely on memory order that you observed on x86. If you write low-level code, learn acquire/release and test on ARM under stress. For learning, read the ARM Architecture Reference Manual sections on the memory model, and Patterson and Hennessy's ARM edition, and try a Raspberry Pi or a Graviton instance to disassemble small C functions (objdump -d) and look at the instructions the compiler chooses.
quiz: What does it mean that ARM is a load/store architecture? || Arithmetic and logic instructions work only on registers. Memory is accessed only by explicit load and store instructions, which keeps each instruction simple and uniform.
Why do fixed-length 4-byte instructions help a CPU decode more instructions per cycle? || The decoder knows where each instruction starts without examining the earlier ones, so several decoders can work in parallel. With variable-length x86 instructions, boundaries must be found first, which is serial and costs area and power.
Thread A writes data then sets a flag; Thread B waits for the flag and reads data. Why can this fail on ARM but work on x86, and what fixes it? || ARM has a weak memory model, so the hardware may make the flag visible before the data. x86 keeps stores in order. Use release on the flag write and acquire on the flag read (STLR and LDAR, or std::atomic or volatile in a high-level language).
A fleet of 400 instances runs a JVM service. What must you check before moving it to Graviton, and how do you roll out? || Check native libraries (JNI) and agents for arm64 builds, and build multi-arch images. Load test and compare latency and cost per request. Roll out in stages (10, 50, 100 percent) while keeping the x86 pool for rollback.
When would you choose an architecture license over a core license, and what is the price? || When you want your own core design for differentiation, as Apple, Qualcomm and NVIDIA do, and you have volume and a large design team. The price is years of design effort and risk. A core license gives a competitive chip faster, but you get no better than Arm's own design.
interview: Why is ARM said to be more power-efficient than x86, and how much of that is really the instruction set? || The ISA helps through fixed-length instructions, a load/store design and fewer special cases, which make wide decode and scheduling cheaper and remove the need for large decode logic. But most of the gap in a given product is implementation: core width, process node, cache and memory design, and the power-management policy. Modern x86 cores close much of the gap, so judge by measurements.
What breaks when you move a lock-free data structure from x86 to ARM, and how do you fix it? || The code may rely on x86 total store ordering. On ARM the hardware can reorder stores and loads, so a reader can see a flag before the data it guards. Fix it with proper atomics: acquire loads, release stores, compare-and-swap with the right memory order, and test with stress tools on ARM hardware.
How do the two Arm license types shape the chips in the market? || Architecture licensees (Apple, Qualcomm, NVIDIA) design their own cores and can tune them to their products. Core licensees (AWS Graviton, Google Axion, Microsoft Cobalt) use Arm's Neoverse designs and add their own memory, interconnect and I/O. Both run the same ISA, so one software ecosystem serves them all.
You are asked to cut the compute bill of a stateless service by 20 percent. Do you move to ARM? What is your plan and what are the risks? || Yes, as an experiment. Build multi-arch images, test native dependencies, run a canary on a small ARM pool, compare p99 latency and cost per request under real traffic, then expand. Risks are missing arm64 libraries, memory-order bugs in concurrent code, vendor agents without ARM builds and the need to keep two pools during the move.
Why did the NVIDIA acquisition of Arm fail, and what does it say about Arm's position? || Regulators in the UK, EU, US and elsewhere worried that NVIDIA could favor itself over competitors who depend on Arm's neutral licensing, so the deal was dropped in February 2022. It shows that Arm's value is as a neutral supplier of the contract to many rivals, and any owner who also competes with them is a conflict of interest.

@@ x86
value: x86 is the instruction set of Intel and AMD processors. It began with the Intel 8086 in 1978 and it is still the contract that most desktop, laptop and server software was written for. A program compiled for x86-64 runs on an Intel Core, an AMD Ryzen and an AMD EPYC chip from today or from twenty years ago. That promise of backward compatibility, kept for more than forty years, is the whole value of x86: the world's operating systems, databases, compilers and business software exist as x86 binaries, and moving them costs money.
Inside, a modern x86 chip is not simple. The instruction set is complex (CISC): instructions have lengths from 1 to 15 bytes, can read memory and compute in the same instruction, and carry many old features. The chip hides this. A front end decodes the complex instructions into simple internal operations called micro-ops, and a wide, out-of-order core (the general-purpose CPU design from cpucomp, L1) runs those micro-ops. So the outside is old and complex, and the inside is modern and RISC-like. The cost of the translation is area and power in the decoder, and that is the main complaint against x86.
For the layers above, x86 is the default platform of Linux (linux, L0) servers, of the cloud (most virtual machines are x86) and of Windows. It gives them a large and fast hardware market with two suppliers, Intel and AMD, and a huge software base. The ISA concept (isa, L3) explains what the contract means and why CISC and RISC differ; cpucomp explains how a core turns a stream of instructions into results. This read shows how x86 combines them, and what it costs.
terms: CISC (complex instruction set computer) — a design where one instruction can do several steps, such as read memory, compute and write back.
Micro-op (µop) — a simple internal operation that the core executes; the front end decodes each x86 instruction into one or more of them.
Variable-length encoding — instructions occupy different numbers of bytes (1 to 15 on x86), so the decoder must find where each one ends.
µop cache — a small cache that stores already decoded micro-ops, so hot loops skip the decoders.
x86-64 (AMD64) — the 64-bit extension of x86 designed by AMD, with 16 general registers and 64-bit addresses.
SIMD — one instruction works on many values packed in a wide register; x86 versions are SSE, AVX, AVX2 and AVX-512.
Total store ordering (TSO) — the x86 memory model: stores from one core become visible in program order, which is stronger than ARM's model.
Microcode — firmware inside the CPU that implements rare or very complex instructions as sequences of micro-ops.
Real mode — the 16-bit start-up mode of the 8086 that every x86 CPU still begins in when it is powered on.
history: In 1978 Intel released the 8086, a 16-bit processor with about 29,000 transistors. Its cheaper cousin, the 8088, was chosen by IBM for the IBM PC in 1981, and that single decision made x86 the standard of personal computing. Because software had already been written, every later processor had to keep running it. The 80286 (1982) added protected mode, and the 80386 (1985) added 32-bit registers, a flat address space and paging, which is what Unix and Windows NT needed.
The big technical step came in 1995 with the Pentium Pro. Its designers could not make the x86 instructions themselves fast, so they translated them into simple micro-ops and ran those in an out-of-order engine. Every high-performance x86 core since then works this way. Intel's attempt to leave x86 failed: the Itanium (2001), a new 64-bit design that needed compilers to find parallelism, was slow on old code and was not adopted. AMD instead extended x86 to 64 bits. It announced AMD64 in 2000 and shipped it in the Opteron in April 2003. It kept compatibility, doubled the general registers to 16, and added 64-bit addresses. Intel copied it in 2004 (as EM64T, now called Intel 64). Microsoft and Linux supported it, and AMD64 became the standard.
After that, the story is about vectors and about competition. SIMD grew from MMX (1997) to SSE (1999), AVX (2011), AVX2 (2013) and AVX-512 (2016), with wider registers each time. AMD's Zen (2017) returned AMD to the lead in cores per socket, using chiplets built by TSMC, while Intel struggled to bring its 10 nm process to production. Apple's M1 (2020) and ARM server chips (AWS Graviton) showed that x86 could be beaten on efficiency. In 2023 Intel proposed APX (more registers and three-operand instructions) and AVX10 (a cleaner vector family). In October 2024 Intel and AMD formed the x86 Ecosystem Advisory Group, with large customers and software vendors, to coordinate the ISA, and in 2025 they announced agreement on features such as FRED (a faster, simpler interrupt and event mechanism), AVX10 and APX. Intel had also proposed X86S, a version without the old 16-bit and 32-bit legacy modes, but it was later withdrawn.
how: Fetching starts with bytes, not with instructions. The core fetches 16 or 32 bytes from the instruction cache and must find where each instruction begins. An x86 instruction may have up to four legacy prefixes, a REX prefix, an opcode of 1 to 3 bytes, an addressing byte (ModRM), an optional scale-index-base byte (SIB), a displacement and an immediate. The length of an instruction depends on its first bytes, so the decoder cannot start the next one until it knows the length of the current one. Hardware solves it by guessing boundaries at every byte in parallel and discarding wrong guesses. That works, and it costs area and power, and it limits how many instructions can be decoded per cycle (Intel's Golden Cove decodes 6 per cycle; Apple's M1 decodes 8 with a fixed-length ISA, see armisa).
To avoid paying this cost repeatedly, x86 cores keep a micro-op cache (Intel calls it the decoded stream buffer; AMD calls it the op cache), which holds thousands of already decoded micro-ops. A hot loop runs from this cache and the decoders are idle, saving power and giving higher bandwidth (6 to 8 micro-ops per cycle on recent cores). The decoders are used for cold code. Rare, complex instructions, such as string operations or system instructions, come from a microcode ROM that expands them into sequences.
The decoded micro-ops go into the out-of-order engine, the general-purpose core from cpucomp. Register renaming maps the 16 architectural registers onto a few hundred physical registers, which removes false dependencies. A reorder buffer of 300 to 500 entries tracks the instructions in flight. Schedulers send micro-ops to execution ports when their inputs are ready. Branch predictors guess the direction of branches so the front end can run ahead. Loads and stores pass through a store buffer that forwards recent stores to later loads. Some pairs, such as a compare followed by a branch, are fused into one micro-op to save slots. From this point, an x86 core and an ARM core look the same inside; the difference was in the front end.
An important contract detail is the memory model. x86 uses total store ordering. A store is never reordered with an earlier store, and loads are never reordered with earlier loads, so the only reordering a programmer must handle is that a later load may pass an earlier store to a different address. A single instruction (MFENCE) or a locked instruction (LOCK ADD, XCHG, CMPXCHG) removes it. This is simple for programmers, and it costs the hardware extra work: the core must track ordering of stores and loads strictly. Code written against this model is the reason that moving to ARM exposes hidden bugs.
Vector instructions give x86 its throughput for data work. AVX2 operates on 256-bit registers (8 floats per instruction) and AVX-512 on 512-bit registers (16 floats) with mask registers for conditions. Spark's vectorized engines, columnar scans in Parquet readers, compression codecs (zstd, LZ4), hashing, and machine-learning kernels all use them. The runtime dispatches by CPU feature (CPUID) so a single binary can use AVX-512 where it exists. AVX-512 has a history of problems: early Intel chips lowered the clock when it was used, Intel removed it from desktop chips from the 12th generation, and AMD supported it first by running 512-bit operations as two 256-bit halves (Zen 4) and later with full-width units (Zen 5). AVX10 is meant to give one consistent vector family across Intel cores.
Scale comes from threads, cores and chiplets. Simultaneous multithreading (Intel Hyper-Threading, AMD SMT) lets two hardware threads share one core, so the units idle less when one thread waits for memory; it often adds 15 to 30 percent throughput for server work. Cores share a last-level cache and keep their private caches consistent with a coherence protocol (MESI and variants). AMD builds its server chips from small chiplets, each with 8 or 16 cores, joined by a fabric to a central I/O die with the memory controllers; this raises yield and lets the same chiplet serve desktop and server. Memory is DDR5 with 8 to 12 channels per socket on servers, which gives roughly 300 to 600 GB/s per socket. For a data engineer this matters more than the core count: a Spark executor that scans Parquet is limited by how many bytes per second the memory and cache system can deliver.
Last, the system level. An x86 chip starts in 16-bit real mode, goes through firmware (UEFI, with ACPI tables describing the hardware), and the kernel switches to 64-bit long mode. Because every PC-class machine follows the same platform conventions, one operating system image boots on any of them. This is the second part of the compatibility advantage: not only the instructions, but the whole platform.

example: Take one load instruction, MOV RAX, [RBX + RCX*8 + 0x10]: "read 8 bytes from the address RBX + 8 x RCX + 16 into RAX". As bytes it is 48 8B 44 CB 10, five bytes. 48 is the REX prefix that selects 64-bit operands. 8B is the opcode for a load. 44 is the ModRM byte: mod = 01 (an 8-bit displacement follows), reg = 000 (RAX), rm = 100 (a SIB byte follows). CB is the SIB byte: scale = 11 (times 8), index = 001 (RCX), base = 011 (RBX). Last, 10 is the displacement. One x86 instruction did a shift, two additions and a memory read.
On AArch64 the same work needs two instructions of 4 bytes each: ADD X1, X1, #16, then LDR X0, [X1, X2, LSL #3]. Eight bytes instead of five, but each one is easy to decode. This is the CISC and RISC trade in one picture: x86 has denser code and a harder decoder. The x86 core splits that load internally into micro-ops (an address calculation and a load), so after decoding both architectures execute something like the same two steps.
Now a throughput example. A loop sums an array: loop: add rbx, [rsi] (load and add in one instruction); add rsi, 8; dec rcx; jnz loop. The first instruction decodes into one fused load-add micro-op. The dec and jnz pair is macro-fused into one micro-op. The loop is therefore 3 micro-ops per iteration. On a core that can issue 6 micro-ops per cycle and run one loop iteration per cycle (limited by 1 taken branch per cycle and the dependency on rbx, which takes 1 cycle), it needs only the micro-op cache and runs at about 1 iteration per cycle. At 4 GHz that is 4 billion elements per second, or 32 GB/s of reads, which is bound by the cache and memory system, not the decoder. With AVX2 you add four values at a time and reach the cache bandwidth limit sooner.
A third example is about cost. A decoded instruction needs about 1 µop on average. Decoders are a modest fraction of the power of a big core. For a small, low-power core the decoder is a larger share, which is why Intel's E-cores (Gracemont and later) use a different design: they decode two groups of three instructions in parallel with a simpler design. Even so, the ISA is only a part of the story, and a modern Zen or Lion Cove core comes within reach of Apple's cores on efficiency for many tasks.
intuition: An old, much-loved language that everyone still speaks, with an interpreter at the door who translates it into a plain internal language before the work starts.
The design makes sense once you see that compatibility is worth more than elegance. A new instruction set would need years of software work and billions in ecosystem cost. A translation layer in hardware costs a few percent of the chip, and it lets the ISA keep growing by addition. So x86 became a stable outside and a changing inside. The inside can be redesigned every two years (wider, deeper, faster) without any application noticing.
mistakes: People often think x86 is slow because it is CISC. In fact modern x86 cores decode into micro-ops and execute them like any RISC core. The complexity costs power and design effort in the front end, but the fastest single-thread cores in the world are x86 or ARM, and the difference between them is mostly implementation.
People often think x86 is obsolete and ARM will replace it soon. In fact x86 still holds most of the server and PC market, has two active suppliers, and the software base is huge. ARM's share is growing in cloud (Graviton, Axion, Cobalt) and laptops, but migration is slow because software, drivers and vendor support must move too.
People often think 64-bit x86 was invented by Intel. In fact AMD designed AMD64 in 2000 and shipped it in 2003, after Intel's Itanium plan failed. Intel adopted a compatible version in 2004.
People often think AVX-512 always makes code faster. In fact on some chips the clock speed drops when wide vector units are busy, mixing scalar and vector code can lose, and the instruction is not available on all cores (it is absent on many Intel client chips). Measure on the target hardware and use runtime CPU detection.
tradeoffs: Choose x86 when you must run existing binaries, Windows software, closed-source agents or vendor appliances without a port, or when your code uses x86-specific libraries (AVX-512 tuned kernels, Intel MKL, some JVM and database features). You pay more power and often a higher price per vCPU in the cloud, and you depend on two suppliers.
Choose AMD EPYC or Intel Xeon by workload. AMD EPYC (Zen 5) offers up to 192 cores per socket (the dense variants) and 12 memory channels, which suits throughput work such as Spark executors, databases and virtualization. Intel Xeon 6 offers up to 128 performance cores or up to 288 efficiency cores per socket, plus built-in accelerators such as AMX for matrix math, which suits inference on CPUs and some network and storage offload. Compare price, power, memory bandwidth and the software you run, and test on your workload.
Choose ARM when the software is portable and the fleet is large (see armisa). Choose x86 when the migration cost, risk or time is larger than the saved cloud bill. A mixed fleet with multi-architecture images lets you move gradually. Choose the wide vector paths (AVX2, AVX-512) when the work is data parallel (scans, compression, hashing), and keep a scalar fallback. You give up simplicity of builds and have a risk of clock drops on older Intel chips.
Choose to depend on x86 compatibility as a long-term asset only if you can accept that it carries legacy: 16-bit modes, segmentation, many rarely used instructions. These are mostly invisible to applications, but they make firmware, security and verification harder.
friction: The front end is the main cost. Variable-length decode, prefixes and legacy instructions need large decoders and a micro-op cache, and they use power even when the chip is idle. In small, low-power devices this matters. Intel and AMD close the gap with better process nodes, power gating and designs such as Lunar Lake (2024), which put memory on the package, but the ISA stays a disadvantage in the lowest power range.
Verification and security are hard. Decades of features make it difficult to prove that the hardware behaves correctly, and the speculative execution that makes cores fast has produced security flaws (Spectre and Meltdown in 2018, and many after). Fixes cost performance. The platform also carries management engines and firmware that run below the operating system, which is a concern for security teams.
Governance is narrow. Only Intel and AMD (and a small licensee in China) are allowed to build x86 chips, under a cross-license that dates from the 1970s and was renewed after a legal settlement in 2009. New features need agreement between two competitors, and for years each added incompatible vector extensions. The Ecosystem Advisory Group is an attempt to fix this. Last, Intel's manufacturing difficulties in the 2010s and its restructuring since show that an ISA does not protect a company from process-technology risk. AMD's use of TSMC is one reason it gained share.
practice: Write portable code and let the compiler choose instructions. Build with a safe baseline target (x86-64-v2 or v3 levels, which Linux distributions use) and use runtime dispatch for AVX2 and AVX-512 paths. Most libraries you use (Arrow, zstd, simdjson, OpenBLAS) already do this. Check which level your fleet supports before you compile with -march=native, because a binary built on one machine may crash on another with an "illegal instruction" error.
When you benchmark, look at more than clock speed. Check the instructions per cycle, the cache misses and the memory bandwidth with perf stat. For data platforms, the memory channels and the cache size per core often decide the Spark and database result more than the core count. Prefer instance types with the newest generation, because each generation of x86 gains 10 to 20 percent per core, and check the hypervisor (on AWS Nitro, the cost of virtualization is very small).
Keep a multi-architecture build pipeline even if you run only x86 today, so that you can try ARM when prices change. For performance-critical code on x86, learn to read compiler output (objdump, perf annotate) and know the difference between instruction count, micro-op count and cycles. For security, apply the microcode and kernel mitigations that your vendor ships, and measure their cost on your workload instead of turning them off.
quiz: What is a micro-op, and why do x86 CPUs use them? || A micro-op is a simple internal operation. The front end decodes each complex x86 instruction into one or more micro-ops, and the out-of-order core executes those, which lets the core work like a RISC machine while keeping the x86 contract.
Why is decoding x86 harder than decoding AArch64? || x86 instructions have variable length (1 to 15 bytes), so the decoder must find instruction boundaries before decoding, and that costs area and power. AArch64 instructions are always 4 bytes, so decoders can work in parallel at known positions.
What does the micro-op cache do for a hot loop? || It stores already decoded micro-ops, so the loop runs without using the legacy decoders. This gives higher bandwidth (6 to 8 micro-ops per cycle) and saves power.
MOV RAX, [RBX + RCX*8 + 0x10] is 5 bytes on x86. How many instructions and bytes does the same work need on AArch64? || Two instructions of 4 bytes each, 8 bytes in total: ADD X1, X1, #16 and LDR X0, [X1, X2, LSL #3]. Code is denser on x86 but easier to decode on ARM.
Your fleet is 600 x86 instances running stateless JVM services, and finance asks for a 20 percent cost cut. What do you evaluate before choosing ARM versus staying on x86? || Check that native libraries and agents have arm64 builds, run a canary on ARM instances and compare p99 latency and cost per request, and consider the migration effort and risk. If the service is portable, ARM usually wins; if you depend on x86-only software or AVX-512 kernels, stay or move to a newer x86 generation.
interview: How can the x86 ISA be CISC and yet the core inside be fast and RISC-like? || The front end translates each instruction into simple micro-ops, and the back end (rename, reorder buffer, schedulers, execution units) works on micro-ops like any out-of-order RISC core. The cost is moved into decoding, which is partly hidden by the micro-op cache. This started with the Pentium Pro in 1995.
Why did AMD64 win over Itanium, and what does it say about ISA design? || AMD64 ran all existing 32-bit software at full speed and added 64-bit addressing and more registers. Itanium needed new compilers and ran old code slowly. It shows that compatibility and an incremental path beat a cleaner design when the software base is large.
What is the x86 memory model and how does it differ from ARM's? || x86 uses total store ordering: stores are seen in program order, and only a later load passing an earlier store to another address is allowed. ARM allows much more reordering. Code with data races may work on x86 and fail on ARM, so use proper atomics and acquire/release semantics.
When would you not use AVX-512 in production code? || When the target fleet is mixed and some CPUs lack it, when it lowers the clock and hurts the scalar code that shares the core, or when the data is memory-bound so wider vectors give no gain. Use runtime detection and measure on the actual hardware.
How would you decide between AMD EPYC, Intel Xeon and Graviton for a Spark cluster? || Benchmark the real job. Check memory channels and bandwidth per core, core count per dollar and per watt, local NVMe availability, and library support. Shuffle-heavy and scan-heavy Spark jobs are often bound by memory and I/O, so the cheapest cores per GB/s often win. Include migration cost for ARM.
What changed with the x86 Ecosystem Advisory Group? || Intel and AMD agreed to coordinate new ISA features with large customers and software vendors. Their goal is to avoid incompatible extensions (as happened with AVX-512 variants) and to align features such as FRED, AVX10 and APX, so software can rely on a common baseline.

@@ nvme
value: NVMe (Non-Volatile Memory Express) is the protocol that lets a computer talk to a flash storage drive directly over the PCIe bus, and an NVMe SSD is the drive that speaks it. Before NVMe, SSDs used SATA and the AHCI command set, which were designed for spinning disks: one command queue, 32 commands deep, and a design that assumes each request takes milliseconds. A flash drive can answer in about 80 microseconds and can serve a million requests per second, so the old interface became the bottleneck. NVMe removes it. A modern NVMe drive reads a random 4 KB block in roughly 70 to 100 microseconds, delivers 1 to 2 million random reads per second, and streams 7 GB/s (PCIe 4.0) or 14 GB/s (PCIe 5.0) in sequence. A 7,200 rpm hard disk does about 100 to 200 random reads per second, so the gap is about 10,000 times for random reads.
This changes how systems are designed. Databases, Kafka brokers, search engines, Spark shuffle and caching layers (for example the Databricks disk cache) treat local NVMe as a large, fast, cheap tier between memory and the object store. Cloud storage-optimized instances (AWS i3en, i4i, Im4gn and similar) attach NVMe drives directly to the host. Software has changed too: the Linux kernel's multi-queue block layer, io_uring and user-space drivers such as SPDK exist because the old storage stack, with its locks and interrupts, cost more than the device.
Two layers below make this work. The storage-device concept (storagedev, L3) explains the medium: NAND flash cells, organized in pages and blocks, which can be read fast but can only be written to erased pages and erased in large blocks. The flash translation layer (ftl, L3) is the firmware that hides these rules. It maps logical block addresses to physical pages, writes new data to fresh pages, collects garbage and spreads wear. NVMe is the clean front door on top: a parallel command protocol that matches many CPU cores, and a controller that runs the FTL behind it.
terms: NAND flash — memory made of transistors that trap charge to store bits; it keeps data without power but must be erased in whole blocks before it is rewritten.
Page and block — a page (4 to 16 KB) is the smallest unit you can program; a block (hundreds of pages, several MB) is the smallest unit you can erase.
FTL (flash translation layer) — controller firmware that maps logical addresses to physical pages, performs garbage collection and wear leveling.
Write amplification — the ratio of bytes the flash actually writes to bytes the host asked to write; it is above 1 because of garbage collection.
Submission queue and completion queue — a pair of ring buffers in host memory: the host puts commands in the first and the drive puts results in the second.
Doorbell — a small register on the drive that the host writes to tell it that new commands are waiting.
Queue depth — the number of commands in flight at once; it is how a host keeps a parallel device busy.
DWPD (drive writes per day) — an endurance rating: how many times you can overwrite the whole drive each day during the warranty (usually 5 years).
Power-loss protection (PLP) — capacitors that let an enterprise drive finish writing its cache to flash after a power cut, so it can acknowledge writes safely at DRAM speed.
history: Flash drives first replaced disks in laptops and servers through SATA, in the late 2000s (the Intel X25-M in 2008 is a famous example). They worked, but the interface capped speed at about 550 MB/s and around 100,000 operations per second. A few companies, first Fusion-io, put flash on PCIe cards with custom drivers to get around this. Each used its own driver, which was a problem for operating systems and customers.
In 2009 a work group led by Intel and about 90 companies began a standard to replace the vendor-specific drivers. The NVM Express 1.0 specification came out on 1 March 2011. Linux added an NVMe driver in 2012 (kernel 3.3), and the multi-queue block layer (blk-mq, Linux 3.13, 2014) was written in part to make use of the many queues. Early drives were PCIe cards; then came the M.2 stick for laptops, U.2 for servers and, later, the EDSFF forms (E1.S, E3.S) for dense, hot-swappable data-centre drives.
The standard kept growing. NVMe over Fabrics (2016) carried the same commands across a network, first over RDMA and Fibre Channel, and then over plain TCP (2018). NVMe 2.0 (2021) split the specification into modules and added Zoned Namespaces (ZNS), which expose flash zones that are written sequentially so the drive does not need to do garbage collection, and Key Value command sets. Flexible Data Placement (FDP) later gave hosts a gentler way to group data by lifetime. Revisions 2.1 (2024), 2.2 (2025) and 2.3 (August 2025) added management, security and live-migration features, and NVMe 2.4 followed in August 2026 with support for post-quantum cryptography and rate limiting. Meanwhile PCIe doubled in speed every few years: a 4-lane link gives about 4 GB/s on PCIe 3.0, 8 GB/s on 4.0, 16 GB/s on 5.0 and 32 GB/s on 6.0. Intel's Optane (3D XPoint, around 10 microsecond latency) was a faster NVMe medium, but it was discontinued in 2022, so NAND flash remains the standard.
how: The key design is the queue pair. The host allocates a submission queue (SQ) and a completion queue (CQ) in its own memory. Each is a ring buffer. To read a block, the driver writes a 64-byte command into the SQ (operation, logical block address, length, and the host memory address where the data should go), then writes the new tail position into a doorbell register on the drive with one memory-mapped write. The drive fetches the command with DMA, does the read, writes the data straight into the host buffer with DMA, and posts a 16-byte entry into the CQ. A phase bit in each entry tells the host that the entry is new. The drive then raises an interrupt (MSI-X), or the host polls the CQ. No locks are needed, because each queue has one producer and one consumer.
The spec allows up to 65,535 I/O queues, each with up to 65,536 commands. Real drives support somewhere between 8 and 128 queues. The Linux driver creates one queue pair per CPU core. Each core submits to its own queue and receives its own completion interrupt on the same core, so no core waits for a lock held by another, and the data stays in that core's cache. AHCI/SATA has one queue of 32 commands shared by all cores, with a lock around it, and each command needs several register reads that are slow on PCIe. An NVMe command needs one doorbell write. This is the first source of speed: the protocol removes software overhead per request, from tens of microseconds to a few microseconds.
Behind the queues sits the controller, and here the layers below add their value. The NAND chips (storagedev) are organized in channels (8 to 16), each with several dies and planes. A read of a page takes about 50 to 100 microseconds inside the chip, a program of a page takes hundreds of microseconds, and an erase of a block takes a few milliseconds. One chip is slow, but the controller reads many in parallel across channels, so the sum is millions of operations per second. That is why a drive needs a high queue depth: one request at a time uses one die, 32 requests in flight use many dies. Little's law makes it exact: operations per second = queue depth / latency. At 80 microseconds, depth 1 gives 12,500 reads per second, and depth 32 gives about 400,000, if the drive has the parallelism to match.
The FTL (ftl) makes the flash look like a normal block device. Flash cannot overwrite a page in place, so for every write the FTL puts the data in a free page and updates a mapping table from logical block address to physical page. The table is large, about 4 bytes per 4 KB page, so roughly 1 GB of drive DRAM per 1 TB of flash. The old page becomes stale. When free blocks run low, garbage collection picks a block with many stale pages, copies its live pages elsewhere, and erases it. The extra copying is write amplification. Wear leveling moves data so that no block gets all the erase cycles, because each block survives only a limited number of erases (roughly 100,000 for SLC, 3,000 for TLC and 1,000 for QLC cells). Over-provisioning, which is spare flash the host cannot see (7 percent in many consumer drives and 28 percent or more in write-heavy enterprise drives), gives garbage collection room to work and lowers write amplification.
Two more parts of the protocol are worth knowing. First, there is one admin queue pair for management commands (create or delete I/O queues, identify the drive, read the health log, format, firmware update), and the I/O queues carry only data commands (read, write, flush, and Dataset Management, which is the command behind TRIM and tells the FTL that blocks are no longer used). Second, a drive exposes one or more namespaces, each a separate range of logical blocks, so a single physical drive can be split or shared between virtual machines. The PCIe link itself (PCIe 4.0 x4 is about 8 GB/s, PCIe 5.0 x4 about 16 GB/s) is a point-to-point link from the drive to the CPU, with no shared bus and no host bus adapter in between, which also removes one hop of latency compared with SATA.
Writes need a special note. A drive acknowledges a write when the data is in its DRAM cache, which is faster than writing to flash. If power fails, the cache is lost. A host that needs durability sends a flush command (this is what fsync turns into). Enterprise drives have capacitors, so they can treat the cache as durable and acknowledge flushes immediately, which allows tens of thousands of synced writes per second. A consumer drive without PLP must really write to flash, so flushes can be much slower. This is the reason databases and Kafka care about the drive model.

example: First, parallelism. Suppose one 4 KB random read takes 80 microseconds in the drive. At queue depth 1, a thread gets 1 / 80 microseconds = 12,500 reads per second, about 50 MB/s, no matter how fast the link is. To reach 1,000,000 reads per second you need 1,000,000 x 80 microseconds = 80 requests in flight. If your program does synchronous reads in one thread, you will see 12.5K IOPS and conclude that the drive is slow. With 8 threads at depth 10 each, you reach the target. That is why io_uring or async I/O and many threads are used for NVMe work.
Second, endurance. A 3.84 TB enterprise drive is rated at 1 DWPD for 5 years. That is 3.84 TB x 365 x 5, about 7,000 TB, or 7 PB of host writes. Suppose a service writes 2 TB per day to this drive. That is about 0.5 DWPD, so the drive lasts about 10 years on paper. Now suppose the application is a RocksDB store with compaction. If the application writes 500 GB per day of user data and the LSM compaction multiplies it by 15, the host writes 7.5 TB per day. That is about 2 DWPD, double the rating, and the drive wears out in about 2.5 years. The flash itself adds its own write amplification (often 1.1 to 3), which is what the DWPD rating already accounts for under a standard workload. Always compute total host writes after software amplification.
Third, fsync. A database does 20,000 transactions per second, and each commit calls fsync. On a drive with power-loss protection, a flush is acknowledged in tens of microseconds, so one log device handles this easily, especially with group commit. On a consumer drive without PLP, each flush may take 1 to several milliseconds, so one thread can do only some hundreds to a few thousand flushes per second, and the commit rate collapses. The two drives have the same advertised read speed, and very different commit throughput.
intuition: A restaurant kitchen with many cooks and many order slips: instead of one waiter handing one slip at a time, every waiter has their own spike of slips, and the kitchen works on all of them in parallel.
The design is natural once you see that flash is parallel inside, and the CPU is parallel outside. A disk head can do one thing at a time, so a single queue was fine. Flash has dozens of dies that can work at once, and a server has dozens of cores that can ask at once. The right interface connects the two sets of parallelism without a shared lock in the middle. The strange rules of flash (write only to clean pages, erase in blocks) are hidden behind a translation layer, so software sees a simple array of blocks, and pays only when the drive is full or busy with background work.
mistakes: People often think a faster sequential speed (for example 14 GB/s) means a faster database. In fact most database work is small random I/O at low queue depth, where latency matters, and drives with the same sequential rating can differ by two times in 4 KB latency or mixed read/write behaviour. Test with fio at your real block size and queue depth.
People often think SSDs have no write problem, because there is no moving part. In fact flash wears out. Each block survives a limited number of erase cycles, and write amplification multiplies the host's writes. Heavy log, compaction or shuffle workloads can reach the rated endurance in a few years.
People often think a write that has returned is safe on disk. In fact it is safe only after a flush (fsync) completes, and a drive without power-loss protection may lose its cache. Applications that skip fsync, or drives that lie about flushing, are a real source of data loss.
People often think instance-store NVMe in the cloud is like a normal disk. In fact the local drives of an instance are tied to the host. Data is lost if the instance stops, is terminated, or the host fails. Use them for caches, shuffle and temporary data, or for storage that is replicated at the application level (Kafka replicas, Cassandra, Elasticsearch), and not as the only copy.
tradeoffs: Choose local NVMe when you need the lowest latency and the highest IOPS per dollar, and the data is replicated by the application or can be rebuilt: Kafka and Cassandra brokers, search indexes, Spark shuffle and spill, query caches. You give up durability beyond the instance and flexibility, because capacity is tied to the instance size and the data is gone if the host is lost. Choose network block storage (EBS gp3, io2) when you need data to survive the instance and be moved or snapshotted, and accept a latency of about 0.5 to 1 millisecond and a per-volume cap on IOPS.
Choose enterprise drives with power-loss protection (and 1 to 3 DWPD) for databases and log devices where fsync latency and durability matter. Choose read-intensive, cheaper drives (about 0.3 to 1 DWPD) for mostly-read datasets, archives and caches. Consumer QLC drives are the cheapest per terabyte, and are fine for a development machine, but a sustained write drops to a slow rate once the fast cache fills and endurance is low.
Choose a higher PCIe generation and more lanes only if you can use the bandwidth. A scan-heavy analytics node reading Parquet can use 14 GB/s from a PCIe 5.0 drive, but an OLTP database at 4 KB random I/O is bound by latency and IOPS, where PCIe 4.0 and 5.0 drives are similar. Network, CPU and memory often become the limit first; a 100 Gbps NIC carries only 12.5 GB/s, which is less than one fast drive.
Choose NVMe over Fabrics (RDMA or TCP) when you want disaggregated, shared flash with near-local latency (about 100 to 200 microseconds with TCP, lower with RDMA). You pay in network design, CPU for the TCP path and operational complexity. Choose an object store (S3) with a local NVMe cache for bulk data: it is cheap and durable, and the NVMe layer recovers speed for hot data.
friction: The main hidden cost is background work. When a drive is full, or when sustained writes exceed what garbage collection can keep up with, latency spikes. A drive that reads in 80 microseconds can show tail latencies of several milliseconds while it erases a block or relocates data. Performance also falls as the drive fills: at 90 percent full, write amplification can be several times higher than at 50 percent. Keep 20 percent or more free or over-provision, and watch p99.9 latency, not the average.
Endurance and retention are limits. QLC cells hold only about 1,000 erase cycles, and data in worn cells can lose charge over months when powered off. Drives report wear through SMART and the NVMe health log (percentage used, media errors, temperature), and these should be monitored. Thermal throttling is real: M.2 drives at full speed need a heat sink or airflow, or they slow down by half.
Software is not free. At millions of IOPS the kernel path (system call, interrupts, copies, the file system) can use more CPU than the device. io_uring, polling, direct I/O and user-space stacks (SPDK) help, at the cost of complexity. File systems and databases written for disks may not use the parallelism. Finally, the drive is a black box. The FTL is proprietary firmware: you cannot see garbage collection, behaviour changes between firmware versions, and failures can be sudden and total. ZNS and FDP try to give hosts more control, but adoption is still slow because they need changes in software.
practice: Measure before you buy. Use fio with your real block size, read/write mix and queue depth, and look at latency percentiles, not only IOPS. Test steady state: fill the drive and run for 30 minutes or more, because fresh drives and drives with a hot cache look much better than they are. Compare the numbers to the instance or drive datasheet, and check the cloud provider's stated IOPS per instance size.
Give a database or Kafka log a drive with power-loss protection, and keep a high queue depth through async I/O or many threads. Use the XFS or ext4 file system with the noatime option, align partitions, and leave a part of the drive unpartitioned or trimmed if the vendor suggests it. Enable discard or run fstrim on a schedule so that the drive knows which blocks are free. For Kafka, sequential appends give low write amplification, and the page cache hides much latency, so the real limit is often network, not disk. For LSM engines (RocksDB, Cassandra), choose the compaction strategy with write amplification in mind, and size drives by endurance as well as capacity.
Monitor the NVMe health: use nvme smart-log and node exporters to track percentage used, media errors and temperature, and alert on rising latency. Plan the failure: for instance-store drives, replicate across hosts and test rebuild time. When using Spark on local NVMe, put shuffle and spill directories on it (spark.local.dir), and size the number of drives so that parallel tasks do not queue on one device. If you have to decide between more RAM and more NVMe, remember that NVMe is about 10 times cheaper per GB than DRAM and about 100 to 1,000 times slower for random access.
quiz: Why does NVMe have so many queues while SATA/AHCI has one? || Flash has many parallel dies and a server has many CPU cores. NVMe gives each core its own submission and completion queue (up to 65,535 queues, each 65,536 deep), so cores do not share locks. AHCI has one queue of 32 commands, designed for a disk head that does one thing at a time.
What happens between a write call and the data being safe on flash, and what does fsync do? || The drive acknowledges the write when the data is in its DRAM cache, which is fast but lost on power failure. fsync makes the host send a flush command, which returns only when the data is durable, either on flash or protected by the drive's power-loss capacitors.
Why must a flash drive erase before it rewrites a page, and what does the FTL do about it? || Flash can program only erased pages, and erase works on whole blocks. The FTL writes new data to a free page, updates the logical-to-physical map, marks the old page stale, and later garbage-collects blocks by copying live pages elsewhere and erasing the block.
A read takes 80 microseconds. How many requests must be in flight to reach 1 million reads per second? || By Little's law, queue depth = rate x latency = 1,000,000 x 0.00008 s = 80 requests in flight.
You design a RocksDB service with 500 GB of user writes per day and compaction write amplification of 15. Do you choose a 1 DWPD or a 3 DWPD drive of 3.84 TB? || Host writes are 7.5 TB per day, about 2 DWPD on 3.84 TB, so a 1 DWPD drive would wear out in about half of its rated 5 years. Choose a 3 DWPD drive or a larger drive, or reduce compaction amplification, and add more headroom for the drive's own write amplification.
interview: Where does the latency of an NVMe read come from, and which parts can software control? || About 70 to 100 microseconds is NAND read time plus controller and error-correction work. Software adds submission, interrupt and kernel overhead (a few microseconds, reducible with polling, io_uring or SPDK), file system and page cache effects, and queueing delay when queue depth exceeds drive parallelism. Software cannot change the NAND time, but it can avoid queueing and avoid background-work collisions.
Your database p99 write latency spikes every few minutes on a drive that is 85 percent full. What do you suspect and how do you check? || Garbage collection with high write amplification, or a full SLC cache. Check the drive's SMART data and latency over time, compare with a drive at 50 percent usage, and run fio steady-state tests. Fix by freeing or over-provisioning space, using fstrim, choosing a drive with more over-provisioning, or spreading writes over more drives.
How do you keep data safe when using instance-store NVMe for Kafka or Cassandra? || The local disks are ephemeral, so rely on application-level replication across hosts and availability zones (replication factor 3), make sure replicas are rebuilt automatically, and keep backups or tiered storage in object storage. Do not rely on a single local copy.
What are ZNS and FDP, and why would you use them? || They give the host a way to place data by lifetime, so the drive does less garbage collection. ZNS exposes sequentially written zones; FDP lets hosts tag writes with placement groups. They lower write amplification and tail latency, but the software, such as RocksDB or file systems, must support them.
Why can a 14 GB/s PCIe 5.0 drive give no gain over a 7 GB/s PCIe 4.0 drive for your OLTP database? || OLTP is small random I/O at low queue depth, bound by latency and IOPS, not by bandwidth. Both drives have similar NAND latency. The extra bandwidth helps scans, backups and bulk loads, not 4 KB transactions.
How is disaggregated flash through NVMe-oF different from local NVMe? || The commands are the same, but they travel over a network (RDMA or TCP), adding network latency (tens to a couple of hundred microseconds) and using network and CPU resources. You get shared capacity, flexible allocation and independent scaling, at the cost of more complexity and a failure domain that includes the network.

@@ riscv
value: RISC-V (pronounced "risk five") is an instruction set that anyone can use, without a licence fee and without asking permission. It was started at the University of California, Berkeley in 2010. For forty years, the choice of a processor instruction set meant buying a licence from a company: Intel and AMD for x86, Arm for ARM. RISC-V changed that. The specification is published by a non-profit, RISC-V International, and any company, university or hobbyist can design a chip that implements it, sell it, and keep the design private if they wish.
The value is control and cost, not speed. A company that builds a storage controller, a network chip or an AI accelerator needs small processor cores inside it to manage the work. With RISC-V it can design or buy such a core, add its own instructions for its special task, and pay no per-chip royalty to a third party. This is why RISC-V first won in microcontrollers and in the hidden cores inside chips (for example the management cores in GPUs and storage controllers), and why countries that fear export controls, such as China, India and the European Union, support it. It is now moving into phones, laptops and servers, where the software ecosystem is the main obstacle.
The layers below explain what is being standardized. The instruction-set concept (isa, L3) is the contract between software and hardware, and RISC-V is a clean example of it: a small base ISA plus optional modules. General-purpose CPU design (cpucomp, L1) is what the implementers build on top: pipelines, out-of-order engines, caches, branch predictors. The ISA is free; a high-performance implementation still takes a team of hundreds of engineers and years of work.
terms: Base ISA — the small mandatory core of RISC-V; RV32I (32-bit) has 47 instructions and RV64I is its 64-bit version.
Extension — an optional module that adds instructions, such as M (multiply and divide), A (atomics), F and D (floating point), C (16-bit compressed instructions) and V (vectors).
Profile — a named bundle of extensions that software can rely on; RVA23 is the profile for 64-bit application processors.
Custom extension — instructions that a vendor adds in the opcode space the standard reserves for this purpose.
Open ISA — the specification is free to use; this is different from open-source hardware, where the chip design itself is published.
Privilege modes — Machine (M), Supervisor (S) and User (U) levels that separate firmware, the operating system kernel and applications.
RVWMO — the RISC-V weak memory model: loads and stores can be reordered unless a fence or an acquire/release operation orders them.
SBI (Supervisor Binary Interface) — the standard calls from the kernel to machine-mode firmware such as OpenSBI.
Soft core — a processor described in a hardware language (Verilog, Chisel) that can be put into an FPGA or a chip, often used with RISC-V.
history: Krste Asanovic, David Patterson and their students at Berkeley needed a simple instruction set for teaching and research in 2010. Existing ones were either closed (ARM), too old and complex (x86) or encumbered by licences. They planned a three-month summer project to design a new one, and it became the fifth generation of Berkeley RISC designs, hence "V". They published the specification in 2011. Patterson had co-invented RISC in the 1980s, and the design reflects 30 years of lessons: no features that exist only to help one implementation.
Interest came from industry, which was tired of licence fees and of dependence on one supplier. In 2015 the RISC-V Foundation was formed to own the specification. In 2019 it announced a move to Switzerland, because of concern that US trade rules could limit an organization based in the United States. It was renamed RISC-V International in March 2020. Companies such as SiFive (founded by the Berkeley team), Andes, Western Digital (which used it in storage controllers), Alibaba's T-Head (Xuantie cores), Espressif (ESP32-C series microcontrollers) and Google (the Titan M2 security chip in Pixel phones) started to ship it. In India, the SHAKTI processors from IIT Madras and C-DAC's Vega processors are RISC-V designs.
The standards grew. The vector extension (V 1.0) and the bit-manipulation extensions were ratified in 2021. The big problem was fragmentation: with many optional extensions, a binary built for one chip might not run on another. The answer was profiles. RVA23, ratified on 21 October 2024, makes the vector and hypervisor extensions mandatory for 64-bit application processors, so Linux distributions and applications can assume a rich baseline. Ubuntu required RVA23 from October 2025. Alibaba released the C930 core in March 2025 and the C950 in March 2026. The European Union committed 270 million euros in 2023 for a RISC-V server CPU project. In 2026 RISC-V International also launched a library of ratified specifications.
how: The base ISA is small and regular. RV32I has 32 integer registers, x0 to x31, and x0 is wired to zero: reading it gives 0 and writing it does nothing. This one trick removes the need for separate move, clear and compare-with-zero instructions: "mv x5, x6" is "add x5, x6, x0". Every instruction is 32 bits, with the register fields in the same bit positions in every format, so the decoder can read the registers before it knows what the instruction is. All instructions are one of six formats (R, I, S, B, U, J). The sign bit of every immediate value is always bit 31, so sign-extension can start at once. These are small decisions, taken from the experience of earlier RISC designs (isa, L3), and they make a simple, fast decoder.
The design is a load/store machine with no condition flags. ARM and x86 keep a flags register that arithmetic instructions set implicitly, and branches read it. Flags create hidden dependencies that complicate the out-of-order engine (cpucomp, L1). RISC-V instead has compare-and-branch instructions (BEQ, BNE, BLT, BGE) that compare two registers and branch in one step, and set-less-than instructions (SLT) that write 0 or 1 to a register. It also leaves out some conveniences: no post-increment addressing, no instruction that loads two registers, and no predication. Large constants take two instructions (LUI and ADDI) for 32 bits, or a load from a table for 64 bits. The designers chose to keep the ISA simple and let compilers and hardware (instruction fusion, where a decoder joins two adjacent instructions into one operation) recover the lost efficiency.
Everything else is an extension. M adds multiply and divide. A adds atomic operations (load-reserved and store-conditional, and atomic add, swap and compare operations). F and D add single and double floating point. C adds 16-bit encodings for the most common instructions, which makes code about 25 to 30 percent smaller; the decoder reads a mixed stream of 16-bit and 32-bit instructions, and 32-bit ones can sit on a 2-byte boundary. The combination I, M, A, F, D (plus a few control instructions) is called G, "general purpose", and Linux needs it. The vector extension V is different from x86 SIMD: like ARM's SVE, it is vector-length agnostic. The program asks for a vector length (vsetvli), the hardware answers with how many elements it can process at once (from 128 up to thousands of bits), and the same binary runs on small and large machines.
The opcode space is divided so that vendors can add instructions without breaking the standard. Four major opcodes are reserved for custom instructions. A company building an AI accelerator can add a dot-product instruction and use it from its compiler, without asking anyone. This is the main difference from ARM, where custom instructions are only possible under special licences (and Arm introduced them for some Cortex-M cores only recently). The risk is fragmentation, which profiles try to contain: RVA23 states exactly what a "standard" application core provides, and anything outside it is optional or vendor-specific.
There are three privilege levels, as in cpucomp's description of kernel and user separation: machine mode (the first code that runs after reset, firmware), supervisor mode (the operating system kernel, with virtual memory using page tables, Sv39, Sv48 or Sv57) and user mode. The hypervisor extension (H) adds virtualization. Linux has supported RISC-V since kernel 4.15 (2018), and common toolchains (GCC, LLVM, Go, Rust, OpenJDK) support it. The memory model, RVWMO, is weak, like ARM's: programs need acquire/release or fences for ordering. An optional extension, Ztso, gives x86-like total store ordering for machines that want to run translated x86 code.
The software contract above the instructions is also standard. The calling convention (the ABI) names the registers: a0 to a7 carry arguments and return values, s0 to s11 are saved by the callee, t0 to t6 are temporaries, ra holds the return address and sp is the stack pointer. A function call is JAL (jump and link), which writes the return address into ra, and a return is a jump through ra. Because the ABI is fixed per profile (for example lp64d for 64-bit with hardware double-precision floating point), a library built by one vendor links with code built by another, which is what lets a Linux distribution ship one image for many boards.
It is important to separate the ISA from implementations. The ISA is open. Cores are not necessarily open. Some are open source (Berkeley's Rocket and BOOM, the OpenHW CVA6 and PicoRV32), and many are commercial and closed (SiFive's P-series, Andes, T-Head's Xuantie, Tenstorrent's Ascalon). A designer can pick a ready core, change one, or write one. Open tools such as Chisel and Chipyard, and open processes such as SkyWater 130 nm shuttles, have lowered the barrier for universities and start-ups.

example: Look at the instruction ADD x5, x6, x7, which means x5 = x6 + x7. It is an R-type instruction. The fields are funct7 = 0000000, rs2 = 7 (00111), rs1 = 6 (00110), funct3 = 000, rd = 5 (00101) and opcode = 0110011. Written together: 0000000 00111 00110 000 00101 0110011, which is the hexadecimal word 0x007302B3. The registers are in fixed places, so the hardware can start reading registers x6 and x7 in the register file before it has finished working out the operation. A load, LW x5, 8(x6), uses the I-type format: a 12-bit immediate 8, rs1 = 6, funct3 = 010 (word), rd = 5 and opcode 0000011, which gives 0x00832283.
Now the loop that sums an array of 64-bit integers, with the pointer in a0, the count in a1 and the sum in a2: loop: ld t0, 0(a0); add a2, a2, t0; addi a0, a0, 8; addi a1, a1, -1; bnez a1, loop. That is five instructions, where ARM needs four because it can increment the pointer inside the load. A RISC-V core with instruction fusion can treat some of these pairs as one operation, and the compressed extension can shrink four of them to 2 bytes each (the load stays at 4 bytes because t0 is outside the set of registers that 2-byte loads can use), so the loop uses about 4 + 2 + 2 + 2 + 2 = 12 bytes, which is less than ARM's 16. Neither design is clearly better: ARM has more complex instructions, and RISC-V relies on the compiler and on hardware tricks.
Finally, a business example. A company builds a flash controller that needs a small management core with 100,000 units per month. With ARM, it pays an upfront licence and a royalty per chip, perhaps cents each on a low-cost core. With RISC-V it can use an open-source core for free, or license a commercial one, and can add a custom instruction for its error-correction code that speeds up a hot loop by 3 times. It carries more risk: it needs to verify the core, support its own toolchain changes, and maintain the design. For high volume and a specialized job, this is attractive. For a phone chip that must run Android apps tomorrow, it is not.
intuition: A common language specification that anyone may publish books in: the grammar is public, but each author still has to write their own book.
The idea is natural because the instruction set is only an interface. Everyone who builds software or hardware benefits from it being stable, public and agreed on, much like the Internet protocols or the Linux kernel interface. The value of owning the interface was never in the interface, but in the implementations. By making the contract open, RISC-V moves competition from "who owns the ISA" to "who builds the best core". Because the base is small and the rest is optional, a tiny microcontroller and a big server can share one family and one toolchain.
mistakes: People often think RISC-V is open-source hardware, and that RISC-V chips are free. In fact only the specification is open. Cores can be closed and cost money, and chips still need to be designed, verified and manufactured. You save the ISA licence fee and gain freedom, not the cost of design.
People often think RISC-V is already as fast as ARM and x86. In fact the best commercial RISC-V application cores are still behind the leading ARM and x86 cores in single-thread speed, and the ecosystem (firmware, drivers, vendor support, optimized libraries) is younger. It is catching up quickly in embedded and accelerator use, where it is already common.
People often think custom extensions are always an advantage. In fact every custom instruction is something your compiler, kernel and libraries must support, and code that uses it is not portable. Teams that add many private extensions end up maintaining their own software stack.
People often think RISC-V is fragmented and so cannot work. In fact the early years had real fragmentation, but profiles (RVA20, RVA22, RVA23) define a common baseline, and distributions such as Ubuntu now target RVA23. Fragmentation is a risk managed by standardization, not a fatal problem.
tradeoffs: Choose RISC-V for embedded controllers, accelerators with a management core, and domain-specific chips, when you value no per-chip royalty, the freedom to add instructions, and independence from one vendor or export rules. You give up a mature ecosystem and take on the cost of verifying and supporting the core yourself, unless you buy a commercial one.
Choose ARM when you need a proven high-performance core now, a large software base (Android, server Linux, Windows on ARM), and vendor support, and can accept the licence and royalty. Choose x86 for the existing PC and server software base. For a general-purpose server fleet today, ARM and x86 are the practical choices, and RISC-V is still a small part of the market.
Choose a standard profile (RVA23) rather than a custom mix of extensions when you want to run mainstream Linux software, because binary compatibility depends on it. Choose custom extensions only for a hot loop that justifies the cost of owning the toolchain. Choose a mature commercial core (SiFive, Andes, T-Head, Tenstorrent) over writing your own unless the core is your product, because verification of a core costs as much as the design.
Choose to start with RISC-V in a new market where ARM and x86 are weak or unavailable by policy, for example national processor programs. Choose to wait on RISC-V for server and desktop workloads where the software stack and performance are not yet ready, unless you are ready to invest in porting.
friction: The software ecosystem is the main problem. Most open-source code builds for RISC-V, but optimized libraries (vector kernels for compression, crypto, codecs, linear algebra), JIT compilers, language runtimes and cloud images lag behind ARM and x86. A binary-only vendor product will probably not exist for RISC-V. Hardware choice is also small: few boards have the performance, memory and PCIe of a server, and there are few server-class systems from established vendors.
Performance engineering is an issue. A weaker base ISA (no post-increment, no flags, limited addressing modes) needs more instructions for the same work, which hardware must recover by fusion. High-performance cores are difficult to build, and the leaders in implementation (Apple, Intel, AMD, Arm) spent decades on branch predictors, caches and memory systems that a new entrant must reproduce. The ISA gives no advantage there.
Governance and fragmentation cost something. Standard extensions take years to ratify, vendors ship pre-standard versions (for example the early vector draft 0.7.1 in T-Head chips, which is incompatible with ratified V 1.0), and custom instructions create vendor lock-in. There are also political risks: the ISA is open, but chip making and tools are not, and an open ISA did not stop export rules on advanced chips or manufacturing equipment. Security is another subject: open design is not the same as secure design, and verifying a core against speculative-execution and side-channel flaws is hard.
practice: If you are evaluating RISC-V for a product, decide first whether you need an application core or an embedded core. For embedded, cores from Espressif, Andes, SiFive or open-source projects are mature and tool support is good. For application processors, choose chips and boards that follow RVA22 or RVA23, check that your distribution (Ubuntu, Debian, Fedora, openSUSE) supports your board, and test your own workloads, because the performance of available boards is much lower than that of a server today.
For software teams, add riscv64 to your build matrix as an experiment: cross-compile with GCC or LLVM, run tests under QEMU (slow but enough for correctness), and look for native dependencies that fail. Use portable code, avoid assuming x86 memory ordering, and check that your language runtime has a RISC-V port (OpenJDK, Go, Rust and .NET have varying levels of support). For hardware teams, start with an open-source core and a simulator (Spike, Verilator), use FPGA boards for prototypes, and consider the cost of verification early.
To learn it, read the Patterson and Waterman book "The RISC-V Reader", then the unprivileged and privileged specifications. Write small programs in assembly and run them in Spike or QEMU. Compare the encoding of a few instructions with ARM and x86 (this read and the ARM and x86 reads give examples), and notice which design decisions make decoding simple. If you are in India, look at the SHAKTI and Vega processor programs, which publish open designs and tutorials.
quiz: What does it mean that RISC-V is an open ISA, and what does it not mean? || The specification is free to implement without licence fee or permission, and governed by RISC-V International. It does not mean that the processor designs are open source, free, or fast, since a core still has to be designed, verified and manufactured.
Why is register x0 hardwired to zero? || It removes the need for separate instructions: a move is add with x0, a clear is add x0 to itself, a compare with zero uses x0, and writes to x0 are discarded. This keeps the instruction set small and the decoder simple.
Why does RISC-V avoid condition flags, and what does it use instead? || Flags create hidden dependencies between instructions that complicate out-of-order execution. RISC-V uses compare-and-branch instructions (BEQ, BLT and others) that compare two registers directly, and SLT instructions that write 0 or 1 to a register.
Encode ADD x5, x6, x7. Which fields are used and what is the word? || R-type: funct7 = 0000000, rs2 = 7, rs1 = 6, funct3 = 000, rd = 5, opcode = 0110011, giving 0x007302B3.
A startup wants to build an AI accelerator with a small control core. Do you recommend RISC-V or an ARM core licence? || RISC-V is a good fit: no per-chip royalty, custom instructions for the hot loop, and the control core runs firmware, not a full desktop OS. Use a proven commercial or open core and a standard toolchain, and budget for verification. If the control core must run Android or a rich Linux ecosystem on day one, ARM is safer.
interview: What problem do RISC-V profiles solve? || Optional extensions mean that two RISC-V chips might not run the same binary. A profile such as RVA23 fixes a mandatory set (including vector and hypervisor), so operating systems and applications can target one baseline. It is the main answer to fragmentation, along with compliance testing.
Why did RISC-V succeed first in microcontrollers and hidden cores, not in laptops and servers? || Those markets need small, cheap, customizable cores where royalty and licence terms matter and the software stack is simple, often just firmware. Laptops and servers need top single-thread performance, a mature OS and driver stack, and vendor-supported software, which take years to build.
What are the risks of custom extensions? || Code using them is not portable, the compiler, kernel and libraries need maintenance, and you may have to keep your own toolchain fork. They are worth it for a measurable gain in a hot loop that you control, not for general code.
How does the RISC-V memory model compare to x86 and ARM, and why does it matter for porting? || RVWMO is weak, like ARM: loads and stores can be reordered unless you use fences or acquire/release operations. x86 has stronger ordering, so racy code may work on x86 and fail on RISC-V. Optional Ztso offers x86-like ordering for special cases.
If you were advising a cloud provider, when would you deploy RISC-V servers? || When a RVA23 server-class chip reaches competitive performance per watt and per dollar, the major distributions and runtimes (JVM, Go, Rust, Python wheels) have good riscv64 support, and there is a business reason such as independence from vendors. Until then, run pilots for portable stateless workloads.
Why does an open ISA not remove the cost of building a chip? || The main costs are core design and verification, physical design, mask sets, IP such as memory and PCIe controllers, and software enablement. The ISA licence is only a small part for a large chip, but for small chips and for control over the roadmap the saving matters.

value: AMD Instinct is AMD's line of data-centre accelerators for AI and scientific computing. The MI300 series (December 2023) and its successors, the MI350 series (June 2025) and the MI400 series (2026), are the only large-scale alternative to NVIDIA GPUs in AI training and inference. An Instinct GPU is a package of many chiplets: compute dies that run thousands of parallel threads and matrix units, stacked high-bandwidth memory (HBM) beside them, and a fast link (Infinity Fabric) that joins several GPUs into one machine. The software is ROCm, an open-source stack, and HIP, a programming language that is very close to NVIDIA's CUDA.
Why does it matter? Large AI models are limited by memory, not only by arithmetic. A language model with 70 billion parameters needs 140 GB just for its weights in 16-bit form. An MI300X holds 192 GB of HBM, so it can keep that model and the working memory for its conversations on one GPU. A MI350 series GPU holds 288 GB and the MI455X announced for 2026 holds 432 GB. Memory capacity and bandwidth (5.3 TB/s on MI300X, 8 TB/s on MI350X) are where AMD competes most strongly. The second reason is supply and price: buyers such as Microsoft, Meta, Oracle and OpenAI want a second source so that one vendor does not set both the price and the delivery date.
The layers below explain the machine. GPU computing (gpucomp, L1) is the programming model: thousands of threads run the same program on different data, grouped in blocks. The matrix core idea (tensorcores, L3) gives the GPU its AI speed by multiplying small tiles of numbers in low precision. DRAM and HBM (dram, L3) explain why memory stacked next to the chip gives terabytes per second. Collective communication (hpc, L1) explains how many GPUs add up their gradients (all-reduce) over Infinity Fabric and the network, and why the supercomputers Frontier and El Capitan can use them at scale.
terms: CDNA — AMD's GPU architecture for data centres (CDNA 3 in MI300, CDNA 4 in MI350), separate from the RDNA gaming architecture.
Compute unit (CU) — the basic block of an AMD GPU: SIMD units, a register file, a matrix unit and a small local memory; MI300X has 304 of them.
Wavefront — a group of 64 threads that execute the same instruction together (NVIDIA calls its group of 32 a warp).
Matrix core and MFMA — the units and the instruction (matrix fused multiply-add) that multiply small tiles of low-precision numbers and accumulate the result.
HBM (high-bandwidth memory) — DRAM dies stacked vertically and placed next to the GPU on a silicon interposer, giving a very wide, short bus.
Infinity Fabric — AMD's coherent interconnect, used inside the package between chiplets and outside between GPUs and CPUs.
ROCm — AMD's open-source software platform: drivers, compilers, math libraries and communication libraries for GPUs.
HIP — a C++ GPU language whose syntax mirrors CUDA, so that CUDA code can be converted by a tool (hipify) with small changes.
APU — a chip that puts CPU cores and GPU cores on one package with shared memory; the MI300A is an example.
history: AMD bought the graphics company ATI in 2006. For years its GPUs were mostly for gaming, and its compute software was weaker than NVIDIA's CUDA. AMD introduced the Instinct name in 2016. A key decision came in 2016 and 2017: it started ROCm as an open-source platform, and HIP as a way to move CUDA code. Around 2019 and 2020 AMD split its GPU designs into two families, so that the architecture for data centres (CDNA) could drop graphics hardware and add compute and matrix units. The MI100 (2020) was the first CDNA chip with matrix cores. The MI250X (2021) joined two dies in one package, and powered Frontier at Oak Ridge National Laboratory, the first exascale supercomputer, which topped the TOP500 list in 2022.
The big step was the MI300 series, launched on 6 December 2023, just as demand for AI hardware exploded after ChatGPT. The MI300A is an APU that combines 24 Zen 4 CPU cores, 228 GPU compute units and 128 GB of HBM3 in one package. The MI300X removed the CPU cores for more GPU: 8 compute chiplets, 304 compute units, 192 GB of HBM3 and 5.3 TB/s of bandwidth, in a 750 W package. NVIDIA's H100 had 80 GB at the time, so AMD's memory lead was a main selling point. The MI300A powers El Capitan at Lawrence Livermore National Laboratory, which was number one on the TOP500 list from November 2024 until June 2026, with about 1.7 exaflops of measured performance and a power use near 30 MW.
AMD then moved to a yearly cadence. The MI325X (late 2024) raised memory to 256 GB. The MI350 series (MI350X and MI355X, June 2025, CDNA 4, 3 nm) has 288 GB of HBM3E, 8 TB/s of bandwidth, and new hardware support for the 4-bit and 6-bit floating-point formats (FP4 and FP6) that make inference cheaper. The MI355X draws up to 1,400 W and reaches about 9.2 petaflops in FP4. In October 2025 OpenAI and AMD announced an agreement to deploy 6 gigawatts of AMD GPUs, with the first gigawatt based on the MI450 starting in the second half of 2026. At CES in January 2026 AMD showed Helios, a liquid-cooled rack with 72 MI455X GPUs, 31 TB of HBM4 in total (432 GB per GPU), planned for later in 2026, and the MI430X for scientific computing.
how: Start with one compute unit. A CU has four SIMD units that each run a wavefront of 64 threads in lockstep, a large register file (the registers hold the state of many wavefronts at once, so the CU can switch to another wavefront when one waits for memory), a 64 KB local data share (programmable shared memory) and matrix cores. This is the GPU model from gpucomp: instead of making one thread fast with caches and speculation, the chip runs tens of thousands of threads and hides memory latency by switching between them. A kernel launch creates a grid of blocks, the scheduler places blocks on CUs, and each block's wavefronts run until they finish.
The matrix cores (tensorcores, L3) are what make AI fast. A deep-learning layer is mostly a large matrix multiplication. A matrix core takes small tiles, for example 16 by 16 values from A and from B in 8-bit or 16-bit format, multiplies them and adds the result into a higher-precision accumulator, all in one MFMA instruction issued by a whole wavefront. The array works like a small systolic block: each input is reused many times inside the unit, so the unit does many multiply-adds for every byte read from the register file. This is why the peak rate depends on the precision: the MI300X peaks near 1.3 petaflops dense for FP16 and 2.6 petaflops for FP8, and CDNA 4 doubles again for FP4 and FP6. Lower precision means more operations per cycle and fewer bytes to move, at some cost in numeric accuracy.
Memory is the second pillar, and dram (L3) explains it. A normal DRAM module sits far from the processor on a narrow bus (64 bits per channel), so a CPU gets 50 to 100 GB/s. HBM stacks 8 to 12 DRAM dies vertically, connects them with thousands of tiny vertical wires (through-silicon vias), and puts the stack next to the GPU on a silicon interposer. Each stack has a bus of 1,024 bits or more, and the MI300X uses eight stacks to reach 5.3 TB/s. The price is cost, heat, and a hard limit on capacity: the number of stacks and their height define the memory size. This is where AMD pushed: more stacks and taller stacks than the competition at the time (192 GB against 80 GB), and then 288 GB with HBM3E, and 432 GB with HBM4 for the MI455X. In MI300X there is also a 256 MB Infinity Cache that sits between the compute dies and HBM, to reduce the traffic to HBM.
The package uses chiplets to get a very large system. The MI300X has 8 compute chiplets (XCDs, 5 nm) stacked on 4 I/O base dies (6 nm) that carry the cache, the memory controllers and Infinity Fabric. The HBM stacks are around them. Splitting the work this way lets AMD mix process nodes and improves manufacturing yield, because a defect only ruins a small die, not a monolithic 800 mm² chip. The whole package has about 153 billion transistors. Inside the package, the compute dies and the base dies are joined by very dense vertical connections, and software sees one GPU (or can be configured to see it as several partitions).
Next comes scaling out. Eight MI300X GPUs sit on one board (a platform of the OAM form factor), fully connected by Infinity Fabric: each GPU has seven links to the others, about 900 GB/s of aggregate bandwidth. Between servers, the GPUs use Ethernet or InfiniBand network cards, such as AMD's Pensando Pollara NIC, with the RoCE protocol. The collective communication library RCCL implements all-reduce, all-gather and reduce-scatter, the operations that data-parallel and tensor-parallel training use (hpc, L1). Because an all-reduce of gradients is limited by the slowest link, the topology matters: the fast links inside the box are used first, then the network between boxes. On the supercomputers the interconnect is HPE Slingshot, and El Capitan has more than 11,000 nodes with four MI300A each. The Helios rack extends the idea: 72 GPUs in one scale-up domain in a single rack.
Finally, the software. ROCm provides the compiler (based on LLVM), the runtime, math libraries (rocBLAS, hipBLASLt, MIOpen, composable_kernel) and RCCL. A developer writes HIP, a language that mirrors CUDA (hipMalloc, hipLaunchKernelGGL, __global__), and hipify tools translate CUDA source. Frameworks such as PyTorch, JAX, and serving engines such as vLLM and SGLang have ROCm backends, and the Triton compiler also targets AMD GPUs. Each GPU generation has its own code target (gfx942 for MI300), so binaries or kernels must be built for the right one. The open-source nature of ROCm lets customers fix issues themselves and lets hyperscalers contribute, which is a real difference from CUDA's closed stack.

example: First, will a 70B model fit? Llama-class models with 70 billion parameters use 2 bytes per weight in FP16, so 70 x 10^9 x 2 = 140 GB. An 80 GB GPU cannot hold it, so it needs at least two GPUs and tensor parallelism with communication at each layer. An MI300X with 192 GB holds the weights and leaves 52 GB. The key-value cache of such a model (80 layers, 8 key-value heads, head size 128, 2 bytes) takes 2 x 80 x 8 x 128 x 2 = 327,680 bytes, about 320 KB for each token of context. A conversation of 32,000 tokens uses about 10.5 GB. So the free 52 GB holds about five such long conversations at the same time, or hundreds of short ones. Memory capacity directly limits how many users one GPU can serve.
Second, speed for one stream. To produce one token the GPU must read all 140 GB of weights. At 5.3 TB/s that takes 140 / 5300 = 0.026 seconds, so the best case is about 38 tokens per second for one user. Batching helps because the weights are read once for the whole batch: with 32 conversations in the same step, the same read yields 32 tokens, and the throughput is about 32 times higher until the arithmetic becomes the limit. The compute needed per token is about 2 x 70 x 10^9 = 140 GFLOPs, so at a realistic 500 TFLOPS the limit is about 3,500 tokens per second; at batch 32, the memory-limited rate is 32 x 38, about 1,200 tokens per second, which is still memory-bound. This is the practical reason that bandwidth and capacity decide inference cost.
Third, porting. A team has a CUDA kernel that computes a fused softmax. They run hipify-perl on it. Most calls convert directly: cudaMalloc becomes hipMalloc, the kernel launch syntax becomes hipLaunchKernelGGL. The harder part is performance: the CUDA code assumes a warp of 32 threads, but AMD's CDNA wavefront has 64, so reductions that use warp shuffles need a change, and the tile sizes need tuning for the matrix cores and the 64 KB local memory. The code compiles in a day and takes weeks to match the performance of the CUDA version. Most teams avoid this by using PyTorch and library kernels, and let the ROCm libraries do the tuning.
intuition: A warehouse with a huge floor, many forklifts and a very wide loading dock: it does not need a faster forklift, it needs more floor and a wider dock.
Modern AI work is moving large arrays of numbers through a small number of simple operations. The cost is dominated by moving bytes. So the design puts as much memory as possible right next to the compute, joins it with a very wide bus, and gives the compute units a tiled matrix multiplier that reuses every byte many times. Chiplets are the way to make something this large at an acceptable cost. The open software is a strategic answer to a lock-in: a second supplier is only useful if the software that runs on the first can run on the second.
mistakes: People often think AMD GPUs are simply cheaper copies of NVIDIA. In fact the design differs in important ways: larger memory per GPU, chiplet packaging, a wavefront of 64, an open software stack, and (on MI300A) a CPU and GPU sharing one memory. They win in some workloads and lose in others, so compare on your model.
People often think peak TFLOPS tell you the speed. In fact most real workloads reach 30 to 60 percent of peak at best, and inference is often memory-bound, where bandwidth and capacity matter, not arithmetic peak. Vendor peak numbers also assume sparse or low-precision modes that your model may not use.
People often think that moving from CUDA to ROCm is a recompile. In fact the HIP language is similar, but libraries, kernel performance, debugging tools, and the long tail of research code (custom CUDA kernels, FlashAttention variants, quantization kernels) need work. The gap has narrowed a lot for mainstream models in PyTorch, but not for everything.
People often think the GPU alone sets the cluster speed. In fact at scale, the network and the communication library decide. A training run with thousands of GPUs spends a large share of time in all-reduce and all-to-all, so the topology, the NIC and the software (RCCL, congestion control) are as important as the chip.
tradeoffs: Choose AMD Instinct when memory capacity per GPU is your bottleneck (large models, long context, many concurrent users on inference), when you want a second supplier for price and availability, or when you run mainstream PyTorch and vLLM workloads that are already well supported on ROCm. You give up the largest software ecosystem, and you must test and tune more yourself.
Choose NVIDIA when you need the most mature software (CUDA, cuDNN, TensorRT-LLM, NCCL), the widest framework support, the newest tricks in training libraries on day one, and the NVLink scale-up network up to large domains. You pay a higher price per GPU, longer waiting lists in some periods, and dependence on one vendor. Many large buyers use both: NVIDIA for the most demanding training and AMD for inference where memory matters.
Choose the APU design (MI300A) for scientific codes that move data between CPU and GPU constantly, because the shared HBM removes the copies. Choose the GPU-only design (MI300X, MI350X) for AI, where the CPU has little to do and more GPU area and memory is better. Choose a pre-built rack system (Helios) when you want one supported unit and fast deployment; choose a standard server with 8 GPUs when you want flexibility and know how to operate it.
Choose the lowest precision your model allows (FP8, then FP4 on MI350 series) for inference. You cut memory and bandwidth by 2 to 4 times against FP16, and get higher throughput, but you must validate quality loss on your task. Choose the cloud (Azure, Oracle, specialized GPU clouds) to try AMD before buying, because the main cost of switching is software testing, not hardware.
friction: Software is the main friction. ROCm supports fewer GPU models than CUDA (data-centre Instinct is well supported; consumer cards less so), releases move fast and sometimes break things, and some libraries arrive later than on NVIDIA or are slower. Debugging and profiling tools are improving but are less polished. Expect to pin the ROCm version, the PyTorch build and the driver, and to run your own regression tests. Kernel-level performance for new model architectures usually appears first on NVIDIA.
Hardware has limits. HBM supply is tight and shared with NVIDIA, so allocation from SK hynix, Samsung and Micron, and packaging capacity at TSMC (CoWoS), are constraints. Power is large (750 W to 1,400 W per GPU, and racks of 100 kW or more) and needs liquid cooling in newer systems. The chiplet design adds latency when data moves between dies, and software has to be aware of memory partitions for the best performance. Scale-up networks (NVIDIA's NVLink domains of 72 GPUs) are a strength of the competition; Helios is AMD's answer, but it is new.
There are also market risks. AMD's data-centre GPU revenue depends on a few very large customers. The yearly release rate means that software teams must follow each new architecture. Finally, the claims of the vendor and the real results in the field differ; independent benchmarks (MLPerf, third-party analyses) are the right way to decide. A large share of AI teams still has no AMD experience, so hiring and operations carry a learning cost.
practice: Test on your own model before you decide. Rent or borrow a node, run your real inference or training job with the same framework, and measure tokens per second per dollar and per watt, at realistic batch sizes and context lengths. Include the time to set up and debug in the comparison. Use a recent ROCm release and the prebuilt Docker images from AMD for PyTorch and vLLM, and pin their versions.
For inference, the memory arithmetic is the best predictor: weights in bytes plus the key-value cache for the number of concurrent sequences must fit in HBM, with room for activations. Use FP8 or lower precision when quality allows, use paged attention (vLLM) to avoid wasting cache memory, and batch requests to use bandwidth well. For training, check that your communication pattern fits the topology (tensor parallelism inside the 8-GPU node, data and pipeline parallelism across nodes), and monitor RCCL performance with the rccl-tests benchmark.
Write portable code: use PyTorch operators and Triton kernels instead of hand-written CUDA when you can, so that you can run on both vendors. Where you must write kernels, use HIP and the vendor's composable kernel libraries, and test with different wavefront sizes in mind. Watch GPU metrics (utilization, HBM bandwidth, power, temperature) with rocm-smi or amd-smi. Finally, plan the facility: power per rack, cooling and network are often the longest lead items, more than the chips.

value: CXL (Compute Express Link) is an open standard that runs on the same wires as PCIe, but adds a way for processors, accelerators and memory devices to share memory with cache coherence. With plain PCIe, a device is something the CPU talks to by sending messages: the device has its own memory, and data must be copied back and forth. With CXL, a device can be a memory: the CPU reads and writes it with ordinary load and store instructions, and the hardware keeps every cache consistent. A server can then add memory through a PCIe-style slot, not only through the DIMM slots next to the CPU, and several servers can draw from a shared pool.
The problem it attacks is the "memory wall" of servers. A CPU socket has a fixed number of memory channels (8 to 12 on current servers) and each channel holds one or two DIMMs, so capacity and bandwidth are capped by the pins on the CPU package. Memory is also a very large part of the cost of a server in memory-heavy fleets, and much of it is wasted: one server has spare memory while the next one runs out, but nothing can move it. CXL gives a second path to memory that uses PCIe lanes (16 lanes need far fewer wires than DDR channels with equal bandwidth), and a way to pool and share it.
The layers below explain it. Cache coherence (coherence, L3) is the idea that makes CXL.cache and CXL.mem possible: when many agents cache the same memory, a protocol of the MESI family tracks who has which line and invalidates stale copies. DRAM (dram, L3) is what sits behind a CXL memory controller: ordinary DDR4 or DDR5 chips, with a controller that translates CXL messages into DRAM commands. CXL does not replace DRAM or HBM; it adds a farther tier, slower than local memory and much bigger and more flexible. It is for architects of servers and clouds, and for engineers of in-memory databases, caches and AI inference.
terms: PCIe — the standard serial bus that connects CPUs to devices; CXL uses its physical layer and its lanes (a x16 PCIe 5.0 link carries about 64 GB/s in each direction).
CXL.io — the CXL protocol that is essentially PCIe: discovery, configuration, interrupts and DMA.
CXL.cache — the protocol that lets a device cache the host's memory coherently.
CXL.mem — the protocol that lets the host access device-attached memory with normal loads and stores.
Type 1, 2, 3 device — Type 1 has a cache but no memory (a smart NIC), Type 2 has both (a GPU or FPGA), and Type 3 is memory only (a memory expander).
Memory expander — a Type 3 device that adds DRAM capacity and bandwidth to a host; the main CXL product today.
Pooling and sharing — pooling gives each host its own slice of a device's memory, assigned dynamically; sharing lets several hosts access the same memory region coherently (CXL 3.0).
NUMA node — a region of memory with its own access cost; CXL memory appears to Linux as a NUMA node that has no CPU cores.
Memory tiering — placing hot pages in the fast local DRAM and cold pages in the slower CXL tier, with the operating system moving pages between them.
history: Before CXL, several groups tried to link CPUs, accelerators and memory coherently: IBM's OpenCAPI, the Gen-Z consortium, AMD and others' CCIX, and NVIDIA's NVLink. None became universal. In March 2019, Intel announced CXL together with Alibaba, Cisco, Dell EMC, Facebook, Google, HPE, Huawei and Microsoft. The strength was a simple choice: build on PCIe, which every CPU and device already had, instead of a new physical layer. The specification CXL 1.0 appeared in March 2019 and 1.1 in June 2019.
CXL 2.0 (November 2020) added switching, memory pooling across hosts, and link encryption and integrity. CXL 3.0 (August 2022) moved to PCIe 6.0 speeds (64 GT/s, twice the bandwidth), added multi-level switching, fabrics, peer-to-peer access, and true memory sharing between hosts. CXL 3.1 (November 2023) and 3.2 (December 2024) refined security and memory management. CXL 4.0 (November 2025) doubles the link rate again, from 64 to 128 GT/s, and adds bundled ports and better reliability features.
The industry consolidated around it. The Gen-Z assets were transferred to the CXL Consortium in November 2021 and OpenCAPI in August 2022, so CXL became the single open standard. The first products were memory expanders from Samsung (a 128 GB module announced in 2021, and 512 GB in 2022), SK hynix and Micron, with controller chips from Astera Labs, Montage, Marvell and others. CPUs began to support it: Intel Sapphire Rapids (CXL 1.1, 2023), AMD EPYC Genoa (CXL 1.1 for memory expanders, 2022) and later generations (Xeon 6 and EPYC Turin in 2024 with CXL 2.0 features). Linux added CXL support in the kernel (the drivers matured around version 6.x). Another reason for CXL's rise: Intel's Optane persistent memory, which had been the product between DRAM and SSD, was discontinued in 2022, so CXL memory took over the idea of a big, slower tier.
how: Physically, CXL uses the PCIe lanes and the same connectors (PCIe slots, M.2-like E3.S modules, add-in cards). When a link comes up, the two ends negotiate. If both support CXL, they switch from PCIe protocol to CXL "flex bus" mode, and on that one link three protocols are multiplexed. CXL.io carries the normal PCIe traffic (device discovery, configuration, DMA, interrupts). CXL.cache and CXL.mem are the new parts, carried in fixed-size units called flits (68 bytes in CXL 1.x and 2.0; 256 bytes from CXL 3.0), which allow low latency and error protection.
CXL.mem is the main one for memory expansion. The host CPU sees the device's memory as a range of physical addresses in its address map. When a core issues a load to such an address, it goes through the cache hierarchy as usual. On a miss, the CPU's home agent sends a CXL.mem read request over the link, the controller on the device reads its DRAM (dram, L3), and sends back the 64-byte line. A write is the same in reverse. There is no driver call, no DMA descriptor and no copy: it is an ordinary memory access, just slower. A CXL memory controller adds typically about 200 ns on top of the DRAM access, so a CXL read costs roughly 170 to 300 ns end to end, against about 80 to 120 ns for local DRAM and 140 to 200 ns for the DRAM of a remote socket.
CXL.cache goes the other way. A Type 1 or Type 2 device, for example a smart network card or an accelerator, can hold copies of host memory lines in its own cache, and the coherence protocol (coherence, L3) keeps them consistent with the CPU caches. The device sends requests to the host (read shared, read own, write back), and the host's home agent snoops other caches and sends back invalidations as needed. This is the same idea as MESI between cores, extended across a link. For a Type 2 device with its own memory (a GPU), CXL adds a "bias" mechanism: in device-bias mode the device accesses its memory without asking the host, and in host-bias mode accesses go through the host's coherence machinery. The software or driver flips pages between modes. CXL 3.0 adds back-invalidation, so that a device can tell the host to drop stale cached lines of device memory.
At the system level, Linux treats CXL memory as one or more NUMA nodes without CPUs. The firmware describes it in ACPI tables, and the kernel's CXL drivers configure the regions and interleave sets. Applications can use the memory in three ways. The first is explicit placement (numactl, mbind): a database puts its cold data on the CXL node. The second is interleaving: pages are spread over local and CXL nodes in a set ratio (Linux has weighted interleave policies), which adds the CXL bandwidth to the local bandwidth. The third is automatic tiering: the kernel watches which pages are hot, keeps them in local DRAM and demotes cold pages to CXL, promoting them back when they become hot (the "promotion and demotion" mechanisms in Linux's memory tiering, and research such as Meta's TPP).
Why a serial link can replace wide channels is a matter of pins. A DDR5 channel needs on the order of a hundred signal pins on the CPU package and delivers up to 38.4 GB/s at DDR5-4800. A x16 CXL link uses 64 signal wires (each lane has a transmit pair and a receive pair of wires) and moves 64 GB/s raw in each direction at the same time, so more bandwidth passes through the same package area. The cost is that the data is serialized, encoded and protected with error checks, which adds latency. The link also needs reliability features: CRC on each flit with retry, poison bits that mark a corrupted line so the consumer can be told, and optional encryption and integrity protection of the link (IDE) added in CXL 2.0.
Switching and pooling come from CXL 2.0 and 3.0. A CXL switch connects several hosts to several devices. A fabric manager (software) divides the memory of a device into slices (logical devices) and assigns each slice to a host; with dynamic capacity devices, slices can be added and released while the machines run. Pooling is not sharing: each slice has one owner at a time. Sharing in CXL 3.0 lets several hosts map the same memory and keeps their caches coherent with hardware back-invalidation, which suits shared data structures but is complex and still rare. Because the hosts pay the switch latency (a few tens of nanoseconds per hop) on top of the device latency, pooled memory is slower than directly attached expanders.

example: Take a server with two CPUs, each with 12 DDR5-4800 channels and 1 DIMM per channel. With 64 GB DIMMs it holds 24 x 64 = 1.5 TB. Suppose you need 2.5 TB for an in-memory database. Option one is to use 128 GB DIMMs, which cost far more per gigabyte than 64 GB DIMMs, and often run only at lower speed when two DIMMs share a channel. Option two is to add four CXL memory expanders of 256 GB each (4 x 256 = 1 TB), in E3.S slots of the front panel, each on a x8 or x16 link. Now the machine has 1.5 TB at about 100 ns and 1 TB at about 250 ns.
How much slower is the machine? Suppose 20 percent of the accesses that miss the CPU caches go to the CXL tier, with no tiering, because pages are placed at random. Average latency = 0.8 x 100 + 0.2 x 250 = 130 ns, which is 30 percent worse than all-local memory. With a tiering policy that keeps hot pages in local DRAM, only 5 percent of the misses go to CXL: 0.95 x 100 + 0.05 x 250 = 107.5 ns, only 7.5 percent worse. This shows the real lever: it is not the raw latency of the CXL tier that decides the result, but how well the software places data. A workload with a small hot set and a large cold set (a cache, a database with a skewed key distribution) works well. A workload that scans all its memory randomly (a large random-access graph) does not.
Bandwidth is the second use. One DDR5-4800 channel gives 38.4 GB/s, so 8 channels give about 307 GB/s. A x16 CXL link on PCIe 5.0 carries 64 GB/s in each direction raw, around 50 to 55 GB/s of useful data. Two such expanders add roughly 100 GB/s, a third more bandwidth, using 32 PCIe lanes, which are available on the CPU anyway. For a bandwidth-bound job (scan-heavy analytics, some HPC codes, large-model inference on CPUs), interleaving local and CXL memory in proportion to bandwidth (for example, 3 pages local to 1 page CXL) raises throughput. The caveat is that CXL traffic is read and write mixed on a link whose efficiency changes with the read/write ratio.
Finally, the cost case. Suppose a cloud runs 10,000 servers, and measurements show that each server reserves 25 percent more memory than its virtual machines use on average, because the largest VM must fit. If servers could take memory from a pool, you would need less in each box. A pool shared by 8 to 16 servers needs less spare memory in total, because peaks in different servers do not happen at the same moment. Microsoft's research on this idea (the Pond system) estimated that pooling could cut the DRAM needed by several percent in large fleets. A few percent of memory is a large amount of money at fleet scale, but it must be larger than the cost of the CXL switches, controllers and operational complexity.
intuition: A storage room down the corridor that every office can use: slower than your own desk drawer, much bigger, and shared when one office needs more than its share.
The idea fits the way hardware evolved. The data bus of the CPU is a scarce, expensive resource, and DDR needs many pins for each channel. PCIe lanes are narrow, fast and general, and every device already uses them. If the memory can ride on the same lanes, then memory capacity is no longer limited by the number of DIMM slots. The cost is latency, since the signal passes through a controller and a serial link. The memory hierarchy already has this shape: registers, caches, DRAM, SSD. CXL adds a level between DRAM and SSD, with latency close to DRAM but capacity and sharing like a network.
mistakes: People often think CXL memory is as fast as local DRAM. In fact it adds a controller and a serial link, so load latency is typically 2 to 3 times that of local memory, and the bandwidth per module is bounded by the link width. It is a tier, not a replacement.
People often think CXL is a new kind of memory chip. In fact it is a link protocol. The memory behind it is ordinary DRAM (DDR4 or DDR5) or, in principle, other media. The value is in how the memory is connected, shared and managed.
People often think pooled memory means any server can use any memory at the speed of local memory, and applications will just work. In fact pooling assigns slices to hosts through a fabric manager, access has extra latency through a switch, and the operating system and applications must be tiering-aware. If a pool device fails, every host using it is affected.
People often think CXL replaces PCIe or GPU interconnects. In fact CXL runs on top of the PCIe physical layer and uses PCIe for I/O. GPU-to-GPU traffic in AI clusters uses NVLink, Infinity Fabric or UALink-type networks, which are designed for far higher bandwidth than a PCIe-class link.
tradeoffs: Choose CXL memory expansion when your workload needs more capacity per server than the DIMM slots allow (large in-memory databases, caches, KV stores, big JVM heaps), or when the price per gigabyte of high-capacity DIMMs is steep, and when your data has a hot subset that fits in local DRAM. You give up latency on the cold part, and you must handle tiering. Choose more or larger DIMMs when the workload is latency-sensitive over its whole working set, because local DRAM is simpler and 2 to 3 times faster.
Choose CXL for bandwidth expansion when you are bound by memory bandwidth and have spare PCIe lanes. You get roughly 50 GB/s per x16 link at about the same watt cost as a DIMM channel, but the latency is worse and the gain needs interleaving tuned to the workload. Choose HBM (on-package) when you need terabytes per second, such as AI accelerators; CXL cannot match it.
Choose pooling and switches only when a fleet is large enough that stranded memory is a visible cost, you control the hypervisor or scheduler to use the pool, and you can tolerate a larger failure domain. Choose directly attached expanders (no switch) first, since they are simpler and have lower latency. Choose sharing (CXL 3.x) only for specialist cases such as tightly coupled clusters with shared data structures; the software support and benefits are still early.
Choose to wait if your software cannot tier. An operating system with tiering and an application that is NUMA-aware turn CXL into savings. Without them, you have a slower machine with more memory. Also compare with the alternatives: larger DIMMs (256 GB RDIMMs), MRDIMMs for more bandwidth, more servers with scale-out, or an SSD tier with a cache, which is far cheaper per gigabyte and fits many workloads.
friction: Latency is the first limit. A CXL read costs 2 to 3 times a local one, and measurements of real devices show that it also varies with the load and the read/write mix. Applications with random access to large working sets suffer. Bandwidth per module is limited by the link, and link efficiency is lower for write-heavy traffic. Controllers use power (several watts each) and add heat, and the modules need airflow. Early devices had firmware and compatibility problems, and testing across CPUs, controllers and DRAM vendors takes effort.
Software and operations are the second limit. Tiering policies in Linux work, but they need tuning, and they can move the wrong pages (page migration has its own cost). Libraries, databases and JVMs need NUMA awareness. Reliability, availability and serviceability are new problems: how to handle an uncorrectable error in a pooled module, how to hot-plug, how to isolate failures between hosts, and how to secure shared memory (CXL 2.0 added link encryption, IDE, but tenant isolation in pools is a design task).
Finally, the economics are uncertain. Pooling saves DRAM only if the fleet has enough stranded memory, and the savings must exceed the cost of controllers, switches and the larger blast radius. The generations of the standard move quickly (3.x and 4.0), while products lag by years, and as far as I know most deployed systems in 2026 are still memory expanders attached directly to a host, with pooling and sharing mostly in pilots or research. HBM's growth and the rise of AI accelerators also pull memory budgets toward on-package memory.
practice: If you want to try CXL, begin with one workload and one CXL-capable platform (recent Intel Xeon or AMD EPYC with CXL expanders). Check how the memory appears with lscpu and numactl --hardware (an extra node with memory and no CPUs), and with the cxl command from ndctl's cxl-cli. Measure first: run a memory latency tool (such as Intel MLC) and a bandwidth test to see the latency and bandwidth of the local and CXL nodes on your hardware.
Then decide on placement. Start with the simplest policy: bind latency-critical processes to local memory (numactl --membind), and put caches, buffers and cold data on the CXL node. Next try interleaving for bandwidth-bound jobs, and kernel memory tiering for mixed ones, and compare p99 latency and throughput against a baseline with all-local memory. Watch page migration activity, because too much of it is a sign of a poor policy.
Estimate the value before buying hardware. Collect the memory use of your fleet over weeks: peak versus average, per host. If the average use is far below the peak because of headroom, pooling could help; if hosts are all full, expansion helps capacity. Compare the cost per gigabyte of expansion with that of larger DIMMs, and include power and operations. Follow the specification level of your CPUs, because CXL 1.1 expanders work on most current servers while pooling needs CXL 2.0 or 3.x support in hosts, switches and firmware.
quiz: What are the three CXL protocols and what does each do? || CXL.io carries PCIe-style I/O (discovery, configuration, DMA, interrupts). CXL.cache lets a device cache host memory coherently. CXL.mem lets the host use device-attached memory with ordinary loads and stores.
Why does CXL use the PCIe physical layer? || Every CPU and device already has PCIe lanes and connectors, so CXL can be adopted without a new physical interface. The same lanes can run as PCIe or CXL, negotiated when the link comes up.
How is CXL memory exposed to Linux, and how can applications use it? || As a NUMA node without CPU cores. Applications can bind data to it (numactl, mbind), interleave pages across local and CXL nodes for bandwidth, or let the kernel's tiering move hot and cold pages automatically.
Local DRAM takes 100 ns and CXL memory 250 ns. What is the average latency if 5 percent of the cache misses go to CXL? || 0.95 x 100 + 0.05 x 250 = 107.5 ns, about 7.5 percent worse than all-local.
A team wants to cut memory cost in a 5,000-server fleet by pooling CXL memory. What would you check before agreeing? || Measure stranded memory (peak versus average use), check that CPUs, switches and firmware support CXL 2.0 pooling, estimate the cost of switches and controllers against the DRAM saved, test tiering and latency impact on key workloads, and assess the larger failure domain. Start with directly attached expanders first.
interview: Why does CXL memory have higher latency than DIMMs, and where does the time go? || A load must pass the CXL controller, serialize over PCIe-style lanes, be decoded by the device controller, read DRAM and return across the link. The controller and link add about 100 to 200 ns, which doubles or triples the load-to-use latency. Switches add more per hop.
How does CXL.cache keep a device's cache coherent with the CPU? || The device sends coherence requests (read shared, read exclusive, write back) to the host's home agent, which snoops other caches and returns data or invalidations, as in MESI between cores. CXL 3.0 added back-invalidation so that devices holding host memory can be told to drop lines.
What is the difference between memory pooling and memory sharing? || In pooling, a fabric manager assigns slices of a device to one host at a time, so no coherence between hosts is needed. In sharing (CXL 3.0), several hosts map the same memory and hardware back-invalidation keeps their caches coherent. Sharing is harder and rarer.
When would a bigger DIMM be better than a CXL expander? || When the working set is latency-sensitive and random across all of memory, when the price premium for large DIMMs is acceptable, or when you cannot manage tiering. Local DRAM is 2 to 3 times faster and simpler.
How do you design a tiering policy for a key-value cache on CXL? || Keep the index and hot values in local DRAM and put cold values on the CXL node, using access counts or the kernel's tiering. Measure the hit distribution, set the hot fraction to cover most accesses (for example the top 5 to 10 percent of keys), and watch p99 latency and the rate of page migration.
How does CXL relate to Optane persistent memory? || Optane gave a big, slower byte-addressable tier between DRAM and SSD, but it was proprietary and discontinued in 2022. CXL memory expanders fill the same architectural role with ordinary DRAM behind an open standard, but without persistence unless the module has it.

value: A quantum processor is a physical machine that stores information in qubits and changes it with precisely timed pulses of microwaves or laser light. Where a classical bit is either 0 or 1, a qubit can be in a combination of both, and several qubits can be entangled, which means their states cannot be described one by one. Quantum algorithms use these properties, and an effect called interference, to make wrong answers cancel and right answers add up. For a few problems (breaking RSA with Shor's algorithm, simulating molecules and materials, some search and optimization tasks) this promises large speed-ups over any known classical method.
Today's processors are real but small and noisy. Google's Willow chip (December 2024) has 105 superconducting qubits. IBM's Nighthawk (November 2025) has 120. Quantinuum's Helios (November 2025) has 98 trapped-ion qubits with two-qubit gate fidelity of 99.92 percent. Every operation has an error of roughly 0.1 to 1 percent, and a qubit loses its state in tens to hundreds of microseconds (superconducting) or in seconds (ions). So the central engineering problem is not the number of qubits but the error rate. The main route to a useful machine is quantum error correction: store one logical qubit in many physical qubits, measure errors all the time and fix them before they spread.
Why does this matter to a software engineer in 2026? Not because you can use it for production work: no quantum computer yet does a commercially useful task faster than a classical computer, and nobody knows exactly when one will. It matters for two reasons. First, a large fault-tolerant machine could break the public-key cryptography (RSA, elliptic curves) that protects the Internet, so migration to post-quantum algorithms is already a planning task. Second, the field is an example of hardware where the physics of the layer below, quantum computing (qcomputing, L5), decides every design choice: which materials, which temperature, which error correction code.
terms: Qubit — a two-level quantum system (such as a tiny superconducting circuit or a single ion) whose state is a combination of 0 and 1 with complex amplitudes.
Superposition and entanglement — superposition is a state that is a mix of 0 and 1; entanglement is a joint state of several qubits that cannot be split into separate states.
Gate — a controlled operation on one or two qubits; two-qubit gates (CZ, CNOT) create entanglement and are the noisiest operations.
Fidelity — how close an operation is to the ideal one; a two-qubit fidelity of 99.9 percent means an error rate of about 0.1 percent per gate.
Coherence time (T1, T2) — how long a qubit keeps its state before the environment destroys it; T1 is for energy loss, T2 for loss of phase.
Transmon — the most common superconducting qubit: a Josephson-junction circuit that acts like an artificial atom, operated near 5 GHz at about 10 millikelvin.
Trapped ion — a single charged atom held in place by electric fields, with qubit states in its energy levels, controlled with lasers.
Logical qubit — an error-protected qubit made from many physical qubits using an error-correcting code.
Surface code — a leading error-correcting code that puts qubits on a 2D grid; a code of distance d uses about 2d² − 1 physical qubits per logical qubit.
history: The idea began as theory. In 1981 Richard Feynman said that simulating quantum physics on a classical computer is hard, and suggested using a quantum system to do it. David Deutsch defined a quantum computer in 1985. The field became a serious engineering matter in 1994, when Peter Shor showed that a quantum computer could factor large numbers in polynomial time, which threatens RSA. Lov Grover followed in 1996 with a search algorithm with a square-root speed-up. The same years brought the other half of the story: Shor (1995) and Steane showed that quantum error correction is possible in principle, and the threshold theorem (1990s) showed that if the error per operation is below some threshold, arbitrarily long computations can be made reliable.
Experiments followed theory. Superconducting qubits improved from nanoseconds of coherence in 1999 to hundreds of microseconds today, and the transmon (Yale, 2007) made them much less sensitive to noise. Ion traps came from atomic clock physics and were used for qubits from 1995 (Cirac and Zoller proposed the gate; NIST demonstrated it). In 2019 Google's 53-qubit Sycamore ran a random-circuit sampling task that Google said would take a classical supercomputer thousands of years; classical algorithms later closed much of that gap, which shows how claims of advantage are contested. IBM put cloud access to small machines online in 2016 and built chips of 127 (2021), 433 (2022) and 1,121 (Condor, 2023) qubits. Then the focus moved from counting qubits to making them better.
The milestone of the last two years is error correction below threshold. In December 2024 Google reported with Willow that going from a code of distance 3 to 5 to 7 reduced the logical error each time by a factor of about 2, reaching a logical error of about 0.14 percent per cycle at distance 7 (a cycle takes about 1.1 microseconds): the more qubits are used, the fewer errors. This had been predicted for 30 years and not shown before. In 2025 IBM announced the Nighthawk processor and an experimental chip, Loon, with the parts needed for a more efficient code, and a roadmap to a fault-tolerant machine called Starling by 2029, with 200 logical qubits and 100 million operations. Quantinuum launched Helios (98 barium ions, 99.921 percent two-qubit fidelity) in November 2025 with demonstrations of dozens of error-detected and error-corrected logical qubits. Neutral-atom machines (QuEra, Atom Computing, Pasqal) and photonic designs (PsiQuantum, Xanadu) are also in development, and Microsoft announced a "topological" chip, Majorana 1, in February 2025, a claim that the community still debates.
how: Take the superconducting qubit first. A transmon is a small loop of aluminium with one or two Josephson junctions (two superconductors separated by a thin insulating layer) on a silicon or sapphire chip. A Josephson junction acts like a nonlinear inductor, so the circuit has energy levels that are not evenly spaced. This lets a microwave pulse at one exact frequency (about 4 to 8 GHz) move the state between level 0 and level 1 without exciting level 2. The chip sits in a dilution refrigerator at about 10 to 20 millikelvin, colder than outer space, so that thermal noise does not excite the qubits and the aluminium stays superconducting. The principle comes from the physics of quantum computing (qcomputing, L5): the qubit is an isolated two-level system whose state can be in a superposition and can be entangled.
To run a program, control electronics at room temperature create microwave pulses, shaped to tens of nanoseconds, and send them down coaxial cables into the fridge. A single-qubit gate is a pulse of about 20 to 50 ns that rotates the state around an axis. A two-qubit gate (such as CZ) is made by tuning two neighbouring qubits, or a coupler between them, so that their states interact for about 30 to 60 ns. To read the result, a resonator coupled to the qubit shifts its frequency depending on the qubit state; a probe pulse reflected from it is amplified and digitized, and the qubit collapses to a classical 0 or 1. Reading out takes hundreds of nanoseconds to about a microsecond.
Trapped-ion machines work differently. Ions of ytterbium or barium are held in a radio-frequency trap in vacuum, in a line or in a 2D layout. Two internal energy states of each ion are the qubit. Laser or microwave pulses rotate single qubits, and two-qubit gates use the shared motion of the ions in the trap: a laser couples the internal state to the motion, so that two ions become entangled. Ions are identical atoms and have very long coherence (seconds), the gate fidelity is the best of any platform (above 99.9 percent), and any ion can be connected to any other, but gates take tens to hundreds of microseconds, a thousand times slower than superconducting gates, and scaling to thousands of ions needs ion shuttling between trap zones.
Errors are the center of the engineering. A physical error rate of 0.1 to 1 percent means that after about 1,000 operations a computation is likely to be wrong, while useful algorithms need billions. Quantum error correction fixes this without copying the state (copying is forbidden by physics). In the surface code, data qubits and measurement qubits are placed in a checkerboard on a 2D grid. Every cycle (about 1 microsecond on Willow) each measurement qubit checks the parity of its four neighbours, without learning the data. The pattern of parity flips, called the syndrome, tells a classical decoder where errors probably occurred; the decoder runs in real time on fast classical hardware and gives corrections. A code of distance d corrects any error pattern of fewer than d/2 qubit errors, uses 2d² − 1 physical qubits per logical qubit, and if the physical error rate p is below the threshold (about 1 percent for the surface code), the logical error falls exponentially as d grows: roughly by a constant factor Λ for each increase of d by 2. Willow measured Λ of about 2.1.
Before any of this, the machine must be calibrated. Each qubit has its own frequency, and each pulse shape and amplitude must be tuned so that the gate is accurate. Two-level defects in the materials drift in and out of resonance, so calibration runs again every few hours on most cloud devices, and the quoted error rates change from day to day. A compiler (Qiskit's transpiler, Cirq) rewrites a program into the native gates of the chip, chooses which physical qubit holds each program qubit, and adds SWAP operations when two qubits that must interact are not neighbours. On a chip with limited connectivity, these extra gates can double the number of two-qubit operations, which is why connectivity (ions: all-to-all; transmons: a grid) changes the effective error of a program.
Logical operations then work on the encoded qubits. In the surface code, a logical two-qubit gate is done by merging and splitting patches of the grid ("lattice surgery"), which takes about d cycles. Non-Clifford gates, needed for general algorithms, need special resource states called magic states, prepared by "distillation" or "cultivation" in separate parts of the chip, which are a major share of the cost. The overall architecture is therefore a cryostat with a chip, thousands of control lines, fast control electronics, a real-time decoder, and a compiler that turns an algorithm into logical operations.

example: Use Willow's numbers to see why the road to a useful machine is long. In the Google experiment, the logical error per cycle fell from about 0.3 percent at distance 5 to 0.14 percent at distance 7, a factor Λ of about 2.1 per step of 2 in distance. A distance-7 patch needs 2 x 49 − 1 = 97 physical qubits (Google's experiment used 101, with a few extra qubits, on a 105-qubit chip). Suppose we want a logical error of 10^-6 per cycle, which is the order that long algorithms need. From 1.4 x 10^-3 we need to reduce by a factor of about 1,400. The number of steps is ln(1400) / ln(2.1), which is 7.24 / 0.74, about 9.8 steps of 2. So the distance must grow by about 20, from 7 to about 27 (the distance is odd). A distance-27 patch uses 2 x 27² − 1 = 1,457 physical qubits. So one logical qubit of that quality costs about 1,500 physical qubits at today's physical quality.
A machine with 1,000 such logical qubits would need about 1.5 million physical qubits, plus the space for magic-state factories and routing. This is why you read "millions of qubits" for breaking RSA-2048. The best published resource estimate (Gidney, 2025) is under one million noisy physical qubits and about a week of running time, for physical error rates around 0.1 percent; earlier work (Gidney and Ekerå, 2019) estimated 20 million qubits and 8 hours. Better codes and better qubits cut this number; a roughly 10 times lower physical error rate would reduce the distance needed and the qubit count by a large factor.
Time is the second cost. One surface-code cycle is about 1 microsecond, and a logical operation by lattice surgery takes about d cycles, so at d = 27 it is about 30 microseconds. An algorithm of 10^9 sequential logical operations then takes 10^9 x 30 µs = 30,000 seconds, about 8 hours. Compare this with a classical computer that does 10^9 simple operations per second per core. The quantum machine is a million times slower per operation and wins only when the algorithm needs exponentially fewer operations. That is why only specific problems are candidates for advantage, and why speed-ups of a modest polynomial kind (such as Grover's square root) are unlikely to pay off after error-correction overhead.
intuition: A very sensitive instrument that must be shielded from the world to keep its memory, plus a team of inspectors who check every second whether anything has changed and quietly fix it.
Quantum information is fragile because any contact with the environment, even a stray photon, measures it. The way out is not to get a perfect qubit, which physics forbids, but to build a reliable system from unreliable parts, as the Internet does with unreliable packets, and as disk arrays do with unreliable disks. Redundancy plus continuous checking turns many noisy physical qubits into one good logical qubit. The new idea in quantum error correction is that you can check parities without reading the data, so the checks do not destroy what they protect.
mistakes: People often think a quantum computer tries all answers at once and picks the best. In fact superposition only gives a state with many components. Measurement returns one random result. Useful algorithms arrange the amplitudes so that wrong answers cancel by interference and the right answer is likely. This works only for problems with the right structure.
People often think more qubits means a better quantum computer. In fact the quality of qubits and gates matters more. Hundreds of noisy qubits can do less than a few dozen good ones, because errors pile up. The right measures are two-qubit error rates, connectivity, speed, and the logical error rate achieved by error correction.
People often think quantum computers will soon replace classical ones, or speed up databases and machine learning in general. In fact they are expected to help for a narrow set of problems, and the data loading and error-correction cost removes advantage for most data-processing tasks. They are accelerators for specific problems, not general replacements.
People often think encryption is already broken by quantum computers. In fact no machine today can run Shor's algorithm on cryptographic key sizes; it would need on the order of a million good physical qubits. But data encrypted now and stored by an attacker could be decrypted later ("harvest now, decrypt later"), so migrating to post-quantum cryptography is a present-day task.
tradeoffs: Choose superconducting qubits when you want fast gates (tens of nanoseconds), mature chip fabrication, and fast error-correction cycles (about 1 microsecond), and accept lower coherence, a dilution refrigerator and nearest-neighbour connectivity on a 2D grid. Choose trapped ions when you value the highest gate fidelity (above 99.9 percent), long coherence and all-to-all connections, and accept gates 100 to 1,000 times slower and harder scaling to thousands of qubits. Neutral atoms offer large arrays (hundreds to thousands of atoms) and flexible connectivity with slower cycles and atom loss to manage; photonic approaches work at room temperature for parts of the system but need huge numbers of components.
Choose to spend on error correction when the target is a useful algorithm (billions of operations), because without it no hardware can run it. Choose noisy intermediate-scale experiments (error mitigation, short circuits) when you want to explore physics or test methods on today's machines, knowing that they have not produced clear commercial advantage. Choose better qubits over more qubits when your error rate is above or close to the threshold, because the overhead falls steeply with each reduction of the physical error rate.
Choose a code by the hardware: the surface code needs only nearest-neighbour connections on a 2D grid and tolerates about 1 percent error, but needs many qubits per logical qubit. Newer qLDPC codes (IBM's plan) need far fewer physical qubits (IBM estimates a reduction of about 90 percent) but need long-range connections that are hard to build. Ions and neutral atoms can host codes with higher efficiency because of flexible connectivity.
For a company, choose cloud access (IBM Quantum, Amazon Braket, Azure Quantum, Google) for learning and for small experiments, and do not buy hardware. Choose to start the migration to post-quantum cryptography now, not when a large machine appears, because migration takes years.
friction: Noise is the first limit. The best two-qubit gate errors are around 0.1 percent for superconducting devices and 0.01 to 0.1 percent for ions, and the surface code needs roughly 1,000 physical qubits per logical qubit at those levels for long algorithms. No machine has yet shown many logical qubits running long computations with logical error low enough. Some systems show dozens of logical qubits with limited error detection or short circuits, which is progress, not the finish line.
Scaling is the second limit. A superconducting chip needs several cables to each qubit, each carrying heat into the cryostat, and the fridge has limited cooling power at 10 millikelvin. Moving to millions of qubits needs new wiring (flex lines, cryogenic control chips), modular chips linked by quantum interconnects, and fridges much bigger than today's. Fabrication variation means each qubit differs slightly, and defects (two-level systems in materials) and cosmic rays cause correlated errors that break the assumption of independent noise. The classical side is also hard: a decoder must process millions of syndrome bits per cycle within a microsecond or so.
The third limit is knowing what the machines are good for. Claims of "quantum advantage" have been challenged by improved classical algorithms several times, and Google's and IBM's recent claims of verifiable advantage on specific tasks are still under study. A commercially useful application (chemistry, materials, optimization) has not been demonstrated, and good classical methods keep improving. Timelines are uncertain: IBM targets fault tolerance by 2029, others say the early 2030s, skeptics say longer. There are not many people who know the full stack, and costs for a single machine are in the tens to hundreds of millions of dollars.
practice: For a software engineer, the practical steps are small. Learn the basics with a free toolkit: Qiskit (IBM) or Cirq (Google) let you write circuits, simulate up to about 30 qubits on a laptop, and run them on cloud hardware. Run a Bell-state circuit and see noise on a real device: you will see about 1 to 5 percent wrong outcomes, which makes the error rate real. Read hardware pages (IBM, Google, Quantinuum) for the quoted two-qubit error rates and coherence, and learn to compare them with the 1 percent surface-code threshold.
Prepare for the cryptographic consequence. NIST published its first post-quantum standards in August 2024 (ML-KEM for key exchange, ML-DSA and SLH-DSA for signatures) and has draft guidance to deprecate RSA and elliptic-curve algorithms around 2030 and disallow them around 2035. Make an inventory of where your systems use public-key cryptography (TLS, VPNs, code signing, certificates, long-lived encrypted data), prioritize data that must stay secret for 10 years or more, and use hybrid key exchange (classical plus ML-KEM) where your libraries support it. Many TLS stacks and browsers already offer it.
For evaluating claims, ask five questions: How many physical qubits, and what two-qubit error rate? Was error correction used, and did the logical error improve with size? What task was run, and what is the best classical method for it? Is the result verifiable? And what would it take to scale it? For learning, read Nielsen and Chuang and the Preskill lecture notes, and for error correction, the Google Willow paper and Gidney's blog posts on the surface code and resource estimates.

@@ zookeeper
value: Apache ZooKeeper is a small, replicated, strongly consistent store for the coordination data of a distributed system: who is the leader, which servers are alive, where is the configuration, who holds the lock. It was built at Yahoo! and became a project of the Apache Software Foundation. It keeps a tree of small records called znodes, in memory, on an ensemble of three or five servers. Clients connect to any server, read and write znodes, and ask to be notified when a znode changes.
The problem it solves is that every distributed system needs a few things to be exactly right, and getting them right is very hard. If two nodes both believe they are the leader, data is corrupted. If a failed server is not detected, requests go to a dead machine. Each team that wrote its own leader election found subtle bugs in the face of network partitions and crashes. ZooKeeper turns this into a service with a small API and a clear guarantee: all clients see the updates in the same order, and an update that succeeded is not lost while a majority of servers is alive. Hadoop HDFS and YARN high availability, HBase, Kafka (until version 4.0), Solr, Pinot through Helix, and many in-house systems used it for this.
The layers below make it work. The coordination-service concept (coordination, L1) is the pattern: a small consensus cluster that holds metadata for large clusters of workers, so the workers do not need to run consensus themselves. ZooKeeper implements that pattern with its own protocol, ZAB (ZooKeeper Atomic Broadcast), which is a leader-based protocol in the same family as Paxos and Raft. The JVM (jvm, L0) is the platform: ZooKeeper is written in Java, so its heap size, garbage-collection pauses and thread behavior are part of the reliability of the cluster.
terms: Znode — a node in ZooKeeper's tree; it holds a small amount of data (usually bytes to kilobytes, at most 1 MB by default), a list of children, and version numbers.
Ensemble — the set of ZooKeeper servers that replicate the data (usually 3 or 5); the service works while a majority is alive.
ZAB — ZooKeeper Atomic Broadcast: the protocol that elects a leader and delivers every write to all servers in the same order.
zxid — a 64-bit transaction id that orders every write; the high 32 bits are the leader's epoch and the low 32 bits are a counter.
Session — a client's connection state with a timeout; if the server hears nothing from the client for that time, the session expires.
Ephemeral znode — a znode that exists only while its creator's session is alive and is deleted when the session ends.
Sequential znode — a znode whose name gets a growing counter appended by the server, which gives a global order to concurrent creators.
Watch — a request to be notified once when a znode's data or children change.
Quorum — a majority of the ensemble (2 of 3, 3 of 5); a write is committed when a quorum has logged it.
history: Large web companies in the mid-2000s were building systems that spanned thousands of machines, and each system needed coordination. Google had published Chubby (Burrows, OSDI 2006), a lock service that Bigtable and GFS depended on. At Yahoo!, Benjamin Reed, Flavio Junqueira and colleagues built a similar service for their own systems, such as the Yahoo! Message Broker and crawling. They made two design choices that differ from Chubby. First, instead of offering locks as a built-in feature, they offered a wait-free API for small data nodes, and let users build locks, queues and barriers as "recipes". Second, they allowed reads to be served by any server for speed, and kept writes ordered through a leader.
ZooKeeper started as a sub-project of Hadoop around 2008 and became its own top-level Apache project in 2010. The paper "ZooKeeper: Wait-free coordination for Internet-scale systems" (Hunt, Konar, Junqueira and Reed) was presented at USENIX ATC 2010, and the paper on its protocol, "Zab: High-performance broadcast for primary-backup systems" (Junqueira, Reed and Serafini), at DSN 2011. The timing was right. Hadoop, HBase, Kafka (2011), Storm, Solr Cloud and Mesos needed such a service, and ZooKeeper was the one they used. The Apache Curator library (from Netflix) made the recipes easy to use from Java.
Since then the role has shrunk in some places. Newer systems embed Raft: etcd (2013) for Kubernetes, Consul for service discovery, and Kafka's own KRaft quorum. Kafka made KRaft production-ready in 3.3 (2022), deprecated ZooKeeper mode in 3.5 and removed ZooKeeper completely in Kafka 4.0 (March 2025). The reason was operational: running two clusters, two security models and two sets of monitoring was a burden, and storing all partition metadata in ZooKeeper limited how many partitions a cluster could have and slowed controller failover. ZooKeeper itself is still maintained (the 3.9 line was current in 2025, with releases such as 3.9.4 in August 2025) and still runs under HBase, Hadoop HA, Solr, and many older platforms.
how: The data model is a tree of znodes with paths like /app/config or /election/n-0000000007. Each server holds the whole tree in memory, so reads are fast and the size is bounded by memory (znode data is small by design, with a default limit of 1 MB per znode and a typical size of well under 1 KB). Every znode has a version, creation and modification transaction ids (czxid, mzxid) and a type. Persistent znodes stay until deleted. Ephemeral znodes are tied to a session and disappear when it ends, which is how ZooKeeper detects failure. Sequential znodes get a counter appended to their name (n-0000000001, n-0000000002), which gives an order to competing clients.
Writes go through ZAB. A client sends a write to the server it is connected to. If that server is a follower, it forwards the request to the leader. The leader turns the request into a transaction with a new zxid, writes it to its log, and broadcasts a proposal to all followers. Each follower appends the proposal to its transaction log on disk and replies with an acknowledgement. When the leader has acknowledgements from a quorum (itself included), it sends a commit, and every server applies the transaction to its in-memory tree in zxid order. The message channels are FIFO (TCP), so each follower sees proposals in order. Only after the commit does the client get its reply. This is the same family as Paxos and Raft (coordination, L1): a majority must persist the change, so any later majority overlaps with it and knows about it.
Leader election and recovery are the other part of ZAB. If the leader fails, the followers run a fast leader election that picks the server with the most recent history (the highest zxid, ties broken by server id). The new leader increments the epoch (the high half of the zxid), then synchronizes the followers: it sends them the transactions they miss or tells them to truncate transactions that were never committed. Only after a quorum is in sync does the broadcast phase start again. The epoch number makes the stale leader's later messages recognizable and ignorable, which prevents two leaders from both committing writes.
Reads are served locally by whichever server the client is connected to, with no coordination. This is why read throughput grows when you add servers (and why the recommended read to write ratio is about 10 to 1). The price is that a read can be slightly stale: the server may be a few transactions behind the leader. ZooKeeper's guarantees are sequential consistency (a client's operations are applied in the order sent, and a client never sees an older state after a newer one, even across a reconnect to another server), atomicity, a single system image and timeliness within a bounded time. When a client needs the very latest value, it calls sync before reading, which makes the server catch up with the leader.
Sessions and watches provide the coordination features. A client opens a session with a timeout (for example 6 seconds) and sends heartbeats. If the ensemble hears nothing for the full timeout, the session expires and its ephemeral znodes are deleted. A watch is a one-time notification: the client reads a znode (or its children) and sets a watch, and the server sends one event when it changes (version 3.6 and later also offers persistent, recursive watches). Combining ephemeral znodes, sequential znodes and watches gives all the recipes. For durability each server writes transactions to a log and periodically takes snapshots of the tree; the log must be forced to disk before acknowledgement, so the disk latency of the log device is the main cost of a write.
The JVM (jvm, L0) shapes operation. The server is a Java process with a heap of a few gigabytes to hold the tree. A garbage-collection pause that is longer than the session timeout makes the server or its clients look dead, which can cause leader elections or mass session expirations. A client application that runs on the JVM and holds a lock has the same problem: a long pause can make it think it still owns a lock that ZooKeeper has already given to someone else. That is why careful designs use fencing tokens, and why ZooKeeper servers are given dedicated machines, a fixed heap, a fast log disk and no swapping.

example: Lock with ephemeral sequential znodes, step by step. Three clients A, B and C want the lock at /lock. Each calls create("/lock/n-", ephemeral+sequential). The server assigns names: A gets /lock/n-0000000001, B gets n-0000000002 and C gets n-0000000003. Each client lists the children of /lock. The client whose name is the lowest owns the lock, so A proceeds. B sees that its predecessor is n-0000000001, and sets a watch on that znode only; C sets a watch on n-0000000002. They do not watch the parent, because then every release would wake every waiter (the herd effect). Now A crashes. After its session timeout, say 6 seconds, the ensemble deletes its ephemeral znode, and B's watch fires. B lists the children again, finds itself the lowest, and takes the lock. C keeps waiting. When B releases it by deleting its znode, C is notified.
There is one more detail. Suppose A did not crash but paused for 10 seconds because of a long garbage collection. Its session expired, B took the lock, and then A woke up still believing it has the lock. Both write to the same storage. To prevent corruption the lock must give a fencing token: for example the sequence number 1, 2, 3 or the zxid of the lock znode. The storage service remembers the highest token it has seen and rejects a write with an older token. A's write has token 1, B's has 2, so A's late write is rejected. A lock service alone cannot make a lock safe, because it cannot stop a paused process.
Now the numbers for write cost. A 3-server ensemble in one data centre with SSD log disks has a log sync of about 0.5 to 1 ms and a network round trip of about 0.3 ms. A write needs the leader's disk sync, one round trip to the followers, and their disk syncs in parallel, so a single write takes about 1.5 to 3 ms. Because the leader batches proposals, throughput can reach tens of thousands of writes per second, but a single client doing synchronous writes gets only 300 to 600 per second. On a spinning disk with a 10 ms sync, one write takes more than 10 ms and the cluster does about 100 writes per second without batching. A 5-server ensemble tolerates two failures instead of one, but each write needs 3 acknowledgements instead of 2, and is a little slower. In practice, 3 servers suit most clusters and 5 suit those that need to survive one planned maintenance with one more failure.
intuition: A small, very careful notary office whose records everyone in the building can read quickly, and where every change must be signed by most of the notaries before it counts.
The design works because it separates two jobs. The hard job, agreeing on order despite failures, is done by a few servers with a protocol that is expensive but correct. The large number of workers do not take part in the agreement: they just read from the notary and ask to be told when something changes. Ephemeral nodes turn "this process died" into "this record vanished", which is a fact that can be observed by everyone in the same order. Locks, leaders and group membership then become small tricks with these records.
mistakes: People often think ZooKeeper is a database for application data. In fact it is built for small, rarely changing coordination data. Znodes are limited to about 1 MB, everything is kept in memory, and every write goes through one leader and a disk sync. Putting large or high-rate data into it slows the whole ensemble.
People often think a ZooKeeper read always returns the latest value. In fact a read is served by the local server, which may lag behind the leader. ZooKeeper gives sequential consistency for reads, not linearizability. Call sync first when you need the latest value, or check versions with a conditional update.
People often think that holding a ZooKeeper lock means you are safe to act. In fact between the moment you were granted the lock and the moment you act, your process may have paused and the lock may have expired. Use fencing tokens (zxid or sequence number) at the resource, and handle the session-expired event by stopping work.
People often think more servers make it faster and more reliable. In fact adding voting servers makes writes slower (more acknowledgements), and gains only more fault tolerance. For more read capacity, add non-voting observers. Use an odd number: 4 servers tolerate only 1 failure, the same as 3.
tradeoffs: Choose ZooKeeper when you already run a system that depends on it (HBase, Hadoop HA, Solr, older Kafka, Pinot/Helix), or when you need its mature recipes and Java client ecosystem (Curator). You accept an extra cluster to operate, with its own JVM tuning, disks and monitoring. Choose etcd for new Kubernetes-style systems, since it has a gRPC API, a simpler key space with revisions and leases, and a Raft implementation embedded in many Go projects. Choose Consul when you also need service discovery and health checks with a DNS interface.
Choose an embedded quorum (Kafka's KRaft, ClickHouse Keeper, CockroachDB's own Raft groups) when you build a product and do not want users to run a separate coordination cluster. You give up the generality of a shared service, and you take on the work of writing and testing consensus code, or using a library. Choose a managed offering (a cloud provider's metadata service) when you cannot afford the operational risk, accepting vendor lock-in and different semantics.
Choose 3 servers for most clusters and 5 when you need to tolerate a failure during maintenance or have a large number of clients. Place servers in different failure domains (racks or zones) only when the network between them has low and stable latency, because write latency includes the inter-server round trip. Choose observers (non-voting servers) in remote data centres for reads, so that voting servers stay close together.
Choose short session timeouts (2 to 6 seconds) for fast failure detection and accept more false positives when GC pauses or network blips occur. Choose longer ones (20 to 40 seconds) when stability matters more than fast failover. This is the main tuning decision for any system built on ephemeral nodes.
friction: ZooKeeper is easy to misuse and hard to run at scale. Because the whole tree is in memory and every client has a session, the number of znodes, watches and connections must stay within what the servers can handle. Large numbers of watches or children lists (listing a znode with a million children produces a huge response) cause latency spikes. A thundering herd, when many clients watch the same znode, can overload the server. Snapshots and log replay at restart take longer as the data grows, and the transaction log must be cleaned (autopurge).
Failures often come from the environment. Slow disks or a log device shared with other loads cause fsync stalls, which show up as client timeouts. JVM garbage collection pauses, swapping, or noisy neighbours in a cloud instance cause session expirations and leader re-elections, and these can cascade: when sessions expire, clients reconnect and re-create ephemeral nodes, adding load at the worst moment. Network partitions that cut off the leader trigger an election. Misconfiguration of the ensemble (different server lists, wrong myid) is a common operational error, and dynamic reconfiguration (3.5 and later) is powerful but less used.
The deeper limit is architectural. The whole data set sits on every server, writes pass through one leader, and there is no sharding, so ZooKeeper does not scale to large amounts of data or to high write rates. Systems that put per-partition or per-file metadata into it (as Kafka did) hit limits at hundreds of thousands of partitions, which was a reason for KRaft. Security needs care: authentication (SASL, Kerberos), ACLs per znode, and TLS between servers and clients must be set up, and many old clusters run with open access.
practice: Run an odd number of servers (3 or 5) on dedicated machines or instances, with the transaction log (dataLogDir) on its own fast SSD, a fixed JVM heap of 1 to 4 GB (no swapping, a modern collector such as G1 with pause goals), and automatic purging of old snapshots and logs (autopurge.snapRetainCount and purgeInterval). Monitor outstanding requests, average and maximum latency, the number of connections and watches, the number of znodes, fsync times (fsync warnings in the log), and leader elections. Use the four-letter words or the AdminServer and the Prometheus metrics provider (3.6 and later).
Design clients carefully. Use Curator recipes instead of writing your own, keep znodes small, avoid listing huge directories, watch only what you need, and do not use ZooKeeper as a queue for high-rate work. Handle session events: on a "disconnected" event you may still hold your lock, but on "expired" you have lost it and must stop acting. Use a session timeout that is longer than your normal GC pauses and network blips, and test failures on purpose (kill the leader, pause a follower, partition the network) to see what your applications do.
If you run Kafka, plan the move from ZooKeeper to KRaft: Kafka 4.0 does not run in ZooKeeper mode, so you must migrate (through version 3.9, which supports a managed migration) before upgrading. Prefer dedicated controller nodes for larger clusters. For new systems that need only leader election and metadata, consider etcd, Consul or an embedded Raft library rather than adding ZooKeeper to your stack.
quiz: What is an ephemeral znode and why is it important? || It is a znode that exists only while its creator's session is alive and is deleted when the session ends. It turns the failure of a process into an observable change in the tree, which is the basis for failure detection, group membership and leader election.
How does ZAB commit a write? || The leader assigns a zxid, logs the transaction and sends a proposal to the followers. Each follower logs it to disk and acknowledges. When a quorum (majority) has acknowledged, the leader sends a commit and all servers apply the transaction in zxid order. Then the client gets its reply.
Why can a ZooKeeper read be stale, and how do you get a fresh value? || Reads are served by the local server without contacting the leader, so the server may be a few transactions behind. Call sync before the read, which makes the server catch up with the leader, or use versions in conditional writes.
In the lock recipe, why does each waiter watch only its predecessor? || If all waiters watched the lock directory, every release would wake all of them (the herd effect) and each would list the children again. Watching only the predecessor means one wake-up per release.
Your team runs a 5-node ZooKeeper ensemble and sees many leader elections after a cloud migration. What do you check first? || Log disk latency (fsync times), JVM garbage-collection pauses, swapping, noisy neighbours and network latency between the nodes, because any of them makes heartbeats time out. Then check session timeouts, tickTime and whether the nodes share failure domains with high latency.
interview: Why does ZooKeeper offer a wait-free API and not locks directly? || A blocking lock service ties server state to waiting clients and slows the service for all. A wait-free API of small data nodes with versions, watches and ephemeral/sequential nodes lets clients build locks, queues and barriers as they need, and keeps the server simple and fast.
What consistency does ZooKeeper provide and how is it different from linearizability? || Writes are linearizable through the leader, and a client's operations are applied in order. Reads are served locally and are sequentially consistent, not linearizable, so a client may read an old value after another client's write completes, unless it calls sync. The trade is high read throughput.
Why did Kafka remove ZooKeeper? || Operating two systems was a burden, and keeping all partition metadata in ZooKeeper limited the number of partitions and made controller failover slow because the new controller had to load the metadata. KRaft stores metadata in Kafka's own Raft log, which scales better and simplifies operations.
How do you make a distributed lock safe against a paused process? || Add a fencing token, a number that grows with each lock grant (the sequence number or zxid). The protected resource records the highest token and rejects requests with lower ones. The lock service alone cannot stop a paused client from acting.
What happens during a ZooKeeper leader failure, step by step? || Followers notice the lost leader, run a leader election that prefers the server with the highest zxid, the new leader starts a new epoch, synchronizes followers (sending missing transactions or truncating uncommitted ones), and after a quorum is in sync it starts broadcasting again. Clients reconnect and sessions survive if their timeouts have not passed.
How would you size and place a ZooKeeper ensemble for a 500-broker Kafka or a large HBase cluster? || Use 5 servers on dedicated hosts with a fast log disk, in one region and, if possible, across three zones with low latency; use observers for remote reads; watch the number of watches and connections. Check that session timeouts exceed GC pauses, and plan the migration path (KRaft) for Kafka.

@@ etcd
value: etcd is a distributed key-value store that keeps a small amount of very important data safe and consistent across a few machines. It uses the Raft consensus algorithm, so that a write is accepted only when a majority of the servers have saved it on disk, and every reader sees the same order of changes. It was created at CoreOS in 2013, it is written in Go, and it is best known as the place where Kubernetes keeps all of its state: every Pod, Deployment, Service, Secret and node record is a key in etcd.
Why was it needed? Clusters need one trustworthy place to answer questions such as "what is the desired state?", "who is the leader?" and "which nodes are alive?". A normal database on one machine is a single point of failure. A replicated database that is not strongly consistent can give two nodes different answers, and then two schedulers launch the same Pod, or two controllers both act as leader. etcd gives the guarantee that the cluster needs: a linearizable key-value API (every read sees the latest committed write), compare-and-swap transactions, a watch that streams changes in order, and leases that attach a time limit to keys.
The layers below explain why it looks this way. The coordination-service concept (coordination, L1) is the pattern of a small consensus cluster of 3 or 5 members that coordinates a large cluster of workers; etcd is the modern example, and ZooKeeper (zookeeper, L0) is the earlier one. Go (golang, L0) is the language: goroutines and channels fit the message-driven Raft loop, gRPC is native to Go, and a static binary is easy to deploy. etcd does not try to store much data. It stores configuration and state measured in megabytes to a few gigabytes, and it does that with strong correctness.
terms: Raft — a consensus algorithm that elects a leader and replicates a log of commands to followers, committing an entry when a majority has stored it.
Term — Raft's logical clock: a number that grows with each election; a message from an older term is ignored.
Quorum — a majority of the members (2 of 3, 3 of 5); it must agree for any write to commit and for a leader to be elected.
Revision — a global 64-bit counter that increases with every change to the store; each version of each key is tied to the revision that created it.
MVCC (multi-version concurrency control) — keeping old versions of keys so readers can see a consistent past state and watchers can resume from a point in history.
Watch — a long-lived stream that sends events (put, delete) for a key or a prefix, starting from a chosen revision.
Lease — a time-to-live attached to keys; if the owner stops renewing it (keep-alive), the lease expires and the keys are deleted.
WAL (write-ahead log) — an append-only file where each Raft entry is written and synced to disk before it is acknowledged.
Compaction and defragmentation — compaction removes old revisions below a chosen revision; defragmentation returns the freed space in the database file to the operating system.
history: The origin was CoreOS, a company that wanted a minimal Linux for clusters, in which updates restart machines safely. Restarting machines requires coordination ("only one node may reboot at a time"), and that requires a consistent store. In June 2013 CoreOS (Alex Polvi, Brandon Philips and Xiang Li) announced etcd. The name comes from the Unix directory /etc plus "d" for distributed. Raft had just been designed by Diego Ongaro and John Ousterhout at Stanford (the paper "In Search of an Understandable Consensus Algorithm" was at USENIX ATC 2014), and etcd was one of the first widely used implementations, which also helped to make Raft famous.
etcd v2 (stable in January 2015) had a hierarchical, directory-like API over HTTP and JSON, and it was easy to try with curl. In 2014 Kubernetes began, and it chose etcd for its state. The load from Kubernetes showed the limits of v2: HTTP polling was heavy, there was no efficient multi-key transaction, and watches could lose events. etcd v3 (June 2016) fixed this with a flat key space, a gRPC API, MVCC with revisions, long-lived watch streams, leases and transactions. Kubernetes moved to the v3 API in version 1.6 (2017).
Governance changed with the market. Red Hat bought CoreOS in 2018. etcd joined the Cloud Native Computing Foundation (CNCF) as an incubating project in December 2018 and graduated in November 2020, with maintainers from Amazon, Google, IBM, Alibaba, Red Hat and others. Release 3.5 came in 2021, and 3.6 in 2025 (3.6.6 was the latest release in November 2025). The Raft library of etcd (now go.etcd.io/raft) is reused by CockroachDB, TiKV (in a Rust port), Dgraph and many other systems. Not everyone keeps etcd underneath: Google Kubernetes Engine moved its control-plane storage to a Spanner-based system in 2024 while keeping the etcd API for compatibility, which shows that the API became a standard even where the engine changed.
how: A write has these steps. A client sends a Put to any member over gRPC. If the member is a follower, it forwards the request to the leader. The leader's Raft module turns it into a log entry with the current term and the next index, appends it to its WAL, and sends AppendEntries messages to the followers. Each follower writes the entry to its own WAL and calls fdatasync before replying. When the leader has acknowledgements from a majority (itself included), the entry is committed. The leader tells the followers the new commit index in the next message. Every member then applies the committed entries, in order, to its state machine, which is the key-value store. The leader replies to the client only after applying. Because a majority must have persisted the entry, any new leader (which must win the votes of a majority) has all committed entries, so no committed write is lost. This is the consensus pattern from coordination (L1), and the cost is that every write waits for the slowest disk in the fastest majority.
Leader election uses randomized timeouts. A follower that hears nothing from the leader for an election timeout (1 second by default, randomised between 1 and 2 timeouts) becomes a candidate, increments its term, votes for itself and asks the others for votes. A member votes for at most one candidate per term, and only for one whose log is at least as up to date as its own. The candidate with a majority becomes leader and sends heartbeats (every 100 ms by default) to keep followers from starting elections. The tuning rule from the documentation is that the heartbeat interval should be around the maximum round-trip time between members, and the election timeout at least ten times the heartbeat. If the network is slower than the settings assume, members start needless elections and the cluster becomes unstable.
Reads are linearizable by default. A read request that went to a follower, or to the leader, first runs a ReadIndex step: the leader confirms with a quorum that it is still the leader (one round of heartbeats), notes the current commit index, and the member waits until it has applied up to that index, then reads locally. This costs a network round trip but no disk write. A client can ask for a serializable read, which is served from the local member without the check; it is faster and spreads load, but may be stale. Kubernetes uses linearizable reads for most operations, and serves many list calls from its own watch cache for scalability.
The storage engine has two parts. In memory there is a B-tree index that maps each key to the list of revisions where it changed. On disk there is bbolt, an embedded B+tree key-value store with a memory-mapped file (a fork of BoltDB). The bbolt buckets store each version under the key "revision", and the value holds the key, its value and metadata. Each write increments the global revision. A read at a given revision uses the B-tree index to find the right version, then loads it from bbolt. This is MVCC, and it gives consistent snapshots and watches that can start from any recent revision. The database grows with history, so compaction deletes versions older than a given revision (Kubernetes asks etcd to compact about every 5 minutes), and defragmentation rewrites the file to release free pages. The default storage quota is 2 GiB, the documentation suggests at most 8 GiB, and when the quota is exceeded etcd raises an alarm and refuses writes until space is freed.
Leases and transactions give the coordination features. A lease has a TTL, and clients keep it alive with a stream of keep-alive messages. Keys attached to the lease are deleted when it expires. A leader election is "create the key /election/leader with my lease only if it does not exist", done in one Txn: If(createRevision == 0) Then(Put) Else(Get). A distributed lock is the same thing with the fencing token being the key's revision. A Txn has compare, success and failure operation lists, and runs atomically through Raft. Kubernetes uses it for optimistic concurrency: an update to an object says "if the object's mod revision is still N, replace it", which is what the resourceVersion field in the Kubernetes API means.
Kubernetes shows how all of this fits. Only the API server talks to etcd. Controllers, kubelets and schedulers talk to the API server, which watches etcd and keeps a cache. A kubelet's heartbeat is a small Lease object that the node updates every 10 seconds, which becomes a write to etcd. When you run kubectl apply, the API server validates the object, writes it under /registry/..., and every watcher gets the event with its new revision. A cluster with 5,000 nodes and many Pods creates thousands of writes per second, so etcd's disk latency and the object sizes decide the control-plane speed.

example: Follow one write. A 3-member cluster has leader L and followers F1 and F2, all in one data centre with a round trip of 0.5 ms and SSDs with an fdatasync of 2 ms. A client sends Put /registry/pods/default/web. L appends the entry to its WAL and syncs (2 ms) while sending AppendEntries to F1 and F2 in parallel. F1 and F2 each take 0.25 ms to receive it, 2 ms to sync, and 0.25 ms to reply. L gets its own sync done at 2 ms and the first follower ack at about 2.5 ms. Two of three members have the entry, so it is committed at about 2.5 ms. L applies it to bbolt, the revision goes from 1000 to 1001, and the client gets the answer at about 3 ms. Watchers get the event {put, key, revision 1001}. If the disks were spinning disks with a 15 ms sync, the same write would take 16 ms or more, and the whole control plane slows down. This is why the documentation insists on fast disks and why the metric wal_fsync_duration_seconds is the first one to watch (the 99th percentile should stay in single-digit milliseconds).
Now MVCC and compaction. Key "a" is written at revision 5 with value x, at revision 8 with value y, and deleted at revision 12. A read of "a" at revision 6 returns x, at revision 9 returns y, and at revision 13 returns "not found". A watch on "a" started from revision 6 delivers the put at revision 8 and the delete at revision 12. Now compact at revision 10. etcd keeps, for each key, the newest version at or below revision 10 (the one at 8) and everything newer, and drops the version at 5. A read at revision 6 now fails with "required revision has been compacted", and a watch that starts from revision 6 gets the same error and must re-list. This is the compacted-revision error that Kubernetes clients handle by listing again and restarting the watch.
Finally, failure. Kill the leader of the 3-member cluster. The followers get no heartbeat; after their election timeout (randomized, 1 to 2 seconds by default) one becomes a candidate in term 8 and wins the vote of the other follower. Writes are unavailable during this time, about one to two seconds, then continue. Existing Pods keep running, because kubelets do not need the control plane to keep containers alive, but no new Pods can be scheduled until the leader returns. If two of the three members fail, no majority exists, writes stop (and linearizable reads too), and you must restore a member or recover from a snapshot. With 5 members you can lose 2 and keep working. Seven members tolerate 3, but every write needs 4 acknowledgements and is slower, so 3 or 5 is the normal choice.
intuition: A small committee that keeps the official minutes: nothing is official until most of the committee has written it down, and anyone can ask what changed since page 1000.
The design is natural because the committee of three or five is cheap, and the cost of agreement is small when the data is small. A Raft log makes the order of changes a fact that everyone shares. Revisions turn that order into a clock that clients can use to ask "show me everything since I last looked" without missing or repeating anything. This is exactly what controllers need: Kubernetes controllers are loops that watch for changes and make the world match the stored desired state, and they can crash and restart at any time and catch up from a revision.
mistakes: People often think etcd is a general-purpose database for application data. In fact it is for small, critical metadata. Requests are limited to 1.5 MiB by default, the default database quota is 2 GiB, and every write is synced to disk through consensus. Large values and high write rates slow down the whole cluster.
People often think more etcd members give more performance. In fact each member holds the full data, and every write needs a majority to acknowledge, so more members make writes slower. Extra members add fault tolerance only. Use 3 members, or 5 for higher availability, and spread them across failure domains with low latency.
People often think etcd uses disk only for backup. In fact the write path calls fsync on the write-ahead log for every batch of entries, so disk latency directly sets write latency. A busy disk shared with other workloads is the most common reason for slow Kubernetes control planes and for leader elections.
People often think a deleted or changed key is gone immediately. In fact old versions stay until compaction, and the file does not shrink until defragmentation. A cluster with heavy churn (for example many Events or Leases) can hit the space quota even if the live data is small.
tradeoffs: Choose etcd when you need strongly consistent, small metadata with watches and leases: Kubernetes, service registries, feature flags and leader election in Go services. You give up scale: a single Raft group, with all data on every member, a few gigabytes at most and thousands of writes per second at most. Choose ZooKeeper when you must support existing Java systems that depend on it, and accept its older API and operational model. Choose Consul when you also want service discovery and health checks built in.
Choose 3 members for most clusters, and 5 if you want to survive a failure during planned maintenance or run across three zones with more redundancy. Choose a single zone or low-latency placement (round trip under a few milliseconds) over geographic spread, since each write waits for a cross-member round trip. Spreading across three availability zones in one region (1 to 2 ms) is a common compromise that survives a zone loss. Cross-region etcd clusters are rarely a good idea.
Choose dedicated, fast disks (local NVMe or a high-IOPS volume with a low p99 fsync) for etcd members, and keep other I/O off them. Choose a separate etcd cluster for high-churn data such as Kubernetes Events when your cluster is large, so that its churn does not hurt the main objects. You pay for extra clusters to operate.
Choose a managed control plane (EKS, GKE, AKS) when you do not want to operate etcd: the provider handles backups, upgrades, sizing and, in some cases, a different storage engine. You give up control and visibility. Choose to run your own etcd only if you need self-managed clusters, and then automate backups (etcdctl snapshot save), restore tests and defragmentation.
friction: Disk and network latency set the limits. A slow fsync, a noisy neighbour, a snapshot or a defragmentation on the leader can cause slow requests, missed heartbeats and elections ("leader changed", "apply request took too long" in the logs). A leader election pauses writes for a few seconds. Cross-zone latency of a few milliseconds is fine, but variable latency is harmful: the election timeout must be tuned and understood.
Size is the second limit. Everything is in one Raft group, all members store all data, and the database is memory-mapped, so a database of several gigabytes needs RAM and takes long to snapshot, transfer to a new member and defragment. Large clusters with many objects (hundreds of thousands) and many watchers put load on the API server and etcd; list calls on large resource types can be heavy. Compaction and defragmentation are manual or scheduled chores, and a full database puts the cluster in an alarm state in which it accepts only reads and deletes.
Operations are the third. Membership changes must be done one at a time and with learner members in recent versions; losing quorum needs a careful recovery from a snapshot, which can lose recent writes. Upgrades have to follow supported version paths. Security needs TLS for client and peer traffic and authentication; an etcd with open access exposes every Kubernetes Secret. Secrets in etcd are not encrypted by default; Kubernetes needs encryption at rest to be configured. Backups of etcd are the cluster's backups, and must be tested.
practice: Give etcd its own fast storage and watch these metrics: etcd_disk_wal_fsync_duration_seconds and backend_commit_duration_seconds (99th percentile in the single-digit milliseconds), leader changes per hour (should be near zero), proposals failed or pending, database size against quota, and the request latency histograms. Run etcdctl endpoint status and endpoint health from time to time and in alerts. Keep the database well below the 2 GiB quota or raise the quota deliberately up to the suggested 8 GiB maximum.
Automate compaction (Kubernetes does it every 5 minutes through the API server) and schedule defragmentation one member at a time, starting with followers and doing the leader last, in a quiet period. Take snapshots regularly with etcdctl snapshot save, store them off the cluster, and practice the restore with etcdutl snapshot restore on a test cluster. Set heartbeat-interval and election-timeout from the measured round trip time between members (heartbeat about the maximum RTT, election timeout at least ten times the heartbeat), especially in clouds with several zones.
For Kubernetes, avoid pushing large objects or ConfigMaps near the 1.5 MiB limit, avoid controllers that write too often (status updates in a loop), and limit the number of Events and Leases. Enable encryption of Secrets at rest. If you write your own services on etcd, use the concurrency package (sessions, mutex, election) instead of hand-written lease logic, use fencing with the revision for safety, and always handle the watch compaction error by re-listing.
quiz: Why does etcd need a majority of members for a write? || Raft commits an entry only when a majority has stored it. Any later leader must be elected by a majority, and every majority overlaps the one that committed the entry, so the new leader has the entry and no committed write is lost.
How does etcd provide linearizable reads without writing to disk? || A read uses ReadIndex: the leader confirms with a quorum that it is still the leader, records its commit index, and the serving member waits until it has applied up to that index, then reads locally. It costs a network round trip, not a disk write.
What is a revision and why does Kubernetes depend on it? || It is a global counter that increases with every change. It allows consistent reads at a point in history, watches that resume from a given revision, and optimistic concurrency (resourceVersion), so controllers can catch up after a restart without missing events.
A 3-member etcd cluster has 2 ms fsync and 0.5 ms round trip. What is the approximate write latency, and what happens with a 15 ms disk? || About 3 ms: the leader syncs while the followers receive, sync (2 ms) and reply, and a majority is reached at about 2.5 ms. With a 15 ms disk it is at least 16 ms, and the control plane becomes slow.
Your Kubernetes control plane is slow and etcd logs show "apply request took too long" and leader changes. How do you investigate? || Check WAL fsync and backend commit latency, disk sharing and noisy neighbours, CPU steal, network latency between members, database size and recent defragmentation or snapshots, and heartbeat/election settings relative to the RTT. Look at large objects and churn from controllers.
interview: Why is 5 members not always better than 3? || Each write needs acknowledgements from a majority: 2 of 3 versus 3 of 5. The larger cluster tolerates two failures instead of one but has higher write latency and more replication traffic. For most clusters 3 is enough; use 5 when availability during maintenance or zone loss matters more than the extra latency.
What happens in a Raft cluster when the leader is partitioned from the majority? || The leader cannot commit new entries, since it cannot reach a quorum, and the majority side elects a new leader in a higher term. When the partition heals, the old leader sees the higher term, steps down and discards uncommitted entries. Linearizable reads on the old leader fail the quorum check, so clients do not read stale data.
How do compaction and defragmentation differ and what happens at the quota? || Compaction removes old revisions from the logical history, creating free pages inside the bbolt file, but the file does not shrink. Defragmentation rewrites the file and returns space to the OS, and it blocks the member while it runs. At the quota, etcd raises a NOSPACE alarm and rejects writes until you compact, defragment and clear the alarm.
How would you build leader election on etcd, and how do you make it safe? || Create a key with a lease in a Txn that checks that it does not exist; the creator is the leader, and others watch the key. Keep the lease alive; if the leader dies, the lease expires and the key is deleted. For safety use the key's revision as a fencing token so that resources reject stale leaders.
Why did Kubernetes choose etcd rather than a relational database? || It needs a linearizable store with ordered watches and optimistic concurrency, replicated across a few machines without extra systems. etcd's revisions, watches and Raft replication fit controllers that react to changes, while a SQL database would need extra mechanisms for change streams.
How do you back up and restore an etcd cluster, and what do you lose? || Take snapshots with etcdctl snapshot save from a healthy member and store them off-cluster. To restore, use etcdutl snapshot restore on each member with a new cluster identity and restart. You lose writes made after the snapshot, and the revision history is reset, so clients with old watch revisions must re-list.

value: Docker is the tool that made Linux containers easy to use. A container is an ordinary Linux process that the kernel has given its own private view of the system (its own process list, network, file system and users) and a limit on how much CPU and memory it may use. Docker adds three things around this: an image format that packs an application together with all the files it needs, a registry system for sharing images, and a simple command line (docker build, docker run, docker push) to use them. Since 2013 this has been the standard way to package and ship server software.
The problem it solved is "it works on my machine". An application depends on a language runtime, system libraries, configuration files and tool versions. Installing these by hand on every laptop, test server and production host leads to differences, and differences cause bugs. With Docker, you describe the build once in a Dockerfile, build an image, and run the same image everywhere. The image is immutable and identified by a hash of its content, so "what is running in production" has a precise answer. A container starts in a fraction of a second and uses no extra operating system, so one host runs dozens or hundreds of them, unlike virtual machines.
The layers below make it work. The Linux kernel (linux, L0) provides the real mechanisms: namespaces for isolation, control groups (cgroups) for resource limits, and the overlay file system for layered images. The container concept (containers, L1) is the idea of operating-system-level virtualization: many isolated user spaces share one kernel. Go (golang, L0) is the language of Docker and of its core parts, containerd and runc, which are static binaries that are easy to ship and good at concurrent system programming. Docker is the base of Kubernetes (kubernetes, L0): Kubernetes schedules containers built as OCI images and started by a runtime such as containerd, which came out of Docker.
terms: Image — a read-only package of files (a stack of layers) plus metadata such as the command to run; it is the template for containers.
Container — a running (or stopped) instance of an image: a process with its own namespaces, cgroup limits and a writable layer on top of the image.
Layer — a set of file changes (added, modified or deleted files) stored as a tar archive and identified by a hash; layers are shared between images.
Namespace — a kernel feature that gives a process its own view of one kind of resource (process ids, network, mounts, hostnames, users, IPC).
cgroup (control group) — a kernel feature that limits and accounts for the CPU, memory, I/O and number of processes of a group of processes.
Overlay file system (OverlayFS) — a union file system that shows several read-only directories plus one writable directory as one tree, with copy-on-write.
Registry — a server that stores and serves images by name and digest (Docker Hub, Amazon ECR, GitHub Container Registry).
OCI (Open Container Initiative) — the industry standards for the image format, the runtime and the registry protocol, so that tools from different vendors interoperate.
runc and containerd — runc is the small tool that actually creates a container process following the OCI runtime spec; containerd is the daemon that manages images, containers and runc.
history: The ideas came before Docker. FreeBSD jails (2000) and Solaris Zones (2004) isolated processes on one kernel. Linux got the parts in steps: mount namespaces (2002), cgroups (contributed by Google engineers in 2007) and more namespaces up to user namespaces (2013). Projects such as LXC (2008) and Google's internal systems used them, but setup was hard and each environment was unique.
Docker came from dotCloud, a platform-as-a-service company. Solomon Hykes showed it in a five-minute talk at PyCon in March 2013 and released it as open source. The key insight was not new kernel technology but a better workflow: a Dockerfile to describe an image, layers that make builds and downloads incremental, and a registry (Docker Hub, 2014) so that anybody could pull ready-made images. The company renamed itself Docker, Inc. Early Docker used LXC underneath; in 2014 (version 0.9) it replaced LXC with its own Go library, libcontainer. Docker 1.0 came in June 2014.
Standardization followed quickly because large companies did not want one vendor to own the format. The Open Container Initiative started in June 2015 under the Linux Foundation. Docker donated its runtime core, which became runc, and the image and runtime specifications reached 1.0 in 2017. Docker also split its engine into parts: containerd (donated to the CNCF in 2017, and graduated in 2019) and the Moby project for components. Kubernetes (2014) became the dominant way to run containers at scale, and it spoke to runtimes through the Container Runtime Interface. Kubernetes removed its built-in Docker support (dockershim) in version 1.24 in 2022, and uses containerd or CRI-O directly. Images built by Docker still run unchanged, because they follow the OCI format.
Docker itself changed as a business. In 2021 Docker Desktop (the app for Mac and Windows) stopped being free for larger companies. BuildKit became the default build engine in 2023 (Docker 23.0). Docker Engine 29 (November 2025) made the containerd image store the default for new installations, and by April 2026 the Engine was at version 29.4. Docker remains the standard developer tool, while production platforms use containerd and runc underneath.
how: Start with an image. A Dockerfile is a recipe of instructions: FROM python:3.12-slim, COPY requirements.txt, RUN pip install, COPY . /app, CMD ["python", "app.py"]. Each instruction that changes the file system (RUN, COPY, ADD) produces a layer, a tar archive of the differences, identified by its SHA-256 digest. An image is a manifest (a JSON list of layer digests), a config (JSON with the command, environment variables, architecture) and the layers. Because layers are content-addressed, two images that share a base share its layers on disk and in the registry, and a pull downloads only the layers the host does not have. The build cache uses the same idea: if an instruction and its inputs are unchanged, the earlier layer is reused, so the order of instructions decides how fast builds are.
To run it, the Docker CLI sends a request over a Unix socket (/var/run/docker.sock) to the Docker daemon (dockerd). The daemon asks containerd to create the container. containerd unpacks the image layers into snapshots, and starts a small shim process that stays alive as the parent of the container. The shim calls runc with an OCI bundle: a directory with a root file system and a config.json that lists namespaces, mounts, cgroup limits and the command. runc then does the kernel work and exits, leaving the container process as a child of the shim. This design means that restarting the daemon does not kill the containers.
The root file system comes from OverlayFS (the linux kernel, L0). The image layers are mounted as read-only lower directories, and a new empty directory is the writable upper layer. A read looks at the upper layer first and then down through the lower layers. A write to a file that exists in a lower layer copies the whole file into the upper layer first (copy-on-write) and changes the copy. A deleted file is hidden by a special "whiteout" marker. When the container is removed, the upper layer is deleted, and the image is unchanged. This is why container storage is cheap to start, and why data that must survive needs a volume (a directory outside the layered file system) or a bind mount.
Isolation comes from namespaces. runc calls clone with flags (or unshare) to create new ones: PID (the container sees its own process tree, where its first process is PID 1), network (its own interfaces, routing table and ports), mount (its own mount table, switched with pivot_root to the image root), UTS (hostname), IPC (shared memory and queues), user (the container's root can map to an unprivileged id on the host) and cgroup. A process in the container is still an ordinary process on the host kernel; the host sees it with another PID. Networking by default uses a virtual bridge (docker0) on the host: each container gets one end of a virtual Ethernet pair (veth) and an address from a private range, and published ports (-p 8080:80) are forwarded by packet-filter rules (iptables by default, with nftables support in recent Engine versions).
Resource limits come from cgroups. With cgroup v2, runc writes files in /sys/fs/cgroup: memory.max sets a memory limit (a container above it is killed by the kernel's OOM killer with exit code 137), and cpu.max sets a CPU quota as "quota period". For example --cpus=1.5 becomes "150000 100000": in each 100 ms period the group may use 150 ms of CPU time in total across all its threads, and when it uses its quota it is throttled until the next period. Security adds more layers: the default set of Linux capabilities is reduced, a seccomp profile blocks dozens of system calls, and AppArmor or SELinux can confine file access. None of these changes the fact that all containers share the host kernel, so a kernel bug is a possible route out of the container.
The OCI standards tie everything together. The image spec defines the layout (manifest, config, layers), the runtime spec defines the bundle that runc takes, and the distribution spec defines the registry HTTP API (pull by tag or by digest). A tag like myapp:1.4 is a movable label; a digest like myapp@sha256:3f9a... is an exact, immutable reference. Multi-architecture images use an index (a manifest list) that points to one manifest per platform (linux/amd64, linux/arm64), so the same name works on an Intel server and on an ARM Mac or Graviton instance. On macOS and Windows, Docker Desktop runs a small Linux virtual machine, because containers need a Linux kernel.

example: Take this Dockerfile for a Python service: FROM python:3.12-slim; WORKDIR /app; COPY requirements.txt .; RUN pip install -r requirements.txt; COPY . .; CMD ["python", "main.py"]. The base image python:3.12-slim is roughly 130 MB, while the full python:3.12 image is roughly 1 GB, because the full image includes compilers and many libraries. Suppose pip install takes 80 seconds and downloads 200 MB. On the first build all layers are built: about 90 seconds. Now you change one line of main.py. Docker checks each instruction from the top. FROM, WORKDIR, COPY requirements.txt (the file is unchanged) and RUN pip install all hit the cache. Only the last COPY runs, and the build takes about 2 seconds. If you had written COPY . . before pip install, any code change would change that layer and invalidate pip install, and every build would take 90 seconds. Order the Dockerfile from least to most frequently changing.
Now a deployment. The new image has 4 layers, of which 3 (the base and dependencies, 190 MB in total) are the same as the version already running on a host. The host pulls the manifest, sees that 3 layers exist locally, and downloads only the one small layer with your code, a few hundred kilobytes. The container starts in under a second. This is why Docker deployments can be fast even for big images, as long as the layers are stable.
Third, limits and the JVM. You run a Spark or Java service with docker run --memory=2g --cpus=2. The kernel sets memory.max to 2 GiB and cpu.max to "200000 100000". A JVM from the last several years reads the cgroup limits and sizes itself from them: with -XX:MaxRAMPercentage=75 the heap is about 1.5 GiB, leaving the rest for metaspace, thread stacks and off-heap buffers. If you instead set -Xmx2g, the process uses more than 2 GiB in total (heap plus native memory), the kernel kills it with exit code 137 and a log line "OOMKilled", and you see a restart loop. Also, with 2 CPUs of quota but 32 visible cores on the host, a multi-threaded application may run 32 threads that use their 200 ms of quota in the first 6 ms of each 100 ms period and then wait for 94 ms. That throttling shows up as latency spikes at the 99th percentile even when the average CPU use looks low.
intuition: A standard shipping container for software: the same sealed box can be loaded onto any ship, truck or train, because the outside is standard and the contents are the sender's concern.
The idea is natural because most of what makes software hard to move is not the program but its surroundings, and the surroundings can be captured as files. The kernel already knows how to give a process a private view of the system; Docker added a convenient, content-addressed way to capture and ship those files. Sharing the kernel makes it light, and layering makes it incremental, so shipping a new version means sending only what changed.
mistakes: People often think a container is a small virtual machine. In fact a container is a normal process on the host's kernel, with namespaces and cgroups around it. There is no guest kernel, so it starts in milliseconds, but it is isolated by the host kernel only, which is weaker than a hypervisor boundary.
People often think containers are only for stateless services and data inside is safe. In fact the writable layer is deleted with the container, so data must go in volumes or external storage. Stateful systems can run in containers, but you must design storage, backup and identity deliberately.
People often think the image tag latest or 1.4 always means the same content. In fact tags can be moved to a new image at any time. For reproducible and secure deployments, pin the digest (name@sha256:...) and rebuild on purpose.
People often think root inside a container is harmless. In fact by default the container's root is the host's root user with fewer capabilities, and access to the Docker socket gives control of the whole host. Run as a non-root user, drop capabilities, use rootless mode or user namespaces, and never mount docker.sock into untrusted containers.
tradeoffs: Choose containers over virtual machines when you want fast start (under a second), high density (dozens of services per host) and a simple build and deploy pipeline, and your workloads trust the shared kernel. Choose virtual machines, or microVMs (Firecracker, Kata Containers) or sandboxes such as gVisor, when you run untrusted or multi-tenant code and need a stronger boundary, accepting more overhead (a guest kernel, hundreds of MB of memory, start in 100 ms to seconds).
Choose small base images (slim, distroless, Alpine) to reduce download time and attack surface, when your application has few native dependencies. Choose Debian or Ubuntu-based images when you use many native libraries or glibc-specific binaries, because Alpine's musl libc can cause compatibility and performance surprises (especially with Python wheels and JVM native code). Choose multi-stage builds to compile in a big image and copy only the result into a small runtime image.
Choose Docker (Engine or Desktop) for local development and building. Choose containerd directly, or CRI-O, for production nodes in Kubernetes, since you need no developer features there. Choose Podman, Buildah or rootless setups when you cannot run a root daemon or when licensing for Docker Desktop is a concern. Choose BuildKit with a remote cache in CI to share layers between builds.
Choose to pin versions and digests, scan images (for known vulnerabilities), generate a software bill of materials (SBOM) and sign images (Sigstore cosign) when your organization has supply-chain requirements; you pay with more pipeline steps. Choose a multi-architecture build (amd64 and arm64) when your fleet or laptops mix architectures; it costs extra build time and testing.
friction: Isolation is weaker than with virtual machines. All containers share the host kernel, so a kernel vulnerability or a misconfiguration (privileged mode, host mounts, the Docker socket) can allow escape. Real escape bugs have occurred in runc (CVE-2019-5736 is a well-known one). Sandboxing runtimes and rootless mode improve this at some cost.
Images are a supply-chain risk and a maintenance load. A base image carries an operating system with packages that need security updates, so images must be rebuilt regularly. Images from public registries may include malware or old vulnerable software. Image size and layer design affect startup time on new nodes (pulling a 2 GB image on a fresh node takes a minute or more), and lazy-pulling techniques exist but add complexity. Build reproducibility is hard: pip install or apt-get without pins gives different results on different days.
Operations have their own pitfalls. The first process in a container is PID 1, which does not get default signal handling and must reap zombie children; a shell script as entrypoint can ignore SIGTERM, so stops take 10 seconds and then a kill. Logging to files inside the container fills the writable layer; log to stdout. Resource limits can hurt: CPU throttling causes latency, and memory limits kill processes. Networking has overhead (NAT, bridge) and surprises with DNS. Docker Desktop on Mac and Windows runs a Linux virtual machine, so file sharing with the host is slower and the CPU architecture of the VM matters. The engine itself changes: Engine 29 changed the default image store, so major upgrades need testing.
practice: Write small, ordered Dockerfiles: put dependency installation before the copy of application code, use .dockerignore, use multi-stage builds, run as a non-root user (USER 10001), set a fixed base version, and use the exec form of CMD so signals reach your process. Add --init (or tini) when your process does not reap children. Log to stdout and stderr. Add a HEALTHCHECK or, in Kubernetes, readiness and liveness probes.
Set resource limits on purpose and make the application aware of them: modern JVMs read cgroup limits, so use -XX:MaxRAMPercentage (about 70 to 75) and leave room for native memory; for Go services set GOMAXPROCS from the CPU quota (or use automaxprocs), and for Python check worker counts. Watch for CPU throttling in the metrics (container_cpu_cfs_throttled_periods_total) and set CPU requests and limits knowingly. Prefer to set a memory limit with a margin above observed peak use.
Build in CI with BuildKit and cache, create multi-architecture images with docker buildx (--platform linux/amd64,linux/arm64), tag with the git commit and deploy by digest, scan images, generate SBOMs and sign them. Clean up regularly: docker system df shows disk use, and old images, stopped containers and build cache can fill a build machine. For learning, run docker run on a simple command and then inspect it from the host: look at the process in ps, at /proc/<pid>/ns, and at the cgroup files, and you will see that a container is a process with fences.
quiz: What are the kernel features that make a Docker container? || Namespaces (private views of process IDs, network, mounts, hostname, IPC, users), cgroups (limits and accounting for CPU, memory, I/O and processes) and an overlay file system for the layered root file system. A container is an ordinary process using them.
Why are Docker images made of layers, and how does that speed up builds and pulls? || Each file-changing instruction produces a content-addressed layer. Unchanged layers are reused from the build cache, and registries and hosts store shared layers once, so a pull downloads only layers that are missing.
What happens when a container writes to a file that exists in the image? || OverlayFS copies the file from the read-only lower layer into the container's writable upper layer (copy-on-write) and changes the copy. The image stays unchanged, and the change is lost when the container is deleted unless a volume is used.
A service runs with --memory=2g and -Xmx2g and is repeatedly killed with exit code 137. Why, and what do you change? || The JVM uses native memory beyond the heap (metaspace, thread stacks, direct buffers), so total use exceeds 2 GiB and the kernel OOM-kills it. Use -XX:MaxRAMPercentage of about 70 to 75 (or a smaller -Xmx) and leave room for native memory.
When do you choose a microVM or gVisor instead of plain Docker containers? || When you run untrusted or multi-tenant code, such as customer functions or CI jobs from unknown users, because a shared kernel is a large attack surface. You accept extra memory and start time for a stronger isolation boundary.
interview: Walk through what happens from docker run to a running process. || The CLI calls dockerd over a Unix socket, which asks containerd to create the container. containerd unpacks the image layers into an OverlayFS snapshot, starts a shim, and the shim calls runc with an OCI bundle. runc creates namespaces, sets up cgroups, mounts the root file system with pivot_root, drops capabilities, applies seccomp, and executes the command. runc exits and the shim remains as parent.
How is a container different from a VM in isolation, performance and security? || A VM has its own kernel on virtualized hardware, with a strong boundary through the hypervisor and some overhead in memory and start time. A container shares the host kernel, so it starts in milliseconds with almost no overhead, but the kernel is the shared attack surface, so isolation is weaker.
Why can CPU limits hurt latency even when average CPU use is low? || The CFS quota gives a group a time budget per period (for example 200 ms in 100 ms). A multi-threaded process can burn the budget in a few milliseconds and then be throttled until the next period, which creates latency spikes. Monitor throttled periods and consider raising or removing limits, and set thread counts from the quota.
How would you make container builds fast and reproducible in CI? || Order instructions for cache reuse, use BuildKit with a shared remote cache, multi-stage builds, pinned base images by digest and pinned package versions, build multi-arch with buildx, and sign and scan the result. Reproducibility also needs fixed timestamps and dependency lockfiles.
What changed when Kubernetes removed dockershim, and what stayed the same? || Kubernetes now talks to runtimes directly through CRI (containerd or CRI-O) and no longer through the Docker daemon. Images built with Docker still run because they follow the OCI image format. What changes is node tooling: docker ps on a node is replaced by crictl.
How do you reduce the risk of running third-party images in production? || Pin by digest, scan for vulnerabilities, prefer minimal or distroless bases, run as non-root with dropped capabilities and a read-only root file system, use rootless or sandboxed runtimes for untrusted workloads, mirror images in a private registry, and verify signatures and SBOMs in admission policy.
