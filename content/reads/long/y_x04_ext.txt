@@+ vmem
terms: Virtual address — the address a program uses; it means nothing to RAM until the MMU translates it.
Page — a fixed-size block of virtual memory, usually 4 KB; the unit of mapping and protection.
Frame — a page-sized block of physical RAM that one or more pages can be mapped to.
Page table entry (PTE) — 8 bytes on x86-64 that hold the frame number plus present, writable, user, no-execute, accessed and dirty bits.
MMU — the memory management unit, hardware in each core that translates every virtual address.
TLB — the translation lookaside buffer, a small cache of recent translations inside each core.
Page fault — a trap into the kernel when a translation is missing or not allowed; minor if no disk read is needed, major if it is.
Copy-on-write — sharing a page read-only between two processes and copying it only when one of them writes.
Resident set size (RSS) — the part of a process's virtual memory that is in RAM right now.
Huge page — a 2 MB or 1 GB page that needs one TLB entry instead of 512 or 262,144.
how: The TLB is small. A recent x86 core has a first-level data TLB of roughly 64–96 entries and a second-level TLB of a few thousand entries. With 4 KB pages, 2,048 entries cover only 8 MB of memory; this number is called the TLB reach. A program that reads a 10 GB table at random therefore misses the TLB on most accesses. CPUs soften the cost with page-walk caches for the upper table levels, and the walk itself reads page-table entries through the normal L1, L2 and L3 caches. This is what the memory hierarchy (memhier) contributes: the TLB is one more cache in front of DRAM, and its hit rate decides whether translation is almost free or adds a DRAM access to every load.
Probability and locality explain why the TLB works at all. Ordinary code reaches TLB hit rates above 99%, because consecutive accesses fall on the same 4 KB page (spatial locality) and the same pages are used again soon (temporal locality). The same statistics drive page replacement (pagereplace). When RAM is full, the kernel must pick a victim page, and the accessed and dirty bits in each entry are its evidence. Linux approximates "least recently used" with active and inactive page lists (and, since kernel 6.1, an optional multi-generation LRU) instead of recording every access. A dirty page must be written back before its frame is reused; a clean file page can simply be dropped and read again later.
The page table is not the full description of a process's memory. Linux also keeps a list of virtual memory areas (VMAs): ranges such as "heap, read-write", "libc code, read-execute" or "this file, mapped shared". On a page fault the kernel looks up the address in this list. If no area covers it, or the access breaks the area's permissions, the process receives SIGSEGV. If the area is valid, the fault is part of normal operation. It is a minor fault when the data is already in RAM or needs none (a zero page to allocate, a page-cache page to map, a copy-on-write copy to make), costing about a microsecond or less. It is a major fault when the data must be read from storage.
Multicore chips add a cost. Each core has its own TLB, so when the kernel removes or changes a mapping (munmap, a permission change, moving a page), it must remove stale entries on every core that may hold them. It does this with a TLB shootdown: it sends an inter-processor interrupt to the other cores, and each one flushes the entry and confirms. A shootdown costs several microseconds and grows with the number of cores, which is one reason mmap-based databases scale poorly when they evict pages often. Context switches used to flush the whole TLB; tagged TLBs (PCID on x86, ASID on Arm) label each entry with an address-space number so entries survive a switch.
Page tables also use memory. Each 4 KB page needs an 8-byte entry, about 0.2% overhead. That looks small until many processes map the same large region: 100 database worker processes that each touch a 64 GB shared buffer pool need about 100 × 128 MB = 12.8 GB of page tables. This is why PostgreSQL servers with large shared buffers are often run with huge pages. Five-level paging (57-bit addresses, supported by Linux since 2017 on recent Intel and AMD server CPUs) raises the limit from 256 TB to 128 PB of virtual address space, at the cost of one more level in every walk.

mistakes: People often think virtual memory means swapping to disk. In fact virtual memory is address translation, and it is active on every memory access of every process, even on servers with swap turned off. Swapping is one optional feature built on it; isolation, copy-on-write, mmap and lazy allocation all work without any swap device.
People often read a process's virtual size (VSZ or VIRT in top) as its memory use. In fact virtual size counts reserved address ranges, most of which are never touched: a JVM reserves address space for its maximum heap, and Go reserves large arenas. What uses RAM is the resident set (RSS). Even RSS overcounts shared pages: ten processes that share a 50 MB library each report it, so tools such as smem report PSS (proportional set size), which divides each shared page among its users.
People often think a successful malloc or mmap means the memory exists. On Linux with default overcommit, allocation only reserves virtual addresses; frames are assigned on first touch. A program can allocate 64 GB on a 16 GB machine and fail only later, when touching the pages exhausts free frames and the OOM killer chooses a victim, which may be a different process.
People often treat page faults as errors. Most faults are normal: the first touch of new heap memory, a copy-on-write after fork, the first read of an mmap'd file page. A busy service may take thousands of minor faults per second at about a microsecond each. Major faults are the ones to watch, because each waits for storage; a steady rate of them means the working set does not fit in RAM.
quiz: What does the TLB store, and what happens on a TLB miss? || It stores recent translations from virtual page number to physical frame, with their permission bits. On a miss, the MMU walks the page tables (up to four memory reads on x86-64 with 4 KB pages) and puts the result in the TLB.
Why is fork() fast even when the parent uses 10 GB of memory? || The kernel does not copy the 10 GB. It copies the page tables and marks the pages read-only in both processes; a page is copied only when one side writes to it (copy-on-write). The cost follows the page-table size, about 20 MB for 10 GB of 4 KB pages, not the data size.
How does the kernel decide whether a page fault is normal demand paging or a segmentation fault? || It looks up the faulting address in the process's list of virtual memory areas. If an area covers the address and allows the access, the kernel allocates, loads or copies the page and retries the instruction; otherwise it sends SIGSEGV.
A core has 1,536 second-level TLB entries that can hold 4 KB or 2 MB translations. How much memory can it map without a miss in each case? || 1,536 × 4 KB = 6 MB with 4 KB pages, and 1,536 × 2 MB = 3 GB with 2 MB pages. A random-access workload over a 20 GB table misses the TLB on most accesses with 4 KB pages, and far less often with 2 MB pages.
Why might a database manage its own buffer pool instead of mmap-ing its data files? || Its own pool lets it choose which pages to evict, decide when dirty pages are written (after the write-ahead log), and handle I/O errors as normal return codes. With mmap the kernel decides eviction and flushing, I/O errors arrive as signals, and evictions cause TLB shootdowns; the price of a private pool is more code, and double caching unless it uses direct I/O.

@@+ memhier
terms: Cache line — the 64-byte block in which data moves between cache levels and DRAM.
Hit rate — the fraction of accesses that a cache level serves; one minus it is the miss rate.
AMAT — average memory access time: hit time plus miss rate times miss penalty, applied level by level.
Working set — the data a program touches during a period of time; speed changes sharply when it outgrows a level.
Set-associative cache — a cache in which each address may live only in one small set of slots (the ways), chosen by address bits.
Prefetcher — hardware that detects an access pattern and loads lines before the program asks for them.
Write-back — a policy where a store updates only the cache and marks the line dirty; memory is updated when the line is evicted.
Coherence (MESI) — the protocol that keeps copies of one line in different cores consistent by giving each copy a state.
False sharing — two threads writing different variables that sit on the same line, so the line bounces between cores.
Memory-level parallelism — the number of cache misses a core can have in flight at the same time.
how: Probability turns hit rates into an expected cost. The average memory access time (AMAT) is hit time + miss rate × miss penalty, and the miss penalty of one level is the AMAT of the level below. Take an L1 that hits 95% of accesses in 1 ns, an L2 that serves 60% of L1 misses in 4 ns, an L3 that serves half of the rest in 15 ns, and DRAM at 90 ns. Then AMAT = 1 + 0.05 × (4 + 0.4 × (15 + 0.5 × 90)) = 1 + 0.05 × 28 = 2.4 ns. If the L1 hit rate falls to 90%, AMAT becomes 1 + 0.10 × 28 = 3.8 ns. A five-point change in hit rate costs almost 60% in average latency, which is why small layout changes have large effects.
A cache is a hardware hash table with a very simple hash function. The address is split into an offset (6 bits for a 64-byte line), a set index and a tag. A 48 KB, 12-way L1 holds 768 lines in 64 sets of 12, so bits 6–11 choose the set and the 12 tags of that set are compared in parallel. Those bits lie inside the 4 KB page offset, so they are the same in the virtual and the physical address; the L1 can choose the set while the TLB translates the rest of the address. This is why L1 sizes are often ways × 4 KB (12 × 4 KB = 48 KB). A line may live only in its own set, so addresses exactly 4 KB apart compete for the same 12 slots. Walking down a column of a matrix whose rows are 4 KB long causes conflict misses even when most of the cache is empty. Within a set, hardware evicts an approximately least recently used line, tracked with a few bits per set.
Writes add their own traffic. Caches are write-back: a store changes the line in L1 and marks it dirty, and memory is written only when the line is evicted. They are also write-allocate: a store to a line that is not cached first reads the whole line, so writing 1 GB of new data can cause 2 GB of DRAM traffic. Streaming (non-temporal) stores skip that read for large copies. Coherence tracks each cached line in one of four MESI states: Modified (only copy, dirty), Exclusive (only copy, clean), Shared (clean, other copies may exist) and Invalid. Before a core writes, it must hold the line in Modified or Exclusive state, so every other copy is invalidated first.
Queueing explains bandwidth. A core can keep only about 10–20 L1 misses in flight, plus some more started by the L2 prefetcher. By Little's law, bandwidth = bytes in flight ÷ latency, so 16 misses × 64 B ÷ 90 ns ≈ 11 GB/s. That is why one core reaches only about 10–20 GB/s, while a server socket delivers hundreds of GB/s only when many cores miss at the same time. A linked-list walk keeps one miss in flight and gets about 64 B ÷ 90 ns ≈ 0.7 GB/s. The memory controller is itself a queue: as DRAM bandwidth use rises past about 70–80%, loaded latency climbs from about 90 ns to 200 ns or more.
Physics sets the shape of the hierarchy. An SRAM cache cell uses six transistors and is read quickly but takes a lot of area. A DRAM cell is one transistor and one capacitor, so it is much denser and cheaper, but reading it is destructive, a whole row must be opened first, and every cell must be refreshed about every 64 ms because the charge leaks away. Bigger arrays need longer word lines and bit lines. The delay of an on-chip wire without repeaters grows with the square of its length, because both its resistance and its capacitance grow with length (the electromagnetism concept), and no signal can be faster than light (the speed of light concept). So L1 stays small enough to answer in 4–5 cycles, L3 is split into slices spread across a ring or mesh, and DRAM sits centimetres away on the board.

mistakes: People often think that a program which reads one byte pays for one byte. In fact every miss moves a whole 64-byte line. Reading one 8-byte field from each 64-byte struct in an array uses only one eighth of the bandwidth spent. A columnar layout that stores that field contiguously uses all of it. The stride of an access pattern matters more than the number of bytes the code appears to touch.
People often think that threads which write different variables cannot slow each other down. In fact coherence works on lines, not variables. If the counters of two threads share one line, every write forces the line to move to the writing core in Modified state, roughly 50–100 ns each time instead of about 1 ns. Code that looks perfectly parallel can run slower on 8 cores than on 1. Padding each counter to its own line (often 128 bytes, because some prefetchers fetch lines in pairs) removes the problem.
People often treat latency and bandwidth as one number. In fact a scan over a large array is limited by bandwidth, because many misses overlap and hide each other's latency. Pointer chasing is limited by latency, because each miss must finish before the next address is known. The same DRAM gives one core about 10–20 GB/s on a sequential scan and under 1 GB/s on a linked list, and faster DRAM bandwidth helps only the first.
People often think a faster CPU will speed up any slow program. A memory-bound program spends most of its cycles waiting for DRAM, and DRAM latency has improved little in twenty years (still about 80–100 ns). A higher clock only makes the core wait for more cycles. Check first with hardware counters: if most cycles are memory stalls, change the data layout, not the hardware.
quiz: What are the three kinds of cache misses? || Compulsory misses happen on the first touch of a line, capacity misses happen when the working set is larger than the cache, and conflict misses happen when too many hot lines map to the same set while other sets still have room.
Why can an L1 cache start its lookup before the TLB has finished translating the address? || The set index and line offset come from address bits 0–11, which lie inside the 4 KB page offset and are identical in the virtual and physical address. The cache selects the set with these bits while the TLB translates the upper bits, and then compares the physical tag.
Why does one core get far less memory bandwidth than the whole socket? || Bandwidth equals bytes in flight divided by latency (Little's law). One core can keep only about 10–20 misses of 64 bytes outstanding, so it gets about 16 × 64 B ÷ 90 ns ≈ 11 GB/s; the socket's hundreds of GB/s need many cores missing at the same time.
An L1 hits 95% of accesses in 1 ns, and its misses cost an average of 28 ns in the lower levels. What is the AMAT, and what is it if the L1 hit rate falls to 90%? || AMAT = 1 + 0.05 × 28 = 2.4 ns. At 90% it becomes 1 + 0.10 × 28 = 3.8 ns, about 58% slower on average, from a five-point drop in hit rate.
Why do chip designers not simply make the L1 cache much larger? || A larger array has longer wires and more tags to compare, so every hit becomes slower, and the L1 hit time sits on the critical path of almost every instruction. Designers keep L1 at 32–64 KB with a 4–5 cycle hit and put larger, slower L2 and L3 caches behind it, trading a little hit rate for a much shorter hit time.

@@+ isolation
terms: Transaction — a group of reads and writes that commits or aborts as one unit.
History (schedule) — the interleaved order in which the operations of concurrent transactions actually ran.
Serializable — a history whose result equals the result of some one-at-a-time order of the same transactions.
Snapshot — a consistent view of the database as of one moment, made of the row versions committed before it.
Conflict — two operations of different transactions on the same item, at least one of them a write.
Anti-dependency (rw edge) — one transaction reads an item and a concurrent transaction writes a newer version of it.
Phantom — a row that appears in, or vanishes from, a range query because another transaction inserted or deleted it.
Write skew — two transactions read overlapping data and write different rows, together breaking a rule that each one checked.
Two-phase locking (2PL) — taking locks as needed and releasing none of them until the transaction ends.
Serialization failure — the error a database returns when it aborts a transaction to keep the history serializable; the client must retry.
how: Most databases implement READ COMMITTED and snapshot isolation with multi-version concurrency control (MVCC). An update does not overwrite a row. It writes a new version tagged with the writing transaction's ID and marks the old version as replaced. In PostgreSQL each row version carries xmin (the transaction that created it) and xmax (the transaction that deleted or replaced it). A snapshot is a short record: the next transaction ID at that moment and the list of transactions still running. A version is visible if its creator committed before the snapshot and its deleter did not. READ COMMITTED takes a new snapshot for each statement; REPEATABLE READ takes one at the first statement and keeps it. Readers never block writers, and writers never block readers. When two snapshot transactions update the same row, PostgreSQL makes the second wait; if the first commits, the second fails with a serialization error ("first updater wins"). This rule stops lost updates on one row. It is also why write skew slips through: the two doctors update different rows, so the rule never fires.
The classic route to SERIALIZABLE is strict two-phase locking. A transaction takes a shared lock before it reads a row and an exclusive lock before it writes one, and holds every lock until commit. Conflicting transactions wait, and a cycle of waits is a deadlock, which the database breaks by aborting one transaction. Row locks alone cannot stop phantoms, because a row that does not exist yet cannot be locked. Locking databases therefore also lock ranges: InnoDB's next-key locks cover an index record and the gap before it, so an insert into a range that another transaction scanned must wait. The price is that readers block writers; a long report holding shared locks stalls every update to the rows it read.
Graph theory turns "is this history serializable?" into a cycle test. Draw one node per committed transaction and an edge Ti → Tj whenever an operation of Ti conflicts with a later operation of Tj on the same item: write then write (ww), write then read (wr: Tj read what Ti wrote), or read then write (rw: Tj overwrote what Ti had read). Each edge says "Ti must come before Tj in any equivalent serial order". If the graph has no cycle, a topological sort gives such an order. If it has a cycle, no order can satisfy every edge. Order theory supplies the meaning: serializability asks whether the partial order made of conflicts can be extended to one total order. Adya's definitions name the levels by the cycles they forbid. READ COMMITTED forbids G0 and G1 (cycles of only ww and wr edges, and reads of aborted or intermediate data). SERIALIZABLE also forbids G2, cycles that contain rw edges. Snapshot isolation sits between them: write skew is a cycle of two rw edges.
Serializable snapshot isolation (SSI) uses a theorem by Fekete and colleagues (2005): every cycle that snapshot isolation allows contains two rw edges in a row, T1 → T2 → T3, where T3 commits first. So PostgreSQL does not build the full graph. Under SERIALIZABLE it records reads with SIRead locks, which never block anyone, and notes for each transaction whether it has an incoming and an outgoing rw edge. When one transaction would become the middle of such a pair, the database aborts a transaction in the pattern. The test is conservative: it also aborts some transactions that were not part of a real cycle. That costs retries but never lets an anomaly through. The overhead is memory for read tracking plus the extra aborts. A long read-only report can avoid aborts by running as SERIALIZABLE READ ONLY DEFERRABLE, which waits until it can take a snapshot that is known to be safe.
Distributed databases add time to the picture. Serializability promises some serial order, not one that matches real time. Strict serializability adds that if T1 commits before T2 starts, T1 comes first in the order. Spanner provides this with TrueTime and commit wait, and CockroachDB uses SERIALIZABLE as its default level. Reads from lagging replicas are the usual way to lose freshness: a follower read can be consistent and serializable yet show data that is seconds old.

mistakes: People often think the SERIALIZABLE keyword always gives serializable behaviour. In Oracle, SERIALIZABLE is in fact snapshot isolation: it prevents lost updates but allows write skew, so the doctor example commits both transactions. Kleppmann's Hermitage tests list what each database's levels really prevent. Check the guarantee, not the keyword, and test the strongest level as carefully as the default.
People often think that putting code between BEGIN and COMMIT makes a read-modify-write safe. Under READ COMMITTED, the default in PostgreSQL, two transactions can both read a balance of 100, both compute 100 − 30 in the application, and both write 70: one withdrawal is lost. MySQL's REPEATABLE READ allows the same loss, because its UPDATE writes over the latest version without checking that the row changed after the snapshot. Only an atomic UPDATE balance = balance − 30, a SELECT … FOR UPDATE, or a level that detects the conflict prevents it.
People often think SERIALIZABLE means transactions run one at a time, so it must be very slow. In fact it means the result equals some serial order; the transactions still run concurrently. Under SSI, transactions that touch unrelated data do not wait for each other at all. The real cost appears under contention, as aborts and retries, and it grows with how much data the transactions read and write in common.
People often think a serializable database never returns stale data. Serializability allows a read-only transaction to be placed before a write that has already committed, as long as the whole history has one valid order. The guarantee that also respects real time is strict serializability (Spanner calls it external consistency). Follower reads and caches can give answers that are serializable and still stale.
quiz: Which anomaly does snapshot isolation allow that SERIALIZABLE prevents? || Write skew. Two transactions read overlapping data from their snapshots, each decides from what it saw, and they write different rows, so no write–write conflict is detected and together they break an invariant.
Why does a cycle in the conflict graph mean that a history is not serializable? || Each edge Ti → Tj says Ti must come before Tj in any equivalent serial order. A cycle demands that some transaction come before itself, so no serial order satisfies every edge; an acyclic graph can be topologically sorted into one.
How does PostgreSQL's serializable snapshot isolation detect danger without building the whole conflict graph? || It records reads with non-blocking SIRead locks and tracks, for each transaction, incoming and outgoing read–write anti-dependencies. When a transaction would have both (two rw edges in a row, the pattern every snapshot-isolation anomaly needs), it aborts one transaction with a serialization failure.
Two transactions under READ COMMITTED each read stock = 1 for the same item and then run UPDATE items SET stock = 0 and insert an order. What happens, and how do you fix it? || Both see stock = 1, both write 0 and both insert an order, so one item is sold twice. Fix it with an atomic conditional update (UPDATE items SET stock = stock − 1 WHERE id = ? AND stock > 0, then check the affected row count), with SELECT … FOR UPDATE, or with SERIALIZABLE and retries.
When would you choose SELECT … FOR UPDATE over SERIALIZABLE with retries? || Explicit locks suit a few known hot rows: conflicting transactions wait instead of aborting, so no retry loop is needed, but someone can forget a lock and deadlocks remain possible. SERIALIZABLE suits invariants that span many rows or queries you cannot list in advance, at the cost of retry logic and wasted work on aborts.

@@+ gc
terms: Root — a reference the program can use directly: a local variable in a stack frame, a register, a static field or a native handle.
Reachable object — an object that can be reached from a root by following references; only these objects are live.
Mark-sweep — mark every reachable object, then free each unmarked object where it lies.
Copying collector — copy the live objects into an empty space and then reuse the whole old space.
Generational hypothesis — the observation that most objects die young, so young objects deserve frequent, cheap collections.
Write barrier — a few instructions the compiler adds to every reference store so the collector can track pointer changes.
Card table — a byte array with one entry per 512-byte card of the old generation, marking cards that may hold old-to-young pointers.
Tri-colour marking — tracking objects as white (not seen), grey (seen, not scanned) or black (scanned) so that marking can run concurrently.
Safepoint — a point in the code where a thread can stop and the collector knows exactly which slots hold references.
Stop-the-world pause — a period during which all application threads are stopped so the collector can work.
how: Marking is a graph traversal, which is what graph theory contributes. Objects are nodes, references are edges, and the roots are the starting set. The collector pushes each root onto a mark stack, then repeatedly pops an object, sets its mark bit and pushes every unmarked object it points to. When the stack is empty, every reachable object is marked. The cost is proportional to the number of live objects and references, not to the heap size: a 32 GB heap with 2 GB of live data costs about as much to mark as a 4 GB heap with the same 2 GB. Sweeping, which walks the heap to free unmarked objects, is proportional to heap size, so many collectors sweep lazily or copy instead. Cheney's copying collector does the traversal breadth-first with no stack at all, because the objects already copied into the new space form the queue.
Moving objects pays off at allocation time. After copying or compaction, free space is one contiguous block, so allocation is a pointer bump: check that pointer + size ≤ limit, return the pointer, add the size. Each thread gets its own thread-local allocation buffer (TLAB), so the bump needs no lock and costs a few instructions. A non-moving collector must keep free lists of holes of many sizes, which is slower and fragments over time: after a long run, the heap may have 1 GB free in total and still no hole large enough for one 10 MB array.
A simple model explains the trade between memory and CPU. Let L be the live data, H the heap size and A the allocation rate. Each collection can reclaim at most H − L, so a collection happens every (H − L) ÷ A seconds, and each one costs work proportional to L. GC work per second is therefore proportional to A × L ÷ (H − L). With L = 2 GB and A = 1 GB/s, a 4 GB heap collects every 2 seconds and an 8 GB heap every 6 seconds: three times less GC work for the same program. Generational collection applies the model to the young generation, where L (the survivors) is tiny. The model also shows why GC CPU explodes when live data approaches the heap limit: as H − L falls towards zero, the collector runs almost all the time.
Generational collection must find old-to-young pointers without scanning the old generation. The JIT compiler adds a write barrier after every reference store. HotSpot divides the old generation into 512-byte cards with one byte per card in a card table, and the barrier marks the card of the updated object as dirty. A young collection then treats the objects in dirty cards as extra roots. G1 goes further and keeps a remembered set per region, listing the cards that point into that region, so it can collect any chosen group of regions.
Concurrent marking uses three colours: white (not yet seen), grey (seen, but its references not yet scanned) and black (seen and fully scanned). Marking ends when no grey objects remain, and the white objects are garbage. The danger is that the program keeps changing pointers while marking runs. If it stores a reference to a white object into a black object, and also removes the last path to that object from every grey object, the collector never visits it and frees a live object. Barriers prevent this. An incremental-update barrier (Dijkstra) shades the newly stored target grey. A snapshot-at-the-beginning barrier (Yuasa, used by G1) records the old value being overwritten, so everything reachable when marking started is kept. Go uses a hybrid of the two.
To scan roots, the collector must know which stack slots and registers hold references. The compiler in the language runtime emits stack maps for safepoints, the places where a thread may stop, such as method returns and loop back-edges. A stop-the-world pause first waits until every thread reaches a safepoint; a long loop without a safepoint check can delay all other threads. ZGC and Shenandoah mark and move most objects concurrently and keep their pauses to short root-scanning steps, typically under a millisecond.

mistakes: People often think a garbage-collected program cannot leak memory. The collector frees only unreachable objects. An object that is still referenced but never used again stays alive forever: an entry in a static map, a listener that is never removed, a ThreadLocal in a pooled thread. Such leaks show up as an old generation that is a little larger after each full collection, and a heap dump that shows who holds the references finds them.
People often think GC cost is proportional to the amount of garbage. For tracing collectors it is the other way round: the work is proportional to the live objects that must be marked or copied. A young collection that finds 30 MB alive in 2 GB costs about the same as one that finds 30 MB alive in 200 MB, because the dead objects are never touched; their space is reused whole. Allocating many short-lived objects is cheap; keeping many objects alive is expensive.
People often think a bigger heap always means longer pauses. With generational and concurrent collectors, a bigger heap usually means fewer collections and less GC CPU, as the headroom model shows. Pause time depends on the live data in the region being collected and on root scanning, not on total heap size. The exception is a full stop-the-world collection, whose cost grows with the live heap, so a well-run service should never need one.
People often think reference counting has no pauses. Freeing is immediate, but dropping the last reference to a large structure, such as a dictionary with 10 million entries, frees all 10 million objects at that moment, which can take a noticeable fraction of a second. In multithreaded code, every count change on a shared object needs an atomic instruction that costs tens of cycles and moves the cache line between cores; this cost is one reason CPython kept a global interpreter lock for so long.
quiz: What are GC roots, and why does the collector start from them? || Roots are the references the program can use directly: the stack slots and registers of every thread, static fields and native handles. Any object the program could still use must be reachable from a root, so everything not reached from them is garbage.
Why does a generational collector need a write barrier? || A young collection scans only the young generation and the roots, but an old object may hold the only reference to a young one. The write barrier marks the card of every object whose reference field changes, so the collector scans just those dirty cards as extra roots instead of the whole old generation.
How can concurrent marking free a live object if there are no barriers? || The program can store a reference to a white (unvisited) object into a black (already scanned) object and remove the last path to it from the grey objects. The collector then never visits it and frees it. Barriers either shade the new target grey (incremental update) or record the overwritten reference (snapshot at the beginning).
A service has 3 GB of live data and allocates 500 MB/s. How often does a collection run with a 4 GB heap and with a 6 GB heap, and how does the GC work change? || Each collection can reclaim at most heap minus live data: 1 GB or 3 GB. Collections run every 1 GB ÷ 0.5 GB/s = 2 s with 4 GB, and every 6 s with 6 GB. Each one still marks about 3 GB, so GC work per second falls about three times with the larger heap.
Which JVM collectors fit a nightly Spark batch job and a latency-sensitive API, and why? || The batch job cares about total throughput, so the Parallel collector or G1, with occasional longer pauses, gives the most work per CPU. The API cares about tail latency, so generational ZGC (or Shenandoah) keeps pauses under a millisecond, at the cost of some CPU for barriers and more heap headroom.

terms: Vector space — a set of objects that can be added and scaled by numbers, following the usual rules of algebra.
Linear map — a function with f(ax + by) = a·f(x) + b·f(y); every linear map from ℝⁿ to ℝᵐ is an m × n matrix.
Basis — a set of independent vectors such that every vector is exactly one combination of them.
Rank — the number of independent directions a matrix can output, the dimension of its column space.
Inner product — a·b = Σ aᵢbᵢ; it measures alignment, and the length is ‖a‖ = √(a·a).
Eigenvector — a nonzero vector v with Av = λv; the matrix only scales it, by the eigenvalue λ.
Orthogonal matrix — a matrix Q with QᵀQ = I; it rotates or reflects vectors without changing lengths or angles.
Singular value decomposition (SVD) — A = UΣVᵀ for any matrix: rotate, scale along the axes by the singular values, rotate again.
Condition number — κ = σ_max ÷ σ_min, the most a matrix can amplify relative errors in its input.
Low-rank approximation — replacing a matrix by the product of two thin matrices that keeps its largest singular values.
how: The definitions are short and worth knowing exactly. A vector space is a set of vectors that you can add and scale, with the usual rules such as a(x + y) = ax + ay. A map f is linear when f(ax + by) = a·f(x) + b·f(y). Every linear map from ℝⁿ to ℝᵐ is an m × n matrix, and the matrix is easy to read: column j is where the map sends the j-th basis vector eⱼ. So a 3 × 2 matrix sends 2D vectors into 3D space, and the product AB means "apply B first, then A". The rank of A is the dimension of its column space, the set of all its outputs. The rank–nullity theorem says rank + nullity = n, where the nullity is the dimension of the set of inputs that A sends to zero. A 4096 × 4096 matrix of rank 16 squeezes every input into a 16-dimensional subspace and loses everything in the other 4,080 directions.
Eigenvectors are the directions a matrix does not turn. For a symmetric matrix (A = Aᵀ), such as a covariance matrix or a graph Laplacian, the spectral theorem guarantees real eigenvalues and a full set of perpendicular unit eigenvectors, so A = QΛQᵀ with Q orthogonal and Λ diagonal. In that basis the matrix is just independent scalings along perpendicular axes, which is why PCA can rank directions by variance. Power iteration finds the top eigenvector by repeating x ← Ax ÷ ‖Ax‖. Each step shrinks every other component, relative to the top one, by the factor |λ₂ ÷ λ₁|, so the gap between the two largest eigenvalues sets the speed. For PageRank with damping factor 0.85, |λ₂| ≤ 0.85, so 50 iterations shrink the error by about 0.85⁵⁰ ≈ 3 × 10⁻⁴.
The SVD works for every matrix, of any shape: A = UΣVᵀ, where U and V have orthonormal columns and Σ is diagonal with singular values σ₁ ≥ σ₂ ≥ … ≥ 0. The Eckart–Young theorem (1936) says that keeping only the k largest singular values gives the best rank-k approximation, and the error in the Frobenius norm is √(σ²ₖ₊₁ + … + σ²ᵣ). So the singular values tell you directly what a rank-k compression loses, before you build it.
Numbers on a computer are rounded, and linear algebra can amplify rounding. The condition number κ(A) = σ₁ ÷ σₙ bounds how much A can magnify a relative error in its input; when you solve Ax = b, you lose roughly log₁₀ κ decimal digits. float32 carries about 7 digits and float64 about 16, so a system with κ = 10⁶ keeps about 1 correct digit in float32 and about 10 in float64. Least squares through the normal equations AᵀAx = Aᵀb squares the condition number, which is why solvers use QR (A = QR with Q orthogonal) or the SVD instead. Gaussian elimination (LU factorization) solves an n × n system in about (2/3)n³ operations. Strassen's algorithm (1969) multiplies matrices in about n^2.81 operations, but it is rarely used, because it is less stable and the blocked n³ method uses caches and tensor cores better.
The two lower concepts in the map explain why so much of the world is linear. Quantum mechanics is linear algebra over complex numbers: a state is a unit vector, an observable is a Hermitian matrix (equal to its own conjugate transpose), the possible measurement results are its eigenvalues, and the probability of each result is the squared length of the state's projection onto the matching eigenvector (the Born rule). Maxwell's equations are linear, so the sum of two solutions is again a solution (superposition). That is why a radio signal can be split into independent frequency components, and why a multi-antenna (MIMO) radio link is modelled as a channel matrix that the receiver inverts. Wherever the underlying physics is linear, or nearly linear, matrices are the natural description.

mistakes: People often treat matrix multiplication like multiplication of numbers. It is not commutative: AB and BA are usually different, and may not even have the same shape. AB means "apply B, then A", and rotating a vector and then stretching one axis gives a different result from stretching first. Many shape bugs in model code come from this.
People often solve Ax = b by computing A⁻¹ and multiplying. Explicit inversion costs about three times as much as solving with an LU factorization, and it is less accurate when the matrix is badly conditioned. Libraries solve directly from a factorization (numpy.linalg.solve, torch.linalg.solve, or lstsq for least squares); an explicit inverse is rarely needed.
People often think every square matrix has a full set of eigenvectors. Some do not: the shear [[1, 1], [0, 1]] has only one eigenvector direction, and a rotation of the plane by 90° has no real eigenvectors at all. The SVD, in contrast, exists for every matrix of any shape, which is why it, and not eigen-decomposition, is the standard tool for data matrices.
People often use the dot product and cosine similarity as if they were the same. They agree only when all vectors have length 1. With raw dot products, long vectors (for example popular items in a recommender) score high against everything. An index built for maximum inner product returns different neighbours from one built for cosine, so decide deliberately whether to normalize embeddings, and do it the same way at indexing and at query time.
quiz: What does the rank of a matrix tell you? || The number of independent directions in its output, the dimension of its column space. An n × n matrix of rank r maps every input into an r-dimensional subspace, and by rank–nullity it sends an (n − r)-dimensional set of inputs to zero.
Why does power iteration converge to the top eigenvector, and what sets its speed? || Write the start vector as a combination of eigenvectors. Each multiplication by A scales each component by its eigenvalue, so the component with the largest |λ| grows fastest. The other components shrink relative to it by |λ₂ ÷ λ₁| per step, so a large gap between the two largest eigenvalues means fast convergence.
Why is the truncated SVD the right tool for compressing a matrix? || The Eckart–Young theorem says that keeping the k largest singular values and their vectors gives the best possible rank-k approximation, with Frobenius error equal to the square root of the sum of the discarded squared singular values. The singular values therefore show exactly what each extra dimension buys.
A 4096 × 4096 weight matrix is fine-tuned with LoRA of rank 16. How many trainable numbers does that need instead of the full update? || The full update has 4096² ≈ 16.8 million numbers. LoRA trains B (4096 × 16) and A (16 × 4096): 2 × 65,536 = 131,072 numbers, about 0.8% of the full count.
Why do numerical libraries solve least squares with QR or the SVD instead of the normal equations AᵀAx = Aᵀb? || Forming AᵀA squares the condition number, so a problem with κ = 10⁴ becomes one with κ = 10⁸ and loses about 8 digits instead of 4, which wipes out float32 accuracy. The normal equations are faster and fine for small, well-conditioned problems; QR and the SVD cost more but stay accurate.

@@+ probability
terms: Sample space (Ω) — the set of all possible outcomes of an experiment.
Event — a subset of the sample space, such as "at least one disk fails today".
Random variable — a function that gives a number for each outcome, such as the count of failed disks.
Distribution — the rule that gives the probability of each value (PMF) or the density of values (PDF) of a random variable.
Expectation — the probability-weighted average E[X] = Σ x·P(X = x).
Variance — E[(X − E[X])²], the expected squared distance from the mean; its square root is the standard deviation σ.
Conditional probability — P(A | B) = P(A ∩ B) ÷ P(B), the probability of A once B is known to have happened.
Independence — P(A ∩ B) = P(A)·P(B); knowing one event tells you nothing about the other.
Union bound — P(A₁ ∪ … ∪ Aₙ) ≤ P(A₁) + … + P(Aₙ), true with or without independence.
Tail — the part of a distribution far from its centre; a heavy tail decays slowly, like a power law.
how: Kolmogorov's axioms (1933) are where set theory contributes. A probability space has a sample space Ω, a collection of events (subsets of Ω, closed under complement and countable unions, called a σ-algebra) and a function P with three rules: P(A) ≥ 0 for every event; P(Ω) = 1; and for disjoint events A₁, A₂, …, P(A₁ ∪ A₂ ∪ …) = P(A₁) + P(A₂) + …. Everything else is derived. Events are sets, so "A and B" is the intersection, "A or B" the union and "not A" the complement, and a rule such as P(A ∪ B) = P(A) + P(B) − P(A ∩ B) is a statement about overlapping sets. The σ-algebra matters for continuous spaces, where it is impossible to give a consistent probability to every subset.
Conditional probability is defined, not assumed: P(A | B) = P(A ∩ B) ÷ P(B). It restricts the world to the outcomes where B happened and rescales them to total 1. Independence means P(A ∩ B) = P(A)·P(B), which is the same as P(A | B) = P(A). The law of total probability, P(A) = Σ P(A | Bᵢ)·P(Bᵢ) over a partition B₁, B₂, …, splits a hard question into cases. Bayes' rule, P(B | A) = P(A | B)·P(B) ÷ P(A), reverses a conditional, and it follows in one line from the definition.
A random variable is a function X: Ω → ℝ, such as "number of failed disks today". Its expectation is E[X] = Σ x·P(X = x), and its variance is Var(X) = E[(X − E[X])²] = E[X²] − E[X]². Linearity of expectation, E[X + Y] = E[X] + E[Y], holds even when X and Y depend on each other. Variance adds only when there is no covariance: Var(X + Y) = Var(X) + Var(Y) + 2·Cov(X, Y). From these two facts comes the most used result in measurement: the average of n independent samples, each with standard deviation σ, has standard deviation σ ÷ √n. Four times more samples halve the error.
Indicator variables make counting problems short. To find the expected number of hash collisions among n keys in m buckets, define one indicator for each pair of keys, equal to 1 if the pair collides, which happens with probability 1/m. There are n(n − 1)/2 pairs, so the expected number of colliding pairs is n(n − 1) ÷ 2m, with no independence needed. With n = 100,000 keys and m = 2³² hash values, that is about 1.16 colliding pairs: the birthday bound in one line.
Tail bounds say how unlikely a large deviation is. Markov's inequality, P(X ≥ a) ≤ E[X] ÷ a for a non-negative X, needs only the mean. Chebyshev's inequality, P(|X − μ| ≥ kσ) ≤ 1 ÷ k², needs the variance. Chernoff bounds, for sums of independent bounded variables, fall exponentially, so a sum far from its mean is extremely rare. The union bound needs nothing at all, which makes it the usual tool for "any of 10,000 machines" questions.
The same mathematics carries two readings, and epistemology is where the choice between them lives. Frequentists read P(A) as the long-run fraction of trials in which A happens; Bayesians read it as a degree of belief that evidence updates. Both obey Kolmogorov's rules, so the calculations agree, and the readings differ in which questions they allow (a Bayesian may give a probability for "this release has a bug"; a frequentist may not). Quantum mechanics adds randomness at the physical level: the Born rule gives each measurement outcome a probability equal to the squared magnitude of its amplitude, and some hardware random-number generators measure such effects to produce bits that no algorithm can predict.

mistakes: People often confuse P(A | B) with P(B | A). A fraud model flags 99% of fraudulent devices and wrongly flags 1% of honest ones, and 0.1% of devices are fraudulent. Then P(fraud | flagged) = 0.99 × 0.001 ÷ (0.99 × 0.001 + 0.01 × 0.999) ≈ 0.00099 ÷ 0.011 ≈ 9%. Ignoring the base rate makes a "99% accurate" detector look far better than it is: about nine alerts in ten are false.
People often think linearity of expectation needs independence. It does not: E[X + Y] = E[X] + E[Y] always holds. What needs independence is the variance of a sum and the probability of a joint event. Confusing the two leads either to avoiding easy proofs or to multiplying probabilities of events that are in fact correlated.
People often think that uncorrelated means independent. Correlation measures only a linear relation. If X is uniform on [−1, 1] and Y = X², their correlation is 0, yet Y is completely determined by X. Feature selection or alert logic that drops "uncorrelated" signals can drop strongly dependent ones.
People often think that a one-in-a-billion event will not happen. At scale it happens every day: a bug that corrupts 1 request in 10⁹ hits a service that handles 10¹⁰ requests a day about 10 times a day. A per-event probability means little until it is multiplied by volume and time, and the union bound gives a quick upper estimate of "at least once".
quiz: State Kolmogorov's three axioms of probability. || Every event has probability at least 0; the whole sample space has probability 1; and the probability of a union of disjoint events (even countably many) is the sum of their probabilities. All other rules follow from these three.
Why does the error of an average fall like 1/√n and not like 1/n? || For n independent samples with standard deviation σ, the variance of the sum is nσ² because variances add, so the sum's standard deviation is σ√n. Dividing the sum by n gives the average a standard deviation of σ√n ÷ n = σ ÷ √n.
How does linearity of expectation give the expected number of hash collisions without assuming independence? || Define one indicator per pair of keys, equal to 1 if the pair collides, with probability 1/m. The expected count is the sum of the indicators' expectations, n(n − 1)/2 × 1/m, and linearity holds even though the indicators depend on each other.
A fleet has 10,000 disks with an annual failure rate of 2%. How many failures do you expect per day, and how likely is a day with at least one? || Expected failures per day = 10,000 × 0.02 ÷ 365 ≈ 0.55. Modelling the count as Poisson, P(no failure) = e^(−0.55) ≈ 0.58, so about 42% of days have at least one failure.
When is the union bound good enough, and when do you need an exact calculation or a simulation? || It is quick and safe when the events are rare: for 1,000 machines that each fail with probability 10⁻⁵ in an hour, P(any failure) ≤ 1%, very close to the exact 0.995%. When the events are common the sum can exceed 1 and tell you nothing, and when you need the chance that several fail together (which depends on correlation) you must model the dependence exactly or simulate it.

@@+ infotheory
terms: Bit — the information in one fair yes-or-no choice; the unit of entropy when logarithms are base 2.
Self-information — −log₂ p, the surprise of an outcome that has probability p.
Entropy — H(X) = −Σ p(x) log₂ p(x), the average surprise and the lower limit for lossless compression.
Cross-entropy — H(p, q), the average number of bits needed to encode data from p with a code built for q.
KL divergence — KL(p ‖ q) = H(p, q) − H(p), the extra bits paid for using the wrong model; it is never negative.
Mutual information — I(X; Y), how many bits knowing Y saves, on average, when describing X.
Prefix code — a code in which no codeword begins another, so a stream can be decoded without separators.
Channel capacity — the highest rate at which a noisy channel can carry data with as few errors as you want.
Perplexity — 2^H, the effective number of equally likely choices a model hesitates between.
Nat — the unit when natural logarithms are used; 1 nat = 1.443 bits.
how: The logarithm is not an arbitrary choice. Shannon asked for a measure of information I(p) that depends only on the probability, falls as p grows, and adds up for independent events: learning two independent facts with probabilities p and q should give I(p) + I(q) = I(pq). The only continuous functions with that property are I(p) = −c·log p. Base 2 makes the unit the bit: a fair coin flip carries exactly 1 bit, and one of 256 equally likely bytes carries 8 bits. Entropy is the expected value of I under the distribution, which is how probability enters: entropy is expected surprise.
The source coding limit comes from the law of large numbers. Take n independent symbols from a source with entropy H. Almost every long sequence the source produces has probability close to 2^(−nH), and there are about 2^(nH) of these "typical" sequences; all other sequences together have a probability that shrinks towards zero as n grows. Numbering the typical sequences takes about nH bits, so nH bits are enough. Fewer cannot work, because there would not be enough short codewords to name all the likely sequences. For the 1.2-bit device column in the example, a block of 1,000 events has about 2^1200 likely values out of 4^1000 = 2^2000 possible ones.
Practical codes are built from codeword lengths. In a prefix code no codeword begins another, so a stream decodes without separators. Kraft's inequality says a prefix code with lengths l₁ … l_k exists exactly when Σ 2^(−lᵢ) ≤ 1, so lengths behave like a probability budget, and the ideal length for a symbol is −log₂ p. That ideal is usually not a whole number. Huffman's algorithm finds the best whole-number lengths and wastes less than 1 bit per symbol, which is a lot for skewed sources: a symbol with p = 0.99 ideally costs 0.015 bits, but Huffman must spend 1. Arithmetic coding and asymmetric numeral systems (ANS, by Jarek Duda) spend fractional bits per symbol and get very close to H. Zstd uses a table-based ANS called FSE for its match offsets and lengths, and Huffman for literal bytes.
Convexity supplies the inequality behind most proofs in the field. Gibbs' inequality says KL(p ‖ q) = Σ p log₂(p/q) ≥ 0, with equality only when p = q. The proof is Jensen's inequality for the concave function log: Σ p log(q/p) ≤ log Σ p·(q/p) = log Σ q = log 1 = 0. This one fact shows that cross-entropy H(p, q) = H(p) + KL(p ‖ q) is never below H(p): a model can match the true distribution but never beat it. It also shows that mutual information, I(X; Y) = KL(p(x, y) ‖ p(x)p(y)), is never negative: on average, extra information never increases uncertainty.
On the channel side, the simplest case shows the trade. A binary symmetric channel flips each bit with probability f, and its capacity is C = 1 − H(f) bits per use. With f = 0.11, H(0.11) ≈ 0.5, so at most half of the transmitted bits can carry data and the rest must be redundancy. The noise in the Shannon–Hartley formula is physical (the thermal noise concept): random thermal motion of electrons in a receiver adds noise power of about kTB, roughly −174 dBm per hertz of bandwidth at room temperature, so a weaker signal or a wider band directly lowers S/N. Landauer's principle puts a floor under computing itself: erasing one bit at temperature T must dissipate at least kT ln 2, about 2.9 × 10⁻²¹ J at 300 K. That is roughly 10,000 times less than the energy of one transistor switch in a current chip, so today's hardware is far from this limit, but the limit shows that information always has a physical carrier and a physical cost.

mistakes: People often think a clever enough compressor can shrink any file. No lossless compressor can shrink every input: there are 2ⁿ files of n bits but only 2ⁿ − 1 shorter bit strings, so some inputs must stay the same size or grow. Compression works only when the model makes some data much more likely than other data. Random data, encrypted data and already compressed data look uniform to any practical model, so compress before you encrypt, never after.
People often treat KL divergence as a distance. It is not symmetric: KL(p ‖ q) and KL(q ‖ p) differ, and neither obeys the triangle inequality. The direction changes behaviour. Minimizing KL(data ‖ model), which is what cross-entropy training does, punishes the model hard for giving low probability to anything real, so it spreads probability widely (mode covering). Minimizing KL(model ‖ target), used in some distillation and RLHF objectives, punishes probability on what the target rejects, so the model concentrates on a few modes (mode seeking).
People often mix up the units. The cross-entropy losses in PyTorch and TensorFlow use natural logarithms, so they report nats, not bits. A loss of 2.0 nats is 2.0 × 1.443 ≈ 2.9 bits per token, and perplexity is e^loss in those units, not 2^loss. Compare runs only in the same unit and with the same tokenizer, because bits per token change when tokens get longer.
People often think the Shannon limit can be beaten with better modulation. Capacity is a theorem about every possible code, not a property of today's codes; above it, errors cannot be made small. The only ways to raise capacity are more bandwidth or a better signal-to-noise ratio, and at high S/N doubling the signal power adds only about 1 bit per second per hertz, because capacity grows with the logarithm of S/N.
quiz: What is the entropy of a fair coin, of a fair 8-sided die, and of a coin that lands heads 90% of the time? || 1 bit, 3 bits, and −(0.9 log₂ 0.9 + 0.1 log₂ 0.1) ≈ 0.47 bits. The biased coin is more predictable, so each flip carries less information.
Why can no lossless compressor beat the entropy of the source on average? || For long sequences, about 2^(nH) typical sequences carry almost all the probability, each with probability near 2^(−nH). Naming them needs about nH bits; with fewer bits there are not enough codewords, so some likely sequences would share a code and could not be decoded.
Why does minimizing cross-entropy loss push a model's predictions towards the data distribution? || Cross-entropy equals H(p) + KL(p ‖ q), where p is the data distribution and q the model. H(p) does not depend on the model, and KL(p ‖ q) ≥ 0 with equality only when q = p (Gibbs' inequality, from Jensen), so the loss is lowest exactly when the model's probabilities equal the data's.
A link has 20 MHz of bandwidth and a signal-to-noise ratio of 30 dB. What is its Shannon capacity? || 30 dB means S/N = 1,000. C = 20 × 10⁶ × log₂(1 + 1,000) ≈ 20 × 10⁶ × 9.97 ≈ 199 Mbit/s, and no modulation or code can carry more without errors.
When would you choose Huffman coding over arithmetic coding or ANS? || Huffman is simple and very fast to decode with table lookups, and it loses little when no symbol is very likely. Arithmetic coding or ANS is worth the extra complexity when the distribution is skewed: for a symbol with probability 0.99, Huffman must still spend 1 bit, while the ideal cost is about 0.015 bits.

@@+ queueing
terms: Arrival rate (λ) — the average number of jobs that arrive per second.
Service rate (μ) — the number of jobs one server can finish per second; the mean service time is 1/μ.
Utilization (ρ) — λ ÷ (c·μ) for c servers, the fraction of time the servers are busy; a stable queue needs ρ < 1.
Little's law — L = λW: the average number in the system equals the arrival rate times the average time spent inside.
Kendall notation — A/S/c, naming the arrival process, the service-time distribution and the number of servers (M = memoryless, D = fixed, G = general).
Coefficient of variation (C) — standard deviation divided by the mean; C² = 1 for exponential times and 0 for fixed ones.
Tail latency — a high percentile of response time, such as p99, the time that 1% of requests exceed.
Open system — a system in which new requests arrive no matter how many are already waiting, like real users of a website.
Load shedding — rejecting work early when queues grow, so that the accepted work still finishes on time.
Back-pressure — slowing the producers when consumers fall behind, so that queues stay bounded.
how: The M/M/1 results come from a Markov chain, which is what the stochastic processes concept contributes. In Kendall's A/S/c notation, A is the arrival process, S the service-time distribution and c the number of servers; M means memoryless (Poisson arrivals or exponential service), D deterministic and G general. In M/M/1, the state is the number of jobs n. Arrivals move it up at rate λ and completions move it down at rate μ. In steady state the flow between neighbouring states balances, λ·p(n) = μ·p(n + 1), so p(n) = (1 − ρ)ρⁿ, a geometric distribution. Its mean is L = ρ ÷ (1 − ρ), and Little's law turns that into W = L ÷ λ = 1 ÷ (μ − λ). The probability that an arriving job finds the server busy is ρ itself.
Variability enters through the Pollaczek–Khinchine formula. For one server with Poisson arrivals and any service distribution (M/G/1), the mean wait in the queue is Wq = ρ ÷ (1 − ρ) × E[S] × (1 + C²) ÷ 2, where C is the coefficient of variation of the service time. Fixed service times (C = 0) wait half as long as exponential ones (C = 1). For the slow-message mix in the example (99% of messages at 4 ms, 1% at 200 ms), the mean is about 6 ms but C² is about 10.7, so the queueing delay is about 5.9 times what an exponential service with the same mean would give. Kingman's approximation for a general single server adds the arrival variability the same way: Wq ≈ ρ ÷ (1 − ρ) × (Cₐ² + Cₛ²) ÷ 2 × E[S]. Utilization, variability and service time multiply, so reducing any one of them helps.
Pooling is the strongest free improvement. Erlang's C formula for M/M/c gives the chance that an arrival finds all c servers busy. Take the Kafka example at 1,750 messages per second (ρ = 0.875). If each of the 8 threads had its own queue with a random eighth of the traffic, each would be an M/M/1 queue with T = 4 ms ÷ (1 − 0.875) = 32 ms. With one shared queue (M/M/8), an arrival waits only when all 8 threads are busy, which happens about 64% of the time, and the mean time in the system is about 6.5 ms. The hardware and the load are the same; the latency is five times lower.
Tails follow from the same model. For M/M/1, the response time is exponential with rate μ − λ, so P(T > t) = e^(−(μ − λ)t) and p99 = ln 100 ÷ (μ − λ), about 4.6 times the mean. Fan-out multiplies exposure to the tail. If a request waits for 100 backends and each one is slower than its own p99 with probability 1%, the chance that all 100 are fast is 0.99¹⁰⁰ ≈ 37%, so 63% of user requests meet at least one p99-slow backend.
Queueing time adds to delays that no capacity can remove. End-to-end latency = propagation (distance ÷ signal speed) + transmission (size ÷ bandwidth) + queueing + service. The speed of light fixes the first term; utilization controls the queueing term. A cross-region call with a 70 ms round trip and 5 ms of service is dominated by distance at low load and by queueing near saturation, and only the second part responds to more servers.

mistakes: People often think a server at 50% average CPU has plenty of room. An average over a minute hides bursts: traffic that arrives at twice the mean rate for 10 seconds of every minute runs the server at 100% during the burst, and queues build exactly then. Measure utilization and queue length at the time scale of the latency target (seconds, not minutes), and look at peak periods.
People often think Little's law needs Poisson arrivals or exponential service. It needs only a stable system, where long-run arrivals equal departures, and it holds for any distribution, any order of service and any boundary you draw: one thread pool, a whole service or a Kafka consumer group. That is why it is safe for sizing pools, while the M/M/1 formulas are only approximations.
People often think several servers with separate queues are as good as one shared queue. Separate queues let one server sit idle while another has a line, as the pooling numbers show (32 ms against 6.5 ms). Random load balancing across backends creates separate queues; routing to the least loaded backend, the "power of two choices" (pick the less busy of two random backends) or a shared work queue recovers most of the benefit.
People often trust load tests in which a fixed number of clients each send the next request only after the previous one returns. That is a closed system: when the server slows down, the clients slow down too, so the queue never builds and latency looks good. Real users form an open system and keep arriving. A tool that also starts its timer only when a request is actually sent hides the waiting completely (Gil Tene calls this coordinated omission). Test latency with a fixed arrival rate.
quiz: State Little's law and what it requires. || L = λW: the average number of items in a system equals the average arrival rate times the average time each item spends inside. It requires only a stable system, with no assumption about distributions or the order of service.
Why does waiting time grow without limit as utilization approaches 100%? || Random arrivals come in bursts, and a queue built in a burst drains only during idle time. At utilization ρ the server is idle only a fraction 1 − ρ of the time, so draining stretches like 1 ÷ (1 − ρ); for M/M/1 the time in the system is S ÷ (1 − ρ), which goes to infinity as ρ approaches 1.
Why does one shared queue for 8 workers give much lower latency than 8 separate queues? || With separate queues a job can wait behind a busy worker while another worker is idle. With a shared queue a job waits only when all 8 workers are busy, which is much rarer. At ρ = 0.875 and 4 ms service, separate M/M/1 queues give about 32 ms, and one M/M/8 queue about 6.5 ms.
A service receives 2,000 requests per second, and each request holds a database connection for 150 ms. What pool size does it need, and what happens with 200 connections? || By Little's law the average number of connections in use is 2,000 × 0.15 s = 300, so the pool needs more than 300 to leave headroom. With 200 connections it can serve at most 200 ÷ 0.15 ≈ 1,333 requests per second, so requests queue for connections and the wait grows until load falls.
Why is it often better to reject some requests near saturation than to let the queue grow? || Past saturation every queued request waits longer, many time out after the server has already spent work on them, and clients retry, so useful throughput falls while load rises. Shedding load early keeps the accepted requests fast and the system stable; the cost is visible errors for the rejected requests, which clients must handle with backoff.

@@+ lightspeed
terms: c — the speed of light in vacuum, exactly 299,792,458 m/s because the metre is defined from it.
Refractive index (n) — how many times slower light travels in a material than in vacuum; about 1.47 for the glass in optical fibre.
Permittivity (εᵣ) — how strongly the charges in a material respond to an electric field; higher permittivity means slower waves.
Velocity factor — the signal speed in a cable or circuit-board trace as a fraction of c, typically 0.5–0.9.
Propagation delay — the time a signal needs to cover a distance: distance ÷ signal speed.
Round-trip time (RTT) — the time for a message to go and a reply to come back; at least twice the propagation delay.
Path stretch — how much longer the real route is than the straight-line (great-circle) distance.
Bandwidth-delay product — bandwidth × RTT, the amount of data in flight on a path that is running at full speed.
Clock uncertainty — the bound on how far a machine's clock may be from true time, limited partly by message delays.
how: Maxwell's equations explain both the number and the slowdown, which is what the electromagnetism concept contributes. The equations combine into a wave equation whose speed is c = 1 ÷ √(μ₀ε₀), where μ₀ and ε₀ are the magnetic and electric constants of empty space. That value matched the measured speed of light, which is how Maxwell concluded in 1865 that light is an electromagnetic wave. In a material the wave travels at v = c ÷ n, and for non-magnetic materials n ≈ √εᵣ. The physical reason is that the wave's electric field pushes the material's electrons back and forth; they radiate small waves of their own, and the combined wave moves more slowly. Silica glass has n ≈ 1.47 at the 1,550 nm wavelength used on long links, so light in fibre moves at about 204,000 km/s, or 4.9 µs per km. Circuit-board material (FR-4, εᵣ around 4) gives about c/2, roughly 15 cm per nanosecond, and the plastic insulation of a coaxial cable about 0.66c.
In a wire, the signal is the electromagnetic field, not the electrons. The field travels in the insulator around and between the conductors, guided by them, which is why the insulator sets the speed. On a chip a second limit is stricter than c. Wires there are only tens of nanometres wide, so their resistance is high, and an unrepeated wire's delay grows with the square of its length because both its resistance and its capacitance grow with length. Designers insert repeaters (buffers) along long wires to make delay grow only linearly, but a signal crossing a 2 cm die still needs several cycles at 4 GHz. This is why chips are divided into clock domains and pipeline stages, and why cache slices far from a core take longer to answer.
Distance limits latency, not bandwidth. The floor on a round trip is RTT = 2d ÷ v, about 1 ms per 100 km of fibre route. The data in flight on a path is bandwidth × RTT, the bandwidth-delay product. A 100 Gbit/s link with a 100 ms round trip holds 1.25 GB in transit, so a TCP sender needs a window of at least 1.25 GB to keep it full, and every lost packet costs at least one round trip to detect and repair. Long, fast paths therefore need large buffers and window scaling, and protocols that need fewer round trips (TLS 1.3, QUIC) save the most on exactly these paths.
Because no signal is faster than light, two machines cannot know each other's "now" exactly; they can only exchange messages and estimate (the relativity of simultaneity concept). NTP and PTP estimate a clock offset by assuming the delay is the same in both directions. If the outbound path takes 10 ms and the return path 30 ms, the estimate is wrong by half the difference, 10 ms, and no exchange of timestamps can reveal it. Spanner's TrueTime makes the uncertainty explicit instead: GPS receivers and atomic clocks in each data centre keep the uncertainty ε at about 1–7 ms (the 2012 paper reports about 4 ms most of the time), and each commit waits until ε has passed, so commit timestamps respect real-time order.
The medium is a design choice. Microwave links travel through air at about 0.9997c, nearly 50% faster than fibre, but they need line-of-sight towers every few tens of kilometres, carry far less data and fade in heavy rain. Microwave also cannot bend around the Earth's curve, so the towers must stand tall and close together, and each repeater adds a little delay. Satellites are the other option; their latency depends almost entirely on orbit height, as the table in the diagram shows.

mistakes: People often think more bandwidth gives lower latency. Bandwidth is how many bits per second a link carries; latency is how long one bit takes to arrive. Upgrading a Mumbai–Frankfurt link from 10 to 400 Gbit/s shortens the time to transfer a large file, but the round trip stays above 100 ms, and a request that needs ten sequential round trips still takes more than a second.
People often think the electrons in a wire move at nearly the speed of light. In fact they drift very slowly: with 1 A flowing in a copper wire of 1 mm² cross-section, they move less than 0.1 mm per second. What travels fast is the electromagnetic field guided by the wire, which pushes on electrons all along the wire at almost the same moment. That is why signal speed depends on the insulating material, not on the metal.
People often think all satellite internet is slow. Geostationary satellites are 35,786 km up, so the path up and down costs about 240 ms in each direction, and a round trip takes more than half a second. Low-earth-orbit satellites at about 550 km add only a few milliseconds, so their latency is close to that of ground networks, and their laser links between satellites travel at c rather than 0.68c.
People often think faster servers or better code can fix slow cross-region writes. If a protocol needs a quorum across regions, each commit waits at least one round trip to the nearest other quorum member, whatever the hardware. Only changes to the protocol or its placement help: put the leader and the quorum near the writers, batch or pipeline commits so that many writes share one round trip, or relax the guarantee to asynchronous replication.

A long wire needs repeaters and several cycles, so designers keep critical paths short and split the chip into clock domains and pipeline stages.

Fibre carries vastly more data, works in all weather and needs no towers; microwave carries little data and fades in heavy rain, so firms use it only for small, time-critical messages.

@@+ transistor
terms: Source and drain — the two heavily doped regions between which current flows when the transistor is on.
Gate — the electrode above the channel, separated from it by a thin insulator; its voltage turns the transistor on or off.
Channel — the thin region under the gate where the gate's electric field creates or removes a conducting path.
Threshold voltage (V_t) — the gate voltage at which the channel starts to conduct strongly.
Inversion layer — the thin sheet of electrons that a positive gate pulls to the surface of p-type silicon; it is the "on" channel.
CMOS — complementary MOS: logic built from pairs of n-type and p-type transistors, so that one of each pair is off in a steady state.
Leakage current — current that flows through a transistor that is supposed to be off, or through its gate insulator.
Subthreshold swing — the gate voltage needed to change the off-state current by 10×; at least about 60 mV at room temperature.
FinFET — a transistor whose channel is a thin vertical fin with the gate wrapped around three sides.
Gate-all-around (GAA) — a transistor whose channel is a stack of thin horizontal sheets with the gate on all four sides.
how: The lower concepts build the switch layer by layer. Doping supplies the regions: the body of an n-type MOSFET is silicon lightly doped with boron (p-type, with spare holes), and the source and drain are heavily doped with phosphorus or arsenic (n-type, with spare electrons). The p–n junction supplies the "off" state: source and drain each form a junction with the body, and with the gate off these two junctions sit back to back, so one is always reverse biased and almost no current flows. A positive gate voltage pushes holes away from the surface and, above the threshold voltage V_t, pulls in an inversion layer of electrons only a few nanometres thick. That layer connects source and drain with carriers of one type, and the switch is on. For a long-channel transistor the on-current follows I ≈ ½ μ C_ox (W/L)(V_G − V_t)², so a shorter channel L and a thinner insulator (larger C_ox) give more current and faster switching. In today's short channels the electrons reach a maximum speed, and the current grows closer to linearly with V_G − V_t.
Thermodynamics explains why the threshold voltage could not keep falling. Below threshold the channel does not switch off sharply. Electrons in the source have a spread of thermal energies (a Boltzmann distribution), and the few with enough energy cross the barrier anyway. As a result, the off-current falls by only 10× for every 60 mV of gate voltage below threshold at room temperature, because (kT/q) × ln 10 ≈ 60 mV at 300 K. An on/off ratio of a million therefore needs at least 6 × 60 = 360 mV between "off" and threshold, and lowering V_t by 120 mV raises leakage about 100×. This fixed swing is why supply voltages stopped falling near 0.7–1 V and why Dennard scaling ended. A tighter grip of the gate on the channel (FinFET, nanosheet) brings the swing close to 60 mV, but no conventional MOSFET can beat it.
The gate insulator met the same wall from the other side, which is where the oxides concept contributes. To keep control of shorter channels, the insulator had to get thinner, and by the 90 nm and 65 nm generations silicon dioxide gate layers were about 1.2 nm thick, only a few atomic layers. Electrons tunnel straight through a layer that thin. High-k dielectrics such as hafnium oxide (relative permittivity around 20–25, against 3.9 for SiO₂) give the same capacitance with a layer several times thicker, which stops most tunneling; Intel shipped them with metal gates in 2007.
Lithography prints the structures. Each layer is made by exposing a light-sensitive resist through a mask, then etching, depositing or implanting through the pattern, and a leading chip needs many dozens of masks. EUV light at 13.5 nm prints the finest layers in one exposure where 193 nm light needed several (multi-patterning). Node names mislead: at "3 nm class" processes the distance between neighbouring gates (the gate pitch) is still about 45–50 nm. Density now comes more from taller and stacked structures, such as nanosheets and, in research, stacked n- and p-transistors, than from smaller pitches.
Copper interconnects then wire billions of switches together through roughly 10–20 metal layers, finest at the bottom. As wires narrow to about 20 nm, copper's resistance rises, because electrons scatter off the wire surfaces and grain boundaries, and the barrier layer that stops copper from diffusing into silicon takes a growing share of each wire. Wires, not transistors, now cause a large share of delay and energy. Backside power delivery moves the power wires below the transistors, to the back of the wafer, and leaves the front layers for signals; Intel's 18A process, in volume production since late 2025, was the first to ship it at scale.

mistakes: People often think a transistor that is "off" uses no power. In fact it leaks: thermally excited electrons cross the channel barrier (the 60 mV per decade limit), and some tunnel through the gate insulator. Leakage rises steeply with temperature, so a hot chip leaks more and gets hotter still. This is why idle cores are power-gated, cut off from the supply by an extra switch, rather than only having their clock stopped.
People often think current flows through the gate to control the transistor. The gate is insulated; electrically it is one plate of a capacitor. A steady gate voltage draws almost no current, and energy is spent only to charge and discharge the gate and wire capacitance when the input changes. Driving more gates from one output (fan-out) therefore costs extra capacitance, slower edges and more C·V² energy per switch, not a steady current.
People often think smaller transistors automatically make chips faster and cooler. That was true under Dennard scaling. Now each shrink still gives more transistors per square millimetre, but the voltage barely falls, so power per square millimetre rises if all of them switch, and narrower wires get more resistive, so a smaller layout is not always faster. Gains now come from design: more cores, specialized units and better transistor shapes.
People often think Moore's law is about speed. Moore's 1965 paper was about the number of components on a chip at the lowest cost per component, which he expected to double every year, and revised in 1975 to every two years. Clock speeds rose for decades only because Dennard scaling came with the shrink; when it ended around 2005, transistor counts kept rising while clock speeds stalled.
quiz: What are the source, drain and gate of a MOSFET, and which one controls the current? || Source and drain are doped regions at the two ends of the channel, and current flows between them. The gate sits above the channel on a thin insulator, and its voltage decides whether a conducting channel forms.
Why does a CMOS gate use almost no power while its inputs are not changing? || In each steady state one transistor of every n/p pair is off, so there is no conducting path from the supply to ground, and the insulated gates draw no current. Energy is used mainly when outputs switch and capacitances charge or discharge, plus leakage.
Why could the threshold voltage, and with it the supply voltage, not keep falling every generation? || Below threshold, thermally excited electrons still cross the barrier, so the off-current falls only 10× per about 60 mV at room temperature ((kT/q) × ln 10). Each 60 mV cut in threshold voltage raises leakage about 10×, so threshold and supply voltages stopped falling, and Dennard scaling ended.
A chip's supply voltage drops from 0.9 V to 0.7 V at the same frequency and switching activity. How much does dynamic power fall? || Dynamic power scales with V², so it becomes (0.7 ÷ 0.9)² ≈ 0.60 of the original, a 40% saving. In practice a lower voltage also forces a lower maximum frequency, which saves more power but costs speed.
Why do chip designers mix low-threshold and high-threshold transistors in one design? || Low-threshold transistors switch faster but leak far more; high-threshold ones leak little but are slower. Designers put the fast, leaky ones only on the critical timing paths and the slow, low-leakage ones everywhere else, trading some design effort for both speed and low idle power.

@@+ contentid
terms: Fingerprint — a compact summary of audio or video computed from the signal itself and designed to survive common distortions.
Spectrogram — a picture of sound: the energy at each frequency over time, computed with short Fourier transforms.
Landmark — a hash of two spectrogram peaks (their two frequencies and the time gap between them) used as a lookup key.
Perceptual hash — a short bit string computed from an image, such that similar images give strings that differ in few bits.
Hamming distance — the number of bit positions in which two bit strings differ.
Bit error rate (BER) — the Hamming distance divided by the number of bits compared; two unrelated strings give about 0.5.
Reference index — the database of fingerprints of known content (songs, ads, live channels) with their IDs and times.
Time-offset alignment — checking that many hits agree on one shift between the query's clock and the reference's clock.
Watermark — a signal deliberately embedded in content at the source, which a detector reads later.
Precision and recall — the share of reported matches that are correct, and the share of true matches that are found.
how: Audio fingerprinting (the fingerprint concept) shows the core ideas most clearly, in the Shazam design described by Avery Wang in 2003. The audio becomes a spectrogram, and only strong local peaks are kept: a sparse "constellation" that survives noise and compression, because loud peaks stay loud. A single peak is not specific, since its frequency fits in about 10 bits and matches a huge number of places in a large catalogue. So each peak, the anchor, is paired with a few peaks in a target zone just after it; Wang's example uses a fan-out of 10. Each pair gives f₁, f₂ and Δt, about 10 bits each, packed into one 32-bit hash, which is about a million times more specific than a single peak. The index stores each hash with its track ID and its time within the track. Storage grows about tenfold, one entry per pair, but in Wang's analysis searches become about 10,000 times faster.
Matching relies on time consistency, not on single hits. For each query hash, the index returns (track, t_ref) pairs. For each candidate track, the matcher computes δ = t_ref − t_query for every hit and builds a histogram of δ. Random hits spread over all offsets. A true match puts many hits into one bin, because the query is a time-shifted copy of the reference. The score is the height of that peak, and the threshold is set from the scores of wrong tracks for a chosen false-positive rate, such as 0.1%. Wang reports queries taking about 5–500 ms against a 20,000-track database on one PC.
The Philips system (Haitsma and Kalker, 2002) takes a different route. It computes a 32-bit sub-fingerprint about every 11.6 ms from the energies in 33 logarithmically spaced frequency bands between 300 and 2,000 Hz. Each bit records whether the energy difference between two neighbouring bands rose or fell compared with the previous frame. 256 consecutive sub-fingerprints, about 3 seconds, form a block, and two blocks match when their bit error rate is below about 0.35, while unrelated audio gives about 0.5. Lookup assumes that at least one of the 256 sub-fingerprints survived the distortion unchanged and uses it as an exact key in a hash table; if that fails, it also tries flipping the least reliable bits, those whose energy difference was close to zero.
For video frames, a perceptual hash (the perceptual hashing concept) maps an image to a short bit string so that similar images give similar strings. Meta's PDQ, for example, computes a discrete cosine transform of a downsampled grey image and sets each of its 256 bits by whether a low-frequency coefficient is above the median; its documentation suggests a Hamming distance of 31 or less as the starting threshold for a match. Low frequencies describe the overall layout of the image, so resizing, recompression and small colour changes barely move them, while a different scene changes many bits. A video fingerprint is a sequence of such frame hashes taken at a fixed rate, and it is aligned in time like the audio landmarks.
Finding all stored 256-bit hashes within distance 31 of a query cannot be done by exact lookup, and comparing against millions of hashes one by one is too slow. Locality-sensitive hashing (the LSH concept) makes it fast by grouping similar hashes into the same buckets. One simple scheme is multi-index hashing, built on the pigeonhole principle. Split every hash into 16 chunks of 16 bits. If two hashes differ in at most 31 bits, at least one chunk differs in at most 1 bit, because 16 chunks with 2 or more differences each would add up to at least 32. So the index keeps one table per chunk, the matcher looks up each query chunk exactly and with each single bit flipped (16 × 17 = 272 lookups), and it computes the full distance only for the candidates found. With 10 million stored hashes, that is on the order of 40,000 full comparisons instead of 10 million.

mistakes: People often think fingerprinting and watermarking are the same thing. A watermark is put into the content at the source (for example ATSC A/335 marks in broadcast video) and read by a detector, so it identifies only content whose owner embedded it. A fingerprint is computed from content as it already is, but it identifies something only if the same content is in the reference index. Watermarks can carry exact data such as channel and time, yet can be lost or stripped; fingerprints need large live references. Many measurement systems use both.
People often think a fingerprint is like a cryptographic hash of the file. A cryptographic hash changes completely when one input bit changes, so re-encoding a video gives a totally different SHA-256. A perceptual fingerprint is designed for the opposite: small changes in the signal give small changes in the bits, so similarity is a Hamming distance, not equality. The same property allows a different attack: an adversary can edit content step by step until its hash drifts past the threshold.
People often think one matching sample is enough to identify content. A single frame hash or landmark can match by chance, especially in a large index full of recurring graphics, theme music and black frames. Reliable systems require several consistent hits over a few seconds, at one time offset, before they emit an event. They trade a few seconds of delay for far fewer false matches.
People often think fingerprints are anonymous, so viewing data built from them raises no privacy issue. The fingerprint itself reveals little, but the matched result, "this device watched this programme at this time", tied to a device or household ID, is personal data under laws such as the GDPR and US state privacy laws. Consent, minimization and deletion apply to the viewing events and to every dataset derived from them.
quiz: Why does a Shazam-style system hash pairs of spectrogram peaks instead of single peaks? || A single peak's frequency gives only about 10 bits, so it matches a huge number of places in a large catalogue. A pair (f₁, f₂, Δt) gives about 30 bits, roughly a million times more specific, and still survives noise because both peaks are loud; the cost is about ten times more stored hashes.
How does time-offset alignment separate a true match from random hash collisions? || For each candidate track the matcher computes t_ref − t_query for every hit. A true match is a time-shifted copy of the reference, so its hits pile up at one offset, while random collisions spread across all offsets; the score is the height of the tallest bin.
How can an index find stored 256-bit hashes within Hamming distance 31 of a query without comparing against every one? || Split each hash into 16 chunks of 16 bits. If the distance is at most 31, at least one chunk differs in at most 1 bit, so the matcher looks up each query chunk exactly and with each single bit flipped, collects the candidates, and computes the full distance only for them (multi-index hashing).
10 million TVs each watch 5 hours a day and send a 200-byte fingerprint every 5 seconds. How much fingerprint data arrives per day, and at what average rate? || Each TV sends 5 × 3,600 ÷ 5 = 3,600 fingerprints a day, so 3.6 × 10¹⁰ fingerprints, about 7.2 TB per day. Spread over 24 hours that is about 420,000 fingerprints per second on average, with prime-time peaks several times higher.
What happens if you raise the Hamming-distance threshold for a match from 31 to 60 bits? || Recall rises, because heavily edited, cropped or overlaid copies still match. Precision falls, because unrelated but similar frames (studio sets, sports graphics, black screens) now match too, and candidate lists grow, so search gets slower. The right threshold comes from labelled data and the relative cost of each kind of error.

@@+ adtech
terms: Impression — one ad served to one viewer; the unit that is bought and sold.
CPM — cost per mille, the price of 1,000 impressions; ₹850 CPM means ₹0.85 per impression.
SSP — supply-side platform: the seller's system that offers impressions to buyers and runs or joins the auctions.
DSP — demand-side platform: the buyer's system that evaluates bid requests and bids on behalf of advertisers.
Ad exchange — the marketplace that sends bid requests to many buyers and runs the auction.
Bid request — the message, usually OpenRTB JSON, that describes one impression opportunity and its deadline (tmax).
Floor price — the lowest price the seller will accept for an impression.
Bid shading — bidding below one's value in a first-price auction in order to keep some surplus.
Frequency cap — a limit on how often one person or household sees a campaign in a period.
Pacing — controlling bids so that a budget is spent evenly over the campaign instead of all at once.
how: The deadline shapes the whole bidder. The bid request carries tmax, the number of milliseconds the exchange will wait for bids, and a bid that arrives later is ignored: every timeout is a lost auction. Exchanges and bidders usually run in the same cloud regions, so the network round trip costs only a few milliseconds, and a well-run bidder answers in tens of milliseconds, keeping a margin for network jitter and garbage-collection pauses. Anything slow (building audience segments, training models, computing pacing multipliers) is done ahead of time, and the bidder only looks results up.
The auction rule decides what a good bid is, which is what the ad-auction concept contributes. In a second-price auction the winner pays the second-highest bid (or the floor), so bidding your true value is the best strategy: your bid only decides whether you win, not what you pay. In a first-price auction the winner pays its own bid, so bidding true value leaves zero surplus. The bidder instead chooses the bid b that maximizes expected surplus, (v − b) × P(win | b), where P(win | b) is learned from past wins and losses (the bid landscape). Suppose v = ₹1,200 CPM and the estimated win probability is 40% at ₹800, 60% at ₹900 and 75% at ₹1,000. Expected surplus is 400 × 0.4 = 160, 300 × 0.6 = 180 and 200 × 0.75 = 150, so the bidder bids ₹900.
The value v comes from models (the regression and bandit concepts). For a campaign that pays per completed view, v = P(completion | request) × value per completion × 1,000. Click and conversion models began as very large logistic regressions over hashed sparse features (McMahan and colleagues described Google's in 2013), and many now use deep networks. One property matters more than the model type: calibration. A bid multiplies a predicted probability by money, so a model that predicts 2% when the truth is 1% overbids by a factor of 2, even if it ranks impressions perfectly. New creatives have no history, so bidders spend a small share of traffic exploring them with bandit methods such as Thompson sampling, then move spend to what works.
Budget pacing (the pacing concept) is a feedback controller. A campaign has a target spend curve over the day, often shaped like the traffic curve. Every few seconds or minutes, the controller compares actual spend with the target and adjusts a bid multiplier or a participation rate (bid on only a fraction of eligible requests): lower when ahead of plan, higher when behind. Without pacing, a campaign with a ₹1 lakh daily budget could spend it in the first busy hour on whatever it wins first and have nothing left for prime time.
Guaranteed deals add an allocation problem (the network flow concept). A publisher's ad server may promise campaign A one million impressions to cricket fans in India and campaign B two million to all adults in Delhi, from supply that overlaps. Deciding which impressions go to which contract, so that every contract is delivered, is a bipartite flow problem: supply groups on one side, contracts on the other, and an edge wherever the targeting matches. The solution becomes serving rules or probabilities, and leftover inventory goes to the auction.
Identity and the supply chain are the last layer (the cookies and device IDs concept). Web bidding relied on third-party cookies matched between companies by cookie syncing, where redirect pixels let two systems map their IDs to each other. Mobile and CTV use device advertising IDs and IP-based household graphs, and consent signals (such as the IAB's TCF and GPP strings) travel inside the bid request. Because one impression can reach a DSP through several resellers, the IAB Tech Lab added ads.txt (publishers list their authorized sellers), sellers.json (exchanges list who they sell for) and the SupplyChain object (each hop recorded in the bid request), so buyers can drop unauthorized or needlessly long paths.

mistakes: People often think that in a first-price auction a bid shows what the advertiser believes the impression is worth. With shading, the bid is the value minus the surplus the bidder hopes to keep, and it depends on the competition it predicts. Two DSPs with the same value can bid very differently, and analysts who read winning prices as values, for example to estimate what an audience is worth, get biased answers.
People often take attribution as proof that ads caused conversions. Last-touch attribution credits the ad that came before a purchase, but many of those people would have bought anyway, especially in retargeting audiences. If an exposed group converts at 5.5% and a randomized holdout at 5.0%, the ads caused about 0.5 points, roughly 9% of the conversions, not all of them. Only experiments (holdouts, ghost ads, geo tests) measure that incremental part.
People often count an impression as an ad that was seen. An impression is usually counted when the ad is served or starts to render, whether or not anyone could see it. The MRC viewability standard counts a display ad as viewable only when at least 50% of its pixels are on screen for at least one continuous second, and a video ad for two seconds. On CTV the screen may be on with nobody in the room, which no pixel can detect.
People often treat each bid request as a separate opportunity. Through header bidding and resellers, the same impression often reaches a DSP as several bid requests from different exchanges. Bidding on all of them means bidding against yourself and paying extra fees, and counting them inflates the supply you think exists. Supply-path optimization picks the shortest, cheapest path, using sellers.json and the SupplyChain object to see each path.
quiz: What do an SSP and a DSP each do in a programmatic auction? || The SSP works for the seller: it turns each impression into bid requests, sets floors and runs or joins the auction. The DSP works for buyers: it checks each request against campaigns, predicts value, applies pacing and frequency caps, and returns a bid before the deadline.
Why does a first-price auction require bid shading while a second-price auction does not? || In a second-price auction the winner pays the next-highest bid, so bidding your true value is optimal: your bid decides only whether you win, not what you pay. In a first-price auction you pay your own bid, so bidding your value leaves no surplus; you choose the bid b that maximizes (value − b) × P(win | b).
Why must impression and click pipelines be idempotent? || Players and networks retry, so the same pixel can arrive twice, and events can arrive late or out of order. Billing, spend and frequency counters must count each event exactly once, so pipelines deduplicate by a unique request or event ID and make every update safe to replay.
A completed view is worth ₹1,200 CPM to a campaign, and the bidder estimates a win probability of 40% at ₹800, 60% at ₹900 and 75% at ₹1,000 CPM. Which bid maximizes expected surplus? || Surplus per thousand is (1,200 − 800) × 0.4 = 160, (1,200 − 900) × 0.6 = 180 and (1,200 − 1,000) × 0.75 = 150, so ₹900 CPM is best. Bidding the full ₹1,200 would win more often but earn no surplus.
Your bidder's p99 latency is 90 ms against a 100 ms budget. Should you add a larger model that predicts better but adds 15 ms? || Not as it stands: more than 1% of requests would then miss the deadline, and a missed deadline loses the auction outright, which usually costs more than better predictions earn. First cut other latency (precomputed features, cached lookups, fewer GC pauses), or run the large model only where it can change the decision, such as high-value requests, and measure revenue per request in an A/B test.
