@@ langruntime
value: A CPU executes only machine code: simple instructions that move numbers between registers and memory, add them, compare them and jump. People write code with names, types, objects, closures, strings and threads. A compiler or a runtime closes that gap. A compiler translates the program into machine code, or into a lower-level form such as bytecode. A runtime is the code that runs next to your program while it executes: it loads code, allocates and frees memory, schedules threads, handles exceptions, and in many systems compiles hot code on the fly. Together they decide how fast a program starts, how fast it runs once warm, how much memory it uses, how long it pauses, and which bugs are impossible.
For a data engineer these choices are visible every day. Spark runs on the JVM, so its speed depends on the JIT compiler and the garbage collector; a long GC pause can look like a lost executor. A Python UDF in PySpark sends rows from the JVM to a separate Python process, which is why such UDFs are often many times slower than built-in functions. Databricks wrote its Photon engine in C++ to control memory and SIMD instructions directly. Polars is written in Rust. The runtime is often the hidden reason one engine is faster than another.
Many lower concepts build this layer: parsing, type systems, SSA intermediate representations and register allocation on the compiler side; interpreters, JIT compilation, allocators and garbage collectors on the runtime side; threads and concurrency models for parallel work; Unicode for strings. The Turing machine sets the frame: all these languages compute the same set of functions, so the differences between them are about cost, safety and convenience, not power.
terms: Ahead-of-time (AOT) compilation — translating a whole program to machine code before it runs, as GCC, Clang, rustc and the Go compiler do.
Bytecode — a compact, portable instruction set for a virtual machine, such as Java class files or CPython's .pyc files.
Just-in-time (JIT) compilation — compiling code to machine code while the program runs, usually only the parts that run often.
Intermediate representation (IR) — the compiler's internal form of the program; most modern IRs use SSA, where each variable is assigned exactly once.
Tiered compilation — running code first in an interpreter or quick compiler, then recompiling hot code with a slower, more optimizing compiler.
Deoptimization — throwing away optimized code whose assumptions turned out false and continuing in slower, safe code.
Garbage collector (GC) — the part of a runtime that finds memory no longer reachable from the program and frees it.
Safepoint — a point where a thread can be paused safely so the runtime can collect garbage or replace code.
Foreign function interface (FFI) — the way one language calls code written in another, such as JNI in Java or C extensions in Python.
history: John Backus's team at IBM delivered the first FORTRAN compiler in 1957. Programmers did not believe a compiler could match hand-written assembly, so the team worked hard on optimization, and the result convinced people that high-level languages could be efficient. John McCarthy's Lisp (1958–1960) introduced garbage collection and an interpreter written in the language itself. C (1972) and Unix made a portable AOT-compiled systems language the norm.
Dynamic compilation grew out of languages too flexible to compile well ahead of time. Deutsch and Schiffman (1984) translated Smalltalk-80 bytecode to machine code on demand. The Self project (David Ungar, Craig Chambers, Urs Hölzle and others, at Stanford and then Sun, 1987–1994) invented most of the modern JIT toolkit: polymorphic inline caches (1991), deoptimization (1992) and optimization driven by type feedback (1994). Some of those engineers built Strongtalk; Sun bought their company in 1997, and its VM became HotSpot, which shipped for Java in 1999 and made the JVM fast enough for servers. Microsoft's .NET CLR followed in 2002.
LLVM, started by Chris Lattner and Vikram Adve at the University of Illinois (CGO 2004 paper), gave everyone a reusable SSA optimizer and code generator; Clang, Rust, Swift and Julia use it. Google's V8 (2008) brought the Self ideas to JavaScript. Go (2009) and Rust (1.0 in 2015) offered new AOT designs: Go with a simple concurrent collector and goroutines, Rust with compile-time ownership instead of a collector. WebAssembly (2017) gave browsers a portable compile target.
The same trade-offs keep moving. Java 21 (2023) added virtual threads and generational ZGC; Java 25 (September 2025) is the current long-term-support release, and Java 27 shipped in September 2026. CPython 3.13 (2024) added an experimental JIT and an optional build without the global interpreter lock; 3.15 (October 2026) upgraded the JIT, which is still experimental. Go 1.26 (February 2026) made its new "Green Tea" collector the default, with 10–40% less GC overhead expected in GC-heavy programs.
how: Every implementation starts the same way. The lexer and parser (the parsing concept) turn source text into an abstract syntax tree whose nodes are declarations, expressions and statements. Name resolution links each use of a name to its definition. The type checker (type systems) then proves facts: this variable is always an int, this call has the right arguments. Those facts are not only for catching bugs. They tell the compiler how big each value is, which method a call can reach, and which operations can become a single machine instruction.
Next the compiler lowers the tree to an intermediate representation, usually in SSA form (the IR and SSA concept); LLVM, GCC, HotSpot's C2, V8's TurboFan and the Go compiler all do this. In SSA each variable is assigned once, and where control flow joins, a φ ("phi") function picks the value from whichever branch ran. Data flow becomes explicit, so optimizations become simple graph rewrites. Constant propagation replaces x with 4 when x is always 4. Common-subexpression elimination computes a × 4 once. Dead-code elimination removes values nobody uses. Inlining copies a small function into its caller, which removes call overhead and, more importantly, exposes the callee's body to every other optimization. Loop optimizations hoist invariant work out of loops and vectorize them, so one SIMD instruction processes 4, 8 or 16 values.
The back end maps the IR onto a real CPU. Instruction selection picks machine instructions. Register allocation (the regalloc concept) decides which of the 16 general-purpose registers on x86-64 holds each value at each moment, and spills the rest to the stack. This matters because a register access is nearly free, while a stack access can miss the cache. An AOT compiler writes object files, and a linker joins them with libraries into an executable. All of this runs once, before the program starts, so the cost is paid at build time.
Managed runtimes (the JVM, .NET, V8, CPython) choose a different moment. The compiler produces bytecode, and the virtual machine starts by interpreting it (the interpreters concept): a loop reads one instruction, jumps to code that performs it, and repeats. Interpretation starts instantly but is slow, often 10 to 50 times slower than optimized machine code, because every instruction pays for dispatch and every value is handled generically. While interpreting, the VM counts how often each method and loop runs and records which types actually appear at each call site.
The JIT compiler (the JIT concept) uses that profile. When a method passes a threshold, the VM compiles it on a background thread. HotSpot does this in tiers: the quick C1 compiler after roughly 200 calls, the optimizing C2 compiler after roughly 5,000 calls or many loop iterations. V8 has four tiers: the Ignition interpreter, the Sparkplug and Maglev compilers, and the optimizing TurboFan. The key trick is speculation. If a call site has only ever seen one class, the JIT inlines that class's method behind a cheap type check called a guard. If the guard ever fails, the runtime deoptimizes: it rebuilds the interpreter's view of the stack frame, continues in slow code, and may recompile later. On-stack replacement lets a long loop switch to compiled code mid-loop. This is why a JIT can sometimes beat an AOT compiler: it optimizes for the types and paths that really occur, not for every possible case.
Memory is the second big job. An allocator (the allocators concept) hands out memory: malloc keeps free blocks in size classes, with per-thread caches (tcmalloc, jemalloc, mimalloc) so most allocations take no lock. Managed runtimes allocate even faster by bumping a pointer inside a thread-local buffer, about ten instructions. Freeing is the hard part. A tracing garbage collector (the GC concept) starts from roots (stack slots, registers, globals), marks every object it can reach, and reuses the rest. Most objects die young, so generational collectors copy the few survivors out of a small young area often and scan the large old area rarely. Concurrent collectors (G1, ZGC, Shenandoah; the concurrent GC concept) do most marking and moving while the program runs, using barriers: small pieces of code the compiler inserts around pointer loads or stores. That is how ZGC keeps pauses under about a millisecond on heaps of hundreds of gigabytes. Other designs exist: CPython and Swift count references, and Rust's type system enforces ownership so the compiler inserts each free at a known point and no collector is needed.
The third job is concurrency. The operating system schedules threads (the threads concept); the runtime decides how language-level tasks map onto them (the concurrency models concept). Java platform threads and C++ std::thread are one-to-one with OS threads. Go's goroutines and Java's virtual threads are many-to-one: the runtime runs millions of cheap tasks (a goroutine starts with a 2 KB stack) on a few OS threads and switches tasks when one blocks on I/O. Node.js and Python's asyncio use one event loop with async functions. Classic CPython has a global interpreter lock, so only one thread runs Python bytecode at a time. Threads also cooperate with the GC by stopping at safepoints, so the collector sees a consistent heap.
Finally, a runtime defines basic data, and strings show this best (the Unicode concept). Java stores strings as UTF-16, or one byte per character when all characters fit in Latin-1. CPython picks 1, 2 or 4 bytes per code point for each string. Go and Rust store UTF-8 bytes. So "length" and "character at index i" mean different things, with different costs, in each language. A call through an FFI must convert such data, and that conversion is often where cross-language systems lose most of their time.

example: Follow one small function through an optimizing compiler, then put numbers on a JVM service.
The function is: x = a * 4; y = a * 4; if (b > 0) x = x + y; return x. In SSA form it becomes: x1 = a * 4; y1 = a * 4; if b > 0 then x2 = x1 + y1; x3 = φ(x1, x2); return x3. Common-subexpression elimination sees that y1 equals x1. Strength reduction turns a * 4 into a << 2, because a shift is cheaper than a multiply. Then x2 = x1 + x1, which is a << 3. Only two values are alive at any moment, so the register allocator keeps both in registers and spills nothing. The result is about six machine instructions.
Now a service on the JVM. Suppose its hot method costs 2 µs per call in the interpreter, 0.3 µs after C1 and 0.1 µs after C2, and it is called 100,000 times per second. Interpreted, it uses 100,000 × 2 µs = 0.2 seconds of CPU per second, one fifth of a core. After C2 it uses 100,000 × 0.1 µs = 0.01 seconds, one hundredth of a core. This one method reaches the thresholds (about 200 and 5,000 calls) in a fraction of a second. But a real service has thousands of warm methods sharing one compile queue, so for the first tens of seconds after a deploy, latency is higher and CPU goes to compilation. That is why rolling deploys send warm-up traffic first.
The same service allocates 1 GB of short-lived objects per second, and its young generation is 2 GB, so a young collection runs every 2 seconds. If 3% of objects survive, the collector copies 60 MB. With 8 GC threads each copying about 1 GB per second, the pause is roughly 60 MB ÷ 8 GB per second ≈ 7.5 ms. The 60 MB of survivors move to the old generation every 2 seconds, 30 MB per second, so a 15 GB old generation fills in about 500 seconds, and G1 must finish marking it concurrently before then. With ZGC, pauses drop below 1 ms, but the collector uses extra CPU and needs spare memory while it works.
intuition: A good runtime is like a translator who reads a new speech aloud word by word at first, notices which paragraphs keep coming back, and prepares polished translations of only those, while an assistant quietly tidies the room.
The design is natural because programs are very uneven. Most running time is spent in a small part of the code, so it makes sense to spend expensive optimization only there, and only after measuring where "there" is. Most objects die soon after they are created, so it makes sense to collect young objects often and old ones rarely. Most dynamic call sites see only one type, so it makes sense to bet on that type and keep a cheap way to back out. Each mechanism is a bet on the common case plus a safe fallback for the rare case. AOT compilation makes the opposite bet: do all the work once, before running, so start-up is instant and behaviour is predictable.
mistakes: People often think "compiled languages are fast and JIT languages are slow". In fact a warm JIT can match or beat AOT code on long-running servers, because it optimizes for the types and branches that really occur. The JIT's real costs are warm-up time, compiler CPU and memory, not peak speed.
People often think interpreted or compiled is a property of the language. In fact it is a property of the implementation. Python has CPython (an interpreter, now with an experimental JIT) and PyPy (a tracing JIT); Java can be compiled AOT with GraalVM Native Image.
People often think garbage collection prevents memory leaks. In fact a GC frees only unreachable objects. A cache with no size limit, a listener that is never removed, or a static map that keeps growing holds reachable objects forever, and the heap fills just the same.
People often blame Python's slowness only on interpretation. In fact boxing (every integer is a heap object of about 28 bytes), dynamic lookups for every attribute and the global interpreter lock matter as much. Fast Python code moves the inner loop into native libraries such as NumPy, Arrow or Polars.
friction: Every runtime trades start-up time, peak speed, memory use and predictability against each other. JIT runtimes start slowly and use extra memory for compiled code and profiles, which hurts short jobs and serverless functions. AOT binaries start instantly but cannot adapt to the real workload unless you feed them a profile (profile-guided optimization).
Garbage collection moves cost rather than removing it. Concurrent collectors cut pauses to around a millisecond, but they use more CPU for barriers and background threads, and they need spare heap. In memory-heavy data engines, GC pressure is a real reason to keep data off-heap in columnar buffers. Manual memory management avoids the collector but brings use-after-free and buffer-overflow bugs: Microsoft and the Chromium project have each reported that roughly 70% of their serious security bugs are memory-safety bugs, the main argument for Rust and other memory-safe languages.
Crossing between runtimes is expensive. JNI calls, Python C extensions and PySpark UDFs all pay for converting data and switching context. Optimizing compilers also have cliffs: a method that grows past an inlining limit, or a call site that suddenly sees a second type, can lose most of its speed, and the cause is invisible in the source. Compile times for C++ and Rust grow with heavy templates and generics, and "undefined behaviour" in C and C++ lets compilers transform buggy code in surprising ways.
practice: Learn your runtime's cost model before tuning code. On the JVM, know your collector: G1 is the default and a good general choice; ZGC (generational by default since Java 23) suits large heaps with strict latency goals. Set the heap size explicitly in containers, use Java Flight Recorder or async-profiler to see where time and allocations go, and warm services up before giving them full traffic. For slow start-up, look at class-data sharing and the ahead-of-time cache from Project Leyden (JDK 24 onward), or GraalVM Native Image.
In Spark, prefer built-in SQL functions to UDFs, because built-ins run inside generated JVM code or inside Photon. If you need Python logic, use Arrow-based pandas UDFs, which move data in columnar batches instead of one row at a time. Watch GC time in the Spark UI; high GC time usually means too little executor memory, too many cached objects, or skewed partitions.
In Go, the collector has two main knobs: GOGC (how much the heap may grow between collections) and GOMEMLIMIT (a soft memory cap, useful in containers). In Python, profile with py-spy or cProfile and move hot loops into vectorized libraries. In C++ and Rust, build releases with optimization, consider link-time and profile-guided optimization, and run sanitizers in CI. Choose a language first by team skills and ecosystem, then check that its runtime fits the service: start-up time, memory per instance, tail latency and how it calls native code.
quiz: What is the difference between an AOT compiler and a JIT compiler? || An AOT compiler translates the whole program to machine code before it runs. A JIT compiler translates code while the program runs, usually only hot code, and can use observed types and branches to optimize.
Why does SSA form make optimization easier? || Each variable is assigned exactly once, so every use points to exactly one definition. Data flow becomes an explicit graph, and optimizations such as constant propagation and dead-code elimination become simple rewrites of that graph.
How can a JIT safely inline a virtual method call, and what happens when its guess is wrong? || It inlines the one class it has seen at that call site behind a cheap type check (a guard). If an object of another class arrives, the guard fails, the runtime deoptimizes to interpreter code, and it may recompile later with the new type information.
A JVM service allocates 2 GB per second with a 4 GB young generation, and 5% of objects survive. How often does a young collection run, and roughly how long is the pause with 8 GC threads copying 1 GB per second each? || Every 4 GB ÷ 2 GB per second = 2 seconds. Each collection copies 5% of 4 GB = 200 MB, and 200 MB ÷ 8 GB per second ≈ 25 ms of pause.
When would you choose an AOT-compiled language such as Go or Rust over a JIT runtime such as the JVM? || When start-up time, memory per instance and predictable latency matter more than peak speed after warm-up, as for CLI tools, serverless functions, sidecars and many small containers. For long-running, CPU-heavy services, a warm JVM is often just as fast.
