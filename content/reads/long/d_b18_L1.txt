@@ blockchain
value: A blockchain is a database that many independent computers keep together. No single computer is in charge, and the participants do not need to trust each other. Every participant holds a copy of the same append-only list of records, the ledger. New records are added in batches called blocks. Each block contains a cryptographic hash of the block before it, so changing any old record changes every later hash, and the change is detected at once. A consensus protocol decides which block comes next, even when some participants lie, crash, or try to spend the same money twice.
The problem it solves is narrow but hard: agreeing on one order of events among strangers on the open internet, where anyone can create thousands of fake identities. Before 2008, every digital payment system needed a trusted operator (a bank, a card network, a company's server) to keep the master record and stop double spending. Bitcoin showed that a network can do this job without an operator, by making the right to add a block cost real resources. The price is high: a public chain's base layer processes a few to a few tens of transactions per second, a single PostgreSQL server tens of thousands, and confirmation takes minutes, not milliseconds.
For the layer above (Bitcoin, Ethereum, stablecoins, permissioned ledgers such as Hyperledger Fabric), this concept gives the core design: a hash-linked chain, a rule for choosing between competing chains, and a way to run programs (smart contracts) that every node executes in the same way. The layers below supply the parts. Merkle trees (L2) commit to thousands of transactions in one 32-byte hash, and let a phone check one transaction with a proof of a few hundred bytes. Proof of work and proof of stake (L2) make the right to add a block cost something, which defeats fake identities. Byzantine fault tolerance (L2) gives voting protocols that reach final agreement while fewer than one third of the participants are malicious. Zero-knowledge proofs (L3) let one party prove that a large batch of transactions is valid, so the chain checks a small proof instead of re-running every transaction.
terms: Block — a batch of transactions plus a header that holds the previous block's hash, a Merkle root of the transactions, a timestamp and consensus data.
Hash pointer — a reference to earlier data by its cryptographic hash; any change to the data breaks the reference.
Fork — two valid blocks that point to the same parent, so the chain briefly has two branches.
Fork-choice rule — the rule a node uses to pick one branch, such as "the valid chain with the most total work".
Finality — the point after which a block cannot be reversed; probabilistic in proof of work, explicit in BFT-style voting.
Double spend — spending the same coin twice by getting two conflicting transactions accepted by different parts of the network.
Sybil attack — creating many fake identities to gain influence in a vote; open blockchains defeat it by tying influence to work or stake.
Smart contract — a program stored on the chain whose state changes only through transactions, executed identically by every full node.
Light client — a client that keeps only block headers and checks single transactions with Merkle proofs.
Rollup — a system that executes transactions off the main chain and posts their data, plus a validity or fraud proof, to it.
history: The pieces are older than Bitcoin. Ralph Merkle described hash trees in 1979. Cynthia Dwork and Moni Naor proposed in 1992 that a sender should pay a small computational cost per email to fight spam ("Pricing via Processing"), and Adam Back's Hashcash (1997) made this a practical puzzle based on partial hash collisions. Stuart Haber and W. Scott Stornetta ("How to Time-Stamp a Digital Document", 1991) chained document hashes so that no one could backdate a record, and in 1993, with Dave Bayer, they added Merkle trees to timestamp many documents at once.
In October 2008, Satoshi Nakamoto published "Bitcoin: A Peer-to-Peer Electronic Cash System", and the network started on 3 January 2009. The key step was to combine a Haber–Stornetta hash chain with Hashcash-style proof of work and a "most work wins" rule. This made the order of transactions a matter of computation, not of identity, so fake identities gave no advantage. Ethereum (proposed by Vitalik Buterin in 2013, launched in July 2015) added a general-purpose virtual machine, so the chain could run arbitrary programs. The DAO hack in June 2016, caused by a bug in one contract, led to a disputed hard fork and showed how costly contract bugs are.
Companies wanted shared ledgers without mining, so permissioned chains such as Hyperledger Fabric (Linux Foundation, from 2016) used classic consensus among known members, building on Castro and Liskov's PBFT (1999). On 15 September 2022, Ethereum switched from proof of work to proof of stake ("the Merge"), which cut its energy use by more than 99.9%. To scale, the ecosystem moved execution to layer-2 rollups. The Dencun upgrade (March 2024) added cheap, temporary "blob" space for rollup data, and Fusaka (December 2025) added PeerDAS, so each node stores only part of that data. By 2025–2026 the largest real-world use was stablecoins, tokens backed by dollars, and the United States passed the GENIUS Act (2025) to regulate them.
how: Start with the data structure. A block holds a list of transactions and a small header. In Bitcoin the header is 80 bytes: a version, the hash of the previous header, the Merkle root of the transactions, a timestamp, the difficulty target and a nonce. Because each header contains the hash of the one before, the headers form a chain of hash pointers. Change one transaction in block 100, and its Merkle root changes, so block 100's hash changes, so block 101's "previous hash" no longer matches, and so on to the newest block. The structure does not prevent tampering, but it makes tampering obvious: anyone who holds the latest hash can detect a change anywhere in history.
The Merkle tree (from the Merkle-tree concept) is how one 32-byte root commits to thousands of transactions. Each transaction is hashed, then pairs of hashes are hashed together, level by level, until one root remains. To prove that a transaction is in a block, you give the transaction and the sibling hash at each level: \( \log_{2}(n) \) hashes in total. For a block of 4,000 transactions that is 12 hashes, or 384 bytes. This is what makes light clients possible. A phone stores only headers (80 bytes per block, under 80 MB for all of Bitcoin's history) and checks any payment with a short proof.
Now the hard part: thousands of nodes must agree on which block comes next. Each node receives transactions and blocks by gossip, checks them against the rules (valid signatures, no coin spent twice), and keeps the valid chain it prefers. If agreement were reached by vote, an attacker could run a million fake nodes and win every vote. This is the Sybil problem. Classic Byzantine protocols assume a known list of members, so they cannot be used as they are on an open network.
Proof of work (from the proof-of-work-and-stake concept) replaces "one node, one vote" with "one unit of computation, one ticket in a lottery". To create a block, a miner must find a nonce such that the double SHA-256 hash of the header is below a target number. The only known way is to try nonces one after another. With difficulty D, the expected number of attempts is \( D \times 2^{32} \). The protocol adjusts the target every 2,016 blocks, so that blocks arrive about every 10 minutes whatever the total hash rate. Nodes follow the fork-choice rule "the valid chain with the most cumulative work". When two miners find blocks at almost the same time, the chain forks briefly; the next block usually breaks the tie, and the other block becomes stale. To rewrite a block buried z blocks deep, an attacker must redo that work and then overtake the honest chain, which keeps growing meanwhile. Nakamoto showed that an attacker with a fraction \( q < 0.5 \) of the hash rate catches up with a probability that falls exponentially with z. Finality is therefore probabilistic: each new block makes a reversal less likely, but never impossible. An attacker with more than half of the hash rate can rewrite recent history at will; this is the "51% attack".
Proof of stake ties influence to locked coins instead of electricity. In Ethereum, a validator deposits at least 32 ETH (since the Pectra upgrade of May 2025, one validator can hold up to 2,048 ETH). Time is cut into 12-second slots. In each slot a pseudo-randomly chosen validator proposes a block, and committees of validators vote ("attest") for it. Every 32 slots (one epoch, 6.4 minutes) the votes act as one round of a Byzantine fault-tolerant protocol (from the BFT concept; Ethereum's version is called Casper FFG). When validators holding two thirds of all stake vote for a checkpoint, and then for the next one, the first checkpoint becomes final. This takes about two epochs, roughly 13 to 15 minutes. The two-thirds threshold is the same as in PBFT, and the reason is simple arithmetic. With n voters, of whom f may be malicious, and \( n \ge 3f + 1 \), any two groups of \( 2f + 1 \) voters overlap in at least \( f + 1 \) members, so they share at least one honest member, and an honest member never votes for two conflicting blocks. Proof of stake adds accountability: a validator who signs two conflicting votes has produced signed evidence against itself, and the protocol destroys ("slashes") part of its deposit. Reverting a final block would cost at least one third of all stake.
Permissioned chains know their members, so they skip the lottery. Hyperledger Fabric orders transactions with a Raft cluster (which tolerates crashes) or, since Fabric 3, with a BFT ordering service (which tolerates lying members). These give finality in seconds and thousands of transactions per second, because a few dozen known nodes vote instead of thousands of anonymous ones.
The ledger defines a state. Bitcoin uses unspent transaction outputs (UTXOs): each coin is an output that a later transaction spends exactly once. Ethereum uses accounts with balances and contract storage, committed to by a Merkle–Patricia trie whose root is stored in each block header. A smart contract is code for the Ethereum Virtual Machine. Every full node re-executes every transaction, so the code must be deterministic: no clocks, no random numbers, no network calls. Each instruction costs "gas", paid by the sender, so a loop that never ends simply runs out of gas instead of stopping the network. This re-execution by every node is also the main limit on throughput.
Rollups move execution off the main chain. A rollup operator collects thousands of transactions, executes them, and posts the compressed transaction data and the new state root to layer 1. An optimistic rollup assumes the batch is correct and lets anyone submit a fraud proof during a challenge window of about a week. A ZK rollup (from the zero-knowledge-proofs concept) attaches a succinct proof that the new state root follows from the old one by applying exactly these transactions. A contract on layer 1 checks the proof quickly, whatever the batch size, so layer 1 verifies instead of re-executing. The data is still posted, in blobs of 128 KB that nodes keep for about 18 days, so that anyone can rebuild the rollup's state if the operator disappears.

example: Three calculations show how the design behaves: the cost of mining a block, the size of a light-client proof, and how safe a payment is after a few confirmations.
Mining. Suppose the Bitcoin difficulty is D = 1.5 × 10¹⁴, roughly its level in late 2025. The expected number of hashes per block is \( D \times 2^{32} \) ≈ 1.5 × 10¹⁴ × 4.3 × 10⁹ ≈ 6.4 × 10²³. Blocks come every 600 seconds, so the network computes about 6.4 × 10²³ / 600 ≈ 1.07 × 10²¹ hashes per second, about one zettahash per second. A mining company with 10 exahashes per second (10¹⁹) has 10¹⁹ / 1.07 × 10²¹ ≈ 0.93% of the total. The network makes 144 blocks a day, so the company expects 144 × 0.0093 ≈ 1.34 blocks per day. Each block pays 3.125 BTC of new coins (since the April 2024 halving) plus transaction fees. The number of blocks it actually finds follows a Poisson distribution, so on about one day in four it finds none (\( e^{-1.34} \approx 0.26 \)). This variance is why small miners join pools.
Light-client proof. A block holds 4,000 transactions, so its Merkle tree has \( \lceil \log_2 4000 \rceil \) = 12 levels. A wallet that wants to check one payment downloads the transaction, 12 sibling hashes (12 × 32 = 384 bytes) and the 80-byte header. It hashes upward 12 times and compares the result with the Merkle root in the header. The alternative is downloading the whole block, typically 1.5 MB or more. The wallet trusts that the header belongs to the chain with the most work, which it can check from the headers alone.
Confirmations. A merchant receives a payment and waits for z blocks on top of it. An attacker with a share q of the hash rate secretly builds a competing chain that leaves the payment out. Nakamoto's formula gives the chance that the attacker ever catches up. With q = 0.1, it is 20.5% after 1 block, 0.09% after 5 blocks and 0.024% after 6 blocks. With q = 0.3, it is still 13% after 6 blocks, and the merchant needs 24 blocks (about 4 hours) to get below 0.1%. The common rule "wait for 6 confirmations, about one hour" therefore assumes that no attacker controls much more than 10% of the hash rate.
Compare proof-of-stake finality. On Ethereum, after two epochs (64 slots × 12 s = 768 s, about 13 minutes, often quoted as "about 15 minutes" because the votes are counted at epoch boundaries), the block is final in a stronger sense. Reversing it would require validators holding at least one third of the stake to sign conflicting votes and lose their deposits. The merchant waits a similar time, but the guarantee is an explicit economic penalty rather than a probability.
intuition: A public notebook copied by everyone, where each page carries a seal made from the previous page, and the right to write the next page is won in a costly lottery.
The design is natural once you separate two problems. The first is integrity: has anyone changed the past? Hash pointers solve it cheaply, because a hash is a short fingerprint of everything before it. The second is order: who decides what comes next, when anyone can pretend to be a thousand people? Counting heads fails, so open chains count something that cannot be faked: computation spent or money locked. Once influence is tied to a scarce resource, an attacker must own a large share of that resource, and honest participants can compute how deep a block must be before reversing it costs more than it gains. The rest (Merkle proofs, light clients, rollups) follows from one principle: let nodes cheaply check what they cannot afford to recompute.
mistakes: People often think a blockchain makes data true. In fact it only makes a record hard to change after it is written. If someone enters a false shipment record, the chain preserves the false record faithfully. Facts about the outside world still need a trusted source; this is called the "oracle problem".
People often think "immutable" means a transaction can never be reversed. In proof of work, recent blocks can be reorganized, and finality is only probabilistic. Social agreement can also rewrite history, as in Ethereum's DAO fork in 2016. "Final" means "reversal would be very expensive", not "impossible".
People often think blockchains are anonymous. Most are pseudonymous: every transaction between addresses is public forever, and analysis firms link addresses to people through exchanges and spending patterns.
People often think that adding a blockchain makes a system decentralized or more secure. If one company runs all the nodes, it is a slow replicated database. Most large losses have come from stolen keys, contract bugs and cross-chain bridges, not from breaking the hash chain.
friction: Throughput is low because every full node validates every transaction, and each block must spread across the world before the next one is built on it. Bitcoin handles roughly 3 to 7 transactions per second and Ethereum's base layer a few tens, while card networks handle thousands per second on average. Raising block size or frequency raises the hardware and bandwidth needed to run a node, which reduces the number of independent nodes. This tension between scale, security and decentralization is often called the "trilemma".
Proof of work consumes large amounts of electricity by design, because the cost of the work is the security. Proof of stake removes that cost but tends to concentrate stake in a few large staking services and exchanges. Mining concentrates too: a small number of pools produce most Bitcoin blocks, and Eyal and Sirer's "selfish mining" paper (2014) showed that a pool with less than half the hash rate can earn more than its fair share by withholding blocks.
Smart contracts are public, hold money, and usually cannot be patched without special upgrade mechanisms, so one bug can be exploited by anyone within minutes. Cross-chain bridges have been among the largest sources of losses; the Ronin bridge lost more than $600 million in 2022 after attackers obtained validator keys. Keys are bearer instruments: a lost key means lost funds, and a stolen key means an irreversible theft. Rollups add trust points of their own: many rely on a single sequencer, and some can be upgraded by a small group of key holders. Finally, the data never goes away, which conflicts with privacy laws that give people a right to deletion.
practice: Start by asking whether you need a blockchain at all. Use one only when several parties who do not trust each other, and do not accept a common operator, must share a record that none of them can change alone. If one party is trusted, or all parties accept an operator, a database with an append-only audit log, signed entries and a regularly published hash of the log (the design of Certificate Transparency) gives tamper evidence at a tiny fraction of the cost.
If you build on a public chain, choose by finality and cost. Wait for finality that matches the value at risk: a small amount after one or two blocks, a large amount after Ethereum finality or many Bitcoin confirmations. Put application logic on a rollup unless it needs the base layer's security directly, and understand the rollup's trust model: who runs the sequencer, who holds the upgrade keys, and how long withdrawals take.
Treat contract code as safety-critical. Use audited libraries (such as OpenZeppelin), keep contracts small, write tests for invariants, consider formal verification, run bug bounties, and limit damage with caps, pause switches and timelocks on upgrades. Hold keys in hardware security modules or multi-party computation (MPC) wallets with multi-signature approval. In data platforms, never put personal data on chain. Store a hash or commitment on chain and the data off chain, so you can delete the data and keep the proof that it existed.
quiz: What does a block header contain that links the chain and commits to the block's transactions? || The hash of the previous block header, which links the chain, and the Merkle root of the block's transactions, which commits to all of them in 32 bytes. Changing any past transaction changes these hashes all the way to the newest block.
Why can't an open blockchain simply let nodes vote on the next block? || Anyone can create many fake identities (a Sybil attack) and outvote honest nodes. Proof of work or proof of stake ties voting power to a scarce resource, computation or locked coins, which cannot be faked cheaply.
How does proof of stake make a finalized block expensive to revert? || Finality needs votes from validators holding two thirds of the stake. Two conflicting finalized blocks would require at least one third of the stake to sign contradictory votes, which is provable from their signatures and causes their deposits to be slashed.
A Merkle tree covers 2,000 transactions. How many hashes are in an inclusion proof, and how many bytes with SHA-256? || \( \lceil \log_2 2000 \rceil \) = 11 sibling hashes, so 11 × 32 = 352 bytes, plus the 80-byte header if the client does not already have it.
Five companies want a shared, tamper-evident record of shipments. Public chain, permissioned chain, or database? || If one company or a neutral operator can be trusted, a database with signed, append-only, hash-chained logs is cheapest. If none can, a permissioned chain with BFT ordering among the five gives finality in seconds without mining. A public chain adds cost and latency and exposes the data, and is only worth it when outsiders must verify the record without permission.

@@ gpucomp
value: GPU computing uses a graphics processor as a general parallel computer. A modern data-centre GPU such as NVIDIA's H100 has 132 streaming multiprocessors that together keep more than 270,000 threads in flight. It performs about 989 trillion 16-bit floating-point operations per second (989 TFLOPS, dense BF16) and reads its memory at 3.35 TB/s. A large server CPU reaches a few TFLOPS. The GPU gets this by giving up what a CPU spends its transistors on (large caches, branch prediction, out-of-order execution) and spending them on arithmetic units instead.
It exists for workloads that apply the same operation to millions of independent elements: matrix multiplications in deep learning, physics simulation, image and video processing, and more and more data processing (GPU dataframes, GPU SQL engines, Spark with the RAPIDS accelerator). For these workloads one GPU replaces many CPU servers. For AI it is the factory floor: the number of GPUs, their memory and their power budget now decide what models a company can train and serve.
For the layer above (CUDA, NVIDIA's H100, Blackwell and Rubin, AMD Instinct GPUs, and Google's TPU as a close relative), this concept defines the execution model: thousands of threads in lockstep groups, an explicit memory hierarchy, and matrix units. The layers below explain its performance. Batching (L2) supplies enough independent work to fill every core and lets each weight loaded from memory be reused many times. Mixed precision (L2) unlocks the tensor cores, which are about 15 times faster in BF16 than the ordinary FP32 units. FlashAttention (L2) is the model case of keeping data in fast on-chip memory instead of going back to HBM. The roofline model (L3) tells you whether a kernel is limited by arithmetic or by memory bandwidth. Amdahl's law (L4) says that the serial part (data loading, Python overhead, communication) caps the speed-up. Moore's law (L5) paid for the 80 billion transistors on one H100.
terms: Streaming multiprocessor (SM) — one of the GPU's many cores; it holds warp schedulers, arithmetic units, tensor cores, registers and on-chip memory.
Warp — a group of 32 threads that execute the same instruction at the same time (AMD's Instinct GPUs use wavefronts of 64).
Kernel — a function launched on the GPU over a grid of thread blocks.
Thread block — a group of up to 1,024 threads that runs on one SM, can synchronize, and shares that SM's on-chip memory.
Shared memory — fast on-chip memory (up to 228 KB per SM on an H100) that a block's threads manage explicitly.
HBM — high-bandwidth memory: DRAM stacked next to the GPU die; 80 GB at 3.35 TB/s on an H100 SXM.
Tensor core — a unit that multiplies and accumulates small matrix tiles in one instruction, in low precision.
Arithmetic intensity — floating-point operations performed per byte moved to or from memory.
Coalescing — when the 32 threads of a warp touch consecutive addresses, the hardware combines them into a few wide memory transactions.
Occupancy — the share of an SM's maximum resident warps that are actually resident; more warps hide more memory latency.
history: GPUs began as fixed-function chips for drawing triangles; NVIDIA marketed the GeForce 256 (1999) as the first "GPU". In 2001, programmable shaders (GeForce 3, DirectX 8) let developers write small programs that ran for every vertex and every pixel. Researchers soon disguised general computations as graphics: store a matrix in a texture, and write a pixel program that computes one output element per pixel. Stanford's Brook (Ian Buck and others, 2004) hid this trick behind a streaming language.
In November 2006, NVIDIA's G80 architecture (GeForce 8800) replaced separate vertex and pixel units with unified cores, and in 2007 NVIDIA released CUDA, led by Ian Buck, which let programmers write C for the GPU directly. OpenCL (2009) followed as a cross-vendor standard. Machine learning arrived next. Raina, Madhavan and Ng (2009) reported large speed-ups for training deep networks on GPUs, and AlexNet (Krizhevsky, Sutskever and Hinton, 2012) won the ImageNet competition after training for five to six days on two consumer GTX 580 cards.
The hardware then specialized for AI. Volta V100 (2017) introduced tensor cores; Ampere A100 (2020) added the TF32 format and structured sparsity; Hopper H100 (2022) added FP8 and a Tensor Memory Accelerator for bulk copies; Blackwell (2024–2025) added FP4 and placed two dies in one package with 208 billion transistors; Rubin is the next generation. AMD's Instinct line (MI300X, 2023) with the ROCm software stack, and Google's TPU (2016), offered alternatives. Software moved up a level too. Libraries such as cuBLAS and cuDNN (2014) gave tuned kernels, OpenAI's Triton (Philippe Tillet, paper 2019, public release 2021) let researchers write fast kernels in Python, and FlashAttention (Tri Dao and others, 2022) showed that redesigning memory traffic could beat years of tuning.
how: Start with the design choice. A CPU core spends most of its area making one thread fast: caches avoid memory latency, and out-of-order execution and branch prediction keep the pipeline busy. A GPU assumes that there is a huge amount of independent work, and spends its area on many simple arithmetic lanes. It does not try to avoid memory latency; it hides it. When one group of threads waits several hundred cycles for memory, the SM switches, in a single cycle, to another group that is ready. Switching is free because every resident thread keeps its own registers on the chip. This is why a GPU needs tens of thousands of threads to be busy, and why problems with little parallel work run badly on it.
The execution model has four levels. A kernel launches a grid of thread blocks. Each block is assigned to one SM and stays there until it finishes. The SM splits the block into warps of 32 threads, and each cycle a warp scheduler issues one instruction for all 32 threads of a warp. NVIDIA calls this SIMT (single instruction, multiple threads). An H100 SM has four schedulers, can hold 64 warps (2,048 threads), and has 65,536 32-bit registers to share among them. If threads in one warp take different sides of an if-statement, the warp runs both sides one after the other, with some threads switched off each time. This is called divergence, and it is why branchy code wastes a GPU.
Memory is a ladder in which each step is larger and slower. Registers are private to a thread. Shared memory and L1 (256 KB per SM, of which up to 228 KB can be shared memory) are on-chip and are managed by the program. The L2 cache is 50 MB for the whole chip. HBM holds 80 GB at 3.35 TB/s. Host memory is reached over PCIe 5.0 at about 64 GB/s in each direction, roughly 50 times slower than HBM, and other GPUs over NVLink at 900 GB/s in total. Access patterns matter at every step. When the 32 threads of a warp read 32 consecutive 4-byte values, the hardware serves them with one 128-byte transaction (coalescing); when they read scattered addresses, the same load can need 32 transactions.
Tensor cores are dedicated matrix units, four per SM on an H100. One instruction computes \( D = A \times B + C \) on a small tile of matrices. They work in low precision, and this is where the mixed-precision concept adds value: inputs are stored in BF16, FP16 or FP8, while sums are accumulated in FP32 so that rounding errors do not pile up. The numbers show the stakes. An H100 SXM does 67 TFLOPS with its ordinary FP32 units, 989 TFLOPS dense in BF16 on tensor cores, and about 1,979 TFLOPS dense in FP8. A model that runs in plain FP32 uses less than a tenth of the chip.
The roofline model (from the roofline concept) turns these numbers into a test. Attainable speed = \( \min(\text{peak FLOP/s},\ \text{arithmetic intensity} \times \text{memory bandwidth}) \). For an H100 in BF16 the "ridge point" is 989 / 3.35 ≈ 295 FLOP per byte. A kernel below that intensity is memory-bound: faster arithmetic would not help it. Element-wise operations (add, activation functions, normalization) do well under 1 FLOP per byte, so they are always memory-bound. Large matrix multiplications do hundreds to thousands of FLOPs per byte, so they can be compute-bound. Most GPU optimization therefore raises arithmetic intensity. Tiling loads a block of each input matrix into shared memory once and reuses every element dozens of times. Kernel fusion performs several element-wise steps in one pass instead of writing intermediate results to HBM and reading them back. FlashAttention (from the FlashAttention concept) is fusion taken further: it computes attention tile by tile in shared memory with a running softmax, so the \( N \times N \) matrix of attention scores is never written to HBM. It performs some extra arithmetic, recomputing values in the backward pass, but it moves far fewer bytes, so it runs faster.
Batching (from the batching concept) is the other lever. Serving a language model one request at a time is a matrix–vector product: each weight is read from HBM and used for only two operations, about 1 FLOP per byte in BF16. Serving 64 requests together turns it into a matrix–matrix product: each weight read is used 64 times, so intensity rises 64 times for almost the same memory traffic. Batching also amortizes fixed costs, such as the few microseconds needed to launch a kernel.
Amdahl's law (from the Amdahl concept) limits what the GPU can deliver. The GPU speeds up only the parallel part of a job. If 10% of each training step is spent on the CPU (loading and decoding data, Python overhead, waiting on communication that is not overlapped), then even an infinitely fast GPU gives at most a 10 times speed-up. That is why serious GPU code prefetches data, copies it asynchronously from pinned (page-locked) host memory, and keeps tensors on the GPU between steps.
Finally, Moore's law and the end of Dennard scaling (from the L5 concept) explain why GPUs grew while CPUs stalled. Parallel throughput scales with the number of transistors, so each new process node gives more SMs and tensor cores, while single-thread speed no longer improves much. But power no longer falls with transistor size, so an H100 draws up to 700 W and a Blackwell GPU around 1,000 W. Lower precision is partly an answer to the power limit: an 8-bit multiplier needs far less energy and silicon area than a 32-bit one.

example: Use the roofline model on an H100 SXM: peak 989 TFLOPS dense BF16, bandwidth 3.35 TB/s, ridge point about 295 FLOP per byte. Three kernels show the three typical cases.
Case 1, vector addition. Add two arrays of 1 billion FP32 numbers. The kernel reads 8 GB, writes 4 GB and does 10⁹ additions. Intensity = 10⁹ / (12 × 10⁹) ≈ 0.08 FLOP per byte, far below 295, so it is memory-bound. Time ≈ 12 GB / 3.35 TB/s ≈ 3.6 ms. The achieved rate is 10⁹ / 3.6 ms ≈ 0.28 TFLOPS, less than 0.1% of the tensor-core peak. Nothing inside the kernel can fix this; only fusing it with neighbouring operations, so the data is read once for several steps, can.
Case 2, a large matrix multiplication. Multiply two 4096 × 4096 BF16 matrices. FLOPs = 2 × 4096³ ≈ 1.37 × 10¹¹. The minimum memory traffic is three matrices of 4096² × 2 bytes, about 101 MB. Intensity ≈ 1.37 × 10¹¹ / 1.01 × 10⁸ ≈ 1,365 FLOP per byte, well above 295, so it is compute-bound. The lower bound on time is 1.37 × 10¹¹ / 989 × 10¹² ≈ 0.14 ms, while moving the bytes would take only 0.03 ms. A tuned library gets close to this bound, and only because of tiling: without shared-memory reuse, each element would be fetched from HBM 4,096 times.
Case 3, generating text with an 8-billion-parameter model. In BF16 the weights take 16 GB. To produce one token for one user, the GPU must read all 16 GB: 16 GB / 3.35 TB/s ≈ 4.8 ms, so at most about 210 tokens per second. The arithmetic is 2 × 8 × 10⁹ = 1.6 × 10¹⁰ FLOPs, which takes 0.016 ms at peak. The tensor cores are idle more than 99% of the time. Now batch 64 users. The weights are still read once per step (4.8 ms), but each read now serves 64 tokens, and the arithmetic grows to about 1.0 ms, still hidden under the memory time. Throughput rises from about 210 to about 13,400 tokens per second on the same GPU. Intensity reaches the ridge point near a batch of 295. In practice each request also reads its own attention cache, which grows with batch size and context length, so the real gain is smaller, but the lesson stands: for inference, batching is the difference between a wasted GPU and a busy one.
intuition: A CPU is a few expert chefs who can cook any dish quickly; a GPU is a thousand line cooks who all make the same cut at the same moment, and the kitchen's real limit is how fast the pantry delivers ingredients.
The design is natural once you accept that the workload is wide. If you have a million independent multiplications, making one of them fast is pointless; you want as many of them in progress as possible. Then waiting for memory stops being a disaster, because there is always other ready work, and the expensive machinery a CPU uses to avoid waiting can be thrown away. What remains is a simple rule that explains most GPU performance work: arithmetic is cheap, moving data is expensive, so arrange the computation so that every byte brought from memory is used as many times as possible before it is dropped.
mistakes: People often think a GPU is faster than a CPU at everything. In fact a single GPU thread is much slower than a CPU thread, and code with many branches, pointer chasing or little parallel work runs worse on a GPU. The GPU wins only when there are thousands of independent operations with regular memory access.
People often think "GPU-Util 100%" in nvidia-smi means the GPU is fully used. In fact that number only measures the share of time in which at least one kernel was running; a kernel that keeps a single SM busy also shows 100%. Model FLOPs utilization (useful FLOPs divided by peak) is the honest measure, and even Meta's training of Llama 3 405B on 16,384 H100s reached 38–43% in BF16.
People often think more TFLOPS means a faster job. Many kernels, and almost all of LLM token generation, are memory-bound, so HBM bandwidth and capacity matter more than the peak FLOPs figure on the data sheet.
People often think moving work to the GPU always helps. Copying data over PCIe runs at about 64 GB/s, so copying 10 GB costs about 150 ms. If the GPU then finishes the work in 5 ms, the transfer dominates, and the CPU may have been faster overall.
friction: Memory is the main limit, and it is getting worse. From V100 (2017) to H100 (2022), 16-bit tensor throughput rose about 8 times (125 to 989 TFLOPS) while HBM bandwidth rose about 3.7 times (0.9 to 3.35 TB/s), so more kernels end up memory-bound with each generation. Capacity is a limit too: a 70-billion-parameter model in BF16 needs 140 GB for weights alone, more than one H100 holds, which forces splitting models across GPUs and paying for communication.
Programming is hard and vendor-specific. Fast kernels need tiling, careful synchronization and tuning for each architecture. Most of the ecosystem is written for CUDA, which ties users to NVIDIA; AMD's ROCm and HIP, and compilers such as Triton, reduce this lock-in but do not remove it. Irregular work (graph traversal, sparse data, divergent branches) still maps poorly to lockstep warps.
Operations at scale add physical problems. A rack of 72 Blackwell GPUs draws more than 100 kW and needs liquid cooling. Hardware fails often: during a 54-day period of Llama 3 training on 16,384 H100s, Meta recorded 419 unexpected interruptions, 58.7% of them caused by GPU issues. Low-precision formats (FP8, FP4) save time and power but need scaling factors and careful testing to avoid overflow and loss of accuracy. Finally, GPUs are expensive and were often scarce from 2023 onwards, so idle GPUs are among the most costly forms of waste in a data centre.
practice: Profile before you optimize. Nsight Systems (or the PyTorch profiler) shows the timeline: gaps between kernels, CPU stalls, data-loading waits, copies between host and device. Nsight Compute then shows, for one kernel, whether it is limited by memory or by compute. Compute model FLOPs utilization for training jobs; a figure below about 30% usually points to data loading, small batches or communication.
Use the hardware's fast paths. Train in BF16 mixed precision by default, and use FP8 on Hopper and Blackwell through libraries such as Transformer Engine once accuracy is validated. Let a compiler fuse element-wise operations (torch.compile, XLA), and use fused attention kernels (FlashAttention, or PyTorch's scaled_dot_product_attention) rather than writing attention by hand. Keep tensor dimensions multiples of 8 or 16 so that tensor cores can be used fully.
Feed the GPU. Use several data-loader workers, pinned memory and prefetching; keep data on the GPU between steps; avoid calls that force the CPU to wait for the GPU (such as reading a single value with .item() inside a loop). For inference, use servers with continuous batching (vLLM, SGLang, TensorRT-LLM).
For data engineering, GPU dataframes (RAPIDS cuDF) and the RAPIDS accelerator for Spark help with large joins, sorts and aggregations on columnar data, but benchmark the whole pipeline, including transfers and I/O, on your own data. Treat GPUs as a shared, scheduled fleet: split large GPUs into up to seven Multi-Instance GPU (MIG) slices for small jobs, and track utilization per job and per team.
quiz: What is a warp, and why does branch divergence slow it down? || A warp is a group of 32 threads that execute the same instruction together. If threads in a warp take different branches, the warp must run each path in turn with some threads switched off, so part of the hardware is idle.
How does a GPU hide memory latency without large caches or out-of-order execution? || It keeps many warps resident on each SM, each with its own registers. When one warp waits for memory, the scheduler issues instructions from another ready warp in the next cycle, so the arithmetic units stay busy as long as there is enough parallel work.
Why does FlashAttention run faster even though it does more arithmetic than standard attention? || Standard attention writes and reads the N × N score matrix in HBM, so it is memory-bound. FlashAttention computes attention tile by tile in on-chip shared memory with a running softmax and never stores that matrix in HBM; the extra recomputation is cheap compared with the memory traffic it saves.
A kernel reads 6 GB and performs 3 × 10¹¹ FLOPs on an H100 (989 TFLOPS BF16, 3.35 TB/s). Is it memory- or compute-bound, and roughly how long does it take? || Intensity is 3 × 10¹¹ / 6 × 10⁹ = 50 FLOP per byte, below the ridge point of about 295, so it is memory-bound. Time ≈ 6 GB / 3.35 TB/s ≈ 1.8 ms, an achieved rate of about 167 TFLOPS.
Your nightly feature job joins and aggregates 2 TB of Parquet on a CPU Spark cluster. When is moving it to GPUs worth it? || When the job is dominated by compute-heavy stages (joins, sorts, aggregations) on columnar data, so that work saved outweighs transfer and I/O costs, and the data per GPU fits in its memory. If the job is bound by reading from object storage or by shuffles over the network, GPUs add cost without much speed-up; benchmark the full pipeline first.
