@@ wasm
value: WebAssembly (Wasm) is a compact binary format for programs, designed so that a runtime can check it for safety before running it, and then run it at speeds close to native machine code. A compiler such as LLVM, Rust or Go turns source code into a .wasm file once; the same file then runs unchanged in a browser, on a server, or inside another application. The problem it solves is simple to state: for twenty years the only language a web page could run was JavaScript, and the only way to run untrusted code from strangers on a server was a heavy process, container or virtual machine. Wasm gives a third option: portable code that starts in microseconds to milliseconds and is confined by construction.
Who uses it: Figma, Google Earth and AutoCAD ship C++ engines to the browser as Wasm; Photoshop and many video and image tools do the same. On servers and at the edge, Cloudflare Workers, Fastly Compute, Shopify Functions and many plugin systems (Envoy proxy filters, database user-defined functions, editor extensions) run customer-supplied Wasm because it is safe to host and cheap to start. Kotlin, Dart (Flutter) and OCaml compile to Wasm as a target for the browser.
For the layer above, Wasm gives a single compilation target. Language authors do not need to write a new backend for each browser and each operating system; they emit Wasm once. It stands on language runtimes and compilers (L1). The compiler side supplies the front end: C, C++, Rust and others are lowered through LLVM to Wasm instead of x86 or ARM machine code. The runtime side supplies the engine: a Wasm engine is a small language runtime with a validator, an interpreter or compiler, and a memory model. V8, SpiderMonkey and JavaScriptCore embed one in the browser; Wasmtime, Wasmer and WasmEdge are standalone engines.
terms: Module — the compiled unit, a .wasm file with typed functions, memory, tables, imports and exports; it is stateless and can be instantiated many times.
Instance — a running copy of a module with its own linear memory, tables and globals.
Linear memory — one large byte array, grown in 64 KiB pages, that the module reads and writes with bounds-checked loads and stores.
Validation — a check done before execution that proves every instruction has correctly typed inputs and every jump goes to a legal place.
Import and export — the only way a module touches the outside world: it calls functions the host gives it, and offers functions to the host.
Trap — a controlled stop when a module breaks a rule at run time, such as reading outside its memory or dividing by zero.
WASI — the WebAssembly System Interface, a set of standard host functions (files, clocks, sockets) so that Wasm can run outside a browser.
Component model — a layer above modules that describes interfaces with types such as strings, records and lists, so components written in different languages can call each other.
Wasm GC — an extension that lets the engine manage structs and arrays on its own garbage-collected heap, for languages like Kotlin and Dart.
history: Before Wasm, people tried to run fast code in the browser in several ways. Plugins such as Flash and Java applets were fast but insecure and closed. Google's Native Client (2011) ran sandboxed x86 code but was tied to Chrome. Mozilla's asm.js (2013, Alon Zakai and others) took a different route: a strict subset of JavaScript that C++ could be compiled into, which engines could optimize very well. asm.js ran within a small factor of native speed, but it was large to download and slow to parse.
In 2015, engineers from Mozilla, Google, Microsoft and Apple formed a W3C Community Group to design a proper binary format. The first version, the "MVP", shipped in all four major browsers by late 2017. The key paper is "Bringing the Web up to Speed with WebAssembly" by Andreas Haas and colleagues (PLDI 2017). Wasm 1.0 became a W3C Recommendation on 5 December 2019.
Standalone use began when Mozilla announced WASI in 2019 and the Bytecode Alliance formed. Solomon Hykes (Docker's founder) wrote in 2019 that if Wasm and WASI had existed in 2008, Docker might not have been needed; the remark showed how far the idea had spread beyond browsers. WASI 0.2 and the component model shipped in January 2024. WASI 0.3, which adds native asynchronous calls and streams to components, shipped on 11 June 2026.
The core spec kept growing. Wasm 2.0 added 128-bit SIMD, bulk memory operations, reference types and multiple return values. On 17 September 2025, the W3C groups published Wasm 3.0, the current standard. It includes garbage-collected structs and arrays, exception handling, tail calls, typed function references, multiple memories and 64-bit memory addresses.
how: A Wasm module is a binary file that starts with the bytes 00 61 73 6D ("\0asm") and a version number, followed by sections: types (function signatures), imports, functions, tables, memory, globals, exports, and the code itself. Values are only numbers: 32-bit and 64-bit integers, 32-bit and 64-bit floats, 128-bit vectors, and opaque references. Everything richer, such as strings or objects, is built by the compiler on top of linear memory (or, with Wasm GC, on the engine's heap).
The instruction set is a stack machine. An instruction like i32.add pops two numbers from an operand stack and pushes their sum. A stack format is compact and, more importantly, easy to check. Control flow is structured: there is block, loop, if and br (branch), but no goto to arbitrary addresses. A branch can only jump to the end of an enclosing block or the start of an enclosing loop. This one design choice is what makes validation fast. The validator walks the code once, keeping a model of the stack types, and proves in linear time that every instruction gets operands of the right type and every branch is legal. Code that fails is never run. Because the control-flow shape is known, the engine can also compile the module in a single pass, even while the file is still downloading (streaming compilation).
Safety comes from three rules. First, memory: a module's linear memory is a separate byte array. Every load and store uses an index into that array, and the engine guarantees an access outside it traps. On 64-bit machines, engines usually avoid explicit checks. They reserve several GiB of virtual address space for the memory, with unmapped guard pages beyond the end, so that any out-of-range access causes a hardware page fault that the engine turns into a trap. The check becomes free. Second, control flow: the call stack and return addresses live outside linear memory, where the module cannot overwrite them, so classic return-address attacks do not work. Indirect calls go through a table of functions, and the engine checks that the function's type matches the call. Third, authority: a module starts with no ability to do anything. It cannot open files, read the clock or send packets. It can only call functions that the host chose to import. This is capability-based security, and WASI follows it: a program gets a handle to one pre-opened directory, not the whole file system.
How the layers below add value: the compiler side (LLVM, Emscripten, the Rust and Go toolchains, from the language-runtimes concept) does the heavy optimization ahead of time, such as inlining and register allocation, so the engine does not have to. The runtime side then adds only a thin layer. Browsers use two tiers: a very fast baseline compiler (Liftoff in V8) produces working code almost immediately, and an optimizing compiler (TurboFan) recompiles hot functions later. Standalone engines usually compile ahead of time or at load with Cranelift (Wasmtime) or LLVM (Wasmer), and can save the machine code to disk. Because modules are stateless and instances are cheap, hosts like Cloudflare can create a fresh instance per request.
Outside the browser, the component model solves the interface problem. Plain Wasm only passes numbers across the boundary, so passing a string means agreeing on pointers and lengths by hand. Components describe interfaces in WIT (WebAssembly Interface Types), and a canonical ABI defines how strings, lists and records are copied across the boundary between languages. A Rust component can then call a Python component without sharing memory.
In the browser, the host side is the JavaScript API. JavaScript calls WebAssembly.instantiateStreaming(fetch(url), imports) to get an instance, and then calls its exported functions like ordinary functions. Numbers pass directly. Strings and objects are copied into linear memory by glue code that tools such as wasm-bindgen generate. Calls from Wasm back to JavaScript go through the imports object. Each crossing is fast, but not free, which is why designs put whole loops inside Wasm.
On speed: measured honestly, Wasm is usually somewhat slower than native code. Jangda and colleagues (USENIX ATC 2019) found SPEC CPU benchmarks about 45 to 55 percent slower than native on average in Chrome and Firefox, with causes such as bounds checks, fewer registers and less aggressive optimization. SIMD and better compilers have narrowed this since then. For most uses, the speed is high enough, and the large gain is predictable performance and fast start compared with JavaScript or a container.

example: Start with the smallest useful function, in the text format:
(func $add (param i32 i32) (result i32) local.get 0 local.get 1 i32.add)
The body compiles to five bytes: 20 00, 20 01, 6A. Run add(2, 3). local.get 0 pushes 2, and the stack is [2]. local.get 1 pushes 3, and the stack is [2, 3]. i32.add pops both and pushes 5. The function ends with one i32 on the stack, which matches the declared result, so validation passes. If the body were only "local.get 0 i32.add", validation would fail before running, because i32.add needs two values and only one is on the stack. This is why the engine never runs ill-formed code.
Now a memory example. A module declares one memory page: 65,536 bytes, valid addresses 0 to 65,535. An i32.load at address 65,532 reads bytes 65,532 to 65,535 and succeeds. An i32.load at address 65,534 would need bytes up to 65,537, so the engine traps. On a 64-bit host the engine reserves, for example, 4 GiB of address space for the memory and leaves the pages after the one real page unmapped. The load touches an unmapped page, the CPU raises a fault, and the engine converts it into a trap, with no compare-and-branch in the compiled code. The module can call memory.grow to add pages, and the engine maps them in.
Now an image-resize plug-in on an edge server. Your platform lets customers upload a resize function, compiled from Rust to a .wasm file of, say, 300 KB. The host imports one function, read_request, and exports nothing but handle. For each request, the platform creates a new instance (well under a millisecond with pre-compiled code and a memory pool), gives it a 64 MiB memory limit and a 50 ms time budget, and runs handle. If the customer's code loops forever, the host stops it at 50 ms. If it reads outside its memory, it traps, and only that one request fails. A container doing the same job would take hundreds of milliseconds to start and use tens of MB at rest.
intuition: Wasm is a shipping container for programs: one standard box, checked at the port, that fits on any ship and cannot reach into the cargo next to it.
The design is natural once you ask what a safe, portable machine code would need. It must be easy to check (so: typed stack, structured control flow), impossible to escape (so: one bounded memory, no raw jumps, no ambient authority), and easy to compile to every CPU (so: a low-level, C-like model, not a high-level object model). Earlier bytecodes, like Java's, assumed an object model and a garbage collector. Wasm assumed nothing, so any language can fit. The extras, GC and components, are added later and only for those who need them.
mistakes: People often think Wasm will replace JavaScript. In fact Wasm cannot touch the page directly: it has no built-in access to the DOM, and calls go through JavaScript glue code. The two work together; Wasm is for heavy compute or reusing existing C++ and Rust code, JavaScript for the page logic.
People often think Wasm is always faster than JavaScript. In fact modern JavaScript engines are very good on typical web code, and each call across the JS and Wasm boundary has a cost. Wasm wins on number crunching, predictable latency and fast startup of large code bases, not on every workload.
People often think a Wasm program is safe from bugs. In fact the sandbox protects the host from the module, not the module from itself. A buffer overflow inside linear memory can still corrupt the module's own data, and many toolchains do not add stack canaries or address randomization inside it. A bug in the engine itself, or a Spectre-style side channel, can also break the walls.
People often think Wasm is only for browsers. In fact, since WASI and engines like Wasmtime, a large share of new use is server-side and embedded, where the draw is fast, safe isolation, not web page speed.
friction: Garbage-collected languages were the first big gap. Before Wasm GC, a language like Java or Go had to ship its own collector inside linear memory, which made files large and could not cooperate with the browser's collector. Wasm 3.0 standardizes GC types, but toolchains and runtimes are still adopting it unevenly.
Threading is limited. Shared memory and atomics exist, but in browsers they require special cross-origin isolation headers, and there is still no finished standard way to create threads inside a module on the server. The component model and WASI 0.3 are young. Support differs between Wasmtime, Wasmer, browsers and cloud platforms, so "write once, run anywhere" still needs testing on your target.
Debugging and profiling tools lag native ones. Source maps and DWARF support help, but stepping through optimized Wasm is harder than a native debugger. Startup is cheap but not zero: a large module must be downloaded, validated and compiled, and a large desktop-class application of tens of MB can still take seconds to load on a slow phone. Finally, the sandbox limits what you can do: no raw sockets or threads unless the host grants them, so porting a program that expects a full POSIX environment can require real work.
tradeoffs: Choose Wasm over containers when you run untrusted or customer-supplied code at high density and need start times under a millisecond; a node can host thousands of instances in one process. Choose containers when the workload is a whole existing application with threads, native libraries and a full POSIX environment, where a container start of 100 to 500 ms is fine. You give up isolation depth either way: a container shares the host kernel, while Wasm shares the engine, so its security rests on one smaller piece of code.
Choose Wasm over native plug-ins (shared libraries) when a crashing or malicious extension must not take down the host, as in proxy filters or database functions. Choose native plug-ins when you need full speed and the extension is trusted, since Wasm costs roughly 1.1x to 2x in CPU time and copies data across the boundary.
Choose Wasm over JavaScript in the browser when you have an existing large C++ or Rust code base or heavy numeric work such as video, CAD or codecs. Choose JavaScript when the work is mostly DOM, network and small logic; the boundary crossing and extra download can outweigh the compute gain.
Choose Wasm over V8 isolates with JavaScript (as used by Cloudflare Workers) when you want many languages and one portable artifact. Choose isolates with JavaScript when your team already writes JavaScript or TypeScript and wants the largest ecosystem; Wasm adds a build step and a language boundary.
practice: In the browser, compile with Emscripten (C and C++) or wasm-pack and wasm-bindgen (Rust), load with WebAssembly.instantiateStreaming so compilation overlaps the download, and serve the file with the application/wasm content type. Keep the JS and Wasm boundary coarse: pass big buffers once rather than many small values, because each crossing costs time and strings must be copied. Run heavy work in a Web Worker so the main thread stays free. Run wasm-opt (Binaryen) on release builds; it usually makes files smaller and faster.
On the server, choose an engine for your language and need: Wasmtime (Rust, with the best WASI and component support), Wasmer, WasmEdge, wazero (pure Go, no cgo), or WAMR for embedded devices. Set memory limits, an instruction budget (fuel) or a deadline, and restrict imports to the minimum. Treat the import list as your security policy: every function you pass in is a power you grant. For plug-in systems, define the interface with WIT and generate bindings instead of passing raw pointers.
Measure on the real engine. Compare Wasm against your native build and against plain JavaScript for the specific job, with a cold start and a warm run. Check which proposals your targets support (SIMD, threads, GC) before relying on them, and keep a fallback.
quiz: What are the three main rules that make a Wasm module safe to run? || The module can only access its own bounds-checked linear memory; control flow is structured and checked (no arbitrary jumps, typed indirect calls, return addresses outside memory); and it has no authority except the functions the host imports.
Why does Wasm use structured control flow instead of goto? || Because every branch targets the end of a block or the start of a loop, the validator can prove the code is well typed in one linear pass, and the engine can compile it in a single pass, even while downloading.
How can an engine bounds-check memory with no compare instruction on a 64-bit machine? || It reserves several GiB of virtual address space for the memory and leaves everything past the real size unmapped (guard pages). An out-of-range access causes a page fault, which the engine converts to a trap.
A module has 2 memory pages. What is the highest valid address for a 4-byte i32.load, and what happens at the next address? || Memory is 2 x 65,536 = 131,072 bytes. The highest valid start address for a 4-byte load is 131,068; at 131,069 the load would pass the end, so the engine traps.
Your platform runs customer code per request. When would you pick Wasm over containers, and what do you give up? || Pick Wasm when you need sub-millisecond starts and thousands of instances per node. You give up a full POSIX environment and native threads, and you accept CPU cost of roughly 1.1x to 2x versus native code.
interview: Why not just use the JVM bytecode or a container for sandboxing plug-ins? || JVM bytecode assumes an object model and GC and has a large runtime and attack surface; Wasm has a tiny typed core with no ambient authority. Containers share the kernel and cost hundreds of ms and MBs per start. Wasm gives a per-request instance in microseconds to ms with a smaller trusted base, at the price of a restricted environment.
How does an engine enforce memory safety fast, and where can it still fail? || Bounds checks via guard pages or explicit compares, typed indirect calls, and a separate call stack. It still fails if the engine has a bug, with Spectre-style side channels, or when the bug is inside the module itself, since linear memory has no internal protection.
What does the component model add over core Wasm and WASI 0.1? || Core Wasm passes only numbers, so strings or structs need hand-written pointer conventions. Components use WIT interfaces and a canonical ABI to pass rich types between languages, and WASI 0.2 and 0.3 are built from such interfaces, with 0.3 adding native async and streams.
A Wasm service is slower than expected. How do you investigate? || Separate startup (download, validate, compile; try AOT or pre-compilation) from steady state (profile hot loops, check SIMD use, bounds-check cost). Count boundary crossings and copies between host and module. Compare optimization level and wasm-opt, and check whether the engine is in baseline or optimizing tier.
Why did Wasm need a separate GC proposal instead of letting languages bring their own collector? || A collector in linear memory cannot see references held by the host or other modules, cannot scan the real call stack, and bloats the download. Engine-managed structs and arrays let the host collector do the work and let cycles across Wasm and JS be collected.

@@ cuda
value: CUDA is NVIDIA's platform for running general programs on its GPUs. You write a function called a kernel in an extended C++ language, launch it from the CPU, and the GPU runs that one function on thousands to millions of threads at the same time. Before CUDA, a GPU could only do graphics, and anyone who wanted to use its raw arithmetic had to disguise their problem as drawing triangles with shader programs. CUDA removed the disguise: it gave programmers memory they can allocate, threads they can index, and a compiler and debugger that look like normal C++ tools.
The reason it matters is the shape of modern workloads. A server CPU has perhaps 64 to 128 strong cores. An NVIDIA H100 has 132 streaming multiprocessors, each able to hold up to 2,048 resident threads, and a memory system that delivers about 3 TB/s, many times what a CPU socket delivers. Matrix multiplication, which is the core of deep learning, fits this shape perfectly. This is why PyTorch, TensorFlow, vLLM and nearly all AI training and serving code end up calling CUDA kernels, either hand-written ones or ones from NVIDIA's libraries (cuBLAS for matrix multiplication, cuDNN for neural network layers, NCCL for communication between GPUs, TensorRT for inference).
For the layer above, CUDA gives a stable programming model on top of changing hardware. It stands on the NVIDIA GPU concept (nvgpu), which supplies the actual hardware: streaming multiprocessors, registers, shared memory, tensor cores and high-bandwidth memory. It stands on GPU computing (gpucomp), which supplies the idea: a throughput machine that hides slow memory by switching between many threads, instead of making each thread fast. CUDA is the contract between the two: it names the hardware's parts in a way a program can use, and keeps old programs running on new chips. Much of NVIDIA's lead comes from this software layer and its libraries, not only from the chips.
terms: Kernel — a function marked __global__ that runs on the GPU, executed by many threads in parallel when launched from the CPU.
Thread block — a group of up to 1,024 threads that run on the same streaming multiprocessor and can share fast memory and synchronize with each other.
Grid — all the blocks of one kernel launch; blocks in a grid cannot synchronize with each other during the kernel.
Warp — 32 threads of one block that the hardware runs together, executing the same instruction at the same time (SIMT).
Streaming multiprocessor (SM) — one of the GPU's processing units, holding a register file, shared memory, schedulers and execution units; blocks are assigned to SMs.
Shared memory — fast on-chip memory (up to about 228 KB per SM on H100) that the threads of one block can read and write together.
Coalescing — when the 32 threads of a warp read neighbouring addresses, the hardware merges them into a few wide memory transactions.
Occupancy — the fraction of an SM's possible resident threads that are actually resident; more resident warps give the scheduler more work to hide delays.
PTX — NVIDIA's virtual instruction set; the compiler emits PTX, and the driver turns it into the GPU's native machine code (SASS).
history: GPUs started as fixed graphics pipelines. In the early 2000s, researchers used programmable shaders for general work ("GPGPU"), writing science code in graphics languages. At Stanford, Ian Buck built Brook, a language that treated the GPU as a stream processor. NVIDIA hired him and, with John Nickolls and others, built CUDA. The G80 chip (GeForce 8800, November 2006) was the first with a unified, general-purpose design, and CUDA 1.0 shipped in June 2007.
The early years built the habits that remain. Version 1 had the grid, block and thread hierarchy, shared memory and __syncthreads. Fermi (2010) added caches and error-correcting memory for scientific computing. In 2012, the AlexNet team trained an image classifier on two consumer GTX 580 GPUs and won the ImageNet contest by a wide margin; deep learning researchers then adopted CUDA, and NVIDIA released cuDNN in 2014 to serve them. That feedback loop, in which researchers wrote code for CUDA and so NVIDIA built more for CUDA, is the core of its moat.
Hardware kept moving. Volta (2017) added tensor cores, units that multiply small matrices in one step. Ampere (2020) added asynchronous copies from global to shared memory. Hopper (2022) added thread block clusters, a tensor memory accelerator and FP8; Blackwell (announced 2024) added FP4 and a dedicated tensor memory. Each generation changed the best way to write kernels, so libraries such as CUTLASS carry that knowledge.
CUDA is now at the 13.x series; the official programming guide in autumn 2026 covers version 13.4. Competitors exist: AMD's ROCm and HIP, Intel's oneAPI and SYCL, and OpenAI's Triton (2021), a Python-based language that compiles to GPU code and is used inside PyTorch's compiler. None yet matches CUDA's library depth.
how: A CUDA program has two parts. Host code runs on the CPU. It allocates GPU memory (cudaMalloc), copies data in (cudaMemcpy), and launches a kernel with a special syntax: my_kernel<<<gridSize, blockSize>>>(args). Device code is the kernel, written like a C++ function. Inside it, each thread reads built-in variables (threadIdx, blockIdx, blockDim) to find which piece of data it owns, typically with i = blockIdx.x * blockDim.x + threadIdx.x. The compiler nvcc (built on LLVM) splits the file, compiles the host part with a normal C++ compiler, and turns the device part into PTX and then native code for chosen GPU generations. Embedding PTX lets the driver compile for newer GPUs later.
At launch, the GPU's scheduler hands blocks to SMs. A block stays on one SM until it finishes. The SM splits the block into warps of 32 threads and runs them under a warp scheduler. All 32 threads of a warp execute the same instruction in lock-step, each on its own data and registers; NVIDIA calls this SIMT (single instruction, multiple threads). If threads of a warp take different sides of an if statement, the hardware runs both sides one after the other with some threads switched off. That is warp divergence, and it can halve speed for a two-way branch.
The key idea of the throughput design is latency hiding. A read from global memory (the GPU's main memory, HBM) takes several hundred clock cycles. A CPU hides this with big caches and out-of-order execution. A GPU instead keeps many warps resident on each SM (up to 64 on H100). When one warp waits for memory, the scheduler switches to another in the same cycle, at no cost, because each warp's registers stay in the huge register file (65,536 32-bit registers per SM). So the performance of a kernel depends on keeping enough independent work in flight: occupancy, and the number of memory requests per thread.
The memory hierarchy decides the speed. Registers are private to a thread and are the fastest. Shared memory is per block, with latency of roughly 20 to 30 cycles, and it is organized in 32 banks; if two threads of a warp hit the same bank at different addresses, the accesses are serialized (a bank conflict). The L2 cache (about 50 MB on H100) is shared by the whole GPU. Global memory has the highest bandwidth but the longest latency, and it is fast only when accesses coalesce: 32 threads reading 32 consecutive 4-byte floats cover 128 contiguous bytes, which the hardware serves with a few 32-byte sector requests, while 32 scattered reads can need 32 sector requests and waste most of the bandwidth. The standard optimization is tiling: a block loads a tile of data from global memory into shared memory once, synchronizes with __syncthreads, and then every thread reuses the tile many times.
Compatibility works through two levels of code. PTX is a virtual instruction set that stays stable across generations; SASS is the real machine code, which changes with every architecture and is identified by a compute capability number (9.0 for Hopper, for example). A binary that contains PTX can be compiled by the driver for a GPU that did not exist when the program was built. This is how the language-runtime idea of a portable intermediate form shows up in CUDA, and it is how a ten-year-old CUDA program can still run on a new chip, though not always at the best speed. Memory has a similar convenience: unified memory (cudaMallocManaged) gives one pointer that works on both CPU and GPU and migrates pages on demand, which is easy to write but slower than explicit copies when the access pattern is not planned.
Around the kernel there is a second system of asynchrony. Kernel launches and memory copies are placed in streams (ordered queues); work in different streams can overlap, so a copy for batch 2 runs while the kernel for batch 1 computes. Each launch has a CPU-side cost of a few microseconds, so for many small kernels CUDA Graphs record a whole sequence once and replay it with one launch. Multiple GPUs communicate through NCCL, using NVLink within a server and network cards between servers. The hardware generations from the nvgpu concept matter here: tensor cores are reached through special instructions (or libraries such as cuBLAS and CUTLASS), and Hopper-era kernels use the tensor memory accelerator to copy whole tiles asynchronously.

example: Take the standard first kernel, y = a*x + y over n = 1,048,576 (2^20) floats.
__global__ void saxpy(int n, float a, const float* x, float* y) { int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) y[i] = a * x[i] + y[i]; }
Launch it with 256 threads per block: grid size is ceil(1,048,576 / 256) = 4,096 blocks, so 1,048,576 threads, one per element. Thread 5 of block 3 gets i = 3 x 256 + 5 = 773. The if (i < n) guard protects the last block when n is not a multiple of 256. In each warp, threads i to i + 31 read 32 consecutive floats, which is perfectly coalesced.
Now cost it. Each element moves 12 bytes: read x (4), read y (4), write y (4). In total 12 x 2^20 = about 12.6 MB. An H100 with about 3 TB/s of memory bandwidth can move that in 12.6 MB / 3 TB/s = about 4 microseconds. The arithmetic is only 2 operations per element, about 2 million in all, which the GPU does in well under a microsecond. So the kernel is memory-bound: its speed is set by bytes, not by FLOPs. Launch overhead is a similar few microseconds. Copying the two 4 MiB input arrays from the CPU over PCIe at roughly 50 GB/s takes about 170 microseconds, forty times longer than the kernel. The lesson: a GPU only pays off if data stays on the GPU across many kernels, or each byte gets a lot of arithmetic.
Next, the tiling gain on matrix multiplication of two 1,024 x 1,024 float matrices. Each output element needs 1,024 multiply-adds. Naively, each thread reads 2 x 1,024 values from global memory, so 2 x 1,024^3 = about 2.1 billion loads, 8.6 GB of traffic if no cache helped. With 32 x 32 tiles in shared memory, each value loaded from global memory is reused by 32 threads, so traffic falls 32 times to about 270 MB. At 3 TB/s that is about 90 microseconds instead of nearly 3 ms. Real GPUs have caches that soften the naive case, but the order of magnitude explains why every serious matrix kernel uses tiling.
Occupancy example: a block has 256 threads (8 warps). The kernel uses 64 registers per thread, so one block needs 256 x 64 = 16,384 registers. An SM has 65,536, so 4 blocks fit: 1,024 resident threads out of 2,048, which is 50% occupancy. Cutting to 32 registers per thread would allow 8 blocks, but might force the compiler to spill values to slow memory. Tuning is a balance.
intuition: A GPU is a stadium of thousands of slow workers, all reading the same instruction sheet in rows of 32; you get speed by giving every worker a seat of its own data, not by making any worker faster.
The model is natural once you accept that memory is the bottleneck. Raw arithmetic is cheap and memory access is slow, so the design spends silicon on many simple lanes, a very large register file, and fast context switching, and gives up the CPU's tricks for making a single thread fast. CUDA exposes just enough of this: a hierarchy that maps to the hardware (thread, warp, block, grid), explicit memory levels, and barriers. If you think in terms of "which thread owns which data, and who reads which memory in which order", the rest follows.
mistakes: People often think each GPU thread is like a CPU thread, only many more. In fact a GPU thread is a lane in a warp. The 32 lanes share one instruction stream, and divergence serializes them. Thousands of threads are cheap because they are not independent processors.
People often think a GPU is always faster than a CPU. In fact for small data, branchy code, or work with little arithmetic per byte, the cost of copying over PCIe (about 50 GB/s) and launching kernels can exceed the whole CPU runtime. The GPU wins for large, regular, data-parallel work.
People often think more threads or higher occupancy always means higher speed. In fact occupancy only needs to be high enough to hide latency. Kernels that use many registers per thread for more instruction-level parallelism, such as the best matrix-multiplication kernels, often run at low occupancy and still reach peak speed.
People often think a kernel's launch returns when the work is done. In fact launches are asynchronous: the CPU continues immediately, errors may appear later at some other CUDA call, and timing code without cudaDeviceSynchronize or events measures only the launch.
friction: The first problem is difficulty. A correct kernel is easy; a fast one needs knowledge of coalescing, bank conflicts, occupancy, register pressure, tensor core shapes and asynchronous copies, and the best choices change with each GPU generation. The best code for Hopper differs from the best code for Ampere. Debugging runs on thousands of threads with no printf-style stepping; compute-sanitizer and Nsight Compute help, but races and out-of-bounds writes are still hard to find.
The second problem is lock-in. CUDA is closed and runs only on NVIDIA hardware. The compiler and the libraries are proprietary, and years of tuned code (cuDNN, cuBLAS, NCCL) are what competitors must match. AMD's HIP can translate much CUDA source, but performance and library coverage differ. Triton and compilers such as MLIR-based stacks reduce the dependency for new kernels, though the generated code still targets PTX on NVIDIA.
Third, scaling problems: GPU memory is small compared with model sizes (80 to 288 GB per GPU on current parts), so large models split across GPUs, and communication through NVLink and the network becomes the limit. Power and supply also constrain use. Errors can be silent: a data race or an unlucky floating-point summation order gives results that differ slightly between runs, because adding floats in a different order gives different rounding.
tradeoffs: Choose a library call (cuBLAS, cuDNN, cuFFT, Thrust) when your operation is standard. Vendor engineers have tuned it per GPU model, and you will rarely beat it for plain matrix multiplication. Choose a custom kernel when you can fuse several steps (for example attention, or a norm plus activation) so the data never returns to global memory; fusion can cut memory traffic several times. You give up portability and maintenance time either way.
Choose Triton (or a similar tile-based Python language) when you want 70 to 90 percent of hand-tuned speed in a fraction of the development time, and your kernel is mostly tile arithmetic. Choose CUDA C++ with CUTLASS or inline PTX when you need the last 10 to 30 percent, or features such as explicit warp specialization and clusters that high-level tools do not yet expose.
Choose CUDA over ROCm or SYCL when the ecosystem matters: the framework you use, the tools, the availability of engineers and cloud GPUs. Choose a portable stack when you are bound to AMD or Intel hardware, want to avoid single-vendor risk, or the workload is simple enough that the library gap does not hurt.
Choose a GPU over a CPU when the work is data parallel and has more than roughly 10 to 50 arithmetic operations per byte moved, and the data can stay on the device. Choose the CPU for small batches, irregular control flow, or low latency on single items, where the PCIe copy and a launch cost of 5 to 10 microseconds dominate.
practice: Start with the profiler, not intuition. Nsight Systems shows the timeline (gaps between kernels, copies, CPU stalls), and Nsight Compute shows each kernel's bandwidth, occupancy, stall reasons and roofline position. Decide first whether a kernel is memory-bound or compute-bound; compare achieved bandwidth with the roughly 3 TB/s limit.
Follow a few habits. Use block sizes that are multiples of 32 (128 or 256 is a common start). Make neighbouring threads access neighbouring addresses. Use structure-of-arrays rather than array-of-structures layouts. Stage reused data in shared memory, and pad shared arrays to avoid bank conflicts. Keep data on the GPU between kernels and overlap copies with compute using streams and pinned host memory. Replace chains of tiny kernels with one fused kernel or a CUDA Graph. Check every call's return code, and run compute-sanitizer on new code.
In deep learning, rarely write raw CUDA. Use PyTorch with torch.compile, use fused attention kernels from libraries, and drop to Triton or CUDA only for a measured hotspot. Read the CUDA Programming Guide's chapters on the programming model and memory, and work through the book "Programming Massively Parallel Processors"; Stanford CS149 covers the same ideas with a systems view.
quiz: What are a thread, a warp, a block and a grid, and which can synchronize? || A thread is one execution lane; a warp is 32 threads executing the same instruction together; a block is up to 1,024 threads on one SM that share shared memory and can synchronize with __syncthreads; a grid is all blocks of a launch, and blocks cannot synchronize with each other inside a kernel.
Why does a GPU run so many more threads than it has execution units? || Global memory latency is several hundred cycles, so while one warp waits, the scheduler switches to another warp at no cost because every warp's registers stay in the register file. Many resident warps hide the latency.
Why is the SAXPY kernel memory-bound, and how long should it take for 2^20 floats on a 3 TB/s GPU? || It does 2 operations but moves 12 bytes per element, so about 12.6 MB in total. At 3 TB/s that is about 4 microseconds, set by bandwidth rather than arithmetic.
A kernel uses 128 registers per thread with 256-thread blocks. An SM has 65,536 registers and a 2,048-thread limit. What is the occupancy? || One block needs 256 x 128 = 32,768 registers, so 2 blocks fit: 512 threads out of 2,048, which is 25% occupancy.
When would you write a custom fused kernel instead of calling cuBLAS and cuDNN steps in sequence? || When several steps are memory-bound and can share data in registers or shared memory, such as attention or normalization plus activation, because fusion avoids writing and reading intermediates from global memory. Do it only after profiling shows the traffic matters, since you take on tuning and maintenance cost.
interview: Explain warp divergence and how you would measure and reduce it. || Threads of a warp share one instruction stream, so if they take different branches, the warp runs both paths with lanes masked off. Measure with Nsight Compute (branch efficiency, active threads per warp). Reduce by reorganizing data so neighbouring threads take the same branch, using predication or sorting work by type.
A kernel reaches only 30% of peak memory bandwidth. What do you check? || Coalescing (stride, array-of-structures layout), enough memory requests in flight (occupancy and loads per thread), L2 hit rates, and whether the kernel is limited by launch gaps or by atomics. Compare achieved bandwidth with the device's measured peak, not the datasheet.
Why does PCIe transfer often dominate small GPU jobs, and what are the fixes? || PCIe moves about 50 GB/s against 3 TB/s on device memory, so copying is 60 times slower per byte. Keep data resident on the GPU, overlap transfer with compute using streams and pinned memory, batch work, or use unified memory with prefetch for oversubscription.
How do tensor cores change how you write a matrix-multiplication kernel? || Tensor cores multiply fixed-size tiles in one instruction at much higher throughput than the standard cores, so the kernel must feed them tiles in the right layout and data type (FP16, BF16, FP8). Real kernels use libraries or CUTLASS, load tiles asynchronously into shared memory, and pipeline loads and math so tensor cores never wait.
Why can floating-point results differ between two runs of the same CUDA kernel? || Floating-point addition is not associative. Parallel reductions and atomic adds combine values in an order that depends on thread timing, so rounding differs. Use deterministic reduction orders or fixed-size tree reductions when reproducibility matters, at some cost.
What would make you pick Triton over CUDA C++ for a new operator? || Faster development and portability across GPU generations, with the compiler handling tiling, shared memory and some scheduling. Pick CUDA C++ if the kernel needs fine control that Triton does not expose, such as warp specialization or special instructions, and the speed gain justifies the work.

value: V8 is the JavaScript and WebAssembly engine inside Chrome, Edge, Node.js, Deno and Cloudflare Workers. It takes JavaScript source text, which is dynamically typed and was designed in ten days in 1995 for small page scripts, and runs it fast enough to build whole applications, such as Google Docs in the browser or an API server handling thousands of requests per second. The core problem is that a dynamic language hides everything the machine needs to know. In `a.x + b.x`, the engine does not know whether `a` is an object, which fields it has, where `x` is stored, or whether `+` means number addition or string joining. A simple interpreter must look all of this up at every execution, which is 10 to 100 times slower than compiled C.
V8's answer is to watch the program run, guess the types from what it sees, generate machine code for the guess, and fall back safely if the guess turns out wrong. For the layer above, this means that React, Node.js servers and browser pages written in plain, flexible JavaScript run at a speed once expected only from typed, compiled languages. The browser (browser) and React (react) both rely on it: Chrome's page scripts run in V8, and React components are ordinary JavaScript functions that V8 compiles.
V8 stands on language runtimes and compilers (langruntime), and is a compact example of nearly all of that concept: a parser that builds an abstract syntax tree, a bytecode interpreter, several just-in-time (JIT) compilers at different speed and quality levels, a generational garbage collector, and the ability to throw compiled code away and return to the interpreter (deoptimization). Each piece reuses compiler ideas (SSA intermediate forms, register allocation, inlining) but adds one key ingredient from language runtimes: runtime feedback.
terms: Isolate — one independent copy of the V8 engine with its own heap; a Chrome tab or a Node.js worker thread runs one isolate.
Ignition — V8's bytecode interpreter; it runs all code first and records type feedback.
Hidden class (map) — a hidden description of an object's shape, meaning its field names and their order, shared by all objects built the same way.
Inline cache (IC) — a small cache at each property access site that remembers which shape it saw and where the field is, so the next access skips the lookup.
Deoptimization — throwing away optimized code when one of its assumptions fails, and continuing in the interpreter from the exact same point.
Tiering — using cheap compilers first and expensive compilers later, only for code that runs often.
Event loop — the single loop that takes one queued task at a time and runs it to completion; Node.js uses libuv to implement it.
Orinoco — V8's garbage collector project: generational, with parallel, incremental and concurrent phases.
Smi — a small integer stored directly in a tagged pointer-sized value, so it needs no heap allocation.
history: Google released Chrome and V8 on 2 September 2008. The V8 team was led by Lars Bak in Aarhus, Denmark, who had earlier built virtual machines for Self, Smalltalk (Strongtalk) and Java HotSpot. At the time, JavaScript engines were plain interpreters. V8 compiled JavaScript straight to machine code, used hidden classes and inline caches (techniques from the Self language), and had a generational collector. It was several times faster than competitors, and started a speed race with Mozilla, Apple and Microsoft.
In 2009 Ryan Dahl combined V8 with an event loop and non-blocking I/O to create Node.js, which put JavaScript on servers. In 2010, V8 added the Crankshaft optimizing compiler. By 2016 the old design was a burden: it used a lot of memory on phones and was hard to extend, and it handled new language features badly. V8 replaced it with Ignition, a bytecode interpreter, plus TurboFan, a new optimizer, shipped together from Chrome 59 in 2017. Ignition also cut memory use, which mattered for low-end phones.
The next steps added more tiers between the two. Sparkplug (Chrome 91, 2021) is a baseline compiler that turns bytecode directly to machine code with no analysis. Maglev (Chrome 117, 2023) is a fast mid-tier optimizer; the V8 team reports it compiles about 10 times faster than TurboFan and 10 times slower than Sparkplug. Other changes include pointer compression (Chrome 80, 2020, which shrank the heap by roughly 40 percent), the Orinoco collector, and a move of TurboFan's back end to a new design called Turboshaft. Chrome ships a new V8 about every four weeks.
how: Execution begins with parsing. The parser first does a quick "pre-parse" of functions to find syntax errors and skip bodies that are never called (lazy parsing), then fully parses a function when first called and builds an abstract syntax tree. Ignition turns that tree into compact bytecode for a register machine and starts running it right away. The bytecode is slow compared with machine code but starts instantly and uses little memory. While it runs, V8 collects feedback in a per-function feedback vector: for each property access, call and arithmetic operation, it records which object shapes, which function targets and which number types appeared.
The data-model idea is the hidden class. In a naive dynamic language, an object is a dictionary, and reading `o.x` means hashing the name "x". V8 gives every object a pointer to a map that describes its shape. Objects created by the same constructor, assigning fields in the same order, share one map, and the fields sit at fixed offsets in the object. Adding a field moves the object to a new map through a transition. Now `o.x` becomes: check that the object's map equals the expected one, then load from a fixed offset. The inline cache stores the expected map and offset at that exact property-access site. If the site always sees one map it is monomorphic and the check is a single compare; with 2 to 4 maps it is polymorphic; with more it becomes megamorphic and falls back to a slower shared hash lookup.
When a function becomes hot, measured by invocation and loop counts, V8 promotes it up the tiers. Sparkplug first removes interpreter dispatch cost by emitting machine code that does the same steps. Maglev and then TurboFan read the bytecode plus the feedback vector and build an intermediate graph in static single assignment form. Using the feedback, they speculate: "this addition always saw small integers" becomes a 32-bit integer add with an overflow check; "this site always saw map M" becomes a map check and a fixed-offset load; small functions are inlined at call sites. After the optimizations (dead code removal, escape analysis, range analysis), the graph is lowered and assigned registers. Every speculation is guarded by a cheap check. If a check fails, execution deoptimizes: V8 rebuilds the interpreter's stack frame from the optimized code's state, resumes in Ignition, and the function may later be re-optimized with the new feedback. This is why the engine can be both aggressive and correct. The language runtime ideas from the layer below, JIT tiers and speculative optimization, are given their sharpest form here.
Memory is managed by a generational garbage collector. New objects go into a small young generation, collected by a scavenger that copies live objects between two semi-spaces; most objects die young, so this is cheap. Objects that survive two scavenges move to the old generation, which is collected by mark-compact. Orinoco makes marking mostly concurrent, running on helper threads while JavaScript continues, and does sweeping and compaction in parallel, so main-thread pauses stay at a few milliseconds even for large heaps.
Numbers and arrays follow the same speculative logic. A small integer (Smi) is stored inside the pointer-sized value itself, so integer loops allocate nothing; a fractional number is boxed on the heap unless the optimizer proves it can stay in a register. Arrays carry an elements kind, such as packed small integers, packed doubles or generic values, and an array can only move toward the more general kind, so one stray string in a numeric array makes every later access slower. To cut start-up cost, V8 keeps a snapshot of the initial heap (the built-in objects) so a new isolate starts without rebuilding them, and embedders such as Chrome and Node.js can store compiled bytecode in a code cache, so a script seen before skips parsing and compiling. WebAssembly runs in the same engine: a fast baseline compiler (Liftoff) produces code at download speed and TurboFan recompiles hot Wasm functions.
Finally, the concurrency model. A JavaScript isolate runs on one thread. In the browser and in Node.js, an event loop takes a task, runs it to completion, then drains the microtask queue (promise callbacks) before the next task. I/O does not block: Node.js hands sockets to the operating system's readiness API (epoll on Linux) through libuv, and file, DNS and some crypto work to a thread pool of 4 threads by default, then queues the callback when done. This lets one thread serve tens of thousands of idle connections, but any long synchronous computation delays every other callback.

example: Take a hot function and watch the tiers: function getX(o) { return o.x; }
Call 1 uses Ignition. The feedback vector slot for `o.x` is empty, so V8 does a full lookup: find the map of `o`, find "x" in its descriptors, and read the value. It then stores the pair (map M1, slot 0) in the inline cache. Call 2 with another object of map M1 hits the cache: one compare and one load. After a few thousand calls the function is compiled by Sparkplug, then by Maglev and TurboFan. The optimized code is roughly: if (o.map != M1) deoptimize; return load(o + 12). Two machine instructions, and when getX is inlined into its caller, often zero.
Now the shape trap. Suppose the program creates objects like this: `{x, y}` for half of the calls, and `{y, x}` for the other half (the same fields in a different order). They have two maps, so the site is polymorphic with 2 maps, and the optimized code checks both. If there are 5 different shapes, which happens when objects are built with fields added conditionally, the site becomes megamorphic. Each access now goes through a global hash table keyed by (map, name). It is several times slower than a monomorphic load, and the function can no longer be inlined well.
Now a deoptimization. function add(a, b) { return a + b; }. It is called a million times with small integers. TurboFan emits a 32-bit add and a jump if the result overflows. Then one call add("a", "b") arrives. The type check fails, V8 deoptimizes, rebuilds the interpreter frame and finishes the call as string concatenation. The feedback vector now says "numbers and strings", so the next optimization is less specialized and slower. This is why a hot function that is fed a rare type can lose speed for the whole run.
Last, the event loop cost. An HTTP handler does 1 ms of CPU work per request. One Node.js process can then serve at most 1,000 requests per second. If one request in 100 does a 200 ms synchronous JSON transform, then during those 200 ms about 200 other requests wait in the queue, and the p99 latency becomes at least 200 ms even though the average CPU use is only about 3 ms per request. The fix is to move such work to a worker thread, split it into chunks, or run more processes.
intuition: V8 is a clerk who first reads each form slowly, notices that every form is filled the same way, and then builds a stamp that handles that kind of form instantly, while keeping the slow method in a drawer for the odd form.
The design is natural because real programs are far more regular than the language allows. Most functions see one or two kinds of objects and numbers. A dynamic language pays for flexibility at every operation, but a runtime can watch what actually happens and pay only for the flexibility that is used. Deoptimization is what makes the bet safe: the compiler may be wrong, because it can always return to the plain interpreter and continue with exactly the same result.
mistakes: People often think JavaScript is interpreted and therefore slow. In fact V8 compiles hot code to optimized machine code, and for numeric loops with stable types, the result can be within a small factor of C. What stays slow is code that keeps changing types and shapes.
People often think Node.js is single-threaded, so it cannot use many cores. In fact your JavaScript runs on one thread, but libuv uses a thread pool for file and some other work, V8 uses helper threads for compilation and garbage collection, and you can run worker threads or one process per core. The limit is that JavaScript objects are not shared between isolates, except through copied messages or SharedArrayBuffer.
People often think async/await makes code run in parallel. In fact it only avoids blocking while waiting; two awaited promises run concurrently only if their work is I/O handled outside the JavaScript thread. A loop of CPU work inside an async function still blocks the loop.
People often think micro-benchmarks show how fast code will be. In fact a tiny benchmark has one shape and one type, so V8 optimizes it perfectly and may even remove the work as dead code. The real application, with many shapes, is slower. Measure with realistic data and profile the production workload.
friction: The main cost of this design is unpredictability. Performance depends on hidden state: which shapes each site has seen, whether a function was optimized, whether it was deoptimized, and whether the collector runs at a bad moment. The same source can run 5 times slower after a small change in how objects are created. Warm-up is also a cost: a short-lived process, such as a serverless function, spends much of its life in the interpreter, which is why V8 uses snapshots and code caches to speed up start.
Memory is a second problem. Objects carry headers, strings can be large, and the generational collector needs spare space to copy into. A Node.js process commonly needs several hundred MB for modest work, and a default old-generation limit (depending on version and machine, around 2 to 4 GB on 64-bit systems) can be hit by large data sets. Pauses are short but not zero, and heap snapshots of a leaking service are heavy to analyze.
Third, the single-threaded model: one blocked call stalls everything in that isolate, and CPU-heavy work needs worker threads or other processes. Fourth, security: a speculative JIT is a large attack surface. Type confusion bugs in optimized code are a leading source of Chrome exploits, so V8 invests in a sandbox that confines the damage, and in 2018 side-channel attacks such as Spectre forced changes to timers and shared memory. Last, because JavaScript semantics are huge and tricky, V8 is a very large and complex code base.
tradeoffs: Choose a V8-based runtime (Node.js, Deno) for I/O-bound services with many concurrent connections, shared code with a browser front end, and a fast development loop. Choose Go, Java or Rust when your work is CPU-heavy, needs many cores in one process with shared memory, or has strict p99 latency targets, since a V8 service gives up shared-memory threads and has a GC with less tuning.
Choose to run more processes per machine (the cluster pattern, or one container per core) when handlers are CPU-light and you want simple scaling; choose worker threads when you need to offload a few CPU-heavy tasks and want to share memory through SharedArrayBuffer. Processes cost memory (each starts with perhaps 50 to 100 MB); workers are lighter, but cannot share ordinary objects.
Choose TypeScript with consistent object construction (same fields, same order, fields initialized in constructors) when performance matters; the types do not make V8 faster by themselves, but the discipline keeps shapes stable. Choose WebAssembly for hot numeric kernels with predictable speed instead of fighting the JIT, accepting the cost of crossing the JS boundary.
Choose V8 isolates (Cloudflare Workers) over containers for edge code that must start in a few milliseconds; you give up native modules and a full operating system. Choose containers when you need them.
practice: Profile before guessing. Run Node with --cpu-prof or use Chrome DevTools to find the hot functions, and use --trace-deopt and --trace-opt to see functions being optimized or thrown back to the interpreter. For memory, take heap snapshots and look for growing retained objects; the --max-old-space-size flag sets the old-generation limit, and you should set it below the container memory limit.
Write monomorphic code in hot paths. Create objects with the same fields in the same order, preferably through a class or a constructor that initializes every field; do not add or delete properties later (delete makes an object slow); avoid mixing integers, doubles and strings in one array, because arrays have element kinds (all small integers, all doubles, generic) that only change toward the more general. Prefer typed arrays for numeric buffers.
Keep the event loop free: do CPU-heavy work in worker_threads, break long loops with setImmediate, and use streams for large bodies instead of reading them whole. Watch event loop delay with perf_hooks.monitorEventLoopDelay; it is a more honest health signal than CPU alone. Never block with *Sync file calls in a server's request path. And set the thread pool size (UV_THREADPOOL_SIZE) if file system or crypto calls queue up.
quiz: What does a hidden class (map) give V8, and what breaks it? || It gives objects of the same shape a shared description with fixed field offsets, so a property read becomes a map check plus one load. Creating objects with fields in different orders, or adding and deleting properties later, creates different maps and slows inline caches.
Why can V8 optimize aggressively without being incorrect? || Optimized code is guarded by cheap checks on its assumptions (types, maps). When a check fails, V8 deoptimizes, rebuilding the interpreter state and continuing in Ignition, so the result is always the same as the plain semantics.
What is the difference between a monomorphic, polymorphic and megamorphic access site? || Monomorphic sites have seen one object shape, polymorphic sites 2 to 4, and megamorphic sites more than that. Cost rises from a single compare, to a few compares, to a slow global hash lookup.
A Node.js handler takes 2 ms of CPU. What is the maximum throughput of one process, and what happens if 1% of requests take 300 ms synchronously? || About 500 requests per second per process at 2 ms each. A 300 ms request blocks the loop, so everything behind it waits up to 300 ms, and tail latency rises sharply; use worker threads or more processes.
When would you move a computation from JavaScript to WebAssembly or a worker thread? || Move it to a worker thread when it is CPU-heavy and blocks the event loop; move it to WebAssembly when you need steady, JIT-independent speed on numeric loops and the cost of copying data across the JS boundary is smaller than the gain.
interview: How does a JIT use runtime feedback, and what happens when feedback is wrong? || The interpreter records types and object maps per site. The optimizer specializes code for them and guards each assumption. On a guard failure, V8 deoptimizes to the interpreter frame with identical state and may re-optimize with updated feedback. The cost is wasted compile time and a slow period.
Why is a megamorphic site slow, and how would you fix it in an application? || The engine cannot assume one shape, so it cannot use a single map check and fixed offset, nor inline the target; it uses a global hash lookup. Fix by building objects consistently (same fields and order), splitting a generic function into specific ones, or separating different kinds into different call sites.
Explain the Node.js event loop and where a long task hurts. || One thread takes a callback from a queue, runs it to completion, drains microtasks, then polls I/O. A long synchronous function stops all callbacks, including timers and health checks, so latency grows for all clients. Offload to worker threads, chunk the work, or use another process.
How does V8's garbage collector keep pauses short? || It is generational: most objects die young and are reclaimed by a cheap copying scavenger. For the old generation, marking runs concurrently on helper threads, with incremental steps and parallel compaction, so the main thread only does short final pauses.
How would you scale a CPU-bound Node.js service to 16 cores? || Run one process per core (cluster or container replicas) behind a load balancer for independent requests, or use a worker thread pool inside a process for offloaded tasks. Watch memory per process and shared-nothing limits; keep state in an external store or pass data by message.

Sparkplug removes dispatch overhead almost at no compile cost; Maglev gets most of the optimized speed at about a tenth of TurboFan's compile cost, so hot code speeds up sooner and TurboFan can wait for truly hot code, saving CPU and energy.

@@ fastapi
value: FastAPI is a Python framework for building web APIs where the type hints on your functions are the single source of truth. You write a function such as `def get_item(item_id: int, q: str | None = None)`, and FastAPI uses those hints to read the value from the URL, convert it to an int, reject bad input with a clear error, pass the clean value to your code, and publish an OpenAPI description plus an interactive documentation page, all without extra code. Before FastAPI, a Python team usually wrote the validation by hand, wrote the documentation separately, and found out they disagreed in production.
The problem it solves is drift between three things that should always match: what the API checks, what the API does, and what the API documents. In most frameworks these are three separate artefacts. In FastAPI, they all come from one declaration, so they cannot drift. This is why it spread quickly in teams that serve machine-learning models, internal tools and LLM applications: a data scientist can turn a function into a typed HTTP endpoint in ten lines, and the front-end or another service can generate a client from the OpenAPI file.
For the layer above, FastAPI gives a service-shaped wrapper around Python code. It stands on Python (python), which supplies type annotations, the asyncio event loop, and the introspection that lets a library read a function's signature at start-up. It stands on microservices (microservices), because its natural unit is a small service with a clear HTTP contract that others call over the network and that you deploy and scale on its own. And it stands on web architecture (webarch), which supplies the HTTP rules it implements: methods, status codes, headers, JSON bodies, content negotiation and CORS.
terms: ASGI — the Asynchronous Server Gateway Interface, the Python standard for how an async web server talks to an async web application; the successor of WSGI.
Starlette — a small ASGI toolkit that provides routing, requests, responses, WebSockets and middleware; FastAPI is built directly on top of it.
Pydantic — a library that checks and converts data according to Python type hints; its core is written in Rust in version 2.
OpenAPI — a standard, machine-readable description of an HTTP API (paths, parameters, request and response shapes).
Dependency injection — a mechanism where a function declares what it needs with Depends(), and the framework builds and passes those objects for each request.
Event loop — the single-threaded loop that runs async functions and switches between them whenever one waits for I/O.
Uvicorn — an ASGI server that accepts connections, parses HTTP, and calls the application.
Response model — a type that describes what an endpoint returns, used to filter and validate the output and to document it.
history: Sebastián Ramírez started FastAPI in 2018 after trying many frameworks and tools and finding that none combined editor help, validation, documentation and speed. The first release was in December 2018. He built it on two existing libraries: Starlette by Tom Christie (the author of Django REST framework), which provides the web layer, and Pydantic by Samuel Colvin, which provides the data layer. Python 3.6 had added variable annotations in 2016 and the typing module was maturing, so the idea of using hints at run time (which Pydantic does) was ready.
The background is the move from WSGI to ASGI. WSGI (PEP 333, 2003) assumes one request per thread and cannot do WebSockets or long-lived connections well. ASGI, developed by Andrew Godwin for Django Channels around 2016 to 2018, made the application interface asynchronous. Python's asyncio had arrived in 3.4 (2014) and async/await in 3.5 (2015). FastAPI was one of the first frameworks designed around it from the start.
Adoption grew fast. By the early 2020s it was one of the most-starred Python web projects, used by teams at companies such as Microsoft, Netflix and Uber, and widely for ML serving. In 2023, Pydantic 2 rewrote validation in Rust, with large speed gains, and FastAPI supported it from version 0.100.0 (July 2023). FastAPI is still numbered 0.x, with frequent releases; version 0.162.0 appeared in October 2026.
how: The design has three layers. At the bottom, an ASGI server such as Uvicorn (using the uvloop event loop and the httptools parser, both written in C) accepts TCP connections, parses HTTP and calls the application object with a scope (request metadata) and two channels: receive and send. In the middle, Starlette matches the URL to a route, runs middleware (CORS, compression, sessions), and handles WebSockets and background tasks. On top, FastAPI adds the type-driven part.
The type-driven part works at start-up. When you write `@app.get("/items/{item_id}")` on a function, FastAPI inspects its signature once. It classifies each parameter: names that appear in the path are path parameters, simple types not in the path are query parameters, Pydantic models are the JSON body, and parameters whose default is Depends(...) are dependencies. For each, it builds a validator from Pydantic. It also builds the OpenAPI entry (using JSON Schema) from the same information. Nothing about this happens per request, so the cost is paid once.
Per request, the flow is: Starlette finds the route; FastAPI reads the query string, headers and body; it solves the dependency tree (calling each dependency, caching results within the request); Pydantic validates and converts each value; if anything is wrong, FastAPI returns HTTP 422 with a JSON list that names the exact location and reason of each error; otherwise it calls your function with clean, typed values. After the function returns, the result is checked and filtered by the response model (so an internal field like password_hash can be removed), serialized to JSON and sent. The OpenAPI file is served at /openapi.json, Swagger UI at /docs and ReDoc at /redoc.
Concurrency is where Python's runtime shapes the framework. If you declare the endpoint `async def`, it runs directly on the event loop; while it awaits a database or HTTP call, the loop serves other requests, so one process can hold thousands of waiting requests. If you declare it with plain `def`, FastAPI runs it in a thread pool (AnyIO, 40 threads by default), so a blocking library does not freeze the loop. Because of the Global Interpreter Lock (GIL), neither mode runs Python code on two cores at once, so you scale across cores with several worker processes (Gunicorn managing Uvicorn workers, or one container per core), each with its own event loop.
Pydantic deserves a closer look, because it is where most per-request CPU goes. In version 2 the validation logic is compiled into a tree of validators in a Rust library (pydantic-core) when a model class is created. Validating a JSON body then means one call into Rust that parses the bytes, checks every field and builds the Python object, instead of a Python loop over fields; the Pydantic project reports that this is between 5 and 50 times faster than version 1, depending on the model. Validation has a lax mode (the default, where the string "5" becomes the integer 5) and a strict mode (where it is an error), and you choose per model or per field. Types such as Optional, Union, Literal, datetime, UUID and nested models are all understood, and the same declaration yields the JSON Schema used in the OpenAPI file.
The app also has a life cycle. A lifespan handler runs once when the process starts and once when it stops, which is the right place to create a database pool, load an ML model or open a message-queue connection. Background tasks run small jobs after the response is sent, in the same process. WebSocket endpoints and streaming responses use the same routing and dependency system. Because everything runs on the one event loop per worker, shared resources such as a connection pool are created per process, not shared between workers.
Dependency injection is the structure for everything shared: authentication, database sessions, settings, pagination. A dependency is just a function (or an async generator with `yield`, so it can open a resource before the request and close it after). The same mechanism is how the framework decides what to document: a dependency that needs an OAuth token adds the security scheme to the OpenAPI file automatically. From the microservices concept comes the habit of treating that OpenAPI contract as the interface between teams, with generated clients and contract tests. From web architecture comes everything on the wire: it follows HTTP semantics for status codes, caching headers, and content types, so standard proxies, load balancers and API gateways work in front of it with no special support.

example: A small service for orders:
class Order(BaseModel): sku: str; qty: int = Field(gt=0, le=100)
@app.post("/orders") async def create(order: Order, user = Depends(current_user)): return await save(order, user)
A client posts {"sku": "A-17", "qty": 0}. Pydantic sees qty = 0, which fails gt=0. FastAPI answers 422 without calling create, with a body like {"detail": [{"type": "greater_than", "loc": ["body", "qty"], "msg": "Input should be greater than 0"}]}. A client posting {"sku": "A-17", "qty": "5"} succeeds: in default mode Pydantic converts the string "5" to the integer 5. A path such as /users/abc for a handler with `user_id: int` gets a 422 as well, with the reason that the value is not a valid integer. You wrote no checking code, and the OpenAPI file lists qty as an integer between 1 and 100.
Now the concurrency arithmetic. Suppose each request makes one database call that takes 50 ms and your code uses almost no CPU. With `async def` and an async driver, one process can have thousands of requests waiting at the same time; the limit is CPU, perhaps 1,000 to 3,000 requests per second if each needs 0.3 to 1 ms of Python work. With plain `def` and a blocking driver, the pool of 40 threads limits you to 40 / 0.05 s = 800 requests per second per process. If the database call takes 200 ms instead, that falls to 200 per second. Now the trap: if you declare `async def` but call a blocking library such as `requests.get` or a synchronous database driver inside, the whole event loop stops for that time. With a 50 ms blocking call, the process serves 20 requests per second in total, far worse than the plain `def` version, and health checks time out too.
Scaling out: if one worker handles about 1,500 requests per second at your typical request size, a 4-core container with 4 workers can handle roughly 4 x 1,500 = 6,000 requests per second, if the database and downstream services allow it. Memory is about 60 to 150 MB per worker, so the same 4 workers use under 1 GB.
intuition: FastAPI is a form with a built-in clerk: you print the form once as a Python type, and the clerk checks every filled form against it, files the good ones, rejects the bad ones with a note, and also prints the instruction leaflet.
The design is natural because the type hint already says what the data is. A framework only has to read it. Once the declaration exists in one place, validation, conversion, documentation and editor autocomplete are all different views of the same fact. The cost of reading hints is paid at start-up, and the per-request work is validation, which Pydantic's Rust core makes cheap.
mistakes: People often think async def makes an endpoint fast. In fact it only helps when the work inside waits on I/O through async libraries. Putting blocking calls or CPU loops inside async def freezes the whole event loop, and a plain def endpoint would have been safer, because FastAPI runs it in a thread pool.
People often think FastAPI is as fast as Go or Rust frameworks because it says "fast". In fact the name refers to its speed on par with Node.js frameworks and to fast development. Python's interpreter limits it: expect one worker to handle thousands, not hundreds of thousands, of simple requests per second, and plan to scale with processes.
People often think type hints are checked by Python at run time. In fact Python ignores them; it is FastAPI and Pydantic that read them and enforce the rules. If you call the same function directly from other code, nothing is validated.
People often think the response is returned exactly as your function builds it. In fact, when you declare a response model, FastAPI validates and filters the output against it. That is useful for hiding fields, but it also costs time, and a return value that does not fit the model produces a server error.
friction: The first limit is Python itself. The GIL means one process uses one core for Python code, so CPU-bound work such as image processing, large JSON handling or model inference inside the request handler blocks other requests in that worker. You move heavy work to a process pool, a task queue (Celery, Arq), or a separate model server, and keep the API layer thin. Memory per worker is large compared with Go or Rust, so cost per request is higher at very large scale.
The second is the sync and async split. Libraries come in both kinds, and mixing them badly is the most frequent production bug. Some drivers (SQLAlchemy's async mode, asyncpg, httpx) are fine; others are not. The ecosystem is also young: FastAPI has no built-in database layer, admin panel, authentication system or migrations, so teams assemble SQLAlchemy, Alembic and an auth library themselves, and larger projects need strong conventions.
Third, FastAPI remains at 0.x, and Pydantic's version 1 to version 2 change broke many projects; pinning versions and reading release notes is needed. Validation is not free either: for large payloads, such as a list of 100,000 objects, building Pydantic models can cost more than the business logic. Finally, the automatic OpenAPI file covers the happy path well, but descriptions, examples and error responses still need human work to be a real contract.
tradeoffs: Choose FastAPI over Flask when you want typed validation, automatic documentation and native async for I/O-heavy work; choose Flask or Django when you need a mature batteries-included stack (Django's ORM, admin and auth), server-rendered pages, or your team already knows it. FastAPI makes API services quick to build, while Django makes complete web applications quick to build.
Choose `async def` with async drivers when each request waits mostly on network calls and you expect hundreds of concurrent requests per process. Choose plain `def` with a thread pool when you rely on blocking libraries or the code is simple; its limit of about 40 concurrent calls per process is enough for many internal services. Mixing is allowed per endpoint.
Choose Python (FastAPI) for ML-serving glue, internal tools, and services where development time dominates and a single instance handles under a few thousand requests per second. Choose Go, Java or Rust for the hot path of high-throughput services, where per-request overhead of microseconds and many cores in one process matter. Many teams keep a FastAPI layer for orchestration and a compiled service for the hot path.
Choose a response model on every public endpoint to stop accidental data leaks, accepting the extra serialization cost. Choose to return raw dicts or pre-serialized bytes only on hot endpoints, where you have measured the cost.
practice: Structure the project into routers (APIRouter) by domain, with schemas (Pydantic models), services and data access in separate modules. Use separate input and output models: for example UserCreate with a password, and UserRead without it. Use dependencies for the database session (yield in a dependency, so cleanup always runs), for current user, and for settings loaded from environment variables through pydantic-settings.
In production, run behind a reverse proxy or load balancer with several worker processes; a common start is one worker per CPU core, then measure. Set timeouts, limit request body size, and expose a cheap health endpoint. Use async drivers (asyncpg, httpx.AsyncClient) inside async def, and wrap unavoidable blocking calls with run_in_threadpool. Measure event loop lag; if it exceeds tens of milliseconds, something is blocking.
Test with the built-in TestClient (Starlette's, based on httpx) and override dependencies in tests with app.dependency_overrides. Check the generated OpenAPI file in CI to catch accidental breaking changes. Add examples and descriptions to fields so /docs can be used by other teams as the real reference, and generate typed clients from /openapi.json. For model serving, load the model once in the lifespan handler rather than per request, and run inference in a worker pool or a dedicated serving system if it uses much CPU or GPU time.

@@ kafka-streams
value: Kafka Streams is a Java library that lets an ordinary application read Kafka topics, keep state (counts, joins, windows), and write results back to Kafka, with no separate processing cluster. You add one dependency, write a topology of operators in a few dozen lines, and deploy the app like any other service. If you start more copies of it, they share the work automatically. If a copy dies, the others take over its share and rebuild its state from Kafka.
The problem it answers is operational. Systems such as Spark Streaming and Flink need their own cluster, scheduler, deployment pipeline and on-call knowledge. Many streaming jobs are small: enrich events, count per key, join two topics, de-duplicate. For those, running a second distributed system is more cost than the job is worth. Kafka Streams makes the stream processor a library, so your service is the processing cluster, and the thing you already operate (Kafka plus your normal container platform) does the heavy parts.
For the layer above (microservices that react to events, materialized views, fraud and alerting rules, real-time metrics), it supplies stateful processing with exactly-once results. It stands on three lower concepts. Kafka (kafka) supplies everything distributed: input and output topics, partitions that define parallelism, consumer groups that assign partitions to instances, compacted topics that back up state, and transactions that make writes atomic. RocksDB (rocksdb) supplies the local state: a fast embedded key-value store that keeps state on disk, so it can be much larger than memory. Stream processing (streamproc) supplies the vocabulary and semantics: operators over unbounded streams, state, event time, windows and late data.
terms: Topology — the directed graph of processing steps (sources, processors, sinks) that you define; it is the program.
KStream — a record stream where each event is an independent fact, such as a click.
KTable — a table built from a stream of updates per key, where a new record for a key replaces the old value; it is the latest-value view of a changelog.
Task — the unit of parallel work: one task handles one partition (of each input topic) of a sub-topology, with its own state stores.
State store — local storage for a task's state, by default RocksDB on local disk.
Changelog topic — a compacted Kafka topic where every update of a state store is also written, used to rebuild the store after a failure.
Repartition topic — an internal topic Kafka Streams creates when you change the key, so records with the same new key land on the same partition.
Standby replica — a copy of a task's state kept up to date on another instance, so failover is fast.
Stream time — the largest record timestamp seen so far by a task; windows close according to it, not according to the wall clock.
history: Kafka started at LinkedIn in 2010 as a log for moving events. Soon the consumers of that log needed to compute things, and the available tools were heavy: Samza (also born at LinkedIn) needed YARN, and Storm and Spark needed their own clusters. The Kafka team at LinkedIn and later Confluent argued that most stream processing is "just" a consumer and a producer with state, and that a library could do it.
Kafka Streams was released with Kafka 0.10.0 in May 2016, introduced by Jay Kreps in the post "Introducing Kafka Streams: Stream Processing Made Simple". It started with the KStream and KTable abstractions, local state with RocksDB, and changelog topics. Exactly-once processing arrived in Kafka 0.11 (2017) with idempotent producers and transactions (KIP-98 and KIP-129). Kafka 2.4 added incremental cooperative rebalancing (KIP-429) so that a rebalance no longer stops every task, and Kafka 2.5 and 2.6 reworked the exactly-once design to use one producer per thread rather than per task (KIP-447; the setting was renamed exactly_once_v2 in Kafka 3.0), which made large deployments practical. Kafka 2.6 added warm-up replicas so that new instances catch up before taking over a task (KIP-441).
The design and its guarantees were described in the SIGMOD 2021 paper "Consistency and Completeness: Rethinking Distributed Stream Processing in Apache Kafka" by Guozhang Wang and colleagues. Kafka 4.0 (March 2025) removed ZooKeeper entirely. In Kafka 4.2 (February 2026), a new broker-driven rebalance protocol for Streams (KIP-1071) became generally available with a limited feature set, moving task assignment from the clients to the brokers.
how: A Kafka Streams program defines a topology: sources that read topics, processors that transform records, and sinks that write topics. Operators fall into two groups. Stateless ones (map, filter, flatMap, branch) look at one record at a time. Stateful ones (count, aggregate, reduce, joins, windowed operations) need memory of earlier records, and these are the ones that use state stores.
Parallelism comes from Kafka's partitions. The library splits the topology into sub-topologies at every point where data must be re-keyed. For each sub-topology, it creates one task per input partition: a topic with 12 partitions gives 12 tasks. A task owns the processing and the state for its partition, and nothing else. Tasks are assigned to stream threads, which run inside application instances. Because instances belong to one consumer group (from the Kafka concept), the group coordinator on the brokers distributes the partitions, and the assignment logic then places tasks, tries to keep a task where its state already is, and spreads standby replicas. Add an instance, and the group rebalances so that it takes some tasks. Remove one, and its tasks move to the others. The hard upper limit on useful threads is the number of tasks, which is the partition count.
State lives in a local store per task and per operator. The default store is RocksDB (from the RocksDB concept): an LSM tree, which turns random updates into sequential writes, and gives sorted keys, so window and range queries are fast. State can therefore be far larger than memory. An in-memory cache in front of the store merges repeated updates to the same key (statestore.cache.max.bytes, 10 MB by default), so the output topic does not get one record per input record. Each update is also written to the store's changelog topic, which is compacted (only the latest value per key is kept), so it stays about as big as the state itself. If an instance dies, whoever receives its task reads the changelog from the beginning and rebuilds the store. A standby replica keeps reading the changelog all the time, so failover takes seconds, not minutes.
Time works on records. Each record has an event timestamp, and a windowed aggregation groups records into tumbling, hopping, sliding or session windows by that timestamp. There are no separate watermarks. Instead, stream time advances with the largest timestamp seen, and a window accepts late records until stream time passes the window end plus a grace period; records later than that are dropped. This is simple and deterministic, with a cost: a quiet partition does not advance, and window results can be delayed.
Correctness comes from Kafka transactions. With processing.guarantee set to exactly_once_v2, one atomic transaction covers, for each batch, the output records, the changelog writes and the commit of the consumer offsets. Either all of these become visible or none do, and downstream consumers using read_committed never see aborted data. If a task crashes mid-batch, the transaction aborts and the replay produces the same results once. The price is a commit interval (100 ms by default with exactly-once, 30 seconds otherwise) and extra transaction overhead.
Below the high-level DSL there is the Processor API, where you write your own processor class, read and write state stores directly, and schedule a punctuation, a callback that fires on stream time or wall-clock time, for example to flush a buffer every minute. The DSL is built on it. A GlobalKTable is a special table that is fully replicated to every instance (not partitioned), so it can be joined with any key without co-partitioning; it suits small reference data such as country codes. Interactive queries let one instance read its local stores over its own API, though the caller must find which instance owns a key.
Joins deserve a separate note. A stream-table join looks up the current value in a table for every stream record. A stream-stream join keeps both sides in windowed stores. Both need co-partitioning: the two topics must have the same number of partitions and the same key partitioning, so that matching keys land in the same task. If you change a key (selectKey, groupBy), the library writes the stream to a repartition topic and reads it back, which costs a full extra pass of write, replication and read.

example: Count page views per user per hour, then join with a user table.
Input topic "views" has 6 partitions, keyed by user id. The topology is groupByKey, windowedBy(1 hour, grace 10 minutes), count. That creates 6 tasks. Start 3 instances: each runs 2 tasks. Start a 4th: after the rebalance, the tasks split 2, 2, 1, 1. A 7th instance would sit idle, because there are only 6 tasks.
Suppose the app holds 60 million active (user, window) keys at roughly 100 bytes each: 6 GB of RocksDB state in all, or 1 GB per task. A task's changelog holds about 1 GB, too. If an instance fails and its two tasks move to another instance without standbys, that instance reads 2 GB from the changelog; at an effective 100 MB/s, this takes about 20 seconds before it can process those partitions, and the lag of those partitions grows meanwhile. With one standby replica per task, the standby is a few seconds behind, so the pause is a few seconds. Standbys cost extra disk and network for every state update, so they double storage for the protected tasks.
Now a record arrives at 10:03 with timestamp 09:58 while stream time is 10:07. The window 09:00 to 10:00 closed at 10:00 plus 10 minutes grace, which is 10:10. Stream time 10:07 is before 10:10, so the record is still counted. If stream time had been 10:11, it would be dropped and the drop counted in a metric.
For the join, the user table topic "users" must also have 6 partitions with the same key. If it has 8, the join fails at start-up with a co-partitioning error. If the stream were keyed by session id instead, you would first call selectKey(userId), which writes 100 percent of the records to a repartition topic and reads them back, doubling Kafka traffic for that step.
intuition: Kafka Streams is a crew of workers sharing a row of numbered mailboxes: each worker keeps a notebook for the mailboxes it owns, copies every notebook entry into a shared log, and if a worker leaves, someone else picks up the mailboxes and rereads the log to restore the notebook.
The design is natural once you see that Kafka already solves the hard parts. Partitions give ordering and parallelism; consumer groups give membership and failover; compacted topics give durable state; transactions give atomicity. What is left is a thin layer that keeps local state beside each partition and writes every change back to Kafka. The processing cluster is simply "all instances of your app."
mistakes: People often think Kafka Streams is a server you install, like Flink. In fact it is a library inside your own JVM service. There is no Streams cluster to start. Your instances, and Kafka, are the whole system.
People often think the state lives in Kafka and RocksDB is only a cache. In fact the local RocksDB store is the working copy that serves reads and writes, and the changelog topic is its backup. After a restart, the state must be restored from the changelog unless the local files survive (a persistent volume allows a fast restart by reading only the missing tail).
People often think adding more instances always makes it faster. In fact the maximum parallelism is the number of tasks, set by the partition count of the input topics. With 6 partitions, a seventh instance does nothing. Also, you cannot easily change the partition count of a keyed input topic later, because state is partitioned by the old layout.
People often think exactly-once means the outside world is touched exactly once. In fact the guarantee covers reading from Kafka, updating state and writing to Kafka. A call to an external HTTP service or database from inside a processor can repeat after a retry unless that system is idempotent.
friction: The biggest limit is that it is tied to Kafka and the JVM. Inputs and outputs are Kafka topics, so databases and files enter and leave through Kafka Connect. There is no official Python or Go version. Parallelism is capped by partitions, and state is sharded the same way, so a hot key produces a hot task that cannot be split.
Rebalances and state restoration are the main operational pain. When membership changes, tasks move and stores must be rebuilt, which can mean minutes of lag for large state. Cooperative rebalancing, standby replicas, warm-up replicas, static membership and the new broker-side protocol all reduce this, but do not remove it. RocksDB memory also needs care: each store has its own buffers and caches, so an app with many stores can use far more memory than expected unless you bound it with a shared cache.
Event-time handling is simpler than in Flink and less flexible: no watermarks, no custom triggers, and per-partition stream time, so quiet partitions delay windows. Late data beyond the grace period is lost. Repartitioning, joins on non-co-partitioned data, and large windowed joins all multiply storage and traffic. Finally, schema changes to a topology (adding a stateful operator, renaming a store) can make old changelogs and repartition topics incompatible, so upgrades need planning.
tradeoffs: Choose Kafka Streams when your data is already in Kafka, the logic is per-key (counts, joins, enrichment, small state machines), and your team prefers deploying a service over running a cluster. Choose Flink when state is very large, you need rich event-time control (watermarks, custom windows, SQL), many non-Kafka sources, or independent scaling of processing from partition count. You give up operational simplicity with Flink, and flexibility with Kafka Streams.
Choose a plain consumer plus producer when the work is stateless or the state is tiny and held in an external database; Kafka Streams adds topology, changelog and rebalance behavior you may not need. Choose Kafka Streams when you need local, partitioned state with exactly-once updates, because building that yourself is a large project.
Choose standby replicas when failover must be seconds and the state is large (gigabytes per task); choose no standbys when the state is small or restore takes only a few seconds, since standbys cost extra disk, network and CPU for every update. Choose a persistent volume for state directories when instances restart often.
Choose exactly_once_v2 when results feed money, inventory or counters that must not double count; choose at_least_once when output is idempotent or approximate, because exactly-once adds transaction overhead and a longer commit path, and lets latency rise by up to the commit interval. Choose ksqlDB or Flink SQL if analysts, not Java developers, write the logic.
practice: Plan partitions first: the partition count of keyed input topics is your parallelism ceiling and is hard to change, so choose with headroom (for example 2 to 3 times the instances you expect). Keep keys well distributed. Name every stateful operator and store explicitly (Materialized.as, Named), so a topology change does not rename internal topics and break upgrades.
Run instances on persistent volumes or use standby replicas (num.standby.replicas=1) for large state. Set num.stream.threads according to cores, and keep the total of threads across instances at or below the task count. Bound RocksDB memory with a RocksDBConfigSetter that shares one block cache and write buffer budget. Monitor consumer lag, the restore-time metrics, record-lateness and dropped-record metrics, and the state directory size. Use static membership (group.instance.id) with a session timeout so a rolling restart does not trigger a rebalance for every pod.
Test with TopologyTestDriver, which runs a topology without a broker, then with a few integration tests on real Kafka. Use interactive queries only for read-mostly lookups and keep the service stateless from the outside by reading from output topics. Upgrade carefully: read the upgrade guide of each Kafka release, because Streams has had breaking changes in internal formats.
quiz: What determines the number of tasks in a Kafka Streams app, and what does that limit? || The number of partitions of the input topics (per sub-topology) gives the number of tasks. It caps useful parallelism: more threads or instances than tasks stay idle.
Why is every state store update also written to a changelog topic? || The local RocksDB store is not replicated. The compacted changelog is its durable backup, so after a failure or move, another instance can rebuild the store by replaying the changelog.
How does exactly_once_v2 achieve exactly-once results inside Kafka? || It wraps output records, changelog writes and consumer offset commits in one Kafka transaction per batch. If the task fails, the transaction aborts and the batch is replayed; downstream consumers using read_committed never see aborted records.
A topic has 8 partitions, state is 16 GB in total, and restore speed is 80 MB/s. How long does a single instance need to restore everything from scratch, and how do standbys help? || About 16,000 MB / 80 MB/s = 200 seconds. A standby replica for each task keeps its store close to current, so failover only replays the last few seconds of changelog.
When would you choose Flink over Kafka Streams? || When state is very large or processing must scale beyond partition count, when you need advanced event-time features such as watermarks and custom windows, or when sources and sinks are not Kafka. Kafka Streams is better when the data is in Kafka and a library inside your service is enough.
interview: Explain what happens, step by step, when an instance of a Kafka Streams app crashes. || The consumer group coordinator notices missing heartbeats and rebalances. The crashed instance's tasks go to others (preferably those with standby copies). Each new owner restores the store from the changelog (or catches up the standby), then resumes from the last committed offset. Open transactions are aborted, so no partial output appears.
Why do joins require co-partitioning, and what do you do when topics are not co-partitioned? || A task sees only one partition of each topic, so matching keys must be in the same partition number. If partition counts or key functions differ, repartition one side through an internal topic with the right count, or use a GlobalKTable, which replicates a small table to every instance.
How do late events work without watermarks? || Stream time is the max timestamp seen per task. A window stays open until stream time passes window end plus grace; records within that bound are added, later ones dropped. It is deterministic but can stall on idle partitions, and it never waits for slow partitions by a wall-clock timer.
What are the costs of exactly-once, and when would you avoid it? || Transactions add coordinator round trips, markers on partitions and a longer commit path, so higher latency and some throughput loss. Avoid it when processing is idempotent or approximate, or when side effects go to systems outside Kafka that it cannot cover.
How would you handle a hot key that overloads a single task? || Tasks cannot be split, so redesign: add a salt to the key and aggregate in two stages (partial per salt, then final), pre-aggregate upstream, or move that workload to a system that can shard by something other than partition.
How do you roll out a new version with a changed topology without losing state? || Keep names of stores and repartition topics stable; add new stateful operators with explicit names; for incompatible changes, run the new version with a new application.id and reprocess from the input, or use a reset tool, and cut over when it has caught up.

@@ kafka-connect
value: Kafka Connect is the part of Apache Kafka that moves data between Kafka and everything else: databases, object stores such as S3, search indexes, data warehouses and SaaS APIs. Instead of writing a consumer or producer application for each integration, you install a connector plugin and give it a JSON configuration. The framework then runs it, splits the work into parallel tasks, tracks how far it has read, retries on failure, and exposes a REST API to start, pause and inspect it.
The problem is repetition. Every team that put Kafka at the centre of its data had to write the same code again and again: poll a table, serialize rows, write to a topic, remember the position, handle a crash, handle a rebalance, batch the writes to S3, and so on. These tasks are easy to start and hard to finish. The usual mistakes (losing a position, writing duplicates, stalling on one bad record) appear only in production. Connect puts the difficult parts into one framework, and leaves connector authors to write only the system-specific part: how to read from, or write to, one particular system.
For the layer above (Debezium, data lake ingestion, search indexing, cache feeding), Connect provides a standard socket: a new pipeline becomes a configuration file instead of a software project. It stands on Kafka (kafka), whose topics, partitions, consumer groups and producer API carry the data, and whose internal topics store the connector configuration, the source offsets and the task status, so Connect needs no database of its own. It stands on change data capture (cdc), which is the idea that a database's own change log is the best source of its changes: log-based source connectors such as Debezium read that log, while simple polling connectors, which query tables repeatedly, can miss deletes and intermediate updates.
terms: Connector — the plugin and its configuration that defines one data flow, either a source (external system into Kafka) or a sink (Kafka into an external system).
Task — a unit of parallel work created by a connector; each task copies a slice of the data (for example a set of partitions or tables).
Worker — a JVM process that runs connectors and tasks; several workers with the same group.id form a Connect cluster.
Converter — the component that turns Connect's internal data into bytes for Kafka and back (Avro, Protobuf, JSON, string).
Single Message Transform (SMT) — a small, stateless change applied to each record in the pipeline, such as renaming a field or routing to a different topic.
Source offset — a connector-defined position in the external system (such as a log sequence number), stored by Connect so a restarted task resumes from the right point.
Dead letter queue (DLQ) — a Kafka topic where a sink connector can send records that fail conversion or transformation instead of stopping.
Standalone mode — a single worker with config in a file, for testing; distributed mode is the cluster for production.
history: By 2014 LinkedIn and others had learned that a streaming platform becomes the hub of a company's data, and that integrations were the bottleneck. Kafka's first answer was "write a consumer", but this left every team with its own half-correct tool. Ewen Cheslack-Postava and the Kafka team at Confluent designed Connect, and it shipped with Kafka 0.9.0 in November 2015, together with the new consumer group protocol it depends on.
The early design choices have lasted. It chose a plugin API in Java, internal Kafka topics for storing state, a REST API for management, and pluggable converters, so the data format and the connector were independent. Kafka 0.10.2 (2017) added Single Message Transforms, and Kafka 2.0 (2018) added better error handling, including a dead letter queue for sinks (KIP-298). Kafka 2.3 (2019) introduced incremental cooperative rebalancing (KIP-415), so adding a connector no longer stopped every other one. Kafka 3.3 (2022) added exactly-once delivery for source connectors (KIP-618), and later versions added REST endpoints for reading and changing connector offsets.
An ecosystem grew around the framework: Confluent's JDBC, S3, Elasticsearch and HDFS connectors, Debezium (from 2016), MirrorMaker 2 for replicating clusters (which is itself a set of Connect connectors), and hundreds of vendor and community connectors. Competing designs such as Airbyte, Fivetran and Flink CDC address the same need from outside Kafka. In Kafka 4.x, Connect remains part of the Apache Kafka distribution; recent releases have added optional settings such as an allowlist for connector client overrides (Kafka 4.2).
how: A Connect cluster is a set of identical workers with the same group.id. You submit a connector configuration to any worker through the REST API (port 8083 by default). The worker writes the configuration into a compacted internal Kafka topic (config.storage.topic). All workers read that topic, so all see the same configuration, and a leader worker computes an assignment of connectors and tasks to workers. The workers use Kafka's group coordination protocol (from the Kafka concept) to agree on the assignment, and incremental cooperative rebalancing so that only the moved tasks pause.
A connector has two roles. The connector object is a small coordinator: it looks at the external system and decides how many tasks to create (up to the tasks.max setting) and what each task's slice is. A JDBC source might give each task a few tables; an S3 sink gets topic partitions. The tasks then do the work in parallel, on any worker. If a worker leaves, its tasks are reassigned.
Source tasks run a poll loop. The task asks the external system for new data, wraps each item as a SourceRecord with a source partition and source offset (for example "binlog file X, position Y"), and returns a batch. The framework converts keys and values with the configured converters, runs the SMT chain, and sends the records through an ordinary Kafka producer. After the producer acknowledges them, the framework periodically commits the source offsets to a second compacted topic (offset.storage.topic). On restart, the task reads its last offset and continues. This gives at-least-once delivery by default: a crash between a successful send and the offset commit repeats a few records. With exactly-once source support turned on, the framework writes records and offsets in a Kafka transaction, so they become visible together, provided the connector can express its position as offsets.
Sink tasks are the mirror image. Connect runs a normal consumer group named connect-<connector name>; each task receives some partitions and gets batches through put(records). The task writes them to the target system. Kafka's own consumer offsets (in __consumer_offsets) record progress, committed only after the task's flush confirms that the data is safe. This is also at-least-once, so sinks should be idempotent: use upserts by primary key, or deterministic file names that include the topic, partition and offset range, so a replay overwrites the same object rather than creating duplicates. The S3 sink does the latter.
Data format is a separate decision from the connector. Converters decide how bytes in Kafka look: Avro or Protobuf with a schema registry (compact, with enforced evolution rules), JSON with or without embedded schema, or plain strings. A connector only produces Connect's internal structured records with a schema, so the same Debezium or JDBC connector can write Avro on one cluster and JSON on another. SMTs then handle small, per-record changes (mask a field, extract a key, add a timestamp, route to a topic by regex); anything that needs state, a join or aggregation belongs in a stream processor.
For a connector author, the API is small. A connector class implements taskConfigs(maxTasks), which returns one configuration map per task, and the framework calls it again whenever the connector reports that the external system changed (for example, a new table appeared). A task class implements start, poll or put, and stop. Because the framework owns threading, offsets, retries and shutdown, a basic connector can be a few hundred lines. The cost of this simplicity is that the connector decides the sharding. A sink is automatically sharded by Kafka partition, because it is a consumer group. A source must invent its own sharding from the external system's structure (tables, key ranges, log files), and a system with a single ordered log, such as one MySQL binlog, can only be read by one task, which is a hard throughput ceiling for that source.
Error handling uses settings such as errors.tolerance (none stops the task at the first bad record; all skips it), errors.retry.timeout and errors.deadletterqueue.topic.name for sink connectors. A task that throws an unrecoverable exception goes into the FAILED state; it does not restart on its own, so monitoring the status endpoint and restarting failed tasks (with the restart API) is part of operations. Plugins are loaded from plugin.path, each in its own class loader, so connectors with conflicting library versions can share one worker.

example: Load the topic "orders" (12 partitions) into S3 as Parquet. The configuration is a few lines of JSON: connector.class (S3 sink), topics=orders, tasks.max=6, format.class (Parquet), flush.size, and the bucket name.
Connect creates 6 tasks; each consumes 2 partitions. Say each partition receives 1,000 records per second of about 1 KB, which is roughly 1 MB/s. The task buffers records per partition and writes a file when flush.size records have been collected. With flush.size=10,000, a file is only 10 MB (before compression) and is written every 10 seconds per partition: 8,640 files per day per partition, and 12 x 8,640 = 103,680 files per day for the topic. That is a small-files problem for any query engine reading S3. With flush.size=300,000, each file holds about 300 MB (before compression) and is written every 5 minutes, which gives 288 files per day per partition and 3,456 for the topic. The cost is latency: data is visible in S3 only after up to 5 minutes. A rotation setting based on time (rotate.interval.ms) bounds that delay when traffic is low.
Files are named with the topic, partition and starting offset, for example orders+3+0000912000.parquet. Suppose a task crashes after uploading this file but before the offset commit. After the restart, it reads the old offset, builds the same batch from offset 912000 and uploads the same key again, overwriting the same object. No duplicate appears. That is how a sink with deterministic names achieves effectively-once results over at-least-once delivery.
Now a failure. A producer writes one malformed record with a field of the wrong type into orders. The sink task throws a conversion error. With errors.tolerance=none the task goes to FAILED, and lag on those partitions grows until someone restarts it; the same bad record would fail again. With errors.tolerance=all and a DLQ topic, the record goes to the DLQ with headers describing the error, and the task keeps going. Someone must watch the DLQ, or bad data silently piles up there.
intuition: Connect is a standard plug socket for Kafka: each connector is an adapter for one appliance, and the socket itself supplies the power, which here means scaling, failover and a record of where each flow stopped.
The idea is natural because integration code has a fixed skeleton and a small variable part. The skeleton (split work, track position, batch, retry, scale, monitor) is the same for every system, and it can be built on Kafka itself: configuration and offsets are just compacted topics, and task assignment is just a consumer group. What remains for each connector is a small piece of code with two methods in essence: "give me the next batch" or "take this batch".
mistakes: People often think Connect transforms and processes data. In fact SMTs are meant for light, stateless, per-record edits. Joins, aggregations, filtering across records and anything stateful belong in Kafka Streams, Flink or Spark. Using Connect for that leads to fragile configuration.
People often think a connector with tasks.max=20 will use 20 tasks. In fact tasks.max is only an upper limit. A sink cannot use more tasks than the topic's partitions, and a JDBC source creates at most one task per table; extra tasks sit idle or are never created.
People often think Connect gives exactly-once delivery. In fact the default is at-least-once for both sources and sinks. Exactly-once exists for source connectors only when enabled and supported by the connector, and for sinks it comes from idempotent writes, not from Connect itself.
People often think a JDBC source connector captures every change. In fact it polls with a query (by timestamp or incrementing id), so it misses deletes and may miss several updates between polls. For a complete change history use log-based CDC such as Debezium.
friction: Connector quality varies. Some are maintained by the system's vendor and well tested; others are community code with weak error handling, no exactly-once support, or poor performance. Licensing differs too: several popular connectors are under the Confluent Community License or a commercial license, not Apache 2.0. Each connector brings its own dependencies and configuration names, so "just a JSON file" still needs reading of long documentation.
Operations have sharp edges. Failed tasks stay failed until restarted. A bad record can stall a pipeline. Large rebalances still cause visible pauses. The REST API has no authentication by default and is often protected only by the network; connector configs may contain passwords, which need config providers or secret stores. Offsets and schemas are managed in separate places, so replaying data or moving a connector to a new cluster takes care.
Schema evolution is the most frequent source of outages: a column added to a source table must flow through the converter, the schema registry compatibility rules and the sink's table definition. Throughput is limited by connector design as well: a single JDBC source task per table cannot read one huge table in parallel. Finally, a Connect cluster is another stateful service to size, monitor and upgrade, with its own JVM memory and its own dependency conflicts.
tradeoffs: Choose Kafka Connect when a maintained connector exists for your system and the job is plain data movement: it gives scaling, offsets and monitoring for free. Choose a custom consumer or producer when the logic is business-specific, the source has no good connector, or you need full control of batching and error handling; you take on the framework problems yourself.
Choose log-based CDC (Debezium on Connect) over the JDBC source when you need deletes, every intermediate change and low load on the database; choose the JDBC source when the table is small, only the latest state matters, and you cannot enable the database's change log. Polling is simpler but loses information.
Choose a few large files (flush.size so that files are 128 MB to 1 GB) when the sink feeds a query engine; choose small, frequent files only when freshness matters more than read efficiency. Choose Avro or Protobuf with a schema registry when many teams share topics and compatibility must be enforced; choose JSON when you need to inspect data easily and the schema is stable, accepting larger messages and weaker guarantees.
Choose a dedicated Connect cluster per criticality tier (for example one for CDC, another for bulk loads) when one noisy connector must not disrupt others; choose one shared cluster for simplicity at small scale. Choose a managed service when your team does not want to operate it, and accept the connector choices and price.
practice: Run Connect in distributed mode with at least three workers, with replication factor 3 for the three internal topics, and use unique group.id and topic names per cluster. Start with a few tasks, check partition balance, and raise tasks.max only up to the number of partitions or tables. Use Avro or Protobuf with a schema registry, and set value.converter and key.converter explicitly per connector, not only at worker level.
Make sinks idempotent: choose upsert mode with a primary key, or deterministic file names. Configure errors.tolerance=all with a DLQ only where you really have a process to review it, and alert on DLQ growth. Monitor connector and task state through the REST API and JMX metrics, alert on any FAILED task, and watch consumer lag for sink connectors; for sources, watch the lag between the source system's latest position and Connect's offsets, which Connect itself does not show.
Secure the cluster: put the REST API behind authentication or a private network, use config providers for secrets, and set client overrides with an allowlist policy. Test upgrades of connector plugins in staging, because they change behaviors and defaults, and keep plugin versions pinned. Before using SMTs, ask whether a downstream stream-processing job would be clearer; a long chain of transformations is a warning sign.
quiz: What are the three internal Kafka topics of a Connect cluster, and what do they store? || The config topic stores connector configurations, the offsets topic stores source connector positions, and the status topic stores the state of connectors and tasks. All are compacted, so Connect needs no external database.
Why is a Connect sink usually at-least-once, and how do you avoid duplicates? || Offsets are committed only after the sink has flushed data, so a crash between write and commit replays records. Make the write idempotent: use upserts by primary key or deterministic output names that include topic, partition and offset range.
How do source connectors resume after a crash without losing data? || The framework stores each source record's connector-defined offset in the offsets topic after the producer has acknowledged the records. A restarted task reads its last stored offset and continues from there, possibly repeating a few records.
A sink topic has 12 partitions. You set tasks.max=20. How many tasks run and why? || At most 12, because each sink task consumes whole partitions through a consumer group and a partition goes to only one task. The extra 8 would have no work.
When would you pick a Debezium source over the JDBC source connector? || When you need every change including deletes, ordering within a key, low load on the database, and consistent snapshots. JDBC polling only sees the latest state at each poll and misses deletes.
interview: Walk through what happens when you POST a new connector configuration to a Connect cluster. || The worker validates it and writes it to the config topic. All workers read the topic; the leader asks the connector to compute task configs and assigns tasks across workers via the group protocol. Tasks start, source tasks load stored offsets and sink tasks join their consumer group, then data flows.
How does Connect handle a worker failure, and what is the visible effect? || The group coordinator detects missing heartbeats and the leader reassigns the dead worker's connectors and tasks. With cooperative rebalancing only moved tasks pause, then resume from stored offsets. Expect a lag spike of seconds, and duplicates for at-least-once paths.
How would you design a sink that writes exactly once to a database? || Use an idempotent write: upsert on the primary key, or store the Kafka offset in the same database transaction as the data and skip already-applied offsets. Connect's own commit is at-least-once, so exactly-once effects come from the target's idempotency.
A source connector's lag keeps growing. What do you check? || Whether tasks.max is the limit, the source query or log read rate, producer settings (batch size, linger, compression), broker throttling, converter and SMT cost, rebalance loops, and whether a single large table or partition caps parallelism.
Why might you not use SMTs for business logic? || They are stateless, per-record, hard to test and configured as strings; they cannot join or aggregate and make pipelines opaque. Use a stream processor or a small service for logic that needs state or tests, and keep SMTs for routing, masking and format fixes.
How do you handle a schema change in the source table end to end? || Choose compatible changes (add optional columns), register the new schema under compatibility rules, ensure the converter and sink handle the new field, test in staging, and deploy sink changes first when they must accept the new field. Break glass: use a DLQ and a new topic version for incompatible changes.

@@ pulsar
value: Apache Pulsar is a messaging and streaming system in which the servers that talk to clients (brokers) hold no data, and the data lives in a separate cluster of storage nodes called bookies, run by Apache BookKeeper. A topic is a replicated, append-only log, as in Kafka. The difference is where the log is kept. In Kafka's original design, a partition lives on the disks of the broker that leads it, so storage and serving are tied together. In Pulsar, the broker only validates, caches and routes; every message is written to BookKeeper.
The reason to split them is operational. If a Kafka broker dies, or a new one is added, the partitions it holds must be copied, which takes minutes to hours for terabytes. In Pulsar, a broker can be added or removed and the topics move to another broker in seconds, because there is nothing to copy. A bookie can be added, and new writes immediately use it. Pulsar also was built for a cloud with many teams: tenants and namespaces with quotas and permissions, geo-replication between data centres as a built-in feature, and subscription types that let one topic work as a stream or as a work queue.
For the layer above (event-driven services, IoT and telecom ingestion, task distribution, multi-tenant platforms), Pulsar gives a log with queue semantics, and storage that scales independently of the serving tier. It stands on the distributed commit log (commitlog), which supplies the central idea: an ordered, append-only, replicated sequence of entries, where order and durability come from agreeing on a single writer and a quorum of copies. It stands on publish-subscribe (pubsub), which supplies the consumer side: a topic with many independent subscriptions, each with its own position, so that adding a reader does not disturb the others.
terms: Broker — a stateless server that serves producers and consumers for the topics it currently owns and caches recent messages.
Bookie — a BookKeeper storage node that stores ledger entries on local disks.
Ledger — an append-only sequence of entries in BookKeeper, written by one writer and closed when full; a topic is a chain of ledgers.
Managed ledger — Pulsar's layer that presents a chain of ledgers as one continuous log for a topic partition.
Ensemble, write quorum, ack quorum — the set of bookies a ledger uses (E), the number each entry is sent to (Qw), and the number that must confirm before the write counts as done (Qa).
Cursor — the stored position of one subscription in a topic (what has been acknowledged).
Subscription — a named consumer group on a topic; its type (exclusive, failover, shared or key-shared) decides how messages go to consumers.
Namespace — a group of topics within a tenant that shares policies such as retention, quotas and replication.
history: Pulsar began at Yahoo around 2013. Yahoo needed one messaging service for many internal products, across data centres, with strong durability and isolation between teams; the tools available then (Kafka at that time, and others) did not handle multiple tenants and geo-replication well. Matteo Merli and Sijie Guo led the work. It was built on BookKeeper, a log storage system that was itself created at Yahoo Research (by Flavio Junqueira and colleagues) as a durable write-ahead log, first for HDFS NameNode high availability. The BookKeeper design is described in "Durability with BookKeeper" (Junqueira, Kelly and Reed, 2013).
Yahoo open-sourced Pulsar in 2016, it entered the Apache Incubator in June 2017, and it became a top-level Apache project in September 2018. Companies such as StreamNative (founded by Pulsar's creators in 2019) and Splunk (through Streamlio) built products on it. Releases added the features that make it a platform: schema registry and functions (lightweight stream processing) in 2.x, tiered storage to object stores, transactions (2.8, 2021), key-shared subscriptions, and protocol handlers such as KoP that let Kafka clients talk to Pulsar.
Pulsar 4.0, the long-term-support release, arrived in October 2024, and the 4.x line continues in 2026. One recent direction is reducing the dependency on ZooKeeper: Pulsar can keep metadata in other stores, including etcd and Oxia, a new horizontally scalable metadata store. Meanwhile Kafka removed ZooKeeper in 4.0 (2025), added tiered storage, and made queue-style "share groups" production-ready in 4.2 (2026). This narrowed what once made Pulsar unique, and the choice now rests on multi-tenancy, geo-replication and the separate storage tier.
how: Consider one partition of a persistent topic. Exactly one broker owns it at a time, and this broker is the single writer. When a producer sends a message, the broker adds it to the topic's current ledger by sending the entry to Qw bookies in the ledger's ensemble (a typical setting is E=3, Qw=3, Qa=2) in parallel. Each bookie first appends the entry to its journal, a sequential write-ahead log on its own disk, and forces it to disk (group commit, so many entries share one fsync). It then acknowledges. When Qa acknowledgements have arrived, the broker acknowledges the producer. The third bookie finishes in the background. This is the quorum commit from the distributed log concept: durability comes from several copies, and latency comes from the second-fastest one, not the slowest.
Bookies keep the journal on one disk (or set of disks) and the long-term ledger storage on another. Writes land in the journal and in a memory table, are later flushed and sorted into entry log files with an index (kept in RocksDB), and the journal can then be trimmed. Because the write path and the read path use different disks, a burst of cold reads, such as a consumer replaying old data, does not slow down the incoming writes, a separation that helps with predictable latency.
A ledger has a size and time limit. When it is full, or when the broker moves, the ledger is closed, and the managed ledger opens a new one; the list of ledgers (their IDs and sizes) is metadata kept in the metadata store (ZooKeeper by default). A topic is therefore a list of closed ledgers plus the one open ledger. This structure is what makes recovery cheap. If a bookie fails, the broker closes the current ledger and opens a new one on a different ensemble, so new writes never wait for a copy of old data. A background auditor notices the under-replicated old ledgers and re-replicates them. If a broker fails, another broker takes over the topic, "fences" the old ledger (so that a delayed old broker can no longer write), reads its last confirmed entry, closes it, and opens a new ledger. Ownership is assigned by a load manager, which can shift topics between brokers to balance load, in seconds, with no data movement.
It helps to compare this with the replication style of the distributed commit log concept. In Kafka, one leader appends to its local log and followers pull from it; the leader decides what is committed, using the in-sync replica set. In BookKeeper, the writer (the broker) itself is the replication engine: it sends each entry to the bookies and counts the acknowledgements, and the bookies never talk to each other during a write. Because a ledger has exactly one writer and is closed before anyone else writes, there is no need for leader election inside the storage layer; the only agreement needed is who owns the topic, and that is decided through the metadata store. The broker also batches small messages into one entry (to cut per-entry overhead at the bookies) and can compress batches before storing them.
Reads come first from the broker's memory cache. A consumer that is keeping up reads recent entries from the cache and never touches a bookie. A consumer that is far behind makes the broker read from bookies, and from tiered storage if old ledgers have been offloaded to S3 or similar. Each subscription has a cursor, which records the acknowledged position, and the cursor is itself stored durably in BookKeeper. Acknowledgement can be individual (message by message, which allows out-of-order processing) or cumulative (everything up to a point).
Subscription type decides delivery. Exclusive allows one consumer. Failover has one active consumer and standbys. Shared spreads messages round-robin over any number of consumers, with no limit tied to the partition count, which makes Pulsar work as a task queue; ordering is lost. Key_Shared sends all messages with the same key to the same consumer, keeping per-key order while scaling consumers beyond partitions. Negative acknowledgements, acknowledgement timeouts, delayed delivery and dead-letter topics add queue-style features. Namespaces and tenants provide isolation: quotas, authentication, and per-namespace replication clusters; with geo-replication enabled, the brokers copy messages to other clusters asynchronously.

example: A topic partition with E=3, Qw=3, Qa=2. A producer sends a 1 KB message. Broker A sends it to bookies 1, 2 and 3. Bookie 1 and bookie 3 write it to their journals and reply after 1 ms. The broker has Qa=2 confirmations and acknowledges the producer after about 1 to 2 ms (plus network). Bookie 2 is slow (a disk stall of 50 ms), but the producer never waits for it. This is why the ack quorum is lower than the write quorum: the tail latency of one slow node is hidden.
Failure: bookie 3 crashes. Broker A's next write to ledger 25 fails to reach it. The broker closes ledger 25 at the last confirmed entry (say entry 90,000) and opens ledger 26 on bookies 1, 2 and 4. The producer sees at most a short pause of tens to hundreds of milliseconds. The old entries of ledger 25 are now under-replicated (two copies), and a background process copies the missing fragments to a new bookie. No operator action is needed, and no partition is "offline".
Storage arithmetic: ingest is 100 MB/s. With Qw=3, the bookies in total receive 300 MB/s. Per day this is 100 MB/s x 86,400 s = 8.64 TB of unique data, or 25.9 TB stored with three copies. Keeping seven days on bookies costs 60.5 TB unique, 181 TB with copies. With tiered storage, keep one day on bookies (25.9 TB with copies) and offload the other six days (52 TB unique) to S3, which stores its own durable copies. Offloaded data is read more slowly, so replays of old data take longer than from bookies, but the bookie cluster is about seven times smaller.
Scale-out: you add two bookies to a cluster of four. New ledgers choose their ensembles from all six bookies, so the load spreads within the next ledger rollover (minutes), and old data does not need to move. Adding a broker is faster still: the load manager moves a few topics to it by changing ownership, with no data transfer.
intuition: Kafka is a shop where the cashier also keeps the stock in the till; Pulsar separates the cashiers from the warehouse, so you can hire more cashiers without moving stock and add shelves without training anyone.
The design is natural if you treat the log as a storage problem and serving as a compute problem. Storage needs durability and many cheap disks, and compute needs CPU, network and cache. Joining them forces both to scale together. A ledger that is written once and then closed makes this split clean: closed ledgers never change, so they can live anywhere and be copied lazily, and only the one open ledger needs a single-writer protocol.
mistakes: People often think Pulsar is just Kafka with extra components. In fact it moves the data model: a topic partition is a chain of ledgers spread across many bookies, not a file set on one leader. This is what gives instant topic movement and storage that grows without partition limits, but also what adds components and one more network hop.
People often think stateless brokers mean no data on brokers. In fact brokers keep a memory cache of recent entries and a lot of per-topic state in memory. They are stateless in the sense that nothing durable depends on them, so losing one loses nothing, but a restart still has a warm-up and takeover cost.
People often think Pulsar is faster than Kafka. In fact Pulsar adds a hop (broker to bookie), so the write path has more steps than a Kafka leader's local write. Benchmarks differ by hardware, settings and who ran them, and vendors on both sides publish results that favour their own product. Test with your own workload.
People often think a shared subscription gives ordering and exactly-once. In fact shared delivery spreads messages with no ordering and is at-least-once, so consumers must handle duplicates and reordering. Use Key_Shared to keep per-key order, and transactions (or idempotent consumers) for stronger guarantees.
friction: The first cost is moving parts. A production Pulsar cluster has brokers, bookies (with separate journal and ledger disks), a metadata store, and often proxies, a function worker and a schema registry. Each one has its own tuning, upgrades and failure modes. BookKeeper in particular needs care: disk layout, garbage collection of entry logs, and recovery settings. Teams without that skill find it harder to run than Kafka.
Second, the ecosystem is smaller. Most streaming tools (connectors, Flink and Spark integrations, schema tooling, hiring pool, managed offerings) assume Kafka's API first. KoP and similar adapters help, but they cover a subset. Third, the performance profile is different: the extra network hop and the fsync-based journal add latency compared with a local Kafka write, and cold reads can compete with tailing reads for broker memory and bookie bandwidth if not isolated.
Fourth, the original advantage has narrowed: Kafka now has KRaft, tiered storage, faster rebalancing and share groups for queue use. Metadata scalability, many-topic workloads (millions of topics) and backlog handling are still areas where Pulsar can be better, but a team must weigh these against operational familiarity. The pace of the community and the company behind it matter for long-term risk.
tradeoffs: Choose Pulsar when you need multi-tenancy with isolation and quotas, native geo-replication across regions, both queue and stream consumption on the same topics, very many topics, or fast elasticity for the serving tier. Choose Kafka when you want the largest ecosystem, the simplest mental model of "partition equals log on a broker", and a stack of stream processing and connector tools that expect Kafka. You give up either ecosystem breadth (Pulsar) or built-in tenant features (Kafka).
Choose Qw=3, Qa=2 for a balance of durability and latency (one slow bookie is hidden); choose Qa=3 when you cannot tolerate even a short window with fewer than three confirmed copies, accepting that the slowest bookie sets your latency. Choose E larger than Qw (for example E=5, Qw=3) when you want write load striped over more bookies per ledger, and accept more complex recovery.
Choose tiered storage when retention is long (days to years) and old data is read rarely; choose keeping everything on bookies when replays are frequent and need low latency. Choose shared or Key_Shared subscriptions for work queues with many workers; choose exclusive or failover subscriptions for strict order on a partition.
Choose a managed Pulsar service when your team cannot staff BookKeeper operations; choose self-hosting on Kubernetes (with the Helm chart) when you need control and have the skills. Consider RabbitMQ or Kafka's share groups instead if all you need is a simple task queue.
practice: Size the layers separately. Brokers need CPU, network and memory for cache; bookies need fast disks with a separate device for the journal (NVMe is common), and enough network for three times the ingest. Start with E=3, Qw=3, Qa=2, three or more bookies per rack-aware zone, and set the rack policy so that copies sit in different failure domains. Use at least three metadata store nodes.
Design topics and namespaces deliberately: one namespace per team or application, with retention, backlog quota, TTL and rate limits set at namespace level. Prefer partitioned topics for throughput (start with a number of partitions that is a multiple of the expected broker count), and pick the subscription type from the semantics you need. Always configure dead-letter topics and retry policies for shared subscriptions, with a plan to inspect them.
Monitor the metrics that matter: publish latency percentiles, backlog size per subscription, storage used per bookie, under-replicated ledgers, bookie journal sync latency, cache hit rate, and ledger rollover rates. Use schema enforcement on topics shared by teams. Enable tiered storage early if retention is long. Test failure by killing a bookie and a broker, and measure the pause. Finally, test client libraries in your languages: Java is the most complete, while others (Go, Python, C++, Node.js) may lag in features.

How does a Pulsar write become durable and fast at the same time? || The broker sends the entry to Qw bookies in parallel; each appends to a journal with fsync (group commit). interview: Explain Pulsar's architecture and how it differs from Kafka's storage model. || Brokers are stateless serving and caching nodes. Each topic partition is a chain of BookKeeper ledgers striped over bookies, with quorum writes. Kafka stores a partition as segment files on its leader and followers. Pulsar moves topics by changing ownership, while Kafka moves data (or relies on tiered storage), so elasticity differs.
What are the write quorum and ack quorum, and how do you choose them? || Qw is how many bookies receive each entry; Qa how many must confirm. Qa below Qw hides slow nodes and keeps latency low while keeping multiple copies. Choose Qw=3, Qa=2 normally, Qa=3 for stricter durability at higher tail latency, and ensure E, Qw match the number of failure domains.
How does Pulsar recover after a broker crash without losing messages? || Another broker takes the topic, fences the last ledger (so the old broker's writes are rejected), reads the last confirmed entry from bookies by quorum, closes the ledger and opens a new one. Entries acknowledged to producers are on at least Qa bookies, so they survive.
Compare shared and key_shared subscriptions. || Shared sends messages round-robin to any consumer, no ordering, maximum parallelism. Key_Shared routes messages with the same key to the same consumer, keeping order per key while allowing more consumers than partitions, at the cost of rebalancing when consumers join or leave.
What operational risks would you manage in a large Pulsar deployment? || Metadata store load and availability, bookie disk and journal health, under-replicated ledgers after failures, cache pressure from backlogs, noisy tenants without quotas, topic count growth, and upgrade sequencing between brokers and bookies.
How would you handle a consumer that falls far behind, with a large backlog? || Check backlog quotas and TTL, add consumers (shared or key-shared), ensure cold reads do not saturate bookies (tune read-ahead, use tiered storage for older data), and apply a backlog eviction policy or dead-letter policy if the data can be dropped. Alert before the quota hits.

@@ redpanda
value: Redpanda is a streaming data platform that speaks the Apache Kafka protocol but is a completely different program. It is written in C++, ships as one binary, runs no JVM and no ZooKeeper, and replicates every partition with the Raft consensus algorithm. Kafka producers, consumers, Kafka Connect and Kafka Streams connect to it without code changes, because to them it looks like a Kafka cluster.
The reason it exists is a bet about hardware. Kafka was designed in 2010 for spinning disks and few cores: it leaned on the operating system's page cache, on the JVM's garbage collector, and on threads that share data and take locks. Today servers have 32 to 128 cores, NVMe drives that handle hundreds of thousands of operations per second, and 25 to 100 Gbit/s networks. On such machines, the costs that matter are lock contention, cache misses between cores, garbage collection pauses and the system-call overhead of the kernel. Redpanda's founder, Alex Gallego, built a log server that avoids those costs by design, aiming at lower and steadier tail latency and at fewer machines for the same load.
For the layer above (event-driven applications, CDC pipelines, real-time analytics, ML feature streams), it offers the same log abstraction and the same wire protocol, with a simpler deployment. It stands on the distributed commit log (commitlog), which is the core idea it re-implements: an ordered, append-only, partitioned and replicated log, where each message has an offset and consumers track their own position. What Redpanda changes is how that log is stored (segment files managed by its own engine, with direct disk I/O), how it is replicated (Raft instead of Kafka's in-sync replica scheme), and how the CPU is used (one thread pinned to each core, sharing nothing).
terms: Seastar — an open-source C++ framework for high-performance servers that uses one thread per core, with no shared memory between cores and asynchronous I/O everywhere.
Shard — one core and everything it owns (memory, partitions, network queues); in Seastar, work is divided into shards.
Raft — a consensus algorithm in which a leader replicates log entries to followers and commits an entry once a majority has stored it.
Partition — an ordered, append-only slice of a topic; in Redpanda each partition is one Raft group.
Direct I/O — reading and writing files while bypassing the operating system's page cache, so the application controls caching and flushing.
fsync — a request that forces written data from memory to the physical disk; an acknowledged write is durable only after it.
Tiered storage — moving old log segments to object storage such as S3 while keeping them readable by consumers.
Controller — the cluster-wide service (itself a Raft group) that stores topic, partition and leadership metadata.
history: Alex Gallego, who had earlier worked on stream processing and low-latency systems at Akamai, founded Vectorized in 2019 to build a Kafka-compatible engine on a new foundation. The product was first called Redpanda, and the company later took that name (Redpanda Data). The base was Seastar, a framework from the ScyllaDB team, who had used the same thread-per-core idea to rebuild Cassandra in C++ as ScyllaDB.
Redpanda's early story was performance: lower tail latency than Kafka, with fewer nodes. It also removed ZooKeeper at a time when Kafka still needed it, which made installation easy and became a selling point. Over the next years it added tiered storage, a built-in schema registry and HTTP proxy, Wasm-based data transforms that run inside the broker, and Redpanda Console. In 2024 the company acquired the Benthos stream-processing tool, which became Redpanda Connect. Recent product lines include Iceberg topics, which write topic data as Apache Iceberg tables for analytics.
The licence is a notable part of the history. The core is source-available under the Business Source License (BSL): you can read and run it freely, but cannot offer Redpanda itself as a competing service, and each version converts to Apache 2.0 four years after release. A paid enterprise licence unlocks features, including tiered storage, RBAC and several balancing features, according to the vendor's documentation. Meanwhile, Kafka removed ZooKeeper with Kafka 4.0 (March 2025), so part of the original simplicity advantage has closed. Performance comparisons between the two have been argued in public, with the vendors and independent engineers (for instance Jack Vanlightly) publishing different results for different workloads.
how: Start with the threading model, because everything follows from it. On a machine with N cores, Redpanda starts N threads and pins each to one core. Each thread (a shard) gets its own slice of memory, allocated at start-up and local to its NUMA node, its own network queues, its own I/O queue to the disk, and its own set of partitions. A shard never takes a lock on another shard's data. If core 3 needs something from core 5, it sends a message through a lock-free queue and gets a reply, as if the two cores were separate machines. Each thread runs an event loop that polls for network events and disk completions and never blocks. There are no garbage collection pauses because there is no GC, and the number of context switches is very low, which keeps latency steady.
Each Kafka partition maps to a Raft group, and each Raft group lives on one shard per replica. With replication factor 3, three brokers each have a copy, and each is on some core. One replica is the leader. A producer's request is handled like this: the connection is accepted by some core; the request is parsed; the partition's batch is sent across to the core that owns the partition if it is not the same; the leader's core appends the batch to its log in memory and sends it to the followers by RPC; each follower appends, writes to disk and replies; when a majority (2 of 3, counting the leader itself) has the batch, the leader marks it committed and replies to the producer. With acks=all and the default settings, Redpanda calls fsync before acknowledging. Kafka, in contrast, does not fsync every write by default and depends on replication across brokers for durability. Redpanda's choice makes each acknowledged write safe against a power failure at the cost of disk speed, which is why NVMe drives matter. Newer versions can also relax this with write caching, trading some durability for speed.
The Raft log is the data log. In Kafka, a partition's data is replicated by in-sync-replica logic, while the new KRaft metadata quorum uses Raft only for cluster metadata. In Redpanda the same Raft log stores the Kafka records, so there is no second write-ahead log. Raft gives well-defined behaviour for leader election and for what counts as committed: a new leader is elected by majority vote, and it must contain all committed entries. This removes whole classes of edge cases around partially replicated data. Raft's cost is one more concept for the operators: a minority of replicas may fail without losing availability, and a majority failure makes the partition unavailable until recovered.
Storage is a set of segment files per partition, written through Seastar's direct I/O path, which bypasses the kernel page cache. Redpanda keeps its own read cache and read-ahead in memory it controls, and issues disk I/O in aligned blocks with its own I/O scheduler, so it can prioritize latency-sensitive writes over background work like compaction. The effect is more predictable performance than depending on the kernel's cache, but the application must be sized with enough memory per core (a couple of GB per core at least).
The read path is simpler. A consumer's fetch request goes to the leader of the partition (or, with follower fetching, to a nearby replica). The shard that owns the partition looks for the requested offsets in its read cache; on a miss it reads the segment file with direct I/O and read-ahead, and it only returns data up to the committed offset, so a consumer never sees a record that could still be lost in a leader change. If no new data exists, the request waits (a long poll) until data arrives or a timeout ends. Idempotent producers and transactions work through producer state kept by the partition leader and replicated in the same Raft log, so duplicates from retries are detected by sequence numbers.
The control plane is also Raft. The controller is a replicated state machine (a Raft group) that stores the cluster's topics, partitions, configuration and leadership; it replaces ZooKeeper. A partition balancer moves leaders and replicas as nodes join or fail. Tiered storage uploads closed segments to object storage; a consumer reading old offsets triggers a fetch from the object store, so retention can be unlimited while local disks hold only recent data. Because the Kafka API is implemented in full for common operations (produce, fetch, consumer groups, transactions, admin), the ecosystem sits on top unchanged. The compatibility with the commitlog concept goes down to offsets, partitions and consumer groups.

example: A topic with 3 partitions, replication factor 3, on three brokers with 8 cores each. Each partition is a Raft group with 3 members, so 9 replicas exist in all, 3 per broker. The leaders are spread: broker 1 leads partition 0, broker 2 leads partition 1, broker 3 leads partition 2.
A producer sends a 16 KB batch (about 16 records of 1 KB) to partition 0. The broker 1 core that accepted the connection forwards the request to the core that owns partition 0, say core 4. Core 4 appends the batch to its buffer, assigns offsets 5,000 to 5,015, and sends the batch to brokers 2 and 3. Both write to their local NVMe drives and call fsync, which takes roughly 50 to 200 microseconds on a good NVMe drive. Follower 2 answers first. The leader has itself plus one follower, which is a majority of 3, and it also flushes its own copy. It marks offset 5,015 committed and replies to the producer. The total is often a few milliseconds across the network, depending on the batching settings.
Why batching matters here: if every batch needed its own fsync at 100 microseconds, one core could do at most about 10,000 flushes per second. With 16 KB batches, that is 160 MB/s per core as an upper bound. Redpanda combines concurrent batches from many partitions on one core into one flush, and producers use linger.ms to build larger batches, so real throughput is higher. This is also why small, unbatched writes with acks=all are expensive on any durable log.
Failure: broker 1 loses power. Brokers 2 and 3 notice the missing heartbeats (a Raft election timeout is typically a second or so). Partition 0's replica on broker 2 starts an election, gets a vote from broker 3, and becomes leader, because both have all committed data. Clients get a not-leader error, refresh metadata, and continue against broker 2. Partitions 1 and 2 are unaffected, except that they run with two replicas until broker 1 returns. When it does, it catches up from the new leaders by Raft log repair.
Capacity thinking: if one core can sustain about 50 MB/s of produce with replication and you need 800 MB/s into the cluster at RF=3, the cluster must absorb 2.4 GB/s of writes across all replicas. At 50 MB/s per core that is 48 cores, so six 8-core brokers is a reasonable first estimate. Then you test it, because the real number depends on batch size, compression, disks and network.
intuition: Redpanda is a kitchen where each cook has a private station with their own tools and ingredients, and passes dishes through a window, instead of everyone fighting over one shared counter.
The idea is natural if you accept that the bottleneck on a modern server is coordination, not computing. Locks, shared caches and a managed heap force cores to wait for each other. If each core owns its data and talks by messages, the cores almost never wait. A Raft group per partition then makes each partition an independent state machine, which fits the one-core-per-partition model: the partition's thread decides, replicates and commits without a global lock.
mistakes: People often think Redpanda is a fork of Kafka. In fact it is a separate code base written from scratch in C++; it implements the Kafka network protocol, so clients work, but the storage engine, replication and threading are different. This also means its bugs and behaviours differ from Kafka's.
People often think Redpanda is always many times faster than Kafka. In fact results depend strongly on the workload: number of partitions, message size, batching, retention, acks setting and disk. Vendor benchmarks show big advantages; independent tests have shown the gap shrinking or reversing in some cases. A well-tuned Kafka cluster on modern hardware is fast, so measure your own workload.
People often think being Kafka-compatible means every feature behaves identically. In fact the protocol, the common client features and the main admin operations are supported, but details such as configuration names, metrics, tooling, and some features of newer Kafka versions can differ. Check the compatibility list before relying on a specific feature.
People often think "open source" in the usual sense. In fact the core is under the Business Source License, and several features, including tiered storage, require an enterprise licence key according to the vendor's licensing page. Check what you need before committing.
friction: The licence is the first friction. BSL code is readable but is not an OSI-approved open-source licence, and many companies treat the enterprise-gated features as a lock-in risk. Features you might expect to be free, such as tiered storage, need a paid licence in the vendor's current model, so costs should be modelled early.
The architecture has its own demands. Memory is preallocated per core, so the machine needs enough RAM per core (the vendor documents a minimum of a couple of GB per core), and each shard busy-polls, so CPU use looks high even when idle. Small machines with a few cores get fewer of the benefits. Raft per partition means many partitions create many small consensus groups with heartbeats, and very high partition counts need tuning within the vendor's partitions-per-core guidance. Fsync-on-ack gives strong durability, but needs good disks and makes tiny writes costly.
The ecosystem is smaller: fewer engineers know how to operate it, there are fewer community tools, and the vendor controls the roadmap. Because the Kafka API keeps evolving (new consumer group protocol, share groups, new transaction details), compatibility is a moving target that Redpanda must keep following. Finally, Kafka's own progress has removed ZooKeeper and added tiered storage, so the case for switching rests more on tail latency and operational cost than on features.
tradeoffs: Choose Redpanda when you run Kafka workloads on dedicated hardware, want strong tail-latency at modest scale, want a small operational footprint (one binary, no ZooKeeper, no JVM tuning), and your use works with the vendor's licence. Choose Apache Kafka when you need the Apache 2.0 licence, the widest ecosystem and operator skill base, the newest protocol features, or a managed service from many providers. You give up community breadth for Redpanda's simplicity, or give up simplicity for breadth.
Choose fsync-per-ack (the default) when losing acknowledged data on a power failure is unacceptable, as in financial records; choose write caching or relaxed flush settings when throughput and latency matter more and replication across zones gives enough safety. Replication across three failure zones is a strong guard in either case.
Choose fewer large nodes (for example 16 to 32 cores) when you want to use the thread-per-core efficiency and have large partitions; choose more small nodes when fault isolation matters and a single node failure must move little load. Choose tiered storage when retention is long and cost matters, accepting the licence and the slower reads of old data.
Choose a managed service (Redpanda Cloud, or MSK or Confluent Cloud for Kafka) when you do not want to run brokers; choose self-managed when data location, cost at scale or custom networking require it. Choose Kinesis or Pulsar if your constraints are AWS-native simplicity or multi-tenant geo-replication instead.
practice: Run Redpanda on instances with local NVMe drives, using XFS or ext4 as the vendor recommends, and use rpk (the command-line tool) to tune the machine: it sets CPU governor, interrupt placement, disk and network parameters. Give each core enough memory and do not run other heavy processes on the same node. Use at least three nodes spread over three failure zones, with rack awareness enabled so replicas land in different zones.
Size partitions deliberately: more partitions give more parallelism, but each is a Raft group with its own overhead, so follow the vendor's partitions-per-core guidance. Set producer batching (linger.ms of a few ms, batch.size of 64 KB or more, compression with lz4 or zstd) so that fsync cost is shared. Keep acks=all and idempotent producers on for important data.
Monitor through the Prometheus endpoint: produce and fetch latency percentiles, partition leadership balance, under-replicated partitions, Raft heartbeat failures, disk usage, and reactor stalls (a long stall means something blocked a core). Test failure modes: kill a node, pull a disk, partition the network. Before adopting, run a trial with your actual clients and your Kafka Connect and Streams applications, check the listed compatibility notes, and decide upfront which enterprise features you will need and what they cost.
quiz: What does thread-per-core mean in Redpanda, and what does it avoid? || One thread is pinned to each CPU core and owns its own memory, network queues, disk I/O and partitions. Cores communicate by messages, so there are almost no locks, cache-line fights between cores or garbage-collection pauses.
How does Redpanda decide a write is committed? || Each partition is a Raft group. The leader appends the batch and replicates it to followers; once a majority has stored it (with fsync by default), the leader marks it committed and acknowledges the producer.
Why can an acknowledged write be lost in Kafka's default setup on a simultaneous power failure but not in Redpanda's default? || Kafka acknowledges after the data is in replicas' memory and page cache, without fsync per write, relying on replication. Redpanda flushes to disk before acknowledging, so data survives even if all replicas lose power at once.
You need 600 MB/s of produce at RF=3 and one core sustains about 50 MB/s of replicated writes. Roughly how many cores does the cluster need? || Total write work is 600 x 3 = 1,800 MB/s across all replicas; at 50 MB/s per core that is 36 cores. Six 8-core brokers (48 cores) give some headroom, to be confirmed by testing.
When would you choose Apache Kafka over Redpanda? || When you need an Apache 2.0 licence, maximum ecosystem and managed-service choices, the newest Kafka protocol features, or you already have deep Kafka expertise. Choose Redpanda when a smaller footprint and tail latency matter and the licence fits.
interview: Explain how a Redpanda produce request is processed from socket to acknowledgment. || A core accepts the connection and parses the request; the batch is routed by message to the core that owns the partition; the leader appends to its log and replicates through Raft to followers; followers append, flush and reply; after a majority holds it, the leader commits, advances the offset and answers the producer.
Why use Raft per partition rather than Kafka's ISR? || Raft has a precise definition of commit and election: only a replica with all committed entries can win, and a majority decides. ISR relies on a controller, high watermarks and configuration such as min.insync.replicas, with historical edge cases. Raft costs per-group overhead and needs a majority alive.
What are the downsides of bypassing the page cache? || The application must implement its own caching, read-ahead and memory management, and be sized correctly; mixed workloads with large cold reads can thrash its cache; and it cannot benefit from free memory as the kernel would. The gain is predictable latency and control over I/O priority.
How would you validate a claim that Redpanda has 10x lower latency than Kafka? || Reproduce with your own message sizes, partition counts, acks, batching and retention on the same hardware, run for hours (not minutes), include consumer load and background tasks such as compaction, and compare the tail latencies (p99 and p99.9) and the cost per MB/s. Read independent analyses.
What risks come with the Business Source License and enterprise gating? || You cannot resell it as a service, features such as tiered storage need a paid key, licence terms can change in future versions, and exit options are limited to the Kafka API, which fortunately makes migration to Kafka feasible.
How do you handle a hot partition on one core? || A partition lives on one core, so its throughput is capped by that core. Fix by choosing keys with better spread, increasing the partition count, balancing leaders, or splitting a hot key with a salt. Check that other partitions on that core are not competing for it.

@@ rabbitmq
value: RabbitMQ is a message broker: a server that sits between programs that produce work and programs that do it. A producer publishes a message to the broker, the broker routes it to one or more queues according to rules you define, and consumers take messages from those queues, process them, and acknowledge them. Once a message is acknowledged, the broker deletes it. If a consumer dies before acknowledging, the broker gives the message to another consumer.
The problem it solves is decoupling in time and in speed. A web request that must send an email, resize an image or call a slow partner API should not wait for the result, and should not fail because the worker is busy or restarting. With a broker, the web server drops a message and moves on; workers pick up messages at their own speed; spikes build a queue instead of causing errors; and failed work is retried. RabbitMQ adds a rich routing layer in front of the queues, so one published message can reach different queues by topic pattern, by header, or by broadcast, without the producer knowing who listens.
For the layer above (background job systems, microservice commands and events, IoT and telemetry gateways), RabbitMQ provides reliable delivery with per-message acknowledgement, flexible fan-out, and low latency, often a millisecond or less per message at moderate load. It stands on the message queue concept (mqueue), which supplies the core contract: messages are held in order in a queue, consumers compete for them, and a message stays "in flight" until it is acknowledged, so that a crash returns it for redelivery. That contract gives at-least-once delivery. RabbitMQ builds on it with exchanges, bindings, acknowledgements, prefetch limits, dead-letter handling and replicated queues.
terms: Exchange — the entry point for published messages; it does not store them but applies routing rules to decide which queues receive a copy.
Binding — a rule linking an exchange to a queue, with an optional pattern (a binding key) that routing keys must match.
Queue — an ordered buffer that holds messages until a consumer takes and acknowledges them.
Routing key — a string set by the producer (for example "order.eu.created") that the exchange uses to choose queues.
Acknowledgement (ack) — the consumer's signal that processing is done, after which the broker deletes the message; a nack or a lost connection causes redelivery.
Prefetch (QoS) — the maximum number of unacknowledged messages the broker will send to a consumer at once.
Publisher confirm — the broker's acknowledgement to the producer that it has taken responsibility for a message (for durable queues, after it is safely stored).
Dead letter exchange (DLX) — an exchange that receives messages that were rejected, expired or exceeded a delivery limit.
Quorum queue — a replicated queue type that uses the Raft consensus algorithm to keep copies on several nodes.
history: RabbitMQ began in 2006 to 2007 at Rabbit Technologies, a joint venture of LShift and CohesiveFT, led by Alexis Richardson and Matthias Radestock. The motivation was AMQP (Advanced Message Queuing Protocol), a standard for message brokers created in the financial industry (at JPMorgan Chase and others) because every bank had been paying for proprietary, incompatible middleware. They chose Erlang, the language Ericsson built for telephone switches, because its lightweight processes, message passing and fault isolation matched the problem: each connection, channel and queue could be a separate, isolated process.
The company was acquired in April 2010 by SpringSource, then a division of VMware. The project later moved to Pivotal and then back to VMware, and today it belongs to Broadcom. The protocol history is messy: AMQP 0-9-1 (2008) became the dominant dialect and is what most RabbitMQ clients speak, while the later, quite different AMQP 1.0 (OASIS standard, 2012) was added as a plugin first and became a native, core protocol in RabbitMQ 4.0. RabbitMQ also supports MQTT for IoT, STOMP, and its own stream protocol.
Reliability work defined the later years. Classic mirrored queues, which copied queues between nodes with a custom protocol, had known weaknesses during network partitions and during synchronization. Quorum queues arrived in RabbitMQ 3.8 (2019), using Raft. Streams, an append-only log type that supports replay, arrived in 3.9 (2021). Mirroring was deprecated and was removed in RabbitMQ 4.0 (September 2024). By October 2026, the 4.x line had reached 4.4 (released 20 October 2026), according to the project's release page.
how: A message takes a path through four objects. A connection is a TCP connection from a client; inside it, lightweight channels are used so that one application can run many logical sessions over one socket. The producer publishes to an exchange with a routing key. The exchange compares the key with its bindings and puts a copy of the message into every matching queue. A consumer subscribes to a queue; the broker pushes messages to it, up to the prefetch limit. When the consumer finishes, it sends an ack, and the queue removes the message.
Exchange types define the routing. A direct exchange sends a message to queues whose binding key equals the routing key exactly. A fanout exchange sends to all bound queues and ignores the key (broadcast). A topic exchange matches dotted keys against patterns: "*" matches exactly one word and "#" matches zero or more words, so the key "order.eu.created" matches "order.*.created" and "order.#". A headers exchange routes on message header values. The default exchange is a built-in direct exchange that routes to the queue whose name equals the routing key, which is what makes simple "send to a queue" code work. Routing is decided at publish time, so a message that matches no queue is dropped unless the producer asks for it to be returned (mandatory flag) or an alternate exchange catches it.
Delivery safety is built from small steps. The producer can enable publisher confirms; the broker confirms a persistent message to a durable queue only after it is written to disk (and, for quorum queues, replicated to a majority). The consumer uses manual acknowledgement, so the message is removed only after the work is done. If the channel or connection closes with unacknowledged messages, the broker puts them back in the queue and delivers them again, marked as redelivered. Together these give at-least-once delivery: no message is lost, but a message can be processed twice (for example when a worker finishes the work and crashes before sending the ack), so consumers must be idempotent. Prefetch is a flow-control tool: with prefetch 1, a slow consumer holds only one message and others go to faster workers; with a large prefetch, throughput is higher but one slow consumer can hoard messages.
Queue types differ in how they store and replicate. A classic queue lives on one node as a single Erlang process, which is fast (tens of thousands of messages per second for small messages is common) but is not replicated in 4.x, so losing the node loses availability, and with it the queue's contents if the disk is lost. A quorum queue has a leader and followers across typically three nodes, uses a Raft log to replicate every operation, and survives the loss of a minority of nodes without losing acknowledged messages. It is slower than a classic queue because it must replicate and fsync before confirming. It also tracks the delivery count of each message and dead-letters a message after a delivery limit (20 by default in 4.0), which stops poison messages from looping forever. A stream is an append-only log stored in segment files and replicated; consumers read from any offset and reading does not delete messages, which gives Kafka-like replay and fan-out for large numbers of consumers.
Other protocols are layered on the same machinery. An MQTT client that subscribes to a topic gets a queue bound to the built-in topic exchange; an AMQP 1.0 client sends to an address that maps to an exchange or queue; so one broker can connect a sensor speaking MQTT to a backend worker speaking AMQP 0-9-1. For streams at larger scale, a super stream splits one logical stream into several partition streams, bound through a special exchange, which gives Kafka-like partitioned parallelism with per-key order.
Protection against overload also matters. RabbitMQ applies credit-based flow control inside the broker and, when memory use reaches a high watermark (40 percent of RAM by default) or free disk space falls below a limit, it blocks publishing connections until the alarm clears. This protects the broker but means a stuck consumer can eventually stop producers. The Erlang runtime gives each connection and queue its own process with its own small heap, so a crash in one is isolated and garbage collection is per process, with no stop-the-world pause. A cluster shares metadata (exchanges, bindings, users, queue definitions) among nodes; the metadata store has been moving from Mnesia to Khepri, a Raft-based store, for better behaviour in partitions.

example: An online shop publishes order events to a topic exchange called "orders". Three queues are bound: "billing" with key "order.*.paid", "eu-ship" with key "order.eu.*", and "audit" with key "order.#". The message with key "order.eu.paid" matches all three bindings and is copied into each queue. The message "order.us.created" matches only "audit". The key "order.eu.paid.refund" has four words, so neither "order.*.paid" nor "order.eu.*" matches it (each allows exactly three words), and only "order.#" does. This is the whole routing logic.
Now consumer behaviour. The "billing" queue has 3 workers, prefetch 5, each message takes about 20 ms. Workers do not poll; the broker pushes up to 5 unacknowledged messages to each. Worker 2 receives messages 11 to 15, finishes 11, 12 and 13 and sends acks for them, then crashes while processing 14. The broker sees the connection close, and requeues 14 and 15 for other workers, flagged redelivered. No message is lost. If worker 2 had processed 14 completely but crashed before acking, the work would be done twice, and the billing code must be idempotent, for example by keying on the order id in the database.
Prefetch arithmetic: the round trip between broker and worker is 1 ms and the work takes 5 ms. With prefetch 1, a worker needs the ack to travel and the next message to arrive before it can start: about 5 + 1 = 6 ms per message, or 167 messages per second. With prefetch 20, the next messages are already waiting, so the worker is busy all the time: 1 / 0.005 = 200 messages per second, 20 percent more. But if work takes 2 seconds, prefetch 20 lets one worker hold 20 messages (40 seconds of work) while other workers are idle, so a small prefetch is better for long jobs.
Capacity: 10,000 messages per second of 1 KB is 10 MB/s. If the consumers stop for one hour, the queue grows by 36 million messages, about 36 GB. A quorum queue with three copies uses about 108 GB across the cluster, and the memory alarm may block publishers before the disk is full. A queue is a buffer for bursts of minutes, not a store for hours of backlog; if you need that, use a stream or Kafka.
intuition: RabbitMQ is a post office with sorting rules: letters arrive at a sorting desk, which copies them into the right mailboxes by address pattern, and a letter is thrown away only when the recipient signs for it.
The design is natural when you start from the question "who needs to do this work, and how do I make sure it is done?" Separating the routing step (exchange) from the buffering step (queue) lets producers and consumers change independently: add a queue and a binding, and a new consumer starts receiving events, with no change to the producer. The acknowledgement rule gives a simple reliability story: the broker keeps a message until someone confirms they handled it.
mistakes: People often think RabbitMQ and Kafka are the same kind of system. In fact RabbitMQ is a smart broker with dumb consumers: it tracks each message, routes it and deletes it after the ack. Kafka is a dumb log with smart consumers: it keeps data for a retention period and each consumer tracks its own offset. This is why Kafka replays and RabbitMQ (queues) does not.
People often think RabbitMQ guarantees exactly-once delivery or global ordering. In fact it guarantees at-least-once with acknowledgements. Order holds within one queue for one consumer, but with several consumers or with redelivery, messages can be processed out of order or twice.
People often think durable queues alone make messages survive a restart. In fact three things are needed: a durable queue, messages published as persistent, and, for confirmation, publisher confirms. A transient message, or a producer that does not wait for confirms, can be lost.
People often think a bigger prefetch is always faster. In fact a large prefetch speeds short tasks but hoards messages in slow consumers, hurts fairness and increases the number of messages redelivered after a crash.
friction: Queues are not designed for very large backlogs. A classic queue and a quorum queue keep messages on disk but also need memory for indexes and in-flight state, and a backlog of tens of millions of messages slows the broker and triggers flow control. There is no replay of consumed messages from a normal queue, and a message goes to one consumer per queue, so a new consumer cannot read history.
Throughput is limited per queue because each queue is processed by one Erlang process (and a quorum queue by one Raft leader). To scale, you use many queues, sharding plugins or consistent-hash exchanges, which adds design work. Quorum queues are slower than classic queues because every message is replicated and fsynced, and they use more memory and disk per queue. Clusters are meant for a LAN; stretching one across regions is not supported, and the Shovel and Federation plugins are used between sites.
Operations have their own sharp points: network partitions need a defined policy (pause-minority is the usual choice), memory alarms stop publishers, thousands of queues or connections consume memory, and the Erlang runtime needs some knowledge for debugging. Behaviour changed across versions: classic queue mirroring was removed in 4.0, so old clusters need migration to quorum queues before upgrading. Last, a stuck consumer with unacked messages can hold them forever unless a consumer timeout (30 minutes by default in recent versions) is set.
tradeoffs: Choose RabbitMQ when you need task queues, request routing by pattern, per-message acknowledgement and retry, priorities or delayed retries, and moderate throughput (thousands to tens of thousands of messages per second). Choose Kafka (or Redpanda) when you need replay, many independent consumers of the same history, very high throughput (hundreds of thousands to millions of messages per second) or stream processing. You give up replay and scale with RabbitMQ; you give up routing flexibility and per-message acknowledgement with a log. Note that Kafka 4.2 made queue-style share groups production-ready, which narrows the gap for simple work queues.
Choose quorum queues for any queue whose messages matter and must survive a node failure; choose classic queues (with transient messages) only for data that you can lose, such as a cache invalidation feed, when you want the lowest latency. Choose streams when many consumers need the same data or replay.
Choose publisher confirms with batching (waiting for confirms of a window of messages) when durability matters; the cost is latency of an fsync and replication. Avoid per-message synchronous confirms, which can limit one connection to hundreds of messages per second. Choose fire-and-forget only for data that is cheap to lose.
Choose a managed queue (Amazon SQS, Google Pub/Sub) when you want no cluster to run and can accept less routing flexibility; choose RabbitMQ when you need exchanges, priorities, low latency and on-premises or hybrid deployment. Choose a single cluster for simplicity, or separate clusters per domain when one team's overload should not block another.
practice: Use quorum queues on three nodes for important queues, set a delivery limit, and attach a dead letter exchange so poison messages end up in a queue you can inspect. Use manual acknowledgements, make consumers idempotent, and use publisher confirms with a window of outstanding messages. Choose prefetch by job length: 1 to 10 for long jobs, 50 to 300 for short ones, and measure.
Design routing as a small set of well-named exchanges (one topic exchange per domain is common) with clear key conventions such as domain.entity.event. Name queues after the consumer service, not the producer, since the queue belongs to the consumer. Declare topology in code at start-up (idempotent declarations) or manage it with definitions files. For delayed retries, use a retry queue with a message TTL that dead-letters back to the work exchange, or the delayed-message plugin, and cap retry counts.
Watch the metrics: queue depth (ready and unacknowledged), consumer count and utilisation, publish and ack rates, memory and disk alarms, and Raft log sizes. Alert on growing queues, not on absolute depth alone. Set a consumer timeout so stuck consumers are detected. Keep connections long-lived and use channels per thread, instead of opening a connection per message. For upgrades, follow the version guide, and move off classic mirrored queues before moving to 4.x.

It does not store messages; if no queue matches, the message is dropped unless returned or sent to an alternate exchange.

How do quorum queues differ from classic mirrored queues, and why were mirrored queues removed? || Quorum queues use Raft with a leader and majority commit, giving defined behaviour in failures and no manual synchronization. A queue's depth keeps growing. For cluster metadata, use pause-minority so that the minority side stops serving, rather than diverging. Clients must reconnect and handle redelivery.

@@ kinesis
value: Amazon Kinesis Data Streams is AWS's managed log service. Producers put records into a stream; the stream spreads records over shards, each shard being an ordered, replicated, append-only sequence; and consumers read the records in order, at their own pace, within the retention period. You do not run brokers, disks or replication. You choose how many shards you need (or let AWS decide in on-demand mode), and AWS stores each record in three Availability Zones.
The problem it solves is the cost of running a streaming system. A self-managed Kafka cluster needs capacity planning, disk management, upgrades, a replication policy, monitoring and an on-call rotation. For a team that already lives on AWS and needs to ingest clickstreams, application logs, IoT telemetry or change events at tens of megabytes per second, renting a log by the shard-hour or by the gigabyte is simpler and easier to start. It connects directly to Lambda, Amazon Data Firehose (which delivers to S3, Redshift and OpenSearch), Managed Service for Apache Flink, and the rest of the AWS data stack, with IAM for access control and CloudWatch for metrics.
For the layer above (real-time analytics, event-driven serverless applications, data lake ingestion), it provides a durable, ordered, replayable buffer between producers and consumers. It stands on the distributed commit log (commitlog), which supplies the core model: an append-only sequence where each record gets a position, order is kept within a partition (here, a shard), data is replicated for durability, and readers keep their own place, so several consumers can read the same data independently and a failed consumer can resume. Kinesis keeps the model and hides the machines.
terms: Shard — the unit of capacity and ordering in a stream: an ordered sequence of records that accepts up to 1 MB/s of writes and serves up to 2 MB/s of reads (provisioned mode).
Partition key — a string chosen by the producer; its MD5 hash decides which shard receives the record, so records with the same key stay in order.
Sequence number — a number assigned by Kinesis to each record in a shard, increasing over time; consumers use it as a position.
Retention period — how long records stay readable, from 24 hours (default) up to 365 days.
Shard iterator — a pointer that tells GetRecords where to start reading in a shard (the oldest record, the latest, a sequence number or a timestamp).
Enhanced fan-out (EFO) — a way for a registered consumer to get its own dedicated 2 MB/s per shard, pushed over HTTP/2, instead of sharing the polling read limit.
On-demand mode — a capacity mode in which Kinesis scales shards automatically with traffic and bills by data volume, instead of by provisioned shards.
KCL — the Kinesis Client Library, which coordinates workers, tracks checkpoints and handles resharding for a consumer application.
history: Kinesis was announced by AWS at re:Invent in November 2013, and it followed the same idea as the log behind Kafka: after LinkedIn's engineers wrote about the log as the unifying abstraction for data (Jay Kreps, 2013), several companies built managed versions. AWS's earlier queue service, SQS (2004), deleted messages on receipt and could not replay; Kinesis added ordered, replayable, multi-consumer streams.
Its feature history is about removing the first design's limits. Retention was 24 hours at first, then 7 days in 2018 and up to 365 days in 2020. Enhanced fan-out arrived in 2018, because several consumers sharing the 2 MB/s read limit of a shard interfered with each other. On-demand capacity mode, launched in November 2021, removed the need to count shards. The 2025 changes raised the maximum record size to 10 MiB, and added an On-demand Advantage tier with higher quotas, such as more registered consumers per stream (50 instead of 20), according to the AWS limits page. Related services were renamed: Kinesis Data Firehose is now Amazon Data Firehose, and Kinesis Data Analytics is Managed Service for Apache Flink.
AWS also offers Amazon MSK, managed Apache Kafka, launched in 2018 for teams that want the Kafka API. The two services overlap and are often compared: Kinesis is simpler, deeply integrated and serverless-like, while MSK offers the full Kafka ecosystem and protocol. Kinesis remains an AWS-only, closed service, with no open-source implementation.
how: A stream is a set of shards. A producer calls PutRecord or PutRecords (up to 500 records and 5 MiB in one call) with a payload and a partition key. Kinesis computes the 128-bit MD5 hash of the key. Each shard owns a contiguous range of the hash space (for two shards, one has the lower half, the other the upper half), so the hash picks the shard. The shard assigns the next sequence number and writes the record to storage in three Availability Zones; only then does the call return success. Records with the same key always go to the same shard, in the order they were accepted. There is no ordering between shards.
Capacity is per shard. In provisioned mode a shard accepts up to 1 MB/s or 1,000 records per second of writes, whichever is reached first, and allows 2 MB/s of reads in total. If a producer exceeds a shard's rate, the service rejects the excess with a ProvisionedThroughputExceededException and the client must back off and retry. The total capacity of the stream is the sum over its shards, so scaling means more shards. You change the count by splitting a shard (dividing its hash range into two child shards) or merging two adjacent ones; the parent shard stays readable until its data expires, and consumers must finish the parent before reading the children, to keep per-key order. In on-demand mode, Kinesis does these splits for you, starts at a default of 4 MB/s write capacity and scales up to quotas that the AWS documentation lists as 10 GB/s in the largest Regions.
Reading has two paths. In the classic path a consumer calls GetShardIterator and then GetRecords repeatedly. Each shard permits 5 GetRecords calls per second and 2 MB/s in total, shared by all consumers that read that shard, so three applications reading the same stream split the same 2 MB/s per shard. In enhanced fan-out, a consumer registers and calls SubscribeToShard; Kinesis pushes records over an HTTP/2 connection with a dedicated 2 MB/s per shard per consumer, and lower latency than polling. A stream can have up to 20 such registered consumers (50 in the Advantage mode). Records are read in order within a shard, and the consumer decides where to start: the oldest record (TRIM_HORIZON), the newest (LATEST), a sequence number, or a timestamp.
Consumers keep their own position, which the service does not track for you. The KCL (and the equivalent in Flink and Spark connectors) stores a lease and a checkpoint per shard in a DynamoDB table: one worker holds the lease of each shard, workers rebalance leases when instances join or leave, and the checkpoint records the last processed sequence number. After a crash, the next lease holder resumes from the checkpoint, which gives at-least-once processing. AWS Lambda can be the consumer: an event source mapping polls each shard, batches records (for example 100 at a time), and invokes the function; with a parallelization factor up to 10, one shard can drive several concurrent invocations while keeping order per key, and options such as bisect-on-error and a failure destination handle poison records.
One detail catches many producers: PutRecords is not all-or-nothing. The response lists a result for each record, and some can fail (for example, because their shard is throttled) while others succeed, with the response's FailedRecordCount field telling you how many. The producer must resend only the failed ones. Because a retried record gets a later sequence number than records sent after it, retries can reorder events for a key; if strict order matters, send one batch at a time per key, or use the SequenceNumberForOrdering parameter of PutRecord, which makes a new record follow a given earlier one. Data at rest is encrypted if you enable server-side encryption with KMS, and a record is readable by consumers right after a successful put, so the end-to-end delay is mostly the consumer's polling or push interval.
The log concept below explains the shape of all this, and Kinesis differs from open-source logs in what it hides and what it fixes. It hides replication, leader election and disk management. It fixes the shard limit and the 24-hour to 365-day retention as service rules. There is no consumer group coordinator, no compaction by key, no transactions, and no exactly-once delivery. Producers that retry after a timeout can create duplicate records, so downstream processing should be idempotent, and the KPL (Kinesis Producer Library) can aggregate many small user records into one Kinesis record to use the 1,000 records per second limit better.

example: You ingest app events: 5,000 records per second, each 2 KB. Write rate is 5,000 x 2 KB = 10 MB/s. Per shard you can do 1 MB/s or 1,000 records/s: by bytes you need 10 shards; by record count you need 5. The tighter limit wins, so 10 shards, and you would keep headroom of, say, 20 to 30 percent and choose 13 shards. Reading capacity is 2 MB/s per shard, so 13 shards offer 26 MB/s in total, with polling.
Now add consumers. Your stream feeds three applications: real-time analytics, a fraud detector and a Firehose delivery to S3. With the classic shared read, each application needs 10 MB/s, so three need 30 MB/s, which exceeds the 26 MB/s the 13 shards can serve. Some calls would be throttled and the consumers would fall behind. With enhanced fan-out, each registered consumer gets its own 2 MB/s per shard, so each can read the full 10 MB/s without competing; the cost is a per-consumer-shard-hour fee and a per-GB fee for the data retrieved.
Hot key: the partition key is the user id, and one test account sends 3 MB/s. All its records hash to one shard, whose limit is 1 MB/s, so that shard throttles while the others are idle. Adding shards does not help, because the hash of that key always lands in one shard. The fix is to add a suffix to the key (for example user id + a random number from 0 to 3) so the traffic spreads over four shards, at the price of losing order across the suffixes for that user.
Resharding: you split shard-1, whose range is [2^126, 2^127). Kinesis creates two child shards, [2^126, 3x2^125) and [3x2^125, 2^127), and closes the parent. Consumers read the parent to its end, then the children. Because the same key always hashed to the parent and now hashes to exactly one child, order per key is kept across the change as long as consumers finish the parent first.
Latency: a producer typically sees tens of milliseconds for a PutRecord call and a consumer using enhanced fan-out typically receives the record within roughly 70 ms of it being accepted. Polling consumers see an extra 200 ms or more because of the polling interval. Both are acceptable for dashboards and alerts but are slower than a tuned Kafka cluster.
intuition: Kinesis is a set of numbered conveyor belts run by someone else: you decide how many belts you need, items with the same label always ride the same belt, and anyone can stand at a belt and look at items from earlier in the shift.
The design is natural once you see that a log scales by splitting it into independent ordered slices. A hash of the key assigns the slice, so order is kept where it matters (per key) and ignored where it does not. A managed service then turns the slice into a unit that can be priced, limited and billed, which is why throughput is stated per shard and why every capacity question reduces to counting shards.
mistakes: People often think Kinesis is just a queue like SQS. In fact records are not deleted when read. They stay until the retention period ends, any number of consumers can read them independently, and a consumer can rewind to reprocess. A queue gives each message to one consumer and removes it.
People often think more shards always improve ordering or speed. In fact each shard is ordered only within itself, so more shards add capacity but give no order across shards. A hot partition key still hits one shard, so its limit cannot be raised by adding shards.
People often think on-demand mode removes all capacity concerns. In fact it scales up automatically, but within quotas, it accommodates up to roughly double the highest throughput seen in the previous 30 days, so a much larger jump can be throttled while it scales, and at steady high volume it can cost more than provisioned shards.
People often think Kinesis gives exactly-once delivery. In fact it is at-least-once on both sides: a producer retry can write a record twice, and a consumer restart can reprocess records after the last checkpoint. Deduplicate with an id in the record or use idempotent writes.
friction: The shard model is the main friction. In provisioned mode you must size shards for peak load, watch for hot shards, and reshard (which has its own rules about parent and child shards and ordering). The per-shard 1 MB/s write limit is small compared with what a single Kafka partition can do on modern hardware (tens of MB/s), so Kinesis needs many more shards for the same throughput, and the 5 reads per second limit makes polling consumers hard to tune.
The service has narrower features than Kafka: no compaction, no transactions, no consumer groups managed by the service (the KCL and DynamoDB do that work), no per-topic configuration depth, and limits on consumers (20 or 50 enhanced fan-out consumers per stream). Cross-Region replication has to be built with other services. Cost can surprise: provisioned streams bill per shard-hour and per PUT payload unit, on-demand bills per GB in and out, and enhanced fan-out adds per-consumer charges, so a design with many consumers and high volume needs a calculation.
Lock-in is real. The API is AWS-specific, the clients (KPL, KCL) are AWS-specific, and integration with IAM, Lambda and Firehose is a benefit that is also a cost to leave. The latency floor of tens of milliseconds and the polling delays are fine for most analytics but not for ultra-low-latency trading-style systems. Finally, the service is single-Region; a Region failure needs a design for failover, because records are not replicated across Regions.
tradeoffs: Choose Kinesis Data Streams when your workload is on AWS, volume is modest to high (up to a few hundred MB/s), you value no operations, and your consumers are Lambda, Firehose or Flink. Choose Amazon MSK or self-managed Kafka when you need the Kafka API and its ecosystem (Connect, Streams, Schema Registry), higher per-partition throughput, longer-term low-cost retention, or portability across clouds. You give up portability with Kinesis, and some simplicity with Kafka.
Choose on-demand mode when traffic is unpredictable or the team has no time to manage shards; choose provisioned mode when traffic is steady and predictable, since provisioned shards are usually cheaper per MB at constant high load, and you can autoscale with the shard count. Estimate both before deciding, as the price crossover depends on volume and record size.
Choose enhanced fan-out when you have two or more consumers that each need full throughput or when latency under 100 ms matters; choose the shared polling path for one or two light consumers, because EFO adds a charge per consumer-shard and per GB. Choose Lambda as a consumer for simple per-record work with low operational burden; choose KCL or Flink when you need long-running state, windows or high throughput per record.
Choose SQS instead of Kinesis if each message is an independent job and you do not need ordering or replay. Choose Firehose directly if the only goal is delivery into S3 or a warehouse with no custom consumer; you give up replay and stream-level control.
practice: Start with the numbers: record rate, record size, number of consumers, and peak-to-average ratio. Compute shards from the stricter of bytes or record count, and add headroom. Choose partition keys with many distinct values and even traffic, and check shard-level metrics (IncomingBytes, WriteProvisionedThroughputExceeded, IteratorAgeMilliseconds) rather than only stream-level ones. Use the KPL aggregation or batch calls (PutRecords) to use the per-shard limits efficiently, and retry throttled records with exponential backoff and jitter.
For consumers, watch the iterator age: if it grows, the consumer is behind, and when it nears the retention period you lose data. Make processing idempotent. With Lambda, tune batch size, batch window and parallelization factor, enable bisect-on-error and an on-failure destination such as an SQS queue, and set the maximum retry attempts so one bad record does not block a shard for days. With KCL, give the DynamoDB lease table enough capacity.
Set retention to match your recovery needs: 24 hours is cheap, but a weekend outage of a consumer needs three days or more. Encrypt with KMS if required, grant least-privilege IAM, and use VPC endpoints to keep traffic private. Plan for Region failure if the stream is critical. For long-term history, deliver to S3 with Firehose rather than extending retention for months, and test resharding in staging before a traffic event.

interview: How do you scale a Kinesis stream that is being throttled, and how do you tell which kind of throttling it is? || Check shard-level metrics. If reads are throttled, consumers share the 2 MB/s per shard, so use enhanced fan-out or fewer pollers.
Explain how resharding preserves order. || A split closes the parent shard and creates two children covering its hash range. Consumers must read the parent shard to its end before reading its children, so records of a key are processed in the order they were written, as the key moved from parent to one child.
How does a Kinesis consumer application coordinate several workers? || With KCL, workers use a DynamoDB table of leases, one per shard; each worker holds some leases, renews them, and checkpoints its position. When workers join or die, leases are rebalanced and the new holder continues from the last checkpoint, so processing is at-least-once.
What delivery guarantees does Kinesis give, and how do you build exactly-once effects? || Durable and ordered per shard, but at-least-once. Producer retries and consumer restarts cause duplicates. value: Debezium is an open-source platform that turns a database into a stream of events. It reads the database's own change log, which the database writes anyway to recover from crashes and to feed its replicas, and publishes one event for every row that is inserted, updated or deleted. The events usually go to Apache Kafka, one topic per table. Other systems can then react to changes within a second or so: update a search index, invalidate a cache, load a data lake, or trigger a microservice, without anyone changing the application that writes to the database.
The problem it solves is that "copy the data somewhere else" is surprisingly hard to do correctly. Periodic queries ("give me rows changed since yesterday") miss deletes, add load to the database, and are late. Having the application write both to the database and to a message broker (a dual write) can leave them inconsistent, because there is no transaction across the two systems: one write succeeds and the other fails. Reading the transaction log avoids both problems. The log has every committed change, in commit order, with almost no extra load on the database, and the application does not need to know.
For the layer above (replicated read models, event-driven microservices, lakehouse ingestion, audit trails), Debezium gives a reliable, ordered change feed. It stands on Kafka Connect (kafka-connect), which supplies the runtime: Debezium connectors are Connect source connectors, so they get task management, offset storage, converters, transformations and a REST API for free. It stands on change data capture (cdc), which supplies the idea: treat the database's log as the source of truth for changes, take an initial snapshot of the existing data, and then stream the log from exactly the position where the snapshot ended.
terms: Change data capture (CDC) — a technique that detects row changes in a database and delivers them as events, ideally by reading the transaction log.
Transaction log — the database's ordered record of committed changes: the write-ahead log (WAL) in PostgreSQL, the binlog in MySQL, the redo log in Oracle.
Logical decoding — a PostgreSQL feature that turns the WAL into row-level change events through an output plugin; a replication slot remembers how far a consumer has read.
Snapshot — the initial consistent copy of existing rows that a connector reads before it starts streaming changes.
Envelope — the structure of a Debezium event: the row before the change, the row after it, source metadata, the operation code and a timestamp.
Tombstone — a record with a key and a null value, emitted after a delete so that Kafka's log compaction can remove the key.
Outbox pattern — writing an event into a special table in the same database transaction as the business change, and having CDC publish it, so the state change and the event are atomic.
Incremental snapshot — a way to re-read a table in chunks while the stream continues, without stopping or locking.
history: Debezium was started at Red Hat in 2015, led at first by Randall Hauch, and its first releases came in early 2016. The idea was not new: LinkedIn had written about database logs as the basis of data integration (Jay Kreps, 2013), its Databus system captured Oracle and MySQL changes, and Yahoo, Facebook and Netflix had internal tools. What was new was an open-source implementation that fitted Kafka Connect, which had just appeared in Kafka 0.9 (2015), and that supported several databases in the same shape.
The first connectors were MySQL, MongoDB and PostgreSQL, and over the years the list grew to SQL Server, Oracle, Db2, Cassandra, Vitess, Spanner, MariaDB and more. As of the 3.7 release (September 2026), the project lists connectors for those and others, such as CockroachDB, Informix, TiDB, SQLite and even Milvus. Gunnar Morling led the project for several years and popularised the outbox pattern in a widely read 2019 article. New runtimes were added beside Kafka Connect: Debezium Engine (a library to embed a connector in your own Java program) and Debezium Server (a standalone process that writes to Amazon Kinesis, Google Pub/Sub, Apache Pulsar, Redis and others), and a Kubernetes operator.
Two technical steps shaped current practice. First, the DBLog paper from Netflix (Andreakis and Papapanagiotou, 2020) described a watermark-based method for taking snapshots in chunks while the log keeps flowing; Debezium adopted it as incremental snapshots (2021), which removed the pain of long locking snapshots. Second, versions 2.x and 3.x moved connectors toward Java 17 and newer, added a JDBC sink for writing events back to relational databases, and improved heartbeat, signalling and transaction-metadata features.
how: A connector starts in one of two phases. In the snapshot phase, it reads the current state of the captured tables so that consumers have a starting point. For PostgreSQL it opens a transaction with a consistent snapshot, and records the log position (the LSN) at that moment; for MySQL it records the binlog file and position (or GTID), reads the tables, and later resumes there. Every row becomes a "read" event (operation code r). When the snapshot ends, the connector switches to streaming from the recorded position, so there is no gap and no overlap between the copy and the changes.
In the streaming phase, it behaves like a replica of the database. For MySQL, it connects with a unique server id and asks for the binlog, which must be in row format with full row images. For PostgreSQL, it creates a replication slot with an output plugin (pgoutput, which is built in), and the server sends decoded changes of the tables in a publication. The server holds back WAL until the client confirms it, and the connector confirms only after Kafka has accepted the events. MongoDB uses change streams; Oracle uses LogMiner or XStream; SQL Server uses its CDC tables. In every case the idea is the same: read the database's own ordered log of committed changes.
Each change becomes an event with a key and a value. The key holds the row's primary key, so all changes to one row go to the same Kafka partition and stay in order. The value is an envelope with before, after, source and op. The source block has the connector name, database, schema, table, the log position (LSN or file and offset), the transaction id and the commit timestamp. The operation is c (create), u (update), d (delete), r (snapshot read) or t (truncate). On a delete, the event has before set and after null, and is followed by a tombstone. Topic names follow server.schema.table, and column types are mapped to Connect and Kafka types, with schema information carried by the converter (Avro, Protobuf or JSON).
Debezium relies on the lower layers in a specific way. From Kafka Connect it gets distribution and recovery: the connector's position is stored as a Connect source offset in Kafka, so after a crash or restart the connector resumes from the last committed position. This is at-least-once: a crash after publishing events but before committing the offset repeats a few events. Connect also supplies the transformations that Debezium uses to reshape events, such as ExtractNewRecordState, which flattens the envelope to just the new row for simple sinks, and the outbox EventRouter, which turns rows from an outbox table into properly routed domain events. From CDC it takes the model: the log is the authority, ordering is per key, and the initial state and the stream are one continuous sequence.
Incremental snapshots deserve a closer look, because they solve the hardest part of CDC: how to copy a huge table while changes keep arriving. The connector reads the table in primary-key order in small chunks (1,024 rows by default). Before each chunk it writes a low watermark into a signalling table, which appears in the log; after the chunk it writes a high watermark. While the chunk is held in memory, the connector watches the log between the two watermarks. Any row in the chunk that was also changed in that window is dropped from the chunk, because the log event is newer and will be emitted anyway. The remaining rows are emitted as read events. The result is a correct merge of copy and stream without locks. Separately, heartbeat events keep the position moving on quiet tables, and optional transaction-metadata events (BEGIN and END markers with event counts) let a consumer rebuild transaction boundaries, which the per-table topics do not show.
Because a database log is one ordered stream, most connectors run a single task (tasks.max is effectively 1 per connector), so scaling comes from running several connectors for different sets of tables or databases, not from adding tasks. For MySQL, a connector also keeps a schema history in a Kafka topic, because the binlog records values by column position, not by name, and the connector must know what each table looked like at every point in time to decode old events; DDL statements are tracked in order. PostgreSQL sends the table's current structure with the stream, so it needs less of this.

A DELETE gives op "d", before filled and after null, then a tombstone with a null value so Kafka can compact the key away eventually.
Now the main operational danger, sized. The database writes 20 MB/s of WAL on average. The Debezium connector goes down for 2 hours (a failed deployment). The replication slot keeps all WAL the connector has not confirmed: 20 MB/s x 7,200 s = 144,000 MB, about 144 GB. If the database disk has 500 GB with 300 GB used, that is fine; if the outage lasts 10 hours, 720 GB would be needed, and the database runs out of disk and stops accepting writes. This is why you monitor slot lag, set max_slot_wal_keep_size, and alert early.
Snapshot cost: a table with 500 million rows of 1 KB is about 500 GB. Read at 50 MB/s by a single connector thread, that takes 10,000 seconds, about 2.8 hours, and on PostgreSQL the snapshot transaction holds back vacuum from removing old row versions meanwhile. With an incremental snapshot using chunks of 1,024 rows, the connector reads about 488,000 chunks interleaved with the live stream; it takes longer overall but never holds a long transaction or blocks writers, and can be paused and resumed.
Outbox: instead of publishing OrderPaid from the application (a dual write), the service inserts an event row into the outbox table in the same transaction as the status update. Either both commit or neither does. Debezium reads the outbox insert from the log and its EventRouter publishes it to a topic named after the aggregate type, using the aggregate id as the key. The service never talks to Kafka directly, and downstream consumers get an event if and only if the business change committed.
intuition: The database already keeps a diary of every change in order, so that it can recover; Debezium simply reads that diary aloud to everyone else, starting from the page where its last reader stopped.
The design is natural because the log is the one place where the truth about changes already exists, in order and complete. Anything else (queries, triggers, application hooks) is a guess about the log. Once you read the log, consistency becomes a question of position: the snapshot is the state at position P, the stream is everything after P, and the pair is a complete, replayable history. Kafka Connect then only needs to remember P.
mistakes: People often think Debezium polls tables for changes. In fact it reads the database's transaction log, so it sees every committed change, including deletes and intermediate updates, at the commit order, without querying the tables. Only the initial and incremental snapshots read tables directly.
People often think a CDC connector is harmless to the source database. In fact on PostgreSQL an unattended replication slot keeps WAL on disk forever and can fill the disk, and a long snapshot transaction can block vacuum. MySQL needs binary log retention longer than any connector outage. Monitor lag and disk, and drop unused slots.
People often think Debezium events show business meaning. In fact they show row-level state changes of the table design, with internal column names and normalised structures. Exposing them directly to other teams couples them to your schema. Use the outbox pattern or a translation layer to publish stable domain events.
People often think CDC gives global ordering and exactly-once delivery. In fact order is kept per primary key (per partition), not across tables, and delivery is at-least-once: a restart can repeat events. Consumers must be idempotent, for example by using the log position or by applying upserts.
friction: Schema change is the leading problem. A new column or a type change flows into events and may break consumers or sink tables; a MySQL connector must process DDL in order and keep its schema history; a dropped column or an incompatible type change can stop the connector. Schema registry compatibility rules and a rollout order (sinks before sources) are needed. Some types need care: decimals, timestamps with time zones, JSONB, and PostgreSQL TOAST columns that are unchanged and so omitted from the log.
The single-task design limits throughput: one connector reads one ordered log, typically tens of thousands of row changes per second at most, and a very write-heavy table can cause lag. Large transactions (a bulk update of millions of rows) produce a burst of events, and on some databases the connector holds the whole transaction in memory until commit unless streaming of in-progress transactions is enabled. Failover is another trouble spot: on PostgreSQL the replication slot lives on the primary, so a failover without synchronized slots can lose the position and force a new snapshot; recent PostgreSQL versions can synchronize slots to standbys, but it must be configured.
There are also security and compliance questions. The log contains every column, including personal data, so topics need access control, masking transformations and deletion handling: a "right to be forgotten" request means compacted topics, tombstones and downstream copies. Oracle capture needs LogMiner or XStream, and XStream has licensing implications. Debezium's guarantees depend on correct database settings (wal_level, binlog_format, row image), and a misconfigured database loses information silently. Finally, upgrades between versions can change event formats or defaults, so consumers need tests.
tradeoffs: Choose log-based CDC with Debezium when you need every change, including deletes, in order, with low load on the source, and a way to replay history. Choose periodic query-based extraction (the JDBC source, or batch ETL) when the table is small, only the current state matters, hourly freshness is enough, and you cannot enable the log settings; you give up deletes, intermediate states and freshness.
Choose the outbox pattern when other services need stable, business-level events with atomic consistency to your state change; choose raw table-level CDC when you replicate data to a lake or a search index and want the physical rows. The outbox adds a table and a small write per event; raw CDC exposes your schema.
Choose Kafka Connect deployment when you already run Connect and Kafka and want standard operations; choose Debezium Server when the target is not Kafka (Kinesis, Pub/Sub, Pulsar) and you want one small process; choose Debezium Engine when you embed capture in a Java application and manage offsets yourself. You give up Connect's tooling with the last two.
Choose Debezium over a managed alternative (AWS DMS, Fivetran, Airbyte, Flink CDC, or a cloud database's native streaming) when you want control, an open format, and low cost at high volume, and have the team to operate it. Choose a managed service when you want less operations work and can accept less flexibility and a per-row price.
Choose a full snapshot at the first start for small tables; choose "schema only" with an incremental snapshot for huge tables that must remain available, accepting a longer time until the data is complete.
practice: Prepare the database first. For PostgreSQL, set wal_level=logical, create a dedicated user with replication rights, a publication for the captured tables, a replication slot per connector, and set max_slot_wal_keep_size to protect the disk; also configure heartbeats (heartbeat.interval.ms) so that slots advance even when captured tables are quiet. For MySQL, enable the binlog in ROW format with FULL row image, GTIDs, and a retention long enough to cover your worst outage.
Capture only the tables you need (table.include.list), not the whole database, and choose REPLICA IDENTITY FULL only where the "before" image matters. Use Avro or Protobuf with a schema registry, and plan compatibility. Use the ExtractNewRecordState transformation for simple sinks, and keep the delete tombstone behaviour consistent with the sink. For huge tables, use incremental snapshots with a signal table, and test the restore path: how do you rebuild a sink from scratch? Keep Kafka retention long enough, or keep a compacted topic.
Monitor: connector status, streaming lag (the JMX metric MilliSecondsBehindSource), queue sizes, slot lag in bytes, database disk, and consumer lag downstream. Alert on a FAILED task and on slot growth. Make consumers idempotent and tolerant of reordering across tables. Treat DDL as a release event: announce schema changes, test them in staging with the connector running, and roll out in compatible steps. Secure topics that contain personal data, and write down the deletion process.
quiz: Why does Debezium read the transaction log instead of querying tables? || The log has every committed change in commit order, including deletes and every intermediate update, and reading it adds almost no load to the database. Polling queries miss deletes and intermediate states, and need extra columns and indexes.
How does a connector avoid gaps or overlaps between the initial snapshot and the stream? || It records the log position at the start of the consistent snapshot, reads the tables as of that position, and then starts streaming the log from exactly that position. The snapshot plus the stream form one continuous history.
What can go wrong with a PostgreSQL replication slot when a connector is down? || The slot keeps all WAL after its last confirmed position, so the WAL grows on the database disk. If the outage is long enough, the disk fills and the database stops accepting writes. Monitor slot lag and set max_slot_wal_keep_size.
The database produces 30 MB/s of WAL and the connector is down for 4 hours. How much WAL does the slot retain? || 30 MB/s x 14,400 s = 432,000 MB, about 432 GB. This must fit on the database disk, or you must limit the slot or restore the connector sooner.
When would you use the outbox pattern instead of capturing business tables directly? || When other services need stable, business-level events that are atomic with the state change, without depending on your table design. Capture the tables directly for replication to lakes or search indexes where physical rows are what you want.
interview: Walk through the dual-write problem and how CDC and the outbox pattern solve it. || Writing to a database and a broker separately is not atomic, so a crash between them loses or invents an event. With the outbox, the event is inserted in the same transaction as the state change, and CDC reads it from the log and publishes it. Either both exist or neither, and delivery is at-least-once, so consumers deduplicate.
What guarantees does Debezium give about ordering and delivery? || Per primary key, events are in commit order because the key chooses the partition; there is no order across tables or partitions. Delivery is at-least-once, because the offset is committed after publishing, so a crash can repeat events. Consumers must be idempotent.
How would you add a large table with 2 billion rows to an existing CDC pipeline without downtime? || Use an incremental snapshot triggered by a signal: it reads the table in chunks, reconciles each chunk with the live log using watermarks, never holds long locks or transactions, and can be paused. Size the chunks, watch the lag, and make sure the sink handles snapshot reads and updates as upserts.
How do schema changes propagate, and how do you keep consumers from breaking? || DDL on the source changes the shape of later events, and the connector registers new schemas. Use backward-compatible changes (add optional columns), the registry's compatibility checks, and upgrade consumers first. For MySQL, ensure the schema history topic is intact. Test with the connector running.
A PostgreSQL primary fails over to a standby. What happens to the connector? || The replication slot exists on the old primary, so unless the slot was synchronized to the standby, the new primary has no slot and the position is lost, forcing a re-snapshot or risking gaps. Use failover or synchronized slots, set up carefully, and test failover before you rely on it.
Why is throughput capped, and how do you scale CDC for a very busy database? || One ordered log is read by one task, so a single connector's speed is bounded by decoding and publishing on one thread. Split by tables or schemas across several connectors (each with its own slot), reduce captured columns and tables, tune batching, and consider whether the database can shard its writes.
