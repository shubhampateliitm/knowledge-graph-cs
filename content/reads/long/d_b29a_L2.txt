@@ contbatch
value: Continuous batching (also called iteration-level or in-flight batching) lets an LLM server change the set of requests it is processing at every single generation step. A request that finishes leaves immediately; a waiting request joins at the next step. Earlier servers used static batching: collect a batch, run it until every request in it finishes, then start the next batch. Because one answer might be 20 tokens and another 2,000, static batches spent most of their time with mostly finished requests occupying slots while new requests waited outside.
The effect is large. Published comparisons from 2023 reported up to about 20 times higher throughput than naive static batching on the same hardware, together with much lower queueing delay. Every serious serving engine (vLLM, SGLang, TensorRT-LLM, Hugging Face TGI and the engines behind commercial APIs) uses it, and it is the scheduling foundation on which chunked prefill, prefix caching and disaggregated serving are built.
Two lower concepts explain it. CPU scheduling (L3) supplies the idea and its vocabulary: a scheduler with a ready queue makes a decision at every time slice about which jobs run, with policies for fairness, priority and preemption. Continuous batching treats each decode step as a time slice. Queueing theory (L4) explains the trade-off it manages: Little's law (requests in the system = arrival rate × time in system) links concurrency, throughput and latency, and keeping a server busy without long waits is exactly the problem queueing theory studies.
terms: Prefill — processing the prompt tokens in one forward pass to build the KV cache; compute-heavy.
Decode step — one forward pass that produces one new token for every request in the batch; memory-bandwidth-heavy.
Static batching — running a fixed batch until all its requests finish.
Iteration-level scheduling — re-forming the batch at every decode step.
Batch slot — capacity for one request in the running batch, limited mainly by KV-cache memory.
Preemption — pausing a running request (and freeing or swapping its KV cache) to admit others or recover memory.
Time to first token (TTFT) — delay from request arrival to the first generated token.
Time per output token (TPOT) — average delay between generated tokens while streaming.
Goodput — throughput counting only requests that meet their latency targets.
history: Batching has always been the main trick for using GPUs efficiently: a GPU is fast only when it does many similar operations at once. Early transformer serving systems, such as NVIDIA's FasterTransformer and Triton Inference Server's dynamic batching, grouped requests that arrived close together and ran them as one batch. That worked for models with fixed-size outputs, such as classifiers, but not for generation, where each request runs a different number of steps.
The Orca paper (Yu and others, OSDI 2022) introduced iteration-level scheduling: the scheduler runs one iteration (one token) at a time and rebuilds the batch after each. It also introduced selective batching, batching the matrix multiplications across requests while handling the attention part per request, since different requests have different sequence lengths. In 2023 vLLM combined continuous batching with PagedAttention, which manages the KV cache in fixed-size blocks so that admitting and evicting requests at each step does not fragment memory. Hugging Face's TGI and NVIDIA's TensorRT-LLM ("in-flight batching") adopted the same model, and an Anyscale benchmark that year popularized the throughput gains.
Later work refined the scheduler rather than replacing it: chunked prefill (2023–2024) so long prompts do not stall decoding, prefix-aware scheduling that groups requests sharing cached prompts, priority and fairness policies for multi-tenant serving, and disaggregation of prefill and decode onto separate GPUs.
how: Start with why batching helps at all. In a decode step, the model must read every weight from GPU memory once, whatever the batch size. For an 8-billion-parameter model in 16-bit precision, that is 16 GB per step. An NVIDIA H100 reads memory at about 3.35 TB/s, so one step takes at least about 5 ms. With one request, that is about 200 tokens per second for the whole GPU. With 64 requests in the batch, the weights are still read once per step, so the step takes only a little longer, and the GPU produces about 64 tokens per step, roughly 60 times the throughput. Batching works until compute or the growing KV-cache reads become the bottleneck.
Static batching wastes this. Suppose a batch of 32 requests has output lengths ranging from 50 to 1,500 tokens. After 200 steps, most requests have finished, but the batch keeps running for 1,300 more steps for the few long ones, with most slots empty. Meanwhile new requests queue outside, adding seconds to their time to first token.
Continuous batching keeps the slots full. The scheduler keeps a waiting queue and a running set. Before every step, it removes requests that produced an end-of-sequence token or hit their length limit, then admits waiting requests as long as two budgets allow: enough free KV-cache blocks for their prompts and expected growth, and a maximum number of tokens processed per step. Newly admitted requests need their prefill, so the step processes a mix: prompt tokens for new requests and one token each for running ones. This is the CPU-scheduling idea at work, with a ready queue, an admission decision every time slice, and preemption when resources run out.
Memory is the binding constraint. Each running request holds a KV cache that grows by one token per step. If the scheduler admits too many requests, memory runs out mid-generation. Engines then preempt: they pick a victim (often the most recently admitted request), free its KV blocks, and either recompute its cache later or swap it to CPU memory. PagedAttention makes this practical by allocating KV memory in small blocks (for example 16 tokens each) on demand, so there is little waste and blocks can be freed individually.
Queueing theory explains the latency side. Little's law says L = λW: the average number of requests in the system equals the arrival rate times the average time each spends there. If a GPU serves 40 requests per second and each takes 4 seconds end to end, 160 requests are in flight on average; if memory allows only 100 concurrent requests, the rest wait in the queue and W grows. As utilization approaches 100%, queueing delay grows sharply, the classic hockey-stick curve, so operators run below full capacity to keep time to first token predictable.
Policies sit on top. First-come-first-served is simple but lets a burst of long prompts delay everyone. Engines add priorities, per-tenant fairness, limits on prompt tokens per step, and admission control that rejects or reroutes requests when the queue is too long. The metric that matters is goodput: how many requests per second meet both their TTFT and TPOT targets, not raw tokens per second.
Selective batching is the detail that makes mixed batches possible. Requests in one step have different lengths, and some are in prefill while others are decoding, so the batch is ragged. The engine flattens all tokens of the step into one long sequence for the parts of the model that treat tokens independently: the large matrix multiplications in the attention projections and the feed-forward layers, which are most of the arithmetic. Only the attention operation itself needs to know which tokens belong to which request; specialized kernels (PagedAttention, FlashAttention variants with variable lengths) compute it per request from the request's own KV blocks. This is why a step can contain 1,500 prompt tokens for one new request and one decode token each for 60 others, all in one forward pass, with the GPU's big matrix units seeing a single tall matrix.

example: A GPU serves an 8B model. Each decode step costs about 5 ms of weight reading plus about 0.05 ms per request for KV reads and compute, and the KV cache has room for 64 concurrent requests of average length. Requests arrive at 20 per second, with outputs uniformly between 50 and 950 tokens (average 500).
Static batching with batch size 32: a batch runs until its longest request finishes, about 950 steps. Step time is 5 + 32 × 0.05 = 6.6 ms, so a batch takes about 6.3 seconds. In that time it generates 32 × 500 = 16,000 useful tokens, about 2,550 tokens per second. But 20 requests arrive per second, so 126 arrive during each batch while the system finishes only 32: the queue grows without limit. The server is overloaded at 32-request batches even though the GPU is idle much of the time.
Continuous batching: the scheduler keeps up to 64 requests running. Step time is 5 + 64 × 0.05 = 8.2 ms, giving 64 / 0.0082 ≈ 7,800 tokens per second. The demand is 20 requests × 500 tokens = 10,000 tokens per second, still above capacity, so this GPU cannot serve 20 requests per second either, but it can serve about 15.6. With Little's law: each request needs 500 steps × 8.2 ms ≈ 4.1 s, and at 15 requests per second, L = 15 × 4.1 ≈ 62 requests in flight, just under the 64 slots. At 15 requests per second the system is stable, with short queues; at 17 it would overflow memory slots and queueing delay would explode.
The lessons: continuous batching roughly tripled useful throughput here (7,800 versus 2,550 tokens per second), and capacity planning is Little's law applied to KV-cache slots: arrival rate × time per request must stay below the number of requests the memory can hold.
intuition: A restaurant that seats a new guest as soon as any chair is free, instead of waiting for the whole table to finish dessert before seating the next group.
The idea is natural once you see that each generation step is a separate, cheap opportunity to reorganize. The GPU pays a nearly fixed price per step (reading the weights), so every empty slot in a step is wasted money. Re-forming the batch every step is just greedy use of that fixed cost, limited by the one resource that really fills up, memory for the KV cache. Operating systems learned the same lesson decades ago: schedule in small time slices and keep the processor busy with whatever is ready.
mistakes: People often think bigger batches always mean better service. Throughput rises with batch size, but each step gets slower, so time per output token and time to first token for new arrivals get worse. The right batch size depends on latency targets, not only on throughput.
People often think continuous batching removes queueing. It removes waste inside the batch; when arrivals exceed capacity, requests still queue, and queueing delay grows sharply near full utilization.
People often think the limit on concurrency is compute. For most LLM serving, the limit is KV-cache memory: how many requests' caches fit on the GPU at their current lengths. Long contexts reduce concurrency directly.
People often think tokens per second is the right metric to compare servers. A server can show high token throughput while many requests miss their latency targets; goodput under realistic arrival patterns is the honest comparison.
friction: Scheduling decisions interact in complicated ways. Admitting a long prompt helps throughput later but stalls decode steps now, which is why chunked prefill exists. Preemption wastes work (recomputing caches) or bandwidth (swapping), and choosing victims fairly is hard. Output lengths are unknown in advance, so memory planning is a guess; reserving too little causes preemptions and reserving too much wastes capacity.
Multi-tenant serving adds fairness and isolation problems: one customer's burst of long requests can raise latency for everyone. Features such as different LoRA adapters per request, structured output constraints and very long contexts make batches less uniform, and kernels must handle mixed lengths efficiently. Finally, benchmarks often use synthetic workloads; real traffic (bursty, heavy-tailed lengths, many shared prefixes) behaves differently.
practice: Use a serving engine with continuous batching and paged KV memory (vLLM, SGLang, TensorRT-LLM) rather than writing your own loop. Tune the two main knobs together: the maximum number of running requests (or KV memory fraction) and the maximum tokens per step, which bounds how much prefill can enter one step.
Measure TTFT, TPOT and goodput at realistic arrival rates and length distributions, and plot latency against load to find the knee of the curve; run below it. Use Little's law for capacity planning: required concurrent slots ≈ arrival rate × average request duration. Watch preemption counts and KV-cache usage; frequent preemptions mean the server is admitting more than memory supports.
For multi-tenant systems, add per-tenant rate limits and priorities, cap prompt length per request, and route long-context requests to separate pools if they hurt interactive traffic.
quiz: Why does batching many requests make LLM decoding much more efficient? || Each decode step must read all model weights from memory once regardless of batch size, so adding requests to the step adds little time while multiplying the tokens produced.
What problem does iteration-level scheduling fix compared with static batching? || In static batching, finished requests leave idle slots until the longest request ends, and new requests wait. Re-forming the batch at every step frees and refills slots immediately.
Requests arrive at 12 per second and each takes 5 seconds end to end. How many concurrent KV-cache slots do you need on average? || By Little's law, L = λW = 12 × 5 = 60 concurrent requests, plus headroom for bursts.
Why is KV-cache memory, rather than compute, usually the limit on how many requests can run at once? || Every running request keeps keys and values for all its tokens on the GPU, growing each step. Memory fills long before compute is saturated, especially with long contexts.
When might you deliberately limit batch size below what memory allows? || When latency targets matter more than throughput: larger batches slow each step, raising time per output token and delaying new requests. Interactive chat may cap batch size, while offline batch jobs run as large as memory allows.

@@ specdecode
value: Speculative decoding makes LLM text generation 2 to 3 times faster without changing the output. A small, fast "draft" mechanism guesses the next several tokens; the large "target" model checks all of the guesses in a single forward pass; a careful acceptance rule keeps the correct prefix of guesses and fixes the first wrong one. Because the rule is mathematically exact, the generated text has exactly the same probability distribution as if the large model had produced every token itself.
It works because of a quirk of hardware. At small batch sizes, generating one token with a large model is limited by reading the model's weights from memory, not by arithmetic. Scoring five tokens in one pass costs almost the same time as scoring one. If the draft is right most of the time, each expensive pass of the large model yields several tokens instead of one. Production systems (Google Search's AI features, major API providers, vLLM, SGLang and TensorRT-LLM) use it to cut latency for interactive use.
It stands on two lower concepts. Probability (L4) supplies the acceptance rule, a form of rejection sampling that guarantees the output follows the target model's distribution exactly. The KV cache (L2) makes it efficient: both draft and target keep caches of what they have processed, and when guesses are rejected, the caches are simply rolled back to the last accepted token.
terms: Target model — the large model whose output distribution must be preserved.
Draft model — a cheap mechanism (a small model, extra heads, or n-gram lookup) that proposes tokens.
Draft length (k) — how many tokens are guessed per round.
Acceptance rate (α) — the probability that a drafted token is accepted by the target.
Verification pass — one forward pass of the target over all k drafted tokens at once.
Rejection sampling — accepting a sample from one distribution with a probability chosen so the accepted samples follow another distribution.
Memory-bound — limited by memory bandwidth rather than arithmetic speed.
Self-speculation — drafting with the target model's own extra heads or layers, as in Medusa or EAGLE, instead of a separate model.
history: The idea of guessing ahead and checking later is old in computer architecture: processors speculate on branches and roll back mispredictions. For transformers, Stern, Shazeer and Uszkoreit's "Blockwise Parallel Decoding" (2018) predicted several future tokens and verified them, but only for greedy decoding. In late 2022 and early 2023, two groups independently published speculative decoding with exact sampling: Leviathan, Kalman and Matias at Google ("Fast Inference from Transformers via Speculative Decoding", ICML 2023) and Chen and colleagues at DeepMind ("Accelerating Large Language Model Decoding with Speculative Sampling", 2023). Both showed 2 to 3 times speed-ups with identical output distributions.
Follow-up work focused on better drafts. Medusa (2024) added several prediction heads on top of the target model, removing the separate draft model. EAGLE (2024) and its successors drafted at the level of the model's hidden features, reaching higher acceptance rates; tree-based verification (SpecInfer, 2023) let the target check several candidate continuations at once. Prompt-lookup or n-gram drafting copies likely continuations from the prompt itself, which works very well for editing and code tasks where outputs repeat inputs. By 2025, speculative decoding was a standard feature of open serving engines and widely reported in commercial systems.
how: First, why it can work at all: the roofline argument. In a decode step at batch size 1, the large model reads all its weights (for example 140 GB for a 70-billion-parameter model in 16-bit precision) to do roughly 2 floating-point operations per weight for one token. The GPU could do hundreds of operations per byte read, so it sits mostly idle on arithmetic. Processing 5 tokens in the same pass reads the same weights once and does 5 times the arithmetic, which still fits in the idle compute. So verifying k tokens costs about the same wall-clock time as generating one.
A round works like this. The draft produces k tokens, x₁ … x_k, one at a time (cheap, because the draft is small), recording its probabilities q(xᵢ) for each. The target runs one forward pass over the current context plus all k drafted tokens and computes its own probabilities p(·) at every position. This gives k + 1 distributions: one for each drafted position and one for the position after the last draft.
The acceptance rule goes left to right. For position i, accept xᵢ with probability min(1, p(xᵢ) / q(xᵢ)). If the target likes the token at least as much as the draft did, it is always accepted; if the draft was overconfident, it is accepted only sometimes. At the first rejection, discard the remaining drafted tokens and sample a replacement token from the normalized distribution max(0, p(·) − q(·)), which puts probability exactly where the draft underweighted. If all k tokens are accepted, sample one bonus token from the target's distribution at position k + 1. The probability concept guarantees that each produced token has exactly the target's distribution p, so the output is statistically identical to normal decoding; with greedy decoding the rule reduces to "accept while the draft matches the target's top choice".
The expected gain depends on the acceptance rate α and the draft length k. If each token is accepted independently with probability α, the expected number of tokens produced per target pass is (1 − α^(k+1)) / (1 − α). With α = 0.8 and k = 4, that is (1 − 0.33) / 0.2 ≈ 3.4 tokens per pass. The actual speed-up is smaller, because drafting costs time and verification of k tokens is slightly slower than one: typical end-to-end gains are 2 to 3 times.
The KV cache makes rounds cheap. The target's verification pass appends keys and values for all k drafted positions to its cache; after the acceptance decision, entries beyond the last accepted token are discarded by moving the cache's length pointer back, so nothing is recomputed. The draft model keeps its own cache and rolls back the same way. In paged KV caches, this means freeing the tail blocks.
The choice of draft matters most. A separate small model from the same family (for example a 1B model drafting for a 70B one) shares the vocabulary and often agrees with the target. Extra heads (Medusa, EAGLE) avoid running a second model and reach acceptance rates around 0.6 to 0.8 per token on chat data. N-gram or prompt lookup is free and excellent when the output copies the input, as in code edits or document rewriting. Systems tune k dynamically: longer drafts when acceptance is high, shorter when it drops.
Batching changes the picture. At large batch sizes, decode is no longer purely memory-bound, because the arithmetic of many requests fills the GPU; then verification of k tokens per request costs real compute, and speculative decoding's benefit shrinks or turns negative. It helps most for latency-sensitive, low-batch serving, which is exactly where users notice speed.

example: A 70-billion-parameter model serves an interactive coding assistant at batch size 1. One target decode step takes about 30 ms (dominated by reading weights). A 1-billion-parameter draft model from the same family takes about 3 ms per token. Verifying k drafted tokens in one target pass takes about 33 ms.
Without speculation: 30 ms per token, about 33 tokens per second.
With k = 4 and a measured acceptance rate α = 0.75: expected tokens per round = (1 − 0.75⁵) / (1 − 0.75) = (1 − 0.237) / 0.25 ≈ 3.05. Time per round = 4 drafts × 3 ms + 33 ms verification = 45 ms. Tokens per second = 3.05 / 0.045 ≈ 68, about 2.0 times faster.
Try k = 8: expected tokens = (1 − 0.75⁹) / 0.25 ≈ (1 − 0.075) / 0.25 ≈ 3.70. Time per round = 8 × 3 + 36 = 60 ms (verification grows slightly). Tokens per second ≈ 62, worse than k = 4: longer drafts waste work after the first rejection. Try k = 2: (1 − 0.42) / 0.25 ≈ 2.31 tokens per 6 + 31.5 = 37.5 ms, about 62 tokens per second. The best k here is around 4.
Now a code-editing task where the output repeats large parts of the input. Prompt-lookup drafting costs nearly nothing and reaches α ≈ 0.9 on copied spans. With k = 8: (1 − 0.9⁹) / 0.1 ≈ 6.1 tokens per 36 ms round, about 170 tokens per second, more than 5 times the baseline on those spans. The same exact acceptance rule guarantees the edited code is what the 70B model would have written.
intuition: An assistant drafts the next few words of your sentence; you glance over them at once, keep the words you would have said anyway, and correct the first one you would not.
The trick feels natural once you accept that the expensive part of generation is the reading, not the thinking: the big model must "open the book" (load its weights) for every step, and checking five words while the book is open costs about the same as producing one. A cheap drafter guesses well for most easy tokens (function words, repeated code, predictable phrases), and the big model's time is spent where it matters. The probability rule is the safety net: it makes sure that the shortcut never changes what the big model would have said, only how fast it says it.
mistakes: People often think speculative decoding approximates the large model and reduces quality. With the exact acceptance rule, the output distribution is identical to the target model's; only speed changes. Lower quality would indicate a bug or a non-exact variant.
People often think a bigger, smarter draft model is always better. A better draft raises acceptance but costs more time per drafted token; the best draft balances acceptance rate against its own cost, and it is often very small.
People often think longer drafts always help. After the first rejection, the rest of the draft is wasted, so expected gains flatten while costs keep rising; the optimal draft length is usually small (3 to 8 tokens) and depends on the acceptance rate.
People often think speculative decoding helps every deployment. At large batch sizes, the GPU's arithmetic is already busy, so verifying extra tokens costs real compute and can reduce total throughput. It helps most for latency-sensitive, low-batch serving.
friction: Gains depend on the workload: acceptance rates vary by domain, language, temperature and prompt, so speed-ups are unpredictable. A separate draft model must share the target's tokenizer, be trained or distilled to match it, be served alongside it (using memory) and be updated whenever the target changes. Extra-head methods require training the heads for each target model.
Integration with batching is complex: different requests accept different numbers of tokens per round, which makes batches ragged and complicates scheduling, KV-cache management and kernels. With high sampling temperatures, acceptance falls. Tree-based verification raises acceptance but uses more compute and memory per round. Finally, measuring benefit requires end-to-end tests under realistic load, because micro-benchmarks at batch size 1 overstate gains for busy servers.
practice: Use speculative decoding where latency matters and batch sizes are small: interactive chat, coding assistants, agents waiting on each step. Start with the engine's built-in options (a small same-family draft model, EAGLE-style heads if available for your model, prompt lookup for editing tasks) and measure acceptance rate and end-to-end tokens per second on your real prompts.
Tune draft length using the formula for expected accepted tokens and your measured costs, or let the engine adapt it. Disable or reduce speculation automatically when batch sizes grow, if your engine supports it. For editing, translation-like and retrieval-heavy tasks where output repeats input, prompt-lookup drafting is nearly free and often gives the largest gains. Verify exactness with distribution tests or greedy-output comparisons after enabling it.

@@ promptcache
value: Prompt caching, also called prefix caching, reuses work an LLM server has already done for the beginning of a prompt. When a request starts with the same tokens as an earlier one (a long system prompt, tool definitions, a document being discussed, or all previous turns of a conversation), the server keeps the attention keys and values computed for those tokens and skips recomputing them. Only the new suffix needs a prefill.
For many real workloads, the shared prefix is most of the prompt. A chat with 20 turns resends the whole history each turn; an agent resends its instructions, tool schemas and growing transcript at every step; a question-answering app sends the same 50-page document with each question. Reusing that work cuts time to first token sharply (often by 50 to 90% on long prompts) and cuts cost: providers charge much less for cached input tokens. It also raises server capacity, because GPU time spent on repeated prefills is freed for other requests.
It stands on three lower concepts. The KV cache (L2) is what is reused: the per-token keys and values for every layer. Hashing (L3) finds reusable blocks quickly: each block of tokens is identified by a hash of its contents and everything before it. Trees and tries (L3) organize prefixes so that requests sharing a common beginning share storage, as in SGLang's radix tree.
terms: Prefix — the first part of a prompt, from the first token up to some position.
KV block — a fixed number of tokens' keys and values (for example 16 tokens) stored together in GPU memory.
Block hash — an identifier computed from a block's tokens plus the hash of the block before it, so equal hashes mean equal prefixes.
Cache hit — a request whose leading blocks are already cached.
Radix tree — a tree where each path from the root spells a token sequence and shared prefixes share nodes.
Eviction — removing cached blocks, usually least recently used ones, when memory is needed.
Time to live (TTL) — how long a provider keeps a cached prefix after its last use.
Cache breakpoint — a marked position in a prompt up to which the API should cache.
history: Reusing transformer computation within one request was built in from the start: the KV cache avoids recomputing past tokens during generation. Reusing it across requests came later, as prompts grew. In 2023, as system prompts, retrieval-augmented generation and agents made long shared prefixes common, serving systems began to share KV blocks between requests. SGLang (Zheng and others, 2023; NeurIPS 2024) introduced RadixAttention, which stores cached prefixes in a radix tree with LRU eviction, and showed large gains on agent and few-shot workloads. vLLM added automatic prefix caching using block hashes over its paged KV cache, and later made it the default in its V1 engine.
Commercial APIs exposed the idea in 2024. Google's Gemini API introduced context caching in mid-2024, Anthropic launched prompt caching for Claude in August 2024 with explicit cache breakpoints and cached reads priced at a tenth of normal input tokens, and OpenAI added automatic caching for long prompts in October 2024. Providers later added options such as longer cache lifetimes. Systems research extended caching beyond one GPU: offloading cached blocks to CPU memory and SSDs, sharing caches across servers, and routing requests to the server that already holds their prefix (for example in NVIDIA Dynamo, LMCache and Moonshot AI's Mooncake).
how: The KV cache concept defines what can be reused. During prefill, each transformer layer computes a key and a value vector for every prompt token and stores them; generation then attends to these. Because a token's keys and values depend only on the tokens before it (causal attention), the cached entries for a prefix are valid for any request that starts with exactly the same tokens, whatever comes after. That is why reuse is limited to prefixes: change one token early, and every later token's keys and values change too.
Finding reusable blocks is a hashing problem. A paged engine such as vLLM splits each prompt into blocks of, for example, 16 tokens. For block i it computes hash(previous block's hash, tokens in block i, plus extra keys such as the LoRA adapter or image inputs). Including the previous hash makes each block's hash identify the entire prefix up to it. A hash table maps block hashes to physical KV blocks in GPU memory. When a request arrives, the engine walks its blocks from the start, looks up each hash, and stops at the first miss; all blocks before that are reused (their reference counts increase), and prefill runs only for the rest.
SGLang organizes the same information as a radix tree, the trie concept. Each edge holds a sequence of tokens, and each node points to the KV memory for its tokens. Requests that share a beginning share the path from the root; a new request walks down the tree as far as its tokens match, reuses everything along the path, and adds a branch for its new tokens. The tree makes it natural to see which prefixes are shared by many requests and to evict leaves (the least shared parts) first.
Eviction keeps memory under control. Cached blocks that no running request is using stay in GPU memory until space is needed, then are evicted in least-recently-used order (with tweaks that prefer to keep blocks shared by many requests). Some systems move evicted blocks to CPU memory or local SSD and bring them back on a hit, which is much faster than recomputing a long prefix. Across a cluster, cache-aware routing sends requests to the server that already holds their prefix, trading some load balance for many more hits.
API-level caching wraps this in pricing and rules. With Anthropic's API, for example, the developer marks cache breakpoints (up to four) in the request; the first request writes the prefix to the cache at a higher price than normal input, and later requests with an identical prefix read it at a tenth of the normal price, as long as they arrive within the cache lifetime (5 minutes by default, refreshed on each hit, with a longer option at a higher write price). Prefixes shorter than a minimum length (around a thousand tokens for many models) are not cached. OpenAI's API caches automatically for long prompts with a discount on cached tokens. In all cases only exact prefixes match, so prompt structure decides the hit rate.
The design rule for applications follows directly: put stable content first and changing content last. System instructions, tool definitions and reference documents go at the beginning, in a fixed order; conversation history follows, appended rather than rewritten; the new user message comes last. A timestamp, request ID or randomly ordered tool list at the top of a prompt destroys every later hit.
Prefix caching also changes scheduling and cost accounting. A request with a cache hit needs much less prefill work, so the scheduler can admit it sooner, and some engines sort the waiting queue to run requests that share a hot prefix together, so the prefix is used several times before it can be evicted. Shared blocks are reference-counted: a block used by 30 running requests is stored once, which multiplies effective KV capacity for workloads with long common prefixes such as few-shot prompts or a shared document. Providers bill these effects explicitly: writing a prefix to the cache costs a little more than normal input, because the server must keep memory for it, and reading it costs a small fraction of the normal price. The break-even point is simple arithmetic: with writes at 1.25 times and reads at 0.1 times the base price, a prefix pays off as soon as it is reused once within its lifetime.

With prefix caching: the first request prefills all 32,100 tokens and the server keeps the 32,000-token prefix. Later requests within the cache lifetime match the system prompt and manual (2,000 blocks of 16 tokens) and prefill only about 100 new tokens: time to first token falls to roughly 0.1 to 0.2 seconds, dominated by the question and scheduling.
Cost through an API priced at $3 per million input tokens, with cache writes at 1.25 times and cache reads at 0.1 times the base price: the first request costs 32,000 × $3.75 / 1M = $0.12 for the cache write plus a little for the question. Each later request costs 32,000 × $0.30 / 1M ≈ $0.0096 plus the question, instead of $0.096. Over 50 requests an hour, prompt cost falls from about $4.80 to about $0.60, roughly an 87% saving, provided requests arrive often enough to keep the cache alive (here, one every 72 seconds on average, well within a 5-minute lifetime).

Prefix caching follows from how attention works: what a model computes for a token depends only on what came before it. So any two requests that begin with the same words share the same work up to the point where they differ. Hashing and trees are the obvious bookkeeping for "which beginnings have I seen?". The only real constraint, exact prefixes, matches everyday intuition too: if the meeting's first sentence was different, your notes on everything after it may no longer apply.
mistakes: People often think the server caches answers. It caches the attention keys and values of prompt tokens; the model still generates a fresh answer for every request, which may differ with sampling.
People often think any repeated content in a prompt is reused. Only exact prefixes from the start of the prompt match. The same document placed after a changing line, or tools listed in a different order, gets no reuse.
People often think caching is free memory. Cached blocks compete with running requests for GPU memory; aggressive caching can reduce concurrency, which is why engines evict least recently used blocks and offload to CPU or SSD.
People often think caching changes the model's output. Reused keys and values are mathematically the same as recomputed ones (up to tiny floating-point differences), so outputs are unchanged.
friction: The exact-prefix rule is strict: small, harmless-looking changes early in a prompt (timestamps, user IDs, reordered tools, different whitespace) destroy reuse, and many applications are not designed with it in mind. Cache lifetimes are short at API providers, so infrequent requests pay write prices without later savings. Inside a cluster, load balancing and cache locality conflict: spreading requests evenly lowers hit rates, while routing by prefix creates hot servers.
Memory pressure limits how much can be cached, especially for long contexts, and offloading to CPU or SSD needs fast transfers to be worth it. Security and isolation matter: providers must keep caches separate between customers, since timing differences could otherwise reveal whether someone else sent the same prefix. Finally, cached content can become stale for the application: if a document changes, its old prefix stays cached until evicted, though it simply stops matching.
practice: Structure prompts for caching: stable content first in a fixed order (system instructions, tool definitions, reference documents), then conversation history appended without rewriting, then the new message. Keep timestamps, request IDs and per-user details out of the shared prefix, or put them at the end.
With APIs, place cache breakpoints after the large stable parts, check the reported cached-token counts in responses to confirm hits, and choose a cache lifetime that matches how often requests arrive. With your own servers, enable prefix caching in vLLM or SGLang, monitor hit rates and evictions, and consider cache-aware routing when many requests share long prefixes.
For agents, which resend growing transcripts on every step, prompt caching is often the largest single cost and latency saving available; design the agent's context to grow by appending rather than by editing earlier parts.

value: An LLM request has two phases with opposite characters. Prefill processes the whole prompt at once: thousands of tokens flow through every layer in large matrix multiplications, keeping the GPU's arithmetic units busy. Decode then generates one token at a time per request: each step does little arithmetic but must read all the weights and the KV cache from memory. When both phases share one GPU naively, they hurt each other: a long prefill (say, a 100,000-token document) occupies the GPU for seconds, and every user who is in the middle of streaming an answer sees their output freeze.
Chunked prefill and disaggregated serving are the two main fixes. Chunked prefill splits long prompts into pieces of a few thousand tokens and mixes each piece into the same batches as ongoing decode steps, so prompts progress without stalling streams. Disaggregated serving goes further: separate pools of GPUs run prefill and decode, and the KV cache built during prefill is transferred to a decode GPU over a fast network. Each pool can then be sized, configured and even built from different hardware for its own bottleneck. Modern engines (vLLM, SGLang, TensorRT-LLM) and large deployments (Moonshot AI's Mooncake, NVIDIA Dynamo-based systems and the large providers) use one or both.
Three lower concepts carry the design. Continuous batching (L2) supplies the step-by-step scheduler into which prefill chunks are inserted. The KV cache (L2) is the state that must be built in prefill and then used, or moved, for decode. The roofline model (L3) explains why the split makes sense: prefill has high arithmetic intensity and is compute-bound, while decode has low arithmetic intensity and is memory-bandwidth-bound, so they want different batch sizes, parallelism and even hardware.
terms: Prefill — processing all prompt tokens to build the KV cache and produce the first output token.
Decode — generating subsequent tokens one step at a time, each step reading weights and the KV cache.
Chunk size (token budget) — the maximum number of tokens processed in one engine step, shared by prefill chunks and decode tokens.
Stall (generation stall) — a pause in token streaming for running requests while the GPU is busy with someone else's prefill.
Disaggregation — running prefill and decode on separate GPU pools.
KV transfer — moving a request's KV cache from the prefill GPU to the decode GPU.
Arithmetic intensity — floating-point operations per byte moved from memory; the roofline model's key quantity.
TTFT and TPOT — time to first token (dominated by prefill and queueing) and time per output token (dominated by decode).
history: Early LLM servers treated a request's prefill as one big step. With continuous batching (Orca 2022, vLLM 2023), the scheduler could mix new requests' prefills and existing requests' decodes, but a long prefill still made one step very long. The SARATHI paper (Agrawal and others, 2023) proposed chunked prefills: split each prompt into equal chunks and "piggyback" decode tokens onto every chunk's batch, filling the arithmetic slack that decode leaves. Its follow-up, Sarathi-Serve (OSDI 2024), made stall-free scheduling with a fixed token budget per step the core of the serving loop. vLLM and other engines adopted chunked prefill, and vLLM's V1 engine (2025) made it the default.
In parallel, researchers argued that the phases should not share GPUs at all. DistServe (Zhong and others, OSDI 2024) and Splitwise (Patel and others at Microsoft, ISCA 2024) placed prefill and decode on separate machines and showed higher goodput under latency targets; Splitwise even proposed different GPU types for each phase. Moonshot AI's Mooncake (FAST 2025), which serves the Kimi assistant, built a KV-cache-centric disaggregated architecture with a distributed cache pool across CPU memory and SSDs. NVIDIA released Dynamo in 2025 with disaggregated serving and KV-transfer libraries, and SGLang and vLLM added prefill–decode disaggregation modes. By 2025–2026, disaggregation was standard at large scale, while chunked prefill remained the default for single-pool deployments.
how: The roofline model explains the conflict. During prefill of a 4,000-token prompt, each weight read from memory is used for 4,000 tokens' worth of multiplications, an arithmetic intensity in the thousands of operations per byte, far above a GPU's ridge point (an H100 can do roughly 300 operations per byte of memory bandwidth). Prefill is therefore compute-bound: it runs at near-peak arithmetic, and its time grows roughly linearly with prompt length (plus a quadratic attention term for very long prompts). During decode, each weight is used for one token per request in the batch, so intensity equals roughly the batch size: memory-bound until batches reach hundreds of requests. Prefill wants all of the GPU's compute; decode wants memory bandwidth and many requests batched together.
Without chunking, a continuous-batching step that admits a 32,000-token prompt must process all 32,000 tokens before anyone gets their next token. At 10,000 prefill tokens per second, that step takes 3.2 seconds, and every streaming user sees a 3.2-second freeze. The user who sent the long prompt waits too, but that is expected; the others' stalls are the problem.
Chunked prefill fixes the step size. The engine sets a token budget per step, for example 2,048 tokens. At each step, it first includes one decode token for every running request (say 60 tokens), then fills the remaining budget with prefill chunks: the next 1,988 tokens of the waiting prompt. The 32,000-token prompt finishes prefill in about 16 steps instead of one giant step, and each step is short enough (here roughly 0.2 to 0.25 seconds of mostly compute, overlapping with the memory-bound decode work) that streaming users see only small hiccups. Because decode alone leaves the arithmetic units mostly idle, the prefill chunk fills that idle compute: piggybacking makes both phases more efficient together than separately. The chunk size is a dial: larger chunks finish prompts faster (better TTFT for long prompts), smaller chunks keep TPOT smoother for everyone else.
The KV cache concept defines what chunking must preserve. Each chunk's tokens attend to all earlier tokens of the same prompt, so the engine keeps the partially built KV cache between chunks and the attention kernel reads the cached prefix plus the current chunk. Paged KV memory makes this simple: chunks allocate new blocks as they go.
Disaggregation removes the interference entirely. A router sends each new request to a prefill worker, which runs the prompt at large batch sizes and full compute, produces the first token, and then transfers the KV cache to a decode worker. Decode workers run large decode batches tuned for memory bandwidth, with no prompt work interrupting them. Each pool can use its own parallelism (for example more tensor parallelism for prefill to cut TTFT, more data parallelism for decode to raise batch size) and scale independently: a workload with long prompts and short answers needs more prefill capacity; chat with short prompts and long answers needs more decode capacity.
The cost is moving the KV cache. For a 70-billion-parameter model with grouped-query attention, the cache is about 320 KB per token, so a 32,000-token prompt produces about 10 GB. Over a 400 Gb/s network link (about 50 GB/s), that takes about 0.2 seconds, which is acceptable compared with seconds of prefill, especially when transfer overlaps with computation layer by layer. Over slower networks it is not, which is why disaggregated serving depends on fast interconnects (InfiniBand, RoCE, NVLink within a rack) and transfer libraries that move GPU memory directly. Combining disaggregation with prefix caching adds a third role: a shared KV store from which prefill or decode workers fetch already computed prefixes.

example: A server runs a 70B model on a node of GPUs. It prefills about 10,000 tokens per second when doing only prefill, and a decode step for its 60 running requests takes about 40 ms. A user submits a 32,000-token contract for summarization while 60 other users are streaming answers.
Without chunking: the engine runs the whole prefill in one step, about 3.2 seconds. All 60 streaming users see output stop for 3.2 seconds; their time per output token, normally 40 ms, spikes to 3,240 ms for one token. If long prompts arrive every 10 seconds, about a third of the time is spent in such freezes.
With chunked prefill and a 2,048-token budget per step: each step carries 60 decode tokens and about 1,988 prompt tokens. Prefill compute for 1,988 tokens is about 0.2 seconds, and the decode work overlaps with it (decode is memory-bound and the prefill chunk uses the idle arithmetic), so a step takes roughly 0.22 seconds. The contract's prefill finishes in 32,000 / 1,988 ≈ 16 steps, about 3.5 seconds, slightly slower than unchunked. The streaming users' worst token gap falls from 3.2 seconds to about 0.22 seconds. Reducing the budget to 512 tokens would cut the gap to about 0.08 seconds but stretch the contract's prefill to about 64 steps.
With disaggregation: the contract goes to a prefill pool, which finishes in about 3.2 seconds (or less with more tensor parallelism), then transfers 32,000 × 320 KB ≈ 10 GB of KV cache to a decode node at about 50 GB/s, about 0.2 seconds, mostly overlapped with the last layers of prefill. The 60 streaming users on the decode node never see a stall. The cost is a second pool of GPUs and fast networking; the benefit is that both TTFT and TPOT targets can be met at the same time, at higher load.
intuition: A kitchen where big catering orders are cut into portions cooked between regular plates, so diners already eating never wait, or, in a larger restaurant, a separate prep kitchen that prepares big orders and hands them to the line.
The design is natural once you see the two phases as different jobs. Prefill is like reading a long document, intense but done once; decode is like speaking a reply word by word, light but constant. Doing both on one machine works if the reading is broken into short sessions between words. At scale it is better to have readers and speakers on different machines, passing notes (the KV cache) between them, as long as passing notes is quick.
mistakes: People often think chunked prefill makes long prompts faster. It usually makes each long prompt's prefill slightly slower; the benefit is smoother streaming for everyone else and better overall goodput.
People often think disaggregation always beats a single pool. It needs fast interconnects, extra coordination and enough traffic to keep two pools busy; for small deployments or slow networks, chunked prefill on one pool is often better.
People often think prefill and decode differ only in size. They differ in bottleneck: prefill is compute-bound and decode memory-bound, which is why they want different batch sizes, parallelism and hardware.
People often think the KV cache is small enough to move freely. For long prompts on large models it reaches gigabytes per request; transfer time and network bandwidth are central design constraints.
friction: Choosing chunk sizes and token budgets is a trade-off between time to first token for long prompts and smoothness for streaming users, and the right setting depends on the traffic mix, which changes during the day. Mixed batches complicate attention kernels and scheduling.
Disaggregation adds operational complexity: two pools to size and autoscale, routing, KV-transfer failures, and the risk of one pool becoming the bottleneck when the workload shifts toward longer prompts or longer answers. It requires high-bandwidth, low-latency networking and careful memory management on both sides. Combining it with prefix caching, speculative decoding and multi-tenant priorities multiplies the scheduling choices. Benchmarks are hard to compare, because results depend heavily on prompt and output length distributions and on latency targets.
practice: On a single pool, enable chunked prefill (it is the default in recent vLLM) and tune the per-step token budget: start around 2,048 to 8,192 tokens, then measure p99 TPOT for streaming users and TTFT for long prompts under realistic traffic. Lower the budget if streams stutter; raise it if long prompts wait too long.
Consider disaggregated serving when you have steady high traffic, strict TTFT and TPOT targets at the same time, and a fast network (InfiniBand, RoCE or NVLink-connected nodes). Size the pools from your workload: total prompt tokens per second sets prefill capacity; total output tokens per second and concurrency set decode capacity. Monitor KV-transfer latency and both pools' utilization, and rebalance as the mix changes.
Measure success with goodput: the share of requests meeting both latency targets at a given load, not with raw tokens per second.
