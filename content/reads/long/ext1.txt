@@+ kafka
history: Kafka was built at LinkedIn around 2010 by Jay Kreps, Neha Narkhede and Jun Rao, open-sourced in early 2011 and graduated from the Apache incubator in 2012. The first goal was modest: move user-activity events and operational metrics from LinkedIn's services into Hadoop and monitoring systems without losing data. Existing message brokers (ActiveMQ, RabbitMQ) tracked per-message acknowledgements and struggled when consumers fell behind; log aggregators like Flume and Scribe were built for batch delivery. Kafka's designers borrowed from databases instead: treat the stream as a log, let consumers track their own position, and lean on the operating system's file and network machinery.
The project then grew in clear steps. Replication arrived in 0.8 (2013). Kafka Connect (2015) and Kafka Streams (2016) turned it into a platform. Idempotent producers and transactions (0.11, 2017) made exactly-once pipelines possible inside Kafka. KIP-500 (proposed in 2019) began removing ZooKeeper; KRaft became production-ready in 3.3 (2022), and Kafka 4.0 (March 2025) removed ZooKeeper entirely and made the new consumer rebalance protocol generally available. Tiered storage became production-ready in 3.9. Meanwhile, the Kafka protocol became an industry standard of its own: Redpanda, WarpStream, Amazon MSK, Confluent Cloud and others speak it, so 'Kafka' now often means the API as much as the Apache project.
how: The storage layout explains most of Kafka's performance. Each partition is a directory of segment files, each named after the first offset it contains, with an .index file (offset to byte position) and a .timeindex file (timestamp to offset). A fetch for offset X is a binary search in the sparse index followed by a short sequential scan. Old segments are deleted or compacted as whole files, which is cheap. Because records are written in batches that are already compressed by the producer, the broker usually never decompresses them: it validates and stores the bytes as they are, and consumers receive the same compressed batches.
The replication protocol is worth tracing once. A follower fetches from the leader exactly like a consumer, starting at its own log end offset. The leader tracks how far each follower has fetched; the high watermark is the highest offset that every in-sync replica has. Consumers can only read up to the high watermark, so they never see data that could be lost if the leader failed. If a follower falls behind for longer than replica.lag.time.max.ms, it drops out of the ISR. When a leader fails, the controller picks a new leader from the ISR, and leader epochs ensure followers truncate any uncommitted tail they may have copied from the old leader. With unclean.leader.election.enable=false (the default), Kafka prefers unavailability over choosing an out-of-date leader and losing acknowledged data.
Note what Kafka does not do by default: it does not fsync each write. Durability comes from having the data in the page cache of several brokers, ideally in different availability zones. This is a deliberate trade-off: a simultaneous power loss across all replicas could lose recent writes, but in exchange every write is a cheap memory copy. If you need stronger guarantees on a single machine, flush settings exist, at a large throughput cost.
practice: Most Kafka design decisions come down to five settings and one key. Choose the partition key for ordering and balance: user ID, device ID or account ID usually; avoid low-cardinality keys like country or event type, which create hot partitions. Choose the partition count for peak consumer parallelism with headroom, because increasing it later changes which partition each key maps to. Set replication.factor=3, min.insync.replicas=2 and acks=all for data you cannot lose; that combination tolerates one broker failure without losing acknowledged writes or blocking producers. Enable idempotence (the default since Kafka 3.0) and tune batch.size and linger.ms together: a few milliseconds of linger often doubles throughput.
Monitor consumer lag in time, not only in messages: 'this consumer is 4 minutes behind' is what the business feels. Watch under-replicated partitions, request queue time and disk usage per broker. For schema management, use a registry with compatibility rules from day one. For cross-region designs, decide whether each region owns its own topics (active–active with MirrorMaker 2 or vendor replication) or one region is primary; do not stretch synchronous replication across distant regions unless you accept tens of milliseconds on every write. And when cost is the main problem, look at tiered storage or object-storage-native Kafka-compatible systems, which trade a little latency for much lower storage and cross-zone network bills.

@@+ commitlog
history: The commit log is one of the oldest ideas in computing. Accountants have kept append-only ledgers for centuries, and databases have used write-ahead logs since the 1970s so that a crash never leaves data half-written. Replicated state machines, described by Lamport in 1978 and formalized by Schneider in 1990, rest on one observation: if several deterministic machines apply the same log of commands in the same order, they end up in the same state. Paxos and later Raft are protocols for agreeing on such a log.
For decades, though, the log stayed hidden inside each database. The shift came around 2010–2013. LinkedIn built Kafka to expose a log as a shared service, and Jay Kreps's 2013 essay 'The Log' argued that this is the unifying abstraction behind databases, replication and data integration. Martin Kleppmann's talk 'Turning the database inside-out' (2014–2015) pushed the idea further: the log is the source of truth, and tables, caches and indexes are materialized views of it. Event sourcing in application design and change data capture in data engineering are the same idea seen from two sides.
how: It helps to see how the commit log connects three worlds. Inside a database, the WAL is a commit log used for crash recovery and replication; physical replication in PostgreSQL ships WAL records to replicas. Between systems, CDC tools like Debezium read that same WAL (through logical decoding) and publish each change into Kafka, so the database's private log becomes a public stream. Inside consensus systems, Raft replicates a log of commands to a majority before applying them, and Kafka's own metadata now lives in such a Raft log (KRaft).
The guarantees a commit log gives are precise and limited. Records in one partition have a total order, and every reader sees them in that order. Committed records survive the failure of a minority of replicas. Readers can start from any retained offset. What a commit log does not give is just as important: there is no ordering across partitions, no built-in query language, no uniqueness constraint, and no protection against a producer writing the same logical event twice unless idempotence or deduplication is used. Systems that need more build it on top, for example by putting all events of one entity in one partition and enforcing rules in a single writer per key.
practice: Treat the log as an API contract. Each topic should have an owner, a schema with compatibility rules, a documented key, a retention policy and a clear meaning ('one record per order state change', not 'stuff about orders'). Separate topics that carry facts (things that happened, immutable) from topics that carry commands or requests; mixing them makes replay dangerous.
Design for replay from the start. Consumers should be idempotent, so reprocessing a day of data does not double-count. Keep enough retention, or archive to a lakehouse, so you can rebuild derived stores. Prefer compacted topics for 'current state per key' data and time-based retention for event histories. And when you need a database change to reach other systems reliably, use CDC or the transactional outbox rather than writing to the database and to Kafka separately in application code.
ref: paper | Implementing Fault-Tolerant Services Using the State Machine Approach: A Tutorial | Fred Schneider, ACM Computing Surveys 1990 |

@@+ streamproc
history: Continuous queries over streams were studied in research systems in the early 2000s (Aurora, Borealis, STREAM, TelegraphCQ) and used in finance as complex event processing. The big-data era brought Apache Storm (2011, from BackType and Twitter), which processed records one at a time but offered only at-least-once guarantees, and Spark Streaming (2013), which ran tiny batches to reuse Spark's fault tolerance. The Lambda architecture (2011) combined a fast but approximate streaming path with a slow but correct batch path, at the cost of writing everything twice.
Google's MillWheel (2013) and Dataflow (2015) papers showed how to get correct results from streams with event time, watermarks and triggers, and argued that batch is just a special case of streaming. Apache Flink (from the Stratosphere project, top-level Apache project in 2014) implemented these ideas with low-latency record-at-a-time processing and Chandy–Lamport-style distributed snapshots. Kafka Streams (2016) made stream processing a library rather than a cluster. Spark Structured Streaming (2016–2017) reframed streams as unbounded tables. More recently, streaming databases (Materialize, RisingWave) and incremental view maintenance in lakehouses (Databricks Declarative Pipelines, Flink and Paimon) have blurred the line between stream processing and databases.
how: The key engineering detail is how state and checkpoints interact. In Flink, the job manager periodically injects checkpoint barriers into every source. When an operator has received the barrier on all its inputs, it snapshots its state (asynchronously, often as incremental RocksDB files uploaded to object storage) and passes the barrier on. When every sink has acknowledged, the checkpoint is complete, and transactional sinks (such as Kafka with transactions) commit the output written since the previous checkpoint. On failure, every operator restores from the last completed checkpoint and the sources rewind to the offsets stored in it. This two-phase commit between checkpoints and sinks is what gives end-to-end exactly-once results.
Joins and aggregations depend on partitioning. Before a keyed operation, records are shuffled so that all records with the same key reach the same parallel task, which owns that key's state. Changing parallelism means redistributing state; Flink groups keys into 'key groups' so state can be moved in chunks. Stream–table joins keep the table side as state (often fed from a compacted topic or CDC stream); stream–stream joins need windows or time bounds, or state grows forever.
practice: Start by asking whether you need streaming at all. If results are needed within minutes rather than seconds, an incremental batch job on a lakehouse (triggered every few minutes) is often simpler to build, test and backfill. Choose streaming when freshness changes the business outcome: fraud, alerting, real-time bidding features, live dashboards, or keeping derived stores in sync.
When you do stream, design time explicitly: decide on event-time versus processing-time semantics, how late data may arrive, and what happens to data later than that (drop, side output or correction). Bound every piece of state with windows, time-to-live or compaction. Plan for code changes that alter state (savepoints in Flink, state schema evolution). Test with replayed production data, including out-of-order and duplicate events. Monitor end-to-end latency, checkpoint duration and size, backpressure, and consumer lag at the source.
ref: paper | MillWheel: Fault-Tolerant Stream Processing at Internet Scale | Akidau et al., VLDB 2013 |
ref: paper | Apache Flink: Stream and Batch Processing in a Single Engine | Carbone et al., IEEE Data Engineering Bulletin 2015 |

@@+ spark
history: Spark began in 2009 as Matei Zaharia's research project at UC Berkeley's AMPLab, motivated by machine-learning researchers who ran the same iterative algorithm over the same data many times, which was painfully slow on Hadoop. The 2010 HotCloud paper and the 2012 NSDI paper on resilient distributed datasets (RDDs) introduced in-memory datasets with lineage-based fault tolerance. Spark became an Apache top-level project in 2014, the same year Databricks was founded by its creators, and it set a world record in the 2014 Daytona GraySort benchmark, sorting 100 TB using about a tenth of the machines of the previous Hadoop record.
The API then moved up in abstraction. Spark SQL and DataFrames (2015) brought declarative queries and the Catalyst optimizer, so the engine, not the user, decided how to execute. Project Tungsten (2015–2016) attacked CPU and memory efficiency with off-heap binary rows and code generation. Spark 2.0 (2016) unified DataFrames and Datasets and introduced Structured Streaming. Spark 3.0 (2020) added adaptive query execution and dynamic partition pruning. Spark 3.4 (2023) introduced Spark Connect, separating thin clients from the cluster. Spark 4.0 (2025) made ANSI SQL the default, added VARIANT and other features, and removed Mesos support; 4.1 added Declarative Pipelines and a real-time streaming mode, and 4.2 followed in July 2026.
how: It helps to understand where time actually goes in a Spark job. A scan reads Parquet files from object storage, using column pruning and row-group statistics to read as little as possible; the number of input partitions is set by file sizes and spark.sql.files.maxPartitionBytes. Narrow transformations (filter, select, map) run in the same stage without moving data. Wide transformations (groupBy, join, distinct, repartition) need a shuffle: each map task writes its output partitioned by key to local disk, and each reduce task fetches its partition from every map task. With M map tasks and R reduce tasks, that is M × R small fetches, which is why shuffle-heavy jobs stress networks and disks, and why the default of 200 shuffle partitions is often wrong in both directions.
Memory is divided between execution (joins, sorts, aggregations) and storage (cached data), sharing a unified pool. When execution memory runs out, operators spill sorted runs to disk and merge them later, an external merge sort. Out-of-memory errors usually come from a single huge partition (skew), a broadcast table that is larger than expected, collecting too much to the driver, or Python processes outside the JVM's control.
practice: When a Spark job is slow, open the Spark UI and find the longest stage. Then look at the task-time distribution in that stage: if the maximum is far above the median, you have skew; salt the key or let AQE split skewed partitions. If all tasks are slow, look at input size per task, spill, and garbage collection time. If there are thousands of tiny tasks, coalesce partitions or compact small input files. If one stage reads far more data than needed, check that filters are pushed down and that tables are partitioned or clustered on the filter columns.
Some habits prevent most problems. Prefer DataFrame operations and built-in functions over Python UDFs. Broadcast small dimension tables explicitly when statistics are missing. Write output files of a sensible size (128 MB to 1 GB) rather than thousands of tiny ones. Cache only data you reuse, and unpersist it after. Keep the driver lightweight. And test jobs on a realistic sample with realistic skew, because Spark performance is mostly about data distribution, not code.

@@+ lakehouse
history: Data warehouses (Teradata, Oracle, later Vertica, Redshift, Snowflake and BigQuery) gave fast SQL and transactions, but on proprietary storage. Hadoop (2006 onwards) made it cheap to store anything in files, and the 'data lake' became the place where raw data landed, usually as CSV, JSON, Avro and later Parquet and ORC files. Hive (2008–2010) put SQL tables on top of those files, but its tables were just directories: no atomic commits, no safe concurrent writes, slow file listing on cloud object stores, and broken queries whenever a job failed halfway.
Around 2017–2019, three projects fixed this from different starting points. Netflix created Apache Iceberg to make huge tables reliable and fast to plan on S3. Uber created Apache Hudi to support upserts and incremental processing. Databricks created Delta Lake (open-sourced in 2019) to give Spark users ACID transactions on cloud storage. The 2021 CIDR paper named the pattern 'lakehouse'. Since then, the main battles have moved to catalogs and interoperability: Databricks acquired Tabular (the company of Iceberg's creators) in 2024, Snowflake released the Polaris catalog, Databricks open-sourced Unity Catalog, and formats added bridges such as Delta UniForm. Iceberg's v3 specification added deletion vectors, row lineage and the VARIANT type.
how: To understand performance, follow a query. The engine asks the catalog for the table's current metadata, reads the transaction log or manifest list, and builds the list of data files for the snapshot. It prunes files using partition values and per-file column statistics (minimum, maximum, null counts). For the files that remain, it reads only the needed columns, and within each Parquet file it skips row groups using their statistics. If deletion vectors exist, it filters out deleted rows while reading. The whole plan depends on metadata being small and well organized, which is why log checkpoints, manifest compaction and file clustering matter.
Writes follow the reverse path. A MERGE statement (the most common lakehouse write) finds the files containing matching rows, rewrites them with changes applied (copy-on-write) or writes deletion vectors and new files (merge-on-read), and commits a new version listing removed and added files. Two concurrent MERGEs that touch different files can both succeed; two that touch the same files will conflict, and one retries. Partitioning and clustering by the merge key reduce both the files touched and the chance of conflict.
practice: A few decisions shape most lakehouse outcomes. Choose partitioning conservatively: partition by a low-cardinality column used in almost every filter (often date), and use clustering (liquid clustering, Z-order or Iceberg sort orders) for the rest; over-partitioning creates millions of tiny files. Size files around 128 MB to 1 GB. Schedule compaction and cleanup (OPTIMIZE and VACUUM, or Iceberg's rewrite and expire procedures) as part of every pipeline, not as an afterthought. Use a catalog for every table, and grant access through it rather than through raw storage paths.
Organize data in layers (bronze for raw, silver for cleaned and conformed, gold for business-ready aggregates) and make each layer reproducible from the one below. Use the transaction log for operations: time travel to debug ('what did this table look like before last night's job?'), change data feeds to drive downstream incremental jobs, and table history to audit who wrote what. And keep an eye on interoperability: if several engines must write to the same tables, check that they agree on the format version and table features before enabling new ones.
