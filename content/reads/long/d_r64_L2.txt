value: Authentication answers one question: is the party on the other end really who they claim to be? HTTP has no memory, so every request arrives alone, and without authentication a server cannot tell Alice from an attacker. Authentication turns an anonymous connection into a known identity. Authorization, which decides what that identity may do, comes after it and is a separate problem.
In practice the work has two halves. First, the user proves identity once, using something they know (a password), something they have (a phone, a security key) or something they are (a fingerprint that unlocks a key on the device). Second, the server hands back a credential that is cheaper to check than the original proof: a session cookie that points to a server-side record, or a signed token that carries the identity inside it. Every later request shows that credential instead of repeating the proof. Single sign-on (SSO) moves the first half to one identity provider (IdP), so dozens of apps can trust one login.
The layers below supply the pieces. Password hashing (pwhash) and cryptographic hash functions (hashfn) let a server check a password without storing it. HMAC (hmac) is the core of one-time codes. Pseudorandom generators (prng) make session IDs and salts unguessable. Public-key cryptography (pkcrypto) and digital signatures (signatures) underlie passkeys and signed tokens, because the verifier holds only a public key and has nothing worth stealing. Web security (websec) explains cookie flags and why a signed-in browser can be tricked into sending requests. USB and NFC (usb, nfc) carry challenges to hardware keys. Above it, OAuth and OIDC (oauth) use authentication to issue tokens that other services accept, and cloud consoles, API gateways and secret stores all start from it.
terms: Session — server-side state that links a random identifier, carried in a cookie, to a logged-in user.
MFA (multi-factor authentication) — requiring proof from two or more different categories (know, have, are), so that stealing one does not suffice.
TOTP — time-based one-time password (RFC 6238): a 6-digit code computed from a shared secret and the current 30-second time step.
Passkey — a FIDO/WebAuthn credential: a key pair created per site, where the private key stays in an authenticator and signs a server challenge.
Phishing-resistant — an authentication method that cannot be replayed on a fake site, because the proof is bound to the real site's origin.
IdP and RP — identity provider (the system that authenticates the user) and relying party (the app that trusts the IdP's assertion).
OIDC and SAML — two protocols for SSO: OpenID Connect sends a signed JSON Web Token (JWT) called an ID token; SAML sends a signed XML document called an assertion.
Revocation — ending a credential's validity before its natural expiry.
Account recovery — the process that restores access when a user loses every credential; it is a second way into the account.
history: Passwords came first. MIT's CTSS time-sharing system used them in the early 1960s, stored in plain text. In 1979 Robert Morris and Ken Thompson described how Unix stored only a salted, deliberately slow hash of each password. That design, now with slower functions such as bcrypt and Argon2, is still right. Kerberos (MIT, late 1980s) let a user log in once and obtain tickets for many services, an early form of SSO. RSA SecurID tokens (1980s) added a hardware second factor.
The web needed state. Lou Montulli at Netscape introduced cookies in 1994 so a server could recognise a returning browser; RFC 6265 (2011) standardised them. Federation grew from the need to log in across company boundaries: SAML 1.0 appeared in 2002 and SAML 2.0 became an OASIS standard in 2005, and it still runs most enterprise SSO. OAuth 1.0 (2007) and OAuth 2.0 (RFC 6749, 2012) let one app act for a user at another without the password. OAuth did not say who the user was, so OpenID Connect (final 2014) added an identity layer on top of it.
The problem then shifted to phishing. One-time codes can be relayed by a fake site in real time. FIDO U2F (2014) put an origin-bound key pair in a USB key. The W3C standardised the browser API, WebAuthn, in 2019 (Level 2 in 2021). In 2022 Apple, Google and Microsoft committed to passkeys that sync between a user's devices, which removed the main barrier: losing the one hardware key. WebAuthn Level 3 became a W3C Recommendation in August 2026. NIST published SP 800-63-4 as a final standard in July 2025, replacing 800-63-3, and it now treats syncable passkeys as a valid authenticator at the second assurance level.
how: Take a sign-in from start to finish. Each step uses a lower layer for one job.
Step 1: Password check. The user sends the password over TLS. The server never stores it. At registration it generated a random salt with a CSPRNG (prng), then ran the password and salt through a slow, memory-hard function such as Argon2id (pwhash, built on hashfn) and stored the salt and output. At login it repeats the computation and compares the results in constant time. A stolen database then forces the attacker to pay the full cost for every guess against every user separately. NIST SP 800-63B-4 asks for at least 15 characters when the password is the only factor, no composition rules, no forced periodic change, and a check against a list of known-breached passwords.
Step 2: Second factor. A TOTP code is an HMAC (hmac). Server and phone share a secret K. Both compute HMAC-SHA1 over the counter \( T = \lfloor t / 30 \rfloor \), take four bytes at an offset chosen by the last nibble of the result, and keep the last six decimal digits. The server accepts the current step and usually one neighbour for clock drift. An attacker has about three chances in a million per guess, so the server must limit attempts. TOTP is not phishing-resistant: the user can type the code into a fake site, and the attacker passes it on within the 30 seconds. SMS codes add SIM-swap risk, and NIST lists SMS as a restricted method.
Step 3: Passkey. At registration the authenticator creates a key pair for this site only and sends the public key to the server (pkcrypto). At login the server sends a random challenge of at least 16 bytes. The browser adds the real origin to the data it passes to the authenticator. The authenticator unlocks the private key with a fingerprint or PIN (user verification) and signs the challenge together with a hash of the site's relying party ID and a set of flags (signatures). The server checks the signature with the stored public key, checks the origin and challenge, and checks that user verification was done. The fake site fails automatically: the browser reports the fake origin, so the signature is wrong for the real site. This is what "phishing-resistant" means mechanically. Nothing secret is stored on the server, so a database leak gives the attacker only public keys. Hardware keys talk to the browser over USB or NFC (usb, nfc); a phone can serve as the authenticator through the hybrid transport (QR code plus Bluetooth proximity).
Step 4: Session. After success, the server creates a session: a random identifier of at least 128 bits (prng), stored with the user ID, creation time and expiry in a database or cache. The browser receives it in a cookie flagged `Secure` (HTTPS only), `HttpOnly` (hidden from JavaScript, which limits what XSS can steal) and `SameSite=Lax` (not sent on most cross-site requests, which blunts CSRF) (websec). The server must issue a new identifier at login, otherwise an attacker who planted the old one (session fixation) shares the session. Each request costs one lookup, about a millisecond or less in an in-memory store.
Step 5: SSO. In OIDC authorization code flow the app redirects the browser to the IdP with a random `state`, a `nonce` and a PKCE challenge. The IdP authenticates the user, using any of the steps above, and redirects back with a short-lived code. The app exchanges the code at the IdP's token endpoint for an ID token. The ID token is a JWT signed by the IdP (oauth, signatures). The app fetches the IdP's public keys from a published key set, verifies the signature, and checks `iss` (issuer), `aud` (this app), `exp`, and the nonce. Only then does it trust `sub` as the user. The app then makes its own session as in Step 4. SAML has the same shape, but the assertion is XML with an XML digital signature, delivered by browser POST. XML signature handling is intricate, so use a maintained library.
Step 6: Tokens and revocation. Signed tokens (JWT) are checked locally by any service that has the public key, with no database call, which is why APIs and microservices like them. The cost is that the server cannot cancel one. Practical systems use access tokens that live 5 to 15 minutes, plus a refresh token that lives days or weeks, is stored server-side and is rotated at each use. Revoking the refresh token stops new access tokens; old ones die within minutes. Where this delay is not acceptable, services check a revocation list or call the token introspection endpoint (RFC 7662), which brings back a lookup per request, the same cost as a session.
Step 7: Recovery. When the user loses all factors, a recovery path must restore access. Whatever proves identity in recovery (email link, phone, recovery codes, a support agent) works like a password that bypasses MFA, so it must be as strong as the primary route. NIST SP 800-63B-4 has a section on recovery with saved and issued recovery codes and a notification to the user whenever recovery happens.

example: Three small calculations show how the parts behave.
Step 1: A TOTP code. Use the test secret from the RFCs, the ASCII string `12345678901234567890`, at Unix time 59 seconds. The time step is \( \lfloor 59/30 \rfloor = 1 \). HMAC-SHA1 of the 8-byte counter 1 under this key is the 20 bytes `75a48a19d4cbe100644e8ac1397eea747a2d33ab`. The last byte is `ab`, so the offset is its low nibble, 0xb = 11. The four bytes starting at byte 11 are `c1397eea`. Clear the top bit and you get 0x41397eea = 1,094,287,082. Take the last 6 digits: 287082. That is the code both sides compute. (RFC 6238 lists the 8-digit form of the same value, 94287082.) A server that accepts the previous, current and next step accepts 3 codes out of 1,000,000, so a guesser has a 0.0003% chance per try. With a limit of 5 attempts it is about 0.0015%.
Step 2: A passkey login on a phishing site. The user clicks a link to `examp1e-bank.com`. The attacker's page asks the browser to sign in. The browser sets the origin to `https://examp1e-bank.com` and looks for credentials whose relying party ID is `examp1e-bank.com`. It finds none. There is nothing for the user to approve, and nothing to relay. With TOTP, the user types 287082 into the fake page and the attacker relays it to the real page within 30 seconds.
Step 3: Revocation delay. Your API issues JWT access tokens that live 15 minutes, with a rotated refresh token. At 10:00 a contractor signs in and gets a token valid until 10:15. At 10:02 you disable the account and revoke the refresh token. The contractor can use the old access token until 10:15, a 13-minute window, on every service that checks only the signature. A server-side session has no window: delete the record and the next request fails. Its price is one cache lookup per request; at 20,000 requests per second that is 20,000 lookups per second, which one small Redis node handles, but every request path now depends on it.
intuition: A hotel checks your passport once at the desk, then gives you a key card; a passkey is a passport that only works at the hotel it was issued for.
Authentication is costly and risky to repeat, so the design splits it in two. The strong check happens once. Its result becomes something cheap to carry and easy to verify, and it expires. The halves tune separately: login can get stronger without slowing every request.
The move from passwords to passkeys follows the same logic. A password is a secret that you must reveal to prove you know it, so anyone you reveal it to can reuse it. A signature proves you hold a key without revealing it, and because the signed data includes the site's identity, it is useless anywhere else. The best secret is one that never leaves the device and never reaches the server.
mistakes: People often think MFA stops phishing. In fact it depends on the factor. TOTP codes, SMS codes and approve-only push prompts can all be relayed or pushed on a user by an attacker in real time. Attackers entered Uber in 2022 by sending repeated push prompts until an employee approved one. Only origin-bound methods such as passkeys and security keys stop the relay, because the proof itself names the site.
People often think a JWT is a more secure kind of session. In fact a JWT is a signed container with no secret in it, and anyone can read the payload. It saves a database lookup, and it loses the ability to cancel the credential at once. A JWT kept in `localStorage` is readable by any XSS, while an `HttpOnly` cookie is hidden from scripts.
People often think a passkey is stored in the browser or on the website. In fact the site stores only a public key. The private key lives in the authenticator: a secure enclave or TPM, a hardware key, or a password manager's encrypted vault. A synced passkey is encrypted end to end between a user's devices by the provider, so its safety depends on how well the user's cloud account is protected.
People often think complex password rules make passwords strong. In fact length and uniqueness matter, and forced symbols and monthly changes push users toward predictable patterns such as `Winter2026!`. NIST SP 800-63B-4 removes composition rules and periodic changes and requires blocklist checks.
People often think the login is the only door. In fact account recovery is a second door, often weaker. If the support desk resets MFA after a phone call, a convincing voice defeats the passkey.
tradeoffs: Choose server-side sessions when the app is a browser app calling its own backend, when you need instant logout or "sign out of all devices", and when one lookup per request is acceptable. Choose signed tokens when many independent services must verify identity without calling a central store, and accept the revocation window: keep access tokens to 5 to 15 minutes and store refresh tokens on the server.
Choose passkeys as the primary method when you can support recovery, because they remove phishing and password reuse. Keep a password or email fallback only if your user base needs it, knowing that the fallback sets your real security level. For high-privilege staff (admins, engineers with production access) require device-bound keys on hardware security keys. NIST states that syncable authenticators cannot reach the highest assurance level (AAL3), which needs a non-exportable key.
Choose OIDC for new SSO integrations and for mobile and single-page apps; the ID token is small JSON and libraries are plentiful. Choose SAML when an enterprise customer's IdP requires it; many large organisations still do. Either way, use an existing IdP (Okta, Entra ID, Keycloak) rather than building one; the price is a critical dependency, because if the IdP is down nobody signs in.
Choose stricter and shorter sessions for sensitive operations (changing payout details, adding a new authenticator) by requiring recent re-authentication, and longer sessions for low-risk reading. NIST shows the scale: at AAL2, re-authentication within 24 hours and a 1-hour inactivity limit; at AAL3, 12 hours and 15 minutes. Each shorter limit costs user patience and support tickets.
friction: Recovery is the hardest unsolved part. A system that is strictly phishing-resistant but lets users recover with an SMS code is only as strong as the SMS. A system with no easy recovery locks out real users, and support teams become the target of social engineering. Good designs push users to register two authenticators, issue single-use recovery codes, delay completion of recovery, and notify every other channel the user has.
Passkeys have rough edges. Users must understand where a passkey lives: a phone keychain, a password manager, a laptop. Moving between ecosystems and shared accounts are still awkward. Enterprises must decide whether synced passkeys are acceptable, because the sync provider joins the trust base. A site that adds passkeys but keeps passwords has two systems to defend.
Federation concentrates risk. One IdP outage or one stolen IdP signing key affects every app. SAML and JWT validation bugs are common and serious: accepting `alg: none`, skipping the audience check, trusting an unsigned part of an XML document (signature wrapping). Malware can steal a session cookie from a compromised browser, which gives the attacker a session without beating MFA (session hijacking); short lifetimes and device-bound sessions are the defences, and the latter are still being rolled out.
Finally, defences cost usability unevenly: people without smartphones, shared devices in clinics or factories, and users with accessibility needs do not fit the standard flows.
practice: Do not write your own authentication. Use a maintained library or a managed IdP and spend your effort on configuration. Hash passwords with Argon2id (or bcrypt or scrypt) using the library's recommended parameters, and tune the cost so one hash takes tens to hundreds of milliseconds on your hardware. Compare a new password against known-breached lists and allow long passwords and paste.
For sessions, use a random identifier of 128 bits or more from the system CSPRNG, set `Secure`, `HttpOnly` and `SameSite`, prefer the `__Host-` cookie prefix, rotate the ID at login and at privilege changes, and set both an idle timeout and an absolute timeout. Protect state-changing requests from CSRF. For tokens, validate the signature with a fixed list of allowed algorithms, check `iss`, `aud` and `exp`, use authorization code flow with PKCE for browser and mobile apps, and read the OAuth security best practice (RFC 9700).
Offer passkeys with conditional UI (the browser suggests a passkey in the username field), and show users their registered authenticators and active sessions with a "sign out everywhere" button. For staff, enforce phishing-resistant MFA at the IdP; where push remains, use number matching instead of plain approve buttons.
Test recovery as seriously as login: list every route into an account and which alerts it sends. Log sign-ins, MFA changes and recoveries, and alert on new devices and bursts of prompts.
interview: Why can a passkey not be phished when a TOTP code can? || The WebAuthn signature covers data that includes the origin as the browser sees it, and the credential is scoped to a relying party ID. A fake site has a different origin, so the browser finds no credential or produces a signature the real server rejects. A TOTP code carries no information about where it was typed, so an attacker can relay it within its 30-second window.
Design logout and "disable this employee now" for a system with JWT access tokens and many services. || Keep access tokens short (about 5 minutes) and rotate server-held refresh tokens; revoking the refresh token stops renewal. For immediate effect, publish a revocation event (session ID or user ID with a timestamp) that gateways cache and check, or reject tokens issued before a per-user `not_before` time. Any immediate revocation brings back shared state.
A user reports their account was taken over although they had MFA. List the likely paths. || Real-time phishing relay of TOTP or SMS, push fatigue, SIM swap, a stolen session cookie from malware or XSS, an OAuth consent grant to a malicious app, or a weak recovery route (support desk, email reset). Check logs for recovery events and new authenticators.
What are the risks in your SSO integration, and what must the relying party check on an ID token? || Verify the signature against the IdP's published keys with an allowed-algorithm list, then `iss`, `aud`, `exp`, and the `nonce` you sent; use PKCE and a `state` check on the redirect. Map users by `iss` plus `sub`, never by email alone, because emails can change or be unverified.
When is a syncable passkey acceptable and when must you require a hardware key? || Synced passkeys suit consumers and most workforce use: they resist phishing and survive device loss. NIST places them at AAL2 at most because the private key is exportable to the sync provider. Require a device-bound key on a hardware token for admins, regulated access or when policy demands AAL3, and pair that with a tested recovery process.
quiz: What is the purpose of the salt in password hashing? || A random salt makes the hash of the same password different for every user. An attacker cannot use one precomputed table against all accounts and must attack each hash separately.
Why does a passkey sign-in on a fake website fail even if the user is fooled? || The browser includes the real origin of the page it is on in the data the authenticator signs, and the credential is tied to the legitimate relying party ID. A fake origin finds no matching credential or produces a signature the real server rejects, so nothing usable can be relayed.
Why can a server not simply "cancel" a JWT that has not yet expired, and what are two ways to limit the damage? || The token is verified by signature alone, with no stored record to delete. Limit the damage by using short lifetimes (about 5 to 15 minutes) with rotating refresh tokens that can be revoked, or by checking a revocation list or an introspection endpoint on each request.
A 6-digit TOTP server accepts the previous, current and next time steps and allows 5 attempts. What is the chance that a blind guesser succeeds? || Three valid codes out of 1,000,000, so 3 in 1,000,000 per attempt, and about 15 in 1,000,000 (0.0015%) across 5 attempts.
Your company must choose between synced passkeys and hardware-only security keys for all staff. How do you decide? || Synced passkeys give easy enrolment and recovery and resist phishing, so they fit most staff, at the cost of trusting the sync provider and having an exportable key. Hardware keys give the highest assurance (non-exportable keys) but cost money, can be lost, and need strong recovery.
