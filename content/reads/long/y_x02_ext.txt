terms: Event time — the time an event really happened, written into the event by the device or service that produced it.
Processing time — the time the stream processor sees the event; it can be seconds, hours or days after the event time.
Watermark — a marker in the stream that says "no more events with event time earlier than T are expected"; it lets time windows close.
Window — a finite group of events cut out of the endless stream, by time (tumbling, sliding, session) or by count.
Keyed state — data an operator remembers per key (a count, an open session, a join buffer), owned by exactly one parallel task.
Checkpoint — a consistent snapshot of all operator state plus the source offsets, used to restart after a failure.
Barrier — a special record injected into the stream that separates "before checkpoint N" from "after checkpoint N".
Backpressure — the slowing down of upstream operators and sources when a downstream operator cannot keep up.
Allowed lateness — how long after a window has fired the system still accepts late events and sends an updated result.
Effectively-once — every event changes the visible state and output exactly once, even if it is processed more than once inside the system.
how: Watermarks have to travel through the graph, and the rule for combining them matters. Each source task creates watermarks from the event times it reads, most often "the largest event time seen so far minus a fixed bound", for example 30 seconds (bounded out-of-orderness). After a shuffle, an operator receives data from every upstream task, so it has several input watermarks. It keeps the latest watermark from each input and uses the minimum as its own, because it can only be sure about a time that all inputs have passed. When its watermark passes the end of a window, the window fires; once it passes the end plus the allowed lateness, the window's state can be deleted. The minimum rule has a sharp edge: one idle input, such as a Kafka partition that receives no data, holds the minimum back, and no window ever closes. Flink lets a source mark itself idle after a timeout (withIdleness), so it is left out of the minimum.
Backpressure is a flow-control mechanism, not only a symptom. In Flink, records move between tasks in network buffers of 32 KB by default. Since Flink 1.5 it uses credit-based flow control: a receiving task tells its sender how many free buffers ("credits") it has, and the sender sends only that many. When a sink slows down, its credits run out, the upstream task's output buffers fill, its processing thread blocks, and the effect moves back step by step to the source, which then simply reads from Kafka more slowly. Nothing is dropped and memory stays bounded. The backlog stays in Kafka, where it is cheap to keep, and it is visible as consumer lag. Kafka Streams needs no such protocol because each task pulls records from Kafka at its own speed; Spark Structured Streaming bounds each micro-batch with options such as maxOffsetsPerTrigger.
Backpressure and checkpoints interact badly. An aligned barrier waits in the queue behind all buffered records, so under heavy backpressure a checkpoint can take minutes. An operator with two inputs must also stop reading the faster input until the barrier arrives on the slower one. Flink 1.11 added unaligned checkpoints: the barrier overtakes the buffered records, and those in-flight records are saved as part of the checkpoint. Checkpoints then finish in roughly constant time, at the price of larger checkpoint files.
Where the state lives decides how big it can grow and how expensive checkpoints are. Heap state keeps Java objects in memory: fast, but limited by memory size and garbage collection, and each checkpoint copies all of it. The RocksDB state backend keeps state in a local LSM tree on disk, so state can be much larger than memory; incremental checkpoints upload only the new SST files since the last checkpoint, so a 500 GB state may need only a few GB of upload per checkpoint. Reads then cost a RocksDB lookup instead of a memory access, which is why hot keys and large values matter. Flink 2.0 (March 2025) added disaggregated state, which keeps state mainly in remote storage (a distributed file system or object store) with a local cache, so rescaling and recovery no longer need to download the whole state first. In every backend, a state time-to-live removes keys that have not been touched for a set time; without it, a job that tracks per-user state grows with every new user forever.

mistakes: People often think a watermark is a guarantee that all earlier events have arrived. In fact it is an estimate, usually based on how out of order the data has been so far. Events can and do arrive after it. Every pipeline needs an explicit policy for them: drop them, send them to a side output, or accept them for an allowed-lateness period and emit corrections.
People often think "exactly-once" means each record is processed only once. In fact, after a failure the job rewinds to the last checkpoint and processes the replayed records again. What happens exactly once is the effect on checkpointed state and on transactional sinks. Side effects outside that boundary, such as calling an HTTP API or writing to a database without transactions, can still happen twice, so they must be idempotent.
People often think processing-time windows are a simpler choice that gives the same answer. In fact processing-time results depend on when the job runs. If you replay yesterday's data after a bug fix, all of it falls into the windows of the replay time, and the numbers are different. Event-time results are the same on every replay. Processing time is fine for measuring the pipeline itself (records per second), not for business results.
People often think more parallel tasks always fix consumer lag. In fact all events of one key go to one task, so if one advertiser or one device sends 30% of the traffic, that task stays overloaded however many tasks you add. The fix is to split hot keys (add a random suffix, aggregate per suffix, then combine) or pre-aggregate locally before the shuffle. Parallelism of a Kafka source is also limited by the number of partitions.
quiz: What is the difference between event time and processing time, and which one should business windows usually use? || Event time is when the event happened; processing time is when the processor sees it. Business windows should usually use event time, because the results then do not depend on delays, outages or replays.
Why does an operator use the minimum of its input watermarks, and what goes wrong when one Kafka partition is idle? || It can only be sure that event time T has passed when every input has passed T, so it takes the minimum. An idle partition never advances its watermark, which holds the minimum back, and windows never fire until that source is marked idle.
How does a Flink checkpoint give exactly-once output to a transactional Kafka sink? || Barriers flow through the graph and each operator snapshots its state when the barrier has arrived on all inputs. The sink writes output inside a Kafka transaction and commits it only when the checkpoint is complete. After a crash, state and source offsets are restored from the last completed checkpoint, and uncommitted output is aborted, so consumers never see duplicates.
A job uses 1-minute tumbling event-time windows and a watermark 30 seconds behind the largest event time seen. The largest event time so far is 10:05:20. Which windows have fired, and is a click with event time 10:04:10 that arrives now late? || The watermark is 10:04:50, so every window that ends at or before 10:04:50 has fired; the last one is [10:03, 10:04). The click belongs to [10:04, 10:05), which ends at 10:05:00 and is still open, so it is counted normally, not late.
When would you enable unaligned checkpoints, and what do you pay for them? || When sustained backpressure makes aligned checkpoints slow or time out, because barriers wait behind full buffers. Unaligned barriers overtake the buffered records and save them in the checkpoint, so checkpoints finish quickly; the cost is larger checkpoints and more I/O, and the cause of the backpressure still needs fixing.

terms: Write-ahead log (WAL) — the file where a database records every change before applying it, so it can recover after a crash; CDC reads it.
Log sequence number (LSN) — a position in the WAL; it orders changes and serves as the point to resume from.
Logical decoding — PostgreSQL's feature that turns physical WAL records into row-level inserts, updates and deletes.
Replication slot — a server-side bookmark for one consumer; the database keeps all WAL the consumer has not yet confirmed.
Binlog — MySQL's replication log; in ROW format it records the before and after values of every changed row.
Before and after images — the values of a row before and after a change; deletes have only a before image, inserts only an after image.
Snapshot — the initial copy of existing rows, taken so that the stream starts from a complete state.
Tombstone — a Kafka record with a key and a null value, telling log compaction that the key is deleted.
Outbox pattern — writing an event row into an outbox table in the same transaction as the business change, and streaming that table with CDC.
Change data feed — a lakehouse table's own record of row changes between versions, used to update downstream tables incrementally.
how: There are three ways to capture changes, and the comparison shows why the log wins. Query-based capture polls with a query such as WHERE updated_at > last_seen. It is easy, but it misses hard deletes, merges several updates that happen between two polls into one, depends on every writer setting updated_at, and adds query load. Trigger-based capture runs a trigger on every insert, update and delete that copies the change into a shadow table; it sees everything, but every transaction now does an extra write. Log-based capture reads the write-ahead log, which the database writes anyway for crash recovery. The WAL contributes three things: it is complete (every committed change is in it), it is ordered (commit order), and it carries a position (the LSN) that a reader can store and resume from. The price is coupling to an internal format, which is why databases expose decoded interfaces instead of raw log bytes.
In PostgreSQL, WAL records are physical: they describe changes to pages, not rows. With wal_level=logical, the server writes enough extra information for logical decoding, and an output plugin (pgoutput is built in since version 10) turns WAL into row changes for the tables listed in a publication. A replication slot stores the consumer's progress as two positions: restart_lsn, the oldest WAL the slot may still need, and confirmed_flush_lsn, what the consumer has acknowledged. Changes are sent only when their transaction commits, in commit order, so a consumer never sees uncommitted or rolled-back data. Very large transactions are buffered (spilled to disk above logical_decoding_work_mem) until they commit. Since version 13, max_slot_wal_keep_size can cap how much WAL a slot may hold; a slot that passes the cap is invalidated instead of filling the disk. Since version 17, logical slots can be synchronized to a physical standby, so CDC can continue after a failover. MySQL works differently but gives the same result: with binlog_format=ROW and binlog_row_image=FULL, the binlog holds full before and after images, and the connector reads it by registering as a replica; GTIDs (global transaction IDs) give positions that survive a failover to another server.
The snapshot is the delicate part. The classic method reads all rows inside one repeatable-read transaction and then streams from the LSN noted at its start. For a table of 2 TB, that transaction may run for hours, holding back WAL cleanup and making the work impossible to pause. Netflix's DBLog (2020) introduced a watermark method that Debezium adopted as incremental snapshots. The connector reads the table in primary-key chunks (say 10,000 rows) while streaming continues. For each chunk it writes a low-watermark row to a small signalling table, selects the chunk, then writes a high-watermark row. Both writes appear in the log. When the connector meets log events between the two watermarks for keys that are also in the chunk, the log events win and those rows are dropped from the chunk buffer, because they are older. At the high watermark, it emits the remaining chunk rows and moves on. Snapshot rows and live changes interleave correctly, without locks, and the snapshot can be paused, resumed or run again for one table.
The outbox pattern uses the same machinery for deliberate events. The service writes its business change (an order row) and an event row (OrderPlaced, with a stable public schema) to an outbox table in the same local transaction. The transaction makes the two writes atomic, so there is no dual-write problem. CDC streams only the outbox table, and a router (Debezium's outbox event router, for example) sends each row to a topic named after its aggregate type. Consumers depend on the event schema, not on the internal tables.
Row lineage carries the idea one level up, into lakehouse tables. A Delta table with change data feed enabled records row changes with three extra columns: _change_type (insert, update_preimage, update_postimage or delete), _commit_version and _commit_timestamp; a query such as table_changes('orders', 41, 45) returns the changes between two versions. Iceberg v3 row lineage gives each row a _row_id that stays the same across updates and a _last_updated_sequence_number, so an engine can tell which rows changed between snapshots even after compaction has rewritten the files. Each table in a bronze, silver and gold chain can then be a CDC source for the next one, and the whole chain can be updated incrementally instead of recomputed.

mistakes: People often think polling with an updated_at column is a cheap, equal form of CDC. In fact it misses hard deletes and every update that is overwritten between two polls. It can also skip rows for ever: a transaction that sets updated_at = 10:00:00 but commits at 10:00:05 becomes visible after the poller has already moved its cursor past 10:00:03. Log-based capture reads in commit order and has neither problem.
People often think log-based CDC is free for the source database. In fact it has real costs. wal_level=logical adds information to the WAL, and REPLICA IDENTITY FULL logs the whole old row on every update and delete, which can multiply WAL volume for wide tables. Decoding runs on the database server and uses CPU there, and a lagging slot keeps WAL on disk. These costs are usually small, but they must be measured on a busy primary.
People often think that turning on exactly-once settings makes CDC consumers safe from duplicates. Kafka Connect can be configured for exactly-once delivery from source connectors (KIP-618), which removes duplicates inside Kafka. But the consumer's write into a search index, cache or Delta table is a separate system. A consumer that crashes after writing but before committing its offset will apply the same event again. Consumers still need idempotent applies, for example "upsert only if this LSN is newer than the stored one".
People often think a change event tells you what happened in the business. In fact it records what changed in storage. Cancelling one order may update four rows in three tables, and the same status update may mean different things in different code paths. A consumer that rebuilds business meaning from table diffs breaks when the schema is refactored. Use raw CDC to copy data, and an outbox when other teams need to know what happened.
quiz: Name the three ways to capture database changes. Which of them sees deletes and every intermediate update without adding writes to each transaction? || Query-based polling, triggers that copy changes into a shadow table, and log-based capture from the WAL or binlog. Log-based capture sees every committed change, including deletes, and adds no extra write per transaction, because the database writes the log anyway.
How does an incremental snapshot avoid missing or duplicating changes that happen while a table is being copied? || For each primary-key chunk, the connector writes a low watermark to the log, reads the chunk, then writes a high watermark. Log events for the same keys that appear between the two watermarks are newer, so those rows are dropped from the chunk buffer, and the remaining chunk rows are emitted at the high watermark.
Why does a stopped CDC consumer make PostgreSQL's disk fill up, and what setting limits the damage? || The replication slot's restart_lsn stops advancing, so the server must keep all WAL written after it. max_slot_wal_keep_size caps that WAL; when the cap is passed the slot is invalidated, the disk is safe, and the connector must take a new snapshot.
A database writes 20 GB of WAL per day and has 60 GB of free disk. The CDC connector stops on Friday at 18:00 and nobody notices. When does the disk fill, and what would max_slot_wal_keep_size = 40GB change? || 60 / 20 = 3 days, so the disk fills around Monday 18:00 and the database stops accepting writes. With a 40 GB cap, the slot is invalidated after about 2 days (Sunday 18:00), the database keeps running, and the cost moves to the consumer, which must re-snapshot.
Should a team publish events for other teams by streaming its raw tables or by using an outbox? || Raw table CDC needs no application code and captures everything, but it couples consumers to the internal schema. An outbox costs some code and an extra insert per transaction, but gives a stable, deliberate contract that is still atomic with the business write. Use raw CDC for internal copies (analytics, search, caches) and an outbox for cross-team events.

@@+ lakehouse
terms: Table format — a specification (Delta Lake, Iceberg, Hudi) for which files make up a table and how its versions change.
Transaction log — the ordered list of commits (Delta's _delta_log, Iceberg's chain of metadata files) that defines every table version.
Snapshot — one version of the table: the exact set of data files, plus schema and statistics, at one commit.
Catalog — the service that maps a table name to its current metadata and, for Iceberg REST catalogs, performs the atomic commit.
Optimistic concurrency — writers work without locks and check for conflicts only at commit time, retrying if someone else committed first.
Copy-on-write — an update rewrites every data file that contains a changed row.
Merge-on-read — an update writes small delete records and new rows, and readers combine them with the old files.
Deletion vector — a compressed bitmap of row positions in one data file that are marked as deleted.
Data skipping — using per-file statistics (minimum, maximum, null count) to avoid reading files that cannot match a filter.
Field ID — a permanent number for each column in Iceberg, so a column keeps its identity when it is renamed or moved.
how: Conflict checking is what makes optimistic commits correct. Suppose a Delta writer read version 41 and, when it tries to commit, finds that versions 42 and 43 already exist. It does not rewrite its data. It reads the actions in 42 and 43 and asks whether they change what it read. Under the default WriteSerializable level, a pure append never conflicts with anything. A MERGE or DELETE conflicts if a concurrent commit removed a file it read, or added new files in a partition it scanned, because those rows might have matched its condition. If there is no conflict, it simply tries again as version 44, and only the small log entry is written again. Iceberg does the same at the catalog: a commit is a compare-and-swap of the table's metadata pointer from snapshot S to S′; if the pointer has moved, the writer re-applies its changes to the new metadata, validates them, and swaps again.
Schema evolution works because metadata, not file layout, defines the columns. Iceberg gives every column a field ID that never changes, and Parquet files store those IDs. Renaming a column only changes its name in the metadata; old files still map by ID. Adding a column creates a new ID, and old files return null for it. Dropping a column and later adding one with the same name gives the new column a new ID, so old data does not reappear by accident. Safe type changes (int to long, float to double, wider decimals) are allowed because old values can be read as the new type. Delta first matched columns by name; its column-mapping mode stores a separate physical name for each column, so renames and drops also become metadata-only changes.
Deletion vectors are how merge-on-read stays cheap in practice. A deletion vector is a Roaring bitmap of the deleted row positions in one data file. Delta stores it in a small side file (or inline in the log when it is tiny) and references it from the file's entry in the log. Iceberg v3 stores it as a blob in a Puffin file, and a new deletion vector for a data file must include all of that file's earlier deletes. This replaces the v2 position delete files, which could pile up and slow readers down. An update becomes a deletion vector on the old file plus a new file with the new row versions. The reader loads the bitmap and skips those positions while scanning. Each deletion vector makes reads a little slower, so compaction later rewrites heavily deleted files and drops the bitmaps.
Row lineage adds the last piece for incremental pipelines. Delta row tracking and Iceberg v3 give each row a stable row ID and the version in which it was last changed, and both survive compaction. A downstream job or materialized view can then ask "which rows changed since version 41?" and process only those, instead of comparing whole tables.

mistakes: People often think a lakehouse table is just a folder of Parquet files that any tool can write into. In fact the table is whatever the log or metadata says. A file copied into the folder without a commit is invisible to readers and will be deleted by VACUUM as garbage. Deleting or moving files by hand breaks the table. Every write must go through a client that speaks the table format's protocol.
People often think time travel is a backup. In fact old versions exist only as long as their files are kept. Delta's VACUUM deletes files no longer referenced by versions newer than the retention period (7 days by default), and Iceberg's snapshot expiry does the same. Time travel also lives in the same bucket and catalog as the table, so dropping the table or losing the bucket removes the history too. Real backups need a separate copy.
People often think a lakehouse transaction can cover several tables at once. In fact Delta and Iceberg commit one table at a time. A job that writes orders and then order_items can leave a reader seeing the new orders without their items. Some catalogs now offer multi-table commits (the Iceberg REST catalog API defines one), but most engines and pipelines do not use them, so cross-table consistency usually needs design: write in a safe order, or let readers pin snapshot IDs that a job publishes together.
People often think per-file min/max statistics make filters fast on any column. In fact they help only when values are clustered. If device IDs are spread randomly, every file's minimum and maximum cover almost the whole range, and no file can be skipped. Delta also collects statistics only for the first 32 columns by default. Skipping works on columns that are sorted, clustered or Z-ordered, and on columns whose statistics are collected.
quiz: What two parts make up a lakehouse table, and which part decides what the table contains? || Immutable data files (usually Parquet) and a metadata layer (a transaction log or a tree of metadata files). The metadata decides: a file is part of a version only if a commit added it and no later commit removed it.
How do two writers commit to the same Delta table without a lock server, and when does one of them have to fail? || Each tries to create the next log file with put-if-absent; only one succeeds. The loser reads the winning commit and checks whether it removed files the loser read or added files in partitions it scanned. If not, it retries with the next number; if so, it fails and must re-run its work on the new version.
Why can Iceberg rename a column without rewriting any data files? || Columns are identified by permanent field IDs stored in both the metadata and the Parquet files. A rename changes only the name attached to the ID in the metadata, and readers still find the old data by ID.
A table has 2,000 files of 512 MB. A privacy request deletes one row in each of 300 files. Roughly how much data does copy-on-write rewrite, and what does a deletion-vector delete write? || Copy-on-write reads and rewrites 300 × 512 MB ≈ 150 GB. With deletion vectors, it writes 300 small bitmaps (a few hundred bytes to a few KB each) and one commit; readers skip those rows until a later compaction removes them physically.
A table receives CDC updates every 5 minutes and is read by dashboards all day. Copy-on-write or merge-on-read? || Merge-on-read with deletion vectors, because each small batch of updates would otherwise rewrite many large files. Pair it with scheduled compaction so reads do not slow down as deletion vectors accumulate. Copy-on-write fits tables that change rarely and are read heavily.

@@+ olap
terms: Fact table — the large table of events or measurements (impressions, orders, views), usually billions of rows.
Dimension table — a small table that describes the facts (campaigns, dates, regions) and is joined to them.
Columnar storage — storing all values of one column together, so a query reads only the columns it uses.
Dictionary encoding — replacing repeated values with small integer codes plus a lookup table.
Run-length encoding — storing a repeated value once with its count, such as "KA × 40,000".
Zone map — the minimum and maximum of a column in one block of rows, used to skip blocks that cannot match.
Bitmap index — one bit per row for each value of a column; filters become bitwise AND and OR operations.
Vectorized execution — operators that process a batch of about a thousand values per call instead of one row at a time.
Late materialization — evaluating filters on a few columns first and fetching the other columns only for the rows that pass.
Rollup — a precomputed aggregate at a coarser grain (per day and state instead of per event).
how: Bitmap indexes deserve a closer look, because they turn filters into arithmetic. Pinot and Druid keep, for each value of an indexed column, a bitmap of the rows that have it. Plain bitmaps waste space for rare values, so most engines use Roaring bitmaps. Roaring splits a 32-bit row number into a high 16-bit part, which picks a chunk of 65,536 rows, and a low 16-bit part inside the chunk. Each chunk is stored in whichever container is smallest: a sorted array of 16-bit numbers when it has at most 4,096 rows (at most 8 KB), a plain 65,536-bit bitmap (exactly 8 KB) when it has more, or a list of runs when rows come in long stretches. AND of two bitmap containers is 1,024 operations on 64-bit words; AND of two small arrays is a merge. A filter such as state = 'KA' AND channel = 'ch7' becomes one bitmap of matching rows, and the engine reads other columns only at those positions.
Engines also work on encoded data directly instead of decoding it first. A filter on a dictionary-encoded column looks up the value once in the dictionary, gets code 3, and then compares small integers, often 32 or 64 at a time with SIMD instructions. A SUM over a run-length-encoded column multiplies each value by its run length. This connects to late materialization: the engine first evaluates the filters on a few columns and produces a selection vector, the list of row positions that passed, and only then reads and decodes the other columns at those positions. If the filter keeps 1% of rows, the expensive columns are touched for that 1% only.
There are two main ways to remove the per-row overhead of classic "one row per call" execution (the Volcano model). Vectorized engines, following MonetDB/X100 (later Vectorwise), call each operator on a vector of about 1,000 to 2,000 values, so the cost of the call is spread over many values and the inner loop is simple enough for SIMD and branch prediction. DuckDB, ClickHouse and Velox work this way. Compiling engines, following HyPer (Neumann, 2011), generate machine code for the whole query pipeline, so a row's values stay in CPU registers from scan to aggregate. A 2018 comparison by Kersten and colleagues found that both approaches reach similar speed, with different strengths: compiled code is better for computation-heavy queries, vectorized code for memory-heavy ones and for easier profiling.
Partitioning and zone maps decide how much data is read at all. Data is usually partitioned by time (one partition per day or hour), so a query over 30 days reads 30 partitions and ignores the rest. Inside a partition, rows are sorted by the most common filter columns, and the engine keeps a zone map per block. ClickHouse, for example, keeps a sparse primary index with one entry per granule of 8,192 rows by default, so a table of 10 billion rows needs only about 1.2 million index entries, small enough to stay in memory. Sorting is what makes zone maps useful: on a column sorted by tenant, each block holds one or two tenants and most blocks are skipped; on a random column, every block's range covers everything.

  plan: filter (bitmaps) -> selection vector -> decode only the
        needed columns at those rows -> partial aggregates per

mistakes: People often think SELECT * costs little more than selecting a few columns, as in a row store. In fact a column store reads and decodes each column separately, so asking for 100 columns instead of 3 can read 30 times more data. In BigQuery, on-demand pricing is based on the bytes of the columns a query references, and adding LIMIT does not reduce that for a normal table. Name only the columns you need.
People often think adding an index speeds up an analytical query, as it would in OLTP. In fact a B-tree index helps when a query touches a few rows. A filter that matches 20% of rows touches nearly every block anyway, and random index lookups are slower than one sequential scan. OLAP speed comes from reading fewer columns, skipping blocks through sort order and zone maps, and pruning partitions.
People often add daily distinct counts to get a monthly distinct count. In fact distinct counts do not add: a device seen on 20 days is counted 20 times. Exact monthly uniques need the full set of IDs again. HyperLogLog sketches solve this because two sketches can be merged into the sketch of the union, so daily sketches can be combined into a correct monthly estimate.
People often think more nodes always make a query faster. In fact each query has fixed costs (planning, scheduling, merging partial results at the coordinator), and a large GROUP BY or a join of two large tables needs a shuffle in which every node sends data to every other node. A query that scans 2 GB can be slower on 100 nodes than on 10. Add nodes for large scans and for concurrency, not for small queries.
quiz: Name three column encodings and the kind of data each one suits. || Dictionary encoding suits strings with few distinct values (countries, channels). Run-length encoding suits sorted or repeated values (dates in a date-sorted table). Delta encoding and bit-packing suit sorted numbers such as timestamps and small integers such as minutes watched.
Why is vectorized execution faster than processing one row per operator call? || The cost of each operator call is spread over a thousand or more values. The inner loops are short and regular, so they use SIMD instructions, keep data in the CPU cache and avoid branch mispredictions, while the one-row-per-call model pays a virtual call and branches for every row.
How does a Roaring bitmap choose its representation, and why does that keep AND and OR fast? || It splits row numbers into chunks of 65,536 and stores each chunk as a sorted array (up to 4,096 rows), a full 8 KB bitmap (denser chunks) or a list of runs. Each pair of container types has a specialized algorithm, such as 1,024 word-wide ANDs for two bitmaps or a merge for two arrays, so space stays small and operations stay fast.
A fact table has 2 billion rows and 120 columns, about 480 bytes per row in a row store. A query reads three columns that take 1, 2 and 4 bytes per row after encoding. How much data does a column store scan, and how long does it take at 200 GB/s of total cluster scan speed? || 2 billion × 7 bytes = 14 GB, which takes about 0.07 seconds. A row store would read about 2 billion × 480 bytes = 960 GB, nearly 70 times more.
When should you build a rollup or pre-aggregated table instead of querying raw events? || When a query is both frequent and expensive and its dimensions are stable, such as a dashboard that groups by day and state every minute. The rollup costs storage, refresh work and freshness, and it cannot answer questions about dimensions it dropped, so ad hoc analysis should still use the raw table.

@@+ coordination
terms: Ensemble — the small set of servers (usually 3 or 5) that run the coordination service and vote on every write.
Quorum — a majority of the voting servers; a write is committed once a quorum has stored it.
Leader — the one server that orders all writes; the others are followers that copy its log.
Term or epoch — a number that increases with every new leader, so messages from an old leader can be recognized and ignored.
Znode — a node in ZooKeeper's tree of small data items, addressed by a path such as /kafka/brokers/3.
Ephemeral node — a znode that is deleted automatically when the session of the client that created it ends.
Lease — etcd's time-limited grant; keys attached to it are deleted when the client stops renewing it.
Watch — a subscription that notifies a client when a key or znode changes, so it does not need to poll.
Revision — etcd's global counter that increases with every write; each key version carries one, and it can serve as a fencing token.
Linearizable read — a read that is guaranteed to see every write committed before the read started.
how: Follow one write through etcd, which uses Raft. The client sends put /config/flags to the leader. The leader appends the entry to its log under its current term, writes it to disk with fsync, and sends it to the followers in an AppendEntries message. Each follower writes the entry to its own log, fsyncs, and replies. As soon as a majority has the entry (2 of 3, or 3 of 5, counting the leader), the leader marks it committed, applies it to its key-value store (etcd keeps keys in the bbolt B-tree, with every version tagged by a revision), and answers the client. The commit latency is therefore one network round trip to the fastest majority plus one fsync: on a local network with good SSDs, roughly 2 to 10 ms. ZooKeeper's Zab protocol follows the same shape: the leader proposes a change tagged with a zxid (epoch plus counter), followers log it and acknowledge, and the leader commits after a quorum.
Quorums are what make leader changes safe. Any two majorities of the same ensemble share at least one server. A Raft candidate can only win an election if its log is at least as up to date as the logs of a majority of voters, so every committed entry is held by at least one voter, and the new leader is guaranteed to have it. This is also why clusters have an odd size. Three servers survive one failure; four servers also survive only one, because a majority of four is three, and every write then needs one more acknowledgement for no extra safety.
Reads have their own rules, and this is where consistency models matter. ZooKeeper answers reads from the memory of whichever server the client is connected to. Each client sees its own writes in order, but a follower can be slightly behind the leader; a client that needs the latest value calls sync() first, which makes its server catch up. etcd's default read is linearizable through a technique called ReadIndex: the leader notes its current commit index, confirms with one heartbeat round that a majority still accepts it as leader, waits until it has applied entries up to that index, and then answers from local state. Nothing is written to the log. A serializable read (an option in etcd) skips that round and answers from the local copy, faster but possibly stale.
Failure detection works at two levels. Inside the ensemble, the leader sends heartbeats; in etcd the defaults are a 100 ms heartbeat interval and a 1,000 ms election timeout, after which a follower that has heard nothing starts an election. For clients, ZooKeeper keeps a session with a timeout (by default it must lie between 2 and 20 ticks; the sample configuration sets one tick to 2 seconds). If the ensemble hears nothing from a client for that long, it expires the session and deletes all of the client's ephemeral nodes in one step, which fires the watches of everyone waiting on them. etcd does the same with leases: a client renews its lease with KeepAlive messages, and when the time-to-live runs out, every key attached to the lease disappears.
The CAP and PACELC trade-offs are visible in this design. During a network partition, the side with a majority keeps committing; the minority side cannot reach a quorum, so it refuses writes and linearizable reads. The service chooses consistency over availability. Even with no partition, every write waits for a majority round trip and an fsync, which is the "else latency" part of PACELC. An ensemble spread across three regions pays tens of milliseconds for every write.
Watches and versioned history make the service useful for building controllers. ZooKeeper watches were originally one-shot: after one notification the client must register again, and persistent watches arrived in version 3.6. etcd keeps the history of every key by revision, so a client can say "send me every change after revision 1,205" and receive them all in order, as long as that history has not been compacted. Kubernetes controllers rely on this: they list objects at revision R and then watch from R + 1, so no change is missed. Recipes combine these pieces. In ZooKeeper leader election, each candidate creates an ephemeral sequential node such as /election/n_0000000042; the lowest number is the leader, and every other candidate watches only the node just before its own. When the leader dies, only one candidate is notified, which avoids a "herd" of clients all reacting at once.

mistakes: People often think a coordination service scales like a normal database: add servers, get more capacity. In fact every write goes through one leader and must reach a majority, so more voters make writes slower; seven voters need four acknowledgements. Read capacity can be added with non-voting members (ZooKeeper observers, etcd learners), but write throughput stays bounded by one leader, on the order of tens of thousands of small writes per second for etcd.
People often think two servers are safer than one, or that an even number adds safety. In fact a two-server ensemble needs both servers for a majority, so losing either one stops all writes; it is less available than a single server. Four servers tolerate one failure, exactly like three. Use 3 or 5 voters.
People often think a watch delivers every change. In ZooKeeper, a classic watch is a one-time signal to re-read: if a value changes three times before the client registers again, the client sees only the latest value. In etcd, a watch that starts from a revision that has already been compacted fails, and the client must list the current state again. Treat watches as "something changed, look again", not as a complete change log, unless you watch from a stored revision.
People often think any read from the service shows the latest committed value. In fact ZooKeeper reads and etcd serializable reads come from one server's local copy, which can lag. A client that reads from one server right after another client wrote through a different server can see the old value. When a decision depends on the latest value, use a linearizable read, call sync(), or compare the version you expect.
quiz: Which primitives does a coordination service offer that leader election and locks are built from? || Linearizable writes with compare-and-swap (create only if absent, or only if the version matches), ephemeral nodes or leases that disappear when a client dies, watches that notify waiting clients, and sequence numbers or revisions that order candidates and serve as fencing tokens.
Why does a five-server ensemble survive two failures, while a four-server ensemble survives only one? || A write needs a majority. The majority of five is three, so two servers can fail and three can still commit. The majority of four is also three, so only one server can fail.
How does etcd serve a linearizable read without writing anything to its log? || With ReadIndex: the leader records its current commit index, confirms with one heartbeat round that a majority still accepts it as leader, waits until it has applied entries up to that index, and then answers from its local state.
An etcd cluster uses a 100 ms heartbeat and a 1,000 ms election timeout. A client holds a 10-second lease and renews it every 3 seconds. How long until a new etcd leader exists after the leader server crashes, and how long until the client's key is deleted after the client process crashes? || A new leader is usually elected about 1 to 2 seconds after the crash: the election timeout, a short random delay and one voting round. The client's lease expires 10 seconds after its last renewal, so the key disappears 7 to 10 seconds after the client crashes.
When should a client use linearizable reads, and when are follower or serializable reads good enough? || Use linearizable reads for decisions that must not act on old data, such as "am I still the leader?" or "is this lock free?". Use follower or serializable reads for high-volume reads that tolerate a little staleness, such as service-discovery lists or configuration shown in a UI, because they avoid the leader round trip and scale with the number of servers.

@@+ cachelayer
terms: Hit rate — the fraction of requests answered by the cache; the miss rate (1 minus hit rate) is the fraction that reaches the backend.
Cache-aside — the application reads the cache, and on a miss reads the database and stores the result in the cache itself.
Time-to-live (TTL) — how long an entry may stay in the cache before it expires and must be fetched again.
Invalidation — deleting or updating a cached entry because the data behind it has changed.
Eviction — removing entries when memory is full, chosen by a policy such as LRU (least recently used) or LFU (least frequently used).
Thundering herd — many requests missing on the same key at the same moment and all hitting the backend together.
Request coalescing — letting only one request rebuild a missing entry while the others wait for its result (also called single flight).
Consistent hashing — a way to assign keys to cache nodes so that adding or removing a node moves only a small share of the keys.
Hot key — one key that receives a large share of all traffic, so the node holding it can be overloaded.
Lease — a token the cache gives to the client that missed; the client's later write is accepted only if the token is still valid.
how: Skew is the reason a small cache works, and the power-law model makes this precise. If popularity follows a Zipf law with exponent near 1, the key of rank r gets traffic proportional to 1/r. A cache holding the top C of N keys then has a hit rate of about H(C) / H(N), where H(n) ≈ ln n + 0.58. For N = 100 million keys, caching the top 1 million (1% of keys) gives (13.8 + 0.58) / (18.4 + 0.58) ≈ 76% hits; caching the top 10 million (10%) gives about 88%. Ten times the memory buys 12 more points of hit rate, but it halves the misses, from 24% to 12%, and so halves the backend load. Real traces are not perfect Zipf, so teams measure a miss-ratio curve (miss rate as a function of cache size) from their own key logs before choosing a size.
The eviction policy decides which keys stay. Exact LRU uses a hash map plus a doubly linked list: each hit moves the entry to the front, and the entry at the back is evicted. That is O(1), but it costs two pointers per entry and a write to shared memory on every read. Redis approximates LRU instead: each key stores a 24-bit clock of its last access, and when memory is full Redis samples a few keys (maxmemory-samples, default 5), keeps the best candidates in a small pool, and evicts the oldest. Its LFU mode keeps an 8-bit logarithmic counter per key that is incremented with a probability that falls as the counter grows, and decays over time. Pure LRU has a known weakness: one scan over many cold keys pushes out the hot ones. TinyLFU (used in Java's Caffeine library) keeps a compact frequency sketch and admits a new key only if it looks more popular than the key it would evict. S3-FIFO puts new keys into a small FIFO queue first, so keys that are used only once leave quickly.
Consistent hashing decides where each key lives. With simple modulo hashing (server = hash(key) mod N), going from 8 to 9 servers moves about 8 of every 9 keys, which empties the cache at once. Consistent hashing places each server at many points on a ring of hash values (virtual nodes, often 100 to 200 per server). A key belongs to the first server point clockwise from the key's own hash. A new server takes over only the ring segments just before its points, about 1/(n + 1) of all keys, and every other key stays where it was. Memcached clients commonly use this scheme (the ketama algorithm). Redis Cluster uses a related idea with fixed slots: a key belongs to slot CRC16(key) mod 16,384, slots are assigned to nodes, and rebalancing moves whole slots. Hash tags, such as {user42} inside a key name, put related keys in the same slot.
The event loop explains why one cache node is fast and also how it can stall. Redis runs commands on a single thread. An event loop (epoll on Linux) waits until sockets are ready, reads a command, executes it in memory, often in well under a microsecond, and queues the reply. No locks are needed, and each command is atomic, which is why INCR or a Lua script can be used as a safe counter or small transaction. One instance serves on the order of 100,000 simple operations per second, and more with pipelining. Since Redis 6, extra I/O threads can read and write network data in parallel, but commands still execute one at a time. The cost is that one slow command blocks every client: KEYS * over 50 million keys, or deleting one huge hash, can freeze the node for seconds. SCAN and UNLINK exist for exactly this reason. Memcached instead runs several worker threads, each with its own event loop, so one instance uses many cores.
Consistency needs care because cache and database are updated in two separate steps. The classic race: reader A misses and reads value v1 from the database; writer B updates the row to v2 and deletes the cache key; then A stores v1 in the cache, where it stays until the TTL ends. Facebook's memcache fixed this with leases. On a miss, the cache gives the client a lease token; a delete of that key invalidates the token; and a later set with an invalid token is rejected. The same tokens limit thundering herds: the cache hands out at most one token per key every 10 seconds, and other clients that miss wait briefly and retry, by which time the value is usually there.

mistakes: People often think that updating the cache on every write is better than deleting the entry. In fact two concurrent writers can commit to the database in one order and set the cache in the other order, leaving the older value cached until the TTL ends. Deleting the key on write is safe whatever the order, because the next reader fetches the committed value, and it avoids computing entries that nobody will read.
People often think that doubling the cache doubles the hit rate. In fact, with skewed traffic, the hit rate grows roughly with the logarithm of the cache size: the first few percent of keys capture most requests, and each further doubling adds only a few points. Those points can still matter, because the backend sees the misses, but the decision should come from a measured miss-ratio curve, not from a guess.
People often think LRU is the natural, best eviction policy. In fact LRU is easily flushed by scans and by keys used only once, which are common in real traffic (crawlers, batch jobs, long-tail users). Policies that also use frequency, such as TinyLFU, or that filter new keys, such as S3-FIFO, reach higher hit rates on many production traces with the same memory.
People often think a cache cluster spreads load evenly across its nodes. In fact each key lives on one node, so a single hot key (a viral post, a celebrity profile) can send hundreds of thousands of requests per second to one machine while the others are idle. Fixes include a small in-process cache with a short TTL for the hottest keys, or several copies of a hot key under different suffixes spread across nodes.

Write: update the database, then delete the cache entry so the next read fetches the new value.
Why does consistent hashing move only about 1/(n + 1) of the keys when a server is added, while modulo hashing moves most of them? || With modulo hashing, changing N changes hash(key) mod N for almost every key. With consistent hashing, a key's owner is the next server point on a fixed ring; a new server only takes the ring segments just before its own points, so only the keys in those segments move.
How do memcache leases prevent both stale sets and thundering herds? || On a miss, the client receives a lease token, and a delete of the key invalidates the token, so a set carrying an old token is rejected and cannot store stale data. Because the cache issues at most one token per key every few seconds, only one client rebuilds a hot key while the others wait and retry.
A service has 100 million keys with Zipf-like popularity and 200,000 requests per second. Caching the top 1% of keys gives about 76% hits; caching the top 10% gives about 88%. How many requests per second reach the database in each case? || With 1%: 24% of 200,000 = 48,000 per second. With 10%: 12% of 200,000 = 24,000 per second, half the load, for ten times the memory.
When would you add an in-process near cache in front of a shared Redis cache, and what does it cost? || When a few hot keys dominate traffic or network latency matters: a local lookup takes well under a microsecond instead of a few hundred microseconds over the network, and hot keys no longer overload one Redis node. The cost is memory duplicated in every instance and harder invalidation, so instances can disagree; keep near caches small, with short TTLs, and only for data that tolerates brief staleness.

@@+ dl
terms: Layer — one step of the network: a linear transformation (multiply by a weight matrix, add a bias) followed by a non-linear function such as ReLU.
Activation — the output of a layer for one input; activations are kept during the forward pass because the backward pass needs them.
Loss — a single number that measures how wrong the outputs are, such as cross-entropy for classification.
Gradient — for every weight, how much the loss would change if that weight changed a little; training moves weights against it.
Backpropagation — computing all gradients in one backward pass through the network, using the chain rule.
Optimizer — the rule that turns gradients into weight updates, such as SGD with momentum or AdamW.
Epoch — one full pass over the training data; a step is one update on one mini-batch.
Residual connection — adding a layer's input to its output (x + f(x)), so signals and gradients can skip the layer.
Mixed precision — doing most arithmetic in 16-bit or 8-bit formats while keeping a 32-bit master copy of the weights.
Overfitting — when a model fits the training data better and better but gets worse on new data.
how: Backpropagation is the chain rule applied in a smart order, and automatic differentiation is what makes it routine. During the forward pass, the framework (PyTorch, JAX) records each operation and keeps the intermediate values it will need. The backward pass walks that record in reverse. Each operation receives the gradient of the loss with respect to its output and turns it into gradients for its inputs and its weights. Because there is one scalar loss and many weights, this reverse mode costs only about twice the forward pass, however many weights there are. A useful rule of thumb follows: training costs about 6 × parameters × training tokens (or examples) floating-point operations, 2 for the forward pass and 4 for the backward pass. The stored activations are often the largest memory cost, so large models use activation checkpointing: they keep only some activations and recompute the rest during the backward pass.
Depth used to be the problem, and two lower concepts fixed it. The gradient that reaches an early layer is a product of one factor per later layer. If each factor is about 0.9, after 50 layers the gradient is 0.9⁵⁰ ≈ 0.005 of its size (vanishing gradients); if each is 1.1, it is 1.1⁵⁰ ≈ 117 times larger (exploding gradients). Residual connections compute x + f(x), so each factor becomes "identity plus something", and there is always a direct path for the gradient back to the input. Normalization layers rescale activations to mean 0 and variance 1: batch normalization over the examples in a batch, layer normalization (or RMSNorm in most transformers) over the features of each example. Every layer then sees inputs in a stable range, and one learning rate works for all layers. Careful initialization (He or Xavier) does the same job at the start of training.
Convolution shows how architecture encodes knowledge about the data. A 3×3 convolution with 64 input and 64 output channels has 3 × 3 × 64 × 64 = 36,864 weights, whatever the image size, because the same small filter slides over every position. A fully connected layer between two 224 × 224 × 64 feature maps would need about 10¹³ weights. Weight sharing builds in the fact that a cat is a cat wherever it appears in the image, so the network needs far fewer weights and far less data.
Mixed precision is where hardware meets numerics. GPU tensor cores multiply 16-bit (FP16, BF16) or 8-bit (FP8) matrices many times faster than 32-bit ones. BF16 keeps FP32's 8 exponent bits, so it has the same range and training rarely needs extra tricks. FP16 has only 5 exponent bits, so small gradients can underflow to zero, and training multiplies the loss by a large factor (loss scaling) to keep them representable. A 32-bit master copy of the weights is kept so that tiny updates are not rounded away. With Adam, each parameter then costs about 16 bytes: 2 for BF16 weights, 2 for gradients, 4 for the master weights and 8 for Adam's two moment estimates. A 7-billion-parameter model needs about 112 GB for this state alone, more than one 80 GB GPU, before any activations.
Parallelism and all-reduce spread the work over many GPUs. In data parallelism, every GPU holds the model, processes a different slice of the batch and computes its own gradients; an all-reduce then averages the gradients so all copies stay identical. Ring all-reduce sends about 2 × (N − 1)/N times the gradient size per GPU, which is almost independent of the number of GPUs N, and frameworks overlap it with the backward pass. Sharded data parallelism (ZeRO, PyTorch FSDP) splits weights, gradients and optimizer state across GPUs and gathers each layer's weights just before it is used. Tensor parallelism splits each large matrix multiplication across the GPUs of one server, which needs fast NVLink connections because they talk in every layer. Pipeline parallelism puts groups of layers on different GPUs and streams small micro-batches through them.
The same machinery trains generative models; only the loss changes. Variational autoencoders train an encoder and a decoder to maximize a lower bound on the probability of the data. Normalizing flows build the network from invertible layers so the exact probability can be computed. GANs train a generator against a discriminator that tries to tell real from generated samples. Diffusion models learn to remove noise step by step. Underneath all of them is still the unit described by McCulloch and Pitts in 1943, a weighted sum followed by a non-linearity, with the hard threshold replaced by smooth functions such as ReLU so that gradients exist. Biology contributed the idea that learning means changing connection strengths; backpropagation itself has no clear counterpart in the brain.

mistakes: People often think artificial neural networks are simplified brains that learn the way brains do. In fact real neurons send timed spikes, compute inside their dendrites and change connections by local rules. No known biological mechanism sends a precise error signal backwards through every layer, as backpropagation does. The brain inspired the field, but the working parts are linear algebra, calculus and optimization.
People often think a network with more parameters than training examples must overfit. In fact very large networks trained with stochastic gradient descent often generalize better than smaller ones, a pattern studied as "double descent" (Belkin and colleagues, 2019; Nakkiran and colleagues, 2019). The classic U-shaped bias–variance picture does not describe them well. Overfitting is still real, as the training curves in the example show, so validation data remains essential.
People often read a classifier's output probabilities as calibrated confidence. In fact modern deep networks are often overconfident: among predictions made with 95% confidence, noticeably fewer than 95% may be right (Guo and colleagues, 2017). If decisions depend on the probability, as with fraud thresholds or bid prices, calibrate on held-out data, for example with temperature scaling, and check reliability per segment.
People often think GPUs make training fast simply because they do arithmetic fast. In fact many steps are limited by memory bandwidth (normalization, activation functions, attention over long sequences) or by the data pipeline feeding the GPU. Even well-tuned large training runs use only about 40 to 50% of the GPU's peak arithmetic; PaLM reported 46%. Larger batches, fused kernels and fast data loading usually matter more than the choice of optimizer.

The backward pass costs about twice the forward pass, so a full training step costs about three forward passes.
Why do residual connections allow networks with more than 100 layers to train? || Each block computes x + f(x), so the gradient through the block is the identity plus the gradient of f. terms: Token — a piece of text (often part of a word) that the model reads and writes; English averages roughly 4 characters per token.
Embedding — the learned vector that represents a token at the input of the model.
Self-attention — the step in which each token compares its query with the keys of earlier tokens and takes a weighted mix of their values.
KV cache — the stored keys and values of all earlier tokens, kept so each new token does not recompute them.
Context window — the maximum number of tokens (prompt plus output) the model can attend to at once.
Mixture of experts (MoE) — a feed-forward layer made of many expert networks, of which a router picks only a few for each token.
Pretraining — training on trillions of tokens of general text to predict the next token.
Post-training — the later stages (supervised fine-tuning and reinforcement learning from feedback) that turn a text predictor into an assistant.
Logits — the raw scores the model outputs for every token in the vocabulary; softmax turns them into probabilities.
Temperature — a number that divides the logits before softmax; lower values make sampling more predictable, higher values more varied.
how: The KV cache is where model design meets memory. Its size per token is 2 (keys and values) × layers × key/value heads × head dimension × bytes per number. For a Llama-3-70B-style model (80 layers, 8 key/value heads of dimension 128, 16-bit numbers) that is 2 × 80 × 8 × 128 × 2 = 327,680 bytes, about 320 KB per token, so one 128,000-token context needs about 42 GB. With classic multi-head attention, where all 64 query heads have their own keys and values, it would be 8 times more. Grouped-query attention lets each group of 8 query heads share one key/value head, with little loss of quality, which is why almost every recent model uses it. FlashAttention attacks the other cost of attention: the standard method writes the full table of token-to-token scores to GPU memory, which grows with the square of the sequence length. FlashAttention computes attention in tiles that stay in fast on-chip memory, keeping a running softmax, and never stores the full table. The result is exactly the same, but memory traffic falls sharply and long contexts become affordable. RoPE fits into the same step: it rotates pairs of dimensions in each query and key by an angle proportional to the token's position, so their dot product depends only on how far apart the two tokens are.
Mixture of experts separates what a model knows from what each token costs. DeepSeek-V3, for example, has 671 billion parameters, but for each token a router selects 8 of its 256 routed experts (plus one shared expert), so only about 37 billion parameters are used per token. The compute per token is like that of a 37-billion-parameter dense model, while the memory needed to hold the weights is that of a 671-billion-parameter one. This is why MoE models are cheap per token but still need many GPUs to serve.
Several lower concepts adapt a trained model without training it again. LoRA freezes the original weights and learns a low-rank update for selected matrices: instead of changing a 4,096 × 4,096 matrix (16.8 million numbers), it trains two thin matrices of 4,096 × 16 and 16 × 4,096, about 131,000 numbers, under 1% of the size, and many such adapters can share one base model. Distillation trains a small model to match the output probabilities of a large one, which carries more information per example than the correct answer alone. Quantization stores weights in 8 or 4 bits instead of 16, halving or quartering memory, usually with a small and measurable quality loss.
Two more lower concepts decide whether we can trust what comes out. Evaluation measures behaviour on benchmarks and task suites; its main danger is contamination, when test questions leak into the training data and scores rise without real ability. Interpretability looks inside the model: methods such as sparse autoencoders decompose the activations of a layer into many more readable "features" (Anthropic reported millions of them in a production model in 2024), some of which can be switched up or down to change behaviour. Both are still young sciences compared with the training methods they examine.

mistakes: People often think the model reads words or letters. In fact it reads tokens from a fixed vocabulary of subword pieces. That is why it can miscount the letters in a word it sees as two tokens, why arithmetic on long numbers is harder than it looks, and why many non-English languages cost more tokens than English for the same meaning, which raises their price and fills the context faster.
People often think temperature 0 makes outputs fully repeatable. Temperature 0 means always picking the most likely token, but the logits themselves can differ slightly between runs, because GPU floating-point sums depend on how requests are batched together. When two tokens are nearly tied, a tiny difference changes the choice, and the rest of the answer follows a different path. Repeatability needs deterministic kernels or caching of answers, not just a setting.
People often compare models by parameter count alone. In fact capability depends heavily on training data and compute: the Chinchilla work (2022) showed that a 70-billion-parameter model trained on 1.4 trillion tokens beat the 280-billion-parameter Gopher. For MoE models, the total parameter count says what memory you need, while the active count says what each token costs. Compare models on your own evaluations.
People often treat the chain of thought that a reasoning model shows as a faithful record of how it reached its answer. In fact research has found that models sometimes reach answers for reasons they do not mention, such as a hint planted in the prompt (Turpin and colleagues, 2023; Anthropic, 2025). The written reasoning helps the model, and it is useful evidence for people, but it is not a guaranteed explanation.

terms: Prefill — processing the whole prompt in one parallel pass to build its KV cache and produce the first output token.
Decode — generating output tokens one at a time, each step reading all the weights and the request's KV cache.
Time to first token (TTFT) — the delay from sending a request to receiving the first output token; set mainly by queueing and prefill.
Inter-token latency — the time between two output tokens of one request; set by the decode step time.
Arithmetic intensity — the number of arithmetic operations done per byte read from memory; low intensity means memory speed is the limit.
Continuous batching — letting requests join and leave the running batch after every decode step.
PagedAttention — storing the KV cache in fixed-size blocks mapped by a per-request block table, like virtual memory pages.
Prefix caching — reusing the KV blocks of a prompt prefix (system prompt, document, chat history) that an earlier request already computed.
Speculative decoding — a cheap draft model proposes several tokens and the large model checks them all in one pass.
Goodput — the rate of requests that complete within their latency targets, as opposed to raw tokens per second.
how: The numbers show why decode is memory-bound. To generate one token, the GPU reads every weight once and does about two operations per weight. For a model with 8 billion parameters in 16-bit numbers, that is 16 GB read for about 16 billion operations: roughly one operation per byte. A modern data-center GPU such as the H100 offers roughly 1,000 trillion 16-bit operations per second but about 3.35 TB/s of memory bandwidth, a ratio of about 300 operations per byte. At batch size 1, the arithmetic units are therefore idle more than 99% of the time, and each decode step takes at least 16 GB ÷ 3.35 TB/s ≈ 5 ms, which caps a single user at about 200 tokens per second. A batch of 64 requests reads the same weights once per step and does 64 times the useful work, so the step time grows only a little (each request still reads its own KV cache). Batching is the main lever, and KV-cache memory is what limits the batch size.
PagedAttention removes most of the waste in that memory. Earlier servers reserved one contiguous KV region per request, sized for the longest possible output, and the vLLM paper measured that they used only about 20 to 40% of their KV memory for real tokens. vLLM instead divides KV memory into blocks of 16 tokens. Each request has a block table that maps its logical blocks to physical blocks, exactly like an operating-system page table, and blocks are allocated only when tokens arrive, so waste is limited to the last, partly filled block. Blocks can also be shared: several samples from the same prompt point to the same prefix blocks, with a reference count, and a block is copied only when one of them writes something different (copy-on-write).
Continuous batching, introduced by Orca as iteration-level scheduling, fixes the scheduling side. With static batching, a batch where one request writes 2,000 tokens and the others write 50 keeps the finished requests' slots empty for 1,950 steps. With continuous batching, the scheduler looks at the batch after every step: finished requests leave, and waiting requests join at once. Prefix caching builds on the paged layout. vLLM identifies each full block by a hash of its tokens together with all tokens before it, so two requests that start with the same 2,000-token system prompt map to the same blocks, and the second request skips that part of prefill. SGLang's RadixAttention keeps cached prefixes in a radix tree (a tree of shared token sequences) and evicts the least recently used branches.
Long prompts are handled by changing how prefill is scheduled. A 30,000-token prefill can take hundreds of milliseconds, and in a naive server every decoding user waits during that time. Chunked prefill splits the prompt into chunks (for example 512 to 2,048 tokens) and runs one chunk in each step together with the ongoing decodes, so inter-token latency stays steady (the idea behind Sarathi-Serve). Disaggregated serving goes further: prefill runs on one pool of GPUs and decode on another, and the KV cache is sent between them over a fast network (DistServe, Mooncake). Each pool can then be sized and tuned for its own bottleneck: arithmetic for prefill, memory bandwidth and capacity for decode.
Speculative decoding uses the spare arithmetic of memory-bound decode. A small draft model (or extra prediction heads on the main model) proposes k tokens. The large model checks all k in one forward pass, which costs about the same as generating one token, because the weights are read once. A rejection-sampling rule accepts each draft token with a probability that keeps the output distribution exactly the same as the large model's own, and the first rejected token is replaced by a correct sample. If each draft token is accepted with probability α, one pass yields on average (1 − α^(k+1)) ÷ (1 − α) tokens: for α = 0.8 and k = 4, about 3.4 tokens instead of 1. The gain shrinks at large batch sizes, where the arithmetic units are already busy.
Quantization helps decode most directly, because decode time is the time to read the weights. Weight-only 4-bit formats (GPTQ, AWQ) read 4 times fewer bytes than 16-bit weights. FP8 for both weights and activations also uses the FP8 tensor cores of recent GPUs, which speeds up prefill. An FP8 KV cache halves cache memory, which doubles the possible batch size or context length for the same GPU.

mistakes: People often think a GPU that shows 100% utilization is fully used. In fact the utilization number in tools such as nvidia-smi is the share of time in which any kernel is running, not the share of arithmetic capacity used. A batch-1 decode can show close to 100% while using under 1% of the GPU's arithmetic. Measure tokens per second, the achieved memory bandwidth and the arithmetic actually used.
People often think speculative decoding is an approximation, like quantization. In fact its acceptance rule keeps the output distribution identical to the large model's; only floating-point details differ. Its real cost is wasted work when drafts are rejected, so it pays off at small and medium batch sizes and can slow a fully loaded server.
People often think a long prompt simply costs proportionally more. In fact a 100,000-token request occupies as much KV memory as 100 requests of 1,000 tokens, which shrinks the batch for everyone on that GPU, and the attention part of its prefill grows with the square of its length. Long-context traffic raises the cost per token of all requests on the server, which is why some providers price long prompts higher.
People often think that spreading a model over twice as many GPUs with tensor parallelism halves latency. In fact tensor parallelism adds an all-reduce in every layer, so going from 4 to 8 GPUs gives clearly less than twice the speed, and for a model that fits on one GPU it can make things slower. To serve more users, add replicas; use tensor parallelism when the model or its KV cache does not fit, or when one request must be faster.

terms: Chunk — a piece of a document (often 300 to 800 tokens) that is indexed, retrieved and placed in the prompt as one unit.
Embedding model — a model that turns a text into a vector so that texts with similar meaning get nearby vectors.
Bi-encoder — an embedding setup in which the question and each passage are encoded separately, so passage vectors can be computed in advance.
Cross-encoder — a model that reads the question and one passage together and outputs a relevance score; accurate but slow, so used for re-ranking.
BM25 — a keyword ranking formula that scores passages by how often they contain the query's words, weighted by how rare those words are.
Hybrid search — running vector search and keyword search together and merging their results.
Reciprocal rank fusion (RRF) — a merge method that scores each result by the sum of 1 / (k + rank) over the lists it appears in.
Recall at k — the fraction of questions for which a passage that contains the answer appears in the top k results.
Faithfulness — whether every claim in the answer is supported by the retrieved passages.
Context window — the token budget of the prompt, which the instructions, the passages and the question must share.
how: Embeddings carry meaning, and the way they are trained explains both their strength and their limit. A bi-encoder is trained contrastively. For each pair of a question and its correct passage in a training batch, the loss pushes their vectors closer and pushes the question away from the other passages in the same batch (an InfoNCE loss with in-batch negatives, as in DPR). Because each passage is encoded without seeing the question, all 500,000 chunk vectors can be computed once at indexing time; at query time only the question is embedded, in a few milliseconds. The limit is that one vector must summarize a whole chunk. A specific number, a rare product code or a negation ("not supported in the EU") can be lost in it.
BM25 covers that gap. Its score for a passage sums, over the query terms, IDF(t) × tf × (k1 + 1) ÷ (tf + k1 × (1 − b + b × length ÷ average length)), where tf is how often the term appears in the passage. IDF (inverse document frequency) makes rare terms count much more than common ones; k1 (often 1.2) makes repeated occurrences count less and less; b (often 0.75) stops long passages from winning only because they are long. A query that contains "ERR_4031" or "Datastream" therefore ranks the few passages that contain that exact string at the top, which an embedding may not do. The scores come from an inverted index: for each term, a list of the passages that contain it.
The two result lists are merged with reciprocal rank fusion. Each passage gets the score Σ 1 ÷ (60 + rank) over the lists in which it appears; k = 60 comes from the original 2009 paper by Cormack, Clarke and Büttcher. RRF uses only ranks, so it never has to compare a BM25 score with a cosine similarity, which are on unrelated scales. It rewards agreement: a passage ranked 3rd in both lists scores 2 ÷ 63 ≈ 0.032 and beats one ranked 1st in one list and 10th in the other (1 ÷ 61 + 1 ÷ 70 ≈ 0.031). A cross-encoder then re-ranks the merged candidates. It runs one transformer pass over the question and the passage together, so attention can compare every question word with every passage word, which makes it much more accurate. It needs one model call per passage, so it is used on the top 50 to 100 candidates, not on the whole corpus. The vector index itself is approximate nearest-neighbour search (HNSW or IVF), which returns the true nearest vectors for perhaps 95 to 99% of queries in a few milliseconds; anything it misses never reaches the later stages.
Chunking and context decide what the model actually sees. Small chunks of 100 to 200 tokens match precisely but lose context: a chunk that says "the limit above applies to all regions" does not say which limit. Chunks of 1,000 tokens or more keep context but blur the embedding and use more prompt tokens per chunk. A common compromise is 300 to 800 tokens, split at headings, with some overlap, and with the document title and section path added to every chunk. Contextual retrieval goes one step further: before indexing, a language model writes one or two sentences that place each chunk in its document, and that text is embedded and indexed with the chunk. Anthropic reported that this cut the share of questions whose answer was missing from the top 20 chunks from 5.7% to 2.9% (contextual embeddings plus contextual BM25), and to 1.9% with re-ranking.
Context engineering is the last step: building the prompt from the results. Put the strongest passages first, because models use the start and the end of a long context better than the middle. Remove near-duplicate chunks. Give each chunk an ID, a title and a date, so the model can cite it and prefer newer sources. Keep a fixed token budget (for example 6 chunks of 500 tokens) and keep the instructions where they are not buried. In agentic RAG, the model also writes its own search queries and searches again when results are weak. A multi-step question such as "who owns the service that failed last night?" becomes two searches: first find the service, then find its owner.

mistakes: People often think vector search returns passages that answer the question. In fact it returns passages whose embeddings are close to the question's embedding, and a question is often closest to other questions, complaints or titles that repeat its words. That is why query rewriting, hybrid search and re-ranking help: they move the search from "texts that sound like the question" toward "texts that contain the answer".
People often treat a similarity score as an absolute measure, for example "above 0.8 means relevant". In fact score ranges depend on the embedding model, the domain and even the length of the texts, and a threshold tuned on one corpus fails on another. Use ranks, re-rankers and a labelled evaluation set, and re-tune any threshold whenever the model or corpus changes.
People often think a re-ranker improves recall. In fact it can only reorder the candidates it receives. If the right passage is not in the top 50 or 100 that retrieval returned, no re-ranker can bring it back. Measure recall at the candidate stage first; the re-ranker improves precision, meaning which few passages reach the prompt.
People often think an answer with citations is grounded. In fact a model can cite a real passage that does not support the sentence it is attached to, or combine two passages into a claim neither makes. Checking that cited IDs exist catches invented citations, but not unsupported ones; faithfulness needs claim-level checks, by a second model call or by human review on a sample.

terms: Agent — a language model running in a loop in which it chooses actions, sees their results and decides the next step until a goal is met.
Harness — the ordinary program around the model that runs the loop, executes tools, enforces permissions and manages the context.
Tool — a function the model may ask the harness to run, described by a name, a description and a JSON schema for its inputs.
Tool call — a structured message from the model naming a tool and its arguments; the harness, not the model, executes it.
ReAct loop — the pattern reason, act (call a tool), observe (read the result), repeated until the task is done.
Context window — the model's working memory for one call; everything the agent knows in a step must fit in it.
Prompt caching — reusing the stored computation for an unchanged prompt prefix, which makes resending long histories cheaper and faster.
Sandbox — an isolated environment (a container or virtual machine with limited network and files) where tool actions run.
Prompt injection — instructions hidden in data the agent reads (a web page, an email, a log file) that try to take control of it.
Sub-agent — a separate model call or loop given a narrow task and a clean context, whose summary result returns to the main agent.
how: Tool calling looks like magic but is plain text processing. The harness puts the tool definitions (name, description, JSON schema of the parameters) into the prompt, usually near the start. During post-training, the model learned to emit a structured block when it wants a tool, such as {"name": "run_shell", "input": {"cmd": "pytest -x"}}, and then to stop generating. Some APIs use constrained decoding so that the arguments always match the schema. The harness parses the block, checks it against the permission rules, runs the tool, and appends the output as a tool-result message. Then it calls the model again with the whole conversation. A model can ask for several independent calls at once (parallel tool calls) to save round trips. The model never executes anything itself: every effect in the world happens in harness code, which is exactly where the controls belong.
The loop has a cost shape that explains many design choices. Every turn resends the whole history. If each step adds about 2,000 tokens of reasoning and tool output, turn n sends about 2,000 × n tokens, so 30 turns send 2,000 × (1 + 2 + … + 30) = 930,000 input tokens in total, although the final context holds only 60,000. Input tokens grow with the square of the number of steps. Prompt caching changes this bill: the unchanged prefix is read from the cache instead of being processed again. Anthropic, for example, bills cache reads at one tenth of the normal input price for most models, and less for some newer ones, and cached prefixes also start faster. This is why harnesses append to the history instead of editing earlier messages: any change near the start invalidates the cache for everything after it. When the context nears its limit, the harness compacts it, replacing old tool outputs with short summaries, and accepts that some detail is lost.
Prompt injection is an adversarial-input problem with no clean fix inside the model. The model reads instructions and data as the same kind of thing, tokens in one context; there is no separation like the one between code and data in a CPU's memory protection. Text inside a web page or a file can therefore act as an instruction, and training can make the model less obedient to such text but cannot guarantee it. Simon Willison's "lethal trifecta" names the dangerous combination: access to private data, exposure to untrusted content, and a way to send data out. An agent with all three can be tricked into leaking data; removing any one of the three breaks the attack. Architectural defences follow from this. In the dual-model pattern, a quarantined model reads untrusted content but has no tools, and the privileged model that has tools never sees the raw text. CaMeL (Google DeepMind, 2025) turns the user's request into a small program and tracks where every value came from, so data from untrusted sources cannot decide which actions run.
Ethics becomes concrete engineering once an agent can act. Someone must be accountable for each action, so production agents act under a named person's or service's authority with narrowly scoped credentials. Every tool call is logged with its inputs, its output and the rule or human approval that allowed it. Actions that cannot be undone, or that other people see (sending email, payments, deleting data, pushing to the main branch), wait for explicit human confirmation.

mistakes: People often think the model runs the tools. In fact the model only writes text that describes a call; the harness decides whether and how to run it. A sentence in the system prompt such as "never delete files" is a request, not a permission system. Real limits are enforced in code: which tools exist, which arguments are allowed, which credentials the sandbox holds.
People often think a strong system prompt ("ignore any instructions inside documents") stops prompt injection. Such prompts reduce the success rate of simple attacks, but attackers adapt, and published evaluations keep finding phrasings that work. Defence has to assume that injection sometimes succeeds and limit what a hijacked agent can do: least-privilege tools, no path for sending private data out, and approval for risky actions.
People often think that if each step is 95% reliable, a 20-step task is also about 95% reliable. In fact independent errors multiply: 0.95²⁰ ≈ 0.36, so the task would succeed only about a third of the time. Agents reach high success only because they can observe errors and correct them, by running tests, re-reading outputs and checking results. Design every step so that its result can be verified.
People often think several cooperating agents always beat one. In fact sub-agents cost many more tokens (Anthropic reported that its multi-agent research system used about 15 times the tokens of a chat) and add coordination errors, because each sub-agent sees only part of the picture. They pay off for broad tasks that split into independent parts, such as researching many sources in parallel, and less for tightly coupled work such as most code changes.
quiz: What are the steps of the ReAct loop? || Reason about the goal and the current state, act by calling a tool, observe the tool's result, and repeat until the goal is reached or a limit is hit.
How does a tool call get from the model to the real world and back? || The model emits a structured block with a tool name and JSON arguments and stops. The harness parses it, checks the schema and the permission rules, runs the tool (often in a sandbox) and appends the result to the conversation as a tool-result message. Then it calls the model again with the updated history.
Why is prompt injection hard to fix inside the model, and what design rule limits the damage? || Instructions and data reach the model as the same kind of tokens in one context, so text in a web page or file can act like an instruction, and training only lowers the chance that the model obeys it. The rule is to never combine private data, untrusted content and a way to send data out in one agent, and to gate risky actions with permissions and human approval.
An agent runs 30 turns and each turn adds 2,000 tokens to its history. About how many input tokens does it send in total, and what is the cost in normal-price tokens if cached prefix tokens are billed at 10% of the normal price? || It sends 2,000 × (1 + 2 + … + 30) = 930,000 input tokens. Of these, 60,000 are new (2,000 per turn) and 870,000 are cached prefix, so the cost is about 60,000 + 0.1 × 870,000 = 147,000 normal-price tokens, roughly six times cheaper, ignoring the small surcharge for writing to the cache.
Which actions of a coding agent should need human approval, and what does requiring approval cost? || Actions that cannot be undone or that others can see: pushing to shared branches, deploying, sending messages, deleting data, spending money. Reading files and running tests in a sandbox should not need approval. Each approval costs latency and human attention, and too many of them teach people to approve without reading, so keep them for the few actions that really matter.

@@+ vectorsearch
terms: Embedding — a vector of a few hundred to a few thousand numbers that represents an item, placed so that similar items are close.
Cosine similarity — the cosine of the angle between two vectors; for unit-length vectors it equals their dot product.
k-nearest neighbours (k-NN) — the k stored vectors closest to the query vector.
Approximate nearest neighbour (ANN) — a search that returns most of the true nearest neighbours much faster than comparing with every vector.
Recall at k — the fraction of the true k nearest neighbours (found by exact search) that the index returns.
HNSW — Hierarchical Navigable Small World, a layered graph in which each vector links to nearby vectors and search walks the links.
IVF — inverted file index: vectors are grouped by k-means into lists, and a query scans only the lists closest to it.
nprobe and efSearch — the query-time knobs of IVF (how many lists to scan) and HNSW (how many candidates to keep); higher means better recall and slower search.
Product quantization (PQ) — compressing a vector by splitting it into sub-vectors and replacing each with the ID of its nearest centroid, usually 1 byte.
Re-ranking (rescoring) — recomputing exact distances with full-precision vectors for the top candidates found with compressed ones.
how: The choice of distance matters less than it seems, as long as it matches how the embedding model was trained. For vectors of length 1, cosine similarity equals the dot product, and the squared Euclidean distance equals 2 − 2 × cosine, so all three give the same ranking. Many systems therefore normalize vectors when they are inserted and use the dot product, which is the cheapest to compute. When vectors are not normalized, as in some recommendation models, maximum inner product search behaves differently, because long vectors win more often.
High dimensions explain why exact methods fail and approximate ones still work. For random data in hundreds of dimensions, distances concentrate: the nearest and the farthest points are at almost the same distance from a query, so a k-d tree must visit most of its leaves and gains nothing. Real embeddings are not random. They lie near much lower-dimensional structure, so neighbourhoods are meaningful, and an index that follows that structure can find good neighbours by visiting a tiny fraction of the data.
HNSW builds that structure as a graph. Each new vector draws a random top layer with an exponentially falling probability; with the usual setting, about 1 in M vectors reaches layer 1, 1 in M² reaches layer 2, and so on (M is the number of links per node, often 16). To insert a vector, the index walks greedily down from the entry point to the vector's top layer. On each layer below that, it runs a wider search that keeps efConstruction candidates (often 100 to 200) and links the vector to M of them, 2M on the bottom layer. A heuristic prefers neighbours in different directions over many neighbours that are close to each other, which keeps the graph navigable. A query does the same walk: a greedy step at each upper layer, which works like an express highway, then a search with a candidate list of size efSearch on layer 0. The number of steps grows roughly with log N. Memory is the price: at M = 16 the bottom layer alone stores 32 links × 4 bytes = 128 bytes per vector, on top of the vector itself.
IVF builds the structure with clustering instead. k-means is trained on a sample to find nlist centroids (the Faiss guidelines suggest 4√N to 16√N), and each vector is stored in the list of its nearest centroid. A query compares itself with all centroids and scans only the nprobe closest lists. Recall rises with nprobe, and nprobe = nlist is exact search. The vectors that get missed are those near cluster boundaries, whose true neighbours sit in a list that was not scanned. When the data drifts, the centroids become stale and the lists unbalanced, so the clustering must be retrained.
Quantization makes the vectors themselves small. Scalar quantization maps each 32-bit float to an 8-bit integer using each dimension's range: 4 times smaller. Binary quantization keeps one bit per dimension, 32 times smaller, and compares vectors with Hamming distance, an XOR followed by a population count, which CPUs do very fast; the top candidates are then rescored with full vectors. Product quantization splits a 768-dimension vector into 96 sub-vectors of 8 dimensions and trains 256 centroids in each sub-space, so each sub-vector becomes one byte. At query time, the engine computes once a table of 96 × 256 distances between the query's sub-vectors and all the centroids. The approximate distance to any stored vector is then the sum of 96 table lookups, with no decompression.
DiskANN combines these ideas for collections larger than memory. It keeps the full vectors and a graph (called Vamana) on SSD, with each node's vector and links in one 4 KB block, and only the PQ codes in RAM. The search uses PQ distances in memory to choose which nodes to visit and reads a few dozen SSD blocks per query to follow links and compute exact distances. The authors reported indexing a billion vectors on one machine with 64 GB of RAM, answering queries in a few milliseconds at about 95% recall.

mistakes: People often think more embedding dimensions always give better search. In fact memory and compute grow in proportion to the dimension, while quality often improves only a little beyond a few hundred dimensions. Many recent embedding models are trained so that their vectors can be cut short (Matryoshka representation learning, 2022): keeping the first 256 of 3,072 dimensions loses some quality but cuts memory 12 times. Measure on your own queries before paying for the largest size.
People often filter after searching: find the top 100 by vector, then remove what the user may not see. If the filter keeps only 2% of items, about 2 of those 100 survive, and the user gets 2 results instead of 10, or poor ones. Selective filters need filter-aware search, partitions per tenant or category, or a much larger candidate list, and their recall must be measured separately.
People often read "recall at 10 = 0.95" as "95% of results are relevant". In fact ANN recall compares the index with exact nearest-neighbour search on the same vectors. It measures how faithful the index is, not whether the nearest vectors are what the user wanted. A perfect index over poor embeddings still returns poor results, so measure index recall and end-to-end relevance as two different numbers.
quiz: Name the two main families of ANN index and the query-time knob each one exposes. || Graph indexes such as HNSW, where efSearch sets how many candidates the search keeps; and cluster indexes such as IVF, where nprobe sets how many lists are scanned. Raising either knob improves recall and slows the search.
Why does an HNSW search take roughly logarithmic time? || Each layer holds about M times fewer vectors than the one below, and links on the sparse upper layers span long distances. The search crosses large distances in a few greedy hops at the top and refines with short links lower down, so the number of steps grows roughly with log N.
How does product quantization compute distances without decompressing the stored vectors? || For each query, it computes once a table of distances between each query sub-vector and the 256 centroids of that sub-space. Each stored vector is a list of centroid IDs, one byte per sub-vector, so its approximate distance is the sum of one table lookup per sub-vector.
You store 50 million vectors of 1,024 dimensions. How much memory do float32, int8 and binary vectors need, and how much does an HNSW graph with M = 16 add? || float32: 50 million × 4,096 bytes ≈ 205 GB; int8: about 51 GB; binary (128 bytes each): about 6.4 GB. The HNSW bottom layer adds about 50 million × 128 bytes ≈ 6.4 GB of links.
For 1 billion vectors of 768 dimensions on a limited budget, would you choose HNSW in memory, IVF-PQ, or DiskANN? || HNSW needs about 3 TB for float32 vectors alone, plus links, so it means a large sharded cluster; it gives the best recall and latency. IVF-PQ at about 96 bytes per vector (roughly 100 GB) fits on one large machine, with lower recall that rescoring can recover. DiskANN keeps compressed codes in RAM and the graph on SSD, giving high recall on one machine at a few milliseconds per query, which is often the best balance.

@@+ replication
terms: Replica — one copy of the data on one machine; the leader (primary) accepts writes and followers (standbys, replicas) copy them.
Replication log — the ordered stream of changes (often the write-ahead log) that the leader sends and every replica applies in the same order.
Synchronous replication — the leader confirms a write to the client only after one or more replicas have stored it.
Asynchronous replication — the leader confirms a write at once and sends it to replicas afterwards; recent writes can be lost on failover.
Replication lag — how far a replica is behind the leader, measured in log bytes or, more usefully, in seconds.
Failover — promoting a replica to leader when the old leader fails, and redirecting clients to it.
Split brain — two nodes both acting as leader and accepting writes, so the copies diverge.
Quorum — the number of replicas that must take part in a write (W) or a read (R) out of N copies.
Read repair — when a read finds a stale replica, the client or coordinator writes the newest value back to it.
Recovery point objective (RPO) — the maximum amount of recent data, measured in time, that you accept losing in a failure.
how: In leader–follower replication, everything revolves around log positions. Each follower reports how far it has received, flushed to disk and applied the log; PostgreSQL shows these as write_lsn, flush_lsn and replay_lsn in pg_stat_replication, and Kafka tracks each follower's log end offset. The leader uses the reports for two things: to decide when a write is safe to acknowledge (enough replicas have flushed it), and to measure lag. Lag in bytes is the leader's position minus the follower's; lag in time is how old the last applied transaction is, which is the number that matters to users.
TCP gives replication an ordered byte stream, but its guarantees end at the connection. Within one connection, bytes arrive in order with no gaps, so a follower reading the stream receives log records in order. But a successful send() only means the bytes reached the local kernel's buffer, and when a connection breaks, neither side knows how much the other actually processed. Replication protocols therefore keep their own acknowledgements and positions. After a reconnect, the follower says "send from position X", and applying records is made idempotent, or tied to positions, so that a record received twice is not applied twice. TCP's flow control also gives natural backpressure: when a slow follower's receive window fills, the leader's send buffer fills too, and the leader must either wait (synchronous) or remember the follower's position and stream the rest from its log files later.
Leaderless replication replaces the leader with arithmetic. With N = 3, W = 2 and R = 2, every set of 2 replicas that took a write overlaps every set of 2 replicas that is read, so at least one replica in every read has the latest successful write. Each value carries a version, either a timestamp (last writer wins) or a version vector that can detect concurrent writes, and the reader returns the newest version and writes it back to stale replicas (read repair). Sloppy quorums keep writes available when some home replicas are down: the write goes to another node, which keeps a "hint" and forwards it later (hinted handoff). Until the hint is delivered, the overlap guarantee does not hold. For data that is rarely read, replicas run anti-entropy with Merkle trees, which are trees of hashes over key ranges. If two replicas' root hashes match, the whole range is identical. If not, they compare the two children and descend only into the halves that differ, so a few differing keys among millions are found with a small number of hash comparisons instead of a full scan.
Distributed systems theory says what no design can avoid. The FLP result (Fischer, Lynch and Paterson, 1985) proves that in a fully asynchronous system, where messages can be delayed without limit and even one process may crash, no deterministic algorithm can guarantee that replicas agree. Practical systems escape by assuming partial synchrony: messages usually arrive within some time, so timeouts eventually tell the truth. That is why failover always depends on timeouts, and why a timeout that is too short causes false failovers during garbage-collection pauses or network blips. The CAP theorem adds the partition case: while replicas cannot reach each other, the system must either refuse some requests or accept that copies may disagree.

mistakes: People often think that W + R > N makes a leaderless store strongly consistent. In fact the overlap guarantees only that a read touches a replica with the newest successful write. Sloppy quorums break the overlap. A write that reached one replica and then reported failure may still be returned by later reads. Concurrent writes resolved by last-writer-wins depend on clocks that can be wrong. Dynamo-style stores with quorums are still not linearizable.
People often think synchronous replication means zero data loss in every case. In fact the guarantee lasts only while the synchronous replica is healthy. PostgreSQL then blocks commits until a synchronous standby answers, which turns a replica failure into an outage unless several candidates are configured. MySQL semi-synchronous replication instead falls back to asynchronous mode after a timeout (10 seconds by default), silently removing the guarantee. Know which behaviour your system has and alert on it.
People often think replication lag is always a few milliseconds, so stale reads are rare. In fact lag jumps during write bursts, large batch updates, schema changes and long queries on the replica. A PostgreSQL standby pauses replay for up to 30 seconds by default (max_standby_streaming_delay) when a query on it conflicts with incoming changes. Read-after-write logic must handle lag of seconds or minutes, not only milliseconds.
People often think TCP makes the replication stream reliable, so a record that was sent has arrived. In fact TCP's reliability covers only an open connection; a successful send means the bytes are in the local buffer. If the leader crashes or the connection breaks, records it "sent" may never have reached the follower's disk. Only an acknowledgement from the follower, naming the position it has flushed, proves that a write is replicated.
quiz: What are the three main styles of replication, and where do writes go in each? || Single-leader: all writes go to one leader, which streams its log to followers. Multi-leader: several leaders, usually one per region, accept writes and exchange them, so conflicts must be resolved. Leaderless: clients write to and read from several replicas directly, using quorums.
Why does W + R > N make a read see the latest successful write, and what can break this? || Any W replicas and any R replicas out of N must share at least one replica, so every read includes a replica that took the latest successful write, and the newest version wins. Sloppy quorums with hinted handoff, partial failed writes and clock-based last-writer-wins can each break or weaken the guarantee.
How do Merkle trees make anti-entropy between two replicas cheap? || Each replica builds a tree of hashes over key ranges. The replicas compare root hashes; if they match, nothing needs syncing. If not, they compare children and descend only into ranges whose hashes differ, so they find the few differing keys without comparing every key.
A synchronous standby is 1,500 km away over fibre, where light travels about 200,000 km per second. What is the minimum extra latency per commit, and how many commits per second can one client doing sequential commits reach? || The round trip is 3,000 km ÷ 200,000 km/s = 15 ms, so each commit waits at least 15 ms more, and one sequential client reaches at most about 66 commits per second. Many concurrent clients can commit together (group commit), but each commit still waits at least 15 ms.
Would you replicate a payments database synchronously or asynchronously? || Use synchronous or quorum replication to a nearby standby, because the recovery point objective is zero lost payments and a 1 to 2 ms delay inside a region is affordable. Add asynchronous replicas for reporting and for another region, where waiting would cost too much latency and a few seconds of possible loss is acceptable for disaster recovery.
