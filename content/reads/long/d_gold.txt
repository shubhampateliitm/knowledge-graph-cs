@@ bloom
value: A Bloom filter answers one question, "is this item in the set?", using far less memory than storing the items themselves. It never says "no" for an item that is in the set (no false negatives). It sometimes says "maybe yes" for an item that is not in the set (a false positive), and you choose that error rate in advance, for example 1%. For one million keys at 1%, a Bloom filter needs about 1.2 MB, while storing the keys themselves (say 16 bytes each) would need 16 MB plus the overhead of a hash table.
That trade is valuable whenever the real lookup is expensive and most lookups are for items that are not there. A storage engine can skip reading a file from disk; a cache can skip asking a remote server; a join can skip sending rows across the network. The filter sits in front of the expensive operation like a cheap guard: if it says "definitely not", you save the work; if it says "maybe", you do the real check.
For the layer above (storage engines such as RocksDB and Cassandra, file formats such as Parquet, query engines such as Spark, caches and CDNs), Bloom filters turn "check every place the key might be" into "check only the places that probably have it". The layers below make this possible: hashing (L3) spreads keys evenly over bit positions, probability (L4) tells you exactly how many bits and hash functions you need for a chosen error rate, and concentration inequalities (L4) explain why the real error rate stays close to that prediction.
terms: Bit array — a sequence of m bits, all starting at 0; the whole filter is just this array.
Hash function — a function that maps any item to a number that looks random; the same item always gives the same number.
k — the number of bit positions each item sets (the number of hash functions).
m — the number of bits in the filter.
n — the number of items inserted.
False positive — the filter says "maybe present" for an item that was never inserted.
False negative — the filter says "absent" for an item that was inserted; a Bloom filter never does this.
Bits per key — m divided by n; the main knob that sets the false-positive rate.
history: Burton Howard Bloom described the structure in 1970 in "Space/Time Trade-offs in Hash Coding with Allowable Errors". His example was hyphenation: about 90% of English words could be hyphenated by simple rules, and only the remaining words needed a slow dictionary lookup on disk. A small in-memory filter could tell the program which words were "probably special" and so worth the disk access. In 1970, memory was extremely expensive, so accepting a small error to save most of the memory was a natural engineering choice.
The idea stayed fairly niche until networking and web systems in the late 1990s. Fan, Cao, Almeida and Broder's "Summary Cache" (2000) used counting Bloom filters so web proxies could tell each other what they cached. Broder and Mitzenmacher's survey "Network Applications of Bloom Filters" (2004) collected many uses and made the structure widely known. Kirsch and Mitzenmacher (2006) showed that two hash functions are enough to simulate k of them, which made filters cheaper to compute.
Then storage systems adopted them everywhere. Google's Bigtable paper (2006) described per-file Bloom filters to avoid disk reads, and LSM-tree databases that followed (HBase, Cassandra, LevelDB, RocksDB) made them standard. Better variants kept appearing: blocked Bloom filters that fit one CPU cache line (Putze, Sanders and Singler, 2007), cuckoo filters that support deletion (2014), xor filters (2019–2020) and ribbon filters (2021, now available in RocksDB), which use less memory for the same error rate.
how: Start with an array of m bits, all set to 0, and choose k hash functions h₁ … h_k, each mapping an item to a position from 0 to m − 1. To insert an item x, compute the k positions h₁(x) … h_k(x) and set those bits to 1. If a bit is already 1, it stays 1. To query an item y, compute its k positions and look at those bits. If any of them is 0, y was certainly never inserted, because inserting y would have set all of them. If all of them are 1, y is probably in the set: either it was inserted, or other items happened to set all of its bits.
The false-positive rate follows from simple probability. After inserting n items with k hashes each, a particular bit is still 0 with probability \( (1 - 1/m)^{kn} \), which is very close to \( e^{-kn/m} \). A query for an absent item is a false positive only if all k of its bits are 1, so the false-positive rate is about
\[ p \approx \left(1 - e^{-kn/m}\right)^k \]
This formula assumes the hash functions behave like independent random functions, which is exactly what good hashing (from the L3 hash-table concept) provides. Concentration inequalities explain why the actual fraction of set bits is very close to its expected value when m is large, so the formula is reliable in practice, not only on average.
Two numbers fall out of the formula. For a given number of bits per key (\( m/n \)), the best number of hash functions is \( k = (m/n) \times \ln 2 \), about 0.69 × bits per key. At that best k, about half the bits are 1, and \( p \approx 0.6185^{m/n} \). Turning it around, to reach a target rate p you need about \( 1.44 \times \log_2(1/p) \) bits per key: about 9.6 bits for 1%, 14.4 bits for 0.1%, and 19.2 bits for 0.01%. Each extra 4.8 bits per key cuts the false-positive rate by a factor of 10. Notice that the size depends only on n and p, not on how big the items are: a filter of URLs costs the same as a filter of integers.
Computing k independent hashes is expensive, so real implementations use a trick from Kirsch and Mitzenmacher: compute two hashes a and b once, and use positions a + i × b (mod m) for i = 0 … k − 1. The false-positive rate is practically the same. Another practical change is blocking. In a classic filter, the k bits of one item are spread across the whole array, so a query may touch k different cache lines, which costs memory latency (about 80–100 ns per miss on a modern server). A blocked Bloom filter first hashes the item to one 64-byte block (one cache line) and sets all k bits inside that block. Each query then costs one cache miss. The price is a slightly higher false-positive rate for the same memory, because blocks fill unevenly.
Bloom filters also combine well. Two filters with the same m, k and hash functions can be merged with a bitwise OR, which gives the filter of the union of the two sets; this is useful when many workers build filters in parallel. You can also estimate how many items a filter holds from the number of 1 bits X: \( n \approx -(m/k) \times \ln(1 - X/m) \).
What they cannot do is delete. Clearing a bit might remove evidence that another item also needs. Counting Bloom filters replace each bit with a small counter (often 4 bits), incrementing on insert and decrementing on delete, at about 4 times the memory. Cuckoo filters (the neighbouring L2 concept) store short fingerprints in a cuckoo hash table instead, which supports deletion and, below about 3% false positives, uses less space than a Bloom filter.

example: Take a filter of m = 20 bits and k = 3 hash functions, as in the diagram. Insert "cat", which hashes to positions 2, 7 and 13; set those three bits. Insert "dog", which hashes to 7, 10 and 17. Bit 7 is already 1, so only 10 and 17 change. Five bits are now 1. Query "owl", which hashes to 3, 7 and 17. Bit 3 is 0, so "owl" was never inserted; this answer is certain. Query "fox", which hashes to 2, 10 and 13. All three bits happen to be 1 (set by "cat" and "dog"), so the filter says "maybe". That is a false positive. With 5 of 20 bits set, the chance that a random absent item lands only on set bits is about (5/20)³ ≈ 1.6%. Every insertion raises this number, which is why filters must be sized for the expected item count.
Now a realistic sizing. An LSM-tree storage engine holds 100 million keys across its files, and you want a 1% false-positive rate. You need 9.6 bits per key, so 960 million bits, which is about 120 MB of filter memory, with k = 7. Compare this with keeping 100 million 16-byte keys in memory: 1.6 GB before any hash-table overhead.
What does the filter buy? Suppose a point lookup for a key that does not exist would otherwise check 8 files on disk, and each check costs one random read of about 100 microseconds on an NVMe SSD. Without filters, the lookup costs about 8 × 100 = 800 microseconds. With 1% filters, each file is read with probability 0.01, so the expected cost is 8 × 0.01 × 100 = 8 microseconds of disk time, plus a few hundred nanoseconds to check 8 filters in memory. That is a 100× improvement for "key not found" lookups, which are common in practice (for example, "insert if not exists" or checking whether a user ID was seen before). Going to 0.1% would cost 14.4 bits per key (180 MB) and cut the remaining disk reads by another 10×; whether that is worth 60 MB more memory is the real tuning decision.
intuition: A guest list where every name ticks a few boxes on a shared sheet; if any of your boxes is empty, you are certainly not on the list, but if all are ticked, you might be.
The idea is natural once you notice the asymmetry of the question. To prove that something is absent, you only need one piece of missing evidence; to prove it is present, you would need the item itself. A Bloom filter keeps a thin, shared trace of each item: enough to rule out most absent items, too little to reconstruct anything. Hashing makes these traces look random, so items rarely overlap by accident, and probability tells you how rarely. You trade a small, controlled error for a large saving in memory, and you only pay the error where it is safe: a "maybe" just leads to the real, exact check.
mistakes: People often think a Bloom filter stores the items in compressed form. In fact it stores no items at all, only bits set by hashes. You cannot list the members, retrieve a value, or recover a key from the filter.
People often think more hash functions always mean fewer errors. In fact the error rate is lowest at k ≈ 0.69 × bits per key. Beyond that, each insertion sets so many bits that the array fills up and false positives rise again. More hashes also cost more CPU and memory accesses.
People often think the false-positive rate stays fixed once chosen. In fact it is a function of how many items have been inserted. If you size a filter for 1 million items and insert 2 million, a 1% filter becomes roughly a 13% filter. Filters must be rebuilt or resized (for example with scalable Bloom filters, which add new layers) when the set grows.
People sometimes use a Bloom filter for security or privacy decisions. In fact an attacker who knows the hash functions can craft items that produce false positives, and a filter can leak which items are likely present. Bitcoin's BIP 37 light-client filters were found to leak wallet addresses for this reason, and were later replaced by a different design (BIP 157/158).
friction: The main limitation is that a Bloom filter answers only membership, only approximately, and cannot delete. Deletion needs counting filters (more memory) or cuckoo filters (which can fail to insert when very full). The size must be planned in advance; a filter that grows beyond its plan degrades steadily, and resizing requires the original items, which the filter does not keep.
The memory is also not optimal. The theoretical minimum for a false-positive rate p is \( \log_2(1/p) \) bits per key, and a Bloom filter uses about 1.44 times that, so roughly 44% is overhead. Xor filters and ribbon filters come much closer to the minimum (RocksDB reports around 30% memory savings with ribbon filters at the same error rate), but they must be built from a complete set at once, which suits immutable files but not sets that change.
Performance has its own costs. Classic filters touch k random cache lines per query; blocked filters fix this but raise the error rate slightly. Filters for very large sets may not fit in memory at all, and then a filter check itself may need a disk read, which defeats the purpose. Finally, a Bloom filter only helps negative lookups. If most of your queries are for items that exist, the filter adds work and saves nothing.
practice: Use a Bloom filter in front of an expensive check when most lookups miss: per-file or per-partition filters in storage engines, filters on join keys before shuffling data, or "have we seen this ID?" checks before hitting a database. Size it from the expected item count and target error: bits per key ≈ \( 1.44 \times \log_2(1/p) \), \( k \approx 0.69 \times \text{bits per key} \). Ten bits per key (about 1%) is a common default; it is the usual starting point in RocksDB, and Cassandra exposes the target rate per table as bloom_filter_fp_chance.
In RocksDB, consider the ribbon filter option for large datasets to save memory, and enable whole-key or prefix filtering to match your access pattern (prefix filters help range scans that share a prefix). In Parquet and Delta tables, Bloom filters on high-cardinality columns that are queried by equality (user IDs, device IDs) let engines skip row groups that min/max statistics cannot skip. In Spark, runtime Bloom filter joins (available since Spark 3.3) can shrink the larger side of a join before the shuffle.
Always measure the real false-positive rate and the memory used, because inserting more items than planned is the most common failure. Use a well-tested library (for example Guava's BloomFilter in Java, or the filters built into your database) rather than writing your own hashing, and never rely on a Bloom filter where an adversary chooses the inputs.
quiz: Can a Bloom filter return a false negative, and why or why not? || No. Inserting an item sets all k of its bits to 1 and bits are never cleared, so a query for an inserted item always finds all its bits set.
Why does adding more hash functions eventually make the false-positive rate worse? || Each insertion sets k bits, so a large k fills the array quickly. Once most bits are 1, absent items easily find all their bits set. The minimum error is at \( k \approx 0.69 \times (m/n) \).
How many bits per key do you need for a 0.1% false-positive rate, and what k? || About 1.44 × log₂(1000) ≈ 1.44 × 9.97 ≈ 14.4 bits per key, with k ≈ 0.69 × 14.4 ≈ 10 hash functions.
An LSM store checks 10 files for a missing key, each read costing 100 µs. What is the expected disk time with 1% Bloom filters on each file? || 10 × 0.01 × 100 µs = 10 µs, instead of 1,000 µs without filters.
When would you choose a cuckoo filter or a ribbon filter instead of a Bloom filter? || A cuckoo filter when you must delete items, or want very low error rates in less space. A ribbon (or xor) filter when the set is fixed at build time, such as an immutable file, and you want close to minimum memory.
