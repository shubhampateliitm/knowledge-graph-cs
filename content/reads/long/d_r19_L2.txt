@@ crossval
value: A model is fitted to data, but you do not care how well it does on that data. You care how well it will do on data it has never seen: tomorrow's ad requests, next month's customers, next year's transactions. The error on the training data is a bad guide to this, because a flexible model can memorize the training rows. A model with enough parameters can reach zero training error and still be useless on new rows. Train, validation and test splits, and cross-validation, are the standard way to get an honest estimate. You hide some data from the training process, and you measure on it.
The three splits have three different jobs. The training set is used to fit the parameters. The validation set is used to make choices: which model family, which regularization strength, which features, when to stop training. The test set is used once, at the end, to report the number you will tell other people. If you use the test set to make choices, it stops being a test set, and the number you report becomes optimistic. Cross-validation is a way to get the same information when data is scarce: instead of one validation set, you rotate the role through k parts of the data and average, so every row is used for both training and validation, but never at the same time.
For the layer above (machine learning in general, ad click-through-rate models, fraud models, recommender systems, and even data-quality checks in tools such as dbt), this is the discipline that separates a model that works from a model that only looks good in a notebook. The layers below explain why it works. Statistics (L4) says that the average error on held-out rows is an unbiased estimate of the error on new rows, and gives the standard error of that estimate: it shrinks like 1/√n. Learning theory (L4) says why you need held-out data at all: the gap between training error and true error grows with the capacity of the model class and shrinks with the amount of data, and the bounds are too loose to use as a measurement. So you measure instead of bounding.
terms: Training set — the rows used to fit the model's parameters (weights, tree splits, and so on).
Validation set — held-out rows used to choose hyperparameters, features or the stopping point; also called the dev set.
Test set — held-out rows touched once, at the end, to report the final performance estimate.
Hyperparameter — a setting chosen by you, not learned by fitting, such as the regularization strength, tree depth or learning rate.
k-fold cross-validation — split the data into k parts (folds); train k times, each time holding out one fold for evaluation; average the k scores.
Leakage — information from the evaluation data (or from the future, or from the label) that reaches the training process, making the estimate too good.
Generalization gap — the difference between the error on new data and the error on the training data.
Stratified split — a split that keeps the class proportions (for example 2% positives) the same in every part.
Group split — a split that keeps all rows of one entity (a user, a device, a household) in the same part.
history: The idea of testing a prediction rule on data that did not build it is old, but the modern form comes from the 1970s. Mervyn Stone (1974) and Seymour Geisser (1975) published the two classic papers on "cross-validatory" assessment of predictions. Stone's paper also describes leaving one observation out at a time, which became leave-one-out cross-validation. The reason was practical: statisticians had small samples, could not afford to set aside a large test set, and wanted a method that did not rely on the model's assumptions being true.
In the 1980s and 1990s, machine learning grew and the question became which variant to use. Ron Kohavi (IJCAI 1995) compared bootstrap and cross-validation on real datasets and concluded that stratified ten-fold cross-validation is a good default: it has less variance than leave-one-out and less bias than two- or five-fold. That paper is the reason "10-fold" became a habit. Hastie, Tibshirani and Friedman's textbook (chapter 7) gave a clear account of the bias and variance of these estimators, and warned about the most common mistake: selecting features using all the labels before cross-validating.
The 2000s brought attention to the second-order problem: using the validation score to choose between many candidates makes the validation score itself optimistic. Varma and Simon (2006) and Cawley and Talbot (2010) showed this with nested cross-validation. Kaufman, Rosset and Perlich (KDD 2011) gave a taxonomy of leakage, drawn from data-mining competitions where the winning models often exploited accidents of how the data was prepared. In the 2010s, as the same benchmark test sets (ImageNet, CIFAR-10) were used by thousands of researchers, Dwork and co-authors (Science, 2015) gave a way to reuse a holdout safely with noise, and Recht and co-authors (2018) built fresh test sets and found that accuracy dropped, but the ranking of models mostly held.
how: Start with the simplest scheme: the holdout. Shuffle the rows, take about 60 to 80 percent for training, and split the rest into validation and test. You fit on training, compare candidates on validation, pick one, and then evaluate the pick once on test. This is cheap, because you train only once per candidate, and it is the right design when you have millions of rows. With millions of rows, a test set of 100,000 already gives a standard error under 0.1 percentage points for an accuracy near 90 percent, so there is no reason to hold out more.
When data is small, a single validation set is noisy and wastes data. K-fold cross-validation fixes this. Split the rows into k folds of equal size. For each fold i, train on the other k − 1 folds and compute the score on fold i. The k scores are averaged to give the estimate, and their spread gives a rough error bar. Each row is used for evaluation exactly once and for training k − 1 times. The cost is k training runs per candidate. The choice of k is a bias-variance trade-off. A small k (such as 2 or 3) trains on much less data than the final model will see, so the estimate is pessimistic (biased). A large k, up to leave-one-out (k = n), has little bias, but the n training sets almost overlap, so the n scores are strongly correlated and the average has high variance, and it costs n fits. Ten or five is the usual compromise. For linear least squares there is a shortcut for leave-one-out: the error for row i is e_i / (1 − h_ii), where e_i is the ordinary residual and h_ii is the i-th diagonal entry of the hat matrix, so all n scores come from one fit. This is the linear algebra (L4) paying for itself.
The split must match how the model will be used, and this is where most real errors come from. The test rows must look, relative to the training rows, like tomorrow looks relative to today. For time-dependent data such as ad clicks, fraud and demand, split by time: train on days 1 to 60, validate on days 61 to 67, test on days 68 to 74. A random split would put Tuesday's rows in training and Monday's rows in test, which lets the model learn things about the future, such as a campaign that only ran that week. Scikit-learn's TimeSeriesSplit makes this rolling: the training window grows and the validation window moves forward. For data with repeated entities, use a group split. If the same user appears in training and in test, a model can recognise the user instead of learning a general rule, and the score is too high. For rare positives, use a stratified split so that every fold has enough of them.
Leakage deserves its own check, because it is the most common reason a model's offline score is much better than its production score. The basic rule is: every step that learns from data (scaling, imputation, feature selection, target encoding, embedding training, even choosing a threshold) must be fitted inside the training part of each fold only, and then applied to the validation part. If you compute the mean and variance of a feature on all rows and then cross-validate, the validation rows have influenced the preprocessing. With feature selection on labels, the effect can be dramatic: on random data with 5,000 features and 50 rows, selecting the 100 best-correlated features on all rows and then cross-validating gives a much better than chance accuracy, even though there is no signal at all. Pipelines (scikit-learn's Pipeline, Spark ML's Pipeline) exist to enforce the rule: the whole sequence is refitted inside each fold.
Last, when you use cross-validation both to choose among many candidates and to report the final performance, the reported number is biased upwards, because you reported the maximum of several noisy scores. The fix is nested cross-validation: an outer loop estimates performance; inside each outer training part, an inner loop chooses the hyperparameters. The outer score is then an honest estimate of the whole procedure "tune and fit". It costs k_outer × k_inner × candidates fits, so it is used for small data and for reporting, not for every experiment.

example: Suppose you build a click-through-rate model for an ad exchange. You have 14 days of logs, 70 million impressions, with a 0.8 percent click rate, so about 560,000 clicks. You compare logistic regression with a gradient-boosted tree model, and for each one you tune a regularization strength.
First the wrong way. You shuffle all 70 million rows, take 80 percent for training and 20 percent for test, and the boosted model shows a log loss of 0.062 against 0.071 for logistic regression. It looks like a clear win. But the shuffle put impressions from the same user, the same auction and the same minute on both sides of the split. The boosted model has learned user IDs and campaign-specific bursts, which do not carry over to new days.
Now the right way. Use days 1 to 10 for training, days 11 and 12 for validation, and days 13 and 14 for test. Fit each candidate on days 1 to 10. Try five regularization strengths for each model and score them on days 11 and 12. Suppose logistic regression's best validation log loss is 0.0715 and the boosted model's best is 0.0702. Choose the boosted model with its best setting. Then, and only then, score it on days 13 and 14: say 0.0709. This number is a little worse than the validation score, which is normal, because you picked the best of several candidates on the validation data and it is slightly optimistic. The gap between 0.0702 and 0.0709 is a measure of that optimism plus the day-to-day drift.
How certain is the test number? For a metric like accuracy, the standard error of a proportion p measured on n rows is √(p(1 − p)/n). With p = 0.9 and n = 10,000 test rows, this is √(0.09/10,000) = 0.003, so the 95 percent interval is about ±0.6 percentage points. A claim that model B beats model A by 0.2 points on this test set is therefore not reliable. To be 95 percent sure, within ±1 percentage point, of any accuracy, Hoeffding's bound says you need n ≥ ln(2/0.05) / (2 × 0.01²) ≈ 3.69 / 0.0002 ≈ 18,400 rows. For rare events, the count of positives matters more than the number of rows: with 0.8 percent clicks, a test set of 10,000 rows has only about 80 clicks, and the click rate itself has a relative error of about 1/√80 ≈ 11 percent.
Finally, the five-fold version for a small dataset. With 1,000 labeled support tickets, split into five folds of 200. Each run trains on 800 and scores on 200. If the five accuracies are 0.84, 0.88, 0.86, 0.82 and 0.90, the mean is 0.86 and the standard deviation is about 0.032, so the standard error of the mean is roughly 0.032/√5 ≈ 0.014 (a slight underestimate, because the folds share training data). You would report 0.86 ± 0.03, and not make claims about differences smaller than that.
intuition: Do not grade students on the exact questions they practiced; keep a few questions in a locked drawer and open it only for the final exam.
A model is a student with a very good memory. If the exam repeats the homework, a student who memorized the answers gets full marks and has learned nothing. The honest exam uses new questions that are drawn from the same source as the homework. Held-out data is that exam. The same logic explains why you can use the "exam" only a limited number of times. Each time you look at the score and change something, you pass a little information about the exam into the student. After many rounds, the student has partly memorized the exam, too, and you need a new, untouched one.
The statistical argument is short. If the held-out rows are a random sample from the same source as the future rows, and the model did not see them, then the average loss on them is an unbiased estimate of the future loss, with a standard error that falls like 1/√n. Every rule in this topic (split by time, split by user, fit preprocessing inside the fold, touch the test set once) is a way to keep that one assumption true: that the held-out rows are independent of the training process, and look like the future.
mistakes: People often think cross-validation gives you a better model. In fact it gives you a better estimate of how good a model will be. It trains k throwaway models. After choosing the settings, you normally retrain once on all the training data and deploy that one.
People often think a random split is always fine. In fact it is fine only when rows are independent and the future looks like the past. With time series, repeated users, duplicated documents or near-duplicate images, a random split puts almost the same row on both sides and inflates the score. The split must copy the way the model will be used.
People often think that leakage is only about putting test rows into training. In fact the more common leaks are quiet: a feature computed from the label (such as "number of refunds" for a fraud model, where refunds happen after the fraud is found), a feature computed with future data (an average over the whole month), normalization fitted on all rows, or duplicates across splits. If a feature makes the model much better than domain experts expect, look for a leak first.
People often think that if the test score is good, the model is good. In fact the test score is an estimate with its own error bar, and it is only valid for data like the test set. After deployment, the data changes (new campaigns, new devices, a changed app), so the production score can be lower. Offline evaluation is necessary, but it does not replace monitoring and online experiments.
People often think the test set can be used a few times, because it is only a peek. In fact each peek that influences a decision leaks information. With enough peeks, you have tuned the model to the test set, and the number is no longer honest. Keep a fresh final set for the last report, or use a reusable-holdout technique.
friction: Leakage is the biggest practical problem, and it is hard to see because it makes things look better. Features built from event logs often include information from after the prediction time, for example "total purchases by this user" computed over a month that includes the event you are predicting. In ads, conversions arrive days after the click, so the most recent training rows have incomplete labels: a click from yesterday looks like a non-conversion only because the conversion has not arrived yet. The fix is to build every feature as of the prediction timestamp and to wait for the label window to close before using a row.
Repeated use of the same validation or test data causes slow, hidden overfitting. A team that runs 200 experiments against one validation set is effectively fitting to it. The bias is small for each decision but accumulates. Fresh data, time-based rolling evaluation and a locked final test set are the main defences. Nested cross-validation fixes the selection bias but multiplies the cost.
The estimate has variance too. With small data, the cross-validation score has a large standard error, and the error bar from the k folds is itself an underestimate, because folds share training rows (Bengio and Grandvalet, 2004, showed that there is no unbiased estimator of the variance of k-fold cross-validation). So small differences between models usually are not significant. For imbalanced problems, plain accuracy misleads, and you need to choose metrics that match the cost, such as log loss, AUC or precision at a given recall.
Finally, the assumption that test data looks like future data is just an assumption. Distribution shift (new users, a changed ad format, a new device type), feedback loops (the model decides which ads are shown, which changes what data you collect) and adversaries break it. Offline scores from logged data are biased by the old policy, and off-policy evaluation is a research area of its own. For high-stakes cases, a held-out set is the start, followed by shadow deployment and A/B tests.
practice: Decide the split from the question "how will this model be used?" before writing code. For anything with a timestamp, split by time, and keep the validation period after the training period, with a gap if features use rolling windows or labels are delayed. For anything with repeated entities, split by entity (GroupKFold in scikit-learn, or hash the user ID to a split bucket so that the assignment is stable across data refreshes). In Spark and data platforms, a stable hash of the entity key, such as pmod(hash(user_id), 100), is a better split than a random number, since it gives the same assignment every time the job runs.
Put every learned step inside a pipeline, and fit it only on the training part of each fold. Check for leaks by asking of every feature: "would I know this value at prediction time?" Run a quick sanity test: shuffle the labels and confirm the score falls to chance; train a very simple baseline to see how far the fancy model really goes beyond it; and look at the top feature importances for anything suspicious, such as an ID or a timestamp.
Use stratified folds for imbalanced classes. Use 5 or 10 folds for small data, and a single holdout when you have millions of rows. Report a mean and a spread, not a single number. Lock the test set: write its identity down, run it once per release, and when you have used it too many times, refresh it with newer data. After choosing hyperparameters, refit on train plus validation before the final test. Track the offline-to-online gap: compare offline predicted metrics with what the A/B test and production logs show, because a persistent gap is the strongest signal that your evaluation does not match reality.
quiz: What are the separate jobs of the training, validation and test sets? || Training fits the parameters. Validation chooses hyperparameters, features and the stopping point. Test is used once at the end to report the final performance. If the test set is used for choices, it becomes a second validation set and the reported number turns optimistic.
Why do you split by time, not randomly, for ad click data? || A random split puts later rows in training and earlier rows in test, so the model can learn patterns from the future, such as a campaign that ran only that week. It also puts rows of the same user and auction on both sides. A time split trains on the past and tests on the future, as in production.
Why must feature scaling or feature selection be fitted inside each cross-validation fold? || If it is fitted on all rows, the validation rows have influenced the preprocessing (their means, or their label correlations), so the validation score is optimistic. On random data with thousands of features, label-based selection before cross-validation can give a high accuracy with no real signal.
A test set has 10,000 rows and the model has 90% accuracy. What is the approximate 95% interval, and can you trust a 0.2-point improvement? || The standard error is √(0.9 × 0.1 / 10,000) = 0.003, so the interval is about ±0.6 points. A 0.2-point difference is inside the noise, so it is not reliable evidence on its own.
You have 3,000 labeled rows and want to compare 20 hyperparameter settings and also report the final accuracy. What design do you use and why? || Use nested cross-validation: an inner loop chooses the setting inside each outer training part, and the outer folds estimate the performance of the whole procedure. Using the same folds for both choosing and reporting would report the maximum of 20 noisy scores, which is biased upwards.
tradeoffs: Choose a single holdout (train, validation, test) when you have more than about a million rows, or when training is slow. The standard error of a held-out score falls as 1/√n, so 100,000 test rows are already enough for most metrics, and k-fold would multiply the training cost by k. You give up a little data efficiency and a look at the variance across splits.
Choose k-fold cross-validation (k = 5 or 10) when you have fewer than roughly 50,000 rows and training takes seconds to minutes. It uses every row for both roles and gives an error bar. Five folds cost half as much as ten and are slightly more pessimistic; ten folds are closer to the final model's data size. Use leave-one-out only when n is tiny or a closed form exists (linear least squares), since its estimates are highly correlated and expensive otherwise.
Choose a time-based split over a random split whenever rows have timestamps and the model will predict the future, and choose a group split whenever an entity repeats. You pay with a smaller, older training set and a score that is more variable and usually lower. That lower number is the honest one. A random split is acceptable only when you can argue the rows are independent and the world is stable.
Choose nested cross-validation when you must both tune and report from a small dataset; choose a simple validation set plus a locked test set when you have enough data. Nested costs k_outer × k_inner × the number of candidates, often 100 times more training; the simpler scheme costs far less but needs more rows.
Choose online evaluation (an A/B test) over offline splits when the model changes what data is collected (ranking, bidding, recommendations). Offline metrics measure how well the model predicts the logged past under the old policy; an A/B test measures the business effect under the new policy. The price is time, traffic and risk, so use offline validation to filter candidates and online tests to decide.
interview: Your model scores 0.95 AUC offline but 0.70 in production. How do you investigate? || Look first for leakage and split mismatch: features using future data or the label, random rather than time splits, duplicates or the same user across splits. Then look for training-serving skew (features computed differently online), distribution shift between the offline period and now, and label delay. Re-run the evaluation with a strict time split and as-of-timestamp features to see if the offline score drops.
Why is k-fold cross-validation's variance estimate unreliable? || The k training sets overlap heavily (each pair shares k − 2 folds), so the k scores are positively correlated, and the naive standard error of the mean underestimates the true variance. Bengio and Grandvalet showed there is no universal unbiased estimator. Use repeated cross-validation or a corrected resampled t-test, and treat small differences with caution.
How would you split data for a model that predicts which users will churn next month? || Use a time-based design with an observation date: build features from the period before the date and the label from the month after it; train on earlier observation dates and test on later ones. Keep each user in only one split, or at least ensure the same user's later labels do not appear in training for an earlier date. Leave a gap if features use rolling windows.
When is leave-one-out preferable to 10-fold? || When n is very small, or when a closed form exists, for example the hat-matrix formula for least squares or ridge, where all n scores come from one fit. Otherwise its n training sets nearly coincide, so the scores are highly correlated, the variance is high and it costs n fits.
You ran 300 experiments against the same validation set. What is wrong and how do you fix it? || The best validation score is the maximum of many noisy estimates, so it is biased high; you have effectively tuned to the validation rows. Evaluate the final candidate on a fresh, locked test set or newer time period, use nested cross-validation or a reusable-holdout method, and reduce the number of peeks.
How do you split data when labels arrive late, such as conversions seven days after a click? || Define a label-maturity cutoff: only use rows whose label window has closed, so the most recent seven days are excluded from training and evaluation, or treat them with a delayed-feedback model. Put the validation period after the training period with a gap of at least the delay, so no training label uses information from the validation period.

@@ regression
value: Linear regression predicts a number as a weighted sum of input features: for example, expected revenue from an ad impression as a base value plus a weight for each feature. Logistic regression predicts a probability: it takes the same weighted sum and passes it through a sigmoid curve, which squeezes any number into the range 0 to 1. Both are fitted by choosing the weights that make the observed data most likely or least wrong. They are the simplest models that learn from data, and they are the baseline against which every other model is measured.
They remain important in production for three reasons. First, they are cheap to train and to serve: a prediction is one dot product, a few hundred nanoseconds even with hundreds of features. Second, each weight has a meaning: it says how much the prediction moves when that feature increases by one unit, which makes the model easy to debug and to explain to a regulator or a business owner. Third, with the right engineering they scale to enormous sparse feature spaces. For years the click-through-rate (CTR) models of large ad systems were logistic regression over billions of sparse features such as "site × ad × hour", trained online. Google's 2013 paper "Ad Click Prediction: a View from the Trenches" describes exactly this setup.
The layers below explain why the models are so well behaved. Optimization (L4) provides the ways to find the weights: closed form for least squares and iterative methods such as Newton's method and gradient descent for the others. Linear algebra (L4) turns the least-squares problem into the matrix equation XᵀXβ = Xᵀy. Probability (L4) says what the models mean: linear regression is maximum likelihood under Gaussian noise, logistic regression is maximum likelihood under Bernoulli noise, and the generalized linear model (GLM) family covers other noise types, such as Poisson counts. Convexity (L4) gives the guarantee that matters most in practice: the loss has no local minima, so any reasonable optimizer finds the single best answer, and you can train the model again tomorrow and get the same result.
terms: Feature — one numeric input to the model, such as the hour of day or a 0/1 flag for "device is a smart TV".
Weight (coefficient) — the number multiplied by a feature; the model's learned knowledge is the set of weights plus a bias (intercept).
Least squares — choose the weights that minimize the sum of squared differences between predictions and true values.
Sigmoid (logistic function) — σ(z) = 1 / (1 + e^(−z)); it maps any real number z to a value between 0 and 1.
Log-odds (logit) — log(p / (1 − p)); logistic regression makes this quantity a linear function of the features.
Cross-entropy (log loss) — the loss −[y·log p + (1 − y)·log(1 − p)] that logistic regression minimizes; it is the negative log-likelihood of the labels.
Link function — the function that connects the linear score to the mean of the outcome in a GLM (identity for linear, logit for logistic, log for Poisson).
Regularization — a penalty on the size of the weights (L2: sum of squares; L1: sum of absolute values) that reduces overfitting.
Calibration — the property that among cases predicted at 3% probability, about 3% really are positive.
history: The method of least squares was published by Adrien-Marie Legendre in 1805 for fitting planetary orbits, and Carl Friedrich Gauss published it in 1809 and claimed he had used it since 1795. Gauss also connected it to the normal distribution of errors, which is the probabilistic reading we still use. The word "regression" comes from Francis Galton in the 1880s, who noticed that the children of very tall parents are on average shorter than their parents, so heights "regress" towards the mean; the name stuck even though the method is general.
The logistic curve was introduced by Pierre-François Verhulst in 1838 for population growth. It entered statistics as a model for yes/no outcomes in the 1940s (Joseph Berkson coined the word "logit" in 1944, as a counterpart to the older "probit") and became standard after David Cox's 1958 paper on the regression analysis of binary sequences. In 1972, John Nelder and Robert Wedderburn unified linear, logistic, Poisson and other models as generalized linear models, with one fitting algorithm, iteratively reweighted least squares. McCullagh and Nelder's 1989 book is the standard reference.
Regularization arrived in the same period: Hoerl and Kennard proposed ridge regression in 1970 to stabilize the fit when features are correlated, and Robert Tibshirani's lasso (1996) added the L1 penalty, which sets many weights exactly to zero. The 2000s and 2010s were about scale. Feature hashing (Weinberger and co-authors, 2009) mapped unlimited categorical values into a fixed-size vector. Vowpal Wabbit and, at Google, the FTRL-Proximal online algorithm (McMahan et al., KDD 2013) trained logistic regression on streaming ad data with per-feature learning rates and L1 sparsity, so a model with a huge number of potential features could be stored in memory and served in microseconds.
how: Start with linear regression. Given n examples, put the features into a matrix X with n rows and d columns (usually with a column of ones for the intercept) and the targets into a vector y. The prediction is ŷ = Xβ, and the loss is the sum of squared errors, ‖y − Xβ‖². Setting the derivative to zero gives the normal equations, XᵀXβ = Xᵀy, so β = (XᵀX)⁻¹Xᵀy when XᵀX is invertible. This is the linear algebra at work: the fitted values Xβ are the projection of y onto the column space of X, and the residual is perpendicular to every feature column. The cost is about O(nd² + d³). In practice, numerical libraries do not invert XᵀX, because forming it squares the condition number; they use a QR or SVD factorization instead. When d is very large, they use gradient descent (the optimization concept) and never form the matrix.
Probability gives the same answer a second meaning. If y = Xβ + noise, with noise normally distributed with constant variance, then the likelihood of the data is largest exactly when the squared error is smallest. So least squares is maximum likelihood estimation under Gaussian noise. This matters because it shows how to change the model when the noise is not Gaussian.
Logistic regression uses that idea for yes/no labels. The model says P(y = 1 | x) = σ(w·x + b). The label is Bernoulli with that probability, so the log-likelihood of the data is Σ [yᵢ log pᵢ + (1 − yᵢ) log(1 − pᵢ)], and we minimize its negative, the cross-entropy. There is no closed form, but the gradient is wonderfully simple: for each weight, ∂loss/∂wⱼ = Σ (pᵢ − yᵢ) xᵢⱼ, which is "prediction minus truth, times the feature". Gradient descent or stochastic gradient descent (one example or a small batch at a time) uses this directly. Newton's method uses the second derivative, XᵀWX with W = diag(p(1 − p)), and each Newton step is a weighted least-squares problem; this is the iteratively reweighted least squares (IRLS) algorithm and typically converges in 5 to 10 iterations. Convexity is the reason it works: the Hessian is positive semi-definite, so the loss is convex, there is one global minimum, and gradient methods cannot get stuck. (If the classes are perfectly separable, the best weights are infinite, and regularization is what keeps them finite.)
The interpretation of the weights is clean. In logistic regression, the log-odds is linear in the features, so adding 1 to feature j adds wⱼ to the log-odds, which multiplies the odds by e^wⱼ. A weight of 0.69 doubles the odds. At a base CTR of 1 percent (odds 0.0101), doubled odds are 0.0202, a CTR of 1.98 percent: for small probabilities, doubling the odds almost doubles the probability.
Generalized linear models make this a recipe. Choose a noise distribution from the exponential family and a link function g so that g(mean) = w·x + b: Gaussian with identity link gives linear regression; Bernoulli with logit link gives logistic regression; Poisson with log link gives a model for counts (impressions per hour) in which the mean is exp(w·x + b), so effects multiply. Because they are all in the exponential family, the same IRLS algorithm and the same convexity argument apply to all of them. Multi-class logistic regression (softmax regression) is the same idea with one score per class; it is also the final layer of most neural classifiers.
Regularization controls overfitting. L2 (ridge) adds λ‖w‖² to the loss, shrinks all weights smoothly and makes XᵀX + λI always invertible. L1 (lasso) adds λ‖w‖₁, which sets many weights to exactly zero and so does feature selection. Both come from probability: L2 is a Gaussian prior on the weights and L1 is a Laplace prior (MAP estimation). For huge sparse inputs, feature hashing sets a feature's index to hash(name) mod 2²⁴, so you never keep a dictionary of feature names; crossing features (for example, site × ad) lets a linear model represent interactions that it cannot discover by itself.
Two practical checks complete the picture. For linear regression, the share of variance explained, R² = 1 − SSE/SST, compares the fit with the trivial model that always predicts the mean (in the example below, SST = 4.67 and SSE = 0.167, so R² ≈ 0.96). The covariance of the fitted weights is σ²(XᵀX)⁻¹, so the standard error of each weight shrinks as 1/√n and grows when features are correlated, which is how the data tells you which weights are poorly determined. For logistic regression, the matching checks are log loss on held-out rows and a calibration table, because the model is used for its probabilities and not only for its ranking.

example: First, linear regression by hand. Take three points (x, y): (1, 2), (2, 3), (3, 5). The means are x̄ = 2 and ȳ = 10/3 ≈ 3.333. The slope is Σ(x − x̄)(y − ȳ) / Σ(x − x̄)². The numerator is (−1)(−1.333) + 0 + (1)(1.667) = 3, and the denominator is 1 + 0 + 1 = 2, so the slope is 1.5. The intercept is 3.333 − 1.5 × 2 = 0.333. The predictions are 1.833, 3.333 and 4.833, so the residuals are 0.167, −0.333 and +0.167. They add up to zero, and the sum of squared errors is 0.0278 + 0.1111 + 0.0278 = 0.167. No other straight line has a smaller sum.
Now one step of logistic regression by hand. One feature x (say, the number of ads this user saw today) and a label y = 1 (clicked). Start with w = 0.8 and b = −2. For x = 3, the score is z = 0.8 × 3 − 2 = 0.4, and the prediction is p = σ(0.4) = 1/(1 + e^(−0.4)) = 0.599. The loss is −ln(0.599) = 0.513. The gradient for w is (p − y) × x = (0.599 − 1) × 3 = −1.204, and for b it is (p − y) = −0.401. With a learning rate of 0.1, the new weights are w = 0.8 + 0.120 = 0.920 and b = −2 + 0.040 = −1.960. Now z = 0.920 × 3 − 1.960 = 0.801, p = σ(0.801) = 0.690, and the loss is 0.370. One small step moved the prediction for this example from 0.60 to 0.69, and the loss fell by about 28 percent. A real training run repeats this over millions of examples with different labels, so the weights settle where the average pull of the "clicked" and "not clicked" examples balances.
A practical detail with real numbers: ad data has 1 percent clicks, so teams often keep all positives and only 10 percent of negatives to speed up training. The model then learns inflated probabilities. If the negatives were kept at rate r = 0.1 and the model predicts p′ = 0.20, the corrected probability is p = r·p′ / (1 − p′ + r·p′) = 0.02 / (0.80 + 0.02) ≈ 0.0244, or 2.4 percent. Without this correction, an auction that multiplies the CTR by a bid would be off by a factor of 8.
intuition: Draw the best straight line (or S-curve) through the data, where each feature's weight says how hard it pushes the prediction up or down.
A linear model is a vote. Every feature casts a vote of its own size, the votes are added up, and the total is the prediction. For regression, the total is the answer. For classification, the total is a confidence score on an unbounded scale, and the sigmoid translates it into a probability: a very large positive total means near certainty of "yes", zero means 50/50, a very negative total means near certainty of "no".
Why is this natural? Adding is the simplest way to combine evidence, and in logistic regression the addition has a meaning. Each independent piece of evidence multiplies the odds by a fixed factor, and the logarithm turns multiplication into addition. This is Bayes' rule in disguise (the naive Bayes classifier is a logistic regression with a particular way to set the weights). Convexity then adds a final practical comfort: because the loss is a bowl, you can always roll downhill to the one best answer.
mistakes: People often think "linear" means the model can only draw straight lines. In fact it is linear in the weights, not in the raw inputs. If you add features such as x², log x, or "site × ad", the model becomes curved in the original space and is still a linear model. Much of classical CTR work was feature engineering for exactly this reason.
People often think the weights of a linear model show which features are most important. In fact weights depend on the scale of the features and on correlation between features. If two features carry the same signal, the model can split the weight between them in any proportion (or give a huge positive weight to one and a huge negative to the other), so the individual numbers become unstable. Standardize features before comparing weights, and be careful about causal claims.
People often think a logistic regression output is always a trustworthy probability. In fact it is calibrated only if the model is roughly right and the training data looks like the data you predict on. Downsampling negatives, class weights, strong regularization and distribution shift all distort it. Where the probability is used (bid = value × predicted CTR), check calibration with a reliability plot and correct it.
People often think accuracy is the right way to judge logistic regression. In fact with 1 percent positives, a model that always says "no" has 99 percent accuracy. Use log loss, AUC or precision/recall at the operating point, and judge by what the decision costs.
People often think the regression in logistic regression is a historical accident and the method is a classifier. In fact it estimates a probability, and the classification is a separate decision made by comparing that probability to a threshold chosen from costs and benefits.
friction: Linear models cannot discover interactions or non-linear effects by themselves. If CTR depends on "this ad on this site at this hour", you must create that cross feature, or the model will miss it. This is the reason that gradient-boosted trees and deep networks took over many tasks with dense, rich features: they learn the interactions, at the cost of interpretability and more expensive serving. Facebook's 2014 work combined the two, using boosted trees to create features for a logistic regression.
Correlated features (multicollinearity) make the weights unstable and the standard errors large, though predictions can still be fine. Outliers hurt least squares badly because errors are squared: one wrong value of 1,000 contributes as much as 100 values that are off by 100. Robust losses (Huber) or clipping help. Perfectly separable classes push the logistic weights to infinity, and a regularizer is needed. Categorical features with millions of values need hashing or embeddings, and hashing creates collisions.
Calibration drifts. Models trained on yesterday's traffic meet today's, with new campaigns and seasons, so the average prediction no longer matches the average outcome. Production systems monitor predicted-versus-actual CTR and retrain often, or learn online. For GLMs, the assumption of a particular noise distribution matters: Poisson assumes variance equals the mean, and real count data usually has more variance (overdispersion), which makes the standard errors too small unless you use a negative binomial or robust errors.
There is also a statistical-practice problem: with hundreds of features and small data, a linear model fits noise. Regularization strength and feature selection need cross-validation on a time-respecting split, and p-values from classical regression are unreliable after you have tried many features.
practice: Always train a linear model first. It gives a baseline in an hour, and if a deep model cannot beat it clearly, the deep model is not worth its cost. Standardize numeric features (mean 0, variance 1) before using regularization, otherwise the penalty treats features unequally. Use L2 by default; use L1 or elastic net when you need a sparse, small model. Choose the strength λ by cross-validation using a time-based split, and report log loss, not only accuracy.
For ad and recommendation data, use one-hot encoding or feature hashing for categorical values (2²² to 2²⁴ buckets is common), add a small number of well-chosen cross features, and train with an online algorithm such as FTRL-Proximal or with SGD. Libraries to know: scikit-learn's LogisticRegression and SGDClassifier, Spark MLlib's LogisticRegression (L-BFGS, distributed over a cluster), Vowpal Wabbit for huge sparse streams, and statsmodels when you need coefficient tables and confidence intervals.
Check the calibration. Plot the mean predicted probability against the observed rate in 10 or 20 buckets, and fix gaps with Platt scaling or isotonic regression, or by correcting for negative downsampling with p = r·p′ / (1 − p′ + r·p′). For counts, use Poisson (or negative binomial) regression with a log link instead of transforming the target. For interpretation, report odds ratios e^w for logistic models, and get confidence intervals before you act on them. When you need more power, keep the linear model as a fallback and as a feature (its score can be an input to a tree model), and compare every new model against it on the same split.

tradeoffs: Choose a linear or logistic model when the data is small (thousands to a few million rows), when you need to explain each prediction, when you must serve in microseconds on cheap hardware, or when the features are already informative. Choose gradient-boosted trees or a neural network when there are many interactions and enough data (millions of rows or more) to learn them; they commonly gain several percent in log loss or AUC on rich tabular data but cost more to train, serve and explain.
Choose L2 regularization when many features carry a little signal each and you want stable weights; choose L1 when you believe only a small subset of thousands of features matters, or when you need a small model (L1 can zero out 90 percent or more of the weights). Elastic net, a mix of the two, is the choice when correlated features make pure L1 pick arbitrary ones. You give up some fit to gain stability or sparsity.
Choose the closed-form or QR solution when d is under a few thousand and the data fits in memory: it is exact and needs no learning rate. Choose SGD or FTRL when n or d is huge or data streams in; it processes each row once, uses little memory, and can be updated hourly, but it needs a learning-rate schedule and gives an approximate answer.
Choose one-hot features with a dictionary when the vocabulary is small and stable (hundreds of values), and feature hashing when it is huge or unbounded (millions of IDs). Hashing removes the dictionary and the memory problem, at the cost of collisions (at 2²⁴ buckets and 1 million active features, about 6 percent of features share a bucket with another) and of not being able to read back feature names without extra bookkeeping.
Choose a GLM with the matching distribution (Poisson, Gamma, Tweedie) over transforming the target when the outcome is a count, a duration or a skewed non-negative amount. Log-transforming and then fitting least squares gives the median-like effect on the log scale, while a log-link GLM models the mean on the original scale; for revenue forecasts the mean is what you need.
interview: Derive the gradient of the logistic loss and explain why it has such a simple form. || With p = σ(z) and σ′ = σ(1 − σ), the derivative of −[y ln p + (1 − y) ln(1 − p)] with respect to z collapses to p − y. By the chain rule, the gradient for weight j is (p − y)·xⱼ. The simplicity comes from the logit being the natural parameter of the Bernoulli distribution, which is true for every GLM with a canonical link.
Why not use squared error for classification with a sigmoid output? || The loss becomes non-convex in the weights, and the gradient has a factor σ′(z) that vanishes when the model is confidently wrong, so learning stalls exactly when it should correct most. Cross-entropy is convex and its gradient stays proportional to the error.

value: A support vector machine (SVM) is a classifier that separates two classes with a boundary chosen to leave the widest possible empty gap, called the margin, between the boundary and the nearest training points. Only those nearest points, the support vectors, decide where the boundary goes; all other points could be removed and the boundary would not move. The kernel trick then lets the same method draw curved boundaries: instead of working with the raw features, the SVM works with a similarity function k(x, z) that equals an inner product in a much larger feature space, and it never builds that space.
From about 1995 to 2012, SVMs were the strongest general-purpose classifier for medium-size data: text classification, handwritten digits, bioinformatics, and early image recognition (with hand-built features) were all dominated by them. Deep learning replaced them on images, speech and text, and gradient-boosted trees replaced them on most tabular data, but SVM ideas did not disappear. Maximum margin, the hinge loss, convex training with a guarantee of a global optimum, duality, and the view of a model as a sum of kernel functions centred on training points all appear in modern machine learning, and some analyses of attention in transformers use exactly this kernel view.
The layers below make the method possible. Convexity (L4) is why training is reliable: maximizing the margin is a convex quadratic program, so there is one global optimum and no tuning of initial values. Linear algebra (L4) supplies the inner products and the idea that a kernel is a Gram matrix of inner products in a hidden space. Linear programming and duality (L4) supply the central trick of training: the problem is solved in its dual form, where the data appears only through inner products, which is what allows a kernel to be substituted.
terms: Hyperplane — the flat boundary w·x + b = 0 in feature space; points on one side are class +1, on the other side class −1.
Margin — the distance between the hyperplane and the closest training points; for a scaled hyperplane it is 2/‖w‖.
Support vector — a training point that lies on or inside the margin; it has a non-zero dual weight and defines the boundary.
Hinge loss — max(0, 1 − y·f(x)); zero for points correctly classified beyond the margin, and growing linearly for points inside the margin or on the wrong side.
Soft margin and C — the penalty C for margin violations; large C punishes errors strongly (narrow margin), small C tolerates errors (wide margin).
Kernel — a function k(x, z) that equals the inner product φ(x)·φ(z) of some feature map φ, without computing φ.
RBF (Gaussian) kernel — k(x, z) = exp(−γ‖x − z‖²), a similarity that is 1 for identical points and falls to 0 with distance; its feature space is infinite-dimensional.
Dual problem — the equivalent optimization over one weight αᵢ per training point; it uses data only through inner products.
Gram matrix — the n × n matrix of all kernel values k(xᵢ, xⱼ).
history: The linear form of the idea comes from Vladimir Vapnik and Alexey Chervonenkis in 1963, as part of their statistical learning theory: a classifier with a large margin has low capacity, so it should generalize. The kernel idea is older still: Aizerman, Braverman and Rozonoer (1964) used kernels as "potential functions", and Mercer's theorem (1909) says which functions are valid kernels (those whose Gram matrices are positive semi-definite). But for decades the two lines of work were not joined, and linear classifiers on small data were the norm.
In 1992 Bernhard Boser, Isabelle Guyon and Vapnik, working at AT&T Bell Labs, combined them: a maximum-margin classifier in the dual form, with kernels replacing inner products. The motivation was handwritten digit recognition, where neural networks were the competitor. In 1995 Corinna Cortes and Vapnik added the soft margin, which allows some errors, and made the method usable on noisy data; their paper "Support-Vector Networks" gave the method its name. Vapnik's 1995 book "The Nature of Statistical Learning Theory" connected it to generalization bounds.
The practical turning point was software. John Platt's sequential minimal optimization (SMO, 1998) solved the dual by optimizing two weights at a time with a closed-form update, which avoided heavy quadratic-programming code. LIBSVM (Chang and Lin, 2001 onward) became the reference implementation. For large sparse data, linear SVM solvers followed: SVM-perf, Pegasos (Shalev-Shwartz et al., 2007) and LIBLINEAR (Fan et al., 2008), which train on millions of documents in minutes. Random Fourier features (Rahimi and Recht, 2007) approximated kernels with an explicit low-dimensional map. After 2012, deep networks overtook kernel methods on perception tasks, which had relied on the same labelled-data growth that SVMs could not use well, because of their super-linear training cost.
how: Take training data (xᵢ, yᵢ) with labels yᵢ = ±1. A linear classifier is f(x) = w·x + b, predicting the sign of f. If the data is linearly separable, there are infinitely many separating hyperplanes. The SVM picks the one with the largest margin. Scale w and b so that the closest points have yᵢ f(xᵢ) = 1; the margin is then 2/‖w‖, so maximizing the margin means minimizing ½‖w‖² subject to yᵢ(w·xᵢ + b) ≥ 1 for all i. The objective is a convex quadratic and the constraints are linear, so this is a convex quadratic program with a single global optimum (this is the convexity concept doing its job).
Real data has overlap and noise, so the soft-margin version allows slack ξᵢ ≥ 0 per point: minimize ½‖w‖² + C Σ ξᵢ subject to yᵢ(w·xᵢ + b) ≥ 1 − ξᵢ. Equivalent to minimizing ½‖w‖² + C Σ max(0, 1 − yᵢ f(xᵢ)): a regularizer (the margin) plus the hinge loss. This is the same pattern as regularized logistic regression, with a different loss. The hinge loss is exactly zero for any point that is correct with a margin of at least 1, so most points contribute nothing to the gradient, which is the reason the solution is sparse in the training points.
Now the key step, from duality. Introduce a Lagrange multiplier αᵢ for each constraint and eliminate w and b. The result is the dual problem: maximize Σ αᵢ − ½ Σᵢ Σⱼ αᵢ αⱼ yᵢ yⱼ (xᵢ·xⱼ), subject to 0 ≤ αᵢ ≤ C and Σ αᵢ yᵢ = 0. Two facts matter. First, the training points appear only through inner products xᵢ·xⱼ. Second, complementary slackness from the optimality conditions (as in linear-programming duality) says that αᵢ = 0 for every point strictly outside the margin. The points with αᵢ > 0 are the support vectors, and w = Σ αᵢ yᵢ xᵢ is a combination of them alone. The prediction for a new point is f(x) = Σ αᵢ yᵢ (xᵢ·x) + b, summed over support vectors.
The kernel trick follows: since data only enters through inner products, replace each xᵢ·xⱼ with k(xᵢ, xⱼ) = φ(xᵢ)·φ(xⱼ). This is the same as running a linear SVM in the feature space φ, but φ is never computed. For the polynomial kernel k(x, z) = (x·z)² on 2-D inputs, φ(x) = (x₁², √2 x₁x₂, x₂²), and the kernel computes the 3-D inner product with one 2-D dot product and a square. For the RBF kernel exp(−γ‖x − z‖²), φ has infinitely many dimensions, which is impossible to build but trivial to evaluate. The kernel must be valid (symmetric and positive semi-definite, per Mercer), which also keeps the dual problem convex. The prediction becomes f(x) = Σ αᵢ yᵢ k(xᵢ, x) + b: a weighted vote of similarities to the support vectors, where RBF with large γ makes each vote local and small γ makes it broad.
Training solves the dual. SMO picks two multipliers, optimizes them analytically while holding the rest fixed (the constraint Σ αᵢ yᵢ = 0 forces them to move together), and repeats with heuristics for choosing the pair, until the optimality conditions hold within a tolerance. It needs rows of the Gram matrix on demand, and caches the recently used ones. The cost is between O(n²) and O(n³) for n training points in practice, and memory for the full Gram matrix is 8n² bytes (80 GB for n = 100,000), so kernel SVMs are used up to roughly 10⁵ to 10⁶ points. Prediction costs one kernel evaluation per support vector, which can be a large part of the data if classes overlap. For huge, sparse, high-dimensional data (text), the data is often already linearly separable enough, and a linear SVM trained with stochastic subgradient descent or dual coordinate descent costs O(nnz) per pass, where nnz is the number of non-zero feature values.
Why does the maximum margin generalize? Statistical learning theory (L4) bounds the error in terms of margin and the radius of the data, not the number of dimensions, so very high-dimensional feature spaces can be fine. A simple related fact: for the hard-margin SVM, the leave-one-out error is at most the fraction of points that are support vectors. If only 5 percent of the points are support vectors, the leave-one-out error is at most 5 percent.

example: First, the kernel trick with numbers. Let x = (1, 2) and z = (3, 1) and use the kernel k(x, z) = (x·z)². The direct computation is x·z = 1×3 + 2×1 = 5, and 5² = 25. Using the explicit map φ(x) = (x₁², √2 x₁x₂, x₂²): φ(x) = (1, 2.828, 4) and φ(z) = (9, 4.243, 1), and their inner product is 1×9 + 2.828×4.243 + 4×1 = 9 + 12 + 4 = 25. The same number, but the kernel needed one 2-D dot product and a square, while the map needed three dimensions. With the RBF kernel the map has infinite dimensions, and the kernel still costs one distance: for ‖x − z‖² = 2 and γ = 0.5, k = e^(−1) = 0.37.
Now a complete tiny problem in one dimension. The positive class is at x = −1 and x = 1; the negative class is at x = −3 and x = 3. No threshold on x separates them. Lift with φ(x) = (x, x²): positives become (−1, 1) and (1, 1), negatives become (−3, 9) and (3, 9). Now the horizontal line x² = 5 separates them. As a hyperplane, w = (0, −0.25) and b = 1.25 gives f = 1.25 − 0.25x², which is +1 at x² = 1, 0 at x² = 5 and −1 at x² = 9. The margin 2/‖w‖ = 2/0.25 = 8 (a half-width of 4 on each side), and all four points lie exactly on the margin, so all four are support vectors. In the original line, the decision rule is "positive if |x| < √5 ≈ 2.24", a curved boundary obtained from a linear one.
Finally, the effect of C and γ, as a reasoning exercise. Suppose you train an RBF SVM on 20,000 labelled documents in which about 10 percent of the labels are wrong. With a very large C and a large γ, every training point can get its own small island of influence. Training accuracy reaches 100 percent, nearly every point becomes a support vector, and held-out accuracy falls, because the model has memorized the wrong labels. With a moderate C and a small γ, the boundary is smooth, training accuracy is lower, only a minority of points are support vectors, and held-out accuracy is higher. A grid search over C = 2⁻⁵ … 2¹⁵ and γ = 2⁻¹⁵ … 2³ on a log scale (the grid recommended in Hsu, Chang and Lin's practical guide) with 5-fold cross-validation finds the best pair. That grid has 21 × 19 = 399 cells, and with 5 folds it needs about 2,000 training runs, which is why the search is usually coarse first, then refined.
intuition: If you cannot separate the points with a line, lift them into a space where a flat sheet can, and pick the sheet with the most room on both sides.
Think of a fence between two groups of people in a field. Many fences would work, but a fence that passes very close to some people is risky: if anyone moves a little, they end up on the wrong side. The safest fence is the one furthest from everybody, and it is held up by the few people standing closest to it, the support vectors. The rest of the crowd could leave and the fence would not move.
The kernel trick is natural for a different reason. Most learning algorithms only need to know how similar two examples are. If you can write the algorithm so that examples are touched only through a similarity function, then you can change the similarity function to change the geometry of the problem, and nothing else in the algorithm needs to change. A kernel is a similarity that is guaranteed to be an inner product in some space, so all the geometry (distances, margins, convexity) still holds there.
mistakes: People often think the kernel trick makes the data separable by magic. In fact it only gives access to a richer family of boundaries. Whether the data becomes separable depends on whether the kernel's feature space contains a good separator, and with a very rich kernel (RBF with large γ) any training set becomes separable by memorizing it, which gives perfect training accuracy and poor held-out accuracy.
People often think all training points matter equally to an SVM. In fact only the support vectors do. Points far from the boundary on the correct side have dual weight zero. This is why the model can be small after training, and also why a single mislabelled point near the boundary can change the result a lot.
People often think SVM outputs are probabilities. In fact f(x) is a signed distance-like score and has no probabilistic meaning. To get probabilities, fit a sigmoid to the scores on held-out data (Platt scaling), which LIBSVM can do with an extra cross-validation step. Do not use raw scores as probabilities in an auction or a risk model.
People often think SVMs do not need feature scaling. In fact the margin and kernels are based on distances, so a feature measured in thousands dominates one measured in fractions. Standardize features first. Forgetting this is the most common reason for poor SVM results.
People often think SVMs are obsolete. In fact linear SVMs (and linear logistic regression) remain fast, strong baselines for sparse high-dimensional data such as text, and the ideas are widely reused. Kernel SVMs are rarely the first choice now only because of their scaling with the number of examples.
friction: The main limit is scale. The dual has one variable per training point, and the kernel matrix has n² entries. Training time grows roughly between n² and n³, so a kernel SVM that takes a minute on 10,000 rows takes hours or days on 1,000,000 rows. Prediction is also slow if there are many support vectors, since each prediction needs one kernel evaluation per support vector. Approximations (random Fourier features, the Nyström method, budgeted SVMs) trade accuracy for speed, but at that point a linear model on explicit features or a neural network is usually simpler.
Hyperparameters are sensitive. C and γ interact, the good region is narrow on a log scale, and the grid search with cross-validation multiplies the cost by the grid size times the number of folds (for example 20 × 20 × 5 = 2,000 trainings). The kernel itself has to be chosen by hand, and the best kernel depends on the problem; learning the kernel (multiple kernel learning) was tried but is complex. There is no learned representation: an SVM is only as good as the features or the kernel it is given, which is the reason deep networks, which learn features, won on images, audio and text.
There is no native probability output, no natural handling of multiple classes (it is built from one-vs-one or one-vs-rest combinations), no handling of missing values, and imbalanced data needs class-specific C values. The solution is sensitive to label noise near the boundary: the hinge loss is linear in the violation, so a few mislabelled points with large violations pull the boundary. Finally, the model is hard to inspect when there are thousands of support vectors in an implicit feature space.
practice: Use a linear SVM (LIBLINEAR, scikit-learn's LinearSVC or SGDClassifier with hinge loss) first for text and other sparse, high-dimensional data; it trains in seconds to minutes on millions of rows and is often as accurate as anything else. Use an RBF kernel SVM (LIBSVM, scikit-learn's SVC) when you have under about 50,000 to 100,000 rows, dense features of moderate dimension, and no better representation. Always standardize features (or use TF-IDF with length normalization for text).
Tune on a logarithmic grid: C from 2⁻⁵ to 2¹⁵ and γ from 2⁻¹⁵ to 2³ is the classic starting point from Hsu, Chang and Lin's "A Practical Guide to Support Vector Classification". First search coarsely, then refine around the best cell, using cross-validation with the right split (by time or by group where needed). Watch the fraction of support vectors: if it is above roughly 50 percent, the model is memorizing or the features are poor. For imbalanced classes, set class weights (class_weight="balanced"), and judge by precision/recall or AUC, not accuracy.
If you need probabilities, calibrate the scores with Platt scaling or isotonic regression on held-out data. If you need to scale up, try an explicit approximation (Nyström or random Fourier features followed by a linear SVM) before abandoning the method. And when you read about attention, retrieval, Gaussian processes or kernel ridge regression, look for the same pattern: a prediction that is a weighted sum of similarities to stored examples, which is what an SVM is.
quiz: What is the margin in an SVM and what are support vectors? || The margin is the gap between the separating hyperplane and the nearest training points, equal to 2/‖w‖ when scaled so the nearest points have y·f(x) = 1. Support vectors are the training points on or inside the margin; they have non-zero dual weights and alone determine the boundary.
Why does solving the dual problem make the kernel trick possible? || In the dual, the training data appears only through inner products xᵢ·xⱼ. Replacing each by a kernel k(xᵢ, xⱼ) = φ(xᵢ)·φ(xⱼ) runs the same algorithm in the feature space φ without ever computing φ, and prediction is Σ αᵢ yᵢ k(xᵢ, x) + b.
What do large C and large γ do to an RBF SVM? || Large C punishes margin violations heavily, so the margin narrows and the model fits the training data closely. Large γ makes each point's influence very local, so the boundary becomes very wiggly. Both increase overfitting risk; small values give a smoother, simpler boundary.
For x = (1, 2) and z = (3, 1), what is the polynomial kernel (x·z)², and what does it equal in feature space? || x·z = 5, so the kernel is 25. It equals the inner product of φ(x) = (x₁², √2x₁x₂, x₂²) and φ(z): 9 + 12 + 4 = 25, computed without building φ.
You have 5 million documents with 2 million sparse TF-IDF features. Would you use an RBF-kernel SVM? || No. The Gram matrix would have 25 trillion entries, and training scales at least quadratically. Use a linear SVM (LIBLINEAR or SGD with hinge loss), which costs O(nnz) per pass and is usually about as accurate on high-dimensional sparse text.
tradeoffs: Choose a linear SVM when the data is sparse and high-dimensional (text, one-hot ad features) or when n is in the millions; it trains in minutes and serves as a dot product. Choose a kernel SVM when n is below about 100,000, features are dense and few (tens to hundreds), and the problem has a smooth non-linear boundary. You give up scalability for flexibility.
Choose an SVM over logistic regression when you care mainly about the decision boundary and not about probabilities, and when data is small with many features (the margin acts as a strong regularizer). Choose logistic regression when you need calibrated probabilities (bidding, risk scores), online updates, or easy multi-class output; its log loss gives probabilities directly, while the hinge loss gives only a score.
Choose gradient-boosted trees over a kernel SVM for tabular data with mixed types, missing values and different scales: trees need no scaling, handle categories and missing values, and usually win in accuracy. Choose a deep network over an SVM when you have more than about a million examples of raw signals (pixels, audio, text), where learned features beat any hand-picked kernel.
Choose the RBF kernel as the default non-linear kernel, with a polynomial kernel only when you believe in interactions of a fixed degree, and a custom kernel (string kernels, graph kernels) when your data is structured and you can define a similarity but not a vector. The cost of a custom kernel is that you must keep it positive semi-definite, and each evaluation can be expensive.
Choose approximations (random Fourier features, Nyström with 1,000 to 10,000 landmarks) when you want a kernel-like boundary at linear-model cost: you lose a little accuracy and gain training time that is linear in n.
interview: Explain why the SVM solution depends only on support vectors, and what that means for generalization. || Complementary slackness from the dual gives αᵢ(yᵢ f(xᵢ) − 1 + ξᵢ) = 0, so αᵢ = 0 whenever a point is strictly outside the margin. The weight vector is a combination of support vectors only. For the hard-margin case, the leave-one-out error is at most the fraction of support vectors, so few support vectors indicates good generalization.
Why is the hinge loss used instead of the 0-1 loss? || The 0-1 loss is not convex and not differentiable, so minimizing it is NP-hard in general. The hinge loss is a convex upper bound on it, which makes training a convex problem with a global optimum, and the margin term gives regularization. The cost is sensitivity to points with large violations and no probabilistic meaning.
How do C and γ control the bias-variance trade-off? || Small C and small γ give a smooth, nearly linear boundary: high bias, low variance. Large C and large γ give a flexible boundary that follows the training points: low bias, high variance. They interact, so tune both together on a log grid with cross-validation.
What makes a function a valid kernel, and why does it matter? || It must be symmetric and give a positive semi-definite Gram matrix for any set of points (Mercer's condition); then it equals an inner product in some feature space. If it is not, the dual loses convexity and the solver can diverge or return meaningless results.
Your SVM is accurate but too slow at prediction time. What can you do? || Prediction cost is proportional to the number of support vectors. Reduce them with a larger margin (smaller C), prune or reduce the support set, use a budgeted SVM, or approximate the kernel with random Fourier features or Nyström and apply a linear model, which needs a single dot product.
Why did kernel methods lose to deep learning on images, and where do they still make sense? || Kernel methods need fixed features or a fixed kernel and cost O(n²) or worse, so they cannot use millions of examples or learn representations. Deep networks learn features and scale with data. Kernels still make sense with small data, structured inputs with a natural similarity, Gaussian processes and as an analysis tool.

@@ clustering
value: Clustering is the task of finding groups in data when nobody has told you what the groups are. You have points (customers, TV households, documents, sensor readings, vectors) and a notion of distance, and you want to split them into groups so that points in a group are close to each other and far from the other groups. There are no labels, so there is no single right answer; the groups are useful if they help you decide something. Typical uses are audience segments for advertising, topic groups in a document collection, grouping of similar devices or sessions, finding anomalies as points that belong to no group, and compressing a large dataset to a few hundred or thousand representative points.
Two algorithms cover most practical needs. K-means is the simple one: it represents each cluster by its centre and assigns every point to the nearest centre. It is fast, it scales to hundreds of millions of points, and it appears inside other systems: IVF vector indexes use k-means to split a vector collection into cells and then search only the nearest cells, and product quantization uses k-means to build its codebooks. The Gaussian mixture model (GMM), fitted with the expectation-maximization (EM) algorithm, is the probabilistic version: each cluster is a bell-shaped distribution with its own centre and shape, and each point has a probability of belonging to each cluster instead of a single label.
The layers below give clustering its meaning and its guarantees. Geometry and metric spaces (L4) supply the distance: k-means is only as good as the distance function it uses, and the squared Euclidean distance is what makes "the mean of the points" the best centre. Probability (L4) supplies the soft memberships and the mixture-model view: a point is generated by first choosing a cluster and then drawing from its Gaussian. Convexity and Jensen's inequality (L4) supply the proof that every EM round improves the likelihood, which is why the algorithm is safe to run until it settles.
terms: Centroid — the mean of the points in a cluster; k-means represents each cluster by its centroid.
k — the number of clusters; in k-means you must choose it in advance.
Within-cluster sum of squares (WCSS, inertia) — the sum over all points of the squared distance to the assigned centroid; k-means tries to minimize it.
Mixture model — a distribution made of several component distributions, each chosen with some probability (the mixing weight πₖ).
Responsibility — in a mixture model, the probability that component k generated point i, computed by Bayes' rule; also called soft assignment.
E-step and M-step — the two alternating steps of EM: compute responsibilities with the current parameters (expectation), then re-estimate the parameters with those responsibilities as weights (maximization).
Local optimum — a solution that cannot be improved by small steps but is not the best overall; k-means and EM can end in one, depending on the starting point.
Silhouette score — a measure from −1 to 1 of how much closer a point is to its own cluster than to the next nearest cluster.
Hard vs soft clustering — hard gives each point exactly one cluster; soft gives it a probability for each.
history: The idea of grouping points by repeatedly averaging goes back to Hugo Steinhaus (1956). Stuart Lloyd, at Bell Labs, described the same algorithm in 1957 for pulse-code modulation, as a way to choose the best set of quantization levels for a signal; his report was only published in 1982, so the standard algorithm is still called Lloyd's algorithm. Edward Forgy (1965) and James MacQueen (1967) published versions, and MacQueen gave it the name "k-means". The motivation in signal processing and statistics was the same: summarize many measurements by a few representative values with the smallest total squared error.
The probabilistic line started with fitting mixtures of normal distributions, an old problem (Karl Pearson, 1894, fitted a mixture of two normals to crab measurements). The general method for fitting models with hidden variables, the EM algorithm, was named and analyzed by Arthur Dempster, Nan Laird and Donald Rubin in 1977. They showed that many earlier methods, including the Baum–Welch algorithm for hidden Markov models, were special cases and proved that the likelihood never decreases.
Later work addressed the practical weak points. Density-based DBSCAN (Ester and co-authors, KDD 1996) found clusters of any shape and treated sparse points as noise. Rousseeuw's silhouette (1987), the BIC criterion (Schwarz, 1978) and Tibshirani's gap statistic (2001) helped to choose k. David Arthur and Sergei Vassilvitskii's k-means++ (2007) chose starting centres by distance-weighted sampling and proved that the result is within a factor O(log k) of the optimum on average. D. Sculley's mini-batch k-means (2010) cut cost by using small random batches, and Bahmani and co-authors' k-means|| (2012) made the seeding parallel, which is the initialization used in Spark MLlib.
how: Start with k-means. The goal is to choose k centres μ₁ … μₖ and an assignment of each point to one centre so that the sum of squared distances, Σᵢ ‖xᵢ − μ_c(i)‖², is as small as possible. Finding the exact best answer is NP-hard, so the algorithm settles for a local optimum with two alternating steps. Step 1, assign: give each point to its nearest centre. Step 2, update: move each centre to the mean of the points assigned to it. Repeat until no assignment changes. Each step cannot increase the objective: for fixed centres, nearest-centre assignment is the best assignment; for a fixed assignment, the mean is the point that minimizes the sum of squared distances (this is the property of squared Euclidean distance that the metric-space concept provides). The objective can only go down, and there are finitely many assignments, so the algorithm must stop. Each iteration costs O(n·k·d) for n points of dimension d, which is a matrix multiplication in disguise and runs fast on GPUs and in vector libraries.
The starting point matters, because the algorithm only finds a local optimum. Choosing k random points often puts two centres in one real group. K-means++ fixes this: choose the first centre at random; then choose each next centre with probability proportional to the squared distance to the nearest centre already chosen, so far-away points are more likely. This spreads the centres out and, with a proof, keeps the final cost within an O(log k) factor of the best possible in expectation. In practice you also run several restarts and keep the lowest cost. To choose k, plot the cost against k (the "elbow" plot; the cost always falls as k rises, reaching zero at k = n, so look for where the gains flatten), or use the silhouette score or the BIC for a mixture model.
The Gaussian mixture model changes the picture from "points belong to a centre" to "points are generated by a mixture". The model says: pick component k with probability πₖ, then draw x from a Gaussian with mean μₖ and covariance Σₖ. The probability of a point is p(x) = Σₖ πₖ N(x | μₖ, Σₖ). The unknowns are all πₖ, μₖ and Σₖ, and we want to maximize the likelihood of the data. The difficulty is the sum inside the logarithm: there is no closed form because we do not know which component made each point (the hidden variable). EM solves this by alternating. The E-step uses Bayes' rule with the current parameters: the responsibility of component k for point i is rᵢₖ = πₖ N(xᵢ | μₖ, Σₖ) / Σⱼ πⱼ N(xᵢ | μⱼ, Σⱼ). The M-step then re-estimates each component as a weighted average, with the responsibilities as weights: Nₖ = Σᵢ rᵢₖ, μₖ = Σᵢ rᵢₖ xᵢ / Nₖ, Σₖ = Σᵢ rᵢₖ (xᵢ − μₖ)(xᵢ − μₖ)ᵀ / Nₖ, and πₖ = Nₖ / n.
Why does EM work? Jensen's inequality gives a lower bound on the log-likelihood that touches the true value at the current parameters. The E-step builds this bound (it makes the bound tight), and the M-step maximizes the bound, which can only push the true likelihood up. So the log-likelihood never decreases, and the process converges to a local optimum (or a saddle point). This is the convexity concept at work: the concavity of the logarithm is what produces the inequality.
K-means is a special case in disguise. If you take a GMM in which all components share the same spherical covariance σ²I and equal weights, and let σ² shrink to zero, the responsibilities become 0 or 1 (hard assignments), and the M-step for the mean becomes the k-means update. So k-means is "EM for spherical Gaussians with hard assignments". The GMM is richer: it can model elongated, rotated clusters (full covariance), clusters of different sizes (different πₖ), and it reports uncertainty. The price is more parameters (a full covariance has d(d + 1)/2 numbers per component), slower iterations, and an extra failure: if a component collapses onto a single point, its variance goes to zero and the likelihood goes to infinity, so implementations add a small value to the diagonal of Σₖ.
Other families fill the gaps. DBSCAN grows clusters from dense regions: a point with at least minPts neighbours within radius ε is a core point, and connected core points form a cluster, with the rest labelled noise; it needs no k and finds arbitrary shapes, but has two parameters and struggles when densities vary. Hierarchical (agglomerative) clustering starts with every point alone and repeatedly merges the closest pair of clusters, producing a tree (dendrogram) that you can cut at any level; it costs O(n²) memory and time in the usual implementation, so it suits thousands of points, not millions.

example: Run k-means by hand on six one-dimensional points: 1, 2, 4, 9, 10, 12, with k = 2 and a deliberately poor start: centres c₁ = 1 and c₂ = 2. Round 1, assign: the point 1 is at distance 0 from c₁ and goes to c₁. Point 2 is at distance 0 from c₂ and goes to c₂. Point 4 has distances 3 and 2, so it goes to c₂; the points 9, 10 and 12 also go to c₂. Cluster 1 is {1}, cluster 2 is {2, 4, 9, 10, 12}. Update: c₁ = 1, c₂ = (2 + 4 + 9 + 10 + 12)/5 = 37/5 = 7.4.
Round 2, assign: point 2 has distances 1 and 5.4, so it goes to c₁; point 4 has distances 3 and 3.4, so it goes to c₁ as well; the points 9, 10, 12 stay with c₂ (distances 1.6, 2.6, 4.6). Cluster 1 is {1, 2, 4}, cluster 2 is {9, 10, 12}. Update: c₁ = 7/3 = 2.33 and c₂ = 31/3 = 10.33. Round 3, assign: nothing changes (point 4 is 1.67 from c₁ and 6.33 from c₂; point 9 is 6.67 from c₁ and 1.33 from c₂). The algorithm stops. The cost: cluster 1 has (1 − 2.33)² + (2 − 2.33)² + (4 − 2.33)² = 1.78 + 0.11 + 2.78 = 4.67, cluster 2 has the same by symmetry, so the total is 9.33. The poor start cost one extra round, not a bad answer. On a harder dataset, a poor start could have trapped the algorithm in a worse solution, which is why you use k-means++ and restarts.
Now one EM step for a two-component, one-dimensional mixture with equal weights (0.5 each), equal variance σ² = 1, and means μ₁ = 3 and μ₂ = 8. Take the point x = 5. Its distance to μ₁ is 2 and to μ₂ is 3, so the unnormalized densities are proportional to e^(−2²/2) = e^(−2) = 0.1353 and e^(−3²/2) = e^(−4.5) = 0.0111. The responsibility of component 1 is 0.1353 / (0.1353 + 0.0111) = 0.924, and of component 2 is 0.076. Point x = 6 has the opposite result: 0.076 for component 1. A point at x = 1 gets a responsibility of nearly 1.0 for component 1. In the M-step, the new μ₁ is the responsibility-weighted mean of the data. Using only these three points: (1.0 × 1 + 0.924 × 5 + 0.076 × 6) / (1.0 + 0.924 + 0.076) = 6.076 / 2.0 ≈ 3.04. The mean moved only a little, because the points near it agree with it. Points like x = 5.5, which belong half to each cluster, pull both means a little towards each other; that is the soft behaviour that k-means does not have.
At scale: k-means with n = 10 million vectors of dimension 128 and k = 1,000 needs about n·k·d = 1.3 × 10¹² multiply-adds per iteration for the distance computation, which a GPU performs in a few seconds and a CPU cluster in tens of seconds. With 20 iterations, the whole run is minutes. The same computation with a full-covariance GMM costs far more per iteration and needs k·d² numbers for the covariances.
intuition: Guess the groups, re-centre each group on its members, regroup, and repeat until nothing moves.
Imagine placing k shops in a city so that the total walking distance of customers to their nearest shop is small. If you know where the shops are, each customer simply walks to the nearest one. If you know which customers each shop serves, the best place for the shop is the average position of those customers. Neither fact is known at the start, but each helps find the other, so you alternate. Each step can only reduce the total walking distance, so the process must settle.
EM has the same shape with a softer rule. If you knew which cluster each point came from, fitting each Gaussian would be easy, just averages. If you knew the Gaussians, computing the probability that each point came from each one would be easy, just Bayes' rule. Instead of choosing a side, you alternate between "guess the missing labels using the current model" and "refit the model using the guessed labels, weighted by how confident the guesses are". Jensen's inequality is the mathematical guarantee that this is never a step backwards.
mistakes: People often think clustering finds the true groups in the data. In fact it finds groups that are good under one distance function and one objective, and a different algorithm or a different scaling of features gives different groups. K-means prefers round clusters of similar size; with long, thin or nested clusters it cuts them wrongly. Whether a cluster is useful is a business question, which you check by looking at the members and at what the groups predict.
People often think k-means gives the same answer every time. In fact it finds a local optimum that depends on the starting centres, and different seeds can give clusters with 10 percent or more difference in cost on hard data. Use k-means++ seeding, several restarts, and a fixed random seed when you need repeatability.
People often think the elbow in the cost curve tells you the right k. In fact the cost always decreases with k, and many datasets show no clear elbow. Use it with other evidence: silhouette, BIC for mixtures, stability of the clusters across resamples, and the number of groups the business can act on.
People often think you can cluster raw features directly. In fact k-means is based on Euclidean distance, so a feature in the range 0 to 100,000 (for example, spend) dominates a feature in the range 0 to 1. Scale features first, drop or transform skewed features (for example with a logarithm), and consider reducing dimension (PCA) before clustering.
People often think soft clustering (GMM) is always better because it is more general. In fact it needs more data to estimate covariances, it can collapse onto single points, it assumes that clusters are Gaussian, and it is slower. With high-dimensional data, a full covariance has too many parameters, so restrict it (diagonal or spherical) or reduce dimension first.
friction: The first problem is choosing k. There is no objective answer, and heuristics such as the elbow, silhouette and BIC often disagree. The second is local optima: k-means and EM are sensitive to initialization. The third is the shape assumption: k-means assumes clusters are compact and of similar size and density; a GMM assumes Gaussian shapes. Data with elongated, nested or very unequal clusters breaks both, and then DBSCAN, spectral clustering or a learned embedding followed by k-means works better.
High dimensions are the fourth problem. As d grows, the distances between pairs of points become nearly equal (the nearest and farthest neighbours are almost the same distance away), so "nearest centre" carries little information. With raw data of hundreds of dimensions, reduce the dimension (PCA, or an embedding model) before clustering. Distance in a good embedding space is far more meaningful than distance between raw feature vectors.
Scale and cost are the fifth. A full Lloyd iteration touches all the data, so for billions of points you use mini-batch k-means, sampling, or a distributed implementation, and you accept slightly worse clusters. Clusters can also be unstable: new data shifts the centres, so segment labels change between weekly runs, which breaks downstream reports unless you match new clusters to old ones or keep the old centres fixed and only assign.
Last, evaluation is hard without labels. Internal measures (silhouette, cost) say how compact the clusters are, not whether they are useful. In advertising, a segment that looks tidy but does not differ in response to an offer has no value. And since segments built on personal viewing data raise privacy questions, check what features you may legally use.
practice: Prepare the features first: choose a distance that reflects similarity for your problem, standardize or normalize features, transform heavy tails with a logarithm, and reduce dimension with PCA or use an embedding when you have hundreds of raw features. Then run k-means with k-means++ seeding and 10 or more restarts for a range of k (for example 2 to 30). Look at the cost curve, the silhouette score and, most important, the cluster sizes and profiles: if one cluster has 95 percent of the points, or several clusters are tiny, change the features or k.
Check stability: cluster two random halves of the data, or two different weeks, and compare the assignments (adjusted Rand index). Unstable clusters mean the structure is weak. For production segments, keep the fitted centres and assign new points to the nearest centre instead of re-clustering each week, and re-fit on a schedule with a mapping to the old labels. In Spark MLlib, KMeans (with k-means|| initialization) and GaussianMixture are available; in scikit-learn, KMeans, MiniBatchKMeans, GaussianMixture, DBSCAN and HDBSCAN; for vectors at scale, FAISS trains k-means on GPUs.
Use GMM when you need membership probabilities, clusters with different shapes, or a density model for anomaly detection (points with low likelihood). Choose covariance_type (full, diag, spherical) by BIC. Use DBSCAN or HDBSCAN when you expect arbitrary shapes and noise. When k-means is a component, as in IVF indexes (the number of cells is commonly set from the square root of the collection size, or a few times that) or product quantization, tune k against the recall and latency you measure, not against cluster beauty.
quiz: What are the two alternating steps of k-means, and why can't the cost go up? || Assign each point to the nearest centre, then move each centre to the mean of its points. For fixed centres, nearest-centre assignment minimizes the cost; for a fixed assignment, the mean minimizes the sum of squared distances. Neither step can increase the cost, so the algorithm converges.
Why does k-means++ give better results than random initial centres? || It picks each new centre with probability proportional to its squared distance from the nearest chosen centre, so the centres spread out across the data instead of landing in one group. It has a proven O(log k) bound on the expected cost relative to the optimum.
What do the E-step and M-step of EM for a Gaussian mixture compute? || The E-step computes each component's responsibility for each point with Bayes' rule, using the current parameters. The M-step re-estimates each component's weight, mean and covariance as responsibility-weighted averages.
In the example with centres μ₁ = 3 and μ₂ = 8, σ = 1 and equal weights, what are the responsibilities for x = 5? || The unnormalized densities are e^(−2) = 0.1353 and e^(−4.5) = 0.0111. The responsibilities are 0.1353/0.1464 ≈ 0.924 for component 1 and 0.076 for component 2.
You have 200 raw behavioural features per household and k-means gives one giant cluster and many tiny ones. What do you try? || The distances are probably dominated by a few large-scale or skewed features and affected by high dimensions. Standardize and log-transform the features, reduce dimension with PCA or an embedding, then re-run with k-means++ and several k; also consider density-based methods if the shapes are not round.
tradeoffs: Choose k-means when the data is large (millions to billions of points), the features are numeric and scaled, and you expect compact groups of similar size. It is fast, simple and parallel. You give up cluster shape, soft membership and automatic selection of k.
Choose a Gaussian mixture when you need probabilities of membership, elongated or differently sized clusters, or a density for anomaly scoring, and when you have enough points per component (at least several times the number of parameters) to estimate covariances. Costs: slower iterations, k·d²/2 covariance numbers with full covariance, and sensitivity to initialization and singularities. In high dimensions, restrict the covariance to diagonal.
Choose DBSCAN or HDBSCAN when clusters have irregular shapes, the number of clusters is unknown, and noise points should stay unassigned. Choose k-means when you need every point assigned to a fixed number of centres, as in IVF indexes or quantization. DBSCAN's costs are two parameters (ε, minPts) that are hard to set when densities vary, and trouble in high dimensions.
Choose hierarchical clustering when n is below a few tens of thousands and you want a tree of nested groups to explore at different levels. It costs O(n²) memory in the common implementation, and a merge is never undone.
Choose k by the use. For vector indexes, choose it to meet recall and latency targets; for business segments, choose the number of groups that teams can act on (often 4 to 12), checked for stability; for compression, choose it from the error you can afford. Choosing by the elbow alone gives a number that is hard to defend.
interview: Prove that the k-means objective never increases, and say what that does and does not guarantee. || The assign step minimizes the cost over assignments for fixed centres, and the update step minimizes it over centres for a fixed assignment (the mean minimizes the sum of squared distances). The cost is non-increasing and bounded below, and the number of assignments is finite, so it converges. It guarantees a local optimum only, not the global one, which is NP-hard to find.
How is k-means related to a Gaussian mixture? || K-means is the limit of EM for a mixture of spherical Gaussians with equal weights and shared variance as the variance goes to zero: responsibilities become hard 0/1 and the mean update is the k-means update. A GMM adds soft assignments, per-cluster covariance and weights, at higher cost.
Why does EM never decrease the likelihood? || The E-step constructs a lower bound on the log-likelihood from Jensen's inequality that equals the true value at the current parameters; the M-step maximizes that bound, so the true likelihood rises at least as much. The sequence of likelihoods is non-decreasing and converges to a local optimum or saddle.
Your k-means segments change completely every week. What do you do? || Check initialization (use k-means++, fixed seeds, several restarts), check whether the clusters are weak (low silhouette, no clear structure), and stop re-clustering from scratch: fix the centres from a reference period and assign new data to them, or align new clusters to old ones by matching centroids.
How would you cluster 500 million embedding vectors? || Train k-means on a sample (a few million vectors) on GPUs with k-means++ or k-means|| seeding or mini-batch updates, then assign all vectors in one pass in parallel. For an IVF index, use that as the coarse quantizer, and tune the number of cells and the number of cells probed against recall and latency.
How would you choose the number of clusters, and what if methods disagree? || Combine internal measures (elbow, silhouette, BIC for mixtures, gap statistic), stability under resampling, and the downstream goal (recall for an index, actionability for segments). If they disagree, prefer stability and the purpose, test a few values of k on the real task, and avoid reading the elbow as truth.

value: Real datasets have many features, and those features are usually not independent. A user's "minutes watched on weekdays" and "minutes watched in the evening" move together; neighbouring pixels in a photo have similar values; the 768 numbers of a text embedding carry far less than 768 numbers' worth of information. Principal component analysis (PCA) finds a small number of new axes, built as combinations of the old features, that capture most of the variation in the data. You keep the first k axes and drop the rest. The result is a shorter vector for each row that keeps most of what matters.
PCA is used to compress data (768-dimensional embeddings to 128 dimensions), to remove noise (the dropped directions are often mostly noise), to speed up and stabilize downstream models (fewer, uncorrelated inputs), to visualize (project to 2 dimensions), and to understand data (the first components often show the main factors of variation). The same mathematics, the singular value decomposition (SVD), sits under latent semantic analysis (the first word vectors), recommender systems, image compression, and low-rank methods such as LoRA for fine-tuning large models. If you understand PCA, you understand why "low-rank" shows up everywhere.
The layers below do all the work. Linear algebra (L4) supplies the central fact: the principal components are the eigenvectors of the covariance matrix, which are the right singular vectors of the centred data matrix, and the Eckart–Young theorem says that the best rank-k approximation of a matrix is given by its top k singular values and vectors. Statistics (L4) supplies the meaning: variance is the quantity to preserve, covariance describes how features move together, and the eigenvalues are the variances along each new axis. Together they turn a vague wish ("keep the important information") into a computation.
terms: Principal component — one of the new axes: a unit-length direction in feature space; the first has the largest variance of the projected data, the second the largest variance among directions perpendicular to the first, and so on.
Covariance matrix — the d × d matrix whose entry (i, j) says how features i and j vary together; the diagonal holds the variances.
Eigenvector and eigenvalue — a direction that a matrix only stretches, and the stretch factor; for the covariance matrix, the eigenvalue is the variance along that eigenvector.
Singular value decomposition (SVD) — a factorization X = UΣVᵀ of any matrix into orthogonal U and V and a diagonal Σ of non-negative singular values.
Explained variance ratio — the share of the total variance captured by a component: λᵢ divided by the sum of all eigenvalues.
Scores (projections) — the coordinates of each row along the principal components; they are the compressed representation.
Reconstruction error — the squared distance between a row and its approximation from the first k components; it equals the sum of the dropped eigenvalues, summed over rows.
Whitening — scaling each component to unit variance so that the new features are uncorrelated and have equal scale.
Rank — the number of independent directions in a matrix; a low-rank matrix can be written with few numbers.
history: Karl Pearson introduced the idea in 1901, in a paper called "On lines and planes of closest fit to systems of points in space". His question was geometric: which line (or plane) is closest to a cloud of points, in the sense of the smallest sum of squared perpendicular distances? Harold Hotelling (1933) arrived at the same axes from statistics, as the linear combinations of variables with the largest variance, and gave them the name "principal components". For decades the computation was hard to do by hand, so it was used on small tables, mostly in psychology and economics.
The mathematical tool behind it is older. The singular value decomposition was discovered by Beltrami and Jordan in the 1870s, and Carl Eckart and Gale Young proved in 1936 that truncating the SVD gives the best low-rank approximation. Practical computation of the SVD came with Golub and Kahan's algorithm in 1965, and the LINPACK and LAPACK libraries made it routine.
PCA then spread to every field that had matrices. Deerwester, Dumais, Furnas, Landauer and Harshman (1990) applied a truncated SVD to word-document counts and called it latent semantic analysis; this was the first widely used way to get dense vectors for words and documents. Turk and Pentland's "eigenfaces" (1991) used PCA on face images for recognition. Tipping and Bishop (1999) gave a probabilistic version, and Schölkopf and co-authors (1998) the kernel version for curved structure. For large data, Halko, Martinsson and Tropp (2011) showed that random projections give an accurate approximate SVD in a fraction of the time, which is how PCA runs on huge matrices today. Non-linear methods for visualization, t-SNE (2008) and UMAP (2018), came later and complement PCA.
how: Start with a data matrix X with n rows (examples) and d columns (features). Step 1: centre it by subtracting each column's mean, so every feature has mean zero. Without centring, the first component would mostly point towards the mean. Often you also divide each column by its standard deviation (standardizing), because otherwise a feature measured in large units dominates the variance. This step matters more than any other choice.
Step 2: find the direction v₁ (a unit vector) such that the projected values Xv₁ have the largest variance. The variance of the projection is v₁ᵀCv₁, where C = XᵀX/(n − 1) is the covariance matrix. Maximizing a quadratic form over unit vectors has a classical answer from linear algebra: the maximizer is the eigenvector of C with the largest eigenvalue λ₁, and the maximum variance is λ₁ itself. The second component is the best direction perpendicular to the first, which is the eigenvector with the second-largest eigenvalue, and so on. Because C is symmetric, its eigenvectors are orthogonal and form a new coordinate system, a rotation of the original axes. The eigenvalues add up to the total variance (the trace of C), so λᵢ divided by the total is the share of the variance carried by component i.
Step 3: project. Keep the top k eigenvectors as the columns of a d × k matrix Vₖ. The new representation of each row is its scores, Z = XVₖ, an n × k matrix. To approximate the original row from the scores, compute Z Vₖᵀ (plus the mean). The reconstruction error, summed over all rows, equals (n − 1) times the sum of the discarded eigenvalues, so choosing k is choosing how much variance to give up. A common rule is the smallest k that keeps 90 to 95 percent of the variance; another is to look for an elbow in the plot of eigenvalues (the scree plot). When the data has noise of known level, Gavish and Donoho (2014) gave a rule for the best cut-off of singular values.
The SVD route is better in practice. Forming XᵀX squares the condition number and costs O(nd²). Instead, compute the SVD of the centred matrix directly: X = UΣVᵀ. The columns of V are the principal directions, the squared singular values divided by (n − 1) are the eigenvalues, and the scores are UΣ. The Eckart–Young theorem then says that keeping the top k singular triplets gives the best rank-k approximation of X in squared error, so no other k-dimensional linear projection can beat PCA at reconstruction. This makes PCA the optimal linear compressor under squared error, and it is the reason the same recipe works for images, ratings matrices and embeddings.
For large matrices, a full SVD costs about O(nd·min(n, d)), which is too much. Randomized SVD (Halko, Martinsson and Tropp) multiplies X by a random d × (k + p) matrix, with a small oversampling p of about 5 to 10, to capture the range of X, orthogonalizes the result with a QR factorization, and computes an exact SVD of the small projected matrix. With a couple of power iterations to sharpen the spectrum, the cost is about O(ndk) and the error is close to the optimum when singular values decay. Incremental PCA processes data in batches, and Spark MLlib computes the covariance matrix in a distributed way when d is a few thousand.
PCA also whitens data: dividing each score by √λᵢ gives features with unit variance and zero correlation. This is useful before methods that assume a spherical shape, such as k-means, but it amplifies noise in the low-variance directions, so apply it with a floor on λ. And remember what PCA cannot do: it only finds linear structure, and it keeps directions of high variance, which are not always the directions that matter for a prediction task.
Why does dropping components remove noise? Suppose each row is a true signal that lies close to a k-dimensional subspace, plus independent noise of similar size in every direction. The signal creates large eigenvalues in k directions. The noise adds about the same small variance to all d directions, so the remaining d − k eigenvalues are small and close to each other. Cutting at the point where the eigenvalues level off removes most of the noise (about (d − k)/d of it) and keeps almost all of the signal. This is the reason PCA is used to denoise images and measurements, and to clean embeddings before search.

example: Take four points in two dimensions: (1, 1), (2, 3), (3, 2), (4, 4). The means are 2.5 and 2.5, so the centred points are (−1.5, −1.5), (−0.5, 0.5), (0.5, −0.5) and (1.5, 1.5). The covariance matrix (dividing by n − 1 = 3) has variance (2.25 + 0.25 + 0.25 + 2.25)/3 = 1.667 for each feature and covariance (2.25 − 0.25 − 0.25 + 2.25)/3 = 1.333 between them: C = [[1.667, 1.333], [1.333, 1.667]]. For a symmetric 2 × 2 matrix of this form, the eigenvectors are (1, 1)/√2 and (1, −1)/√2, with eigenvalues 1.667 + 1.333 = 3.0 and 1.667 − 1.333 = 0.333.
So PC1 points along the diagonal and carries 3.0 / 3.333 = 90 percent of the variance. PC2 is the perpendicular direction and carries 10 percent. Project onto PC1: the scores are (−1.5 − 1.5)/√2 = −2.12, then 0, 0 and +2.12. Four rows of two numbers became four single numbers. Check the variance of the scores: (4.5 + 0 + 0 + 4.5)/3 = 3.0, equal to λ₁. To reconstruct, multiply each score by the direction (0.707, 0.707): the point (−1.5, −1.5) comes back exactly, while (−0.5, 0.5) becomes (0, 0), an error of 0.707 in length. The total squared error is 0.5 + 0.5 = 1.0, which equals (n − 1) × λ₂ = 3 × 0.333. The SVD view gives the same numbers: the singular values are √(3 × 3.0) = 3 and √(3 × 0.333) = 1.
Now see why scaling matters. If the second feature were measured in different units (multiplied by 100, say millimetres instead of centimetres), its variance would grow by 10,000 and PC1 would point almost exactly along that feature, whatever the data says about the first feature. Standardizing each feature to unit variance first gives each feature an equal chance.
A realistic sizing: one million embedding vectors of dimension 768 in float32 take 3.07 GB. PCA to 128 dimensions with 95 percent of the variance kept, if the spectrum allows it, brings it to 512 MB, and distance computations become six times cheaper. The covariance matrix needs about n·d² = 10⁶ × 768² ≈ 5.9 × 10¹¹ multiply-adds, a minute or so on one machine. Fitting on a random sample of 100,000 vectors gives almost the same components at a tenth of the cost, then you apply the projection to all vectors.
intuition: Rotate the cloud of points so its longest axis lines up with the first coordinate, then drop the thinnest axes.
Think of a flat sheet of paper floating in a three-dimensional room, with points drawn on it. Each point has three coordinates, but the sheet is only two-dimensional, so one coordinate is redundant. Real data is rarely perfectly flat, but often it is nearly flat: it spreads a lot in a few directions and very little in the others. PCA finds the sheet. The directions with large spread are where the information is (different rows differ there), and the directions with tiny spread are mostly noise or tiny details, so dropping them loses little.
Why variance? A direction where all rows have almost the same value cannot help tell rows apart, so it is natural to keep the directions where rows differ most. The Eckart–Young theorem makes this exact: no other choice of k directions keeps more squared information. The method is natural because its answer is just the stretching directions of the data cloud, which linear algebra gives directly.
mistakes: People often think PCA picks the most important original features. In fact each component is a mixture of all the original features, so the output features are new and not always easy to name. Feature selection (keeping a subset of the original columns) is a different technique.
People often think the components with the largest variance are the most useful for prediction. In fact PCA ignores the labels. A direction with small variance can be the one that separates two classes (for example, a small but decisive signal), and PCA may drop it. If prediction is the goal, test several values of k with cross-validation, or use a supervised method such as linear discriminant analysis or partial least squares.
People often think PCA does not need preparation. In fact it depends on centring and on the scale of the features. Without standardizing, features with large units dominate. Heavy-tailed features and outliers also pull the components, so transform skewed features and consider robust variants.
People often think the 2-D PCA plot shows the true structure of the data. In fact it shows the two directions of largest variance only; clusters that differ in other directions overlap in the picture. For visualizing local structure, t-SNE or UMAP are often better, but they distort global distances, so they have their own risks.
People often think the sign or the exact values of a component mean something stable. In fact eigenvectors are only defined up to sign, and when two eigenvalues are nearly equal, the individual directions are unstable and any rotation within that pair is equally valid. Compare the subspace, not single vectors.
friction: PCA is linear. Data on a curved surface, such as a spiral or a ring, cannot be flattened without loss, and PCA will need many components where a non-linear method needs two. Kernel PCA, autoencoders, t-SNE and UMAP handle curvature, at higher cost and with less guarantees. PCA is also unsupervised and sensitive to scale, as above; the right preprocessing is part of the method, not an optional extra.
Interpretation is hard because components are mixtures with positive and negative loadings, and the sign is arbitrary. Sparse PCA and non-negative matrix factorization give more readable parts at the price of the clean optimality. Outliers have a large effect because variance is a squared quantity; one extreme row can rotate the first component. And PCA assumes that variance means signal. In some data the biggest variance is a nuisance (for example, a batch effect, or overall user activity level), and removing that component, not keeping it, is the right operation.
Cost and scale: the full covariance route costs O(nd²) and the d × d matrix does not fit in memory for very large d, so use randomized or incremental methods. The projection must be stored and applied consistently at serving time (the mean and V matrix are part of the model), and when the data distribution drifts, the components drift as well, so refit on a schedule and watch the explained variance. Finally, after PCA the features lose their meaning for audit and for regulation, which matters when you must explain a decision.
practice: Standardize features (or at least centre them) before PCA, fit on the training data only (leakage again: fitting on all data gives the validation rows influence), and apply the same mean, scale and V to new data. Choose k by explained variance (90 to 95 percent is a common start), by the scree plot, or best by the performance of the downstream task under cross-validation. Check the reconstruction error on held-out data.
Use the SVD-based implementation (scikit-learn's PCA uses it, with a randomized solver for large matrices when you ask for few components; TruncatedSVD for sparse matrices, which does not centre the data because that would make it dense; Spark MLlib's PCA and RowMatrix.computeSVD for distributed data). For embeddings, PCA to a lower dimension, followed by product quantization or an HNSW index, reduces memory and speeds up search with a small loss of recall; measure that loss on your queries. Fit on a sample of 100,000 to 1,000,000 vectors, not on all of them.
Inspect the results: look at the loadings of the top components to name them, plot the first two scores coloured by an important variable, and see how much variance the first component takes (a first component with 60 percent often means a "size" or "activity" factor you may want to remove). Use PCA to remove correlated inputs before linear models and to denoise. And remember the connection: when you meet matrix factorization, LSA, LoRA or low-rank attention, you are looking at the same truncated SVD idea with a different dataset.

You have 5 million sparse TF-IDF vectors with 300,000 features and want 200 dimensions. How do you proceed? || Do not form a dense covariance matrix (300,000² entries) and do not centre the sparse data. tradeoffs: Choose PCA when the structure is roughly linear, you want a fast, deterministic, interpretable-by-loadings reduction, and you will apply the same projection at serving time. Choose a non-linear method (autoencoder, UMAP, t-SNE) when the data lies on a curved surface and you need that structure, accepting slower fitting, tuning, and no simple inverse; use t-SNE or UMAP only for visualization or exploration, not as a model input without care.
Choose to keep more components (95 to 99 percent of variance) when the downstream task is sensitive to fine detail, as in nearest-neighbour search with high recall requirements; choose fewer (70 to 90 percent) when you want denoising, speed or visualization. Each step down saves memory and time linearly in k and gives up some accuracy that you should measure on the real task, not on the variance alone.
Choose standardized PCA (correlation matrix) when features have different units or scales, and unstandardized PCA (covariance matrix) when all features share the same unit and the scale carries information, as with pixel intensities or embedding coordinates. The wrong choice lets an arbitrary unit decide the result.
Choose exact SVD when d is small or moderate (up to a few thousand) and accuracy is important; choose randomized or incremental SVD when the matrix is large (millions of rows or very wide) and the spectrum decays quickly. Randomized methods lose accuracy when the singular values decay slowly, which is the case for noisy data, and then you need more power iterations.
Choose a supervised reduction (LDA, partial least squares, or learning the projection end to end in a network) when the aim is prediction and the label is available; choose PCA when you have no labels, or when you want one representation for many tasks.
interview: Derive why the first principal component is the top eigenvector of the covariance matrix. || The variance of the data projected on a unit vector v is vᵀCv. Maximizing it under ‖v‖ = 1 with a Lagrange multiplier gives Cv = λv, so v must be an eigenvector, and the variance equals λ. The maximum is the largest eigenvalue. The next component repeats this under the orthogonality constraint.
What is the relationship between PCA and SVD, and which do you compute in practice? || If X is the centred data matrix with SVD X = UΣVᵀ, then XᵀX = VΣ²Vᵀ, so V holds the principal directions and σᵢ²/(n − 1) the eigenvalues. In practice compute the SVD of X directly (or a randomized one): it avoids squaring the condition number and the O(nd²) cost of forming the covariance.
How do you choose the number of components, and what could go wrong? || Use cumulative explained variance (90 to 95 percent), a scree-plot elbow, or cross-validated downstream performance, with a noise-based threshold if the noise level is known. Variance is not relevance: a low-variance direction may carry the label signal, and if the top component is a nuisance factor (activity level), keeping it hurts.
Why is PCA sensitive to feature scale and outliers? || Variance is measured in squared units, so a feature with large units dominates the covariance and the first components. Outliers inflate variance in their direction because errors are squared. Standardize, transform skewed features, remove or clip outliers, or use a robust PCA.
You apply PCA to 768-dimensional embeddings before a vector index. What do you check? || Fit on the training sample only, measure recall@k and latency before and after on real queries, check the explained variance, and confirm that the same mean and projection are applied to queries and documents. Consider that dropped dimensions may carry the fine distinctions between near neighbours.
How is PCA related to matrix factorization for recommendations? || Both are low-rank approximations X ≈ UVᵀ. PCA is the exact SVD of a fully observed, centred matrix. Recommendation matrices are mostly missing, so you fit the factors only to the observed entries with regularization (by SGD or alternating least squares) instead of taking an SVD.

@@ matfact
value: Matrix factorization is the standard way to predict who will like what from a table of past behaviour. Put users in rows and items (movies, ads, products, shows) in columns. Each cell holds a rating, a click, a watch or nothing. Almost every cell is empty: in the Netflix Prize data, about 480,000 users had rated about 17,800 movies, a table of 8.5 billion cells of which only about 1.2 percent (100 million ratings) were filled. The task is to predict the empty cells. Matrix factorization does this by giving each user a short vector of numbers (say 50 or 100) and each item a short vector of the same size, so that the dot product of a user vector and an item vector approximates that user's rating of that item.
The vectors are learned. Nobody tells the model what the numbers mean, but they usually turn into hidden "taste" dimensions: one might separate action from drama, another serious from light, another old from new. A user's vector says how much that user likes each hidden dimension, and an item's vector says how much of each it contains. Because each user is a point in a small space, the model generalizes: two users who liked some of the same items end up close together, and each is recommended what the other liked. The method won the Netflix Prize era (2006 to 2009) and remains a strong, cheap baseline for recommendation, ad targeting and audience modelling. The learned item vectors are also a form of embedding, and the dot-product scoring is the same shape as a two-tower model or a vector search.
The layers below provide the parts. Linear algebra (L4) says what the model is: a low-rank approximation R ≈ P Qᵀ of the big matrix, which is the same idea as the truncated SVD in PCA but for a matrix that is mostly missing. Gradient descent (L2) is one way to learn the vectors, a few ratings at a time. Regularization (L2) stops the vectors from memorizing the few ratings each user has: it is what makes the model work with 1 percent of the cells observed.
terms: User-item matrix — a table with one row per user and one column per item; most cells are unknown.
Latent factor — one hidden dimension of taste or content, learned from data, with no name given in advance.
Factor vectors (embeddings) — the short vector pᵤ for a user and qᵢ for an item; the predicted rating is their dot product plus biases.
Bias terms — a global average μ, a user offset bᵤ (generous or harsh raters) and an item offset bᵢ (popular or unpopular items).
RMSE — root mean squared error between predicted and true ratings; the metric of the Netflix Prize.
SGD (stochastic gradient descent) — update the vectors a little after each observed rating, in the direction that reduces its error.
ALS (alternating least squares) — fix all item vectors and solve exactly for all user vectors, then swap; each solve is a small ridge regression.
Implicit feedback — behaviour such as views, clicks and purchases, which shows what users did, not what they liked; absent behaviour is not a negative rating.
Cold start — the problem of a new user or item with no history, so no vector can be learned yet.
history: Collaborative filtering, using the behaviour of many users to recommend to one, began in the early 1990s (the Tapestry system at Xerox PARC, 1992; GroupLens for Usenet news, 1994). Early methods were neighbourhood-based: find similar users or similar items and average their ratings, as in Amazon's item-to-item filtering (Linden, Smith and York, 2003). Using the SVD for recommendations was explored in the early 2000s (Sarwar and co-authors, 2000) but the missing entries made it awkward.
In October 2006, Netflix started a public contest: a one-million-dollar prize for the first team to improve the RMSE of its own recommender, Cinematch, by 10 percent on a hidden test set of ratings, using a training set of about 100 million ratings. Within two months, Simon Funk (Brandyn Webb) described on his blog a simple method: fit a low-rank factorization to the observed ratings only, by stochastic gradient descent. It worked far better than expected and the field adopted it. Yehuda Koren, Robert Bell and Chris Volinsky (the BellKor team) then added biases, time effects and implicit feedback (SVD++), and showed how to blend many models. The prize was awarded in September 2009 to the team BellKor's Pragmatic Chaos, who reached a 10.06 percent improvement. Their summary paper, "Matrix Factorization Techniques for Recommender Systems" (IEEE Computer, 2009), is the standard reference.
The contest data had explicit star ratings, but real products mostly have implicit signals. Hu, Koren and Volinsky (ICDM 2008) gave the standard treatment: treat every unobserved pair as a weak negative and every observed one as a positive with confidence that grows with the amount of activity, and train with ALS in a way that scales with the number of observed entries. Rendle and co-authors' Bayesian personalized ranking (2009) optimized the ranking of items directly. After 2015, neural two-tower models and sequence models replaced pure matrix factorization in many large systems, but they inherited its core: users and items as vectors, scored by a dot product.
how: Let R be the user-item matrix with a set Ω of observed entries. The model predicts the rating of user u for item i as r̂ᵤᵢ = μ + bᵤ + bᵢ + pᵤ·qᵢ. The first three terms capture simple effects (the average rating, how generous this user is, how well-liked this item is). They are always included, because they take care of the simple effects, so that the vectors can concentrate on personal taste. The last term is the personal part: pᵤ and qᵢ are k-dimensional vectors, with k typically between 20 and 200. In matrix form, R ≈ P Qᵀ, where P is the users × k matrix and Q is the items × k matrix. The rank k is the number of hidden dimensions, and the model has (users + items) × k numbers, about 50 million for the Netflix data at k = 100, instead of 8.5 billion cells.
Training minimizes the squared error on observed entries only, plus a penalty: the sum over (u, i) in Ω of (rᵤᵢ − r̂ᵤᵢ)² + λ(‖pᵤ‖² + ‖qᵢ‖² + bᵤ² + bᵢ²). The key difference from PCA and the plain SVD is the word "observed". A truncated SVD needs a complete matrix, and filling the empty cells with zeros or averages teaches the model about the filler. Here the loss ignores unobserved cells entirely. The problem is not convex (it has products of unknowns) but is easy in each half: if the item vectors are fixed, the loss is an ordinary regularized least-squares problem in the user vectors, and vice versa.
There are two main ways to optimize. Stochastic gradient descent loops over the observed ratings. For one rating, compute the error e = rᵤᵢ − r̂ᵤᵢ and update pᵤ ← pᵤ + γ(e·qᵢ − λpᵤ) and qᵢ ← qᵢ + γ(e·pᵤ − λqᵢ), with similar updates for the biases; here γ is the learning rate, typically 0.005 to 0.05. It is simple, uses little memory and handles streams, and it can be parallelized with care (Hogwild-style lock-free updates work well because two ratings rarely touch the same vectors). Alternating least squares fixes Q and solves, for each user u separately, the ridge regression pᵤ = (Qᵤᵀ Qᵤ + λI)⁻¹ Qᵤᵀ rᵤ, where Qᵤ stacks the vectors of the items that user rated. Then it fixes P and solves for every item. All users can be solved in parallel, which is why ALS is the algorithm in Spark MLlib; each sweep costs about O(|Ω|k² + (users + items)k³).
Implicit feedback changes the target. A view or a click is a signal of interest, but a missing view is not dislike. Hu, Koren and Volinsky define a binary preference pᵤᵢ = 1 if the user interacted with the item, 0 otherwise, and a confidence cᵤᵢ = 1 + α·(amount of activity) (for example, watch count or minutes). The loss then sums over all pairs, observed or not: Σ cᵤᵢ (pᵤᵢ − pᵤ·qᵢ)² + regularization. That looks like it needs a sum over billions of cells, but the ALS solution for one user is (QᵀQ + Qᵀ(Cᵘ − I)Q + λI)⁻¹ QᵀCᵘp(u), where QᵀQ is computed once for all users and Cᵘ − I is non-zero only for the items the user touched. So the cost depends on the number of observations, not on the size of the full matrix. Spark MLlib's ALS supports this with implicitPrefs=true.
Using the model is a dot product, which is cheap. To recommend, compute pᵤ·qᵢ for candidate items and take the top N. With millions of items you do not score them all: you build an index for maximum inner product search (the vector search concept) over the item vectors, and query it with pᵤ. For a brand-new user, you can fold in: compute pᵤ for the few interactions they have by solving the same ridge regression with Q fixed, without retraining the item vectors. Extra information (item categories, user demographics, context) can be added as side features, which leads to factorization machines and to the neural models that replaced the plain version.
Two details matter in practice. Initialization: set the vectors to small random numbers (for example, normal with standard deviation 0.1 divided by √k), not to zeros, because with all-zero vectors the gradients are also zero and nothing moves. Hyperparameters: k, λ and the learning rate interact, so tune them together on a held-out set that is later in time than the training set. A well-regularized model with a large k usually beats an unregularized model with a small k, because regularization lets each vector use only as many dimensions as the user's data supports.

example: Take one observed rating and apply one SGD step. Use a global mean μ = 3.6, user bias bᵤ = 0.2, item bias bᵢ = −0.1, user vector pᵤ = (0.1, 0.3) and item vector qᵢ = (0.5, −0.2). The dot product is 0.1 × 0.5 + 0.3 × (−0.2) = 0.05 − 0.06 = −0.01. The prediction is r̂ = 3.6 + 0.2 − 0.1 − 0.01 = 3.69. The user actually gave a 5, so the error is e = 5 − 3.69 = 1.31. Use learning rate γ = 0.05 and regularization λ = 0.1.
Update the user vector: pᵤ ← pᵤ + γ(e·qᵢ − λ·pᵤ). First component: 0.1 + 0.05 × (1.31 × 0.5 − 0.1 × 0.1) = 0.1 + 0.05 × 0.645 = 0.132. Second: 0.3 + 0.05 × (1.31 × (−0.2) − 0.1 × 0.3) = 0.3 + 0.05 × (−0.292) = 0.285. Update the item vector using the old pᵤ: first component 0.5 + 0.05 × (1.31 × 0.1 − 0.1 × 0.5) = 0.5 + 0.05 × 0.081 = 0.504; second −0.2 + 0.05 × (1.31 × 0.3 − 0.1 × (−0.2)) = −0.2 + 0.05 × 0.413 = −0.179. Update the biases: bᵤ ← 0.2 + 0.05 × (1.31 − 0.1 × 0.2) = 0.2645 and bᵢ ← −0.1 + 0.05 × (1.31 + 0.01) = −0.034. The new prediction is 3.6 + 0.2645 − 0.034 + (0.132 × 0.504 + 0.285 × (−0.179)) = 3.83 + 0.0155 ≈ 3.85. The error fell from 1.31 to about 1.15 after a single step. Over many ratings, the vectors drift until a typical error is near 0.85 to 0.9 stars, as in the Netflix data.
Next, one ALS solve with numbers, to see what regularization does. Let k = 2 and suppose user u rated two items whose vectors are q₁ = (1, 0) and q₂ = (0, 1), with ratings 4 and 2 (assume the biases are already removed). Then QᵤᵀQᵤ is the identity matrix, and with λ = 1, pᵤ = (I + I)⁻¹ Qᵤᵀ r = (4, 2)/2 = (2, 1). Without regularization the answer would be (4, 2), fitting these two ratings exactly. With λ = 1 it is shrunk by half. With only two ratings, this shrinkage is wise: the user's true taste is uncertain, so the model stays closer to the average (the zero vector). A user with 200 ratings would have a large QᵤᵀQᵤ and almost no shrinkage. This automatic trust in proportion to the amount of evidence is what lets the method work on very sparse data.
At scale: for 100 million ratings with k = 100, solving for all user vectors (half a sweep) needs about |Ω|k² = 10⁸ × 10⁴ = 10¹² multiply-adds to build the normal equations, plus 480,000 solves of 100 × 100 systems at about 10⁶ operations each, about 5 × 10¹¹. That is about 1.5 × 10¹² operations per half sweep, and twice that for a full sweep over users and items, which a modest cluster handles in minutes. Ten sweeps usually suffice.
intuition: Explain every rating as a match between a few hidden tastes of the user and a few hidden traits of the item.
Think of a film critic who describes every film with five numbers (how much action, how much humour, how serious, how romantic, how violent) and every viewer with five numbers for how much they like each of these. The predicted enjoyment is the sum of the products. Nobody writes these numbers down; the algorithm invents the five dimensions that best explain the ratings it has seen. Two viewers with similar vectors will like similar films, even if they have never watched the same film.
Why does it work with so few observed cells? Because taste is low-dimensional: people are not 17,000 independent individuals, they are combinations of a few tastes. A matrix that is the product of two thin matrices has few free numbers, so a small number of observations pins them down. Regularization says: prefer simple explanations unless the data insists. The fit is the same shape as PCA, with one difference: PCA needs every cell, and matrix factorization learns only from the cells that exist.
mistakes: People often think matrix factorization fills the matrix by finding similar users. In fact it does not compare users directly. It learns a shared set of hidden dimensions and places every user and item in that space; similar users end up with similar vectors as a result. This is why it generalizes to pairs of users with no items in common.
People often think the latent factors have clear meanings. In fact they are only defined up to rotation: for any invertible matrix A, (PA)(QA⁻ᵀ)ᵀ gives the same predictions. Individual factors can sometimes be read as genres, but often they cannot, and they change when you retrain.
People often think implicit feedback can be treated like ratings, with "no click" as a low rating. In fact a missing interaction mostly means the user never saw the item. Treating all missing cells as zeros trains the model to predict exposure. Use confidence weighting, negative sampling or ranking losses, and remember that logged data reflects what the old recommender chose to show.
People often think a lower RMSE means better recommendations. In fact RMSE measures the accuracy of predicted ratings over all items, while a product shows the top few. A model can improve RMSE and hurt the quality of the top-10 list. Netflix itself reported that it did not use the full prize-winning ensemble in production, because the gains in RMSE did not justify the engineering cost once its product moved to streaming and implicit signals. Evaluate with ranking metrics (precision@k, NDCG, recall@k) and online experiments.
People often think a larger k is always better. In fact beyond a point it overfits, especially for users and items with few observations. Choose k and λ together by validation on a time-based split, and expect that a higher k needs a larger λ.
friction: Cold start is the biggest practical limit. A new user or new item has no interactions, so there is no vector; a few interactions give a noisy vector. Systems use content features (item metadata, user attributes), popular-item fallbacks, onboarding questions, and exploration to collect early data. Factorization machines and two-tower models, which take features as input, are the usual next step.
The data is biased. Users only rate or click what they were shown, and what they were shown depends on the previous recommender, so popular items get more data and become more popular (a feedback loop). Missing data is not random: people rate the movies they loved or hated. Unbiased evaluation needs randomized exploration or inverse propensity weighting. The dot product is also limited: it cannot express complex interactions, such as "likes A and B separately, but not together", and it cannot use context such as time, device or what was just watched, which sequence and deep models handle.
Operational costs: user vectors go stale as tastes change, so they must be refreshed (daily, or by folding in new events in real time). Models for hundreds of millions of users and millions of items need a lot of memory for the vectors (100 million users × 64 floats × 4 bytes = 25.6 GB), and the retrieval of the top items needs an approximate maximum-inner-product index. There are also fairness and privacy concerns: the vectors encode sensitive attributes that were never given to the model, and they can leak information about individual users.
practice: Start with a strong non-personalized baseline (most popular items, perhaps per segment), then a simple factorization, and compare on a time-based split by ranking metrics (recall@k, NDCG@k). For explicit ratings, use biases plus factors with SGD or ALS. For implicit data (views, clicks, watch time), use implicit ALS (Spark MLlib ALS with implicitPrefs=true, or the `implicit` Python library) with confidence weights, or a ranking loss such as BPR. Typical settings to try: k from 32 to 128, λ from 0.01 to 1 (on a log scale), α from 1 to 40 for confidence, 10 to 20 ALS iterations.
Validate the pipeline by holding out each user's latest interactions and asking whether the model ranks them near the top among items the user has not seen; compare with the popularity baseline, which is surprisingly hard to beat. Handle cold start with fallbacks and content features. Serve with precomputed top-N lists for batch use cases (email, home screens) or a nearest-neighbour index over item vectors for real-time use; refresh user vectors often.
In ad tech, the same approach builds audience models: the rows are households or devices, the columns are shows, apps or ad categories, and the learned vectors become inputs for lookalike audiences and segment scoring. Check for leakage (an item vector built from data that includes the target event), keep the vectors as features for downstream models, and monitor drift. When you outgrow it, keep the factors: they make good initial embeddings or features for a two-tower or sequence model.

Every user (or item) problem is independent, so all of them can be solved in parallel across a cluster.

tradeoffs: Choose matrix factorization when you have lots of user-item interactions, no rich features, and you need a cheap, scalable model with a dot-product serving path. Choose a two-tower or deep model when you have side features, context and sequences and enough data; it gains accuracy but costs more to train and serve. Keep factorization as the baseline and as a source of initial embeddings.
Choose SGD when data streams in, memory is tight, or you want to add features easily; it is sensitive to the learning rate and harder to parallelize exactly. Choose ALS when you have a cluster, want few hyperparameters and stable convergence, and especially for implicit feedback: each sweep is more expensive but converges in 10 to 20 sweeps and the solves are parallel.
Choose a smaller k (20 to 50) for sparse data, cold-start-heavy catalogues or when you need small vectors for fast retrieval; choose a larger k (100 to 300) when users have long histories and the catalogue is large, with a larger λ. Each doubling of k doubles the memory and the retrieval cost and roughly quadruples the ALS cost per sweep.
Choose item-based neighbourhood methods when you need explainability ("because you watched X") and have a small catalogue; choose factorization when the catalogue is large and sparse, as neighbourhood methods struggle with sparse overlaps. Choose a ranking loss (BPR, sampled softmax) over squared error when the product shows a top-N list, and squared error when you truly predict a rating.
Choose to retrain from scratch on a schedule when tastes change slowly, and online folding-in of new events when freshness matters (news, short videos); folding in fixes user vectors cheaply but lets item vectors go stale.
interview: Why is the matrix-factorization objective non-convex, and why does that rarely hurt? || The product pᵤ·qᵢ of two unknowns makes the loss non-convex jointly. It is convex in each factor when the other is fixed, which is why ALS works well, and in practice local optima reached from random starts give similar quality. Regularization and a good initialization (small random values) help.
How does implicit-feedback ALS avoid summing over all user-item pairs? || The solve for user u is (QᵀQ + Qᵀ(Cᵘ − I)Q + λI)p = QᵀCᵘp(u). QᵀQ is computed once for all users, and Cᵘ − I is non-zero only for items the user interacted with, so the per-user cost depends on the number of interactions, not on the catalogue size.
How would you handle a new item with no interactions? || Use content features (a model that maps metadata to an item vector), a popularity or category prior, and exploration to collect early interactions; after a few interactions fold in the vector with Q fixed. Hybrid and two-tower models handle this by design.
Your offline RMSE improved but online engagement fell. What happened? || RMSE weighs all items equally, while users see the top few; the model may have improved on unseen, irrelevant items. Offline data is biased by the previous recommender's exposure. Switch to ranking metrics on a time-based split, apply propensity correction, and rely on A/B tests.
How do you serve recommendations for 100 million users and 10 million items at 50 ms latency? || Store item vectors in an approximate maximum-inner-product index (HNSW or IVF with quantization); at request time, look up or compute the user vector, query the index for top candidates (hundreds), then rerank with a richer model and business rules. Precompute for batch surfaces.
What is the connection between matrix factorization and PCA, and what is different? || Both find a low-rank approximation R ≈ PQᵀ. PCA is the SVD of a fully observed, centred matrix and is solved exactly. Factorization fits only the observed entries with regularization, so it needs iterative optimization, and it adds biases and confidence weights.

value: A photo or a video frame is a grid of millions of numbers, but neighbouring numbers are very similar: a patch of sky is nearly constant, a wall changes slowly. Storing each pixel separately wastes space on this repetition. The discrete cosine transform (DCT) rewrites a block of pixels (usually 8 × 8 or 4 × 4 up to 32 × 32) as a sum of cosine patterns of increasing frequency. For natural images, almost all the energy of the block lands in a few low-frequency coefficients, and the high-frequency coefficients are small. This is the basis of transform coding: transform the block, round the coefficients coarsely (most become zero), and then store the few remaining numbers with an entropy coder.
The result is lossy compression that is tuned to the eye. JPEG (1992) uses an 8 × 8 DCT. MPEG-1, MPEG-2, H.264, HEVC and AV1 all code the prediction error of each block with a DCT or an integer approximation of it. Audio codecs such as MP3 and AAC use a close relative, the modified DCT (MDCT), on overlapping windows of samples. A typical photograph keeps good visual quality at 10 to 20 times smaller than the raw pixels, and the transform step is where that gain comes from: it turns "many similar numbers" into "a few large numbers and many zeros".
The layers below explain why this works. Fourier analysis (L4) provides the idea that any signal is a sum of waves, and the DCT is a real-valued cousin of the Fourier transform with a better behaviour at the block edges. Linear algebra (L4) shows that the DCT is just a change of basis by an orthogonal matrix: it preserves energy exactly, can be inverted by the transpose, and "packs" that energy into few coefficients. Human vision (L5) tells the encoder which coefficients can be rounded harshly: the eye is much less sensitive to fine detail than to broad shapes, and much less sensitive to colour detail than to brightness detail.
terms: Transform coding — compress by changing basis to one where the signal is sparse, quantizing the coefficients, and entropy-coding the result.
Basis function — one of the fixed patterns (here, a cosine of a given frequency) that the block is built from; the coefficient says how much of it is present.
DC and AC coefficients — the DC coefficient is the block average (frequency zero); the AC coefficients are the other 63 frequencies of an 8 × 8 block.
Energy compaction — the property that most of the signal energy ends up in a few coefficients.
Quantization — dividing each coefficient by a step size and rounding to an integer; this is the only lossy step.
Quantization matrix — a table of step sizes, larger for high frequencies, that sets how much each frequency is rounded.
Zigzag scan — reading the 2-D coefficient block in order of increasing frequency, so zeros fall together at the end.
Entropy coding — lossless coding (Huffman, arithmetic, CABAC) that gives short codes to frequent symbols.
Blocking artifact — a visible grid of 8 × 8 squares at low bitrates, because each block is coded on its own.
MDCT — the modified discrete cosine transform: a lapped version for audio, where windows overlap by half.
history: In the early 1970s, Nasir Ahmed was looking for a practical approximation of the Karhunen–Loève transform (KLT), which is the best possible transform for compression but depends on the data and is expensive. With T. Natarajan and K. R. Rao he published "Discrete Cosine Transform" in 1974. They showed that for signals with high correlation between neighbours, a first-order Markov model of images, the DCT performs almost as well as the KLT, while having fixed basis functions and a fast algorithm. The transform was seen as a curiosity at first, and its major use came with digital image standards in the late 1980s.
The Joint Photographic Experts Group published the JPEG still-image standard in 1992 (ITU-T T.81), based on the 8 × 8 DCT, with quantization tuned by perception experiments, a zigzag scan and Huffman coding. Gregory Wallace's 1991 article in the Communications of the ACM is the standard description. MPEG-1 (1993) and MPEG-2 (1995) used the same block DCT for the residual of motion-compensated prediction, and so did H.263 and MPEG-4 Part 2.
The next change was to make the transform exact in integers. A floating-point DCT gives slightly different results on different hardware, and that causes drift between the encoder and the decoder in video. H.264/AVC (2003) uses a 4 × 4 integer transform designed by Henrique Malvar and colleagues, and an 8 × 8 integer transform in its High profile, with scaling folded into the quantization. HEVC (2013) added sizes up to 32 × 32 and a discrete sine transform for 4 × 4 intra-predicted luma blocks. AV1 (2018) offers DCT, asymmetric DST and identity transforms in several sizes, up to 64 × 64, and lets the encoder choose per block. For audio, Princen and Bradley (1986) introduced the MDCT with time-domain aliasing cancellation, which MP3 (1993 to 1995) and AAC use.
how: Start with the 1-D case with N samples x₀ … x_{N−1}. The DCT (type II, the one used in coding) is X_k = α_k Σₙ xₙ cos[π(2n + 1)k / (2N)], for k = 0 … N − 1, with α₀ = √(1/N) and α_k = √(2/N) for k > 0. Coefficient k tells how much of a cosine wave with k half-cycles over the block is present. X₀ is proportional to the average (DC); X₁ measures a slow rise or fall; higher k measure faster wiggles. With this scaling the N × N matrix is orthogonal: the inverse is its transpose, and the sum of squares of the coefficients equals the sum of squares of the samples (Parseval's relation). That is the linear algebra at work: a rotation of the coordinate system that loses nothing and lets you decide later what to throw away.
For images, apply the transform to every row and then every column of an 8 × 8 block (it is separable). The 64 pixel values become 64 coefficients arranged by horizontal and vertical frequency, with the DC term in the corner. A smooth block gives a large DC value, a few small low-frequency values, and near-zero everything else. An edge or texture spreads energy into the higher frequencies. A fast algorithm (Chen, Loeffler and others) computes an 8-point DCT with about 11 multiplications and 29 additions, which is why the 8 × 8 transform is cheap: it needs about 16 one-dimensional transforms per block, and the cost is O(N log N) per row.
Why a cosine transform, and not simply the Fourier transform? The discrete Fourier transform treats the block as if it repeated periodically. A block that starts at brightness 10 and ends at 200 then has a sharp jump where the copies meet, and a jump needs many high frequencies to describe. The DCT is equivalent to a Fourier transform of the block mirrored at its edges (an even extension), so there is no artificial jump, and the energy is more compact. It also uses real numbers only. This edge behaviour is the reason the DCT, and not the DFT, became the workhorse of compression.
The lossy step is quantization. The encoder divides each coefficient by a step size from a quantization matrix and rounds to the nearest integer: q = round(X / Q). In JPEG's example luminance table the step for the DC coefficient is 16, and the steps grow to around 100 for the highest frequencies. The matrix comes from perception: contrast sensitivity of the eye falls steeply for fine spatial detail, and chroma detail is less visible still (so colour channels are first converted to Y, Cb, Cr, and the chroma planes are often subsampled by two in each direction, 4:2:0). A quality setting scales the whole matrix; a larger scale means more zeros and a smaller file. In modern video codecs, one quantization parameter (QP) plays this role; in H.264 and HEVC, an increase of 6 in QP doubles the step size.
After quantization the entropy coder takes over, and it is lossless. In JPEG, the 64 integers are read in zigzag order, so the many zeros at high frequencies form a long run at the end. The DC value is coded as a difference from the previous block's DC; the AC values are coded as (run of zeros, value) pairs with Huffman codes, and a single "end of block" symbol replaces the trailing zeros. H.264 and HEVC use context-adaptive arithmetic coding (CABAC), which adapts its probabilities to the neighbouring blocks and saves another 10 percent or so over Huffman-style coding.
Decoding runs the same chain backwards: entropy-decode, multiply by the step sizes (dequantize), apply the inverse DCT, and add back any prediction. The rounding error from quantization appears as noise whose size is limited by the step. Because most noise falls in high frequencies where the eye is least sensitive, quality looks good at far fewer bits. At very low bitrates the blocks are coded so coarsely that their edges do not match, and the 8 × 8 grid becomes visible; video codecs apply a deblocking filter to hide it.
It helps to picture the 2-D transform as 64 fixed small images, the basis patterns: one flat image, then images with one horizontal or vertical wave, then checkerboard-like images with waves in both directions. Any 8 × 8 block is a weighted sum of these 64 images, and the coefficients are the weights. Because the 64 patterns are orthogonal, each weight is found independently by taking the inner product of the block with the pattern, and the same patterns are used for every block in every image, so the decoder needs no side information other than the coefficients and the step sizes.

example: Transform four pixel values by hand: x = [10, 12, 14, 16], a smooth ramp. Use the orthonormal DCT-II with N = 4, so α₀ = 0.5 and α₁ = α₂ = α₃ = 0.7071. The cosine values needed are cos(π/8) = 0.9239 and cos(3π/8) = 0.3827. X₀ = 0.5 × (10 + 12 + 14 + 16) = 26. For X₁, the weights over the four samples are cos(π/8), cos(3π/8), cos(5π/8), cos(7π/8) = 0.9239, 0.3827, −0.3827, −0.9239, so the sum is 9.239 + 4.592 − 5.358 − 14.782 = −6.309, and X₁ = 0.7071 × (−6.309) = −4.46. For X₂ the weights are +0.7071, −0.7071, −0.7071, +0.7071, and the sum 10 − 12 − 14 + 16 = 0, so X₂ = 0. For X₃ the weights are 0.3827, −0.9239, 0.9239, −0.3827, giving 3.827 − 11.087 + 12.935 − 6.123 = −0.448 and X₃ = −0.32. So the four numbers become [26, −4.46, 0, −0.32].
Check the energy: the squares of the samples sum to 100 + 144 + 196 + 256 = 696. The squares of the coefficients sum to 676 + 19.9 + 0 + 0.1 = 696. Nothing was lost, and 97 percent of the energy is in X₀ alone, with 99.9 percent in the first two coefficients. Now quantize with a step of 5: 26/5 = 5.2 rounds to 5; −4.46/5 = −0.89 rounds to −1; the others round to 0. We keep two small integers, [5, −1, 0, 0]. Decode: multiply back to [25, −5, 0, 0] and invert the transform. The first sample is 0.5 × 25 + 0.7071 × (−5) × 0.9239 = 12.5 − 3.27 = 9.23. The four decoded values are about [9.2, 11.1, 13.9, 15.8], and no value is off by more than 0.9 out of a range of 10 to 16. Four numbers became two non-zero integers, and an entropy coder spends only a few bits on each of them.
Now an 8 × 8 block of a smooth sky, with all 64 pixels near 120. After subtracting 128 (JPEG's level shift), the values are near −8. The DC coefficient is 8 × (−8) = −64 (with the orthonormal scaling the DC of an 8 × 8 block is 8 times the mean), and the AC coefficients are tiny, like ±1 or less. With the JPEG quantization step of 16 for DC, the DC becomes −4, and with steps of 11 or more for the first AC terms, they all round to zero. The block is stored as one number plus an "end of block" symbol, a few bits for 64 pixels, against 512 bits raw. A block with a sharp text edge keeps many coefficients and costs perhaps 100 to 200 bits. The average over a photograph, at a good quality, is about 1 to 2 bits per pixel against 24 for raw colour.
intuition: Describe the picture as "mostly this colour, with a gentle gradient, plus a little fine detail", then drop most of the fine detail.
Imagine describing a patch of wall to someone over the phone. You would not read 64 brightness values. You would say "mostly light grey, a bit brighter on the left". That is the first two or three DCT coefficients. The remaining 61 coefficients say things like "a fine checkerboard pattern of strength 2", and if you leave them out, nobody can tell. The DCT organizes the description from coarse to fine so that you can stop whenever the quality is good enough.
It is natural because neighbouring pixels in real images are correlated, and correlation means redundancy. A good transform removes redundancy by rotating the numbers into a coordinate system where they are no longer correlated, and for smooth signals the cosines are very close to the best possible rotation (the KLT). Quantization then costs the least where the eye cares the least. Both the maths and the biology agree on the same order, from coarse to fine.
mistakes: People often think the DCT itself compresses the data. In fact the transform is lossless and produces as many numbers as it takes in. Compression comes from quantization (rounding many small coefficients to zero) and from the entropy coder that stores the zeros cheaply. The transform only makes the data easy to compress by concentrating the energy.
People often think JPEG-style blocks are 8 × 8 because that is optimal. In fact it was a compromise in 1992 between compaction (larger blocks compact smooth areas better) and cost, and artifacts (larger blocks spread ringing and lose detail at edges). Modern codecs choose among sizes from 4 × 4 up to 32 × 32 or 64 × 64 for each region, because flat areas benefit from large blocks and detailed areas from small ones.
People often think high frequencies are unimportant. In fact they carry edges, texture and text. The quantization matrix reduces them gradually. For screenshots, text and graphics, which are full of sharp edges, DCT coding creates visible ringing around edges, and other tools (palette modes, lossless coding, screen-content tools in HEVC and AV1) work better.
People often think video codecs still use the exact real-valued DCT. In fact H.264, HEVC and AV1 use integer approximations with specified exact arithmetic, so that every decoder reconstructs identical pixels; otherwise small floating-point differences would accumulate over a sequence of predicted frames (drift).
People often think audio codecs use the same DCT as JPEG. In fact they use the MDCT, which overlaps consecutive windows by 50 percent and cancels the aliasing between them. A plain block DCT of audio would produce audible clicks at block boundaries, the audio equivalent of blocking artifacts.
friction: At low bitrates, block-based coding shows its limit. Each block is quantized independently, so neighbouring blocks get different errors, and the block grid becomes visible (blocking). Sharp edges inside a block need many coefficients; when they are rounded away, ripples appear around the edge (ringing, also called mosquito noise). Video codecs fight this with in-loop deblocking and sample-adaptive filters, at the cost of complexity and a small blur.
The DCT is not the best transform for everything. It is a fixed, linear, global-per-block basis. Wavelets (JPEG 2000) give better quality at very low rates and no block grid, but they need more computation and memory and never replaced the DCT in video. Residuals after prediction behave differently from pixels: they are less smooth, so HEVC and AV1 add other transforms (sine, identity, transform skip), and the encoder searches over transform type and size per block, which makes encoding much slower (the choice is part of the rate-distortion search that dominates encoder cost). Learned image codecs based on neural networks now beat DCT-based codecs at equal quality in research, but they are heavy for decoders and standardization is slow.
Tuning is subjective. The quantization matrices came from experiments with human viewers under certain viewing conditions. Different displays, ages and viewing distances change what is visible. Repeated compression (decode, edit, re-encode) accumulates errors, which is why JPEG images shared and re-saved many times look worse. And the DCT is not a security or privacy method: the coefficients still contain the image, and also support forensic analysis, for example the detection of double JPEG compression.
practice: As an engineer you rarely write a DCT, but you often choose its settings. For still images, use quality 75 to 85 for photographs on the web as a starting point and compare file sizes by eye; use 4:2:0 chroma subsampling unless you have fine coloured text; consider modern formats (WebP, AVIF, HEIF), which use video-codec transforms and often give files 25 percent or more smaller than JPEG at similar quality (measure on your own images). For video, think in terms of QP or CRF (constant rate factor) rather than transform details: CRF 18 to 23 is typical for H.264 for good quality, and a rise of 6 roughly halves the bitrate.
Understand where content breaks the model. Screen content, thin lines and text need higher quality or special tools. Film grain and noise are costly because noise is not compressible: it fills all frequencies. Pre-filtering noise before encoding saves bits. For streaming, the encoder settings (bitrate ladder, GOP structure) matter more than the transform, but the transform is why a still, smooth scene costs far fewer bits than a noisy, detailed one.
When you meet the DCT elsewhere, such as in perceptual hashing (pHash takes the low-frequency DCT coefficients of a downsized image), audio features (MFCCs use a DCT of log filter-bank energies) or fast image processing in the compressed domain, the reasoning is the same: low-frequency coefficients capture the coarse structure and are stable under small changes. If you want to experiment, use scipy.fft.dctn on an 8 × 8 block, zero out coefficients below a threshold, invert, and watch the error and the image change.
quiz: What does the DCT do to a block of pixels, and is it lossy? || It rewrites the block as a weighted sum of cosine patterns of increasing frequency, giving as many coefficients as pixels. The transform itself is exactly invertible (orthogonal), so it is lossless; the loss comes from quantization.
Why does the DCT compact energy better than the DFT for image blocks? || The DFT assumes the block repeats periodically, so a difference between left and right edges looks like a jump that needs many high frequencies. The DCT corresponds to mirroring the block at its edges, so there is no jump, and smooth blocks put almost all energy in a few low-frequency terms.
Why are high-frequency coefficients quantized more coarsely than low-frequency ones? || Human vision is much less sensitive to fine spatial detail than to broad shapes, and natural-image blocks have little energy at high frequencies anyway. Larger steps there create many zeros and save bits while the error is hardly visible.
For x = [10, 12, 14, 16], the 4-point orthonormal DCT gives about [26, −4.46, 0, −0.32]. What share of the energy is in X₀, and what do you get with step 5? || X₀² = 676 of a total 696, which is 97%. Dividing by 5 and rounding gives [5, −1, 0, 0], and decoding gives about [9.2, 11.1, 13.9, 15.8], with errors under 0.9.
Why do H.264 and HEVC use integer transforms instead of the real DCT? || The decoder must reproduce the encoder's reconstruction exactly, because later frames are predicted from earlier decoded frames. Floating-point results differ between devices and the error would accumulate (drift). An integer transform with specified arithmetic is identical everywhere and cheaper in hardware.
tradeoffs: Choose larger transform blocks (16 × 16 to 64 × 64) for smooth, low-detail regions such as sky, walls and animation backgrounds, where energy compaction is better and side information is smaller; choose small blocks (4 × 4 or 8 × 8) for edges and texture, where large blocks smear ringing over a wide area. Modern codecs let the encoder choose per region by testing both, which costs encoder time (often several times slower encoding for a few percent bitrate savings).
Choose DCT-based coding when you need a mature, hardware-supported standard (JPEG, H.264, HEVC, AV1): decoders exist in every phone, TV and browser, and encoders are fast. Choose wavelets (JPEG 2000) when you need scalable resolution or very low-rate smooth images, at the cost of support and speed. Choose learned codecs only in research or controlled systems, until decoder cost and standards catch up.
Choose a coarser quantizer (higher QP or lower JPEG quality) when bandwidth is the constraint; each step of 6 in QP halves the bitrate in H.264 and HEVC, at the cost of more visible blocking and loss of fine texture. Choose a finer quantizer for content with text, graphics or grain, where artifacts are most visible, or for material that will be edited and re-encoded.
Choose 4:2:0 chroma subsampling for natural video and photos (it halves the raw data with little visible loss); choose 4:4:4 for screen content, thin coloured lines and graphics, where chroma detail is visible.
Choose the MDCT with overlapping windows for audio, and the block DCT for images and video residuals: overlap removes the boundary artifacts in audio at the price of a window delay (important for live and conversational codecs, which then use short windows).
interview: Why does the DCT give better compression than the DFT on image blocks? || The DFT implies periodic extension, so a block whose ends differ creates a discontinuity, spreading energy across many frequencies. The DCT implies an even (mirrored) extension, with no discontinuity, so energy compacts into low frequencies. It is also real-valued, and for highly correlated signals it approaches the optimal KLT.
Walk through JPEG encoding of one block. || Convert to Y/Cb/Cr and subsample chroma; split into 8 × 8 blocks; subtract 128; apply the 2-D DCT; divide by the quantization matrix and round (the lossy step); zigzag scan; code DC as a difference from the previous block and AC as (zero run, value) pairs with Huffman codes, ending with an end-of-block code.
Where does the loss occur, and what controls the quality-size trade-off? || Only in quantization. The step sizes (the matrix scaled by a quality factor, or QP in video) decide how many coefficients become zero. Larger steps give smaller files and more distortion; the rate-distortion trade-off is controlled by that parameter and by the encoder's choices.
Why did video standards move from the real DCT to integer transforms? || Encoder and decoder must reconstruct identical frames, since frames are predicted from decoded frames; floating-point mismatch accumulates as drift. Integer transforms with exact arithmetic remove the mismatch, are cheaper in hardware, and can fold the scaling into quantization.
How does the transform interact with motion compensation in a video codec? || Motion compensation predicts the block from a reference frame, and the transform codes the residual (the difference). Residuals are less smooth than pixels, so the best transform type and size differ; HEVC and AV1 add DST, identity and different sizes and the encoder searches them per block. Good prediction leaves a sparse residual, which the transform and quantizer compress to a few coefficients.
Why does a noisy video cost many more bits than a clean one at the same quality? || Noise has energy at all frequencies, so the coefficients do not compact, the quantizer cannot zero them without visible change, and prediction from the previous frame fails because the noise is random. Pre-filtering or denoising before encoding saves bits.

value: Video is a sequence of pictures, and consecutive pictures are almost the same. In a talk show, the background does not change at all from one frame to the next; in a football match, the pitch slides sideways while the players move a few pixels. Motion compensation exploits this. Instead of storing every frame in full, the encoder describes a block of the current frame as "copy the block from the previous frame, shifted by (dx, dy) pixels", and then stores only the small difference between the shifted copy and the real block. The shift is called a motion vector, and the difference is called the residual.
This is where most of the compression of video comes from. A raw 1080p video at 30 frames per second, with 8-bit samples and 4:2:0 colour, is 1920 × 1080 × 1.5 bytes × 30 ≈ 93 MB per second, about 750 megabits per second. A typical H.264 stream of the same video for streaming uses 3 to 8 megabits per second, a factor of 100 to 250. Compressing each frame alone as a JPEG-like image (the DCT concept) would give a factor of 10 to 20. The remaining factor of 10 comes from not repeating what the previous frames already show.
Every modern video codec is built around this idea: MPEG-2, H.264/AVC, HEVC/H.265, VP9 and AV1 (the codecs concept in L0), and every streaming service delivers video made this way (the video streaming concept in L1). The layer below is optimization (L4): the encoder must find, for each block, the motion vector that minimizes the cost of coding that block, a search problem over thousands of candidates, repeated millions of times per second of video. That search is what makes encoding expensive and decoding cheap, and it is the reason a good encoder produces much smaller files than a fast one.
terms: Motion vector (MV) — a pair of numbers (dx, dy), possibly fractions of a pixel, that says where in a reference frame the best match for a block is found.
Residual — the pixel-by-pixel difference between the block and its motion-compensated prediction; it is what remains to be coded by transform and quantization.
Reference frame — an already decoded frame that is used to predict the current one.
I-frame (intra) — a frame coded without reference to other frames; it can be decoded alone, so it is a random-access point.
P-frame — a frame predicted from earlier frames only.
B-frame — a frame predicted from both earlier and later frames (in display order), so the encoder codes frames out of display order.
GOP (group of pictures) — the run of frames from one I-frame to the next; streaming segments normally start at an I-frame.
SAD — sum of absolute differences between two blocks; the standard cheap measure of how well a candidate matches.
Sub-pixel motion — motion vectors with half- or quarter-pixel precision, using interpolated reference samples.
Rate-distortion cost — J = D + λR, where D is the error, R the number of bits and λ a weight; the encoder picks the choice with the smallest J.
history: Interframe coding was studied from the 1960s, but it became practical when Netravali and Robbins (1979) and then Jain and Jain (1981) described motion estimation by matching blocks of pixels. Block matching was simple enough to implement in hardware, and the three-step search of Koga and co-authors (1981) cut its cost sharply. The first international video standard to use motion-compensated prediction was ITU-T H.261 (1988 to 1990), made for video conferencing over ISDN lines: 16 × 16 pixel macroblocks, one motion vector each, whole-pixel accuracy.
MPEG-1 (1992) added half-pixel vectors and B-frames, which allowed the prediction of a frame from the future as well as the past. MPEG-2 (1994 to 1995) carried this into digital television and DVD. H.263 (1995) improved low-bitrate video. H.264/AVC (2003) made large steps: quarter-pixel vectors, block sizes from 16 × 16 down to 4 × 4, several reference frames per block, a deblocking filter inside the prediction loop, and weighted prediction. It reduced the bitrate by roughly half for the same quality compared with MPEG-2.
HEVC/H.265 (2013) replaced the 16 × 16 macroblock by coding tree units up to 64 × 64 split by a quadtree, improved the interpolation filters (8-tap for luma) and added merge mode and advanced motion vector prediction, which reuse the vectors of neighbouring blocks. AV1 (2018, Alliance for Open Media) added overlapped block motion compensation, warped and global motion models for zooms and rotations, and compound prediction that averages two references. Each generation gave about 30 to 50 percent savings at the same quality, and most of these savings came from better prediction, not from the transform. Faster search patterns, such as diamond and hexagon search, made the search affordable in software encoders like x264 and x265.
how: Take the current frame and split it into blocks (16 × 16 in H.264, variable 4 × 4 to 64 × 64 in HEVC and AV1). For each block the encoder asks: where in an already decoded reference frame is there a block that looks most like this one? It tests candidate positions within a search range, say ±16 pixels, and for each candidate computes a matching cost, usually the sum of absolute differences (SAD) between the block and the candidate. The candidate with the best cost gives the motion vector. The prediction is the reference block at that position; the residual is the current block minus the prediction. The residual is then coded with the DCT, quantization and entropy coding. If the match is good, the residual is nearly zero and costs almost nothing.
Why the encoder needs a search, and what the optimization is. The best vector is not simply the one with the smallest SAD. A vector costs bits to send, and a residual costs bits too, so the encoder minimizes a rate-distortion cost J = D + λR over the choices (vector, block size, reference frame, prediction mode). This is constrained optimization with a Lagrange multiplier λ, which ties together the quality and the bitrate. Full search tests every position: for a ±16 range that is 33 × 33 = 1,089 candidates, each costing 256 absolute differences for a 16 × 16 block, about 280,000 operations per block, or about 2.3 billion per 1080p frame. Real encoders use fast patterns that exploit the fact that the cost surface is mostly smooth: start from a predicted vector (the median of the neighbours' vectors), then test a small diamond or hexagon of positions around the current best, move to the best, and repeat until the centre wins. This takes 20 to 40 candidates instead of 1,089, with a small loss in quality.
Motion is not an integer number of pixels, so the best match often lies between pixels. Codecs interpolate the reference frame to build half-pixel and quarter-pixel positions: H.264 uses a 6-tap filter (1, −5, 20, 20, −5, 1)/32 for half-pixel samples and averages for quarter-pixel ones; HEVC uses 8-tap and 7-tap filters. The encoder first finds the best whole-pixel vector, then refines it by testing the eight half-pixel and then quarter-pixel neighbours. Sub-pixel accuracy gives clear bitrate savings over whole-pixel vectors, and it matters most for slow motion and smooth content.
The motion vectors themselves must be sent, so they are compressed. A vector is predicted from the vectors of the already coded neighbouring blocks (left, above, above-right), and only the difference is coded. In merge and skip modes, the block copies a neighbour's vector and sends no residual, costing a few bits for a whole block. This works because neighbouring blocks usually belong to the same moving object. Large blocks need fewer vectors, small blocks follow object boundaries better, and the encoder decides the partition by testing both under the J cost.
The frame types organize which frames serve as references. An I-frame is coded without any reference, so it is large (5 to 20 times a P-frame) but gives a random access point and stops error propagation. A P-frame predicts from earlier frames. A B-frame predicts from one earlier and one later frame, using the average of two motion-compensated blocks, which reduces noise and handles objects that are uncovered or covered as they move. To code a B-frame the encoder needs the later frame first, so the coding order differs from the display order (for example, I0 P3 B1 B2 P6 B4 B5), and the decoder must buffer and reorder. A typical group of pictures runs from one I-frame to the next, anywhere from 1 to 10 seconds in streaming, and it must align with the segment boundaries of HLS and DASH so that each segment can be decoded alone and a player can switch quality at a segment boundary (the adaptive bitrate concept).
The decoder is simple by comparison: it parses the stream, copies the blocks that the vectors point to (with interpolation), adds the decoded residual, and filters. There is no search. This asymmetry, an expensive encoder run once and a cheap decoder run on every device, matches the economics of broadcasting and streaming. Live encoding is different: the encoder must finish each frame within the frame time, so it uses faster search, fewer B-frames and fewer reference frames, and the file is larger for the same quality.

example: Work through a one-dimensional version with a pen. The reference row has the pixel values [10, 10, 10, 50, 90, 50, 10, 10, 10, 10] (positions 0 to 9): a bright object sits at positions 3 to 5. In the current frame the object has moved two pixels to the right: [10, 10, 10, 10, 10, 50, 90, 50, 10, 10]. Take the block at positions 4 to 7 of the current frame, with values [10, 50, 90, 50]. Without motion compensation, predicting it from the same position in the reference, positions 4 to 7, which hold [90, 50, 10, 10], gives a residual of [−80, 0, 80, 40] and a SAD of 200. That is a large, high-energy residual that costs many bits.
Now search. Candidate shift 1 (compare with reference positions 3 to 6, [50, 90, 50, 10]): SAD = 40 + 40 + 40 + 40 = 160. Candidate shift 2 (positions 2 to 5, [10, 50, 90, 50]): SAD = 0, a perfect match. Candidate shift 3 (positions 1 to 4, [10, 10, 50, 90]): SAD = 0 + 40 + 40 + 40 = 120. The best candidate is the block two positions to the left in the reference, so the motion vector is −2 (the block came from two pixels to the left). The residual is [0, 0, 0, 0]. The encoder sends the vector (a couple of bits, even fewer if the neighbouring block has the same vector) and a flag that says there is no residual. Instead of 4 pixel values it sends a few bits.
A cost estimate for a real picture. A 1080p frame has 8,160 macroblocks of 16 × 16. Suppose the encoder uses a full search over ±16 for each block on one reference: 8,160 × 1,089 candidates × 256 absolute differences ≈ 2.3 × 10⁹ operations per frame, or about 68 × 10⁹ per second at 30 frames per second, too much for a real-time software encoder on one core. With a diamond search of about 30 candidates, the cost is 8,160 × 30 × 256 ≈ 63 × 10⁶ per frame, about 2 × 10⁹ per second: 36 times cheaper. Sub-pixel refinement, several reference frames, and small block sizes then multiply the cost again, so a "slow" encoder preset can be many times slower than a "fast" one for a saving in bitrate of some percent (the exact exchange rate depends on the content and the encoder).
Error propagation: suppose a packet with part of frame P3 is lost. Every block of P6, B4 and B5 that points into the damaged area copies the damage and passes it on, so the error spreads and stays until the next I-frame. This is why live and conferencing systems use short GOPs, periodic intra refresh, or feedback to request a new I-frame.
intuition: Instead of redrawing the whole scene, say "this patch moved two pixels to the left" and fix what changed.
A flip-book animator who wants to save effort can trace the background once and only redraw the parts that move. Motion compensation is the automated version of this, with one extra step: the encoder does not know which parts moved, so it tries shifts and keeps the one that leaves the least to correct.
It is natural because the physical world changes slowly from moment to moment. Objects have inertia, cameras pan smoothly, and the frame rate is high enough that most pixels in the new frame can be found somewhere in the old frame. A search problem turns this observation into bits saved: you pay computation at the encoder (which runs once) to save bits that every viewer downloads (which are paid many times).
mistakes: People often think a video file is a sequence of compressed pictures. In fact only the I-frames are pictures in that sense. Most frames are descriptions of how to build a picture from other frames, so they cannot be decoded without their references. This is why you cannot cut a video at any frame without re-encoding, and why seeking jumps to the previous I-frame and decodes forward.
People often think motion vectors describe the real motion of objects. In fact the encoder picks the vector that minimizes the coding cost, which may not match the true motion, especially in flat or noisy regions where many vectors work equally well. Motion estimation for coding is not the same as optical flow for computer vision, although encoders' vectors are sometimes reused as a cheap motion signal.
People often think B-frames are just bidirectional and so always better. In fact B-frames give the best compression (they often take far fewer bits than P-frames at the same quality), but they need future frames, so they add delay and need frame reordering memory. Live and interactive video uses few or no B-frames.
People often think a higher bitrate makes motion compensation unnecessary. In fact even at very high bitrates, prediction is still the main source of savings, since the alternative of coding every frame in full costs an order of magnitude more. Intra-only codecs (such as ProRes or Motion JPEG) are used for editing, where random access to each frame matters more than size.
People often think the decoder has to search too. In fact the decoder only follows the vectors that the encoder sent. This is why decoding runs in real time on a phone, while a high-quality encode of the same video can run slower than real time on a server.
friction: Search is the dominant cost of encoding. Better compression needs more reference frames, more block sizes, finer sub-pixel precision and more candidate modes, and each multiplies the search. This is why encoders offer presets, why hardware encoders (on GPUs and phones) give larger files than slow software encoders at the same quality, and why per-title encoding for a streaming catalogue is run on large clusters. Next-generation codecs such as AV1 and VVC gain compression at several times the encoding complexity of H.264.
Prediction fails where the world does not move as a rigid block: scene cuts (nothing to predict from, so an I-frame is inserted), fast motion beyond the search range, motion blur, fades and flashes (weighted prediction helps), camera zooms and rotations (warped motion helps), rain, smoke, confetti and film grain (random patterns that cannot be matched). Such content needs many more bits for the same visual quality. Occlusion is another limit: when an object moves, it uncovers background that appears in no earlier frame, which B-frames partly solve by looking forward.
Dependencies create fragility. Because frames depend on one another, one lost or corrupted frame damages many, so streaming needs reliable delivery or recovery. Random access and quality switching are only possible at I-frames, so GOP length is a trade-off between compression (long GOPs) and responsiveness (short GOPs and short segments). Latency is a further cost: B-frame reordering and lookahead for rate control add tens to hundreds of milliseconds, which is a problem for live sports, video calls and cloud gaming. Finally, vectors in the stream make it possible to analyze motion cheaply, but the standard fixes the decoder, not the encoder, so encoder quality varies a lot between implementations.
practice: As an engineer you control the settings that decide how much prediction the encoder may use. Set the GOP (keyframe interval) to match the segment length of your streaming format, typically 2 to 6 seconds, and force keyframes at segment boundaries (for example, x264's keyint and scenecut options, or FFmpeg's -force_key_frames) so every segment starts with an I-frame and adaptive bitrate switching is clean. For live low-latency streams, reduce or disable B-frames and use a short lookahead; for video on demand, use B-frames (3 to 5 is common), several reference frames and a slower preset.
Choose the encoder preset by value: a slower preset saves bitrate but costs compute, and the exchange rate differs between content. For a title that will be streamed millions of times, the extra encoding cost is repaid many times by the saved bandwidth; for a one-off video, it is not. Use constant rate factor (CRF) encoding for quality-targeted VOD and capped bitrate for live. Pre-process noisy sources, because noise cannot be predicted and costs bits.
When you debug video, look at the frame types. ffprobe -show_frames lists I, P and B frames with sizes; a surprisingly large share of I-frames suggests too many scene-cut detections or a too-short keyframe interval. Seeking delays, blocky corruption that fades at the next keyframe, and green or smeared patches after packet loss are all signs of reference-chain damage. For analysis tasks such as content recognition, the I-frames are cheap to decode and give a good sample of the video without decoding every frame.
quiz: What are a motion vector and a residual? || A motion vector says where in a reference frame the best match for a block is found (dx, dy), and the residual is the difference between the block and that matched prediction. The vector and the transform-coded residual are what the encoder stores.
Why does the encoder need a search but the decoder does not? || The encoder does not know the motion, so it tests many candidate positions for each block and keeps the one with the lowest rate-distortion cost. The decoder receives the chosen vectors and simply copies the referenced blocks and adds the residual, so its work is small and fixed.
Why are B-frames coded out of display order, and what does that cost? || A B-frame is predicted from a later frame as well as an earlier one, so the later frame must be coded and decoded first. The price is reordering memory and extra delay, which is why low-latency live video uses few or no B-frames.
A full search over ±16 pixels tests 1,089 positions of a 16 × 16 block. How many absolute differences per 1080p frame, and how much cheaper is a 30-candidate diamond search? || 8,160 blocks × 1,089 × 256 ≈ 2.3 × 10⁹ per frame. A diamond search with 30 candidates uses 8,160 × 30 × 256 ≈ 63 × 10⁶, about 36 times fewer.
A live sports stream has a 6-second GOP and viewers complain that channel switching takes several seconds. What do you change and what does it cost? || Shorten the GOP and segment length (for example, 2 seconds) so a player finds an I-frame sooner. Each I-frame is much larger than a P- or B-frame, so more frequent I-frames raise the bitrate at the same quality.
tradeoffs: Choose long GOPs (4 to 10 seconds) for video on demand, where bandwidth is the main cost and viewers rarely switch or seek. Choose short GOPs (1 to 2 seconds) for live, sports and interactive streams, where fast channel start, quality switching and error recovery matter. Each I-frame costs 5 to 20 times a P-frame, so halving the GOP raises the average bitrate by several percent at equal quality.
Choose B-frames (3 to 5, with a pyramid structure) for VOD, to save a double-digit percentage of bits on typical content; choose none or one for low-latency live and conferencing, where each B-frame adds a frame of delay at 30 fps (33 ms) and needs reorder memory.
Choose a slow software encoder preset when the video will be watched many times or the audience is large (the saving per view multiplies), and a fast or hardware preset when the video is watched once or latency decides. Hardware encoders are many times faster and use less power but usually need more bits for equal quality than the best software encoders.
Choose more reference frames and finer partitioning for complex, high-motion content, accepting longer encode times and more decoder memory; choose fewer for simple content, where extra search finds nothing. Choose a newer codec (HEVC, AV1) when the decoders in your audience devices support it and the saving of 30 to 50 percent bandwidth justifies encode costs of several times; otherwise stay with H.264, which plays everywhere, including older TVs.
Choose intra-only coding for editing, archiving and production workflows, where each frame must be independently accessible and generation losses must be low, and inter coding for distribution. The file is 5 to 10 times larger but frame-accurate seeking is free.
interview: Explain how a video codec achieves 100× compression. || Intra-frame coding with DCT, quantization and entropy coding gives roughly 10 to 20×. Motion compensation adds about 10× more by predicting each block from previous (and future) frames with a motion vector and coding only the small residual. Sub-pixel vectors, multiple references, bidirectional prediction and arithmetic coding add the rest.
Why is motion estimation the most expensive part of an encoder, and how is it made cheaper? || It is a search over positions, block sizes, references and sub-pixel offsets, each needing a cost evaluation. Encoders use predicted starting vectors from neighbours, diamond or hexagon patterns instead of full search, early termination, hierarchical (downsampled) search, and hardware SAD units or SIMD instructions.
What is the rate-distortion cost and how does it change decisions? || J = D + λR picks the choice with the best trade-off between quality and bits. The smallest-SAD vector may need more bits to send, or a small block partition may cost more in side information than it saves in residual. Evaluating J for each candidate mode makes the encoder consistent with a target bitrate.
How do GOP structure and segment length interact in adaptive streaming? || A player can switch bitrate only at a segment start, and a segment must start with an I-frame (closed GOP) to be decodable alone. So keyframes are forced at segment boundaries, and all renditions must have aligned boundaries. Shorter segments give faster switching and lower latency but cost more I-frame bits and more requests.
A packet-loss glitch lasts several seconds in a stream. Why, and how do you reduce it? || The damaged blocks serve as references for later frames, so the error propagates until the next I-frame. Reduce it with shorter GOPs or periodic intra refresh, retransmission or forward error correction, and feedback that triggers an immediate keyframe in conferencing systems.
Why does film grain or sensor noise make video so expensive to encode, and what do you do about it? || Noise is random from frame to frame, so no motion vector matches it and the residual has energy at all frequencies, which the transform and quantizer cannot remove cheaply. Denoise before encoding, or signal the grain as parameters and synthesize it at the decoder, as AV1 does with film grain synthesis.

value: A video stream needs bandwidth, and a viewer's bandwidth is not constant. A phone moves between Wi-Fi and 4G; a household's broadband is shared with other people; a TV's Wi-Fi link drops when a microwave oven runs. If the video is sent at one fixed bitrate, a drop in bandwidth makes the player run out of data and freeze (a stall, or rebuffering), and a high bandwidth is wasted on a low-quality picture. Adaptive bitrate streaming (ABR) solves this by preparing the same video at several quality levels and letting the player switch between them every few seconds, choosing the highest quality that the network can carry right now.
The method is the basis of HLS and DASH, which deliver nearly all internet video and connected-TV streaming, including the video in ad-supported streaming apps. The server is simple: it holds many short files and a text manifest, and any ordinary web server or CDN can deliver them over HTTP. All the intelligence is in the player, which measures what it sees (how fast the last download was, how much video is in its buffer) and decides what to request next. The decision rule matters a lot: it sets how often viewers see a spinning wheel, how soon the picture starts, and how sharp it looks.
The layers below describe the player's problem exactly. Control theory (L4) says what kind of problem it is: the player is a feedback controller whose output is the chosen bitrate, whose sensor is the buffer level and throughput, and whose disturbance is the unpredictable network. Queueing theory (L4) says what the buffer is: a queue that downloads fill and playback empties at a fixed rate of one second of video per second, so its level obeys a simple conservation law (Little's law and the flow-balance equation), and a stall is an empty queue.
terms: Rendition (representation) — one encoded version of the video at a given bitrate and resolution, such as 1080p at 6 Mbps.
Bitrate ladder — the set of renditions offered for a title, from the lowest quality to the highest.
Segment (chunk) — a short piece of video, typically 2 to 6 seconds, that can be fetched and decoded by itself; renditions are cut at the same time boundaries.
Manifest (playlist) — the text file (an HLS .m3u8 playlist or a DASH MPD) that lists the renditions and the segment URLs.
Buffer level — the number of seconds of downloaded video that has not yet been played.
Rebuffering (stall) — playback stops because the buffer is empty; the main thing viewers hate.
Throughput estimate — the player's estimate of download speed, from the time it took to fetch recent segments.
Startup delay — the time from pressing play to the first frame.
QoE (quality of experience) — a score that combines picture quality, stalls, startup delay and the frequency of quality switches.
history: Early internet video used either a download of the whole file or special streaming protocols (RTSP, RTMP) with dedicated servers, which needed their own infrastructure and often could not pass through firewalls. Between 2007 and 2009, three companies moved to plain HTTP with short files: Move Networks, Microsoft (Smooth Streaming, 2008) and Apple (HTTP Live Streaming, announced in 2009 and later written down as RFC 8216 in 2017). HTTP worked through firewalls and caches, and let the existing CDNs serve video at web scale. Adobe offered HTTP Dynamic Streaming. MPEG-DASH, an open standard, was published in 2012 (ISO/IEC 23009-1); CMAF (2018) unified the media format of HLS and DASH, so one set of files can serve both.
The standards define the manifest and the files, not the adaptation algorithm, so researchers and companies built their own. The first designs were throughput-based: estimate the bandwidth from recent downloads and pick the highest bitrate below it. Jiang, Sekar and Zhang's FESTIVE (2012) and the measurement study "Confused, Timid, and Unstable" by Huang and co-authors (IMC 2012) showed that these estimates behave badly: they are noisy, and several players on the same link interfere with each other. Te-Yuan Huang and colleagues at Netflix and Stanford proposed the buffer-based approach BBA (SIGCOMM 2014), which picks the rate from the buffer level and ignores throughput estimates, and tested it on real Netflix users with fewer stalls.
Spiteri, Urgaonkar and Sitaraman's BOLA (INFOCOM 2016) derived a buffer-based rule from Lyapunov optimization with a performance guarantee, and it became the default in the dash.js reference player. Yin, Jindal, Sekar and Sinopoli (SIGCOMM 2015) formulated the choice as model predictive control (MPC), planning several segments ahead. Mao, Netravali and Alizadeh's Pensieve (SIGCOMM 2017) trained a neural network with reinforcement learning to choose bitrates. In parallel, encoding improved: Netflix described per-title encoding (2015) and per-shot encoding (2018), where the ladder is tuned to each video's complexity. Low-latency modes (LL-HLS, LL-DASH with CMAF chunks, 2019 onwards) shrank the buffer to a few seconds, which made adaptation harder.
how: Preparation first. The encoder produces the ladder: for example 6 to 10 renditions, say 400 kbps at 360p, 1 Mbps at 480p, 2.5 Mbps at 720p, 5 Mbps at 1080p and 10 Mbps at higher resolutions (an illustrative ladder; real ones are tuned per title). Each rendition is cut into segments of equal duration (2 to 6 seconds, commonly 4 to 6 for video on demand and 2 or shorter for live), and the cuts all fall on keyframes (the motion compensation concept), because a segment must start with an I-frame to be decodable alone and every rendition must switch at the same times. The manifest lists renditions with their bitrates and resolutions and the URL pattern of the segments. All of this is static files on a CDN.
At playback the player downloads the manifest, picks a first rendition (usually low, so the picture starts fast), and then loops: request the next segment of some rendition, measure how long it took, update its estimates, decide the rendition for the next segment. The key relation comes from the queue: downloading a segment of L seconds at bitrate R bits per second, over a link of throughput C, takes L·R/C seconds. During that time the player consumes L·R/C seconds of buffer, and when the download ends it adds L. So the buffer changes by L − L·R/C = L(1 − R/C) per segment. If R < C, the buffer grows; if R > C, it shrinks, and if it hits zero, the video stalls. This is the flow-balance law of a queue, and it is the whole game: the player wants R as high as possible, but R/C must stay below 1 on average and the buffer must never empty.
Throughput-based rules estimate C from recent downloads, usually with a conservative filter such as the harmonic mean of the last several segments (it is dominated by the slow samples), and choose the highest rendition with R ≤ safety × estimate, for example 0.8 or 0.9. The rule is easy and reacts quickly, but the estimate is noisy: the download of a short segment is affected by TCP slow start, and when the buffer is full the player pauses between requests (an on-off pattern), which makes the measurements misleading. Buffer-based rules (BBA) ignore the estimate and use a map from the buffer level B to the bitrate: below a low "reservoir" (a few segments) choose the lowest rendition; above a high threshold choose the highest; in between, rise linearly. This is a feedback controller in the control-theory sense: the buffer is the state to regulate, and the bitrate is the control input, so when the buffer falls the rate falls, which slows the drain until the system settles where download rate equals playback rate. It cannot overshoot far, because it reacts to the buffer itself. Its weakness is startup, when the buffer is empty and the map says "lowest rate", so real players combine it with throughput estimates in the first seconds.
Hybrid and optimization-based rules combine them. BOLA picks the rendition that maximizes a utility (a function of quality, such as log of bitrate) minus a buffer-dependent penalty, a Lyapunov drift-plus-penalty rule that yields near-optimal utility with a bounded buffer. MPC predicts the throughput over the next few segments, enumerates the sequences of renditions, simulates the buffer for each, and picks the first step of the best sequence under a QoE objective such as: sum of qualities − μ × total stall time − ν × sum of quality changes. Learned players (Pensieve) approximate this with a neural network trained in a simulator.
Additional rules make the system practical: avoid frequent switching (viewers notice every change, so require a margin or a dwell time before switching up), switch down fast but up slowly (an asymmetry because a stall is worse than a lower quality), abandon a slow segment download midway if it will not arrive in time, limit the maximum rendition to the screen size (no 4K stream to a phone), and cap buffer length (30 to 60 seconds is common, less for live and for memory-poor TVs). Sources of information include segment download times, buffer, and the screen and decoder capabilities. Server-side ad insertion needs ladders and segment durations of the ad and the content to match, so that the player sees one continuous stream.

example: Take a ladder of 1, 2, 4 and 8 Mbps, segments of L = 4 seconds, and a starting buffer of 8 seconds. First a throughput-based player with a safety factor of 0.8. The last download showed 6 Mbps, so the target is 4.8 Mbps and the player picks the 4 Mbps rendition. The segment holds 4 s × 4 Mbps = 16 megabits. Suddenly the network drops to 2.5 Mbps. The download takes 16 / 2.5 = 6.4 seconds. During that time the buffer drains by 6.4 seconds, then gains 4 seconds when the segment arrives: 8 − 6.4 + 4 = 5.6 seconds. The player now measures 2.5 Mbps, targets 0.8 × 2.5 = 2.0 and picks the 2 Mbps rendition. That segment is 8 megabits and takes 3.2 seconds, so the buffer becomes 5.6 − 3.2 + 4 = 6.4 seconds, and from then on it grows by 0.8 seconds per segment. There was no stall because the buffer absorbed one bad download. If the player had stayed at 4 Mbps with a 1.5 Mbps link, each segment would take 16 / 1.5 = 10.7 seconds and the buffer would lose 6.7 seconds per segment: 8 seconds of buffer would last only 1.2 segments before the video froze.
Now a buffer-based player with the same ladder, using a simple map: below 6 seconds of buffer pick 1 Mbps; above 18 seconds pick 8 Mbps; in between pick the rendition by linear interpolation (6 to 10 s: 1 Mbps, 10 to 14 s: 2 Mbps, 14 to 18 s: 4 Mbps). Starting with 8 seconds, the player picks 1 Mbps and downloads a 4-megabit segment in 1.6 seconds on the 2.5 Mbps link: the buffer rises to 8 − 1.6 + 4 = 10.4 seconds, then the player picks 2 Mbps: 8 megabits take 3.2 seconds, so the buffer becomes 10.4 − 3.2 + 4 = 11.2 seconds. The buffer keeps growing by 0.8 seconds per segment while the rendition holds at 2 Mbps, until it reaches 14 seconds. There the map asks for 4 Mbps, which is above the link rate, so the buffer starts to fall and the player returns to 2 Mbps. It hovers around 14 seconds, using 2 Mbps most of the time and 4 Mbps now and then, which is the right mix for a 2.5 Mbps link, and it never needed to know the link speed. The cost is a slow start: the player spent its first segments at low quality while the buffer filled.
Startup delay: with a 1 Mbps first segment of 4 seconds (4 megabits) on a 10 Mbps link, the transfer takes 0.4 seconds, and then manifest download, DNS, TLS and request round-trips add perhaps 0.3 to 1 seconds. Viewers are impatient: studies of large video services (Krishnan and Sitaraman, 2012) found that viewers begin to abandon when startup takes more than about 2 seconds, and that abandonment grows with each extra second. That is why the first segment is requested at a low bitrate.
intuition: Drive in the highest gear the road allows, shifting down on a hill before the engine stalls.
The buffer is a fuel tank that the network fills and playback drains at a fixed rate. Quality is how fast you choose to drive, which sets how much fuel each second of video costs to fetch. You cannot see the road ahead, because you do not know what the bandwidth will be in ten seconds, but you can see the fuel gauge. When it is high, you can afford to spend more; when it falls, you must slow down.
The design is natural because it separates two time scales. The buffer absorbs short fluctuations that the player cannot predict, and the rate choice handles long-term trends. A control loop that reads the fuel gauge needs no model of the road. The queueing view explains why this works: the buffer is the integral of the difference between download rate and playback rate, so any rate choice that sits below the average bandwidth keeps it positive.
mistakes: People often think the server picks the quality. In fact the server only holds files. Each player decides for itself, using only information it can see. That is why different devices and apps on the same network can behave differently, and why you tune the player's algorithm, not the CDN, to change stall rates.
People often think that the best algorithm always picks the highest bitrate the measured bandwidth allows. In fact the measured bandwidth is noisy and past values do not guarantee the future, and several players on the same link interact. Picking right at the limit leads to stalls and to oscillation. Safety margins, smoothing and buffer-aware rules exist for this reason.
People often think more quality levels in the ladder is always better. In fact each extra rendition costs encoding time, storage and CDN cache space, and steps closer than about 1.5 times in bitrate are hard to tell apart. A good ladder has steps of roughly 1.5 to 2 times and is tuned to the content: simple animation needs a lower top bitrate than a football match.
People often think rebuffering is the only measure that matters. In fact viewers also react to low resolution, to frequent switches and to long startup. QoE models weigh them, and the weights depend on the content (a stall in a live goal moment is worse) and the audience. Optimizing a single metric, for example zero stalls, leads to a conservative player that sits at low quality.
People often think ABR needs a special streaming server. In fact it works over plain HTTP from any web server or CDN. This is the main reason it won over the earlier streaming protocols: it reuses caches, firewalls and load balancers that already exist.
friction: Estimating the bandwidth is hard. Each segment download is a short TCP transfer, affected by slow start, by the server and CDN, by Wi-Fi interference and by other flows. The measurement from one segment may differ by a factor of two or more from the next. When the buffer is full the player pauses, and the on-off pattern can make a throughput-based player underestimate and pick too low. Several players sharing a link can oscillate against each other. Wireless networks and mobile handovers change the bandwidth abruptly.
Live streaming is the hardest case. The buffer is small (a few seconds, to keep latency low), so there is little room to absorb a bad download, and the player cannot fetch segments that do not exist yet. Low-latency modes use sub-segment chunks, which makes the measurement of throughput from chunk downloads unreliable, because chunks arrive at the encoder's pace and not at the network's. Conservative rules cost quality; aggressive rules cause stalls. In addition, the trade-off between latency and stalls is direct: a buffer of 30 seconds is nearly stall-proof and 3 seconds is not.
There are system-level costs. A video ladder of 8 renditions multiplies encoding and storage by about 8 (somewhat less in practice) and splits the CDN cache over many objects. ABR also hides congestion: when a link is shared, aggressive players take a larger share, which raises fairness questions. Defining QoE is difficult, because the right weights for quality, stalls and switches differ per audience and are measured by A/B tests. And learned algorithms such as Pensieve are trained in simulators, and they can behave unpredictably on networks unlike their training data, so most production players keep simple, well-understood rules.
practice: Start with a standard player that implements a tested rule (for example hls.js or dash.js with BOLA, Shaka Player, ExoPlayer or the native AVPlayer) and tune from data before writing your own. Design the ladder first: 6 to 8 renditions with steps of about 1.5 to 2 times, a lowest rendition small enough for poor mobile networks (for example 200 to 400 kbps) and a top rendition that matches your audience's screens. Prefer per-title or content-aware ladders for catalogues with large viewing volume. Use segments of 4 to 6 seconds for video on demand, 2 seconds or less for low-latency live, and force keyframes at segment boundaries in every rendition.
Measure what viewers experience: collect from the player the startup time, rebuffering ratio (time stalled divided by time watched), number of stalls, average and median bitrate, number of switches and the share of sessions that fail to start. Slice by device (smart TV, phone, browser), by network and by CDN. These are the numbers that tell whether a change to the algorithm or the ladder helps, and they should be checked in an A/B test, not only in a simulator. For connected TV, test on the weakest devices, as TV chipsets and Wi-Fi are usually the bottleneck.
Tune the knobs that matter: the maximum buffer length, the safety factor on the throughput estimate, the dwell time before switching up, the rule for the first segment (start from a throughput estimate cached from the previous session, so startup is both fast and not too low), and the abandon logic for slow downloads. Keep the manifest small and cacheable, serve segments from a CDN with good hit rates, and make sure ad insertion keeps the ladder and segment alignment intact.

A buffer-based rule maps the buffer level directly to a bitrate, which is a stable feedback loop. Its weakness is startup, when the buffer is empty and the rule chooses the lowest quality.

Viewers dislike stalls most, so players drop the rate quickly when the buffer shrinks and raise it only after the buffer and throughput confirm that it is safe.

tradeoffs: Choose throughput-based adaptation when the buffer is small (live, low latency) and you need to react within a segment, and when startup quality matters; choose buffer-based adaptation (BBA, BOLA) for video on demand, where the buffer is large and stability and few stalls matter most. Most production players blend them: throughput for the first segments and for sudden drops, buffer for the steady state.
Choose short segments (1 to 2 seconds) for live and for fast switching, and long segments (4 to 6 seconds) for video on demand. Short segments react faster and allow lower latency but have more HTTP requests (more overhead), larger manifests, and poorer compression, because each segment must start with an I-frame. Long segments compress better and need fewer requests, but react slowly and add startup and latency.
Choose a large maximum buffer (30 to 60 seconds) for stable networks and ample memory, because it absorbs outages; choose a small buffer on memory-limited TVs, for live, or when the viewer may skip around, because a large buffer wastes bandwidth on video that is never watched. The cost of the large buffer is wasted data when users leave and slower reaction to rendition changes.
Choose a conservative policy (lower safety factor, slow upward switches) for audiences on mobile or poor Wi-Fi, where a stall is the worst outcome; choose an aggressive policy for stable wired connections where users judge sharpness. Tune from the measured stall rate and bitrate by device class, in A/B tests.
Choose a rule-based algorithm in production unless you have strong evidence that a learned one wins; learned policies can beat hand-tuned rules in simulation by a few percent of QoE, but they are harder to debug and may fail on unusual networks. Use them where you can run careful experiments and have fallbacks.

The buffer changes by +L − L·R/C = L(1 − R/C). So over time the selected bitrate must average below the throughput, otherwise the buffer drains to zero and playback stalls. The buffer is the integral of the rate mismatch, so it acts as the controller's state.
Why can't a player just pick the highest bitrate below its measured throughput? || The estimate is noisy (slow start, short transfers, sharing, on-off patterns), throughput changes between segments, and a wrong guess costs a stall while a conservative guess only costs quality. Also, if the buffer is full the player pauses, and the next measurement understates capacity. So players smooth estimates, apply safety factors and consider the buffer.
Compare BBA, BOLA and MPC. || BBA maps buffer level to rate with a reservoir and a cushion, ignoring throughput. BOLA maximizes a utility minus a buffer-dependent penalty (Lyapunov optimization), with provable near-optimality and no throughput prediction. MPC predicts throughput for the next few segments and optimizes a QoE objective over rendition sequences, which is powerful but sensitive to prediction errors.
How do you design a bitrate ladder for a catalogue of mixed content? || Choose renditions with 1.5 to 2 times spacing from a low rate usable on poor mobile links up to the top resolution your devices display; use per-title or per-shot encoding to set the rates by content complexity so that easy content gets lower bitrates; check with perceptual metrics such as VMAF; limit the number of renditions, because each adds encoding, storage and cache cost.
What changes for low-latency live streaming? || Latency targets of a few seconds force buffers of a few seconds, so there is little room for error. Segments are split into chunks (CMAF) delivered while still being produced, so segment download time reflects the encoder, not the network, which breaks throughput estimation; players use chunk-level or other signals, more conservative switching and strict catch-up logic. You trade stability and quality for latency.
How would you measure whether a new ABR algorithm is better? || Run an A/B test on real traffic and compare QoE components: startup time, rebuffering ratio, stall count, average bitrate, switch rate, session abandonment and ultimately engagement or retention. Slice by device and network, and use simulation or trace replay only for pre-screening, since real networks and devices behave differently.

@@ fingerprint
value: An audio or video fingerprint is a small digest of a piece of content that stays almost the same when the content is damaged in ordinary ways: recorded through a phone microphone in a noisy bar, re-encoded at a lower bitrate, scaled, cropped, or covered by a channel logo. It is the opposite of a cryptographic hash, where changing one bit changes the whole output. With a fingerprint you can ask: "which known song, film or broadcast does this ten-second sample come from?" and get an answer in a fraction of a second from a database of millions of items.
The system has two halves. The reference side processes every known item (every track in a music catalogue, every frame of every TV channel being broadcast) and stores its fingerprints in an index. The query side processes a short sample (from a phone, or from a television's own screen) in the same way and looks up the fingerprints in the index. A match is declared when many query fingerprints agree on the same item at a consistent time position. Shazam identifies songs this way; YouTube Content ID finds uploads of copyrighted material; broadcasters monitor ad playback; and automatic content recognition (ACR) in smart TVs identifies what is on the screen so that viewing can be measured and ads can be targeted.
The layers below supply the two ingredients. Fourier analysis (L4) turns a sound into a spectrogram, a picture of which frequencies are present at each moment, where the loudest peaks are stable under noise, volume changes and compression. Hashing and hash tables (L3) make the lookup fast: each fingerprint is a number that is used as a key in a huge index, so finding all reference positions that share a fingerprint takes about one memory access per query hash, however large the database is.
terms: Spectrogram — a picture of a sound: time on one axis, frequency on the other, brightness showing energy; computed with a short-time Fourier transform.
Landmark (peak) — a point in the spectrogram that is a local maximum of energy; landmarks survive noise and compression better than other points.
Constellation map — the set of landmarks of a track, drawn as dots; it looks like a star map.
Fingerprint hash — a compact number, for example 32 bits, built from a pair of landmarks and their time difference.
Inverted index — a table from each hash value to the list of (track, time) places where it occurs in the reference.
Time-offset histogram — for one candidate track, a count of matching hashes by the difference between reference time and query time; a true match gives one tall bar.
Robustness — the ability of the fingerprint to survive noise, compression, scaling, cropping and overlays.
Discriminability — the ability to tell different content apart; the opposite risk is a false match.
Bit error rate — the share of bits that differ between two fingerprints; used when fingerprints are compared directly by Hamming distance.
history: The idea of recognizing music by its content was studied by several research groups from the late 1990s. Two papers made it practical. Jaap Haitsma and Ton Kalker at Philips published "A Highly Robust Audio Fingerprinting System" (ISMIR 2002): they cut audio into overlapping frames, computed the energy in 33 frequency bands, and derived one bit per band boundary from the sign of energy differences across both frequency and time, producing a 32-bit sub-fingerprint for each frame. Matching compared blocks of consecutive sub-fingerprints by bit error rate, which handled noise well.
In 2003 Avery Wang published "An Industrial-Strength Audio Search Algorithm" (ISMIR 2003), describing the method of Shazam, the service he co-founded with Chris Barton, Philip Inghelbrecht and Dhiraj Mukherjee. Shazam launched in the UK in 2002 as a service where users dialled a number (2580), held the phone to the music and received a text message with the song name. Wang's key idea was to use pairs of spectrogram peaks and their time difference as hash keys, and to find the match by looking for a consistent time offset. The scheme worked on short, noisy samples, even with several songs mixed. Apple bought Shazam in 2018.
For video, YouTube introduced Content ID in 2007, matching uploaded videos against reference files from rights holders and applying the owner's policy (block, monetize or track). Research on video copy detection grew in the 2000s (the TRECVID evaluation had a copy-detection task), using features such as block-wise brightness patterns, colour histograms and local keypoints. Smart-TV ACR followed in the 2010s: TV makers and companies such as Samba TV, Inscape (Vizio) and Alphonso built fingerprinting into television firmware, sampling pictures from the screen and matching them to a reference of live broadcasts. Privacy rules came with it: in 2017 the US Federal Trade Commission and the New Jersey Attorney General reached a settlement with Vizio over collecting viewing data from its televisions without adequate consent. More recent work uses learned embeddings for audio and video (neural fingerprints), at higher compute cost.
how: Audio first, in the Shazam style. Step 1: convert the sound to a spectrogram. Cut the signal into short overlapping windows (for example 30 to 60 ms), apply a window function and a fast Fourier transform to each, and keep the magnitudes. The result is a grid of time frames by frequency bins. Fourier analysis is the tool that makes this possible: it separates the mixture of waves into their frequencies, and the peaks of that picture are caused by actual tones, so they are robust to added noise (noise raises the floor but rarely removes the loudest peaks), to equalization and to lossy compression.
Step 2: choose landmarks. Find the local maxima of the spectrogram, points higher than all neighbours in a time-frequency neighbourhood, and keep only a limited number per second, spread over the whole frequency range so that no region dominates (for example a few tens per second). The collection of dots is the constellation map. Using only peaks is already a large reduction: a 4-minute track becomes some thousands of dots instead of millions of spectrogram cells. Step 3: form hashes from pairs. A single peak (frequency only) is not specific enough: with a few hundred possible frequency values, every track has many matches. So each peak is used as an anchor and paired with several peaks in a "target zone" a little later in time (for example 1 to 4 seconds ahead and within a frequency band). Each pair gives a hash built from (anchor frequency, target frequency, time difference), packed into about 32 bits, and is stored along with the anchor's time. If each anchor is paired with, say, 5 targets, the track gets roughly 5 times as many hashes as peaks, but each hash is far more specific, because it combines three numbers.
Step 4: index and look up. For the reference, every hash is inserted into an inverted index: hash value → list of (track id, anchor time). A query clip goes through the same steps, giving a few thousand hashes for a 10-second clip. For each query hash, the index returns the list of reference places where it occurs (this is the hash table of L3 at work: one access per hash). Many of those hits are accidents, since 32-bit hashes collide with other tracks' hashes, and noise removes some true hashes. The decisive step is to check geometry. For a true match, each hit has the same time offset: reference time minus query time is the same constant, because the clip is a contiguous piece of the track. So for each candidate track, collect the offsets of all its hits and count them in a histogram. A true track shows a tall bar at one offset (dozens of hits), while accidental hits spread out evenly across offsets with a count of 1 or 2 per bin. Declare a match if the tallest bar exceeds a threshold, and the bar's position tells where in the track the clip came from. Using a pair of peaks and offsets makes the system tolerant of lost peaks, because only a fraction of the hashes need to survive.
Variants exist. The Philips approach computes a dense bit pattern per frame and compares blocks by Hamming distance, which is simple but needs a good index (for example, look up exact matches for some sub-fingerprints, then verify the rest with bit error rate). Chromaprint, the open-source fingerprint behind the AcoustID service, uses chroma features (energy per musical note class) and a learned set of filters. For other kinds of audio, such as broadcast monitoring, the same tools find known jingles and ads.
Video follows the same pattern with different features. A frame is reduced to a tiny greyscale thumbnail, for example 16 × 16 or 32 × 32 pixels, divided into blocks whose average brightness is compared with neighbours, or passed through a DCT whose low-frequency coefficients are kept (the perceptual hash concept); the signs of these comparisons give a bit string. A fingerprint is computed for frames sampled at intervals of a fraction of a second, and the sequence of hashes is matched. As with audio, hits are accumulated by time offset, so a few damaged frames do not matter. Robust video fingerprints must survive re-encoding (the transform coding and motion compensation concepts), scaling, letterboxing, logos, and changes in frame rate.
In ACR for television, the system differs from a music search in one useful way. The television samples its own screen and sends fingerprints to a server, where they are matched against references built continuously by ingesting live broadcasts of hundreds of channels, plus an archive of ads and programmes. The live reference covers only a window of minutes, so the index is small, and a match returns a channel and an air time, or an ad identifier. The small index makes a false match unlikely and a lookup quick.

example: Suppose a track is represented by 30 landmarks per second, and each anchor is paired with 5 targets, giving 150 hashes per second. A 4-minute (240 s) track then has 36,000 hashes. A catalogue of 10 million tracks has 3.6 × 10¹¹ hashes. Stored as a 4-byte hash key plus about 4 to 8 bytes for track id and time, that is about 3 to 4 terabytes of index, spread over a cluster of servers. (These are illustrative figures for the size of the problem, not the numbers of a real service.)
A user holds a phone to a song for 10 seconds. The phone computes 150 × 10 = 1,500 query hashes. Because of the noise, only about 20 percent of the true hashes survive, so about 300 query hashes are present in the reference of the right track. In addition, each query hash also collides with other tracks' hashes: a 32-bit hash space has 4.3 × 10⁹ values, so with 3.6 × 10¹¹ entries a random value would have about 84 entries, though real hash distributions are uneven. The query therefore gets about 1,500 × 84 ≈ 126,000 accidental hits, spread over many tracks, and the 300 true ones.
Now the time-offset check. Each hit is put in a bin (track id, offset), with a bin width of about 30 ms and about 8,000 possible offsets per track, so there are about 10⁷ × 8,000 = 8 × 10¹⁰ bins. The accidental hits fall nearly uniformly among them. The expected number of bins that receive 2 or more accidental hits is about (126,000)² / (2 × 8 × 10¹⁰) ≈ 0.1, and the chance of any bin with 5 accidental hits is negligible. The 300 true hits all land in one bin (or two neighbouring ones, due to jitter), so the winner has about 300 hits against at most 2 for any other bin. A threshold of 5 to 10 gives a safe, confident match, and even if 95 percent of the true hashes were lost (leaving 75), the true bin would still stand out. This is why the method works with very noisy, short samples.
For ACR, take a television that samples a frame about every half second, reduces it to a 64-bit hash, and sends it. The server compares it with the hashes of the last few minutes of 800 channels at 2 hashes per second each: 800 × 120 s × 2 = 192,000 reference hashes in the window. A hash that is within 5 bits (Hamming distance) of exactly one reference entry, and is followed a second later by another hash that matches the same channel at the right offset, identifies the channel and the moment. A single hash is not enough, because a still logo or a black frame matches many channels, so the server requires a short run of consistent matches.
intuition: Identify a song by the constellation of its loudest notes and the gaps between them, not by every sound.
Think of recognizing a friend's face from a few facial landmarks: the distance between eyes and mouth and the position of the nose. Lighting changes, a hat or a smaller picture do not alter those relationships. A fingerprint picks the features that are stable under damage, and ignores everything else. Choosing pairs of peaks makes each feature specific, and requiring many of them to agree at one time offset makes a false positive vanishingly unlikely.
The design is natural because it combines two kinds of redundancy. Within a clip, there are hundreds of independent hashes, so losing most of them does not matter. Across the database, the hash table finds candidates in constant time, and the offset check turns many weak, noisy votes into one strong decision. The overall decision is the sum of many small pieces of evidence, much like a Bloom filter or a vote.
mistakes: People often think a fingerprint is a hash of the audio or video file. In fact a file hash (SHA-256) changes completely when the file is re-encoded or trimmed. A fingerprint is built from perceptual features, so that two different files of the same content give similar fingerprints, and it is looked up in an index, not compared by equality.
People often think matching means finding one identical hash. In fact single hits are cheap to get by accident. The decision comes from the number of hits that agree on a consistent time offset in the same track. Without the offset check, the false-match rate on a large database would be very high.
People often think fingerprinting identifies speakers or understands content. In fact it identifies known recordings by their signal. It cannot recognize a new live performance of a song, a cover version or a person's voice, unless the same recording is in the reference. Cover detection and speaker recognition use different models.
People often think video fingerprints are the same as video file formats or watermarks. In fact a watermark is a signal embedded in the content by the producer, and must be present before distribution; a fingerprint is computed from the content itself and needs no change to it. Watermarks can carry data (an ID); fingerprints can only look things up in a reference.
People often think ACR on a television listens to the room. In fact most TV ACR systems take their samples from the video frames (and sometimes the audio) in the TV's own output, not from a microphone. What they collect, how often, and with what consent is a legal and policy matter, and it differs between countries.
friction: The first problem is the reference. For music, every new release must be ingested before it can be recognized. For live television, the reference must be built in real time from broadcast feeds of every channel and region the audience can see, with a delay between air time and the availability of the reference of only a few seconds, or the match fails. Missing a regional feed, a different cut of the programme or a different ad version means no match or a wrong one.
Ambiguity is the second. The same ad airs on many channels at once, a programme is repeated, or a movie appears with different edits; the content identifier is then not enough to say what the viewer is watching, and the system needs the channel and time as well. Short samples of silence, black frames or static logos carry no information and must be rejected. Video has more failure modes than audio: picture-in-picture, overlays, split screens, aspect-ratio changes, game and app content that is not in the reference, and user-generated edits (mirroring, cropping, speed change) which can defeat simple fingerprints. Pitch or tempo changes similarly defeat audio fingerprints built on exact frequency values.
Scale and cost are the third. Indexes for tens of millions of items are terabytes, and every query makes thousands of lookups. Hash tables must be partitioned and replicated; the index must be updated continuously. Adversaries are the fourth: people who upload copyrighted video deliberately change speed, mirror the picture or add borders to avoid detection, which starts an arms race. Fifth, privacy and regulation: fingerprints taken from a TV reveal what a household watches, which is personal data in many jurisdictions; collection needs consent, clear disclosure, retention limits and the ability to opt out. The legal risk is as important as the technical one.
practice: Match the fingerprint to the task. For music and speech identification, use the landmark-pair approach (or an existing library such as Chromaprint/AcoustID for open music identification). For video copy detection and ACR, use block-based or DCT-based frame hashes combined with temporal verification. For near-duplicate frames, perceptual hashes with Hamming-distance search are enough. For difficult edits, learned embeddings with a vector index give robustness at higher compute.
Design the index for the lookup pattern: keep hashes in a partitioned key-value store or sorted files, make index writes append-only, and decide how long reference data lives (for live TV, minutes to hours in memory; for archives, long-term storage). Always verify matches with a temporal consistency check: require several hashes to agree on content and offset, and measure precision and recall on realistic degraded queries (noise, compression, overlays, speed changes) before trusting a threshold.
Plan the operations: ingest the reference with low latency and monitor the lag, track the match rate per channel and per device model (a sudden fall means a feed or firmware problem), and keep a labelled test set of known content. Treat privacy as a design input: minimize what the device sends (hashes, not frames), define retention, honour opt-outs and regional rules (for example consent under GDPR and state privacy laws), and keep the mapping from fingerprint to household separate and access-controlled.

tradeoffs: Choose landmark-pair hashing with an inverted index when you search a large catalogue (millions of items) with short, noisy queries and need a fast lookup; choose dense per-frame bit patterns with Hamming-distance search when the reference is small (such as a live window of minutes) and you want simplicity. The landmark index is larger and more complex to build; the dense method scales worse with a big catalogue.
Choose more hashes per second (a higher fan-out and more peaks) for noisy conditions, where redundancy rescues the match: it improves recall and robustness but grows the index and the number of lookups roughly in proportion. Choose fewer, more selective hashes when the index must be small or queries are cheap and clean.
Choose a longer query window (10 to 15 seconds) when precision matters (rights enforcement, billing) and a shorter one (3 to 5 seconds) when responsiveness matters (second-screen features, ad measurement in near real time). Each extra second adds more evidence, so the false-match rate falls fast, but the user or system waits.
Choose hand-designed fingerprints (landmarks, DCT hashes) for large-scale, low-cost, explainable matching; choose learned embeddings when you must survive heavy edits (cropping, mirroring, re-recording off a screen) and can pay for model inference and a vector index. Many systems use hand-designed hashes for the first stage and a learned model to re-check hard cases.
Choose on-device processing that sends only hashes when privacy and bandwidth matter, accepting less flexibility to improve the algorithm later (new methods need firmware updates); choose server-side processing of richer data only where consent and law clearly allow it.
interview: Walk through how a Shazam-style system identifies a song. || Compute a spectrogram with an STFT; pick local peaks spread across frequency; pair each anchor peak with several later peaks in a target zone; hash (f1, f2, Δt) into about 32 bits with the anchor time; look up the hashes in an inverted index; for each candidate track build a histogram of reference-minus-query time offsets; a tall bar above a threshold is the match and gives the position.
Why is the false-positive rate low even though hashes collide? || A collision is a single weak vote. A true match needs many hashes to agree on both the track and the time offset, and accidental hits are spread over a huge number of (track, offset) bins, so the chance that several land in one bin is tiny. The threshold is chosen from the measured distribution of accidental counts.
How would you scale such an index to hundreds of millions of tracks? || Partition the index by hash value across machines, so each query hash goes to one shard; keep postings compact (delta-coded times, compressed track ids); put hot shards in memory and the rest on SSD; limit hashes per track by selecting stable peaks; replicate for availability; and do a two-stage match, with a cheap candidate step by hit counts and then exact verification of the top few.
How does ACR differ from music identification? || The reference is live broadcast content, ingested in real time, so the index is a small sliding window and the answer is channel plus time, not a title. The query comes from the TV's own screen, so there is no acoustic noise but there are overlays, ads and repeated content. Latency, regional feeds and privacy dominate the design.
How do you evaluate a fingerprinting system? || Build a test set of known items degraded in realistic ways (noise levels, compression, speed, crop, overlays), and measure precision, recall and time-to-identify as a function of query length. Measure false matches on a large set of content not in the reference. Track the same metrics in production by device and channel.
How do you defend against someone trying to evade detection? || Use features that are invariant to the common edits (mirroring, cropping, speed or pitch change, borders), add augmented copies of references or learned embeddings trained with those edits, use multiple independent fingerprints, and combine with other signals (metadata, human review). Expect an arms race and monitor evasion trends.

@@ perceptualhash
value: A perceptual hash is a short code, usually 64 to 256 bits, computed from the look of an image or a video frame, such that images that look alike get codes that are alike. If you resize a photo, change its compression, brighten it or add a small watermark, a cryptographic hash such as SHA-256 changes completely, but a perceptual hash changes in only a few bits. To decide whether two images are "the same picture", you do not test for equal hashes; you count how many bits differ (the Hamming distance) and compare it to a threshold.
This is the tool for near-duplicate detection at scale. Photo services use it to find repeated uploads and to group similar pictures. Content-moderation systems use it to find known harmful images that have been re-uploaded with small changes: Microsoft's PhotoDNA, Meta's open-source PDQ and similar systems work this way. Video and TV systems use it to match frames, for example in automatic content recognition (ACR), where a television reduces a frame to a small code and a server matches it against a reference. Because the codes are small, billions of them fit in memory and can be searched quickly.
The layers below give the method its two parts. The discrete cosine transform (L2) provides the features: after shrinking the image, the low-frequency DCT coefficients describe its coarse structure (where it is light or dark, the broad shapes), which survives resizing, re-compression and mild edits. Geometry and metric spaces (L4) provide the idea of closeness: the Hamming distance is a metric on bit strings, so "looks similar" becomes "small distance", and the tools of metric spaces (balls, the triangle inequality, the pigeonhole argument) are what make fast search possible.
terms: Perceptual hash — a short bit string computed from image content so that similar-looking images give similar strings.
Hamming distance — the number of bit positions at which two bit strings differ.
Cryptographic hash — a hash designed so that any change to the input changes the output completely; the opposite property.
aHash, dHash, pHash — three simple perceptual hashes: average hash (pixels versus the mean), difference hash (neighbouring pixels compared) and DCT hash (low-frequency DCT coefficients versus their median).
PDQ — Meta's 256-bit perceptual hash, based on a DCT of a downscaled luminance image; open source since 2019.
Threshold — the largest Hamming distance at which two images are called a match.
Multi-index hashing — a search method that splits the code into pieces and uses exact lookups on the pieces to find all codes within a small Hamming distance.
Robustness — resistance of the hash to harmless changes such as resizing, compression, small colour changes and logos.
Collision (false match) — two different images that get hashes within the threshold.
history: The need appeared with the web: large image collections contained many copies of the same picture, and exact hashes could not find them. Early academic work on robust image hashing for copy detection and watermark-style identification appeared in the late 1990s and 2000s (for example Fridrich and Goljan's robust hash functions for digital watermarking, 2000). Marr–Hildreth-operator hashes and block-mean hashes were among the first practical ones. Christoph Zauner's 2010 thesis compared several perceptual hashes systematically, and the open-source pHash library (by Evan Klinger and David Starkweather) made a DCT-based hash widely available.
Neal Krawetz's blog posts "Looks Like It" (2011) and "Kind of Like That" (2013) described simple recipes for the average hash and the difference hash, which anyone could implement in a few lines of code. These became the usual starting points for developers, and they are still in common libraries such as ImageHash for Python.
In the industrial field, Microsoft with Hany Farid developed PhotoDNA (2009) to help find known child sexual abuse images; it is licensed to platforms and the National Center for Missing & Exploited Children. Its algorithm is not public. In August 2019 Facebook (now Meta) open-sourced PDQ (for pictures) and TMK+PDQF (for video), with a published algorithm and reference code, so that smaller platforms can share and match hashes of harmful content. Apple's NeuralHash (2021) used a neural network instead of hand-made features; researchers found collisions and could generate images with chosen hashes within days of its code being examined, an important lesson about adversaries. Research on fast search in Hamming space, such as Norouzi, Punjani and Fleet's multi-index hashing (2012), made searching billions of such codes practical.
how: The standard recipe has four steps: shrink, simplify, measure, threshold. The pHash algorithm in detail. Step 1: convert the image to greyscale (colour changes are ignored, and brightness carries the structure). Step 2: shrink it to 32 × 32 pixels with area averaging. This throws away fine detail, noise and the effects of compression, and makes the result independent of the original size; it also makes the hash small to compute. Step 3: apply a 2-D DCT (the transform coding concept) to the 32 × 32 image and keep only the top-left 8 × 8 block of coefficients: the lowest frequencies, which describe the coarse layout of light and dark. The DC coefficient (the average brightness) is usually dropped or ignored in the median, because it is much larger than the others and says only how bright the picture is overall. Step 4: compute the median of the 64 coefficients and set each bit to 1 if its coefficient is above the median, and 0 otherwise. The result is a 64-bit code.
Why do these bits survive edits? Resizing and mild compression change fine detail but leave the low-frequency coefficients almost unchanged, so most coefficients keep their position relative to the median. A coefficient that is close to the median can flip with a small change, which is why a few bits differ. Changing the brightness or contrast scales or shifts the coefficients but the comparison with the median stays the same. A different picture has unrelated low-frequency patterns, so about half of its bits differ.
The dHash is simpler and needs no transform. Shrink the greyscale image to 9 × 8 pixels. For each row, compare each pixel to its right neighbour: the bit is 1 if the left pixel is brighter. That gives 8 bits for each of the 8 rows, 64 in total. It captures the direction of the gradients, and it is robust to global brightness and contrast changes (a difference in brightness does not change the sign of a difference between neighbours) and is very fast. The aHash compares each pixel of an 8 × 8 thumbnail to the average; it is the cheapest and the least robust. PDQ takes the pHash idea and makes it stronger: it computes a luminance image, downscales it to 64 × 64 with a box filter, applies a 2-D DCT, keeps the 16 × 16 lowest-frequency block (256 coefficients) and thresholds against the median, giving a 256-bit hash, plus a quality score that tells when an image has too little structure (for example, a flat or very blurred one) to give a reliable hash.
Comparison and search come next. The distance between two hashes is popcount(a XOR b), one machine instruction on a modern CPU. A threshold is chosen from data: for 64-bit pHash, distances of about 10 or less are usually treated as "same image", and for 256-bit PDQ a threshold of about 30 bits (for example 31) is a common starting point. Why a longer hash? With random unrelated images, the probability that two 64-bit hashes are within 10 bits of each other is about 10⁻⁸ (the sum of binomial coefficients C(64, k) for k ≤ 10 over 2⁶⁴), which sounds small, but with 100 million images in a database a query sees about one false match by chance. For 256 bits and a threshold of 31, the same chance is about 10⁻³⁷, so false matches are not a concern. (Real images are not uniformly random, so real false-match rates are higher; measure them on your data.)
A linear scan is simple: XOR and count bits against every stored hash, at around a billion comparisons per second per core with vectorized code, so 100 million 64-bit hashes can be scanned in a fraction of a second per query. For billions of hashes, or many queries, use an index. Multi-index hashing uses the pigeonhole principle (metric-space reasoning): split the code into m substrings; if two codes differ in at most r bits, then at least one substring differs in at most ⌊r/m⌋ bits. So look up each substring in its own hash table, enumerate all substrings within radius ⌊r/m⌋, collect the candidates and verify each by the full Hamming distance. Other choices are BK-trees (a tree for metric spaces) and bit-sampling locality-sensitive hashing (Indyk and Motwani, 1998), which hashes on random subsets of bits.
For video, hashes are computed per frame or per sampled frame (every second or every few frames, or at scene changes), and a video is a sequence of hashes. TMK+PDQF adds a temporal part: it combines the frame descriptors over time into a fixed-length vector for a whole video, comparable by cosine similarity. ACR does similar matching on the TV side with small hashes of the screen image and a time-consistency check on the server. The same hash serves two jobs: finding exact-ish duplicates cheaply, and being the first stage before a heavier model.

example: Compute a tiny dHash by hand. Take a 5 × 4 greyscale thumbnail (5 pixels across, 4 rows). The rows are: row 1: 10, 20, 15, 40, 30; row 2: 50, 60, 70, 65, 80; row 3: 30, 25, 20, 40, 45; row 4: 90, 85, 95, 100, 90. For each row, compare each pixel with the pixel to its right, giving 1 if the right pixel is greater and 0 otherwise. Row 1: 20 > 10 gives 1, 15 > 20 gives 0, 40 > 15 gives 1, 30 > 40 gives 0: bits 1010. Row 2: 60 > 50 is 1, 70 > 60 is 1, 65 > 70 is 0, 80 > 65 is 1: bits 1101. Row 3: 25 > 30 is 0, 20 > 25 is 0, 40 > 20 is 1, 45 > 40 is 1: bits 0011. Row 4: 85 > 90 is 0, 95 > 85 is 1, 100 > 95 is 1, 90 > 100 is 0: bits 0110. The 16-bit hash is 1010 1101 0011 0110.
Now brighten the whole image by 20. Every pixel rises by 20, all differences between neighbours are unchanged, and the hash is exactly the same. A cryptographic hash of the pixels would change completely. Next, suppose a small object or watermark changes one pixel: the fourth pixel of row 1 goes from 40 to 14. Row 1 becomes 10, 20, 15, 14, 30. Its bits: 20 > 10 is 1, 15 > 20 is 0, 14 > 15 is 0, 30 > 14 is 1, so 1001. Compared with the original 1010, two bits differ (the third and the fourth); the other rows are unchanged. The Hamming distance is 2 out of 16. A different photo would typically differ in about half the bits, 8 of 16. With a threshold of 3, the edited image matches and the unrelated one does not.
A scale check for pHash with 64-bit codes. Suppose the threshold is 10 bits. Compare two random, unrelated 64-bit codes: the chance of a distance of 10 or less is about 10⁻⁸. Your database has 100 million hashes, so one query expects 100,000,000 × 10⁻⁸ ≈ 1 accidental match. That is why large systems use longer hashes: with 256 bits and a threshold of 31, the chance is about 10⁻³⁷ for random codes. Now the multi-index search for 64 bits and radius 10: split the code into 4 pieces of 16 bits. Two codes within distance 10 must have a piece that differs in at most ⌊10/4⌋ = 2 bits (otherwise each piece would differ in 3 bits or more, for a total of at least 12). The number of 16-bit values within distance 2 of a given piece is 1 + 16 + 120 = 137. So the query needs 4 × 137 = 548 hash-table lookups, and verifies the candidates; this is fast and exact, with no false negatives.
intuition: A thumbnail sketch so rough that small edits do not change it.
Imagine describing a picture to a friend in one short sentence: "dark at the top, bright patch in the lower left, a diagonal edge across." If someone resizes the photo, saves it at a different quality or makes it slightly brighter, the sentence stays the same. If you used a tiny detail, such as the exact value of one pixel, the sentence would change with every edit. The perceptual hash is a very short sentence in numbers, and it uses only the coarse features that edits rarely touch.
The design is natural because the things that people regard as "the same picture" are exactly the coarse structure: low spatial frequencies. The DCT sorts a picture from coarse to fine, so keeping the first few coefficients keeps what survives edits. Comparing against the median, or comparing neighbours, makes each bit depend on an order relation, not on an exact value, and order relations survive monotone changes such as brightness and contrast. Hamming distance then turns "somewhat different" into a count.
mistakes: People often think a perceptual hash is a cryptographic hash that tolerates small changes. In fact it is a different thing, with the opposite goal: equal-looking inputs should give close outputs. It is not collision resistant, offers no security guarantees, and must not be used to verify integrity or to authenticate files.
People often think that two images with the same perceptual hash are the same image. In fact different images can collide, especially simple, low-contrast ones (a blank slide, a mostly white logo, a dark frame), whose coarse structure is nearly identical. A match is a candidate that needs a threshold chosen on data, a quality check and often a second, stronger comparison.
People often think perceptual hashes survive any edit. In fact they survive resizing, re-compression, mild colour and brightness changes and small overlays. They fail on rotation, flipping, strong cropping, perspective changes and big overlays, because those change the coarse layout. Systems add the hashes of flipped or rotated versions to the reference, or use learned embeddings, to cover these.
People often think they are safe against attack. In fact an attacker who knows the algorithm can craft an image that looks different but has a given hash (a second-preimage collision), or can make a small edit that pushes an image beyond the threshold. Neural hashes are not exempt: collisions for NeuralHash were found soon after its release. Treat the match as evidence, not proof, in any setting where someone has a reason to cheat.
People often think a longer hash is always better. In fact beyond a point it adds storage and search cost and also makes the hash sensitive to details that edits change. Length should be chosen from the database size and the required false-match rate: 64 bits for millions of images, 256 bits for billions.
friction: The central difficulty is the trade-off between robustness and discrimination. A threshold that is generous enough to catch a cropped, filtered copy also lets in unrelated images, and one that is strict misses edits. There is no setting that fits all content: flat graphics, text screenshots and dark frames collide, while photos separate well. In practice, one needs a quality score to refuse to hash images with too little structure, per-type thresholds, and a human or model review of borderline matches. In moderation, a false match can wrongly remove a user's picture, and a miss lets harmful content stay, so thresholds are a policy decision as much as an engineering one.
Geometric edits are not handled. Mirroring, rotation by arbitrary angles, heavy cropping and zooming move the content, and the hash changes. Computing hashes for several transforms multiplies index size and cost. Video adds the time dimension: speed changes, dropped frames, inserted ads and different frame rates make frame-by-frame comparison fragile, so systems align sequences with offsets, as in audio fingerprinting.
Scale needs engineering. Searching billions of 256-bit codes within a radius needs an index (multi-index hashing, partitioned scans on GPUs or with SIMD) and careful memory planning: 10 billion 256-bit hashes are 320 GB before any index overhead. Adversaries adapt, so the hash and thresholds need monitoring and updating, and sharing hashes between organizations needs agreed formats and governance. Privacy and law apply as well: the hash of a person's photo is still derived from personal data, and moderation systems operate under rules about what may be scanned and reported.
practice: For a first version use a library: ImageHash (Python) gives aHash, dHash, pHash and wHash; OpenCV has the img_hash module; Meta's PDQ has reference code in C++, Python and Java. Pick pHash or PDQ for robustness to resizing and compression, and dHash when speed matters most. Choose the hash length from the collection size so that the expected number of accidental matches at your threshold is far below one per query, and validate the threshold on pairs of true duplicates (with realistic edits) and pairs of non-duplicates from your own data.
Build the evaluation set first: take sample images and apply the edits you expect (resize, JPEG at several qualities, crop of 5 and 10 percent, brightness, a watermark, mirror), compute the distance distributions for edited and unrelated pairs, and set the threshold where the curves separate; then measure precision and recall. Add a quality filter that skips flat or very blurred images. Store hashes as integers (64-bit or four 64-bit words), scan with XOR and popcount at small scale, and use multi-index hashing or a partitioned index at large scale.
For video and ACR, sample frames at a rate that fits the content (scene changes or every second or so), match sequences, not single frames, and require consistent time offsets. For higher-stakes cases such as moderation, combine hashes with a second stage (a learned embedding or a human review), log the distances of matches, and revisit thresholds regularly. Keep the algorithm and thresholds versioned, so stored hashes are comparable across time.
quiz: Why does a perceptual hash survive resizing and re-compression when SHA-256 does not? || SHA-256 is designed so any change to the input flips about half of the output bits. A perceptual hash is computed from coarse features (low-frequency DCT coefficients or neighbour comparisons of a tiny thumbnail), which resizing and compression barely change, so only a few bits differ.
Describe the steps of the pHash algorithm. || Convert to greyscale, shrink to 32 × 32, apply a 2-D DCT, keep the 8 × 8 lowest-frequency coefficients, compute their median and set each bit to 1 if its coefficient is above the median. The result is a 64-bit code compared by Hamming distance.
In the multi-index method with 64-bit codes, 4 pieces and a radius of 10 bits, why is it enough to search each piece with radius 2? || By the pigeonhole principle: if every piece differed in 3 or more bits, the total would be at least 12 > 10. So any code within 10 bits matches at least one piece within 2 bits, and checking that piece's radius-2 neighbourhood finds all true matches.
With 64-bit hashes and a threshold of 10 bits, the false-match probability for random unrelated pairs is about 10⁻⁸. What happens with 100 million stored hashes, and what do you change? || A single query expects about 100,000,000 × 10⁻⁸ ≈ 1 accidental match. Use a longer hash (such as 256 bits, where the chance is about 10⁻³⁷ at a threshold of 31), a stricter threshold, or a second verification stage.
You must find re-uploads of a banned image that people crop, flip and add text to. Is a pHash index enough? || No. pHash tolerates resizing, compression and small overlays but not mirroring, rotation or strong cropping. Add the hashes of flipped and rotated versions to the index, use stronger local-feature or learned embeddings for hard cases, review borderline matches, and plan for adversaries.
tradeoffs: Choose dHash for speed and simplicity when you need a quick near-duplicate filter on photos (it costs microseconds per image and needs no transform); choose pHash or PDQ when you need more robustness to compression, blur and small edits and can afford a DCT per image. You give up some compute for a lower miss rate.
Choose 64 bits for collections up to a few million images with a threshold around 5 to 10; choose 256 bits (PDQ) for hundreds of millions to billions of images, where false matches by chance must be negligible. The costs are 4 times the memory (320 GB per 10 billion images) and slower scans, but the false-match rate falls by many orders of magnitude.
Choose a linear scan with XOR and popcount below roughly 10⁸ hashes or for rare queries (simple, exact, hardware-friendly); choose multi-index hashing or another index for billions of hashes or heavy query load, at the price of memory for the tables and of tuning the number of pieces to the radius. Choose a tight threshold (low distance) where a wrong match is costly (account actions) and a loose one with human review where a miss is costly (safety triage).
Choose learned embeddings with approximate nearest-neighbour search (the vector search concept) when you must survive crops, rotations and heavy edits, or when "similar" means semantically alike; choose perceptual hashes when you need a tiny code, exact Hamming search, explainability and cheap computation. Embeddings cost 100 to 2,000 bytes per item and GPU inference; hashes cost 8 to 32 bytes and microseconds.
Choose to hash once per scene or at fixed intervals for video; denser sampling finds shorter matching clips and tolerates frame drops, and sparser sampling lowers cost and index size. Tune this against the shortest clip you must catch.
interview: Why use Hamming distance on short codes instead of comparing images directly? || Direct comparison needs the pixels (megabytes each) and is sensitive to resizing and compression. A 64- to 256-bit code is cheap to store and compare (XOR plus popcount), and since the code is built from coarse, edit-stable features, the Hamming distance approximates visual dissimilarity.
How would you search 5 billion 256-bit hashes for all within distance 31? || A linear scan is about 5 × 10⁹ comparisons per query, too slow for many queries. Use multi-index hashing: split the code into m pieces, so a match within radius r must agree within ⌊r/m⌋ on some piece; build tables per piece, probe the radius neighbourhoods, verify candidates by full distance. With r = 31, you need a large m (for example 16 pieces of 16 bits, radius 1 per piece), shard by prefix across machines, and consider GPUs for the verification.
How do you choose the threshold? || Collect labelled pairs: true duplicates with realistic edits, and non-duplicates from the real collection. Plot the two distance distributions, choose the point that gives the required precision at acceptable recall, and check it by false matches per query against the database size. Use separate thresholds for flat or low-quality images.
What edits break pHash and how do you handle them? || Rotation, mirroring, strong cropping, perspective and large overlays change the coarse layout. Index hashes of flipped and rotated copies, use region- or keypoint-based descriptors, or learned embeddings; combine with metadata and review.
Is a perceptual hash safe to use for moderation without review? || No. Collisions occur on simple images and attackers can craft collisions or evasions (as with NeuralHash). Use hashes to find candidates and then verify them with a second model or humans, with thresholds set by the cost of errors, audit logs and an appeals path.
How does perceptual hashing relate to locality-sensitive hashing? || Both map similar items to similar or equal hash values, but an LSH family has a proven collision probability that falls with distance, and is used to find candidates by bucket equality. A perceptual hash is a feature-based code compared by Hamming distance; bit sampling on it is an LSH family for the Hamming space.
