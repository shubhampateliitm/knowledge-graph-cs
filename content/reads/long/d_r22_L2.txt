value: A search engine keeps an inverted index: for every term, a posting list, which is the sorted list of IDs of the documents that contain the term. For a web-scale or log-scale corpus these lists are the largest part of the index. The term "the" may appear in hundreds of millions of documents, so its list holds hundreds of millions of integers. Stored as plain 32-bit integers, the postings of a large index would be several times larger than they need to be, would not fit in memory, and would have to be read from disk on every query.
Posting-list compression fixes this with one observation: the list is sorted, so you do not need to store the IDs. You store the gaps between neighbouring IDs. A list 3, 7, 21, 28 becomes 3, 4, 14, 7. Gaps are small numbers, and small numbers can be written with few bits. The classic book example (Manning, Raghavan and Schütze, Introduction to Information Retrieval) is the Reuters RCV1 collection: the postings take about 400 MB as 32-bit integers, about 116 MB with variable-byte codes and about 101 MB with Elias gamma codes. A shrink of 3.5 to 4 times is typical, and modern block codes keep that ratio while decoding billions of integers per second.
For the layer above, the search engine (L1), this is what makes keyword search cheap. Elasticsearch, Solr, OpenSearch and Lucene all rely on it. A smaller index fits more of itself in the operating system page cache, so queries do less disk I/O. Decoding is fast enough that the CPU cost is repaid by reading fewer bytes. The layers below explain why it works. Information theory (L4) says how many bits a gap needs at minimum: the entropy of the gap distribution. Sorting (L3) is what creates small gaps in the first place; an unsorted list of the same IDs has no small differences to exploit.
terms: Posting list — the sorted list of document IDs (often with term frequencies and positions) for one term.
Document ID (docID) — a small integer that the index assigns to each document, usually in the order the documents were indexed.
Gap (delta) — the difference between a document ID and the previous one in the list; the first gap is the first ID itself.
Variable-byte code (VByte, VInt) — an integer is written in 7-bit groups, one group per byte, and the top bit of each byte says whether more bytes follow.
Elias gamma code — a bit-level code: the number of bits of n written in unary (zeros), then the bits of n itself; it takes 2⌊log₂ n⌋ + 1 bits.
Bit-packing / frame of reference (FOR) — store a block of integers using the same bit width b, where b fits the largest value in the block.
PFOR (patched frame of reference) — FOR with a smaller width that fits most values, plus a short list of exceptions for the rare large values.
Skip list (skip data) — extra entries every N postings (docID and file position) that let a reader jump forward without decoding the postings in between.
Entropy — the average number of bits per symbol that any lossless code needs at minimum, given the distribution of the symbols.
history: Compressing inverted lists is as old as inverted indexes. In the 1970s and 1980s, Peter Elias (1975) published the gamma and delta codes, and Solomon Golomb (1966) published the code for geometric distributions that bears his name. In 1990s information-retrieval work, Witten, Moffat and Bell wrote "Managing Gigabytes" (1994, 2nd edition 1999), which showed that gap coding plus Golomb or Elias codes could shrink an index to a small fraction of the text. The motivation was practical: disks were slow and memory was small, so every byte saved was a saved seek.
In the 2000s the bottleneck moved. Bit-level codes such as gamma are compact but decode one bit at a time, with branches that the CPU predicts badly. Byte-aligned codes (variable-byte) decode faster but are larger. Anh and Moffat's Simple-9 (2005) packed several small numbers into one 32-bit word. Zukowski, Heman, Nes and Boncz introduced PForDelta (ICDE 2006), which packs a block of gaps at a fixed width and patches the exceptions; it is fast because decoding a fixed width has no data-dependent branching. Lucene adopted block-based bit-packing in its 4.1 codec (2013).
Then came SIMD. Lemire and Boytsov's "Decoding billions of integers per second through vectorization" (2012, Software: Practice and Experience 2015) showed that SIMD bit-packing decodes billions of integers per second on one core. Lemire and others later built Stream VByte (2018), which keeps byte-aligned codes but separates the length descriptors from the data so that SIMD can decode them. Ottaviano and Venturini's partitioned Elias-Fano (SIGIR 2014) went in another direction: a code that allows fast random access and "next value at or above x" without decoding everything. Later work reorders document IDs to make gaps smaller (recursive graph bisection, KDD 2016).
how: Step 1, sort and delta. The index builder collects the documents that contain a term in increasing docID order. This is natural, because documents are indexed one after another and each new document gets the next ID; building a segment or merging segments is a merge of sorted lists (L3 sorting). Each docID is replaced by the difference from its predecessor. The sum of all gaps in a list is at most the number of documents, so a term that appears in many documents must have small gaps on average. If a term appears in a fraction p of the documents, the average gap is 1/p.
Step 2, choose a code for the gaps. Information theory gives the target. If a term occurs in each document independently with probability p, the gaps follow a geometric distribution, and its entropy is about log₂(e/p) bits. For p = 1% (average gap 100), that is about 8.1 bits per posting, compared with 32 bits for a raw integer. A frequent term (p = 20%) needs only about 3.4 bits. A rare term (p = 0.001%) needs about 18 bits, but it has few postings. A good code gets close to this bound and, importantly, decodes quickly.
Step 3, the codes. Variable-byte writes each gap in 7-bit groups: values below 128 take one byte, values below 16,384 take two. It is simple and byte-aligned, but a gap of 3 still takes 8 bits. Elias gamma writes a gap n using 2⌊log₂ n⌋ + 1 bits, so a gap of 1 takes 1 bit and a gap of 849 takes 19 bits; it is good for tiny gaps, but slow because it works at the bit level. Golomb and Rice codes pick a parameter b from the average gap and write n as a quotient (unary) and a remainder (b bits), which fits the geometric distribution closely. Frame of reference (FOR) takes a block of gaps, finds the largest, and stores every gap in that many bits. PFOR picks a smaller width that fits about 90% of the values and stores the exceptions separately, so one huge gap does not inflate the whole block.
Step 4, blocks. Lucene, whose design most engines copy, splits a posting list into blocks of 128 gaps. Each full block is stored as a one-byte header (the bit width) followed by the packed gaps, and the last, partial block is written as variable-byte integers. Term frequencies are packed in their own blocks, without deltas, because they are not sorted. Positions (needed for phrase queries) are deltas within one document and live in a separate file, so a query that needs only docIDs never reads them. This split also means each stream can use the width that suits its own values. The fixed block size lets the decoder run an unrolled loop for each bit width, which the compiler and CPU turn into SIMD-like code. Both Lucene's Java implementation and C++ libraries decode at roughly one to a few billion integers per second.
Step 5, skipping. Queries are conjunctions: "apache AND kafka" needs the documents in both lists. The engine walks the shorter list and asks the longer one "advance to the first docID ≥ x". Decoding every block of the long list would waste the savings. So the writer adds skip data: for each block, the last docID in it and its file position, and in Lucene a second level every 4,096 documents. The reader jumps over whole blocks without decoding them, and then decodes only the block where the target must be. Lucene also stores in the skip data the highest possible score in each block, so top-k queries (see BM25) can skip blocks that cannot reach the current best scores (the block-max WAND method).
Step 6, merging and dense lists. When segments merge, each term's lists are decoded, remapped to new docIDs (deleted documents dropped) and encoded again; the lists are already sorted, so the work is linear. For dense lists, gaps are 1 or 2 and even packed codes waste effort, so systems switch to a bitmap (one bit per document, see the Roaring bitmap concept) or to run-length codes. Lucene's query cache and Pinot's inverted indexes use Roaring bitmaps for this reason.

example: Take the posting list from the diagram: documents 3, 7, 21, 28, 150, 151 and 1000. As 32-bit integers it takes 7 × 4 = 28 bytes. First compute the gaps: 3, 4, 14, 7, 122, 1, 849. All but the last fit in one VByte byte, because each is below 128. The last, 849, is 1101010001 in binary, which is 10 bits, so it needs two bytes: the low 7 bits (1010001, with the continue flag set, so the byte is 0xD1) and the high 3 bits (110, so 0x06). The total is 6 + 2 = 8 bytes, 3.5 times smaller than the raw list.
With Elias gamma, a gap n takes 2⌊log₂ n⌋ + 1 bits: gap 3 takes 3 bits (011), gap 4 takes 5 (00100), 14 takes 7, 7 takes 5, 122 takes 13, 1 takes 1, and 849 takes 19. The sum is 53 bits, about 6.6 bytes. Gamma is slightly smaller than VByte here, but you must read bit by bit; decoding 849 requires counting nine zeros first.
FOR is simplest to see. The largest gap is 849, which needs 10 bits, so all seven gaps are stored in 10 bits each: 70 bits. That is worse than gamma because one big value inflates the whole block. PFOR uses width 4 instead: five gaps (3, 4, 14, 7, 1) fit in 4 bits, so the main part is 7 × 4 = 28 bits, and the two large gaps are patched in from a small exception list. A real Lucene block holds 128 gaps, so one outlier in 128 costs little, and the block width is chosen per block.
Now a skipping example. A rare term has 1,000 postings, and a frequent term has 10 million. You want the documents in both. The engine takes each of the 1,000 docIDs and calls advance on the long list. With 128-posting blocks, the long list has about 78,000 blocks. For each candidate, the skip data lets the reader move to the right block by comparing against block-end docIDs, and then decode exactly one block of 128 gaps (about 100 nanoseconds). So the work is about 1,000 block decodes, about 128,000 integers, instead of 10 million. The compression made the data small, and the skip data made the reading short.
intuition: Instead of house numbers 1001, 1005, 1012, write "start at 1001, then +4, then +7".
The idea is natural because a sorted list carries two kinds of information: the order, which is free, and the spacing, which is all that is left to store. When a list is long, the spacing must be small on average, so the spacing needs few bits; when a list is short, the spacing is large but there are few entries. Either way the total is close to a fixed budget of about log₂(N/df) bits per posting. All the codes in this concept are different ways of paying that budget with fast decoding. Entropy sets the lower limit; the engineering is in coming near it while keeping the decoder free of branches and cache misses.
mistakes: People often think better compression always means a better index. In fact the best code is the one that makes queries fastest, not the smallest. Gamma is smaller than VByte for tiny gaps but decodes several times slower. That is why Lucene chooses fixed-width blocks: they cost a few percent more space than the best bit-level codes and decode 5 to 10 times faster.
People often think the compressed list must be decompressed in full to answer a query. In fact skip data lets the engine decode only the blocks it needs. For an AND query between a short and a long list, the long list is almost never decoded in full. The block-max scores allow top-k queries to skip blocks even for OR queries.
People often think document IDs are fixed by the data. In fact the engine assigns them, and the assignment matters. If similar documents (same site, same language, near-duplicates) receive neighbouring IDs, gaps become smaller and lists shrink, in published work by roughly 10% for web crawls. Index sorting and graph-bisection reordering exploit this.
People often think compression only saves disk space. In fact its main gain is speed. Memory bandwidth is limited, and a query that reads 4 times fewer bytes finishes sooner as long as decoding runs faster than the memory can supply raw bytes. SIMD decoders do, which is why compressed lists are often faster to scan than raw ones.
friction: Every query pays decode cost. A block of 128 integers must be decoded before you can look at any of them, so random access inside a block is not possible, and a very selective query still decodes whole blocks. Skip data helps but costs space (a few percent) and complexity. Codes that decode fastest on one CPU (AVX2 or AVX-512) may need different implementations for ARM; Java relies on the JIT and the vector API to approach native speed.
The structure is also hard to update. A compressed block cannot be changed in place: inserting one document ID shifts all following gaps. This is why Lucene segments are immutable and updates are done by writing new segments and merging them later. The merge rewrites and re-encodes the lists, which is real write amplification.
Positions, which phrase queries need, are often the largest part of the index and compress less well than docID gaps, because offsets inside documents look close to random.
practice: Do not write your own codec; use the one in your engine, and tune what the engine exposes. In Elasticsearch and OpenSearch, the index.codec setting changes only stored-field compression; postings are always block-packed. For postings, the practical levers are indirect: keep fields you never search for out of the index (index: false), turn off positions for fields that never need phrase queries (index_options: docs or freqs), and turn off norms on fields that do not need scoring.
If you control document order, sorting the index by a field that clusters similar documents (for example a site or tenant ID, or a timestamp) both shrinks postings and helps range filters. Force-merging a read-only index into fewer segments makes the lists longer and the gaps more regular, and usually saves a few percent. Check the real numbers with the Lucene index-size tools or the Elasticsearch disk usage API (_disk_usage), which split the size by field and by structure (postings, positions, doc values, stored fields).
If you build your own structures, use a library such as Lemire's FastPFor or the Roaring bitmaps library, and measure on your own data: short sparse lists suit VByte or Stream VByte; long dense lists suit bit-packed blocks or bitmaps. Watch the ratio of index size to source size; a sudden growth after a mapping change usually means positions or a new analysed field were added.
tradeoffs: Choose variable-byte or Stream VByte when lists are short, you decode few integers per query and simplicity matters, or when the data is not sorted well (for example, very sparse IDs in a key-value store). It costs 30 to 50% more space than the best bit-level code for dense lists, because a gap of 1 still takes 8 bits. You gain code that is trivial to write and works without block structure.
Choose block bit-packing with patching (the Lucene approach: 128 values, per-block width) when you have long lists and care about throughput. It reaches about 1 to 3 billion integers per second per core with SIMD and keeps the size within 10 to 20% of the entropy bound. You give up random access inside a block and need skip data to avoid decoding blocks you do not need.
Choose Elias-Fano or partitioned Elias-Fano when you need fast "next value at or above x" on very large static collections, and space matters. It gives near the best size and direct access, and academic systems show strong intersection speed. You give up simple incremental building and merging, and it is much less common in production engines.
Choose a bitmap (Roaring) over a list when a list is dense, more than about 1 in 16 documents (a bitmap container costs 8 KB for 65,536 documents, so it wins once a chunk holds more than about 4,096 documents). Below that density, array or run containers inside Roaring win. The price is slower iteration when sparse and no gap compression across chunks.
Choose to reorder document IDs when the corpus is static or batch-built and index size is a large cost. You gain roughly 10% in size and faster intersections; you pay a heavy offline step and lose the rule that ID order equals arrival order.
interview: Why store gaps instead of document IDs, and what does that depend on? || Sorted IDs differ by small amounts, and small numbers need fewer bits. The saving depends on the list being sorted and on density: the average gap is N/df, so frequent terms get tiny gaps. Entropy says about log₂(e × N/df) bits per posting are needed at minimum for random placement. Real corpora have clustering, which makes gaps even more compressible.
Why does Lucene use blocks of 128 with fixed-width packing rather than Elias gamma? || Fixed-width blocks decode with straight-line code and no unpredictable branches, so the CPU and SIMD units run at full speed; gamma needs a variable number of bit reads per integer. The blocks are a few percent larger, but 5 to 10 times faster to decode. 128 is a trade-off: large enough to amortize the bit-width header and use SIMD, small enough that skipping and decoding one block is cheap.
How does an AND query between a 1,000-document list and a 10-million-document list avoid decoding the long list? || The short list drives. For each candidate docID, the reader calls advance on the long list. Skip data stores the last docID and file pointer for each block (and a coarser level), so the reader jumps to the one block that can hold the candidate and decodes only it. About 1,000 blocks are decoded, not 78,000.
How would you update a document in a compressed posting list? || You cannot change a packed block in place. Lucene marks the old document deleted in a live-docs bitmap, indexes the new version in a new segment, and drops deleted postings during later merges, which decode, filter and re-encode the lists.
A new field is added with positions enabled and the index grows 40%. Why, and what do you do? || Positions are stored for every occurrence of every term, not once per document, and offsets inside a document are nearly random, so they compress worse than docID gaps. Turn off positions (index_options: docs or freqs) if the field never needs phrase or proximity queries, or use a separate field for phrase search.
quiz: What is stored in a gap-coded posting list for documents 5, 9, 10, 40? || The first ID and then differences: 5, 4, 1, 30. The original IDs are rebuilt by adding the gaps cumulatively (prefix sum).
Why do fixed-width bit-packed blocks decode faster than Elias gamma codes? || Every integer in a block has the same bit width, so decoding is a fixed unrolled loop that SIMD can run on many integers at once. Gamma has to read a unary length first, which creates data-dependent branches.
How many bytes does VByte need for the gaps 3, 4, 14, 7, 122, 1 and 849? || One byte for each gap below 128 (six gaps) and two bytes for 849, so 8 bytes in total, against 28 bytes as 32-bit integers.
A term is in 1% of 100 million documents. What is the approximate minimum size of its posting list, ignoring frequencies? || It has 1 million postings with an average gap of 100, so the entropy is about log₂(e × 100) ≈ 8.1 bits each, about 1 MB. A raw 32-bit list would be 4 MB.
When would you store a posting list as a bitmap instead of gap-coded blocks? || When the list is dense, roughly more than 1 in 16 documents, so a bit per document costs less than a code per posting, and bitwise AND and OR then give very fast intersections. Sparse lists stay gap-coded.

@@ bm25
value: A keyword search returns every document that contains the query words. For a common query that can be millions of documents, and the user will look at ten. The engine needs a number for each match that says "how well does this document answer this query", so it can sort and return the top few. BM25 is the formula that most search engines use for this number. It is the default scoring function in Lucene, Elasticsearch, OpenSearch, Solr, Tantivy and Vespa's text ranking, and it is the standard baseline in retrieval research.
The score is built from three simple ideas. First, a document that mentions a query word more often is probably more about it, but the gain from each extra mention shrinks (term frequency with saturation). Second, a rare word tells you more than a common word: a match on "compaction" is stronger evidence than a match on "the" (inverse document frequency). Third, a long document mentions more words by chance, so counts are judged against the average document length (length normalization). The score of a document is the sum, over the query terms, of the product of the rarity of the term and its saturated, length-adjusted frequency.
For the layer above, the search engine (L1), BM25 is the ranking step that turns an inverted index into a useful product, and it is cheap: all the inputs (term frequency, document length, document frequency) are already stored in the index. For retrieval-augmented generation (RAG, L1), BM25 matters because vectors are weak at exact names, error codes and rare identifiers, while BM25 is strong there; most production RAG systems combine both. The layers below give the formula its meaning. Probability (L4) provides the model of relevance from which the weights are derived, and information theory (L4) explains why rare terms deserve more weight: a rare event carries more bits.
terms: Term frequency (tf) — how many times a query term occurs in one document.
Document frequency (df) — the number of documents in the whole collection that contain the term.
Inverse document frequency (idf) — a weight that is large for terms with low df and near zero for terms in almost every document.
Document length (dl) and average length (avgdl) — the number of tokens in this document, and the mean over the collection.
k1 — the saturation parameter; it controls how fast extra occurrences stop adding score (default about 1.2).
b — the length-normalization parameter from 0 (ignore length) to 1 (full normalization); default 0.75.
Probability Ranking Principle — the idea that ranking documents by their probability of being relevant gives the best possible result.
Lexical match — a match on the exact word forms (after analysis such as lowercasing or stemming), not on meaning.
Top-k retrieval — returning only the k best documents, which lets the engine skip documents that cannot reach the top.
history: The first idea is from Karen Spärck Jones. In 1972 she proposed in the Journal of Documentation that a term should be weighted by its specificity, that is, by how few documents contain it. This became inverse document frequency. Gerard Salton's SMART system at Cornell combined tf and idf in the vector space model of the 1970s and 1980s, with cosine normalization for length. This "TF-IDF" family was the default for a long time, and Lucene's classic scorer was of this type.
The second line is probabilistic. Maron and Kuhns (1960) first used probability for retrieval. In 1976, Stephen Robertson and Spärck Jones published the "relevance weighting" paper, which derived a term weight from the probability that the term appears in relevant and non-relevant documents. In 1977 Robertson stated the Probability Ranking Principle. The difficulty was term frequency: the natural model, a "two-Poisson" mixture (Harter, 1975), had parameters that were hard to estimate.
In 1994 Robertson and Stephen Walker, at City University London, published "Some simple effective approximations to the 2-Poisson model for probabilistic weighted retrieval" (SIGIR 1994). They replaced the complex model with a simple curve that rises and saturates, and added a length-normalization term. The scheme ran in the Okapi system and was named BM25, one in a numbered series of "best match" weighting functions; its results at TREC-3 (1994) showed that it worked well. Singhal, Buckley and Mitra's pivoted length normalization (1996) was a parallel finding about document length.
Adoption by open-source engines was slow. Lucene used a TF-IDF scorer until Lucene 6.0 (2016), which made BM25 the default; Elasticsearch followed in version 5.0 the same year. Later work added fields (BM25F, Robertson, Zaragoza and Taylor, 2004), fixes for very long documents (BM25+, Lv and Zhai, 2011), and the BEIR benchmark (Thakur and others, 2021), which showed that BM25 stays hard to beat on many out-of-domain tasks, against dense neural retrievers.
how: The formula for one term t in document d is: score(t, d) = idf(t) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × dl / avgdl)). The score of a query is the sum over its terms. Let us read it from the outside in.
Inverse document frequency. In Lucene, idf(t) = ln(1 + (N − df + 0.5) / (df + 0.5)), where N is the number of documents. The 0.5 terms come from the Robertson and Spärck Jones relevance weight with no relevance information (smoothing for small counts). The form is a log of the odds that a random document does not contain the term. It is the information-theory view: the self-information of the event "a document contains t" is −log₂ (df / N) bits, so a term in one document in a million carries about 20 bits, and a term in half of all documents carries 1 bit. The old formula could go negative for terms in more than half of the documents; Lucene's "1 +" inside the log prevents this.
Term-frequency saturation. The fraction tf × (k1 + 1) / (tf + K) rises with tf but flattens. For K = 1.2 (a document of average length), tf = 1 gives 1.0, tf = 2 gives 1.38, tf = 5 gives 1.77, tf = 50 gives 2.15. The ceiling is k1 + 1 = 2.2. This is the probabilistic part: Robertson and Walker showed this hyperbola approximates the behaviour of the two-Poisson model, where a document is either "about" the term, with a high rate, or not. A high k1 makes the curve slower to saturate, so repeated words keep helping; k1 near 0 turns tf into a yes/no feature.
Length normalization. K = k1 × (1 − b + b × dl / avgdl) grows with the document's length. A document twice as long as average has a larger K, so the same tf gives a smaller fraction. With b = 0 the length is ignored; with b = 1 the full ratio dl / avgdl is used. The reasoning is that long documents come in two kinds: those that repeat themselves (verbose, so normalize fully), and those that cover many topics (scope, so do not normalize). The default b = 0.75 is a compromise tuned on news collections.
Where the numbers come from in the index. The inverted index (see the posting-list compression concept) supplies tf for each posting. The term dictionary supplies df. Lucene stores each document's length in a "norm", one byte per field per document, which is a lossy log-scale encoding of the length; the avgdl is a per-field statistic. Nothing else is needed, and this is why BM25 adds almost no index size.
Analysis comes first. Before any counting, an analyzer splits text into tokens, lowercases them and may stem them ("compacting" becomes "compact"), so tf, df and dl are all counted over the analyzed tokens. A change to the analyzer therefore changes every score, and a query must be analyzed in the same way as the documents.
Making top-k fast. Scoring every matching document is too slow when millions match. Because each term's contribution has an upper bound (idf × (k1 + 1)), the engine can use the WAND algorithm (Broder and others, 2003) and Block-Max WAND (Ding and Suel, 2011): keep the score of the k-th best document so far, and skip any document, or a whole 128-document block, whose upper bound is lower. Lucene 8 (2019) added this, storing for each block the largest (tf, norm) pair; Elasticsearch 7 then stopped counting the exact total hits by default. In Lucene 8 the constant factor (k1 + 1) was removed from the formula, since it multiplies all scores equally and does not change the order.
Combining with other signals. BM25 is rarely the whole ranking. Systems use it to retrieve a few hundred candidates, then re-rank them with a learning-to-rank model or a neural cross-encoder, or fuse BM25 with a vector search by reciprocal rank fusion. Because BM25 scores are not on a fixed scale (they depend on idf and on the query), you cannot add them directly to a cosine similarity without normalization.

example: A collection has N = 1,000,000 documents and avgdl = 100 tokens. The query is "kafka compaction". The term "kafka" appears in 10,000 documents, so idf = ln(1 + 990,000.5 / 10,000.5) = 4.61. The term "compaction" appears in 100 documents, so idf = 9.21. Use k1 = 1.2 and b = 0.75.
Document A has 100 tokens and mentions "kafka" 10 times but not "compaction". For kafka with tf = 10 and an average-length document, K = 1.2, so the fraction is 10 × 2.2 / (10 + 1.2) = 1.96. The score is 4.61 × 1.96 = 9.05. Document B has 100 tokens, mentions "kafka" once and "compaction" twice. Kafka: 1 × 2.2 / 2.2 = 1.0, so 4.61. Compaction: 2 × 2.2 / 3.2 = 1.375, so 9.21 × 1.375 = 12.66. The total is 17.26. B wins clearly, although it has fewer mentions in total, because it matches both terms and one of them is rare. A plain sum of term counts would rank A first (10 against 3), and raw TF-IDF (tf × ln(N/df)) would give A 46 against B 23. Saturation and idf together reverse this.
Document C has 400 tokens, mentions "kafka" 10 times and "compaction" once. Now K = 1.2 × (0.25 + 0.75 × 4) = 3.9. Kafka: 10 × 2.2 / 13.9 = 1.58, so 7.29. Compaction: 1 × 2.2 / 4.9 = 0.449, so 4.13. The total is 11.42. If we set b = 0 (no length normalization), C would score 18.25, ahead of B; with b = 1 it would score 10.34. So b decides whether a long document that contains everything outranks a short one that mentions it briefly.
Document D has only 30 tokens, with "kafka" twice and "compaction" once. K = 1.2 × (0.25 + 0.75 × 0.3) = 0.57. Kafka: 2 × 2.2 / 2.57 = 1.71, so 7.88. Compaction: 2.2 / 1.57 = 1.40, so 12.9. The total is 20.78, the top result: a short, dense document that matches both terms.
The ranking is D (20.8), B (17.3), C (11.4), A (9.1). Notice that A has the most occurrences of a query word of all four, and is last.
intuition: A document that mentions a rare word several times is probably about it; mentioning a common word many times matters less, and a long document should not win just because it is long.
The design is natural because each factor answers one question a reader would ask. How surprising is this word? (idf, information.) How much more convincing is each further mention? (saturation, with a limit.) Is this document long, so that it would mention the word anyway? (normalization.) Probability theory says that summing log-odds of independent pieces of evidence is the right way to combine them, and idf is that log-odds weight. The independence assumption is wrong, because words are correlated, but the errors are mild in practice and the ranking stays useful.
mistakes: People often think BM25 is a single fixed formula. In fact it is a family. Implementations differ in the idf formula (Lucene's "1 +" form, the original RSJ form), in the (k1 + 1) factor, and in how length is measured (Lucene stores a lossy one-byte norm). Scores from two engines are not comparable, and the scores are not probabilities or percentages.
People often think a higher k1 or b is always better, or that the defaults are tuned for your data. In fact k1 = 1.2 and b = 0.75 were tuned on newswire. Titles, product names, tweets and logs have different length behaviour; for very short fields, b is often set low, so tune with a labelled query set.
People often think BM25 understands meaning. In fact it matches analysed tokens only. "car" and "automobile" are unrelated, a misspelling gives zero, and the word "bank" is the same in a river and in finance. Analysis (stemming, synonyms) patches some of this; dense embeddings address the rest.
People often think IDF is computed across the whole cluster. In fact Elasticsearch computes document frequency per shard by default, so the same query on a small index with many shards can give different idf values. For small indexes use one shard, or search_type=dfs_query_then_fetch, which first collects global statistics.
People often think scores can be added across fields or compared across queries. In fact scores depend on the query's idf values and are only meaningful for ordering the results of one query. For multi-field documents use BM25F, or combine per-field scores with explicit weights.
friction: BM25 is purely lexical, so recall is limited by vocabulary mismatch: the user's words are not the document's words. This is the main reason that vector search, query expansion and learned sparse models (SPLADE, DeepImpact) exist. On the BEIR benchmark BM25 is competitive, but neural models fine-tuned on in-domain data beat it clearly.
The model assumes the terms are independent and documents are bags of words, so word order, phrases and proximity are ignored; engines add phrase and proximity boosts on top. It has parameters that need tuning per corpus and per field. The length model is crude: for long documents, such as books, the penalty can be too harsh, which BM25+ and other variants address, and for chunked RAG corpora, where all chunks have similar size, b matters less.
Statistics also cause practical problems. Document frequencies are collection-wide, so they shift as the index changes, and they are computed per shard in distributed engines; deleted documents are still counted until segments merge. Rare-term idf is high, so a typo that matches one document by accident can outrank good results. Finally, top-k pruning with WAND depends on score upper bounds, so any custom scoring that breaks the bounds forces full scoring and a large slowdown.
practice: Start with the defaults, and measure before tuning. Build a small judged query set (even 50 to 100 queries with a few labelled results), compute nDCG@10 or MRR, and then change k1 (try 0.9 to 2.0) and b (try 0.3 to 0.9) one at a time. In Elasticsearch you define a custom similarity in the index settings and assign it to the field in the mapping.
Use the explain API (explain: true) to see the idf, tf and norm for each term of one hit; this is the quickest way to debug a surprising ranking. Use field boosts to express "title matters more than body", or a multi_match query with best_fields or cross_fields so that a term is scored across fields correctly. For very short fields such as titles, consider a lower b, since length differences carry little meaning.
For RAG and agent search, use BM25 together with dense vectors. Retrieve 50 to 100 candidates from each, fuse them with reciprocal rank fusion (score = Σ 1 / (60 + rank)), and then re-rank the top few with a cross-encoder. BM25 will rescue the queries with exact names, version numbers and error codes. In Databricks and similar platforms, check whether the vector index offers a hybrid (keyword plus vector) mode before building your own.
tradeoffs: Choose BM25 when queries contain exact terms that must match (names, SKUs, error messages, code), the corpus changes often, you need explainable scores, and latency must be in the low milliseconds at millions of documents. It costs almost nothing extra to index and needs no training. You give up synonyms and paraphrase matching.
Choose dense vector retrieval when users describe needs in their own words and the vocabulary differs from the documents. Embeddings cost an encoder pass per document and per query, a vector index of 1 to 4 KB per document, and are weaker on rare identifiers. You give up exact-match precision and cheap explanations.
Choose hybrid retrieval (BM25 plus vectors with rank fusion) when you can afford two indexes and care about recall across both kinds of queries. Reciprocal rank fusion has one parameter and needs no score calibration, which is why it is the default choice; a weighted sum of normalized scores can be better if you have labelled data. You pay double storage and a more complex pipeline.
Choose learned sparse retrieval (SPLADE) when you want neural term expansion but still want to use an inverted index. It improves recall over BM25 and keeps the index structure, at the cost of a neural model at indexing time and longer posting lists (slower queries).
Choose to tune k1 and b only when you have judged queries and a field with unusual length behaviour. Without measurement, tuning is guessing; the defaults are often close to the best setting.
interview: Explain each part of the BM25 formula and what would break if you removed it. || Without idf, common words dominate and every match counts equally. Without saturation (k1), long repetitive documents and keyword stuffing win, since score grows linearly with tf. Without length normalization (b), long documents are favored because they contain more words. Each part answers one question: how informative is the word, how convincing is repetition, how likely is the match by chance.
Why does BM25 saturate term frequency, and where does k1 come from? || It approximates the two-Poisson model, where a document is either about a term (high rate) or not. The hyperbola tf / (tf + K) rises quickly and flattens at 1, with K controlling the speed. k1 sets the tf at which the curve reaches half its ceiling for an average document; a large k1 lets repetitions keep counting, a small one treats tf as a presence flag.
The same query returns documents in a different order after you change the number of shards of a small Elasticsearch index. Why? || IDF is computed from per-shard statistics unless you request global statistics (dfs_query_then_fetch). With few documents per shard, df and N are noisy, so idf and scores differ. Fix with fewer shards, more data per shard, or the dfs search type; also note that deleted documents count in df until merged.
How would you make top-10 retrieval fast when 5 million documents match? || Use dynamic pruning: WAND or Block-Max WAND. Each term has an upper bound for its score, and blocks of postings carry their maximum possible contribution. Once the heap holds ten scores, any document or block whose bound is below the 10th best score is skipped. This avoids scoring most documents, but the result is exact.
Why not replace BM25 with embeddings entirely? || Embeddings handle paraphrase but are weak on rare tokens, exact identifiers and out-of-domain text; the BEIR results show BM25 is hard to beat zero-shot on several datasets. Vectors also cost more storage and compute, and results are harder to explain. Use both and fuse the rankings, then re-rank the top few.
quiz: In BM25, what does the parameter b control? || How strongly the score is normalized by document length: b = 0 ignores length, b = 1 normalizes fully by dl / avgdl. The common default is 0.75.
Why does the term-frequency part of BM25 flatten as tf grows? || The fraction tf × (k1 + 1) / (tf + K) approaches the ceiling k1 + 1, so each additional occurrence adds less. This models the fact that after a few mentions, more mentions say little more about relevance, and it limits keyword stuffing.
Why is a match on a rare word worth more than a match on a common word? || The idf weight is based on the self-information of the term: −log of the fraction of documents containing it. A term in 100 of 1,000,000 documents gets idf ≈ 9.2, while a term in half of all documents gets ≈ 0.69.
With k1 = 1.2, b = 0.75 and avgdl = 100, what is the tf part for tf = 3 in a document of 100 tokens? || K = 1.2 × (0.25 + 0.75 × 1) = 1.2, so the fraction is 3 × 2.2 / (3 + 1.2) = 6.6 / 4.2 ≈ 1.57. Multiply by the term's idf to get its score.
When would you use BM25F or a multi-field query rather than concatenating all fields into one? || When fields differ in importance and length, such as title versus body. Concatenation hides that a title match is stronger, and the combined length distorts normalization. BM25F combines the term counts across fields with weights before saturation; multi_match or per-field boosts are the practical form.

value: A search engine must keep a dictionary of every distinct term in its index, and the dictionary has to answer three kinds of questions quickly: "where is the posting list of this exact term?", "which terms start with this prefix?" and "which terms are within two typos of this word?" An index over a large log or web corpus can hold hundreds of millions of distinct terms (every identifier, URL fragment and misspelling counts). Stored as a sorted array of strings, that dictionary costs gigabytes of heap and still cannot answer fuzzy queries without scanning it.
A finite-state transducer (FST) is a compact way to store a sorted set of strings, with a number attached to each string. It is a trie (a tree where each edge is a character) in which identical sub-trees are stored only once, so words that share beginnings and endings share states. The number, such as a file offset or a term ordinal, is spread along the edges and added up while you walk. A lookup costs one step per byte of the key, independent of how many keys exist. Because it is an automaton, it can be combined with another automaton, such as a regular expression or an edit-distance machine, to list matches without visiting most keys.
For the layer above, the search engine (L1), the FST is what lets the term index sit in memory or in a memory-mapped file while the full dictionary and posting lists stay on disk. Lucene 4.0 (2012) introduced it, and Elasticsearch, Solr, OpenSearch and the Rust library Tantivy depend on it or on close relatives for term lookup, completion suggesters, synonym maps and fuzzy search. The layers below supply the ideas: finite automata (L3) give the machine model and the minimization that merges equivalent states, and trees and tries (L3) give the prefix-sharing starting point that the FST extends with suffix sharing.
terms: Finite-state automaton (FSA) — a machine with states and labelled transitions that accepts a string if its characters lead from the start state to a final state.
Finite-state transducer (FST) — an automaton whose transitions also carry an output, so that it maps each accepted input string to a value.
Trie — a tree where each path from the root spells a key; keys with the same prefix share the start of their path.
Minimal automaton — the automaton with the fewest states for a given set of strings; two states are merged when everything reachable from them is identical.
Suffix sharing — storing the common endings of different keys (such as "-ing" or "-tion") once, by merging the states that lead to them.
Arc (edge) — one transition: an input byte, an output value and a target state.
Terms index and terms dictionary — in Lucene, the small in-memory index (FST or trie) that points to blocks, and the larger on-disk dictionary of the actual terms.
Levenshtein automaton — an automaton that accepts every string within edit distance n of a given word.
Memory-mapped file — a file that the operating system maps into the address space, so that pages are read from disk only when touched.
history: Finite automata come from Kleene (1951) and Rabin and Scott (1959). Using them to store dictionaries was developed in language technology, where spelling checkers and morphological analyzers needed small dictionaries. Jan Daciuk, Stoyan Mihov, Bruce Watson and Richard Watson published "Incremental construction of minimal acyclic finite-state automata" (Computational Linguistics, 2000), the algorithm that builds a minimal automaton from sorted words in one pass. Transducers, with outputs on arcs, were studied by Mehryar Mohri at AT&T for speech recognition (1997 onward).
In 2010 Michael McCandless, a Lucene committer, wrote an FST implementation for Lucene (see his blog post "Using Finite State Transducers in Lucene"). In his test, 9.8 million terms of a Wikipedia index fit in a 69 MB FST, built in about 8 seconds with less than 256 MB of heap. Lucene 4.0 (October 2012) used it for the terms index and for the suggesters. In the same release Robert Muir used the work of Mihov and Schulz ("Fast approximate search in large dictionary", 2004) on Levenshtein automata to make FuzzyQuery much faster: instead of computing the edit distance for every term, Lucene intersects an automaton with the dictionary.
Andrew Gallant (BurntSushi) wrote the Rust fst crate in 2015 and described it in a widely read post, "Index 1,600,000,000 Keys with Automata and Rust": he stored 1.65 billion Common Crawl URLs (134 GB sorted) in a 27 GB FST in 82 minutes using 56 MB of memory. Tantivy, a Rust search library, uses this crate for its term dictionary. In Lucene 10.3 the block tree terms index changed from an FST to a specialized trie, while FSTs stay in use elsewhere in Lucene (suggesters, synonym maps, analyzers' dictionaries).
how: Building. The builder requires keys in sorted order. It keeps only the path of the last key as "unfrozen" nodes. When the next key shares a prefix with the previous one, the shared part stays open and the remainder of the old path is "frozen": no later key can reach it, because sorted order guarantees that the later keys differ earlier. A frozen node is looked up in a hash table (a registry) by its content: its arcs, their targets and whether it is final. If an identical node exists, the new one is replaced by a pointer to it; this is how suffix sharing happens. Otherwise it is added. Frozen nodes can be written straight to the output, so memory stays small and time is linear. Lucene's registry is bounded, so the result is close to minimal rather than exactly minimal.
Outputs. The value of a key is the sum of the outputs on its arcs. Suppose terms are numbered by their position in sorted order. The builder pushes the common part of outputs as far toward the root as possible, and keeps only the differences on later arcs. For "talk" (0), "talked" (1) and "talks" (2), the arc for "t" carries 0, the arc for "e" carries 1 and the arc for "s" carries 2. Because the shared part is moved forward, two branches that differ only in their first arc (like "t" and "w" in the diagram) can still lead into the same state. The output algebra needs addition, subtraction and a common prefix; for integers the prefix is the minimum.
Lookup. To find a key, start at the root and for each byte of the key follow the arc with that label (a binary search or direct addressing, depending on how many arcs the node has), adding its output. If the walk ends in a final state, the key exists and its value is the sum. The cost is O(key length), not O(log n). Nodes with few arcs are scanned linearly; nodes with many arcs use a table indexed by the byte value. No decompression is needed, because the structure is read in place: states are stored as compact byte sequences with relative offsets, so it can be memory-mapped, and the operating system loads only the pages a query touches.
How Lucene uses it. Lucene's default "block tree" terms dictionary does not put every term in the FST. It groups terms that share a prefix into blocks of roughly 25 to 48 terms stored on disk, and the in-memory index maps each block's prefix to the file pointer of the block. A lookup walks the FST to find the longest matching prefix, jumps to the block and scans the few suffixes inside it. This keeps the memory per term at a few bytes or less. From Lucene 10.3 the index is a specialized trie instead of an FST, with the same job. Whole-term FSTs are used where the full set must be searched with automata, such as the completion suggester, synonym maps and the term dictionaries of Rust and other engines.
Prefix, regex and fuzzy queries. A prefix query walks the FST to the prefix and enumerates everything below it. For a regular expression or an edit-distance query, the engine builds an automaton for the pattern and walks both machines together: it holds a pair (FST state, pattern state), takes only the arcs that the pattern state can accept, and stops a branch when the pattern state is dead. For "kafka" with at most 1 edit, the pattern automaton has a few dozen states, and the walk visits only the FST paths that stay within one edit, which is a tiny part of the dictionary. This is the contribution of the automata concept: the same formalism describes both the dictionary and the query, so combining them is just an intersection.
Segments. An FST is immutable, since a change in one key could alter the shared states of many others. Each Lucene segment has its own, and merging segments builds a new one from the merged sorted terms, which is cheap because the input is already sorted. This is why the term index never needs a lock or an in-place update: readers use old segments while new ones are built.

example: Build the FST for the six words in the diagram, whose ordinals are talk 0, talked 1, talks 2, walk 3, walked 4 and walks 5. A plain trie has 15 nodes: a root, seven nodes for the branch of "t" (t, ta, tal, talk, talke, talked, talks) and seven for the branch of "w". Insert "talk", "talked" and "talks" in this order. They share the path t-a-l-k, and then the path splits into "e-d" and "s". Now insert "walk". It shares nothing with "talks", so the builder freezes the whole t-branch from the bottom. The node after "d" and the node after "s" are both final and have no arcs, so they are identical, and they merge into one state, F. The other nodes are unique so far, so they are kept. Next the builder inserts "walk", "walked" and "walks", and when it freezes the w-branch, each of its nodes is identical to the node at the same place in the t-branch, so it is replaced by a pointer to the existing node. Only the first arcs differ, and both point to the same state A. The result has 7 states: the root, A, B, C, D, E and F.
Now the outputs. The three t-words have 0, 1 and 2, so the smallest, 0, goes on the "t" arc; the differences go on the "e" arc (1) and the "s" arc (2). For the w-words the smallest is 3, which goes on the "w" arc, and the differences are 1 and 2 again. These are the same differences as in the t-branch, which is exactly why the lower part of the two branches can be one shared piece. Lookup of "walked" sums 3 + 1 = 4, the correct ordinal.
Now a size estimate. A sorted array of 100 million terms of 12 bytes on average needs about 1.2 GB for the characters plus 400 MB of offsets. Real FSTs take roughly 5 to 15 bytes per key including values: McCandless saw 69 MB for 9.8 million Wikipedia terms (about 7 bytes each), and Gallant saw 27 GB for 1.65 billion long URLs (about 16 bytes each). The block tree goes further: with blocks of about 30 terms, the index has about 3 million entries instead of 100 million, so it takes tens of megabytes.
For fuzzy search, take the query "kafka" with at most 1 edit. The walk keeps the number of edits spent so far in each automaton state. From the root, the arc "k" costs nothing; any other first byte costs one edit (a substitution) and then the rest must match "afka" exactly. A branch that has spent its edit and then meets a wrong byte is dropped at once. At each depth only a handful of paths are alive, roughly the key length times the alphabet size times the number of edits, so the query touches hundreds of states, not hundreds of millions of terms.
intuition: A trie that also merges common endings, like sharing both "pre-" and "-tion" among many words.
The design is natural because language and identifiers are repetitive: the same prefixes and the same endings appear under thousands of different stems. A trie removes repeated beginnings. The minimal automaton removes repeated endings too, since two states with the same future need only one copy. Putting the values on the arcs, in a way that lets them add up, keeps this sharing intact even when each key has a different value. And because the whole thing is a machine, "does it match this pattern" becomes "run two machines together".
mistakes: People often think Lucene stores its whole term dictionary in an FST. In fact the block tree stores only prefixes in the FST (and, since 10.3, in a trie); the actual terms are in on-disk blocks. Whole-term FSTs appear in suggesters, synonyms and some other engines.
People often think an FST is a compressed hash map with fast updates. In fact it is built once from sorted input and cannot be modified; changes need a rebuild, which is why it fits immutable segments. It also does not beat a general-purpose compressor on size: Gallant's gzip result for the same URLs was smaller (15 GB against 27 GB), but gzip cannot be searched without decompressing.
People often think the output is always the sum of numbers or that the value is stored at the end. In fact it is spread over the arcs, and the builder moves common parts forward; that is why the builder needs the output type to support a common prefix and subtraction. Byte sequences and sets of ordinals can be outputs too.
People often think the FST makes lookups faster than a hash table. In fact a hash lookup takes one probe and an FST lookup takes one step per byte, with memory reads that may miss the cache. The FST wins on memory, on ordered iteration and on prefix, range and automaton queries, not on point lookups.
friction: Immutability and sorted input are the hard limits. A segment's terms must be sorted before the build, and any change needs a new FST. Build cost is small but not zero: Gallant needed 82 minutes for 1.65 billion keys even with sorted input, and 240 minutes when the input was unsorted.
Size depends on the data. Suffix sharing helps for natural-language words and structured identifiers but little for random strings such as hashes or UUIDs, whose endings are all different; in that case an FST is no smaller than a trie and may be larger than the keys themselves with their outputs. Wide outputs (offsets of 8 bytes that are all distinct) cannot be shared and dominate the size, which is one reason Lucene keeps the FST small by pointing to blocks.
Read performance matters when the FST is not in memory. A lookup takes one dependent memory read per byte of the key, and when the pages are cold, each read can be a disk read. Gallant measured a wildcard query over the 27 GB FST at about 2 seconds when cold and 0.1 seconds when cached. Older Lucene versions kept the term index FSTs on the Java heap, which put pressure on garbage collection; newer ones can read them from memory-mapped files. Lucene 10.3 replaced the FST in this index with a specialized trie.
Fuzzy queries are limited too: Lucene allows at most 2 edits, and a pattern that starts with a wildcard still visits a large part of the dictionary.
practice: You rarely write an FST; you choose the settings and the field types that decide how large the term index is. In Elasticsearch, check the memory used by the terms index with the index stats or the _cat/segments API (the memory columns), and the disk usage API for the share of the terms dictionary. Fields never searched by term (only used for aggregations) should have index: false and rely on doc values; every indexed field with many unique values, such as IDs or URLs, makes a large terms dictionary.
Be careful with high-cardinality keyword fields. Random IDs (UUIDs) compress badly in the term dictionary, because they share few prefixes. If you control the ID format, prefixes that are common (such as a time-ordered or tenant-ordered prefix) make the dictionary and its index smaller and make lookups more cache friendly. Elasticsearch's auto-generated IDs follow this idea.
For prefix search-as-you-type, use the dedicated field types (search_as_you_type, edge n-grams, or the completion suggester). The completion suggester keeps an FST per segment in memory, so it is fast but its size should be monitored. For fuzzy search, limit fuzziness to 1 or 2, set prefix_length to 1 or more (the first characters must match exactly, which prunes the walk), and cap max_expansions.
tradeoffs: Choose an FST (or the block tree structure built on it) when you have a large, mostly static set of sorted string keys, need prefix, range or automaton queries as well as exact lookups, and memory is the limit. It gives a size 2 to 10 times smaller than a trie or sorted array and O(key length) lookups. You give up updates, and point lookups are slower than in a hash table.
Choose a hash map when you have point lookups only and the keys change often; a lookup is one probe and updates are cheap, but the memory per key is high and there is no ordering or prefix search.
Choose a plain trie, or the specialized trie of Lucene 10.3, when decoding simplicity matters more than the last bit of size. Suffix sharing probably saves little in an index of prefixes, so giving it up costs little; you lose some compression and gain a layout that is easier to read in place.
Choose compression with a general codec (such as Zstd) when you only need to store the dictionary and always read it entirely. It is usually smaller, as the URL example shows, but you cannot search it in place.
interview: Why does a minimal FST need sorted input, and what does the builder keep in memory? || With sorted input, once a new key diverges from the previous one, the old branch can never gain new keys, so it can be frozen, checked against a registry of equivalent states and written out. The builder holds only the path of the last key plus a bounded registry, so memory is small and time is linear. Unsorted input would force keeping and revisiting every state.
Lucene does not put every term in the FST. What does it put there and why? || The block tree terms index stores prefixes that point to blocks of roughly 25 to 48 terms on disk. This makes the in-memory structure hold millions of entries rather than hundreds of millions, and a lookup becomes: walk the index to the prefix, read one block, scan its suffixes. The price is a small scan and one disk read per lookup, compared with a full in-memory dictionary.
How does a fuzzy query avoid comparing the query against every term? || It builds a Levenshtein automaton that accepts all strings within n edits of the query (n is at most 2), and walks it together with the FST. A branch ends as soon as the automaton enters a dead state, so only a few hundred paths are visited. Setting a mandatory exact prefix (prefix_length) prunes still more.
Why can an FST not be updated in place, and what does a search engine do about it? || Suffix sharing means one state can be reachable from many keys, so changing one key can change states used by others. Engines therefore build a new FST per immutable segment and merge segments in the background, which rebuilds the structure from the merged sorted terms.
Why did Lucene 10.3 replace the FST in the block tree index with a trie? || The release notes only state the change. A reasonable explanation is that the index holds prefixes, where suffix sharing saves little, so a trie with a simpler layout is enough. FSTs remain where sharing across whole terms helps, such as suggesters.
quiz: What is the difference between a trie and a minimal FST for the same set of words? || A trie shares only common prefixes. A minimal FST also merges states with identical futures, so it shares common suffixes, and it carries output values on its arcs.
How does an FST return a value for a key? || It follows the arcs for each byte of the key and adds up the outputs on those arcs. If it ends in a final state, the sum is the value (for example a term ordinal or a file offset).
Why must the keys be added in sorted order during construction? || Sorted order guarantees that, after a key diverges from the previous one, no later key can reach the old branch. That branch can be frozen, merged with an equal earlier state and written out, which keeps memory small.
In the example, the trie for talk, talked, talks, walk, walked, walks has 15 nodes. How many states does the minimal FST need? || Seven: the root, the states A, B, C and D along the shared a-l-k tail, state E after "e", and one shared final state F after "d" or "s".
When is an FST a poor choice compared with a hash map or a general compressor? || When keys change often (it is immutable), when you only need point lookups (hash is faster), when keys are random like UUIDs (little sharing), or when you never search the data in place (a compressor such as Zstd is smaller).

@@ docvalues
value: An inverted index is built to answer "which documents contain this term?" Many queries need the opposite question: "for these documents, what is the value of this field?" Sorting by price, grouping by country, computing the average latency of 2 million matching log lines, or reading a number inside a script all need the value of one field for each of many documents. The inverted index is a poor tool for this. To find the value for document 4711 you would have to look through every term of the field to see which posting list contains 4711.
Doc values are Lucene's answer: a column store inside every segment. For each field, the values of all documents are written next to each other, indexed by document ID, in a compact encoded form, in a file that the operating system maps into memory. To read "price of document 4711" you jump to a position computed from 4711. To sum a field over a million matches, you read one dense array in docID order. Elasticsearch, OpenSearch and Solr all use doc values for sorting, aggregations, scripting and (in newer versions) for rebuilding the source of a document.
For the layer above, the search engine (L1), this gives one index that answers both questions, so a single system can run full-text search and analytics on the same data. The layer below that explains the speed is cache lines and locality (L3): a column of similar small values packs many values into each 64-byte cache line and is read sequentially, so the CPU and the disk prefetcher work at full speed, while a row-wise layout would drag the whole document through the cache to read one field.
terms: Doc values — Lucene's per-field, per-segment column of values indexed by document ID.
Column store — a layout in which all values of one field are stored together, instead of all fields of one record together.
Inverted index — the term-to-documents structure; the opposite direction from doc values.
FieldCache / fielddata — the older approach: build the docID-to-value array at query time by reading the inverted index, and keep it on the Java heap.
Ordinal — a small integer that stands for a distinct string value; the strings are sorted and numbered from 0.
Global ordinals — a mapping that gives the same ordinal to the same string across all segments of a shard, so that segment results can be combined without comparing strings.
Doc value types — NUMERIC (one number per document), BINARY (bytes), SORTED (one string per document), SORTED_NUMERIC (several numbers) and SORTED_SET (several strings).
Memory-mapped file — a file the operating system exposes as memory; pages are loaded on demand and kept in the page cache.
Segment — an immutable unit of a Lucene index; doc values are written once per segment and never changed.
history: Before Lucene 4.0, sorting and faceting used the FieldCache. On first use, Lucene walked every term of the field in the inverted index and, for each term, every posting, filling a docID-indexed array on the Java heap ("uninverting" the index). This was slow after every reopen of the index, used heap proportional to the data, and caused long garbage collection pauses. Elasticsearch called its version "fielddata" and many early production outages came from fielddata filling the heap.
The doc values project (led by Simon Willnauer, with Robert Muir, Michael McCandless and others, 2011 to 2012) moved the work from query time to index time. Values are written to disk when a segment is created, and read through memory-mapped files, so there is no warm-up and the heap is not used. Lucene 4.0 (October 2012) shipped doc values. Column stores in databases were older: Stonebraker's C-Store (2005) and MonetDB showed the speed of columnar layouts for analytics, and doc values apply the same idea inside a search engine.
Elasticsearch turned doc values on by default for non-text fields in version 2.0 (2015), and later removed the heap-based fielddata for them. Lucene 7.0 (2017) made them sparse-aware, so a field present in only 1% of documents no longer costs space for every document. Lucene 10 (2024) added a skip index for doc values, which stores the minimum and maximum of each block of 4,096 documents so range queries and sorts can skip blocks. Newer Elasticsearch versions use doc values to rebuild a document's source ("synthetic source") and save storage.
how: Writing. When Lucene flushes an in-memory buffer to a new segment, it writes each doc-values field as a column. For a NUMERIC field, it processes the values in blocks of 16,384 documents (in Lucene 8 and later formats). For each block it finds the minimum, the greatest common divisor (GCD) of the differences, and the range. If the values are, say, timestamps in milliseconds that are all multiples of 1,000, the GCD is 1,000. It then stores (value − min) / GCD with the smallest bit width that fits the block, or, if the block has few distinct values (up to 256), a table of the values and small codes pointing into it. A field with all values equal takes almost no space.
SORTED (one string per document) uses two parts. A dictionary holds the distinct strings in sorted order, compressed in small blocks with shared prefixes (this is where the FST and block ideas return, in simple form). The column holds, for each document, the ordinal of its string, bit-packed. SORTED_SET stores a list of ordinals per document. SORTED_NUMERIC stores several numbers per document, sorted, with a counts structure. When only some documents have a value, an IndexedDISI structure marks which documents are present in blocks of 65,536 documents: dense blocks as bitsets, sparse blocks as sorted arrays. The reader can then jump to the value index of the n-th document that has a value.
Reading. A reader asks for the iterator of a field in a segment and calls advanceExact(docID); then it reads the value at that position. For a bit-packed column, the position is docID × bits, so reading is a shift and a mask on memory-mapped bytes. Nothing is decoded in advance: the reader never loads the whole column. The pages that are touched come into the operating system page cache, and the rest stay on disk. If the machine has enough free memory, hot columns behave like in-memory arrays without using the Java heap. This is the reason Elasticsearch documentation tells you to leave half of the RAM to the file system cache.
Sorting. To sort the top 10 of a hit list by price, the collector keeps a priority queue of 10 entries. For each matching document, it reads the price from the column and compares it with the smallest value in the queue; most documents are rejected after one read and one comparison. If the index itself is sorted by that field (index sorting), the collector can stop early after the first 10 matches in each segment. The new skip index (min and max per block of 4,096 documents) lets a range query or a sort skip entire blocks that cannot qualify.
Aggregations. For a terms aggregation on a string field, the engine does not read strings. It reads the ordinal of each matching document, adds 1 to count[ordinal], and at the end resolves only the top buckets back to strings through the dictionary. Segments have their own ordinals, so Elasticsearch builds global ordinals per shard: a mapping from each segment's ordinals to shard-wide ones. Building it needs a pass over all the dictionaries and is done at refresh time or on first use, and the mapping lives on the heap. For numeric aggregations (sum, avg, histogram), the engine reads values directly in docID order, which is sequential memory access.
Merging. When segments merge, the columns are read, deleted documents are dropped, the values are renumbered to the new docIDs and the block statistics (minimum, GCD, bit width) are computed again. String dictionaries are merged like sorted lists. A merge can therefore shrink the columns, and a force-merged read-only index often has the smallest doc values.
Relation to the inverted index. Both structures are written at the same time from the same documents. They do not depend on each other: a field can be indexed but have no doc values, or the reverse. A term query uses postings; a sort on the same field uses doc values. A text field, after analysis, has several tokens per document and no single value to sort on, so it has no doc values; to aggregate on text, you index a second field of type keyword, which has doc values.

example: Take six documents with a country field and a price field in cents, as in the diagram. For the country column, the sorted dictionary is DE, IN, US, with ordinals 0, 1, 2. The six documents have the ordinals 1, 2, 1, 0, 2, 1, which fit in 2 bits each: 12 bits for six documents. For the price column, the values are 1000, 1500, 2500, 1000, 1500, 1000. The minimum is 1000, the differences are 0, 500, 1500, 0, 500, 0, and their GCD is 500, so the stored numbers are 0, 1, 3, 0, 1, 0, which also fit in 2 bits. To get the price of document 2, the reader reads the 2-bit field at position 2 × 2 = 4 (value 3) and computes 1000 + 3 × 500 = 2500.
Now the query "sum of price grouped by country over all documents". The engine walks the matching documents in order. For document 0, it reads country ordinal 1 and price 1000, and adds 1000 to sum[1]. It does the same for the others. The result is sum[0] = 1000 (DE), sum[1] = 1000 + 2500 + 1000 = 4500 (IN), sum[2] = 3000 (US). Only now does it read the dictionary to give names to the three ordinals. No string was compared during the scan.
A realistic size. A log index has 100 million documents in a day, with a timestamp field in milliseconds. If the timestamps are only stored to the second, the GCD of the differences is 1,000. A day has 86,400 seconds, so after subtracting the minimum a value needs 17 bits. The column takes 100 million × 17 bits ≈ 212 MB, against 800 MB if stored as 64-bit longs. In practice Lucene chooses widths per block of 16,384, and timestamps that increase with the document order give even narrower blocks. A status code field with 5 distinct values takes 3 bits per document, or 37 MB for 100 million documents.
For comparison, a log line in _source might be 500 bytes. Reading "latency_ms" from _source for 2 million matches means decompressing and parsing about 1 GB of stored fields; from doc values it is a few megabytes of small integers.
intuition: Search needs "which documents contain X" (inverted); aggregations need "what is X for these documents" (columnar). Lucene keeps both, like a book that has an index at the back and also a table of facts by chapter.
The idea is natural because the two questions have opposite shapes. The inverted index starts from a value and finds many documents, so it is sorted by value. An aggregation starts from many documents and wants one value from each, so it should be sorted by document. A structure good at one is bad at the other, so keeping both is the straightforward answer. Writing the second structure at index time, as one more segment file, lets the system pay the cost once, when it already has the document in hand.
mistakes: People often think doc values are only for aggregations. In fact they are also used for sorting, for script access (doc['field']), for range filtering together with the skip index, for joins and for geo-distance sorting, and in new versions to rebuild the document source.
People often think doc values live on the Java heap like the old fielddata. In fact they are read from memory-mapped segment files and managed by the operating system page cache. The exception is global ordinals, which are kept on the heap. This is why a cluster with little free RAM for the file system cache is slow on aggregations even if the heap looks fine.
People often think you can aggregate on a text field. In fact a text field has no doc values, because analysis turns one value into many tokens. Elasticsearch refuses unless you enable fielddata, which uninverts the field onto the heap and is the cause of many memory problems. The right way is a keyword sub-field (a multi-field).
People often think disabling doc values is a free saving. In fact if a field never needs sorting, aggregation or scripting, you can set doc_values: false to save disk space, but you cannot turn them back on without reindexing. Some features that you may need later (sort, a script, rebuilding the source in synthetic mode) depend on them.
friction: Doc values cost disk space and indexing time, since each field is stored twice in different forms (postings and a column). On typical logs they are a significant share of the index size. They need free RAM for the page cache: if the working set of the queried columns does not fit, queries become disk bound and slow.
String columns have special costs. High-cardinality keyword fields (IDs, URLs) have large dictionaries, and global ordinals for them take heap and time to build. Elasticsearch has a setting to build them eagerly at refresh, which moves the cost to indexing and increases refresh time. Terms aggregations on such fields are slow and approximate across shards (each shard returns its top buckets only).
Multi-valued fields (arrays) are stored sorted and de-duplicated per document in SORTED_SET and SORTED_NUMERIC, so the original order and duplicates are lost; this is why the source and the doc values can differ. Very long strings are not suited to doc values; Elasticsearch ignores values longer than a limit for keyword (ignore_above), which is typically set to 256 or 1,024 characters.
Compared with a real columnar database, the format is basic: simple encodings (bit-packing, GCD, a small value table), no vectorized execution and no pre-aggregation. Scans run one document at a time through iterators, which is slower per row than in ClickHouse, Pinot or DuckDB.
practice: Decide for every field what it is used for: search (indexed), sorting and aggregation (doc values), display (stored in _source). Use keyword for IDs, enums and anything you filter, sort or group by; use text only for free text. For a field you only search, set doc_values: false; for a field you only aggregate on, set index: false and keep doc values.
Leave memory for the file system cache: on a node with 64 GB of RAM, give the JVM about 30 GB at most (staying below the compressed pointer limit) and leave the rest to the operating system. Check the size of doc values per field with the analyze index disk usage API (_disk_usage) and look at fields with unexpectedly large columns, such as high-cardinality strings. For terms aggregations on big keyword fields, consider eager_global_ordinals only if the field is aggregated in most queries.
Use index sorting on the field you most often sort or filter by (for example the timestamp, descending) when the use case allows it. It improves compression, enables early termination and makes the skip index much more effective. For time-series data, use the time series data stream mode, which sorts and encodes metrics for you. For exact counts of distinct values at large scale, use the cardinality aggregation (HyperLogLog++), which reads doc values but keeps small memory.
tradeoffs: Choose doc values (the default for keyword, numeric, date and boolean) when a field will be sorted, aggregated or read in a script. You pay roughly the size of one more copy of the field, in disk and page cache, and some indexing time; you gain index-time work instead of query-time heap use.
Choose doc_values: false when a field is only matched by term or range and never sorted or aggregated, and storage is the main cost, for example big log indexes with many fields kept for filtering. You save the column but lose sort, aggregation and scripting on it, and you can only recover by reindexing.
Choose fielddata on a text field only for small, bounded cases, since it uninverts the field onto the heap and can use gigabytes; prefer a keyword sub-field. Choose eager global ordinals when aggregation latency matters more than refresh time and heap; keep the lazy default when you aggregate rarely.
Choose a separate analytical store (ClickHouse, Pinot, Druid, or Databricks over Delta tables) when analytics is the main workload: billions of rows, many group-bys, high-cardinality dimensions, joins. Lucene doc values give you search and aggregation in one engine with one copy of the data and near-real-time updates; the dedicated stores give you vectorized scans, better encodings, pre-aggregation (see the star-tree concept) and cheaper storage, at the cost of a second system and less flexible text search.
interview: Why can't the inverted index serve sorting and aggregations, and what do doc values change? || The inverted index maps value to documents; sorting needs document to value. Without doc values, an engine must uninvert the index at query time (the old FieldCache), which is slow and uses heap. Doc values store the document-to-value column at index time, memory-mapped, so reads are one positional lookup with no warm-up and no heap.
How does a terms aggregation on a keyword field work and why is it fast? || It reads the segment ordinal of each matching document from the SORTED column and increments a counter array indexed by ordinal; global ordinals align the ordinals across segments, and strings are looked up only for the final top buckets. Integer array updates over a sequential column are fast and avoid string comparison. The cost is the global ordinals build, which is on the heap.
A cluster has plenty of heap but aggregations are slow after a restart. What is going on? || Doc values are memory-mapped, so after a restart the page cache is cold and each column is read from disk on first use. Warm the cache (queries or pre-load settings), add RAM for the file system cache, and check that global ordinals are not being rebuilt on every refresh for high-cardinality fields.
How are numeric doc values compressed, and why does it matter for design? || Per block of 16,384 values, Lucene subtracts the minimum, divides by the GCD, and bit-packs with the smallest width (or uses a table of up to 256 distinct values). So coarser units (seconds instead of milliseconds) and clustered values reduce the width and cut the size. Choose the field type and resolution with that in mind, for example scaled_float or date resolution.
When would you not use Lucene doc values for analytics? || When queries scan billions of rows with many group-bys and joins, because Lucene iterates documents one at a time and lacks vectorized execution, pre-aggregation and strong column encodings. Use a columnar engine for the heavy aggregation, and keep Lucene for search and for moderate aggregations on filtered subsets.

@@ startree
value: Dashboards ask the same kind of question again and again: "total impressions by country for the last week", "sum of spend where browser = Chrome". Each question groups a very large table by a few columns and adds up a metric. A column store can scan a billion rows in a fraction of a second per core, but a dashboard with 50 panels, each refreshed by hundreds of users, still needs tens of thousands of scans per minute. The star-tree index, from Apache Pinot, avoids the scan. It precomputes the aggregates for combinations of dimension values and stores them in a tree, so a typical query reads a handful of precomputed rows instead of millions of raw ones.
The key design point is that it does not precompute everything. A full data cube stores the aggregate for every possible subset of the dimensions, which grows as the product of the column cardinalities and quickly becomes larger than the data. The star-tree keeps the aggregates only down to a threshold: when a part of the tree covers few enough raw records (10,000 by default in Pinot), it stops and leaves a small scan for the rest. You choose how much to trade storage for speed with that one number, plus the choice of dimensions.
For the layer above, real-time analytics (L1), the star-tree gives predictable latency in single-digit to tens of milliseconds for the common group-by queries, even at very high query rates, which is what user-facing analytics (such as "who viewed your profile" at LinkedIn) needs. The layers below provide the parts. Trees (L3) give the structure, a tree over dimension values with a special "star" branch. Combinatorics (L4) gives the size: the number of dimension combinations decides how large the index can grow. Range-query structures (L2), such as segment trees and Fenwick trees, give the principle: store aggregates of canonical groups so any query combines only a few of them.
terms: Dimension — a column that you filter or group by, such as country or browser; usually low or medium cardinality.
Metric — a numeric column that you aggregate, such as impressions or spend.
Data cube — the set of aggregates for every subset of the dimensions (every possible group-by).
Star node — a special child of a tree node that stands for "all values" of that level's dimension; its records are aggregated with that dimension removed.
Split order (dimensionsSplitOrder) — the ordered list of dimensions; level i of the tree splits on the dimension at position i.
maxLeafRecords (T) — the threshold: a node with T or fewer records is not split any further.
Pre-aggregation — computing the result of a group-by in advance and storing it.
Distributive aggregation — an aggregate such as SUM, COUNT, MIN or MAX that can be computed from partial results of parts of the data.
Sketch — a small fixed-size summary (for example HyperLogLog) that can be merged and gives an approximate distinct count.
history: The ancestor is the data cube. Gray, Chaudhuri, Bosworth and others (1997) defined the CUBE operator, which computes the group-by for every subset of the listed dimensions: with d dimensions that is 2^d group-bys. Harinarayan, Rajaraman and Ullman (SIGMOD 1996) asked which of these views to materialize under a space budget, and gave a greedy algorithm with a proven guarantee. Beyer and Ramakrishnan (1999) introduced "iceberg cubes", which keep only the cells whose value is above a threshold, because most cells in a sparse cube are tiny.
In 2003, Dong Xin, Jiawei Han, Xiaolei Li and Benjamin Wah published "Star-Cubing" (VLDB). It computed iceberg cubes with a "star tree": a tree over the dimensions in which attribute values that cannot reach the threshold are collapsed into a "star" value, so the tree stays small. The name and the idea of star nodes come from this work.
Apache Pinot was built at LinkedIn (open-sourced in 2015) for user-facing analytics with very high query rates and strict latency. The Pinot star-tree takes the star-cubing idea but differs from the paper. As its documentation describes, a node is split only while it holds more than a threshold T of records (maxLeafRecords), and the remaining small groups are scanned at query time. The tree is built per immutable segment from sorted data, so it fits the segment model. Later versions added sketch and percentile aggregations, several star-trees per table and null handling.
how: The index is built for each segment from a configuration: the split order of dimensions, the list of function-column pairs to pre-aggregate (such as SUM of impressions, or COUNT of rows), and maxLeafRecords.
Step 1, project and aggregate. The builder keeps only the dimensions in the split order and drops other columns. It groups the rows by the full combination of those dimensions and computes the aggregates for each group. This already collapses many raw rows into one: a billion events may become a few million combinations.
Step 2, sort and build. The combinations are sorted by the first dimension, then the second, and so on. The builder creates the root, which covers all records. For a node that has more than T records, it splits on the dimension for the node's level: one child for each distinct value, each pointing to a contiguous range of the sorted documents. This works because sorting makes each value's records adjacent.
Step 3, add star nodes. For every split, the builder also creates a star child. Its records are those of the parent with that level's dimension removed and the metrics merged: all rows that differ only in this dimension are combined into one. The new records are appended to the document store, and the star child is split further on the next dimension if it still holds more than T records. A star node is skipped if the dimension has only one value under the node (it would duplicate that child), or if the dimension is listed in skipStarNodeCreationForDimensions, which is how you avoid blow-up on a high-cardinality dimension.
Step 4, query. For a query, the engine checks that the filter columns, the group-by columns and the aggregations are all covered by a star-tree configuration; if not, it ignores the index and runs the normal scan. Otherwise it walks the tree from the root, and at each level looks at the level's dimension. With a predicate on it, the walk follows only the matching children. With a group-by on it (and no predicate), it follows all children except the star node. With neither, it follows the star node, which already holds the aggregate over every value. At the end, it has a set of nodes. If a node's path has satisfied every predicate and group-by, its single aggregated record is the answer; otherwise it scans the node's range of records, which holds at most about T records, and aggregates them.
Storage. The aggregated documents are stored like other columns, and the tree itself is a compact array of fixed-size nodes, each holding a dimension value, a range of document IDs and the ID of its aggregated document. The index sits inside the segment and is read through memory mapping.
Step 5, merge partials. Each segment returns its partial result, and the broker merges them. This works because the supported aggregates are distributive (SUM, COUNT, MIN, MAX) or have a small mergeable state (AVG as sum and count, HyperLogLog and theta sketches for distinct counts, t-digest for percentiles). Exact distinct count and exact percentile are not supported, since their partial state is not bounded by a small size: to merge two exact distinct counts you need the sets themselves.
Why the tree stays small. In the worst case, with cardinalities c₁, c₂, …, c_d, the number of records in the full tree equals the product of (cᵢ + 1) over the dimensions, the +1 being the star value (that is the number of cells of the data cube). For d = 3 with 200 countries, 30 browsers and 10 devices, the bound is 201 × 31 × 11 = 68,541 records, whatever the number of raw rows. Real data is sparser, because not every combination occurs. The threshold T cuts the tree off before the deepest levels, so with high-cardinality dimensions late in the split order the number of nodes is much smaller than the bound.
Dimension order matters. Level i splits on the dimension at position i, and queries can use the star branch only for the levels they do not touch. Pinot's default tree (enableDefaultStarTree) uses the low-cardinality dimensions (up to 10,000 values) in descending order of cardinality. That is a starting point; test the order against your own queries.

example: Use the five rows in the diagram: IN Chrome 300, IN Safari 100, US Chrome 600, US Safari 200 and US Edge 50. The split order is [Country, Browser], the aggregate is SUM of impressions, and T = 1 so that every node with more than one record is split. The root holds 5 records, so it splits on Country: an IN child with 2 records, a US child with 3 records, and a star child that merges the countries: Chrome 900, Safari 300, Edge 50 (3 records). Each of these has more than one record, so each splits on Browser, with its own star record. IN gets Chrome 300, Safari 100 and star 400. US gets Chrome 600, Safari 200, Edge 50 and star 850. The star child of the root gets Chrome 900, Safari 300, Edge 50 and star 1,250. The total is 5 base documents plus 6 aggregated documents: (IN,*) 400, (US,*) 850, (*,Chrome) 900, (*,Safari) 300, (*,Edge) 50 and (*,*) 1,250, which makes 11. The worst case would be (2 + 1) × (3 + 1) = 12.
Query 1: SELECT SUM(impressions) WHERE country = 'US'. At the Country level there is a predicate, so go to the US child. At the Browser level there is neither a predicate nor a group-by, so take the star node: the document (US,*) = 850. One record is read, and the answer is 850. Query 2: SELECT browser, SUM(impressions) GROUP BY browser. At the Country level there is nothing, so take the star node. At the Browser level there is a group-by, so take all children except the star: Chrome 900, Safari 300, Edge 50. Three records are read. Query 3: SELECT SUM(impressions), with no filter. Star at both levels gives (*,*) = 1,250. One record. With 5 billion raw rows instead of 5, the star-tree would still read only 1 to 3 records for these queries.
Now scale it. A table with 1 billion events per day has the three dimensions of 200 countries, 30 browsers and 10 devices. The upper bound is 68,541 records, so the star-tree adds well under 1 MB for one metric, and "SUM by country and device" reads at most 200 × 10 = 2,000 pre-aggregated records instead of 1 billion rows. A scan of a single 4-byte column over 1 billion rows is 4 GB of memory traffic, about 0.4 seconds on one core at 10 GB/s, before counting the filter and group-by columns. The star-tree answer takes well under a millisecond of CPU.
Last, the limit. Add a fourth dimension, user ID with 10 million values. The bound becomes 68,541 × 10,000,001, which is larger than the raw table. In this case you leave the dimension out of the split order (queries that filter by it will scan), or put it last so that T stops the splitting before it, or skip star-node creation for it.
intuition: A partially pre-computed pivot table, built only where it pays off.
The idea is natural because there are two cheap extremes and both fail. Scanning everything is exact and flexible but slow for each query. Precomputing everything is fast but grows as the product of the cardinalities. The star-tree is the middle: arrange the combinations in a tree so any query can find its answer by walking down a few branches, and use the "star" branch for "I do not care about this dimension". Wherever the leftover data is small, stop and scan: scanning 10,000 rows is as cheap as another level of the tree.
mistakes: People often think the star-tree is a full data cube. In fact it stops splitting when a node has T or fewer records, and a query may still scan up to about T records. The threshold is the knob that bounds both the index size and the worst-case scan.
People often think it speeds up any group-by query. In fact it applies only when every filter column, every group-by column and every aggregation of the query is covered by the configured tree. One filter on a column outside the split order sends the query to the normal path. It also cannot serve exact distinct counts, exact percentiles, regex filters or IS NULL filters, and OR works only within one dimension.
People often think a star-tree is built once for the table. In fact it is built for each segment, when the segment is created or reloaded, and it is part of the segment. Changing the configuration needs a segment reload, and changing a dimension to a raw (not dictionary-encoded) column can make the existing tree unreadable, so Pinot drops it.
People often think more dimensions in the tree are always better. In fact each added dimension multiplies the size bound by its cardinality plus one, and a high-cardinality dimension can make the tree larger than the data. Choose the dimensions that real queries filter or group by, and skip star nodes for the large ones.
friction: Space and build time grow with the number of dimensions and their cardinalities, and the worst case is the product. Segment build gets slower, and the tree is rebuilt whenever a segment is created, reloaded or merged. Several trees for different query shapes multiply this cost.
The index is query-shape specific. The queries you did not plan for fall back to scans, so the benefit depends on the dashboards being stable. If the product team adds a new filter, the query loses the speed-up until the tree is changed and the segments are reloaded. The pre-aggregated functions are fixed at build time: you cannot ask for SUM of a metric you did not list, and every added function-column pair increases the size.
Supported predicates are limited (equality, in, range, and; or only on a single dimension), and aggregations with unbounded partial state are excluded. Because the index is invisible to the query writer, a small change in a query can move it off the fast path, so you must check latency or scanned-entry counts to see that the tree is used.
practice: Start from the real query log, not from the schema. List the queries a dashboard issues, find the ones with the largest scan cost and the highest rates, and design a tree for them: the dimension list is the union of their filters and group-bys, and the function-column pairs are their aggregates (including COUNT(*) if you need it). Put low-cardinality, frequently filtered dimensions first. Keep maxLeafRecords at the default 10,000 at first, then reduce it (for example to 1,000) if queries scan too many leaf records and the index is small enough, or raise it if the index is too large.
Check the effect before rollout. Compare the segment size and build time with and without the index on a representative segment, and measure query latency and the number of entries scanned in the query response statistics (Pinot reports docs scanned). If the tree is not used, the number of scanned entries will be close to the segment size.
For high-cardinality dimensions, use skipStarNodeCreationForDimensions, or leave the dimension out and accept scans for the queries that filter on it. Prefer approximate aggregations (HyperLogLog, theta sketch) for distinct counts so that they can be pre-aggregated. Use several smaller trees for different query families rather than one tree with all the dimensions.
When you change the configuration, the segments need a reload. In a warehouse stack, the same idea appears as aggregate tables or materialized views.
tradeoffs: Choose a star-tree when queries are repetitive group-bys and filters over a stable set of 3 to 8 dimensions of low or moderate cardinality, the aggregates are SUM, COUNT, MIN, MAX or sketches, and you need latency of milliseconds at high query rates. You pay extra storage, which depends on the cardinalities, and build time, and you lose flexibility for shapes outside the configuration.
Choose a plain scan with inverted, sorted and range indexes (Pinot's other indexes) when queries vary a lot, the dimension set is large, or the filters are selective enough to reduce the rows to a few thousand. A sorted column plus inverted index already gives millisecond answers for selective filters, with no pre-aggregation cost.
Choose rollup at ingestion (Druid style) or a pre-aggregated table (a Delta table of daily aggregates, or a materialized view) when you know the dimensions and the time granularity in advance and can drop the raw rows. This is the cheapest way, since the raw data is not stored at all. You give up the ability to query raw events and to change the grain later.
Choose to lower maxLeafRecords when latency is the goal and storage is cheap, and to raise it when the index is too large or the build is slow. A smaller T means a deeper tree and more stored aggregates but shorter final scans; a larger T means the reverse. The worst case of the scan is bounded by about T records per matching node.
interview: What is the star node and why does it make group-by and filter queries fast? || A star node stands for "all values" of a dimension: it holds the records of its parent with that dimension removed and the metrics already merged. When a query has no filter or group-by on a dimension, the walk goes down the star branch and reads one precomputed record instead of combining many children or scanning rows.
How do you bound the size of the index, and what is the worst case? || The worst case is the data cube: the product of (cardinality + 1) over the split dimensions. The threshold maxLeafRecords stops splitting nodes that cover few records, skipStarNodeCreationForDimensions removes star branches for big dimensions, and the choice of dimensions keeps the product small. Leaving a high-cardinality dimension out is often the biggest saving.
Why can the star-tree answer SUM and AVG but not exact distinct count? || The pre-aggregated records are merged across many raw records and later across segments, so the aggregate needs bounded, mergeable partial state. SUM, COUNT, MIN and MAX are distributive; AVG is stored as sum and count. An exact distinct count needs the set of values, which is unbounded; sketches such as HyperLogLog have fixed size and can be merged, so they are supported.
A query that used to be fast became 50 times slower after a dashboard change. What do you check? || Whether the new query uses a column or function that is not in the star-tree configuration, so the planner fell back to scans. Check the query statistics (documents scanned), compare the filter, group-by and aggregation columns with the dimensionsSplitOrder and function-column pairs, and update the tree and reload segments.
How would you choose the split order? || Use the query log: dimensions that appear in most queries first, with lower cardinality first so that early levels have few branches and star nodes cover whole subtrees. Test on one segment for size and latency. A high-cardinality dimension late in the order, or without star nodes, avoids blow-up.
Compare the star-tree with Druid's rollup at ingestion. || Rollup aggregates rows at ingestion and discards the raw data at the chosen grain, which is cheapest in storage but permanent. The star-tree keeps the raw rows and adds a pre-aggregated index beside them, so queries outside the tree still work. The star-tree costs more storage and build time and helps only for the configured shapes.

@@ bitmap
value: A bitmap index answers filter queries by set arithmetic. For each distinct value of a column (country = IN, browser = Chrome), it keeps one bitmap with one bit per row: bit i is 1 if row i has that value. The query "country = IN AND browser = Chrome AND day = Monday" becomes the bitwise AND of three bitmaps, and "country = IN OR country = US" becomes an OR. A CPU can AND 256 or 512 bits in one instruction, so combining filters over a hundred million rows takes milliseconds and never touches the row data until the final list of matching rows is known.
The classic problem is size. A plain bitmap needs one bit per row for every value: 100 million rows and 1,000 distinct values mean 1,000 × 12.5 MB = 12.5 GB, most of it zeros. Older fixes compress runs of zeros (WAH, EWAH, Concise), but compressed runs make AND and OR slow and random access impossible. Roaring bitmaps, by Daniel Lemire and colleagues, split the row-number space into chunks and choose the best representation for each chunk: a small sorted array when the chunk has few rows, a plain bitmap when it is dense, and a list of runs when it is clustered. The result is close to the smallest size of every method, with fast set operations.
For the layer above, OLAP analytics (L1), Roaring bitmaps turn filters into fast bitwise operations. They are used in Apache Pinot (inverted indexes), Druid, Elasticsearch and Lucene (cached filters), Spark (shuffle metadata), ClickHouse (bitmap functions) and Delta Lake (deletion vectors). The layers below give the two ideas. Set theory (L4) says that a bitmap is a set of row numbers, and that AND, OR and NOT are intersection, union and complement. SIMD (L3) says that one instruction can operate on 256 or 512 bits, so these set operations on dense chunks run at memory speed.
terms: Bitmap index — an index with one bitmap per distinct value of a column; bit i says whether row i has the value.
Cardinality — the number of distinct values in a column; also the number of elements in a set (the number of 1 bits in a bitmap).
Roaring bitmap — a compressed bitmap for 32-bit integers that splits them into chunks of 65,536 and stores each chunk in the best container type.
Container — the structure that stores one chunk: an array, a bitmap or a list of runs.
Array container — a sorted array of 16-bit values; used when a chunk holds at most 4,096 elements.
Bitmap container — a fixed 8,192-byte (65,536-bit) bitmap; used for dense chunks.
Run container — a list of (start, length) pairs; used when the chunk consists of long runs of consecutive values.
Run-length encoding (RLE) — storing a run of equal values as (value, count).
Popcount — the CPU instruction that counts the 1 bits in a word; used to compute cardinality.
history: Bitmap indexes are old. Patrick O'Neil described them for the Model 204 database in 1987, and Oracle, Sybase IQ and others shipped them in the 1990s for data warehouses with low-cardinality columns such as gender or region. O'Neil and Quass (SIGMOD 1997) added bit-sliced indexes, which store a numeric column as one bitmap per bit position so that range queries and sums become bitmap arithmetic.
The size problem led to a series of compression schemes based on run lengths: BBC (Antoshenkov, 1995), WAH (Wu, Otoo and Shoshani, 2006), Concise (Colantonio and Di Pietro, 2010) and EWAH (Lemire, Kaser and Aouiche, 2010). They shrink sparse bitmaps and keep AND and OR linear in the compressed size, but they cannot jump to row k without decoding, and operations cannot skip parts.
Roaring came from Samy Chambi, Daniel Lemire, Owen Kaser and Robert Godin ("Better bitmap performance with Roaring bitmaps", Software: Practice and Experience 2016, arXiv 2014). It uses a two-level index and two container types, array and bitmap. In 2016 the same group added run containers ("Consistently faster and smaller compressed bitmaps with Roaring") and in 2018 published a library paper with SIMD implementations using AVX2 and AVX-512 instructions. The reference implementations are CRoaring (C), RoaringBitmap (Java), and ports for Go, Rust, Python and others.
Adoption was fast. Lucene added a Roaring-based set for cached filters in the 4.x series, Druid added Roaring as an alternative to Concise in the mid-2010s, Spark uses it for shuffle map status, and Pinot uses it for inverted indexes. Delta Lake and Apache Iceberg (version 3) use a Roaring format for deletion vectors. The Roaring serialization format is fixed in a public specification so that different languages can exchange bitmaps.
how: Layout. A Roaring bitmap stores 32-bit unsigned integers (row numbers). It splits each value into the high 16 bits (the key) and the low 16 bits. All values with the same key belong to the same chunk of 65,536 consecutive numbers. The bitmap keeps a sorted array of keys, and for each key a container that stores the low 16 bits of its values. To find a value, binary-search the key array (a few comparisons for typical sizes) and then look inside one container.
Choosing the container. A container for a chunk with n elements is one of three kinds. An array container is a sorted array of 16-bit values, which costs 2n bytes. A bitmap container is always 8,192 bytes (65,536 bits). These two cost the same at n = 4,096, which is the threshold: at most 4,096 elements means an array, more means a bitmap. A run container stores r runs as (start, length) pairs of 16 bits each, which costs about 4r bytes plus a small header; it is chosen when it is smaller than the other two. So a chunk costs at most 8 KB, and a sparse chunk costs 2 bytes per element. The overhead is about 8 bytes per container for the key, cardinality and offset.
AND and OR on containers. The operations run container by container, with a merge of the key arrays first: only keys present in both bitmaps matter for an AND. For two bitmap containers, an AND is 1,024 64-bit word ANDs, which AVX2 does with 32 instructions on 256-bit registers, and a popcount gives the new cardinality. For two array containers, it is a merge of two sorted lists, or a galloping search when one is much shorter than the other; SIMD versions compare 8 values at once. For an array and a bitmap, each array value is tested with one bit lookup, which costs the size of the array. The result is converted: an AND of two bitmaps with fewer than 4,096 results becomes an array. This is the set theory idea in action: the filter is an intersection of sets, and each container intersection is an operation on smaller sets.
Using the index. For each distinct value of a column, the index stores one Roaring bitmap. A query with predicates evaluates each predicate to a bitmap (an equality is a lookup; an IN list or a range of dictionary ids is the OR of several bitmaps), ANDs the bitmaps of the predicates, and then reads or aggregates only the surviving rows. NOT is an ANDNOT against the full set, or against the set of valid rows. Because the cardinality of each container is stored, counting the matches (COUNT(*) with filters) needs no row access at all.
Building and updating. A bitmap index is built by scanning the column once and adding each row number to the bitmap of its value. As rows are added in increasing order, building is an append to the last container. For immutable segments (Pinot, Druid, Lucene), the bitmaps are built once, optionally run-optimized and written to disk in the portable format, then memory-mapped for reading without parsing. Mutable Roaring bitmaps also support add and remove in time proportional to the size of one container, which is how in-memory indexes for streaming data are kept.
Why this design is fast. Run-length schemes such as WAH must decode from the start to reach row k, and combining two of them walks both streams. Roaring is a two-level index: the key array lets an operation skip every chunk that is absent from one side, and inside a chunk the position is direct (array: binary search; bitmap: a shift and a mask). Membership, rank (how many elements are below x) and select (the k-th element) therefore cost a binary search over keys plus a small amount of work in one container. On disk, the portable format stores the keys, cardinalities and offsets in a header, so a reader can memory-map the file and touch only the containers that a query needs.
Beyond equality. A numeric column can be indexed as bit-sliced bitmaps: one bitmap per bit position of the value. A range condition such as price ≥ 500 becomes a sequence of ANDs and ORs over about 20 bitmaps, and a sum comes from the popcounts of the slices weighted by powers of two.

example: First the layout. The row numbers 3, 70000, 70001 and 5,000,000 split as in the diagram: 3 has key 0 and low part 3. 70000 is 65,536 + 4,464, so key 1 and low part 4,464; 70001 has key 1 and 4,465. 5,000,000 is 76 × 65,536 + 19,264, so key 76 and 19,264. The bitmap has three containers, each an array container: 2 bytes, 4 bytes and 2 bytes of data, plus about 8 bytes of header each. Compare this with a plain bitmap of 5 million bits, which is 625 KB.
Now the container choice for a chunk. If a chunk holds the 10,000 even numbers from 0 to 19,998, an array would take 20,000 bytes, a bitmap container takes 8,192 bytes, and a run container would need 10,000 runs of length 1 (40,000 bytes). The bitmap wins. If a chunk holds the numbers 1,000 to 40,999 as one run, the array takes 80,000 bytes (not allowed above 4,096 elements), the bitmap takes 8,192 and the run container takes about 6 bytes (a count and one pair). The run container wins by a factor of more than 1,000. Roaring picks the smallest automatically when you call runOptimize.
Now the sizing for a column. A table has 100 million rows and a column with 1,000 values spread evenly at random. Each value has 100,000 rows. The row space has 100,000,000 / 65,536 ≈ 1,526 chunks, so each value has about 65 rows per chunk: array containers with about 130 bytes each, so about 1,526 × (130 + 8) ≈ 210 KB per value, and 210 MB for the whole column. A plain bitmap index would take 1,000 × 12.5 MB = 12.5 GB, about 60 times more. A forward column with a 10-bit dictionary code takes 125 MB, so the bitmap index costs a bit more than the column, which is normal for an inverted index. If the data is sorted by this column, each value occupies one run, and the whole index shrinks to a few KB.
Now a query. The filters are country = IN (bitmap with 20 million rows), browser = Chrome (50 million rows) and day = Monday (14 million rows) over 100 million rows. The engine walks 1,526 chunks. In each chunk, the three bitmaps are dense (about 13,000, 33,000 and 9,000 rows per chunk), so all three are bitmap containers. Each AND of two bitmap containers is 1,024 64-bit words, which is 256 AVX2 operations, and a chunk needs two of them plus loads and stores, roughly half a microsecond to a microsecond. So 1,526 chunks take about 1 to 2 milliseconds, and COUNT(*) comes from the final popcounts without reading any row.
intuition: A row of light switches per value: to combine filters, compare the switch rows.
The idea is natural because a filter asks "which rows", and a set of row numbers is the plain answer. If every value has its own set, and sets can be intersected quickly, then the query planner has almost nothing to do. The only difficulty is representing sets of very different densities well. Roaring uses the observation that the best representation depends on the density of a small chunk, not of the whole set: so it decides chunk by chunk, with three simple rules, and the cost of any chunk is never more than 8 KB.
mistakes: People often think bitmap indexes only work for low-cardinality columns. In fact plain bitmaps do, because their size grows with cardinality × rows. Compressed bitmaps such as Roaring store only the set bits in sparse chunks, so a column with a million distinct values costs about as much as an ordinary inverted index. The cost per row becomes high only when every bitmap has fewer than one row per chunk, because the per-container overhead of about 8 bytes then dominates.
People often think Roaring is a run-length compression. In fact run containers are only one of three kinds, and the main trick is to combine array, bitmap and run containers per chunk. Pure run-length schemes (WAH, EWAH) are good for sorted or clustered data but slow for random data.
People often think a bitmap index is faster than scanning a column for any filter. In fact for a selective filter (a few hundred matches in 100 million rows) a sorted column or a B-tree lookup is as fast or faster, and for a filter that matches most rows a scan is cheaper, because producing a huge bitmap of row ids costs as much as reading the column. Bitmaps win when several moderately selective filters combine.
People often think Roaring stores arbitrary 64-bit values natively. In fact the standard format is for 32-bit unsigned integers (up to about 4.29 billion rows per bitmap). 64-bit variants keep a map from the high 32 bits to a 32-bit Roaring bitmap; Delta Lake and Iceberg deletion vectors use this scheme.
friction: Updates are the main limit. A bitmap index on an immutable segment is cheap to build and read, but changing a row in a large segment means changing two bitmaps (remove from the old value, add to the new one) and, in a compressed on-disk file, rewriting the containers. This is why bitmap indexes sit in immutable segments and why mutable data uses a separate in-memory structure that is merged later.
Each value needs its own bitmap object, so a column with 100 million distinct values (a user ID) needs 100 million bitmaps of one row, each with its own key and header, which costs more than a plain posting list; such columns use other index types (sorted, hash or Bloom). Bitmaps also fit numeric ranges poorly unless you use bit slicing.
Performance depends on the data layout. A dense bitmap is fast, but a query that ORs a thousand sparse bitmaps (a wide IN list, a prefix match on a dictionary) pays for every container it touches. Results can also be large: converting a bitmap with millions of rows to row ids and fetching the rows is a random-access pattern, and this can cost more than the filter. Finally, SIMD speed depends on the CPU: the AVX-512 paths exist only on some processors, and the library falls back to AVX2 or scalar code.
practice: Use the bitmap index that your engine provides rather than building your own, and decide per column. In Pinot, an inverted index (Roaring bitmaps per dictionary id) is the right choice for columns that are filtered by equality and have low to medium cardinality; a sorted column is better for the one column you filter on most; a range index is for numeric ranges. Check the index sizes in the segment metadata and the query statistics for the number of entries scanned in the filter.
If you control the data layout, sort or cluster the rows by the columns you filter most. Clustered values form long runs, which Roaring stores in a few bytes, and clustering also helps the other filters by making the bitmaps dense in fewer chunks. Call runOptimize (or the equivalent) after building a bitmap that you will store, since it is cheap and can shrink it by large factors for sorted data.
When you use the library directly, for example to track a set of user IDs or deleted rows, keep to 32-bit IDs where possible (use a dense surrogate ID rather than a hash), reuse buffers for results with the in-place operations (and, or, andNot) to avoid allocation, and serialize with the portable format so other languages can read it. For counting only, use andCardinality, which does not build the result. For very large unions, use the fast aggregation functions (FastAggregation.or), which merge many bitmaps with a priority queue or a bitmap accumulator.
tradeoffs: Choose a Roaring bitmap inverted index when filters combine several moderately selective predicates on columns with up to millions of distinct values, and the data sits in immutable segments. You pay about 2 bytes per row per indexed column in the sparse case, and you gain millisecond AND and OR over hundreds of millions of rows. You give up cheap updates.
Choose a sorted column (the data physically ordered by the column) for the single column you filter by most. It needs no extra index (the matching rows are one contiguous range found with a binary search) and it also makes other indexes smaller. It can be used for only one column per copy of the data.
Choose run-length compressed bitmaps (EWAH, Concise) or a purely run-based format only for very clustered data where the sequential, streaming operations on two bitmaps matter; they can be smaller there. For general data, Roaring is usually faster and not much larger, and it supports random access.
Choose a plain bitset (a fixed-size bit array) when the set is dense (more than about 1 in 16 rows), the universe is small and fixed, and you want the simplest and fastest operations, as in query-time filters over one segment. It wastes memory when sparse.
Choose a Bloom filter or a hash index when you only need membership tests on a high-cardinality key, not set algebra. Choose a bit-sliced index or a range index for numeric ranges over many values.

A chunk never costs more than 8 KB, and sparse chunks cost 2 bytes per element.

A bitmap index on a user_id column with 100 million distinct values is huge. Why, and what would you use? || Every value has one row, so there are 100 million tiny bitmaps with a key and header each, much more than a plain posting list or a sorted column. Use a sorted index, a hash index or a Bloom filter for equality lookups on such keys, and keep bitmaps for columns with repeated values.
Why do systems keep Roaring bitmaps in immutable segments, and how do they handle updates? || A compressed bitmap on disk cannot be changed in place without rewriting containers, and an update touches two bitmaps. Systems write new segments or keep a small mutable in-memory bitmap, record deletes in a deletion vector (itself a Roaring bitmap) and merge in the background.
When is a scan faster than a bitmap filter? || When the filter matches a large fraction of the rows, because building and iterating the bitmap costs as much as reading the column, or when a single selective predicate is already served by a sorted column. Bitmaps pay off when combining several predicates before touching row data.
quiz: Which container does Roaring use for a chunk with 100 scattered elements, and how many bytes does it take? || An array container of 16-bit values, 100 × 2 = 200 bytes (plus a small header).
Why can a Roaring AND skip most of the data? || The two bitmaps are matched by key first, so chunks that exist in only one bitmap are skipped without looking inside. Within a chunk, only containers with the same key are intersected.
What are the key and low part of the row number 200,000? || 200,000 = 3 × 65,536 + 3,392, so the key is 3 and the low 16 bits are 3,392.
A plain bitmap index covers 200 million rows and 500 distinct values. How large is it uncompressed? || Each bitmap is 200 million bits = 25 MB, so 500 × 25 MB = 12.5 GB.
Why is a sorted column often a better choice than a bitmap index for the main filter column? || Rows with the same value are contiguous, so the filter is one range found by binary search, with no index to store, and the rows can be read sequentially. Bitmaps are better when several different columns must be combined.

@@ segments
value: A commit log is an append-only sequence of records, and in a system such as Kafka it never stops growing. If it were one file, three things would be hard. You could not delete old data without rewriting the whole file, you could not find an offset without scanning from the start, and one file of many terabytes would be impossible to move, back up or repair. Log segments solve all three with one move: cut the log into files of bounded size, named by the first offset they contain.
In Kafka, each partition is a directory of segment files. Only the newest one, the active segment, receives writes. Older segments are closed and never change again. A small sparse index beside each segment maps an offset to a byte position, so a read can jump close to the record it wants. Retention then becomes "delete the oldest files", compaction becomes "rewrite closed files", and tiered storage becomes "upload closed files to object storage". Each of these is a plain file operation on an immutable unit.
For the layer above, the distributed commit log (L1), this is the physical form of the log: sequential writes at disk speed, reads that mostly hit the page cache, and a lifetime policy that costs almost nothing. The layers below supply the parts. File systems (L3) give files, directories, append-only writes, the page cache and cheap deletion by unlinking a file. Indexing (L3) gives the idea of a sparse index: index only every few KB, because a short scan after the index lookup is cheaper than a large dense index.
terms: Offset — the sequence number of a record within a partition; the first record is 0, and it never changes.
Segment — one file of a log, holding a contiguous range of offsets; named by its base offset.
Base offset — the offset of the first record in a segment; used as the file name, padded to 20 digits.
Active segment — the newest segment, the only one that accepts appends; it is rolled (closed and replaced) when it is full or old.
Sparse index — an index with an entry only for some records (here, about one per 4 KB of data), not for every record.
Time index — a sparse index from timestamp to offset, used to find records by time.
Retention — the policy that deletes data older than a time limit or beyond a size limit.
Log compaction — a policy that keeps only the latest record for each key, by rewriting closed segments.
Tiered storage — a feature that copies closed segments to remote storage (object storage) and serves old reads from there.
history: Append-only logs on disk are older than databases. Rosenblum and Ousterhout's log-structured file system (1991) wrote everything sequentially into large fixed-size segments and used a "cleaner" to reclaim space from segments that held mostly dead data. Database write-ahead logs follow the same pattern: PostgreSQL stores its WAL in 16 MB segment files named by log position, and Cassandra's commit log uses 32 MB segments, so that old segments can be recycled once their data is safely in tables. Bitcask (Basho, 2010) keeps a key-value store as one active file plus immutable files with a merge process.
Kafka was built at LinkedIn in 2010 and 2011 (Kreps, Narkhede and Rao, "Kafka: a distributed messaging system for log processing", NetDB 2011). The paper describes a partition as a list of segment files of about 1 GB, with a message addressed by its offset in the log instead of an ID, and an in-memory sorted list of the first offset of each segment for lookup. Kafka then added files as needs appeared. In the 0.8 series (2013) each segment got an offset index file. The time index came in 0.10.1 (KIP-33, 2016) so consumers could seek by timestamp and retention could use record time. Transactions in 0.11 (2017) added a transaction index of aborted transactions.
The segment idea now appears across data systems: Pulsar's BookKeeper ledgers, Redpanda's segments, the metadata log of Kafka's KRaft mode, and tiered storage. KIP-405 (tiered storage) was introduced as early access in Kafka 3.6 and declared production-ready in Kafka 3.9 (November 2024). It uploads only closed segments, which is possible because they are immutable.
how: Layout. A partition directory such as orders-3 contains, for each segment, a group of files with the same name: the base offset padded to 20 digits. For base offset 1,000,000 they are 00000000000001000000.log (the records), .index (the offset index), .timeindex (the time index), and, when transactions are used, .txnindex and a .snapshot file with producer state. The .log file holds batches of records, written in the same format that goes over the network, which is why a broker can send them to a consumer straight from the page cache with the sendfile system call and no copy in user space.
Appending. A write goes to the end of the active segment. The operating system buffers it in the page cache and writes it to disk later; durability comes from replication, with fsync optional. When the active segment reaches log.segment.bytes (1 GiB by default) or is older than log.roll.hours (168 hours, seven days), Kafka rolls it: it closes the old files, trims the preallocated index files to their used size, and opens a new segment whose base offset is the next offset to be written. Closed segments are immutable. Follower replicas fetch from the leader and append to their own segments in the same way, so every replica has the same offsets but its own files, and consumers may read only up to the high watermark, the offset that all in-sync replicas have.
The sparse index. While appending, Kafka adds an entry to the offset index after about log.index.interval.bytes (4,096) bytes of data. An entry is 8 bytes: a 4-byte offset relative to the base offset and a 4-byte byte position in the .log file. The index file is memory-mapped, preallocated up to log.index.size.max.bytes (10 MiB) and kept sorted by construction, since offsets only grow. Because it is sparse, a 1 GiB segment needs only 262,144 entries, about 2 MiB, and it fits in memory.
Reading offset X. First, Kafka finds the segment: it keeps the segments in an in-memory sorted map keyed by base offset and takes the entry with the greatest base offset not above X. Second, it binary-searches that segment's index for the largest indexed offset not above X, which gives a byte position. Third, it reads the .log file from that position and scans forward, batch by batch, until it reaches X. The scan covers at most about 4 KB. The cost is a few comparisons in memory, then one short sequential read, which is almost always served from the page cache.
Recovery. After an unclean shutdown, the broker scans the segments written since its last checkpoint, rebuilds their indexes and truncates any partial record at the end. Closed segments need no checking.
Seeking by time. To find the first offset at or after timestamp T, Kafka does the same on the time index: it finds the segment by the largest timestamp, binary-searches the 12-byte entries (8-byte timestamp, 4-byte relative offset), and then continues with the offset lookup. This is how consumers reset to a point in time.
Retention. A background task (every 5 minutes by default) looks at the closed segments. A segment is eligible for deletion when its largest record timestamp is older than retention (log.retention.hours, 168 by default), or when the partition exceeds its size limit. The task renames the files with a .deleted suffix and removes them after a delay (60 seconds by default). Deleting a file is a metadata operation of the file system (see the file systems concept): its blocks are freed without reading or rewriting any data. The active segment is never deleted.
Compaction. For topics with cleanup.policy=compact, a cleaner thread scans the closed segments, builds a map from key to latest offset, and writes new segments that keep only the latest record for each key (and tombstones for a limited time). Because segments are immutable, the cleaner works on copies and swaps them in with a rename. The active segment is not cleaned, which is why a compacted topic can show older values for a key until it rolls.
Tiered storage. When it is enabled, closed segments are copied to remote storage, and the broker keeps only a short local window (local.retention). A read for an old offset is served from the remote copy, using the same offset index (fetched and cached), so the segment is also the unit of remote storage.

example: Take a topic whose records are about 1 KB each, with default settings: 1 GiB segments, an index entry every 4,096 bytes and 8 bytes per entry. For simplicity, say each segment holds exactly 1,000,000 records, so the base offsets are 0, 1,000,000, 2,000,000 and so on. The index of one segment has about 1 GiB / 4 KiB ≈ 262,000 entries; at 8 bytes each, this is about 2 MiB, so a broker with 2,000 segments keeps about 4 GB of index files, mostly cold and mapped from disk.
A consumer asks for offset 1,234,567. The broker looks in its segment map and finds base offset 1,000,000. The relative offset is 234,567. The index has an entry about every 4 records (4 KB divided by 1 KB), so the entries are around 234,564 and 234,568. A binary search over 262,000 entries takes about 18 steps. It returns relative offset 234,564 with a byte position of about 234 MB into the file. The broker reads from there and skips three records to reach the right one. The total work is about 18 memory reads for the index and one read of about 4 KB, instead of reading 234 MB from the start of the file.
Now retention. A partition receives 2 MB per second, which is about 173 GB per day. A 1 GiB segment fills in about 9 minutes, so there are about 160 segments per day. With seven days of retention a partition holds about 1,100 segments, and a segment becomes deletable about 9 minutes after the last record in it turns seven days old. Retention is accurate to about 9 minutes. The files are removed one by one in milliseconds each, with no rewriting.
The same settings behave very differently for a quiet partition that receives 1 KB per second. A 1 GiB segment would take about 12 days to fill, so the 7-day roll time closes it after 7 days. Its newest record is then about 7 days old, and it is deleted only when that newest record is older than 7 days, which is another 7 days later. A record written on day 0 at the start of a segment can therefore live about 14 days although retention is "7 days". The fix is to lower log.segment.bytes or segment.ms for low-volume topics (for example a 1-day roll gives retention accurate to one day).
intuition: A long scroll cut into labelled volumes, each with a small table of contents.
The design is natural because an append-only log has one hot end and a long cold tail. The hot end needs fast sequential writes, so it is one open file. The cold tail needs no changes at all, so it can be cut into units that are cheap to delete, copy, compact and cache. A sparse index is enough because the log is sorted by offset already: the index only needs to get close, and a short sequential scan does the rest at the speed of the disk. Everything else (retention, compaction, tiering, replication catch-up) is a policy over whole files.
mistakes: People often think Kafka deletes each message when its retention expires. In fact it deletes whole segments, and only closed ones. A record can outlive its retention time until its segment rolls and the segment's newest record expires, which can be up to the retention time plus the roll time.
People often think the offset index has an entry for every message. In fact it is sparse, with an entry about every 4 KB of log data. That keeps the index small enough to map into memory for all segments, and the cost is a short scan after the index lookup. Making it denser (a smaller log.index.interval.bytes) trades memory for shorter scans, and is rarely worth it.
People often think a smaller segment size is always better because it gives finer-grained retention. In fact every segment adds files, memory mappings and a deletion task, and many tiny segments slow broker startup (each log may be recovered) and the retention pass. Segments of a few hundred MB to 1 GiB are the usual balance; very small ones suit only very low-volume topics.
People often think compaction runs on the whole log. In fact it works only on closed segments; the active segment is excluded. Consumers of a compacted topic can see several records for the same key near the head of the log, and deletes (tombstones) stay visible for delete.retention.ms.
friction: The cost of segments is the cost of files. Every partition replica holds several segments, each with two or three files, and each of those uses a file descriptor, a memory mapping and operating system metadata. Brokers with tens of thousands of partitions hit limits on open files and mappings, and slow recovery after an unclean shutdown, since every segment of the active logs may need checking. The number of files grows with partitions times segments.
Retention is coarse. Granularity is one segment, and the accuracy depends on the data rate, as shown for the quiet partition. Size-based retention has the same coarseness. If you need exact time-to-live per record, a log is the wrong tool; use a store with per-key expiry.
Random access is limited. Looking up by offset or time is cheap, but looking up by key or by content is not possible in the log, which is why other systems index on top of it. Reading very old data from a cold disk can bring out sequential scans that compete with live traffic, which tiered storage reduces by moving them to object storage, at the price of higher latency for old reads and a more complex failure model (remote service outage, upload lag). Compaction rewrites data, so it adds write amplification and I/O load, and deleting a key's older values is only eventual.
practice: Pick log.segment.bytes by the data rate of a partition, not by habit. A good target is that a segment fills in hours rather than minutes or weeks: for a partition at 1 MB/s, 1 GiB fills in about 17 minutes, which is fine; for a partition at 1 KB/s, set segment.ms to one day so that retention is accurate. The retention time should be larger than the roll time by a wide margin.
Watch the operating system limits: raise the open file limit (ulimit -n, often 100,000 or more) and vm.max_map_count (for example 262,144 or more) for brokers with many partitions, and keep the partition count per broker in the range your Kafka version supports. Keep the log directories on fast local disks (XFS or ext4 are the usual choices), spread over several disks with the JBOD feature if needed, and leave memory for the page cache, because both consumers and the follower replicas read the recent part of the log from it.
For compacted topics, tune min.cleanable.dirty.ratio, segment.ms and delete.retention.ms together, because a compacted topic only cleans closed segments. For tiered storage, set the local retention to cover your hot reads (typically hours to a day) and the total retention to the full requirement, then monitor the upload lag and the remote fetch latency.
tradeoffs: Choose larger segments (1 GiB or more) when partitions are busy and you want fewer files, fewer mappings and less overhead; you give up granularity of retention, and recovery of a large active segment takes longer. Choose smaller segments (100 to 256 MB, or a roll time of hours) when the partition rate is low, retention accuracy matters, or you use tiered storage and want to ship data to remote storage sooner; you pay with more files and more background work.
Choose a denser offset index (log.index.interval.bytes lower than 4,096) only when your consumers do many random reads and the extra index memory is acceptable; the usual access is sequential, where a sparse index is enough and uses less memory.
Choose compaction over time or size retention when the topic is a changelog of state (the latest value per key is what matters), accepting more disk I/O for the cleaner and the rule that old values of a key can remain for a while. Choose delete retention when the topic is an event stream and old events lose their value.
Choose tiered storage when you need retention of weeks or months and the local disk would be the cost driver; a segment is uploaded after it closes, so recent data stays local. You pay with higher latency for old reads and a dependence on the object store. Choose more local disks or a larger instance type when most reads are of recent data and you want the simple model.
interview: Why does Kafka split a partition into segments, and what does it get from that? || Segments bound file size and make the log's lifecycle a file operation: retention deletes whole closed files without rewriting, compaction rewrites closed files, tiered storage uploads them, and recovery and replication work on bounded units. Only the active segment is written, so the older ones are immutable and safe to cache and copy.
How does a consumer find offset X inside a partition, and why is a sparse index enough? || A lookup in the in-memory segment map by base offset, a binary search in the segment's offset index for the largest indexed offset not above X, then a short sequential scan of the log from that byte position. The log is sorted by offset and records are contiguous, so getting within about 4 KB is enough, and the scan is cheap and cache friendly.
A topic has 7-day retention but you find 13-day-old data on disk. Why? || Retention deletes only closed segments whose newest record has expired. For a low-volume partition, the active segment closes only after log.roll.hours (7 days by default), and then waits for its newest record to age 7 more days. Lower segment.ms (or segment.bytes) for such topics.
What limits how many partitions a broker can host from a storage point of view? || Files and mappings: each segment has several files, and the index files are memory-mapped, so open files and vm.max_map_count become limits, and recovery time after a crash grows with the number of segments. The page cache is also shared by all partitions, so more partitions mean a smaller cache per partition.
How does compaction interact with the segment structure? || The cleaner reads closed segments, builds a key to latest-offset map, and writes new segments with only the latest record per key, then swaps them in. It never touches the active segment. Offsets of kept records do not change, so consumers keep their positions; the new segments get new index files.
What changes when tiered storage is enabled, and what stays the same? || Closed segments are uploaded to remote storage and removed from local disk after the local retention, but the segment is still the unit, with the same base offset naming and offset index. Reads of old data go to the remote copy, with higher latency. The active segment and recent data stay local, so the write path is unchanged.
quiz: How is a segment file named, and why? || By its base offset (the offset of its first record), padded to 20 digits. This lets the broker find the right segment for any offset by a search over the names.
Why is the offset index sparse? || A dense index would need an entry for every record and would not fit in memory for large logs. With an entry every 4 KB, the index is small, and a short sequential scan finds the exact record.
A 1 GiB segment has an index entry every 4,096 bytes and 8 bytes per entry. How big is its index? || 1 GiB / 4 KiB = 262,144 entries, times 8 bytes = 2 MiB.
A partition receives 2 MB/s and segments are 1 GiB. About how long does a segment take to fill? || 1,024 MB / 2 MB/s = 512 seconds, a little over 8 minutes (about 9 minutes with overhead).
Why does the active segment never get deleted or compacted? || It is still being written, and the cleaner and the retention task work only on immutable closed segments. It becomes eligible after it rolls and is closed.

@@ cowmor
value: Data lake tables are made of immutable files, usually Parquet files of 128 MB to 1 GB. Immutable files are what make cloud storage cheap and readers safe, but they raise a question: when one row changes, what do you do? There are two basic answers. Copy-on-write (COW) writes a new copy of every file that contains a changed row, with the change applied, and then swaps the table to point at the new files. Merge-on-read (MOR) leaves the old file alone, writes the change into a small separate file (a log of changes, or a list of deleted row positions), and makes every reader combine the base file and the changes when it reads.
The two answers move the same cost to different moments. COW pays at write time and makes reads trivial: readers see plain files, with no merge logic. MOR pays at read time and makes writes cheap: a write costs about as much as the changed data, not as much as the files that contain it. For a table where 10,000 scattered rows change in each batch, COW can rewrite almost the whole table, while MOR writes a few megabytes.
For the layer above, the lakehouse (L1), this choice decides whether MERGE, UPDATE and DELETE can run every few minutes at reasonable cost. Delta Lake, Apache Iceberg and Apache Hudi all support both styles. The layers below shape the choice. File systems and object stores (L3) give immutable files and atomic rename or put-if-absent, which is why changes are new files and not in-place edits. Concurrency control (L3) explains the third effect: the more files a writer rewrites, the more likely it conflicts with another writer, so COW has a higher conflict rate than MOR at the same update rate.
terms: Copy-on-write (COW) — apply a change by writing a new version of the whole data file that contains it.
Merge-on-read (MOR) — record a change in a separate delta; apply it when the data is read.
Base file — the main columnar data file of a table (usually Parquet).
Delta (log) file — a small file with changes: new row versions, or the identity of deleted rows.
Position delete / deletion vector — a delta that marks rows deleted by their position in a data file.
Equality delete — a delta that marks rows deleted by the value of key columns, not by position.
Compaction — a background job that rewrites base files and deltas into new base files, removing the deltas.
Write amplification — bytes written divided by bytes of logical change.
Read amplification — extra bytes or work at read time caused by deltas that must be merged.
history: Merge-on-read is older than copy-on-write in databases. Severance and Lohman's "Differential files" (ACM TODS, 1976) proposed keeping a big read-only main file and a small file of changes, with queries looking at both, and merging them from time to time. The log-structured merge tree (O'Neil and others, 1996) generalized this to many levels. C-Store (Stonebraker and others, 2005) had a read-optimized store and a write-optimized store, with a "tuple mover" between them. Héman and others ("Positional update handling in column stores", SIGMOD 2010) showed that changes tracked by row position can be merged into column scans cheaply.
Copy-on-write comes from file systems and storage: ZFS, btrfs and LMDB never overwrite a block, they write a new one and switch a pointer, which gives cheap snapshots. Data lakes took this approach first because the immutable-file model made it the obvious one: HDFS files and S3 objects cannot be edited in place.
Hive ACID (2014 onward) added delta directories to Hive tables with "base plus delta" reads and minor and major compactions. Apache Hudi, created at Uber in 2016 to apply database changes to a Hadoop lake incrementally, offered the two table types by name: COPY_ON_WRITE and MERGE_ON_READ. Iceberg's format version 2 (around 2022) added position delete files and equality delete files, so engines could choose either mode per operation. Delta Lake wrote only copies until deletion vectors arrived in 2023. Iceberg's format version 3 replaced position delete files with deletion vectors, and Databricks can enable deletion vectors by default for new tables.
how: Copy-on-write. To process an UPDATE, DELETE or MERGE, the engine first finds the data files that contain matching rows. In Delta and Iceberg, it does this by a scan or a join between the changes and the table, using file statistics (min and max per column, partition values) to prune files. Then, for each touched file, it reads the whole file, applies the change to the rows in memory, and writes a new file with the result. The commit is a metadata transaction: add the new files, remove the old files. The old files stay on storage until a cleanup job (VACUUM or snapshot expiration) removes them, which gives time travel. Readers need no extra logic.
Merge-on-read. The engine finds the matching rows in the same way, but writes only the change. A delete becomes a record of which rows are gone: in Iceberg v2 a position delete file lists (data file path, row position) pairs, and an equality delete file lists key values; in Delta and Iceberg v3, a deletion vector holds a bitmap of positions for one data file (see the deletion vectors concept). An update is a delete of the old row plus an insert of the new row version in a new data file. Hudi's MOR table instead appends changed records to a log file attached to the base file's file group, in a row format such as Avro.
Reading with deltas. A reader opens a base file, loads the deltas that apply to it, and filters or overlays during the scan. With positions, this is cheap: the reader keeps a bitmap of deleted positions and skips them while reading row groups; the cost is proportional to the number of deleted rows plus one bitmap check per row. With keys (equality deletes, or Hudi log records), the reader must match each base row against the set of deleted or updated keys, usually through a hash table, which costs memory and CPU per row and may require reading the key columns first. This difference is the reason formats moved to position-based deletes.
Compaction. If deltas accumulate, reads slow down and storage grows. A compaction job reads base files together with their deltas, applies them, and writes new base files without deltas, usually also merging small files into target-size files. Hudi runs compaction after a number of delta commits, inline or asynchronously. Iceberg has rewrite_data_files and rewrite_position_delete_files, and Delta has OPTIMIZE and REORG TABLE APPLY (PURGE). Compaction is where the write amplification of MOR is paid later, but in bulk, off the critical path, and on a schedule you choose.
Concurrency. A commit in these formats is an optimistic transaction (see the optimistic concurrency concept): the writer builds its change against a snapshot, and at commit time the table checks whether another writer has changed the files it read or rewrote. The conflict rule is mostly file-level. A COW writer that rewrites 2,000 files conflicts with any other writer that touched any of those files; a MOR writer that only adds delta files and marks rows deleted can often commit alongside others, unless both change the same file's deletion vector or the same rows.
Finding the rows. Every UPDATE, DELETE and MERGE starts with a search. Delta's MERGE works in two passes: the first joins the source rows with the target table to find which files contain matches (pruned by partition values and min and max statistics), and the second rewrites those files with the changes applied. With deletion vectors, the second pass shrinks to writing the new row versions plus one bitmap per touched file. Hudi keeps an index from record key to file group (Bloom filters in file footers are one option), so upserts do not need a full join. In every format, the cost of finding the rows depends on how well the data is laid out.
Choosing per operation. Iceberg exposes the mode as table properties write.delete.mode, write.update.mode and write.merge.mode (copy-on-write by default). Delta chooses by whether deletion vectors are enabled on the table. Hudi chooses per table when you create it. You can mix modes: for example, MOR for the streaming upserts that run every minute and COW for the nightly batch rewrite.

    commit:  table = F1' F2 F3 F4          (F1 kept for time travel)
    read  :  plain files, no merge logic

  MERGE-ON-READ  (same change)

    before:  F1 F2 F3 F4
    write :  D1 = {F1: row 7 deleted}   N1 = {new version of row 7}
    commit:  table = F1 F2 F3 F4 + D1 + N1         (a few KB written)
    read  :  scan F1 skipping row 7, scan N1, scan F2 F3 F4
    later :  compaction rewrites F1 + D1 + N1 into F1''; deltas vanish

                  COW                        MOR
  write cost   ~ size of touched files    ~ size of the change
  read cost    base files only            base files + deltas
  commit       many files replaced        few small files added
  upkeep       none                       compaction required

example: A table holds 2 TB in 2,000 files of 1 GB each. A nightly job updates 10,000 rows. The rows are scattered, not clustered. The number of files touched is the expected number of distinct files hit by 10,000 random rows: 2,000 × (1 − (1 − 1/2,000)^10,000) ≈ 2,000 × (1 − e^−5) ≈ 1,987 files. With COW, the job rewrites about 1,987 files, nearly 2 TB, to change about 10,000 rows of maybe 1 KB each, which is 10 MB of real change. The write amplification is about 200,000 times. At a sustained write speed of 1 GB per second across the cluster, this takes over 30 minutes, plus the read of the same amount.
With MOR, the job writes one new data file with the 10,000 new row versions (about 10 MB) and about 1,987 deletion vectors, each marking about 5 positions, which take a few dozen bytes each. The total is about 10 MB plus a little metadata, so the write takes seconds. The commit adds about 1,988 file entries to the metadata. After the commit, a reader scanning the table opens 2,000 base files, applies a tiny bitmap to about 1,987 of them, and reads one extra 10 MB file. The read overhead is small, about 0.5% more data.
Now repeat this every 5 minutes for a day: 288 commits. With COW, you would rewrite the table 288 times; this is not possible. With MOR, each commit adds about 10 MB and 2,000 small deletion vector updates. After one day, each base file has about 288 × 5 = 1,440 deleted positions out of about 1 million rows (a file of 1 GB with 1 KB rows holds about a million rows), so 0.14% of rows are dead, and there are 288 small data files of 10 MB. The scan still skips them quickly, but 288 extra files and 288 versions of metadata begin to cost, so the table needs compaction every few hours or every night. The nightly compaction rewrites the touched files once (about 2 TB), instead of 288 times.
Now the opposite case. If the job changes 30% of all rows, spread everywhere, COW rewrites every file once (2 TB, the same as a full reload) and leaves clean files. MOR would mark 30% of the rows in each file as deleted and write 600 GB of new rows in new files, so every later read skips 30% dead rows. Here COW, or MOR followed by an immediate full compaction, is better: the work is the same size, and COW leaves the table clean.
intuition: Reprint the page now, or stick a correction note on it and let readers apply it.
Both are a choice about when to do the work, and the best choice depends on who is waiting. If many readers will read the page many times, one reprint is cheaper than every reader applying the same note. If the correction is a single word on a thick book and changes arrive every minute, reprinting the book each time is absurd, and notes are better, with an occasional reprint to fold them in. Compaction is that occasional reprint.
mistakes: People often think merge-on-read is simply faster. In fact it moves cost from the writer to every reader, and the cost grows until compaction. A table with weeks of uncompacted deltas can be several times slower to scan, and key-based merges (equality deletes, Hudi log records) cost far more than position-based ones.
People often think copy-on-write rewrites the whole table. In fact it rewrites only the files that contain changed rows. If the changes are clustered in a few partitions or files (by partitioning, sorting or clustering on the update key), COW touches few files; if they are scattered, it can approach the whole table. Data layout decides the cost.
People often think a deletion vector or delete file removes the data. In fact the data remains in the old file until compaction rewrites it, and the old file remains until VACUUM or snapshot expiration. For privacy deletes (such as GDPR requests), you must purge and vacuum for the data to be physically gone.
friction: MOR needs upkeep. Without compaction, reads slow down, small files multiply and metadata grows. Compaction costs compute, can conflict with writers (it rewrites files that writers want to change), and needs scheduling, monitoring and sometimes a separate cluster. Many production incidents are "the compaction job fell behind".
Engine and reader support is uneven. Deletion vectors and delete files need readers that understand them; a table protocol upgrade can lock out older clients, and some tools (manifest generation for external engines, certain exports) require a purge first. Equality deletes, common in Flink streaming upserts, are expensive to apply and are difficult for some engines.
COW has its own friction: write amplification, long commits, and a high chance of conflicts for concurrent writers that touch the same files. It also depends on file size: 1 GB files give fewer metadata entries but make each touched file costlier to rewrite, while 128 MB files rewrite less per touch but increase the file count. Updates that are scattered are the worst case for COW, and many small updates are the worst case for naive MOR.
practice: Start from the update pattern. Measure the fraction of rows changed per batch and, more importantly, the fraction of files touched. If a batch touches under about 10 to 20% of the files, or happens once a day, COW is usually fine and gives the fastest reads. If batches are frequent (minutes) and touch many files with few rows each, use MOR (deletion vectors in Delta and Iceberg v3, merge-on-read mode in Iceberg v2, MOR tables in Hudi).
Improve locality before choosing a mode. Partition or cluster the table by the column that updates follow (such as an event date or a key range), so changes land in few files. Use Z-order, liquid clustering or sort order in the writer. Keep file sizes in a healthy range, 128 MB to 1 GB, and avoid thousands of small files.
Schedule compaction as part of the design: after N commits or at a fixed interval, with a limit on the share of deleted rows per file (for example, rewrite a file when more than 10 to 20% of its rows are deleted). Monitor the number of delta files or deletion vectors per table, the share of deleted rows and read latency over time. On Databricks, keep deletion vectors enabled for tables with frequent DML, and run OPTIMIZE regularly; use REORG TABLE APPLY (PURGE) followed by VACUUM when data must physically disappear.
Check compatibility before turning on MOR features: every engine that reads the table must support deletion vectors or delete files.
tradeoffs: Choose COW when reads dominate (many queries per write), updates arrive in large daily or hourly batches, the changed rows are clustered into few files, and you want the simplest reader behaviour and maximum compatibility. You give up write speed and accept long commits and write amplification of 100 to 100,000 times for scattered updates.
Choose MOR when changes are frequent and small, are scattered across many files, and you need fresh data within minutes at low write cost. You give up read speed between compactions (typically a few percent with position deletes, several times with large key-based logs), and you accept the operational work of compaction and a table that some readers cannot read.
Choose position-based deltas (deletion vectors, position deletes) over key-based ones (equality deletes, log merging) whenever the writer can find the position of the row, which is the case for batch UPDATE and MERGE. Choose equality deletes or Hudi-style log records only when the writer cannot afford to look up the row first, such as a high-rate streaming upsert from Flink, and plan for aggressive compaction.
Choose a hybrid: MOR for hot, recent partitions with frequent updates, and compacted data for cold partitions read many times. Use a read-optimized view (Hudi) when dashboards need the fastest scans and can accept slightly stale data.

value: A table in a lakehouse is a set of immutable Parquet files. To delete one row from a 1 GB file the simple way, a writer must read the whole file, drop the row, write a new 1 GB file and commit the swap. A deletion vector avoids that. It is a small side structure, a bitmap, that lists the positions of the rows in a file that are no longer part of the table. The data file stays untouched. A reader opens the file, loads its bitmap, and skips the marked rows while scanning.
This turns a delete from "rewrite the file" into "write a few kilobytes and commit a pointer". An UPDATE becomes a delete of the old row version plus an insert of the new version into a different file, and a MERGE is both operations together. For a table where a daily job changes a few thousand rows scattered over thousands of files, the work changes from rewriting terabytes to writing megabytes. Deletion vectors are the main way Delta Lake and Apache Iceberg (format version 3) implement merge-on-read for row-level changes.
For the layer above, the lakehouse (L1), this is what makes row-level operations (GDPR deletes, change data capture merges, upserts) practical on files in object storage. The layers below supply two ideas. Indexing (L3): the vector is an index from a file to its dead row positions, and positions are numbers that a reader can test in constant time. Set theory (L4): the live rows of a file are the set of all its row positions minus the deleted set, so reading is a set difference, and merging two sets of deletes is a union. Roaring bitmaps (see the bitmap concept) provide the compact storage for the set.
terms: Deletion vector (DV) — a bitmap of row positions in one data file that are logically deleted.
Row position (row index) — the zero-based ordinal of a row inside its Parquet file.
Soft delete — marking a row as deleted without removing its bytes from storage.
Purge — rewriting a data file without its deleted rows, so the bytes are physically gone.
Position delete file — the Iceberg v2 way of recording deletes: a Parquet file of (data file path, row position) pairs.
Puffin — an Iceberg file format for storing blobs of auxiliary data, including deletion vectors in v3.
Roaring bitmap — a compressed set of integers that adapts its encoding to local density.
Selection vector — a list or bitmap of the rows of a batch that survive filtering; the DV is applied by clearing bits in it.
Protocol version — the Delta table setting that says which features readers and writers must support.
history: Marking rows deleted instead of rewriting data is an old idea. Column stores adopted it early: Vertica keeps "delete vectors" for each storage container, and SQL Server's columnstore indexes keep a "delete bitmap" next to compressed row groups. LSM trees use tombstones for the same purpose. In the Hadoop world, Hive ACID (2014) wrote delta directories with update and delete markers and merged them at read time, and Iceberg's format version 2 (around 2022) added position delete files and equality delete files.
Position delete files had a flaw: each commit could add new delete files, a data file might be referenced by dozens of them, and a reader had to read and join them (a file path plus position, per row) with the data. Delete files multiplied small files and slowed reads until compaction.
Databricks introduced deletion vectors for Delta Lake in 2023 as part of its "predictive I/O" work for faster updates in Photon. The open-source Delta Lake added read support in version 2.3, DELETE in 2.4, UPDATE in 3.0 and MERGE in 3.1. In the Delta protocol, a DV is part of a file's entry in the transaction log, and the bitmap is stored in the Roaring portable format.
Apache Iceberg then adopted the same idea for format version 3: one deletion vector per data file, stored as a blob in a Puffin file, serialized as 64-bit Roaring bitmaps with the same layout choices as Delta (the Iceberg specification notes that big-endian length and CRC fields were chosen for compatibility with existing Delta deletion vectors). With both formats using the same bitmap structure, engines can share code and the DV has become the common way to do row-level deletes in lakehouse tables.
how: Row positions. A Parquet file is a sequence of row groups, and every row has a zero-based position in the file. The position is not stored in the data; the reader computes it while scanning, as the number of rows before the current row group plus the offset inside it. This works because Parquet files are immutable, so a position is a stable identity for a row as long as the file lives. Spark's Parquet reader exposes it as a metadata column (row index).
Writing a delete. For a DELETE, UPDATE or MERGE, the engine finds the rows to change by scanning the table with the predicate, and for every matching row it records the file and the row position. For each touched file, it builds a new bitmap equal to the old bitmap (if the file already had a DV) united with the new positions. Then it writes the bitmap: in Delta, either inline in the transaction log (small vectors, base85-encoded) or in a deletion_vector file in the table directory, where one file may hold many vectors, each found through an offset and a size. In Iceberg v3, it writes a blob into a Puffin file. The commit then replaces the file's entry: in Delta, a remove of the file with the old DV and an add of the same path with the new DV, in one atomic commit. The Parquet file itself is not touched. The old DV file also stays, so earlier table versions still see the old state (time travel).
Writing an update. An UPDATE adds the changed rows to the DV of the old file and writes the new versions of the rows into new data files, in the usual way. A MERGE with matched and not-matched clauses does both for its set of rows. Engines write the new rows with the same file-size and clustering rules as an insert.
The descriptor. In Delta, the file entry carries a descriptor with a storage type ('u' for a file with a path derived from a UUID, 'i' for inline, 'p' for an absolute path), the path or inline bytes, an offset and size inside the file, and the cardinality, the number of rows deleted. The DV file layout is a version byte, then for each vector its size, the bitmap data and a CRC-32 checksum. In Iceberg v3, the manifest entry gives the referenced data file, the offset and length of the blob in the Puffin file, and the cardinality; the blob holds a length, four magic bytes, the 64-bit Roaring bitmap and a CRC-32. A rule in Iceberg is that there is at most one DV per data file in a snapshot, and that it must contain all earlier deletes of that file, including those from older position delete files.
Reading. For every data file, the reader looks at the entry: if there is a DV, it loads the bitmap (reading a few KB from an inline string or a byte range of a file), then scans the file as usual. For every batch of rows, it clears the selection bits for positions in the bitmap, so the deleted rows never reach the filter or the output. Row groups that are completely deleted can be skipped without reading them. Because the check is a bitmap lookup on a position, it costs a few nanoseconds per row, and usually much less when the engine tests a whole range of positions with a container at a time.
Statistics. File-level statistics (min and max values per column) are written when the file is created, so after deletes they may be too wide, which is safe for skipping but not tight. Delta marks them with a tightBounds flag. The number of rows in the file is known, and the DV's cardinality is subtracted, so COUNT(*) without filters can still be answered from metadata (rows minus deleted rows).
Cleaning. A DV is a soft delete. The deleted bytes stay in the file until the file is rewritten. Compaction (OPTIMIZE in Delta, rewrite_data_files in Iceberg) rewrites files with their DVs applied and drops the DV. REORG TABLE ... APPLY (PURGE) does this for all files with DVs. The old files, and the data they contain, stay on storage until VACUUM or snapshot expiration removes them after the retention period.

example: A data file has 1,000,000 rows, positions 0 to 999,999. A GDPR request deletes a user whose rows are at positions 17, 4,096 and 70,000. The writer builds a Roaring bitmap of these three numbers. In Roaring terms, 17 and 4,096 are in chunk 0 (positions 0 to 65,535) and 70,000 is in chunk 1 (65,536 + 4,464). Both are array containers, so the bitmap stores three 16-bit numbers plus a small header: well under 100 bytes. The Delta log entry for the file gets a DV descriptor, with cardinality 3 and, if the bitmap is small, the bytes inline. The Parquet file, 1 GB, is not read again or written.
A query now scans the file. The reader loads the descriptor, decodes the 3-position bitmap and reads the row groups. While processing the batch that contains position 17, it clears the bit for that row, and the same for 4,096 and 70,000. The output has 999,997 rows from this file. A COUNT(*) with no filter would not even read the file: the metadata has numRecords = 1,000,000 and the DV has cardinality 3, so the answer for this file is 999,997.
Another job deletes positions 17 (again) and 500,000. It reads the current DV, builds the union {17, 4,096, 70,000, 500,000}, writes it as a new vector, and commits remove(file with old DV) and add(file with new DV). Time travel to the earlier version still uses the 3-row vector, because DV files are never modified after being written.
Now the cost comparison. Suppose a table has 1,000 files of 1 GB, and a delete touches 2 rows in each of 800 files. Without DVs, the writer rewrites 800 GB. With DVs, it writes 800 vectors of two positions each, perhaps 100 bytes each, 80 KB in total, plus about 800 log entries. Even in the worst case where 30% of a million-row file is deleted, the bitmap is at most 16 chunks × 8 KB = 128 KB, compared with rewriting the 1 GB file, which is about 8,000 times larger.
The price is paid later. If the deletes accumulate to 30% of the rows of every file, each scan reads 100% of the bytes and throws away 30% of the rows. Compaction rewrites the files once, and the table returns to 100% live rows.
intuition: Cross out lines in a printed report instead of reprinting it.
The method works because a row's position in an immutable file never changes. That makes the position a perfect, tiny identity: no key lookup, no hash, just an integer. A set of integers is exactly what Roaring bitmaps store well. The writer pays for what changed, and the reader pays a very small price per row. The physical clean-up moves to a job that can run when the cluster is quiet.
mistakes: People often think a deletion vector removes the data. In fact the data stays in the file and in older table versions. For a privacy deletion you must purge (rewrite the files) and then VACUUM or expire snapshots after the retention period; until then the bytes are still readable by time travel or directly from storage.
People often think deletion vectors always make operations faster. In fact they move the cost to readers and to later compaction. Scattered, small changes gain a lot. A change touching most rows of most files gains nothing: the rewrite is needed anyway, and the vectors would only add overhead until the next compaction.
People often think every engine can read a table that has deletion vectors. In fact a table with the feature enabled has a higher protocol version (Delta reader version 3 and writer version 7), and older clients cannot read it. In Delta 3.0 and later, and in recent Databricks runtimes, you can drop the feature after purging to restore compatibility. Some tools, such as manifest generation for external engines, require a purge first.
People often think the DV stores row IDs from your data. In fact it stores physical positions in one particular file, which have meaning only for that exact version of that file. After a rewrite, positions change, and the vector is dropped. This is why a compaction must apply and remove the vector in the same commit.
friction: Reads must apply the vectors until compaction. A few deleted rows per file cost almost nothing, but vectors that grow over many commits add reading and decoding work, and the data bytes of deleted rows are still read from storage (in the same row groups) and then discarded, so scan I/O does not shrink. UPDATE and MERGE also produce new small data files with the new row versions, so the table accumulates small files until compaction.
Statistics get looser. After deletes, a file's min and max values may describe rows that no longer exist, so data skipping is less effective until the file is rewritten. Count and aggregate shortcuts from metadata must account for the DV cardinality.
Concurrency has limits. Two writers that delete different rows of the same file both want to replace that file's vector. A format that detects conflicts at file level will reject one of them. Some platforms add row-level conflict detection for tables with deletion vectors, but support differs between engines, and file-level detection is the basic behavior.
Compatibility is the other practical cost: protocol upgrades, readers that do not support the feature, scheduled OPTIMIZE or REORG jobs, and users who find a deleted record still readable in an older table version.
practice: Turn on deletion vectors for tables that receive frequent small deletes, updates and merges, such as CDC targets and tables with GDPR deletion. In Delta, set delta.enableDeletionVectors = true (on Databricks, a workspace setting can enable it by default for new tables on DBR 14.3 LTS and later); in Iceberg, use format version 3. Check every engine that reads the table, because the table protocol changes when you enable the feature.
Run compaction on a schedule. For Delta, OPTIMIZE rewrites files and applies DVs when it selects them (not guaranteed for all files); REORG TABLE ... APPLY (PURGE) applies all of them, and you can limit it with a WHERE clause to the affected partitions. Follow with VACUUM when the old bytes must disappear; the retention threshold must account for the time of the purge. Monitor the number of files with DVs and the share of deleted rows (the table history reports the number of deletion vectors and deleted rows).
Make the search for rows cheap, since the DV only fixes the rewrite cost. Cluster or partition the table by the key used in deletes (such as a user ID hash or event date), and keep file statistics fresh, so that the scan for the rows to delete reads few files. For large deletes (more than about 20 to 30% of the table), use a normal rewrite or run compaction right after.
tradeoffs: Choose deletion vectors when changes are small and scattered over many files, changes arrive often (minutes to hours), and readers can tolerate a little extra work until compaction. You gain writes that cost kilobytes instead of gigabytes and commits that finish in seconds; you pay with read-side filtering, small-file growth and scheduled compaction.
Choose a plain rewrite (copy-on-write) for large batch changes that touch most of the rows of most files, for tables that must be readable by engines without DV support, and for legal deletion deadlines where physical removal must be quick and verifiable. You give up write speed and accept high write amplification, and you get clean files and the simplest read path.
Choose position-based DVs over equality delete files when the writer can find positions (batch DML). Choose equality deletes only when the writer cannot look up the row, such as high-rate streaming upserts, and then compact often, because every read has to match keys.
Choose to purge soon after a delete when data must be gone (privacy) or when the share of deleted rows is high (above 10 to 20% of a file); choose to let vectors accumulate when deletes are rare and compaction can run once a day or week. A lower threshold costs more rewrite I/O, a higher threshold costs more read overhead.
interview: What is stored in a deletion vector, and how does a reader use it? || A set of row positions (zero-based ordinals in the Parquet file) that are logically deleted, stored as a Roaring bitmap and referenced from the table metadata. The reader loads the bitmap for each file and clears the selection bits of those positions while scanning, so the rows never reach the output.
Why are positions a safe identity for a row? || Parquet files are immutable, so a row's position never changes while the file exists. Any rewrite creates a new file with new positions, and the old vector is dropped in the same commit. That is also why a DV is only valid for the exact file version it was built against.
How does a DELETE with deletion vectors commit, and how does time travel still work? || The writer scans to find matching positions, unions them with the existing vector, writes a new vector, and commits remove(file, old DV) plus add(file, new DV) atomically. Vectors are never modified in place, so earlier table versions still point at their older vectors and files.
What is the downside of many small updates with DVs and how do you manage it? || The table accumulates vectors that must be applied on every scan, small data files with the new row versions, and wider statistics. Run OPTIMIZE or REORG ... PURGE on a schedule or when the deleted share per file passes a threshold; compaction rewrites files with the vectors applied and removes them.
Compare Iceberg v2 position delete files and v3 deletion vectors. || Position delete files are Parquet files of (file path, position) rows. There may be many per data file, and a reader must read and join them with the data. A v3 DV is one bitmap per data file in a Puffin file, containing all earlier deletes, so the reader loads one small structure per file with no join.
A user asks you to guarantee that deleted data is gone from storage. What do you do? || Run DELETE, then purge (REORG ... @@ occ
value: When several programs change the same data, something must prevent them from overwriting each other. The traditional answer is a lock: take it before you read, hold it until you finish, and make everyone else wait. Locks are safe, but they have costs. A program that holds a lock and then stalls blocks everyone, deadlocks need detection, and on a distributed system or an object store, a lock service is one more thing to run. Optimistic concurrency control (OCC) takes the opposite bet: conflicts are rare, so let everyone work without locks, and check for a conflict only at the end, at commit time. If nothing relevant changed, commit. If it did, throw the work away and retry.
The mechanism needs only one primitive from the storage: an atomic conditional write, such as "write this if the version is still N" (compare-and-swap) or "create this file only if it does not exist". Everything else is checking and retrying in the client. That is why OCC is the concurrency model of lakehouse tables (Delta Lake, Iceberg, Hudi commit with an atomic step on a log or a pointer), of HTTP APIs (ETag with If-Match), of DynamoDB conditional writes, and of several databases (FoundationDB, Hekaton, Silo).
For the layer above, the lakehouse (L1), OCC lets many Spark jobs write to one table on object storage without any lock service: each job writes its data files freely, then commits by atomically adding the next entry to the table log. For the data catalog (L1), a table commit is an atomic pointer update. The layers below give the correctness argument. Concurrency control (L3) provides the framework: validate at commit, in the optimistic family. ACID transactions (L3) provide the goal: validation makes the committed result equal to some serial order of the transactions, so isolation holds, and the single atomic step is what makes the commit all-or-nothing.
terms: Optimistic concurrency control (OCC) — run without locks, validate at commit, abort and retry on conflict.
Pessimistic concurrency control — take locks first (for example two-phase locking) and make conflicting transactions wait.
Read set and write set — the items a transaction read, and the items it wants to change.
Validation — the commit-time check that no transaction committed since mine started has changed anything I read.
Compare-and-swap (CAS) — an atomic operation: set a value to new only if it is still equal to expected.
Put-if-absent (conditional create) — an atomic write that succeeds only if the object does not already exist.
Snapshot — the table state at one version; a transaction reads from one snapshot.
Write skew — an anomaly where two transactions read the same data, change different items, and together break a rule that each one checked.
Backoff with jitter — waiting a random, growing time between retries so that competing clients do not retry in lockstep.
history: Locking was the first method. Eswaran, Gray, Lorie and Traiger (1976) formalized two-phase locking, and for the next decade it was the way databases did concurrency. In 1981, H. T. Kung and John T. Robinson published "On Optimistic Methods for Concurrency Control" (ACM TODS). They observed that locking has a cost even when there are no conflicts, and that for many workloads, such as read-mostly or large B-trees where updates rarely meet, it is better to run freely and verify at the end. Their transaction has three phases: read (work on private copies), validation, and write (make the changes visible, only if validation passed).
Related ideas followed. Multiversion concurrency control with snapshot isolation (Berenson and others, "A critique of ANSI SQL isolation levels", 1995) let readers use a snapshot and writers detect write-write conflicts with "first committer wins". Serializable snapshot isolation (Cahill, Röhm and Fekete, 2008; in PostgreSQL since 9.1, 2011) added read-write conflict tracking. Main-memory databases revived OCC: Hekaton at Microsoft (Larson and others, VLDB 2011) and Silo (Tu and others, SOSP 2013). FoundationDB (2013 onward) uses OCC with a conflict-checking service and a 5-second transaction limit.
For storage systems, OCC became the natural model once cloud object stores arrived: they offer immutable objects and, later, conditional operations, but no locks and no rename. Delta Lake (Armbrust and others, VLDB 2020) commits by atomically creating the next numbered log file, and Iceberg commits by atomically swapping the table's metadata pointer in a catalog. Amazon S3 added conditional writes with If-None-Match in August 2024 and If-Match (compare-and-swap on the object's ETag) in November 2024. Before then, Delta on S3 needed an external coordinator, such as a DynamoDB table, to supply the atomic step.
how: The core loop has five steps. Step 1, begin: read the current version V of the data (for a table, the latest log entry or metadata pointer). Step 2, work: read the data from that snapshot and compute the changes, writing new data files freely; the new files are invisible to others because no log entry mentions them. Step 3, validate: look at what happened between V and now, meaning the commits with versions after V, and check whether any of them conflicts with what this transaction read or wants to write. Step 4, commit: do the atomic conditional write that makes the change visible, such as creating log entry V+1 only if it does not exist. Step 5, on failure, either the conditional write fails (someone committed V+1 first) or validation finds a conflict. In the first case, go back to step 3 with the newer commits; in the second, abort and rerun from step 1.
Where validation gets its answer. A conflict is defined by the read and write sets. With backward validation (Kung and Robinson), transaction T is checked against every transaction that committed after T started: T may commit if none of their write sets overlap T's read set. This is enough to make the committed transactions behave as if they ran one after another, in commit order. The set granularity decides the strictness. Delta tracks files and predicates: a delete that read file f1 conflicts with a commit that removed or rewrote f1. A concurrent append to a different partition does not conflict. Iceberg tracks files and, for some operations, the filter expressions (the validation of an overwrite checks that no conflicting data files were added within its filter).
The atomic step. Everything depends on a single operation that cannot be split. Delta needs put-if-absent for _delta_log/<version>.json: two writers racing for version 13 will have exactly one succeed. On an object store without that primitive, the table needs an external coordinator (DynamoDB conditional puts, or the service of the vendor), or it is not safe for concurrent writers. Iceberg needs compare-and-swap of the current-metadata pointer in the catalog, which the catalog implements with a database row update with a condition, a lock in the Hive metastore, or an atomic call in a REST catalog. The new metadata file is already written and complete before the pointer moves, so readers see either the old table or the new one, never a partial state.
Retrying without redoing the work. If a commit lost the race but the new commits do not conflict with it, the transaction does not rerun its job. It rebases: it re-reads only the metadata (the new log entries), re-checks, and commits at the next version. The expensive part, writing data files, is kept. Iceberg does the same by reapplying its manifest changes on top of the refreshed metadata, with a default of a few retries (4) and exponential backoff between them. Only a true conflict, meaning the data it read changed, sends the writer back to the start.
Contention handling. A long transaction racing with a stream of short ones may fail every time: its read set is invalidated by whoever commits during its run. Systems use bounded retries, exponential backoff with random jitter (so competing clients spread out), and sometimes a fallback to locking after repeated failures, which is what Kung and Robinson suggested for starvation. The practical measure is to reduce the window (shorter transactions) and the overlap (narrower write sets).
Isolation level choices. Delta Lake offers Serializable, where the outcome equals some serial order and a concurrent append that could match a delete's predicate causes a conflict, and WriteSerializable (the default for most operations), which only requires that the writes be serializable and permits some reorderings of reads, in exchange for fewer conflicts. This is the usual trade: a weaker check gives fewer aborts and admits more anomalies, like write skew.
Mapping to ACID. Atomicity comes from the single commit step: either the log entry exists or it does not. Isolation comes from validation, which makes the committed result equal to a serial order. Durability comes from the storage having accepted the file before the commit. Consistency is the application's own rules, which validation protects by preventing lost updates.

example: Use the log in the diagram. A Delta table is at version 12 with partitions by day. Writer A runs a DELETE for day 2026-10-01 that reads and rewrites file f1. Writer B appends a new file f9 to day 2026-10-02. Both start from version 12. B finishes first and creates 13.json with the put-if-absent call, which succeeds. A finishes and tries to create 13.json; the call fails because the file exists. A reads 13.json and sees that B added f9 in another partition. A's read set contains f1 only, so there is no conflict. A does not rerun the delete (that could have taken ten minutes); it creates 14.json and succeeds. The cost of losing the race was one failed conditional write and one small metadata read, a few hundred milliseconds.
Writer C also started at version 12 and rewrote f1, for example in a MERGE. When C tries to commit, 13.json and 14.json exist. C reads them and sees that A, in 14.json, removed f1 and added f1'. C read f1, so its work is based on a file that no longer exists in the table. Delta raises a concurrent-modification exception (ConcurrentDeleteReadException, because a file C read was removed). C must rerun from version 14, which repeats its scan and rewrite. If the job takes 10 minutes, this costs 10 minutes.
Now the probability. A table has 2,000 files. Writer A rewrites k files and writer B rewrites k files, chosen at random. The chance that they share at least one file is about 1 − (1 − k/2000)^k. For k = 5 it is 1.2%. For k = 20 it is 18%. For k = 100 it is 99.4%. So the conflict rate grows with the square of the footprint: a job that touches 20 files conflicts with another such job once in five tries, and a job that rewrites a fifth of the table nearly always does. Conflicts depend on which files a job touches, not on how many bytes it writes, so deletion vectors make the job cheaper but leave the file-level footprint the same. The remedy is not a smarter retry but a smaller footprint: partition so that writers use different files, or write through a single committer.
The expected number of runs is 1/(1 − p), where p is the chance that one attempt conflicts. For p = 0.1 that is 1.11 runs; p = 0.5 gives 2 runs; p = 0.9 gives 10 runs, and the cost explodes. This is the number that tells you when to stop being optimistic.
intuition: Edit freely, and at save time check whether someone else changed the same thing.
OCC is natural because checking is cheaper than preventing. A lock must be acquired by everyone on every transaction, including the 99% that would never have conflicted, and it must be released even if the holder crashes. A check at the end costs one comparison for the transactions that did not conflict, and costs a retry only for those that did. The bet is good when conflicts are rare and retries are cheap, and bad when conflicts are common and work is expensive.
mistakes: People often think OCC means no coordination. In fact it still needs one atomic, strongly consistent step on shared state: a conditional write, a CAS or a put-if-absent. Without that primitive (as on older object stores), two writers can both succeed and silently overwrite each other's log entry, and the table is corrupted.
People often think a failed commit always means the job must be redone. In fact most lost races, when the other commit touched other files, are resolved by re-checking metadata and committing again at the next version. Only a real conflict repeats the data work. This is why the conflict rate depends on what writers touch, not on how many writers run.
People often think OCC is the same as snapshot isolation. In fact snapshot isolation detects only write-write conflicts ("first committer wins") and permits write skew, in which two transactions each read a rule and change different rows so that together they break it. Full OCC validation includes the read set. Delta's WriteSerializable level is weaker than Serializable in a related way.
People often think OCC is always faster than locking. In fact under high contention it wastes work: p = 0.9 means about ten executions per success, and long transactions can starve. Pessimistic locking, or a single writer that queues the changes, wins on hot spots such as one counter or one key updated by everyone.
friction: Wasted work under contention is the main cost. A job that runs for an hour and loses the race on its last step has used an hour of compute for nothing, and a few such jobs together can be much worse than serial execution. Retrying with backoff reduces the collisions but increases latency, and a long transaction may never get through while short ones keep committing, which is a form of starvation.
Throughput on a single object is limited. All commits to one table serialize through one log or pointer, and each commit takes a round trip to storage or the catalog (tens to hundreds of milliseconds). With hundreds of small writers, such as streaming micro-batches every second, the table sees many races, and the metadata (log entries or snapshots) grows fast and needs checkpointing and compaction.
The correctness of OCC depends on the primitive. Object stores that provide only eventually consistent or non-atomic operations make it unsafe; catalogs with weak locks cause bugs. Validation granularity is a design problem: file-level detection reports false conflicts (two writers updating different rows in the same file), while row-level detection needs more metadata and engine support. Finally, side effects: anything the transaction does outside the transaction (sending an email, calling an API) is repeated at every retry, so work must be idempotent or deferred until after commit.
practice: Make footprints small and disjoint. Partition or cluster tables so that concurrent jobs write to different partitions, and declare the partition in the job (for example a replaceWhere or a partition predicate in the condition of MERGE), because a narrow predicate lets the engine prove that two jobs do not overlap. Avoid many jobs doing UPDATE or MERGE on the same files at the same time. Where possible, use append-only writes, which almost never conflict in Delta and Iceberg.
Keep transactions short: do the heavy computation first, then commit quickly. Retry on conflict exceptions with exponential backoff and jitter and a cap on attempts, and make the job idempotent. In Delta, catch the concurrent modification exceptions and rerun; in Iceberg, the retry settings (commit.retry.num-retries, min-wait-ms, max-wait-ms) control the loop. Make compaction jobs (OPTIMIZE, rewrite_data_files) run on partitions that are not being written, or on a schedule that avoids active writers, since compaction rewrites files that writers may also change.
For hot spots, use a single committer. Many writers can write data files, and one process (a streaming job, a Kafka consumer or a small service) commits them in batches. This replaces N-way races with a queue, and commits less often with more data, which also reduces small files and log growth.
For HTTP APIs and key-value stores, use the same pattern: read the version (ETag or revision), send If-Match or a conditional write, and handle 412 or the conditional failure by re-reading and merging. Never do an unchecked read-modify-write on a shared record.
tradeoffs: Choose OCC when conflicts are rare (as a rule of thumb, a conflict probability below about 10 to 20% per attempt), transactions are short or their expensive part can be kept across retries, and there is no lock service. You get no lock waits, no deadlocks and no stale locks from crashed clients; you pay with wasted work on conflict and with starvation of long transactions.
Choose pessimistic locking or a queue (single writer) when a few records or files are hot and every writer touches them, when a transaction is expensive and conflicts are likely, or when the work has side effects that cannot be repeated. You pay with lock waits, deadlock handling and a lock service, or with the throughput limit of one writer, and you gain predictable completion.
Choose coarse validation (whole table or partition) when simplicity matters and writers rarely overlap; choose fine validation (files, predicates, rows) when many writers work in parallel on different parts of the same table. Fine validation needs more metadata and engine support and has a cost per commit; it reduces false aborts.
Choose Serializable when correctness rules span rows (balances, quotas, uniqueness enforced by the application) and WriteSerializable or snapshot isolation when jobs mostly append or touch disjoint data and you can accept the anomalies. The weaker level aborts less, the stronger level protects invariants.
interview: How does a lakehouse table implement a commit without locks? || The writer creates its data files first, which are invisible. To commit it atomically creates the next log entry (put-if-absent) or swaps the metadata pointer (compare-and-swap). If that fails, someone committed first, so it reads the new commits, validates against them, and retries at the next version, or aborts if they conflict with what it read.
Two writers update the same table at the same time. When do they conflict, and when not? || They conflict if one of them changed (or removed) a file that the other read or wants to change, or, at Serializable, added data that matches the other's predicate. Appends to different partitions or updates of different files do not conflict, so the later writer re-checks and commits without redoing its work.
What is the failure mode of OCC with a long-running job and many short writers, and how do you fix it? || The long job's read set is invalidated by almost every short commit, so it aborts repeatedly and starves, wasting hours of compute. Reduce its footprint with partitions or predicates, split it into smaller transactions, schedule it when others are quiet, or serialize the short writers through a single committer.
Why is compare-and-swap (or put-if-absent) essential, and what happens without it? || Validation and commit are two steps, and another writer can commit between them unless the commit itself is conditional. Without the conditional primitive, two writers can both pass validation and both write the same version, so one commit silently overwrites the other. Stores without it need an external coordinator.
Compare snapshot isolation and serializable OCC validation. || Snapshot isolation detects write-write conflicts only, so two transactions that read overlapping data and write different rows can both commit, allowing write skew. Validating the read set against concurrent writes closes that hole, at the price of more aborts.
How would you choose between OCC and a queue with a single committer for a table fed by 200 streaming jobs? || Many small writers racing on one table give frequent conflicts and metadata growth. A single committer batches their files into fewer, larger commits and removes races, at the cost of an extra component, a small added latency and a single point to make highly available. If the jobs write disjoint partitions and commits are infrequent, plain OCC is fine.
quiz: What are the three phases of an optimistic transaction? || Read (work on private copies), validation (check for conflicts with transactions that committed meanwhile), and write (make the changes visible if validation passed).
Why does a lakehouse commit use put-if-absent or compare-and-swap? || It makes the commit atomic and conditional: only one writer can create a given version, so a concurrent writer is forced to see the other commit and re-validate instead of overwriting it.
Two writers each rewrite 20 random files out of 2,000. About how likely are they to conflict? || About 1 − (1 − 20/2000)^20 = 1 − 0.99^20 ≈ 18%.
If each attempt conflicts with probability 0.5, how many executions are needed on average? || 1 / (1 − 0.5) = 2 executions per success.
Why can a conflicting writer sometimes commit without rerunning its job? || If the other commits touched different files or partitions than it read, validation passes, and it only needs to re-read the new metadata and commit at the next version; its data files are still valid.

@@ encoding
value: Every analytic query is limited by how fast it can move bytes: from object storage over the network, from disk into memory, and from memory into the CPU caches. Encoding and compression attack this limit directly. If a column takes one third of the bytes, the scan moves one third of the data. Columnar files such as Parquet and ORC usually shrink a table by 3 to 10 times compared with the raw text, and the scan gets faster by a similar factor as long as decoding is fast. The same ideas cut storage cost, and make time-series databases store a metric sample in about one or two bytes.
Two layers do the work, and they do different jobs. Lightweight encodings (dictionary, run-length, delta, frame of reference, bit-packing) use the structure of a column: values repeat, are sorted, or lie in a small range. They are cheap to decode, and some can be used without decoding at all. General-purpose compressors (LZ4, Snappy, Zstd, Gzip) are then applied to the encoded bytes to remove whatever redundancy is left. Real files use both: Parquet first encodes a page of a column with a dictionary and bit-packing, then compresses that page with a codec such as Snappy or Zstd.
For the layers above, OLAP analytics (L1) gets the 5 to 10 times smaller columns and engines that filter on dictionary codes directly, and observability (L1) gets time series that cost a byte or two per point by using delta and XOR encoding. The layers below explain the limits. Information theory (L4) says how much a column can shrink at best: its entropy. Kolmogorov complexity (L4) says the same thing in terms of description length: the shortest description of the data is the best compression, and we can only approximate it with practical methods.
terms: Entropy — the average number of bits per value that any lossless code needs at minimum, given the distribution of the values.
Dictionary encoding — replace each value by a small integer code and store the list of distinct values once.
Run-length encoding (RLE) — store a repeated value as (value, count).
Delta encoding — store the difference between each value and the previous one; delta-of-delta stores the difference of those differences.
Frame of reference (FOR) and bit-packing — subtract a base value from a block, then store each result using only as many bits as the largest one needs.
LZ77 — a compression method that replaces a repeated byte sequence with a pointer (distance, length) to its earlier copy.
Entropy coding (Huffman, ANS) — assign short codes to frequent symbols and long codes to rare ones.
Compression ratio — original size divided by compressed size.
Late materialization — keeping data encoded as long as possible during a query and decoding only the values that reach the output.
history: Claude Shannon's 1948 paper defined entropy and proved that no lossless code can use fewer bits per symbol on average. David Huffman (1952) gave an optimal code for symbol-by-symbol coding. Abraham Lempel and Jacob Ziv (1977, 1978) invented LZ77 and LZ78, which find repeated strings instead of repeated symbols. DEFLATE, in gzip and zlib (1990s), combines LZ77 with Huffman coding and is still everywhere.
Database compression started with column stores. The MonetDB and C-Store/Vertica work (2000s) argued that data in a column is similar and so compresses well. Abadi, Madden and Ferreira ("Integrating compression and execution in column-oriented database systems", SIGMOD 2006) showed that an engine can run queries directly on RLE and dictionary data, and that the choice of scheme should depend on sort order and cardinality. Parquet and ORC (2013) brought these encodings to Hadoop-style files; Parquet follows the Dremel paper (2010).
Speed became the next goal. Google's Snappy and Yann Collet's LZ4 (both 2011) accept a lower ratio for decoding at memory speeds. Collet's Zstandard (Facebook, 2016; standardized in RFC 8478, now RFC 8878) uses a faster entropy coder, finite state entropy, based on the asymmetric numeral systems of Jarek Duda (2009 to 2013), to get ratios near zlib at much higher speed. Facebook's Gorilla (Pelkonen and others, VLDB 2015) compressed time-series points from 16 bytes to about 1.37 bytes with delta-of-delta timestamps and XOR floating-point values.
Recent research continues: FSST (Boncz, Neumann and Leis, VLDB 2020) compresses short strings while allowing random access; BtrBlocks (Kuschewski and others, SIGMOD 2023) chooses among cascades of lightweight encodings per block, aiming at fast decoding for data lakes; ALP (Afroozeh and others, SIGMOD 2024) compresses floating-point columns that are really decimals.
how: Step 1, encode by structure. A column writer looks at a page of values (Parquet default pages are about 1 MB) and picks an encoding. Dictionary encoding: collect the distinct values (up to a limit; Parquet's dictionary page defaults to 1 MB and the writer falls back to plain encoding when it overflows), assign codes 0, 1, 2, …, and write the codes. A column with d distinct values needs ⌈log₂ d⌉ bits per code, so 20 cities need 5 bits, not 80. Bit-packing writes the codes with exactly that width, and Parquet's RLE/bit-packing hybrid switches between runs (value and count) and groups of 8 packed values depending on the data.
Step 2, other lightweight encodings by data type. For sorted or slowly changing integers (timestamps, IDs), delta encoding stores differences, which are small; then frame of reference subtracts the block minimum and bit-packs (Parquet's DELTA_BINARY_PACKED does this in miniblocks). For strings that share prefixes (URLs, sorted keys), front coding stores the length of the shared prefix and the new suffix. For floating-point values, XOR with the previous value (Gorilla) or splitting the bytes of each value into separate streams (Parquet's BYTE_STREAM_SPLIT) exposes zero bytes and repeated bytes. For time series with regular intervals, delta-of-delta makes most timestamps zero, which cost one bit each.
Step 3, apply a general compressor. The encoded page is compressed as a whole with a codec. LZ77-style codecs (LZ4, Snappy) scan the bytes with a hash table of recent positions and emit literals and (distance, length) matches, which is fast and needs no entropy coding. Zstd and DEFLATE add entropy coding of the literals and match symbols (Huffman or FSE), which gives better ratios at a lower speed. On the Silesia corpus (zstd's benchmark, 1.5.7), LZ4 gets a ratio of about 2.1 and decodes at about 3.9 GB/s per core; Snappy gets 2.09 and 1.5 GB/s; Zstd at level 1 gets 2.9 and 1.55 GB/s; zlib level 1 gets 2.74 and 0.39 GB/s. These numbers are for general text-like data; encoded columns often compress further.
Step 4, why both layers. A general compressor works on bytes and finds repeats within a window, but it does not know that a column holds 20 distinct strings or that each value is the previous plus a small number. Lightweight encodings turn this knowledge into smaller numbers and long runs, and the compressor then squeezes the remaining patterns. Doing it in the other order does not work, because compressed bytes look random to an encoder.
Step 5, read and decode. A reader loads the page, undoes the compression (decompression speed matters most, because every query pays it), and then either decodes the values into arrays or operates on the encoded form. A filter such as city = 'Pune' becomes a filter on one integer code: look up the code in the dictionary once, then compare integers (with SIMD, many at a time). If a page's dictionary does not contain the code, the whole page is skipped. For RLE data, a predicate is checked once per run, and a COUNT or SUM can be computed as count × value. This is the "operate on compressed data" idea.
Layout and statistics. Pages are grouped into column chunks and row groups, and each chunk records its encoding, its compressed and uncompressed sizes, and min and max values. A reader uses these statistics to skip whole chunks before reading any bytes, so encoding choices also shape what can be skipped: sorted data gives tight min and max ranges per page, and random data gives wide ones.
Step 6, the entropy limit. Information theory says what is possible: if the values in a column have a skewed distribution, the best code uses the entropy H = −Σ p log₂ p bits per value. Dictionary plus fixed-width bit-packing spends ⌈log₂ d⌉ bits regardless of skew. Huffman or ANS coding gets closer to H. A general compressor's literal coder does this on bytes. Kolmogorov complexity says that the true minimum is the length of the shortest program that prints the data, which no algorithm can compute; practical compressors use fixed families of models (repeats, small ranges, runs) and the work is choosing the right family for the data.
diagram:
  raw column "city" (1M rows, 20 distinct values, unsorted)
    "Pune" "Delhi" "Pune" "Mumbai" "Pune" ...        ~ 14 MB as text

  1) dictionary      dict  = [Delhi, Mumbai, Pune, ...]  (20 entries)
                     codes = 2 0 2 1 2 ...
  2) bit-pack 5 bits 00010 00000 00010 00001 00010 ...    ~ 625 KB
  3) LZ4 / Zstd on the page bytes                         a bit smaller

  the same column sorted by city:
  dictionary + RLE   (Delhi x 51,200) (Mumbai x 43,000) ...
                     20 runs                              ~ 120 bytes

  timestamps in ms, sorted:
    1700000000000  +100  +95  +103  +98 ...
    base + small deltas, frame of reference, 9 bits each  ~ 1.1 MB
                                                          (was 8 MB)
    regular 1 s samples: delta-of-delta = 0 0 0 ...       ~ 1 bit each

                     (knows the column)      (finds byte repeats)

example: Take a column of 1,000,000 city names, 20 distinct values, 10 bytes on average. As plain strings with a 4-byte length each, it is about 14 MB. With dictionary encoding, the 20 names are stored once (about 200 bytes), and each row gets a 5-bit code (2^5 = 32 ≥ 20): 1,000,000 × 5 bits = 625 KB, a ratio above 20. If the values are skewed, 40% in one city, 30% in another and the remaining 30% spread across 18 cities, the entropy is −0.4 log₂ 0.4 − 0.3 log₂ 0.3 − 0.3 log₂(0.0167) ≈ 0.53 + 0.52 + 1.77 = 2.82 bits per row, so an ideal entropy code would need about 353 KB. A general codec on the bit-packed bytes will recover part of that gap, but not all, because the 5-bit codes do not align with byte boundaries.
Now sort the table by city. The column is now 20 long runs. RLE stores each run as a (code, count) pair, so the whole column is about 20 × 6 bytes = 120 bytes. Sorting by one column makes that column almost free, and it helps the other columns a little, which is why some systems sort or cluster tables on purpose.
Timestamps. 1,000,000 events in milliseconds, sorted, arriving about 10 per second, so the gaps are 0 to about 400 ms. Plain 64-bit values take 8 MB. With delta encoding, each gap is below 512, so a 9-bit field is enough: 1,000,000 × 9 bits ≈ 1.1 MB, a ratio of 7. For a metric sampled exactly every 1,000 ms, the delta is always 1,000 and the delta-of-delta is 0. Gorilla writes a single zero bit for that case, so a million timestamps take 125 KB, and the value can be XOR-coded as well.
Now the speed question. A node reads from object storage over a 25 Gb/s network, about 3 GB/s. Compressed data arrives at 3 GB/s, and the CPU must expand it to the logical stream. With Zstd at a 2.9 ratio, the logical rate is 8.7 GB/s, and decoding that at 1.55 GB/s per core needs about 5.6 cores. With LZ4 at a 2.1 ratio, the logical rate is 6.3 GB/s, and the decoder needs only 1.6 cores at 3.9 GB/s per core. On an 8-core node, Zstd leaves about 2.4 cores for the query operators and moves more logical data per second; LZ4 leaves 6.4 cores and moves less. Which is better depends on how heavy the query is: a light scan benefits from Zstd, while a join-heavy query may prefer LZ4. With uncompressed data the same node would only see 3 GB/s of logical data, with all cores free for the query.
intuition: Write "the same as above × 1,000" instead of copying a value a thousand times.
Compression is possible because real data is not random. If every value were equally likely and unrelated to its neighbours, nothing could be saved; a counting argument shows that no lossless method can shrink all inputs. But columns are repetitive in specific, simple ways: few distinct values, long runs, small steps. Each lightweight encoding is a small model of one such pattern, and each costs a few instructions to undo. The compressor is a catch-all for the rest. The better the model matches the data, the closer the size gets to its entropy.
mistakes: People often think compression always saves time. In fact it moves cost from I/O to CPU. If the data is already in memory, or the CPU is the bottleneck, a heavier codec slows the query. The correct test is end-to-end: storage bandwidth times ratio against the number of cores needed to decode.
People often think a higher compression level is just better. In fact higher levels cost much more CPU on writes for a small ratio gain, and they do not change decoding speed much for Zstd. Choose a level by write throughput and storage price; for hot, frequently rewritten tables, a low level (1 to 3) is common, and a high level (such as 9 or 19) fits cold archives written once.
People often think the general compressor does all the work. In fact much of the gain in columnar files comes from the lightweight encodings, and the order of the data matters. Sorting by a low-cardinality column can shrink it by orders of magnitude, while the same data in random order barely benefits from RLE.
People often think encoded data must be decompressed before use. In fact good engines evaluate filters, joins and aggregates on dictionary codes and runs, and decode only the values that reach the result. This is the idea behind late materialization, and it is where compression gives speed and not just space.
friction: Decoding costs CPU on every read, and random access into a compressed page is hard: to read row 500,000 you may need to decode the whole page or block unless the encoding supports offsets (bit-packing does, RLE needs a search, general codecs need the full block). Pages are therefore a few hundred KB to 1 MB, a balance between ratio, memory and skipping granularity.
Effectiveness depends on the data. High-cardinality columns (UUIDs, free text, hashes) have almost no repeated structure, so dictionaries overflow and fall back to plain, and the compressor finds little; random UUID strings compress by little more than the hex-to-binary ratio. Floating-point measurements with noisy low bits resist compression. Data order matters, and you may not be able to choose it.
Portability and write cost are further limits: choosing an encoding per page needs a sampling pass, some readers do not support newer Parquet encodings such as DELTA_BINARY_PACKED or BYTE_STREAM_SPLIT, and changing a codec means rewriting the table. Finally, compression hides the true data volume: query cost and memory use follow the decoded size, and a very compressible column can still blow up in memory after decoding.
practice: Use the defaults of the format first, then measure. In Parquet, the writer picks dictionary or plain encoding per column automatically, and you choose the codec per file or table. Snappy and LZ4 favor speed; Zstd (level 1 to 3) is a good default for lakehouse tables because it gives noticeably smaller files than Snappy for a modest decode cost, which matters when the network is the bottleneck. Check the codec your engine uses by default; it varies by engine and version, and you can set it per table or per write.
Sort or cluster data by the columns that you filter on and that have low cardinality (date, country, tenant). This is the cheapest way to get better RLE and dictionary effects, and it also makes data skipping effective. Z-ordering and liquid clustering trade some of this for multi-column locality.
Look at the real column sizes: use the Parquet metadata (parquet-tools or pyarrow's metadata) to see encodings and compressed and uncompressed sizes per column chunk. Large columns are the ones to attack: for a high-cardinality string, consider hashing, splitting it into parts (such as URL host and path), or storing it once in a dimension table. Store timestamps and measures as numbers with the right resolution (seconds instead of milliseconds when that is enough; decimals as scaled integers). For time series, use a database or format with delta-of-delta and XOR encoding, and avoid storing the same series as text.
For hot data in memory prefer light codecs (dictionary, bit-packing, LZ4); for cold archives prefer Zstd at a higher level. Test with representative data, because benchmark ratios do not transfer to your columns.
tradeoffs: Choose LZ4 or Snappy when the CPU is the bottleneck, data is read from local SSD or memory, or latency is important. You get decoding at 1.5 to 4 GB/s per core and a ratio of about 2 on general data, and you give up 30% or more of the space that Zstd would save.
Choose Zstd at a low level (1 to 3) as the default for data lakes: it gives ratios about 40% better than LZ4 (2.9 against 2.1 on the Silesia corpus), with decoding about 2.5 times slower (1.55 against 3.85 GB/s per core) and good write speed. Choose a high Zstd level (10 to 19) for cold data written once and read rarely, accepting writes 10 to 100 times slower. Avoid Gzip for new tables, since Zstd gives similar or better ratios with decoding several times faster.
Choose dictionary encoding for columns with fewer than about 10,000 distinct values or many repeats (it also enables fast filters on codes); choose plain or delta-length encoding for high-cardinality strings, where the dictionary would be as large as the data. Choose delta or delta-of-delta for sorted or regular numbers; choose BYTE_STREAM_SPLIT for floating-point columns with a general codec.
Choose to spend sorting effort at write time when the table is read far more often than written; choose not to sort when writes are streaming and latency matters, and use periodic compaction with a sort instead.
interview: Why do column stores compress better than row stores, and what does dictionary encoding give besides size? || A column holds values of one type and domain, with repeats and often sorted or clustered, so lightweight encodings work. Dictionary encoding also turns string filters and group-bys into integer operations on codes (one dictionary lookup per query, then SIMD integer comparison), and lets whole pages be skipped when the dictionary lacks the value.
When does compression make a query slower? || When the scan is CPU-bound or data is already in memory: the decode cost is paid and no I/O is saved. Check the balance: effective logical rate = bandwidth × ratio, which needs (logical rate ÷ decode speed per core) cores. If this uses most of the cores, a lighter codec such as LZ4 or no general codec is better.
Explain Parquet's two-stage approach and why the order matters. || The encoding stage (dictionary, RLE/bit-packing, delta) uses knowledge of the column to produce small integers and runs; the codec stage (Snappy, Zstd) removes remaining byte-level repeats. Encoding first works because encoded bytes still have structure; compressing first hides the structure from the encoder.
How would you reduce the size of a 5 TB table of events with a user ID, a timestamp and a JSON payload? || Look at column sizes first. Sort by event date and a low-cardinality key, store timestamps as delta-friendly integers, replace user IDs with a compact integer where possible, parse the JSON into typed columns (so each gets its own encoding), use Zstd instead of Snappy, and move rarely used fields to a separate table.
What is the theoretical limit of compression for a column, and how close do practical encodings get? || Entropy of the value distribution under a good model. Fixed-width dictionary codes spend ⌈log₂ d⌉ bits per value, which is far above entropy for skewed data; Huffman or ANS coding gets near entropy per value but costs more to decode, and general codecs capture repetition patterns the model misses. Kolmogorov complexity is the true limit and cannot be computed.
Why is random access a problem for compressed columns and how do formats handle it? || Codecs and delta encodings work on blocks, so reading one value needs the whole block decoded. Formats keep blocks small (pages), store offsets and statistics so that readers can skip pages, and use fixed-width bit-packing within a block so that a position can be computed directly.
quiz: Why does dictionary encoding with 20 distinct values need 5 bits per row? || A code must name one of 20 values. With 4 bits there are 16 codes, which is too few; 5 bits give 32 codes. The size is ⌈log₂ 20⌉ = 5 bits.
Which encoding fits a sorted timestamp column best, and why? || Delta encoding (with frame of reference and bit-packing), because the differences between neighbours are small numbers that need few bits. For regular intervals, delta-of-delta is even smaller.
A column has a skewed distribution with entropy 2.8 bits per value. What does 5-bit dictionary packing waste, per million rows? || About 2.2 bits per row, which is 1,000,000 × 2.2 / 8 ≈ 275 KB, that an entropy coder could save.
Why can an engine run a filter on dictionary-encoded data without decoding it? || It looks up the filter value in the dictionary once to get its code, then compares integer codes in the column. If the value is not in the dictionary, no row matches.
Name one case where heavier compression makes a query slower. || When the data is cached in memory or read from fast local storage, so that I/O is no longer the bottleneck and the extra decode work only adds CPU time.
