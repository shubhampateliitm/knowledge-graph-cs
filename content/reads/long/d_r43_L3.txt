@@ ssh
value: SSH (Secure Shell) lets you log in to another machine, run commands on it, copy files to it and reach services behind it, over a network that anyone can watch and tamper with. Before SSH, telnet, rlogin, rsh and ftp sent your password and every keystroke as plain text, readable by anyone on the same network segment. SSH replaces them with one TCP connection that is authenticated at both ends, encrypted, protected against modification, and able to carry many independent streams: a shell, a file transfer, a forwarded port.
SSH is three protocols stacked together, and each uses a different foundation from below. The transport layer builds the secure pipe. Public-key cryptography (pkcrypto) gives a key exchange that produces a shared secret nobody else can compute. Digital signatures (signatures) let the server prove which machine it is. Cryptographic hashes (hashfn) bind the whole conversation into one value that is signed, and derive the keys. Authenticated encryption (aead, built on the symmetric ciphers of symcrypto) hides every packet and makes tampering detectable. The authentication layer uses signatures again, this time from the user's key. The connection layer multiplexes channels. All of it rides on TCP (tcp), which supplies a reliable, ordered byte stream, so SSH has no retransmission logic of its own.
For the layer above, SSH is a general secure tunnel. Git pushes run `git-receive-pack` as an SSH command. Ansible, rsync, backup tools and cloud consoles run commands over it. A bastion host turns one reachable machine into a door to a private network.
terms: Host key — the long-term key pair that identifies a server machine; clients compare its public half with what they saw before.
known_hosts — the client file (~/.ssh/known_hosts) that records host keys seen earlier, so a changed key is detected.
Key exchange (KEX) — the first step, where both sides use temporary keys to agree on a secret that is never sent over the wire.
Exchange hash (H) — a hash of both identification lines, both algorithm lists, the host key, both temporary public keys and the shared secret; the server signs it, and the first H is the session ID.
Channel — a numbered logical stream inside the one encrypted connection, with its own flow-control window.
Window — the number of bytes a sender may still send on a channel before the receiver grants more credit.
authorized_keys — the server-side file that lists the public keys allowed to log in as that user.
ssh-agent — a process that holds your decrypted private keys and signs challenges over a Unix socket, so the key never leaves it.
SSH certificate — a public key signed by a certificate authority, with allowed user names and a validity period.
history: In spring 1995 a password-sniffing attack hit the network of Helsinki University of Technology, where Tatu Ylönen worked. He wrote a replacement for rlogin and telnet within months and released it as free software in July 1995. It spread fast. He founded SSH Communications Security that year, and he later said he picked port 22 because it was free and sat between ftp (21) and telnet (23). SSH-1 had design weaknesses, such as a CRC-32 integrity check that allowed insertion attacks.
SSH-2 was designed from 1996 as a cleaner, incompatible protocol, and the IETF standardised it in January 2006 as RFC 4250 to 4254. Meanwhile the original software's licence became restrictive, so the OpenBSD developers took the last free version (1.2.12) and made OpenSSH, released in December 1999. OpenSSH is now the SSH on Linux, macOS, BSD and Windows, and its releases set the practical standard.
OpenSSH then moved the protocol forward mostly by removing old cryptography. Roughly: certificates (2010); Ed25519 keys, Curve25519 key exchange and ChaCha20-Poly1305 (6.5, 2014); FIDO security keys (8.2, 2020); SHA-1 ssh-rsa signatures off by default (8.8, 2021). The release notes confirm the later steps. OpenSSH 9.0 (April 2022) made hybrid sntrup761x25519 the default key exchange. OpenSSH 9.6 (December 2023) added "strict KEX" after the Terrapin attack. OpenSSH 10.0 (April 2025) made mlkem768x25519-sha256 the default and removed DSA. OpenSSH 10.1 (October 2025) began warning about key exchange that is not post-quantum safe. The newest release is 10.6 (October 2026).
how: RFC 4251 defines three protocols over TCP port 22: transport (RFC 4253) gives a secure packet pipe, user authentication (RFC 4252) proves who the user is, and the connection protocol (RFC 4254) splits the pipe into channels. TCP delivers bytes reliably and in order, and that is all SSH asks of it.
Step 1, hello. Both sides send a text line such as `SSH-2.0-OpenSSH_10.0`, then a KEXINIT message with ordered lists of supported algorithms: key exchange, host key type, cipher, MAC. In each category, the first client entry that the server also supports wins. This is why weak algorithms can be removed without changing the protocol. Everything so far is plain text, because there is no key yet.
Step 2, key exchange. With curve25519-sha256 the client makes a fresh X25519 key pair and sends the 32-byte public key (Q_C). The server sends its own (Q_S). Both compute the same 32-byte secret K by Diffie–Hellman: public-key cryptography lets them agree on K in the open without ever sending it. The temporary keys are deleted afterwards, so an attacker who records the traffic and steals a key later still cannot recover K. This is forward secrecy. The default since OpenSSH 10.0, mlkem768x25519-sha256, runs X25519 and ML-KEM-768 side by side: the client sends a 1,184-byte ML-KEM public key plus its X25519 key, the server returns a 1,088-byte ML-KEM ciphertext plus its X25519 key, and both hash the two secrets together. An attacker must break both. The size is the price of defence against "harvest now, decrypt later": recording traffic today to decrypt it when a quantum computer exists.
Step 3, the server proves itself. In the same reply the server sends its host public key (for example ssh-ed25519, 32 bytes) and a signature over H. H is a hash (hashfn) of both identification lines, both KEXINIT messages, the host key, Q_C, Q_S and K. Any byte changed earlier by a man in the middle changes H, and the signature fails. The client then looks the host up in known_hosts. If it is new, ssh asks the user (trust on first use). If the key differs from the stored one, ssh refuses with a loud warning. The fingerprint you compare is a hash too: `SHA256:` and 43 base64 characters.
Step 4, keys and encryption. Both sides send NEWKEYS. Six values are derived as HASH(K || H || letter || session_id) with the letters A to F: the IV, the encryption key and the integrity key for each direction. From now on every packet is protected by an AEAD cipher (aead): chacha20-poly1305@openssh.com or AES-GCM. A packet is a 4-byte length, a 1-byte padding length, the payload, 4 to 255 random padding bytes (the total must be a multiple of the block size, at least 8), and a 16-byte tag. A sequence number per direction is never sent but is covered by the tag, so replayed, dropped or reordered packets fail. In ChaCha20-Poly1305 the length field has its own key, so it cannot be read or changed. RFC 4253 recommends fresh keys after each gigabyte or each hour; either side simply starts a new key exchange inside the session.
Step 5, user authentication. The client requests the `ssh-userauth` service and sends USERAUTH_REQUEST messages. The first, method `none`, fails but returns the allowed methods. For `publickey`, the client offers a key without a signature; if authorized_keys lists it, the server answers PK_OK. The client then repeats the request with a signature over a message containing the session ID, user name and key. The session ID is unique to this connection, so the signature is useless elsewhere, and no password or private key crosses the network. The key can live in an ssh-agent or on a FIDO hardware key that needs a touch. Other methods are password, keyboard-interactive (for one-time codes) and Kerberos.
Step 6, channels. The client sends CHANNEL_OPEN of type `session` with a channel number, a window (OpenSSH uses 2 MiB) and a maximum packet size (32 KiB). The server confirms. Requests follow: `pty-req` (terminal type and size), then `shell`, `exec "command"` or `subsystem sftp`. Data flows in CHANNEL_DATA messages; the sender stops when the window is used up, and the receiver sends WINDOW_ADJUST as it drains data. A slow reader on one channel therefore cannot block another. Forwarding uses the same machinery: `-L` opens a `direct-tcpip` channel to a target the server can reach, `-R` sends a `tcpip-forward` request so the server listens and opens channels back, and `ProxyJump` runs a second SSH session inside a `direct-tcpip` channel to the next hop.

example: Run `ssh dev@build1` over a link with a 150 ms round-trip time (RTT), for example Bengaluru to Europe. The round-trip counts are typical, not exact; `ssh -vvv` shows your client's real sequence.
Round trips: TCP connect 1; key exchange 1; service request plus the `none` probe about 2; public-key offer 1; signed request 1; channel open and shell about 1. That is roughly 7 RTT, so 7 × 150 ms ≈ 1 second before the prompt. Cryptography is small by comparison: X25519 and Ed25519 operations take about 50 microseconds each. On a LAN with 0.5 ms RTT the same login takes tens of milliseconds. With `ControlMaster`, the next ssh to that host reuses the open connection and needs only the channel step, about 1 RTT.
Bytes for one keystroke: CHANNEL_DATA has 1 byte of type, 4 of channel number, 4 of string length and 1 of data, so 10 bytes of payload. Add the 4-byte length and 1-byte padding field: 15. Padding must be at least 4 bytes and make the total a multiple of 8, so it is 9 bytes: 24. Add the 16-byte tag: 40 bytes. With TCP and IPv4 headers (assuming 12 bytes of TCP options) that is about 92 bytes on the wire for one letter.
Window limit: copy a 1 GB file with scp over the same link. A 2 MiB window means at most 2 MiB can be outstanding at the SSH level, so throughput is at most \( \text{window} \div \text{RTT} \) = 2,097,152 B ÷ 0.15 s ≈ 14 MB/s ≈ 112 Mbit/s, even if the link carries 1 Gbit/s. The file takes at least about 72 seconds. At 20 ms RTT the ceiling is about 840 Mbit/s, and on a LAN the cipher speed becomes the limit. This is the same cap a TCP receive window puts on TCP, one level higher; the two limits stack.
intuition: A locked courier case that two strangers build in public: they agree on the combination in front of everyone without saying it, the courier shows a signed seal that proves who sent it, and every item inside has a tamper stamp.
The design is natural once you separate three questions. How do we get a shared secret on a hostile network? Diffie–Hellman. Who is at the other end? Signatures, once for the machine and once for the user. How do we use the secret safely, packet after packet? Authenticated encryption with sequence numbers. Each question has its own layer, so each can be upgraded alone, which is how OpenSSH changed its key exchange twice (2022, 2025) while old scripts kept working. Channels follow the same logic: the handshake is costly, so pay once and reuse it for many streams, with a window per stream so a busy one cannot starve the others.
mistakes: People often think SSH encrypts traffic with the public and private key pair. In fact the key pairs authenticate and, in the key exchange, help agree on a secret. The data is encrypted with a fast symmetric cipher under keys derived from that secret. Public-key operations take tens of microseconds, too slow for every packet.
People often think the first-connection fingerprint prompt is a formality. In fact it is the only defence against a man in the middle on the first connection, because SSH has no certificate authority by default. If you press "yes" without comparing the fingerprint with a trusted source, an attacker in the path can answer in the server's place.
People often think agent forwarding (`ssh -A`) is just a convenience. In fact anyone with root on the remote host can ask your agent to sign logins while the connection is open. They never see the private key, but they can become you on any server that trusts it. Use `ProxyJump` for hops.
People often think a changed-host-key warning should be silenced with `StrictHostKeyChecking no`. In fact it means either the server was legitimately rebuilt or someone is impersonating it, and turning the check off removes the only protection against the second case. Verify the new fingerprint another way, then run `ssh-keygen -R host`.
friction: Trust is the weakest part. Trust on first use leaves a gap that people close by clicking "yes". At scale, known_hosts files go stale, because every rebuilt cloud instance has a new host key, and the usual answers are bad (turn the check off) or heavy (run a host CA). Plain SSH keys have no expiry and no owner field: a key copied into 200 authorized_keys files years ago still works, and removing a leaver means finding every copy.
The protocol and its main implementation have had real flaws. Terrapin (2023): sequence numbers kept counting through the handshake, so an active attacker could insert messages before NEWKEYS and delete the same number right after it, unnoticed. Strict KEX resets the counter, but only works if both sides support it. regreSSHion (CVE-2024-6387, July 2024) was a signal-handler race in sshd 8.5p1 to 9.7p1 that could give remote root on 32-bit glibc Linux. The 2024 xz backdoor tried to reach sshd through a library loaded by systemd. An internet-facing sshd is a high-value target, which is why it splits into a root monitor and an unprivileged process that parses network data.
Performance has limits. The fixed 2 MiB channel window starves long, fast links, as the example showed. One connection's cipher runs on one core, roughly 1 GB/s with AES-GCM. Every interactive keystroke costs a round trip, and nothing can beat the speed of light. Keystroke timing also leaks information, which is why OpenSSH 9.5 added fake packets at fixed intervals (ObscureKeystrokeTiming). Finally, host and user signatures (RSA, Ed25519) are not post-quantum. They matter only at connection time, so there is no "record now, forge later" attack, but they will need replacing; OpenSSH 10.4 and 10.6 added experimental hybrid ML-DSA signatures.
tradeoffs: Choose trust on first use with known_hosts for a handful of long-lived servers. Choose host certificates (a CA signs each host key; clients trust it with `@cert-authority`) for dozens of hosts or machines rebuilt often. You give up "no infrastructure" and must protect the CA key.
Choose static keys in authorized_keys for a small team, where you can list who has access by hand. Choose short-lived user certificates (valid for hours, issued after single sign-on) beyond roughly 20 people or 50 hosts, or when you need expiry and audit. The price is a signing service that must be available. A further step is a cloud session service with no open port 22: central logs, but tied to one provider.
Choose ChaCha20-Poly1305 on devices without AES instructions (old phones, small ARM boards); choose AES-GCM on servers with AES-NI, at about 1 GB/s or more per core. OpenSSH defaults already pick well.
Choose `ProxyJump` through a bastion over agent forwarding, because the bastion only relays encrypted bytes. Choose a VPN or zero-trust proxy when many non-SSH services need private access, at the cost of more moving parts.
On slow or lossy links, choose mosh (UDP with local echo prediction) for interactive work; keep plain SSH for compatibility and port forwarding.
practice: Use Ed25519 keys with a passphrase in an agent, or a FIDO key (`-t ed25519-sk`) for sensitive access. Keep clients current so the post-quantum exchange is used, and notice the warning that OpenSSH 10.1 and later print when a server cannot do it.
On servers set `PasswordAuthentication no`, `PermitRootLogin no`, and `AllowUsers` or `AllowGroups`. Use `command=` and `restrict` in authorized_keys for automation keys, so a leaked deploy key can run only one command.
In ~/.ssh/config use `IdentitiesOnly yes` (otherwise ssh offers every key to every server, which can hit the attempt limit and leak your key list), `ProxyJump bastion`, `ControlMaster auto` with `ControlPath ~/.ssh/cm-%C` and `ControlPersist 10m`, and `ServerAliveInterval 30` so NAT devices do not drop idle sessions. When login fails, read `ssh -vvv` from the top: which algorithms were agreed, which keys were offered, which methods the server allowed. Most problems are file permissions, wrong user names or a mismatched key.
For fleets, issue certificates with `ssh-keygen -s ca_key -I id -n principals -V +8h user_key.pub` and set `TrustedUserCAKeys` on servers.
interview: A teammate says "SSH is secure because it encrypts with the server's public key." What is wrong? || Traffic is encrypted with symmetric keys derived from a Diffie–Hellman (or ML-KEM hybrid) exchange. The host key only signs the exchange hash, to prove identity. A stolen host key later cannot decrypt recorded sessions, because the temporary keys are gone (forward secrecy).
How could a man in the middle attack a first connection, and what stops him later? || On first contact he can present his own host key, and only the fingerprint check or a host certificate catches him. Afterwards known_hosts holds the real key, so his key differs and ssh refuses. Mitigations: host certificates, SSHFP records with DNSSEC, or distributing known_hosts by configuration management.
A 2 GB scp across an RTT of 180 ms reaches only about 90 Mbit/s on a 1 Gbit/s link. Why, and what do you do? || The 2 MiB channel window allows about 2 MiB per round trip: 2 MiB ÷ 0.18 s ≈ 93 Mbit/s. Options: parallel streams (parallel rsync), patched SSH with larger windows (HPN-SSH), or a wide-area transfer tool. Stock OpenSSH has no simple setting for a larger window.
A contractor with keys on 300 servers leaves. What do you do, and what would you change? || Find and remove the key everywhere, using configuration management and a search by key fingerprint. The root problem is that keys never expire. Move to short-lived user certificates with a CA trusted by servers, so access ends by itself within hours.
Why does the server sign a hash of the version lines and algorithm lists too? || To stop downgrades. If a man in the middle edits the client's algorithm list to force a weak cipher, the two sides compute different hashes and the server's signature fails. Terrapin showed that message counting needs the same care, which strict KEX adds.
quiz: What exactly does the server sign during the SSH handshake, and why? || It signs the exchange hash H, a hash of both version lines, both KEXINIT messages, its host key, both temporary public keys and the shared secret. This proves it holds the host private key and took part in this very exchange.
Why does a stolen host key not decrypt SSH sessions recorded last month? || Session keys come from a Diffie–Hellman exchange with temporary key pairs deleted after the handshake. The host key only signs; it neither encrypts nor derives keys.
Why does the user's signature in public-key authentication include the session ID? || The session ID is unique to the connection, so the signature is valid only here and a recording cannot be replayed elsewhere.
With a 2 MiB channel window and a 100 ms RTT, what is the maximum throughput of one channel? || \( \text{Window} \div \text{RTT} \) = 2,097,152 B ÷ 0.1 s ≈ 21 MB/s, about 168 Mbit/s, however fast the link is.
When would you choose SSH certificates over authorized_keys and known_hosts files? || With many hosts or users, frequently rebuilt machines, or a need for expiry and audit. Servers and clients then trust one CA instead of many keys, at the cost of running and protecting that CA.

@@ dhcp
value: DHCP (Dynamic Host Configuration Protocol) gives a device everything it needs to use an IP network, without a person typing anything: an IP address, the subnet mask, the default gateway, the DNS servers, often a time server, a search domain and extra routes. It solves a chicken-and-egg problem. To talk to a server a device needs an address, but to learn its address it must talk to a server. And it solves a scale problem: configuring thousands of laptops, phones and virtual machines by hand is impossible, and giving each a fixed address wastes space when most are away.
The answer is a loan. The server gives out an address as a lease with an expiry time, and the device must renew it. Three lower concepts make this work. Ethernet (ethernet) provides broadcast frames, sent to the address ff:ff:ff:ff:ff:ff, which every device on the local link receives, and the client's MAC address, which is its only identity before it has an IP address. IP and routing (iprouting) define the special addresses 0.0.0.0 ("this host, unknown") and 255.255.255.255 ("everyone on this link"), and they define what DHCP delivers: an address, a mask that says which destinations are on-link, and a default route. UDP (the UDP part of the quic concept) is the carrier: a connectionless datagram needs no handshake and no source address worth checking, so a device with no configuration can use it. TCP could not do this.
The layer above, cloud networks, home routers, office Wi-Fi and network boot, all depend on it. Every laptop that joins a network, and in most clouds every virtual machine, learns its basic network settings from DHCP.
terms: Lease — the right to use an address until an expiry time; the client must renew it before then.
DORA — the four messages Discover, Offer, Request, Acknowledge that give a new client an address.
Option — a code-length-value field in a DHCP message that carries one setting, such as option 3 (router) or option 6 (DNS servers).
Scope (pool) — the range of addresses a server may give out for one subnet, with the options that go with it.
Reservation — a rule that always gives the same address to a given client (matched by MAC or client ID).
Relay agent — a router or switch that forwards a client's broadcast to a server on another subnet and stamps it with the client's subnet (giaddr).
Transaction ID (xid) — a random 32-bit number the client puts in each request, so replies can be matched to it.
T1 and T2 — the renewal timers: T1 (default half the lease) starts renewal with the same server; T2 (default 87.5%) starts a search for any server.
DHCP snooping — a switch feature that drops server messages arriving on ports not marked trusted, blocking rogue servers.
history: Early diskless workstations needed to learn their address at boot. RARP (RFC 903, 1984) asked "what is my IP address?" using only the MAC address, but it could not carry a mask, a gateway or anything else, and it needed a server on every link. BOOTP (RFC 951, 1985, by Croft and Gilmore) fixed this: it used UDP broadcast, added a relay mechanism so one server could serve many subnets, and sent a bootfile name so a machine could load its operating system. But BOOTP addresses were assigned by hand in a table, one per machine, forever.
In the early 1990s, laptops and large campus networks made that table impossible to keep. Ralph Droms wrote DHCP as an extension of BOOTP (RFC 1531, October 1993; revised as RFC 2131 and the option list RFC 2132 in March 1997). It kept the BOOTP message format, so existing relays kept working, and added leases, automatic address pools and a flexible options field. RFC 2131 is still the base document today, extended by many later RFCs. The main ones are: the relay agent information option, option 82 (RFC 3046, 2001), classless static routes, option 121 (RFC 3442, 2002), address conflict detection by ARP probes (RFC 5227, 2008), a captive-portal URL, option 114 (RFC 8910, 2020), and "IPv6-only preferred", option 108 (RFC 8925, 2020). DHCPv6 (RFC 3315, 2003; now RFC 8415) is a separate protocol with a different message format.
The best-known server for 25 years was ISC DHCP (dhcpd). ISC ended its maintenance at the end of 2022, and its successor Kea (with a database backend, an API and hot-standby high availability) reached version 3.0, its first long-term-support release, in June 2025.
how: DHCP messages travel over UDP: servers listen on port 67 and clients use port 68. A message has a fixed 236-byte header inherited from BOOTP (operation, hardware type, hops, transaction ID xid, seconds, flags, four address fields ciaddr/yiaddr/siaddr/giaddr, the client's hardware address chaddr, and two legacy fields), then the magic cookie 99.130.83.99 and a list of options. Options come as code, length, value; the message type is option 53. Messages are often padded to 300 bytes, the BOOTP packet size.
Step 1, DISCOVER. The client has no address, so it sends from 0.0.0.0 port 68 to 255.255.255.255 port 67, in an Ethernet frame to ff:ff:ff:ff:ff:ff. It sets a random xid, puts its MAC in chaddr, and adds options: its client identifier, a parameter request list (option 55: "I would like mask, router, DNS, domain, ...") and, if it remembers an old address, a requested IP (option 50). The switch floods the frame to every port in the VLAN. Every DHCP server on the link may answer.
Step 2, OFFER. A server picks an address. It prefers the client's existing binding, then a reservation, then the address the client asked for, then a free address from the pool. Good servers check that it is unused (an ICMP ping, or the client's later ARP probe) and mark it as held for a short time. The OFFER carries the address in yiaddr, the server identifier (option 54), the lease time (option 51) and the requested options. If the client's broadcast flag is clear, the server sends the reply as a unicast to the client's MAC, even though the client has no IP address yet; the server writes the frame directly instead of using ARP.
Step 3, REQUEST. The client may get several offers. It picks one (usually the first) and broadcasts a REQUEST that names the chosen server (option 54) and address (option 50). It is a broadcast so the other servers also hear it and release their held offers.
Step 4, ACK. The chosen server writes the binding (client, address, expiry) to its lease database, and only then sends DHCPACK with the final parameters. If something changed, it sends DHCPNAK and the client restarts. Before using the address, a careful client sends an ARP probe, "who has 192.168.1.23?" (RFC 5227). If someone answers, it sends DHCPDECLINE and starts again, and the server marks that address as bad.
Step 5, the lease lifecycle. The client configures its interface, installs the default route and writes the DNS servers. At T1, 50% of the lease, it unicasts a REQUEST to the same server (RENEWING). A new ACK restarts the clock. If the server does not answer, the client retries, halving the remaining time until T2 but not faster than every 60 seconds. At T2, 87.5%, it broadcasts the REQUEST to any server (REBINDING). If the lease ends with no answer, it must stop using the address and return to DISCOVER. Clients may send DHCPRELEASE when they leave, but phones and laptops usually do not, because they simply disappear. After a reboot, or when rejoining a known network, a client can skip DISCOVER and send a REQUEST for its old address (INIT-REBOOT): one round trip, and the server answers ACK, or NAK if the client has moved to another subnet.
Step 6, relays. A router does not forward 255.255.255.255 or Ethernet broadcasts, so a client in a subnet without a server would never be heard. The router interface (or switch) is configured as a relay agent. It hears the broadcast, writes its own interface address in giaddr, optionally adds option 82 (which switch and port the client is on), and unicasts the message to a configured server. The server matches giaddr against its subnet definitions to pick the right pool (the iprouting idea of "which subnet is this address in"), answers to giaddr port 67, and the relay delivers the reply to the client. One server can run hundreds of VLANs.

example: A coffee shop runs one /24 for guest Wi-Fi: 254 addresses, minus the gateway (192.168.1.1), leaves 253 for clients. On average 100 new devices join each hour and each stays about 30 minutes. Phones do not send DHCPRELEASE, so each address stays bound until its lease expires. By Little's law, the number of bound addresses is the arrival rate times the lease time.
With a lease of 8 hours: 100 per hour × 8 hours = 800 addresses wanted, but the pool has 253. It runs out after about 253 ÷ 100 ≈ 2.5 hours, and new customers get no address. With a 1-hour lease: 100 in use, about 40% of the pool. With a 30-minute lease: about 50 in use. So for transient guests the lease should be a little longer than a typical stay, and an 8-hour or 24-hour lease is right only for stable offices.
Shorter leases cost control traffic. Take an office with 10,000 clients. A 24-hour lease means each renews every 12 hours (T1): 10,000 ÷ 43,200 s ≈ 0.23 requests per second. A 1-hour lease: 10,000 ÷ 1,800 s ≈ 5.6 per second. A 1-minute lease: 10,000 ÷ 30 s ≈ 333 per second, and every one of them writes to the lease database. The first two are trivial; the last needs a serious server.
Last, a trace of a laptop with a 24-hour lease (86,400 s). The lease starts at time 0. At 12 h (T1) the laptop unicasts a REQUEST to the server, which ACKs. If the server is down, the laptop keeps using the address and retries; at 21 h (T2) it broadcasts to any server; the address stays valid until hour 24. A server outage of several hours therefore does not break existing clients, which is one reason to avoid very short leases. Only new devices suffer.
intuition: A hotel front desk that lends room keys which stop working at a set time unless the guest comes back to the desk to renew them.
The idea is natural because it handles the hard part, forgetting. A server cannot know when a phone has left the building. If addresses were permanent, the pool would fill with ghosts. With a lease, the server needs no goodbye: silence means the address returns to the pool when the timer ends. This is soft state, the same idea as a TTL in DNS or a heartbeat. The broadcast is natural too: a device that knows nothing can still shout "is anyone a DHCP server?" to its own wire, and a server answers the same way.
mistakes: People often think DHCP only hands out IP addresses. In fact the address is one of many options. A typical ACK also gives the mask, router, DNS servers, search domains, time servers, extra routes (option 121), a captive-portal URL, and, for network boot, a boot server and file name.
People often think a lease that expires drops your connections at once. In fact a healthy client renews at 50% of the lease and keeps the address, and the server can be down for hours without any effect on clients that are already bound. Only a client that cannot reach any server by the end of the lease loses its address.
People often think a server in the cloud with a "static" private IP does not use DHCP. In fact in most clouds the platform's network control plane decides the address, and the instance still learns it through DHCP (for example in AWS VPCs, where DHCP option sets also supply DNS and domain names). DHCP delivers the decision; it does not make it.
People often think DHCP is secure because it is "internal". In fact there is no authentication in practice. Any host can answer a DISCOVER, and the client usually takes the first offer. A rogue server can send a gateway and DNS server of its own and sit in the middle of all traffic.
friction: DHCP trusts the local wire. A rogue server wins by being fast. A starvation attack sends DISCOVERs with thousands of forged MAC addresses until the pool is empty. The TunnelVision technique (CVE-2024-3661, published May 2024) uses option 121 from a rogue server to add routes that steer traffic around a VPN tunnel, because many VPN clients rely on the routing table. Defences exist but are on the switch: DHCP snooping, port security and rate limits. There is no cryptographic fix in common use.
Operations give more pain. Pools run out without warning, as in the example. Static addresses configured by hand that sit inside the pool cause duplicate addresses. Modern phones use a random MAC address per network, and some rotate it, so "the same device" is no longer recognisable by MAC and leases pile up. High availability is hard because two servers must not give the same address: either the pool is split between them (simple, fragile) or they share lease state (Kea hot-standby, load-balancing). Each ACK needs a durable write, so the lease database can become the bottleneck at very short leases. DHCP clients may also lie about their host name, so DNS entries built from it can be spoofed. Finally, IPv6 changes the picture: most hosts build addresses themselves (SLAAC), and DHCPv6 is used for extra options or where tracking is needed. Android has historically relied on SLAAC alone.
tradeoffs: Choose a short lease (30 to 60 minutes) for guest and mobile networks where devices come and go, since it protects a small pool. Choose a long lease (8 to 24 hours, or days) for stable office or data center networks, since it cuts server load and survives server outages. The price of short leases is renewal load and a stronger dependence on the server; the price of long ones is stale bindings and a slow clean-up.
Choose reservations (the server always gives a fixed address to a MAC) for printers, cameras and servers over static configuration on the device. The address is still set centrally and can be changed in one place. You give up the independence of a device that boots without any server, so keep infrastructure like the DHCP server and routers on true static addresses.
Choose a central DHCP server with relays when you have many subnets: one set of pools, logs and policy. Choose the router's built-in DHCP server for a small site or branch, which needs nothing else and survives a WAN failure. For high availability choose a shared-state pair (Kea hot-standby or load-balancing) over splitting the pool 50/50 when the pool is small, since each half would run out alone.
Choose DHCP snooping with trusted ports when you control the switches; it blocks rogue servers cheaply and builds a binding table that also feeds ARP inspection. Choose 802.1X port authentication when you must also control who can connect at all. Neither replaces the other.
practice: Plan pools using arrival rate × lease time, as in the example, and add 20 to 30% headroom. Alert when a pool reaches 80% in use. Keep fixed-address devices outside the pool or as reservations, and never run two uncoordinated servers on one VLAN.
To debug, look at the wire: `tcpdump -i eth0 -n -vv 'port 67 or port 68'` shows the four messages with their options, and an OFFER that never comes means the server, relay or VLAN is wrong. Check the client's lease file or logs (`journalctl -u NetworkManager`, `dhclient -v`, `ipconfig /all` on Windows). An address like 169.254.x.x on a client means no server answered; the client chose a link-local address itself. Several OFFERs from different servers mean a rogue or duplicate server.
Set the options that matter: DNS servers, search domain, NTP, and only as many routes as needed. Enable DHCP snooping on access switches with trusted uplinks. Configure relays on every routed interface with more than one DHCP server for resilience, and turn on option 82 logging so you can tell which port a client used. For Kea or similar, use a database backend and keep the lease writes on fast storage.
In clouds, treat DHCP options as part of the network definition (the VPC's DHCP option set) and test that new instances get the right DNS and domain. For laptops and phones, remember that per-network random MACs mean a reservation by MAC needs the device's per-network address.

value: Wi-Fi (the IEEE 802.11 family) lets phones, laptops and TVs join a local network over radio and use it as if it were Ethernet. The problem is that radio is a hard medium. Everyone in range shares one channel, so only one device can usefully talk at a time. A transmitter is about 100 dB (ten billion times) louder than the faint signal it hopes to receive, so a radio cannot listen while it sends, and cannot detect a collision the way an Ethernet card can. Signals fade with distance, walls and reflections. And anyone within range can listen, so confidentiality must be built in. Wi-Fi gives the layer above a plain Ethernet-like frame service (a source and destination MAC address and a payload) and hides all of this.
The layers below do the work. Ethernet (ethernet) supplies the idea of MAC addresses, frames and listen-before-talk sharing, and an access point bridges Wi-Fi frames onto a wired Ethernet. Electromagnetism (maxwell) explains the medium: wavelength, antennas, how power falls with distance and through walls. Thermal noise (noise) and coding theory (codingtheory) decide how many bits each symbol can carry and how errors are corrected. Fourier analysis (fourier) gives OFDM, which sends data on many parallel narrow frequencies using an inverse FFT. Randomized algorithms (randalgo) give the random backoff that lets stations share a channel without a coordinator. Authenticated encryption (aead) protects every frame.
Video streams (mediastream) usually end on a Wi-Fi link in the home, so Wi-Fi's airtime sharing and retries shape what viewers see.
terms: BSS and SSID — a BSS (basic service set) is one access point and its associated devices, identified by the AP's MAC address (BSSID); the SSID is the human-readable network name, which many APs can share.
Station (STA) and AP — a station is any device that joins; the access point connects stations to the wired network.
CSMA/CA — carrier-sense multiple access with collision avoidance: listen first, wait a random time, then send, and expect an acknowledgement.
Contention window (CW) — the range from which a station draws its random backoff count; it starts at 0 to 15 and doubles after each failure, up to 1023.
SIFS and DIFS — the short gap (16 µs at 5 GHz) before an ACK, and the longer gap (34 µs) a new transmission must wait, so acknowledgements always win.
NAV — network allocation vector: a timer, set from the Duration field of frames a station overhears, that tells it the channel is reserved even if it hears nothing now.
OFDM — orthogonal frequency-division multiplexing: the channel is split into many narrow subcarriers, each carrying its own symbols at the same time.
MCS — modulation and coding scheme: the index (0 to 11 or 13) that fixes bits per symbol and the error-correcting code rate for a transmission.
Airtime — the time a transmission occupies the shared channel; the real scarce resource in Wi-Fi.
history: Random-access radio began with ALOHAnet in Hawaii (Norman Abramson, 1971), where stations simply sent and retried after a random delay. Ethernet (1973 to 1976) improved it with carrier sensing and collision detection. In 1985 the US regulator, the FCC, opened the ISM bands (unlicensed, for industrial, scientific and medical use) to spread-spectrum devices, which made cheap wireless LANs legal. The IEEE 802.11 working group, chaired by Vic Hayes, started in 1990.
The first standard, 802.11-1997, gave 1 and 2 Mbit/s. 802.11b (1999) reached 11 Mbit/s at 2.4 GHz and made Wi-Fi a mass product; the Wi-Fi Alliance was founded in 1999 to certify interoperability. 802.11a (5 GHz) and 802.11g (2003) brought OFDM and 54 Mbit/s. 802.11n (2009) added several antennas (MIMO), 40 MHz channels and frame aggregation, for up to 600 Mbit/s. 802.11ac (2013, "Wi-Fi 5") added 160 MHz and 256-QAM at 5 GHz. 802.11ax ("Wi-Fi 6", 2021) added OFDMA, 1024-QAM and scheduling for dense networks; Wi-Fi 6E took it to the 6 GHz band, opened in the US in 2020.
IEEE published 802.11be, "Wi-Fi 7", on 22 July 2025, after the Alliance began certifying devices in January 2024. It adds 320 MHz channels, 4096-QAM and multi-link operation (using several bands at once). Wi-Fi 8 (802.11bn) is in development, aimed at reliability and latency rather than peak speed, with approval expected around 2028.
Security had a rocky start. WEP (1997) was broken in 2001. WPA (2003) and WPA2 (2004, with AES) fixed it, but WPA2-Personal allowed offline password guessing, and the KRACK attack (2017, Vanhoef and Piessens) showed that the four-way handshake could be tricked into reusing a key. WPA3 (2018) added SAE and protected management frames; the "Dragonblood" flaws (2019) were found in early implementations.
how: A station finds a network from beacon frames that an AP broadcasts about every 102.4 ms (100 time units of 1,024 µs), or by sending probe requests. It then authenticates (an empty legacy step) and associates, receiving an association ID. Then a four-way handshake creates encryption keys (below). After that, the AP bridges the station's frames to the wired network. Nothing in this setup depends on IP, which is why IP and DHCP come after it.
Sharing the channel: the distributed coordination function (DCF). Before sending, a station must sense that the channel is idle. It listens physically (energy or a recognised preamble) and virtually (the NAV, set from the Duration field of overheard frames). When the channel has been idle for DIFS (34 µs at 5 GHz), it draws a random number from 0 to CW (initially 15) and counts down in 9 µs slots, but only while the channel stays idle. If someone else starts, the countdown freezes and resumes later, so a station that waited longer gets an earlier turn. At zero it sends. Because a radio cannot hear a collision, the receiver sends a 14-byte ACK after SIFS (16 µs, shorter than DIFS, so no one can interrupt it). No ACK means a collision or loss: the station doubles CW (15, 31, 63 ... 1023), draws again and retries, up to about 7 times. Random draws are the randalgo idea: two stations that collide choose again independently and are unlikely to collide twice, with no one in charge.
Hidden terminals are the weak point. Two stations on opposite sides of an AP may not hear each other, so both see an idle channel and collide at the AP. The optional fix is RTS/CTS: the sender asks (RTS), the AP answers (CTS), and everyone who hears the CTS sets its NAV. It costs airtime, so it is used only for large frames. For quality of service, EDCA (the WMM feature) gives voice and video shorter waits and smaller windows than best-effort and background traffic.
Sending bits: OFDM. A 20 MHz channel is split into subcarriers 312.5 kHz apart (78.125 kHz in Wi-Fi 6). Each carries one QAM symbol: BPSK is 1 bit, 64-QAM 6 bits, 1024-QAM 10 bits, 4096-QAM 12 bits. The sender builds the time signal with an inverse FFT and the receiver recovers the symbols with an FFT (fourier). Each symbol lasts long (12.8 µs in Wi-Fi 6) and a 0.8 µs guard interval absorbs reflections, so echoes from walls do little harm. Error-correcting codes (codingtheory), LDPC in modern Wi-Fi at rates 1/2 to 5/6, repair bit errors. The rate follows from arithmetic: data subcarriers × bits per symbol × code rate ÷ symbol time. Several antennas send parallel spatial streams, which multiply the rate.
How fast depends on signal-to-noise ratio (noise). The noise floor of a 20 MHz channel is about −174 dBm/Hz + 73 dB = −101 dBm, and receiver electronics add 5 to 10 dB. Dense modulation needs a clean signal: 1024-QAM needs roughly 35 dB or more, BPSK only a few dB. The sender adapts: it tracks successes and failures, and steps the MCS up or down. Path loss (maxwell) makes SNR drop with distance: free-space loss at 10 m is about 60 dB at 2.4 GHz and 66 dB at 5 GHz, and each wall costs several dB more.
Efficiency: every transmission pays a fixed overhead for waiting, the preamble and the ACK, roughly 100 to 200 µs. At 1,200 Mbit/s a 1,500-byte packet takes only 10 µs on the air, so the overhead would dominate. Aggregation (A-MPDU, from 802.11n) packs up to dozens of frames into one transmission with one block ACK. Wi-Fi 6 OFDMA also splits the channel into resource units so that one transmission serves several clients, which helps many small packets.
Security. WPA2-Personal turns the passphrase and the SSID into a 256-bit master key (PBKDF2, 4,096 rounds of HMAC-SHA1). The four-way handshake mixes that key with fresh random numbers from both sides into a per-session key, so each session has different keys. Data frames are encrypted and authenticated with AES in CCM mode (CCMP) or, in WPA3, GCMP-256 (aead), with a packet number against replay. WPA3-Personal replaces the passphrase step with SAE, a password-authenticated key exchange: an eavesdropper cannot test guesses offline, and recorded traffic stays safe even if the password leaks later. Protected management frames stop forged disconnect messages.

example: Two calculations show why Wi-Fi speeds disappoint and why one slow device hurts everyone.
First, collisions. Suppose n stations all draw a fresh backoff from 0 to 15 and the lowest number wins. A collision happens when the lowest value is drawn by two or more stations. This is a simplified worst case, but the numbers are informative: n = 2 gives about 6% chance of a collision, n = 5 about 15%, n = 10 about 28%, n = 20 about 50% and n = 30 about 67%. After a collision CW doubles to 31, which halves the odds but wastes time. A crowded channel of 30 active devices loses a large share of its airtime this way.
Second, the performance anomaly. Take 1,500-byte frames (12,000 bits) and a fixed overhead of about 160 µs per frame for DIFS, average backoff, preamble, SIFS and ACK. A single laptop at 54 Mbit/s needs 222 µs of data time plus 160 µs: 382 µs per frame, which is 12,000 ÷ 382 µs ≈ 31 Mbit/s. Now a second device far away connects at 6 Mbit/s. Its frame needs 2,000 µs of data time. DCF gives each station the same chance to send per turn, not the same airtime. In one round each sends one frame: 222 + 2,000 + 2 × 160 = 2,542 µs. Each station now gets 12,000 bits per 2,542 µs ≈ 4.7 Mbit/s. The fast laptop fell from 31 to 4.7 Mbit/s, a drop of 85%, and the slow device uses 85% of the airtime. Fixes are airtime-fair scheduling in the AP, switching off the lowest rates, and moving the far device to a closer AP.
Third, the rate formula. Wi-Fi 6, 80 MHz channel, 1 stream, MCS 11: 980 data subcarriers × 10 bits (1024-QAM) × 5/6 code rate = 8,167 bits per symbol; the symbol lasts 12.8 + 0.8 = 13.6 µs; so 8,167 ÷ 13.6 µs ≈ 600 Mbit/s. Two streams give about 1,200 Mbit/s. Wi-Fi 7 at 320 MHz with 4096-QAM: 3,920 × 12 × 5/6 ÷ 13.6 µs ≈ 2,882 Mbit/s per stream, but only at very high SNR, so mostly close to the AP.
intuition: A meeting with no chairperson where everyone waits for a pause, then waits a random extra moment, so two people rarely start at the same time.
The design is natural because the medium forces it. No one can be in charge cheaply, since a central scheduler would need every device to hear it and to follow it. Listening first, and drawing a random wait when the channel is free, is the least a distributed group can do. Random numbers break the tie between equal parties without any messages. The acknowledgement replaces the missing collision detector: silence means something went wrong. The rest is physics and coding: pick as many bits per symbol as the noise allows, split the channel so echoes matter less, and add redundancy so the receiver can repair errors.
mistakes: People often think the headline rate ("AX3000", "1.2 Gbit/s") is the speed they will get. In fact it is the physical rate of the best modulation, summed over bands or streams. Real throughput is roughly 50 to 70% of one link's physical rate at best, because of waiting, ACKs and headers, and the channel is shared and half-duplex: when one device sends, all others wait.
People often think a hidden network name or a MAC address filter secures the network. In fact the SSID appears in client probe requests and association frames, and MAC addresses are visible in every frame, so both can be learned and copied. Real protection is WPA3 (or WPA2 with a long random passphrase).
People often think everyone sharing a WPA2 password cannot read each other's traffic because the frames are encrypted. In fact in WPA2-Personal every key derives from the shared passphrase plus public nonces. Someone who knows the passphrase and records your handshake can compute your session keys. WPA3-SAE and OWE give each client keys that knowledge of the password cannot reveal.
People often think wider channels always mean faster Wi-Fi. In fact each doubling of width doubles the noise power (3 dB less SNR), uses up scarce channels, and makes interference from neighbours more likely. In dense apartment buildings 80 MHz or even 40 MHz often beats 160 MHz.
friction: Airtime is shared and half-duplex, so latency has a long tail. A frame may wait for others, collide, or be retried up to seven times, which is why Wi-Fi shows jitter that wired links do not. A device must also defer to any transmission it can detect, even from a neighbour's network, so a distant AP on the same channel steals airtime without ever appearing in your settings. Microwave ovens and Bluetooth add noise at 2.4 GHz, which has only three non-overlapping 20 MHz channels (1, 6 and 11 in most countries).
Old devices slow everyone: beacons and multicast go out at the lowest basic rate, and one 802.11b device forces protection mechanisms on the whole cell. Clients decide when to roam, and "sticky" clients hold on to a distant AP at a low rate instead of moving to a near one. Power saving trades latency for battery: a sleeping device wakes at beacons and hears about waiting frames. Parts of the 5 GHz band are shared with radar, so an AP must leave a channel when it detects radar (DFS). The 6 GHz band is rules-dependent: the US opened 1,200 MHz, while the EU opened only the lower 480 MHz.
Security still has gaps: "transition mode" keeps the weaker WPA2 handshake available, open guest networks give no protection unless OWE is used, and short WPA2 passphrases can be cracked offline from a captured handshake.
tradeoffs: Choose 2.4 GHz for range and wall penetration (about 6 dB less loss than 5 GHz) and for simple IoT devices. Accept three clear channels, crowding and 20 or 40 MHz widths. Choose 5 GHz for most clients and streaming, and 6 GHz where clients support it and you want clean spectrum and 160 or 320 MHz channels; 6 GHz has the shortest range.
Choose 20 or 40 MHz channels in dense deployments (offices, apartments, stadiums) where reusing channels matters more than peak speed. Choose 80 or 160 MHz at home with few neighbours, accepting 3 dB of SNR per doubling.
Choose many low-power access points over a few strong ones in dense places. Each cell then serves fewer clients and has stronger signals and higher rates, at the cost of cabling and planning. A strong AP is heard far away, but weak phones cannot answer it, so the link is lopsided.
Choose wired backhaul for mesh nodes and access points: a wireless backhaul on the same radio roughly halves throughput at each hop, because the same airtime is used twice. Use Ethernet for fixed devices and Wi-Fi for mobility.
Choose WPA3-Personal for homes and small offices; choose WPA2/3 Enterprise (802.1X with per-user credentials or certificates) for organisations beyond a few dozen users, at the cost of a RADIUS server and certificate management.
practice: Measure before changing anything. Signal (RSSI) of −67 dBm or better is the usual target for video, and an SNR above 25 dB for high rates. On Linux `iw dev wlan0 link` shows signal and rate; a Wi-Fi analyser shows channel use; Wireshark in monitor mode shows retries (the retry bit) and the rates in use. A retry rate above about 10 to 15% means interference or weak signal.
Place APs high and central, away from metal and water, and wire them. Use non-overlapping channels, fixed 20 or 40 MHz widths in dense areas, and let power be low enough that neighbouring APs on the same channel do not overlap too much. Disable the lowest data rates (1, 2 and 5.5 Mbit/s on 2.4 GHz) so that beacons and old devices do not waste airtime. Use one SSID across APs and enable 802.11k, v and r so that clients roam sensibly.
Use WPA3-Personal, or WPA2/WPA3 transition mode only while old devices need it. Use a random passphrase of 16 or more characters, protected management frames, and a separate isolated guest network. For streaming boxes and smart TVs, prefer 5 GHz or Ethernet; adaptive players cope with low throughput by lowering quality, but not with jitter.

Users in the corner of a building stay connected to a faraway AP and have poor video. Why, and what do you change? || The client chooses when to roam and often holds on until the signal is very poor (sticky client). Improve it with more APs at lower power, minimum RSSI or minimum-rate settings, and 802.11k/v/r so the network can suggest a better AP and speed up reassociation.
Why is WPA2-Personal weak in a café with a posted password, and how does WPA3 differ? || Keys derive from the shared passphrase, so anyone who knows it and captures your four-way handshake can derive your session keys and decrypt your traffic. A weak passphrase can also be guessed offline. WPA3 uses SAE, so each session key is fresh and independent, and guesses must be tested online against the AP.
quiz: Why can a Wi-Fi station not detect a collision, and what does it use instead? || It cannot hear while it transmits, because its own signal is far louder than any incoming one. It uses acknowledgements: if no ACK arrives after SIFS, it assumes failure, doubles its contention window and retries.
What are DIFS and SIFS for? || A new transmission must wait DIFS (34 µs at 5 GHz), but an ACK is sent after only SIFS (16 µs). The shorter gap ensures that acknowledgements get the channel before anyone starts a new frame.
Compute the data rate of Wi-Fi 6 at 80 MHz, 1 stream, 1024-QAM, code rate 5/6, 980 data subcarriers and a 13.6 µs symbol. || 980 × 10 × 5/6 = 8,167 bits per symbol; ÷ 13.6 µs ≈ 600 Mbit/s.
A fast laptop (54 Mbit/s) and a slow phone (6 Mbit/s) both send 1,500-byte frames. Why does the laptop's throughput drop from about 31 to about 5 Mbit/s? || DCF lets each station send one frame per turn. The phone's frame takes 2,000 µs on the air against 222 µs for the laptop, so each round takes about 2.5 ms and each station gets about 12,000 bits per round, around 4.7 Mbit/s.
When would you choose a 160 MHz channel over 80 MHz, and when not? || Choose it with few neighbours, strong signal and clients that support it, to get up to double the peak rate. Do not choose it in dense buildings: it costs 3 dB of SNR, leaves few non-overlapping channels, and overlaps with neighbours.
