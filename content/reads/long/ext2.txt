@@+ pinot
history: LinkedIn started Pinot around 2013–2014 because its member-facing analytics ('Who viewed your profile', post analytics, recruiter dashboards) needed something no existing system offered: thousands of queries per second, latency in tens of milliseconds, and data only seconds old. Hadoop was too slow, Druid was young, and key–value precomputation could not answer flexible questions. Pinot was open-sourced in 2015, entered the Apache incubator in 2018 and became a top-level Apache project in 2021. The founders of StarTree, a company offering managed Pinot, came from the LinkedIn team.
Uber adopted Pinot for real-time operational analytics (for example, restaurant and courier dashboards for Uber Eats) and contributed upserts. Later work added a multi-stage query engine for joins and window functions, tiered storage for older segments, and more index types. Pinot's place in the ecosystem has stayed the same: the last step between a stream and a user-facing product, where many people ask small analytic questions at the same time.
how: The user-facing latency of Pinot comes from doing as little work as possible per query, in four places. First, the broker prunes: it uses time boundaries and partition metadata to send the query only to servers holding relevant segments, so a query on the last hour of one customer's data may touch a handful of segments out of hundreds of thousands. Second, each server prunes again, using segment-level column statistics and Bloom filters. Third, inside a segment, filters use indexes: an inverted or sorted index turns 'campaign_id = 42 AND country = IN' into a bitmap intersection, and a range index answers time and numeric ranges. Fourth, aggregations read only the matching rows from dictionary-encoded, bit-packed forward indexes, or, with a star-tree index, read a few pre-aggregated records instead of millions of raw rows.
Real-time ingestion has its own mechanics. Each consuming segment is owned by one or more servers that read the same Kafka partition from the same starting offset. When the segment reaches its size or time threshold, the controller coordinates a commit: one replica builds the immutable segment and uploads it, and the others either download that copy or confirm they built an identical one. This makes replicas consistent without a separate consensus protocol, because the Kafka partition and its offsets act as the shared log.
practice: Design Pinot tables backwards from the queries. List the top query shapes (filters, group-bys, time ranges, concurrency and latency targets) and choose, per column: the sorted column (usually the most selective filter that appears in almost every query, such as a customer or tenant ID), inverted indexes for other equality filters, range indexes for numeric and time ranges, and star-tree indexes for the most frequent aggregation patterns. Partition real-time tables by the same key as the Kafka topic, so brokers can prune by partition and upserts stay local.
Keep segment sizes in a healthy range (roughly 100–500 MB), because too many small segments increase broker routing and server overhead, while huge segments slow down commits and recovery. Use hybrid tables or tiered storage to keep recent data on fast disks and older data cheaper. Test with realistic concurrency, because Pinot's strength is many simultaneous queries, and its tail latency depends on the slowest server in each scatter–gather.

@@+ elasticsearch
history: Shay Banon released Compass, a Java search framework, in 2004, then rewrote it as Elasticsearch, first released in 2010, built on Doug Cutting's Lucene library (1999). The company Elasticsearch BV (later Elastic) was founded in 2012. The 'ELK stack' (Elasticsearch, Logstash, Kibana) made it the default open-source log-analytics platform during the 2010s, competing with Splunk.
In 2021 Elastic moved Elasticsearch and Kibana from the Apache 2.0 license to a dual Elastic License and SSPL, in response to cloud providers offering it as a service. Amazon forked the last Apache-licensed version as OpenSearch, which moved to the Linux Foundation in 2024. In August 2024 Elastic added the AGPL as a third licensing option, making Elasticsearch open source again. Technically, the main recent shift has been toward vector and hybrid search: dense vector fields with HNSW indexes (in Lucene since 9.0), quantization to shrink vectors, and ranking that combines BM25 and vector scores for retrieval-augmented generation.
how: Several design choices explain both Elasticsearch's power and its operational pain. Because each shard is a full Lucene index with immutable segments, writes are cheap appends but updates are really 'delete plus re-add': the old document is marked deleted in a bitmap and the new one goes into a new segment. Merges later rewrite segments without the deleted documents. Heavy update workloads therefore create heavy merge work.
Relevance and aggregations use different data structures. Scoring uses the inverted index (term to documents). Sorting and aggregations use doc values, a columnar per-field store written at index time, so 'average price by brand' does not need to load all documents into memory. Text fields are analyzed for search but cannot be aggregated directly; you usually map a field twice, as text for search and as keyword for exact matching and aggregations. Vector search uses an HNSW graph per segment, so searching many segments means searching many graphs, which is one reason merges and segment counts matter for vector workloads too.
Cluster state (index mappings, shard locations) is managed by elected master nodes. Since version 7, Elasticsearch uses its own consensus-based cluster coordination, replacing the older Zen discovery that was vulnerable to split-brain without careful configuration.
practice: Plan shards by size, not by habit: aim for shards of roughly 10–50 GB, and avoid thousands of tiny shards, each of which costs memory and file handles. For logs and other time-series data, use time-based indices or data streams with index lifecycle management to roll over, shrink, move to cheaper hardware and delete old data automatically. Define explicit mappings to avoid 'mapping explosion' from dynamic fields, and use keyword fields for anything you filter or aggregate exactly.
For relevance work, measure before tuning: build a small judged query set and track metrics such as NDCG or recall at k when you change analyzers, boosts or hybrid weights. For vector search, check recall against exact search on a sample, and consider quantization to control memory. Keep heap at or below about half of machine memory (and under about 31 GB for compressed object pointers), leaving the rest to the page cache, because Lucene relies heavily on memory-mapped files.

@@+ postgres
history: Michael Stonebraker started POSTGRES at Berkeley in 1986 as the successor to Ingres, aiming to support richer data types and rules. It used its own query language, PostQUEL, until two students, Andrew Yu and Jolly Chen, added SQL in 1994–1995 (Postgres95). Renamed PostgreSQL in 1996, it has been developed since by a global community with no single owning company, a governance model that has helped it stay trusted for decades.
Key milestones include multi-version concurrency control (6.5, 1999), the write-ahead log (7.1, 2001), built-in streaming replication and hot standbys (9.0, 2010), JSONB (9.4, 2014), logical replication (10, 2017), and steady improvements in parallel query, partitioning and performance. PostgreSQL 18 (September 2025) added an asynchronous I/O subsystem. Its extension system became a strategic advantage: PostGIS for geospatial data, TimescaleDB for time series, Citus for sharding and pgvector for vector search all build on it. Many cloud databases (Amazon Aurora PostgreSQL, AlloyDB, Neon, Supabase) keep the PostgreSQL interface while changing the storage underneath.
how: Two internal details explain much of PostgreSQL's behaviour. The first is the buffer pool (shared_buffers): pages are cached in shared memory, and PostgreSQL also relies on the operating system's page cache, so effective memory is both. When a page is modified, it stays in the buffer as 'dirty' until a checkpoint or the background writer flushes it. Checkpoints that write too much at once cause I/O spikes, which is why checkpoint spreading and WAL size settings matter.
The second is how updates interact with indexes. Because an update creates a new tuple version, every index normally needs a new entry pointing to it. Heap-only tuple (HOT) updates avoid this when no indexed column changes and there is free space on the same page, which is why leaving free space in pages (fillfactor) helps update-heavy tables. Index-only scans can answer queries from the index alone, but only for pages marked all-visible in the visibility map, which VACUUM maintains. So VACUUM affects not only space but also query speed.
practice: A few habits prevent most PostgreSQL problems. Use a connection pooler (PgBouncer or a built-in proxy) in front of busy applications, because each connection is a process. Monitor autovacuum and table bloat, and tune autovacuum to be more aggressive on large, frequently updated tables; never let long-running transactions sit idle, because they block cleanup for everyone. Read query plans with EXPLAIN (ANALYZE, BUFFERS), compare estimated and actual row counts, and fix bad estimates with ANALYZE, extended statistics or better indexes rather than query hints.
For scaling, go in steps: indexes and query fixes first, then read replicas for read-heavy load, then partitioning for very large tables, and only then sharding or a distributed SQL system. Use logical replication or CDC to feed Kafka and analytics systems instead of running heavy analytic queries on the primary.

@@+ kubernetes
history: Google ran its internal workloads on Borg from about 2003–2004, and on a second system, Omega, that explored a shared-state scheduler. In 2014 a group of Google engineers (Joe Beda, Brendan Burns and Craig McLuckie among the founders) started Kubernetes as an open-source system that applied Borg's lessons to Docker containers, which had become popular the year before. Google donated it to the newly formed Cloud Native Computing Foundation in 2015, and version 1.0 shipped that year.
By about 2017 Kubernetes had won the 'orchestrator wars' against Docker Swarm and Apache Mesos (Marathon), and every major cloud offered a managed version. Later milestones added custom resources and operators (2017–2018), the container runtime interface (removing the Docker shim in 1.24, 2022), and newer APIs such as the Gateway API for traffic routing. Recent work focuses on workloads that once seemed unsuited to it: stateful databases, batch and AI jobs with GPU scheduling, and dynamic resource allocation for accelerators.
how: The scheduler deserves a closer look. For each unscheduled pod, it filters nodes that can run it (enough requested CPU and memory, matching node selectors and affinities, tolerated taints, available volumes) and scores the rest (spreading replicas, packing efficiently, preferring nodes with cached images). It then binds the pod to the best node by writing to the API. The kubelet on that node sees the binding, asks the container runtime (containerd or CRI-O) to pull images and start containers in a new set of namespaces and cgroups, and reports status back.
Networking follows a simple rule: every pod gets its own IP address and can reach every other pod without NAT. A CNI plugin (such as Cilium, Calico or a cloud-native plugin) implements this. A Service gives a stable virtual IP and DNS name to a changing set of pods, implemented by kube-proxy rules (iptables or IPVS) or by eBPF programs. Because everything is asynchronous and level-triggered, components can crash and restart without losing track: they simply re-read the current state and continue reconciling.
practice: Set resource requests on every container, because the scheduler places pods by requests, not by actual use. Be careful with CPU limits for latency-sensitive services: cgroup throttling can add long pauses even when average CPU is low; many teams set requests and memory limits but leave CPU limits off. Add readiness probes (whether to send traffic) and liveness probes (whether to restart) with care, since an aggressive liveness probe can restart a slow but healthy service in a loop. Use PodDisruptionBudgets so node maintenance does not take down too many replicas at once.
For stateful systems like Kafka, Flink or databases, use a mature operator and understand what it automates (rolling restarts, rebalancing, storage expansion) and what it does not. Keep the number of add-ons small, and treat cluster upgrades as a regular, practiced process rather than a yearly emergency.

@@+ olap
history: The term OLAP was coined by E. F. Codd in 1993, but analytical databases are older. Teradata (1979) built a parallel database for analytics, and Ralph Kimball and Bill Inmon defined data warehouse modelling in the 1990s (star schemas and dimensional modelling from Kimball, the normalized enterprise warehouse from Inmon). Early OLAP products precomputed 'cubes' of aggregates (MOLAP), which were fast but rigid.
Column stores changed the field. Sybase IQ (1990s) and research systems like MonetDB showed the idea; C-Store (2005) and its commercial version Vertica made it mainstream, followed by cloud warehouses: Redshift (2012), BigQuery (from Google's Dremel, 2010 paper), and Snowflake (founded 2012, generally available 2014–2015), which separated storage and compute. Real-time OLAP engines (Druid 2011, Pinot 2014, ClickHouse open-sourced 2016) added streaming ingestion and very low latency. DuckDB (2019) brought a fast column store into a single process, and lakehouse engines brought OLAP to open file formats.
how: It is worth seeing why aggregation is fast in a column store. Consider SUM(revenue) GROUP BY country over a billion rows. The engine reads two columns. The country column is dictionary-encoded into small integers, so grouping becomes indexing into an array of partial sums. The revenue column is bit-packed or delta-encoded integers, decoded with SIMD instructions in batches of thousands. Each worker thread processes its own blocks into a private hash table or array, and the partial results are merged at the end. Memory traffic, not arithmetic, is the bottleneck, so every byte saved by encoding is time saved.
Distributed OLAP adds a layer of planning. Large fact tables are partitioned across nodes; small dimension tables are replicated or broadcast; joins are pushed close to the data; partial aggregates are computed locally and combined. For very large group-bys, a shuffle by group key is unavoidable. Materialized views, rollups and pre-aggregation (cubes, star-trees, aggregate tables) trade storage and freshness for speed, a choice OLAP systems have made since the beginning.
practice: Model for the queries you serve. Wide, denormalized tables are often faster than many joins in real-time OLAP engines; star schemas remain the best compromise in warehouses and lakehouses. Choose sort and cluster keys on the most common filters (time and tenant are typical), and keep partitions coarse. Pre-aggregate only the queries that are both frequent and expensive, and measure the freshness cost.
Use approximate functions where exact answers do not matter: HyperLogLog for distinct counts, t-digest or KLL sketches for percentiles. They are often 10–100 times cheaper and mergeable across partitions and time. And watch costs as closely as latency: in usage-priced systems, a missing filter on a large table can cost more than a month of storage.
