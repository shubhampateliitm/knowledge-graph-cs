@@ simd
value: SIMD (single instruction, multiple data) means that one CPU instruction works on a whole short vector of values at the same time. A 256-bit AVX2 register holds 8 single-precision floats, or 32 bytes; a 512-bit AVX-512 register holds 16 floats, or 64 bytes. One instruction adds all 8 or 16 pairs. The CPU spends roughly the same time and energy to fetch, decode and schedule that one instruction as it would for a scalar one, so the useful work per instruction goes up by the vector width.
This matters because the front part of a CPU (fetching, decoding, scheduling, renaming registers) costs far more energy than the arithmetic itself. SIMD amortizes that fixed cost over many values. A single modern core with two 512-bit fused multiply-add units can do 64 single-precision floating-point operations per cycle, about 190 GFLOPS at 3 GHz, versus 4 per cycle for a scalar core with the same units. This is also the cheapest form of parallelism there is: no threads, no locks, no memory model, just wider arithmetic inside one thread.
For the layer above, SIMD is what turns clean, array-shaped designs into fast ones. Columnar storage keeps all values of one type next to each other, which is exactly what a vector register wants. Vectorized query engines (Photon, DuckDB, ClickHouse, Velox) process batches of 1,000 or more values per operator call so the inner loop compiles to vector instructions. Bitmap indexes such as Roaring run AND, OR and population count over 512 bits at a time. Libraries such as simdjson parse JSON at gigabytes per second per core by testing 32 or 64 input bytes per instruction. The layer below that makes this natural is linear algebra (L4): a vector register is a small vector, the instructions are component-wise vector operations, and the fused multiply-add is the building block of dot products and matrix products.
terms: Lane — one element position inside a vector register; a 256-bit register has 8 lanes of 32 bits.
Vector width — the size of a SIMD register in bits: 128 (SSE, NEON), 256 (AVX2), 512 (AVX-512); SVE and the RISC-V vector extension leave it to the hardware.
Intrinsic — a function that the compiler turns into one specific SIMD instruction, such as _mm256_add_ps.
Auto-vectorization — the compiler rewrites a scalar loop into vector instructions by itself.
Mask — a per-lane yes/no value used to apply an operation to only some lanes; it replaces branches.
Shuffle (permute) — an instruction that moves values between lanes according to an index pattern.
FMA — fused multiply-add: computes a × b + c in one instruction with one rounding.
Horizontal operation — an operation across the lanes of one register (for example, summing its lanes); it is slower than the vertical operations between registers.
Gather — a vector load from several unrelated memory addresses; much slower than a contiguous load.
history: In 1966 Michael Flynn classified computers into SISD, SIMD, MISD and MIMD by how many instruction streams and data streams they handle. The first SIMD machines were large: ILLIAC IV (built 1972 to 1975) drove an array of 64 processing elements from one control unit. Seymour Cray's Cray-1 (1976) took a different path, vector registers of 64 elements that a pipeline streamed through one element per cycle. The Connection Machine CM-1 (1985) had 65,536 one-bit processors. These were supercomputers.
SIMD came to ordinary processors in the 1990s because of multimedia. Pixels, audio samples and video blocks are small integers (8 or 16 bits), and a 64-bit register can hold eight of them. HP added MAX to PA-RISC in 1994, Intel shipped MMX in 1997, and Motorola's AltiVec appeared in 1999. Intel's SSE (Pentium III, 1999) added 128-bit registers with four floats, and SSE2 (2001) added doubles and integers, so compilers could use SSE instead of the old x87 floating-point unit. ARM added NEON (128-bit) in 2005.
AVX (Sandy Bridge, 2011) doubled the width to 256 bits; AVX2 and FMA3 (Haswell, 2013) added integer operations and fused multiply-add. AVX-512 (Xeon Phi Knights Landing 2016, Skylake-X 2017) went to 512 bits and added mask registers, which made per-lane conditions cheap. Early Intel chips lowered their clock speed when running heavy 512-bit code, and the instruction set was split into many optional subsets, which slowed adoption. AMD added AVX-512 in Zen 4 (2022), executed on 256-bit halves, and widened the datapaths to full 512 bits in Zen 5 (2024) on desktop and server chips (the mobile Zen 5 parts keep 256-bit paths). Intel switched off AVX-512 in consumer chips from Alder Lake (2021) because its efficiency cores lacked it, and has since published AVX10 to unify the instruction set across core types.
A second line of design avoids fixing the width. Arm's Scalable Vector Extension (announced 2016; Fujitsu's A64FX, used in the Fugaku supercomputer, had 512-bit SVE) and SVE2 in Armv9 (2021), and the RISC-V Vector extension (version 1.0 ratified in 2021), let the same binary run on hardware with different vector lengths. Meanwhile, Langdale and Lemire's simdjson (2019) showed that even branchy text parsing can be rebuilt around vector instructions.
how: A SIMD register is a fixed number of bits that the instruction set interprets as lanes. The same 256 bits can be 32 bytes, 16 half-words, 8 floats or 4 doubles, depending on which instruction you use. Most instructions are vertical: lane i of the result depends only on lane i of the inputs. An add of two registers does 8 independent additions in the time of one. Linear algebra defines this exactly: adding two vectors, scaling a vector, and the dot product (multiply component-wise, then sum) are all built from component-wise operations. The FMA instruction does the multiply and the add together and is the primitive behind dot products, polynomial evaluation and matrix multiplication.
Data must reach the registers. A vector load reads 32 or 64 contiguous bytes in one go, ideally from one cache line (64 bytes). Contiguous loads run at the speed of the cache: a modern core can load two 32-byte vectors per cycle from the L1 cache. Gathers (loading from scattered addresses) and strided loads are far slower, often one element per cycle. This is why the data layout decides everything. A structure-of-arrays layout (all x values together, then all y values) loads straight into registers. An array of structures (x, y, z, x, y, z) must first be shuffled apart.
Conditions are handled without branches. A compare instruction produces a mask, one result per lane. With the mask you can blend (pick lane values from one of two registers), or, in AVX-512, make any instruction act on only the lanes whose mask bit is set. A branch-free filter such as "keep values greater than 10" computes the mask for 16 values, and a compress instruction (VPCOMPRESSD in AVX-512) packs the selected lanes together. The cost is that every lane does the work for both sides of a condition, so wasted work grows when the condition is rare and the work is large.
Shuffles are what make non-trivial algorithms possible. A byte shuffle (pshufb in SSSE3, vpermb in AVX-512 VBMI) uses a vector of indexes to look up bytes inside a register, so a 16-entry or 64-entry table lookup happens for all lanes at once. Movemask instructions turn a vector of byte results into an ordinary integer bit mask that scalar code can inspect with bit scan instructions. These two tools are the heart of simdjson and of fast UTF-8 validators and Base64 codecs.
The end of an array needs care. If the length is not a multiple of the vector width, the code needs either a scalar remainder loop or a masked final iteration (AVX-512 and SVE have masked loads that do not touch the missing elements). Moving data between lanes is also limited: in AVX2 most shuffles work only inside each 128-bit half of the register, and crossing the halves costs extra cycles, which is why algorithms are designed to keep lanes independent for as long as possible.
There are four ways to get SIMD code. First, write plain loops and let the compiler auto-vectorize them. This works when iterations are independent, the pointers are known not to overlap (the C keyword restrict helps), and the loop has no early exit. The compiler can tell you why it failed (GCC: -fopt-info-vec-missed; Clang: -Rpass-missed=loop-vectorize). Floating-point sums are an important exception: changing the order of additions changes the result, so compilers refuse to vectorize a float reduction unless you allow it (-ffast-math or an OpenMP reduction clause). Second, use intrinsics. Third, use a portable wrapper such as Google Highway, C++ std::simd, Rust's portable SIMD, or the Java Vector API, which compile to the right instructions for the target. Fourth, call a library that already has tuned kernels (BLAS, simdjson, a compression codec, or your database engine).
The CPU generation decides what you may use, so serious libraries detect features at run time with the CPUID instruction and choose among several code paths when the program starts. Compiling everything with -march=native makes a binary that crashes with an illegal-instruction error on an older machine. Finally, SIMD is limited by the memory below it. A core can compute 190 GFLOPS but a socket's DRAM delivers perhaps 100 to 300 GB/s shared by all cores, so a loop that streams data once and does one operation per value is limited by memory (see the roofline concept) and gains little from wider vectors.

example: Sum 1,024 single-precision floats. A plain scalar loop keeps one running total. Each addition needs the previous result, and a floating-point add has a latency of about 4 cycles on a typical Intel core. So the loop takes about 1,024 × 4 = 4,096 cycles, no matter how many execution units the core has. The compiler cannot fix this alone, because splitting the sum into pieces changes the rounding.
Now do it by hand with AVX2. A 256-bit register holds 8 floats, so the array is 128 vectors. With one vector accumulator, you do 128 vector adds, each waiting 4 cycles for the previous one: 128 × 4 = 512 cycles. That is already 8 times faster. The core can start 2 adds per cycle and each takes 4 cycles, so 8 adds can be in flight. Use 8 independent accumulators and the dependency chain is no longer the limit. Now the limit is the loads: the core can issue 2 vector loads per cycle, so 128 loads take 64 cycles. After the loop, add the 8 accumulators together (7 vector adds), then reduce the 8 lanes of the result (three shuffle-and-add steps). That final reduction costs about 10 to 15 cycles. The total is roughly 80 cycles, about 50 times faster than the scalar loop. It is not 8 times faster because the scalar loop was also latency-bound, so SIMD and independent accumulators together gave the gain.
The answer is not bit-identical to the scalar loop: 8 partial sums were added in a different order. For most uses this is acceptable and often more accurate, because each partial sum is smaller. For reproducible results you must fix the order yourself.
A second example, from simdjson: find every double quote in a 64-byte block of JSON text. Load the 64 bytes as two 32-byte vectors. Compare each with a vector filled with the byte for the quote character (one compare per vector, 32 comparisons each). Each compare gives 32 result bytes of 0x00 or 0xFF. A movemask instruction converts each into a 32-bit integer with one bit per byte. Combine the two into a 64-bit integer. Bit i is 1 exactly when byte i is a quote. About eight instructions have classified 64 characters, and scalar code can walk the set bits with a bit-scan instruction. A byte-by-byte parser would run a branch for each of the 64 characters.
intuition: A stamp that prints eight labels at once.
The idea is natural because most programs do the same small thing to a great many values: add two columns, compare every byte with a quote, scale every pixel. A processor that handles one value per instruction repeats all its bookkeeping (decoding, scheduling, renaming registers) for each value. If the data is already lined up in memory, doing 8 or 16 values per instruction removes the repeated bookkeeping and leaves only the arithmetic. The hardware cost is small, because a vector unit is just several copies of an arithmetic unit wired to one control signal. The price is that the lanes cannot do different things, so the programmer must present the work as aligned batches that all follow the same steps.
mistakes: People often think a wider vector means a proportionally faster program. In fact the speed-up is capped by memory bandwidth, by the loop's dependency chains, and by the fraction of the program that vectorizes. If a loop reads each value once and does one operation on it, DRAM bandwidth is the limit, and going from AVX2 to AVX-512 changes nothing.
People often think the compiler will vectorize any loop. In fact it vectorizes only loops it can prove safe: no dependence between iterations, no pointer aliasing it cannot rule out, no function calls it cannot inline, and (for floating point) no reassociation of sums unless you allow it. A small change, such as an early break or a pointer that might overlap another, silently turns off vectorization. Read the compiler's vectorization report instead of guessing.
People often think SIMD and GPU SIMT are the same thing. In fact SIMD exposes the vector width to the programmer, who writes instructions on registers; SIMT shows the programmer many scalar threads and lets the hardware group them into warps. SIMT has per-thread program counters and handles divergence for you (slowly), while SIMD needs masks written by you or the compiler.
People often think AVX-512 always slows the CPU down. In fact the clock reduction was real on the first generations of Intel Xeon (Skylake-SP, 2017), where heavy 512-bit instructions moved the core to a lower frequency license. Newer Intel cores and AMD's implementation have far smaller penalties. Measure on your target hardware instead of copying an old rule.
tradeoffs: Choose auto-vectorization when the loops are simple, the arrays are contiguous and a 2 to 4 times gain is enough. It costs nothing to maintain and moves with the compiler. Choose intrinsics or a portable library such as Highway when profiling shows a hot kernel that the compiler cannot vectorize (parsing, compression, bit manipulation). You pay with code that few engineers can read and a separate path for each instruction set, usually AVX2, AVX-512 and NEON.
Choose AVX2 as the baseline for server software that runs on mixed hardware, since essentially every x86 server since 2013 has it. Choose AVX-512 when you control the fleet (for example your own cloud instances), the work is wide (database scans, compression, vector search), and you can use the mask and compress features that AVX2 lacks. You give up portability: a binary built for AVX-512 fails on machines without it unless you dispatch at run time.
Choose SIMD over a GPU when the data is already in CPU memory, the batch is small (thousands to a few million items) or latency matters. Moving data over PCIe (about 32 to 64 GB/s each way for Gen 5 x16) takes longer than the vectorized loop. Choose a GPU when the work is large, regular and compute-heavy, such as matrix multiplication, where one GPU delivers 100 times or more the arithmetic of one CPU socket.
Choose a scalable-vector instruction set (SVE, RISC-V vector) when you want one binary across hardware with different vector lengths. You give up some control: you cannot assume a register size, so tricks that depend on a fixed 16 or 64 bytes (such as table lookups sized to the register) are harder.
friction: SIMD is brittle. A loop is vectorizable only if its data is contiguous, its iterations are independent and its branches are predictable or removable. Irregular access (pointer chasing, hash-table probes, sparse data) gives gathers that run at scalar speed. Short loops pay the fixed costs of setup, the remainder loop for the last few elements, and the final horizontal reduction, so vectors below about 16 to 64 elements may run slower.
Portability is an ongoing problem. x86 has SSE2, SSE4.2, AVX, AVX2 and AVX-512 with more than ten optional subsets; Arm has NEON and SVE; RISC-V has its own. Libraries ship several code paths and a dispatcher, and every new instruction set multiplies the testing. Run-time dispatch also stops inlining across the dispatch boundary. Containers and cloud providers add a further complication: the CPU you test on may not be the CPU in production, and an instance may hide some feature flags.
Floating-point results change with vectorization because the order of operations changes, which breaks bit-exact reproducibility between builds or machines. Power and heat are also real: dense 512-bit work raises the power draw of the core, and on some chips lowers the clock for neighbouring work on the same core. Finally, correctness is harder: vector code that reads past the end of an array (loading a full register when only 3 elements remain) can touch an unmapped page and crash, so careful libraries use masked loads or pad their buffers.
practice: Lay data out as structure-of-arrays or as columns, with contiguous arrays of one type, and keep them aligned to at least the cache line. Batch the work: process 1,000 to 10,000 values per call, not one value per function call, so the inner loop is a tight loop over arrays. This is the design reason behind vectorized query engines.
Check whether the compiler vectorized your hot loop before writing intrinsics. Compile with -O3 and look at the report; add restrict to pointers that do not overlap; separate the loop from branches and function calls; and use the compiler's pragma only when you have proved independence. Look at the generated assembly for ymm or zmm registers (x86) and for v-registers with .4s lanes (NEON). Benchmark with a representative data size, since vectors that fit in the L1 cache behave very differently from vectors streamed from DRAM.
If you must write kernels, prefer a portable library (Google Highway, xsimd, std::simd) over raw intrinsics, test every instruction-set path in continuous integration, and keep a plain scalar version as the reference for tests. Use CPUID-based dispatch for anything you distribute. Do not use -march=native for artifacts that run elsewhere.
In data systems, the practical wins are already built in: use columnar formats (Parquet, Delta) and engines with vectorized execution (Photon on Databricks, Velox, DuckDB, ClickHouse), and check that your own UDFs do not break vectorization by going row by row. A Python or Spark user gets SIMD by using NumPy, Arrow or native column expressions and avoiding row-at-a-time Python functions. For JSON, text or compression hot paths, check whether simdjson or a SIMD UTF-8 validator replaces your slow step.
quiz: What does a SIMD instruction do, and how many floats does one AVX2 add handle? || It applies one operation to all lanes of a vector register at once. A 256-bit AVX2 register holds 8 single-precision floats, so one add performs 8 additions.
Why will a compiler usually refuse to auto-vectorize a floating-point sum unless you pass -ffast-math? || Vectorizing a sum splits it into several partial sums added in a different order. Floating-point addition is not associative, so the result may change in the last bits, and the compiler must keep the exact order unless you allow reassociation.
Why are masks better than branches in SIMD code? || All lanes execute the same instruction, so a branch cannot send lanes different ways. A compare produces a per-lane mask, and blend or masked instructions apply the result to selected lanes only, with no branch misprediction.
A loop adds 1,024 floats with one scalar accumulator and the add latency is 4 cycles. About how long does it take, and what does an 8-accumulator AVX2 version approach? || The scalar loop is latency-bound at about 1,024 × 4 = 4,096 cycles. The AVX2 version with 8 independent accumulators is limited by loads: 128 vector loads at 2 per cycle is about 64 cycles, plus roughly 15 cycles of final reduction.
You have a database scan that filters one column of 10 billion integers stored on disk-backed Parquet files. Will moving from AVX2 to AVX-512 double the speed? || Probably not. The scan is limited by reading and decoding data and by memory bandwidth, not by arithmetic. Wider vectors help only when the data is already in cache or when decoding is compute-bound; measure before changing the build.
interview: How would you decide whether a hot loop is worth hand-vectorizing? || Profile first and confirm the loop dominates the run time. Check the compiler report to see whether it already vectorized, and compare the achieved memory bandwidth with the machine limit; if the loop is already near the bandwidth limit, vectors will not help. Hand-write only when the compiler is blocked by something you can reason about, and keep a scalar reference for testing.
Explain how simdjson parses JSON faster than a traditional parser. || It processes the input in 64-byte blocks. For each block, vector compares find quotes, backslashes and structural characters, and movemask converts them to 64-bit integers. Bit tricks on those integers (carry-less multiplication for quote regions, for example) remove characters inside strings, and a second stage walks the bit positions to build the document. Branches that depend on the data are replaced by arithmetic on masks.
Why does array-of-structures layout hurt SIMD, and what do you do about it? || A vector load wants consecutive values of one field. With an array of structures the field values are strided, so you need gathers or shuffles that cost more than the arithmetic. Switch to structure-of-arrays, or use blocked layouts (for example groups of 8 structures stored field by field).
Your service runs correctly on your laptop and crashes with an illegal instruction in production. What happened and how do you prevent it? || The binary was compiled for a newer instruction set (for example with -march=native or an AVX-512 flag) than the production CPU supports. Prevent it with a baseline target such as x86-64-v2 or v3, and use run-time feature detection and dispatch for optional faster paths.

@@ simt
value: SIMT (single instruction, multiple threads) is the execution model of GPUs. The programmer writes code for one scalar thread, and launches tens of thousands or millions of threads. The hardware groups every 32 consecutive threads into a warp and runs the warp in lockstep: one instruction is fetched and decoded once and applied to 32 threads' data. This gives the cost advantage of SIMD hardware (one control unit for many arithmetic units) while the programmer keeps the comfortable view of independent threads with their own variables and branches.
A second idea makes GPUs fast on memory-heavy work. A CPU hides the delay of a memory access (about 80 ns for DRAM) with large caches and out-of-order execution. A GPU hides it with a very large number of threads. When one warp waits for memory, the scheduler switches to another warp that is ready, at no cost, because the registers of all resident warps are kept on the chip at the same time. An NVIDIA H100 streaming multiprocessor (SM) can hold up to 2,048 threads, 64 warps, and the chip has 132 SMs, so more than 270,000 threads are resident at once. The chip spends its area on arithmetic units and registers, not on caches and branch prediction.
For the layer above, SIMT is what makes deep learning practical. FlashAttention assigns one tile of the attention computation to one thread block and keeps it in fast shared memory. ML compilers (Triton, XLA, torch.compile) generate kernels that map to this hierarchy of threads, warps and blocks. Hardware products such as the H100 and Blackwell are, at the programming level, large collections of SMs running warps. Underneath, the model comes from linear algebra (L4): graphics is a sequence of 4 × 4 matrix-vector products on millions of independent vertices and pixels, and tensor algebra (L4) describes neural network layers as index expressions in which every output element can be computed independently, so each can be one thread.
terms: Thread — one scalar execution context in a kernel, with its own registers and its own index.
Warp — a group of 32 consecutive threads (NVIDIA) that execute one instruction together; AMD calls the group a wavefront (32 or 64 threads).
Thread block — a group of up to 1,024 threads that runs on one SM, shares fast memory and can synchronize.
Grid — all the thread blocks of one kernel launch.
Streaming multiprocessor (SM) — the GPU's core unit: schedulers, arithmetic lanes, register file and shared memory. An H100 has 132.
Divergence — threads of one warp take different branches, so the warp runs both paths one after the other with threads masked off.
Coalescing — combining the memory accesses of a warp into a few wide transactions, which happens when the 32 threads touch neighbouring addresses.
Shared memory — a fast, programmer-managed memory (up to 228 KB per SM on H100) shared by the threads of a block.
Occupancy — the fraction of an SM's maximum resident warps that a kernel actually keeps resident.
history: Early GPUs (the name was popularized by NVIDIA's GeForce 256 in 1999) were fixed-function graphics pipelines. Programmable shaders arrived in 2001 with GeForce 3. Researchers soon noticed that a pixel shader is a small program run on millions of independent pixels, and used it for general computing by pretending the data was a texture. The Stanford language Brook (Buck et al., 2004) hid this trick, and Buck then joined NVIDIA.
The key design step was the GeForce 8800 (November 2006), the Tesla architecture, which replaced separate vertex and pixel hardware with one array of identical programmable processors. NVIDIA released CUDA in 2007, and Lindholm and colleagues described the design in IEEE Micro in 2008, using the term SIMT. Fermi (2010) added real caches and error correction; Kepler, Maxwell and Pascal improved efficiency. In 2012, Krizhevsky, Sutskever and Hinton trained AlexNet on two GeForce GTX 580 cards, and deep learning moved onto GPUs.
Volta (2017) changed two important things. It gave every thread its own program counter and call stack (independent thread scheduling), so divergent threads can interleave and a lock inside a warp no longer deadlocks the warp. It also added tensor cores (see the tensor cores concept). Ampere (2020) and Hopper (2022) added asynchronous copies between global and shared memory, and thread block clusters. AMD followed with its own wavefront-based designs (GCN, then RDNA for graphics and CDNA for compute), and Khronos standardized OpenCL in 2009. As of 2026, the same ideas run in NVIDIA Blackwell and in AMD Instinct accelerators.
how: A GPU program is a kernel: a function that every thread runs. The launch gives a grid of thread blocks, for example 4,000 blocks of 256 threads. The hardware hands each block to an SM, and the block stays there until it finishes. Each thread learns its place from built-in variables (blockIdx, threadIdx), so it knows which element of the data to process. Blocks cannot depend on each other, which is what lets the same kernel run on a small GPU with 20 SMs or a large one with 132: the hardware simply schedules more or fewer blocks at a time.
Inside the SM, a block is cut into warps of 32 threads. An H100 SM has four partitions. Each has a warp scheduler, which issues one instruction per cycle, and 32 FP32 lanes, so 128 FP32 lanes per SM. A scheduler picks a ready warp every cycle and sends the same instruction to the 32 lanes. All warps resident on the SM share a register file of 64K 32-bit registers (256 KB). Registers are allocated to a warp for its whole life. So switching from one warp to another needs no saving or restoring, and costs zero cycles. This is the mechanism behind latency hiding: global memory takes several hundred cycles, but if the scheduler has dozens of warps, some other warp is almost always ready.
Latency hiding follows Little's law: the data in flight equals bandwidth times latency. If H100 memory delivers about 3.35 TB/s and a load takes roughly 300 ns, about 1 MB must be in flight chip-wide, or about 7.5 KB per SM. If each thread loads 4 bytes, that needs nearly 2,000 outstanding loads per SM, which is why GPUs need thousands of threads (or wide 16-byte loads) per SM to reach their memory bandwidth. Occupancy is limited by whichever resource runs out first: 2,048 threads, 64K registers (so a kernel using 128 registers per thread fits only 512 threads), or shared memory per block.
Branches work through an active mask. When threads of a warp disagree on an if, the hardware runs the "then" path with the disagreeing threads masked off, then the "else" path with the others masked off, then the warp reconverges. Cost is the sum of both paths. Divergence between warps is free, because each warp has its own program counter, so you should arrange that the condition is uniform inside each group of 32 threads. This is the same mask idea as in SIMD, with the difference that the hardware tracks the masks and the programmer does not write them.
Memory access has its own rule. When a warp executes a load, the hardware looks at the 32 addresses. If they fall in a few adjacent 32-byte sectors (for 32 threads reading consecutive floats, 128 bytes), the access is served by one or a few transactions. If the addresses are scattered, up to 32 transactions are needed and most of the fetched bytes are wasted. Shared memory is divided into 32 banks of 4 bytes, and 32 threads can read it in one cycle if they hit different banks; if several threads hit the same bank (a bank conflict), the access is serialized. The usual kernel pattern is therefore: load a tile from global memory in a coalesced way into shared memory, synchronize the block with __syncthreads(), compute from the fast shared memory many times, and write the result back. Matrix multiplication and FlashAttention are built this way.
Threads in a warp can also exchange values directly through registers with shuffle instructions, and a block can synchronize with a barrier. Atomic operations allow global counters and histograms. Between blocks there is no cheap synchronization; a kernel boundary is the usual barrier.

example: Add two arrays of 1,000,000 floats on an H100. Choose blocks of 256 threads. You need ceil(1,000,000 / 256) = 3,907 blocks. Each block has 256 / 32 = 8 warps. Thread i computes c[i] = a[i] + b[i], with i = blockIdx.x × 256 + threadIdx.x; the last block has threads past the end, which a bounds check skips.
An SM can hold 2,048 threads, so 8 blocks of 256 at once. The chip can run 132 × 8 = 1,056 blocks at once, so the 3,907 blocks run in about 3.7 "waves". Each warp's load of a[i..i+31] reads 32 neighbouring floats, which is 128 bytes, a perfect coalesced access: 4 sectors, no waste. The kernel moves 12 bytes per element (two reads, one write), so 12 MB in total. At 3.35 TB/s peak this is about 3.6 µs; in practice the launch overhead (a few µs) is as large as the work. The arithmetic is only one add per 12 bytes, so the kernel is limited by memory, not by the 60 TFLOPS of FP32 the chip could do.
Now change the access: thread i reads a[i × 32]. Each lane of a warp now touches a different 128-byte line, and each lane needs a separate 32-byte sector. The hardware fetches 32 sectors, 1,024 bytes, to use 128 bytes: 12.5% efficiency, so the kernel takes about 8 times longer. Next change the code to "if (threadIdx.x % 2 == 0) do X; else do Y" with 10 instructions each. Even and odd lanes of every warp diverge, so each warp executes 20 instructions instead of 10. If you write the condition as "(threadIdx.x / 32) % 2 == 0", the whole warp takes one path and the cost stays 10. The result is the same amount of work per thread, arranged so that warps agree.
intuition: A drill sergeant shouting one command to a platoon; anyone who must do something different waits their turn.
The design is natural once you see what graphics and tensor work look like: huge numbers of independent items doing the same steps. For such work, control logic is the expensive part of a processor, so share it: one instruction stream for 32 lanes. Memory is the other expensive part, and slow; instead of building bigger caches to avoid waiting, keep so many threads in flight that waiting never stops the arithmetic units. The programmer gets a simple model (write one thread), while the hardware gets regular, wide work. The price is that you must keep the 32 threads of a warp doing the same thing and touching neighbouring memory.
mistakes: People often think a GPU core is like a CPU core. In fact an NVIDIA "CUDA core" is just one FP32 lane in a warp. The real unit comparable to a CPU core is the SM, and a GPU with 16,896 CUDA cores has 132 SMs. A single GPU thread is much slower than a CPU thread; the GPU wins by running many.
People often think GPU threads are independent, so branches are free. In fact the 32 threads of a warp share an instruction stream. A branch with both outcomes inside one warp executes both paths one after the other. Volta's independent thread scheduling made this safe for locks, not fast.
People often think more threads per block is always better. In fact the best size depends on registers, shared memory and the launch shape. A block of 1,024 threads that uses 100 registers per thread cannot fit two blocks in one SM, and a kernel with low occupancy may still be fast if each thread has independent work in flight. Measure with a profiler instead.
People often think the GPU is slow to read memory, because its latency is high. In fact its bandwidth is very high (3.35 TB/s on H100 compared with about 300 GB/s for a large CPU socket). The latency is hidden by warps. A kernel with too few threads, or with dependent loads, exposes the latency and runs far below the bandwidth limit.
tradeoffs: Choose a GPU when the work has millions of independent items with regular memory access and a high ratio of arithmetic to memory traffic (matrix multiplication, convolution, attention, image processing). Choose a CPU for code with irregular branching, small batches, pointer-heavy data structures or tight latency, such as a request handler. A GPU kernel launch costs about 5 to 10 µs, and a PCIe transfer for 100 MB takes about 2 to 3 ms at 32 to 64 GB/s, so small jobs never pay back.
Choose bigger blocks and high occupancy when the kernel is limited by memory latency, since more warps hide more delay. Choose smaller blocks and more registers per thread when each thread has a long chain of independent arithmetic (instruction-level parallelism) or needs big per-thread tiles, as in high-performance matrix multiplication. You trade occupancy for registers, and the right balance has to be measured.
Choose CUDA when you need the full performance, the libraries (cuBLAS, cuDNN, NCCL) and the tooling; choose a portable layer (OpenCL, SYCL, HIP, Triton, or a framework such as PyTorch) when you need to run on more than one vendor. You give up some performance for portability, and you accept dependence on someone else's compiler either way. Choose a compiler like Triton when you want near-hand-tuned speed with block-level code and automatic management of coalescing and shared memory; choose raw CUDA when you must control warp-level details.
friction: Divergence, uncoalesced access and bank conflicts can each cut performance by a factor of 2 to 30, and they are invisible in the source code; only a profiler (Nsight Compute) shows them. Occupancy is a multi-way trade between registers, shared memory and block size, and the best settings differ by chip generation, so tuned kernels do not carry over without retuning. Memory capacity is small (80 to 288 GB) compared with a CPU server (terabytes), and memory-bandwidth demand grows faster than supply, which is why attention and large-model inference are limited by memory traffic more than by arithmetic.
Programming is harder than on a CPU. Debugging thousands of threads, race conditions in shared memory, and floating-point non-determinism from atomic additions (the order of adds changes between runs) are standing problems. Host-device transfers and kernel-launch overhead add costs that a CPU does not have; CUDA graphs and fused kernels reduce them. The ecosystem is concentrated: CUDA, with its libraries, is a strong lock-in, and AMD's ROCm and others are catching up but still lag in some areas. Finally, power: a modern GPU draws 700 W or more (H100 SXM up to 700 W), so data-center cooling and power set the limit of a cluster.
practice: Think in three levels. At the grid level, make enough blocks (several times the number of SMs) to keep every SM busy and to even out the tail. At the block level, choose 128 to 256 threads as a starting point, and tile your data through shared memory. At the warp level, make the 32 threads access neighbouring addresses and take the same branch. Always check that the fastest-changing index (threadIdx.x) maps to the fastest-changing (contiguous) array dimension.
Do not write raw kernels first. Start with libraries (cuBLAS, cuDNN, cuFFT, Thrust or CUB, RAPIDS) and framework operators, and fuse operations with torch.compile or Triton to avoid writing intermediate results to memory. When you must write a kernel, begin with a simple correct version, profile it with Nsight Systems (whole program: gaps, transfers) and Nsight Compute (one kernel: occupancy, memory throughput, warp stalls), and fix the biggest limit first. Compare the achieved bandwidth and FLOPS with the roofline limit to know whether you are memory-bound or compute-bound.
Use asynchronous copies and streams to overlap transfers with compute, keep data on the GPU between steps, and batch small operations. For Spark and data platforms, GPU acceleration (RAPIDS Accelerator) pays off for wide, arithmetic-heavy or sort/join/aggregate work on large data, and not for small shuffles or heavy UDFs written for rows. In production, watch GPU utilization together with memory bandwidth utilization; "100% utilization" only says a kernel was running, not that the hardware was busy.
quiz: What is a warp, and what happens when threads in a warp take different branches? || A warp is a group of 32 threads that execute one instruction together. If they branch differently, the hardware runs each path in turn with the non-participating threads masked off, so the warp takes the sum of the time of both paths.
Why can a GPU switch between warps at no cost, and what does that buy? || All resident warps keep their registers in the SM's large register file at the same time, so switching is just choosing another warp. It hides memory latency: when one warp waits for memory, another one issues instructions.
Why is a warp reading 32 consecutive floats efficient and a warp reading every 32nd float not? || Consecutive floats are 128 contiguous bytes, so one or a few memory transactions serve all 32 lanes. With a stride of 32 floats each lane needs a different 32-byte sector, so 32 sectors (1,024 bytes) are fetched for 128 useful bytes, about 12.5% efficiency.
A kernel uses 128 registers per thread. An SM has 65,536 registers. How many threads can be resident, and what fraction of the 2,048-thread maximum is that? || 65,536 / 128 = 512 threads, which is 16 warps and 25% of the maximum occupancy. Fewer registers per thread would allow more warps to hide latency.
When would you prefer a CPU over a GPU for a data-processing step? || When the data is small (a launch and a transfer cost milliseconds), when the logic is branchy or pointer-based, when it needs low latency per request, or when the data does not fit in GPU memory. Large, regular, arithmetic-heavy batches favour the GPU.
interview: Explain SIMT versus SIMD. What does the programmer see in each? || In SIMD the programmer (or compiler) works with explicit vector registers and lane masks. In SIMT the programmer writes scalar code per thread, and the hardware groups 32 threads into a warp, with an active mask and per-thread program counters since Volta. SIMT makes divergence legal but slow; SIMD makes it explicit.
Your kernel reaches only 30% of peak memory bandwidth. How do you find out why? || Profile with Nsight Compute. Check coalescing (sectors per request), whether occupancy and bytes in flight are enough by Little's law, bank conflicts, tail effects (too few blocks), and whether the access is dependent (pointer chasing). Then fix the largest cause, for example by vectorizing loads to 16 bytes or restructuring the access order.
What is the cost of divergence, and how do you reduce it? || A divergent warp executes both paths, so a warp with all 32 lanes taking different paths of an if/else can run at half speed or worse. Reduce it by sorting or grouping work so that neighbouring threads follow the same path, using predication for short branches, and moving the branch to a warp boundary.
Why do GPUs need so many threads, and why is occupancy not the same as performance? || Latency hiding requires enough memory requests in flight (Little's law). But a kernel can reach full bandwidth at 50% occupancy if each thread issues several independent loads. High occupancy can even hurt when it forces fewer registers per thread and so causes register spills to memory.
Why is the SIMT model a good fit for deep learning and a poor fit for a hash-join with skewed keys? || Dense layers are regular: independent outputs, predictable access, high arithmetic intensity. A skewed hash join has irregular memory access and uneven work per thread, which causes divergence, uncoalesced loads and idle lanes, although GPU libraries have found workable approaches for some cases.

@@ tensorcores
value: A tensor core is a hardware block that multiplies two small matrices and adds a third in a single operation, \( D = A \times B + C \). A systolic array is a grid of multiply-accumulate units through which data flows rhythmically from neighbour to neighbour. Both do the same job: matrix multiplication, which is almost all of the arithmetic in a neural network. They exist because a general-purpose lane, even in a GPU, spends most of its energy on fetching operands and not on the multiplication. A matrix unit reuses every operand many times after it has been fetched once.
The gain is large. On NVIDIA's V100 (2017), the 640 tensor cores deliver 125 TFLOPS of FP16 matrix arithmetic, about 4 times what the ordinary FP16 lanes deliver and 8 times the FP32 rate. On an H100, dense FP16 tensor throughput is about 989 TFLOPS against 67 TFLOPS for ordinary FP32, roughly 15 times. In FP8 the H100 reaches about 1,979 TFLOPS dense. Nearly all of an AI accelerator's quoted FLOPs come from these units. Google's TPU is the same idea built as a whole chip around a systolic array, and AMD's Matrix Cores in Instinct GPUs follow it.
The layers above depend on this directly. Self-attention and the feed-forward layers of a transformer are large matrix multiplications that run on tensor cores. Mixed precision and quantization exist because tensor cores reach full speed only in low-precision formats (BF16, FP8, FP4), so formats shrank to match the hardware. The layers below explain the work: linear algebra (L4) defines the matrix multiply-accumulate itself, and tensor algebra (L4) shows how any large tensor contraction can be cut into small tiles, each of which is one of these small matrix operations. Without that tiling property, a hardware block of fixed size (such as 16 × 8 × 16) could not serve matrices of arbitrary size.
terms: Matrix multiply-accumulate (MMA) — the operation \( D = A \times B + C \) on small matrices (tiles); the unit of work of a tensor core.
Systolic array — a regular grid of processing elements that pass data to their neighbours each clock tick, so each value is reused many times without returning to memory.
Processing element (PE) — one cell of the array: a multiplier, an adder and a register.
Weight-stationary — a dataflow in which the weights stay in the PEs while the activations flow through (the original TPU design).
Accumulator — the register that holds the running sum of products; it is kept in higher precision (FP32 or INT32) than the inputs.
Tile — a small block of a large matrix, for example 16 × 16, that one MMA instruction handles.
Arithmetic intensity — FLOPs performed per byte moved to or from memory; matrix units raise the demand for it.
Structured sparsity (2:4) — a pattern in which 2 of every 4 weights are zero, which the hardware can skip to double throughput (Ampere and later).
Microscaling — a format in which a small block (for example 32 values) shares one scale factor, so each value can use only 4 to 8 bits (FP4, FP8).
history: In 1978, H. T. Kung and Charles Leiserson described systolic arrays: regular grids of simple cells in which "data flows rhythmically", like blood pumped by the heart (hence "systolic"). Their motivation was the new field of VLSI. Wires and memory access, not arithmetic, were becoming the cost, so a design should fetch each data item once and use it many times. Kung's 1982 paper "Why Systolic Architectures?" made the argument for matrix, signal-processing and graph problems. Several systolic machines were built in the 1980s (CMU's Warp, Intel iWarp), but general-purpose CPUs improved fast enough that they stayed niche.
Neural networks brought the idea back. Around 2013, Google projected that speech recognition with deep networks would need a doubling of its data centers. It built the Tensor Processing Unit, deployed in 2015 and described by Jouppi and colleagues in 2017: a 256 × 256 systolic array with 65,536 8-bit multiply-accumulate units, 92 trillion operations per second at 700 MHz, with 28 MiB of on-chip memory. TPU v2 (2017) moved to a floating-point format that Google named bfloat16, to allow training.
NVIDIA announced tensor cores with Volta in 2017: each performs a 4 × 4 × 4 matrix multiply-accumulate per clock, 64 fused multiply-adds. Later generations extended the formats and the tile sizes. Turing (2018) added INT8 and INT4; Ampere (2020) added TF32, BF16, FP64 and 2:4 sparsity; Hopper (2022) added FP8, a Transformer Engine that chooses precision per layer, an asynchronous warpgroup matrix instruction and the Tensor Memory Accelerator for tile copies; Blackwell (2024) added FP4 and FP6 with microscaling and a dedicated Tensor Memory. For Rubin, announced in 2026, NVIDIA quotes tens of petaFLOPS in its NVFP4 format; independent measurements will tell how much of that survives in real models.
how: The core of a matrix unit is the multiply-accumulate (MAC). A product is added to a running sum. A matrix product \( C = A \times B \) is nothing but many MACs: \( C[i][j] = \sum_k A[i][k] \times B[k][j] \). Linear algebra tells us two things that hardware uses. First, each A element is used for every column of B, and each B element for every row of A. Second, the sums are independent for different (i, j). So an \( n \times n \) by \( n \times n \) product has \( 2n^3 \) operations on only \( 3n^2 \) numbers: n-fold reuse. A hardware unit that fetches an operand once and uses it n times has an energy advantage. In a 45 nm process, a 32-bit DRAM read costs roughly 640 pJ and a 16-bit floating-point multiply about 1 pJ (Horowitz, 2014): a factor of several hundred. Moving data is the expensive part, and a systolic array moves it only between neighbouring cells.
In a systolic array, weights are loaded into the cells and held there. Input vectors enter from the left edge, one row of cells per input element, delayed by one cycle per row (skewed). Each cell multiplies the input it receives by its stored weight, adds the partial sum arriving from above, passes the input on to the right and the new partial sum down. After the data has crossed the array, complete dot products leave from the bottom edge, one result column per cycle in steady state. A 256 × 256 array does 65,536 MACs per cycle with no memory access inside the array. The latency to fill the array is about 2 × 256 cycles, and then it runs at full rate, so it needs long streams of inputs to be efficient.
A GPU tensor core is a smaller, more flexible version. It is a fixed-function unit inside the SM, programmed through warp-wide instructions (mma.sync in PTX, shapes such as m16n8k16). The 32 threads of a warp together hold the tile fragments in their registers, and one instruction does the whole tile multiply-accumulate. On Hopper, the wgmma instruction works at the level of 128 threads (a warpgroup), reads the tile from shared memory directly and runs asynchronously, so the SM can copy the next tile while the current tile is multiplied. Libraries and compilers (cuBLAS, CUTLASS, Triton) cut a large matrix product into thread-block tiles, then warp tiles, then these small MMA tiles. This is the tensor-algebra step: any contraction is a sum of tile products.
Precision is the second ingredient. Multiplying two FP16 numbers produces a product with up to 22 significant bits, which fits exactly in the 24 bits of an FP32 number. So the hardware multiplies in low precision and accumulates in FP32, and the only rounding error is in the additions. This is why FP16 inputs with FP32 accumulation train networks well. Narrower formats need extra care: FP8 comes in two flavours, E4M3 (more precision, range up to 448) and E5M2 (more range), and FP4 relies on a shared scale per block of 16 or 32 values to keep range. The internal summation order and rounding inside a tensor core are not fully specified by vendors, so results can differ slightly between GPU generations.
Memory still has to keep up. A V100 tensor core array can consume far more operands per second than the L1 cache can supply from naive code, so the program must stage tiles in shared memory and registers and reuse them. As matrix units got faster (a factor of about 8 from V100 to H100 for FP16) while memory bandwidth grew by about 3.7 times (900 GB/s to 3.35 TB/s), the ratio of arithmetic to memory has gone up. Bigger tiles, asynchronous copies and fused kernels like FlashAttention are the answer.

example: Use the 2 × 2 array in the diagram, with the weights W = [[1, 2], [3, 4]] stored in the cells. Multiply two input vectors, r0 = [5, 6] and r1 = [7, 8], by W. The expected answers are r0 × W = [5·1 + 6·3, 5·2 + 6·4] = [23, 34] and r1 × W = [7·1 + 8·3, 7·2 + 8·4] = [31, 46].
Cycle 0: the value 5 enters the top-left cell (weight 1) and gives a partial sum of 5. Cycle 1: this partial sum moves down to the bottom-left cell (weight 3), where the value 6 has just arrived (it enters one cycle later). The cell adds 6 × 3 = 18 to give 23, the first output, from the left column. At the same time, the value 5 has moved right to the top-right cell (weight 2) and gives 10; and the second vector's value 7 has entered the top-left cell and gives 7. Cycle 2: the 10 moves down to the bottom-right cell where 6 has arrived and gives 10 + 6 × 4 = 34. The 7 moves down and picks up 8 × 3 = 24, giving 31. Cycle 3: the second vector's right column finishes: 14 + 8 × 4 = 46. In four cycles, 8 multiplications and 4 additions were done by 4 cells, and nothing was read from memory except the inputs. A larger array behaves the same, and in steady state every cell works every cycle.
Now count the benefit for a real shape. Multiplying two 4,096 × 4,096 FP16 matrices needs 2 × 4,096³ ≈ 137 billion FLOPs. On an H100 with about 989 TFLOPS dense FP16 tensor throughput, the ideal time is 137 × 10⁹ / 989 × 10¹² ≈ 0.14 ms. Real kernels reach 60 to 80% of the peak, so about 0.2 ms. On the ordinary FP32 lanes (67 TFLOPS) it would take about 2 ms. The matrices occupy 3 × 4,096² × 2 bytes ≈ 100 MB, which takes about 30 µs to stream from HBM at 3.35 TB/s, so this size is compute-bound. With a 256 × 256 matrix, the same 3 × 128 KB moves quickly but the work is only 33 MFLOPs, and launch overhead dominates.
intuition: A bucket brigade of calculators, each doing a multiply and passing the numbers on.
A matrix product reuses every number many times, so the best machine fetches each number once and lets neighbours pass it along. A systolic array is exactly this: a pipeline in two dimensions where all arithmetic units are busy at every clock tick and the only wires are short ones between neighbours. A tensor core takes the same idea into a GPU by making the unit of work a small matrix tile instead of a single number. Because neural networks spend most of their time in this one operation, a unit that does only this operation and does it with the least data movement is the most efficient use of silicon.
mistakes: People often think tensor cores make all GPU code faster. In fact they accelerate only matrix multiply-accumulate with supported shapes and data types. Elementwise operations, softmax, layer norm, data loading and irregular code run on the ordinary lanes and are often limited by memory bandwidth.
People often think low precision means low accuracy. In fact the products and sums are accumulated in higher precision (FP32 or INT32), and the low-precision inputs are what limit accuracy. Networks tolerate this well when the scale is chosen carefully; FP16 training needs loss scaling, and FP8 or FP4 need per-tensor or per-block scale factors. With wrong scaling the values overflow or underflow, and training diverges.
People often think the quoted peak TFLOPS is what you will get. In fact the peak assumes the largest data type, dense matrices, large tiles, and operands arriving on time. Sparse figures assume 2:4 sparsity, which is double the dense number; always compare the dense number. Real matrix multiplications reach 50 to 80% of peak, and small or oddly shaped ones far less.
People often think a TPU and a GPU tensor core are different kinds of thing. In fact both are matrix-multiply units. The TPU makes a very large array (128 × 128 or 256 × 256) the center of the chip and feeds it from big on-chip buffers; a GPU has many small units spread across hundreds of SMs, controlled by threads, and keeps flexibility for other workloads.
tradeoffs: Choose a large systolic array (TPU style) when the workload is dominated by large, regular matrix products, you can keep batch sizes high, and cost per FLOP and energy matter most. A 256 × 256 array is efficient only for matrices at least that big, and it idles on small batches or odd shapes. Choose a GPU with tensor cores when the workload mixes matrix products with irregular operations (custom kernels, sparse operations, graphics, data preprocessing), or when software support and flexibility are worth more than the last factor in efficiency.
Choose BF16 for training when you want FP32's exponent range with no loss scaling and can accept 7 bits of mantissa; choose FP16 when you need more precision and can manage loss scaling. Choose FP8 for inference and for training with a mature recipe (per-tensor scaling, delayed scaling), where it doubles throughput and halves memory traffic against FP16; choose FP4 with block scaling for inference of large models when the memory and speed gain is worth a small quality loss that must be measured on your task.
Choose 2:4 structured sparsity only if you can fine-tune the model after pruning to keep quality. It offers up to 2 times the math throughput but not 2 times the end-to-end speed, since memory traffic and other layers do not shrink as much. Choose to rely on vendor libraries (cuBLAS, cuDNN) for standard shapes and a template or compiler path (CUTLASS, Triton) for fused or unusual kernels; the price of the second is the effort to tune it per hardware generation.
friction: Memory bandwidth is the main limit. Matrix units have grown faster than memory, so small or skinny matrices (as in token-by-token decoding of a language model, where the batch is small) cannot use the arithmetic; they read all the weights once per step and are bound by HBM bandwidth. This is why batching, quantization of weights and the KV cache design matter so much for inference.
Programming is hard. The tile shapes, the register layout of fragments, shared-memory bank layouts, asynchronous pipelines and the instructions all change from one GPU generation to the next, so the best kernels are rewritten for each (Hopper's wgmma and Blackwell's tcgen05 are different from Ampere's mma.sync). Numerical behavior is not fully specified: the order of accumulation and the handling of rounding and denormals differ, so the same model can give slightly different results on different hardware. Low-precision training is still an active research area, with loss spikes and instability that need per-layer care.
Systolic arrays have utilization problems: a fixed-size array wastes cells when a matrix dimension is not a multiple of the array size, and there is a fill and drain delay at the start and end of each tile. Finally, supply and power: the units are cheap in area but the HBM and packaging that feed them are the scarce part, and a rack of such accelerators draws tens to over a hundred kilowatts.
practice: Make dimensions multiples of the tile size, usually 8 or 16 for FP16 and BF16, and 16 or 32 for FP8 and INT8 (padding vocabulary sizes and hidden sizes to multiples of 64 is a well-known trick). Use BF16 or FP16 autocast in PyTorch (torch.autocast) and keep master weights and optimizer state in FP32. Check that the profiler shows tensor-core kernels (names with "gemm", "wmma" or "cutlass", and a tensor-core utilization metric) instead of plain FP32 kernels.
Know your bound before optimizing. Compute the arithmetic intensity of an operation: FLOPs divided by bytes moved. If it is below the machine's balance point (for H100 FP16, 989 TFLOPS / 3.35 TB/s ≈ 295 FLOPs per byte), the operation is memory-bound and faster tensor cores will not help. Matrix products with large batches are above it; decoding one token at a time is far below it. Fuse elementwise work into the matrix kernel (bias, activation) so that you do not write intermediate results to HBM.
Batch requests for inference so the matrix dimension is large. Use quantized weights (INT8, FP8, FP4) to cut memory traffic when decoding. Compare results against a higher-precision run before moving to a lower format, and track both accuracy and end-to-end throughput, not only the kernel speed. When reading vendor numbers, find the data type, whether it is dense or sparse, and whether it is a peak or a measured figure.

interview: Why did low-precision formats (FP16, BF16, FP8, FP4) become central to AI hardware? || Narrower numbers need smaller multipliers (area and energy fall roughly with the square of the mantissa width) and fewer bytes to move, so throughput per watt and per HBM byte rises. What is the difference between the roofline of a decode step and of a prefill step in an LLM? || Prefill processes many tokens at once, so its matrices are large and its arithmetic intensity is high; it runs near the compute roof. Decode processes one token per sequence, so intensity is low (about 1 to a few FLOPs per byte) and it sits under the memory-bandwidth slope. The fixes differ: bigger tiles and lower precision for prefill, batching and weight compression for decode.

@@ dram
value: DRAM (dynamic random-access memory) is the main memory of nearly every computer. Each bit is a tiny capacitor with one transistor; a charged capacitor means 1, an empty one means 0. This is the smallest and cheapest way to build fast, random-access memory, so DRAM gives you gigabytes to terabytes at a few dollars per GB. The price is time: an access from a CPU core takes roughly 80 to 100 ns, which is hundreds of CPU cycles, and the capacitors leak, so the memory has to be refreshed all the time.
HBM (high-bandwidth memory) is DRAM rebuilt for bandwidth. Instead of a few wide DIMMs on a motherboard, it stacks 8 to 16 DRAM dies on top of each other, connects them with thousands of vertical wires, and places the stack on the same package as the processor. One HBM3 stack has a 1,024-bit interface and delivers about 800 GB/s; the H100 GPU with five active stacks reaches 3.35 TB/s, roughly ten times a two-socket server's 12-channel DDR5. The newest standard, HBM4 (JEDEC, April 2025), doubles the interface to 2,048 bits, up to 2 TB/s per stack.
For the layers above, DRAM sets the speed limit of almost everything. Transformer inference reads all the weights and the KV cache from HBM for each generated token, so memory bandwidth, not arithmetic, usually decides the speed. FlashAttention exists to avoid writing the large attention matrix to HBM. The roofline model uses DRAM or HBM bandwidth as its slanted limit. The physics below explains each feature: electromagnetism (L5) describes a capacitor holding charge, quantum tunneling (L5) is one reason the charge leaks away, and through-silicon vias (die stacking, L5) are the vertical wires that make HBM possible.
terms: Cell — one capacitor plus one access transistor; stores one bit as charge.
Row buffer — the set of sense amplifiers (about 1 to 2 KB per bank) that holds the most recently opened row; later accesses to the same row are fast.
Refresh — periodically reading and rewriting every row so the leaking charge is restored (every 32 to 64 ms).
Bank — an independent array of rows and columns inside a DRAM chip; several banks work in parallel.
Channel — an independent set of wires between a memory controller and its DIMMs; bandwidth adds up across channels.
tRCD, CL, tRP — the main timings: row-to-column delay, column access latency and row precharge time; each is about 14 to 16 ns in DDR4 and DDR5.
DDR5 — the current main-memory standard for servers and PCs (JEDEC 2020), running at 4,800 to 8,800 MT/s per pin.
HBM — high-bandwidth memory: stacked DRAM dies next to the processor, with a very wide interface.
TSV — through-silicon via: a vertical conductor through a thinned silicon die that links stacked dies.
Rowhammer — a fault attack that flips bits in a DRAM row by repeatedly accessing neighbouring rows.
history: The DRAM cell was invented by Robert Dennard at IBM in 1966, and patented in 1968. His one-transistor, one-capacitor design replaced the six-transistor static memory cell and the magnetic cores of that time. Intel's 1103 (1970) was the first commercial DRAM chip, with 1 Kbit, and it made semiconductor memory cheaper than core memory. Since then, capacity has grown by a factor of about a million, with chips of 16 to 32 Gbit now common.
Interfaces changed faster than cells. Synchronous DRAM (SDRAM, standardized in the early 1990s) tied the chip to a clock. DDR (2000) transferred data on both clock edges, and each generation (DDR2, DDR3, DDR4, DDR5) doubled the internal fetch size and raised the transfer rate. DDR5 (JEDEC, July 2020) split each module into two independent 32-bit sub-channels, added on-chip error correction and moved voltage regulation onto the module. At the same time, raw access latency barely changed: it has stayed near 13 to 15 ns for the core array timings for twenty years, because it is set by how fast a tiny capacitor can charge a long wire.
Wulf and McKee named the "memory wall" in 1995: processor speed was improving about 50 to 60% a year, DRAM latency only about 7% a year, so the gap would eventually dominate. The industry's answers were caches (see the memory hierarchy concept), prefetching and out-of-order execution, and then, for bandwidth-hungry parallel chips, stacking. HBM was developed by AMD and SK hynix and standardized by JEDEC in 2013. AMD's Fiji GPU (2015) was the first product. HBM2 and HBM2E served NVIDIA's V100 and A100; HBM3 (2022) powers the H100; HBM3E powers H200 and Blackwell; HBM4 (2025) is for the next generation. Since 2023, HBM supply (SK hynix, Samsung, Micron) has been one of the constrained inputs for AI accelerators.
Rowhammer was shown by Kim and colleagues in 2014: as cells became smaller and closer, repeated activation of one row disturbed charge in the adjacent rows. It was later turned into privilege-escalation exploits, and vendors responded with refresh-based mitigations that researchers have repeatedly bypassed, including on DDR5.
how: A DRAM chip is a collection of banks. A bank is a two-dimensional array of cells: a row is selected by a word line, and each column has a bit line that runs down the array. To read a cell, the controller sends an ACTIVATE command with a row address. The word line turns on all the access transistors in that row, so every cell shares its charge with its bit line. The cell capacitor is tiny (about 20 to 30 femtofarads, from the physics of a capacitor storing charge as an electric field), and the bit line is much bigger, so the voltage on the bit line moves by only some tens of millivolts. A sense amplifier at the end of each column detects this small change, amplifies it to a full 0 or 1, and, at the same time, writes the value back into the cell. Reading is destructive; the restore is part of every read. The whole row (1 to 2 KB per bank, 8 KB across the chips of a rank) now sits in the sense amplifiers: this is the row buffer.
A READ command then picks a column from the row buffer and sends a burst of data (16 transfers on a DDR5 sub-channel, which is one 64-byte cache line). If the next access falls in the same open row, it needs only the column access: a row-buffer hit, about 14 ns inside the chip. If it falls in a different row of the same bank, the controller must first PRECHARGE (close the row and reset the bit lines) and then ACTIVATE the new row: a row conflict, three timings in a row, about 40 to 50 ns. Adding the memory controller, the on-chip network and the caches' miss handling, a load from a CPU core sees roughly 80 to 100 ns, and more on large multi-socket servers.
The system hides this with parallelism. A channel has many banks (DDR5 has 32 banks per chip, in 8 bank groups), and the controller reorders requests to keep several banks busy at once and to group accesses to open rows. A modern CPU has several channels (12 for AMD EPYC Genoa, 8 for Intel Sapphire Rapids) and cores that track 10 to 20 outstanding misses each. Because of these layers, DRAM rewards sequential access (many hits in the open row) and punishes random access (a new row every time).
Charge in the cell does not last. Leakage through the access transistor and the capacitor's dielectric, including quantum tunneling of electrons through the very thin insulating layers, drains the cell. At normal temperature the weakest cells hold their value for tens to hundreds of milliseconds, so the standard requires that every row is refreshed within 32 ms (DDR5) or 64 ms (DDR4). The controller issues a refresh command about every 3.9 to 7.8 µs, and each one occupies the chip for 300 to 400 ns, so a few percent of the time (more in denser chips and at high temperature) is spent refreshing, and a request that arrives during a refresh waits.
HBM keeps the same cells but changes the packaging and the interface. A stack holds a base logic die and 8 to 16 DRAM dies, each thinned to a few tens of micrometers, connected by thousands of through-silicon vias and tiny solder microbumps. Each stack has 1,024 data pins in HBM3 (2,048 in HBM4) running at a modest 6.4 to 9.6 Gbit/s per pin (HBM4: up to 8). The processor and the stacks sit on a silicon interposer (for example TSMC's CoWoS) that carries these thousands of short wires; short wires need little drive power, so the energy per bit is lower than for DDR. Bandwidth per stack is pins times rate: 1,024 × 6.4 Gbit/s / 8 = 819 GB/s for HBM3, and 2,048 × 8 / 8 = 2 TB/s for HBM4. An H100 SXM has five active HBM3 stacks (80 GB, 3.35 TB/s). Blackwell B200 has 192 GB of HBM3E at 8 TB/s. NVIDIA has announced Rubin with 288 GB of HBM4 and up to about 22 TB/s.

example: First, bandwidth. A DDR5-4800 channel moves 8 bytes per transfer at 4.8 billion transfers per second: 38.4 GB/s. A server socket with 12 channels has 12 × 38.4 = 460.8 GB/s. Scanning a 100 GB table that sits in memory with sequential access takes at best 100 / 460.8 ≈ 0.22 s per socket. Random access is very different. A core that can keep 10 cache-line misses in flight, each taking 90 ns, gets 10 × 64 bytes / 90 ns ≈ 7 GB/s. That is Little's law: the data in flight equals the bandwidth times the latency. So one core doing pointer chasing (one miss at a time) gets 64 B / 90 ns ≈ 0.7 GB/s, 50 times less than the channel could give.
Now HBM. A model with 70 billion parameters stored in 8-bit weights occupies 70 GB. It fits in the 80 GB of one H100 but leaves little room for the KV cache, so real deployments use more GPUs or smaller weights. To generate one token at batch size 1, the GPU must read every weight once from HBM. At 3.35 TB/s this takes at least 70 GB / 3.35 TB/s ≈ 21 ms, so at most about 48 tokens per second per sequence, however fast the tensor cores are. With 16-bit weights (140 GB) the model needs two GPUs, and each reads half the weights in parallel, so the bound is again about 21 ms per token. With 4-bit weights (35 GB) it falls to about 10 ms.
Batching changes the picture. With a batch of 64 sequences, the same 70 GB of weights is read once and used for 64 tokens, so arithmetic per byte rises 64 times. The decode step stays near 21 ms but produces 64 tokens: about 3,000 tokens per second across the batch, until the KV cache, which grows with each sequence and each token, takes more bandwidth than the weights.
intuition: A huge warehouse with slow forklifts; fetching a shelf takes time, but grabbing more from the same shelf is quick.
A cell must be tiny to make memory cheap, and a tiny capacitor can only hold a small and leaking charge. All the machinery of DRAM follows from that: sense amplifiers that detect a faint signal, a row buffer that keeps the amplified row so more of it can be read cheaply, refresh to restore charge, and wide parallel banks to hide the wait. HBM follows from the other side: if the limit is the number of wires between the memory and the chip, then make the wires shorter and many more, by stacking and placing the memory next to the processor.
mistakes: People often think DRAM is "random access" with the same cost for any address. In fact the cost depends on the state of the row buffer: a hit is about three times faster inside the chip than a conflict, and sequential reads achieve many times the bandwidth of random reads. This is why data layout and access order matter.
People often think more memory capacity means more speed. In fact capacity and bandwidth are separate. Bandwidth comes from the number of channels (or HBM stacks) and their speed; one 128 GB DIMM in an eight-channel server is slower than eight 16 GB DIMMs. Filling all channels matters more than the total size.
People often think HBM is simply faster DRAM. In fact its latency is similar to DDR (a bit higher in many measurements). It wins on bandwidth by width and short wires. A workload limited by latency, such as pointer chasing, gains nothing from HBM.
People often think DRAM's refresh is a small detail. In fact refresh is a visible cost: it takes a few percent of the bandwidth, adds a latency tail when a request meets a refresh, and costs power in idle data centers. The needed refresh rate also rises with temperature, which is why hot servers throttle memory.
tradeoffs: Choose DDR5 DIMMs when you need capacity at a low cost per GB: a server can hold 1 to 6 TB per socket at a price per GB several times lower than HBM, with 40 GB/s per channel. Choose HBM when the workload needs bandwidth of 1 TB/s or more and a capacity of tens to hundreds of GB, as in AI training and inference. You pay several times more per GB, you cannot upgrade it (it is part of the package), and its total size is limited by the number of stacks that fit around the die.
Choose to add channels (more DIMM slots populated) before adding capacity when the application is bandwidth-bound; choose higher-capacity DIMMs, or a CXL memory expander, when the data set does not fit. CXL memory gives you more gigabytes at a higher latency (roughly 150 to 250 ns) and lower bandwidth, so it suits warm data, not the hot working set.
Choose GDDR (as on gaming and many inference cards) when you want 500 GB/s to about 1.8 TB/s at a lower price and can accept more power per bit; choose HBM for the top end. Choose to quantize weights and compress the KV cache when HBM capacity or bandwidth limits you, trading a small accuracy cost for a smaller footprint.
Choose ECC memory for servers and databases. It costs about 12% more chip capacity and a little latency, and it protects from the random single-bit flips that large fleets see regularly; it also reduces, but does not remove, the risk from Rowhammer.
friction: The memory wall is still the central limit. Latency has barely improved, bandwidth grows more slowly than arithmetic, and each new accelerator generation raises the arithmetic-to-bandwidth ratio. Capacity per chip grows slowly too: shrinking the cell is hard because a smaller capacitor holds less charge and leaks faster, and refresh overhead rises with density. DRAM scaling is slower than logic scaling, and the industry is moving toward 3D structures and new capacitor materials.
HBM is expensive and hard to make. Stacking 12 or 16 thinned dies reduces yield, the packaging (interposer, bonding, thermal) is a bottleneck, and heat from the stack is hard to remove because the hot logic die sits beside the DRAM, which prefers to stay cool. The supply is concentrated in three companies, and demand from AI has pushed capacity commitments years ahead. Cost per GB is several times that of DDR, so large-memory systems are expensive.
Security and reliability: Rowhammer and its successors (TRRespass, Half-Double and attacks on DDR5) show that vendor mitigations are heuristics. Soft errors cause silent data corruption in large fleets, which on-die and system ECC reduce but do not eliminate. Power is also a limit: refresh and I/O make memory a large share of server power at idle.
practice: Think of memory in terms of bandwidth, latency and capacity separately. Measure them with tools (Intel MLC, STREAM, lmbench) before designing around them. Make access sequential where you can: arrays rather than linked structures, columnar layouts, batch processing. Keep working sets in cache when possible. Populate all memory channels on servers (one DIMM per channel is often the fastest configuration), and keep NUMA locality in mind (see the NUMA concept).
For GPU work, estimate the bandwidth bound first: bytes moved divided by HBM bandwidth. If your kernel is within about 70% of that bound, it is memory-bound and arithmetic will not help; fuse kernels, use lower precision, or reduce the data. For LLM serving, budget HBM as weights + KV cache + activations; per token, the KV cache costs 2 × layers × KV heads × head dimension × bytes, which grouped-query attention and KV quantization shrink. Monitor GPU memory bandwidth utilization, not just compute utilization.
For data platforms, memory is cheap enough to cache hot data (Spark and Databricks disk caches, in-memory join sides) but not so cheap that you can ignore it: oversized Spark executors cause long garbage-collection pauses and spill. Use ECC servers, watch corrected-error counters (EDAC in Linux) as an early warning of a failing DIMM, and treat a rising rate as a replace-soon signal.

interview: Why has DRAM latency stayed almost flat for twenty years while bandwidth grew by 100 times? || Latency is set by the physics of the array: charging a long bit line from a small capacitor and sensing a small voltage, which scales poorly. Bandwidth can be increased by parallelism: more banks, wider interfaces, more channels, higher signalling rates, and prefetching a longer burst per access.
How would you find out whether a Spark or database job is limited by memory bandwidth or by CPU? || Measure with hardware counters (perf, Intel VTune or PCM): instructions per cycle, cache misses and memory bandwidth against the platform maximum measured by STREAM. Low IPC with bandwidth near the peak means a bandwidth limit; low IPC with low bandwidth and many misses suggests latency-bound pointer chasing.
Explain what a row hit, a row miss and a row conflict are, and how a memory controller exploits them. || A hit is an access to the currently open row; a miss is an access to a bank with no open row (activate then read); a conflict needs a precharge of another row first. The controller reorders requests (for example, First-Ready First-Come-First-Served) to group hits, interleaves addresses across banks and channels so sequential streams use all of them, and balances fairness against throughput.

The cost: a fixed memory size per package, high cost and low yield of stacking and packaging, heat that is hard to remove, and no user upgrade. It also ties supply to a few memory vendors and packaging lines.

Hardware has counters and extra refreshes (target row refresh), ECC, and shorter refresh intervals; software can isolate untrusted code in separate memory domains, keep page-table pages away from attacker-controlled memory, and use ECC servers. No mitigation is complete.

@@ numa
value: NUMA (non-uniform memory access) describes a computer in which every CPU can reach all of the memory, but some memory is closer than the rest. In a typical two-socket server, each socket has its own memory controllers and its own DIMMs. A core reads its local memory in about 80 to 100 ns. To read memory attached to the other socket, the request must cross a socket-to-socket link, and takes roughly 140 to 200 ns, with lower bandwidth. The program does not see this difference in the code. It sees one flat address space, and the cost shows up only as slowness.
It matters because the penalty is large and silent. Databases, JVM services, Kafka brokers and Spark executors that run on big machines often lose 20 to 50% of their throughput when threads and their data end up on different sockets. A well-known case is the MySQL "swap insanity" problem (Jeremy Cole, 2010): a server with plenty of free memory started swapping, because the operating system had filled one node and preferred to reclaim memory there instead of using the free memory of the other node. NUMA is the price paid for building machines with many cores and many memory channels, which a single shared bus could never feed.
For the layers above, NUMA shapes how big-machine software is built. General-purpose CPU servers (L1) expose it as nodes that you can bind processes to. Thread-per-core (shared-nothing) systems such as ScyllaDB and Seastar allocate each core's memory on its own node and never share data between cores, which avoids remote access by design. The memory hierarchy and caches (L3) explain the local side: NUMA adds one more, slower level in which remote DRAM sits behind the other socket's caches. The speed of light (L5) sets the floor: signals need time to cross a board and a link, and each extra hop adds more.
terms: NUMA node — a group of CPU cores together with the memory directly attached to them; often one per socket, sometimes several per socket.
Local access — a core reads memory attached to its own node.
Remote access — a core reads memory attached to another node, over an interconnect.
Interconnect — the link between sockets: Intel UPI (earlier QPI) or AMD Infinity Fabric (xGMI).
First-touch policy — the Linux default: a page is placed on the node of the CPU that first writes to it.
Interleave — spreading pages round-robin across nodes, so every thread gets an average of local and remote speed.
NUMA distance — a table of relative costs between nodes (10 means local; 20 to 32 is typical for remote), shown by numactl --hardware.
Cache coherence — the protocol that keeps each core's cached copies of memory consistent, which also crosses the interconnect.
Page migration — moving a page of memory from one node to another so it is close to the threads that use it.
Affinity (pinning) — fixing a thread or process to chosen cores or nodes so the scheduler does not move it.
history: Early multiprocessors were symmetric (SMP): all CPUs shared one memory bus, so every access had the same cost. This is simple, but the bus becomes the bottleneck at around 8 to 16 processors. Research machines broke this limit by giving every processor board its own memory and a scalable network between them, with directories to keep caches coherent. Stanford's DASH (Lenoski et al., 1992) demonstrated the design, and commercial machines followed in the 1990s: Sequent NUMA-Q and SGI Origin 2000 (1996). These were large, expensive servers.
NUMA reached ordinary servers in 2003, when AMD's Opteron put a memory controller inside every CPU and linked sockets with HyperTransport. Any two-socket Opteron server was a NUMA machine. Intel followed with Nehalem and QuickPath Interconnect in 2008. Linux gained NUMA support in the 2.4 and 2.6 kernels (libnuma, numactl, memory policies), and automatic NUMA balancing arrived in kernel 3.8 (2013): the kernel samples page accesses and moves tasks or pages toward each other.
Later, NUMA moved inside the socket. AMD EPYC (2017) packages several chiplets, each with its own cache and a path to the memory controllers, and offers a BIOS setting (NPS1, NPS2, NPS4) that presents the socket as 1, 2 or 4 NUMA nodes. Intel offers a similar sub-NUMA clustering mode. Cloud providers now sell instances that span two sockets, with virtual NUMA exposed to the guest. Accelerators add another layer: a GPU or a network card is attached by PCIe to one socket, so I/O has a "local" socket as well.
how: Hardware first. Each socket contains cores, a shared last-level cache and memory controllers with their DIMMs. Sockets are connected by one or more point-to-point links. A load that misses all caches goes to the home node of the address, which is determined by the physical address: the firmware tells the operating system which address ranges belong to which node (the ACPI SRAT and SLIT tables). If the home node is local, the request goes to the local memory controller. If remote, it crosses the link to the other socket, whose memory controller reads the line and sends it back. A coherence protocol (snooping or a directory) must also check that no other cache holds a newer copy. These extra steps cost roughly 50 to 100 ns on top of the local access, and the link has less bandwidth than the sum of the local memory channels.
The wire itself is not the main cost. A signal travels about 15 cm per nanosecond on a circuit board, so a 30 cm path costs 2 ns each way. The remote penalty comes from the serialization onto the link, the coherence lookups and the extra hops of the interconnect, as well as queuing when the link is busy. The speed-of-light limit explains why distance eventually matters, and why memory attached through a cable or a switch (rack-scale machines, CXL) is slower again, at about 5 ns per metre of cable plus the protocol cost.
Caches make the cross-socket cost visible even when no data is placed badly. The memory hierarchy gives each core private L1 and L2 caches and a shared L3 per socket. When a core on socket 1 writes a cache line that socket 0 holds, the coherence protocol must invalidate or transfer that line over the link. A lock or counter that is shared by threads on both sockets therefore bounces between them, and each bounce costs roughly the remote latency, 100 to 200 ns, instead of the 10 to 40 ns of a transfer inside one socket. This is why a shared atomic counter that scales to 16 threads on one socket can slow down when threads are spread over two.
The distance table is only a coarse guide. Firmware reports one number per pair of nodes, but real costs depend on the load: an idle link may add 60 ns, and a busy one may add several times more because requests queue. Chiplet designs make the picture more detailed still. On an AMD EPYC with the BIOS in single-node mode (NPS1), memory is interleaved across all channels of the socket, so every core sees the same average latency but no core is close to its data. In NPS4 mode, each quarter of the socket has its own channels, so accesses are faster for threads placed in that quarter, and slower for threads placed elsewhere. The operating system sees four nodes and the application must respect them.
Software next. Linux exposes nodes through numactl --hardware, lscpu and /sys/devices/system/node. Memory is allocated lazily: malloc reserves address space, and the physical page is placed when a thread first touches it, by default on that thread's node (first touch). This is good if each thread initializes its own data, and bad if one thread initializes everything. A single-threaded loader that fills a big table puts all pages on node 0; later, worker threads on both sockets read it, and half of them pay the remote cost while all of them share one set of memory channels.
You can control placement. numactl --cpunodebind=0 --membind=0 runs a process on node 0 with node 0 memory. numactl --interleave=all spreads pages round-robin, which gives predictable average performance and balanced use of all memory channels, at the cost of never being fully local. In code, libnuma functions (numa_alloc_onnode) and the mbind and set_mempolicy system calls do the same per allocation. Automatic NUMA balancing makes the kernel try to fix bad placement by unmapping pages briefly, watching which CPU faults on them, and then migrating the page or the task. It helps long-running, stable workloads, and can hurt others through the cost of the faults and migration, so database vendors often turn it off and pin memory by hand.
Practical systems use three strategies. Partition: run one process (one JVM, one broker) per NUMA node, each bound to the node's cores and memory, so there is no remote access. Share-nothing: give each core its own data and memory, and pass messages to other cores (thread-per-core design). Interleave: when the application cannot be partitioned, interleave memory to avoid hot nodes. Network cards and GPUs matter as well: DMA between a NIC on socket 0 and a buffer on node 1 crosses the link, so high-speed network threads should run on the NIC's socket (nvidia-smi topo -m and lstopo show the affinity).

example: A server has two sockets, each with 8 DDR5-4800 channels (about 307 GB/s per socket) and 128 GB of memory. Local latency is 90 ns, remote latency is 150 ns. A database starts with one loader thread on node 0 that reads 100 GB of data into memory. By first touch, all 100 GB sits on node 0. Then 64 query threads start, 32 on each socket, and do random reads.
Latency: the 32 threads on node 0 see 90 ns; the 32 on node 1 see 150 ns. The average is (90 + 150) / 2 = 120 ns, which is 33% slower than the 90 ns an ideal placement would give. If each thread is limited by latency (one miss in flight), throughput is proportional to 1 / latency: the node 1 threads run at 90 / 150 = 60% of the node 0 speed.
Bandwidth: all traffic now goes through the 8 memory channels of node 0, so the machine's reading capacity is 307 GB/s instead of 614 GB/s. The remote half must also pass through the interconnect, which may carry roughly 100 to 150 GB/s in each direction; if the node 1 threads want more than the link supplies, they queue. A scan-heavy workload can drop by 40 to 50%, far more than the latency alone suggests.
Now fix it in three ways. First, interleave: numactl --interleave=all puts half of the pages on each node, so both sets of channels work. Every thread sees half local and half remote accesses, average 120 ns, but bandwidth is the full 614 GB/s. Second, partition: split the data into two halves, run two processes, one per node, each bound to its own node; every access is local at 90 ns and bandwidth is again 614 GB/s. Third, parallel first-touch: have each worker thread, pinned to its node, load its own part of the data, so pages land where they will be used. The second and third options give the best latency, and the first is the easiest.
intuition: Your own kitchen is closer than the neighbour's, even if you're allowed to use both.
Memory that is near to a processor is cheap to reach, and memory that is far costs a trip over shared links. Once a machine has too many cores for one bus or one memory controller, it must be split into pieces, each with its own memory, and the pieces must be joined by links. This keeps the system scalable, but it makes distance part of the performance model. A programmer who keeps data near the threads that use it gets the full benefit of the machine, and one who ignores it still gets correct results, only slower.
mistakes: People often think NUMA is only about large or exotic servers. In fact any two-socket server is NUMA, and many single-socket chips are too: AMD EPYC with chiplets can expose 2 or 4 nodes inside a socket, and Intel parts do so in sub-NUMA clustering mode. Check with lscpu or numactl --hardware before assuming.
People often think the operating system will place memory well on its own. In fact the default first-touch policy is only as good as your initialization pattern, and the scheduler may migrate threads away from their memory. Automatic NUMA balancing helps some workloads and hurts others.
People often think remote memory is always the problem. In fact for bandwidth-heavy workloads the larger risk is concentrating all memory on one node, which leaves half of the memory channels idle. Interleaving can beat strict local placement when threads share data across sockets or when load is uneven.
People often think pinning threads is enough. In fact pinning the CPU without controlling where memory is allocated gives nothing, because pages placed earlier stay where they are. You must bind or interleave memory as well, and also place the NIC and GPU interrupts and DMA buffers on the right node.
tradeoffs: Choose strict binding (one process per node, --membind) when the workload is partitionable (per-node Kafka brokers, per-socket database instances, sharded caches) and latency matters. You get the lowest and most predictable latency. You give up flexibility: a node can run out of memory while the other has free space, and rebalancing is manual.
Choose interleaving when the workload is a single large shared process (a JVM with one big heap, an in-memory database) that cannot be split. Memory use is balanced and results are predictable, at the cost of about half the accesses being remote. Choose first-touch with parallel initialization when threads own their data and stay on their cores; it gives the best result without any binding, but breaks when the scheduler moves threads.
Choose automatic NUMA balancing for mixed, long-lived workloads where you cannot tune by hand, and accept fault overhead and some jitter. Turn it off for latency-sensitive databases that you have already pinned, since page migration can cause pauses.
Choose a single-socket server when the workload fits in one socket's cores and memory (up to 128 cores and 12 channels for current AMD parts): you remove the NUMA issue completely and often get a lower cost per core. Choose two sockets when you need more than that: more memory or more cores in one machine than a single socket offers, and accept the remote penalty.
friction: NUMA problems are hard to see. Nothing fails; the program is just slower, with unexplained variation between runs, and the effect depends on the BIOS settings, the kernel version and where the scheduler put the threads. The standard tools (numastat, perf, Intel PCM, numa_maps) give counters but you must know what to look for, such as the share of remote accesses and the imbalance in memory use per node.
Virtualization and containers hide the topology. A VM may see a single flat node while its vCPUs and memory sit on different physical sockets; hypervisors can expose virtual NUMA, but only if the VM fits and is configured for it. Containers on Kubernetes need the CPU and topology manager policies to get aligned cores, memory and devices. Garbage-collected runtimes move objects, so the JVM option -XX:+UseNUMA only helps for some collectors and workloads.
The model is also getting more complex, with chiplets, cache hierarchies that are not uniform within a socket, memory tiers (DRAM, CXL, HBM) and accelerators with unified memory. Each tier adds another distance. The tuning knowledge is also fragile: a setting that works on one CPU generation can be wrong on the next.
practice: Start by looking: run numactl --hardware and lscpu to see nodes, distances and which cores belong to which node, and numastat -p <pid> to see where a process's memory lives. Check the BIOS or cloud instance type for the number of sockets and the NUMA mode. If you cannot see a remote-access problem in counters, do not tune.
For services that run on big machines, prefer one instance per node with binding (numactl, systemd CPUAffinity and NUMAPolicy, or container cpuset and memory node settings) over one giant instance. This is common for Kafka brokers, Cassandra or Redis nodes, and JVM services. For a single large process, use interleave first, then measure. In Java, try -XX:+UseNUMA with ParallelGC or G1, and use pre-touching (-XX:+AlwaysPreTouch) so the heap is placed at start in a predictable way.
In your own code, initialize data in parallel with the same thread layout as the computation, and keep threads pinned. Avoid sharing mutable data between sockets: false sharing and lock contention across sockets cost several times more than within one. For network and GPU work, run the I/O threads and the buffers on the node of the device. In the cloud, prefer instance sizes that fit within one socket for latency-critical work, and measure before paying for the largest instance size, which is often two sockets.
quiz: What does "non-uniform" mean in NUMA? || Every CPU can address all memory, but the access time depends on which node the memory is attached to. Local memory is faster (about 90 ns) than memory on another socket (about 150 ns or more), and the remote path has less bandwidth.
What is the first-touch policy and why can it cause trouble? || Linux places a physical page on the node of the CPU that first writes to it. If one thread initializes a big data set, all pages land on its node, and threads on other nodes then read remotely and all load one set of memory channels.
Why does interleaving memory give predictable performance, and what does it cost? || Pages are spread round-robin over all nodes, so every thread sees the same mix (about half local, half remote) and all memory channels are used. It costs the benefit of local access: no thread is ever fully local.
A two-socket server has 90 ns local and 150 ns remote latency. A latency-bound workload runs half its accesses remote. What is the average latency and the slowdown against all-local? || (90 + 150) / 2 = 120 ns, which is 120 / 90 = 1.33 times as long, a 33% slowdown (throughput 75% of the all-local case).
When would you run one broker per NUMA node, and when would you use a single process with interleaving? || One per node when the work can be partitioned (separate partitions or shards) and you want the lowest latency; a single interleaved process when the state is one big shared structure that cannot be split, accepting average-case latency.
interview: A service is 30% slower on a new two-socket server than on the old single-socket server, although the new CPUs are faster. How do you diagnose it? || Check numactl --hardware and numastat for the memory split, and perf or PCM for remote access share and memory bandwidth per node. Likely causes: first-touch placement from a single loader thread, threads migrating across sockets, a NIC on the other socket. Test with numactl --interleave=all, then with per-node instances.
How does the operating system decide where to put a page, and how can an application change that? || By default, the page goes to the node of the first-touching CPU (local allocation policy), falling back to other nodes when full. Applications can use numactl, mbind, set_mempolicy or libnuma to bind, prefer or interleave memory, and can move pages with move_pages or let automatic NUMA balancing migrate them.
Why can a NUMA machine swap while another node has free memory? || With strict or local-only reclaim (zone_reclaim_mode) and a large allocation on one node, the kernel can reclaim page cache or swap on the full node instead of allocating from the free node. This was the MySQL swap-insanity issue. The fix is interleaving, or disabling zone reclaim, and making sure memory is balanced.
How does thread-per-core design avoid NUMA problems? || Each core owns its data and memory (allocated on its own node), requests are routed to the owning core by key, and cores communicate by message passing. So no data is shared across sockets, there is no cross-socket locking, and all accesses are local by construction. The cost is load imbalance and the complexity of cross-core requests.
Is remote memory slow because of the speed of light? || Only in a minor way. A board trace adds a few nanoseconds. Most of the penalty comes from interconnect serialization, coherence protocol steps, extra hops and queuing. Distance becomes the main part only at larger scales, such as rack-scale or CXL-attached memory.

value: Storage devices are where data survives power loss, and two kinds dominate. A hard disk drive (HDD) stores bits as tiny magnetized regions on spinning platters and reads them with a head on a moving arm. A solid-state drive (SSD) stores bits as electric charge in NAND flash cells and has no moving parts. Their costs differ by orders of magnitude. A random read on an HDD takes about 8 to 12 ms, because the arm must move and the platter must turn; an NVMe SSD does the same read in about 80 to 100 µs, and does hundreds of thousands to a million of them per second. Sequential reads on an HDD reach 150 to 280 MB/s, but still lose to an SSD at 3 to 14 GB/s.
These numbers shape nearly all storage software. Because a disk seek is 100,000 times slower than a CPU cycle, databases use B-trees to touch few pages, logs and LSM trees to turn random writes into sequential ones, and large caches to avoid the device altogether. SSDs changed some of these assumptions, since random reads became cheap, but they added new ones: flash can only be erased in large blocks, wears out, and needs a translation layer (FTL) in firmware to hide this. Cost per GB still decides the tiering: HDD for cold data in object storage (S3-class systems, backups, data lakes), SSD for hot data and databases.
For the layers above, the device defines what "durable" means. The write-ahead log, fsync, file systems and journaling all assume a particular behavior of the device: that a flushed write survives a power cut. The layers below explain why the devices work. Magnetism (L5) explains how a head senses and flips the direction of a magnetic domain on a platter. Quantum tunneling (L5) is how electrons are pushed through a thin oxide onto the flash cell and pulled off again. Oxides and high-k dielectrics (L5) are that insulating layer, which both holds the charge for years and is damaged a little by each write, which gives flash its limited endurance.
terms: Platter — a rigid disk coated with magnetic material; an HDD has one to ten of them, spinning at 5,400 to 7,200 rpm (10,000 to 15,000 in older server drives).
Seek time — the time to move the head to the right track, roughly 3 to 9 ms on a modern drive.
Rotational latency — the wait for the right sector to arrive under the head; on average half a turn, 4.17 ms at 7,200 rpm.
NAND flash — non-volatile memory made of transistors that hold charge; organized into pages and blocks.
Page — the smallest unit of NAND that can be read or programmed (4 to 16 KB).
Block (erase block) — the smallest unit that can be erased; hundreds to thousands of pages, several MB or more.
P/E cycle — one program and erase cycle of a block; each cell survives a limited number of them (about 1,000 to 3,000 for TLC).
TLC / QLC — flash cells that store 3 or 4 bits by distinguishing 8 or 16 charge levels; denser and cheaper, but slower and less durable than SLC (1 bit).
Queue depth — the number of I/O requests outstanding at once; SSDs need many to reach full speed.
IOPS — input/output operations per second, usually quoted for random 4 KB reads or writes.
history: Hard disks began with the IBM 305 RAMAC in 1956: 50 platters of 24 inches, about 5 MB of data, in a cabinet the size of two refrigerators. The Winchester design (IBM 3340, 1973) put the head on an air bearing that floats a few nanometers above the platter and made the drive sealed and reliable. Capacity per drive grew by millions of times over 60 years. Key steps were thin-film and then magnetoresistive heads, giant magnetoresistance (Fert and Grünberg, 1988, Nobel prize 2007) which allowed much smaller bits to be read, and perpendicular recording (about 2005). Today's drives hold 30 TB or more using shingled tracks and heat-assisted recording (HAMR). Seek time and rotation speed, in contrast, changed little after the 1990s, so capacity grew far faster than random I/O speed.
Flash memory was invented by Fujio Masuoka at Toshiba in the early 1980s; NOR flash came first (1984), and NAND flash (1987) trades random access for density. Flash first replaced small devices (cameras, phones, USB sticks). The Intel X25-M (2008) made SSDs practical for PCs and servers. Cells moved from one bit (SLC) to two, three and four bits per cell, and in 2013 Samsung's V-NAND stacked the cells in vertical layers; recent chips have more than 200 layers. NVMe (specification 1.0 in 2011) replaced the old disk interface with a design for flash: tens of thousands of queues over PCIe.
The 2000s and 2010s also brought a gradual rethink of software. Early file systems and databases assumed the disk model, and many SSD-aware designs followed: log-structured file systems (F2FS), LSM trees, and later zoned storage. Intel's Optane (3D XPoint, 2017) tried a faster non-flash memory but was discontinued in 2022. As of 2026, the pattern is stable: NVMe flash for performance, HDD for capacity, tape for archives.
how: Start with the hard disk. Data lives on concentric tracks of the spinning platters, in sectors (512 bytes or 4 KB). The head is carried by an arm; a voice-coil actuator moves it to the right track in a seek. Then the controller waits until the wanted sector passes under the head. A random read thus costs seek (3 to 9 ms) plus rotational latency (4.17 ms on average at 7,200 rpm) plus a short transfer, about 8 to 12 ms in total, or 80 to 120 random operations per second. A sequential read pays the seek once and then streams at the platter's speed under the head, 150 to 280 MB/s, faster on the outer tracks where more sectors pass per turn. So sequential access can be 500 times faster per byte than random access of 4 KB blocks. The drive also reorders queued requests (native command queuing) to shorten the arm's path, which helps a little.
Now the SSD. A NAND cell is a transistor with an extra insulated layer (a floating gate, or in 3D NAND a charge-trap layer) that can hold electrons. To program a cell, the controller applies a high voltage (around 20 V), which makes electrons tunnel through the thin oxide into the storage layer (quantum tunneling). More electrons raise the voltage at which the transistor turns on. To read, the controller applies reference voltages and sees whether the transistor conducts; with TLC, it distinguishes 8 charge levels to read 3 bits. To erase, a high voltage on the substrate pulls the electrons back out through the oxide, and this works only on a whole block at once. Each pass of electrons damages the oxide a little, until the cell cannot hold charge reliably: this limits endurance to roughly 100,000 cycles for SLC, 3,000 to 10,000 for MLC, 1,000 to 3,000 for TLC and a few hundred to 1,000 for QLC.
These physics give flash its access rules. Reads work on pages (4 to 16 KB) and take about 50 to 100 µs. Programming works on pages too, but a page can be written only once after its block is erased, and pages in a block are written in order. Programming takes 0.4 to 1 ms or more for TLC. Erasing works on a whole block (several MB) and takes several milliseconds. So an SSD cannot overwrite data in place; updating 4 KB means writing the new data to a fresh page somewhere else and marking the old page stale. The flash translation layer, a firmware component inside the drive, hides this, and is the next concept in this map.
The speed of an SSD comes from parallelism. A controller has 8 to 16 channels to flash, each channel serves several dies, each die has several planes that work in parallel. Hundreds of page operations can be in flight, so one operation of 80 µs becomes a million operations per second at high queue depth (Little's law: IOPS = queue depth / latency, so 1,000,000 IOPS at 80 µs needs about 80 requests in flight). NVMe lets the host open up to 65,535 submission queues with up to 65,536 entries each, so many CPU cores can submit I/O without locks; PCIe 4.0 x4 gives about 7 GB/s and PCIe 5.0 x4 about 14 GB/s.
Persistence adds a further layer. A device acknowledges a write only when its data reaches a safe place. Enterprise SSDs contain capacitors that give enough energy to flush their volatile buffer after power loss. Consumer drives and HDDs may acknowledge writes from a volatile cache, which is why the operating system issues a flush command when software calls fsync, and why durability depends on the device telling the truth.

example: Compare the two devices on 4 KB random reads. A 7,200 rpm HDD: average seek 4 ms plus half a rotation of 4.17 ms is about 8.2 ms. That is 1 / 0.0082 ≈ 122 reads per second, and 122 × 4 KB ≈ 0.5 MB/s. The same drive reads sequentially at 250 MB/s, 500 times more bytes per second. An NVMe SSD with 80 µs latency and 64 requests in flight: 64 / 80 µs = 800,000 IOPS, or 3.2 GB/s from 4 KB reads. With only one request in flight, it does 1 / 80 µs = 12,500 IOPS, 64 times less. So queue depth matters for SSDs and hardly at all for a single HDD.
Now a B-tree lookup with three uncached levels. On the HDD, three dependent reads cost 3 × 8 ms = 24 ms, and the disk can serve about 40 such lookups per second. On the NVMe SSD, 3 × 80 µs = 240 µs per lookup per thread; with 64 threads the drive can do about 64 / 240 µs ≈ 260,000 lookups per second. This 6,500-fold difference is why moving a database from HDD to SSD changes its design limits; and why caching the upper levels of the tree matters less on SSD.
Now a cost view for a 100 TB data lake. At roughly 20 TB per HDD, you need 5 drives, each giving about 250 MB/s sequentially: 1.25 GB/s total, a full scan takes 100 TB / 1.25 GB/s ≈ 80,000 s, about 22 hours. A 15 TB NVMe SSD costs several times more per TB (the exact ratio varies by year, often 3 to 6 times), and 100 TB takes 7 drives, each reading 6 GB/s sequentially: 42 GB/s total, a scan in about 40 minutes. For cold data scanned rarely, HDD wins on price; for data scanned daily by many users, SSD can win on cost per query. Public cloud object stores (S3) hide this choice, but their latency of tens of ms per request reflects the disk tier.
Last, write endurance. A 4 TB TLC drive rated at 1,000 P/E cycles can take roughly 4 PB of writes if there were no write amplification. At a write amplification of 3 (see the FTL concept), the host can write about 1.3 PB. A database that writes 2 TB per day uses that in about 650 days, under two years. So enterprise drives are rated in drive writes per day (DWPD), and you choose the rating to match your write rate.
intuition: A record player (find the track, then it streams) versus a wall of light switches you can flip in any order.
A hard disk is a mechanical device: moving the arm and waiting for the platter take milliseconds, but once the head is in place data flows steadily. Everything follows from that shape: batch work into long sequential runs. Flash has no moving parts, so any page is equally near, but its physics ask for care: charge is pushed through an oxide that wears, and removal needs a whole block. The software rules have a common shape for both devices: write large, sequential, append-style units, avoid tiny random updates in place, and keep many requests in flight.
mistakes: People often think SSDs have no sequential-versus-random difference. In fact random small writes are still costlier than large sequential ones: they cause more write amplification and garbage collection, and small reads cannot use all flash channels unless the queue is deep. The gap is a factor of 2 to 10 instead of a factor of 500, but it is real.
People often think an SSD is simply a faster disk with the same behavior. In fact it has different failure modes: wear-out from erase cycles, read disturb and retention loss, latency spikes during internal garbage collection, and a risk of losing data in flight when power fails on a drive without capacitors. Its capacity and speed can also change as it fills.
People often think a flushed write is always on stable media. In fact a drive may acknowledge from a volatile cache, and consumer devices have been caught ignoring flush commands. Durability needs a device with power-loss protection, correct fsync and flush handling, and testing.
People often think HDDs are obsolete. In fact they still hold most of the world's data at roughly one third to one sixth of the price per TB of SSDs, and their sequential bandwidth is good. They are the right choice for cold data, backups, large sequential scans and log archives, as long as access is large and sequential.
tradeoffs: Choose HDD for capacity-dominated, sequentially accessed, cold data (data lakes read in 128 MB+ chunks, backups, video archives), where the price per TB is the deciding factor. You give up random access: plan for 100 IOPS per spindle, and design with large I/Os and an SSD or memory cache in front. Choose SSD for anything with random access, small objects, or latency targets below 10 ms: OLTP databases, indexes, metadata stores, shuffle spill and caches.
Choose TLC for general server use and QLC for read-heavy, write-light data (large read-only datasets, warm object storage) where the lower cost per GB is worth the lower endurance (a few hundred to 1,000 P/E cycles) and slower writes. Choose SLC mode or a high-endurance enterprise drive (3 DWPD or more) for write-heavy logs, journals and database write-ahead logs.
Choose NVMe over SATA SSD when you need more than 550 MB/s or more than about 100,000 IOPS, or deep parallel queues for many cores. A SATA SSD still suits boot drives and modest workloads at lower cost. Choose local NVMe (instance storage) for the lowest latency and scratch data, and choose network-attached block storage when the data must survive instance loss and you accept 0.5 to 2 ms latency and lower IOPS per volume.
Choose over-provisioning (leaving 10 to 30% of the drive unused) for write-heavy loads: you give up capacity and gain lower write amplification and steadier latency.
friction: Latency tails are the main practical trouble on SSDs: a read that normally takes 80 µs can take milliseconds when it queues behind a block erase or garbage collection in the same die. Write amplification, wear and the dependence on drive fill level make performance hard to predict: a drive that is 90% full behaves worse than an empty one. Vendor numbers are measured on fresh drives with ideal workloads, and steady-state numbers can be several times lower.
Reliability is subtle. Flash errors rise with wear, temperature and retention time, and strong error-correcting codes (LDPC) hide this until they cannot; a failing SSD may fail suddenly. HDDs fail mechanically, with an annual failure rate near 1 to 2% in large fleets (Backblaze publishes data), and sector errors can appear silently, so systems add checksums and replication. Silent corruption, firmware bugs and misreported flushes have caused real data loss, and erasure coding and scrubbing are needed above the device.
Economics change over time. NAND prices swing with supply and demand, and demand from AI data centers can push prices up. Density gains are slowing: more bits per cell cost endurance and speed. For HDDs, higher capacity at the same random IOPS means the IOPS per TB keeps falling, so a 30 TB drive is a poor choice for a hot dataset. Finally, the software contract with the device is complex ("The Unwritten Contract of Solid State Drives" lists five rules): a program that looks sequential to the file system may still be random to the device.
practice: Know your numbers: HDD about 100 IOPS and 200 MB/s; NVMe SSD about 100 µs latency, 500K to 1M IOPS, 3 to 14 GB/s; DRAM about 100 ns. Choose block sizes accordingly: 128 KB to 1 MB or larger I/Os for HDD, 4 to 16 KB aligned I/Os for SSD, and align partitions and file-system blocks to the device page. Prefer append-only logs and log-structured designs, batch small writes, and issue many parallel requests to SSDs (async I/O, io_uring, multiple threads) instead of one at a time.
Measure with fio using the real block size, mix and queue depth, and run long enough to reach steady state (hours for a full drive), not just a quick test on a fresh one. Watch p99 and p99.9 latency, not only throughput. Use iostat (await, aqu-sz, %util) and the device's SMART data: wear level (percentage used), media errors, and temperature. Alert before an SSD reaches its endurance rating. Enable TRIM or discard (periodic fstrim) so the drive knows which blocks are free, and leave some space unallocated.
For durability, use drives with power-loss protection for databases, keep write caches configured as your database expects, and test with power-failure tools. Replicate or erasure-code across devices and machines, and verify with checksums. In cloud systems, put hot data on local NVMe or high-IOPS volumes, warm data on standard SSD volumes, and cold data on object storage, and check IOPS and throughput limits per volume, which are often the real bottleneck.

@@ ftl
value: The flash translation layer (FTL) is the firmware inside every SSD that makes raw NAND flash look like an ordinary disk. The operating system sees a flat array of logical blocks, numbered 0 to N and rewritable in any order. The flash chips underneath cannot do that: a page can be written only once after its whole block is erased, erasing works on blocks of several MB, and each block survives only a limited number of erase cycles. The FTL closes this gap with a mapping table, a log-structured write path, garbage collection and wear leveling.
Everything an engineer notices about SSD behavior is an FTL effect. Write amplification (the drive writes more bytes to flash than the host sent), the slowdown of a nearly full drive, the sudden latency spike of a normal read, the benefit of TRIM, the endurance rating in drive writes per day, the value of leaving some space unused: all come from what the FTL must do to keep the "rewrite anywhere" illusion. A typical SSD has an ARM-class controller with several cores and 1 GB of DRAM per TB of flash that holds the mapping, so the FTL is a small storage engine of its own, hidden from you.
The FTL stands on two concepts. Storage devices (L3) provide the rules of NAND: pages, blocks, erase-before-write and parallel channels, which the FTL must respect. Quantum tunneling (L5) explains the wear: each program and erase pass pushes electrons through a thin oxide and damages it a little, so the FTL counts erases per block and spreads them out. The layer above is the NVMe SSD (L0), which ships the FTL as firmware and exposes commands for TRIM, namespaces and, in newer drives, zones and data placement hints that let the host share the FTL's job.
terms: Logical block address (LBA) — the block number the host uses; the FTL maps it to a physical flash page.
Mapping table (L2P) — the table from logical to physical pages; typically 4 bytes for each 4 KB page, so 1 GB of DRAM per 1 TB of flash.
Garbage collection (GC) — choosing a block with many stale pages, copying its still-valid pages elsewhere and erasing it to make free space.
Write amplification (WA) — flash bytes written divided by host bytes written; it is at least 1 and often 2 to 5.
Over-provisioning (OP) — flash capacity that the host cannot see, kept as spare space for GC; typically 7% to 28%.
Wear leveling — spreading erases evenly over all blocks so none wears out early.
TRIM (deallocate) — a host command saying that certain logical blocks no longer hold useful data, so GC need not copy them.
Stale (invalid) page — a physical page whose logical block has been rewritten elsewhere.
Zoned namespace (ZNS) — an NVMe interface in which the host writes sequentially inside zones and manages garbage collection itself.
Bad block — a flash block that fails and is retired; drives keep spares to replace them.
history: Flash started as a replacement for read-only memory, but the first flash cards (late 1980s, early 1990s) needed software to be usable as a disk. M-Systems (Israel) and others introduced flash translation layers in the mid-1990s, and a flash translation layer specification existed for PCMCIA flash cards. The idea was borrowed from log-structured file systems (Rosenblum and Ousterhout, 1992): never overwrite, always append, and clean up later. Raw flash file systems such as JFFS and YAFFS did the same job in the operating system for embedded devices.
Research in the 2000s turned FTL design into a field. Gal and Toledo's 2005 survey classified algorithms by mapping granularity: block mapping (small table, but a one-page update forces a whole-block rewrite), page mapping (large table, flexible) and hybrid log-block schemes (such as FAST) that used a few log blocks. The DFTL paper (Gupta, Kim and Urgaonkar, 2009) kept a page-level map but cached only its hot part in RAM. Agrawal and colleagues (2008) explained the performance tradeoffs of parallelism, striping and garbage collection, and Hu and others (2009) and Desnoyers (2012) modeled write amplification mathematically. As DRAM got cheap, enterprise SSDs went to a full page-level map in DRAM.
In the last ten years the question became who should run the FTL. Open-Channel SSDs (Linux LightNVM, around 2017) moved it to the host and were hard to use. NVMe Zoned Namespaces (ratified 2020) and Flexible Data Placement (FDP, NVMe technical proposal 4146, ratified 2022) are the compromises: the host gets an interface that matches the flash better, and the drive keeps the low-level work such as error correction and wear. The ZNS paper by Bjørling and colleagues (USENIX ATC 2021) showed RocksDB write throughput 2 times higher and 99.9th percentile read latency at least 2 to 4 times lower on a ZNS drive than on a normal block-interface drive with the same hardware.
how: The FTL has four jobs. The first is address mapping. Each host write to LBA x is placed in the next free page of an open block, and the table entry for x is changed to point at that physical page. The old physical page becomes stale. Reads look up the table (a DRAM access, about 100 ns) and read the page. A page-level map needs 4 bytes per 4 KB page, which is why a 4 TB drive carries about 4 GB of DRAM. To survive a power cut, the FTL also stores each page's logical address in a small spare area next to the data, and journals changes to the table, so that it can rebuild the map after a crash. Enterprise drives have capacitors so that the table and buffered writes can be saved when power fails.
The second job is the write path. Because pages inside a block must be written in order, and flash is fast only when many chips work at once, the FTL collects incoming writes in a buffer and stripes them across channels and dies, filling an open block on each. This is a log-structured design: the drive turns random host writes into sequential writes on flash. It is the reason a fresh SSD absorbs random writes nearly as fast as sequential writes. Many drives also write the first copy in a fast SLC-mode region and move it to TLC or QLC later, so bursts are fast and sustained writes are slower.
The third job is garbage collection. Over time blocks become partly stale. When the number of free blocks falls below a threshold, the FTL picks a victim block (the greedy policy picks the one with the fewest valid pages, and cost-benefit policies also consider age), copies its valid pages to a fresh block, and erases it. If the victim has a fraction u of valid pages, then for every (1 − u) pages of space freed, u pages are copied. So the write amplification is 1 / (1 − u): u = 0.5 gives 2, u = 0.8 gives 5. Over-provisioning keeps u low: with more spare blocks, blocks wait longer, more of their pages go stale, and victims are emptier. With uniform random writes and greedy GC, a rough estimate is a WA of 7 or more at 7% spare space and about 2.5 to 3 at 28% (the exact number depends on the controller). Sequential and hot-cold separated workloads do much better, with a WA close to 1.
The fourth job is wear leveling and health. The FTL counts erases per block. Dynamic wear leveling sends new writes to the least-worn free blocks; static wear leveling also moves rarely changed (cold) data off lightly worn blocks so those blocks can take new writes. A block that fails is retired and replaced from a spare pool. Because raw flash makes bit errors that grow with wear, retention time and temperature, each page carries error-correcting code (BCH in older drives, LDPC in recent ones). The FTL also retries reads with shifted voltages, refreshes data that has sat too long, and watches for neighbouring-page disturbance from heavy reads.
The host can help. TRIM tells the drive that deleted file blocks are free, so GC does not copy them and WA falls. Aligning writes to the drive's page size and writing large sequential chunks avoids partial-page work. ZNS and FDP let the host group data that dies together: if all data in a zone or reclaim unit is deleted at the same time, GC finds blocks that are entirely stale and has nothing to copy. A log-structured database such as RocksDB does exactly this when it deletes whole SSTable files.

example: Take a toy drive with 6 flash blocks of 4 pages each (24 pages) and a logical size of 16 pages (LBA 0 to 15), so the spare space is 8 pages. Rule: always keep one erased block as landing space; run GC when only one erased block remains.
Step 0: the host writes LBA 0 to 15 in order. Block B0 holds LBA 0 to 3, B1 holds 4 to 7, B2 holds 8 to 11, B3 holds 12 to 15. B4 and B5 are erased. 16 host writes, 16 flash writes.
Step 1: the host rewrites LBA 1, 6, 11 and 2. They go to B4 as new pages. The old copies are stale: B0 has only LBA 0 and 3 valid, B1 has 4, 5, 7 valid, B2 has 8, 9, 10 valid, B3 is fully valid. Only B5 is erased, so GC must run.
Step 2: GC picks the block with the fewest valid pages, B0 (2 valid). It copies LBA 0 and 3 into B5 (2 extra writes) and erases B0. Now B0 is erased and B5 has two free pages.
Step 3: the host rewrites LBA 13 and 14. They fill the rest of B5. Now B3 has only LBA 12 and 15 valid, and again only one erased block (B0) remains.
Step 4: GC picks B3 (2 valid), copies LBA 12 and 15 into B0 (2 extra writes), and erases B3.
Count for steps 1 to 4: 6 host writes, 6 + 2 + 2 = 10 flash writes. WA = 10 / 6 ≈ 1.67. Two erases happened, one on B0 and one on B3. The victims were cheap because the overwritten data was spread so that two blocks became half-stale. If every victim had 3 valid pages out of 4 (u = 0.75), WA would be 1 / 0.25 = 4. If the host had rewritten whole blocks in order (LBA 0 to 3 together), a whole block would go stale and GC would copy nothing: WA = 1.
Now scale up. A 1 TB drive with 7% spare space sees uniform random 4 KB overwrites at 100 MB/s. With WA of about 7, the flash is written at 700 MB/s, which uses up the drive's internal bandwidth and its erase budget. The latency of host writes rises during GC, and the drive's life is shortened 7 times. At 28% spare, WA is about 2.5 to 3, so the same host load costs 250 to 300 MB/s of flash writes. If the file system also issues TRIM, deleted data is not copied, and WA falls further.
intuition: A notebook you can't erase single lines in, only tear out whole pages, so you keep rewriting and recycling.
Flash allows only two cheap moves: write to an empty page, and erase a big block. The FTL builds the familiar "overwrite anywhere" interface from these moves by never overwriting. It writes updates to new places, remembers where things are, and recycles the old pages in the background. The cost of recycling depends on how full blocks are of still-valid data, which is why spare space and data lifetimes matter so much. It is the same design as a log-structured file system or an LSM tree, only inside the drive.
mistakes: People often think write amplification is a flaw of poor drives. In fact it is inherent: any drive with erase-before-write must copy valid data out of blocks before erasing them. Good designs lower it with spare space, hot-cold separation and host hints, but it cannot reach 1 for random overwrites on a nearly full drive.
People often think deleting a file frees space on the SSD at once. In fact the drive only learns that the blocks are unused if the file system sends TRIM. Without it, the FTL treats deleted data as valid and copies it again and again during GC. Make sure periodic fstrim or the discard option is on, and understand that a TRIM is a hint, not a guarantee of erasure.
People often think an SSD's rated capacity is all usable flash. In fact there is always hidden spare space: at least about 7% from the gap between binary gibibytes and decimal gigabytes, and more in enterprise drives (a 960 GB drive may have 1,024 GB or more of raw flash). Formatting only part of a drive adds more spare space.
People often think the FTL protects against all data loss. In fact it protects against wear and low-level errors, but a power cut can still lose acknowledged writes on drives without power-loss protection, and FTL bugs have corrupted data. Redundancy and checksums above the drive remain necessary.
tradeoffs: Choose a page-level mapping with a full table in DRAM when random read and write performance matters and you can afford 1 GB of DRAM per TB. This is the enterprise default. Choose a cached or coarser mapping (DRAM-less drives that keep part of the table in flash or host memory) for cheap consumer drives, and accept slow random access once the working set exceeds the cached part of the table.
Choose more over-provisioning for write-heavy random workloads: going from 7% to 28% spare space can cut write amplification from about 7 to about 3, which means 2 times less wear and steadier latency, for about 16% less usable capacity. For read-mostly workloads, minimal spare space is fine and cheaper.
Choose a conventional block-interface SSD when your software is general purpose or unmodified: databases, file systems and VMs on the block interface. Choose ZNS when you control the software (a log-structured store, RocksDB with ZenFS, a distributed storage system) and can write sequentially within zones: you get almost no write amplification, little spare space and much less DRAM, but the host must do garbage collection, handle zone resets and live with the append-only rule. Choose FDP when you want most of the benefit while staying compatible with the block interface: you add placement tags, and old software keeps working, but the gains depend on the application tagging data with equal lifetimes.
Choose greedy garbage collection for uniform workloads and cost-benefit (or age-aware) policies for skewed ones with hot and cold data. Aggressive background GC keeps latency stable but costs more wear; lazy GC saves wear but causes sudden stalls when the free pool runs out.
friction: The FTL is a black box with performance that changes with history. The same drive can have very different speed when empty, full, or after hours of random writes; background GC causes tail latency spikes of milliseconds; and the vendor does not publish the policies. Databases that track p99.9 latency see this as unexplained noise. The FTL also duplicates work done above it: an LSM tree compacts to remove stale data, and then the FTL runs GC on the same data. Stacked log-structured layers multiply write amplification (the "log-on-log" problem), so an application WA of 10 and a device WA of 3 gives 30 times flash writes per user byte.
Resource costs are significant: DRAM for the map (a 30 TB drive needs about 30 GB), controller cores and power, capacitors for power-loss protection, and over-provisioning that you pay for but cannot use. Reliability depends on firmware quality; real firmware bugs have caused drives to lose data or to brick at a specific uptime. Finally, the interface is changing: ZNS adoption has so far been narrow, FDP is newer, and the mix of interfaces fragments the software that has to support them.
practice: Leave room. Do not fill SSDs beyond 80 to 90%, and give write-heavy databases extra spare space by under-partitioning the drive or by choosing a drive with more over-provisioning. Run fstrim weekly (or mount with discard on drives where it is cheap) so that deleted blocks are returned. Prefer large, aligned, sequential writes and append-only formats; a LSM database that deletes whole files at once works well with the FTL.
Measure the effect with the drive's own counters: NVMe SMART logs report data units written by the host, and many vendors expose NAND writes, so you can compute WA = NAND writes / host writes. Track the percentage of life used and alert at a threshold. Benchmark in steady state (fill the drive twice, run random writes for an hour) and look at p99 latency, not only throughput, because a fresh-drive benchmark hides GC.
Separate data by lifetime where you can: keep the write-ahead log, hot tables and cold archives on different namespaces or devices, or use FDP or multi-stream hints. If you run RocksDB or a similar engine on very large write volumes, consider ZNS or FDP, or at least tune the file size so that a compaction output is a multiple of the erase block. For cloud workloads, remember that instance-local NVMe drives have a fixed FTL behavior you cannot change, so test them with your own pattern and leave headroom.

interview: Explain what happens inside an SSD when you overwrite a 4 KB block. || The controller writes the new data to a free page in an open block (possibly after buffering and striping over channels), updates the L2P table, and marks the old page stale. Why does SSD performance degrade when the drive fills up, and how do you manage it? || Fewer free blocks mean GC victims have more valid pages (higher u), so write amplification and background copying grow, and host writes wait. @@ digitallogic
value: Digital logic is how switches become computation. A logic gate is a small circuit whose output is 1 or 0 according to a Boolean function of its inputs: AND, OR, NOT, NAND, XOR. Gates wired into combinational circuits (the output depends only on the current inputs) compute things like addition, comparison and selection. Gates plus memory elements, flip-flops that store one bit on each clock tick, make sequential circuits: registers, counters, state machines, and finally whole processors. Every CPU, GPU, network chip and memory controller is built from these two kinds of circuit, with billions of gates. A 2024-class GPU has over 200 billion transistors.
The value of the abstraction is that it separates two worlds. Below it, transistors are analog devices with leakage, noise and variation. Above it, you can treat every signal as exactly 0 or 1 and reason with Boolean algebra. The boundary holds because each gate regenerates its output to a clean high or low voltage, so small errors do not add up along a chain of a hundred gates. This is why a chip can switch billions of gates billions of times per second without the results drifting.
For the layer above, digital logic supplies the building blocks of the machine: the adders and ALUs that execute instructions, the latches between pipeline stages, the decoders that turn an instruction into control signals, the state machines in interrupt controllers and DMA engines. Boolean algebra (L4) is the mathematics underneath: any truth table can be written as a formula, simplified by algebraic rules, and mapped to gates. The transistor (L5) is the physical switch: a few of them, wired in a CMOS pattern, form each gate and give it the property of restoring the signal level.
terms: Gate — a circuit computing a simple Boolean function (AND, OR, NOT, NAND, NOR, XOR) from its input voltages.
Combinational circuit — a circuit with no memory; the outputs are a function of the present inputs only.
Sequential circuit — a circuit with state; its outputs depend on the inputs and on stored bits.
Flip-flop — a one-bit storage element that copies its input at a clock edge and holds it until the next edge.
Clock — a periodic signal that tells all flip-flops when to sample their inputs; its period limits how much logic can sit between flip-flops.
Critical path — the slowest chain of gates between two flip-flops; it sets the minimum clock period.
Setup and hold time — the window around the clock edge in which a flip-flop's input must be stable.
Full adder — a circuit that adds three bits (two inputs and a carry-in) and gives a sum bit and a carry-out.
Carry-lookahead — an adder design that computes all carries in parallel, in time that grows with log n instead of n.
HDL (Verilog, VHDL) — a hardware description language that describes circuits as text; tools compile it into gates.
history: In 1937, Claude Shannon's master's thesis at MIT, "A Symbolic Analysis of Relay and Switching Circuits", showed that George Boole's algebra of 1854 describes networks of switches exactly: series switches are AND, parallel switches are OR. That made circuit design a branch of mathematics. Early computers used relays and then vacuum tubes (ENIAC in 1945 had about 18,000 tubes). The transistor (Bardeen, Brattain and Shockley, Bell Labs, 1947) replaced the tube, and the integrated circuit (Jack Kilby at Texas Instruments, 1958; Robert Noyce at Fairchild, 1959) put many on one piece of silicon.
Standard parts spread the practice. Texas Instruments' 7400 series (1964 onward) offered cheap gates, flip-flops and counters in small packages, and engineers built computers from them. The Intel 4004 (1971) put a whole CPU on one chip with about 2,300 transistors. Mead and Conway's textbook "Introduction to VLSI Systems" (1980) taught software-minded people to design chips with a few simple rules, and began the separation between designers and fabrication plants.
From the 1980s, designers moved from drawing gates to describing behavior. VHDL emerged from a U.S. Defense Department program and became IEEE standard 1076 in 1987; Verilog was created at Gateway Design Automation in 1984 and standardized as IEEE 1364 in 1995. Logic synthesis tools turn the description into gates, and place-and-route tools turn gates into layout. FPGAs (Xilinx, 1985) let designers test circuits as programmable lookup tables. Power became the limit in the mid-2000s, when voltage stopped scaling (the end of Dennard scaling) and clock rates stalled near 4 to 5 GHz, so designers added cores and special-purpose logic instead of faster clocks. Open tools (Yosys, Verilator, Chisel) and open instruction sets (RISC-V) have recently made hardware design more accessible.
how: A modern gate is built in CMOS (complementary MOS) from two networks of transistors. A pull-up network of PMOS transistors connects the output to the supply voltage when the function should give 1, and a pull-down network of NMOS transistors connects it to ground when the function should give 0. Exactly one network conducts for any input, so a gate draws almost no current except while switching. A NOT gate uses 2 transistors, a NAND gate 4. NAND is universal: any Boolean function can be built from NAND gates alone. Since each gate fully drives its output to the supply or to ground, a degraded input signal is restored at every stage. This restoring property is what makes the digital abstraction work, and it is a property of the transistor's strongly non-linear response.
Combinational design follows from Boolean algebra. Write the truth table of the function, express it as a sum of products (an OR of AND terms), simplify with algebraic rules (De Morgan's laws, absorption) or a Karnaugh map, and implement with gates. Common blocks are the multiplexer (select one of several inputs), the decoder (turn an n-bit number into one of \( 2^n \) lines, used for register selection and instruction decoding), the comparator, and the adder. A full adder gives \( \text{sum} = a \oplus b \oplus c_{\text{in}} \) and \( c_{\text{out}} = (a \cdot b) + (c_{\text{in}} \cdot (a \oplus b)) \): two XOR gates, two AND gates and one OR gate. Chaining n of them gives a ripple-carry adder, where the carry must travel through all n stages, so delay grows linearly with n.
Faster adders trade area for time. Let \( g = a \cdot b \) (this position generates a carry) and \( p = a \oplus b \) (this position passes a carry along). The carry out of bit i is \( c_{i+1} = g_i + p_i \cdot c_i \). Expanding this recursively, you can compute all carries from the g and p values with a tree of AND-OR gates of depth about \( \log_2 n \). This is carry-lookahead (and variants such as Kogge-Stone), and it is why a 64-bit add in a CPU takes around 10 to 15 gate delays instead of over 100. The same idea, doing work in parallel with more gates, appears in multipliers (partial products added in a tree) and barrel shifters (log n stages of multiplexers).
State needs feedback. Two cross-coupled NOR or NAND gates form an SR latch that keeps a bit as long as power is on. A D latch adds a gate input so that the stored bit follows the data when the clock is high; two latches in series, one transparent on each clock phase, give an edge-triggered D flip-flop that copies its input at the rising edge and ignores it otherwise. A register is a row of flip-flops sharing a clock. Static RAM stores bits in a 6-transistor cell instead. Put registers and combinational logic in a loop, and you have a finite state machine: next state = f(current state, inputs), outputs = g(state, inputs). A CPU is a very large state machine: the program counter, the registers and the pipeline latches are the state, and the logic between them is the instruction decode and the ALU.
The clock makes the timing simple to reason about. Between two flip-flops, the signal must go through the logic and settle before the next clock edge. So the clock period must be at least the flip-flop's clock-to-output delay, plus the longest path through the logic, plus the setup time of the next flip-flop, plus any clock skew. If a signal arrives late, the flip-flop may capture a wrong or half-way value (a setup violation). If an input changes too soon after the edge, there is a hold violation, which no clock slowdown can fix. When a signal from another clock domain arrives at a random time, the flip-flop can enter metastability, an undecided state that resolves after a random delay; designers use two or three flip-flops in series (synchronizers) to make the chance of failure negligible. Pipelining, the subject of the next concepts in this layer, splits long logic into stages separated by registers, so the clock can be faster.
Design is done in layers. An engineer writes register-transfer-level code in Verilog or SystemVerilog, simulates it, and a synthesis tool maps it to a library of gates from the foundry, aiming at the clock target with minimum area and power. Place-and-route positions the gates and wires (wire delay now matters as much as gate delay), timing analysis checks every path, and verification (simulation, formal proofs, emulation) takes more effort than the design itself.

example: Add 6 and 7 with a 4-bit ripple-carry adder. In binary, a = 0110 and b = 0111. Work from bit 0 (the least significant).
Bit 0: a0 = 0, b0 = 1, carry-in 0. Sum = 0 ⊕ 1 ⊕ 0 = 1. Carry-out = 0·1 + 0·(0 ⊕ 1) = 0. Bit 1: a1 = 1, b1 = 1, carry-in 0. Sum = 1 ⊕ 1 ⊕ 0 = 0. Carry-out = 1·1 + 0 = 1. Bit 2: a2 = 1, b2 = 1, carry-in 1. Sum = 1 ⊕ 1 ⊕ 1 = 1. Carry-out = 1·1 + 1·(1 ⊕ 1) = 1. Bit 3: a3 = 0, b3 = 0, carry-in 1. Sum = 0 ⊕ 0 ⊕ 1 = 1. Carry-out = 0 + 1·0 = 0. The result is 1101 in binary, which is 13. A carry-out of 0 from the top bit means no unsigned overflow.
Now count cost. A full adder has 5 gates (2 XOR, 2 AND, 1 OR), so a 64-bit ripple adder has 320 gates. The carry path goes through an AND and an OR in each stage, 2 gate delays per bit, so about 128 gate delays. At 15 ps per gate delay, that is 1.9 ns, which limits the clock to about 500 MHz. With carry-lookahead, the carry for bit 63 is computed through a tree of about 6 levels (log₂ 64), each level about 2 gate delays, plus the first g/p stage and the final XOR: roughly 14 gate delays, about 210 ps. The cost is more gates (perhaps 2 to 3 times as many) and more wiring, but the add fits in a 250 ps clock cycle.
Now a timing budget. Suppose the flip-flop clock-to-output delay is 40 ps, setup is 20 ps, clock skew is 10 ps, and the adder takes 200 ps. The minimum period is 40 + 200 + 20 + 10 = 270 ps, so the maximum clock is 1 / 270 ps ≈ 3.7 GHz. If you split the adder into two pipeline stages of 100 ps each, the period becomes 40 + 100 + 20 + 10 = 170 ps (5.9 GHz). The latency of an add rises from one cycle to two (340 ps instead of 270 ps), but throughput is higher. This is the trade-off of every pipeline, and each added register also costs area and power.
intuition: Lego bricks of logic: a few simple shapes, combined in huge numbers, make anything.
Boolean algebra says that any rule you can write as a table of yes and no can be built from AND, OR and NOT. A switch that is either on or off is the cheapest physical way to represent yes and no, and a restoring gate cleans up the signal at each step. Once you can compute, you add one more ingredient, a clock-driven memory, and you can do a sequence of computations, remembering the intermediate results. All of computing is the repeated application of these two ingredients at enormous scale and speed.
mistakes: People often think a digital signal is perfectly clean. In fact it is an analog voltage that is interpreted as 0 or 1 by thresholds. Noise, crosstalk and power droop are real, and the design works because every gate restores the level and the timing has margin. When margins are lost (a signal arrives too late, or a flip-flop sees a changing input), the circuit produces wrong values, or metastable ones.
People often think a faster clock is just a matter of better transistors. In fact the clock period must cover the slowest path, including wires, flip-flop overhead and skew; and power grows with frequency (and with the square of voltage), so it also hits the limit of what the chip can cool. This is why clock speeds stopped near 5 GHz around 2005 and added cores instead.
People often think hardware description languages are programming languages. In fact a Verilog module describes physical circuitry that all exists at once and runs in parallel. A loop in HDL is unrolled into copies of hardware, not executed over time. Treating it as sequential code produces circuits that are huge, slow, or cannot be synthesized.
People often think software is flexible and hardware is not, so hardware logic is irrelevant to software engineers. In fact its rules show up in software: why memory ordering exists (separate pipelines and buffers), why atomic operations cost what they cost (cache coherence logic), and why branchy code is slow (pipeline flushes).
tradeoffs: Choose a ripple-carry adder (or other minimal-area design) for small, rarely used or slow-clock circuits, such as an address incrementer in a microcontroller; it uses the fewest gates. Choose carry-lookahead or parallel-prefix adders for the datapath of a high-speed processor, where adder delay is on the critical path. You pay with 2 to 3 times the gates and with wiring complexity.
Choose an ASIC when the volume is high (hundreds of thousands of units and more) and performance and power matter: custom silicon can be 10 to 100 times more energy-efficient than a general processor for a fixed task, but the design and mask cost reach tens to hundreds of millions of dollars at advanced nodes, and a bug is permanent. Choose an FPGA for low volume, changing requirements or fast prototyping: it runs at a lower clock (hundreds of MHz) and uses more power per function, but you can reprogram it in seconds. Choose a CPU or GPU with software when the function will change often; give up some efficiency for flexibility.
Choose synchronous design (one clock) for almost everything, since timing tools and methods are mature; choose asynchronous or multiple clock domains only where you must (low power, different interface speeds), and add proper synchronizers. Choose more pipeline stages for throughput and clock speed, at the cost of latency, branch penalties and register power; choose fewer stages for low-power, small designs.
friction: Physical limits constrain logic. Wire delay now exceeds gate delay for long wires, so layout decides timing. Power density limits how many gates can switch at once: a big chip cannot run all of its transistors at full speed without overheating (dark silicon). Leakage current grows as transistors shrink. Variation in manufacturing means that identical gates have different delays, so designers add margin, and chips are sorted into speed grades.
Verification is the biggest cost. A chip with billions of gates has states beyond any exhaustive test; most of the effort goes into simulation, formal methods and emulation, and bugs still escape (Intel's Pentium FDIV bug in 1994 cost about 475 million dollars). Because a fabricated chip cannot be patched, a logic bug becomes a recall or a microcode and software workaround. Security flaws such as Spectre came from performance features that were correct in logic but leaked information through timing.
Designing at the gate level does not scale, so tools and abstraction carry the load, and the tools are expensive and proprietary (a few vendors dominate EDA). Skills are scarce: logic design, timing closure and verification are specialized. Also, the clock distribution to billions of gates uses a large part of the power budget, and synchronizing separate clock domains remains a source of rare, hard-to-reproduce faults.
practice: Learn by building. The best path is Nand to Tetris: from a NAND gate to an ALU, a CPU and an assembler. Then write a small CPU in Verilog, simulate it with an open tool (Verilator, Icarus Verilog, Yosys for synthesis), and run it on a cheap FPGA board. Draw the timing diagram before you write the code. Read a critical-path report once to see that the clock period is a sum of real delays.
For software engineers, the practical lessons are: a mental model of cost (an integer add is one cycle, a division 10 to 40 cycles, a multiply 3 to 4 cycles, a cache miss hundreds), the idea that parallel hardware is free but serial dependencies are not (instruction-level parallelism), and respect for the clock-domain and reset problems that appear as race conditions in driver code.
When working with hardware teams (accelerators, FPGAs, SmartNICs), ask about the clock frequency, the pipeline depth (latency in cycles), the throughput per cycle, and what happens at reset and at clock-domain crossings. For FPGA-based data processing, check whether the work maps to wide, regular pipelines, since an FPGA at 300 MHz beats a CPU only through parallelism. For reliability, know that bit flips (cosmic rays) hit latches and memories, and that ECC and parity are standard.
quiz: Why is NAND called a universal gate? || Any Boolean function can be built using only NAND gates, because NOT, AND and OR can each be made from NAND (for example, NOT x = NAND(x, x)). So a chip needs only one gate type, built from four CMOS transistors.
Why does a ripple-carry adder get slower as it gets wider, and how does carry-lookahead fix this? || Each bit's carry depends on the previous bit's carry, so delay grows linearly with the width. Carry-lookahead computes generate and propagate signals per bit and combines them in a tree, so all carries are ready after about \( \log_2 n \) levels.
What sets the maximum clock frequency of a synchronous circuit? || The period must be at least the clock-to-output delay of the launching flip-flop plus the longest combinational path plus the setup time of the capturing flip-flop plus clock skew. The longest such path (the critical path) decides.
A flip-flop has 40 ps clock-to-output, 20 ps setup and 10 ps skew, and the logic path takes 130 ps. What is the maximum clock frequency? || The period is 40 + 130 + 20 + 10 = 200 ps, so the frequency is 1 / 200 ps = 5 GHz.
When would you choose an FPGA over an ASIC, and when the reverse? || FPGA for low volumes, changing requirements and fast time to market; it is reprogrammable but slower and less power-efficient. ASIC for high volumes with fixed functionality, where much better performance per watt and per unit cost justifies tens of millions in design cost.
interview: Why can't we just raise the clock frequency to make computers faster? || The period must cover the critical path, and dynamic power grows with frequency and voltage squared (\( P \approx \alpha C V^2 f \)). Around 2005, power density hit the cooling limit, so frequency stalled near 4 to 5 GHz. Performance now comes from parallelism: more cores, wider SIMD, deeper pipelines and special-purpose units.
What is metastability, and how do engineers handle it? || A flip-flop sampling a signal that changes inside its setup and hold window can settle to an undefined voltage for an unpredictable time. It cannot be removed, only made rare: put two or three flip-flops in series (a synchronizer), which makes the mean time between failures very long, and use handshakes or asynchronous FIFOs across clock domains.
How does pipelining raise throughput, and what does it cost? || It cuts the logic into stages with registers between them, so the clock period shrinks to the longest stage and one result is completed each cycle. It costs latency (more cycles per operation), registers (area, power), and complexity from hazards and flushes when branches mispredict.
Explain how you would design a fast 64-bit adder, and what are the trade-offs. || Use a parallel-prefix carry network (Kogge-Stone, Brent-Kung, Sklansky). Kogge-Stone has the fewest levels (log₂ 64 = 6) but many wires and gates; Brent-Kung uses fewer gates and wires but about twice the levels. Choose from the clock target, area and wire congestion.
Why do hardware designers simulate and verify so heavily compared with software teams? || A fabricated chip cannot be patched, and a mask set costs millions at advanced nodes, so bugs must be found before tape-out. Verification uses constrained-random simulation, formal methods and emulation, and is often more than half of the project effort.

value: Every computer has a few clocks, and they do different jobs. Inside a chip, a clock signal of several GHz tells every flip-flop when to capture its input; this is the heartbeat that makes synchronous logic work. Next to it, a counter (on x86, the time-stamp counter) increments at a fixed rate and lets software measure short intervals in nanoseconds. A battery-backed real-time clock keeps the date while the machine is off. And the operating system combines these into two software clocks: a wall clock that tries to match real-world time, and a monotonic clock that only counts forward.
All of them are made from the same thing, an oscillator, and no oscillator is perfect. A typical quartz crystal is off by 10 to 50 parts per million (ppm) depending on temperature and age. 50 ppm is 4.3 seconds per day. Two machines left alone therefore disagree by seconds within a day, and the disagreement keeps growing. Protocols such as NTP and PTP measure the difference over the network and steer the local clock, which gets typical errors down to milliseconds (NTP over the internet) or microseconds and below (PTP with hardware timestamps).
This matters to the layers above because distributed systems use clocks for decisions: lease expiry in leader election, heartbeat timeouts in failure detection, "last write wins" ordering of updates, and certificate and token validity. Each of these breaks in specific ways when clocks drift, jump or pause. Hybrid logical clocks and TrueTime exist because physical clocks are useful but not trustworthy, and fencing tokens exist because a lease checked against a local clock cannot stop a paused process. The layers below explain the limits: a quartz crystal (L5) oscillates at a frequency that depends on its cut and temperature, and atomic clocks and GPS (L5) provide the external reference that corrects the drift.
terms: Oscillator — a circuit that produces a repeating signal at a nearly constant frequency; in computers, usually a quartz crystal.
PPM (parts per million) — a unit of frequency error; 1 ppm is 0.0864 seconds per day.
Drift — the slow, steady divergence of a clock from true time because its frequency is slightly wrong.
Skew (offset) — the difference between two clocks at a given moment.
TSC (time-stamp counter) — a per-core counter on x86 that counts at a constant rate; read with the RDTSC instruction in a few nanoseconds.
Wall-clock time — time that tries to match civil time (UTC); it can be adjusted and can jump, including backwards.
Monotonic clock — a clock that never goes backwards and is not set by the administrator; right for measuring durations and timeouts.
NTP / PTP — protocols that synchronize a clock with a reference over a network; NTP gets milliseconds, PTP (IEEE 1588) gets microseconds or better with hardware timestamping.
Slew vs step — correcting a clock by changing its rate slightly (slew) or by setting it directly (step).
Leap second — a second added to UTC (23:59:60) to keep it close to the Earth's rotation.
history: Mechanical clocks gave way to quartz in the 1920s to 1960s: Warren Marrison at Bell Labs built the first quartz clock in 1927, and quartz watches reached the market in 1969. The reason is physical: a quartz crystal vibrates at a very stable frequency and loses little energy. The 32.768 kHz watch crystal, which is 2 to the power 15, is still used as the real-time clock in computers: a 15-stage binary divider produces exactly one pulse per second. Atomic clocks defined the second in 1967 as 9,192,631,770 periods of a caesium-133 transition, and GPS (operational in the 1990s) put atomic clocks in orbit and let any receiver get time to tens of nanoseconds.
Network time protocols began with David Mills's work in the early 1980s. NTP version 4 is specified in RFC 5905 (2010). IEEE 1588 (the Precision Time Protocol, 2002, revised 2008 and 2019) added hardware timestamping in network cards and switches to remove the software delays that limit NTP. Operating systems gained better primitives: Linux added high-resolution timers, a monotonic clock and tickless operation around 2006 to 2008, and Intel gave processors an "invariant" TSC that runs at constant rate in all power states (Nehalem, 2008), which made nanosecond timing cheap.
The distributed systems community drew the conclusions. Lamport (1978) showed that ordering events does not need physical time at all. In practice, time kept causing incidents: the leap second on 30 June 2012 triggered Linux kernel and Java problems that put many sites (Reddit, Mozilla and others) into high CPU use; at the end of 2016, a leap second made a clock difference negative in Cloudflare's DNS software and caused failures on 1 January 2017. Google's Spanner (2012) took the opposite approach and built TrueTime from GPS receivers and atomic clocks, exposing the uncertainty of time as an interval. In 2022, the international metrology conference (CGPM) decided to stop using leap seconds by 2035.
how: Inside the chip. A crystal oscillator on the board, typically 25 or 100 MHz, supplies a reference. A phase-locked loop (PLL) compares the reference with a divided-down copy of a faster on-chip oscillator and adjusts the oscillator until they match, which multiplies the frequency: 100 MHz × 40 gives a 4 GHz core clock. A clock distribution network of buffers sends this signal to every flip-flop, designed so that all arrive within a few picoseconds of each other (low skew). The crystal's accuracy does not matter here, since all that counts is that every flip-flop uses the same clock; the actual frequency changes with temperature and power state. In many systems, spread-spectrum modulation moves the frequency slightly up and down to reduce electromagnetic interference.
Counting time. Computers need a free-running counter that software can read. On x86, the TSC increments at a fixed rate (the crystal-derived base frequency, for example 2.5 GHz), even when the core frequency changes. Reading it with RDTSC takes roughly 20 to 30 cycles. On Arm, a generic timer counter (typically running at some tens of MHz) is read from a system register. Older sources are slower to read: the HPET (at least 10 MHz) and the ACPI power-management timer (3.58 MHz) need a device access that can take about a microsecond. Linux selects one source (clocksource), and exposes it to programs through the vDSO, a small piece of kernel code mapped into every process, so that clock_gettime costs about 20 to 50 ns without a system call. For timers that must fire at a given time, a per-core timer (the local APIC timer on x86) raises an interrupt; the kernel keeps the next deadline in a timer structure, and in tickless mode does not wake up a sleeping core without a reason.
Software clocks. The kernel converts the counter into time: wall time = a reference time + (counter difference × a rate). Linux offers CLOCK_REALTIME, which can be set and adjusted and counts UTC since 1970; CLOCK_MONOTONIC, which starts from an arbitrary point, never steps, and is slewed (its rate adjusted slightly) by NTP but does not count time while the machine is suspended; CLOCK_MONOTONIC_RAW, which is not slewed; and CLOCK_BOOTTIME, which includes suspend. Java offers currentTimeMillis (wall) and nanoTime (monotonic); Go's time.Now() has carried a monotonic reading since Go 1.9, so subtractions are safe. For a timeout or a duration, use a monotonic source. For a timestamp that other machines or people will read, use wall time. Mixing the two is a classic bug.
Synchronization. NTP estimates the offset between a client and a server by exchanging four timestamps: the client sends at t1 (client clock), the server receives at t2 and replies at t3 (server clock), the client receives at t4 (client clock). The offset is \( \theta = \frac{(t_2 - t_1) + (t_3 - t_4)}{2} \) and the round-trip delay is \( \delta = (t_4 - t_1) - (t_3 - t_2) \). The formula assumes the outbound and return paths take equal time; if they do not, the error is half of the asymmetry, and \( \delta / 2 \) is the largest error that can be excluded. Clients poll several servers, filter noisy samples, and steer their clock: small errors are removed by slewing (up to 500 ppm, about 43 seconds per day, in Linux), large errors by a step. chrony does this better than the older ntpd, especially with virtual machines and variable networks. PTP uses the same exchange but timestamps packets in the network card hardware, which removes the unpredictable kernel and queueing delays, and switches can correct for their own delay, so accuracy reaches below a microsecond. Cloud providers offer time services with a stated error bound, some of them with microsecond-level accuracy through hardware clocks.
The hard part is uncertainty. A clock reading is really "the time is t, plus or minus ε", where ε grows with the time since the last synchronization (about the drift rate, 10 to 100 ppm, times the elapsed time) and with network asymmetry. Systems such as Spanner keep ε small (a few milliseconds) and publish it as an interval; TrueTime guarantees that true time lies inside [earliest, latest], and a transaction waits out the uncertainty before it commits, so timestamps follow real-time order. Systems without such a guarantee must not treat two timestamps within the clock error as ordered.

example: Use NTP's four timestamps on a client whose clock is 100 ms behind the server. The one-way delay is 10 ms each way and the server needs 1 ms to reply. The client sends at its t1 = 1000.000. The server clock is 100 ms ahead, so when the request arrives (10 ms later) the server clock reads t2 = 1000.110. The server replies 1 ms later: t3 = 1000.111. The reply takes 10 ms more; the server clock would then read 1000.121, which the client clock shows as 1000.021. So t4 = 1000.021.
Offset: ((t2 − t1) + (t3 − t4)) / 2 = (0.110 + 0.090) / 2 = 0.100 s. The client learns that it is 100 ms behind: correct. Delay: (t4 − t1) − (t3 − t2) = 0.021 − 0.001 = 0.020 s, the round trip.
Now make the network asymmetric: 18 ms out and 2 ms back (still 20 ms in total). Then t2 = 1000.118, t3 = 1000.119, t4 is again 1000.021. Offset: (0.118 + 0.098) / 2 = 0.108 s. The client thinks it is 108 ms behind, an error of 8 ms, which is half of the asymmetry (18 − 2 = 16 ms, divided by 2). The client cannot detect this from the four numbers, which is why NTP accuracy is limited by path asymmetry, and why hardware timestamps and symmetric paths help.
Now drift. Two servers whose crystals are +50 ppm and −50 ppm drift apart at 100 ppm, which is 100 µs per second. If they poll NTP every 1,024 s, the error just before a correction is up to about 1,024 × 100 µs ≈ 100 ms; if they poll every 64 s, about 6.4 ms. This is why a "last write wins" database that uses wall-clock timestamps from such servers can lose a newer write: a write at true time T on the slow server gets an earlier timestamp than an older write on the fast one, if the writes are within 100 ms of each other.
Finally a lease. A lock service grants a lease of 10 seconds. The holder checks its monotonic clock before writing: "8 seconds elapsed, I still hold the lease." Then a garbage-collection pause of 15 seconds stops the process after the check but before the write. When it resumes, the lease expired, the lock server has granted it to another client, and the old holder writes anyway. No clock accuracy would prevent this; the fix is a fencing token checked by the storage.
intuition: Every watch in the room runs slightly fast or slow; agreeing on time needs constant correction.
A clock is only a counter driven by an oscillator, and an oscillator is a physical object with a slightly wrong frequency that depends on temperature. Inside one chip, that does not matter: everything uses the same clock, so everything stays in step. Between machines it matters, because there is no shared oscillator, only messages that take an unknown time to travel. So the best we can do is estimate the difference, correct it a little at a time, and remember that the estimate has an error bar. A system that treats a clock reading as exact will, sooner or later, be wrong in a way that is hard to find.
mistakes: People often think the system clock is accurate. In fact an unsynchronized crystal gains or loses seconds per day, a synchronized one is typically within milliseconds, and during a network outage or after a VM pause it can be off by much more. Always design as if clocks disagree by more than you expect.
People often think wall-clock time never goes backwards. In fact NTP steps, administrators, leap seconds and virtual machine restores can all make it jump, forward or back. Code that computes elapsed time as end minus start from wall-clock readings can get negative numbers, as in the Cloudflare incident; use a monotonic clock for durations.
People often think a monotonic clock is the same on every machine. In fact its starting point is arbitrary and local; values from different machines cannot be compared. It can also stop during suspend (CLOCK_MONOTONIC) and run at a slightly different rate from real time because of slewing.
People often think a lease or a timeout makes a lock safe. In fact a lease reasons about time at the node that grants it and time at the node that holds it; a long pause (garbage collection, swap, VM freeze, a slow network) can make the holder act after its lease ended. Safety needs a fencing token or an operation that the storage can check.
tradeoffs: Choose NTP (chrony) with a few good servers for general services where a millisecond or ten of error is acceptable (logs, metrics, certificates, most business logic). Choose PTP with hardware timestamping, or a cloud provider's hardware time source, when you need microseconds: trading systems, telecom, distributed databases that rely on bounded clock error. You pay with specialized network cards, switches and more careful operations.
Choose timestamp-based ordering ("last write wins", snapshot timestamps) when you can bound the clock error and tolerate waiting or occasional lost writes: this is cheap and needs no coordination. Choose logical clocks (Lamport, vector, hybrid logical clocks) when you need causal order without trusting wall time, and accept that the numbers do not match real time exactly. Choose TrueTime-style bounded uncertainty with commit wait when you need external consistency across data centers and can fund GPS and atomic-clock hardware; each commit waits a few milliseconds.
Choose leap-second smearing (spreading the extra second over about 24 hours, as Google and others do) over a step at 23:59:60 so that clocks never repeat or skip; but do not mix smeared and non-smeared servers in one NTP pool, since they differ by up to half a second during the smear. Choose a monotonic clock for every duration, and wall time only for values meant to be compared with the outside world.
Choose generous lease margins (a lease of 10 s with a clock-error budget of 1 s) and fencing tokens for correctness. Shorter leases give faster failover but more false expiry when a node is slow; longer ones give stability but slower recovery.
friction: Time is never fully solved. Every synchronization method has an error from asymmetric network delay, queueing, temperature changes, and the reference itself. NTP over the internet gives tens of milliseconds in bad conditions, and cloud networks vary. Virtual machines make it worse: a paused or migrated VM sees time jump, the hypervisor's clock source may differ from the host, and oversubscribed hosts add delay to timers.
Leap seconds remain a source of outages until they are abolished (planned by 2035). Different systems handle them differently: step, smear over 24 hours, or ignore. GPS time has no leap seconds and is now 18 s ahead of UTC; TAI is 37 s ahead. Time zone and daylight-saving rules change often, so storing local time instead of UTC causes errors. Also, the 32-bit time_t overflows in January 2038 on systems that still use it.
Many software assumptions are fragile: timeouts that depend on tick rate, sleeps that last longer than requested, timers that fire late under load, and processes paused by the scheduler or the garbage collector for seconds. The attacker's view matters too: NTP can be spoofed or abused for amplification, and a wrong clock breaks TLS certificate validation and Kerberos, so important systems authenticate time (NTS, authenticated NTP) and monitor offsets.
practice: Run chrony (or the cloud provider's time service) on every server, configured with several sources, and monitor the offset and the sync state; alert when the offset exceeds your budget, say 100 ms for general systems, or when the clock is unsynchronized. Make sure all servers use the same source type and handle leap seconds the same way (smeared everywhere or nowhere).
In code, use monotonic clocks for durations, deadlines and timeouts (Python time.monotonic, Java System.nanoTime, Go time.Now with its monotonic part, Rust Instant). Store timestamps as UTC (epoch milliseconds or ISO 8601 with Z) and convert to local time only for display. Never compute elapsed time from two wall-clock readings, and never compare timestamps from different machines closer than your known clock error without a rule for ties.
For distributed correctness, do not let a lease check be the only guard: use fencing tokens, compare-and-set versions or conditional writes. For event ordering, prefer a per-record version, a Lamport or hybrid logical clock, or a database's sequence, and use the wall time only as a tiebreaker or for display. When using "last write wins" (Cassandra, DynamoDB global tables), know that client or node clocks decide, and keep clock error small.
In testing, inject clock jumps, drift and long pauses (libfaketime, SIGSTOP on a process), and check what happens to leases, TTL caches, token expiry and rate limits.
quiz: Why does an uncorrected quartz clock drift, and by roughly how much? || Real crystals oscillate at a frequency that is slightly off nominal and changes with temperature and age, typically 10 to 50 ppm. 50 ppm accumulates 50 µs of error per second, about 4.3 seconds per day.
What is the difference between CLOCK_REALTIME and CLOCK_MONOTONIC, and which should a timeout use? || Realtime is wall-clock UTC time and can be stepped by NTP or an administrator, including backwards. Monotonic never goes backwards and has no meaning outside the machine. Timeouts and durations should use monotonic time.
In NTP, how does the client compute offset and what causes the remaining error? || With the four timestamps, offset = ((t2 − t1) + (t3 − t4)) / 2. It assumes the outbound and return delays are equal. If they differ, the error is half of the difference, and the client cannot tell from the timestamps.
Two servers with crystals at +40 ppm and −40 ppm sync with NTP every 512 s. How large can their disagreement be just before the next sync (ignoring sync error)? || The relative drift is 80 ppm = 80 µs per second. Over 512 s that is 512 × 80 µs ≈ 41 ms.
Your service uses a 10-second lease and checks the lease with its own monotonic clock before each write. Why can it still corrupt data, and what do you add? || A pause (garbage collection, VM stall) can happen between the check and the write, so the holder writes after the lease expired and another client holds it. Add a fencing token issued with the lease and checked by the storage system, which rejects writes with an old token.
interview: Why do distributed systems avoid using wall-clock time for ordering, and what do they use instead? || Clocks on different machines differ by milliseconds or more, drift, and can jump, so timestamps within that error cannot be ordered. Systems use logical clocks (Lamport, vector clocks), hybrid logical clocks (physical time plus a counter, bounded close to wall time), per-key versions or consensus logs, and in Spanner's case bounded-uncertainty clocks with commit wait.
What did the leap second incidents (2012 Linux, 2017 Cloudflare) teach? || Time can repeat, skip or go backwards, and code that assumes otherwise breaks: a negative duration caused a panic in Cloudflare's DNS software, and a kernel timer bug caused load spikes in 2012. Use monotonic clocks for durations, smear leap seconds consistently, test with injected clock jumps, and plan for leap seconds being rare so that the code path is rarely exercised.
How does Spanner's TrueTime work and what does it cost? || Each data center has GPS receivers and atomic clocks; TrueTime returns an interval [earliest, latest] that contains true time, with an uncertainty of a few milliseconds. A transaction picks a commit timestamp and waits until it is surely in the past (commit wait) before releasing locks, so timestamps agree with real-time order. The cost is the commit wait, about the uncertainty, and the specialized hardware.
A VM was live-migrated and the application saw a clock jump of 3 seconds. What breaks and how would you detect it? || Timeouts and leases measured against wall time fire early or late; TTL caches expire; heartbeats may declare nodes dead. Detect with a monitor that compares the wall clock against the monotonic clock, alerts on jumps, and use the hypervisor's clock-sync features. Design leases to tolerate pauses.
How accurate can software timing be on one machine, and what limits it? || Reading the invariant TSC takes about 20 to 30 cycles, so intervals of tens of nanoseconds are measurable. Limits: out-of-order execution (use fences or RDTSCP), frequency scaling between cores, preemption by the scheduler, interrupts, and VM overhead. For durations longer than microseconds, the OS monotonic clock is accurate to its slewing (up to 500 ppm).

@@ floatingpoint
value: A floating-point number stores a real number in a fixed number of bits as three fields: a sign, an exponent and a significand (also called mantissa). The value is roughly \( \pm 1.\text{fraction} \times 2^{\text{exponent}} \), like scientific notation in base 2. This one design covers an enormous range with a roughly constant relative precision. A 64-bit double can represent numbers from about 10⁻³⁰⁸ to 10³⁰⁸ with about 16 significant decimal digits, while a 64-bit integer covers only up to about 9 × 10¹⁸ and has no fractions. The price is that most real numbers cannot be stored exactly, so every operation rounds, and the results are slightly wrong in a way that you have to understand.
IEEE 754 (1985) made the behavior of floating point the same on all machines: the same bit layouts, the same rounding rules, special values for infinity and "not a number" (NaN), and results that are correctly rounded for the basic operations. Before it, every vendor had its own format, and the same program gave different answers on different computers. Today the standard governs the CPU, the GPU and all numeric libraries.
Floating point matters to modern systems for a new reason. In machine learning, the choice of format is the main lever on speed and memory. Moving from FP32 to BF16 or FP16 halves memory traffic and unlocks tensor cores (mixed precision); FP8 and FP4 halve it again (quantization). Each step trades precision or range for throughput, and works only because neural networks tolerate noise. The layers below explain what is happening: binary (L3) gives the bit-level encoding, including the biased exponent that makes floats sort like integers, and numerical analysis (L4) gives the theory of rounding error, condition numbers and stable algorithms that tells you when the errors matter.
terms: Sign, exponent, significand — the three fields: one bit for the sign, a biased exponent giving the power of two, and the significand holding the digits after the leading 1.
Bias — a constant added to the true exponent so it can be stored as an unsigned number: 127 for FP32 and 1023 for FP64.
Machine epsilon — the gap between 1.0 and the next larger float: \( 2^{-23} \approx 1.2 \times 10^{-7} \) for FP32 and \( 2^{-52} \approx 2.2 \times 10^{-16} \) for FP64.
ULP (unit in the last place) — the spacing between two neighbouring floats at a given magnitude; it doubles each time the exponent grows by one.
Rounding mode — the rule for choosing a float when a result is between two; the default is round to nearest, ties to even.
Subnormal (denormal) number — a very small number with exponent field 0 and no implicit leading 1, which fills the gap between zero and the smallest normal number.
NaN and infinity — special values: infinity results from overflow or division by a nonzero value by zero; NaN results from 0/0 or \( \sqrt{-1} \) and is not equal even to itself.
Catastrophic cancellation — loss of most significant digits when you subtract two nearly equal numbers that already carry rounding errors.
BF16 / FP16 / FP8 / FP4 — the 16-, 8- and 4-bit formats used in machine learning; they differ in how many bits go to exponent (range) and to significand (precision).
FMA (fused multiply-add) — computes a × b + c with a single rounding at the end.
history: Early computers used fixed-point or each their own floating-point format. Konrad Zuse's Z3 (1941) already had binary floating point. IBM's System/360 (1964) used a hexadecimal format with poor rounding, and by the 1970s, different machines gave different answers for the same program, sometimes dangerously. William Kahan, a numerical analyst at Berkeley, led the effort for a good standard, working with Intel on the 8087 coprocessor (1980). IEEE 754 was published in 1985, and Kahan received the Turing Award in 1989 for this work.
Mistakes in floating point were costly and drew attention. In 1991, a Patriot missile battery in Dhahran failed to intercept a missile: the system counted time in tenths of a second in a 24-bit fixed-point register, and 0.1 cannot be represented exactly in binary, so after 100 hours the clock was off by about 0.34 seconds, which at the missile's speed was more than half a kilometre. In 1994, Intel's Pentium had a flaw in its division lookup table, discovered by Thomas Nicely, and Intel had to replace chips at a cost of about 475 million dollars. David Goldberg's 1991 paper "What Every Computer Scientist Should Know About Floating-Point Arithmetic" became the standard introduction.
The standard was revised in 2008 (adding fused multiply-add, decimal formats and the 16-bit half format) and in 2019 (clarifications). The recent action is in machine learning. Google introduced bfloat16 (8 exponent bits, 7 significand bits) in its TPUs around 2017 because training needs the range of FP32 more than its precision. NVIDIA added TF32 in Ampere (2020) and FP8 in Hopper (2022), with the E4M3 and E5M2 variants described in a 2022 paper by NVIDIA, Arm and Intel. In 2023, the Open Compute Project published the Microscaling (MX) formats, where a block of 32 values shares one scale, which supports 8-, 6- and 4-bit elements. FP4 with block scaling is in NVIDIA Blackwell hardware.
how: A 32-bit float has 1 sign bit, 8 exponent bits and 23 fraction bits. If the exponent field e is between 1 and 254, the number is normal: value = \( (-1)^s \times 1.f \times 2^{e-127} \). The leading 1 is not stored (the "hidden bit"), which gives 24 bits of precision for 23 stored bits. If e = 0, the number is subnormal: value = \( (-1)^s \times 0.f \times 2^{-126} \), which lets values shrink gradually towards zero instead of dropping from 1.2 × 10⁻³⁸ straight to 0. If e = 255, the number is infinity (f = 0) or NaN (f ≠ 0). The same scheme applies to other sizes. FP64 has 11 exponent bits (bias 1023) and 52 fraction bits. FP16 has 5 and 10 (bias 15), with a maximum of 65,504. BF16 has 8 and 7, the same range as FP32 but only about 2 to 3 decimal digits. FP8 has two variants: E4M3 (maximum 448) and E5M2 (maximum 57,344). FP4 (E2M1) has only eight non-negative values: 0, 0.5, 1, 1.5, 2, 3, 4 and 6.
Relative precision is constant, and absolute precision is not. Between \( 2^k \) and \( 2^{k+1} \) the floats are evenly spaced, \( 2^{k-23} \) apart in FP32. Near 1 the spacing is 1.2 × 10⁻⁷; near 16 million (2²⁴) it is 2, so 16,777,217 cannot be stored and 16,777,216 + 1 equals 16,777,216. Rounding to the nearest float gives a relative error of at most \( 2^{-24} \approx 6 \times 10^{-8} \) in FP32 per operation. This is the standard model used in numerical analysis: each operation returns \( (\text{exact result}) \times (1 + \delta) \) with \( |\delta| \le u \). All the theory of how errors grow follows from it.
Binary representation gives useful properties. Because the exponent is stored before the fraction and is biased, positive floats sort in the same order as their bit patterns read as integers, so comparison and radix sorting can be done with integer operations (negative values need the sign bit and the other bits flipped). Because 0.1, 0.2 and 0.3 have infinite binary expansions (like 1/3 in decimal), they are stored as the nearest float. 0.1 in FP32 is 0x3DCCCCCD, exactly 0.100000001490116…; in FP64 it is 0.1000000000000000055511…. Therefore 0.1 + 0.2 gives 0.30000000000000004 in FP64, which is not the same float as 0.3.
Arithmetic is done as if exactly and then rounded. IEEE 754 requires correct rounding for add, subtract, multiply, divide, square root and FMA. This makes basic operations predictable, but the combination is not: floating-point addition is commutative but not associative. For example (10¹⁶ + (−10¹⁶)) + 1 = 1, while 10¹⁶ + ((−10¹⁶) + 1) = 0 in FP64, because −10¹⁶ + 1 rounds back to −10¹⁶. So any change in the order of a sum, whether from a compiler, a parallel reduction or a different number of threads, can change the result in the last digits. Summing n numbers in order has an error bound that grows like n × u; pairwise (tree) summation gives log n × u, and Kahan's compensated summation keeps an extra variable with the lost low-order part, giving an error independent of n.
Numerical analysis tells which errors matter. Subtraction of nearly equal numbers (cancellation) exposes earlier rounding errors, because the leading digits cancel and the noise remains. A problem has a condition number: how much the output changes for a small relative change in the input. A stable algorithm adds only a small amount of error beyond what the condition number forces. For example, the quadratic formula suffers cancellation when \( b^2 \gg 4ac \); a stable version computes the larger root first and gets the other from the product of roots \( c/a \). Machine learning adds its own techniques: loss scaling for FP16 (multiply the loss by a factor such as 1,024 so small gradients do not underflow), per-tensor or per-block scaling factors for FP8 and FP4, and accumulation in FP32 inside the tensor cores.

example: Encode 0.15625 in FP32. In binary, 0.15625 = 5/32 = 0.00101. Normalize: 0.00101 = 1.01 × 2⁻³. The sign is 0. The stored exponent is −3 + 127 = 124 = 01111100. The fraction is the digits after the leading 1: 01, padded to 23 bits: 01000000000000000000000. The 32 bits are 0 01111100 01000000000000000000000, which is 0x3E200000 in hexadecimal. This number is exact because it is a sum of powers of two. Now try 0.1. In binary, 0.1 = 0.000110011001100…, repeating. Normalized: 1.100110011001100… × 2⁻⁴. The exponent is 123 (01111011). The fraction repeats 1001 1001 …; cut after 23 bits, the next bits are 1001…, so round up, and the fraction ends in …1101. The result is 0x3DCCCCCD, the value 0.100000001490116119384765625. It is a bit too large, by 1.5 × 10⁻⁹.
Now watch errors accumulate. In FP64, add 0.1 ten times starting from 0. The sum is 0.9999999999999999, not 1.0, because each addition rounds, and the stored 0.1 is slightly above 0.1 while the roundings pull the sum slightly down. A test like (sum == 1.0) fails. Compare with a tolerance (abs(a − b) ≤ 1e-9 × max(abs(a), abs(b))) instead.
Next, absorption. In FP32 add 1 to 16,777,216 (2²⁴): the exact sum 16,777,217 lies halfway between 16,777,216 and 16,777,218. Ties go to the even significand, so the result is 16,777,216 and the 1 is lost. A counter held in FP32 therefore stops counting at 16,777,216; that is a real bug in code that accumulates counts or timestamps in float. In FP16 the same happens at 2,048.
Last, a long sum. Add 0.1 one million times in FP32 with a plain loop. The exact answer is 100,000. As the running total grows, the spacing between floats near it grows too: near 100,000 it is 2⁻⁷ ≈ 0.0078, so each added 0.1 is rounded to a multiple of that spacing, and the roundings do not cancel. A well-known test of this loop gives roughly 100,958, an error of about 1%. Pairwise summation keeps the partial sums small and balanced, so each rounding is tiny, and gets very close to 100,000. Kahan summation keeps the lost low-order part in a second variable and does even better. This is why GPU libraries sum in trees, and why the same reduction on a different number of threads gives slightly different answers.
intuition: Scientific notation with a fixed number of significant digits.
The set of floats is like a ruler with marks that are dense near zero and widely spaced for large numbers, with the same relative spacing at every scale. That is exactly what measurements and most scientific quantities need: a relative error of a millionth is equally fine for a nanometer and for a light-year. A result that falls between marks goes to the nearest mark. So each operation is a correct calculation followed by a tiny, bounded nudge, and the art of numerical computing is making sure the nudges do not add up or get magnified.
mistakes: People often think floating-point arithmetic is random or unreliable. In fact it is fully deterministic: the same operations on the same inputs in the same order give the same bits on every IEEE 754 machine. What changes results is the order of operations (parallelism, compiler reassociation), fused multiply-add, and library choices.
People often think doubles are exact for integers and decimals. Doubles represent every integer exactly up to 2⁵³ ≈ 9 × 10¹⁵, but not beyond (database IDs of 64 bits stored in JSON as numbers lose their low digits in JavaScript). And decimals such as 0.1 and 19.99 are not exact in binary, so money should use integers (cents) or a decimal type.
People often think more bits always help. In fact the right format depends on the range and the noise tolerated. FP16 has more precision than BF16 but overflows above 65,504, which breaks training without loss scaling. BF16 trades precision for range. A narrow format with accumulation in a wider format is often both fast and accurate.
People often think comparing floats with == is the problem and a tolerance is always the answer. In fact an absolute tolerance fails across scales, and a relative one fails near zero. Choose a tolerance from the problem (both relative and absolute), and remember that NaN compares unequal to everything, including itself, so sorting and hashing floats with NaN need care.
tradeoffs: Choose FP64 for scientific computing, financial risk models with long chains of operations, and any algorithm that is ill-conditioned (such as solving nearly singular linear systems); its 16 digits give room to lose digits. You pay 2 times the memory and bandwidth of FP32 and, on GPUs, often 2 to 64 times lower throughput depending on the chip (consumer GPUs are very slow in FP64). Choose FP32 as the default for most numeric code and as the accumulator type in machine learning.
Choose BF16 for training large models when range matters and you want no loss scaling; choose FP16 when you need an extra three bits of precision and can manage scaling (inference is the usual case). Choose FP8 for matmul inputs and activations in training or inference on Hopper and later, with per-tensor or per-block scales, to halve memory traffic against 16-bit; choose FP4 (block-scaled) for inference on Blackwell-class hardware when a small quality loss on your task is acceptable after measuring.
Choose integers or decimals for money, counts and identifiers: Decimal types (Java BigDecimal, SQL DECIMAL(p,s)) give exact decimal arithmetic at the cost of speed (10 to 100 times slower than floats) and fixed precision. Choose integers in the smallest unit (cents) when range allows; they are exact and fast.
Choose compensated or pairwise summation when you sum many values and need accuracy (a few percent slower); choose a plain loop when relative error of a sum of n × u is fine. Choose bit-reproducible computation (fixed order of reduction, no fast-math, no FMA differences, or an integer or fixed-point accumulation) when results must match exactly across runs, for tests, audits or consensus; this costs speed because it prevents automatic parallelism and reordering.
friction: Rounding error is hard to see and test. Programs run, produce plausible numbers, and are wrong in the fifth digit. The same code gives slightly different results on different CPUs, compilers, optimization levels (fast-math allows reassociation and ignores NaN), and numbers of threads, which complicates testing and debugging, particularly in distributed training and in distributed SQL aggregations. In Spark and Databricks, a sum of doubles can differ between runs because the order in which partial sums are combined depends on data partitioning and task timing.
Special values cause trouble: NaN propagates silently through a computation and then appears only at the end; infinities arise from overflow; subnormal numbers are handled slowly on many CPUs (tens to hundreds of cycles per operation, which is why flush-to-zero modes exist) and are flushed or ignored by some GPU formats. Hardware formats differ too: x87 uses 80-bit internal registers, which gave different results from SSE; some accelerators round differently, truncate or do not support all rounding modes or subnormals.
Low-precision machine learning is an active research area: training in FP8 and FP4 needs careful scaling, loss spikes and divergence are common failure modes, and published recipes differ between vendors. Finally, languages hide the problems: JavaScript has only doubles, SQL has several float and decimal types with implicit conversions, and JSON has no way to say how a number should be stored, so a large integer ID can be silently rounded.
practice: Use double (FP64) by default for general computing unless you have a reason; use FP32 or lower for large arrays on GPUs, with FP32 accumulation. Never use floats for money or identifiers; use integers or decimal types. Do not compare floats with ==; use a relative-plus-absolute tolerance (math.isclose in Python, numpy.allclose), and use isnan for NaN. Put 64-bit IDs in JSON as strings.
Be aware of the order of operations. For sums over large data, use pairwise or Kahan summation (Python math.fsum, numpy's pairwise sum), or accumulate in a wider type. In Spark, expect small run-to-run differences in double aggregates, use DECIMAL for exact financial sums, and round results at the output instead of in the middle. For tests, compare with tolerances and fix the thread count or reduction order when you need bit-identical results.
For machine learning, start with BF16 or FP16 autocast with FP32 master weights and FP32 accumulation, and add loss scaling if you use FP16. Watch for NaN and inf (enable anomaly detection or checks on the loss), and compare quantized models with the full-precision model on your own metrics. Know the limits of each format: FP16 maximum 65,504, BF16 about 3 significant digits, FP8 E4M3 maximum 448.
To explore, print floats in hex (Python float.hex, struct.pack), use the Python decimal and fractions modules to see the exact value of a float (Decimal(0.1)), and use a numerical tool such as Herbie, which rewrites expressions to reduce rounding error. Read Goldberg's paper once, and keep the "floating-point-gui.de" rules in mind: floats are approximate, not unreliable.
quiz: How many bits are used for the sign, exponent and fraction in FP32 and FP64? || FP32 has 1, 8 and 23 bits; FP64 has 1, 11 and 52 bits. The bias is 127 and 1023.
Why does 0.1 + 0.2 not equal 0.3 in binary floating point? || 0.1, 0.2 and 0.3 have infinite binary expansions and are stored as the nearest float, each with a small error. The sum of the two stored values rounds to a float that differs from the stored 0.3 (it prints as 0.30000000000000004).
Why is floating-point addition not associative, and what does it imply for parallel sums? || Each addition rounds its exact result, so the rounding depends on the magnitudes of the operands at that step. A different grouping or order rounds differently, so a parallel reduction with a different number of threads or partitions can give a slightly different sum.
At what integer does FP32 stop representing every integer, and what happens if you add 1 to it? || At 2²⁴ = 16,777,216. The next float above is 16,777,218, so 16,777,216 + 1 is a tie and rounds (to even) back to 16,777,216: the increment is lost.
You must store prices and compute monthly totals for millions of orders in a Spark job. Which type do you use and why? || Use DECIMAL (or integer cents), not DOUBLE. Prices such as 19.99 are not exact in binary, errors accumulate over millions of additions, and double sums can vary between runs because of partition order. Decimal is exact and reproducible, at some speed cost.
interview: Explain what FP16, BF16 and FP8 give up compared with FP32, and why training copes. || FP16 keeps 10 fraction bits but only 5 exponent bits (maximum 65,504), BF16 keeps FP32's range with 7 fraction bits, and FP8 has 2 to 3 fraction bits. Neural networks are noise-tolerant, and stochastic gradient noise is larger than rounding noise; accumulation in FP32, master weights and scaling (loss scaling, per-block scales) keep the errors from growing and the values from overflowing.
How would you debug a result that differs by 1e-12 between two runs of the same Spark job? || Suspect a non-deterministic order of floating-point additions (shuffle order, partitioning, task retries) and not a logic error. Check by running with a fixed partitioning and a single thread, compare against a high-precision reference (decimal or fsum), and decide whether the difference is within tolerance. If exactness matters, use DECIMAL or integer arithmetic.
What is catastrophic cancellation? Give an example and a fix. || Subtracting two nearly equal numbers keeps the large leading digits, which cancel, and leaves the rounding noise. For (\( 1 - \cos x \)) with small x, the result is mostly noise; rewrite it as \( 2 \sin^2(x/2) \). The quadratic formula has the same problem and can be fixed by computing the larger root and deriving the other from the product of the roots.
Why do compilers need -ffast-math to vectorize a float sum, and what is the risk? || Vectorizing splits the sum into several partial sums, which reassociates additions and can change the result. Fast-math also lets the compiler assume no NaN or infinity, replace division by reciprocal, and flush subnormals. The risk is silently different or wrong results, so enable it only for code that tolerates this, or use explicit vector code with a known order.
How would you implement a reproducible parallel sum of doubles? || Fix the reduction tree independent of the thread count (for example, sum fixed-size blocks in order, then combine the block sums in a fixed order), or convert values to a wide integer accumulator (a superaccumulator or fixed-point) whose addition is exact and associative. Disable fast-math and FMA differences between platforms.

@@ binary
value: Computers store everything as bits, each 0 or 1, because a two-state signal is the easiest thing to make reliable: a transistor is clearly on or clearly off, and small noise does not change the answer. Numbers, text, images, machine instructions and network packets are all patterns of bits, and their meaning comes only from an agreement on how to read them. A group of 8 bits is a byte, and a group of 32 or 64 bits is a machine word, the unit that a CPU adds in one instruction.
For integers there are two standard readings. In unsigned binary, bit i of an n-bit number has the value \( 2^i \), so 8 bits give 0 to 255. In two's complement, the top bit has the value \( -2^{n-1} \) instead of \( +2^{n-1} \), so 8 bits give −128 to 127. The second reading is used for signed integers in almost every machine, because the same adder circuit then works for both: the hardware does not need to know whether the numbers are signed. Subtraction is addition of the negated number, and negation is "flip all bits and add 1".
This is the base of the layer above. Floating-point numbers (L3) are bit fields with a sign, a biased exponent and a fraction. Unicode and UTF-8 (L3) are rules for packing code points into bytes. Clustering and Z-ordering (L2) interleave the bits of several columns into one sort key. Memory-safety bugs (L3) often start with integer overflow in a length computation. Underneath, three L4 and L5 ideas explain why the encoding works. Boolean algebra (L4) makes each bit position a logic function, and an adder is built from XOR and AND gates; number theory (L4) says that n-bit integers form arithmetic modulo 2^n, so overflow is a wrap-around and negative numbers are just large numbers in disguise; and Leibniz (L5) described binary arithmetic in 1703, long before any machine used it.
terms: Bit, byte, word — one binary digit; 8 bits; and the natural width of the CPU's registers (64 bits on current servers).
Two's complement — the encoding of signed integers in which the negative of x is 2^n − x, so −1 is all ones.
Overflow — a result that does not fit in n bits; the stored value wraps around modulo 2^n.
Sign extension — widening a signed number by copying its top bit into the new upper bits, which keeps its value.
Arithmetic and logical shift — a right shift that copies the sign bit (arithmetic) or inserts zeros (logical); a left shift by k multiplies by 2^k.
Bit mask — a constant with ones at the positions of interest; AND with it extracts bits, OR sets them, AND with its complement clears them.
Endianness — the order of the bytes of a multi-byte number in memory: little-endian puts the least significant byte first (x86, Arm default), big-endian puts it last (network order).
Hexadecimal — base 16; each digit is exactly 4 bits, so two digits are one byte (0xFF = 255).
Varint — a variable-length integer encoding that uses fewer bytes for small values, as in Protocol Buffers and Kafka.
ZigZag encoding — a mapping of signed integers to unsigned ones (0, −1, 1, −2, 2 → 0, 1, 2, 3, 4) so small negative numbers also have short varints.
history: The idea of counting with two symbols is old, but Gottfried Leibniz gave binary arithmetic its first complete description. He wrote it in 1679 and published "Explication de l'arithmétique binaire" in 1703, seeing in it a calculus of reasoning and finding a link to the hexagrams of the I Ching. George Boole's 1854 "Laws of Thought" gave an algebra of true and false, and Claude Shannon's 1937 thesis connected it to switching circuits. John Tukey coined the word "bit", which Shannon used in his 1948 paper.
Early computers disagreed about negative numbers. Sign-magnitude (a sign bit and an absolute value) was natural but had two zeros and needed separate add and subtract circuits. One's complement (flip all bits to negate) was used in the CDC 6600 and similar machines and also had two zeros. Two's complement removed both problems, and became the standard with machines such as EDSAC (1949) and the IBM System/360 (1964). Byte-addressed memory and the 8-bit byte also spread with System/360. Later, the little-endian x86 line fixed the dominant byte order for personal computers and servers, while internet protocols chose big-endian ("network byte order"). Danny Cohen's 1980 note "On Holy Wars and a Plea for Peace" named the two camps after the egg-breaking factions of Gulliver's Travels.
The lessons of overflow came repeatedly. In 1996, the Ariane 5 rocket was lost after 37 seconds because a 64-bit floating-point value was converted to a 16-bit signed integer and overflowed. In 2006, Joshua Bloch described a bug in the binary search of the Java library, present for years: computing the midpoint as (low + high) / 2 overflows for arrays with more than 2³⁰ elements. In 2015, the FAA ordered Boeing 787 generators to be restarted periodically because an internal counter in hundredths of a second overflowed after 248 days. Software now often chooses 64-bit integers, checked arithmetic or arbitrary-precision numbers, and the Unix time_t problem of January 2038 shows how the same pattern repeats.
how: Unsigned binary is positional, like decimal with base 2. The 8-bit pattern 10110101 has the value 128 + 32 + 16 + 4 + 1 = 181. Addition works like schoolbook addition: add the bits from the right, write the sum bit and carry the rest. At each position a full adder takes two input bits and the carry, produces a sum bit = a XOR b XOR carry-in, and a carry-out. This is the Boolean-algebra layer at work, and it is how the hardware implements the integer add of the CPU. If the carry out of the top bit is 1, the unsigned result did not fit: this is unsigned overflow, and the stored result is the true sum minus 2^n.
Two's complement keeps this circuit and gives it a signed meaning. The key fact comes from number theory: with n bits, arithmetic is done modulo \( 2^n \), so the number \( 2^n - x \) behaves exactly like \( -x \), because \( x + (2^n - x) = 2^n \equiv 0 \). The pattern for \( 2^n - x \) is obtained by flipping all bits of x (which gives \( 2^n - 1 - x \)) and adding 1. So the 8-bit pattern for −5 is: 5 = 00000101, flipped = 11111010, plus 1 = 11111011 (0xFB, as unsigned 251 = 256 − 5). The top bit is 1 for negative numbers. The range is \( -2^{n-1} \) to \( 2^{n-1} - 1 \), asymmetric by one: −128 to 127 for 8 bits, so negating −128 gives −128 again. There is only one zero.
Because the arithmetic is the same, the adder is shared. Signed overflow is detected differently from unsigned overflow: it happens when two numbers of the same sign give a result of the opposite sign, or equivalently when the carry into the top bit differs from the carry out of it. Multiplying the low n bits of a product gives the same bits for signed and unsigned operands, which is why CPUs have one instruction for the low half and separate ones for the high half. Comparison, however, differs: the byte 0xFF is 255 unsigned and −1 signed, so CPUs provide separate signed and unsigned conditions, and a comparison of a signed with an unsigned value in C converts the signed one, so −1 > 1u is true.
Shifts and masks do much of the real work. A left shift by k multiplies by 2^k. A right shift divides by 2^k, with a difference: an arithmetic shift of a negative number rounds toward minus infinity (−5 >> 1 = −3), while C division rounds toward zero (−5 / 2 = −2). Bit tricks follow from the arithmetic of two's complement: x & (x − 1) clears the lowest set bit (used to count bits and to iterate over set bits of a bitmap); x & −x isolates the lowest set bit; (x & (x − 1)) == 0 tests for a power of two. Flags are packed into one integer (Unix permissions 0755 is 111 101 101), and Bloom filters, bitmaps and Roaring bitmaps are arrays of bits manipulated in 64-bit words. Z-order keys interleave the bits of coordinates, so that numbers close in several dimensions are close in the one-dimensional key.
Multi-byte numbers need a byte order. The 32-bit value 0x12345678 is stored in memory on a little-endian machine as the bytes 78 56 34 12, and on a big-endian one as 12 34 56 78. Nothing is wrong with either, but files and network protocols must say which they use: TCP/IP headers are big-endian, so code calls htonl and ntohl; Parquet and Arrow use little-endian. A mismatch produces numbers that look random but are only byte-swapped.
Finally, fixed width is wasteful for small numbers, so formats use variable-length encodings. A varint (as in Protocol Buffers, and the LEB128 format) stores 7 bits of the number in each byte, with the top bit set when more bytes follow. The number 300 is 100101100 in binary; the low seven bits are 0101100 (0x2C) and with the continuation bit give 0xAC; the remaining bits 10 give 0x02. So 300 is the two bytes AC 02, instead of four. Signed values would have ten bytes for any negative number in this scheme (a negative number has all high bits set), so ZigZag maps −1 to 1, 1 to 2, −2 to 3 and so on with (n << 1) XOR (n >> 31), and Kafka's record format and Protocol Buffers sint types use that.

example: Take 8-bit signed integers. Add 100 and 50. In binary, 100 = 01100100 and 50 = 00110010. The sum is 10010110. As unsigned this is 150, which is correct as a count. As signed, the top bit is 1, so it is −128 + 22 = −106. The result is wrong: two positive numbers gave a negative one, which is signed overflow. The true sum 150 is 256 − 106, the wrap-around modulo 256. The hardware flagged it: the carry into the top bit was 1, and the carry out of it was 0.
Now negate 5 and add: 5 + (−5) = 00000101 + 11111011 = 1 00000000. The ninth bit is the carry out; it is dropped, and the stored result is 0. This is why no special subtract circuit is needed. For −128 = 10000000, flipping gives 01111111 and adding 1 gives 10000000, which is −128 again, so abs(−128) fails in 8 bits.
Next, the binary search bug with 32-bit signed ints. Let low = 1,500,000,000 and high = 2,000,000,000 in a very large array. low + high = 3,500,000,000, which exceeds 2,147,483,647. It wraps to 3,500,000,000 − 4,294,967,296 = −794,967,296. Dividing by 2 gives −397,483,648, a negative index, and the program throws an exception or reads wrong memory. Safe versions compute low + (high − low) / 2 (the difference cannot overflow) or use an unsigned shift (low + high) >>> 1.
Then the Boeing 787 counter. A 32-bit signed counter incremented every 10 ms overflows after 2³¹ ticks = 2,147,483,648 × 0.01 s = 21,474,836 s = 248.55 days. A generator control unit powered on for 248 days would hit the overflow, so the FAA required a restart schedule in 2015 until the software was fixed.
Last, a varint comparison. A Kafka-like record field with the value 300 takes 2 bytes as a varint; a field with the value 5 takes 1 byte, versus 4 bytes in fixed 32-bit. For a stream of one billion small offsets, averaging 1.3 bytes versus 4, the saving is about 2.7 GB, at the cost of branching during decoding (which SIMD varint decoders reduce).
intuition: Everything is a long row of light switches; meaning comes from agreeing how to read them.
A switch has two positions, and a row of n switches has 2^n combinations, so a few dozen of them can name any number a program needs. The reading rule decides what the pattern means; two's complement was chosen so that one circuit does arithmetic for both positive and negative numbers. It works because a fixed number of bits is a clock face of 2^n hours: going back 5 hours is the same as going forward 2^n − 5. Once you see numbers as positions on a circle, overflow is just passing 12 o'clock.
mistakes: People often think that a variable has a type inside the machine. In fact memory holds only bits; the type is in the instructions and the program that interpret them. The same four bytes can be a 32-bit integer, a float, four characters or an address, and many bugs and exploits come from reading bits with the wrong rule.
People often think overflow is an error that the machine reports. In fact, most hardware silently wraps around, and C and C++ treat signed overflow as undefined behavior, which lets the compiler assume it never happens and delete checks written as if (x + 1 < x). Java wraps silently, Rust panics in debug builds and wraps in release builds by default, and Python has no overflow because it uses arbitrary-size integers. Use checked or wider arithmetic where values come from outside.
People often think a right shift is the same as division. In fact for negative numbers an arithmetic shift rounds toward minus infinity and C division rounds toward zero, so −5 >> 1 is −3 and −5 / 2 is −2. A logical shift on a signed value gives a huge positive number.
People often think big-endian or little-endian is "better". In fact neither has a technical advantage that matters now; the cost comes only from mismatch. The rule is to define the byte order in every file format and protocol, convert at the boundary, and never write a struct to disk or to the network by copying its memory.
tradeoffs: Choose 64-bit signed integers (long, int64) as the default for counters, sizes, IDs and timestamps; they hold up to 9.2 × 10¹⁸ and avoid most overflow. Choose 32-bit values only when memory or bandwidth decides (arrays of billions, SIMD lanes, GPU registers), and then check every computation that could exceed 2.1 × 10⁹, such as byte offsets and products.
Choose unsigned types for bit patterns, hashes, masks and sizes that must not be negative, with care: subtracting two unsigned values wraps to a huge number (size_t comparisons are a classic bug). Choose signed types for quantities that can be compared and differenced, where a negative value is meaningful and a bug is easier to see.
Choose fixed-width encodings (4 or 8 bytes) when random access and speed matter: you can compute the position of the i-th value and SIMD-decode it. Choose varints when most values are small and you read sequentially (Protocol Buffers, Kafka records, index postings), saving 50 to 75% of space, and accept slower decoding and no random access. Choose bit-packing with a fixed bit width per block (Parquet, Lucene) as a middle path: dense, and fast with SIMD.
Choose checked arithmetic (Math.addExact in Java, checked_add in Rust) at trust boundaries and in financial or size calculations, accepting a small speed cost; choose wrapping arithmetic deliberately for hashes, checksums and random number generators, where mod 2^n is the intent. Choose arbitrary precision (BigInteger, Python int) when the range is not bounded, as in cryptography, giving up speed.
friction: Binary representation causes quiet bugs. Overflow and sign errors in length, offset or index computations turn into buffer overflows and security holes; a 32-bit multiplication of two sizes can wrap and lead to an allocation that is too small. Mixing signed and unsigned types in comparisons gives surprising results through implicit conversion rules. Types differ by language and platform: the width of long is 32 bits on 64-bit Windows and 64 bits on Linux; char may be signed or unsigned.
Interoperability is hard: endianness, struct padding and alignment, and different integer widths all matter when data crosses machines, languages, or years. JavaScript's numbers are doubles, so integers above 2⁵³ lose precision; JSON offers no integer type; a 64-bit ID sent through a browser can be corrupted. Time values show the long-term problem: 32-bit time_t overflows on 19 January 2038, and embedded systems that will still be running then must be found and fixed.
Bit-level code is also hard to read and to verify. Clever masks and shifts are error-prone, undefined behavior (shifting by the word width or more, signed overflow) differs between compilers and optimization levels, and tests rarely cover the extremes. Tools help (sanitizers such as UBSan, fuzzing, static analysis, property-based tests at the boundaries), but the only reliable defense is careful handling of ranges at every input.
practice: Know the limits by heart: 2¹⁰ ≈ 10³, 2³¹ − 1 = 2,147,483,647, 2³² = 4,294,967,296, 2⁵³ ≈ 9 × 10¹⁵, 2⁶³ − 1 ≈ 9.22 × 10¹⁸. For any computation, ask what the largest intermediate value is, not only the final result: (a × b) / c overflows if a × b does, even when the quotient is small. Cast to the wider type before multiplying. Compute midpoints as low + (high − low) / 2.
Use explicit-width types (int32_t, uint64_t, Rust's i32 and u64, Java's int and long) and fix the byte order in file formats and protocols. Serialize with a library (Protocol Buffers, Avro, Arrow, Parquet) instead of copying structs. When a number crosses to JavaScript or JSON, send 64-bit IDs as strings. For bit sets and flags, use named constants or enums and masks, and test bits with (x & MASK) != 0.
Turn on the safety nets: compile with -fsanitize=undefined,address in tests; use Rust or checked arithmetic for parsing code; fuzz the parsers; enable compiler warnings for sign comparison (-Wsign-compare). In Java and Kotlin, use Math.addExact, multiplyExact and toIntExact at boundaries. In Spark SQL, know that integer overflow behavior depends on the ANSI mode setting (without it, overflow wraps silently; with it, Spark raises an error, and ANSI mode became the default in Spark 4.0), and that casting between types can silently truncate.
To practice, print values in binary and hex while you work (Python bin(), hex(), int.to_bytes, struct.pack), write a two's complement adder from the logic gates, implement a varint encoder, and read the bytes of a Parquet or Protobuf file with a hex dump. These exercises show where the types and arithmetic of your language come from.
quiz: How do you negate a number in two's complement, and why does it work? || Flip all bits and add 1. Flipping gives 2^n − 1 − x; adding 1 gives 2^n − x, which equals −x modulo 2^n, and the machine works modulo 2^n.
What range does an 8-bit two's complement integer have, and what is special about its minimum value? || −128 to 127. The negation of −128 does not fit in 8 bits: flipping and adding 1 gives −128 again, so abs(−128) and −(−128) overflow.
Why does the same adder circuit work for signed and unsigned integers? || Both are arithmetic modulo \( 2^n \); two's complement just reads the same bit patterns with the top bit weighted \( -2^{n-1} \). The sum bits are identical; only the overflow condition and the interpretation differ.
Compute (low + high) / 2 in 32-bit signed arithmetic for low = 1.6 × 10⁹ and high = 1.9 × 10⁹. What happens and what is the fix? || The sum 3.5 × 10⁹ exceeds 2,147,483,647 and wraps to about −794,967,296; halving gives a negative index. Use low + (high − low) / 2, or an unsigned shift (low + high) >>> 1.
Encode 300 as a Protocol Buffers varint, and say why ZigZag exists. || 300 = 0b100101100; low 7 bits 0101100 with the continuation bit gives 0xAC, then the next bits 10 give 0x02: bytes AC 02. A negative int has all high bits set and would take 10 bytes, so ZigZag maps small negative numbers to small unsigned ones first.
interview: What is undefined about signed overflow in C, and how can it make a security check disappear? || The standard leaves the result undefined, so the compiler may assume it never occurs. A check like if (x + 100 < x) is always false under that assumption and can be removed. Use unsigned arithmetic, compiler flags such as -fwrapv, or check the range before the operation, for example x > INT_MAX − 100.
How would you find the position of the lowest set bit and count the set bits of a 64-bit word, and where do you use it? || x & −x isolates the lowest set bit; a count-trailing-zeros instruction gives its index; popcount counts bits in one instruction. They are used to iterate over set bits of bitmaps, in Roaring bitmaps, bit-packed filters, free-block allocators and SIMD mask processing (iterate with x &= x − 1).
Why is two's complement preferred over sign-magnitude and one's complement? || Both alternatives have two zeros and need extra logic for addition and subtraction. Two's complement has a single zero, makes addition and subtraction use the same circuit as unsigned, and extends cleanly to wider widths by sign extension.
How should a service send a 64-bit database ID to a browser client, and why? || As a string. JavaScript numbers are doubles with 53 bits of integer precision, so IDs above 2⁵³ are rounded and two different IDs can become equal. JSON itself has no integer width, so the contract must say how it is encoded.
You see 32-bit counters in a system that runs for years. What risks do you look for? || Wrap-around of counters (248 days for 10 ms ticks, 49.7 days for 1 ms ticks in unsigned 32-bit, 2038 for time_t), comparisons that break after wrap, and allocations computed with overflowing products. Fix with 64-bit counters, wrap-safe comparison (subtract then compare as signed), or monotonic clocks, and test by starting counters near the limit.
