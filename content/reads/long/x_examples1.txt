# Worked examples: concrete walk-throughs with real numbers.

@@+ kafka
example: Follow one ad-impression event. A bidder sends {device: d42, campaign: c7, ts: 10:00:01.250} to the topic impressions, which has 12 partitions, replication factor 3, min.insync.replicas = 2, and the producer uses acks = all, linger.ms = 5 and lz4 compression.
The producer hashes the key d42 with murmur2; say the result modulo 12 is 7, so the record goes to partition 7. It waits up to 5 ms to fill a batch with other records for partition 7 (perhaps 300 records, about 60 KB, compressing to 15 KB) and sends the batch to broker B2, the current leader of partition 7.
B2 appends the 15 KB to the end of the active segment file 00000000000004821733.log with one write call; the bytes land in the page cache. Followers B1 and B3 are already waiting in fetch requests; they receive the batch, append it to their own logs and fetch again, which tells B2 how far they have copied. When both have it, B2 moves the high watermark past the batch and answers the producer: offsets 4,830,100 to 4,830,399 are committed. Elapsed time: about 5 ms of linger plus a few milliseconds of network and replication.
Now a consumer group pacing-service with 4 members reads the topic; member 2 owns partitions 6, 7 and 8. It fetches from partition 7 starting at its committed offset 4,830,000, receives the compressed batch exactly as stored (B2 sends it from the page cache with sendfile, never decompressing it), processes the 300 events and commits offset 4,830,400. If member 2 crashes before committing, the group rebalances, another member takes partition 7, and it re-reads from 4,830,000: the events are processed again, which is why the pacing service must be idempotent or use transactions.
If B2 dies, the controller (a KRaft quorum) picks B1 or B3, both in the in-sync replica set, as the new leader within seconds. Because acks = all waited for both, no acknowledged event is lost. If only B2 had been in sync, min.insync.replicas = 2 would have made producers fail fast instead of risking loss.

@@+ raft
example: Five nodes A to E run Raft; A is leader in term 4 and every log holds entries 1 to 10 committed. A client sends SET x=5. A appends it as entry 11 (term 4), sends AppendEntries to B to E with 'previous entry is index 10, term 4'. B, C and D accept and reply; E is slow. With A itself, 4 of 5 have entry 11, more than a majority of 3, so A marks it committed, applies x=5 and replies to the client. The next heartbeat tells followers that the commit index is 11, and they apply it too.
Now A's network cable is pulled. B's election timer (randomized, say 180 ms) fires first. B increments the term to 5, votes for itself and asks the others for votes, saying 'my last entry is index 11, term 4'. C and D grant their votes, because B's log is at least as up to date as theirs and they have not voted in term 5. E, which is missing entry 11, also grants (B is more up to date). B wins with 4 votes and starts sending heartbeats for term 5.
Meanwhile A, isolated, still thinks it is leader and accepts SET y=7 as entry 12 in term 4, but cannot reach a majority, so it never commits it and never replies success. When the cable is fixed, A receives a message with term 5, steps down to follower, and B's AppendEntries reveals that A's entry 12 (term 4) conflicts with B's log; A deletes it and copies B's entries. The client that sent SET y=7 gets a timeout, retries against B, and the system never showed y=7 as committed. This is exactly the safety property: a committed entry (x=5) survives leader change; an uncommitted one (y=7) may vanish, and clients must retry.

@@+ mvcc
example: In PostgreSQL, an account row has balance 100, written by transaction 900, so the tuple has xmin = 900 and xmax = 0 (not deleted). At time t1, a reporting transaction T1 (ID 1000) starts under REPEATABLE READ and takes a snapshot: all transactions below 1000 that have committed are visible.
At t2, transaction T2 (ID 1001) runs UPDATE accounts SET balance = 70. PostgreSQL does not overwrite the row: it sets xmax = 1001 on the old tuple and inserts a new tuple with balance 70, xmin = 1001. T2 commits.
At t3, T1 reads the account again. For the old tuple, xmin 900 is committed and visible to T1, and xmax 1001 is not visible to T1's snapshot (it started later), so for T1 the old tuple is still alive: T1 sees 100. The new tuple's xmin 1001 is not in T1's snapshot, so T1 ignores it. A new transaction T3 started at t3 sees 70. Readers never waited for the writer, and the writer never waited for readers.
Both versions stay in the table. Once T1 finishes and no running transaction has a snapshot older than 1001, VACUUM can remove the old tuple and mark its space reusable. If T1 had been an analyst's session left open 'idle in transaction' for a day, VACUUM could not remove any tuple deleted after it started, across the whole database, and update-heavy tables would bloat: the most common way MVCC hurts in production.

@@+ btree
example: An index on orders(customer_id) covers 1 billion rows. Each index entry (an 8-byte key plus a 6-byte row pointer and overhead) takes about 20 bytes, so an 8 KB page holds about 400 entries. The leaf level needs about 2.5 million pages (about 20 GB). The level above holds one entry per leaf page: 2.5 million entries, about 6,250 pages. The next level: about 16 pages. Then the root: one page. So the tree has four levels.
A lookup for customer_id = 42 reads the root, picks the child whose key range contains 42, reads that page, and so on: four page reads. The root and the second level (about 6,250 pages, 50 MB) easily stay in memory, so in practice a lookup needs one or two reads from disk, roughly 0.1–0.2 ms on NVMe, even though the table has a billion rows. A range query (customer_id between 42 and 45) finds the first leaf and then walks the linked leaves sequentially.
Insertions go into the right leaf. When a leaf is full, it splits into two half-full leaves and a new separator key is added to the parent, which may split in turn; very rarely the root splits and the tree grows one level taller. Every split is logged in the write-ahead log first, so a crash mid-split can be repaired. If keys are random (random UUIDs), inserts land on random leaves across the 20 GB of leaf pages, so most need a disk read and many splits happen everywhere; with increasing keys (timestamps, UUIDv7), inserts hit the rightmost leaf, which stays in memory.

@@+ lsm
example: RocksDB stores user profiles with 100-byte values, using leveled compaction with a size ratio of 10, a 64 MB memtable and Bloom filters with 10 bits per key.
Writes: each update appends to the WAL and inserts into the in-memory memtable (a skip list), taking a few microseconds. When the memtable reaches 64 MB, it becomes immutable and is flushed as a sorted SST file into level 0. Background compaction merges level-0 files into level 1 (about 256 MB), and when level 1 exceeds its target, some of its files are merged into level 2 (about 2.5 GB), then level 3 (25 GB), level 4 (250 GB). Each byte is rewritten roughly once per level times the overlap, so total write amplification is often 10–30×: the price paid for turning random updates into sequential writes.
Reads: a Get for user u123 first checks the memtable, then level-0 files, then exactly one file per deeper level (files within a level do not overlap), using each file's index block to find the right data block. For levels that do not contain u123, the Bloom filter answers 'definitely not here' with a 1% false-positive rate, so the read usually touches only one data block on disk: the one holding the newest version. Upper levels' index and filter blocks sit in the block cache.
Deletes: deleting u123 writes a tombstone. Older values in deeper levels are hidden by it but still occupy space until compaction pushes the tombstone down and drops both. A job that deletes millions of keys can therefore make range scans slower (they must skip tombstones) until compaction catches up, and if writes outpace compaction, RocksDB slows or stalls writes to protect read performance.

@@+ attention
example: Take a tiny model with embedding size 4 and the sentence 'cats chase mice'. Each token's embedding is multiplied by three learned 4×4 matrices to produce a query, a key and a value. Suppose the query for 'chase' is q = [1, 0, 1, 0], and the keys are: cats k1 = [1, 0, 1, 0], chase k2 = [0, 1, 0, 0], mice k3 = [1, 0, 0, 1].
Scores are dot products divided by √4 = 2: q·k1 = 2 → 1.0; q·k2 = 0 → 0.0; q·k3 = 1 → 0.5. Softmax turns [1.0, 0.0, 0.5] into weights: e¹ ≈ 2.72, e⁰ = 1, e⁰·⁵ ≈ 1.65, summing to 5.37, so weights ≈ [0.51, 0.19, 0.31]. The output for 'chase' is 0.51 × v_cats + 0.19 × v_chase + 0.31 × v_mice: a new vector that mixes in information about who chases and what is chased. A different head, with different matrices, might focus on word order or grammar instead.
Scale this up: a model with 4,096-dimensional embeddings, 32 heads of size 128, and a 8,000-token prompt computes, per head and layer, an 8,000 × 8,000 score matrix (64 million entries). Across 32 heads that is 2 billion scores per layer, which is why naive attention runs out of memory and why FlashAttention computes it tile by tile without storing the matrix. During generation, the queries come only from the newest token, while keys and values for all earlier tokens are read from the KV cache.

@@+ gd
example: Fit \( y = w x \) to three points: (1, 2), (2, 4), (3, 6.5), using mean squared error \( L(w) = \tfrac{1}{3} \sum_i (w x_i - y_i)^2 \). Its gradient is \( dL/dw = \tfrac{2}{3} \sum_i x_i (w x_i - y_i) \). Start at w = 0 with learning rate 0.1.
At w = 0: errors are −2, −4, −6.5; gradient = (2/3)(1·−2 + 2·−4 + 3·−6.5) = (2/3)(−29.5) ≈ −19.67. Update: w = 0 − 0.1 × (−19.67) ≈ 1.97. At w = 1.97: errors ≈ −0.03, −0.06, −0.59; gradient ≈ (2/3)(−0.03 − 0.12 − 1.77) ≈ −1.28; w ≈ 2.10. At w = 2.10: errors ≈ 0.10, 0.20, −0.20; gradient ≈ (2/3)(0.10 + 0.40 − 0.60) ≈ −0.07; w ≈ 2.11, close to the exact least-squares answer 29.5/14 ≈ 2.107. Three steps did almost all the work.
If the learning rate were 0.2, the first step would jump to w ≈ 3.93, past the minimum, and the next gradient would push back too far: w would zigzag around the minimum and settle only slowly. Above a learning rate of about 0.214 (2 divided by the curvature, 9.33), each zigzag would grow instead of shrink, and at 0.25 the loss would diverge. With 0.01, progress would be ten times slower. This is the same tension practitioners manage when training networks with billions of weights, where the 'gradient' is a vector of billions of numbers computed by backpropagation on a mini-batch, and optimizers like AdamW adapt the step size for each weight.

@@+ wal
example: A PostgreSQL transaction transfers 50 from account A to account B: two UPDATE statements and a COMMIT. Each UPDATE modifies a heap page (and maybe index pages) in shared buffers in memory, and appends WAL records describing those changes, each with a log sequence number (LSN), say 0/3A000100 and 0/3A000180. Nothing has been written to the table files yet.
At COMMIT, PostgreSQL appends a commit record (LSN 0/3A000200) and calls fsync on the WAL segment file up to that position. On a good NVMe drive with power-loss protection this takes about 50–200 µs; on network block storage it may take a millisecond or more. If 20 other transactions commit at nearly the same moment, group commit flushes them all with one fsync. Only after the flush returns is the client told 'COMMIT'.
The modified data pages are written to the table files later by the background writer or the next checkpoint (by default at least every 5 minutes). Suppose the server loses power two seconds after the commit, before those pages were written. On restart, PostgreSQL reads the last checkpoint location from the control file, then replays every WAL record after it: it reapplies the two updates (redo), and since the transaction's commit record is in the log, the transfer is complete. A transaction that had written its UPDATE records but not its commit record is simply treated as aborted: its changes are invisible because it never committed. The same WAL stream, shipped to a standby, keeps a replica up to date.

@@+ isolation
example: A hospital rule says at least one doctor must be on call. Alice and Bob are both on call. Each, at the same moment, asks to go off call; the application runs, for each request: begin; count doctors on call; if count ≥ 2, update my row to off call; commit.
Under snapshot isolation (PostgreSQL REPEATABLE READ), both transactions take snapshots in which 2 doctors are on call. Alice's transaction updates Alice's row; Bob's updates Bob's row. They write different rows, so there is no write–write conflict, and both commit. Now nobody is on call: write skew. READ COMMITTED behaves the same way here.
Under SERIALIZABLE in PostgreSQL, serializable snapshot isolation tracks that each transaction read data the other later wrote (a read–write dependency in both directions, forming a dangerous structure). When the second transaction tries to commit, it fails with 'could not serialize access due to read/write dependencies'. The application retries it; on retry, the count is 1, so the request is refused. The rule holds.
Alternatives without SERIALIZABLE: lock the rows being counted (SELECT ... FOR UPDATE on all on-call doctors), so the second transaction waits for the first and then sees the new count; or turn the rule into data the database can enforce (a separate shift row both transactions must update, which creates a real write–write conflict). The lesson is that business rules spanning several rows need either serializable isolation or explicit locking; snapshot isolation alone will not protect them.

@@+ columnar
example: A table of 1 billion ad impressions has 60 columns; a row averages 400 bytes, so the raw data is about 400 GB. The query is SELECT country, SUM(revenue) FROM impressions WHERE date = '2026-10-25' GROUP BY country.
In a row store, the engine must read every row of the day's data, all 60 columns, to get 3 of them. If a day is 30 million rows, that is 12 GB read to use about 0.6 GB.
In Parquet, each column is stored separately. date is sorted within files, so row-group statistics (min and max) let the reader skip every row group not from 2026-10-25: 29 million out of 1 billion rows remain, a few dozen row groups. country has about 200 distinct values: dictionary-encoded, each value becomes a 1-byte code, and runs of the same country compress further; 30 million values take perhaps 10–20 MB. revenue is a decimal stored as integers in micro-units with bit-packing and Zstd: perhaps 60–100 MB. So the query reads about 100 MB instead of 12 GB, over 100 times less.
Execution then works on the encoded data: group by the 1-byte country code using a 256-entry array of partial sums (no hash table needed), processing values in batches of a few thousand with SIMD instructions, and translate codes back to country names only for the final 200 rows. On a laptop with DuckDB, this kind of query over a day's data finishes in well under a second.

@@+ tcp
example: A service in Bengaluru calls an API in Virginia: round-trip time about 220 ms. A new TCP connection costs one round trip for the handshake, and with TLS 1.3 one more for the TLS handshake, so about 440 ms pass before the first request byte is sent, even though the request itself is tiny. Reusing a kept-alive connection removes both.
Now the service downloads a 10 MB response. TCP starts with a congestion window of about 10 segments (about 14 KB). Slow start doubles the window every round trip: 14 KB, 28 KB, 56 KB, 112 KB and so on, so reaching a window large enough to fill a 100 Mbit/s path (the bandwidth–delay product: 100 Mbit/s × 0.22 s ≈ 2.75 MB in flight) takes about 8 round trips, almost 2 seconds, during which the link is underused. A fresh connection's first megabytes therefore crawl; a warm connection with a large window moves them quickly.
If a packet is lost, the receiver keeps acknowledging the last in-order byte; three duplicate acknowledgements trigger a fast retransmit, and CUBIC cuts the window (by 30%), then grows it back over many round trips. Over a long, lossy path, throughput can fall far below link capacity; BBR, which paces based on measured bandwidth and RTT rather than loss, often does much better there. If the receiver's socket buffer is smaller than 2.75 MB, the advertised receive window caps throughput no matter what congestion control does, which is why cross-region replication and transfers need large socket buffers.
