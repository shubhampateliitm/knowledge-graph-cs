@@ ratelimit
value: Rate limiting decides, for every incoming request, whether the caller has used more than its share. If it has, the request is rejected or delayed (HTTP 429 "Too Many Requests") before it can do work. The most common mechanism is the token bucket: a counter that refills at a fixed rate and is spent one unit per request. It gives a clean contract: "you may average 10 requests per second, and you may burst up to 20 at once".
The problem it solves is simple and old. Every service has a finite capacity, and the clients of a service do not coordinate with each other. A bug in one client (a retry loop with no delay), one noisy tenant, or a scraper can send ten times the normal traffic. Without a limit, the service slows down for everyone, queues grow, timeouts cause retries, and retries add more load. A limit turns an unpredictable overload into a predictable, local rejection that the guilty caller sees, while other callers keep their latency. It is also how products are priced and protected: a free tier gets 60 requests per minute, a paid tier gets 6,000, and a login endpoint allows 5 attempts per minute to slow down password guessing.
For the layer above, API gateways, service meshes, multi-tenant platforms and microservices all need this one building block. A gateway applies it per API key at the front door. A service mesh proxy such as Envoy applies it per route or per caller. A multi-tenant database applies quotas so one tenant cannot starve the rest. The layers below make it cheap and predictable. A token bucket is just a bounded counter, so it costs two numbers of state per caller (queues and counters, L3). Queueing theory (L4) explains why the limit is needed and where to set it: latency grows without bound as arrival rate approaches service rate, so a limit below capacity keeps queues short.
terms: Token bucket — a counter that holds at most B tokens, gains r tokens per second, and loses one token for each accepted request.
Burst size (capacity) — B, the largest number of requests that can be accepted at once after a quiet period.
Rate — r, the long-run average number of requests per second that the limiter allows.
Leaky bucket — a bounded queue that is drained at a fixed rate; extra requests wait or are dropped, so the output is smooth.
Fixed window — a counter per time slice (for example per minute) that resets at the slice boundary.
Sliding window — a limit counted over "the last T seconds" ending now, either exactly (log of timestamps) or by approximation.
429 and Retry-After — the HTTP status for "too many requests" and the response header that tells the caller how many seconds to wait.
Load shedding — rejecting work because the whole service is overloaded, as opposed to rate limiting a particular caller for using too much.
history: The ideas come from telecommunications, not from the web. In 1986 Jonathan Turner described the leaky bucket in "New directions in communications" as a way to police how fast a source sends cells into a network. In the early 1990s, ATM networks standardized the Generic Cell Rate Algorithm (GCRA) in ITU-T I.371 and the ATM Forum specifications. It is equivalent to a token bucket but stores one timestamp instead of a counter. Networking textbooks such as Tanenbaum's "Computer Networks" taught the token bucket and the leaky bucket as the two standard "traffic shaping" tools. Linux has had a token bucket filter (tbf) in its traffic control subsystem for a long time.
Web services rediscovered the problem when public APIs appeared in the 2000s. Early limiters were simple fixed-window counters in a database or memcached. RFC 6585 (2012) added the 429 status code, so there was finally a standard way to say "slow down". The 2010s brought the distributed versions: Lyft's Envoy proxy (2016) introduced a separate global rate limit service that many proxies call; Stripe's 2017 engineering post "Scaling your API with rate limiters" described a token bucket on Redis plus separate load shedders for overload; Cloudflare's 2017 post described a sliding window counter that uses very little memory per client. Brandur Leach's redis-cell module (2016) put GCRA directly inside Redis as one command.
The practice has also become part of the HTTP contract. Many APIs return headers such as X-RateLimit-Remaining, and an IETF working group has been standardizing a common RateLimit header field, so clients can slow down before they are rejected. The check on the exact state of that draft is worth doing before you depend on it.
how: A token bucket has three numbers: capacity B, refill rate r (tokens per second), and the current token count. A request that arrives takes one token and is accepted if a token is available; otherwise it is rejected or delayed. Because tokens accumulate while the caller is quiet, up to B of them, the caller can burst. Over a long time, the accepted rate cannot exceed r. In any window of T seconds, at most B + r × T requests can be accepted. This is the whole contract, and it is why the bucket is easy to explain to API users.
Nobody runs a timer that adds tokens. The implementation is lazy. For each caller, store two values: the token count and the time of the last update. When a request arrives at time now, compute tokens = min(B, tokens + (now − last) × r), set last = now, and then check and spend. This costs O(1) time and about 16 bytes per caller. Millions of callers fit in memory. This is the first place where the layer below matters: a bounded counter with a lazy update (queues and counters, L3) is all the state you need.
The leaky bucket is the mirror image, and it uses the queue directly. Requests go into a bounded FIFO queue (often a ring buffer); a worker takes one out every 1/r seconds. If the queue is full, the new request is dropped. The output is perfectly smooth, but accepted requests wait in the queue, so latency goes up. A token bucket as a "meter" says yes or no immediately and lets bursts through; a leaky bucket as a "shaper" delays requests to make the output smooth. Nginx's limit_req is a leaky bucket: its burst setting is the queue size, and the nodelay option makes it behave like a token bucket.
Window counters are the cheap alternative. A fixed window keeps one counter per caller per minute and resets it on the boundary. It is trivial, but it allows double the limit across a boundary: 100 requests in the last second of one minute and 100 in the first second of the next. A sliding window log keeps every timestamp, which is exact but costs memory proportional to the limit. A sliding window counter keeps just two counters, for the current and previous window, and estimates the count as previous × (fraction of the previous window still inside the sliding window) + current. This is cheap and, in Cloudflare's measurements, wrong for only a tiny fraction of requests.
Where does the limit come from? Queueing theory (L4) gives the reason and the rule. In a simple single-server queue, the average time in the system is \( 1/(\mu - \lambda) \), where μ is the service rate and λ the arrival rate. As λ approaches μ, the delay grows without bound. Little's law (\( L = \lambda W \)) says the number of requests in flight grows the same way. So a service should publish limits whose sum stays safely below μ, usually 60–80% of the capacity you measured, so that queues stay short and the system has room for failures. Per-caller limits protect fairness; a global limit protects the service.
Distributed limiting is the hard part. One proxy can keep its buckets in local memory. But with 20 gateway instances behind a load balancer, a caller's requests are spread across all 20. There are three choices. The first is a central store: every check calls Redis, usually through a small Lua script so that read, update and write happen atomically. This is exact but adds a network round trip (roughly 0.2–1 ms inside one data centre) and makes Redis a dependency. The second is to split the limit: give each of N instances limit/N, which is local and fast but wrong when traffic is uneven. The third is a hybrid: each instance takes a batch of tokens from the central store and spends them locally, refilling when empty. This trades a little accuracy for far fewer remote calls. Envoy supports both a local token bucket filter and a global rate limit service.
Finally, rejection must be handled well. The server should return 429 with a Retry-After header. The client should wait that long, add random jitter, and use exponential backoff. A client that retries immediately turns a rejection into more load, which is the feedback loop that limiting was meant to break.

example: Take r = 10 requests per second and B = 20. The bucket starts full, so tokens = 20 at time 0.
A client sends 30 requests in the same instant. The first 20 each take one token and are accepted. The bucket is now empty, so requests 21 to 30 are rejected with 429. The client waits. After 0.5 seconds, the lazy update gives tokens = min(20, 0 + 0.5 × 10) = 5, so 5 more requests can pass. After 2 seconds of silence, the bucket is full again, because 20 tokens at 10 per second takes 2 seconds. The most this client can ever send in one second is B + r × 1 = 30 requests. Over one hour, the most it can send is 20 + 10 × 3600 = 36,020, which is almost exactly 10 per second on average.
Now see why the limit protects the server. Suppose the service can handle μ = 1,000 requests per second with a 1 ms service time. With the simple single-server model, mean latency is \( 1/(\mu - \lambda) \). At λ = 900 per second, latency is 1/100 = 10 ms. At λ = 990, it is 1/10 = 100 ms. At λ = 999, it is 1 second. The service did not get slower; the queue grew. A total limit of 900 per second keeps the worst case at about 10 ms. Without it, one burst of retries from a bug can push λ above μ, and the queue then grows until timeouts fire.
Now compare window types with a limit of 100 requests per minute. With a fixed window, a client sends 100 requests at 12:00:59 and 100 more at 12:01:00. Both bursts are accepted, so 200 requests arrive in two seconds. With the sliding window counter at 12:01:15 (25% into the current window), suppose the previous window had 84 requests and the current one has 36. The estimate is 84 × 0.75 + 36 = 99. One more request is accepted (estimate 100), and the next one is rejected. The boundary trick no longer works, and the state is only two integers per caller.
Last, a distributed case. A caller has a global limit of 1,000 per minute and talks to 10 gateway instances. If each instance uses a local limit of 100 per minute and the load balancer sends 70% of this caller's traffic to one instance, that instance rejects at 100 while the other nine stay mostly idle: the caller is rejected after about 143 requests, far below 1,000. This is why the batch-from-central-store design exists.
intuition: A turnstile that hands out tickets at a steady pace and lets you save up a few; when you have none, you wait.
The design is natural because it separates two things people usually mix together: the long-run rate and the tolerated burst. Real traffic is bursty, so a hard "N per second" rule would reject harmless spikes. A bucket says that quiet time is credit you may spend later, up to a cap, while the long-run average is still fixed by the refill rate. The state is tiny because the bucket does not remember each request. It only remembers how much credit is left. And because the arithmetic is the arithmetic of a queue, the limiter and the service it protects can be reasoned about together: keep the admitted rate below the service rate, and the queue stays short.
mistakes: People often think rate limiting and load shedding are the same. In fact a rate limit is about one caller's share (fairness and pricing), and load shedding is about the total load the service can carry right now. A service can be overloaded while every caller is within its limit, for example when many tenants peak together. You need both.
People often think a token bucket "smooths" traffic. In fact it allows bursts of size B at full speed, and passes them through unchanged. If the backend needs smooth input, use a leaky bucket (a shaper with a queue) or keep B small.
People often think fixed windows are good enough because the limit is "100 per minute". In fact a client can send nearly 200 requests in two seconds across a boundary. If your backend cannot take that, use a sliding window counter or a token bucket.
People often think a distributed limiter must be exact. In fact exactness costs a remote call per request and a single point of failure. Most systems accept a small error (a few percent) in exchange for local decisions. Decide what error you can tolerate, then pick the design.
People often think the right response to a limit is to retry quickly. In fact immediate retries add load and keep the client over the limit. The client should wait for Retry-After, add jitter, and back off exponentially.
tradeoffs: Choose a token bucket when callers are bursty and the backend can absorb short spikes; B sets the spike size and r sets the average. Choose a leaky bucket (a queue drained at a fixed rate) when the downstream needs smooth input, for example a third-party API that bans you above 50 requests per second, and you can accept added waiting time. You give up either burst tolerance or latency.
Choose a sliding window counter when you want a limit stated as "N per minute" with little memory and no boundary trick; choose an exact sliding log only for small limits (say under a few hundred per window) where an error is costly, such as login attempts. The log costs memory proportional to the limit for each caller, so 1 million callers with 1,000 requests each is on the order of a billion stored timestamps.
Choose a central store (Redis with an atomic script) when the limit must be accurate and the traffic is moderate: an extra 0.5 ms per request is acceptable, and the store can handle perhaps 100,000 checks per second per node. Choose local or batched token buckets when the request rate is in the hundreds of thousands per second, or when the limiter must keep working if the store is down. You give up some accuracy and gain latency and availability. Decide the failure mode too: "fail open" (allow when the store is down) protects users but not the backend; "fail closed" does the reverse.
Choose limits per caller and a global limit together. Per-caller limits give fairness; the global limit protects capacity. If you only have per-caller limits, 1,000 callers each within a 100 per second limit can still send 100,000 per second to a service that handles 20,000.
Choose to limit by cost, not by count, when requests differ a lot. A search query that touches a million rows should spend more tokens than a key lookup. You gain fairness and lose simplicity: clients can no longer predict their budget by counting calls.
friction: The hardest problem is choosing numbers. A limit that is too low rejects real users at peak; one that is too high protects nothing. Good limits come from load tests and from watching real per-caller traffic, and they need to change as the service and its customers change. Per-tenant tiers add a configuration system to maintain.
Distributed accuracy is a permanent trade-off. Clocks differ between machines, so timestamp-based schemes need either one clock (the central store's) or tolerance for drift. Partitions between gateways and the store force the fail-open or fail-closed decision. The limiter can itself become the bottleneck or the single point of failure for the entire API.
Identity is weaker than it looks. Limits by IP address punish many users behind one NAT and miss attackers with many addresses. Limits by API key are fair only if keys cannot be created freely. Attackers who rotate identities defeat a simple limiter; that needs bot detection, not a counter.
Clients also behave badly. Without jitter, thousands of clients that were rejected at the same moment all retry together when their wait ends, which creates a new spike (a thundering herd). A limit also gives no signal about overload that comes from slow dependencies: the service can be at 100% busy at a fraction of its tested request rate if each request got more expensive. That is why adaptive limits (such as concurrency limits that watch latency, in the style of TCP congestion control) and load shedding are used next to fixed rates.
practice: Put a limiter at every trust boundary: the public gateway (per API key and per IP), each service (per calling service), and each expensive resource (database, third-party API). Start from measurement: find the saturation throughput of the service in a load test, set the global limit at 60–80% of it, and split it between tenants by tier.
Use token buckets with a sensible burst: B equal to one to ten seconds of the rate is a common range. Return 429 with Retry-After and, if you can, headers that show the limit and the remaining budget, so well-behaved clients slow down before they are rejected. Document the limits in the API reference.
For distributed limiting, use an atomic script in Redis, or a library that does it for you (for example Envoy's rate limit service, or redis-cell for GCRA). Make a decision on fail-open versus fail-closed per endpoint: fail-open for ordinary reads, fail-closed for login and anything that costs money. Add a cheap local limiter in front of the remote one so a flood cannot overload the store.
Monitor the rate of 429 responses per caller. A sudden increase from one caller is usually a client bug. A broad increase means that your limits are too low or that capacity has fallen. Test the client side too: a rate limit that clients handle badly is worse than none. On the client, always honour Retry-After, add jitter, cap the number of retries, and use a client-side limiter or a retry budget so that retries stay a small fraction of all traffic.
quiz: In a token bucket with B = 50 and r = 5 per second, what is the most requests accepted in a 10-second window, starting from a full bucket? || B + r × T = 50 + 5 × 10 = 100 requests. The first 50 go through at once, and the refill adds 50 more during the 10 seconds.
Why does the token bucket not need a timer thread to add tokens? || It stores the token count and the last update time, and computes the refill when a request arrives: tokens = min(B, tokens + (now − last) × r). That makes the cost O(1) per request and a few bytes per caller.
Why does a limit below the service capacity keep latency low, according to queueing theory? || In a simple queue the mean delay is \( 1/(\mu - \lambda) \), which grows without bound as the arrival rate λ approaches the service rate μ. Keeping λ well below μ, for example at 70–80%, keeps queues and delays small.
A caller has a limit of 1,000 per minute spread over 10 gateways that each enforce 100 per minute locally. Traffic is skewed so one gateway gets 70% of it. At about what total does the caller start to be rejected? || That gateway hits 100 when the caller has sent about 100 / 0.7 ≈ 143 requests, so the caller is rejected at about 14% of its intended limit. Fix this with a central counter or by taking batches of tokens from a shared store.
When would you choose a leaky bucket instead of a token bucket? || When the downstream needs smooth, constant-rate input, such as a third-party API with a hard per-second ban, and you can accept that requests wait in a queue. A token bucket lets bursts through unchanged.
interview: Design a rate limiter for a public API with 10 million API keys and 50 gateway instances. What do you choose? || Per-key token bucket with state (tokens, last_update), about 16 bytes per key, so 10 million keys is about 160 MB. Put the state in a Redis cluster sharded by key and run the check in a Lua script for atomicity. Add a local fast path: each gateway takes batches of tokens for hot keys. State the error you accept, the fail-open or fail-closed choice per endpoint, and use 429 with Retry-After.
Why is a fixed window counter risky, and what do you use instead? || It allows up to twice the limit around a window boundary. Use a sliding window counter (two counters and a weighted estimate) or a token bucket. The sliding window counter gives nearly exact behaviour with two integers per caller.
Your limiter's Redis goes down. What happens, and what should happen? || By default every check fails. For general traffic fail open with a local conservative limit so the API stays up; for login, payments and expensive endpoints fail closed. Add timeouts of a few milliseconds on the Redis call so the limiter never adds more latency than the limit saves.
How do rate limiting, load shedding and backpressure differ? || Rate limiting caps one caller's share, usually by a fixed policy. Load shedding drops work because the service is overloaded in total, often by priority and by measured latency or queue length. Backpressure pushes the slow-down signal to the producer through the protocol, for example a full queue or TCP flow control. A resilient system uses all three.
Clients behind a corporate NAT share one IP and get limited unfairly. What do you do? || Limit by authenticated identity (API key or user) as the main key, and use IP limits only as a loose outer guard with a higher threshold. For anonymous endpoints, combine IP with other signals and consider challenges instead of hard blocks.
A customer complains that they are rejected even though their average rate is below the limit. How do you diagnose it? || Check burst size: their requests may arrive in spikes larger than B (cron jobs at the top of the minute). Look at the 429 timestamps and the limiter's token count at the time. The fix is a larger B, spreading their jobs with jitter, or a queue on their side.

@@ merkle
value: Content addressing means that the name of a piece of data is the hash of its content. A Merkle tree goes one step further: it hashes data in a tree, where each parent holds the hash of its children, so that one short root hash commits to an entire large collection. If you hold the root hash, you can check any single item with a short proof, and you can check that two copies of a huge data set are identical by comparing just two 32-byte values.
The problem is trust and cost. Suppose you download a 4 GB file in 4 million blocks from many untrusted peers. A single hash of the whole file tells you only at the end that something is wrong, and not which block. Or suppose two database replicas hold a billion rows each, and you want to find the few rows that differ. Sending all rows costs too much. Or suppose a phone must confirm that a payment is inside a block of 3,000 transactions, and the phone cannot download the block. A Merkle tree solves all three with the same trick: a proof is only one path from a leaf to the root, about \( \log_2 n \) hashes, for example 12 hashes (384 bytes) for 3,000 transactions or 30 hashes (960 bytes) for a billion items.
For the layer above, this is the integrity layer of modern systems. Git names every commit, directory and file by hash, so history cannot be changed without everyone noticing (version control, L1). Bitcoin and Ethereum put a Merkle root of the transactions in every block header (L0, L1 blockchains), so light clients can verify a payment with a short proof. Cassandra, Dynamo-style stores and similar systems compare Merkle trees to repair replicas with little traffic (read repair and anti-entropy, L2). Certificate Transparency logs, Docker image layers, IPFS and package registries use the same idea. The layers below supply the two parts: cryptographic hash functions (L3) give a short fingerprint that cannot be forged, and trees (L3) give the shape that turns "check everything" into "check one path".
terms: Cryptographic hash — a function that maps any data to a fixed-size fingerprint (for example 32 bytes for SHA-256) so that finding two inputs with the same output, or an input for a given output, is computationally infeasible.
Content addressing — naming and looking up data by the hash of its bytes instead of by location or a chosen name.
Leaf — a node at the bottom of the tree that holds the hash of one data block.
Root hash — the hash at the top of the tree; it depends on every leaf, so it commits to the whole data set.
Inclusion proof (Merkle proof) — the list of sibling hashes along the path from a leaf to the root; with it, anyone can recompute the root and check that the leaf belongs.
Consistency proof — a proof that a newer tree extends an older tree, meaning the old entries were not changed; used by append-only logs.
Anti-entropy — a background process in which replicas compare their data and repair differences; Merkle trees make the comparison cheap.
Domain separation — hashing leaves and internal nodes with different prefixes so that a leaf can never be mistaken for an internal node.
history: Ralph Merkle invented the hash tree for his 1979 Stanford PhD work on public-key cryptography and digital signatures; his patent was filed in 1979 and granted in 1982, and the paper "A Digital Signature Based on a Conventional Encryption Function" appeared at CRYPTO 1987. His goal was to build digital signatures from only a hash function (no number theory), where one published root hash authenticates many one-time keys. That idea is still alive in modern hash-based signatures that are designed to resist quantum computers.
Content addressing grew from practical storage problems. Plan 9's Venti (Quinlan and Dorward, 2002) stored each block under the hash of its content, which removed duplicates in an archival system. ZFS (2005) stores a checksum of each block in the parent's block pointer, so a whole file system forms a Merkle tree and silent disk corruption is detected on read. Git (2005) made the object store content-addressed: a commit points to a tree, which points to blobs, all by hash. Amazon's Dynamo paper (2007) used Merkle trees so replicas could find differing key ranges without sending data; Cassandra and Riak copied this.
Bitcoin (2008) placed a Merkle root in every block header and described simplified payment verification (SPV) for light clients. Certificate Transparency (RFC 6962, 2013, updated by RFC 9162 in 2021) made Merkle trees the standard way to run a public, append-only log of certificates, and added consistency proofs. IPFS (2014) and Docker image digests spread content addressing to files and containers. The main shock came in 2017, when the SHAttered attack produced the first real SHA-1 collision, which forced Git and others to plan a move to SHA-256. Git supports SHA-256 repositories as an option since version 2.29 (2020), but migration is slow because every object name changes.
how: Start with the data split into blocks, for example 4 transactions A, B, C, D. Hash each block to make a leaf: \( L_1 = H(A) \), \( L_2 = H(B) \), and so on. Then hash pairs of leaves to make the next level: \( N_1 = H(L_1 \,\|\, L_2) \), \( N_2 = H(L_3 \,\|\, L_4) \). Hash again: \( \text{root} = H(N_1 \,\|\, N_2) \). With n leaves there are about \( \log_2 n \) levels. Cryptographic hash functions (L3) are what make this safe. Because it is infeasible to find another input with the same hash (second-preimage and collision resistance), nobody can change any block without changing its leaf, then every hash above it, and finally the root. The root is therefore a fingerprint of everything below it.
The tree (L3) is what makes it cheap. To prove that block C is in the set, you do not send the other blocks. You send the sibling hashes along C's path: L4 (the sibling of L3) and N1 (the sibling of N2). The verifier hashes C to get L3, combines it with L4 to get N2, combines N1 and N2 to get a root, and compares with the trusted root. If the roots match, C is in the set. The proof has \( \log_2 n \) hashes, and the verification costs \( \log_2 n \) hash computations. For one billion items this is 30 hashes, about 960 bytes.
Details matter for safety. Without domain separation, an attacker could present an internal node (the concatenation of two hashes, 64 bytes) as if it were a leaf. The fix, used in RFC 6962, is to hash leaves as H(0x00 ‖ data) and internal nodes as H(0x01 ‖ left ‖ right). Odd numbers of leaves need a rule. Bitcoin duplicates the last hash, which created a known weakness (CVE-2012-2459) in which two different lists of transactions could have the same root; RFC 6962 instead splits the list at the largest power of two below n, which avoids it. A good implementation also fixes the encoding of lengths and order, because H(a ‖ b) must not be confusable with another split of the same bytes.
Updates are cheap. If one block changes, you recompute its leaf and the \( \log_2 n \) hashes on the path to the root, and nothing else. Appending to an append-only log changes only the right edge of the tree. A consistency proof lets a client that remembers an old root (for tree size m) check that the log with size \( n > m \) only added entries: the server sends a few hashes that let the client recompute both roots. This is how Certificate Transparency catches a log that rewrites history.
Comparing two copies uses the same structure from the top. Replica A and replica B each build a tree over the same key ranges. They exchange roots. If the roots are equal, the data is identical, and the work is done after one comparison. If not, they exchange the two children of the root, find which side differs, and descend only into the differing subtrees. If k leaves differ, about \( k \times \log_2 n \) hashes are exchanged, instead of n. Cassandra's repair works like this, with leaves that cover ranges of keys, so a differing leaf means streaming that whole range, not one row.
Content addressing is the other half. When the name of a block is its hash, three properties follow for free. Anyone who receives the block can check it against its name, without trusting the sender. Two identical blocks have the same name, so storage deduplicates automatically. And a named object never changes, so it can be cached forever and shared safely. Chaining these names (a commit contains the hash of its parent and of its tree) produces a Merkle DAG, a directed acyclic graph, where a single commit hash commits to the whole history.

example: Let us build a real tree. Use SHA-256 and show only the first 8 hex characters. The four blocks are the strings tx-A, tx-B, tx-C and tx-D. Leaves are H(0x00 ‖ data): L1 = b3cbd586, L2 = 29dd9348, L3 = 2cb4d1f4, L4 = 85975b41. Internal nodes are H(0x01 ‖ left ‖ right): N1 = e0ff7c9c and N2 = f9069be6. The root is 1538dec0 (in reality all values have 64 hex characters; we cut them to fit).
Prove that tx-C is in the tree. The prover sends tx-C, plus L4 = 85975b41 and N1 = e0ff7c9c, and the information that C is the left child at the first step. The verifier computes L3 from tx-C and gets 2cb4d1f4. It computes N2 = H(0x01 ‖ 2cb4d1f4 ‖ 85975b41) = f9069be6. It computes H(0x01 ‖ e0ff7c9c ‖ f9069be6) = 1538dec0. This equals the trusted root, so tx-C is in the tree. Two hashes were sent for four leaves.
Now an attacker changes tx-C to tx-C! (one added character). The new leaf is c03a0583, the new N2 is c577b921, and the new root is 1a3a46a4, which does not match 1538dec0. The change is visible to anyone who holds the old root. The attacker would have to find a different block with the same hash, which is infeasible for SHA-256.
Next, replica repair at scale. Two replicas each hold 1 billion rows in a token range, and a tree with 2²⁰ ≈ 1 million leaves summarizes each; each leaf covers about 1,000 rows. Exactly 3 rows differ, in 3 different leaves. The replicas compare roots (1 comparison), then descend: at each of the 20 levels, they compare the children of each differing node, so about 3 × 20 × 2 = 120 hash comparisons find the 3 differing leaves. They then stream about 3 × 1,000 = 3,000 rows, not 1 billion. The cost of building the trees is a full scan of the data on both sides, which is the real expense of this method.
Last, the SPV proof. A Bitcoin block has about 3,000 transactions, so a Merkle proof has \( \lceil \log_2 3000 \rceil = 12 \) hashes of 32 bytes, which is 384 bytes. The light client also needs the 80-byte block header (which contains the root). The block itself is about 1 to 2 MB. The phone checks a payment with about 0.5 KB instead of 1–2 MB, a reduction of roughly 2,000 to 4,000 times.
intuition: A fingerprint of fingerprints: each parent seals its children, so the top seal cannot stay the same if anything underneath changes.
The design is natural because it combines two facts. A hash is a short, unforgeable summary of any amount of data. A tree lets you split a large problem so that any one part can be reached in a few steps. If every node summarizes its children, then the root summarizes everything, and a proof for one item needs only the summaries of its neighbours on the way up, never the data of other items. The cost of checking grows with the depth of the tree, which grows with the logarithm of the data size. That is why you can verify a billion items with about 30 hashes. Content addressing is the same thought applied to naming: if the name is the fingerprint, the name proves the content.
mistakes: People often think a Merkle tree encrypts or hides the data. In fact it provides integrity only. Hashes do not hide content, and small or guessable blocks can be found by guessing and hashing. Confidentiality needs encryption on top.
People often think the root hash proves that the data is correct or true. In fact it only proves that the data is the same as what was committed. If the party who made the root committed to wrong data, the tree is a faithful fingerprint of wrong data. You must also get the root from a source you trust, such as a signed block header or a signed tree head.
People often think a Merkle proof proves that an item is absent. In fact an ordinary inclusion proof shows only presence. To prove absence you need a sorted tree, a sparse Merkle tree, or a Merkle trie, where the missing key's position is also committed.
People often think Merkle-based repair finds the exact differing rows. In fact the leaves cover ranges, so a single differing row can force streaming a whole range of thousands of rows, and a tree that is too shallow makes this worse. The depth is a memory and CPU trade-off.
People often think the hash algorithm can be upgraded later like any other library. In fact names are hashes, so changing the algorithm changes every name, every parent hash and every reference. Git's move from SHA-1 to SHA-256 needs a new repository format and tooling, which is why it is slow.
tradeoffs: Choose a binary Merkle tree when proofs must be small and verification cheap (light clients, transparency logs): proof size is \( \log_2 n \) hashes. Choose a wider tree (for example 16 children per node) when the tree is read from disk or stored in a database, because a node is then one disk page and the tree is shallower, at the cost of larger proofs: a 16-ary proof for n items carries 15 sibling hashes per level, so about (15 / 4) ≈ 3.75 times as many hashes as a binary proof.
Choose a Merkle tree with a flat structure per range (as in Cassandra) when you only need to find which ranges differ, and accept that repair streams whole ranges. Choose a deeper tree or smaller ranges when rows are large or differences are rare, which costs more memory to hold the tree (2²⁰ leaves × 32 bytes = 32 MB per range per tree). The deciding numbers are the number of leaves versus the number of differing rows.
Choose a plain list of hashes (a hash list) or one hash of the whole file when you only need an end-to-end check and never need partial proofs. This is simpler, with one hash and no tree maintenance, but you give up the ability to verify or repair a part. Choose a tree when blocks arrive from different sources and you want to reject bad blocks immediately, as in BitTorrent v2 (which uses per-file Merkle trees).
Choose a Merkle tree (an append-only history) over a signed database snapshot when other parties must audit that nothing was rewritten; you pay with the cost of hashing every update (\( \log_2 n \) hashes) and the work of keeping an online log honest. Choose a sparse Merkle tree or a Merkle Patricia trie (as Ethereum does) when you need proofs of key-value state and of absence; you pay with more complex code and deeper paths. Finally, choose SHA-256 or a newer hash (SHA-3, BLAKE3) by speed and by what the ecosystem verifies; BLAKE3 is itself a Merkle tree, which allows parallel hashing.
friction: Every update changes a leaf-to-root path, so a hot tree needs locking or batching at the top. Many writers updating different leaves all touch the root, so systems batch updates and compute the root once per block or per interval, rather than per write.
Building a tree needs a full pass over the data, and in anti-entropy systems that is a heavy disk scan. Cassandra operators know this well: repair is slow, uses a lot of I/O, and runs in the background for hours on large nodes. Over-streaming from coarse leaves is a known cost. The comparison also needs both replicas to agree on the same range boundaries and the same serialization of each row. A tiny difference in encoding makes every hash differ.
The cryptographic assumptions are not permanent. SHA-1 broke in practice, and the name-by-hash design makes migration painful. Quantum computers are less of a danger for hashes than for signatures: Grover's algorithm gives only a quadratic speed-up, so a 256-bit hash still gives about 128 bits of security against it.
Proofs prove inclusion in a committed set, not that the set is good. A transparency log needs auditors and gossip so that a log cannot show different trees to different people (a split-view attack). A Merkle tree does not remove the need to trust the root. Finally, deletion is awkward in content-addressed storage: data is shared by many references, so deleting needs garbage collection (reference tracing), which is a hard problem in itself, and "right to be forgotten" laws are hard to meet when names are permanent.
practice: Use a standard construction, not your own: copy the RFC 6962 / RFC 9162 definitions (with 0x00 and 0x01 prefixes and the power-of-two split) or use a well-reviewed library. Use SHA-256 (or BLAKE3 for speed) and fix the byte encoding of leaves precisely.
For replica repair, pick leaf ranges so that a leaf holds a reasonable amount of data (hundreds to thousands of rows), keep the tree in memory, and schedule repair when the cluster is quiet. Compare roots first, since most of the time the roots match. For Cassandra, use incremental repair or a managed repair tool, and track how much data repair streams.
For integrity of large files or downloads, split the file into blocks (for example 256 KB to 4 MB), publish the root hash through a trusted channel, and verify each block as it arrives. For logs, publish signed tree heads regularly and let clients check consistency proofs between the heads they have seen.
Name immutable artifacts by digest: pin container images by sha256 digest (image@sha256:...) in production deployments instead of by mutable tags, and verify checksums of build inputs. Remember that git's commit hash is a Merkle root of the entire tree and history. Use signed commits or tags if you need to trust who made it, since the hash alone does not say who.
To study it, implement a small Merkle tree with inclusion proofs in 50 lines, then add a consistency proof from the RFC 6962 text. It is one of the best exercises for understanding why hashing and trees combine well.
quiz: What is in an inclusion proof, and how big is it for 1 billion leaves? || The sibling hashes along the path from the leaf to the root. It has about \( \log_2(10^9) \approx 30 \) hashes, which is 30 × 32 = 960 bytes with SHA-256.
Why does a change in one leaf change the root? || Each parent is the hash of its children, so a changed leaf changes its parent, then that parent's parent, and so on up the path. Because the hash is collision resistant, no other data can give the same root.
Why do RFC 6962 trees hash leaves with a 0x00 prefix and internal nodes with a 0x01 prefix? || To separate the two kinds of node. Without it, an attacker could present the 64-byte concatenation of two child hashes as a "leaf" and obtain a valid-looking proof for data that was never in the tree.
Two replicas have 2²⁰ leaves each and 4 rows differ in 4 different leaves. Roughly how many hash comparisons find them? || About 4 paths × 20 levels × 2 children = 160 comparisons, plus the root comparison. It is far fewer than comparing 1 million leaves.
When would you use a hash list or one file hash instead of a Merkle tree? || When you only need an end-to-end check of a whole object and never need to verify or repair parts. A tree is better when blocks come from many untrusted sources, or when partial proofs and fast diffs matter.
interview: How do Cassandra or Dynamo-style replicas use Merkle trees, and what are the limits? || Each replica builds a tree over each token range, with leaves covering sub-ranges. They compare roots, then descend into differing subtrees to find the differing leaf ranges and stream only those. Limits: building the tree needs a full scan, coarse leaves cause over-streaming, and trees are limited in depth for memory. It is also a periodic repair, not a real-time sync.
Explain how a light client verifies a transaction without downloading the block. || It keeps block headers (80 bytes each in Bitcoin), which contain the Merkle root. A full node sends the transaction and the sibling hashes on its path (12 hashes for about 3,000 transactions). The client recomputes the root and compares it with the header, and trusts the header because it has the most proof-of-work. It cannot prove that other transactions are absent or valid, only that this one was included.
Why is a Merkle tree better than hashing the whole file when you download from many peers? || You can verify each block on arrival and reject a bad one at once, so one bad peer wastes one block, not the entire download. With a single file hash you learn of corruption only at the end and cannot tell which block was bad.
What goes wrong if the tree duplicates the last node when the number of leaves is odd? || Two different lists, [a, b, c] and [a, b, c, c], produce the same root. Bitcoin had this issue (CVE-2012-2459). A safer rule splits at the largest power of two, as in RFC 6962, and a check for duplicates helps.
Git is "a Merkle DAG". What does that give, and why was SHA-1 a problem? || Each object is named by the hash of its content and references other objects by hash, so one commit hash commits to the whole tree and all history, and identical content is stored once. Because names are hashes, a collision could allow a different object with the same name (SHAttered, 2017 showed SHA-1 collisions). Moving to SHA-256 changes all names, so migration is hard.
Design a tamper-evident audit log for 10 billion events. || An append-only Merkle log with signed tree heads published at intervals. Writers append and get an inclusion proof; auditors request consistency proofs between heads to show nothing was rewritten. Batch appends to avoid root contention, keep recent nodes in memory, and use independent monitors or gossip to defeat split-view attacks. Proof size is about 34 hashes.

@@ sampling
value: Sampling means that you look at a small, carefully chosen part of the data and use it to say something about all of it. It exists because many systems produce more data than anyone can store, send or analyse. A service that handles 10,000 requests per second, with 20 spans of 1 KB each in every trace, produces about 200 MB per second of tracing data, which is roughly 17 TB per day. Keeping 1% of it costs 1% as much, and for most questions (what is the error rate, what is the median latency, how many users saw this ad) the answer from the 1% is almost as good as the answer from the whole.
The reason this works is statistical, and it is the main reason to trust it. The error of an estimate from a random sample depends on the sample size, not on the size of the full data. Roughly, the error shrinks as \( 1/\sqrt{n} \). A random sample of 10,000 events estimates a proportion to within about ±1 percentage point (95% confidence), whether the full data has one million or one trillion events. So sampling cuts cost by orders of magnitude while giving a known, small loss of accuracy. The word "known" matters: unlike ad-hoc dropping of data, a proper sample comes with a confidence interval.
For the layer above, sampling is how observability keeps tracing and logging affordable (trace sampling), how experimentation forms its groups (each arm of an A/B test is a random sample of users), and how machine learning trains on huge logs or replays past experience (experience replay in Q-learning). The layers below provide the guarantees. Statistics and estimation (L4) say how to turn a sample into an estimate and a confidence interval. The law of large numbers and the central limit theorem (L4) say why sample averages concentrate around the truth and how fast. Streaming algorithms (L3) supply the one-pass methods, such as reservoir sampling, that draw a fair sample from data whose size you do not know in advance.
terms: Population and sample — the population is all the events or items you care about; the sample is the subset you actually keep.
Sampling rate — the fraction of the population that is kept, such as 1% or 1 in 100; also the probability that any one item is kept.
Unbiased estimator — a way to compute a population quantity from a sample so that, averaged over many samples, it gives exactly the true value.
Confidence interval — a range around an estimate that contains the true value with a stated probability, such as 95%.
Stratified sampling — splitting the population into groups (strata) and sampling each group separately, so that small but important groups are represented.
Reservoir sampling — a one-pass algorithm that keeps a uniform random sample of k items from a stream of unknown length, using only k slots of memory.
Head-based and tail-based sampling — deciding to keep a trace at its start, before knowing what happens, versus deciding after it finishes, when errors and slow requests are known.
Inverse-probability weighting — counting each kept item as 1/rate items, so that totals computed from the sample estimate the totals of the population.
history: Sampling is older than computers. Statisticians used it to study populations too large to count. Jerzy Neyman's 1934 paper on the "representative method" showed that random sampling, and not hand-picked "typical" samples, gives valid estimates, and described stratified sampling with optimal allocation. Horvitz and Thompson (1952) gave the general rule for unbiased totals from samples with unequal probabilities: weight each item by the inverse of its chance of being selected. The famous warning about bias comes from the 1936 US presidential election, when the Literary Digest polled about 2.4 million people and predicted the wrong winner, while George Gallup's much smaller, better designed sample of about 50,000 predicted the right one. Size does not cure a biased selection.
In computing, sampling appeared wherever data outgrew storage. Knuth's "The Art of Computer Programming" (volume 2, 1969) described a simple algorithm for choosing k items from a stream (credited to Alan Waterman), and Jeffrey Vitter's 1985 paper "Random Sampling with a Reservoir" made it fast by computing how many items to skip. Network routers adopted packet sampling in tools such as sFlow and NetFlow, which look at 1 packet in N so that line-rate links can be monitored. Database systems added approximate query processing with sampling in the 1990s (the AQUA project and later BlinkDB).
For distributed tracing, Google's Dapper paper (Sigelman et al., 2010) explained that uniform sampling, at the start of a request, at rates as low as 1 in 1,024, was enough for most uses and kept the overhead small. Open-source tracers (Zipkin, Jaeger, OpenTelemetry) copied this. Their weakness, that rare errors are usually dropped, led to tail-based sampling (decide after the trace is complete) and to dynamic sampling in commercial tools. In machine learning, sampling became central through stochastic gradient descent, negative sampling for embeddings and click-through models, and importance sampling for rare events and reinforcement learning.
how: The basic method is uniform random sampling: keep each item independently with probability p. This is called Bernoulli sampling, and it can be done in a single pass over data of unknown size, with no coordination: flip a biased coin for each event. The count of kept items is random (about \( p \times N \)), and each item has exactly the same chance. To estimate a total, you multiply the sample count by \( 1/p \). To estimate a proportion or an average, you compute it on the sample. The statistics layer (L4) gives the error: for a proportion q estimated from n sampled items, the standard error is \( \sqrt{q(1 - q)/n} \), and a 95% interval is about ±1.96 times that. The central limit theorem (L4) is why the interval is a normal curve for large n, and the law of large numbers is why the estimate converges.
There are other ways to draw a sample. Systematic sampling keeps every k-th item, which is cheap but dangerous when the data has a period of k. Hash-based sampling keeps an item if hash(key) mod 100 is below the target percentage. This is deterministic, so every machine that sees the same key makes the same decision without talking to others. It is the basis of consistent trace sampling (hash the trace ID, so all spans of a trace are kept or dropped together) and of sampling joined tables (sample both tables by the same key hash, so that matching rows survive; if you sample each table independently at 10%, only 1% of the joined pairs survive).
Reservoir sampling answers a different question: how to keep exactly k items, uniformly, when you do not know how many items will arrive. Keep the first k items. For the i-th item (i > k), with probability k/i, include it by replacing a uniformly random slot in the reservoir; otherwise ignore it. A short argument shows that, after n items, every item has probability k/n of being in the reservoir. The i-th item enters with probability k/i. At each later step j it is evicted with probability (k/j) × (1/k) = 1/j, so it survives with probability 1 − 1/j. Multiplying the survival terms from i + 1 to n gives i/n, and (k/i) × (i/n) = k/n. This streaming algorithm (L3) uses O(k) memory and one pass.
Uniform sampling has a weak point: rare groups. If 0.1% of requests fail, a 1% sample contains only 1 failure for every 1,000 sampled requests, which is too noisy for analysis of failures. Stratified sampling fixes this. Split the data into strata (by status code, customer, endpoint) and set a different rate for each: keep all errors, 1% of successes. Because rates now differ, you must correct totals with inverse-probability weights: an event kept at rate 1% counts for 100; an event kept at rate 100% counts for 1. This is the Horvitz–Thompson estimator, and it remains unbiased for any known selection probabilities. Store the sample rate on each event, so that later queries can re-weight correctly.
For traces there are two main designs. Head-based sampling decides at the root span, before anything is known, and passes the decision to all downstream services in the trace context (for example the "sampled" flag in the W3C Trace Context). It is cheap and needs no buffering, but it cannot favour errors or slow requests because they have not happened yet. Tail-based sampling lets all spans flow to a collector, holds them in memory until the trace ends (waiting for a time limit, often 10–60 seconds), and then applies rules: keep if any span has an error, keep if the duration is above the 99th percentile, otherwise keep 1%. It captures the interesting traces, but costs memory and requires that all spans of one trace reach the same collector (route by trace ID).
Importance sampling generalizes this. To estimate E[f(X)] when the interesting values of f are rare, draw from a different distribution q that favours them and re-weight each draw by p(x)/q(x). The weighting keeps the estimate unbiased while the variance drops, which is why it is used in rare-event simulation, in off-policy reinforcement learning, and in training click models on logs with downsampled negatives.

example: First, how good is a sample? A service logs 100 million requests per day, and the true error rate is 2%. You keep a 1% uniform sample, so n = 1,000,000 events. The standard error is √(0.02 × 0.98 / 1,000,000) = √(0.0000000196) ≈ 0.00014, or 0.014 percentage points. The 95% interval is about ±0.027 percentage points, so you would report an error rate of 2.00% ± 0.03%. Now keep only 0.01% (n = 10,000): the interval grows to ±0.27 points, ten times wider, because 100 times fewer data gives √100 = 10 times more error. This is the \( 1/\sqrt{n} \) rule.
Second, a rare event. Suppose a bug affects 1 request in 100,000. In 100 million requests that is 1,000 requests. A 1% sample keeps about 10 of them. The count has a standard deviation of about √10 ≈ 3.2, so your estimate of the number of affected requests, 10 × 100 = 1,000, has an error of about 32% (95% interval roughly ±62%). You will notice the problem, but you cannot measure it well. If you keep every request with an error status and 1% of the rest, you have all 1,000 affected requests, and the estimate is exact.
Third, a tracing budget. At 10,000 requests per second, with 20 spans of 1 KB, keeping everything is 200 MB/s, about 17 TB per day. With 1% head-based sampling, that is about 173 GB per day. But if 0.1% of requests fail (10 per second), head sampling keeps just 0.1 failed traces per second, and most failures have no trace. With tail-based sampling you keep all 10 error traces per second plus 1% of the other 9,990, about 100 per second, so 110 traces per second in total, about 1.1% of traffic, and every error is present. The price is buffering: with a 30-second wait you hold 10,000 × 30 = 300,000 traces of 20 KB each, about 6 GB, in the collectors.
Fourth, re-weighting. After the tail-based rules, the stored data has two kinds of trace: error traces (kept at rate 1.0, so weight 1) and OK traces (kept at rate 0.01, so weight 100). Over one hour, the store holds about 36,000 error traces (10 per second × 3,600) and about 360,000 OK traces (100 per second × 3,600). The estimated number of requests is 36,000 × 1 + 360,000 × 100 = 36,036,000. The true number is 10,000 × 3,600 = 36,000,000, so the estimate is within 0.1%. If you forget the weights and just count the stored traces, you get 396,000, which is about 90 times too low.
Last, downsampled negatives in ad prediction. Only 0.2% of ad impressions get a click. You train on all clicks and 10% of non-clicks (w = 0.1). The model learns an inflated probability p′. To get the true probability, use \( p = \frac{p'}{p' + (1 - p')/w} \). If the model says p′ = 0.02, then p = 0.02 / (0.02 + 0.98/0.1) = 0.02 / (0.02 + 9.8) ≈ 0.002. Without this correction, bids based on the predicted click rate would be 10 times too high.
intuition: Taste a spoonful of a well-stirred soup to know the whole pot; the spoon can be small because the stirring makes every spoonful alike.
The idea is natural because randomness removes the need to know where the interesting data is. If every item has the same chance of being picked, then what you see is a fair, scaled-down copy of everything, and statistics tells you how blurry the copy is. The blur depends on how many items you looked at, not on the size of the pot, which is why 10,000 well-chosen items can describe a trillion. When the soup is not well stirred (rare ingredients, clumps), you stir differently: take extra spoonfuls from the rare part and note how much extra you took, so the final count can be corrected.
mistakes: People often think a bigger sample fixes a biased sample. In fact bias does not shrink with size. The Literary Digest's 2.4 million responses were worse than Gallup's 50,000 because the Digest's list over-represented wealthy people. Only a better selection method fixes bias.
People often think a 1% sample means 1% of the accuracy. In fact accuracy depends on the sample size n, with error proportional to \( 1/\sqrt{n} \). A 1% sample of a very large data set can be more accurate than a 50% sample of a small one. The sample fraction matters only for rare groups, where the count in the sample is what limits you.
People often think you can sample each table independently and join the samples. In fact a join of two independent 10% samples keeps only about 1% of the pairs, and the result is a biased view of the join. Sample both tables by the same hash of the join key, or sample one table and keep the other whole.
People often think sampled data can be summed like full data. In fact if the rates differ between groups or services, the totals are wrong unless each item is weighted by 1/rate. Always store the sampling rate with the data, and remember that sample counts, not sample averages, are what need weighting.
People often think head-based trace sampling will catch the slow and failing requests. In fact the decision is made before the outcome is known, so the chance of keeping a failed trace is just the base rate. To keep errors and slow requests you need tail-based sampling or a separate rule such as always logging errors.
tradeoffs: Choose uniform random sampling when the question is about common events and you want unbiased, simple estimates: averages, medians, overall error rate. Choose stratified or rule-based sampling when the interesting events are rare (errors, large customers, new features): you keep rare strata whole and sample the common ones heavily, and you pay with weights that you must track and a more complex pipeline.
Choose head-based trace sampling when volume is high, you cannot afford buffering, and a uniform view is enough for latency distributions. Choose tail-based sampling when debugging failures matters more than cost: you can keep 100% of errors and slow traces with roughly 1% of the total data, but you pay for memory (in the example, about 6 GB for a 30-second window), for routing all spans of a trace to one collector, and for a delay before data appears. Many teams combine them: a low head rate for baseline, plus always-keep rules at the collector.
Choose hash-based sampling over random coin flips when decisions must agree across machines or across time (all spans of a trace, all events of a user, both sides of a join). You lose the ability to get a fresh independent sample on a second look, and a skewed key (one huge customer) can make the sample lumpy.
Choose reservoir sampling when you need a fixed-size sample from a stream of unknown length, such as the last day of requests for a debugging dump; choose Bernoulli sampling when a fixed rate is fine and you want no state. Reservoir needs O(k) state and a lock or per-shard reservoirs that are merged later; Bernoulli has a random sample size.
Choose to sample less and aggregate more (metrics, sketches such as HyperLogLog or t-digest) when you only need counts and percentiles; choose to sample and keep raw events when you need to look at individual records. Aggregation is cheaper and exact for what it measures, but it cannot answer a question you did not plan for.
friction: A sample answers only the questions its design allows. A uniform 1% sample cannot find a bug that affects 1 request in a million, and it cannot support a question about a single user, since you probably did not keep that user's events. Rare-event analysis, security investigations and audits often need full data, which is a reason not to sample the audit trail.
Weights add complexity and error. If the sampling rate is not recorded, or changes over time (as adaptive samplers do), later analysis can silently be wrong. Dashboards that mix sampled and unsampled sources are a common source of wrong numbers. Variance also grows with the weights: if a few kept events carry weight 10,000, one of them can dominate an estimate.
Bias enters in subtle ways: sampling by a field that is correlated with the outcome, dropping data when a system is overloaded (which is exactly when interesting things happen), or sampling in a place where retries and duplicates distort the rate. Systematic sampling can line up with periodic behaviour.
Tail-based sampling needs state, memory sizing and routing, and the collector becomes critical infrastructure; if traces are very long or very large, the wait window may not be enough. Finally, for machine learning, downsampling changes the data distribution, so predicted probabilities must be re-calibrated, and sampling that depends on the model itself can create feedback loops.
practice: Decide the question first, then the sampling design. For metrics where you need counts and percentiles, aggregate in the pipeline (counters, histograms) instead of sampling raw events. For raw events, keep everything that is rare and important (errors, high latency, security events) and sample the rest. Record the sampling rate on every kept event as a field, so that analysis can weight correctly, and so that you can change the rate later.
Use hash-based decisions on a stable key (trace ID, user ID) when consistency matters. In OpenTelemetry, use a parent-based sampler with a trace-ID ratio for the head decision, and add the tail sampling processor in a collector tier for error and latency rules, with load balancing by trace ID in front of it. Size the buffer: traces per second × wait time × average trace size.
In Spark or SQL, use sample or TABLESAMPLE for quick exploration, sampleBy for stratified sampling, and remember that a sample is not deterministic unless you give a seed. When you downsample negatives for a click or conversion model, apply the odds correction \( p = \frac{p'}{p' + (1 - p')/w} \), or calibrate the model afterwards on unsampled data. For A/B tests, randomize by a hash of the user ID and a per-experiment salt, so that assignments are stable and independent between experiments.
Always report uncertainty: give a confidence interval with every sampled estimate, and check that the sample is representative by comparing it with a known total (for example total request count from a cheap counter). Look at the tail separately: percentiles at p99 or p99.9 need many more samples than a mean.
quiz: Why does a sample of 10,000 estimate a proportion about as well for a population of 1 million as for a population of 1 trillion? || The standard error \( \sqrt{q(1 - q)/n} \) depends on the sample size n, not on the population size. With n = 10,000 the 95% interval is at most about ±1 percentage point in both cases.
In reservoir sampling with k slots, the i-th item (i > k) enters with probability k/i. Why does every item end with probability k/n? || An item that entered at step i is evicted at each later step j with probability 1/j, so it survives with probability 1 − 1/j. The product of survival terms from i + 1 to n is i/n, and (k/i) × (i/n) = k/n.
A trace sampler keeps all error traces at rate 1.0 and OK traces at rate 0.02. Out of the stored data, 5,000 OK traces and 40 error traces are found in an hour. Estimate the number of requests. || OK traces count for 1/0.02 = 50 each: 5,000 × 50 = 250,000. Error traces count once each: 40. The total is about 250,040 requests.
Why can head-based sampling not guarantee that error traces are kept, and what do you use instead? || The decision is made at the start of the request, before the error happens, so errors are kept only at the base rate. Use tail-based sampling at a collector, which decides after the trace is complete, or add rules to always keep errors.
You must join a clicks table and an impressions table, but both are too large. How do you sample? || Sample both tables with the same hash of the join key (for example user ID), at the same rate. Then matching rows are kept together and the join of the samples is a fair sample of the full join. Independent sampling at rate p would keep only \( p^2 \) of the pairs.
interview: Design the sampling strategy for a tracing system at 1 million requests per second. What do you decide and what can go wrong? || Use a low head rate (say 0.1%) for baselines, written into the trace context so that all services follow it, plus a tail-sampling collector tier for errors and slow traces, fed by a load balancer that routes by trace ID. Size the buffer as traces per second × wait time × trace size. Failures: collector overload drops spans, partial traces, rate changes that break dashboards unless each trace carries its rate, and long traces exceeding the wait.
How would you estimate the number of unique users from a 1% sample of events? || You cannot simply multiply the sample's distinct count by 100: a user with many events is likely to be in the sample, so the sample's distinct count is biased low in an unknown way. Sample by user ID hash instead, so that you keep all events of 1% of users, count their distinct users and multiply by 100. Or use a sketch such as HyperLogLog, which handles distinct counts directly.
Explain stratified sampling and why you need weights. || Split the population into groups and sample each at its own rate, so small groups are well represented. Different rates mean an item from a heavily sampled group represents fewer population items, so you weight each item by 1/rate to get unbiased totals (Horvitz–Thompson). Without weights, the estimates over-count the groups sampled at higher rates.
You train a click model on logs with 99% of negatives dropped. The predicted click rate is 2%. What is wrong, and how do you fix it? || The model was trained on a distribution with many more positives, so its probability is inflated by about 100 times in odds. Correct with \( p = \frac{p'}{p' + (1 - p')/w} \), where \( w = 0.01 \), which gives about 0.0002, or calibrate on a held-out unsampled set. Otherwise bids or budgets based on it are far too high.
A dashboard shows traffic dropped 30% right after a sampling change. How do you find out if it is real? || Check whether the sampling rate changed at that time and whether the dashboard weights by it. Compare with an unsampled counter (load balancer request count). If the unsampled counter is flat, the drop is an artifact of un-weighted sampled data.

@@ autoscaling
value: Autoscaling changes the amount of capacity (pods, VMs, Spark executors, function instances) automatically while the load changes, so you do not have to buy for the peak all day. Real traffic is uneven. If a service needs 100 pods for 4 hours a day and 20 pods for the other 20 hours, a fixed fleet sized for the peak costs 100 × 24 = 2,400 pod-hours per day, while an autoscaled fleet costs about 100 × 4 + 20 × 20 = 800. The saving is two thirds, and the same mechanism protects you when an unexpected spike arrives and nobody is awake to add machines.
At its core, autoscaling is a feedback loop. A controller measures something (CPU use, requests per second, queue length, Kafka consumer lag), compares it with a target, and changes the number of replicas to bring the measurement back to the target. Then it measures again. Kubernetes' Horizontal Pod Autoscaler (HPA), the Cluster Autoscaler and Karpenter for nodes, KEDA for event-driven workloads, Spark dynamic allocation, Databricks cluster autoscaling and serverless platforms are all this one loop with different sensors and different actuators.
For the layer above, autoscaling is what makes cloud computing "elastic" (cloud computing, L1), what lets orchestrators such as Kubernetes keep a service healthy without a human (container orchestration, L1), and what serverless platforms hide completely (serverless, L1). The layers below explain why the loop works and where it fails. Control theory (L4) provides the vocabulary of setpoint, error, gain and delay, and the warning that a feedback loop with a delay and too much gain oscillates. Queueing theory and Little's law (L4) explain which signal to watch and which target to choose: latency does not rise slowly with load, it rises sharply as utilization nears 100%, so the best target is well below full use.
terms: Setpoint (target) — the value of the metric the controller tries to maintain, such as 60% average CPU or 100 requests per second per pod.
Control loop — the repeating cycle of measure, compare with the setpoint, decide, act, and wait.
Scale out and scale in — adding or removing replicas (horizontal scaling); scaling up or down means changing the size of one replica (vertical scaling).
Stabilization window (cool-down) — a period during which the controller refuses to reverse a decision, or looks back at past recommendations, to avoid flapping.
Headroom — spare capacity kept below the target utilization so that a sudden increase can be absorbed while new capacity is starting.
Provisioning delay — the time from the decision to add capacity until that capacity can serve traffic: scheduling, VM boot, image pull, start-up and warm-up.
Predictive and scheduled scaling — scaling ahead of load, from a forecast of regular patterns or from a calendar, instead of reacting after load arrives.
Cold start — the slow first request on a new instance that has no loaded code, caches or connections; for serverless, it also includes creating the instance.
history: Capacity planning used to be a human task: you estimated the peak, bought servers for it and waited weeks for delivery. When Amazon launched EC2 in 2006, a server could be created in minutes, and in May 2009 it added CloudWatch metrics, Elastic Load Balancing and Auto Scaling, which allowed rules such as "add two instances when average CPU is above 70% for five minutes". The same period saw research on feedback control of computing systems, collected in Hellerstein, Diao, Parekh and Tilbury's book "Feedback Control of Computing Systems" (2004), which brought classical control methods to servers.
Reactive rules were not enough for predictable patterns. Netflix described Scryer (2013), a system that forecasts demand from past weeks and scales ahead of it, and AWS added predictive scaling in 2018. Inside Google, the Borg system had vertical and horizontal autoscaling for years, described in the 2020 paper "Autopilot: workload autoscaling at Google". Apache Spark added dynamic allocation of executors in version 1.2 (2014), so a job could grow and shrink with its number of pending tasks.
Kubernetes brought the idea to everyone. The Horizontal Pod Autoscaler appeared in 2015, first using CPU only; the autoscaling/v2 API later added memory, custom metrics, external metrics and a behavior section for fine control. The Cluster Autoscaler adds nodes when pods cannot be scheduled. KEDA (started by Microsoft and Red Hat in 2019, now a CNCF project) scales on event sources such as Kafka lag, queue depth or cron schedules, and can scale a workload to zero. Karpenter (from AWS, 2021) provisions nodes directly from pending pods and picks instance types on its own. Serverless platforms (AWS Lambda, 2014) pushed the loop inside the provider: you pay per request, and the platform adds instances.
how: Each pass of the loop has five steps. Observe: collect a metric for the workload, such as average CPU as a fraction of requested CPU, or requests per second per pod, or consumer lag. Compare: divide by the target. Decide: compute the desired number of replicas. Constrain: clamp it between a minimum and a maximum, and apply rate limits on how fast it may change. Act: ask the platform to change the replica count, then wait for the system to react before deciding again. Control theory (L4) names these parts: the metric is the measured output, the target is the setpoint, the difference is the error, and the replica count is the control input.
The decision rule in Kubernetes is a proportional controller: desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric). If 4 pods run at 90% CPU and the target is 60%, then 4 × 90/60 = 6 pods. If the metric is within a tolerance of the target (10% by default), nothing changes, which avoids small, pointless moves. The same idea works for other signals: if each consumer can process 8,000 messages per second and 60,000 arrive, you need ceil(60,000 / 8,000) = 8 consumers. Proportional rules are simple and fast, but they assume that the metric moves in proportion to the number of replicas, which is true for stateless services and false for many others.
Choosing the signal is where queueing theory (L4) helps. Little's law says that the average number of requests in the system equals the arrival rate times the time each spends there (\( L = \lambda W \)). So you can compute how many concurrent workers you need: 2,000 requests per second with 50 ms of service time means 2,000 × 0.05 = 100 requests in flight. If one pod runs 8 requests at once, 100 / 8 = 12.5 pods would be busy all the time. But a server that is busy all the time has a long queue. In the simplest queue model (M/M/1), the average response time is \( S / (1 - \rho) \), where S is the service time and ρ the utilization. At ρ = 50% the time is 2 × S, at 70% it is 3.3 × S, at 90% it is 10 × S, and at 95% it is 20 × S. This sharp knee is why targets of 50–70% utilization are common and why a target of 90% gives bad latency.
Delays make feedback loops risky. After the controller decides to add pods, many things must happen: the metric system scrapes values (every 15–60 s), the HPA runs (every 15 s by default), the scheduler places the pod, and if there is no room, the node autoscaler must start a VM (1–3 minutes), the image must be pulled, the application must start and pass its readiness check. The total can be 2–6 minutes. During that time the metric is still high, because the new capacity is not ready. A naive controller keeps adding more, then overshoots, then removes too many, and the system oscillates. Control theory describes this: high gain plus delay gives instability. Practical defences are rate limits on scale-up (by default HPA can at most double the pods or add 4 per 15 seconds, whichever is larger), ignoring pods that are not ready yet, and, most importantly, slow scale-down. The HPA scale-down uses a stabilization window of 300 seconds by default: it looks at the recommendations of the past five minutes and takes the highest, so a short dip in load does not remove capacity that will be needed again soon.
There are two layers of capacity. The pod autoscaler decides how many replicas the workload wants. If the cluster has no room, the pods stay Pending, and a node autoscaler (Cluster Autoscaler or Karpenter) sees them and adds nodes; later, when nodes are mostly empty, it drains and removes them. Spark works the same way inside a job: dynamic allocation requests 1 extra executor after tasks have been waiting for 1 second, then 2, 4, 8 in each following round while the backlog stays, and removes an executor that has been idle for 60 seconds. It must not lose shuffle files held by executors that are removed, so it needs an external shuffle service, shuffle tracking, or decommissioning to be enabled.
Beyond reactive rules, predictive autoscaling forecasts the next hours from daily and weekly patterns and starts capacity early, which hides the provisioning delay. Scheduled scaling does the same with a calendar for known events, such as a launch or a daily batch window. Event-driven autoscaling (KEDA) uses the work waiting, not the work being done, as the signal: Kafka lag, queue length, or the number of pending jobs. For consumer groups, the maximum useful number of replicas is the number of partitions, because extra consumers would sit idle.

example: Take a web service. Each pod serves 8 requests at a time, the average request takes 50 ms, and the HPA target is 65% utilization.
Sizing from Little's law. At 2,000 requests per second, requests in flight = 2,000 × 0.05 = 100. A fully busy pod handles 8, so you would need 12.5 pods at 100% load. At the 65% target you need 100 / (8 × 0.65) = 19.2, so 20 pods. At the night load of 400 requests per second, in-flight = 20, so 20 / (8 × 0.65) = 3.85, so 4 pods. If the minimum is 4 and the maximum is 40, the fleet moves between 4 and 40 pods over the day.
One HPA step. Currently 10 pods run at 91% CPU against a target of 65%. The ratio is 91 / 65 = 1.4, which is beyond the 10% tolerance. Desired = ceil(10 × 1.4) = 14 pods. The scale-up rule allows at most max(100% of 10, 4 pods) = 10 extra pods in 15 seconds, so 14 is allowed. After the new pods are ready, CPU falls to about 91 × 10/14 = 65%, as intended.
The cost of delay. Suppose a flash sale raises the load from 2,000 to 3,000 requests per second. The 20 pods have a capacity of 20 × 8 / 0.05 = 3,200 requests per second at 100% busy, but at 3,000 they run at 94% busy and the latency knee is steep (M/M/1: 1/(1 − 0.94) ≈ 17 times the service time, about 830 ms instead of 50 ms). The HPA computes 20 × (94/65) = 29 pods. If the extra nodes need 165 seconds to appear (as in the diagram), users see slow responses for nearly three minutes. A lower target (50%) or a predictive rule that scales before the sale would avoid it. This is the headroom trade-off in numbers.
Scale-down and flapping. After the sale the load falls to 1,000 requests per second. The HPA recommends 10 pods. With the 300-second window, it keeps the highest recommendation of the last five minutes, so for 5 minutes it stays at the higher count, and then removes pods in steps. If load jumps back after 3 minutes, no capacity was lost. Without this window, the fleet would shrink and then immediately grow again, paying the start-up cost twice.
Last, a Kafka consumer group. The topic has 12 partitions and receives 60,000 messages per second. One consumer processes 8,000 per second. Needed = ceil(60,000 / 8,000) = 8 consumers. If the rate rises to 120,000, the computed need is 15, but only 12 are useful, because a partition is read by at most one consumer in the group. Autoscaling beyond 12 does nothing; the fix is more partitions or faster consumers.
intuition: A thermostat for servers: it measures the room, compares it with the number you set, and turns the heating up or down, but it must wait for the room to warm up before measuring again.
The idea is natural because load changes while capacity is cheap to change. If you can observe how loaded the system is and you can change its size, then a rule that moves the size toward "just enough" follows. Everything difficult comes from two facts that the thermostat also has: the room reacts slowly (provisioning delay), and the sensor is noisy. A controller that ignores delay overreacts, and one that ignores noise flaps. So the design is always the same: a proportional rule, a target with headroom, quick growth, slow shrinkage, and limits at both ends.
mistakes: People often think autoscaling solves every capacity problem. In fact it adds replicas only for the part of the system that scales. If the bottleneck is a database, a lock or an external API, more pods make it worse: 100 new pods with 20 connections each open 2,000 database connections.
People often think CPU is the right metric for everything. In fact CPU is a good signal only for CPU-bound stateless work. For services waiting on I/O it stays low while latency rises; for consumers the right signal is lag or queue length; for latency-sensitive APIs requests per second or concurrency per pod is better.
People often think autoscaling reacts instantly. In fact the whole path from metric to ready pod takes minutes, and for a sudden spike the damage is done before help arrives. Autoscaling handles trends over minutes and hours; spikes over seconds need headroom, queues, load shedding or pre-warmed capacity.
People often think scale-down is free savings. In fact removing a pod can drop warm caches, in-flight work and connections, and can trigger rebalancing in stateful systems (Kafka consumer groups, Spark shuffle files). Too-aggressive scale-down creates flapping, which costs more than steady capacity.
People often think scale to zero is always good. In fact the first request after zero pays a cold start of seconds, which breaks latency targets for user-facing paths. Scale to zero fits batch and event-driven workloads that tolerate a delay.
tradeoffs: Choose reactive autoscaling when load changes slowly or unpredictably and a few minutes of delay is acceptable. Choose predictive or scheduled scaling when the pattern is regular (daily peaks, a known launch at 9:00) and the provisioning delay is long: you pay for capacity slightly early, but you avoid the minutes of overload. Combine them: predictive for the baseline, reactive for surprises.
Choose a low utilization target (40–60%) for latency-sensitive services with slow start-up, where a spike of 50% in load must be absorbed without new pods; you pay about 1.5 to 2 times more for steady capacity. Choose a high target (70–80%) for batch, background or tolerant services, where throughput per dollar matters more than tail latency. The M/M/1 numbers show the price: at 80% the mean response time is 5 service times, at 50% it is 2.
Choose CPU or memory as the metric when the workload is CPU-bound and stateless, since it needs no extra setup. Choose requests per second or concurrency per pod when CPU does not track load (I/O-bound services). Choose queue length or consumer lag when the work arrives through a queue, because lag measures work that is waiting, not work being done, and so it reacts earlier. Lag-based scaling needs a cap by partition count and care to avoid rebalance storms.
Choose horizontal scaling (more replicas) when the service is stateless and can be copied; choose vertical scaling (bigger pods, VPA) when the workload cannot be split or has a fixed number of shards. Do not let the HPA and the VPA act on the same metric, since they fight each other.
Choose aggressive scale-down (short window) when cost dominates and start-up is fast (a few seconds); choose slow scale-down (5–15 minutes) when start-up is slow or caches are expensive. Choose scale to zero for rarely used or event-driven workloads; keep at least 1–2 replicas for user-facing services, and at least 2 across zones when availability matters.
friction: Delay is the main enemy. Image pulls of several GB, JVM warm-up, model loading for ML services, and node boot all stretch the time to useful capacity. Teams reduce it with smaller images, pre-pulled images, warm pools of nodes, overprovisioning pods that are evicted when real pods arrive, and faster start-up. Without that work, autoscaling reacts to the last spike, not the current one.
Stateful and shared-resource systems scale badly. Databases, caches and brokers need data movement and rebalancing when nodes join, which is slow and can reduce performance while it happens. Downstream systems have fixed limits: connection pools, API quotas, licence counts. A burst of new pods can overload them and create a failure larger than the one you were avoiding.
Metrics are imperfect. Averages hide imbalanced pods, scrape delays make the signal old, and a bad metric (for example CPU of a pod that is mostly throttled) makes a wrong decision. Many HPA surprises come from wrong resource requests: utilization is relative to the request, so a pod that requests 100m CPU and uses 300m looks 300% busy.
Cluster-level issues add more. Bin-packing leaves nodes half empty, pod disruption budgets and local storage block node removal, spot capacity can disappear, and cloud quotas can stop scale-out when it matters most. Cost can also surprise: a metric bug or a retry storm can scale out to the maximum and stay there. Finally, autoscaling hides inefficiency: a service that needs 40 pods because of a slow query will quietly pay for them.
practice: Start from measurement. Load-test one pod to find the throughput at which latency stays within the objective (not the point where it falls over), then set the target from that number, usually 50–70% of the saturation point. Set accurate CPU and memory requests, because the HPA computes utilization against them.
Set sensible bounds. The minimum should cover your baseline and your availability needs (at least 2 replicas, in different zones, for a production service). The maximum should reflect budget and what downstream systems can take, and you should alert when the service is at its maximum, since then autoscaling can no longer help. Scale up fast and down slowly: keep the default 300 s scale-down window or lengthen it, and use scale-up policies to allow doubling when needed.
Reduce the delay: keep images small, use readiness probes that reflect real readiness, warm caches before accepting traffic, and keep a little spare node capacity (overprovisioning). For queue consumers, use KEDA with lag or queue length and cap replicas at the partition count. For Spark and Databricks, set minimum and maximum workers or executors, enable shuffle tracking or decommissioning, and prefer job clusters that exist only for a run.
Observe the loop itself: chart desired versus actual replicas, the metric, the target, and the time from spike to ready pods. If the replica count oscillates, lengthen the windows or lower the gain. Rehearse a spike in a test environment before it happens in production. Use scheduled or predictive scaling for known peaks, and keep a manual override for incidents.
quiz: In the HPA formula, 6 pods run at 80% CPU with a target of 50%. How many pods are desired? || desired = ceil(6 × 80 / 50) = ceil(9.6) = 10 pods.
Why does a high delay between decision and effect make a proportional controller oscillate? || The metric stays high until the new capacity is ready, so the controller keeps adding more than needed (overshoot). When the capacity arrives, the metric drops and the controller removes too much. Rate limits, stabilization windows and ignoring not-ready pods reduce this.
Why is a utilization target of 90% usually a poor choice for a latency-sensitive service? || Queueing theory shows that response time grows like 1/(1 − ρ): at 90% it is about 10 times the service time, and at 50% only 2 times. A spike also leaves no room while new pods start. A target of 50–70% keeps latency low and gives headroom.
A topic has 16 partitions and 200,000 messages per second arrive; one consumer handles 10,000 per second. How many consumers should autoscaling run? || The computed need is 200,000 / 10,000 = 20, but only 16 consumers are useful because each partition is read by one consumer in the group. Run 16 and add partitions or speed up consumers if lag still grows.
When would you choose predictive or scheduled scaling over a reactive HPA? || When the load pattern is regular (daily peaks, known launches) and capacity takes minutes to become ready. Scaling ahead of time hides the provisioning delay, while a reactive rule only responds after users are already slowed. Keep a reactive rule for surprises.
interview: Why did our HPA scale to the maximum and stay there, although traffic is normal? || Likely a bad metric or request setting: CPU requests set too low make utilization look high, or a retry storm or slow dependency raised work per request. Check the metric against requests, look at downstream latency and error rates, and verify that pods are ready. Fix the cause (requests, a timeout, a dependency), and add an alert when the service sits at its maximum.
Explain why scale-down is slower than scale-up by default. || Scaling up too late hurts users at once, while scaling down too early only wastes money for a few minutes and risks flapping, where capacity is removed and must be added again at the cost of start-up delay. HPA's 300 s stabilization window takes the highest recommendation over five minutes, which is the asymmetric rule from control practice.
How do you autoscale a Kafka consumer service, and what limits it? || Scale on consumer lag (or lag per replica) with KEDA or a custom metric, so the signal is work waiting. The upper limit is the number of partitions, since one partition goes to at most one consumer. Each scale event triggers a rebalance that pauses consumption, so use cooperative rebalancing, static membership and conservative windows.
Your service scales fine but latency still spikes for two minutes at each load jump. What can you do? || The provisioning delay dominates. Lower the target for more headroom, pre-scale with a schedule or prediction, keep warm spare nodes and overprovisioned low-priority pods, shrink images, speed up start-up and warm-up, and use readiness gates. Also add load shedding or queueing for the gap.
Compare HPA, VPA and Cluster Autoscaler. How do they interact? || HPA changes the number of pods, VPA changes pod resource requests, and Cluster Autoscaler (or Karpenter) changes the number of nodes in response to pending pods. HPA and VPA should not both act on CPU or memory for the same workload. HPA scale-out may need the node autoscaler, which adds the largest part of the delay.
What would you watch to know if autoscaling is working well? || Desired versus ready replicas, time from load rise to ready capacity, latency and error rate during scale-up, time at maximum replicas, flapping count, utilization after settling, and cost per request. The aim is stable latency with the lowest steady cost.

@@ residual
value: A residual connection (also called a skip connection) adds the input of a block to the output of the block: \( y = x + F(x) \). The block F no longer has to produce the whole answer. It only has to produce a correction to x. This one addition is the reason that neural networks with 100, 1,000 or more layers can be trained at all. Before 2015, making a network deeper beyond about 20 layers made it harder to train and often made it worse, even on the training data. ResNet (He, Zhang, Ren and Sun, 2015) added the skip, trained a network with 152 layers, and won the ImageNet 2015 classification, detection and localization tasks.
The reason is about how learning signals travel. Training uses backpropagation: the error at the output is sent backward through every layer, and each layer multiplies it by its local derivative. In a plain deep network, that product has dozens of factors. If the typical factor is a little below 1, the signal that reaches the early layers is almost zero (0.9 multiplied 50 times is 0.005); if it is a little above 1, it explodes. A skip connection gives the signal a second route that passes through the addition with a factor of exactly 1, so the early layers always receive a usable gradient. The calculus of the chain rule (L4) gives this directly: the derivative of x + F(x) is 1 + F′(x), and the "1" is the identity path.
For the layer above, almost everything in modern deep learning uses this. Every transformer layer is two residual blocks, one around attention and one around the MLP, so every large language model is a stack of residual additions (deep learning, L1). Image models, diffusion U-Nets, speech models and recommendation networks use it too. Interpretability research (L2) treats the running sum as a shared channel, the "residual stream", which each layer reads from and writes to, and studies what each layer adds. The single lower layer here, calculus, supplies the argument for why it works: gradients through a sum are the sum of gradients, so an additive path never shrinks the signal.
terms: Residual block — a small group of layers F with a skip around it, computing \( y = x + F(x) \).
Skip (shortcut) connection — the path that carries x around the block and adds it to the output.
Identity mapping — a function that returns its input unchanged, \( f(x) = x \).
Vanishing and exploding gradients — the backpropagated signal becoming extremely small or extremely large because it is multiplied by many factors below or above 1.
Degradation problem — the observation that adding layers to a plain deep network can increase the training error, which is not caused by overfitting.
Residual stream — in a transformer, the vector that is carried from layer to layer, to which every attention and MLP block adds its output.
Layer normalization (LayerNorm) — rescaling a vector to zero mean and unit variance across its features, with learned scale and shift; it stabilizes the size of activations.
Pre-LN and post-LN — the two placements of normalization: pre-LN computes x + F(LN(x)), post-LN computes LN(x + F(x)).
history: Deep networks were known to be hard to train long before ResNet. Hochreiter (1991) and Bengio, Simard and Frasconi (1994) explained the vanishing gradient problem for recurrent networks. The LSTM (Hochreiter and Schmidhuber, 1997) fixed it for sequences with an additive cell state, \( c_t = f \times c_{t-1} + i \times g \) (the forget gate f was added by Gers et al. in 2000), which is a skip connection through time. For feed-forward networks, better initialization and batch normalization (Ioffe and Szegedy, 2015) made 20-layer networks trainable, but deeper plain networks hit a new problem.
In their 2015 paper (arXiv December 2015, CVPR 2016 best paper), He, Zhang, Ren and Sun at Microsoft Research documented the degradation problem: on CIFAR-10 a 56-layer plain network had higher training error than a 20-layer one. This was surprising, because a deeper network could, in principle, copy the shallower one and set its extra layers to the identity, so it should never be worse. Optimizers apparently could not find that solution. Their fix was to build the identity in: let the layers learn \( F(x) = H(x) - x \), so the identity is the easy solution, "all weights near zero". A 152-layer ResNet reached about 3.6% top-5 error on ImageNet as an ensemble, below the roughly 5% usually quoted for human performance on that task, and it did so with fewer operations than the 19-layer VGG network (about 11.3 billion versus 19.6 billion multiply-adds). They also trained a 1,202-layer network on CIFAR-10 without optimization trouble, though it overfit.
Related ideas came just before and after. Highway Networks (Srivastava, Greff and Schmidhuber, May 2015) used a learned gate to mix input and transformation; ResNet removed the gate. "Identity Mappings in Deep Residual Networks" (He et al., 2016) showed that keeping the skip path completely clean, with no ReLU or normalization on it ("pre-activation"), trained a 1,001-layer network better. Veit, Wilber and Belongie (2016) showed that a ResNet behaves like an ensemble of many shallow paths. DenseNet (2017) concatenated instead of adding. The transformer (Vaswani et al., 2017) used a residual connection around every sub-layer. GPT-2 (2019) moved the normalization to the inside of the branch (pre-LN), and Xiong et al. (2020) explained why this makes training stable without a long learning-rate warm-up. Elhage et al. (2021) introduced the residual stream view for interpretability.
how: The computation is a single line. A block has a function F (for example two convolutions, or an attention layer, or an MLP) with its own learned weights. The output is \( y = x + F(x) \). The input x and the output of F must have the same shape, so that they can be added element by element. When the shape changes (more channels, lower resolution), the skip path uses a 1×1 convolution or a linear projection to match, and in a transformer every block keeps the same width, d_model, so no projection is needed.
Why does this help? Look at the backward pass with the chain rule (calculus, L4). The derivative of y with respect to x is \( I + \partial F/\partial x \), the identity matrix plus the block's Jacobian. Now stack L blocks: \( x_L = x_l + F_l(x_l) + F_{l+1}(x_{l+1}) + \cdots + F_{L-1}(x_{L-1}) \). The output of any layer is the input of an earlier layer plus a sum of corrections. So the gradient of the loss with respect to x_l is the gradient at the top plus terms that flow through the F branches: \( \partial \text{Loss}/\partial x_l = \partial \text{Loss}/\partial x_L \times \left(I + \frac{\partial}{\partial x_l} \sum F_i\right) \). The first term, the identity, does not depend on the depth or on any weights. No product of many small numbers can wipe it out. A plain network has only the second kind of term: a long product of Jacobians.
There is also an easier optimization problem at the start. With small random initial weights, F(x) is close to zero, so each block starts as nearly the identity, and the whole 100-layer network starts as nearly "output = input". The optimizer then adds small useful corrections, layer by layer. In a plain network, the layers must learn to pass information through unchanged, which means finding weights whose nonlinear composition equals the identity, a much harder target. The skip makes "do nothing" the default and "do something" the learned part.
ResNet for images uses two block types. The basic block has two 3×3 convolutions, \( y = x + \mathrm{conv}(\mathrm{relu}(\mathrm{conv}(x))) \). The bottleneck block, used in ResNet-50/101/152, uses 1×1 convolution to reduce channels (256 to 64), a 3×3 convolution at the low width, and a 1×1 convolution to expand back (64 to 256). That block has 16,384 + 36,864 + 16,384 = 69,632 weights, while two 3×3 convolutions at 256 channels would need 2 × 589,824 ≈ 1.18 million. Batch normalization sits inside the branch, so the skip path stays clean.
In a transformer, each layer has two residual blocks: x ← x + Attention(LN(x)), then x ← x + MLP(LN(x)). Every token has its own stream vector of size d_model (for example 4,096). The embedding writes the first value into it. Each attention head reads the stream through its own projections and writes a result back by adding. Each MLP does the same. At the end, a final LayerNorm and the unembedding matrix turn the stream into next-token scores. The stream therefore carries everything, and each of the, say, 64 sub-layers (32 layers × 2) only edits it. Because the sum is linear, different components do not overwrite each other; they add to a shared space. This is the picture used in interpretability, and it makes methods such as the "logit lens" (reading predictions out of intermediate layers) meaningful.
The placement of normalization matters. In the original transformer (post-LN), \( y = \mathrm{LN}(x + F(x)) \), the normalization sits on the main path, so gradients pass through a LayerNorm at every layer and the identity path is no longer clean. Deep post-LN models need careful warm-up and often diverge. Pre-LN, \( y = x + F(\mathrm{LN}(x)) \), keeps the main path as a pure sum, so it trains stably, and nearly all current large models use it (or close variants such as RMSNorm). Its cost is that the stream grows in size with depth, since each block adds to it, so later layers have a relatively smaller effect unless the model compensates. A common fix at initialization, used in GPT-2, is to scale the output weights of each residual branch by \( 1/\sqrt{N} \), where N is the number of residual layers, so the variance of the sum stays under control.

example: Gradient through depth, with numbers. Imagine 50 layers and look at one number: the factor by which each layer multiplies the backward signal. In a plain network at initialization, these factors are not controlled. If each is about 0.9, the signal reaching layer 1 is 0.9⁵⁰ ≈ 0.005, or half a percent of the original. If each is about 1.1, it is 1.1⁵⁰ ≈ 117. Either way the early layers get an unusable signal.
In a residual network, each factor is \( 1 + j \), where j is the branch's derivative. At initialization the branches output small values, so j is small, say between −0.02 and +0.02 with random signs. The product of 50 such factors is about 1 with a spread of roughly 0.02 × √50 ≈ 0.14. The signal reaches layer 1 at about its original strength. Even if training later makes some j values larger, the identity path remains.
Now count parameters in one ResNet-50 bottleneck on 256-channel input. Reduce with a 1×1 convolution to 64 channels: 256 × 64 = 16,384 weights. Apply a 3×3 convolution at 64 channels: 3 × 3 × 64 × 64 = 36,864. Expand with a 1×1 convolution back to 256: 64 × 256 = 16,384. The block has 69,632 weights, and the output has the same shape as the input, so the skip is a plain addition. A plain 3×3 layer pair at 256 channels would need 2 × (3 × 3 × 256 × 256) = 1,179,648 weights, about 17 times more. Bottlenecks let ResNets be deep and still cheap.
Next, a tiny forward pass. Let x = (2.0, −1.0) and let a block compute F(x) = (0.1, 0.3) after training. The output is \( y = x + F(x) \) = (2.1, −0.7). If the block has nothing to add, it learns F(x) = (0, 0) and passes x unchanged. Without the skip, the block would have to reproduce (2.0, −1.0) through its own layers and nonlinearities, which is a much harder thing to learn than "output zero".
Last, the transformer stream. Take a model with d_model = 4,096 and 32 layers. For one token the stream is a vector of 4,096 numbers. It starts as the token embedding with typical size about 1. After each of the 64 sub-layers, it gets a new addition. If each addition has a typical size of 0.3 and the additions are roughly independent, the norm of the stream grows like 0.3 × √64 ≈ 2.4, so the final stream is a few times larger than the embedding. The last LayerNorm removes that scale before the output projection. This growth is why pre-LN models rely on the final normalization, and why some architectures scale the branch outputs.
intuition: Each layer edits a draft instead of rewriting it from scratch; if a layer has nothing useful to add, it hands the draft on unchanged.
The idea is natural because it makes the default behaviour safe. A deep network is a long chain of steps, and any chain is only as good as its weakest step, for both the forward signal and the backward error. With a skip, the chain always has a bypass that does nothing harmful, and each layer only has to find a small improvement. Learning a small change is easier than learning a whole new representation, and a mistake in one layer cannot erase the information already collected. The backward pass benefits in the same way: errors from the output can reach any layer directly. It also explains why ResNets behave like ensembles of shallow networks: there are many routes from input to output, and short routes carry most of the gradient.
mistakes: People often think a residual connection makes the network learn an identity function. In fact it makes the identity the default and cheap, so the layers learn only what is needed on top. A trained ResNet's blocks are far from zero, and the final function is highly nonlinear.
People often think skip connections only fix vanishing gradients. In fact they also change the optimization landscape, making it smoother and easier to follow, and they change the function class: the network can be seen as a combination of paths of different depths. Batch normalization already helped with gradient scale, yet very deep plain networks still showed the degradation problem.
People often think the order of normalization is a detail. In fact post-LN and pre-LN behave very differently in deep transformers. Post-LN puts a normalization on the main path, which weakens the clean gradient route and needs warm-up; pre-LN keeps the route clean and trains stably, at the cost of a growing stream norm.
People often think a deeper ResNet is always better. In fact returns diminish: ResNet-1202 on CIFAR-10 was worse than ResNet-110 because it overfit. The skip makes depth trainable, not useful. Width, data and regularization still decide the result.
People often think the residual stream is just an implementation trick. In fact in a transformer it is the main data structure: all components communicate through it, its width d_model limits how much information fits, and interpretability work analyses the model by tracking what each component writes into it.
tradeoffs: Choose pre-LN (x + F(LN(x))) when you train a deep transformer and want stability without delicate warm-up; choose post-LN when you can afford careful tuning and want slightly better results at moderate depth, as in some smaller published models. You trade stability against a possible small quality gain, and with pre-LN you accept a growing stream norm and a weaker effect of late layers.
Choose addition (ResNet) when you want a cheap shortcut that keeps the width constant; choose concatenation (DenseNet, U-Net) when later layers should reuse early features directly, such as in segmentation where high-resolution detail is needed. Concatenation grows the width, and with it memory and compute, so it costs more per layer; addition mixes information in a fixed-size space and is cheaper but can blur features together.
Choose a bottleneck block (1×1, 3×3, 1×1) when depth is large and compute is limited, as in ResNet-50 and above; choose the basic block for shallow networks (18 or 34 layers) where simplicity is enough. The bottleneck reduces cost about 17 times for the block in the example, but needs more layers and a more careful channel design.
Choose learned gates or scales on the branch (Highway, ReZero, LayerScale) when you must train very deep or unusual networks without warm-up; the scale starts near zero so each block begins as the identity. You add a few parameters and a bit of complexity, and in standard well-tuned recipes plain residuals are usually enough.
Choose more depth only if the task benefits from it: for a fixed parameter budget, wider and shallower models run faster on GPUs because layers execute one after another, while deeper models can represent more steps of computation. Memory for activations also grows linearly with depth, which is why training deep models uses activation checkpointing (recompute instead of store).
friction: The skip path is not free. The input x must stay in memory until the addition, and the sum forces the same shape on all blocks, which limits architecture choices; changing width needs a projection and weakens the clean path.
In pre-LN transformers, each block adds to the stream, so its norm grows with depth. Recent work points out that the deepest layers then contribute little relative to the stream and can sometimes be removed with small loss, which means that part of the depth is wasted parameters and compute. Research such as hyper-connections (2024) lets the model learn how to mix several streams, to give depth more value, but these are not yet standard.
Numerical range matters at scale. In low precision (bfloat16, FP8) a long running sum of many small additions loses accuracy, and some models show a few dimensions of the stream with huge values ("massive activations") that matter for behaviour and are hard for quantization. The stream is also crowded: the model packs many features into d_model dimensions (superposition), so it is hard to say what any direction means, which is a central difficulty for interpretability.
Theory is incomplete. We know skip connections help and have good arguments (gradient paths, smoother loss surfaces, ensembles of paths), but there is no complete explanation of how deep a network should be or how to choose the scale of the residual branches. Practice relies on tuned recipes: initialization scaling, learning-rate warm-up, and normalization placement.
practice: Use residual connections by default in any network deeper than a few layers; in transformers use pre-LN or RMSNorm placed inside the branch, with a final norm before the output. Keep the skip path as clean as you can: no activation or normalization on it. If you design a block that changes the width, use a projection only on the skip that needs it.
Initialize the branches so that they start near zero or small: scale the output projection of each branch by about \( 1/\sqrt{\text{number of residual layers}} \) (as GPT-2 did), or use a zero-initialized gamma in the last normalization of the branch (a common trick in ResNets), or use ReZero/LayerScale. This makes the network start near the identity and trains more smoothly.
When a very deep model is unstable, check the stream norm per layer first. A norm that grows quickly or contains a few huge dimensions is a warning sign. Monitor gradient norms per layer; with residual connections they should be of similar order across depth. Use gradient clipping and a warm-up schedule as usual.
For understanding a trained model, read the residual stream view: measure how much each layer changes the stream (norm of F(x) relative to x), try the logit lens on intermediate layers, and remember that ablating a single block in a ResNet or transformer usually hurts only a little, which is a sign of the ensemble-like behaviour. To study the idea, train a plain 40-layer network and a residual one on CIFAR-10 for a few epochs and compare the training curves; the difference is clear in a notebook.

interview: Explain why ResNet works, beyond "it fixes vanishing gradients". || Three views: (1) gradient path, since \( d(x + F)/dx = I + F' \) gives a direct route that does not decay; (2) easier optimization, since the zero function for F is the identity, so extra layers cannot hurt at the start and layers learn small corrections; (3) ensemble view, since the network is a sum over many paths of different lengths, mostly short, so no single layer is critical. Evidence: ablating one block barely changes accuracy, and very deep nets train with skips and not without.
What is the difference between pre-LN and post-LN, and which would you pick for a 100-layer transformer? || Post-LN is LN(x + F(x)), pre-LN is x + F(LN(x)). Post-LN puts normalization on the main path, which gives larger gradients near the output and needs warm-up and careful tuning to avoid divergence. Pre-LN keeps an unobstructed identity path and is stable. For 100 layers I would use pre-LN (or RMSNorm), a final norm, and scaled initialization of branch outputs, accepting that the stream norm grows.
What does "residual stream" mean for a transformer, and how does it help interpretability? || The stream is the vector per token that every attention head and MLP reads from and adds to. Since the final output is the sum of all contributions, you can attribute logits to individual components (direct logit attribution) and study how information moves between layers. The width d_model is the communication bandwidth.
Your 200-layer network trains well for 1,000 steps and then diverges. How do you debug it? || Log the stream norm and per-layer gradient norms. Check initialization of branch outputs (scale by \( 1/\sqrt{N} \) or zero-init), normalization placement, learning rate and warm-up, and numeric precision (bf16 accumulation, large activations). Try lower learning rate, gradient clipping, and a branch scale such as LayerScale. Find the first layer whose activation norm grows abnormally.
Can you use a skip connection if the block changes the tensor shape? || Yes, with a projection on the skip path, such as a 1×1 convolution with stride or a linear layer, so the shapes match before the addition. The projection adds parameters and removes the perfect identity path, so use it only where the shape changes and keep the other skips as pure identity.
How is a residual connection related to an Euler step of an ODE? || \( x_{l+1} = x_l + F(x_l) \) is one explicit Euler step of \( dx/dt = F(x) \) with step size 1. Neural ODEs take this limit with an adaptive solver. The view explains smooth feature evolution but real networks use different weights per step and are not exactly ODE flows.

value: A convolutional layer slides a small set of weights, called a filter or kernel, over an image (or a sound wave, or any signal laid out on a grid) and computes a weighted sum at every position. The same weights are used at every position. This builds one assumption into the network: a pattern means the same thing wherever it appears. An edge in the top left corner is the same kind of edge as one in the bottom right, so one detector is enough for both.
That assumption removes almost all of the cost of a fully connected layer. Take a colour image of 224 × 224 pixels (150,528 numbers) and a first layer that produces 64 feature maps of 112 × 112. A fully connected layer would need 150,528 × 802,816 ≈ 120 billion weights. A convolutional layer with 64 filters of size 7 × 7 needs 7 × 7 × 3 × 64 = 9,408 weights, which is about 13 million times fewer, and it learns faster because every image position provides training signal for the same weights. Convolutional networks (CNNs) made computer vision work in practice: LeNet read handwritten digits in the 1990s, AlexNet won ImageNet in 2012 by a wide margin, and ResNet, VGG and their successors became the base of image classification, detection, segmentation and many audio and video models.
For the layer above, convolution is the building block that deep learning (L1) uses for images, audio and time series, and the base of computer vision systems (L1). The layers below explain why it is both correct and fast. Linear algebra (L4) shows that a convolution is a matrix multiplication with a special, weight-shared matrix, which is why GPUs can run it as a matrix multiply. Fourier analysis (L4) gives the convolution theorem: convolution in space equals multiplication in frequency, which explains what filters do (blur removes high frequencies, edge filters keep them) and offers fast algorithms for large kernels. The visual cortex (L5), where Hubel and Wiesel found cells that respond to oriented edges in small regions, was the biological inspiration for stacking local detectors into a hierarchy.
terms: Kernel (filter) — a small grid of learned weights, such as 3 × 3 × C, that is slid over the input.
Feature map (channel) — the output of one filter at all positions; a layer with 64 filters produces 64 feature maps.
Stride — the step by which the kernel moves; stride 2 halves the output width and height.
Padding — extra values (usually zeros) added around the border so the kernel can be centred on edge positions and the output size can be kept.
Receptive field — the region of the original input that can influence one output value; it grows with depth.
Weight sharing — using the same kernel weights at every position, so the number of parameters does not depend on the image size.
Translation equivariance — if the input shifts, the output shifts by the same amount; the layer gives the same answers at a new place.
Pooling — reducing resolution by summarizing small regions, for example taking the maximum of each 2 × 2 block.
history: The biological story begins with David Hubel and Torsten Wiesel, who in 1959 and 1962 recorded from cat visual cortex and found "simple cells" that respond to an edge at one orientation in a small area, and "complex cells" that respond to such an edge anywhere in a slightly larger area. They received the Nobel Prize in 1981. Kunihiko Fukushima's Neocognitron (1980) turned this into a layered model with alternating feature-detecting and pooling layers, but it was trained with hand-designed rules, not backpropagation.
Yann LeCun and colleagues at Bell Labs (1989) trained such a network end to end with backpropagation to read handwritten zip codes, using local connections and shared weights. The refined LeNet-5 (LeCun, Bottou, Bengio and Haffner, 1998) read cheques in production. For about a decade, CNNs stayed in this niche, because large labelled datasets and fast hardware were missing, and kernel methods and hand-made features (SIFT, HOG) looked better on benchmarks.
In 2012 Krizhevsky, Sutskever and Hinton's AlexNet, trained on two GPUs, cut the ImageNet top-5 error from about 26% to 15.3%. It had 5 convolutional layers, 3 fully connected layers and about 60 million parameters, and it used ReLU and dropout. The following years brought deeper designs: VGG (2014) showed that stacks of 3 × 3 kernels work well, GoogLeNet (2014) used 1 × 1 convolutions to cut cost, ResNet (2015) added skip connections to reach 152 layers, and MobileNet (2017) used depthwise separable convolutions for phones. Dilated convolutions (WaveNet, 2016) brought the idea to audio. From 2020, Vision Transformers (Dosovitskiy et al.) matched and then exceeded CNNs when trained on very large datasets, and ConvNeXt (2022) showed that a CNN modernised with similar training recipes can match transformers again.
how: Think of a single-channel image first. A 3 × 3 kernel has 9 weights. Place it on the top-left 3 × 3 patch of the image, multiply each pixel by the matching weight, add the 9 products (and a bias), and write the sum into the output at that position. Move the kernel one step right and repeat; at the end of the row, go down one row. The output is a new image, a feature map. For a colour or multi-channel input with C channels, the kernel is 3 × 3 × C and the sum runs over all channels. A layer has F different kernels, so it produces F feature maps. Its parameters are F × (K × K × C + 1), where K is the kernel size.
(In deep learning libraries, this operation is technically cross-correlation, since the kernel is not flipped as in the mathematical definition. Because the kernel is learned, the flip makes no difference, and everybody calls it convolution.)
The output size follows from the sliding: for input width W, kernel K, padding P and stride S, the output width is floor((W − K + 2P) / S) + 1. For W = 224, K = 7, P = 3, S = 2 this is floor(223 / 2) + 1 = 112. The cost is the output size times the work per output value: 112 × 112 × 64 outputs, each needing 7 × 7 × 3 = 147 multiply-adds, which is about 118 million multiply-adds for this one layer.
Weight sharing gives translation equivariance: shift the input by one pixel and the feature maps shift by one pixel, with the same values. It is equivariance, not invariance; the network's final answer becomes approximately invariant only through pooling, strides and global averaging at the end. The linear algebra view (L4) is useful: if you flatten the image into a vector, a convolution is multiplication by a big sparse matrix whose rows are shifted copies of the same few weights (a Toeplitz structure). That is why gradients work as usual: the gradient for a shared weight is the sum of its gradients over all positions where it was used, and the gradient with respect to the input is a convolution with the flipped kernel (the "transposed convolution").
Stacking layers builds a hierarchy. A 3 × 3 layer sees a 3 × 3 area; a second 3 × 3 layer on top sees 5 × 5 of the original; a third sees 7 × 7. Three stacked 3 × 3 layers have the same receptive field as one 7 × 7 layer but only \( 3 \times 9 \times C^2 = 27C^2 \) weights instead of \( 49C^2 \), and they have three nonlinearities instead of one. That is why VGG and its successors use small kernels. Between stages, a stride-2 convolution or pooling halves the resolution and the network doubles the number of channels (in ResNet, 64 → 128 → 256 → 512 at the basic widths), so early layers hold fine detail (edges, colour), middle layers hold textures and parts, and late layers hold objects. A final global average pool and a linear layer produce the class scores.
A GPU does not slide windows one by one. The common method, im2col, copies every K × K × C patch into a column of a big matrix and multiplies it by the matrix of filters, so the convolution becomes one large matrix multiplication (GEMM) that tensor cores run at peak speed. For 3 × 3 kernels, the Winograd algorithm (Lavin and Gray, 2015) reduces the multiplications: a 2 × 2 output tile from a 3 × 3 kernel needs 16 instead of 36. For large kernels, the Fourier layer's convolution theorem pays off: transform to frequency space with an FFT, multiply, and transform back, at \( O(N \log N) \) instead of \( O(N \times K^2) \). Libraries such as cuDNN pick among these methods for each layer.
Cheaper variants change how channels and space are mixed. A 1 × 1 convolution mixes channels at each position and costs only \( C_{\text{in}} \times C_{\text{out}} \) weights; it is used to shrink or grow the channel count. A depthwise convolution applies one K × K kernel per channel with no mixing across channels; a depthwise separable convolution follows it with a 1 × 1 convolution. For K = 3 and 128 output channels it costs about \( 1/128 + 1/9 \) ≈ 12% of a standard convolution, roughly 8 times less. A dilated convolution spaces the kernel taps apart to see a wider area at the same cost. One-dimensional convolutions work on audio and time series, three-dimensional ones on video and volumes.

example: A one-dimensional example you can do by hand. The input is x = [0, 0, 0, 5, 5, 5], a signal with a step in the middle. The kernel is w = [1, 0, −1], which computes the difference between a value and the value two steps to its right. Slide it. Output 1 = 1×0 + 0×0 + (−1)×0 = 0. Output 2 = 1×0 + 0×0 + (−1)×5 = −5. Output 3 = 1×0 + 0×5 + (−1)×5 = −5. Output 4 = 1×5 + 0×5 + (−1)×5 = 0. The result is [0, −5, −5, 0]: it is zero in flat regions and large exactly at the step. This kernel is an edge detector, found by hand here, and learned automatically in a CNN. If the step moved one position to the right, the pattern in the output would move one position too, which is equivariance.
Now a real layer. The first layer of ResNet-50 takes a 224 × 224 × 3 image, applies 64 kernels of 7 × 7 with stride 2 and padding 3, and outputs 112 × 112 × 64. Weights: 7 × 7 × 3 × 64 = 9,408 (plus 64 biases). Output values: 112 × 112 × 64 = 802,816. Multiply-adds: 802,816 × 147 ≈ 118 million. A fully connected layer between the same two tensors would need 150,528 × 802,816 ≈ 1.2 × 10¹¹ weights, which at 4 bytes each is 480 GB, more than any GPU holds.
Next, the receptive-field and parameter trade-off with 64 channels in and out. One 7 × 7 layer has 49 × 64 × 64 = 200,704 weights. Three 3 × 3 layers have 3 × 9 × 64 × 64 = 110,592 weights and the same 7 × 7 receptive field, with 3 nonlinearities and about 45% fewer weights.
Last, depthwise separable cost. Input 56 × 56 × 128, output 128 channels, kernel 3 × 3. A standard convolution has 3 × 3 × 128 × 128 = 147,456 weights and 56 × 56 × 147,456 ≈ 462 million multiply-adds. The depthwise part has 3 × 3 × 128 = 1,152 weights, the 1 × 1 part has 128 × 128 = 16,384, together 17,536 weights (about 8.4 times fewer) and about 55 million multiply-adds. The catch is arithmetic intensity: the depthwise step does little work per byte moved, so on GPUs it often runs far below its theoretical advantage.
intuition: Scan a magnifying glass over the picture, looking for the same small shape everywhere.
The design is natural because of two facts about images. Nearby pixels are related much more than distant ones (locality), and the same kind of structure, an edge or a texture, can appear anywhere (translation symmetry). A fully connected layer ignores both facts and must learn each location separately, which needs far more data and weights. A convolution encodes both facts as hard rules, so the network spends its capacity on what to detect, not on where. The result is a hierarchy that resembles the cortex: small local detectors, combined layer by layer into larger and more abstract ones. It also shows the trade-off of strong assumptions: they help a lot when true and limit flexibility when not true, which is the point of the competition with attention.
mistakes: People often think a convolutional network recognises objects wherever they are, so it is translation invariant. In fact a convolution layer is equivariant, and exact invariance is not guaranteed. Strided layers and pooling break exact shift symmetry (a one-pixel shift can change predictions), and CNNs learn position cues from padding. Data augmentation is still needed.
People often think "convolution" in deep learning is the same as in signal processing. In fact libraries compute cross-correlation, with no kernel flip. This does not matter for learning, but it matters if you import kernels from a signal processing text or reason about the convolution theorem exactly.
People often think larger kernels are always better, since they see more. In fact stacks of small kernels give the same receptive field with fewer weights and more nonlinearity. Large kernels have returned in recent designs (7 × 7 depthwise in ConvNeXt), but only in depthwise form that keeps the cost low.
People often think the receptive field is what the network really uses. In fact the effective receptive field is much smaller than the theoretical one and has a Gaussian-like shape, concentrated at the centre. Tasks that need global context may need dilation, attention or a deeper network.
People often think CNNs are obsolete because of Vision Transformers. In fact CNNs are still strong when data is limited, and they are often faster and cheaper on edge devices. Many hybrid models use convolutions to turn pixels into patches and for local processing, and transformers for global mixing.
tradeoffs: Choose convolution when your data has a grid structure with local patterns and little training data: the built-in locality and weight sharing act as a prior, so you get good accuracy with thousands to millions of images. Choose attention (Vision Transformer) when you have very large pretraining sets (hundreds of millions of images) or need global relations from the first layer; you give up the prior and pay \( O(N^2) \) in the number of patches for full attention.
Choose small stacked kernels (3 × 3) for general accuracy per cost, as in VGG and ResNet. Choose large depthwise kernels (7 × 7 to 31 × 31) when you need a wide receptive field with low parameters and have time to tune; the large kernels run slowly on some hardware. Choose dilation when you need a wide view without losing resolution (segmentation, audio) and accept a possible gridding artifact.
Choose standard convolutions when running on GPUs with tensor cores and the goal is throughput, since dense matrix work reaches high utilization. Choose depthwise separable convolutions for phones and embedded chips when FLOPs and model size are the limit: you save about 8 times in FLOPs and parameters but may see little real speed-up on GPUs because the layers are memory-bound.
Choose max pooling or strided convolution to cut resolution quickly and save memory; choose to keep high resolution (fewer downsampling steps) for small objects and dense predictions, at higher cost, since compute scales with the number of positions. Choose a 1D convolution (or a temporal convolutional network) over a transformer for long audio or sensor streams when latency and memory must be linear in length; choose attention when relations over long distances matter and the sequence is short enough.
friction: The local receptive field means long-range relationships need many layers or special tricks. A pattern at the left of an image and one at the right can only interact after the receptive field has grown to cover both, so CNNs are weaker than attention at global reasoning when data is plentiful.
Convolutions are tied to a grid. Irregular data (graphs, point clouds, sets) does not fit, and variable object scale and rotation are not handled: the network must learn each scale and orientation from examples, or from augmentation. Equivariance to rotation and scale needs special architectures (group-equivariant networks).
Hardware efficiency can be uneven. Dense convolutions map well to matrix multiplication, but depthwise, dilated and very large kernels have low arithmetic intensity, so their FLOP savings do not turn into speed. Memory for activations at high resolution is large, and training needs it for the backward pass. Transposed convolutions can create checkerboard artifacts in generated images.
Finally, CNNs are known to lean on texture and background more than humans do, and they can be fooled by small adversarial changes. Evaluation on shifted data (different cameras, lighting) often shows large drops. These are problems of learning from data in general, but the strong local prior makes some of them more visible.
practice: For images, start from a proven backbone (ResNet, EfficientNet, ConvNeXt) pretrained on a large dataset, and fine-tune. Training from scratch needs far more data. Use 3 × 3 kernels, batch or group normalization, ReLU-family activations, and skip connections for depth. Keep input size and batch size in mind: activation memory grows with resolution squared.
Count cost before you build. For each layer: \( \text{parameters} = F \times (K^2 \times C + 1) \); \( \text{multiply-adds} = \text{output height} \times \text{output width} \times F \times K^2 \times C \). A quick spreadsheet shows where the compute and the memory go; early high-resolution layers dominate FLOPs, late layers dominate parameters. Use 1 × 1 bottlenecks to cut channels before expensive 3 × 3 layers.
On GPUs, use channels-last layout, mixed precision (FP16 or bf16), and let cuDNN autotune (torch.backends.cudnn.benchmark = True for fixed input sizes). Fuse convolution, normalization and activation for inference, for example with TensorRT or ONNX Runtime. On phones, choose depthwise separable architectures and quantize to int8, then measure real latency on the device, because FLOPs are a poor predictor.
Use augmentation (random crops, flips, colour jitter) to teach the invariances that the architecture does not guarantee. For audio and time series, try 1D convolutions with dilation before moving to heavier models. To build intuition, implement a 2D convolution in NumPy, check it against a library function, and then visualise the first-layer filters of a pretrained network: they look like oriented edges and colour blobs, as Hubel and Wiesel would predict.

interview: Explain why a convolution is a matrix multiplication and why that matters. || Flatten the input; the convolution is multiplication by a sparse matrix whose rows are shifted copies of the kernel (Toeplitz structure). Invariance is approximate and comes from pooling, strides, global average pooling at the end, and augmentation.

Why do 1×1 convolutions exist, and where are they used? || They mix channels at each position with C_in × C_out weights. They reduce or expand channel counts (bottlenecks in ResNet, Inception), form the pointwise step of depthwise separable convolutions, and act as per-position linear layers.

value: Multi-head attention (MHA) lets a transformer look at its input in several ways at once: the model's width is split into h heads, and each head has its own queries, keys and values, so each can learn a different kind of relation between tokens. The price shows up when the model generates text. To produce each new token, the model needs the keys and values of every earlier token, so it stores them in a KV cache. For a large model with a long context, this cache is bigger than anything else in memory except the weights, and reading it at every step is a main limit on speed.
Multi-query attention (MQA) and grouped-query attention (GQA) attack this directly: many query heads share a smaller number of key and value heads. In MQA, all heads share one K and one V. In GQA, the heads are split into groups and each group shares one K/V pair. Llama 2 70B has 64 query heads but only 8 key/value heads, so its cache is 8 times smaller than full multi-head attention would need: 320 KB per token instead of 2.5 MB. The number of query heads does not change, so the model keeps nearly all its ability to attend in different ways, and the quality loss is small. Most current open models use GQA: Llama 2 70B and all Llama 3 sizes, Mistral 7B, Qwen and Gemma models.
For the layer above, this decides how many users a GPU can serve at once and how long a context it can hold (transformers and LLMs, L1). The layer below explains why this is the right place to save. GPU memory (DRAM and HBM, L3) has limited capacity, such as 80 GB on an H100, and limited bandwidth, about 3.35 TB/s. During generation, attention does very little arithmetic for each byte it reads, so its speed is set by how many bytes of cache have to be moved from HBM at each step, not by how many multiplications are needed. Sharing keys and values cuts both the bytes stored and the bytes moved.
terms: Attention head — one independent attention computation, with its own query, key and value projections of size d_head (often 64 or 128).
KV cache — the stored keys and values of all earlier tokens, kept so that each new token only computes its own K and V and attends over the stored ones.
Query head and KV head — query heads produce the queries; KV heads produce the keys and values that are attended over; in MHA the counts are equal, in GQA there are fewer KV heads.
Group — a set of query heads that share one KV head; with 64 query heads and 8 KV heads, each group has 8 query heads.
Prefill and decode — prefill processes the whole prompt at once (compute-bound); decode generates one token at a time (memory-bound).
Memory-bound — the speed is limited by how fast data moves from memory, not by how fast the chip multiplies.
Uptraining — converting an existing MHA checkpoint to MQA or GQA by merging its KV heads and training a little more, instead of training from scratch.
Latent attention (MLA) — compressing keys and values into one small vector per token and rebuilding them when needed, as in DeepSeek models.
history: Multi-head attention came with the transformer (Vaswani et al., 2017), which used 8 heads of 64 dimensions each. The cost of the KV cache was not a concern in translation with short sentences. It became one when models grew and people wanted to serve them for chat. Noam Shazeer saw the problem early. In "Fast Transformer Decoding: One Write-Head is All You Need" (2019), he proposed multi-query attention: keep many query heads but only one K/V head. On a translation model this made incremental decoding much faster with only a small loss in quality. The idea was used in PaLM (2022), in StarCoder and in Falcon, but many teams avoided it because quality dropped on some tasks and training could be less stable.
Ainslie et al. (Google, EMNLP 2023) offered the middle path in "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints". They also showed how to convert an existing MHA checkpoint: average the key heads (and value heads) within each group, then continue training with about 5% of the original pre-training compute. With 8 groups, quality was close to MHA and speed close to MQA. Meta used it in Llama 2 70B (July 2023), where the paper says the feed-forward width was increased to compensate for the parameters saved. After that it became the default: Mistral 7B (2023), all Llama 3 models (2024), Qwen2 and Gemma.
The next step reduced the cache further without losing heads. DeepSeek-V2 (2024) introduced Multi-head Latent Attention (MLA), which stores a single low-dimensional latent vector per token per layer (512 numbers plus a 64-number rotary key) instead of separate K and V for each head, and reported a 93.3% smaller cache than its dense predecessor. DeepSeek-V3 (2024) kept MLA, with a cache of about 70 KB per token, compared with about 516 KB for Llama 3.1 405B. In parallel, systems work attacked the same cost from the outside: PagedAttention in vLLM (Kwon et al., SOSP 2023) removed memory waste in the cache, and quantizing the cache to 8 or 4 bits halves or quarters its size.
how: Start with standard MHA. The input x of width d_model is projected by three matrices into queries Q, keys K and values V, which are cut into h heads of size \( d_{\text{head}} = d_{\text{model}} / h \). For each head i, attention is \( \mathrm{softmax}(Q_i K_i^{\top} / \sqrt{d_{\text{head}}})\, V_i \). The h outputs are concatenated and mixed by an output matrix. Each head can learn its own pattern, such as attending to the previous token, to a matching earlier token, or to the subject of a sentence. The parameter count of the attention block is about \( 4 \times d_{\text{model}}^2 \) and does not depend on h.
Now generation. The model produces one token at a time. To compute the new token's attention, it needs K and V of all earlier tokens at every layer. Recomputing them for every step would cost quadratic work, so they are stored: the KV cache. The cache size per token is 2 (K and V) × n_layers × n_kv_heads × d_head × bytes per number. For MHA, n_kv_heads equals h. The cache grows linearly with context length and with the number of simultaneous sequences, and this is what GPU memory has to hold next to the model weights.
The lower layer explains why the cache matters for speed. During decode, one new token is processed per sequence. The weights are read once per step and shared by all sequences in the batch, so a bigger batch spreads their cost. But the KV cache belongs to each sequence: every sequence's cache must be read in full at every step. Attention does about 2 floating-point operations per cache number read (one multiply and one add per element), which is roughly 1 operation per byte for 16-bit numbers. An H100 can do about 300 operations per byte moved from HBM (about 990 teraFLOPs of dense bf16 matrix math against 3.35 TB/s), so attention uses less than 1% of the chip's arithmetic and is entirely limited by memory bandwidth. Time per step is about (bytes of cache read) / (HBM bandwidth). Cut the cache by 8 and this part of the step is 8 times faster. This is why DRAM and HBM (L3) is the right foundation to name: bandwidth and capacity are the resources GQA saves.
GQA changes only the key/value side. The model keeps h query heads but only g KV heads, where g divides h. Query head i uses KV head \( \lfloor i / (h / g) \rfloor \). With h = 64 and g = 8, query heads 0–7 use KV head 0, heads 8–15 use KV head 1, and so on. The attention formula per head is unchanged; the K and V tensors are simply reused by the heads of a group (efficient kernels read them once and apply them to all heads of the group, without copying). The K and V projection matrices become smaller: \( d_{\text{model}} \times (g \times d_{\text{head}}) \) instead of \( d_{\text{model}} \times d_{\text{model}} \). For g = h it is MHA; for g = 1 it is MQA.
Savings in numbers are straight. The cache shrinks by \( h/g \). The compute for QKᵀ stays the same, because there are still h query heads, so GQA is a memory optimization, not a FLOP optimization. During prefill, which is compute-bound, GQA matters little; it helps most in decode and in memory capacity. The projection weights shrink too. In Llama 2 70B, K and V projections drop from 2 × 8192 × 8192 ≈ 134M to 2 × 8192 × 1024 ≈ 17M parameters per layer, a saving of about 117M per layer, 9.4 billion across 80 layers, which designers can spend elsewhere.
Training a GQA model from scratch needs nothing special. Converting an MHA model needs uptraining: for each group, take the mean of the group's K projection matrices (and the V matrices), put the result in as the single shared head, and continue training for a small fraction of the original steps. A model cannot simply be run with merged heads without training, since the heads learned different things.
A practical issue is tensor parallelism, which shards attention heads across GPUs. With 8 KV heads and 8 GPUs, each GPU holds exactly one KV head and its group of queries. With 16 GPUs, KV heads must be replicated, and part of the saving is lost. This is one reason why g = 8 is such a common choice.

example: Take Llama 2 70B: 80 layers, 64 query heads, d_head = 128, 8 KV heads, 16-bit numbers (2 bytes).
Cache per token with GQA: 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes = 320 KB. If the same model used MHA (64 KV heads): 2 × 80 × 64 × 128 × 2 = 2,621,440 bytes, about 2.5 MB. The ratio is 8, as expected. For a context of 4,096 tokens, one sequence needs 4,096 × 320 KB ≈ 1.34 GB with GQA, and about 10.7 GB with MHA.
How many users fit? Use a server with 8 H100 GPUs: 8 × 80 = 640 GB. The weights in 16-bit are about 140 GB. Keep 10% for activations and overhead, leaving roughly 640 × 0.9 − 140 ≈ 436 GB for cache. With MHA, 436 / 10.7 ≈ 40 sequences at 4K context. With GQA, 436 / 1.34 ≈ 325 sequences. That is 8 times more concurrent users on the same hardware, or 8 times longer context for the same users.
Speed. The 8 GPUs have an aggregate memory bandwidth of about 8 × 3.35 = 26.8 TB/s. Reading the weights once per decode step takes 140 GB / 26.8 TB/s ≈ 5.2 ms. Take a batch of 32 sequences at 4K context. The KV reads are 32 × 1.34 GB ≈ 43 GB with GQA, so 43 / 26,800 ≈ 1.6 ms. With MHA they would be 32 × 10.7 ≈ 343 GB, which is 12.8 ms. A decode step then costs roughly 5.2 + 1.6 ≈ 6.8 ms with GQA, but about 5.2 + 12.8 = 18 ms with MHA, and the cache read dominates. These are simple lower bounds that ignore overlap and overheads, but the ratio is realistic: GQA makes decode about 2.6 times faster here, and the gain grows with context length.
Longer contexts. Llama 3 8B has 32 layers, 8 KV heads and d_head = 128, so 2 × 32 × 8 × 128 × 2 = 131,072 bytes = 128 KB per token. At 128K tokens, one sequence needs about 17 GB of cache, more than the 16 GB of the model weights themselves. With MHA (32 KV heads) it would be 69 GB. For Llama 3.1 405B (126 layers, 8 KV heads) the cache is about 516 KB per token, or 68 GB for one 128K sequence. DeepSeek-V3's MLA stores 576 numbers per layer per token: 576 × 61 layers × 2 bytes ≈ 70 KB per token, so a 128K sequence needs about 9.2 GB.
Last, how uptraining works on a small case: an MHA layer with 4 heads has key matrices K0, K1, K2, K3. To go to 2 groups, set the new shared key matrices to (K0 + K1) / 2 and (K2 + K3) / 2, do the same for the value matrices, and train a little. The averaged heads start out as a rough compromise that training then repairs.

The design is natural once you see where the cost sits. The "question" side (queries) is computed fresh for the one new token and thrown away, so it costs nothing to store. The "index" side (keys and values) is created once per token and kept for the whole conversation, so it is what fills memory and what must be read again at every step. Different heads need different questions to find different relations, but they do not need entirely different indexes: much of the content of the keys and values is similar between heads. Sharing the stored part and keeping the asking part separate saves the expensive thing and keeps the useful thing.
mistakes: People often think GQA reduces the amount of computation. In fact the number of query heads, and so the work for QKᵀ and attention scores, is unchanged. What shrinks is the cache, and with it the memory traffic and capacity. That is why it helps decode speed and batch size much more than prefill.
People often think GQA has fewer attention heads. In fact it has the same number of query heads as MHA, and each head still forms its own attention pattern. Only the keys and values are shared inside a group.
People often think you can turn any MHA model into a GQA model at inference time by merging heads. In fact heads learned different roles; merging them without training damages the model. The conversion needs uptraining (about 5% of the original compute in the GQA paper), or training with GQA from the start.
People often think the KV cache matters in training. In fact training processes whole sequences at once in parallel and does not keep a growing cache; the benefit is at inference, when tokens are generated one by one. It is a design choice made at training time for the sake of serving.
People often think MQA is simply better than GQA because it saves most. In fact MQA saves the most memory but loses more quality and sometimes trains less stably, while GQA with 8 groups keeps nearly all MHA quality at one eighth the cache. The best choice depends on how much quality you can give up for serving cost.
tradeoffs: Choose GQA with a moderate number of groups (4 to 8 KV heads) for a general-purpose model that will be served at scale. You get most of the cache saving (h/g, usually 4 to 8 times) with a quality loss that is small enough to be hard to measure in many benchmarks. Choose full MHA only for small models or research settings where serving cost is not the issue, or when you need the last bit of quality; you pay up to 8 times more cache.
Choose MQA (one KV head) when serving cost is the dominant limit, for example a very long-context or very high-throughput service, and you can accept a measurable loss in quality and some training sensitivity. It saves the most cache but has the least capacity for different heads to look at different content.
Choose MLA (latent attention) when you want a cache smaller even than GQA and are willing to take on more complex code: it needs a decoupled rotary key, matrix absorption at inference, and custom kernels. DeepSeek reports quality at least as good as MHA with a cache of about 70 KB per token for a 671B model, but fewer inference engines support it well, and it adds compute in some paths.
Choose KV-cache quantization (8-bit or 4-bit) on top of GQA when the cache is still the limit and the task tolerates small numeric error: it gives another 2 to 4 times saving with little work, but can hurt long-context accuracy, so test it. Choose sliding-window attention for layers where only recent tokens matter; it bounds the cache per layer but loses distant information in those layers.
Choose the number of KV heads to match your parallelism plan: if you will use tensor parallelism of 8, then 8 KV heads divide cleanly; if you need 16-way, then you either replicate KV heads (lose the saving) or use other parallel schemes. Choose uptraining of an existing model when you cannot afford to train from scratch, accepting a short retraining run and a small quality gap.
friction: GQA reduces the cache but does not remove its linear growth with context. A 1 million token context still needs tens to hundreds of GB per sequence, even with 8 KV heads, so long-context serving needs more: quantization, offloading to CPU memory, sliding windows, or compressed caches.
There is a quality cost. MQA shows a clear drop on some tasks, and even GQA is slightly below MHA for the same parameters, although the saved parameters can be spent elsewhere (as Llama 2 did with a wider feed-forward layer). Heads in a group must share one set of keys and values, which limits how different their attention patterns can be, and very small models lose more.
Systems details complicate the gains. Tensor parallelism beyond the number of KV heads replicates the cache. Kernel support is needed so that group members share loads instead of copying. Paged cache managers must handle the different shapes. In prefill, which is compute-bound, GQA brings little benefit, and for short contexts and small batches the weights, not the cache, dominate the traffic.
Finally, the field is moving. MLA, cross-layer cache sharing, linear-attention and state-space hybrids, and compressed memory all try to make the cache smaller or constant-size. It is not settled which wins at which scale, and the best choice depends on hardware generation (HBM bandwidth and capacity change every two years).
practice: When you choose or train a model for serving, compute the cache per token from its configuration: 2 × layers × KV heads × head size × bytes. Read these numbers from the model's config file (num_key_value_heads, num_attention_heads, head_dim). Multiply by context length and the number of concurrent sequences, and compare with free GPU memory after the weights. This single calculation predicts your batch size limit.
For new models, use GQA with 8 KV heads as a default, keep head dimension at 128, and check that the KV head count divides your tensor-parallel degree. Spend saved parameters on the feed-forward layers if you want to keep the model size constant. For existing MHA models, uptrain with about 5% of the original token budget, mean-pooling the heads in each group.
For serving, use an engine with paged KV cache and fused attention kernels that understand GQA (vLLM, TensorRT-LLM, SGLang, FlashAttention-based kernels). Consider FP8 or INT8 cache quantization if memory is the limit, and measure accuracy on long-context tests. Enable prefix caching when many requests share a long system prompt: the cache for the common prefix is computed once and reused.
Watch the right metrics: GPU memory used by cache, tokens per second per GPU at your target latency, and the maximum batch size before preemption. If decode speed is lower than expected, check whether attention kernels are bandwidth-bound and whether KV heads are replicated by your parallel setup. To understand the idea, read the config files of Llama 3 8B, Llama 3 70B and DeepSeek-V3 and compute the cache per token for each; the numbers explain much of how these models are served.

value: Attention by itself has no sense of order. If you shuffle the tokens of a sentence, the attention scores between any two tokens stay the same, because a score depends only on the content of the query and the key. Yet "dog bites man" and "man bites dog" are different. A transformer therefore needs a way to inject position. Rotary position embedding (RoPE) does it in an unusual way: it does not add a position vector to the input. Instead, inside every attention layer, it rotates each query vector and each key vector by an angle that depends on the token's position. The result is that the score between a query at position m and a key at position n depends on the content of both and on the distance m − n, and not on m and n separately.
That is the property language needs. The meaning of "the word two places back" does not depend on whether we are at token 50 or token 5,000. RoPE gives attention relative positions with no extra parameters, no change to the cost of attention, and a simple formula that is easy to modify. It is used by nearly all current open language models (Llama, Mistral, Qwen, Gemma, DeepSeek and others), and because its angles come from a short list of frequencies, it is the base of the methods that stretch a model trained on 4K or 8K tokens to 128K or more (position interpolation, NTK-aware scaling, YaRN).
For the layer above, RoPE is the part of the transformer (transformers and LLMs, L1) that tells attention how far apart tokens are, and it largely decides how long a context the model can handle. Two layers below explain it. Linear algebra (L4) provides the rotation: each pair of coordinates is multiplied by a 2 × 2 rotation matrix, which keeps vector length unchanged and has the key rule \( R(a)^{\top} R(b) = R(b - a) \), which turns two absolute positions into one relative offset. Fourier analysis (L4) provides the choice of angles: the pairs rotate at different frequencies, from fast to very slow, in a geometric sequence, like the basis of sinusoids in a Fourier series, so that the model can read both fine and coarse distance.
terms: Token position — the index m of a token in the sequence (0, 1, 2, …).
Absolute and relative position — absolute is "this is token 57"; relative is "this token is 3 places before that one".
Rotation matrix — a 2 × 2 matrix R(φ) that turns a 2D vector by angle φ without changing its length.
Frequency \( \theta_i \) — the rotation angle per token for dimension pair i; fast pairs have large θ and slow pairs have small θ.
Base — the constant (10,000 in the original design) that sets how quickly the frequencies fall across the pairs: \( \theta_i = \text{base}^{-2i/d} \).
Head dimension d — the size of the query and key vectors in one attention head, often 128; it gives d/2 rotating pairs.
Context extension — making a model that was trained on length L work well on a longer length L′, by changing the rotation frequencies and doing a little extra training.
Wavelength — \( 2\pi / \theta_i \), the number of tokens after which a pair makes one full turn.
history: The original transformer (Vaswani et al., 2017) added a fixed sinusoidal vector to each token embedding at the input, with many frequencies chosen so that each position has a unique pattern. BERT and GPT-2 used learned absolute position vectors instead, which cannot handle positions beyond the training length at all. Relative position ideas followed: Shaw et al. (2018) added learned relative-distance vectors to attention, Transformer-XL (Dai et al., 2019) reworked the formula so that only relative distance enters, and T5 (2019–2020) added a learned bias to the attention score, depending on distance buckets. These worked but made attention slower or more complex.
Jianlin Su and colleagues proposed RoFormer with rotary embedding in 2021. The idea: find a transformation of queries and keys such that the dot product depends only on relative position, using nothing more than complex-number multiplication. It cost almost nothing, so it spread quickly: GPT-J and GPT-NeoX adopted it in 2021–2022, PaLM (2022) and Llama (February 2023) made it the standard. ALiBi (Press, Smith and Lewis, 2021) took another route, adding a linear distance penalty to scores, and was used in a few models such as BLOOM and MPT, but RoPE became dominant.
Context extension became the main story in 2023. A model trained with RoPE on 2,048 or 4,096 tokens fails when run on much longer text, because it sees rotation angles it never saw in training. Chen, Wong, Chen and Tian at Meta (June 2023) proposed position interpolation: shrink the positions by the ratio L/L′ so that all angles stay inside the trained range, then fine-tune briefly. An anonymous user "bloc97" proposed NTK-aware scaling the same month, which changes the base instead of the positions, so high-frequency pairs are kept intact. Peng, Quesnelle, Fan and Shippole's YaRN (September 2023, ICLR 2024) combined per-frequency treatment with an attention temperature factor and needed far less fine-tuning. Code Llama used a base of 1,000,000 to reach 100K tokens. Llama 3 (2024) used a base of 500,000 from the start, and Llama 3.1 added frequency scaling to reach 128K tokens. Later work, such as LongRoPE and "Base of RoPE bounds context length", studies how the base relates to the achievable length.
how: Take a query or key vector of dimension d in one head. Group its coordinates into d/2 pairs: (x₀, x₁), (x₂, x₃), and so on. Treat each pair as a point in a plane (or a complex number x₀ + i x₁). For a token at position m, rotate pair i by the angle \( m \times \theta_i \), where \( \theta_i = \text{base}^{-2i/d} \) with base = 10,000 in the original design. The rotation is the usual one: \( x_0' = x_0 \cos(m\theta) - x_1 \sin(m\theta) \), and \( x_1' = x_0 \sin(m\theta) + x_1 \cos(m\theta) \). That is all. The rotated query is q_m, the rotated key is k_n, and attention uses their dot product as usual. Values are not rotated.
Why does this give relative position? Linear algebra (L4) answers it. The rotation of the whole vector is a block-diagonal matrix \( R_m \) made of d/2 small 2 × 2 rotations. Rotation matrices are orthogonal, and rotating by a and then reversing b is the same as rotating by a − b. So the dot product of the rotated vectors is
\[ (R_m q)^{\top} (R_n k) = q^{\top} R_m^{\top} R_n k = q^{\top} R_{n-m} k \]
The two absolute positions have disappeared; only the offset n − m is left. In complex form, each pair contributes \( \mathrm{Re}\!\left[ q_i \cdot \overline{k_i} \cdot e^{i(m-n)\theta_i} \right] \), a sum of cosines in the distance times a content-dependent amplitude and phase. The attention score is therefore a function of the content of q and k and of the distance, with no absolute position.
The frequencies matter, and here the Fourier view (L4) applies. Pair 0 rotates fastest, θ₀ = 1 radian per token, so its wavelength is about 6.3 tokens: it separates neighbouring tokens. Later pairs rotate more slowly. With d = 128 and base 10,000, pair 16 has θ = 0.1 (wavelength about 63 tokens), pair 32 has θ = 0.01 (about 630 tokens), pair 48 has θ = 0.001 (about 6,300), and the last pair, 63, has θ ≈ 0.000115 (wavelength about 54,000 tokens). Together they work like the digits of a number in different bases or the hands of a clock: fast hands tell small differences exactly, slow hands tell large differences without wrapping around. A larger base (500,000 in Llama 3) stretches the slow end, so the slowest wavelength becomes about 2.6 million tokens.
Implementation is cheap. Cosine and sine tables of shape [max_length, d/2] are precomputed. For each layer, the code applies the rotation to Q and K right after the projections: a few element-wise multiplications on tensors that are already in memory, with no new weights. The rotated keys are what is stored in the KV cache, so past keys are never rotated again. During generation of token m, only the new query and key are rotated by angle mθ. There are two conventions for pairing coordinates: adjacent pairs (the original) and the first half with the second half (used by many libraries via a function called rotate_half). They are mathematically equivalent but the weights of one cannot be loaded into code written for the other without permuting dimensions, which is a common conversion bug.
Because the angles at long distance can fall outside what the model saw in training, extension methods change the angles. Position interpolation divides all positions by \( s = L'/L \), for example 4 to go from 8K to 32K, so no angle exceeds the trained range. Its weakness is that neighbouring tokens, which used to differ by 1 radian in the fastest pair, now differ by 0.25, so local detail becomes blurry. NTK-aware scaling increases the base instead (to about \( \text{base} \times s^{d/(d-2)} \), about 41,000 for s = 4 and d = 128), which leaves the fastest pairs almost unchanged and slows only the slow pairs. YaRN goes further: pairs whose wavelength is short compared with the training length are left alone, pairs whose wavelength is longer than the training length are interpolated fully, pairs in between are blended, and the attention logits are scaled by a small factor that grows with s, which restores sharpness. After this, a short fine-tune on long text finishes the job. Llama 3.1 uses a similar per-frequency scheme.
RoPE can be used on only part of the head. GPT-NeoX rotates just 25% of the dimensions and leaves the rest as pure content. DeepSeek's latent attention keeps a separate small rotated key (64 dimensions) next to the compressed content, because rotation does not commute with compression.

example: Start with the smallest case: a head of size 2, so one pair, and θ = 30° per token. Let the content vectors be q = (1, 0) and k = (1, 0). Put q at position m = 3 and k at position n = 1.
Rotate q by 3 × 30° = 90°: q₃ = (cos 90°, sin 90°) = (0, 1). Rotate k by 1 × 30° = 30°: k₁ = (cos 30°, sin 30°) = (0.866, 0.5). The dot product is 0 × 0.866 + 1 × 0.5 = 0.5. This equals cos(60°), where 60° = (3 − 1) × 30°.
Move both tokens: q at m = 10, k at n = 8. Rotate q by 300°: (cos 300°, sin 300°) = (0.5, −0.866). Rotate k by 240°: (cos 240°, sin 240°) = (−0.5, −0.866). Dot product: 0.5 × (−0.5) + (−0.866) × (−0.866) = −0.25 + 0.75 = 0.5. The same result, because the distance is still 2. At distance 0 the score is cos 0° = 1; at distance 1 it is cos 30° = 0.866; at distance 3 it is cos 90° = 0; at distance 6 it is cos 180° = −1. So the pair gives the content match, modulated by distance.
Now two pairs, d = 4, base 10,000. The frequencies are θ₀ = 10,000^0 = 1 radian and θ₁ = 10,000^(−2/4) = 0.01 radian. Tokens 1 apart: pair 0 turns by 1 rad (57°), pair 1 by 0.01 rad (0.6°). Tokens 100 apart: pair 0 turns by 100 rad, which is the same as 100 − 15 × 2π ≈ 5.75 rad (329°), so it has wrapped around many times and tells little; pair 1 turns by 1 rad (57°), a clear signal. So the fast pair tells near from far at short range, and the slow pair does it at long range. A real head with 64 pairs covers all the scales between.
Now context extension. A model is trained on 8,192 tokens with d = 128 and base 10,000, and we want 32,768 (s = 4). Without changes, at distance 20,000 the slowest pair has angle 20,000 × 0.000115 = 2.3 rad, but in training this pair only saw angles up to 8,192 × 0.000115 = 0.94 rad, so 2.3 rad is a value it has never seen. Middle pairs show the same problem. With position interpolation, positions are divided by 4, so a distance of 20,000 becomes 5,000 and every angle stays inside the trained range, but the fastest pair now moves 0.25 rad per token instead of 1, so the model sees neighbours as more alike than before. With NTK-aware scaling, the base becomes about 10,000 × 4^(128/126) ≈ 40,900: the fastest pair still moves 1 rad per token, and the slowest pair's wavelength grows from 54,000 to about 216,000 tokens. The model then needs only a small fine-tune to adjust.
Finally, cost. For a model with 32 layers, 32 query heads and 8 KV heads of size 128, a token needs RoPE on 32 + 8 = 40 head vectors per layer, each with 64 pairs and 4 multiplications per pair: 40 × 64 × 4 ≈ 10,000 multiplications per layer, about 330,000 per token over 32 layers. The model itself uses billions per token for matrix multiplications, so the rotation is below 0.01% of the compute.
intuition: Each token is a clock hand turned by its position; comparing two hands tells you how far apart they are, not where they are.
The idea is natural because of a fact about turning: if two arrows are both rotated by their own amount, the angle between them depends on the difference of their rotations, not on the rotations themselves. Attention is built from dot products, which measure the angle between vectors. So if the arrows carry the content and the rotation carries the position, the dot product automatically reports content and distance together. Using many clock hands at different speeds, as clocks do for seconds, minutes and hours, lets one head read distances from one token to tens of thousands of tokens. No learned table is needed, so the method works for any position, and the only question is whether the model trained on those angles.
mistakes: People often think RoPE adds a position vector to the token embedding. In fact it adds nothing; it rotates queries and keys inside attention at every layer. Values and the residual stream carry no positional vector.
People often think a RoPE model can handle any length, since the formula works for any position. In fact the formula works, but the model has only seen angles up to its training length. Beyond that, scores become unreliable and quality collapses. Extension methods and extra training are needed.
People often think RoPE means the model knows nothing about absolute position. In fact with a causal mask, a model can infer absolute position indirectly, for example from how many tokens it can attend to, and it often uses the first token as an anchor (an attention sink). RoPE makes the scores relative, but the model can still build absolute information in its hidden states.
People often think context extension is a free software switch. In fact changing frequencies needs some fine-tuning on long text, and aggressive scaling can reduce quality at short lengths. A longer window also does not guarantee that the model uses it well; retrieval from the middle of long input is often weaker.
People often think that rotation shrinks attention with distance like a decay. In fact rotation preserves vector length. Any "long-term decay" of scores comes from the interaction of many frequencies for typical content and is not guaranteed; the model can learn to attend to distant tokens strongly.
tradeoffs: Choose RoPE when you want relative positions with no extra parameters and no change in attention cost, and you will use standard tooling: it works with FlashAttention, KV caching and GQA, and context extension recipes are well studied. Choose ALiBi (a linear distance penalty) when you want simple extrapolation to somewhat longer inputs without extra training, accepting that it biases the model strongly toward recent tokens and has less support in current open models.
Choose learned absolute embeddings only for small, fixed-length models (a classifier on 512 tokens), where simplicity matters and you will never exceed the length. You give up any ability to go beyond the trained length and any relative structure.
Choose a larger base (500,000 or 1,000,000) when you plan long context from the start: it stretches the slow pairs so that the angle at 128K tokens is still in a sensible range, at the cost of coarser resolution at medium distances, which pre-training on enough long data compensates for. Choose a small base (10,000) for short-context models, where it gives finer resolution for local structure.
Choose position interpolation for a quick extension with a small fine-tune and when local detail is not critical; choose NTK-aware or YaRN when you want to keep short-context behaviour and need fewer fine-tuning steps; choose full long-context continued pre-training with a changed base when quality at the new length matters most and you can afford many billions of tokens.
Choose partial rotary (rotate only some dimensions) or a decoupled rotary key (MLA) when other design needs conflict with rotation, such as cache compression; you pay with extra dimensions and more complex code. Some recent models also interleave layers with RoPE and layers without any position encoding to improve length generalization; this trades some local precision for long-range behaviour.
friction: RoPE does not solve long context. Beyond the trained or fine-tuned length, quality degrades, and even within it, models often use the middle of a long input less well than its start and end ("lost in the middle"). Position encoding is only one cause; training data with real long-range dependencies matters at least as much.
The high-frequency pairs wrap around quickly, so for large distances only the slow pairs carry reliable information, and the effective resolution of distance is coarse for far tokens. This is probably acceptable for language, where exact far positions rarely matter, but it limits tasks that need exact indexing in long inputs, such as copying the 50,000th token.
Numerical precision is a practical issue. Angles m × θ for large m must be computed in float32 (not in half precision), or cos and sin tables will be wrong at high positions. Differences between libraries in pairing convention, base, scaling formulas and rounding cause silent quality loss when a model is converted between frameworks.
The frequency schedule is a fixed design choice (the geometric sequence), not learned. Research has questioned whether it is optimal and whether the rotation interacts badly with quantization or with outlier dimensions in the keys. Finally, RoPE couples position to the key vectors in the KV cache, which makes some cache-compression and cache-reuse schemes harder: you cannot move a cached chunk to a different position without re-rotating it.
practice: Use the settings the model was trained with: base, head dimension, rotation convention and any scaling are part of the model definition. When you load or convert weights, check rope_theta (the base), rope_scaling and the pairing convention in the config, and test that perplexity or logits match a reference implementation on a few hundred tokens.
To extend context for an open model, prefer a documented recipe (YaRN or the model's own scaling configuration) and then fine-tune on long documents, even briefly (hundreds of millions of tokens or fewer). Evaluate at several lengths, including the short lengths you care about, and with tasks that need long-range retrieval (needle-in-a-haystack is only a start, so also test multi-document questions and summarisation). Compare perplexity on long text at 2K, 8K, 32K and beyond to see where it breaks.
Keep trig tables in float32, compute them once, and use fused kernels where available (FlashAttention and inference engines apply RoPE inside the kernel). Remember that cached keys are already rotated, so prompt caching reuses a prefix only when the positions are the same.
To understand it by hand, implement the rotation in 15 lines of NumPy, check numerically that the dot product between rotated vectors depends only on the offset, and plot cos(Δ θ_i) for several i. Then try a trained small model with different bases and see where perplexity rises with length.

interview: Explain RoPE to a colleague and why it is better than adding sinusoidal embeddings to the input. || RoPE rotates pairs of coordinates of Q and K by position-dependent angles, so the score depends on content and relative offset. Input-added sinusoids mix position into the content early, and attention must extract relative distance from it; RoPE builds relative distance into the score at every layer with no parameters and no extra cost, and works with KV caching.
Why does a RoPE model fail beyond its training length, and how do you fix it? || The model has seen only a range of angles per frequency pair; at longer distances the slow pairs have angles that are out of distribution and attention scores become unreliable. Fixes: interpolate positions, change the base (NTK-aware), or per-frequency schemes such as YaRN, plus fine-tuning on long text. Better still, train with a large base on long data from the start.
What is the relation between the base and the maximum useful context? || The slowest pair has wavelength about \( 2\pi \times \text{base}^{(d-2)/d} \), roughly \( 2\pi \times \text{base} \). To distinguish positions at distance L without wrapping, you need slow pairs with wavelength well above L. Larger base gives longer wavelengths, which is why long-context models use bases of 500K to 1M, at the cost of coarser medium-distance resolution.
How does RoPE interact with the KV cache and with GQA or MLA? || Keys are stored after rotation, so each cached key already encodes its position, and only the new query and key are rotated. GQA is unaffected because each KV head is rotated the same way. MLA compresses keys into a latent, and rotation does not commute with the compression, so it keeps a separate small rotated key (decoupled RoPE).
You convert a model between two frameworks and the outputs are garbage. Compare logits for the first tokens with a reference.

But with a causal mask, the model can infer absolute position (for example by counting visible tokens or using the first token as an anchor), and learned features in the hidden state can carry it. @@ embeddings
value: An embedding is a list of numbers (a vector) that represents an item such as a word, a sentence, a product, a user, an image or a document, learned so that items with similar meaning or behaviour get nearby vectors. Computers cannot compare the meaning of "cheap flights" and "low-cost airfare" by looking at their letters: the strings share almost no characters. If a model maps both to vectors, the two vectors point in almost the same direction, and a single dot product says they are similar. Meaning becomes geometry, and geometry is something that mathematics and hardware handle very well.
This is the interface between messy real-world objects and neural networks, and it is everywhere in the systems above it. A language model turns every token into an embedding as its first step, and every hidden state it computes later is a vector of the same kind (transformers and LLMs, L1). Retrieval-augmented generation embeds the question and the passages, then returns the passages whose vectors are closest (RAG, L1; vector search, L1). Recommender systems learn a vector per user and per item and predict interest as a dot product (L1). Natural language processing, multimodal models (which place text and images in one space) and ad targeting use the same idea.
Three lower layers make it work. Linear algebra (L4) says that an embedding table is just a matrix whose rows are the vectors, and lookup is selecting a row. Geometry and metric spaces (L4) supply the idea that similarity is a distance or an angle (dot product, cosine, Euclidean) in that space. Distributional semantics (L5), the linguistic idea that a word's meaning is given by the contexts in which it appears, tells us what to train on: no one writes the vectors by hand; they are adjusted until words that appear in similar contexts have similar vectors. And PCA and dimensionality reduction (L2) are the ancestor: the first successful word vectors came from a truncated SVD of word co-occurrence counts, and modern models can be seen as learning the same kind of low-rank structure by gradient descent.
terms: Vector (embedding) — a fixed-length list of real numbers, typically 128 to 4,096 of them, that represents one item.
Embedding table — a matrix of size V × d (V items, d dimensions) whose row i is the vector of item i; lookup returns that row.
Cosine similarity — the cosine of the angle between two vectors, from −1 to 1; it ignores length and compares direction only.
Dot product — the sum of the products of matching coordinates; for vectors of length 1 it equals cosine similarity.
Distributional hypothesis — the idea that words that occur in similar contexts have similar meanings.
Contrastive learning — training that pulls the vectors of related pairs together and pushes unrelated pairs apart.
Negative sampling — using a few randomly chosen unrelated items as the "push apart" examples, instead of all items.
Contextual embedding — a vector for a word that depends on the sentence around it, such as a hidden state of a transformer; the word "bank" gets different vectors in "river bank" and "bank loan".
history: The idea starts in linguistics. Zellig Harris (1954) argued that words with similar distribution have similar meaning, and J. R. Firth (1957) wrote the famous line "You shall know a word by the company it keeps". The first computational version was Latent Semantic Analysis (Deerwester, Dumais, Landauer and others, 1990): build a term-by-document count matrix, compute a truncated singular value decomposition, and use the top 100–300 dimensions as word and document vectors.
Neural embeddings came next. Bengio, Ducharme, Vincent and Jauvin (2003) trained a neural language model whose first layer was a learned table of word vectors, so the vectors were by-products of predicting the next word. The method became cheap and famous with word2vec (Mikolov et al., 2013), which used a very simple shallow model (skip-gram or CBOW) with negative sampling, trained on billions of words in a day or less. It showed linear patterns such as \( \text{vector}(\text{king}) - \text{vector}(\text{man}) + \text{vector}(\text{woman}) \approx \text{vector}(\text{queen}) \). GloVe (Pennington, Socher and Manning, 2014) fitted vectors to global co-occurrence counts. Levy and Goldberg (2014) showed that skip-gram with negative sampling is implicitly factorizing a shifted pointwise mutual information matrix, which connected the neural method back to SVD-style methods. fastText (2016) added subword pieces so rare words and misspellings get sensible vectors.
Then vectors became contextual: ELMo (2018) and BERT (2018) produced a different vector for the same word in each sentence. Sentence-BERT (Reimers and Gurevych, 2019) trained BERT with a siamese setup so that whole sentences have good vectors for similarity search. Contrastive training at scale (SimCSE 2021, E5, BGE and OpenAI/Cohere embedding models) and dense passage retrieval (Karpukhin et al., 2020) made text embeddings the standard base of search and RAG. CLIP (Radford et al., 2021) placed images and text in the same space. Matryoshka representation learning (Kusupati et al., 2022) trained vectors whose first k dimensions are useful on their own, allowing cheap truncation. In recommendation, matrix factorization became famous through the Netflix Prize (2006–2009), and two-tower neural models (YouTube, 2016, and many others) became the standard for large-scale retrieval.
how: The simplest embedding is a table. Give each item an integer ID from 0 to V − 1 and keep a matrix E of size V × d, filled with small random numbers at the start. The embedding of item i is row i. This is the same as multiplying a one-hot vector by E, which is why linear algebra (L4) is the right description. The table is a set of parameters trained by gradient descent like any other weights. The question is what objective moves the rows into useful places.
The classic objective is word2vec's skip-gram with negative sampling. Take a window of text. For a center word c and a nearby word o (a real neighbour), the model has two vectors per word, v for center use and u for context use. It computes the score \( u_o \cdot v_c \), passes it through the sigmoid σ, and increases \( \sigma(u_o \cdot v_c) \) for real pairs. It also draws k (5 to 20) random words as negatives and decreases \( \sigma(u_n \cdot v_c) \) for them. The gradient moves v_c toward the vectors of words it appears with and away from random words. After many passes over a large corpus, words that share contexts have nearly the same context statistics, so they receive nearly the same updates and end up close together. This is the distributional hypothesis (L5) turned into an algorithm. The result is related to SVD of a PMI matrix (the PCA layer): both find a low-dimensional space that preserves who co-occurs with whom.
Modern text embedding models use contrastive learning on pairs. Take a transformer encoder, run a sentence through it, and average the token outputs (mean pooling) into one vector, then normalize it to length 1. Train on pairs that should be close, such as a question and its answer passage, a title and its article, two paraphrases. In a batch of B pairs, each query's own partner is the positive, and the other B − 1 passages are negatives. The loss (InfoNCE) is −log of exp(sim(q, p⁺)/τ) divided by the sum of exp(sim(q, p)/τ) over all passages in the batch, where sim is cosine similarity and τ is a temperature around 0.02–0.1. Larger batches provide more negatives and usually better vectors. Hard negatives, passages that look relevant but are not, improve the model further.
Similarity is geometry (metric spaces, L4). Cosine similarity compares directions. If vectors are normalized to unit length, cosine equals the dot product and the Euclidean distance is a monotone function of it, since \( |a - b|^2 = 2 - 2\, a \cdot b \). So the nearest neighbour by cosine, by dot product and by Euclidean distance are the same. In search, we compute the similarity of the query vector to all stored vectors and return the top results. Brute force for 1 million vectors of 768 dimensions is 0.77 billion multiply-adds per query, which a GPU does in about a millisecond. For hundreds of millions of vectors, approximate nearest-neighbour indexes such as HNSW are used (vector search, L1).
In a language model the table is trained end to end. The embedding rows start random and receive gradients from the next-token loss, so the model decides what each token's vector must carry. The same matrix is often reused, transposed, to turn the final hidden state into scores over the vocabulary (weight tying). After the first layer, the vector for a token is no longer a fixed row: each layer adds to it using attention to the other tokens, so the hidden states are contextual embeddings. The first layer's table is the static part, and everything above it builds context.
In recommendation, two embedding tables are learned: one for users, one for items. The predicted interest is the dot product \( u_{\text{user}} \cdot v_{\text{item}} \), and training pushes observed interactions to score higher than random items. A two-tower model computes the user vector and the item vector with separate networks from their features; item vectors can be precomputed and indexed, so serving one user is one network call and one nearest-neighbour search.

example: First, similarity by hand. Let three words have 3-dimensional vectors: cat = (0.8, 0.1, 0.3), dog = (0.7, 0.2, 0.35), car = (0.05, 0.9, 0.1). The dot products: cat·dog = 0.56 + 0.02 + 0.105 = 0.685, and cat·car = 0.04 + 0.09 + 0.03 = 0.16. The lengths: |cat| = √0.74 ≈ 0.860, |dog| = √0.6525 ≈ 0.808, |car| = √0.8225 ≈ 0.907. Cosine(cat, dog) = 0.685 / (0.860 × 0.808) ≈ 0.986. Cosine(cat, car) = 0.16 / (0.860 × 0.907) ≈ 0.205. The model says cat and dog are nearly the same kind of thing and car is different. These made-up numbers have the shape that real embeddings show, with many more dimensions.
Second, one skip-gram training step. Let the center word have v = (0.1, 0.2) and a real context word have u = (0.3, −0.1). The score is 0.1 × 0.3 + 0.2 × (−0.1) = 0.01, and σ(0.01) ≈ 0.5025. The "pull" gradient on v is (1 − 0.5025) × u = (0.149, −0.050). A random negative word has u′ = (0.4, 0.5): its score is 0.14, σ(0.14) ≈ 0.535, and the "push" gradient on v is −0.535 × u′ = (−0.214, −0.267). With learning rate 0.5 and updating only v for simplicity: v_new = (0.1, 0.2) + 0.5 × (0.149 − 0.214, −0.050 − 0.267) = (0.068, 0.041). Now the score with the real context word is 0.016 (up from 0.010) and the score with the negative is 0.048 (down from 0.140). Repeated billions of times, this turns co-occurrence into geometry.
Third, memory and cost. A model with a vocabulary of 128,256 and d = 4,096 (Llama 3 8B) has an input table of 128,256 × 4,096 ≈ 525 million parameters, about 1.05 GB in 16-bit. A search index of 1 million documents with 768-dimensional float32 vectors is 1,000,000 × 768 × 4 bytes ≈ 3.1 GB. With 8-bit quantization it is 0.77 GB; with 1 bit per dimension it is 96 MB, 32 times smaller, with some loss of recall. A recommender with 50 million users and 64 dimensions in float32 needs 50,000,000 × 64 × 4 = 12.8 GB, which is why huge embedding tables are often sharded across machines or kept in CPU memory.
Fourth, the price of a model change. You have 200 million passages embedded with a model that produces 768-dimensional vectors. A new model gives better results, but its vectors live in a different space, so none of the old ones can be compared with new queries. You must re-embed all 200 million passages. At 2,000 passages per second per GPU, that is 100,000 seconds of GPU time, about 28 GPU-hours, plus the cost of rebuilding the index. This is why teams store the model name with each vector and re-embed in the background.
intuition: Place every item on a map where distance means "how different", and meaning becomes geometry.
The idea is natural because comparison is the basic need of reasoning and retrieval, and numbers are the only thing we can compare cheaply. A discrete symbol such as the word "dog" has no built-in relation to the word "puppy"; as separate IDs they are as far apart as "dog" and "tax". A vector gives each item coordinates, and the training process arranges the coordinates so that the things that behave alike are neighbours. The map has many dimensions because meaning has many aspects, such as topic, tone, tense and entity type, and each dimension can carry a mixture of them. Once the map exists, every other operation, such as search, classification, clustering and generation, can use the same simple tools of distance and direction.
mistakes: People often think each dimension of an embedding has a meaning, like "animal-ness" or "royalty". In fact the dimensions are not individually interpretable. Meaning is spread over many dimensions, and the space can be rotated without changing any distances. Only directions and distances carry information.
People often think vectors from different models can be compared or mixed. In fact each model learns its own space. A vector from model A means nothing in model B's space, even if both have 768 dimensions. Use the same model (and version) for queries and documents, and store the model name with the vectors.
People often think embedding similarity means "same meaning" or "answers the question". In fact it means "appears in similar contexts" or "was trained to be close". Text that mentions the opposite ("the flight was cancelled" and "the flight was not cancelled") often has very high similarity; numbers, negation and exact identifiers are weak spots. A question and its answer can also be far apart unless the model was trained for retrieval.
People often think the king − man + woman = queen example shows that embeddings capture reasoning. In fact it works in selected, cleaned examples and fails often when tested widely; the nearest neighbour is frequently one of the input words. It is a useful demonstration of linear structure, not a general rule.
People often think higher dimension always gives better quality. In fact quality gains flatten quickly (for many text tasks, 384 to 1,024 dimensions are close to 3,072), while storage, memory bandwidth and search time grow linearly. Training quality and data matter more than size.
tradeoffs: Choose a static embedding (word2vec, a lookup table) when you have a closed vocabulary of items, such as product IDs or user IDs, and you need fast, cheap, compact vectors; choose a contextual or sentence model when meaning depends on surrounding text. Static vectors cost one table lookup, contextual vectors cost a full model run (milliseconds on a GPU), but handle ambiguity and unseen text.
Choose a small embedding dimension (128 to 384) when the index is huge (hundreds of millions of items) or latency and memory are tight; choose 768 to 1,536 when quality on hard queries matters more. Matryoshka-trained models let you decide later by truncating, trading a few points of recall for a 2 to 8 times smaller index. Choose int8 or binary quantization with re-scoring on the top results when memory dominates: you keep most of the recall for a 4 to 32 times smaller index.
Choose dense retrieval alone when queries are natural language and the vocabulary differs between queries and documents; choose keyword retrieval (BM25) when queries contain exact identifiers, error codes or rare terms; choose hybrid (both, merged) for most production search, because each fails where the other works, at the cost of running two systems.
Choose a general-purpose pretrained model when you lack labelled pairs; choose fine-tuning on your own query-document pairs when the domain is specialised (legal, medical, ad products) and you have thousands of good pairs, since this can lift retrieval quality substantially. The cost is training, evaluation and a re-embedding of the corpus each time the model changes.
Choose normalized vectors with cosine/dot product for similarity of content; choose raw dot product when the vector length carries signal, as in recommenders where a large norm can encode item popularity or confidence. Choose a hosted embedding API for speed of development and a self-hosted open model when volume is high, data is sensitive, or you want control over versions; a hosted model can be changed or retired by the provider, which forces re-embedding.
friction: Embeddings carry whatever the training data contained, including social bias. Word vectors trained on news associate occupations with gender; sentence models can rank text by dialect or topic in unfair ways. Because the dimensions are not interpretable, such behaviour is hard to find and hard to remove.
Versioning is the main operational pain. A new model means a new space, and an index built with the old model is useless for new queries, so a change costs a full re-embedding and index rebuild, and there is a period where both versions must be served. Models also drift in meaning when data changes (new products, new slang).
Quality has limits that are easy to forget. A single vector for a long document averages many topics; models have input limits (often 512 to 8,192 tokens), so long texts must be cut into chunks, and chunking decisions change results a lot. Similarity in high dimensions suffers from hubness: a few vectors are close to everything and appear in too many results. Exact matches for rare terms, numbers and names are weak. Evaluating quality needs labelled queries; public benchmarks (such as MTEB) are a guide but often do not match your domain.
Privacy: embeddings are not a safe anonymization. Research (Morris et al., 2023) showed that text can be reconstructed with high accuracy from its embedding, so vectors of sensitive text must be protected like the text. Finally, huge embedding tables dominate memory in recommenders and need sharding, which makes training and serving more complex.
practice: Pick a model by testing on your own data. Build a small evaluation set of 100 to 500 real queries with known relevant documents, compute recall@k and MRR for two or three candidate models, and choose by those numbers, using public leaderboards only to shortlist. Check the maximum input length, the dimension, the license, the cost per million tokens or the GPU throughput, and whether the model needs special prefixes for queries versus documents.
Store the model name, version, dimension and normalization with every vector, and keep the raw text so you can re-embed. Use the same preprocessing and the same model for queries and documents. Normalize vectors to length 1 and use inner product in your index. Chunk long documents (for example 200 to 500 tokens with some overlap), keep titles with chunks, and test chunk sizes.
Combine dense search with keyword search and a re-ranker for the final ordering; this hybrid is more robust than any single method. Use an approximate index (HNSW or IVF-PQ) once the data passes a few million vectors, and tune recall against latency on your own queries. Use quantization to cut memory, and measure the recall loss.
For recommenders and ad systems, train two-tower models with in-batch negatives, correct for sampling bias (popular items appear too often as negatives), and refresh item vectors regularly. Plan the re-embedding path from day one: build the new index in the background, compare results, then switch traffic. To learn the idea, train word2vec on a small corpus with gensim, look at nearest neighbours for several words, and then compare with a pretrained sentence model on your own documents.
quiz: What is the cosine similarity of the vectors (1, 0) and (1, 1)? || The dot product is 1; the lengths are 1 and √2, so cosine = 1/√2 ≈ 0.707 (an angle of 45 degrees).
Why do words that appear in similar contexts end up with similar vectors in skip-gram training? || They receive nearly the same gradient updates: each is pulled toward the same context words and pushed away from the same random negatives. Similar update histories lead to nearby positions.
Why does the nearest neighbour by cosine equal the nearest neighbour by Euclidean distance when vectors have unit length? || For unit vectors, \( |a - b|^2 = |a|^2 + |b|^2 - 2\, a \cdot b = 2 - 2\, a \cdot b \). Distance decreases exactly when the dot product (cosine) increases, so the ranking is identical.
You have 20 million documents and 1,024-dimensional float32 embeddings. How much memory does the vector index need, and how much with int8 quantization? || 20,000,000 × 1,024 × 4 bytes ≈ 82 GB in float32. With int8 it is a quarter, about 20 GB, plus index overhead such as graph links for HNSW.
When would you choose hybrid search (dense plus BM25) instead of dense retrieval alone? || When queries include exact tokens such as product codes, names, error messages or rare terms, which dense vectors match poorly, and also natural-language queries where words differ from the documents. Hybrid covers both failure types, at the cost of operating two indexes and a merge step.
interview: Explain how you would build semantic search over 100 million documents. What are the main design decisions? || Chunk documents, embed with a retrieval-trained model, store normalized vectors with metadata in an ANN index (HNSW or IVF-PQ), shard by size. Sizing: 100M × 768 × 1 byte (int8) ≈ 77 GB plus graph overhead. Add BM25 for exact matches and a cross-encoder re-ranker on the top 50–100. Why can't you mix embeddings from two different models, and how do you migrate? || Each model defines its own coordinate system; there is no shared meaning of dimension 17. Migration: embed the corpus with the new model into a new index in the background, run both for comparison (shadow traffic), switch queries to the new model once recall is better, then delete the old index. Store model version with each vector.
How does contrastive training with in-batch negatives work and what does batch size change? || For each query in a batch, its paired passage is the positive and the other passages are negatives; the loss pushes the positive's similarity up relative to all others (softmax cross entropy over cosine/τ). A larger batch gives more negatives per query, which sharpens the learned space; hard negatives help further. Risks: false negatives (an unlabelled passage that is actually relevant) and popularity bias.
What is the relation between word2vec and matrix factorization? || Skip-gram with negative sampling implicitly factorizes a word-context matrix of shifted pointwise mutual information (Levy and Goldberg, 2014). So it finds a low-rank approximation of co-occurrence statistics, like SVD in LSA, but trained by stochastic gradient descent and weighting frequent pairs differently.
How do embeddings in an LLM differ from the sentence embeddings used for retrieval? || The input table maps token IDs to static vectors trained for next-token prediction; the hidden states are contextual and tuned for predicting what follows, not for similarity of whole texts. Retrieval models are trained with a contrastive loss so that one pooled vector represents a whole text. Using raw LLM hidden states for retrieval works poorly without such training.
Your search results favour long, generic documents and some items appear for every query. What is happening? || Possibly hubness or norm effects: some vectors sit near the centre of the distribution and have high similarity to many queries. @@ bpe
value: A language model cannot read raw text. It reads a sequence of integers, each one the ID of a token from a fixed vocabulary. The tokenizer is the program that turns text into those IDs and back. Byte-pair encoding (BPE) is the most common way to build the vocabulary and to split text: it learns a list of frequent pieces of text from a large corpus, so that common words become one token, rarer words become a few pieces, and anything at all, even a new name or a line of code in a language the model never saw, can be written as a sequence of known pieces.
The problem it solves is a dilemma. If the vocabulary is whole words, it must be huge (hundreds of thousands of entries for English alone, millions across languages), and every new word, typo or name is "unknown". If the vocabulary is single characters or bytes, nothing is unknown, but a sentence becomes 4 to 5 times longer, and attention cost grows with the square of length. BPE sits in between with a vocabulary of typically 32,000 to 256,000 tokens. In practice, English text takes about 1.3 tokens per word, or roughly 4 characters per token.
For the layer above, the tokenizer decides what the model sees (transformers and LLMs, L1; natural language processing, L1). It sets how many tokens a text costs, and therefore the price of an API call, the latency, and how much fits in the context window. It also explains many strange behaviours: why models are poor at counting letters in a word, why arithmetic on long numbers is uneven, and why some languages are more expensive. The layers below supply the machinery. Hash tables (L3) hold the pair counts and the token-to-ID map. Trees and tries (L3) support fast matching of vocabulary pieces. Greedy algorithms (L3) are the training rule: merge the most frequent pair, again and again. Information theory (L4) explains the idea: BPE began as a compression algorithm, and a good vocabulary is a code that gives short descriptions to frequent strings.
terms: Token — one entry of the vocabulary; a piece of text (a word, part of a word, a space plus a word, a byte) with an integer ID.
Vocabulary — the fixed list of all tokens, with size V (for example 128,256).
Merge rule — a learned instruction "join symbol A and symbol B into the new symbol AB"; the vocabulary is the base symbols plus all merges.
Merge rank — the order in which a merge was learned; earlier merges are more frequent and are applied first when encoding.
Pre-tokenization — a first split of the text into chunks (words, numbers, punctuation) by a regular expression, so that merges never cross chunk boundaries.
Byte-level BPE — BPE whose base symbols are the 256 byte values, so any text in any language or encoding can be represented, and no "unknown" token is needed.
Token fertility — the average number of tokens needed per word or per character in a language; high fertility means higher cost and less context.
Unigram language model tokenizer — an alternative method that starts with a large vocabulary and removes tokens that contribute least to the likelihood of the corpus.
history: Philip Gage described byte-pair encoding in 1994 in the C Users Journal as a simple data compression method: find the most frequent pair of adjacent bytes, replace it with a byte that does not occur in the data, record the substitution in a table, and repeat. It compressed reasonably well and decompressed very fast, but it was a minor technique next to Lempel-Ziv methods.
Rico Sennrich, Barry Haddow and Alexandra Birch (ACL 2016) used it for a different purpose. Neural machine translation systems had a fixed word vocabulary of 30,000–50,000 words and replaced everything else with an "unknown" symbol, which ruined the translation of names, compounds and rare words. They applied the BPE merging procedure to words (starting from characters, merging frequent pairs), so rare words are spelled with known pieces. This was the "subword units" idea and it quickly became standard. Wu et al. (Google, 2016) used a similar likelihood-based method called WordPiece, later used in BERT (vocabulary 30,522), and Kudo and Richardson (2018) released SentencePiece, which works on raw text without a word-splitting step and offers both BPE and the unigram model (Kudo, 2018).
GPT-2 (Radford et al., 2019) made BPE work at the byte level: the base alphabet is the 256 byte values, so any string can be encoded, and a regular expression splits text into pre-tokens (letters, digits, punctuation, spaces) so that merges do not join across categories. Its vocabulary has 50,257 entries: 256 bytes, 50,000 merges and one end-of-text token. Later vocabularies grew: Llama 2 used 32,000 tokens; GPT-4's cl100k_base has about 100,000; GPT-4o's o200k_base about 200,000; Llama 3 (2024) has 128,256, partly to cover more languages and code; Gemma has about 256,000. Meta reported that moving from 32,000 to 128,000 tokens cut the token count for English text by roughly 15%. Andrej Karpathy's minbpe code and video (2024) and OpenAI's tiktoken library made the algorithm easy to study. Research in 2024 and later tries to remove tokenizers by working directly on bytes with learned patching (for example the Byte Latent Transformer), but subword tokenizers remain standard in production models.
how: Training a BPE vocabulary has a simple loop. First, split the training text into pre-tokens with a regular expression (words with their leading space, digits in groups, punctuation). Count each distinct pre-token with its frequency, which turns a corpus of trillions of characters into a table of perhaps tens of millions of distinct words with counts. Represent each word as a list of base symbols: bytes for byte-level BPE, or characters. Then repeat until the vocabulary has the target size: count all adjacent pairs of symbols across all words, weighted by word frequency; pick the most frequent pair (A, B); add the new symbol AB to the vocabulary; record the merge with its rank; replace every occurrence of A B by AB in all words. This is a greedy algorithm (L3): at each step it makes the locally best choice, and it does not look ahead. It does not give the smallest possible encoding overall, but it is fast and works well.
The data structures matter for speed. The pair counts live in a hash table (L3) mapping each pair to its count. A naive implementation recounts all pairs after each merge, costing time proportional to the corpus for each of the 100,000 merges. Real implementations keep an index from each pair to the words that contain it, update only those words after a merge, and use a priority queue to find the best pair. After a merge of (A, B), only pairs touching A or B change, so the work per merge is proportional to the words affected, not to the whole data. The final vocabulary maps each token string to an integer ID in a hash table, and the list of merges with ranks gives the encoder its rules.
Encoding new text uses the same merges in the same order. Pre-tokenize the text with the same regular expression. For each pre-token, start from base symbols; find, among all adjacent pairs currently present, the one with the lowest merge rank (the earliest learned) and merge it; repeat until no pair in the word is a known merge. This is not "longest match first". A frequent merge learned early is applied before a rare, longer one. The result is deterministic and consistent with how the training corpus would have been split. Implementations speed this up with a cache of already-seen pre-tokens (most text is made of a few common words), a heap for choosing the lowest rank, and compiled code. Related tokenizers use tries (L3): WordPiece finds the longest vocabulary piece at each position by walking a trie, and the unigram model uses a trie plus dynamic programming (the Viterbi algorithm) to find the best segmentation among all those possible.
Decoding is trivial: look up each ID's byte string and concatenate. With byte-level BPE this always gives back valid bytes, though a single token can end in the middle of a multi-byte UTF-8 character, so streaming output must buffer incomplete characters.
Information theory (L4) explains what the vocabulary is doing. Each merge replaces a frequent pair by one symbol, so the sequence gets shorter, as in compression: frequent strings get short codes and rare strings long ones. But the code is not for minimising bits; the token IDs are inputs to a model. A vocabulary of size V costs V × d parameters in the input embedding and another V × d in the output layer, and the output softmax is computed over V entries at every position. A larger V shortens sequences (so attention and the number of steps fall) but adds parameters and leaves rare tokens with few training examples. Choosing V is a trade-off between these costs, and current practice is moving toward 100,000 to 256,000.
Special tokens complete the picture: markers such as end-of-text, the start and end of a chat turn, and tool-call delimiters are added to the vocabulary outside the learned merges, and the tokenizer must treat them as atomic. Chat formats depend on exact use of these tokens, and a mismatch between how a model was trained and how it is prompted can reduce quality.

example: Use the classic toy corpus from the 2016 paper: the word "low" appears 5 times, "lower" 2 times, "newest" 6 times and "widest" 3 times. Write each word as characters with an end-of-word marker </w>. For example "newest" is n e w e s t </w>.
Round 1: count adjacent pairs, weighted by frequency. The pair (e, s) occurs in newest (6) and widest (3), so its count is 9. The pairs (s, t) and (t, </w>) also have 9. Ties are broken arbitrarily; take (e, s) and merge it into "es". Now newest is n e w es t </w> and widest is w i d es t </w>.
Round 2: the pair (es, t) has count 9. Merge into "est". Round 3: (est, </w>) has count 9. Merge into "est</w>", which is now a single token meaning "a word ending in est". Round 4: the most frequent pair is (l, o) with count 7 (low 5 + lower 2); merge into "lo". Round 5: (lo, w) has count 7; merge into "low". After five merges the vocabulary is the original characters plus es, est, est</w>, lo and low.
Now encode a word the training set never contained: "lowest". Start with l o w e s t </w>. Apply the merges in rank order: es gives l o w es t </w>; est gives l o w est </w>; est</w> gives l o w est</w>; lo gives lo w est</w>; low gives low est</w>. The word is two tokens, "low" and "est</w>", although "lowest" was never seen. A word with an unknown character would still be spelled with base symbols, and with byte-level BPE nothing is ever unknown.
Now the real cost effect. Suppose a 1,000-word English paragraph is 1,300 tokens in a 100,000-token vocabulary. A text in a language that the vocabulary covers badly may need 3 to 5 times as many tokens per word. With a price per token, it costs the same factor more and uses that much more of the context window. Attention work grows with the square of length, so a 3× longer sequence costs about 9× in the attention part.
Last, the vocabulary-size trade-off in numbers. Going from V = 32,000 to V = 128,000 at width d = 4,096 raises the input embedding from 131 million to 525 million parameters, and the output layer by the same amount, so about 0.8 billion more parameters in total. If this cuts token counts by 15%, the number of tokens processed for the same text falls to 0.85, the cost of the linear layers falls by 15%, and the attention cost falls to 0.85² ≈ 0.72, about 28% less. For an 8-billion-parameter model the extra 0.8 billion parameters are about 10%, so the trade is positive when the saved tokens are worth more than the extra parameters.
intuition: Give frequent letter combinations their own shorthand symbol, like a stenographer, and keep the ability to spell anything out letter by letter when no shorthand exists.
The idea is natural because language is uneven. A few strings ("the", " of", "ing") account for a large share of all text, and compressing the common cases gives most of the benefit. Keeping all the single bytes in the vocabulary as a safety net removes the risk of unknown input. The model then works with pieces that are short enough to be reused (a suffix such as "ing" has the same role in many words) and long enough that sequences are not too long. The merges are learned from the data, so the vocabulary adapts to the language and domain it was trained on: a vocabulary trained on code has tokens for indentation and common keywords, and one trained on English has few tokens for other scripts.
mistakes: People often think a token is a word. In fact a token is whatever piece the merge rules produced. A common word with a leading space is often one token, a rare word is several, and a number or an emoji may be split into pieces. Counting words to estimate cost is only a rough guide (about 1.3 tokens per English word, and much more in other languages).
People often think the model sees letters, so it should be good at spelling or counting letters. In fact the model sees token IDs, and "strawberry" may be two or three tokens whose internal spelling it must learn indirectly. This explains much of the trouble with counting letters, reversing strings or rhyming.
People often think BPE splits words into meaningful morphemes. In fact the pieces come from frequency, not from linguistics. Sometimes they match prefixes and suffixes ("un", "ing"), but often they do not, because a piece is chosen for being frequent and not for being a unit of meaning. The same word may also be split differently with and without a leading space or with different capital letters.
People often think you can change or extend the tokenizer of a trained model freely. In fact the embedding rows and the output layer are tied to the exact vocabulary. Adding tokens needs new embeddings and training; changing the merges changes every ID. The tokenizer is part of the model and must be shipped with it.
People often think all languages are treated alike. In fact the merges reflect the training corpus, so languages with less data are split into more and smaller pieces. Studies have found that the same sentence can need many times more tokens in some languages than in English, which means higher price, slower responses and less context for those users.
tradeoffs: Choose a larger vocabulary (100,000 to 256,000) when you serve many languages, code or long documents and want shorter sequences: fewer tokens means cheaper attention and more text in the context. You pay with larger embedding and output matrices (about V × d each), a softmax over more classes at each step, and rare tokens that get few training examples and may become poorly trained ("glitch tokens"). Choose a smaller vocabulary (32,000 to 50,000) for small models, where the embedding table would otherwise be a large share of all parameters, or for a single language.
Choose byte-level BPE when you cannot allow unknown characters (web text, code, many scripts, emoji); you accept slightly longer sequences for rare scripts. Choose character-based BPE with byte fallback (as in SentencePiece-based models) when you want cleaner Unicode handling and still need a safety net. Choose BPE for simplicity, speed and a strong track record; choose the unigram model when you want several possible segmentations for the same text, which gives a useful regularization during training (subword regularization) and may suit morphologically rich languages.
Choose to split digits individually (Llama 1 and 2 did) when arithmetic and consistent number handling matter, because every number is then written the same way; choose groups of up to three digits (Llama 3) or whole numbers as tokens to save sequence length, at the price of inconsistent splits across numbers. Choose to train the tokenizer on a mix that matches deployment (languages, code, domain) and not on a convenient English sample.
Choose a tokenizer-free design (bytes with learned patching) only for research or when tokenization problems dominate your errors; you gain robustness to spelling and scripts, and you pay with much longer sequences and less mature tooling. For most projects, take the tokenizer that comes with the model and spend effort on measuring its cost on your own data.
friction: Tokens do not align with human units, and this produces the oddities users see: errors in counting letters, uneven arithmetic, different behaviour for "Hello", " Hello" and "hello" (three different token sequences), and sensitivity to trailing spaces in prompts. Models also see text with different tokenizations of the same string as different inputs, so a prompt that ends in the middle of a word can behave worse than one that ends at a token boundary.
There are fairness and cost effects. A vocabulary trained mostly on English gives high fertility for other languages, so their users pay more and get less context for the same meaning. Larger multilingual vocabularies reduce the gap but do not close it. Domain text (chemical names, legal citations, logs, identifiers) can tokenize badly, wasting context.
Under-trained tokens are a known failure: strings that were frequent in the data used to build the vocabulary but rare in the data used to train the model (such as usernames from a forum) can have almost-random embeddings and trigger odd behaviour (the "SolidGoldMagikarp" case reported by Rumbelow and Watkins in 2023). Special tokens can also be injected in user text if the application does not escape them, which is a security issue.
Finally, the tokenizer is a frozen preprocessing step with its own bugs. Differences between implementations (a Python library, a Rust library, a serving engine), or between versions, produce different IDs for the same text and silent quality loss. Changing it later means retraining the model. Streaming decode must handle tokens that end in the middle of a character.
practice: Treat the tokenizer as part of the model: ship the exact vocabulary and merge files, pin library versions, and test that your serving stack produces the same IDs as the training stack on a few thousand varied strings, including emoji, rare scripts, long whitespace and code.
Measure tokens on your own data before estimating cost. Take a sample of real prompts and documents, tokenize them with the model's tokenizer (tiktoken, Hugging Face tokenizers, SentencePiece), and compute tokens per word and per character by language. Use that number for budgets, context planning and chunk sizes (chunk by tokens, not characters). Count tokens with the provider's own counter when you pay per token.
When you train a model, build the vocabulary on a sample that matches your deployment mix, reserve special tokens for chat and tools from the start, use a regular expression for pre-tokenization that matches the best open practice (split digits, keep spaces attached to words), and check the vocabulary for odd tokens. Choose V by estimating the extra parameters against the saved tokens, as in the example above.
In prompts, keep formatting consistent and avoid ending a prompt in the middle of a word; leave a trailing space out unless you know the tokenization. For tasks that depend on characters (spelling, ciphers), give the model the letters separated by spaces or ask it to write them out. To learn the algorithm, implement BPE training in about 30 lines of Python on a small text file, then compare with a library. Karpathy's minbpe is a good guide.

interview: Walk through how a BPE tokenizer is trained and what its time cost is. || Pre-tokenize with a regex, count distinct words and their frequencies, represent words as base symbols, then loop: count adjacent pairs weighted by frequency, merge the most frequent pair, record its rank, update affected words. Total cost is roughly (number of merges) × (average affected words), plus the initial counting pass.

Compare BPE, WordPiece and the unigram model. || BPE builds up by merging the most frequent pair and encodes by applying merges in rank order. value: A mixture-of-experts (MoE) layer replaces one big feed-forward block of a transformer with many smaller feed-forward blocks, the experts, and a small router that chooses, for each token, only a few experts to run. The model has a very large number of parameters, but each token uses only a small part of them. DeepSeek-V3 has 671 billion parameters, and each token uses 37 billion, about 5.5%. Mixtral 8x7B has 46.7 billion parameters and uses 12.9 billion per token. The compute cost per token follows the active parameters (roughly 2 floating-point operations per active parameter), while the quality follows more closely the total parameters. That is the promise: the knowledge capacity of a large model at the running cost of a small one.
The reason this matters is that, for language models, more parameters and more data improve quality predictably (scaling laws), but a dense model pays for every parameter on every token. Training and serving cost then grows in proportion to size. MoE breaks that link: you can raise the number of parameters by 8 or 32 times while the cost per token rises only a little. Most frontier and large open models now use it, including Mixtral, DeepSeek-V2 and V3, Qwen3's MoE models, Llama 4 and Kimi K2.
For the layer above, MoE is the way transformers (transformers and LLMs, L1) get more capacity per unit of compute. The layers below do two jobs. Probability (L4) gives the router: it computes a softmax over the experts, a probability distribution, then keeps the top-k and uses the probabilities as weights for combining the expert outputs. Optimization (L4) deals with the main difficulty of training: without a push toward balance, the router sends most tokens to a few experts and the others never learn. Auxiliary losses or bias adjustments keep the load even, and the usual gradient descent trains the router and the selected experts together. In addition, the residual connection (L2) gives MoE a safe fallback: if a token is not processed by an expert, for example because it is dropped when the expert is full, its representation still passes forward unchanged.
terms: Expert — one feed-forward sub-network (usually a gated MLP) inside an MoE layer; each layer has N of them.
Router (gate) — a small linear layer that gives each token a score for each expert.
Top-k routing — choosing the k experts with the highest scores for a token (k is 1, 2 or 8 in different models).
Total and active parameters — total is all weights of the model; active is the weights actually used for one token (shared layers plus the k selected experts).
Load balancing — keeping the number of tokens per expert roughly equal so that no expert is idle or overloaded.
Capacity factor — a limit on how many tokens one expert accepts per batch, expressed as a multiple of the average; tokens beyond it are dropped or rerouted.
Expert parallelism — placing different experts on different GPUs and sending tokens to the GPU that holds their chosen experts.
Shared expert — an expert that every token always uses, next to the routed experts, to hold common knowledge.
history: The idea is older than deep learning. Jacobs, Jordan, Nowlan and Hinton (1991) proposed "adaptive mixtures of local experts": several networks learn to handle different parts of the input, and a gating network learns who should answer, so the system divides a task by itself. Jordan and Jacobs (1994) extended it to a hierarchy. For two decades it stayed a small-model technique, because the original form ran all experts on every input, so it saved no computation.
The turn to sparse MoE came with Shazeer et al. (2017), "Outrageously Large Neural Networks". They put a layer with up to thousands of experts between LSTM layers, kept only the top-k of the gate outputs and added noise and balancing losses. They reached 137 billion parameters in a translation and language-modelling setup, much larger than anything else at that time. GShard (Lepikhin et al., 2020) brought this to transformers, scaling a translation model to 600 billion parameters with top-2 routing and expert parallelism across TPUs. The Switch Transformer (Fedus, Zoph and Shazeer, 2021) simplified routing to top-1, introduced the common load-balancing loss, and reached 1.6 trillion parameters. GLaM (Du et al., 2021) showed a 1.2 trillion parameter MoE using about 97 billion parameters per token and better results than GPT-3 at lower cost. ST-MoE (Zoph et al., 2022) added a router z-loss to tame instability.
For some years MoE was used mostly inside large companies. Mixtral 8x7B (Mistral, December 2023) changed this: an open model with 8 experts per layer and top-2 routing, 46.7 billion total and 12.9 billion active parameters, that matched or beat Llama 2 70B on many benchmarks at much lower compute per token. DeepSeekMoE (Dai et al., January 2024) proposed many small "fine-grained" experts plus always-on shared experts, and DeepSeek-V3 (December 2024) scaled it to 256 routed experts with 8 chosen per token and one shared expert, using a new bias-based balancing without an auxiliary loss. In 2025, Qwen3-235B-A22B (128 experts, 8 active), Llama 4 (Scout with 16 experts and Maverick with 128, both with 17 billion active parameters) and Kimi K2 (about one trillion total parameters, 32 billion active) followed. Sparse upcycling (Komatsuzaki et al., 2022) showed that a dense checkpoint can be turned into an MoE by copying its feed-forward block into each expert and continuing training.
how: Recall the structure of a transformer layer: attention, then a feed-forward block (an MLP), each wrapped in a residual connection. In an MoE layer, only the MLP changes. The single MLP is replaced by N experts E₁ … E_N, each an MLP of its own (often with a smaller hidden size), plus a router. Attention stays dense and is shared by all tokens. In most models, not every layer is MoE: DeepSeek-V3 keeps the first three layers dense and uses MoE for the rest, and some models alternate dense and MoE layers.
The router is a single linear map from the token's vector x (size d) to N scores: \( s = W_r x \). Probability (L4) turns the scores into a distribution, typically with a softmax, \( p_i = \frac{\exp(s_i)}{\sum_j \exp(s_j)} \), or, in DeepSeek-V3, a sigmoid per expert. The router keeps the k largest, say the experts with indices in a set T. The gate weights are the probabilities of those experts, renormalized to add up to 1. The layer output is \( y = \sum_{i \in T} g_i E_i(x) \). Because the weights g_i depend continuously on W_r, the router receives gradients through them, even though the choice of the top-k is a hard decision. Experts that are not chosen for this token get no gradient from it and do no computation.
The decision is per token and per layer. Two neighbouring tokens may use different experts, and the same token uses different experts in different layers. The experts do not become "the biology expert" and "the law expert" in a clean way; studies of Mixtral found routing that follows syntax and token type (for example indentation, punctuation or particular function words) more than topic. What the experts specialize in is learned, not designed, and is hard to interpret.
Balance is the central training problem. Early in training, a few experts that happen to be slightly better receive more tokens, so they train faster and get better, so the router sends them more tokens. The result is routing collapse: most experts are idle and the model wastes its parameters. The classic remedy (Switch Transformer) is an auxiliary loss: \( L_{\text{aux}} = \alpha \times N \times \sum_i f_i P_i \), where f_i is the fraction of tokens sent to expert i and P_i is the average router probability for expert i. It has its minimum when both are uniform (every expert gets 1/N), and pushes the router toward even use. A small α (around 0.01) is added to the training loss. A z-loss on the router logits keeps them small and stabilizes training. DeepSeek-V3 avoids the extra loss, which can slightly hurt quality: it adds a bias b_i to each expert's score only when choosing the top-k, and after each step it lowers b_i for overloaded experts and raises it for underloaded ones, with a tiny sequence-level loss as a safety net.
A capacity limit helps in hardware. With a batch of T tokens, N experts and top-k, the average load per expert is T × k / N tokens. The capacity is a factor (1.0 to 1.5) times that. If an expert receives more, the extra tokens are dropped for that expert: the layer contributes nothing for them, and the residual connection (L2) carries the token's vector to the next layer. Dropping loses a little quality, so newer designs balance better or avoid dropping, at the price of uneven work among GPUs.
Experts are spread across GPUs (expert parallelism). Each GPU holds a few experts. After the router decides, tokens must travel: an all-to-all communication sends each token's vector to the GPU that holds its chosen expert, the experts compute, and a second all-to-all sends the results back to be combined. This happens twice per MoE layer, forward, and again in the backward pass. The cost is network bandwidth, and it is the main systems challenge. DeepSeek-V3 limits each token to experts on at most 4 nodes, so that the slower inter-node network carries less traffic, and overlaps communication with computation.
Fine-grained design is a recent trend. Instead of 8 large experts and top-2, use for example 64 smaller ones and top-8, with the same active parameters. The number of possible combinations of experts goes from \( \binom{16}{2} \) = 120 to \( \binom{64}{8} \) ≈ 4.4 billion in the DeepSeekMoE comparison, so the model can mix expertise in more ways, and shared experts take the common knowledge so that routed experts can be more specialized.

example: A single token and a tiny layer. There are N = 4 experts and top-2 routing. The router scores for the token are s = (2.0, 1.0, 0.1, −1.0). The two largest are experts 1 and 2 (scores 2.0 and 1.0). Take the softmax over just these two: e² = 7.389 and e¹ = 2.718, with a sum of 10.107. The gates are g₁ = 0.731 and g₂ = 0.269. The layer output is 0.731 × E₁(x) + 0.269 × E₂(x). Experts 3 and 4 do no work for this token.
Now the balancing loss on a batch of 8 tokens with top-1 dispatch. The dispatch counts are (4, 2, 1, 1), so the fractions are f = (0.5, 0.25, 0.125, 0.125). The average router probabilities are P = (0.4, 0.3, 0.2, 0.1). Then \( \sum_i f_i P_i \) = 0.2 + 0.075 + 0.025 + 0.0125 = 0.3125, and \( L_{\text{aux}} = \alpha \times 4 \times 0.3125 = 1.25\alpha \). If the load were perfectly even, f = P = 0.25 for all four, the sum would be 0.25 and the loss 1.0 α. The extra 0.25 α is the penalty for imbalance, and its gradient pushes probability away from expert 1 and toward the others.
Capacity. A layer processes 4,096 tokens with N = 8 experts and top-2. The average load is 4,096 × 2 / 8 = 1,024 tokens per expert. With a capacity factor of 1.25, each expert takes at most 1,280. If the router sends 1,500 tokens to one expert, 220 are dropped, which is 14.7% of that expert's tokens. They pass through on the residual path.

Attention (32 query heads, 8 KV heads) is about 42 million per layer, 1.34 billion in all, and embeddings and output about 0.26 billion. The total is about 46.7 billion. Each token uses 2 experts: 32 × 2 × 176M ≈ 11.3 billion plus 1.6 billion shared, about 12.9 billion active. The compute per token matches a dense 13-billion model, but the memory must hold 46.7 billion parameters, about 93 GB in 16-bit weights, which needs at least two 80 GB GPUs.
Why small batches are inefficient. Take Mixtral with 8 experts and top-2: for one token, 2 of 8 experts (25%) are read from memory. For a batch of 8 independent tokens the chance that a given expert is used by at least one token is 1 − 0.75⁸ ≈ 90%, and for 16 tokens about 99%. So at a batch of 16, decoding reads nearly all 46.7 billion parameters, not 12.9 billion, and memory traffic is that of a model 3.6 times bigger. For DeepSeek-V3 (256 experts, top-8, so each expert is chosen with probability 1/32), a batch of 32 tokens touches 1 − (31/32)³² ≈ 64% of the experts and a batch of 128 touches about 98%. This is why large MoE models are served in big batches over many GPUs.
Communication. With hidden size 4,096 in 16-bit (8 KB per token vector) and top-2, each token sends two copies out and gets two back per MoE layer: about 32 KB. A GPU processing 8,192 tokens per step across 32 MoE layers moves roughly 8,192 × 32 KB × 32 ≈ 8.6 GB per step, much of it over the network. At 50 GB/s per node this is about 170 ms if not hidden behind computation, which is why overlap and node-limited routing matter.
intuition: A hospital with many specialists and a triage nurse: each patient sees only the doctors they need, so the hospital can employ far more specialists than any one patient pays for.
The design is natural because knowledge and computation are different things. A model needs many parameters to store a lot of knowledge, but a given token (a word in a code file, a number in a table) needs only a small part of that knowledge. A dense layer applies everything to everything. A sparse layer lets a cheap decision, the router, select the part that matters. The cost of the decision is tiny compared with the saving. The price is that the whole hospital must still be built and staffed (all parameters in memory), and that the triage must be fair, so that no specialist is overloaded and none is idle.
mistakes: People often think a model with 8 experts is 8 separate models, or that each expert is a specialist in a topic. In fact the experts are parts of every layer, chosen per token and per layer, and they share attention, embeddings and the residual stream. Analyses show specialization by syntax or token type more than by subject, and not as a clean division of labour.
People often think MoE makes a model cheaper to run in every way. In fact it cuts compute per token, but not memory: all parameters must be loaded, so a 46.7-billion MoE needs the memory of a 46.7-billion dense model. It also adds all-to-all communication, and at small batch sizes the saving in memory traffic mostly disappears, because different tokens touch different experts.
People often think the parameter count of an MoE model is comparable to a dense model's count. In fact "671B" and "70B" mean different things: for an MoE the active parameters (37B) set the compute and the total (671B) sets the memory and capacity. Compare models on both numbers, and on measured quality, not on one number.
People often think the router chooses the best experts by a hard rule that cannot be trained. In fact the router is a trained linear layer; the top-k choice is hard, but the gate weights are differentiable and carry gradients to the router. Training does not work without a balancing mechanism, because routing otherwise collapses to a few experts.
People often think that dropped tokens mean lost information. In fact a token that does not get an expert still keeps its vector through the residual connection, so it is processed less, not erased. Frequent dropping still hurts quality and can make results depend on the other tokens in the batch.
tradeoffs: Choose an MoE when you are limited by training or serving compute and have memory and network to spare: you gain a model with several times more parameters, and so more quality, at the same FLOPs per token. Choose a dense model when memory or deployment simplicity is the limit, for example on a single GPU, in small-batch or on-device use, or when you need predictable latency; a dense 8B model is much easier to run than an MoE with 47B total parameters.
Choose few large experts with top-2 (Mixtral style) for simplicity and good hardware efficiency: matrices are big, and communication is moderate. Choose many small experts with shared experts (DeepSeek style) when you want the best quality per active parameter and can build the systems to handle more routing, smaller matrices (lower arithmetic intensity) and all-to-all traffic across many GPUs.
Choose an auxiliary balancing loss when you want a simple, proven method and accept a small distortion of the training objective; choose bias-based, loss-free balancing (DeepSeek-V3) when quality matters more and you can manage the extra control logic. Choose capacity limits with token dropping when GPU work must be even and fixed (static shapes, training on TPUs); choose dropless implementations (block-sparse kernels such as MegaBlocks) when quality matters and your hardware and software support irregular loads.
Choose top-1 (Switch) to minimize communication and compute, accepting lower quality per layer and a need for more experts; choose top-2 or higher for better quality and smoother gradients. Choose expert parallelism across many GPUs when the model is large, together with data and tensor parallelism; this pays off only with fast interconnect (NVLink inside a node, InfiniBand between nodes).
Choose to build an MoE from a trained dense model (sparse upcycling) when you have a good dense checkpoint and a limited budget; choose to train from scratch when you can afford it and want the best final quality, since upcycled experts start identical and take time to differentiate.
friction: All parameters must fit in memory even though most are idle for any token. A 671-billion-parameter model needs about 700 GB in 8-bit weights, so it needs a multi-GPU node at minimum, and efficient serving needs many GPUs with expert parallelism. Fine-tuning is harder too: optimizer states are needed for every expert, and small datasets can make experts overfit or the router unstable.
Communication is the other cost. The two all-to-all exchanges per layer push large volumes of data through the network, and the slowest GPU, the one with the most loaded expert, sets the speed of the layer. Imbalance shows up directly as idle hardware. Small-batch inference is inefficient, because few tokens per expert means small matrix multiplies and poor use of the GPU, and latency-sensitive serving cannot always wait for a large batch.
Training is more fragile. Routing can collapse or oscillate, router logits can grow and cause loss spikes, and balancing losses interfere with the main objective. Results can depend on the batch composition when capacity limits drop tokens. The model's behaviour is also harder to interpret and to debug than a dense model's.
Evaluation is unclear in some areas: the same total parameter count gives different quality depending on expert size, number and top-k, so scaling laws for MoE are still being refined. Finally, the field changes quickly: new routing methods (expert choice, where experts pick tokens), finer experts, and hybrid designs keep appearing, and best practice from a year ago may be outdated.
practice: When you read about an MoE model, record four numbers: total parameters, active parameters, number of experts with top-k, and the number of shared experts. From them compute the memory (total × bytes per weight) and the compute (about 2 × active per token). Together they tell you what hardware you need and what it will cost.
For serving, use an engine with MoE support (vLLM, SGLang, TensorRT-LLM) and expert parallelism. Plan for large batches: continuous batching with many concurrent requests keeps experts busy. Place experts so that heavily used ones are spread across GPUs, and watch the per-expert load in production, since a skew in your traffic (for example mostly code) can overload some experts. Use 8-bit or 4-bit weights to cut memory, and keep the router in higher precision.
For training, start from an established recipe: top-2 or fine-grained top-k, a balancing mechanism, router z-loss or logit clipping, and capacity factor around 1.25 if you use capacity. Monitor expert load (the fraction of tokens per expert), router entropy and loss spikes. Initialize the router with small weights so that routing starts near uniform. Consider upcycling a dense checkpoint if compute is limited.
For fine-tuning, prefer methods that keep the router stable: low learning rates, LoRA on attention and selected experts, and checks that load balance has not collapsed. To compare models fairly, always compare at equal active parameters or equal measured cost, and at equal total parameters or memory; one number can mislead. To understand the idea, build a two-expert layer in PyTorch, train it on a toy task, and plot how the router splits the inputs with and without the balancing loss.
quiz: What is the difference between total and active parameters in an MoE model, and what does each determine? || Total parameters are all weights; they set the memory needed and the model's capacity. Active parameters are the ones used for a single token (shared layers plus the chosen experts); they set the compute per token (about 2 FLOPs per active parameter).
Why does MoE training need a load-balancing mechanism? || Without it, experts that start slightly better get more tokens, train faster and attract even more tokens, so the router collapses onto a few experts and the rest are wasted. An auxiliary loss \( L = \alpha N \sum_i f_i P_i \), or bias adjustments, pushes the load to be even.
A router gives scores (3, 1, 0, −1) for four experts and the layer uses top-2. What are the gate weights? || The top two are scores 3 and 1. Softmax over them: e³ = 20.09 and e¹ = 2.718, sum 22.80, so the gates are 0.881 and 0.119.
A layer has 8,192 tokens, 16 experts and top-2. What is the average tokens per expert, and the capacity at factor 1.25? || Average = 8,192 × 2 / 16 = 1,024 tokens. Capacity = 1.25 × 1,024 = 1,280 tokens per expert. Tokens beyond that are dropped (they pass on the residual path).
When would you choose a dense model over an MoE of similar quality? || When memory or simplicity is the limit: single-GPU or on-device use, small-batch serving, or fine-tuning with little data. The MoE needs all parameters in memory, all-to-all communication and large batches for efficiency, while the dense model's cost is predictable.
interview: Explain how an MoE layer works and where the cost saving comes from. || A router scores each token against N expert MLPs, selects the top-k, and combines their outputs with the normalized gate weights. Only k of N experts run per token, so FLOPs follow active parameters while capacity follows total parameters. The saving applies to compute; memory is still total parameters and communication is added. Mention residual connection, load balancing and capacity.
Why is MoE inference at batch size 1 not much cheaper in memory traffic than a dense model, and what happens at larger batches? || At batch 1, only the k chosen experts are read, which is cheap. As the batch grows, different tokens choose different experts, so the fraction of experts touched rises quickly (1 − (1 − k/N)^b); at b = 16 with top-2 of 8 about 99% of experts are read. Memory traffic then approaches that of the full model, so MoE favours large batches spread over many GPUs.
What are the failure modes of routing, and how do you fix them? || Collapse (few experts get all tokens), oscillation, router-logit growth and loss spikes, and overload that causes drops. Fixes: auxiliary balancing loss or bias-based balancing, router z-loss, small router initialization, capacity factors or dropless kernels, noise in routing early in training, and monitoring per-expert load.
How is expert parallelism implemented, and what limits its scaling? || Experts are sharded across GPUs. After routing, an all-to-all sends each token to the GPU with its expert and a second all-to-all returns the results. Limits: network bandwidth (especially between nodes), load imbalance (the slowest GPU sets the speed), and small per-expert batches that lower arithmetic intensity. Mitigations: node-limited routing, overlap of communication and compute, and larger batches.
Why did DeepSeek use many small experts and shared experts? || Fine-grained experts (for example top-8 of 256) give far more combinations (\( \binom{64}{8} \) ≈ 4.4 billion versus \( \binom{16}{2} \) = 120 at equal active size) so tokens can combine knowledge more flexibly. Shared experts hold common knowledge that every token needs, so the routed experts can specialize and redundancy between them falls.
Would you choose an MoE or a dense model for a product with strict latency and a single 80 GB GPU? || Probably dense (or a small MoE that fits): an MoE with tens of billions of total parameters does not fit in 80 GB in 16-bit and needs quantization or multiple GPUs, and small batches use experts poorly. If quality demands a large MoE, use quantization, expert offloading with caching, or several GPUs, and measure latency at your batch size.
