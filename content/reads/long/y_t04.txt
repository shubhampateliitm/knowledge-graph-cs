@@+ kubernetes
tradeoffs: Choose Kubernetes when you run many services or jobs (roughly 20 or more deployable units) on shared machines, need rolling updates, autoscaling and a common API for several teams, or must run the same way on more than one cloud. Choose something simpler when you run fewer than about 10 services: ECS or Fargate, Cloud Run, or even systemd units and Docker Compose on two or three VMs. You give up a day-two cost that is easy to underestimate: someone must own upgrades (a minor version about every four months, each supported for roughly 14 months), CNI and ingress choices, RBAC, and the cluster's own failure modes. A managed control plane (EKS, GKE, AKS, about $73 per month per EKS cluster) removes etcd and API-server care, but not node upgrades or add-on care.
Choose one big shared cluster per environment when teams trust each other and you want high bin-packing (60–70% node utilisation is realistic); choose several smaller clusters when you need hard isolation (regulated data, different regions, untrusted tenants) or a limit on blast radius. One cluster saves the fixed cost of control planes, monitoring and add-ons per cluster, but a bad CRD, admission webhook or upgrade can hurt every team at once. Namespaces give names, RBAC and quotas, not security; for untrusted code you need separate node pools, gVisor or Kata, or separate clusters. Also remember the soft limits: the tested envelope is 5,000 nodes and 150,000 pods per cluster, and etcd becomes the first limit (a database over about 8 GB is a warning).
Choose requests equal to limits (Guaranteed QoS) for latency-sensitive and memory-heavy services such as JVM services, Kafka clients and databases; choose requests below limits (Burstable) for spiky stateless work where you want density. The price of Guaranteed is idle reserved capacity, often 30–50% of CPU. The price of Burstable is noisy neighbours and OOM kills when many pods burst at the same time. Set CPU limits with care: a CPU limit throttles in 100 ms windows, so a service with a 2-core limit can stall for tens of milliseconds even when the node is idle. Many teams set CPU requests but no CPU limits, and always set memory limits.
Choose Horizontal Pod Autoscaler on CPU or a queue-based metric (KEDA) for stateless services, which reacts in about 15–60 seconds plus pod start-up time; choose Vertical Pod Autoscaler in recommendation mode to right-size requests; choose Cluster Autoscaler or Karpenter to add nodes, which takes 1–3 minutes for a new VM. Together they give elasticity at the price of cold starts: for a latency-critical service keep a warm minimum or spare headroom pods. Choose Spot or preemptible nodes (60–90% cheaper) for batch, Spark executors and stateless replicas with a disruption budget, and on-demand nodes for the control-plane add-ons and stateful sets.
Choose a StatefulSet with an operator (for example for Kafka, Postgres, Cassandra) when you want the operator's upgrade and failover logic and you have storage classes you trust; choose a managed service (RDS, MSK, Cloud SQL) when the data is critical and your team is small. Running stateful systems on Kubernetes is possible but you now own volume attach times (often 30 seconds to several minutes after a node failure), zone-bound volumes, and operator bugs. For Spark and Flink, the Kubernetes scheduler gives one platform and cheap isolation; YARN gave better data locality and a gang scheduler, which on Kubernetes needs Volcano or Kueue.
interview: A team wants to move 12 services from ECS to Kubernetes. What do you ask before agreeing? || I ask what problem they have today: ECS usually does rolling deploys, autoscaling and service discovery well already. A valid reason is a need for operators (Spark, Kafka, Flink), a portable multi-cloud API, a rich ecosystem (Argo, Istio, KEDA) or high bin-packing across many teams. A weak reason is fashion. I would also count the cost: a platform owner of 2–3 engineers, upgrade work every four months, and a migration of IAM, networking and deploy pipelines. I would pilot with two services and compare incident rates before moving the rest.
Pods of one service show uneven CPU: one is at 90%, the others at 10%. Why, and what do you do? || Probably long-lived gRPC or HTTP/2 connections. A Service balances per connection (kube-proxy iptables or IPVS rules), so a client that opens one connection keeps hitting one pod. Fixes: client-side balancing over a headless Service, a proxy or mesh that balances per request (Envoy, Linkerd), or a connection max-age so clients reconnect. I would first confirm by looking at connections per pod, not guess.
A node dies at 3 a.m. Walk through what Kubernetes does and how long it takes. || The kubelet stops renewing its Lease. After the node-monitor grace period (40 seconds by default) the node controller marks the node NotReady and adds the unreachable taint. Pods tolerate that taint for 300 seconds by default, then are evicted. The ReplicaSet controller creates replacements, the scheduler places them, the kubelets pull images and start them, and readiness probes admit traffic. So five to six minutes is normal, and for StatefulSets with volumes it can be longer. To go faster, lower the toleration seconds, use more replicas with topology spread across zones, and a PodDisruptionBudget for planned drains.
Your pods are OOM-killed although the node has free memory. Explain. || The container exceeded its own memory limit, and the kernel cgroup killed it; free memory on the node does not matter. The limit counts page cache and kernel memory of the container too, and for a JVM it counts heap plus metaspace, thread stacks, direct buffers and code cache. Check the limit against the real peak (working-set bytes), set -XX:MaxRAMPercentage to about 70–75 so heap leaves room, and raise the limit or reduce off-heap use.
Why is the control plane built on watches and level-triggered controllers instead of events and commands? || A controller that reacts to edges (events) loses a change if it was down or missed an event. A level-triggered controller reads the whole desired and actual state again and acts on the difference, so it self-corrects after crashes, restarts and duplicate or lost events. The cost is that every object type needs an idempotent reconcile function and a re-list after a watch gap; the benefit is that failure handling is the normal path. This is the same idea as a thermostat compared with a "turn on heating" command.
What limits how large a single cluster can grow, and what do you do beyond it? || Mainly etcd (write throughput, database size, Raft round trips), API-server watch fan-out, scheduler throughput (hundreds of pods per second at best), and add-ons such as DNS and kube-proxy rule counts. Past a few thousand nodes I would shard by cluster (per region or per tenant group) and add a fleet layer for config and placement, rather than push one etcd harder. Large object counts also slow kubectl, controllers and upgrades, so I would also cap objects per namespace and avoid very chatty CRDs.
@@+ airflow
tradeoffs: Choose Airflow when your work is "run these steps in this order at these times" across many systems (Spark, warehouses, APIs, dbt), you want a large library of provider operators (hundreds of integrations), and your team already writes Python. Choose Dagster when the thing you care about is the data product and its freshness: assets, partitions, data checks and lineage are first-class there, and you pay with a new model that your team must learn. Choose Temporal when a "workflow" is really a long-running business process with signals, timers and retries per step (days or months), not a schedule. You give up the huge Airflow ecosystem and hiring pool when you leave it; you give up native asset and lineage views when you stay.
Choose the executor from your task profile. LocalExecutor suits one machine and under about 50 light tasks in parallel. CeleryExecutor suits many short tasks (under a minute) because workers are already running, so latency is a second or two; the price is a broker (Redis or RabbitMQ), shared worker images and noisy neighbours. KubernetesExecutor suits heavy, long, differently-packaged tasks, because each task gets its own pod and dependencies; the price is 5–30 seconds of pod start for every task, so a DAG of 5,000 one-second tasks becomes slow and expensive. Teams often run a hybrid (CeleryKubernetes) and, better still, make each task a thin launcher for a Spark or Databricks job so the executor hardly matters.
Choose few, coarse tasks (one task per Spark job or per table-group) over thousands of tiny ones. Every task instance is a database row, a scheduling decision and a log, so a scheduler comfortably handles tens of thousands of task instances per day, but one DAG with 20,000 mapped tasks per run will slow parsing, the UI and the metadata database. Choose dynamic task mapping when the fan-out is data-dependent and under a few thousand; choose a single task that loops inside Spark when it is larger. You give up per-item retries and visibility when you batch; you give up scheduler headroom when you split.
Choose time-based schedules (cron, interval timetables) when the upstream data arrives on a clock and you can tolerate a safety margin; choose asset-aware scheduling (Datasets/Assets in Airflow 3) or sensors when upstream timing varies. Sensors in deferrable mode cost almost nothing (the triggerer holds thousands of waits in one process), while classic poke sensors hold a worker slot and can starve a pool. The trade-off is correctness against simplicity: a cron at 02:00 that "should be done by then" silently reads partial data on a slow day, while event-driven triggering adds metadata to maintain and a chain of dependencies to reason about.
Choose managed Airflow (MWAA, Cloud Composer, Astronomer) when the team is small and the cost is acceptable (roughly $350–$1,000 or more per month for a small environment before workers); choose self-hosting on Kubernetes with the official Helm chart when you need custom networking, many environments, or tight cost control. Self-hosting means you own metadata-database sizing, upgrades (Airflow 2 to 3 moved to the Task SDK and API server and removed direct database access from tasks, so old DAGs that touched the database need changes) and DAG delivery. Managed services lag on versions by months and limit plugins and networking.
interview: Your nightly DAG started finishing at noon instead of 6 a.m. How do you find out why? || First separate waiting from running: for the slowest path (critical path) I look at each task's queued time, start delay and duration in the Gantt view. Long queue time means no free slots (pool, parallelism or worker capacity or executor start-up). Long run time means the work itself got slower (data volume, a skewed Spark stage). A long gap before the DAG starts points to scheduler lag or DAG parse time (heavy top-level imports). I would check scheduler loop duration, metadata-database load, and sensors holding slots.
How do you make a task safe to retry and to backfill? || Make it idempotent and parameterised by the logical date or data interval, not by "now". Write to a partition with overwrite, or MERGE by key, write to a temporary location and swap, and avoid appends without a dedupe key. Pass the interval in as a template variable. Then a retry or a backfill of 90 days repeats the same result, and I can run backfills in parallel with a limit on active runs.
When would you not use Airflow? || For streaming or low-latency work (it schedules batches, with a latency of seconds at best), for a long-running stateful process with human waits and signals (Temporal), for pure SQL transformation dependency graphs where dbt and its scheduler are enough, or for a very small team with three cron jobs. Also when the real need is lineage and freshness of data assets, where Dagster fits better.
Why do DAG files with network calls at the top level cause outages? || The DAG processor runs the file on every parse, every 30 seconds by default per file, so a call to a database, secret store or API at module level runs thousands of times per day, and if it is slow every DAG in that file waits (parse timeout and missing DAGs). Move such calls inside tasks or use Variables and Connections through templates, which are read at run time.
You have 300 DAGs and a single scheduler is at its limit. What are your options? || First reduce waste: fix slow parsing (imports, one file per DAG, DAG bundles that are not re-synced too often), tune max active runs and pools, and trim the metadata database. Then run several schedulers (supported since Airflow 2, using row-level locks in PostgreSQL or MySQL 8 on the same database), which scales roughly linearly until the database is the limit. Beyond that, split into separate Airflow deployments by team, which also limits the blast radius.
@@+ dagster
tradeoffs: Choose Dagster when your team thinks in tables, files and models ("is the daily revenue table fresh and correct?"), when you want partitions, backfills, data checks and lineage without extra tooling, and when you can start fresh or migrate gradually. Choose Airflow when you must orchestrate many heterogeneous actions (restart a service, call an API, move files) on a clock, depend on a specific provider operator, or already have hundreds of working DAGs and a team that knows it. The migration is not free: a one-to-one port of tasks to ops gains little, and a proper remodel to assets is real work, often weeks per major pipeline. You give up the larger Airflow ecosystem and hiring pool; you gain a catalog of what exists and how fresh it is.
Choose assets with partitions for tables that have a natural key such as day, region or customer; choose a plain op-based job for a side effect that makes no data (send a report, call an API, rotate a key). Choose daily partitions for daily tables, but be careful with many fine partitions: 10 years of hourly partitions is about 87,600 partitions per asset, and the UI, status queries and backfill requests slow down, so use coarser partitions or multi-partition keys with care. Dynamic partitions suit customers or files that appear at run time, at the price of managing the partition set yourself.
Choose Declarative Automation (conditions such as "on missing or upstream updated") when you want freshness to drive runs and the graph is small or medium; choose explicit cron schedules at the leaves when you want predictable runs and costs. Eager conditions on a graph of thousands of assets can fire many runs when one source changes, each with its own cost in Spark or warehouse credits. A good default is cron on the edges, conditions inside, run limits via concurrency pools, and freshness checks to alert when the plan fails.
Choose Dagster+ (hosted control plane, serverless or hybrid agents) when you want to avoid running the web server, daemon and storage and accept per-credit pricing; choose open-source Dagster on Kubernetes when you need full control or must keep metadata inside your network. Self-hosting means PostgreSQL for run and event storage that grows quickly (every step writes events), retention jobs, and running the daemon (schedules, sensors, run queue) as a single point you must monitor. Code locations in separate containers let teams deploy independently, with the cost of one gRPC server per location and version skew of dependencies.
Choose IO managers for small Python-computed data (pandas frames up to a few GB) where load and save should be automatic; choose "compute in the warehouse or Spark" assets, where the function only starts the work and returns metadata, for anything big. Loading a 50 GB table into the Dagster process because a parameter said so is the common mistake. The cost of the second style is that you describe storage yourself and lose automatic type handling; the benefit is that Dagster never touches your data volume.
interview: How is an asset different from a task, and why does it matter when something fails? || A task says "run this code"; an asset says "this table should exist, and this code produces it". With assets, the system knows each asset's latest materialization, partition status and upstream versions, so after a failure it can show which tables are stale or missing, rerun only the failed asset and what is downstream, and answer "is this dashboard based on today's data?". In a task DAG you know only that a task ran; you must infer the data state yourself.
You need to backfill 2 years of daily partitions for 40 assets. How do you do it safely? || Select the assets and partition range in a backfill, which creates runs per partition (or one run covering a range if the asset supports range runs). Limit concurrency with a pool or run-queue limit so you do not overload the warehouse, run a small range first to test, make the asset idempotent (overwrite the partition), and watch cost. Because status is tracked per partition, a failed backfill can be resumed for only the failed partitions.
When is Dagster the wrong choice? || When the work is mostly side effects with no data product, when the team has a large working Airflow estate and no pain from it, when you need a very specific operator that exists only for Airflow, or when you need durable long-running processes with signals (Temporal). It is also a poor fit if the team will not model assets and would only translate tasks.
What happens to scheduling if the Dagster daemon is down? || The webserver and run workers can still serve the UI and finish active runs, but nothing evaluates schedules, sensors or automation conditions, and queued runs are not dequeued. So scheduled data does not arrive until the daemon returns, and in the meantime missed ticks may be skipped or caught up depending on the schedule settings. So I would run it with a health check and alert on a stale daemon heartbeat, and design schedules to tolerate a late run.
How would you migrate gradually from Airflow to Dagster? || Do not stop the old system. First observe the Airflow DAGs from Dagster with the airlift tools, so they appear as assets and lineage becomes visible. Then move one pipeline at a time: model its outputs as assets, add checks, run both in parallel and compare outputs, then switch consumers and retire the DAG. Start with the pipelines that have the most backfill pain or the least dependencies.
@@+ jvm
tradeoffs: Choose the JVM when you need a long-running service or data engine with a mature ecosystem and steady peak throughput: after warm-up, C2-compiled Java is typically within 1.0–2x of C++ on throughput, with far less memory-safety risk. Choose Go when you want small static binaries, start-up in milliseconds and simple concurrency, and can accept a weaker optimiser and 1.5–3x lower peak on compute-heavy code. Choose Rust or C++ when you need no GC pauses at all, tight memory (a JVM needs a few hundred MB before it does work) or direct control of layout. You give up warm-up time (seconds to minutes to reach peak speed) and a larger memory footprint when you choose the JVM; you give up the library ecosystem (Kafka clients, Lucene, Spark, Flink, Netty) when you leave it.
Choose the collector from your latency target and heap size. G1 (default) suits heaps of 4–64 GB with pause goals of roughly 100–200 ms and balanced throughput. ParallelGC suits batch jobs where only total throughput counts, and can give 5–15% more throughput than G1 because its barriers are cheaper. ZGC (generational since JDK 21, default mode in 23) suits large heaps (up to 16 TB) with pauses under 1 ms, at the price of 5–15% more CPU and some extra memory for coloured pointers and relocation headroom. Shenandoah is similar to ZGC in goal. Rule of thumb: if p99 matters more than throughput and the machine has spare cores, choose ZGC; if every core is busy with a batch job, choose Parallel.
Choose heap size by live set, not by the machine: a good start is 2–3x the live data after a full collection, and a container limit of heap plus 25–40% for metaspace, thread stacks, direct buffers and code cache. A heap that is too small causes constant collection; one that is too large makes full collections rare but long for G1 and costs cache locality and money. Set -Xms equal to -Xmx on servers to avoid resize pauses. Choose off-heap memory (direct buffers, Netty pooled allocators, Arrow) for large long-lived data such as Kafka and Spark buffers, and give up easy leak detection and safe memory limits.
Choose JIT warm-up (the default) for services that run for hours; choose CDS or AppCDS archives, CRaC checkpoints, or GraalVM native image when start-up time or memory matters (serverless, CLI tools, autoscaling that adds pods every few minutes). Native image starts in tens of milliseconds and uses perhaps a third of the memory, but gives up dynamic features (reflection needs configuration, no runtime class loading), compiles slowly (minutes), and has lower peak throughput than C2 unless profile-guided optimisation is used. Project Leyden is moving part of this into the standard JDK.
Choose virtual threads (JDK 21+) for services that wait on many I/O calls (thousands of blocked requests) and want simple blocking code; choose a reactive library or asynchronous frameworks only when you already depend on one or need back-pressure operators. Choose a bounded platform-thread pool for CPU-bound work (cores to cores x 2). Virtual threads give no CPU gain, and unlimited virtual threads can overload a downstream database or exhaust a connection pool, so you still need semaphores and limits.
interview: A Spark executor shows long GC pauses and lost heartbeats. How do you diagnose and fix it? || Turn on GC logging (-Xlog:gc*) and look at pause length, heap after collection and cause. If heap after a full GC stays near the maximum, the live set is too large: increase executor memory, reduce cores per executor (each concurrent task holds data), or fix skew. If the live set is small but pauses are long, tune the collector (G1 region size, pause goal, ZGC for large heaps). Also check that memory overhead for off-heap and Python is sufficient, since container memory kills look like lost executors.
Your Java service has p99 latency spikes of 300 ms every few minutes. What are the likely causes? || Candidates: a G1 mixed or full collection (check GC log), a safepoint pause caused by a long counted loop or biased lock-style operations, JIT deoptimisation after a type change, a container CPU throttle (cgroup quota), and a periodic task such as a cache refresh or log rotation. I would match spike timestamps against GC logs, safepoint logs (-Xlog:safepoint), and container throttling counters, then use JFR to confirm.
Why does a JVM service in a container get OOM-killed although the heap limit is below the container limit? || Heap is only part of the process: metaspace, thread stacks (about 1 MB each by default), direct byte buffers, code cache, GC structures and native libraries also count, and the kernel kills at the container limit. With -XX:MaxRAMPercentage of 75 and large direct buffers or many threads, the total can exceed 100%. I measure with Native Memory Tracking (-XX:NativeMemoryTracking=summary) and lower heap or buffer size.
Explain what the JIT does and why a benchmark with a simple loop can mislead. || The JVM starts in the interpreter, profiles hot methods, compiles them with C1 and then C2, inlining, removing dead code and speculating on types. A naive loop may measure the interpreter, include compile time, or be optimised away because its result is unused. Use JMH, which handles warm-up, forks, and consumes results, and report percentiles over many iterations.
When would you pick ZGC over G1 in production, and what does it cost? || When the heap is large (tens to hundreds of GB) or the p99 target is a few milliseconds, since ZGC pauses stay under 1 ms regardless of heap size. The cost is higher CPU use (concurrent work and load barriers), some extra memory headroom and, in older versions, lower throughput. I would benchmark both with production-like allocation rates, because ZGC can stall allocation when the allocation rate outruns concurrent collection.
@@+ pytorch
tradeoffs: Choose PyTorch eager mode for research, debugging and most training: you write Python, set breakpoints and change a model every hour. Choose torch.compile when the model is stable and runs many small ops (transformers, optimisers, normalisation): speedups of 1.3–2x are common, and larger for memory-bound code, but you pay minutes of compile time, risk graph breaks and recompiles when shapes change, and harder errors. Choose CUDA graphs (also via mode="reduce-overhead") for small-batch inference where Python launch overhead is the bottleneck; you give up dynamic shapes and memory flexibility. Do not compile a model that changes every day, or one with data-dependent control flow that you cannot fix.
Choose a distributed strategy by model size. DDP (full copy per GPU, gradient all-reduce) suits models that fit in one GPU's memory with room for activations, up to about 1–3B parameters on 80 GB GPUs with Adam (training memory is roughly 16 bytes per parameter in mixed precision: weights, gradients and two optimiser states, so 1B parameters is about 16 GB before activations). FSDP shards weights, gradients and optimiser state and suits 3B–70B parameters, at the price of extra all-gather traffic that needs fast interconnect. Add tensor parallel inside a node (NVLink) and pipeline parallel across nodes only when a layer or the model does not fit, since both add code complexity and idle time (pipeline bubbles).
Choose bf16 mixed precision for training on A100/H100-class and newer GPUs: it keeps fp32's range so it needs no loss scaling, and it halves memory traffic. Choose fp16 with loss scaling only on older GPUs; choose fp8 (Transformer Engine) when the model is large enough that matmul time dominates and you can afford careful validation. The cost of lower precision is rare instability (loss spikes, NaNs), which costs far more than the speedup when a run of 1,000 GPUs restarts. Keep reductions, softmax and normalisation statistics in fp32.
Choose PyTorch over JAX when you need the largest model zoo, easy hiring and tools that assume it (Hugging Face, vLLM, DeepSpeed); choose JAX when you train on TPUs at scale or want composable transforms such as vmap and per-example gradients. Choose PyTorch over TensorFlow for almost all new work; choose TensorFlow or TF Lite only when you maintain an existing serving stack or need a mobile path you already have. For serving, choose TorchScript-free routes: torch.export to ONNX/ExecuTorch for edge, vLLM or TensorRT-LLM for LLMs, and plain PyTorch with batching for small models (up to a few hundred requests per second).
Choose the DataLoader settings by measuring: num_workers around 4–8 per GPU, pin_memory=True and persistent_workers for image or tabular data. Choose a streaming dataset format (WebDataset, Mosaic Streaming, Parquet) when data is larger than local disk or comes from object storage; the cost is shuffle quality and resume complexity. If GPU utilisation is below 80% with no communication wait, the input pipeline or Python overhead is the usual cause, not the model.
interview: Training loss is NaN after 2,000 steps on 64 GPUs. How do you find the cause? || Check whether it appears on all ranks or one (a single bad batch or a faulty GPU). Log gradient norm and loss per step to see a spike before the NaN; use anomaly detection (torch.autograd.set_detect_anomaly) in a small repro. Typical causes: learning rate too high or warm-up too short, fp16 overflow without loss scaling, a bad data sample, a division by zero in a norm, or low-precision softmax. Remedies: gradient clipping, bf16, lower learning rate, skip and log bad batches, and checkpoint often so you can resume before the spike.
When do you choose FSDP over DDP, and what does it cost? || When parameters plus gradients plus optimiser state exceed one GPU's memory, roughly above 1–3B parameters on 80 GB. FSDP shards the three and gathers weights layer by layer, so memory falls by about the number of GPUs, but communication grows (all-gather in forward and backward plus reduce-scatter), so you need NVLink or fast network and overlap with compute. For smaller models DDP is simpler and faster.
Why can a model run fine in eager mode and be slower after torch.compile? || Graph breaks split the model into many small graphs, shape changes cause recompilation (each new shape compiles again), and guard checks add overhead. For short runs, compile time (minutes) is not paid back. I would use TORCH_LOGS to see breaks and recompiles, mark dynamic dimensions, pad to a few bucket sizes, and compile only the hot sub-module.
GPU utilisation is 40%. Where do you look? || Separate waiting on data, on Python or launches, on communication and on memory-bound kernels. Use the profiler timeline: gaps between kernels mean launch or CPU overhead (fuse ops, compile, CUDA graphs); idle GPU at the start of a step means the DataLoader; long NCCL kernels mean communication not overlapped; many tiny kernels mean small batch size. Fix the biggest gap first and re-measure.
Why does GPU out-of-memory happen on step 1000 and not step 1? || Memory use depends on input shape, so a longer sequence batch may need more activations, and the caching allocator fragments over time. Another cause is holding references to tensors with graph attached (appending loss instead of loss.item()). Check torch.cuda.memory_summary and memory snapshots, cap sequence length or bucket by length, use activation checkpointing, and set expandable segments in the allocator.
@@+ tensorflow
tradeoffs: Choose TensorFlow for new work only when you have a concrete reason: an existing SavedModel and TF Serving estate, TF Lite or TF.js paths already in production, TFX pipelines, or a Google-internal and TPU stack built on it. Choose PyTorch for almost everything else, because new models, papers and tools (Hugging Face, vLLM, DeepSpeed) arrive there first. Choose JAX when you train on TPUs at large scale. You give up an ecosystem that is moving away from you (releases are slower, TF Addons ended in 2024, Keras 3 now runs on JAX, PyTorch and TensorFlow) and gain stability of an old, well-understood serving path. A rewrite of a working recommender from TF to PyTorch typically costs months of validation for little user-visible gain, so migrate when you touch the model anyway.
Choose Keras 3 as the model-writing layer when you want one codebase that can run on TensorFlow, JAX or PyTorch back ends and you use standard layers; choose raw tf.function and tf.GradientTape for custom training loops, research ops and fine control. Keras gives speed of writing and portability; you give up control over the training step and sometimes performance, because the multi-backend layer cannot use every back end's special features. Choose tf.keras (Keras 2, via the tf-keras package) only to keep old code running.
Choose graph execution (tf.function) for training and serving, and eager for debugging. The trade-off is retracing: each new Python argument value or tensor shape traces a new graph, which costs seconds to minutes. Fix input signatures, use None dimensions for batch and sequence, and avoid passing Python numbers that change every call. Choose XLA (jit_compile=True) for models with many small elementwise ops or on TPU, where it can give 1.2–2x; avoid it for models with changing shapes or ops that XLA lacks, where recompiles and failures cost more than they save.
Choose the tf.data pipeline when input is the bottleneck: parallel map, interleave, prefetch and caching can keep GPUs busy, and it integrates with TFRecord and object storage. You give up flexibility and easy debugging compared with plain Python generators or PyTorch DataLoader; the pipeline is a graph too. For recommendation with huge embedding tables, choose TF's parameter-server strategy or TPU embedding hardware when tables reach tens or hundreds of GB; for GPU-only shops, sharded embeddings in PyTorch (TorchRec) are now the common path.
Choose TF Serving or a SavedModel behind a model server for stable, high-throughput inference (thousands of requests per second per node with batching); choose ONNX Runtime or TensorRT after export when you need lower latency or a non-TF runtime, accepting op-coverage gaps and extra validation. On mobile, choose TF Lite for existing models and consider ExecuTorch or ONNX for new PyTorch models.
interview: Your team's recommender runs on TensorFlow. Leadership asks to move to PyTorch. What do you say? || I ask what problem it solves. Reasons that count: hiring, access to new model code, better debugging, or a GPU-focused stack. Costs: re-implementing feature pipelines and custom ops, re-validating metrics, rebuilding serving and monitoring, and running both in parallel. I would propose moving new models first, keep the TF serving path until a model needs change, and do a full migration only when the cost of staying (blocked features, hiring, upgrades) is higher than months of work.
A tf.function-decorated training step is slow and the log shows repeated tracing messages. Why? || Each call is creating a new graph because arguments differ: Python ints or strings that change, tensors with varying shapes, or objects created inside the function. Fix with an input_signature using None for variable dimensions, pass counters as tensors, create variables outside, and pad or bucket variable shapes. Retracing is a silent performance bug, so I would monitor trace counts.
Why does print inside a tf.function print once? || Python code runs during tracing only. The graph records TensorFlow ops; the print is not an op. Use tf.print to add a print op, tf.Variable for state, and tf.random instead of Python random, otherwise the value from trace time is baked into the graph.
When would you pick XLA, and when does it hurt? || It helps when there are many small ops that can fuse (less memory traffic) and on TPU, where it is required. It hurts with changing shapes (recompile for each), data-dependent shapes, and unsupported ops, and it adds compile time at start. Choose a local stdio server when the tool acts on the user's own machine (files, git, a local database): it needs no network, no OAuth, and runs with the user's rights. Choose a remote server over streamable HTTP with OAuth when the tool is a shared service or SaaS, you need central updates, audit logs and per-user authorisation. The cost of local servers is installing and updating software on every machine and giving a process the user's full privileges; the cost of remote servers is running a stateful or stateless service, authorisation at every request and an internet-facing attack surface.
Choose few, well-named tools with precise descriptions and typed schemas over a one-to-one wrapper of a big API. Every tool definition goes into context on each call: 50 tools with detailed schemas can use 10,000–25,000 tokens, and models choose worse as the list grows. Choose to expose higher-level actions ("create_ticket") rather than raw endpoints, and use tool search or lazy loading when you really need hundreds of tools. Choose code execution, where the model writes code that calls tools and returns only a summary, when intermediate results are large; it cuts tokens a lot (one report: 150,000 to 2,000) but needs a sandbox, which is its own risk.
Choose to separate read-only and write tools, and make the host, not the server, enforce policy: confirmation for destructive actions, allow-lists per task, and logging of every call. Treat tool results and server descriptions as untrusted text, because they can carry prompt injection. Avoid giving one agent all three parts of the lethal trifecta at once: private data, untrusted content and an outbound channel. The price is friction (approvals, narrower agents); the alternative is that a web page or email can steer your agent to leak data.
Choose MCP for agent-to-tool connections and A2A when one agent delegates to another agent as a peer; choose a framework such as LangGraph for orchestration inside one application. They sit at different layers and combine: a LangGraph node can call MCP tools. Choose to pin a protocol revision and test on upgrade, because the specification has changed five times in under two years, and the 2026-07-28 revision broke session-based designs; do not assume 2025-era servers and clients interoperate unchanged.
interview: Your company wants to expose its internal API to AI agents through MCP. How do you design it? || Not a wrapper of every endpoint. I would design 10–20 task-level tools with clear descriptions, schemas and examples, split read and write tools, and return compact results (summaries and ids, with pagination) so context stays small. Use a remote server with OAuth so each call runs with the user's own permissions, not a shared service account, add rate limits, audit logs and idempotency keys for writes, and test with an evaluation set of real tasks to see if models choose the right tools.
What is the security model of MCP, and where does it fall short? || The protocol defines transport, authorisation for remote servers (OAuth) and capability negotiation, but it cannot decide what is safe. The model reads tool descriptions and results as text, so a malicious or compromised server, or a web page the agent reads, can inject instructions; annotations like readOnlyHint are not guarantees. Defence belongs in the host: least-privilege tokens, user confirmation, allow-lists, sandboxing, output filtering, and never combining private data, untrusted input and an exfiltration path in one agent.
Why not just give the model a REST API and an OpenAPI file? || You can for one app, and it works. MCP adds standard discovery of tools, resources and prompts, a common way to do authorisation, streaming and updates, and reuse across hosts. The OpenAPI route usually has too many endpoints and parameters for a model, with no guidance on use, so a curated MCP layer often performs better. The trade-off is another component to run and secure.
What happens to the context window when you connect many MCP servers? || Each tool's name, description and schema sits in the prompt for every request, so context and cost grow with the tool count, and accuracy of tool choice falls. Mitigate with fewer tools, per-task tool sets, dynamic tool search, shorter descriptions, and code-execution patterns where results stay outside the model context.
How do you make a remote MCP server scale to thousands of clients? || Keep it stateless where possible: use streamable HTTP, authorise every call, make session state explicit and store handles in a shared store rather than in process memory, and put it behind a normal load balancer. Apply per-user rate limits, timeouts and idempotent writes, return paginated, compact results, and monitor tool latency and error rates. Long-running work should return a task handle that the client polls, not hold a connection open.
