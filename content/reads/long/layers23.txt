@@ L2
value: Layer 2 is the toolbox of mechanisms: replication, partitioning, consensus, the write-ahead log, LSM trees, B-trees, MVCC, columnar storage, encodings, Bloom filters, HyperLogLog, query optimization, vectorized execution, shuffles, watermarks, checkpoints, retries with backoff, attention, gradient descent, the KV cache, quantization. These are the moves that experienced engineers reach for again and again, across products and decades. They are where most real engineering trade-offs live, and they are what a serious system-design discussion at Staff+ level is really about.
The value of this layer is reuse with understanding. The write-ahead log appears in PostgreSQL, Kafka, RocksDB, etcd, the Delta Lake transaction log and Temporal's workflow history. Partitioning appears in Kafka topics, Spark shuffles, Cassandra rings, Elasticsearch shards and Pinot segments. Consensus appears in Kafka's KRaft controllers, etcd under Kubernetes, CockroachDB ranges and ZooKeeper. Once you understand a technique deeply, you understand a slice of dozens of products at once, and you can predict how they behave under load, under failure and under change.
Layer 2 is also where performance is decided. Two products built from the same pattern can differ by ten times in speed or cost because of technique choices: row versus column storage, B-tree versus LSM tree, interpreted versus vectorized versus compiled execution, synchronous versus asynchronous replication, FP16 versus FP8 weights. Products advertise features, but their performance profile comes from this layer.
history: Most techniques on this layer were invented under pressure from a specific hardware limit, and many were reinvented when the hardware changed. B-trees (1970–1972) were designed for disks where reading a block was slow, so each node holds many keys. Write-ahead logging and ARIES-style recovery (1980s–1992) came from making transactions survive crashes cheaply. LSM trees (1996) appeared because sequential writes were far cheaper than random writes on spinning disks, and became dominant again with flash-based key–value stores like LevelDB and RocksDB.
Distributed techniques grew with networks. Lamport clocks (1978), two-phase commit, Paxos (written in 1989, published in 1998), quorums and gossip came from the research community; consistent hashing (1997) came from web caching; Dynamo (2007) combined many of them into a production design. Raft (2014) re-explained consensus so that engineers could implement it correctly, and it spread quickly into etcd, Consul, CockroachDB and Kafka.
In analytics, columnar storage (C-Store, 2005), vectorized execution (MonetDB/X100, 2005) and query compilation (HyPer, 2011) responded to CPUs becoming much faster than memory. In machine learning, backpropagation (1986), convolution, residual connections (2015), attention (2017), mixture of experts, low-rank adaptation (2021) and FlashAttention (2022) each removed a specific bottleneck: trainability, depth, sequence modelling, compute per token, fine-tuning cost or memory traffic.
how: Each technique turns a Layer 3 fact into a useful property. Sequential disk access is much faster than random access (a Layer 3 fact about storage devices), so the write-ahead log and the LSM tree turn random updates into sequential appends. Memory moves in 64-byte cache lines and CPUs have SIMD units (Layer 3 architecture), so columnar storage and vectorized execution keep useful values packed together and processed in batches. Networks lose and delay messages, and nodes crash (Layer 3 distributed systems theory), so replication and consensus are designed around majorities, terms and leases. GPUs are fast at dense matrix multiplication but have limited high-bandwidth memory (Layer 3 architecture), so attention is written as matrix products, and the KV cache is managed like virtual memory pages.
Layer 4 mathematics gives each technique its guarantees and its costs. Quorums work because any two majorities overlap (combinatorics). Consistent hashing moves only about 1/n of keys when a node joins (probability). Bloom filters have a false-positive rate you can compute from bits per key and the number of hash functions. HyperLogLog estimates distinct counts from the statistics of random hash values. Gradient descent works because the chain rule makes gradients cheap, and stochastic gradients work because averages of noisy estimates converge. Compression cannot beat entropy (information theory). Without the maths, a technique is a recipe; with it, you know when and how it will fail.
Techniques also stack on each other inside this layer. Exactly-once processing is built from idempotent writes, transactions and checkpoints. MVCC is built on a write-ahead log and timestamps. Raft is built on leader election, log replication, quorums and failure detection. Speculative decoding is built on the KV cache and rejection sampling. In the map, these appear as 'uses' links between Layer 2 nodes, and they explain why understanding a few core techniques (the log, hashing, quorums, caching, batching) unlocks many others.
intuition: Most Layer 2 techniques are clever ways of paying a cost at a better time or in a better place. A write-ahead log pays for durability with one sequential write now instead of many random writes. An LSM tree accepts cheap writes now and pays later during compaction. MVCC pays with extra storage so readers never wait for writers. A cache pays with memory to avoid recomputation. Batching pays with a little latency to save a lot of per-item overhead. Speculative execution pays with duplicate work to cut tail latency. Replication pays with more machines and network traffic to survive failures. When you meet a new technique, ask three questions: what cost does it move, from where, and to where?
A second intuition: many techniques are the same idea in different clothes. PagedAttention in vLLM is virtual memory for the KV cache. Kafka log compaction is LSM compaction for topics. A CRDT merge is a lattice join. Kubernetes reconciliation is a thermostat. Lineage-based recovery in Spark is a recipe kept instead of a backup. Change data capture is replication with the database log exposed to outsiders. Noticing these echoes is a large part of what people mean by first-principles thinking: you stop seeing hundreds of tricks and start seeing a few ideas applied in many places.
A third intuition: every technique has a 'happy regime'. B-trees are happy with read-heavy, update-in-place workloads; LSM trees with write-heavy ones. Synchronous replication is happy inside one data centre; asynchronous replication across regions. Hash partitioning is happy with uniform keys; range partitioning with ordered scans. Most production trouble starts when the workload drifts out of the regime a technique was chosen for.
friction: Every technique has a failure mode that somebody learned the hard way. Replication lag makes reads stale. Consensus slows down to the speed of its slowest quorum member, and a leader with a slow disk slows everyone. LSM compaction steals disk bandwidth at the worst moment and multiplies writes. MVCC needs garbage collection (PostgreSQL's VACUUM), and long transactions block it. Retries without jitter create retry storms that keep a failing service down. Exactly-once is really 'effectively once', and only inside one system's boundaries. Caches return stale data and fall over together when they all expire at once. Attention costs grow with the square of context length, and the KV cache grows linearly with every token.
The friction is rarely in the idea itself. It is in the edge cases, the tuning knobs and the interactions between techniques. A retry policy interacts with a timeout, a circuit breaker and a queue. A partitioning key interacts with skew, joins and rebalancing. A quantization scheme interacts with outlier activations and kernel support. That is why every read in this map lists both what a technique stands on and what is built on it: to debug a technique, you need both directions.
There is also a knowledge friction. Many of these techniques are explained clearly only in papers or in source code, and blog explanations often skip the failure cases. Jepsen analyses have repeatedly shown that databases claiming a consistency level did not provide it under partitions. Treat claims about a technique's guarantees as hypotheses to test, not facts.
practice: When you design or review a system, list the techniques it relies on at the boundaries where data changes hands: where is the log, where are the replicas, how is data partitioned, what is cached, what is batched, what is retried, and what is approximate? For each, write down its happy regime and its typical failure, and check that your expected load stays inside the regime.
When you debug, map the symptom to the technique that usually causes it. Latency spikes every few minutes: compaction, garbage collection or checkpointing. Throughput collapse under load: retries, lock contention or queueing near full utilization. Stale or missing reads: replication lag, cache invalidation or isolation level. Sudden skew: a hot partition key. This symptom-to-technique map is one of the most valuable things a senior engineer carries in their head.

@@ L3
value: Layer 3 holds the classic subjects of a computer science degree: networks, operating systems, computer architecture, database theory, algorithms and data structures, compilers and programming languages, theory of computation and cryptography. They are the physics of software: the stable rules that every technique above has to obey. They change slowly. TCP dates from 1974, virtual memory from 1962, the relational model from 1970, B-trees from 1972, public-key cryptography from 1976. And they explain almost every performance surprise and production bug you will ever see.
The value of this layer is that it turns mysteries into mechanisms. Why is Kafka fast? Sequential I/O, the page cache and zero-copy sendfile. Why did latency jump when a service moved to another region? Round-trip time and TCP slow start. Why is this Spark job slow even though CPUs are idle? Network shuffle and spills to disk. Why does a PostgreSQL replica lag? WAL replay is largely single-threaded. Why does a JVM service pause? Garbage collection. Why did a 'safe' write disappear after a power cut? It was in the page cache, not on disk, because fsync was never called. Each answer is a Layer 3 concept.
Layer 3 also gives you numbers to reason with. An L1 cache hit costs about 1 nanosecond, a DRAM access about 100 nanoseconds, an NVMe SSD read about 20–100 microseconds, a round trip inside a data centre about 0.5 milliseconds, and a round trip across a continent about 50–150 milliseconds. These numbers span eight orders of magnitude. They explain why most Layer 2 techniques exist: almost every technique is a way of avoiding the expensive end of that range.
history: Each subject on this layer was born when a new machine created a new problem. Operating systems appeared in the 1950s and 1960s to share expensive computers among many users; the Atlas computer introduced virtual memory in 1962, and Unix (1969–1973) gave the process, file and pipe abstractions still used today. Networking grew from ARPANET (1969) and the TCP/IP design by Cerf and Kahn (1974); congestion control was added in 1988 after the internet nearly collapsed under its own traffic in 1986.
Computer architecture went from simple sequential processors to pipelines, caches, out-of-order execution, multicore chips and, after about 2006, a shift toward parallel and specialized hardware such as GPUs and tensor cores, because single-core speed stopped improving quickly. Database theory began with Codd's relational model (1970) and the System R and Ingres projects, which produced SQL, query optimization and transaction recovery. Algorithms as a discipline took shape with Knuth's The Art of Computer Programming (from 1968); complexity theory with Cook and Karp (1971–1972). Compilers go back to FORTRAN (1957); garbage collection to Lisp (1960); just-in-time compilation became mainstream with Java and JavaScript engines in the 1990s and 2000s. Modern cryptography began with Diffie–Hellman (1976) and RSA (1977).
how: Each subject provides abstractions that the techniques above build on. The operating system gives processes, threads, virtual memory, the page cache, file systems and system calls. Networks give addressing and routing (IP), reliable ordered byte streams (TCP), names (DNS) and secure channels (TLS). Computer architecture gives pipelines, caches, SIMD, GPUs and memory models. Database theory gives the relational model, transactions, isolation levels, concurrency control and recovery. Algorithms give hashing, trees, sorting, graph search and dynamic programming. Compilers give parsing, type systems, intermediate representations, JIT compilation and garbage collection. Theory gives Turing machines, computability and complexity. Cryptography gives hash functions, encryption and signatures.
Each Layer 2 technique is a specific use of these abstractions. The write-ahead log uses sequential file appends and fsync. Zero-copy uses the page cache, DMA and the sendfile system call. Vectorized execution uses cache lines and SIMD. Consensus uses timeouts, TCP connections and the theory of failure detectors. PagedAttention uses the idea of page tables. Query optimization uses relational algebra and dynamic programming. Content addressing uses cryptographic hash functions.
Layer 3 in turn rests on mathematics (Layer 4) and physics (Layer 5). Routing rests on graph theory; TCP congestion control on control theory and queueing; hashing on probability and the birthday bound; databases on set theory and logic; type systems on lambda calculus and type theory; cryptography on number theory and finite fields. Computer architecture rests directly on physics: digital logic is built from transistors, memory latency is set partly by wire length and signal speed, DRAM must be refreshed because capacitors leak, and flash wears out because each write pushes electrons through an insulating layer.
intuition: Each Layer 3 subject is a contract between two worlds, and each contract is a useful illusion. The operating system tells each program 'you may pretend you have the whole machine and endless memory'. TCP tells applications 'you may pretend the network never drops, duplicates or reorders bytes'. SQL tells people 'say what you want, not how to get it'. A compiler tells programmers 'write in a language for humans, and the machine will understand'. A memory model tells concurrent code 'these are the only orderings you may observe'. Learning Layer 3 is learning how each illusion is maintained and exactly where it breaks.
A second intuition: the numbers matter more than the definitions. You do not need to remember every detail of the TCP state machine, but you should know that a cross-region round trip is about a million times slower than a cache hit. If you carry the latency numbers, the cost of a context switch, the size of a page and a cache line, and the throughput of a disk and a network card, you can estimate whether a design will work before building it.
A third intuition: Layer 3 subjects mirror each other. Caches exist in CPUs, operating systems (the page cache), databases (the buffer pool), CDNs and browsers, with the same eviction problems everywhere. Scheduling exists in CPUs, operating systems, Kubernetes, Spark and LLM servers. Logs exist in file systems (journals), databases (WAL) and networks (sequence numbers). Once you see the shared structure, each new system is easier to learn.
friction: The illusions leak in specific, learnable ways. Virtual memory leaks as page faults, swapping and TLB misses. TCP leaks as head-of-line blocking, slow start and retransmission timeouts. The page cache leaks when a write is acknowledged before it is durable. Isolation levels leak as anomalies such as write skew under snapshot isolation. Garbage collection leaks as pauses. Floating point leaks as rounding error and results that change with summation order. Memory models leak as bugs that appear only on ARM servers, or only under load.
Almost every hard production bug is one of these illusions breaking. The good news is that the list of leaks is finite, and engineers who know them debug much faster. The bad news is that the leaks interact: a GC pause causes a missed heartbeat, which causes a leader election, which causes a retry storm, which causes queueing delay. Debugging at this level means following a chain across subjects that are usually taught separately.
That is the teaching friction: these subjects are taught in different semesters, with toy examples, and rarely connected to real systems. This map tries to fix that by linking each subject upward. Virtual memory is not only an exam topic; it is also why vLLM can serve more users, why Kafka relies on the page cache, and why a container can be killed by the out-of-memory killer even when the JVM heap looks healthy.
practice: Learn the latency and throughput numbers for your own hardware, not only the textbook ones: measure a disk with fio, a network path with ping and iperf, and a cache miss with a small benchmark. Keep them in your head when reviewing designs.
When something is slow, ask which Layer 3 resource is saturated: CPU, memory bandwidth, disk I/O, network, locks or the scheduler. Brendan Gregg's USE method (utilization, saturation and errors for every resource) is a simple, systematic way to do this. Tools like perf, eBPF-based profilers and flame graphs let you see where time actually goes, which is very often in a Layer 3 mechanism you were not expecting.
