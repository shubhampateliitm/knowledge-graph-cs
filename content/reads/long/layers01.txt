@@ L0
value: Layer 0 is where computer science becomes something you can install, configure, pay for and get paged about. Kafka, Spark, Delta Lake, PostgreSQL, Redis, Kubernetes, PyTorch, vLLM, Claude, an NVIDIA GPU: each one is a bundle of dozens of ideas from the layers below, chosen, combined and polished so that you do not have to think about most of them. That is the main value of this layer. A product packages decisions.
When you start a Kafka cluster, you accept, without writing a line of code, a specific answer to many hard questions: how data is laid out on disk (append-only segment files), how replicas agree (leader and in-sync replicas, with metadata in a Raft log), how consumers track their position (offsets stored in an internal compacted topic), how the network is used (batching, compression, zero-copy reads). When you call an LLM API, you use byte-pair tokenization, embeddings, dozens of transformer layers, attention kernels, a paged KV cache, quantized weights, continuous batching and a GPU cluster, and you see none of it. Somebody made thousands of decisions so you could make one call.
This packaging gives leverage. In 2004, building a reliable distributed log meant writing your own replication protocol and storage engine, and only a few companies could do it. Today it means choosing between Kafka, Redpanda, Pulsar, Kinesis or a managed service, and one engineer can run what once took a research team. The same is true for analytics (Spark and Databricks instead of hand-written MapReduce), search (Elasticsearch instead of your own inverted index) and machine learning (PyTorch instead of writing gradients by hand).
Products also create a shared vocabulary. A team that says 'we land events in Kafka, write bronze and silver Delta tables with Spark Structured Streaming, and serve dashboards from Pinot' has described a whole architecture in one sentence. Everybody who knows those products knows roughly what each part guarantees, how it fails and what it costs. That shared vocabulary is a large part of why the industry moves fast.
Finally, products come with an operational surface: configuration, metrics, logs, upgrade paths, security features, client libraries in many languages, documentation and a community that has already hit most of the bugs you will hit. That surface is often more valuable than the core algorithm. Many teams could write a basic log store in a month; almost none could produce Kafka's ecosystem of connectors, monitoring, tooling and operating experience.
history: The product layer has followed a repeating cycle for about 25 years. First, a large company publishes a paper describing an internal system. Then an open-source project rebuilds the idea. Then a company forms around the project and offers a managed cloud service. Finally the idea becomes a commodity that every cloud offers.
Google's papers started the modern cycle: the Google File System (2003), MapReduce (2004) and Bigtable (2006) became Hadoop HDFS, Hadoop MapReduce and HBase. Amazon's Dynamo paper (2007) inspired Cassandra and Riak. Spark (2010–2012) came from Berkeley research on keeping data in memory between steps. Kafka (2011) came from LinkedIn's need to move activity data between systems. Docker (2013) and Kubernetes (2014) packaged Linux kernel features and Google's Borg experience. Delta Lake (2019), Apache Iceberg and Apache Hudi brought database transactions to files in object storage.
Each wave moved complexity out of user code and into products. The current wave does the same for AI. Model providers package pre-training, post-training and serving into an API; open-weight models plus serving engines like vLLM and SGLang let teams run models themselves; agent frameworks and protocols like the Model Context Protocol package tool use. The cycle also has a second half: once a product dominates, its license and business model change. Elasticsearch, Redis and Terraform all moved away from open-source licenses, and forks appeared (OpenSearch, Valkey, OpenTofu); Redis later added an open-source AGPL option again in 2025. Knowing this cycle helps you predict where a product is heading.
how: The most useful skill this map teaches is how to read a product as a combination of patterns and techniques. Instead of memorizing features, ask four questions. Which Layer 1 patterns does it combine? Which Layer 2 techniques does it use inside each pattern, and with which settings? Which Layer 3 facts does it depend on? Which Layer 4 or Layer 5 limits does it hit first?
Take Kafka. It is a distributed commit log (Layer 1) plus publish–subscribe plus a consensus-based metadata service. Inside, it uses partitioning by key, leader–follower replication with an in-sync replica set, segment files with sparse indexes, batching, compression, idempotent producers and log compaction (Layer 2). Those techniques work because of Layer 3 facts: sequential disk I/O is fast, the operating system page cache keeps recent data in memory, sendfile can move bytes from the page cache to a socket without copying, and TCP provides ordered byte streams. Its limits come from Layer 4 and Layer 5: queueing theory explains why latency rises sharply as brokers approach full utilization, and the speed of light explains why replicating synchronously across regions adds tens of milliseconds to every acknowledged write.
Follow a single Kafka write down the stack and every layer shows up. The producer serializes your record, hashes the key with murmur2 to choose a partition, and adds the record to an in-memory batch. When the batch is full or linger.ms passes, it is compressed and sent over a TCP connection, often encrypted with TLS, to the partition leader. The leader appends the bytes to the end of the active segment file with a write system call; the data lands in the page cache, not yet on disk. Followers fetch the new bytes. When all in-sync replicas have them, the leader advances the high watermark and, with acks=all, replies to the producer. Durability comes from copies on several machines, not from forcing each write to disk. Every step is a technique from Layer 2 sitting on a fact from Layer 3.
Now follow an LLM API call. Your request travels over HTTPS (TLS over TCP, or HTTP/3 over QUIC) to a load balancer and a router that picks a GPU server, preferably one that already holds your prompt prefix in its cache. The text is split into tokens with byte-pair encoding. During prefill, the model runs all prompt tokens through its layers at once: large matrix multiplications on tensor cores, attention computed by FlashAttention-style kernels that keep data in fast on-chip memory, and keys and values stored in a paged KV cache in high-bandwidth memory. Then decoding begins: one token at a time, each step reading the whole KV cache, so the speed is limited by memory bandwidth more than by arithmetic. Continuous batching mixes your request with hundreds of others so the GPU stays busy. Each token is chosen by a sampling rule and streamed back. A single sentence of output touches linear algebra, probability, computer architecture, memory hierarchy, networking and the physics of HBM stacked next to the GPU.
Products also stand on other products. Kafka runs on the JVM and its clients rely on the JVM's garbage collector. Kafka Streams keeps local state in RocksDB. Databricks is Spark plus Delta Lake plus Unity Catalog plus Photon. Elasticsearch is a distributed system wrapped around Lucene. Pinot uses Helix and ZooKeeper for cluster management. In the map, these show up as 'uses' links between Layer 0 nodes. When something breaks, you often need to go one product down before you go one layer down.
intuition: Think of Layer 0 as the shelf of finished tools in a workshop. A good carpenter does not forge a new saw for each job. But a great carpenter knows how saws are made, so she can tell when a cheap one will bind, which tooth pattern suits which wood, and when nothing on the shelf fits and something new must be built. That is why it pays to walk down the stack: products change every few years, while the ideas underneath change every few decades. Kafka may be replaced one day; the append-only log will not.
A second intuition: products are opinions. Delta Lake and Iceberg solve the same problem (transactions over files) with different opinions about where metadata lives and how it is organized. Pinot and Elasticsearch both answer fast analytic queries, with different opinions about indexing and data layout. Redis and Memcached both cache, with different opinions about data structures and threading. When two products look similar, the useful question is not 'which has more features?' but 'which lower-layer trade-off did each one choose?' The map answers that by showing their links downward.
A third intuition: configuration knobs are the leftover trade-offs. Every setting is a decision that the product's designers could not make for everyone, so they left it to you. Kafka's acks, linger.ms and min.insync.replicas are durability-versus-latency and throughput-versus-latency choices. Spark's spark.sql.shuffle.partitions is a parallelism-versus-overhead choice. PostgreSQL's synchronous_commit is a durability-versus-speed choice. If you understand the technique behind a knob, you can set it from first principles instead of copying a blog post.
friction: The cost of packaging is that hidden decisions still leak. Kafka hides the log until a consumer group rebalances during a deployment and lag spikes. Spark hides the shuffle until one skewed key makes a single task run for an hour while 199 others sit idle. Kubernetes hides machines until a noisy neighbour on the same node eats memory bandwidth, or CPU limits throttle a latency-sensitive service. Elasticsearch hides Lucene segments until a mapping explosion or a merge storm hurts the cluster. Joel Spolsky's 'law of leaky abstractions' says every non-trivial abstraction leaks somewhere, and Layer 0 is where you feel the leak, usually at 2 a.m.
Managed services hide even more. That is convenient until you need to explain a bill, a throttling limit or a latency spike that happens inside a black box. Cost itself is a leak: serverless and managed products price by requests, bytes scanned or compute-seconds, so a design that is elegant in theory can be expensive in practice. Engineers increasingly need to understand pricing models as well as algorithms.
There is also churn. Kafka removed ZooKeeper in 4.0 (March 2025). Spark removed Mesos support in 4.0. Delta Lake reached 4.x, adding features like variant types and catalog-managed tables. Licenses change and forks appear. AI model names change every few months. Every fact on this layer has a date attached, and this map records status as of October 2026; check the project pages before relying on a version detail.
Finally, products drift. Kafka gained queue-like share groups, Pinot added upserts, PostgreSQL added vector search through extensions, and warehouses learned to read lake files. Convergence is useful, but it tempts teams to push a product far outside the design it was optimized for. The defence is to know which patterns and techniques sit at its core, so you can tell a new feature that fits the design from one that fights it.
practice: Here is a practical way to learn any new Layer 0 product in about an hour. First, find its log: where does it write data first, and how is that made durable? Second, find its partitioning: how is data split across machines, and by what key? Third, find its replication and consistency model: who is the leader, how do replicas agree, and what can a reader see? Fourth, find its storage format and indexes: rows or columns, which encodings, which indexes, how are files compacted? Fifth, find its failure modes: read the operations guide, the open bug list and, for databases, any Jepsen analysis. Sixth, read the original paper or design document if one exists.
Then look at the default configuration and ask why each default was chosen. Defaults show the workloads the designers expected. Finally, place the product on this map: open it, follow its links down to Layer 2 and Layer 3, and check whether you understand each one. The gaps you find are your reading list.

@@ L1
value: Layer 1 is the layer of patterns: the shapes that keep appearing when people build real systems. A distributed commit log, a lakehouse, an OLAP engine, a coordination service, a search engine, a container orchestrator, a stream processor, a transformer language model, retrieval-augmented generation, an agent loop. None of these is a single product, and none is a single technique. Each is a recipe that combines several Layer 2 techniques to deliver one kind of value: durable and replayable streams, cheap analytics on files, fast aggregations, agreement on metadata, relevance-ranked retrieval, self-healing deployments, continuous computation over events, fluent text, grounded answers, tool-using automation.
Patterns are the right level for design conversations. When you design a system, you rarely start by choosing Raft versus Paxos or B-tree versus LSM tree. You start by saying 'we need a durable, replayable log between ingestion and processing, a lakehouse for history, a real-time OLAP store for dashboards, and a cache in front of the serving API'. That sentence is made entirely of Layer 1 nouns. Once you know the patterns, you can choose products from Layer 0, and you know which Layer 2 techniques you will need to tune.
Patterns also carry knowledge about failure. A pattern is not only 'what to build' but 'what usually goes wrong'. If you choose stream processing, you inherit the problems of late data, watermarks and state recovery. If you choose microservices, you inherit network failures, partial outages and distributed tracing. If you choose an agent, you inherit non-determinism, prompt injection and the cost of long loops. Naming the pattern early lets a team borrow decades of other people's mistakes instead of making them again.
For a Staff+ engineer, this is the layer where most leverage lives. Products can be swapped, and techniques can be tuned by specialists, but choosing the wrong pattern (a batch design where the business needs real-time, a single shared database where teams need independence, a fine-tuned model where retrieval would do) creates costs that last for years.
history: Most patterns were discovered more than once, usually when a new constraint made the old pattern too expensive. Relational databases (1970s) were the first great pattern: one system for storage, querying and transactions. Data warehouses (1980s–1990s) split analytics away from transaction processing, with star schemas and columnar engines. The web era added caches, search engines and message queues. When data outgrew single machines, Google's papers created the 'big data' patterns: distributed file systems, MapReduce batch processing and wide-column stores.
The 2010s added streams and orchestration. LinkedIn's work on Kafka turned the log from an internal database detail into a central architectural pattern; the Lambda architecture (2011) ran batch and streaming side by side, and the Kappa architecture (2014) argued that one replayable log could do both. Docker and Kubernetes turned 'deploy to machines' into 'declare desired state'. Lakehouses (around 2020–2021) merged data lakes and warehouses by adding transaction logs to files in object storage.
Machine learning followed its own path: classical models on hand-built features, then deep learning (2012 onwards), then transformers (2017), then large pre-trained language models, then RAG (2020) and agents (2022 onwards). In both data systems and AI, the direction has been the same: patterns that let more people get a capability without understanding every technique beneath it.
how: Each pattern is held up by a small set of techniques from Layer 2. A distributed commit log needs a write-ahead log, partitioning, replication, idempotent producers, consumer offsets and batching. A lakehouse needs an atomic commit protocol over files (optimistic concurrency), snapshot isolation through versioned metadata (MVCC), columnar files, statistics for data skipping and compaction. An OLAP engine needs columnar storage, encoding and compression, vectorized execution, bitmap and range indexes and scatter–gather query execution. A coordination service needs consensus (Raft or Zab), leases and watches. A transformer LLM needs tokenization, embeddings, attention, residual connections, normalization, a KV cache and post-training with human or AI feedback. An agent needs a model, tool calling, a ReAct-style loop and careful context management.
The lower layers explain why each pattern takes the shape it does. OLAP is columnar because CPUs move memory in 64-byte cache lines and SIMD units process many values at once (Layer 3), and because a column of similar values compresses close to its entropy (Layer 4). Consensus services exist because of impossibility results like FLP and the two generals problem (Layer 3 theory), and they work because any two majorities overlap (Layer 4 combinatorics). Stream processing needs watermarks because there is no global clock (Layer 5 physics, made practical in Layer 3). Deep learning works because the chain rule makes gradients cheap to compute (Layer 4) and GPUs make matrix multiplication cheap to run (Layer 3 and Layer 5).
Patterns also lean sideways on each other. Stream processing needs a commit log underneath to replay from. Change data capture turns a database's log into a stream. RAG needs vector search and a language model. Agents need language models and tools. Event sourcing and CQRS need a log. The lakehouse evolved from the data lake and absorbed the warehouse. Those sideways links appear as 'Related' in each node's read; following them is a quick way to see the design space around a pattern.
intuition: Patterns are like building types in architecture: house, bridge, warehouse, hospital, stadium. Each type solves a recurring problem in a recognizable way, and once you know the type you can 'read' any building of that type quickly. A senior engineer looking at an unfamiliar system mostly does pattern-matching: 'this is a log with compaction acting as a table', 'this is scatter–gather search over shards', 'this is a reconciliation loop with a cache in front'. The map helps you build that library on purpose rather than by accident.
A second intuition: most patterns are answers to a tension. The commit log answers 'how do many systems see the same history without being coupled to each other?'. The lakehouse answers 'how do we get warehouse guarantees at data-lake prices?'. The orchestrator answers 'how do we run a thousand services without placing each one by hand?'. RAG answers 'how do we give a model knowledge it was not trained on, with sources?'. The agent answers 'how do we turn a model that talks into a system that does things?'. If you can name the tension, you can also tell when the pattern is the wrong choice: if there is no tension, there is no need for the pattern.
A third intuition: a pattern is a set of promises. A log promises order within a partition and replay. A lakehouse promises atomic table commits and time travel. A coordination service promises linearizable writes. A search engine promises relevance ranking, not exact counts. Most production surprises come from assuming a promise the pattern never made, such as global order from a partitioned log or exact aggregates from an approximate sketch.
friction: Patterns get adopted by fashion as much as by need. Microservices, the Lambda architecture, data mesh and agents have all been applied where a simpler design would have done better. Every pattern carries costs that its marketing leaves out. Microservices add network failure to every function call. Lakehouses add small-file problems and compaction jobs. Stream processing adds event-time complexity and state management. RAG adds retrieval quality as a new failure point. Agents add non-determinism, cost and new security risks like prompt injection.
Patterns also blur over time. Kafka now has queue semantics, Pinot supports upserts, PostgreSQL stores vectors, warehouses read open table formats, and OLAP engines run full SQL joins. That convergence is healthy, but it makes 'which pattern is this?' harder to answer, and teams sometimes choose a product for its main pattern and then push it far outside its comfort zone. The practical defence is to know each pattern's supporting techniques, so you can see when a product's design no longer fits the load.
Finally, patterns are hard to change once chosen. A data model, a partitioning key or a service boundary leaks into every client, dashboard and team. Moving from batch to streaming, or from a shared database to separate services, often takes years. This is why pattern choices deserve more design time than product choices.
practice: When you face a design problem, try writing the requirement as a tension first: what two things do we want that pull against each other? Fresh data and low cost? Independent teams and consistent data? Fluent answers and correct facts? Then look for the pattern built for that tension, read its 'Where it still hurts' section, and decide whether you can live with that friction.
When you review someone else's design, list its patterns explicitly and, for each one, its promises and its typical failures. Then ask where the design depends on a promise the pattern does not make. That single exercise finds a large share of serious design flaws before any code is written.
