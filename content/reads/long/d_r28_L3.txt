@@ unicode
value: Unicode is a catalogue that gives every character of every writing system one number, called a code point. UTF-8 is the way to write those numbers as bytes. Together they let one string hold English, Hindi, Kannada, Chinese and emoji, and let one program on one machine read text written on another. Before Unicode, each language area had its own "code page" (a table that said what byte 0xE9 means), and text opened with the wrong table turned into garbage. Unicode 18.0, released in September 2026, defines about 172,000 characters across more than 170 scripts.
UTF-8 is the reason this works in practice. It uses 1 byte for the 128 ASCII characters, exactly as ASCII did, and 2 to 4 bytes for everything else. So every old ASCII file is already valid UTF-8, and old C code that stops at a zero byte still works. The format has no byte-order problem, and a reader that lands in the middle of a character can find the next character start without scanning from the beginning. Roughly 98 to 99 percent of websites that declare an encoding use UTF-8, and it is the default in the HTML, JSON, Rust, Go and Python 3 ecosystems.
For the layer above, Unicode decides what "a string" means. Language runtimes (the langruntime concept) store strings as sequences of code points or code units; the web (the webarch concept) is UTF-8 from HTTP headers to HTML to JSON. The layers below make it work. Binary (L3) gives the idea that a number is just a bit pattern, so a code point can be packed into bytes under any rule we choose. Coding theory (L4) gives the idea of a prefix-free, self-synchronizing variable-length code, which is what makes UTF-8 safe to scan, search and cut. Ad-tech engineers meet this every day: device names, app names and search queries from many countries all flow through Kafka, Spark and Parquet as bytes that must decode the same way everywhere.
terms: Code point — an integer from 0 to 0x10FFFF (1,114,112 possible values) that Unicode assigns to one character or mark, written U+0041 for "A".
Encoding form — a rule that turns code points into code units; UTF-8 (8-bit units), UTF-16 (16-bit units) and UTF-32 (32-bit units) are the three standard forms.
Code unit — the fixed-size piece an encoding is built from: one byte in UTF-8, one 16-bit value in UTF-16.
Grapheme cluster — what a person sees as one character on screen; it can be several code points, such as a letter plus an accent, an Indic syllable, or a family emoji.
Combining mark — a code point that attaches to the previous one, such as the accent U+0301 or a Devanagari vowel sign.
Normalization — converting text to a canonical form (NFC composes, NFD decomposes) so that visually identical strings become byte-identical.
Surrogate pair — two reserved 16-bit values (U+D800 to U+DFFF) that UTF-16 uses together to encode one code point above U+FFFF.
Self-synchronizing — a property of a code where you can start reading at any byte and find the next character boundary within a few bytes.
Byte order mark (BOM) — the code point U+FEFF placed at the start of a file to signal byte order or encoding; UTF-8 does not need it.
history: Two projects started separately. In 1987 Joe Becker at Xerox and Lee Collins and Mark Davis at Apple began designing a universal character set; Becker's 1988 paper "Unicode 88" argued that 16 bits (65,536 values) would be enough for all the characters in modern use. The Unicode Consortium was founded in 1991 and published Unicode 1.0 that year. At the same time ISO was building its own standard, ISO/IEC 10646, with a 31-bit space. In 1991 to 1993 the two groups merged their character tables, and since then the code points of the two standards are identical.
The 16-bit assumption turned out to be wrong, because the Han ideographs alone need tens of thousands of values. By then Windows NT (1993) and Java (1995) had chosen fixed 16-bit characters (UCS-2). Unicode 2.0 (1996) expanded the space to 17 planes of 65,536 code points, and UTF-16 was created with surrogate pairs so that old 16-bit systems could reach the new range. This is why Java, JavaScript and Windows APIs still count some characters as two units.
UTF-8 came from a different pressure. The first proposed byte encoding (UTF-1) was awkward, and X/Open wanted one that kept Unix file names working. In September 1992 Ken Thompson and Rob Pike designed what became UTF-8 in a few days, with a famous sketch on a placemat in a New Jersey diner, and converted Plan 9 to it within the same week. It was presented at USENIX in January 1993. RFC 3629 (2003) fixed the final rules: at most 4 bytes, nothing above U+10FFFF, and no surrogates. Unicode 6.0 (2010) brought emoji into the standard, which pushed more people to handle code points above U+FFFF correctly. In 2008 Google reported that UTF-8 had passed ASCII and Latin-1 as the most common encoding on the web.
how: Unicode itself is a table. Each entry has a code point, a name, and properties: script, general category (letter, digit, mark, punctuation), case mappings, direction (left-to-right or right-to-left), and more. The table is divided into 17 planes of 65,536 code points. Plane 0, the Basic Multilingual Plane, holds most living scripts. Plane 1 holds historic scripts and emoji. Plane 2 holds rare Han characters. The first 128 code points are identical to ASCII, and the first 256 are identical to Latin-1.
UTF-8 maps a code point to bytes with four patterns. For U+0000 to U+007F the byte is 0xxxxxxx (7 free bits). For U+0080 to U+07FF it is 110xxxxx 10xxxxxx (11 free bits). For U+0800 to U+FFFF it is 1110xxxx 10xxxxxx 10xxxxxx (16 free bits). For U+10000 to U+10FFFF it is 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx (21 free bits). The first byte says how long the character is, by counting leading 1 bits. Every following byte starts with 10 and carries 6 payload bits. To encode, write the code point in binary, pad it to the free bits of the shortest pattern that fits, and split it across the pattern. To decode, read the lead byte, strip its prefix, and append 6 bits from each continuation byte.
This design gives several properties that come from coding theory. It is a prefix code: no valid byte sequence is the beginning of another, so decoding is unambiguous. It is self-synchronizing: a lead byte (0xxxxxxx or 11xxxxxx) can never be confused with a continuation byte (10xxxxxx), so after a damaged or cut stream you skip continuation bytes until the next lead byte, and you lose at most one character. Substring search can use plain byte search, because a valid character's byte pattern can never appear in the middle of another character. Sorting UTF-8 strings byte by byte gives the same order as sorting by code point. And no byte of a multi-byte character is zero or a "/", so Unix file names and C strings keep working. The shortest-form rule matters too: each code point has exactly one valid encoding. Decoders must reject "overlong" forms such as C0 AF for "/", which were used in real attacks that slipped path separators past filters.
UTF-16 and UTF-32 are the other two forms. UTF-32 stores every code point in 4 bytes, so indexing by code point is a simple multiplication, but text is 4 times larger than ASCII. UTF-16 uses 2 bytes for the Basic Multilingual Plane and a surrogate pair (two reserved values, U+D800 to U+DFFF) for everything above, so it is variable-length too and carries all the complexity of UTF-8 with none of its ASCII compatibility. It also has two byte orders (UTF-16LE and UTF-16BE), which is why files in it often start with a byte order mark. This history is why the surrogate range is excluded from the code point space: UTF-16 could not represent those values as characters.
Above code points there is another layer, because people do not see code points. A grapheme cluster is defined by the rules in Unicode Standard Annex 29. The letter "é" can be one code point (U+00E9) or two ("e" then U+0301, a combining accent). They look the same but compare as different byte strings. Normalization form NFC composes pairs when it can; NFD splits them; NFKC and NFKD also fold "compatibility" variants such as the ligature "ﬁ" to "fi". Case is not simple either: German "ß" uppercases to "SS", and the Turkish dotted and dotless "i" need locale rules. Unicode collation (UCA) defines sort order by language, which byte order cannot do.
Last, the practical connection to the rest of the stack. Binary representation turns the code point into bits; the UTF-8 rules then decide which bits go into which byte. Machine learning tokenizers (the layer above) usually start from UTF-8 bytes: byte-level BPE, used by GPT-2 and later models, starts with the 256 possible byte values and merges frequent pairs, so any string can be encoded and nothing is "unknown". Scripts that need 3 bytes per character start with a handicap, and so cost more tokens for the same meaning.

example: Encode the string "Hi क😀" by hand. It has five code points: "H" is U+0048, "i" is U+0069, the space is U+0020, "क" (Devanagari KA) is U+0915, and the grinning face is U+1F600.
The first three are below U+0080, so each is one byte: 48 69 20. For U+0915, the value is above U+07FF, so use the 3-byte pattern with 16 free bits. In binary 0x0915 is 0000 1001 0001 0101. Split it into 4, 6 and 6 bits: 0000 | 100100 | 010101. Add the prefixes: 1110 0000 = E0, 10 100100 = A4, 10 010101 = 95. So "क" is E0 A4 95. For U+1F600 use the 4-byte pattern with 21 free bits. In binary it is 000 011111 011000 000000, split 3 | 6 | 6 | 6. With prefixes this gives 11110 000 = F0, 10 011111 = 9F, 10 011000 = 98, 10 000000 = 80. So the face is F0 9F 98 80.
The whole string is 3 + 3 + 4 = 10 bytes for 5 code points. Now compare the other lengths. In UTF-16, "H", "i", space and "क" are one 16-bit unit each (4 units), and the face needs a surrogate pair: subtract 0x10000 to get 0xF600, split into the high 10 bits (0x03D) and low 10 bits (0x200), and add D800 and DC00 to get D83D DE00. That is 6 units, or 12 bytes. So the same string has length 10 in bytes, 6 in UTF-16 units, and 5 in code points. Java's String.length() and JavaScript's length return 6, Python's len() returns 5, Go's len() and Rust's len() return 10, and a user would say 5.
Now test self-synchronization. Cut the stream after "H" and start reading at the second byte of "क": the bytes are A4 95 F0 9F 98 80. A4 is 10100100, a continuation byte, so skip it. 95 is also a continuation byte, skip it. F0 starts with 1111, a lead byte for a 4-byte character, so decoding restarts cleanly with the face. You lost one character, not the rest of the stream.
intuition: A very large phone book gives every character a number, and UTF-8 is a shorthand for writing the numbers, with the common ones kept short.
The design is natural once you see the two goals. The catalogue must be big enough for everyone, and it must not punish the old world. A variable-length code gives both: English text stays one byte per character, so nothing breaks, and rarer characters pay with more bytes. The length marker in the first byte and the "10" marker on every following byte are a small amount of redundancy, and that redundancy buys safe searching, cutting and recovery. It is the same trade a prefix code makes everywhere: spend a few bits to make boundaries obvious.
mistakes: People often think a Unicode string has one obvious length. In fact there are at least three lengths (bytes, code points, grapheme clusters), plus UTF-16 units in Java and JavaScript. Which one you need depends on the task: byte length for storage limits and network protocols, code points for most algorithms, graphemes for what the user sees. Truncating a username at 20 bytes can cut a character in half and produce invalid UTF-8.
People often think "Unicode" and "UTF-8" mean the same thing, or that Unicode is a 16-bit encoding. In fact Unicode is the table of code points, and UTF-8, UTF-16 and UTF-32 are three ways to write them. The 16-bit belief comes from the early design and from UCS-2, which could not represent anything above U+FFFF. Emoji and many Han characters are above that line.
People often think two strings that look the same are equal. In fact "é" as U+00E9 and as "e" plus U+0301 are different byte sequences. A database lookup, a hash key or a join on an unnormalized name can silently miss. Normalize at the system boundary (NFC is the usual choice) before comparing, hashing or storing keys.
friction: Counting and cutting are the daily pain. APIs that look simple (substring by index, string reversal, fixed-width columns) are wrong for text with combining marks or surrogate pairs. Different languages index strings differently, so the same offset means different things in Python, Java, Go and JavaScript. Moving offsets between systems, for example between a Java search client and a Python service, is a source of off-by-one bugs.
Normalization and comparison are a second pain. Equal-looking text can differ at the byte level, and some inputs are used for spoofing: Cyrillic "а" looks like Latin "a", so a domain name or a user name can imitate another (a homograph attack). Domain names use a separate scheme, Punycode, for this reason. Invalid input also needs a policy: decoders can fail, replace bad bytes with U+FFFD, or pass them through, and different libraries choose differently. Data pipelines often meet text that is not UTF-8 at all (Latin-1 or Windows-1252 from old systems, or "mojibake" that was decoded twice), and guessing the encoding is never fully reliable.
Cost is the third. UTF-8 takes 3 bytes for most Indic and East Asian characters, where UTF-16 takes 2, and tokenizers trained mostly on English need several times more tokens for the same sentence in Hindi or Kannada, so the same prompt costs more. Segmentation rules also change between versions (Indic conjuncts became one grapheme in Unicode 15.1), so an old library may count differently from a new one.
tradeoffs: Choose UTF-8 for storage, files and network protocols, and choose UTF-16 only when you must match an existing API (Windows, Java, JavaScript internals). UTF-8 has no byte-order problem, is ASCII-compatible and is the default of the web. UTF-16 is only worth considering if your data is mostly East Asian text and every byte counts, and even then general-purpose compression closes most of the gap. You give up constant-time code point indexing either way.
Choose to normalize on input (NFC) when text is used as a key, an identifier or a join column, and keep the original only if you must display what the user typed. Normalizing costs one pass over each string and may change what is stored (NFKC can fold distinct characters together, which is lossy). Do not normalize free text that must round-trip exactly, such as file contents or legal documents.
Choose bytes with a validated UTF-8 type (for example Rust's str, or a database column that rejects invalid sequences) when data crosses trust boundaries. Strict validation rejects bad data early but can drop real-world records; lenient decoding with replacement keeps the pipeline running but hides corruption. Pick one policy per pipeline and log counts of replaced bytes.
For comparing and sorting, choose binary order when you only need a stable, fast, consistent order (index keys, partitioning, hashing), and locale collation when humans read the sorted result. Binary order is fast and identical everywhere; collation is slower and depends on library and locale version, so a collation upgrade can reorder an existing index.
practice: Treat text as bytes at the edges and as validated Unicode inside. Always state the encoding explicitly: charset=utf-8 in HTTP and HTML, an explicit encoding on file reads (Python's open(..., encoding="utf-8")), and UTF-8 in database settings (use utf8mb4 in MySQL, because its older "utf8" stores only 3-byte characters and cannot hold emoji). Do not rely on platform defaults.
Decide what unit each limit uses. A "name must be at most 50 characters" rule should count grapheme clusters or code points with a library; a "column is at most 255 bytes" rule counts bytes. When truncating, cut at a code point boundary at least, and at a grapheme boundary for display. Use a segmentation library such as ICU, or the standard library support in Swift, Go's x/text, or Rust's unicode-segmentation, and not hand-written loops.
Normalize identifiers (email local parts, device and app names, search keys) to NFC and case-fold them at the entry point. For Spark and Parquet jobs, note that Parquet strings are UTF-8 bytes, and Spark's length() counts characters while octet_length() counts bytes. Check how your join keys were produced upstream. When you read old files, detect the encoding with a library, and keep a counter of U+FFFD replacement characters in the output to see data loss.
For security, never validate a string before decoding and then use it after a different decoding step, reject overlong forms, and treat mixed-script names with suspicion. For LLM work, measure tokens per character for your languages before estimating cost, and note that the same meaning in Kannada can cost several times the tokens of English.
interview: A user's display name is stored with VARCHAR(20) and some names are being cut and show a broken character. What happened and how do you fix it? || The limit counts bytes, and the truncation cut a multi-byte UTF-8 sequence in the middle, leaving an invalid trailing lead byte. Fix it by counting and cutting by code point or grapheme cluster with a library, validating UTF-8 on write, and sizing the column in bytes (up to 4 per code point) or using a character-based length.
Why was UTF-8 able to win over UTF-16 and UTF-32? || It is a superset of ASCII, so existing files, C strings and protocols kept working with no migration. It has no endianness issue, is self-synchronizing, and is compact for the Latin text that dominated protocols and source code. UTF-16 breaks ASCII compatibility and needs a byte order mark, and UTF-32 wastes space.
Two services hash the same user name and get different hashes, though both print "José". Why, and what is the fix? || One string uses the single code point U+00E9 (NFC) and the other uses "e" plus the combining accent U+0301 (NFD), so their bytes differ. Normalize to one form (usually NFC) at ingestion, before hashing or using it as a key; use NFKC only if you accept folding compatibility variants.
How does UTF-8 let a decoder recover from a corrupted byte in the middle of a stream? || Continuation bytes always start with 10 and lead bytes never do, so after the damage the decoder skips continuation bytes until the next lead byte and resumes. It loses at most the damaged character, and standard practice is to emit U+FFFD for it.
Your model serves Hindi and English users; Hindi prompts hit the context limit sooner. Why, and what can you do? || The tokenizer was trained mostly on English, so Devanagari text breaks into many more tokens (often byte-level pieces, with 3 bytes per character). Options are a tokenizer with better coverage of the language, measuring tokens per character, and trimming or compressing context for these users.
quiz: What are the UTF-8 bytes for U+00E9 (é)? || U+00E9 is above U+007F, so it uses the 2-byte pattern 110xxxxx 10xxxxxx. The 11-bit value is 00011 101001, giving C3 A9.
Why can a UTF-8 decoder find the next character start from any byte? || Lead bytes start with 0 or 11, and continuation bytes always start with 10. A decoder that lands in the middle of a character skips bytes that begin with 10 until it sees a lead byte, so UTF-8 is self-synchronizing.
Why does the emoji U+1F600 have length 2 in Java and JavaScript, 1 in Python, and 4 in Go? || Java and JavaScript count UTF-16 units, and the code point is above U+FFFF so it needs a surrogate pair (2 units). Python counts code points (1). Go's len counts UTF-8 bytes (4 bytes: F0 9F 98 80).
A 1 GB file of ASCII English text is converted to UTF-16. How large is it, and what if the file is Hindi text of 300 million characters in UTF-8? || The English file doubles to about 2 GB because each character becomes 2 bytes. The Hindi text takes 3 bytes per character in UTF-8 (about 900 MB) and 2 bytes per character in UTF-16 (about 600 MB), so UTF-16 is smaller by a third before compression.
When should you choose NFC normalization on input, and when should you not? || Choose it for identifiers, join keys and search terms, where visually equal strings must be byte-equal. Do not apply it to data that must round-trip exactly, and avoid NFKC for such data, because it folds distinct characters together.

@@ roofline
value: The roofline model answers one question about any computation: is it limited by how fast the chip can calculate, or by how fast data can reach the chip? It needs only two machine numbers (peak compute in FLOP/s and memory bandwidth in bytes/s) and one number for the program (arithmetic intensity, the FLOPs done for each byte moved from memory). The result is a simple upper bound: attainable speed = min(peak compute, bandwidth × intensity). Which term is smaller tells you which optimizations can help, and which cannot.
This matters because the two numbers have drifted apart. Peak arithmetic on GPUs has grown much faster than memory bandwidth, so on a modern accelerator most operations are limited by memory, not by arithmetic. An NVIDIA H100 has about 989 TFLOP/s of dense BF16 compute and 3.35 TB/s of memory bandwidth, so a kernel needs roughly 300 FLOPs per byte to use all the compute. Adding two vectors does about 0.1 FLOP per byte, and decoding one token of a language model at batch size 1 does about 1 FLOP per byte. Both sit far below the line, and a faster arithmetic unit would not help them at all.
For the layer above, this model explains why LLM decoding is slow on huge GPUs (the KV cache and weights are streamed through at memory speed), why operator fusion in ML compilers pays off, why FlashAttention keeps its working data on chip, and why serving systems batch requests or split prefill from decode. The layers below supply its three parts. The memory hierarchy (L3) explains why bandwidth differs by level and why reuse in registers and caches raises intensity. DRAM and HBM (L3) set the bandwidth number that forms the sloped roof. Asymptotic analysis (L4) gives the habit of counting operations and data as functions of problem size, which is exactly how intensity is computed.
terms: FLOP/s — floating-point operations per second; the peak value is the most the arithmetic units can do when fully fed.
Memory bandwidth — bytes per second that the memory system can deliver, for example 3.35 TB/s for the HBM on an H100.
Arithmetic intensity — FLOPs performed divided by bytes moved to or from main memory (FLOP per byte); a property of the algorithm and its implementation.
Ridge point — the intensity where the sloped roof meets the flat roof, equal to peak FLOP/s divided by bandwidth; also called machine balance.
Memory-bound — the kernel's intensity is left of the ridge, so bandwidth limits its speed.
Compute-bound — the intensity is right of the ridge, so peak arithmetic limits its speed.
Operator fusion — combining several operations into one kernel so intermediate results stay in registers or cache and never go to main memory.
Tiling (blocking) — processing data in small blocks that fit in fast memory, so each loaded byte is reused many times.
HBM — high-bandwidth memory, DRAM chips stacked vertically and attached to the processor through a very wide interface.
history: The idea behind the roofline is older than the picture. John Backus's 1978 Turing lecture named the "von Neumann bottleneck": a thin channel between the processor and memory. Callahan, Cocke and Kennedy (1988) defined the balance of a loop, the ratio of memory operations to floating-point operations, and compared it with the balance of the machine. In 1981 Hong and Kung proved, with the "red-blue pebble game", that multiplying two N×N matrices with a fast memory of M words must move at least about N³/√M words, so reuse in fast memory is a mathematical limit, not an engineering detail. Wulf and McKee's "Hitting the Memory Wall" (1995) predicted that memory speed, not processor speed, would limit computing, because processors improved faster each year.
Samuel Williams, Andrew Waterman and David Patterson at Berkeley published the roofline model in Communications of the ACM in April 2009. They were studying multicore chips from AMD, Intel, Sun and IBM, and wanted a single picture that would tell a programmer why a kernel was slow and what to try next. They plotted attainable GFLOP/s against intensity on log-log axes and placed kernels such as sparse matrix-vector multiply, stencils, FFT and dense matrix multiply on it. The picture became a standard tool: Intel Advisor, NVIDIA Nsight Compute and the NERSC supercomputing centre all added roofline views.
The model became widely known outside HPC (high-performance computing) because of deep learning. Gholami and co-authors (IEEE Micro, 2024) measured that peak compute grew about 3× every two years while DRAM bandwidth grew about 1.6×, so the ridge point keeps moving right. Transformer inference papers from 2022 (for example Pope et al. at Google) and FlashAttention (Dao et al., 2022) used roofline reasoning directly. Horace He's essay "Making Deep Learning Go Brrrr From First Principles" (2022) taught the same idea to many ML engineers as the split between compute, memory bandwidth and overhead.
how: Start with the two machine numbers. Peak compute P is the number of arithmetic units times clock speed times operations per cycle, taken from the data sheet for the precision in use (BF16 and FP8 have different peaks). Bandwidth B is best measured with a streaming benchmark such as STREAM (McCalpin, 1995), because the data-sheet value is rarely reached. The ridge point is R = P / B. For an H100 SXM, 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOP per byte in BF16, and about 590 in FP8 (which doubles P but not B).
Next the program number. Arithmetic intensity I = W / Q, where W is the work in FLOPs and Q is the traffic in bytes to and from main memory. Q is the part people get wrong. It is not the number of loads in the code, because caches and registers absorb repeated reads. It is the data that actually crosses the memory interface, so intensity depends on the implementation: the same matrix multiply is memory-bound if written naively and compute-bound if tiled well. Here the memory hierarchy does its work. Tiling loads a block into fast memory once and uses it many times, which raises I without changing W.
Then the bound. Attainable performance = min(P, B × I). On log-log axes this is a line with slope 1 from the left (the sloped roof, where performance rises in proportion to intensity) joined to a horizontal line (the flat roof) at the ridge. A kernel with I below R can reach at most B × I; for I above R, at most P. The model therefore says what to do. If you are under the sloped roof, reduce bytes (fusion, lower precision, compression, better layout, reuse through tiling) and do not bother optimizing arithmetic. If you are under the flat roof, reduce work or use faster units (tensor cores, vector instructions).
Asymptotic analysis shows how intensity scales with problem size. Vector addition does N operations on 3N numbers, so I stays constant at a small value for all N and the kernel is memory-bound however large it is. Matrix multiply does 2N³ FLOPs on 3N² numbers, so I grows with N: larger matrices are more likely to be compute-bound. Convolutions, attention and stencils lie in between, and attention's score matrix grows as N² while the work per byte of it stays small, which is the reason FlashAttention avoids writing that matrix to HBM.
Where does the bandwidth number come from? DRAM and HBM set it by geometry. One HBM3 stack is a tower of DRAM dies with a 1,024-bit interface running at roughly 5 to 6.4 Gbit/s per pin, which is 650 to 820 GB/s per stack. An H100 has five active stacks beside the GPU die on a silicon interposer, which gives its 3.35 TB/s. A desktop with two DDR5 channels has a 128-bit path and gets about 90 GB/s. Wider and closer is the only way to raise B, and it is limited by the number of pins and by power, which is why B grows slowly. Peak compute P, in contrast, grows with every added transistor and every narrower number format, which is why the ridge keeps moving right.
The memory hierarchy decides how much of the traffic ever reaches that interface. A GPU has about 256 KB of registers and up to roughly 228 KB of shared memory per streaming multiprocessor, and tens of MB of L2 cache. These levels deliver many times the bandwidth of HBM, but only for data that is already there. So the practical way to read the plot is a loop: compute I from the tensor shapes, find the roof above it, measure the achieved speed, and ask whether the gap to the roof is a bytes problem (reuse is poor, so Q is larger than the ideal) or an efficiency problem (the roof is right but the kernel does not reach it).
Real machines have several roofs. Each level of the hierarchy has its own bandwidth: registers, shared memory or L1, L2, HBM, and across the network. A kernel can be compute-bound with respect to HBM traffic yet limited by shared-memory bandwidth. The cache-aware roofline (Ilic et al., 2014) plots one sloped line per level. There are also lower flat roofs: using plain FP32 cores instead of tensor cores, or an instruction mix with no fused multiply-add, caps P at a lower ceiling. Measured points sit below the roofs, and the gap says whether latency, imperfect parallelism or poor instruction mix is the next problem.

example: Take an H100 with P = 989 TFLOP/s (BF16) and B = 3.35 TB/s, so the ridge R is about 295 FLOP per byte.
Case 1, decoding with batch size 1. A model with 8 billion parameters in BF16 (2 bytes each) is 16 GB. To produce one token, the GPU must read every weight once and does about 2 FLOPs per weight (one multiply, one add). So W = 16 GFLOP and Q = 16 GB, giving I = 1 FLOP per byte. The bound is B × I = 3.35 TFLOP/s, which is 0.34% of peak. The time per token is at least 16 GB ÷ 3.35 TB/s ≈ 4.8 ms, so at most about 210 tokens per second for one sequence, whatever the arithmetic speed. A GPU with twice the FLOPs gives the same answer; one with twice the bandwidth halves the time.
Case 2, batching. If 64 requests share each weight read, the work per step is 64 times larger but the weight traffic is the same. Intensity becomes about 64 FLOP per byte, and the bound rises to 64 × 3.35 = 214 TFLOP/s (22% of peak). A step still takes about 4.8 ms, but now it produces 64 tokens, so total throughput is about 13,000 tokens per second. At a batch of about 295 the kernel reaches the ridge and the weights become cheap. In practice the gain stops earlier, because each request also has its own KV cache, which must be read in full for every token and does not amortize across requests, and because larger batches raise latency.
Case 3, matrix multiply. For C = A × B with N×N BF16 matrices and ideal reuse, W = 2N³ and Q = 3N² × 2 bytes = 6N², so I = N/3. For N = 256, I ≈ 85, so the bound is 85 × 3.35 = 286 TFLOP/s, about 29% of peak: memory-bound. For N = 1,024, I ≈ 341, above the ridge, so the bound is the full 989 TFLOP/s: compute-bound. The crossover is at N ≈ 885. This is why small matrix multiplies run far below the advertised peak.
Case 4, fusion. Three separate elementwise kernels (for example GELU, dropout, add) over a BF16 tensor each read and write it: 3 × 4 bytes per element. Fused into one kernel, it reads once and writes once: 4 bytes per element. The FLOPs are unchanged, but the traffic is a third, so the memory-bound kernel runs about 3 times faster.
intuition: A kitchen is limited either by how fast the cooks can chop or by how fast ingredients arrive from the store room; if the delivery door is the narrow point, hiring more cooks changes nothing.
The roofline is natural because every computation must do two things: move data and transform it. Either the mover or the transformer is slower, and the slower one sets the pace. Intensity is the exchange rate between the two, how much transforming you get from each byte you pay to move. The sloped roof is where moving is the limit, so each extra byte per FLOP costs time. The flat roof is where transforming is the limit. Because there are only two limits, the picture is a single bend, and every optimization is a move on it: raise intensity (move right), or raise the roof.
mistakes: People often think a GPU with more TFLOPS will run any workload faster. In fact a memory-bound kernel sees no benefit from extra FLOPs. Decode throughput tracks memory bandwidth, which is why a newer chip with a similar bandwidth gives little decode gain, and why quoting only peak FLOPs is misleading.
People often think the roofline predicts the speed of a kernel. In fact it gives an upper bound. Real kernels sit below it because of latency, poor parallelism, bank conflicts, tail effects and instruction mix. A kernel at 20% of its roof has a different problem from one at 95%, and the model tells you which roof to look at, not how to reach it.
People often think arithmetic intensity is a fixed property of an algorithm. In fact it depends on the bytes that cross the memory interface, which depends on tile sizes, cache sizes and data type. Moving from BF16 to FP8 halves Q, so intensity doubles, and the ridge also moves because P changes.
People often think "memory-bound" means the program is wasting memory or using too much of it. In fact it means bandwidth is the limiting rate, and it is a statement about speed, not capacity. A kernel can be memory-bound while using only a small part of the available memory size.
friction: The model has no notion of latency, so it fails for kernels with dependent loads, pointer chasing or small problem sizes, where the machine is waiting rather than streaming. It also ignores overheads such as kernel launch time (a few microseconds each), which dominate when kernels are tiny; this is a third regime that He calls overhead-bound. It treats compute and memory as perfectly overlapped, which is only true if the program has enough parallelism to hide memory latency.
Counting Q is hard. Hardware counters can measure real traffic but differ by vendor, and cache behaviour depends on the other work on the machine. Multiple levels need multiple roofs, and multi-GPU programs add network roofs where link bandwidth (for example NVLink or InfiniBand) sets another slope. The ridge point also keeps rising with each hardware generation, so code that was compute-bound on an older chip can become memory-bound on a newer one with no change.
Finally, the model describes single kernels. A whole application is a sequence of kernels with different intensities, plus host-device copies and communication, so the end-to-end speed is a weighted mix. Sparse and irregular workloads, such as embedding lookups in recommendation models, are limited by random access, which a streaming bandwidth number overstates.
tradeoffs: Choose tiling and fusion when a kernel is left of the ridge and its intermediates are large: they cut bytes without changing results. The costs are register and shared-memory pressure, which reduces how many blocks run at once (occupancy), and less modular code. Choose to leave kernels unfused when they are already compute-bound or when flexibility, debugging and model iteration matter more than the last 20%.
Choose lower precision (FP8, INT8, 4-bit weights) when decode or training is bandwidth-bound: halving bytes roughly doubles intensity and decode speed. You give up numerical range and may lose accuracy, and the gain disappears when the kernel is already compute-bound or when dequantization adds work.
Choose bigger batches when throughput per dollar matters, since each weight read is shared across more tokens. Choose small batches when tail latency matters (interactive chat), accepting low utilization. The deciding numbers are the ridge point (about 300 for BF16 on an H100) and the service-level latency target; serving systems often pick a batch near the knee of the latency curve, not at the ridge.
Choose recomputation over storage when memory traffic is the bottleneck: FlashAttention recomputes parts of attention in the backward pass rather than saving an N² matrix to HBM, doing more FLOPs for fewer bytes. This is a good trade only on the sloped side of the roofline.
practice: Before optimizing, compute the ridge point of your hardware and the intensity of your kernel on paper. Count FLOPs from the algorithm and bytes from the tensor sizes (reads plus writes, once each), then compare with a profiler. NVIDIA Nsight Compute can draw a roofline chart for a kernel; on CPUs, Intel Advisor or perf with memory-bandwidth counters give the same view. Measure bandwidth with a streaming test first so you know the real roof, usually 80 to 90% of the data-sheet number.
If the kernel is left of the ridge, work on bytes: fuse elementwise operations (torch.compile, XLA and Triton do this automatically in many cases), pick a layout that lets loads be contiguous, use lower precision for storage, and tile to reuse data in shared memory. If it is right of the ridge, check that tensor cores are used and the shapes are multiples of the hardware tile size (for example multiples of 8 or 64), because wrong shapes drop you to a lower ceiling.
For LLM serving, estimate tokens per second at batch 1 as bandwidth ÷ model bytes, then raise the batch until latency limits you. Quantize weights to cut bytes, and watch the KV cache, which grows with sequence length and batch and eventually dominates traffic. For Spark and data jobs the same reasoning applies on CPUs: a columnar scan of integers does a few operations per byte and runs at memory or storage bandwidth, so reading fewer columns and compressing help more than faster code.

value: A layered network model splits the hard problem "send data from a program on one machine to a program on another" into a stack of smaller problems. Each layer solves one problem, offers a simple service to the layer above, and hides how it does it. The two famous models are the 7-layer OSI reference model and the 4-layer TCP/IP model. The internet runs on TCP/IP; OSI survives as a vocabulary, which is why people say "layer 2 switch", "layer 4 load balancer" and "layer 7 firewall".
The value is independence. A web application does not care if its bytes cross Wi-Fi, fibre, a 5G radio or a satellite, because the link layer hides that. A new link technology can be added without changing HTTP, and a new application protocol can be added without changing any router. The internet grew from a few hundred networks to many tens of thousands of independently run ones because every network only had to agree on the narrow middle (IP), not on what was above or below it.
This concept is the map for the whole networking part of the stack. It stands on four concrete layers: Ethernet and switching moves frames between neighbours on one link, IP and routing carries packets across many networks, TCP gives programs a reliable byte stream, and NAT and firewalls sit at the edge and rewrite or filter what passes. What makes them a stack, and not four unrelated tools, is reductionism and abstraction (L5): the discipline of defining each part by its interface, so that a part can be replaced without breaking the parts around it. The web (the webarch concept) is the main user: a single page load crosses every layer.
terms: Layer — a group of functions that offers one service to the layer above and uses the service of the layer below.
Protocol — the agreed rules for messages between the same layer on two machines, such as TCP or HTTP.
Interface — the boundary between two neighbouring layers on one machine, such as the socket API between an application and TCP.
Encapsulation — wrapping the data from the layer above inside the layer's own header (and sometimes trailer) before passing it down.
Header — the control information a layer adds in front of its payload, such as addresses, ports and sequence numbers.
PDU (protocol data unit) — the name for a layer's unit of data: frame (link), packet (network), segment (TCP) or datagram (UDP), message (application).
MTU (maximum transmission unit) — the largest packet a link can carry; 1,500 bytes on standard Ethernet.
End-to-end principle — the rule that functions needing knowledge of the application should be done at the endpoints, with the network core kept simple.
Middlebox — a device in the path, such as a NAT, firewall or load balancer, that looks at or changes more than the headers of its own layer.
history: Before the 1970s each vendor had its own network design (IBM SNA, DEC DECnet) and machines from different vendors could not talk. ARPANET, started in 1969, used a protocol called NCP, which assumed a single reliable network. Vint Cerf and Robert Kahn's 1974 paper "A Protocol for Packet Network Intercommunication" proposed something different: a common protocol that runs over any network, so that many different networks can be joined. It was later split into TCP (reliable delivery between endpoints) and IP (addressing and forwarding), specified in RFC 791 and 793 in 1981. On January 1, 1983, ARPANET switched from NCP to TCP/IP in one coordinated "flag day".
In parallel, ISO began a standard in 1977, and Charles Bachman's proposal of seven layers became the base of the OSI reference model, published as ISO 7498 in 1984. OSI had many committees and complete protocol suites, and governments backed it, but TCP/IP already ran, had free implementations in Berkeley Unix (1983), and worked. By the early 1990s TCP/IP had won. RFC 1122 (1989) described the practical four layers: link, internet, transport, application. Layers 5 and 6 of OSI (session and presentation) never became separate parts of the internet; their jobs are done inside applications and libraries such as TLS.
Two papers gave the design its reasons. Saltzer, Reed and Clark's "End-to-End Arguments in System Design" (1984) argued that a function such as reliable delivery cannot be fully provided by the middle of the network, because only the endpoints know whether the data arrived correctly, so the network should stay simple. David Clark's "The Design Philosophy of the DARPA Internet Protocols" (1988) explained the ordered goals: survive failures first, support many service types second, and accounting last. Steve Deering later described the result as an hourglass: many protocols above, many links below, and one thin waist, IP, in the middle.
how: Take the TCP/IP model first. The link layer moves a frame between two machines on the same link, using link-local addresses (MAC addresses on Ethernet). The internet layer (IP) moves a packet between any two machines, across many links, using global addresses. The transport layer moves data between two programs, using port numbers: TCP adds a reliable ordered byte stream, UDP adds only ports and a checksum. The application layer is everything else: HTTP, DNS, TLS-wrapped protocols, Kafka's wire protocol. OSI splits the same work into seven: physical, data link, network, transport, session, presentation, application. In practice "layer 2" means link, "layer 3" means IP, "layer 4" means TCP or UDP, and "layer 7" means the application protocol.
Each layer works only with two things: the data it is given and its own header. When an application sends 100 bytes, the transport layer prepends a header (TCP: ports, sequence number, acknowledgment, window; 20 bytes minimum) and passes the result down as a segment. The network layer prepends an IP header (source and destination address, time-to-live, protocol number; 20 bytes for IPv4). The link layer prepends an Ethernet header (destination and source MAC, type; 14 bytes) and appends a 4-byte checksum. This wrapping is encapsulation. The receiver reverses it: each layer strips its header and passes the payload up, using a field in the header (EtherType, IP protocol number, port) to choose which protocol receives it. This demultiplexing is what lets one wire carry many protocols and one machine run many programs.
The decisive property is that headers are read only at their own layer, and by the machines that need them. A switch reads the Ethernet header and forwards by MAC address. A router reads the IP header, decrements the time-to-live, and forwards by destination address; it does not look at the TCP header or the payload. Only the two endpoints read the TCP header. Because of this, the link below can be changed at every hop: the frame is rebuilt at each router, with new MAC addresses and perhaps a different link type, while the IP packet inside stays the same. The reductionist idea of abstraction is exactly this: a layer is defined by what it promises, not by how it works inside.
The service each layer promises is deliberately modest. Ethernet delivers a frame to a neighbour, perhaps with errors detected and dropped. IP promises best effort: a packet may be lost, duplicated or reordered. TCP builds a reliable stream out of that unreliable service with sequence numbers, acknowledgments, retransmission and congestion control. This is the end-to-end principle at work: the core stays simple and cheap (a router only has to look up an address), and complexity lives in the endpoints, where it can be changed without touching the network.
Layers also map to where the code runs. The physical and link layers live in the network card and its driver; many cards also compute checksums and split large TCP writes into packets (segmentation offload), which saves CPU. The IP and TCP layers live in the operating-system kernel, reached through the socket interface. The application layer runs in your process. Between layers, two small fields glue things together: the EtherType in an Ethernet header says whether the payload is IPv4, IPv6 or ARP, and the protocol number in an IP header says whether it is TCP (6), UDP (17) or ICMP (1). Without these tags a receiver could not know which parser to run. The IP time-to-live field has a second job: it bounds how long a looping packet can live, so a routing mistake wastes bandwidth for at most 64 or so hops and not forever.
The OSI numbering maps onto this as follows: layer 1 (physical) and layer 2 (data link) are the TCP/IP link layer; layer 3 (network) is IP; layer 4 (transport) is TCP and UDP; layers 5 to 7 (session, presentation, application) are all inside the application layer. An engineer who says "layer 2 problem" means a link or switching issue, such as a loop, a wrong VLAN or a bad cable.
NAT and firewalls show where the clean picture bends. A NAT device rewrites IP addresses and TCP or UDP ports, so it reads headers from layers 3 and 4. A firewall may filter on layer 3 and 4 fields, or inspect layer 7 content. They work because the lower layers allow it, but they break the strict "read only your own layer" rule, which is why the model is a guide and not a law.

example: A browser on a laptop sends a request of 100 bytes to a web server at 203.0.113.10, over a home Wi-Fi/Ethernet network and the internet.
Step 1, application. The HTTP request is 100 bytes of text (ignore TLS here).
Step 2, transport. TCP adds a 20-byte header (source port 51234, destination port 443, sequence number, flags). The segment is 120 bytes.
Step 3, network. IP adds 20 bytes (source 192.168.1.20, destination 203.0.113.10, TTL 64, protocol 6 for TCP). The packet is 140 bytes. 140 is far below the 1,500-byte MTU, so no splitting is needed.
Step 4, link. The laptop sees that 203.0.113.10 is not on its local network, so it sends the packet to its default gateway, the home router. It asks for the router's MAC address (ARP, the protocol that maps IP addresses to MAC addresses on a link), then adds a 14-byte Ethernet header and a 4-byte checksum. The frame is 158 bytes. On the wire there are also 8 bytes of preamble and a 12-byte gap, so it uses 178 bytes of link time. At 1 Gbit/s, that is about 1.4 microseconds.
Step 5, the router. The home router strips the Ethernet header, reads the IP header, and applies NAT: it rewrites the source address 192.168.1.20 to its public address and picks a public port, then records the mapping so the reply can be reversed. It reduces TTL to 63, builds a new Ethernet frame for the next hop (the ISP) with new MAC addresses, and sends it. Each of the 8 to 15 routers on the way repeats the same job, reducing TTL by 1 and rebuilding the frame.
Step 6, the server. Its network card receives a frame addressed to its MAC, the IP layer sees its own address and protocol 6, TCP finds the connection from the four values (source address and port, destination address and port), and passes the 100 bytes to the web server, which sees an ordinary read.
Efficiency follows from these numbers. A full segment carries 1,460 bytes of data in 1,538 bytes of link time (1,460 + 20 + 20 + 14 + 4 + 20), which is 95% efficient. The 100-byte request uses 178 bytes of link time for 100 bytes of data, which is 56%. This is one reason batching small messages (as Kafka does) matters.
intuition: A letter inside an envelope inside a mailbag inside a truck: each handler reads only their own label, and no handler cares what the layer outside or inside is made of.
The design is natural because networking has several unrelated problems: electrical signals, local delivery, global addressing, reliability, and application meaning. If one design handled all of them together, every new link technology or application would force changes everywhere. Cutting along narrow interfaces lets each problem be solved and replaced alone. The cost is a few header bytes per layer, and that is a good price for being able to put the same HTTP over a cable, a radio and a satellite.
mistakes: People often think the internet uses the seven-layer OSI model. In fact it uses TCP/IP, which has four layers and was running before OSI was published. OSI's session and presentation layers do not exist as separate parts. When engineers say "layer 7", they mean "the application protocol", and "layer 5" has almost no meaning.
People often think each layer is fully independent of the others. In fact layers leak. TCP's checksum covers parts of the IP header (the pseudo-header), TLS sits between TCP and HTTP, QUIC puts transport and encryption together in user space, and MTU at the link affects TCP's segment size. Performance and failures often need knowledge of more than one layer.
People often think a router works only at layer 3, and a switch only at layer 2. In fact modern devices cross layers: a router must also do link-layer work on every interface, load balancers hash on layer 4 ports, and "layer 3 switches" route. The layer names describe the main header used for the decision, not the box.
People often think encapsulation is encryption or hiding. In fact encapsulation only adds headers and does not protect content. Anyone on the path can read every header and the payload, unless something like TLS or IPsec encrypts it.
friction: Strict layering costs performance. Every layer copies or processes data, crossing the kernel boundary costs CPU, and a high-speed link (100 Gbit/s) needs tricks such as segmentation offload, kernel bypass (DPDK) or RDMA, which skip layers on purpose. Some information needed above is hidden below: an application cannot easily see whether a delay comes from Wi-Fi retransmission, a congested link or a slow server, and TCP treats packet loss as congestion even when the link is a lossy radio.
Middleboxes damaged the end-to-end principle. NATs, firewalls, caches and load balancers look at higher-layer fields and sometimes change them. Protocols that do not look familiar get dropped or broken, so new transport protocols such as SCTP saw little use outside telecom networks, and the network core "ossified". This is the main reason QUIC runs on UDP and encrypts almost all of its header. Tunnels and overlays (VXLAN, GRE, WireGuard) put layers inside layers, and each adds bytes: VXLAN adds 50 bytes per packet, which can push packets over the MTU and cause silent drops if path MTU discovery fails.
The model also gives no help with the layers that matter most to users: naming (DNS), trust (certificates), and routing policy (BGP) do not fit a single layer. They are applications that serve the layers beneath them.
tradeoffs: Choose strict layering when you build general-purpose systems that must outlive any one technology: the narrow waist (IP) is what allowed new links and applications to appear for fifty years. Choose to break layers deliberately only when you can measure a clear gain and own both ends: kernel bypass and RDMA in a data centre, or QUIC's merger of transport and security. You pay with portability and with the loss of generic tooling (tcpdump, firewalls) that understands the standard layers.
Choose a layer 4 load balancer when you need very high throughput and low latency and do not need to look at requests: it forwards connections using only addresses and ports and can handle millions of connections. Choose a layer 7 load balancer when you need routing by path or header, TLS termination, retries or per-request metrics, and accept extra CPU, latency of roughly one to a few milliseconds and a bigger failure surface.
Choose to put a function in the network (caching, compression, DDoS filtering) when it benefits all users and the cost of doing it at every endpoint is higher; choose the endpoint when only the application can judge correctness, which is the end-to-end argument. Middleboxes help performance and security but make evolution harder.
Choose standard MTU (1,500 bytes) for traffic that crosses the internet, and jumbo frames (about 9,000 bytes) only inside a network you control from end to end. Jumbo frames cut header overhead from about 5% to under 1% and reduce packets per second, but one device with a smaller MTU causes drops.
practice: Debug in layers, from the bottom up. Check the link (interface up, speed, errors in ip -s link), then IP (ping tests reachability and round-trip time, traceroute shows each hop, ip route shows which route the host will use), then transport (ss -tan shows connection states, curl -v shows connect time), then the application (status codes, logs). Most outages are found by asking at which layer the packet last behaved correctly. tcpdump or Wireshark shows the nested headers directly and is the most honest tool.
When you name a component, say its layer. In AWS, a Network Load Balancer works at layer 4 and keeps the client IP, an Application Load Balancer works at layer 7 and understands HTTP, and security groups filter at layers 3 and 4. For services with latency goals, remember that every layer adds a round trip or a copy: a new HTTPS connection costs one TCP round trip plus one TLS round trip before the first request byte, so reuse connections.
Watch the MTU when you use overlays (Kubernetes CNI plugins, VPNs, VXLAN): lower the pod MTU by the encapsulation overhead or large responses will stall while small ones work, a classic symptom. Keep chatty small messages in batches.

It decrements TTL (and updates the IP checksum in IPv4) and writes a new link header for the next hop; it does not need the TCP header.
A packet carries 1,460 bytes of TCP data over Ethernet with IPv4. How many bytes of link time does it take, counting preamble and gap? || 1,460 + 20 (TCP) + 20 (IP) + 14 (Ethernet) + 4 (FCS) + 8 (preamble) + 12 (gap) = 1,538 bytes, so about 95% is data.
Why is IP called the narrow waist of the internet? || Everything above it (TCP, UDP, QUIC, applications) and everything below it (Ethernet, Wi-Fi, fibre, 5G) only has to agree on IP. This lets both sides change independently.
When should you break layering on purpose? || When you control both ends and have measured that the layer boundary costs too much, such as RDMA or kernel bypass in a data centre. You then lose the generic tools and portability of the standard stack.

@@ ethernet
value: Ethernet is the way machines on the same network send each other frames, and switching is how a network of many machines forwards those frames without every machine hearing every conversation. Every server, laptop, phone-charger-sized camera and data-centre switch speaks it. A frame carries the destination and source hardware addresses (MAC addresses), a type field, a payload of up to 1,500 bytes and a checksum. A switch learns which port leads to which address and sends each frame only there.
It matters to a distributed-systems engineer because Ethernet sets the physical limits for everything above. The speed of a port (1, 10, 25, 100, 400 and now 800 Gbit/s) bounds how fast Kafka brokers, Spark shuffles and Delta reads can move data. The shape of the network (a leaf-spine fabric, in which any two servers are the same small number of hops apart over many equal paths) decides how much traffic can cross the cluster at once. And its failure modes, such as full switch buffers that drop packets when many servers answer one client together (incast), appear to applications as mysterious tail latency.
The layers below give Ethernet its two key ideas. Electromagnetism (L5) explains what a bit is on the wire: a voltage pattern on twisted copper pairs, or pulses of light in fibre, behaving as Maxwell's equations require, which fixes distance and speed limits. Probability (L4) explains how early shared Ethernet avoided collisions without a central controller: each station waited a random time, and the range of the random wait doubled after each collision. Above it, the layered network model (the osi concept) uses Ethernet as its link layer: IP packets travel in Ethernet frames, one hop at a time.
terms: MAC address — a 48-bit hardware address of a network interface, written as six hex pairs such as 3c:22:fb:12:ab:01; the first 24 bits identify the manufacturer.
Frame — the unit of data at the link layer: header, payload and a 4-byte checksum.
Switch — a device with many ports that forwards each frame only to the port where its destination MAC address was last seen.
MAC table — the switch's memory of address-to-port mappings, filled by watching source addresses and expiring old entries (often after 300 seconds).
Broadcast — a frame sent to the address ff:ff:ff:ff:ff:ff, which every machine on the segment receives.
VLAN — a virtual LAN: a tag in the frame that splits one physical switch network into separate logical ones.
CSMA/CD — carrier sense multiple access with collision detection, the shared-cable rule of classic Ethernet: listen first, send if quiet, stop and retry later if two senders collide.
Spanning tree — a protocol that switches use to disable redundant links so the network has no loops.
Clos (leaf-spine) fabric — a data-centre topology in which every leaf switch connects to every spine switch.
Incast — many senders replying to one receiver at the same time, overflowing the receiver's switch port buffer.
history: Bob Metcalfe wrote the memo that started Ethernet on May 22, 1973 at Xerox PARC. He was inspired by ALOHAnet, a Hawaiian radio network where stations sent whenever they liked and retried after collisions. Metcalfe and David Boggs built a version on a coaxial cable ("the ether") at 2.94 Mbit/s to connect Xerox Alto computers to laser printers. Their 1976 CACM paper described the design: a shared cable, listen-before-send, collision detection, and back-off with growing random delay. In 1980 Digital, Intel and Xerox (DIX) published a 10 Mbit/s standard, and IEEE standardized it as 802.3 in 1983.
The cable was shared at first, so every machine saw every frame. Two changes ended that. In 1990, 10BASE-T put Ethernet on twisted-pair telephone-style wiring in a star around a central device, and the first multiport switches appeared in the same years. Switches replaced hubs, and full-duplex operation (sending and receiving at once on separate wire pairs) was standardized in 1997, which removed collisions entirely. Radia Perlman's spanning tree algorithm (1985) let switches be wired redundantly without frames circulating forever.
Speed then grew by ten every few years: Fast Ethernet 100 Mbit/s (1995), Gigabit (1998 to 1999), 10 Gbit/s (2002), 40 and 100 Gbit/s (2010), 400 Gbit/s (2017) and 800 Gbit/s (IEEE 802.3df, 2024), with 1.6 Tbit/s in development. Data centres changed the topology too. Charles Clos had designed a multi-stage switching network for telephones in 1953; Al-Fares, Loukissas and Vahdat (SIGCOMM 2008) showed how to build a data-centre network from cheap identical switches in a fat-tree, and Google's "Jupiter Rising" paper (2015) described a decade of such fabrics. In 2025 the Ultra Ethernet Consortium published its 1.0 specification for AI-cluster networks.
how: A frame starts with a preamble and a start marker (8 bytes) that let the receiver synchronize its clock. Then comes the destination MAC (6 bytes), the source MAC (6 bytes), a 2-byte type field (0x0800 means IPv4, 0x86DD IPv6, 0x0806 ARP), the payload (46 to 1,500 bytes) and a 4-byte frame check sequence, a CRC-32 over the frame. A receiver that finds a bad checksum drops the frame silently; Ethernet does not retransmit, which is left to TCP. If a VLAN tag is present, 4 more bytes carry a 12-bit VLAN ID (4,094 usable values) and a 3-bit priority.
Classic shared Ethernet used the probability idea. A station listens; if the cable is quiet it sends while listening to itself. If it hears a different signal, there was a collision, so it sends a jam signal, stops, and waits a random number of slot times chosen from 0 to 2ⁿ − 1, where n is the number of collisions so far for this frame (capped at 10). It gives up after 16 attempts. The slot time was 512 bit times (51.2 µs at 10 Mbit/s), and the minimum frame size of 64 bytes comes from it: a sender must still be transmitting when news of a collision at the far end of a 2.5 km network returns. Random doubling works because the number of competing stations is unknown; if few compete, the first wait is short, and if many compete, the range grows until they separate. Modern full-duplex links have no collisions, but the 64-byte minimum remains.
A switch replaces the shared cable with a table. For each incoming frame, it first learns: it records "source MAC X came from port 3" in its MAC table. Then it forwards: if the destination MAC is in the table, it sends the frame only out of that port; if not (unknown unicast) or if it is a broadcast, it floods the frame out of all other ports. When the destination replies, the switch learns that address too, and after a short time most traffic is point to point. Entries expire so that a machine that moves is found again. Several conversations can run at full speed at once, as long as they use different ports, so a 48-port 10 Gbit/s switch can carry far more than 10 Gbit/s in total; the figure is set by its internal fabric (the switching capacity), often 1 Tbit/s or more.
Switches forward in two styles. Store-and-forward waits for the whole frame and checks the checksum, adding a serialization delay (a 1,538-byte frame at 10 Gbit/s takes about 1.2 µs, at 100 Gbit/s about 0.12 µs). Cut-through starts sending as soon as it has read the destination address, in a few hundred nanoseconds, at the cost of sometimes forwarding a bad frame. Data-centre switches usually do cut-through.
Broadcast and loops limit how large a layer-2 network can be. ARP, DHCP and other protocols broadcast, and every machine must process them. A loop in the switch wiring makes broadcast frames circle forever (a broadcast storm), which is why spanning tree disables redundant links. That wastes capacity, so large data centres do not stretch layer 2 widely. They use small layer-2 domains and route (layer 3) between racks, with ECMP (equal-cost multipath: the router hashes each flow to one of many equal paths). VXLAN tunnels, which wrap Ethernet frames inside UDP with a 24-bit network ID, allow virtual machines and containers to keep layer-2 behaviour across routed fabrics.
The topology that results is a leaf-spine (two-tier Clos) fabric. Each server connects to a leaf switch at the top of its rack. Each leaf connects to every spine switch. Any two servers on different racks are exactly three switch hops apart (leaf, spine, leaf), with as many equal paths as there are spines. If a leaf uses half its ports for servers and half for spines, there is no oversubscription. With 64-port switches, one tier of leaves and spines reaches 64 × 32 = 2,048 servers, and a three-tier fat tree reaches k³/4 = 65,536 servers for k = 64.

example: Part 1, learning. A four-port switch starts with an empty table. A (port 1) sends to B. The switch records A = port 1. B is unknown, so it floods the frame out of ports 2, 3 and 4. C and D discard it (the destination is not theirs); B accepts it. B replies to A. The switch records B = port 2, finds A in the table, and sends the frame only out of port 1. From now on A and B talk directly, and C and D see nothing of it. The table has two entries after two frames.
Part 2, serialization time. A full frame is 1,538 bytes on the wire (1,500 payload, 18 header and checksum, 20 preamble and gap), which is 12,304 bits. At 1 Gbit/s that takes 12.3 µs; at 10 Gbit/s 1.23 µs; at 100 Gbit/s 0.12 µs. Light in fibre or electrical signals in copper travel at about two thirds of the speed of light, roughly 5 µs per kilometre. So a 100 m cable adds 0.5 µs, which is comparable to one serialization at 10 Gbit/s. In a data centre, a path of five switch hops with 1 µs per hop is around 5 to 10 µs one way, and most of the 100 µs or so round trip that applications see is software, not the wire.
Part 3, incast. A Spark reducer (the client) fetches 40 shuffle blocks of 64 KB from 40 different executors at once. The reducer's switch port runs at 10 Gbit/s and has a buffer of about 256 KB for it. All 40 responses arrive within microseconds: 40 × 64 KB = 2.56 MB. The port can drain 2.56 MB in about 2 ms, but only 256 KB fits in the buffer, so roughly 2.3 MB is dropped. The senders' TCP then waits for a retransmission timeout, which is often a minimum of 200 ms on Linux by default. A transfer that should take 2 ms takes more than 200 ms. Fixes are lower minimum retransmission timeouts, shared deep buffers, ECN-based congestion control such as DCTCP, limiting how many fetches run at the same time, and spreading requests in time.
intuition: A mail room that learns which desk each person sits at: the first letter for someone new is copied to every desk, but after the reply, letters go straight to the right desk.
The design is natural because it asks the least from everyone. Machines only need a unique address and the ability to put it on a frame. The switch does not need configuration, because it can learn the map from the traffic itself, and it treats anything unknown by shouting, which always works. The random back-off of the original cable is the same insight: with no central controller, make each party yield a random, growing amount, and the group sorts itself out. Each simple local rule produces global order.
mistakes: People often think Ethernet is a cable or a speed. In fact it is a family of standards for frames and for the signalling over many media (copper, fibre, backplane). The same frame format has run from 3 Mbit/s to 800 Gbit/s.
People often think a switch keeps traffic private. In fact a switch only avoids sending unicast frames to ports that do not need them; it floods broadcast and unknown-destination frames, and an attacker can fill the MAC table (MAC flooding) to make a switch flood everything. Use encryption (TLS, IPsec) when the content matters.
People often think collisions and CSMA/CD still matter on modern networks. In fact full-duplex switched links have no collisions. If you see "collisions" counters rising, you have a duplex mismatch or an old hub.
People often think the IP address is how Ethernet delivers a frame. In fact Ethernet knows only MAC addresses; ARP (for IPv4) or neighbour discovery (for IPv6) translates an IP address to a MAC on the local link. When a destination is on another network, the frame is addressed to the router's MAC, not the destination's.
People often think more switch bandwidth always means fewer drops. In fact drops come from buffer overflow when many inputs target one output at the same time, and a switch with huge total capacity can still drop at one port.
friction: Layer-2 domains do not scale: broadcast traffic grows with the number of hosts, the MAC table is limited (tens of thousands to a few hundred thousand entries), and loops are dangerous. This pushes designs to routed fabrics and overlays, which add complexity and per-packet overhead. A spanning-tree misconfiguration can take down a whole data centre in seconds.
Buffers are the main performance problem. Shallow shared buffers in commodity switches drop packets under incast and microbursts, while deep buffers create queueing delay (bufferbloat). Congestion control at the sender and ECN marking at the switch have to cooperate. For AI training and storage, RDMA over Converged Ethernet (RoCEv2) needs a nearly lossless network, built with priority flow control (PFC), which pauses senders. PFC can cause head-of-line blocking, pause storms and deadlocks, and tuning it with ECN-based schemes such as DCQCN is a specialist job. The Ultra Ethernet specification tries to replace this with a better transport on standard Ethernet.
Speed also brings physical limits. At 100 Gbit/s per lane, signals use PAM4 modulation (4 voltage levels, so 2 bits per symbol), which has a worse signal-to-noise ratio and needs forward error correction, adding latency and occasional errors. Copper reaches only a few metres at the highest rates, so fibre and optics dominate cost and power. Finally, the 1,500-byte MTU is a legacy: at 400 Gbit/s a standard frame arrives every 31 ns, so hosts depend on offloads, and jumbo frames of about 9,000 bytes are used where the whole path supports them.
tradeoffs: Choose a routed leaf-spine fabric with layer-3 to the top-of-rack switch when you run more than a few racks: it limits broadcast domains, uses all links through ECMP, and fails in small pieces. Choose a large layer-2 network only when applications need it, such as legacy clustering or live migration of VMs with fixed IPs, and accept the spanning-tree and flooding risks. Overlays (VXLAN) give you the layer-2 behaviour on a routed fabric for 50 bytes per packet of overhead.
Choose oversubscription (for example 3:1 between leaf and spine) for general web and batch workloads where traffic is mostly local to a rack; choose 1:1 non-blocking for shuffle-heavy analytics and AI training, where every server talks to every other. Non-blocking costs about two to three times as many spine ports and optics.
Choose shallow-buffered cut-through switches for latency-sensitive RPC traffic, with ECN and DCTCP to keep queues short. Choose deep-buffer switches where traffic is bursty and loss is very expensive, such as the boundary to a wide-area network, and accept higher and more variable queueing delay.
Choose lossless Ethernet with PFC (RoCEv2) when you need RDMA performance for storage or training and have the skill to operate it. Choose lossy Ethernet with TCP or QUIC when you can tolerate a few microseconds more latency, since it is much simpler to run and debug.
practice: Check link health first: interface speed and duplex (ethtool eth0), error and drop counters (ip -s link, ethtool -S), and the MTU on both ends. Make sure the MTU is consistent along the entire path; on AWS, traffic inside a VPC can use 9,001-byte jumbo frames, but traffic out to the internet is limited to 1,500. A dropped-packet counter that rises under load usually points to buffer overflow, not a faulty cable; rising CRC or FCS errors point to bad optics or cables.
When you design placement for shuffle or replication traffic, know your oversubscription ratio, put replicas of a Kafka partition in different racks (which also separates failure domains such as a top-of-rack switch), and avoid fan-in patterns that cause incast. Tune the number of simultaneous shuffle fetches (spark.reducer.maxReqsInFlight and maxSizeInFlight) in line with what the network can absorb. Use network cards with offloads enabled, spread interrupts or use multiple queues so one core does not receive everything, and prefer 25 or 100 Gbit/s NICs for storage-heavy nodes.
For debugging, tcpdump on both sides tells you where frames disappear, and a switch's MAC table (show mac address-table) answers "which port is this host on". Learn the three or four tools your network team uses, and read the Jupiter Rising paper to see how a large operator thinks about the fabric as one system.

@@ iprouting
value: The Internet Protocol (IP) gives every machine on the internet an address and defines a packet format that any network can carry. Routing is the work of deciding, at each router, which neighbour is closer to the destination. Together they let a packet travel from a laptop in Bengaluru to a server in Virginia across dozens of networks owned by different companies, with no central planner and no connection set up in advance.
The internet works because IP promises very little. It offers best effort: a packet may be lost, duplicated, delayed or reordered, and the network does not tell the sender. Because the promise is so small, almost any link technology can keep it, and every network is free to run inside however it wants. Reliability is built above (TCP), and naming is built beside (DNS). IPv4 uses 32-bit addresses (about 4.3 billion), IPv6 uses 128 bits.
For the layer above, IP is the carrier. TCP segments, UDP datagrams and therefore QUIC and all of HTTP travel inside IP packets, and NAT works by rewriting IP addresses and ports. The layers below supply the algorithms. Graph theory (L4) turns the internet into a graph of routers and links, and shortest-path algorithms (Dijkstra and Bellman-Ford) compute the best next hop inside one network. BGP (a neighbouring L3 concept) handles the harder problem between networks, where the choice follows business policy and not distance, and it fills the routers' tables with a path to every network on the internet. Ad-tech and data-platform teams meet IP when they design cloud networks (VPC address plans, route tables, peering) and debug latency across regions.
terms: IP address — a number that identifies a network interface: 32 bits in IPv4 (written 203.0.113.10) and 128 bits in IPv6.
Prefix (CIDR block) — an address range written as address/length, such as 10.1.0.0/16, where the first 16 bits are fixed and the remaining bits vary.
Router — a device that receives packets on one link and forwards each one toward its destination on another.
Forwarding table (FIB) — the table a router uses to pick the output link for each packet, mapping prefixes to next hops.
Longest-prefix match — the rule that, when several table entries match a destination, the one with the longest prefix wins.
TTL (time to live) — a counter in the header that every router decrements; at zero the packet is dropped, which stops loops.
Autonomous system (AS) — a network under one administrative policy that has its own number (ASN), such as an ISP, a cloud provider or a large company.
Control plane and data plane — the control plane builds the tables (routing protocols); the data plane uses them to forward each packet at line rate.
MTU and fragmentation — the largest packet a link carries, and the splitting of larger packets into pieces.
Default route — the entry 0.0.0.0/0 that matches every address and sends traffic toward the rest of the internet.
history: The idea of connecting different networks came from the early 1970s, when ARPANET, packet radio and satellite networks each worked differently. Vint Cerf and Robert Kahn's 1974 paper described a gateway-based design with a common address space. Jon Postel edited the specifications that fixed IPv4 in RFC 791 (September 1981), with a 32-bit address and a header of 20 bytes without options. In 1983 the ARPANET moved to IP, and in 1986 the NSFNET backbone carried it between universities.
IPv4 originally split addresses into classes: a class A network was /8 (16 million addresses), class B was /16 (65,536) and class C was /24 (256). Class B was the usual size and ran out fast, while a class C was too small, so organizations took many separate C blocks and the routing table grew quickly. By 1992 the table was on track to overflow routers' memory. The fix was CIDR (Classless Inter-Domain Routing, RFC 1519, 1993), which allowed any prefix length and let providers combine several blocks into one announcement. NAT (RFC 1631, 1994) and private ranges (RFC 1918) slowed address use. IPv6 began as a design in 1994 to 1995 and was published in RFC 2460 (1998), now RFC 8200 (2017).
Exhaustion arrived anyway: IANA allocated its last free IPv4 blocks in February 2011, and the regional registries followed (APNIC in 2011, RIPE in 2012, ARIN in 2015). IPv6 adoption has been slow. Cloudflare's 2025 review found that fewer than one third of requests to dual-stack sites used IPv6 globally, with India above two thirds. Inside networks, the routing protocols date from the 1980s: RIP (distance vector, 1988), OSPF (link state, 1991) and IS-IS, and in data centres BGP is now common (RFC 7938, 2016).
how: Every host and router keeps a table, and every packet is handled independently, with no memory of the previous one. When a host sends a packet, it first asks: is the destination in my own subnet? It compares the destination address to its own address under its subnet mask. If yes, it sends the packet directly across the link (finding the destination's MAC with ARP). If not, it sends the packet to its default gateway, the first router. From there each router looks up the destination in its forwarding table and sends the packet to the next hop. The packet's addresses never change on the way (unless NAT is applied); only the link-layer frame around it is rebuilt at every hop.
The forwarding table is a list of prefixes, each with a next hop and an output interface. More than one prefix can match a destination, because prefixes nest: 10.0.0.0/8 contains 10.1.0.0/16, which contains 10.1.2.0/24. The router must choose the most specific match, the longest prefix. This is the rule that makes aggregation work: a provider can announce one big block to the world, and a customer inside it can have a more specific route that wins locally. A default route 0.0.0.0/0 is the shortest possible match, so it is used only when nothing else fits.
The lookup must be very fast. A router with 100 Gbit/s ports sees up to about 150 million small packets per second per port, so it has a few nanoseconds per lookup. Software routers (Linux) store prefixes in a compressed binary trie (the fib_trie, a level-compressed trie after Nilsson and Karlsson) and use caches. DPDK's longest-prefix-match library uses the DIR-24-8 idea: a table directly indexed by the top 24 address bits (16 million entries) answers most lookups with one memory read, and a second small table handles prefixes longer than /24. Hardware routers use TCAM (ternary content-addressable memory), which compares the address against all entries at once and reports the best match in one cycle, at a high cost in power and chip area. This is why the size of the global routing table matters: it is on the order of a million IPv4 prefixes, and every core router must hold it in expensive memory.
Where does the table come from? Here the control plane works, using graph theory. Inside one network, a link-state protocol such as OSPF or IS-IS makes every router flood a description of its own links to all others. Each router then holds the same map (a graph with routers as vertices and links as weighted edges) and runs Dijkstra's shortest-path algorithm from itself, which costs O(E log V), then installs the first hop of each shortest path. A distance-vector protocol such as RIP runs the Bellman-Ford algorithm in a distributed way: each router tells neighbours its distances and learns from theirs. It is simpler but converges slowly and can count to infinity. When a link fails, the neighbours notice, flood the change, and all routers recompute, usually in well under a second to a few seconds.
Between networks, shortest-path is not the goal. An ISP wants to send traffic through the customer that pays it, then through free peers, and last through the provider that it pays, no matter the hop count. BGP lets each autonomous system announce "I can reach this prefix, via this path of ASNs" to its neighbours, who apply policy before passing it on. The best route is chosen first by local preference (policy), then by shortest AS path and other tie-breakers. The result fills the forwarding tables of border routers with paths to every prefix. BGP is trust-based; announcements are not checked unless RPKI route origin validation is used.
Two supporting protocols complete the picture. ICMP carries error and diagnostic messages: "destination unreachable", "time exceeded" and "fragmentation needed". The traceroute tool uses TTL on purpose: it sends packets with TTL 1, 2, 3 and so on, and each router that drops one returns an ICMP message, which reveals the path. And the path MTU issue: IPv4 routers could fragment oversized packets, but fragmentation is slow and fragile, so hosts set the Don't Fragment bit and use ICMP feedback to find the smallest MTU on the path. IPv6 forbids router fragmentation entirely, has a fixed 40-byte header, and no header checksum.

    0.0.0.0/0         192.0.2.1       eth3    (default route)

   10     -> match 10.0.0.0/8       (via eth0)   keep as best so far

example: Router R has four entries: 10.1.2.0/24 via eth2, 10.1.0.0/16 via eth1, 10.0.0.0/8 via eth0, and the default route 0.0.0.0/0 via eth3. Look up four destinations.
Destination 10.1.2.77. Its first 24 bits are 10.1.2, so it matches the /24, and also the /16 and the /8. The longest is /24, so the packet leaves on eth2. Destination 10.1.9.5. The first 16 bits (10.1) match the /16 and the /8, but 10.1.9 does not match 10.1.2, so the /16 wins: eth1. Destination 10.200.0.1. Only the /8 matches (the second byte 200 is not 1): eth0. Destination 8.8.8.8. Nothing but the default matches: eth3. The table has 4 entries but covers all 2³² addresses, because the default route catches the rest.
Subnet arithmetic uses the same bit counting. A /24 has 32 − 24 = 8 free bits, so 2⁸ = 256 addresses (254 usable hosts in classic subnets, since the first is the network address and the last the broadcast). A /16 has 65,536 addresses. In an AWS VPC, a /28 subnet has 16 addresses, of which AWS reserves 5, leaving 11 for your instances; a VPC with 10.0.0.0/16 divided into /20 subnets gives 2⁴ = 16 subnets of 4,096 addresses. Overlapping prefixes between two VPCs make peering impossible, because routes would be ambiguous, so plan blocks before building.
Traceroute shows the TTL mechanism. You send a probe to a server with TTL = 1. The first router decrements it to 0, drops the packet and returns an ICMP "time exceeded" message from its own address; that is hop 1, and the round-trip time is measured. Then TTL = 2 reaches the second router, and so on. If the path has 12 routers, the tenth probe's reply is from the tenth router and the thirteenth probe reaches the server. A typical path from India to a US East Coast server has 12 to 20 hops and a round-trip time of roughly 200 to 250 ms, of which most is the speed of light in fibre (about 5 µs per km one way over 13,000 km or more of cable, which gives roughly 130 ms round trip as a physical lower bound).
intuition: Each post office needs to know only which neighbouring office is closer to the destination, not the whole route, and the most specific address on its list wins.
This works because the decision is local and the table is small compared with the world. A router does not need a map of the path; it needs one correct next step, and if every router takes a correct next step, the packet arrives. Prefixes let one entry stand for millions of addresses, so tables stay manageable, and "longest match" lets exceptions override general rules without any special mechanism. The scheme tolerates failure because there is no setup state: when a link dies, the next packet simply takes a different next step.
mistakes: People often think a packet follows a fixed path decided by the sender. In fact each router decides independently, and two packets of the same connection can take different paths (ECMP hashes by flow to avoid this, but a route change can still move a flow). Packets can arrive out of order, which TCP and QUIC expect.
People often think the IP address changes along the path. In fact source and destination addresses stay the same from end to end, except where NAT rewrites them. What changes at each hop is the link-layer frame (MAC addresses) and the TTL.
People often think IP guarantees delivery, or that a lost packet is reported. In fact IP is best effort. Routers drop packets when queues are full or TTL expires, and often no one is told (ICMP messages are optional and rate-limited, and are often blocked). Reliability is the job of TCP or the application.
People often think the shortest path (fewest hops) is always chosen across the internet. In fact between networks BGP picks by policy first: money and agreements. A route with fewer hops can lose against one through a preferred customer or peer, so the path to a nearby server may leave the country.
friction: The big problems are in the control plane. BGP trusts announcements, so a misconfiguration or malicious announcement can pull traffic to the wrong place (a route leak or hijack): in 2008 Pakistan Telecom's attempt to block YouTube spread globally and took YouTube offline for about two hours, and mistakes at large providers still cause outages every year. RPKI lets owners sign which AS may announce a prefix, and a growing share of the table is covered, but it validates only the origin, not the full path, and it is not deployed everywhere. Convergence after failure is not instant: a BGP withdrawal can take tens of seconds to minutes to settle across the internet.
Scale and exhaustion are the second problem. The IPv4 table holds on the order of a million prefixes because many networks announce separate small blocks for traffic engineering, and each needs expensive TCAM. Address scarcity pushed the whole internet behind NAT and carrier-grade NAT, which breaks end-to-end connectivity and complicates peer-to-peer and logging (many users share one public address, and the log shows only the shared one). IPv6 solves it but dual operation doubles the work: two address plans, two sets of firewall rules, and a slow tail of services that cannot use it.
Operationally, ICMP filtering breaks path MTU discovery, producing the black hole where small requests work and large responses hang. Equal-cost multipath can send one flow's packets over different paths if hashing changes, causing reordering. Asymmetric routing (the return path differs from the forward path) confuses stateful firewalls and makes traceroute misleading. IP also gives no security: addresses can be forged (spoofed), which makes UDP amplification attacks possible unless networks filter at the edge (BCP 38).
tradeoffs: Choose static routes and a default route when the network is small and its shape rarely changes: they are predictable and need no protocol. Choose a dynamic protocol (OSPF or IS-IS inside a site, BGP between sites and in large data centres) when you have many links, redundancy, or frequent change. You pay with convergence behaviour, protocol bugs and more to monitor; a typical rule is to adopt a dynamic protocol once you have more than a handful of routers.
Choose BGP in the data-centre fabric (as large operators do, RFC 7938) for its simple, well-understood policy and stability at tens of thousands of nodes, and choose OSPF or IS-IS when the fabric is small and you value fast shortest-path computation and a single flat view. BGP converges more slowly but isolates failures better.
Choose large, simple address blocks with careful aggregation in a cloud design (for example a /16 per VPC split into /20 subnets), and avoid overlap with on-premise ranges. Small blocks save addresses but are painful to grow, since AWS cannot enlarge a subnet; large blocks cost nothing in IPv4 private space but make peering hard if two teams pick overlapping ranges.
Choose IPv6 (or dual stack) for new public services and for very large internal clusters where private IPv4 space would run out, for example Kubernetes with many pods. Stay on IPv4 with NAT when your dependencies (vendors, on-premise firewalls) do not support IPv6 and the address space suffices. The cost of dual stack is double the configuration and testing.
practice: Learn to read a routing table (ip route, ip route get 10.1.2.77 shows which route would be used) and the AWS equivalent: each subnet's route table, where the most specific route wins just as in IP, and the local route always wins for traffic inside the VPC. Plan address space once and write it down: a non-overlapping block per VPC, environment and region, leaving room (the common mistake is a /24 per VPC that runs out of IPs when containers arrive). Reserve 5 addresses per AWS subnet in your capacity calculation.
Use ping for reachability and round-trip time, traceroute or mtr for the path and the place where loss starts (remember that a hop which does not answer ICMP may still forward traffic well), and tcpdump to prove packets leave and arrive. For problems that appear only with large payloads, test the path MTU with ping -M do -s 1472 (1,472 bytes of data plus 28 bytes of headers equals 1,500). Allow ICMP types 3 (destination unreachable, including "fragmentation needed") and 11 (time exceeded) through firewalls.
For services, prefer DNS names to hard-coded IPs, since addresses change. Use RPKI-aware transit and check that your own prefixes have valid ROAs if you announce any. Monitor with BGP looking glasses (RIPE RIS, bgp.tools) when a region becomes unreachable, because many "cloud outages" begin as routing events.
interview: A packet from client to server crosses 14 routers. Explain exactly what each router does and what changes. || It strips the link-layer header, checks the IP header and decrements TTL, looks up the destination with longest-prefix match to get a next hop and interface, updates the header checksum (IPv4), builds a new link-layer frame for the next hop, and queues it. Source and destination IPs do not change (except NAT); TTL and MAC addresses do.
Why longest-prefix match and not exact match, and how do routers do it fast? || Prefixes aggregate millions of addresses into one entry, and the more specific entry must override the general one. Exact match would need a table of billions. Routers use TCAM in hardware, or compressed tries and direct-index tables like DIR-24-8 in software, to find the longest match in a few memory accesses.
How does traceroute work, and why might a hop show stars while traffic flows fine? || It sends probes with increasing TTL and reads the ICMP time-exceeded replies. A router may rate-limit or filter ICMP, or reply from a control-plane CPU that is slow, so stars do not prove loss; look at whether later hops respond.
Two VPCs must connect but both use 10.0.0.0/16. What are your options? || Overlapping ranges make direct peering and routing ambiguous. Options: renumber one VPC (best, but hard once populated), use NAT or a proxy between them for specific services, or expose services through private link endpoints that do not need routing between ranges.
What happens when a BGP route is hijacked, and what can be done to limit it? || A more specific or falsely originated announcement attracts traffic to the attacker, because routers prefer the longest prefix. Mitigations are RPKI origin validation with ROAs, filtering customer announcements, announcing your own prefixes with the narrowest sensible length, and monitoring.
Why does IPv6 remove router fragmentation, and what does it mean for applications? || Fragmenting at routers is slow, wastes state and enables attacks. In IPv6 only the sending host fragments, after learning the path MTU through ICMPv6. So applications must keep packets below the path MTU (1,280 is the guaranteed minimum), and blocking ICMPv6 breaks connectivity.
quiz: Which entry wins for destination 10.1.2.5 if the table has 10.0.0.0/8, 10.1.0.0/16 and 0.0.0.0/0? || The /16 entry, because it is the longest prefix that matches (the first 16 bits, 10.1, match; the /8 matches too but is shorter, and the default is shortest).
Why does a packet have a TTL field? || Each router decrements it and drops the packet at zero, so a routing loop cannot circulate packets forever. Traceroute also uses it to discover the path.
How many addresses does 172.16.0.0/20 contain, and what is its last address? || 32 − 20 = 12 free bits, so 4,096 addresses. The range runs from 172.16.0.0 to 172.16.15.255.
Why can't BGP simply pick the shortest path like OSPF? || Between independent companies, routing follows commercial policy: prefer customers (who pay), then peers (free), then providers (who are paid). Hop count is only a tie-breaker. Each network also hides internal topology.
Why did CIDR replace classful addressing in 1993? || Classes forced either too large (class B) or too small (class C) blocks, which exhausted addresses and bloated the routing table. CIDR allows any prefix length and lets providers aggregate many blocks into one announcement.

@@ congestion
value: Congestion control is how thousands of senders share a network without any of them knowing how many others exist. The network never tells a sender its fair share. Instead each sender probes: it raises its sending rate until it sees a sign of overload (a lost packet, a rising delay, or a mark from a switch), then lowers it. Done by every sender with the same rules, this keeps links busy and shares them roughly fairly.
Without it, the internet fails badly. In October 1986 the link between Lawrence Berkeley Laboratory and UC Berkeley, 400 yards apart, dropped from 32 kbit/s to 40 bit/s, about a thousand times lower. Senders kept retransmitting lost packets, which made the overload worse, so the network spent its capacity on copies that were also dropped: congestion collapse. Van Jacobson's 1988 fix is still the base of TCP. Today the same feedback idea appears in Kafka producer backpressure, API rate limiting and autoscalers.
For the layer above, TCP's sending speed is whatever its congestion-control algorithm allows: Reno and CUBIC grow a window until loss, BBR models the path, and data-centre variants use switch marks. The layers below supply the reasoning. Control theory (L4) says each sender is a controller with delayed feedback, and explains the sawtooth and the risk of oscillation. Queueing theory and Little's law (L4) explain why delay grows as a queue builds, which is the early signal that BBR and Vegas use. Optimization (L4) frames fair sharing as maximizing total utility, and shows that simple additive-increase rules solve that problem without central control.
terms: Congestion window (cwnd) — the maximum amount of unacknowledged data a TCP sender may have in the network, in bytes or segments.
Bandwidth-delay product (BDP) — bottleneck rate multiplied by round-trip time; the amount of data needed in flight to keep the link full.
Slow start — the opening phase in which cwnd doubles every round trip until the first loss or a threshold.
AIMD — additive increase, multiplicative decrease: add a small amount per round trip, cut by a fraction on congestion.
Round-trip time (RTT) — the time from sending a packet to receiving its acknowledgment.
ECN — explicit congestion notification, in which a router sets a bit in a packet header instead of dropping it when its queue grows.
Bufferbloat — excess queueing delay caused by very large buffers that fill up before any loss occurs.
Pacing — spreading packets evenly in time instead of sending a whole window as a burst.
Goodput — useful data delivered per second, excluding retransmissions.
Congestion collapse — a state in which the network is busy but delivers almost no useful data, because most traffic is retransmitted copies.
history: John Nagle described congestion collapse in a 1984 memo (RFC 896) after seeing it in the early IP networks of the time. The real event came in October 1986, when the ARPANET and the Berkeley-area networks collapsed. Van Jacobson, then at Lawrence Berkeley Laboratory, traced it to TCP senders that sent a full window at once, and retransmitted on a timer that was too short. His paper "Congestion Avoidance and Control" (SIGCOMM 1988, with Karels' implementation in 4BSD) added slow start, congestion avoidance with additive increase and multiplicative decrease, a better round-trip timer that includes variance, and the principle of "conservation of packets": a new packet enters only when an old one leaves, so acknowledgments clock the sender. Fast retransmit and fast recovery followed in 1990 (Reno).
The theory came next. Chiu and Jain (1989) proved that AIMD converges to a fair and efficient allocation, while other combinations (additive increase with additive decrease) do not. Kelly, Maulloo and Tan (1998) showed that rate control can be read as a distributed solution to a utility-maximization problem, with congestion signals acting as prices. Brakmo and Peterson's Vegas (1994) used delay, and not loss, as the signal.
As links became faster, loss-based Reno became too slow to recover, so new algorithms appeared: FAST, HighSpeed TCP and CUBIC (Ha, Rhee and Xu, 2008; Linux default from 2006; standardized as RFC 9438 in August 2023). Bufferbloat, named by Jim Gettys in 2010 to 2011, led to CoDel (Nichols and Jacobson, 2012). Data centres got DCTCP (Alizadeh et al., SIGCOMM 2010), using ECN marks. In 2016 Google published BBR (Cardwell, Cheng, Gunn, Yeganeh and Jacobson), which builds a model of the path and does not wait for loss; later versions (BBRv2, then v3 in 2023) added reaction to loss and ECN for fairness. QUIC reuses the same algorithms in user space.
how: A TCP sender is limited by a window: at most min(cwnd, receiver window) bytes may be unacknowledged. The receiver window protects the receiver's buffer (flow control). The congestion window protects the network, and the sender must estimate it, because the network gives no number. Because the sender releases new data when ACKs come back, the sending rate is about cwnd ÷ RTT. A window equal to the bandwidth-delay product keeps the link exactly full. A smaller window leaves it idle; a larger window only fills the queue at the bottleneck.
Classic Reno-style control has three parts. In slow start, cwnd starts small (10 segments is standard since RFC 6928) and grows by one segment per ACK, which doubles it each round trip, until loss or until it reaches a threshold (ssthresh). In congestion avoidance, it grows by about one segment per round trip: this is the additive increase. When loss is detected by three duplicate ACKs, the sender sets ssthresh and cwnd to half of the current cwnd (multiplicative decrease) and retransmits; when the retransmission timer fires, it assumes heavy loss and restarts from a small window. Chiu and Jain's result explains why this pair is right: additive increase moves two flows' rates in parallel (keeping their difference), while multiplicative decrease shrinks the difference, so rates converge toward equal shares while total load oscillates around capacity.
The control-theory view explains the sawtooth. The sender is a controller; the network is a plant with a delay of one RTT; the congestion signal is a delayed measurement. Because feedback arrives a full RTT late, the sender cannot react instantly and always overshoots a little. The queue at the bottleneck acts as an integrator: when input exceeds capacity, queue length grows linearly. With a buffer of one BDP, Reno's cwnd swings between 1 BDP and 2 BDP and the link never goes idle; with smaller buffers, utilization drops. Queueing theory gives the delay side: by Little's law, the number of packets in the queue equals arrival rate times waiting time, so a standing queue of 1 MB at 100 Mbit/s is 80 ms of added delay for every flow that shares it. Loss-based control tends to fill any buffer until it overflows, so large buffers mean large delay.
At high speed, additive increase is too slow, since recovery takes one round trip per segment lost from the window. CUBIC replaces the line with a cubic function of time since the last loss: after a loss it cuts the window to 70% (not 50%), then grows fast, flattens near the old maximum Wmax to probe gently, and then speeds up again. Because it depends on elapsed real time, not on RTT, flows with different round-trip times share more evenly than in Reno.
BBR starts from a different question: what are the bottleneck bandwidth and the minimum RTT? It measures the delivery rate (the maximum over the last ~10 round trips) and the smallest RTT seen (over the last ~10 seconds), sends at the estimated bandwidth with pacing, and caps data in flight at about 2 × BDP. It cycles through phases: it probes by sending 25% faster for one RTT to see if more bandwidth exists, then 25% slower to drain any queue it made, and every ~10 seconds it cuts the window to 4 packets for ~200 ms to re-measure the true RTT. Loss alone does not make it back off, which helps on lossy paths and keeps queues short, but it caused unfairness against CUBIC and high retransmission rates in version 1.
In data centres, switches mark packets with ECN as soon as the queue passes a small threshold. DCTCP senders track the fraction of marked packets α (smoothed over time) and cut the window by α/2: a gentle cut for light congestion and a deep cut only if all packets are marked. This keeps queues at tens of microseconds instead of milliseconds.
A few details complete the picture. The sending rate is not only cwnd ÷ RTT: if a sender releases a whole window as one burst, the burst itself fills a switch queue, so modern stacks pace packets evenly over the round trip (Linux does this with the fq scheduler or in the TCP stack). Retransmission timers use a smoothed RTT plus four times its variance, and double after each timeout (exponential backoff), the same idea Ethernet uses for collisions. For ECN, the router sets a mark bit instead of dropping, the receiver echoes it, and the sender reacts as if one packet was lost, but without losing data; the newer L4S scheme lets senders react in proportion to the number of marks. Finally, the algorithm only controls one connection: the total load on a link is the sum of all senders, so fairness is among flows, not users.

example: A link has 100 Mbit/s and a base RTT of 40 ms. Segments are 1,460 bytes (MSS).
Step 1, the BDP. 100 Mbit/s × 0.040 s = 4 Mbit = 500,000 bytes, about 342 segments. This is how much must be in flight to fill the link.
Step 2, slow start. With an initial window of 10 segments: 10, 20, 40, 80, 160, 320 across successive round trips. It needs about 5 round trips (200 ms) to reach roughly the BDP. A web response of 100 KB (about 69 segments) needs 10 + 20 + 40 = 70 segments, so 3 round trips (120 ms) after the handshake, and never fills the link. For short transfers, latency, not bandwidth, decides.
Step 3, Reno after a loss. Suppose the buffer holds one BDP. The window peaks at about 684 segments (BDP plus a full buffer) and a loss halves it to 342. Growing by one segment per round trip, it takes 342 round trips to come back: 342 × 40 ms ≈ 13.7 seconds. Now take a long, fast path, 10 Gbit/s with 100 ms RTT: the BDP is 125 MB, about 85,600 segments. After a halving, Reno needs about 42,800 round trips, which is 4,280 seconds, over an hour, to recover. That is why Reno cannot fill fast long paths, and why CUBIC and BBR exist. Mathis' formula shows the same thing: rate ≈ (MSS ÷ RTT) × 1.22 ÷ √p. For MSS 1,460 bytes, RTT 40 ms and loss rate p = 0.01% (10⁻⁴): 11,680 bits ÷ 0.04 s = 292 kbit/s, times 1.22 ÷ 0.01 = 122, gives about 35.6 Mbit/s. To reach 100 Mbit/s the loss rate must be below about 1.3 × 10⁻⁵, which is one packet in 79,000.
Step 4, queue delay. If the sender keeps 1 MB queued at the 100 Mbit/s bottleneck, every packet waits 1 MB × 8 ÷ 100 Mbit/s = 80 ms, doubling the RTT from 40 ms to 120 ms. A delay-based or model-based sender (Vegas, BBR) would notice the RTT rising above its minimum and stop adding to the queue; Reno and CUBIC only notice when the buffer overflows.
intuition: Drive faster until you see brake lights, then ease off sharply, and speed up again slowly; everyone doing the same keeps the road full without a traffic controller.
It is natural because no one can know the capacity, but everyone can measure the effect of their own sending. Probing upward slowly is cheap if wrong, and backing off sharply removes the overload quickly, so the asymmetry (slow up, fast down) comes from the fact that overload hurts everyone, while spare capacity wastes only a little. Fairness comes for free: if two cars brake by the same fraction and accelerate by the same amount, the faster one loses more speed each time and they drift together.
mistakes: People often think congestion control is the same as flow control. In fact flow control (the receiver window) protects the receiver from being overrun, and congestion control protects the network. TCP obeys the smaller of the two windows.
People often think a bigger buffer in a router or a bigger socket buffer always improves throughput. In fact large buffers hide congestion: loss-based senders fill them, delay climbs to hundreds of milliseconds (bufferbloat), and interactive traffic suffers while throughput does not improve. Buffers of about one BDP (or less, with many flows) are enough.
People often think loss always means congestion. In fact on Wi-Fi, cellular and some long-distance links, packets are lost for other reasons, and a loss-based sender then slows down needlessly. That is a main reason BBR and other model-based methods exist.
People often think BBR or CUBIC is simply better than Reno. In fact each has weak points. CUBIC fills buffers. BBR version 1 shared bandwidth unfairly with CUBIC flows and ignored moderate loss. A better choice depends on the path and on who shares it.
People often think the internet's fairness is per user. In fact it is per flow: a program that opens 20 parallel connections gets about 20 times the share of one that opens one, which is why browsers and download tools limit connections, and why HTTP/2 and QUIC use one connection with many streams.
friction: Congestion control works only if everyone cooperates, and nothing enforces it. A sender that does not back off can take bandwidth from others, and different algorithms sharing one queue (CUBIC and BBR) can be unfair in either direction. The loss signal is noisy on wireless links, ECN is not yet deployed everywhere, and delay is noisy on shared links, so every signal has a failure mode.
Short flows are not helped at all. Most web objects finish within slow start, so they never reach the steady state that these algorithms optimize; the initial window and the handshake round trips matter more. In data centres, incast and microbursts arrive faster than any end-to-end feedback loop of one RTT can react, so switch buffering, ECN thresholds and application-level limits matter. For AI training networks, a small number of very large flows (elephants) collide on the same ECMP path, which standard congestion control does not fix; this is a reason for new transports.
Finally, congestion control interacts with everything. A rate limiter on top of TCP can cause bursts and timeouts; pacing needs timers with fine resolution; a middlebox that splits the connection (a performance-enhancing proxy) hides the real path; and the algorithm runs on the sender, so for a download the server operator sets the policy.
tradeoffs: Choose CUBIC (the Linux default) for general traffic on the public internet when you want a proven, widely tested algorithm that shares fairly with other CUBIC flows and works well on high-BDP paths. Its cost is that it fills buffers, so latency under load is high on bloated paths, and it reacts to random loss.
Choose BBR when your paths are long, lossy or shallow-buffered and you care about throughput and latency under load, such as video delivery to mobile users or cross-region transfers. Google reported large throughput gains on lossy long-haul paths. You give up predictable coexistence: BBR can take more than its share against CUBIC, so test on your own paths, and prefer v3 where available.
Choose DCTCP or another ECN-based scheme inside a data centre you control, where switches support ECN and all flows use it. You get queue delays of tens of microseconds and less incast loss. You give up compatibility with traffic leaving the data centre, and it requires switch configuration on all hops.
Choose larger initial windows and connection reuse (or HTTP/2, QUIC) for short, latency-sensitive transfers: more of the first round trips carry data. The risk is more burst loss on slow links.
Choose the application-level limit (bounded in-flight requests, backpressure, rate limits) as well as transport control for batch pipelines: TCP controls the network, not your downstream consumer, and an unbounded queue in the application just moves the bloat from the router to your heap.
practice: Check which algorithm a Linux host uses: sysctl net.ipv4.tcp_congestion_control (usually cubic) and see the available ones in net.ipv4.tcp_available_congestion_control. Per-connection state is visible with ss -ti, which prints cwnd, rtt, retransmissions and pacing rate; if cwnd is small and retransmits are high, congestion is the problem, not the application. Switching to BBR is one sysctl on modern kernels (older ones also need the fq queueing discipline for pacing); try it on a canary, and compare throughput and retransmits, not just speed tests.
For transfers across regions (Kafka MirrorMaker, Spark writing to remote object storage, large file copies), the BDP is large. Use several parallel streams only after raising the buffer limits (net.ipv4.tcp_rmem and tcp_wmem maximums) to at least one BDP (about 6 MB for 1 Gbit/s and 50 ms), because a window cap, not congestion, often limits long-haul throughput. Keep connections open to avoid repeating slow start.
Inside your own services, apply the same control idea: put bounds on queues, shed or slow down when latency rises (AIMD-style concurrency limits as in Netflix's concurrency-limits library), and give clients retry rules with exponential backoff and jitter so a failure does not cause a retry storm. On AWS, remember that instance network limits and per-flow caps (about 5 Gbit/s per single flow, or 10 Gbit/s inside a cluster placement group) matter more than the algorithm.
interview: Explain AIMD and why it converges to fairness. || Each flow adds a fixed amount per round trip and multiplies its rate by a fraction (for example 0.5) on congestion. Additive increase keeps the gap between two flows, multiplicative decrease halves the gap, so repeated cycles move them toward equal rates while the total oscillates around capacity (Chiu and Jain, 1989).
Why does Reno underuse a 10 Gbit/s, 100 ms path, and how do CUBIC and BBR address it? || After a loss, additive increase needs about half a BDP in round trips to recover, which is tens of thousands of RTTs, and a loss rate of even 10⁻⁶ limits throughput (Mathis). CUBIC regrows with a cubic function in real time and reduces by 30%, and BBR ignores isolated loss and paces at the measured bottleneck bandwidth.
Your service shows 300 ms latency under load but low CPU. How do you tell whether bufferbloat is the cause? || Compare RTT under load with idle RTT (ping, or ss -ti rtt values, or a test such as a loaded-latency test). If RTT grows by hundreds of milliseconds while throughput is flat, a standing queue exists. Fix with smaller or smarter queues (fq_codel), pacing, or a delay-aware algorithm like BBR.
Why is loss a bad congestion signal on Wi-Fi, and what is better? || Radio errors drop packets that have nothing to do with queue overflow, so loss-based senders slow down needlessly. Better signals are measured delivery rate and RTT (BBR), or explicit marks from the network (ECN, L4S).
How would you design backpressure for a pipeline that is slower downstream than upstream? || Use bounded queues and propagate the signal upstream: when the queue is full, producers block or slow down (Kafka's buffer.memory and max.block.ms, reactive streams demand), plus rate limiting and retry with backoff. This is the same loop as TCP: measure overload, reduce rate sharply, increase slowly.
quiz: What are the two phases of Reno's window growth? || Slow start doubles the window each round trip until loss or ssthresh. Congestion avoidance then adds about one segment per round trip. A loss halves the window.
Why does a standing queue at the bottleneck hurt latency but not raise throughput? || The link is already fully used, so extra queued packets only wait. Queue delay equals queued bytes divided by link rate, for example 1 MB at 100 Mbit/s is 80 ms.
What is the BDP of a 1 Gbit/s link with 20 ms RTT, and why does it matter? || 1 Gbit/s × 0.02 s = 20 Mbit = 2.5 MB. A TCP sender needs a window of at least this size to fill the link, so socket buffers must allow it.
Why does CUBIC share better between flows of different RTTs than Reno? || Reno grows one segment per RTT, so short-RTT flows grow faster and get more. CUBIC's growth depends on time since the last loss, not on RTT, so flows with different RTTs grow at similar rates.
When should you prefer BBR over CUBIC, and what is the risk? || Prefer BBR on long, lossy or shallow-buffered paths where throughput and latency matter. The risk is unfairness to other flows and higher retransmissions in older versions, so test on your own paths.

@@ quic
value: UDP is the simplest transport on the internet: it adds port numbers and a checksum to IP and nothing else. No connection, no retransmission, no ordering. QUIC is a modern transport protocol built on top of UDP that adds everything TCP provides (reliable delivery, ordering, flow control, congestion control) plus built-in encryption (TLS 1.3) and many independent streams in one connection. It is the base of HTTP/3 and is supported by all major browsers, CDNs and many cloud load balancers.
It exists because TCP could no longer be improved. TCP lives in operating-system kernels, which update slowly, and its header is readable and rewritable by every NAT, firewall and load balancer on the path, so any change risks breakage (ossification). Running over UDP in user space lets an application update its transport as fast as it ships software, and encrypting almost the whole header keeps middleboxes from depending on it. The result removes a round trip from connection setup, stops one lost packet from stalling unrelated requests, and lets a connection survive a change of network.
For the layer above, HTTP/3 maps each request to a QUIC stream. The layers below supply the parts. IP and routing carry the UDP datagrams, and set the packet-size budget (QUIC assumes at least 1,200 bytes). Authenticated encryption (AEAD, L3) protects every packet and its header fields, so tampering is detected. Control theory (L4) shows up in loss recovery and congestion control, which are feedback loops: QUIC moves them out of the kernel into the library, so they can be changed per application. Ad-tech and video teams see QUIC mostly through CDNs: the first byte arrives sooner on poor mobile networks.
terms: UDP — a transport protocol that sends independent datagrams with ports and a checksum, with no delivery guarantee.
Stream — an ordered, reliable byte sequence inside a QUIC connection; many streams share one connection and fail independently.
Connection ID — an identifier in each QUIC packet that names the connection, so it survives changes of IP address and port.
Head-of-line blocking — a delay in which data behind a missing item must wait for it, even if the data is unrelated.
0-RTT — sending application data in the first flight of a resumed connection, before the handshake finishes.
Connection migration — continuing a connection after the client's network address changes.
Packet number — a counter on every QUIC packet that is never reused, even for retransmitted data.
Frame — a typed unit inside a QUIC packet, such as STREAM, ACK, CRYPTO or MAX_DATA.
Ossification — the loss of protocol flexibility because middleboxes assume the current wire format.
Amplification limit — the rule that a server may not send more than 3 times the bytes it has received from an unverified address.
history: UDP is old: Jon Postel specified it in RFC 768 in 1980 as a minimal way for programs to send datagrams. For decades it carried DNS, DHCP, NTP and real-time media, while TCP carried the web. By the late 2000s the web's problems were visible. HTTP/1.1 needed many TCP connections per page; SPDY (Google, 2009) and HTTP/2 (2015) multiplexed requests over one TCP connection, but then a single lost packet delayed every request. Attempts to change TCP, such as TCP Fast Open, were slow to deploy and failed in many networks that dropped unknown options.
Jim Roskind at Google started QUIC in 2012 ("Quick UDP Internet Connections", though the IETF later said the name is not an acronym). It was enabled in Chrome in 2013 against Google servers. By the 2017 SIGCOMM paper by Langley and colleagues, QUIC carried over 30% of Google's egress traffic, about 7% of internet traffic, and reduced search latency and YouTube rebuffering, mostly on poor networks. The IETF formed a working group in 2016 and redesigned the protocol, replacing Google's own crypto with TLS 1.3 and splitting out HTTP/3. The core RFCs appeared in May 2021: RFC 9000 (transport), 9001 (TLS) and 9002 (loss detection and congestion control). HTTP/3 followed as RFC 9114 in June 2022, with QPACK header compression in RFC 9204. QUIC version 2 (RFC 9369) exists mainly to prove that versioning works and to keep the protocol from freezing.
Today QUIC carries more than the web: DNS over QUIC (RFC 9250), the WebTransport API, SMB file sharing over QUIC in Windows, proxying (MASQUE), and the Media over QUIC work for live video. Library implementations include Google's quiche, Microsoft's MsQuic, ngtcp2, quic-go, Quinn and Cloudflare's quiche.
how: A QUIC connection starts with a handshake that carries TLS 1.3 inside it. The client's first packet (an Initial, padded to at least 1,200 bytes) holds a TLS ClientHello in a CRYPTO frame. The server replies with its own Initial (ServerHello) and Handshake packets (certificate, finished). After one round trip, both sides have 1-RTT keys, and the client can send requests. TCP plus TLS 1.3 needs two round trips before the first request: one for the TCP handshake and one for TLS. QUIC merges them. For a repeat visit, the client holds a session ticket and may send a request in its very first flight (0-RTT), which the server can answer in the first round trip. 0-RTT data can be replayed by an attacker, so servers should accept only idempotent requests in it, such as GET.
Every packet is protected. QUIC uses an AEAD cipher (AES-GCM or ChaCha20-Poly1305) with keys from the TLS handshake. The packet number goes into building the nonce, and the header is authenticated as additional data, so changing any bit fails the tag check. A second step, header protection, masks the packet number and some flags with a key derived from a sample of the ciphertext. The visible header is mostly the connection ID and a few flags; there is no sequence number, no acknowledgment and no window that a middlebox can read or modify. The Initial packets use keys derived from the destination connection ID with a public salt, which only obscures them; the real secrecy starts after the handshake.
Inside the encrypted packet are frames. A STREAM frame carries bytes of one stream with an offset. An ACK frame lists ranges of received packet numbers. MAX_DATA and MAX_STREAM_DATA implement flow control, per connection and per stream. Stream IDs encode who started the stream (client or server) and whether it is bidirectional or one-way. A client opens as many streams as it likes; each is an ordered byte sequence, but different streams are independent, so a gap in stream 4 does not hold back stream 8. This removes the head-of-line blocking of HTTP/2 over TCP, where all streams share a single ordered byte stream.
Loss recovery is simpler than in TCP because packet numbers are never reused. If a packet is lost, its frames are put into a new packet with a new number. The sender therefore never confuses an acknowledgment of the original with one of the retransmission, which makes RTT samples cleaner, an ambiguity TCP has to work around. A packet is declared lost if later packets were acknowledged (a threshold of 3 packets) or if a time threshold (about 9/8 of the RTT) has passed; a probe timeout sends a probe when acknowledgments stop. Congestion control uses the usual algorithms: RFC 9002 describes a NewReno-style controller, and implementations offer CUBIC and BBR. Because this lives in user space, a CDN can tune it per customer, and researchers can try new algorithms without waiting for kernels.
Connection IDs let a connection move. When a phone leaves Wi-Fi for mobile data, its source address changes; a TCP connection is identified by the four-tuple of addresses and ports and breaks. A QUIC server finds the connection from the ID, and checks the new path with a PATH_CHALLENGE/PATH_RESPONSE exchange (so an attacker cannot redirect the traffic), then continues. The client switches to a new connection ID on the new path so that observers cannot link the two. Load balancers can also encode routing information into the connection ID to keep a connection on the same backend.
HTTP/3 uses these pieces directly. Each request and response is one bidirectional QUIC stream, so the browser can open hundreds without extra handshakes. Three one-way streams are reserved: a control stream for settings, and two for QPACK, the header compression scheme, which (unlike HTTP/2's HPACK) is designed to survive reordering between streams. Several small frames can be packed into one packet, and several packets can be coalesced into one UDP datagram during the handshake. Packet size is kept at or below the path limit: QUIC refuses to start on paths that cannot carry a 1,200-byte UDP payload, which also fits inside the IPv6 minimum MTU of 1,280, and it probes upward with datagram path MTU discovery. The IP layer is used exactly as it always was; QUIC does not need any router to know about it.

example: A phone on a mobile network has an RTT of 80 ms to a CDN and loads a page with 20 objects over one connection.
Setup. With TCP and TLS 1.3, the TCP handshake takes 80 ms and the TLS handshake another 80 ms, so the first request leaves at 160 ms and the first response byte arrives at 240 ms. (With TLS 1.2 it would be 240 ms and 320 ms.) With QUIC, the request leaves at 80 ms and the first response byte arrives at 160 ms. On a return visit with 0-RTT, the request leaves at 0 ms and the response begins at 80 ms. The saving of 80 to 160 ms is large next to a page-load budget of one or two seconds.
Head-of-line blocking. The 20 requests share one connection. Suppose packet 57 is lost and it carried part of image 7, while packets 58 to 70 carry other images and are received. With HTTP/2 over TCP, the kernel cannot deliver bytes after the gap to the application until packet 57 is retransmitted, so every stream stalls. Detection by three duplicate ACKs takes about one RTT, and the retransmission arrives about one more half RTT later, so all 20 objects wait about 80 to 120 ms. With QUIC, packets 58 to 70 contain frames of other streams, which are delivered at once. Only image 7 waits for the retransmission. At 2% packet loss, which is common on poor mobile links, this happens often during a page load.
Migration. The user walks out of Wi-Fi range and the phone switches to cellular with a new IP address. With TCP the old connection dies; the app must reconnect, costing 160 ms of handshakes at least plus a new slow start, and any in-flight request fails. With QUIC the next packet comes from the new address with the same connection ID. The server sends a path challenge, receives the response one round trip later (80 ms), and the downloads continue, keeping their congestion state in most cases (some implementations reset it for the new path).
intuition: Several independent conveyor belts in one sealed tunnel, instead of a single belt where one jammed box stops everything behind it.
The design is natural once you ask where to put what. The things that must be fast to change (loss recovery, congestion control, stream scheduling) go in the application library. The things that must be stable for the network (IP and UDP) stay in the kernel and on the path. Encrypting the header makes that boundary firm: the network sees only that a UDP packet exists. Putting TLS inside the transport removes a round trip because both secrets and transport parameters are agreed in one exchange.
mistakes: People often think QUIC is unreliable because it uses UDP. In fact UDP is only the envelope. QUIC does its own acknowledgments, retransmission, ordering within each stream, flow control and congestion control, and it is as reliable as TCP.
People often think QUIC is always faster than TCP. In fact the gains are largest on high-latency or lossy paths and for short or multi-object transfers. On a fast, clean data-centre network, kernel TCP with offloads often uses less CPU and can be faster, so many internal services stay on TCP.
People often think 0-RTT is free. In fact early data has no replay protection, and the server cannot tell a replayed request from a new one. Using it for non-idempotent actions (a payment, a POST that creates an order) is unsafe. It also gives weaker forward secrecy for that first flight.
People often think QUIC avoids congestion control, so it can send as fast as it likes. In fact it must use a congestion controller, and RFC 9002 requires one that is fair to TCP. Some early deployments tuned aggressively, but the protocol expects a standard controller.
People often think encrypted headers mean operators can see nothing. In fact they can still see addresses, ports, packet sizes and timing, and a "spin bit" in the header is an optional signal that lets on-path observers estimate RTT. What they lose is easy access to sequence numbers and losses.
friction: QUIC costs more CPU per byte than kernel TCP, especially on servers. Encryption is per packet, UDP lacks mature offloads on many NICs, and packets cross the kernel boundary one datagram at a time unless batching is used. Large operators report significantly more CPU for the same HTTP traffic and invest in GSO/GRO, io_uring, kernel-bypass and hardware offload. Linux's UDP socket buffers also need raising (net.core.rmem_max) or the kernel silently drops bursts.
Network reachability is imperfect. Some corporate networks and a share of consumer networks block or throttle UDP on port 443, and some routers apply poor UDP NAT timeouts (30 seconds or less), killing idle connections. Clients therefore race or fall back to TCP, so a service must keep running both HTTP/2 and HTTP/3, and discovery relies on Alt-Svc or the HTTPS DNS record (RFC 9460) because the first connection usually starts on TCP.
Operations are harder. Encrypted headers remove tools that read TCP state from the wire; debugging needs qlog output and key logs on the endpoints. Load balancing needs connection-ID-aware routing, because the four-tuple no longer identifies a connection. DDoS defence has fewer signals. The ecosystem is young, with many implementations at different levels of quality, and subtle bugs in loss recovery and flow control still appear. Finally, QUIC's user-space design means each application bundles its own transport, which spreads security patches across many codebases.
tradeoffs: Choose HTTP/3 over QUIC for public web and mobile traffic with high latency, loss, or changing networks: a faster first byte, fewer stalls, survival of network changes. Choose HTTP/2 over TCP for internal service traffic inside a well-run data centre, where RTTs are under a millisecond, loss is rare, and kernel offloads give lower CPU per request. You give up QUIC's migration and per-stream loss isolation, which matter little there.
Choose 0-RTT only for requests that are safe to repeat (GET of public or cacheable data), and disable it on endpoints that change state. You gain one round trip on resumed connections; you accept replay risk and a weaker security guarantee for the first flight. Choose 1-RTT when correctness matters more than the last 80 ms.
Choose a user-space QUIC library in your own client or server when you need to tune congestion control or scheduling for your workload (video, bulk sync), and accept the CPU and maintenance cost. Choose a managed endpoint (a CDN or cloud load balancer that terminates QUIC) when you only want the user benefits, and let the provider carry the cost; your origin can stay on HTTP/2 or HTTP/1.1 over TCP.
Choose to keep a TCP fallback always. UDP blocking affects a small but real share of users, and a service that works only over QUIC would lose them.
Choose BBR or CUBIC inside QUIC based on the path: BBR for long lossy paths, CUBIC for fairness on shared paths, as in TCP.
practice: To use HTTP/3 in practice you usually do not write QUIC. Enable it on your CDN or load balancer (most large CDNs, including Cloudflare, CloudFront, Fastly and Akamai, support it; check your own load balancer's current status), open UDP 443 in security groups and firewalls, and serve an Alt-Svc header or HTTPS DNS record so clients learn about it. Check with curl --http3 -I https://example.com (if your curl build supports it) or Chrome's network panel, which shows the protocol column as h3.
Measure on real clients, not synthetic tests. Compare time to first byte, page load and error rates by protocol and network type, using real user monitoring, because the effect depends on RTT and loss. Watch the share of clients falling back to TCP, and CPU per request on your edge.
If you run QUIC servers yourself, raise UDP buffer limits, enable GSO/GRO, pin the load balancer's hash to the connection ID (or use a QUIC-aware layer 4 balancer), rotate keys and tokens, and log qlog traces for debugging. Do not enable 0-RTT on unsafe routes. Treat DNS over QUIC and WebTransport as later steps. For internal gRPC and Kafka traffic, stay on TCP unless you have measured a reason.
interview: Walk through how QUIC saves a round trip compared with TCP plus TLS 1.3. || TCP needs one round trip for SYN/SYN-ACK before TLS can start, and TLS 1.3 needs one more. QUIC sends the TLS ClientHello in its first packet and completes transport and crypto setup together, so the first request leaves after one round trip. With a resumption ticket, it can send the request in the first flight.
What is head-of-line blocking, and does HTTP/3 remove all of it? || It is delay of data behind a missing earlier item. HTTP/2 over TCP has it across all streams, because TCP delivers one ordered byte stream. HTTP/3 removes it between streams, but inside a single stream the data is still ordered, and header compression state (QPACK) can still make a stream wait for the encoder stream.
Why did QUIC choose UDP and user space rather than a new IP protocol or a kernel change? || A new IP protocol number would be dropped by NATs and firewalls, and kernel changes take years to reach users. UDP passes almost everywhere, and a user-space library updates with the application. Encrypting the header also stops middleboxes from freezing the format again.
A mobile app using HTTP/3 shows higher server CPU than before. Why, and what do you do? || Per-packet encryption, user-space processing and small UDP datagrams cost more than kernel TCP with offloads. Enable UDP GSO/GRO and batching, tune buffer sizes, check the congestion controller, and compare cost per request against the latency gain; terminate QUIC at the edge if the origin cost is too high.
How does a server defend against amplification and spoofing during the QUIC handshake? || It limits unauthenticated replies to 3 times the bytes received, requires the client's Initial to be padded to 1,200 bytes, and can send a Retry packet with a token to validate the client's address before it spends memory on state.
quiz: Why does QUIC never reuse a packet number, even for retransmitted data? || Retransmitted frames go into a new packet with a new number, so each acknowledgment refers to exactly one transmission. That gives cleaner RTT measurement and simpler loss detection than TCP.
How many round trips before the first HTTP request byte with TCP + TLS 1.3 versus QUIC, and what is the saving at an 80 ms RTT? || TCP + TLS 1.3 needs 2 round trips (160 ms); QUIC needs 1 (80 ms), and 0 with resumption. The saving is 80 ms, or 160 ms with 0-RTT.
What lets a QUIC connection survive a switch from Wi-Fi to mobile data? || Packets carry a connection ID that is independent of the IP address and port. The server recognizes the connection, validates the new path with PATH_CHALLENGE, and continues with the same keys and stream state.
A page's 20 streams share a connection and one packet is lost. How many streams stall in HTTP/2 over TCP, and how many in HTTP/3? || In HTTP/2 over TCP, all 20 wait for the retransmission, because TCP delivers a single ordered byte stream. In HTTP/3 only the stream whose data was in the lost packet waits.
When should you not rely on QUIC? || Inside a clean, low-latency data centre where kernel TCP with offloads is cheaper, or for users and networks that block UDP 443. Always keep a TCP fallback.

@@ dns
value: The Domain Name System (DNS) turns names that people use, like example.com, into the numbers that networks use, like 203.0.113.10. It is a distributed database with no single owner: the data is split into zones, each run by the organization that owns the names in it, and a hierarchy of servers lets any client find the right one starting from only 13 well-known addresses. Almost every connection your software makes starts with a DNS lookup.
It is more than a phone book. Because every client asks DNS first, DNS is also a control point: it spreads load across servers (several addresses for one name), steers users to a nearby site (the answer depends on who asks), fails traffic over when a data centre dies (change the answer), and provides service discovery inside clusters (Kubernetes names every service). It is also a frequent cause of outages, since it sits under everything and caches hide changes for minutes or hours.
For the layer above, the web (webarch) depends on DNS to find servers, and CDNs and global load balancers are built on answering DNS differently for different clients. Two lower concepts explain the design. Graph theory (L4) describes the namespace as a tree: names are read right to left, from the root through top-level domains to a zone, and authority is delegated down the tree, so no server needs the whole database. Probability (L4) explains why caching works: lookups follow a heavy-tailed popularity pattern, where a few names account for most queries, so a cache that keeps answers for their time-to-live (TTL) absorbs the large majority of traffic.
terms: Resolver (recursive resolver) — a server that answers a client's question by asking other servers and caching the result, such as your ISP's resolver or 8.8.8.8.
Authoritative server — the server that holds the real records for a zone and gives the final answer for it.
Zone — a part of the namespace managed as one unit, such as example.com and its records.
Resource record — one entry in a zone: a name, a type (A, AAAA, CNAME, MX, TXT, NS), a TTL and a value.
TTL — the time in seconds that a resolver may keep an answer before it must ask again.
Delegation — an NS record in a parent zone that says which servers are responsible for a child zone.
Glue record — an address given in the parent zone for a name server inside the child zone, which avoids a circular lookup.
Stub resolver — the small client library in your operating system that sends the question to a recursive resolver.
NXDOMAIN — the answer meaning "this name does not exist"; it is cached too (negative caching).
Anycast — announcing the same IP address from many places, so each client reaches the nearest one; root servers and public resolvers use it.
history: Before DNS, the ARPANET used one file, HOSTS.TXT, kept at SRI's Network Information Center. Every host downloaded the file from time to time. By the early 1980s, with hundreds of hosts and daily changes, the file was too big, took too long to distribute, and had name collisions. Paul Mockapetris, then at USC's Information Sciences Institute, designed DNS in 1983 (RFC 882 and 883); the revised RFC 1034 and 1035 (1987) are still the core of the system. The key ideas were a hierarchy with delegation, so that each organization manages its own names, and caching with a TTL, so that the load stays low.
The first widely used server was BIND, written at Berkeley in the mid-1980s and still maintained. The root of the tree was served by a small set of servers, named A to M; the number 13 was set by the old limit of a DNS reply in a 512-byte UDP packet, which could list only 13 server addresses. Anycast later spread each of these 13 names over many sites, so there are now well over a thousand root server instances worldwide.
Security came late. In 2008 Dan Kaminsky showed that a resolver's cache could be poisoned by guessing the 16-bit query ID, which led to random source ports as an emergency fix. DNSSEC (RFC 4033 to 4035, 2005) adds digital signatures along the delegation chain, and the root zone was signed in 2010. Encrypted transports followed: DNS over TLS (RFC 7858, 2016) and DNS over HTTPS (RFC 8484, 2018). Large outages taught operators about concentration: the Mirai attack on Dyn on October 21, 2016 took many well-known sites offline, Facebook's DNS servers became unreachable on October 4, 2021 after a routing change, and on October 19 to 20, 2025 an Amazon DynamoDB DNS fault in us-east-1 began a long cascade of failures in other services.
how: A client program calls a library function (getaddrinfo) that asks the operating system's stub resolver. The stub checks the local cache and the hosts file, then sends one question to the configured recursive resolver, usually the one your network or cloud provides (in AWS, the VPC resolver at the base of the VPC range plus two). It sends the question as a UDP datagram to port 53: a 12-byte header (ID, flags, counts) followed by the name and the record type wanted. The resolver does the real work.
If the resolver has the answer in cache, it replies at once. Otherwise it walks the tree, from the top. It asks a root server for www.example.com. The root does not know, but it knows who runs com, so it replies with a referral: the NS records for the .com servers and their addresses (glue). The resolver asks a .com server, which refers it to the name servers for example.com. The resolver asks one of those. This server is authoritative, so it returns the answer, such as an A record with an address and a TTL of 300 seconds. The resolver caches every step: the .com servers (which have TTLs of a day or more), the example.com servers, and the final answer. The next lookup for a sibling name skips the root and .com steps entirely. Because most answers come from the resolver's cache, the root servers see only a tiny fraction of the real demand.
Names are read right to left, which is the tree structure. In www.example.com the dot-separated labels are leaves under example, under com, under the root (written as an empty label, the final dot). Each label can be up to 63 bytes and the whole name up to 253 characters. Delegation is a pair of records: a parent zone holds NS records pointing at a child zone's servers, and that is the only link. Because the data is partitioned by zone and each zone can be served by several servers (at least two are required), the system has no central point and scales by adding zones.
Record types carry different meanings. A and AAAA give IPv4 and IPv6 addresses. CNAME makes a name an alias for another name and cannot sit at the apex of a zone beside other records. MX names mail servers, TXT holds free text (used for domain verification and email authentication like SPF and DKIM), SRV gives host and port for a service, and the newer HTTPS and SVCB records (RFC 9460) tell a client about HTTP/3 support and alternative endpoints before connecting. A SOA record holds zone parameters, including how long to cache NXDOMAIN answers (negative caching, RFC 2308).
Probability explains why TTL is the main lever. A cached answer is valid for TTL seconds. If a name is asked for often, the chance that a request finds a fresh entry is high, and the authoritative server sees at most one query per resolver per TTL. The result is the usual trade-off: a long TTL means fewer queries and lower latency for users, but changes (a failover, a migration) take up to a full TTL to reach everyone, and some resolvers and applications keep answers longer than the TTL says.
DNS answers can differ by asker, which is how global load balancing works. An authoritative service such as Route 53 or a CDN looks at the resolver's address (or, with EDNS Client Subnet, part of the client's address) and returns the address of a nearby or healthy server, or picks from several by weight. Health checks remove failed endpoints from answers. Inside Kubernetes, the cluster DNS (CoreDNS) answers names like my-svc.my-namespace.svc.cluster.local with the service's virtual IP, which is DNS used for service discovery.
Security has three parts. DNSSEC lets a validating resolver check that records are signed by the zone owner, with trust anchored in the signed root, but it proves authenticity and not privacy, and adds complexity. DNS over TLS or HTTPS hides queries from the local network, though the resolver operator still sees them. Resolvers also defend against spoofing with random source ports and query IDs, which makes blind guessing very hard.

example: Trace one cold lookup. A client asks its resolver for www.example.com and the resolver's cache is empty. The resolver sends a query to a root server over anycast, 20 ms away round trip; the reply is a referral to the .com servers. It queries a .com server, 25 ms away; the reply is a referral to ns1.example.com. It queries ns1.example.com, 30 ms away, which answers with A 203.0.113.10 and TTL 300. Total: 3 upstream queries and about 75 ms, plus the 1 ms from the client. If the example.com name servers' addresses were not in the glue, there would be extra lookups. A second client asking the same resolver 10 seconds later gets the answer in about 1 ms from cache. A client asking after 301 seconds makes the resolver repeat only the last query (the .com delegation is still cached), about 30 ms.
Now the TTL arithmetic. A service has 10,000 distinct resolvers asking about its name. Each resolver asks the authoritative server at most once per TTL if the name is popular. With TTL 3600 s the authoritative load is at most 10,000 ÷ 3,600 ≈ 2.8 queries per second. With TTL 60 s it is about 167 queries per second, and with TTL 5 s about 2,000 per second. The failover cost goes the other way. After you change the record at time 0, a resolver that just cached the old value will keep serving it for the whole TTL: up to 1 hour, 1 minute or 5 seconds. Expect a tail beyond this, since some clients hold the old answer longer: a Java program keeps its own cache (30 seconds by default in many setups), and some resolvers enforce minimum TTLs.
A common production surprise comes from Kubernetes. Pods get a resolv.conf with ndots:5 and several search domains. A lookup for "api.example.com" has only 2 dots, fewer than 5, so the resolver first tries api.example.com.default.svc.cluster.local, then api.example.com.svc.cluster.local, then api.example.com.cluster.local, each failing with NXDOMAIN, and only then the real name. With A and AAAA queries this is about 8 queries instead of 2, and every external call pays for it. Writing the name with a trailing dot ("api.example.com."), setting ndots lower, or running a node-local DNS cache removes most of it.
intuition: A hierarchy of phone books where each book only says which other book to open next, and everyone keeps a short list of numbers they looked up recently.
The design is natural because names have owners. Rather than one list that everyone must update, each owner keeps the records for their own part and the parent only records who that owner is. Lookups are cheap because the answer is almost always on a nearby cache, and the full walk from the root is rare. The TTL is a promise from the owner: "this will not change for five minutes", which lets every cache in the world serve the answer without asking.
mistakes: People often think DNS lookups are slow and add a delay to every request. In fact most lookups hit a cache within a millisecond or two. The cold walk costs tens to a few hundred milliseconds, but it happens once per TTL per resolver. The real cost appears with very low TTLs, large search lists, or many short-lived connections that look up the name each time.
People often think that after changing a DNS record, the world sees the change at once, or exactly after the TTL. In fact caches expire at different times, so you see a mix of old and new answers for up to one TTL, and software may add its own caching beyond that (JVM, application connection pools, browsers, long-lived connections that never look up again). Lower the TTL days before a planned change.
People often think DNS is the same as load balancing or health checking. In fact DNS only hands out addresses; it cannot know whether a server is overloaded or healthy unless a service checks and changes the answers, and clients may cache dead addresses or pick the first address from a round-robin list every time.
People often think a CNAME can be placed anywhere. In fact a CNAME cannot coexist with other records on the same name, so it cannot sit at a zone apex (example.com) that needs SOA and NS records. Providers offer ALIAS or ANAME flattening for this case.
People often think encrypted DNS (DoH, DoT) makes browsing private. In fact it hides the query from the local network only. The resolver sees every name, and the following connection still reveals the destination address and, unless Encrypted Client Hello is used, the server name in the TLS handshake.
friction: Caching is both the strength and the weakness. Stale data hides changes, negative answers are cached too (a name created right after a failed lookup may stay missing for the negative TTL), and a bad record can be served for hours after the fix. Application-level caches ignore TTL: Java's default positive cache and long-lived pooled connections mean a failover that DNS completed in 30 seconds can take many minutes for a service.
DNS is a shared dependency with a large blast radius. If the resolver or the authoritative servers are unavailable, almost everything fails, often in confusing ways, because the symptoms are timeouts in unrelated services. The 2021 Facebook and 2025 DynamoDB events were different root causes but the same shape: name resolution failed and dependent systems could not recover on their own. Resolver limits also matter: inside AWS, each network interface can send only 1,024 packets per second to the VPC resolver (a limit shared with other link-local services such as the instance metadata service), and a chatty service can reach that and see sporadic failures.
Security remains weak by default. Plain DNS is unencrypted and unauthenticated; DNSSEC adoption is partial, difficult to operate (key rollovers, expiry of signatures cause outages), and does not protect the last hop to the user. DNS is also used as an attack tool (amplification, using small queries to cause large replies toward a victim) and as a covert channel for data theft. Trust is concentrated in a few registries, registrars and resolver operators. Finally, the 512-byte legacy and large records (DNSSEC, HTTPS records) lead to fragmentation and fallback to TCP, and operators set EDNS buffer sizes around 1,232 bytes to avoid IP fragmentation.
tradeoffs: Choose a long TTL (an hour or more) for stable records such as MX, NS and static assets, where a lookup is a pure cost; choose a short TTL (30 to 60 seconds) for names you may need to move in an emergency, such as a front-door load balancer or failover endpoint. Short TTL costs query volume and a small latency risk; long TTL costs slow recovery. For planned changes, lower the TTL one full old-TTL beforehand and raise it afterwards.
Choose DNS-based routing (weighted, latency or geo) for coarse global steering across regions, where seconds-to-minutes of staleness are acceptable. Choose a real load balancer or anycast for fast failover and fine control over single connections. DNS is cheap and cannot see load; a load balancer can see health and connections but is one more component to run.
Choose service discovery by DNS (Kubernetes services, Consul DNS) when clients are simple and the set of backends changes slowly. Choose client-side discovery with a registry (or a service mesh) when you need instant updates, weights and health data. DNS is universal but gives only addresses, with caching you do not control.
Choose a managed, highly available DNS provider with anycast for public zones, and use two independent providers if the zone is critical enough to justify the complexity of keeping them in sync. Choose to run your own resolvers or node-local caches inside large clusters, to cut latency and avoid per-interface limits, at the price of operating one more tier.
practice: Use dig to see what really happens: dig www.example.com shows the answer, TTL and which server answered; dig +trace walks from the root so you see each referral; dig @8.8.8.8 and dig @your-resolver compare resolvers. Check TTLs before any migration, and compare what the authoritative server says (dig @ns1.example.com) with what resolvers still cache.
In applications, do not hard-code IP addresses, and do not cache lookups forever. For the JVM, set networkaddress.cache.ttl to a small value (for example 30 to 60 seconds) when backends move; for Kafka clients, set client.dns.lookup=use_all_dns_ips so a bootstrap name with several addresses is used fully. Reuse connections to avoid repeated lookups, and put a timeout and retry policy on resolution as you would for any remote call.
In Kubernetes, check ndots and search paths, use fully qualified names ending with a dot for external hosts, and run a node-local DNS cache or scale CoreDNS with the cluster (watch its error and latency metrics). In AWS, use Route 53 health checks with failover or latency records, keep records for private zones in sync across VPCs, and remember the per-interface resolver limit.
interview: Walk through everything that happens when a browser resolves www.example.com for the first time. || The OS stub resolver checks its cache and hosts file and asks the recursive resolver. On a miss, the resolver asks a root server (referral to .com), then a .com server (referral to example.com's name servers), then the authoritative server, which answers with an address and TTL. Each step is cached; the answer returns to the client, which then opens a connection.
You need to move a service to a new region with minimal downtime. How do you use DNS safely? || Lower the TTL to 30 to 60 seconds at least one old-TTL ahead, bring the new region up and test it, then shift traffic gradually with weighted records. Watch both regions, keep the old one running for longer than the old TTL plus client-side caches, and raise the TTL again afterwards.
Why can't a CNAME be at the zone apex, and what do you do for a bare domain pointing to a CDN? || A CNAME means "this name is an alias for that name, for all record types", which conflicts with the SOA and NS records required at the apex. Use an ALIAS/ANAME (flattening) record offered by the DNS provider, or the HTTPS/SVCB record, or A/AAAA records pointing to the CDN's addresses.
A service intermittently fails with timeouts, and in the cluster the DNS error rate is low but latency is high. What do you check? || Search-domain expansion (ndots), conntrack races for UDP, resolver rate limits per network interface, and CoreDNS load. Capture queries to see multiplied or failing lookups, add a node-local cache, and use absolute names.
How does DNS cache poisoning work, and what mitigates it? || An attacker floods the resolver with forged answers hoping to match the query's ID and source port before the real reply, and a forged answer is cached. Random source ports and IDs (the 2008 fix), 0x20 case randomization, and DNSSEC validation raise the cost; DNSSEC gives actual proof of authenticity.
Why do DNS failures often look like unrelated timeouts, and how do you design for it? || Every service resolves names first, so a resolver or authoritative failure shows up as connect timeouts everywhere at once. Design with cached or multiple resolvers, sensible timeouts and retries, long enough TTLs for stable names, connection reuse, and monitoring of resolution latency and error rate as a first-class signal.
quiz: What is the difference between a recursive resolver and an authoritative server? || A recursive resolver answers client questions by querying other servers and caching results. An authoritative server holds the actual records of a zone and gives the final answer for names in it.
Why are there 13 root server names? || Early DNS replies had to fit in a 512-byte UDP packet, which could hold the names and addresses of about 13 servers. Each name is now anycast across many sites.
A name has TTL 120 and is queried through 6,000 resolvers. What is the maximum authoritative load? || Each resolver asks at most once per 120 s, so at most 6,000 ÷ 120 = 50 queries per second.
Why does a pod lookup of api.example.com send several failing queries in Kubernetes? || The default ndots:5 makes names with fewer than five dots be tried with each search domain first, so three or more NXDOMAIN answers occur before the real name resolves. Use a trailing dot or lower ndots.
When would you choose DNS failover over a load balancer for high availability? || When you need coarse, cheap, global failover between regions or providers and can accept minutes of staleness. For fast, per-connection failover use a load balancer or anycast.

value: HTTP (Hypertext Transfer Protocol) is the request and response protocol of the web, and now of most service APIs. A client sends a request that names an action (a method such as GET or POST), a resource (a path) and some headers; the server sends back a status code, headers and a body. Each exchange is self-contained, which is called stateless: the server needs nothing from earlier requests to understand this one.
That simple shape is why HTTP became the universal interface between programs. Any language has an HTTP client; any proxy, load balancer or CDN can handle the traffic because the semantics (methods, status codes, caching headers) are standard; and the same protocol serves web pages, JSON APIs, gRPC, S3 object access, video chunks (HLS and DASH), tracking pixels and LLM tool servers. Statelessness lets any server in a pool answer any request, which is the basis of horizontal scaling.
HTTP stands on three lower pieces. TCP (L3) gives HTTP/1.1 and HTTP/2 a reliable ordered byte stream, so HTTP itself never deals with lost or reordered packets. QUIC (L3) does the same for HTTP/3, with independent streams over UDP. Parsing and grammars (L3) matter because HTTP/1.1 is a text format with a formal grammar, and a request is only as safe as the parser that reads it: different parsers reading the same bytes differently is the root of request smuggling attacks. Cookies and device IDs, web security, S3 access and tracking pixels (all above) are built from nothing more than HTTP requests and headers.
terms: Method — the verb of a request: GET reads, POST submits data, PUT replaces, DELETE removes, PATCH changes part of a resource.
Status code — a three-digit result: 2xx success, 3xx redirect or cache hit, 4xx client error, 5xx server error.
Header — a name and value pair that carries metadata, such as Content-Type, Cache-Control or Authorization.
Idempotent — an operation that has the same effect if repeated once or many times; GET, PUT and DELETE are idempotent, POST is not.
Keep-alive (persistent connection) — reusing one TCP connection for several requests instead of opening one per request.
Multiplexing — sending several requests and responses at the same time on one connection, as separate streams.
Head-of-line blocking — a delay in which a slow or lost item at the front of a queue holds up the items behind it.
ETag — a version label for a response; a client sends it back so the server can answer "not modified" without resending the body.
Reverse proxy — a server in front of backend servers that accepts client requests and forwards them, adding TLS, caching or load balancing.
Content negotiation — the client states what it can accept (language, format, compression) and the server picks.
history: Tim Berners-Lee wrote the first version of HTTP at CERN around 1990 to 1991 for the first web server. Version 0.9 had one method, GET, one line (GET /page), and returned only HTML. HTTP/1.0 (RFC 1945, 1996) added headers, methods like POST and status codes, but closed the connection after every request, so each image cost a new TCP handshake. HTTP/1.1 (RFC 2068, 1997, then RFC 2616, 1999) made connections persistent by default, required the Host header (so one IP address could serve many sites), and added chunked transfer, caching controls and range requests. Roy Fielding, one of its authors, described the architectural style behind the web as REST in his 2000 dissertation.
Pages grew to dozens of resources, and HTTP/1.1 could only run one request at a time per connection. Browsers opened about six connections per host and sites split resources across several hostnames. Google's SPDY (2009) and then HTTP/2 (RFC 7540, 2015) introduced binary framing, many streams on one connection, and header compression (HPACK). gRPC (2015) built RPC on HTTP/2. HTTP/2 kept TCP's single ordered stream, so one lost packet stalled every stream; HTTP/3 (RFC 9114, 2022) moved to QUIC to fix that.
In June 2022 the IETF restructured the specifications by version-independent meaning: RFC 9110 (HTTP Semantics), RFC 9111 (Caching), with RFC 9112 for HTTP/1.1 messages, RFC 9113 for HTTP/2 and RFC 9114 for HTTP/3. The semantics (methods, status codes, headers) are the same in all versions, and only the wire format changes. HTTP/2 server push, once a headline feature, proved hard to use well and was removed from Chrome in 2022.
how: In HTTP/1.1 a request is plain text. The first line is the request line: method, target and version. Then come header lines, an empty line, and an optional body. For example: GET /v1/segments/42 HTTP/1.1, then Host: api.example.com, then Accept: application/json. The response starts with a status line (HTTP/1.1 200 OK), then headers (Content-Type, Content-Length, ETag, Cache-Control), an empty line and the body. The format is defined by a formal grammar (ABNF) in the RFCs. A parser must find where each message ends: by Content-Length (the body is that many bytes) or by chunked transfer encoding (the body is a series of size-prefixed chunks, ending with a zero-sized one). If two parsers in a path, such as a proxy and a server, disagree on this, an attacker can hide a second request inside the first (request smuggling), so strict parsing is a security matter, not a style matter.
The method defines what the request means and what repeating it does. GET and HEAD are safe (they must not change state) and idempotent, so caches, crawlers and retries can use them freely. PUT and DELETE are idempotent: doing them twice leaves the same final state. POST and PATCH are neither, so a blind retry after a timeout can charge a customer twice. Status codes give the result in a standard way: 200 OK, 201 Created, 204 No Content (the usual answer for a tracking pixel), 301 and 302 redirects, 304 Not Modified, 400, 401 (not authenticated), 403 (not allowed), 404, 409 (conflict), 429 (too many requests, often with Retry-After), 500, 502, 503 and 504 (gateway timeout). Clients and proxies use these classes to decide whether to retry.
Caching is built into the protocol. A response can carry Cache-Control: max-age=3600, meaning any cache (browser, CDN, proxy) may reuse it for an hour without asking. After that the cache can revalidate: it sends If-None-Match with the stored ETag, and a server whose resource has not changed replies 304 with no body, saving the transfer. The Vary header says which request headers (for example Accept-Encoding) change the response, so caches keep separate copies. Directives such as no-store (never keep), private (browser only), s-maxage (shared caches) and stale-while-revalidate (serve old while fetching new) let operators tune freshness against load. This is why a CDN can absorb most traffic for static assets and HLS video chunks.
Connection use is where versions differ. HTTP/1.1 reuses a TCP connection but handles one request at a time on it; pipelining (sending several without waiting) was never reliably supported. Browsers therefore open up to six connections per host, each paying TCP and TLS setup and its own slow start. HTTP/2 puts every request on its own stream in one connection. Messages are cut into frames with a 9-byte header (length, type, flags, stream ID), so frames of different streams can interleave; HPACK compresses repeated headers (cookies and user-agent strings that repeat on every request) with a table shared by the two ends. Flow control works per stream and per connection. The remaining weakness is that TCP delivers one ordered byte stream: a single lost packet holds back frames of all streams behind it. HTTP/3 replaces TCP and TLS with QUIC, where each request is a QUIC stream and a loss affects only its own stream; it also compresses headers with QPACK.
Two headers do quiet but important work. Host names the site the client wants, so one server and one IP address can serve thousands of domains (virtual hosting) and a reverse proxy can route by name. Accept-Encoding and Content-Encoding let the two sides agree on compression such as gzip or Brotli, which often shrinks text responses by 70 to 80 percent. Authorization carries credentials on every request, because the server remembers nothing; this is why tokens are checked on each call. Redirects (301, 302, 307, 308) send the client to another URL, and each one costs a full extra round trip.
Beyond browsers, HTTP carries APIs. REST uses URLs for resources and methods for actions, with JSON bodies. gRPC uses HTTP/2 streams with Protocol Buffers bodies and trailers for status. Object stores such as S3 are HTTP APIs: a Spark job reading a Parquet file sends GET with a Range header to fetch only the footer and the needed column chunks, and uploads use PUT and multipart POST requests. Long responses stream over chunked encoding or Server-Sent Events, which is how LLM answers appear token by token. WebSockets begin as an HTTP request and then upgrade the connection to a different protocol.

example: A page needs 60 small resources (scripts, images, API calls) from one host. The round-trip time is 50 ms, and transfer time for each object is negligible.
HTTP/1.1 with 6 connections. Each connection first needs TCP (1 RTT = 50 ms) and TLS 1.3 (1 RTT = 50 ms), so requests can start at 100 ms. The 60 requests split across 6 connections is 10 per connection, and each connection handles them one at a time, each costing one round trip. That is 10 × 50 = 500 ms of waiting after the handshakes, about 600 ms in total. Because each new connection also starts with a small congestion window, larger objects are slower still.
HTTP/2 with one connection. After the same 100 ms of setup, the browser sends all 60 requests at once as separate streams. The server answers them in parallel as data is ready. With negligible transfer time the page finishes about one round trip later, around 150 ms, a saving of roughly 450 ms. In practice bandwidth and server time matter too, so the gain is smaller, but fewer connections also means one slow start instead of six.
Now caching. A 120 KB JSON response has ETag "a1b2". The client asked again after max-age expired, sending If-None-Match: "a1b2" (about 300 bytes in the request). The data has not changed, so the server replies 304 Not Modified with about 200 bytes of headers and no body. The client saves 120 KB and the transfer time (at 20 Mbit/s that would be about 48 ms) and still gets a correct, validated answer. If a CDN absorbs 95% of requests with max-age and 304 responses, the origin sees 5% of the load.
Finally retries. A client posts a payment, but the connection times out after the server processed it. A retry of the POST would charge twice. The standard defence is an idempotency key: the client sends the same random Idempotency-Key header on the retry, and the server stores the result under that key and returns it again rather than repeating the work. GET, PUT and DELETE are safe to retry because they are idempotent by definition.
intuition: A standard order form that every shop in the world understands, filled in fresh each time, so any clerk can serve you without knowing your history.
The design works because it fixes only the small, stable part: what a message looks like and what the verbs mean. Everything else is left free: how the server stores data, how many servers there are, whether an answer comes from a cache. Because requests carry all their context, any machine in the path can handle, cache, retry or reroute one without coordination. Each version of HTTP kept this contract and changed only how the bytes travel, which is why the web could be upgraded without breaking sites.
mistakes: People often think HTTP is the same as the web or as HTML. In fact HTTP is a general transfer protocol. Most HTTP traffic today carries JSON, images, video chunks and binary data, and HTTP is used between servers more than between browsers and servers.
People often think stateless means no state. In fact the protocol itself keeps no state between requests, so state is pushed elsewhere: cookies and tokens in the request, and sessions, databases and caches on the server side. Statelessness only means each request carries enough information to be understood alone.
People often think POST is for writes and GET is for reads, and nothing more. In fact the difference is about guarantees: GET must be safe, so caches, crawlers and prefetchers may call it at any time. A GET endpoint that deletes data will be triggered by link previews and crawlers. And a POST retry is dangerous without an idempotency key.
People often think HTTP/2 or HTTP/3 will fix a slow page by themselves. In fact they remove connection and head-of-line overhead but cannot shorten the server's work, large payloads or too many round trips caused by dependent requests. Measure before you change.
People often think 200 means success in every case. In fact some APIs return 200 with an error in the body, which hides failures from proxies, monitoring and retry logic. Use the status code classes honestly, and mark retryable errors (429, 503) so clients can back off.
friction: Statelessness moves complexity elsewhere. Authentication tokens, session stores and cookies are state added back on top, with their own security risks (see web security). Large request headers repeat on every request, and cookies are sent to every request on a domain. HTTP/1.1 and HTTP/2 over TCP suffer from head-of-line blocking at different levels, and long-lived connections complicate load balancing: one busy HTTP/2 or gRPC connection pins all its streams to one backend, so a layer 4 balancer can leave servers unevenly loaded.
Semantics are often misused. Retries, timeouts and idempotency are left to application authors, who frequently forget them; proxies and clients retry non-idempotent requests in some cases and cause duplicates. Intermediaries interpret messages differently, which gives request smuggling and cache poisoning bugs. HTTP/2 has its own attack surface, such as the Rapid Reset flood of 2023, which exploited cheap stream creation and cancellation to overload servers.
The ecosystem is large and still moving. Versions, extensions and conventions (REST styles, problem-details errors, pagination, rate-limit headers) differ among APIs, so every integration has a learning cost. Text parsing in HTTP/1.1 costs CPU compared with binary framing. HTTP cannot push data to the client by itself: server-initiated updates need long polling, Server-Sent Events, WebSockets or HTTP/2 and HTTP/3 streaming, each with its own failure modes through proxies and idle-timeouts.
tradeoffs: Choose HTTP/2 or HTTP/3 for browser-facing and mobile traffic with many resources and high latency: fewer connections, header compression, no per-request round trips. Choose HTTP/1.1 for simple internal calls, tools with no HTTP/2 support, and debugging by hand with curl or telnet; it is easy to read, and for a few long requests there is little difference.
Choose REST-style JSON over HTTP for public APIs and wide compatibility, where clients are unknown and debuggability matters. Choose gRPC for internal service-to-service calls where you control both ends: compact binary encoding, schemas, streaming and generated clients. You give up easy browser access and human-readable payloads, and need an HTTP/2-aware load balancer.
Choose aggressive caching (long max-age with versioned URLs, plus a CDN) for static and rarely changing data: it removes load and latency. Choose short or no caching with validation (ETag) for data that must be fresh, and no-store for private data. The cost of long caching is stale content, so the standard approach is to put a content hash in the file name and cache it for a year.
Choose a long-lived connection (WebSocket, SSE, or HTTP streaming) when the server must push updates to many clients with low delay. Choose plain request-response with polling when updates are rare, because long-lived connections need sticky routing, heartbeats and careful handling of idle timeouts in every proxy on the path.
Choose strict, small request limits and a hardened proxy in front of any service exposed to the internet. The cost is occasional rejection of unusual but legitimate clients.
practice: Learn curl well: curl -v shows the request and response headers and timing; curl -w with timing variables shows DNS, connect, TLS, first byte and total time; curl --http2 or --http3 selects the version. Read Cache-Control, ETag, Vary and Content-Type on every endpoint you own and decide on purpose what each should be. Put a content hash in static asset names and cache them for a year; keep HTML short-lived.
Design APIs with the semantics of the protocol: use GET only for reads, PUT or DELETE for idempotent changes, and POST with an idempotency key for operations that must not repeat. Return correct status codes (429 or 503 with Retry-After for overload), set client timeouts explicitly (connect, read and total), and retry only idempotent requests with exponential backoff and jitter. Reuse connections with a pool; creating one per call wastes two round trips and, with TLS, CPU.
For data systems: Spark, Delta and Parquet readers use HTTP range requests on S3, so file layout (row group size, footer) affects the number of requests; S3 supports on the order of thousands of requests per second per prefix before it returns 503 Slow Down, so spread keys and retry with backoff. For pixel and event collection, return 204 quickly, keep the endpoint cacheable-free (no-store), and batch events when you can. Behind a load balancer, check idle timeouts (AWS ALB defaults to 60 seconds) against your longest request, and enable keep-alive between proxy and backend.
interview: Explain what changed from HTTP/1.1 to HTTP/2 to HTTP/3, and what problem each solved. || HTTP/1.1 allows one request at a time per connection, so browsers used many connections. HTTP/2 multiplexes streams on one TCP connection with binary framing and header compression, but a lost TCP packet blocks all streams. HTTP/3 uses QUIC, where streams are independent and the handshake merges transport and TLS, so loss stalls only one stream.
A client times out on a POST /charge and retries. How do you make it safe? || The POST may have succeeded, so a naive retry duplicates the charge. The client sends an idempotency key with each logical operation; the server records the key with the result and returns the stored result on a repeat. Keep keys for a defined window, and make the check atomic with the work.
How does HTTP caching work end to end, and what is the difference between no-cache and no-store? || A response with max-age can be reused until it expires; then the cache revalidates with If-None-Match or If-Modified-Since and gets 304 if unchanged. no-cache means the cache may store the response but must revalidate before every reuse. no-store means it must not store it at all.
Why does request smuggling happen, and how do you prevent it? || A front-end proxy and a back-end server disagree about where one request ends, for example when both Content-Length and Transfer-Encoding are present, so the attacker's extra bytes are treated as the start of another user's request. Prevent it by rejecting ambiguous messages, using HTTP/2 or HTTP/3 end to end, and keeping proxies and servers up to date and consistent.
Your gRPC service behind a layer 4 load balancer sends all traffic to one pod. Why, and what do you do? || gRPC keeps one long HTTP/2 connection and multiplexes all calls on it, so a connection-level balancer picks the backend once. Use a layer 7 balancer that balances per request or per stream, client-side load balancing, or a service mesh.
When is it wrong to use HTTP for communication between services? || When you need very low latency and high throughput with binary protocols and persistent streams (a database or Kafka protocol), or when a message broker's delivery guarantees, ordering and replay are needed. HTTP is request-response and leaves retries, ordering and durability to you.
quiz: What are the parts of an HTTP/1.1 request? || A request line (method, target, version), header lines, an empty line, and an optional body.
Which methods are idempotent, and why does it matter? || GET, HEAD, PUT, DELETE and OPTIONS are idempotent. Clients, proxies and load balancers can retry them after a timeout without changing the outcome. POST and PATCH are not, so retries need an idempotency key.
A page has 60 resources, RTT is 50 ms, and the browser uses 6 HTTP/1.1 connections. About how many round trips of waiting per connection after setup? || 60 ÷ 6 = 10 requests per connection, one at a time, so about 10 round trips or 500 ms. HTTP/2 sends them all at once.
What does a 304 response contain and why is it useful? || It has headers but no body. It tells the client that its cached copy (matched by ETag or date) is still valid, so the large body is not transferred again.
When would you choose gRPC over REST? || For internal service-to-service calls where you control both sides and want a compact binary format, a schema, streaming and generated clients. Choose REST for public APIs and browser clients.

@@ tls
value: Transport Layer Security (TLS) gives a network connection three properties: privacy (nobody on the path can read the data), integrity (nobody can change it without being detected) and authentication (you know which server you are talking to, and optionally which client). It sits between the transport (TCP, or inside QUIC) and the application protocol. HTTPS is HTTP inside TLS, and the same layer protects Kafka brokers, database connections, gRPC calls and service-to-service traffic.
The problem is that two machines that have never met must agree on a secret over a network that an attacker can read, and must also be sure the other side is who it claims to be. TLS solves it in a short handshake. The two sides agree on a fresh secret with an ephemeral Diffie-Hellman key exchange, the server proves its identity with a certificate signed by an authority the client already trusts, and all later data is encrypted with a fast symmetric cipher that also authenticates every record. The whole setup costs one round trip in TLS 1.3 and a few hundred microseconds of CPU.
Each lower layer contributes one piece. Public-key cryptography (L3) supplies the key exchange: ECDHE lets two parties compute the same secret without ever sending it. Digital signatures and PKI (L3) supply identity: the certificate binds a name to a public key and a chain of signatures leads to a root in the client's trust store. Symmetric encryption (AES) and authenticated encryption (AEAD) supply the bulk protection: AES-GCM or ChaCha20-Poly1305 encrypts each record and detects tampering. Post-quantum cryptography (L3) is now added to the key exchange as a hybrid, so recorded traffic stays safe against future quantum computers. Web architecture, mutual TLS, security architecture and web security (above) all assume this layer.
terms: Handshake — the opening exchange in which client and server agree on a protocol version, cipher, and shared keys, and the server proves its identity.
Certificate — a signed document that binds a domain name to a public key, issued by a certificate authority.
Certificate authority (CA) — an organization that is trusted to sign certificates after checking that the requester controls the name.
Chain of trust — the path of signatures from the server's certificate through intermediate certificates to a root certificate stored in the client.
ECDHE — elliptic-curve Diffie-Hellman with ephemeral keys: both sides create temporary key pairs and combine them into a shared secret.
Forward secrecy — the property that stealing a server's long-term key later does not let an attacker decrypt past recorded traffic.
Cipher suite — the set of algorithms in use; in TLS 1.3 it names only the AEAD cipher and the hash, such as TLS_AES_128_GCM_SHA256.
Record — the unit of TLS data on the wire: a small header and an encrypted block of up to 16 KB.
SNI (server name indication) — a handshake field that tells the server which hostname the client wants, so one IP address can host many certificates.
Session resumption — reusing a secret from an earlier connection (a pre-shared key) to start a new one faster.
history: Netscape created SSL (Secure Sockets Layer) for its browser in 1994 to 1995, so that credit card numbers could be sent on the web. SSL 2.0 (1995) had serious flaws and SSL 3.0 (1996, by Kocher, Freier and Karlton) replaced it. The IETF took over the protocol and published TLS 1.0 as RFC 2246 in January 1999. TLS 1.1 (2006) and TLS 1.2 (RFC 5246, 2008) added protection against attacks on CBC encryption and allowed authenticated encryption and stronger hashes. TLS 1.2 stayed the main version for a decade.
Meanwhile many attacks showed that old options were dangerous: BEAST (2011), CRIME (2012), Lucky 13, POODLE (2014), FREAK and Logjam (2015), and Heartbleed (April 2014), which was not a protocol flaw but a missing bounds check in OpenSSL's heartbeat code that let attackers read server memory. Each time, the remedy was to remove a feature. TLS 1.3 (RFC 8446, August 2018, mainly by Eric Rescorla) did this on purpose: it dropped RSA key exchange, static Diffie-Hellman, CBC modes, compression, renegotiation and weak hashes, left only AEAD ciphers and forward-secret key exchange, and cut the handshake to one round trip. TLS 1.0 and 1.1 were formally deprecated in 2021 (RFC 8996).
Cost and trust changed too. The Let's Encrypt authority, started in 2015 and 2016 by the Internet Security Research Group, offered free certificates issued automatically by the ACME protocol (RFC 8555, 2019), and HTTPS became the default for most of the web. The CA/Browser Forum has since been shortening certificate lifetimes: a maximum of 200 days from March 2026, 100 days from March 2027 and 47 days from March 2029, so renewal must be automated. In 2024 Chrome enabled a hybrid post-quantum key exchange by default, and Encrypted Client Hello was published as RFC 9849 in 2026.
how: After the TCP connection opens (or inside QUIC), the client sends ClientHello: a random value, the list of cipher suites it supports, the key-exchange groups it will use (for example X25519), a key share (its ephemeral public key for one or two guessed groups, so no extra round is needed), the signature algorithms it accepts, the server name (SNI) and the application protocols it can speak (ALPN: h2, http/1.1). The server picks parameters and replies with ServerHello containing its own ephemeral public key.
At that moment both sides can compute the same shared secret. With X25519, each side multiplies the other's public point by its own private scalar. An attacker who sees both public values cannot compute the result, because that requires solving the elliptic-curve discrete logarithm problem. Both sides feed the secret and a hash of all messages so far into HKDF (a key derivation function) and obtain separate keys and IVs for each direction. From this point everything is encrypted, including the rest of the handshake. This is a change from TLS 1.2, where the certificate was sent in clear.
Now the server proves identity. It sends EncryptedExtensions, then its Certificate message (the leaf certificate and any intermediates), then CertificateVerify: a digital signature, made with the private key matching the certificate, over a hash of the whole handshake transcript. Then it sends Finished, an HMAC over the transcript that confirms both sides saw the same messages. The client checks the chain: each certificate must be signed by the next, the last one must be a root it trusts (operating systems and browsers ship about 100 to 150 roots), dates must be valid, the hostname must match a Subject Alternative Name, and usage fields must allow server authentication. Revocation is weak in practice, so browsers rely on short lifetimes and pushed revocation lists, and Certificate Transparency logs let the public detect wrongly issued certificates. The client then sends its own Finished and application data may flow. The whole handshake is 1 round trip after TCP.
Application data is carried in records. Each record holds up to 16,384 bytes of plaintext, plus a hidden content type and padding, encrypted with an AEAD cipher: AES-128-GCM, AES-256-GCM or ChaCha20-Poly1305. The nonce for each record is the IV combined with a 64-bit sequence number, so a nonce never repeats, and the 5-byte record header is authenticated as additional data. A 16-byte tag is appended; any change to ciphertext, header or order makes the tag check fail and the connection closes. AES-GCM runs at several GB/s per core with hardware instructions (AES-NI), and ChaCha20 is fast on devices without them, which is why mobile clients often negotiate it.
Forward secrecy comes from the ephemeral keys. The Diffie-Hellman private values exist only in memory for one connection and are discarded. The server's long-term key only signs; it never encrypts the session. So an attacker who records traffic today and steals the server key next year learns nothing about the old sessions. For quantum risk, the key exchange now often combines X25519 with ML-KEM-768 (a lattice-based scheme standardized in 2024 as FIPS 203): the secret is derived from both, so it is safe unless both are broken. This adds about 1.2 KB to the ClientHello and about 1.1 KB to the server reply. Certificates and signatures are still classical (ECDSA or RSA) because a quantum attacker cannot go back and forge a signature in a past session; moving them to post-quantum signatures would add several kilobytes per certificate and is still being worked out.
Keys do not last forever. Either side can send a KeyUpdate message to derive new traffic keys from the old ones without a new handshake, which matters for long-lived connections because AEAD ciphers have a limit on how much data one key may protect. Alert messages carry errors and the close notification, which prevents an attacker from silently truncating a stream.
Resumption and early data save time on repeat visits. After the handshake the server sends a session ticket; the client can present it later as a pre-shared key, skipping the certificate exchange, and may send application data in its first flight (0-RTT). Early data is not protected against replay, so it should carry only requests that are safe to repeat. Mutual TLS adds a CertificateRequest from the server and a client certificate with its own CertificateVerify, which gives services a strong identity for each workload.

example: A toy Diffie-Hellman exchange shows the idea with numbers small enough for a pen. The public values are the prime p = 23 and the generator g = 5. The client picks a private number a = 6 and sends A = 5⁶ mod 23. Since 5² = 25 ≡ 2, 5³ ≡ 10, 5⁶ = 10² = 100 ≡ 8, so A = 8. The server picks b = 15 and sends B = 5¹⁵ mod 23 = 19. The client computes B⁶ mod 23: 19² ≡ 16, 19⁴ ≡ 3, so 19⁶ ≡ 3 × 16 = 48 ≡ 2. The server computes A¹⁵ mod 23 = 8¹⁵ ≡ 2. Both get the shared secret 2, and an eavesdropper who saw 23, 5, 8 and 19 must find a or b, which is easy for 23 but infeasible for the 256-bit elliptic-curve version. Real TLS never uses the secret directly; it feeds it into HKDF with the transcript hash to get the keys.
Now the cost of a real connection. Assume the round trip is 70 ms. TCP takes 70 ms, and the TLS 1.3 handshake another 70 ms, so the first HTTP request leaves the client at 140 ms. On resumption with a ticket the cost is still one round trip but the server flight is smaller (no certificate); with 0-RTT early data the request leaves at 70 ms, right after TCP. The bytes are small: ClientHello about 250 to 300 bytes, the server's reply about 3 to 5 KB (mostly the certificate chain: an ECDSA chain is around 1.5 KB, an RSA-2048 chain is 3 to 4 KB). With a hybrid post-quantum share the ClientHello grows to about 1.5 KB, which can no longer fit a single minimum-size packet on some paths and has broken buggy middleboxes. CPU is also small: an ECDSA P-256 signature takes about 50 microseconds, an RSA-2048 signature about 1 ms, X25519 about 50 to 100 microseconds. A server core can therefore do thousands of full handshakes per second.
Per-record overhead: 5 bytes header + 1 content type + 16 byte tag = 22 bytes. For a full 16,384-byte record that is 0.13%. For a 100-byte message it is 22%, which is one reason to batch small writes.
intuition: Agree on a secret code in public while nobody can overhear it, after checking the other side's ID card against a registry you already trust.
The design is natural once the three jobs are separated. A shared secret has to be made fresh each time (ephemeral Diffie-Hellman), because then no stored key can unlock the past. Identity has to come from outside the connection (a signature chain to a root you already hold), because a stranger's claim proves nothing. And bulk data needs a fast cipher that also detects changes (AEAD), because asymmetric math is too slow for every byte. The handshake joins the three by signing the transcript, so the identity proof is tied to this exact key exchange and cannot be moved to another.
mistakes: People often think the padlock means the site is safe or trustworthy. In fact it means the connection is encrypted and the certificate matches the name. A phishing site can have a valid certificate for its own look-alike domain, and certificates are issued automatically for any domain whose owner proves control.
People often think TLS hides everything about a connection. In fact the IP address, the timing and sizes of records, and (unless Encrypted Client Hello is used) the server name in the handshake are visible to anyone on the path. TLS protects content, not the fact of communication.
People often think encryption slows servers a lot. In fact with AES hardware instructions and elliptic-curve key exchange, the cost is a small fraction of total CPU for most services. The costs that remain are the handshake round trip, which connection reuse and resumption avoid, and the handling of many short connections.
People often think a self-signed certificate or disabling verification is fine inside the company. In fact without verification there is no authentication, and an attacker on the network can sit in the middle. Switching off checks (verify=False, trust-all managers) is one of the most common serious bugs in internal code. Use a private CA and distribute its root instead.
People often think TLS 1.3 is just a faster TLS 1.2. In fact it removed many options: no RSA key exchange, so forward secrecy is always on, and no negotiation of weak ciphers, so downgrade attacks are far harder. That is as important as the faster handshake.
friction: Certificates are the operational weak point. They expire, and an expired certificate is a total outage for every client at once: a root expiry in September 2021 (the DST Root CA X3 used by Let's Encrypt's older chain) broke older devices, and expired leaf certificates have taken down large services. With maximum lifetimes falling to 200 days in 2026 and 47 days by 2029, manual renewal will not work; automation (ACME, cert-manager, cloud-managed certificates) is required, and so is monitoring of expiry dates.
Trust is concentrated and imperfect. Any of the roughly 100 trusted root CAs can issue a certificate for any name, and incidents of mis-issuance have happened (DigiNotar in 2011); Certificate Transparency and CAA records reduce the risk but do not remove it. Revocation does not work well in practice, and lifetimes are being shortened partly for that reason. Operating a private CA for internal mTLS, with rotation of thousands of workload certificates, is a significant effort.
Visibility is reduced. Security tools cannot inspect encrypted traffic without terminating TLS in a proxy that holds a trusted CA, which becomes a high-value target. CPU cost matters only at very high throughput or with huge numbers of short connections; kernel TLS and hardware offload exist for that. Post-quantum key shares grow the handshake and have exposed broken middleboxes. And TLS protects the channel, not the endpoints: a compromised server or client still leaks everything.
tradeoffs: Choose TLS termination at the load balancer when you want central certificate management, WAF features and layer 7 routing, and accept that traffic inside your network is plaintext unless you re-encrypt. Choose end-to-end TLS (passthrough, or re-encryption to backends) when compliance or zero-trust requires encryption on every hop, and pay with certificate distribution, extra CPU on backends and loss of layer 7 visibility at the balancer.
Choose mutual TLS for service-to-service traffic when you want a cryptographic workload identity and are willing to run a CA, automate short-lived certificates and handle rotation (a service mesh or SPIFFE helps). Choose simple network-level controls plus token authentication when the environment is small and certificate automation does not exist yet; you accept weaker identity guarantees.
Choose ECDSA (P-256) certificates for smaller handshakes and faster signing; choose RSA only for old clients that need it. Dual certificates are possible but double the management work. Choose short lifetimes and automated renewal over long-lived certificates: you cut exposure from key theft and avoid reliance on revocation, and you accept that any broken automation shows up as an outage within weeks.
Choose 0-RTT early data only for idempotent requests, such as GET for cacheable content; it removes a round trip on repeats but allows replay by an attacker, so it is wrong for payments and state-changing calls.
practice: Use TLS 1.3 with TLS 1.2 as the fallback, and disable older versions. Take the default cipher suites from a maintained profile such as Mozilla's server-side TLS configuration instead of editing them yourself. Enable HTTP/2 or HTTP/3 through ALPN, turn on session tickets and OCSP stapling where your server supports it, and add HSTS (Strict-Transport-Security) once everything on the domain works over HTTPS.
Automate certificates: ACME with Let's Encrypt or your cloud's certificate manager for public names, cert-manager for Kubernetes, and an internal CA with short-lived certificates for service identity. Alert on any certificate expiring in under 14 to 21 days, and monitor the real chain from outside (openssl s_client -connect host:443 -servername host shows the chain, versions and verification result). Test your endpoints with SSL Labs or testssl.sh.
In code, never disable verification. Verify the hostname as well as the chain, load a custom CA bundle when needed, and set connect and handshake timeouts. For Kafka, Spark and database clients, enable TLS for brokers and drivers, and remember that JVM truststores are separate from the operating system's: update them when your private CA changes. Reuse connections to avoid paying the handshake each time, and keep connection pools sized so that rotation of certificates does not cause a flood of reconnects.
Watch for protocol-level costs in latency budgets: one extra round trip for TLS on every new connection, and a larger first flight with post-quantum groups. When you must inspect traffic, do it at a controlled termination point and log who can see plaintext.

Records use AEAD ciphers, which give encryption and integrity together.

What do you check and how do you prevent it? || The certificate or an intermediate probably expired, or the chain changed. Forging a signature requires breaking it during the handshake, which a future computer cannot do retroactively, and post-quantum signatures are large and still being integrated into PKI.

@@ sockets
value: A socket is the operating system's handle for one end of a network conversation. A program creates a socket, connects it or accepts connections on it, and then reads and writes bytes through it with the same calls it uses for files. Everything underneath, such as TCP state, retransmission, congestion control, routing and the network card, is the kernel's job. Every server, client library and database driver reaches the network through this interface, whether the programmer sees it or not.
The idea matters because the socket is where application code meets the limits of the machine. The size of a socket's buffers decides how much data can be in flight. The number of open file descriptors and available local ports decides how many connections one process or one client machine can hold. The way the program waits for sockets (one blocking thread per connection, or one event loop watching thousands) decides whether a server handles 1,000 or 1,000,000 connections. Many "mysterious" production problems, such as connection resets, timeouts under load and latency spikes of exactly 40 ms, are explained by how sockets work.
Sockets stand on two lower concepts. System calls (L3) are the only door from a user program into the kernel: socket, bind, listen, accept, connect, send, recv and close are system calls, and each crossing costs time and a copy of the data. TCP (L3) is what a stream socket actually is: the kernel's TCP state machine, with its send buffer, receive buffer, window and timers, hangs behind the descriptor. The layers above build on this directly: zero-copy I/O tries to remove the copies between kernel and user space, remote procedure calls (rpc) run over TCP connections opened with sockets, and local tool servers for LLM agents often speak over stdio or Unix sockets.
terms: File descriptor — a small integer that a process uses to refer to an open file, pipe or socket; the kernel keeps the real object.
Stream socket (SOCK_STREAM) — a socket for a reliable ordered byte stream, which means TCP on the internet.
Datagram socket (SOCK_DGRAM) — a socket for independent messages, which means UDP.
Listening socket — a socket that waits for incoming connections; each accepted connection gets a new, separate socket.
Backlog — the queue of connections that finished the handshake but that the program has not yet accepted.
Socket buffer — kernel memory that holds data waiting to be sent (until acknowledged) or waiting to be read by the program.
Blocking vs non-blocking — a blocking call waits until it can finish; a non-blocking call returns at once with an error such as EAGAIN if it cannot.
I/O multiplexing — waiting on many sockets at once with one call (select, poll, epoll, kqueue) and acting only on the ready ones.
Ephemeral port — a temporary local port, chosen by the kernel for the client side of an outgoing connection.
TIME_WAIT — a TCP state, usually 60 seconds on Linux, that the side that closes first stays in so that late packets of the old connection do not confuse a new one.
history: The sockets interface was created at the University of California, Berkeley, for 4.2BSD, released in August 1983, funded by DARPA to put TCP/IP into Unix. Bill Joy and colleagues of the Computer Systems Research Group designed it so that a network connection looks like a file: you get a descriptor and call read and write. That choice fit the Unix idea that "everything is a file", and was copied by nearly every other system: Windows added Winsock in 1992 to 1993, and POSIX standardized the interface later. W. Richard Stevens' book "UNIX Network Programming" (1990, with later editions) taught generations of engineers how to use it.
The early model was one process, and later one thread, for each connection, using blocking calls. That is easy to write and wasteful: each thread needs a stack and a scheduler slot, and a thousand threads spend much time switching. In 1999 Dan Kegel's "C10K problem" page asked how to serve 10,000 simultaneous clients on one machine and gathered the answer: do not block, and ask the kernel which sockets are ready. select (1983) and poll scan the whole list on each call, which is O(n). FreeBSD added kqueue in 2000 and Linux added epoll in 2002 (kernel 2.5.44), which keep the interest list inside the kernel and return only ready descriptors. Windows used I/O completion ports. Nginx (2004), Node.js (2009) and Netty were built on this model.
The next change targets the system call cost itself. Linux io_uring (kernel 5.1, 2019, by Jens Axboe) lets a program put many requests into a shared ring buffer and read completions from another ring, with few or no system calls per operation. Alongside, kernel-bypass libraries (DPDK, 2010s), RDMA and eBPF-based paths move packet handling out of the standard socket path where throughput or latency demands it. Linux also gained SO_REUSEPORT (3.9, 2013) and many tuning options for high-rate servers.
how: A server begins with socket(AF_INET, SOCK_STREAM, 0), which asks the kernel for a TCP endpoint and returns a file descriptor, say 3. The descriptor indexes a table of the process's open files; the kernel entry points to a socket object, which points to the protocol's own state (for TCP, the connection control block with sequence numbers, timers and buffers). The server calls bind(fd, address and port) to claim a local port, for example 8080, and then listen(fd, backlog) to mark the socket as accepting connections. From now on the kernel itself answers SYN packets for that port. It does not need the program to run for the handshake.
The kernel keeps two queues per listening socket. A new SYN creates an entry in the SYN queue (half-open connections). When the three-way handshake finishes, the connection moves to the accept queue. The program's accept(fd) call takes one finished connection out of that queue and returns a new descriptor, say 4, for that one client. The listening descriptor stays open for the next. If the accept queue is full because the program is too slow, the kernel drops the final ACK or ignores new SYNs, and the client retransmits its SYN after one second, which shows up as a connect delay of exactly 1 s, 3 s and so on. The queue size is the smaller of the backlog argument and net.core.somaxconn (4,096 by default since Linux 5.4; it was 128 before).
A client calls socket() and connect(fd, server address). If it never called bind, the kernel picks a local address and an ephemeral port from net.ipv4.ip_local_port_range (default 32768 to 60999, so 28,232 ports). A TCP connection is identified by the four-tuple of source address and port plus destination address and port, so one client can have 28,232 connections to one destination address and port at the same time, and a different destination gives a new set. The connect call blocks for the handshake: one round trip.
Data moves with send and recv (or write and read). A send copies bytes from the program into the socket's send buffer and returns; the kernel's TCP sends them as the window allows, and keeps them until they are acknowledged, in case of retransmission. If the buffer is full, a blocking send waits and a non-blocking one returns EAGAIN. This is how TCP flow control and congestion control reach the program: a slow receiver or a slow network makes the buffer fill and makes the writer wait. The recv call copies bytes from the receive buffer into the program. It can return fewer bytes than requested, and one send does not map to one recv. TCP preserves the order of bytes and no message boundaries, so every protocol must frame its messages, usually with a length prefix, as Kafka's wire protocol and HTTP/2 do.
Closing is subtle. close() ends the program's interest; the kernel still sends buffered data and then a FIN. A recv that returns 0 means the peer sent FIN, so no more data will arrive. shutdown(SHUT_WR) closes only the sending direction (a half-close), so a client can say "I am done sending" and still read the reply. If the peer has already gone and you keep writing, the first write may succeed but the peer replies with RST (reset), and the next write fails with EPIPE or ECONNRESET. The side that closes first enters TIME_WAIT for 60 seconds on Linux, holding its port.
To serve many connections, a server uses I/O multiplexing. With epoll, the program creates an epoll instance, registers each socket with epoll_ctl, and calls epoll_wait, which sleeps until some sockets are ready and returns only those. Sockets are set non-blocking, and the program reads or writes until EAGAIN. Level-triggered mode reports a socket as long as it is ready; edge-triggered mode reports only changes and requires reading until EAGAIN. One thread can then handle tens of thousands of idle connections, because an idle connection costs only kernel memory (a few KB), not a thread. Kafka brokers, Netty, nginx and Node.js work this way, with a few event-loop threads and a pool of workers for slow tasks.
Socket options tune behaviour. TCP_NODELAY turns off Nagle's algorithm, which otherwise holds small writes until the previous data is acknowledged. SO_REUSEADDR lets a server restart while old connections are in TIME_WAIT. SO_REUSEPORT lets several processes or threads listen on the same port, and the kernel spreads incoming connections among them. SO_KEEPALIVE makes the kernel probe idle connections (first probe after 2 hours by default). SO_RCVBUF and SO_SNDBUF set buffer sizes; setting them by hand switches off Linux's automatic tuning, so most programs should leave them alone.

example: A minimal echo server shows the sequence. It calls socket, bind to port 7000, listen, then loops on accept. A client connects, sends "hello" and waits. The server's recv returns 5 bytes, and its send writes them back. When the client closes, the server's recv returns 0 and the server closes the descriptor.
Now the numbers. First, the framing problem. A client sends two messages with send("HEAD", 4) and send("BODY...", 100). The server may see them as one recv of 104 bytes, or three recvs of 50, 50 and 4 bytes. Never assume the boundaries; a length prefix such as "4 bytes giving the length, then the bytes" lets the reader loop until it has exactly the number it needs.
Second, the latency trap. A client writes a 4-byte header and then a 1,000-byte body in two separate small writes. With Nagle's algorithm on, the second write waits until the first is acknowledged. The server's TCP delays its acknowledgment up to 40 ms hoping to piggyback it on a reply. The result is a stall of about 40 ms on every request, a famous bug. The fix is to set TCP_NODELAY, or better to combine both parts into one write (writev) so one segment goes out.
Third, port exhaustion. A client service talks to one backend (same destination address and port). It has 28,232 ephemeral ports. If it opens a new connection per request and closes it, each closed connection leaves a port in TIME_WAIT for 60 s. The sustainable rate is 28,232 ÷ 60 ≈ 470 new connections per second. Beyond that, connect fails with "cannot assign requested address". With a pool of reused connections, one connection can carry thousands of requests. Putting the backend behind several addresses, or widening the port range, raises the limit.
Fourth, buffer sizing. A transfer at 1 Gbit/s over a 20 ms round trip has a bandwidth-delay product of 1 Gbit/s × 0.02 s = 20 Mbit = 2.5 MB. The receive buffer must hold at least this much for the sender to keep the link full. Linux autotuning raises the receive buffer up to the maximum in tcp_rmem (about 6 MB by default), so this works; if a program set SO_RCVBUF to 64 KB by hand, throughput would be capped at 64 KB ÷ 0.02 s = 3.2 MB/s, about 26 Mbit/s.
intuition: A phone socket in the wall: you plug in, dial, and talk, and the wiring behind it is the kernel's job.
The design is natural because it reuses the most successful idea in Unix: treat everything as a stream of bytes with a handle. The program does not need to know about packets, windows or routes, only about "this connection". The few extra calls (bind, listen, accept) exist because a network conversation has a rendezvous problem that a file does not: one side must wait for the other to show up. Everything else is the same read and write.
mistakes: People often think one send call produces one recv call on the other side. In fact TCP is a byte stream. Data can be split or merged arbitrarily, so a program must read in a loop and frame its messages. Tests on localhost often hide this because small messages usually arrive intact.
People often think a successful send means the peer received the data. In fact it means the kernel accepted the bytes into its send buffer. They may still be waiting, lost or sent to a peer that has already crashed. Only an application-level acknowledgment proves the peer processed them, and a clean close() does not guarantee delivery either.
People often think TIME_WAIT is a bug or a leak to be removed. In fact it protects against old packets corrupting a new connection with the same four-tuple. Tuning it away with tricks can cause hard-to-find data corruption. The right fixes are connection reuse, letting the other side close first, and enough ports and addresses.
People often think running out of file descriptors is a rare edge case. In fact the default soft limit is often 1,024, and every connection, file, pipe and epoll instance counts. A busy server hits it long before it hits CPU or memory limits, and the symptom is "too many open files" errors.
friction: Each byte crosses the kernel boundary. A receive copies data from the network card into kernel buffers and then into user memory; a send copies the other way, and each system call costs from a fraction of a microsecond to a few microseconds, more with security mitigations. At 100 Gbit/s with small messages, a core cannot keep up, which is why high-end systems use zero-copy calls (sendfile, MSG_ZEROCOPY), batching (io_uring), offloads, or bypass the kernel with DPDK and RDMA. The cost is a loss of the standard tools and portability.
Limits are many and quiet. File descriptors, the accept backlog, ephemeral ports, conntrack table entries, socket buffer memory and TIME_WAIT all have separate caps, and failures look like timeouts or resets, not clear errors. The half-open and half-closed states (CLOSE_WAIT piling up because the program forgot to close; FIN_WAIT2; a peer that vanishes without sending FIN) leave connections dead without anyone noticing, until keepalives or timeouts notice, which by default can take two hours.
Programming errors are common. Handling partial reads and writes, EINTR and EAGAIN, SIGPIPE on write to a closed socket, back-pressure when the peer is slow, timeouts on every call, and graceful shutdown (stop accepting, finish in-flight work, then close) all have to be done by hand or by a library. Mixing blocking and non-blocking logic is a typical source of stalls. Portability differs between Linux epoll, BSD kqueue, Windows IOCP and, in Java, NIO; most people rely on libraries such as Netty, libuv or Tokio, which hide this but also add their own behaviour to learn.
tradeoffs: Choose thread-per-connection with blocking sockets when connection counts are modest (hundreds to a few thousand), the code must be simple, and each request does real work. Choose an event loop with non-blocking sockets when you hold tens of thousands of mostly idle connections (gateways, push services, chat, brokers). You give up straight-line code and must avoid any blocking call in the loop; virtual threads (Java 21) and goroutines offer a middle path with blocking-style code and cheap threads.
Choose epoll (or kqueue) over select or poll for any server with more than a few hundred connections: the cost scales with ready sockets and not with all sockets. Choose io_uring when system call overhead dominates (very high rates, storage plus network in one loop) and you accept a newer, more complex API and a history of kernel security fixes, which makes some environments disable it.
Choose connection pooling and keep-alive for clients that call the same service repeatedly: it avoids handshake round trips, slow start and port exhaustion. Choose a connection per request only for rare or long calls. The pool needs limits, health checks and idle timeouts shorter than any firewall or load balancer in the path (for example an AWS NLB drops idle TCP flows after 350 seconds).
Choose a Unix domain socket for communication between processes on the same host (local proxies, databases, container runtimes): no TCP processing, lower latency and file-permission access control. Choose TCP loopback or a real network socket when the peer may move to another machine.
practice: Inspect first. ss -tan shows connection states and counts (a large number of TIME_WAIT is normal for a client making many short calls; piles of CLOSE_WAIT mean your program is not closing). ss -ltn shows listening sockets: Recv-Q is the current accept queue length and Send-Q is its maximum, so a Recv-Q near the maximum means the accept loop is too slow. ss -ti shows per-connection RTT, window and retransmission details. Check limits with ulimit -n, cat /proc/sys/net/core/somaxconn and sysctl net.ipv4.ip_local_port_range.
Set sane defaults. Raise the file descriptor limit for servers (systemd LimitNOFILE of 65,536 or more), set explicit connect, read and write timeouts on every client socket, enable keepalive with shorter intervals than the default for long-lived idle connections, and reuse connections through a pool. Frame messages explicitly and handle partial reads. Set TCP_NODELAY in client libraries for RPC. Leave buffer sizes to Linux autotuning unless you have measured a reason, and raise tcp_rmem and tcp_wmem maximums for high bandwidth-delay paths such as cross-region replication.
For servers, use a proven framework (Netty, nginx, Tokio, Go's net package) rather than raw epoll code. Handle shutdown gracefully, apply backpressure (stop reading when downstream is slow), and bound queues everywhere. Make the accept loop fast and hand off work. Use SO_REUSEPORT to spread accepts across cores when one acceptor thread becomes a bottleneck.
interview: Your server stops accepting new connections under load but CPU is low. What do you check? || Look at the accept queue (ss -ltn Recv-Q versus Send-Q) and ListenOverflows in nstat, the backlog and somaxconn settings, the file descriptor limit (too many open files), and whether the accept loop is blocked or slow. Then fix the cause: faster accept, larger backlog, more descriptors, or SO_REUSEPORT with more acceptors.
Explain how epoll lets one thread handle 100,000 connections, and what can still go wrong. || The kernel keeps the interest list and wakes the thread only with the ready sockets, so cost grows with activity and not with connection count; idle connections cost only memory. Problems: a blocking call or heavy computation stalls all connections, one connection with a slow reader can fill the buffers (needs backpressure), and a single thread may become the CPU bottleneck so you use one loop per core.
Why can a client run out of ports even when it has few simultaneous connections? || Closed connections stay in TIME_WAIT for 60 seconds, occupying their four-tuple. A client opening and closing connections to a single destination at more than about 470 per second (28,232 ports ÷ 60 s) exhausts the range. Reuse connections, add destination addresses or widen the port range.
What does recv returning 0 mean, versus -1 with EAGAIN? || Zero means the peer closed its sending direction (FIN), so no more data will arrive. EAGAIN on a non-blocking socket means no data is available right now; try again when epoll reports it ready.
Why do two small writes sometimes cost 40 ms, and how do you fix it? || Nagle's algorithm holds the second small write until the first is acknowledged, while the receiver's delayed ACK waits up to 40 ms. Set TCP_NODELAY and/or send the message in a single write.
quiz: What does accept() return? || A new file descriptor for one established connection. The listening socket stays open and can accept further clients.
Why must protocols built on TCP add their own message framing? || TCP delivers an ordered byte stream with no message boundaries, so one send may arrive as several recvs or several sends as one. A length prefix or delimiter lets the reader find message boundaries.
A client makes short connections to one backend. With 28,232 ports and a 60 s TIME_WAIT, what is the maximum sustained connection rate? || About 28,232 ÷ 60 ≈ 470 new connections per second to that destination; more fails with address-in-use style errors unless connections are reused.
What limits throughput to 3.2 MB/s if a program sets SO_RCVBUF to 64 KB on a 20 ms round-trip path? || A sender can have at most one receive window in flight per round trip: 64 KB ÷ 0.02 s = 3.2 MB/s, no matter how fast the link is.
When would you choose an event loop over thread-per-connection? || When you hold tens of thousands of mostly idle or slow connections (gateways, brokers, push services), because a thread per connection costs memory and context switching. Choose threads for fewer, busier connections and simpler code.
