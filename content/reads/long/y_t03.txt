@@+ sqlite
tradeoffs: SQLite or PostgreSQL. Choose SQLite when one process (or several on one machine) owns the data, the dataset is below a few hundred gigabytes, and write transactions are short. A write lock held for 1 ms caps one file at about 1,000 write transactions per second; with 0.2 ms transactions it is about 5,000. Choose PostgreSQL when several machines must write the same data, when you need roles and row-level permissions, or when one dataset needs more than a few thousand write transactions per second. You give up, with SQLite, the network, replication and access control; with PostgreSQL, you give up the zero-operations deployment and pay a network round trip (about 0.2–1 ms inside a data centre) on every statement, compared with a function call of a few microseconds.
One file per tenant or one shared database. A file per tenant gives isolation, simple deletion (delete the file, which helps with erasure requests), cheap moves between servers and writes that scale with the number of tenants. It costs you cross-tenant queries, schema migrations that must run against 50,000 files, and a connection and page-cache budget per open file. Choose it when tenants rarely interact and the biggest tenant stays under the single-writer limit. Choose one shared client-server database when you report across tenants every day or when tenant sizes are very skewed.
Rollback journal or WAL, and how much durability to buy. WAL gives concurrent readers and usually faster commits, but it needs shared memory on one host, adds -wal and -shm files, and lets the WAL grow if a reader never ends. The rollback journal works on more unusual file systems and has a single-file backup story, but readers and the writer block each other. With WAL, synchronous = NORMAL removes the per-commit fsync (about 2–10 ms on typical flash) at the price of losing the last few commits after a power cut; FULL keeps every acknowledged commit and limits you to roughly 100–500 commits per second on a slow device. A mobile cache can accept NORMAL; a payments ledger cannot.
SQLite or DuckDB. SQLite stores rows and is built for point reads and small writes; DuckDB stores columns and is built for scans and aggregates, often tens of times faster on a group-by over millions of rows but weak at many small concurrent updates. Choose SQLite for the application's state and DuckDB for analysing an export of it; DuckDB can even attach and query a SQLite file directly. When you want SQLite semantics with replication, the options in the map are managed layers such as Cloudflare D1 or Turso and Litestream for streaming backups; you give up the pure "just a file" simplicity and take on the layer's limits and maturity.
interview: A team wants to run their web service on SQLite with three application servers. What do you say? || Three servers cannot safely share one SQLite file over a network file system, because locks are unreliable and WAL needs shared memory on one host. Options: keep SQLite but make one server the only writer and replicate with Litestream, LiteFS or a managed layer; split the data into per-tenant files each owned by one server; or move to PostgreSQL. The deciding question is whether more than one machine must write the same data.
Your SQLite import of 10 million rows takes an hour. How do you debug and fix it? || First check whether each insert is its own transaction, since each commit pays an fsync of several milliseconds. Wrap batches of 10,000 to 100,000 inserts in one transaction, use WAL with synchronous = NORMAL if a short durability window is acceptable, reuse one prepared statement, and create secondary indexes after the load. This usually brings the job to seconds or a few minutes.
Why is "database is locked" appearing under load, even in WAL mode? || WAL allows one writer at a time, so a second writer waits and then fails with SQLITE_BUSY after busy_timeout. A common hidden cause is a transaction that begins as a read and later upgrades to a write after another writer has committed, which fails immediately; BEGIN IMMEDIATE avoids it. Also look for long write transactions that wait on the network, and shorten them.
A reader process is killed while holding a transaction and the WAL file is 40 GB. What happened and what is the fix? || A checkpoint cannot pass the oldest active reader's end mark, so a reader that stays open stops the WAL from being reset and the file keeps growing, and reads slow down as the wal-index grows. Close the stuck reader, run PRAGMA wal_checkpoint(TRUNCATE), and set a rule that read transactions are short. Monitor WAL size as an alert metric.
When would you refuse to use SQLite for a new server-side design? || When the same dataset needs sustained writes beyond about one thousand to a few thousand transactions per second, when multiple machines write it, when users need fine-grained permissions, or when online schema change and failover must be built in. In those cases PostgreSQL or a distributed SQL system carries features that you would otherwise have to build around SQLite.
@@+ mongodb
tradeoffs: MongoDB or PostgreSQL with JSONB. Choose MongoDB when the main object is a nested document that is read and written whole, its shape varies between records, and you expect to shard across machines. Choose PostgreSQL when the data is shared across many parents, when you need joins, constraints and multi-row transactions as the normal case, or when one machine (up to a few terabytes and tens of thousands of writes per second) is enough. With MongoDB you give up cheap joins and database-enforced integrity; with PostgreSQL JSONB you give up built-in sharding and the convenience of partial in-place document updates (a JSONB change rewrites the whole value).
Embed or reference. Embed when the child data is bounded (say under a few hundred items, far below the 16 MB limit) and is nearly always read with the parent: one read, one atomic update. Reference when children are shared, grow without bound, or are updated much more often than the parent; then you pay a $lookup or a second query, often 2–10 times slower than an embedded read. A frequent compromise is to embed a bounded summary (the last 10 comments) and reference the rest.
Write concern and read concern. w: 1 acknowledges in a fraction of a millisecond but can be rolled back after a failover; w: "majority" costs about 1–3 ms extra inside one region and about the inter-region round trip if a majority spans regions, and it is the default since 5.0. Choose w: 1 only for data you can regenerate, such as logs and metrics. Reading from secondaries scales reads and costs staleness of replication lag (normally under a second); keep money and inventory reads on the primary or in causally consistent sessions.
When to shard. A replica set on current hardware commonly serves several terabytes and tens of thousands of operations per second. Shard when the working set cannot fit in one node's RAM, when one primary's write rate is the limit, or when data must live in zones for residency. Every shard adds a scatter-gather cost to queries without the shard key and a config server and balancer to operate. Vertical scaling and archiving old data to cheaper storage are cheaper first steps. Self-managed or Atlas: Atlas removes patching, backups and upgrades at a price premium (often 2–3 times the raw cloud instance cost); self-managed gives control and a lower bill, but you take the pager, and the SSPL limits how you may resell it.
interview: You have a MongoDB collection of orders with embedded line items. A product manager now wants per-product sales reports. What do you do? || Embedded items make per-product aggregation require $unwind over every order, which scans all documents. Options: add a multikey index on the product field for selective queries, maintain a pre-aggregated collection updated in the same transaction or from a change stream, or send the data to an analytical store through change streams. The choice depends on report freshness and volume; do not reshape the operational model for reports.
Explain what happens to an acknowledged write when the primary crashes, with w: 1 and with majority. || With w: 1 the write may exist only on the old primary. A secondary becomes primary without it, and when the old node rejoins, the write is rolled back. With w: "majority" the client is acknowledged only after most members journaled it, and the new primary must have it because elections choose the member with the most recent oplog among a majority. So it survives a single failure.
Why did the team's 10-shard cluster have one hot shard, and how do you fix it? || The shard key is probably monotonic (a timestamp or ObjectId), so every insert goes to the highest chunk. Fix by moving to a hashed key or a compound key with a well-spread leading field such as device or tenant, using live resharding (5.0 and later), which needs spare disk and I/O capacity because it copies the collection. Ranged queries then lose locality, so also check which queries include the key.
Someone proposes using MongoDB multi-document transactions for every request. Good idea? || Usually not. Single-document updates are already atomic and cheaper; multi-document transactions use snapshots, hold versions in the WiredTiger cache, have a 60-second default limit and need two-phase commit across shards. A model that keeps each invariant in one document avoids most of them. Use transactions for rare cross-document changes, with retries on write conflicts.
How would you decide between MongoDB and DynamoDB for a new service on AWS? || DynamoDB if access patterns are few, known and key-based, you want no cluster operations and predictable single-digit-millisecond latency at any scale. MongoDB if you need rich ad-hoc queries, secondary indexes on many fields, aggregation and search, or portability across clouds. DynamoDB costs you flexibility and carries AWS lock-in; MongoDB costs you cluster design, shard-key care and, on Atlas, a higher bill.
@@+ cassandra
tradeoffs: Cassandra or a Dynamo-style managed store (DynamoDB). Choose Cassandra when you want multi-data-centre active-active writes under your control, the lowest cost per terabyte on owned hardware, and no cloud vendor lock-in. Choose DynamoDB when you are on AWS and prefer paying for requests to running a cluster: you give up control over placement, compaction and cost shape, and gain the removal of repairs, upgrades and capacity planning. A rough rule is that Cassandra wins on cost once you can keep nodes 50–70% utilised with a team that already runs it; DynamoDB wins for spiky or small workloads.
Cassandra or ScyllaDB. Both speak the same protocol and data model. Scylla is written in C++ with one shard per core and no JVM garbage collection, so it often serves the same load on a third to a half of the nodes and has lower p99 latency. Cassandra has the larger community, the Apache governance, SAI indexes and the new Accord transactions. Choose Scylla when p99 and node count drive cost; choose Cassandra when ecosystem, licensing and features such as Accord matter more than raw efficiency.
Consistency level. With replication factor 3, QUORUM reads and writes (2 + 2 > 3) give read-your-writes and cost the latency of the second-fastest replica; LOCAL_QUORUM keeps this inside one data centre at 1–5 ms, while a global QUORUM pays the cross-region delay (50–200 ms). ONE is fastest and survives two failures, but a read can return stale data until repair or read repair fixes it. Choose LOCAL_QUORUM by default, ONE for idempotent time-series writes you can re-send, and LWT or Accord only for compare-and-set; a lightweight transaction needs several round trips (four with the old Paxos, about two with Paxos v2 from 4.1) and is several times slower than a plain write.
Compaction strategy. Size-tiered is cheapest for writes (low write amplification) but needs up to about 50% spare disk and can read many files; leveled has about 10 times lower read amplification and bounded space overhead, but it rewrites data many times (write amplification often 10 or more), which hurts write-heavy tables; time-window suits TTL time series, because whole files expire together. Choosing wrongly shows up months later as disk full or read latency growth.
Cassandra or a distributed SQL database (CockroachDB, Spanner). Pick Cassandra when you query by key, accept denormalised copies and want write availability during partitions. Pick distributed SQL when you need joins, secondary access paths and serializable multi-row transactions, and can pay a Raft or Paxos majority on every write and some retry logic.
interview: Why can a Cassandra cluster with 100 nodes still have one overloaded node? || Data is placed by hashing the partition key, so a single hot or very large partition lives on only RF replicas whatever the cluster size. Fix the data model: add a bucket (such as the day or a hash suffix) to the partition key, keep partitions below about 100 MB, and avoid keys with skewed popularity. Adding nodes does not help a hot key.
Explain why read and write quorum of 2 with RF 3 gives read-your-writes, and when it still fails. || Any two replicas out of three overlap in at least one, so a quorum read includes a replica that acknowledged the latest quorum write, and timestamps pick it. It can still fail when clocks skew and last-write-wins picks the wrong version, when a write times out but partially succeeds, or when writers use different consistency levels. Quorum is not linearizable without LWT or Accord.
What is a tombstone problem, and how do you avoid it? || A delete writes a tombstone marker that must stay for gc_grace_seconds (10 days by default) so that repair can propagate it. Queries over partitions with many tombstones scan them all and slow down or fail. Avoid using the table as a queue, avoid writing nulls, use TTLs with time-window compaction so whole files drop, and run repair inside gc_grace.
You must add a data centre in another region. What do you change and what can go wrong? || Add the data centre to the keyspace's NetworkTopologyStrategy replication settings, bootstrap nodes there, then run rebuild to stream data from the existing data centre. Use LOCAL_ consistency levels in clients so latency stays local. Risks are streaming load on the source nodes, clients still using global levels, and repair taking days on large data.
When would you say Cassandra is the wrong choice? || When the workload needs ad-hoc queries, joins, multi-row transactions, or strong consistency as the default, or when the dataset is small (a few hundred gigabytes) and the team has no Cassandra experience. A managed PostgreSQL, or a distributed SQL database, costs less to operate there.
@@+ dynamodb
tradeoffs: On-demand or provisioned capacity. On-demand needs no planning and absorbs spikes, but each request costs several times more than the same request on fully used provisioned capacity. Provisioned with auto scaling is cheaper once traffic is steady, with a predictable daily curve, and you can buy reserved capacity for the base. Start on-demand; switch a table when its monthly bill is large enough to justify the capacity work and the traffic stays above roughly 20–30% of the provisioned peak most of the day. You give up simplicity and gain a lower bill, and you accept throttling when the forecast is wrong.
Single-table or multiple tables. Single-table design puts several entity types under one partition key so one Query (single-digit milliseconds, up to 1 MB per page) returns related items; it saves requests and money, but every new access pattern may need a new GSI or a migration, and the table is hard to read. Multiple tables are easier to evolve and to give separate capacity, backups and permissions, but joins become several round trips in the application. Choose single-table when the access patterns are stable and latency or cost per request matters at very large scale; choose several tables when the model is still changing or teams own different entities.
Consistency and index choices. Eventually consistent reads cost half the read units of strongly consistent ones and may lag for tens of milliseconds; use strong reads for read-after-write on the base table. GSIs are always eventually consistent, repeat the write cost for every projected change, and have their own capacity; an LSI shares the partition key, supports strong reads and limits item collections to 10 GB. Choose a GSI for most new patterns; projecting only needed attributes keeps it cheap.
Transactions and global tables. Transactions (up to 100 items, 4 MB) cost double the units and fail under contention; use conditional writes with a version attribute for single-item concurrency instead. For multi-region, global tables with multiple writers are fast and available but resolve conflicts by last writer wins; strongly consistent global tables avoid conflicts and pay a cross-region round trip on every write. If you need ad-hoc SQL, secondary access paths on many columns, or items above 400 KB, DynamoDB is the wrong tool; MongoDB, PostgreSQL or Cassandra (no vendor lock-in) are the alternatives.
interview: How does DynamoDB spread load, and how can a table still throttle at far below its provisioned capacity? || Items are placed by a hash of the partition key into partitions, each limited to about 3,000 read units and 1,000 write units per second. If traffic concentrates on one key, or on keys that hash to one partition, that partition throttles even though the table total is idle. Fix with higher-cardinality keys, write sharding with a suffix, caching (DAX or an application cache), or splitting large item collections.
Design the keys for a chat application: messages per conversation, newest first, plus a user's conversation list. || Table with partition key conversation_id and sort key a time-ordered ID (ULID), so Query with ScanIndexForward = false gives newest first with pagination. A second item per participant or a GSI keyed by user_id with sort key last-message time serves the conversation list. Very large group chats need bucketed partition keys (conversation_id#day) to bound item collections.
What does a conditional write give you, and how would you implement an idempotent payment? || A ConditionExpression makes a write succeed only if an attribute condition holds, atomically. For idempotency, put the payment ID as the key and use attribute_not_exists(pk), so a retry fails safely and returns the stored result. For updates, include a version number in the condition and increment it, giving optimistic concurrency.
Your DynamoDB bill doubled after adding two GSIs. Why? || Each write to the base table also writes to every GSI whose key or projected attributes change, and each GSI is charged for its own write units and storage. Large projections multiply the cost. Reduce by projecting keys only, removing unused indexes, and sparse indexes that only contain items with the indexed attribute.
How would you design for the possibility that DynamoDB is unavailable in one region? || Decide the failure goal first. Use global tables in two regions with clients that fail over, accept last-writer-wins for conflicts or use strongly consistent global tables if no conflict is tolerable, make writes idempotent, and rehearse failover including DNS and credentials. Also remove hidden dependencies on a single region's control plane.
@@+ spanner
tradeoffs: Spanner or PostgreSQL. Choose Spanner when one logical SQL database must outgrow a machine, survive the loss of a zone or region with zero data loss, and stay writable and consistent across regions. Choose managed PostgreSQL when the data is a few terabytes and the writes are a few thousand per second in one region: it is cheaper, has the full PostgreSQL feature set and answers a simple write in about 1–2 ms, where Spanner needs a Paxos majority (a few milliseconds in one region, tens to over 100 ms for multi-region configurations that place voters on different continents). You give up the extension ecosystem and low entry price with Spanner; you give up elastic scale-out and cross-region failover without data loss with PostgreSQL.
Spanner or CockroachDB. Both give serializable distributed SQL. Spanner uses TrueTime, so a commit waits out a clock-uncertainty window of a few milliseconds (seven at most, in the original paper) and reads need no restarts; it is a Google-operated service, with Omni now offering a self-managed option. CockroachDB uses hybrid logical clocks with a default maximum offset of 500 ms, can restart reads that fall inside the uncertainty window, but runs on any cloud or your own servers. Choose Spanner on Google Cloud when you want the lowest operating burden; choose CockroachDB when you must run on several clouds or on premises and accept the licence and the clock-sync duty.
Instance configuration. A regional configuration (three zones) keeps writes in a few milliseconds and survives a zone loss; a multi-region configuration survives a region loss and adds the round trip to the nearest voting replicas on each commit, while read-only replicas serve local stale reads. Choose regional unless the business requires region-loss survival; the extra write latency and a price roughly 2–3 times higher are the cost. Put the default leader region where most writes originate.
Read type. A strong read goes to the leader or checks with it; a bounded-staleness or exact-staleness read (for example 10 seconds) is served by the nearest replica in a few milliseconds and does not take locks. Choose stale reads for catalogues, feeds and dashboards, and strong read-write transactions only for what must be current. Transactions that touch several splits add two-phase commit, so interleave parent and child tables and design keys that keep related rows together; if your workload is mostly single-key lookups with no relations, Bigtable-style or DynamoDB-style stores are cheaper alternatives.
interview: Explain commit wait. Why does Spanner wait before releasing locks? || TrueTime returns an interval [earliest, latest] that contains the true time. Spanner gives a transaction a commit timestamp at least as late as the latest bound, then waits until that timestamp is surely in the past before acknowledging. Then any transaction that starts after the commit, anywhere, gets a larger timestamp, giving external consistency. The wait equals the clock uncertainty, a few milliseconds.
How would a system without atomic clocks provide similar guarantees, and what does it give up? || Use hybrid logical clocks with a maximum clock offset assumption. Reads that find a value inside the uncertainty window must restart at a later timestamp, and nodes whose clocks drift beyond the limit must shut down. So it gets serializability and mostly consistent reads, but not the guaranteed external consistency, and it pays occasional read restarts.
Your Spanner write throughput is stuck at a low level though CPU is low. Why? || Likely a hot split caused by a monotonic key such as a timestamp or auto-increment ID, so all writes go to one split served by one leader. Check Key Visualizer, then switch to UUIDv4, a bit-reversed sequence or a hashed leading column. Lock contention in read-write transactions can also cause aborts and retries.
When would you choose regional over multi-region Spanner, and what do you lose? || Choose regional when zone-level survival and single-region latency satisfy the requirement. You lose protection against a whole-region outage and local reads in other regions. Multi-region adds commit latency and cost, so use it when the recovery-point objective for region loss is zero.
A service needs global inventory counters with strong consistency. What are the trade-offs? || Spanner allows a serializable transaction on the counter row, but one hot row serializes all updates at roughly the commit latency, so a few hundred updates per second at best for a cross-region leader. Shard the counter into N rows and sum them on read, or reserve stock in batches per region. This gives up exact instantaneous totals for throughput.
@@+ cockroach
tradeoffs: CockroachDB or PostgreSQL. Choose CockroachDB when one SQL database must keep working after a zone or region fails, grow past one machine's disk or write rate, or hold rows in specific regions. Choose PostgreSQL (with a replica, or managed Aurora) when the data fits one primary and downtime of tens of seconds during failover is acceptable. A single-row write in CockroachDB takes about 2–5 ms in one region and 30–150 ms across regions, because each write needs a Raft majority; PostgreSQL commits in about 1 ms locally. You give up PostgreSQL's full feature set, simplicity and single-node speed; you gain survival goals and horizontal scale.
CockroachDB or Spanner, YugabyteDB, TiDB. Spanner has TrueTime and no clock-offset worries but is Google-only. YugabyteDB reuses PostgreSQL's query layer and so is closer to PostgreSQL behaviour. TiDB speaks the MySQL protocol and splits transaction storage (TiKV) from analytics (TiFlash), which suits mixed workloads. Choose CockroachDB when you want PostgreSQL-wire compatibility, serializable isolation by default and multi-region primitives in SQL (REGIONAL BY ROW); choose TiDB if your estate is MySQL; choose Spanner if you are already on Google Cloud. The licence now needs a paid enterprise licence for larger companies, which is itself a deciding factor.
Survival goal. Zone survival keeps writes inside one region, so latency stays a few milliseconds and you lose nothing if one zone dies, but a region outage stops the database. Region survival places replicas across three regions, so every write waits for the second-nearest region, often 30–100 ms. Choose zone survival for most tables and region survival only for data whose business loss from a regional outage exceeds the latency cost. Table localities (REGIONAL BY ROW, GLOBAL) let you mix both.
Serializable and retries. Serializable isolation prevents write skew and removes a class of correctness bugs, but under contention transactions abort with error 40001 and the client must retry. Choose short transactions, touching hot rows last, follower reads (a few seconds stale) for reports, and queues based on SKIP LOCKED-like patterns or sharded counters for hot rows. Read-committed mode, available in recent versions, reduces retries and gives up some guarantees. Cassandra or DynamoDB avoid these costs by dropping multi-row transactions.
interview: How does CockroachDB execute a write to one row, step by step? || The SQL gateway finds the range that owns the key and sends the request to its leaseholder. The leaseholder proposes the write to the range's Raft group; once a majority of replicas append it to their logs, it is committed and applied to Pebble. The leaseholder also serves consistent reads without a Raft round, using its lease. Cost is one majority round trip plus disk sync.
What is a transaction restart error and how should an application handle it? || It is error 40001: the transaction was pushed or aborted by a conflicting one or by clock uncertainty. The application must retry the whole transaction in a loop with backoff and a retry limit, and must make side effects idempotent or perform them after commit. Short transactions reduce the rate.
Why does CockroachDB care about clock synchronization though it uses Raft? || Raft orders writes inside a range, but transactions across ranges are ordered by timestamps from hybrid logical clocks. If node clocks differ by more than the maximum offset (500 ms by default), a node could serve a stale read, so nodes that detect excessive offset shut down. Use NTP or chrony and alert on offset.
Your sequential primary key creates a hot range. How do you fix it? || A monotonic key sends all inserts to the range at the end of the key space, served by one leaseholder. Use UUIDs, hash-sharded indexes, or a composite key with a well-spread leading column. You lose cheap ordered scans on the original key unless you keep a secondary index.
Latency at 3 regions is 80 ms per write. What are your options? || Move to zone survival with a home region per row (REGIONAL BY ROW), so most writes stay local and a region outage affects only that region's rows; use GLOBAL tables only for read-mostly reference data; or batch writes into fewer transactions. The cost is the loss of region-failure survival for those rows.
@@+ redis
tradeoffs: Redis as a cache or as a primary store. As a cache, a lost key only costs a database read, so asynchronous replication and RDB snapshots are enough and you can run at 100% of RAM with eviction. As a primary store, you must accept that a failover can lose the last second or more of writes (AOF everysec loses up to about 1 second on a crash; asynchronous replicas lose whatever was not yet sent), and you pay for RAM at about 10–30 times the price per gigabyte of SSD storage. Choose a primary-store role only for data that is small, rebuildable or tolerant of loss (sessions, rate-limit counters, leaderboards, queues of jobs that can be retried); use PostgreSQL, DynamoDB or Cassandra for data that must not be lost.
Redis, Valkey, Memcached. Memcached is multi-threaded, stores only byte strings and has no persistence; it is the right tool for a pure, large, simple cache where you want many cores on one box and nothing else. Redis and Valkey cost more memory per key but give data structures (sorted sets, streams, hashes, HyperLogLog) that turn many application loops into one O(log n) command. Choose Memcached when you only need get and set with TTL at the highest throughput per node; choose Redis or Valkey when you need counters, ranking, rate limiting, pub/sub or atomic scripts.
Persistence. No persistence is fastest and fits caches. RDB snapshots every few minutes give a fast restart and small files, but lose everything since the last snapshot and cost a fork (copy-on-write memory can reach up to 2 times the dataset under heavy writes). AOF with fsync every second bounds loss to about a second at a small throughput cost; AOF with fsync always is safest and can cut throughput by an order of magnitude on ordinary disks. Combine RDB and AOF only when you want both quick restarts and small loss windows.
Single instance or Cluster. One instance serves about 100,000 or more simple operations per second per core, and well over a million per second with pipelining, so most applications never need more than a primary and a replica for failover (Sentinel). Choose Cluster when data exceeds one machine's RAM (often 64–256 GB in practice) or when one thread's throughput is the limit. You then give up multi-key operations across slots, simple transactions and Lua across keys; you gain 16,384 hash slots spread across primaries. Locks: use Redis locks for efficiency (avoid duplicate work), and a consensus store such as etcd or a database lock with fencing tokens when correctness depends on mutual exclusion.
interview: Redis is single-threaded. How can it handle 100,000 requests per second, and when does that break? || Commands are in-memory operations of microseconds, there are no locks between them, and the event loop uses epoll to serve many sockets, with I/O threads for reading and writing in newer versions. It breaks when one command is O(N) on a big key (KEYS, a huge ZRANGE, a long Lua script), because it blocks every other client; a CPU-bound workload also cannot use more than one core per instance, so you shard.
What happens to data during a failover? || Replication is asynchronous, so the replica promoted may lack the newest writes and they are lost. WAIT can ask for replica acknowledgement but does not make it strongly consistent. During a partition, an isolated old primary can keep accepting writes that are discarded later. So treat Redis as a fast tier unless loss is acceptable.
Design a rate limiter for 10,000 requests per second across many app servers. || Use a key per client and window, with INCR and EXPIRE in one Lua script or a token bucket in a script, so the check is atomic. Use a hash tag so keys for one client stay in one slot in a cluster. Accept small errors at window edges, or use a sliding window with a sorted set at higher memory cost. Add a local fallback if Redis is down.
Is a Redis lock safe? || Only if the lock is for efficiency. A client can pause (garbage collection, network delay) after its lock expired and then write while another client holds the lock. Correctness needs a fencing token checked by the storage layer, or a consensus system. Redlock across several nodes does not remove the pause problem.
Memory is at 95% and latency is rising. What do you check? || Check the maxmemory policy and eviction counts, big keys (--bigkeys, MEMORY USAGE), fragmentation ratio, replica output buffers, and whether a fork for RDB or AOF rewrite is running. Then fix by TTLs, smaller encodings, hashes for small fields, dropping unused keys, or sharding. Keep headroom of 25–50% if you use persistence.
@@+ valkey
tradeoffs: Valkey or Redis. Choose Valkey when you want a BSD licence with multi-vendor governance (Linux Foundation, supported by AWS, Google Cloud and others), lower managed prices (AWS priced ElastiCache for Valkey roughly 20% below Redis OSS on node-based and about 33% below on serverless) and commands and clients you already use. Choose Redis 8 when you depend on its built-in query engine, JSON, time series and vector features, or on Redis Ltd. commercial support. The two now diverge in features and settings, so you give up easy switching later; migration from Redis 7.2 or earlier is the simple path, and newer Redis data formats may not load.
Valkey or Memcached or an application-local cache. A local in-process cache has no network cost (nanoseconds against 0.2–1 ms) but each server holds its own copy and invalidation is hard; use it for tiny, very hot, rarely changing data, with a short TTL. Memcached suits plain object caches that need all cores; Valkey suits caches that need atomic counters, structures, replication and persistence. A common design is a local cache for the hottest 1% of keys in front of Valkey for the rest, accepting a few seconds of staleness.
Threads and cluster size. Valkey 8 added I/O threads that move socket reads and writes off the main thread, so one node can reach over a million requests per second in the project's tests, at the price of extra CPU cores and some added complexity. Command execution stays single-threaded, so a CPU-heavy command still blocks. Choose I/O threads when a node is network-bound at tens of thousands of connections; choose more shards when memory, not requests, is the limit. A 4-core node cannot also run 8 I/O threads; leave cores for the OS and replication.
Persistence and durability. For a cache, run with replication and no persistence, and let a warm-up job refill. For a store of derived data (feature values, sessions), use AOF everysec plus a replica in another zone and accept a loss window of about a second. Valkey cannot give synchronous durability with strong consistency; for that, use a database. Cluster mode adds failover in a few seconds, and replication of the slot topology; atomic slot migration in Valkey 9 reduces the risk of resharding but does not remove the need for headroom.
interview: Why did Valkey appear and what does it mean for an engineering team? || Redis Ltd. changed the licence in 2024 from BSD to source-available terms, and contributors and cloud vendors forked the last BSD version (7.2) as Valkey under the Linux Foundation. For a team it means a choice of licence and roadmap: Valkey for permissive licensing and managed-service cost, Redis for its newer modules and vendor support. Test compatibility before migrating.
How do you choose an eviction policy? || For a pure cache use allkeys-lru or allkeys-lfu, so the server may remove any key to stay under maxmemory. If some keys must never be evicted (sessions, queues), use volatile-ttl or volatile-lru with TTLs only on cache keys, or noeviction and let writes fail visibly. LFU resists scans better; LRU is simpler.
A cache stampede brings your database down every hour. Why and how do you fix it? || Many keys were set with the same TTL and expire together, or one hot key expires and thousands of requests rebuild it. Add random jitter to TTLs, use request coalescing (a lock or a single-flight per key), refresh before expiry, and serve stale data while one worker refreshes.
Describe how a Valkey cluster routes a request and what a client must handle. || The key is hashed with CRC16 modulo 16,384 to a slot, and each primary owns a range of slots. A cluster-aware client keeps the slot map and sends commands to the right node; if the slot moved it receives MOVED or ASK and updates its map. Multi-key commands must use keys in one slot, which hash tags provide.
Would you put a payment ledger in Valkey? || No. Asynchronous replication and AOF fsync intervals mean acknowledged writes can be lost on failover, and there are no multi-key transactions across slots. A ledger needs a durable relational database. Valkey can hold derived or temporary data around it, such as idempotency keys with TTL.
@@+ rocksdb
tradeoffs: RocksDB or a B-tree engine (InnoDB, SQLite, LMDB). A B-tree updates pages in place: reads touch about 3–4 pages, but a random write rewrites a 4–16 KB page, so write amplification on small records is high and writes are random I/O. An LSM tree writes sequentially into the memtable and sorted files, which suits write-heavy workloads, compresses well (often 2–3 times smaller than a B-tree) and wears SSDs less; the price is that a read may check several levels (Bloom filters at about 10 bits per key bring false positives to roughly 1%) and compaction rewrites data in the background. Choose RocksDB when writes are at least comparable to reads, keys are written once and rarely updated, or space matters; choose a B-tree when reads dominate and tail latency must be flat.
Compaction style. Leveled compaction keeps about 1.1 times the data size on disk and one lookup per level, but a byte may be rewritten 10–30 times (write amplification). Universal compaction rewrites far less (often 3–8 times) but can need up to about 2 times the space during a merge and reads more files. FIFO compaction simply drops the oldest files and fits TTL logs and caches. Choose leveled for read-heavy or space-bound data on expensive SSDs; universal for bursty, write-heavy data where disk is cheap; FIFO when old data has no value.
Values and sizes. For values below a few hundred bytes the LSM default is right. For values of 1 KB and more, compaction rewrites large values repeatedly; BlobDB keeps values in separate files so only keys are rewritten, trading extra reads and garbage collection of blob files for much lower write amplification. If values are megabytes, store them in object storage (s3) and keep a pointer in RocksDB.
Embedded or standalone. RocksDB has no network, replication or query language; embedding it in your process (Flink state, Kafka Streams, a Raft state machine) removes a network hop and gives microsecond access, but you own backup, memory sizing and recovery. A standalone store (Cassandra, CockroachDB with Pebble, TiKV, or a managed service) gives replication and operations at the price of latency and a bigger system. Choose RocksDB directly only when you are building a system, or when local state is large and needs ordered keys; for a simple local database, SQLite is easier.
interview: Walk through how RocksDB handles a write and a read. || A write is appended to the write-ahead log, optionally synced, and inserted into the in-memory memtable (a skip list). When the memtable fills (64 MB by default) it becomes immutable and is flushed to a sorted SST file at level 0. A read checks the memtable, immutable memtables, then level 0 files and one file per deeper level, using Bloom filters to skip files that cannot contain the key.
What is write amplification, and how would you reduce it? || It is the bytes written to disk divided by the bytes the application wrote, caused mainly by compaction rewriting data as it moves down levels. With leveled compaction and a size ratio of 10 it is often 10–30. Reduce it with universal compaction, a larger memtable and first-level size, key-value separation with BlobDB, or fewer levels; each choice raises space or read cost.
A service sees p99 read latency spikes every few minutes. Where do you look? || Likely compaction or flush bursts competing for disk and CPU, write stalls when level-0 files or pending compaction bytes pass limits, or block cache misses after a large scan evicts hot blocks. Check the stall counters and pending compaction bytes, add a rate limiter and background jobs, use partitioned filters, and give the block cache a fixed budget.
Why do deletes in an LSM tree not free space immediately? || A delete writes a tombstone that hides older versions; the old data is physically removed only when compaction merges the tombstone with it at the bottom level. Heavy delete workloads leave many tombstones that slow scans. Use DeleteRange for ranges, TTL compaction filters or periodic compaction to clean up.
How do you size memory for many RocksDB instances in one process, as in Flink? || Total memory is memtables plus block cache plus index and filter blocks plus iterators. Set a shared cache and a write buffer manager that caps memtable memory across all instances, and count the native memory outside the JVM heap in the container limit. Without this, the container is killed by the operating system although the heap looks healthy.
@@+ neo4j
tradeoffs: A graph database or SQL joins. In a relational database each hop is an index lookup of roughly O(log n), and a join over millions of rows can produce intermediate results that grow with every hop. In Neo4j a hop follows a stored pointer in O(1), and cost depends on the number of relationships visited, not on the table size. Choose Neo4j when the key queries need 3 or more hops of unknown depth (fraud rings, dependency impact, permission inheritance) and the graph fits mostly in memory; choose PostgreSQL, with recursive CTEs, when you traverse 1–3 hops, the data is already there, and you also need aggregates and constraints. Recursive CTEs are fine for a few levels and bounded fan-out, and become slow when millions of paths are explored.
Graph database, warehouse or graph processing framework. Questions such as "who are the neighbours of this account within 3 hops?" are lookups from a starting point, and Neo4j answers them in milliseconds. Questions such as "rank all 500 million nodes" (PageRank, community detection over everything) touch the entire graph, and are better run in Spark GraphFrames or a dedicated analytics engine on columnar files, or with the Graph Data Science library on a large memory machine. You pay for the wrong choice either with minutes of latency or with an oversized transactional server.
Scale up or scale out. A single Neo4j database holds graphs of billions of relationships on one large machine (hundreds of gigabytes to terabytes of RAM and NVMe), with read replicas in a cluster for read scale and automatic leader election for availability. Writes go to one leader, so write rate is one machine's. Sharding the topology turns cheap pointer hops into network calls of about 0.5 ms, 500 times slower, so choose to scale up first, and use property sharding (Infinigraph) only when the properties, not the structure, outgrow a machine. Distributed graph stores such as JanusGraph, or a key-value model on TiKV, scale out but give up the speed of local traversals.
Property graph or knowledge graph with RDF. Property graphs (Neo4j, Cypher, GQL) are simple to query and fast to traverse; RDF triple stores give standard vocabularies, reasoning and data exchange. Choose a property graph for application queries, and RDF for sharing data across organisations. For GraphRAG, Neo4j is chosen when the knowledge graph needs traversal combined with vector search; pgvector alone cannot follow relationships.
interview: Why can a graph traversal be faster than a join, and when is it not? || Index-free adjacency stores direct references from each node to its relationships, so each hop costs the same regardless of total data size, while a join looks up each step in an index and may build large intermediate sets. It is not faster when the query scans or aggregates a large fraction of the data, when the starting set is huge and fan-out is high, or when the graph does not fit in memory, because pointer chasing becomes random disk reads.
What is a supernode and how do you handle one? || A node with millions of relationships, for example a country or a popular account. Any traversal through it visits all those edges, and writes to it contend for locks. Remodel by splitting it (by time or type, with intermediate nodes), by filtering on relationship type first, or by avoiding traversals through it with a label check.
You need to find shared devices between accounts up to 4 hops away, in under 100 ms. How do you design it? || Model accounts and devices as nodes with a SHARES_DEVICE or USES relationship, start from an indexed account node, bound the path ([*1..4]), use DISTINCT between hops, and PROFILE to confirm that db hits are small. Keep the store in page cache. Exclude high-degree devices (like a public Wi-Fi) from traversal, because they explode results.
How do you load 2 billion relationships into Neo4j? || Use the offline neo4j-admin import tool, which writes store files directly from CSV or Parquet-derived files and is far faster than transactions. Create indexes and constraints after the load, and use batched transactions of 10,000 to 50,000 changes for later incremental updates.
Why is Neo4j hard to scale horizontally? || Graph partitioning is a hard problem. Real graphs do not split cleanly, so any cut makes many edges cross machines, and a query that follows them pays network round trips. So the usual path is a big machine plus read replicas, and sharding by property or by independent subgraphs where the data allows it.
@@+ pgvector
tradeoffs: pgvector or a dedicated vector database. Choose pgvector when the vectors belong to rows you already keep in PostgreSQL, the collection is below roughly 10–50 million vectors, and you want one transaction to update a record and its embedding, with SQL filters and joins in the same query. Choose Milvus or Pinecone when the collection reaches hundreds of millions of vectors, writes are high, or you need sharded search, quantization tiers and tuning that one PostgreSQL primary cannot do. With pgvector you give up scale-out and specialised indexes; with a dedicated system you give up transactional consistency with your source data and take on a second system to keep in sync, including deletes.
HNSW or IVFFlat. HNSW gives better recall at a given speed (95–99% recall in about a millisecond to a few milliseconds per query at a million vectors), supports inserts without retraining and needs no training data; the price is slow, memory-hungry builds (hours for tens of millions) and an index of about 6 KB per 1,536-dimension vector in memory. IVFFlat builds in minutes and is smaller, but recall depends on how many lists you probe and on training on representative data, and quality drops as data drifts. Choose HNSW by default; choose IVFFlat for static data or when build time and memory are the main limits.
Precision. Storing vectors as halfvec (16-bit) halves the column and index memory with very small recall loss in most embedding models; binary quantization shrinks memory 32 times and needs a re-ranking step with the full vectors to recover recall. Choose halfvec from the start for most work; choose binary quantization plus re-rank when memory is the hard limit and you can afford a second pass. Lower dimension embeddings (for example 512 instead of 1,536 where the model supports it) cut cost linearly and cost some accuracy.
Filtering. If a filter matches a large share of the rows, run the vector search and filter after (iterative scans make this work); if it matches very few rows, a B-tree on the filter column followed by exact distance on those rows is faster and exact; for tenants, partition by tenant. Hybrid search combines PostgreSQL full-text search with vectors using reciprocal rank fusion; for a stronger keyword side use Elasticsearch or OpenSearch, which gives up the single-database simplicity.
interview: A query using pgvector returns only 3 rows though you asked for 10 with a filter. Why? || The HNSW index returns its top ef_search candidates (40 by default), then the filter removes those that do not match, leaving fewer than the limit. Enable iterative index scans (hnsw.iterative_scan), raise ef_search, add a B-tree or partition for the filter column, or use exact search when the filter is selective.
How would you size memory for 20 million 1,536-dimension vectors? || Raw float32 is 6,144 bytes per vector, so about 123 GB; the HNSW index adds links and totals roughly 6.4 KB per row, about 130 GB. With halfvec the vector part halves to about 61 GB plus links. The index should stay in shared_buffers plus OS cache for fast queries, so choose an instance with sufficient RAM or reduce the data.
How do you measure whether the index is good enough? || Take a few hundred real queries, compute exact nearest neighbours with the index disabled, and measure recall at k (the share of true neighbours returned) and the latency percentiles for each ef_search value. Pick the smallest setting that reaches the recall the application needs (often 0.95), and re-measure after data or index changes.
When would you move from pgvector to a dedicated system? || When measurements show a problem pgvector cannot fix: the index no longer fits memory economically, builds block maintenance windows, write load competes with the main database, query rates need horizontal scale, or you need features like multi-vector ranking and tiered storage. Moving early adds an extra system and a synchronisation pipeline for no gain.
What happens to an embedding index when you change the embedding model? || Vectors from different models are not comparable, so all rows must be re-embedded and the index rebuilt. Store the model name and version in a column, create the new embeddings and index in the background (a new column or table), then switch queries, and drop the old index.
@@+ milvus
tradeoffs: Milvus or pgvector. Choose Milvus when the collection is above tens of millions of vectors, grows to billions, needs high write rates, or needs many index types and sharding built in; choose pgvector when the data is smaller and tied to PostgreSQL rows. Milvus separates storage (object storage), compute (query nodes) and coordination, so you can scale each part, and it gives you up to hundreds of millions of vectors per cluster with replicas; the price is a distributed system (proxies, coordinators, data, query and streaming nodes, etcd, object storage) to run on Kubernetes, or a paid managed service (Zilliz Cloud). For a million vectors, Milvus Lite or Standalone is enough and pgvector may be simpler.
Index type from the constraint. HNSW gives the highest recall and lowest latency but needs the vectors and graph in RAM, often 1.2–2 times the raw size. IVF_SQ8 stores 8-bit values, a quarter of the memory, with a small recall loss that a refine step recovers. DiskANN keeps most data on NVMe and RAM for a compressed copy, costing about 1–5 ms per query instead of under 1 ms and supporting data several times larger than memory. GPU_CAGRA fits very high query rates and fast builds, if you have GPUs. For 100 million vectors of 768 dimensions, raw float32 is about 307 GB; HNSW needs around 400 GB, SQ8 about 80–100 GB, and DiskANN a fraction of that in RAM.
Consistency level. Strong reads wait for all writes to be visible and add latency; bounded staleness (the default) allows a lag of a few seconds and gives the best throughput; session consistency lets a client see its own writes. Choose bounded for search and recommendation, session for an upload-then-search flow, and strong only for tests. Milvus is not a transactional store: there are no multi-record transactions, and deletes need compaction.
Milvus or Pinecone or Elasticsearch. Pinecone removes operations and fixes the index choice, with a bill that grows with queries; Milvus gives control and open source, with a bill in engineers and nodes. Choose Pinecone for a small team that wants no operations, Milvus when scale, control or on-premises hosting matter, and Elasticsearch or OpenSearch when text search with BM25 matters at least as much as vectors and a cluster already exists. Milvus has built-in sparse vectors and full-text search for hybrid retrieval, which reduces the need for a second system.
interview: Why can't you just put all vectors in one HNSW graph on one machine at 1 billion scale? || Memory: a billion 768-dimension float32 vectors are about 3 TB raw, plus graph links, and builds take very long. So you shard across nodes, compress with quantization, or use a disk-based index such as DiskANN with a compressed in-memory copy. Each choice moves cost to recall loss, SSD latency or merging results from many shards.
How does Milvus make writes visible and what is a segment? || Writes go to a streaming layer and a growing segment that is searched by brute force; at a size limit the segment is sealed, and an index is built on it, then stored in object storage. Queries search sealed indexed segments and growing segments together and merge results. Compaction merges small segments and removes deleted data.
You see recall dropping after months of ingestion. What do you check? || Check whether new data is in unindexed growing segments, whether index parameters (nlist, nprobe, ef) are still right for the larger data, whether the embedding distribution changed, and whether filters became more selective. Re-run recall against exact search on a test set, and tune or rebuild the index.
How do you handle multi-tenancy with 100,000 tenants? || Use a partition key on the tenant field, so tenants share a few physical partitions and the filter is applied inside the search. Separate collections or databases per tenant create too much metadata at this count. Very large tenants can have their own collection. This gives up hard isolation for lower overhead.
How do you migrate to a new embedding model without downtime? || Create a new collection with the new model's dimension, backfill by bulk import from stored source data, dual-write new items, compare recall and quality, then switch an alias to the new collection and delete the old one. Keep the source text so re-embedding is possible.
@@+ pinecone
tradeoffs: Buy Pinecone or run an open-source system (pgvector, Milvus). Choose Pinecone when the team is small (one or two engineers), vectors number in the millions to billions, the workload is spiky or has many tenants, and the value of no operations is greater than the bill. Choose pgvector when the data is small and sits in PostgreSQL already, and Milvus when you need on-premises hosting, index control or lower cost at steady, very high query volume. You give up index choice, the ability to inspect why a result was missed, and portability; you gain no nodes to size, automatic scaling and storage on object storage. Regulated data may force Bring Your Own Cloud or a self-hosted system.
Namespaces or metadata filters. A namespace is a hard partition: a query touches only that namespace, so cost and latency scale with its size, not the whole index. Use one namespace per tenant or user when every query names it; with 100,000 tenants it keeps each query small and gives isolation. Use metadata filters inside a namespace for soft conditions (document type, date), which scan more and cost more. You cannot query across namespaces in one call, so cross-tenant search needs a shared namespace with a tenant filter, at the cost of more work per query.
On-demand or dedicated capacity. On-demand read units scale with namespace size times query count, which is cheap for bursty or low traffic and costly for a large namespace with constant high query rates. Dedicated Read Nodes give a fixed price per node and predictable latency; they suit steady traffic above some number of queries per second (where the monthly on-demand bill passes the node price), but bring back capacity planning. Work out queries per day times GB per namespace before launch, and re-check after growth.
Dense, sparse and reranking. Dense vectors capture meaning but miss exact names, codes and rare tokens; sparse (keyword) vectors catch those. For user-facing RAG, use hybrid retrieval with a reranker on the top 50–100 candidates, which usually raises quality more than moving to a larger embedding model, and costs an extra 50–300 ms and a reranker fee. Pure dense search is enough for image similarity or recommendation where meaning dominates. Keep source data in your own database, since Pinecone has no transactions or joins and deletes are your pipeline's job.
interview: Why not just use pgvector, since you already have PostgreSQL? || For up to a few tens of millions of vectors and modest query rates, pgvector is often better: one system, transactional consistency and SQL filters. Pinecone is chosen when scale, many tenants or traffic spikes exceed one database, or when the team does not want to run a search index. The decision rests on size, traffic shape and team capacity, measured, not assumed.
How do you keep Pinecone consistent with your source of truth? || Treat Pinecone as a derived index. Write records through an outbox or change data capture stream from the source database, make upserts idempotent by using stable IDs, propagate deletes explicitly, and run a periodic reconciliation that compares IDs. Record the embedding model version in metadata so you can find stale vectors.
Your read costs grew 5 times with data growth, with no traffic increase. Why? || On-demand read cost scales with the size of the namespace queried, so a namespace that grew 5 times costs about 5 times more per query. Split data into smaller namespaces by tenant or time, use metadata filters carefully, or move a high-traffic namespace to dedicated nodes.
Search quality is poor for product codes and names. What do you change? || Dense embeddings blur exact tokens. Add sparse or full-text retrieval and combine scores (hybrid), use a reranker, and check chunking. Evaluate with a labelled set of queries and recall at k before and after, instead of judging by a few examples.
How would you evaluate recall on a closed service? || Export a sample of the vectors, compute exact nearest neighbours offline for several hundred real queries, query Pinecone for the same queries, and compare results at k. Repeat after large data changes, since you cannot see or tune the index. Also measure p95 latency from your own region, including cold namespaces.
