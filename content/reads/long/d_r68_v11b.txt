@@ chainrep
value: Chain replication keeps several copies of each object in a strict line of servers. Writes enter at the first server, the head. Each server applies the write and passes it to the next server. The last server, the tail, applies it and sends the reply to the client. Reads go only to the tail. The tail has only seen writes that every earlier server has already stored. So a read can never return a value that might later be lost.
This gives strong consistency (linearizability) with a very simple protocol. There are no votes, no leader elections and no quorums on the data path. With t servers, the chain keeps working after t − 1 failures. A majority protocol such as Raft needs 2f + 1 servers to survive f failures, so it needs 5 servers to survive 2. A chain needs 3. The price is that the chain relies on an outside service, called the master, to decide who is alive and what the chain looks like.
The idea was published by Robbert van Renesse and Fred B. Schneider at OSDI 2004. It is used in research and in real storage systems because it spreads the network load evenly. The head receives one copy and sends one copy. The same is true for every server. A primary that sends to all backups must send t − 1 copies itself. The best-known descendant, CRAQ, lets every server answer reads, so read capacity grows with the chain length. The same forwarding shape appears in the HDFS write pipeline, where a client writes a block to three DataNodes one after another.
This concept stands on four lower ideas. Replication gives the goal: several copies of the same data. Consistency models give the target: linearizable results. Failure detection gives the repair step: someone must decide that a server is dead. TCP gives the links: ordered, reliable streams between neighbours.
terms: Head — the first server in the chain; it receives every update from clients and decides the order of updates.
Tail — the last server in the chain; it answers all reads and sends the reply for every update.
Master — a small, reliable service that detects failures, changes the chain and tells clients who the head and tail are.
Successor and predecessor — the next and the previous server in the chain.
Committed update — an update that has reached the tail; from then on it is safe against t − 1 failures.
Sent list — for each server, the updates it forwarded to its successor and has not yet seen acknowledged by the tail.
Fail-stop — a failure model where a server either works correctly or stops; it never sends wrong answers.
Apportioned query — the CRAQ idea of sending reads to any server in the chain, not only to the tail.
Pipeline (HDFS) — the path of one block write through three DataNodes in order, with acknowledgements flowing back.
history: Primary/backup replication is old. One server orders the writes and copies them to backups. By the early 2000s, storage services needed more than that. They wanted high throughput, high availability and strong consistency together. Many large systems gave up strong consistency to get the other two. Van Renesse and Schneider, at Cornell, described chain replication in "Chain Replication for Supporting High Throughput and Availability" at OSDI 2004. Their point was that a line of servers is simpler than a primary with many backups, and it uses the network better.
The paper assumes fail-stop servers and reliable FIFO links. It describes a master that watches the servers and changes the chains. In their prototype the master itself is replicated on several hosts and kept consistent with Paxos. Their experiments compared chain replication with primary/backup and found equal or better throughput for every update percentage they tried. Failure handling was quick. The master needed a little more than 10 seconds to notice a failure in their experiment, and then the service reconfigured.
Chain replication was then reused in several designs. FAWN-KV (SOSP 2009) and the Hibari key-value store used it. CORFU (NSDI 2012) used chains of flash devices to build a shared log. The most important extension is CRAQ, by Jeff Terrace and Michael Freedman at Princeton (USENIX ATC 2009). It keeps strong consistency but lets every server serve reads, which suits read-heavy workloads.
Meanwhile, the HDFS write pipeline (Hadoop, from about 2006) arrived at a similar data path for another reason. The goal was to use every DataNode's outgoing bandwidth well when writing very large blocks. Today courses such as MIT 6.5840 and Stanford CS 244B teach chain replication as the main alternative to leader-and-quorum designs.
how: Start with a chain of t servers for one object or one group of objects. The master keeps the list and tells every server its successor and predecessor. It also tells clients which server is the head and which is the tail.
Step 1: a client sends an update to the head. The head applies it to its local copy and forwards it to its successor. Each server does the same. Servers are connected by reliable, ordered streams. TCP gives this, and its sequence numbers and retransmission are what make the "forward in order" rule safe. Because of the FIFO order, the updates seen by each server always form a prefix of the updates seen by its successor.
Step 2: the tail applies the update. At this moment the update is committed. The tail sends the reply to the client. It also sends an acknowledgement back up the chain. Each server keeps a Sent list: the updates it forwarded but has not seen acknowledged. When the acknowledgement arrives, the server removes the entry and passes the acknowledgement on.
Step 3: a read goes to the tail. The tail answers from its own copy, with no communication with other servers. The tail holds exactly the committed updates, so every read sees the latest committed value. Clients see one single order of updates, which is the linearizable level on the consistency ladder. Reads and writes by different clients line up in a single history.
Failures are where the master matters. The master uses failure detection: heartbeats and timeouts. Because the model is fail-stop, a server the master declares dead is removed for good. Even if it was only slow, it is not allowed back with old state. There are three cases. If the head fails, its successor becomes the new head. Updates the old head had not forwarded were never committed, and the client did not get a reply, so the client retries. If the tail fails, its predecessor becomes the new tail. It has seen at least what the old tail saw, so more updates become committed.
If a middle server S fails, the master tells S's successor and then S's predecessor. The successor reports the last update it received. The predecessor then sends the missing part of its Sent list. No update is lost and none is applied twice. A new server is added at the tail: it copies the state from the old tail, then receives the updates in the old tail's Sent list, and then takes over as tail.
Why is this cheaper than primary/backup? In primary/backup, the primary sends each update to all t − 1 backups. Its outgoing link carries t − 1 copies, and it also serves every read. In a chain, each link carries one copy. The head does the ordering and the tail does the reading, so the work is split between two different servers. The paper's experiments showed this as equal or better throughput than primary/backup.
To use all servers well, a real system runs many chains. Each server is the head of some chains, a middle server of others and the tail of the rest. This spreads both read load (on tails) and write entry (on heads) over the whole cluster.
CRAQ changes one rule: any server can answer a read. Each server keeps, for each object, a clean version and possibly newer dirty versions that are still travelling down the chain. A clean read is answered locally. If the server holds a dirty version, it asks the tail only for the latest committed version number (a small version query), and then returns that version. Reads are strongly consistent and spread across all servers. When a write reaches the tail, it sends the acknowledgement back, and each server marks that version clean and drops older ones. CRAQ also offers weaker read modes (eventual, and eventual with a bound) for clients that accept stale answers in exchange for speed.
The HDFS pipeline uses the same forwarding shape, with a different control plane. The NameNode picks three DataNodes. The client sends the block in packets (65,536 bytes by default) to the first DataNode. That node writes each portion locally and forwards it to the second, which forwards it to the third. A DataNode receives from the previous node while it sends to the next one, so the three disks and links work in parallel. The NameNode, not a chain master, keeps the file system metadata.

example: Take a chain of three servers, S1 (head), S2 and S3 (tail), holding a counter named x with value 5. A client sends "set x = 6" to S1. S1 stores 6, appends the update to its Sent list and forwards it. S2 stores 6 and also appends it to its Sent list and forwards it. S3 stores 6. The update is now committed. S3 replies to the client and sends an acknowledgement back. S2 and S1 remove the entry from their Sent lists.
Now a second client reads x at S3 at any time. If the read arrives before the update reaches S3, it returns 5. If it arrives after, it returns 6. It never returns 6 and then 5 later, because 6 was not visible anywhere that a client reads from until it was safe on all three servers. Compare a read at S1 in a basic chain: it could return 6 early, and if S1 and S2 then failed, 6 would be gone.
Now add a failure. A second update "set x = 7" reaches S1 and S2, and then S2 crashes before forwarding it. S1's Sent list contains update 7. The master notices after its timeout and removes S2. It tells S3 first, and S3 says its last update was 6. The master then tells S1 that S3 is its new successor. S1 sends update 7 to S3. S3 applies it and acknowledges. The client's request is answered by the tail as before. If the client timed out and retried, a real system needs a request identifier so that it can detect the duplicate. The chain is now S1 and S3, so it survives only one more failure until a new tail server is added.
Now use CRAQ on the same chain. Update 7 is travelling, so S1 and S2 hold both 6 (clean) and 7 (dirty). A read at S2 sees a dirty entry. S2 sends a version query to S3. S3 says the committed version is 6. S2 returns 6. A read at S1 after the acknowledgement returns 7 locally.
For a rough throughput view, suppose each server can do 20,000 reads per second. A plain chain serves 20,000 reads per second at the tail. A three-node CRAQ chain with few writes can approach 60,000. CRAQ's authors measured about three times the read rate of plain chain replication under a read-mostly load (about 59,900 against about 20,600 reads per second), and about twice with writes saturating the chain.
intuition: A chain is a bucket line: water moves from hand to hand, and you only count a bucket as delivered when the last person has it.
The design is natural because order is easy in a line and hard in a crowd. In a quorum system, many servers must agree on an order, which needs votes and extra messages. In a chain, the head picks the order and the line preserves it, because each link is a FIFO stream. The tail is the one place where "everyone has it" is true, so reading there is safe by construction.
The cost of this simplicity is moved, not removed. Agreement on who is in the chain is now needed only when something fails, and a small consensus service does that. The data path, which is the busy path, has no agreement at all. This is a common trick in distributed design: separate the rare, hard decision (membership) from the frequent, easy one (data flow).
mistakes: People often think chain replication is slow because a write passes through every server. In fact, throughput is not hurt, because the chain is a pipeline. Many updates are in flight at once, and each server forwards one copy. Only the latency of a single write grows with chain length, by one hop per server.
People often think a chain needs no consensus. In fact, the master must give all servers and clients the same view of the chain. In the paper, it is replicated with Paxos. Chain replication moves consensus off the data path. It does not remove it.
People often think reading at the tail wastes the other servers. In basic chain replication it does. That is the reason for CRAQ, and for running many chains so each server is the tail of some of them.
People often think the HDFS pipeline is full chain replication. In fact, it shares the forwarding shape, but HDFS reads can go to any replica, and the NameNode and the client handle failures in their own way. It is a pipeline for write bandwidth, not a linearizable store by itself.
People often think a chain survives network partitions on its own. In fact, the model assumes fail-stop servers. If a partition cuts the head from the master, an old head may keep accepting updates while a new head exists. Real systems need leases or epoch numbers to prevent this. The paper's model does not cover partitions.
tradeoffs: Choose chain replication when you need strong consistency, a read-mostly or balanced workload, and large objects or logs where network bandwidth is the limit. Each server sends one copy of each write, so total bandwidth is shared equally. Choose a leader with quorum replication (Raft, Paxos) when you want low and steady write latency without a separate membership service, or when a slow replica must not slow a write. A quorum of 3 out of 5 hides one slow server. A chain waits for every server, so one slow server slows every write until the master removes it.
Choose plain chain replication when the read load is small and write throughput matters. Choose CRAQ when reads dominate, for example 95% reads or more. A dirty object costs one extra small round trip to the tail, so CRAQ is worse for hot keys that are written often. In that case the tail gets both reads and version queries.
Choose primary/backup with parallel copies when the write latency of one request matters more than network load. The primary sends all copies at the same time, so latency is the slowest backup. A chain adds the latencies of all hops. For example, with 0.5 ms per hop and 3 servers, the chain adds about 1 ms for the two hops. A primary with parallel copies adds about 0.5 ms.
Choose a longer chain when you need to survive more failures (t − 1 with t servers), and a shorter one when write latency counts. Most systems use 3. Either way, you pay with the master: you must run and trust a small consistent service, and a false failure alarm removes a healthy server and forces a data copy.
friction: Latency is the first limit. One write must cross t − 1 links before the tail replies. In a single data centre this is small, perhaps hundreds of microseconds. Across regions it is large, which is why geo-distributed chains are rare, and why CRAQ's authors designed local reads for wide-area chains.
The second limit is the slowest server. Every write passes through every server, so a slow disk or a garbage-collection pause in one node slows the whole chain until the master removes it. A quorum system hides a slow minority. Failure detection must therefore be tuned: too fast gives false removals, too slow gives long outages. In the original experiments, the outage for updates was about 10 seconds, mostly detection time.
The third limit is the master. It is a new component to build, test and operate, and the safety of the chain depends on it. The paper assumes fail-stop behaviour. Real servers can be slow or partitioned, so real systems add leases and epoch numbers so an old head or tail knows it was removed.
The fourth limit is hot objects. Under basic chain replication all reads for one object hit its tail. Under CRAQ, many writes to one object make servers dirty, and reads fall back to the tail. Finally, recovery after a failure copies a whole replica to the new tail, which can take minutes for large data and reduces the chain's fault tolerance until it finishes.
practice: Use chain replication ideas when the data path is a large, ordered stream and bandwidth is the main cost: block storage, shared logs, object stores and key-value stores with strong consistency. Always put membership in a small consensus service (ZooKeeper, etcd or your own Raft group) and keep it off the data path. CRAQ itself used ZooKeeper for this.
Run many short chains instead of one big one, so that every server is a head, a middle and a tail for some chains. This spreads load and shortens repair time, because after a failure many servers copy a little each. Put the servers of one chain in different failure domains (racks), and keep chains within one data centre when latency matters.
Add a version or epoch number to every chain configuration and reject messages from an older one. This stops a removed server that wakes up from serving stale reads. Tune the failure detector with measured pause times, and test with injected slow nodes, not only dead nodes.
When you read the HDFS write path, look for the pipeline: the client, DataNode 1, DataNode 2 and DataNode 3, with acknowledgements flowing back. Read how HDFS recovers when a DataNode in the pipeline fails: the client removes the failed DataNode, gives the block a new generation stamp and continues on the remaining nodes; by policy it can ask the NameNode for a replacement node. In HDFS, dfs.replication defaults to 3 and the client write packet size to 65,536 bytes, and both are configurable. For your own systems, compare designs by writing down who orders writes, who answers reads, and who decides membership. Chain replication answers: the head, the tail, and the master.
interview: Why can a chain serve reads from only the tail, and still be linearizable? || The tail has applied exactly the committed updates, and each update reached all servers before it. A read there never sees a value that could still be lost. All reads and writes can be placed in one order: the order the head chose.
What happens when the middle server fails, and how is no update lost or duplicated? || The master removes it and tells the successor first. The successor reports its last update number. The predecessor resends the part of its Sent list after that number. FIFO links and sequence numbers prevent gaps and repeats.
Why does chain replication tolerate t − 1 failures when Raft needs 2f + 1 servers? || Raft must keep a majority alive to agree on a leader and entries without outside help. A chain relies on the master to decide who is dead, so one live server with the data is enough. The cost is the master and the fail-stop assumption.
When would you pick CRAQ over plain chain replication, and when not? || Pick it when reads dominate and keys are mostly clean, since all servers answer reads. Avoid it when a few hot keys are written constantly, since reads turn into version queries at the tail.
How would you handle a slow but alive server in a chain? || Use lease and epoch numbers and a failure detector with a sensible timeout. The master removes the slow node and adds a new tail, so one slow node does not hold up all writes.
Compare chain replication with Kafka's leader and follower replication for a log. || Kafka's leader receives each write and followers pull it; the leader's outgoing bandwidth carries all follower copies, and a write is committed when all in-sync replicas have it. Chain replication moves one copy per link and reads at the tail, but adds hop latency and needs a membership service.
quiz: Which server answers reads in basic chain replication, and why is this safe? || The tail. It has applied only updates that every earlier server already stored, so it never returns an update that could be lost.
Why does the chain have to use an outside master? || Servers in the chain cannot safely decide among themselves who failed. A master with a single view of the chain tells everyone the new order, and in the paper's prototype it is replicated with Paxos.
What does a Sent list contain, and how does it help when a middle server fails? || It has the updates a server forwarded but has not seen acknowledged. After a failure, the predecessor resends the missing suffix of this list to the new successor, so nothing is lost.
A chain has 3 servers and each can serve 20,000 reads per second. What is the read capacity of plain chain replication and of CRAQ with almost no writes? || Plain chain replication: about 20,000 reads per second, all at the tail. CRAQ: up to about 60,000, because all three servers answer reads.
You must choose between a 3-server chain and a 5-server Raft group, with a slow replica that sometimes pauses for 200 ms. Which fits better, and why? || Raft fits better for latency. A quorum of 3 out of 5 hides one slow replica. A chain waits for every server, so each pause delays writes until the master removes the slow node.

@@ kbypass
value: Kernel-bypass networking means that your program talks to the network card directly. It does not go through the operating system kernel for each packet. The program maps the card's receive and transmit queues into its own memory. It then polls those queues in a loop on a dedicated CPU core. A packet is handled where it lands, with no system call, no interrupt and no copy between kernel and user memory.
The reason is speed at small scale. At 10 Gb/s a 64-byte packet arrives about every 67 nanoseconds. That is the line rate of roughly 14.9 million packets per second. A modern CPU core runs at about 3 GHz, so it has only about 200 cycles per packet. The normal Linux path spends more than that on a system call, an interrupt, a buffer allocation and a lock. Bypass libraries remove those costs. DPDK describes its target as fewer than 80 CPU cycles per packet.
Where does it matter? Network functions such as load balancers and firewalls, trading systems, storage targets (NVMe over fabrics), and databases and logs whose latency in the tail counts. For the layer above, it gives microsecond latency and many millions of packets per second per core. The price is that one or more cores spin at 100% all the time, and you lose parts of the kernel that you may need: its TCP stack, firewall and tools.
This concept stands on five lower ideas. DMA lets the card write packets straight into memory. Interrupts are replaced by polling. System calls are removed from the data path. Zero-copy I/O is taken to its limit: the packet is never copied. Sockets, the standard API, are replaced by queues and, when you need TCP, a user-space TCP stack.
terms: Poll-mode driver (PMD) — a network driver that runs in user space and checks the NIC queues in a loop instead of waiting for interrupts.
DPDK — the Data Plane Development Kit, a set of user-space libraries and drivers for fast packet processing, started by Intel in 2010.
SPDK — the Storage Performance Development Kit, the same idea for NVMe disks: a user-space, polled, lock-free driver.
AF_XDP — a Linux socket type that passes packets from an XDP program to user space through shared rings, with an optional zero-copy mode.
RDMA — remote direct memory access; the NIC reads or writes memory on another machine without that machine's CPU handling the data.
UMEM — in AF_XDP, the memory region that holds packet buffers; the kernel and the program share it.
Queue pair — an RDMA send queue and receive queue that an application posts work requests to.
Hugepage — a large memory page (2 MB or 1 GB) that reduces address-translation misses; bypass libraries use them for packet buffers.
Thread per core — a design with one pinned thread per CPU core, each owning its data, as in Seastar.
history: By the late 1990s, researchers saw that the kernel was a bottleneck for fast networks. Early ideas such as U-Net (1995) and the Virtual Interface Architecture let applications reach the network card directly. The InfiniBand standard, around 2000, made this a hardware feature: its verbs interface lets applications post work straight to the card. RDMA then spread to Ethernet through iWARP and RoCE.
For ordinary Ethernet, the push came when 10 Gb/s cards arrived in the late 2000s. A single core could no longer handle line rate through the kernel. Intel created DPDK in 2010 for its own NICs. The community started at DPDK.org in 2013, run by 6WIND, and DPDK is now a Linux Foundation project. Luigi Rizzo's netmap (USENIX ATC 2012) showed another route: a shared-memory API that keeps the kernel driver. SPDK applied the same idea to NVMe SSDs.
Research in 2014 asked whether bypass needs to give up protection. IX (Belay et al., OSDI 2014) and Arrakis (Peter et al., OSDI 2014) gave applications direct queue access with hardware-based isolation. mTCP (NSDI 2014) built a user-space TCP stack for multicore servers. The same year FaRM (Microsoft Research, NSDI 2014) showed a key-value store on RDMA with 167 million lookups per second on 20 machines.
Linux then brought part of this idea into the kernel with XDP and AF_XDP (AF_XDP arrived in Linux 4.18, in 2018). They keep the kernel driver and let a program pick which packets go to user space.
On the application side, ScyllaDB's Seastar library (the base of ScyllaDB, 2015, and Redpanda, 2019) offered a thread-per-core design with an optional user-space TCP/IP stack on DPDK. Courses such as Stanford CS 240 and CS 244 and MIT 6.5820 teach these ideas as part of high-performance networking.
how: The normal path first. A packet arrives at the NIC, which copies it by DMA into a kernel buffer and raises an interrupt. The kernel handler runs, builds a socket buffer, runs IP and TCP code, and queues data for a socket. Your thread wakes up from epoll or read, makes a system call and the kernel copies the bytes to your buffer. Each step is small, but together they cost microseconds and add variation.
Kernel bypass removes the kernel from this data path. Step 1: the NIC is taken away from the kernel driver. With DPDK, the port is bound to a generic kernel module such as VFIO, which only lets the program map the device and set up IOMMU protection. Step 2: the program allocates packet buffers in hugepage memory and gives the NIC their addresses. The NIC fills them using DMA, so packets arrive directly in user memory.
Step 3: the program runs a loop on a dedicated core. It asks the receive ring for a batch of packets (DPDK calls this a burst, often up to 32). It processes them, and writes the replies to the transmit ring. There is no interrupt, because the loop checks the ring all the time. There is no system call, because the rings are shared memory. There is no copy, because processing happens in the buffer where the NIC put the packet. Batching spreads the cost of cache misses over many packets. DPDK's memory pool, ring and buffer libraries use per-core caches and lock-free rings so cores do not wait for each other.
Step 4: scaling. Modern NICs split traffic into many queues using a hash of the connection (receive-side scaling). Each core owns one queue pair. A connection always goes to the same core, so its state needs no locks. This is the thread-per-core model, and it connects to NUMA: memory and the NIC should be on the same socket as the core that uses them.
Each lower idea removes one cost. DMA means the NIC, not the CPU, moves the bytes, and the buffers are already in user memory. Polling replaces the interrupt: the cost of waking a core and switching context is paid once, as a core that never sleeps, and not once per packet. Removing system calls avoids the mode switch between user and kernel code, which costs on the order of a hundred nanoseconds or more per call, depending on the CPU and its security fixes. Zero-copy avoids moving each byte again through the memory bus. The socket API, which hides all of this behind read and write, is replaced by the ring.
The cost is that you must now provide what the kernel gave you. DPDK gives you Ethernet frames, not TCP. For UDP-style or custom protocols this is fine. For TCP you need a user-space stack, such as the one in Seastar, or in mTCP. ARP, routing and a firewall also need your own code, or you pass some packets back to the kernel.
There are softer options. AF_XDP keeps the kernel driver. An XDP program runs in the driver for each packet and can redirect chosen packets to an AF_XDP socket. The socket has four rings. The program owns the buffers (the UMEM). It puts empty buffers in the fill ring, the kernel puts received packets in the receive ring, the program puts packets in the transmit ring, and finished buffers come back through the completion ring. In zero-copy mode the NIC writes directly into the UMEM. If the driver does not support it, the kernel falls back to copy mode. The program can set a need-wakeup flag, so that a system call is needed only when the kernel is idle.
RDMA goes one step further. The application registers memory with the NIC, and posts work requests on a queue pair. A one-sided read or write moves bytes to or from a remote machine's memory, and the remote CPU is not involved at all. SPDK does the same for storage: a user-space NVMe driver polls the completion queue of the SSD, with message passing instead of locks. Seastar applies the idea to a whole application, with one reactor thread per core and, optionally, its own TCP/IP stack over DPDK.

example: Do the arithmetic for a 10 Gb/s link carrying 64-byte packets. Each frame uses 64 bytes plus 20 bytes of preamble and gap on the wire, so 84 bytes or 672 bits. At 10,000,000,000 bits per second this is about 14.88 million packets per second, or one packet every 67 ns. At 3 GHz that is about 200 cycles. If each packet needed 1 µs of CPU time in the kernel path (an assumption for this example), one core handles 1 million packets per second. You would need 15 cores for line rate. With a polling loop at 80 cycles per packet, one core handles 3 GHz / 80, about 37 million packets per second, so one core can keep up with a 10 Gb/s link.
Now latency. In the IX paper, two Linux servers had a one-way latency of 24 µs for 64-byte messages on 10GbE. Two IX servers, using polling and run-to-completion, had 5.7 µs. This was measured in 2014, so numbers on newer hardware will differ, but the ratio is a useful guide. The difference is about 18 µs one way, or 37 µs for a round trip.
Next, an ad-tech case. Suppose a bidder must answer in 10 ms and uses four one-way network legs per bid request: it receives the request, sends a profile lookup, gets the reply and sends the bid. Bypass would save roughly 4 × 18 = 72 µs, which is under 1% of the budget. For one request that does not matter. The gain is in CPU per request. At 500,000 requests per second, even 5 µs of saved kernel time per request is 2.5 CPU cores. Most bidders gain more from removing garbage-collection pauses and slow lookups than from bypass. Bypass is worth it when a very busy front end (a load balancer, a filter that drops bad traffic early) handles millions of packets per second.
Last, a storage case. An NVMe SSD completes a 4 KB read in tens of microseconds, depending on the device. The kernel block layer adds a few microseconds. This is small for a slow SSD. But a fast device can complete hundreds of thousands of operations per second, and then the CPU per operation counts. That is the case SPDK was built for.
intuition: Kernel bypass is like having a private door to the warehouse instead of sending every parcel through the main reception desk.
The reception desk (the kernel) is safe and fair. It serves everyone, checks every parcel and keeps records. That is what you want when a thousand programs share one machine. If one program does nothing but handle parcels, the desk is only a delay. Give that program its own door and its own staff, and it moves parcels in nanoseconds.
This is also why the design is natural. A modern NIC already has many queues and DMA engines. A fast CPU core is cheap compared with a lost microsecond. The kernel's general rules (sharing, protection, fairness) are the real cost, so the design keeps the rules that matter (isolation through the IOMMU) and drops the rest.
mistakes: People often think kernel bypass is always faster. In fact, it wins only when per-packet overhead dominates: small packets, high rates or tight tail-latency targets. For large transfers, the kernel with TCP segmentation offload and zero-copy sends reaches line rate with little CPU, and bypass adds work for no gain.
People often think ScyllaDB and Redpanda use DPDK by default. In fact, both are built on Seastar, whose design is thread-per-core and shared-nothing. Seastar can use its own TCP stack over DPDK, but it can also use the normal Linux sockets. Check the documentation of your version and your deployment before assuming bypass. Their main gains come from pinned threads, no locks and direct disk I/O.
People often think bypass means no operating system. In fact, the kernel still sets up the device, memory mappings and permissions. Only the per-packet path leaves the kernel. If you use AF_XDP, the kernel driver is still in use.
People often think busy polling wastes energy for nothing. In fact, it trades CPU time for latency. The core is busy, but it is the cost of not waiting for interrupts. Under low load it is wasteful, so many systems adapt, polling under load and sleeping when idle.
People often think RDMA is just a faster TCP. In fact, RDMA is a different model: one-sided reads and writes need no code on the remote CPU, and the programmer must manage memory registration, queue pairs and flow control. FaRM reported 9 to 11 times the request rate of TCP/IP for 16 to 512 byte requests. This is gained by redesigning the application, not by swapping a library.
tradeoffs: Choose the normal kernel stack with epoll or io_uring when your service handles thousands to a few hundred thousand requests per second per machine, and your latency budget is milliseconds. It is simpler, supports all tools (tcpdump, iptables, eBPF, standard TCP) and survives upgrades. Choose bypass when you need millions of packets per second per core, or microsecond-level tail latency, and you accept to own the stack.
Choose AF_XDP over DPDK when you want to keep the kernel driver, ordinary tooling and the option of passing some packets to the kernel. You give up some speed and sometimes zero-copy support, which depends on the driver. Choose DPDK when you need the highest packet rate, many NIC features and a rich library, and you accept dedicated NICs and cores, hugepages and your own protocol handling.
Choose RDMA when your application can be built around one-sided reads and writes in one data centre, for example a distributed in-memory store or storage replication, and your network supports it (InfiniBand or lossless Ethernet with RoCE). Choose a thread-per-core framework such as Seastar over raw bypass when you need a whole server and not only a packet loop: you get futures, per-core memory and message passing, and you can still run on the kernel stack.
Choose to spend a core on polling only after you measure. Each polling core is a core that you pay for and cannot sell to other work. If bypass saves more cores elsewhere (as in the example), it pays. If not, it does not.
friction: The first problem is operations. Packets taken by DPDK are invisible to the kernel. tcpdump, iptables, routing and ARP do not see them, so you need your own tools and monitoring. The NIC needs a compatible driver; DPDK supports many NICs, and the AWS ENA adapter has a DPDK driver, but features differ between NICs and between clouds.
The second problem is the TCP stack. Writing or choosing a user-space TCP stack means owning congestion control, retransmission timers and many edge cases that Linux has fixed over decades. Many bypass users stay with UDP or custom protocols for this reason.
The third problem is waste and sizing. A polling core is at 100% even with no traffic. You must reserve cores and isolate them from the scheduler. You need hugepages and good NUMA placement, because a buffer on the wrong socket slows every access.
The fourth problem is protection and sharing. The NIC with DMA can write anywhere in memory unless the IOMMU limits it. A bug in a bypass program can break the whole data path, and sharing one NIC among several programs is hard. Cloud virtual machines add one more layer, so you need drivers for the virtual device (virtio or ENA).
Finally, the benefit is shrinking in some cases. The kernel has improved: XDP, io_uring, busy polling and larger offloads closed part of the gap. Always measure your own p99, not the numbers in a paper from 2014.
practice: Start with the question: where is the time going? Use perf, flame graphs and per-core CPU counters to see if the kernel network path is truly the cost. Fix batching, connection reuse and garbage collection first. These often give more than bypass.
If you do need more, climb in steps. First tune the kernel path: pin interrupt handlers, use busy polling, use io_uring, enable receive-side scaling and large offloads. Then try AF_XDP for packet filtering and custom protocols. Then use DPDK only for the few services that need it, such as a front-line load balancer or a market-data feed handler.
For streaming and databases, you often get the main benefit with no bypass. Redpanda documents a thread-per-core model, direct memory access for disk I/O, and tuners that set up the machine. ScyllaDB maps one data shard to each core with its own memory and no sharing. Run them with the recommended tuning on a few large nodes, and give each core its own work.
For storage, use SPDK when your target is an NVMe-over-fabrics server or a user-space block device, and when SSD IOPS per core is the limit. For RDMA, design the data layout first (what a one-sided read returns, who writes it) and keep control messages on ordinary TCP.
Test failure modes: what happens when a polling core stalls, when a NIC queue is full, when packets arrive in a burst. Add counters for ring occupancy and dropped packets. Keep a fallback to the kernel stack, so you can run on any machine in a test.
interview: Why can a user-space polling loop beat the kernel for small packets? || The kernel path adds an interrupt, a system call, a buffer allocation, locks and a copy to each packet. These cost hundreds of nanoseconds to microseconds. A polling loop reads packets from a shared ring in batches, with no interrupt, no system call and no copy. At 14.9 million packets per second you have roughly 200 cycles for each packet.
What do you lose when you move a service to DPDK? || You lose the kernel's TCP stack, routing, ARP, firewall and its standard tools. You must dedicate cores and NICs, use hugepages and handle NUMA. You also get no protection from kernel scheduling, so a bug affects the whole data path.
How is AF_XDP different from DPDK? || AF_XDP keeps the kernel driver. An XDP program chooses which packets go to a user-space socket through ring buffers, so other traffic still uses the kernel. DPDK takes the NIC away from the kernel. AF_XDP is easier to run beside normal traffic, and DPDK usually gives the highest rate.
Redpanda and ScyllaDB are fast. Is it because of kernel bypass? || Mostly not. Both use Seastar's thread-per-core, shared-nothing design: pinned threads, per-core memory, message passing instead of locks and direct disk I/O. Seastar can use DPDK, but the normal Linux stack is also supported, so check the deployment before crediting bypass.
When would you recommend bypass for an RTB bidder? || Rarely for the bidder logic, since its budget is milliseconds and the saved network time is tens of microseconds. Consider it for a front-line load balancer or traffic filter that handles millions of packets per second, after profiling shows the kernel is the limit.
How does RDMA reduce latency in a distributed store? || One-sided reads and writes let a client fetch remote memory without running code on the remote CPU. FaRM used this for lookups and saw a latency of 31 µs at 167 million lookups per second on 20 machines. The cost is a design built around memory layout and registration, in one data centre.
quiz: What are the four steps that kernel bypass removes from the packet path? || The interrupt, the system call, the copy between kernel and user memory, and the kernel's per-packet buffers and locking. The NIC writes into user memory by DMA and a polling loop reads it.
Why does a polling core on a dedicated queue need no locks? || The NIC hashes each connection to one receive queue, and each queue belongs to one core. That core is the only one that touches the connection's state, so no other core competes for it.
What are the four rings of AF_XDP, and who produces into each? || Fill ring: the program gives empty buffers to the kernel. Receive ring: the kernel gives received packets to the program. Transmit ring: the program gives packets to send. Completion ring: the kernel returns buffers it finished sending.
At 10 Gb/s with 64-byte packets, how many packets per second and how many cycles per packet at 3 GHz? || About 14.88 million packets per second, so about 67 ns or about 200 cycles per packet. The wire uses 84 bytes per packet including preamble and gap.
A team wants to move a bidder with a 10 ms budget to DPDK to save latency. What would you tell them? || The saved network time is perhaps 70 µs, under 1% of the budget. Profile first. Garbage collection, lookups and fan-out cost more. Consider bypass only for a high-rate front end, or if CPU per request is the real limit.
