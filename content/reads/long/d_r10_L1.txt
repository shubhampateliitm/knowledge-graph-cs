@@ mqueue
value: A message queue is a buffer between a part of a system that creates work (the producer) and a part that does the work (the consumer). The producer puts a message in the queue and moves on. A consumer takes the message, does the work, and tells the queue "done" (an acknowledgement). Only then does the queue delete the message. Each message is handled by exactly one consumer, even when many consumers read from the same queue. This is called the competing-consumers pattern.
Three problems pushed people to build this. First, load is bursty: a web site may receive 10,000 requests in one minute and 500 in the next, and sizing the workers for the peak wastes money. The queue absorbs the burst, and workers drain it at their own speed. Second, producers and consumers fail at different times. If the consumer is down for ten minutes, the producer should not fail; the messages wait. Third, work must be spread over many machines without the producer knowing how many there are. You add workers, and they share the queue.
For the layer above (job systems, email and notification senders, image and video processing, order handling, ad-event enrichment), a queue turns "call a service and hope it is up" into "write down the work and let someone reliably do it". The layers below make this possible: delivery guarantees (L2) define what a lost acknowledgement means and why duplicates happen, backpressure (L2) keeps the queue and its consumers from being overwhelmed, and share groups (L2) bring the same work-queue behaviour to Kafka, which was built as a log.
terms: Producer — the program that creates messages and sends them to the queue.
Consumer — the program that receives a message, does the work and acknowledges it.
Acknowledgement (ack) — a signal from the consumer that the message was processed, after which the broker may delete it.
Visibility timeout — in Amazon SQS, the time during which a received message is hidden from other consumers; if no ack arrives in that time, the message becomes visible again.
Redelivery — the broker giving a message to another consumer because the first one did not acknowledge in time.
Prefetch — the number of unacknowledged messages a broker is allowed to push to one consumer; it limits how much one consumer can hold.
Dead-letter queue (DLQ) — a separate queue that receives messages that failed too many times, so they can be inspected without blocking the main queue.
Poison message — a message that always makes the consumer fail, for example because its content is malformed.
Competing consumers — many consumers reading one queue so that each message goes to only one of them.
history: Message queues are older than the web. IBM released MQSeries (now IBM MQ) in 1993 to connect business applications reliably across different machines and networks, and Microsoft's MSMQ followed in the 1990s. Banks needed this: a payment instruction must not be lost because one system was restarting. For years each vendor used its own protocol, so applications were tied to one product.
Work on AMQP (Advanced Message Queuing Protocol) began at JPMorgan Chase in 2003, with the aim of an open wire protocol so that different products could work together. RabbitMQ, written in Erlang, appeared in 2007 and implemented an early AMQP version. The OASIS standard AMQP 1.0 followed in 2012. Meanwhile Java applications used the JMS API (2001) with brokers such as ActiveMQ.
Amazon launched Simple Queue Service (SQS) in 2004 as one of its first public services; it became generally available in 2006. It made a queue something you rent by the request, with no broker to run. Task-queue libraries for web applications (Celery for Python, Resque and Sidekiq for Ruby) around 2009–2012 made "run this in the background" a normal part of every web stack. Gregor Hohpe and Bobby Woolf's book "Enterprise Integration Patterns" (2003) gave the field its vocabulary: channels, competing consumers, dead-letter channels, idempotent receivers.
The 2010s brought log-based systems, mainly Apache Kafka (LinkedIn, 2011), which keep messages after they are read and let many groups replay them. They are excellent for streams, but they gave each partition to only one consumer in a group, so they were awkward as work queues. Kafka Improvement Proposal 932, "Queues for Kafka", added share groups to fix this. Share groups arrived as early access in Kafka 4.0 (2025) and were declared production-ready in Kafka 4.2.0 on 17 February 2026.
how: A queue broker keeps an ordered list of messages and hands them out. The life of one message has four steps. The producer sends the message and the broker stores it, often on disk, and confirms. A consumer asks for work (pull), or the broker pushes it. The broker marks the message as "in flight" for that consumer and starts a timer. When the consumer finishes, it sends an ack and the broker deletes the message. If the consumer crashes or is too slow, the timer expires (or the connection closes) and the broker makes the message available again for another consumer.
This is where delivery guarantees (L2) matter. A broker cannot know whether a silent consumer crashed before or after doing the work. If the broker redelivers, the work may happen twice. If it does not, the work may happen zero times. Real queues choose redelivery. This is called at-least-once delivery. Amazon SQS standard queues, RabbitMQ with acks, and Kafka share groups all work this way. True exactly-once effect is reached only by making the handler idempotent, for example by recording a message ID in the same database transaction as the result.
The timers differ by product. SQS uses a visibility timeout (default 30 seconds, adjustable from 0 seconds to 12 hours). The message is not removed when received; it is only hidden. A consumer that needs more time can extend the timeout. RabbitMQ pushes messages over an open connection and treats a closed channel as a signal to requeue everything unacknowledged. Kafka share groups use an acquisition lock: a consumer that fetches a record holds it for 30 seconds by default, and then can accept it (done), release it (retry now, for example after a temporary error) or reject it (never retry, for example malformed content). After 5 delivery attempts by default, the record is archived and not delivered again.
Backpressure (L2) is how a queue protects its consumers and itself. Without limits, a broker could push a million messages to one slow consumer and starve the others. RabbitMQ's prefetch (basic.qos) caps unacknowledged messages per consumer; a value of 1 gives fair dispatch but wastes round trips, while a value of 10–100 is typical for short tasks. SQS consumers pull in batches of up to 10 messages and use long polling (waiting up to 20 seconds) to avoid empty requests. On the producer side, bounded queues, flow control or publisher confirms slow producers when the broker is full. Without this, an unbounded queue just moves the failure from "slow" to "out of memory or disk" at 3 a.m.
Ordering is weak by design. With one consumer, messages are processed in order. With several, message 2 may finish before message 1, and a redelivered message arrives late. SQS standard queues give best-effort ordering. SQS FIFO queues and RabbitMQ quorum queues give stronger ordering, but only per message group or per consumer, and at lower throughput (SQS FIFO is limited to 300 API calls per second per action without batching, or 3,000 messages per second with batching of 10, in the default mode). If you need strict order for one entity (for example all events of one account), route that entity always to the same group, and accept that one slow message blocks the others in that group.
Durability and replication are the next layer. A single broker is a single point of failure. RabbitMQ quorum queues replicate each queue with the Raft consensus algorithm across an odd number of nodes (usually three), and they replaced the older mirrored classic queues, which were removed in RabbitMQ 4.0 (2024). SQS spreads data across multiple availability zones inside AWS. Kafka share groups store the delivery state of each record in an internal topic, so a broker crash does not forget which records were acknowledged.
Last, the dead-letter queue. Each time a message is redelivered, the broker increments a counter (SQS calls it ReceiveCount). When the counter passes a limit, for example 5, the broker moves the message to the DLQ instead of the main queue. This keeps one poison message from being retried forever and blocking the line, and it keeps the evidence for a human to look at.
Push and pull are the two ways a consumer gets work, and they trade control against latency. In a pull system (SQS, Kafka) the consumer asks when it has capacity, so it can never be overloaded, but it adds a polling delay unless long polling is used. In a push system (RabbitMQ) the broker sends as soon as a message arrives, which gives the lowest latency, but it needs the prefetch limit to avoid flooding a slow consumer. Throughput comes from batching: sending, receiving and deleting 10 messages in one call cuts the number of billed requests and network round trips by about 10 times, at the price of a larger group to redo if one worker fails.

example: An ad-tech team processes uploaded audience files. A file arrives, and a worker must parse it (about 20 seconds) and write rows to a database. They use an SQS standard queue with a visibility timeout of 30 seconds and a dead-letter queue with maxReceiveCount = 3.
Step 1. The uploader sends 1,000 messages in a burst, one per file. The queue holds them. The upload service is not slowed down.
Step 2. Ten workers each pull up to 10 messages. So 100 messages are in flight, and 900 wait. Each worker processes one file at a time, 20 seconds each. Each worker must handle 1,000 / 10 = 100 files, so the total time is 100 × 20 s = 2,000 s, about 33 minutes. The team can see this from the queue: 1,000 waiting messages and a drain rate of about 0.5 messages per second.
Step 3. A problem: a worker pulled 10 messages in one batch, but it handles them one by one. The last message waits 9 × 20 = 180 s before its turn, but its visibility timeout is only 30 s. At 30 s the broker makes messages 2 to 10 visible again, and other workers take them. Now two workers process the same file, and rows are written twice. The fix has two parts: pull only 1 message when each takes 20 s (or extend the timeout as you go), and make the database write idempotent by using the file ID plus row number as the key, so the second write changes nothing.
Step 4. A file with a broken header makes the parser throw an exception every time. Delivery 1 fails after 2 s, and the message reappears after 30 s. Delivery 2 and 3 fail the same way. On the fourth receive attempt the count has passed 3, so SQS moves the message to the DLQ. An alarm fires because the DLQ depth is above 0. An engineer fixes the parser and "redrives" the message back to the main queue.
Step 5. Now watch the right metric. Queue length (1,000) matters less than age of the oldest message. If the oldest message is 40 minutes old and the promise to customers is "ready in 15 minutes", the team needs more workers: 1,000 × 20 s / 15 min = 22 workers, so about 23 with some margin.
intuition: A ticket counter at a deli: each ticket is served by one clerk, and if the clerk walks away without finishing, the ticket goes back to the queue.
The idea is natural because it separates "asking for work" from "doing work" in time, in speed and in failure. A direct call ties the caller to the callee: if the callee is slow, the caller is slow; if it is down, the caller fails. A queue turns that tight link into a loose one. The price is that you now have a third party that must remember things, and a question that has no perfect answer: when a consumer goes silent, has the work been done? The designers answered with a time limit and repetition. They chose to risk doing work twice rather than not at all, and left it to the application to make repetition harmless.
mistakes: People often think a queue gives exactly-once processing. In fact it gives at-least-once delivery. A consumer can finish the work and crash before the ack, and then the message is delivered again. Exactly-once effect comes from idempotent handlers, not from the queue.
People often think a queue is the same as Kafka or any "event stream". In fact a queue deletes messages after acknowledgement and gives each message to one consumer, while a log keeps messages, lets many independent groups read them, and lets you replay. Kafka share groups give queue behaviour on top of a log, but you still choose by semantics: work to be done once (queue) or facts to be read by many (log, pub/sub).
People often think queue length shows whether you are healthy. In fact a queue of 100,000 messages that drains in 2 seconds is fine, and a queue of 50 messages whose oldest member is 3 hours old is broken. Watch the age of the oldest message and the processing rate.
People often think messages are processed in the order they were sent. In fact with more than one consumer, retries and redeliveries change the order. If order matters for one entity, group messages by that entity and process each group serially.
People often think a dead-letter queue solves poison messages. In fact it only parks them. If nobody watches it and nobody redrives or deletes its contents, work is silently lost.
tradeoffs: Choose a queue (SQS, RabbitMQ, Kafka share groups) when each message is a task that one worker should do once, and you want to scale workers up and down. Choose a log (Kafka consumer groups, Kinesis) when many independent consumers need the same events, or when you need replay, long retention or strict per-key order at high throughput. You give up replay with a queue: once a message is acknowledged, it is gone.
Choose a managed queue such as SQS when you want no servers and can accept at-least-once delivery, best-effort order and a few tens of milliseconds of latency per call; its price is per request, so cost grows with message volume and with every empty poll. Choose RabbitMQ when you need rich routing (exchanges, topics, headers), per-message priority or very low latency, and you can operate a cluster; you give up scale-out, because one queue lives on one replica set and very large backlogs are painful. Choose Kafka share groups when you already run Kafka and want a work queue next to your streams, without a second system; you give up some mature queue features (for example per-message delays and priorities) and take on the ordering and delivery rules described above.
Choose strict ordering (FIFO queues, one consumer per message group) when correctness depends on order for one entity, such as account balance changes. Choose unordered parallel processing when tasks are independent and throughput matters. Ordering costs you throughput and head-of-line blocking: one slow or failing message holds up all the messages behind it in the same group.
Choose a long visibility timeout when processing time varies a lot, and you do not mind that a crashed worker's messages wait that long before another worker tries. Choose a short one with heartbeat extensions when you want fast recovery. Either way, the timeout must be longer than the slowest normal processing, or you create duplicates yourself.
friction: Duplicates are the first cost. Every consumer must be idempotent, and this is harder than it sounds when the work touches several systems: sending an email, charging a card and updating a database cannot all be made atomic. Teams use idempotency keys, deduplication tables, or the outbox pattern.
Backlogs are the second cost. A queue hides a slowdown: the producer sees success while the consumers fall behind. If a backlog reaches millions of messages, draining it can take hours, and the late results may be useless. Retention limits (4 days by default in SQS, up to 14 days) can delete unprocessed messages silently if the backlog lasts too long.
Poison messages and retry storms are the third. A bad deploy makes every message fail, every message is retried 5 times, and the queue's load multiplies by 5 while the DLQ fills. Retries with backoff delay help, but a plain visibility timeout gives no growing backoff.
Operations are the fourth. Self-run brokers need disk space alerts, memory limits and careful upgrades; when a broker's disk fills, it blocks all producers. Large messages (SQS limits message size to hundreds of kilobytes) force a "claim check" pattern: store the data in object storage and put only its address in the message.
Finally, observability across queues is poor. A request that passes through three queues has no single trace unless you pass a trace ID in message attributes and log it in every consumer.
practice: Use a queue when each message is a unit of work that one worker should do, and order across messages does not matter much. Set the visibility timeout or ack deadline above the slowest normal processing time, and extend it for long jobs. Make handlers idempotent: key every write by message ID or a business key, because the crash window between "work done" and "ack sent" always exists.
Configure a dead-letter queue with a maximum delivery count (3 to 5 is common) and alert when its depth is above zero. Practise the redrive: SQS has a built-in redrive to the source queue. Keep messages small (an identifier and a few fields) and read the large data from storage. Put a trace ID and a creation timestamp in every message.
Alert on the age of the oldest message, not on the length. Autoscale workers on backlog per worker (messages waiting divided by the number of workers, multiplied by the average processing time). Set prefetch deliberately: in RabbitMQ start with 10 to 50 for short tasks and 1 for long tasks.
If you use Kafka and have task-like work where per-partition limits hurt (many more consumers than partitions, or slow uneven tasks), look at share groups; if you need ordered streams per key, stay with consumer groups. Test the failure paths on purpose: kill a worker mid-task, make the handler throw, fill the queue, and watch what the metrics show.
quiz: What guarantee do SQS standard queues and RabbitMQ with acks give about delivery, and what does it mean for your handler? || At-least-once delivery. A message may be delivered more than once, so the handler must be idempotent.
Why can a visibility timeout shorter than the processing time cause duplicate work? || The broker only knows that no ack arrived within the timeout. It makes the message visible again while the first worker is still processing, so a second worker takes it and both do the work.
Why does a queue with 1,000 waiting messages sometimes show no problem, while a queue with 50 messages does? || Because age matters, not length. If 1,000 messages drain in seconds, latency is low. If the oldest of 50 messages has waited hours, consumers are stuck or too slow.
Workers take 20 s per message. You must clear a 3,000-message backlog within 10 minutes. How many workers do you need? || 3,000 × 20 s = 60,000 worker-seconds. Divided by 600 s, that is 100 workers (a few more for margin).
When would you choose Kafka share groups instead of a separate queue system, and when not? || Choose them when you already run Kafka and want task-style work (any consumer takes any record) beside your streams. Avoid them when you need strict per-key order or mature queue features such as per-message delays and priorities.
interview: A consumer processes a message, writes to the database, and crashes before the ack. What happens, and how do you make it safe? || The broker redelivers after the timeout, so the work runs twice. Make the write idempotent: use a unique key (message ID or business key) with an upsert or a unique constraint, or store processed IDs in the same transaction as the result. Do not rely on the queue for exactly-once.
Why not use Kafka for everything instead of a message queue? || Kafka consumer groups assign each partition to one consumer, so parallelism is capped by partition count, a slow message blocks the rest of its partition, and there is no per-message ack or retry. Share groups remove some of this, but you still get weak ordering and fewer queue features. If the need is a job queue with retries, a queue is the simpler fit.
How do you choose the visibility timeout, and what goes wrong in each direction? || Set it above the p99.9 processing time, or extend it with heartbeats. Too short gives duplicates and wasted work. Too long means a crashed worker's messages are stuck for that whole time and recovery is slow.
Your queue backlog grows after a deploy. How do you find out whether to add workers or roll back? || Look at the failure rate and DLQ rate first. If messages fail and are retried, adding workers multiplies the failures, so roll back. If processing succeeds but each is slower than the arrival rate, scale workers; compute needed workers as arrival rate × processing time.
How do you keep order for one customer while processing many customers in parallel? || Use a message-group ID or partition key equal to the customer ID (SQS FIFO message groups, or one queue per shard). Messages in one group are delivered one at a time in order; different groups proceed in parallel. The cost is head-of-line blocking within a group.
What does backpressure mean for a queue, and where would you apply it? || A producer must slow down when the system cannot keep up. Apply it with bounded queues and publisher confirms (broker pushes back), prefetch limits (per consumer), and rate limits or load shedding at the entry point. Unbounded queues only delay the failure.

@@ catalog
value: A data catalog is the system of record for what data exists. For every table it keeps the name, the schema, the place in storage where the files live, the owner, the permissions, the tags and the lineage (which jobs and tables it was built from). Without it, a data lake is a large pile of files that only the people who wrote them can use. With it, an analyst can search "customer orders", see who owns the table, read its description, and query it by name, and an auditor can see who may read the personal data in it.
A modern catalog does two jobs that used to be separate. The first is technical: it maps a table name to the current version of the table. In a lakehouse, a table is a set of immutable data files plus a metadata pointer, and a commit means moving that pointer from version N to N+1 in one atomic step. The catalog is the place where that step happens, so it decides which writers win when two commit at the same time. The second job is governance: it checks, on every request, whether this user may read this column, and it records who did what.
For the layer above, the catalog is where cross-team and cross-engine sharing happens. Spark, Trino, Flink and a BI tool all ask the same catalog "where is main.sales.orders and may I read it?". Data mesh (L1) publishes data products through a catalog. Databricks, Unity Catalog and Hive Metastore (all L0) are catalogs. The layer below that matters most is optimistic concurrency (L2): it gives the catalog a way to accept concurrent commits safely without holding locks while writers compute for minutes.
terms: Metastore — a service that stores table definitions (name, columns, partitions, storage location); the Hive Metastore is the classic example.
Namespace — a group of tables, such as a database or schema; modern catalogs use catalog.schema.table, three levels.
Table metadata — the file or record that describes one table version: schema, partition layout, list of data files, snapshot history.
Atomic commit — an update that either fully happens or does not happen; readers never see a half-written table.
Lineage — the record of which inputs produced which outputs, at table or column level.
Securable — an object that permissions apply to: a catalog, schema, table, column, view or storage location.
Credential vending — the catalog hands an engine short-lived storage credentials limited to one table's files, so engines never hold broad keys.
Data classification — a tag such as "contains personal data" that policies and audits use.
history: Every database has a system catalog, a set of tables that describe the tables. IBM's System R (1970s) already had one. What changed was that data moved out of databases into files. In the Hadoop era (2008–2012), Facebook built Hive (open-sourced in 2008), which let users write SQL over files, and its Hive Metastore stored table definitions in a relational database such as MySQL. Because it was simple and shared, Spark, Presto, Impala and others all adopted it, and it became the default catalog for a decade.
As companies had thousands of tables, finding and trusting data became a problem of its own. Open-source discovery tools followed: Apache Atlas (Hortonworks, 2015), LinkedIn's DataHub (announced in 2019, building on WhereHows), Lyft's Amundsen (2019), and commercial products such as Alation and Collibra. OpenLineage (2020, now under the Linux Foundation) defined a common event format so jobs from Airflow, Spark and dbt could report lineage in one way. Regulation (GDPR in 2018, CCPA in 2020) added pressure: companies had to know where personal data lives.
The next change came from table formats. Delta Lake, Apache Iceberg and Apache Hudi (2017–2019) added transactions to files in object storage. These formats need a place for an atomic "current version" pointer, so the catalog became part of the write path, not a directory for readers. The Iceberg REST catalog specification gave engines one HTTP interface to talk to any catalog. Databricks announced Unity Catalog in 2021 and open-sourced a version in June 2024. Snowflake and Dremio built Polaris, a REST catalog, and donated it to the Apache Software Foundation in August 2024; Apache Polaris became a top-level Apache project in early 2026. AWS Glue Data Catalog and Google's and Microsoft's catalogs fill the same role in the clouds.
how: Think of the catalog as three stores behind one API. The first store is technical metadata: for each table, the location in object storage, the schema, the format (Delta, Iceberg, Parquet) and a pointer to the current version. The second is policy: grants of permissions to users and groups on securables, plus row filters and column masks. The third is context: descriptions, owners, tags and lineage. Engines call the API; people use a user interface or search.
Take the commit path first, since this is where the lower layer, optimistic concurrency (L2), does its work. In Iceberg, a table version is a metadata JSON file that lists the schema and the current snapshot. A writer reads the current metadata, writes its new data files, writes a new metadata file that includes them, and then asks the catalog: "change the pointer from the version I started from to this new one". The catalog performs a compare-and-swap. If the pointer is still what the writer expected, it moves and the commit succeeds. If another writer moved it first, the swap fails. The failed writer does not wait with a lock; it refreshes the metadata, checks whether its changes conflict with the new snapshot (for example, did both rewrite the same files?), and if not, retries on top of the new version. This is optimistic concurrency: assume no conflict, detect it at the end, retry if needed. Locks would be expensive here, because a write job may run for minutes while the catalog only needs milliseconds to swap a pointer.
Delta Lake uses a related idea inside the table's own log folder: a writer tries to create the file for version N+1 with a put-if-absent operation, and exactly one writer succeeds. Catalogs such as Unity Catalog are moving more of this coordination into the catalog, so that the catalog is the single authority on the latest version and can enforce rules on every commit.
Now the read path with governance. An engine asks the catalog to resolve the name main.sales.orders. The catalog authenticates the caller (through OAuth or a cloud identity), checks grants (for example SELECT on the table, USE on the schema and catalog), applies column masks and row filters (for example, show only rows where region = the user's region), and answers with the table's location. Better catalogs then vend credentials: they call the cloud's token service and return a short-lived, narrowly scoped credential for just that table's path. This means the engine never holds a broad storage key, and the audit log in the catalog shows who read which table, when. Without vending, you have to give every engine wide storage access, and then catalog permissions are advice and not enforcement.
Lineage is captured in two ways. Engines or schedulers emit events (OpenLineage) that say "job J read tables A and B and wrote table C", or the platform parses query plans and records the column-level flow itself, as Unity Catalog does on Databricks. The catalog stores these edges as a graph. Impact analysis ("what breaks if I drop this column?") is then a graph traversal downstream, and root-cause analysis ("where does this wrong number come from?") is a traversal upstream.
Discovery uses the third store. Crawlers or push APIs collect metadata from many systems into a searchable index. Search matches names and descriptions, ranks by usage (tables that many people query rank higher), and shows owners, freshness and quality results. Classification tags, whether manual or from scanners that detect emails and phone numbers, then drive policies such as "mask this column for everyone outside the privacy group".
The catalog has to be fast and available because every query starts with a catalog call. Production catalogs cache metadata in engines for seconds, return table metadata in tens of milliseconds, and run replicated. The Hive Metastore, backed by one relational database, showed the limits: listing millions of partitions made queries slow, and it had no multi-file atomic commit, which is why table formats and new catalogs replaced it.
Many organizations have more than one catalog, so catalogs also federate. An engine can ask one catalog to expose tables that live in another, either by mirroring metadata or by forwarding the request, and permissions are then checked by the catalog that owns the table. Federation is useful during migrations, for example while the Hive Metastore is replaced by Unity Catalog or Polaris, but it is lossy. A table may be readable through both catalogs while only one of them knows its masks and lineage. For this reason, design the end state with one authority per table, and use federation only as a bridge.

example: Two writers update the table main.sales.orders, which is at version 5. The catalog holds the pointer "orders -> metadata v5".
Step 1. Job A (a nightly load) and job B (a correction job) both read version 5 at 01:00. A will add 200 new Parquet files. B will rewrite 3 files that contain wrong prices.
Step 2. Job B finishes first, at 01:04. It asks the catalog: "move orders from v5 to v6". The pointer is still v5, so the swap succeeds. Version 6 exists.
Step 3. Job A finishes at 01:10 and asks for "v5 to v7". The catalog sees that the pointer is v6, not v5, and refuses with a conflict error. A did not lose its 200 files; they are already written, but they are not yet part of any version.
Step 4. Job A reads v6 and compares. B rewrote 3 files. Did A also touch those 3? No, A only added files. The changes do not conflict, so A creates v7 = v6 + its 200 files, and retries "v6 to v7". It succeeds. The whole retry cost about one metadata read and one small write, a few hundred milliseconds, not another 10-minute job.
Step 5. If instead A had also rewritten one of the same 3 files, the check would find a real conflict. A would fail and its owner would see a clear error, which is correct: silently accepting both would lose one set of changes.
Now the governance side, with numbers. The table has 40 columns; one is email. A rule says "mask email unless you are in group pii_readers". An analyst outside the group runs SELECT email, amount FROM orders. The catalog authorizes the table and returns a mask expression, so the engine sees hashed values. The query log shows who ran it. Later, the privacy team asks, "Which downstream tables contain data derived from email?" A traversal of the column-level lineage graph from orders.email finds, say, 12 tables and 4 dashboards in a few seconds. Without lineage, this would be a week of asking teams.
intuition: The card catalogue and the security desk of a library, combined, with one librarian who also holds the single master copy of "which edition is current".
The idea is natural because data has three questions that no file can answer by itself: where is it, who may use it, and what does it mean. Files in a bucket have a name and nothing else. As soon as many teams and many engines share data, someone must be the single source of truth for those answers, and that source must also decide ties when two writers act at once. Putting both jobs in one service is natural because the same pointer that says "this is the current version" is the best place to check "you are allowed to see it".
mistakes: People often think a catalog stores the data. In fact it stores metadata: names, schemas, pointers, permissions and lineage. The data stays in object storage. This is why a catalog outage stops queries even though the files are fine.
People often think permissions in the catalog protect the data. In fact they protect it only if engines must go through the catalog to get access. If users or jobs also hold direct storage keys, they can read the files and skip all grants, masks and filters. Credential vending or storage policies that allow only the catalog's identity close this gap.
People often think a catalog is mainly a documentation tool. In fact for lakehouse tables it is on the write path: it arbitrates commits. A catalog with weak atomic-commit behaviour can lose updates or corrupt table state, no matter how good its search is.
People often think one catalog per engine is fine. In fact each separate catalog is a separate truth about the same table, with its own grants and its own idea of the latest version. Two catalogs pointing at the same Iceberg table can overwrite each other's commits.
People often think lineage is complete once a tool is installed. In fact lineage only covers the engines and jobs that report it. A notebook that exports a file by hand creates an invisible edge.
tradeoffs: Choose one central catalog for the organization when many teams share data and you need uniform permissions and audit. You give up some team autonomy and accept that the catalog is a critical dependency: it must be highly available, because every query calls it. Choose several catalogs (per domain or per cloud) when teams are truly independent or regions have separate legal rules; you give up easy cross-team discovery and must federate or sync metadata.
Choose a catalog with an open interface (Iceberg REST, Unity Catalog open APIs, Polaris) when you run more than one engine or may change vendors; you give up some vendor-only features. Choose the vendor's built-in catalog (Unity Catalog on Databricks, Glue on AWS) when most of your work runs on one platform and you want the deepest integration, such as column-level lineage and automatic credential vending, at the price of tighter lock-in.
Choose pushing metadata from jobs (events at run time, such as OpenLineage) when you want fresh lineage and can instrument the jobs; choose pulling by crawlers when you must cover many existing systems without changing them, and accept that the metadata is hours old and shallower.
Choose fine-grained controls (row filters, column masks, tag-driven policies) when personal or regulated data sits in shared tables; you pay with more policy logic, harder debugging of "why can't I see this row", and some query overhead. Choose coarse table-level grants plus separate curated tables when the rules are simple; you pay with more copies of the data.
friction: Metadata goes stale. Descriptions written once are wrong a year later, and owners leave the company. Without automation (owners synced from the org chart, descriptions drafted from code, tags set by scanners) the catalog fills with entries nobody trusts, and people go back to asking in chat.
Ownership is a people problem. A catalog can record that table T belongs to team X, but it cannot make team X answer questions or fix quality.
Multiple catalogs and formats create conflicting sources of truth. Federation between Hive Metastore, Glue, Unity Catalog and Polaris is improving but still loses detail, and permissions rarely translate one to one: a column mask in one system has no equivalent in another.
Scale and availability are real limits. A catalog is on the critical path of every query and every commit, so a slow or down catalog stops the platform. Commit throughput is limited by the compare-and-swap: tables with hundreds of small commits per minute (streaming writers) see many retries and conflicts, so teams batch commits.
Lineage is expensive and incomplete. Column-level lineage needs deep parsing of queries and breaks with dynamic SQL, UDFs and external tools.
Finally, security depends on the whole path. The catalog enforces permissions only for engines that honour them, and open-source engines that read files directly can bypass them unless storage access is also locked down.
practice: Register every production table in one catalog with an owner, a description, a classification (for example personal data) and a retention rule. Use three-level names and keep the naming convention simple, such as catalog per environment, schema per domain.
Grant access to groups and roles, never to individuals, and never share storage keys. Make the catalog the only identity that can read the storage paths of managed tables, and use credential vending for external engines. Review grants on a schedule, and keep the audit log for the period your auditors require.
Automate metadata. Pull owners from your directory, require a description in the pull request that creates a table, scan for personal data, and emit lineage from every pipeline (OpenLineage from Airflow and Spark, native lineage on Databricks). Measure coverage: the share of production tables with an owner, a description and lineage.
Plan for commit load: avoid very small, frequent commits to one table; compact files and batch micro-batches. Set retry policy on writers for commit conflicts, and watch the conflict rate as a metric.
Choose the catalog based on which engines need to read and write. Read support is common; write support through the catalog is where lock-in sits. Test a second engine reading and writing a table before you commit to a choice. Finally, keep a documented plan for catalog outage and for restoring metadata, since losing the catalog can mean losing track of which files make up a table.
quiz: What are the two main jobs of a catalog in a lakehouse? || Technical: map table names to the current version and arbitrate atomic commits. Governance: authorize access, mask data, and record lineage, ownership and tags.
How does optimistic concurrency let two writers commit to the same table without locks? || Each writer works on a snapshot, then asks the catalog to move the table pointer from the version it started with. Only one swap succeeds. The other refreshes, checks for real conflict, and retries on the new version.
Why can a user bypass catalog permissions even when grants are set correctly? || If the user or engine also holds direct storage credentials, it can read the files without asking the catalog. Credential vending and restricted storage access force all reads through the catalog.
A streaming job commits to one Iceberg table every 2 seconds and a nightly job also writes to it. What problem do you expect, and what do you do? || Many commits per minute cause frequent pointer conflicts and retries, and many small files. Batch the commits (for example every 1–5 minutes), compact files, and give the nightly job a retry policy.
You operate Spark, Trino and Flink. Do you choose a catalog bundled with one vendor or an open REST catalog? || Prefer a catalog with an open interface (Iceberg REST, Polaris, Unity open APIs) if several engines must write. Choose the vendor-bundled one only if almost all work stays on that platform and you accept lock-in for better integration.
interview: A catalog is down for 10 minutes. What breaks, and what do you design so the blast radius is small? || New queries cannot resolve names or check grants, and commits fail, though data files are safe. Cache metadata and grants in engines for short periods, run the catalog replicated across zones, make writers retry with backoff, and give read-only dashboards a stale-but-served fallback.
How does an Iceberg commit work, and what happens on a conflict? || The writer writes data files and a new metadata file, then asks the catalog to swap the table pointer from the base version to the new one. If the base is stale, the swap fails; the writer re-reads, validates there is no conflict with concurrent changes, rebuilds the metadata on the new base and retries. Real conflicts (same files rewritten) must fail.
Why is Hive Metastore not enough for a modern lakehouse? || It is one relational database behind a Thrift API: slow with millions of partitions, no multi-file atomic commit, weak fine-grained access control, and no credential vending. Table formats and catalogs like Unity Catalog or Polaris add those.
How would you enforce that personal data is masked for most users across Spark and Trino? || Tag columns as personal data, attach a mask policy to the tag in the catalog, make engines fetch the policy at query time, and block direct storage access. If an engine cannot enforce masks, it must not be given raw access.
How do you answer "what breaks if I rename this column?" || Use column-level lineage: traverse downstream edges from the column to jobs, tables and dashboards, and notify their owners. Coverage depends on lineage events from all engines, so check for gaps such as manual exports.
What would make you pick several catalogs instead of one? || Hard isolation needs (regulated region, separate legal entity), acquisitions with different stacks, or very different scale and availability needs. The cost is federation work and duplicated governance.

@@ servicemesh
value: When an application is split into hundreds of services, every service needs the same boring network features: encrypt the connection, prove who is calling, retry a failed call, give up after a timeout, spread calls across healthy copies, and report metrics and traces. Written inside each service, these features are copied in many languages and versions, and each copy has different bugs. A service mesh moves them out of the application into a uniform layer of proxies that sit next to every service and handle all traffic. The application makes a plain call to "orders:8080"; the mesh does the rest.
The central idea is a split into a data plane and a control plane. The data plane is the fleet of proxies that carry real requests. The control plane is a small set of servers that tell every proxy what to do: which services exist, which certificate to use, how many retries are allowed, what share of traffic goes to the new version. An operator writes a policy once, and within seconds all proxies follow it, whatever language the services use.
For the layer above, the mesh gives a platform team a place to enforce security (every call encrypted and authenticated), reliability (uniform timeouts and retries) and visibility (the same metrics for every service) without asking every product team to change code. The layers below supply the mechanisms inside the proxy: rate limiting (L2) protects services from overload with token buckets, failure detection (L2) removes unhealthy endpoints, retries with backoff and jitter (L2) hide short failures, timeouts and circuit breakers (L2) stop a slow service from taking down its callers, and mutual TLS (L2) gives each call encryption and an identity.
terms: Sidecar — a proxy that runs in the same pod (or machine) as the application and handles all of its inbound and outbound traffic.
Data plane — the proxies that carry the actual requests between services.
Control plane — the servers that compute configuration and certificates and push them to the proxies; in Istio this is a program called istiod.
xDS — the family of discovery APIs (listeners, routes, clusters, endpoints, secrets) through which a control plane configures an Envoy proxy over a streaming connection.
Workload identity — a name, such as a SPIFFE ID, that a certificate gives to a service so that others can verify who is calling.
Outlier detection — a passive health check: the proxy removes an endpoint from rotation after it returns several errors in a row.
Traffic shifting — sending a chosen percentage of requests to a different version of a service, used for canary releases.
Ambient mode — an Istio design with no sidecar per pod: a shared per-node proxy (ztunnel) handles encryption and identity, and optional waypoint proxies handle application-level rules.
history: Before meshes, big internet companies put these features in client libraries. Twitter built Finagle on the JVM, and Netflix released Hystrix (circuit breakers), Ribbon (client-side load balancing) and Eureka (service discovery). This worked while the company used one language. When teams started to use Go, Python and Node.js, each library had to be rewritten, and upgrading it meant redeploying every service.
William Morgan and Oliver Gould, who had worked on Twitter's infrastructure, founded Buoyant and released Linkerd in 2016, a proxy based on Finagle that ran next to each service. The name "service mesh" came from this work. Lyft released Envoy, a high-performance proxy written in C++ with dynamic configuration, in 2016; it joined the Cloud Native Computing Foundation and graduated in 2018. Google, IBM and Lyft announced Istio in 2017, which used Envoy as its data plane and added a control plane; Istio 1.0 came in July 2018. Linkerd 2 (2018) was rewritten in Go and Rust with a very small purpose-built proxy and graduated in the CNCF in 2021.
Experience showed the costs. A sidecar in every pod used a lot of CPU and memory, delayed pod start-up, and made upgrades painful because every pod had to be restarted. Istio released ambient mode as a new design and declared it generally available in version 1.24 on 7 November 2024. Cilium took another path, doing part of the work in the Linux kernel with eBPF and Envoy running per node. The Kubernetes Gateway API (generally available in 2023) is becoming the common way to configure routing for both north-south and mesh traffic.
how: Start with how traffic reaches the proxy. In sidecar mode, a proxy container (Envoy in Istio) is added to every pod. Rules in the pod's network namespace (iptables, or an Istio CNI plugin) redirect all outbound TCP traffic from the application to the proxy's outbound port, and all inbound traffic to its inbound port. The application does not know. When service A calls B, the request leaves A's application, is captured by A's sidecar, travels to B's sidecar, and only then reaches B's application. That is two extra proxy hops per call.
The control plane builds each proxy's configuration. It watches the Kubernetes API for services, endpoints and the mesh's own policy objects (in Istio: VirtualService, DestinationRule, AuthorizationPolicy, PeerAuthentication). It turns this into Envoy's xDS resources: listeners (which ports to accept), routes (how to match a request), clusters (groups of upstream endpoints) and endpoints (the addresses of the pods). It streams updates to each proxy over a long-lived gRPC connection. A proxy never restarts to change configuration; it swaps the new configuration in while serving traffic. This is why a change in policy reaches thousands of proxies in a few seconds.
Identity and encryption use mutual TLS (L2). The control plane acts as a certificate authority. Each proxy generates a key pair, proves which pod it belongs to (through the Kubernetes service account token), and receives a short-lived certificate with an identity such as spiffe://cluster.local/ns/prod/sa/orders. In Istio the default certificate lifetime is 24 hours, and the proxy rotates the certificate before it expires through the secret discovery service (SDS), without a restart. When A calls B, the two proxies perform a TLS handshake where both sides present certificates. So the traffic is encrypted, and B's proxy knows the caller is "the orders service", not just "some IP address". An authorization policy can then say "only orders may call payments, only POST /charge".
Reliability features come from the lower concepts and are configured as policy. Retries (L2): a route can say "retry up to 2 times on connect failure or HTTP 503, with a 25 ms base interval and jitter". Timeouts and circuit breakers (L2): a route has a total timeout, for example 2 seconds, and a cluster has limits on connections and pending requests, so that when they are full the proxy fails immediately with an error instead of queueing. Failure detection (L2) appears as outlier detection: if an endpoint returns 5 consecutive 5xx responses, the proxy ejects it from the load-balancing pool for 30 seconds (growing with repeated ejections) and then tries it again. Rate limiting (L2) uses token buckets in the proxy: a local limit protects one pod, and a global limit asks a shared rate-limit service so a caller gets the same quota across all proxies.
Load balancing inside the proxy is per request, not per connection, so it works with HTTP/2 and gRPC, where a single long connection would otherwise pin all traffic to one pod. The default is typically least-request using the "power of two choices" idea, with locality preference to keep traffic inside a zone when possible.
Telemetry is almost free because every request passes through a proxy. Each proxy exports the same metrics for every service: request rate, error rate and latency histograms (the RED signals), plus access logs and trace spans. One caution: the proxy cannot connect the incoming request to the outgoing requests that the application makes because of it. The application must copy the trace headers (for example traceparent) from the incoming to the outgoing calls; otherwise traces break into disconnected pieces.
Ambient mode splits the work in two. A ztunnel runs on each node as a shared proxy that handles layer-4 features only: mutual TLS, identity, simple authorization and telemetry for all pods on the node. When layer-7 features are needed (retries on HTTP status, header routing, JWT checks), traffic goes through a waypoint proxy that runs per namespace or per service, outside the application pods. Teams add workloads to the mesh by labelling a namespace, with no pod restarts.
Traffic that leaves the mesh needs its own rules. An egress gateway is a dedicated proxy through which all calls to outside hosts must pass, so the team can allow only named destinations, log them, and apply timeouts. Between clusters, an east-west gateway forwards mutual TLS traffic from one cluster to another, and the control planes share service lists so a service in cluster 1 can call a healthy copy in cluster 2 if its local copies fail. These multi-cluster features multiply the operational surface, so teams add them only after one cluster is stable.

example: A shop has 200 services. The platform team wants three things: mutual TLS everywhere, a canary release of the new version of "cart", and safe retries.
Step 1. Cost estimate for sidecars. Istio's published numbers for version 1.24 are about 0.20 vCPU and 60 MB of memory per sidecar at 1,000 requests per second. If the 200 services run 2,000 pods in total, the sidecars use up to 2,000 × 0.20 = 400 vCPU and 2,000 × 60 MB = 120 GB. That is the worst case at the test load; idle pods use less. With ambient mode, a cluster of 100 nodes needs one ztunnel per node, about 0.06 vCPU and 12 MB each at the same load: 6 vCPU and 1.2 GB for the layer-4 part. Waypoints add cost only for the namespaces that need layer-7 rules.
Step 2. Canary. The team writes a rule: 95% of requests to "cart" go to version v1, 5% to v2. The control plane turns this into weighted clusters in every client proxy. Each proxy picks a destination per request using the weights. With 1,000 requests per second to cart, about 50 per second reach v2. The team watches the error rate and p99 latency of v2 in the mesh dashboards. After 10 minutes with no regression, they change the weights to 50/50, then 100% v2. No client code or DNS changed.
Step 3. The retry trap. Suppose a request passes through three services: frontend calls cart, cart calls pricing, pricing calls a database. The mesh is set to 3 attempts per hop, and the application libraries also retry 3 times. If the database is slow and every call fails, each layer multiplies the attempts. With mesh retries alone at three layers, one user request creates 3 × 3 × 3 = 27 database attempts. If the application libraries also retry, the number is even higher. At 1,000 user requests per second that is 27,000 attempts per second against an already struggling database. The fix: retry in one layer only (usually the one nearest the failure), use a retry budget (for example "retries may be at most 20% of the request volume", as Linkerd does) and set timeouts that decrease along the call chain.
Step 4. Policy. The team applies "default deny" and then allows only frontend to call cart, and cart to call pricing. A compromised "email" service tries to call pricing; its certificate identity is not in the allow list, and the proxy rejects the call at once.
intuition: Every service gets a bodyguard and an interpreter who handle the dangerous and tedious parts of every conversation, and a central office that gives all of them the same instructions.
The design is natural because the network behaviour of a call does not depend on the business logic, so it can be moved to a place that is the same for every service. Putting it in a separate process, rather than a library, means one implementation, written once in a fast language, works for all languages, and it can be upgraded without touching the application. The control-plane split follows an old pattern: keep the fast path simple and stateless, and put decisions and state in a slow path that only sends instructions.
mistakes: People often think a service mesh is needed for microservices. In fact many systems run well with a few services, client libraries and a gateway. A mesh pays for itself when you have many services, many languages and a real need for uniform mTLS, policy and telemetry.
People often think the mesh makes the application resilient automatically. In fact it provides the tools; the policies decide the result. A retry rule applied at every layer multiplies load, and a timeout longer than the caller's timeout does nothing useful. The mesh also cannot make a non-idempotent POST safe to retry.
People often think mutual TLS in the mesh protects all traffic. In fact it protects traffic between meshed workloads. Traffic to workloads outside the mesh, or in permissive mode (which accepts plain text during migration), is not protected. The traffic between the application and its sidecar on localhost is also in clear text, which matters only if the pod itself is compromised.
People often think traces appear without any code change. In fact the proxy creates spans for each hop, but only the application can pass the trace context from an incoming request to the outgoing ones, so it must propagate the headers.
People often think sidecars add no meaningful latency. In fact each call goes through two extra proxies, each adding some latency and CPU; the cost is small per hop, but with deep call chains it adds up, and tail latency (p99) is affected more than the median.
tradeoffs: Choose a mesh when you have dozens of services in several languages and a clear need for mutual TLS, uniform policy and consistent telemetry, and you have a platform team to run it. Choose libraries plus a gateway when you have a few services in one or two languages; you give up uniformity and central control, but avoid an extra system whose upgrades and failures you must handle.
Choose sidecar mode when you need strong per-pod isolation of proxy and rich layer-7 features on every workload, and you can pay about 0.2 vCPU and 60 MB per pod. Choose ambient mode (or Cilium's per-node design) when the cost and restarts of sidecars hurt and most workloads only need mutual TLS and basic authorization; you give up the strict per-pod boundary (a per-node proxy is shared by many pods) and you add a waypoint hop for layer-7 features.
Choose Istio when you need the richest traffic management, multi-cluster support and a large ecosystem; you accept a large API and more operational work. Choose Linkerd when you want a small, simple mesh with a lightweight Rust proxy and are happy with a smaller feature set; check the current licensing and release model of the distribution you plan to use, since stable builds from the vendor have been offered under commercial terms.
Choose retries and timeouts in the mesh when you want one consistent policy; choose them in the application when the application understands which operations are idempotent and can degrade gracefully. Either way, avoid doing both.
friction: Cost and latency come first. Sidecars use CPU and memory in every pod, and the sum can be a visible part of the cluster bill. Each hop adds proxy processing time, and the tail latency matters most in long call chains.
Complexity is the second cost. Policy objects interact in non-obvious ways (a route rule, a destination rule, an authorization policy and a Kubernetes network policy may all apply), and when a call fails it is hard to know which layer said no. Debugging means reading proxy logs, configuration dumps and metrics, not only application logs.
Operations is the third. The control plane is critical: if it is down, existing proxies keep working with their last configuration, but new pods cannot get certificates or configuration, and certificate expiry becomes a risk if the outage is long. Upgrading the mesh means restarting all sidecars in a controlled order, and versions of control plane and data plane must stay compatible.
Scale is a limit: the control plane must send configuration to every proxy, and if every proxy knows about every service, memory and update time grow quickly. Teams scope each workload's view of the mesh.
Application interaction is the fourth: protocols that the proxy does not understand are treated as raw TCP, server-first protocols can fail at start-up, and long-lived streaming connections need care at rollout.
Finally, a mesh does not remove the need for good application design. It cannot fix a service that is slow or chatty. And it adds a new place to hide mistakes: a misconfigured mesh can take down every service at once.
practice: Adopt gradually. First install the mesh in observability mode for a few services and look at the metrics. Then enable mutual TLS in permissive mode, check that nothing sends plain text, and switch to strict. Add authorization policies last, starting from the most sensitive services, and use default-deny only when you have a complete map of who calls whom (the mesh's own telemetry gives you this map).
Set timeouts and retries on purpose. A good starting rule: a timeout on every route; one layer retries; retries only on connect failures and clearly safe status codes; a retry budget; timeouts that shrink down the chain. Test with fault injection (the mesh can inject delays and errors) to see how the chain behaves.
Limit configuration scope so that each proxy loads only what it needs; this lowers memory and speeds up updates. Set resource requests for proxies, and monitor proxy CPU, memory and the time it takes for configuration to arrive. Keep control plane replicas at three or more across zones and rehearse certificate expiry and control plane outage.
Propagate trace headers in every service, and put the trace ID in logs. Decide who owns the mesh: a small platform team with on-call, clear upgrade rules, and a canary process for upgrading the mesh itself. If your main need is only mutual TLS or network policy by identity, consider whether a simpler option is enough, such as Cilium's identity-based policies or per-node ambient mode.
quiz: What is the difference between the data plane and the control plane in a service mesh? || The data plane is the set of proxies that carry requests between services. The control plane computes configuration and certificates and pushes them to the proxies, but does not touch request traffic.
How does a mesh give every service an identity usable for mutual TLS? || The control plane acts as a certificate authority. Each proxy proves which workload it serves (through its service account token) and gets a short-lived certificate with an identity like a SPIFFE ID, rotated automatically. Both sides present certificates in the TLS handshake.
Why can retries in the mesh and in the application together cause an outage? || Retries multiply across layers. With 3 attempts at each of 3 hops, one user request can cause 27 calls to the last service, which overloads an already slow dependency. Use one retry layer and a retry budget.
Using Istio's published numbers (0.20 vCPU and 60 MB per sidecar, 0.06 vCPU and 12 MB per ztunnel), what do 1,500 pods on 60 nodes cost in sidecar mode and in ambient (layer-4 only) mode? || Sidecars: 1,500 × 0.20 = 300 vCPU and 1,500 × 60 MB = 90 GB. Ambient ztunnels: 60 × 0.06 = 3.6 vCPU and 60 × 12 MB = 720 MB (waypoints extra), at 1,000 requests per second per proxy.
When would you not adopt a service mesh? || When you have only a handful of services, one language, and no strict policy need. Libraries, a gateway and plain TLS cost less than running a mesh and its control plane.
interview: What exactly happens to a request from service A to service B in sidecar mode? || Traffic from A's application is redirected by iptables or CNI rules to A's sidecar, which picks an endpoint of B (load balancing, retries, timeout), opens an mTLS connection to B's sidecar, which checks the caller identity against policy and forwards to B's application on localhost. Both proxies record metrics and spans.
The control plane goes down for an hour. What breaks? || Existing proxies keep serving with their last configuration and certificates. New pods cannot get configuration or certificates, policy changes do not apply, and certificates that expire during the outage (default 24 hours) cause failures if the outage is longer. Run replicas across zones.
Why would you pick ambient mode over sidecars, and what do you lose? || Lower CPU and memory (a shared per-node proxy), no pod restarts to join the mesh, and simpler upgrades. You lose a per-pod proxy boundary, and layer-7 features need a waypoint hop, which can add latency and concentrate load.
A team reports p99 latency doubled after joining the mesh. How do you investigate? || Compare proxy-reported latency with application latency, check proxy CPU throttling (a low CPU limit is common), connection pool limits, retries and timeouts, mTLS handshake rate (connection reuse), and configuration size. Test with the proxy bypassed on one pod.
How do you stop retry storms in a mesh? || Retry at one layer, retry only safe failures, use a retry budget or a limited number of attempts, add jitter, set shrinking timeouts and circuit-breaker limits, and make operations idempotent.
How is a mesh different from an API gateway? || A gateway is the front door for external client traffic (north-south): authentication of end users, quotas, routing to services. A mesh handles traffic between internal services (east-west) with workload identity and policy. They are often used together.

@@ apigateway
value: An API gateway is one server (or a small cluster) that stands in front of many backend services and receives every request from outside clients: mobile apps, browsers, partner systems. It decides who the caller is, whether the caller may continue, how many requests the caller may make, and which backend should receive the request. It then forwards the request and returns the answer.
The problem is easy to see in a system with 40 services. Without a gateway, each service would need its own public address, its own TLS certificate, its own code to check tokens, its own rate limiter, its own logging format and its own version rules. Clients would need to know all 40 addresses and would break each time a service moved. Every one of these copies would also be a place where a security mistake can hide. The gateway collects the shared work at one entry point, so the services behind it can stay small and can trust that a request that reached them has already passed the checks.
For the layer above (public APIs, mobile back ends, partner integrations, developer portals, and more recently AI gateways that route calls to language-model providers), the gateway gives a stable contract: a fixed address, a documented set of paths and versions, quotas, and an analytics view of who uses what. The layers below do the technical work: rate limiting (L2) with token buckets protects backends from overload and gives each customer a fair share, and tokens, OAuth and OIDC (L2) let the gateway check identity and permissions from a signed token on each request, without calling a login server every time.
terms: Reverse proxy — a server that accepts client requests and forwards them to backend servers, then returns the responses; the client talks only to the proxy.
TLS termination — the gateway ends the encrypted connection from the client, so backends can receive plain or re-encrypted traffic inside the network.
Route — a rule that maps a request (host, path, method, headers) to a backend and to policies.
JWT (JSON Web Token) — a signed token that carries claims such as user ID and scopes, which the gateway can verify locally with a public key.
Quota — a limit on how many requests a client may make in a period, such as 10,000 per day.
Throttling — slowing or rejecting requests above a rate limit, usually with HTTP status 429 (Too Many Requests).
Backend for frontend (BFF) — a gateway built for one kind of client (for example the mobile app) that shapes responses for that client.
North-south traffic — traffic between outside clients and the system; traffic between internal services is called east-west.
history: Reverse proxies came first. Apache httpd's proxy modules, Squid, and then NGINX (released by Igor Sysoev in 2004), and HAProxy (2001) sat in front of web applications to terminate TLS, cache and balance load. They were configured with files and knew little about APIs.
As companies exposed public APIs in the late 2000s, they needed API management: keys, quotas, billing and developer portals. Apigee was founded in 2004 and offered this as a product (Google acquired it in 2016). Mashape built Kong on NGINX and OpenResty and open-sourced it in 2015, with plug-ins for authentication and rate limiting. Amazon API Gateway launched in July 2015 as a managed service tied to AWS Lambda. Netflix released Zuul as its edge service, and Sam Newman described the backend-for-frontend pattern around 2015 for cases where one gateway could not serve both a phone and a web page.
Kubernetes made routing a standard object. The Ingress API handled simple host and path rules, but every controller used its own annotations to add features. The Gateway API project, developed by the Kubernetes community from 2019, replaced annotations with typed resources (GatewayClass, Gateway, HTTPRoute) with clear roles for infrastructure owners and application teams. It reached version 1.0 and general availability for core features in October 2023. In November 2025 the Kubernetes project announced that the widely used ingress-nginx controller would receive only best-effort maintenance until March 2026 and then be retired, and it named Gateway API as the way forward. The newest variant is the AI gateway, which applies the same ideas (authentication, per-key quotas, routing, logging) to calls to model providers, counting tokens instead of requests.
how: A request reaches the gateway's public address, normally through a cloud load balancer. The gateway works through a pipeline of steps, usually called a filter chain or plug-in chain. The order matters, because cheap checks should come first.
Step 1, connection and TLS. The gateway ends the TLS connection (the L3 TLS concept does the heavy cryptographic work: the handshake, certificate check and session keys). It reads the HTTP request, and often enforces limits on header size, body size and timeouts, to stop slow or oversize requests early.
Step 2, routing. The gateway matches the request against route rules, using host, path prefix, method and headers. For example, /v2/orders/* goes to the orders service version 2. The route table is held in memory and updated dynamically from a control plane or from the Kubernetes API, without restarts.
Step 3, authentication. The gateway reads the Authorization header. For a JWT it checks the signature with a public key it fetched earlier from the identity provider (a JWKS endpoint) and cached, then checks the expiry time, the issuer and the audience. This is the tokens and OIDC concept (L2) at work: because the token is signed, the gateway needs no call to the identity provider for each request, so the check takes microseconds. For opaque tokens or API keys, the gateway looks them up in a cache, and goes to a token-introspection endpoint or a key store on a miss. Mutual TLS or request signing are used for partner systems.
Step 4, authorization. The gateway compares scopes or roles in the token with what the route requires, for example "needs scope orders:read". Fine-grained decisions (this user may see this order) still belong to the service, because only the service knows its data.
Step 5, rate limiting and quotas. Here the rate limiting concept (L2) is used. A token bucket per client holds, say, 100 tokens and refills at 50 tokens per second; each request removes one token. If the bucket is empty, the gateway answers 429 with a Retry-After header, and the backend never sees the request. With several gateway nodes, the bucket must be shared (a fast store such as Redis) or divided (each node gets a share of the limit), and the choice trades accuracy against latency and failure risk. Limits are usually set per API key, per user, per IP address and per route, and can differ per plan.
Step 6, transformation and protection. The gateway may add or remove headers (for example add a verified user ID header, and strip any such header sent by the client), rewrite paths, convert protocols (REST at the edge, gRPC inside), validate the request against a schema, and check it with a web application firewall.
Step 7, forwarding. The gateway picks a healthy backend instance, using load balancing and health checks, opens or reuses a connection, applies a timeout and possibly a limited retry for safe operations, and streams the response back. A circuit breaker can stop forwarding to a failing service and return a fast error or a cached answer.
Step 8, observability. The gateway writes an access log line and metrics (request count, status codes, latency) and starts or continues a trace by adding a trace ID header. Because every external request passes here, this is the best place to measure the whole system as users see it.
Some gateways also aggregate: one client call fans out to three services and the gateway combines the results. This saves round trips for mobile clients on slow networks, but it moves business logic into the gateway, which should be done with care.
Where the gateway runs also matters. A common layout has a cloud load balancer (layer 4) in front of a pool of gateway instances in several availability zones, and the gateway instances are stateless: routes, keys and certificates are loaded from a control plane and cached in memory, so any instance can serve any request and instances can be added or removed freely. Response caching is another gateway feature. For public, read-only endpoints, the gateway can keep a copy of a response for a few seconds, keyed by path and relevant headers, which can remove most load from a backend during a spike. Long-lived connections such as WebSockets and server-sent events need separate timeouts and connection limits, since a gateway that holds 100,000 open streams uses memory in proportion to them.

example: A company exposes an orders API through a gateway with three plans. The free plan allows 5 requests per second and 10,000 per day; the paid plan 100 per second and 5 million per day.
Step 1. A client with a free key sends requests at 8 per second. The gateway uses a token bucket with capacity 10 and refill 5 tokens per second. The bucket starts full. Second 1: 10 + 5 − 8 = 7 tokens left. Second 2: 7 + 5 − 8 = 4 left. Second 3: 4 + 5 − 8 = 1 left. Second 4: only 1 + 5 = 6 tokens are available for 8 requests, so 6 pass and 2 get HTTP 429 with Retry-After: 1. From then on only about 5 requests per second pass. The initial burst was allowed, and the long-term rate is held at 5. A well-written client slows down when it sees 429.
Step 2. The daily quota is a counter per key. 10,000 requests per day means the counter reaches 10,000 at some time and the key is blocked until midnight (or a rolling window).
Step 3. Authentication. A mobile app sends a JWT valid for 15 minutes. The gateway verifies it with a cached public key: roughly 20 to 100 microseconds of CPU for an RSA-2048 signature check on modern hardware (ES256 checks take a little longer). At 2,000 requests per second, that is well under one CPU core. If the gateway instead called the login server for each request, that server would see 2,000 calls per second.
Step 4. A key is stolen and used from a new country. The team revokes the key. With a JWT, revocation takes effect only when the token expires (up to 15 minutes), unless the gateway also checks a deny list. This is the trade of short-lived signed tokens: fast checks, slow revocation, solved by short lifetimes and deny lists for emergencies.
Step 5. The gateway adds 1.5 ms to the median request (TLS reuse, JWT check, routing) and the backend takes 20 ms, so users see about 21.5 ms. At 2,000 requests per second, two gateway instances at 50% load each keep failure safe: if one dies the other takes 100% and the load balancer removes the dead one in a few seconds.
intuition: The reception desk of a building: it checks ID, gives directions, limits how many people enter at once, and keeps a visitor log, so the offices behind it can focus on their own work.
It is natural because these tasks are the same for every service and are better done once, at the one place all external traffic must pass. A single choke point is a good place to enforce rules, because it cannot be bypassed if the backends accept only gateway traffic. The same design also makes the gateway dangerous: everything depends on it, so it must stay simple and fast.
mistakes: People often think the gateway should contain business logic, such as pricing rules or workflow steps. In fact logic in the gateway becomes a hidden second application, owned by nobody, deployed on a different schedule from the services it affects. Keep it to cross-cutting concerns.
People often think the gateway replaces authorization inside services. In fact it can check who you are and coarse permissions, but only the service knows whether this user owns this order. If services trust any request that reaches them, one bypass of the gateway (a misconfigured network path) exposes everything.
People often think a gateway and a service mesh are the same thing. In fact the gateway handles traffic from outside clients (north-south), where callers are untrusted and many; the mesh handles traffic between services (east-west), with workload identities. Many systems use both.
People often think rate limiting stops denial-of-service attacks. In fact per-key limits protect against a misbehaving client, but a large attack from thousands of addresses needs protection at the network edge (a CDN or DDoS service) before traffic reaches the gateway.
People often think the gateway is a single point of failure by nature. In fact a gateway can be run as many stateless instances behind a load balancer. It becomes a single point of failure when it depends on one shared store (for limits or sessions) with no fallback decision for when that store fails.
tradeoffs: Choose a managed gateway (Amazon API Gateway, Google Apigee, Azure API Management) when you want no servers to operate and built-in features such as keys, plans and developer portals, and your request volume is moderate; you pay per request, you accept the vendor's limits (for example a fixed integration timeout and payload size) and you accept lock-in. Choose a self-run gateway (Kong, Envoy-based, NGINX) when you have high volume (per-request pricing becomes large at billions of requests), need custom plug-ins or must run on your own network; you give up convenience and take on upgrades and on-call.
Choose a thin gateway (routing, authentication, limits) when your services are well designed and clients can call them directly in a few round trips. Choose a backend-for-frontend or aggregation layer when mobile clients on slow networks need one call instead of five; you give up simplicity, and each client type needs its own team to own that layer.
Choose a local rate limit in each gateway instance when approximate fairness is enough and you want the lowest latency and no shared dependency; the limit then is "N per instance", so the real total changes with the number of instances. Choose a shared, global limit (Redis or a rate-limit service) when you sell quotas or must be exact; you add about a millisecond per request and a dependency whose failure you must handle by deciding to allow or to block.
Choose signed JWTs checked locally when you want speed and no per-request call to the identity provider; you give up instant revocation. Choose opaque tokens with introspection (or a cache with short time-to-live) when you must revoke at once; you add load on the token service.
friction: The gateway is on the path of every request, so its latency and availability are your latency and availability. A slow plug-in, a slow authentication call, or a slow upstream with no timeout can use all connections and take the front door down for all clients.
Logic creeps in. Every team wants "just one small rule" in the gateway: a rewrite, a special case for one customer, a feature flag. Over years this becomes a large, fragile script that only a few people understand. The cure is a clear rule about what belongs there, and review of every change.
Configuration is a risk. A bad route or a wrong rate limit applies to all traffic immediately. Teams need configuration in version control, review, validation, gradual rollout and fast rollback.
Shared state is difficult. Global rate limits, sessions and caches need a shared store, which adds latency and a new failure mode. Different gateways in different regions may count the same client twice.
Versioning and compatibility need discipline. Once a path and a field are public, clients depend on them. Breaking changes need new versions and long overlap, with the gateway used to route old versions to old code and to measure who still uses them.
Costs can be surprising. Per-request pricing, data transfer, and log volume add up, and a gateway that logs full bodies creates both cost and privacy risk. Finally, the move from ingress controllers to the Gateway API, including the retirement of ingress-nginx in 2026, means that many teams must migrate configuration and learn new resources.
practice: Keep the gateway thin. Put authentication, coarse authorization, rate limits, TLS termination, request validation, routing and observability there, and nothing else. Review any request to add business logic, and move it into a service.
Enforce limits and timeouts everywhere: request size, header size, connection and read timeouts for clients, and per-route timeouts for backends. Return clear errors: 401 for missing or invalid credentials, 403 for not allowed, 429 for rate limited with a Retry-After header, and 503 with a short body when a backend is unavailable. Document the limits per plan.
Make backends accept traffic only from the gateway (network policy, mutual TLS), and strip any identity headers that clients send, before adding your own. Pass the verified identity to services in a signed token or a trusted header.
Run at least three instances in separate zones, and size them so the loss of one still leaves 50% headroom. Decide what happens when the rate-limit store is down; for most APIs, "fail open for a short time with local limits" is better than refusing everyone. Keep configuration in Git, validate in CI, roll out by percentage, and keep a one-step rollback. Measure per-route latency, error rate and 429 rate, and alert on changes.
Version your API explicitly (in the path or a header), announce deprecations, and use gateway analytics to see which clients still call old versions before you remove them. If you run Kubernetes, choose Gateway API resources for new work, since the older Ingress API is frozen and the ingress-nginx controller has been retired.
quiz: What are the main jobs of an API gateway, and which do the lower concepts supply? || Terminate TLS, authenticate and authorize using tokens (OAuth/OIDC), apply rate limits (token buckets), route requests to backends, and log and measure traffic. Tokens give identity without a login call per request; rate limiting protects backends and shares capacity fairly.
Why can a gateway check a JWT without calling the identity provider on each request, and what does it cost? || The JWT is signed, so the gateway verifies it locally with a cached public key and checks expiry and audience. The cost is that revoking a token before it expires needs an extra deny list or short lifetimes.
A token bucket has capacity 10 and refills at 5 tokens per second. A client sends 8 requests every second, starting with a full bucket. When does the first 429 appear, and what rate passes afterwards? || The bucket holds 7, then 4, then 1 tokens after seconds 1, 2 and 3 (10 + 5 − 8 = 7, and so on). In the fourth second only 1 + 5 = 6 tokens are available for 8 requests, so 2 are rejected. Afterwards about 5 requests per second pass.
Why is rate limiting in the gateway not enough to defend against a large distributed attack? || Attackers use many addresses and keys, so per-client limits do not trigger, and the traffic can fill the gateway's network or connections. Defence belongs at the network edge (a CDN or DDoS service) before the gateway.
When would you choose Amazon API Gateway over self-run Kong or Envoy, and when the reverse? || Choose the managed service for moderate traffic, fast setup and built-in keys and plans. Choose a self-run gateway for very high volume (per-request cost), custom plug-ins, or when you must run in your own network, accepting operations work.
interview: A gateway adds 3 ms at p50 but 400 ms at p99. Where do you look? || Look at connection pool limits and queueing to upstreams, slow plug-ins (token introspection, remote rate-limit calls), TLS handshakes from short-lived clients, garbage collection or CPU throttling, and retries. Compare gateway-measured upstream time with total time to separate gateway cost from backend cost.
How do you implement a rate limit across 10 gateway instances? || Options are a shared counter in Redis (exact, adds a network call and a dependency), local limits of N/10 per instance (cheap, inexact if load is uneven), or a hybrid where instances take blocks of tokens from a central store and refill in batches. Decide what happens if the store fails.
What goes in the gateway and what does not? || In: TLS, authentication, coarse authorization, rate limits, routing, validation, observability, protocol translation. Out: business rules, workflow, data joins, per-customer special cases. The reason is ownership and release cadence: the gateway should change rarely and for platform reasons.
How do you roll out a gateway configuration change safely? || Keep config in Git, validate and test in CI, deploy to a canary instance or a small share of traffic, watch error rate and latency, and roll back with one step. Gateway config affects all clients at once.
A client's access token was stolen. How do you respond? || Revoke the refresh token and the session at the identity provider, add the token ID to a gateway deny list for the remaining lifetime, rotate keys if needed, and check logs for usage. Short access-token lifetimes limit exposure.
Why might you place a CDN or WAF in front of the gateway? || Absorb volumetric attacks, cache public responses, block known bad patterns, and hide the gateway's origin address. The gateway then focuses on identity and API policy.

@@ loadbalancing
value: One server has a limit: a fixed number of requests per second, and one machine that can fail. A load balancer solves both problems by standing in front of many identical copies of a service (the backends) and deciding, for every connection or request, which copy should take it. Clients see one address. If a backend dies, the balancer stops sending it traffic. If demand grows, you add backends, and the balancer starts using them.
The hard part is the word "decide". Sending requests in turn is easy. But requests cost different amounts, backends differ in speed, some requests must go to the same backend (a cache that holds the data), and a backend that is alive may still be sick. A good balancer must pick the right backend with little information and very little time, since it sits in front of every request and adds its own latency to each.
For the layer above (web sites, APIs, databases with read replicas, streaming services, ad exchanges that must answer in under 100 ms), the balancer provides capacity and availability. It also allows rolling deployments: take one backend out, update it, put it back. The layers below supply two ideas. Consistent hashing (L2) lets the balancer map a key, such as a user ID or a cache key, to a backend so that adding or removing a backend moves only a small share of keys. Failure detection and heartbeats (L2) let the balancer find dead or slow backends through health checks and remove them quickly, without sending real users to them to find out.
terms: Backend — one copy of the service that receives traffic from the balancer; also called an upstream, target or endpoint.
Layer 4 (L4) balancing — choosing a backend per TCP or UDP connection, using only IP addresses and ports.
Layer 7 (L7) balancing — choosing a backend per HTTP request, using the path, headers or cookies; it needs to read and often to terminate the protocol.
Health check — a probe, active (the balancer calls a URL every few seconds) or passive (it watches real traffic for errors), that decides whether a backend may receive traffic.
Session affinity (sticky sessions) — sending all requests of one client to the same backend, by cookie or by hashing the client address.
Connection draining — letting a backend finish its current requests before removal, while giving it no new ones.
Anycast — announcing the same IP address from many places so that routing sends each client to the nearest one.
Power of two choices — pick two backends at random and use the one with less load.
history: In the early web, the simplest balancer was DNS round robin: one name returned several addresses in rotating order. It costs nothing, but it cannot detect a dead server, and caches keep old answers for the TTL period. Hardware appliances solved this in the late 1990s. F5 Networks (founded 1996) shipped BIG-IP in 1997, and Cisco, Citrix NetScaler and others followed. They sat in front of server rooms and used specialised chips, and they were expensive.
Software replaced them. Linux Virtual Server (1998) put a layer-4 balancer in the kernel. Willy Tarreau's HAProxy (2001) and NGINX (2004) did layer 7 on commodity machines. Cloud providers offered balancers as a service: Amazon Elastic Load Balancing began in 2009, and today AWS sells an Application Load Balancer (layer 7), a Network Load Balancer (layer 4) and a Gateway Load Balancer.
Theory improved the algorithms. In 1994 Azar, Broder, Karlin and Upfal showed that putting each ball in the less full of two random bins gives an exponentially smaller maximum load than using one random bin. Michael Mitzenmacher's 1996 PhD thesis applied this "power of two choices" to load balancing with delayed information. Consistent hashing (Karger et al., 1997) came from the same period for web caches. In 2016 Google described Maglev in an NSDI paper: a software network load balancer on ordinary servers that uses ECMP routing from the routers and its own variant of consistent hashing, so that no hardware box is needed, and it scales by adding machines. Also in 2016, Google researchers published "consistent hashing with bounded loads", later used in HAProxy and by Vimeo.
Microservices moved some balancing into the client. gRPC clients, and the sidecar proxies of service meshes, balance each request themselves using a list of endpoints received from a control plane (the xDS protocol), so there is no central balancer to become a bottleneck. Global traffic management uses DNS and anycast to send users to the nearest region.
how: Every balancer does four things: it knows the list of backends, it knows which ones are healthy, it picks one per unit of work, and it forwards the traffic. Each of these has options.
Forwarding comes in two layers. A layer-4 balancer reads only the TCP or UDP headers. It picks a backend when the first packet of a connection arrives, remembers the choice in a connection table, and forwards all later packets of that connection to the same backend. Because it does not parse HTTP, it is fast (millions of packets per second per machine), but it sees only connections. A layer-7 balancer terminates the client connection, reads each HTTP request, and sends it over its own connection to a backend. It can route by path, host or header, retry on failure, add headers, and balance each request separately, at the price of more CPU and of holding TLS keys. Large systems often use both: an L4 tier (like Maglev or an NLB) spreads connections over a fleet of L7 proxies.
Choosing a backend is the algorithm. Round robin goes down the list in turn, and weighted round robin gives bigger backends more turns. It works when all requests cost about the same. Least connections picks the backend with the fewest open connections, and least requests uses the number of requests in flight instead. Envoy's least-request policy by default samples two random backends and picks the one with fewer active requests. This reacts to slow backends: a backend that is slow has more requests waiting, so it receives fewer new ones. Power of two choices avoids the cost and staleness of looking at all backends: pick two at random, compare, and take the better one. With n backends and random choice, the busiest backend carries about log n / log log n times the average, while with two choices it carries only about log log n, a large drop. It also avoids herd behaviour: if every balancer sends all requests to the single least-loaded server, that server is flooded before the next update.
Hashing is used when the request has a key that should always reach the same backend, for example a cache key, a user ID or a video ID. Plain hash(key) mod N breaks when N changes: going from 10 to 9 backends remaps about 90% of the keys. Consistent hashing (L2) places backends and keys on a ring (or uses a lookup table, as in Maglev hashing), and each key goes to the next backend on the ring; removing a backend moves only the keys it owned, roughly 1/N of them. Virtual nodes (each backend appears at 100 to 200 points on the ring) smooth out the share. With bounded loads, a backend that exceeds, say, 1.25 times the average load passes the key to the next one, so a hot key cannot overload a single machine.
Health checking uses failure detection (L2). Active checks send a request such as GET /healthz every 2 to 10 seconds. A backend is removed after a few consecutive failures (for example 3) and added back after a few successes (for example 2), which gives hysteresis, and prevents flapping. Passive checks (outlier detection) watch real traffic, and eject a backend after several consecutive errors for a period. A good health endpoint reports whether the instance can serve real work (its dependencies, its warm-up state), but it should be careful: if the check calls a shared database and the database is slow, all backends can fail the check at once and the balancer removes the whole fleet.
Operations around the algorithm matter as much. Slow start gradually increases the share of traffic to a new backend while its caches and JIT warm up. Connection draining gives a leaving backend time to finish requests (AWS target groups default to 300 seconds of deregistration delay, which is often too long). Retries to a different backend help for idempotent requests, but must be limited by a retry budget, or they multiply load during an outage.
Finally, global load balancing chooses the region. DNS-based systems return different addresses by client location and health, with short TTLs (30 to 60 seconds). Anycast uses BGP (L3) so that the same IP is announced from many data centres and the internet routes each client to the nearest one, and a failed site withdraws its announcement. The cost is that routing is not aware of load, and a route change in the middle of a connection can break it, so anycast works best for short requests (such as DNS and HTTP over short connections).

example: Four examples with numbers show how the choices matter.
Example 1, remapping with hashing. A cache tier has 10 servers and 1,000,000 keys. With key mod 10, one server fails, and the rule becomes key mod 9. A key keeps its server only if key mod 10 equals key mod 9. Over any block of 90 consecutive keys this holds for only 9 keys, so about 90% of keys move, and 900,000 lookups per million now miss the cache and hit the database. With consistent hashing, only the keys of the failed server move: about 100,000, which is 10%. The database sees one tenth of the extra load.
Example 2, power of two choices. Place 1,000,000 balls into 1,000,000 bins, one at a time. If each ball picks one random bin, the fullest bin typically ends with about 8 to 10 balls, while the average is 1. If each ball looks at two random bins and goes to the emptier one, the fullest bin has only about 4. Think of the balls as requests and the bins as servers: sampling two servers and taking the less loaded one removes most of the worst pile-ups, with no shared state between balancers.
Example 3, HTTP/2 pinning. A gRPC client opens one long connection through an L4 balancer to backend B1 out of 4. All its requests stay on B1. With 4 clients and 4 backends, random connection placement leaves probability 4!/4⁴ = 24/256 ≈ 9.4% that all four backends get exactly one client. In most cases, some backend gets two clients and another gets none. Then you add a fifth backend; it receives nothing, since all existing connections remain. The fix is an L7 balancer or client-side balancing that chooses a backend for each request, and a maximum connection age (for example 5 minutes) so connections are replaced.
Example 4, health check settings. Checks run every 5 seconds, fail after 3 failures, and recover after 2 successes. A backend that crashes at time 0 is detected after 3 failed checks: between 10 and 15 seconds. During that time, with 10 backends, 10% of the traffic goes to a dead server and fails, unless the balancer retries on another backend. At 1,000 requests per second, that is about 100 failed requests per second for up to 15 seconds, or up to 1,500 requests, without retries. With passive outlier detection (eject after 3 consecutive errors), the dead server is removed within about 3 requests to it, a fraction of a second.
intuition: Several checkout lanes with a person at the front who sends each customer to the shortest line, and who closes a lane when the cashier leaves.
The design is natural because the problem splits into two parts that are easy to separate: knowing what is available (the list and the health) and deciding where to send. Randomness helps with the second part: a random pick spreads load without any shared state, and a small amount of information (two samples) fixes most of the imbalance. Hashing helps when state is local to a backend: send the key to the place that already has the data.
mistakes: People often think round robin is fair. In fact it is fair in the number of requests, not in the work. If one request in a hundred takes 100 times longer, round robin sends the next requests to a backend that is already busy. Least-requests or power of two choices adapts to this.
People often think a health check that returns 200 means the backend is healthy. In fact many checks only prove that the process answers. A backend may have a full queue, a broken connection to its database, or a cold cache. Make the check represent readiness for real work, but do not make it depend on shared dependencies, or one dependency failure removes everything.
People often think that adding a backend immediately shares the load. In fact with long-lived connections (HTTP/2, gRPC, WebSockets), existing connections stay where they are, and the new backend gets little or nothing until connections are renewed. Balance per request, or set a maximum connection age.
People often think sticky sessions are a good way to keep state. In fact they make load uneven and make failures hurt more: when the backend dies, all its sessions are lost. Keep state in a shared store or a signed cookie, and use affinity only as an optimisation for caches.
People often think the load balancer cannot fail. In fact it is a single point of failure unless it is itself redundant. Cloud balancers hide this with multiple nodes, but a self-run pair of HAProxy servers needs a failover mechanism (such as a floating IP with VRRP) or an L4 tier with ECMP.
tradeoffs: Choose L4 balancing when you need maximum throughput and low latency, or when the protocol is not HTTP (databases, MQTT, custom TCP); you give up request-level routing, retries and header-based decisions. Choose L7 when you need path routing, per-request balancing for HTTP/2 or gRPC, TLS termination and retries; you give up CPU (typically several times more per request than L4), and the proxy holds your certificates.
Choose round robin or random when requests are uniform and backends are identical, because it needs no state. Choose least-requests or power of two choices when request cost varies or backends differ; you give up some predictability, and you need accurate in-flight counts at each balancer. If many balancers each see only part of the traffic, power of two choices still works well, since it needs no global view.
Choose consistent hashing when locality is worth more than perfect balance: caches, sharded state, or sticky workloads, where a cache hit saves milliseconds or a database read. You give up even load, because popular keys create hot spots; bounded loads or replicas of hot keys reduce that. Choose a plain stateless pool for everything else.
Choose a central balancer (cloud ALB, HAProxy fleet) when you want simple clients and central control and TLS; you add a hop (about 0.5 to 2 ms) and a component to scale. Choose client-side balancing (gRPC with xDS, or a sidecar) when you want no extra hop and fast reaction to failures; you give up simplicity, since each client needs the endpoint list and correct behaviour, and bugs are spread over many languages.
Choose active health checks for slow, steady detection with low risk of false alarms; choose passive outlier detection for fast reaction to real errors. Use both: active checks for readiness, passive checks for sudden failure.
friction: Load balancers hide the real cause of many outages. When a backend is slow, not dead, health checks pass, the balancer keeps sending traffic, and queues grow. Least-requests helps, but a slow backend with many retries can still pull down the fleet. Overload is the other failure: when the remaining backends carry the load of failed ones, they may fail too (cascading failure). Capacity must allow for losing a zone, usually 30 to 50% headroom.
Uneven load comes from many sources: long connections, large requests, hot keys, different instance sizes, noisy neighbours. Measure the load per backend (requests, CPU, p99), not only the average.
Health checking has trade-offs. Aggressive checks detect failure sooner but cause flapping in a brief pause (a GC pause of two seconds can remove a healthy backend); gentle checks leave users on bad servers for longer. A change in the health endpoint can take the whole service out.
State and affinity cause problems. Sticky sessions pin users to servers; caches warm differently on different backends; consistent hashing sends all requests for a viral item to one machine.
The balancer itself is limited. L4 balancers are limited by packets per second and connection table size; L7 by CPU and TLS handshakes. New TLS connections cost much more than reused ones (a full handshake costs much more CPU than a request on a reused connection), so a connection storm after a restart can overload a proxy fleet.
Finally, the controls can fight each other. The balancer retries, the client retries, the mesh retries, and an autoscaler adds capacity slowly, so during an incident the combined effect is a surge of load. Retry budgets, timeouts that shrink along the path and load shedding at the backend are the usual defences.
practice: Use health checks that test real readiness (the process can accept work, its essential dependencies are reachable, warm-up is done), keep them cheap, and do not make them depend on a shared database. Set check intervals of a few seconds and thresholds of 2 to 3 failures to remove and 2 to 3 successes to add. Add passive outlier detection for real traffic.
Prefer least-requests or power of two choices to plain round robin when request costs vary. For HTTP/2 and gRPC, balance per request (L7 or client-side), and set a maximum connection age or send GOAWAY periodically so connections are rebalanced when you scale out. Use consistent hashing only when affinity matters, with virtual nodes and a bounded-load option.
Drain connections during deployments: stop sending new requests, wait for in-flight requests to finish (30 to 60 seconds is often enough, and shorter than the platform's default), then stop the process. Use slow start for new instances.
Plan capacity for failure: with N zones, size for the loss of one (each zone must carry N/(N−1) of its normal load, 150% with 3 zones). Test it by removing a zone in a game day. Limit retries with a budget and make sure the timeouts decrease down the call chain.
Measure per-backend request rate, concurrency, error rate and latency, and alert on imbalance, for example when the busiest backend has more than 1.5 times the median load. For global traffic, keep DNS TTLs short for failover records, and test region failover regularly. For a database fleet, remember that balancing reads across replicas needs awareness of replication lag.
quiz: What is the difference between L4 and L7 load balancing? || L4 chooses a backend per TCP/UDP connection using IP addresses and ports; it is fast but blind to HTTP. L7 reads each HTTP request, so it can route by path or header and balance per request, at a higher CPU cost.
Why does the power of two choices give much better balance than a single random choice? || Comparing two random backends and taking the less loaded one avoids the worst pile-ups. The maximum load falls from about log n / log log n to about log log n times the average, with no global state.
A cache tier has 20 servers and one fails. How many keys move with mod-N hashing and with consistent hashing? || With mod-N (20 to 19), about 95% of keys move. With consistent hashing, only the failed server's keys move, about 1/20 = 5%.
Health checks run every 4 s, with 3 failures needed to remove a backend. In the worst case, how long does a crashed backend keep receiving traffic, and what limits the damage? || Between about 8 and 12 s, depending on when the crash falls between two checks (3 × 4 = 12 s at most, plus any check timeout). Retries to another backend, and passive outlier detection that ejects after a few real errors, limit the damage.
You add 5 new backends to a gRPC service behind an L4 balancer, and they get no traffic. Why, and what do you do? || Existing long-lived HTTP/2 connections stay pinned to the old backends, and L4 balances only per connection. Use L7 or client-side per-request balancing, and set a maximum connection age so clients reconnect.
interview: How does consistent hashing reduce remapping, and what problem remains? || Backends and keys sit on a ring, and a key goes to the next backend clockwise. Removing a backend moves only its keys, about 1/N. The remaining problem is uneven load: backends own arcs of different length and hot keys land on one server. Virtual nodes smooth arcs, and bounded loads or replication handle hot keys.
Your service has 10 backends and one becomes slow but still passes health checks. What happens with round robin, and what do you change? || Round robin keeps sending it 10% of requests, so latency and queues grow and clients time out. Use least-requests or power of two choices, add passive outlier detection, and make the health check include latency or error rate.
Why does a balancing tier often have L4 in front of L7? || L4 handles connection-level distribution cheaply at very high packet rates and gives stable addresses; the L7 proxies do TLS, routing, and per-request balancing. The L4 tier scales horizontally with ECMP and consistent hashing, so L7 proxies can be added or removed.
How do you design for the loss of an entire availability zone? || Run backends in at least 3 zones, size so two zones carry full load (about 150% per zone), use zone-aware balancing with failover, check that dependencies are also redundant, and test it. Beware of retry storms and cold caches after failover.
What are the dangers of retries at the balancer? || They multiply load during overload and can cause cascades. Retry only idempotent requests and connection errors, use a retry budget (for example 10 to 20% of traffic), add jitter, and use a different backend for the retry.
How would you balance requests to a stateful, sharded cache with hot keys? || Hash by key to a shard (consistent hashing with virtual nodes), replicate hot keys to several shards or add a small local cache in front, use bounded loads to cap any one node, and monitor per-key request rates to find hot keys early.

value: A content delivery network (CDN) is a worldwide fleet of cache servers, placed in hundreds of cities and inside internet providers' networks. When a user asks for a picture, a script, a video segment or a web page, the CDN answers from a server a few milliseconds away instead of from your own server (the origin), which may be 10,000 kilometres away. If the CDN does not have the object, it fetches it once from the origin, keeps a copy and serves the next users from the copy.
Two problems drive this. The first is physics. Light in fibre travels at about 200,000 km per second, so a round trip between New York and Sydney needs at least 160 ms, and real routes are slower. A page that needs several round trips (TCP, TLS, request) is slow, whatever your server does. The second is load. If a million people watch the same live stream or download the same software update, an origin cannot send the same bytes a million times. A CDN lets the origin send them once to each cache and lets the cache serve the crowd.
For the layer above, nearly all consumer internet traffic depends on CDNs: video streaming, web sites, software and game downloads, mobile app assets. Ad delivery relies on them for creatives and tracking scripts. The layers below supply the machinery. Cache eviction (L2) decides which objects stay on a cache server's limited disk and memory. Consistent hashing (L2) decides which server inside a data centre owns which object, so servers do not store duplicates and the cluster survives machine loss. BGP and internet routing (L3) let anycast CDNs announce the same IP address from many places, so the network itself steers each user to a nearby site.
terms: Origin — the server that holds the authoritative copy of the content, run by the site owner or a storage service.
Edge (point of presence, PoP) — a CDN site close to users, with cache servers.
Cache hit / miss — a hit is served from the cache; a miss needs a fetch from a higher tier or the origin.
Cache hit ratio — the share of requests (or bytes) served from cache; 95% is a good value for static content.
TTL (time to live) — how long a cached copy counts as fresh, set by the origin through Cache-Control headers.
Purge (invalidation) — an instruction to the CDN to remove or mark stale an object before its TTL ends.
Origin shield (tiered cache) — a middle layer of caches that edges ask first, so that the origin sees one request for a missing object instead of one from every edge.
Anycast — announcing the same IP address from many locations, so each user reaches the nearest one by normal routing.
history: In the 1990s, "flash crowds" (sudden floods of visitors) could bring down a single web server. In 1998 MIT professor Tom Leighton and his student Danny Lewin, with others, founded Akamai to solve this. The theory behind it was consistent hashing, a 1997 paper by Karger, Leighton, Lewin and others, which allows many caches to share load without a central directory. Akamai started commercial service in 1999. Its original method was DNS-based: its name servers answered each user's DNS query with the address of a nearby, healthy cache. Other early companies included Digital Island and Speedera.
The market grew with video and e-commerce. Amazon CloudFront launched in 2008. Limelight, Level 3 and Edgecast were large players. Cloudflare was founded in 2009 and launched in 2010, with a different architecture: anycast, where every data centre announces the same addresses, plus a focus on security services for small customers. Fastly began in 2011 with an emphasis on instant purge and programmable configuration (using the Varnish cache). Netflix started building Open Connect in 2011 and 2012: its own cache appliances, installed free of charge inside internet service providers, filled overnight with popular titles, so that most streaming traffic never crosses the wider internet.
CDNs then turned from caches into general edge platforms. They absorb denial-of-service attacks, run web application firewalls, terminate TLS, and run customers' code at the edge (Cloudflare Workers from 2017, Lambda@Edge, Compute at Edge). In 2022 the IETF published RFC 9111, the current HTTP caching standard, which collects rules from many earlier documents. Today a few providers (Akamai, Cloudflare, Fastly, and the clouds' own CDNs) carry a large part of the world's web traffic, which brings its own risks when one of them fails.
how: A CDN request has five steps: get the user to the right site, pick the right server in the site, check the cache, fetch on a miss, and decide what to keep.
Step 1, steering. There are two main methods. With DNS steering (Akamai's original design), the CDN's name server answers www.example.com with the IP of a server chosen using the resolver's location, current load and measured network quality. With anycast (Cloudflare, and part of other CDNs), the same IP is announced from every site through BGP (L3). Routers on the internet send a packet along the shortest BGP path, which usually leads to the nearest site. If a site fails, it stops announcing the address, and traffic moves to the next nearest site within seconds to a minute. Big CDNs combine both methods.
Step 2, choosing a server inside the site. A site has dozens or hundreds of cache servers. If a request went to a random server, each server would hold a copy of every popular object, and the total cache space would be small. So a layer-4 or layer-7 balancer uses consistent hashing (L2) on the URL: all requests for one object go to the same server (or a few of them), and the site's disk is used once, not many times. When a server joins or fails, consistent hashing moves only about 1/N of the objects, instead of all of them. Very popular objects are copied to several servers to avoid a hot spot.
Step 3, the cache lookup. The key is usually the host plus path plus selected query parameters plus the values of headers named in the Vary header. The server looks the key up in memory (an index), and reads the body from RAM or disk. If the object is fresh (its age is below max-age or s-maxage in the Cache-Control header), it is a hit and the server replies at once. If it is stale, the server may revalidate: it sends the origin a conditional request with If-None-Match (the ETag), and the origin can answer 304 Not Modified with no body, which is cheap. The directive stale-while-revalidate (RFC 5861) lets the cache serve the stale copy while it refreshes in the background, so users never wait.
Step 4, the miss. The edge asks the next tier: a regional cache or an origin shield, and only that tier talks to the origin. When 1,000 users request an uncached object at the same moment, request collapsing (also called coalescing) makes the cache send one request to the upstream and hold the others until the answer arrives. Without this, a cold popular object produces a stampede on the origin. The origin's response travels back through the tiers; each tier may store it according to its headers.
Step 5, the eviction decision. Cache space is finite, and eviction (L2) removes the least useful objects: LRU removes the one not used for the longest time, LFU the least frequently used, and modern designs mix recency, frequency and size (for example, TinyLFU-style admission). CDN traffic has a special feature. Akamai's engineers Maggs and Sitaraman reported that nearly three quarters of the objects in one trace were requested only once ("one-hit wonders"). Caching them wastes disk writes and pushes out useful content. Akamai's answer is "cache on second hit": a Bloom filter (a compact set-membership structure) records which URLs were seen once, and an object is stored only when it comes a second time. In their data this cut disk writes by about 44% and raised the byte hit rate from 74% to 83%.
Beyond caching, edge code can rewrite requests, check tokens, resize images, and assemble pages from cached fragments. Large video is split into segments of a few seconds (HLS or DASH), and each segment is a separate cacheable object, so a stream is just many small files, which fits a cache well. For live video, segments are very short-lived and the key issue is to collapse the many viewers' requests for the newest segment into one origin request.
Security and cost controls sit in the same path. The edge terminates TLS, so it holds certificates for the customer's domains and often renews them automatically; it can check signed URLs or cookies before serving paid content; and it can apply rate limits and a web application firewall before a request reaches the cache or the origin. Large uploads and API writes are not cached but still travel faster, because the user's connection ends at a nearby edge, and the edge reuses a warm, long-lived connection to the origin. Billing follows the same path: most CDNs charge for bytes sent to users, for requests, and sometimes for fetches from the origin.

example: A shop's web site serves product images. Peak traffic is 20,000 requests per second. The average image is 200 KB.
Step 1, bandwidth. 20,000 × 200 KB = 4 GB/s, or 32 Gbit/s. The shop's origin has a 2 Gbit/s link, so it cannot serve this alone. With a CDN at a 95% hit ratio, only 5% of requests reach the origin: 32 × 0.05 = 1.6 Gbit/s, which fits. At 99% it would be 0.32 Gbit/s. The hit ratio is the most important number: moving from 95% to 99% cuts origin load by five times.
Step 2, latency. A user in Sydney, origin in New York, round-trip time (RTT) about 220 ms in practice. Without a CDN: TCP handshake (1 RTT), TLS 1.3 handshake (1 RTT) and the request (1 RTT) means about 3 × 220 = 660 ms before the first byte arrives. With a CDN edge in Sydney at an RTT of 15 ms: 3 × 15 = 45 ms on a hit. Even on a miss, the edge to origin link uses a warm, reused connection, so the miss costs about 1 × 220 ms plus origin time, and not 3 RTT.
Step 3, the stampede. A new product photo is published at 09:00 and 5,000 users request it in the first second. Without collapsing, each of those 5,000 requests can be a miss that goes to the origin. With collapsing at each of 30 edge sites, there are at most 30 origin requests. With an origin shield, there is exactly 1.
Step 4, versioning. The page links to /img/shoe.jpg. The shop changes the photo. The cache still holds the old one for its TTL of 24 hours. Fix: name files by content hash, /img/shoe.3f9a1c.jpg, and set Cache-Control: public, max-age=31536000, immutable. A change makes a new name, so there is nothing to purge. Only the HTML page that refers to the names needs a short TTL (for example 60 s) or a purge.
Step 5, an urgent purge. A wrong price appears in cached HTML at 10:00. The team calls the purge API for the surrogate key "product-4711" (a tag attached to all pages that show this product). The CDN removes those pages from all PoPs; on fast networks this takes from under a second to a few seconds. For the next minutes, the origin must handle the refill: 30 sites each asking again, or one shield request.
intuition: Stock the popular products in every neighbourhood shop instead of shipping each one from the central warehouse, and put one regional depot between the shops and the warehouse.
The idea is natural because requests are not equal: a small share of objects gets most of the requests, and the same object is wanted by many people in the same place. Copy the object near them once, serve it many times. Physics sets the lower bound on latency, so the only way to go below it is to be closer. Caches then turn a distance problem into a storage problem, which is cheap.
mistakes: People often think a CDN is only for static files. In fact CDNs also accelerate dynamic content: they terminate TLS near the user, keep warm connections to the origin, route over better paths, and can cache API responses for seconds. Even a TTL of 5 seconds on a busy endpoint turns thousands of requests into one.
People often think purge is instant and reliable, so long TTLs are safe. In fact purges take time to spread, can fail for some PoPs, and cost operational effort. The robust approach is immutable, versioned file names for assets, and short TTLs only for entry pages.
People often think more cache is always better. In fact caching personalised or private responses by mistake is a serious security bug: if the cache key ignores a cookie or an Authorization header, one user's page can be served to another. Use Cache-Control: private or no-store for user-specific content, and check what is in the cache key.
People often think the CDN protects the origin completely. In fact only cached objects are protected. Attacks can add random query strings to make every request a miss (cache busting), so the origin needs its own limits and the CDN's rules should ignore unknown parameters.
People often think the hit ratio is a single number. In fact it differs by object type, region and hour, and by request count versus bytes. A 95% request hit ratio with large video objects missing can still send most of the bytes to the origin.
tradeoffs: Choose a CDN for any public content with global users or a traffic peak larger than your origin; the cost per GB is far lower than building your own capacity, and latency drops by large factors. You give up some control: configuration errors can break all traffic quickly, and you depend on the provider's availability.
Choose long TTLs with versioned names for static assets, because they give hit ratios above 95% and no purge need. Choose short TTLs or purge-by-tag for content that changes unpredictably (prices, news); you give up hit ratio and add origin load, and you need a purge pipeline you can trust. Choose stale-while-revalidate and stale-if-error when slightly old content is acceptable, to hide origin slowness and outages.
Choose an origin shield when you have many PoPs and a weak or costly origin; you give up one extra hop on misses (some milliseconds) and add a single tier that must be reliable. Skip it when traffic is small or the origin is strong.
Choose one CDN when simplicity and a single contract matter. Choose two or more (multi-CDN) when your business cannot tolerate a provider outage, or when performance differs by region; you give up simple configuration, cache sharing and consistent security rules, and you need steering logic (usually DNS-based) and double the integration work.
Choose a managed CDN when your traffic is mixed and moderate. Choose building your own caches inside ISP networks (as Netflix did) only at very large, predictable video volumes where the savings in transit cost pay for the engineering and hardware.
Choose edge compute for small, latency-sensitive logic (redirects, A/B tests, token checks, header changes). Keep stateful or heavy logic in the core region, since edge functions have tight CPU and memory limits and data may be far away.
friction: Invalidation is the oldest problem. A cached copy is a promise that may be wrong, and the more places copies live, the harder it is to withdraw them. Purges are eventually consistent across the fleet.
Personalised content is hard to cache: the cache key must include everything that changes the response, but every extra key part reduces the hit ratio. Teams often split a page into a cacheable shell and small personalised fragments loaded by script.
The hit ratio can fall without warning, because of new query parameters, cookies added by a tracking script, headers in Vary, or a deploy that changes URLs. Cold caches after a big purge or a new region make the origin take the full load at once, so origin capacity must be planned for misses, not for the average.
Costs hide in many places: egress per GB, request fees, log delivery, edge compute time, and origin fetch fees. Prices differ by region, and cache-busting traffic can bring a large bill.
Concentration is a risk. When one large provider has an outage, many sites fail together, and the failure can also take down your control plane for purging and configuration at the same time.
Debugging is harder: behaviour depends on the PoP, on the tier, and on which version of configuration reached it. You need response headers that show hit or miss, age and PoP, and log streams from the CDN.
Finally, privacy and compliance matter. The CDN terminates TLS and sees all unencrypted data, and may store objects in many countries. Contracts, regional controls and encryption of sensitive fields are needed.
practice: Set cache headers on purpose. For static assets use content-hashed file names and Cache-Control: public, max-age=31536000, immutable. For HTML and API responses decide a short TTL (seconds to minutes) plus stale-while-revalidate and stale-if-error, and use no-store or private for personalised data. Make sure the cache key includes what changes the response (language, device class if you serve different content) and ignores what does not (tracking parameters).
Use surrogate keys or cache tags so you can purge a product, an article or a section in one call. Test purge as a routine: you want to know how long it takes before the incident.
Turn on origin shielding and request collapsing. Size the origin for the miss rate at its worst: a full purge, a cold start, and failure of one PoP. Add rate limits at the origin too.
Measure the hit ratio by content type, by region and by bytes, and watch the origin request rate. Log the CDN's cache status header. Alert on a drop in hit ratio, a rise in origin 5xx, and a rise in the share of uncacheable responses.
For video, use segment lengths of 2 to 6 seconds and keep manifests short-lived and segments long-lived; pre-position popular content before an event. For software releases, warm the caches by requesting the files from several regions before announcing.
Lock down the origin so that it accepts only CDN traffic (allow lists, signed headers, or private connectivity), and use signed URLs for paid content. Review the plan for a CDN outage: lower TTL for the DNS record, a second provider, or direct-to-origin fallback for critical paths.

How does anycast steer users, and what are its risks? || The same prefix is announced by BGP from many sites, and routers pick the shortest path, usually nearby. Risks: BGP paths do not reflect load or real latency, route changes can break long connections, and a site must withdraw its route when failing.
Your hit ratio dropped from 96% to 70% after a release. How do you debug it? || Check what changed in cache keys and headers: new query parameters or cookies, a changed Vary header, Cache-Control or Set-Cookie on responses, new URLs, shorter TTLs, or a purge. Look at the cache-status header by URL pattern and compare the top uncached URLs before and after.
How do you stop a thundering herd on the origin when a popular object expires? || Request collapsing at each tier, an origin shield, stale-while-revalidate so users are served the old copy during refresh, jittered TTLs, and origin-side rate limits. Plan origin capacity for the miss path.
Why does a CDN need an eviction policy tuned differently from a normal LRU cache? || CDN traffic has many one-hit wonders and objects of very different sizes. Plain LRU lets scans and large objects flush useful content. Admission filters (second-hit), frequency tracking and size-aware policies raise the hit ratio and reduce disk writes.
How do you serve personalised pages while using a CDN? || Cache the shared shell and static assets, vary on a small number of keys (such as language), load personal parts with separate API calls that are private or short-cached, or use edge logic to assemble fragments. Never cache by default responses that depend on cookies or authorization.

@@ workflow
value: A data platform does not run one job. It runs hundreds that depend on each other: load raw events, clean them, join them with reference data, build a daily table, refresh a dashboard, train a model. Each step needs the earlier steps to finish correctly, some run every hour and some every day, and some fail for reasons that disappear when you try again. A workflow orchestrator is the system that knows these dependencies, starts each task at the right time, retries it when it fails, records what happened, and tells a person when it cannot fix the problem alone.
Before orchestrators, teams used cron: a list of times with commands. Cron starts a command at a time and then forgets it. It does not know that the second job needs the first one's output, it does not retry, it does not show which run failed, and it cannot rerun last month. The orchestrator replaces "run at 02:00" with "run when the inputs are ready, in the right order, and keep a record".
For the layer above (Airflow, Dagster, dbt runs, Databricks Workflows, Temporal workflows, nightly ETL and machine-learning pipelines), the orchestrator is the control tower of the data platform: it decides what runs, when, and what to do on failure. It stands on three lower ideas. DAG scheduling (L2) gives the dependency graph and the rule "a task is ready when all its upstream tasks have succeeded". Idempotence (L2) makes retries and reruns safe, because running a task twice gives the same result as running it once. Durable execution (L1) is the newer idea for long-running, code-defined workflows: the engine records every step so that a workflow can survive crashes and continue where it stopped.
terms: DAG (directed acyclic graph) — tasks as nodes and dependencies as arrows, with no cycles, so there is always a valid order to run them.
Task — one unit of work in the graph, such as running a Spark job or a SQL statement.
Run — one execution of the whole graph for a given time interval or trigger.
Logical date (data interval) — the slice of data a run is responsible for, such as "2026-10-25", independent of the clock time when it actually runs.
Backfill — running the graph for past intervals, for example after fixing a bug or adding a new table.
Sensor — a task that waits for a condition, such as a file arriving or a partition appearing.
Retry policy — how many times, and with what delay, a failed task is tried again.
SLA / freshness target — the deadline by which an output must be ready, such as "gold table by 06:00".
Asset — a data product (a table, a file, a model) that the orchestrator tracks, as opposed to only tracking tasks.
history: Unix cron (1975) started commands on a schedule, and for twenty years that was the whole story. As Hadoop pipelines grew in the late 2000s, chains of cron jobs broke in confusing ways. Yahoo built Oozie for Hadoop (open-sourced in 2010), with workflows written in XML. Spotify wrote Luigi (2012) in Python, where tasks declare their outputs and dependencies. Maxime Beauchemin, at Airbnb, created Airflow in 2014 with one important choice: pipelines are Python code, so they can be generated, tested and reviewed like any program. It was open-sourced in 2015, joined the Apache incubator in 2016 and became a top-level Apache project in 2019. Airflow became the de facto standard.
Its limits also became clear: scheduling by time and not by data, a scheduler that parses all DAG files again and again, tasks that share data awkwardly, and hard local testing. Newer tools answered these points. Prefect (2018) focused on Python functions that run anywhere. Dagster (2018, from Elementl, 1.0 in 2022) made data assets the centre: you declare tables and the code that produces them, and the system derives the graph. Argo Workflows (2017) ran each step as a container on Kubernetes. Managed products appeared inside data platforms, such as Databricks Workflows (jobs with task graphs) and cloud services like AWS Step Functions and Cloud Composer.
In parallel, the durable-execution idea spread. Amazon's Simple Workflow Service (2012), then Uber's Cadence (2017) and its fork Temporal (2019) let developers write a long-running process as ordinary code while the engine stores an event history and replays it after any failure. Airflow itself changed: Airflow 2.4 added data-aware scheduling with datasets, and Airflow 3.0 (22 April 2025) added assets, a task execution API, scheduler-managed backfills, DAG versioning and a new interface, moving closer to these newer ideas.
how: An orchestrator has five parts: a definition of the graph, a scheduler, a state store, executors, and an interface for people. The pieces work in a loop.
First, the definition. In Airflow, a DAG is a Python file that creates task objects and sets dependencies (extract >> transform >> load). In Dagster, you declare assets and what they depend on. The graph is a DAG (L2): its edges mean "must finish before", and because it has no cycles, there is always a valid topological order. Tasks that do not depend on each other can run in parallel, so the shape of the graph sets the shortest possible time (its critical path).
Second, the scheduler creates runs. A schedule such as "daily at 02:00" or a trigger such as "when asset A is updated" creates a run for a specific logical date. A run holds one task instance per task, each with a state: scheduled, queued, running, success, failed, up for retry, skipped, or upstream failed. These states live in a database, which is the single source of truth. The scheduler loops over all active runs, finds tasks whose upstream tasks have all succeeded (the DAG scheduling rule), checks limits such as pools and concurrency, and queues them.
Third, executors run the tasks. The scheduler does not run the work. It hands each ready task to an executor: a local process, a Celery worker, a Kubernetes pod, or a call to Databricks or Spark. The worker updates the task state when it finishes. A good design keeps the heavy work in the engine that is built for it (Spark, SQL warehouse, dbt), so the orchestrator only starts the work, waits and records. A task that downloads and transforms a 50 GB file on the orchestrator's own worker is a common design error.
Fourth, failure handling. A task has a retry policy, for example 3 attempts with delays of 5, 10 and 20 minutes (exponential backoff). This works because of idempotence (L2): the task is written so that running it again for the same logical date replaces its previous result rather than adding to it. A task overwrites the partition for date D, or uses MERGE on a key, so a retry after a half-finished attempt leaves the right data. If retries are exhausted, the task becomes failed, downstream tasks get "upstream failed", and the system sends an alert. A person fixes the cause and clears the failed task, and the scheduler continues from there, without rerunning what already succeeded.
Fifth, time and data. The logical date matters because runs must be about data intervals, not about the clock. The run for 2026-10-25 processes that day's data even when it executes on the 26th at 02:00, and a rerun in December still processes 25 October. Backfills use this: the scheduler creates runs for each past interval, subject to a limit on how many run at once. Sensors and data-aware triggers handle late data: instead of "run at 02:00 and hope the input is there", the run waits for the partition to exist, or starts when the upstream asset is updated.
Durable execution works differently. In Temporal, the workflow is a function in ordinary code, which calls activities (the units with side effects). Every step result is stored in an event history. If the worker dies, another worker replays the function from the start, using the stored results instead of redoing the activities, until it reaches the point where it stopped. This is why workflow code must be deterministic (no random numbers or clock reads outside the engine's API). It suits long processes with waits (days for an approval, a timer for 30 days), where a DAG with a fixed shape is awkward.
Finally, observability: the interface shows runs, durations, failure reasons, logs and a calendar of history, and metrics such as queue time and task duration are exported. For freshness, good setups track whether an output was ready on time (an SLA), not only whether each task ran.
A word on scale and failure of the orchestrator itself. The scheduler is a loop that must finish each pass quickly, so large installations run several scheduler copies that coordinate through row locks in the database, and they keep DAG parsing in separate processes. Workers are stateless and can be lost at any time: if a worker dies, the scheduler notices the missing heartbeat after a timeout (often a few minutes), marks the task instance as failed or up for retry, and starts it elsewhere. This is again failure detection with heartbeats, and it is another reason tasks must be safe to run twice. Task logs and the output of each attempt are kept, so a person can see why attempt 1 and attempt 2 differed.

example: A team runs a daily pipeline for ad-impression reports. Tasks: extract (reads yesterday's files, 10 min), clean (Spark, 25 min), aggregate (Spark SQL, 15 min), publish (refresh dashboard table, 2 min). Schedule: daily at 02:00. The report must be ready by 06:00.
Step 1, the critical path. The tasks are in a chain, so the run takes 10 + 25 + 15 + 2 = 52 minutes. Started at 02:00, it ends at about 02:52, leaving a 3 h 08 min margin to the 06:00 deadline.
Step 2, a transient failure. At 02:35, the clean task fails because a cluster node was lost. The retry policy waits 5 minutes and tries again. Because clean is idempotent (it overwrites the partition date=2026-10-25 using an INSERT OVERWRITE for that date), the second attempt starts fresh and ends correctly at 03:05. The rest of the chain runs and ends at about 03:22. Nobody was woken up.
Step 3, a data problem. The next night the input files are late; the source system finishes at 03:30. The 02:00 run started with no data, and extract produced an empty table. A better design replaces the time-based start with a sensor or an asset trigger: the extract task waits until the partition for the day exists (checking every 5 minutes, with a timeout of 3 hours), or the whole run starts when the upstream asset is updated. Now the run starts at 03:30 and ends at 04:22, still before 06:00. The SLA monitor would alert at 05:30 if the output were not ready, which gives a person 30 minutes.
Step 4, a bug and a backfill. A bug in the aggregate step has produced wrong numbers for 30 days. After the fix, the team backfills those 30 logical dates. Each run takes 52 minutes. The cluster allows 5 runs at the same time. The total time is 30 / 5 = 6 rounds × 52 minutes = 312 minutes, about 5 hours 12 minutes. If runs were not idempotent, the backfill would double-count rows; because each run overwrites its date partition, the final data is right even if some runs are retried or the backfill is stopped and started again.
Step 5, the cost of a bad design. Suppose extract and clean run inside the orchestrator's worker and use 16 GB of memory. With 20 daily DAGs starting at 02:00, workers run out of memory, tasks are killed, and the scheduler's own heartbeat is delayed. The fix is to submit the work to Spark and keep the orchestrator light.
intuition: A conductor who knows the order of the music, starts each section on time, and restarts a section when a musician misses a note, without stopping the whole orchestra.
The idea is natural because a pipeline is a graph of promises: this table will exist when that table is correct. If you write the graph down, a program can do what people did by hand: start work in order, wait, retry, and show what is red. The extra step that makes it work well is idempotence, which turns "do it again" from a risk into a normal repair.
mistakes: People often think the orchestrator should run the heavy computation. In fact it should only coordinate. Heavy work belongs in Spark, a warehouse or a container service. Work done on the orchestrator's workers makes the scheduler slow and hard to scale.
People often think a retry fixes failures. In fact a retry fixes only transient failures, and it is safe only if the task is idempotent. A task that appends rows to a table, retried after a partial write, creates duplicates. Retrying a deterministic bug three times only delays the alert.
People often think a green run means the data is right. In fact the orchestrator knows whether a task exited without an error, not whether the output is complete or correct. An extract that reads zero rows succeeds. Add data checks (row counts, freshness, null rates) as tasks that can fail the run.
People often think a schedule by clock time is enough. In fact if the upstream is late, a time-based run processes missing data and shows success. Wait for the data (sensors, asset triggers), or at least check that the input exists.
People often think the logical date is the date the job runs. In fact it labels the data interval the run is about, and in Airflow classic scheduling the run for an interval starts after that interval ends. Mixing these up causes off-by-one-day errors.
People often think Temporal-style workflows and Airflow compete for the same job. In fact DAG schedulers fit batch pipelines with a fixed shape; durable execution fits long-lived business processes with branching, waiting and many instances. Many companies use both.
tradeoffs: Choose Airflow when you want the largest ecosystem (hundreds of provider packages for clouds and databases), Python-defined pipelines, and a team that can run it or a managed version; you give up asset awareness in older designs, accept scheduler tuning at scale, and need discipline so DAG files stay light. Choose Dagster or an asset-centred design when the main question is "is this table fresh and correct" and you want lineage and data checks built in; you give up some of Airflow's breadth and must learn a different model.
Choose the orchestrator inside your data platform (Databricks Workflows and its declarative pipelines) when nearly all work runs on that platform; you get tight integration, no separate cluster to operate, and automatic dependency tracking for pipelines. You give up cross-system reach (calling a system outside the platform may need extra work) and you accept platform lock-in. Choose a general orchestrator when work spans several systems.
Choose time-based schedules for simple, independent daily jobs with reliable inputs. Choose data-aware triggers (assets, sensors on partitions or table versions) when inputs arrive late or vary; you give up simplicity of "runs at 2 a.m." and gain correctness.
Choose a DAG when the steps are known and repeated, and the unit of retry is a task. Choose durable execution (Temporal, Step Functions) when a process lasts hours to months, waits for people or timers, and must survive restarts; you give up the batch-oriented UI and must write deterministic workflow code.
Choose small DAGs that each produce one data product when teams are separate; choose one big DAG only if the steps are tightly coupled. Many small DAGs linked through assets scale better in teams, but need clear contracts between them.
friction: Orchestrators become dumping grounds. Business logic, credentials, SQL strings and one-off scripts accumulate in DAG files until nobody dares to change them. Keep the orchestration layer thin, with code in tested libraries.
Time-based scheduling gives silent failures. A run starts, the input is late, and everything is green. The cure is data-aware dependencies and data-quality checks, but they need effort and discipline.
Scale limits appear. A scheduler must evaluate thousands of tasks continuously. Parsing thousands of DAG files, queries to the metadata database, and many tiny tasks (each with start-up cost of seconds) can slow it. Teams split deployments, use fewer and larger tasks, or move to managed services.
Backfills and reruns are risky when tasks are not idempotent or depend on "now". Code that reads the current time, a "latest" table or a mutable reference table gives different answers on rerun. Parameterise everything by the logical date.
Dependencies across DAGs and teams are hard to see and test. Ownership is unclear when a failure in one team's DAG blocks another's. Alert fatigue follows: 50 alerts for one root cause. Alert on outputs missing deadlines, not on every task.
Local development and testing are weaker than for ordinary code. It is difficult to run the whole graph on a laptop, so teams build test harnesses, small data sets, and separate environments.
Finally, observability across tools is uneven. Lineage and quality results live in the catalog, the engine, the orchestrator and the BI tool, and you usually must join them yourself.
practice: Keep orchestration thin. Use the orchestrator to start and monitor work in Spark, SQL and dbt, and keep the transformation code in its own repository with tests. Write tasks to be idempotent and parameterised by logical date: overwrite a partition, or MERGE on a key, and never append blindly. Avoid reading "now" or "latest" inside a task.
Define dependencies by data. Wait for a partition or a table version, or use asset triggers, and set timeouts so a missing input fails loudly. Add data-quality tasks (row count within a range, freshness, uniqueness of keys) that fail the run before bad data reaches consumers.
Configure retries sensibly: 2 to 3 attempts with exponential backoff and jitter for transient failures, none for tasks that fail from logic errors. Set task timeouts and pool or concurrency limits so one DAG cannot take the whole cluster. Alert on outcomes: "gold table not ready by 06:00" and "run duration above twice its median", not on every task failure.
Keep DAGs small and readable, with clear owners and a runbook link in each. Version DAG code in Git with review and tests that check DAG import and dependency structure. Make backfill a first-class, rehearsed operation with a concurrency limit, and always test it on a small range first.
Plan operations: a highly available scheduler, a managed metadata database with backups, regular upgrades, and a way to see queue time. For long-running business processes, use durable execution and design activities to be idempotent, with timeouts at every call.
quiz: Why does an orchestrator need tasks to be idempotent? || Because retries, reruns and backfills execute a task more than once for the same data interval. If the task replaces its output (overwrite a partition, MERGE), the repeated run gives the same result. If it appends, duplicates appear.
What is the logical date of a run, and why is it used instead of the current time? || It identifies the data interval the run processes, such as 2026-10-25, whatever the actual start time. Using it lets retries and backfills reproduce the same data and avoids dependence on the clock.
Four tasks of 10, 25, 15 and 2 minutes run in a chain. A backfill of 30 days runs 5 at a time. How long does it take? || Each run takes 52 minutes. Thirty runs in groups of 5 make 6 rounds, so 6 × 52 = 312 minutes (5 h 12 min).
Why is "run at 02:00" a weak design for a pipeline whose input arrives at a variable time, and what replaces it? || If the input is late the run processes missing data and may still be green. Use a sensor or an asset/table-version trigger so the run starts when the data exists, with a timeout and a freshness alert.
When would you choose Temporal-style durable execution over an Airflow DAG? || For long-running, event-driven processes that wait for timers or people, have many concurrent instances and branching logic, and must survive crashes mid-way. For fixed-shape batch pipelines on a schedule, a DAG scheduler is the simpler fit.
interview: How does an orchestrator decide a task can run, and what limits can stop it? || The scheduler checks that all upstream tasks in the run have succeeded (or skipped, depending on trigger rule), that the run is active and the task is not already queued. Pools, global and per-DAG concurrency, and executor slots can still hold it back. The task then moves to queued and an executor starts it.
A daily pipeline is green but the dashboard shows yesterday's data. What happened and how do you prevent it? || Likely the run started before upstream data arrived, or a task succeeded with zero rows. Fix with data-aware dependencies (sensors or assets), data-quality checks that fail the run, and a freshness SLA alert on the output.
How do you make a backfill safe? || Make every task idempotent by logical date (overwrite partitions, MERGE), do not read current time or mutable "latest" data, cap concurrency to protect the cluster and sources, run a small range first, and verify counts against the source.
Airflow versus Dagster versus Temporal: how do you choose? || Airflow for broad integrations and scheduled batch DAGs with a large community. Dagster when assets, lineage and checks are central to the team's thinking. Temporal for long-running, stateful business workflows in code with durable execution. They can coexist.
Your scheduler is slow with 5,000 DAGs. What do you look at? || DAG file parsing time and top-level code in DAG files, metadata database load and indexes, number of tiny tasks, scheduler count and settings, and executor start-up latency. Move heavy imports into tasks, shard DAGs across deployments, and use fewer, larger tasks.
How does durable execution survive a crash in the middle of a workflow? || The engine stores each step's result in an event history. After a crash another worker replays the workflow code from the start, feeding it stored results instead of re-running completed activities, until it reaches the unfinished step. This requires deterministic workflow code.

@@ iac
value: Infrastructure as code (IaC) means that the servers, networks, databases, permissions and clusters of a system are described in text files, stored in version control, reviewed like software and applied by a tool, not by a person clicking in a console. The files say what should exist ("a network with three subnets, a Kubernetes cluster with five nodes, a bucket with encryption on"). The tool compares this with what exists and makes the changes needed.
The problem is old and costly. A hand-built environment cannot be reproduced: the second environment differs in small ways, and nobody knows which. A change made at night in the console is not recorded; when something breaks, no one can say what changed. Recovery after a disaster means remembering hundreds of steps. And the cloud made this worse, because a modern system has thousands of resources with many links between them, created through APIs at a speed that makes manual work error-prone.
For the layer above (cloud platforms, Kubernetes clusters, data platforms with workspaces, catalogs and permissions, every environment from test to production), IaC provides repeatability, review and audit: a pull request shows the exact change, a plan shows the exact effect, and history shows who changed what and when. Two lower ideas do the core work. The reconciliation loop (L2) is the pattern "compare desired state with actual state, and act on the difference", which is what plan and apply (and GitOps controllers) do. DAG scheduling (L2) orders the work, because resources depend on each other: a subnet needs its network first, and a database needs its subnet, so the tool builds a graph and creates resources in dependency order (and destroys in reverse order), running independent branches in parallel.
terms: Desired state — what the code says should exist.
Actual state — what really exists in the cloud, read through provider APIs.
State file — the tool's record of which real resources it manages and their last known attributes; Terraform keeps it in a file or a remote backend.
Plan — a preview of the changes the tool will make (create, update in place, replace, destroy), computed before anything changes.
Apply — executing the plan by calling provider APIs in dependency order.
Drift — a difference between code and reality caused by changes made outside the tool.
Provider — a plug-in that knows how to create and read one kind of resource, such as AWS, Kubernetes or Databricks.
Module — a reusable package of resources with inputs and outputs, such as "a standard VPC".
Idempotent apply — applying the same code twice gives the same result and changes nothing the second time.
history: Automation of servers began with configuration management. Mark Burgess's CFEngine (1993) introduced the idea of describing the state a machine should be in and converging to it. Puppet (2005), Chef (2009) and Ansible (2012) made this practical for fleets. They managed what ran on a machine. When the cloud arrived (Amazon EC2 in 2006), the machine itself became an API call, and tools moved up to provisioning whole environments.
AWS CloudFormation (2011) described AWS resources in JSON or YAML templates. HashiCorp, founded by Mitchell Hashimoto and Armon Dadgar, released Terraform in 2014 with three ideas: a language that works across clouds through providers, a dependency graph, and a plan step that shows changes before they happen. Terraform became the common language of infrastructure. Pulumi (2018) and the AWS Cloud Development Kit (generally available in 2019) let teams write infrastructure in general-purpose languages such as TypeScript and Python, which are then turned into the same kind of resource graph.
Containers changed the target. Kubernetes (2014) made desired state a core idea: you declare a Deployment and controllers continually reconcile. "GitOps" (a term from Weaveworks, 2017) took the next step: Git is the source of truth, and a controller in the cluster (Flux, Argo CD) pulls the repository and reconciles continuously, instead of a pipeline pushing changes once. Crossplane (2018) used the Kubernetes reconciliation model to manage cloud resources too.
Licensing then became news. In August 2023 HashiCorp changed Terraform's licence from open source (MPL) to the Business Source License. Within weeks, a group of companies announced a fork, first called OpenTF and then OpenTofu, now hosted by the Linux Foundation; OpenTofu 1.6 was its first stable release in January 2024. In 2025 IBM completed its acquisition of HashiCorp. The two projects now evolve separately but remain largely compatible for common use.
how: The core of a declarative tool is a loop of four steps: read the code, read the world, compute the difference, apply the difference.
Step 1, parse and build the graph. The tool reads the configuration and builds a graph where each resource is a node. An edge exists where one resource refers to another: if the subnet uses the network's ID, the network must be created first. This is DAG scheduling (L2). Independent resources are created in parallel (Terraform's default is 10 at once), and the graph also sets the order of destruction, which is the reverse.
Step 2, load the state and refresh. The state records, for each managed resource, its real ID in the cloud and the attributes seen the last time. The tool calls the provider API to read each resource's current values (refresh). This is how it detects drift, for example when someone added a firewall rule by hand.
Step 3, compute the plan. For each resource, the tool compares desired values with the refreshed values, and classifies the action: no change; update in place (a tag changes); replace, meaning destroy and create (a property that the cloud cannot change in place, such as a database engine name); create (new in code); or destroy (removed from code). This is the reconciliation idea (L2): the difference between the desired and actual state defines the work. The plan is shown to a human, or saved as a file, and a review can approve exactly this plan.
Step 4, apply. The tool walks the graph and calls the provider API for each action, waits until the resource is ready (some, like a Kubernetes cluster or database, take 10 to 30 minutes), records the new attributes in the state, and continues. If something fails halfway, the state still records what was done; the next run plans only the rest. The result of a second apply is no change, which is idempotence.
The state is a critical part. It maps names in code to real objects, and it stores values that cannot be read back (such as generated passwords). Stored locally it is unsafe for a team, so teams use a remote backend (object storage, or a hosted service) with locking so two applies cannot run at the same time. Modern backends can do the locking in the storage itself. The state may contain secrets, so it needs encryption and access control. OpenTofu added client-side state encryption in 2024.
Alternative models exist. Imperative tools (shell scripts, Ansible modules) describe steps, and they can be idempotent only if each step checks first. General-language tools (Pulumi, CDK) allow loops, functions and tests, but the program must still produce a deterministic desired state. Kubernetes-native tools (Crossplane, cloud operators) run the reconcile loop continuously inside a cluster, so drift is corrected within minutes without anyone running a command. GitOps controllers do the same for manifests: they pull from Git every few minutes (or on webhook), diff against the cluster, and apply.
Around the tool is the workflow. A change is a pull request. The pipeline runs formatting and validation, a security scan for dangerous settings (open ports, public buckets), and a plan that is posted to the pull request. After review and merge, the pipeline applies, with credentials held by the pipeline and not by individuals. Modules make standard parts reusable, and policy-as-code tools (Open Policy Agent, Sentinel) can reject plans that break rules, such as "no public storage".
Providers deserve a closer look, because they carry the real work. A provider is a separate program that speaks a small protocol to the core tool: it declares the resource types and their attributes, validates the configuration, reads a resource, and creates, updates or deletes it by calling the cloud's API. Each attribute is marked as changeable in place, forcing replacement, or computed by the cloud (such as an ID). That marking is what lets the core tool decide between update and replace, without knowing anything about any one cloud. The core also handles references: when a resource uses another's computed ID, the value is unknown at plan time and appears as "known after apply". Data sources let code read facts without owning them (the latest machine image, an existing network), and outputs expose values to other modules or other state files. Lifecycle rules refine the default behaviour: create the new resource before destroying the old one, ignore changes made by an autoscaler, or refuse to destroy a database.

example: A team manages a small data environment in code: 1 network, 3 subnets, 1 storage bucket, 1 cluster with 3 nodes, and 1 database. That is 7 resources.
Step 1, first apply. The state is empty, so the plan says 7 to create. The graph shows the order: network first (about 10 seconds), then 3 subnets and the bucket in parallel (about 10 seconds), then the cluster (about 12 minutes) and the database (about 8 minutes) in parallel. The cluster and database wait only for the subnets, not for each other. Total time is about 12 minutes, not the 20 minutes of a sequential run.
Step 2, a safe change. Someone changes the cluster node count from 3 to 5 in the code and opens a pull request. The CI plan shows "1 to update in place: node_count 3 -> 5", and "6 unchanged". The reviewer sees one line and approves. Apply takes about 4 minutes.
Step 3, a dangerous change. Another pull request renames the database resource from "db" to "main_db" in the code, with no other change. The tool sees that "db" no longer exists in code and "main_db" is new, so the plan shows "1 to destroy, 1 to create". If applied, production data would be deleted. The review catches it because the plan is reviewed, not only the code. The right fix is a "moved" block (or state move command) that tells the tool that this is the same object under a new name. Teams also set deletion protection on databases and a "prevent destroy" rule in the code.
Step 4, drift. At night, an engineer opens port 22 to the whole internet on a security group in the console to debug a problem and forgets about it. The next scheduled plan, run daily in CI, shows "1 to update: remove ingress rule 0.0.0.0/0:22". The team receives an alert, and either reverts it by apply or, if the change was correct, adds it to the code. With a GitOps controller the change would be reversed within minutes automatically.
Step 5, blast radius. The team splits the code into three states: network (changes a few times a year), data (monthly) and applications (daily). A mistake in the daily-changing code can then not destroy the network or the database. Plans are also faster: a plan that refreshes 7 resources takes seconds, while one with 2,000 resources can take several minutes because every resource is read through rate-limited APIs.
intuition: A recipe that rebuilds the same kitchen every time, and a checker who compares the real kitchen with the recipe and tells you what is different before you cook.
The idea is natural because infrastructure has the same problems as software: it is complex, it changes, and mistakes are expensive. Software solved these by writing things down in text, reviewing changes, keeping history, testing before release, and automating the build. IaC applies the same discipline. The plan step is the key: because the tool can compute the difference without acting, humans can review the consequences.
mistakes: People often think IaC is just scripting the console. In fact the point is a declared end state and a computed difference. A script that runs "create database" fails or duplicates when run twice. A declarative tool plans from the current state, so the second run does nothing.
People often think the code is always the truth. In fact the real truth is the cloud, and the code is a claim about it. Without drift detection and a rule against manual changes, they diverge, and the next apply may undo a needed fix or fail.
People often think a plan shows everything that will happen. In fact it shows what the tool knows. Values computed during apply, changes in resources outside the state, side effects inside a server (what a script does) and cloud-side limits (quotas, eventual consistency) are not visible. Read plans carefully, especially "replace" and "destroy".
People often think the state file is an implementation detail. In fact it is the tool's memory of what it owns. If it is lost, the tool may try to create resources that exist already; if two people write it at once, it is corrupted. It may also hold secrets. Treat it as production data.
People often think one big configuration is simpler. In fact a single state for everything means every plan touches everything, every mistake can destroy everything, and every team waits for the same lock. Split by lifecycle, team and risk.
tradeoffs: Choose a declarative tool (Terraform or OpenTofu, CloudFormation) when you want previews, drift detection and a clear model of what exists. You give up flexibility for unusual procedures and must learn the tool's limits (for example how it handles replacement). Choose imperative scripts or Ansible for one-time or procedural work, such as configuring software inside servers, where there is no stable "end state" to declare.
Choose Terraform or OpenTofu when you want a large provider ecosystem and a language that is simple to review. Choose OpenTofu if you want an open-source licence under neutral governance or features such as state encryption; choose Terraform if your organisation uses HashiCorp's commercial platform and supports it. For basic use the two are close; check the licence terms and your vendor needs. Choose Pulumi or CDK when your team wants real programming languages, loops and unit tests; you give up the simple, uniform reading of a declarative file, and reviewers must reason about programs.
Choose push-based apply from CI when infrastructure changes are infrequent and you want explicit approval. Choose pull-based GitOps controllers (Argo CD, Flux) when you manage Kubernetes at scale and want continuous reconciliation and automatic drift correction; you give up the simple plan-and-approve step, and a bad commit is applied immediately unless protected by review and progressive rollout.
Choose small state files (by environment, region and lifecycle) for safety and speed; you give up easy cross-references, which need outputs or data lookups between states. Choose a single large state only for small systems.
Choose strict "no console changes" for production, with break-glass access that is logged and followed by a code change. You give up speed in emergencies, but you keep the record trustworthy.
friction: Drift never fully disappears. Auto-scaling, operators, other tools and people change resources, and some attributes always show up as differences. Teams spend effort deciding what the code owns and what it ignores.
Blast radius is real. A wrong apply can delete databases or lock people out of an account. Protection comes from small states, deletion protection, reviewed plans, limited credentials, and backups.
Secrets are awkward. Passwords and keys appear in state files and plan output, so state needs encryption, and code should fetch secrets from a secret manager rather than contain them.
Large estates are slow. Refreshing thousands of resources through rate-limited APIs makes plans take minutes, and a long lock blocks others. Splitting state and targeting help, but add complexity.
The tool is bound by provider coverage and bugs. A new cloud feature may not be supported for months, and some provider behaviour (eventual consistency, replacements) causes surprising plans. Upgrading a provider or the tool itself can change plans, so versions are pinned and upgrades tested.
Refactoring is hard. Renaming or moving resources between modules and states needs explicit moves, or the tool destroys and recreates. Learning curve and review skill matter: people approve plans they do not read.
Finally, testing infrastructure code is slow and costly: a real test creates real resources for minutes and costs money, so teams rely on validation, policy checks, and a small number of integration environments.
practice: Keep all infrastructure in version control and make the pipeline the only way to apply to production. Run plan on every pull request and post it for review. Apply from automation with narrow, short-lived credentials (for example through OIDC federation from CI), not from laptops. Run plan on a schedule to detect drift and alert on it.
Use a remote backend with locking and encryption, restricted access, and versioning for recovery. Split the state by environment and lifecycle: network, data and applications separately; production separately from test. Pin provider and tool versions and upgrade deliberately.
Write modules for standard parts with few inputs and safe defaults, and publish them with versions. Add policy checks to reject unsafe plans (public buckets, open ports, untagged resources). Use deletion protection and "prevent destroy" for stateful resources, and use explicit "moved" blocks when refactoring.
Do not put secrets in code. Read them from a secret manager at apply or run time, and mark outputs as sensitive. Tag every resource with owner and environment so cost and ownership are visible. Import existing resources into code gradually, starting with the most risky ones.
Define a break-glass process: an emergency console change is allowed, logged, and brought back into code within a set time. For Kubernetes, use a GitOps controller to correct drift and apply changes progressively. Practise disaster recovery by recreating a non-production environment from code regularly: if you cannot rebuild it, the code is not complete.

Apply executes them in dependency order. The plan lets people review consequences before they happen.
Why does the tool build a dependency graph? || Resources depend on each other (a subnet needs its network). The graph gives the creation order, the reverse destruction order, and shows which resources can be built in parallel to save time.
What is drift, and how do you handle it? || Drift is a difference between code and real infrastructure caused by manual or external changes. Detect it with scheduled plans (or continuous reconciliation by GitOps controllers), then either revert the change by applying the code or update the code to match.
A rename of a resource in code produces "1 to destroy, 1 to create" for a production database. What happened and what do you do? || The tool sees the old name as removed and the new name as new, so it plans to delete and recreate. Do not apply. Add a moved block (or move the state entry) so the same object is tracked under the new name, and enable deletion protection.
Why split state into several files? || It limits blast radius, speeds up plans (fewer resources to refresh), reduces lock contention between teams, and lets different parts change at different rates and with different approvals.
interview: How does Terraform decide what to change? || It builds a graph from the configuration, loads the state and refreshes it with provider API reads, compares desired and actual attributes for each resource, and labels each as create, update, replace or destroy. Replace happens when an attribute cannot change in place. Apply then walks the graph in order.
What are the risks of the state file, and how do you manage them? || Loss or corruption makes the tool lose track of resources; concurrent writes corrupt it; it can contain secrets. Use a remote backend with locking, versioning and encryption, restrict access, and back it up.
Terraform vs Pulumi vs Crossplane: how do you choose? || Terraform/OpenTofu for the broadest provider support and reviewable declarative files. Pulumi/CDK when programming-language features and tests matter. Crossplane when you want continuous reconciliation and a Kubernetes-API based platform for developers. Mixed use is common.
How do you prevent an IaC change from deleting production data? || Review plans (not just code), set deletion protection and prevent-destroy, separate state for stateful resources, use limited credentials with approval for destroy actions, keep backups, and use policy checks that fail plans containing destroy of protected types.

@@ observability
value: A running system is a black box. You cannot attach a debugger to a service that handles 20,000 requests per second across 300 containers. What you can do is make the system emit a record of what it does, and then ask questions of that record. Observability is the practice of building systems that explain themselves through their outputs, so that when a user says "checkout is slow", an engineer can find "this service, this dependency, since this deploy" in minutes and not in hours.
Three kinds of signal carry most of the information. Metrics are numbers over time (requests per second, error rate, memory in use); they are cheap and good for alerting and trends. Logs are records of individual events (a request failed, a user logged in); they are rich but large. Traces follow one request through many services and show where the time went. Profiles, which show which code uses CPU or memory, are a fourth signal that is becoming standard. Monitoring checks things you know can go wrong. Observability aims at the unknown: new failure modes you did not predict, which you can still investigate because the data is detailed enough to slice in new ways.
For the layer above (Prometheus, OpenTelemetry, Grafana, Elasticsearch and OpenSearch for logs, the on-call practice of every large service), observability is how a team knows whether it keeps its promises to users. The layers below make it affordable at scale. HyperLogLog (L2) counts distinct values, such as active users or active time series, in a few kilobytes. Count-min sketches (L2) find the heaviest items in a stream, such as the noisiest tenant or the most common error, with fixed memory. Encoding and compression (L2) store each metric sample in about one to two bytes. Sampling (L2) keeps the traces that matter and drops the rest, so that cost is bounded.
terms: Metric — a named number measured over time, such as http_requests_total, stored as a time series.
Label (dimension) — a key-value pair attached to a metric, such as service="cart" or status="500".
Cardinality — the number of distinct time series (or distinct values of a field); it is the product of the number of values of each label.
Span — one timed operation inside a trace, with a start time, a duration, attributes and a parent span.
Trace — the tree of spans that describes one request across all services it touched, tied together by a trace ID.
Context propagation — passing the trace ID and parent span ID from one service to the next, usually in an HTTP header such as traceparent.
SLI / SLO — a service level indicator is a measured quality (share of requests faster than 300 ms); a service level objective is the target for it (99.9% over 30 days).
Error budget — the allowed amount of failure implied by an SLO; a 99.9% objective allows 0.1% bad events.
Burn rate — how fast the error budget is being used compared with the rate that would use exactly all of it by the end of the window.
history: Early monitoring was about machines and checks. Nagios (1999) ran scripts and showed green or red. Graphite (2008) and RRDtool stored time series for graphs. These tools worked for tens of servers and fixed checks.
Large distributed systems needed more. Google's Dapper paper (2010) described tracing every request across thousands of services with very low overhead by sampling, assigning trace IDs and propagating them with each call. Twitter's Zipkin (2012) and Uber's Jaeger (open-sourced in 2017) followed. Prometheus began at SoundCloud in 2012 with a new model, metrics with labels queried by a language (PromQL) and collected by pulling; it joined the Cloud Native Computing Foundation in 2016 and became the standard for Kubernetes metrics. Prometheus 3.0 arrived on 14 November 2024, with better support for OpenTelemetry data. Facebook's Gorilla paper (2015) showed how to compress time series to about 1.4 bytes per sample, and the same ideas now sit in most time-series databases.
Google's "Site Reliability Engineering" book (2016) spread the vocabulary of service level objectives, error budgets and alerting on symptoms. Charity Majors and Honeycomb argued from about 2016 that high-cardinality, wide events are the right basic unit, and used the word observability in this sense. OpenTelemetry (OTel) was formed in 2019 by merging OpenTracing and OpenCensus; it defines APIs, SDKs, a wire protocol (OTLP) and a collector for traces, metrics and logs, and is among the busiest CNCF projects. W3C Trace Context became a W3C Recommendation in 2021, giving one standard header for propagation. Today the open questions are cost (telemetry bills can reach the size of the compute bill), continuous profiling, and using machine learning to help with root causes.
how: An observability system has four stages: instrument, collect, store, ask.
Instrument. The code, or a library inside it, creates telemetry. A metric counter is incremented per request. A span is started when a request arrives and ended when the response is sent, with attributes such as route and status code. A log line is written in a structured form (JSON) with fields, not as free text. OpenTelemetry provides one set of APIs for all three, and automatic instrumentation for common frameworks. The key rule for traces is context propagation: when service A calls B, A adds the trace ID and its own span ID as a traceparent header, and B uses them as the parent of its own spans. The application must carry the context from the incoming request to the outgoing calls, or the trace breaks into separate pieces.
Collect. Telemetry goes to an agent or collector, either next to the application or as a gateway service. The collector batches data, adds attributes (cluster, region), removes sensitive fields, and decides what to drop. This is where sampling (L2) is applied. Head sampling decides when the trace starts (for example keep 1%), which is cheap but blind: it cannot know that this trace will turn out to be slow or failed. Tail sampling waits until the trace is complete (typically 10 to 30 seconds), then keeps all traces with errors or high latency plus a small random share of the rest. Tail sampling gives much better data, but needs a collector tier that holds all spans of a trace in memory, which means routing by trace ID.
Store. Each signal has its own storage because the access patterns differ. Metrics go into a time-series database (Prometheus, Mimir, VictoriaMetrics, Thanos). Each series is a stream of (timestamp, value) pairs. Delta-of-delta encoding makes timestamps cost about one bit when samples arrive at regular intervals, and XOR encoding of consecutive floating-point values makes slowly changing values cost a few bits. This is encoding and compression (L2) at work, and it brings 16 bytes per raw sample down to 1 to 2 bytes. Logs go into a search engine (Elasticsearch, OpenSearch) or into cheaper columnar or object storage (ClickHouse, Loki), which index fewer fields. Traces go into stores keyed by trace ID (Tempo, Jaeger) or into a columnar store that can be queried by attribute.
Cardinality is the central cost of metrics. The number of time series is the product of the label values. A request metric with 50 services, 40 routes and 8 status codes already has 16,000 series; add a pod label with 200 values and you have 3.2 million series. Add a user ID label and the series count explodes, and the database may run out of memory. A good system counts and limits cardinality, and approximate counting (HyperLogLog, L2) lets it estimate distinct label values with a few kilobytes per metric, to warn before the damage. Count-min sketches (L2) find the heavy hitters, for example which tenant is creating most series, or which log pattern is most frequent, in a single pass with fixed memory.
Ask. Engineers query with a language (PromQL for metrics, a log query language, a trace search by attributes) and see results as dashboards. Alerts evaluate queries every minute or so. Good practice is to alert on symptoms that users feel, derived from SLOs, and to use the other signals to find the cause. A typical investigation starts at an alert on error budget burn, uses a dashboard to find the failing service, jumps from a metric point to an example trace (an "exemplar" links a metric sample to a trace ID), reads the slow span, and then finds the log lines for that trace ID to see the actual error.
Wide events are another approach. Instead of three separate pipelines, each request produces one rich event with dozens of fields (user, build, route, region, feature flags, durations). Because storage is columnar and indexes are not fixed, you can group by any field after the fact, such as "p99 latency by build ID for users in this region". This is how new questions are answered without having planned for them.
Two details make the pipeline workable in practice. First, metric types: a counter only goes up (requests served), and you ask for its rate over a window; a gauge goes up and down (memory in use); a histogram counts observations into buckets (requests faster than 10, 50, 100, 500 ms), which lets you compute percentiles after the fact and merge them across instances. Second, resource attributes: every signal is labelled with where it came from (service name, version, region, pod), so that a spike can be tied to one release or one zone. Consistent names across the three signals are what let a dashboard jump from a metric to the matching trace and logs.

example: A shop promises 99.9% of checkout requests succeed within 30 days. It handles 1,000 requests per second.
Step 1, the error budget. In 30 days there are 1,000 × 86,400 × 30 = 2.592 billion requests. A 99.9% objective allows 0.1% bad requests: 2.592 million. In time, 0.1% of 30 days is 43.2 minutes of total outage.
Step 2, burn-rate alerts. Alerting on every error is noisy. Instead the team computes the burn rate: the observed error rate divided by the allowed rate (0.1%). If the error rate is 1.44%, the burn rate is 14.4. At that speed the whole 30-day budget would be used in 30 / 14.4 ≈ 2.08 days, and 2% of the budget is spent in one hour. A common rule (from the Google SRE workbook) pages when the burn rate is above 14.4 over 1 hour and also over the last 5 minutes (so that the alert stops soon after recovery). A slower burn, such as 6 times over 6 hours, can still page, while a burn of 1 time over 3 days creates a ticket instead.
Step 3, finding the cause. At 14:05 the page fires: errors at 2%. The on-call opens the dashboard: the errors come from the "cart" service only, started at 14:00. A deploy marker on the graph shows that cart version 412 started rolling out at 14:00. The metric is split by version label (a low-cardinality label), and only version 412 pods fail. The engineer opens an exemplar trace for a failed request: the span "cart → pricing" takes 5 s and times out. The logs with that trace ID show "connection pool exhausted". Rollback takes 3 minutes. The total time from page to fix is about 15 minutes. Without trace IDs in logs and a version label, this would be a long search.
Step 4, the cardinality mistake. A developer adds user_id as a label to the request counter. Before: 50 services × 40 routes × 8 codes × 200 pods = 3.2 million series (about 10 GB of memory at a few KB per active series). After: 2 million users make that up to billions of possible series, and the database is killed by memory exhaustion. The right place for user_id is a log line or a trace attribute, not a metric label.
Step 5, the cost of traces. 10,000 requests per second, each trace has 20 spans of about 500 bytes: 10 KB per trace, so 100 MB/s, which is about 8.6 TB per day. Head sampling at 1% brings that to 86 GB per day, but loses 99% of the rare failures. With tail sampling the team keeps all traces with errors (0.5%) and all traces slower than 1 s (1%) plus 1% of the rest: about 2.5% in total, 215 GB per day, and every failure is available.
intuition: Instruments on an aircraft dashboard for the pilot, plus a flight recorder for the investigators afterwards.
The idea is natural because a system that you cannot open must be understood through what it says. The three signals answer different questions at different costs: metrics say that something is wrong, traces say where, and logs say why. The trick is to link them with shared identifiers so that one question leads to the next. The mathematics of sketches and compression is what keeps a huge stream affordable.
mistakes: People often think observability means having the three pillars. In fact it is the ability to answer new questions. Three separate tools with no shared IDs give monitoring in three places, not observability. The links (trace IDs in logs, exemplars on metrics, consistent labels) are what make a difference.
People often think more data is better. In fact data has a cost and noise has a cost. Unbounded labels, debug logs in production and 100% trace capture create bills and slow queries. Decide what each signal is for, sample, aggregate and set retention by value.
People often think averages describe latency. In fact the average hides the tail. A service with 99% of requests at 50 ms and 1% at 5 s has an average of about 100 ms, and a p99 of 5 s that users with many requests will meet constantly. Use histograms and percentiles; do not average percentiles across instances, but merge histograms.
People often think alerts should fire on every symptom or cause. In fact alerts on causes (CPU is 80%) are noisy and often irrelevant. Alert on user-visible symptoms and SLO burn, and use dashboards for causes.
People often think logs alone are enough. In fact logs have poor structure for aggregation, are expensive at scale, and cannot show how a request moved across services unless a trace ID is added. They are best for the details that explain a specific event.
tradeoffs: Choose metrics for alerting, trends and capacity, where cost per signal is low and the answer is a number. Choose traces to find where time is spent across services. Choose logs for the exact details of an event, audit trails and debugging. Using all three costs more than one, and the cost is mostly in storage and in query time, so decide on retention for each (metrics for 13 months in aggregated form, traces for 7 to 14 days, logs for 14 to 30 days online and longer in cold storage).
Choose head sampling when you want the cheapest, simplest pipeline and traffic is high and uniform. Choose tail sampling when finding rare errors and slow requests matters most; you pay with collector memory, routing by trace ID and added delay.
Choose a pull-based metrics system (Prometheus) when you want simple discovery, health from the scrape itself, and control from the collector side. Choose push (OTLP, StatsD) for short-lived jobs, serverless functions and environments where the collector cannot reach the targets.
Choose self-hosted open-source tooling (Prometheus, Grafana, Loki, Tempo, ClickHouse) when volume is large and you have staff to run it; you give up convenience and carry on-call. Choose a vendor when the team is small or the need for speed is high; you give up price control, and bills can grow quickly with volume and cardinality, so negotiate and set budgets. OpenTelemetry for instrumentation reduces the cost of switching.
Choose pre-aggregated metrics when the questions are known and cardinality must be controlled; choose wide events or a columnar store when you need to slice by any field after the fact, accepting higher storage cost and more careful data governance.
friction: Cost grows with every dimension: number of services, label values, log lines, retention and query load. Telemetry spending can grow to a large share of the infrastructure bill, and it is hard to cut because everyone depends on it. Cardinality control, sampling, log levels and retention policies are the main tools.
Sampling loses information. Rare events may be dropped, statistics must be corrected by the sampling rate, and a trace that is dropped cannot be recovered. Tail sampling reduces this problem and adds infrastructure.
Alert fatigue is a human cost. Too many alerts mean engineers ignore them. Alerts need owners, runbooks and regular review; the page count per on-call shift is a metric worth tracking.
Correlation across signals and tools is still weak. Different tools use different names, labels and time stamps, and context propagation breaks at queues, batch jobs and third-party systems. Asynchronous flows (a message in a queue, processed later) need links between traces, not parent-child spans.
Instrumentation takes work and drifts. Auto-instrumentation covers frameworks, but business-level spans and attributes need developers, and naming conventions must be kept consistent.
Privacy and security matter: logs and traces easily capture personal data and secrets. Redaction must be done in the collector, and access to telemetry must be controlled.
Finally, data pipelines are hard to observe. A job can succeed while the data it produced is late, partial or wrong, so observability for data needs its own signals: freshness, volume, schema and distribution checks.
practice: Start from user-facing objectives. Define SLIs for the journeys that matter (availability, latency, freshness) and SLOs with an error budget. Alert on burn rate with two windows (a long one for sensitivity and a short one for quick reset), and send slow burns to tickets, not pages.
Instrument with OpenTelemetry. Use standard names and attributes (service name, version, environment). Propagate trace context through every call, including queues and background jobs, and add the trace ID to every log line. Add deploy markers and a version label so that changes are visible on graphs.
Control cost and cardinality at the source. Keep labels to bounded sets (route template and not raw URL; status class; region), never IDs. Put high-cardinality data in traces and logs. Set limits on series per metric and on log volume per service, with an alert before the limit. Use tail sampling to keep errors and slow traces. Set retention by value and move old data to cheap storage.
Use histograms for latency (with buckets matching your SLO thresholds, or native exponential histograms) and compute percentiles from merged histograms. Write runbooks for each page and review alerts monthly: delete those that nobody acts on.
For data platforms, observe the data itself: freshness (is the table updated by its deadline), volume (row count within the usual range), schema changes, and null or duplicate rates, in addition to job success. Test the observability setup during game days: break something and see how quickly you find it.
quiz: What question does each of the three signals answer best? || Metrics show that something is wrong and how big it is, traces show where in the request path the time or error is, and logs show the detailed reason for a specific event.
Why is high cardinality dangerous for metrics, and how do you avoid it? || Each distinct combination of label values is a separate time series that costs memory and index space. A label like user_id creates millions of series. Keep labels bounded and put IDs in logs or trace attributes.
For a 99.9% SLO over 30 days, how much error budget is there in minutes, and what is a burn rate of 14.4? || 0.1% of 30 days is 43.2 minutes. A burn rate of 14.4 means errors at 14.4 times the allowed rate (1.44% of requests), which would use the whole budget in about 2 days and 2% of it in one hour.
Why is tail sampling better than head sampling for finding failures, and what does it cost? || The decision is made after the whole trace is known, so errors and slow traces are always kept. It costs collector memory and routing all spans of a trace to the same collector, and adds delay.
A service sees 5,000 requests per second, 20 spans per trace, 500 bytes per span. How much trace data per day is created without sampling? || 5,000 × 20 × 500 B = 50 MB/s, which is 50 × 86,400 = 4.32 TB per day.
interview: What is the difference between monitoring and observability? || Monitoring checks known failure modes with predefined dashboards and alerts. Observability means the telemetry is rich and linked enough (high-cardinality fields, trace IDs, wide events) to investigate unknown problems by asking new questions without shipping new code.
How do you design alerting for a service? || Define SLOs for user-facing symptoms and alert on multi-window burn rate, with pages for fast burns and tickets for slow ones. Keep cause-based alerts (CPU, disk) as non-paging dashboards, except for hard limits that will cause outage soon. Each alert has an owner and runbook.
Your Prometheus runs out of memory after a release. What do you check? || The number of active series (growth by metric and label), a new high-cardinality label (user ID, request path, pod name churn), scrape targets that multiplied, and histogram bucket counts. Find the top metrics by series count, drop or relabel the label, and add limits.
How would you trace a request through a message queue? || Put the trace context in message headers when producing, and start the consumer span with a link to the producer span (or as a child if the processing is part of the same operation). Batch consumers use span links because one batch relates to many traces.
How do you control observability cost without losing important data? || Limit cardinality, use tail sampling to keep errors and slow traces, drop debug logs by default, aggregate metrics at the collector, set retention tiers, and measure cost per service so owners see it. Keep full detail for critical paths.
What does a trace ID in the logs give you? || It lets you pull exactly the log lines for one request across all services, and jump between logs and the trace view. Without it, correlation relies on time and guesswork.

@@ security
value: Security architecture is the design of a system so that an attacker who gets a small foothold cannot easily turn it into a large breach. It answers four questions for every request and every piece of data: who is asking (identity), what are they allowed to do (authorization), can anyone read or change it on the way or at rest (confidentiality and integrity), and will we notice if something goes wrong (detection and response).
The older model was the castle: a strong wall (firewall, VPN) around a trusted inside. Once an attacker was inside, with one stolen laptop or one phishing success, everything was open. Modern systems are spread over clouds, partners, remote staff and thousands of services, so there is no single inside. The current answer is called zero trust: no request is trusted because of where it comes from. Every request is authenticated, authorized and encrypted, access is the smallest needed (least privilege), credentials are short-lived, and every step is logged.
For the layer above (cloud platforms, Kubernetes, service meshes, secret stores, edge networks that absorb attacks), security architecture sets the rules these products enforce. The layers below give it its tools, and it is worth naming what each one contributes. TLS (L3) encrypts and authenticates connections. Public-key cryptography (L3) lets two parties who have never met agree on a key and prove identity. Digital signatures and PKI (L3) bind names to keys through certificates and make tokens and software artifacts verifiable. Cryptographic hash functions (L3) protect passwords and detect any change in data. OAuth and OIDC tokens (L2) carry identity and permissions on each request. Mutual TLS (L2) lets services prove who they are to each other. Exploit mitigations (L3) make memory bugs harder to turn into attacks. Web security rules (L3) protect the most attacked surface. And the immune system (L5) is the biological model for detecting what does not belong.
terms: Authentication (authN) — proving who you are, by password, key, certificate, token or biometrics.
Authorization (authZ) — deciding what an authenticated identity may do.
Least privilege — giving each identity only the permissions it needs, for the time it needs them.
Zero trust — a design in which no network location is trusted and every request is verified.
Workload identity — a verifiable identity for software (a service, a job, a pod) rather than for a person, often a certificate or a signed token.
Envelope encryption — encrypting data with a data key, then encrypting that data key with a master key held in a key management service (KMS).
Defence in depth — several independent layers of protection, so one failure does not give access.
Threat model — a written list of what you protect, who might attack, and how.
SBOM (software bill of materials) — a list of the components inside a piece of software, used to find vulnerable ones.
Blast radius — the amount of damage possible if one component or credential is compromised.
history: Security began with trust in the machine room. Early multi-user systems (Multics, 1960s–70s) introduced access control and rings of privilege. The Morris worm (1988) showed that the networked internet could be attacked at scale, and firewalls appeared at the network edge in the late 1980s and early 1990s. The VPN extended the castle to remote staff. SSL, later TLS, brought encryption to web traffic from 1995, and public-key infrastructure gave websites certificates.
The castle model failed repeatedly. Attackers who entered through one weak point moved sideways freely. In 2009–2010 Google was attacked in what became known as Operation Aurora, and in response it built BeyondCorp, described by Ward and Beyer in 2014: access depends on the user and the device state, not on the network, and all employees work as if on the open internet. John Kindervag at Forrester had used the term "zero trust" in 2010. The US standards body NIST published SP 800-207, "Zero Trust Architecture", in August 2020.
Cloud computing made identity the new perimeter. A role with too many permissions became the main target: in the 2019 Capital One breach, an attacker used a server-side request forgery flaw in a web application firewall to obtain temporary credentials of an over-permitted role from the cloud metadata service, and used them to download data of about 100 million people. Cloud providers answered with stronger defaults, for instance IMDSv2 on AWS (2019) and short-lived credentials by federation. Workload identity standards such as SPIFFE (2017) gave services certificates without passwords.
Supply-chain attacks then moved the focus to what we build and run: SolarWinds (December 2020) planted malicious code in a signed software update, Log4Shell (December 2021) showed how one library could expose thousands of products, and the xz backdoor (March 2024) came very close to entering Linux distributions through a trusted maintainer. Industry answers include SBOMs, build provenance (the SLSA framework) and keyless signing (Sigstore, 2021). Since 2022, US government agencies (NSA, CISA) have urged a move to memory-safe languages. Most recently, AI agents opened a new surface: prompt injection, where text in a document or web page tells the model to act against its owner.
how: A secure architecture is built from layers that each assume the others can fail. The mechanism has six parts.
Identity. Every person and every workload has a verifiable identity. People sign in through single sign-on (OIDC or SAML) with multi-factor authentication, preferably phishing-resistant (security keys, passkeys, based on public-key cryptography, L3). A private key stays on the device and the server stores only the public key, so there is no password to steal from the server. Workloads get identities from the platform: cloud IAM roles, Kubernetes service accounts, or SPIFFE IDs in X.509 certificates, issued for hours, not years. Certificates are verified through a chain of digital signatures up to a trusted root (signatures and PKI, L3).
Authenticated, encrypted channels. TLS (L3) protects every connection. A handshake uses public-key cryptography to agree on a shared secret (an ephemeral Diffie–Hellman exchange, which gives forward secrecy: a later key theft cannot decrypt old traffic), and then uses fast symmetric encryption (AES-GCM or ChaCha20) for the data. The server proves its identity with a certificate. Between services, mutual TLS (L2) makes the client also present a certificate, so each side knows exactly who the other is. A service mesh or the platform can automate certificate issue and rotation.
Tokens and authorization. After sign-in, requests carry tokens (OAuth 2.0 access tokens, often JWTs, L2) that state who the caller is, for which audience (which service may accept it), what scopes it has, and when it expires, signed by the identity provider. A service verifies the signature and expiry without a network call. Then a policy decides: RBAC (roles), ABAC (attributes such as department, device state, time) or a policy engine (OPA, Cedar). Rules to follow: deny by default, check on every request, and check at the resource, not only at the edge.
Data protection. Data at rest is encrypted with envelope encryption: each object or volume uses its own data key (AES-256), and the data key is encrypted by a master key that never leaves the key management service (KMS) or a hardware security module. Access to the master key is itself logged and governed by policy, so a stolen disk or backup is useless. Cryptographic hashes (L3) serve two purposes. For passwords the store keeps only a salted, deliberately slow, memory-hard hash (Argon2id or bcrypt), so that stolen hashes are expensive to crack; for integrity, SHA-256 digests of files, container images and commits make any change detectable, and signed hashes prove who produced them.
Hardening the code and the build. Memory-safety bugs are a major source of serious vulnerabilities (Microsoft and the Chromium project have each reported that around 70% of their severe bugs were memory-safety issues). Exploit mitigations (L3) such as ASLR (random addresses), DEP/NX (data is not executable), stack canaries (detect overwritten return addresses) and control-flow integrity make a bug harder to exploit, and memory-safe languages remove the bug class. Web applications add their own rules (L3): same-origin policy, output encoding against cross-site scripting, CSRF tokens or SameSite cookies, and content security policy. The software supply chain is protected by pinned and scanned dependencies, SBOMs, reproducible builds, and signed artifacts verified at deploy time.
Detection and response. Logs from identity, network, cloud control plane and applications flow into a central store with strict write-once access. Detection looks for what does not belong. This is where the immune system (L5) is the model: natural immune systems learn "self" and react to "non-self", and early host-intrusion research (Forrest and colleagues in the 1990s) copied that idea by learning normal system-call patterns and flagging deviations. Today this means baselines of normal behaviour per user and service, with alerts on a login from a new country, a service calling an API it never called, or a sudden large download. A rehearsed incident response plan (contain, investigate, recover, learn) turns detection into action.
Around all of this is a method: a threat model written at design time (for example with STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege), and attention to blast radius, so that compromise of one key, account or service cannot reach everything.
Two cross-cutting rules shape all six parts. The first is to verify at the resource, not only at the edge: a service that checks the token and the policy itself keeps working correctly when an upstream layer is misconfigured or bypassed. The second is to separate the planes: the control plane that issues identities, keys and policies is small, heavily protected and audited, while the data plane that carries requests only caches what it needs and keeps working for a short time if the control plane is down. When these rules are followed, a failure of any one component changes how much an attacker gains but does not decide the outcome alone.

example: A company runs an internal reporting service that reads customer records. Walk through the design and what each control stops.
Step 1, sign-in. An analyst signs in with single sign-on and a passkey. The access proxy checks that the laptop is managed and its disk is encrypted. A phishing e-mail that steals her password gets the attacker nothing, because the passkey is bound to the real site's domain and the device.
Step 2, token. The identity provider issues a token that expires in 15 minutes, for audience "reporting", with scope "reports:read". If the token leaks, an attacker has at most 15 minutes and only this service. If the company had used a static API key with no expiry, a copy found in a public code repository could be used for years; automated scanners find leaked keys in minutes.
Step 3, service to service. The reporting service must call the customer database service. Both run in the cluster with SPIFFE identities issued by the platform and valid for 1 hour (rotated at about half life). The database service has a policy: only "reporting" and "billing" may call GET /customers, and only "billing" may write. A compromised "email-sender" pod tries the same call, presents its own certificate, and is denied, and the denial is logged.
Step 4, data. Customer records are stored encrypted with a data key per table. The data keys are wrapped by a master key in KMS. A stolen backup tape is just random bytes. Passwords of customers (if stored at all) use Argon2id with about 19 MiB of memory per hash, so a GPU attacker who steals the table cannot test billions of guesses per second, as would be possible with plain SHA-256; the memory cost cuts the guess rate by orders of magnitude.
Step 5, a mistake and blast radius. A developer's laptop is compromised and the attacker steals the developer's cloud credentials. Because credentials are short-lived (1 hour) and the role is limited to the test account, the attacker cannot reach production, and the unusual API calls (listing all buckets from a new country) raise an alert in 4 minutes. Compare the 2019 Capital One case: one over-permissive role was enough to read a large data set.
Step 6, supply chain. A new version of an open-source library appears with a hidden backdoor. The build pipeline pins versions by hash, scans against known vulnerabilities, requires signed artifacts from the build system and checks the SBOM. It does not stop every attack, but it makes silent changes visible and allows the company to answer "where do we use this library?" in minutes after the next advisory.
intuition: Check ID at every door inside the building, give each person a key that opens only the doors they need and stops working tonight, and keep a camera log of every door.
The design is natural because failure is certain. Some password will be phished, some library will have a bug, some employee will make a mistake. A system that depends on none of these ever happening has no chance. A system that assumes each will happen, and limits what each can do, degrades gracefully. Cryptography supplies cheap, strong checks so that "verify on every request" is affordable, and the immune-system view adds the last layer: watch for the unexpected.
mistakes: People often think a firewall or VPN makes the inside safe. In fact attackers who are inside (through phishing, a stolen laptop, a compromised partner or a vulnerable service) face no barrier in a flat network. Authenticate and authorize every request, even from the internal network.
People often think encryption equals security. In fact encryption protects confidentiality in transit or at rest against specific attackers. It does not decide who may ask, and it does not help if the application decrypts data for anyone who asks. Key management and access policy matter as much as the cipher.
People often think most breaches come from clever attacks on cryptography. In fact most come from stolen credentials, misconfiguration (a public bucket, an over-permissive role), unpatched software and phishing. Cryptography is rarely broken; it is usually bypassed.
People often think compliance is the same as security. In fact standards and audits set a floor and test a snapshot. A company can pass an audit and still have long-lived keys and a flat network. Treat compliance as a by-product of good controls.
People often think security slows teams down, so it must be added at the end. In fact controls added later are expensive and incomplete, while defaults built into the platform (short-lived credentials, deny by default, automated certificates) cost developers little, because they do not have to do anything.
People often think a tool that detects attacks removes the need for prevention. In fact detection is slow compared with an automated attacker. It limits damage after the fact; prevention and small blast radius reduce the damage that can occur at all.
tradeoffs: Choose zero trust with identity-aware access when you have remote staff, many services and cloud resources; you give up the simplicity of "inside is trusted", and you must run identity, device management and policy systems well, since they become critical. Keep a perimeter as one more layer, not as the only one.
Choose short-lived credentials (minutes to hours) over long-lived keys wherever the platform supports it; you pay with more moving parts (token issuers, rotation, clock sync, retry on expiry) and with an outage risk if the issuer fails. Choose longer lifetimes only where short ones are impractical, and add monitoring.
Choose mutual TLS with automatic identities for service-to-service calls in large estates; you accept certificate operations and a small CPU and latency cost. Choose application-level tokens in addition when you need to carry the end user's identity through several services, since mTLS identifies the service, not the person.
Choose coarse roles (RBAC) when permission sets are stable and teams are small; they are simple to audit. Choose attribute- or policy-based control when rules depend on context (data classification, region, device), and accept harder reasoning and testing. Either way, review permissions regularly and remove unused ones.
Choose managed keys in a cloud KMS for most data (simple, audited, cheap). Choose customer-managed or external keys (and hardware security modules) when regulation or risk requires control over the key lifecycle; you take on availability and recovery duties: lose the key and you lose the data.
Choose strong controls on high-value assets and lighter ones elsewhere. A uniform maximum level for everything creates friction that pushes people to bypass the controls; a threat model tells you where the effort pays.
Choose to buy a security service (DDoS absorption, managed detection) when you lack scale or staff; you give up some visibility and depend on a vendor. Build detection yourself only where your data and context make you better than a general product.
friction: Security adds friction for developers and users: extra sign-in steps, denied requests whose cause is unclear, certificate and token expiry, and approval workflows. Poor design pushes people to workarounds such as shared accounts. The goal is controls that are invisible when everything is normal.
Misconfiguration is the main cause of cloud incidents. The number of settings is huge (IAM policies, storage rules, network paths), and one wrong line can expose data. Policy as code, scanning, and secure-by-default templates help, but they need maintenance.
Legacy systems resist modern identity: they use shared passwords, plain-text protocols and service accounts with broad rights. Wrapping them with proxies helps but leaves gaps.
Complexity is itself a risk. Each new security component (a mesh, a vault, a policy engine) must itself be secured, upgraded and monitored, and failures in it can cause outages. A broken certificate authority can stop all traffic.
Supply-chain risk is hard to remove. Modern software has hundreds of dependencies, and a trusted maintainer or a build system can be compromised; SBOMs and signatures show what is inside and who built it, but not whether it is safe.
People remain the weak point. Phishing, social engineering and insiders cannot be fixed by code alone, though phishing-resistant authentication removes the most common route.
Measurement is difficult. You rarely know how secure you are; you know the incidents you found. Red-team exercises, bug bounties and incident drills are the main sources of evidence.
AI agents add new problems. A model that reads untrusted text and can call tools may be tricked into leaking data or taking actions. The risk is highest when an agent combines three things: access to private data, exposure to untrusted content, and the ability to send data out. Remove one of them, or require human approval for risky actions.
practice: Start with identity and least privilege. Use single sign-on and phishing-resistant MFA for people. Give every workload its own identity with a narrowly scoped role, and issue credentials that expire in minutes or hours. Remove static keys from code, images and CI settings; scan for them and rotate any that you find.
Encrypt everything in transit (TLS 1.2 minimum, TLS 1.3 preferred; mTLS between services) and at rest with managed keys, using separate keys for separate data sets where it matters. Keep secrets in a secret manager with access policy and audit logs, and prefer dynamic secrets that are created on demand and expire.
Default to deny. Write authorization as policy that can be reviewed and tested, enforce it at the resource, and review access on a schedule. Segment networks and cloud accounts so one compromise cannot reach everything, and put production in separate accounts with separate credentials.
Patch quickly and know your dependencies: keep an inventory with SBOMs, scan images and libraries, pin and verify versions, sign build outputs and verify them at deploy. Prefer memory-safe languages for new network-facing code, and keep exploit mitigations on.
Log security events centrally (sign-ins, permission changes, API calls to the control plane, data access) with protected storage and retention. Write detection rules for the few things that matter most and rehearse the response: who is on call, how to cut off an account, how to rotate every secret.
Write a threat model for each new system, short and honest. For agent systems, treat all model inputs from tools, documents and web pages as untrusted. Give agents narrow, revocable credentials, log every tool call, and put a human approval step in front of actions that move data out or change production.
quiz: What does "zero trust" mean in practice? || No request is trusted because of its network location. Every request is authenticated and authorized, communication is encrypted, access is least-privilege with short-lived credentials, and everything is logged.
How does envelope encryption work, and why use it? || Each object or volume is encrypted with its own data key; the data key is encrypted by a master key held in a KMS or HSM. Only a small key is sent to the KMS, access to the master key is controlled and logged, and rotating the master key is cheap.
Why is a salted, slow, memory-hard hash used for passwords but SHA-256 alone is a poor choice? || SHA-256 is designed to be fast, so an attacker can test billions of guesses per second on GPUs. Argon2id or bcrypt add a salt (so identical passwords differ) and a large work or memory cost per guess, which makes cracking stolen hashes expensive.
A leaked credential is valid for 1 hour instead of 1 year. How much does the attacker's window shrink, and what does it cost you? || The window shrinks by a factor of about 8,760 (24 × 365). The cost is the machinery for automatic issue and rotation, and the need for services to handle expiry and refresh without failing.
Why add mutual TLS if the network is already segmented? || Segmentation only limits where traffic may flow; it does not say who is calling. mTLS gives cryptographic service identity and encryption, so a compromised host in the allowed segment still cannot pretend to be another service, and policy can be written by identity.
interview: What are the main differences between the perimeter model and zero trust, and what are the risks of zero trust? || Perimeter: trust inside the network. Zero trust: verify user, device and request every time, and enforce least privilege. Risks: identity systems and policy engines become critical single points, mistakes in policy can lock out everyone, and the complexity and operational cost are higher.
How would you secure service-to-service communication in Kubernetes? || Workload identities (service accounts or SPIFFE), mTLS between pods (mesh or CNI), authorization policies by identity, network policies as a second layer, short-lived certificates with automated rotation, secrets from a vault, and audit logs. Also limit what each service account can do against the Kubernetes API.
A cloud access key was found in a public repository. What do you do? || Revoke or rotate the key at once, then review the cloud audit log for its use during the exposure, check what it could access, remove and rotate anything it touched, find how it got committed and add secret scanning and pre-commit checks, and move to short-lived federated credentials.
How do you design permissions so that a compromised service has a small blast radius? || One identity per service, scoped to exactly the resources and actions it needs, separate accounts or projects per environment, no wildcard permissions, short-lived credentials, network policy by identity, and alerts on unusual use. Test with "what can this role do?" analysis tools.
Explain how a signed token lets a service authorize a request without calling the identity provider. || The identity provider signs the token (claims: subject, audience, scopes, expiry) with a private key. The service verifies the signature with the provider's public key, which it caches, then checks expiry, audience and scopes. The trade-off is that revocation before expiry needs extra mechanisms, so lifetimes are short.
How would you protect an AI agent that can read internal documents and send e-mail? || Treat document and web content as untrusted input, separate the agent's permissions from the user's by task, remove the combination of private data access, untrusted content and outbound communication, require human approval for sending data out, log all tool calls, and test with injection attempts.

@@ microservices
value: A microservice architecture builds one application as a set of small services. Each service owns one business capability (orders, payments, search, recommendations), runs as its own process or container, keeps its own data, and is built, tested, deployed and scaled by its own team without asking the others. Services talk to each other only through the network, with HTTP, gRPC or messages.
The problem it addresses is not technical at first, it is organisational. In a large monolith (one codebase, one deployable, one database) a hundred engineers must coordinate every release. A change to the checkout page waits for a release train that also carries the search team's half-finished work. One memory leak in one module takes down everything. The whole system has to be scaled together even if only one part is busy. Splitting along business lines lets each team move at its own speed, scale only the hot parts, and contain failures.
For the layer above (frameworks such as gRPC and FastAPI, platforms such as Kubernetes, gateways and meshes), microservices set the shape of the work: many small programs, each exposing an API. But the split has a price: every function call that used to take nanoseconds inside a process becomes a network call that takes milliseconds and can fail. The layers below are what make this survivable. Remote procedure calls (L3) define how services call each other and encode data. Timeouts and circuit breakers (L2) stop a slow dependency from tying up every thread. Retries with backoff and jitter (L2) hide short failures. Idempotence (L2) makes a retried call safe. Rate limiting (L2) protects a service from overload and shares capacity fairly. Failure detection and heartbeats (L2) find unhealthy instances. The outbox and saga patterns (L2) keep data consistent when there is no shared transaction. Software engineering principles (L3) provide the rules for good boundaries.
terms: Service boundary — the line around one service's responsibility and data; everything across it goes through a public API.
Bounded context — a term from domain-driven design for a part of the business with its own model and vocabulary; a good unit for a service.
Database per service — each service has its own private data store, and no other service reads it directly.
Saga — a long business transaction made of local transactions in several services, with compensating actions to undo steps if a later step fails.
Transactional outbox — writing an event into a table in the same database transaction as the data change, so a separate process can publish it reliably.
Idempotency key — a unique ID sent with a request so that the server can detect a repeated request and return the first result instead of acting twice.
Distributed monolith — a system split into services that still must be changed and deployed together; it has the costs of both designs.
Conway's law — the observation (1968) that a system's structure tends to copy the communication structure of the organisation that builds it.
Contract test — a test that checks that a service meets the exact expectations of its callers, without running the whole system.
history: The idea of splitting software into parts with clear interfaces is old (David Parnas wrote about information hiding in 1972). In the 1990s CORBA and in the 2000s service-oriented architecture (SOA) split enterprise systems into services connected by heavy middleware: enterprise service buses, SOAP and XML, central governance. They often delivered slow projects and tangled integration.
Web companies took a lighter path. Amazon reorganised into small teams around services in the early 2000s, with the often-quoted "API mandate" (all teams expose data and functions through service interfaces, and talk only through them), and the rule that a team should be small enough to be fed by two pizzas. Netflix, after a database corruption in 2008, moved to the cloud from 2009 and finished in 2016, and published much of its tooling: Eureka (service discovery), Hystrix (circuit breaker), Ribbon (client-side load balancing), Zuul (gateway). Etsy, SoundCloud, Uber and others followed. In March 2014 James Lewis and Martin Fowler published an article that named and described "microservices": small services, built around business capabilities, independently deployable, decentralised data, "smart endpoints and dumb pipes".
Docker (2013) and Kubernetes (2014) made running hundreds of small services practical, and service meshes, tracing and API gateways supplied the shared infrastructure. Then the costs showed. Segment published "Goodbye Microservices" in 2018 about merging more than a hundred services back into one. Fowler's "MonolithFirst" (2015) advice, that most successful microservice systems started as monoliths, gained weight. By the 2020s many companies promoted the "modular monolith": one deployable with strong internal module boundaries, which can be split later (Google's Service Weaver, 2023, even lets a program be written as modules and deployed as either). The mainstream view today is that microservices are a tool for large organisations with real scaling or team-independence problems, not a default.
how: A microservice system has four structural parts: boundaries, communication, data and operations. Each part has a standard solution, built from the lower concepts.
Boundaries. The first and hardest decision is where to cut. Software engineering principles (L3) give the rule: high cohesion inside a module and low coupling between modules, hiding implementation behind a stable interface. Domain-driven design turns this into bounded contexts: the "Order" in billing is not the "Order" in warehouse, and each context is a candidate service. Good boundaries follow business capabilities and team ownership (Conway's law used on purpose), so that most changes touch one service. Cutting along technical layers (a "database service", a "UI service") leads to changes that touch many services at once.
Communication. Services call each other synchronously, with request and response, or asynchronously through messages and events. Synchronous calls use RPC (L3): the client has a generated stub, data is encoded in a compact schema-based format (Protocol Buffers over gRPC, or JSON over HTTP), and the call travels over a network. Because the network can fail, every call needs the defensive tools from the lower layers. A timeout limits the wait (without it, one slow dependency uses all threads and the caller fails too). Retries with exponential backoff and jitter (L2) repeat a failed call after a delay that grows and is randomised, so a thousand clients do not retry at the same instant. A circuit breaker (L2) counts recent failures; past a threshold (for example 50% of the last 20 calls) it "opens" and rejects calls at once for some seconds, then lets a few probes through (half-open) to see whether the dependency has recovered. Failure detection (L2) with health checks and heartbeats removes dead instances from rotation. Rate limiting (L2) with token buckets protects a service from callers that send too much, so one noisy neighbour cannot starve others.
Retries create duplicates, so idempotence (L2) matters. A payment call that times out may or may not have been executed. The client sends an idempotency key with the request. The server stores the key with the result for some time (often 24 hours); a repeated request with the same key returns the stored result and does not charge the card again. Read operations and PUT-style updates are idempotent by nature; creating things needs a key.
Data. Each service owns its data and exposes it only through its API, which allows the owner to change its schema freely. The price is that there are no joins and no single ACID transaction across services. For a business process that spans services (place order, reserve stock, take payment, ship), a saga (L2) runs a sequence of local transactions, and each step has a compensating action (release stock, refund) that runs if a later step fails. Events are published to tell others about changes. To publish an event reliably together with a database change, the transactional outbox (L2) writes the event to an outbox table in the same local transaction as the change; a relay (a poller, or change data capture such as Debezium) then reads the table and publishes to the broker with at-least-once delivery, and consumers handle duplicates idempotently. This avoids the "dual write" problem, where the database commit succeeds and the publish fails (or the reverse).
Operations. Each service has its own pipeline and version, is deployed by rolling or canary release, and runs in several instances. Service discovery finds the instances (DNS in Kubernetes, or a registry). An API gateway handles outside traffic, and a service mesh can handle security and retries between services. Observability is essential: metrics per service, structured logs, and distributed traces with propagated IDs. Contract tests and consumer-driven contracts let a team change a service with confidence that its callers will not break, and API versioning rules (add fields freely, never change meaning, deprecate with notice) let services evolve at different speeds.
The costs add up in numbers. If a request depends on five services in series, each 99.9% available, the chain is \( 0.999^5 \) ≈ 99.5% available. Latency adds up too, and the tail grows: if each call has a 1% chance of being slow, a request that fans out to 10 services has \( 1 - 0.99^10 \) ≈ 9.6% chance that at least one is slow. This is why timeouts, hedged requests and caching become design topics.

example: An online shop splits "place order" into orders, payments and inventory services. Follow one order through the failure cases.
Step 1, the happy path. The customer clicks Pay. The orders service writes the order (state PENDING) and an outbox row "OrderCreated" in one local database transaction, then returns. The relay publishes the event within about 100 ms. Inventory consumes it and reserves 2 units (local transaction), publishes "StockReserved". Payments consumes that, charges the card and publishes "PaymentTaken". Orders consumes it and sets the state to CONFIRMED. The whole saga takes roughly 300 to 500 ms.
Step 2, a timeout and a retry. Orders calls payments directly in a simpler design: POST /charge with Idempotency-Key = order-8841. The call times out after 2 seconds. Orders retries after 200 ms plus random jitter, then 400 ms. It does not know whether the first call worked. Payments stores the key with its result, so the second request returns "already charged, payment id 77" and the card is charged once. Without the key, the customer would be charged twice.
Step 3, compensation. Inventory has no stock for item B, so it publishes "StockFailed". The saga compensates: payments refunds the earlier charge (a new, idempotent action with its own key), and orders sets the state to CANCELLED. The customer sees "out of stock" and a refund notice. There is no global rollback, only forward actions that undo the business effect. During the few hundred milliseconds in between, the system is inconsistent, and the design must accept it (for example by showing "processing").
Step 4, a slow dependency. Payments becomes slow: p99 rises from 80 ms to 6 s. Orders has a 2 s timeout and a circuit breaker that opens when more than half of the last 20 calls fail. After 10 failures the breaker opens, and orders rejects new payment calls immediately and shows "payment temporarily unavailable, we will confirm by e-mail", while payments recovers. Without the timeout and breaker, orders threads (say a pool of 200) would all wait 6 s; at 100 requests per second, the pool fills in 2 seconds and orders is down as well.
Step 5, the cost of availability. The checkout path now depends on orders, payments, inventory, and the broker. Each is 99.9% available. In series: \( 0.999^4 \) ≈ 99.6%, about 3 hours of downtime per month if failures are independent and hard. With a saga and queues, the customer-facing step only depends on orders and its database (99.9%): the other steps are delayed, not failed, when a service is down. Decoupling in time is what keeps the front door open.
intuition: Many small shops with clear contracts and their own cash registers, instead of one huge department store where every change needs the whole store to close.
The idea is natural because it follows how humans organise: small teams that own a purpose can decide and act quickly, as long as the interfaces between them are stable. The cost is the same as in any federation: communication is slower and less reliable than inside one team, so you need written agreements (APIs), ways to cope with silence (timeouts) and ways to repair (compensation).
mistakes: People often think microservices are always better than a monolith. In fact they trade simplicity for independence. For a team of 10 working on one product, a well-structured monolith is faster to build, easier to debug, and cheaper to run. Microservices pay off when team count and scale make coordination the bottleneck.
People often think that smaller services are better. In fact the right size is set by the boundary of a business capability and a team's ability to own it, not by lines of code. Too many tiny services create a chain of calls for every action, with the network cost and failure modes of each.
People often think that having separate deployables means independence. In fact if services share a database, a library with business logic, or must be released in a fixed order, they are a distributed monolith. A test is whether one team can deploy its service on its own at any time.
People often think the network is reliable if you use HTTP. In fact calls fail, hang, and arrive twice. Treat every remote call as something that can do any of these, and design timeouts, retries with idempotency and fallbacks from the first day.
People often think distributed transactions can be avoided by using a message broker. In fact a broker moves the problem. Without an outbox, a service can commit its data and fail to publish (or the reverse). With at-least-once delivery, consumers see duplicates. You need the outbox, idempotent consumers, and sagas with compensation.
People often think a service mesh or Kubernetes removes the complexity. In fact they provide shared plumbing (routing, retries, discovery), but the hard parts remain: boundaries, data ownership, versioning, and consistency.
tradeoffs: Choose a modular monolith when the team is below about 30 to 50 engineers, when the domain is still changing, or when you do not yet know where the boundaries are; you keep fast refactoring, simple transactions and easy debugging, and you give up independent scaling and release. Choose microservices when many teams (dozens) need to release independently, parts have very different scale or reliability needs, or you must isolate failures; you give up simplicity and pay the distributed-systems tax.
Choose synchronous calls (gRPC, HTTP) when the caller needs the answer now and the interaction is a query or a short command; you give up availability coupling, because the caller fails if the callee is down, unless protected by timeouts and fallbacks. Choose asynchronous events when work can happen later or many services need to react; you give up immediate consistency and simple request tracing, and take on duplicate handling and eventual consistency.
Choose orchestration for a saga (a central coordinator that tells each step what to do) when the process is complex and you want clear visibility; you give up some decoupling. Choose choreography (services react to each other's events) when the flow is simple and teams are independent; you give up an overview, since the flow is spread over many services and gets hard to understand.
Choose database per service to allow independent change and scaling; you give up joins, and reporting needs a separate pipeline (events into a warehouse). A shared database is simpler at first but ties every service to one schema and is the usual cause of a distributed monolith.
Choose fine-grained services where the capability is truly separate, with its own scaling profile (such as image processing), and coarser ones elsewhere. Merging services back is a legitimate fix when the call chain and coordination cost exceed the benefit.
friction: Every function call is now a network call: slower by a factor of about 10,000 or more (microseconds in the network at best, milliseconds usually, against nanoseconds in-process), and it can fail, time out, or be slow. Latency adds up across a chain and the tail gets worse with fan-out.
Data consistency is the deepest problem. Without a shared transaction, you design for eventual consistency with sagas, compensations and idempotent consumers. Reporting and analytics across services need data pipelines. Referential integrity across services is a convention, not a guarantee.
Operations grow. Hundreds of services mean hundreds of pipelines, dashboards, alerts, runbooks, dependency upgrades and security patches. The platform team's work becomes essential, and its cost is a fixed overhead per service.
Debugging and testing are harder. A failure may involve six services and a queue. Without distributed tracing and correlated logs it is almost impossible. End-to-end tests are slow and flaky, so teams depend on contract tests and production monitoring with gradual rollouts.
Versioning and compatibility need constant care. Callers deploy at different times, so every change to an API must be backward compatible for a long overlap. Shared libraries become a hidden coupling.
Organisational risks matter too: unclear ownership, duplicated work, inconsistent standards, and a "distributed monolith". Many teams later consolidate services.
Cost can rise: more instances, each with a minimum footprint, cross-zone network traffic, observability data per service, and the people to run the platform.
practice: Draw boundaries around business capabilities owned by one team, and test them by asking which changes would need two teams. Start with a monolith or a modular monolith, and extract a service when there is a clear reason: independent scaling, a different release rate, team independence, or fault isolation.
Give every service its own data store and publish data through APIs or events, never through shared tables. Define APIs as contracts (OpenAPI or protobuf), version them, and test them with consumer-driven contract tests.
Budget for the distributed-systems tax from the first service: a timeout on every call, retries with exponential backoff, jitter and a budget, idempotency keys on every operation that changes state, circuit breakers and bulkheads (separate thread or connection pools per dependency), and sensible fallbacks. Use the outbox pattern when you must change data and publish an event, and design consumers to handle duplicates and reordering.
Invest in the platform early: one paved path for building, deploying, observing and securing a service, so a new service takes hours and not weeks. Trace every request with propagated IDs, and track SLOs per service. Limit the number of synchronous hops in a user request (three is a good target) and the fan-out.
Measure whether the architecture works: deployment frequency and lead time per service, the share of changes that touch more than one service, incident causes, and cost per service. If a team cannot deploy its service independently, the split has not delivered its main benefit; fix the coupling or merge the services.
quiz: What is the main benefit of microservices, and what is the main price? || Teams can build, deploy and scale their services independently, so large organisations move faster and failures are contained. The price is that every interaction becomes a network call that can fail or be slow, and data consistency across services needs sagas and events.
Why do retries need idempotency keys? || A timed-out call may have succeeded. Retrying without a key could repeat the action (charge twice). With a key, the server stores the first result and returns it for repeats, so the effect happens once.
What problem does the transactional outbox solve? || The dual write: a service must change its database and publish an event, and one of the two can fail. The outbox writes the event into the same local transaction as the change, and a relay publishes it afterwards with at-least-once delivery.
Five services in series each have 99.9% availability. What is the availability of the chain, and about how much downtime per month is that? || \( 0.999^5 \approx 0.995 \), or 99.5%. That is about 0.5% of a 30-day month, around 3.6 hours.
A 12-person team asks whether to start with microservices. What do you advise? || Start with a modular monolith. The team is small, boundaries are not yet known, and the coordination cost of microservices is higher than the benefit. Extract services later where scale or team independence requires it.
interview: How do you handle a transaction that spans orders, payments and inventory? || Use a saga: a sequence of local transactions with compensating actions, coordinated by an orchestrator or by events. Use the outbox to publish events reliably, make consumers idempotent, and design the user experience for temporary inconsistency. Two-phase commit is usually avoided for availability and coupling reasons.
A downstream service becomes slow and your service starts failing too. What happened and how do you prevent it? || Threads or connections were held by slow calls until pools were full (resource exhaustion), so the failure cascaded. Use timeouts shorter than the caller's, circuit breakers, bulkheads (separate pools per dependency), load shedding, and fallbacks. Retries must use backoff and a retry budget.
How do you decide service boundaries? || By business capability and data ownership, using domain-driven design: find bounded contexts, put data and behaviour that change together in one service, minimise synchronous calls between services, and align with team ownership. Validate by looking at which changes cross boundaries; if many do, the boundaries are wrong.
How do you change an API without breaking callers? || Make additive, backward-compatible changes (new optional fields), never change meaning, run old and new versions side by side, use consumer-driven contract tests to see who depends on what, announce deprecation and track usage, and remove only when traffic is gone.
Why might a company move from microservices back to a monolith, and how would you know it is time? || When the cost of the network, coordination and operations exceeds the benefit: signs are changes that need several services, heavy synchronous call chains, slow deploys due to coupling, a small team carrying many services, and high platform cost. Merge services along the heaviest coupling first.
How do you test a system made of many services? || A large base of unit and service-level tests, contract tests between each caller and callee, a few end-to-end tests for critical journeys, and testing in production with canary releases, feature flags and strong monitoring. Full end-to-end suites alone are too slow and flaky.
