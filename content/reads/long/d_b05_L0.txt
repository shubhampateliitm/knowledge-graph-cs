@@ mysql
value: MySQL is an open-source relational database, and InnoDB is the storage engine inside it that does the real work: it lays rows out on disk, runs transactions, keeps old versions for readers, and recovers after a crash. MySQL was the "M" in the LAMP stack (Linux, Apache, MySQL, PHP) that built much of the early web, and it still runs very large systems: Facebook's user data, YouTube (through the Vitess sharding layer), GitHub, Shopify, Booking.com and Uber. In the 2025 Stack Overflow survey about 40% of professional developers said they use it, against about 55% for PostgreSQL.
The problem InnoDB solves is the OLTP problem, which is the first concept it stands on. OLTP (online transaction processing) means thousands of small transactions per second, each reading or changing a few rows found by key, each needing ACID guarantees and low latency. Every major InnoDB choice follows from that workload: rows are stored inside the primary-key B+tree so key lookups and short range scans are fast; row-level locks let unrelated transactions run in parallel; old row versions are kept in an undo log so readers never wait for writers (MVCC, multi-version concurrency control); a redo log turns random page updates into sequential log writes for durability; and a binary log ships every committed change to replicas and to change-data-capture tools.
The second concept it stands on is HTAP (hybrid transactional and analytical processing). Oracle's HeatWave engine keeps an in-memory columnar copy of InnoDB tables, so reports can read fresh data without a separate warehouse. For the layer above, MySQL gives frameworks, sharding layers (Vitess), CDC pipelines (Debezium reading the binlog into Kafka) and managed services (RDS, Aurora, Cloud SQL) a well-understood transactional core. The project is also at a turning point: MySQL 8.0 reached end of life on 30 April 2026, the current long-term-support lines are 8.4 and 9.7, and in September 2025 Oracle reportedly cut a large part of the MySQL engineering team.
terms: Clustered index — an index whose leaf pages hold the full rows; in InnoDB the primary-key B+tree is the table itself.
Secondary index — an extra B+tree whose leaves hold the indexed columns plus the primary-key value of each row, not a disk address.
Page — the unit of storage and I/O in InnoDB, 16 KB by default.
Buffer pool — InnoDB's cache of pages in memory, usually sized at 50–75% of the server's RAM.
Redo log — a write-ahead log of changes to pages, replayed after a crash to restore committed work.
Undo log — records of old row values, used to roll back a transaction and to rebuild older row versions for MVCC reads.
Read view — the snapshot a transaction uses to decide which row versions it is allowed to see.
Binary log (binlog) — a logical log of committed changes, in commit order, read by replicas and CDC tools.
Next-key lock — a lock on an index record plus the gap before it, used to block "phantom" rows from being inserted.
GTID — a global transaction identifier (server UUID plus a sequence number) that names each transaction in the binlog.
history: Michael "Monty" Widenius, David Axmark and Allan Larsson released MySQL in 1995 through their Swedish company MySQL AB; the name comes from Monty's daughter My. Early MySQL used the MyISAM engine: fast for read-heavy web pages, but with table-level locks, no transactions and no crash safety. Its speed, simplicity and free license made it the default database of the early web.
In 1995 Heikki Tuuri founded Innobase Oy in Finland and wrote InnoDB, a transactional engine modelled on classic database designs: B+trees, write-ahead logging, row locks and multi-versioning. It shipped with MySQL from about 2001 and slowly replaced MyISAM for serious work. Ownership then moved several times. Oracle bought Innobase in 2005, Sun Microsystems bought MySQL AB in 2008 for about 1 billion US dollars, and Oracle bought Sun in 2010. Fear of Oracle control led Monty to start the MariaDB fork in 2009; Percona Server became a second, closer fork.
Under Oracle, InnoDB became the default engine in MySQL 5.5 (2010). Version 5.6 (2013) added GTIDs and online schema changes; 5.7 (2015) added a JSON type and, in late 2016, Group Replication, a Paxos-based multi-node mode. MySQL 8.0 (April 2018) was a large rewrite: a transactional data dictionary, common table expressions, window functions, instant ADD COLUMN, a new redo log design and, from 8.0.18, hash joins. In 2023 Oracle split releases into short "Innovation" releases and long-term-support (LTS) releases: 8.4 LTS came in April 2024, 9.0 in July 2024 added a VECTOR column type, and 9.7 LTS in April 2026 brought the hypergraph join optimizer and several Group Replication tools to the free Community Edition. HeatWave, launched in 2020 as part of Oracle's cloud MySQL service, became Oracle's commercial focus. Large users pushed the engine too: Facebook built MyRocks (MySQL on RocksDB) to save space, and Uber's 2016 move from PostgreSQL to MySQL made the clustered-index design widely discussed.
how: Storage starts with pages. Each table lives in a tablespace file made of 16 KB pages, and the table is one B+tree ordered by the primary key. Internal pages hold keys and child page numbers; leaf pages hold whole rows, and leaves are linked in both directions so a range scan just walks along them. InnoDB adds hidden columns to every row: DB_TRX_ID (6 bytes, the ID of the last transaction that changed the row) and DB_ROLL_PTR (7 bytes, a pointer to the row's previous version in the undo log). If you declare no primary key, InnoDB uses the first UNIQUE NOT NULL index, or else invents a hidden 6-byte row ID. With an 8-byte key, an internal page holds several hundred to about a thousand child pointers, so even a table of hundreds of millions of rows is only 3 or 4 levels deep, and the upper levels are small enough to stay in the buffer pool.
Secondary indexes are separate B+trees whose leaves contain the indexed columns plus the primary key. A lookup by a secondary index therefore does two tree searches: one in the secondary index to find the primary key, then one in the clustered index to fetch the row. Using the primary key instead of a physical address has a reason. When a page splits, rows move to new pages, but their primary keys do not change, so secondary indexes need no update. The cost is that a wide primary key (for example a 36-character UUID string) is copied into every secondary index entry. If an index already contains every column a query needs (a covering index), the second search is skipped.
The write path is where the OLTP concept turns into mechanism. Take UPDATE orders SET status = 'shipped' WHERE id = 7. InnoDB finds the leaf page (reading it into the buffer pool if needed), takes an exclusive row lock on the record, writes the old value of status into an undo record, changes the row in place, sets DB_TRX_ID and DB_ROLL_PTR, and appends a redo record describing the page change to the in-memory log buffer. The data page is now "dirty" in memory and is not written yet. At COMMIT, with the binlog enabled, MySQL runs an internal two-phase commit: InnoDB writes a "prepare" record and flushes the redo log, MySQL writes the transaction's row events to the binlog and flushes it, then InnoDB marks the transaction committed. With the safe settings innodb_flush_log_at_trx_commit = 1 and sync_binlog = 1, a commit costs two fsyncs, and group commit lets many concurrent transactions share each fsync.
Dirty pages are written back later by background page-cleaner threads, which lets the redo log be reused up to the latest checkpoint. A 16 KB page write is not atomic on most storage: the OS or disk may write only 4 KB of it before power fails. That "torn page" cannot be fixed by redo, because redo records describe changes to an intact page. So InnoDB first writes each page to a doublewrite area, flushes it, and only then writes it to its real place; after a crash, a torn page is restored from its doublewrite copy. Recovery itself follows the classic ARIES pattern: replay redo from the last checkpoint so every page is current, then use undo to roll back transactions that never committed. A transaction left in the prepared state is committed if its events reached the binlog and rolled back if not, so InnoDB and the binlog always agree.
Reads use MVCC. A plain SELECT is a "consistent read": the transaction builds a read view, which records which transaction IDs were still active when the view was created. For each row it meets, InnoDB checks DB_TRX_ID; if that change is not visible to the view, it follows DB_ROLL_PTR into the undo log and rebuilds the older version, repeating until it finds a visible one. At the default REPEATABLE READ level, the view is created at the first read and kept for the whole transaction; at READ COMMITTED, each statement gets a fresh view. Purge threads delete undo records once no read view can need them. Locking reads (SELECT ... FOR UPDATE, UPDATE, DELETE) are different: they read the latest committed version and take record locks, and at REPEATABLE READ they also lock the gaps between index records (next-key locks) so that no new row can appear inside a scanned range. Deadlocks are detected automatically and one transaction is rolled back.
Replication reads the binlog. Each replica pulls events into a local relay log and applies them with parallel worker threads. Replication is asynchronous by default: the primary commits without waiting. Semi-synchronous replication waits until at least one replica has received the events. Group Replication sends each transaction's writeset through a Paxos-based group layer; every member certifies it against concurrent transactions in the same order, and it commits only after a majority agrees.
Finally, the HTAP concept appears in HeatWave. Tables are loaded from InnoDB into a cluster of HeatWave nodes in a compressed, in-memory columnar format. Committed InnoDB changes flow to that copy automatically, and the optimizer sends large scans, joins and aggregations to HeatWave while short transactional queries stay on InnoDB. The row store stays the source of truth; the column store is a derived view of it.

example: Take an orders table with a BIGINT AUTO_INCREMENT primary key and 100 million rows of about 200 bytes each. InnoDB fills pages to about 15/16 on sequential inserts, so a 16 KB leaf holds about 15,000 / 200 ≈ 75 rows. That gives 100,000,000 / 75 ≈ 1.33 million leaf pages, about 21 GB. An internal-page entry is roughly 8 bytes of key, a 4-byte child page number and a 5-byte record header, about 17 bytes, so one internal page points to about 900 children. The level above the leaves needs 1.33 million / 900 ≈ 1,480 pages (about 23 MB); the next level needs 2 pages; then one root. The tree is 4 levels deep, and the top three levels take about 23 MB, which always stays in the buffer pool. A lookup by id therefore costs at most one disk read, for the leaf: about 0.1 ms on an NVMe SSD, or nothing if the leaf is cached.
Now add a secondary index on customer_id (a 4-byte INT). Each entry is about 4 + 8 (the primary key) + 5 ≈ 17 bytes, so a leaf holds about 900 entries, and the index needs about 111,000 leaf pages, about 1.8 GB. The query SELECT * FROM orders WHERE customer_id = 42 matches 50 orders. Finding them in the secondary index takes one descent and one or two leaf pages. Fetching the full rows takes 50 separate descents of the clustered index. Old orders of one customer are spread across the table, so if they are not cached this is up to 50 random reads: 50 × 0.1 ms = 5 ms. If the query only needs customer_id, created_at and amount, a covering index on (customer_id, created_at, amount) answers it from the secondary index alone, in well under 1 ms.
The primary key choice changes write cost too. With AUTO_INCREMENT, every new row goes to the rightmost leaf, which is always hot in memory, and full pages are left 15/16 full. With random UUIDv4 keys, each insert lands on a random one of 1.33 million leaves. If the buffer pool is 8 GB and the leaves are 21 GB, roughly 60% of inserts must first read a leaf from disk, and random splits leave pages only about 50–70% full, so the table and every secondary index grow by roughly 1.4 times. Storing the UUID as a 36-byte string instead of BINARY(16) adds 28 more bytes to every entry of every secondary index. A time-ordered key such as UUIDv7 in BINARY(16) keeps uniqueness across systems and keeps inserts near the right edge of the tree.
Last, durability. With innodb_flush_log_at_trx_commit = 1 and sync_binlog = 1, each commit needs two fsyncs. If an fsync takes 0.5 ms, a single connection can commit at most about 1,000 transactions per second. With 64 concurrent connections, group commit lets one fsync cover many transactions, so the server can commit tens of thousands per second. Durability is limited by latency per commit, not by total throughput.
intuition: A library where books stand on the shelves in call-number order, the catalog cards only record the call number, and the librarian writes every change in a logbook before touching any shelf.
Once the workload is "find a few rows by key, change them, commit", the design follows naturally. If rows live inside the primary-key tree, the most common lookup is one tree walk with no extra jump. If secondary indexes point to keys instead of shelf positions, moving books between shelves never invalidates the catalog. If every change is first written as a short sequential log entry, the expensive random page writes can wait, be batched and still survive a crash. And if old values are kept on the side, a reader can always reconstruct the version it is allowed to see instead of waiting for the writer to finish. Each piece removes one source of waiting or one random disk write from the hot path of a small transaction.
mistakes: People often think InnoDB stores a table as a heap of rows plus separate indexes, as PostgreSQL does. In fact the primary-key B+tree is the table. This is why primary-key range scans are fast, why secondary-index lookups need a second search, and why the primary key's size and order matter so much.
People often think REPEATABLE READ in MySQL is the same as snapshot isolation. Plain SELECTs do read a snapshot, but UPDATE, DELETE and SELECT ... FOR UPDATE read the latest committed version. Jepsen's 2023 analysis of MySQL 8.0.34 showed that REPEATABLE READ allows lost updates, write skew and read skew. If correctness depends on it, use SELECT ... FOR UPDATE, explicit version checks or SERIALIZABLE.
People often think a replica is a safe, always-current copy. Replication is asynchronous by default, so a replica can lag by seconds or more, and after a failover the newest committed transactions on the old primary can be lost. Semi-synchronous replication or Group Replication reduces this risk, at a latency cost on every commit.
People often think SELECT COUNT(*) is answered from a stored counter. Because of MVCC, different transactions may see different row counts, so InnoDB has no single correct counter and must scan an index. On a large table this takes seconds; keep a separate summary or use an approximate count from table statistics.
friction: The primary key is the physical layout, so choosing it badly is expensive to undo: changing it rebuilds the table and every secondary index. Long-running transactions are a common silent problem. A read view that stays open for an hour stops purge, the undo history grows (the "history list length" can reach millions of entries), and every reader must walk longer version chains, so the whole server slows down. Gap and next-key locks at REPEATABLE READ cause deadlocks that surprise developers, especially with concurrent INSERTs into the same range.
Writes scale only vertically on one primary. Group Replication helps availability, not write throughput, because every member applies every write; scaling writes means sharding, usually with Vitess or application-level routing. Schema changes are much better than they were (many ADD COLUMN operations are now INSTANT), but some changes still copy the table, and large teams use online tools such as gh-ost or pt-online-schema-change. The optimizer was long weaker than PostgreSQL's for complex queries; hash joins arrived only in 8.0.18 and the hypergraph optimizer reached the free edition only in 9.7.
Finally, stewardship. Oracle develops MySQL mostly in private and publishes code at release time. After the September 2025 cuts, which Percona's co-founder estimated at 60–70% of the engineering team, many users worry about the pace of the Community Edition. MariaDB has drifted away from MySQL 8.x, so it is not a drop-in replacement; Percona Server is closer.
practice: Choose the primary key first: a BIGINT AUTO_INCREMENT, or a time-ordered UUIDv7 stored as BINARY(16) when IDs must be generated outside the database. Avoid random UUIDv4 and wide string keys. Design indexes per query, use covering indexes for hot read paths, and read plans with EXPLAIN ANALYZE (available since 8.0.18).
Size the buffer pool to hold the working set (indexes plus hot rows); on a dedicated server, innodb_dedicated_server sets the buffer pool and redo capacity from the machine's memory. Keep innodb_flush_log_at_trx_commit = 1 and sync_binlog = 1 unless you have decided, in writing, how many seconds of commits you can lose. Use row-based binlogs with GTIDs; they make failover, replica rebuilding and CDC with Debezium straightforward.
Keep transactions short and never leave a transaction open while waiting for a user or a remote call. Monitor the history list length (in SHOW ENGINE INNODB STATUS or information_schema.INNODB_METRICS), replication lag, deadlock counts and buffer-pool hit rate. If gap-lock deadlocks hurt and your code does not depend on REPEATABLE READ, READ COMMITTED is a common and reasonable choice; it is the default in several large installations. Use explicit locking reads for read-modify-write logic.
Keep heavy analytics off the primary: use a replica, CDC into a lakehouse, or HeatWave if you are on Oracle Cloud and need fresh analytics. If you are still on 8.0, plan the move to 8.4 LTS or 9.7 LTS now; 8.4 changed many defaults (for example, the adaptive hash index and change buffering are off by default), so test performance before switching.
quiz: Where does InnoDB store the full row, and what does a secondary index leaf contain? || The full row lives in the leaf pages of the clustered primary-key B+tree. A secondary index leaf contains the indexed columns plus the row's primary-key value, which is used for a second lookup in the clustered index.
Why do secondary indexes store the primary key rather than a physical row address? || Rows move between pages when pages split or merge, but their primary keys do not change. Storing the primary key means secondary indexes never need updating when rows move; the cost is an extra tree search and larger index entries for wide keys.
How does a REPEATABLE READ transaction see an old value of a row that another transaction has already updated and committed? || Its read view says the newer DB_TRX_ID is not visible, so InnoDB follows the row's DB_ROLL_PTR into the undo log and rebuilds the older version, repeating until it reaches a version the view may see.
A table has 100 million rows, about 75 rows per leaf page and about 900 child pointers per internal page. How many levels does the B+tree have? || About 1.33 million leaf pages, about 1,480 pages one level up, 2 pages above that, and one root: 4 levels. Only the leaf read usually touches disk, because the upper levels (about 23 MB) stay in memory.
You need IDs generated by many services without coordination. Should the InnoDB primary key be a random UUIDv4 string? || No. Random keys scatter inserts over all leaf pages, causing disk reads, page splits and about 1.4 times more space, and a string key bloats every secondary index. Use a time-ordered UUIDv7 stored as BINARY(16), or keep a BIGINT primary key and put the external UUID in a unique secondary index.

@@ sqlite
value: SQLite is a complete SQL database packed into one C library and one ordinary file. There is no server process, no network protocol, no user accounts and no configuration: a program links the library, opens a file, and runs SQL with full ACID transactions. The SQLite team estimates that more than one trillion SQLite databases are in active use. Every Android and iOS device, every Mac and Windows 10/11 installation, and the Chrome, Firefox and Safari browsers all use it; so do most TV sets and set-top boxes, car infotainment systems, and the flight software of the Airbus A350 family.
The concept it stands on is OLTP (online transaction processing): many small reads and writes, each in an ACID transaction. SQLite keeps all the classic OLTP ingredients, namely B-tree storage, a log for atomic commit, and locks for isolation, but shrinks them to fit inside one process and one file. A lock manager becomes a few file locks. A buffer pool becomes a small page cache. A recovery manager becomes the rule "if a journal file is left next to the database, roll it back". The result is OLTP for one application, not for thousands of network clients.
For the layer above, SQLite turns "a file" into "a database". Applications use it as their file format (Apple's Photos and Core Data, Adobe Lightroom catalogs, Chrome history), as a local cache of server data on phones, and as an exchange format; the US Library of Congress lists it as a recommended format for storing datasets. Since about 2022 it has also returned to servers: Ruby on Rails 8 (2024) made SQLite a supported production default, and Cloudflare D1 and Durable Objects, Turso and Litestream add replication and backups around it. It is worth understanding now because "one SQLite file per user or per tenant" has become a serious design for small and medium services, and its limits (one writer at a time, same-machine access) decide when that design works.
terms: Page — the fixed-size unit of the database file, 4096 bytes by default (any power of two from 512 to 65,536).
Table B-tree — a B+tree keyed by a 64-bit integer rowid; full rows are stored only in the leaf pages.
Index B-tree — a B-tree whose entries are the indexed columns followed by the rowid, with no other row data.
Pager — the module that reads and writes pages, caches them, and makes commits atomic with a journal or WAL.
Rollback journal — a side file holding the original content of pages before a transaction changes them.
WAL (write-ahead log) — a side file to which new versions of changed pages are appended; the database file is updated later.
Checkpoint — copying the newest page versions from the WAL back into the database file.
VDBE — the Virtual Database Engine, a small bytecode virtual machine that executes compiled SQL statements.
Type affinity — SQLite's flexible typing: a column suggests a type, but any value can be stored unless the table is declared STRICT.
fsync — the system call that forces written data from OS buffers to durable storage; it is the main cost of a commit.
history: D. Richard Hipp wrote SQLite in spring 2000 while working for General Dynamics on damage-control software for US Navy destroyers. The software used an Informix database, and when the database server was down, the program could not run at all. Hipp wanted a database that needed no server and no administrator, and the first release came in August 2000. Version 1 stored data in the gdbm key-value library; version 2 (2001) used SQLite's own B-tree code; version 3 (June 2004) introduced the file format still used today, with UTF-16 text and more compact records.
Adoption grew through embedded software. Symbian, Mozilla Firefox, Apple and then Android and the iPhone (2007–2008) built SQLite into their platforms. Large users funded development through the SQLite Consortium (from 2007). Work on avionics pushed the team to the aviation standard DO-178B, which led to the TH3 test harness and 100% MC/DC coverage (every branch condition shown to affect the outcome) of the core library. Version 3.7.0 (July 2010) added write-ahead logging, which let readers and a writer work at the same time.
Later releases added full-text search, JSON functions (built in from 3.38.0, 2022), a binary JSONB format (3.45.0, January 2024) and STRICT tables with enforced column types (3.37.0, 2021). The file format is promised to stay readable until at least 2050. The code is in the public domain, and the small core team (led by Hipp, with Dan Kennedy and a few others) does not accept outside code patches, which keeps the copyright situation simple. Others fork it instead: libSQL (2022, by Turso) added network replication, and Turso is now rewriting SQLite in Rust; its MVCC-based concurrent writes entered public preview in August 2026. In 2026 the team fixed a rare WAL corruption bug that had existed since 3.7.0; it needed two connections to write or checkpoint at the same instant and was fixed in 3.51.3 (March 2026). The current release in October 2026 is 3.54.1.
how: SQLite is a stack of layers. A tokenizer and a parser (generated by Hipp's Lemon parser generator) turn SQL text into a parse tree. The code generator and query planner turn that tree into a bytecode program, and the VDBE runs it, one opcode at a time: open a cursor on a B-tree, seek to a key, read a column, compare, jump, emit a result row. Below the VDBE sit the B-tree module, the pager, and a VFS (virtual file system) layer that hides the operating system. You can see the bytecode for any statement with EXPLAIN. Compiling to bytecode keeps the executor small and makes prepared statements cheap to run many times.
The file is an array of pages. Page 1 begins with a 100-byte header that starts with the string "SQLite format 3". Every table is a B+tree keyed by a 64-bit rowid (or by its primary key for WITHOUT ROWID tables), and every index is a separate B-tree whose entries hold the indexed columns plus the rowid. A row is stored as a record: a small header of variable-length integers (varints) giving each column's type and size, followed by the values. A record that does not fit in a page continues in a chain of overflow pages. The schema itself is stored as rows of a special table, sqlite_schema, on page 1. Because one file holds everything, copying the file copies the whole database.
Atomic commit is the core of the OLTP inheritance, and SQLite has two ways to do it. In rollback-journal mode (the default), a writer first takes a RESERVED file lock, which allows readers to continue but blocks other writers. Before changing any page, it copies the page's original content into the journal file. When the transaction commits, it fsyncs the journal, takes an EXCLUSIVE lock (waiting for readers to leave), writes the changed pages into the database file, fsyncs the file, and then deletes the journal. Deleting the journal is the commit point. If power fails before that, the next program to open the database finds a "hot" journal and copies the original pages back, so the transaction disappears completely. If power fails after it, the database file already holds the new pages.
WAL mode turns this around. The database file is left untouched during a transaction; instead, new versions of changed pages are appended to a -wal file as frames, and a commit is simply a frame marked as the end of a transaction. A shared-memory file (-shm) holds the wal-index, a hash table that tells readers which frame holds the newest copy of each page. Each reader remembers the last committed frame when it starts (its "end mark") and ignores later frames, so it sees a stable snapshot. This is MVCC at page granularity: readers do not block the writer and the writer does not block readers. When the WAL reaches 1,000 pages (about 4 MB with 4 KB pages), a checkpoint copies the newest pages into the database file. A checkpoint cannot move past the end mark of the oldest active reader, so a reader that never finishes lets the WAL grow without limit.
Only one writer can exist at a time in both modes, because there is one journal or one WAL and the lock is on the whole file. Other writers get SQLITE_BUSY or wait up to busy_timeout. A transaction that starts by reading and later tries to write can fail with SQLITE_BUSY if another writer committed in between, because its snapshot is now stale; starting write transactions with BEGIN IMMEDIATE takes the write lock at once and avoids this. Since commits are serialized, SQLite transactions are serializable by construction.
The synchronous setting controls fsync cost. With synchronous = FULL, every commit is durable when COMMIT returns. In WAL mode with synchronous = NORMAL, commits do not fsync at all; only checkpoints do. A power cut can then lose the last few commits, but it cannot corrupt the database, because frames are checked with checksums and an incomplete transaction is ignored. On top of all this, SQLite uses file locks provided by the operating system. Network file systems often implement those locks badly, which is why SQLite warns against sharing a database file over NFS or SMB, and why WAL mode requires all users to be on the same machine.

example: A phone app stores 10 million messages of about 100 bytes each in a table with an INTEGER PRIMARY KEY. With 4 KB pages and some per-cell overhead, a leaf page holds about 35 rows, so the table needs 10,000,000 / 35 ≈ 286,000 leaf pages, about 1.2 GB. An interior page entry is a 4-byte child page number plus a rowid varint of about 4 bytes, plus a 2-byte cell pointer, so about 400 entries fit in a page. The level above the leaves needs 286,000 / 400 ≈ 715 pages, the next level 2 pages, then the root: 4 levels. Reading a message by rowid touches 4 pages; with the default page cache of about 2 MB, the top levels stay in memory and at most one or two pages come from flash, roughly 0.1–0.2 ms each.
Now the commit cost, which surprises most people. Suppose an fsync takes about 2 ms on this phone's flash storage. The app imports 10,000 new messages with one INSERT per transaction (autocommit) in rollback-journal mode. Each commit needs at least two fsyncs (journal, then database file) and creates and deletes a file, so each insert costs about 5 ms: 10,000 × 5 ms = 50 seconds. Wrapping all 10,000 inserts in one BEGIN ... COMMIT costs the same few fsyncs once: the whole import takes well under a second, limited by CPU and writing about 300 changed pages.
Switching to WAL mode with synchronous = NORMAL changes the shape again. Each small commit appends a few frames (each frame is a 24-byte header plus a 4 KB page) to the WAL without any fsync. Even 10,000 separate transactions finish in about a second or two. After roughly 1,000 pages have been appended, a checkpoint copies them into the database file with one or two fsyncs. The price is the durability window: if the phone loses power, the last commits since the most recent WAL sync can be lost, but the database stays consistent.
Last, concurrency. A web service keeps one SQLite file per customer and runs 20 request threads. Reads in WAL mode never wait. Writes are serialized: if each write transaction holds the lock for 1 ms, one database file supports at most about 1,000 write transactions per second, no matter how many cores the server has. If one customer needs 5,000 writes per second, that customer has outgrown a single SQLite file; the other customers, at 10 writes per second each, are far below the limit.
intuition: A notebook with its own careful rules for erasing: before you change a page, you photocopy it, so you can always put the old page back if you are interrupted.
SQLite feels natural once you see that most programs do not need a database server at all. They need structured data, queries and crash safety for one application on one machine. A server exists to share data among many clients over a network, to manage users and to schedule many concurrent writers. Remove those needs and what remains is small: a B-tree in a file, a page cache, and one well-tested way to make a group of page writes all-or-nothing. The journal or WAL provides that all-or-nothing step; a single writer lock makes isolation trivial because transactions simply take turns. Every feature that SQLite leaves out is a feature whose cost you do not pay.
mistakes: People often think SQLite is a toy database for tests and prototypes. In fact it has complete ACID transactions, survives power loss, and is tested more heavily than most software: 100% branch and MC/DC coverage of the core, and test code about 590 times larger than the library (as of version 3.42.0). It is in safety-critical and very high-volume systems.
People often think SQLite cannot handle concurrency at all. In WAL mode any number of readers run in parallel with one writer, and short write transactions can reach thousands of commits per second. The real limit is one writer at a time per database file, and the right question is how long each write transaction holds the lock.
People often think slow inserts mean SQLite itself is slow. Usually each insert is its own transaction, and each transaction pays for fsyncs. Grouping inserts into one transaction, or using WAL with synchronous = NORMAL, often makes bulk loading 100 times faster.
People often think a column declared INTEGER only holds integers. Without STRICT, SQLite uses type affinity: it converts values when it can, but it will store the text "abc" in an INTEGER column. Declare tables STRICT, or add CHECK constraints, when the type must be enforced.
People often put a SQLite file on a network share for several machines. File locking on network file systems is often unreliable, and WAL mode needs shared memory on one host, so this can corrupt the database. For multi-machine access, use a client-server database, or a replication layer designed for SQLite.
friction: The single-writer design is the central limit. Write throughput cannot grow with cores, and one long write transaction blocks all other writers. Long read transactions in WAL mode cause "checkpoint starvation": the WAL file keeps growing and reads become slower because each page lookup must search more of the wal-index. There is no built-in replication, no network access, no user permissions and no online schema change system; ALTER TABLE supports only a few operations (add, rename or drop a column), and other changes require creating a new table and copying the data.
The query planner is good for OLTP but has limits on analytics. A 2022 VLDB paper by Gaffney, Hipp, Patel and others measured SQLite as much slower than DuckDB on analytical queries, and SQLite added a Bloom filter step for large joins in response; for heavy analytics, DuckDB is the usual embedded choice. Flexible typing hides bugs unless tables are STRICT. Running SQLite as a server database moves classic server problems to the layer around it: backups, failover and multi-region reads must come from tools such as Litestream (whose 0.5 release in October 2025 reworked its replication format), LiteFS, Cloudflare D1 or Turso, each with its own limits and maturity. Finally, the project's closed contribution model means new features, such as concurrent writers, appear first in forks or experimental branches rather than in the main release.
practice: Turn on WAL mode (PRAGMA journal_mode = WAL) for almost every application with concurrent readers; it persists in the file. Use synchronous = NORMAL with WAL unless losing the last few commits after a power cut is unacceptable. Set busy_timeout (for example 5,000 ms) so writers wait instead of failing at once, and start write transactions with BEGIN IMMEDIATE.
Group writes into transactions, keep write transactions short, and never hold a transaction open while waiting for the network or a user. Reuse prepared statements in loops. Declare new tables STRICT, enable foreign keys explicitly (PRAGMA foreign_keys = ON, which is off by default for backward compatibility), and use EXPLAIN QUERY PLAN to check that queries use indexes.
For backups, never copy a live database file with cp: use the online backup API, VACUUM INTO, or a tool like Litestream that understands the WAL. Run PRAGMA optimize periodically (for example when closing a connection) so the planner has fresh statistics. Keep SQLite up to date; the 2026 WAL-reset fix is a good example of why.
Choose SQLite on servers when data naturally splits into many small databases (one per user, tenant or device), writes per database are modest, and all access is on one machine. Choose PostgreSQL or MySQL when many machines must write the same data, when you need fine-grained permissions, or when one dataset needs thousands of writes per second.
quiz: What is the commit point of a transaction in SQLite's rollback-journal mode? || Deleting (or invalidating) the rollback journal after the new pages are written and synced to the database file. If a crash happens before that, the hot journal is used to restore the original pages; after it, the new data is already in the file.
How does WAL mode let readers run while a writer is active? || The writer appends new page versions to the WAL instead of changing the database file. Each reader records the last committed frame when it starts and uses the wal-index to read only page versions up to that point, so it sees a stable snapshot while new frames are added.
Why does a long-running read transaction cause the WAL file to keep growing? || A checkpoint can copy frames back into the database file only up to the end mark of the oldest active reader, because that reader may still need the older page versions. Until the reader finishes, the WAL cannot be reset and keeps growing.
An app inserts 10,000 rows in separate autocommit transactions, and each commit costs about 5 ms of fsync and file work. How long does it take, and what is the fix? || About 10,000 × 5 ms = 50 seconds. Wrapping the inserts in one transaction pays the fsync cost once and finishes in well under a second; WAL mode with synchronous = NORMAL also removes most per-commit fsyncs.
A SaaS product has 50,000 tenants, each with a few writes per second, and one large tenant with 8,000 writes per second. Is one SQLite file per tenant a good design? || It fits the small tenants well, since each file is far below the one-writer limit and is easy to back up and move. The large tenant would exceed a single writer's throughput, so it needs a client-server database or must be split into several files.

@@ mongodb
value: MongoDB is the most widely used document database. Instead of rows in tables, it stores documents: nested, JSON-like records encoded in a binary format called BSON, each up to 16 MB, grouped into collections. A document can hold an order with its customer, address and line items in one place, so the application reads and writes it as one object instead of joining five tables. Schemas are flexible by default: two documents in the same collection may have different fields, and validation rules are optional. This fits the way most application code already thinks, and it lets teams change data shapes without a migration for every new field. MongoDB runs on-premises as Community or Enterprise Server and, more often today, as the managed Atlas service.
The concept it stands on is the distributed key-value and wide-column store (the "nosql" family). From that family MongoDB takes three ideas: data is partitioned across many machines by a key (the shard key), each partition is replicated with automatic failover, and data is modelled around access patterns, with deliberate denormalization instead of joins. Unlike Dynamo-style systems, though, MongoDB is leader-based: each shard is a replica set with one primary that accepts writes, and a central config service records which shard owns which key range. That makes it closer to Bigtable than to Cassandra, and it lets MongoDB offer strong single-document atomicity, secondary indexes on any field, and multi-document ACID transactions.
For the layer above (web and mobile back ends, content and catalog systems, IoT, gaming, and now AI applications that need text and vector search), MongoDB gives one system for operational data, rich queries, change streams and search. It matters now because the product has moved far from its early "fast but unsafe" image. Majority writes are the default since 5.0, transactions work across shards since 4.2, Search and Vector Search reached the self-managed editions in preview with 8.2 (2025), and MongoDB 9.0 (September 2026) added per-operation memory limits, workload management and new encrypted-query types. Knowing which guarantees you actually get, and which settings and data models give them, is the real skill.
terms: Document — a BSON record of fields and nested values, the unit of storage and of atomic update.
Collection — a group of documents, roughly like a table but with no required schema.
WiredTiger — the storage engine since version 3.2; it stores each collection and each index as a B-tree file.
Replica set — a group of mongod servers holding the same data: one primary takes writes, secondaries copy them.
Oplog — the replica set's operation log, a special collection of idempotent change records that secondaries pull and apply.
Write concern — how many replica-set members must confirm a write before it is acknowledged (for example w: 1 or w: "majority").
Read concern — which data a read may return, for example "local" (newest on this node) or "majority" (only data a majority has stored).
Shard key — the field or fields used to split a collection across shards, by range or by hash.
Chunk — a contiguous range of shard-key values stored on one shard and moved as a unit by the balancer.
mongos — the query router that applications connect to in a sharded cluster; it sends each operation to the right shards.
history: In 2007 Dwight Merriman, Eliot Horowitz and Kevin Ryan, who had built the ad server company DoubleClick, founded 10gen to build a cloud application platform. The database they wrote for it was the part people wanted, so they open-sourced it as MongoDB (from "humongous") in 2009. It spread fast with Node.js and the "NoSQL" wave: JSON in the browser, JSON in the server, JSON in the database. Early versions earned a reputation for losing data. Until late 2012, drivers sent writes without waiting for any reply from the server, and the MMAPv1 engine locked whole databases and relied on memory-mapped files.
The company was renamed MongoDB Inc. in 2013. In December 2014 it bought WiredTiger, the company of Keith Bostic and Michael Cahill (both earlier creators of Berkeley DB), and WiredTiger became the default engine in 3.2 (2015), bringing document-level concurrency, compression and checkpoints; MMAPv1 was removed in 4.2. Version 3.2 also introduced a Raft-like replication protocol. The managed Atlas service launched in 2016 and now produces most of the company's revenue. MongoDB went public in 2017. In October 2018 it moved the server from the AGPL to its own Server Side Public License (SSPL), mainly to stop cloud providers from selling it as a service; the OSI did not approve the SSPL as open source, and some Linux distributions dropped MongoDB. AWS answered with DocumentDB, an API-compatible service built on its own storage.
Correctness work followed. Version 4.0 (2018) added multi-document transactions inside a replica set and 4.2 (2019) across shards. Jepsen's 2020 analysis of 4.2.6 by Kyle Kingsbury found that, under weak defaults, transactions could lose writes, and that even the strongest settings showed anomalies such as read skew. This pushed MongoDB to fix bugs and make w: "majority" the default write concern in 5.0 (2021). Later releases added live resharding (5.0), time-series collections, Queryable Encryption (7.0, 2023) and a much faster 8.0 (2024). The company bought the embedding-model company Voyage AI in early 2025, Chirantan "CJ" Desai replaced Dev Ittycheria as CEO in November 2025, and 9.0 shipped in September 2026 together with Atlas Infinite, a preview that separates compute from storage.
how: Start with a single node. WiredTiger stores each collection as a B-tree keyed by an internal record ID, with the BSON documents in the leaf pages, and each index as another B-tree mapping index keys to record IDs. The _id field always has a unique index. Data in memory lives in the WiredTiger cache (by default about half of RAM minus 1 GB) in an uncompressed, update-friendly form; on disk, pages are compressed (Snappy for data and prefix compression for indexes by default). Concurrency is optimistic and per document: two operations on different documents never block each other, and if two operations change the same document, one gets an internal write conflict and is retried. Readers use MVCC snapshots, so they see a consistent view without blocking writers.
Durability uses two mechanisms, as in most B-tree engines. Every change is written to a journal (a write-ahead log), which is flushed to disk in group commits, by default every 100 ms or immediately when a write asks for j: true. Every 60 seconds WiredTiger writes a checkpoint: a consistent snapshot of all B-trees written to new pages, after which older journal files can be removed. After a crash, the node opens the last checkpoint and replays the journal from that point.
Replication is the first idea from the nosql concept. A replica set has one primary and usually two or more secondaries (at most 50 members, of which at most 7 vote). Every write on the primary is also written to the oplog, as an idempotent record such as "set field status to 'paid' in document 42". Secondaries pull the oplog, apply it in batches, and report how far they have come. If the primary stops sending heartbeats for 10 seconds (the default election timeout), a secondary starts an election in a new term, as in Raft, and the member with the most recent oplog that wins a majority of votes becomes primary. A former primary that comes back with writes that never reached a majority must roll them back. This is why write concern matters. With w: 1, the client is acknowledged as soon as the primary has applied the write, and that write can later be rolled back. With w: "majority", the default since 5.0, the client waits until a majority has the write in its journal, and then it survives any single failover.
Reads have their own knobs. Read preference decides which member serves a read (primary, or a secondary for lower load at the cost of staleness). Read concern decides what the read may see: "local" returns the newest data on that node, even if it might be rolled back; "majority" returns only data a majority has stored; "linearizable" also confirms the primary is still primary. Causally consistent sessions attach a cluster time to each operation so that a client always reads its own writes, even from a secondary.
Sharding is the second idea from the nosql concept. A sharded cluster has several shards (each a replica set), a config server replica set that stores the routing table, and mongos routers. The shard key splits a collection into chunks, contiguous key ranges of up to 128 MB by default since 6.0. With a ranged key, nearby key values sit in the same chunk; with a hashed key, MongoDB hashes the value first, so writes spread evenly but range queries on the key lose locality. The balancer moves chunks between shards to even out data, and since 5.0 you can reshard a collection to a new key while it stays online. mongos caches the routing table. A query that includes the shard key goes to one shard (a targeted query); a query without it must go to every shard and merge the results (scatter-gather).
Transactions add relational guarantees on top. A single-document update is always atomic, including changes to nested arrays. A multi-document transaction uses snapshot isolation: it reads from one snapshot and, at commit, fails with a write conflict if another transaction changed the same documents. If it touches several shards, mongos runs two-phase commit, with one shard acting as coordinator. By default a transaction may last at most 60 seconds, because WiredTiger must keep all versions it might need in its cache. The query language sits above all this: filters on any field, an aggregation pipeline of stages ($match, $group, $lookup for joins, $unionWith), change streams built on the oplog, and in Atlas and recent self-managed versions, $search and $vectorSearch served by a separate search process (mongot) built on Apache Lucene.

example: An IoT platform stores sensor readings: 50,000 inserts per second, each document about 1 KB, from 2 million devices. The team plans 10 shards. The first design uses the shard key { ts: 1 }, the reading timestamp. Every new reading has a larger timestamp than the last, so every insert lands in the chunk with the highest range, on one shard. That shard receives 50,000 inserts per second while nine shards sit idle, and the balancer keeps splitting and moving chunks behind it. This is the classic monotonic shard key mistake.
The second design uses { device_id: "hashed" }. Hashing spreads devices evenly, so each shard receives about 50,000 / 10 = 5,000 inserts per second, or about 5 MB per second of new data. The query "readings of device D in the last hour" includes the shard key by equality, so mongos sends it to one shard; an index on { device_id: 1, ts: -1 } then finds the hour's readings with one index range scan. The query "average temperature of all devices in the last 5 minutes" has no device_id, so it goes to all 10 shards, each scans its own part with an index on ts, and mongos merges 10 partial results. That is acceptable for a dashboard every minute, but not for 10,000 requests per second.
A third design avoids one document per reading. A "bucket" document holds one device's readings for one hour. At one reading per minute, that is 60 readings of about 100 bytes, so 6 KB per document instead of 60 documents of 1 KB. The number of documents falls by 60 times, index entries fall by the same factor, and reading a device's hour is one document fetch. (Time-series collections do this bucketing automatically.) The limit is the 16 MB document size: an unbounded array, such as every reading a device has ever sent, would reach 16 MB after about 160,000 readings of 100 bytes, which is why buckets are bounded by time.
Last, durability cost. The replica set spans three availability zones with about 1 ms round trips between them. With w: 1, an insert is acknowledged after the primary applies it in memory: roughly 0.3 ms. With w: "majority", the primary waits until one secondary has pulled the oplog entry and journaled it: roughly 2–3 ms. The client gets durability across a zone failure for about 2 ms more per write. Because many writes are in flight at once, throughput barely changes; only latency per write increases.
intuition: Keep each customer's whole folder in one drawer, instead of filing every page in a different cabinet and collecting the pages each time you need them.
The design is natural when most operations touch one business object at a time. An order, a user profile or a device's hour of readings is read and written together, so storing it together turns many index lookups and joins into one B-tree lookup and one atomic update. Once data is grouped into self-contained documents, splitting it across machines is easy: choose a key, give each machine a range, and send each request where its key lives. Replica sets then add the familiar primary-plus-copies pattern for failover. Everything costly in MongoDB (scatter-gather queries, $lookup joins, cross-shard transactions) appears exactly where data that belongs together was not stored together.
mistakes: People often think MongoDB has no schema. In fact every application has a schema; MongoDB only stops the database from enforcing it unless you ask. Without JSON Schema validation and disciplined code, a collection slowly fills with old, partial and misspelled shapes that every reader must handle.
People often think MongoDB cannot do transactions. Single-document updates have always been atomic, and multi-document ACID transactions work in replica sets since 4.0 and across shards since 4.2. They are more expensive than single-document writes, though, and are limited to 60 seconds by default, so a good data model still keeps most invariants inside one document.
People often think a write acknowledged by MongoDB is safe. With w: 1, an acknowledged write can be rolled back if the primary fails before a secondary copies it. Only w: "majority" (the default since 5.0, but often overridden by older code or drivers) guarantees the write survives a failover. Reads at read concern "local" can also return data that is later rolled back.
People often think sharding fixes performance problems. A bad shard key (monotonic, low cardinality, or missing from most queries) creates hot shards or scatter-gather queries, and adding shards does not help. Changing the key later is possible with resharding since 5.0, but it copies the whole collection and needs large spare capacity.
friction: Modelling is the main cost. Embedding works until data is shared across many parents or grows without bound; then you need references and $lookup, which is slower and less flexible than a relational join, especially across shards. Denormalized copies of data must be kept in sync by the application. Large documents that are updated often are expensive, because the engine keeps versions of them in cache and rewrites each one in full when its page goes to disk, and the 16 MB limit is a hard wall.
Operations need care. The working set (indexes plus hot documents) must fit in the WiredTiger cache, or latency rises sharply as pages are read and evicted. Long-running transactions and long snapshot reads pin old versions in the cache and can create cache pressure for everyone. Elections take seconds, during which writes fail and drivers must retry (retryable writes are on by default). In a sharded cluster, the balancer, chunk migrations and orphaned documents add moving parts, and scatter-gather queries grow more expensive with every shard.
Licensing is a business constraint: the SSPL is not an open-source license by the OSI definition, and cloud vendors offer compatible but different services (Amazon DocumentDB, Azure Cosmos DB for MongoDB) that do not support every feature or behave the same under failure. Finally, the default write concern and read concern pair still does not give linearizable reads; you must choose stronger settings when correctness depends on them.
practice: Design documents around your queries: embed data that is read together and has bounded size, reference data that is shared or unbounded, and use the "bucket" pattern for time-series or event data. Add JSON Schema validation to every important collection. Build indexes for every frequent query and check them with explain(); compound indexes should follow the equality, sort, range order of fields.
Use w: "majority" for writes that matter and read concern "majority" (or a causally consistent session) when a reader must not see rolled-back data. Keep transactions short and few; if you need many multi-document transactions, check whether a different document model or a relational database fits better. Leave retryable writes and reads on.
Shard only when one replica set is not enough, which with modern hardware is often several terabytes and tens of thousands of writes per second. Choose a shard key with high cardinality and even write distribution that appears in most queries, often a compound of a tenant or device ID with a time field, or a hashed ID. Monitor cache usage and eviction, replication lag, oplog window (how many hours of history the oplog holds, which limits how long a secondary may be down), slow queries and chunk balance.
When upgrading to 9.0, test queries against the new default per-operation memory limit (1 GB or 20% of memory) and the 10,000 open-transaction limit, and run your own benchmarks rather than relying on vendor numbers.
quiz: What does a MongoDB shard key decide, and what happens to a query that does not include it? || The shard key decides which chunk, and therefore which shard, holds each document. A query without the shard key cannot be routed to one shard, so mongos sends it to every shard and merges the results (scatter-gather).
How does a replica set choose a new primary, and why can an acknowledged write be lost with w: 1? || If secondaries stop hearing from the primary for the election timeout (10 s by default), one calls an election in a new term and the member with an up-to-date oplog that wins a majority becomes primary. A write acknowledged with w: 1 may exist only on the old primary; if it never reached a majority, it is rolled back when that node rejoins.
Why does WiredTiger limit multi-document transactions to 60 seconds by default? || A transaction reads from one snapshot, so WiredTiger must keep every older document version that the snapshot might need in its cache. Long transactions pin more and more old versions, creating cache pressure for all operations, so a time limit protects the whole server.
A collection receives 50,000 inserts per second across 10 shards. What load does each shard get with a monotonic timestamp shard key versus a hashed device ID? || With a monotonic timestamp, all inserts go to the chunk holding the highest range, so one shard takes about 50,000 inserts per second. With a hashed device ID, writes spread evenly, about 5,000 per shard.
A blog stores comments embedded in the post document. When is that a good choice and when should comments live in their own collection? || Embedding is good when a post has a bounded, modest number of comments that are read together with it, since one read returns everything atomically. Popular posts with unbounded comments risk the 16 MB limit and expensive rewrites of a large document, so a separate collection keyed by post ID, with an index, is safer there.

@@ cassandra
value: Apache Cassandra is a distributed wide-column database built for very high write throughput and for staying available when machines, racks or whole data centres fail. There is no primary node and no single point of failure: every node can accept any read or write, data is copied to several nodes, and the client chooses per query how many copies must answer. Apple, Netflix, Uber and many banks and telecom companies run clusters of hundreds or thousands of nodes, mostly for workloads that write a lot and read by key: messaging, user activity, device data, fraud signals and time series.
It stands on two lower concepts. The first is the distributed key-value and wide-column store (the "nosql" family), and in particular Amazon's Dynamo design. From Dynamo, Cassandra takes consistent hashing to place data on a ring of nodes, replication to N nodes, tunable read and write quorums, and the repair tools that bring replicas back into agreement (hinted handoff, read repair, Merkle-tree anti-entropy). From Google's Bigtable it takes the data model (rows grouped into partitions, with sorted columns inside them) and the LSM-tree storage engine (commit log, memtable, immutable SSTables, compaction). The second lower concept is the JVM: Cassandra is written in Java, which gives it portable, mature networking and concurrency libraries and a large tooling ecosystem, but also makes garbage-collection pauses a central concern for tail latency.
For the layer above, Cassandra provides a store that keeps accepting writes during network partitions and node failures, grows almost linearly by adding nodes, and replicates across regions without any external tool. The price is a query-first data model: you design one table per query, with no joins and limited secondary indexing. It is worth understanding deeply now because the project is changing its foundations. Cassandra 5.0 (2024) added storage-attached indexes, vector search and new trie-based storage formats, and Cassandra 6.0, in alpha during 2026, adds Accord, a leaderless protocol for multi-partition ACID transactions, and replaces gossip-based cluster metadata with a transactional metadata log.
terms: Partition key — the part of the primary key that is hashed to a token and decides which nodes store the row.
Clustering columns — the rest of the primary key; they sort rows inside one partition on disk.
Token ring — the space of hash values (−2^63 to 2^63 − 1 with the Murmur3 partitioner) divided among nodes.
Virtual nodes (vnodes) — many small token ranges per node (16 by default since 4.0), so data and load spread evenly.
Replication factor (RF) — the number of nodes that store each partition, set per keyspace and per data centre.
Consistency level — how many replicas must answer a read or write: ONE, QUORUM, LOCAL_QUORUM, ALL and others.
Memtable and SSTable — the in-memory sorted buffer of recent writes, and the immutable sorted file it is flushed to.
Compaction — background merging of SSTables to remove old versions and deleted data and to reduce the files a read must check.
Tombstone — a marker that records a deletion; it must be kept long enough (gc_grace_seconds, 10 days by default) to reach every replica.
Repair — the process that compares replicas with Merkle trees and copies missing or newer data between them.
history: Avinash Lakshman, one of the authors of Amazon's Dynamo paper, and Prashant Malik built Cassandra at Facebook in 2007–2008 to power Inbox Search, which needed to store a reverse index of hundreds of millions of users' messages with very high write rates. Facebook open-sourced it in July 2008. Their paper, "Cassandra: A Decentralized Structured Storage System" (LADIS 2009, published in 2010), described it plainly as Dynamo's distribution combined with Bigtable's data model and storage. Facebook itself later moved its messaging to HBase, but Cassandra entered the Apache Incubator in 2009 and became a top-level Apache project in February 2010, with Jonathan Ellis as project chair. Ellis co-founded Riptano, later DataStax, to sell support and an enterprise edition.
The early API (Thrift) was low level. CQL, an SQL-like language, arrived in 0.8 (2011) and became the main interface with CQL3 in version 1.2 (2013). Version 2.0 (2013) added lightweight transactions using Paxos. Version 3.0 (2015) rewrote the storage engine around CQL rows. Version 4.0 (July 2021) came after a long stabilization effort with extensive testing, and added zero-copy streaming, audit logging and Java 11 support. Version 4.1 (2022) improved Paxos and added guardrails. Version 5.0 (September 2024) added storage-attached indexes (SAI), vector search, trie-based memtables and SSTables, the Unified Compaction Strategy and Java 17 support.
Rivals pushed the design too. ScyllaDB (2015) reimplemented Cassandra's API in C++ with a thread-per-core design to avoid garbage-collection pauses, and Discord described in 2023 how it moved trillions of messages from Cassandra to ScyllaDB because of GC pauses, hot partitions and repair cost. IBM completed its purchase of DataStax in May 2025. In 2026 the community is testing Cassandra 6.0 alphas with Accord transactions and Transactional Cluster Metadata, while 5.0.x (5.0.9 in August 2026) is the current stable line.
how: Placement comes from the nosql concept. Each row's partition key is hashed with Murmur3 into a 64-bit token. The token space forms a ring, and each node owns several token ranges (vnodes). With replication factor 3, a partition is stored on the node that owns its token and on the next two distinct nodes clockwise on the ring; with NetworkTopologyStrategy, replicas are also spread across racks and data centres. Every node knows the whole ring, so any node can act as coordinator for any request. Membership and node state have traditionally spread by gossip: once per second each node exchanges state with a few random peers, so news reaches the whole cluster in a few rounds. A failure detector (phi accrual) marks a node down when its heartbeats stop arriving as expected.
A write goes from the client to a coordinator, which sends it to all replicas at once and waits only for as many acknowledgements as the consistency level requires. Each replica appends the write to its commit log (by default synced to disk every 10 seconds, so a single node can lose the last few seconds; the other replicas cover that), inserts it into the memtable, and replies. Nothing is read before writing, so writes are very fast and an UPDATE is the same as an INSERT. Every cell carries a write timestamp, and when two versions of a cell meet, the newer timestamp wins (last write wins). If a replica is down, the coordinator stores a hint and replays it when the node returns, for up to 3 hours by default.
Storage on each node is an LSM tree, the Bigtable half of the design. When a memtable is full, it is flushed as an immutable SSTable, sorted by token and then by clustering columns. Each SSTable has a Bloom filter, a partition index and compression metadata. A read on a replica checks the memtable and every SSTable whose Bloom filter says the partition may be present, then merges the cells by timestamp. Compaction merges SSTables in the background so reads touch fewer files. The strategy is chosen per table: size-tiered (merge files of similar size, good for writes), leveled (keep files in non-overlapping levels, good for reads), time-window (one bucket per time window, ideal for time series with TTL), and since 5.0 unified compaction, which can be tuned between these behaviours.
Reads use the same consistency levels. For QUORUM with RF 3, the coordinator asks the fastest replica for the data and another replica for a digest (a hash) of it. If they match, it returns the data. If not, it fetches full data from both, returns the newest cells and writes them back to the stale replica (read repair). Consistency comes from overlap: if the write consistency level W and read consistency level R satisfy R + W > RF, every read meets at least one replica that has the latest acknowledged write. LOCAL_QUORUM counts only replicas in the local data centre, which keeps latency low while other regions catch up asynchronously.
Deletes are writes too. A DELETE writes a tombstone with a timestamp. Compaction can remove the tombstone and the data it covers only after gc_grace_seconds (10 days by default). Repair must run on every node within that window. If a replica missed the delete and the tombstone is purged before repair, that replica's old value comes back to life (a "zombie"). Repair builds Merkle trees (trees of hashes over token ranges) on each replica, compares them, and streams only the ranges that differ. Incremental repair marks repaired SSTables so later repairs scan less, and Cassandra 6.0 builds repair scheduling into the server.
For conditional updates (INSERT ... IF NOT EXISTS, UPDATE ... IF balance = 100), Cassandra runs lightweight transactions on a single partition using Paxos among its replicas. They cost several round trips (Cassandra 4.1's improved Paxos roughly halved them) and should be used sparingly. Cassandra 6.0's Accord protocol generalizes this to strict-serializable transactions across partitions, using timestamps from loosely synchronized clocks and a leaderless fast path that commits in one round trip when there is no conflict.
The JVM concept shapes operations. Memtables, caches, Bloom filters and compaction all create objects or use memory, and a long garbage-collection pause makes a node miss deadlines or look dead to gossip. Cassandra moves large structures off the Java heap (off-heap memtables, Bloom filters, compression metadata, the new trie structures), and with Java 17 operators can use low-pause collectors such as ZGC or tuned G1.

example: A chat service stores messages in this table: PRIMARY KEY ((channel_id, day), message_id), with message_id a time-ordered ID sorted newest first. A busy channel receives 1,000 messages per hour, each about 500 bytes. One day of one channel is then 24 × 1,000 × 500 bytes = 12 MB, which is a healthy partition size (a common guideline is to stay below about 100 MB). If the partition key were only channel_id, a channel active for a year would grow to 365 × 12 MB ≈ 4.4 GB in one partition on the same three nodes: too large to compact, repair and cache efficiently, and a permanent hot spot. Adding day to the partition key is called bucketing.
The cluster has 12 nodes in one data centre, RF = 3, and writes and reads use LOCAL_QUORUM, which here means 2 of 3. Since 2 + 2 > 3, every read overlaps at least one replica that took the latest acknowledged write. If one of the three replicas is down, writes and reads still succeed with the other two. If two are down, LOCAL_QUORUM requests for that partition fail; ONE would still succeed but could return old data.
Now throughput. The service writes 300,000 messages per second at peak. Each message is stored 3 times, so the cluster performs 900,000 replica writes per second, about 75,000 per node. Each write is a sequential commit-log append plus a memtable insert, which a modern node with NVMe disks handles, but compaction must keep up: 900,000 × 500 bytes = 450 MB per second of new data across the cluster, about 37 MB per second per node, and leveled compaction may rewrite each byte about 10 times, so roughly 370 MB per second of compaction I/O per node. With size-tiered or time-window compaction the rewrite factor is lower. This is the real capacity calculation for an LSM store.
Last, deletes. A moderator deletes 50,000 messages from one channel-day. These are 50,000 tombstones. A client then reads the newest 50 messages of that day. The read must scan past every tombstone that sorts before the live rows, and Cassandra warns at 1,000 tombstones per query and aborts at 100,000 by default. A single range tombstone (DELETE ... WHERE channel_id = ? AND day = ? AND message_id > X) would have been one marker instead of 50,000.
intuition: A group of equal clerks who all keep copies of the same ledgers; any clerk takes your entry, passes it to the others who hold that ledger, and they compare notes later to fix anything one of them missed.
The design follows from one decision: never make a write wait for a single special machine. If every node can coordinate, and data is placed by hashing, there is no leader to fail over and no central directory to overload. If replicas only append and timestamp each value, there is nothing to coordinate at write time; disagreements are resolved later by "newest wins". The LSM tree is the natural storage for this, because it turns every write into a sequential append and pushes the cost of organizing data into background compaction. Tunable consistency then lets each query decide how much agreement it needs, instead of forcing one global answer.
mistakes: People often think QUORUM makes Cassandra strongly consistent. It gives overlap between reads and writes that use quorums, but writes are still last-write-wins by timestamp, a failed QUORUM write may still be applied on some replicas, and concurrent writes to the same cell are not isolated. For compare-and-set logic you need lightweight transactions (or Accord in 6.0).
People often think a Cassandra table can be queried like a SQL table. Efficient queries must name the partition key, and can filter or sort only along clustering columns. ALLOW FILTERING or secondary indexes on high-cardinality columns can turn a query into a scan of the cluster. You design one table per query and write the same data to several tables.
People often think deletes free space at once. A delete writes a tombstone, which uses space and slows reads until compaction removes it after gc_grace_seconds. Workloads that delete heavily, such as queues, are a poor fit for Cassandra.
People often think repair is optional maintenance. Without regular repair within gc_grace_seconds, replicas that missed deletes can resurrect deleted data, and replicas that missed writes stay inconsistent. Repair is part of correctness, not just tidiness.
friction: Data modelling is the first cost. Every new query pattern may need a new table, and denormalized copies must be written by the application, often with logged batches to keep them together. Partition sizing is a constant concern: a hot or oversized partition is served by only RF nodes, no matter how large the cluster is.
Operations are the second cost. Repairs, compaction tuning, tombstone management, and adding or removing nodes (which streams token ranges) all need skill and monitoring. Garbage-collection pauses on the JVM have long caused latency spikes at the 99th percentile, which is the main reason ScyllaDB exists. Clock skew between clients or nodes can make a later write lose to an earlier one under last-write-wins. Gossip-based schema and membership changes have caused disagreements in large clusters, which Transactional Cluster Metadata in 6.0 aims to fix.
Finally, consistency and transactions. Until Accord ships in a stable release, there are no multi-partition transactions; lightweight transactions are slow and limited to one partition. Secondary indexing improved a lot with SAI in 5.0, but analytical queries still belong in Spark or a warehouse fed from Cassandra. Accord itself is new, and its performance and failure behaviour in large production clusters are still being learned in 2026.
practice: Start from the queries. For each query, design a table whose partition key is in the WHERE clause by equality, whose clustering columns give the needed order, and whose partitions stay well below about 100 MB; add a time bucket to the partition key for unbounded data. Use NetworkTopologyStrategy with RF = 3 per data centre, and LOCAL_QUORUM for both reads and writes as a default.
Choose compaction per table: time-window compaction for time series with TTL, leveled for read-heavy tables with updates, and unified compaction on 5.0 when you want one tunable strategy. Avoid patterns that create many tombstones (frequent deletes, writing nulls, using tables as queues); use TTLs and range deletes instead.
Run repair on a schedule that finishes within gc_grace_seconds, using a tool such as Cassandra Reaper on versions before 6.0. Monitor p99 latency, pending compactions, dropped messages, tombstone warnings, partition size histograms and GC pause times. On 5.0, run Java 17 with a low-pause collector, and keep enough free disk (often 30–50%) for compaction.
Use lightweight transactions only for rare operations that truly need compare-and-set, such as claiming a username. If most of your workload needs joins, ad-hoc queries or multi-row transactions, choose a relational or distributed SQL database instead; Cassandra fits best when writes are heavy, access is by key, and availability matters more than immediate consistency.
quiz: Which lower designs does Cassandra combine, and what does each contribute? || It takes Dynamo's distribution (consistent hashing, replication, tunable quorums, hinted handoff and repair) and Bigtable's data model and LSM storage (partitions with sorted columns, commit log, memtables, SSTables, compaction). It runs on the JVM, which shapes its memory management and latency.
Why does R + W > RF give a read the latest acknowledged write? || The W replicas that acknowledged the write and the R replicas the read contacts are both subsets of the same RF replicas. If R + W is larger than RF, the two subsets must share at least one replica, and timestamp comparison returns that replica's newer value.
How can a deleted row come back to life in Cassandra? || A replica that was down misses the tombstone. If the tombstone is compacted away on the other replicas after gc_grace_seconds and no repair copied it to the stale replica first, the old value on that replica is now the newest version and is returned again.
A table with RF = 3 receives 200,000 writes per second of 1 KB on a 10-node cluster. How many replica writes and bytes per second does each node handle? || 200,000 × 3 = 600,000 replica writes per second, about 60,000 per node. That is about 60 MB per second of new data per node, before compaction rewrites it several more times.
When would you choose Cassandra over a distributed SQL database such as CockroachDB? || When the workload is write-heavy, accessed by known keys, must stay writable during failures and network partitions, and can accept last-write-wins and per-query consistency. Choose distributed SQL when you need multi-row transactions, joins or ad-hoc queries with serializable guarantees and can accept consensus latency on every write.

@@ dynamodb
value: Amazon DynamoDB is a fully managed key-value and document database. You create a table, choose a primary key, and read and write items through an HTTPS API; there are no servers, versions, disks or replicas for you to manage. Its main promise is predictable latency at any size: a request for one item takes single-digit milliseconds whether the table holds 1 GB or 1 PB, and whether it serves 10 requests per second or millions. Amazon's own retail systems depend on it. During Prime Day 2025, Amazon systems made tens of trillions of DynamoDB calls, with a peak of 151 million requests per second.
The concept it stands on is the distributed key-value and wide-column store (the "nosql" family). DynamoDB keeps that family's core idea: data is spread across many machines by hashing a key, each piece is replicated across failure domains, and the data model is designed around known access patterns, with no joins and few query shapes. But it changes the replication model. Amazon's 2007 Dynamo paper used leaderless replication with sloppy quorums and vector clocks, which pushed conflict handling onto applications. DynamoDB instead gives every partition a leader elected with Multi-Paxos, so each item has one order of writes, strongly consistent reads are possible, and conditional writes and transactions work.
For the layer above, DynamoDB is a building block for serverless and microservice back ends: Lambda functions, API Gateway, Step Functions, and event pipelines that read its change stream. It removes capacity planning for storage, patching, failover and backups, and it bills per request or per provisioned unit. It is worth understanding deeply now for two reasons. Its cost model and its throughput limits per partition decide whether a design is cheap or ruinously expensive. And the October 2025 outage in us-east-1, caused by a race condition in DynamoDB's own DNS automation, showed how many other services, inside and outside AWS, quietly depend on it.
terms: Partition key — the attribute that is hashed to choose an item's partition; every item has one.
Sort key — an optional second key attribute; items with the same partition key are stored together, sorted by it.
Item collection — all items that share one partition key; a Query reads a range of one item collection.
Partition — a slice of a table's key space, held by a replication group of three storage replicas in three Availability Zones.
RCU and WCU — capacity units: one RCU is one strongly consistent read per second of up to 4 KB; one WCU is one write per second of up to 1 KB.
Global secondary index (GSI) — a separately partitioned copy of selected attributes under a different key, updated asynchronously.
Conditional write — a write that succeeds only if a condition on the current item is true, such as "version = 7".
DynamoDB Streams — an ordered log of item-level changes, kept for 24 hours, used for triggers and change data capture.
Global table — a table replicated across AWS Regions, with asynchronous multi-writer or, since 2025, strongly consistent replication.
Throttling — the rejection of requests that exceed table, index or partition limits, returned as a retryable error.
history: In the 2004 holiday season, parts of Amazon's retail site struggled because a central relational database could not scale. Engineers built Dynamo, an internal key-value store that stayed writable during failures, and described it in the 2007 SOSP paper "Dynamo: Amazon's Highly Available Key-value Store" by Giuseppe DeCandia, Werner Vogels and colleagues. The paper shaped a generation of databases, including Cassandra and Riak. Inside Amazon, though, many teams did not adopt Dynamo, because each team had to run its own installation. They preferred SimpleDB (2007), a managed service, even though it had small table limits and unpredictable latency.
DynamoDB, launched on 18 January 2012, combined the two lessons: Dynamo's scalable, partitioned design and SimpleDB's fully managed model. Swami Sivasubramanian, a co-author of the Dynamo paper, was one of its leaders. Features arrived steadily: global secondary indexes (2013), JSON document support (2014), Streams (2015), global tables, time-to-live and the DAX cache (2017), on-demand capacity and ACID transactions (2018), PartiQL and export to S3 (2020), and transactions of up to 100 items (2022). In 2022 the team published a detailed USENIX ATC paper by Mostafa Elhemali and colleagues on how the service really works, and in 2023 a second paper on its transaction protocol.
Recent years focused on cost and multi-region strength. On 1 November 2024, on-demand throughput prices fell by 50% and global-table replication prices by up to 67%. On 30 June 2025, global tables with multi-Region strong consistency became generally available, giving a recovery point objective of zero. On 19–20 October 2025, a race condition between two instances of DynamoDB's DNS automation left the regional endpoint in us-east-1 with an empty DNS record. DynamoDB API errors lasted from 11:48 PM to 2:40 AM Pacific time, and many dependent AWS services took much longer to recover. AWS disabled that automation worldwide until the race was fixed.
how: A request first reaches a request router. The router authenticates it, checks permissions, and looks up which partition holds the key in a metadata service with an in-memory cache. It then sends the request to the storage node that leads that partition. The partition key is hashed, and each partition owns a contiguous range of hash values, so items spread evenly when keys are diverse. Inside a partition, items with the same partition key are stored together in sort-key order. This is what makes a Query ("all orders of customer 42 from October, newest first") one sequential range read on one partition.
Each partition is a replication group of three storage replicas, one in each of three Availability Zones. One replica is the leader, elected with Multi-Paxos and holding a time-limited lease. For a write, the leader checks any condition, assigns the write a position in the partition's write-ahead log, and sends the log record to its two peers. Once two of the three replicas, including the leader, have stored the record durably, the write is acknowledged. Each storage replica keeps the log plus a B-tree of the items. A strongly consistent read goes to the leader, which knows it has every acknowledged write; an eventually consistent read can go to any replica and costs half as much. If the leader fails, the lease runs out and a peer becomes leader. To avoid needless elections caused by "gray" partial failures, a replica that cannot reach the leader first asks the others whether they can.
Replacing a failed replica could take a long time, because the B-tree may hold many gigabytes. So DynamoDB first adds a log replica, which stores only recent log records and can join the group in seconds, keeping the write quorum healthy while a full replica is rebuilt. Write-ahead logs are also archived to S3, which provides backups and point-in-time recovery for the last 35 days. Every log record carries checksums, and background jobs compare replicas and archived logs to catch silent corruption.
Partitions split automatically. A partition holds up to roughly 10 GB, and serves at most 3,000 RCU and 1,000 WCU per second. When it grows past its size limit, or when traffic exceeds what it can serve, DynamoDB splits it, choosing the split point from the observed distribution of key traffic rather than the middle of the key range. Admission control decides whether to accept each request. Early DynamoDB divided a table's provisioned capacity evenly among partitions, so skewed traffic was throttled even when the table had spare capacity. The 2022 paper describes the fixes: bursting with unused capacity saved from the last 5 minutes, adaptive capacity that shifts throughput to hot partitions, global admission control that tracks capacity for the whole table with token buckets, and splitting partitions for heat. Today a single partition key can still use only one partition's limits.
Secondary indexes are implemented as other tables. A global secondary index has its own partition key and its own partitions. When a base-table write changes an indexed attribute, the change is sent asynchronously to the index, so GSI queries are eventually consistent. If an index cannot keep up, DynamoDB throttles writes to the base table, so an under-provisioned index can slow the whole table. Local secondary indexes share the base table's partition key, are updated in the same write, and limit each item collection to 10 GB.
Transactions sit on top of single-item operations. TransactWriteItems can change up to 100 items, possibly in different tables. A transaction coordinator in the router fleet assigns a timestamp, sends a prepare message to the leader of each item's partition, which checks conditions and timestamp order, and commits only if all agree; otherwise the whole transaction is cancelled. Coordinators record progress in a durable ledger, so another coordinator can finish the work after a crash. There are no long-held locks, so conflicting transactions are cancelled rather than blocked, and each transactional operation costs twice the normal capacity units.
Changes leave the table through DynamoDB Streams, which records every item change in order per item and keeps it for 24 hours, or through Kinesis Data Streams. Global tables are built on this: by default, each Region accepts writes and replicates them asynchronously, typically within a second, and concurrent writes to the same item are resolved by last writer wins. With multi-Region strong consistency, a write must be stored in a second Region before it is acknowledged, using exactly three Regions (or two plus a witness), so every Region reads the latest data at the cost of cross-region latency on each write.

example: An ad-tech service counts impressions per campaign and stores user events. First, the events table. It receives 5,000 writes per second of 1 KB items, with partition key user_id and sort key event_time. Each write costs 1 WCU, so the table needs 5,000 WCU, at least 5 partitions' worth of write capacity, and with millions of users the load spreads evenly. In on-demand mode in us-east-1, writes cost $0.625 per million, so the monthly cost is 5,000 × 2,592,000 seconds ≈ 13 billion writes ≈ $8,100. With provisioned capacity at about $0.00065 per WCU-hour, 5,000 WCU for 720 hours costs about $2,340. At steady, predictable load provisioned capacity is roughly 3.5 times cheaper; on-demand wins when traffic is spiky or mostly idle.
Now add two global secondary indexes, each projecting the whole item. Every write now also updates two index tables, so the write cost triples: about 15,000 WCU in total. This is the most common surprise in DynamoDB bills. Projecting only the attributes each index query needs (KEYS_ONLY or INCLUDE) reduces the cost of each index write.
Next, reads. A dashboard reads 20,000 items per second of 6 KB each. A strongly consistent read of 6 KB costs ⌈6 / 4⌉ = 2 RCU, so 40,000 RCU. Eventually consistent reads cost half, 20,000 RCU. If the dashboard can accept data that is up to a second old, that halves the read bill.
Finally, the hot key. The impression counter for one large campaign uses partition key campaign_id and receives 8,000 increments per second. One partition key can use at most 1,000 WCU, so about 7,000 increments per second are throttled, even though the table has plenty of total capacity. The fix is write sharding. Use keys campaign_id#0 to campaign_id#9, pick a random suffix for each increment, and each key receives about 800 writes per second, under the limit. To read the total, the service reads 10 items, 10 × 1 RCU = 10 RCU, and adds them. If exact real-time totals are not needed, an even cheaper design batches increments in memory for 1 second and writes one update per server per second.
intuition: A huge locker hall run by a careful staff: you give your key, the desk tells you exactly which locker row holds it, and three guards in three buildings each keep a copy of every change before saying "done".
The design is natural once you accept one rule: every request names a key. With a key, the system can always compute which small group of three machines is responsible, so no request ever needs to talk to the whole fleet. Each group is small enough to run a simple, well-understood consensus protocol, and adding data only means adding more groups. Predictable latency follows from predictable work: a GetItem is one hash, one network hop and one B-tree lookup, no matter how large the table is. Everything the system refuses to do (joins, ad-hoc filters, unbounded scans) is exactly the work that would break that predictability.
mistakes: People often think DynamoDB is Dynamo as a service. In fact it shares the partitioning idea but not the replication model: each partition has a Multi-Paxos leader, writes are ordered per item, and strongly consistent reads, conditional writes and transactions are possible. Leaderless "sloppy quorums" and client-side conflict resolution are not part of it, except for last-writer-wins in multi-writer global tables.
People often think on-demand mode means unlimited throughput for any key. On-demand removes table-level planning, but each partition still serves at most 3,000 RCU and 1,000 WCU, so one hot partition key is throttled no matter the mode. Key design, not capacity mode, solves hot keys.
People often think a Scan with a filter is a cheap query. A Scan reads every item in the table (or segment) and charges for all data read, before the filter removes items. Filters reduce what you receive, not what you pay. Frequent access patterns need a key or an index.
People often think GSI reads are consistent with the base table. GSIs are updated asynchronously and support only eventually consistent reads. A read right after a write can miss the change, so read-your-write logic must use the base table.
friction: Access patterns must be known in advance. Single-table design, where many entity types share one table with overloaded keys so that one Query fetches related items, is efficient but hard to learn, hard to read and hard to change when new query patterns appear. Ad-hoc analytics are poor; teams export to S3 or use zero-ETL integrations into Redshift or OpenSearch. Items are limited to 400 KB, and transactions to 100 items and 4 MB.
Costs need modelling. GSIs multiply write costs, large items consume many units, on-demand pricing at steady high load costs several times more than provisioned capacity, and strongly consistent reads cost double. Throttling appears as retryable errors that the SDK hides with backoff until latency suddenly grows.
Operationally DynamoDB is very reliable, but it is also a shared dependency. The October 2025 us-east-1 outage showed that a fault in DynamoDB's control systems can stop many AWS services that are built on it; single-Region designs inherited that risk. Multi-Region designs help, but multi-writer global tables resolve conflicts by last writer wins, and strongly consistent global tables add cross-region latency to every write and are offered only in some Regions. Finally, there is vendor lock-in: the API, the capacity model and the surrounding services are AWS-specific, and moving off DynamoDB usually means redesigning the data model.
practice: Write down every access pattern first, with its frequency and latency need, and design keys and indexes to serve each one with GetItem or Query. Choose high-cardinality partition keys, put time or type in the sort key, and keep item collections bounded. Use write sharding or batching for hot counters.
Start new or unpredictable tables in on-demand mode; switch steady, high-volume tables to provisioned capacity with auto scaling, and consider reserved capacity for the base load. Project only needed attributes into GSIs, and keep items small by storing large blobs in S3 with a pointer in the item.
Use conditional writes with a version attribute for optimistic concurrency, and transactions only where several items must change together. Enable point-in-time recovery on important tables. Consume changes through Streams with Lambda or through Kinesis for analytics and search indexing.
Monitor throttled requests, consumed versus provisioned capacity, and the most-accessed keys (CloudWatch Contributor Insights shows them). For critical systems, decide explicitly between single-Region, multi-writer global tables and strongly consistent global tables, and test what your application does when the DynamoDB endpoint in one Region cannot be resolved.
quiz: What limits apply to a single DynamoDB partition, and why do they matter for key design? || A partition serves at most 3,000 RCU and 1,000 WCU per second and holds roughly 10 GB. All traffic for one partition key goes to one partition, so a very popular key is throttled at these limits regardless of the table's total capacity.
How does DynamoDB make a write durable before acknowledging it? || The partition leader assigns the write a place in its write-ahead log and sends the record to its two peer replicas in other Availability Zones. The write is acknowledged once two of the three replicas have stored it durably, as decided by Multi-Paxos.
Why are reads on a global secondary index only eventually consistent? || A GSI is a separately partitioned table. Base-table changes are propagated to it asynchronously, so for a short time after a write the index may not yet reflect it.
A table receives 2,000 writes per second of 3 KB items and has one GSI that projects all attributes. How many WCU does it consume? || Each 3 KB write costs ⌈3 / 1⌉ = 3 WCU, so 6,000 WCU on the base table, and the GSI write costs another 6,000. The total is about 12,000 WCU.
When is DynamoDB a poor choice compared with PostgreSQL? || When access patterns are unknown or change often, when you need ad-hoc queries, joins or aggregations, or when transactions span many rows. PostgreSQL handles flexible queries well; DynamoDB is best when every frequent request can be served by a key lookup or a range query on one partition.

@@ spanner
value: Google Spanner is a distributed SQL database that runs one logical database across many machines, data centres and continents, while giving transactions the strongest common guarantee: external consistency. That means transactions behave as if they ran one at a time, in an order that matches real time. If transaction T1 commits before T2 starts, anywhere in the world, T2 sees T1's effects and gets a later commit timestamp. Spanner was described in 2012 and has run Google's advertising system, Gmail metadata, Google Photos and many other services. By the end of 2024 Google said it handled over 4 billion queries per second at peak and more than 15 exabytes of data. Since 2017 it has also been sold as Cloud Spanner, and in 2026 Google announced Spanner Omni, an edition you can run outside Google Cloud.
The concept it stands on is distributed SQL (the "newsql" family): SQL and ACID transactions across many machines, built from data split into ranges, consensus replication for each range, multi-version storage with timestamps, and a commit protocol across ranges. Spanner is the system that defined this family, so the relationship runs both ways. From the general design it uses range partitioning, Paxos groups, two-phase commit and MVCC. What it adds is TrueTime, a clock service that reports time as an interval with a known error bound. With TrueTime, commit timestamps can respect real-time order without any central timestamp server, and read-only transactions can read a consistent snapshot from any sufficiently fresh replica without locks.
For the layer above, Spanner gives applications what used to require choosing between a sharded MySQL setup and a NoSQL store: horizontal scale, synchronous replication with zero data loss across zones or regions, SQL (GoogleSQL or a PostgreSQL dialect), secondary indexes, and transactions that never show anomalies. It matters to understand now because its ideas spread everywhere. CockroachDB, YugabyteDB and TiDB copy its architecture with ordinary clocks, AWS's Aurora DSQL uses a related time-based approach, and Spanner itself now adds graph, full-text and vector search on the same data.
terms: External consistency — if T1 commits before T2 begins in real time, T1's commit timestamp is smaller; also called strict serializability.
TrueTime — Google's clock API; TT.now() returns an interval [earliest, latest] that is guaranteed to contain the true current time.
ε (epsilon) — half the width of the TrueTime interval, the current clock uncertainty.
Commit wait — after choosing a commit timestamp s, the leader waits until TT.now().earliest > s before making the commit visible.
Split — a contiguous range of rows (by primary key) that is the unit of placement, replication and load balancing.
Paxos group — the replicas of one split, which agree on an ordered log of writes through Paxos; one replica is the leader.
Leader lease — a time-limited promise (10 seconds by default in the paper) that lets one replica act as leader without asking the others for each read.
Safe time — the timestamp up to which a replica knows it has every committed write, so it can serve reads at or below it.
Two-phase commit (2PC) — a protocol in which a coordinator asks all participants to prepare, then tells them all to commit.
Interleaved table — a child table stored physically inside its parent's rows (for example orders inside customers) so related rows share a split.
history: Google's ad system ran for years on a manually sharded MySQL setup. Resharding it was a large, risky project, and Bigtable (2006), which scaled well, offered only single-row transactions and eventual consistency between data centres. Megastore (2011) added transactions on top of Bigtable, but with poor write throughput. Spanner was built in the late 2000s to provide both scale and real transactions. The OSDI 2012 paper "Spanner: Google's Globally-Distributed Database" by James Corbett, Jeffrey Dean, Sanjay Ghemawat, Wilson Hsieh and others won the best paper award, mostly for TrueTime: the idea that a database could use carefully measured physical time, backed by GPS receivers and atomic clocks in every data centre, to order transactions.
The F1 paper (VLDB 2013) described how Google's AdWords moved from sharded MySQL to F1, a SQL layer on top of Spanner. Over the next years Spanner itself became a full SQL database, described in "Spanner: Becoming a SQL System" (SIGMOD 2017), which covered distributed query execution, restartable queries and a new columnar-style storage format called Ressi. Google launched Cloud Spanner in 2017, the same year Eric Brewer published "Spanner, TrueTime and the CAP Theorem", which explained that Spanner is technically a CP system (consistent under partitions) whose availability, above five nines, makes it look like CA in practice.
Later changes made it broader and cheaper. Smaller instances (processing units, from a tenth of a node) arrived in 2021, a PostgreSQL interface in 2021–2022, and in 2024 tiered editions, Spanner Graph, full-text search, vector search and geo-partitioning. In April 2026 Google announced Spanner Omni in preview: a downloadable edition that replaces atomic-clock TrueTime with a software time service and Google's Colossus file system with local disks.
how: Data is organized by primary key. Each table is sorted by its primary key, and the key space is cut into splits. Rows of an interleaved child table are stored right after their parent row, so a customer and all of that customer's orders sit in the same split. When a split grows large or hot, Spanner divides it and may move pieces between servers; this is automatic load-based splitting. Each split is replicated, typically with 3 replicas in 3 zones of one region, or 5 or more across several regions. The replicas form a Paxos group. Writes go to the leader, which appends them to a Paxos log; a write is durable once a majority of replicas has logged it. Storage underneath is a log-structured, multi-version store on Google's Colossus file system: every value is kept with the timestamp at which it was written.
TrueTime is the special ingredient. Each data centre has time master servers, most with GPS receivers and some with atomic clocks, which fail in different ways. A daemon on every machine polls several masters, rejects liars, and computes an interval that must contain the true time. Between polls, the interval widens at an assumed worst-case drift rate (200 microseconds per second in the paper). The 2012 paper reported ε as a sawtooth between about 1 and 7 ms, about 4 ms most of the time. The key property is not that clocks are perfect, but that the error is known and bounded.
A read-write transaction works like this. Reads go to the leader of each split involved, which takes read locks (Spanner uses two-phase locking with wound-wait to avoid deadlocks; older transactions win). Writes are buffered at the client. At commit, the client picks one involved group as coordinator. Each participant leader takes write locks, chooses a prepare timestamp larger than any timestamp it has already given, logs a prepare record through Paxos and reports to the coordinator. The coordinator chooses a commit timestamp s that is at least every prepare timestamp and at least TT.now().latest, logs the commit through Paxos, and then performs commit wait: it waits until TT.now().earliest > s. Only then does it release locks and tell the client and participants. A transaction that touches only one split skips 2PC and just uses that group's Paxos log.
Commit wait is what turns clock uncertainty into a correctness guarantee. When the wait ends, every correct clock in the world reads later than s. So any transaction that starts after T1's commit becomes visible will get a timestamp greater than s, because its own TT.now().latest is greater than s. Timestamp order therefore matches real-time order. The wait lasts about \( 2\varepsilon \), and it runs in parallel with the Paxos round to replicate the commit record, so with a few milliseconds of ε and multi-millisecond replication, much of it is hidden.
Read-only transactions take no locks at all. Spanner picks a read timestamp, normally TT.now().latest (or, for a single split, the timestamp of the last committed write), and reads the multi-version data as of that timestamp. Any replica can serve the read if its safe time has reached the read timestamp: it must have applied all Paxos writes up to that point and have no prepared-but-undecided transaction that could commit below it. Otherwise the replica waits briefly or asks the leader. Stale reads, for example "as of 15 seconds ago", can be served immediately by the nearest replica, which is how globally distributed applications get local read latency.
The SQL layer turns queries into distributed plans. A query is split along split boundaries, and a "distributed union" operator sends sub-plans to the servers holding each range and merges results. Queries can restart transparently after a server failure, because the plan knows which key ranges have been finished. Leader leases also make strong reads cheap: a leader holding a valid lease knows no other leader can exist and can answer from its own state. Schema changes are scheduled at a future timestamp and applied without blocking traffic.
Seen through the newsql concept, each lower piece has a clear job. Range partitioning lets the system grow by adding splits. Paxos per split gives durability and automatic failover without a single global log. MVCC timestamps let readers see a snapshot while writers continue. Two-phase commit makes multi-split transactions atomic. The SQL layer hides all of this behind tables and queries. Spanner's own contribution is the timestamp source: other systems in the family must either use a central timestamp oracle (as TiDB does) or accept clock uncertainty and restart some reads (as CockroachDB does), while Spanner bounds the uncertainty and waits it out.

example: Take a multi-region configuration with read-write replicas in two US regions about 10 ms apart, and a witness region, and use the paper's ε of 4 ms. A transaction T1 moves money between two accounts that live in different splits. At true time 100.000 s, the coordinator leader sees TT.now() = [99.996, 100.004]. Assume the participant's prepare timestamp was 100.001. The coordinator chooses s = max(100.001, 100.004) = 100.004.
Now it must wait until TT.now().earliest > 100.004. Since earliest is about true time minus 4 ms, that happens at true time about 100.008, so commit wait is about 8 ms. Meanwhile, the coordinator sends its commit record through Paxos. A majority requires one round trip to the other US region, about 10 ms. The commit wait (8 ms) finishes inside the replication time (10 ms), so it adds almost nothing. The client sees about 10–15 ms for the commit, plus earlier rounds for reads and prepare.
A second user, T2, reads the destination balance right after T1 replies. T2 begins at true time about 100.012, so its read timestamp is TT.now().latest ≈ 100.016, which is larger than s = 100.004. T2 sees T1's transfer. External consistency held without any machine asking a central clock.
Now the costs for a global user base. Suppose the leaders are in the US and a user in Europe, about 100 ms round trip away, makes a read-write transaction. Each read inside the transaction goes to a US leader (about 100 ms each), and the commit needs one more trip plus US replication. A transaction with two reads and a commit costs roughly 3 × 100 + 10 ≈ 310 ms. The same user doing a stale read "as of 10 seconds ago" from a European read-only replica pays about 5 ms. This is why Spanner applications place leaders near the users who write most, use geo-partitioning for regional data, read with bounded staleness when they can, and keep read-write transactions short.
Finally, key design. A table keyed by a timestamp or an increasing integer sends every insert to the last split, so one Paxos leader takes all the write load. If each split leader can handle a few thousand writes per second and the application inserts 30,000 rows per second, that one hot split becomes the bottleneck even on a 50-node instance. A UUIDv4 key, a hashed prefix, or Spanner's bit-reversed sequence spreads the inserts across all splits.
intuition: Two people who each know their watch may be wrong by up to 4 ms can still agree on order, if whoever acts first simply waits 8 ms before saying "done".
The design feels natural once you separate two problems: agreeing on what happened inside one piece of data, and agreeing on order across pieces. Paxos solves the first for each split, independently, so the system scales by adding more independent groups. The second problem usually needs a central sequencer, which becomes a bottleneck and a distance problem on a global system. TrueTime replaces that sequencer with physics: if every machine knows the current time within a bounded error, a transaction can choose a timestamp and wait out the error. Uncertainty is not hidden or ignored; it is measured, and its cost is paid as a few milliseconds of waiting, often overlapped with replication that has to happen anyway.
mistakes: People often think Spanner beats the CAP theorem. It does not: during a network partition, the minority side of a Paxos group cannot accept writes, so Spanner chooses consistency. It looks "always available" because Google's private network and redundant paths make such partitions very rare, as Eric Brewer explained in 2017.
People often think TrueTime means Google has perfectly synchronized clocks. TrueTime's value is that it reports its own error. Clocks still drift and are still uncertain by milliseconds; correctness comes from commit wait, which waits out that uncertainty, not from perfect time.
People often think every Spanner write pays a global round trip. Writes pay a majority round trip within the split's replica set. In a regional configuration that is a few milliseconds between zones; only multi-region configurations pay inter-region latency, and only for writes and strong reads, not for stale reads.
People often think distributed SQL removes the need for schema and key design. Monotonic keys still create hot splits, transactions that touch many splits still pay two-phase commit, and long read-write transactions still hold locks and get aborted by wound-wait. Interleaving and key choice remain central to performance.
friction: Writes cost more than in a single-node database. Every commit needs a Paxos majority, cross-split transactions add two-phase commit, and multi-region configurations add tens of milliseconds per write. Locking read-write transactions can abort under contention, so clients must retry; the client libraries do this automatically, which can hide repeated work. Large analytical scans compete with transactional traffic unless you use Data Boost or export to BigQuery.
TrueTime depends on Google's hardware and operations: GPS antennas, atomic clocks and monitoring in every data centre. Systems outside Google, such as CockroachDB and YugabyteDB, use hybrid logical clocks with larger assumed uncertainty and must sometimes restart reads instead of waiting. Spanner Omni's software time service is new, and its uncertainty depends on network round trips to a primary time server, so its behaviour in diverse customer environments is still being learned.
Cost and lock-in matter too. Spanner is priced per node or processing unit plus storage; smaller instances made it cheaper, but it is still more expensive than a single PostgreSQL server for modest workloads. Its SQL dialects (GoogleSQL and a PostgreSQL interface that lacks some PostgreSQL features and extensions) and its specific features make moving away a real migration. Finally, debugging performance needs Spanner-specific skills: reading lock statistics, split hot spots, and query plans with distributed unions.
practice: Choose Spanner when you need relational data with strong consistency beyond one machine, zero data loss across zones or regions, and very high availability, and when you are on Google Cloud or can run Spanner Omni. For a few terabytes and a few thousand writes per second in one region, a managed PostgreSQL is usually simpler and cheaper.
Design keys to spread writes: UUIDv4, hashed or bit-reversed sequences, or a well-distributed leading column such as a tenant ID. Use interleaved tables for parent-child data that is read and written together, so transactions stay inside one split. Keep read-write transactions short and avoid user interaction inside them.
Use read-only transactions or single reads for everything that does not write, and bounded-staleness reads (for example 10–15 seconds) when slightly old data is acceptable; they are served by the nearest replica without contacting leaders. Choose the instance configuration (regional, dual-region or multi-region) and the default leader region based on where writes come from. Use change streams to feed BigQuery, Pub/Sub or Kafka rather than running heavy analytics on the transactional instance.
Monitor CPU per instance (Google recommends keeping high-priority CPU well below 100%, around 65% for regional instances), lock wait and abort rates, hot splits in Key Visualizer, and commit latency. Use query statistics to find slow plans, and test retries and failover behaviour in your application before production.
quiz: What guarantee does external consistency give, and how is it stronger than serializability? || It guarantees that if T1 commits before T2 starts in real time, T1's timestamp is smaller and T2 sees its effects. Plain serializability only requires some serial order, which might not match real time.
Why does Spanner wait after choosing a commit timestamp? || The leader chose s ≥ TT.now().latest, but other clocks may be behind. Waiting until TT.now().earliest > s guarantees that s is in the past on every correct clock, so any transaction that starts afterwards gets a larger timestamp.
How can a read-only transaction run at a replica without taking locks? || It reads multi-version data at a fixed timestamp. A replica may serve it once its safe time has reached that timestamp, meaning it has applied every write and resolved every prepared transaction that could commit at or below it.
With ε = 3 ms and a Paxos round of 12 ms for the commit record, about how much latency does commit wait add? || Commit wait lasts about \( 2\varepsilon \) = 6 ms and runs in parallel with the 12 ms Paxos round, so it adds almost nothing. It would dominate only if \( 2\varepsilon \) were larger than the replication time.
A global app has writes mostly from Europe and reads from everywhere. How should it be configured? || Put the default leader region in Europe so writes pay only local or nearby replication, use geo-partitioning if regions own separate data, and serve most global reads with bounded-staleness reads from nearby replicas. Strong reads and read-write transactions from other continents will still pay the trip to the leader.

@@ cockroach
value: CockroachDB is a distributed SQL database that follows Google Spanner's design but runs on ordinary servers and clouds, without atomic clocks. It splits all data into ranges of up to 512 MiB, replicates each range with its own Raft group, and offers serializable ACID transactions across all of them. It speaks the PostgreSQL wire protocol, so most PostgreSQL drivers and many tools work unchanged. It is built to survive the loss of a disk, a machine, an availability zone or, with enough replicas, a whole region, while continuing to serve reads and writes; that is where the name comes from. Banks, payment companies, gaming platforms and SaaS vendors use it for systems of record that must scale beyond one machine or span regions.
It stands on two lower concepts. The first is distributed SQL (the "newsql" family): data split into key ranges, consensus replication per range, multi-version storage with timestamps, a distributed commit protocol, and a SQL layer on top. CockroachDB implements each piece with its own twist: Raft instead of Paxos, hybrid logical clocks instead of TrueTime, and a commit protocol (parallel commits) that needs only one round of consensus. The second is RocksDB. Every CockroachDB node stores its replicas in Pebble, a log-structured merge-tree (LSM) engine written in Go and modelled closely on RocksDB, which CockroachDB itself used until 2020. From RocksDB it inherits the memtable-plus-sorted-files design, levelled compaction, Bloom filters and the on-disk table format; Pebble keeps those ideas but drops features CockroachDB did not need and avoids the cost of calling C++ from Go.
For the layer above, CockroachDB gives application teams a single logical PostgreSQL-like database that grows by adding nodes, rebalances itself, and can pin rows to regions for latency or data-residency laws. It matters to understand now because it is the most widely used open design for "Spanner without special hardware", and its trade-offs show what you lose when clocks are uncertain: some transactions must restart, and applications must retry. The project is also active in 2026: leader leases became the default in v25.2, v26.2 (April 2026) made SQL triggers and buffered writes generally available, and since November 2024 self-hosted use is under a single enterprise license that is free only for companies below 10 million US dollars of annual revenue.
terms: Range — a contiguous slice of the sorted key space, up to 512 MiB by default, and the unit of replication and rebalancing.
Replica and Raft group — each range is copied to (usually) 3 or 5 nodes, and those replicas agree on a log of changes with Raft.
Leaseholder — the one replica allowed to serve consistent reads and propose writes for a range; normally also its Raft leader.
Hybrid logical clock (HLC) — a timestamp made of physical time plus a logical counter, which never goes backwards and follows causality between nodes.
Maximum clock offset — the largest clock difference allowed between nodes, 500 ms by default; nodes whose clocks drift too far stop themselves.
Uncertainty interval — the window (read timestamp, read timestamp + max offset] in which a value's timestamp might be "in the past" or "in the future" relative to the reader.
Write intent — a provisional MVCC value written by an uncommitted transaction, pointing to the transaction's record.
Transaction record — a small key that stores a transaction's status (PENDING, STAGING, COMMITTED or ABORTED).
Timestamp cache — a per-leaseholder structure recording the latest timestamp at which each key was read, so later writes cannot rewrite history beneath a read.
Pebble — CockroachDB's LSM storage engine in Go, inspired by and compatible in design with RocksDB.
history: Spencer Kimball, Peter Mattis and Ben Darnell had all worked at Google, where they used Bigtable and saw Spanner. Kimball and Mattis had earlier, as Berkeley students, created the GIMP image editor. Kimball started CockroachDB as an open-source project on GitHub in 2014, and the three founded Cockroach Labs in 2015. Their goal was an open-source Spanner: a scalable, strongly consistent SQL database that anyone could run. Version 1.0 shipped in May 2017. A Jepsen analysis of a 2016 beta by Kyle Kingsbury found serializability bugs, which were fixed; it also confirmed that the overall design worked as claimed when clocks stayed within limits.
Releases then filled in the SQL and performance story: a cost-based optimizer (2.1, 2018), transaction pipelining (2.1), parallel commits (19.2, 2019), and Pebble replacing RocksDB as the default storage engine (20.2, 2020). The SIGMOD 2020 paper "CockroachDB: The Resilient Geo-Distributed SQL Database" by Rebecca Taft and colleagues described the architecture, the transaction protocol and the multi-region features. Later versions added REGIONAL BY ROW and GLOBAL tables for multi-region applications (21.1), READ COMMITTED isolation (generally available in 24.1), vector indexes (25.2) and leader leases (default in 25.2), which merge the Raft leader and leaseholder roles and, according to Cockroach Labs, cut lease-maintenance CPU by up to 85% at scale.
Licensing changed in steps. The code began under the Apache 2.0 license. In 2019 the core moved to the Business Source License, which forbids offering CockroachDB as a commercial database service, and enterprise features were under a separate license. On 18 November 2024, Cockroach Labs retired the free Core edition and put everything under one CockroachDB enterprise license: free for individuals and companies under 10 million US dollars of annual revenue (with required telemetry), paid for larger ones. The source remains readable, but it is no longer open source in the OSI sense.
how: Start with how data becomes keys. Every row is encoded as a key-value pair: the key is the table ID, the index ID and the primary-key columns; the value holds the other columns. Each secondary index entry is another key made of the index columns plus the primary key. All these keys live in one sorted key space, which is cut into ranges. A two-level index of special "meta" ranges records where each range lives, and every node caches these range descriptors, so a request can be sent straight to the right node. Ranges split when they exceed 512 MiB or receive too much load, merge when they become small, and are moved between nodes by the allocator to balance disk use, load and placement rules.
Each range is replicated with Raft, the consensus piece of the newsql concept. The leaseholder receives all requests for the range. A write is proposed to the Raft log and is durable when a majority of replicas has appended it. A consistent read is served by the leaseholder alone, without a Raft round, because the lease guarantees no other replica can accept conflicting writes during that time. Since v25.2, leader leases tie the lease to Raft leadership and to a node-level health mechanism, which simplifies failover; Cockroach Labs reports recovery from most node failures in under a second in its tests.
Storage on each node is Pebble, the RocksDB contribution. Each replica's keys are stored with an MVCC timestamp suffix, so one logical key has many versions in the LSM tree: newest first, older versions behind it. Writes go to Pebble's write-ahead log and memtable, memtables flush to sorted files (SSTables), and compaction merges files level by level, using Bloom filters to skip files on point reads. Old versions are kept for the garbage-collection TTL (4 hours by default in recent versions), which allows historical reads and backups. Raft log entries are stored in the same engine.
Transactions use timestamps from hybrid logical clocks. When a transaction starts, the gateway node (the node the client connected to) gives it a timestamp. Each write is laid down as a write intent at that timestamp: an MVCC value marked as provisional, with a pointer to the transaction record. Readers that meet an intent check the record: if the writer committed, they treat the value as committed; if it is still pending, they wait in a lock-wait queue or, if the writer seems dead, push it (abort it or move it to a later timestamp). On commit, the record becomes COMMITTED and intents are converted to normal values in the background.
Serializable isolation needs two more mechanisms. First, the timestamp cache: if transaction B tries to write a key that someone has already read at a later timestamp, B's write timestamp is pushed above that read, so the read never sees history change underneath it. A pushed transaction must then refresh: it re-checks that every key it read has not changed between its old and new timestamps. If the check passes, it commits at the new timestamp; if not, it restarts with a retryable error (SQLSTATE 40001). Second, uncertainty. Clocks on different nodes may differ by up to the maximum offset (500 ms by default). If a reader at timestamp t finds a value with a timestamp between t and t + 500 ms, it cannot tell whether that write really happened before it started. It therefore moves its own timestamp above the value and refreshes, or restarts. Spanner waits out uncertainty at commit time; CockroachDB instead pays for it, occasionally, at read time. Nodes track the timestamps they have observed from other nodes to shrink this window, and a node whose clock drifts beyond the allowed offset from most of the cluster shuts itself down to protect correctness.
Commits are made cheap by two optimizations. With transaction pipelining, each write is sent to Raft without waiting for it to finish, so a transaction with ten writes does not pay ten consensus rounds in sequence. With parallel commits, the commit step marks the transaction record as STAGING and lists the writes still in flight; as soon as all of them and the STAGING record are replicated, the transaction is committed, even before the record is changed to COMMITTED. This turns two sequential consensus rounds (write intents, then commit record) into one.
Above the transaction layer is the SQL layer. It parses PostgreSQL-dialect SQL, uses a cost-based optimizer, and with DistSQL sends parts of a query (filters, aggregations, joins) to the nodes holding the data and merges partial results. Multi-region features build on range placement. A database lists its regions and a survival goal (survive a zone failure or a region failure). REGIONAL BY ROW tables keep each row's leaseholder and replicas in the row's home region. GLOBAL tables use writes at future timestamps so every region can serve fast, consistent reads from local replicas, at the cost of slower writes. Follower reads (AS OF SYSTEM TIME a few seconds in the past) let any nearby replica answer.

  Pebble (LSM, RocksDB-style): WAL -> memtable -> SSTables

example: A payments service uses a 9-node cluster in one region, spread over 3 availability zones, with replication factor 3. The data is 2 TB. If ranges average about 300 MB (they split at 512 MiB), there are about 2,000,000 / 300 ≈ 6,700 ranges and 20,000 replicas, about 2,200 replicas per node. A Raft round between zones takes about 1–2 ms. A transaction that debits one account and credits another writes two keys in two ranges. With pipelining and parallel commits, the two intent writes and the STAGING record are replicated in parallel, so the commit costs about one consensus round: roughly 2 ms, plus SQL processing, for a total of about 4–6 ms.
Now a clock example. Node A's clock runs 200 ms ahead of node B's, within the 500 ms limit. Transaction T1, through node A, writes balance = 90 at timestamp 10.200 and commits. A moment later, in real time, transaction T2 starts on node B, whose clock reads 10.050, and reads the balance. It finds the value at 10.200. That is "in the future" for T2, but it falls inside T2's uncertainty interval (10.050, 10.550]. T2 cannot know whether T1 finished before it started, so to be safe it moves its read timestamp to 10.200 and refreshes the reads it has already made. If nothing else changed, T2 continues and sees 90, which is the correct, real-time-respecting result. If an earlier read is no longer valid at 10.200, T2 must restart. With well-synchronized clocks (a few milliseconds of difference) and short transactions, such restarts are rare.
Next, contention. One hot row, a merchant's daily total, is updated by 500 transactions per second. Each update reads and writes the row, so transactions conflict. Each must wait for the previous intent to resolve, which takes at least one consensus round of about 2 ms, so the row supports at most about 500 updates per second, and retries rise quickly near that limit. Splitting the counter into 10 rows (merchant_id, shard 0–9) and summing on read raises the ceiling to about 5,000 updates per second.
Last, a region-survival setup. Replicas are placed in us-east, us-west and eu-west, with round trips of about 70 ms (east to west) and 80 ms (east to Europe). A write with the leaseholder in us-east needs a majority, so it waits for the nearest other region: about 70 ms per consensus round. The same transaction that cost 5 ms in one region now costs about 75 ms. This is the price of surviving the loss of a whole region, and it is why REGIONAL BY ROW tables and zone-survival goals exist for data that does not need it.
intuition: Spanner's plan with ordinary watches: since no one knows the exact time, anyone who sees a timestamp too close to their own simply re-checks their work as if it came slightly later.
The design is natural once you accept three facts. A single machine cannot hold the data, so it must be cut into ranges. Each range needs to survive failures, so each is a small Raft group, and the system grows by adding groups. Transactions across ranges need an order, and without a central sequencer that order must come from clocks, which are never perfect. Spanner buys accurate clocks and waits; CockroachDB accepts cheaper, less accurate clocks and checks for doubt only when a read actually meets a nearby timestamp. Most transactions never meet such a value, so most pay nothing. The cost is concentrated where it belongs: on transactions that really race with each other.
mistakes: People often think CockroachDB is PostgreSQL with sharding. It only speaks PostgreSQL's wire protocol and much of its SQL dialect; the storage, transaction model, optimizer and many behaviours are different. Some PostgreSQL features and extensions are missing or behave differently, so test the application rather than assuming compatibility.
People often think a serializable database never asks the client to retry. Under contention or clock uncertainty, CockroachDB returns retryable errors (40001), and the application or driver must rerun the whole transaction. Many retries are handled automatically on the server for single statements, but multi-statement transactions need a retry loop in client code.
People often think CockroachDB needs no clock synchronization because it has no atomic clocks. It depends on clocks staying within the maximum offset (500 ms by default). Clocks that drift beyond it can break the uncertainty argument, so nodes shut themselves down. Run NTP or chrony with a reliable source, and in clouds use their precision time services.
People often think adding nodes always increases write throughput. It does for well-spread keys, but writes with monotonically increasing primary keys (timestamps, SERIAL) all land in the last range, on one leaseholder. Use UUIDs or hash-sharded indexes to spread such writes.
friction: Latency is the first cost. Every write needs a Raft majority, so single-row writes take a few milliseconds within a region and tens of milliseconds or more when the replicas span regions. Serializable isolation under contention leads to retries and aborted work, and long transactions that read many rows are more likely to need restarts after a push. Applications must be written with retry loops, short transactions and hot spots in mind.
Operations are heavier than for a single PostgreSQL server. A cluster has thousands of ranges and Raft groups, and operators must understand leaseholder placement, rebalancing, LSM compaction health (read amplification in Pebble's level 0), admission control and backup schedules. Large schema changes run as background jobs and can take hours on big tables. Analytical queries are possible with DistSQL, but heavy scans compete with transactional work, and the system is not a column store.
Compatibility and cost are the last frictions. Not every PostgreSQL feature exists, some PostgreSQL behaviours differ (for example the default isolation level is SERIALIZABLE, not READ COMMITTED), and some ORMs need adjustments. The November 2024 license change means larger companies must pay for self-hosted use, and smaller ones must send telemetry, which closed the free path that many teams had relied on and pushed some to look at YugabyteDB, TiDB or managed PostgreSQL alternatives.
practice: Use CockroachDB when you need SQL transactions with data that outgrows one machine, automatic failover across zones or regions, or rows pinned to regions for residency rules. For a few hundred gigabytes in one region with modest write rates, a managed PostgreSQL with a replica is simpler and faster per query.
Design keys for spread: UUID primary keys (gen_random_uuid()) or hash-sharded indexes for time-ordered data. Keep transactions small and short, touch hot rows as late as possible in a transaction, and avoid interactive transactions that wait on users or remote calls. Implement a retry loop for 40001 errors in every client, with a limit and backoff.
Run reliable clock synchronization on every node and alert on clock offset. Choose survival goals and table localities deliberately: zone survival for most data, region survival only where the latency is worth it, REGIONAL BY ROW for user data with a home region, and GLOBAL for small, read-mostly reference tables. Use follower reads (AS OF SYSTEM TIME follower_read_timestamp()) for reports and dashboards that can be a few seconds old.
Monitor SQL latency percentiles, transaction retries and contention events, range hot spots, leaseholder distribution, LSM health and disk usage, and keep at least 30–40% disk headroom. Test upgrades on a staging cluster, read the release notes for regular versus optional innovation releases, and check the license terms that apply to your company size.
quiz: What does CockroachDB use instead of TrueTime, and what is the cost of that choice? || It uses hybrid logical clocks on ordinary servers with a configured maximum clock offset (500 ms by default). Because it cannot wait out a small, measured uncertainty, a read that meets a value inside its uncertainty window must move its timestamp up and refresh, or restart.
How do parallel commits reduce commit latency? || The transaction record is written in a STAGING state listing all in-flight writes. As soon as those writes and the STAGING record are replicated, the transaction is committed, so the separate consensus round to write the COMMITTED record is removed from the client's critical path.
Why must a transaction refresh its reads when its timestamp is pushed? || It will commit at a later timestamp than it read at, so its earlier reads are only valid if none of those keys changed between the old and new timestamps. If a refresh finds a change, committing would break serializability, so the transaction restarts.
A table holds 3 TB and ranges average 300 MB with replication factor 3 on 12 nodes. How many replicas does each node hold? || About 3,000,000 / 300 = 10,000 ranges, so 30,000 replicas, which is about 2,500 replicas per node.
A global SaaS app stores user profiles that each belong to one country, plus a small currency table read by everyone. Which table localities fit? || User profiles fit REGIONAL BY ROW, so each row's leaseholder and replicas live in the user's home region and local reads and writes are fast. The small, read-mostly currency table fits a GLOBAL table, which gives fast consistent reads in every region at the cost of slower writes.

@@ valkey
value: Valkey is an open-source, in-memory key-value data store: a server that keeps all its data in RAM and answers commands on strings, hashes, lists, sets, sorted sets, streams, bitmaps and HyperLogLogs in well under a millisecond. It began in March 2024 as a fork of Redis 7.2.4, the last version under the permissive BSD license, after Redis Ltd. moved Redis to source-available licenses. The Linux Foundation hosts it, and AWS, Google Cloud, Oracle, Alibaba Cloud, Tencent, Ericsson, Percona, Aiven, DigitalOcean and others back it. It speaks the same RESP protocol and commands as Redis 7.2, so existing Redis clients and most applications work unchanged.
The concept it stands on is the caching layer: keep hot data in a faster, smaller tier in front of a slower store. Valkey is the most common building block for that tier, together with Redis and Memcached. From the caching concept it takes its main job and its main tools: time-to-live on keys, memory limits with eviction policies (approximate LRU and LFU), and the cache-aside pattern in which applications fill the cache after a miss. On top of plain caching, its data structures let the same server act as a session store, rate limiter, leaderboard, queue, pub/sub bus and real-time counter, because each command is an atomic operation on a structure in memory.
For the layer above, Valkey offers a free, vendor-neutral path for the huge number of systems built on Redis. AWS ElastiCache and MemoryDB, Google Memorystore, Aiven and others now offer it as a managed engine, AWS at prices 20–33% lower than its Redis OSS engine. It matters to understand now because the forks are diverging. Valkey 8.0 (September 2024) reworked I/O threading for up to 1.2 million requests per second on one AWS r7g instance; 8.1 (2025) replaced the core hash table to save about 20–30 bytes per key; 9.0 (October 2025) added atomic slot migration, per-field hash expiry and clusters of up to 2,000 nodes; and 9.1 (May 2026) cut per-key memory by up to another 10%. Meanwhile Redis 8 (2025) added the AGPL license and its own new features. Choosing between them is now a real engineering decision.
terms: RESP — the Redis serialization protocol, a simple text-and-length-prefixed format that Valkey speaks unchanged.
Event loop — the main thread's loop that waits for socket events (epoll on Linux) and executes ready commands one at a time.
I/O threads — helper threads that read and parse requests and write responses, while command execution stays on the main thread.
maxmemory and eviction policy — the memory limit and the rule (for example allkeys-lru or allkeys-lfu) for choosing which keys to delete when it is reached.
TTL (time to live) — an expiry time on a key; expired keys are removed lazily on access and by a periodic background sweep.
RDB and AOF — the two persistence formats: point-in-time snapshots, and an append-only log of write commands.
Hash slot — one of 16,384 buckets in cluster mode; a key's slot is CRC16(key) mod 16,384, and each primary owns a set of slots.
Hash tag — the part of a key inside braces, such as {user:42}, which is hashed alone so related keys share a slot.
Replica — a server that receives an asynchronous stream of writes from a primary and can take over if the primary fails.
Slot migration — moving a slot's keys from one primary to another while the cluster keeps serving traffic.
history: Salvatore Sanfilippo (antirez) created Redis in 2009, and for 15 years it was BSD-licensed. On 20 March 2024 Redis Ltd. announced that future Redis versions would use the Redis Source Available License and the Server Side Public License, which restrict offering Redis as a managed service. Cloud providers and long-time contributors saw this as the end of open-source Redis. Eight days later, on 28 March 2024, the Linux Foundation announced Valkey, forked from Redis 7.2.4. Madelyn Olson of AWS, a long-time Redis core maintainer, and engineers from Alibaba, Ericsson, Google, Huawei and Tencent formed its first technical steering committee. Valkey 7.2.4, a renamed copy of the fork point, shipped in April 2024.
The project then moved quickly, because many of its maintainers had been doing much of the open-source Redis core work for years. Valkey 8.0 (September 2024) rebuilt the I/O threading model and added dual-channel replication and per-slot metrics. AWS launched ElastiCache for Valkey in October 2024, Google launched Memorystore for Valkey, and other providers followed. Valkey 8.1 (2025) introduced a new hash table designed by Viktor Söderqvist and others, built from 64-byte buckets that each fit in one CPU cache line, and the project published modules for JSON, Bloom filters and search (including vector search).
Redis responded. Antirez returned to Redis Ltd. in late 2024, and with Redis 8 in May 2025 Redis added the AGPLv3 as an open-source license option and merged its JSON, search and time-series modules into the core. Valkey continued on its own path: 9.0 in October 2025 (atomic slot migration, hash field expiration, multiple databases in cluster mode, clusters of up to 2,000 nodes serving over a billion requests per second) and 9.1 on 19 May 2026 (lower per-key memory, database-level access control, automatic TLS certificate reloading and a cluster-wide CLUSTERSCAN command), with over 80 contributors to that release.
how: The core design is inherited from Redis. All data lives in memory in one big hash table per database, mapping each key to a value object. Small values use compact encodings: a small hash, list or sorted set is stored as a listpack, one contiguous block of bytes, and converts to a real hash table, quicklist or skip list once it grows past configured limits. A main thread runs an event loop. It waits on epoll for sockets with data, and for each complete request it looks up the command and executes it from start to finish before the next one. Because only one thread changes data, every command is atomic without locks, and MULTI/EXEC transactions and Lua scripts simply run without interruption.
Valkey 8.0 changed what happens around that single executor. In Redis 6 and 7, I/O threads could help read and write sockets, but the main thread still did much of the work and waited for helpers in lockstep. In Valkey 8, the main thread hands out jobs and the I/O threads work asynchronously: they read and parse requests, write replies, run epoll_wait, and free memory of deleted objects. The main thread also prefetches the memory of keys needed by a batch of parsed commands before executing them, so that CPU cache misses overlap instead of stalling one after another. The number of active I/O threads grows and shrinks with load. The result, on an AWS r7g instance, was about 1.2 million requests per second, more than three times the previous version, while command execution stays strictly single-threaded.
Valkey 8.1 replaced the core dictionary. The old Redis dict was a chained hash table: each key had a separate 24-byte dictEntry with a pointer to the key, a pointer to the value and a "next" pointer, so a lookup touched about four separate memory locations. The new table uses 64-byte buckets, one cache line each, holding up to seven entries plus one byte of extra hash per entry to reject most non-matching slots without reading the key. The key and value are embedded in a single object, so the dictEntry disappears. A lookup touches about two memory locations, and memory falls by roughly 20 bytes per key, or about 30 bytes for keys with a TTL, according to the Valkey team.
The caching-layer concept appears in maxmemory. When used memory exceeds the limit, the server evicts keys according to the chosen policy before running a write command. LRU is approximated: instead of a global linked list, Valkey samples a few keys (5 by default) and evicts the one idle longest, keeping a pool of good candidates between rounds. LFU keeps an 8-bit logarithmic access counter per key that grows more slowly as it rises and decays over time, so keys that were popular yesterday but not today can be evicted. Expiry is handled lazily, when a key is accessed, and actively, by a background cycle that samples keys with TTLs and deletes expired ones.
Persistence is optional. An RDB snapshot is made by fork(): the child process writes the dataset to a file while the parent continues serving, and the operating system's copy-on-write means only pages the parent changes during the snapshot are duplicated. The AOF logs every write command; with appendfsync everysec, at most about one second of writes is lost on a crash. Replication is asynchronous. A new replica gets a full snapshot and then a stream of commands; if it disconnects briefly, it resumes from a replication backlog buffer. Valkey 8's dual-channel replication sends the snapshot on a separate connection while the primary streams new writes to the replica, which reduces memory pressure on the primary during a full sync.
Cluster mode shards data. Every key maps to one of 16,384 hash slots, and each primary owns a set of slots, usually with one or more replicas. Nodes exchange state over a cluster bus with a gossip protocol. A client that sends a command to the wrong node receives a MOVED reply with the right address and updates its slot map. If a primary fails, its replicas ask the other primaries for votes, and one is promoted once a majority agrees. Multi-key commands work only if all keys are in the same slot, which hash tags control. Before 9.0, resharding moved keys one at a time with MIGRATE, and clients could see ASK redirects and slow large keys. Valkey 9.0's atomic slot migration copies a slot like a mini replication stream and then switches ownership in one step, so a slot is never split between two nodes.

example: A streaming service caches user sessions in Valkey: 100 million keys, each with a 20-byte key, a 100-byte value and a 30-minute TTL. On Redis 7.2, each key carried roughly 80 bytes of overhead (a dictEntry, a value object, string headers and an entry in the separate expiry table), so each key used about 20 + 100 + 80 = 200 bytes, or 20 GB in total. Valkey 8.1's new hash table saves about 30 bytes per key with a TTL, bringing this to about 170 bytes per key and 17 GB. That is 3 GB less per copy of the data. The memory allocator (jemalloc) adds fragmentation of about 10–20%, so plan for about 20 GB used on each primary node.
Now the cluster plan. The team runs 3 shards, each with one primary and one replica, so each primary holds about 7 GB of data, about 8 GB with fragmentation. If RDB snapshots are on, a write-heavy period during a fork can duplicate many pages; leaving 30–50% headroom gives nodes of about 12–16 GB, rather than 8 GB. Without persistence (a pure cache), the headroom can be smaller.
Next, throughput. Peak traffic is 900,000 requests per second, 90% reads. Spread across 3 primaries, that is 300,000 per primary. On Valkey 8 with I/O threads, one node can serve well above that for small requests, while older single-threaded I/O configurations would have needed more shards for CPU, not for memory. Reads can also go to replicas if slightly stale sessions are acceptable.
Finally, the cache's effect on the database behind it. Session lookups hit the cache 97% of the time. The 3% misses at 810,000 reads per second mean 24,300 database reads per second. If one cache shard fails and its replica is promoted within a few seconds, a third of the keys are briefly unavailable. If instead an entire shard's data were lost and had to be refilled, about 270,000 reads per second would fall on the database for a while, about eleven times its normal load. That is why caches need replicas, why TTLs should have random jitter (for example 30 minutes plus 0–120 seconds), and why the database must have protection such as request coalescing or load shedding.
intuition: A very fast clerk at one counter who never shares the ledger, now given assistants who open the mail and post the replies, so the clerk only does the bookkeeping.
The design makes sense because most cache and coordination operations are tiny: get a key, increment a counter, add to a sorted set. For such operations the cost is not computation but waiting: for the network, for system calls, for memory. A single executing thread removes all locking and makes every command atomic, which is exactly what counters, rate limiters and locks need. Valkey's changes keep that simple model and attack the waiting around it: helper threads take the system calls and parsing, prefetching hides memory latency, and a cache-line-sized hash table reduces how many memory locations each lookup touches. The data model stays the same; the time spent around it shrinks.
mistakes: People often think Valkey is now multi-threaded like a typical database, so long commands are safe. Command execution is still single-threaded. One slow command, such as KEYS on millions of keys, a large ZRANGE or a long Lua script, still blocks every other client. Use SCAN, paginate ranges and keep scripts short.
People often think Valkey and Redis are interchangeable forever. They share the 7.2 base, and clients work with both, but features added after the fork differ: Redis 8 has vector sets and built-in query modules, while Valkey has its own modules, atomic slot migration and different internal memory layouts. Snapshot files from newer Redis versions may not load in Valkey, so migrations from recent Redis need testing or replication-based tools.
People often think an in-memory store with persistence is a durable database. Replication is asynchronous, so a failover can lose acknowledged writes, and AOF with everysec can lose about a second. Use Valkey as the source of truth only for data you can afford to lose or rebuild, or choose a service built for durability on top of it, such as MemoryDB.
People often think more memory automatically means more cache hits. Hit rate depends on the access pattern and TTLs, and on the eviction policy. A workload with a large scan-like pattern can flush a pure LRU cache, while allkeys-lfu keeps frequently used keys. Measure hit rate and evictions before buying memory.
friction: Memory is the main cost. All data must fit in RAM, replicas double or triple it, fork-based snapshots need headroom, and fragmentation adds more. Values are stored as bytes, so large or poorly encoded values are expensive; per-key overhead dominates when values are small.
Consistency is weak by design. Replication is asynchronous, cluster failover can lose recent writes, and during a network partition a minority primary may accept writes that are later discarded. Multi-key operations, transactions and Lua scripts in cluster mode are limited to one slot. Distributed locks built on Valkey (such as Redlock) are not safe for correctness without fencing tokens.
The ecosystem split is a practical cost. Redis modules from Redis Ltd. (such as the full Redis query engine) are not part of Valkey; Valkey's own modules for JSON, Bloom filters and search are younger and differ in features. Documentation, tools and blog posts often describe Redis behaviour that may not match the Valkey version you run. Managed services add their own variations and version lags. Finally, the project's fast pace (four feature releases in two years) means operators must track release notes, because defaults and internal behaviour change more often than in the last years of open-source Redis.
practice: Treat Valkey as a fast tier, not the system of record. Set maxmemory explicitly, choose an eviction policy (allkeys-lfu or allkeys-lru for pure caches, volatile-ttl or noeviction when some keys must not be evicted), add TTLs with random jitter, and monitor hit rate, evicted keys, memory fragmentation and replication lag.
Enable I/O threads on Valkey 8 and later for high request rates (io-threads set to a few less than the number of cores), and use pipelining from clients to cut round trips. Avoid O(N) commands on large keys; use SCAN, HSCAN and ZSCAN, and find big keys with --bigkeys or the memory analysis tools. Keep values small and use hashes for groups of small fields.
In cluster mode, design keys with hash tags so that data used together shares a slot, plan for client-side MOVED handling (use a cluster-aware client such as Valkey GLIDE or a recent Jedis, Lettuce or redis-py), and prefer Valkey 9's atomic slot migration when resharding. For persistence, use AOF with everysec when you need roughly one-second durability, and leave memory headroom for forks.
When migrating from Redis, start from Redis 7.2 or earlier for the simplest path; for newer Redis versions, test data formats, commands and modules first. Choose Valkey for a BSD-licensed, multi-vendor future and lower managed-service prices; choose Redis 8 if you depend on its newer built-in modules or on Redis Ltd. support.

@@ rocksdb
value: RocksDB is an embeddable, persistent key-value store: a C++ library that a program links into its own process to keep a sorted map of byte-string keys to byte-string values on local SSD. It supports point lookups, ordered iteration and range scans, atomic write batches, snapshots and transactions, and it is designed for fast flash storage and many CPU cores. Meta started it in 2012 from Google's LevelDB and open-sourced it in 2013. It is now the storage layer inside a long list of systems: MyRocks (MySQL on RocksDB) at Meta, Kafka Streams and Apache Flink state stores, TiKV under TiDB, Ceph's BlueStore metadata, YugabyteDB (as a modified fork), Apache Kvrocks, and many internal services. CockroachDB used it until 2020 and then replaced it with Pebble, a Go engine modelled on it.
It stands on two lower concepts. The first is the embedded storage engine: the library under a database that lays data out on disk. RocksDB is purely that layer. It has no network protocol, no replication, no SQL and no distribution; the host system adds those and uses RocksDB to make one machine's data durable, compact and fast to read. The second is C++. Writing it in C++ gives control over memory layout, allocation, cache-friendly data structures, lock-free concurrency and direct system calls, which matters when one engine must handle millions of operations per second per server. Java systems such as Kafka Streams and Flink reach it through the RocksJava JNI bindings, which is why their state stores have native memory that the JVM does not see.
Inside, RocksDB is a log-structured merge tree (LSM tree). Writes are appended to a log and buffered in memory, then written out as immutable sorted files, which background compaction merges into larger sorted levels. This turns random writes into sequential ones, which SSDs and disks handle much better, and it compresses well. For the layer above, that means high write throughput, small on-disk size and state that can grow far beyond RAM. The cost is a set of trade-offs between write, read and space amplification, controlled by dozens of options. Understanding those trade-offs is the key skill, and it matters for anyone running Flink, Kafka Streams or TiDB at scale, because their performance problems are very often RocksDB compaction, memory or tuning problems.
terms: Memtable — the in-memory sorted buffer (a skip list by default) that receives new writes before they are flushed.
WAL (write-ahead log) — an append-only file of write batches, replayed after a crash to rebuild unflushed memtables.
SST file — an immutable sorted string table on disk: data blocks, an index block, an optional filter block and metadata.
Level — a set of SST files; L0 files may overlap in key range, while files in L1 and below do not overlap within a level.
Compaction — the background job that merges SST files, drops overwritten and deleted entries, and writes new files to a lower level.
Sequence number — a 56-bit counter attached to every write; snapshots and iterators use it to see a consistent version.
Column family — a separate key space with its own memtables, SST files and options, sharing one WAL with the others for atomic writes.
Block cache — the in-memory cache of uncompressed data, index and filter blocks read from SST files.
Write amplification — bytes written to storage divided by bytes written by the application; leveled compaction often gives 10–30.
Write stall — RocksDB deliberately slowing or stopping writes when flushes or compactions fall behind.
history: The LSM tree comes from Patrick O'Neil, Edward Cheng, Dieter Gawlick and Elizabeth O'Neil's 1996 paper "The Log-Structured Merge-Tree". Google's Bigtable (2006) used the idea for its tablets, and in 2011 Jeff Dean and Sanjay Ghemawat released LevelDB, a small embedded LSM library based on Bigtable's tablet code. LevelDB was simple and fast for small datasets, but it used one compaction thread, assumed spinning disks, and had few options.
In 2012 Dhruba Borthakur, who had worked on Hadoop's file system, started RocksDB at Facebook by forking LevelDB, to serve large datasets on flash with many cores. It was open-sourced in November 2013. Multi-threaded compaction, universal compaction, column families, merge operators, transactions and many statistics followed. In 2016–2017 Facebook moved its main social-graph MySQL database (UDB) from InnoDB to MyRocks, and reported roughly halving storage space compared with compressed InnoDB. The CIDR 2017 paper "Optimizing Space Amplification in RocksDB" by Siying Dong, Mark Callaghan and colleagues explained the dynamic level sizing behind this, and the FAST 2021 paper by Dong, Andrew Kryczka, Yanqin Jin and Michael Stumm described how priorities shifted over time from write amplification to space efficiency, then to CPU efficiency, and to large-scale operation.
Other systems adopted it widely: Kafka Streams made it the default state store, Flink added a RocksDB state backend with incremental checkpoints, and TiKV, CockroachDB and many others built on it. Features kept arriving: ribbon filters (2020–2021), integrated BlobDB for storing large values in separate blob files (2021), the lock-free HyperClockCache, user-defined timestamps, wide-column entities, tiered storage, remote compaction and asynchronous I/O. Dynamic level sizing became the default in version 8.4 (2023). In 2026 the project is in its 11.x series, with work on asynchronous reads and I/O.
how: A write starts as a WriteBatch: one or more puts, deletes or merges that must apply atomically. RocksDB groups concurrent batches from many threads: one thread becomes the leader, appends all their records to the WAL in one sequential write, optionally syncs it, and then the batches are inserted into the active memtable, which allows concurrent inserts. Every entry gets a sequence number, and internally a key is stored as the user key plus 8 bytes holding the sequence number and the operation type (value, deletion, merge). That is the whole write path: one sequential log append and one in-memory insert, which is why writes are fast.
When the memtable reaches its size (64 MB by default), it becomes immutable and a new one takes over. A background flush writes the immutable memtable to a new SST file in level 0. An SST file is a sequence of data blocks (4 KB by default, each compressed, for example with LZ4 or ZSTD), followed by an index block that maps each data block's last key to its position, a filter block (typically a Bloom or ribbon filter over all keys) and properties. The set of live SST files is recorded in the MANIFEST, an append-only log of "version edits" such as "add file 123 to L1, remove files 98 and 99 from L0". Applying edits atomically lets compactions replace files without ever exposing a half-finished state.
Compaction gives the LSM tree its shape. In the default leveled compaction, L0 files may overlap, but every lower level is one sorted run split into non-overlapping files, and each level is about 10 times larger than the one above. When L0 has 4 files, they are merged into the base level; when a level exceeds its target size, a file from it is merged with the overlapping files of the next level. Merging is a sorted merge of several inputs. For each key it keeps the newest version still needed by a live snapshot and drops older ones; deletion markers (tombstones) are dropped once they reach the last level. With dynamic level sizing, the last level is sized to the real data and the levels above it are 1/10, 1/100 and so on of it, so about 90% of the data sits in the last level and space amplification stays near 1.1. Universal compaction instead merges whole sorted runs of similar size, which writes less but needs more temporary space, and FIFO compaction just deletes the oldest files, which suits time-to-live data.
A point lookup searches from newest to oldest: the active memtable, the immutable memtables, every L0 file (because they overlap), then one file per lower level, found by binary search on file key ranges. For each candidate file, it first checks the filter block; with about 10 bits per key, a file that lacks the key is skipped 99% of the time. If the filter says "maybe", the index block finds the one data block that could hold the key, which is read from the block cache or from disk and searched. The first version found is the answer, so recent keys are found early. A range scan opens an iterator on every memtable and every relevant file and merges them in key order, which is why scans touch more data than lookups.
Several features build on this core. Snapshots are just sequence numbers: a reader at sequence 1,000 ignores entries with higher numbers, and compaction keeps the versions that live snapshots need. Checkpoints hard-link the current SST files into another directory, which is how Flink takes cheap incremental checkpoints: only new files need uploading. Merge operators let a write say "add 5 to this counter" without reading first; the operands are combined lazily during reads and compaction. Column families give separate key spaces with separate options and files, with atomic writes across them through the shared WAL. TransactionDB adds pessimistic row locks, and OptimisticTransactionDB checks for conflicts at commit. BlobDB stores large values in separate blob files so compaction moves only keys and small pointers.
The C++ contribution shows in the details. The block cache stores uncompressed blocks and is sharded to reduce lock contention; HyperClockCache avoids locks on lookups entirely. Memtable skip lists support concurrent inserts with atomic operations. Rate limiters smooth compaction I/O, and statistics and perf contexts count every block read, cache hit and stall. The storage-engine contribution shows in the boundaries: RocksDB does not decide what is replicated or where; systems like TiKV and CockroachDB put a Raft log above or beside it and use RocksDB only as one node's durable state machine.

example: A stream processor keeps 1 TB of state in RocksDB on one node: about 1 billion keys with values of about 1 KB. With dynamic level sizing and a multiplier of 10, the last level holds about 1 TB, the level above about 100 GB, then about 10 GB and about 1 GB; smaller levels stay empty. Total space is about 1 TB + 100 GB + 10 GB + 1 GB ≈ 1.11 TB, so space amplification is about 1.11, before compression shrinks everything.
Now write amplification. Each byte the application writes is written once to the WAL and once by the flush to L0. It is then rewritten when L0 merges into the base level, and again at each move to a lower level. When a file moves down one level, it is merged with the overlapping part of the next level, which is up to 10 times larger, so in the worst case about 10 bytes are rewritten per byte moved. With three moves below the base level, a rough worst case is 1 + 1 + 1 + 3 × 10 = 33; measured values are often 15–30. Take 20.
That number decides hardware. Suppose the application writes 20 MB per second of new data. The SSD then receives about 20 × 20 = 400 MB per second of writes, about 35 TB per day. A 4 TB data-centre SSD rated for 1 drive write per day can absorb about 4 TB per day, so this workload would wear it out roughly nine times faster than its rating. The options are: universal compaction (lower write amplification, more space), BlobDB (compaction stops rewriting the 1 KB values and moves only keys and pointers), larger memtables, or more drives. Endurance, not throughput, is often the real limit of an LSM store.
Next, reads and memory. Bloom filters at 10 bits per key for 1 billion keys need about 10 billion bits, about 1.25 GB. Index blocks, one entry per 4 KB data block, cover about 250 million blocks and can need several gigabytes. If filters and indexes do not fit in the block cache, each lookup may first read index or filter blocks from disk, and latency doubles or triples. Partitioned indexes and filters (which load only the needed parts) or 16 KB blocks reduce this memory. With filters and indexes cached, a lookup for a missing key checks the memtables and about 8 filters and reads almost nothing from disk (8 × 1% ≈ 0.08 expected block reads), while a lookup for a key in the last level reads one 4 KB data block, about 100 microseconds on NVMe if it is not cached.
intuition: A clerk who never edits old files: every change is written on a new card and dropped in a tray, and at night the trays are sorted and merged into the big alphabetical cabinets.
The design is natural once you look at what storage devices like. Random small writes are expensive: on SSDs they cause internal garbage collection, and on disks they cost a seek each. Sequential writes of large sorted files are cheap. So RocksDB never updates data in place. It accepts each write into memory and a log, writes large sorted files later, and pays the cost of keeping data organized in the background, where it can be batched, compressed and scheduled. Reads then have to look in several places, but most of those places can be ruled out quickly by filters and indexes, and the newest data is found first. Every tuning option is a choice about how much background work to do now to make reads, or space, cheaper later.
mistakes: People often think RocksDB is a database server. It is a library inside your process, with no network protocol, replication or failover. If the process or the machine dies, the data is only as safe as that machine's disk and the host system's replication.
People often think Bloom filters are on by default. With plain default options, BlockBasedTableOptions has no filter policy, so every lookup for a missing key may read a data block from every level. You must set a filter policy (for example a Bloom filter with 10 bits per key) yourself. Kafka Streams sets one for its stores, but Flink's option for it (state.backend.rocksdb.use-bloom-filter) is off by default.
People often think deletes immediately free space and make reads cheaper. A delete writes a tombstone. Until compaction pushes it to the last level, both the tombstone and the old value take space, and scans over ranges full of tombstones become slow. DeleteRange and compaction-on-deletion options exist for this.
People often think write stalls are a bug. They are RocksDB protecting itself: when L0 files pile up (20 files trigger a slowdown and 36 a stop by default) or pending compaction bytes grow too large, writes slow down so compaction can catch up. Stalls mean the sustained write rate is above what compaction can handle with the current settings and hardware.
friction: Tuning is the main pain. There are dozens of interacting options for memtables, levels, compaction style, compression per level, caches, filters and rate limits, and defaults are only a starting point. The RUM trade-off (read, update, memory) is real: lowering write amplification raises space or read amplification, and the other way around. Benchmarks on small data or short runs mislead, because compaction debt shows up only after hours.
Compaction itself causes latency spikes: bursts of background I/O compete with foreground reads, and write stalls appear when it falls behind. Large values make compaction rewrite much more data, unless BlobDB is used. Memory accounting is tricky: memtables, block cache, index and filter blocks, and iterators pinning blocks all use native memory, so in Java hosts the process can run out of memory while the JVM heap looks fine. Many open iterators or old snapshots stop compaction from dropping obsolete versions.
Finally, scale-out and operations belong to the host. RocksDB has no built-in replication or distribution, a single database is limited to one machine's disks, and features such as remote compaction and tiered storage need integration work. Its API is large, and options or behaviours change across major versions, so upgrading the RocksDB inside Flink, Kafka Streams or TiKV is part of upgrading those systems.
practice: Start from the access pattern. For write-heavy data with mostly point lookups, use leveled compaction with dynamic level sizing (the default since 8.4), a Bloom or ribbon filter at about 10 bits per key, and LZ4 for upper levels with ZSTD for the bottom level. For time-series data with time-to-live, consider FIFO compaction or TTL-based compaction; for very write-heavy workloads where space is cheap, consider universal compaction; for values larger than about 1 KB, consider BlobDB.
Size memory deliberately. Give the block cache a fixed budget, set cache_index_and_filter_blocks with pinning of top-level index and filter partitions, and use partitioned index and filters for large databases. Limit total memtable memory with a write buffer manager, especially in Flink and Kafka Streams, which run many RocksDB instances in one process.
Watch the right numbers: write amplification, pending compaction bytes, L0 file count, stall time, block cache hit rate, read latency percentiles and disk endurance. Use a rate limiter for compaction I/O to protect foreground latency, and add background threads (max_background_jobs) if compaction falls behind on fast disks.
Test with realistic data larger than memory and run for hours, with tools such as db_bench. Use snapshots and iterators carefully and close them, because they hold old data. For deletes over ranges, use DeleteRange instead of many single deletes. If you need replication, rely on the host system (Raft in TiKV, changelog topics in Kafka Streams, checkpoints in Flink) rather than trying to copy RocksDB files by hand.
quiz: What are the main steps of a RocksDB write, and why is it fast? || The write batch is appended to the WAL and inserted into the in-memory memtable; nothing on disk is updated in place. That is one sequential log write plus a memory insert, with flushing and compaction done later in the background.
Why must a point lookup check every L0 file but only one file in each lower level? || L0 files are flushed memtables whose key ranges can overlap, so any of them may hold the key. In L1 and below, files within a level do not overlap, so binary search on their key ranges identifies the single file that could contain it.
How does dynamic level sizing keep space amplification near 1.1? || It sizes the last level to the actual data and makes each level above it about one tenth of the next. Then about 90% of data is in the last level, and obsolete versions in upper levels add only about 11% extra space.
An application writes 10 MB per second and measured write amplification is 25. How much does the SSD write per day? || 10 × 25 = 250 MB per second, which is 250 × 86,400 ≈ 21.6 TB per day. That is far above the endurance budget of a typical 4 TB drive rated for one drive write per day.
When would you choose universal compaction or BlobDB instead of default leveled compaction? || Universal compaction when writes dominate and you can afford more temporary and total disk space, because it rewrites data fewer times. BlobDB when values are large, because it keeps values in separate blob files so compaction moves only keys and pointers.
