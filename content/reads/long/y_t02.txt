@@+ beam
tradeoffs: Beam or the engine's own API. Choose Beam when you run on Google Cloud, because Dataflow is the one runner that implements the whole model (autoscaling, dynamic work rebalancing, Streaming Engine) as a managed service, or when one codebase must serve both a live stream and a historical backfill. Choose Flink directly when you run Kubernetes or AWS already, because you then get every Flink feature the day it ships, one fewer abstraction to debug, and no gRPC hop for Java code. Choose Spark Structured Streaming when the team already runs Spark or Databricks and a latency of a few seconds is fine. You give up, with Beam off Dataflow, direct access to engine features and a quick path from a bug to its cause; with the native API, you give up a clean way to move engines later and a single pipeline definition for batch and stream.
Which language for the SDK. Java and Go pipelines run user code in the same kind of process as the runner or in a thin harness; Python pipelines run user code in a separate SDK harness, and every element crosses a gRPC boundary with encoding and decoding. For a heavy per-element step (a model call, a regex over a large string) the boundary is noise; for a cheap step (parse an integer, add two fields) it can be most of the CPU bill, so measure with a sample before committing a 5 million events per second pipeline to Python. Choose Python when the team's skill, ML libraries or Dataflow's Python streaming matter more than raw throughput; choose Java when the pipeline is a cheap, high-volume transform.
Window shape and lateness are a cost decision, not only a correctness one. A sliding window of 10 minutes every 1 minute puts every element into 10 windows, so state, shuffle bytes and output rows are about 10 times those of a fixed 1-minute window. Allowed lateness multiplies state by the number of windows kept open: 50,000 keys with 11 open windows at 50 bytes each is only about 27 MB, but 5 million keys with 1-hour lateness over 1-minute windows is 5 million × 61 × 50 bytes, about 15 GB. Choose a short lateness plus a separate late-data side output or a nightly batch correction when most late events arrive within a minute; choose long lateness only when late data is common and the consumer can apply upserts.
Streaming pipeline or Beam batch backfill, versus a lakehouse job. Reprocessing a year of history through the same Beam code guarantees the same logic and the same windows, but it runs on a general engine and is usually slower and costlier per terabyte than a Spark/Photon job reading Delta tables with a plain SQL group-by. Choose the Beam backfill when the logic is stateful and time-dependent (sessions, per-key timers) so that a rewrite would risk disagreement; choose the SQL job when the logic is an aggregation you can state in a dozen lines.
Beam or Kafka Streams. If the input and output are both Kafka topics, the logic is a join or aggregation on keys, and you want a library in a normal service rather than a cluster, Kafka Streams is much simpler to run. Beam wins when sources and sinks are mixed (files, Pub/Sub, BigQuery), when the same code must read bounded and unbounded data, or when you need rich triggers and watermarks across many sources. The price of Beam is a runner to operate and a larger concept surface that every new engineer must learn.
interview: A team wants "one pipeline for batch and streaming". When is Beam the right answer and when is it a trap? || It is right when the logic depends on event time (windows, sessions, late data) and you run on Dataflow or already operate Flink, because the same program then gives the same windows in a backfill and in the live stream. It is a trap when the logic is a simple aggregation, when you are on Databricks or AWS and would add a runner layer for no managed benefit, or when the team has no one who understands watermarks, since the model moves the hard decisions into code rather than removing them.
Your Beam job's lag grows even though CPU is low. What do you check? || First the watermark: if it is stuck, look for an idle source partition, a hot key that holds one worker, or one slow DoFn (for example an external call without batching) that blocks a fused stage. Then check fusion: a small input expanding to many elements needs a Reshuffle. Finally check the sink, because backpressure from a slow BigQuery or database write looks like low CPU upstream.
How would you size the cost of allowed lateness for a pipeline with a million keys? || State is roughly keys × open windows × bytes per key and window, so 1 million keys, 1-minute windows and 30 minutes of lateness is 1 million × 31 × about 50 bytes, near 1.5 GB, plus timers. I would also ask what share of events arrive later than 1 minute; if it is under 1%, I would use a short lateness and send the rest to a side output for a batch correction.
Why can the same Beam pipeline give different results on two runners? || The model fixes the semantics but not the details of watermark estimation, trigger firing times, bundle sizes or supported features. Early and late panes can differ, and runners that lack a state or timer feature fail or behave differently. The on-time final result should match when the sink is idempotent; I would test with a deterministic test stream (TestStream) on both runners.
You need exactly-once into a database sink. Does Beam give it? || Beam gives exactly-once effect on state inside the pipeline, but the sink sees at-least-once writes, because a bundle can be retried. I would make the write idempotent (upsert by key and window, which also suits accumulating panes) or use a sink with a transactional or deduplication protocol, as the BigQuery Storage Write API does.
@@+ delta
tradeoffs: Delta, Iceberg or Hudi. Choose Delta when Databricks or Spark is your main engine, because every new feature (deletion vectors, liquid clustering, change data feed, predictive optimization) arrives there first and works best. Choose Iceberg when several engines must read and write the same tables (Trino, Flink, Snowflake, Spark) and you want a vendor-neutral REST catalog; its snapshot tree and hidden partitioning are designed for that. Choose Hudi when the workload is record-level upserts from CDC at a high rate and you want its record index and merge-on-read tables tuned for it. You give up, with Delta, the most neutral multi-engine story (UniForm exposes Iceberg metadata but with feature limits); with Iceberg, some Databricks-only conveniences; with Hudi, a smaller ecosystem and more tuning knobs.
Partitioning, Z-order or liquid clustering. Hive-style partitioning works when a table is over about 1 TB, you filter on a low-cardinality column (usually date) in almost every query, and each partition holds at least 1 GB, so you do not create thousands of tiny files. Below that, or when the filter columns change, use liquid clustering: it is incremental, can be changed without rewriting the whole table, and replaces the fixed layout of partitions plus Z-order. You give up with clustering a hard physical boundary, so a delete of one month is no longer a metadata operation, and you pay clustering work in OPTIMIZE; with partitions, you pay in small files and in having to guess correctly once.
Deletion vectors or copy-on-write. Deletion vectors turn a DELETE or UPDATE touching 3 rows in each of 50 files into 50 small bitmaps instead of rewriting 50 GB, and make MERGE cheap when it changes under about 5–10% of the rows in the files it touches. They cost reads a small amount, because each scan applies the bitmap, and they raise the table's reader protocol so older engines cannot read it. Choose them for CDC upserts and privacy deletions on big tables; keep copy-on-write for tables rewritten wholesale each night, where every file changes anyway and the bitmaps are overhead.
Delta or plain Parquet files. Plain Parquet in a folder is enough for append-only data written by one job and read by one engine, and it avoids log maintenance. Choose Delta as soon as there are two writers, any update or delete, a need to roll back a bad load, or a need to know which files make up a consistent snapshot; the cost is one extra log read (a checkpoint plus a few JSON files, usually tens of milliseconds) per query and a commit rate of a few commits per second per table, because each commit is a conditional put on object storage that fails and retries under conflict. Do not use Delta as a queue: use kafka and write micro-batches of at least a few hundred megabytes per hour of data to it.
Retention is a three-way trade. The defaults keep 30 days of log (delta.logRetentionDuration) and 7 days of removed files (delta.deletedFileRetentionDuration). A longer period gives longer time travel and safer streaming restarts, but storage for the old files is paid in S3 at about $0.023 per GB-month; a shorter one saves money but makes VACUUM remove files that a slow reader or a replayed stream still needs. For GDPR-style deletion, remember that a DELETE is not final until VACUUM removes the old files, so retention is also a legal setting.
interview: When would you not use Delta Lake? || For a small append-only dataset with one writer and one reader, plain Parquet is simpler. When several non-Spark engines need full read-write access, Iceberg with a REST catalog is a better fit. When a workload is low-latency point lookups or high-rate row updates, a database such as postgres or a store like Pinot is the right tool, since Delta commits take hundreds of milliseconds and a table accepts only a few commits per second.
Two streaming jobs write to the same table and keep failing with conflicts. What do you do? || Commits use optimistic concurrency: both jobs read version N and the second to commit finds the first changed overlapping files, so it retries or fails. I would make their writes touch disjoint partitions or clustering ranges, add explicit conditions to MERGE so fewer files are involved, write in larger micro-batches, or send both jobs through one writer. Reducing commit frequency is usually the strongest lever.
How does Delta compare with Iceberg on how a reader finds the files of a snapshot? || Delta reads the last checkpoint and replays the JSON commits after it, so planning is a list-and-read of a bounded log. Iceberg follows a pointer from the catalog to a metadata file, a manifest list and manifests, which allows pruning by partition statistics at the manifest level. Both give snapshot isolation; Iceberg suits catalogs that coordinate many engines, Delta gives a very direct log.
A table has millions of small files from streaming. What are your options and their cost? || Run OPTIMIZE (bin-packing to about 1 GB files) on a schedule, or enable auto compaction and optimized writes so files are right-sized at write time, at the cost of extra shuffle and slightly higher write latency. I would also reduce the trigger frequency so each micro-batch writes a bigger file. Compaction rewrites data, so it costs compute and creates new files that must be vacuumed.
How do you make a Delta table support both time travel for 30 days and deletion of one user's data? || Time travel relies on old files that still contain the user's data. I would delete the rows, then run VACUUM with a retention that matches the legal deadline, accepting that time travel past that point is lost, or store the user's data in a separate table with shorter retention. This is a conflict between audit history and erasure, and it should be resolved as a written policy.
@@+ pinot
tradeoffs: Pinot, Druid or ClickHouse. Choose Pinot when the product is user-facing analytics with hundreds to thousands of queries per second and a p99 target under about 100 ms, when records need upserts by primary key (a latest-state table fed by CDC), or when the same group-by shapes repeat so star-tree indexes pay off. Choose ClickHouse when concurrency is modest (tens of queries per second), queries are wide ad-hoc scans over raw events, and you want one binary and flexible SQL with joins. Choose Druid when data is time-series, pre-aggregation at ingestion is acceptable, and its tiering and exactly-once Kafka ingestion matter. You give up, with Pinot, easy ad-hoc SQL (joins and window functions are newer) and a simple deployment; with ClickHouse, built-in upsert semantics and strong fanout for thousands of concurrent users; with Druid, cheap row-level corrections.
Pinot or a warehouse. Snowflake, BigQuery and Databricks answer a scan over billions of rows in seconds with strong joins, and are the right choice when fewer than about 50 people query at once and a 2 to 10 second answer is fine. They get expensive and slow to react when a public dashboard issues 1,000 queries per second, because each query needs warehouse compute and queueing appears. Pinot answers those queries in tens of milliseconds because the indexes and pre-aggregates are built into the segments; you pay with a second copy of the data (the Pinot tables) and a team that tunes indexes. Many designs keep both: the warehouse as the source of truth and Pinot as the serving layer for the few queries that face users.
Indexes are a storage-versus-latency decision per column. A sorted column costs nothing extra but only one column per segment can be sorted; inverted indexes add roughly 5–20% of the column's size for equality filters; range indexes serve numeric and time ranges; a star-tree index can take another 1–3 times the size of the pre-aggregated columns but bounds a group-by to a few thousand records per query. Choose star-tree for the 3 to 5 query shapes that fill a dashboard and are stable for months; choose inverted and range indexes when users build their own filters, because a star-tree only helps queries whose dimensions and aggregations it was configured for.
Upsert costs memory. Full upsert keeps a primary-key to record-location map on each server (in heap or off-heap), at tens of bytes per key plus the key itself, so a table with 1 billion keys needs tens of gigabytes across the servers and requires that the Kafka topic is partitioned by that key so each key lives on one server. Partial upsert, deletes and out-of-order handling add more. Choose upsert for state tables up to a few hundred million keys per server group; choose an append-only table with a "latest row per key" query or a periodic offline rebuild when keys are in the billions and a small delay in correction is acceptable.
Real-time, offline or hybrid tables, and segment size. A real-time table reads Kafka directly and gives freshness of a few seconds; an offline table is built from batch jobs into larger, better-compressed, better-sorted segments. A hybrid table serves the last days from real-time segments and the rest from offline segments, and is the usual choice for years of history; the cost is a daily job that must stay correct. Keep segments between 100 and 500 MB: under that, the broker and server handle too many segments per query (a 1 TB table in 10 MB segments is 100,000 segments to prune); over that, commits and recovery slow down.
interview: A dashboard query on Pinot is slow. Walk me through how you find out why. || I would check the query's response statistics: segments queried versus matched, entries scanned in filter versus post-filter, and docs scanned. Many segments queried means pruning is poor, so I would partition on the filter key or set time pruning. A high entries-scanned-in-filter count means a missing index on the filter column; high docs scanned with aggregations suggests a star-tree or a pre-aggregated table. I would also check broker-side merging of large group-by results and server GC.
Why partition both the Kafka topic and the Pinot table on the same key? || The broker uses the partition function to send a query that filters on that key only to the servers that hold the matching partition. This cuts work by the number of partitions (31 of 32 segments skipped with 32 partitions) and is required for upsert, since all versions of a key must be on the same server to be compared. The cost is that a hot key makes a hot partition.
Compare Pinot with Elasticsearch for log analytics. || Elasticsearch builds an inverted index for every field, so text search over messages is its strength, but aggregations over billions of rows are slower and storage per event is larger. Pinot stores columnar segments and is faster at group-bys and time-series counts, and it has a text index, but full-text relevance and free-form log exploration are less mature. For structured events with many aggregations I choose Pinot or ClickHouse; for searching messages I choose elasticsearch or opensearch.
How would you handle a schema change, for example a new column that should be backfilled? || A new column can be added to the schema and appears as null (or a default) in old segments; consuming segments pick it up on reload. To backfill, I would push replaced offline segments or reload segments with a transform function, which costs server CPU and I/O across the table. For a large table I would roll this out table by table, watching load, since the reload rebuilds indexes.
What are the failure modes when a server dies in the middle of a real-time ingest? || The consuming segment replicas on other servers continue, because each replica reads the same Kafka partition independently. The controller's segment-completion protocol makes one replica the committer; if it dies, another is chosen, and the rest catch up to the committed offset or download the segment from the deep store. With replication of 2 or more there is no data loss and a short pause in freshness; with replication of 1 the data is read again from Kafka after the server returns, if retention still allows it.
@@+ druid
tradeoffs: Rollup or raw events. Rollup merges rows with the same dimensions and time bucket at ingestion, so a stream of 2 billion events a day with 50,000 combinations per minute shrinks to 72 million rows, about 28 times fewer. Queries read less, segments are smaller, and dashboards answer in tens of milliseconds. You give up the original events: you cannot drill to one user's click, count a dimension you did not keep, or change the bucket size without reprocessing. Choose rollup when product queries are fixed aggregates (a minute or an hour granularity, tens of dimensions); choose no rollup, or keep raw data separately in the lake, when users investigate individual events or the rollup ratio you measure on a sample is under about 3 times, since then you pay the complexity for little gain.
Druid, Pinot or ClickHouse again, by workload. Druid fits time-partitioned data where most queries filter on a recent window, tiering older data to cheaper nodes, and exactly-once Kafka ingestion matter. Pinot fits when you need upserts and very high concurrency with star-tree indexes. ClickHouse fits when you want raw events, joins and a small number of services to run. Choose Druid when your analytics are mostly "count and sum by a few dimensions over time" and the team accepts a cluster of six service types; choose the others when updates and ad-hoc SQL dominate. The deciding factor in practice is often operations: a 3-person team running Druid on Kubernetes, with ZooKeeper, a metadata database and deep storage, carries more risk than one running a ClickHouse cluster.
Exact or approximate distinct counts. A count distinct of user IDs over a billion rows is expensive and cannot be re-aggregated across rollup buckets. A theta or HLL sketch uses a few kilobytes per group, merges across segments, and is accurate to about 1.6–2% at default sizes; theta sketches also support set operations (users who saw A and B). Choose sketches for audience and reach dashboards; choose exact counts only for small cardinalities or billing numbers, and then compute them in the warehouse (snowflake or bigquery) where the raw data is available.
Segment granularity and compaction. Hourly segment granularity keeps each segment small and lets late data update recent intervals cheaply, but a year of data becomes 8,760 segments per datasource, plus the extra small ones from late events. Daily segments reduce the count by 24 times, and are the right choice when ingestion is below roughly 5 million rows per day per partition or data is loaded in batch. Compaction merges segments back to a target near 5 million rows (300–700 MB), and costs a background job that reads and rewrites the interval; skipping it makes the Broker and Historicals touch thousands of tiny segments and raises latency steadily.
Native query engine or the multi-stage engine (MSQ). The native engine is fast for single-table scans and groupings with filters and is what dashboards use. The multi-stage engine supports shuffle joins, subqueries and SQL-based ingestion, which makes batch loads and some joins possible, but it is heavier and not tuned for 1,000 queries per second. Use native for serving and MSQ for ingestion and occasional joins; if your queries are mostly large joins, a warehouse or ClickHouse is a better fit.
interview: How do you decide on dimensions and metrics for a new Druid datasource? || I start from the dashboard queries: every column used in a filter or group-by is a dimension, every aggregated number is a metric with an aggregator (sum, count, a sketch). I choose the coarsest query granularity users accept, ingest a day of data, and measure the rollup ratio. If the ratio is poor because of a high-cardinality dimension such as user ID or URL, I drop it, hash it to a sketch, or move that analysis to the lake.
A user asks to delete their data from Druid. What happens? || Segments are immutable, so a delete means a compaction or reindex task that rewrites every segment of the intervals that contain the user's rows, and this can take hours on a large datasource. For regular privacy deletions I would avoid keeping user-level data in Druid, aggregate before ingestion, or batch deletions weekly in one rewrite job per interval.
Dashboard latency doubled after a week of heavy late-arriving data. What do you suspect? || Late events create new small segments for old intervals, so queries that touch those intervals open many more segments. I would check segment count and average size per interval, run or tune automatic compaction, widen the late-message window carefully, and consider a batch re-ingest for the affected days.
Explain how Druid gets fresh data to be queryable in seconds. || The real-time task holds recent rows in memory and exposes them to Brokers, which query them together with the immutable segments on Historicals. Periodically the task persists, then publishes finished segments to deep storage and the metadata store, and Historicals load them. A query therefore merges results from both, and nothing waits for a segment to be published.
What would make you move off Druid? || Frequent updates by key, the need for wide ad-hoc SQL with large joins, a team that cannot afford to operate six service types, or a rollup ratio too small to justify it. Then I would move to pinot for upserts and concurrency, clickhouse for flexible SQL and raw data, or a warehouse if latency of a few seconds is acceptable.
@@+ clickhouse
tradeoffs: ClickHouse or a cloud warehouse. Choose ClickHouse when queries must return in under a second on billions of rows, many users or services query at once (tens to hundreds of queries per second), and the data is append-mostly events, logs or metrics. Choose Snowflake or BigQuery when the workload is varied analyst SQL with large joins, usage is bursty, and nobody wants to run servers; a nightly job that scans 5 TB costs a few dollars of compute there and nothing while idle. You give up, with ClickHouse, elastic scaling and zero administration (unless you pay for ClickHouse Cloud) and the comfort of many-way joins; with the warehouse, the sub-second latency and the low cost per query at constant high load.
ClickHouse or Pinot and Druid. ClickHouse keeps raw events, runs flexible SQL, and answers a scan of a billion rows in about a second per node because it reads only the needed columns and granules and runs vectorized code on all cores. Pinot adds upserts, star-tree indexes and a design for thousands of concurrent queries; Druid adds rollup, tiering and exactly-once Kafka ingestion. Choose ClickHouse for observability, product analytics and internal analytics where the query set keeps changing; choose Pinot when a customer-facing application issues the same few query shapes at 1,000+ queries per second and needs row-level upserts. With ClickHouse at high concurrency, plan for one query using several cores and a ceiling of roughly 100 to 200 concurrent queries per node before latency degrades.
ClickHouse or DuckDB or Postgres. For a dataset under about 100 GB that one machine can hold, DuckDB (embedded, no server) or PostgreSQL with good indexes is often enough, and simpler: no Keeper, no parts, no merges. PostgreSQL stays comfortable for analytics up to a few hundred million rows if the queries filter on indexed columns; beyond roughly a billion rows, or when a group-by scans the whole table, a columnar engine is 10 to 100 times faster and compresses data 5 to 10 times better. Choose ClickHouse once the analytical scans, not the point lookups, are the bottleneck; keep postgres as the system of record and load ClickHouse by CDC.
Sorting key order is a trade between compression and pruning. Putting low-cardinality columns first (tenant, event type) clusters equal values, so they compress well and a filter on them reads a short contiguous range. Putting the most frequently filtered column first prunes best for that column. A common compromise is (tenant_id, event_type, toStartOfHour(ts)): the first two filter almost every query, and time comes last. A key of 3–4 columns is usual; a long key slows inserts and bloats the primary index (still only a few MB for a billion rows). If a second access path matters, a projection or a materialized view into a table with another sorting key costs another full copy of the columns it holds plus insert work, so add one only for a query that runs thousands of times a day.
Updates: choose the right MergeTree. ReplacingMergeTree keeps the newest row per key after background merges, so reads must use FINAL or argMax to be exact, which costs extra CPU (often 2 to 5 times slower for scans over large tables); lightweight updates and deletes are good for occasional corrections, but each one leaves a patch that reads must apply until a merge absorbs it. For continuous change streams from a database, choose a design that reads the latest row cheaply, such as a pre-aggregated table with argMax; for rare corrections, mutate. If more than a few percent of your rows change each day, reconsider whether ClickHouse is the serving layer.
interview: Why is a ClickHouse insert of one row at a time a bad idea? || Every insert creates a new sorted part on disk, and background merges must then combine them. At one row per insert you create thousands of parts per second, the merge process cannot keep up, and ClickHouse will start rejecting inserts with "too many parts". Batch at least thousands of rows (ideally 10,000–1,000,000) about once a second per table, or use async inserts or a Kafka engine, so parts stay few and large.
How do you choose partition key and sorting key for a 20 TB events table? || Partition by month or day, only for data lifecycle (drop or move old partitions) and not for query speed, because partitions multiply parts and merges. The sorting key comes from the filters: put the columns that almost every query filters on first, from low to high cardinality, then a time bucket. I check the result with EXPLAIN indexes = 1 and look at the ratio of selected granules to total granules.
A query that joins a 10-billion-row fact table to a 1-billion-row table runs out of memory. What are your options? || The default hash join holds the right side in memory, so first put the smaller table on the right, filter both sides early, and add a join algorithm that spills to disk (grace hash or partial merge). Better, denormalize the dimension into the fact table at ingestion, or use a dictionary for key-value lookups. If the workload is really many large joins, I would say a warehouse is the better tool.
How would you build a dashboard of daily active users over 2 years of raw data? || I would create a materialized view that feeds an AggregatingMergeTree table keyed by day and the dimensions, storing a uniq state (an HLL-style sketch) per group, and query it with uniqMerge. This turns a scan of billions of rows into a read of thousands of rows, at the cost of approximate counts (about 1% error with uniq; uniqExact is available) and storage for the aggregate state.
What happens to replica consistency when a node is down for an hour? || Replicated tables use Keeper to log inserts and merges; when the node returns it fetches the missing parts from other replicas, so it catches up without manual work if the replication queue is healthy. Reads from that replica may be stale until then, and a read-your-writes need requires select_sequential_consistency or reading from the replica that took the write. Keeper itself needs a quorum of 3 or 5 nodes.
@@+ lucene
tradeoffs: Embed Lucene or run a search server. Embed Lucene directly when one application owns the data, the index is below a few hundred gigabytes and fits one machine, and you want index and application in one process with no network hop: a typical query then takes 1 to 10 milliseconds. Run Elasticsearch or OpenSearch when the index must be sharded over several machines, replicated for availability, or shared by several services; they add the REST API, cluster state, shard routing and recovery. You give up, with embedding, replication, distribution and ready-made operations (you write the merge, backup and failover logic yourself); with a server, a few milliseconds of overhead, the cost of the cluster, and direct control of the Lucene settings.
Few large segments or many small ones. Searching one big segment is the fastest, since each term is looked up once and postings are contiguous; searching 50 segments does 50 term lookups and merges 50 result sets. But creating large segments means merging, and each merge rewrites the data again, so total write cost grows with the number of merge levels (write amplification of about 3 to 10 times is common with the default tiered policy). Choose to force-merge an index to a few segments when it is read-only (yesterday's logs, a catalogue rebuilt nightly); choose to let the policy run in the background when documents change continuously, since forcing merges there only moves the cost to the indexing path.
Which data structure for which field. The inverted index serves search and filters on a term; doc values, a columnar copy, serve sorting, aggregation and faceting; stored fields return the original document; points (BKD trees) serve numeric and range filters; vectors (HNSW) serve nearest-neighbour search. Each costs disk and indexing time: removing positions from a text field can cut its postings size noticeably but breaks phrase queries; disabling doc values on a field you never sort or aggregate saves its columnar copy; storing the source twice (stored fields and an external database) wastes space. Choose fields by the queries you will run, since the choice is fixed at index time and changing it means reindexing.
Lexical, vector or hybrid retrieval. BM25 over an inverted index finds exact words, names, codes and rare terms, runs in a few milliseconds over tens of millions of documents, and needs no model. Dense vectors (HNSW) find paraphrases and related meaning but need an embedding model, use memory (a 768-dimension float32 vector is 3 KB, plus graph links), and miss exact identifiers. For most search products a hybrid, with BM25 and vector results fused by reciprocal rank or a re-ranker, beats either alone. Quantizing vectors to 8 bits cuts memory 4 times for a small recall loss; binary quantization cuts 32 times but needs re-scoring with the full vectors. If vectors become the main workload at hundreds of millions of items, a specialized engine (Milvus, Pinecone) or pgvector for small sets may suit better.
Near-real-time freshness or throughput. Opening a new reader after a flush makes new documents searchable in about a second, but each refresh creates a small segment, which means more merges later and a cold cache for it. A bulk load that is not searched until it finishes can refresh every 30 seconds or not at all and be 20–50% faster; a user-facing search where a new product must appear at once cannot. Commit (fsync) is separate from refresh and is what makes data durable, so a crash loses unflushed documents unless a transaction log, like Elasticsearch's translog, replays them.
interview: Why is Lucene fast at search but updating a document is expensive? || Segments are immutable and compressed, with sorted term dictionaries and delta-coded postings, which is ideal for reading. An update is a delete (a bit set in the live-docs file) plus a new document in a new segment, and the old version only disappears when a merge rewrites the segment. A heavily updated index therefore grows with deleted documents and spends I/O in merges.
How does Lucene find the top 10 results for a query without scoring every matching document? || It runs the query term by term over postings in document-ID order and uses a priority queue of the best 10. With block-max WAND (or MaxScore), each block of postings stores its highest possible score, and whole blocks that cannot beat the current tenth-best score are skipped. For common terms this skips most of the postings.
How do you size memory for a Lucene-based server? || Give the JVM heap only what it needs (often under 30 GB so compressed object pointers still work, and around half of RAM at most), and leave the rest to the operating system page cache, because Lucene reads index files with mmap. A 100 GB index on a machine with 64 GB of RAM works only if the hot parts (term dictionaries, postings for common queries, doc values) fit in the cache; otherwise queries wait on disk.
When would you not use BM25 as the ranking function? || When queries are questions in natural language with little word overlap, when the corpus is very short texts, or when user behaviour (clicks, purchases) should drive ranking. Then I would add a learning-to-rank model on top of BM25 candidates, a vector retriever, or both. BM25 stays useful as a first stage that is cheap and explainable.
What happens to an index when two writers try to open it? || Lucene allows one IndexWriter per index directory and enforces it with a write lock file, so a second writer fails. Many readers can search concurrently. To scale writes you split into several indexes (shards), which is what Elasticsearch and OpenSearch do, and merge results at query time.
@@+ elasticsearch
tradeoffs: Elasticsearch or OpenSearch. Choose Elasticsearch when you want the newest features first from the vendor (ES|QL, newer vector and semantic search capabilities, the Elastic Cloud service) and the license terms (Elastic License or AGPL) are acceptable. Choose OpenSearch when you want a permissive Apache 2.0 license, you run on AWS where the managed service is native, or you must stay compatible with the 7.10 line of clients and tools. The core of indexing, shards and search is the same Lucene underneath. You give up, with either, easy movement between the two, since APIs and plugins have been drifting apart since 2021; test your clients and mappings before assuming a swap.
Search engine or analytical database for logs. Elasticsearch indexes every field, so searching a message for a word across 30 days is very fast and flexible, but the index costs disk (often 1 to 1.5 times the raw size, versus about one tenth of raw size in columnar engines like ClickHouse or Pinot) and aggregations over billions of rows are slower. Choose Elasticsearch for free-text search, relevance-ranked results and ad-hoc investigation across heterogeneous fields; choose ClickHouse or Pinot when the logs are structured and the usual query is a count, percentile or group-by over time; use Loki-style label-only indexing when storage cost matters most and grepping a time slice is acceptable.
Shard size and count. A good primary shard holds 10–50 GB: below that you spend heap and file handles on many tiny shards, since each shard is a Lucene index with its own segments and memory; above 50–100 GB, recovery and rebalancing take too long. A common rule is under about 20 shards per GB of heap per node. For time-series data, use rollover by size (for example at 30–50 GB) instead of a fixed number of daily indices; a 100 GB-per-day log stream then uses 2–3 shards per day, not 20. Replicas add read capacity and durability but double disk: with 1 replica, 2 TB a day for 7 days is 28 TB of raw disk before overhead.
Hot, warm, cold and frozen tiers. Recent data sits on fast SSD nodes with replicas; ILM moves it to cheaper nodes after days, shrinks and force-merges it, and later to searchable snapshots on object storage (s3), where queries read segments through a local cache. Frozen data costs a fraction of hot storage, perhaps one tenth, but queries run in seconds to minutes instead of milliseconds. Choose a long frozen tier for compliance logs that are rarely read; keep the 7–14 days that incident responders query on hot nodes.
Elasticsearch as the primary store or a derived index. Elasticsearch gives near-real-time search, not transactions: there is no multi-document transaction, a write is visible only after a refresh, and a mapping mistake needs a reindex. Keep the source of truth in a database such as PostgreSQL and feed the index through change data capture (debezium and kafka), so that you can rebuild it. Choose Elasticsearch as the primary store only for logs and events that can be lost or re-sent; accept that a rebuild of a large index takes hours.
interview: A search cluster has red status after a node failure. What do you do? || Red means at least one primary shard is unassigned. I check the allocation explain API to see why: disk watermarks, a missing replica copy because there was no replica, or allocation rules. If the node returns, the shard recovers from its disk; otherwise I restore from a snapshot. Prevention is at least 1 replica, snapshots to object storage, and capacity headroom below the 85% disk watermark.
Why does deep pagination get slower and what should you do instead? || With from and size, each shard must build a priority queue of from+size hits and return them, so asking for results 100,000 to 100,010 over 5 shards sorts 500,050 entries in the coordinating node. Use search_after with a point-in-time for sequential paging, or the scroll/PIT API for bulk export. The index also limits from+size to 10,000 by default.
You see mapping explosion and slow cluster state updates. What happened? || Dynamic mapping created a field for every new key in the JSON, such as user-supplied keys, and the cluster state (held on master and shared with all nodes) grew. Fix by using flattened or an explicit key-value structure for unbounded keys, setting dynamic to strict or false for the index, and keeping index.mapping.total_fields.limit (default 1,000) as a safety net.
How do you tune an index for a heavy one-time bulk load? || Set replicas to 0 and a long refresh interval (or -1) during the load, use bulk requests of 5–15 MB with parallel clients, and raise the translog flush threshold if the data can be re-sent. After the load, restore replicas and the refresh interval and force-merge if the index is read-only. The cost is that the data is unreplicated and invisible to search until you restore them.
When would you pick Elasticsearch over Postgres full-text search? || When the corpus is over a few million documents, you need relevance tuning, typo tolerance, facets, highlighting or multilingual analyzers, or the search load would hurt the transactional database. For a small corpus (a hundred thousand rows) with simple queries, postgres tsvector with a GIN index avoids a second system and a sync pipeline.
@@+ opensearch
tradeoffs: OpenSearch or Elasticsearch. Choose OpenSearch when an Apache 2.0 license and independent governance (the Linux Foundation) matter, when you want the AWS managed service (Amazon OpenSearch Service or Serverless), or when you depend on its bundled security, alerting and k-NN plugins without a paid tier. Choose Elasticsearch when you want the Elastic vendor's roadmap, ES|QL and the integrated Elastic Stack. You give up, with OpenSearch, Elastic's newest features and some client libraries (official Elastic clients now refuse to connect to forks); with Elasticsearch, the permissive license and the AWS-first operational story.
Segment replication or document replication. With document replication every replica re-indexes each document, so a cluster with 1 primary and 2 replicas does three times the indexing CPU. Segment replication has only the primary index and copies the finished segments to replicas, which saves indexing CPU on replicas (often 30–50% less in write-heavy workloads) and gives higher ingest throughput. The cost is slightly higher replica lag, more network traffic for copying segments, and a replica that, after a primary failure, has less data until the translog is replayed. Choose segment replication for log and metrics workloads that ingest heavily and tolerate a second of lag; choose document replication when search freshness on replicas is strict or write volume is low.
Which vector engine. Lucene's own engine supports efficient filtering during the graph search and is the simplest, but its graph and vectors rely on the page cache and fit best up to some tens of millions of vectors per cluster. Faiss supports HNSW and IVF with product quantization, uses native off-heap memory, and fits larger sets, with filtering less integrated for some modes. Memory is the cost to plan: 2 million 1,024-dimension vectors with M = 16 need several gigabytes with replicas, and 200 million need hundreds. Choose scalar or binary quantization and the on-disk mode when memory is the limit and you can accept a few points of recall; choose full-precision in memory when recall and latency under 20 ms are the priority. For a first prototype below 1 million vectors, pgvector in your database is often enough.
Index lifecycle for logs and traces. Daily indices are simple but produce many small shards on quiet days; rollover by size or age with Index State Management (ISM) gives even shards of 10–50 GB. UltraWarm and cold tiers on AWS, or searchable snapshots on S3, cut storage cost by several times compared with hot nodes, at the cost of slower queries. Choose a short hot window (3–7 days) for incident response and a long cold window for compliance. If observability data is mostly structured metrics and traces, compare with ClickHouse and Prometheus-style stores before committing to indexing every field.
Managed service or self-managed. Amazon OpenSearch Service removes patching, snapshots and node replacement and bills per instance-hour and storage, so a three-node, three-AZ domain has a baseline cost around which you cannot go lower; Serverless bills in OpenSearch Compute Units with a floor that makes small, quiet workloads relatively expensive. Self-managing on Kubernetes gives control of versions and plugins and is cheaper at steady large scale, at the cost of an on-call burden for shard allocation and upgrades. Choose managed until the monthly bill is large enough to pay for an engineer.
interview: Why did OpenSearch fork, and what are the practical consequences for you? || Elastic changed Elasticsearch's license in 2021 from Apache 2.0 to a source-available license, partly because of cloud providers selling it as a service; AWS forked the 7.10 code as OpenSearch. In practice, APIs diverge over time, official Elastic clients check the server product, and features such as ES|QL exist on only one side, so migrations need compatibility testing.
A cluster is slow at indexing and the CPU is 90% on data nodes. What would you change? || I would look at the number of replicas and the replication type: segment replication cuts replica CPU. Then raise refresh interval, use bulk requests of a few megabytes, reduce the number of indexed fields (map only the ones searched, disable doc_values or index on those not used), and check the shard count so each node has a sensible number of active shards. If it is still saturated, add data nodes.
How would you use OpenSearch for semantic search, and what can go wrong? || Create a k-NN index with a knn_vector field, produce embeddings at ingest (an ingest pipeline calling a model) and at query time, and combine with BM25 in a hybrid query. Problems include memory growth, embedding model changes that require reindexing all vectors, recall loss from quantization, and filters that reduce candidate sets so the approximate search returns too few results. I would measure recall against exact search on a sample.
How does a distributed search return the global top 10 from 5 shards? || The coordinating node sends the query to one copy of each shard; each returns its local top 10 with scores (query phase); the coordinator merges 50 candidates and picks the best 10, then fetches the documents for only those 10 (fetch phase). Scores use per-shard statistics unless you request global term statistics, so tiny shards can give slightly inconsistent ranking.
What is the cost of too many shards? || Each shard has its own segments, caches, file handles and thread pool use, and the master must track it in the cluster state. Thousands of tiny shards slow cluster state updates and waste heap; searches that touch hundreds of shards have high coordination cost. I would target shards of 10–50 GB, use rollover, and shrink or merge old indices.
@@+ snowflake
tradeoffs: Bigger warehouse or more clusters. Each size step doubles the credits per hour (X-Small 1, Small 2, Medium 4, Large 8) and, for a query that scales well, halves its time, so the credit cost of that query stays about the same while the wait shrinks. Choose a larger warehouse for one big scan, a heavy join that spills to local disk, or an ETL step on the critical path; spilling queries often become cheaper on a bigger size because they stop writing to disk. Choose a multi-cluster warehouse (the same size, up to N clusters) when the problem is many concurrent short queries queueing, such as a BI tool at 9 am. A bigger size does not help a query that is already limited by one slow stage or a small table. You give up, by scaling up, money when the query does not scale; by scaling out, cache warmth, because each new cluster starts with a cold local cache.
Auto-suspend: money against cache. Billing is per second with a 60-second minimum each time a warehouse resumes, so a Medium warehouse that wakes for a 15-second query every 10 minutes is charged 60 seconds plus the idle time before suspending. A 60-second auto-suspend minimizes idle charge but loses the local SSD cache, so the next query reads from object storage (slower by 2 to 10 times for a cold scan); a 10-minute suspend keeps the cache warm for dashboards that refresh every few minutes but pays for idle time. Choose 60 seconds for ETL and ad-hoc warehouses; choose 5–10 minutes for a BI warehouse used continuously through the day. Separate warehouses for ETL, BI and data science also give you per-team cost attribution.
Clustering key, search optimization or a different table. Natural load order by time gives excellent pruning on date and poor pruning on customer_id. A clustering key on customer_id sorts data in the background (automatic clustering is billed in credits), and is worth it for tables above roughly 1 TB with filters that select under about 1% of the data and data that changes slowly; for a table that is rewritten daily, the reclustering cost can exceed the savings. Search optimization service adds an index-like structure for point lookups and highly selective filters, at storage and maintenance cost. A materialized view or dynamic table pre-computes an aggregate when the same query repeats. Choose the cheapest that meets the latency target, in this order: better SQL filters, clustering, then search optimization.
Snowflake or Databricks, BigQuery and Redshift. Snowflake is the easiest to operate: SQL-first, no tuning of distribution or vacuum, instant clones, data sharing across accounts, and per-second compute. Databricks is stronger when the same platform must run Spark, ML and streaming over open Delta or Iceberg files; BigQuery has no clusters to size and bills per byte scanned or per slot; Redshift is cheapest for steady AWS-resident workloads with reserved capacity. Choose Snowflake for a SQL-centred analytics team that values low administration and cross-company sharing; choose a lakehouse when most data is already in open formats and ML is central. You give up with Snowflake the openness of data (unless you store in Iceberg tables) and a bill that can grow fast with careless warehouses.
Snowflake is not a serving database. A warehouse query has a floor of tens to hundreds of milliseconds for compile and scheduling, and 1,000 queries per second would mean many clusters running all day. For user-facing analytics with p99 under 100 ms, put Pinot or ClickHouse in front, fed from Snowflake or from Kafka. Hybrid tables handle low-latency single-row operations but are not a substitute for a primary OLTP system such as PostgreSQL at thousands of transactions per second.
interview: Your Snowflake bill doubled this quarter. How do you investigate? || I query the account usage views for credits by warehouse, user, query tag and hour. Typical causes are warehouses left running or with long auto-suspend, a new dashboard with a refresh every minute, queries that spill or full-scan because of missing filters, automatic clustering or materialized views on tables that change constantly, and big Time Travel retention on churning tables. I fix the largest item first, set resource monitors, and give each team its own warehouse so costs are attributable.
How do micro-partitions and pruning work, and when does pruning fail? || Each micro-partition (50–500 MB compressed) stores min, max and distinct counts per column. The optimizer compares a filter with those ranges and skips partitions that cannot match. Pruning fails when the filter column is not correlated with load order (a random customer ID), when the filter wraps the column in a function, or when the data was clustered on another column. Clustering keys or a different load order restore it.
Two teams need the same 20 TB table, one for ETL and one for dashboards. How do you set it up? || One copy of the data in storage, two warehouses: a large ETL warehouse with short bursts and a medium multi-cluster BI warehouse with a longer auto-suspend. Because compute is separate from storage, they do not compete for resources. The trade-off is that each warehouse keeps its own local cache and bill, so I tag and monitor both.
What are the risks of zero-copy cloning for a dev environment? || A clone shares the original micro-partitions, so it is instant and costs nothing until data diverges; after changes, only the changed partitions cost storage. Risks are production data (including sensitive columns) reaching a dev role, so masking policies or restricted roles must apply, and retained Time Travel on a heavily changed clone can raise storage. Clones also do not copy some objects, such as external-table data.
Why can a MERGE into a big table be slow, and what can you do? || MERGE has to find the matching micro-partitions and rewrite each one that holds a changed row, so scattered updates rewrite many 100 MB files for a few rows. Cluster or load the target in the order of the merge key so the touched rows are in few partitions, limit the source to the changed rows, and run it on a right-sized warehouse. If updates are continuous and small, consider a dynamic table or a design that appends and resolves the latest row at query time.
@@+ bigquery
tradeoffs: On-demand or reserved slots. On-demand charges about $6 per TiB scanned (check the current price) with a pool of slots shared by the project; editions charge per slot-hour (about $0.04 for Standard and $0.06 for Enterprise, with autoscaling and optional commitments). The break-even is simple: 100 slots running all month is roughly 100 × 730 h × $0.04 = $2,900, which equals about 470 TiB scanned on-demand. Choose on-demand when usage is small, spiky, or under that volume, and when a bad query that scans 50 TiB ($300) is acceptable or guarded with a byte limit. Choose editions when scans are large and steady, when you need predictable cost, or when one team must be isolated from another through reservations. You give up with on-demand cost predictability (one careless SELECT * is expensive); with reservations, you pay for idle slots and must manage assignments.
Partitioning and clustering: which, and how many. Partition on a date or integer column that almost every query filters by, so a 400-partition table with a 10-day filter scans 2.5% of the bytes. A table can have at most 10,000 partitions, and partitions smaller than about 1 GB are inefficient; for small tables, partition nothing. Cluster by up to four columns used in filters or joins, ordered from the most to the least frequently filtered; clustering is best-effort and refreshed in the background, and the exact bytes saved are known only after the query runs. Choose partitioning when you must bound cost and expire old data cheaply (partition expiration); choose clustering to speed up selective filters inside a partition. Require a partition filter on large tables to stop accidental full scans.
Normalized star schema or nested denormalized tables. BigQuery stores nested and repeated fields (ARRAY and STRUCT) in the columnar Capacitor format, so an order with its line items in one row avoids a join and scans only the sub-columns needed. Star schemas keep dimension updates simple and are what BI tools expect. Choose nesting for event data and one-to-many parent-child relationships queried together; choose a star schema when dimensions change often and are shared by many facts. Joins are well supported through the shuffle service, but a join between two huge unpartitioned tables still shuffles terabytes and consumes slots.
Ingestion path: batch load, streaming or Storage Write API. Load jobs from files are free and are the cheapest path for data that can wait minutes; the Storage Write API (about half the price of the older insertAll streaming) delivers data within seconds with exactly-once streams, and is right for event feeds. Choose batch loads from files in S3 or Cloud Storage for hourly or daily data; choose the Write API when dashboards need freshness under a minute. Keep in mind that data in the streaming buffer cannot be modified by DML for a short time.
BigQuery or a serving store. BigQuery answers a scan of terabytes in seconds, but even a small query has a start-up cost of about a few hundred milliseconds to one second, and concurrency of thousands of queries per second is not what it is designed for. BI Engine caching and materialized views bring dashboards to sub-second, but for customer-facing latency under 100 ms, load aggregates into Pinot or a key-value store. Choose BigQuery as the analytics source of truth and the batch brain; do not make it the request path of an application.
interview: A query scanned 8 TiB but only needed 200 GB of data. How do you reduce the cost? || Check which columns it reads (never SELECT *, because billing is per column bytes), whether the table is partitioned on the filtered column and the filter is a constant or simple expression that allows pruning, and whether clustering exists on other filters. Then consider a materialized view or an aggregate table for repeated queries. LIMIT does not reduce bytes billed. A dry run gives the estimate before running.
Explain slots and what happens when a query needs more than are available. || A slot is a unit of compute (CPU, memory and I/O) used by a stage of a query. A query's plan has stages that each ask for as many slots as they can use; if the reservation is full, work queues, and the query takes longer rather than failing. With on-demand pricing you share a pool of about 2,000 slots per project by default, with bursts; with editions you set a baseline and autoscale ceiling.
Why does BigQuery separate the shuffle service from the workers? || Shuffle data lives in a distributed in-memory (and disk-backed) service, not on worker disks, so workers are stateless and can be added, removed or restarted without losing intermediate results. This helps fault tolerance and elasticity, and allows the optimizer to repartition between stages. The cost is a network hop for every shuffle and a dependence on the shuffle service's capacity.
How would you do slowly changing updates on a large table? || BigQuery supports DML (MERGE, UPDATE), but each DML rewrites affected storage blocks and is subject to quotas, so many tiny updates are slow and costly. I would batch changes into a staging table and run one MERGE per interval, or append change rows with timestamps and use a view or materialized view for the latest state. For heavy row-level changes the Storage Write API's CDC support with upserts is an option.
Your pipeline joins a 10 TiB fact table to a 500 GB dimension and runs for 40 minutes. What do you check? || The execution graph for stage skew and bytes shuffled, then whether both sides are filtered or pre-aggregated before the join, whether the join keys are skewed (one value with a huge share), and whether clustering on the join key reduces shuffle. I would also check slot contention; if the job is slot-bound, a larger reservation may help more than rewriting the query.
@@+ redshift
tradeoffs: Provisioned or Serverless. Serverless bills RPU-seconds only while queries run (a 64-RPU workgroup at $0.375 per RPU-hour for 3 hours a day is about 64 × 3 × 30 × $0.375, roughly $2,160 a month), and scales with demand, so it fits workloads that are idle most of the day, unpredictable, or small. A provisioned RA3 cluster costs the same every hour of the month but can be cut by 1-year or 3-year reserved pricing (discounts of roughly 30–60%), so it wins for steady, near-24-hour load. Choose Serverless for new, spiky or development workloads and Provisioned with reservations once the base load is known. You give up, with Serverless, cost predictability unless you set a maximum RPU and usage limits; with Provisioned, the elasticity, because resize takes minutes and concurrency scaling covers only bursts.
Distribution style, per table. ALL copies a small dimension (your 20,000-row table) to every node, so joins to it need no network movement, at the cost of storage times the node count and slower loads; choose it for dimensions under a few million rows. KEY places rows by a column so two large tables joined on the same key sit together and the join is local, but a skewed key (one customer with 30% of rows) overloads one slice. EVEN spreads rows round-robin and is safe when there is no dominant join. AUTO lets Redshift choose and change it as the table grows; start there, and set KEY only when you see large redistribution steps (DS_DIST_BOTH) in the query plan. You give up with KEY the freedom to join on other columns cheaply.
Sort keys and encoding. A compound sort key on the column used by range filters (often the event date) makes zone maps prune blocks, so a one-day filter on a year of data reads about 1/365 of the blocks. Interleaved sort keys serve several filter columns equally, but they make loads and vacuums heavier and rarely win; automatic table optimization usually picks a good compound key. Column compression (ZSTD or AZ64) typically shrinks data 3 to 5 times. Choose a sort key for the most selective, most common filter; skip manual tuning if AUTO and automatic vacuum keep up.
Warehouse in Redshift, or lake query with Spectrum and Athena. Local RA3 tables on managed storage give the lowest latency, with strong joins on collocated data, and are right for the hot, frequently queried data, the last year of facts for example. Spectrum reads Parquet in S3 (s3) at a per-TB-scanned price, scales independently, and is right for cold history and shared lake tables, but is slower (seconds more) and cannot use sort keys and distribution. Many designs keep recent facts in Redshift and older ones in the lake, with a view that unions them. Compare also Snowflake, BigQuery and Databricks SQL when you are not tied to AWS.
Concurrency: queues, concurrency scaling or separate clusters. Workload management with query queues and short-query acceleration stops a long ETL query from blocking dashboards on the same cluster. Concurrency scaling adds transient clusters for read bursts (a free daily credit, then per-second billing), and data sharing lets a second cluster or workgroup read the same data without copying it. Choose separate workgroups per workload when ETL and BI have different peak hours; choose concurrency scaling for rare bursts. Redshift still has far less per-query elasticity than BigQuery's slots or Snowflake's resize.
interview: A join between two big tables is slow and the plan shows DS_DIST_BOTH. What does it mean and how do you fix it? || It means both tables are redistributed across the network at query time because they are not collocated on the join key. Distribute both tables with KEY on the join column, so the matching rows live on the same slice, provided the key has no heavy skew. If one table is small, use ALL. Check the plan again for DS_DIST_NONE.
How do zone maps and sort keys decide how much data a query reads? || Each 1 MB block records the min and max of its values. If rows are sorted by date, a date filter matches a few contiguous blocks and the others are skipped. If the data is unsorted, each block spans the full range and nothing is skipped. After many inserts or deletes, unsorted regions grow and vacuum sort restores order, which automatic vacuum handles in the background.
Why is Redshift poor at single-row inserts, and how do you load data? || Each COPY or INSERT commit goes through the leader node and a commit queue, and each insert creates data in small blocks that must be sorted and compacted; many single-row inserts are slow and fragment the table. Use COPY from files in S3 with a number of files that is a multiple of the slice count, or use the streaming ingestion from Kinesis or Kafka into a materialized view, and batch changes with MERGE.
When would you move from Redshift to another system? || When workloads need elastic compute per query (hundreds of concurrent users, spiky), when most data is already open-format in a lake and multi-engine access matters, when you want almost no tuning, or when you leave AWS. Then Snowflake, BigQuery or a Delta/Iceberg lakehouse fits better. Staying with Redshift is rational for AWS-centred, steady workloads with reserved pricing and tight integration with other AWS services.
How would you control cost for a Redshift Serverless workgroup? || Set a maximum RPU capacity and usage limits with an action (alert or stop), choose a base capacity that matches typical queries rather than the peak, use materialized views and result caching for repeated dashboards, and review the long-running queries. Because billing is per second with a 60-second minimum per charge, many tiny queries spread across the day keep the workgroup awake, so batching them helps.
@@+ postgres
tradeoffs: PostgreSQL or MySQL. Choose PostgreSQL when you need rich types and SQL (JSONB, arrays, ranges, window functions, CTEs), strong constraints, extensions (PostGIS, pgvector, TimescaleDB), partial and expression indexes, or serializable isolation that really works. Choose MySQL (InnoDB) when reads by primary key dominate, the team already runs it with Vitess or similar sharding, or you value its simple replication tooling and the clustered index's locality for range scans by primary key. In practice both handle tens of thousands of simple transactions per second on one good machine. You give up, with PostgreSQL, cheap updates of wide, heavily indexed rows (every update writes a new row version and may touch every index unless it is a HOT update) and the need to manage vacuum; with MySQL, the extension ecosystem and some SQL features.
Stay on one PostgreSQL node, add replicas, partition, or shard. A well-tuned single node with NVMe storage handles 1–10 TB and several thousand to tens of thousands of transactions per second, and is the right default for years. Add read replicas when reads dominate and slightly stale reads are acceptable (asynchronous lag is usually milliseconds but can reach seconds under write bursts). Use declarative partitioning when tables pass about 100 GB and old data is dropped by range, because dropping a partition is instant and avoids vacuum on dead rows. Shard (Citus, application-level) only when one node's writes or storage are exhausted, because cross-shard transactions, joins and migrations become your problem. If you need global distribution or horizontal scale from day one, compare cockroach, spanner and tidb.
Connections and pooling. PostgreSQL uses a process per connection, each using several MB and competing for locks, so performance drops after a few hundred active connections on typical hardware. Put PgBouncer (transaction pooling) in front, which lets thousands of clients share 50–200 server connections; the cost is that session features (prepared statements by name in older modes, advisory locks, SET) need care. Choose a pool size near 2–4 times the CPU cores for CPU-bound work; larger pools mostly add contention.
Isolation level. Read Committed (the default) gives each statement a fresh snapshot and is fast and simple, but allows non-repeatable reads and lost updates unless you use SELECT FOR UPDATE or atomic updates. Repeatable Read gives one snapshot per transaction and fails with a serialization error on conflicting updates. Serializable (SSI) prevents all anomalies without blocking, at the price of tracking read dependencies, some false-positive aborts, and a need for the application to retry. Choose Read Committed with explicit locks for simple CRUD; choose Serializable for invariants spanning rows (booking, ledger balances) when you are willing to retry transactions.
Postgres as the one database or alongside specialized stores. PostgreSQL with pgvector handles vector search for a few million vectors, tsvector handles full text for modest corpora, and JSONB with GIN indexes handles semi-structured data; one system means one backup and no sync pipeline. Move to a separate system when the load changes shape: analytics over billions of rows (ClickHouse or a warehouse, fed by CDC), search relevance at scale (Elasticsearch), or hundreds of millions of vectors. Keep PostgreSQL as the system of record.
interview: Why does PostgreSQL need vacuum, and what happens if autovacuum falls behind? || An UPDATE or DELETE leaves the old tuple version in the heap because other transactions may still see it; vacuum removes versions no snapshot needs, updates the visibility map and free-space map, and freezes old tuples. If it falls behind, tables and indexes bloat, scans slow down, and in the extreme the transaction ID wraparound protection forces an emergency shutdown to writes. I tune autovacuum per table (lower scale factors on big tables), watch long-running transactions and replication slots that hold back cleanup, and monitor dead tuples.
A table update is slow because the table has eight indexes. What can you do? || Each non-HOT update writes a new tuple and a new entry in every index. I would drop unused indexes (check pg_stat_user_indexes), keep the updated columns out of indexes so HOT updates are possible, and lower fillfactor (for example 80) so the new version fits in the same page. If the table is write-heavy with many indexes, that cost is inherent to PostgreSQL's design.
How does streaming replication work and when is synchronous replication acceptable? || The primary ships WAL records to replicas that replay them. Synchronous mode waits for at least one replica to flush (or apply) the commit before acknowledging, so a primary failure loses no committed data, at the price of added latency (one network round trip, often 1–5 ms in a region) and stalls if the replica is down unless several candidates are configured. Use it for financial or critical data and keep async for the rest.
How would you add a column or index to a 2 TB table with no downtime? || Adding a nullable column or one with a constant default is a metadata change in recent versions. For an index, use CREATE INDEX CONCURRENTLY, which builds in two passes without blocking writes, takes longer, and can leave an invalid index on failure that must be dropped. For rewriting changes (type change), I would add a new column, backfill in batches, switch the application, then drop the old column, and always set lock_timeout so DDL queues do not block traffic.
What goes wrong with a long-running transaction? || It holds a snapshot, so vacuum cannot remove tuples newer than its start, causing bloat across the database; it also holds locks, and an idle in transaction session can block DDL which then blocks everything behind it. Set idle_in_transaction_session_timeout and statement_timeout, and watch pg_stat_activity.
@@+ mysql
tradeoffs: UUID or sequential primary key. In InnoDB the table is a B+tree ordered by primary key, so a random UUIDv4 inserts into random leaf pages: the working set must stay in the buffer pool, pages split about half-full, and the table can be 30–50% larger than with an increasing key. Every secondary index also stores the primary key, so a 36-character UUID string (36 bytes) against an 8-byte BIGINT inflates every secondary index by 28 bytes per entry; with five indexes and 1 billion rows, that is on the order of 140 GB extra. Choose an auto-increment BIGINT for a single database; choose a time-ordered ID (UUIDv7, Snowflake-style ID) when many services must generate IDs without coordination; use BINARY(16) rather than text. Pay the random-UUID cost only when you must hide order and can afford memory.
Read Committed or Repeatable Read. MySQL defaults to Repeatable Read, which takes next-key (gap) locks on range scans to prevent phantoms, so concurrent inserts into a range can block and deadlocks are common in busy tables. Read Committed takes fewer gap locks, reduces deadlocks, and is what many large MySQL users run (it requires row-based binary logging). You give up repeatable reads inside a transaction, so two reads of the same query can differ; choose Read Committed for high-concurrency OLTP and Repeatable Read when transactions do multi-step reads that must see one snapshot.
Replication topology. Asynchronous replication is simple and fast, but a primary failure can lose the last transactions and replicas lag under heavy writes, so reads from replicas need tolerance to staleness. Semi-synchronous replication waits for one replica to receive the event (adds roughly one network round trip), cutting the loss window to near zero. Group Replication (InnoDB Cluster) gives automatic failover with a consensus protocol, at the price of write latency and a limit on the practical size (about 5–9 members). Choose async plus semi-sync for most; choose Group Replication when you want automatic failover without external tooling. For horizontal write scaling beyond one primary, look at Vitess, TiDB (a MySQL-compatible newsql system) or Aurora.
Buffer pool and durability settings. Setting innodb_buffer_pool_size to 60–75% of RAM keeps the hot working set in memory; going higher risks swapping because of per-connection buffers and the OS. innodb_flush_log_at_trx_commit = 1 with sync_binlog = 1 makes every commit durable at the cost of one or two fsyncs (about 1–5 ms on flash, so ~200–1000 commits per second per connection thread, grouped by group commit to thousands in total); setting it to 2 raises throughput several times but can lose up to a second of commits on an OS crash. Choose 1 for money and orders, 2 for caches, sessions and metrics.
Schema changes on big tables. Online DDL in InnoDB (ALGORITHM=INSTANT for adding a column at the end, INPLACE for many index changes) avoids locks for many cases, but some changes rebuild the whole table and replicas must replay them, causing lag. Tools such as gh-ost or pt-online-schema-change copy rows in the background and cut over, using a shadow table at the cost of extra disk (the table size again) and several hours on a 1 TB table. Choose INSTANT or INPLACE when documented as supported; choose gh-ost for risky changes where you need to throttle and pause.
interview: What is stored in an InnoDB secondary index leaf and why does it matter? || The indexed columns plus the primary key value. A lookup goes down the secondary index, gets the primary key, then goes down the clustered index to fetch the row (a "double lookup"), unless a covering index includes every needed column. It means a wide primary key bloats all secondary indexes, and that covering indexes pay off on hot read queries.
How does MVCC work in InnoDB compared with PostgreSQL? || InnoDB updates the row in place in the clustered index and stores older versions in undo logs, linked through a roll pointer in the row; a reader with an older snapshot follows the chain to rebuild the old version. PostgreSQL leaves the old tuple in the heap and uses vacuum to clean it. InnoDB avoids table bloat from updates but a long-running transaction makes the undo history (and the purge lag) grow.
A deadlock appears in production at 500 transactions per second. How do you handle it? || Read the latest detected deadlock with SHOW ENGINE INNODB STATUS to see the two statements and the locks. Typical fixes are accessing rows in a consistent order, making transactions shorter, using an index so a statement locks fewer rows, using Read Committed to avoid gap locks, and retrying the victim transaction because InnoDB rolls one back automatically. Deadlocks cannot be eliminated entirely, so the application must retry.
Why can a replica lag far behind the primary, and what can you do? || Historically the replica applied events in one thread, so a primary with many parallel writers outran it. Use multi-threaded replication with a writeset-based dependency tracking, avoid giant transactions (a 10-minute DELETE replays as a 10-minute event), and keep replicas on the same hardware class. Monitor lag in seconds and route latency-sensitive reads to the primary.
When would you pick MySQL over PostgreSQL for a new system? || When the team has deep MySQL operations experience, when the workload is key-based reads and writes at very high rates and the managed service or sharding layer (Aurora, Vitess) is the plan, or when you need HeatWave for analytics beside InnoDB. For complex queries, strict constraints and extensions, I would pick postgres.
