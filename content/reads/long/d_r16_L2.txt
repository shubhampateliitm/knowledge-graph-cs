@@ lamport
value: A Lamport clock is a counter that lets machines agree on an order of events without trusting any physical clock. Each process keeps one integer. It adds one before each event, stamps every message with its value, and on receiving a message jumps ahead of the stamp it received. The result is a number on every event with one guarantee: if event A could have influenced event B (A "happened before" B), then A's number is smaller than B's.
The problem it solves is old and hard. Two servers in different data centres cannot say which of two events came first by reading their clocks, because the clocks disagree by milliseconds or more, and messages take unpredictable time. Leslie Lamport's 1978 paper showed that for most purposes you do not need real time. You need an order that respects cause and effect. If a message from A reaches B, then whatever A did before sending must come before whatever B does after receiving. Everything else is a free choice, and any consistent choice is fine.
This is the base layer for the rest of distributed systems. Lamport timestamps plus a tie-break on process id give a total order on all events, and with a total order you can build a replicated state machine: every replica applies the same commands in the same order and ends in the same state. Raft terms, Paxos ballot numbers, version vectors, hybrid logical clocks and the ordering of a commit log all grow from this idea. It stands on two lower concepts. Distributed systems theory (L3) supplies the model: no shared memory, no global clock, messages with unbounded delay. Order theory (L4) supplies the mathematics: "happened before" is a strict partial order, and a Lamport clock is a function from that partial order into the integers that never reverses an ordered pair.
terms: Event — one step at one process: a local computation, a send, or a receive.
Happened-before (→) — the smallest relation where (1) events in the same process are ordered by their execution order, (2) a send happens before its matching receive, and (3) it is transitive.
Concurrent — two events where neither happened before the other; no chain of messages connects them.
Logical clock — a counter that is advanced by rules about events and messages, not by physical time.
Clock condition — if A → B then C(A) < C(B); this is the one promise a Lamport clock makes.
Total order — an order in which every pair of events is comparable; Lamport builds it by sorting on (timestamp, process id).
Partial order — an order in which some pairs are not comparable; happened-before is one, because concurrent events have no order.
Replicated state machine — copies of a deterministic program that stay identical by applying the same inputs in the same order.
history: Leslie Lamport published "Time, Clocks, and the Ordering of Events in a Distributed System" in Communications of the ACM in July 1978. He has said that the idea came from reading a paper on replicated databases by Robert Thomas and Paul Johnson, which used timestamps to order updates. Lamport saw that their scheme could violate causality, and that the cure was to make clocks obey the happened-before relation. He then noticed that the same trick gives a general method for building any distributed system as a state machine.
The paper has three parts. First, it defines happened-before and shows that events form a partial order, not a time line. Second, it gives the logical clock and the total order. Third, it uses the total order to solve a concrete problem, distributed mutual exclusion, and then discusses physical clocks and how closely they can be synchronised so that the system also respects what a human observer sees. It is one of the most cited papers in computer science, and it won the ACM SIGOPS Hall of Fame Award.
The next steps came quickly. Fidge (1988) and Mattern (1989) independently invented vector clocks, which keep one counter per process and so can detect concurrency, something a single Lamport counter cannot do. Lamport's later work built on the state-machine idea: the Paxos protocol (written around 1989, published in 1998) gets machines to agree on the order of commands without a central clock. Dynamo (2007) used vector clocks for versioning. Hybrid logical clocks (2014) joined Lamport's logic to physical time. Today the idea is so common that it is often invisible: a Raft term, an etcd revision or a Kafka leader epoch is a logical clock under another name.
how: The rules are very short. Each process P keeps an integer C, starting at 0. Rule 1: before each event at P (a local step or a send), P sets C = C + 1. Rule 2: when P sends a message, it attaches the current C as the message's timestamp T. Rule 3: when P receives a message with timestamp T, it sets C = max(C, T) + 1, and this new value is the timestamp of the receive event. That is the whole algorithm. It needs no extra messages and one integer per process.
Why does this satisfy the clock condition (A → B implies C(A) < C(B))? Check the three cases of happened-before. If A and B are in the same process, A came first, and C only increases, so C(A) < C(B). If A is a send and B is its receive, rule 3 forces C(B) to be at least T + 1, and T = C(A), so C(B) > C(A). If A → X → B by a chain, apply the two cases step by step: the numbers go up at every link, so they go up end to end. The proof is three lines because the rules were chosen to make it so.
The converse is false, and this is the key limit. C(A) < C(B) does not mean A happened before B. Two events that are concurrent get numbers that still compare one way or the other. If P1 has done five local steps and P2 has done two, an event at P1 with number 5 is not "after" an event at P2 with number 2; they may not be connected at all. So a Lamport timestamp can order events, but it cannot tell you whether two events are causally related. Vector clocks fix this by storing one counter per process, at a cost of O(N) space per timestamp.
To make a total order, sort events by the pair (C, process id). Two different events at the same process always have different C, so ties can only occur between different processes, and the process id breaks them. The tie-break is arbitrary, but it is the same everywhere, so every process that sees the same events sorts them the same way. This total order is consistent with causality: if A → B, then A sorts before B.
Lamport used this total order for distributed mutual exclusion, to show its power. To enter a critical section, process Pi stamps a request with (C, i) and sends it to all other N − 1 processes, putting it in its own queue. Every process that receives a request puts it in its queue and sends back an acknowledgement. Pi may enter when its own request is first in its queue under the total order and it has received a message with a later timestamp from every other process. On leaving, it sends a release message to everyone, and they remove the request. Each entry costs 3(N − 1) messages. The paper assumes messages between each pair arrive in order and none are lost. It also has a weakness: if any process stops, everyone waits. That weakness is why practical systems later moved to consensus protocols, which tolerate failures.
The same idea gives a replicated state machine. Each client command gets a timestamp, and all replicas apply commands sorted by the total order. A replica can apply a command only when it knows that no command with a smaller timestamp can still arrive, which it learns from hearing a later timestamp from every other replica. This is the "stability" condition, and it is the origin of the idea of waiting for a quorum or a heartbeat before committing.
Finally, the lower layers matter in a precise way. Distributed systems theory tells us why we must do this at all: with unbounded message delay and no shared memory, physical timestamps cannot be trusted to order events. Order theory tells us what we can hope for: a partial order cannot be turned into numbers that preserve every comparison with one integer per event, but it can be mapped to numbers that never contradict it. A Lamport clock is exactly such an order-preserving map, and the sort by (C, id) is a standard way to extend a partial order to a total order (a linear extension).

example: Use three processes P1, P2 and P3, all counters at 0, as in the diagram. At P1, event a is a local step: C becomes 1. Then P1 sends message m1 to P2. The send is event b, so C becomes 2 and m1 carries timestamp 2. Meanwhile P2 does a local step c: its C becomes 1. Now P2 receives m1. By rule 3, C = max(1, 2) + 1 = 3, so the receive d has timestamp 3. P2 then sends m2 to P3. The send e has timestamp 4, and m2 carries 4.
At P3, two local steps f and g give C = 1 and then 2. Now m2 arrives. C = max(2, 4) + 1 = 5, so the receive h has timestamp 5. The chain a → b → d → e → h has timestamps 1, 2, 3, 4, 5, which is increasing, as the clock condition promises.
Now look at what the numbers do not say. Event f at P3 has timestamp 1 and event b at P1 has timestamp 2. Is f before b? No. There is no message path between them, so they are concurrent. But 1 < 2, so a reader who trusts the numbers would wrongly believe f came first. Likewise a at P1 and c at P2 both have timestamp 1. To produce a total order we sort by (C, id): a is (1, P1), c is (1, P2), f is (1, P3), so the order is a, c, f, then b (2, P1), g (2, P3), and so on. The order puts a before c although neither caused the other. That is acceptable, because any order that respects causality is a valid history.
Now use the order for a lock. Suppose P1 requests the lock at timestamp (5, P1) and P2 requests it at (5, P2) at about the same time. Each process sorts the two requests the same way, with P1 first, because 5 = 5 and P1 < P2. P1 enters. P2 waits until it sees P1's release. Nobody needed a central server or a real clock. With N = 3 the cost is 3 × (3 − 1) = 6 messages per entry. With N = 100 it would be 297, which shows why this algorithm is a teaching tool and not a production lock.
intuition: Two people who never share a watch can still agree on "before" if each says "my next event is later than anything I have heard about".
The design is natural because order only matters where information flows. If nothing connects two events, no observer anywhere could ever tell which came first, so any choice is correct. If something connects them, one event could change what the other one does, so the order must be fixed. A Lamport clock records exactly the flow of information: it grows when a process learns something new from another process, and not otherwise. It is a clock that measures knowledge, not seconds.
mistakes: People often think a smaller Lamport timestamp means "happened earlier". In fact the rule works in one direction only: if A happened before B, then C(A) < C(B). Two concurrent events can have any relative numbers, so you cannot use timestamps to detect that two writes conflicted. Vector clocks or version vectors are needed for that.
People often think Lamport clocks are related to wall-clock time. In fact the number has no unit. A process that sends many messages can have a counter far ahead of real time, and a quiet process stays low. A timestamp of 1,000,000 does not mean one million of anything physical. If you need to show users a time, or expire data after an hour, you need physical time (or a hybrid logical clock).
People often think the tie-break by process id makes the order "fair" or "real". In fact it is arbitrary. It is only useful because every process applies it the same way. If process ids are fixed, the lowest-numbered process always wins ties, which can matter in a lock when many requests are tied.
People often think a Lamport-clock lock is practical. In fact the original algorithm needs reliable in-order delivery and every process to answer, so one crashed process blocks everyone. Real systems use consensus (Paxos, Raft) or a lock service with leases and fencing. The paper's value is the idea of a deterministic order, not that specific algorithm.
friction: The main limit is the one already mentioned: a Lamport timestamp cannot tell concurrent events from ordered events. If your system must detect conflicting writes, as Dynamo-style stores do, you need vector clocks, at O(N) bytes per timestamp where N is the number of writers. When N grows to thousands of clients, vector clocks become large, and systems prune them or move the tracking to the servers.
There is a second limit with physical reality. Lamport's paper points out the "anomalous behaviour" problem: a user can make a request on one machine, phone a friend, and the friend makes a request on another machine. The two requests are causally linked in the real world, but not through any message the system saw, so the logical clocks may order them the wrong way. Systems that must avoid this need clocks tied to real time (TrueTime, hybrid logical clocks) or must route the dependency through the system itself.
The third limit is liveness. Ordering a request only means something once you know that nothing earlier can still arrive. That needs messages from every process (or a quorum), so a slow or silent process delays everyone. This is a general rule: without a bound on delay, you cannot be sure you have seen all earlier events, which is the root of the failure-detection problem. Finally, there is the question of counter drift. If one buggy process sends a huge timestamp, every other process jumps to it and stays ahead. Counters are 64-bit in practice, so overflow is not a worry, but a corrupted value can still break meaning, so some systems check that timestamps stay within a sane range.
practice: Use Lamport-style logical clocks whenever you need an order that respects causality but not real time. Examples: a per-partition offset in a log, a version number that is bumped when a leader changes (a Raft term or Kafka leader epoch), or a sequence number in a message protocol. In all of these, "take the max of what I have seen and add one" is the key operation. When you design such a field, say which relation it respects, and say how ties are broken.
Pair the logical clock with an id whenever you need a total order, and keep the pair together in storage. For last-writer-wins stores, a (counter, node id) pair is deterministic: two replicas that see the same writes pick the same winner. Remember that "last" means "highest in the logical order", not "latest in real time", and tell product owners, because users may see an older-looking edit win.
If you need to detect conflicts, choose a vector clock or version vector. If you need timestamps that are close to real time and fit in one 64-bit field, choose a hybrid logical clock. If you need an order that also matches what outside observers saw, you need hardware clocks with bounded error and a commit wait, as in TrueTime. Do not roll your own consensus on top of Lamport locks. Use a coordination service with fencing tokens, and treat Lamport's mutual exclusion as a way to understand why ordering and agreement are separate problems.
When debugging distributed traces, remember that spans from different hosts have unreliable wall-clock times. Tracing systems often show a causal order from parent-child links and message links, which is the happened-before relation again. When logs from two machines look inconsistent, check the causal links before you trust the timestamps.
tradeoffs: Choose a Lamport clock when you only need an order consistent with causality, you want O(1) space per event (one 64-bit integer), and you do not need to detect concurrent updates. Choose a vector clock when you must tell "B saw A's write" from "A and B wrote independently", for example in a store that keeps sibling versions; you pay O(N) space per timestamp for N writers, which is fine for 3 to 10 replicas and poor for thousands of clients.
Choose physical timestamps (NTP-synchronised, with microsecond or nanosecond fields) when users and operators need to read times, when you need to expire data, or when you accept last-writer-wins with occasional lost updates when clocks are off by tens of milliseconds. Choose a hybrid logical clock when you want both: a value within the clock-error bound of real time, and causality kept. You give up pure independence from clock quality, because correctness of some features now depends on bounded skew.
Choose a central sequencer or timestamp oracle (as TiDB's placement driver does, or a single Kafka partition leader) when a total order is required and a single machine can hand out 100,000 or more numbers per second. You get an easy total order and strong guarantees, and you pay with a round trip per number (or batching) and a single point to make highly available. Choose Lamport-style decentralised ordering when there is no natural central point or when latency to a central point would be too high, and accept that stability (knowing no earlier event is missing) needs input from every process.
Choose consensus (Raft, Paxos) over a Lamport mutual-exclusion protocol whenever processes can fail. The cost is at least one round trip to a majority per decision, but the system survives the loss of a minority of machines.
interview: Define happened-before and explain why it is only a partial order. || It is the smallest transitive relation containing "earlier in the same process" and "send before receive". Events with no message path between them are concurrent, so neither is before the other, and the relation does not order all pairs. That is why a single time line is the wrong model for a distributed system.
Prove that a Lamport clock satisfies the clock condition, and then show why the converse fails. || If A and B are in one process, the counter only grows. If A is a send and B its receive, B gets max(local, T) + 1 > T = C(A). Transitivity covers chains. The converse fails because concurrent events can have any numbers: a process with a high counter has events numbered high even if they relate to nothing at a process with a low counter.
How do you build a total order from Lamport timestamps and why does a replica need to wait before applying a command? || Sort by (timestamp, process id). A replica may apply a command only when it knows that no command with a smaller pair can still arrive, which means it must have seen a later timestamp from every other process (or a quorum, in practice). Otherwise a late message would arrive in the past and break the order.
Lamport's mutual exclusion uses 3(N − 1) messages per entry. Why is it not used in production, and what replaces it? || Every process must answer, so one crash blocks everyone, and it assumes reliable in-order delivery. Production systems use consensus (Raft or Paxos) or a lock service with leases, and they add fencing tokens because leases alone can be wrong after a pause.
A user edits a document on machine 1, then calls a colleague who edits it on machine 2. Can Lamport clocks order these correctly? || Not necessarily. The dependency passed through the real world, not through a system message, so the clocks did not see it, and machine 2's edit may get a smaller timestamp. You need real-time-bounded clocks with commit wait, or you must pass the dependency through the system, for example by returning a timestamp token to the user that the next request carries.

quiz: What are the three rules of a Lamport clock? || Before each event, increment the counter. Attach the counter to every message you send. On receiving a message with timestamp T, set the counter to max(local, T) + 1.

@@ hlc
value: A hybrid logical clock (HLC) is a timestamp made of two parts: the largest physical time the node has seen, and a small counter that breaks ties. It is built to give two things that normally conflict. Like a Lamport clock, it respects cause and effect: if event A can influence event B, A's timestamp is smaller. Like a wall clock, it stays close to real time, never more than the clock-error bound away, so you can ask for "data as of five minutes ago", expire rows by age, and read the value in a log. And it fits in 64 bits, which is small enough to store on every row version.
This is the answer to a practical problem in distributed databases. You want each transaction to have a timestamp, and you want timestamps to be consistent with causality, so that a transaction that reads another's result is ordered after it. Hardware that gives bounded clock error, as Google's TrueTime does, solves this but is not available to most teams. A pure Lamport clock needs no hardware but has no link to real time. An HLC needs only ordinary clock synchronisation (NTP, or better a cloud time service) and still gives you both. CockroachDB, YugabyteDB and MongoDB (for its cluster time) use it, and many other systems use a variant.
It stands on two lower concepts. Hardware clocks and timers (L3) supply the physical part: a quartz oscillator that drifts by tens of parts per million, disciplined by a time protocol, so that it is usually within a few milliseconds of true time. The relativity of simultaneity (L5) supplies the reason that uncertainty cannot be removed: two separated machines have no shared "now", so any two clock readings carry an error that you must bound and plan for. The logical counter handles the part the physical clock cannot, which is deciding the order of events that fall inside that error.
terms: Physical time (pt) — the reading of the local wall clock, usually in milliseconds or nanoseconds.
Logical component (c) — a small counter that orders events that share the same physical value.
HLC timestamp — the pair (l, c), compared first on l and then on c; l is the largest physical time this node has seen directly or through messages.
Clock skew or offset — the difference between two nodes' clocks at the same instant.
Maximum offset (ε) — the largest skew the system assumes; the guarantees depend on it holding.
Uncertainty interval — the window after a transaction's timestamp in which another node's timestamps may or may not be in the past, because of possible skew.
Read restart — when a read meets a value inside its uncertainty interval, it moves its timestamp above that value and reads again.
Causality — the relation where one event can have influenced another, through a chain of messages.
history: Sandeep Kulkarni, Murat Demirbas, Deepak Madappa, Bharadwaj Avva and Markus Leone published "Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases" at OPODIS in 2014. The motivation was the cost of TrueTime. Spanner had shown in 2012 that bounded clock uncertainty gives strong consistency, but it needed GPS receivers and atomic clocks in every data centre. The authors asked what could be done with ordinary NTP. Their answer was a clock that uses physical time as far as possible and falls back on a Lamport-style counter exactly where physical time is not enough.
Adoption was fast because the idea is small. CockroachDB, started in 2014 by former Google engineers, built its transaction timestamps on an HLC from the beginning, with a wall-time part of nanoseconds and a logical part of 32 bits. YugabyteDB, based on the same ideas, followed. MongoDB 3.6 (2017) introduced "cluster time", a hybrid logical clock sent along with each command, to support causal consistency in sessions and change streams. Its value has a 32-bit seconds part and a 32-bit increment part.
Cloud providers later added better time sources, which made HLCs safer. Amazon offers a time service with microsecond-level accuracy for EC2 and a library called ClockBound that returns an error bound, and Amazon Aurora DSQL, released in 2025, uses synchronised clocks in its design. Better clocks do not remove the need for an HLC: they reduce the uncertainty window, and the HLC remains the cheap way to keep causality.
how: Each node keeps a pair (l, c). The invariant is that l is the largest physical time the node knows about, either from its own clock or from a timestamp it received, and c counts events that happened at that same value of l. A timestamp is compared as a pair: first l, then c.
For a local event or a message send, the node reads its physical clock pt. It saves the old l, then sets l = max(old l, pt). If l did not change (the physical clock has not moved past the old l, perhaps because it is within the same millisecond, or because it is behind), it increments c. If l moved forward, it resets c to 0. The new (l, c) is the event's timestamp, and the node attaches it to outgoing messages.
For a message receive, the node has the message's timestamp (m.l, m.c). It sets l = max(old l, m.l, pt). Then there are four cases. If l equals both old l and m.l, set c = max(old c, m.c) + 1. If l equals only old l, set c = old c + 1. If l equals only m.l, set c = m.c + 1. Otherwise l is the new physical time, so set c = 0. In every case the new timestamp is strictly larger than both the node's previous timestamp and the message's timestamp, which is the Lamport rule written for pairs.
Two properties follow. First, causality: if A happened before B, then (l, c) of A is smaller than that of B, for the same reason as in a Lamport clock. This is how the HLC builds on Lamport clocks (the neighbouring concept): the pair behaves like a Lamport counter whose high part is pulled up by real time. Second, closeness to real time: l is never more than the maximum clock offset ε ahead of the node's own physical clock, because l can only be pushed ahead by a message from a node whose physical clock was itself within ε. This holds only if clocks really are within ε. The counter c stays small, because it grows only when many events fall into the same l, and it resets whenever physical time moves on. In practice c is almost always 0, and the timestamp looks like a plain wall-clock time.
How does a database use this? Each transaction gets a timestamp from the HLC of the node that starts it, and every version of a row is stored with the timestamp of the transaction that wrote it. A read at timestamp t sees the newest version with timestamp ≤ t. This is multi-version concurrency control, and the HLC provides the version numbers. Because every request and reply carries an HLC value, clocks of nodes that talk to each other are pulled forward together, so causally related transactions always get increasing timestamps.
The hard part is that the HLC does not remove the clock error. Suppose node A's clock is up to ε behind node B's. A transaction that starts at A with timestamp t might not see a value written at B with timestamp slightly above t, although the write really finished before the transaction started. To prevent a stale read, CockroachDB gives each transaction an uncertainty interval from t to t + ε. If a read finds a value with a timestamp inside that interval, it cannot know whether the value was written before or after the read began in real time. The safe move is to treat it as before: the transaction pushes its timestamp above that value and retries the read, which is the read restart. Values above t + ε are certainly later and are ignored. The upper limit of the window is fixed when the transaction begins, so the window can only shrink, and a transaction restarts a bounded number of times.
Finally, the system must enforce ε. CockroachDB nodes measure each other's clock offsets during their regular RPC heartbeats. By default the maximum offset is 500 ms. A node that finds its clock out of line with at least half of the other nodes, by 80% of the maximum offset, shuts itself down, because continuing could serve inconsistent reads. The lower concepts again show their value: the hardware clock gives the base reading and its drift rate, which determines how large ε must be, and the lack of a global "now" is the reason ε exists at all.

example: Follow two nodes with pen and paper. Node B starts with (l, c) = (95, 0). Node A has physical time 100 and sends a message after a local step. A's local step: old l was, say, 99, so l = max(99, 100) = 100 and c = 0. The send is another event: pt is still 100, so l stays 100 and c becomes 1. The message carries (100, 1).
B receives it when B's own clock reads 98. The new l = max(95, 100, 98) = 100. This equals the message's l but not B's old l, so c = m.c + 1 = 2. B's timestamp is (100, 2), larger than A's (100, 1) and larger than B's earlier (95, 0). Now B does a local step while its clock reads 99. l = max(100, 99) = 100, which equals the old l, so c becomes 3. The timestamp is (100, 3). When B's clock reaches 101, l = max(100, 101) = 101 and c resets to 0. Notice that l − pt was 2 at its largest (100 versus 98), within the ε of the system. Causality was kept even though B's clock was behind A's.
Now the uncertainty interval, using milliseconds. A transaction starts on node A at HLC time 1000, and ε is 500, so its window is 1000 to 1500. It reads key k and finds three versions. A version stamped 800 was written clearly before, so the transaction reads it normally. A version stamped 1600 is beyond 1500, so even with the worst clock error it was written after the transaction began, and the read ignores it. A version stamped 1200 is in the window. The writer's node might have had a clock 300 ms ahead, in which case the write finished before the read began and must be seen. The read cannot tell, so it restarts: the transaction moves its timestamp to just above 1200 and reads again. Now version 1200 is visible. The cost is one retry and a few milliseconds. If ε were 5 ms instead of 500, a version would fall in the window much less often, so restarts become rare.
A cost check on the shutdown rule: with a maximum offset of 500 ms, a node whose clock is 400 ms or more from the others (80% of 500) is stopped. That looks strict, but it is cheaper to lose one node than to let it hand out timestamps that break the serial order.
intuition: Use the wall clock as the main hand of a watch, and a tiny second hand that only moves when two events fall in the same tick.
The design is natural because the two clocks fail in opposite ways. A wall clock is meaningful but sometimes wrong and can go backwards after a correction. A logical clock is never wrong about causality but has no meaning outside the system. If you keep the largest physical value ever seen and never let it go back, you inherit the logical clock's guarantee. If you keep that value close to the real clock, you inherit the wall clock's meaning. The pair costs almost nothing to maintain, because it only needs a max operation and a comparison.
mistakes: People often think an HLC gives the same guarantee as TrueTime. In fact it does not. TrueTime gives an interval that is guaranteed to contain true time, and Spanner waits out the interval so that its commits are externally consistent. An HLC gives causal order and a skew bound that you must enforce yourself, and the database handles the uncertainty with read restarts and without commit wait.
People often think using an HLC means the database is linearizable across all keys. In fact CockroachDB documents that it is serializable and gives single-key linearizability, but it can show a "causal reverse" anomaly: two transactions that touch different keys and have no overlap in data may get timestamps in the opposite order of real time. A system with TrueTime-style commit wait avoids that.
People often think the logical counter will grow without bound. In fact c resets to 0 each time l moves forward, and l moves forward whenever the physical clock passes it. c becomes large only when many events share a very small time window, or when a clock jump forward by another node makes l run ahead of the local clock for a while.
People often think HLC makes clock quality irrelevant. In fact correctness of reads depends on the real skew staying below ε. NTP failures, virtual machine pauses, leap-second handling and bad hypervisor clocks can break this, which is why databases monitor offsets and shut nodes down.
friction: The biggest limit is the dependence on a skew bound that the software cannot prove. If a clock drifts beyond ε and the node does not notice in time, a read can miss a recent write. CockroachDB's answer is to stop nodes that look out of line, which turns a correctness risk into an availability event. Teams that run on virtual machines with poor time sync see exactly this: nodes crashing with "clock offset" messages after a host migration or a pause.
A larger ε costs performance. With a maximum offset of 500 ms, more reads fall inside the uncertainty window and restart, and the more contended a key is, the more often this happens. Operators who tune ε down to a few milliseconds (with good time sources) get fewer restarts, but the risk of a node being shut down by a transient skew rises. This is a trade-off between latency and safety, set by the clock infrastructure rather than the database.
A clock that jumps forward, because of a bug or a hostile peer, can drag the whole cluster's l ahead. Since l never moves back, the damage lasts until real time catches up, and for a jump of an hour that is an hour. MongoDB limits this by refusing cluster times more than about a year ahead of wall time, which still allows a long window; other systems check the offset against the local clock and reject larger values.
Finally, an HLC does not give a global snapshot for free across systems. Two different databases, each with its own HLC, cannot compare timestamps unless they exchange them. Cross-system consistency needs a shared time service or an explicit token passed between them.
practice: Run time synchronisation as a first-class service. Use chrony or the cloud provider's time source (Amazon Time Sync, Google's NTP service, Azure's host-based time) and monitor offset on every database node. Alert long before the shutdown threshold, for example at a quarter of the maximum offset. Treat virtual machine live migration and pauses as possible causes of jumps.
Set the maximum offset to match your clock quality, not the default. With a good cloud time source you can often use a value far below 500 ms, which reduces read restarts. Lower it step by step and watch the restart counters and node crash logs. Do not lower it on machines where you cannot measure the real skew.
If you design your own system, store timestamps as a single 64-bit integer by packing the physical part (for example 48 bits of milliseconds) and the counter (16 bits), so ordinary integer comparison gives the right order. Make "update on receive" a single function, test it with random clock jumps in both directions, and put a sanity limit on how far a received timestamp may be ahead of local time.
When you debug anomalies, read the timestamp pair, not just the wall part. Two writes with the same l and different c were ordered by the logical counter and may have happened within one tick. For cross-service causality (for example, a read-after-write on a replica), pass the HLC value in the request as a token, which is what MongoDB's afterClusterTime does for causally consistent sessions.
tradeoffs: Choose an HLC when you run on commodity machines with NTP-grade clocks (offsets of 1 to 10 ms with good sources), you need MVCC timestamps close to real time, and you accept read restarts. Choose TrueTime-style bounded clocks, which give the hardware and the error bound, when you need external consistency across the world and can afford GPS or atomic references; you pay with infrastructure and a commit wait of about twice the uncertainty, a few milliseconds.
Choose a pure Lamport clock when real-time meaning is not needed, such as ordering messages in a protocol. Choose a central timestamp oracle (as in TiDB or Percolator) when one service can hand out 100,000 or more timestamps per second and the extra round trip, often 1 ms in a data centre, is acceptable; you get a perfect order and one component to keep available. Avoid it across regions where the round trip is 50 to 150 ms.
Choose a small maximum offset (tens of milliseconds) when clock quality is monitored and good: fewer restarts, lower latency. Choose a large one (hundreds of milliseconds) when your environment is uncertain, accepting more restarts and slower contended transactions in exchange for fewer node shutdowns.
Choose HLC-based causal tokens for read-your-writes on replicas when you want to avoid sending every read to the leader. You give up a little freshness (a replica may need to wait to catch up to the token) in exchange for taking load off the leader.
interview: Walk through how an HLC handles a message from a node whose clock is ahead of yours. || Take l = max(old l, m.l, pt). Since m.l is larger, l becomes m.l and c = m.c + 1. My timestamp is now larger than the message's, so causality holds, and my l is ahead of my own clock by the sender's lead, which must be within ε. When my clock catches up, l follows pt and c returns to 0.
Why is a restart needed when a read sees a value inside the uncertainty interval? || The writer's clock might be ahead by up to ε, so the write might have finished before the read began in real time even though its timestamp is higher. Ignoring it could return a stale value and break the guarantee that a read sees everything committed before it started. Restarting above that timestamp makes the transaction see it.
What happens if one node's clock jumps forward by an hour? || Its HLC l jumps forward and spreads to peers through messages, because every receiver takes the max. Receivers should reject timestamps beyond a sanity limit or detect the offset and shut down the offender. Otherwise the cluster's timestamps run an hour ahead of wall time until real time catches up, which breaks time-based features.
Compare HLC with TrueTime for external consistency. || TrueTime returns an interval guaranteed to contain true time, and Spanner waits out the interval before making a commit visible, so later transactions always get later timestamps. An HLC has a bound that is assumed, not guaranteed, and no commit wait, so non-overlapping transactions on different keys can be ordered against real time. HLC is cheaper to run but weaker.
How would you pack an HLC into 64 bits and what limits does it have? || For example 48 bits of milliseconds (about 8,900 years) and 16 bits of counter (65,536 events per millisecond per node). If the counter overflows within one millisecond, the node must wait for the next tick or advance l by one. CockroachDB uses a wider format: 64 bits of nanoseconds and a 32-bit counter.
quiz: What two parts make up an HLC timestamp and how are they compared? || A physical part l (the largest physical time seen) and a logical counter c. They are compared as a pair, l first and c second.
Why does c usually stay at 0? || It increments only when an event happens at the same l as the previous one. As soon as the physical clock moves past l, l advances and c resets to 0, so in normal operation the timestamp looks like a plain wall-clock time.
Why does a database need an uncertainty interval when it already has HLC timestamps? || HLC keeps causal order but clocks may differ by up to ε, so a value with a higher timestamp could have been written earlier in real time. The interval marks values that cannot be classified as past or future, and the read restarts above them.

Loosening the offset stops the crashes but increases read restarts and the risk of weaker guarantees if real skew is larger. Tightening makes crashes worse. The setting should match measured skew, not be used to hide a clock problem.

value: TrueTime is a clock API that admits it is not exact. Instead of returning one number for "now", it returns an interval [earliest, latest] that is guaranteed to contain the true time. Google built it for Spanner, its globally distributed SQL database. The interval is usually narrow, about 1 to 7 milliseconds wide in Google's data centres, and the system's correctness rests on one rule: if you need to be sure that a moment has passed, wait until the whole interval is beyond it.
This turns a hard problem into an engineering budget. Distributed databases want external consistency: if transaction T1 finishes before T2 starts, as seen by any outside observer, then T1's commit timestamp must be smaller than T2's, across continents. With sloppy clocks you cannot promise that. With TrueTime, Spanner assigns a commit timestamp, then deliberately waits (the "commit wait") until that timestamp is definitely in the past before telling anyone the transaction is committed. The wait costs a few milliseconds, and in return every later transaction anywhere gets a larger timestamp. The same clock also gives lock-free consistent reads at a timestamp, which is why large read-only queries in Spanner do not block writers.
It stands on two lower concepts. Hardware clocks and timers (L3) give the raw material: quartz oscillators in each server that drift by up to a known rate, disciplined by GPS receivers and atomic clocks in each data centre. The relativity of simultaneity (L5) gives the reason the interval cannot be made zero: there is no single "now" shared by separated machines, and every time signal arrives late by an amount that can only be bounded. TrueTime does not fight this. It measures the uncertainty, publishes it, and lets the database pay for it explicitly, in milliseconds of waiting.
terms: Time master — a server in a data centre with a GPS receiver or atomic clock that serves reference time to others.
Armageddon master — a time master that uses an atomic clock instead of GPS, so that time service survives a GPS failure or attack.
Uncertainty (ε, epsilon) — half the width of the TrueTime interval; the largest possible error of the local estimate.
TT.now() — returns an interval [earliest, latest] guaranteed to contain absolute time at the moment of the call.
TT.after(t) and TT.before(t) — true when t has definitely passed, or definitely not yet arrived.
Commit wait — the pause between choosing a commit timestamp and making the commit visible, until TT.after(timestamp) is true.
External consistency — if transaction T1 commits before T2 starts in real time, then T1's timestamp is smaller than T2's; it is linearizability for whole transactions.
Marzullo's algorithm — a method to combine several uncertain time readings into the smallest interval that agrees with the majority, rejecting liars.
history: Spanner was developed at Google in the late 2000s and described in the OSDI 2012 paper "Spanner: Google's Globally-Distributed Database" by James Corbett, Jeffrey Dean and many co-authors. It replaced a manually sharded MySQL setup behind Google's advertising system, called F1. The engineers wanted the convenience of a single SQL database with transactions and also the scale, replication and geographic spread of Bigtable. The hardest part was ordering transactions across data centres that are thousands of kilometres apart.
Earlier systems had avoided real time because clocks were unreliable. Lamport's 1978 paper made logical clocks the standard answer, and Google's Percolator (2010) used a central timestamp oracle. Spanner took a different path: make physical time trustworthy by measuring its error. The key move is the interval, an old idea from time-synchronisation research (Marzullo's 1984 work on intervals) joined with a hardware investment. Each data centre got GPS receivers and atomic clocks, a small cost compared with the value of a consistent global database.
After 2012 the idea spread in two ways. Spanner became a cloud product (Cloud Spanner, generally available in 2017), so outside users got TrueTime-backed consistency without the hardware. Also in 2017, Eric Brewer's paper "Spanner, TrueTime and the CAP Theorem" explained that Spanner is formally a CP system, and that its real availability is very high because Google's private network makes partitions rare. Other builders chose cheaper paths: hybrid logical clocks (CockroachDB, 2014 onwards) and, more recently, cloud time services. Amazon offers microsecond-accurate time on EC2 and a library, ClockBound, that returns an error bound, and Amazon Aurora DSQL (2025) uses them in the way TrueTime was used.
how: Start with how the interval is made. Each data centre has a set of time masters. Most have GPS receivers with their own antennas. The others, the Armageddon masters, have atomic clocks. Every server runs a time daemon. The daemon polls several masters, including some from other data centres, about every 30 seconds. Because any one source might be wrong (a GPS antenna can fail or be spoofed), the daemon applies a variant of Marzullo's algorithm: it takes all the intervals reported by masters and keeps the smallest interval that is consistent with most of them. Liars are dropped.
Between polls, the daemon cannot see the reference, and its own quartz clock drifts. Google assumes a worst-case drift of 200 microseconds per second (200 parts per million). So the uncertainty grows linearly from near zero right after a poll to about 6 ms just before the next one (30 s × 200 µs/s = 6 ms), and drops again at the next poll. Add about 1 ms for network delay to the master. That gives the sawtooth shape in the paper: ε is typically about 4 ms on average and ranges between roughly 1 and 7 ms. TT.now() returns [local clock − ε, local clock + ε] at that moment.
Why is any of this needed? Because of the lower concepts. The local oscillator gives a reading but drifts, so the hardware clock is the source of the drift term in ε. The reference signal comes from GPS, whose satellite clocks work only because engineers correct for relativity (about 38 microseconds per day of net difference between the satellite and the ground). The relativity of simultaneity says that two places have no common now; the best you can do is to bound how late a signal is. TrueTime packages that bound into the API.
Now the transaction protocol. Spanner runs data in groups of replicas, each group using Paxos with a leader. A transaction that touches only one group commits through that group's Paxos log. A transaction that touches several groups uses two-phase commit across the groups, where one group's leader is the coordinator and each group is a participant. Every Paxos group's leader also holds a lease (10 seconds by default) so that only one leader acts at a time.
The commit timestamp follows two rules. Start: the coordinator chooses a commit timestamp s that is no smaller than TT.now().latest, read after the commit request arrives, and at least as large as every timestamp the group has already assigned. Commit wait: the coordinator does not apply the commit or reply to the client until TT.after(s) is true, meaning that s is definitely in the past. Since the true time at the choice was at least TT.now().earliest, and s ≥ latest, the wait is about 2ε. With ε near 4 ms, that is about 8 ms, and the paper notes that it overlaps with the time Paxos needs to replicate the log entry, so much of it is hidden.
Why does this give external consistency? Suppose T1 commits at timestamp s1. Its commit becomes visible only after real time has passed s1. T2 starts after that, so T2 starts at real time greater than s1. T2's start rule picks a timestamp no smaller than TT.now().latest, which is at least the true time, and so greater than s1. Hence s2 > s1. The argument needs only one fact: the interval always contains true time. It does not need clocks to agree, only to be honest about their error.
Read-only transactions use the same clock without locks. The system picks a read timestamp (TT.now().latest for a read that needs to see everything committed before it started), and any replica that is up to date to that timestamp, tracked by a value called safe time, can answer. These reads take no locks and do not wait for writers, and the paper reports about 1.3 to 1.4 ms for a single read in a lab setting. Writes with commit wait cost around 14 ms for small replicated writes in the same setting.

example: Take ε = 4 ms. Transaction T1 asks for TT.now() and gets [1000.000, 1000.008] seconds (the true time is somewhere inside, say 1000.004). The coordinator picks the commit timestamp s1 = latest = 1000.008. It must now wait until TT.after(s1) is true, which means the new earliest has passed 1000.008. If the true time is 1000.004, earliest is 1000.000, so it waits until the true time is about 1000.012: roughly 8 ms, which equals 2ε. In the meantime, Paxos replication to a majority of replicas takes perhaps 10 ms across zones, so the commit wait finishes at about the same time as replication and adds little extra.
At true time 1000.012 the commit becomes visible and the client is told. The client of T2, which saw T1's reply, starts a transaction at true time 1000.013. T2 calls TT.now() and gets [1000.009, 1000.017], so s2 ≥ 1000.017 > 1000.008 = s1. The order of timestamps equals the real order.
Now see what the wait prevents. Suppose Spanner skipped it and told the client at true time 1000.004. T2 starts at 1000.005 on another server that polled a master a moment ago, so its interval is narrow, [1000.004, 1000.006], and it picks s2 = 1000.006. That is smaller than s1 = 1000.008, although T2 started after T1 was reported committed. An observer would see the order reversed. With the wait, T2 cannot start before true time 1000.012, and any honest interval at that moment has latest ≥ 1000.012, which is above s1.
Now the cost. If ε averages 4 ms, the wait is about 8 ms per read-write transaction, but it overlaps with replication and only writers pay it. The commit holds its locks until it finishes, so a row updated one transaction after another can take about 1000 divided by the commit latency in milliseconds: at 14 ms per commit that is roughly 70 updates per second on that one row. Any millisecond of wait that replication does not hide lowers that ceiling directly. In the paper, Google's F1 workload saw mean commit latencies of about 72 ms for single-site and 103 ms for multi-site writes, dominated by cross-data-centre replication and not by commit wait.
Finally the failure case. If a server loses contact with all masters for one hour, its drift is assumed to be 200 µs/s × 3,600 s = 0.72 s, so ε grows to about 720 ms and commit waits become very long. The system stays correct and becomes slow, which is the intended trade: honesty about error never breaks consistency, it only costs time.
intuition: If you know your watch could be 4 ms wrong either way, announce a result only after 8 ms, and nobody can tell it was announced early.
The design is natural because it makes uncertainty a number instead of a hidden risk. Every other approach pretends that "now" is a point and then repairs the damage with retries, anomalies or manual rules. TrueTime accepts that "now" is an interval and only makes claims that hold for every point inside it. Waiting out the interval is a way to convert uncertainty into latency. Latency can be measured, budgeted and reduced with better hardware, whereas wrong order of transactions cannot be fixed afterwards.
mistakes: People often think TrueTime is a perfectly synchronised clock. In fact it is the opposite: it never claims to know the time exactly, it publishes the error. The guarantee is that true time lies inside the interval, not that two servers see the same value.
People often think Spanner beats the CAP theorem because of TrueTime. In fact Spanner is a CP system: during a real partition, the side without a majority cannot commit. Brewer's 2017 paper explains that Spanner is effectively highly available because Google's network makes partitions rare and because replicas are spread over many failure domains. TrueTime solves ordering, not partitions.
People often think commit wait delays every transaction. In fact only read-write transactions wait, and the wait overlaps with replication. Read-only transactions at a chosen timestamp take no locks and do not wait for writers. Single-key snapshot reads from a nearby replica are fast.
People often think atomic clocks are the main ingredient. In fact most time masters use GPS, and atomic clocks serve as a second, independent source for the case when GPS fails. What matters most is the error bound and the discipline of using it. A system without hardware but with a sound error bound, such as a cloud time service that reports its own uncertainty, can use the same idea with a larger ε.
friction: The first limit is infrastructure. GPS antennas, atomic clocks, dedicated time masters in every data centre and a daemon on every server are a real cost. Most companies cannot build this, so they rely on a cloud provider's time service or choose a weaker design such as hybrid logical clocks. Cloud time services have improved: microsecond-level synchronisation over hardware-assisted protocols is now available on major clouds, though you still need the error bound reported with each reading.
The second limit is latency tied to ε. Every millisecond of uncertainty adds a millisecond to each read-write commit's lock hold time, and hot rows pay most. If ε grows because of a failing master, a congested network or a daemon problem, commit latencies grow in proportion, and the effect shows first on contended data. Operators therefore monitor ε as a first-class health signal.
The third limit is that the guarantee is only as good as the bound. If the true drift exceeds the assumed 200 µs/s (a faulty oscillator, for example), the interval might not contain true time, and the proof fails. Google handles this by watching machines and evicting those whose clocks diverge from the masters. A fourth limit is that the argument covers a single system. Two different databases, each with its own clock bound, are not externally consistent with each other unless they share a timeline. Finally, wide-area replication still dominates latency: even with a perfect clock, a transaction across continents needs round trips measured in tens or hundreds of milliseconds, and TrueTime does nothing about the speed of light.
practice: If you run on a cloud that offers a time service with an error bound, such as Amazon's ClockBound or a comparable offering, use the bound, not just the reading. Ask for the interval, and make decisions that hold for the whole interval: for example, treat a lease as expired only when the latest possible time has passed its end, and treat it as valid only while the earliest possible time is before its end.
Apply the "wait out the uncertainty" pattern in your own designs where it is cheap. A leader that hands over a lease can wait for the uncertainty window before the new leader acts. A system that stamps events with wall-clock time can record the error bound next to the timestamp, so that analysis later can tell which orderings are certain and which are not. Cassandra's last-write-wins is the opposite approach, trusting raw timestamps, and it silently loses writes when clocks differ by more than the gap between writes.
Monitor clock health: offset from the reference, the reported error bound, and the time since the last successful sync. Alert on a growing bound, not only on a large offset. Test your system with injected clock skew and pauses. When you choose a database, ask the vendor what its clock assumption is, what happens when it is violated (crash, wrong answer, slowdown), and what its commit protocol waits for.
When using Cloud Spanner, place leaders near the writers, group data that is updated together under the same parent key to avoid distributed transactions, and use stale reads (a bounded staleness of, say, 10 seconds) for dashboards and lookups that do not need the latest value. These reads use the clock to pick a timestamp and avoid any cross-region round trip.
tradeoffs: Choose TrueTime-style bounded clocks when you need external consistency across regions, you can control the time infrastructure or buy it from a cloud, and you accept 5 to 10 ms of commit wait for read-write transactions. You give up money and operational complexity, and you gain a clean guarantee that needs no application-level workarounds.
Choose hybrid logical clocks when you run on ordinary machines with NTP, you can accept serializable isolation with possible causal-reverse anomalies between unrelated keys, and you are willing to restart reads that fall into the uncertainty window. You give up the strongest guarantee, and you gain freedom from special hardware.
Choose a central timestamp oracle when your deployment is mostly in one region and a round trip of around 1 ms to a replicated service is acceptable. It is simple and gives a perfect order. It does not scale across oceans, because each transaction pays a trans-oceanic round trip of 100 ms or more.
Choose a smaller uncertainty (better references, more frequent polls, hardware-assisted sync) when you have hot rows and strict latency goals, accepting the cost of equipment and monitoring. Choose bounded-staleness reads when the product can show data that is 5 to 15 seconds old; you give up freshness and gain local reads with no coordination.

@@ crdt
value: A CRDT (conflict-free replicated data type) is a data structure designed so that copies on different machines can be changed independently, with no locks and no coordination, and still end up identical once they have exchanged their updates. The design trick is in the merge. The merge operation is built so that the order of merges, the grouping of merges and repeated merges do not change the result. If every replica eventually receives every update, they all reach the same state. No application code has to decide who wins a conflict.
The problem it solves is the cost of agreement. A normal replicated database makes writes go through a leader or a quorum, so a user on a plane, a phone with no signal, or a data centre on the other side of the ocean either waits or cannot write. With CRDTs every replica accepts writes immediately, using only local state, and sends changes in the background. This is called strong eventual consistency: replicas that have seen the same set of updates are in the same state, with no rollback. It is the basis of collaborative editors (Yjs, Automerge), local-first apps, active-active databases (Redis Enterprise Active-Active, Riak data types), and offline-capable mobile sync.
The design stands on two lower concepts. Distributed systems theory (L3) gives the model and the limits: messages are delayed, reordered, duplicated or lost, there is no global clock, and the CAP result says you cannot have both unconditional availability and strong consistency in a partition. CRDTs choose availability and settle for convergence. Order theory (L4) gives the structure that makes convergence automatic: a join-semilattice, a set with a partial order in which any two elements have a least upper bound (their join). If every update moves the state up in the order, and merge is the join, then all replicas move toward the same top.
terms: Replica — one copy of the data on one node or device that accepts reads and writes locally.
Strong eventual consistency (SEC) — replicas that have received the same updates, in any order, hold equal state; no conflict resolution step is needed.
State-based CRDT (CvRDT) — replicas send their whole state (or a delta) and merge with a join function.
Operation-based CRDT (CmRDT) — replicas send operations, which must commute when delivered in causal order, exactly once.
Join-semilattice — a set with a partial order where every pair has a least upper bound; the join is commutative, associative and idempotent.
Idempotent — applying an operation twice gives the same result as applying it once.
Tombstone — a marker that records a deletion so that a later merge does not bring the item back.
Causal stability — the point where every replica is known to have seen an update, so metadata about it can be discarded.
history: The roots are in two lines of work. The first is operational transformation (OT), invented by Ellis and Gibbs in 1989 for collaborative editing: transform each incoming operation against concurrent ones so that all users converge. OT turned out to be very hard to get right without a central server, and many published algorithms were later found to be wrong. The second line is the study of eventually consistent databases in the 2000s, driven by systems such as Amazon's Dynamo (2007), where concurrent writes produced siblings that the application had to merge by hand.
In 2006 to 2009 several researchers proposed text structures with unique, ordered identifiers for each character, so that inserts commute: WOOT (Oster et al., 2006), Treedoc (Preguiça et al., 2009) and Logoot (Weiss et al., 2009). In 2011 Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski unified these ideas in "Conflict-free Replicated Data Types" (SSS 2011) and a long INRIA report. They defined state-based and operation-based CRDTs, proved that both reach strong eventual consistency under simple conditions, and gave a catalogue: counters, sets, registers, and graphs.
Practice followed. Riak 2.0 (2014) shipped CRDT data types (counters, sets, maps, flags, registers) inside a production store. Delta-state CRDTs (Almeida, Shoker and Baquero, 2015 and later) sent small deltas instead of full state, which made state-based types practical. Yjs (Kevin Jahns, 2015 onward) and Automerge (Martin Kleppmann and others) made CRDT-based text editing fast enough for real documents. The 2019 essay "Local-first software" by Kleppmann and colleagues at Ink & Switch argued for CRDTs as the way to build apps that work offline and keep data on the user's device. Work such as Fugue (Weidner and Kleppmann, 2023) improved how concurrent text inserts are interleaved.
how: Think of the state of a replica as a point in a lattice. Take the simplest example: a grow-only set. The state is a set, the order is "is a subset of", and the join is union. Union is commutative (A ∪ B = B ∪ A), associative ((A ∪ B) ∪ C = A ∪ (B ∪ C)) and idempotent (A ∪ A = A). An update adds an element, so the state only moves up. Because of these three properties, a replica can merge any set of states received in any order, with duplicates, and the answer is always the union of everything. That is the entire proof of convergence, and it uses the order-theory facts about joins directly.
A state-based CRDT is defined by a state type, update operations that are inflationary (they never move the state down), and a merge that is the join. Replicas gossip their states or deltas, and each merges what it receives. A counter shows how to build richer types. A single integer cannot be merged: if two replicas both hold 5, do they hold the same five increments or different ones? The grow-only counter solves this by giving each replica its own slot in a vector. Replica i only increments slot i. The value is the sum of the slots, and merge takes the maximum of each slot. Each slot is a monotone counter owned by one writer, so maximum is the correct join. A counter that supports decrements, the PN-counter, keeps two such vectors, one for increments and one for decrements.
An operation-based CRDT sends operations instead of state. This needs a delivery layer that gives causal order (if one operation depends on another, the second arrives after the first) and exactly-once delivery, or operations that are themselves idempotent. The advantage is small messages. The disadvantage is that the network layer must be reliable and track causality, usually with version vectors, which is where the Lamport and vector clocks of the lower layers show up.
Why is convergence guaranteed, in plain steps? Each replica's state is the join of the initial state and every update it has applied. Because the join is commutative and associative, that value depends only on the set of updates, not on their order or grouping. Because it is idempotent, receiving an update twice is the same as once. So two replicas that have seen the same set of updates hold the same value, whatever the network did. The only liveness requirement is that every update eventually reaches every replica, which a simple gossip or sync protocol provides. Notice what is not needed: no leader, no clocks, no quorum and no ordering of messages. That is what order theory buys here, and it is why the proof fits in a few lines.
Removal is the hard part, because "delete" is not monotone. The observed-remove set (OR-set) solves it. Every add creates a unique tag, and the set stores (element, tag) pairs. A remove deletes only the pairs that the remover has seen. If another replica adds the same element concurrently, that add has a new tag nobody has seen, so it survives. The result is "add wins" over a concurrent remove, which is deterministic, so every replica makes the same choice. Registers use the same trick: a last-writer-wins register keeps the value with the highest (timestamp, replica id), and a multi-value register keeps all concurrent values and lets the application choose.
Sequences, used for text and lists, give each element a unique, totally ordered identifier that stays valid as neighbours change. In Logoot and similar designs the identifier is a path of numbers between neighbours. In RGA, Yjs and Automerge, each inserted character records the identifier of the character to its left and the system orders siblings deterministically using (logical timestamp, replica id). Two users who both type after the same character produce two inserts with the same parent. All replicas order those two the same way. Deleted characters stay as tombstones, so that identifiers remain valid for operations still in flight, and they can be removed once every replica has seen the delete (causal stability).
The limits come from the same mathematics. A CRDT can express only what is monotone, or what can be made monotone with tags. Invariants that need a global view, such as "balance never goes below zero" or "usernames are unique", cannot be kept by local operations alone, because two replicas can each approve a valid-looking operation that is invalid together. These need some coordination, for example reserving part of a budget per replica (bounded counters, also called escrow) or a consensus step for the rare operations that need it.

example: Three phones count "likes" with a grow-only counter. Phone A is offline and records 3 likes: A's vector is [3, 0, 0]. Phone B records 2 likes: [0, 2, 0]. Phone C records 4: [0, 0, 4]. When A and B meet, each takes the maximum per slot and both hold [3, 2, 0], which shows 5. Later B meets C and gets [3, 2, 4], which shows 9. Phone C meets A: also [3, 2, 4]. If B's message to C is delivered twice, taking the maximum again changes nothing. If A's old state [3, 0, 0] arrives late, the maximum ignores it. The total is 9 everywhere, with no server involved. Compare a naive design where each phone sends the number "5": a replica receiving 5 twice cannot tell whether that is one batch of five likes or two.
Now an observed-remove set for a shopping list. Phone A adds "milk", creating the pair (milk, a1). It syncs to phone B, which now holds {(milk, a1)}. B removes "milk": it deletes the pair (milk, a1) from its state and records that a1 was removed. At the same time, phone C, which has not seen B's remove, adds "milk" again, creating (milk, c1). When all three sync, the removed set contains a1 only, so (milk, a1) is gone, and (milk, c1) remains. Milk is on the list. If the order of merges differs, the result is the same. The rule is deterministic and simple to explain to a user: "an add that you did not know about wins over your remove".
A cost estimate for text. A document of 100,000 characters in a sequence CRDT stores, for each character, an identifier (a replica id and a counter, roughly 8 to 16 bytes in a compact encoding), a link to its left neighbour and a deleted flag. Naively that is 20 to 40 bytes per character, or 2 to 4 MB for 100 KB of text. Modern implementations compress runs of consecutive characters typed by one user into one record, so the real size is often within a small multiple of the text itself. That is why careful encoding matters more than the choice of algorithm.
intuition: Design the data so that merging is like pouring more water into a bucket: the order you pour in does not matter, and pouring the same cup twice does not change what was already there.
The idea is natural once you notice that conflicts come from operations that do not commute, such as "set to 5" and "set to 7". If you restrict yourself to operations that do commute, or make them commute by adding unique tags and per-replica slots, conflicts cannot appear. The mathematics of semilattices is the exact statement of that restriction: monotone growth plus a join. You pay with expressiveness. You cannot express "the latest wins" without saying what "latest" means (a timestamp), and you cannot express "never negative" at all without coordination.
mistakes: People often think CRDTs remove all conflicts. In fact they remove merge failures, not semantic conflicts. Two users who edit the same sentence get a deterministic result, but it may not be what either meant. The merge is always defined; whether the outcome fits the user's intention is a product question.
People often think CRDTs and operational transformation are the same thing, or that CRDTs are always better. In fact OT transforms operations against concurrent ones and usually needs a central server to order them, as Google Docs does. CRDTs make the data structure itself commutative and work peer to peer. CRDTs cost more metadata; OT costs more algorithmic complexity and a server. Figma has described its multiplayer system as inspired by CRDTs but built on a central server that decides order, not a pure CRDT.
People often think state-based CRDTs always send the whole state. In fact delta-state CRDTs send only the part that changed since the last exchange, with the same convergence proof, so message size is proportional to the change.
People often think CRDTs give strong consistency. In fact they give strong eventual consistency: replicas agree after they have seen the same updates, but at any moment two replicas may show different values. They cannot enforce invariants across replicas, such as unique names or non-negative balances, without added coordination.
friction: Metadata is the main cost. An OR-set keeps a tag per add. A sequence keeps an identifier per character and tombstones for deleted ones. A multi-value register can grow with the number of concurrent writers. Garbage collection needs causal stability, which means knowing that every replica has seen an operation, and that is impossible to know if a replica has gone away for a year. Systems cap it by expiring replicas, forcing old clients to resync, or accepting growth.
Semantics are the second cost. Add-wins and last-writer-wins are policies, and a different policy may suit your application. Concurrent text inserts at the same position can interleave letter by letter in some algorithms, producing garbled words, and designing orderings that avoid this is still active research. Moving an item in a list or tree (drag a block to a new parent) is hard: two users moving the same node to different places can create cycles or duplicates unless the algorithm is designed carefully, as in Kleppmann's work on move operations in replicated trees.
Third, invariants. Anything needing a global check, such as unique constraints, inventory limits, money, or access control revocation that must take effect immediately, needs a coordination step on top. Teams often discover this late. Fourth, debugging and history: because merges are automatic, a surprising result may be hard to trace without a stored history of operations. Finally, security: a malicious replica can send operations that are valid in form but harmful, such as huge identifiers or forged ids, and a CRDT has no authority to reject them without extra design.
practice: Use CRDTs when users must write while offline or with high latency, when replicas are many and unreliable, or when you want peer-to-peer collaboration. Start from a library: Yjs or Automerge for documents and rich text, the data types in Redis Enterprise Active-Active for counters and sets, and the CRDT types in Riak or similar stores for server-side state. Avoid writing your own sequence CRDT; the edge cases around interleaving and tombstones are subtle.
Model your data to fit what CRDTs do well. Prefer counters and sets to read-modify-write fields. Store each logical field as a register or map entry rather than one big blob, so that edits to different fields merge cleanly. Use add-wins sets for membership and tag-based deletes for removal. Where you need a bound, such as inventory, split it into per-replica shares and move shares between replicas with coordination only when a replica runs out.
Plan the lifecycle: how large the state is after a month of heavy editing, how you compact history, how old replicas rejoin, and how you migrate the schema. Measure the memory and bandwidth of the real workload, and ask whether replicas can be bounded in number (servers only) to keep version vectors small. Keep a server that stores snapshots and history even in peer-to-peer designs, for backup and for new devices.
For an engineer in data platforms: the closest everyday relatives are idempotent upserts and "max" aggregations in streaming jobs, which are tiny CRDTs. A watermark column that only increases, merged with max, has the same convergence property. Recognising this helps you design pipelines that can be replayed safely in any order.
tradeoffs: Choose CRDTs when availability and low write latency matter more than immediate agreement, replicas may be offline for hours, and your data fits monotone or tag-based types. You give up the ability to enforce global invariants without extra coordination, and you pay in metadata, often two to ten times the raw data size for sequences with history.
Choose consensus (Raft or Paxos in a database) when you need linearizable writes and invariants such as uniqueness or non-negative balance, and a round trip to a majority (1 ms in a data centre, 50 to 150 ms across regions) is acceptable. You give up writes during partitions on the minority side.
Choose operational transformation with a central server when you already run a server for every edit, want compact metadata and have a team that can maintain the transformation functions. Choose a CRDT when peer-to-peer or offline use is required, or when you want to avoid the proofs OT needs.
Choose state-based or delta-state CRDTs when the network is unreliable and messages may be lost or duplicated, because merging is idempotent. Choose operation-based CRDTs when bandwidth matters most and you can guarantee causal, exactly-once delivery, for example through a reliable log. Choose last-writer-wins registers only when losing a concurrent write is acceptable; choose multi-value registers when it is not, and accept that the application must resolve siblings.
interview: What three properties must a merge function have, and why does each matter? || Commutative: the order in which two states arrive does not matter. Associative: the grouping of merges does not matter, so replicas can merge in different trees. Idempotent: duplicate messages are harmless. Together they make the merge a lattice join, and any set of updates delivered in any pattern yields the same state.
How does an OR-set handle a concurrent add and remove of the same element, and what does it cost? || Each add has a unique tag and a remove deletes only the tags it has seen. A concurrent add carries a tag the remover never saw, so it survives, giving add-wins. The cost is a tag per element occurrence and a record of removed tags until causal stability allows garbage collection.
Why can't a CRDT enforce "account balance never below zero"? || Two replicas can each accept a withdrawal that is valid alone and invalid together, and local merge cannot reject either afterwards. You need coordination: a consensus step, or an escrow scheme where each replica holds a share of the balance it may spend locally.
Compare CRDTs with operational transformation. || OT transforms each operation against concurrent ones and usually relies on a server to order operations; metadata is small but the algorithms are subtle and easy to get wrong. CRDTs build commutativity into the data type, work without a server, and are easier to prove, but carry more metadata such as ids and tombstones.
How would you garbage-collect tombstones in a text CRDT? || Wait for causal stability: when every replica is known to have seen the delete, no operation can still refer to the tombstone, so it can be removed. This needs knowledge of the replica set, so systems limit replica lifetime or force late replicas to resync from a snapshot.
Your active-active database uses last-writer-wins for a counter and you lose increments. What is wrong and what is the fix? || LWW keeps one value and discards the other concurrent update, so two increments become one. A counter CRDT keeps per-replica slots and merges by maximum per slot, summing them for the value, so both increments are kept.
quiz: What is the merge rule for a grow-only counter with one slot per replica? || Take the maximum of each slot, and read the value as the sum of all slots. Each slot has a single writer and only grows, so the maximum is the correct join.
Why is idempotence needed in a CRDT merge? || Messages can be duplicated or replayed after a retry. If merging the same state twice changed the result, replicas would diverge. Idempotence makes duplicates harmless.
In an OR-set, replica B removes milk (tag a1) while replica C concurrently adds milk (tag c1). After a full merge, is milk present? || Yes. B's remove deleted only tag a1, and c1 was unseen by B, so (milk, c1) survives. This is the add-wins behaviour.
A G-counter has slots [4, 1, 6] on replica A and [4, 3, 2] on replica B. What do both hold after merging, and what is the value? || Maximum per slot gives [4, 3, 6], so the value is 13.
When would you choose a consensus-based store over a CRDT-based one? || When you need invariants that depend on a global view, such as unique usernames or non-negative balances, and you can accept coordination latency. CRDTs would let two replicas each accept a valid-looking update that breaks the invariant when combined.

@@ gossip
value: A gossip protocol (also called an epidemic protocol) spreads information through a cluster the way a rumour spreads through a crowd. Every node, at regular intervals, picks a few other nodes at random and exchanges what it knows. A new fact told to one node reaches every node in a number of rounds that grows only with the logarithm of the cluster size: about 17 rounds for 1,000 nodes, and about 34 for a million. No node is in charge, no node needs a full list of peers, and the failure of any node, or of many nodes, does not stop the spread.
The problem it solves is dissemination at scale without a bottleneck. If one coordinator tells everyone, it needs N messages and is a single point of failure. If every node tells every other node, there are N² messages. Gossip keeps the work per node constant (a few messages per round, whatever N is) and the total work at about N log N messages for one update. It is used for cluster membership (who is in the cluster), failure detection (who has died), propagating small pieces of state (token ownership, schema versions, load) and anti-entropy (repairing replicas that have drifted apart). Cassandra, Dynamo, Riak, Consul and Serf, Redis Cluster, Akka Cluster and the peer-to-peer layers of Bitcoin and Ethereum all use it in some form.
It stands on two lower concepts. Probability (L4) explains why random choices spread information so quickly: informed nodes multiply each round, the growth follows a logistic curve, and the last few uninformed nodes die out at a known exponential rate. Random and small-world graphs (L4) explain why random contacts are enough: the graph formed by random peer choices is an expander, with a short diameter of order log N and no weak cuts, so there is almost always a path from any node to any other. Gossip gives you this well-connected overlay without designing one.
terms: Round — one gossip interval, in which each node contacts its chosen peers (often one second in practice).
Fanout — the number of peers a node contacts in each round.
Push, pull, push-pull — a node sends its news to the peer (push), asks the peer for news (pull), or both in one exchange.
Anti-entropy — periodically comparing full state (or digests of it) with a peer and repairing any difference.
Rumour mongering — spreading each new update only while it is still "hot", then stopping once it seems old to most peers.
Digest — a compact summary of a node's state (for example, each key with its version number) used to find differences without sending the data.
Membership list — the set of nodes a node believes are in the cluster; gossip keeps these lists in agreement.
Suspicion — a state between "alive" and "dead" in which a node is doubted but not yet removed, to avoid false alarms.
history: Gossip came from a practical problem at Xerox PARC. The Clearinghouse name service kept many replicas of a database spread across a worldwide network, and the first method for keeping them in step, mailing each update to every site, overloaded the network and lost messages. Alan Demers, Dan Greene, Carl Hauser, Wes Irish, John Larson, Scott Shenker, Howard Sturgis, Dan Swinehart and Doug Terry wrote "Epidemic Algorithms for Replicated Database Maintenance" (PODC 1987). They borrowed the mathematics of epidemics: a rumour is like a disease, and the model tells you how fast it spreads and how to make it stop. They defined anti-entropy and rumour mongering, and tested them against the real Xerox Corporate Internet.
For about a decade this stayed a replicated-database technique. Pittel's 1987 analysis gave the exact round count for push gossip: about log₂ N + ln N. Then in the late 1990s and 2000s the scale of peer-to-peer systems and data centres created demand. Van Renesse, Minsky and Hayden's "A gossip-style failure detection service" (1998) used gossip for failure detection. SWIM (Das, Gupta and Motivala, DSN 2002) separated failure detection from dissemination and made the message load per node constant. Amazon's Dynamo paper (2007) used gossip for membership, and Cassandra, Riak and Voldemort followed.
In the 2010s HashiCorp built memberlist, Serf and Consul on SWIM, and in 2018 published Lifeguard, which added awareness of the sender's own health, so that a slow node stops falsely accusing healthy ones. In blockchains, transaction and block relay is gossip, and Ethereum's networking layer uses GossipSub from libp2p, a structured variant that keeps a small mesh of peers per topic. Recent work in Cassandra moves cluster metadata off gossip onto a consensus-style log, because gossip's eventual convergence is hard to reason about for schema and topology changes. Gossip remains the standard tool for liveness and soft state.
how: Every node holds some state: a set of key-value entries, each with a version number. Every round (say each second) a node picks a random peer (or a few) and runs an exchange. In push-pull anti-entropy the exchange has three steps. The initiator sends a digest of its state: for each key, the version it holds. The peer compares it with its own, replies with the entries it has that are newer, and asks for the entries where the initiator is newer. The initiator then sends those. Both end with the newer version of each entry. Cassandra calls the three messages SYN, ACK and ACK2. Because versions only increase, two nodes always agree on which is newer, and repeating an exchange is harmless.
Why does it spread so quickly? Count informed nodes. At the start one node knows. Each round, every informed node tells one random node, so the number of informed nodes about doubles while most nodes are still uninformed. This is exponential growth, and it takes about log₂ N rounds to inform half the cluster. Then the situation reverses. When most nodes are informed, each uninformed node is hit by a push with probability about 1 − 1/e per round, so the number of uninformed nodes shrinks by a factor of about e each round, and it takes about ln N more rounds to reach zero. The total is log₂ N + ln N, Pittel's result. Pull helps in the endgame: an uninformed node asks a random peer, and the peer is very likely informed. Push-pull shortens the tail so that the second phase takes only about log log N rounds.
Larger fanout reduces rounds but increases messages. With fanout f, the doubling becomes multiplication by (1 + f), so the first phase is log base (1 + f) of N. Usually f is 1 to 3. The random graph facts from the lower layer are why this works for any starting node: random contact choices form a graph whose diameter is of order log N, and which stays connected even if a large fraction of nodes disappear. That is why there is no need for any node to keep a perfect view of the cluster; a partial or slightly stale list is enough to pick random peers.
Gossip is used for two jobs, and they differ. For dissemination of state, each node keeps a table such as "node → (heartbeat counter, status, tokens, datacentre)". Cassandra has each node bump its own heartbeat version every second and gossip with up to three others per round: one random live node, possibly a seed node, and possibly an unreachable node to detect recovery. Seeds are known entry points for new nodes. A new node contacts a seed, learns the member list, and from then on gossip is symmetric. For failure detection, SWIM does not rely on heartbeats spreading. Each period a member pings one random member. If no ack arrives in time, it asks k other members to ping the target indirectly. If still no ack, it marks the target suspect and gossips this, giving the target time to refute it, before declaring it dead. Information about joins, suspects and deaths is piggybacked on the ping and ack messages, so there are no extra messages. The detection time is constant, on average about 1.6 protocol periods, and the load per member is constant, whatever the cluster size.
The decision "is that node dead" can use the heartbeat history. Cassandra uses a phi-accrual detector (the neighbouring concept on failure detection): it learns how often heartbeats from each node arrive and computes a suspicion value, which it compares with a threshold (8 by default). Redis Cluster uses gossip differently: each node marks another as possibly failing (PFAIL) after a timeout, shares that opinion by gossip, and a node is marked failed (FAIL) only when a majority of master nodes report it, which avoids one bad link from causing a failover.
Finally, gossip needs a way to stop. In rumour mongering a node keeps pushing an update until it has contacted several peers that already knew it, and then it stops. This saves bandwidth but allows a small chance that some node never hears; an occasional anti-entropy round fixes the gap. Real systems combine them: rumour mongering for speed, anti-entropy for certainty.

example: Take a cluster of N = 1,000 nodes and a single update, for example "node 417 joined". Use push gossip with fanout 1 and one round per second. At round 0 one node knows. Each informed node pushes to one random node per round. Early on, collisions are rare, so the count about doubles: 1, 2, 4, 8, 16, 32, 64, 128, 256, 500 after about 9 to 10 rounds. Now about half the nodes know. Each push now reaches an uninformed node with probability about one half, and uninformed nodes are hit often. The uninformed count falls from 500 by a factor near e each round: about 184, 68, 25, 9, 3, 1 over the next six or seven rounds. So all nodes know after roughly 17 rounds, matching log₂ 1000 + ln 1000 = 9.97 + 6.91 ≈ 16.9. At one round per second, the whole cluster learns in about 17 seconds. The message count is about 1,000 messages per round once most nodes are informed, so a few thousand messages per second cluster-wide and one per node per second. With a million nodes the same calculation gives about 34 rounds.
Next, bandwidth. Suppose each node gossips with 3 peers per second, and the SYN digest costs about 30 bytes per cluster member (an address, a generation and a version; an assumption for illustration). For 1,000 nodes a digest is about 30 KB. Three per second is about 90 KB/s per node outbound for digests, and about 90 MB/s across the cluster. For 100 nodes it is 3 KB per digest, so 9 KB/s per node. This shows the real cost of full-state anti-entropy: the digest grows linearly with the cluster, so the cost per node grows linearly and the cluster-wide cost grows with N². Large systems therefore use smaller digests, gossip only changed entries, or use SWIM-style piggybacking, where each message carries only a few recent updates.
Failure detection with SWIM numbers. With a protocol period of 1 second and a probe timeout of 500 ms, a failed node is probed by someone, on average, within about 1.6 periods. After a failed direct and indirect probe it becomes suspect, and a suspicion timeout (typically a few periods, scaled with log N) gives it a chance to refute before being declared dead. A node that is truly dead is therefore removed from every member's list within roughly 5 to 10 seconds in a cluster of thousands.
intuition: Like a rumour at a party: nobody makes an announcement, each person tells a few others, and soon everyone knows.
The design is natural because it replaces a plan by a probability. A plan, such as a spanning tree, is efficient until a node fails, and then it must be repaired. Random contact needs no structure to repair. Since every node does the same simple thing, there is no special role to lose. The exponential growth of an epidemic gives speed, and the randomness gives resilience: a few failed nodes only remove a few of the many paths.
mistakes: People often think gossip delivers an update to every node for sure, within a fixed time. In fact delivery is probabilistic. The round count log₂ N + ln N is the expected time for everyone; the chance that some node is still missing after a few more rounds is small and drops exponentially, but it is not zero. For a hard guarantee you add anti-entropy, which eventually compares full state.
People often think gossip is cheap because each node sends only a few messages. In fact the cost depends on message size. Full-state digests grow with cluster size, and each update is delivered to each node several times (a node gets about log N copies), so total traffic is larger than the minimum of N messages per update. Large deployments cap the digest size or gossip only recent changes.
People often think gossip gives a consistent view of the cluster. In fact views differ at any moment. Node A may think B is dead while C still thinks B is alive. That is fine for membership hints and failure suspicion, but not for decisions that need agreement, such as who is the leader or what the schema is. Those need consensus.
People often think gossip means the failure detector is accurate. In fact gossip spreads opinions; it does not make them right. A slow or overloaded node can be falsely suspected by many peers, and the suspicion spreads quickly. SWIM's indirect probes and suspicion period, and Lifeguard's self-health checks, exist to reduce such false positives.
friction: Convergence time is probabilistic and depends on churn. During a rolling restart of hundreds of nodes, new information arrives faster than it spreads, and nodes can hold conflicting views for minutes. Cassandra operators know this: after large topology changes, schema disagreement and "node appears down on some nodes" reports can last until gossip settles, and some operations need to wait for it.
Gossip is also hard to debug and hard to bound. A bug that corrupts state can spread as fast as a good update. Amazon's S3 outage of July 2008 was caused by a corrupted gossip message that spread through the system and had to be flushed by stopping all servers and restoring a known state. The same speed that makes gossip strong makes errors travel.
Security and scale bring more limits. A malicious node can inject false state, claim to be everywhere or accuse healthy nodes, and basic gossip has no authentication. Bandwidth grows with state size, so a cluster with large per-node state or very many members needs hierarchy or sampling. Finally, gossip provides eventual agreement only. It cannot give you a total order, a leader or an atomic change, and teams sometimes push too much onto it, such as schema and topology changes, then spend years debugging convergence races.
practice: Use gossip for soft state that tolerates some staleness: membership, health, load, locations of data, and configuration hints. Keep entries small and versioned, make merges monotone (newer version wins, by a counter and not by wall-clock time), and make every merge idempotent. Use a heartbeat counter owned by each node, so a node's own claim about itself is always authoritative over others' opinions.
Choose the parameters from the numbers above. Round interval of 1 second and fanout of 1 to 3 is typical. Check that your convergence time (about log₂ N + ln N rounds) fits your needs: for 1,000 nodes, about 17 seconds. If you need faster failure detection, shorten the protocol period or use SWIM-style probing with indirect pings, and tune the suspicion timeout using a few multiples of the period. Add awareness of local health so that a stalled node does not accuse others.
Do not use gossip for decisions that need agreement: electing a leader, assigning ownership of a shard, committing schema changes. Use a consensus-based store (a Raft group or ZooKeeper) for these, and let gossip carry only hints and liveness. Seed nodes should be several, in different failure domains, and should not be special for correctness.
In operations, monitor the gossip layer: number of nodes each node sees, heartbeat age, pending gossip tasks, and message sizes. In Cassandra, watch for nodes that show different cluster views (nodetool status from several nodes) and schema disagreement before and after changes, and roll restarts slowly enough for gossip to catch up. Test with partitions and node pauses, not only with clean crashes.
tradeoffs: Choose gossip when the cluster has hundreds to thousands of nodes, state is small and tolerates seconds of staleness, and you want no single point of failure. You give up fast, exact agreement: views differ for seconds, and delivery is probabilistic.
Choose a central registry or a consensus-backed coordination service (etcd, ZooKeeper, Consul servers) when you have tens to a few hundred members and need linearizable membership or locks. You get one authoritative view and pay with a few round trips per change and a small quorum that must be kept healthy. Many systems combine them: a small consensus group for decisions, gossip for liveness of the many.
Choose push-pull over push alone when latency of the last nodes matters; it reduces the endgame from ln N rounds to about log log N at the cost of two-way exchanges. Choose rumour mongering over pure anti-entropy when updates are frequent and small and bandwidth is scarce; choose anti-entropy when you must guarantee convergence and can afford to compare digests.
Choose a higher fanout or shorter interval when you need seconds-level detection and have bandwidth to spare; choose a lower fanout and longer interval for very large clusters or wide-area links, accepting detection in tens of seconds. Choose SWIM-style piggybacking over full-state gossip when state per node is large or the cluster is above a few hundred nodes, since it keeps per-node load constant.
interview: Derive roughly how many rounds push gossip needs to inform N nodes and explain the two phases. || About log₂ N + ln N. Why does push-pull converge faster than push? || In the endgame most nodes are informed, so an uninformed node that pulls from a random peer almost surely gets the update. Only if all fail does the target become suspect. Indirect probes avoid false positives caused by a bad link between two particular nodes. News is piggybacked on probes, so load per member does not grow with the cluster size.

quiz: What is the difference between anti-entropy and rumour mongering? || Anti-entropy periodically compares full state (or digests) with a peer and repairs any difference, so it is certain but costly. value: A failure detector is the part of a distributed system that answers one question: has that node stopped working? The answer is always a guess. In a network where messages can be delayed without limit, a node that has crashed and a node that is only slow look the same from outside: no reply arrives. So every detector chooses how long to wait, and this choice is a trade between detecting real failures quickly and accusing healthy nodes by mistake. Wait 1 second and a 2-second garbage-collection pause causes a false alarm. Wait 60 seconds and a real crash leaves users hanging for a minute.
The answer drives everything above it. When a detector says "dead", the system fails over to a replica, elects a new leader, releases the node's locks, removes it from the load balancer and rebalances its data. A false positive means an expensive failover, possibly with two nodes both believing they are the leader. A false negative means long stalls. Coordination services such as ZooKeeper and etcd use session timeouts to release locks. Load balancers use health checks. Service meshes eject slow endpoints. Circuit breakers trip on timeouts. Kafka consumer groups rebalance when heartbeats stop. All of them are failure detectors with different settings.
It stands on two lower concepts. Hardware clocks and timers (L3) provide the only tool a detector has: measuring how much local time has passed since the last message. Timers must be monotonic (not jump with clock corrections), and they run at slightly different speeds on different machines. Statistics and estimation (L4) provide the way to choose the timeout well. Heartbeat arrival times are a random variable with a mean, a spread and a tail. Estimating that distribution from recent history, and asking how unlikely the current silence is, replaces a hand-picked constant with a probability.
terms: Heartbeat — a small periodic message ("I am alive") sent from a node to a monitor, or a probe and reply in the other direction.
Timeout — the silence after which a node is declared failed.
Completeness — every node that really crashes is eventually suspected by every working node.
Accuracy — working nodes are not suspected (strong: never; eventual: only for a finite time).
False positive — a healthy node declared dead; its cost is a needless failover.
Detection time — the delay between the crash and the declaration.
Lease — a promise to act as owner for a fixed time; the holder must stop when its own clock says the lease is over.
Phi (φ) accrual — a continuous suspicion value computed from the history of heartbeat arrival times, compared with a threshold chosen by the user.
history: The theory came first. Fischer, Lynch and Paterson proved in 1985 (the FLP result) that no deterministic algorithm can guarantee consensus in an asynchronous system if even one process may crash, and the reason is exactly that a slow process cannot be told apart from a dead one. Chandra and Toueg's "Unreliable Failure Detectors for Reliable Distributed Systems" (JACM 1996) turned the obstacle into a tool. They defined detectors by two properties, completeness and accuracy, and showed that consensus becomes solvable with a detector that is only eventually accurate (called ◇S) when a majority of nodes stay up. This is the theoretical reason that Paxos and Raft work with timeouts: they need the detector only to be right eventually, for liveness. Safety never depends on it.
Practice added the engineering. Gray and Cheriton's "Leases" (SOSP 1989) described time-limited grants as a fault-tolerant alternative to locks. Chen, Toueg and Aguilera ("On the quality of service of failure detectors", 2002) defined measures such as detection time and mistake rate, so that detectors could be compared. Hayashibara, Défago, Yared and Katayama published the φ accrual failure detector in 2004: instead of saying "dead" or "alive", it outputs a number that grows with the silence. Cassandra adopted it, and so did Akka. SWIM (2002) added indirect probing through third nodes to cut false positives caused by one bad link. HashiCorp's Lifeguard (2017) made a node aware of its own slowness.
In the 2010s large cloud systems showed a new class: gray failures, described by Huang and colleagues at Microsoft in 2017. A node answers heartbeats but cannot do real work, for example a disk that takes seconds per write. The detector says healthy while users suffer. Modern systems add application-level health signals and outlier detection to catch such cases.
how: A detector has two parts: a source of evidence and a rule that turns evidence into a verdict. The evidence is messages from the node, or replies to probes. The simplest scheme is a heartbeat with a fixed timeout. The monitored node sends a message every period T_h (for example 1 second). The monitor keeps the time of the last heartbeat on its local monotonic clock. If more than T_o has passed without one, it declares the node failed. T_o must be larger than T_h plus the typical delay, and a common rule is to allow several missed heartbeats, such as T_o = 3 × T_h. Raft follows this scheme: a follower that hears no heartbeat from the leader for a randomised election timeout (the paper uses 150 to 300 ms) starts an election. ZooKeeper clients keep a session alive with pings, and the server expires the session if it hears nothing for the session timeout, which is bounded between 2 and 20 times the server's tick time.
Pull is the alternative: the monitor sends a probe and waits for a reply (a ping). This tests the round trip, including the path back to the monitor, and works through firewalls, at the cost of more messages. Health checks from a load balancer are pull detectors. They usually require several consecutive failures before removing a backend (for example 2 or 3) and several successes before restoring it, which gives hysteresis against flapping.
The fixed timeout has an obvious weakness: network delay is not constant. On a quiet local network heartbeats arrive within a millisecond of schedule and a 3-second timeout wastes time. On a congested wide-area link the same timeout produces false alarms. The adaptive approach measures. Keep a sliding window of recent inter-arrival times, estimate their mean and variance, and set the timeout to mean plus a multiple of the spread. TCP does exactly this for retransmissions: Jacobson's algorithm sets the timeout to the smoothed round-trip time plus four times the smoothed deviation. This is the use of statistics at its simplest.
The φ accrual detector goes one step further and avoids choosing the timeout at all. It fits a distribution to the window of inter-arrival times (a normal distribution in the paper and in Akka, an exponential one in Cassandra). Given the silence so far, Δ, it computes the probability P that a heartbeat would still arrive after Δ, and outputs φ = −log₁₀(P). So φ = 1 means a 10% chance that the node is merely late, φ = 2 means 1%, φ = 3 means 0.1%, and φ = 8 means one in 100 million. The application chooses a threshold (8 is the default in both Akka and Cassandra). The same threshold then gives sensible timeouts on fast and slow links, because the estimate adapts. Different consumers can use different thresholds on the same φ: a load balancer might act at φ = 3, a failover manager at φ = 10.
Indirect probing deals with the case where the path between monitor and target is bad but the target is fine. In SWIM, a monitor that gets no ack asks k other nodes to probe the target. Only if all fail does it suspect the target. This reduces the false positives caused by one failed link, a common cause in practice. A suspicion state, rather than immediate death, gives a slow node time to answer "I am alive" before it is removed.
Leases add a different guarantee. A lease is a heartbeat that gives the holder a right: "you are the leader until time X". The holder must renew before expiry and must stop acting when its own timer says the lease is over. The monitor does not need synchronised clocks, only a bound on how fast clocks can drift: the grantor waits slightly longer than the lease duration before reusing the resource. Leases make the system safe when a node is cut off: it stops by itself. But leases rest on local timers, so a long pause of the holder (a garbage collection, a stopped virtual machine) can cause it to act after its lease has expired. That is why storage should also check fencing tokens, the neighbouring concept.
Finally, completeness across the cluster needs sharing: in gossip-based detectors, each node's opinion is spread to others, and a node is removed when a quorum agrees (as in Redis Cluster) or when the suspicion expires without refutation (as in SWIM).

example: Take heartbeats sent every 1.0 second. On a quiet network their arrival gaps have mean 1.0 s and standard deviation 0.2 s. Use the normal model of the φ accrual detector. The silence since the last heartbeat is Δ. Compute z = (Δ − 1.0) / 0.2 and then P = the chance that a gap is longer than Δ. At Δ = 1.5 s, z = 2.5 and P ≈ 0.0062, so φ = −log₁₀(0.0062) ≈ 2.2. At Δ = 2.0 s, z = 5, P ≈ 3 × 10⁻⁷, so φ ≈ 6.5. At Δ = 2.12 s, z = 5.6, P ≈ 1 × 10⁻⁸, so φ ≈ 8, the usual threshold. So on this link the node is declared dead after about 2.1 seconds of silence.
Now the same threshold on a noisy link whose gaps have standard deviation 1.0 s. The threshold is reached at Δ = 1.0 + 5.6 × 1.0 = 6.6 s. A fixed timeout of 3 s would be too slow on the quiet link (it waits 3 s when 2.1 s is enough) and too quick on the noisy link, where it would fire often during normal variation. The adaptive detector gives about 2 s detection on one and 6.6 s on the other, with the same false-alarm target of one in 10⁸ per check.
Cassandra uses an exponential model, where P = e^(−Δ/mean), and then φ = Δ / mean × log₁₀(e) = 0.434 × Δ / mean. With a mean of 1 s and threshold 8, it declares a node down after 8 / 0.434 ≈ 18.4 s of silence. That is much more patient than the normal model, because an exponential tail is heavier than a normal one and so tolerates long gaps. This explains why Cassandra takes many seconds to mark a node down by default, and why operators on noisy cloud networks sometimes raise the threshold to 12 so that a brief pause does not cause a flap.
A lease example. A leader gets a 10-second lease and renews every 3 seconds. The grantor will not give the lease to anyone else until 10 s plus a drift margin (say 0.5 s) have passed since its last grant. If the leader loses the network at time 0, it stops acting at time 10 by its own timer. The grantor lets a new leader start at about 10.5 s on its timer. If the old leader's process was frozen by a 15-second garbage-collection pause, however, it wakes up at 15 s and thinks it still holds the lease until its code checks the timer. A write sent in that gap is stale; fencing tokens at the storage layer catch it.
intuition: How long do you wait for a reply before you decide someone has left the call? Too short and you hang up on slow talkers; too long and you wait forever.
The design is natural because you cannot see the other machine, only the messages it sends. Silence is the only evidence, and silence is weak: it fits both "dead" and "late". The honest answer is therefore a degree of belief that grows as silence grows. Accrual detectors say that directly. Everything else (fixed timeouts, quorum votes, suspicion periods) is a way of turning a degree of belief into an action while paying a known price for being wrong.
mistakes: People often think a failure detector can tell whether a node is dead. In fact it can only report that the node has not answered within some time. In an asynchronous network a perfect detector is impossible, which is the heart of the FLP result. Systems must work correctly even when the detector is wrong, using consensus and fencing so that a wrongly accused node cannot do harm.
People often think a shorter timeout is always better because failover is faster. In fact a short timeout multiplies false positives, and each false positive has a cost: a failover can move leadership, trigger data movement and cause a burst of load that makes other nodes late, which causes more false positives. Several outages have followed this feedback loop.
People often think heartbeats prove a service is healthy. In fact a heartbeat thread can run normally while the request-handling threads are stuck, as in gray failures. A heartbeat proves only that the process and the network path work. Health checks should exercise something real, such as a cheap query, and the monitor should also look at error rates and latency.
People often think leases solve the problem of knowing who is alive. In fact a lease limits the damage of a silent node only if its timer is accurate and the node runs the check before every action. A process paused for longer than the lease can still act on a stale belief. Fencing tokens are needed in addition.
friction: False positives and false negatives cannot both be removed. Any improvement in one costs the other, and the best detector for your system depends on your tolerance for each. A measured frame helps: Chen, Toueg and Aguilera propose three numbers, detection time, mistake recurrence time and mistake duration, and the first two trade against each other.
Pauses are the largest source of false alarms in managed-runtime systems. A stop-the-world garbage collection of 5 to 30 seconds, a virtual machine live migration, a noisy neighbour, or swapping can stall a healthy node longer than the timeout. Kafka's consumer settings show the compromise: session.timeout.ms defaults to 45 seconds (since version 3.0), heartbeat.interval.ms to 3 seconds, and a separate max.poll.interval.ms of 5 minutes catches consumers that are alive but stuck. KRaft brokers use a shorter 9-second session timeout. The more you tolerate, the slower the failover.
Partial failures are harder still. A node reachable from some peers and not from others will be declared dead by some, alive by others. A node that can send but not receive keeps heartbeating while deaf. Gray failures pass every heartbeat. Detection in large clusters adds a scale problem: all-to-all heartbeats cost N² messages, so large systems use gossip or random probing, which brings its own delay and inconsistency. Finally, local time itself can mislead: a timer based on the wall clock jumps when NTP steps the clock, and a monotonic clock may stop during suspend, so implementation details cause real incidents.
practice: Set the timeout from measurement, not guess. Record the distribution of heartbeat gaps or round-trip times in production, including the tail (p99, p99.9), and choose the timeout above the tail with margin, accepting the detection delay it implies. AWS's guidance on timeouts uses the same approach: pick the acceptable false-timeout rate, for example 0.1%, and set the timeout at the matching latency percentile.
Use monotonic timers for all timeouts. Use several consecutive misses before acting, and use hysteresis (more successes needed to recover than failures to eject) to stop flapping. Separate detection from action: let the detector produce a suspicion, and let a slower, more careful process (with a quorum or a human) decide for costly actions such as promoting a database primary or evicting a whole rack.
Always assume the detector can be wrong. Whenever a failover is triggered by a detector, make the old holder harmless: use leases that the old holder honours, fencing tokens checked by storage, or shooting the old node (STONITH) before the new one starts. Prefer consensus-based leader election (Raft, ZooKeeper, etcd) over homegrown heartbeat protocols.
Monitor the detectors themselves: count suspicions, refutations and flaps, and alert on a rising false-positive rate. Where possible, combine signals: network heartbeats, application health checks, error rates and request latency, as service meshes do with outlier detection (eject an endpoint after a few consecutive errors, for a base time that grows with repeated ejections, and cap the share of ejected hosts so a bad deploy cannot empty the pool).
tradeoffs: Choose a fixed timeout with several missed heartbeats when the network is stable, delays are well known (a single rack, a data-centre LAN) and you want a simple, predictable rule. You give up adaptivity: it will be too slow on good links and too nervous on bad ones.
Choose an accrual detector (φ) when links differ in quality, as across zones or regions, and you want one threshold to behave consistently; you pay with a statistical model that can be wrong in the tail and some state per monitored node. Choose a threshold near 8 for decisions that are costly to reverse, and lower (3 to 5) for cheap, reversible actions such as removing a backend from rotation.
Choose all-to-all heartbeats when the cluster has fewer than about 50 nodes and you want the fastest and most direct signal. Choose SWIM-style random probing with gossip when the cluster has hundreds to thousands, accepting detection in several seconds and less consistent views, in exchange for constant load per node.
Choose a longer timeout and a quorum decision for stateful failover (databases, leaders), where a false positive can corrupt data or cause a split brain and 10 to 30 seconds of delay is tolerable. Choose a short timeout with a quick retry for stateless services behind a load balancer, where a false positive only moves traffic, and 1 to 3 seconds is typical.
interview: Why can't a failure detector in an asynchronous network be both complete and accurate? || A crashed node and a very slow node produce the same evidence: silence. To be complete, you must eventually suspect silent nodes. To be always accurate, you must never suspect a slow node. With unbounded delays both cannot hold. Real detectors give up accuracy for a while (eventual accuracy) and rely on higher layers to stay safe.
How does the φ accrual detector work, and why is it better than a fixed timeout? || It keeps a window of heartbeat inter-arrival times, fits a distribution, and computes φ = −log₁₀ of the probability that a heartbeat is still to come after the current silence. The user picks a threshold on φ. Because the distribution adapts to the link, the same threshold works on fast and noisy paths, whereas one fixed timeout fits only one of them.
A Cassandra node is marked down repeatedly during GC pauses. What would you change and why? || First reduce the pauses (heap size, collector settings), because they also hurt latency. Then consider raising phi_convict_threshold moderately, which lengthens detection but cuts false alarms. Check network and CPU saturation as causes. Avoid a very high value that would leave real failures undetected for a long time.
Why do leases need clocks only for drift and not for synchronisation, and where do they still fail? || The holder and the grantor each measure a duration on their own clocks; only the rate at which clocks run must be bounded, and the grantor adds a margin. Leases fail when the holder is paused beyond the lease and acts without re-checking, which is why storage should enforce fencing tokens.
Design failure detection for a 2,000-node service. || Use SWIM-style probing: each node probes one random peer per second with indirect probes through a few others, a suspicion period of a few seconds, and piggybacked updates for membership. Add local-health awareness, and application-level health checks for gray failures. Let a small consensus group make costly decisions such as electing leaders.
What is a gray failure and how would you detect it? || A component that looks healthy to the detector but fails the real work, such as a slow disk or a thread pool deadlock. Detect it with end-to-end checks (a real read or write), latency and error-rate outlier detection against peers, and observations from clients that use the component.
quiz: What two properties define a failure detector in Chandra and Toueg's framework? || Completeness (crashed nodes are eventually suspected) and accuracy (working nodes are not suspected, either never or only for a limited time).
Why does a φ value of 3 mean what it means? || φ = −log₁₀(P), so φ = 3 means P = 0.001: there is a 0.1% chance that a heartbeat would still arrive after this much silence, so a mistaken accusation would occur about once in a thousand checks.
Heartbeats have a mean gap of 1 s and standard deviation of 0.2 s. At roughly what silence does the normal-model φ cross 8? || φ = 8 means P = 10⁻⁸, which is about 5.6 standard deviations, so 1.0 + 5.6 × 0.2 ≈ 2.1 s.
Why does SWIM probe through other nodes before suspecting a target? || The failure may be on the link between the prober and the target. If other nodes can reach the target, it is alive, so indirect probes cut false positives from a single bad path.
When should a system use a short timeout, and when a long one with a quorum? || Short for stateless services behind a load balancer where a false positive only moves traffic. Long, with quorum agreement, for stateful failover such as database primaries, where a false positive can cause split brain or data loss.

@@ twopc
value: Two-phase commit (2PC) is the classic protocol for making a transaction atomic across several machines: either every machine commits its part, or every machine aborts. Without it, a transfer of money from an account on one shard to an account on another could commit on one side and fail on the other, and money would be created or destroyed. 2PC prevents this by splitting the commit into a vote and a decision. First the coordinator asks every participant "can you commit?", and each participant makes its changes durable and promises to be able to commit. Only after all promises are in does the coordinator decide, record the decision durably, and tell everyone.
The key idea is the promise. Once a participant has voted yes, it has given up its right to abort on its own. It will commit if told to commit and abort if told to abort, even if it crashes and restarts in between. That promise is what lets the coordinator make an irrevocable decision for the group. The price is that a participant that has voted yes must wait for the decision, holding its locks, and if the coordinator disappears at the wrong moment, it can be stuck.
2PC is used wherever one logical transaction touches several resources: distributed SQL databases (Spanner and CockroachDB across ranges or Paxos groups), sharded MySQL and PostgreSQL setups, XA transactions that join a database and a message broker, Kafka transactions that write to several partitions, and even inside a single MySQL server, which uses 2PC between its binary log and the storage engine to keep them consistent. It stands on two lower concepts. ACID transactions (L3) define the property being extended: atomicity and durability on one machine become atomicity across machines. Crash recovery with write-ahead logging, as in ARIES (L3), supplies the durable "prepared" record, and the recovery procedure that brings an in-doubt transaction back, with its locks, after a restart.
terms: Coordinator — the node that drives the protocol, collects votes and decides the outcome.
Participant (or resource manager) — a node that holds part of the transaction's data and votes.
Prepare (vote request) — phase 1: the participant makes its changes durable, logs a prepared record, and votes yes or no.
Commit or abort decision — phase 2: the coordinator logs the outcome and sends it to all participants.
In-doubt (uncertain) — the state of a participant that voted yes and has not yet heard the outcome; it cannot decide alone.
Forced write — a log write flushed to stable storage before the protocol proceeds (fsync).
Blocking — the property that participants may have to wait indefinitely for a failed coordinator to recover.
Presumed abort — an optimisation: if the coordinator has no record of a transaction after a crash, everyone assumes it aborted.
history: The idea appeared in the mid-1970s. Butler Lampson and Howard Sturgis described a crash-recovery protocol for distributed storage in 1976. Jim Gray's 1978 "Notes on Data Base Operating Systems" gave the clearest early account of two-phase commit. It is the first widely read description, and Gray later received the Turing Award (1998) for his work on transactions. IBM's System R* research project (1980s) refined it: C. Mohan, Bruce Lindsay and Ron Obermarck published "Transaction Management in the R* Distributed Database Management System" (1986), which introduced the presumed-abort and presumed-commit optimisations that cut the number of log writes and messages.
Standardisation followed. The X/Open DTP model and its XA interface (1991) let a transaction manager coordinate several databases and queues from different vendors, and Java's JTA made it the standard enterprise pattern in the 1990s and 2000s. At the same time researchers studied its weakness. Dale Skeen's three-phase commit (1981) removed blocking under strong timing assumptions that real networks do not meet. In 2006 Jim Gray and Leslie Lamport's "Consensus on Transaction Commit" showed Paxos Commit: store each participant's vote with a Paxos consensus group, so that the decision survives coordinator failure. Classic 2PC is the special case with a single acceptor.
Modern systems use 2PC in new forms. Google's Percolator (2010) ran a client-driven 2PC on top of Bigtable rows, with one "primary" lock deciding the outcome. Spanner (2012) runs 2PC between Paxos-replicated groups, so the coordinator and participants never disappear as single machines. CockroachDB's parallel commits (2019 onward) cut one round trip from the commit path. Calvin (2012) avoided 2PC for deterministic transactions by agreeing on an order first. For long business processes, Garcia-Molina and Salem's sagas (1987) replaced atomic commit with compensating actions.
how: The protocol has a coordinator C and participants P1 … Pn. The client asks C to commit a transaction that has already done its reads and writes at the participants, which hold locks on the data they touched.
Phase 1, prepare. C writes a start record to its log (optional in some variants) and sends PREPARE to every participant. Each participant checks that it can commit: no constraint violation, no deadlock victim, enough space. If it can, it forces a prepared record to its write-ahead log, which contains everything needed to redo the transaction after a crash (its writes, plus its locks). Only after that write is on stable storage does it reply VOTE-YES. It keeps all its locks. If it cannot commit, it aborts the transaction locally, releases its locks, and replies VOTE-NO.
Phase 2, decide. If C receives YES from all participants, it forces a commit record to its own log. This single write is the commit point: from this instant the transaction is committed, even if the machines crash straight afterwards. C then sends COMMIT to all participants. If any participant voted NO, or did not answer within the timeout, C decides to abort, logs it (or, under presumed abort, writes nothing) and sends ABORT. Each participant, on receiving the decision, writes a commit or abort record, applies it, releases its locks, and acknowledges. When all acknowledgements arrive, C writes an end record and can forget the transaction.
Why is this atomic? Because the commit point is a single durable fact at one place. Before C's commit record exists, no participant has been told to commit, and any participant can still be told to abort. After it exists, the outcome is commit, and every participant, having promised, will commit when it learns. The prepared record on each participant is what makes the promise survive crashes. Crash recovery from the lower layer does the rest. On restart, a participant replays its log and finds a prepared transaction with no outcome. It must not abort it or commit it on its own. It restores the transaction's writes and locks (the ARIES recovery procedure treats it as in-doubt) and asks the coordinator what happened. The coordinator, on its restart, finds in its log either a commit record (resend COMMIT), or no decision (under presumed abort, answer ABORT).
Messages and log forces: for n participants, 2PC uses 4n messages (prepare, vote, decision, acknowledgement) and about 2n + 1 forced log writes: a prepare record and a commit record per participant, plus the coordinator's commit record. The latency the client sees is about two round trips plus log forces: one round trip for the votes, the coordinator's forced commit write, and then it can tell the client "committed". The participants learn the outcome one half round trip later. The locks, though, are held for the whole two round trips plus forces, and this lock hold time is what limits throughput. Optimisations exist: read-only participants vote read-only and drop out of phase 2; presumed abort avoids forced writes for aborts; one-phase commit applies when only one participant has written.
The weakness is blocking. Suppose the coordinator crashes after collecting votes but before sending the decision. The participants hold locks and are in doubt. They cannot abort, because the coordinator might have already decided to commit and told another participant. They cannot commit, because some participant might have voted no. They may ask each other (the cooperative termination protocol): if any participant has seen the outcome, or has not voted yes, they can resolve. If all are in doubt, they wait for the coordinator to return. During this time the locked rows are unavailable to everyone.
Modern designs remove the weak point by making the coordinator itself fault-tolerant. In Spanner, the coordinator is a Paxos group's leader, and its decision is written to a replicated log, so another replica takes over. In Percolator, the decision is the state of a single primary key in Bigtable, and any client that finds a stuck transaction can look at that key and finish the protocol. In CockroachDB the transaction record is itself replicated by Raft, and parallel commits let the transaction be treated as committed once all its writes are replicated, even before the final status is written.

example: Move 500 rupees from account X on shard A to account Y on shard B. The coordinator is a service node, and a transaction id is T7. The client has already done, at A, "X = X − 500" and, at B, "Y = Y + 500". Each shard holds a lock on its row.
Phase 1. C sends PREPARE(T7) to A and B. A checks that X stays non-negative, forces "T7 prepared: X old 2000, new 1500" to its log (one fsync, perhaps 0.2 ms on an NVMe drive), and replies YES. B forces "T7 prepared: Y old 100, new 600" and replies YES. Both still hold their row locks. Inside a data centre with a round trip of 0.5 ms, phase 1 takes about 0.5 ms for the network plus 0.2 ms for the slower fsync.
Phase 2. C has two YES votes. It forces "T7 commit" to its log, another 0.2 ms. The transaction is now committed. C tells the client "done" and sends COMMIT to A and B. They write commit records, release locks and acknowledge. From the client's view the commit took about 0.9 ms. The row locks were held for about 1.4 ms until the decision reached the participants. If one row is updated by a chain of such transfers, the ceiling is about 1 / 1.4 ms ≈ 700 per second on that row. Across regions with an 80 ms round trip, the locks are held for at least 160 ms and the hot-row ceiling falls to about 6 per second. This is the main reason distributed transactions are expensive.
Failure cases. First: B cannot commit (Y was closed). B votes NO and aborts locally. C sees the NO, decides abort, and tells A, which was prepared and now rolls back and releases its lock. No money moved. Second: C crashes after sending PREPARE and receiving both votes, before writing a decision. A and B are in doubt with locks held. They ask each other, both say "I voted yes, no outcome", so they wait. When C restarts, its log has no commit record, so under presumed abort it answers ABORT to both. Third: C crashes just after forcing the commit record. On restart it reads "T7 commit" and resends COMMIT until both acknowledge. The money moves exactly once, because applying COMMIT twice is harmless: it is idempotent.
The cost of the blocking case: if C stays down for 10 minutes, rows X and Y are locked for 10 minutes, and any other transaction that touches them waits. Systems limit this by timeouts on the transaction manager, automatic failover of the coordinator, and administrators' tools for forcing a heuristic decision, which risks inconsistency if the guess is wrong.
intuition: A wedding: the officiant asks each side "do you?", and only when both have said yes aloud does the officiant declare them married; after that nobody can take it back.
The protocol is natural because agreement needs a point of no return, and you cannot create one with a single message across unreliable machines. The first phase collects promises without changing the outcome, so anything can still be undone. The second phase is the decision, and it depends on one durable write, which is something a single machine can do atomically. The rest is bookkeeping to make sure that everyone who promised eventually learns the result.
mistakes: People often think two-phase commit and two-phase locking are related. In fact they are different things with a similar name. Two-phase locking is a concurrency-control method about when locks are taken and released on a database. Two-phase commit is an atomic-commit protocol across machines. A system can use either, both, or neither.
People often think 2PC gives consensus and is as fault tolerant as Paxos or Raft. In fact 2PC tolerates failures of participants (they abort) but not of the coordinator at the wrong moment, where it blocks. It needs all participants to answer, whereas consensus needs only a majority. Paxos Commit and Spanner make the coordinator and participants fault tolerant by replicating them with consensus, which is why modern systems use 2PC on top of consensus, not instead of it.
People often think a participant that voted yes can time out and abort. In fact it cannot, because the coordinator may have decided commit and told others. Aborting alone would break atomicity. Only a participant that has not yet voted can abort alone.
People often think three-phase commit solves blocking in practice. In fact 3PC is non-blocking only if the network has bounded delays and failures are crashes that can be detected correctly. With a network partition it can lead to inconsistency. Real systems choose consensus-replicated coordinators instead.
friction: Latency and lock holding are the first cost. Locks are held for two round trips and two forced writes. In a single region this is about a millisecond or two, and across continents it is hundreds of milliseconds, so hot rows become bottlenecks. This is why sharding schemes work hard to keep transactions on one shard, and why some systems (Calvin, Fauna) order transactions first to avoid 2PC.
Availability is the second. The transaction needs every participant, so the probability of success falls with participants: if each of 5 shards is available 99.9% of the time, the transaction commits successfully only about 99.5% of the time. And blocking: a stuck in-doubt transaction holds locks, and in PostgreSQL an abandoned prepared transaction (PREPARE TRANSACTION) holds locks and also prevents vacuum from cleaning old rows, which can bloat tables; this is why max_prepared_transactions is 0 by default and why orphaned prepared transactions are a known operational hazard.
Heterogeneous systems add trouble. XA depends on every resource manager honouring its prepare promise and on a transaction manager with a reliable log. When it fails, operators must resolve in-doubt transactions by hand, with heuristic commit or rollback that can leave the participants in disagreement. Many teams therefore avoid XA across services and use sagas, outbox patterns and idempotent consumers, which give eventual consistency instead of atomicity. Finally, 2PC provides atomicity but not isolation by itself: it needs a concurrency control scheme (locking or snapshot timestamps) to ensure serializability across participants.
practice: Avoid distributed transactions when you can: choose shard keys so that most transactions touch one shard, since a single-shard commit costs one log force and no coordination. When you must coordinate, prefer a system where the coordinator is replicated (Spanner, CockroachDB, TiDB, YugabyteDB) over one where it is a single process, and keep the number of participants small, since cost and failure probability grow with each.
If you use XA or PostgreSQL prepared transactions, run the transaction manager with a highly available log, set transaction timeouts, and monitor for in-doubt transactions: in PostgreSQL, look at pg_prepared_xacts for old entries, and alert on any older than a few minutes. Document the procedure for resolving them, and never use a heuristic outcome without checking every participant.
Keep transactions short. Do reads and slow work before the prepare phase, and keep the window between prepare and decision as small as possible. Make participants' prepare work cheap: validate constraints early, so a NO vote is rare.
For cross-service workflows (an order service, a payment service, an inventory service), use sagas with compensations, or a transactional outbox with idempotent consumers, and accept eventual consistency. Use 2PC only inside a system that is designed for it. In Kafka, use transactions with a stable transactional.id for atomic writes to several partitions and offset commits; it is 2PC with the broker's transaction coordinator, and consumers read with isolation.level=read_committed.
tradeoffs: Choose 2PC (over a replicated coordinator) when you need true atomic, serializable updates across shards, the data is mostly in one region, and a lock hold time of one to a few milliseconds is acceptable. You give up throughput on hot rows and some availability, since all participants must respond.
Choose a single-shard design or co-located data when most transactions can be placed together. You give up flexible queries across entities and gain commit latency of a single log write.
Choose sagas with compensations when the process spans services or crosses organisations, takes seconds to days, and users can tolerate intermediate states. You give up isolation and atomicity: other readers can see partial results, and you must design and test the compensating action for every step. Choose 2PC when a half-done state is unacceptable, as with money moving between ledgers of the same system.
Choose deterministic ordering (Calvin-style) when transactions' read and write sets are known in advance and you can afford a global sequencing layer; you give up interactive transactions. Choose Paxos Commit or a Raft-replicated coordinator when coordinator crash must not block the system; you pay an extra consensus round per decision. Choose presumed abort when most transactions commit and you want fewer log writes on aborts; choose presumed commit when aborts are rare and you want to save acknowledgements for commits.

@@ idempotence
value: An operation is idempotent if doing it twice has the same effect as doing it once. "Set the status to shipped" is idempotent. "Add 100 rupees to the balance" is not: run twice, it adds 200. This small property is what makes it safe to retry in a distributed system. When a client sends a request and gets no answer, it cannot know whether the request was lost, or was executed and the reply was lost. If the operation is idempotent, the client can simply send it again. If it is not, a retry may charge a card twice, ship two parcels or write a duplicate record.
The deeper reason is a hard limit. Over an unreliable network, a sender can choose at-most-once delivery (send once, never retry, accept loss) or at-least-once delivery (retry until acknowledged, accept duplicates). It cannot get exactly-once delivery, because the acknowledgement itself can be lost (the Two Generals problem). What systems call "exactly-once" is at-least-once delivery plus idempotent processing: duplicates arrive, but their effect is applied once. So idempotence is the piece that turns retries from a hazard into a tool.
It shows up everywhere data moves. Kafka producers attach a producer id and sequence numbers so brokers drop duplicate writes. Payment APIs such as Stripe accept an Idempotency-Key header. Spark and Databricks jobs are written so that a re-run overwrites a partition, or merges by key, instead of appending twice. Workflow engines retry tasks. Event-sourced consumers replay events. The concept stands on relations and functions (L4): an idempotent function f satisfies f(f(x)) = f(x), as projections, maximum, set union and "set to constant" do. That algebraic fact tells you which operations are naturally safe, and how to reshape the unsafe ones.
terms: Idempotent operation — an operation whose repeated application leaves the system in the same state as one application: f(f(x)) = f(x).
Safe operation — an operation with no side effects at all, such as a read; every safe operation is idempotent, but not the other way round.
At-least-once delivery — the sender retries until it sees an acknowledgement, so the receiver may see duplicates.
Exactly-once effect — each logical operation changes the state once, achieved by at-least-once delivery plus deduplication or idempotent writes.
Idempotency key — a unique id chosen by the client for one logical operation and sent with every retry of it.
Deduplication — recognising a repeated request or message, usually by a stored id, and skipping its effect.
Upsert — a write that inserts a row if its key is absent and updates it if present; repeating it gives the same row.
Sequence number — a counter attached to each message from a sender, letting the receiver see duplicates and gaps.
history: The word is old mathematics. Benjamin Peirce introduced "idempotent" in 1870 for algebraic elements with x² = x, from Latin idem (same) and potens (power). In computing the idea entered through operating systems and networks. Sun's Network File System (1984) was designed with idempotent, stateless operations such as "write these bytes at this offset", so that a client could retry after a server crash without harm. Birrell and Nelson's 1984 paper on remote procedure calls discussed what a call means after failures: a call that is retried until it succeeds may run more than once, so it is safe only for idempotent procedures.
The HTTP specification made the property part of the web. RFC 2616 (1999) defined GET, HEAD, PUT, DELETE, OPTIONS and TRACE as idempotent, and POST as not. The current RFC 9110 (2022) keeps this, and explains that browsers and proxies may automatically retry idempotent requests. For POST, the missing guarantee led to application-level keys. Payment APIs, most visibly Stripe's (the 2017 post by Brandur Leach is the standard reference), adopted a client-chosen Idempotency-Key header. An IETF draft proposes a standard header based on these practices.
Streaming systems made the idea central to data engineering. Kafka added the idempotent producer and transactions in version 0.11 (2017, KIP-98), then made idempotence the default producer setting in version 3.0 (2021). Spark Structured Streaming combined replayable sources, checkpoints and idempotent sinks to give end-to-end exactly-once results. Delta Lake added transactional writes and MERGE, and later idempotent-write options for streaming batches. The Lambda architecture (Nathan Marz, early 2010s) and the later Kappa and medallion designs all depend on the ability to reprocess data without double-counting.
how: Start with the algebra from the lower layer. A function f is idempotent when applying it twice equals applying it once. Some building blocks are naturally idempotent: assignment (x := 5), set union and insertion into a set, maximum (x := max(x, v)), delete-by-key (the row is gone after the first delete), and writing a file at a given path and offset. Others are not: increment, append to a list, insert without a key, send an email. The design task is to turn the second kind into the first.
Technique 1: replace relative updates with absolute ones. Instead of "balance = balance + 100", send "set the balance to 600 if it is now 500" (a conditional write with a version number or compare-and-set). A retry then fails the condition harmlessly. This is optimistic concurrency, and it also protects against lost updates from other writers.
Technique 2: give writes a natural key and use upsert. If each event has a unique id (an order id, a device id plus a timestamp, a content hash), write it with INSERT … ON CONFLICT DO NOTHING, or MERGE INTO in Delta Lake. A second write of the same key changes nothing. The key must be stable across retries, so derive it from the data or assign it before the first attempt, never at the time of each attempt. In batch jobs, the same idea is partition overwrite: a job for 2026-10-25 writes the whole partition for that date, so re-running replaces it, not duplicates it. Databricks' COPY INTO is idempotent in this way, since it skips files it has already loaded.
Technique 3: idempotency keys. The client generates a unique key (a random UUID) for each logical operation and sends it with every attempt. The server stores the key, together with a hash of the request and the result, in a table with a unique constraint on the key. On a new request it inserts the key row first, in state "started". If the insert fails because the key exists, it knows this is a repeat. If the earlier attempt completed, it returns the stored response. If the earlier attempt is still running, it returns a conflict or waits. If the stored request hash differs from the new one, the client misused the key, and the server rejects it. Stripe works this way: it saves the status code and body of the first request that began execution, returns it for retries with the same key (including for errors), allows keys up to 255 characters, and may prune them after 24 hours.
The most important detail is atomicity. The key record and the effect must be committed together, in one local database transaction. If the server charges a card and then crashes before recording the key, a retry will charge again. If it records the key first and crashes before charging, the retry sees "started" and must be able to resume. Brandur Leach's advice is to break the work into steps with recovery points: after each step the progress is stored, so a retry continues from the last completed step. For effects outside your database (calling a payment provider, sending an email), pass the same idempotency key to that service, or write the intent to an outbox table in the same transaction, and have a relay deliver it at-least-once to an idempotent consumer.
Technique 4: sequence numbers. When a single sender produces an ordered stream, number the messages. The receiver remembers the highest sequence number it has accepted per sender, and ignores anything at or below it. Kafka's idempotent producer works like this. The broker gives each producer a producer id (PID). For each topic partition, the producer numbers its batches 0, 1, 2 and so on. The broker remembers the latest sequence numbers (the last five batches per producer and partition, which is why max.in.flight.requests.per.connection must be 5 or less) and responds to a duplicate batch with success without appending it. A gap raises an out-of-order error. The scope is one producer session: after a restart the PID changes, so a Kafka transactional.id is used to carry identity across restarts and to fence older instances.
Technique 5: idempotent consumers. A consumer that reads from a log at least once (it may re-read after a crash, because offsets are committed after processing) must make its processing idempotent. The usual ways are an upsert keyed by event id, a processed-ids table updated in the same transaction as the effect, or writing results and offsets together in one transaction so that either both or neither persist. Spark Structured Streaming does the last for you when the sink supports it. For Delta Lake in a foreachBatch function, the options txnAppId and txnVersion let Delta skip a micro-batch it has already written.
Finally, remember what the definition covers. Idempotence concerns the effect on state, not the response. The second DELETE of a resource may return 404 while the first returned 204, and it is still idempotent. Also, idempotence is about repetition of the same operation. Interleavings of different operations still need concurrency control.

Step 2: call the payment provider, passing K as its own idempotency key. Step 3: UPDATE the row to state 'done' with the response body, and write the order's paid status, in the same transaction. Step 4: commit and return 200.
Now the network drops the 200. The client waits, times out and retries with the same K. The server's insert fails on the unique key, so it reads the row: state 'done'. It returns the stored response immediately, without calling the provider. One charge of 500, two requests. If a second request with the same K arrives while the first is still running, the row is in state 'started', and the server answers 409 (conflict) or waits for a few hundred milliseconds. If the server crashed after step 2 but before step 3, the retry finds 'started' with no result. It calls the provider again with the same K, and the provider, which also deduplicates, returns its saved result without a second charge.
Storage cost: at 1,000 requests per second, one day is 86.4 million requests. At about 100 bytes per record (key, hash, state, a short response), that is 8.6 GB per day. With 24-hour retention this is easy to hold. At 100,000 requests per second it would be 860 GB per day, so you would partition the table by time and drop old partitions, or hold keys in a store with expiry. The retention must be longer than the longest time a client may keep retrying, or a very late retry will run again as a new request.
Now Kafka. A producer has PID 7 and writes to partition 0. It sends batch 5 (sequence 5). The broker appends it and replies, but the reply is lost. The producer times out and resends batch 5. The broker expects sequence 6, sees 5, recognises that it already has it, and replies success without appending. Without this, the log would contain the records twice. If instead batch 7 arrived while the broker expects 6, a batch has been lost or reordered, and the broker returns an error so that the producer can react.
A batch job: a Spark job computes daily revenue and writes it with append mode. A retry after a failure at 90% appends the whole result again, and the revenue doubles. Change the write to overwrite the partition for that date (replaceWhere in Delta), or MERGE by (date, product). Run it three times and the table looks the same.
intuition: Pressing the lift button twice does not call two lifts.
The design is natural because the sender has no way to learn the truth. After a timeout there are only two possibilities, and they look the same: the request never arrived, or it arrived and the reply was lost. The only strategy that is correct in both cases is to make the second possibility harmless. Idempotence moves the burden from the network, which cannot provide certainty, to the receiver, which can: it can remember what it has done, or define the operation so that remembering is not needed.
mistakes: People often think exactly-once delivery is possible if the system is good enough. In fact it is impossible over an unreliable network, because an acknowledgement can always be lost. Systems that advertise exactly-once provide exactly-once effects, by combining retries with deduplication or idempotent writes, within a defined scope such as one Kafka cluster, and not across external systems.
People often think idempotent means the response is always the same. In fact it concerns the state, not the reply. A repeated DELETE can return 404 the second time. A repeated charge with the same key should return the original response, which is a stronger design but not part of the definition.
People often think HTTP PUT and DELETE are safe to retry because the standard says they are idempotent. In fact the standard describes the intended semantics. A badly written PUT handler that appends to a list, or a DELETE that triggers a side effect each time, is not idempotent. Also, idempotent operations that interleave with other writers can still give surprising results: PUT x = 1, PUT x = 2, then a retried PUT x = 1 changes the final value.
People often think Kafka's idempotent producer gives end-to-end exactly-once. In fact it prevents duplicates from producer retries into one partition within a session. A consumer that processes the data and writes to a database still needs its own idempotence or a transactional read-process-write cycle. Kafka transactions and read_committed isolation cover read-process-write inside Kafka only.
People often think "check if exists, then insert" is idempotent. In fact two concurrent retries can both see "not exists" and both insert. The check and the write must be one atomic step, such as a unique constraint or a conditional write.
friction: Dedup state costs storage and must expire. Keep keys too long and the table grows without bound; keep them too short and a late retry runs twice. Keys also need a scope: per customer, per endpoint, per tenant. A global table becomes a hot spot and a cross-tenant leak risk.
Side effects outside your control are the hardest part. You can make your own database writes idempotent, but an email, an SMS, a webhook to a partner or a call to a payment provider without key support cannot be undone. The options are to pass the key through, to record the intent and make the external call at-least-once with the receiver deduplicating, or to accept rare duplicates and design for them. Atomicity between "the effect happened" and "I recorded it" is not possible across two systems without a protocol such as an outbox or two-phase commit, so there is always a small window.
Idempotence also interacts badly with time and ordering. A retried "set status = shipped" arriving after "set status = delivered" regresses the state. This is solved with versions or monotone state machines, where an update is applied only if it moves forward. Non-deterministic operations (generating a random id, reading the current time inside the operation) break idempotence on replay, because the retry produces a different result. Finally, retries by the client hide only one kind of duplicate; duplicates can also come from user double-clicks (new key each time), from upstream replays, or from two separate jobs, and each needs its own defence.
practice: Design every write path that may be retried with a defined identity for the logical operation. For APIs, require an idempotency key on every non-idempotent POST that moves money, creates orders or sends messages. Generate the key on the client before the first attempt, reuse it on retries, and store a hash of the request to detect misuse. Keep records at least as long as the client retry window plus a margin (Stripe uses 24 hours).
Write the key record and the effect in one transaction. Use a unique constraint, not an application-level check. Return the stored response for repeats. Handle the in-progress case explicitly. Propagate the key to downstream services that support it.
In data pipelines, make every job re-runnable. Write results by overwriting a partition keyed by the run's logical date, or by MERGE on a business key, never by blind append. Make each stage a deterministic function of its inputs and a run id. Use Structured Streaming with checkpoints and idempotent sinks, and use COPY INTO or Auto Loader for file ingestion, which track processed files. For foreachBatch writes to Delta, set txnAppId and txnVersion so a replayed micro-batch is skipped.
For consumers, commit offsets after processing and make processing idempotent. Test it: replay the last hour of events twice in a staging environment and compare the final state to a single run. Use fault injection (kill the process between the effect and the acknowledgement) to prove the claim. For Kafka producers, leave enable.idempotence on (it is the default in current versions), keep acks=all, and use transactional.id when you need atomic multi-partition writes.
tradeoffs: Choose natural idempotence (absolute writes, upserts by key, partition overwrite) whenever the operation allows it. It needs no extra state and is the simplest to reason about. You give up some flexibility: you must know the key or the target state before writing, and updates become "last write wins" unless guarded by versions.
Choose an idempotency-key table when the operation is inherently one-shot (charge, send, create) and the client can generate a key. You pay in storage, an extra write per request, and a retention policy. Choose sequence numbers per sender when one sender produces an ordered stream and the receiver can keep a small amount of state per sender, as Kafka does, which is cheaper than a per-message key.
Choose end-to-end exactly-once frameworks (Kafka transactions, Spark Structured Streaming with transactional sinks) when the whole pipeline lives inside systems that support them, and you accept lower throughput (commit markers, small batches) and added latency. Choose at-least-once with idempotent consumers when the pipeline crosses systems that do not share a transaction scope, which is more portable and often simpler to operate.
Choose a short key retention (hours) when clients retry quickly and storage is tight; choose longer (days) when retries come from queues or human re-submission. Choose to reject a reused key with a different payload rather than ignore it, since silent acceptance hides client bugs.
interview: Why is exactly-once delivery impossible and what do systems provide instead? || The sender cannot distinguish a lost request from a lost acknowledgement, so it must either retry (possible duplicates) or not (possible loss). Systems provide exactly-once effects: at-least-once delivery plus deduplication or idempotent writes, so each logical operation changes state once within a defined scope.
Design an idempotency-key mechanism for a payment API and handle concurrent duplicates. || Client sends a unique key. Server inserts a row (key, request hash, state=started) with a unique constraint as the first step of the transaction. A failed insert means a repeat: return the stored response if done, a conflict or wait if in progress, an error if the request hash differs. Store the result and the business effect in one transaction, pass the key downstream, and expire keys after a retention period.
How does Kafka's idempotent producer prevent duplicates and what are its limits? || The broker assigns a producer id; the producer numbers batches per partition; the broker keeps the latest sequence numbers (last five batches) and drops a batch it already has, acknowledging it. Limits: it covers one producer session and one partition's sequence; a restart gets a new id unless transactional.id is used; it says nothing about consumer-side effects.
Your Spark job failed at 90% and was re-run, and the table has double the rows for one day. What is the fix? || The job appended. Make the write idempotent: overwrite the partition for the run date (replaceWhere in Delta), or MERGE by the business key, or use txnAppId and txnVersion in streaming foreachBatch. Add a check that counts rows per date and alerts on unexpected growth.
A consumer processes a message, writes to a database, then crashes before committing the offset. What happens and how do you make it correct? || On restart it re-reads and re-processes the message, so the database write happens twice. Make the write an upsert keyed by the event id, or store the processed offset in the same transaction as the write and resume from it, so the repeat is skipped.
Is an HTTP PUT always idempotent? || By specification yes, because repeating the same PUT should leave the same resource state. A handler can violate this by appending or by triggering side effects. Also a delayed retried PUT can overwrite a newer update, so use versions or ETags (If-Match) to guard against that.
quiz: Which of these is idempotent: "balance += 100", "balance = 600", "append row"? || Only "balance = 600". Repeating it leaves the balance at 600. The other two change the state again each time.
Why does an idempotency key need to be generated before the first attempt? || The retry must carry the same identifier as the original attempt, so the server can recognise it as a repeat. A key created per attempt would look like a new operation each time.
Why must the idempotency record and the business effect be committed in one transaction? || If they commit separately, a crash between them leaves either an effect with no record (a retry repeats it) or a record with no effect (a retry skips it). One transaction makes them succeed or fail together.
A Kafka producer sends batch with sequence 9, the ack is lost, and it resends sequence 9. The broker expects 10. What does it do? || It recognises sequence 9 as a duplicate of a batch it already appended, acknowledges success, and does not append it again.
When would you choose at-least-once with idempotent consumers over Kafka transactions? || When the pipeline writes to systems outside Kafka (a database, a search index, an external API) where Kafka's transaction scope does not reach, or when you want simpler operations and portability and can make the sink an upsert.

@@ retries
value: A retry is the simplest fault-tolerance tool: if a call fails, call again. Many failures in a distributed system are brief: a packet is dropped, a server restarts, a leader changes, a queue is full for a moment. A retry turns most of these into a success the user never notices. If a call has 99% success and failures are independent, one retry lifts it to 99.99%. But a retry is also extra load on a service that is already having trouble, and it is "selfish": it spends the server's time to improve one client's chance. When many clients retry at once, a short problem can become a long outage.
Good retry design therefore has four parts. A timeout, so that a call cannot wait forever. Backoff, so that each new attempt waits longer than the last, giving the server time to recover. Jitter, so that clients do not all retry at the same instant. And a limit, in the number of attempts, the total time and the share of traffic that retries can add. Each part answers a specific failure: hanging calls, hammering a weak server, synchronised waves, and runaway amplification.
The concept stands on two lower concepts. Probability (L4) explains jitter: if N clients fail together and use the same backoff schedule, they stay synchronised and hit the server in waves; adding a random delay spreads the attempts evenly over time, and the expected load becomes smooth. Queueing theory and Little's law (L4) explain why retries are dangerous: a server near full utilisation has a queue that grows without bound, and extra arrivals from retries push it over the edge. Each failed call that is retried adds an arrival, and slow responses cause more timeouts, which cause more retries.
terms: Timeout — the longest time a caller waits for a reply before treating the call as failed.
Backoff — increasing the wait between attempts, usually doubling it each time (exponential backoff).
Jitter — random variation added to a delay so that clients do not act in lockstep.
Retry budget — a cap on retries as a share of normal traffic (for example 10%), or a token bucket that retries must draw from.
Retry storm (retry amplification) — a surge of retries that raises load on a struggling service and keeps it failing.
Thundering herd — many clients acting at the same moment, for example all retrying or all refreshing an expired cache entry.
Transient fault — a failure that disappears if you wait and try again, unlike a permanent one such as an invalid request.
Deadline — the absolute time by which the whole request, including all retries, must finish.
history: Backoff began in networking. The ALOHA network at the University of Hawaii (Abramson, 1970) let radios send whenever they had data; when two transmissions collided, both waited a random time and tried again. Metcalfe and Boggs' Ethernet (1976) refined this to binary exponential backoff: after the k-th collision, wait a random number of slot times chosen from 0 to 2^k − 1. TCP followed. Jacobson's 1988 paper "Congestion Avoidance and Control" added exponential backoff of the retransmission timer and showed that without it, a congested network collapses as everyone retransmits. These are the roots of the modern pattern: random delay to break symmetry, growing delay to reduce load.
In the cloud era the same ideas moved up to application calls. Netflix's Hystrix (2012) and the "Release It!" book (Nygard, 2007) popularised timeouts and fail-fast behaviour. Marc Brooker's 2015 AWS Architecture Blog post "Exponential Backoff And Jitter" measured the effect with simulation, compared full, equal and decorrelated jitter, and recommended jitter on every retry. Google's Site Reliability Engineering book (2016) described retry budgets and warned about retries amplified across layers. AWS added a token-bucket retry throttle to its SDKs in 2016, and its Builders' Library article on timeouts, retries and backoff with jitter explained the reasoning.
Research then named the failure mode. Bronson, Aghayev, Charapko and Zhu's "Metastable Failures in Distributed Systems" (HotOS 2021) described systems that stay in a failing state after the original trigger is gone, because a feedback loop such as retries sustains the overload. Service meshes (Envoy, Linkerd, Istio) moved retry policy into the proxy with limits and budgets, and gRPC added a retry policy with throttling in its specification.
how: A retry policy has a classifier and a schedule. The classifier decides whether to retry: retry on timeouts, connection resets, HTTP 503 and 429 (honouring a Retry-After header if present), and gRPC UNAVAILABLE; do not retry on client errors such as 400, 401 or 404, because the result will not change. Only retry operations that are safe to repeat: reads, naturally idempotent writes, or writes with an idempotency key. The neighbouring concept of idempotence is the condition that makes retrying legal.
The schedule decides when. Start with a timeout on every remote call. A timeout is part of the policy because a retry cannot begin until the previous attempt ends. Choose it from the downstream service's latency distribution: decide the false-timeout rate you accept (for example 0.1%) and use the matching percentile (p99.9) plus margin. Too low and healthy calls are cut off and retried, creating load. Too high and threads and connections stay occupied.
Backoff: the delay before attempt k (k = 1, 2, 3 …) is min(cap, base × 2^k). With base 100 ms and cap 20 s: 200 ms, 400 ms, 800 ms, and so on, up to 20 s. The growth means the total retry rate from a client falls geometrically, so a long outage does not receive a constant hammering.
Jitter: randomise the delay. Brooker's three variants: full jitter, sleep = random(0, min(cap, base × 2^k)); equal jitter, half fixed and half random; decorrelated jitter, sleep = min(cap, random(base, previous sleep × 3)). Full jitter is simple and works well. Why is it needed? Suppose 1,000 clients all fail at time 0 because the server restarted. With plain exponential backoff all 1,000 retry at 200 ms, then at 600 ms, then at 1,400 ms. Each wave is as big as the original burst, so the recovering server meets a spike every time. With full jitter each client draws a uniform delay in the window, so the same 1,000 attempts are spread across the window and each millisecond sees a small fraction. This is the probability fact from the lower layer: independent uniform random delays turn a spike into a flat rate.
Limits: cap the number of attempts (commonly 3, including the first), and cap the total time with a deadline. The deadline should be passed down the call chain, as in gRPC, so that a downstream service does not keep working on a request whose caller has already given up. A retry must also not start if there is too little time left to finish.
Budgets: even with backoff, a widespread failure can make every client retry, and total load becomes the normal rate times the number of attempts. A retry budget limits this. Google's SRE book describes a per-client budget: allow a retry only while retries are below about 10% of requests; AWS SDKs use a token bucket where each retry spends tokens (for example 5, more for timeouts), successes refund a little, and when the bucket is empty the client stops retrying and fails fast. The effect is that when the failure is rare, retries are free, and when the failure is widespread, they turn themselves off. Envoy and gRPC provide similar throttles.
Placement: retry at one layer. Suppose a request passes through 5 layers and each makes 3 attempts. If the lowest service fails permanently, the database sees 3⁵ = 243 calls for one user request. AWS recommends retrying at a single point in the stack, usually the layer closest to the user or the one with the most context, with lower layers failing fast. The trade-off is that retrying only at the top wastes the work done by earlier steps.
The queueing view explains why this all matters. For a server with service rate μ and arrival rate λ, utilisation is ρ = λ/μ, and the average time in system in the simplest model is 1 / (μ − λ). At 80% load the time is 5 times the service time; at 95% it is 20 times; at 100% the queue grows without limit. Little's law, L = λW, ties the number of requests in the system to arrival rate and time. If a brief slowdown makes some requests time out and retry, λ rises; higher λ raises W; higher W causes more timeouts. This positive feedback loop is a retry storm.
Breakers and retries work together. Retry briefly for transient errors. When errors persist, a circuit breaker should open and stop calls altogether, so that retries do not add load to a dependency that is clearly down.

example: A service has capacity μ = 1,000 requests per second and normal load λ = 800 per second (80% utilisation). A deploy causes 30% of calls to fail for a few seconds. Clients retry up to 3 attempts, immediately and without a budget. First retry wave: 30% of 800 = 240 extra requests per second. Second wave: 30% of 240 = 72 more. Total attempts: 800 + 240 + 72 ≈ 1,112 per second, which is above the capacity of 1,000. The queue grows, response times rise, requests begin to time out even where the server would have succeeded, and the failure fraction climbs. If it reaches 100%, every request is attempted 3 times: 800 × 3 = 2,400 per second, 2.4 times the capacity. The service is now drowning in its own retries, and removing the original bug does not help, because the load stays above capacity. This is the metastable state.
Now the same system with protections. Use full jitter with base 100 ms. Add a retry budget of 10%: clients may retry only while retries are less than 10% of requests. Extra load is capped at 80 requests per second, so total load is at most 880 per second, below capacity. Failed calls beyond the budget fail fast, the user sees errors for a few seconds, and the service recovers when the bug is fixed. A circuit breaker would do the same from another direction.
Backoff arithmetic. Base 100 ms, cap 20 s, full jitter. Attempt windows: 0-200 ms, 0-400 ms, 0-800 ms. The expected delay is half the window: 100, 200, 400 ms. Three attempts with a 1-second timeout each give a worst case near 3 + 0.6 = 3.6 seconds before giving up (three timeouts plus two backoff waits). If the user-facing deadline is 2 seconds, this policy cannot fit, so set attempts and timeouts from the deadline: for example a 400 ms timeout and 2 attempts.
Jitter check with numbers. A cache entry that 10,000 clients refresh every 60 seconds, all expiring at the same moment, produces a burst of 10,000 requests. Adding random jitter of ±10% to the TTL (54 to 66 seconds) spreads the refreshes across 12 seconds, about 830 per second, an order of magnitude gentler.
intuition: If the line is busy, wait a bit longer each time before calling again, and do not all call at the same second.
The design is natural because it combines two ideas from different fields. Exponential backoff is a feedback rule from control: if the system looks overloaded, reduce your rate, and reduce it faster the longer the trouble lasts. Jitter is a rule from probability: if many agents follow the same rule, break their symmetry with randomness. A retry budget adds a third: keep the total extra work bounded, so that helping one client never hurts all clients.
mistakes: People often think retries are free insurance. In fact each retry is extra load. When failures are rare, the extra load is tiny, and when failures are widespread, retries multiply the load exactly when the service can least take it. A retry must be designed together with a limit.
People often think exponential backoff alone is enough. In fact without jitter, clients that failed together retry together, so the waves stay synchronised. The delays grow, but each wave is still as large as the original burst.
People often think more layers with retries mean more reliability. In fact retries multiply across layers: 3 attempts at each of 3 layers is 27 calls. Retry at one layer and make others fail fast, or use budgets that are shared across the call chain.
People often think a longer timeout is safer. In fact a long timeout holds threads, sockets and memory for every slow call, so a slow dependency can exhaust the caller's resources, and the caller may time out upstream anyway, so the work is wasted. A timeout should be based on measured latency percentiles and the caller's deadline.
People often think retrying a failed write is safe. In fact a timeout does not mean the write failed; it may have succeeded and only the reply was lost. A retry without idempotence can duplicate the effect.
friction: Choosing parameters is difficult. There is no universal timeout or backoff base; the right values depend on the dependency's latency distribution, the user's deadline and the cost of a false timeout. Settings copied from another service are often wrong. Timeouts that look generous in tests fail after a deploy that adds TLS setup or a cold cache.
Retries hide problems. A service with 20% hidden retry rate looks healthy on its success dashboard while using 25% extra capacity, and when one more failure arrives the margin is gone. Measure and alert on retry rate and attempts per request, not only on final success. Retries also distort latency: the p99 of a call with retries includes timeouts and backoff, which may be several seconds.
Systems with metastable behaviour are the worst case. Once the system is in the overloaded state, the load that sustains it comes from retries and from queued work, so recovery needs an active action: shedding load, disabling retries, shrinking the client pool or restarting with empty queues. Budgets and breakers reduce the risk but cannot remove it. Deadline propagation and load shedding at the server (rejecting early when queues are long) are the matching defences on the other side.
Finally, retries interact with ordering and idempotence in subtle ways. A retried request that overtakes a newer request can overwrite newer data. Retrying on a different replica can read stale data. Retrying non-idempotent calls needs keys. And in a service mesh, retry settings in the proxy and in the application stack on top of each other, which is the multiplication problem again, hidden in configuration.
practice: Put a timeout on every network call, including database, cache and internal RPC calls; never use the default of "no timeout". Derive it from measured latency: look at the downstream p99.9 (or your accepted false-timeout rate), add margin, and make sure it is below the caller's deadline.
Use exponential backoff with full jitter as the default: sleep = random(0, min(cap, base × 2^attempt)), with base 50 to 100 ms, cap in seconds, 2 or 3 attempts in total for interactive requests. For background jobs and queue consumers allow more attempts and longer caps, with dead-letter queues for poison messages. Honour Retry-After and 429 from servers.
Add a retry budget (10% of requests is the common starting point) or a token bucket, and retry at one layer only. Pass a deadline down the chain, and do not retry if the remaining time is shorter than a typical call. Retry only idempotent operations, or attach idempotency keys. Combine with a circuit breaker for dependencies that fail for long periods.
Use the platform's tested implementations: the AWS SDK's standard retry mode, gRPC's retry policy and throttling, Envoy's retry budgets, resilience4j or Polly in application code, Spark's task retry settings and Databricks job retries. Jitter periodic work too: stagger cron jobs, cache expiry, health checks and lease renewals.
Measure: attempts per request, retry ratio, timeout rate by dependency, and queue depth. Test with fault injection (add latency, drop 30% of calls) and watch whether load on the dependency rises by more than your budget. Have a runbook step to disable retries quickly.
tradeoffs: Choose few attempts (2 or 3) with short timeouts for interactive requests, where the user's deadline is a second or two and a fast failure is better than a slow success. You give up some success rate on longer outages. Choose many attempts with long, capped backoff for background work where latency does not matter, such as batch ingestion, accepting that the work completes minutes later.
Choose full jitter when many clients may fail together; choose decorrelated jitter when you want the lowest total contention in simulation and do not mind a less predictable schedule; avoid plain exponential backoff without jitter except in a single-client tool. Choose retries at the edge of the system, close to the user, when you want one clear policy; choose retries inside the service that owns the dependency when it can judge errors better, and accept that the upper layers must then fail fast.
Choose a retry budget or token bucket rather than a circuit breaker when you want simple local behaviour that is easy to test (AWS makes this argument, noting that breakers add modes that are hard to exercise). Choose a circuit breaker as well when a dependency is down for long periods and you want to avoid even budgeted calls and to return a fallback quickly.
Choose hedged requests (send a second copy after the p95 latency and take the first reply) when tail latency matters more than load and the call is idempotent and cheap; you spend perhaps 5% extra load for a lower p99. Do not hedge calls to a service that is already overloaded.
interview: What goes wrong with exponential backoff without jitter? || Clients that failed together keep the same schedule, so they retry together in waves of equal size. The server meets a spike at every retry time. Jitter randomises each delay so the same attempts spread over the window and arrive at a smooth rate.
Explain retry amplification across layers and how to prevent it. || With r attempts at each of k layers, the bottom service can see r^k calls per user request (3 attempts at 5 layers gives 243). Prevent it by retrying at one layer, having lower layers fail fast, using retry budgets, propagating deadlines, and measuring attempts per request.
A dependency slows down, retries rise, and the system stays down even after the dependency is fixed. What happened and what do you do? || A metastable failure: the load from retries and queued requests keeps utilisation above capacity. Break the loop by shedding load, disabling or throttling retries, shrinking client concurrency, or restarting with empty queues. Prevent it with budgets, breakers, server-side load shedding and deadlines.
How would you choose a timeout for a call to a service whose latency is 20 ms at p50 and 200 ms at p99.9? || Decide the false-timeout rate you can accept. For 0.1%, set the timeout near the p99.9 of 200 ms with some margin, say 250 ms, and ensure it fits the caller's deadline. Check that p99.9 is not close to p50 plus noise. Revisit after deploys, since TLS handshakes and cold caches shift the tail.
Which operations can be retried safely, and how do you make others safe? || Reads and naturally idempotent writes can be retried. For others, a timeout may hide a success, so use idempotency keys or conditional writes so that a repeat has no extra effect, and do not retry on errors that are deterministic, such as validation failures.
Why does a token-bucket retry throttle work better than a fixed retry count during a widespread failure? || A fixed count lets every client retry every request, tripling the load. A token bucket spends tokens on retries and refills slowly on successes, so when failures are widespread the bucket empties and clients fail fast, capping total extra load; when failures are rare the bucket is full and retries are free.
quiz: What are the four ingredients of a safe retry policy? || A timeout on each call, exponential backoff between attempts, random jitter on the delays, and a limit (attempts, deadline and a retry budget).

@@ circuitbreaker
value: Timeouts and circuit breakers stop one slow or failing dependency from taking down the services that call it. A timeout limits how long a caller waits for one call. A circuit breaker watches many calls, and when too many have failed, it opens: for a while it rejects calls immediately, without even trying the dependency. The caller gets a fast error (or a fallback answer) in microseconds instead of a slow one after seconds, and the struggling dependency gets quiet time to recover.
The danger they address is cascading failure. Imagine service A calls service B, and B becomes slow, not dead. Each call from A now holds a thread, a connection and memory for seconds. A has a fixed pool of, say, 200 threads. Once all of them are waiting for B, A cannot serve any request, even those that never need B, and A looks dead to its own callers. Their pools fill next. A slowdown in one small service spreads upward through the call graph until the whole system is down. Slow failures are worse than fast ones, because a fast error frees the thread immediately.
The pattern was named by Michael Nygard in "Release It!" and has three companions: bulkheads (separate resource pools per dependency, so one cannot consume everything), load shedding (a server refuses excess work early so that the work it accepts is done well), and fail-fast behaviour in general. It stands on two lower concepts. Control theory and feedback (L4) says what a breaker is: a feedback controller that measures an error rate and switches the system between two modes, with a delay (hysteresis) to prevent rapid flapping. Failure detection (L2) supplies the signal: the breaker is a passive failure detector that uses the outcomes and timeouts of real calls as its evidence, where heartbeats would use probes.
terms: Timeout — the longest a caller waits for one call before giving up on it.
Circuit breaker — a wrapper around calls to a dependency with three states (closed, open, half-open) that stops calls when the failure rate is high.
Closed — the normal state: calls pass through and results are counted.
Open — the tripped state: calls are rejected immediately, for a cool-down period.
Half-open — the probing state after the cool-down: a few trial calls are allowed to test whether the dependency has recovered.
Bulkhead — isolation of resources (thread pools, connection pools, semaphores) per dependency, so that one failing dependency cannot use them all.
Load shedding — a server deliberately rejecting some requests (with 429 or 503) when overloaded, to keep serving the rest well.
Fallback — a degraded answer returned when the real call is not possible: cached data, a default, or a reduced feature.
history: The ideas came from hard experience with enterprise systems. Michael Nygard, an operations-minded engineer, collected failure stories in "Release It!" (2007) and described stability patterns: Timeouts, Circuit Breaker, Bulkheads, Fail Fast and Steady State. The name comes from the electrical device that cuts the current when it exceeds a limit to protect the wiring. Martin Fowler's 2014 article on the pattern brought it to a wider audience.
Netflix turned it into infrastructure. Its API gateway called dozens of backend services, and a single slow one could freeze the gateway. Netflix built Hystrix (open-sourced in 2012), which wrapped every dependency call in a command with a timeout, a per-dependency thread pool (the bulkhead), a circuit breaker and a fallback, and showed the state in a live dashboard. By default it opened the circuit when at least 20 requests in a 10-second window had been seen and 50% of them failed, and it retried after 5 seconds. Hystrix entered maintenance mode in late 2018, and Netflix pointed to adaptive concurrency limits and to Resilience4j, a lighter library with the same ideas, as the future.
The pattern then moved into the infrastructure layer. Envoy, the proxy behind many service meshes, implemented "circuit breaking" as limits on connections, pending requests and concurrent requests per upstream cluster, and added outlier detection, which ejects an endpoint from the load-balancing pool after consecutive errors. From 2019, Amazon's Builders' Library (Yanacek, on load shedding; Brooker, on timeouts and retries) stressed the server-side counterpart: reject early, keep queues short, and design for static stability. Today breakers, bulkheads and load shedding appear together in most resilience guides.
how: Begin with the timeout, because everything else relies on it. Without a timeout, a call to a hung dependency never returns, and no breaker can count a failure that never completes. Each call gets a time limit based on the dependency's measured latency (p99.9 plus margin) and the caller's own deadline. A timeout bounds the damage per call, but not the total: if 1,000 calls per second each wait 1 second, 1,000 threads are held.
Little's law shows the size of the problem. The number of calls in flight is L = λ × W, arrival rate times time in system. With a pool of 200 threads and a dependency that normally answers in 50 ms, the pool supports up to 200 / 0.05 = 4,000 calls per second. If the dependency slows to 5 seconds, the same pool supports only 200 / 5 = 40 per second. At 1,000 calls per second, all 200 threads are busy within 0.2 seconds, and everything else on that service stops. Shortening the timeout to 500 ms still allows 1,000 × 0.5 = 500 calls in flight, more than the pool holds. Only refusing calls outright solves it. That is the breaker's job.
The breaker is a small state machine around the call. In the closed state each call goes through, and its outcome (success, error, or too slow) is recorded in a sliding window, which holds either the last N calls (count-based) or the last T seconds (time-based). The failure rate is computed over this window. If the number of calls in the window is at least a minimum (so that two failures out of three calls in a quiet period do not trip it) and the failure rate exceeds a threshold, the breaker opens. Resilience4j's defaults are a count-based window of 100 calls, a minimum of 100 calls, a failure threshold of 50%, and a slow-call rule that treats calls over a duration threshold as failures.
In the open state every call fails at once with an exception (or returns a fallback). No request reaches the dependency, so it sees no load from this caller. A timer runs for the wait duration (60 seconds by default in Resilience4j, 5 seconds in Hystrix). Then the breaker becomes half-open and lets a limited number of trial calls through (10 by default in Resilience4j; Hystrix allowed a single call). If the trial calls succeed, the breaker closes and clears its window. If too many fail, it opens again, often with a longer wait. The half-open state is the feedback-control part: a small, cautious step in the direction of recovery, which is measured before committing.
Which outcomes count? Count timeouts, connection failures and server errors (5xx). Do not count client errors (4xx such as invalid input), because they say nothing about the health of the dependency. Slow responses count when they are slower than a threshold, since slowness is what exhausts resources.
Bulkheads limit how much a single dependency can take. Give each dependency its own thread pool or semaphore with a fixed size (Hystrix's default was 10 threads per dependency). If B is slow, only B's pool fills; calls to C and D continue. Combined with a breaker, B's pool is also released quickly. In a service mesh or load balancer the equivalent is a per-cluster limit on concurrent requests, as in Envoy. Isolation costs some efficiency: reserved capacity sits idle when its dependency is idle.
Outlier detection works per endpoint instead of per service. A proxy counts consecutive errors from each upstream host (Envoy ejects a host after 5 consecutive 5xx responses by default), removes it from the pool for a base time (30 seconds, growing with repeated ejections) and caps the share of hosts that can be ejected (10% by default) so that a systemic problem does not empty the pool. This is a breaker on an instance: one bad pod is avoided, while the others serve.
Load shedding is the server-side partner. When queue length or latency exceeds a limit, the server rejects new work quickly with 503 or 429, instead of accepting it and answering all requests late. Priorities help: drop background traffic before user traffic. Rejecting costs microseconds, and serving a request that will time out costs the full work and delivers nothing. Clients should treat these responses as signals to back off, not to retry harder.
Fallbacks give a useful answer when the breaker is open: serve cached data, a default list, a previous result, or hide the feature. A fallback must itself be reliable and cheap; a fallback that calls another remote service just moves the problem. Design so that the system works in degraded form: "static stability" means the data plane keeps working when the control plane is down.

example: A web service calls a pricing service at 100 requests per second, with a pool of 200 threads, a timeout of 1 second and a breaker with a window of 20 calls, a failure threshold of 50%, a 30-second open time and 5 trial calls in half-open state. Normally pricing answers in 40 ms, so about 100 × 0.04 = 4 threads are busy.
At time 0 pricing starts to hang. Every call now runs for the full 1 second timeout. By t = 1 s, 100 calls are in flight, so 100 threads are busy, half the pool, and the first timeouts begin to complete. The breaker's window of 20 calls fills with failures by about t = 1.2 s, a rate of 100%, above 50%, so it opens then, with about 120 threads busy at that moment. From then on, calls fail in microseconds with a fallback (the last known price from a cache). Busy threads drop from 100 back to about 4, because nothing waits any more. Without the breaker, the thread count would stay near 100 for as long as pricing hung, and any rise in traffic above 200 requests per second would exhaust the pool and take down unrelated endpoints too.
At t = 31 s the breaker becomes half-open and lets 5 calls through. Suppose pricing has recovered: 5 successes close the breaker, and traffic returns to normal. Suppose it has not: 3 of the 5 time out, the breaker reopens for another 30 seconds, and the cost of the test was 5 calls instead of 3,000. During the outage the pricing service saw almost no load from this caller, which gave it a chance to restart.
Numbers for the trade. During the 30-second open period, the service served about 3,000 requests with a cached price instead of 3,000 slow errors. If the cached price is accurate 95% of the time, 150 users saw a stale price, and 2,850 saw a correct one, against 3,000 failures. That is the value of the fallback. If no fallback exists, the same 3,000 users get an immediate error, which is still better than waiting a second for the error, and the service stays healthy for the other endpoints.
A tuning example. If the threshold is 50% with a window of 100 calls, one noisy second with 60 failures in a window of 100 trips the breaker even if the next second is clean. Raising the minimum number of calls and using a time-based window of 10 seconds smooths this; lowering the open time to 5 seconds recovers sooner but tests the dependency more often.
intuition: An electrical breaker trips when the current is too high, to protect the house; you reset it after the fault is fixed, not before.
The design is natural because failing fast is a kind of kindness. A caller that keeps trying a broken dependency wastes its own resources and adds load to a service that needs rest. A breaker makes the caller notice what the data says: when most recent calls have failed, the next one probably will too. Opening gives the dependency time, closing carefully with a small test avoids restarting the flood. It is the same feedback logic as a thermostat with hysteresis, applied to error rates.
mistakes: People often think a timeout alone protects the caller. In fact a timeout bounds each call but not the number of concurrent calls. With high traffic and a 1-second timeout, many threads can still be held at once. You need a breaker or bulkhead to cap total damage.
People often think the breaker protects the dependency from failing. In fact it protects the caller from the dependency's failure, and it gives the dependency relief as a side effect. Server-side load shedding and rate limits protect the server directly.
People often think all errors should count towards opening the breaker. In fact only errors that indicate a health problem should count: timeouts, connection failures and 5xx responses. Counting validation errors or 404s lets one user's bad input open the circuit for everyone.
People often think a breaker needs a long time window to be accurate. In fact a window that is too long reacts slowly, and one that is too short is noisy with low traffic. The minimum call count matters as much as the threshold: with 2 calls in the window, one failure is already 50%.
People often think half-open means the dependency is healthy. In fact it is a test. If every client's breaker closes at the same moment and sends full traffic, a recovering service can be flooded again. Use a limited number of trial calls and jitter in the open time.
friction: Thresholds are hard to tune. Too sensitive and the breaker opens on a blip and rejects good calls, which is a self-inflicted outage. Too lenient and it does nothing until the pool is already full. Good settings depend on traffic volume, which changes between peak and night, so a fixed count that works at peak may never fill at night.
Breakers are modal: the system behaves differently when open, with fallbacks and error paths that run rarely and are therefore less tested. The Amazon Builders' Library argues for this reason that simple retry token buckets and server-side load shedding are easier to test and reason about than client breakers. Breakers in many clients can also flap together: all open at once, all probe at once, all close and re-flood. Because each client decides independently, the dependency sees a pulsing load unless jitter and limited trial calls are used.
Fallbacks can mislead users or break correctness. Stale prices, empty recommendation lists and "unknown" statuses must be acceptable for the product, and some operations (payments, writes) have no safe fallback. A breaker can also hide a real problem: dashboards show fast errors and low latency while a feature is simply off. Alert on breaker state changes and on the rate of fallbacks.
Finally, breakers work best on synchronous calls with clear success or failure. Asynchronous queues, streaming and batch jobs need other tools: backpressure, consumer lag limits, pause and resume. And a breaker per client instance sees only that client's slice of traffic; a low-volume caller may take a long time to learn what a high-volume caller learned at once. Sharing health information across instances (as a mesh does) improves this but adds complexity.
practice: Order the defences. First, a timeout on every remote call, set from measured latency and under the caller's deadline. Second, a limit on concurrency per dependency (bulkhead or semaphore) sized from Little's law: concurrency = peak rate × normal latency × safety factor. Third, a breaker with a minimum call count, a failure rate threshold of around 50%, a slow-call rule, and a wait time of tens of seconds with jitter. Fourth, a fallback only where one is safe.
Use a maintained library or the mesh: Resilience4j for JVM services, Polly for .NET, Envoy or Istio outlier detection and connection limits at the proxy layer. Keep one policy per dependency in one place, so that timeouts, retries and breakers agree: retries should be fewer than the breaker's window can absorb, and the breaker should see each attempt.
Add server-side protection as well. Limit the queue length, reject early when over a latency target, and prioritise user-facing traffic over background work. Clients that receive 429 or 503 should back off. In Databricks and Spark jobs, apply the same ideas to calls to external services from tasks: timeouts, limited parallelism per executor and a failure threshold that fails the job early, instead of letting thousands of tasks wait on a dead API.
Test it. Inject latency and errors in staging (for instance 5 seconds delay on a dependency) and confirm that the breaker opens, the fallback works, unrelated endpoints stay healthy and recovery happens without a flood. Export metrics: breaker state, calls by outcome, rejected calls, slow-call rate, and fallback count. Alert when a breaker has been open for longer than expected, and review settings after major traffic changes.
tradeoffs: Choose a breaker when a dependency can fail slowly or for minutes, calls are synchronous and each holds a scarce resource, and a fast error or fallback is acceptable. You give up a small number of good calls during the open period and take on tuning and extra code paths.
Choose only timeouts plus a retry budget when failures are short and you want the simplest behaviour that is easy to test. Add breakers when you have seen outages that lasted longer than a retry budget can handle. Choose bulkheads when dependencies differ in importance and speed, so a minor dependency cannot starve a critical path; you pay with idle reserved capacity, typically 10 to 30% less efficient use of threads.
Choose breakers in the client library when your fleet is small and homogeneous, so teams can tune per call and use rich fallbacks. Choose breakers and outlier detection in the mesh proxy when you have many languages and teams and want one consistent policy, accepting less visibility into the application's fallback options. Choose server-side load shedding as well in any case, because it protects the server from all clients, including those without breakers.
Choose a short open time (seconds) when the dependency usually recovers quickly and the cost of missing calls is high; choose a long one (a minute or more) when recovery is slow, as with restarts or failovers, and probing too often would delay it. Choose a count-based window for steady traffic, and a time-based window with a minimum call count for traffic that varies.

@@ fencing
value: A fencing token is a number that increases every time a lock, lease or leadership is granted, and that the protected resource uses to refuse stale writers. It solves a problem that timeouts cannot solve. A client takes a lock with a 30-second lease and starts work. The client pauses for 40 seconds (a long garbage-collection pause, a frozen virtual machine, a slow disk), the lease expires, and a second client takes the lock and writes. Then the first client wakes up. It does not know that time has passed, and it still believes it holds the lock. If it writes now, it overwrites or corrupts the second client's work. No check inside the first client can prevent this, because the client is exactly the part that is confused.
The fix is to move the check to the place that cannot be confused: the resource itself. Each time the lock service grants the lock, it also returns a token, a number larger than any it gave before. The client sends the token with every write. The storage system remembers the highest token it has seen and rejects any write that carries a lower one. When the first client wakes up and writes with token 33, the storage has already seen 34 from the second client and answers "rejected". The old holder is fenced off, like a zombie cut from the system.
This is the pattern behind several things you already use. Raft terms, Paxos ballot numbers, ZooKeeper epochs, Kafka's controller epoch, leader epoch and producer epoch, HDFS's NameNode epochs in the journal nodes, and Elasticsearch's primary terms are all fencing tokens under different names. The concept stands on two lower concepts. Leader election and leases (L2) supply the grants: each new lease or leader term arrives with a higher number, and the election service can order grants because it is built on consensus. Hardware clocks and timers (L3) explain why a lease alone is not enough: lease expiry is measured by local clocks, which drift, jump when corrected and stop when a process is paused, so time alone cannot guarantee that an old holder has stopped.
terms: Lease — a lock that expires after a fixed time unless renewed, so a crashed holder cannot block others forever.
Fencing token — a number returned with each grant of a lock or lease; larger tokens were granted later.
Epoch (term, generation) — the same idea under another name: a counter that identifies one period of leadership or ownership.
Zombie (stale holder) — a node that still believes it holds a lock or leadership after it has lost it.
Split brain — two nodes acting as leader at the same time.
Linearizable — behaving as if all operations happened one at a time in a real-time order; the lock service must be this so that tokens are strictly increasing.
Conditional write (compare-and-set) — a write that succeeds only if a stated condition on the current state holds, checked atomically.
STONITH — "shoot the other node in the head": cutting power to a suspected node before taking over, a hardware form of fencing.
history: The word "fencing" comes from high-availability clusters of the 1990s. When a standby node takes over from a primary that may only be unreachable, the cluster software must be sure the old node can no longer touch the shared disk. It does this by fencing: cutting its power (STONITH), cutting its network port, or using SCSI persistent reservations that make the disk reject the old node's commands. This protects the shared resource by acting on the node.
Google's Chubby paper (Burrows, OSDI 2006) described the token version. A Chubby lock holder can ask for a sequencer, a string naming the lock and its generation number, and attach it to requests to other services, which check with Chubby or compare against the latest they know. For services that do not understand sequencers, Chubby offers a lock-delay: after a holder's session is lost, the lock stays unavailable for a period (up to one minute), giving stale operations time to drain. Burrows noted that lock-delay is imperfect protection but better than nothing.
The term "fencing token" in its current sense was popularised by Martin Kleppmann in his 2016 essay "How to do distributed locking" and in "Designing Data-Intensive Applications" (2017). The essay argued that a lock service must return a token, that the storage must check it, and that a lock without this check is unsafe whatever the timing assumptions, because a process can be paused at any instruction. He applied this to Redis's Redlock algorithm (Sanfilippo, 2014), which has no way to generate tokens, and set off a public debate. Salvatore Sanfilippo replied that the timing assumptions behind Redlock are reasonable in practice.
Meanwhile, production systems had already built the same mechanism into their protocols. Raft (Ongaro and Ousterhout, 2014) rejects any message with an older term. Kafka added a leader epoch in version 0.11 (KIP-101, 2017) and producer epochs with transactional.id fencing (KIP-98). HDFS High Availability uses an epoch number from the quorum journal manager so that an old NameNode cannot write the edit log. Modern object stores and databases supply the needed primitive, atomic conditional writes: DynamoDB conditional expressions, etcd transactions on revisions and, since 2024, S3 conditional writes.
how: Start with the failure being prevented. A client C1 acquires a lock from a lock service and gets a lease valid for 30 seconds. It reads some data, plans a write and then stops for 40 seconds. Typical causes are a stop-the-world garbage collection, the operating system swapping memory out, the virtual machine being paused for live migration, a CPU starved by a noisy neighbour, or a packet delayed in the network on the way to storage. When C1 resumes, no code in C1 can tell that 40 seconds have passed: the check "is my lease still valid?" and the write that follows are two separate steps, and the pause can happen between them. Even if the check passes, the lease can expire a microsecond later, before the write reaches storage.
This is the key point. Mutual exclusion based on timing needs an upper bound on pauses and delays, and real systems have none. So the protection must be placed at the resource, where the write is actually applied, and it must not depend on any timing assumption.
The mechanism has three parts. First, the lock service issues tokens. Each successful grant returns a number that is strictly larger than all previous ones. This requires the lock service to be linearizable, so there is a single agreed order of grants. In practice this is a consensus-based system: ZooKeeper's zxid or the version of a znode, etcd's revision, a counter incremented through Raft, or a Chubby generation number. The leader election concept provides exactly this: each election increases a term. A single-node lock server with a counter would also work for the order, but it is a single point of failure.
Second, the client attaches the token to every request that touches the protected resource. The write carries (data, token).
Third, the resource checks the token atomically with the write. It keeps the highest token seen so far, max_token, stored next to the data. On a request it does, as one atomic step: if token < max_token, reject; otherwise set max_token = token and apply the write. If tokens are equal, the write comes from the current holder and is accepted; if larger, a new holder has arrived and the old one is fenced. The check and the write must be atomic (a database transaction, a conditional write, a single-threaded state machine), otherwise two requests can interleave. The max_token must be durable, or a restart of the storage would forget it and accept stale writers again.
With this in place the scenario ends differently. C1 holds token 33. It pauses; the lease expires; C2 acquires the lock with token 34 and writes; the storage records max_token = 34. C1 wakes up and writes with 33; the storage rejects it. C1 learns its error (it can then re-acquire the lock or step down). Correctness no longer depends on how long the pause was.
Note what has changed. The system no longer promises that two clients never think they hold the lock at once. It promises that at most one of them can have an effect on the resource. This is a weaker claim about the clients and a stronger claim about the data, and it is the one that matters.
The same pattern is used in every replicated system with leaders. In Raft, a leader has a term. Every message carries the sender's term. A server that sees a higher term in a message updates its own term and, if it was leader, steps down. A server that sees a lower term rejects the message and replies with its own term. So a deposed leader that wakes up after a partition cannot commit entries: followers reject its append requests, and its stale term is the fencing token. In Kafka, when the controller elects a new leader for a partition, it increments the leader epoch. Followers reject fetch and replication requests from the old leader with a fenced-epoch error. When a producer with a transactional.id restarts, it asks for a new producer epoch, and the broker rejects the old instance with ProducerFencedException. In HDFS HA, each new active NameNode obtains a new epoch from the journal nodes; they reject writes from any NameNode with a lower epoch.
Tokens also combine with leases rather than replace them. The lease still has a job: it lets the system make progress after a real crash, because the lock becomes available again without a human. The token is what keeps this safe when the old holder was not really dead. Together: leases give liveness, tokens give safety.
When the resource cannot check tokens (it is a third-party API, an email gateway or a legacy system), there are weaker options: make the operation idempotent so a duplicate does no harm, use the resource's own conditional-write feature as a token (for example a version number or ETag with If-Match), or route all access through a single gatekeeper process that implements the check.

  without the check: C1's late write overwrites C2's data

  rule at storage (atomic with the write):
    if token < max_token: reject
    else: max_token = token; apply write
example: Two workers share a job that rewrites a configuration file in an object store. The lock service is etcd, and each lock acquisition returns the key's revision as the token. Worker A acquires the lock and gets revision 33. Its lease is 30 seconds. A starts to read the file, then a 40-second JVM garbage-collection pause hits it. At t = 30 s the lease expires. Worker B acquires the lock and gets revision 34. B writes the new file at t = 35 s, sending token 34. The storage layer (a small service in front of the object store) stores the file together with the number 34.
At t = 40 s, A wakes up. It does not know it lost the lock, and it sends its write with token 33. The storage compares 33 with its stored 34. Since 33 < 34, it rejects the request with an error. A sees the error, re-reads the lock state, finds it no longer holds the lock, and stops. The file contains B's version, as it should. Without the check, the A write would have landed after B's and replaced it with an older computation.
Now see the cost of a missing atomic check. Suppose the storage first reads max_token, then compares, then writes in separate steps. A's write and B's write arrive within the same millisecond. Both read max_token = 33 (from A's earlier request), both pass the comparison and both write; the last one wins, which may be A. The check and update of max_token and the data write must be one atomic operation, such as a conditional put or a transaction.
A second example, in Kafka. A partition's leader L1 has leader epoch 5. A network partition cuts L1 off from the controller for 20 seconds. The controller elects follower L2 as leader and raises the epoch to 6. Producers move to L2. L1 is still running, does not know, and for a short time accepts writes from a client that can still reach it. When the partition heals, the followers receive replication or fetch requests tagged epoch 5 from L1, compare with their current epoch 6 and reject them. L1 discovers the newer epoch, truncates its log to the last point that agrees with epoch 6, and becomes a follower. Records accepted by L1 during the partition with fewer than the required acknowledgements (acks=all with min.insync.replicas) were never confirmed to producers, so nothing acknowledged is lost.
Finally, a size check: a 64-bit token incremented once per second would last about 585 billion years, so token overflow is never the concern. What matters is that tokens are issued by a single linearizable source, so that "larger" always means "later".
intuition: Each new manager gets a higher badge number, and the warehouse accepts orders only from the highest badge number it has ever seen.
The design is natural because it replaces a question nobody can answer ("am I still the owner right now?") with a question the storage can answer exactly ("is this the newest owner I know of?"). Time is unreliable for the client, but order is reliable for the storage: it only needs to compare two integers. Once the ordering is in the data path, delays, pauses and clock errors cannot break safety, they can only cause rejected requests.
mistakes: People often think a lease with a short timeout is enough to make a lock safe. In fact a lease limits how long a crashed holder blocks others, but it cannot stop a live-but-paused holder from acting after expiry, because the pause can fall between the lease check and the write. Safety needs the check at the resource.
People often think the client can protect itself by checking the lease just before writing. In fact the pause can happen right after the check. The time between "I checked" and "my write was applied" includes network delay and operating-system scheduling, neither of which has a bound.
People often think Redis-based locks or ZooKeeper locks give exclusion by themselves. In fact a lock service tells a client "you hold it now" and nothing more. ZooKeeper's strength is that it offers a linearizable order (zxid, znode version) that can serve as a token; the application still has to pass it to storage and have storage check it. A lock without fencing is fine for efficiency (avoiding duplicate work) but not for correctness.
People often think fencing needs synchronised clocks. In fact tokens are logical counters. The only requirement is a single source that hands them out in a linear order. This is a strength: the protocol works however wrong the clocks are.
People often think fencing is only for distributed locks. In fact the same idea is inside leader election, replication and exclusive file or topic ownership: Raft terms, Kafka epochs, HDFS journal epochs. Whenever one party must stop another from acting on old authority, a monotonically increasing number is the standard tool.
friction: The storage must cooperate. It has to accept a token, store the maximum durably, and check it atomically with the write. Many systems cannot: a plain S3 PUT without conditions, an email service, a payment gateway, a legacy database without conditional updates. In those cases you cannot fence, and must rely on idempotence or accept a risk. Teams often discover this after designing a lock with a nice service and no way to enforce it.
Tokens must be comparable across all resources that the lock protects. If a workflow writes to two stores, both must see tokens from the same source, and each keeps its own maximum. A write that succeeds on one store and is rejected on the other leaves partial work, so fencing gives safety against stale writers but does not make a multi-store operation atomic. For that you need a transaction or compensation.
The lock service itself needs consensus, so it has a cost and availability limit: a majority of its nodes must be up, and each grant is a round trip to a quorum (milliseconds in a data centre, more across regions). Every request carries an extra 8-byte token, and every storage node keeps per-resource state. Rejected stale writes need handling: the client must treat rejection as a signal to stop and to re-acquire the lock rather than retry blindly, or the retries will keep failing. Also, work done by the zombie before the rejected write, such as reading, computing and calling external systems, is wasted, and side effects outside the fenced resource are not undone.
Finally, fencing works only if a new holder is granted only after the old holder's authority is superseded in the lock service. If the lock service is split-brained or restored from an old backup, tokens could repeat or go back, and all guarantees fail. Lock service state therefore needs strong durability and careful operations.
practice: Decide first whether the lock is for efficiency or for correctness. If a duplicate run only wastes work (a cache refresh, a report), a simple lease from a single Redis node may be fine. If an overlap could corrupt data, charge money or send two commands to a machine, use a consensus-backed service (ZooKeeper, etcd, Consul) and fencing tokens.
Get tokens from the lock service: the ZooKeeper znode version or zxid, the etcd key's mod_revision or lease revision, or a counter in a Raft-replicated store. Pass the token on every call to the protected resource. Where you control the resource, enforce the check inside the same atomic operation as the write: a database row with a token column and an UPDATE … WHERE token <= :t; a DynamoDB conditional write with a condition on the stored token; an object-store put with a precondition such as If-Match on an ETag or a version; a state machine that applies commands in log order and drops stale ones.
Use the same idea for ownership in your own protocols. Give each new leader, writer or job run a generation number; store it with the output; and reject older generations. In data pipelines this is how you stop a slow, restarted task from overwriting the output of its replacement: write outputs under a run or attempt id and commit by an atomic rename or a put-if-absent, as Delta Lake's commit protocol does with numbered log files, where creating the next version file only succeeds for one writer.
Keep timeouts as a liveness tool, not a safety tool. Use monotonic clocks for lease timers. Make clients check their lease before long operations and handle "rejected: stale token" by stopping work. Reduce pauses where you can (garbage collector tuning), but never rely on that. Test it: inject a long pause between lock acquisition and write (SIGSTOP the process) and confirm the stale write is rejected. If the resource cannot check tokens, write down that the design is not safe against pauses, and add idempotence or a gatekeeper.
tradeoffs: Choose fencing tokens when a stale writer could corrupt data, the lock service is consensus-based, and the resource can check a number atomically with the write. You pay a token in each request and some state in the resource, and you gain safety that does not depend on clocks or pause lengths.
Choose a plain lease (no tokens) for efficiency-only locks, where an overlap wastes work but harms nothing: avoiding duplicate cache rebuilds, picking a cron host. It is cheaper, simpler and needs only a single Redis or database row; you give up a safety guarantee.
Choose resource-level fencing, such as conditional writes with a version, when the store supports it. This often needs no separate lock service for single-key operations: compare-and-set alone gives mutual exclusion on that key. Choose an external lock service with tokens when the critical section spans several operations or several resources, accepting that each resource must still check the token.
Choose node-level fencing (STONITH, power or network isolation, SCSI reservations) when the resource is a shared disk or device that cannot check tokens, and you control the hardware or hypervisor. You pay with specialised infrastructure, and the shutdown action itself can fail. Choose idempotent operations plus a short lease when neither token checks nor node fencing is possible, accepting that rare overlaps cause duplicate effects.
Choose a long lease (tens of seconds) when pauses are frequent and failover is rare and expensive; choose a short lease (a few seconds) for fast failover, accepting more false expiries. With fencing in place, a false expiry costs a rejected write and a retry, not corrupted data, which is a reason to shorten leases safely.
interview: Why can't a lease with a timeout guarantee mutual exclusion? || The holder can be paused (garbage collection, VM pause, scheduling delay) after checking its lease and before its write takes effect. Network delay adds more uncontrolled time. No timing bound exists, so a stale holder can act after the lease expired. The resource must reject stale holders.
Describe the fencing token mechanism and where the check must happen. || The lock service returns a strictly increasing number on each grant. The client sends it with every write. The resource stores the maximum token seen and rejects lower ones, in one atomic step with the write. The check must be at the resource, since only it sees the write at the point of effect.
What properties must the token source have? || A single linearizable source, so that grants are totally ordered and larger always means later, and durable state so that numbers never repeat or go back after a failure. A consensus-based service such as ZooKeeper or etcd, or a Raft counter, provides this.
How does Raft's term act as a fencing token? || Each election increases the term. Every RPC carries the sender's term. A node receiving a higher term updates and steps down; a node receiving a lower term rejects the message. A deposed leader's appends are therefore refused by followers, so it cannot commit.
Your workflow writes to S3 and sends an email under a lock. What can fencing protect? || The conditional S3 write can be fenced with a version or precondition. The email cannot be fenced because the mail service cannot check tokens; use an idempotency key or a deduplicating outbox. Fencing protects only resources that enforce the token.
What would you do if storage does not support conditional writes? || Put a gatekeeper service in front that serialises writes and checks tokens, or make operations idempotent, or use node-level fencing, or change storage. If none is possible, document that the lock is for efficiency only.
quiz: What does a fencing token prevent? || A client that wrongly believes it still holds a lock (after a pause or partition) from writing over the work of the current holder, because storage rejects its older token.
Why is the check done at the storage and not in the client? || The client is the part that can be paused or confused; a check in the client and the write that follows are separate steps with unbounded delay between them. Storage sees the write at the moment it takes effect.
Client A has token 33, client B has token 34. Storage has seen 34. What happens to A's write with token 33 and to B's next write with 34? || A's write is rejected because 33 < 34. B's write is accepted because 34 is not less than the stored maximum.
Which of these is a fencing token in practice: Raft term, Kafka leader epoch, wall-clock timestamp? || Raft term and Kafka leader epoch are. A wall-clock timestamp is not reliable because clocks can differ or jump, so it cannot guarantee order.
When is a plain lease without tokens acceptable? || When the lock only avoids duplicate work and an occasional overlap does no harm, such as refreshing a cache or choosing which host runs a report. For correctness-critical exclusion, use tokens.
