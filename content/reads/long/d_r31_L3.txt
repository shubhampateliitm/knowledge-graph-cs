@@ scheduling
value: A CPU scheduler answers one question many times per second on every core: which thread runs next, and for how long? A machine usually has far more runnable threads than cores. A busy server may have 500 threads that want to run and 16 cores. Someone must choose, and the choice decides who waits. If the choice is bad, an interactive request waits behind a long batch job, one tenant starves another, or a core sits idle while another core has a long queue.
Every program you run depends on this decision. A web server thread that wakes up when a request arrives needs a core within microseconds, not milliseconds, or the tail latency (the slowest 1% of requests) grows. A Spark executor with 8 task threads wants all of them running at once. A container with a CPU limit of "2 cores" must be stopped from using more, without being stopped so often that it stutters. All of this is scheduling policy, and it explains many surprises: latency spikes at 70% CPU, containers that are "throttled" while the node looks idle, and "noisy neighbours" on shared machines.
The scheduler stands on two lower ideas. Queueing theory (L4) says what happens to waiting time as load grows: a run queue is a queue, and delay does not grow in a straight line, it explodes as utilization approaches 100%. Optimization (L4) frames the design: fairness, latency and throughput pull in different directions, and the scheduler is an online heuristic that trades them off with limited information, in nanoseconds, without knowing the future. In turn, processes, threads, condition variables, thread-per-core designs and even continuous batching in LLM serving depend on a scheduler to turn "runnable" into "running".
terms: Runnable — a thread that is ready to execute and only waits for a core; threads blocked on I/O or locks are not runnable.
Run queue — the per-core list (in Linux a tree or list inside the scheduler) of runnable threads waiting for that core.
Time slice — the amount of CPU time a thread may use before the scheduler may switch to another thread.
Preemption — the kernel stops a running thread, usually on a timer interrupt or when a more urgent thread wakes, and runs another one.
Virtual runtime (vruntime) — in CFS, the CPU time a thread has used, scaled by its weight; the scheduler tries to keep these numbers equal.
Weight / nice value — a number that says how large a share of CPU a thread should get; nice 0 has weight 1024, and each nice step changes the share by about 25%.
Lag and virtual deadline — in EEVDF, lag is how much CPU a thread is owed; a virtual deadline is the virtual time by which its next slice should finish.
CPU affinity — a restriction or preference that keeps a thread on certain cores so its cache data stays warm.
Quota (CFS bandwidth control) — a limit such as "50 ms of CPU per 100 ms period" for a cgroup, enforced by stopping the group when the budget is used.
history: The first time-sharing systems in the early 1960s, such as CTSS at MIT, had to share one expensive CPU among many terminals. Fernando Corbató's group introduced multilevel feedback queues: new or interactive jobs run at high priority with short slices, and jobs that use their whole slice move down to lower priority. Unix kept the idea with priorities that decay with CPU use. The goal was a simple one: make interactive users feel that the machine is theirs while long jobs still make progress.
The theory of fair sharing came from networking. Weighted fair queueing (Demers, Keshav and Shenker, 1989) divided link bandwidth among flows in proportion to weights using a virtual clock. Waldspurger's lottery scheduling (1994) gave each process tickets and drew a random winner. Stoica and Abdel-Wahab described EEVDF, "Earliest Eligible Virtual Deadline First", in 1995 as a proportional-share algorithm with a bound on how far any task can fall behind its fair share.
Linux used a simple O(n) scheduler through the 2.4 series, which scanned every runnable task. Ingo Molnar's O(1) scheduler (2003, Linux 2.6) used priority arrays and fixed cost per decision, but its heuristics for detecting "interactive" tasks were fragile. In 2007 Molnar replaced it with the Completely Fair Scheduler (CFS, Linux 2.6.23), which kept tasks in a red-black tree ordered by virtual runtime and dropped most heuristics. Group scheduling arrived in 2.6.24, and CFS bandwidth control (Paul Turner at Google) in Linux 3.2, which is the origin of container CPU limits.
In 2023 Peter Zijlstra's EEVDF replaced the CFS pick logic in Linux 6.6. The reason was that CFS had grown many special cases to give latency-sensitive tasks a fair chance, and EEVDF expresses latency directly as a per-task slice length. In 2024, Linux 6.12 merged sched_ext (mainly from Tejun Heo and engineers at Meta and Google), which lets a scheduling policy be loaded as an eBPF program, so teams can try new policies without rebuilding the kernel.
how: Each core has its own run queue. A core takes a scheduling decision at a few moments: when the running thread blocks (waits for I/O or a lock), when it exits, when a timer tick shows that it has run long enough, and when another thread wakes up and may deserve to run sooner. At each of these points the scheduler picks one thread from that core's queue and the context switch (the neighbouring L3 concept) installs it. The policy question is how to pick.
Linux has several scheduling classes with strict order. Deadline (SCHED_DEADLINE) threads come first, then real-time threads (SCHED_FIFO and SCHED_RR, priority 1 to 99), then ordinary threads (SCHED_OTHER, also called the fair class), then idle. A real-time thread that stays runnable can starve all normal threads on its core, which is why the kernel by default limits real-time CPU use to 95% of each second (sched_rt_runtime_us). Almost all application threads are in the fair class, so the rest of this section is about it.
The fair class is a form of weighted fair queueing applied to CPU time. Each thread has a weight derived from its nice value (-20 to +19). Nice 0 has weight 1024; each step of nice changes the weight by a factor of about 1.25, so nice 5 has weight 335 and nice -5 has weight 3121. A thread that is supposed to get twice the CPU of another thread has twice the weight. In CFS the scheduler tracked vruntime: every time a thread ran for delta_exec nanoseconds, its vruntime grew by delta_exec × 1024 / weight. A heavy thread's vruntime grows slowly, so it is chosen more often. The scheduler always picked the thread with the smallest vruntime (the leftmost node of the red-black tree, found in O(1) from a cached pointer, with O(log n) insert and removal). If all threads have equal vruntime, they all received exactly their fair share.
EEVDF keeps this accounting but changes the choice. For each thread it tracks lag, the difference between the CPU time the thread should have received and what it did receive. A thread with \( \text{lag} \ge 0 \) is eligible: the system owes it time. Among eligible threads, EEVDF picks the one with the earliest virtual deadline, which is its virtual start time plus its requested slice divided by its weight. A thread that asks for a short slice gets an early deadline and is scheduled soon, but it runs only briefly each time. A thread with a long slice is scheduled less often but runs longer, which helps throughput and cache use. Since Linux 6.12, a program can set this slice with sched_setattr(), so a latency-sensitive thread can ask for a short one without taking more total CPU. The default base slice is a few milliseconds at most.
Waiting costs depend on load, and here queueing theory matters. In the simplest model (random arrivals, one core, random service times; the M/M/1 queue), the mean time a job spends in the system is \( 1 / (\mu - \lambda) \), where \( \mu \) is the service rate and \( \lambda \) the arrival rate. If a request needs 1 ms of CPU and the core is 50% busy, the mean time is 2 ms. At 90% it is 10 ms, and at 99% it is 100 ms. Little's law (\( L = \lambda \times W \)) says the same thing from the other side: the average number of waiting tasks equals arrival rate times mean wait. This is why a CPU at "70% average" can still produce a bad tail: bursts push utilization to 100% for short periods, and the queue builds up. Schedulers cannot remove this effect; they can only choose who waits.
Multicore adds the problem of placement. Each core has its own queue, so the kernel must balance load by moving threads between cores, without destroying cache locality. Linux balances periodically (every few milliseconds, with longer intervals for larger groups of cores), and also when a core goes idle (it tries to "pull" work). Wake-up placement tries to put a woken thread on the core where it ran before, or on a core that shares a cache with the waker. The scheduler follows the machine's topology: hyperthread siblings, cores sharing an L3 cache, NUMA nodes (memory is closer to some cores than others), and on phones big and little cores. Migrating a thread across a NUMA node means its memory is now remote, so such moves are made reluctantly.
Containers are controlled with cgroups (the L3 concept nscgroups). The cpu.weight setting (cpu.shares in cgroup v1) gives a group a proportional share only when cores are contended; unused CPU is available to others. The cpu.max setting (quota and period, for example "200000 100000") is a hard cap: the group can use 200 ms of CPU time per 100 ms period, summed over all of its threads on all cores. When the budget is exhausted, all threads of the group are stopped until the next period. A multi-threaded service with a limit of 2 CPUs and 16 threads can spend its whole budget in 12.5 ms of wall time, then sleep for 87.5 ms. That is the throttling that appears as latency spikes while average CPU looks low.

example: Take the CFS accounting first, with three threads on one core: A and B at nice 0 (weight 1024 each) and C at nice 5 (weight 335). The total weight is 2383. The fair shares are A = 1024/2383 = 43%, B = 43%, and C = 335/2383 = 14%. Let all three run for a 10 ms period in proportion: A and B get about 4.3 ms each and C gets 1.4 ms. Check the vruntime: A's vruntime grows by 4.3 × 1024/1024 = 4.3 ms, and C's grows by 1.4 × 1024/335 = 4.3 ms. All three vruntimes grew by the same amount, so the scheduler sees them as equal. This is the whole idea: a lighter thread's clock runs faster, so it falls behind sooner and waits.
Now the EEVDF choice, simplified, with two threads of equal weight. Thread A requests a 3 ms slice and thread B requests a 1 ms slice. Measure virtual time in milliseconds of CPU. At the start, both have lag 0 and are eligible. A's virtual deadline is 0 + 3 = 3, and B's is 0 + 1 = 1. The earliest deadline is B's, so B runs first, for 1 ms. Now B has used more than the average, so its lag is negative (about −0.5 ms) and B is not eligible. Only A is eligible, so A runs. After A has run 1 ms, both have used 1 ms and lag is zero again. B is eligible and its new request has deadline 1 + 1 = 2, earlier than A's deadline of 3. At the next scheduling check B runs again for 1 ms. Over these 3 ms, A and B received 1.5 ms each on average and will converge to 50% each. The difference between them is latency. When B wakes up from sleep, it can run within about one slice, because its deadline is early. A, with its 3 ms slice, waits longer to be scheduled but is interrupted less. Under plain CFS, achieving this needed special wake-up bonuses; in EEVDF it follows from the slice request.
Now throttling, with numbers. A service runs in a container with cpu.max = "100000 100000", which means a 1 CPU limit (100 ms of CPU per 100 ms period). The service has 4 busy threads on a 4-core node. All four run at once, so they use 4 ms of CPU per 1 ms of wall time. After 25 ms of wall time the quota of 100 ms is used up. For the remaining 75 ms of the period, all four threads are stopped. Average CPU for the whole period is exactly 1 core, so the dashboard shows 100% of the limit, yet any request that arrives during the frozen 75 ms waits up to 75 ms. If the same service had a 3 ms request on a thread that was running, its latency would be 3 ms most of the time, and up to 78 ms when it hits the stop. Raising the limit to 4 CPUs, or removing the limit and using only a weight, removes the stall.
intuition: A fair queue at a single counter, where every customer is served in turn, but customers with bigger tickets are served more often and customers who ask for quick service are called first.
The design is natural because the scheduler has an impossible job done with a simple rule. The ideal is a processor that runs every thread at the same time, each at 1/n of the speed. No real core can do that, so the scheduler imitates it by giving threads short turns and keeping a running score of who is behind. Picking the one who is most behind (CFS) or the one whose turn is due first among those who are owed time (EEVDF) keeps the error small and the decision cheap. The score is just arithmetic, and the data structure is a sorted tree, so the cost per decision is tiny compared with the work that threads do.
mistakes: People often think that CPU at 60% average means the machine has plenty of room. In fact queueing delay depends on short bursts, not on the average. A queue with random arrivals has long waits when utilization is high, and bursts reach 100% for milliseconds even when the average is low. Latency-sensitive services are usually run well below 60%.
People often think that setting a CPU limit makes a container "use at most that much, smoothly". In fact the quota is a budget per period (100 ms by default) summed over all threads. A multi-threaded program can use its whole budget in a fraction of the period and then freeze. The effect is throttling, visible in cpu.stat as nr_throttled, and it hurts tail latency even when average use is far below the limit.
People often think that a higher thread priority makes a program faster. In fact priority changes only who waits when cores are contended. If a core is free, any thread runs at once. Raising priority does nothing for a program that is waiting on disk or on a lock, and a real-time priority can lock up a machine if the thread never blocks.
tradeoffs: Choose the fair class with default weights when your threads are similar and the machine is not overloaded; this is the right default for nearly all services and batch jobs. Choose real-time classes (SCHED_FIFO or SCHED_DEADLINE) only for work with hard deadlines, such as audio or control loops, and only with a bounded run time. You gain predictable latency, but a bug that loops forever can starve the whole core, and you must keep cores free for the rest of the system.
Choose cpu.weight (shares) for containers when you want to use idle capacity and only need fairness under contention. Choose cpu.max (quota) when you must cap a tenant for billing or isolation, accepting throttling stalls. A common compromise is to set requests (weights) for every pod and to set limits only for noisy or untrusted workloads, or to set limits high enough (for example, the number of cores that the process can really use in parallel) that throttling is rare.
Choose pinning (CPU affinity, cpuset, or thread-per-core designs) when cache locality and predictable latency matter more than using every core evenly, for example a packet-processing or in-memory store process. You give up the load balancer's ability to move work to idle cores, so a hot core cannot get help. Choose floating threads when load is uneven or unpredictable.
friction: Fairness and latency pull against each other. A strictly fair scheduler gives a woken thread no special treatment, but request-serving threads sleep and wake often and need to run immediately. CFS used heuristics, such as giving sleepers a credit, and these were hard to tune and sometimes unfair. EEVDF handles this better through slices, but it is still new, and some workloads regressed on 6.6 and needed fixes in later versions.
The scheduler works with little knowledge. It sees which threads are runnable, but not which request a thread serves, whether it holds a lock that others need, or whether it is about to wait for the network. Priority inversion (a low-priority thread holds a lock that a high-priority thread needs) is solved only for some locks (priority inheritance on real-time mutexes). User-space runtimes, such as the Go runtime, JVM and Erlang VM, run their own schedulers on top of kernel threads, so two schedulers decide independently and can disagree.
Multicore balancing is a heuristic that works at the scale of milliseconds. It can leave a core idle for a short time while another has a queue, and moving threads costs cache misses. On NUMA machines and with hyperthreading, the right placement depends on what the threads do, which the kernel does not know. On virtual machines there is a third layer, the hypervisor scheduler, so "steal time" appears: the guest believes it runs, but the host gave the core to another VM.
practice: Measure before tuning. Look at run-queue delay, not only utilization: the PSI files (/proc/pressure/cpu and cpu.pressure per cgroup) report the share of time that tasks waited for a CPU, and perf sched or eBPF tools such as runqlat show the distribution of waiting time. For containers, read cpu.stat: if nr_throttled and throttled_usec grow, the limit is hurting you.
Size thread pools for the work. For CPU-bound work use about one thread per core; for work that blocks on I/O use more, with a bound. More runnable threads than cores adds waiting and context switches and gives no extra work. In the JVM and Go, check that the runtime sees the container's real CPU count (container-aware settings; GOMAXPROCS is not automatically limited by cpu.max in older Go versions), or the runtime will create too many threads and then be throttled.
On Kubernetes, set CPU requests for every pod (they become weights) and use limits carefully. For latency-critical pods use the static CPU manager policy with integer CPU requests, which gives exclusive cores. Use nice for background work such as compaction or backups so that it yields to serving threads, and ionice for disk work. For databases and brokers with a hot-path thread, consider isolcpus or cpuset pinning and keep interrupts off those cores.
interview: A service shows p99 latency spikes every 100 ms although CPU is at 40% in the dashboard. What do you suspect and how do you confirm it? || CFS quota throttling in a container with a CPU limit. The period is 100 ms, so threads are frozen when the quota is used within the period. I check cpu.stat for nr_throttled and throttled_time, compare with request latency, then raise or remove the limit, or reduce thread count so the budget is not burned in bursts.
How does EEVDF differ from CFS, and why was the change made? || CFS picked the smallest vruntime and added heuristics for latency. EEVDF picks, among threads with non-negative lag, the one with the earliest virtual deadline, and the deadline depends on a per-thread slice. Latency becomes an explicit parameter and fairness has a bound, so fewer special cases are needed.
Why is a mean-utilization number a poor predictor of latency? || Queueing delay is nonlinear: in the M/M/1 model mean time grows as \( 1/(\mu - \lambda) \), so going from 50% to 90% load multiplies waiting by about 5 and 99% by about 50. Bursts push short periods to saturation, so tail latency is set by bursts, not averages.
How would you give a latency-critical thread on a shared machine consistent performance? || Reduce interference at every level: pin it to dedicated cores (cpuset, isolcpus), keep interrupts and other threads off them, avoid quota limits on its cgroup, use a short slice or a real-time class with bounded work, and place memory on the same NUMA node. Accept that those cores are not shared.
What goes wrong if a SCHED_FIFO thread spins in a loop? || It never blocks, and no normal thread on that core can run, so the core appears hung. Linux limits real-time CPU to 95% by default, and watchdogs may report stalls. Real-time threads must block or yield and have bounded work.
quiz: What does the scheduler look at to choose the next thread in CFS? || The smallest virtual runtime, which is CPU time used scaled by thread weight. The thread furthest behind its fair share runs next.
Why does a 1-CPU container limit cause freezes even if the average CPU is under 1 core? || The quota is a budget per 100 ms period summed over all threads. Several threads can spend the budget in a few milliseconds and then all are stopped until the next period.
Two nice-0 threads and one nice-5 thread (weight 335) share a core. What fraction of CPU does the nice-5 thread get? || 335 / (1024 + 1024 + 335) = 335 / 2383, about 14%.
A request needs 2 ms of CPU. At what core utilization will the average time in system reach 20 ms in an M/M/1 model? || Time = service time / (1 − ρ), so 20 = 2 / (1 − ρ), giving ρ = 0.9, or 90% utilization.
When would you choose pinned threads over letting the kernel scheduler move them? || When cache locality and tail latency matter more than balance, for example a packet or in-memory-store thread. You lose the ability to use idle cores when one core is hot, so load must be spread by design.

@@ ctxswitch
value: A context switch is the moment when a CPU core stops running one thread and starts running another. The kernel saves the first thread's registers, chooses the second, loads its registers, and, if the second belongs to a different process, switches the address space too. This is what lets 500 threads share 8 cores: each thread believes it has a processor of its own.
The visible cost is small, about 1 to 3 microseconds on a modern x86 server for the switch itself. The hidden cost is larger. The new thread finds the caches, the TLB (the cache of address translations) and the branch predictor full of the old thread's data. Until they refill, the new thread runs slowly. For a thread with a working set of a few hundred kilobytes, the refill can cost tens of microseconds. So a switch is not "free work done by the kernel", it is a loss of speed that is spread over the next thread's first milliseconds.
This cost shapes the design of high-performance servers. One thread per connection is simple, but 10,000 connections mean many switches. An event loop (L2) serves many connections from one thread and switches only when the kernel has nothing ready. Thread-per-core designs pin one thread to each core and avoid most switches. Batching processes many items per wake-up. All of them are ways to buy more useful work per switch. The memory hierarchy (L3) is the lower idea that explains the hidden cost: the caches, TLB and predictors that make a warm thread fast are the same structures that a switch makes cold.
terms: Context — the CPU state of a running thread: general registers, instruction pointer, stack pointer, flags, and floating-point/vector registers.
Voluntary switch — a thread gives up the CPU because it blocks, for example on I/O, a lock or sleep.
Involuntary switch — the kernel takes the CPU away, for example at the end of a time slice or for a more urgent thread.
Thread switch vs process switch — a thread switch inside one process keeps the same address space; a process switch also changes the page tables.
Address space switch — loading a new page-table root (register CR3 on x86), so that virtual addresses map to different memory.
TLB — the translation lookaside buffer, a small cache of recent virtual-to-physical address translations; a miss costs a page-table walk.
PCID — process-context identifier, a tag on TLB entries that lets entries of several address spaces coexist, so a switch need not flush the TLB.
Kernel stack — a small per-thread stack (16 KB on x86-64 Linux) used when the thread runs in the kernel; the context switch changes which one is in use.
history: Time-sharing in the 1960s (CTSS, Multics) needed a way to move one CPU among many users, so the idea of saving and restoring a process's registers is as old as multiprogramming. Early machines had few registers, so a switch was cheap; the cost grew as CPUs added registers, caches, vector units and deep pipelines.
In the 1990s, lmbench (Larry McVoy and Carl Staelin) made the cost measurable with a simple test: processes pass a token through pipes, and the time per hop is the switch cost. Operating-system research also pushed the thread idea in two directions. Kernel threads made switches cheap enough to use freely. User-level threads (green threads, later goroutines and async tasks) avoided the kernel entirely, at roughly 100 to 200 nanoseconds per switch.
The web made the cost matter. In the late 1990s, servers that used one process or thread per connection met the C10K problem (10,000 connections on one machine), and the answer was event-driven I/O (epoll, kqueue). In 2007, Li, Ding and Shen's paper "Quantifying the Cost of Context Switch" showed that the indirect cache cost can be as large as or larger than the direct cost, depending on the working set.
In January 2018, the Meltdown and Spectre attacks forced new defences. Kernel page-table isolation (KPTI) gave user mode and kernel mode separate page tables, so every entry to the kernel changes CR3. Linux uses PCID so this does not flush the TLB, but the work is still visible. Branch-predictor barriers on process switches added more cost. Since then, switch and system-call overhead has been a larger part of the bill than in 2015.
how: A switch begins with a reason to enter the kernel: a timer interrupt, a system call, a device interrupt, or a page fault. The hardware switches to kernel mode and the entry code saves the user registers on the thread's kernel stack. Now the kernel decides what to do. If the current thread has blocked (for example it called read() on an empty socket) it is marked sleeping and removed from the run queue. If its time slice ended, or a more urgent thread was woken, the kernel sets a need-reschedule flag. On the way back to user mode, the kernel calls the scheduler (the CPU scheduling concept) to choose the next thread.
The switch itself has two parts. First, if the next thread belongs to a different process, the kernel loads the new page-table root into CR3. Without PCID, this flushes the TLB, so every memory access starts with a miss. With PCID, entries are tagged and may survive. Threads of the same process skip this step, which is why thread switches are cheaper than process switches.
Second, the kernel switches the register state and stack. On x86-64 Linux the function __switch_to_asm pushes the callee-saved registers (rbx, rbp, r12 to r15) on the old thread's kernel stack, stores the stack pointer in the old thread's task structure, loads the stack pointer of the new thread, pops that thread's saved registers and executes a return. That return jumps to wherever the new thread was suspended, usually inside its own earlier call to schedule(). The trick is that the code looks like a normal function call that comes back much later. Only the registers the compiler does not already treat as free need saving. Then the kernel returns to user mode and restores the new thread's user registers.
Two more details explain when switches happen. The timer interrupt fires on every core at a fixed rate (commonly 250 or 1,000 times per second); at each tick the scheduler checks whether the running thread has used its slice. A wake-up is the second trigger: when a network packet completes, the interrupt handler marks a sleeping thread runnable and may set the need-reschedule flag on the core where that thread should run, which can mean sending an inter-processor interrupt to another core. Kernels built with full preemption can switch even inside kernel code, while server kernels often allow it only at defined points, trading a little latency for fewer switches.
Vector and floating-point state is large: AVX-512 state is about 2.5 KB. The kernel saves it with the XSAVE instruction and uses features that skip unused parts, so a thread that never touched vector registers costs little. Threads that use wide vector math make switches slower.
The hidden costs come from the memory hierarchy. The L1 cache (32 to 48 KB per core) and L2 cache (about 1 to 2 MB) hold the old thread's lines. The new thread misses on its first accesses: an L2 miss that hits L3 costs roughly 10 to 15 ns, and a miss that goes to DRAM costs roughly 80 to 100 ns. A thread with 256 KB of hot data has 4,096 cache lines of 64 bytes; at a mix of L3 and DRAM latencies of about 15 to 50 ns per line, the refill takes about 60 to 200 microseconds if the accesses cannot overlap. Out-of-order execution and prefetching hide part of it, so real numbers are lower, but the order of magnitude is much larger than the 1 to 3 microseconds of the direct switch. The branch predictor and the TLB add more penalty. With hyperthreading, two threads share one core's caches, so a switch on one sibling is partly absorbed by the other.
Counting helps reasoning. Linux reports switches per thread in /proc/<pid>/status as voluntary_ctxt_switches and nonvoluntary_ctxt_switches, and per system in the "cs" column of vmstat. A high voluntary rate means threads block a lot (I/O or locks). A high involuntary rate means more runnable threads than cores. These two numbers tell you different stories and need different fixes: reduce blocking, or reduce thread count.
User-level threads show the alternative. A goroutine or an async task switch saves only a few registers and the stack pointer, with no kernel entry, no CR3 change and no scheduler-class logic, so it costs on the order of 100 to 200 ns, and the working sets of tasks on one thread stay in the same cache. The price is that the runtime cannot preempt code that never yields (older Go versions), and a blocking system call blocks the underlying kernel thread unless the runtime moves other work elsewhere.

example: Measure the direct cost with the classic ping-pong test. Two threads are connected by two pipes. Thread A writes one byte to pipe 1 and reads pipe 2; thread B reads pipe 1 and writes pipe 2. Each round trip needs two context switches (A to B, B to A). Pin both threads to one core so that no cross-core wake-up is involved. If 1,000,000 round trips take 4 seconds, one round trip is 4 µs and one switch plus the pipe system calls costs about 2 µs. That number includes two system calls, so the pure switch is a little less. Without pinning, the threads land on different cores and each wake-up costs an inter-processor interrupt, which often makes it slower.
Now a server. A thread-per-request design handles 50,000 requests per second on one core. Each request blocks once on the network (the thread sleeps and wakes), so there are 2 switches per request, or 100,000 switches per second. At 2 µs direct cost that is 0.2 s of every second, or 20% of the core. Add the hidden cost. If each switch causes 20 µs of extra cache and TLB misses on the next thread, the loss is 100,000 × 22 µs = 2.2 s per second, which is more than the core has. The server saturates well before 50,000 requests per second, and the extra time is spent not in any function you can profile but spread as stalls across all of them. This is why measured throughput of thread-per-request servers falls as thread counts grow.
Compare an event loop. One thread calls epoll_wait and receives up to 64 ready sockets in one call. It handles all of them, which means its caches stay warm because the same code and data (the parser, the connection table) run again and again. At the same 50,000 requests per second, it makes perhaps 1,000 to 5,000 wake-ups per second, each followed by 10 to 60 requests. The switch cost per request falls by an order of magnitude. The price is that the code is structured as callbacks or async tasks, and a slow handler blocks all connections on that thread.
intuition: Switching between books: you lose your place, and for a while you read slowly until the story is back in your head.
The saving and loading of registers is the easy part, like marking a page with a bookmark. The real cost is that the reader has to rebuild context. A CPU is fast only because it keeps what it needs close: caches, translations, predictions. Those structures are trained by the thread that ran before and are useless, or even harmful, for the next thread. So the efficient rule is the same as for a person: do more work between interruptions, and avoid interruptions you can batch.
mistakes: People often think a context switch costs only the 1 to 3 microseconds you measure with a ping-pong test. In fact that test uses tiny working sets, so it shows only the direct cost. In real programs the cache, TLB and branch-predictor refill is often several times larger, and it shows up as slow code after the switch, not as time in the kernel.
People often think threads and processes cost the same to switch. In fact a switch within one process keeps the page tables, so the TLB can stay warm. A switch between processes loads a new address space, which costs more, especially without PCID.
People often think user-space code is not affected by switches because the kernel does them. In fact the cost is paid by user code: it runs slower afterwards. A profile can show a function as slow although its code did not change; the cause was a cold cache after a switch.
People often think that more threads always increase throughput. In fact beyond the number of cores, extra runnable threads add switches and cache competition without adding compute. For CPU-bound work the best thread count is close to the core count.
tradeoffs: Choose thread-per-request (or thread-per-connection) when concurrency is moderate (hundreds, not tens of thousands), the code is blocking and simple, and requests do real CPU work or call blocking libraries. You pay with memory (each thread has a stack, commonly 1 MB reserved and 16 KB of kernel stack) and with switch costs that grow with thread count. Choose an event loop or async runtime when you have thousands of mostly idle connections and short handlers. You pay with more complex code and the risk that one blocking call stalls everything.
Choose user-level threads (goroutines, Java virtual threads, Erlang processes) when you want the simple blocking style of code with the low switch cost of an event loop. You give up some control: the runtime's scheduler is invisible to the kernel, CPU-bound tasks can hog a worker thread, and native code that blocks needs special handling.
Choose pinned threads (thread-per-core) when tail latency is the main goal and work can be partitioned by key. You avoid migrations and most switches, but you give up automatic load balancing: a hot partition cannot borrow another core. Choose floating threads when load is uneven or you cannot partition it.
Choose to keep security mitigations on (KPTI where needed, branch-predictor barriers) in multi-tenant or untrusted environments, even though they raise switch cost by a few percent to tens of percent for syscall-heavy loads. On dedicated machines that run only trusted code, some teams relax them, accepting the risk for speed. Newer CPUs with hardware fixes make this choice less costly.
friction: The indirect cost is hard to measure and impossible to put on a single number. It depends on the working set, the cache sizes, what the previous thread did, and whether the two threads share a core, a cache or a NUMA node. Benchmarks that show 1 to 2 µs miss most of the damage, and a profiler attributes the cost to whatever function happens to run after the switch.
Switches interact with other mechanisms. A thread that holds a lock and is switched out makes others wait for it; a lock convoy forms when many threads repeatedly block on the same lock and are woken one by one, each wake-up costing a switch. Wake-ups across cores need inter-processor interrupts and may need the target core to leave a deep power-saving state, which can add tens of microseconds. In virtual machines, a switch can trigger exits to the hypervisor.
Security work made it worse. Meltdown and Spectre mitigations add CR3 changes, buffer flushes and barriers. Hardware features such as PCID reduce the cost, but containers and VMs on shared hosts may still pay it. The more the workload depends on short system calls and wake-ups, the more it pays.
There is no general fix. Reducing switches (batching, event loops, pinning, fewer threads) moves complexity to the application, and user-level threading depends on every library cooperating. The remaining open problems are mostly in coordination: how a runtime and the kernel can agree on who runs what, as research on user-level scheduling and eBPF-based schedulers (sched_ext) tries to do.
practice: Look at the counters first. Run vmstat 1 and check "cs" (switches per second) and "r" (runnable threads); use pidstat -w to see voluntary and involuntary switches per process; use perf sched or eBPF tools (for example cpudist and runqlat) to see how long threads run and wait. A rate of tens of thousands of switches per second per core is a warning sign. If switches are mostly voluntary, find what blocks (locks, I/O); if involuntary, you have too many runnable threads.
Size pools by work type: about one thread per core for CPU-bound work, and a bounded larger pool for blocking work, kept separate so one cannot starve the other. Avoid creating a thread per task. Prefer batching: process a queue in chunks, flush logs in groups, send network writes together, and let one worker drain many items per wake-up.
Pin latency-critical threads to cores (taskset, cpuset, or the runtime's affinity setting), and keep their interrupts and other threads away. Keep related threads, such as a producer and consumer that exchange data, on cores that share a cache. On NUMA hosts, keep a thread near its memory.
Use async runtimes or virtual threads for I/O-heavy servers, and test with the real number of connections, not a small benchmark. Check that your language runtime honours container CPU limits, or it will create more threads than the quota allows.

A process switch loads new page tables; without PCID the TLB is flushed, with PCID the entries are tagged by address space and survive. After KPTI, PCID matters for every kernel entry, not only for process switches.

quiz: What does the kernel save and restore in a thread switch? || The CPU registers (general registers, instruction and stack pointers, flags, and vector state when used). For a different process it also loads a new page-table root.

@@ pagecache
value: The page cache is the part of RAM where the Linux kernel keeps copies of file data. When a program reads a file, the kernel first looks in this cache. If the data is there, the read is a memory copy that takes about a microsecond. If not, the kernel reads the data from the device, which takes about 100 microseconds on an NVMe SSD and 5 to 10 milliseconds on a spinning disk, and keeps a copy for the next reader. Writes also go to the cache first: write() copies data into a page, marks it dirty and returns, and the kernel writes the page to the device later.
Almost every program uses it without asking. The free memory on a server is not wasted: the kernel fills it with file data, and gives it back when programs need it. A 64 GB machine that runs a 10 GB service will, over time, hold up to 50 GB of recently used file data. This is why a second run of a job is often much faster than the first, and why a restart that empties the cache makes a database slow for minutes. Kafka is designed around this: it writes to files and lets the page cache serve the consumers that read recent data. PostgreSQL has its own buffer pool but relies on the page cache too.
The page cache stands on three lower ideas. The memory hierarchy (L3) explains the gap it fills: RAM is about 100 times faster than SSD and 10,000 times faster than disk, so a cache in RAM pays off. Virtual memory and demand paging (L3) give it the machinery: file data lives in the same 4 KB pages, with the same free lists and reclaim as process memory. Page replacement (L3) decides which pages to evict when memory is needed. Probability (L4) explains why it works at all: file access is skewed, so a small hot part receives most reads and a cache hit rate of 90% to 99% is common. The layers above use it for logs (write-ahead logs), memory-mapped files and zero-copy transfers.
terms: Page — the unit of memory management, 4 KB on x86-64; the page cache stores file data in pages (or in larger groups called folios).
Page cache hit / miss — a hit finds the requested file data already in RAM; a miss must read it from the device.
Dirty page — a cached page that was modified and has not yet been written to the device.
Writeback — the process of writing dirty pages to the device, done by kernel flusher threads in the background or forced by fsync.
Readahead — reading file pages before the program asks for them, because the access pattern looks sequential.
Buffered I/O vs O_DIRECT — buffered I/O goes through the page cache; O_DIRECT bypasses it and moves data between the device and the program's buffer.
Active / inactive list — the two LRU lists the kernel uses to rank cached pages; new pages start inactive and move to active when used again.
Reclaim — the kernel freeing pages, starting with clean cached pages, when free memory is low.
history: Early Unix (1970s) had a buffer cache: a fixed pool of disk blocks kept in kernel memory, separate from the virtual memory system. This created two problems. The size had to be fixed in advance, and a file mapped into memory could exist twice, once in the buffer cache and once in the process's pages. SunOS 4 (around 1988) merged file caching into the virtual memory system, so file pages and process pages were the same kind of object. Linux followed. In Linux 2.4 (2001) the block buffers became part of the page cache, and the cache could use all free memory.
The next steps were about quality of eviction. The 2.6 kernels used two LRU lists, active and inactive, to resist scans, so one pass over a huge file does not push out the hot set. In Linux 3.15 (2014), Johannes Weiner added workingset detection: when a page is evicted, the kernel keeps a small "shadow" entry, and if the page is read again soon (a refault), the kernel learns that the cache was too small for the workload and treats that page as hot. Linux 4.20 replaced the radix tree index with the XArray, and Matthew Wilcox's folios (Linux 5.16 onward) let the cache handle groups of pages as one unit, which cuts per-page overhead for large files. Linux 6.1 added the multi-generational LRU (Yu Zhao), a finer-grained aging scheme that is used on large systems, and Linux 6.5 added the cachestat() system call so programs can ask how much of a file is cached.
Reading the page cache design is also reading the history of an old trade: use idle memory as a cache, but never hold memory that an application needs. The kernel's job is to keep the cache as large as possible and to shrink it fast when pressure appears.
how: Each open file has an inode, and each inode has an address_space object that holds the cached pages of that file, indexed by page number (the file offset divided by 4 KB) in an XArray, which is a radix-tree-like structure with O(log n) lookup and a few cache misses for large files. A read(fd, buf, 8192) at offset 40960 turns into a lookup of page indexes 10 and 11. For each page present, the kernel copies the data from the cached page to the user buffer (about 4 KB in 0.3 to 0.5 µs at 10 GB/s) and the call returns. This hit path has no device access and no sleep.
On a miss, the kernel allocates a free page, adds it to the cache in a "locked, not up to date" state, and submits a read to the block layer. The calling thread sleeps. When the device raises an interrupt, the page is marked up to date and unlocked, and the sleeping thread wakes. Other threads that ask for the same page in the meantime find it in the cache, wait on the same lock, and share one device read. This is also why the cache is shared: any process that reads the same file sees the same pages.
Readahead hides the delay for sequential reads. The kernel tracks the pattern of each open file. When it sees reads at consecutive offsets, it starts with a window (by default 128 KB, read_ahead_kb) and enlarges it up to the maximum while the pattern continues. It marks one page in the window; when the program reaches that marker, the kernel starts the next window asynchronously, so data is arriving while the program uses the previous window. Random reads turn readahead down. Programs can also give hints with posix_fadvise (SEQUENTIAL, RANDOM, WILLNEED, DONTNEED) or readahead().
Writes follow a different path. write() finds or creates the cached page, copies the user's data into it, marks the page dirty, and returns, usually in 1 to 2 µs. Nothing has reached the device. Flusher threads (kworkers, one set per backing device) scan for dirty pages and write them back in three situations: the page has been dirty longer than dirty_expire_centisecs (30 seconds by default, checked every 5 seconds); the fraction of dirty memory has passed vm.dirty_background_ratio (10% of reclaimable memory by default), which starts background writing; or the fraction passes vm.dirty_ratio (20%), when writers themselves are slowed or blocked inside write() until dirty memory goes down (balance_dirty_pages). An fsync call forces the writeback of one file at once, which is the next concept in the map.
Eviction uses the same ideas as process memory (page replacement). A new file page goes to the inactive list. If it is accessed again, it moves to the active list. When free memory is low, the reclaimer scans from the tail of the inactive list: clean pages are dropped at once, because the device has a copy; dirty pages must be written first. The active list is trimmed into the inactive list when it grows too large. For pages that processes access through memory mappings, the hardware sets an "accessed" bit in the page table, which the kernel checks. Pages that belong to anonymous process memory have no file copy, so they can be reclaimed only by swapping them out; the kernel balances between the two kinds (vm.swappiness).
The cache is also visible to controls. In cgroup v2, page cache pages are charged to the cgroup that first read them, so memory.current includes cache, and the limit memory.max triggers reclaim of the cache before it kills anything. That is why a container can look "full" of memory without a problem. Tools show the numbers: free reports buff/cache and an "available" estimate that counts reclaimable cache; /proc/meminfo has Cached, Dirty and Writeback.
Why does this work? Because of skew. If reads follow a skewed distribution, for example 80% of reads go to 5% of the pages, a cache holding just that 5% serves 80% of the traffic. Real access patterns of logs, indexes and recent data are even more skewed. Probability gives the expected time: with hit rate h, hit time t_h and miss time t_m, the mean read time is h × t_h + (1 − h) × t_m. The miss term dominates, so each point of hit rate matters.

example: Take a service that reads 4 KB records from a data file on an NVMe SSD. A device read costs about 100 µs. A page cache hit costs about 1 µs, including the system call and the copy. The mean read time is h × 1 + (1 − h) × 100 µs. At a hit rate of 50% it is 50.5 µs. At 90% it is 0.9 + 10 = 10.9 µs. At 99% it is 0.99 + 1 = 1.99 µs. Going from 90% to 99% hit rate makes reads 5.5 times faster, although only 9 more reads in 100 are hits. On a spinning disk with 8 ms misses the same figures are 4,000 µs, 801 µs and 81 µs, so the cache matters even more.
Now size it. A data file is 200 GB and 90% of reads go to the hottest 20 GB. The machine has 64 GB of RAM, with 16 GB for the application. About 48 GB is free for cache, which holds the whole 20 GB hot set and part of the rest. The hit rate is perhaps 95% or higher. If another job on the same machine allocates 40 GB, the cache shrinks to 8 GB. The hot set no longer fits, the hit rate drops to maybe 55%, and the mean read time rises from about 6 µs to 45 µs, a 7 times slowdown, with no change in the service itself. Disk reads per second jump, and tail latency follows.
Next, writes. An application logs 50 MB/s. Each write() takes 2 µs because it only fills a page. With 64 GB of RAM, the background threshold is about 10% of reclaimable memory, so around 5 GB or more. The kernel starts background writeback long before that when pages pass 30 seconds of age, so at 50 MB/s the dirty set stays near 30 s × 50 MB/s = 1.5 GB. If the disk is slower than 50 MB/s for a minute, dirty memory grows until it crosses the 20% limit. At that point write() itself blocks, and the application sees a pause of seconds even though it never called fsync. If the machine loses power with 1.5 GB dirty, those 30 seconds of log are lost, which is why logs that must be durable call fsync or use O_SYNC.
intuition: The operating system keeps the files you used recently open on the desk instead of walking back to the archive each time.
The idea is natural because it uses a resource that would be idle. Programs rarely need all of RAM, and storage is far slower than RAM. A cache that uses free memory costs nothing when memory is plentiful, and the kernel can drop it in microseconds when memory is needed, since clean pages have a copy on disk. Skewed access means that a small cache gives a large gain. And by treating file pages as ordinary pages, the system needs one memory manager, one eviction policy and one place to look, instead of one cache for files and another for memory.
mistakes: People often think that free memory is wasted and that "used" memory on a server is a problem. In fact most "used" memory on a file-heavy server is page cache that the kernel drops on demand. Look at "available" in free, not "free". A server with 1 GB free and 50 GB of cache is healthy.
People often think that write() means the data is on disk. In fact it means the data is in the page cache. If the machine loses power before writeback, the data is lost. Only fsync (or O_SYNC and similar) gives durability.
People often think that a database should always use O_DIRECT and skip the page cache. In fact it depends. Databases that manage their own buffer pool and know their access patterns, such as InnoDB, often use O_DIRECT to avoid double caching. PostgreSQL deliberately uses buffered I/O and leans on the kernel cache, and Kafka relies entirely on it. Bypassing the cache also loses readahead and write merging unless the program implements them.
People often think that dropping caches (echo 3 > /proc/sys/vm/drop_caches) is a good way to free memory. In fact it throws away useful data and makes the next minutes slow. It is a testing tool for cold-cache benchmarks, not a tuning tool.
People often think a container's memory limit applies only to its program's memory. In fact the container is charged for page cache it touches too. Reclaim handles this, but heavy writing can build up dirty pages that hit limits and make writers stall.
tradeoffs: Choose buffered I/O (the page cache) when access is skewed, reads repeat, and the kernel's readahead and eviction are good enough, which holds for most services, Kafka brokers and many databases. You give up control: you cannot easily say what stays cached, and the cache competes with your processes for memory. Choose O_DIRECT with your own buffer pool when you know your access pattern better than an LRU does, when you need predictable memory use, or when double caching wastes a large share of RAM. You then implement caching, readahead and write merging yourself, and you give up cheap sharing between processes.
Choose a larger application cache (for example a big JVM heap or buffer pool) when decoded objects are expensive to rebuild from raw pages, and a smaller one when raw bytes are the unit of use. A rule of thumb for PostgreSQL is a shared_buffers of about 25% of RAM, leaving the rest to the page cache. A large heap also adds garbage-collection pauses and takes memory away from the page cache, so every gigabyte is a decision.
Choose to let the kernel flush dirty pages in the background (default settings) for throughput and when you can tolerate losing the last seconds on a crash. Choose smaller dirty thresholds (for example dirty_background_bytes of a few hundred MB) when the device is slow and you want steady write rates instead of long pauses, accepting less write merging. Choose fsync or O_DSYNC when you must not lose acknowledged data, accepting a milliseconds-level cost per sync.
Choose madvise/fadvise hints and prefetching (WILLNEED, DONTNEED) when you know a job will scan a big file once, so it does not push out the hot set. You give up some simplicity, and the hints are advice, which the kernel may ignore.
friction: The cache is shared, and it is hard to control. A backup job that reads 500 GB can push out the hot data of a database, and on a shared machine one tenant's file reads can evict another's. Control tools exist (cgroup memory limits, fadvise DONTNEED, O_DIRECT for the scan), but each needs care, and there is no general per-file quota for cache.
Double caching is a standing cost. A database that keeps its own buffer pool and also reads through the page cache stores each hot page twice. Compressed formats make it worse: the cache holds compressed bytes and the application holds decompressed data. The usual cures are O_DIRECT or sizing the application cache smaller.
Writeback causes latency spikes. Dirty data builds up, then the kernel writes a lot at once, queues grow in the device, and reads that need the same device slow down. Writers can also be throttled inside write(). Tuning the ratios helps but depends on the device; with network-attached storage, writeback can stall across a whole fleet.
Errors are hard. A buffered write can fail long after write() returned success, when the flusher fails to write the page. The error reaches the program only at fsync or close, and in older kernels it could be lost, which is the subject of the fsync concept. For durability, the page cache is a place where data is not yet safe.
Finally, a cold cache hurts. After a reboot, failover or new node, the hot set must be read again from the device, and for large datasets this warm-up takes minutes to hours. Services behind load balancers may time out while warming. Some systems pre-warm by reading files at startup (vmtouch, or cat file > /dev/null).
practice: Check hit rates and pressure. Use free, /proc/meminfo and vmstat for the big picture; fincore, vmtouch or the cachestat system call to see how much of a file is cached; and eBPF tools (cachestat, biosnoop) for hit rates and device reads per second. If major faults and disk reads rise while memory is nearly full, the working set no longer fits in cache.
Leave memory for the cache. For file-heavy systems such as Kafka, Elasticsearch/Lucene, Cassandra and ClickHouse, do not give the JVM or the process almost all of RAM. A common starting point is to keep the heap small (for Kafka, a few GB) and let the rest of RAM serve as cache. In Kubernetes, set memory requests with the cache in mind; a pod whose working set is the data on disk needs RAM for it.
Set writeback thresholds for the device. On servers with large RAM, the default 10%/20% ratios can mean many gigabytes of dirty data; set vm.dirty_background_bytes and vm.dirty_bytes to values the device can flush in a few seconds. For logging and WAL files, call fsync at the points where data must be durable, and batch them.
Keep scans from polluting the cache: for big sequential jobs use posix_fadvise(DONTNEED) after reading, or O_DIRECT, or run them in a cgroup with a memory limit. To prepare a node, pre-read the hot files. When you benchmark, say whether the cache was warm or cold, and test both. Never conclude that storage is fast from a second run.
interview: Kafka does not fsync each message and has no big in-process cache. How can it still serve reads fast and stay safe? || Producers append to log segments, so writes land in the page cache and go to disk sequentially. Consumers near the end of the log read from the same cached pages, and sendfile moves them to the socket without copying into user space. Safety comes from replication to other brokers, not from fsync per message; the cache also survives a broker process restart as long as the machine stays up.
A node's "free" memory is near zero but nothing is wrong. How do you tell whether it is healthy? || Look at available memory, page cache size and dirty/writeback in /proc/meminfo, plus major page faults, swap activity and pressure stall information (PSI memory). If cache is large, available is high, and there is no swapping or reclaim stall, it is healthy. Trouble shows as rising direct reclaim, swap-in and device reads.
Why does a long-running scan make an OLTP database slow, and how do you prevent it? || The scan fills the cache with cold pages, and without scan resistance it evicts the hot set, so the database misses and reads from disk. The active/inactive lists and workingset detection help, but not fully. Use fadvise DONTNEED or O_DIRECT for the scan, run it in a memory-limited cgroup, or run it on a replica.
A write-heavy service sees multi-second pauses in write() with low disk utilization on average. What is happening? || Dirty memory crossed vm.dirty_ratio, so the kernel throttles writers in balance_dirty_pages until flusher threads reduce it, and the device is saturated in bursts. Lower dirty_background_bytes and dirty_bytes so writeback starts earlier and smoother, spread writes with periodic sync_file_range or fsync, and check the device throughput.
When is O_DIRECT the right choice? || When the application has its own cache with better knowledge of the workload (for example a database buffer pool), when it needs predictable memory and latency, or to avoid double caching. It requires aligned buffers and offsets and gives up kernel readahead and write merging, so the application must supply those.
quiz: What happens on a read() when the requested file page is not in the page cache? || The kernel allocates a page, submits a device read, and puts the thread to sleep. When the interrupt arrives the page is marked up to date and the thread is woken, and the data is copied to the user buffer. The page stays cached for later reads.
Why do the active and inactive lists help against a one-time large file scan? || New pages enter the inactive list and move to the active list only on a second access. A scan touches each page once, so scanned pages are evicted from the inactive list first and the hot pages in the active list survive.
With a 1 µs hit and a 100 µs miss, what is the mean read time at a 98% hit rate? || 0.98 × 1 + 0.02 × 100 = 0.98 + 2 = 2.98 µs.
Why can write() block even though the program never calls fsync? || When dirty pages exceed vm.dirty_ratio the kernel throttles the writing process in balance_dirty_pages until background flushers write enough data to bring the dirty fraction down.
You run a database on a 64 GB machine. Should you give the database 60 GB of buffer pool? || Usually not. With buffered I/O, the page cache also needs room, and a pool that large leaves little for the kernel, causes double caching, and risks memory pressure. A smaller pool (for example about 25% of RAM for PostgreSQL) or O_DIRECT with a large pool are consistent designs.

@@ mmap
value: Memory mapping lets a program treat a file as an array in memory. After mmap() returns a pointer, reading byte 5,000,000 of the file is the expression p[5000000]. There is no read() call, no buffer to manage, and no copy into user space. The kernel loads the needed 4 KB pages from disk when the program first touches them, and it writes changed pages back later.
It is used where code wants fast random access to large files with the least effort. The dynamic loader maps every executable and shared library, so many processes share one copy of the code in RAM. Lucene and Elasticsearch read their index files through mapped memory. LMDB is a whole database built on one mapping. Kafka maps its offset index files. llama.cpp maps model weights so that a 4 GB model starts almost at once and a second process reuses the same cached pages. In all of these, the file is much larger than the program wants to copy around, and the access pattern is random or repeated.
Mapping stands on two lower ideas. Virtual memory and paging (L3) provide the mechanism: the page table can point a virtual page at any physical page, and a page fault lets the kernel fill in a page on first access. The page cache (L3) provides the data: a mapped file page is the very same physical page that read() would have used, so the program, the kernel and other processes share one copy. mmap is therefore not a different storage path. It is a different interface onto the page cache, and that is both its strength (no copies, no system calls on hits) and its weakness (the program cannot control when I/O happens). Zero-copy I/O and Lucene's directory layer build on it.
terms: Mapping (VMA) — a range of a process's virtual addresses that the kernel has tied to a file or to anonymous memory; the kernel records it as a virtual memory area.
Page fault — a hardware exception raised when the program touches a virtual page that has no valid page-table entry; the kernel handles it and the instruction is retried.
Minor fault — a fault resolved without device I/O, because the page is already in the page cache or is a zero page.
Major fault — a fault that must read the page from the device and so sleeps for about 100 µs on an SSD and milliseconds on a disk.
MAP_SHARED / MAP_PRIVATE — shared: writes go to the file and are visible to others; private: writes make a private copy-on-write page that never reaches the file.
msync — a system call that forces dirty pages of a shared mapping to be written to the file, like fsync.
madvise — a call that gives the kernel hints about a mapping, such as sequential, random, will-need or do-not-need.
TLB shootdown — when the kernel unmaps a page, it must tell other cores to drop the cached translation, using inter-processor interrupts.
SIGBUS — the signal a program receives if a mapped page cannot be provided, for example after an I/O error or when the file was truncated.
history: The idea that files and memory are one thing is very old. The Multics system (1960s) had a single-level store: every file was a segment that programs addressed directly, and the system moved data between disk and memory. Unix started with read() and write() on byte streams, but the Berkeley group designed mmap for 4.2BSD (1983) as a better way to share memory and access files. It was not fully implemented there. SunOS 4 (1988) provided the first widely used implementation as part of its unified virtual memory system, and System V Release 4 and POSIX adopted it. Windows has the same idea under the name file mapping.
Databases adopted mapping early because it saved the work of a buffer pool. MongoDB's original storage engine (MMAPv1) mapped its data files and left paging to the operating system. LMDB (2011) built a copy-on-write B-tree on a read-only mapping and became popular because it was small and fast on read-heavy workloads. Lucene's MMapDirectory became the default on 64-bit systems after 64-bit address spaces made it possible to map files larger than 4 GB; Uwe Schindler's 2012 post explained why it should be used.
Experience then showed the limits. MongoDB replaced MMAPv1 with WiredTiger (default in 3.2, MMAPv1 removed in 4.2). Several database developers published warnings about the problems of paging out of control. In 2022 Andrew Crotty, Viktor Leis and Andrew Pavlo wrote "Are You Sure You Want to Use MMAP in Your Database Management System?" at CIDR. They named four problem areas: transactional safety, I/O stalls, error handling and performance, and showed that on fast NVMe drives, mapping loses clearly to explicit I/O once data does not fit in memory. At the same time mapping stayed popular where the data is read-only or fits in memory.
how: The call mmap(addr, length, prot, flags, fd, offset) does very little work. It creates a VMA, a record that says "virtual addresses A to B are backed by file F starting at offset O, with these permissions". No page is read, no page-table entry is made, and the call returns in a few microseconds even for a 1 TB file. On 64-bit x86 a process has 128 TiB of user address space, so large files can be mapped whole.
The first access to an address in the range triggers a page fault. The CPU raises an exception, the kernel looks up the address in the VMA tree, finds that it belongs to a file, and asks the file system for that page. The kernel looks in the file's page cache. If the page is there (a minor fault), the kernel writes a page-table entry that points to it and returns, and the instruction runs again. The cost is about 0.5 to 1 µs for the exception, lookup and table update. Linux also maps up to 16 neighbouring pages that are already cached in the same fault (the "fault-around" size is 64 KB by default), so a sequential scan of cached data takes one fault per 16 pages. If the page is not cached (a major fault), the kernel starts a device read, puts the thread to sleep, and builds the entry when the data arrives, as in the normal read path (page cache). Readahead applies, and madvise can tell the kernel the pattern.
After the first fault, access is plain memory access: a load goes through the TLB to the physical page at the speed of RAM, about 100 ns for a cache miss and a few ns for a hit. There is no system call and no copy. This is the real gain: for repeated random access to cached data, a mapped lookup costs a memory access, whereas pread() costs a system call (100 ns or more with mitigations) plus a copy.
Writes depend on the flags. With MAP_PRIVATE, a write triggers copy-on-write: the kernel copies the page and the process changes its own copy, which never goes back to the file. With MAP_SHARED, the kernel first maps clean pages read-only. The first store causes a fault, the kernel marks the page dirty and makes the entry writable, and later stores to that page run at full speed. The flusher threads write dirty pages back in the background, as for write(); msync(MS_SYNC) forces it and waits, and munmap does not. So a store to mapped memory is not durable until msync, and the kernel may write any dirty page at any time and in any order.
Eviction goes through the same reclaim as the page cache. To free a mapped page, the kernel must first remove it from every page table that maps it (reverse mapping) and flush the translation from the TLB of every core that might hold it. The second step is a TLB shootdown, done with inter-processor interrupts, and it costs microseconds and interrupts running threads. With many cores and fast SSDs, this overhead and the single-threaded nature of some reclaim paths become the bottleneck, which is one of the findings in the CIDR paper.
There are three further points about control. First, a fault is invisible to the program: the thread simply stops at an instruction while the kernel reads from disk. It cannot do other work meanwhile, and it cannot choose a different page to wait for. Second, an I/O error or a truncated file makes the fault fail, and the program receives SIGBUS, not an error code from a call it could check. Third, the program can only advise: madvise(WILLNEED) asks for prefetch, MAP_POPULATE pre-faults the range, and mlock pins pages in RAM, but the kernel decides.
Because of the TLB, mapping large files has its own cost. With 4 KB pages, a 1 GB mapping needs 262,144 translations, while a core's TLB holds a few thousand entries, covering a few megabytes. Random access over a large mapping therefore often misses the TLB and needs a page-table walk of up to four memory accesses. Huge pages reduce this, but file-backed huge pages are limited on Linux.

example: Map a 1 GB file that is already fully in the page cache and scan it sequentially. The call to mmap takes a few microseconds. The scan touches 262,144 pages. With fault-around of 16 pages, there are about 16,384 faults. At about 1.5 µs each (a mapping of 16 entries per fault costs more than one), that is about 25 ms of fault handling. The scan then reads memory at several GB/s, so the 1 GB costs maybe 100 to 150 ms of memory time in total. Compare read() in 1 MB chunks: 1,024 system calls at about 1 µs is 1 ms, and the kernel copies 1 GB into the user buffer, which at about 10 GB/s costs another 100 ms, followed by the program reading the buffer. The two approaches are in the same range. Mapping saves one copy but pays faults, and read() with a large buffer is simple and predictable. For one sequential pass, neither wins by much.
Now random lookups. A key-value store keeps a 100 GB data file and does 1 million random 4 KB lookups per second on a machine with 256 GB of RAM, so everything is cached. With pread, each lookup costs a system call of about 0.3 µs (with mitigations), a page cache lookup of about 0.2 µs and a 4 KB copy of about 0.4 µs, about 1 µs in total. With mmap, after the first touch of each page, a lookup is a pointer dereference and a TLB hit or miss: about 0.1 to 0.3 µs. Mapping is three to ten times cheaper in CPU, which is the reason LMDB and Lucene readers are fast on cached data.
Then the data does not fit. The file is 1 TB and RAM is 256 GB, so about 75% of lookups are major faults. Each takes about 100 µs of device time and blocks the thread. With explicit I/O, a program can issue 64 reads at once and use io_uring or a thread pool to keep the NVMe drive busy at 500,000 or more reads per second. With mmap, each thread has one outstanding fault at a time; 32 threads give about 32 / 100 µs = 320,000 faults per second at best, and the kernel's eviction work (page-table updates, shootdowns) takes time from the same cores. Throughput is lower, and latency is at the mercy of the kernel's reclaim. This is the regime in which the CIDR paper measured large slowdowns.
intuition: Open the book directly on the table instead of photocopying the pages you need.
The idea is natural because the machine already has the mechanism. Virtual memory means every program already lives in a world of addresses translated by page tables, and the kernel already caches file pages. Mapping simply says: let this range of addresses translate to those cached pages. Then the program uses ordinary loads and stores, and the hardware and kernel do the paging. The same property is the danger: because disk access looks like a memory read, nothing in the code shows where it may stall for 100 microseconds, fail with a signal, or be reordered on the way to disk.
mistakes: People often think mmap reads the whole file into memory. In fact it reads nothing at the call. Pages are loaded on first access, and only the touched pages (plus readahead and fault-around) are in RAM. A mapped 1 TB file does not need 1 TB of memory.
People often think mmap is always faster than read(). In fact it saves the system call and the copy, but it costs page faults, TLB misses and shootdowns. For a single sequential pass, read() with a large buffer is similar. For data that does not fit in memory on fast SSDs, explicit I/O is often much faster.
People often think writes to a mapped file are safe once the store executes. In fact the store only changes a page in RAM. The kernel may write it at any time, in any order, and it is durable only after msync and a successful return. A crash can leave half of a multi-page update on disk, so a database needs its own logging or copy-on-write on top.
People often think that errors show up as return codes. In fact a failed page-in or access past the end of a truncated file raises SIGBUS in the thread that touched the page. Handling that signal safely in application code is hard.
People often think mapped memory is free of memory accounting. In fact mapped file pages count in the page cache and can be charged to a container's cgroup; the process's RSS includes them. They are easy to reclaim when clean, but dirty mapped pages need writeback first.
tradeoffs: Choose mmap when the file is read-mostly or immutable, mostly fits in memory, and is accessed randomly with many small reads, for example search index segments, SSTable-like files and model weights. You gain simple code, no copies and shared memory between processes. You give up control over I/O timing and error handling. Choose pread/pwrite with your own buffer pool when the data is bigger than memory, when you need to schedule I/O (prefetch, batching, priorities), or when you need strict write ordering for transactions. You pay with more code and with copy costs, but you decide what stays in memory.
Choose io_uring or asynchronous direct I/O when you need very high random-read throughput from NVMe and have many requests in flight. A mapping gives you one blocking fault per thread. You give up simplicity and portability.
Choose MAP_PRIVATE (copy-on-write) when a process only reads a shared file, or when it wants a scratch copy of loaded data (for example, a copy-on-write snapshot of a model). Choose MAP_SHARED with explicit msync only when the format is safe against partial and reordered writes, such as a copy-on-write B-tree like LMDB.
Choose to prefault and lock (MAP_POPULATE, mlock) when latency spikes from major faults are unacceptable and the data fits in RAM, accepting a slow start and RAM that the system cannot reclaim. Choose lazy loading when start-up time matters more than the first-access latency.
friction: The central problem is lost control. The database or application cannot say which page to keep, which to drop, or when to read. The kernel's LRU does not know the application's priorities, such as keeping index pages over data pages. The application also cannot overlap I/O with computation inside a fault. In latency-sensitive systems a major fault can cost 100 µs to many milliseconds and appears at a random place in the code.
Transactional safety is the second problem. Database systems need to write the log before the data page. With a shared mapping, the kernel can flush a modified data page at any moment, ahead of the log record. To avoid it, the system must use private mappings and copy pages itself, or copy-on-write structures, and then much of the advantage of mapping is gone.
Error handling is awkward. I/O errors surface as SIGBUS, there may be no clear place to catch them, and a reader of a file that is truncated by another process can crash. Portability is also limited: behaviour of msync, huge pages and sparse files differs between operating systems, and 32-bit systems cannot map large files.
Performance does not scale with fast hardware. Page-table updates, shared locks on the address space (mmap_lock, now split into per-VMA locks in recent kernels), reclaim by a few kernel threads, and TLB shootdowns across many cores become the limits as NVMe drives reach millions of IOPS. Finally, mapping hides memory use: a monitoring graph that shows RSS or cache growth is partly the mapped file, and sizing a heap or a container limit becomes harder.
practice: Use it for read-mostly data that is shared and mostly cached: index files, model weights, lookup tables, static data files. Give the data to the kernel and leave RAM for it: with Lucene or Elasticsearch keep the JVM heap small (well below half of RAM) so that the page cache can hold the index. Elasticsearch requires vm.max_map_count of at least 262,144 because it maps many files. Check ulimit and vm.max_map_count in your own services if you map many files.
Give hints. Use madvise(MADV_SEQUENTIAL) for scans, MADV_RANDOM for point lookups to turn off readahead, MADV_WILLNEED to prefetch the next part, and MADV_DONTNEED to drop pages you have finished with. Use mincore() or the fincore tool to see what is resident. For latency-critical data, pre-fault it at startup (MAP_POPULATE, or touch each page) and consider mlock.
If you write through a mapping, use msync at points where the data must be durable, design the file format so a partial write is detectable (checksums, versioned root pointers), and prefer append-only or copy-on-write layouts. For general-purpose transactional storage, use explicit I/O and your own buffer manager, or a well-tested engine.
Watch the signals: in languages with managed runtimes, a SIGBUS can crash the process (the JVM may terminate on a truncated mapped file). Do not truncate files that others have mapped. Measure with perf for page-faults and dTLB misses, and with /proc/<pid>/smaps to see how much of a mapping is resident, shared and dirty.
interview: Why is a mapped read of cached data cheaper than pread, and when does that advantage disappear? || After the first fault, a read is a normal load through the TLB, with no system call and no copy; pread pays both on every call. The advantage disappears when data is not cached (every access is a major fault that blocks one thread), when TLB misses dominate over a huge mapping, or when page-fault and eviction overhead (shootdowns, locks) grows with core count.
Name the problems the CIDR 2022 paper finds with mmap in a DBMS. || Transactional safety (the kernel can flush dirty pages in any order and at any time, so write-ahead logging is hard to enforce), I/O stalls (page faults block with no way to schedule or prefetch), error handling (SIGBUS instead of return codes), and performance (page-table contention, single-threaded eviction, TLB shootdowns), which hurts on fast NVMe when data exceeds RAM.
How does LMDB get transactional safety while using a shared mapping? || It never overwrites pages in place. It uses a copy-on-write B-tree and commits by writing a new root pointer (two meta pages alternate) after the new pages are durable. A crash leaves the old, consistent tree. Readers use the old snapshot with no locks.
A service that maps a 200 GB file shows random 50 ms latency spikes. How do you investigate? || Check for major faults (perf, /proc/<pid>/stat, eBPF), page cache pressure from other processes, writeback of dirty mapped pages, and compaction or reclaim stalls (PSI memory). Fixes: leave more RAM for cache, prefault and mlock hot ranges, madvise hints, move large scans out of the process, or replace faults with explicit async reads.
Why does Elasticsearch need vm.max_map_count raised, and what does it say about the design? || Each index segment file is mapped, and a node with many shards can create hundreds of thousands of mappings; the default limit of 65,530 per process is too low. The design bets that the page cache plus mapping gives fast reads without a heap-managed cache, which is why the heap is kept small.
quiz: What happens when a program first touches a page in a mapped file that is already in the page cache? || A minor page fault: the kernel finds the cached page and writes a page-table entry for it, then the instruction runs again. No device read happens.
Why can a store to a MAP_SHARED mapping be lost on a crash even after the store instruction completed? || The store only changes a page in RAM. The page reaches the file when the kernel flushes it or when msync completes. A crash before that loses the change, and the kernel may have written other pages first.
A file of 4 GB is mapped and the program reads every page once with fault-around of 16 pages. About how many page faults happen? || 4 GB / 4 KB = 1,048,576 pages; divided by 16 gives about 65,536 faults.
Why is mmap often slower than explicit I/O for random reads on a big NVMe drive when data exceeds RAM? || Each thread has one blocking fault at a time, so the drive cannot be kept busy with many requests, and the kernel's eviction work (page-table changes, TLB shootdowns, reclaim threads) takes CPU and does not scale. Explicit async I/O can keep many reads in flight.
You build a read-only search index served by many processes on one host. Do you use mmap? || Yes, usually. The data is immutable, so there are no write-ordering problems, mapping shares one copy of the pages between all processes, and reads are cheap. Keep enough RAM for the cache and add madvise or prefault if tail latency matters.

@@ syscalls
value: A system call is the only door from a user program into the kernel. A program cannot touch a disk, a network card or another process's memory itself, because the CPU forbids it in user mode. Instead it asks the kernel to do the work, through a small, fixed list of numbered requests such as read, write, open, mmap, clone and futex. Linux has several hundred of them. Every file read, every network packet sent, every memory allocation that grows the heap and every new thread passes through this door.
The door exists for protection. The kernel runs in a privileged CPU mode that can access all memory and all devices, and user programs run in an unprivileged mode. A system call is the controlled way to cross: the program cannot jump to an arbitrary kernel address, it can only execute a special instruction that enters the kernel at one fixed entry point, with a call number and arguments. The kernel then checks every pointer and permission before it acts. This is why one buggy or hostile program cannot overwrite another one or read the disk directly.
The crossing costs time, roughly 70 to 250 nanoseconds for an empty call depending on the CPU and the security mitigations, and more for real work. That sounds small, but at a million calls per second it is a large part of a core. So much of high-performance systems engineering is about making fewer, bigger calls: buffered I/O, readv/writev, sendfile, epoll, io_uring and the vDSO. The mechanism stands on interrupts (L3): a system call is a deliberate trap, a synchronous exception, which uses the same hardware path to switch privilege level, save state and jump to a kernel handler. Sockets, zero-copy I/O and batching are built on this interface.
terms: User mode / kernel mode — two CPU privilege levels; kernel mode may use all instructions and memory, user mode may not.
System call number — the integer that selects the requested service, placed in a register (rax on x86-64); for example 0 is read and 1 is write on x86-64 Linux.
Trap — a synchronous transfer into the kernel caused by an instruction, as opposed to an interrupt that comes from a device.
errno — the thread-local error code in the C library; the kernel returns a negative value and the wrapper stores its absolute value here.
vDSO — a small shared library that the kernel maps into every process, so that a few calls such as clock_gettime run in user mode without entering the kernel.
seccomp — a kernel feature that filters which system calls a process may make, using a small program (BPF) that inspects the call number and arguments.
libc wrapper — the C library function (such as read()) that loads the registers, executes the trap instruction and converts the result to errno.
Short read / short write — a call that transfers fewer bytes than asked; callers must loop.
history: Early computers had no protection, so a program could do anything. Time-sharing systems of the 1960s, such as Multics, introduced hardware rings and controlled entry points ("gates") to protect the supervisor. Unix kept the idea in a very small form: the first Unix (1971) had a few dozen calls, among them open, read, write, fork and exec, and this small orthogonal set has stayed the model. Linux 0.01 (1991) had fewer than 100 calls. Today Linux has several hundred, but the oldest ones still work with their original meaning.
Hardware made the trap faster. The i386 used a software interrupt (int 0x80), which went through the interrupt descriptor table and was slow. Intel added sysenter, and Linux used it from about 2002 (kernel 2.5.53, with the vsyscall page that later became the vDSO). AMD defined syscall and sysret for 64-bit mode in the AMD64 architecture (2003), and x86-64 Linux has used them since. Arm64 uses svc and RISC-V uses ecall.
Security reshaped the interface. Seccomp (2005) first allowed only read, write, exit and sigreturn; seccomp-bpf (Linux 3.5, 2012) allowed arbitrary filters and became the basis of sandboxes in Chrome, Docker and systemd. In January 2018, Meltdown forced kernel page-table isolation (KPTI), which added a page-table switch to every system call on affected CPUs. The research on cost goes back further: Soares and Stumm's FlexSC (OSDI 2010) measured that the indirect cost of a call, through cache and predictor pollution, can exceed the direct cost, and proposed exception-less calls through shared queues. io_uring (Linux 5.1, 2019, Jens Axboe) brought that idea into the mainstream.
how: Take write(fd, buf, n) on x86-64 Linux. The C library function puts the call number 1 into rax and the arguments into rdi (fd), rsi (buf) and rdx (n); the registers rdi, rsi, rdx, r10, r8 and r9 carry up to six arguments. Then it executes the syscall instruction. The CPU saves the return address in rcx and the flags in r11, switches to privilege level 0, and jumps to the address stored in a model-specific register (LSTAR) that the kernel set at boot. This is the single entry point; the program cannot choose another one.
At that entry (entry_SYSCALL_64), the kernel switches to the thread's kernel stack, because the user stack cannot be trusted. It saves the user registers in a pt_regs structure. On CPUs that need page-table isolation, it also loads the kernel's page tables (a CR3 write; PCID tags keep the TLB mostly valid). It then calls do_syscall_64, which uses rax as an index into the system call table, after checking that the number is valid and, for speculative-execution safety, masking the index.
The handler for write validates its arguments. It looks up fd in the process's file descriptor table to get a struct file, and fails with EBADF if there is none. It checks that the file is open for writing and that the user buffer is an address in user space (access_ok), and it copies bytes with special routines (copy_from_user) that survive a bad pointer by returning an error instead of crashing. Then it calls the file's write method, which for a regular file writes into the page cache and for a socket queues data in the TCP stack. These layers are the ones below the call: the interface is thin, and what happens next depends on the kind of file.
The call may complete at once, or it may sleep. If a read on a socket has no data, the kernel marks the thread as waiting, puts it on a wait queue and calls the scheduler, which switches to another thread (see context switching). When the data arrives, an interrupt handler wakes the thread. From the program's point of view the call just took a long time. A signal can interrupt a sleeping call: the call returns EINTR, or the kernel restarts it automatically depending on the signal settings (SA_RESTART).
On return the kernel stores the result in rax. A value from -4095 to -1 means error with that errno; the library wrapper converts it to −1 and sets errno. Before leaving, the kernel checks for pending work: a signal to deliver, a need to reschedule, a trace request. Then it restores the user registers and executes sysret, which returns to the saved address and drops to user mode.
The direct cost is the mode switch and entry/exit code, around 50 to 100 ns on a CPU without isolation overhead, and up to a few hundred ns with page-table isolation on older CPUs without PCID. There is also an indirect cost: kernel code evicts some user cache lines and predictor state, and the cost of branch-predictor barriers after Spectre. Because every I/O call pays this, systems reduce the number of calls. Buffered I/O collects small writes into one. readv and writev, sendmmsg and recvmmsg send many pieces in one call. epoll returns many ready sockets at once. sendfile and splice move data inside the kernel with no user buffer. io_uring puts requests in a ring shared with the kernel, so many operations are submitted with one call, or none in polling mode.
The vDSO removes the call entirely for reads of kernel-maintained data. clock_gettime, gettimeofday and time read a time value that the kernel updates in a page mapped read-only into the process. The library call then costs about 20 ns instead of about 100 to 250 ns. This matters in programs that read the clock millions of times per second, such as tracing and logging libraries.
Finally, the interface is also the place for policy. seccomp-bpf filters run at entry, before the handler, and can allow, deny with an errno, or kill the process, which is how Docker's default profile blocks dozens of rarely needed calls. Tools like strace use ptrace to stop the process at each call, and eBPF tracepoints can observe them with less overhead. Because the numbers and meanings of Linux system calls are stable, the interface is the real boundary between kernel and user space; some languages (Go on Linux) call it directly, while others (macOS, Windows) force programs to go through a library whose calls can change.

example: Measure the cost with a copy loop. Copy a 100 MB file with a program that reads and writes one byte at a time. That is 100 million read calls and 100 million write calls, 200 million system calls in total. At about 150 ns each (an assumed mid-range value with mitigations), the time is 200,000,000 × 150 ns = 30 seconds of pure crossing, plus the work inside. Real runs of dd with bs=1 take a minute or more for a file this size. The throughput is about 1 to 3 MB/s.
Now copy the same file with 1 MB blocks. That needs 100 reads and 100 writes, 200 calls in total, about 30 microseconds of crossing. The time is dominated by copying the data, 100 MB at about 5 to 10 GB/s, which is 10 to 20 ms. The speed is a few thousand times higher, and the file is the same. This is the reason that stdio buffers (4 KB to 64 KB) exist: fwrite() collects bytes in user memory and calls write() once per buffer.
A network example. A server sends 200,000 small responses per second, each in its own send() call. At 1 µs per call (the syscall plus the TCP work), that is 20% of one core. If the server uses sendmmsg or batches responses to the same client, or uses io_uring to submit 32 sends per call, the crossing cost falls 30 times, but the TCP work per packet is the same. The saving is the 100 to 250 ns of mode switch and entry code per call, so check what share of the time it is before optimizing.
Look at your own process with strace -c ./program. It prints a table with the number of calls, errors and time per system call. A program that shows 400,000 calls of read with 8-byte results is an obvious candidate for buffering. strace -T shows the time in each call, which finds the slow ones, such as an fsync of 8 ms or a futex wait of 200 ms. Remember that strace itself slows the program by 10 times or more, so use it for counts and patterns, not for timing a fast path; perf trace or eBPF costs much less.
intuition: A bank teller window: you cannot walk into the vault, but you can slip a request through the window, and the teller checks it and does the work for you.
The design is natural because protection needs a narrow, well-guarded entrance. If everyone could jump anywhere in the kernel, there would be no protection. By making the entrance a single instruction with a number and some registers, the kernel can check everything before it acts, and the hardware can guarantee that the caller returns in user mode afterwards. Every request has a fixed cost for crossing the window, so you do better with one large request than with many small ones.
mistakes: People often think a system call is just a function call. In fact it changes privilege level, switches stacks, may switch page tables, validates arguments, and may block. It costs 50 to 100 times more than a plain function call, and it can take milliseconds if it sleeps.
People often think that read() and write() always transfer the number of bytes requested. In fact they can return less (a short read or write) because of a signal, a full pipe or socket buffer, or the end of the file. Correct code loops until all bytes are processed and handles EINTR and EAGAIN.
People often think the C library function and the system call are the same thing. In fact libc adds buffering (fopen, fread), caching (getpid used to be cached), and error translation. printf calls write only when its buffer is full or flushed, and some "system calls" such as clock_gettime never enter the kernel because of the vDSO.
People often think that fewer system calls always means faster code. In fact the data copying and the work inside the kernel often dominate. Batching helps when calls are small and frequent; for 1 MB writes the crossing is negligible.
People often think a system call is secure because the kernel checks it. In fact the large and complex interface is the main attack surface of the kernel, and many privilege-escalation bugs are bugs in a system call handler. That is why sandboxes filter the list with seccomp.
tradeoffs: Choose plain blocking calls with buffering when the program handles moderate rates (thousands of calls per second per thread) and clarity matters. Choose batching interfaces (readv/writev, sendmmsg, epoll, io_uring) when profiles show a large share of time in kernel entry and exit, typically above 100,000 calls per second per core. You pay with more complex code, and with io_uring a larger attack surface.
Choose to stay in user space (vDSO calls, user-space networking such as DPDK, or kernel-bypass libraries like SPDK) when the cost per operation must be a few hundred nanoseconds. You give up the kernel's sharing, protection and ready-made protocols; your program must poll and own the device, and typically needs dedicated cores.
Choose a tight seccomp filter (allow-list of calls) for processes that handle untrusted input, such as parsers and code sandboxes. You reduce the kernel attack surface, but you must maintain the list as libraries change, and an incomplete list crashes the program with a hard-to-read error.
Choose the vDSO clock calls rather than reading time with a system call, and cache a timestamp when millisecond resolution is enough. You give up precise per-operation time, but you save a call per event. Choose to leave mitigations (KPTI and Spectre fixes) on in multi-tenant systems; turn them off only on machines that run fully trusted code with CPUs that do not need them, accepting the risk.
friction: The per-call overhead is not constant. It has risen since 2018 because of mitigations, and it differs by CPU generation: newer processors with hardware fixes pay less. The indirect cost (cache and branch-predictor pollution) is hard to measure and does not appear in the time of the call itself.
Blocking calls are a problem for scalability. A thread that waits in read() cannot do other work, so a server must have a thread per waiting request, or switch to non-blocking and readiness APIs, which are harder to program. Not all calls have non-blocking forms: file reads and metadata operations such as stat and open have no true non-blocking mode on most systems, so event-loop runtimes use thread pools for them.
The interface is large and subtle. Calls have many flags and edge cases (EINTR restarts, short writes, signal races, behaviours that differ across file systems), and programs written without care work in tests and fail in production. New calls are added over time (io_uring_enter, openat2, clone3), so the old ones remain for compatibility, and the same function can be done in several ways with different guarantees.
Security remains the hardest topic. A bug in any handler, or in the code that checks user pointers, can give an attacker kernel control. Confused-deputy and time-of-check-to-time-of-use races occur, because user memory can change after the kernel read it. Seccomp filters decide by call number and arguments but cannot look into memory a pointer refers to, which limits what they can check.
practice: Know your call profile. Use strace -c -f for a first look at counts, perf trace or bpftrace for lower-overhead views, and check for patterns: tiny reads and writes, repeated stat or open calls on the same path, frequent getrandom or clock calls, many futex calls. Fix by buffering, caching results, batching, or by using a better interface.
Use buffered streams for text and small records: set a 64 KB to 1 MB buffer for file readers and writers, and flush at logical boundaries. For network servers, write one response in one call (writev for header and body), use epoll or an async runtime, and consider sendfile for static files. Tune the number of syscalls on the hot path with measurements, not by instinct.
Always handle partial results and errors: loop on read and write until the count is complete, retry on EINTR (or set SA_RESTART), treat EAGAIN as "try later", and check the result of close(). In languages with runtimes (Java, Go, Python) check how the standard library batches system calls; a Java FileInputStream.read() with no buffer does a system call per byte.
In containers, use the default seccomp profile or a stricter one, and know that io_uring is blocked in some default profiles and environments. When you need very low latency timestamps, rely on clock_gettime (vDSO). When reviewing performance on a new machine type or kernel, re-measure the cost of a trivial call, because mitigations change between kernel and CPU versions.
interview: Walk through what happens between write() in user code and the data reaching the file system. || The libc wrapper loads the call number and arguments into registers and executes syscall. The CPU saves the return address, switches to kernel mode and jumps to the fixed entry point. The kernel switches stacks, saves registers, indexes the table, and runs ksys_write: it maps fd to a struct file, checks arguments, copies from the user buffer, and calls the file system's write, which updates the page cache. It returns through sysret with the byte count or a negative errno.
Why did system calls become more expensive in 2018, and what reduces the cost? || Meltdown required kernel page-table isolation, so the kernel unmaps most of its memory while in user mode and must switch page tables on each entry and exit; Spectre fixes added barriers. PCID avoids full TLB flushes, newer CPUs with hardware fixes avoid some mitigations, and the main software answer is making fewer calls.
How does the vDSO work and which calls use it? || The kernel maps a small shared object into each process and keeps data such as the current time in a read-only page that it updates. Calls like clock_gettime, gettimeofday and time read that page in user mode, so they avoid the trap. It works only for calls that read data the kernel can publish without per-call checks.
You see 500,000 read calls per second on a service, each returning a few bytes. What do you do? || Find the call site with strace/perf trace or a profiler, then add buffering or a larger read size, or use readv, mmap or a different protocol framing. Check whether the data comes from a socket or a file, and verify that the new version reduces CPU and p99 latency, not only the call count.
When is it right to bypass the kernel, and what do you lose? || When per-operation costs must be below what a system call allows (packet processing at tens of millions per second, NVMe at millions of IOPS). Kernel-bypass libraries poll devices from user space on dedicated cores. You lose the kernel's protocol stack, fair sharing, security isolation and tooling, and must handle everything yourself.
quiz: Why can a user program not read a disk block directly? || User mode is not allowed to run privileged instructions or access device memory. The program must ask the kernel through a system call, and the kernel checks permissions before doing the I/O.
What is the role of the number in rax at a system call on x86-64 Linux? || It selects which kernel service to run: the kernel uses it as an index into the system call table. For example, 0 is read and 1 is write.
A loop calls write() with 1 byte 50 million times. Each call costs 150 ns of crossing. How much time is crossing overhead, and what is the fix? || 50,000,000 × 150 ns = 7.5 seconds. Buffer the bytes in user memory and write in blocks of 64 KB or more, which reduces the calls by about 65,000 times.
Why is clock_gettime so much cheaper than getpid-style calls in many programs? || It is served by the vDSO, which reads a time value the kernel keeps in a page mapped into the process, so no mode switch happens. A true system call has to trap into the kernel.
Your team wants to run untrusted plugins in a process. What would you do with system calls? || Run them in a sandbox with a seccomp allow-list that permits only the calls they need (and no new process creation, no raw sockets), often together with namespaces and cgroup limits. This lowers the kernel attack surface but needs careful testing of the list.

@@ filesystems
value: A file system turns a raw array of numbered blocks (4 KB each, on an SSD or disk) into the thing programs actually use: named files in a tree of directories, with sizes, permissions and timestamps, that can grow, shrink, be renamed and survive a power cut. The device offers only "read block 9,431,207" and "write block 9,431,207". The file system decides which blocks belong to which file, where to put new data, how to find a name quickly, and how to leave a consistent structure on disk if the machine stops in the middle of a change.
Almost all data that you manage sits on one. A Kafka log segment is a file. A RocksDB SSTable is a file. A Spark shuffle block, a Parquet file in a local cache, a container image layer, a checkpoint and a database write-ahead log are all files on ext4 or XFS. Their speed and safety are set by what the file system does: how it lays out a large file (one run of blocks or thousands of fragments), what it guarantees after a crash, how fast it creates a file, and what rename and delete cost. Object stores such as S3 look similar but are different: they have a flat key space, no real directories and no cheap rename, which shapes how lakehouse table formats are built.
The file system stands on four lower ideas. Trees (L3) give the structure: directories form a tree, and extent maps and large directories are B-trees. Graph theory (L4) names the shape: a directory hierarchy is a rooted tree, and hard links make files a directed acyclic graph, which is why directories cannot be hard-linked. Storage devices (L3) set the physical rules: block size, seek time on disks, erase blocks on flash. File-system journaling (L3) gives crash safety by writing intended changes to a log first. Above it sit logs, LSM trees, segment files, shuffle and snapshots, which all assume that files can be appended, renamed atomically and deleted whole.
terms: Block — the unit of allocation, usually 4 KB; a file always occupies a whole number of blocks.
Inode — the on-disk record of a file: size, owner, permissions, timestamps, link count, and where its data blocks are; it does not contain the name.
Directory — a special file that maps names to inode numbers.
Extent — a run of contiguous blocks described by a start block and a length, which replaces a long list of single block numbers.
Superblock — the record at a known location that describes the whole file system: block size, block counts, feature flags.
VFS (virtual file system) — the kernel layer that gives every file system the same interface (open, read, write) and caches names and inodes.
Dentry cache — the in-memory cache of directory entries, so that a path lookup does not read the disk again.
Hard link / symbolic link — a hard link is another name for the same inode; a symbolic link is a small file that contains a path.
Copy-on-write file system — a design that never overwrites a block in place but writes a new copy and then switches a pointer (ZFS, Btrfs).
history: Multics (1960s) introduced the hierarchical file system with directories, and Unix (1971) made it simple: a superblock, a table of inodes, and data blocks; a directory is just a file of (name, inode number) pairs. The first design was clean but slow. On a disk with 8 ms seeks, a file system that scattered a file's blocks spent most of its time moving the head. The Berkeley Fast File System (McKusick, Joy, Leffler and Fabry, 1984) fixed this with larger blocks, cylinder groups that keep a file's inode, data and its directory near each other, and smarter allocation. Most later designs follow this pattern of grouping related data.
The next problem was crashes. After a power failure, the file system could be inconsistent (an inode points to a block that is marked free, a directory entry points to nothing). The repair tool fsck scanned the whole disk, which took hours on large volumes. Journaling solved it: write the intended metadata changes to a log, then apply them. IBM's JFS (1990), SGI's XFS (1993, ported to Linux in the early 2000s), NTFS (1993) and Linux ext3 (2001, Stephen Tweedie) used it. Rosenblum and Ousterhout's log-structured file system (1991) went further and made the whole disk a log.
ZFS (Sun, 2005, Jeff Bonwick and Matt Ahrens) and Btrfs (Chris Mason, 2007; in Linux since 2.6.29, 2009) used copy-on-write trees with checksums, which made snapshots cheap and detected silent corruption. ext4 (Linux 2.6.28, late 2008) extended ext3 with extents, delayed allocation and larger limits, and it remains the most common default on Linux. XFS became the default of Red Hat Enterprise Linux 7 in 2014 because it scales to large files and many threads. F2FS (2012) was designed for flash.
Research since then has focused on the gap between promises and behaviour. Pillai et al. (OSDI 2014) tested real file systems and showed that applications depend on ordering guarantees that differ between ext4, XFS and Btrfs, and many applications were not crash-safe. Cloud storage changed the picture again: Amazon S3 offers objects, not files, and lakehouse formats such as Delta Lake and Iceberg add the missing atomic commit on top.
how: Start with the on-disk layout of an ext4-like system. The disk is divided into block groups (128 MB each with 4 KB blocks), and each group holds a bitmap of free blocks, a bitmap of free inodes, a table of inodes and then the data blocks. A superblock at the start describes the whole file system. Putting inodes and data for related files in the same group keeps the disk head, or the SSD's access pattern, local. ext4 fixes the number of inodes when the file system is made (by default one per 16 KB of space), so a volume can run out of inodes while it still has free space; df -i shows it.
A file is its inode. The inode records the size, owner, mode, times, a link count and the location of the data. Old Unix systems (and ext2, ext3) stored 12 direct block numbers, then a pointer to an indirect block of pointers (1,024 of them with 4 KB blocks and 4-byte numbers), then double and triple indirect blocks. This reaches large files but needs several reads to find a block far into the file, and a 1 GB file needs 262,144 pointers. ext4 and XFS use extents instead: an entry says "logical blocks 0 to 32,767 are at physical block 5,000,000", which describes up to 128 MB in 12 bytes. ext4 keeps up to four extents in the inode itself; more are held in a tree of blocks, a B-tree whose nodes are one block each. With a 4 KB block and about 250 entries per node, a three-level tree describes about 15 million extents, so finding any block of any file needs at most a few block reads, and usually none, since the nodes are cached.
A directory is a file whose data is a list of (name, inode number) entries. Looking up a name in a small directory scans the list. For large directories, ext4 uses a hashed B-tree index (htree) keyed by a hash of the name, and XFS uses B+trees, so a lookup in a directory with a million names reads about three blocks. The file name lives only in the directory, so one inode can have many names (hard links), and the file's data is freed only when the link count and the open file count are both zero. Resolving /var/log/app.log means: read the root inode, find "var" in the root directory, read that inode, find "log", and so on. Each step is a lookup; the VFS keeps a dentry cache of results, so a warm path lookup takes tens to hundreds of nanoseconds and no I/O.
Writing allocates blocks. When a program appends 1 MB, the file system does not choose blocks at write() time. Delayed allocation keeps the data in the page cache and picks blocks when the pages are written back. By then it knows how much data there is, so it can find one long free run and create one extent. The result is less fragmentation and fewer metadata updates. Programs that know the size in advance can call fallocate to reserve space and avoid failures later.
Crash safety is the job of the journal (journaling concept). A single create or append changes several structures: the block bitmap, the inode, the directory and the extent tree. If the machine stops between those writes, the structures disagree. The journal records the set of changed metadata blocks as one transaction in a log area, writes a commit record, and only then writes the blocks to their real places (checkpointing). After a crash the system replays committed transactions and ignores incomplete ones, which takes seconds instead of the hours of a full fsck. ext4's default data=ordered mode journals only metadata but forces data blocks to disk before the metadata that points to them is committed, so a file never points at garbage. It does not make a write durable: that needs fsync.
Copy-on-write systems take another route. ZFS and Btrfs never overwrite a live block. A change writes new blocks for the data and for each tree node up to the root, then updates the root pointer in one atomic step. The old tree stays valid until the pointer moves, so no journal is needed, snapshots are only a saved old root, and each block pointer can carry a checksum. The costs are write amplification (changing one block rewrites a path of nodes), fragmentation of files that are updated in place, and more complex space accounting.
Everything is reached through the VFS, which defines common objects: the superblock, the inode, the dentry and the open file. A file system implements operations such as lookup, read_iter and write_iter, and the VFS provides the caches and the system call layer. This is why the same read() works on ext4, XFS, NFS, tmpfs and overlayfs, which stacks layers for containers.

example: Work out how a 10 MB file is described. With 4 KB blocks it has 2,560 blocks. In the old ext2 style, the inode holds 12 direct pointers (48 KB), then one single-indirect block holding 1,024 pointers (4 MB), so 4 MB + 48 KB are reached. The rest of the file, about 6 MB, needs the double-indirect block, which points to indirect blocks that point to data. To read the last block the system reads up to two extra metadata blocks, which are usually cached. In an extent-based system, if the 10 MB were written in one go and the free space is contiguous, the whole file is one extent: a start block and a length of 2,560. The inode holds it directly, and no extra metadata block is needed. If the file grew slowly in small appends mixed with other files, delayed allocation still groups writes into a few extents.
Now see what a crash does. A program appends 8 KB to a log file. The file system must update the block bitmap (mark two blocks used), the inode (new size and extent), and perhaps the directory times. In ext4 these metadata blocks are written to the journal as one transaction, a commit record follows, and later the blocks are written in place. If power fails before the commit record is on disk, the transaction is discarded, and the log has its old size: the append is lost but the file system is consistent. If power fails after the commit record, replay applies the changes and the new size is correct. In ordered mode, the data blocks were written before the commit, so the new size never points to unwritten garbage. What is not promised is that the append is on disk at the time write() returns: for that you need fsync.
Finally, the atomic replace pattern used by many programs. To update config.json safely, write config.json.tmp completely, call fsync on it, call rename("config.json.tmp", "config.json"), and call fsync on the directory. On POSIX file systems, rename replaces the name atomically: any other reader sees the old file or the new one, never a mixture. The two fsyncs make the data and the name change durable in the right order. On an object store like S3 there is no rename; a "rename" is a copy of every byte followed by a delete, and not atomic for a prefix with many objects, which is why table formats use a transaction log and an atomic put-if-absent on a manifest.
intuition: A library catalogue that remembers which shelf holds each part of each book, and writes a note of every change before moving any books.
The design is natural because it splits two problems that a disk cannot solve itself. Names are for people and need a tree that is quick to search. Blocks are for the device and need large contiguous runs. The inode is the bridge: it holds the data location and everything except the name. Extents and B-trees keep that bridge small and fast for any file size. The journal handles the one thing that cannot be avoided: a change is never one write, so a crash can land in the middle. By logging first, you turn many small writes into one atomic decision.
mistakes: People often think a file's name is part of the file. In fact the name is an entry in a directory, and the inode, which holds the data location, has no name. This is why rename is a cheap directory edit, why one file can have several hard links, and why you can delete a file that a process still has open.
People often think that a journaling file system protects your data. In fact it protects the file system's own structure. By default ext4 journals metadata only. Your data can still be lost or partly written after a crash unless you call fsync and design your file format for it.
People often think that rename is safe to use for atomic updates without fsync. In fact rename is atomic with respect to other processes, but after a crash the new file's data may not yet be on disk. Early ext4 systems showed zero-length files after crashes in 2009 for this reason, and the file system added heuristics for the replace-by-rename pattern. A correct program syncs the file first.
People often think that "no space left on device" always means the disk is full. In fact it may mean the file system has run out of inodes (many small files), or that a quota or reserved-block limit is reached. Check df -h and df -i.
People often think that object storage is a file system with a different API. In fact it has no directories, no atomic rename and no append, and listing a "folder" is a prefix scan. Software written for POSIX file systems, including some Spark committers, behaves differently or slowly on it.
tradeoffs: Choose ext4 when you want a mature default for general servers, boot disks and moderate-size volumes, with strong tooling and predictable behaviour. Choose XFS when you have very large files and file systems (tens of terabytes), many parallel writers, or heavy Kafka, database or analytics workloads; XFS spreads work across allocation groups and scales better with many threads. XFS cannot be shrunk, while ext4 can be shrunk offline.
Choose a copy-on-write file system (ZFS, Btrfs) when you want snapshots, checksums for silent corruption, compression, or send/receive replication, and you accept write amplification, fragmentation on update-in-place workloads like databases (usually tuned with recordsize or no-COW flags), and more memory use. Choose a plain journaling file system under a database that already checksums and logs its own data.
Choose few large files over many small files for data pipelines. One file means one inode, a few extents and sequential reads; a million tiny files cost a million creates, opens and directory entries, and each open is a few microseconds to milliseconds on a network file system. This is the small-file problem, and the reason why compaction exists. You give up fine-grained updates, which is why immutable files plus compaction (LSM trees, Delta) are common.
Choose local disks with a POSIX file system for low-latency state (RocksDB, shuffle spill), and object storage for durable, shared, cheap data. Local disks give microsecond access, rename and fsync; object storage gives practically unlimited capacity, high durability and cost around a few cents per GB-month, but with tens of milliseconds per request and no atomic rename. Many systems use both: local cache over object store.
friction: Crash behaviour is the hardest part. Applications assume that if they write A and then B, a crash leaves A without B. Whether this holds depends on the file system, its mount options and the kind of operation. Pillai et al. found that many programs relied on guarantees that only some file systems gave. The only reliable way is to use fsync at the right points, follow a known pattern (write to a temporary file, fsync, rename, fsync the directory), and test with crash-injection tools.
Metadata-heavy work is slow. Creating, listing and deleting millions of files is bound by journal commits, locking on directories and inode allocation. Operations like ls -l or du touch every inode. On network file systems every operation also has a round trip. On a flash device, small files and frequent metadata updates also cause write amplification.
Fragmentation and ageing still happen. A file system that is nearly full cannot find long free runs, so large files are split into many extents; copy-on-write systems fragment faster when files are rewritten in the middle. SSDs hide much of the seek penalty, but small extents still mean more metadata and more I/O requests. Keeping 10 to 20% of the space free is a common rule.
The interface is old and weak in some respects. POSIX gives limited atomicity (no multi-file transactions), loose rules for error reporting, and timestamps that cost writes. File systems differ in details such as maximum names, case sensitivity, and extended attributes. Finally, repair is a risk: an fsck on a multi-terabyte volume with millions of files can take hours, and a bug in the file system code can corrupt a large amount of data. This is one reason that large cloud systems prefer simple append-only files above the file system and replicate the data.
practice: Pick the file system by workload and keep to mainstream choices: ext4 or XFS for servers, with XFS preferred for large volumes and heavy concurrent I/O. Use the mount options that your database or broker documents, for example noatime to avoid a metadata write on every read, and keep the defaults for the journal unless you have a measured reason. Leave free space and monitor both df -h and df -i.
Design for the file system. Prefer large, append-only or immutable files that are written once and deleted whole (log segments, SSTables, Parquet files). Preallocate with fallocate when you know the size. Spread files over directories to avoid a single directory with tens of millions of entries. For atomic updates use write-temp, fsync, rename, fsync-directory. Do not assume ordering between files without fsync.
Know your layers. In containers, the writable layer is overlayfs and is slow for write-heavy paths, so put data on a mounted volume. On cloud VMs, local NVMe has different durability than network volumes; instance-store data disappears when the instance stops. On object storage, never depend on rename or list-then-act for correctness; use a table format or conditional writes. S3 has offered strong read-after-write consistency since December 2020 and added conditional writes in 2024.
Observe it. iostat shows device-level utilization and latency, perf and eBPF tools (ext4slower, xfsslower in bcc) show slow file operations, and strace -T shows slow opens and fsyncs. Check the number of open files and inode usage. Test failure: use power-cut or fault-injection tools (for example dm-flakey, dm-log-writes, or CrashMonkey-style tests) for systems that claim durability.
interview: Explain what an inode is and why the file name is not in it. || An inode is the on-disk record of a file: metadata plus the location of its data (block pointers or extents). Names are in directories as (name, inode number) pairs. This allows hard links, cheap rename and deleting an open file, since the data is freed when the link count and open count reach zero.
Why do ext4 and XFS use extents and B-trees rather than lists of block numbers? || A list needs one entry per block (262,144 for 1 GB with 4 KB blocks) and indirect blocks to hold it. An extent covers a whole contiguous run in a few bytes, and a B-tree with high fan-out finds any extent in a few block reads. Both reduce metadata size and the number of I/Os.
A process writes a file, calls rename onto the real name, and the machine crashes. After reboot the file is empty. What happened and how is it prevented? || The rename was committed in the journal, but the data blocks had not been written because of delayed allocation, so the new name pointed to an empty file. Prevent it by fsync-ing the temporary file before the rename, and the directory after it. Some file systems add heuristics for this pattern, but portable code must not rely on them.
Why is a data lake with millions of small files slow, and what do you do? || Each file costs listing, open, metadata and task-scheduling overhead, and small reads cannot use sequential bandwidth. On object stores every request has tens of milliseconds of latency. Compact into files of hundreds of megabytes, partition sensibly, and use a table format with metadata so engines read only the files they need.
How do copy-on-write file systems provide snapshots and crash consistency without a journal? || They write modified blocks to new places, build new tree nodes up to the root, and flip the root pointer atomically. The old root still describes a consistent tree, so a crash leaves either the old or the new state. A snapshot is simply a retained old root. The cost is write amplification and fragmentation.
quiz: What does a directory contain? || A list of (name, inode number) entries. The inode, which holds the size, permissions and data location, is found by number; the name is not stored in the inode.
Why do extents reduce metadata compared with block pointers? || One extent (start block and length) describes a whole contiguous run, up to 128 MB in ext4, instead of one pointer per 4 KB block.
A volume has 1 TB of space and one inode per 16 KB. How many inodes does it have, and what failure can follow? || About 1 TB / 16 KB = 64 million inodes. If you create more than 64 million files you get "no space left on device" even with free blocks.
Why does delayed allocation help, and what is its risk? || Waiting until writeback lets the file system see the whole run of data and allocate one contiguous extent, which reduces fragmentation. The risk is that data not yet allocated or written is lost on a crash, and renaming a new file without fsync can expose an empty file.
You must store 500 million small records for a batch job. Local files per record, or fewer large files? || Fewer large files. Per-record files would cost 500 million inodes, directory entries and opens, and would be slow to create, list and delete. Large files with an index, or a columnar format, give sequential I/O and low metadata cost.

@@ fsync
value: When write() returns, your data is almost never on the disk. It is in the kernel's page cache, and perhaps in a volatile cache inside the drive. If the power fails now, it is gone. fsync(fd) is the call that closes this gap: it returns only after the file's data, and the metadata needed to find it, have been written to stable storage, meaning storage that keeps its content without power. It draws the line between "written" and "durable".
That line decides what a database can promise. A bank that tells a customer "your transfer is done" must not lose the transfer in a power cut. A write-ahead log, a Raft node that votes, a Kafka broker that acknowledges a message with acks=all, and a file editor that saves a document all depend on fsync for this. The price is high. A write() into the page cache costs about 1 to 2 microseconds. An fsync costs about 8 ms on a spinning disk, roughly 0.5 to 3 ms on a consumer SSD, and 20 to 100 µs on an enterprise NVMe drive that has capacitors to survive power loss. That gap of 100 to 5,000 times is why durability is the main cost of a commit and why systems batch commits.
fsync stands on the physical device (storage devices, L3). A drive has its own volatile write cache, and a flash drive writes through a translation layer that remaps blocks. So fsync is not complete when the kernel has sent the data: the kernel must also tell the drive to flush its cache (a FLUSH command or a write with the FUA flag, "force unit access"), and the drive must really obey. The layers above rely on this contract: the log is durable before the data page is changed, a vote is durable before a reply is sent, and a journal commit is durable before the changes are applied in place.
terms: Durability — the guarantee that data acknowledged as written survives a crash or power loss.
Stable storage — storage whose content survives power loss, such as flash, disk or battery-backed memory.
Volatile write cache — fast memory inside a drive that holds data before it reaches the media; its content is lost on power failure unless the drive has protection.
Flush (cache flush) — a device command (SATA FLUSH CACHE, NVMe Flush) that makes the drive write all cached data to its media before it completes.
FUA (force unit access) — a flag on one write that asks the drive to put that write on stable media before reporting completion.
fdatasync — like fsync, but skips metadata that is not needed to read the data back (such as the modification time).
Group commit — a technique where many transactions share one fsync, so the cost is divided among them.
Power-loss protection (PLP) — capacitors in an enterprise SSD that let it finish writing its cache after power fails, which makes flushes cheap.
history: The problem is as old as caching. Unix had sync() to flush all buffers, and fsync() for one file arrived in 4.2BSD (1983). For some decades it was used by databases and little else, since desktop programs took the risk. The need grew with write-ahead logging, formalised in ARIES (Mohan et al., 1992): a transaction commits when its log record is on stable storage, so every commit contains an fsync of the log.
Drives made it harder. From the 1990s, disks had write caches that reordered and delayed writes, and some firmware acknowledged a flush without performing it. Linux added "write barriers" in the 2.6 series (about 2005 to 2009) so that file systems could order journal commits, and in 2.6.37 (2010) replaced barriers with explicit flush and FUA flags in the block layer. In 2009 ext4's delayed allocation showed users empty files after crashes, because programs wrote and renamed without fsync; Ted Ts'o explained that POSIX never promised more, and the file system added workarounds.
Research then measured the gap. Zheng et al. (FAST 2013) cut power to SSDs during writes and found that many lost acknowledged data or corrupted it. Pillai et al. (OSDI 2014) showed that applications depend on file-system ordering that is not guaranteed. Dan Luu's 2015 essay "Files are hard" popularised the point that correct crash-safe code is rare.
The most important event for fsync itself was "fsyncgate" in 2018. Craig Ringer reported on the PostgreSQL mailing list that Linux could mark pages clean after a failed write-back, so a second fsync on the same file returned success although the data was never written. PostgreSQL had retried fsync for years on that assumption. The PostgreSQL project changed to stop with a PANIC on fsync failure, in the minor releases of February 2019 and in version 12, and the Linux kernel improved error reporting (errseq_t, in 4.13 and later). Rebello et al. (USENIX ATC 2020) then tested how file systems and applications behave after a failed fsync and found that many cannot recover.
how: Start with the layers that hold your data between write() and the media. The program may have its own buffer (for example in stdio or a Java stream). Calling write() copies it into the kernel page cache and marks the pages dirty. The file system keeps a journal. The block layer queues requests to the device. The device has a volatile cache. And finally the NAND flash or magnetic media holds the data. Each layer can lose data on power failure, and each needs its own step to push the data down.
The call fsync(fd) does these steps in the kernel. First, it finds the dirty pages of the file in the page cache and writes them to the device, and waits for completion. Second, it makes the file system's metadata durable. On ext4 it asks the journal to commit the running transaction: the journal blocks (inode, extent tree changes, bitmaps) are written, followed by a commit record. For safety the commit record is written after a cache flush, and with FUA or another flush after it, so the device cannot reorder the commit before the blocks it covers. Third, the block layer sends a flush command, so that data still in the drive's cache reaches the media. The call returns only after all of these have finished.
So one fsync is really two or three sequential device operations: the data write, the journal write with a flush, and the flush after the commit. That is why fsync on a file system with a journal can cost two to three times the device's write latency, even for one 4 KB append. fdatasync can skip the journal commit when only the modification time has changed, and it is therefore faster for overwrites in a pre-allocated file. When the file size changes, it must also be made durable, so appending still involves the journal.
There are other ways to ask for the same thing. open(O_SYNC) makes every write behave as if followed by fsync; O_DSYNC does it as fdatasync. O_DIRECT bypasses the page cache but does not by itself guarantee durability, as the data may still sit in the drive cache; on most systems you still need a flush or the FUA-based O_DSYNC. sync_file_range() starts or waits for write-back of a range, but it does not flush the device cache or metadata and is not a durability guarantee. msync() is the equivalent for memory mappings.
Directories need care. A newly created file has two parts: its data and its name in a directory. fsync on the file persists the data and its inode; POSIX does not promise that the directory entry is persisted. Linux file systems often persist it for you, but portable code calls fsync on the parent directory after creating or renaming a file. The same applies to a rename used as an atomic replace.
Now the device side, which is where the lower layer matters. A hard disk with a write cache loses its content if power fails, so the flush command forces the head to write the cached sectors, taking at least one rotation (8.3 ms at 7,200 rpm) in the worst case. A consumer SSD buffers writes in DRAM and flash pages, and a flush makes it program the NAND, which takes about 0.5 to 3 ms. An enterprise SSD with power-loss protection treats its cache as non-volatile, so a flush returns almost immediately, and an fsync costs only the write itself, 20 to 100 µs. A cloud network volume adds a network round trip and replication, so an fsync typically takes about 0.5 to 2 ms. Therefore the same code gives 100 commits per second on one machine and 20,000 on another.
Because the cost per fsync is fixed and mostly waiting, systems amortize it. Group commit works as follows: when several transactions are ready to commit, one of them issues the fsync for the log up to the latest record, and all the others wait for it and share the result. If the fsync takes 1 ms and 32 transactions arrive during that time, throughput is about 32,000 commits per second instead of 1,000, and each commit sees a latency of 1 to 2 ms. PostgreSQL, MySQL's InnoDB, etcd, Kafka's log and Raft implementations all do some form of it. The trade is a slightly higher latency for the first committer in a group, in exchange for much more throughput.

example: Measure the cost with a simple loop: append 4 KB to a file and call fsync after each append. On a machine whose fsync takes 1 ms, the loop reaches about 1,000 appends per second, which is 4 MB/s. Remove the fsync and the same loop reaches several hundred thousand appends per second (each write is 1 to 2 µs), but nothing is safe. The ratio is about 500 to 1000 times. On a spinning disk with 8 ms flushes, the loop gives about 120 commits per second; this is the reason older databases were limited to a few hundred transactions per second per disk. On an NVMe with PLP at 50 µs the loop gives 20,000 commits per second, with no batching at all.
Now add group commit. A database receives 5,000 transactions per second, each needing a durable log record, with 1 ms fsync. Without batching, the system needs 5,000 fsyncs per second but can do only 1,000, so a queue builds up without limit. With group commit, while one fsync is running (1 ms), about 5 new transactions arrive; the next fsync covers those 5. The system issues about 1,000 fsyncs per second, each covering 5 transactions, keeps up with the load, and each transaction waits for about 1 to 2 ms (the remainder of the current fsync plus its own). If the load grows to 20,000 per second, groups grow to 20, and it still works. The fsync is the bottleneck only when the group is limited by something else, such as a single-threaded committer.
Finally a failure case. A process appends to a log, calls fsync, and gets EIO because the SSD returned an error for a block. If the program retries fsync and receives success, it may believe the data is durable. In older kernels, the failed pages were already marked clean, so the second call reports success while the data is lost; in newer kernels the error is reported once per open file description, and later calls may still succeed because the dirty pages were dropped. The safe response is the one PostgreSQL adopted: treat the first fsync error as fatal, stop, and recover from the log after restart, instead of retrying.
intuition: Saying "it is in the post" versus "the recipient has signed for it".
write() hands the letter to a clerk who puts it in a tray; the tray may burn down. fsync waits until the receiver has signed. The design is natural because storage is built in layers of caches, each faster and less safe than the one below, and the only way to know that data is safe is to follow it to the bottom and wait for confirmation. The cost is the time of the slowest step, and the way to reduce it is to send many letters in one delivery.
mistakes: People often think write() followed by close() makes data durable. In fact close() does not flush anything to the device. The data sits in the page cache until write-back, which can be 30 seconds later, or until fsync.
People often think fsync returning success means the data is on the media, always. In fact it means that the kernel received success from the device. Some devices acknowledge flushes while data is still in volatile memory, some virtualised or misconfigured setups ignore flushes, and macOS fsync() does not flush the drive cache (F_FULLFSYNC does). Trust requires a drive with power-loss protection and tests.
People often think a failed fsync can be retried. In fact after a failed write-back, the kernel may already have discarded the dirty pages or marked them clean, so a retry may succeed without writing anything. Treat a failure as a loss of the unflushed data and recover from the log; this is what fsyncgate taught.
People often think O_DIRECT, or sync_file_range, gives durability. In fact O_DIRECT bypasses only the page cache, and sync_file_range does not flush metadata or the device cache. Only fsync, fdatasync, O_SYNC and O_DSYNC (with a drive that obeys) have the durability contract.
People often think that fsyncing the file is enough after creating it. In fact the directory entry is separate, and portable programs must also fsync the containing directory so the name survives.
tradeoffs: Choose fsync on every commit (synchronous durability) when losing one acknowledged transaction is not acceptable: payments, metadata stores, consensus logs. etcd, for example, expects the 99th percentile of WAL fsync to stay under about 10 ms. You pay with commit latency of one device flush, and a need for fast disks. Choose periodic flushing (every 100 ms to 1 s, such as Redis appendfsync everysec, MySQL innodb_flush_log_at_trx_commit=2, Cassandra's periodic commit log) when you can lose up to one interval of data on a machine crash, and need throughput. You give up the guarantee for the last interval after power loss, though not after a process crash, since the data is in the page cache.
Choose replication instead of local fsync when you have several machines that fail independently. Kafka by default does not fsync per message, and relies on in-sync replicas: a message acknowledged by all of 3 replicas is lost only if all of them fail before flushing. You give up protection against correlated failures such as a data-centre power cut; Choose fsync as well when that matters or when a cluster can restart together.
Choose group commit with a short delay when throughput matters and the latency of 1 or 2 ms is acceptable; choose no delay when tail latency matters most and the load is low. PostgreSQL's commit_delay is off by default for this reason. Choose fdatasync with pre-allocated files over fsync with growing files when the log is written constantly, since it avoids journal commits, accepting that you must zero-fill space in advance.
Choose enterprise drives with PLP for databases and logs. They cost more per GB, but make a commit 10 to 50 times faster than a consumer drive that must really program flash on every flush, and they close the window in which the device lies. Choose consumer drives only for data that can be rebuilt.
friction: The first problem is cost and variance. An fsync flushes more than your file: on ext4, the journal commit may include other files' metadata, so a busy system makes one program's fsync wait for another's (the "fsync stall" seen when a backup runs). Tail latencies of tens of milliseconds appear on shared disks. Cloud volumes add throttling and network jitter.
Error semantics are poor. The kernel reports a write-back error to the next fsync, but only once, to one open file description, and the pages may be lost. Applications cannot know which writes failed, and file systems differ in what they keep. Rebello et al. found that ext4, XFS and Btrfs behave differently and that applications such as Redis, LMDB and PostgreSQL mishandle some of them. The safest approach, to stop and recover, requires a log designed for it.
Trust in hardware is hard to check. A drive can acknowledge a flush early, a RAID controller with a battery may be configured as write-back, and virtualisation can drop flushes. Power-fault tests exist but are costly, and most teams never run them. A cluster that loses power at once can lose acknowledged data on every replica.
The programming model is subtle. You need fsync on the file, on the directory, in the right order, and the combinations differ across file systems and operating systems (macOS, Windows' FlushFileBuffers, network file systems that may cache). New devices such as persistent memory and zoned storage change the primitives (cache-line flush instructions instead of fsync), and the old interface does not map well.
practice: Know what you promise and measure its price. Run a test on your actual disks before choosing hardware: pg_test_fsync (shipped with PostgreSQL) or fio with --fsync=1 or --fdatasync=1 reports fsyncs per second and latency. If you get 100 to 200 per second, you have a spinning disk or a drive that is honest and slow; if you get 100,000 per second on a consumer SSD, ask whether it is lying.
Follow safe patterns. For a log, preallocate, append, and use fdatasync with group commit. For replacing a file: write a temporary file, fsync it, rename it over the target, then fsync the directory. Check every return value, including those of close and fsync. Treat an fsync error as fatal for that file, and recover from the log.
Choose settings for each system on purpose. In databases keep the safe defaults (PostgreSQL fsync=on and synchronous_commit=on, InnoDB flush at commit with sync_binlog=1 when you need it), and relax them only for data you can rebuild, such as a staging load. For Kafka, rely on replication.factor 3, min.insync.replicas 2 and acks=all; consider flush settings only when the cluster could lose all replicas at once. For etcd and other consensus systems, put the log on a dedicated fast disk and watch the fsync latency metric.
Operate with care. Use enterprise drives or cloud volumes with documented flush behaviour. Monitor write latency and fsync histograms (for example with eBPF tools such as biolatency, or the database's own metrics). Avoid sharing the log disk with backups or noisy neighbours. Test recovery by killing the machine, not only the process.
interview: What exactly does fsync do on ext4, and why can it cost more than one device write? || It writes the file's dirty data pages, commits the journal transaction (metadata blocks followed by a commit record, with flush or FUA to order them), and sends a cache flush to the device. These are sequential device operations, so one fsync can cost two or three write latencies. fdatasync can skip the journal commit if only timestamps changed.

Your service does 500 commits per second, each with an fsync of 2 ms. A team reports that Kafka lost acknowledged messages after a data-centre power cut although acks=all was set. Explain. || Kafka acknowledges after the data is in the page cache of all in-sync replicas, not after fsync. If all replicas lose power together, un-flushed data is lost on all of them. quiz: What is the difference between write() returning and fsync() returning? || write() returns when data has been copied into the page cache. fsync() returns after the data and needed metadata have been written to the device and the device cache has been flushed.

@@ iomodels
value: An I/O model is the answer to a simple question: what does your thread do while it waits for the disk or the network? A packet arrives in 50 microseconds or in 5 seconds; a disk read takes 100 microseconds; a thread cannot know in advance. In the blocking model the thread sleeps inside the call until the data is there. In the readiness model the thread asks the kernel "which of my 10,000 sockets can be read now?" and then reads only those. In the completion model the thread hands the kernel a list of operations to do and collects results later.
The choice sets how many connections or requests one core can serve. A thread per connection is simple, but 10,000 threads mean 10,000 stacks and many context switches. One thread that waits on all sockets at once with epoll can serve tens of thousands of connections, and this is how nginx, Node.js, Redis, Netty and Go's network poller work. Newer, io_uring (Linux 5.1, 2019) lets a program submit many reads, writes and accepts in one system call, or none at all, which matters for NVMe drives that do millions of operations per second.
Two lower ideas make this work. Interrupts (L3) are the source of all events: the network card or the disk raises an interrupt when a packet arrives or a transfer ends, the kernel handles it, and then wakes whoever is waiting. Ring buffers (L3, queues) give io_uring its design: two fixed-size queues in memory shared between the program and the kernel, one for requests and one for results, each written by one side and read by the other with no lock. The layers above, the event loop and the Linux kernel's server story, are built from these.
terms: Blocking I/O — a call such as read() that does not return until data is available or the operation is done; the thread sleeps meanwhile.
Non-blocking I/O — a call on a descriptor set with O_NONBLOCK that returns at once, with the error EAGAIN if no data is ready.
Readiness notification — the kernel reports that a descriptor is ready to read or write; the program then does the I/O itself (select, poll, epoll, kqueue).
Completion notification — the program submits an operation and the kernel reports when it is finished, with the result (IOCP, io_uring).
Level-triggered / edge-triggered — level: epoll reports a descriptor as long as it is ready; edge: it reports only when the state changes, so the program must read until EAGAIN.
Interest list / ready list — in epoll, the set of descriptors you registered and the subset that is currently ready.
Submission queue / completion queue — the two rings in io_uring: the program puts requests in the first, and the kernel puts results in the second.
Direct I/O (O_DIRECT) — I/O that bypasses the page cache and moves data directly between the device and a user buffer.
history: Unix started with blocking I/O: the process sleeps in read() and another process runs. For servers with many clients, the first tools were select() (4.2BSD, 1983) and poll() (System V, 1986). Both take the whole list of descriptors on every call and the kernel scans all of them, so the cost grows with the number of descriptors, not with the number of ready ones. select also has a fixed limit of 1,024 descriptors in its standard bit-set type.
By 1999 the web made this a pressing issue. Dan Kegel's "C10K problem" page asked how to serve 10,000 clients on one machine and surveyed the options. The answer was event notification where cost depends on active descriptors: FreeBSD's kqueue (Jonathan Lemon, 2000), Linux's epoll (Davide Libenzi, merged in kernel 2.5.44, 2002), Solaris event ports and Windows I/O completion ports (IOCP, since Windows NT 3.5, 1994). Servers built on them, nginx (2004), then Node.js (2009) and Redis (2009), made the single-threaded event loop common.
Disk I/O stayed awkward. Readiness does not fit files, because a regular file is always "ready" in the sense that a read will not wait for the sender, but it may still block for the disk. Linux had native asynchronous I/O (io_submit, libaio) from the 2.5 kernels, but it worked well only with O_DIRECT and could still block in other cases. Most runtimes used thread pools for file operations instead.
Jens Axboe's io_uring, merged in Linux 5.1 (May 2019), solved both problems with one design: shared rings for submissions and completions, usable for files, sockets and many other operations. It grew quickly with new operations (accept, send, recv, open, fsync, timeouts, multi-shot variants) and became the basis of runtimes such as Tokio-uring, Glommio and Seastar's reactor backend. It also became a security concern: Google reported in 2023 that about 60% of the exploit submissions to its kernel bug-reward program involved io_uring and disabled it on ChromeOS, Android apps and its production servers. Linux 6.6 added the sysctl kernel.io_uring_disabled to turn it off.
how: Begin with blocking I/O. A thread calls read(fd). If no data is in the socket's receive queue, the kernel puts the thread on that socket's wait queue and calls the scheduler, so the thread uses no CPU while it waits. When a packet arrives, the network card raises an interrupt; the kernel processes the packet, appends the data to the socket's receive queue, and wakes the threads on the wait queue. The thread runs again and read() returns. This is simple and efficient per operation. Its cost is one thread per concurrent wait: with 10,000 clients, 10,000 threads, each with a stack and kernel structures, plus context switches whenever one wakes.
Readiness with epoll puts many waits into one. The program calls epoll_create to get an epoll instance, then epoll_ctl(ADD) for each socket, with the events it cares about. The kernel stores the interest list in a red-black tree keyed by descriptor, and for each registered socket it adds a callback to the socket's wait queue. When data arrives and the socket's wait queue is woken, the callback (ep_poll_callback) appends that descriptor to the epoll instance's ready list, a linked list, and wakes a thread sleeping in epoll_wait. The program calls epoll_wait(epfd, events, 64, timeout) and receives an array of up to 64 ready descriptors. The cost depends on the number of ready descriptors, not on the number registered, which is the key difference from select and poll. For each ready socket the program calls read() on a non-blocking socket, processes, and writes the reply.
Two modes of epoll matter. In level-triggered mode (the default) a descriptor with unread data keeps being reported, which is forgiving: if you read only part, you will be told again. In edge-triggered mode (EPOLLET) you are told once per new arrival, so you must read until read() returns EAGAIN; it makes fewer wake-ups but is easy to get wrong, because leftover data is never reported again. EPOLLONESHOT disables a descriptor after one event, which helps when several threads share one epoll instance. When many processes wait on one listening socket, a new connection can wake them all (the thundering herd); EPOLLEXCLUSIVE (Linux 4.5) and SO_REUSEPORT (3.9, one listener per worker) avoid it.
Readiness has limits. A regular file cannot be added to epoll at all: epoll_ctl returns EPERM, and select or poll report files as always ready, so the read may still block on the disk. Therefore event loops send file reads to a thread pool (libuv does this) and wake the loop when done. Also, readiness is a hint: between epoll_wait and read, another thread may have taken the data, so non-blocking reads must handle EAGAIN.
Completion with io_uring changes the contract. At setup, the program asks the kernel for two rings and maps them into its address space with mmap. The submission queue (SQ) holds entries (SQEs) of 64 bytes: an opcode (read, write, accept, recv, fsync and so on), a file descriptor, a buffer address, a length, and a user_data tag. The completion queue (CQ) holds entries (CQEs) of 16 bytes: the user_data tag, the result (bytes transferred or a negative errno) and flags. Each ring is a single-producer, single-consumer ring buffer with a head and a tail index: the program advances the SQ tail and the kernel advances the SQ head; for the CQ, the roles reverse. Memory barriers order the updates, so no lock is needed.
To use it the program writes N SQEs and calls io_uring_enter once, which tells the kernel to consume them; the same call can wait for completions. One system call can start dozens of operations. The kernel tries to do each operation inline; if it would block (for example a buffered file read that misses the page cache), it hands it to a worker thread (io-wq), so the submitting thread never blocks. With SQPOLL, a kernel thread polls the SQ, and the program needs no system call at all, only memory writes. Registered files and buffers avoid repeated lookups and page pinning. Multi-shot operations (accept and recv, from Linux 5.19 and 6.0) produce a stream of completions from one submission.
So the three models differ in who does the I/O. In blocking and readiness models, your thread calls read or write and pays one system call per operation; readiness reduces waiting but not calls. In the completion model, the kernel does the I/O for you and calls are batched, so the cost per operation falls, and the same interface also covers files. The price is a larger interface, buffers that must stay valid until completion, and more complex error and cancellation handling.

example: Count the system calls for a server that handles 100,000 requests per second, where each request is one small read and one small write on an existing connection. With blocking threads, each request costs 2 system calls plus the wake-up, 200,000 calls per second, and 2 context switches (sleep and wake) per request if the thread has to wait. With epoll and an event loop, the loop calls epoll_wait; under load each call returns about 32 ready sockets, so 100,000 / 32 ≈ 3,125 epoll_wait calls per second, plus 200,000 read and write calls. Switches almost vanish, since the thread rarely sleeps. Total calls: about 203,000 per second. At 150 ns per call, that is 30 ms of kernel entry per second, 3% of a core, plus the work inside the calls.
With io_uring, the loop prepares a recv for each ready connection and a send for each response and submits them in batches of 32. Calls per second: 200,000 operations / 32 ≈ 6,250 io_uring_enter calls, which is 1 ms per second of entry cost. The saving in entry cost is about 29 ms per second, which is small for this example. The gain is larger when the per-call cost is higher (mitigations, virtual machines), when the operations are more, or when the kernel work is cheap, as with NVMe reads at 1 million per second per core, where 1 million calls at 150 ns would burn 15% of a core.
Now the cost of select versus epoll with 10,000 connections of which 100 are active. Each select or poll call scans all 10,000 descriptors in the kernel, building the result and also copying the set, which takes about 100 to 200 µs per call. If the loop calls it 1,000 times a second, that is 10% to 20% of a core just for scanning, and it grows with the number of idle connections. epoll_wait returns the 100 ready entries from its list, about 5 to 10 µs, regardless of how many connections are idle. This is the essence of C10K: the cost must depend on the active set, not the total.
intuition: Wait at the counter until your food is ready (blocking), take a buzzer that tells you when to come (readiness), or give your order list to the kitchen and get everything delivered to the table (completion).
The design follows from one fact: waiting is free for the CPU but expensive in memory if each wait needs its own thread. Readiness lets one thread wait on everything and only pay for what is ready. Completion goes further by observing that the real cost is the crossing between your code and the kernel, so you give the kernel a list and let it work in batches. The shared ring buffers are the simplest way for two parties to hand each other work without a lock or a call: one only writes the tail, the other only writes the head.
mistakes: People often think non-blocking I/O means asynchronous I/O. In fact a non-blocking read returns immediately with EAGAIN if no data is ready, but you still make the call and copy the data yourself. True asynchronous (completion) I/O means the kernel performs the operation and tells you when it is done.
People often think epoll works for disk files. In fact epoll_ctl fails with EPERM for regular files, and select or poll treat them as always ready, so a read can still block on the disk. Disk I/O in event loops goes to thread pools or to io_uring.
People often think edge-triggered epoll is simply faster. In fact it reduces the number of wake-ups but requires reading until EAGAIN, with a loop per descriptor that must not starve others. A missed read leaves data stuck with no new event. For most programs level-triggered mode is the safer choice.
People often think io_uring always beats epoll. In fact for a network server with modest rates, the gain is small, since the kernel work per packet dominates, and the added complexity and security exposure are real. It shines for storage-heavy workloads, very high operation rates, and cases that need to mix files and sockets.
People often think an event loop is automatically fast. In fact a single slow callback, such as a CPU-heavy function or a blocking call, stalls every connection on that loop. Event loops need short handlers and thread pools for blocking work.
tradeoffs: Choose blocking I/O with threads (or virtual threads) when concurrency is up to a few thousand, handlers do blocking work such as database calls, and clear sequential code matters. You pay in memory per thread and context switches; with virtual threads (Java 21) or goroutines, the runtime hides the cost and you get blocking-style code over epoll underneath. Choose an event loop on epoll when you have 10,000 or more mostly idle connections, short handlers and a need for predictable memory, accepting callback or async/await code and the rule that nothing may block.
Choose level-triggered epoll as the default and edge-triggered only when you have measured wake-up cost and can write the read-until-EAGAIN logic correctly. Choose one loop per core with SO_REUSEPORT listeners when you need to scale an event loop across cores without shared state; you give up automatic balancing, so a hot connection can overload one loop.
Choose io_uring when the workload is storage-heavy (NVMe at hundreds of thousands to millions of operations per second per core), when you want one interface for files and sockets, or when system-call overhead is measurable in profiles. You give up portability (Linux only, and features differ by kernel version), accept more complex buffer lifetime rules, and face security restrictions: some container runtimes and cloud platforms disable it, so check where you deploy. Choose thread pools around blocking file calls when the file load is modest and you need to run on old kernels.
Choose direct I/O (O_DIRECT) only when you run your own cache and want predictable I/O, accepting alignment rules and the loss of kernel readahead and caching. Choose buffered I/O otherwise.
friction: Asynchronous code is harder. Callbacks or async/await split a simple sequence into pieces, stack traces lose context, and cancellation is difficult: after you submit an io_uring read, the buffer must remain valid until the completion arrives, even if the caller gave up, which is a hard problem for memory-safe languages. Back-pressure is manual: if a client reads slowly, you must stop reading from the next stage to avoid unbounded buffers.
The models do not cover everything. Readiness does not fit files or some operations, such as opening files, resolving names (getaddrinfo is blocking in libc), or reading metadata. Runtimes hide these behind thread pools, which reintroduces threads and queueing. Completion models like io_uring cover more operations, but not all, and some run in worker threads anyway.
Security and stability are open issues for io_uring. It is a large new kernel interface with many opcodes, and a high share of recent kernel vulnerabilities involved it, which is why Google disabled it in several products and why some container sandboxes block it. Features also depend on kernel version, so portable software needs fallbacks.
Performance is not only about system calls. The network stack, copies, interrupts and the scheduler dominate for many servers; techniques such as busy polling, NIC offloads, and kernel-bypass (DPDK, AF_XDP) go further, and they trade generality for speed. Finally, one thread per core with an event loop avoids locks, but a skewed load, a slow handler or a garbage collection pause on one core stalls its share of the clients.
practice: Start from the workload. For a typical network service with thousands of connections, use an established runtime (Netty, Go's runtime, Tokio, Node, nginx) rather than writing epoll code. These use epoll underneath with tested handling of edge cases. Make sure handlers never block: move CPU work, disk access and blocking libraries to separate pools with bounded queues.
Count calls and wake-ups. Use strace -c -f, perf trace or eBPF tools to see how many epoll_wait, read and write calls you make per request. If epoll_wait returns 1 event on average at high load, your loop is not batching; check the timeout and the number of events requested. If you see many EAGAIN results, you may be reading more often than needed.
Set limits and socket options on purpose: raise the open files limit (ulimit -n and fs.file-max) for tens of thousands of connections, set listen backlog (somaxconn), use SO_REUSEPORT for multi-loop servers, and use TCP_NODELAY with care. Watch for memory per connection: buffers of 16 KB to 64 KB for 100,000 connections is 1.6 GB to 6.4 GB.
Try io_uring for storage engines and high-rate proxies when profiles show system-call overhead or file-I/O thread-pool overhead. Use a library (liburing, or a runtime with an io_uring backend), pin kernel version requirements, test with your container security profile, and keep an epoll fallback. Measure p99 latency and CPU per request on your own hardware, since published gains vary widely.

@@ locks
value: When two threads change the same memory at the same time, the result can be wrong even for the simplest statement. The line counter++ is really three steps: load the value, add one, store the result. If two threads interleave those steps, both load 5 and both store 6, and one increment is lost. A lock (mutex) fixes this by allowing only one thread at a time into the critical section, the code that touches the shared data. An atomic operation fixes it for a single word without a lock: the hardware guarantees that "add one" happens as one indivisible step.
Every concurrent program is built from these two things. A queue between threads, a connection pool, a cache with a hit counter, the buffer pool of a database, a JVM's monitor on an object and the kernel's own data structures all use locks or atomics somewhere. Their cost shapes what scales: an uncontended lock takes about 20 nanoseconds, but a lock that 16 threads fight over turns a parallel program into a serial one, and the cores spend their time passing a cache line back and forth.
Three lower ideas explain how this works. Memory models (L3) say what one thread may see of another thread's writes and in which order: a lock acquire and release carry the ordering guarantees that make the data inside the critical section visible to the next owner. Cache coherence (L3, MESI) is the hardware protocol that makes an atomic instruction possible and also makes contention expensive, since an atomic must own the cache line exclusively. Deadlock (L3) is the failure mode of using several locks: the rules of lock ordering come from there. Above them, threads, condition variables and lock-free structures are built.
terms: Critical section — a piece of code that must not run in two threads at once because it touches shared data.
Mutex — a lock with two operations, lock and unlock; a thread that calls lock on a held mutex waits.
Atomic operation — an operation that appears to all threads as a single indivisible step, such as fetch-and-add or compare-and-swap.
Compare-and-swap (CAS) — an atomic instruction that sets a memory word to a new value only if it still holds an expected old value, and reports whether it did.
Spinlock — a lock whose waiters loop on the lock word, using CPU, instead of sleeping.
Futex — the Linux system call that lets a mutex sleep in the kernel only when it is contended, so the uncontended path needs no system call.
Contention — several threads wanting the same lock or cache line at the same time.
False sharing — two unrelated variables in the same 64-byte cache line, so writes to one slow down the other.
history: The problem is as old as multiprogramming. Edsger Dijkstra's 1965 paper on mutual exclusion and his semaphores showed that two processes can exclude each other with only ordinary reads and writes, in a clever but fragile way. Dekker's algorithm, Lamport's bakery algorithm (1974) and Peterson's algorithm (1981) are of this kind. They work only under strict memory ordering, which real processors do not give, so they are used for teaching, not for practice.
Hardware soon added instructions: IBM System/360 had test-and-set (1964) and System/370 added compare-and-swap (1970). In 1991 Maurice Herlihy's "Wait-Free Synchronization" proved that CAS is universal, meaning that any shared object can be built from it, while test-and-set cannot do that for more than two threads. DEC's Alpha (1992) and later ARM and RISC-V used a different pair, load-linked and store-conditional (LL/SC), which can build the same operations.
Software then dealt with performance. Mellor-Crummey and Scott (1991) showed with the MCS lock that spinning on a single shared word wastes the interconnect, and that waiters should each spin on their own cache line. Hoare's monitors (1974) and later Mesa's condition variables gave a safer language-level structure. Linux used a Big Kernel Lock for years, and it was removed only in 2011 (2.6.39). Linux added futexes in 2002 (Franke, Russell and Kirkwood), which let a user-space mutex avoid the kernel; Ulrich Drepper's "Futexes Are Tricky" (2003) described how to build correct locks on them.
Famous failures shaped practice. In 1997 the Mars Pathfinder lander reset repeatedly because a low-priority task held a lock that a high-priority task needed while a medium-priority task kept running (priority inversion); engineers enabled priority inheritance remotely. In 2015 Linux 4.2 introduced the queued spinlock, an MCS design packed into 4 bytes, for scalability on large machines. Language runtimes changed too: Go's sync.Mutex got a starvation mode in 1.9 (2017), and Rust's standard mutex moved to futexes in 1.62 (2022).
how: Start with the hardware primitive. On x86, instructions with the LOCK prefix (LOCK XADD for fetch-and-add, LOCK CMPXCHG for compare-and-swap, XCHG with a memory operand) make a read-modify-write indivisible. The core first gets the cache line in the exclusive state, which, by the MESI protocol, invalidates every other core's copy. While it holds the line it performs load, modify and store, and refuses requests for the line until it is done. Arm and RISC-V provide either LL/SC pairs (the store fails if another core touched the line since the load) or direct atomic operations (Arm LSE, RISC-V AMO). These instructions also act as barriers, so earlier writes are visible before later ones.
Cost follows from coherence. An atomic on a line already in the core's L1 in exclusive state takes about 5 to 20 cycles (a few nanoseconds). If another core owns the line, it must be transferred, which costs about 50 to 100 ns between cores on one chip and 100 to 300 ns between sockets. When N threads hammer one word, each operation needs the line, so they run one after another, and the total rate is that of a single core's transfers, however many cores there are.
The simplest lock is a spinlock built on test-and-set: loop until an atomic exchange of the lock word to 1 returns 0. This is correct but wasteful, since every spinning core keeps writing the line. Test-and-test-and-set first reads the word (a read hits the local cache and costs nothing on the bus) and attempts the atomic exchange only when the word looks free; adding exponential backoff reduces collisions. Ticket locks give FIFO fairness: each arrival takes a number with fetch-and-add and waits until "now serving" equals its number. MCS and queued locks go further: each waiter enqueues a small node with one atomic exchange on the tail and spins on a flag in its own node, so a release touches only the next waiter's line. Spinlocks are suitable for short critical sections that cannot sleep (inside kernel interrupt handlers) or when the owner is running on another core.
A general-purpose mutex avoids burning CPU while it waits. On Linux, a pthread mutex is one 32-bit word with three states: 0 unlocked, 1 locked with no waiters, 2 locked with waiters. To lock, the thread tries a CAS from 0 to 1. If that succeeds (the common case), it is done: no system call, about 20 ns. If not, it may spin briefly (the owner often finishes within a microsecond), then sets the state to 2 and calls futex(FUTEX_WAIT), which puts the thread to sleep in the kernel only if the word is still 2. To unlock, the owner exchanges the word to 0; if the old value was 2, there may be waiters, so it calls futex(FUTEX_WAKE) for one of them. The kernel keeps wait queues in a hash table keyed by the word's address. So the uncontended path is user-space atomics only, and the kernel is used only for sleeping and waking.
Locks also carry ordering. Unlock is a release operation: all writes made inside the critical section become visible before the lock word shows "free". Lock is an acquire operation: reads inside the critical section cannot move before the acquisition. Together they give the next owner a consistent view of the data. This is what the memory model promises for correctly locked code, and it lets programmers reason as if threads took turns.
Several variants exist because workloads differ. Reader-writer locks allow many readers or one writer, which helps when reads dominate and critical sections are long; but each reader still performs an atomic increment of a shared reader count, so the cache line bounces and read-heavy locks do not scale to many cores. Seqlocks let readers read without locking and retry if a writer changed the data (sequence counter before and after); RCU, used throughout the Linux kernel, lets readers run with no atomic at all and delays freeing old versions until all readers are done. Atomic counters (fetch-and-add) replace locks for single statistics. Striped or per-thread counters (Java's LongAdder) keep each thread on its own line and sum them on read.
Lock-free structures use CAS in loops: read the current value, compute the new one, and CAS it in; if the CAS fails, another thread got there first, so retry. No thread holds a lock, so a stalled thread cannot block the others, but the structures are hard to design. The ABA problem is the classic trap: a CAS succeeds because the value is the same as before, although it changed to something else and back, and meanwhile the meaning changed (for example a freed and reused node). Tagged pointers, hazard pointers or epochs prevent it.

example: First the lost update, which you can follow with a pen. Shared variable x = 5. Thread A and thread B both execute x = x + 1. A loads 5. B loads 5. A computes 6 and stores 6. B computes 6 and stores 6. Final x = 6, but two increments ran. If the increment is an atomic fetch-and-add, the hardware performs load-add-store as one step: A makes x 6, B then makes it 7. If a mutex protects the code, B waits until A unlocks, and the result is also 7.
Now the same increment built from CAS. Each thread runs: loop { old = x; new = old + 1; if CAS(x, old, new) succeeds, stop }. A reads old = 5. B reads old = 5. A runs CAS(x, 5, 6): x is 5, so it succeeds and x = 6. B runs CAS(x, 5, 6): x is now 6, not 5, so it fails. B loops: old = 6, new = 7, CAS(x, 6, 7) succeeds. The failed CAS told B that its view was stale. Under heavy contention many CAS attempts fail and retry, which wastes work, but at least one thread always succeeds in each round.
Next, the cost of contention. A program counts events with one shared counter. A single thread doing an uncontended atomic add reaches about 100 to 200 million increments per second (5 to 10 ns each). With 8 threads on 8 cores all adding to the same counter, each add needs the cache line from another core, about 50 to 100 ns, and the adds execute one at a time, so the total is about 10 to 20 million per second, which is less than a single thread. Eight threads are slower than one. If each thread has its own counter on its own cache line (padded to 64 bytes) and the totals are summed when needed, each thread runs at full speed, about 8 × 150 = 1.2 billion increments per second in total. Same logic, 60 to 100 times more throughput. If the per-thread counters are packed next to each other in one 64-byte line (false sharing), they ping-pong again and you are back to about 15 million per second.
Finally, Amdahl's law applies to locks. If a critical section is 10% of each task's time and all threads share one lock, the maximum speed-up is 1 / 0.1 = 10 times, no matter how many cores. With 16 cores and 10% serial time, speedup is 1 / (0.1 + 0.9/16) ≈ 6.4. In practice, contention adds to the serial part with the cost of the line transfer and of waking sleepers (a futex wake and context switch cost several microseconds), so real results are worse than Amdahl's.
intuition: The key to a single bathroom: only one person can use it, others queue at the door, and the real cost is in passing the key around.
The design is natural because shared memory has no built-in turn-taking. Hardware offers one thing that cannot be broken by interleaving, an atomic read-modify-write on one word, and everything else is built from it. A lock turns that one-word guarantee into a guarantee for a whole block of code. The cache-coherence protocol then shows why the key is expensive to pass: the line holding the lock word has to move from core to core. The best locks are the ones that are rarely contended, and the best designs avoid sharing.
mistakes: People often think volatile (in Java) or an ordinary variable makes counter++ safe. In fact volatile gives visibility and ordering but not atomicity: the increment is still load, add, store. Use AtomicInteger, LongAdder or a lock. In C and C++, volatile does not provide atomicity or ordering for threads at all; use std::atomic.
People often think lock-free code is always faster than locks. In fact lock-free means that some thread always makes progress, not that it is fast. Under contention, CAS loops waste work and bounce cache lines just like locks. A simple mutex is often as fast for moderate contention and much easier to get right.
People often think that more fine-grained locks always give more parallelism. In fact each lock adds acquire/release cost, memory, and the risk of deadlock when code takes several. Finer locks help only if contention was the limit; sometimes sharding the data (per-thread or per-partition state) is a better answer than more locks.
People often think a read-write lock is faster than a mutex for read-heavy data. In fact readers still update a shared count atomically, so with many cores the line bounces, and writers can starve or readers can. For short read sections a plain mutex can win; for scalable reads, use RCU, seqlocks or immutable snapshots.
People often think spinning is always bad, or always good. In fact it depends on the wait: for waits shorter than a context switch (a few microseconds) with the owner running, spinning is cheaper; if the owner is descheduled, spinning wastes whole time slices. Adaptive mutexes spin briefly, then sleep.
tradeoffs: Choose a plain mutex when the critical section is more than a few dozen instructions, contention is moderate, and you value correctness; its uncontended cost is about 20 ns and it sleeps when contended. Choose an atomic (fetch-and-add, CAS on a single word) when the shared state is one word, such as a counter, a flag or a reference count; you give up the ability to protect more than one variable at once. Choose a spinlock only for very short sections where the owner cannot be descheduled (kernel code with preemption disabled), because a preempted lock holder turns spinning into waste.
Choose sharding (per-core counters, per-partition locks, thread-local buffers) when a lock is hot and the data can be split or summed later. You gain near-linear scaling and give up exact instantaneous values and simplicity: reads must combine shards. Choose a single lock when correctness across all the data is needed and the throughput is enough.
Choose a reader-writer lock when reads are long and many, and writes are rare (a configuration table used by many threads for milliseconds at a time). Choose RCU, immutable copy-on-write snapshots or seqlocks when reads are very short, very frequent and must not write shared memory; the price is more complex writers and delayed memory reclamation.
Choose fair (queued, ticket or FIFO) locks when tail latency and starvation matter and throughput can drop by some percent; choose unfair locks (barging) when throughput matters most, since a running thread can retake the lock without waiting for a sleeping waiter to wake. Go's mutex switches between the two: it normally lets a new arrival barge in, and if a waiter has waited longer than 1 ms, it switches to FIFO handoff.
Choose lock-free structures only for well-understood components (queues, counters, stacks from a trusted library) where a stalled thread must not block others, as in signal handlers, real-time paths or very high-contention queues. You pay with complexity and the need for safe memory reclamation.
friction: Contention serialises work, and the cost is not only waiting but also the cache-line transfers and wake-ups. Locks are invisible in the code's structure: a hot lock may sit deep in a library. Profilers that sample on-CPU time miss threads sleeping on locks, so you need off-CPU and lock profiling (perf lock, eBPF, async-profiler lock mode) to find them.
Composition is weak. Two correct, locked components can deadlock or race when combined, because a lock protects one object and says nothing about invariants across objects. Holding a lock while calling unknown code (callbacks, I/O, logging) is a common source of stalls and deadlocks. Priority inversion appears whenever a low-priority thread holds a lock needed by a high-priority one; real-time systems use priority inheritance.
Performance problems are subtle: false sharing, lock convoys (many threads wake one after another, each causing a context switch), lock holder preemption (the owner is descheduled while others spin), and NUMA effects (a lock word owned by a remote socket costs hundreds of nanoseconds per transfer). Spinning threads in a virtual machine can waste host time, as the hypervisor cannot see why they spin.
Lock-free programming brings its own difficulties: the ABA problem, safe memory reclamation, ordering bugs that appear only on weakly ordered machines like Arm, and proofs that are hard to write. Tools help (ThreadSanitizer, Loom, Jepsen-style stress tests, model checkers), but no tool is complete. The open question is how to write concurrent code that is correct by construction, which is why newer languages use ownership (Rust), message passing (Go channels, actors) or software transactional memory.
practice: First avoid sharing: give each thread its own data, partition work by key, and merge results at the end. Where sharing is unavoidable, protect with one mutex per logical object, keep critical sections short and free of I/O, allocation and callbacks, and document which lock guards which data. Take multiple locks in one global order (see deadlock) or use a tool that takes them together (std::scoped_lock in C++).
Use the right primitive from a library: std::mutex, pthread_mutex, java.util.concurrent locks and atomics, Go's sync package, Rust's Mutex and atomics. Prefer atomic counters and LongAdder-style striped counters for statistics. Pad hot variables to cache-line size (alignas(64), @Contended in Java, repr(align(64)) in Rust) when different threads write neighbouring fields.
Measure. Look at lock hold and wait times with perf lock, eBPF (offcputime, futex tracing), the Java Flight Recorder lock events, or Go's mutex and block profiles. A high count of futex calls and context switches with low CPU points to lock contention. Check scaling by running with 1, 2, 4, 8 and 16 threads: if throughput is flat, you have a serial bottleneck.
Test for races: run ThreadSanitizer in CI, use stress tests with many threads and random delays, and test on weakly ordered hardware (Arm) if you use atomics with relaxed ordering. Default to sequentially consistent atomics until profiling shows that relaxed or acquire/release ordering is needed, and then only in code reviewed by someone who knows the memory model.
interview: Explain how a futex-based mutex avoids system calls on the fast path. || The mutex is a word in user memory. Lock does a CAS from 0 to 1; if it succeeds, there is no kernel involvement. Only on contention does the thread set the state to "locked with waiters" and call futex_wait, which sleeps if the word still has that value. Unlock exchanges to 0 and calls futex_wake only if waiters were recorded. The kernel keeps wait queues keyed by the word's address.
Why do eight threads incrementing one atomic counter run slower than one thread, and how do you fix it? || Each atomic needs the cache line in exclusive state, so the line moves between cores for every increment (50 to 100 ns), and the increments are serialised. Fix by giving each thread its own padded counter and summing on read (LongAdder), or by batching increments locally.
What is the ABA problem and how do you prevent it? || A CAS checks only that a word equals the expected value. If the word changed from A to B and back to A, the CAS succeeds although the state is different, for example a node was freed and reallocated. Prevent it with version tags next to the pointer (double-width CAS), hazard pointers, epoch-based reclamation, or by not reusing memory while readers might hold references.
When is a spinlock better than a sleeping mutex, and what can go wrong? || When the critical section is shorter than a context switch (about a microsecond or two), the owner is running on another core, and the code cannot sleep (interrupt context). It goes wrong when the owner is preempted or the machine is oversubscribed, as waiters burn their time slices; it also wastes power and hurts hyperthreads. Use adaptive mutexes in user space.
Your service shows low CPU but poor throughput and many context switches. What do you check for lock problems? || Off-CPU profiling for time in futex waits, the lock with the longest total wait, the hold time of that lock (what runs inside it: I/O, logging, allocation), and thread-count scaling. Fixes: shorten critical sections, shard the state, replace the lock with atomics or read-copy-update, or reduce the number of threads contending.
quiz: Why is counter++ not safe across threads? || It is load, add and store as separate steps. Two threads can load the same value and both store the same result, losing one increment.
What does compare-and-swap do, and what does a failure tell you? || It writes a new value to a word only if the word still holds the expected old value. A failure means another thread changed the word after you read it, so you must re-read and retry.
Eight threads share one atomic counter and each add costs 80 ns when the line must move. About what is the maximum total rate? || The adds are serialised, so the rate is about 1 / 80 ns = 12.5 million per second in total, not 8 times a single thread.
Why does Amdahl's law limit a program where 20% of the work is under one lock? || The locked part runs serially, so even with infinite cores, the speed-up cannot exceed 1 / 0.2 = 5 times. With 16 cores it is 1 / (0.2 + 0.8/16) = 4.
A shared configuration object is read 100,000 times a second and replaced once an hour. What synchronization do you choose? || Immutable snapshots published through an atomic pointer swap (or RCU): readers do one atomic load and never write shared memory; the writer builds a new copy and swaps the pointer. A mutex or reader-writer lock would make the reader count a contended cache line.

@@ deadlock
value: A deadlock is a state in which a group of threads (or transactions, or processes) are all waiting, and each one waits for something that another one in the group holds. None can continue, and none will ever release what it holds, because releasing needs progress. The program does not crash and does not use CPU. It just stops, often only for some requests, which makes it hard to notice until a queue fills up or a timeout fires.
The simplest case has two locks, A and B. Thread 1 takes A and then asks for B. Thread 2 takes B and then asks for A. If each gets its first lock before the other asks for its second, both wait forever. The same pattern appears in databases (two transactions update the same two rows in opposite order), in thread pools (every worker waits for a task that is queued behind it), in message passing (two processes both do a blocking send to each other) and across services (A calls B, B calls A, and both have limited worker pools).
Deadlock is useful to study because it has a precise theory. Four conditions must all hold (Coffman, 1971); remove any one and deadlock is impossible. This gives a short list of design options: prevent it by breaking a condition, avoid it by checking each request, or detect it and recover. Detection rests on graph theory (L4) and graph algorithms (L3): the system is a directed graph of "waits for" edges, and a deadlock is a cycle, found by depth-first search in O(V + E). Higher layers meet it constantly: two-phase locking in databases can deadlock, so every lock-based database has a detector or timeout, and the lock ordering rules of the previous concept exist because of it.
terms: Wait-for graph — a directed graph with a node per thread or transaction and an edge from X to Y when X waits for a resource held by Y.
Cycle — a path in the graph that returns to its start; in a wait-for graph a cycle means deadlock (for single-unit resources).
Mutual exclusion — a resource can be held by only one party at a time.
Hold and wait — a party holds some resources while waiting for more.
No preemption — a resource cannot be taken away from its holder; it is released only voluntarily.
Circular wait — a chain of parties each waiting for the next, with the last waiting for the first.
Lock ordering — a global rule that locks are always acquired in one agreed order, which makes circular wait impossible.
Livelock — parties keep changing state in response to each other but make no progress, so they are active and still stuck.
history: Edsger Dijkstra named the problem the "deadly embrace" in the mid-1960s while studying cooperating processes. His banker's algorithm (1965) decides whether granting a resource request leaves the system in a safe state, one from which all processes can still finish in some order. His dining philosophers puzzle, five philosophers who each need two forks from a shared table, gave everyone a standard picture: if all take their left fork at once, nobody eats.
In 1968 Havender at IBM proposed the practical prevention rules used on OS/360: request all resources at once, or request them in a fixed order. Coffman, Elphick and Shoshani's survey "System Deadlocks" (1971) stated the four necessary conditions that textbooks still use. Holt (1972) modelled systems as resource-allocation graphs, which made detection a graph algorithm. In databases, Gray and the System R team (1970s) accepted that locking can deadlock, and chose detection plus abort over prevention, because transactions can be rolled back safely. Rosenkrantz, Stearns and Lewis (1978) gave the timestamp rules wait-die and wound-wait, which prevent cycles without detection. For distributed systems, Chandy, Misra and Haas (1983) described "edge-chasing" detection, where probe messages follow wait-for edges across machines.
Tools followed. The Linux kernel's lockdep (Ingo Molnar and Arjan van de Ven, 2006) builds a graph of lock classes at run time and warns when two code paths take locks in opposite orders, even if the deadlock never happened. Java's thread dumps report "Found one Java-level deadlock". ThreadSanitizer and the Go and Rust ecosystems have lock-order detectors too. Today deadlock is less a research topic than a design discipline.
how: The four conditions give the structure. Mutual exclusion: the resource is a lock, a row lock or a single-slot buffer, and cannot be shared. Hold and wait: a thread keeps what it has while asking for more. No preemption: the system will not take the lock away. Circular wait: the waits form a cycle. All four must be true at the same time. A deadlock needs no bad luck beyond timing: the code only has to allow it, and a rare interleaving will find it.
Prevention removes one condition by design. Lock ordering removes circular wait: number the locks, and let every thread acquire them in increasing order. If thread 1 needs A and B, and thread 2 needs B and A, both must take A first, so the second waits for the first, and no cycle can form. To order dynamic locks, use a stable key such as an account id or the lock's address. Acquiring all locks at once (try to lock all, release all if one fails) removes hold and wait, but may cause livelock and wasted work. Using try-lock with timeout and back-off gives up what you hold, which removes no-preemption in effect. Lock-free or optimistic designs remove mutual exclusion altogether.
Avoidance checks each request against what could happen later. The banker's algorithm knows each process's maximum need and grants a request only if there is still an order in which all processes can finish. It needs advance knowledge of maximum demands, which real programs rarely have, so it is mostly a teaching tool. In practice, avoidance appears in the form of timestamp schemes in databases. Wait-die: an older transaction may wait for a younger one, but a younger transaction that wants a lock held by an older one is aborted ("dies") and restarted with its original timestamp. Wound-wait: an older transaction that wants a lock held by a younger one "wounds" it (forces its abort), while a younger one waits for an older. In both, waits go in only one direction of age, so a cycle cannot exist. The cost is aborts that were not strictly necessary.
Detection and recovery is the database approach. The lock manager keeps a wait-for graph. When a transaction must wait, the system adds an edge and searches for a cycle through the new edge. This depth-first search costs O(V + E), usually tiny since most transactions wait for few others. InnoDB (MySQL) runs it immediately on every lock wait by default (innodb_deadlock_detect), and rolls back the transaction that has changed the fewest rows. PostgreSQL waits first: when a lock request has waited for deadlock_timeout (1 second by default), it runs the detector, so that the cost is paid only by requests that are really slow, and then aborts one transaction with the error 40P01. The application receives an error and is expected to retry. The key property is that a transaction can be undone, so the system can always make progress by choosing a victim.
When resources have several identical units (a pool of 4 connections), a cycle in the graph is necessary but not sufficient for deadlock, as some other holder may release a unit. For single-unit locks, a cycle means deadlock. This is why the graph theory is exact for locks and databases.
Many deadlocks are not about locks. Thread-pool starvation: a pool of 8 threads runs 8 tasks that each submit a subtask to the same pool and wait for its result; the subtasks sit in the queue and no thread is free to run them. Asynchronous code: blocking on a result (Task.Result in .NET, join on a future) inside a thread that the awaited work needs. Message passing: two processes each send a large message to the other with blocking sends and full buffers (a classic MPI bug). Resource exhaustion across services: service A uses all its workers to call B, and B uses all its workers to call A. In each case the same four conditions hold, with "locks" replaced by threads, buffers or workers.
Finally, livelock and starvation are close relatives. In livelock, two threads detect a conflict, both back off and retry at the same moment, repeatedly, as two people stepping aside in a corridor. Random back-off solves it. In starvation, one thread waits forever because others keep winning, even though the system as a whole progresses. Fair locks and bounded waiting prevent it.

example: Take a bank transfer with locks on accounts. transfer(from, to, amount) does lock(from), lock(to), moves the money, then unlocks both. Thread 1 runs transfer(account 7, account 9); thread 2 runs transfer(account 9, account 7) at the same time. Thread 1 locks 7. Thread 2 locks 9. Thread 1 asks for 9 and waits. Thread 2 asks for 7 and waits. Deadlock. It needs a precise overlap, so in testing with one request at a time it never happens, and in production with 5,000 transfers per second it can happen several times a day, and each time two threads are stuck holding two locks, and every later transfer touching those accounts piles up behind them.
The fix is lock ordering by account id. transfer() locks min(from, to) first and max(from, to) second. Both threads now lock account 7 first. Thread 2 waits for 7 while holding nothing, thread 1 gets 9, finishes, and releases both. There is no cycle. The cost is one comparison. In C++, std::scoped_lock(a, b) does this for you using a deadlock-avoidance algorithm; in Java, order by System.identityHashCode or by id, with a tie-breaker lock for equal hashes.
Now a database. Two transactions run: T1 does UPDATE accounts SET balance = balance - 10 WHERE id = 7, then updates id 9. T2 updates id 9 first, then id 7. T1 holds a lock on row 7, T2 holds row 9. T1 requests row 9 and waits; T2 requests row 7 and waits. In InnoDB, the second request triggers the cycle check at once. It finds T1 and T2 in a cycle, picks the one with less work done, say T2, rolls it back, and returns error 1213 (deadlock found when trying to get lock). T1 continues. The application should catch the error and retry T2, which then succeeds. In PostgreSQL the same thing happens after the 1 second deadlock_timeout, and the error is 40P01. The cheap prevention is to make both transactions touch rows in the same order, for example by sorting the ids before the updates.
Count the cost of the thread-pool deadlock. A pool has 8 threads. A request handler uses a thread, submits one subtask to the same pool, and waits. With 8 concurrent requests, all 8 threads hold a request handler and wait for subtasks, and the 8 subtasks wait in the queue. Nothing moves. With 7 concurrent requests, one thread is free, and it runs the subtasks one by one: slow but alive. So the system works at low load and freezes exactly at the load of 8, a typical sign of a pool deadlock. The fixes: use separate pools for parent and child tasks, make the parent not wait (continue with a callback), or size the pool above the maximum nesting depth times concurrency.
intuition: Two people in a narrow corridor, each politely waiting for the other to step aside.
The theory is simple because deadlock is only a cycle in a "who waits for whom" graph. If you can make waiting go in one direction only (by lock order, by age, or by priority), a cycle cannot form, just as a one-way street cannot have two cars facing each other. If you cannot, you accept that cycles may happen and arrange for someone to give way, as databases do by aborting a transaction. Every solution is either a rule that keeps arrows pointing the same way or a referee who breaks a cycle after the fact.
mistakes: People often think deadlock needs many locks or complex code. In fact two locks and two threads are enough, and so are one lock taken twice by the same thread (a non-reentrant mutex locked again), or a thread pool that waits on itself.
People often think a deadlock will show up quickly in testing. In fact it needs a specific interleaving, so it often passes tests and appears in production under load. Lock-order checkers (lockdep, ThreadSanitizer) find potential deadlocks without waiting for them to happen, and are more reliable than stress tests.
People often think that a timeout solves deadlock. In fact a timeout turns a hang into an error, which is better than a hang, but it does not fix the cause, can abort healthy slow operations (false positives), and the retry may hit the same deadlock again. Use timeouts as a safety net, not as the design.
People often think that deadlock detection is expensive and so databases avoid it. In fact databases use detection precisely because it is cheap: a cycle search in a graph with a few hundred nodes takes microseconds, and a transaction can be rolled back safely. It is application-level locks, which cannot be rolled back, that need prevention.
People often think livelock and deadlock are the same. In fact in deadlock nothing runs; in livelock threads run (and burn CPU) but make no progress. The cures differ: ordering for deadlock, randomised back-off or an arbiter for livelock.
tradeoffs: Choose lock ordering (prevention) when you control all the code that takes the locks and the set of locks is known, for example inside one library or one module. It costs nothing at run time. You give up flexibility: every new lock must fit in the hierarchy, and callbacks that run while holding a lock can break it. Choose detection with abort and retry when work can be rolled back safely, as in databases; you accept wasted work from aborted transactions (often under 1% of transactions) in exchange for freedom to touch rows in any order.
Choose try-lock with timeout and back-off when you must call code you do not control while holding a lock, or when lock sets are dynamic. You pay with retry logic, possible livelock (add randomised delays) and the chance of failing the operation. Choose one coarse lock over many fine locks when the code is not hot: with one lock there is no lock order and no deadlock between locks, and the price is less parallelism.
Choose wait-die or wound-wait (timestamp schemes) in distributed databases or systems where a global wait-for graph is too costly to build, as in Spanner-like designs; you pay in extra aborts, since a transaction may be aborted although no deadlock existed. Choose a central or per-node detector (periodic or edge-chasing) when aborts are expensive and you can afford the detector's messages and delay. Choose optimistic concurrency (OCC, as in Delta Lake commits) when conflicts are rare; there are no locks held, so no deadlock, but conflicting transactions fail at commit and must redo their work.
Choose bounded queues with separate pools per stage, or non-blocking designs, for pipelines; you give up simplicity of "just wait for the result" and gain freedom from pool-starvation deadlocks.
friction: A global lock order is hard to maintain in a large codebase. It lives in people's heads or in comments, new code breaks it, and libraries that take locks inside callbacks hide edges. The Linux kernel needs lockdep to keep thousands of lock classes in order, and the annotations are a significant effort.
Detecting deadlock after the fact has limits. In a single process, a wait-for graph is easy. Across processes, services and machines, no one sees the whole graph. A cycle might include a database lock, a thread pool and a remote call, and no component can detect it. The usual defence is timeouts at every boundary, which fire after the damage (a stuck worker, a queue that grows) and can also kill valid slow work.
Recovery is only free when work can be undone. A database can abort a transaction; a thread holding an in-memory lock in the middle of updating a data structure cannot be aborted safely, so the process must restart. Choosing a victim needs a policy (least work, youngest, lowest priority) and can cause starvation if the same transaction is chosen repeatedly.
Related problems remain even with no deadlock. Priority inversion can block a high-priority thread behind a low-priority one holding a lock. Lock convoys and contention can produce the same symptoms as a deadlock, a stall with low CPU, and are harder to tell apart without data. Finally, some designs have deadlocks that formal methods can find (model checking with TLA+ or SPIN), but this is rare in industry code, and most teams rely on conventions, reviews and testing under load.
practice: Make a rule and enforce it. Write the lock order down in the code next to the lock declarations, take multiple locks through one helper that sorts them (by id, or address), never call unknown code, perform I/O, or take another lock while holding a lock unless the order allows it. Keep critical sections short. Prefer one lock per object with immutable or message-passing designs for the rest.
Use tools. Run ThreadSanitizer or a lock-order checker in CI; in the Linux kernel enable lockdep when testing drivers. In Java, run jstack or jcmd Thread.print on a hung process and look for "Found one Java-level deadlock"; use ThreadMXBean.findDeadlockedThreads in a health check. In Go, use the block and mutex profiles and a goroutine dump (SIGQUIT). In Python, faulthandler can dump stacks.
In databases, keep transactions short, access rows in a consistent order (for example UPDATE with ORDER BY id, or sort ids in the application), use SELECT ... FOR UPDATE in a stable order, add indexes so that statements lock only the rows they need (a missing index can lock a whole range and cause gap-lock deadlocks in InnoDB), and always retry on deadlock errors (MySQL 1213, PostgreSQL 40P01) with a limit. Read SHOW ENGINE INNODB STATUS, which includes the latest detected deadlock, or PostgreSQL's log with log_lock_waits and the pg_locks view.
For services, give each stage its own bounded pool, set timeouts that shrink along the call chain (each hop gets a shorter deadline than its caller), avoid cyclic calls between services, and test with load that fills the pools. When a process hangs, take two thread dumps a few seconds apart; threads that have not moved and wait for each other are your suspects.
interview: State the four necessary conditions for deadlock and give a practical way to break each one. || Mutual exclusion (use lock-free, immutable or optimistic designs), hold and wait (acquire all locks at once or try-lock and back off), no preemption (let the system abort and retry, as databases do), circular wait (a global lock order). Breaking one is enough; lock ordering is the most common in application code.
How do InnoDB and PostgreSQL handle deadlock differently? || Both keep a wait-for graph and abort a victim. InnoDB checks at once when a lock wait begins (innodb_deadlock_detect) and picks the transaction that has changed the least. PostgreSQL waits for deadlock_timeout (1 s by default) before running the check, so that short waits cost nothing. Both return an error that the client must retry.
Your service hangs under load but works fine in tests, with 0% CPU. How do you find out whether it is a deadlock? || Take thread dumps (jstack, goroutine dump, gdb thread apply all bt) twice; look for threads blocked on locks held by other blocked threads, forming a cycle, or all pool threads waiting on futures. Tools such as jstack report Java deadlocks. If there is no cycle, look for pool starvation, a missing notify, or a stuck remote call.
What is the difference between wait-die and wound-wait, and why do they prevent deadlock? || Both use transaction timestamps. In wait-die an older transaction waits for a younger one, and a younger one that requests a lock held by an older one is aborted. In wound-wait the older one aborts (wounds) the younger holder, and a younger one waits. In both, waiting follows age in one direction, so there is no cycle. They cause extra aborts but need no graph.
Why can a thread pool deadlock even though no locks are involved, and how do you avoid it? || If tasks wait for results of other tasks queued in the same pool, then when all threads are held by waiting tasks, the queued subtasks never run. It is a circular wait on threads, not locks. Avoid it with separate pools per level, non-blocking continuations, or bounded nesting with a pool large enough for the worst case.
quiz: What are the four Coffman conditions? || Mutual exclusion, hold and wait, no preemption, and circular wait. All four must hold for deadlock to occur.
Why does acquiring locks in a fixed global order prevent deadlock? || It makes all waits go from lower to higher locks, so a cycle of waits cannot form. A thread holding the highest lock never waits for a lower one.
In a wait-for graph with edges T1 -> T2, T2 -> T3, T3 -> T1, what happens and what does the database do? || The edges form a cycle, so T1, T2 and T3 are deadlocked. The database picks a victim (for example the transaction with the least work), rolls it back, and releases its locks so the others continue.
A pool has 16 threads and each request needs 1 handler thread plus 1 subtask thread from the same pool. At what concurrency can it deadlock? || At 16 concurrent requests: all 16 threads are handlers waiting on subtasks, and no thread is left to run any subtask. Below 16 requests it still works, which hides the problem in tests.
Would you use wait-die timestamps or a detector in a geo-distributed database where a global wait-for graph is costly? || Timestamp schemes like wait-die or wound-wait are attractive because they need no global graph, only the timestamps carried by transactions. The cost is extra aborts. A detector with edge-chasing messages avoids needless aborts but adds latency and complexity.

value: A container is not a special kind of object in the Linux kernel. It is an ordinary process (or a group of processes) to which the kernel has applied two kinds of restriction. Namespaces change what the process can see: its own process ID numbering, its own network interfaces, its own mount points and hostname, its own user IDs. Control groups (cgroups) change what the process can use: how much CPU time, memory, disk bandwidth and how many processes. Together they give the impression of a separate small machine, without a second operating system and without the cost of a virtual machine.
This is the base of nearly everything that is called a container or a sandbox. Docker, containerd, Kubernetes pods, systemd services, AWS Lambda functions and Fargate tasks, CI runners, and the code sandboxes that AI agents use to run commands all start a process with a set of namespaces and a cgroup. The practical result is density and speed: a container starts in tens of milliseconds, adds almost no memory overhead beyond its own processes, and a host can run hundreds of them. A virtual machine needs its own kernel and a boot process, so it is heavier.
The mechanism stands on the process abstraction (L3). A process already has an identity (a PID), a memory space, open files and a parent. Namespaces make some of these identities relative to a group: PID 1 inside a container is, say, PID 48213 on the host. Cgroups attach a process to a node in a tree on which the kernel's own resource managers (the CPU scheduler, the memory manager, the block layer) keep counters and enforce limits. The layers above add images (overlayfs), security filters (seccomp, capabilities) and orchestration, but the isolation itself comes from these two kernel features.
terms: Namespace — a kernel object that gives a group of processes their own private view of one kind of global resource, such as process IDs or network devices.
cgroup (control group) — a node in a tree of process groups on which the kernel limits, accounts for and prioritises resources.
Controller — a part of cgroups that manages one resource, for example cpu, memory, io or pids.
clone / unshare / setns — system calls that create a process in new namespaces, move the calling process into new ones, or join an existing namespace.
PID namespace — a namespace in which processes have their own numbering starting at 1; the first process there acts as init.
Mount namespace — a namespace with its own table of mounted file systems, which lets a container have its own root directory.
User namespace — a namespace that maps user IDs, so that root (UID 0) inside is an ordinary user outside.
OOM killer — the kernel routine that kills a process when memory cannot be freed; with cgroups it acts when a group reaches its memory limit.
history: The first isolation tool was chroot (Unix V7, 1979), which changes the root directory of a process. It hides files, but not processes or the network, and it was not designed as a security boundary. FreeBSD jails (2000) and Solaris Zones (2004) went further and gave each tenant a view of processes, network and users. Linux built the pieces one by one. The mount namespace came in 2002 (kernel 2.4.19); UTS and IPC namespaces in 2.6.19 (2006); the PID namespace in 2.6.24 (2008); the network namespace was completed around 2.6.29 (2009); the user namespace arrived in 3.8 (2013); cgroup and time namespaces in 4.6 (2016) and 5.6 (2020).
Cgroups started at Google. Paul Menage and Rohit Seth wrote "process containers" for resource control in a shared cluster, renamed to control groups to avoid confusion with other uses of the word, and merged in Linux 2.6.24 (January 2008). Version 1 gave each controller its own hierarchy, which made it hard to combine controllers. Tejun Heo led cgroup v2, with a single unified hierarchy and clearer rules (declared stable in Linux 4.5, 2016); most distributions switched to it by default around 2020 to 2022.
LXC (2008) combined the pieces into a tool, but it was Docker (2013) that made containers popular, with a simple image format and workflow. Kubernetes (2014) added scheduling across machines. The Open Container Initiative (2015) standardised the runtime interface, with runc as the reference implementation. Kubernetes support for cgroup v2 reached general availability in 1.25 (2022).
The shared kernel is the main weakness, so stronger isolation grew alongside. gVisor (Google, 2018) implements much of the Linux interface in a user-space process, so that application calls rarely reach the real kernel. Firecracker (AWS, 2018) is a minimal virtual machine monitor that boots a microVM in roughly 125 milliseconds, and it runs Lambda and Fargate. Kata Containers wrap each pod in a lightweight VM. These keep the container workflow but add a hardware boundary.
how: Every process in Linux has a pointer to a set of namespaces (the nsproxy structure, with one entry per namespace type) and a membership in cgroups. When a process forks, the child inherits both. To get a new view, the program calls clone() with flags such as CLONE_NEWPID, CLONE_NEWNET, CLONE_NEWNS (mount), CLONE_NEWUTS, CLONE_NEWIPC, CLONE_NEWUSER and CLONE_NEWCGROUP, or calls unshare() to leave the current namespaces, or setns() to join an existing one through a file descriptor from /proc/<pid>/ns/. A namespace lives as long as some process or open handle refers to it.
Each namespace virtualises one global table. A PID namespace keeps its own numbering; a process has one PID per level of nesting and sees only the processes in its own namespace and below. The first process in the new namespace is PID 1, and if it exits, the kernel kills all others in the namespace. A network namespace has its own network devices, IP addresses, routing table, firewall rules and port numbers, so two containers can both listen on port 80. A virtual Ethernet pair (veth) connects the container's namespace to a bridge or router in the host namespace. A mount namespace has its own mount table: the runtime builds the container's root file system (usually an overlayfs of image layers) and uses pivot_root so that it becomes "/". A UTS namespace gives its own hostname. An IPC namespace separates shared memory and message queues. A user namespace maps IDs, for example UID 0 inside to UID 100000 outside, so the container's root has no rights on the host; this is the basis of rootless containers.
Cgroups are controlled through a file system, normally mounted at /sys/fs/cgroup. Creating a directory creates a group; writing a PID to its cgroup.procs file moves the process into it; writing to control files sets limits. In v2 there is one tree. A controller must be enabled for the children of a node in cgroup.subtree_control. The main controllers: cpu (cpu.weight sets a relative share when CPUs are contended; cpu.max sets a hard cap, for example "50000 100000" means 50 ms of CPU time per 100 ms period, enforced by the scheduler's bandwidth control); memory (memory.max is a hard limit; memory.high is a soft limit that makes the group reclaim and slow down; memory.min and memory.low protect memory from reclaim; memory.current shows the usage); io (io.max and io.weight for block device bandwidth and IOPS); pids (pids.max limits the number of processes and threads, which stops fork bombs); and cpuset (which CPUs and NUMA nodes the group may use).
The kernel components enforce the limits where they already do their work. The memory controller charges each page to the cgroup that allocated it, covering anonymous memory, page cache and some kernel memory (slab allocations, page tables). When the charge reaches memory.max, the kernel first tries to reclaim from the group: it drops clean page cache and swaps if allowed. If it cannot free enough, the group's OOM killer selects a process in the group and sends SIGKILL; with memory.oom.group set (Linux 4.19), it kills the whole group. The scheduler counts the CPU time used by the group's threads; when the group exhausts its quota within a period, its threads are stopped until the next period. The block layer tracks the I/O issued by each group; in v2 it also attributes buffered writeback to the group that dirtied the pages.
Containers are the combination. A runtime such as runc does these steps: create namespaces with clone, set up the root file system and mounts, create the cgroup and put the process in it, drop Linux capabilities, install a seccomp filter, and execute the program. Kubernetes maps its settings to cgroup files: a CPU request becomes cpu.weight (relative share), a CPU limit becomes cpu.max, and a memory limit becomes memory.max. Docker's --cpus=0.5 writes "50000 100000" to cpu.max and --memory=100m writes 104857600 to memory.max.
Because everything is a file or a system call, the setup can be done by any program, which is why runtimes differ little in mechanism: Docker, containerd, CRI-O, Podman and systemd-nspawn all call the same clone, mount and cgroup operations, and a systemd service with options such as PrivateTmp, ProtectSystem and MemoryMax is a lightweight container too. Observability uses the same files. /proc/<pid>/cgroup shows the group of a process, /proc/<pid>/ns lists namespace handles, lsns lists namespaces, and each cgroup has cpu.stat (including throttling counts), memory.stat, memory.events (including oom_kill counts) and pressure files (cpu.pressure, memory.pressure, io.pressure) that report how long tasks were stalled because of lack of that resource.

example: Build a tiny container by hand and look at the effect. Run unshare --pid --fork --mount-proc --uts bash as root. The shell is now in new PID, mount and UTS namespaces. Run hostname demo: it changes the name inside only. Run ps aux: it shows only two processes, bash as PID 1 and ps, while the host runs hundreds. From another terminal on the host, ps shows the same bash with a large PID such as 48213. That is a namespace: one process, two names. Run ls -l /proc/self/ns/ in both shells; the pid and uts links point to different inode numbers, which identify the different namespaces.
Now add limits. On the host, with cgroup v2: mkdir /sys/fs/cgroup/demo, then echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max, then echo <pid of the bash> > /sys/fs/cgroup/demo/cgroup.procs. Start a busy loop in that shell (while :; do :; done). top shows it using about 50% of one core, although a whole core is free. Check cpu.stat: nr_throttled grows by about 10 per second (one throttle per 100 ms period), because the loop uses its 50 ms in the first half of each period and is stopped for the rest. Now set echo 100M > memory.max and run a program that allocates 200 MB. When usage reaches 100 MB, the kernel reclaims what it can; there is nothing to reclaim for anonymous memory without swap, so it kills the program, the shell says "Killed" (exit status 137 = 128 + 9), and memory.events shows oom_kill 1.
Next, read what Kubernetes does with a pod spec: requests.cpu = 500m, limits.cpu = 1, limits.memory = 256Mi, on a node with cgroup v2. The CPU request becomes a weight, proportional to 500, which matters only when the node is busy. The limit becomes cpu.max = "100000 100000" (100 ms per 100 ms period, one core). The memory limit becomes memory.max = 268435456. If the application is multi-threaded and runs 4 threads in parallel, it consumes the 100 ms budget in 25 ms of wall time and is frozen for the remaining 75 ms. The dashboard shows average CPU of 100% of the limit, while requests that arrive in the frozen window wait up to 75 ms. If its resident memory plus page cache charged to the pod reaches 256 MiB and cannot be reclaimed, the container is killed and Kubernetes reports OOMKilled.
intuition: Blinders for what a program can see, and a budget for what it can spend.
The design is natural because the kernel already keeps one global table for each kind of resource (the process table, the network stack, the mount table) and already does the accounting for each resource (the scheduler, the memory manager). Namespaces add one level of indirection to the tables: instead of one global table, each process points to one of several. Cgroups add one level of grouping to the accounting: instead of charging each process alone, charge a group and compare it with a limit. Neither adds a new mechanism, which is why they cost almost nothing at run time, and why a container is only a process.
mistakes: People often think a container is a small virtual machine. In fact it runs on the host kernel, with no separate kernel, no hardware emulation and no boot. This is why it starts fast and uses little memory, and also why a kernel bug can let a process escape into the host.
People often think namespaces provide security by themselves. In fact they provide separation of views, not a strong boundary. A container that runs as real root with many capabilities, or one that mounts the Docker socket or host paths, can take over the host. Real isolation also needs user namespaces, dropped capabilities, seccomp filters and an LSM profile such as AppArmor or SELinux.
People often think a CPU limit of 2 means the container can use 2 cores at any moment. In fact it means 200 ms of CPU time per 100 ms period, summed over threads, and the container can use many cores at once for a short time and is then frozen. The result is throttling and latency spikes, even when average CPU is low.
People often think a container sees only its own resources in every tool. In fact files such as /proc/meminfo, /proc/cpuinfo and the output of free or nproc show the host's values unless a tool such as lxcfs is used. A runtime that sizes its thread pools or heap from them (older JVMs, many native programs) will think it has the whole machine. Modern JVMs (since JDK 10, and 8u191) and Go 1.25 read cgroup limits.
People often think that setting a memory limit counts only the program's heap. In fact the cgroup also counts page cache, tmpfs, kernel memory and thread stacks. The page cache can be reclaimed, but anonymous memory and tmpfs cannot, so a container that writes large temporary files to tmpfs can hit its limit and be killed.
tradeoffs: Choose containers (namespaces and cgroups) when you run your own or trusted code at high density and want fast start-up: microservices, batch jobs, CI. You give up the strong isolation of a separate kernel. Choose microVMs (Firecracker, Kata) or user-space kernels (gVisor) when you run untrusted or multi-tenant code, such as customer functions or code written by an AI agent, accepting a start-up cost of tens to hundreds of milliseconds, extra memory per instance (some megabytes) and, for gVisor, slower system calls and I/O.
Choose CPU requests (weights) without limits when the node is shared by your own services and you want to use idle capacity and avoid throttling; many latency-sensitive teams do this. Choose CPU limits when you must cap a tenant for fairness or cost, or when you need predictable performance in tests; set them high enough that threads are not frozen in bursts, accepting that unused capacity may sit idle. Choose memory limits almost always, since memory cannot be shared in time like CPU: set the request close to the limit for predictable placement, accepting that exceeding the limit kills the process.
Choose memory.high (a soft limit) with an external monitor when you prefer slow-down and reclaim to sudden death, for example in batch workers; choose memory.max alone when a fast, clear failure is better than a slow, degraded process. Choose rootless containers with user namespaces when you want to reduce the damage from an escape, accepting limits on networking, some file systems and performance. Choose cgroup v2 on current kernels for its unified hierarchy, pressure information and better I/O accounting; v1 remains only for old software.
friction: The isolation is leaky by design. The kernel is shared, so a kernel vulnerability or a mistake in the container configuration can break out; real incidents include runc's CVE-2019-5736 and many kernel privilege escalations. Some resources are not isolated: the CPU cache and memory bandwidth are shared, so a neighbour that streams memory slows others (Intel's resctrl can partition the cache, but it is rarely used); the kernel's own data structures (dentry cache, inotify limits, file-handle table) are partly global; time is shared except for offsets.
Accounting is subtle. Page cache is charged to the group that first read the page, so the next group that reads the same file pays nothing. Kernel memory, network buffers and tmpfs count in confusing ways. The out-of-memory behaviour surprises people: exit code 137 without a stack trace, and the kernel killing the process that is biggest, not the one that leaked. A container can also be slow long before it is killed, because it spends its time in reclaim; the memory pressure files show this.
CPU limits cause throttling, as described, and tools that read the host's CPU count start too many threads. The I/O controller works well only on cgroup v2 and on devices and file systems that support it, and cannot limit a noisy neighbour on a shared network disk. Network bandwidth is not limited by cgroups at all (it needs tc and other tools).
Complexity is the last cost. A container runtime has to combine eight namespace types, several controllers, capabilities, seccomp and an LSM correctly, and each combination has edge cases. Debugging means looking inside the right namespace (nsenter) and the right cgroup. The security of user namespaces is itself debated, because they expose kernel features to unprivileged users and some distributions restrict them.
practice: Set both requests and limits for memory, and be deliberate about CPU limits. Watch cpu.stat (nr_throttled, throttled_usec) and the pressure files, not only average CPU. Size memory limits from observed peak plus headroom, include the page cache your service needs, and alert on memory.events (oom_kill) and the container's restarts with reason OOMKilled.
Make runtimes container-aware. Use a recent JDK (container support is on by default), set -XX:MaxRAMPercentage rather than a fixed heap, give Go's GOMAXPROCS the CPU limit (automatic since Go 1.25, or use automaxprocs), and check Python or Node worker counts. Remember that memory usage in dashboards may include cache; use the working-set metric when you decide about eviction.
Harden by default. Run as a non-root user, drop capabilities (--cap-drop=ALL, add back only what is needed), keep the default seccomp profile or a stricter one, use a read-only root file system, do not mount the Docker socket or host paths into containers, and enable user namespaces or rootless mode where possible. For untrusted code, use gVisor or a microVM instead of plain containers.
To learn and debug, make a container by hand as in the example, then look at a real one: docker inspect for the PID, lsns -p <pid> for its namespaces, nsenter -t <pid> -n ip addr to run commands in its network namespace, and cat /proc/<pid>/cgroup and the files in that group to see its limits and counters. systemd-cgtop and systemd-cgls show the cgroup tree and usage on a host.
interview: What exactly is a container in Linux terms, and how is it different from a virtual machine? || A container is a normal process (or group) started in a set of new namespaces (pid, net, mnt, uts, ipc, user, cgroup) and placed in a cgroup, usually with an overlayfs root, dropped capabilities and a seccomp filter. It shares the host kernel. A VM runs its own kernel on virtual hardware, with stronger isolation and a higher cost in start-up time and memory.
A pod's JVM is killed with OOMKilled although the heap is under the limit. What are the likely causes? || The cgroup counts more than the heap: metaspace, thread stacks, direct buffers, code cache, native libraries, page cache and tmpfs. Check memory.stat, set MaxRAMPercentage lower, bound direct memory and thread counts, and compare the working set with memory.max.
Explain cpu.weight versus cpu.max, and which you would set for a latency-sensitive service. || cpu.weight is a relative share, used only when CPUs are contended; unused CPU is available to others. cpu.max is a hard cap per period, which freezes the group when its budget is gone. For latency-sensitive services I prefer weight (requests) without a tight cap, or a limit large enough that bursts do not exhaust it, and I monitor throttling.
What does a PID namespace do, and what must PID 1 in a container handle? || It gives its own numbering and a limited view of processes. PID 1 is special: it must reap orphaned child zombies, and by default signals without handlers are not delivered to it from inside, so a plain application may ignore SIGTERM. Use an init process (tini, --init) or handle signals.
When are namespaces and cgroups not enough, and what do you use? || For untrusted or multi-tenant code, because the kernel is shared and the attack surface is large. Use microVMs (Firecracker, Kata) or gVisor, plus seccomp, user namespaces and a minimal image. Also, shared hardware resources (cache, memory bandwidth) are not isolated, so noisy neighbours need dedicated nodes or cache partitioning.
quiz: What does a namespace limit, and what does a cgroup limit? || A namespace limits what a process can see (its view of PIDs, network, mounts and so on). A cgroup limits what it can use (CPU, memory, I/O, process count).
Why can two containers on one host both listen on port 80? || Each has its own network namespace, with its own interfaces, addresses and port table, so port 80 in one is unrelated to port 80 in the other.
A container has cpu.max = "50000 100000" and runs 4 busy threads. How much wall time passes before it is throttled in each period? || The budget is 50 ms of CPU per 100 ms. Four threads use 4 ms of CPU per ms of wall time, so the budget is gone after 12.5 ms, and the threads are frozen for the remaining 87.5 ms.
Why does exceeding memory.max kill a process even when plenty of memory is free on the host? || The limit is per cgroup. When the group's charged memory reaches memory.max and the kernel cannot reclaim enough (page cache first), the group's OOM killer kills a process, regardless of free memory elsewhere.
Your platform runs customers' code in containers. Is a hardened container enough? || Usually not for hostile tenants. A shared kernel means one kernel exploit breaks all isolation. Add user namespaces, seccomp and an LSM, and prefer gVisor or microVMs (Firecracker, Kata) for untrusted code, accepting more start-up time and memory.
