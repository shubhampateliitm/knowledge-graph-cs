@@ replication
value: Replication keeps copies of the same data on several machines. It is how distributed systems survive machine failures without losing data, serve more reads than one machine could, and put data closer to users in other regions. Almost every system on this map replicates something: Kafka partitions, Postgres standbys, Elasticsearch shards, Cassandra rows, HDFS blocks, etcd's log.
how: There are three main styles. Single-leader (primary–replica): all writes go to one leader, which sends a stream of changes (usually its log) to followers. Simple and consistent per leader, but the leader limits write throughput and failover must be handled. Multi-leader: several nodes accept writes, typically one per region, and exchange changes; this needs conflict resolution when the same data is changed in two places. Leaderless (Dynamo-style: Cassandra, Riak, DynamoDB's original design): clients write to several replicas and read from several, using quorums (if W + R > N, reads and writes overlap) plus repair mechanisms (read repair, hinted handoff, Merkle-tree anti-entropy).
Replication can be synchronous (the write waits for replicas, safer but slower) or asynchronous (faster, but recent writes can be lost if the leader dies). Many systems mix the two: Kafka waits for the in-sync replica set; Postgres can wait for one synchronous standby. When the leader fails, a follower must be promoted, ideally by a consensus protocol so two leaders never coexist ('split brain'), and clients must be redirected. Fencing tokens or terms stop an old leader from writing after it has been replaced.
What replication copies varies: the physical log (WAL shipping in Postgres), logical changes (rows or events), or whole state (snapshots). Replicated logs are the cleanest: if every replica applies the same log in the same order, they converge.
How the lower layers add value: the write-ahead log (Layer 2) is what gets shipped; TCP (Layer 3) carries it; distributed systems theory (Layer 3) defines which failures can be survived; combinatorics (Layer 4) proves quorums overlap; and the speed of light (Layer 5) sets the price of synchronous replication across regions, roughly 1 ms per 100 km of round trip in fibre.
intuition: Important documents are kept in several fireproof safes in different buildings. Either one clerk updates the master copy and couriers updates to the others (leader-based), or any clerk can update any copy and they reconcile later (leaderless). The safer you want to be, the longer you wait for couriers before telling the customer 'done'.
friction: Replication lag creates anomalies: a user writes, then reads from a stale replica and their change seems to vanish (read-your-writes violations), or sees time go backwards (monotonic-read violations). Failover is the riskiest moment: an asynchronous follower may be missing writes, and a falsely detected failure can cause split brain. Conflict resolution in multi-leader and leaderless systems (last-writer-wins silently drops data; CRDTs and version vectors are safer but more complex) is a frequent source of bugs. And replicas cost money: three copies triple storage, which is why object stores and HDFS also use erasure coding.

@@ partitioning
value: Partitioning (also called sharding) splits a dataset into pieces that live on different machines, so that storage, writes and queries scale beyond one machine. Kafka topics have partitions, Spark DataFrames have partitions, Cassandra and DynamoDB distribute rows across nodes, Elasticsearch splits indexes into shards, and lakehouse tables are partitioned by date or clustered by key. Partitioning is the main source of parallelism in data systems.
how: A partitioning function maps each record's key to a partition. Range partitioning assigns contiguous key ranges (A–F, G–M, …); it keeps related keys together and supports range scans, but sequential keys like timestamps create hot spots. Hash partitioning applies a hash function and takes the result modulo the number of partitions; it spreads load evenly but destroys ordering across keys. Consistent hashing places keys and nodes on a ring so that adding a node moves only about 1/N of the keys; virtual nodes even out the load.
Partitions must be rebalanced as data grows or nodes change: fixed many-partitions-per-node schemes (Kafka, Elasticsearch, Riak), dynamic splitting of ranges (HBase, CockroachDB, TiKV), or per-node partitioning. Requests must be routed to the right partition, either through a routing tier, a coordination service that holds the map, or client-side knowledge. Secondary indexes are hard: either each partition indexes its own data (local index, queries must scatter to all partitions) or the index is partitioned by the indexed value (global index, writes must update remote partitions).
In compute engines, repartitioning by key is the shuffle: data is hashed to new partitions so that all rows with the same key meet in one task for joins and aggregations.
How the lower layers add value: hash tables and number theory (Layers 3–4) give the mapping; probability (Layer 4) explains how evenly keys spread; power laws (Layer 4) explain why real keys are skewed; and Amdahl's law (Layer 4) explains why one oversized partition limits the whole job.
intuition: A post office sorts letters into bins by postcode so many workers can deliver in parallel. Sorting by postcode range keeps neighbors together, but one busy postcode can overflow its bin. Sorting by a scrambled code spreads letters evenly but scatters neighbors. Either way, the sorting rule must be known by everyone who needs to find a letter.
friction: Skew is the constant enemy: a celebrity user, a popular product or one giant customer can overload one partition while others idle. Repartitioning is expensive and often breaks ordering guarantees. Choosing the partition count early is hard to change later (Kafka). Cross-partition operations, such as transactions, joins and global secondary indexes, are slow or complex. Many small partitions waste overhead (small files, small Kafka partitions); few large ones limit parallelism.

@@ lsm
value: The log-structured merge tree (LSM tree, O'Neil et al., 1996) is the storage engine design behind RocksDB, LevelDB, Cassandra, ScyllaDB, HBase, CockroachDB's Pebble, InfluxDB and many more. Its value is very fast writes: it turns random updates into sequential appends, which disks and SSDs handle far better. It is the engine of choice for write-heavy workloads such as time series, event data, messaging state and stream-processor state.
how: Writes go to two places: an append-only write-ahead log on disk (for crash safety) and an in-memory sorted structure called the memtable (often a skip list). When the memtable fills, it is written out as an immutable, sorted file: an SSTable (sorted string table), with an index and a bloom filter. Over time many SSTables accumulate, so background compaction merges them, like the merge step of merge sort, keeping only the newest version of each key and removing deleted keys (marked by tombstones).
Reads check the memtable first, then SSTables from newest to oldest. Bloom filters let a read skip files that definitely do not contain the key, and indexes find the right block within a file. Compaction strategies trade costs: leveled compaction (LevelDB, RocksDB default) keeps files in levels of increasing size with non-overlapping key ranges, giving better read and space efficiency but more write amplification; size-tiered compaction (Cassandra's original) merges similar-sized files, writing less but using more space and reading more files.
How the lower layers add value: the write-ahead log and bloom filters (Layer 2) make it safe and fast; external merge sort and skip lists (Layer 3) are its algorithms; the external-memory model (Layer 3) explains why batching writes into large sequential blocks wins; and the physics of flash (Layer 5), which must erase a whole block before rewriting and wears out with each erase, is exactly why append-only designs fit SSDs.
intuition: Instead of filing every new paper into the right folder immediately (slow, lots of walking), you put new papers in an inbox in order of arrival. When the inbox fills, you sort it and file it as a new sorted stack. Every so often you merge stacks into bigger sorted stacks and throw away outdated copies. Finding something means checking the inbox and then the stacks, newest first, and a quick 'definitely not in this stack' card (bloom filter) saves most of the searching.
friction: The famous trade-off is the RUM conjecture: you cannot minimize read cost, update cost and memory/space cost at once. LSM trees pay with write amplification (each byte rewritten several times during compaction, which also wears SSDs), read amplification (several files may need checking, especially for range scans), and space amplification (old versions linger until compaction). Compaction competes with foreground work for I/O and CPU, causing latency spikes and 'write stalls' when it falls behind. Tombstones can pile up and slow reads. Tuning RocksDB has dozens of knobs, and it is a real skill.

@@ btree
value: The B-tree (Bayer and McCreight, 1970–72) is the most important index structure in databases. PostgreSQL, MySQL InnoDB, SQLite, SQL Server, Oracle, MongoDB's WiredTiger and most file systems use B-trees or B+trees. Their value is fast lookups and range scans on data much larger than memory, with only a few disk reads per lookup, and efficient in-place updates.
how: A B-tree is a balanced search tree where each node is a fixed-size page (for example 8 KB in Postgres, 16 KB in InnoDB) holding many sorted keys and child pointers. Because each node has hundreds of children (high fan-out), the tree is very shallow: three or four levels can index billions of rows. A lookup reads the root page (usually cached), follows the pointer for the right key range, and repeats down to a leaf. In a B+tree, all values live in the leaves, and leaves are linked in key order, so range scans just walk along the leaf level.
Inserting into a full node splits it into two and pushes a separator key up to the parent; splits can cascade to the root, which is how the tree grows taller while staying balanced. Deletes may merge or redistribute nodes. Concurrency control uses latches on pages ('latch crabbing': lock the child, then release the parent if the child is safe). Crash safety comes from the write-ahead log: page changes are logged before pages are written, because a split touches several pages that must change atomically.
How the lower layers add value: the external-memory model (Layer 3) explains the design: cost is counted in page reads, so maximize fan-out per page; storage devices (Layer 3) read in blocks; the page cache and buffer pool keep the top levels in memory; trees and proofs by induction (Layers 3–4) guarantee balance and logarithmic height.
intuition: A B-tree is a well-organized encyclopedia set. The spine of each volume tells you its range (A–Bay, Bay–Cal…), the volume's guide words tell you the page, and you find any entry by opening only two or three books. When one volume gets too thick, the publisher splits it into two and updates the spines.
friction: B-trees pay for reads with random writes: updating a row in place means rewriting a whole page somewhere on disk, plus the WAL entry. Page splits cause fragmentation and write amplification, and random keys such as UUIDv4 spread inserts across the whole tree, hurting cache hit rates (one reason time-ordered UUIDv7 is now popular). Under heavy write loads, LSM trees usually win; under read-heavy workloads with range queries and updates in place, B-trees usually win. Concurrency on hot pages (like the rightmost leaf for increasing keys) can become a bottleneck.

@@ mvcc
value: Multi-version concurrency control lets many transactions read and write the same data at the same time without readers blocking writers or writers blocking readers. Instead of overwriting a row, the database keeps several versions and shows each transaction the version that matches its snapshot. PostgreSQL, MySQL InnoDB, Oracle, SQL Server (snapshot mode), CockroachDB, Spanner, and every lakehouse table format (each commit is a new table version) use MVCC. Its value is high concurrency with consistent reads, plus cheap features like time travel and consistent backups.
how: Each write creates a new version tagged with the creating transaction's ID or commit timestamp. A transaction starts with a snapshot: a timestamp, or a list of which transactions were committed at that moment. When it reads a row, it walks the versions and picks the newest one that was committed before its snapshot. Writes to the same row by concurrent transactions are detected: under snapshot isolation, the first committer wins and the other aborts (or waits on a row lock, depending on the system).
Implementations differ. PostgreSQL stores all versions in the table heap and marks them with xmin and xmax transaction IDs, so updates create new tuples and VACUUM removes dead ones later. InnoDB keeps the latest version in place and rebuilds older versions from undo logs. Distributed databases use timestamps from hybrid logical clocks (CockroachDB) or TrueTime (Spanner). Lakehouse formats keep old data files until a retention period expires, so 'version 41' of a table can still be read.
Plain snapshot isolation allows a subtle anomaly called write skew: two transactions read overlapping data, each writes a different row, and together they break a rule neither broke alone (for example, two doctors both going off call). Serializable Snapshot Isolation (PostgreSQL's SERIALIZABLE level) detects these dangerous patterns and aborts one transaction.
How the lower layers add value: concurrency control and isolation theory (Layer 3) define what 'correct' means; order theory and graph theory (Layer 4) define serializability as the absence of cycles in a dependency graph; and clocks (Layers 3 and 5) are why distributed MVCC is hard: there is no single global 'now'.
intuition: MVCC is like a shared document where every edit creates a new saved version. When you open the document, you get a frozen copy of how it looked at that moment, and others can keep editing without disturbing you. If two people edit the same paragraph from the same starting copy, the second one to save is told 'someone changed this since you opened it'.
friction: Old versions take space and must be garbage-collected; long-running transactions prevent cleanup and cause bloat (a classic PostgreSQL problem). Snapshot isolation is not serializable, and many applications run at weaker isolation than they believe. Version chains slow down reads of frequently updated rows. In distributed systems, snapshot timestamps need careful clock handling, which costs latency (Spanner's commit wait) or causes retries (CockroachDB's uncertainty restarts).

@@ columnar
value: Columnar storage stores each column of a table together instead of storing each row together. For analytics, where queries touch a few columns of billions of rows, this means reading far less data and compressing it far better. It is the storage idea under Parquet, ORC, Arrow, Snowflake, BigQuery, Redshift, ClickHouse, DuckDB, Druid, Pinot, Vertica and Databricks Photon, and it is the main reason analytical queries became 10–100× faster than on row stores.
how: A row store lays out 'id, name, country, amount' for row 1, then row 2, and so on. A column store lays out all ids, then all names, then all countries, then all amounts, usually in chunks (Parquet row groups of ~128 MB, split into column chunks and pages). A query like SUM(amount) WHERE country = 'IN' reads only the country and amount columns.
Values in one column are similar, so they compress well. Dictionary encoding replaces repeated strings with small integers; run-length encoding stores 'IN × 50,000'; delta encoding stores differences between sorted numbers; bit-packing uses only as many bits as needed. General compressors (Snappy, LZ4, Zstd) then shrink the result further. Each chunk keeps statistics (min, max, null count), so whole chunks can be skipped. Execution engines operate directly on encoded columns where possible and process values in vectors of thousands at a time, using SIMD instructions. Late materialization stitches rows back together only for the rows and columns that survive filters.
How the lower layers add value: the memory hierarchy and cache lines (Layer 3) reward contiguous, homogeneous data: every byte of each 64-byte line is useful; SIMD (Layer 3) processes 8–64 values per instruction; information theory (Layer 4) says similar values have low entropy and compress well; and the physics of memory bandwidth (Layer 5) is the real limit, so reading fewer bytes beats computing faster.
intuition: A school stores report cards. To compute the average maths mark, you could open every student's full report card (row store), or you could keep one sheet with every student's maths mark (column store) and add them up in one pass. The second is obviously faster, and the sheet compresses well because marks are all small numbers.
friction: Writing and updating single rows is expensive: one row touches every column file. That is why column stores batch writes, use delta stores or merge-on-read, and struggle with frequent small updates and point lookups. Reconstructing many columns for a wide 'SELECT *' loses the advantage. Very small files and too many columns hurt. And the best performance requires sorting or clustering data so that statistics are selective, which is extra design work.
