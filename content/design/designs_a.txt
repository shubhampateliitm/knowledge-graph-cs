@@ rate-limiter
title: Design a distributed rate limiter
category: Infrastructure
level: Senior / Staff
concepts: ratelimit, redis, apigateway, envoy, partitioning, conshash, replication, cap, backpressure, retries, circuitbreaker, cms, hwclocks, queueing, loadbalancing, cachelayer, amortized, observability
summary: A rate limiter decides, for every incoming request, whether the caller has used up its allowed share in the current period. Callers are identified by an API key, a user id or an IP address. The rules are simple: "100 requests per minute per key". What makes it hard is that the limit is global but the traffic is spread over hundreds of gateway machines. The limiter sits on the hot path of every request, so it must add under 2 ms at the 99th percentile, must not become a single point of failure, and must stay reasonably exact even when machines fail or clocks drift. We design a limiter for a public API platform that sits behind a fleet of gateways and uses a sharded in-memory store.
requirements: Functional requirements. Each request is checked against one or more rules. A rule has a key template (for example "api_key" or "ip + route"), a limit, a period and an algorithm. When a request is over the limit, the gateway returns HTTP 429 (Too Many Requests, RFC 6585) with a Retry-After header and headers that show the limit, the remaining quota and the reset time. Rules can be changed at runtime without a deploy. Different customer tiers have different limits, and a few internal callers are exempt.
Non-functional requirements. Latency: the check adds at most 2 ms at p99. Availability: if the limiter is down, the API must stay up. We choose "fail open" (allow the request) for ordinary traffic and "fail closed" only for a small list of expensive or abusive routes. Accuracy: we accept up to about 10 percent error on the count near the limit, because a limit is a protection and not a bill. Billing-grade quotas are a different system. Scale: tens of millions of active keys and a few hundred thousand checks per second at peak. Fairness: one hot customer must not slow down the checks of other customers.
Assumptions. The platform serves 5 billion API requests per day. Traffic is spread over 300 gateway instances in 3 availability zones. Most keys are small customers; the top 100 keys send about 30 percent of the traffic.
estimates: Average load. 5 billion requests per day divided by 86,400 seconds is about 58,000 requests per second. Peak is usually 4 to 5 times the average. Use 5: 58,000 times 5 is about 290,000 requests per second.
Counter operations. Each request is checked against two rules (per API key and per IP), so the peak is 290,000 times 2 = 580,000 counter operations per second. A single Redis primary executes roughly 100,000 simple commands per second. A Lua script that reads and writes a few fields is slower, say 60,000 to 70,000 per second. We want 50 percent headroom, so one shard should carry at most 35,000 operations per second. 580,000 divided by 35,000 is about 17. We round up to 20 shards, each with one replica in another zone, so 40 Redis processes in total.
Memory. Assume 20 million keys are active within the window. A token bucket needs two numbers: the token count and the last refill time. With the key name and Redis object overhead this is about 200 bytes per key. 20 million times 200 bytes is 4 GB in total, or 200 MB per shard. Memory is not the problem. Compare the sliding window log, which stores one timestamp per request: a limit of 100 per minute means up to 100 entries of about 16 bytes, so 1.6 KB per key, and 20 million keys need 32 GB. This is 8 times more memory for the same job.
Network. A check sends about 100 bytes and receives about 50 bytes. 580,000 times 150 bytes is about 87 MB per second, roughly 0.7 Gbit per second across the whole fleet. This is small.
Latency budget. A round trip inside one availability zone is about 0.3 to 0.5 ms. Redis executes the script in about 20 to 50 microseconds. So a remote check costs about 0.5 to 1 ms, inside our 2 ms budget. A cross-zone call costs about 1 to 2 ms, so gateways should prefer a same-zone replica for reads only when they can tolerate stale counts.
Local batching. If gateways fetch quota in chunks (a "lease" of 10 tokens), remote calls drop by up to 10 times: 580,000 divided by 10 is 58,000 per second, which 20 shards carry easily.
api: The public API does not change. The limiter appears as a library or sidecar with one call: allow(rule_id, key, cost=1) returns {allowed, limit, remaining, reset_after_ms}. The gateway turns this into headers.
Internal check call (gateway to limiter service, gRPC): ShouldRateLimit(domain, descriptors[], hits_addend) returns overall_code OK or OVER_LIMIT plus one status per descriptor. This is the shape used by the Envoy global rate limit service.
Rule admin API: PUT /v1/rules/{rule_id} with body {key_template, limit, period_s, algorithm, burst, fail_mode, tier}. GET /v1/rules lists the rules. Changes are written to a config store and pushed to all gateways, which apply them within seconds.
Response headers on every API response: RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (the names follow the IETF draft for RateLimit header fields; many APIs still use the older X-RateLimit-* names). On a rejection the status is 429 and Retry-After carries the number of seconds to wait (RFC 9110).
datamodel: Counter state lives in Redis. The key is "rl:{rule_id}:{identity}", for example "rl:api_key_minute:ak_81f3". For a token bucket the value is a hash with two fields: "tokens" (a number) and "ts" (the last refill time in milliseconds). The key has an expiry (TTL) equal to the time the bucket needs to refill completely, plus a small margin. When the caller goes quiet, the key disappears and memory is freed without any cleanup job.
For a fixed or sliding window counter the key includes the window number: "rl:{rule_id}:{identity}:{window_start}". The value is one integer, and the TTL is two window lengths. The sliding window counter reads the current and the previous window and weights the previous one by the part of the window that has not yet passed.
Sharding. The shard is chosen by consistent hashing of "{rule_id}:{identity}". All checks for one key must reach the same shard, because a counter is only correct when one process owns it. Two rules for the same request go to different shards, so one request may need two parallel calls.
Rules are small (a few thousand at most) and are stored in a normal config database. Every gateway keeps all rules in memory and receives updates by watch or by periodic poll. They are never read on the request path from a remote store.
design: The request path. A client calls the API. The load balancer sends the request to a gateway instance. The gateway authenticates the caller to get the API key and tier, then picks the rules that apply to this route and tier. For each rule it builds a key and calls the limiter. If any rule says "over limit", the gateway stops and returns 429 with Retry-After. Otherwise the request goes on to the backend. The check happens before the expensive work, so a rejected request costs the platform only a few hundred microseconds.
Where the limiter runs. We put the decision logic in a thin library inside the gateway (for example an Envoy filter calling a rate limit service). The state is in a sharded Redis cluster. The gateway computes the shard from the key with a consistent hash ring, so it talks directly to the right shard and no proxy hop is needed. Consistent hashing means that adding or removing a shard moves only about 1/N of the keys, so a resize does not reset every counter.
The algorithm. We use the token bucket for most rules. A bucket has a capacity (the burst size) and a refill rate (the average rate). Each request takes tokens. The bucket allows short bursts and a steady average, which is what API users expect. For rules where the customer-visible promise is "N per calendar minute" we use the sliding window counter, because it needs only two integers per key and removes the burst-at-the-boundary problem of the plain fixed window. A fixed window lets a client send 100 requests at 12:00:59 and 100 more at 12:01:00, which is 200 requests in two seconds against a "100 per minute" rule.
Atomicity. A check is read, compute, write. If two gateways do this at the same time without protection, both read the same token count and both subtract, so one update is lost and the client gets extra requests. We run the whole step as one Lua script inside Redis. Redis runs commands on a single thread, so the script is atomic without locks. The script takes the time as an argument or reads it from Redis, and returns allowed, remaining and reset time in one reply.
Local leases to cut load. For very hot keys the shard would see most of its traffic from one key. A gateway can ask for a lease: "give me up to 10 tokens". It spends them locally with no network call and asks again when they run out. This turns many small remote calls into few big ones (an amortized cost). The price is accuracy: tokens leased to a gateway that then sees no traffic are lost for a short time. We cap the lease at a small share of the remaining quota, so that 300 gateways cannot lock away more than a few percent of a limit.
Rules and observability. Every decision increments local metrics (allowed, rejected, per rule). Rejections are sampled into a log with the key, rule and count. Without this the operator cannot tell if a limit is too strict or an attack is under way.

deepdive: Algorithm choice and exactness. The four classic algorithms differ in memory, burst behavior and exactness. The token bucket stores two numbers and allows bursts up to capacity. The leaky bucket also stores two numbers but outputs a smooth rate, which suits a queue in front of a slow backend. The fixed window counter stores one number but allows up to 2 times the limit around a window boundary. The sliding window log is exact but costs memory in proportion to the limit. The sliding window counter estimates the rolling count as current + previous x (1 - elapsed/window). If the previous window had 80 requests, the current has 30 and 25 percent of the window has passed, the estimate is 30 + 80 x 0.75 = 90. The error depends on how evenly the previous window was spread, and Cloudflare reported that in a large sample only a very small share of requests were wrongly allowed or blocked. For API protection this is good enough.
Clock and time. If every gateway uses its own clock to compute refills, a gateway whose clock is 2 seconds behind would compute negative elapsed time or double refills. The fix is to let the store provide the time. Inside a Redis script, we pass the gateway's time only as a hint and use the Redis server time (the TIME command, or the time in the script argument validated against it) for the refill. One clock per shard is consistent for every key on it. We also clamp elapsed time to be at least zero and at most the full refill time, so a clock jump cannot create or destroy more than one full bucket.
Race conditions and the hot key. A hot key sends all its traffic to one shard and one Redis thread. At 35,000 operations per second per shard, a single customer with 50,000 requests per second cannot be handled by one key. Options: use local leases so the shard sees one call per 10 requests; split the key into K sub-keys ("ak_81f3#0..#3") and give each a quarter of the limit, with a gateway choosing a sub-key at random; or enforce the limit loosely at the edge in each gateway (a local token bucket with limit/300) and reconcile with the shard every second. Each method trades some accuracy for throughput. Splitting is easy but wastes quota when traffic is uneven.
Synchronization versus accuracy. A fully centralized limiter is exact but each request pays a network round trip. A fully local limiter pays nothing but cannot know the global count. The usual middle way is a periodic sync: each gateway counts locally and every 100 ms to 1 s sends its count to the store and receives the global count back. Between syncs it may allow up to (limit x local share) extra requests. The error is bounded by sync interval x peak rate. With a 1 s sync and a 1,000 per minute limit, the possible overshoot is small compared to the limit. Count-min sketches can replace the exact counter when the number of keys is huge, for example per-IP limits against a botnet with 100 million addresses, at the cost of occasional over-counting.
Failure of the store and fail-open. If a shard does not answer within 5 ms, the gateway must decide alone. Fail open means allow the request and count it locally. A circuit breaker opens after, say, 50 percent of calls fail within 10 seconds, and the gateway uses only its local bucket for 5 seconds before trying again. This keeps the API available at the cost of weaker limits. For routes where a missing limit is dangerous (a password login, an SMS send), the rule says fail closed, or uses a stricter local limit.
Rules, tiers and cost. A request can have a cost: a search may cost 5 tokens and a read 1. The Lua script takes the cost as an argument. This is better than separate limits because it gives one budget that reflects real load on the backend. Rules are evaluated in a fixed order and the first rejection wins, but all matching counters are still read so that the Retry-After is the longest wait.
tradeoffs: Centralized store versus local counters. Choose a central store (Redis) when the limit must hold across all gateways within a few percent, when keys are many and values small, and when a 0.5 to 1 ms cost per request is acceptable. Choose local counters with periodic sync when traffic per key is very high, when latency budget is tight (under 100 microseconds), or when you cannot afford a hard dependency. You give up exactness in the second case and latency in the first.
Token bucket versus sliding window. Choose the token bucket when clients may burst and you care about the average rate, which is the case for most APIs. Choose the sliding window counter when the limit is a contract such as "1,000 per minute" and the customer sees the window. Choose the sliding window log only for small limits with high value per request (for example 5 password attempts per hour), where exactness is worth 8 times more memory.
Redis versus an embedded or custom store. Choose Redis (or Valkey) when you want a ready, well-known tool with Lua scripts and replicas. Choose a custom in-memory service (for example a Go or Rust process that owns shards and speaks gRPC) when you need over 500,000 operations per second per node, custom eviction, or leases built into the protocol. The custom service costs engineering time and operations, and Redis rarely loses on the first two years of growth.
Fail open versus fail closed. Choose fail open for normal API traffic: an outage of the limiter should not become an outage of the product. Choose fail closed for abuse-sensitive actions and for expensive calls where a flood can bring down the backend. Many teams get it wrong by choosing one policy for all routes.
Where to enforce: edge, gateway or service. Choose the edge/CDN for coarse per-IP protection against floods, since it stops the traffic before it reaches your network. Choose the gateway for per-customer quotas, because it knows the identity. Choose in-service limits (concurrency limits, load shedding) to protect against your own bugs and slow dependencies. A real system uses all three, each with a different purpose.
failures: A Redis primary fails. Its replica is promoted, which takes a few seconds. Counters written in the last moments may be lost because replication is asynchronous, so some customers get a little extra quota. This is acceptable. During the failover, calls to that shard time out, the circuit breaker opens, and gateways fall back to local limits for that shard only. Other shards are unaffected.
A whole availability zone fails. One third of the gateways and one third of the replicas disappear. The load balancer sends traffic to the other zones, and replicas in the surviving zones become primaries. Since the limiter state is small and every counter has a short TTL, even a total loss of state only gives each customer one fresh bucket. The worst result is a short period of weaker limits, never a wrong block.
Network partition between gateways and one shard. Gateways in the partition cannot reach the shard. They fail open after the timeout. This is the CAP choice in practice: we pick availability and accept that the count may be wrong for a while. When the partition heals, counters are still valid because they never moved.
Overload of the limiter itself. If the limiter slows down, every request waits for it, and the slow limiter would cause a queue in gateways and then a cascade. We protect with a hard timeout of 5 ms, a bounded number of in-flight limiter calls per gateway and backpressure: when the limit on calls is reached, the gateway skips the remote check and uses the local bucket.
Bad rule deploy. A rule with a limit of 0 or a wrong key template can block every customer. Rules are validated, rolled out to 1 percent of gateways first, and compared with the previous decision rate. A "kill switch" setting turns all rules to log-only mode in seconds.
Clock jump. If a shard host changes its clock by an hour, buckets may refill completely or never. Elapsed time is clamped, and the host uses a monotonic clock source for intervals. Alerts fire if the ratio of rejections changes by more than a set factor in a minute.
evolution: At 1,000 users, one gateway with an in-process token bucket per key is enough. There is no distributed problem; a hash map and a mutex do the job. At 1 million users and a few gateways, add one Redis primary and a replica, with the Lua script. At 100 million users and 300 gateways, shard Redis with consistent hashing, add local leases and a circuit breaker. At 1 billion users, add a hierarchy: edge limits per IP at the CDN, regional limiters per customer, and a slow global reconciliation every few seconds that moves quota between regions, so that no request ever crosses an ocean for a counter. Approximate sketches handle the long tail of keys, and exact counters are kept only for paying customers.
followups: Why not count requests in the database with an UPDATE ... SET count = count + 1? || A row update takes a lock and a disk write, so one hot key serializes at maybe a few thousand updates per second and adds milliseconds of latency. An in-memory store with atomic scripts handles tens of thousands per second per shard in microseconds. Counters also do not need durability, because losing them only gives a customer a fresh quota.
How do you make the check atomic across many gateways? || Run the read-compute-write inside one Lua script on the shard that owns the key. Redis runs one command at a time, so there is no lost update. The alternative is compare-and-swap with retries, which wastes round trips under contention.
What happens at a fixed window boundary and how do you fix it? || A client can send the full limit at the end of one window and again at the start of the next, so twice the limit within a short time. The sliding window counter weights the previous window by the remaining fraction, and the token bucket removes the boundary completely.
How do you handle one customer sending 50,000 requests per second on one key? || Use local leases of several tokens, or split the key into sub-keys with a share of the limit each, or enforce at the gateway with a local bucket and sync to the shard every second. Accept a bounded error. Also consider that such a customer may need a dedicated limit tier and capacity.
Should the limiter fail open or closed? || Fail open for normal traffic so the limiter is not a single point of failure, with a circuit breaker and local fallback buckets. Fail closed for sensitive routes such as login or SMS. The policy is per rule, not global.
How do clients behave when they get a 429, and how does that change the design? || Well-behaved clients wait for Retry-After and use exponential backoff with jitter. Bad clients retry immediately and make the load worse, so the limiter must be cheap for rejected requests, and we may add a penalty box that blocks a key for some seconds after repeated violations.
How do you limit by IP when many users share one IP, such as a mobile carrier NAT? || An IP limit is a coarse defense, so set it high and combine it with the authenticated identity once known. Use a lower limit for anonymous traffic and a higher one for signed-in users. Add signals such as device id, and challenge with a CAPTCHA instead of a hard block.

@@ kv-store
title: Design a distributed key-value store like Dynamo
category: Infrastructure
level: Senior / Staff
concepts: nosql, dynamodb, cassandra, conshash, partitioning, replication, quorum, vectorclocks, gossip, failuredetect, merkle, antientropy, cap, pacelc, consmodels, lsm, wal, bloom, storageengine, crdt, hlc, raft, consensus, idempotence
summary: We build a key-value store that keeps petabytes of small values across thousands of commodity machines, answers get and put in single-digit milliseconds, and keeps accepting writes while machines, racks and even a whole zone fail. This is the design of Amazon's Dynamo (2007), the root of Cassandra, Riak and Voldemort, and an ancestor of DynamoDB. The hard part is the choice made by the CAP theorem: we put availability and latency first, so replicas can disagree for a short time, and we need mechanisms (versioning, hinted handoff, read repair, anti-entropy) that bring them back together without a central coordinator.
requirements: Functional requirements. put(key, value, context) stores a value of up to a few hundred KB. get(key) returns the value, or several conflicting values with a context that the next put must carry. delete(key) writes a tombstone. Keys are opaque byte strings; there is no query by value and no multi-key transaction. The store is multi-tenant, and each table can choose its own replication factor and consistency level.
Non-functional requirements. Always writable: a put must succeed if at least one healthy replica set member is reachable in the local zone. Latency: p99 under 10 ms for reads and writes inside one region. Scale: add nodes online and see throughput grow linearly. No single point of failure and no master that all requests need. Durability: an acknowledged write must survive the loss of any one node, and with W=2 of N=3 it survives the loss of one zone. Consistency: eventual by default, with tunable quorums for callers that want more.
Assumptions. 5 billion items of 1 KB on average. Peak load 300,000 reads per second and 100,000 writes per second. Replication factor N=3, spread over 3 availability zones.
estimates: Data size. 5 billion items times 1 KB is 5 TB of user data. With 3 replicas this is 15 TB. A log-structured merge tree (LSM) needs free space for compaction and has some metadata, so we plan to fill disks to at most 50 percent. 15 TB divided by 0.5 is 30 TB of raw disk.
Request load on the replicas. A write goes to all 3 replicas: 100,000 times 3 is 300,000 replica writes per second. A read with R=2 contacts 2 replicas (one returns data, the other a digest): 300,000 times 2 is 600,000 replica reads per second.
Per-node capacity. A node with NVMe SSDs and an LSM engine handles roughly 50,000 point reads per second when most reads miss the cache, and about 30,000 writes per second. We want 40 percent headroom for compaction, repairs and failures, so we plan for 30,000 reads and 18,000 writes per second per node. Reads need 600,000 divided by 30,000 = 20 nodes. Writes need 300,000 divided by 18,000 = about 17 nodes. Reads dominate, so we choose 24 nodes (8 per zone). Each node holds 2 TB of usable disk, so 24 times 2 TB is 48 TB. Fill is 15 divided by 48, about 31 percent, which is healthy.
Virtual nodes. We give each node 128 tokens on the ring, so 24 times 128 = 3,072 tokens. Each token owns about 1/3,072 of the key space. When a node joins, it takes about 128 small ranges from many peers, not one big range from one peer.
Network. Client traffic is 300,000 reads times 1 KB plus 100,000 writes times 1 KB, about 400 MB/s. Replication adds 100,000 times 2 extra copies times 1 KB, about 200 MB/s. Across 24 nodes this is under 30 MB/s per node, so the 10 Gbit/s links are almost idle.
Hinted handoff. If a node is down for one hour, the others store its writes as hints. Each node is a replica for 3 out of 24 shares of the data, so it receives 100,000 times 3 / 24 = 12,500 writes per second. In one hour that is 12,500 times 1 KB times 3,600 = 45 GB of hints, spread over its peers. We cap the hint window at about 3 hours; after that a full repair is needed.
api: put(key, value, context) returns {ok, new_context}. The context carries the version (a vector clock) that the caller read. If the caller did not read first, the context is empty and a new branch may be created. HTTP form: PUT /v1/tables/{table}/items/{key} with header X-Context and optional X-Consistency: one | quorum | all.
get(key, consistency) returns {values: [{value, context}], ...}. Usually there is one value. After concurrent writes there may be several siblings, and the client must merge them and write the merged value back with the combined context. HTTP form: GET /v1/tables/{table}/items/{key}.
delete(key, context) writes a tombstone value with the same versioning rules. The tombstone is kept for a grace period (for example 10 days) so that repair does not bring the old value back.
Admin: POST /v1/cluster/nodes to add a node, DELETE to decommission one, GET /v1/cluster/ring for the token map. Clients usually do not call these; operators or an autoscaler do.
Conditional put (optional): put with if-version or if-absent. This needs a stronger protocol (a consensus round such as Paxos or Raft within the replica set), so we offer it only per table and with higher latency.
datamodel: Keys and values. The key is a byte string, hashed with a 128-bit hash (for example MD5 or Murmur3) to a position on a ring of 2^128 positions. The value is an opaque blob plus metadata: a vector clock, a write timestamp, and a flag for tombstones.
Partitioning. The ring is divided by tokens. Each physical node owns 128 tokens. A key belongs to the first token clockwise from its hash. The preference list for the key is the next N=3 distinct physical nodes clockwise, skipping nodes in the same zone when possible so that the 3 copies are in 3 zones.
Local storage on each node. An LSM engine such as RocksDB: writes go to a write-ahead log and a memtable, then flush to sorted immutable files (SSTables) on disk. Each file has a Bloom filter so that a get for a key that is not in the file does not read the file. The row key in the engine is (token, key) so that ranges for one token are contiguous on disk and can be streamed to a new node as whole files.
Version metadata. A vector clock is a small list of (node id, counter) pairs, usually kept to at most 10 entries (the oldest are dropped). With a last-write-wins table the vector clock is replaced by a timestamp from a hybrid logical clock.
Membership. Each node keeps a full copy of the ring (token to node map), spread by gossip. This allows a request to reach the right node in one hop.
design: Cluster layout. All nodes are equal. There is no leader and no metadata server on the request path. A client library or a load balancer sends a request to any node, which acts as the coordinator for that request. If the coordinator is not in the key's preference list, it forwards the request to the first node of the list. Smart clients that know the ring send the request directly to a replica, saving a hop.
The write path. The coordinator generates a new version: it increments its own counter in the vector clock that the client sent. It writes the value locally (log, then memtable) and sends it in parallel to the other N-1 replicas. It waits for W-1 acknowledgments and answers the client. With N=3 and W=2 the client sees success after 2 copies are written, and the third arrives a moment later. The write latency is the second-fastest of 3 replicas, which cuts the slow tail.
The read path. The coordinator sends the read to all N replicas (or to R plus a speculative extra one), waits for R=2 answers and compares versions. If one version dominates all others, it is returned. If versions are concurrent, all of them are returned as siblings. In the background, the coordinator repairs any replica that returned a stale version. This is read repair.
Tunable quorums. N is the number of copies, R the number of replicas that must answer a read, W the number that must acknowledge a write. If R + W > N (for example 2 + 2 > 3), a read quorum and a write quorum overlap on at least one replica, so a read sees the latest acknowledged write when there are no failures and no sloppy quorum. With W=1 and R=1 the store is fast and may return old data. With W=3 a write needs all replicas and any single failure blocks writes.
Sloppy quorum and hinted handoff. When a replica in the preference list is down or slow, the coordinator writes to the next healthy node on the ring instead. That node keeps the item in a separate hint store with a note for the real owner. When the owner returns, the hint is sent back and deleted. This keeps writes available during failures. It also means that R + W > N does not strictly guarantee that a read sees the last write, because the write may sit on a node outside the preference list.
Failure detection and membership. Nodes exchange state with a few random peers every second (gossip). Each node learns who is up and which tokens exist. A node is marked down by a phi-accrual style detector, which is more flexible than a fixed timeout because it adapts to network jitter. Adding a node is a controlled operation: it picks tokens, streams the ranges it will own, and then starts serving.
Anti-entropy with Merkle trees. Read repair only fixes keys that are read. Cold keys can stay inconsistent forever. Each node builds a Merkle tree (a tree of hashes) over each token range, with the leaves covering small key ranges. Two replicas compare the root hash; if it differs they walk down the tree and exchange only the differing leaf ranges. Cost is proportional to the amount of difference, not to the data size.

deepdive: Versioning and conflicts. When two clients update the same key at the same time through different coordinators, the replicas get two versions that neither came before the other. A vector clock detects this. Version {A:2} descends from {A:1} because every counter is greater or equal. Versions {A:2} and {A:1,B:1} are concurrent, because each has a counter the other lacks. The store cannot know which is right, so it keeps both as siblings and returns both. The application merges them (for the shopping cart in the paper: take the union of items) and writes the result with a clock that dominates both. Deleted items can come back in this merge, which the Dynamo authors accepted for the cart. The alternative is last-write-wins (LWW), which keeps the version with the highest timestamp. It is simple and never returns siblings, but it silently drops one of two concurrent writes, and a wrong clock can make an old write win. Cassandra uses LWW per column. If you want LWW, use hybrid logical clocks so that skew between machines does not reorder causally related writes.
CRDTs as another answer. If the value is a data type with a merge function that is commutative, associative and idempotent (a counter, a set, a map of registers), replicas can merge in any order and converge without user code. Riak offers such types. This moves the conflict logic from every application into the store, but only for data shapes that fit.
Consistency levels and what they guarantee. With quorum reads and writes (R=2, W=2, N=3), a client that gets an ack for a write and then reads will usually see it, but not always: a sloppy quorum, a concurrent write or a failed partial write can break it. A write that fails after reaching one replica is not rolled back; it may appear later. For strict guarantees (a unique username, a lock) use a different tool: a consensus-based store such as one built on Raft, or conditional writes in a single replica set with Paxos as in Cassandra's lightweight transactions. In PACELC terms (if partition: availability or consistency; else: latency or consistency) this design is PA/EL.
Membership and rebalancing. When node D joins, it takes 128 tokens. For each token it becomes a replica for one range and a previous replica drops that range after the transfer. Because the tokens are random and many, D streams small pieces from many peers in parallel, so the load is spread. With one token per node (the first Dynamo scheme) a join moves one big range from one neighbor, and a failure puts all the load on the neighbors. The later Dynamo scheme splits the space into equal fixed partitions and assigns partitions to nodes, which makes the data placement easier to reason about.
Hot keys and hot partitions. Hashing spreads keys evenly, but one very popular key (a celebrity profile) still lands on 3 replicas. Remedies are a cache in front, replication of that key to more replicas, or splitting the key into sub-keys written randomly and merged on read. DynamoDB adds adaptive capacity, which moves throughput budget to hot partitions and splits them.
Deletes and tombstones. A delete cannot simply remove the item, since a replica that missed it would send the old value back during repair. The delete is a write of a tombstone, kept for a grace period longer than the maximum time a replica can be away (the hint window plus repair interval). Only after that can compaction drop it. If a node is down longer than the grace period, it must be wiped and rebuilt, or deleted data comes back ("zombie" data).
Storage engine costs. The LSM turns random writes into sequential ones, which makes writes cheap. Reads may touch several files, so the Bloom filters and the block cache matter. Compaction merges files in the background and writes the data several times (write amplification of 10 or more with leveled compaction). This is why we keep 40 percent of the node capacity free for background work.
tradeoffs: Availability or consistency. Choose a Dynamo-style store when the business loses money if writes fail (shopping carts, sessions, device state, feature flags per user) and when stale reads for a few hundred milliseconds are harmless. Choose a consensus-based store such as Spanner, CockroachDB or etcd when you need linearizable reads and transactions, such as account balances or inventory counts. You give up write availability during a partition in the second case and strict ordering in the first.
Vector clocks or last-write-wins. Choose vector clocks and application merge when losing a concurrent update is unacceptable and the data has a natural merge. Choose LWW when updates replace the whole value, when conflicts are rare, and when a lost write is cheap. Choose CRDTs when the data is a counter or a set and you want the store to merge for you. Vector clocks put work on every client developer, which is why many modern systems choose LWW.
Number of replicas and quorum settings. Choose N=3, R=2, W=2 as the default: it survives one failure for reads and writes and gives overlapping quorums. Choose N=5 for critical data or when two simultaneous failures must be survived. Choose W=1 for logs or metrics where a lost write is cheap and speed matters. Each added replica costs storage and write bandwidth in proportion.
Gossip with full ring or a central service. Choose gossip with a full ring on every node up to a few thousand nodes: no central point and one-hop routing. Choose a central metadata service (ZooKeeper or etcd, or a small Raft group) when you need strict agreement on membership or have tens of thousands of nodes. The central service is easier to reason about but is something that can be down.
Managed service or self-run. Choose DynamoDB or a managed Cassandra service when the team is small and the access pattern fits single-key or simple range access. Choose self-run when you need control of hardware, compaction tuning or cross-cloud placement, and when you have people to carry the pager.
failures: One node fails. Gossip marks it down after a few seconds. Coordinators send its writes to the next healthy node as hints. Reads still find 2 of 3 replicas. When the node returns, hints are replayed, and Merkle-tree repair closes any gap. If the node is gone for good, a replacement streams its ranges from the other replicas.
A whole zone fails. Each key has one replica per zone, so every key still has 2 of 3 copies. Quorum reads and writes with R=2, W=2 continue to work. Capacity falls to two thirds, so we run with at least 40 percent headroom. When the zone returns, repair brings it up to date.
Network partition. Both sides keep accepting writes with sloppy quorums. When the partition heals, replicas have diverged versions. Vector clocks reveal the conflicts, and read repair or the application merges them. This is the case the design is built for.
Slow node (gray failure). A node that is alive but slow is worse than a dead one, because failure detection does not trigger. Coordinators use speculative reads (send to a third replica after the median latency) and dynamic snitching that prefers fast replicas. Operators track p99 per node and eject outliers.
Clock skew. With LWW, a node whose clock is 10 seconds ahead wins every conflict. Use NTP or PTP monitoring and hybrid logical clocks, and reject writes with timestamps too far in the future.
Overload and compaction storms. A burst of writes creates many small files; reads slow down; clients retry; load grows. We bound queues, shed load with backpressure when a node's pending compactions exceed a threshold, and give clients retry budgets with jitter.
Bad deploy or corruption. Checksums on every block detect bit rot. Rolling upgrades take one node per zone at a time. Backups are snapshots of immutable files, which are cheap because SSTables never change.
evolution: At 1,000 users, one PostgreSQL or Redis primary with a replica is simpler and gives transactions. At 1 million users, a 3-node cluster with N=3 gives high availability with a single token range. At 100 million users, 24 to 100 nodes with virtual nodes, 3 zones and the repair schedule above. At 1 billion users, multiple regions: each region is its own ring with local quorums (LOCAL_QUORUM), and cross-region replication is asynchronous with conflict resolution by LWW or CRDTs. Hot-partition splitting, per-tenant quotas and tiered storage for cold data become necessary. DynamoDB took this path and added transactions with a separate coordinator layer for those who need them.
followups: Why is R + W > N not enough for strong consistency? || It only makes read and write sets overlap, but sloppy quorums can place a write outside the preference list, a failed write can leave partial state, and concurrent writes are not ordered. You need a single ordering mechanism such as Raft or a leader per key for linearizability.
How does the coordinator know two versions are concurrent? || It compares vector clocks. If every counter of one is less than or equal to the other, the first is an ancestor and can be dropped. If each has a counter that the other lacks, they are concurrent and both are kept as siblings for the application to merge.
Why use virtual nodes instead of one token per node? || Many tokens per node spread a joining or failing node's load over many peers, balance uneven hardware by giving more tokens to bigger machines, and make streaming parallel. One token means one neighbor carries all the load of a failed node.
How do you repair data that is never read? || Anti-entropy with Merkle trees: replicas compare tree roots for each token range and exchange only the leaf ranges that differ. Repairs run on a schedule, at least once within the tombstone grace period.
What happens if a node comes back after the tombstone grace period? || It may still hold data that the others deleted, and repair will treat it as a live value and resurrect it. The safe answer is to wipe the node and rebuild it from replicas, and to alarm when nodes are down longer than the grace period.
How would you add a unique-username constraint? || An eventually consistent store cannot do it safely, since two coordinators can accept the same name. Use conditional writes through consensus (Paxos or Raft) for that table, or a separate strongly consistent store for the uniqueness check.
How do you serve a celebrity key that gets 100,000 reads per second? || Put a cache in front, replicate the hot key to more nodes, or split it into several sub-keys and read from a random one. Detect hot keys with per-partition metrics and split the partition automatically.

@@ distributed-cache
title: Design a distributed cache
category: Infrastructure
level: Senior / Staff
concepts: cachelayer, memcached, redis, valkey, conshash, partitioning, replication, eviction, allocators, hashtables, powerlaws, bloom, gossip, cap, consmodels, backpressure, retries, circuitbreaker, loadbalancing, eventloop, cdn
summary: A distributed cache keeps the most used data in the memory of many machines, so that most reads never touch the database. It must answer in under a millisecond, hold terabytes, survive node loss without sending a flood of misses to the database, and stay "fresh enough". The hard parts are not the hash table. They are: how keys are spread when nodes come and go, how to avoid a stampede when a hot key expires or a whole node dies, how to keep the cache from showing stale data for long, and what to do about a few keys that get a huge share of traffic. We design a cache tier in front of a sharded SQL database, in the style of memcached at Facebook and Redis Cluster.
requirements: Functional requirements. get(key), set(key, value, ttl), delete(key), and a few atomic operations (increment, compare-and-set). Values are small blobs, up to 1 MB, mostly 1 to 4 KB. Keys expire by TTL and are also evicted when memory is full. Applications use the cache-aside pattern: on a miss they read the database and fill the cache. A second API, a library wrapper, offers read-through with request coalescing.
Non-functional requirements. Latency: p99 under 1 ms inside a zone for a get. Hit ratio: at least 95 percent for the main workloads. Throughput: 1 million reads per second at peak. Availability: loss of a node or a zone must not cause an outage of the database behind it. Consistency: eventual. After a database write, the old cache value may be visible for a bounded time (seconds), and never forever. Operations: add and remove nodes online with little movement of keys.
Assumptions. 200 million hot objects with an average size of 2 KB. Read to write ratio of about 50 to 1. Access follows a Zipf-like distribution: a small share of keys gets most of the traffic.
estimates: Data size. 200 million objects times 2 KB is 400 GB. Each item also has overhead for key, pointers, TTL and slab rounding. Memcached has about 50 to 60 bytes of header per item and slab classes waste on average 10 to 20 percent. We multiply by 1.3: 400 GB times 1.3 = 520 GB of memory.
Nodes by memory. A node with 32 GB of RAM can use about 28 GB for data (the rest is OS, connections and buffers). 520 / 28 = 18.6 nodes. We want headroom for growth and skew, so we plan 24 nodes: 24 times 28 GB = 672 GB, and the cache is about 77 percent full.
Throughput. 1,000,000 reads per second plus 20,000 writes per second (50 to 1). Over 24 nodes this is about 42,000 operations per second per node on average. Real traffic is skewed, so the hottest node may see 2 times the average: 84,000. A memcached node with 8 threads handles 200,000 or more small operations per second, and a Redis shard (single-threaded command execution) handles roughly 100,000. We are fine on both.
Network. 1,000,000 reads times 2 KB is 2 GB/s in total, or 83 MB/s per node, which is 0.67 Gbit/s. A 10 Gbit/s NIC is far from saturated. For a 100 KB object the same rate would need 100 GB/s, so large values need a different design (a CDN or object store).
Database load. At a 95 percent hit ratio, 5 percent of 1,000,000 = 50,000 reads per second reach the database. At a 90 percent hit ratio it is 100,000, double. A change of 5 points in the hit ratio doubles the database load. This is why we watch the hit ratio more than the cache CPU.
Cold start. If the whole cache is lost, 1,000,000 reads per second would hit a database that can serve 100,000. That is 10 times its capacity. Refilling 520 GB at 100,000 reads of 2 KB per second (200 MB/s) takes 2,600 s, about 43 minutes. The hot keys refill much faster because of the Zipf shape, but the database still sees a spike. We design to avoid this case.
api: get(key) returns {value, flags, cas_token} or a miss. The cas_token is a version id for compare-and-set.
set(key, value, ttl_s, flags) stores the value. add(key, ...) stores only if the key is absent; replace only if present; cas(key, value, token) only if the token is unchanged.
delete(key) removes the key. For invalidation the database write path calls delete, not set (see the deep dive).
incr(key, delta) and decr atomically change a number. touch(key, ttl) changes the TTL without sending the value.
Lease variant (for stampede control): get_with_lease(key) returns either the value, or a miss together with a lease token if this caller is the first to miss; other callers get a "wait" answer. set_with_lease(key, value, token) succeeds only if the lease is still valid.
Wire form: a compact binary or text protocol over TCP, or RESP for Redis. Clients keep persistent connections and use pipelining (many requests in one packet) to reduce the number of syscalls and round trips.
datamodel: A node is a large hash table in memory. The key is a string of up to 250 bytes in memcached. The value is a blob with flags and an expiry time. Memcached allocates memory with a slab allocator: memory is cut into 1 MB pages and each page is assigned to a slab class of fixed chunk sizes (for example 96, 120, 152 bytes, growing by a factor of 1.25). An item goes to the smallest class that fits. This avoids fragmentation of the general heap at the price of internal waste.
Eviction. Each slab class has an LRU list (memcached uses a segmented LRU with hot, warm and cold parts). When memory is full, the item at the cold tail is removed. Redis does not keep a full LRU list. It samples a few keys (5 by default) and evicts the best candidate by idle time or by access frequency (LFU mode). Expired keys are removed lazily when touched, and by a background crawler that scans a few keys at a time.
Placement. Keys are placed by consistent hashing with virtual nodes (about 100 to 200 points per node on a ring of 32-bit hash values) in client libraries or in a proxy such as mcrouter or Twemproxy. Redis Cluster uses 16,384 fixed hash slots: slot = CRC16(key) mod 16384. Each node owns a set of slots, and moving a slot moves a known group of keys.
Key naming. "user:{id}:profile:v3" gives a namespace, an id and a schema version. Changing the version suffix invalidates a whole class of entries without a flush. Related keys that must be on the same node use a hash tag ("{user42}:cart", "{user42}:profile"), since Redis hashes only the part in braces.
design: Topology. The application servers run a client library or talk to a local proxy. The cache nodes are grouped into pools by workload (for example one for user objects, one for sessions) so that a noisy workload cannot evict the data of another. Each pool is spread over three availability zones, and each client prefers nodes in its own zone when there are replicas, to save the cross-zone latency and cost.
Read path (cache-aside). The client hashes the key, finds the node and sends get. On a hit the answer returns in about 0.3 to 0.5 ms. On a miss the client reads the database (5 to 20 ms), then sends set with a TTL. The cache never reads the database itself. This keeps the cache simple, and the application can store a derived object (a rendered profile) that is not a database row.
Write path. The application writes to the database first, then deletes the cache key (not set). Delete is safer than set: two writers racing to set may leave the older value in the cache, while with delete the next reader fetches the newest row. We still need a safeguard for the race where a reader fetched an old row, a writer updated and deleted, and then the reader sets the old row. Leases (below) fix this. The strongest approach feeds invalidations from the database's own commit log, so that a missed delete in the application cannot leave a stale key.
Replication inside the cache. Pure memcached has no replication. A lost node means a loss of 1/24 of the data, and its keys are served from the database until refilled (about 4 percent of the keyspace, so the database load rises by about 4 percent of 1,000,000, i.e. 40,000 reads per second, if they were all hot; in practice less). To avoid this for the hottest data, Facebook used a small "gutter" pool: when a node is down, its requests go to the gutter pool with a very short TTL, which absorbs the load without remapping the whole ring. Redis offers primary-replica replication (asynchronous) with automatic failover through Sentinel or the Cluster bus.
Request batching and fan-out. A page may need 100 keys. The client groups the keys per node and sends one multiget per node in parallel. The page latency is the slowest node, so the p99 of a single node matters much more than the average. Limit the number of keys per request, set tight timeouts and use hedged requests only for read-only gets.
Admission and warming. New nodes join with an empty memory. We warm them by copying keys from a peer or by letting the proxy send a copy of a fraction of misses to the new node. A rolling restart replaces at most a few nodes at a time.

deepdive: Cache stampede (thundering herd). A popular key expires, and 5,000 requests per second all miss at once, and all 5,000 read the database. The database slows down, the fills get slower, and more requests miss: a feedback loop. Defenses, from simple to strong. (1) Request coalescing in the application: the first miss per key per process takes a local lock, and the others wait for its result. (2) Leases in the cache, as in the animation: only one client per key per few seconds is allowed to fill. (3) Early probabilistic refresh: a reader that sees a value near expiry recomputes it with a probability that grows as expiry gets closer (the XFetch rule: refresh if now - delta x beta x ln(rand) >= expiry, where delta is the time the recompute takes). (4) Stale-while-revalidate: keep a soft TTL for freshness and a hard TTL for survival; after the soft TTL one request refreshes while the others get the old value. (5) TTL jitter: set the TTL to base x (1 + random 0..0.1) so that a batch of keys filled together does not expire together.
Hot keys. By the Zipf shape, a few keys get a large share of the reads. If one key gets 200,000 reads per second, one node cannot serve it (we estimated roughly 100,000 for a Redis shard). Fixes: (1) a small in-process cache (L1) in every app server, with a TTL of 1 to 5 seconds, which cuts the load by the number of reads per app server per second; (2) replicate the hot key under several names (key#0 to key#7) and read a random one; (3) detect hot keys from node counters or sampling and promote them automatically. The cost is staleness equal to the L1 TTL and the extra invalidation work for each copy.
Consistency and stale data. Cache-aside has races. Reader R reads row v1 from the database; writer W updates to v2 and deletes the key; R then sets v1. The cache now holds v1 until the TTL. Leases solve this: a delete invalidates the outstanding lease, so R's set with the old token is rejected. Another source of stale data is replica lag: a reader that fetches from a lagging database replica fills the cache with an old row after the delete. Facebook handled this by tagging deletes that travel with the replication stream, so the delete happens at each region after the replica is updated. A TTL is the last line of defense. We state the guarantee openly: stale for at most TTL, in practice for under a second.
Failure of a node and remapping. With plain modulo hashing (hash mod 24), losing one node remaps almost all keys, a disaster. Consistent hashing remaps only the keys of the lost node, about 1/24 or 4 percent. With Redis Cluster slots, the cluster reassigns the slots of a failed primary to its promoted replica. A client that has an old map gets a MOVED error and updates its map. During slot migration, ASK redirects handle keys that are in transit.
Memory efficiency and eviction. LRU is cheap but a scan of cold data can flush the hot set. Frequency-based admission such as TinyLFU, with a small window, keeps a key out of the cache until it has been seen more than the key it would evict. Caffeine, the Java library, uses it for local caches, and it improves the hit ratio by several points on skewed loads. For a distributed tier the same idea is used by segmenting the LRU into hot, warm and cold. A Bloom filter in front of the database can avoid the database call for keys that do not exist (negative caching with a short TTL covers the same case).
Large values and the network. A 1 MB value takes 0.8 ms to send on a 10 Gbit/s link, and with 100 concurrent requests the NIC is saturated at 1,250 per second. Keep values small. Compress large JSON (a 4:1 ratio is common), or store large objects in an object store with a CDN, and keep only pointers in the cache.
tradeoffs: Cache-aside, read-through or write-through. Choose cache-aside when you want a simple cache that can fail without breaking the system, and the application understands its own data model. Choose read-through (a library or proxy that loads on miss) when many teams use the cache and you want one place for coalescing and metrics. Choose write-through when reads must see the newest write and the write rate is small, at the cost of write latency and a larger blast radius. Write-behind (cache absorbs writes and flushes later) gives the lowest write latency, but data can be lost if the node dies, so use it only for counters or data that can be rebuilt.
Memcached or Redis (Valkey). Choose memcached for a pure cache of blobs: multi-threaded, simple, low memory overhead, easy to scale with a client-side ring. Choose Redis or Valkey when you need data types (lists, sorted sets, hashes), atomic scripts, persistence or replication, and accept single-threaded command execution per shard and a bit more memory per key. Redis often becomes a small database, and then it needs a plan for durability that a cache does not.
Client-side ring, proxy or cluster-aware client. Choose a client-side ring for the least latency and no extra hop; but then every client language needs the logic and every config change must reach all clients. Choose a proxy (mcrouter, Envoy) to centralize routing, pooling, replication and failover, paying one extra hop of 100 to 200 microseconds. Choose Redis Cluster's smart clients when you use Redis and want slot-based resharding.
Replicated or non-replicated cache. Choose no replication when the database can absorb the loss of one node and you want the full memory for data. Choose primary-replica when losing a node would cause a miss storm that the database cannot survive, accepting that half the memory holds copies. A cheaper middle path is the gutter pool plus warm-up.
Local cache, distributed cache or CDN. Choose a local in-process cache for tiny, very hot and tolerant data, with a TTL of seconds. Choose the distributed tier for shared data, with consistent invalidation. Choose a CDN for public content that is the same for many users. Layering all three is normal, with each layer cutting the load of the next.
failures: One cache node dies. Clients get connection errors and time out within 20 to 50 ms. A circuit breaker marks the node as down for a few seconds. The proxy routes its keys to the gutter pool, with a short TTL (for example 10 seconds), or to the database with coalescing. The database load increases by roughly 1/24 of the traffic. The replacement node starts cold and is warmed.
A zone fails. If pools span three zones, a third of the nodes is lost. Without replicas, a third of the hit traffic goes to the database, about 330,000 reads per second at the worst. This is beyond 100,000, so we need load shedding: the application returns a degraded answer (an old or partial object) for low-priority requests and keeps the database alive. Replicas in other zones for the hottest keys make this much smaller.
Database slow or down. A cache can hide a short outage for hot keys. We serve stale values past TTL (stale-if-error), set negative caching for failures with a very short TTL and limit concurrent database reads per key with a bulkhead.
Whole cache flush by mistake or bad deploy. This is the scariest event. Protect with permissions on flush commands, a deploy that restarts few nodes at once, and a ramp-up procedure: send 1 percent of traffic to the new cache, then 10 and so on, while the hit ratio grows.
Network issues and slow nodes. A node with high latency makes every page that touches it slow. Use short timeouts (5 to 10 ms), limited retries with jitter, hedged reads for tail latency, and outlier detection that removes a node from the ring if its p99 exceeds a threshold.
Poison and bad data. A bug writes wrong data under a key with a long TTL. Version your keys and have a way to bump the version for a namespace. Keep TTLs finite for everything.
evolution: At 1,000 users, an in-process cache with a TTL is enough. At 1 million users, one Redis or memcached node with a replica serves everything, and the client uses cache-aside. At 100 million users, a ring of 24 nodes with consistent hashing, a proxy, leases and a gutter pool. At 1 billion users, multiple regions, each with its own cache pools and a way to broadcast invalidations from the database to all regions, hot-key detection, and tiers: a small RAM tier for hot data and an NVMe-backed tier (such as the flash-based extensions in modern caches) for the warm data, which gives 5 to 10 times more capacity per dollar at a latency of 100 microseconds instead of 10.
followups: Why delete the cache key on a write instead of updating it? || Two concurrent writers can set their values in the opposite order to the database order and leave the older value in the cache. A delete makes the next reader read the current row. Updates also require the writer to know how to build the cached form of the object.
What is a cache stampede and how do you stop it? || Many requests miss the same expired key and all call the database. Stop it with request coalescing, leases that allow one filler, probabilistic early refresh, stale-while-revalidate, and TTL jitter. Combine two or three.
How does consistent hashing help when a node fails? || Only the keys that lived on the failed node move, about 1/N of the keyspace, while modulo hashing would remap nearly all keys and turn the hit ratio to near zero. Virtual nodes spread those keys across many neighbors, so no single neighbor takes the whole load.
How do you handle a key with 200,000 reads per second? || Add an L1 in-process cache with a TTL of a few seconds, copy the key to several names and read at random, detect hot keys automatically and accept bounded staleness. Do not rely on one shard.
Which eviction policy do you use and why? || Approximate LRU is cheap and works for most loads. For loads with scans or one-time reads, TinyLFU-style admission keeps the hot set and raises the hit ratio. Measure hit ratio per pool with replayed traces before changing the policy.
Can the cache and database disagree forever? || With cache-aside they can, if a delete is lost or a race fills an old row. A finite TTL bounds the damage, and a commit-log-driven invalidation stream removes most causes. Then monitor stale reads by sampling cache against database.
How would you size the cache for a target hit ratio? || Take a trace of key accesses and compute the hit ratio as a function of cache size (a miss ratio curve). Because of the skewed access pattern, the curve flattens: the first 20 percent of memory often gives most of the hits. Pick the point where the next GB gives less database savings than it costs.

@@ unique-id
title: Design a unique ID generator like Snowflake
category: Infrastructure
level: Senior / Staff
concepts: hwclocks, hlc, lamport, truetime, atomicclock, birthday, btree, indexing, partitioning, zookeeper, etcd, coordination, leaderelect, fencing, consensus, binary, postgres, hashfn, failuredetect, microservices
summary: Every row, event, tweet and order needs an identifier that no other machine will ever create again. In one database this is an auto-increment counter. In a distributed system with thousands of writers there is no single counter, and calling a central one on every write is slow and fragile. We design a generator that produces 64-bit numbers that are unique across machines, roughly sorted by time, fast to create (no network call), and small enough to be a good database key. The hard part is not the bit layout. It is what happens when clocks go backward, when two machines get the same worker id, and when "sorted by time" is not the same as "ordered by cause".
requirements: Functional requirements. generate() returns a 64-bit integer id. IDs are unique across all services and data centers. IDs are roughly time-ordered: an id created later has a larger value, with ordering exact for one machine and within a few milliseconds across machines. IDs fit in a signed 64-bit integer, so they work in every language and database, and in JSON as a string. Optionally, the id lets us read the creation time without a lookup.
Non-functional requirements. Throughput: 1 million ids per second across the fleet at peak. Latency: under 10 microseconds when the generator runs inside the service process, and under 1 ms for a network service. Availability: id creation must continue when the coordination service is down. Safety: never produce a duplicate, even after a crash, a restart, a clock change or a split of the network. We prefer to refuse to issue an id over issuing a duplicate. Ids must not leak business data (how many orders per day) more than we accept.
Assumptions. The platform has 400 service instances that create ids, in 4 data centers. Average 100,000 ids per second, peak 1,000,000.
estimates: Bit budget. A signed 64-bit integer has 63 usable bits (the sign bit stays 0). Snowflake uses: 41 bits of timestamp in milliseconds, 10 bits for the worker id, 12 bits for a sequence number. 41 + 10 + 12 = 63.
Time range. 2^41 milliseconds = 2,199,023,255,552 ms. Divide by 1,000 ms/s and 86,400 s/day and 365.25 days/year: 2.199e12 / 3.156e10 = about 69.7 years. With a custom epoch set at our launch date (Twitter used 4 November 2010), the ids work until about 2080.
Capacity of one worker. 12 bits of sequence give 4,096 ids per millisecond, which is 4,096,000 per second per worker. Our peak of 1,000,000 per second over 400 instances is 2,500 per second per instance, which is 0.06 percent of one worker's capacity. We have enormous headroom, so the sequence will almost never overflow.
Worker ids. 10 bits give 1,024 workers. We have 400 instances now. With autoscaling and restarts, worker ids are reused over time, so the real constraint is the number of live workers at the same moment, not total. If we expect more than 1,024, we can move to 8 bits of sequence (256 per ms, 256,000 per second per worker, still 100 times our need) and 14 bits of worker id (16,384 workers).
Storage. Ids per day at the average: 100,000 times 86,400 = 8.64 billion. As 8-byte integers that is 69 GB per day of ids alone, versus 138 GB as 16-byte UUIDs. In an indexed column, the index doubles this (the key is repeated in each index). Over a year, 8.64e9 times 365 = 3.15 trillion ids, so the key size is a real cost.
Collision risk for random ids. A random 122-bit UUID (version 4) has a collision probability of about n^2 / 2^123 for n ids (the birthday bound). For n = 10^12, n^2 = 10^24, 2^123 is about 1.06e37, so the probability is about 10^-13. Safe in practice, but it relies on a good random source, and random keys are bad for B-tree indexes.
Network service option. If we serve ids through a service instead of a library: 1,000,000 per second at a batch of 100 ids per call is 10,000 calls per second, easily served by 3 nodes. Batching removes most of the network cost.
api: Library call: nextId() returns int64. In-process, no network. This is the default.
Service call (for languages or teams that cannot embed the library): POST /v1/ids?count=100 returns {"ids": [..100 numbers..]} as strings, since JavaScript numbers lose precision above 2^53. The caller may use the batch locally.
Decoding call: parse(id) returns {timestamp_ms, datacenter, worker, sequence}. Used for debugging and for range queries by time (the smallest id for a given time is time << 22).
Admin call: POST /v1/workers/lease returns {worker_id, lease_ttl_s, epoch_token}. A process calls it at startup, renews the lease while running and releases it at shutdown.
Health call: GET /v1/health returns the clock offset estimate, the last issued timestamp and the number of times the clock moved backward.
datamodel: The id itself is the data model. Layout, from the most significant bit to the least:
bit 63: 0 (sign). bits 62..22: milliseconds since our custom epoch (41 bits). bits 21..12: worker id (10 bits; for example 5 bits of data center and 5 bits of machine). bits 11..0: sequence in the same millisecond (12 bits).
Because the timestamp is in the top bits, ids sort by time, and a B-tree index on the id grows on the right edge like an auto-increment column. New rows go to the last page, which stays in cache, and pages are filled to nearly 100 percent. With random ids, each insert goes to a random page: more cache misses, page splits and a fill around 70 percent.
State in each generator: last_timestamp (the last millisecond used), sequence (the counter inside that millisecond), and worker_id. Nothing else, and nothing is written to disk on the hot path.
Worker registry (the only shared state): a small table or a key in a coordination store, "worker/{id}" with a lease. The lease holder is the only process that may use that id while the lease is valid. A fencing token (a number that grows with each grant) records the grant order.
design: The core algorithm. When nextId() is called, read the clock in milliseconds: now. If now equals last_timestamp, increment the sequence. If the sequence passes 4,095, wait for the next millisecond (spin until now > last_timestamp), then reset the sequence to 0. If now is greater than last_timestamp, set last_timestamp = now and sequence = 0 (or a small random start, to avoid all ids ending in zero, which skews shards that use id mod N). If now is less than last_timestamp, the clock went backward; see the deep dive. Then compose the id: ((now - epoch) << 22) | (worker_id << 12) | sequence. The function takes a lock or a compare-and-swap on one 64-bit state, so it is thread safe, and costs about 50 to 200 nanoseconds.
How workers get unique ids. Uniqueness comes from the worker id: two different workers can never produce the same id, since the worker id is part of it. So the problem moves to "never give the same worker id to two live processes". Three common ways. (1) Static configuration: worker id = ordinal of a Kubernetes StatefulSet pod, or from the host inventory. Simple and enough for fixed fleets. (2) A lease in ZooKeeper or etcd: at start, the process creates an ephemeral node or a key with a lease for the lowest free id and keeps it alive. If the process dies, the lease expires and the id returns to the pool. (3) A relational table with a unique key and a heartbeat column. All three need a time gap before an id is reused: a new holder must wait longer than the lease TTL plus the maximum clock skew, so the old holder (which might be alive but paused) has surely stopped.
Deployment shapes. Embedded library: fastest, no network, but every service needs a worker id. Sidecar or local daemon: one generator per host serves all processes on it via a Unix socket. Central service: easy for clients, but a network hop and a new dependency. Twitter's original Snowflake was a service with a Thrift API on each cluster. Instagram instead generated ids inside PostgreSQL with a PL/pgSQL function, using a shard id in place of the worker id: 41 bits of time, 13 bits of logical shard, 10 bits of sequence.
Restart safety. After a crash, last_timestamp is lost. If the machine restarts within the same millisecond range and the clock is correct, it simply continues with a later time, so no duplicates. The danger is a restart with a clock that is behind the old process's last timestamp, for example a VM restored from a snapshot. Solution: persist the last timestamp from time to time (every second, with a margin of a few seconds ahead), and on start wait until now is greater than the persisted value.
Data centers and regions. The data center bits keep ids unique across sites without any cross-site traffic. The system keeps working if a site is cut off. IDs from different sites are only roughly ordered by time (limited by clock sync).

deepdive: Clock going backward. A generator that trusts the wall clock can produce duplicates: if the clock steps back by 5 ms, the same (time, worker, sequence) can occur twice. Causes: NTP step corrections, leap second smearing done wrongly, a VM that is paused and resumed, a live migration, an operator setting the time. Defenses: (1) Prefer the monotonic clock for intervals and the wall clock only to anchor: at start, take wall time W0 and monotonic time M0, and compute now = W0 + (M_now - M0). Then the wall clock stepping does not matter. This drifts slowly from true time, so re-anchor with a limit on the correction. (2) Keep last_timestamp and never go below it. For a small offset (under 5 ms) wait; for a larger one, return an error or keep issuing with last_timestamp and an incrementing sequence until the clock catches up (this "borrowing" can overflow 4,096 ids per ms, then wait). (3) Run chrony or another slewing time daemon in a mode that never steps the clock, and alarm on offset above, say, 10 ms.
Duplicate worker ids. The worst bug is two live processes with the same worker id. This happens with a split brain in the lease system, a process that was paused (a long garbage collection pause of 30 s) after its lease expired and then wakes up believing it still holds the lease, or manual configuration mistakes. Mitigations: the process checks the lease validity (using a monotonic clock and a safety margin) before every batch of ids, not only at start; the lease TTL is long compared with clock skew; the process keeps issuing only while now is less than lease_expiry minus margin; and the reuse of a worker id is delayed. With a fencing token as the high bits of worker registration you can detect which holder is the newer one, but ids already issued cannot be recalled.
Roughly sorted is not causally ordered. Two machines with clocks 3 ms apart can create id A (earlier in real time, on the fast clock) and id B (later in real time, on the slow clock) with B smaller than A. For sorting a feed this is fine. For ordering events that depend on each other (a comment and its reply), it is not. Alternatives: a Lamport clock or hybrid logical clock (HLC) that takes the maximum of the local and received timestamps on every message, so that if A caused B then id(B) > id(A). Google Spanner uses TrueTime, with atomic clocks and GPS and an uncertainty interval, and waits out the uncertainty (around 7 ms at worst in the paper) before commit, giving external consistency. That is the costly end of the range.
Sequence behavior and hot shards. If most calls come one per millisecond, the sequence is nearly always 0, so ids mod a small number of shards are the same, and a sharding scheme using id mod N would send all rows to one shard. Fix: start the sequence at a random value for each new millisecond, or shard by a hash of the id, never by a modulus of a time-based id. A related effect is information leak: sequential ids reveal the creation rate. If this matters, encrypt the id before showing it, or use a random public id next to the internal one.
The ticket server alternative. Flickr used two MySQL servers, one generating odd and one generating even numbers, with REPLACE INTO on a one-row table. Every id costs a network round trip, and the servers are a dependency, but ids are dense and small. A common upgrade is to hand out blocks: a worker takes 10,000 ids at once with one database update and uses them locally, so the database sees 1 call per 10,000 ids. After a crash, the unused part of the block is lost, which is fine if gaps are acceptable.
tradeoffs: Snowflake-style id or UUID. Choose a Snowflake-style 64-bit id when the id is a primary key in a large indexed table, when you need time order, and when a compact number matters (8 bytes against 16, and half the index size). Choose UUIDv4 when the id must be unguessable and generated anywhere with no worker registry, accepting random inserts and larger indexes. Choose UUIDv7 (RFC 9562, 2024) or ULID when you want no coordination and time ordering: 48 bits of millisecond time and the rest random, 128 bits in total. You pay 8 more bytes per id than Snowflake and rely on randomness for uniqueness.
Library, sidecar or service. Choose an embedded library when latency matters and each service can get a worker id from the platform. Choose a central service when you have many languages or you want one place to enforce clock checks and rate, and you accept a hop and a new dependency; batching reduces the cost. Choose a database ticket server when you have a small system, need dense gapless-ish ids and already run a reliable database.
Wall clock or logical clock. Choose the wall-clock Snowflake when ordering to within a few ms is enough, which is true for most feeds, logs and database keys. Choose HLC when causal order matters between services and you can carry the timestamp in each message. Choose TrueTime-like hardware only if you control the data centers and need external consistency; this is rarely the right answer outside a database kernel.
Static, lease-based or random worker ids. Choose static ids from a StatefulSet ordinal when the fleet is stable and you can guarantee one pod per ordinal. Choose leases in etcd or ZooKeeper for dynamic fleets, paying with a dependency at startup only. Choose random worker bits (for example 10 random bits) only if collisions are acceptable, which they are not for a primary key unless you check on insert and retry.
Public ids and security. Choose sequential-looking ids for internal keys. Choose random or encrypted ids for anything exposed to users when guessing the next id would allow scraping (enumeration attacks) or reveals volume. Do not put the internal id in URLs without an authorization check; time-ordered ids are easy to guess.
failures: Coordination store down. Running generators keep their leases until expiry (30 s, renewed every 10 s). If the outage is longer, they must stop issuing ids when the lease expires, or accept the risk. We choose: stop. To soften it, give the lease a long TTL (for example 5 minutes with renewal every minute), so that a brief outage of the store has no effect, while the delay to reuse a dead worker id stays small enough. New processes cannot start during the outage, so autoscaling pauses.
Clock fault. NTP unreachable: the clock drifts by roughly 10 to 100 ppm, that is 1 to 9 s per day at 100 ppm. We alarm if the offset estimate passes 50 ms and stop at a hard limit. A step backward is handled as above.
Process crash and restart. The new process takes a worker id (maybe the same one) and waits until the clock is past the old process's persisted last timestamp. Ids in flight in the crashed process are lost, but never duplicated.
Sequence overflow. More than 4,096 ids in one millisecond: the generator waits for the next millisecond. Under heavy load this limits one worker to 4.096 million ids per second. If it happens in practice, add workers.
Whole data center lost. Other sites continue. Because the site is part of every id, no id from the lost site can collide with one from another.
Worker id exhaustion. All 1,024 ids are leased because of a leak (processes that do not release). Alarm at 80 percent, free ids of dead processes by TTL, and prepare the 8/14-bit layout change before it is needed. Layout changes are done by using a new version bit pattern from a cut-over time, with decoders that read both.
Epoch overflow. After 69.7 years from the custom epoch, the timestamp wraps. That is far away, but write the decoder so the epoch is a configuration value stored with the data, and plan for 128-bit ids if the system is to live longer.
evolution: At 1,000 users, an auto-increment column is simplest and correct. At 1 million users with one primary and replicas, the same still works; exposing the counter in URLs is the main concern, so add a random public id. At 100 million users with sharded databases, use Snowflake-style ids in a library, with worker ids from the StatefulSet ordinal. At 1 billion users and several regions, add data center bits, leases for dynamic fleets, clock health checks and monitoring of skew, and consider HLC timestamps where causality matters. If keys must never be guessed, store a 128-bit random or encrypted id next to the 64-bit key.
followups: How do you guarantee uniqueness without talking to anything on each call? || Uniqueness is split into parts: the worker id makes the generators disjoint (two workers can never issue the same id), and inside one worker the pair (millisecond, sequence) is strictly increasing. So only the assignment of worker ids needs coordination, and it happens rarely, at startup.
What if the system clock moves backward? || Never issue an id with a timestamp below the last one used. For a small step, wait; for a large one, refuse and alarm. Better, use a monotonic clock anchored to the wall clock, and run a time daemon that slews instead of stepping.
Why not use UUIDs for everything? || They are 16 bytes, so keys and indexes are twice as large, and random v4 values cause random B-tree inserts and page splits. Time-ordered formats such as UUIDv7 fix the ordering, but are still twice the size of a 64-bit id. UUIDs are the right choice when you cannot manage worker ids or ids must be unguessable.
Are Snowflake ids globally ordered? || No. They are ordered by timestamp, and two machines with different clock errors can issue ids that are out of real-time order by the skew. For causal order use a Lamport or hybrid logical clock, or one writer per entity.
How do you pick the worker id for a Kubernetes deployment? || Use a StatefulSet ordinal when you can, or lease an id from etcd with a TTL. Make the new holder wait longer than the TTL plus the maximum clock skew before it reuses an id, and have the process stop issuing when its lease might have expired.
What happens at the end of the 41-bit range? || After about 69.7 years from the custom epoch, the timestamp overflows. Use a recent custom epoch, store the epoch as configuration, and keep a version in the layout so a new format can start before the old one ends.
How would you shard a table by these ids? || Do not use id mod N, because with low traffic the low bits are nearly constant. Hash the id, or use the worker bits or a range of the time bits. A hash gives even load, while a range of time keeps recent data together for fast scans and easy deletion of old data.

@@ message-queue
title: Design a distributed message queue like Kafka
category: Data & analytics
level: Senior / Staff
concepts: kafka, commitlog, mqueue, pubsub, partitioning, replication, isr, consensus, raft, leaderelect, consumergroups, exactlyonce, deliverysem, idempotence, backpressure, segments, zerocopy, pagecache, batching, logcompaction, tieredstorage, sepstorage
summary: A message queue lets producers write messages and consumers read them later, at their own speed, without the two sides knowing each other. A Kafka-style system stores each topic as a set of append-only, replicated logs. It must take about a million messages per second, keep them for days, let many independent consumer groups replay them, keep order where it matters, and not lose acknowledged data when a broker dies. What makes it hard is replication with clear rules about what is committed, the assignment of partitions to consumers while members join and leave, and delivery guarantees that stay honest (at-least-once, effectively-once) across failures.
requirements: Functional requirements. Producers send messages to a topic, with an optional key. Messages with the same key keep their order. Consumers join a consumer group; the group as a whole reads each message once, and different groups each read all messages. Consumers can seek to any offset or time and replay. Retention is by time (7 days) or size, and some topics keep the latest value per key (compaction). Topics can be created and resized at runtime.
Non-functional requirements. Throughput: 1 million messages per second at peak, 1 KB each. Latency: producer ack in under 10 ms at p99 within a region, end-to-end under 50 ms. Durability: an acknowledged message survives the loss of any one broker (and any two with the right settings). Availability: a broker or zone failure causes only a short pause (seconds) for the affected partitions. Ordering: total order inside one partition, none across partitions. Delivery: at-least-once by default, effectively-once with idempotent producers and transactions.
Assumptions. Average load is half of the peak. Messages compress about 3 to 1 with batch compression. Replication factor 3 over 3 availability zones, retention 7 days, three consumer groups read every message.
estimates: Ingest. Peak 1,000,000 messages per second times 1 KB = 1 GB/s. Average is half: 500 MB/s. After compression (3 to 1), the cluster writes 167 MB/s on average, or 333 MB/s at peak, before replication.
Storage. Average raw ingest 500 MB/s times 86,400 s = 43.2 TB per day. For 7 days: 43.2 times 7 = 302 TB raw. Compressed 3 to 1 gives 101 TB. With replication factor 3: 302 TB on disk. Brokers have 20 TB of NVMe disk each, and we fill them to 60 percent for headroom (12 TB usable). 302 / 12 = 25 brokers. Storage, not throughput, sets the size of the cluster.
Throughput check per broker. Replicated write traffic at peak is 333 MB/s times 3 copies = 1 GB/s over 25 brokers, about 40 MB/s per broker, tiny against a modern NVMe disk (a GB/s) and a 25 Gbit/s NIC (3 GB/s). Reads: three consumer groups mean 3 times 333 MB/s = 1 GB/s of egress for tail reads, 40 MB/s per broker. Most of these reads come from the page cache, since consumers are near the head of the log.
Partitions. A consumer that processes 20,000 messages per second per thread needs 1,000,000 / 20,000 = 50 partitions to keep up. We want room for 4 times growth and for slow consumers, so the main topic gets 200 partitions. Each partition then has about 1 GB/s / 200 = 5 MB/s at peak, well inside what one partition leader can do (tens of MB/s). With replication factor 3, 200 partitions make 600 replicas, spread over 25 brokers, 24 per broker.
Page cache. A broker with 64 GB of RAM keeps most of it for the OS page cache. At peak a broker receives about 40 MB/s of replicated writes. The newest 10 minutes are 40 MB/s times 600 s = 24 GB, which fits in the page cache, so tail reads come from memory and the disk is used mostly for replays and recovery.
Metadata. 200 partitions is small. Clusters can hold hundreds of thousands of partitions once the metadata is stored in KRaft rather than ZooKeeper, so partition count is not a limit here.
api: Produce: send(topic, key, value, headers) returns {partition, offset} after the ack level is satisfied. Clients batch: they collect messages for linger.ms (for example 5 ms) or until the batch reaches 64 KB, compress it, and send one request per partition leader.
Fetch: fetch(topic, partition, offset, max_bytes, max_wait) returns a batch of messages from the offset. The consumer asks for the next offset and long-polls when none is available. Consumers can also seek by timestamp: offsetForTime(topic, partition, ts).
Group API: join(group, topics) returns an assignment of partitions; heartbeat(group, member) keeps membership; commit(group, topic, partition, offset) stores the position; the position is stored in an internal compacted topic.
Admin API: createTopic(name, partitions, replication_factor, configs), alterConfig, increasePartitions, reassignPartitions. Configs include retention.ms, cleanup.policy (delete or compact), min.insync.replicas.
Transactions: beginTransaction, send (many, to many partitions), sendOffsetsToTransaction, commitTransaction or abortTransaction.
datamodel: Topic and partition. A topic is split into partitions. A partition is an ordered, append-only log of records. Each record has an offset, a number that grows by 1 within the partition. A record is: key, value, timestamp, headers. Records are written in batches, and the batch is the unit of compression, replication and disk write.
On disk, a partition is a directory of segment files. Each segment has a .log file with records, an .index file mapping offsets to file positions (sparse: one entry per about 4 KB), and a .timeindex file mapping timestamps to offsets. A segment is rolled when it reaches 1 GB or 7 days. Only the active segment is written. Deleting old data means deleting whole segment files, which costs almost nothing.
Replication metadata. Each partition has a leader and followers. The in-sync replica set (ISR) lists the followers that are caught up. The leader epoch is a number that grows at each leader change, stored in every batch, so replicas can detect and truncate divergent history after a failover.
Consumer positions. For each (group, topic, partition) the committed offset is stored as a record in the compacted internal topic __consumer_offsets, keyed by the triple. The latest record per key is the current position.
Cluster metadata. The controller quorum (KRaft, a Raft group of 3 or 5 nodes) stores topics, partitions, leaders, ISRs and configs in a replicated metadata log. Brokers read this log and keep a local copy. ZooKeeper mode was removed in Kafka 4.0 (2025).
design: Writing. A producer picks the partition: hash(key) mod number of partitions when there is a key, or a sticky choice for batching when there is none. It sends the batch to the leader of that partition. The leader appends the batch to the active segment's file. The write goes to the OS page cache, not to disk with fsync. The leader replies when the ack level is met: acks=1 means the leader wrote it; acks=all means all replicas in the ISR have it, and the ISR must contain at least min.insync.replicas (2 for a durable setup, or the write fails). Durability then comes from replication on different machines, not from fsync on one machine.
Replication. Followers act as consumers: each follower sends fetch requests to the leader and appends what it receives. The leader tracks how far each follower has fetched. The high watermark is the offset up to which all ISR members have the data. Consumers can only read messages below the high watermark, so they never see a message that could be lost in a failover. A follower that does not fetch for replica.lag.time.max.ms (30 s by default) is removed from the ISR. When it catches up, it returns.
Leader election. If the leader of a partition fails, the controller picks a new leader from the ISR. Because every ISR member has everything below the high watermark, no committed message is lost. By default, unclean leader election (choosing a replica that is not in the ISR) is off: the partition stays unavailable instead of losing data. The leader epoch lets the new followers truncate any extra, uncommitted records they had.
Consumer groups. Within a group, each partition is assigned to one consumer, so ordering inside a partition is kept and no two members read the same partition. A group coordinator (a broker chosen by hashing the group id onto a partition of __consumer_offsets) tracks members through heartbeats. When a member joins or leaves, partitions are reassigned. Kafka 4.0 made the new group protocol (KIP-848) generally available, where the coordinator computes assignments and members change gradually, replacing the old stop-the-world rebalance. Consumers commit offsets after processing, which gives at-least-once delivery: after a crash, the new owner restarts from the last commit and some messages are processed twice.
Why it is fast. Writes are sequential appends, which disks and SSDs do at full bandwidth. Batching amortizes the cost of requests and syscalls, and compression shrinks the network and disk bytes. The broker does not copy data into its own heap for reads: it uses the sendfile system call (zero-copy) to send bytes from the page cache directly to the socket. The page cache holds recent data automatically and survives a broker process restart.
Retention and compaction. A cleaner thread deletes segments older than the retention. For a compacted topic, it rewrites old segments and keeps only the latest record for each key; a record with a null value is a tombstone that removes the key. Tiered storage lets a broker keep only the newest hours on local disk and move closed segments to an object store, so retention can be months without more brokers.

deepdive: Replication, commit and what "durable" means. A message is committed when all members of the ISR have it. With acks=all, min.insync.replicas=2 and replication factor 3, the producer gets an ack only when at least 2 replicas hold the message. If two brokers fail at once and the third was the only one left, the partition stops accepting writes (it cannot reach 2 in-sync replicas) instead of accepting writes that only one machine holds. We choose consistency over availability at this boundary. If you set acks=1, a leader crash right after the ack loses the message; this is a real data-loss path used for logs where speed matters more. The ISR design needs fewer replicas than a majority quorum for the same durability: with replication factor 3, committed data survives the loss of 2 brokers, because any one in-sync replica has all of it. The price is that availability for writes needs min.insync.replicas members, so with min ISR of 2 the partition accepts writes only while 2 replicas are in sync.
Ordering and idempotence. Within a partition the order is the order of appends. If a producer retries a batch after a timeout, the first attempt may have succeeded, so the log would contain duplicates, and with several in-flight requests the retry could also reorder messages. Idempotent producers fix this: each producer gets a producer id from the broker, and each batch carries a sequence number per partition. The broker keeps the last sequence numbers (for the last 5 batches) and rejects duplicates and out-of-order batches. This is on by default in recent versions. The guarantee covers one producer session and one partition.
Transactions and effectively-once. For read-process-write pipelines, a transactional producer writes to several output partitions and also writes the consumer offsets of the input in one atomic transaction. A transaction coordinator uses a transaction log (a replicated internal topic) and writes commit or abort markers to every partition involved. Consumers with isolation.level=read_committed see only records of committed transactions. The result is that each input message affects the output exactly once, as long as the processing stays inside Kafka. Side effects outside (an email, a database write) still need their own idempotency key.
Partition count, keys and hot partitions. The number of partitions limits the parallelism of one consumer group: with 200 partitions at most 200 consumers are active. Adding partitions later changes the hash mapping, so keys move to different partitions and per-key order breaks across the change, so plan partitions with growth in mind. A skewed key (one customer with 30 percent of traffic) produces a hot partition: its leader, its disk and its consumer carry the load. Remedies: salt the key (customer-17 plus a random suffix of 0 to 7) and merge downstream, accept loss of ordering for that customer, or give the hot customer a topic of its own.
Consumer lag, rebalances and slow consumers. Lag is the log end offset minus the committed offset. It is the most important metric. A consumer that takes longer than max.poll.interval.ms (5 minutes by default) between polls is removed from the group and its partitions move, so slow processing causes rebalances, duplicates and more lag. Keep processing short, or hand the work to a pool and commit only after it ends. The new group protocol reduces the cost of a rebalance but does not remove duplicates.
Controller and metadata. The controller quorum in KRaft is a Raft group that stores the metadata log. A new active controller starts from the log, not by reading from ZooKeeper, so failover of the controller takes well under a second, and clusters can have a much larger number of partitions. Brokers fetch metadata updates as a stream. The metadata is small but critical, so it runs on dedicated nodes in big clusters.
Backpressure. A queue decouples speeds, but the log is finite. If consumers fall behind by more than the retention period, the data is deleted before it is read. Alarm on lag in time (seconds behind head) and not only in messages, and size retention at several times the longest expected outage of a consumer. Producers see backpressure through quotas (bytes per second per client id) that make the broker delay responses, and through the buffer limit in the client.
tradeoffs: Log-based queue or a classic broker. Choose a Kafka-style log when many consumers must read the same data, replay is needed, volume is high (hundreds of MB/s) and order per key matters. Choose a classic queue (RabbitMQ, SQS) when each message is a task for one worker, you need per-message acknowledgment, retries with delay, priority and dead-letter queues, and volume is moderate. You give up per-message control in the log, and replay and fan-out in the classic queue.
Partition count. Choose more partitions (hundreds) when consumers are slow and need parallelism, or when you expect growth, because you cannot add them without breaking key order. Choose fewer (10 to 50) when throughput is modest, to keep failover fast, end-to-end latency low and the number of open files and replication fetchers small. Each partition has a cost on the controller and on recovery time.
Durability settings. Choose acks=all with min.insync.replicas=2 and replication factor 3 for business events and money. Choose acks=1 for telemetry and logs where losing a few seconds on a broker crash is fine and latency or throughput matters. Choose fsync on every write only for very strict needs; it cuts throughput by an order of magnitude and replication gives the same safety against single machine loss.
Delivery semantics. Choose at-least-once with idempotent consumers (database upsert by message id) in most pipelines, since it is simple and robust. Choose Kafka transactions when the pipeline reads from and writes to Kafka (stream processing) and duplicates in the output would be costly. Choose at-most-once (commit before processing) only for data where a loss is cheaper than a duplicate.
Local disks or tiered storage. Choose local disks when retention is days and latency of replay matters. Choose tiered storage when retention is weeks or months, because broker count is then driven by compute, not by disk, and recovery of a broker is faster (it has less data to copy). Replay of old data is slower because it reads from object storage.
Self-run or managed (MSK, Confluent Cloud, Redpanda). Choose managed if cluster operations are not your core work, accepting the price and less control. Choose self-run for cost at very high volume or for special networking. Redpanda and others offer a Kafka API with a different engine, useful if you want fewer moving parts or lower tail latency.
failures: A broker dies. The controller notices missed heartbeats (a few seconds), elects new leaders from the ISR for each partition that the broker led, and publishes new metadata. Producers get an error, refresh metadata and retry to the new leader, so the pause is a few seconds. With 8 leaders on the broker, all fail over in parallel. Followers on the dead broker leave the ISR. When it returns it fetches the missing data and rejoins, and a preferred leader election moves leadership back to balance load.
A zone fails. With racks (zones) set, replicas of one partition are in three different zones, so each partition keeps 2 of 3 replicas. With min.insync.replicas=2 writes continue. Capacity falls to 2/3, so we run with the headroom noted before. A cluster with only 2 zones cannot do this with min ISR 2 and replication 3 in a clean way, so use 3.
Slow disk or gray failure. A broker with a failing disk slows every produce with acks=all that includes it, until it falls out of the ISR after 30 s. Lower replica.lag.time.max.ms for tighter control, watch request latency per broker, and use automatic throttling and replacement.
Controller quorum loss. If 2 of 3 controller nodes are down, metadata changes stop: no new topics and no leader elections. Existing leaders keep serving reads and writes, so the data plane runs for a while, but any broker failure in this period cannot be repaired. Use 5 controller nodes across zones for large clusters.
Consumer failure. The group coordinator removes the member after the session timeout (45 s by default in recent versions), and its partitions go to others, who resume from the last committed offset. Messages processed after the last commit are processed again. Idempotent handling is needed.
Producer or network partition. A producer cut off from the leader buffers locally up to buffer.memory, then blocks or fails. With delivery.timeout.ms, it gives up after a limit; the application must handle the failure, for example by writing to a local outbox and retrying.
Overload and bad deploy. A consumer that suddenly reads from the beginning of a 7-day log for a new group reads 100 TB and could pull the page cache away from the producers' tail reads. Client quotas for fetch bytes per second protect the cluster. Roll upgrades one broker at a time and wait for the under-replicated partitions to reach zero before the next.
evolution: At 1,000 messages per second, three brokers with 12 partitions per topic are enough, or even a managed cloud queue. At 1 million messages per minute (about 17,000 per second), the same three brokers with replication factor 3 work, and the effort goes to schema management and consumer lag alerts. At 1 million messages per second, the 25-broker cluster above, with KRaft controllers on separate nodes, rack awareness and quotas. At 1 billion messages per second across the company, run many clusters by domain, replicate between regions with MirrorMaker 2 or a similar tool, use tiered storage to keep brokers small, add a schema registry with compatibility rules, and build a platform team with self-service topic creation and cost attribution.
followups: What does acks=all actually guarantee? || The leader acknowledges after all replicas in the in-sync replica set have the message, and the ISR size must be at least min.insync.replicas, or the write fails. So an acknowledged message is on at least that many machines. Together with replication factor 3 and min ISR 2, one broker can fail with no loss.
How does Kafka keep order and why only per partition? || Each partition is a single append-only log with a single leader that assigns offsets. Across partitions there is no coordinator, so there is no order. If you need order for an entity, use the entity id as the key so that all its messages go to one partition.
How do you get exactly-once? || Delivery is at-least-once on the wire. Idempotent producers remove duplicates from retries within a session, transactions make the read-process-write cycle atomic inside Kafka, and consumers with read_committed skip aborted data. For outside side effects, use idempotency keys at the sink.
Why is Kafka fast with a disk-based log? || Sequential appends, batching and compression, zero-copy sendfile from the page cache to the socket, and consumers that mostly read recent data from memory. No per-message index or acknowledgments in the broker.
What happens to a consumer group when a member dies? || After the session timeout the coordinator removes it and its partitions are reassigned; the new owners resume from the committed offsets. Uncommitted work is repeated. The new protocol (KIP-848) only moves the partitions that need to move, and does not stop all members.
How do you choose the number of partitions? || Take the target throughput divided by what one consumer can handle per partition, add room for growth, and remember that partitions cannot be reduced and changing the count breaks key mapping. Too many partitions slow recovery and use memory and file handles.
Why did Kafka replace ZooKeeper with KRaft? || ZooKeeper was a second system to run, with its own limits on metadata size and slow controller failover, which restricted the partition count. KRaft stores metadata in a Raft-replicated log inside Kafka, so failover is fast and clusters scale to far more partitions. ZooKeeper support was removed in Kafka 4.0.

title: Design an object store like S3
category: Infrastructure
level: Senior / Staff
concepts: s3, erasurecoding, sepstorage, partitioning, conshash, replication, paxos, raft, consensus, consmodels, storagedev, fsync, codingtheory, apigateway, lsm, btree, tieredstorage, datalake, hashfn, reconcile, cdn, signatures
summary: An object store keeps immutable blobs, from a few bytes to terabytes, under a flat name (bucket plus key), reachable by HTTP. It must hold exabytes in the end, never lose an object (S3 advertises 99.999999999 percent annual durability, eleven nines), serve reads from thousands of clients in parallel, and cost much less per byte than a disk array. The hard parts are durability at low cost (erasure coding instead of copies), a metadata index with strong consistency for billions of keys, listing keys in order, and repair of failed disks fast enough that failures do not pile up. We design a store for 100 PB, in the style of S3 and its open relatives.
requirements: Functional requirements. PUT object (up to 5 GB in one request, up to 5 TB with multipart upload), GET object with byte ranges, HEAD, DELETE, and LIST keys by prefix in lexicographic order, with a delimiter to group "folders". Buckets with access policy, optional versioning, lifecycle rules (delete or move to a cheaper class after N days), and signed URLs for temporary access. A read after a successful write or delete must show the new state (strong read-after-write consistency, which S3 has had for all operations since December 2020).
Non-functional requirements. Durability: eleven nines per object per year. Availability: 99.99 percent for reads. Scale: 100 PB of data, 25 billion objects. Throughput: scale out linearly by adding machines, with large objects streamed at line rate. Cost: raw storage cost under 1.5 times the logical size. Security: encryption at rest and in transit, per-object checksums, and no cross-tenant leaks. Operations: replace disks and servers without downtime.
Assumptions. Average object size 4 MB (many small, a long tail of large ones). Peak 30,000 GET per second and 5,000 PUT per second. Data is placed in one region over 3 availability zones.
estimates: Logical data. 25 billion objects times 4 MB = 100 PB.
Erasure coding. We use a Reed-Solomon code with 6 data shards and 3 parity shards (6+3), with 3 shards in each of 3 zones. Raw size is 9/6 = 1.5 times the logical size: 100 PB times 1.5 = 150 PB. Three-way replication would need 300 PB, twice as much. A 6+3 code survives the loss of any 3 shards of a group, so it survives the loss of a whole zone. A wider code such as 10+4 costs only 1.4 times, but it cannot survive a zone loss in a 3-zone region (see the design section).
Disks. A 20 TB HDD, filled to 80 percent, holds 16 TB. 150 PB / 16 TB = 9,375 drives. A storage server has 60 drives, so we need 156 servers, say 160. Each is a JBOD box with a modest CPU, since the work is mostly I/O.
IOPS check. An HDD does about 100 random I/Os per second. A GET of a 4 MB object reads 6 data shards of about 670 KB, so 6 disk I/Os (each takes about 8 ms seek plus 3 ms transfer at 200 MB/s). 30,000 GET/s times 6 = 180,000 IOPS. A PUT writes 9 shards: 5,000 times 9 = 45,000 IOPS. Total 225,000. At 50 percent utilization one drive gives 50 IOPS, so we need 225,000 / 50 = 4,500 drives. Capacity needs 9,375 drives, so the cluster is limited by space, not by IOPS, and has room to grow traffic by 2 times. With small objects (4 KB) the IOPS would dominate, and the design packs small objects together (see the data layout).
Bandwidth. 30,000 GET/s times 4 MB = 120 GB/s out, plus 5,000 PUT/s times 4 MB = 20 GB/s in: 140 GB/s, about 1.1 Tbit/s. A front-end server with a 100 Gbit/s NIC (12.5 GB/s) at 50 percent gives 6 GB/s, so we need 140 / 6 = 23 front-end servers at the minimum; we plan 40 for failures and zone loss. Writes also fan out to 9 storage servers, so internal traffic from front ends to storage is 1.5 times 20 = 30 GB/s on writes.
Metadata. Each object has a record of about 500 bytes (key, size, checksum, version id, time, shard locations, ACL id). 25 billion times 500 bytes = 12.5 TB. Each partition of the index holds 200 GB, so 12.5 TB / 200 GB = 63, rounded to 64 partitions at the start. With 3 replicas this is 37.5 TB on SSD. Metadata operations equal request rate (35,000 per second) plus LIST, which is light by comparison.
Repair. A failed 20 TB drive (16 TB used) must be rebuilt by reading 6 shards for each lost shard. If 200 drives take part at 50 MB/s each, aggregate write speed is 10 GB/s, and 16 TB is written back in 16e12 / 10e9 = 1,600 s, under 30 minutes (the reads are 6 times larger, 96 TB, spread over many drives, which is why many drives must help). If the rebuild goes to one spare drive, the limit is that drive's 200 MB/s write: 16 TB / 200 MB/s = 80,000 s = 22 hours. So spread the rebuild across the cluster.
Durability arithmetic. HDD annual failure rate about 1.5 percent. A group of 9 shards loses data when 4 shards fail before repair. Per group, the first failure happens 9 times 0.015 = 0.135 times a year. Repair window T = 12 hours (a cautious number including detection and queueing). A drive fails in that window with probability 0.015 x 12 / 8,760 = 2e-5. Three more failures among the 8 others: C(8,3) = 56, times (2e-5)^3 = 8e-15, gives 4.5e-13. Times 0.135: about 6e-14 per group per year. The target is 1e-11, so independent disk failures leave a margin of about 170 times. The real risk is correlated: a bad firmware batch, a zone fire (3 shards at once, which leaves only 0 further failures to survive), a software bug that deletes or corrupts data, an operator error. Design for those, with zone spread, checksums, versioning and slow deletes.
api: PUT /{bucket}/{key} with body and headers Content-MD5 or x-amz-checksum-sha256. Returns 200 with an ETag and, if versioning is on, a version id. Single request limit 5 GB.
GET /{bucket}/{key}, optional Range: bytes=0-1048575 header, optional ?versionId=. Returns 200 or 206 with the body and the checksum. Conditional headers (If-None-Match) are supported.
Multipart upload: POST /{bucket}/{key}?uploads returns an upload id. PUT /{bucket}/{key}?partNumber=N&uploadId=U uploads a part (5 MiB to 5 GiB, up to 10,000 parts). POST /{bucket}/{key}?uploadId=U with a list of part numbers and ETags completes it. DELETE with the upload id aborts it. Parts can be uploaded in parallel and retried independently.
GET /{bucket}?list-type=2&prefix=logs/2026/&delimiter=/&max-keys=1000&continuation-token=T returns keys in lexicographic order, common prefixes, and a token for the next page.
DELETE /{bucket}/{key}: with versioning, adds a delete marker; without, removes the object. Authentication uses signed requests (AWS Signature V4: an HMAC-SHA256 over the request) or presigned URLs with an expiry.
datamodel: Two separate systems. The metadata index maps (bucket, key, version) to the object record. The data store holds shards on disks. Separating them lets each scale on its own: metadata is small, random-access and needs strong consistency; data is large, mostly sequential and only needs durability.
Metadata layout. A sorted key-value table with the key (bucket id, key bytes, inverted version time) so that the newest version of a key sorts first, and LIST is a range scan. The table is split into ranges (partitions) by key; each partition is a replicated state machine (Raft or Paxos) with 3 replicas in 3 zones. The storage engine inside is an LSM tree or a B-tree. Partitions split when they grow beyond 200 GB or get hot, and a directory service maps key ranges to partitions.
Object record: size, content type, user metadata, checksum, storage class, encryption key id, ACL id, creation time, and a list of chunk groups. Large objects are cut into chunks of, say, 64 MB, and each chunk is erasure coded as its own stripe, so a 4 MB object is one stripe, and a 1 TB object has 16,000 stripes.
Data layout. A stripe of 6 data + 3 parity shards is written to 9 different drives on 9 different servers, 3 in each zone. Each shard is a record in a large append-only "extent" file of, for example, 1 GB per drive. A shard has a header with its stripe id, length and a checksum (CRC32C). A small per-drive index maps stripe id to extent and offset. Extents are sealed when full and never changed; deletes mark space dead and a garbage collector compacts extents later.
Small objects. Objects under 1 MB are packed into larger stripes: many objects are written into a shared stripe, with the index holding (stripe, offset, length) for each. This keeps the number of disk I/Os per PUT low and avoids tiny shards, the idea of Facebook's Haystack. A GET then reads from one or two data shards, and no parity read is needed unless a drive is down.
design: Front end. A client request reaches a load balancer (DNS with many addresses, or anycast) and then a stateless front-end server. The front end checks the signature and policy, finds the bucket's configuration, and handles TLS. It also throttles per account, so a noisy tenant cannot take all capacity. Front ends hold no durable state, so we scale them by adding machines.
PUT path. The front end streams the body. It computes the SHA-256 while reading, splits the data into stripes, computes 3 parity shards for each stripe (Reed-Solomon over a finite field, using SIMD instructions at several GB/s per core), and writes the 9 shards in parallel to 9 storage nodes chosen by a placement service for balance and zone spread. Each node appends the shard to its extent, checks the checksum, and acknowledges after the data is on stable storage (fsync or a battery-backed write cache). When at least 8 of 9 shards are durable (more than the 6 needed, so there is a margin for a later failure), the front end commits the metadata record with a consensus write in the right index partition, and only then returns 200. If it fails before the commit, the shards are orphans, and a background garbage collector deletes them.
GET path. The front end reads the metadata record (from the partition leader or a replica with a lease, for strong consistency), then fetches the 6 data shards in parallel from their nodes, checks each checksum, and streams the bytes. To cut tail latency it can ask for 7 shards and use the first 6 that arrive. If a data shard is missing or corrupted, it reads a parity shard and reconstructs. A range request reads only the stripes and shards that cover the range.
Placement and failure domains. The placement service picks 9 drives so that no two are on the same server or rack, exactly 3 are in each zone, and drives are balanced by free space and load. A 10+4 code over 3 zones would put up to 5 shards in one zone, more than its 4-shard tolerance, so it cannot survive a zone loss. A 6+3 code with 3 shards per zone can. The price is 1.5 times raw size instead of 1.4. Single-zone storage classes use 10+4 for lower cost.
Metadata consistency. The index partitions use Raft or Paxos. A write goes to the leader of the partition, is replicated to a majority, and is applied in order. Reads go through the leader or a replica that holds a lease. This gives strong consistency for GET after PUT, HEAD, and LIST after PUT (a LIST reads a consistent snapshot of the range).
Background services. Scrubbers read every shard periodically and verify checksums to find silent corruption (bit rot) before a second failure. Repair workers rebuild lost shards from the survivors on healthy drives. A rebalancer moves data when new drives join. A lifecycle engine applies the bucket rules. A garbage collector removes orphan shards and dead extents.

deepdive: Erasure coding and repair cost. Reed-Solomon (k, m) turns k data shards into k + m shards so that any k are enough to rebuild. The storage overhead is (k + m)/k. 6+3 costs 1.5 times, 10+4 costs 1.4 times, and 3 copies cost 3 times. The price is paid on repair and degraded reads: rebuilding one lost shard needs k reads. Locally repairable codes (LRC), as in Windows Azure Storage, add local parity so that a single lost shard is rebuilt from a small group (for example 6 reads instead of 12), at a small extra storage cost. Hot data is often replicated or cached, and cold data is erasure coded: the code is chosen by storage class.
Strong consistency for listing. LIST must return keys in order, and after a PUT the key must appear. If the index is sharded by key range, a LIST by prefix usually hits one or two partitions and is a range scan, so it is cheap. If it were sharded by hash of the key (as for a pure key-value store), a LIST would have to ask every partition and merge. This is why object stores shard the index by key range, and why a hot prefix (a million writes per second into "logs/2026-10-26/") can overload a single partition. The remedy is automatic splitting by load and a note to customers to spread keys over many prefixes. S3 does this partition splitting for you now and supports at least 3,500 writes and 5,500 reads per second per prefix.
Durability beyond the math. Disks lie. A write may be acknowledged and lost, a read may return old data, a bit may flip. Defenses: a checksum on every shard, checked on write, on read and in the scrubber; end-to-end checksums from the client (x-amz-checksum headers) so corruption in the network or memory of the front end is also caught; a rule that data is never overwritten, only appended and later garbage-collected; and slow deletes (a delay between logical delete and physical erase) so that a bug in the delete path can be noticed and rolled back. Many incidents in storage systems come from deletion and repair code, not from the disks.
Multipart upload and atomic visibility. Each part is stored as its own set of stripes under the upload id, and nothing is visible. Complete writes one metadata record that lists the parts, a single atomic commit. Abort, or a lifecycle rule for unfinished uploads after 7 days, frees the parts. Clients upload parts in parallel (8 to 16 connections) to use the line rate, and retry a failed part alone. The final ETag is a hash of the part hashes, so it is not the MD5 of the whole object.
tradeoffs: Erasure coding or replication. Choose replication (3 copies) for small hot objects, for the first hours after write, or when read latency and simple degraded reads matter more than cost. Choose erasure coding for large and cold data, where the 1.4 to 1.5 times overhead saves hundreds of PB. You give up repair cost and CPU in the second case, and money in the first.
Code parameters. Choose wide codes such as 10+4 or 12+4 when the cluster has many racks in one failure domain and cost is critical. Choose narrower codes such as 6+3 when you have only 3 zones and must survive a zone loss, or when you want fewer reads per repair. Wider codes use fewer bytes but need more I/Os per GET and per repair, and the tail latency of reading 10 or 12 shards is worse.
Index sharding by range or by hash. Choose range sharding when LIST by prefix is a core feature, as in S3, and handle hot ranges by splitting. Choose hash sharding for a pure key-value access pattern, where even load is more important than ordered scans. Range gives order and risks hot spots; hash gives balance and loses order.
Strong or eventual consistency. Choose strong consistency (a consensus log for metadata) when applications such as Spark, Hive and table formats list directories and expect to see their own writes. This is now standard in cloud storage. Eventual consistency is cheaper to build, but it forced users to build workarounds for years.
Build or use S3. Choose a managed object store in almost every case; it is cheaper than the people needed to run a 100 PB system. Choose Ceph, MinIO or SeaweedFS for on-premises needs, data sovereignty or very high egress costs, and staff a team for repair and capacity planning.
failures: A drive fails. The node reports errors or the scrubber finds bad checksums. The repair service lists the stripes that had a shard on the drive (the per-drive index tells it), reads the survivors, rebuilds each lost shard, and writes it to a new drive in another failure domain. With the whole pool helping, 16 TB takes about 30 minutes in our estimate. During this time GETs for these stripes use parity reads and are slower.
A server or rack fails. Up to 60 shards are lost per server, spread over many stripes (at most one per stripe by the placement rule). Repair is the same, but for 60 drives of data. Rack-aware placement keeps at most one shard per rack for a stripe, so a rack loss never takes more than one shard of any stripe.
A zone fails. With 6+3 over 3 zones, every stripe loses 3 shards and still has 6, enough to read. Reads cost more because they need decoding. New writes continue: the front end writes the 9 shards over the two live zones (5 and 4), accepting that these stripes cannot survive another zone loss, and a background job moves them to the normal 3-3-3 layout when the zone returns. The metadata partitions keep a Raft majority from the 2 live zones.
Metadata partition leader fails. The Raft group elects a new leader in about a second, and requests for those key ranges pause for that time. Clients retry with backoff. Since each partition is small and independent, only 1/64 of the key space is affected.
Silent corruption. The scrubber reads every shard periodically and compares checksums. 150 PB over 9,375 drives is 16 TB per drive; at a background rate of 50 MB/s per drive that is 320,000 s, about 3.7 days of pure reading, so a full cycle takes 2 to 4 weeks at low priority. Any mismatch triggers repair.
evolution: At 1 TB, a single server with a file system and an HTTP front end (or MinIO) is enough, with two copies. At 1 PB, 10 to 30 nodes with 3-way replication and metadata in PostgreSQL or an embedded Raft store. At 100 PB, the design above: erasure coding, a range-partitioned index, zones and scrubbing. At exabyte scale, add automatic index splitting, per-tenant placement, storage classes (SSD for small hot objects, HDD for the bulk, archive tiers for cold data), cross-region replication and a fleet system that continuously replaces hardware. Table formats such as Iceberg and Delta then add atomic multi-file commits on top, since an object store has none.
followups: Why erasure coding and not three copies? || 10+4 uses 1.4 times the space against 3 times and survives 4 lost shards instead of 2 lost copies. It costs more I/O on read and repair, so it is used for large and cold data, and replication or a cache is used for hot data.
How do you get strong consistency for GET after PUT? || Put the commit of the metadata record through a consensus group (Raft or Paxos) per key range, and serve reads from the leader or a leased replica. The PUT returns only after the record is committed and the shards are durable, so any later read sees it.
How does LIST work with billions of keys? || The index is a sorted table split into key ranges, so listing a prefix is a range scan on one or few partitions that returns up to 1,000 keys and a continuation token. Hot prefixes are split by load. Hash sharding would make LIST a scatter-gather over all partitions.
How do you detect and repair bit rot? || Every shard has a checksum checked on write, read and by a background scrubber. A mismatch triggers reconstruction from the other shards in the stripe, and the bad shard is replaced. End-to-end checksums from the client protect against corruption before the data enters the store.
How do you upload a 2 TB file reliably? || Use multipart upload: split into parts of 200 MB or more (the limit is 10,000 parts), upload parts in parallel, retry failed parts only, and complete with one request that commits the object atomically. A lifecycle rule cleans up abandoned uploads.
Where do eleven nines come from and can you promise them? || From many independent shards with fast repair, so that data loss needs four simultaneous shard failures before repair finishes. The model gives about 6e-14 per group per year, but real loss comes from correlated failures and software bugs, so the number is a design target backed by zone spread, checksums, scrubbing and slow deletes, not a measured fact.

@@ job-scheduler
title: Design a distributed job scheduler
category: Infrastructure
level: Senior / Staff
concepts: workflow, airflow, temporal, durableexec, leaderelect, coordination, etcd, zookeeper, fencing, idempotence, retries, backpressure, partitioning, conshash, mqueue, postgres, orchestration, kubernetes, autoscaling, deliverysem, exactlyonce, dagsched, hwclocks
summary: A job scheduler runs work at the right time and on a free machine. Users define jobs ("run this report every day at 09:00 Bengaluru time", "retry this payment in 10 minutes") and the system must start each one on time, exactly once as far as the user can see, even if schedulers and workers crash, clocks differ, and a million jobs are due at the same minute. The hard parts are: making sure that one trigger leads to one execution when several scheduler instances race; keeping a job alive across worker failures with leases and heartbeats; retries without storms; fairness between tenants; and the odd rules of time (time zones, daylight saving, missed runs).
requirements: Functional requirements. Create, update, pause and delete a job with a schedule: a cron expression with a time zone, a fixed interval, or a one-time timestamp. Each job has a payload, a target (a queue name or an HTTP endpoint or a container image), a timeout, a retry policy and a concurrency policy (allow overlap, skip if still running, replace the old run). Users can trigger a job manually, cancel a run, see the history of runs with status and logs, and get alerts when a run fails or does not start.
Non-functional requirements. Timeliness: p50 start delay under 1 s and p99 under 30 s, also at the top of the minute and hour when many jobs are due. Reliability: at-least-once execution of every trigger; at-most-one active execution per trigger when the job asks for it; no trigger lost when any single scheduler, worker or database node fails. Scale: 50 million job definitions and 1 billion executions per day. Multi-tenancy: one tenant cannot starve others. Operability: clear states, metrics, and a way to see why a run did not start.
Assumptions. The average run takes 2 seconds of a worker slot. About 30 percent of recurring jobs use cron expressions on round minutes, so load comes in spikes at :00 of each minute.
estimates: Executions. 1 billion per day divided by 86,400 s = 11,574 executions per second on average, about 11,600. Spike: if 30 percent of the day's fires on a minute boundary, think of it per minute: 1e9 / 1,440 minutes = 694,000 executions in an average minute, 30 percent of them, about 208,000, are due in the first 2 seconds of the minute, which is 100,000 per second at the start of every minute. We design for 100,000 triggers per second for a few seconds, and for 11,600 per second on average.
Storage of definitions. 50 million jobs times 1 KB (schedule, payload up to a few hundred bytes, policy, owner) = 50 GB. This fits easily in a sharded SQL database.
Storage of executions. Each execution row is about 300 bytes (ids, state, times, attempt, worker, result code). 1e9 per day times 300 bytes = 300 GB per day. Seven days of hot history is 2.1 TB, and older rows move to cheap storage (object store, columnar files) in a daily job. The write rate on the execution table is several writes per execution (created, started, heartbeat, finished), so about 5 times 11,600 = 58,000 row writes per second on average. Heartbeats are kept out of the table (see design), otherwise it would be much larger.
Shards. We split the job space into 256 shards by hash of the job id. Peak 100,000 triggers per second over 256 shards is about 390 per shard per second, and the average is 45 per shard per second. One Postgres primary comfortably handles a few thousand simple transactions per second, so the database is not the limit. Each shard holds 50 GB / 256 = 195 MB of definitions and 8 GB/day of executions.
Workers. Average concurrency is executions per second times duration: 11,600 times 2 s = 23,200 busy slots. A worker has 64 slots, so the average needs 363 workers. At the minute peak, 100,000 per second would need 200,000 slots. We do not buy that. We size the fleet for 800 workers x 64 = 51,200 slots, which can start 25,600 two-second jobs per second. A spike of 100,000 per second for 2 s makes 200,000 jobs; with 25,600 per second capacity minus 11,600 average load, the spare is 14,000 per second, so the backlog drains in 200,000 / 14,000 = 14 seconds. That meets the p99 of 30 s. Autoscaling adds workers in the next minutes if the backlog stays.
Poll rate. A scheduler instance polls its shards for due work every 500 ms. 256 shards x 2 polls per second = 512 queries per second in total, trivial.
api: POST /v1/jobs creates a job: {name, schedule: {cron: "0 9 * * *", tz: "Asia/Kolkata"} or {every_s: 300} or {at: "2026-11-02T10:00:00Z"}, target, payload, timeout_s, retry: {max_attempts, backoff}, concurrency: "allow" | "forbid" | "replace"}. Returns {job_id, next_run_at}.
PATCH /v1/jobs/{id} changes the schedule or policy, and POST /v1/jobs/{id}:pause and :resume. DELETE /v1/jobs/{id} removes it; running executions finish or are cancelled by choice.
POST /v1/jobs/{id}/runs triggers a run now (manual). The call accepts an Idempotency-Key header, so a retried HTTP request does not create two runs.
GET /v1/jobs/{id}/runs?state=failed&limit=50 lists executions. GET /v1/runs/{run_id} returns the state, attempts, timings and log pointer. POST /v1/runs/{run_id}:cancel asks for cancellation.
Worker protocol (internal): lease(queue, max_n, lease_s) returns runs; heartbeat(run_id, lease_token) extends the lease; complete(run_id, lease_token, status, result) closes it. The lease token is a number that increases with each lease, and the complete call is rejected if the token is old.
datamodel: jobs table (sharded by hash(job_id)): job_id, tenant_id, schedule (cron text, tz, interval, one-time), payload, target, policy, state (active, paused), next_run_at, version. Index on (state, next_run_at) so that the scheduler can find due jobs by range scan.
runs table (same shard as the job): run_id, job_id, scheduled_for (the planned time, not the actual), attempt, state (queued, leased, running, succeeded, failed, cancelled, timed_out), lease_token, lease_until, worker_id, enqueued_at, started_at, finished_at, result. Unique key on (job_id, scheduled_for). This key is the foundation of "one trigger, one run": a second insert for the same trigger fails.
Queue of ready work. A run in state queued is a ready task. Workers take work from a queue per priority class and tenant. We keep it in the runs table with index (queue, priority, enqueued_at) where state = queued, taken with SELECT ... FOR UPDATE SKIP LOCKED, which is a good fit up to a few thousand tasks per second per shard. For higher rates a separate queue system (Kafka, SQS) holds the ready tasks and the table keeps the truth.
Heartbeats are in memory or in Redis with a short TTL, keyed by run_id, not written to the table; the table stores lease_until only when a worker takes or renews the lease at a coarse interval (every 30 s).
Leases for shards: key "shard/{n}" in etcd or ZooKeeper with a TTL; the holder is the scheduler instance responsible for those jobs. The value includes a fencing epoch that increases at each new owner.
design: Components. A stateless API service writes jobs. A set of scheduler instances each own a subset of the 256 shards through leases. A dispatch layer makes ready runs available to workers. A fleet of workers executes them. A reaper finds runs whose lease expired. A history archiver moves old runs to cold storage.
Scheduling loop. For each owned shard every 500 ms, the scheduler selects jobs with next_run_at <= now + 1 s, in batches of 500, and for each job it does one transaction: insert a run row with scheduled_for = next_run_at (the unique key prevents duplicates), compute the next fire time from the cron expression, update next_run_at, and commit. A job whose fire time is in the near future (within the next second) is loaded into an in-memory timing wheel, a ring of time slots, so the scheduler wakes at the exact moment and moves the run to queued without another query. Using the planned time and not the clock reading makes the trigger identity deterministic: if two schedulers think they own the shard, both try to insert (job, 09:00:00) and only one succeeds.
Ownership and fencing. Each scheduler holds leases for its shards in etcd. If an instance stalls (a long GC pause) and loses its lease, another instance takes the shard and starts to fire. The old one may wake up and continue to write. The unique key already makes duplicate triggers harmless, and each write also includes the fencing epoch: the update of next_run_at has a condition "WHERE shard_epoch <= my_epoch", so a stale owner cannot move the schedule backward. Safety does not rely on the lease being perfect.
Dispatch and execution. A queued run is taken by a worker with a lease of, say, 60 seconds. The worker marks it running, calls the target with the run id as an idempotency key, and sends heartbeats every 15 s. On success, the worker calls complete with the lease token, and the run becomes succeeded. The next trigger is never held back by a running one unless the job's concurrency policy says "forbid" (the scheduler checks for a non-final run of the same job and records the new trigger as skipped).
Failure handling. If a worker dies, its heartbeats stop and the lease runs out. The reaper finds runs with lease_until < now and state running, increases the attempt counter, and returns the run to queued with a delay computed from the retry policy: delay = min(cap, base x 2^attempt) with a random jitter of plus or minus 20 percent. After max_attempts the run is failed and an alert is sent. A worker that comes back after its lease was lost has an old token, and its complete call is rejected.
Multi-tenancy and priority. The queue is a set of logical queues per tenant, served by weighted fair queuing: each tenant gets a share of worker slots proportional to its weight, and unused share flows to others. A tenant that creates 10 million jobs for 09:00 gets its share and a deep queue, while other tenants keep their start delay. Priority classes (critical, normal, batch) have separate pools so that batch work cannot delay critical work.

deepdive: One trigger, one run. The scheduler must not fire a job twice because two instances overlapped, and must not skip it because both thought the other had it. The reliable pattern is to make the trigger a row with a deterministic identity (job_id, scheduled_for) and rely on a unique constraint in the database, a single linearizable point. Leader election and leases reduce the number of races, so the database sees few conflicts, but they are not the safety mechanism. This is the same idea as Google's cron: the schedule is replicated state, and launching is made idempotent by naming each launch (job name plus planned time), so that after a leader change the new leader can ask "was this launch done?" and neither repeat nor miss it.
At-least-once and idempotent work. After the worker calls the target, it may die before it records success. The reaper will run the job again. So the system gives at-least-once execution, and the target must be safe to run twice. The run id is passed as an idempotency key, and well-built targets keep a table of processed ids or make the effect idempotent (set a value, not add to it). Exactly-once execution of side effects is not possible in general without the cooperation of the target. Some systems (Temporal, Step Functions) give exactly-once for the orchestration itself with replay of a recorded history, but activities still run at-least-once.
Time is hard. A cron expression like "0 2 30 * *" has no next fire in February; "0 2 * * *" in a zone with daylight saving has no 02:00 on the day clocks jump from 01:59 to 03:00, and 01:00 happens twice on the day clocks go back. Decide and document: for skipped local times run at the next valid time (03:00); for repeated local times run once (the first). Compute next fire times in the job's IANA time zone with a maintained library, and store both the local rule and the next fire time in UTC. Update the time zone database (tzdata) on all nodes together, since its rules change several times a year in some countries. Also, never schedule by sleeping: compute the absolute fire time and compare with a clock that is NTP-synchronized; a skew of 200 ms is tolerable, a skew of minutes is a bug to alarm on.
Misfires and catch-up. If all schedulers are down for 10 minutes, a job that fires every minute has 10 missed triggers. Policies: skip all missed (for a "refresh cache" job), run one catch-up (for "daily report"), or run all in order (for a billing tick). The policy is part of the job. A limit such as "run missed triggers only if less than 1 hour late" prevents a flood after a long outage. Kubernetes CronJob counts missed starts and stops scheduling after 100 misses, which shows the same trade-off.
The top-of-the-minute spike. Humans choose round times. Add jitter by design: let users mark jobs as tolerant ("start within 5 minutes") and spread them by hash(job_id) across the window; show the actual start in the history. Pre-compute the next minute's due set a few seconds ahead and load it into the wheel, so the work at :00 is moving in-memory entries and a batch insert, not a fresh scan. Insert runs in batches of 500 to 1,000 per transaction. Admission control on queue depth protects the workers.
Retry storms. If a downstream service is down, every job that calls it fails, retries after the same backoff, and hits it again together. Use exponential backoff with jitter, a per-target circuit breaker that pauses dispatch to a target after many failures, and a retry budget per tenant. Move the run to a dead-letter state after max attempts, and make it easy to replay in bulk after the fix.
Long-running jobs and checkpoints. A job that runs for 6 hours cannot be restarted from zero at every worker loss. The worker reports progress or checkpoints to the target; on retry the payload includes the last checkpoint. For multi-step flows with dependencies (a DAG), use a workflow engine on top: each task is a job, dependencies are edges, the engine triggers a task when its upstream tasks succeed. Airflow keeps this state in a metadata database; Temporal stores an event history and replays the workflow code.
tradeoffs: Database-backed queue or message broker. Choose the database (Postgres with SKIP LOCKED) as the queue when rates are under a few thousand tasks per second per shard and you value one place for state, transactions with the run row and easy debugging. Choose Kafka or SQS for the ready queue when the rate is far above that or you need many independent consumers; the database then keeps only the truth. The price of the broker is a second system and the need to keep it consistent with the table (use an outbox).
Pull or push dispatch. Choose pull (workers lease tasks) because workers take only what they can handle, and a slow worker does not receive more. Backpressure is natural. Choose push (the scheduler calls the worker) when the latency target is a few milliseconds and workers are stateless HTTP services behind a load balancer; then you need your own queue-depth control and retries.
Leader per shard or one global leader. Choose one global leader (a single scheduler elected through etcd) up to about 10,000 triggers per second, since it is simple and has no shard map. Choose sharded ownership with leases when you need more capacity or want a failure to affect only a part of the schedule. More shards means more things to balance and a rebalance protocol.
Polling the database or a timing wheel. Choose polling an indexed next_run_at column for simplicity, with a poll interval of 0.5 to 1 s, which is the usual choice and enough for second-level timeliness. Choose an in-memory hierarchical timing wheel for sub-second accuracy and very high counts of near-term timers, loading from the database in windows. The wheel gives O(1) insert and expiry but must be rebuilt after a restart.
Build or adopt. Choose Airflow, Temporal, Argo or Kubernetes CronJob when the jobs are data pipelines or workflows and the volume is modest. Choose to build a custom scheduler when you have millions of per-user timers (reminders, subscription renewals, retries) which general workflow engines handle poorly in cost and latency. The decisive facts are the number of timers and the need for tenant fairness.
failures: A scheduler instance dies. Its etcd lease expires in about 10 seconds. Another instance takes the shards, reloads due jobs from the database, and continues. Triggers due during the gap fire late (up to about 10 to 15 s) but are not lost, since next_run_at in the database says what is due. Unique keys prevent duplicates for anything already fired.
Database shard primary fails. Failover to a replica takes 10 to 30 seconds. Jobs of that shard (1/256 of the system) are delayed. We use synchronous replication to one replica in another zone for the runs table, so no committed run is lost. Other shards are unaffected.
Coordination service (etcd) down. Running schedulers keep their shards until their leases expire; if the outage is longer, they stop firing (safe), and the system falls behind. When it returns, missed triggers are handled by the misfire policy. Make the lease TTL longer than typical etcd leader elections (a few seconds) to avoid flapping.
Worker failure and slow worker. Dead workers are handled by lease expiry. A slow or hung job is stopped by the timeout and a kill signal, then retried. A worker with a bad disk can fail many jobs; the dispatcher marks it unhealthy after a failure rate threshold and drains it.
Zone failure. Schedulers, database replicas and workers run in three zones. Losing one reduces worker capacity by a third, and the backlog grows during the minute peaks. Priority classes keep critical jobs flowing, batch jobs wait. Autoscaling adds workers in the surviving zones.
Overload and cascading retry. A bug floods the system with 10 million jobs at once. Per-tenant quotas on job creation and on queue depth reject extra work with 429, fair queuing limits the effect to that tenant, and the reaper never retries immediately.
Bad deploy. A scheduler version that computes cron wrongly could skip or double-fire thousands of jobs. Deploy to one shard first, compare the number of triggers per minute with the previous day, and keep a dry-run mode that computes next fire times and diffs them with the stored ones.
evolution: At 1,000 jobs, one process with a library such as Quartz or APScheduler and a database table is enough, with one standby and a lock. At 1 million jobs, a few scheduler instances with a leader elected by the database or etcd, and a queue for execution. At 50 million jobs and 1 billion executions per day, the sharded design above with fair queues and archiving. At 1 billion jobs (a timer per user or device), move to a hierarchical timing wheel per shard that holds only the next hour in memory, partition by tenant and time bucket in a wide-column or LSM store, batch triggers into one dispatch per bucket, and give workers a pull protocol over a durable log.
followups: How do you make sure a job runs exactly once when several scheduler instances are running? || You cannot guarantee exactly-once execution, only exactly-once triggering. Give each trigger a deterministic id (job id plus planned time) and insert it with a unique constraint, so duplicates are rejected. Execution is at-least-once, and the job must be idempotent, using the run id as an idempotency key.
What if a worker dies in the middle of a job? || Heartbeats stop and the lease expires. A reaper puts the run back in the queue with attempt + 1 and a backoff. The old worker's later completion is rejected because its lease token is old (fencing). Long jobs should checkpoint so the retry does not start from zero.
What is the role of leader election if the database already prevents duplicates? || It reduces conflicts and wasted work, so the shard has one active scheduler and the polling load is not repeated. The unique key and the fencing epoch are the safety mechanism; leases only give liveness and efficiency. A stale leader can do no harm.
How do you handle daylight saving time? || Store the rule with the IANA zone, compute next fire times with a tz library, and define policies: a skipped local time runs at the next valid instant, a repeated local time runs once. Keep tzdata updated everywhere and test with the dates of transitions.
How do you stop a spike at the top of the hour from hurting the system? || Let tolerant jobs declare a window and spread them by a hash, precompute the next minute's due jobs, batch inserts, and use admission control and fair queues. Size workers for the average plus an acceptable drain time, and autoscale on queue age, not CPU.
How do you prevent one tenant from starving the others? || Weighted fair queuing per tenant, quotas on job creation and concurrent runs, separate pools for priority classes, and shedding of the tenant's excess with 429. Measure start delay per tenant, not just overall.
How would this change for a million timers per second, such as delayed retries? || Use a log-structured or wide-column store partitioned by time bucket, a hierarchical timing wheel in memory for the next minutes, and batch dispatch per bucket. Avoid a row update per timer fire; delete whole expired buckets instead.

@@ metrics-monitoring
title: Design a metrics and monitoring system
category: Infrastructure
level: Senior / Staff
concepts: prometheus, grafana, otel, observability, invindex, postings, encoding, wal, compaction, partitioning, conshash, replication, quorum, cms, hll, sampling, tieredstorage, sepstorage, windowing, backpressure, pubsub, bloom, s3
summary: A metrics system collects numbers from every machine and service (CPU, request counts, latencies), stores them as time series, answers queries for dashboards in under a second, and evaluates alert rules that wake a person when something breaks. It must keep working when the rest of the company is failing, because that is exactly when it is needed. The hard parts are the write volume (millions of samples per second, all appends), storing years of data cheaply with good compression and rollups, label cardinality that can grow without bound, queries that cover thousands of series, and an alerting path that is more reliable than the thing it watches.
requirements: Functional requirements. Ingest samples (series name plus labels, timestamp, value) from services and hosts, by pull (scrape an HTTP endpoint) or by push (an agent or OpenTelemetry collector). Query with a time-series language (selectors by label, rate, sum by, histogram quantile). Dashboards show graphs over a range. Alert rules are queries evaluated on a schedule; they fire when a condition holds for some time, are grouped and routed to on-call tools (pager, chat), and can be silenced. Retention: full resolution for 15 days, 5-minute rollups for 13 months.
Non-functional requirements. Write availability: never drop data when one node fails; a short loss of query service is acceptable, a loss of ingestion is not. Freshness: a sample is queryable within 10 seconds of being scraped. Query latency: p95 under 2 s for dashboard queries over 6 hours and under 10 s over 30 days. Alert latency: from a failure to a page in under 2 minutes. Scale: 50 million active series. Cost: storage under 2 bytes per sample on average. Isolation: a team that adds a high-cardinality label must not break others.
Assumptions. 50,000 servers and containers, each exposing about 1,000 series on average, scraped every 10 seconds. Series are mostly stable (they live for days). Samples are 64-bit floats.
estimates: Active series. 50,000 targets times 1,000 series = 50 million active series.
Ingest rate. Each series gets a sample every 10 seconds: 50 million / 10 = 5 million samples per second. Per day: 5e6 times 86,400 = 432 billion samples.
Raw versus compressed size. A sample stored naively is 16 bytes (8 for timestamp, 8 for value): 432e9 times 16 = 6.9 TB per day. With Gorilla-style compression (delta-of-delta for timestamps, XOR for values), the Facebook paper reports about 1.37 bytes per sample on average. 432e9 times 1.37 = 592 GB per day. Prometheus reports about 1 to 2 bytes per sample in practice. We use 1.5: 648 GB per day.
Retention of full-resolution data. 15 days times 648 GB = 9.7 TB. With replication factor 3 in the ingest layer for a short time and 2 copies in long-term storage on object storage (the object store keeps its own durability), we plan for 10 TB on object storage and 3 days of local disk on the ingesters.
Rollups. A 5-minute rollup keeps min, max, sum and count (4 values) for each series. Points per day per series: 288. 50 million times 288 = 14.4 billion points per day. At about 6 bytes per point after compression: 86 GB per day. For 13 months (395 days): 34 TB. Together with raw data, about 44 TB. This is cheap on an object store: at $0.023 per GB-month, 44 TB costs about $1,000 per month. Rollups cut the cost of old data by a factor 8 to 10 compared with keeping raw samples (395 days of raw would be 256 TB).
Memory for the head. Recent data is kept in memory. A series costs about 3 KB in the in-memory head (labels, chunk buffers, index entries). 50 million times 3 KB = 150 GB. With replication factor 3 this is 450 GB across the ingesters.
Ingesters. One ingester can take about 100,000 samples per second with comfortable headroom. The write load with replication factor 3 is 15 million samples per second, so 150 ingesters. Each holds 50e6 times 3 / 150 = 1 million series and 3 GB of head. We choose ingesters with 16 GB of RAM, using 3 GB for the head, 5 GB for the WAL and recent blocks cache, and the rest for queries and the OS.
Network. Each sample on the wire is about 10 to 20 bytes after protocol compression (snappy). 5 million times 20 = 100 MB/s from agents to the distributors, 300 MB/s to ingesters with replication factor 3. This is small.
Queries and alerts. 100,000 alert rules evaluated every 60 s is 1,667 queries per second. Each looks at a few hundred series for 5 to 10 minutes of data from memory, taking 5 to 20 ms, so 20 CPU cores handle them. Dashboards: 5,000 users with 10 panels each refreshing every 30 s is 1,667 queries per second as well. A panel over 6 hours touches 200 series x 2,160 samples = 432,000 samples, which is about 650 KB compressed and takes about 10 to 50 ms to decode.
api: Write (push): POST /api/v1/push with a compressed protobuf of {labels, samples[{timestamp_ms, value}]} per series (Prometheus remote-write, or OTLP over HTTP). Returns 200 once the write is accepted by a quorum of ingesters, 429 when the tenant is over its limits.
Scrape (pull): the collector requests GET /metrics from each target, parses the text format (name{label="v"} value), adds the labels job and instance and the scrape time, and pushes the result to the write path.
Instant query: GET /api/v1/query?query=sum by (service)(rate(http_requests_total[5m]))&time=T returns the vector at time T. Range query: GET /api/v1/query_range?query=...&start=...&end=...&step=15s returns a matrix for graphs.
Metadata: GET /api/v1/label/{name}/values, GET /api/v1/series?match[]=..., used by dashboards for autocompletion.
Rules: PUT /api/v1/rules/{namespace} with a group of recording rules and alerting rules: {alert: "HighErrorRate", expr: "...", for: "5m", labels: {severity: "page"}, annotations: {...}}. Alerts are sent to the alert manager with POST /api/v2/alerts. Silences: POST /api/v2/silences with matchers and an end time.
datamodel: A series is identified by its name and the full set of labels: http_requests_total{service="cart", method="GET", status="200", pod="cart-7f"}. A sample is (timestamp in milliseconds, 64-bit float). Series ids are 64-bit integers assigned by the ingester, or the hash of the label set.
In-memory head. Per series: labels, the open chunk (up to 120 samples, about 2 hours of data at 1 sample per minute or 20 minutes at 10 s), and previous closed chunks. Writes first go to a write-ahead log on local disk (so a crash loses at most the last fsync interval), then to the head chunk.
Blocks. Every 2 hours the head is cut into an immutable block: a directory with chunk files (series data), an index and metadata. The index has: a symbol table for label strings, a posting list for each label pair (the sorted list of series ids that have this label pair, stored as compressed integers), and the series table with the chunk references. Blocks are uploaded to object storage. A compactor merges blocks into bigger ones (12 hours, then 24 hours) and deduplicates the copies from the 3 replicas.
Sharding. The distributor hashes the series (tenant id, name and labels) and places it on a ring of ingesters by consistent hashing with replication factor 3, in three zones. A query for one series contacts 3 ingesters; a query by label contacts all of them (scatter-gather).
Cold data and rollups. Block files in object storage are partitioned by tenant and time. A rollup job reads raw blocks and writes 5-minute blocks with the 4 aggregates. Query planning picks raw, 5-minute or 1-hour data depending on the range and step.
design: The write path. Agents scrape targets every 10 s, attach external labels (cluster, region), and send batches by remote write to the nearest distributor. The distributor checks the tenant's limits (series count, samples per second), hashes each series, and sends it to 3 ingesters in 3 zones. It returns success when 2 of 3 acknowledge (a quorum). Each ingester appends to its WAL and updates the head. The ingester adds the series to its inverted index in memory: label pair to a set of series ids. If the series did not exist, this is a new series and counts against the tenant limit.
The storage path. Every 2 hours each ingester writes its head to a block on local disk and uploads it to object storage. The three copies of each series are written by three ingesters, so the compactor later merges them to one copy (deduplication by series and timestamp). Local blocks stay for about 3 days, to serve the most common queries without going to the object store. After compaction, the store-gateway nodes serve older blocks from object storage using a cached copy of the index and small range reads for chunks.
The read path. A query frontend splits a long range query into day-long pieces and caches the results by (query, step, time range), so that a dashboard refreshing every 30 s asks only for the last 30 s. Each piece goes to a querier. The querier parses the expression, finds the series by looking up postings: for {service="cart", status=~"5.."} it takes the posting list for service="cart", intersects with the union of the lists for matching status values, and gets the series ids. It reads chunks from the ingesters (for the last hours) and from the store-gateways (for older blocks), merges and deduplicates the replicas, decodes the samples, and evaluates the functions (rate, sum by) in a streaming way.
Alerting. A ruler service evaluates the alert rules every 60 s against the recent data. An alert moves through pending (the condition is true, waiting for the "for" duration), firing, and resolved. Firing alerts are sent to the alert manager cluster. It groups alerts by labels (so 500 pods failing produce one page), deduplicates the notifications from several rulers, applies silences and inhibition rules (do not page for a service if its cluster is down), and routes to receivers with repeat intervals. The alert manager instances gossip with each other so that one notification is sent even if all instances get the alert.
Watching the watcher. A dead-man's-switch rule that always fires is sent to an independent service; if it stops arriving, the independent system pages the on-call. The monitoring system should run in a separate failure domain (another account or cluster) from what it watches, and its own metrics should be scraped by a second small instance.

deepdive: Compression of time series. Samples arrive at fixed intervals, so timestamps are very regular. Gorilla stores the first timestamp in full, the first delta, and then the delta of deltas: for a 10 s scrape the delta of delta is 0 in most cases, and a zero costs 1 bit. Values are encoded by XOR with the previous value: if a counter increases slowly, the XOR has many leading and trailing zero bits, and only the middle bits are stored with a short header. Many series (a gauge that does not change, a counter that is zero) cost 1 or 2 bits per sample. The paper reports an average of 1.37 bytes per sample, down from 16, and a 26 hour in-memory window served queries about 73 times faster than the previous HBase-backed store. Compression works on blocks of consecutive samples of one series, so the layout is column-like: all timestamps and values of one series together. Prometheus uses delta-of-delta timestamps and XOR values in 120-sample chunks, which is the reason a chunk holds about 2 hours at a 1-minute scrape.
Cardinality. The number of series is the product of the number of values of each label. Counter http_requests_total with service (500 values), route (50), method (4), status (10) already has 500 x 50 x 4 x 10 = 1,000,000 possible series, and with a "pod" label (2,000 values) it becomes 2 billion possible combinations, though only the used ones exist. A label such as user_id or request_id with millions of values creates a series per value and kills the system: memory for the head and the size of the index grow with series, not with samples. Defenses: a per-tenant limit on active series (reject new series beyond 2 million), a limit on labels per series and on value length, a cardinality analysis API ("top 10 metrics by series count") and cost attribution per team, relabeling rules that drop or aggregate labels at the collector, and a policy that high-cardinality data belongs in logs or traces. Approximate structures help to estimate unique counts: HyperLogLog for distinct label values, count-min sketch for top offenders.
Pull versus push, and service discovery. Pull (Prometheus) makes it easy to know whether a target is up (a failed scrape is data: the metric "up" is 0), lets you scrape from many places and keeps the target simple. It needs service discovery (Kubernetes API, Consul) and network access to every target. Push (StatsD, OpenTelemetry, Graphite) works for short-lived jobs (a batch job that lives 5 seconds) and across firewalls, but you lose the automatic up signal and can overload the collector. Many large systems use both: pull inside a cluster, push through an agent to a central store.
Rollups and the accuracy of aggregates. Averaging averages is wrong. For a rollup, keep sum and count, so the average over a long range is the sum of sums divided by the sum of counts. For counters, keep the last value and the increase, because rate over a rolled-up counter must handle resets. For latency, store histograms with fixed buckets (the sum of bucket counts across hosts is valid; the quantile is estimated from the merged buckets) and not precomputed quantiles, since the p99 of p99s means nothing. Newer histograms (native histograms in Prometheus, DDSketch and t-digest elsewhere) give better accuracy at a fixed relative error.
Availability of writes against queries. Ingestion uses replication factor 3 and a quorum of 2, so any one ingester or one zone can fail without losing writes. A read must merge results from replicas, as they may differ by a few seconds of data. During rolling restarts, the ingester flushes its head to the WAL on disk and replays it on startup (can take several minutes for 1 million series), so the rollout goes one zone at a time. A zone-aware ring makes sure the 3 copies of each series are in different zones.
Backpressure and overload. When ingesters are slow, the distributors queue and then return 5xx; agents retry with backoff and buffer on disk (a few GB per agent covers an outage of 30 to 60 minutes). Per-tenant rate limits return 429 for the offending tenant only. Queries are limited by the number of series (for example 100,000 per query), by time range and by concurrency per tenant, and a query that is too large fails fast with a clear message.
tradeoffs: Build on Prometheus-compatible open source or buy a vendor. Choose open source (Prometheus with Mimir, Thanos or VictoriaMetrics; Grafana for the dashboards) when you have more than a few million series, your team can operate it, and you want to avoid per-series pricing that grows with cardinality. Choose a vendor (Datadog, Grafana Cloud, Chronosphere) when the team is small and time to value matters, accepting the bill and possible limits on custom data. Decide with the real cost per million series per month in hand.
Single Prometheus or a sharded system. Choose a single Prometheus (with a replica pair) up to about 1 to 5 million series per server, for a team or cluster; it is simple and local. Choose a horizontally scalable backend (Mimir, Cortex, Thanos with sidecars, VictoriaMetrics cluster) when you need a global view across clusters, long retention on object storage, or more than 10 million series. You pay with more components and more cost to run.
Pull or push. Choose pull for long-lived services in a managed network, where discovery is available and you want free up/down detection. Choose push for ephemeral jobs, serverless functions, edge devices or when the metrics backend is in another network. Choose OpenTelemetry collectors in the middle when you want one pipeline for metrics, logs and traces and the freedom to change the backend.
Retention and resolution. Choose full resolution for 2 weeks when operators debug incidents with 10 s detail. Choose rollups to 5 minutes or 1 hour for capacity planning and year-over-year comparison, and drop old raw data to save 8 to 10 times the storage. Keep exact data longer only for business-critical SLO metrics, with a separate retention class.
failures: An ingester dies. The ring marks it unhealthy after missed heartbeats. Writes continue with the 2 other replicas (quorum 2 of 3). Queries read from the other two. A replacement ingester starts, replays its WAL if the disk survived, or fetches data from the other replicas, and rejoins. No data is lost, and the gap is invisible to users.
A zone fails. One of the 3 replicas of every series is gone, quorum 2 of 3 still holds, and writes and alerts keep working. The risk is a second failure while degraded, so we keep the capacity to take full load with 2 zones, which means each zone runs below 65 percent of its capacity.
Object storage is unavailable. Ingesters keep blocks locally (3 days of space), so writes and recent queries work. Older queries fail or return partial results with a warning. Uploads retry when the store returns.
Cardinality explosion. A deployment adds a request_id label. In minutes the series count grows from 50 million to 120 million. The distributor limit rejects new series for that tenant after the cap, so other tenants are protected, and the owner gets an alert with the metric name that grew the most. The operator drops the label with a relabel rule.
Alerting path failures. If the ruler or alert manager is down, alerts do not fire. Run rulers in at least two replicas with sharded rule groups, and alert manager as a cluster of 3 with gossip. The dead-man's switch from an external service catches a total failure of the path, which a normal alert cannot.
evolution: At 1,000 series, one Prometheus on a small VM, a Grafana and Alertmanager are enough, with a day of work to set up. At 1 million series, one or two Prometheus pairs per cluster with 30 days of local disk. At 50 million series, the distributed design above with object storage, rollups, per-tenant limits and sharded rulers. At 1 billion series (the scale of Google's Monarch or the largest vendors), data is kept in memory in regional zones close to the source, with a global query layer that fans out to zones, a strict push model with a hierarchy of collectors, exact-versus-approximate trade-offs for aggregates, and automated cardinality governance. At that point, cost per series, not performance, drives most decisions.
followups: How do you store 5 million samples per second cheaply? || Append to an in-memory head and a write-ahead log, compress each series with delta-of-delta timestamps and XOR values (about 1.4 bytes per sample), cut immutable 2-hour blocks, and move them to object storage with rollups for old data. All writes are sequential, and no sample is updated in place.
What is cardinality and why does it break time-series databases? || The number of distinct label combinations is the number of series. Memory, index size and query cost grow with series, not with samples. A label such as user id turns one metric into millions of series. Limit series per tenant, review labels, and push high-cardinality data to logs or traces.
Pull or push for metrics collection? || Pull gives a free health signal (a failed scrape), central control of the interval and simple targets, but needs discovery and network access. Push suits short-lived jobs and firewalled sources but needs protection against overload and loses the automatic up signal. Large systems use both.
How do you make the alerting path more reliable than the system it watches? || Run it in a separate failure domain, replicate the rulers and the alert manager with gossip, use a quorum write path, keep rules simple, and add an external dead-man's switch that pages when the always-firing heartbeat alert stops arriving.
How do you compute a p99 over many hosts? || Do not average p99 values. Export histograms with shared bucket boundaries, sum the bucket counters across hosts, and estimate the quantile from the merged buckets, or use mergeable sketches such as DDSketch or t-digest. The accuracy depends on the bucket layout.
How do you query one year of data fast? || Use rollups (5-minute or 1-hour aggregates with min, max, sum, count), let the planner choose the resolution by range and step, split the query by time and cache the pieces in a query frontend, and parallelize over blocks. Raw data is not scanned.
What happens when you reorganize pods and create churn? || Each new pod name creates new series and the index grows, slowing long-range queries even if the active number stays constant. Use stable labels, aggregate away the pod label in recording rules, and set block and retention policies that expire old series.

@@ sso-gateway
title: Design an API gateway with single sign-on
category: Infrastructure
level: Senior / Staff
concepts: apigateway, oauth, identity, security, websec, cookies, mtls, tls, pkcrypto, signatures, hashfn, envoy, servicemesh, ratelimit, circuitbreaker, cachelayer, redis, loadbalancing, microservices, observability, http
summary: An API gateway is the single door to dozens of backend services: it terminates TLS, finds the route, checks who the caller is and what they may do, limits their rate, and forwards the call. Single sign-on (SSO) means a person logs in once at a central identity provider and then uses many applications without logging in again. Together, they must authenticate millions of users at tens of thousands of requests per second with a few milliseconds of overhead, never let a request skip a check, survive an outage of the identity provider for users who already have a session, and make logout and revocation really work. The hard parts are token design (what the browser holds and what the services see), validation without a network call, revocation, and the security details of the redirects.
requirements: Functional requirements. Browser users and mobile apps log in through an OpenID Connect (OIDC) flow with a central identity provider (IdP); enterprise customers can bring their own IdP by SAML or OIDC. After login the user reaches any application behind the gateway without another prompt. Machine clients use API keys or OAuth client credentials. The gateway routes by host and path, authenticates, authorizes by role and scope, rate limits, adds headers for the backend (user id, tenant, roles), and logs every decision. Multi-factor authentication (MFA) and step-up for sensitive actions. Logout from one app ends the session everywhere.
Non-functional requirements. Overhead: under 5 ms at p99 for an authenticated request that needs no IdP call. Scale: 100,000 requests per second at peak. Availability: 99.99 percent for the gateway; a short IdP outage must not log out active users. Security: no token in URLs or in browser storage that scripts can read; protection against CSRF, open redirects, token replay and code interception; keys rotated without downtime. Revocation: a disabled employee loses access within 5 minutes. Auditability: every login, token issue and denial is logged.
Assumptions. 20 million registered users, 5 million active per day, 3 million interactive logins per day with a peak of 3 times the average rate in the morning hour. Access tokens live 10 minutes, refresh tokens 30 days with rotation, the IdP session 8 hours with a 1 hour idle limit.
estimates: Login rate. 3 million logins per day divided by 86,400 = 35 per second on average. Logins cluster in the morning: if 40 percent happen in one hour, that is 1.2 million / 3,600 = 333 per second, and a burst of 3 times that for a few minutes gives about 1,000 per second. We design for 1,000 interactive logins per second.
Password hashing cost. A login checks the password with a slow hash such as Argon2id, tuned to about 50 ms of CPU and 19 MiB of memory per hash (the OWASP minimum setting is 19 MiB, 2 iterations, 1 degree of parallelism). 1,000 logins per second times 0.05 s = 50 cores busy on hashing. With 16-core servers, 4 servers at full load, and we plan 8 for headroom. Memory: 1,000 concurrent x 19 MiB = 19 GB peak, spread over the 8 servers. This is why login is the expensive path, and why we protect it with rate limits per account and per IP.
Token operations. Each login issues an ID token, an access token and a refresh token. Signing a JWT with RSA-2048 costs about 1 ms, with ECDSA P-256 about 0.1 ms. 1,000 logins per second times 2 signatures = 2,000 ms of CPU per second, 2 cores. Refresh: access tokens last 10 minutes, so 5 million active users refresh about 6 times per hour of use. With 1 million users online at a time, that is 1,000,000 x 6 / 3,600 = 1,667 refreshes per second, each costing one signature and a database lookup. This is small.
Validation cost. Verifying an RS256 signature costs about 30 to 50 microseconds, an ES256 verification about 100 to 150 microseconds. At 100,000 requests per second with 50 microseconds each: 5 CPU cores in total. Local validation is cheap. A call to the IdP to introspect each token would need 100,000 calls per second at about 1 ms each, and make the IdP a bottleneck and a single point of failure. So the gateway validates locally.
Sessions. For the browser path the gateway keeps a server-side session (the BFF pattern, "backend for frontend"). One million concurrent sessions times about 2 KB (session id, user id, access token, refresh token, expiry times) = 2 GB, in a Redis cluster, with 3 replicas it is 6 GB. Reads: every browser request does one lookup at 0.3 to 0.5 ms; 100,000 per second is within the capacity of 3 Redis shards (about 50,000 to 100,000 simple reads per second each).
api: Browser flow endpoints on the gateway: GET /auth/login?return_to=/app redirects to the IdP. GET /auth/callback?code=...&state=... completes the login and sets the session cookie. POST /auth/logout ends the session. GET /auth/me returns the user profile for the single-page application.
IdP endpoints (OIDC): GET /authorize with response_type=code, client_id, redirect_uri, scope="openid profile", state, nonce, code_challenge and code_challenge_method=S256 (PKCE). POST /token exchanges a code (with code_verifier) for tokens, or a refresh token for new tokens. GET /.well-known/openid-configuration publishes the endpoints and the JWKS address. GET /jwks returns the public keys. POST /revoke revokes a refresh token. GET /logout is the RP-initiated logout.
Back-channel logout: the IdP sends POST /auth/backchannel-logout with a signed logout_token to every app that took part in the session. The gateway deletes the matching sessions.
Machine access: POST /token with grant_type=client_credentials and client authentication by secret, private key JWT or mTLS. The call returns an access token with scopes.
Headers to backends: X-User-Id, X-Tenant-Id, X-Roles and a short-lived internal JWT signed by the gateway (audience = the service, lifetime 60 seconds), so that services trust a signature and not a header.
datamodel: User and credential store (IdP): users(id, tenant_id, email, status, created_at), credentials(user_id, type [password, passkey, totp], hash, params), federated_identities(user_id, provider, subject). Passwords are stored as Argon2id hashes with per-user salt. Sessions at the IdP: idp_sessions(id, user_id, auth_time, amr [methods used], expires_at, last_seen).
Gateway session (Redis): key "sess:{random 256-bit id}" with fields user_id, tenant, roles hash, access_token, refresh_token, access_exp, idle_exp, abs_exp, idp_sid (the IdP session id, for back-channel logout), csrf_token. A second key "idp_sid:{sid}" lists session ids for that IdP session. Redis TTL equals the absolute expiry.
Token content. Access token (JWT, signed with ES256): header {alg, kid}, claims {iss, sub, aud, exp (now + 600 s), iat, jti, scope, tenant, roles}. Short and small (under 1 KB), since it is sent on each request. The ID token has the user claims {sub, name, email, nonce, auth_time, amr} and is only for the client, never sent to APIs.
Policy store: routes(host, path_prefix, upstream, auth_mode [none, session, jwt, apikey], required_scopes, rate_limit_rule); authz policies in a policy language (for example Rego for Open Policy Agent, or Cedar) bundled and pushed to gateways. API keys: api_keys(key_prefix, hash of key, client_id, scopes, expires_at); only a hash of the key is stored, and lookups use the visible prefix.
Audit log: append-only events (time, actor, action, result, ip, user agent, request id) to a log stream, then a warehouse.
design: Request path for a browser user. The browser requests https://app.example.com/orders. The load balancer terminates TLS and passes the request to a gateway instance. The gateway finds the route, sees auth_mode = session, reads the session cookie (HttpOnly, Secure, SameSite=Lax, prefix __Host-), and looks up the session in Redis. If the access token in the session expires in less than a minute, the gateway refreshes it at the IdP first (one refresh per session at a time, using a lock). It then runs authorization (role and scope against the route policy), checks the rate limit for the user, and adds the identity headers and an internal JWT. The request goes to the upstream service by mTLS. The response goes back through the gateway, which adds security headers (HSTS, CSP) and logs the result.
Login path. If there is no valid session, the gateway starts the authorization code flow with PKCE: it creates random state, nonce and a code_verifier, stores them in a short-lived pre-login record bound to a cookie, and redirects the browser to the IdP /authorize. The IdP has its own session cookie. If the user already logged in to another application, the IdP does not ask for credentials and redirects back immediately with a code: this is the single sign-on. Otherwise the IdP shows the login page, checks the password or passkey, runs MFA and then redirects back. At /auth/callback the gateway checks the state, exchanges the code (with the verifier) over a back channel for tokens, validates the ID token (signature, iss, aud, exp, nonce), creates the session, sets the cookie and redirects to the original page. The browser never sees the tokens.
API path for tokens (mobile apps and machines). The client sends Authorization: Bearer <JWT>. The gateway checks the signature using the cached JWKS key with the right kid, then iss, aud, exp (with 30 seconds of leeway) and scope, and the jti against the local deny list. It needs no network call. Opaque tokens are possible too, but then each check goes to the IdP or a cache.
Authorization. Authentication says who; authorization says what. The gateway does coarse checks (is this scope allowed on this route, is the tenant right). Fine checks (can this user see this order) belong to the service, because only the service knows the data. Policies as code are pushed to gateways and evaluated in-process in microseconds. Defaults deny.
Identity propagation. Backends should not trust a plain header from the network. The gateway signs a new short-lived internal token for the exact audience, and services verify it or rely on mTLS identities from the service mesh (SPIFFE ids). Downstream calls between services pass the same token or exchange it (OAuth token exchange, RFC 8693) for a token with less scope.
Rate limiting and protection. The gateway applies the limits described in the rate limiter design: per user, per API key, per IP, and a strict limit on /auth/* and on login attempts per account to slow down password guessing. It also enforces request size limits, timeouts and a WAF.

deepdive: Why the authorization code flow with PKCE. The older implicit flow returned tokens in the URL fragment, where browser history, extensions and referrer headers could leak them. The code flow returns a short-lived, one-time code, and the token request happens on a back channel. PKCE (RFC 7636) protects the code: the client invents a random code_verifier, sends only its SHA-256 hash (the code_challenge) at the start, and sends the verifier when exchanging. An attacker who steals the code from a redirect (for example on a phone with a malicious app registered for the same URL scheme) cannot exchange it without the verifier. The state parameter binds the response to the browser that started the flow and defeats login CSRF; the nonce in the ID token defeats replay of an ID token. The redirect URI must match a registered value exactly, or an open redirect leaks codes. Current security guidance (RFC 9700) asks for PKCE in all clients and exact redirect matching.
Where tokens live. Putting an access token in browser local storage exposes it to any script that runs on the page (cross-site scripting), and a stolen token works from anywhere until it expires. The BFF pattern keeps tokens on the server and gives the browser a session cookie that is HttpOnly (not readable by scripts), Secure, and SameSite=Lax or Strict (not sent from other sites in most cases). A cookie-based session needs CSRF protection for state-changing requests: a double-submit or synchronizer token, and checking the Origin header. Native apps and machine clients hold tokens themselves, so use short lifetimes, refresh rotation, and where possible sender-constrained tokens (DPoP, RFC 9449, or mTLS-bound tokens) which cannot be replayed from another machine.
Validation without a network call, and the revocation problem. A signed JWT is valid until exp, anywhere, with no database. That is why it scales, and also why it cannot be revoked. We accept that for 10 minutes, and add three tools. (1) Short lifetime plus refresh, so the IdP decides every 10 minutes if the user is still allowed; disabling a user kills the refresh token and the next refresh fails. (2) A small deny list of jti or user ids (about 70 entries for our numbers) pushed to all gateways within seconds by a pub-sub channel, for emergencies such as a stolen laptop. (3) For high-risk operations (change password, move money) require a fresh authentication (auth_time recent) or step-up MFA, and call the IdP for introspection. The server-side session in the BFF path is easier: delete the key in Redis and the user is out at once.
Refresh token rotation and reuse detection. On each refresh the IdP issues a new refresh token and invalidates the old. If the old token appears again, someone has a copy (the thief or the real user), so the IdP revokes the whole token family and forces a new login. Rotation needs care with concurrent refreshes from two tabs; the gateway serializes refresh per session with a lock so that only one refresh runs. A short grace window (a few seconds) for the old token handles retries after a network error.
Key management and rotation. The IdP signs with a private key kept in an HSM or a key management service. The public keys appear in the JWKS with a kid. Rotation: publish the new key in the JWKS first, wait until all gateways have refreshed their caches (at least the cache TTL, 5 to 10 minutes), start signing with the new key, and remove the old key only after the longest token lifetime (10 minutes plus skew) has passed. A gateway that sees an unknown kid should refetch the JWKS once, with a rate limit to avoid being used for a denial of service. Never accept alg=none or switch algorithms based on the token header: pin the algorithm per issuer (the classic JWT confusion attack).
Single logout. Each application has its own session, so logout must reach all of them. Back-channel logout (OIDC Back-Channel Logout) has the IdP call each application with a signed logout token that contains the IdP session id; the gateway finds sessions with that sid and deletes them. Front-channel logout loads hidden iframes in the browser, which fails when third-party cookies are blocked. Logout is best effort for apps that were offline; the short access token lifetime limits how long they stay valid. Always make logout a POST with CSRF protection, or a bad site can log users out.
tradeoffs: Sessions or JWTs for browsers. Choose server-side sessions (BFF with an opaque cookie) for browser applications you control: tokens are not exposed to scripts, logout and revocation are immediate, and the cost is a Redis lookup of 0.5 ms per request. Choose bearer JWTs in the browser only for pure single-page apps with no backend of their own, accepting the risk of token theft and weak revocation, and mitigate with short lifetimes and refresh rotation.
Local JWT validation or introspection. Choose local validation for access tokens on the hot path: no dependency on the IdP and microseconds of CPU. Choose introspection (RFC 7662) or opaque tokens when you need immediate revocation and can pay a call per request, which you can reduce by caching positive answers for 10 to 60 seconds. Many systems use JWT for most routes and introspection for a short list of sensitive ones.
Where to enforce authentication: gateway, mesh or service. Choose the gateway for external traffic: one place for TLS, authentication, rate limiting and audit. Choose the service mesh with mTLS for service-to-service identity inside the cluster. Choose in-service checks for data-level authorization. Doing only the gateway makes every service trust the network; doing it only in services duplicates security code in every language. Use all three for different questions.
Build or buy the IdP. Choose a managed IdP (Okta, Auth0, Microsoft Entra ID, Cognito) or an open-source server (Keycloak, Ory) rather than building: password storage, MFA, account recovery, brute-force defense and standards details take years to get right. Build your own only if identity is your product. You give up some flexibility and pay per user in the managed case, or operate a critical stateful service in the open-source case.
failures: The IdP is down. Users with a gateway session keep working until their access token expires; the gateway cannot refresh, so extend the effective session by allowing a refresh to fail open for up to 30 minutes for low-risk routes, or serve with an already issued token until its refresh window ends. New logins fail. The IdP runs in 3 zones with a replicated database, and the login page degrades with a clear message. Keys and JWKS are served from a CDN, so validation continues even if the IdP is down.
Redis (session store) fails. A failover to a replica takes seconds; sessions written in the last second may be lost, so a few users see a login prompt (and immediately get an SSO redirect, since the IdP session still exists). If the whole cluster is lost, all users re-authenticate through SSO without typing a password, which creates a login burst of up to 1 million redirects; the IdP and the gateway must handle it, so rate limit and queue.
Key compromise or wrong rotation. If a signing key leaks, remove it from the JWKS at once and issue a new one; all tokens signed by it become invalid within the gateway cache TTL, and all users refresh. If rotation removes a key too early, valid tokens fail with 401 for everyone: always publish before use and remove after expiry, and alert on a spike of invalid signature errors.
Gateway overload or bad route config. A wrong route or policy bundle can open or close access for everyone. Config is validated and rolled out gradually with a canary, policies default to deny, and the previous version is kept for instant rollback. Timeouts, circuit breakers and connection limits per upstream keep one slow service from consuming all the gateway's workers.
Credential stuffing and brute force. Attackers try leaked passwords against /login at thousands per second. Defenses: per-account and per-IP rate limits, breached-password checks, MFA and passkeys, bot detection, and the cost of Argon2id itself, which makes each guess cost 50 ms of CPU for us too, so the limit protects our servers.
evolution: At 1,000 users, use a library or a managed service with a few lines of middleware in the app, and cookie sessions. At 1 million users, put an API gateway or reverse proxy in front, use a hosted IdP with OIDC, and validate JWTs at the gateway. At 100 million users, run a dedicated identity platform with multi-region IdP, a Redis session layer, JWKS on a CDN, policy as code and a service mesh with mTLS. At 1 billion users, shard the user database by region, move to passkeys and risk-based authentication, sender-constrained tokens, and a continuous access evaluation protocol so that revocation events push to gateways in seconds.
followups: Why do you use the authorization code flow with PKCE for a single-page app? || Tokens must not travel in the URL, and a stolen code must be useless. The code flow gives a one-time code over the front channel and tokens over a back channel. PKCE binds the code to the client that started the flow by a hash challenge and a secret verifier, so an interceptor cannot redeem it. State and nonce add protection against CSRF and replay.
How does the gateway validate a JWT without calling the IdP? || It takes the kid from the header, uses the cached public key from the JWKS, verifies the signature with a pinned algorithm, then checks issuer, audience, expiry and scopes. That costs about 50 microseconds of CPU. The trade-off is that revocation is limited by the token lifetime, so tokens are short and a deny list covers emergencies.
How do you revoke access for a user who was just fired? || Disable the account at the IdP, which revokes refresh tokens and sessions and sends back-channel logout to applications; push the user id to the gateway deny list for the remaining life of access tokens (10 minutes); delete the gateway sessions in Redis. Sensitive routes use introspection or require recent authentication.
Where should tokens be stored for a browser app? || Not in local storage, which scripts can read. Keep them on the server in a session and give the browser an HttpOnly, Secure, SameSite cookie (the BFF pattern), with CSRF protection for writes. Native and machine clients keep tokens in secure storage with short lifetimes and, if possible, sender-constrained tokens.
How does single logout work and what are its limits? || The IdP sends a signed back-channel logout token with the session id to each relying party, which deletes the matching sessions. It works for applications that are reachable and implement it; for others, short access token lifetimes limit the exposure. Front-channel logout depends on cookies in iframes and often fails.
How do services behind the gateway know who the caller is? || The gateway verifies the external credential and creates a short-lived internal JWT for the target service, and mTLS (for example SPIFFE identities from a mesh) authenticates the gateway itself. Services verify the signature and audience and do not trust plain headers. For calls to other services they use token exchange with reduced scope.
What happens when you rotate the signing keys? || Publish the new public key in the JWKS first and let gateway caches refresh, then start signing with it, and keep the old key published until all tokens signed by it have expired. Gateways refetch the JWKS once on an unknown kid. Removing keys early causes a global 401 storm.

title: Design an email service like Gmail
category: Web & product
level: Senior / Staff
concepts: dns, sockets, tcp, tls, signatures, pkcrypto, mqueue, retries, idempotence, ratelimit, partitioning, replication, s3, erasurecoding, invindex, postings, searchengine, bloom, ml, nlp, backpressure, circuitbreaker, pubsub, commitlog
summary: An email service accepts mail from the whole internet over SMTP, decides what is spam, stores each message safely for years, shows the mailbox quickly, searches it, and sends mail out to other providers who may refuse it. Email is a federated protocol from 1982 with no central authority and no strong sender identity, so most of the design is defense and reliability: authentication checks (SPF, DKIM, DMARC), spam filtering, retries for days, and the rule that once you accept a message you own it. The hard parts are the volume of small writes, per-user consistent mailbox state, search over a lifetime of mail, and reputation for outgoing servers.
requirements: Functional requirements. Receive mail for our domains on SMTP port 25. Send mail from users, by web, mobile apps or SMTP submission (port 587). Show a mailbox: labels or folders, conversations (threads), unread counts, flags (read, starred). Full-text search with operators (from:, has:attachment, date range). Attachments up to 25 MB (bigger ones become links). Spam and phishing filtering with a spam folder. Access by IMAP and a web API; push notification when new mail arrives. Delete, archive, undo send, forwarding rules, and export.
Non-functional requirements. Durability: never lose an accepted message (target eleven nines, like an object store). Availability: 99.99 percent for reading and receiving; if our servers are down, senders retry for days, so short outages do not lose mail. Latency: a new message appears in the inbox within 5 seconds of SMTP acceptance; opening the inbox in under 300 ms; search in under 1 s. Safety: more than 99.9 percent of spam is stopped; a legitimate message is almost never filtered out. Privacy: encryption in transit and at rest, strict access control, deletion that is final.
Assumptions. 100 million users. Each receives about 40 messages per day that are accepted and stored (after rejecting most spam at the connection stage). Average stored message 50 KB. 3 messages sent per user per day. Peak is 2 times the average. Each user opens the mailbox 20 times per day.
estimates: Inbound. 100 million users times 40 messages = 4 billion stored messages per day. Per second: 4e9 / 86,400 = 46,300 on average, 93,000 at peak. Messages that are attempted but rejected before storing are many more, maybe 3 times as many, so the SMTP edge sees about 4 times 46,300 = 185,000 attempts per second on average, 370,000 at peak.
Outbound. 100 million times 3 = 300 million per day, 3,500 per second on average (7,000 at peak), and each message may go to several recipients (average 2), so about 7,000 deliveries per second on average (14,000 at peak) to other providers.
Storage. 4 billion messages times 50 KB = 200 TB per day. For a year: 73 PB. With 6+3 erasure coding (1.5 times), 110 PB raw per year of growth. Many attachments are duplicates (the same file forwarded or sent to many), so content-addressed storage saves maybe 20 percent, but we do not count on it. Mail is kept for years, so after 5 years the store holds about 400 PB logical.
Metadata. Per message: ids, thread id, labels, flags, size, date, sender, subject and a 200-byte snippet: about 600 bytes. 4e9 times 600 bytes = 2.4 TB per day, 876 TB per year. It must sit on SSD with replication factor 3: 2.6 PB per year of SSD growth. Sharded by user: 100 million users into 10,000 shards of 10,000 users each; a shard holds 10,000 users x (365 x 40 x 600 bytes = 8.8 MB per user per year) = 88 GB per year per shard. Fine for one replicated database node set.
Search index. A message has about 10 KB of indexable text (the rest is attachments and markup). The index costs about 20 percent of the text: 2 KB per message. 4e9 times 2 KB = 8 TB per day, 2.9 PB per year. The index is also per user, in the same shard.
Reads. 100 million times 20 opens = 2 billion mailbox loads per day = 23,000 per second on average, 70,000 at peak (mornings). Each load reads a list of 50 conversations: one range read of 50 x 600 bytes = 30 KB from the metadata store.
Bandwidth. Inbound: 46,300 per second times 50 KB = 2.3 GB/s (18 Gbit/s) on average, 4.6 GB/s at peak (37 Gbit/s). Spread over 250 edge servers this is under 0.2 Gbit/s each, which is easy.
SMTP edge capacity. A well-tuned SMTP server handles about 2,000 to 5,000 messages per second if the content scan is cheap; with spam scanning the cost is 5 to 20 ms of CPU per message. 370,000 attempts per second times 5 ms (rejects at the cheaper stage, 20 ms for those that get to content scan, assume an average of 8 ms) = 2,960 cores. About 200 servers with 16 cores at 80 percent load, 250 with headroom.
api: SMTP inbound (RFC 5321): EHLO, STARTTLS, MAIL FROM:<sender>, RCPT TO:<user@our.domain>, DATA ... then the final answer 250 (accepted), 4xx (try again later) or 5xx (permanent refusal). The server replies after each step, so it can refuse early.
Submission: SMTP on port 587 with authentication (AUTH) and TLS, or POST /v1/messages:send with a JSON or raw RFC 5322 message. Returns {message_id, thread_id}. A delay of 10 to 30 seconds before real sending allows "undo send".
Mailbox API (web and apps): GET /v1/threads?label=INBOX&limit=50&page_token=T returns thread summaries. GET /v1/messages/{id} returns headers and body. POST /v1/messages/{id}:modify {add_labels, remove_labels} changes flags and labels. DELETE /v1/messages/{id} moves to trash; a purge job deletes after 30 days.
Sync: GET /v1/history?start_history_id=H returns the changes (new, changed, deleted messages) after sequence number H, so a client updates incrementally. IMAP offers the same with UID, MODSEQ and IDLE. A push channel (WebSocket or mobile push) tells the client that something changed.
Search: GET /v1/search?q=from:ana has:attachment after:2026/01/01&limit=25.
datamodel: Everything about one user lives in one shard, with the user id as the partition key. Tables: messages(user_id, message_id, thread_id, internal_date, size, label_ids, flags, headers_summary, snippet, blob_ref, history_id). Primary key (user_id, message_id), with a secondary index (user_id, label, internal_date desc) to list a label newest first. threads(user_id, thread_id, last_date, message_ids, labels). labels(user_id, label_id, name, counts). history(user_id, history_id, change type, message_id): an append-only changelog with a counter per user. Counters(user_id, label, unread).
Message body and attachments are not in the metadata store. The raw message (RFC 5322 text with MIME parts) is stored once as a blob in the object store, with the key being a hash of the content: "blob/{sha256}". Attachments are extracted and stored as separate blobs, deduplicated by hash. The blob store uses erasure coding. The metadata row points to it by blob_ref.
Search index per user: inverted index terms to message ids, stored as small immutable segments (like Lucene segments) in the same shard, merged in the background. Fields: from, to, subject, body, labels, date, has_attachment. Attachment text (PDF, Office files) is extracted in a background job.
Mail queue (outbound): queue(destination domain, next_attempt_at, message_id, recipients, attempts, last_error) in a durable queue, partitioned by destination domain so that we can apply per-domain rate limits and backoff.
Reputation and rules: ip_reputation(ip, score, last_seen), sender_domain_policies(domain, spf/dkim/dmarc results cache), user filters (rules the user set) as a small document per user.
design: Receiving. Mail for our domains reaches us because DNS MX records of our domain list our SMTP edge servers. A sending server connects (TCP, port 25), says EHLO and offers STARTTLS. Before reading the message, our edge checks the client: IP reputation, reverse DNS, rate per IP, and whether the RCPT address exists (refuse unknown users at once with 550, so we never accept mail we cannot deliver). After DATA, the edge checks authentication: SPF (is the IP allowed to send for the envelope domain?), DKIM (does the signature in the header verify with the public key published in DNS?), and DMARC (does the From domain align with SPF or DKIM, and what does its policy say: none, quarantine, reject?). Then spam and malware filters run: fast rules and blocklists first, then machine-learning classifiers on content, links and sender behavior, then scanning of attachments. The decision is accept to inbox, accept to spam folder, or reject with 5xx. Rejection during the SMTP session is important: if we accept first and bounce later, the bounce goes to a forged sender and becomes backscatter spam.
Accept means durable. The edge writes the raw message to the blob store and a delivery record to a durable queue (replicated log), and only then answers 250. After 250, the message is our responsibility; the sender will delete its copy. If the edge fails before 250, the sender retries and we may get a duplicate, which we remove by Message-ID and content hash per user. Delivery workers read the queue, expand aliases and forwarding, apply the user's filters, and for each recipient send a command to the user's shard.
Mailbox shard. The shard leader for the user inserts the message row, updates thread, label counts, and appends to the history log in one transaction, which assigns the next history id. The shard replicates synchronously to a replica in another zone (or via Paxos/Raft) before acknowledging. Then an event goes to the notification service (to push to the user's open sessions) and to the indexer (to add the message to the search index). The message is visible in the inbox as soon as the transaction commits; search catches up a few seconds later.
Reading. The client asks for the inbox. The request goes to the user's shard (found by a directory service or by hashing the user id), which returns one range of rows with the label index, plus the unread counters. A cache of the first page per active user (a few KB) cuts the load. Opening a message fetches the body from the blob store (or a cache) by its hash and renders it in a sandbox (remote images are proxied, scripts removed). Clients with a history id ask for changes since that id, which is a cheap range read on the history log.
Sending. The user presses send. The web app calls the send API, which stores the message in Sent (a normal delivery to the user's own mailbox) and enqueues one delivery per recipient domain. After the undo window, the outbound MTA signs the message with DKIM (using a private key per domain), looks up the MX records, picks a source IP from a pool with good reputation, opens a TLS connection and sends. A 2xx answer ends the task. A 4xx answer (greylisting, mailbox full, rate limit) schedules a retry. A 5xx answer creates a bounce message (DSN) to the sender. Messages that stay undelivered for 5 days produce a final bounce.
Search. A query goes to the user's shard. The indexer searches the user's index segments, which are small (an average user has 20,000 messages and 40 MB of index), ranks by date and relevance, and returns ids. The metadata is joined from the same shard. Because the index is per user, queries never scan other users' data and are isolated by design.

deepdive: Authentication of senders. SMTP has no sender identity; the "From:" header can be anything. Three layers add it. SPF (RFC 7208) is a DNS record that lists IPs allowed to send mail for a domain; the receiver checks the connecting IP against the envelope sender's domain. SPF breaks on forwarding. DKIM (RFC 6376) lets the sender sign selected headers and the body with a private key; the public key is a DNS TXT record at selector._domainkey.domain. A valid signature proves the domain that signed and that the content was not changed, and survives forwarding unless the message is modified. DMARC (RFC 7489) ties them to the visible From domain: at least one of SPF or DKIM must pass and be aligned with the From domain, and the domain owner's policy says what to do on failure (none, quarantine, reject) and where to send reports. ARC lets intermediaries such as mailing lists vouch for the earlier results. Since February 2024, Gmail and Yahoo require senders of bulk mail (over 5,000 messages per day to their users) to have SPF, DKIM and DMARC, one-click unsubscribe, and a user-reported spam rate below 0.3 percent.
Spam filtering at scale. Layers run from cheap to costly, so most spam dies early. (1) Connection: IP and ASN reputation, rate limits, blocklists, greylisting for unknown senders. (2) Envelope and headers: invalid recipients, forged identity, authentication failures. (3) Content: rules, URL reputation, near-duplicate fingerprints (many spam messages are variants of one template, so a fuzzy hash catches them), and ML classifiers trained on user "report spam" signals and on mail that users move out of spam. (4) Behavior: a sudden sender sending 10,000 messages at once to new recipients. The cost of errors is not equal: a false positive (real mail in spam) is worse than a false negative. Feedback from users is the best training data, and attackers adapt, so models retrain daily.
Per-user consistency and the history log. A mailbox must look consistent: if I mark a message read on my phone, my laptop must see it, and counts must be right. We make each user's shard the only writer for that user's data. Every change gets the next history id inside the same transaction. A client keeps the last history id it has seen and asks for everything after it. If the log was truncated (too old), the client does a full resync. This is the same idea as the Kafka offset: an ordered log per user that clients replay. IMAP has UIDVALIDITY, UID and MODSEQ for the same purpose; JMAP (RFC 8620) is a modern JSON protocol with state strings. The single-writer rule avoids distributed transactions, because no operation touches two users... except sending to many local recipients, which is just independent deliveries done by a queue with idempotent shard writes keyed by (user, message id).
Idempotent delivery. The queue gives at-least-once. A delivery worker may crash after the shard commit and before the queue ack. The retry sends the same (user, message id, internal id) and the shard sees the row already exists and returns success. Without this, users get duplicates. The key is the SMTP-level id we generate at acceptance, not the Message-ID header (senders reuse or omit it).
Outbound deliverability and reputation. Big providers rate-limit unknown senders. Our outbound IPs need a good reputation: warm up new IPs slowly (hundreds per day up to millions over weeks), separate pools for user mail, bulk mail and risky accounts, so that a compromised account does not hurt everyone, keep complaint rates low, process bounces fast (remove addresses after a hard bounce), register for feedback loops, and publish DMARC, reverse DNS and MTA-STS. Per-destination queues with connection pooling avoid opening 1,000 connections to one provider: a typical limit is 10 to 50 parallel connections and a message rate that adapts to 4xx responses (backoff with jitter, doubling up to 1 hour or so).
Search at scale and privacy. A per-user index avoids global ranking problems and keeps deletes simple: deleting an account deletes its shard. Index updates are asynchronous from the commit; a user searching for a message that arrived 2 seconds ago may miss it, and the UI can merge the latest messages from the metadata store. Deleted messages must disappear from the index and blob store: blobs are reference counted by user, and purge jobs delete blobs when no reference remains. Encryption at rest uses per-user data keys wrapped by a key management service, so deleting the key makes the data unreadable ("crypto-shredding").
tradeoffs: Per-user sharding or global tables. Choose per-user sharding (all of a user's mail in one replicated partition) because every operation is about one user, it gives single-writer consistency without distributed transactions, and it makes isolation, export and deletion simple. You give up cross-user queries (an admin search across a company needs a separate pipeline), and a very large or very active mailbox can be a hot shard, which needs splitting by label or time inside the user's range.
Store messages as blobs or in the database. Choose an object store plus metadata rows because bodies are large (50 KB), immutable and written once, and the metadata is small and read often. Choose a database only for tiny deployments, where one PostgreSQL holds everything and Dovecot-style Maildir or mdbox files on a filesystem are enough up to thousands of users.
Accept then filter, or filter during SMTP. Choose to filter during the SMTP session whenever you can, so rejections are 5xx answers to the sender and no bounce is generated. Choose to accept and quarantine when the verdict is uncertain and a false rejection would lose real mail: put it in the spam folder where the user can still see it. The two can be combined by threshold: reject above a very high score, quarantine in the middle.
failures: SMTP edge server fails. The sender's connection drops before 250. The sender retries (RFC 5321 says to retry for 4 to 5 days), and DNS MX priorities send it to another server. No mail is lost, and a duplicate can appear if the failure happened between our write and the 250; we remove it by content hash.
Shard primary fails. The shard promotes the synchronous replica in another zone within seconds. During that time, deliveries to those 10,000 users stay in the queue and reads for them fail or serve stale cached data. No acknowledged message is lost because replication was synchronous.
Zone or region failure. With three zones, shards, queues and blobs survive a zone loss. For a region loss, a second region holds asynchronous replicas of shards (a few seconds behind) and a copy of blobs; failover accepts the loss of the last seconds of metadata, but the blob and queue records let us redeliver and repair. Senders also retry during the outage because MX has a backup site.
Spam flood or attack. A campaign sends 5 million messages per minute to our users. Edge rate limits per IP and ASN, early rejection, and shedding of unauthenticated mail under load keep legitimate traffic flowing. We prefer 4xx (try later) to 5xx when overloaded, since real senders retry, and spam often does not.
Account compromise. A stolen password is used to send phishing to the contacts. Detect by rate and by content similarity, hold messages, and move the account to a quarantined sending pool so that shared IPs keep their reputation. Notify the user and require a password reset.
evolution: At 1,000 users, one server running Postfix, Dovecot and Rspamd is enough, with Maildir on RAID, backups and good DNS records. At 1 million users, a few SMTP servers, a database for metadata, an object store for bodies, Elasticsearch or a similar engine for search, and a managed anti-spam layer. At 100 million users, the sharded design above, with 10,000 user shards, queues, ML spam filtering, and separate outbound IP pools. At 1 billion users, multiple regions with users pinned to a home region, cross-region replicas, automatic shard splitting and rebalancing, a global abuse intelligence system, and tiering of old mail to cheaper storage with lazy index loading for inactive users.
followups: Why does SMTP have no strong sender identity, and how do SPF, DKIM and DMARC fix it? || SMTP trusts the sender to claim the From address. SPF checks the sending IP against a DNS list for the envelope domain, DKIM verifies a cryptographic signature with a public key from DNS, and DMARC requires alignment of one of them with the visible From domain and publishes a policy and reports. Together they stop most simple spoofing.
When do you answer 250, and what does it promise? || Only after the message is durably stored in the blob store and the delivery queue is replicated. After 250 the sender deletes its copy, so we own the delivery. If we crash before it, the sender retries.
Why reject during the SMTP session instead of bouncing later? || A later bounce goes to the forged "From" address, which is usually an innocent third party (backscatter). A 5xx during the session is returned to the connecting server, which is the real source, and costs us nothing more.
How do you keep a mailbox consistent across devices? || One writer per user (the shard leader) and an ordered history log with a sequence number per change. Clients remember the last number and fetch changes after it. If the log is truncated, they do a full sync. IMAP uses UID and MODSEQ; JMAP uses state strings.
How do you make search fast for a user with 10 years of mail? || A per-user inverted index of immutable segments, merged in the background, with fields and filters for date and labels, plus recency-first ordering. Each query touches only that user's data. Inactive users' segments are on cheap storage and loaded on demand.
What causes duplicate messages and how do you prevent them? || Sender retries after a lost 250, queue redelivery after a worker crash, and client double submit. Use an acceptance id, a unique key (user, message id) in the shard so the delivery is idempotent, and a content hash plus Message-ID check for sender-level duplicates.
How do you protect the reputation of your outbound IPs? || Separate pools for trusted users, bulk and suspicious accounts, slow warm-up of new IPs, per-recipient-domain rate limits and backoff, rapid bounce handling, outbound spam scanning, DKIM and DMARC alignment, and monitoring of complaint rates and blocklists.

title: Design a stock exchange matching engine
category: Web & product
level: Senior / Staff
concepts: eventsourcing, lockfree, concmodels, raft, consensus, replication, commitlog, wal, memhier, cachelines, numa, gc, allocators, batching, zerocopy, sockets, hwclocks, lamport, idempotence, failuredetect, pubsub, dst, hashtables, trees, interrupts
summary: A stock exchange takes buy and sell orders from many brokers, matches them by strict rules (best price first, then first in, first out), reports every trade, and publishes the order book to everyone at the same time. The load is not huge by web standards (about a million messages per second), but the demands are unusual: every message must be handled in microseconds with a flat latency tail, in exactly the same order on the primary and the backup, with no lost or duplicated trade, and with fairness that regulators can audit. The design is a single-threaded, deterministic state machine fed by a sequenced, replicated input log, wrapped by gateways that check risk and by a market data publisher.
requirements: Functional requirements. Accept orders from members over a session protocol: new limit order, market order, cancel, cancel/replace, with time-in-force (day, immediate-or-cancel, fill-or-kill) and flags (post-only). Match continuously by price-time priority per symbol. Report acknowledgments, fills and rejects to the sender. Publish market data: every order book change and every trade, to all subscribers at the same time. Support an opening and a closing auction, trading halts, and circuit breakers. Send trades to clearing. Risk checks before orders reach the book: limits on size, price bands, credit, a kill switch per member.
Non-functional requirements. Latency: median under 50 microseconds from the gateway receiving an order to sending the ack, and the 99.99th percentile within a few hundred microseconds, since fairness depends on a flat tail. Throughput: 1 million messages per second across all symbols, with bursts of 10 times for short periods (news events). Determinism: the same input sequence always produces the same output, byte for byte. Durability: an acknowledged order or trade is never lost, even if the primary dies at the worst moment. Availability: failover in under a second inside the trading day. Fairness: orders are processed in the order they arrive at the sequencer, and market data reaches all members at the same time. Audit: complete, replayable record of every event with accurate timestamps.
Assumptions. 5,000 listed symbols, 6.5-hour trading day (23,400 seconds). Of all messages 95 percent are new orders and cancels and only about 5 percent lead to a trade (typical order-to-trade ratios are high). The busiest symbol sends 5 percent of all messages. Prices are integers in units of 1/10,000 of a currency unit.
estimates: Message rate. 1 million messages per second at peak. Busiest symbol: 5 percent, so 50,000 messages per second. Trades: 5 percent of messages, so 50,000 trades per second across the exchange at peak.
Per-message time budget. A single thread handling 1 million messages per second has 1 microsecond per message. A real matching step (hash lookup of an order, update of a price level, one or a few fills) takes 200 to 500 nanoseconds when the data is in cache. The busiest symbol needs 50,000 times 0.5 microseconds = 25 milliseconds of CPU per second, 2.5 percent of one core. The engine is not CPU bound; the goal is latency and determinism, not throughput.
Size of the book in memory. Live resting orders: assume 10 million across all symbols, 100 bytes each (id, side, price, quantity, member, timestamp, links): 1 GB total. Per symbol average: 2,000 orders = 200 KB, which fits in the 1 to 2 MB L2 cache of a core. Even the busiest symbol with 50,000 live orders is 5 MB, which fits in L3. This is why a design with arrays and pooled objects, without pointer chasing, is very fast.
Message size and bandwidth. A binary order entry message (OUCH style) is about 50 to 70 bytes. Inbound: 1,000,000 times 64 bytes = 64 MB/s = 0.5 Gbit/s. Outbound acks: about the same. Market data: each book event is about 30 to 40 bytes (ITCH style): 1,000,000 times 40 = 40 MB/s = 320 Mbit/s per feed, sent once by multicast to all subscribers.
Journal. The sequenced input log: 64 MB/s times 23,400 s = 1.5 TB per trading day. At 250 trading days, 375 TB per year, which goes to cheap storage after the day. Replication to a second machine's memory adds one network round trip of about 10 to 20 microseconds per batch.
Recovery time. Snapshot of all books: 1 GB, written every minute in the background. If a cold process must rebuild, it loads the snapshot (1 GB at 2 GB/s = 0.5 s) and replays up to 60 seconds of input: 60 million messages at 2 million per second replay speed = 30 s. This is too slow for failover, so we keep a hot standby that applies the same stream continuously, and cold recovery is only for the third copy.
Latency budget (median, in microseconds): wire in and NIC 5, gateway decode and risk 5, sequencer and replicate 15, matching 2, journal ack 0 (already counted), response encode and send 5, total about 32 to 40. Each network hop inside the data center costs 3 to 10 microseconds with kernel bypass, and 30 to 100 with the normal kernel stack.
api: Order entry (binary session protocol over TCP, like OUCH or FIX binary): Enter Order {client_order_id, symbol, side, quantity, price, time_in_force, flags}. Replace Order {client_order_id, new_quantity, new_price}. Cancel Order {client_order_id}. Each session message carries a session sequence number so gaps can be detected and resent.
Responses: Accepted {client_order_id, exchange_order_id, timestamp}, Rejected {reason}, Executed {client_order_id, trade_id, price, quantity, leaves_quantity}, Canceled {client_order_id, reason}. Fills reach the sender at the same time as the market data event.
Market data (UDP multicast, like ITCH): Add Order {order_ref, side, symbol, quantity, price}, Order Executed {order_ref, quantity, match_number}, Order Cancel {order_ref, quantity}, Order Replace, Trade {price, quantity}, System Event (start, halt, close). Every packet has a sequence number. A separate unicast channel serves retransmissions of gaps and a snapshot of the book for late joiners.
Drop copy and clearing: a stream of all executions to the member's risk system, and a feed of trade reports to the clearing house, which settles trades in the US one business day after the trade date (T+1 since May 2024).
Admin: halt symbol, resume, set price bands, kill switch for a member, and query the order book state (read-only, from a replica).
datamodel: Order: id (64-bit, assigned by the sequencer), member id, symbol id, side, price (integer ticks), quantity, remaining quantity, sequence number at entry, flags, and two links (previous and next order at the same price level).
Order book per symbol: two sides, bids and asks. Each side is a set of price levels. A price level holds the total quantity, the order count, and a FIFO queue of orders (an intrusive doubly linked list, so removal of any order is O(1)). Levels are found by price: either an array indexed by (price minus base price) divided by tick size when the range around the market is bounded (O(1) lookup, and the best price is tracked by a pointer), or a sorted tree (O(log n)) for wide ranges. Best bid and best ask pointers make the "is there a match" test a comparison of two integers.
Order index: a hash map from order id (or from member id and client order id) to the order, for O(1) cancel and replace. Pre-allocated pools of order objects avoid memory allocation on the hot path. All memory is allocated at startup.
Journal: an append-only log of sequenced input events: (sequence number, timestamp, session, message bytes). The output events are not stored; they are derived by replay, because the engine is deterministic. A snapshot is a dump of all books and the next sequence number.
Reference data: symbols, tick sizes, price bands, lot sizes, trading phase per symbol (pre-open, open auction, continuous, halted, closing auction, closed). Loaded at start of day, and changed only by sequenced admin events, so that all replicas see the change at the same point in the stream.
Member state: session ids, credit and position limits, order rate counters. Risk counters live in the gateway, near the member's sessions.
design: The shape. The system is an event-sourced state machine. Gateways (many) take orders from members, validate and run risk checks, and send them to the sequencer. The sequencer (one per partition of symbols) gives each input a global sequence number and a timestamp, writes it to the journal and replicates it to the backup. Matching engines (primary and hot standby, plus a third copy) consume the same sequenced stream in order and produce identical outputs. Outputs go to the order-response path and to the market data publisher. Clearing and surveillance read the output stream.
Why one thread. Matching is a sequence of dependent decisions: the result of order 1,001 depends on the book left by order 1,000. Locks would cost more than the matching itself and make the order of events depend on thread timing, which breaks determinism and fairness. A single thread per partition, pinned to a core, in a busy-spin loop (no sleeping, no interrupts), reading from a ring buffer, has no locks, no cache-line bouncing, and predictable latency. The LMAX architecture reported over 6 million orders per second on one thread for this style. Scale-out happens by partitioning symbols across engines, never by splitting one symbol's book.
Order flow. A member sends an order. The gateway decodes the binary message, checks session sequence, risk limits and price bands in a few microseconds, and forwards it. The sequencer assigns sequence number n and timestamp from its own clock, appends to the journal, and replicates to the backup and to the engine. The engine, reading event n, looks up the symbol's book and runs the matching procedure. For a buy limit order at price p with quantity q: while q > 0 and best ask <= p, take the first order at the best ask level, trade min(q, resting quantity) at the resting order's price, reduce both, remove the resting order if filled, and emit an execution event for each side. If q > 0 remains and the order is not immediate-or-cancel, add it to the bid level at p, at the tail of the queue. Sell orders mirror this. Events go out through the response path and the market data publisher.
Durability and replication. fsync of a log to NVMe takes tens of microseconds with a high tail, and would dominate the latency. Instead the sequencer replicates each batch of inputs to the memory of one or two other machines (using a replicated log such as Aeron Cluster, or a Raft-style protocol), and considers the input committed when a majority has it. Data in the memory of two or three machines in different power domains survives the failure of any one. The log is also written to disk asynchronously. The engine does not output an ack for event n until n is committed, so an acknowledged order is never lost.
Market data and fairness. The publisher turns each output event into a market data message and sends it once by UDP multicast on two redundant feeds (A and B) so that receivers can merge them and fill gaps from the other. Members connect with cables of equal length (colocation rules) and the exchange sends the data to all at the same instant, so no member gets the information earlier. Order responses and public data are released together or in a defined order.

deepdive: Determinism and the replicated state machine. The matching engine is a pure function of the ordered input: state_n+1, outputs = f(state_n, input_n). It reads no wall clock (time is a field of the input), no random numbers, no thread timing, no hash-map iteration order that differs between runs. Then primary, backup and the replay on a test machine produce identical outputs. This gives hot failover (the backup is always at the same sequence number), exact audit and replay, and testing by deterministic simulation: run millions of random order sequences, compare the engine with a slow reference model, and replay any production day. Sources of non-determinism that cause real bugs include floating-point math (use integers), uninitialized memory, pointer-address ordering, and time-dependent features like order expiry (expiry must be a sequenced event emitted by a timer that the sequencer generates, not a local clock read).
Sequencing is the real bottleneck for correctness. The sequencer defines "who was first". It must be a single logical point per partition, since distributed clocks cannot decide ordering within microseconds. Gateways timestamp arrival with hardware clocks synchronized by PTP (precision time protocol) to under a microsecond for audit, but the order for matching is the sequence number. To reduce unfairness from different cable paths, the exchange uses equal-length cross-connects, and some exchanges add a deliberate delay ("speed bump") to all incoming orders. The sequencer can batch inputs (for example up to 64 messages) to amortize the replication cost, trading about 1 microsecond of delay for lower per-message cost.
Failover without losing or duplicating. If the primary dies, the backup has every committed input up to sequence n. It takes over the output role and must send responses for events that the primary may or may not have sent. Outputs carry the input sequence number, and receivers (gateways, market data consumers) de-duplicate by it. Sessions with members use sequence numbers; on reconnect, the member and gateway exchange the last sequence numbers and resend the gap. A failure detector on heartbeats (every 100 ms, with 3 missed) triggers election; a consensus protocol ensures only one primary at a time (split brain would create two truths). Total failover in the hundreds of milliseconds is typical.
Garbage, caches and the latency tail. Average latency is easy; the tail is hard. Causes of 1 ms spikes: garbage collection pauses (so Java engines allocate nothing on the hot path and use pre-allocated pools, or use C++ and Rust), page faults (lock and pre-touch memory, use huge pages), context switches and interrupts (pin threads to isolated cores, move interrupts to other cores), the kernel network stack (use kernel bypass such as DPDK, Solarflare Onload or RDMA), NUMA remote memory (keep the thread, the NIC and the memory on one socket), CPU frequency changes and SMT neighbors (disable power saving and hyperthreading), and logging (write to a ring buffer and let another thread flush). Measure with hardware timestamps, and watch the 99.99th percentile.
Order book data structures. The two operations that dominate are adding at a price and canceling by id (about 90 percent or more of messages are cancels or cancel-like). A hash map from order id to order node gives O(1) cancel: unlink the node from its level's list, subtract the quantity, and if the level is empty remove it. Price-level lookup by array index is O(1) when prices are in a bounded band around the market; far-away prices go in a sorted overflow structure. Best price is cached; it moves only when the best level empties. Memory is laid out for the cache: levels in contiguous arrays, orders in a pooled slab. A match step touches one or two cache lines.
tradeoffs: Single-threaded or multi-threaded matching. Choose single-threaded per symbol group when you want determinism, simple correctness and the lowest, flattest latency, which is the standard for exchanges. Choose multi-threaded matching, with locks or lock-free structures, only if one book must exceed millions of messages per second, which is rare; you pay with complex ordering rules and harder audit. Scale through more partitions of symbols instead.
Price-time (FIFO) or pro-rata allocation. Choose FIFO for stocks and most markets: it rewards early quotes and is simple to explain and implement. Choose pro-rata (fills shared by size at the best price) for markets such as some interest-rate futures where large resting orders should not be ignored; the matching is more complex and needs rounding rules, and it encourages oversized quoting.
Replicated memory or disk for durability. Choose replication to the memory of a second and third machine, with async disk, for microsecond commits; it survives any single failure, but a simultaneous power loss of all copies loses the tail, so spread power domains. Choose synchronous disk (NVMe with fsync, or persistent memory) when regulation or business demands survival of a full-site power loss at once, accepting tens of microseconds of added latency.
Primary-backup or consensus cluster. Choose primary with a hot standby and a third witness (Raft-like quorum of three) for exchanges: one writer, fast commit, clear failover. Choose a larger consensus group only across sites; each added replica or distance adds latency (a 100 km link is 1 ms round trip), so cross-site is for disaster recovery with asynchronous replication.
Centralized matching or a distributed design. Choose central matching in one data center for a regulated exchange, where the order of events must be unique and audited. Choose distributed or sharded designs (by symbol or by market) for crypto venues and internal matching, where you can accept more latency to scale the number of markets and tolerate regions.
failures: Matching engine primary dies. The hot standby is at the same sequence number. After the failure detector fires and the quorum agrees, it becomes primary and resumes outputs from the last committed sequence. Members see a pause of a few hundred milliseconds. Duplicate outputs are filtered by sequence numbers. The old primary, if it was only paused, is fenced (it must see the new epoch before it can output).
Sequencer or journal replication fails. If a majority of the replicas is unavailable the sequencer stops accepting inputs: the exchange halts rather than risk losing or reordering trades. Better to halt than to be wrong. A halt is announced on the market data feed, and trading resumes after a controlled recovery and often a reopening auction.
Gateway crash. Members reconnect to another gateway; session sequence numbers allow resending of missed acks. Open orders stay in the book unless the member selected "cancel on disconnect", a common option which the exchange runs as a sequenced mass-cancel to protect members from stale quotes.
Market data gap. A receiver misses packet 5,120 on the A feed. It uses the B feed. If both miss it, it requests a retransmission on the unicast channel, or takes a snapshot and then the live feed from the snapshot's sequence number. Receivers that are too slow are cut off, because a slow consumer must not slow the multicast.
Data center loss. A disaster recovery site gets the journal with asynchronous replication a few milliseconds behind. A failover is a human decision: the exchange accepts that a few milliseconds of events could be missing, reconciles with members by their own records, and restarts the day from the last known sequence. Regulation sets the recovery time (for example two hours).
Bad software release. A new engine version could differ on subtle rules. Run the new version as a shadow on live input and compare all outputs with the primary byte by byte before switching. Replay the last several days. Release only on weekends and after a regression suite with deterministic simulation.
evolution: At 1,000 messages per second (an internal crossing network or a small crypto venue), a single process in any language with a database journal is enough. At 100,000 per second, a single-threaded engine with an in-memory book, a replicated log (Raft) and a hot standby in the same zone. At 1 million per second, the design above: kernel bypass, pinned cores, sequencer with batched replication, symbol partitions across engines, A/B multicast feeds. At the scale of the largest venues (tens of millions of messages per second in bursts across many matching units), the symbol space is split over many independent matching units, each with its own sequencer, with a common gateway layer, shared reference data and a consolidated market data tape, plus hardware acceleration (FPGAs in gateways and market data) for sub-microsecond tick-to-trade.
followups: Why is the matching engine single-threaded? || Each order depends on the book left by the previous one, so work is inherently serial per symbol. A single thread avoids locks, cache-line contention and timing-dependent ordering, gives deterministic replay and low jitter, and a core can process millions of messages per second. Scale out by partitioning symbols across engines.
How do you guarantee an acknowledged order is never lost? || The sequencer commits an input only after a majority of replicas hold it in memory (and the journal is written asynchronously). The engine releases the ack after that commit. A single machine failure cannot lose it, and a hot standby with the same sequence takes over.
What data structure holds the order book? || Per side, price levels in a sorted structure or an array indexed by price tick, each level a FIFO list of orders, plus a hash map from order id to order for O(1) cancels, and cached best bid and ask. Memory is pooled and contiguous to stay in cache.
How do you ensure fairness between members? || Order is defined by the sequencer's number, not by the wall clock. Equal-length cables and a common network design give equal access, and market data goes out by multicast at the same moment. Hardware timestamps allow audit. Some venues add a small speed bump to all inbound orders.
What happens if the primary and backup disagree after a failure? || They cannot, if the engine is deterministic and they consume the same committed sequence. The backup only acts on committed inputs, a quorum protocol selects one primary per epoch, and the old primary is fenced. Outputs include input sequence numbers, so duplicates can be dropped.
How do you handle 90 percent cancels at high rate? || Cancel is a hash lookup and an O(1) unlink from the level list, with no search. The engine keeps counters for the level quantity and best price pointers. Gateways also rate limit message-to-trade ratios per member.
How would you test the engine? || Deterministic simulation: generate random order streams, run the engine and a simple reference implementation, compare all outputs and invariants (no crossed book, quantity conservation, price-time priority). Replay production journals, run shadow versions on live traffic, and test failure injection at every point in the replication protocol.
