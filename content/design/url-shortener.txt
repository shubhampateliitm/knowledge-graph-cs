title: Design a URL shortener
category: Web & product
level: Senior / Staff
concepts: nosql, partitioning, cachelayer, conshash, eviction, cdn, http, replication, birthday, hashfn, quorum, idempotence, ratelimit, bloom, kafka, streamproc, olap, hll, loadbalancing, dns
summary: Build a service like bit.ly: a user gives a long URL and gets back a short link such as https://sho.rt/aZ3kQ9x. Anyone who opens the short link is sent to the long URL in a few milliseconds, and the owner can see how many people clicked. The idea is simple, but the numbers are not: reads outnumber writes about 100 to 1, a single link can go viral and take 50,000 clicks per second, every short code must be unique across billions of links, and the redirect must keep working when a cache, a database node or a whole region fails. The interview is about the ID scheme, the key-value data model, caching a very skewed read load, and keeping analytics off the critical path.
requirements: Functional requirements. A user can create a short link for a long URL, optionally with a custom alias (sho.rt/summer-sale) and an expiry date. Opening a short link redirects to the long URL. The owner can list their links, disable a link, and see click counts per day, unique visitors, top countries and top referrers. Short codes are 7 characters from [a-zA-Z0-9]. Editing the destination of a link is out of scope (it is a follow-up).
Non-functional requirements. The redirect is the product: it must be highly available (99.99%, about 52 minutes of downtime per year) and fast (p99 under 20 ms inside our data center, under 100 ms for the user end to end). Creating a link can be slower (p99 under 300 ms) and may be briefly unavailable without much harm. A link must work immediately after it is created, because people paste it into a chat within seconds: this is read-your-writes for the creator and, in practice, for everyone. Codes must not be guessable in sequence. Analytics may lag by a minute and lose a tiny fraction of clicks; redirects never wait for analytics.
Assumptions I choose: 100 million new links per month, a read-to-write ratio of 100:1, links kept for 5 years by default, and a public API used by both our web app and business customers with API keys.
estimates: Writes. 100 million links per month divided by about 2.6 million seconds per month is about 40 creates per second on average. With a peak factor of 5 for business hours and batch API customers, plan for 200 creates per second.
Reads. At 100:1, that is about 4,000 redirects per second on average and 20,000 per second at a normal daily peak. One viral link alone can add 50,000 per second for a few minutes, so the redirect path must handle hot keys, not just total volume.
Storage. One link record is a 7-byte code, a long URL (average about 100 bytes, maximum 2,048), the owner id, created and expiry timestamps and a few flags: about 250 bytes of data, or about 500 bytes with key and index overhead. 100 million links times 500 bytes is 50 GB per month, 600 GB per year and 3 TB over 5 years. With 3 replicas we store about 9 TB. Small for a partitioned key-value store, but too big for one relational node with room to grow.
Code space. 62^7 is about 3.5 trillion codes. After 5 years we have 6 billion links, so only 0.17% of the space is used. That is enough room for random codes, as long as we check for collisions (see deep dive).
Cache memory. Clicks follow a power law: a small share of links gets most of the traffic. If we cache the 20% of the last month's links that are hot, that is 20 million records times about 500 bytes, about 10 GB. That fits in a small Redis cluster (3 primaries with 8 GB each, plus replicas).
Bandwidth. A redirect response is only headers, about 400 to 500 bytes, so 20,000 per second is about 10 MB/s out. Each click also produces an analytics event of about 200 bytes: 4,000 per second times 200 bytes is 0.8 MB/s, about 70 GB per day into the event log before compression.
Machines. One stateless redirect server answering mostly from cache does 5,000 to 10,000 requests per second, so peak needs 3 to 4. We run 3 per zone in 3 zones (9 per region), so losing a zone still leaves headroom. After the cache absorbs over 90% of reads the database sees a few thousand reads per second; 6 nodes per region is plenty, sized by storage and by the load it must take if the cache fails.
api: POST /api/v1/links. Body: {"long_url": "...", "custom_alias": optional, "expires_at": optional}. Header Idempotency-Key: a client-chosen UUID. Returns 201 with {"code", "short_url", "expires_at"}; 409 if the alias is taken, 400 for a bad or blocked URL, 429 over the rate limit.
GET /{code}. The redirect itself, on the short domain. Returns 302 Found (or 301, see trade-offs) with a Location header holding the long URL, 404 for an unknown code and 410 Gone for an expired or disabled link.
GET /api/v1/links?owner=me&cursor=... Lists the caller's links, newest first, 50 per page, with a cursor for the next page. DELETE /api/v1/links/{code} disables a link (a soft delete: the code is never reused).
GET /api/v1/links/{code}/stats?from=...&to=...&granularity=day. Returns clicks per bucket, unique visitors, and top countries and referrers. Served from the analytics store.
datamodel: Table links, partition key code. Columns: code (7 chars), long_url, owner_id, created_at, expires_at, status (active, disabled), flags. Every redirect is a lookup by exact code, so the code is the perfect partition key: hashing it spreads load evenly over the partitions, and there are no range queries on codes. This is the access pattern a distributed key-value store (DynamoDB, Cassandra, or a sharded Postgres) is built for.
Table links_by_owner, partition key owner_id, sort key created_at descending, value code and a copy of long_url. This serves "list my links" without a scatter-gather over every partition. It is written in the same create request and retried if it fails; a missing row here only affects the owner's list.
Table aliases is not needed: a custom alias is just a code chosen by the user, stored in the same links table, so uniqueness is enforced by the same conditional write.
Table idempotency_keys, key (api_key, idempotency_key), value the response, TTL 24 hours, so a retried create returns the same link instead of making a second one.
Analytics live elsewhere: click events go to a log (Kafka) and are rolled up into an OLAP store, partitioned by day and clustered by code, holding per-minute counts and HyperLogLog sketches for unique visitors.
design: The path of a redirect. The user opens https://sho.rt/aZ3kQ9x. DNS for sho.rt returns the address of the nearest region (geo DNS with a 60-second TTL, so traffic can leave a broken region in about a minute). The request reaches a CDN edge first; for most links the edge does not cache the response and forwards it. Inside the region, a layer 7 load balancer terminates TLS and sends the request to one of the stateless redirect servers.
The redirect server looks up the code in its own small in-process cache (an LRU of about 100,000 entries, which catches the hottest links with no network hop at all), then in the shared Redis caching layer, and only on a miss in both does it read the links table. A hit costs microseconds in process or about 0.5 ms in Redis; a database read costs 2 to 5 ms. The server then checks status and expiry and answers 302 with the Location header. It also puts a click event into an in-memory buffer that a background thread sends to Kafka in batches every 100 ms; the response never waits for Kafka.
The path of a create. The create request goes through the API gateway, which checks the API key and applies rate limiting (a token bucket per key and per IP address). The link service validates the URL (http or https, at most 2,048 characters, domain not on a phishing blocklist), then generates a random 7-character code with a cryptographically secure random generator and writes the row with a conditional write: insert only if no row with this code exists. If the condition fails, it simply draws a new code and tries again. On success it also writes the row into Redis (write-through), so the first click is a cache hit even before replicas catch up, and answers 201.
The cache tier is a cluster of Redis primaries, each with a replica in another zone. Keys are spread over the primaries with hash slots, a fixed form of consistent hashing, so adding a node moves only a slice of keys instead of reshuffling all of them. Entries have a 24-hour TTL and the cluster uses an LFU eviction policy, which keeps long-lived popular links better than plain LRU when a burst of one-time clicks passes through. Negative answers ("no such code") are cached for 60 seconds.
The database is partitioned by a hash of the code and replicated 3 times across zones. Reads on a cache miss use a quorum read (with 3 replicas, write to 2 and read from 2, so every read overlaps the latest successful write), which gives read-your-writes even if the write-through to the cache failed.
Analytics is a separate pipeline. Kafka holds click events (code, timestamp, country from the IP address, referrer, user agent class, a hashed visitor id) for 7 days. A stream processing job reads them, removes obvious bots, aggregates per code and per minute, updates a HyperLogLog sketch per code and day for unique visitors, and writes the results to the OLAP store that the stats API reads. If this pipeline is down, redirects do not notice; stats just lag.

deepdive: Generating unique codes. There are three classic choices. First, hash the long URL with a cryptographic hash function (SHA-256) and keep 7 base62 characters. The same URL always gives the same code, but different URLs can still collide on 7 characters, and two users who shorten the same URL share one link and its statistics. Second, a counter: a global sequence turned into base62. It never collides, but sequential codes are guessable and one counter is a bottleneck; the fix is to hand each server ranges of 10,000 ids from a coordination service and scramble them with a reversible permutation. Third, random codes with a conditional insert, our choice: no coordination, not guessable, and put-if-absent gives uniqueness.
Why random codes need the collision check: the birthday bound. With a space of N = 3.5 trillion codes, the chance that some two random codes collide passes 50% after only about 1.2 times the square root of N, about 2.2 million codes. So collisions happen in the first week. What matters is the chance that a new code hits an existing one, which is simply (links stored) / N: 6 billion / 3.5 trillion = 0.17% after 5 years. So about 1 create in 600 needs a second try, and two retries in a row happen about once in 350,000 creates.
Hot keys. A viral link can receive 50,000 clicks per second. All of them hash to the same Redis slot and the same database partition. The in-process LRU on each redirect server takes almost all of this load: with 9 servers, each sees about 5,500 per second for that key and answers from memory. For extreme cases (a link in a TV ad), servers send Cache-Control: public, max-age=60 for codes above a click-rate threshold, so the CDN edge answers almost every request; that minute's counts then come from CDN logs.
Read-your-writes. A friend clicks a new link 2 seconds after it was created, maybe in another region. Three things make this work: write-through to Redis in the creating region, quorum reads on a cache miss, and, for multi-region, routing a miss for an unknown code to the code's home region before answering 404. We put the home region into the code: the first character is drawn from a range of characters reserved for that region, so two regions can never create the same code.
Protecting the database from scanners. Bots try a different random code every time, so the negative cache does not help. Rate limiting 404 answers by IP address helps, and a Bloom filter of existing codes answers most 404s without a database read: at a 1% false positive rate it needs about 9.6 bits per code, so 1.2 billion codes from the last year take about 1.4 GB. A false positive just costs one normal database read.
Analytics without slowing redirects. Counting clicks with a database increment per click would put 4,000 to 50,000 writes per second on a single hot row. Instead each click is an event in Kafka, partitioned by code so per-link order is kept, and the stream job aggregates in memory and writes one row per code per minute. Unique visitors use HyperLogLog: about 12 KB per code per day at most (and much less in its sparse form for small links) gives about 1% error, instead of storing every visitor id.
tradeoffs: 302 or 301. Choose 302 (or 307) when analytics and control matter: every click comes to us, we can count it, and we can disable a link that turns out to be phishing. Choose 301 for the fewest requests: browsers cache a permanent redirect, so repeat clicks never reach you; that saves load but loses counts and makes a bad link hard to stop. We default to 302; a 301 with a short Cache-Control max-age is a middle ground.
Key-value store or relational database. Choose a sharded relational database (Postgres) when the team knows it well and the scale is in the low billions of rows: unique constraints, transactions for the two tables and easy ad-hoc queries are worth a lot. Choose a managed key-value store (DynamoDB) or Cassandra when you want partitioning, replication and multi-region built in and you only "get by key": you give up joins and ad-hoc queries, and each other access pattern (like links_by_owner) becomes its own table.
Random codes or counter ranges. Random codes need no coordination and are not guessable, but they need a conditional write and an occasional retry. Counter ranges never collide and make codes as short as possible early on (a 5-character code covers the first 900 million links), but they need a coordination service for range allocation and a scrambling step so codes are not sequential. With a 7-character code from day one, random wins on simplicity.
Cache aside or write-through. Write-through costs one extra Redis write per create (200 per second at peak) and makes the first click a cache hit. Pure cache aside is simpler but sends the first clicks of each new link to the database, just when replicas may lack the row. With so few writes, write-through wins.
failures: A redirect server dies. The load balancer health check removes it within about 10 seconds; the servers are stateless, so the others take over. We run enough servers that losing a whole zone (a third of them) still leaves capacity for peak traffic.
A Redis primary fails. Its replica in another zone is promoted in about 10 to 30 seconds. During that time misses for its keys go to the database. The bigger danger is losing the whole cache tier: the database would see 20,000 reads per second instead of 2,000. We protect it with request coalescing (one database read per code per server at a time), the in-process LRU, and load shedding: past a latency threshold, servers answer 503 with Retry-After for cold codes instead of letting queues grow.
A database node or zone fails. Each partition has 3 replicas in 3 zones and we read and write with quorums of 2, so one replica down changes nothing visible.
A region fails. Geo DNS stops sending traffic there within about a minute (the DNS TTL). The links table is replicated to the other regions asynchronously, usually in under a second, so only links created in the last second or so in the failed region may be missing for a while; their home-region prefix tells the other regions to answer "try again shortly" rather than a permanent 404.
Kafka or the stream job is down. The redirect servers keep a bounded in-memory buffer (100,000 events, about 20 MB) and drop the oldest when it fills, counting the drops. Redirects never block; stats lag.
A bad deploy. Canary on one server per zone, with automatic rollback if the 5xx rate or p99 latency rises.
Abuse. Phishing is the largest real risk. We check URLs at create time, rescan in the background, and disable a code by updating the row and deleting the cache entry; with 302 the next click sees it.
evolution: 1,000 users. One Postgres instance with a unique index on code, one application server that does both create and redirect, and a daily backup. A counter turned into base62 is fine here.
1 million users. Add Redis in front of the database for redirects, run 3 or more stateless servers behind a load balancer, add a read replica, move click counting to a queue and batch writes, and add rate limiting on the API. Switch to random codes with a conditional insert so you are ready to shard.
1 billion users. Partition the links table by code across many nodes (or move to a managed key-value store), run in several regions with geo DNS and region prefixes in codes, add the in-process cache and CDN caching for hot links, and build the Kafka, stream processing and OLAP pipeline for analytics. At this size most effort goes into abuse, multi-region failures and cost.
followups: How would you let users change the destination of an existing link? || Store a version or updated_at on the row, update the database first, then delete (not update) the cache entry so the next read loads the new value. Keep redirects as 302 so browsers do not cache the old target. Mention the race between a stale cache fill and the delete; a short TTL or a version check fixes it.
Your counter-based ID service is down. What happens to creates? || With range allocation, each server still has its current range of ids, so creates continue until the ranges run out; a larger range per server buys more time. This is why random codes with a conditional write are attractive: no service to lose. Redirects are not affected either way.
How do you make "list my links" fast for a business account with 50 million links? || Use the links_by_owner table with the owner as the partition key and created_at as the sort key, and page with a cursor. For very large owners the partition gets too big, so add a bucket to the key (owner_id plus month) to split it. Search over these links goes to a separate search index fed from the change stream.
How do you count clicks exactly once? || Clicks can be duplicated by retries from the server buffer and by Kafka redelivery. Give each event an id, use Kafka's idempotent producer, and make the stream job's output idempotent: write per-minute aggregates keyed by (code, minute) with overwrite, using checkpoints, so a replay produces the same numbers.
Why not keep everything in Redis and skip the database? || Redis keeps data in memory: 9 TB with replicas is expensive in RAM, and persistence (snapshots and append-only files) gives weaker durability than a replicated database. Losing links is unacceptable because printed links live for years. Redis is the right place for the hot 10 GB, not for the full history.
