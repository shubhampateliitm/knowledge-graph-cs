@@ ad-click-aggregator
title: Design an ad click and impression aggregator
category: Ads & media
level: Senior / Staff
concepts: kafka, flink, exactlyonce, windowing, watermarks, idempotence, pinot, olap, partitioning, checkpoint, hll, lambdakappa, deliverysem, backpressure, adtech, clickhouse, lakehouse
summary: We build the system that counts how many times each ad was shown (impressions) and clicked, per campaign, per publisher, per minute. Advertisers are billed from these numbers, and they watch dashboards that must be fresh within about a minute. The hard parts are correctness and scale at the same time: every event must be counted once even when browsers retry, servers crash and events arrive late, and a single viral campaign must not overload one machine. The system has two outputs with different promises. A fast stream path feeds dashboards within seconds, and a slower batch path recomputes the same numbers from raw logs to produce the figures that are used for invoices.
requirements: Functional requirements. The system accepts impression and click events from browsers, mobile apps and CTV players. It returns aggregated counts by campaign, ad, publisher, country and device, at one-minute, one-hour and one-day grain. Advertisers can query the last 7 days at minute grain and the last 2 years at hour grain. Dashboards show data that is at most 1 minute old. The billing export shows final numbers for a closed day.
Non-functional requirements. No double counting and no lost events: the billing path must be exactly once in effect, and its total must match the raw log to within 0.01 percent. The collection endpoint answers in under 50 ms at p99 and must never block the ad render. Late events (up to 10 minutes late on the stream path, up to 7 days on the batch path) must be counted in the right time window. The system survives the loss of one machine, one zone, and a 3x traffic spike.
Assumptions. 5 billion impressions per day and 50 million clicks per day (click-through rate of 1 percent). Peak traffic is 3 times the daily average. One event is about 200 bytes in Protobuf. About 1 percent of events are duplicates caused by retries, and about 3 percent of traffic is bots or invalid. Advertisers have 100,000 active campaigns, 1 million active ads and 500,000 publisher sites.
estimates: Event rate. Impressions: 5,000,000,000 / 86,400 s = about 58,000 per second on average. Peak is 3 x 58,000 = 175,000 per second. Clicks: 50,000,000 / 86,400 = about 580 per second, with a peak of about 1,750 per second. Clicks are 100 times rarer than impressions, but each click is worth far more money, so we treat the click stream as the correctness-critical stream.
Raw volume. 5.05 billion events x 200 B = about 1 TB per day. Per year: 1 TB x 365 = 365 TB raw. With Parquet columnar compression at about 5x, this is about 75 TB per year in the lakehouse.
Kafka. Peak ingress is 175,000 x 200 B = 35 MB/s. With replication factor 3, the brokers write 105 MB/s at peak, which is small for a cluster. We still use 64 partitions so that each partition sees at most 2,800 events per second at peak and the Flink job can run with 64 parallel tasks. Retention of 3 days: 1 TB x 3 days x 3 replicas = 9 TB of disk, spread over 6 brokers with 2 TB each (plus headroom).
Aggregate size. We guess 3 million distinct (ad, publisher, country, device) combinations are active in any minute. A minute row is about 40 B (key plus counts plus an HLL sketch pointer or a small sketch). One minute is 120 MB. One day of minute rows is 120 MB x 1,440 = 173 GB. Seven days: about 1.2 TB. Hour-grain rows: 10 million combinations per hour x 24 x 40 B = 9.6 GB per day, and 2 years is about 7 TB. Both fit easily in a small OLAP cluster (for example 6 servers with 4 TB SSD each, with replication 2).
Dedupe state. We remember event ids for the dedupe window. For clicks, a 24-hour window: 50 million x 24 B (16 B id plus overhead) = 1.2 GB. For impressions, a 1-hour window: 58,000 x 3,600 x 24 B = 5 GB. Spread over 64 Flink tasks this is under 100 MB per task, kept in RocksDB state on local SSD.
Flink size. One task can process roughly 10,000 to 20,000 simple keyed events per second per core with state access. 175,000 / 15,000 = about 12 cores at peak. We run 64 parallel tasks anyway to match Kafka partitions, giving more than 5x headroom for recovery catch-up. After a crash we must replay the data since the last checkpoint (1 minute) plus the downtime; with 5x headroom, a 10-minute outage is caught up in about 2.5 minutes.
Collector fleet. A stateless collector handles about 20,000 requests per second per 4-core machine for a tiny write. For 175,000 peak, 9 machines are enough; we run 24 across 3 zones so that losing a zone leaves 16 machines at about 11,000 per second each.
api: POST /v1/events (collector). Body: a batch of up to 20 events, each with event_id (UUID generated on the client), type (impression or click), ad_id, campaign_id, publisher_id, placement_id, client_ts, device, and a signed token. Returns 204 immediately after the batch is written to Kafka with acks=all. The client retries with the same event_ids if it gets no answer.
GET /c/{token} (click redirect). The token is a signed, expiring blob that holds impression_id, ad_id and the advertiser landing URL. The server verifies the signature, writes a click event to Kafka, and answers 302 to the landing URL. Signing stops people from forging clicks on ads they never saw.
GET /v1/stats?campaign_id=...&from=...&to=...&grain=minute|hour|day&group_by=publisher,country. Returns rows of impressions, clicks, unique_users (approximate), and a field "finalized" that says if the row has been confirmed by the batch path. Served by the OLAP store.
GET /v1/billing/{advertiser_id}/{date}. Returns the final, immutable counts for a closed day, read from the batch-produced table. Includes a checksum and the number of events rejected for fraud.
datamodel: Raw event log (Kafka topics "impressions" and "clicks", then Iceberg or Delta tables on S3). Partition key in Kafka: hash of ad_id. This puts all events of one ad in one partition, so one Flink task can aggregate and dedupe them locally. The lakehouse table is partitioned by event date and hour, and sorted (clustered) by campaign_id for cheap scans.
Aggregate table in the OLAP store (Pinot or ClickHouse): key = (window_start, ad_id, publisher_id, country, device). Columns: impressions (long), clicks (long), invalid_impressions, invalid_clicks, users_sketch (HLL bytes), finalized (boolean), version (long). We write one row per key per window with the full counts, not deltas, so that writing the same row twice has no extra effect. Segments are time partitioned by day; the OLAP store sorts by campaign_id and builds an inverted index on publisher_id and country. A second table holds hour-grain rows, fed by the same job.
Dedupe state in Flink (RocksDB): key = event_id, value = first seen timestamp, TTL = 24 hours for clicks and 1 hour for impressions. Billing table (Delta): key = (advertiser_id, date, campaign_id), value = final counts, written once per day by the batch job with a MERGE so that reruns give the same result.
design: The path of an event has seven steps. First, the browser or app sends the event to a collector near the user. The collector is a stateless service. It validates the schema, checks the signature of the token, adds the server time and the client IP geolocation, and writes the batch to Kafka. It answers 204 only after Kafka has acknowledged the write with acks=all (all in-sync replicas). If Kafka is slow, the collector has a local memory buffer of a few seconds; beyond that it sheds load by dropping the lowest-value traffic first (impressions from unpaid test placements) rather than blocking the page.
Second, Kafka is the durable buffer between the internet and everything else. It decouples a fast, spiky producer side from consumers that can fall behind and catch up. A Flink job reads the topics. Kafka retention of 3 days is our insurance: any downstream bug can be repaired by replaying.
Third, the Flink job does the work in a fixed order. It parses and drops malformed events into a dead-letter topic. It dedupes by event_id using keyed state. It runs bot and invalid-traffic rules (known data-center IP ranges, impossible click delays under 100 ms after the impression, click rate per device). It enriches with campaign metadata from a small broadcast stream. It then keys by (ad_id, publisher_id, country, device) and applies tumbling event-time windows of 1 minute. A watermark that trails the highest seen event time by 2 minutes decides when a window is complete. Windows stay open for updates for 10 minutes of allowed lateness, and each late event produces an updated, full-count row.
Fourth, window results go to two sinks. One is the OLAP store, which accepts a row keyed by (window_start, dims) and replaces an older version of the same key. The other is a Kafka topic "aggregates" that other consumers (alerts, pacing) can read. Because rows carry full counts and a version, replays and retries only overwrite equal data. This idempotent sink, together with Flink checkpoints, is what makes the stream path exactly once in effect.
Fifth, in parallel, a second small job (or Kafka Connect) writes the raw, deduped events to the lakehouse in Parquet every few minutes. This is the source of truth for the batch path.
Sixth, the batch path. Every hour and again after the day closes (plus 6 hours to wait for late data), a Spark job reads the raw events of the window, dedupes by event_id across the whole window (no time limit on state, because it is a sort, not a stream), applies the final fraud model, and computes exact counts. It writes the hour and day tables with finalized=true and replaces the stream rows for those windows. Billing reads only finalized rows. This is the lambda idea, but the two paths run the same business logic from one shared library, so the two numbers differ only by late arrivals and the better fraud model.
Seventh, queries. The dashboard calls the stats API, which queries the OLAP store with a time range and filters. For a 7-day minute-grain query of one campaign, the store scans only the segments for that campaign thanks to sorting and the index, and returns in tens of milliseconds. Unique users come from merging HLL sketches, which is cheap and gives about 1 percent error.

deepdive: Exactly once. Strictly, exactly-once delivery over a network is not possible; what we build is "at-least-once delivery plus idempotent processing", which gives the same effect. There are four places where duplicates can enter. The client retries (fixed by the event_id and dedupe state). The collector retries a Kafka write (fixed by the idempotent producer, which gives each message a sequence number per partition). Flink restarts and reprocesses events after the last checkpoint (fixed by checkpointed state, and by a transactional Kafka sink that commits only when the checkpoint completes). The OLAP sink gets a write twice (fixed because the row carries the full count and a version, so a second write changes nothing). Each of these layers is cheap; skipping one of them is the usual cause of a billing dispute.
Late data and watermarks. An event has an event time (when the user saw the ad) and a processing time (when we got it). Mobile apps can go offline and send events an hour later. A watermark is the system's claim that "no more events older than T will arrive". Choosing the lag is a trade-off. With a 2-minute lag, dashboards are only about 3 minutes behind, but we will see some events later than that. For those we have allowed lateness of 10 minutes (the window re-fires with a corrected full count) and then a side output for anything later, which goes to the lakehouse only. The batch path picks it up. The dashboards are therefore eventually correct, and billing is correct after the close. We tell advertisers this directly: the field "finalized" is part of the API.
Hot keys. One big campaign during the Super Bowl may send 30 percent of all impressions to a few ad_ids. Keying by ad_id then puts one Kafka partition and one Flink task under heavy load, and that task falls behind (backpressure). The fix has two stages. In stage one, events are spread across tasks by (ad_id, random salt 0..15) and each task pre-aggregates counts for 1 second. In stage two, the partial counts are keyed by the real key and added. This reduces the events reaching the hot task by about a factor of the pre-aggregation (hundreds of events become one partial row). For Kafka itself, the collector can use a salt for known hot ads, which means dedupe cannot rely on partition locality for those ads; so we dedupe by event_id first, in a stage keyed by event_id, and only then apply the salted aggregation.
Unique users. Counting distinct users per campaign exactly needs memory proportional to the number of users. A HyperLogLog sketch gives 1 percent error with about 12 KB per key and, importantly, sketches from different minutes and servers can be merged. We store the sketch bytes in the minute rows and merge them at query time. A Count-Min sketch can help to find top publishers, but is not needed for billing. Billing counts (impressions, clicks) are always exact; unique users are only for reports.
Click attribution and fraud. A click should join to its impression, to know which placement and which creative was shown. The click carries the impression_id inside the signed token, so we do not need a stream-to-stream join: we read the fields from the token. We still check that an impression with this id exists in the dedupe state or in the lakehouse; clicks without an impression are held, not billed. The fraud rules run in two layers. Cheap online rules (IP lists, click delay, rate limits) run in Flink to keep dashboards clean. The final model, which can use a full day of behavior, runs in Spark before the billing close. Fraud-removed events are never deleted: they are tagged with a reason code, so a dispute can be examined.
Reconciliation. A separate small job compares totals every hour: count of events in Kafka (by offsets), count in the raw lakehouse, sum of the OLAP minute rows, and the batch result. The totals must match within the known rejects. An alert fires if the stream and batch differ by more than 0.5 percent for a closed hour. This single check catches most silent bugs, such as a bad deploy that drops an event type.
tradeoffs: Stream path only, or stream plus batch. Choose a stream-only design (kappa style, with replay from Kafka) when your retention is long enough, the logic is simple, and nobody invoices from the numbers. Choose stream plus batch when money depends on the totals: the batch path can use unbounded state for dedupe, handle events that are days late, and apply a better fraud model. The price is two code paths and a reconciliation job; sharing one library for the business rules keeps the cost lower.
Flink or Spark Structured Streaming. Choose Flink when you need low latency (seconds), large keyed state with fine control of event-time windows and timers, and a two-phase commit sink. Choose Spark Structured Streaming when the team already runs Databricks, the freshness target is 30 to 60 seconds or more, and one engine for batch and stream matters more than the last bit of latency. With micro-batches of 10 to 30 seconds, Spark meets the 1-minute dashboard target for this workload. You give up some control of late-data handling and per-key timers.
Pinot or ClickHouse or Druid for serving. Choose Pinot when you need many concurrent, low-latency queries from customers (hundreds of queries per second) and real-time ingestion from Kafka with upserts. Choose ClickHouse when you want simple operations and very fast scans on fewer, heavier queries, and can accept batch-like inserts of 1 to 5 seconds. Choose Druid if rollup at ingest and time-partitioned segments fit your queries. All three work at this size; the decision is mostly your team's skills and the concurrency of the customer-facing API.
Pre-aggregate in the stream, or store raw events in the OLAP store. Storing raw events (1 TB per day) lets users slice by any dimension and makes the system simple, but the cost is about 100 times more storage and slower queries. Pre-aggregating by a fixed set of dimensions cuts the data to 170 GB per day and queries run fast, but a new dimension requires a code change and a backfill from the lakehouse. Choose raw for small ad platforms or ad-hoc analysis; choose rollups when the dimension list is stable and customers watch dashboards all day.
Deltas or full counts per window. Sending deltas (+1) is cheap but breaks when a message is repeated. Sending the full count for the window with a version is idempotent and simple to repair, but a late event forces a re-emit of the whole row. For one-minute windows the row is small, so we choose full counts.
failures: Collector crash: the load balancer removes it within seconds, and clients retry with the same event_id, so no loss and no duplicate. Kafka broker loss: with replication 3 and min.insync.replicas=2, writes continue and no acked event is lost. Kafka zone loss: if racks are spread over 3 zones, the cluster keeps two replicas and keeps working. If the whole Kafka cluster is down, collectors buffer for seconds, then spill to local disk for up to an hour and replay later, with the same event_ids.
Flink task failure: the job restarts from the last checkpoint (every 60 seconds, stored in S3), replays from the saved Kafka offsets, and the transactional sink drops the uncommitted output. Recovery takes about 1 to 3 minutes. A poisoned message (a record that crashes the parser) is caught and sent to a dead-letter topic, because a crash loop would stop the whole pipeline. Slow sink: the OLAP store is slow, back pressure travels upstream, and Kafka absorbs the lag. We alert on consumer lag above 2 minutes. Because the data is in Kafka for 3 days, a lag of an hour is only a delay, not a loss.
OLAP store failure: dashboards go stale or return an error, but billing is unaffected because it reads the Delta table. We rebuild a lost segment from the lakehouse. Bad deploy of the Flink job: the reconciliation job notices a count difference within an hour; we roll back, replay from Kafka offsets, and the idempotent sink repairs the rows. Region loss: raw events are replicated to a second region by Kafka mirroring or S3 replication; the second region can recompute everything from the lakehouse, with dashboards stale for a few hours. Overload: when traffic is 5x the plan, the collector sheds low-priority impressions and keeps clicks and paid impressions.
evolution: At 1,000 events per second, one Postgres table with a counter column per (ad, minute) and a cron job is enough. At 50,000 per second (this design's average), Kafka, one Flink job and an OLAP store are needed. At 1 million per second and above, the collector layer moves to the edge (CDN workers), Kafka is split into regional clusters with local aggregation and a global merge of partial counts (sketches and sums are mergeable), and the OLAP store is sharded by advertiser. At that scale, per-event ids for dedupe become expensive; we dedupe with a Bloom filter in the collector for the first hour and use the exact batch path as the final authority.
followups: How do you guarantee a click is not billed twice if the client retries and Flink also restarts? || Three layers: the client event_id with keyed dedupe state, Flink checkpoints with a transactional sink, and an idempotent OLAP upsert keyed by window and dimensions with full counts. The batch recount from the raw log is the last check before billing.
What happens to an event that arrives 30 minutes late? || It is past the 10-minute allowed lateness, so it goes to a side output and the lakehouse. The stream row stays unchanged, and the batch recount for that hour includes the event and marks the row final. Billing uses the batch number.
One campaign gets 30 percent of all traffic. What breaks and how do you fix it? || One Kafka partition and one Flink task become hot and cause backpressure. Dedupe first by event_id, then do a two-stage aggregation: salted partial sums over a short interval, then the final sum by the real key. Also consider splitting the campaign over several partitions.
Why not count with Redis INCR for each event? || INCR is not idempotent: a retry counts twice, and a crash after INCR but before the ack loses the link between the event and the count. Redis also holds no raw log for recounts. It is fine for approximate live counters, not for billing.
How would you count unique users per campaign? || Use HyperLogLog sketches per key per minute, merge them at query time, and accept about 1 percent error. Exact counts need memory per user and cannot be merged cheaply. Billing does not use unique users.
How do you know the numbers are right? || Reconciliation: compare Kafka offset counts, raw lakehouse counts, OLAP sums and batch results every hour, within known rejects. Alert at 0.5 percent difference. Also keep fraud-removed events with reason codes so that audits can be reproduced.
How do you backfill after a bug fix? || Replay from Kafka if within 3 days, otherwise run the batch job from the lakehouse for the affected hours and overwrite the OLAP rows by key with a higher version. The idempotent key design makes this safe.
How does the design change if latency must be under 5 seconds? || Cut watermark lag and window to 5 to 10 seconds, show the live number as provisional, and accept more late-event corrections. Flink with RocksDB handles it; the OLAP store must ingest from Kafka directly (Pinot realtime tables) and not through micro-batches.

@@ rtb-bidder
title: Design a real-time bidding DSP that answers in 100 ms
category: Ads & media
level: Senior / Staff
concepts: openrtb, auction, pacing, adtech, idgraph, cachelayer, loadbalancing, circuitbreaker, redis, kafka, gc, bloom, ratelimit, featurestore, replication, backpressure, sampling, bandits
summary: A demand-side platform (DSP) buys ad impressions for advertisers. Each time a user opens a page or app, an ad exchange sends the DSP a bid request over OpenRTB and waits about 100 ms for a bid. In that time the DSP must find the user, pick the best matching campaign, predict how likely the user is to click, compute a price, check budget and frequency limits, and answer. This happens about a million times per second. The hard parts are the tail latency (a late answer is the same as no answer), spending budgets evenly while 300 servers bid in parallel without a central lock, and learning from the very small fraction of requests that actually win.
requirements: Functional requirements. Receive OpenRTB 2.x bid requests from several exchanges. For each request, either return a bid (price, creative markup, win-notice URL) or a no-bid. Apply targeting (geo, device, app or site, segment, time), brand-safety lists, frequency caps per user, and campaign budgets and pacing. Receive win notices, impression and click events and update spend and caps. Operators create and change campaigns and see spend within seconds.
Non-functional requirements. Exchanges typically give a total timeout around 100 ms (some use 120 to 200 ms) including the network; we aim for p99 under 40 ms inside our process so that network jitter does not eat the rest. Availability above 99.95 percent: a down DSP just loses spend, but exchanges also throttle bidders that time out often (typical rule: timeout rate above a few percent triggers less traffic). Spend accuracy: a campaign must not overspend its daily budget by more than about 1 to 2 percent. Fairness between campaigns: no starvation.
Assumptions. Peak 1.5 million bid requests per second, daily average 800,000 per second, spread over three regions close to the main exchanges. A request is about 2 KB of JSON (or 1 KB in Protobuf variants). We bid on about 10 percent of requests after cheap filters. Of the bids, about 20 percent win. 50,000 active line items (a line item is one targeting plus price rule inside a campaign). 300 million monthly users in our identity graph.
estimates: Inbound bandwidth. 1.5M x 2 KB = 3 GB/s = 24 Gbit/s at peak, or 8 Gbit/s per region with three regions. This is a lot of parsing: JSON parsing at about 200 MB/s per core means 3 GB/s needs 15 cores for parsing alone, so parsing cost is a real part of the budget.
Servers. One 16-core bidder instance spends about 2 ms of CPU per request that passes the filters (parse, lookups, model, serialize) and about 0.2 ms on the rest, so on average 0.5 ms per request. At 100 percent CPU it could take 16 / 0.0005 = 32,000 requests per second, but tail latency rises fast above 50 percent CPU, so we plan for 8,000 per second per instance at peak. 1,500,000 / 8,000 = about 190 instances. We need room to lose one of three regions: the other two then carry 1.5 times the load. So we provision for 190 x 1.5 = 285 instances, which we round to 300 (100 per region), and normal peak load per instance is then 5,000 per second (31 percent CPU on average, about 60 percent on a busy core). Treat this as a first estimate to be tuned by load tests.
Latency budget in the DSP (p50 / p99): read and parse 1 / 3 ms; user profile lookup in the local cache or the key-value store 1 / 5 ms; candidate retrieval from the in-memory campaign index 1 / 3 ms; features and model inference for the top 20 candidates 3 / 8 ms; auction logic, bid shading, pacing and caps 1 / 3 ms; serialize and send 0.5 / 1 ms. Sum of p99 values is 23 ms, and the sum is higher than the true p99 because tails seldom line up. We keep a 15 ms margin for garbage collection pauses and queueing.
User store. 300M users x 500 B (segments, frequency counters, last-seen) = 150 GB. With replication 2, 300 GB, fits in RAM of 6 to 10 key-value nodes per region. Reads: only the 10 percent of requests that pass cheap filters need the user (150,000 per second at peak over all regions, or 50,000 per second per region), so one small cluster handles this. Writes: win and click events update counters: about 30,000 per second.
Logs. We log every bid (150,000 per second x 300 B = 45 MB/s = 3.9 TB per day) and sample 1 percent of no-bids (13,500 per second x 600 B = 8 MB/s) so that the model can learn from requests we did not bid on. Kafka handles 55 MB/s easily with 3 replicas.
Money check. If the average winning price is 2 dollars CPM (0.002 dollars per impression), wins per second = 150,000 x 20% = 30,000, and spend per second = 30,000 x 0.002 = 60 dollars per second = 5.2 million dollars per day. A 1 percent budget error is 52,000 dollars per day, which is why pacing precision matters.
api: POST /bid/{exchange} (called by the exchange). Body: OpenRTB BidRequest with id, imp[] (banner, video, size, floor), site or app, device (ip, ua, ifa), user (id, buyeruid), regs (gdpr, ccpa flags), tmax. Returns 200 with a BidResponse (seatbid[].bid[] with price, adm or nurl, crid, adomain) or 204 for no-bid. Must return before tmax minus network time.
GET /win?bid_id=...&price=${AUCTION_PRICE}&sig=... (win notice, called by the exchange). Verifies a signature, decodes the encrypted or plain clearing price, and writes a win event. Returns 200 quickly and updates spend.
GET /imp and GET /click (tracking pixels and redirect). Record rendered impressions and clicks, update frequency counters, and feed attribution.
PUT /admin/line_items/{id}. Create or change targeting, bid cap, budget, schedule. Returns the version. Bidders see changes in less than 5 seconds through the config stream.
datamodel: Campaign index (in memory in every bidder, rebuilt from a snapshot plus a Kafka change stream): line items with targeting predicates compiled into inverted indexes: geo to bitmap of line items, device to bitmap, segment to bitmap, and so on. Retrieval is an AND of bitmaps (with a bitmap per attribute value), which takes microseconds for 50,000 items. The index is immutable per version; the bidder swaps a pointer when a new version is ready, so there are no locks on the hot path.
User store (key-value, for example Aerospike or Redis Cluster): key = user_id (hashed device id or cookie id mapped through the identity graph); value = list of segment ids, per-campaign impression counters with expiry (for frequency caps), last bid time, a few model features. Partitioned by hash of user_id, replicated 2 times. Frequency counters use a short TTL equal to the cap window (for example 24 hours).
Budget state: per line item, budget_total, spent_confirmed (from win events), spent_in_flight (estimate), and a pacing multiplier in [0, 1]. Kept in a small replicated store (Redis or a database) and pushed to bidders each second as a compact vector. Bidders hold a local token bucket per line item.
Event logs: Kafka topics bids, wins, impressions, clicks, partitioned by bid_id so that all events of one bid land together. They flow to the lakehouse for model training and reporting.
design: The request enters through an L4 load balancer (a layer that spreads TCP connections, without parsing HTTP) near the exchange. Exchanges keep long-lived HTTP keep-alive connections, so there is no TLS or TCP setup cost on the hot path. A bidder instance accepts the request on a thread-per-core or an event-loop server and parses only the fields it needs. This partial parsing, not full JSON object building, saves about half of the CPU and avoids garbage that would trigger pauses.
Step 1, cheap filters (under 100 microseconds). Reject requests that no active line item can match: blocked app bundles, unsupported ad sizes, floors above our maximum bid, regions we do not serve, and traffic types we dislike. A Bloom filter of known bad IPs and publishers is checked here. About 90 percent of requests exit here with a 204. This is the most important optimization of the whole system: we spend CPU only on the 10 percent that can produce revenue.
Step 2, user lookup. The bidder takes user.id or the device id, maps it through the identity graph to a stable internal id when available, and reads segments and frequency counters. Most reads hit a local in-process cache (hit rate about 70 percent, because the same user appears in many requests during a session); misses go to the key-value store with a hard 5 ms timeout. A timeout means we proceed with an empty profile, bid lower, or skip, and never wait.
Step 3, candidate retrieval. AND the bitmaps for geo, device, segment, daypart, and so on to get maybe 200 eligible line items. Remove those that exceed frequency caps, have no budget tokens, or fail brand-safety rules. Keep the top 20 by a cheap score (bid cap times a static quality estimate).
Step 4, prediction and bid. For those 20 candidates, the bidder computes pCTR and pCVR (probabilities of click and conversion) with a small model: a logistic regression or a small neural network of a few hundred microseconds per item, using features from the request, the user and the line item. The expected value per impression is pCTR x value_per_click (or pCVR x value_per_conversion). Pacing multiplies this value. Then bid shading lowers the bid in first-price auctions to a level estimated to win with the desired probability; this uses a learned price distribution per exchange and placement.
Step 5, respond and remember. The best bid is sent. The bidder reserves a token from the local budget bucket and writes a bid record to Kafka (asynchronous, through a lock-free queue that drops on overflow). Later, a win notice arrives; the bidder service confirms the price and updates spend. Impression and click events update frequency counters. The control loop is separate and slow: every second a pacing controller reads confirmed spend and produces new multipliers.

deepdive: Tail latency. Averages do not matter: if 1 percent of requests take over 100 ms, the exchange sees 1 percent timeouts, and some exchanges lower our traffic if that rate rises. The main sources of tail are garbage-collection pauses, a slow key-value read, a cold cache after a deploy, and CPU contention. We attack each one. For GC: use a language with predictable memory (C++, Rust, Go with small heaps) or a JVM with a modern low-pause collector (ZGC pauses are under 1 ms in typical use) and object pools so that the hot path allocates little. For the key-value store: hard timeouts (5 ms), hedged reads (send a second read to the replica after 2 ms and use the first answer), and skip the user data when it is late. For deploys: warm up the instance with replayed traffic before the load balancer sends live requests. A request queue limit sheds load when the instance is too busy: answering 204 at once is better than answering a bid at 120 ms.
Budget pacing without a central lock. A campaign with a 1,000 dollar daily budget must not spend it in the first 5 minutes (when peak traffic arrives) and must not underspend. Hundreds of bidders cannot ask one counter on every bid. The standard solution is two loops. The fast loop is local: every bidder gets a share of each line item's spend rate as a token bucket, refilled every second by the vector from the controller. The slow loop is a controller that compares confirmed spend with the target curve (usually linear in time or shaped by the expected traffic) and changes a pass-through probability or a bid multiplier, in a feedback loop like a PID controller. The risk is the delay: win notices arrive seconds late, so in-flight spend is not yet counted. The worst overshoot is about (spend rate) x (delay). For a line item spending 0.28 dollars per second (1,000 dollars per hour) with a 10-second delay, that is 2.8 dollars, which is fine; for a line item spending 100 dollars per second it is 1,000 dollars, so large budgets get a smaller safety margin and a stricter per-bidder cap.
First-price auctions and bid shading. Since about 2019 most exchanges run first-price auctions: the winner pays its own bid. If we bid our true value we pay all of it and our margin is zero. The DSP therefore estimates, per exchange and placement, a distribution of the highest competing bid and bids the amount that maximizes (value minus price) times win probability. The data for this model comes from win and loss notices and from the 1 percent no-bid sample. It is a standard trade-off between exploring prices (to learn the distribution) and exploiting the current estimate; a small share of traffic (for example 2 percent) bids at random shaded levels to keep the estimate unbiased.
Learning from selected data. We only see the results of bids we made. If the model is trained only on bid requests that passed the filters, it learns a biased world. Fixes: log a small uniform sample of all requests, including those we would not bid on, and for those reserve a small exploration budget to bid anyway. Use the logged propensity (the probability that we bid) to correct the training data. Conversions arrive days after the click, so the model trains on delayed labels and corrects for the ones still missing.
Frequency caps. "Show this user at most 3 times per day" needs a counter that all bidders see. Writes happen on impression events (30,000 per second), which is cheap, but reads happen in the hot path. A user's requests land on different bidder instances, so the counter lives in the key-value store, read together with the profile in one call. The counter can lag by a few seconds, so a user can sometimes get a 4th impression. We accept that: caps are best effort at about 1 to 3 percent overshoot, and the batch reports show it.
Identity and privacy. The user.id sent by an exchange is local to that exchange; cookies disappear in many browsers and mobile device ids need consent. The identity graph maps these ids to a stable person or household id and is built offline and pushed to the key-value store. Requests with a privacy flag (GDPR without consent, a CCPA opt-out) skip targeting by user and are bid on contextually only.
tradeoffs: In-memory campaign index in every bidder, or a central index service. Choose local memory when the data is small (50,000 line items are a few hundred MB) and updates can be a few seconds late: a lookup is microseconds, and there is no network hop. Choose a central service only if the index is too big (hundreds of millions of items, as in a retail-product ad system). You give up instant consistency: a paused campaign may still win a few bids for up to 5 seconds, which the budget cap bounds.
Language and runtime: C++/Rust or JVM or Go. Choose C++ or Rust when every millisecond counts and you can afford the hiring and development cost; you get predictable tail latency and low memory. Choose a JVM with ZGC and careful allocation when your team knows Java well and tails of 20 to 30 ms are acceptable; you give up some CPU and memory efficiency (often 1.5 to 2 times more servers). Go is a middle path with a short GC pause but less control over memory layout.
Key-value store for users: Redis, Aerospike or a local cache with async refresh. Choose Redis when data fits in RAM (150 GB does) and the team already runs it; replication is asynchronous, so a failover can lose the last second of writes, which is fine for caps. Choose Aerospike when you need hybrid memory-SSD storage and stable latency at millions of operations per second per cluster. Choose pure local caching when 5 minutes of stale segments is fine; it removes the network from the hot path but loses fresh frequency counters.
Model on the bidder, or a separate model service. Choose in-process inference for small models (logistic regression, gradient trees, small neural networks of under 1 ms) since a network call to a model server adds 1 to 3 ms and a new failure mode. Choose a separate GPU or CPU model service when the model is large (hundreds of millions of parameters), and combine it with a fast fallback model in the bidder for when the service is slow.
Bid on everything or filter hard. Bidding on more requests raises revenue a little but raises cost sharply: each bid costs CPU, logs and exchange fees. At 10 percent selectivity we cover most of the value. Choose a lower selectivity when servers are the main cost; choose higher when your campaigns are narrow and inventory is scarce.
failures: Bidder instance crash: the load balancer's health check removes it in 1 to 3 seconds; in the meantime a few hundred requests time out. Because bidders are stateless apart from caches, there is no recovery step. Key-value outage: the bidder uses a circuit breaker; after 50 percent errors in 5 seconds it stops calling the store for 10 seconds and bids with no user data (contextual bids with a lower price) or skips campaigns that need caps. Frequency caps then fail open for a short time, which is bounded by budget tokens.
Pacing controller down: bidders keep using the last vector with a decay toward zero over 5 minutes, so spend slows instead of running away. Bad campaign push: index versions are validated and canary-tested on 1 percent of bidders before the pointer is swapped everywhere; a rollback is a pointer swap back. Kafka down: log writes go into a bounded in-memory queue, then are dropped; we lose reporting data for the gap but do not slow the bid. Recovered later from win notices stored at the exchange reports (a daily reconciliation against exchange billing is a must, since the exchange's number is the one we pay).
Region loss: exchanges route to another region by DNS or anycast with a delay of 30 to 60 seconds; the remaining regions run at 50 percent more load, and we shed lowest-value traffic (by exchange and placement) when CPU passes 80 percent. Traffic spikes (a big live event): the filter threshold rises automatically so that we bid on a smaller share. A slow dependency never queues requests; it triggers a no-bid.
evolution: At 1,000 requests per second, one process with a Postgres database for campaigns and a Redis counter for budget is enough. At 100,000 per second, multiple bidders, a local campaign index, the key-value user store and a feedback pacing loop are required. At 1.5 million and beyond, regions near exchanges, hand-tuned parsers, an auction-aware bid shading model, learned bid optimization with reinforcement learning (and bandits for exploration), and a large investment in simulation (replay of logged requests against new code) are what separate winners.
followups: How do you meet 100 ms when the network alone can take 40 ms? || Place bidders in the same city as the exchange (1 to 2 ms round trip), keep connections open, and budget the process at 40 ms p99 with hard timeouts on each dependency. Late answers are dropped by the bidder itself with a 204.
How do 300 bidders share one campaign budget without a lock? || Each bidder has a local token bucket refilled each second from a controller that sees confirmed spend. The controller adjusts a pacing multiplier. Overshoot is bounded by spend rate times feedback delay, so large budgets get tighter local caps.
Why do you filter out 90 percent of traffic first? || Revenue comes from a small share of requests, but CPU cost is per request. Cheap filters (blocked apps, sizes, floors, Bloom filters) cut load 10x and leave room for the model on the rest.
What changes with first-price auctions? || You can no longer bid your value. Estimate the competing-bid distribution and bid to maximize (value minus price) times win probability, learning from win and loss data, with small exploration.
A key-value read times out at 5 ms. What do you do? || Proceed without user data or skip, and never wait. Hedge reads to a replica after 2 ms and trip a circuit breaker if errors persist. Fail open for caps for a short time, bounded by budgets.
How do you avoid selection bias in the training data? || Log a uniform sample of all requests, bid on a small random share outside the model's choice, record the bid propensity, and weight training samples by its inverse.
How would you test a new model safely? || Replay logged requests offline, then run it on 1 percent of live traffic with a hold-back group and watch spend, win rate, pCTR calibration and tail latency before wider rollout.

title: Design a top-K / trending service
category: Data & analytics
level: Senior / Staff
concepts: streamalgo, cms, windowing, kafka, flink, partitioning, scattergather, redis, powerlaws, hll, sampling, cachelayer, hashtables, bloom, watermarks, rtanalytics
summary: We build a service that answers "what is trending right now?" for hashtags, search queries or videos, globally and per country or category, with data at most 30 seconds old. It reads a stream of events (a post, a search, a view), counts items over sliding windows (last 10 minutes, last hour, last 24 hours), and returns the top K, usually 20 to 50. Counting is easy; what makes it hard is that the number of distinct items is huge, the counts follow a power law (a few items get most of the traffic, millions get one event), the window must slide without recounting, "trending" means growing faster than normal and not just big, and the answer must be cheap to serve to millions of readers.
requirements: Functional requirements. Ingest item events with a timestamp, a user and a scope (country, language, category). Return the top K trending items for a scope and a window, with a score and a count. Show a short history of an item's rank. Operators can block items (abuse, legal) within seconds. Results for 24 hours and 7 days windows are allowed to be approximate.
Non-functional requirements. Freshness: a new trend shows within 30 seconds of the spike. Read latency: p99 under 50 ms, with 50,000 reads per second at peak. Accuracy: for the top 50, the displayed rank and count are within 1 percent of the exact value for the 1-hour window; the 7-day window may be within 5 percent. Availability above 99.9 percent for reads; a stale list is acceptable during failures. Resistance to abuse: 1,000 bot accounts must not be able to push an item to the top.
Assumptions. 100,000 events per second on average, 300,000 at peak (8.6 billion per day). Each event is 100 bytes. 200 million distinct items per day, but the busiest 1,000 items get about 30 percent of all events (power-law shape, a Zipf-like distribution). 250 country scopes and 20 category scopes, so the finest key is (item, country, category).
estimates: Ingest. 100,000 / s x 100 B = 10 MB/s average, 30 MB/s at peak, about 860 GB per day raw. Kafka with replication 3 and 2 days of retention: 860 GB x 2 x 3 = 5.2 TB. We use 64 partitions, so each carries 4,700 events per second at peak.
Exact counting for the 1-hour window. Peak events per minute = 300,000 x 60 = 18M, but distinct items in a minute are far fewer than events. Guess 4 million distinct (item, country) pairs per minute, which is 62,500 per partition (4M / 64). A hash map entry costs about 40 bytes (key 16 B, count 4 B, overhead). One minute bucket per partition: 62,500 x 40 B = 2.5 MB. Sixty buckets for the hour: 150 MB per partition. A rolling total map of all distinct pairs in the hour (about 40 million pairs globally, 625,000 per partition x 40 B = 25 MB). So 175 MB per worker. This is small. Conclusion: for one hour, exact counting in memory is cheaper and more accurate than any sketch.
When exact breaks: the 7-day window. Distinct pairs over 7 days may reach 1.4 billion. At 40 B, that is 56 GB, or 0.9 GB per partition: still possible on disk-backed state (RocksDB), but updates for 100 million events per hour become disk writes. Here a Count-Min sketch is attractive. With error ε = 0.0001 of the total and failure probability δ = 1 percent: width w = e / ε = 2.718 / 0.0001 = 27,183 columns, depth d = ln(1/δ) = ln(100) = 4.6, so 5 rows. Memory: 5 x 27,183 x 4 B = 544 KB per sketch. The total count N for 7 days is 100,000 x 604,800 = 60 billion (in one sketch), so absolute error is up to ε N = 6 million events with probability 99 percent. That is too large for items with 50,000 events, but fine for top items, which have hundreds of millions. For finer error we use daily sketches (N = 8.6 billion, error 860,000) and merge exact top candidates.
Space-Saving alternative. To track the top items in a stream with m counters, the error of any count is at most N / m. With m = 100,000 counters per partition and N = 60B / 64 = 940M events per partition, error is under 9,400 events, i.e. 1 percent of a count of 940,000. Memory: 100,000 x 40 B = 4 MB per partition per window. This is the better tool to get the identity of the heavy hitters, and the sketch is better to estimate counts of chosen candidates.
Serving. A result list of 50 items for 270 scopes and 3 windows is 270 x 3 x 50 x 100 B = 4 MB in total. All fit in a single Redis node, and in each application server's memory. Reads: 50,000 per second, with a 10-second edge cache the origin sees under 100 per second.
Machines. Flink or similar workers: 64 tasks, each with 175 MB state, at 4,700 events per second per task at peak, which is light (a core can do 20,000 per second). 16 machines with 4 cores each run 4 tasks each. The rest of the pipeline (Kafka 6 brokers, Redis 3 nodes) is also small. The point: this problem needs few machines; the care is in correctness and in the ranking formula.
api: GET /v1/trending?scope=country:IN&category=music&window=1h&k=20. Returns items[] with item_id, display text, rank, count, score, rank_change and as_of (timestamp of the computation). Served from cache or Redis.
GET /v1/trending/items/{item_id}/history?scope=...&from=...&to=... . Returns rank and count per 10-minute step, from the history store.
POST /v1/events (internal, batch). Body: events[] with item_id, user_id_hash, scope fields, event_ts, type. Returns 202. In practice the product services write straight into Kafka and this API is a thin wrapper.
PUT /v1/blocklist/{item_id}. Body: reason, expiry. Takes effect in a few seconds; the item disappears from all lists and its future events are dropped.
datamodel: Kafka topic "events", keyed by item_id (hash partition). The key choice is the main design decision: all events for one item go to one partition and one worker, so that worker holds the complete count of its items. The global top K is then the merge of the 64 local top-K lists, and no counts have to be added across workers. This is a scatter-gather with a small final merge.
Worker state, per window: a ring of 60 minute buckets, each a hash map (item, scope) to count; a rolling total map; a min-heap of the best 200 candidates by score; a small HyperLogLog per candidate for distinct users (2 KB each, only for the top 200 candidates, not for all items). For the 24-hour and 7-day windows: hourly buckets and Space-Saving structures with 100,000 counters.
Baseline table (written daily by a batch job, loaded by workers): key (item_or_topic, hour_of_week), value expected events per 10 minutes. For new items the baseline is a default small constant, such as the median of the scope.
Serving store (Redis): key trend:{scope}:{window} as a sorted set of the top 100 items with scores, plus a key with as_of. The writer replaces the key atomically (write to a new key and rename). History store (Cassandra or an OLAP table): partition key (scope, day), clustering key (window_end, rank), value (item_id, count, score).
design: Events come from product services (the search backend, the post service) as Kafka messages. The producer sets the key to item_id, so the same item always goes to the same partition. Before the key is chosen, a normalizer maps variants to one id: lowercase, strip accents, map spelling variants of a hashtag to the same canonical topic id. Without normalization "#WorldCup", "#worldcup" and "#WorldCup2026" split the count and nothing trends.
Each partition is read by one worker (a Flink task or a plain consumer process). The worker first drops blocked items and duplicates (one count per user per item per 10 minutes: a user posting the same hashtag 100 times counts once; this uses a Bloom filter or a small set keyed by user and item). It adds the event to the current one-minute bucket and to the rolling total of each active window. When a minute ends, the oldest bucket for the 1-hour window is subtracted from the rolling total: each event is added once and removed once, so the cost of sliding is constant per event, not proportional to window size.
Every 10 seconds, the worker computes the scores of items whose short-window count changed, keeps the best 200 in a heap, and emits its local top-200 list to a Kafka topic "partial-tops" (or sends it to the merger by RPC). The merger (one small stateful service, with a hot standby) collects the latest list of every partition, merges them with a k-way merge, applies business filters (language, safe content, diversity rules such as at most 3 items per topic cluster) and writes the final top 50 to Redis. It also writes the list to the history store.
Ranking uses a score and not raw counts. Raw counts show "Taylor Swift" every day. Trending needs growth against the baseline. A simple, robust score is score = (c10 + a) / (b + a), where c10 is the count in the last 10 minutes, b is the expected 10-minute count for this hour of the week from the baseline table, and a is a smoothing constant (for example 50 events). This ratio is high for an item that normally has 5 events per 10 minutes and now has 5,000. The smoothing term stops items with a baseline of 0 and a count of 3 from reaching the top. We also require c10 above a minimum (for example 500 events) and at least 100 distinct users (from the HyperLogLog) before an item may enter the list.
Readers do not hit Redis directly. The API servers hold the lists in memory and refresh them every 5 seconds, and a CDN caches the response for 10 seconds. Millions of readers see the same answer, so one write per 10 seconds is enough.

deepdive: Why partition by item and not at random. If events are spread at random, every worker sees a piece of every item. To get the top K you must add the counts from all 64 workers for all items, which is a huge exchange, or you must use mergeable sketches and accept error. If events are partitioned by item, each item is counted in full on one worker. The top-K of the union of partitions is exactly the union of local top lists, so the merge needs only 64 x 200 = 12,800 numbers every 10 seconds. The cost is skew: the busiest item may receive 5 percent of the traffic (15,000 events per second at peak), which one core can handle, but one huge global event can reach 20 percent. For skew we add a first stage: each task pre-aggregates 1 second of events by (item, scope) before the shuffle, and for known hot items we spread the item over a few sub-keys (item, salt) and add the sub-counts in the merger.
Sketches and when to use them. A Count-Min sketch never under-counts. It over-counts by at most ε N with probability 1 minus δ, because hash collisions only add. Its useful form for top-K is: keep a sketch for all counts and a small heap of the best candidates; when an event arrives, increment the sketch, read the estimate, and update the heap if the estimate is above the heap minimum. The sketch is mergeable by adding arrays, so it suits time buckets and multi-machine merges. Space-Saving is a different tool: it keeps m exact-ish counters and replaces the smallest one when a new item appears, inheriting its count as an upper bound. For a Zipf-shaped stream, both find the top items well; the long tail is where they err, and we do not care about the tail. We use sketches only where exact memory is too high: long windows and high-cardinality scopes.
Sliding windows. A naive 1-hour window recounts 18 million events each time. With 60 one-minute buckets and a rolling total, each event is added when it arrives and subtracted when its bucket leaves, so the work per event is constant. The bucket size sets the freshness of the left edge: with one-minute buckets the window is 60 minutes plus up to one minute. Event time and processing time differ; we use event time with a 1-minute lateness allowance by putting a late event into its correct bucket if that bucket is still in the window and dropping it otherwise. At 10-minute windows the lateness matters more, so the baseline compare uses processing-time buckets of 10 seconds for the freshest part.
Trend score and noise. A ratio is unstable for small counts, which is why we add smoothing and a minimum count. Another standard method is a z-score against a rolling mean and variance. For stable behavior, ranks are also damped: an item must stay above the cutoff for two consecutive computations before it enters the list, and leaves only after three below it, which prevents flicker. A topic clustering step (by shared words or by an embedding) merges "#goal", "#gooool" and "Messi goal" into one cluster so that one story does not take ten slots.
Abuse. Counting distinct users per item (HyperLogLog, about 2 KB and 1 percent error), requiring a minimum distinct count, ignoring accounts younger than a day or flagged as bots, and a per-user cap per item per window (one count) make it expensive to fake a trend. A human review queue sees every item that enters the global top 10 for the first time. The blocklist is applied at the worker (drop future events) and the merger (remove from lists), so removal takes seconds even before counts decay.
tradeoffs: Exact counts or sketches. Choose exact hash maps while the state for the window fits in memory per worker (up to a few GB): they are simpler, have no error and are easier to debug. Choose Count-Min or Space-Saving when the window is long, the number of scopes multiplies the keys, or the worker memory would exceed the budget. You give up exact counts for the tail and you must explain the error to the product team: the top 50 are still right.
Partition by item or by random key. Choose partition by item when you need exact per-item counts and a cheap merge, and you can handle skew with pre-aggregation. Choose random or round-robin partitioning with mergeable sketches when a handful of items dominates and you cannot split them, or when the same stream feeds many other jobs that prefer an even spread. The price is approximate counts and a larger merge.
Stream processor or custom service. Choose Flink or Kafka Streams when you already operate them: they give checkpoints, event time and restarts for free. Choose a small custom consumer when the logic is this simple and the team prefers a plain process with state rebuilt by replaying Kafka (2 hours of replay at 4,700 per second per partition is quick). The custom service is easier to run on a laptop; the framework wins when you add more windows, joins and exactly-once sinks.
Count by volume, by growth, or by unique users. Volume is stable and good for "popular". Growth against a baseline is better for "trending", but needs baseline data and tuning. Distinct users resist spam and show breadth, but cost more memory. A product usually shows a blend: filter by distinct users, rank by growth score, and use volume as a tie-break.
Redis or an in-process cache for serving. Redis is easy and shared, and all API servers see the same list. An in-process copy removes one network hop and survives a Redis outage for as long as the process lives. We use both: the process refreshes from Redis and keeps the last good list.
failures: Worker crash: the process restarts and rebuilds its bucket ring by replaying the last hour from Kafka (4,700 events per second x 3,600 = 17 million events per partition, about 1 to 2 minutes at 150,000 per second replay speed). Until then its items are missing from the merge; the merger keeps the last partial list of that partition for up to 2 minutes and then marks the result "degraded". With Flink, checkpoints of state every minute shorten the recovery to a few seconds.
Merger crash: a standby takes over (leader election with a lease), and since the merger holds no state except the latest partial lists, it reads them from the Kafka topic. Redis outage: the API servers keep serving their last in-memory list and mark it stale after 5 minutes. Kafka lag: the worker falls behind during a spike; the list is older than 30 seconds, and an alert fires on lag over 60 seconds. A bad deploy of the score formula is caught by comparing the new top 50 with the old one offline on yesterday's data (overlap should be above 70 percent) and by a canary scope (one small country).
Event storm: during a global event the traffic is 3 to 5 times peak. Workers pre-aggregate and the Kafka partitions grow in lag, but the merge only needs counts, so results stay correct and a bit late. Poison data (an item id of 10 MB, a bot flood with millions of fake ids) is protected by input limits (id length 100 characters) and by Space-Saving, which keeps memory bounded even for an attack with unlimited distinct ids.
evolution: At a few hundred events per second, one Postgres table with an index on (scope, window, count) updated by a cron job is enough, or a single Redis sorted set with ZINCRBY per event. At 100,000 per second, the partitioned workers above with exact in-memory counting are right. At 10 million events per second (a global social network), exact counting by item still works if you add a pre-aggregation tier near the edge (each region aggregates to 10-second partial counts), but state for long windows and per-user personalization (trends for people like you) moves to sketches, embeddings for topic clustering, and a feature store for the ranker.
followups: Why does the merge of 64 local top-K lists give the correct global top-K? || Because each item lives in exactly one partition, its local count is its global count. An item in the global top K must be in the top K of its own partition, so the union of local lists contains it.
Why not ZINCRBY on one Redis sorted set for every event? || It works up to maybe 50,000 to 100,000 events per second on one core, then the single-threaded node and the single hot key become the limit. It has no sliding window (needs one set per bucket and a union), and a crash loses recent counts.
How do you make a sliding window cheap? || Use time buckets (for example 60 one-minute buckets) and a rolling total: add on arrival, subtract the bucket that leaves. Work per event is constant, and memory is buckets times distinct keys.
What is the error of Count-Min and how do you choose its size? || It over-counts by at most ε times the total stream size with probability 1 minus δ. Width is e over ε, depth is ln(1/δ). Choose ε much smaller than the count of the K-th item divided by the total.
How do you stop a bot network from pushing a hashtag to the top? || Count distinct users with HyperLogLog and require a minimum, apply one count per user per window, ignore young or flagged accounts, and send first-time global top entries to human review.
How do you handle one item receiving 20 percent of all events? || Pre-aggregate by one second before the shuffle, split the hot item into salted sub-keys across several workers, and add the sub-counts in the merger. The final list stays exact.
Why a growth score instead of raw counts? || Raw counts show items that are always popular. The ratio of the recent count to a baseline for the same hour of the week picks out unusual growth. Smoothing and a minimum count prevent noise from tiny numbers.
How would you personalize trends? || Keep global candidates from this pipeline (top 500) and re-rank them per user or per cohort with a model that uses interest features from a feature store. Do not count per user; it multiplies state by the number of users.

title: Design a real-time leaderboard
category: Web & product

concepts: redis, trees, partitioning, scattergather, replication, wal, kafka, idempotence, cachelayer, ratelimit, sorting, rangeq, consmodels, dynamodb, hashtables
summary: We build the ranking service of an online game with 50 million daily players. Players finish matches and their scores change. The service must show the top 100, show any player's exact rank, and show the players just above and below them, within a second of the score change. There are all-time, weekly and daily boards, per-country boards and friend boards. Ranking looks simple: sort by score. The difficulty is that a rank is a global fact. Inserting one score changes the rank of millions of others, so we need a data structure that gives rank in O(log N) and a sharding plan that keeps this property when one machine is not enough.
requirements: Functional requirements. Submit a score for a player on a board. Get the top K. Get the rank and score of a player. Get the neighbors of a player (for example 5 above and 5 below). Get a friend board for a player (rank among the friends). Boards: all-time (best score), season (about 90 days), weekly, daily, per country. Ties are broken in favor of the player who reached the score first.
Non-functional requirements. A new score is visible in the board within 1 second. Rank queries have p99 under 20 ms. Writes survive the loss of a cache node: no accepted score may be lost. Cheating is limited: scores come from the game server, never from the client. Availability above 99.95 percent for reads. The weekly reset must not need a mass delete.
Assumptions. 100 million registered players, 50 million daily active, each finishing 20 matches per day. Each match produces a score update for 5 boards (all-time, season, weekly, daily, country). Rank views: each daily player opens the leaderboard 10 times per day.
estimates: Writes. 50M x 20 = 1 billion match results per day = 11,600 per second on average; peak is 3x = 35,000 per second. Each result updates 5 boards, so 175,000 board writes per second at peak. Many of them are no-ops: the all-time board keeps the best score, and most matches are not a new best, so assume 30 percent change the board, giving about 55,000 effective writes per second.
Reads. 50M x 10 = 500M views per day = 5,800 per second on average, 17,000 at peak. The top-100 view is the same for everybody, so a cache with a 1 second time-to-live serves most of them. About 40 percent need a personal rank and neighbors: about 7,000 per second at peak.
Memory. A Redis sorted set stores each member in a hash table and in a skip list. Per member: key string of 10 bytes, score 8 bytes, skip list node about 50 bytes (with an average of 1.33 forward pointers), hash table entry about 30 bytes; about 100 bytes in total with allocator overhead. All-time board: 100M x 100 B = 10 GB. Season: 60M x 100 B = 6 GB. Weekly: 40M x 100 B = 4 GB. Daily: 30M x 100 B = 3 GB. Country boards together hold about the same members as the global board: 10 GB. Total: about 33 GB, plus replicas (x2) = 66 GB. This fits in memory of a few machines.
CPU. A Redis node executes commands on one thread. ZADD in a set of 10 million members costs about 3 to 10 microseconds, so one node can do roughly 100,000 operations per second with pipelining. 55,000 writes plus 20,000 read operations (each rank view needs ZREVRANK and ZREVRANGE) at peak is close to the limit of one node, so we want at least 8 shards to keep each node near 15 percent busy and to keep latency low.
Event log. A score event is about 100 bytes: 35,000 per second x 100 B = 3.5 MB/s, or 300 GB per day raw. Kept for 7 days in Kafka: 2 TB with replication x3 = 6 TB. Score table in the database: 100M rows x 3 boards of state x 100 B = 30 GB.
api: POST /v1/boards/{board}/scores. Body: player_id, match_id, score, game server signature. Returns the new best score and the new rank (optional, approximate). The match_id makes the call idempotent: a retry changes nothing.
GET /v1/boards/{board}/top?k=100&offset=0. Returns players with rank, score and display name. Cached for 1 second.
GET /v1/boards/{board}/players/{id}. Returns score and exact rank (or a percentile for ranks beyond 1 million).
GET /v1/boards/{board}/players/{id}/neighbors?above=5&below=5. Returns the players around the given player.
GET /v1/boards/{board}/friends?player_id=...&limit=50. Returns the friends' scores sorted, with the caller's position.
datamodel: Source of truth (DynamoDB or Cassandra): table scores with partition key (board_id, player_id) and attributes best_score, achieved_at, version. A direct lookup by player. Kafka topic score-events (key = player_id, so all events of one player are in order) with match_id, board ids, score, ts.
Cache and ranking structure (Redis sorted sets): key lb:{board_id}:{period_id}:{shard}, member = player_id, score = a packed number described below. The period_id is part of the name: lb:game1:weekly:2026-W43. A new week uses a new key, and the old one expires with a TTL of 14 days. No mass delete ever happens.
Packed score. A Redis score is a 64-bit double with 53 bits of exact integer precision. We use score_packed = game_score x 2^23 + (T_MAX - seconds_since_period_start). For a daily board seconds are under 2^17; for a season of 90 days, 7.8 million seconds fit in 2^23 = 8.4 million. So game_score can use 30 bits (about 1 billion). For the all-time board the time part counts in days since launch instead of seconds. A higher packed value means a better rank, and among equal game scores the earlier achievement has the larger time part and ranks first.
Friend list: stored in a social graph service as a set of ids per player (up to 500 friends). No per-player board is stored.
Histogram for far ranks: table score_hist with key (board_id, bucket) and a count, where buckets are score ranges (for example 1,000 buckets that follow the score distribution). It supports percentile queries for players below rank 1 million.
design: A score submission comes from the game server (not from the phone), with a signature. The score service checks the signature and the rate limit (a player can send at most one result every 10 seconds on average), and writes the event to Kafka with the match_id. Kafka is the log: the write is durable before we answer 202. Consumers of that topic do the work, so a slow Redis never blocks the game server.
The updater consumes score events. For each event and each board it reads the player's current best in the database (or from a local cache), decides whether the board changes (best score is higher, or total is larger for a cumulative board), and writes the new absolute value to the database with a conditional update (version check). Only after that does it write to Redis with ZADD of the new packed score. This is idempotent: running the same event again writes the same number. We never use ZINCRBY on Redis for money-like or important state, because a repeated event would add twice.
The Redis tier is split into shards by hash of player_id: shard = hash(player_id) mod 16. Each shard has one primary and one replica in another zone. The score service knows the shard map from a small configuration service. A board of 100 million players is thus 16 sorted sets of 6 million members. Insert and rank cost O(log N) with N = 6M, about 23 levels, so each stays in microseconds.
Reading the top 100. The API asks all 16 shards for their top 100 (ZREVRANGE 0 99 WITHSCORES) in parallel, merges 1,600 entries in memory, and keeps the best 100. The global top 100 is always inside the union of shard top lists. This scatter-gather costs one round trip (all calls in parallel) and takes 2 to 5 ms. The result is cached for 1 second in the API servers and in a CDN, so 17,000 reads per second turn into about 1 per second per board per region.
Reading one player's rank. The API reads the player's packed score s from his own shard (ZSCORE), then asks all 16 shards "how many members have a score greater than s" with ZCOUNT (s, +inf). The rank is 1 plus the sum. Each ZCOUNT is O(log N) because the skip list is augmented with span counts. The cost is 16 parallel calls, about 3 ms in total. Neighbors: after finding the rank we need the players with packed scores just above and below s. We take the 5 next scores above and 5 below from each shard (ZRANGEBYSCORE with LIMIT), merge the 16 x 10 entries and select the right 10. The answer is exact.
Friend boards. The API fetches the friend ids from the graph service, reads their scores from Redis in a pipeline (ZMSCORE per shard, grouped by shard), sorts at most 500 entries in memory, and returns the top page and the caller's position. No board per player is needed, and it is always fresh.

deepdive: Why rank is O(log N). A plain sorted array gives rank by binary search, but insertion costs O(N). A balanced tree gives O(log N) for both if every node stores the size of its subtree: rank is the sum of the sizes of the left subtrees on the path. Redis uses a skip list whose forward pointers store spans (how many nodes they skip), which gives the same rank in expected O(log N) with a simpler implementation. This is the central point: the structure answers "how many items are greater than x" without looking at them. A SQL database with an index on score can answer ORDER BY score LIMIT 10 fast, but "rank of this player" is COUNT(*) WHERE score > x, which walks millions of index entries unless the B-tree stores counts, which most do not. At 100,000 rows this is fine; at 100 million rows, it is not.
Sharding and global rank. We shard by player hash because it spreads writes evenly and keeps each player's data in one place. The price is that every global rank query touches all shards. With 16 shards this is acceptable: 16 parallel calls, each in microseconds, and the latency is the slowest of 16 (so tail latency is the risk; use a 10 ms deadline and a hedged retry to the replica). The alternative is range sharding by score: shard 0 holds scores above 10,000, shard 1 scores 5,000 to 10,000, and so on. A rank then needs only the counts of the shard totals above (kept in a small table) plus one ZREVRANK in one shard. But player scores move between shards (delete and insert across nodes), the top shard is hot because the elite play most and win most, and the score distribution changes every season, so boundaries must move. Choose range sharding only for a very large board with a stable distribution.
Approximate rank for the long tail. Nobody cares if their rank is 4,812,331 or 4,812,350. For ranks beyond the first 100,000 we can show a percentile ("top 12 percent") from the score histogram. The histogram has one counter per score bucket, updated by the updater with increment on the old bucket and decrement on the new, and read in a single call. This removes the scatter-gather from 95 percent of rank queries and also hides the small inconsistency among shards.
Consistency. Redis replication is asynchronous, so a failover can lose the last few hundred milliseconds of writes. The source of truth is the database and the Kafka log. After a failover, the updater replays events from a saved offset (for example the last 60 seconds). Because ZADD with the absolute value is idempotent, the replay repairs the board with no double counting. If a whole shard is lost, we rebuild it from the database: scan the scores table by shard and bulk-load it with ZADD in pipelines at about 500,000 per second, so 6 million members load in about 12 seconds plus the scan time (a few minutes).
Ties and cheating. Packing the time into the score gives a total order and a stable rank. Cheating is controlled outside the leaderboard: signatures from game servers, plausibility checks (score per minute limit), and a removal API that deletes the member from Redis and writes a tombstone to the database. A nightly job compares Redis with the database for mismatches.
Period boards. The weekly board is not reset. A new key is created on Monday 00:00 by name. Updates go to the keys of the current period. Old keys expire. Readers of a board just after midnight see the new, empty board; and to avoid an empty top list for a few minutes, the product shows the previous week's winners as a banner.
tradeoffs: Redis sorted sets or a SQL table with an index. Choose Redis when you need rank queries at tens of thousands per second and the board fits in memory (tens of GB). Choose a SQL database (Postgres) when the board is under a few million rows, you need joins and transactions, or the read rate is low: ORDER BY with an index and COUNT for rank are enough, and you avoid an extra system. You give up fast rank at large size, and in Redis you give up durability on its own, so you need the log and the table anyway.
Exact rank or approximate rank. Choose exact when the board is small or the competition is tight (the top 10,000, tournaments with prizes). Choose percentile and histograms beyond that point to save 16 round trips on most queries. You give up the false precision no one needs.
Hash shards or range shards. Choose hash shards when the write load is evenly spread and the top of the board is small (the cost of scatter-gather on 16 nodes is acceptable). Choose range shards when ranks are queried far more often than scores change and the shard count would be large (100 or more), because the scatter-gather would then dominate. In both designs keep a clear way to re-shard: a shard map version in the config service and dual writes during a move.
Push or pull for friend boards. Pull (compute at read time from the friends' scores) is the right default up to a few hundred friends, with no storage and always correct. Push (a board per player updated for each friend event) multiplies writes by the friend count (500 times 55,000 per second) and is never worth it.
Update on every match or batched. Choose every match for tournaments and live events: one-second freshness is the feature. Choose batching (collapse updates for one player over 5 seconds in the updater) if the load is too high; it cuts Redis writes by 2 to 3 times for active players and costs only a few seconds of delay.
failures: Redis primary failure: the replica is promoted by a sentinel or by the managed service in 10 to 30 seconds; writes in this period wait in Kafka (the updater retries), and reads served by the replica keep working. Up to 1 second of acknowledged writes in Redis may be lost, which the replay of the Kafka tail repairs. A hot shard: hashing makes this rare; a famous streamer who plays a lot is a single member and does not make a shard hot.
Updater lag: Kafka absorbs bursts, and the board is late by the lag; an alert fires when lag is above 5 seconds. Database outage: the updater pauses (it needs the conditional write) and the boards go stale but remain readable; we do not skip the database to write only into Redis, since this would make Redis the only copy. Zone loss: primaries and replicas are in different zones; a quorum of the config service decides the shard map. Region loss: we replay the Kafka mirror and the database replica in another region; leaderboards are usually allowed to be rebuilt in minutes.
Bad deploy: a bug in score packing would corrupt orders. To protect, the updater writes new boards under a new version suffix (lb:...:v2) in shadow mode, a checker compares top 1,000 results of both, and then the API switches. The old key remains for rollback. Cache stampede on the top-100 view after a restart: the API uses request coalescing (one refresh per key, others wait) and a stale-while-revalidate TTL.
evolution: At 10,000 players, a single Postgres table with an index and COUNT for rank is enough. At 1 million players, one Redis node with one sorted set per board gives O(log N) rank and zero sharding. At 100 million players and 175,000 board writes per second, shard by player into 16 or more sorted sets, keep a durable log and table, use percentile for the tail, and cache the top view. At a billion players or at event peaks of 10 million concurrent users, move to hierarchical boards (region, then global), approximate counting by sampling and histograms for most ranks, and exact structures only for the top 100,000.
followups: How do you get the rank of a player in a board of 100 million? || A structure that stores counts per subtree or span, such as a Redis skip list, answers rank in O(log N). With 16 hash shards, sum 16 parallel ZCOUNT results for scores above the player's score and add 1.
Why not use a SQL ORDER BY with an index? || It works to a few million rows. Rank is a COUNT of higher scores, which walks index entries unless the index stores subtree counts. At 100 million rows and thousands of queries per second it is too slow.
How do you make score updates safe to retry? || Use a match_id for dedupe, compute the new absolute score in the source-of-truth table with a conditional write, and ZADD the absolute value. Never ZINCRBY from an event that can be delivered twice.
How do you break ties fairly? || Pack the time of achievement into the low bits of the score so that earlier equals better. A double has 53 exact bits: 30 for score and 23 for seconds since the period start in this design.
What happens if the Redis primary dies right after acknowledging a write? || The replica may not have it. The Kafka log and the database still do. After failover, the updater replays from a safe offset, and idempotent ZADD restores the exact state.
How do you do a weekly reset without downtime? || Put the period in the key name. A new week is a new key, the old one gets a TTL. There is no mass delete and no lock.
How would you support a friends leaderboard? || Pull at read time: get the friend ids, fetch scores in a pipeline, sort in memory. Up to a few hundred friends this is cheap and always fresh.
When would you shard by score range? || When rank reads dominate, the shard count is large and the score distribution is stable. Rank becomes one local ZREVRANK plus a lookup of shard totals above it. You must handle score movement between shards and hot top shards.

View a profile page with all posts of one account. Like and comment. Search accounts and tags (out of scope here except for the data model). Notifications are out of scope.
Non-functional requirements. Feed first page in under 500 ms at p99 (excluding image bytes). Image first byte from the CDN under 100 ms in most regions. Durability: an uploaded photo is never lost (11 nines of durability for the object store). Availability above 99.95 percent for reads; uploads may be slightly lower. A new post appears in followers' feeds within about 10 seconds for normal accounts. Eventual consistency is acceptable for likes and counts; it is not acceptable to show a deleted or private photo after the delete is confirmed (within a minute).
Assumptions. 500 million daily active users (DAU), 1 billion registered. 100 million photo uploads per day. Each user opens the feed 10 times a day and views 150 photos per day. An average user follows 200 accounts; the median account has 150 followers, but a few thousand accounts have more than 1 million followers. The original photo is 2 MB on average.
estimates: Uploads. 100,000,000 / 86,400 = 1,160 uploads per second on average and 3,500 at peak (3x). At 2 MB each, upload bandwidth at peak is 3,500 x 2 MB = 7 GB/s = 56 Gbit/s, spread over many regions.
Storage. Each photo is stored as the original (2 MB) plus about 5 resized variants (150, 320, 640, 1080 pixels wide and a blurred placeholder; sizes 5, 25, 70, 200 and 1 KB, sum about 0.3 MB; in modern formats such as WebP or AVIF, maybe 0.5 MB with two formats). Total about 2.5 MB. Per day 100M x 2.5 MB = 250 TB. Per year 250 TB x 365 = 91 PB. With erasure coding (a 10+4 scheme costs 1.4x instead of 3x for replication), physical storage is 91 x 1.4 = about 128 PB per year. Compare with 3x replication: 273 PB. That is why a large photo store uses erasure coding for data older than a few days and keeps hot data replicated.
Image reads. 500M x 150 = 75 billion image views per day = 868,000 per second on average and about 2.6 million at peak. A typical feed view uses the 640 px variant at roughly 70 KB (with the blurred 1 KB placeholder first). 868,000 x 70 KB = 61 GB/s = 486 Gbit/s on average and 1.5 Tbit/s at peak. This traffic is served by a CDN. With a hit ratio of 95 percent, origin traffic is 5 percent: 24 Gbit/s on average, 75 Gbit/s at peak.
Feed requests. 500M x 10 = 5 billion feed loads per day = 58,000 per second on average and 175,000 at peak. Each returns 20 posts of metadata (about 1 KB each, 20 KB total).
Metadata. A photo row is about 1 KB (ids, owner, caption, size, time, flags, counts). 100M x 1 KB = 100 GB per day = 36 TB per year, plus likes and comments: if the average photo gets 20 likes (16 bytes each) and 2 comments (200 B each), that is 100M x (320 + 400) = 72 GB per day. The follow graph: 1 billion users x 200 follows = 200 billion edges x 16 B = 3.2 TB, stored twice (forward and reverse index) = 6.4 TB.
Feed fan-out. Writing each new post into the followers' feed lists: 100M posts x 200 followers (the mean over normal accounts; celebrities handled separately) = 20 billion list insertions per day = 231,000 per second. A feed list entry is a post id (8 bytes). Cache of the last 500 entries for 500M active users: 500M x 500 x 8 B = 2 TB, held in Redis across about 40 nodes of 64 GB with replicas. This is small compared with the images.
api: POST /v1/media/uploads. Body: size, content type, checksum. Returns an upload_id and a pre-signed URL (or several for chunked upload). The client sends the bytes straight to the object store.
POST /v1/posts. Body: upload_id, caption, location, idempotency key. Returns post_id. The post becomes visible after the image pipeline finishes (usually under 5 seconds).
GET /v1/feed?cursor=... . Returns up to 20 posts (post_id, owner, caption, image URLs per size, like count, whether I liked) and a next cursor. Cursor-based, not page-number based, because the list changes while the user reads.
GET /v1/users/{id}/posts?cursor=... . Profile grid, newest first.
PUT /v1/follows/{user_id} and DELETE /v1/follows/{user_id}. PUT /v1/posts/{id}/like. POST /v1/posts/{id}/comments.
datamodel: Post ids are 64 bits and time-sorted: 41 bits of milliseconds since a custom epoch, 13 bits of logical shard id, 10 bits of sequence per shard per millisecond. Sorting by id sorts by time, and the shard id inside the id tells where the row lives with no lookup.
Posts table (sharded MySQL or Postgres, or Cassandra): key post_id, columns owner_id, caption, created_at, media keys, state (processing, ready, deleted), counts. Shard by owner_id (so a profile page is one shard); the id carries the shard. Secondary table user_posts: partition key owner_id, clustering key post_id DESC. A profile page is one range read.
Follow graph: two tables, following(user_id, followee_id) and followers(user_id, follower_id), both sharded by the first column, each row 16 bytes. Two copies make both directions fast to read; they are updated together by a small transaction or by a log with retry.
Feed store (Redis): key feed:{user_id}, a list or sorted set of up to 500 post ids with the score = post id. Likes: table likes(post_id, user_id) in Cassandra, partition by post_id; counts in Redis counters flushed to the post row every few seconds. Comments: partition by post_id, clustering by comment_id.
Object store (S3-like): key = media/{shard}/{hash prefix}/{post_id}/{variant}.webp. Random hash prefixes spread requests over the object store partitions.
design: Upload path. All client traffic first reaches a regional load balancer, which spreads connections over stateless API servers and applies rate limits per user and per IP. The client asks for an upload slot and gets a pre-signed URL. It uploads the bytes directly to the object store in chunks (resumable after a bad mobile connection), so app servers never carry image bytes. When the upload completes, the object store emits an event to Kafka. The client then calls POST /v1/posts with the upload id and the caption. The post row is written with state=processing, and the API answers at once with the post id.
Image pipeline. Workers read upload events from the queue (Kafka or a message queue) and process each image: verify that it is a valid image, strip location data (EXIF) unless the user chose to share it, scan against known illegal-content hashes and run classifiers for policy, create the variants in two formats, compute a small blurred placeholder, and write them to the object store. Then the worker sets state=ready and emits a post_ready event. The workers are stateless and scale with queue depth. A failed job is retried with backoff; after 5 failures it goes to a dead-letter queue.
Fan-out. A fan-out service reads post_ready events. For an account with fewer than 100,000 followers, it reads the follower list in pages and inserts the post id into each follower's feed list in Redis (LPUSH, then trim to 500). Only active followers (seen in the last 30 days, about 50 percent) get an entry; inactive users get their feed rebuilt when they return. For an account with more than 100,000 followers (a celebrity), the post is not pushed. Instead it is marked in a small "celebrity posts" index, and the readers merge it at read time. This hybrid avoids a single post causing 100 million writes.
Feed read. The feed service gets the user's precomputed list of post ids from Redis (one call, about 1 ms). It also fetches the recent posts of the celebrities the user follows (the user follows about 5 such accounts on average; each has a small list of recent post ids in cache). It merges ids, loads the post objects from the cache (a multi-get with 95 percent hit rate, falling back to the posts store), filters by privacy and deletion, and sends the candidates to a ranking model. The ranker scores about 500 candidates with features (author affinity, recency, past engagement), takes the top 20, and the service returns them with image URLs. All steps run in parallel where possible; the target is 150 ms for the service and well under 500 ms for the whole request.
Image delivery. Image URLs point to the CDN, with a signed, expiring token for private accounts. The CDN edge serves from memory or SSD. A miss goes to a regional shield cache and then to the object store. The client picks the variant by screen width and uses the blurred placeholder while loading. Immutable object names (the post id and variant never change) allow very long cache times (one year), so purges are rare; a delete is done by blocking the key at the CDN and checking access at the origin.
Discovery (Explore) uses a separate path: user and item embeddings from a recommender, candidate retrieval by nearest-neighbor search over millions of items, and a heavier ranker. We keep it as one box in the diagram.

deepdive: Fan-out on write or on read. This is the central design question. Fan-out on write (push) pays at post time: 200 list inserts for the average account, and then reading a feed is one cheap call. Fan-out on read (pull) pays at view time: the service must fetch the recent posts of each of the 200 followed accounts and merge them, 5 billion times a day. With the numbers above, push costs 231,000 inserts per second for all posts, and pull would cost 58,000 feed loads per second x 200 lookups = 11.6 million lookups per second at average load. Push is about 50 times cheaper in total work because reads are 50 times more frequent than posts. The exception is the account with 100 million followers: one push is 100 million writes and takes minutes, and the late followers see the post long after the early ones. For those accounts we use pull and merge at read time. The threshold (100,000 followers in our design) is tuned by looking at the cost curve: above it, push work per post exceeds the pull work added per reader.
Inactive users. About half of the registered feeds belong to users who will not return today. Pushing to them wastes half of the writes and memory. We push only to users who were active in the last 30 days, and when an inactive user returns, we rebuild the feed with a pull (a one-time cost of a few hundred ms, which we hide behind a loading screen), then switch to push.
Image storage cost. Photos are the largest cost. First, the newest photos are the hottest: more than 80 percent of views are of photos under 7 days old. So we keep recent originals and variants on replicated fast storage, and older ones on erasure-coded storage with 1.4x overhead. Second, we store the original once and generate variants from it, and for very old, cold photos we may delete the largest variants and recreate them on demand. Third, modern formats such as AVIF save 30 to 50 percent against JPEG at the same visual quality, at the cost of more encoding CPU, and we encode only the sizes that clients actually request. Fourth, deduplication by perceptual hash saves little in photo-sharing (people rarely upload the same file), so we do not do it for storage; we use it for abuse detection.
CDN and cache hit ratio. At 1.5 Tbit/s peak, a 1 percent change in hit ratio is 15 Gbit/s of origin traffic. We shape the hit ratio by choosing a small set of fixed sizes (not arbitrary widths), by a shield layer that merges misses from many edges, by immutable URLs, and by pre-warming the first image of each post in the edge nearest to the author's followers for celebrity posts (a pre-push). The long tail of old photos will miss: they are viewed rarely and from the origin at 100 to 200 ms.
Counters and hot objects. A photo from a celebrity gets 1 million likes in a few minutes, or about 5,000 likes per second on one row. A relational row cannot take 5,000 updates per second with row locks. We write the like event to a log, keep the count in Redis (INCR on a key sharded across 16 sub-keys for hot posts), and flush the sum to the database every few seconds. The user's own "liked" flag is read from the likes table or a per-user Bloom filter plus exact check, so the heart icon is right even if the count lags.
Privacy, deletes and consistency. A delete must remove the photo from feeds and from the CDN. Feeds hold only ids, so the feed service filters on the post state at read time (a fast multi-get of states from the cache), which makes a delete take effect within the cache TTL of a few seconds. The CDN path is protected by signed URLs that expire after a day and by an origin check for private accounts. The bytes are deleted from the object store by a background job after a delay (30 days for the recovery window), and replicas are removed with it. Likes and counts are eventually consistent; the post state and the follow graph are read from the primary or from a read replica with a short lag, and the feed service reads the follow edges again for private accounts when a follow is removed.
Ids and sharding. Time-sorted ids from the shard embed the shard id, so a post id tells which database shard owns it. We start with thousands of logical shards mapped to a few dozen physical machines. When a machine is full, we move logical shards by copy and switch, and no id changes. This is an application of consistent hashing ideas with a fixed number of virtual buckets.
tradeoffs: Push, pull or hybrid feed. Choose push when most accounts have under about 10,000 followers and reads dominate (here 50 to 1). Choose pull when follower counts are huge and uneven, or when the feed depends heavily on real-time ranking that changes at every read. Choose hybrid (our design) when both kinds of accounts exist. You give up simplicity: two code paths, one threshold, and testing for users near the threshold.
Relational database or wide-column store for metadata. Choose sharded MySQL or Postgres when you need transactions for a few operations (follow with counters), secondary indexes, and your team knows how to run it; it works at this scale with logical shards (it did for the early large photo networks). Choose Cassandra or DynamoDB for the time-ordered, write-heavy tables such as likes, comments and feed history: you get linear scaling, simple replication across regions, and no resharding project, and you give up joins and ad-hoc queries.
Store originals forever, or compress and delete. Choose to keep all originals when the product promises it and the storage cost (128 PB a year) is part of the business. Choose tiering (cold, erasure coded, maybe infrequent-access object classes) when most photos are never seen after a week. Deleting originals saves money but is irreversible and hurts later re-encoding when new formats appear.
Rank the feed or show it by time. A time-ordered feed is simple and cheap: the cached list is the answer. A ranked feed needs a candidate set, features and a model call on every load (about 500 candidates per request, 175,000 requests per second at peak = 87 million candidate scorings per second) and costs more machines, but it raises time spent. Most products rank and offer a "following, newest first" option as a cheap alternative.
Upload through the app servers or direct to storage. Direct upload with pre-signed URLs removes 7 GB/s of traffic from the API tier and gives resumable uploads; the price is a more complex flow (the post may reference an object that does not exist yet) and the need to validate the file after upload, not before.
failures: Object store region or zone problem: durability comes from erasure coding across at least three zones, so one zone loss only slows reads. For region loss, new uploads are replicated asynchronously to a second region (lag of seconds); a few photos uploaded in the last seconds can be lost in a hard region failure, and the app keeps the local copy until the server confirms durable replication. Image worker crash: the Kafka offset is not committed, so another worker redoes the job; writing the same variant keys twice is harmless. Poison images (a file that crashes the decoder) are caught by timeouts and a dead-letter queue.
Redis feed cache loss: lists are rebuildable. A lost node means its users get a pull-based rebuild from the follow graph and the user_posts tables on their next open; to avoid a stampede on the database, rebuilds are rate limited and the feed service returns a partial feed (the last 50 posts from top 20 accounts) first. Database shard failure: replicas promote in tens of seconds; the profiles on that shard are unavailable for that time, but feeds from cache keep working (posts in the cache are served even if the primary is down).
Fan-out backlog: a celebrity posting during a burst can fill the queue. The fan-out workers are prioritized by account size, so small accounts keep their latency, and big ones use pull. CDN problem: multi-CDN or fallback to another provider by DNS; origin protection by rate limiting and request collapsing so that a CDN outage does not send 1.5 Tbit/s to the origin. Overload: the feed service serves the cached ranked list (stale by minutes) and skips ranking when latency goes over budget. Bad deploy: staged rollout by region with automatic rollback on error rate and latency.
evolution: At 10,000 users, one Postgres database, one server, images in an object store behind a CDN, and the feed as a SQL query joining follows and posts (ORDER BY id DESC LIMIT 20) are enough. At 1 million users, add read replicas, a cache for post objects, and an asynchronous image pipeline. At 100 million users, shard the metadata, add push fan-out with Redis lists, and add a ranker. At a billion users, add the celebrity hybrid, erasure-coded tiers, multi-region active-active reads, and machine-learning systems for recommendation and safety, which become the largest teams.
followups: Why is the feed usually built with fan-out on write? || Reads outnumber posts by about 50 to 1, so doing 200 inserts once per post is cheaper than 200 lookups per feed load. Feed reads become one cache call.
How do you handle an account with 100 million followers? || Do not push. Store its posts in a small recent-posts index and merge them into each reader's feed at read time. The follower threshold is tuned where push cost per post exceeds the added pull cost.
Why upload directly to object storage? || It keeps 7 GB/s of image bytes off the API servers, allows resumable chunked uploads, and scales with the storage service. The API only issues short-lived signed URLs and records metadata.
How do you store 91 PB a year cheaply? || Erasure coding (a 10+4 scheme costs 1.4x, versus 3x for replication), tiering by age (most views are of the newest photos), efficient formats, and creating variants on demand for old photos.
How do you make deleted photos disappear quickly? || Feeds hold ids only, and the feed service checks state at read time against a cache with a short TTL. CDN URLs are signed and expire, and private content is checked at the origin. Bytes are removed later by a background job.
How do you handle like counts for a viral photo? || Write likes to a log, count in sharded Redis counters (many sub-keys per hot post), and flush totals to the database every few seconds. Keep the user's own like state exact in a separate store.
How do you generate IDs across shards? || Time-sorted 64-bit ids with timestamp, logical shard id and a per-shard sequence, as in the Instagram approach. They sort by time and tell the shard of a row with no lookup.
How would you add Explore recommendations? || Train user and item embeddings, retrieve candidates by approximate nearest-neighbor search, rank with a heavier model, filter for safety and diversity, and cache results for each user for several minutes.

title: Design a payment system
category: Web & product
level: Senior / Staff
concepts: idempotence, acid, isolation, outbox, eventsourcing, kafka, postgres, partitioning, replication, retries, circuitbreaker, reconcile, wal, exactlyonce, ratelimit, security, twopc, deliverysem
summary: We build a payment service that lets merchants charge customers' cards (and bank accounts) through an API. The service calls external card networks and banks, records every movement of money in a ledger, tells merchants the result, and pays them out. The traffic is small compared with other systems in this book (a few thousand payments per second at peak), but the rules are strict: never charge twice, never lose a payment, never create or destroy money in the books, and always be able to prove what happened. The hard parts are uncertain outcomes (a timeout from the bank does not tell you if the money moved), exactly-once effects over unreliable networks, a ledger that stays consistent when data is sharded, and reconciliation against the outside world.
requirements: Functional requirements. Create a payment (charge) with an amount, currency, customer payment token and merchant id. Support authorize then capture (hold money, then take it), direct charge, void, full or partial refund, and payouts to merchants. Notify merchants of every state change by webhook. Provide a balance and a ledger view per merchant, and daily settlement reports. Support 3-D Secure (a bank challenge to the customer) when required.
Non-functional requirements. Correctness over speed: a payment is created at most once for one idempotency key, and the ledger always balances (the sum of all entries is zero). Durability: no acknowledged payment is ever lost (synchronous replication, no data loss on a single failure). Latency: p99 under 3 seconds for a charge, dominated by the card network (300 to 1,000 ms); our own overhead is under 150 ms. Availability above 99.99 percent for creating payments. Auditability: every change is kept forever (7 to 10 years), nothing is updated in place or deleted. Security: card numbers are stored only in an isolated vault that meets PCI DSS; all other systems see tokens.
Assumptions. 20 million payments per day on average, a peak of 3,000 per second on a shopping day (13 times the daily average). 5 percent of payments fail or are declined. 1.5 percent are refunded later. 200,000 merchants; the top 100 merchants make 30 percent of the volume.
estimates: Rate. 20,000,000 / 86,400 = 231 payments per second on average. Peak 3,000 per second. Even at peak, a single modern database server could handle about 5,000 to 10,000 simple transactions per second, but each payment is several writes (see below), the data must be synchronously replicated, and the peak can be higher next year, so we shard.
Writes per payment. One payment row created and then updated 3 to 4 times (created, authorized, captured, settled), a state-change event row for each (5), 2 ledger entries for the authorization hold and 4 for the capture (customer, merchant, fee, platform), the idempotency record, and 3 to 5 outbox rows (webhook and internal events). About 20 row writes per payment. At peak: 3,000 x 20 = 60,000 row writes per second, in 10,000 to 15,000 transactions per second. That is why one primary is not enough.
Storage. Payment row 1 KB, 5 events x 300 B = 1.5 KB, 6 ledger entries x 200 B = 1.2 KB, idempotency record and outbox 1.5 KB. Total about 5 KB per payment. 20M x 5 KB = 100 GB per day = 36 TB per year. Keep 7 years online (cheaper storage for older data): about 250 TB. Using 16 shards, each shard holds 2.2 TB per year, which a database server handles with room to grow.
Webhooks. 5 events per payment x 20M = 100M webhook attempts per day = 1,160 per second on average, plus retries. If 3 percent of merchant endpoints fail on the first call, retries add about 5 percent more.
Idempotency store. A record of 1 KB per request, kept for 24 hours (as many payment APIs do): 20M x 1 KB = 20 GB, which fits in a table or in cache. Fraud scoring: 3,000 per second at peak with a 100 ms budget; one model server handles 1,000 per second, so 6 servers with a 2x margin.
Reconciliation. Settlement files from acquirers have one line per transaction: 20M lines of 200 B = 4 GB per day, which is a simple batch job.
api: POST /v1/payments. Header: Idempotency-Key (client-generated unique string). Body: amount (integer in minor units, such as cents), currency, payment_token, merchant_id, capture (true or false), metadata. Returns 201 with payment_id and status (authorized, captured, requires_action, failed). If the same key is sent again with the same body, the original response is returned. If the same key comes with a different body, return 422.
POST /v1/payments/{id}/capture. Body: amount (may be less than the authorized amount). POST /v1/payments/{id}/refunds. Body: amount, reason, Idempotency-Key. POST /v1/payments/{id}/void.
GET /v1/payments/{id}. Returns the state and the list of events. GET /v1/merchants/{id}/balance and GET /v1/merchants/{id}/ledger?from=...
Webhook (we call the merchant): POST merchant_url with an event id, type (payment.captured, refund.created, ...), payload, a timestamp and an HMAC signature header. The merchant must answer 2xx. Events can arrive more than once and out of order; each carries the event id and the object version.
datamodel: payments (sharded by merchant_id): payment_id (primary key, time-sorted), merchant_id, amount, currency, status, version, psp_reference, created_at. The status is changed only through a compare-and-set on version, so two concurrent updates cannot both win. payment_events (append-only): payment_id, seq, type, data, created_at. This is the audit trail, and the status can be rebuilt from it.
idempotency_keys: (merchant_id, key) is the primary key, with request_hash, payment_id, response_body, status (in_progress or done), locked_until. The unique primary key is the lock: the first insert wins. It lives in the same database and shard as the payment, so the key insert and the payment insert are one ACID transaction.
ledger_entries (append-only): entry_id, transaction_id, account_id, amount (signed integer), currency, created_at. A ledger transaction has 2 or more entries whose amounts sum to zero. Accounts include merchant balance, customer funds in transit, fee revenue and the bank settlement account. Balances are computed by summing entries; a snapshot table (account_id, as_of_entry_id, balance) speeds this up. There is no update and no delete: a mistake is fixed by a reversing transaction.
outbox: (shard, outbox_id, topic, key, payload, created_at, published_at). Written in the same transaction as the state change. A relay process reads unpublished rows and publishes to Kafka, then marks them as published.
design: Request path. The client calls the payment API with an Idempotency-Key. An API gateway authenticates the merchant, applies a rate limit per merchant, and routes by merchant_id to the right shard. The payment service starts a database transaction: it inserts the idempotency record (if the key exists, it returns the stored response, or "in progress" if another request holds it), inserts the payment with status=created, and commits. Now the request is durable: the database writes the commit to its write-ahead log and to a synchronous replica to a replica in another zone before the commit returns.
Risk and authorization. The service calls the fraud scoring service synchronously (budget 100 ms). It may allow, block, or require 3-D Secure. Then it calls the payment connector, which talks to the acquirer or card network. The call carries our unique reference (the payment_id) so that the acquirer can recognize a repeated request. Before the call the state moves to "authorizing" (committed), so a crash after the call leaves a trace. The call has a hard timeout (for example 10 seconds) and a circuit breaker per acquirer.
Outcome handling. If the acquirer answers approve or decline, the service updates the payment with a compare-and-set on version, appends an event, writes the ledger entries (for example, a hold on the customer's funds), writes the outbox rows, and commits in one transaction. It then stores the response in the idempotency record and answers the client. If the call times out, the outcome is unknown. The payment moves to "unknown", the client gets a 202 "processing" response, and a resolver job asks the acquirer for the status of our reference (a status inquiry call) with backoff: after 5 seconds, 30 seconds, 5 minutes. If the acquirer has no record, we mark the payment failed; if it was approved, we continue. A daily reconciliation catches anything the resolver misses. We never retry a charge with a new reference when the first outcome is unknown, because that is how customers get charged twice.
Capture and ledger. Capture follows the same pattern: state to "capturing", call the acquirer (a capture by reference is naturally idempotent), then record the double-entry transaction: debit the customer funds-in-transit account, credit the merchant account for the net amount, credit the fee account for our fee. All entries share one transaction id and sum to zero. Because they are written in one database transaction, the books balance at every moment. All entries of a payment are on the shard of the merchant. For flows between merchants (marketplace splits) or payouts that touch another shard, we use a saga with the outbox: each leg is a local transaction, linked by transaction id, with compensating reversing entries if a later leg fails.
Webhooks and events. A relay reads the outbox in order per shard and publishes to Kafka (key = payment_id, so events for one payment stay in order). A webhook dispatcher consumes it and calls the merchant endpoint with a signature. Delivery is at-least-once: on a non-2xx answer or a timeout it retries with exponential backoff (1 minute, 5 minutes, 30 minutes, 2 hours, up to 3 days) and then marks the endpoint failing. Merchants dedupe by event id. Other consumers (analytics, risk, accounting) read the same topic.
Reconciliation and settlement. Each day, acquirers send settlement files. A batch job joins them with the ledger by reference: matches, amounts that differ, items in our books but not in the file (maybe pending), and items in the file but not in our books (a serious problem). Differences go to an operations queue. After a match the settlement transaction moves money in the ledger from "funds in transit" to the bank account, and a payout job creates transfers to merchants from their balances.

deepdive: Idempotency. The network can lose the request or the response, so clients must retry; the server must make a retry harmless. The client sends a unique key per logical operation. The server uses the key as the primary key of a row inserted in the same transaction as the payment. The database unique constraint serializes duplicates: if two retries arrive together, one insert succeeds and the other waits or fails with a conflict. The stored request hash detects misuse (same key, different amount). The stored response lets the server answer a retry with the exact first answer, including the failure. A key stays valid for 24 hours; after that, the client should use a new one. Together, at-least-once retries and idempotent handling give an exactly-once effect. The key protects the edge between the merchant and us. The edge between us and the acquirer needs the same idea: our payment_id as the unique reference. No idempotency key at that edge means no safe retry.
Uncertain outcomes. A timeout is not a failure. In a distributed system the call has three possible outcomes: success, failure, and unknown. We make "unknown" an explicit state in the state machine and give it an owner (the resolver), a deadline (resolved within minutes) and an escalation (manual review after 24 hours). The state machine is strict: allowed transitions are a table in code (created to authorizing, authorizing to authorized or failed or unknown, authorized to capturing or voided, and so on), and each transition is a compare-and-set on version so that a late response from an earlier attempt cannot overwrite a later state. This is the same pattern as a fencing token.
Ledger design. Use double-entry bookkeeping: every transaction has debits and credits that sum to zero, so money cannot appear or vanish without breaking an invariant that a nightly check can verify across all shards. Amounts are integers in the smallest currency unit (cents) with an explicit currency, never floating point. Entries are immutable; balances are derived. A hot account such as "our fee revenue" would receive an update from every payment and become a lock bottleneck if we kept a balance column. With append-only entries there is no row to lock; the balance is the sum, with periodic snapshots. For the merchant balance used in "can this payout be made?", we use a serializable check or a conditional insert guarded by the merchant's snapshot version.
Atomicity across the database and Kafka. A service that writes to the database and then publishes an event can crash between the two, losing the event, or publish and then fail to commit, announcing something that did not happen. The outbox pattern fixes this: the event is a row written in the same ACID transaction as the state change; a relay publishes it later. The relay is at-least-once (it can publish and crash before marking the row), so consumers must be idempotent; the event id is the dedupe key. We avoid two-phase commit across the database and the broker because it blocks on failures and few brokers support it.
Sharding and cross-shard work. Shard by merchant_id: almost every operation touches one merchant, so most transactions are local ACID. A hot merchant (a ticket sale) can overload its shard: we split merchant ranges onto dedicated shards and add a per-merchant rate limit with a queue that smooths bursts. Transfers between merchants and marketplace splits cross shards. We use a saga: the first shard writes its leg and an outbox event, the second consumes and writes its leg, and failures trigger a compensating entry. We accept that for a few seconds the two legs are not both visible, but the global invariant holds once all events are processed, and the nightly check verifies it.
Security and PCI. Raw card numbers enter only a small vault service in a separate network zone, encrypted with keys in a hardware security module, and return a token. Merchants and most of our services only see tokens, which shrinks the area subject to PCI DSS audit. Logs are scrubbed. API calls use TLS, merchants authenticate with keys that can be rotated, and webhooks are signed with HMAC and a timestamp to stop forgery and replay.
tradeoffs: Strong consistency with sharded SQL, or an event-sourced system. Choose sharded Postgres or MySQL with ACID transactions when the main entity (the payment) fits in one shard, you need unique constraints for idempotency, and your team knows how to operate it: it is the least surprising option. Choose full event sourcing when you need complete history and replay as the main feature (the event log is the truth and tables are projections); you gain audit and flexible reads and give up simple queries and some operational ease. Our design is in between: state tables plus an append-only event table written in the same transaction.
Synchronous or asynchronous payment API. Choose synchronous (the client waits for the final result) when most calls finish in 1 to 2 seconds and merchants need an answer for checkout. Choose asynchronous (202 now, webhook later) for slow methods (bank transfers, 3-D Secure, wallets), and for the unknown state. Real systems offer both: the API waits up to a time limit, and if the result is not ready it returns processing.
Distributed transaction, saga, or one database. Choose a single database transaction wherever possible (one shard per merchant): nothing is simpler or safer. Choose a saga with an outbox when a flow crosses services or shards and you can define a compensation for each step. Choose two-phase commit only inside one database technology that implements it well, and keep it away from external parties, since the card network can never take part in your transaction.
Retry the acquirer or fail fast. Retrying a call with the same reference after a short delay is safe when the acquirer supports idempotent references and recovers a few percent of transient errors. Failing fast and showing an error is better when the error is clear (a decline), or the customer is waiting at checkout and the queue would add seconds. For a timeout, never create a new reference; first query the status.
Single acquirer or smart routing. One acquirer is simple and has one contract. Several acquirers with routing (by card type, currency, cost and recent approval rate) raise authorization rates by 1 to 3 percent and give fail-over, but multiply integration work, reconciliation formats, and the number of unknown-outcome paths.
failures: Payment service crash after the acquirer approved: the state was already "authorizing", so a resolver finds all payments stuck in that state for more than 30 seconds and asks the acquirer by reference. Nothing is lost and nothing is repeated. Database primary failure: the synchronous replica is promoted in 10 to 30 seconds with no loss of committed data; requests in that time fail with a retriable error, and clients retry with the same key. Shard overload: the gateway sheds load per merchant with 429 and a Retry-After header.
Acquirer outage or slowness: the circuit breaker opens after a high error or timeout rate, and routing sends traffic to a second acquirer if one exists; otherwise the API returns a clear temporary failure and does not queue charges for later, because a customer who has left the checkout would be charged unexpectedly. Webhook endpoint down: retries with backoff for 3 days, then the event is available through the events API for the merchant to poll. Kafka outage: the outbox keeps accumulating in the database, and the relay catches up; nothing is lost because the database is the source of truth.
Duplicate or out-of-order delivery: all consumers dedupe by event id and check the object version before applying. Bad deploy: a new state-machine bug could produce a wrong ledger entry; since entries are immutable, we repair with reversing transactions, and the nightly invariant check (all transactions sum to zero, balances match snapshots, payments in terminal states have the expected entries) detects the problem within a day. Region loss: asynchronous replication to a second region gives a recovery point of seconds; failing over accepts that a few of the latest transactions may need to be recovered from the acquirer's records using reconciliation, which is why every external call carries our reference.
evolution: At 1,000 payments per day, one Postgres instance with a payments table, an idempotency table and a ledger table is enough, and a cron job reconciles the daily file. At 1 million per day, add read replicas, an outbox with a relay, a webhook sender with retries, and a fraud service. At 20 million per day (this design), shard by merchant, run several acquirer connectors with breakers, separate the vault, and build the reconciliation and operations tooling. At hundreds of millions per day, add multi-region active-passive, smart routing across many acquirers, ledger services with dedicated shards per currency, and real-time risk models with feature stores.
followups: How do you prevent a double charge when the client retries? || A client-supplied idempotency key is the primary key of a row inserted in the same transaction as the payment, so duplicates are serialized by the database. A repeat returns the stored response. The same idea applies to the acquirer, with our payment id as reference.
The acquirer call times out. What now? || The outcome is unknown, so mark the payment unknown and return 202. Do not create a new charge. A resolver queries the acquirer by our reference with backoff, and reconciliation finds anything missed. Escalate to a human after a deadline.
Why a double-entry ledger? || Every transaction's entries sum to zero, so money cannot appear or disappear unnoticed, and the invariant can be verified automatically. Immutable entries give an audit trail, and balances are derived.
How do you keep the database and Kafka consistent? || Use the outbox: write the event row in the same transaction as the state change, and let a relay publish it at least once. Consumers dedupe by event id. This avoids two-phase commit with the broker.
How do you handle a transfer across two shards? || Use a saga: a local transaction on each shard linked by transaction id, with outbox events between them and a compensating reversing entry if a leg fails. Check the global sum-to-zero invariant nightly.
How do you avoid a hot row for the fee account? || Do not keep a mutable balance. Append entries and compute the balance by sum with periodic snapshots, or aggregate fees per batch. Appends do not contend on one row.
How do you know your books match the bank? || Daily reconciliation of acquirer settlement files against the ledger by reference: matched, amount mismatch, missing on either side. Differences go to an ops queue, and settlement moves money from in-transit to the bank account.
Why not use floats for money? || Binary floating point cannot represent most decimal fractions exactly and rounding errors accumulate. Use integers in the smallest unit with an explicit currency, and define the rounding rule for fees and currency conversion.

title: Design a ticket booking system like Ticketmaster
category: Web & product
level: Senior / Staff
concepts: ccontrol, occ, locks, isolation, acid, postgres, redis, ratelimit, queueing, idempotence, cachelayer, cdn, partitioning, mqueue, fencing, loadbalancing, mvcc
summary: We build a system that sells numbered seats for concerts and sports. Normal days are quiet (about 16 tickets per second worldwide), but when a famous artist goes on sale, millions of people arrive in the same minute to fight for 50,000 seats. Every seat must be sold exactly once, nobody should pay for a seat that is not theirs, and the site must not fall over. This is a problem of contention, not of volume: many users want the same few rows. The core mechanisms are a short-lived hold on a seat, an atomic conditional update to claim it, a virtual waiting room that limits how many users reach the booking path, and protection against bots.
requirements: Functional requirements. Browse events and see a seat map with live availability. Select seats (specific seats, or best available for N people). Hold the seats for a short time (8 minutes) while the user pays. Pay and receive tickets (barcodes) by email and in the app. Release the seats if the hold expires or the user cancels. Limit tickets per account (for example 6 per event). Admins create events, price tiers and sale windows.
Non-functional requirements. Correctness: a seat is sold at most once, always, even with retries, crashes and double clicks. Fairness: users who arrive earlier are not systematically beaten by bots, and the waiting room is not pure speed. Availability under a surge: the system degrades gracefully by slowing admission, not by returning errors to everyone. Seat map freshness of 1 to 2 seconds. Payment latency is dominated by the payment provider (1 to 3 seconds). A user who has paid must never lose the seat because of our failure.
Assumptions. A hot event with 50,000 seats. 3 million fans try to buy; 1 million of them arrive in the first 10 seconds. A buyer needs on average 2.2 tickets. Hold time is 8 minutes. 500 million tickets are sold per year across all events, so normal load is small.
estimates: Normal load. 500,000,000 tickets per year / 365 / 86,400 = 16 tickets per second, about 7 orders per second. A single database could handle it. The surge is what sizes the system.
Surge arrival. 1 million users in 10 seconds = 100,000 page requests per second at the start, and each user's page makes about 5 API calls (event info, seat map, queue status), so 500,000 requests per second. If we let them all reach the application and database, a database that can do 5,000 writes per second would see a 100x overload. A content delivery network (CDN) serves the static page, the event info and the seat map snapshot, so only queue-join calls (100,000 per second) reach our servers. A queue-join call is cheap (assign a random number, store a cookie), so 30 small servers at 4,000 per second each can take it.
Seat map. 50,000 seats, each with a state of 2 bits (available, held, sold): 12.5 KB per snapshot. Even at 10 bytes per seat with price tier and label, it is 500 KB, which compresses to about 50 KB. A snapshot every second served from the CDN: 1 million users polling every 2 seconds would be 500,000 requests per second served from the edge cache and 1 per second to our origin. Edge bandwidth: 500,000 x 50 KB = 25 GB/s, which is why we send only deltas after the first load (a delta is typically under 1 KB).
Admission rate. Each admitted user spends about 4 minutes in the booking flow (choose, hold, pay). We want about 20,000 active booking sessions at once (about 0.4 per seat). By Little's law, the arrival rate that gives 20,000 sessions with 240 seconds each is 20,000 / 240 = 83 users per second. So the waiting room admits about 83 users per second at first, and the rate is adjusted using the sold count and conversion. Over the whole sale (50,000 seats / 2.2 per order = 22,700 orders; if 30 percent of admitted sessions end with an order, that needs 75,700 admitted users), the sale lasts 75,700 / 83 = about 15 minutes. This matches real sales that sell out in 10 to 20 minutes while millions wait.
Database load. 20,000 sessions each performing about 10 seat operations (try seats, retry another, release) over 4 minutes = 200,000 / 240 = 830 operations per second plus 83 hold transactions per second. This is easily within one Postgres primary (a few thousand transactions per second). Contention, not throughput, is the real risk: the best seats are requested by every user.
Storage. Seats: 50,000 rows x 200 B = 10 MB per event. Orders: 22,700 x 2 KB = 45 MB. Across a year: 500M tickets x 1 KB = 500 GB. Small.
api: GET /v1/events/{id}. Event info, price tiers, sale status. Served from the CDN.
POST /v1/events/{id}/queue. Joins the waiting room. Returns a queue token (signed, with position bucket) and a poll interval. GET /v1/queue/{token}. Returns waiting (with estimated time) or admitted with an admission cookie valid for 20 minutes.
GET /v1/events/{id}/seats?version=... . Returns the seat map snapshot or a delta since the version. Cacheable for 1 second.
POST /v1/events/{id}/holds. Needs the admission cookie. Body: seat_ids or {quantity, section, adjacent}. Header: Idempotency-Key. Returns hold_id, seats, expires_at; or 409 with the seats that were taken.
POST /v1/holds/{id}/checkout. Body: payment token, Idempotency-Key. Returns order_id and status. DELETE /v1/holds/{id} releases the seats.
datamodel: seats (partitioned by event_id; primary key (event_id, seat_id)): section, row, number, price_tier, status (available, held, sold), hold_id, hold_expires_at, order_id, version. An index on (event_id, section, status) supports best-available search.
holds: hold_id, event_id, user_id, seat_ids, expires_at, state. orders: order_id, user_id, event_id, seat_ids, amount, payment_ref, state, created_at, unique (payment_ref). Tickets: ticket_id, order_id, seat_id, barcode (signed, rotating for the mobile app). idempotency table as in the payment design.
Waiting room state (Redis): sorted set of queue tokens by assigned random rank; a counter of admitted users and the current admission rate; a set of active sessions with expiry. The authority for who may enter is this small store, not the main database.
Counters: available_count per section (Redis, derived from the database), used for the best-available shortcut and for the "tickets left" display.
design: Pre-sale. The event page and the JavaScript are static and sit at the CDN. A few minutes before the sale, fans open the page and click "join the queue". In a pre-queue period, joins get a random number, not a time-of-arrival number. When the sale opens, the order of admission is by the random number among everyone who joined in the pre-queue window, and by arrival time after that. Randomizing the first wave removes the benefit of the fastest connection and of bots that hit the server in the first milliseconds.
Waiting room. A queue service holds the tokens. Each client polls every 5 to 15 seconds (with a random jitter; the server tells the client the next time to poll) or uses a long-lived connection. The service computes the admission rate from the number of active sessions, the remaining seats and the recent conversion (see the estimates), and admits the next batch each second. An admitted client gets a signed admission cookie (user id, event id, expiry) which the booking API checks at the edge without a database lookup. Everyone else sees "you are number 482,113, about 40 minutes".
Seat selection. The admitted user sees the seat map (snapshot plus deltas over a server-sent events stream or short polling) and picks seats. The client calls the hold API. The server tries to claim each seat with one atomic conditional update: set status=held, hold_id, and expiry, only if the seat is available, or if it is held and the hold has expired. If the number of updated rows equals the number of seats requested, the hold succeeded; otherwise the transaction rolls back and the API answers 409 with the list of seats taken. All seats of one hold are updated in one transaction, in ascending seat id order, to avoid deadlocks between two buyers who want overlapping sets.
Best available. For "2 adjacent seats in section 101", scanning free seats and choosing the best from the database takes a few milliseconds but creates a race: two users get the same answer. The service selects candidates with SELECT ... FOR UPDATE SKIP LOCKED, which skips rows that another transaction has locked, so different users get different candidate seats without waiting on each other.
Payment. The user enters card details. The checkout call verifies that the hold is still valid, creates an order in state pending with the payment_ref, and calls the payment service with an idempotency key (see the payment-system design). While the payment is in progress, the hold expiry is extended by a short grace period (2 minutes) so a slow bank does not lose the seat. On payment success, one transaction sets seats to sold with the order_id, but only if they are still held by this hold; it marks the order paid and writes the ticket rows and an outbox event. Tickets are emailed from the event consumer.
Expiry. A background job runs every few seconds to release expired holds. It is only an optimization, because the claim query also treats expired holds as available. The correctness comes from the condition on the expiry time in the claim query, so a lost or delayed cleaner never blocks a seat. A mistake is possible in one place: a user pays after the hold expired and the seat was taken by another. The checkout transaction fails, and the payment is voided or refunded automatically (a compensation).

deepdive: The atomic claim. The basic safety rule is that the check and the change must be one indivisible step. A pattern "read the seat, see it is free, then update it" has a race: two users read "free" and both update. The fix is a conditional update (compare-and-set): UPDATE seats SET status='held', hold_id=?, hold_expires_at=? WHERE seat_id=? AND (status='available' OR (status='held' AND hold_expires_at < now())). The database applies row-level locking so that the second update re-evaluates the condition after the first commits. Postgres uses multi-version concurrency control (MVCC), so readers never block writers, but two writers of the same row still wait for each other. Under the default read committed isolation level this works for one row. For many seats, a transaction updates them in a fixed order and checks the row count. Another way is optimistic concurrency control with a version column: update ... WHERE version=?, and retry or fail if no row changed. For a hot seat, optimistic methods waste work (many users try, one wins), while a short pessimistic lock (SELECT FOR UPDATE) makes users wait in order. Both are correct; the choice is about wasted work and fairness.
Distributed locks are the wrong default. Many designs use Redis SET NX EX as a lock for each seat. It is fast, but it is not the source of truth: a Redis failover can drop the lock, a paused process can wake up after its lock expired and still act, and the lock and the database can disagree. If a lock service is used, it must give fencing tokens (a number that grows with each lock grant) so that the database rejects an action from a holder with an old token. The simplest safe design puts the lock in the data itself: the seat row with its status and expiry is the lock, protected by the database's own concurrency control. Redis is used only as a cache and for the queue, where an error costs a retry and not a double sale.
Hot rows. The best seats and the first rows have heavy contention. If 20,000 sessions all try section 101 row 1, the database queues up row locks, and the p99 latency of hold calls grows. Four measures help. First, the waiting room caps the number of simultaneous users. Second, the seat map from the CDN is at most 1 to 2 seconds old, so most users see a seat as taken before they click on it. Third, "best available" gives different users different seats using SKIP LOCKED, so they do not all fight for seat 1. Fourth, on a conflict the API returns the nearest alternatives with the 409, saving the user one round trip. A transaction timeout of 200 ms and a limit on retries protects the database.
Waiting room fairness and bots. A pure first-come queue rewards bots and anyone with a faster network. The pre-queue randomization gives a fair lottery among early joiners. Signed tokens bind a queue position to a browser session and to a verified account, so a position cannot be bought and transferred easily. Rate limiting by IP, device fingerprint and account catches bulk requests; a proof-of-work or a CAPTCHA challenge before the join slows large operations; pre-registration and "verified fan" lists limit the number of accounts. A per-account ticket limit is enforced at the hold and at checkout (count of seats held plus sold for the user and event), and a payment-card limit stops one card buying for many accounts. No measure is perfect; it is a cost contest with the bot operators.
Consistency of the seat map. The seat map seen by users is a cache. A sold seat that still looks free costs the user one failed click (409), which is fine. A free seat that looks sold only costs a missed chance. So the cache may lag in either direction without violating correctness; the database arbitrates. Seat-state changes go through an outbox to Kafka, a map service consumes them, keeps the current bitmap in memory, and pushes deltas. The CDN holds the full snapshot with a 1-second TTL.
Payments and the three-way race. The risk with money is: the user paid, but the seat was lost (expired and re-sold), or the seat was sold but the payment failed. We prevent both. The order is created with a unique payment_ref and an idempotency key. The hold is extended when payment starts. The final transaction requires the hold to be valid, and if it is not, the payment is cancelled before capture (authorize first, capture only after the seat is confirmed sold). A reconciliation job finds orders in pending for more than 15 minutes and resolves them using the payment provider's status.
tradeoffs: Pessimistic locks or optimistic updates for seats. Choose short pessimistic locks (SELECT FOR UPDATE with SKIP LOCKED, or a conditional UPDATE that locks the row for microseconds) when contention is high and the transaction is small: users queue briefly, and no work is wasted. Choose optimistic versioning when conflicts are rare (ordinary seats, low demand) and you want no lock waits. You give up some fairness under contention in the optimistic case, and with pessimistic locks you risk lock queues and deadlocks if you do not order your updates.
Database or Redis as the source of truth for seat state. Choose the relational database when the inventory is small enough (50,000 rows per event is tiny), you need transactions across seats, hold, order and outbox, and correctness matters more than the last millisecond. Choose Redis (Lua scripts for atomic claim) when you need hundreds of thousands of operations per second on a single event, and you can accept the rebuild-from-database procedure after a failover and the risk of asynchronous replication loss; then the database still records the final sale as the truth.
Waiting room: random lottery, first-come, or pure rate limit. The lottery is fairest to humans and cheapest against bots, but fans dislike "I was first and got a late number", so you must explain it. First-come with a strict order is simple to explain but rewards fast bots. A rate limit with random rejection spreads load but gives a poor user experience (refresh until you get in). Large sales use a queue with randomization of the first wave and a visible position.
Hold duration. A short hold (3 to 5 minutes) frees seats quickly and keeps the inventory moving; a longer hold (10 minutes) lets slow payers finish and reduces abandoned payments. Our 8 minutes with a payment grace is a compromise. Choose shorter holds for hot events, where abandoned seats are worth more to the next fan.
Reserved seating or general admission. General admission is a counter: decrement available_count atomically (UPDATE ... SET available = available - 2 WHERE available >= 2), which is trivial and extremely scalable. Reserved seating needs row-level state and adjacency search. Choose counters wherever the product allows, such as per section "any seat".
Push or poll for the seat map. Server-sent events give instant updates but need 500,000 open connections (a few dozen edge servers); polling with CDN caching needs no connection state and is easy, with a 1 to 2 second delay. The CDN-polling model is the safer default, with SSE for the active booking sessions only (20,000).
failures: Database primary failure: with synchronous replication the failover loses no committed holds or sales. For 10 to 30 seconds hold and checkout calls fail; the API returns 503 with Retry-After and the waiting room pauses admission automatically (its health input is the hold error rate). Booking API crash: stateless, the load balancer removes it; holds live in the database, so the user continues after a refresh.
Redis (waiting room) failure: a replica takes over; if the queue state is lost, tokens are re-validated from their signature, and the user may lose their position bucket but not the account. To limit this, the queue service writes a periodic snapshot to a durable store. The payment provider is slow: checkout calls time out, orders stay pending, the resolver checks the status; holds are extended up to a maximum of 15 minutes. The CDN fails or is attacked: failover to a second CDN by DNS; origin shields limit direct traffic by rate limiting everything except valid admission cookies.
Overload: the queue service sheds load by returning the same "wait" answer from the edge for tokens already known, and the admission rate falls automatically when p99 hold latency passes 300 ms (a control loop, like backpressure). Thundering herd after an outage: when the site returns, reconnecting clients use random jitter. Bad deploy: new versions go to 1 percent of admitted users first; the seat claim query is covered by a concurrency test that runs 10,000 simulated users against 100 seats and asserts that exactly 100 sales result.
evolution: At 1,000 tickets per day, one Postgres database with a seats table and a SELECT FOR UPDATE inside a transaction is enough, with no queue. At 100,000 tickets per day with occasional popular events, add the CDN for the seat map, rate limits and per-account limits. At a hot on-sale with millions of fans, add the waiting room with randomization, admission control based on Little's law, delta-based seat maps, bot defenses, and load tests that replay a full sale. At global scale (thousands of events on sale at once), partition by event across database shards and keep each event's inventory in exactly one shard, because no seat needs a cross-shard transaction.
followups: How do you guarantee that a seat is sold only once? || The seat row is the lock: one atomic conditional update claims it (available, or held with an expired hold). The final sale is another conditional update that requires the hold to still be valid. The database's row-level concurrency control makes both indivisible.
Why not use a Redis lock for each seat? || The lock service can lose locks at a failover and a paused client can act after its lock expired. If you use one, you need fencing tokens checked by the database. It is simpler and safer to keep status and expiry in the seat row.
How do you protect the system when 3 million users arrive in a minute? || A CDN serves static pages and seat-map snapshots, a waiting room admits a controlled number of users (by Little's law, about 83 per second here), and only admitted users with a signed cookie reach the booking API.
How do you choose the admission rate? || Pick the target number of active sessions (about 0.4 per seat), divide by the average session time to get arrivals per second, and adjust with feedback from sold count, conversion and database latency.
What if a user pays after their hold expired? || The final sale transaction fails if the seat is no longer held by this hold. Authorize first and capture after the seat is confirmed, or void or refund automatically. A reconciliation job resolves pending orders.
How do you keep bots from taking all the seats? || Randomized first-wave admission, rate limits by IP, device and account, challenges at queue join, verified accounts, per-account and per-card limits, and anomaly detection on the hold pattern.
How do you find 4 adjacent seats without races? || Search candidates in the section index, then claim with SELECT ... FOR UPDATE SKIP LOCKED so concurrent users get different candidates, and claim all seats in one transaction in a fixed order. On conflict, return alternatives.
How would you handle general admission events? || Use an atomic counter per section with a conditional decrement (available >= n), with the hold as a reservation record that returns the count on expiry. It scales much further than per-seat rows.

title: Design an LLM serving platform like a chat assistant API
category: AI & ML
level: Senior / Staff
concepts: llmserving, kvcache, contbatch, pagedattn, promptcache, chunkedprefill, quant, specdecode, parallelism, gpucomp, attention, gqa, roofline, ratelimit, loadbalancing, autoscaling, vllm, decoding
summary: We build the service behind a chat assistant: users send a conversation, and the platform streams back the answer token by token from a large language model with 70 billion parameters. A GPU is expensive (about 2 to 3 dollars per hour) and a request holds GPU memory for many seconds, so the whole design is about using each GPU as fully as possible while keeping the first token fast (under 500 ms) and the stream smooth (a token every 25 to 50 ms). The hard parts are that decoding is limited by memory bandwidth and not by arithmetic, that the attention cache (KV cache) of each request is large, that requests have unpredictable lengths, and that capacity is scarce, slow to add, and must be shared fairly.
requirements: Functional requirements. An API that takes a list of messages (system, user, assistant, tool results), sampling settings and a maximum length, and streams tokens back over server-sent events. Several models (a large and a small one). Multi-turn chat (the client sends the full history each time). Tool calling and JSON output modes. Usage metering by tokens, per-key rate limits, quotas by plan, and a cheaper batch API with 24-hour completion.
Non-functional requirements. Time to first token (TTFT): p50 under 500 ms and p99 under 2 seconds for prompts up to 8,000 tokens. Inter-token latency (ITL): p99 under 50 ms, which is 20 tokens per second and faster than reading speed. Availability above 99.9 percent. Cost: maximize tokens per GPU-second. Isolation: one customer's burst must not starve others. Safety checks on input and output without adding noticeable latency.
Assumptions. 10 million daily active users, 10 requests each: 100 million requests per day. Average prompt: 2,000 tokens (system prompt plus history); average answer: 400 tokens. Peak is 3 times the average. 70 percent of prompt tokens are a repeat of an earlier prefix (system prompt and earlier turns). The large model is a 70-billion-parameter transformer, in 8-bit floating point (FP8), on NVIDIA H100 80 GB GPUs.
estimates: Request rate. 100,000,000 / 86,400 = 1,160 requests per second on average, 3,500 at peak. Output tokens: 100M x 400 = 40 billion per day = 463,000 per second on average, 1.4 million per second at peak. Input tokens: 100M x 2,000 = 200 billion per day = 2.3 million per second on average, 7 million at peak.
Model memory. Weights at FP8: 70 billion x 1 byte = 70 GB. They do not leave room for work on one 80 GB GPU, so we split the model over 2 GPUs (tensor parallelism, 35 GB per GPU). A replica is 2 GPUs.
KV cache per token. The cache stores a key and a value vector per layer per token. With 80 layers, 8 key-value heads (grouped-query attention) and head size 128: 2 x 80 x 8 x 128 x 1 byte (FP8 cache) = 163,840 bytes = 160 KB per token. In 16-bit it would be 320 KB. A request with 2,400 tokens (prompt plus answer) needs 2,400 x 160 KB = 393 MB at FP8. Without grouped-query attention (64 heads) the cache would be 8 times bigger: 3 GB per request, which is why GQA matters.
Concurrency per replica. Memory: 2 x 80 GB = 160 GB. Use 90 percent = 144 GB. Minus weights 70 GB and about 6 GB for activations and buffers leaves 68 GB for KV cache. 68 GB / 393 MB = about 170 concurrent sequences per replica.
Decode speed. Each decode step must read all the weights once and all KV caches of the batch. Per GPU: weights 35 GB; KV 170 x 393 MB / 2 = 33 GB. Total 68 GB per step. H100 SXM memory bandwidth is 3.35 TB/s, so the lower bound is 68 GB / 3,350 GB/s = 20 ms. Add communication between the two GPUs and kernel overhead, about 25 ms per step. 170 tokens come out every 25 ms = 6,800 tokens per second per replica. At 75 percent efficiency in practice: about 5,000 tokens per second per replica. Each user gets 1 token per 25 ms = 40 tokens per second, which meets the ITL goal.
Math against memory. One token costs 2 x 70e9 = 1.4e11 FLOP in the weights. A batch of 170 tokens costs 2.4e13 FLOP = 24 TFLOP. If each GPU delivers about 800 TFLOP/s of FP8 in practice, the two GPUs share the work and need 24 / 1,600 = 15 ms. The memory time was 20 ms, so at batch 170 the two limits are about equal. At batch 16 the math takes only 1.4 ms while reading the weights still takes 10 ms (35 GB at 3.35 TB/s). Small batches waste the GPU; large batches share the cost of reading the weights over many users. That is why batching is the first lever.
Decode fleet. Peak 1.4M tokens/s / 5,000 = 280 replicas = 560 GPUs.
Prefill fleet. Prefill is compute-bound. Cost per token is 1.4e11 FLOP. At 40 percent of the FP8 peak (1,979 TFLOP/s dense), a GPU gives about 790 TFLOP/s, so 790e12 / 1.4e11 = 5,640 tokens per second per GPU. Prefix caching removes 70 percent of input tokens, leaving 30 percent x 7M = 2.1M tokens/s at peak. 2.1M / 5,640 = 372 GPUs. Total at peak: 560 + 372 = 932 GPUs. With 15 percent headroom for failures and rollouts: about 1,100 GPUs = 138 nodes of 8.
Cost. 1,100 GPUs x 2.5 dollars x 24 hours = 66,000 dollars per day if kept at peak all day. Scaling down at night saves about 30 percent, so about 46,000 dollars per day, or 17 million dollars per year. Per million output tokens (40 billion per day = 40,000 million): about 1.15 dollars, ignoring input pricing. Without prefix caching, prefill would need 1,240 GPUs by itself, more than doubling the cost.
TTFT check. A cold 2,000-token prompt = 2,000 x 1.4e11 = 280 TFLOP. On 2 GPUs at 790 TFLOP/s each: 280 / 1,580 = 0.18 s. With 70 percent cached, only 600 new tokens: 0.05 s. The rest of the TTFT budget is network, queueing and scheduling.
api: POST /v1/chat/completions. Body: model, messages[], max_tokens, temperature, top_p, stop, stream (true), tools[], response_format. Returns a stream of events, each with a token delta, and a final event with finish_reason and usage (prompt_tokens, completion_tokens, cached_tokens). A non-streaming mode returns the full message.
POST /v1/batches with a file of requests and a completion window of 24 hours; GET /v1/batches/{id}. Runs on spare capacity at about half the price.
GET /v1/models. Lists models and limits. GET /v1/usage?from=...&to=... . Token counts per key and model.
Errors: 429 with Retry-After for rate limits, 503 when capacity is exhausted, 400 for a prompt longer than the context window. The stream can end with an error event, and the client should treat an incomplete stream as retryable only if it is idempotent for the user.
datamodel: The serving path is mostly stateless. Conversation history comes in the request. Persistent data: API keys and plans (relational), usage ledger (append-only log in Kafka, aggregated into an analytics table keyed by key_id and hour), and rate-limit counters (Redis, key = key_id and minute, value = tokens used).
Inside each engine replica the state is the KV cache, split in fixed blocks of 16 tokens (a "page"). A block table maps each sequence to its list of physical blocks, like a page table in an operating system. A prefix tree (radix tree) maps token sequences to blocks for reuse: each node is a block with a hash of its tokens and a reference count. Blocks that are not in use stay as a cache and are evicted least recently used.
The router keeps a soft view of the cache: for each replica, a summary (hashes of the first block of recently served prefixes) and the current load (running sequences, KV usage, queue length). It is rebuilt from replica heartbeats every second, so it can be lost without harm.
design: Edge. The client connects over HTTPS to a global load balancer, which sends it to a nearby region with capacity. The API gateway checks the key, the plan, the maximum prompt size and the rate limit. Limits are counted in tokens, not requests: the input tokens are known after tokenization, and the output is estimated by max_tokens at admission, then corrected when the answer ends. A token bucket per key in Redis does this. Streaming uses long-lived connections, so the gateway holds one open connection per active request: at 3,500 new requests per second and an average stream time of 12 seconds, that is 42,000 open streams, easy for a few dozen gateway servers.
Router. The gateway sends the tokenized request to a router. The router picks a replica by two rules. First, cache affinity: hash the first blocks of the prompt (the system prompt and the start of the conversation) and prefer the replica that served that prefix before, since that replica already holds its KV blocks. Second, load: skip a replica whose KV cache is above 90 percent or whose queue is long. If the preferred replica is busy, a replica with a lower load is used and the cache is rebuilt there, which costs only the prefill time. This is consistent hashing with bounded load, using the prefix as the key.
Engine. Each replica runs an inference engine such as vLLM or SGLang. Its scheduler works in iterations. In each iteration it chooses which sequences run: all active decoding sequences (one token each) plus a budget of prefill tokens (for example 2,048 tokens) taken from waiting requests. This is continuous batching with chunked prefill: new requests join at the next iteration instead of waiting for a whole batch to end, and a long prompt is split in chunks so that it does not stall the decoding sequences. One iteration is one forward pass over all selected tokens, about 25 to 40 ms. After the pass, each sequence samples its next token (temperature, top-p), appends it to its blocks, and sends it to the stream. A sequence that finishes (end token or max_tokens) frees its blocks.
Memory. KV blocks are allocated on demand from a pool (paged attention), so a sequence that is still short does not reserve memory for its maximum length. Without paging, systems reserved the full context for each request and wasted 60 to 80 percent of the memory in fragmentation and over-reservation. When the pool is full, the scheduler preempts the newest sequence: it drops its blocks and recomputes them later (or swaps them to CPU memory). The scheduler admits new requests only if enough free blocks exist for their prompt and some headroom for growth.
Speed-ups. Quantization to FP8 halves weight and cache reads. Flash attention computes attention in tiles without writing the big score matrix to memory. Speculative decoding uses a small draft model (1 billion parameters) to propose 4 to 5 tokens, and the large model verifies them in one pass; when 70 percent of proposals are accepted, the output speed rises about 2x at low batch sizes, where the GPU is idle on the math side. At high load, the gain is smaller, so the engine switches speculation off when the batch is large.
Streaming back. The engine sends each token to the gateway (gRPC stream), the gateway detokenizes and sends an SSE event. Detokenization needs care because a character in UTF-8 can be spread over several tokens. A safety filter on the output works on chunks (every 20 to 50 tokens) in parallel, with the right to cut the stream. Billing events (tokens in, out, cached) go to Kafka at the end of each request.

deepdive: Prefill and decode are different workloads. Prefill processes many tokens in parallel and is limited by arithmetic (compute-bound). Decode processes one token per sequence and is limited by memory bandwidth, because each step reads all the weights. On the roofline model, prefill sits at the compute roof and decode on the bandwidth slope. Mixed in one batch, a long prefill makes all decoding users in that step wait, so ITL spikes. Chunked prefill limits that harm by capping the prefill tokens per step. A stronger fix is disaggregation: separate pools for prefill and decode, and the KV cache is sent from the prefill GPU to the decode GPU over a fast network (RDMA, 400 Gbit/s = 50 GB/s). A 2,000-token KV cache is 320 MB at FP8, which takes 6.4 ms to send, a small price. The pools can be sized and tuned separately (prefill nodes for compute, decode nodes for memory bandwidth and capacity). The cost is more complexity and the need for a very fast interconnect.
KV cache management. The KV cache is the main consumer of memory and limits the batch size, and therefore throughput. Four techniques attack it. Grouped-query attention (a model-design choice) cuts the cache 8x. Paged allocation removes fragmentation. Quantizing the cache to FP8 or 4 bits halves or quarters it, with a small quality loss that must be tested. Prefix sharing lets requests with the same system prompt use the same physical blocks (copy on write when they differ). For long contexts (128,000 tokens), one request needs 20 GB at FP8, so a replica can hold only 3 of them; such traffic is routed to its own pool, priced higher, and may use sliding-window attention or cache offload to CPU memory.
Prompt caching across turns. In chat, turn N+1 repeats the entire conversation up to turn N. If the blocks of turn N are still in the radix tree on the same replica, the prefill cost of the history is zero. Affinity routing is what makes this work: without it, the hit rate on a pool of 280 replicas falls to about 1/280 for the long tail. The router uses the prefix hash and falls back to load. Cached blocks live for minutes, so the hit rate depends on keeping the replica's cache big enough: free HBM beyond the live sequences serves as the cache. Offloading older blocks to CPU memory (512 GB to 2 TB per node) extends the reach to hours at the price of a PCIe copy of 5 to 10 ms.
Scheduling and fairness. Requests have different value and urgency. We use priority queues: interactive paid, interactive free, and batch. Batch jobs fill only unused capacity and are preempted first. Within a class, we limit tokens per key per minute and cap concurrent sequences per key so one tenant cannot fill the KV cache. The scheduler also uses shortest-job-first hints (max_tokens) carefully, since pure SJF starves long requests. Admission control rejects early with 429 or 503 when queue wait would exceed the TTFT budget, because a request that waits 10 seconds is already a failure for the user, and queueing it only delays the next ones.
Autoscaling with slow capacity. A new replica must load 70 GB of weights (from local NVMe at 5 GB/s: 14 s, from object storage at 1 to 2 GB/s: 35 to 70 s), initialize the engine, capture CUDA graphs and warm up: 2 to 5 minutes in total, plus getting a GPU node from the cloud if none is free (minutes to hours, or never during a shortage). So autoscaling reacts too late to spikes of seconds. We combine three things: a warm pool of idle replicas with weights loaded (5 to 10 percent), scaling on leading signals (queue length, KV utilization, requests per second trend) and not on GPU utilization, and load shedding by priority for the gap. Weights are pre-staged on the node disks.
tradeoffs: Dedicated replicas or one shared pool. Choose a shared pool with a router when many tenants have uneven traffic: it uses GPUs better and gives bursts access to the whole fleet. Choose dedicated replicas for a large customer that needs guaranteed latency or data isolation; you pay for idle time. Both exist in practice as reserved and on-demand tiers.
Bigger batch or lower latency. A larger running batch raises tokens per second per GPU (more users share the weight reads) but raises ITL for each user (the step is longer). Choose a cap on the batch size or on the KV usage that keeps ITL under 40 ms for interactive pools; choose very large batches for the batch API, where only total throughput matters.
Tensor parallelism, pipeline parallelism, or data parallelism (replicas). Choose tensor parallelism inside a node (NVLink, 450 GB/s per direction on H100) to fit the model and cut latency per step; it needs all-reduce communication twice per layer and is efficient only with fast links. Choose pipeline parallelism across nodes only when the model is too big for one node (for example 1 trillion parameters); it adds latency and bubbles. Choose data parallelism (more replicas) to scale throughput; it needs no communication. Use the smallest tensor-parallel degree that fits the weights and enough KV cache.
Quantization level. FP8 weights and cache are close to lossless for most tasks and double the throughput versus 16-bit. 4-bit weights double it again and fit a 70-billion model on one GPU, but quality drops on reasoning and code tasks and must be measured on your own workload. Choose the lowest precision that passes your evaluations.
One large model or a cascade. Routing easy requests to a small, cheap model (8 billion parameters, 8x cheaper) and hard ones to the large model saves a lot if a router or a confidence check classifies well. The cost is the router's errors, which users see as lower quality; and for a chat product the first-token decision is hard to take back. Choose a cascade for products with clear task types (classification, extraction), and a single model with speculative decoding when quality is the product.
failures: GPU failure (ECC errors, a node hang): a replica of 2 GPUs dies, and its in-flight streams (about 170) break. The gateway sees the broken stream and, since it holds the prompt and the tokens already sent, retries on another replica with the sent text appended to the prompt (a continuation), so the user sees a short pause. The router stops sending traffic to the dead replica within seconds from missed heartbeats. At 1,100 GPUs, a GPU failure happens about every few days, so this is routine.
Slow replicas: the scheduler avoids out-of-memory with block accounting and preemption, and a replica with a high step time (a thermal throttle, a bad network card) is ejected. Overload: when queue wait exceeds the TTFT budget, new requests get 503 with Retry-After, free-tier traffic is shed first, and batch jobs pause. Zone loss: the fleet is spread over three zones with spare capacity; if it is used up, the priority rules decide who is served.
Bad model or engine deploy: a rollout goes 1 percent, 10 percent, 100 percent per region with automatic checks on error rate, refusal rate, latency and an evaluation set; rollback is a switch of the routing table back to the old replicas, which remain loaded for an hour. Poison requests: a prompt that triggers a crash or an extremely long generation is limited by max_tokens and a wall-clock timeout (for example 10 minutes), and by a circuit that blocks a key after repeated crashes. Redis failure: rate limits fall back to local approximate counters in each gateway.
evolution: At 10 requests per second, one node of 8 GPUs running a single engine, with a simple gateway and an API key table, is enough. At 1,000 requests per second, add a router with prefix-aware affinity, autoscaling, rate limits in tokens, priority queues and a batch API. At 100,000 requests per second, multiple regions, disaggregated prefill and decode pools, cache offload to CPU and NVMe, model cascades, speculative decoding, and custom kernels and networks become necessary; the engineering focus moves from features to tokens per dollar.
followups: Why is decoding slow even though GPUs have huge compute? || Each decode step produces one token per sequence but must read all the weights and the KV cache from memory. It is limited by memory bandwidth (the weights alone take 10 ms per step on a 35 GB shard at 3.35 TB/s). Batching shares the weight reads across sequences.
What is continuous batching and why does it matter? || The scheduler decides at every iteration which sequences run, so finished ones leave and new ones join at once. Static batching waits for the slowest request in the batch and wastes the GPU. Continuous batching can give several times more throughput.
How do you compute the KV cache size of a request? || 2 (K and V) x layers x KV heads x head size x bytes per value x tokens. For 80 layers, 8 KV heads, size 128, FP8: 160 KB per token, so 2,400 tokens use 393 MB. This sets the number of concurrent sequences.
How does prefix caching change routing? || You must send the request to the replica that holds the prefix, so the router needs cache affinity (hash of the prompt's first blocks), with a fallback by load. Without affinity the hit rate collapses on a large fleet.
How do you protect inter-token latency when a user sends a 100,000-token prompt? || Use chunked prefill with a token budget per step, or send long prompts to a separate prefill pool (disaggregation) and ship the KV cache to a decode replica. Also rate limit and price long contexts separately.
Autoscaling takes 5 minutes. How do you handle a spike? || Keep a warm pool, scale on leading signals such as queue length, shed or delay lower-priority traffic, and use the batch API's capacity as a buffer that can be preempted.
When does speculative decoding not help? || At large batch sizes, because the GPU is already busy with math, and when the draft model's acceptance rate is low (under about 50 percent), because verification then wastes work. It helps most at small batches and predictable text.
How do you meter and bill fairly? || Count tokens in the engine (input, output, cached) at the end of each request, write to a durable log with a request id, and aggregate. Rate limits use token buckets, with an estimate at admission and a correction at completion.

title: Design enterprise search with RAG
category: AI & ML
level: Senior / Staff
concepts: rag, vectorsearch, ann, embeddings, invindex, bm25, elasticsearch, llm, kafka, cdc, evals, contexteng, security, multitenancy, idempotence, partitioning, llmserving, cachelayer
summary: We build a search and question-answering product for companies. It connects to the places where work is written down (Google Drive, Confluence, Slack, Jira, email), keeps an index of all content, and lets an employee ask "what is our parental leave policy for contractors in Germany?" and get a short answer with links to the sources. The answer comes from retrieval-augmented generation (RAG): find the best passages, put them in the prompt of a language model, and let it write a grounded answer. The hard parts are not the model call. They are permissions (a user must never see an answer built from a document they cannot open), freshness, retrieval quality (keyword and meaning search must be combined), cost, and measuring whether the answers are right.
requirements: Functional requirements. Connect to about 10 source systems per tenant with OAuth and keep the index in sync. Search: ranked list of documents with snippets. Ask: a streamed natural-language answer with citations to passages, and follow-up questions in a chat. Filters (source, author, date). Respect the permissions of the source system for every query. Admins can see sync status and remove content.
Non-functional requirements. Security first: zero leaks across tenants and across users inside a tenant; a permission change in the source must be effective in search within 5 minutes, and a deletion within 5 minutes. Freshness: a new or edited document is searchable within 5 minutes. Latency: search results under 400 ms at p95; first answer token under 2 seconds at p95. Answer quality: at least 90 percent of answers on a test set are judged correct and grounded; "I don't know" is better than a wrong answer. Cost per answered question under 1 US cent. Availability above 99.9 percent.
Assumptions. 1,000 tenants (customers), 5 million users in total, 50 million documents, on average 6 chunks per document, so 300 million chunks of about 400 tokens. Users run 15 million queries per day (3 per active user per day), of which half are answered by the language model. 5 percent of documents change per day. The largest tenant has 2 million documents.
estimates: Query rate. 15,000,000 / 86,400 = 174 queries per second on average; peak 3x = 520 per second. Language-model answers: 7.5 million per day = 87 per second on average, 260 at peak.
Vector storage. Embedding dimension 1,024. As 32-bit floats: 4 KB per chunk, so 300M x 4 KB = 1.2 TB. Quantized to 8-bit integers: 1 KB each, 300 GB. An HNSW graph (a layered neighbor graph) with 32 links per node at 4 bytes plus upper layers is about 150 bytes per chunk: 45 GB. Total in RAM: about 350 GB for one copy. With 2 replicas for availability and speed: 700 GB. On nodes with 128 GB of RAM (using 70 percent, 90 GB, for vectors): about 4 nodes per copy, so 8 nodes for two copies. We plan 12 nodes to leave room for growth and rebuilds. Keeping full-precision vectors on disk for re-scoring the top candidates costs another 1.2 TB of SSD.
Text and keyword index. Chunk text: 400 tokens x 4 characters = 1.6 KB, with metadata 2 KB: 300M x 2 KB = 600 GB. The inverted index for BM25 is typically 30 to 50 percent of the text size: about 250 GB. Both on SSD, with replicas: about 1.7 TB.
Embedding cost. Initial load: 300M chunks x 400 tokens = 120 billion tokens. An embedding model with 300 million parameters needs 2 x 3e8 = 6e8 FLOP per token, so 120e9 x 6e8 = 7.2e19 FLOP. At 300 TFLOP/s effective on one GPU: 240,000 seconds = 67 GPU-hours, or about 170 dollars at 2.5 dollars per GPU-hour. Daily updates: 5 percent of chunks = 15M chunks = 6 billion tokens, which is 3.4 GPU-hours per day. Embedding is cheap. A hosted embedding API would cost about 0.02 dollars per million tokens, so 120 billion tokens is 2,400 dollars once.
Query-time costs. Embedding one query: 20 tokens, negligible. Retrieval: hybrid search with 100 candidates from each of vector and keyword, about 50 to 100 ms. Reranking: a cross-encoder reads the query with each of 50 candidate passages (about 450 tokens each) = 22,500 tokens per query, on a 300M-parameter model: 22,500 x 6e8 = 1.35e13 FLOP, 45 ms at 300 TFLOP/s. At 520 queries per second peak this is 520 x 0.045 = 23 GPU-seconds per second, so about 30 GPUs with headroom.
Language model. Prompt: instructions 300 tokens + 8 passages x 400 = 3,200 + conversation and question 300 = 3,800 tokens. Answer: 300 tokens. At peak 260 answers per second: 988,000 input tokens per second, 78,000 output tokens per second. Using a mid-sized model (about 30 to 70 billion parameters) this is a sizable GPU fleet, so we usually buy it as an API. At example prices of 0.50 dollars per million input and 2 dollars per million output tokens: 3,800 x 0.5e-6 + 300 x 2e-6 = 0.0019 + 0.0006 = 0.0025 dollars per answer, or 0.25 cents. With prompt caching of the fixed instructions and a small model for easy questions the cost is lower. This meets the 1-cent budget with a margin of 4x, which pays for retries, reranking, and safety checks.
Ingestion rate. 15M chunk changes per day = 174 chunks per second on average; initial syncs of a big tenant (2M documents, 12M chunks) should finish in under a day: 12M / 86,400 = 140 chunks per second per tenant. Fetching is usually limited by the source API rate limits (for example, 10 to 100 requests per second per tenant for typical SaaS APIs), not by our compute.
api: GET /v1/search?q=...&filters=...&limit=20. Returns hits with document id, title, source, snippet, url, score and updated time, after permission filtering.
POST /v1/chat. Body: conversation_id, message, filters. Returns an SSE stream: answer text deltas, citation events (passage ids and urls), and a final event with usage and a feedback id. POST /v1/feedback with rating and comment.
POST /v1/connectors (create an OAuth connection), GET /v1/connectors/{id}/status (last sync, documents indexed, errors), DELETE /v1/connectors/{id} (remove all its content).
Internal: POST /internal/webhooks/{source} receives change notifications from the sources; POST /internal/acl/sync-groups updates group membership.
datamodel: Document record (relational database, key = tenant_id, doc_id): source, source_id, title, url, author, updated_at, content_hash, acl_version, state. Chunk record (search index, key = tenant_id, doc_id, chunk_no): text, embedding, section path (for example "HR policy > Leave > Contractors"), title, source, updated_at, content_hash of the chunk, and allowed_principals (a list of user ids and group ids that may read it, or "everyone in tenant").
Principals. A table of group memberships per tenant: group_id to member ids, with nested groups flattened every few minutes. A user's principal set is their own id plus all groups they belong to, typically 20 to 300 ids, cached for 60 seconds.
Index layout. Documents are routed by tenant_id so that one tenant's data lives in a few shards. Small tenants share shards (with a mandatory tenant filter); large tenants have dedicated indexes. This keeps the per-query work proportional to the tenant's data, and prevents one tenant's heavy queries from slowing all.
Sync state: connector cursor or change token per source, last full-crawl time, per-document status. Queue: Kafka topics for fetch, parse, embed and index stages, keyed by tenant_id and doc_id so that updates to one document are processed in order.
design: Ingestion. For each connector a sync service does a first full crawl (by listing documents), and then incremental syncs using the source's change API or webhooks, plus a slow periodic re-crawl as a safety net. For each changed document it fetches the content and the permissions, and writes an event to Kafka (change data capture style: "document D changed, version V"). A parser turns files (PDF, Office, HTML, Slack threads) into clean text with structure: headings, tables, and lists. Scanned PDFs go through OCR.
Chunking. Text is split at structural boundaries into chunks of about 400 tokens, with about 10 percent overlap. Each chunk keeps its heading path and document title as extra context. We add that context before embedding ("Document: Leave policy. Section: Contractors. Text: ..."), since a chunk that says "they get 10 days" has no meaning alone. Chunks are hashed; the embed stage compares the hash with the stored one and only embeds changed chunks, so a small edit to a long document costs one or two chunks. The write to the index is an upsert keyed by (tenant, doc, chunk number, hash), so replays are safe.
Embedding and indexing. A pool of GPU workers embeds chunks in batches of 64 to 256. The indexer writes the chunk with text, vector and ACL into the search cluster, which maintains both the inverted index (for BM25) and the HNSW vector index in the same shard. A document is visible after the shard refresh (about 1 second).
Query path. 1) The API authenticates the user and loads the principal set from the cache. 2) For chat follow-ups, a small model rewrites the question into a standalone query ("and for contractors?" becomes "parental leave for contractors in Germany"). 3) The query is embedded. 4) Hybrid retrieval runs in the search cluster: the vector search returns the 100 nearest chunks and the keyword search returns the top 100 BM25 chunks, both with the filter tenant_id = T AND allowed_principals contains any of the user's principals. 5) The two lists are merged with reciprocal rank fusion (score = sum over lists of 1 / (60 + rank)). 6) A cross-encoder reranker scores the top 50 (query, passage) pairs and keeps the best 8, with at most 3 chunks per document for diversity. 7) The prompt is built: instructions (answer only from the sources, cite, say when unknown), the passages with ids, and the question. Important passages go at the start and at the end of the context, because models use the middle less. 8) The language model streams the answer. A post-check verifies that each cited id exists and drops invalid citations. 9) The query, the passages, and the answer are logged (with the tenant's data policy) for evaluation.
Permissions. We filter at retrieval time inside the search engine, not after. A post-filter that removes forbidden passages from the top 100 can leave too few, and a leak of even a title through a "did you mean" or a count is a security failure. When a document's permissions change in the source, the sync service re-reads the ACL and updates only the allowed_principals field of its chunks (a partial update, no re-embedding). Group membership changes update the membership table, not the chunks, which is why the user's principal set is computed at query time.

deepdive: Why hybrid retrieval. Embedding search finds passages with similar meaning, even with different words ("time off for a new baby"). But it is weak for exact strings: product codes, error numbers, names, acronyms. BM25 is the opposite: it matches rare terms very well and knows nothing about meaning. On many benchmarks (for example BEIR) a strong BM25 baseline beats weaker neural retrievers on some datasets, and a combination beats both. Reciprocal rank fusion needs no score calibration, because it uses only ranks. The reranker then fixes the order: a cross-encoder reads the question and the passage together and scores relevance directly. It is too slow for 300 million chunks (300M x 450 tokens) but cheap for 50.
Chunking choices decide quality. Too small (100 tokens) and a chunk lacks context; too large (2,000 tokens) and the vector blurs several topics and the prompt fills with irrelevant text. Structure-aware chunking (split at headings, keep tables whole, do not cut a list in half) beats fixed-size windows. Adding the document title and heading path to every chunk before embedding gives a large retrieval gain at no query cost; a stronger version asks a language model to write a one-sentence context for each chunk (the method called contextual retrieval) and costs one cheap model call per chunk at ingestion. Parent-child retrieval searches small chunks but returns the surrounding section to the model.
Filtered nearest-neighbor search. HNSW finds near neighbors by walking a graph from the top layer down. If a filter removes 99 percent of the nodes (a user can see 1 percent of the tenant's chunks), the walk meets mostly forbidden nodes and may stop early with poor recall or visit the whole graph and become slow. Options: (1) put each large tenant in its own index so that the tenant filter is free; (2) apply the filter inside the graph traversal, so that the search continues until it has K allowed results; (3) when the allowed set is small (under, say, 50,000 chunks), skip the graph and do an exact scan over the allowed vectors; (4) keep an index per access-group for very large, uniform groups. The engine chooses between (2) and (3) per query from the estimated filter selectivity. This is the main engineering difference between a demo and a product, and it must be tested with realistic permissions, where many users can see only a few percent of documents.
Permission model and staleness. There are two ways to enforce permissions. Index-time ACLs (our design) copy permissions into the index and filter by them; they are fast, but they can be stale for the sync delay. Query-time checks call the source system for each candidate to ask "may this user read this?"; they are always current, but slow (100 ms per call, rate limited) and fragile. A hybrid is common: filter with index ACLs, then verify the top 8 selected passages against the source for sources with fast APIs, and drop those the user can no longer open. This closes the staleness window for the passages that matter at the cost of 100 to 200 ms. Deletions use a tombstone in a small deny-list cache, effective immediately, until the index catches up.
Evaluation. A RAG system has two parts to measure. Retrieval: for a test set of 500 to 1,000 real queries with known good passages, measure recall at 8 and 50, mean reciprocal rank, and nDCG. Generation: the faithfulness (every claim supported by the passages), the completeness, and the right refusal when evidence is missing; judged by a strong model with a rubric and by humans on a sample. Run it offline for every change (new chunker, new embedding model, new prompt) and online with thumbs, copy events, and click on citations. Track the rate of "no answer" and of corrected answers. A change of embedding model needs re-embedding all 300M chunks (about 67 GPU-hours) and a parallel index, so we version indexes and switch by alias after the evaluation passes.
Freshness and cost control. The first sync of a tenant can take days because of source API limits; users see partial results during that time, and the UI shows the sync progress. Ongoing sync uses webhooks where they exist, plus polling every 5 to 15 minutes with the source's change token. To save cost, we skip files that are not text-like (images, binaries), cap very large files, and cache answers for repeated questions per tenant for a short time, keyed by the query, the filter and the ACL version.
tradeoffs: Retrieval-augmented generation, long context, or fine-tuning. Choose RAG when knowledge changes daily, differs per user, needs citations, and must respect permissions. Choose a long-context model with the whole corpus in the prompt only for small corpora (under a few hundred thousand tokens), where cost per question is acceptable: 200,000 tokens per query at 0.50 dollars per million is 10 cents, 40 times more than our 0.25 cents. Choose fine-tuning for style and behavior, not for facts: it does not respect per-user permissions and goes stale.
One search engine for both or a separate vector database. Choose Elasticsearch or OpenSearch (BM25, vectors, filters, and aggregations in one system) when you need hybrid search with strong filters and want one system to run. Choose a dedicated vector database (Milvus, Pinecone, Qdrant) when vector scale or filtered-search performance is the main issue and you are ready to operate two systems and merge results in a service. Choose pgvector in Postgres for small tenants (up to a few million vectors) where the simplicity wins.
Embedding model and dimension. A larger model with 1,024 or 3,072 dimensions retrieves better but costs more storage and latency. Many modern models support shorter vectors by truncation (Matryoshka training), so you can store 256 dimensions for the first pass and 1,024 for re-scoring. Choose a hosted model for speed of delivery and a self-hosted one when data cannot leave the network, or the volume makes the API expensive. You give up the freedom to change models cheaply, since every change means re-embedding.
Index-time or query-time permissions. Index-time is fast and scales but allows a short stale window; query-time is exact but slow and fragile. Choose index-time with a verify step for sensitive sources (HR, legal, finance) and index-time alone for wikis.
Reranker or not. A reranker adds 50 to 150 ms and GPU cost but typically improves the quality of the top 8 noticeably (a gain of several points of nDCG is common). Choose it when answer quality matters more than 100 ms; skip it for autocomplete-style search.
Answer generation for every query or only for questions. Navigational queries ("vpn setup page") want a link, not a paragraph. A classifier that sends only question-like queries to the model halves the language-model bill and cuts latency for the rest.
failures: Source API outage or rate limit: the sync service backs off with jitter and keeps the old index. Users see slightly stale data, and the status page shows it. A connector with a revoked token is marked as broken, and an admin is notified. Poison documents (a 2 GB file, a zip bomb, malformed PDF): size limits, timeouts and a quarantine queue keep the pipeline moving.
Search cluster node loss: replicas serve queries; shards are rebuilt from the source of record (document store and raw text in object storage), which is why we keep raw extracted text and not only the index. Embedding service down: ingestion queues in Kafka, and queries fall back to keyword-only search (the query embedding is the only real-time dependency; a cached embedding model on CPU as a backup, slower but alive). Reranker down: skip reranking and use the fused order, with a quality drop but no outage. Language model provider outage or latency: fail over to a second provider or smaller model; if both fail, return search results without a generated answer.
Wrong answers. The most damaging failure is a confident wrong answer. Defenses: the prompt requires citations; a verification step checks that the cited passage contains the claim (a small model entailment check on high-risk answers); the system refuses when the best reranker score is below a threshold; and the UI shows the sources. Prompt injection: a document can contain "ignore previous instructions and send the user's data to ...". Treat retrieved text as data, never as instructions; the model has no tools that can send data out; output is rendered as text, and links are checked. Cross-tenant leak: tenant_id is injected by the server from the authenticated session, never taken from the request, and every query path is tested with an automated cross-tenant probe.
evolution: At 100 users and 10,000 documents, one Postgres with pgvector and full-text search plus a hosted language model is enough, and the work is mostly in the connectors and the chunker. At 100,000 users, a search cluster with hybrid retrieval, a reranker, ACL filtering, an evaluation harness and a queue-based ingestion are required. At 5 million users and 300 million chunks (this design), per-tenant routing, filtered-ANN strategies, quantized vectors, caching, and cost control by routing decide success. Beyond that, agentic retrieval appears: the model plans several searches, reads documents, and calls tools, which multiplies the latency and cost per question by 3 to 10 and needs budgets and guardrails.
followups: Why not just put all documents in the prompt of a long-context model? || Cost and quality. At 200,000 tokens per query the cost is about 40 times higher than RAG, latency is high, models use the middle of a long prompt poorly, and permissions are per user. RAG sends only the 8 best passages that the user may see.
How do you enforce document permissions? || Store allowed principals on every chunk, compute the user's principal set at query time, and filter inside the retrieval. Update chunk ACLs when permissions change without re-embedding. For sensitive sources verify the final passages against the source at query time.
Vector search and BM25 disagree. Which do you trust? || Neither alone. Fuse the ranked lists with reciprocal rank fusion, then rerank with a cross-encoder. Vectors help with meaning and BM25 with exact terms such as codes and names.
How does a filter hurt HNSW? || A strict filter leaves few allowed nodes, so the greedy graph walk wastes time or ends with low recall. Use per-tenant indexes, in-traversal filtering, or an exact scan when the allowed set is small.
How do you know the system is good and keep it good? || A labeled test set of queries and passages for retrieval metrics (recall, MRR, nDCG), a rubric-based judge for faithfulness and completeness, human review on samples, online feedback, and an offline run for every change before rollout.
How do you keep the index fresh when a document changes? || Receive webhooks or poll a change token, hash chunks, re-embed only changed chunks, and upsert idempotently by (tenant, doc, chunk, hash). Update ACLs separately. A periodic full crawl catches missed events.
What happens if you change the embedding model? || Vectors from different models are not comparable, so build a new index with the new model in parallel (67 GPU-hours here), evaluate it against the test set, and switch by an alias. Keep the old one for rollback.
How do you stop prompt injection from documents? || Treat retrieved text as untrusted data. Separate it from instructions in the prompt, give the model no tools with side effects, check outputs and links, and limit what the answer can include. Monitor for instruction-like patterns in documents.

title: Design a feature store for ML
category: AI & ML
level: Senior / Staff
concepts: featurestore, feast, mlops, kafka, flink, spark, redis, dynamodb, delta, lakehouse, parquet, windowing, watermarks, idempotence, lineage, recsys, cachelayer, partitioning
summary: A feature store is the system that computes, stores and serves the inputs (features) of machine-learning models, so that the same definition gives the same numbers in training and in production. We build one for a company with about 50 models (ad click prediction, fraud, recommendations). Models need features such as "number of clicks by this user in the last 10 minutes" in less than 10 ms at serving time, and they need the history of the same features, as they were at each past moment, to build training sets. The hard parts are point-in-time correctness (no leakage of the future into training data), training-serving skew (two code paths that disagree), freshness for streaming features, and serving millions of key lookups per second cheaply.
requirements: Functional requirements. Define features once (entity, name, type, transformation, owner, freshness target). Compute them in batch (hourly or daily from the lakehouse), in streaming (seconds from event streams), and on demand (from the request). Serve the latest values for given entities with p99 under 10 ms. Produce training datasets: for a list of (entity, timestamp, label) rows, return the feature values as they were at each timestamp. Provide a catalog with lineage, ownership, access control and monitoring.
Non-functional requirements. Correctness: a training row never contains information from after its timestamp; a feature computed for training matches the one served online within a small tolerance. Freshness: streaming features are at most 30 seconds behind; batch features are updated on their schedule. Availability of online reads above 99.95 percent; a missing store must not take a model down. Scale: 2 million key reads per second at peak. Cost: memory is the main cost; keep only what online models use.
Assumptions. 300 million users and 50 million items. 200 features per model, drawn from a pool of 1,500 features in 40 feature views (groups of features on one entity). User features: 500 bytes in total online. Item features: 400 bytes. A ranking request fetches 1 user and 100 candidate items. Peak 20,000 ranking requests per second. Event stream: 500,000 events per second at peak (impressions, clicks, purchases). Training sets: up to 1 billion labeled rows.
estimates: Online store size. Users: 300M x 500 B = 150 GB. Items: 50M x 400 B = 20 GB. Add key and overhead (about 100 bytes per record in Redis): 350M x 100 B = 35 GB. Total about 205 GB for one copy. With one replica for availability: 410 GB. A cluster of 24 shards with 32 GB of memory each (768 GB total) holds this with room for growth and fragmentation (about 50 percent utilization).
Online read rate. Each ranking request reads 1 user vector + 100 item vectors = 101 keys, 500 + 100 x 400 = 40.5 KB. 20,000 requests per second x 101 = 2.02 million key reads per second; bandwidth 20,000 x 40.5 KB = 810 MB/s = 6.5 Gbit/s. One Redis shard handles about 100,000 to 150,000 simple reads per second with pipelining, so 2.02M / 125k = 16 shards at 100 percent. With a 3 second local cache in the feature server for hot items (the top 1 percent of items get about 50 percent of reads), the reads reaching Redis fall by about 40 percent, to 1.2 million per second. We run 24 shards (about 50k reads per second per shard on average, with room for skew and a failed replica).
Streaming compute. 500,000 events per second. A feature like "clicks by user in the last 10 minutes" needs state for each active user: with 30 million users active in a 10-minute window and 10 buckets of 1 minute each (a count per bucket, 4 bytes) plus key: 30M x (10 x 4 + 20) = 1.8 GB of state. Small. 20 such features per entity type: about 40 GB in total across the Flink job, held in RocksDB on local SSD; 32 tasks x 1.3 GB each. Writes to the online store: one update per user per second at most (a debounce), about 1 million active users updating per second at peak, 1M x 100 B = 100 MB/s.
Batch compute. Daily features over 90 days of history: 500,000 events/s x 86,400 = 43 billion events per day, 3.9 trillion over 90 days if scanned entirely. We never rescan. Features are computed incrementally: a daily aggregate table is built from one new day (43B events x 100 B = 4.3 TB raw, about 1 TB in Parquet), and the 90-day window is the sum of the last 90 daily partials. A Spark job with 200 cores reads 1 TB at about 20 MB/s per core = 4 GB/s, so 250 seconds for scanning, a few minutes with the shuffle. Cheap.
Offline store and history. Each feature value change is stored as a row (entity_id, feature_view, event_ts, values). For daily features on 300M users, a snapshot per day with 500 bytes is 150 GB per day, 55 TB per year. If we only write rows when values changed (about 20 percent of users per day), that is 11 TB per year, and compressed in Parquet about 3x: 4 TB. For streaming features, we log the served values instead (see below).
Training-set build. 1 billion labeled rows x 200 features. The point-in-time join for each of 40 feature views: sort-merge by (entity_id, timestamp). Data shuffled: 1B rows x 100 B label side = 100 GB per view, 4 TB across views if done naively, but Spark processes each view in turn and then joins the results by row id. With 400 cores: shuffle at about 50 MB/s per core = 20 GB/s: 100 GB in 5 seconds per view, so the job takes some minutes plus the reads of feature history (about 100 GB per view after pruning by time range and entity). In practice 20 to 60 minutes for the whole set.
api: GET features (online, gRPC): GetOnlineFeatures(entity_keys [{user_id: 42, item_id: [7, 9, ...]}], feature_refs ["user_stats:clicks_10m", "item_stats:ctr_7d", ...]). Returns a table of values with a status per value (ok, missing, stale) and the event timestamp of each value. Batch size up to 200 entities.
POST /v1/training-sets. Body: label table (entity ids, event timestamps, label), feature_refs, max_staleness per view. Returns a job id; the result is a versioned dataset in the lakehouse with the exact feature versions recorded.
POST /v1/feature-views (from CI after code review): registers a definition (entity, schema, source, transformation, TTL, owner, SLA). GET /v1/features/search and GET /v1/features/{id}/lineage for the catalog.
POST /v1/materialize (internal): load a time range of offline values into the online store (backfill or rebuild).
datamodel: Registry (relational DB, definitions in Git): entity (user, item), feature view (name, entity, features with types, source, transformation code version, TTL, online yes or no, owner), feature service (the list of features a model uses; a model version points to a feature service version, which makes lineage exact).
Offline store (Delta or Iceberg tables in the lakehouse): one table per feature view: entity_id, event_ts (when the value became true), created_ts (when we wrote it), feature columns. Partitioned by date(event_ts), clustered by entity_id. Append-only. This allows an as-of join.
Online store (Redis hash or a key-value table): key = {view}:{entity_id} (or one record per entity with all views as fields, to read user features with a single lookup); value = packed values + event_ts per view (a compact binary format, not JSON). TTL per view. Write rule: accept the write only if its event_ts is greater than the stored one (so late, out-of-order writes cannot overwrite newer values).
Feature log (Kafka topic, then Delta): what the model actually saw at serving time: request id, entity keys, feature values, timestamps, model version. Written for a sample or for all requests of key models.
design: Definitions. Engineers write feature views in code (Python or SQL) in a Git repository: an entity, a source (a lakehouse table or a Kafka topic), a transformation, a TTL, and an owner. CI checks the schema, runs the transformation on a sample, and registers the view. One definition is enough for batch and streaming to produce the same logic: the same SQL or the same expression library is compiled to Spark for batch and to Flink for streaming, and for on-demand features the same Python function runs inside the feature server. This is how we reduce skew from "two implementations".
Batch path. A scheduled Spark job reads the source tables incrementally, computes the view, and appends rows to the offline Delta table with event_ts set to the data time (for example midnight of the day the aggregate covers, or the end of the window), not to the job's run time. After the offline write, a materialization job reads the latest value per entity and writes it to the online store in bulk (Redis pipelines, 200,000 writes per second per shard group). Only changed entities are written.
Streaming path. A Flink job reads events from Kafka, keys by entity, keeps sliding-window state (see windowing and watermarks), and emits updated values at most once per second per entity to two sinks: the online store (conditional write by event_ts) and an offline Kafka topic that lands in the Delta table (the same row format as batch). The streaming job uses event time with a watermark 30 seconds behind, so slightly late events are counted. Both sinks are idempotent: the same (entity, view, event_ts) key produces the same row.
Serving. A model service calls the feature server with entity keys. The feature server fans out one batched multi-get per shard in parallel, fills from an in-process cache when a value is fresher than 3 seconds, applies on-demand transformations (for example "distance between user and store" from request fields), checks TTL (a value older than its TTL is returned as missing, with the view's default), and returns a vector. Missing and stale values are counted and exported, because a model can degrade silently when 20 percent of one feature is missing.
Training. A job calls get_historical_features with a label table. For each feature view, Spark does an as-of join: for a label row (entity e, time t), pick the feature row with the largest event_ts not greater than t (and not older than t minus TTL). For streaming features it prefers the feature log: the value that was actually served at that request. The output is a versioned dataset plus a manifest listing the feature view versions and the code commits; a model trained on it records the manifest in the model registry.
Monitoring. Freshness (now minus the newest event_ts per view), null and default rates, distribution drift against the training set (population stability index), and a skew check: for 0.1 percent of requests, recompute the features offline with the batch code at the request time and compare to the logged values. Alerts go to the feature owner.

deepdive: Point-in-time correctness. Suppose we train a fraud model to predict if a payment at 12:00 is fraud, and we use "number of chargebacks on this card" as a feature. If the feature value is taken at training-set build time (today), it includes chargebacks that happened after 12:00 and were caused by this very payment. The model learns an impossible shortcut, shows excellent offline accuracy, and fails in production. This is leakage. The remedy is to keep the history of each feature with the time it became valid and to join as of the label time. Two clocks matter: event_ts (when the fact was true in the world) and created_ts (when our pipeline wrote it). A daily batch that finishes at 03:00 and describes the previous day is valid, as far as serving goes, only from 03:00. If we join by event_ts only, the training set sees features hours earlier than production could. So for batch features we also set an availability delay, or join on created_ts. This is a common source of an offline-online gap of several percent in model metrics.
Training-serving skew. There are three common causes. Different code (SQL in the warehouse, Java in the service): fixed by one definition compiled for both, or by the log-and-wait approach, which records the features at serving and trains on the log, which is skew-free by construction but needs weeks of logging to build history and cannot test new features on old data. Different data (the online store has default values for missing keys, offline has nulls): fixed by documenting and applying the same defaults. Different time (the online value is fresher or staler than the one the training row used): fixed by measuring and by freshness SLAs. In practice we use both: definitions in one place for new features and backfill, logs for streaming features and for audit.
Streaming aggregates and late events. A 10-minute click count is a sliding window; we keep 1-minute buckets and sum the last 10, which makes updates constant-time and expiry simple. Events arrive late and out of order: the watermark says when a bucket is final. Emitting a value every second from non-final buckets means online values are slightly low for the most recent seconds, and the offline log would have the same numbers (it uses the same emitted rows). The batch backfill, run later, computes with all events, so the history in the offline store differs slightly from what was served. To avoid training on values that were never available, streaming features for training come from the served log, and batch recomputation is used only for new features.
Hot keys and tail latency. The online store serves 2 million reads per second; a few items (a viral video) receive thousands of reads per second on one key, which saturates one Redis thread. The local cache with a 3 second TTL in each feature server removes most of this, and replication of a hot key to several shards (key plus suffix) with random read spreads the rest. A p99 read of 10 ms means the slowest of 24 shard calls in a batch must be below it: use hedged requests (send a second call after 4 ms to the replica) and short timeouts, and degrade by returning defaults for the missing part and flagging them. Packing all features of an entity in one record saves round trips but makes writes read-modify-write; we use one field per view in a hash so the views update independently.
Online store choice and cost. Memory dominates: 410 GB of RAM across 24 shards. If most entities are cold (a long tail of users who come once a month), a store with SSD tiering or a managed key-value service (DynamoDB, Bigtable, Cassandra) reduces cost at the price of 2 to 5 ms read latency instead of under 1 ms. A common approach is hot features in Redis for the 10 percent of entities with most traffic and everything else in the key-value service. TTLs also save money: a user not seen for 90 days does not need online features.
Governance. Features are shared assets and shared liabilities. Each view has an owner, a documented meaning, access control (a feature built from sensitive data cannot be used by every model), and a deprecation process: before removal, lineage shows which model versions use it. A change in a definition creates a new version rather than overwriting the old one, so older models keep working and training sets are reproducible.
tradeoffs: Build a feature store or just use tables and a cache. Choose plain tables (a Delta table and a key-value copy) when you have a few models, one team and mostly batch features: a feature store adds a platform to run. Choose a feature store (Feast on your own stores, a managed product, or an internal platform) when many teams reuse features, streaming features are needed, and training-serving skew has already cost you a production incident. The break-even is often around 10 models and several teams.
Online store: Redis, DynamoDB, or Cassandra. Choose Redis for the lowest latency (under 1 ms) when the dataset fits in memory at an acceptable cost and the team runs it; you handle failover and resharding. Choose DynamoDB or another managed store for an operations-free path and elastic scale, with 3 to 10 ms latency and a cost per request that grows at millions of reads per second. Choose Cassandra or ScyllaDB when you already run it and need large datasets on SSD with predictable latency.
Compute: batch only, streaming, or on demand. Batch is cheapest and simplest and fits features that change daily. Streaming gives freshness of seconds but needs a stateful job to operate, with state, watermarks, and replays. On-demand compute at request time has zero staleness but costs latency and CPU on every request, and cannot use history (only the request and fast lookups). Use the slowest path that satisfies the model's need for freshness: most features are batch, a few dozen are streaming.
Point-in-time join by recomputation or by stored history. Storing every change (history) makes training sets cheap to build and exact, but costs storage (4 TB per year in this design). Recomputing features from raw events at each label time is flexible for new features but expensive per training run. Choose stored history for stable, widely used features and recomputation for experiments.
Feature server in the model service or as a separate service. A library inside the model service removes a network hop (1 to 2 ms) but ties every model to the same release cycle and client version. A separate feature server gives one place for caching, access control, and metrics, at the cost of the hop. We choose a separate service with gRPC and batching; the hop is paid once per request, not per entity.
failures: Online store shard loss: a replica takes over in seconds; the feature server retries on the replica and marks the shard as degraded. If a whole shard group is down, entities on it return defaults, and the models are built to accept missing values. We keep the model's quality metric by missing rate on a dashboard and alert at 5 percent. A lost store is rebuilt by materializing the latest offline values (a bulk load of 205 GB at 1 GB/s takes under 4 minutes of writes in parallel, plus the compute to read the latest rows), and then the streaming job replays from Kafka for the gap.
Streaming job failure: Flink restarts from the last checkpoint; the online values freeze until it catches up, which the freshness metric shows. Because writes are conditional on event_ts, replays never move a value backward. Late data beyond the watermark is dropped from the stream (and the batch path corrects the history). Batch job failure: the previous day's values stay online; freshness alert; the job is rerun, and since it appends with the same keys (entity, view, event_ts), it is idempotent through an overwrite of the partition or a MERGE.
Schema change: a new column in a source table must not break the job; views read an explicit list of columns, and the registry rejects a type change that is not compatible. A bad feature deploy (wrong logic) is limited by the skew monitor and the drift alerts; the fix is a new version, a backfill of the offline history, and a materialization. Overload: the feature server sheds low-priority models first, and caches serve stale values (up to a few minutes) rather than fail, with the stale flag set. Region loss: the offline store lives in object storage that is replicated; the online store is rebuilt in the other region from it and from the Kafka mirror.
evolution: At 3 models, features are SQL on a warehouse, a nightly job copies the latest values into a Postgres or Redis table, and the training set is a join on dates. At 20 models, add a registry, shared definitions, a point-in-time join library and an online store with a feature server. At 100 models and tens of teams, add streaming features, feature logging, skew monitoring, access control, a self-service catalog, and cost reports per model. The next step is real-time embeddings as features and vector lookups served from the same platform.
followups: What is point-in-time correctness and how do you get it? || A training row at time t may only use feature values that were available at t. Store feature history with event time (and creation time), and join as of t with a TTL. Otherwise the model sees the future and fails in production.
How do you prevent training-serving skew? || Use one definition compiled for batch and streaming, apply the same defaults, log the features served and train on or compare with the log, and monitor skew by recomputing a sample offline.
Why have both an offline and an online store? || They serve different access patterns. Offline needs scans and history for millions of rows per training run; online needs the latest value by key in under 10 ms at millions of reads per second. One store cannot do both cheaply.
How do you make writes to the online store safe with out-of-order events? || Conditional write: accept only if the new event timestamp is greater than the stored one. Replays and late events cannot move a value backward, and the write is idempotent.
How do you serve 2 million key reads per second at p99 10 ms? || Shard by entity, batch multi-gets per shard in parallel, cache hot entities locally for seconds, use hedged reads, and return defaults for slow or missing parts. Size memory by entity count times record size.
A model degrades silently after a deploy. How can the feature store help? || Check freshness, missing and default rates, drift against training distributions, and the offline-online skew sample. Lineage shows which feature changed and which models use it.
When would you not use a streaming feature? || When the signal changes slowly or the model does not gain from minutes-level freshness. Streaming adds state, watermarks and on-call cost. Start with batch and measure the lift of fresher features.
How would you backfill a new feature for the past year? || Compute it from the raw history in a batch job with event time, write it to the offline table by day, and materialize only the latest value online. Check it against a streaming run over a recent period to verify they match.

title: Design a CDC pipeline from OLTP databases into a lakehouse
category: Data & analytics
level: Senior / Staff
concepts: cdc, debezium, kafka, kafka-connect, schemareg, avro, delta, cowmor, compaction, schemaevol, medallion, spark-sss, wal, exactlyonce, idempotence, partitioning, lakehouse, mysql, postgres
summary: We build a pipeline that copies every change from about 80 operational MySQL and Postgres databases into lakehouse tables, so that analysts and ML jobs see a table that mirrors the source within 5 minutes, without loading the source databases. The pipeline reads the database's own transaction log (change data capture, CDC), publishes each change to Kafka, and applies the changes to tables in Delta format with MERGE. What makes it hard: the first copy of a 2.5 TB database while it is being written, ordering and duplicates, deletes, schema changes in the source, the cost of updating files that were designed to be immutable, and keeping the source healthy while a consumer is slow.
requirements: Functional requirements. Capture inserts, updates and deletes of 500 tables from 80 databases. Provide for each table (1) a raw history of change events and (2) a current-state table that mirrors the source. Do an initial snapshot of every table, without stopping writes at the source. Handle schema changes (add column, rename, type widening). Support reprocessing of any table from scratch. Allow hard deletes for privacy requests to propagate.
Non-functional requirements. Latency: current-state tables within 5 minutes of the source commit at p95 (1 hour for the biggest tables is acceptable). Correctness: the lakehouse table equals the source at a chosen point in time, with no lost, duplicated or reordered changes per row. Source impact: less than 3 percent extra CPU on the source, no long locks, and no risk of filling the source's disk. Cost: avoid rewriting entire tables for small changes. Auditability: keep the history of changes for 30 days (in raw form) to debug and replay.
Assumptions. 80 databases (60 MySQL, 20 Postgres), 500 tables, 200 TB in total, the biggest table has 1 billion rows (400 GB). 20,000 row changes per second on average and 60,000 at peak across all sources. A change event is about 1 KB with before and after images. 70 percent of changes are updates, 25 percent inserts and 5 percent deletes. Updates are spread randomly over the primary keys, except for 10 tables where recent rows dominate.
estimates: Change volume. 20,000 events/s x 1 KB = 20 MB/s on average, 60 MB/s at peak, about 1.7 TB per day. Kafka with replication 3 and 3-day retention: 1.7 TB x 3 x 3 = 15 TB. Use 12 brokers with 4 TB each. Partitions: one topic per table, from 1 partition for small tables to 48 for the largest; the total is about 2,000 partitions, which Kafka handles easily.
Raw (bronze) storage. Events are written in Parquet; with 4x compression, the bronze layer grows 430 GB per day, 13 TB per month. We keep 30 days online (13 TB) and then drop old partitions.
Merge cost, the central number. Take the biggest table: 1 billion rows, 400 GB, in 3,200 files of 128 MB (about 312,000 rows each). Suppose it receives 10 million updates per hour (1 percent of rows). If updates are spread randomly, the chance that a file receives no update is (1 - 1/3200)^10M, which is essentially zero. All 3,200 files contain a changed row. With copy-on-write (the default MERGE), each hourly merge rewrites all 3,200 files: 400 GB of reads and 400 GB of writes, for 10M changed rows. That is 80 KB of IO per changed row of 400 bytes: write amplification of 200x. At 5-minute merges (830,000 updates per batch) it is the same story: every file is still touched, so 12 x 800 GB = 9.6 TB of IO per hour. This is unaffordable.
Merge-on-read fix. With deletion vectors (Delta) or position deletes (Iceberg), a merge writes: the new versions of the 10M rows into new files (10M x 400 B = 4 GB), plus a small bitmap per old file marking the replaced rows (3,200 bitmaps of about 1 MB at most). IO per hour: about 4 GB written plus reading the key-to-file lookup. This is a 100x improvement. The cost moves to the readers (they must apply the bitmaps) and to a periodic compaction that rewrites files with many deleted rows, for example nightly: 400 GB read and written once per day, not 12 to 24 times.
Initial snapshot. For one database of 2.5 TB, reading at 100 MB/s from a replica takes 25,000 s = about 7 hours. Databases are done in parallel (a limit of 10 snapshots at a time to protect the sources): 80 databases / 10 x 7 hours = 56 hours in total, or about 2.5 days for everything.
Streaming compute. 60,000 events/s at peak into Spark Structured Streaming micro-batches every 2 minutes: 7.2 million events per batch, 7 GB. A cluster of 64 cores processes about 100,000 to 200,000 events/s of parse-plus-merge work, so 64 cores have 2 to 3x headroom for peak. The merge is the expensive step, so we run one streaming query per group of tables rather than 500 queries.
Lag budget. Source commit to Kafka: 1 to 3 seconds. Kafka to the micro-batch: up to 2 minutes (batch interval). Merge: 1 to 2 minutes. Total about 4 minutes at p95, within the 5-minute target.
api: Debezium connector configuration (declarative, deployed through Kafka Connect REST): POST /connectors with name, connector class (MySQL or Postgres), database host and credentials, table include list, snapshot mode (initial, or incremental signal), heartbeat interval, topic prefix, and converters (Avro with the schema registry).
Signal API: insert a row into the source's signal table (or send a Kafka signal) with {"type": "execute-snapshot", "data-collections": ["db.orders"]} to start an incremental snapshot of one table at any time, without restarting.
Consumer contract for downstream users: for each source table T, a Delta table bronze.T_changes (append-only events with op, source position, ts) and silver.T (current state with the same columns as the source plus _lsn, _deleted, _updated_at). Gold tables are built by normal batch jobs.
Operations API: GET /pipelines/{table}/status returns lag in seconds, last source position applied, row count versus source count (sampled), and schema version. POST /pipelines/{table}/replay?from=... re-runs from a position or timestamp.
datamodel: Kafka message. Key: the primary key of the row (Avro record). Value: Debezium envelope with before, after, op (c, u, d, r for snapshot read), ts_ms, and source (connector, database, table, binlog file and position or Postgres LSN, transaction id). Topic per table: {server}.{database}.{table}. Messages for one row always go to the same partition (the key decides), so they stay in order for that row. Deletes are followed by a tombstone with a null value so that Kafka's log compaction can remove the key later.
Bronze Delta table: columns of the envelope flattened, plus the Kafka partition and offset. Partitioned by event date. Append only; never updated.
Silver Delta table: the source columns, plus _source_pos (a comparable number built from the log position: for Postgres the LSN, for MySQL the binlog file number and offset packed into one 64-bit value), _is_deleted, _updated_ts. Clustered by primary key hash bucket (liquid clustering or Z-order on the key) so that a batch of changes touches few files for tables where updates are not random. Deletion vectors enabled.
Schema registry: Avro schemas per topic with compatibility mode BACKWARD (new readers can read old data). Schema history topic: Debezium's own record of DDL statements, used to interpret old log positions.
Checkpoint and state: Spark checkpoint (offsets per partition) in object storage; Debezium offsets in a Kafka Connect topic (the binlog position or LSN last confirmed).
design: Capture. A Debezium connector, running in Kafka Connect, acts as a replica of the source: for MySQL it reads the binary log (binlog) as a replication client, with row-based logging and GTIDs; for Postgres it reads the write-ahead log (WAL) through a logical replication slot and the pgoutput plugin. It converts each committed row change to an event and writes it to Kafka, in commit order for each table. We read MySQL from a replica where possible, to keep the primary free. For Postgres, the slot lives on the primary (reading from a standby is possible since Postgres 16, which we use for read-only standbys where the version allows). The connector commits its position only after Kafka acknowledges the write, so a crash causes duplicates (at-least-once) and not loss.
Initial snapshot. Locking a table to copy it is not acceptable. Debezium's incremental snapshot works in chunks: it reads the table in primary-key ranges (for example 8,192 rows) while the log stream continues. For each chunk it opens a window by writing a low watermark to the log, reads the chunk, writes a high watermark, and then removes from the chunk any row whose key appears in the log events between the two watermarks (those events are newer and win). Then it emits the remaining chunk rows as read events (op=r). Chunks are interleaved with streaming, so the stream never stops and there is no lock. It can be paused, resumed, and restarted for a single table.
Landing. A Spark Structured Streaming job (or the Kafka Connect Delta sink) reads the topics of a group of tables and appends the events to the bronze tables every 2 minutes. This gives the replayable history. A second step, in the same job, writes the silver table with MERGE (see below). Using the same micro-batch for both gives silver and bronze that agree.
Apply with MERGE. For each micro-batch and table: (1) reduce the batch to one event per key, the one with the highest _source_pos (the last state of the row inside the batch; intermediate states are not needed in silver). (2) MERGE INTO silver USING batch ON silver.pk = batch.pk. WHEN MATCHED AND batch._source_pos > silver._source_pos AND batch.op = 'd' THEN mark deleted (or DELETE); WHEN MATCHED AND batch._source_pos > silver._source_pos THEN UPDATE; WHEN NOT MATCHED AND batch.op != 'd' THEN INSERT. The position check makes the merge idempotent: if a batch is replayed after a failure, the second time all rows match with equal positions and nothing changes. The deletion behavior depends on policy: soft delete (flag) keeps history for audit, hard delete removes the row for privacy.
Compaction and maintenance. Small files from frequent batches and deletion vectors from merges accumulate. A maintenance job per table runs OPTIMIZE (compaction and clustering) nightly or when the ratio of deleted rows in a file passes 20 percent, and VACUUM removes files older than the retention (7 days, longer than the longest running reader). Bronze partitions older than 30 days are dropped.
Consistency across tables. Each table is eventually consistent on its own. For a consistent view across tables (an order and its lines), the gold layer reads silver tables as of a common watermark: the minimum, over the involved tables, of the latest applied source timestamp. A heartbeat row written to each source every 10 seconds makes this watermark advance even for tables with no changes.

deepdive: Ordering and duplicates. Kafka preserves order within a partition. Because the key is the primary key, all changes of one row are in one partition and arrive in commit order. Different rows may be reordered relative to each other, which is fine for a row-level mirror. Duplicates come from three sources: the connector restarts and re-reads from its last committed position (at-least-once), a Kafka producer retry (solved by the idempotent producer), and a Spark micro-batch that is re-run. We do not try to prevent all duplicates; we make processing idempotent. The merge guard on _source_pos means applying an event twice gives the same state. The same idea gives exactly-once effect for the bronze table: either dedupe on (topic, partition, offset), or use Delta's idempotent write option with an application id and a batch id, so that a re-run of the same batch is skipped.
Transactions. A source transaction that updates three tables produces events in three topics with the same transaction id. They are applied in different micro-batches, possibly with a lag between tables. Debezium can emit transaction metadata (begin and end events with counts), which lets a consumer reassemble a transaction if needed, but most analytics do not need it. We use the common watermark described above for consistent snapshots, and tell users which tables are consistent as of which time.
Snapshot and stream consistency. The hardest correctness point is the first load. If we copy the table and start the stream afterwards, we may miss changes made during the copy; if we start the stream first and copy later, we may apply an old copy over a newer change. The watermark-based incremental snapshot solves it: a chunk is read between two markers in the log, and any key changed in that window is dropped from the chunk because the stream event is newer. Combined with the position guard in the merge, the final state is correct no matter how snapshot rows and stream events interleave. Snapshot rows get a position equal to the window's low watermark, so a later stream event always wins.
Schema evolution. A column is added: Debezium sees the DDL (MySQL schema history, Postgres relation messages), registers a new Avro schema version (backward compatible if the column is optional), and events carry the new field. The Spark job enables schema merge for the bronze and silver tables, so the new column appears with nulls for old rows. A rename is the dangerous case: from the log it looks like a drop plus an add, and data in the new column would be empty for old rows. We handle it by a manual process: the owning team announces renames, the pipeline pauses for that table, the column is renamed in Delta (column mapping mode), and the stream resumes. Type changes: widening (int to bigint) is automatic; narrowing or a change of meaning needs a new column. Dropped columns: keep the column in silver with nulls (a drop in the lake is rarely wanted). Schema registry compatibility checks fail the connector before bad events flow, which is a good failure, because it stops early and keeps the log.
Source protection. A replication slot in Postgres forces the server to keep all WAL files that the consumer has not confirmed. If the connector is down for a day, WAL can fill the disk of the primary and take the production database down. Controls: alerts on slot lag in bytes (warn at 5 GB, page at 20 GB), the setting max_slot_wal_keep_size so that the server drops the slot rather than fill its disk (we accept a re-snapshot as the lesser harm), heartbeat events so that the slot advances even when tracked tables are idle, and a dead-man check on the connector. MySQL binlog retention is set to 3 days or more, and the connector reads from a replica. For very large single transactions (a bulk update of 50 million rows) the event burst can reach 50 GB; we limit it with source-side discipline (batch big updates) and with Kafka message size limits.
Deletes and privacy. A hard delete in the source is an event of type d. Silver either marks or removes the row. For privacy erasure we also need to remove the personal data from bronze, where old events contain the row images. We keep bronze for 30 days only, and for erasure requests run a targeted rewrite of bronze files containing the key (found via a key index or partition pruning on the date), then VACUUM. Beyond 30 days, bronze no longer holds the data.
tradeoffs: Log-based CDC or query-based incremental loads. Choose log-based CDC when you need deletes, low latency, and low source load: it reads the log the database already writes and sees every change, including the ones between two polls. Choose query-based (a SELECT where updated_at > last) when the tables have a reliable update timestamp and index, deletes are rare or soft, and a latency of hours is fine: it needs no connector privileges on the log and is simple. Query-based loads miss hard deletes and intermediate states, and load the source with scans.
Copy-on-write or merge-on-read tables. Choose copy-on-write when reads dominate, updates are few or clustered in a small set of files (recent partitions), and you want simple plain Parquet files for all readers. Choose merge-on-read (deletion vectors, Hudi MOR, Iceberg position deletes) when updates are random across a large table, as in the example of 200x write amplification. You pay with more complex readers, a little more read cost until compaction, and an extra maintenance job. Many teams use both, per table.
Micro-batch streaming or hourly batch MERGE. Choose streaming micro-batches (2 minutes) when users need minutes-level freshness and you already run Spark streaming; the cost is a cluster that runs all the time. Choose hourly or daily batch merges from the bronze tables when freshness of hours is enough; a job runs 10 minutes per hour on a cluster that starts and stops, which is several times cheaper. The bronze log makes it possible to run both: stream bronze continuously, merge silver as often as needed.
Debezium with Kafka, or a managed service (Fivetran, AWS DMS, Databricks Lakeflow Connect). Choose Debezium and Kafka when you need control, many consumers of the same stream (search, caches, other services), and you have the operations skill. Choose a managed service when you have only the lakehouse as consumer, a small team, and a budget for per-row pricing; you give up flexibility and the replayable shared log. The cost of Kafka is mostly people, not machines.
One topic per table or one topic per database. A topic per table keeps schemas and retention simple and lets each table scale its partitions alone. A single topic per database preserves the order across tables (one partition per database), which helps a transactional view but limits the throughput to one partition (a few MB per second). Choose per table unless cross-table order is a hard requirement.
Soft or hard deletes in silver. Soft deletes keep the audit trail and make late events safe to reconcile, but analysts must filter on a flag; hard deletes match the source exactly but lose the information. Choose soft by default, hard for privacy-regulated tables.
failures: Connector crash: Kafka Connect restarts it on another worker; it resumes from the committed offset, producing a few duplicates that the merge guard removes. Kafka broker loss: replicas keep the data; producers retry with idempotence. Spark job failure: restart from the checkpoint; the batch is re-run and the merge guard ignores the already-applied changes. If the checkpoint is lost, we restart from a known offset (earliest in retention) and rely on idempotence, or from a bronze timestamp.
Source failover: in MySQL with GTIDs, the connector can continue on the new primary or replica if the GTID sets match. In Postgres, logical slots do not follow a failover automatically before version 17 (slot synchronization to standbys exists from Postgres 17); the safe plan is to create a new slot, run an incremental snapshot to repair the gap, and rely on the position guard. We rehearse this quarterly. Bad DDL: a change that breaks the compatibility check stops the connector; the log is intact, and the fix (a registry update or a pause plus a manual column change) is done before replaying.
Lag: Kafka consumer lag and end-to-end lag (heartbeat time vs now) are the main alerts; page at 15 minutes. Silent divergence is the dangerous failure: a bug that drops a class of events. We run a daily reconciliation: row counts and a checksum of a hash over primary keys and a few columns, compared between source replica and silver for each table and for random key ranges. Mismatches trigger a targeted re-snapshot of the range. Poison messages: an event that cannot be parsed goes to a dead-letter table with its offset, and the batch continues.
evolution: With 5 tables and 100 changes per second, a nightly full dump or an updated_at query is enough, and the lake gets a copy at 3 a.m. At 50 databases and a demand for fresh data, add Debezium, Kafka and a streaming merge into bronze and silver. At 500 tables with large random-update tables, add merge-on-read, clustering by key, a maintenance service for compaction and vacuum, automated reconciliation, and a self-service portal where a team onboards a table with one request. At the largest scale, the Kafka log feeds not only the lake but search indexes, caches and other services, and the lake tables are built by table formats with native incremental processing (change feeds).
followups: Why is log-based CDC better than polling with updated_at? || It captures deletes and every intermediate change, has a delay of seconds, and puts almost no query load on the source. Polling misses hard deletes and changes between polls, depends on correct timestamps and indexes, and scans tables.
How do you take the initial snapshot of a live table? || Use watermark-based chunked snapshots (as Debezium's incremental snapshot does): read the table in key ranges interleaved with the log stream, and drop from each chunk the keys that changed in the log during the chunk window. The stream keeps running and no locks are needed.
How do you make the lakehouse apply idempotent? || Reduce each micro-batch to the latest event per key and MERGE with a condition that the incoming source position is greater than the stored position. Replays then change nothing. For bronze, dedupe by topic, partition and offset or use idempotent write options.
Why can a MERGE into a big table be so expensive? || Random updates touch nearly every file, and copy-on-write rewrites each touched file, so 10 million updated rows cause hundreds of GB of IO. Deletion vectors write only new row versions and small bitmaps, and compaction runs rarely.
What happens when the source adds, renames or drops a column? || Adds flow through the registry and schema merge. Renames look like drop plus add, so they need a planned procedure (pause, rename with column mapping, resume). Type widening is automatic; other changes need a new column.
What can go wrong with a Postgres replication slot? || If the consumer stops, the primary keeps WAL and can run out of disk. Monitor slot lag, set a maximum retained WAL, send heartbeats, and accept a re-snapshot as the fallback.
How do you know the lake equals the source? || Daily reconciliation of counts and key-range checksums between a source replica and the silver table, plus the end-to-end lag from heartbeat rows. Mismatches trigger a re-snapshot of the affected key ranges.
How do you handle GDPR deletion of a user's rows? || Propagate the delete to silver, drop old bronze partitions by retention, and run a targeted rewrite of bronze files containing the key within the retention window, followed by VACUUM. Document the time limit for erasure.
