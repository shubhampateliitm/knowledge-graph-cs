@@ news-feed
title: Design a news feed like Twitter/X
category: Web & product
level: Senior / Staff
concepts: partitioning, cachelayer, redis, kafka, recsys, replication, consmodels, cassandra, conshash, ratelimit, cdn, scattergather, powerlaws, featurestore, idempotence, cap, failuredetect, backpressure, circuitbreaker, observability
summary: A news feed (the "home timeline") shows each user a list of posts written by the accounts they follow, newest or most relevant first. About 300 million people open it ten times a day, but only a small part of them write. The design is a classic read-heavy system, so the core question is where to do the work: when a post is written (push, or "fan-out on write") or when the feed is read (pull, or "fan-out on read"). The hard parts are celebrity accounts with 100 million followers, which break pure push, and ranking, which turns a simple merge of lists into a machine learning pipeline with a latency budget of a few hundred milliseconds.
requirements: Functional. A user can publish a post (text up to 280 characters, optional images or video). A user can follow and unfollow other accounts. A user can open the home timeline and get the latest 20 posts from followed accounts, then scroll to older ones (pagination). The timeline can be ranked (a "For You" tab) or purely by time (a "Following" tab). Users can like and repost, and see counts. We leave out direct messages, search, ads and trending topics, and we only name the notification path.
Non-functional. Timeline reads must be fast: p99 under 300 ms for the API, which leaves room for ranking. Posting must feel instant: the author sees the post in their own timeline at once ("read your writes"), but followers may see it a few seconds later. We choose availability over strict consistency (eventual consistency): a feed that is 5 seconds stale is fine, a feed that fails to load is not. Posts must never be lost once the API says "OK". A follower should never see the same post twice, and deleted posts must disappear within a minute.
Assumptions we choose: 300 million daily active users (DAU), 600 million registered users, average 200 followers per account (the mean is far above the median, because the distribution follows a power law), 150 million new posts per day, 10 timeline opens per DAU per day, and 20 posts per page.
estimates: Timeline reads. 300M DAU x 10 opens = 3 billion opens per day. 3,000,000,000 / 86,400 s = about 34,700 per second on average. Peak is about 3x the average, so about 100,000 reads per second.
Writes. 300M x 25% posters x 2 posts = 150M posts per day. 150,000,000 / 86,400 = about 1,740 posts per second on average, about 5,200 per second at peak. The read to write ratio is about 20 to 1 for opens, and much higher for individual post views.
Fan-out. With push, each post is copied into the timeline of every follower. 150M posts x 200 followers = 30 billion timeline inserts per day, which is 347,000 per second on average and about 1 million per second at peak. This is the number that decides the design: writes are small, but there are many of them.
Timeline cache memory. Keep the newest 800 entries per active user. The raw payload per entry is a post id (8 bytes) plus a score or author id (8 bytes) = 16 bytes. 800 x 16 B = 12.8 KB per user. Redis adds overhead for its structures, so we budget 2x: 25.6 KB per user. For 300M users that is 300,000,000 x 25.6 KB = 7.7 TB. With 3 copies (one primary, two replicas) it is 23 TB. A cache node with 256 GB of RAM can use about 150 GB, so 23 TB / 150 GB = about 154, we round to 160 nodes. Users inactive for 30 days are dropped from the cache and rebuilt on demand, so the real number is lower.
Post storage. A post row is about 500 bytes (text up to 560 bytes in UTF-8, ids, timestamps, counters). 150M x 500 B = 75 GB per day, about 27 TB per year, 82 TB with 3 replicas. This is small. Media is the large part: 20% of posts carry media, average 1 MB after compression, so 30M x 1 MB = 30 TB per day, about 11 PB per year, kept in object storage and served from a CDN.
Read bandwidth. One timeline page is 20 posts x 500 B = 10 KB of JSON, plus the author profile data. 100,000 per second x 10 KB = 1 GB/s = 8 Gbit/s at the API layer, which is small. Media bytes dominate and are served by the CDN, not by our servers.
api: POST /v1/posts with body {text, media_ids[], reply_to?} and header Idempotency-Key. Returns {post_id, created_at}. The idempotency key lets a client retry after a timeout without creating two posts.
POST /v1/follows with {followee_id}, and DELETE /v1/follows/{followee_id}. Both return 204. They update the follow graph and trigger a small backfill of the feed.
GET /v1/timeline/home?mode=for_you|following&cursor=<opaque>&limit=20. Returns {posts[], next_cursor}. The cursor encodes the last post id and a ranking session id, so that page 2 continues page 1 and is not recomputed against a new world.
GET /v1/users/{id}/posts?cursor=&limit=20. The user's own profile timeline. This is a plain range read on one partition, no fan-out.
POST /v1/posts/{id}/likes and DELETE /v1/posts/{id}/likes. Counters are updated asynchronously.
datamodel: Posts table, key-value or wide-column (Cassandra or similar): partition key post_id (a 64-bit time-sortable id, in the style of Snowflake ids: 41 bits of milliseconds, 10 bits of machine id, 12 bits of sequence). Columns: author_id, text, media_refs, created_at, reply_to, deleted flag. Lookup by id is the main access path, so hash partitioning spreads load evenly.
User posts table (for profile pages): partition key author_id, clustering key post_id descending. One range scan gives the latest N posts of one author. This table is also the source for pull at read time.
Follow graph: two tables, followers(user_id, follower_id) and following(user_id, followee_id). Both are partitioned by the first column. The first answers "who gets my post?" (used by fan-out), the second answers "whose posts do I merge?" (used by pull). We store both because each question is asked at very high rate, and a join across partitions is too slow.
Home timeline cache: Redis, one sorted structure per user, key tl:{user_id}, members are post ids, score is the post id (time-sortable), capped at 800 entries by trimming the oldest. It is a cache, not the source of truth: if it is lost it can be rebuilt from following + user posts.
Counters (likes, reposts, views): separate store, sharded counters per post, written through a log and aggregated, so a popular post does not become a hot row.
design: Writing a post. The client calls POST /v1/posts through the API gateway, which authenticates the user and applies rate limiting (for example 300 posts per 3 hours per user). The post service validates the text, takes an id from the id generator, writes the post row to the posts store with replication factor 3 and quorum write, and returns OK. Then it publishes a "post created" event to a Kafka topic partitioned by author_id. The user sees success after the durable write and does not wait for fan-out.
Fan-out workers. A pool of consumers reads the topic. For each event the worker asks the follow graph for the author's followers and, for each follower who has a timeline in the cache, inserts the post id into that follower's Redis structure. Work is batched: followers are split into chunks of 1,000 and each chunk is one task, so one slow chunk does not block the others. Because followers are spread across many cache shards using consistent hashing on user_id, the writes run in parallel on many nodes. A normal author with 200 followers finishes in a few milliseconds of work and appears within about a second.
Hybrid model for celebrities. Pure push fails for accounts with millions of followers: one post from an account with 100 million followers would mean 100 million cache writes. At 1 million inserts per second for the whole cluster, that single post would take 100 seconds and would starve everyone else's fan-out. So we set a threshold, for example 50,000 followers. Authors above it are not fanned out. Their posts are only stored in their own user posts table (and cached hot in memory). Everyone else uses push.
Reading the home timeline. The timeline service takes the user's Redis list of precomputed post ids (the push part). It also looks up which celebrities this user follows (a short list, usually under 100, kept in the following table with a "celebrity" flag) and pulls their latest posts from the user posts tables or a hot cache. It merges these ids by time, drops anything blocked or muted, then hydrates: it fetches post bodies, author profiles and counters in bulk with multi-get calls to the caching layer in front of the posts store. A typical read touches 1 Redis node, 5 to 10 celebrity partitions and about 3 bulk lookups, all in parallel (scatter-gather), so latency is the slowest call, not the sum.
Ranking for the "For You" tab. Time order is simple, but a ranked feed gives better engagement. The service takes a candidate set of about 1,500 posts (the push list, celebrity posts, and out-of-network posts found by a recommender system from social graph and embeddings), scores them with a light model, then a heavier neural model on the top few hundred, and applies rules (diversity: not 10 posts from one author; safety filters). X published its pipeline in 2023 in the open-source "the-algorithm" repository: candidate sourcing, light ranker, heavy ranker, then mixing. The budget is about 150 ms for all of it, so features are read from a feature store and not computed live.
Likes, replies and counters. A like is written to a log (Kafka) and a counter aggregator updates the per-post count every second or so. The client shows its own like immediately (optimistic UI). Counts are eventually consistent; nobody notices if a count is off by a few for a second.

deepdive: Push, pull or hybrid: the math. Push costs (posts per second) x (followers per post) writes and almost nothing at read time. Pull costs nothing at write time but at read time must fetch the latest posts of every followee: a user following 500 accounts needs 500 partition reads per open, and at 100,000 opens per second that is 50 million reads per second. Push turns this into 1 read. Push wins because reads are 20 times more frequent than writes and most users follow few accounts. The hybrid model keeps the benefit for the 99.9% of accounts and uses pull only for the few accounts where push is too expensive. The threshold is a tuning knob: lower it and write load drops but reads get more expensive.
Hot keys and the power law. Follower counts and post popularity follow a power law (Zipf-like). A few accounts produce most of the extreme load. For a hot post that is read by 10 million people in a minute, the posts store and cache see one key requested 160,000 times per second. One cache node cannot serve that. We replicate hot keys: the caching layer detects keys above a threshold request rate and keeps copies on several nodes (or inside each timeline service process for a few seconds, a local cache with a short time to live). Counters are the same: use sharded counters (for example 16 sub-counters per post, summed on read).
Fan-out ordering and idempotence. Kafka delivers at least once, so a worker may process the same event twice after a crash. The Redis insert of a post id into a sorted structure is idempotent (same member, same score gives the same state), which makes duplicates harmless. This is the reason we use a sorted set with the post id as the member and not a list with append. Ordering inside one timeline is by the time-sortable post id, so late arrivals still fall in the right place and nobody needs a global order.
Read your writes. After posting, the author must see the post. Fan-out may need a second, and the author's own timeline might not yet contain it. The timeline service therefore merges the user's own recent posts (from the user posts table, or a short-lived session cache) into the result. This is a small special case that makes the system feel consistent without paying for strong consistency.
Deletes, blocks and unfollows. Removing a post from 200 or 2 million timelines is expensive. We do not do it. We mark the post deleted in the posts store and the hydration step drops deleted posts when the page is built. The same trick applies to blocks and mutes: they are filters at read time, using a small per-user set. For an unfollow, the old ids stay in the timeline until they scroll out of the 800-entry window, and the read-time filter hides them. A background job cleans up in bulk.
Cold start and cache rebuild. A user who has not opened the app for 30 days has no timeline in Redis. On the first open the service builds it by pulling the latest 50 posts of each followee (bounded by a cap, for example 200 followees) and writes the result into Redis. This rebuild is the same code as the pull path, which is a good reason to keep that path alive and tested. It also is the recovery plan if a Redis shard is lost.
Pagination. Offsets break when new posts arrive (page 2 would repeat items). We use cursors: the cursor holds the last post id seen, and the next page asks for ids smaller than it. For ranked feeds the cursor also carries a ranking snapshot id, so that page 2 comes from the same ranked list, which we keep in cache for a few minutes.
tradeoffs: Push (fan-out on write) versus pull (fan-out on read). Choose push when reads greatly outnumber writes, followers per author are moderate, and read latency matters most; this is the case for almost every consumer feed. Choose pull when authors have huge audiences, when users follow thousands of accounts but rarely read (so most precomputed work is wasted), or when you have few users and simplicity is worth more. A hybrid costs more code (two paths, a threshold, a merge) but is what Twitter described in its timeline architecture. You give up simplicity and some freshness for celebrity posts.
Cache the timeline in Redis versus store it in a durable database. Choose an in-memory cache (Redis or Memcached) when timelines can be rebuilt from source data and you need sub-millisecond reads; you pay for RAM (about 8 TB for one copy here) and accept rebuild work after a failure. Choose a durable wide-column store such as Cassandra for the timeline itself when RAM cost dominates (disk is about 20 times cheaper per byte) and you can live with 5 to 10 ms reads. At 300M users, the RAM bill (160 nodes) is large but affordable; at a smaller product, a database-only design is simpler.
Chronological versus ranked. Choose a time-ordered feed when users want predictability, when you lack training data or ML engineers, or for regulatory or trust reasons (some platforms must offer a non-algorithmic option). Choose ranking when engagement and time spent are the business goal; ranking costs about 150 ms of latency and a large feature and model platform. The cost of ranking is paid on every read, so it must be cached and bounded.
SQL versus NoSQL for the graph and posts. A relational database such as sharded MySQL handles the follow graph well up to a few billion edges, and gives transactions for follow and unfollow. Choose a key-value or wide-column store when you need linear scaling by adding nodes and your queries are by key. Facebook built TAO, a cache and graph API on top of sharded MySQL, because it wanted both. Choose a graph database only for multi-hop queries such as "friends of friends"; the home timeline needs only one hop.
Strong versus eventual consistency. Choose strong consistency only for the follow action and for deletes that have legal meaning (for example user blocking). For the timeline, eventual consistency with read-your-writes for the author is almost free and avoids cross-region coordination (the CAP trade-off: during a partition we keep serving).
failures: A Redis shard dies. Users on that shard lose their timeline cache. Replicas take over within seconds (failure detection by heartbeats, then promotion). If a replica is also lost, the timeline service falls back to the pull path for those users and rewrites the cache in the background. Latency rises from 30 ms to maybe 200 ms for them, but the feed works.
Fan-out workers fall behind. If the consumer lag in Kafka grows (a bad deploy, or a post with a very large follower count), the feeds of followers become stale. The lag is the main alert (observability: consumer lag in seconds). We scale the worker pool, and large fan-out jobs run on a separate low-priority topic so a celebrity-adjacent account cannot delay ordinary users. Backpressure is natural: Kafka stores events until the workers catch up.
Ranking service is slow or down. The timeline service sets a timeout (for example 150 ms) with a circuit breaker. On failure it returns the merged chronological list. The user sees a worse feed, not an error. This degradation must be tested regularly.
Posts store partition is slow. Reads use quorum with hedged requests (send to a second replica after the 95th percentile latency). Hydration returns partial pages if a few bodies are missing: the timeline shows 18 posts instead of failing, and the missing ids are retried on the next request.
Zone or region failure. Data is replicated across three zones in a region; reads and writes continue with quorum. For region loss we run an active-active setup with asynchronous cross-region replication: users are routed to their home region, and recent posts that did not replicate may appear late after failover. We accept losing a few seconds of fan-out but not the posts themselves, because the posts store is written with cross-zone quorum before the OK.
Traffic spike (an event, an election, a game final). Reads can double within minutes. The CDN and the hot-key caches absorb most. We shed load in order: first the ranker (fall back to chronological), then non-critical decorations (counters shown stale, "who to follow"), then new low-priority fan-out. Rate limits protect the post path from bots.
evolution: At 1,000 users, one Postgres database and a single query joining follows and posts is enough: SELECT from posts WHERE author_id IN (followees) ORDER BY created_at DESC LIMIT 20, with an index on (author_id, created_at). This is pull and it is correct. At 1 million users, the join starts to cost; add a read replica, cache timelines in Redis for active users, and push on write with a simple background job. At 1 billion registered users, you need sharded storage, Kafka for the event path, a hybrid fan-out, a feature store, multi-region deployment, and a team that owns the ranking models. Each step is forced by a measured bottleneck, not by fashion: keep the simple design as long as it meets the latency target.
followups: A user follows 5,000 accounts. What breaks, and how do you fix it? || Pull gets expensive (5,000 partition reads), but the pushed list still works for normal authors. Cap the pull to the most active followees, keep the precomputed list as the main source, and let ranking drop low-value items. Also say that following 5,000 accounts makes a time-ordered feed noisy, so ranking is part of the answer.
A celebrity with 100 million followers posts. Walk me through it. || It is not fanned out. The post goes into the author's own partition and a hot cache. Each follower's read merges it in at request time, so the cost is paid by readers, spread over minutes, and served from cache. The key is one hot key read by many, so we replicate it across cache nodes and add a short local cache in the timeline service.
How do you avoid showing the same post twice or in the wrong order? || Use time-sortable 64-bit ids, a sorted set keyed by post id (idempotent inserts), and cursors that carry the last id seen. At-least-once delivery from Kafka then causes no duplicates. For ranked feeds, keep a ranking snapshot id in the cursor so page 2 continues page 1.
How do you handle a deleted post or a blocked user? || Do not touch millions of timelines. Mark the post deleted in the posts store and filter at hydration time. Blocks and mutes are small per-user sets checked at read time. A background job removes stale ids later.
Why not just use a relational join at scale? || The join needs data from many shards (all followees' partitions) and cannot be indexed across shards. It costs one read per followee for each open. The push model changes the read to a single key lookup by paying once per write, and that is a good trade when reads are 20 times writes.
What happens when the Redis cluster loses a whole shard and its replicas? || The timeline service falls back to the pull path for the affected users, builds the list from followees' recent posts, and writes it back. Latency is higher but correct. We keep this path exercised with regular fault injection, otherwise it will be broken on the day we need it.
How do you measure that the feed is healthy? || Track p99 read latency per stage, fan-out lag in seconds (time from post created to last follower insert), cache hit rate for timelines and for hydration, ranker timeout rate, and a freshness probe: a synthetic account posts every minute and a synthetic follower measures when it appears.
How would you rank without destroying latency? || Two stages: a cheap light ranker on 1,500 candidates and a heavy model on the best few hundred, with features precomputed in a feature store. Put a hard timeout and a fallback to chronological order. Cache the ranked page for the cursor session.

@@ chat
title: Design a chat system like WhatsApp
category: Web & product
level: Senior / Staff
concepts: sockets, tcp, mqueue, partitioning, conshash, idempotence, deliverysem, consmodels, lamport, pkcrypto, aead, cassandra, redis, failuredetect, loadbalancing, backpressure, retries, rocksdb, quic, cdn, ratelimit
summary: A chat system moves short messages between people in real time, tells the sender when each message was delivered and read, works for groups, and survives phones that go offline for hours. About 500 million people use it every day. The hard parts are holding hundreds of millions of long-lived connections, routing a message to the right connection on the right server in milliseconds, keeping order and avoiding duplicates over unreliable mobile networks, and doing all this with end-to-end encryption, so the servers can move messages but cannot read them.
requirements: Functional. One-to-one chat and group chat (up to 1,024 members). Text messages and media (photos, voice notes, video, documents). Delivery receipts: sent (one tick), delivered (two ticks), read (blue ticks). Online status ("last seen") and typing indicators. Messages sent to an offline user are delivered when the user returns. A user can have several devices (one phone and up to four linked devices). Push notifications wake a sleeping phone. We leave out voice and video calls, status stories and payments.
Non-functional. Latency: when both users are online, a message arrives in under 200 ms at the 99th percentile in the same region. Reliability: no message is lost once the sender sees one tick, and none is shown twice. Ordering: messages of one conversation appear in the same order for all members. Privacy: end-to-end encryption by default, so the server stores only ciphertext and only for as long as it needs for delivery. Availability matters more than strict consistency, but we need clear rules for ordering and for what happens during a failure.
Assumptions we choose: 500 million daily active users (DAU), 40 messages sent per user per day, 10% of messages carry media averaging 200 KB, 40% of users connected at the busiest hour, groups are mostly small (average 10 members).
estimates: Messages. 500M x 40 = 20 billion messages per day. 20,000,000,000 / 86,400 = about 231,000 per second on average, about 700,000 per second at peak (3x). Each group message becomes several deliveries, so with 25% of messages going to groups of average 10 members, deliveries are about 20B x (0.75 x 1 + 0.25 x 10) = 20B x 3.25 = 65 billion per day, about 750,000 per second on average and 2.2 million per second at peak.
Connections. 40% of 500M = 200 million concurrent connections at peak. WhatsApp reported more than 2 million connections on one Erlang server in 2012, but we plan 500,000 per gateway to leave room for TLS, encryption work and spikes. 200,000,000 / 500,000 = 400 gateways. With 2x headroom for failures and deploys: 800 gateways. Memory: about 20 KB per connection (socket buffers, TLS state, session) x 500,000 = 10 GB per gateway, fine for a 64 GB machine.
Offline storage. The server keeps a message only until the receiver acknowledges it (store and forward). Suppose 5% of deliveries find the receiver offline: 65B x 5% = 3.25B queued messages per day. At 1 KB each (small ciphertext plus headers) that is 3.25 TB per day. Most are collected within hours, so assume average stay of 1 day: about 3 TB live data, 10 TB with 3 replicas. A message not collected within 30 days is dropped. This is small for modern storage; the connections are the expensive part, not the bytes.
Media. 20B x 10% = 2 billion media messages per day x 200 KB = 400 TB per day, which is 400,000,000 MB / 86,400 = about 4.6 GB/s of upload on average. Media is encrypted by the sender with a random key and uploaded as a blob to object storage; the message carries only the link and the key. If we keep a blob for 3 days on average: 400 TB x 3 = 1.2 PB.
What if the server kept full history (like Messenger or Telegram)? 20B messages x 1 KB = 20 TB per day, 7.3 PB per year, 22 PB with 3 replicas. That is a large, permanent cost, and it is the reason the "no history on the server" choice is also a cost choice.
api: Clients talk to the gateway over one persistent TCP connection with TLS, using a compact binary protocol (WhatsApp uses its own binary protocol derived from XMPP; we show logical calls). Frames are small, so one frame fits in one TCP segment.
SEND {msg_id, to, ciphertexts[per device], type}. msg_id is generated by the client (UUID) so a retry is recognised. Reply: ACK {msg_id, server_ts}, which gives the sender one tick.
DELIVER {msg_id, from, ciphertext, server_seq, server_ts}. Server to client. The client replies with RECEIVED {server_seq}, after which the server deletes the message and sends a delivery receipt to the sender.
RECEIPT {msg_id, kind=delivered|read}. Client to server and then to the sender. Receipts are small messages and travel the same path as normal messages.
PRESENCE {state}, TYPING {chat_id}. Fire-and-forget. They are never stored and may be dropped.
POST /v1/media (HTTPS) returns {upload_url, blob_id}. The client uploads the encrypted file directly to storage, then sends blob_id and key inside the encrypted message.
GET /v1/keys/{user_id}. Returns the user's identity key and a one-time prekey for each device, so a sender can start an encrypted session when the receiver is offline.
datamodel: Inbox, one per device: stored in a wide-column or LSM-based store (Cassandra, or RocksDB behind our own service). Partition key (user_id, device_id), clustering key server_seq (ascending), value the ciphertext envelope. Delivery reads the lowest unacknowledged sequence numbers; an acknowledgement deletes a range. All data of one device sits in one partition, so catch-up after being offline is one sequential range scan.
Connection registry: key user_id:device_id, value gateway_id plus connection epoch, with a time to live of 60 seconds refreshed by heartbeats. Kept in a sharded in-memory store (Redis style) or in a consistent-hashing service. It is soft state: if lost, devices reconnect and re-register in seconds.
Groups: group_id -> members and roles, version number. Stored in a replicated key-value or SQL store because it changes rarely and is read often; cached in the message service.
Key directory: user_id, device_id -> identity public key, signed prekey, batch of one-time prekeys. When the one-time prekeys run low, the server asks the device to upload more.
Receipts and message states are not a separate table: they are messages in the inbox of the original sender. The client keeps the full chat history in a local database (SQLite), backed up by the user to their own cloud account.
design: Connecting. The client opens a TCP connection to a regional endpoint chosen by DNS and the load balancer. After the TLS handshake and authentication, the gateway registers the device in the connection registry and starts a heartbeat. The gateway is a thin, almost stateless process: it terminates connections, decodes frames and forwards them. Event-driven I/O (epoll) lets one process hold hundreds of thousands of sockets, because an idle socket costs only memory.
Sending to an online user. Alice's phone sends SEND over her connection. Her gateway checks the rate limit, then calls the message service, which does three things. It writes the ciphertext into Bob's inbox with the next server_seq for Bob's device, with a durable write (replication to 2 of 3 nodes). It returns ACK to Alice, who shows one tick. Then it looks up Bob's device in the connection registry. If it finds gateway G7, it sends DELIVER there; G7 writes it to Bob's socket. Bob's phone replies RECEIVED; the message service deletes it from the inbox and sends a "delivered" receipt to Alice's inbox, which shows two ticks. When Bob opens the chat, a "read" receipt follows the same path. The whole online path is one durable write, one registry lookup and one hop to the gateway: a few milliseconds inside the data centre.
Sending to an offline user. The registry has no entry for Bob. The message is already in Bob's inbox, so nothing is lost. The message service sends a push notification through APNs (Apple) or FCM (Google). Because messages are end-to-end encrypted, the push carries no text, only a wake-up signal. The phone wakes, opens a connection, and the gateway sends everything with server_seq above the last acknowledged one. If the phone stays off for 30 days, the inbox is deleted.
Groups. The sender encrypts the message once using a per-group "sender key" (so one ciphertext, not 10) and sends it to the message service. The service looks up the member list and writes one inbox entry per member device: fan-out on write, as in a news feed. For groups of at most 1,024 members this is cheap (up to 1,024 small writes); for very large broadcast channels we would switch to a pull model where members read from a shared log.
Media. The client encrypts the file with a random AES key, uploads the blob to object storage through a CDN edge, and sends the blob link and key as a normal encrypted message. The chat path stays small and fast. The receiver downloads the blob when it wants it. The server cannot read the file. Blobs expire after all recipients have fetched them or after a retention period.
Presence and typing. A user's online state is simply "is there a live registry entry". A subscriber does not poll: when a chat window opens, the client subscribes to that contact's presence, and the gateway pushes changes. Typing events are sent only to the other party in the open chat and are never stored. Fan-out of presence to all contacts would be too costly (500 contacts x every connection change), which is why we limit it to open chats.
Encryption. Each device has an identity key pair and uploads prekeys. To start a session, Alice fetches Bob's key bundle and runs the X3DH key agreement (public key cryptography), then both sides use the Double Ratchet to derive a new key for every message, with authenticated encryption (AEAD) of the payload. The server stores public keys and ciphertext only. Multi-device means Alice encrypts the message separately for each of Bob's devices and each of her own other devices.

deepdive: Ordering. Clocks on phones are wrong by seconds or minutes, so we cannot sort by client time. Two kinds of order matter. First, the order in which one receiver sees messages: the message service assigns server_seq numbers per inbox, so the receiver gets one total order, and it is the same on retry because the sequence is stored with the message. Second, the order that all members of a group see. Each member's inbox has its own sequence, so two members could see two messages in different order if the writes race. The fix is to give every group message one group-level sequence number from a single sequencer for that group (the group is partitioned to one message-service shard), and members sort by it. This is a logical clock per conversation, like a Lamport clock with a single writer. Replies that depend on a message are ordered after it automatically, because the sender had already seen the earlier number.
Exactly-once appearance. The network gives at-least-once delivery: if the ACK is lost, Alice's phone retries SEND; if the RECEIVED is lost, the server sends DELIVER again. We make this safe with idempotence on both sides. The message service keeps a short-lived table (msg_id, sender) for 7 days; a second SEND with the same msg_id returns the old ACK and writes nothing. The receiving client keeps the last seen server_seq and ignores anything lower or equal. At-least-once plus these two dedup rules gives effectively-once appearance without distributed transactions.
Gateway failure and the registry. A gateway with 500,000 connections can die. All clients detect a closed or silent socket (heartbeat every 30 seconds, timeout at 60) and reconnect with exponential backoff and jitter, so 500,000 phones do not return in the same second. The registry entries for the dead gateway expire by TTL in 60 seconds, but messages that arrive in the gap are not lost: the message service tries DELIVER, gets a failure, and leaves the message in the inbox. The inbox is the source of truth, the registry is an optimisation. When the device returns, it syncs from its last acknowledged sequence.
Stale registry and duplicate connections. A phone switches from Wi-Fi to mobile data and opens a second connection while the old one is still half open. Each registration carries an epoch number; the registry keeps the highest epoch, and the old gateway closes the older socket when it learns about the newer one. This is a small fencing token idea: the newest connection wins.
Reconnect storms and backpressure. After a regional network failure, 100 million phones reconnect together. Gateways admit new connections at a limited rate and tell the others to retry later with a random delay in the response. The inbox read path on reconnect streams messages in batches of 100 and waits for acknowledgements (a sliding window), so a phone with 50,000 queued messages does not flood its own link or our servers. Rate limits also stop one abusive sender, for example 100 messages per second per user.
Hot groups and celebrities. A group with 1,024 members and a very active chat produces 1,024 inbox writes per message. At 50 messages per second in that group, this is 51,200 writes per second against 1,024 partitions, which is fine, but the sequencer of that group is a single point of order. We pin it to one shard with a standby; one shard handles about 50,000 sequence assignments per second, so a group is never the limit.
Key distribution and trust. The server could cheat by giving Alice a fake key for Bob (a man-in-the-middle attack). Clients therefore show a "safety number" that two people can compare out of band, and warn when a contact's key changes. The one-time prekeys are consumed once, so the directory must make sure that the same prekey is not given to two senders (an atomic pop in the directory shard).
tradeoffs: Store-and-forward (delete after delivery) versus server-side history. Choose store-and-forward when privacy is a feature, when your cost model matters (we computed 3 TB live data instead of 7.3 PB per year), and when clients are capable phones with local storage. Choose server-side history when users expect to use the web or a new device and see all old chats at once (Telegram, Slack), when search across history is a feature, or when moderation requires access. You give up either easy multi-device and search (first) or privacy and storage cost (second).
WebSocket or a custom binary protocol on TCP, versus HTTP polling or server-sent events. Choose a persistent TCP/WebSocket connection when the latency target is under a second and messages are frequent; the per-message overhead is a few bytes. Choose long polling only when you must pass restrictive proxies, because each poll costs a new request, headers of a few hundred bytes, and server threads. Choose HTTP/2 or QUIC streams when you want connection migration across networks (QUIC survives a Wi-Fi to mobile switch without a new handshake). The price of persistent connections is that you carry state: 200 million sockets, a registry, and careful deploys (draining a gateway slowly).
Erlang/JVM thread-per-connection versus event-driven I/O. WhatsApp reached millions of connections per machine using Erlang lightweight processes on FreeBSD. Choose the Erlang or Go model when you want each connection to be simple sequential code with cheap isolation; choose epoll/io_uring event loops (Netty, Rust with Tokio) when you need the lowest memory per connection. Whatever you pick, plan for 20 KB per connection, not for thread stacks of 1 MB (which would need 500 GB for 500,000 connections).
Fan-out on write versus on read for groups. Choose write fan-out (one inbox entry per member) up to about a thousand members: delivery is a simple range read for each device. Choose read fan-out (one shared log per group or channel, readers keep a cursor) for channels with hundreds of thousands of members; writes become 1 instead of N, but each reader needs to find which logs to read, and read receipts are no longer exact.
Cassandra-style wide column store versus a custom RocksDB service. Choose Cassandra (or ScyllaDB) when you want operations tools, replication and repair built in; Discord used this path and later moved from Cassandra to ScyllaDB. Choose a custom service on RocksDB when the data is a queue with short life, because deletes in an LSM tree create tombstones and compaction work. Whichever you choose, avoid tombstone-heavy partitions: delete ranges, and partition by day if needed.
failures: Gateway crash: clients reconnect in seconds and sync from the inbox; no message loss. Message service node crash: it is stateless; the gateway retries on another node. A retried SEND is deduplicated by msg_id.
Inbox store node or zone loss: writes use quorum (2 of 3 across zones), so one zone can fail without losing acknowledged messages. After the zone returns, anti-entropy repairs the replicas. If two zones fail, writes stop for the affected partitions; we return errors, and clients show a clock icon and retry. We choose consistency here: we never send an ACK for a message not stored on a quorum.
Registry loss: all entries vanish. The message service sees "offline" for everyone and sends push notifications; phones wake and some are already connected. To avoid a wave of useless pushes, gateways re-register their live connections within seconds (they hold the truth), and the push service waits 2 seconds before sending a push for fresh messages, which also removes most pushes for users who are online.
Push provider outage (APNs or FCM): the notification path is best-effort; phones still get messages whenever the app opens or the connection is up. We keep a retry queue with a limit and do not make delivery depend on pushes.
Bad deploy of the gateway: roll out by 1% of machines, watch connection drop rate and message latency, and drain connections gradually (close 1% per minute with a reconnect hint) so a rollback does not cause a storm.
Region failure: users are routed to another region by DNS and the load balancer. Their undelivered inbox must be available there: we replicate inboxes asynchronously across regions, so a message that was acknowledged just before the failure may be late until the region returns. We accept this narrow gap and tell users that messages may be delayed, since messages are never deleted until acknowledged.
evolution: At 1,000 users one machine with a WebSocket server and Postgres is enough; the inbox is a table, the registry is an in-memory map. At 1 million users, split into gateways and a message service, add Redis for the registry and push notifications; one database cluster still holds inboxes. At 1 billion users, you need inboxes partitioned by user across many clusters, regional gateways, per-region key directories, abuse and spam systems (rate limits, reputation), multi-device support with per-device encryption, and careful deploy tooling for stateful connections. The connection count, not the message bytes, sets the number of machines.
followups: How do you guarantee a message is not lost if the receiver's phone is switched off? || The message is written to the receiver's inbox on a quorum of replicas before the sender gets the first tick. It stays there until the phone sends RECEIVED. Push notifications are only a hint to wake the phone. On return the phone syncs from its last acknowledged sequence number.
How do you route a message to the right gateway among 800? || A connection registry maps user and device to gateway with a TTL refreshed by heartbeats. The message service looks it up per message. If the entry is stale or missing, the delivery fails or finds nothing and the message simply stays in the inbox, so the registry is a hint and never the source of truth.
How do you order messages in a group chat when members have different clocks? || Use a sequence number assigned by one sequencer per group (the group is owned by one shard), not client timestamps. Members sort by it. It is a logical clock with a single writer. If the sequencer fails over, a new owner continues from the highest stored number plus a gap.
How does end-to-end encryption change the design? || The server cannot index, scan or transform message content, so there is no server-side search, no link previews done by the server, and push notifications cannot include text. Groups use sender keys to avoid N encryptions. Multi-device needs per-device ciphertext. Key changes must be visible to users to defend against a malicious server.
What happens after a region-wide reconnect storm? || Gateways cap the accept rate, return a retry-after with jitter, and the clients use exponential backoff. The inbox sync is windowed. Admission control protects the auth service, the registry and the inbox store, which would otherwise fail together.
Why not use Kafka as the inbox? || Kafka is excellent for a few thousand topics but we need hundreds of millions of tiny per-device queues with random deletes and acknowledgements per message. A topic per device does not scale; a shared topic would need consumers to filter. A keyed store with range scans fits better. Kafka can still carry the audit, receipts analytics and abuse signals.
How would you add message search and cloud backup without breaking privacy? || Search runs on the client over the local database. Backup is an encrypted blob uploaded to the user's own cloud account, with a key derived from a user secret or hardware-held key, so the server cannot read it. The trade-off is that losing the secret loses the backup.

title: Design a notification system
category: Web & product
level: Senior / Staff
concepts: kafka, mqueue, pubsub, idempotence, deliverysem, exactlyonce, retries, backpressure, ratelimit, circuitbreaker, outbox, partitioning, redis, batching, cassandra, http, multitenancy, observability, workflow, bloom
summary: A notification system tells users that something happened: a payment succeeded, a friend replied, a delivery is near, or a sale started. It sends the message through push (APNs for Apple, FCM for Android), email, SMS and in-app inbox. Many product teams call it, so it is a shared platform. It looks easy, but it must respect user choices, avoid duplicates, never let a marketing blast delay a one-time password, and survive slow and failing third-party providers that we do not control.
requirements: Functional. Other services send an event or a request ("order 123 shipped") and the platform decides who gets what, on which channel, in the user's language. Channels: mobile push, email, SMS, web push and an in-app inbox with unread count. Users set preferences per category and channel, and quiet hours. Teams can send bulk campaigns to a segment of millions of users. Messages can be scheduled for a time or a time zone. We track status: queued, sent, delivered, opened, failed.
Non-functional. Priority and latency: security codes and payment alerts must reach the provider within 2 seconds at p99 even during a campaign; social alerts within 10 seconds; marketing within hours. Reliability: a critical notification must not be lost (at-least-once). Duplicates must be rare, because users hate two identical messages, and SMS duplicates cost money. Isolation: one team's bug must not starve another. Compliance: unsubscribe is honoured within minutes, and consent is stored.
Assumptions we choose: 200 million registered users, 100 million daily active, an average of 10 notifications per user per day, channel mix 70% push, 20% email, 5% SMS, 5% in-app only, and a daily marketing campaign to 50 million users.
estimates: Volume. 200M users x 10 = 2 billion notifications per day. 2,000,000,000 / 86,400 = about 23,000 per second on average. Event-driven traffic peaks at about 3x: 70,000 per second.
Campaign burst. A marketing push to 50 million users that must finish in 20 minutes needs 50,000,000 / 1,200 s = 41,700 sends per second. This alone is above the average, so it must run in its own lane or it will delay everything else.
Channel numbers. Push: 2B x 70% = 1.4B per day. Email: 400M per day, which at about 50 KB per HTML email is 20 TB per day of outbound traffic. SMS: 100M per day; SMS costs roughly 0.5 to 1 US cent each, so 100M x $0.007 = $700,000 per day if we send them all. This is why SMS is limited to critical messages, and the preference and rate-limit rules are a money question as well as a user experience question. Email through a cloud sender costs about $0.10 per 1,000: 400M / 1000 x $0.10 = $40,000 per day. Push is free.
Provider limits. A push payload is limited to 4 KB (4,096 bytes) on both APNs and FCM. APNs uses HTTP/2, and one connection carries many concurrent streams (the server announces the limit, often about 1,000). If one connection sends 2,000 requests per second, 70,000 per second needs at least 35 connections; we use 200 for headroom and for failure.
Storage. A status record is about 200 bytes. 2B x 200 B = 400 GB per day. Keep 30 days hot: 12 TB, with 3 replicas 36 TB. Inbox items for in-app: 5% x 2B = 100M per day x 500 B = 50 GB per day, kept 90 days = 4.5 TB. Device tokens: 100M users x 2 devices x 200 B = 40 GB, easily cached.
api: POST /v1/notifications (internal, from product services). Body {idempotency_key, user_id or segment_id, category (for example order_update), template_id, params, priority (critical|high|normal|bulk), channels_hint, send_at?, ttl_seconds}. Returns 202 {notification_id}. 202 means accepted and durably queued, not delivered.
GET /v1/notifications/{id} returns status per channel with timestamps. Used for support and debugging.
PUT /v1/users/{id}/preferences with {category, channel, enabled, quiet_hours, timezone}. Returns 204. Takes effect within a minute.
POST /v1/devices registers a push token {user_id, platform, token, app_version}. DELETE /v1/devices/{token} removes it (and the platform feedback also removes dead tokens).
GET /v1/users/{id}/inbox?cursor= returns in-app notifications and unread_count. POST /v1/users/{id}/inbox/read marks items as read.
POST /v1/webhooks/provider/{name} receives delivery and bounce callbacks from email and SMS providers. Signed, and idempotent.
datamodel: notification_request: key notification_id (time-sortable), idempotency_key (unique index), producer, category, priority, template_id, params, created_at. Stored in a partitioned store; the unique index implements deduplication, and a Redis key with a 24-hour expiry guards the fast path.
delivery_attempt (the status log): partition key user_id, clustering key notification_id and channel; fields status, provider_message_id, attempts, last_error, updated_at. A wide-column store such as Cassandra with a 30-day time to live suits this: high write rate, and queries are by user ("why did I not get X?").
user_preference: key user_id, rows per (category, channel); also global flags: do_not_disturb, quiet hours with timezone, language, consent records for marketing. It is read on every notification, so it is cached; the cache entry is dropped on update.
device_token: key user_id, rows (device_id, platform, token, last_seen, app_version). A reverse index token -> user_id lets us delete a token the provider reports invalid.
template: key template_id + locale + version, with subject and body in a safe template language. Rendered by the worker, so product teams change copy without code.
inbox_item: partition key user_id, clustering key created_at descending; fields title, body, deep link, read flag. A per-user unread counter is kept in Redis.
design: Accepting a request. A product service calls POST /v1/notifications. To avoid the dual-write problem (the order service saves an order and also tells the notification service, and one of the two fails), services should use the outbox pattern: write the event in the same database transaction as the business change, and a relay publishes it to Kafka. The notification API validates, checks the idempotency key, writes the request, and publishes to a Kafka topic chosen by priority: notif.critical, notif.high, notif.normal, notif.bulk. It answers 202.
The pipeline. Separate topics per priority give isolation: the consumers of notif.critical never share threads or partitions with bulk. Each stage is a stateless worker group: (1) the resolver turns a user or segment into concrete recipients (a segment of 50 million is expanded in chunks of 1,000 users, each chunk a message on the topic); (2) the policy stage reads preferences, quiet hours, the daily frequency cap and the dedup key, and decides the channels, or drops the message with a recorded reason; (3) the renderer fills the template in the user's language; (4) the channel dispatcher sends to the provider. Between stages we use Kafka so that each stage can be scaled and replayed on its own.
Partitioning. Topics are partitioned by user_id. This keeps all messages for one user in order on one partition, which allows the policy stage to apply frequency caps without cross-partition locks, and makes collapse rules (replace "3 new messages" with "4 new messages") easy.
Channel dispatchers. The push dispatcher keeps long-lived HTTP/2 connections to APNs and FCM, sends batches, and handles responses: success, retryable (timeout, 429, 5xx), or permanent (invalid or unregistered token; the token is deleted). Email and SMS dispatchers call vendor APIs, with several vendors per channel for failover. Each dispatcher has a rate limiter per provider (a token bucket) so we stay under vendor limits and do not get blocked.
Retries and the dead letter queue. A retryable failure is put on a retry topic with exponential backoff and jitter (for example 1 s, 5 s, 30 s, 5 min, 1 h) and a maximum of 5 attempts, after which the message goes to a dead letter queue for inspection. Critical messages also switch vendor on the second failure.
Scheduling. For send_at in the future, the request is stored in a time-bucketed store (a sorted set in Redis, or a table partitioned by minute). A scheduler wakes each minute, takes due items and publishes them. "Send at 9 am local time" becomes one scheduled item per time zone group, not per user.
In-app inbox and feedback. In-app items are written directly to the inbox store and push an unread count over the open connection if the app is open. Delivery and open events come back from clients and provider webhooks, update the status log, and feed analytics, so we can compute delivery rate and open rate per template.

deepdive: Duplicates and idempotence. End-to-end exactly-once is not possible, because the provider is outside our system: we send, the network drops the answer, and we cannot know if the push was accepted. So we use at-least-once delivery with several layers of deduplication. Layer 1: the idempotency key on the API (a retry from the caller creates one request). Layer 2: the policy stage writes a claim record (notification_id, channel) with a conditional insert before it sends; a second worker that processes the same Kafka message sees the claim and skips. Layer 3: for push, we set a collapse id (APNs collapse-id, FCM collapse_key) equal to the notification id, so if a duplicate reaches the provider the phone shows one message. Layer 4: the app deduplicates by id when it handles the payload. A crash between "sent" and "claim marked sent" can still cause one duplicate for email and SMS, and we accept that as the price of not losing messages. For critical messages we prefer a duplicate to a loss; for marketing we prefer a loss to a duplicate, so the retry policy differs by priority.
Priority isolation and backpressure. When a campaign puts 50 million items on a topic, the consumers of that topic can be hours behind, and that is fine. What must not happen is that critical traffic waits behind them. Separate topics, separate consumer groups and separate worker pools make this a hard guarantee, and also separate provider connections and, where possible, separate vendor accounts (OTP SMS on a premium route, marketing on a cheap one). The campaign resolver is rate-controlled: it emits chunks only when the bulk topic's lag is under a limit, which is application-level backpressure. The tool shows its operator an estimated finish time computed from the current rate.
Provider rate limits and slow providers. APNs and FCM respond in 20 to 100 ms normally, but vendor email APIs can take seconds and fail in bursts. Each dispatcher uses a token bucket per provider and a circuit breaker: after N errors in a window the breaker opens, traffic goes to the second vendor (email, SMS) or waits (push has no second provider for the same device), and the breaker probes again after a cool-down. Without a breaker, retries pile up, threads block, and a slow vendor turns into our own outage.
Frequency caps and user fatigue. A policy stage that only follows preferences still allows 40 notifications in a day from five teams. We keep a per-user counter in Redis per category and per day (INCR with expiry), and a global cap (for example 6 non-critical notifications per day). Items over the cap are dropped, delayed to a digest, or merged ("5 people liked your post"). Digests need a delay window; this is the one place where we deliberately add latency, and only for low-priority categories.
Token hygiene. Device tokens go bad when users uninstall the app or restore a phone. APNs returns 410 (Unregistered) and FCM returns UNREGISTERED. We delete the token on the first permanent error. Sending to dead tokens wastes capacity and can lower reputation with the provider. Email has the same problem: hard bounces must suppress the address at once, and complaints (spam reports) must unsubscribe the user, otherwise the sending domain is flagged and all email goes to the spam folder.
Multi-tenancy and quotas. The platform serves many teams. Each producer has a quota per priority (requests per second and daily volume) enforced at the API, so a runaway loop in one service returns 429 and does not fill the topics. Templates and categories are registered, and unregistered categories cannot send, which keeps the preference center meaningful.
Large fan-out to millions of users. Expanding a segment is a query on the data platform (for example a Spark or SQL job that writes user ids), and the resolver reads the result in pages. We store a campaign cursor so a crash resumes at the last chunk, and chunk ids are deterministic, so a re-run produces the same notification ids and the dedup claim records stop double sends. A Bloom filter of "already sent for this campaign" can stand in front of the claim store as a cheap first check, with a small false-positive rate that only causes us to ask the store.
tradeoffs: Push through your own queue versus a managed service. Choose a managed provider (a cloud notification service, or a vendor such as OneSignal or Braze) when volume is below a few hundred million per month and the team is small; you pay per message and give up control over priority isolation. Choose to build the pipeline when volume is in billions per day, when you need strict priority lanes, custom policy such as frequency caps tied to your business data, or the unit cost of vendors is too high. Even then you still send through APNs and FCM; "building" means owning everything before them.
Kafka versus a traditional message queue (RabbitMQ, SQS). Choose Kafka when you need replay, per-user ordering through partitions, and high throughput (hundreds of thousands per second per cluster). Choose a queue with per-message acknowledgement and delay (SQS with delay seconds, RabbitMQ) when volume is modest, you need simple retries with visibility timeouts, and you do not want to manage partitions. Kafka has no built-in delay or per-message retry, so you add retry topics; the price is a bit more design work.
Fan-out on request versus fan-out in the pipeline. Choose letting each producer service resolve its own recipients when messages go to one user (a payment alert). Choose the platform's resolver when a campaign targets a segment, because it can rate-control, chunk, resume, and apply the global frequency cap in one place. The cost is that the platform now needs access to segments and preferences.
Preference check at send time versus at request time. Check at send time (our design): the user's latest choice is honoured even if the message waited an hour in the queue. The cost is a cache lookup per message (a hit rate above 99% keeps it cheap). Check only at request time when latency is critical and the queue wait is seconds, but then you may send to someone who unsubscribed a minute earlier, which is a legal risk for marketing.
Strict ordering versus throughput. Ordering per user is cheap with partitioning by user_id, and it is enough: nobody needs a global order. Choose a stricter rule (one in-flight message per user) only for a sequence like "code sent" then "code expired".
failures: APNs or FCM outage or slowdown. The circuit breaker opens; messages stay in Kafka (retention 3 days) and are retried with backoff. Critical messages that have a second channel (SMS for a login code) fail over to it after a short timeout. The TTL on each notification (apns-expiration, FCM ttl) matters: a "your driver is arriving" push is useless after 5 minutes, so it expires and is not delivered late.
Worker crash. Kafka offsets are committed after the dispatch result is stored. The restarted worker re-reads the uncommitted messages, the claim record stops a second send in most cases, and the rare duplicate is limited to email and SMS.
Zone or region failure. Kafka runs across three zones with replication factor 3 and min in-sync replicas 2. Stateless workers restart anywhere. For a region failure, the API in another region accepts new requests; pending work in the lost region is recovered from replicated topics (mirrored) or from the outbox of the producers, which retry the call because they never received a 202.
Bad deploy of a template or the policy stage. A wrong template can send a wrong message to millions. Templates are versioned and go out by canary (1% of recipients first). A kill switch per category and per campaign stops sending within seconds, and bulk campaigns have an approval step and a dry run with sample rendering.
Preference store down. Fail closed for marketing (do not send) and fail open for critical categories (send, since the user cannot opt out of security messages). The choice is made per category and recorded.
Provider reputation. A sudden jump in spam complaints or bounces triggers an automatic throttle of that sender domain or SMS route and an alert, because the damage (blocked sending domain) takes weeks to repair.
evolution: At 1,000 users, one service that calls FCM and an email API inside the request handler, with a table for preferences, is fine. At 1 million users, move sending to a background queue (SQS or Redis based), add retries, a token table, templates and the idempotency key. At 1 billion notifications a day, add priority lanes, per-user partitioning, a campaign resolver, multiple vendors, a status log in a wide-column store, per-team quotas and an analytics pipeline, and treat the platform as a product with an on-call team and clear service levels per priority.
followups: How do you make sure a one-time password is never delayed by a campaign? || Separate priority topics, consumer groups, worker pools and provider connections. A quota on the API for each producer. The bulk resolver slows itself when its own lag is high. Measure the p99 of the critical lane and alert on it separately.
Can you guarantee exactly-once delivery? || No. The provider call is outside our transaction; if the answer is lost we cannot know the result. We use at-least-once plus idempotency keys, a claim record before sending, collapse ids at APNs and FCM, and deduplication by id in the app. Duplicates become rare, not impossible.
How do you handle a user with three devices and a new message? || Each device has a token. The dispatcher sends to all active tokens (last seen within 60 days). When the user reads it on one device, a silent push or the next sync clears it on the others. Collapse ids keep one message per device.
What happens when APNs returns 429 or the connection drops? || Respect the retry-after, reduce the rate with the token bucket, reconnect with jittered backoff, and keep the messages in Kafka. Do not retry in a tight loop. The breaker protects the thread pool.
How would you implement 'send at 9 am local time' for 50 million users? || Group users by time zone, create one scheduled item per zone (about 40), and at the due time each fires a chunked fan-out that is rate-controlled. Daylight saving changes are handled by storing the IANA zone name, not an offset.
How do you test and roll out a new template safely? || Render with sample data in CI for all locales, send to employees first, then canary to 1% with monitoring of failures, opt-outs and complaints, then ramp. Keep the previous version and a kill switch.
How do you debug 'I never got the notification'? || Query the status log by user_id: was the request received, did policy drop it (preference, cap, quiet hours), was a token present, what did the provider answer? Every drop writes a reason code. This log is the reason the platform is trusted.

@@ web-crawler
title: Design a web crawler
category: Data & analytics
level: Senior / Staff
concepts: partitioning, conshash, bloom, hashtables, trees, dns, http, tls, ratelimit, lsh, pagerank, rocksdb, kafka, s3, parsing, retries, circuitbreaker, iomodels, searchengine, graphsalgo, probability
summary: A web crawler starts from a list of seed URLs, downloads the pages, finds the links in them, and repeats, so that a search engine or a data team has a fresh copy of a large part of the web. The idea is a breadth-first search on a graph with tens of billions of nodes, but the real work is everything around it: not hurting the sites you visit (politeness), not crawling the same page twice, escaping infinite URL spaces, deciding what to refresh and when, and spreading all this over many machines without a central bottleneck.
requirements: Functional. Given seed URLs, discover and download HTML pages (and optionally images and PDFs), extract text and outgoing links, store the content for the indexing pipeline, and schedule re-crawls so that fresh pages stay fresh. Respect robots.txt and crawl-delay hints. Support priorities (news sites hourly, rarely changing sites monthly). Detect duplicate content and near-duplicates. Handle redirects, errors and different encodings.
Non-functional. Scale: refresh 5 billion pages per 30 days. Politeness: no more than about one request per second to one host, and fewer if the site is slow. Robustness: bad HTML, endless pages, slow servers and malicious sites are normal. Extensibility: new content types (PDF, JavaScript-rendered pages) plug in without redesign. Freshness over completeness: it is better to have the 1 billion important pages fresh than the whole long tail stale. Cost: crawling is network and storage bound, so bytes matter.
Assumptions we choose: 5 billion pages are re-fetched every 30 days, the average HTML page is 100 KB (uncompressed), each page has about 10 outgoing links, the crawler finds about 30 billion distinct URLs over time (most of them never fetched), and we store content gzip-compressed.
estimates: Fetch rate. 5,000,000,000 pages / (30 days x 86,400 s) = 5e9 / 2.592e6 = about 1,930 pages per second. We design for 5,000 per second to catch up after failures and to support priority crawls.
Bandwidth. 1,930 pages per second x 100 KB = 193 MB/s = about 1.5 Gbit/s on average; at 5,000 per second it is 500 MB/s = 4 Gbit/s. This is a modest amount for a data centre, so the network is not the limit. The limit is politeness and DNS.
Storage. One full snapshot is 5e9 x 100 KB = 500 TB raw. Gzip on HTML gives about 4:1, so 125 TB. Keeping the last 3 versions of each page: 375 TB in object storage. Extracted text and links (say 20 KB per page) add 100 TB.
URL set. 30 billion distinct URLs. Storing each as an 8-byte hash needs 30e9 x 8 B = 240 GB; with hash table overhead about 400 GB. A Bloom filter at 1% false positive rate needs about 9.6 bits per element: 30e9 x 9.6 = 288e9 bits = 36 GB. With 16 shards this is about 2.3 GB per machine, which fits in RAM. The cost is that 1% of new URLs are wrongly seen as already known and skipped, which is acceptable for discovery; it is not acceptable for the "was this page fetched" record, which uses an exact store.
Frontier size. 30e9 URLs x 100 bytes of metadata (URL, priority, last fetch time, change estimate) = 3 TB. This lives on disk (RocksDB on SSD) with a small in-memory index, not in RAM.
Fetcher machines. One fetcher process with an event loop can hold 1,000 open connections. If one fetch takes 1 second (DNS, TCP connect, TLS, transfer; many sites are slow), one process does about 1,000 fetches per second in theory. Parsing and compression use CPU: about 5 ms per 100 KB page on one core. So 5,000 pages per second needs 25 cores for parsing. We choose 40 fetcher machines with 16 cores each, which is 8x headroom for slow sites, retries and rendering.
Politeness bound. At one request per second per host, 5,000 pages per second need 5,000 different hosts being crawled at the same time. That is easy for the whole web (hundreds of millions of hosts), but it means a single site with 50 million pages takes 50e6 s = 580 days at 1 request per second. Big sites get a higher negotiated rate or sitemaps.
DNS. Almost every new host needs a lookup. At 5,000 fetches per second but with 50 pages per host average per cycle, new-host lookups are about 100 per second; the public resolvers would rate limit that, so we run our own caching resolvers.
api: Internal APIs only, since a crawler is a pipeline, not a public service.
POST /frontier/seeds with {urls[], priority, source}. Adds seed URLs, normalised. Returns {accepted, duplicates}.
GET /frontier/next?worker=<id>&n=100 (or a streaming pull). Returns a batch of {url, host_ip_hint, attempt, deadline} that are due and allowed by politeness. A fetcher pulls only what it can fetch within the deadline.
POST /fetch-results with {url, status, final_url, content_hash, fetched_at, fetch_ms, etag, last_modified, content_ref, links[]}. Fetchers report results in batches; the frontier updates its schedule.
PUT /hosts/{host}/policy with {crawl_delay, max_rps, allow_js_render, budget_pages}. Operators or an automatic controller set per-host policy.
GET /hosts/{host}/stats shows pages fetched, error rate, average latency, robots.txt version. Used by operators when a site owner complains.
datamodel: url_state: key = hash(normalised URL) (64-bit), value = {url, host_id, depth, priority, last_fetch, next_fetch, change_rate_estimate, content_hash, status, fail_count}. Stored in an LSM key-value store (RocksDB) sharded by host_id, not by URL hash: all URLs of one host live on one shard, so the politeness state for that host is local. Point lookups and updates are cheap in an LSM tree and the data is write-heavy.
host_state: key host_id, value {robots_txt (parsed, with fetched time), crawl_delay, last_request_at, ip_addresses, error_ema, page_budget_used}. Small (500 million hosts x 1 KB = 500 GB, sharded) and hot.
frontier queues: per host a priority list of due URLs, plus a global min-heap per shard ordered by "next time this host may be hit". See the design.
content store: object storage (S3-like), key content_hash, value gzip HTML; metadata row (url, fetched_at, content_hash) in a table partitioned by date for the indexer to read. Sharing by content hash makes exact duplicates free.
link graph: edges (from_url_hash, to_url_hash) appended as files in a columnar format on the data lake, used for link-based ranking (PageRank) and for discovery.
design: The loop. (1) The frontier hands out URLs that are due. (2) A fetcher resolves the host (own DNS cache), reads robots.txt from a cache, opens a connection (HTTP keep-alive and TLS session reuse), downloads the page with a size limit (for example 5 MB) and timeouts (10 s connect plus read). (3) The parser checks the content type and encoding, extracts the text and links, resolves relative links, and normalises URLs. (4) Duplicate checks: content hash for exact copies and a SimHash for near-duplicates. (5) Content goes to storage; new links go to the URL filter and then to the frontier. (6) The result updates the schedule of the fetched URL.
The URL frontier (Mercator design). The frontier is not a simple queue. It has two layers. Front queues are by priority (for example 1 to 10), filled by a prioritiser that uses page importance (link-based score), site importance and change rate. A biased selector picks from the front queues, favouring high priority. Back queues are by host: each host has its own FIFO queue, and a heap holds one entry per back queue ordered by the earliest time that host may be contacted again. A fetcher takes the top of the heap, waits if needed, takes one URL from that host's queue and fetches it. After the fetch it puts the host back in the heap with time = now + max(crawl_delay, 10 x last fetch time). The "10 x" rule makes slow sites get fewer requests, which is polite and also fast for us.
Distribution. The URL space is partitioned by host with consistent hashing, so one shard owns a host completely. This is what makes politeness easy: there is no cross-machine coordination to ensure one request per second per host. A fetcher process joins as a client of one or more shards. When a parser finds a link whose host belongs to another shard, it sends it in a batch (for example 1,000 URLs or 1 second) to that shard over Kafka or RPC. Adding or removing a shard moves only 1/N of the hosts.
URL filtering and deduplication. Before a discovered URL reaches the frontier it is normalised: lower-case scheme and host, remove default port and fragment (#...), sort query parameters, remove known session ids and tracking parameters, resolve "../". Then a Bloom filter on the shard asks "seen before?". A no is certain, so the URL is added. A yes could be a false positive (1%), and we accept losing those. An exact check on the url_state store runs only for URLs about to be added to important queues.
Content deduplication. Many different URLs have the same text (print versions, mirrors, tracking parameters). An exact SHA-256 over the cleaned body catches identical pages. For near-duplicates, SimHash gives a 64-bit fingerprint such that similar documents have fingerprints with small Hamming distance; two pages are near-duplicates when they differ in at most 3 bits (Manku et al., Google, 2007). To search fast, the fingerprint is split into blocks and indexed in several permuted tables, a form of locality-sensitive hashing. Near-duplicates are still stored, but marked, so the index can show one.
Recrawl policy. Pages change at different rates. We keep an estimate per URL: each visit tells us if the content hash changed, and a Poisson model with rate lambda per day is updated with every visit. The next visit time is chosen to maximise the expected freshness per fetch: pages that change daily and matter are revisited daily, pages that never changed in a year are revisited every 60 days. HTTP conditional requests (If-None-Match with ETag, If-Modified-Since) turn most re-fetches into a 304 response of a few hundred bytes.

deepdive: Politeness in detail. A crawler that sends 100 requests per second to a small site can take it down, and the site owner will block us. Four rules together keep us safe. One: robots.txt (RFC 9309) is fetched first for every host, cached for up to 24 hours, and obeyed; a robots.txt that returns 5xx means "treat the site as disallowed for now", and 4xx means "no restrictions". Two: at most one connection per host, with a delay of max(crawl_delay, 10 x last response time), and an adaptive slowdown when the error rate or latency rises. Three: a per-IP limit, because many hosts share one IP (shared hosting, CDNs); a limit per host would still overload the shared server. Four: a per-host page budget per cycle, so one big site cannot use all the capacity. The back-queue design gives rules one and two for free.
Spider traps. Calendars with a "next month" link, session ids in URLs, and search result pages create infinite URL spaces. Defences: a maximum URL length (2,000 characters), a maximum depth from a seed, a maximum number of pages per host per cycle, detection of repeating path segments (/a/b/a/b/a/b), and a duplicate-content ratio per host: if 90% of the last 1,000 pages of a host are near-duplicates or empty, the host's budget is cut. Because the traps are many, a human-visible dashboard of "top hosts by pages fetched" is as important as the code.
DNS and connection costs. A cold fetch pays DNS (about 20 to 100 ms), TCP connect (one round trip), and TLS (one more round trip with TLS 1.3), before the first byte. At 5,000 pages per second we cannot afford to repeat this. We keep a local DNS cache with a long time to live and prefetch the next hosts in each queue; connections are kept alive per host and reused for the next page, and one host's queue is drained in bursts (for example up to 5 pages in a row when the crawl delay is small). We also resolve to the IP address once and store it in host_state, which helps the per-IP limit.
JavaScript pages. A growing part of the web renders content in the browser. A headless browser costs 10 to 50 times more CPU and memory than a plain HTTP fetch. We run it as a separate, small pool: the parser flags pages with little text and many scripts, and only those (or hosts on a list) are sent to the render queue. This keeps the cost under control and the main pipeline fast.
Failure handling per URL. A fetch can fail by DNS error, timeout, connection reset, 5xx or 429. Each URL has a failure counter; the retry delay doubles (1 hour, 4 hours, 1 day, 4 days) with jitter, and after 5 failures the URL is parked for a month. A host that fails often gets a circuit breaker: the whole host is paused for an hour, which protects both sides. Redirect chains are followed up to 5 hops, and the final URL is recorded as the canonical one.
Prioritisation. What to crawl first matters more than how fast we crawl. The priority score combines: link-based importance (PageRank computed offline on the link graph and refreshed every few days), site authority, the page's own change rate, and the demand signal from the search engine (pages that users click or that appear in queries). New URLs found on high-priority pages inherit a fraction of the score. The score is used both to pick front queues and to decide which URLs are dropped when the frontier is too large.
Checkpointing and restart. A crawler runs for months. Every shard persists its frontier in RocksDB with a write-ahead log, so a restart resumes where it was. Fetcher results are written to Kafka and the content store before the frontier is updated; if a crash happens in between, the URL is simply fetched again (idempotent, since the content hash will match).
tradeoffs: Breadth-first versus best-first (priority) crawling. Choose breadth-first when you want a broad, unbiased sample (for example a research corpus like Common Crawl), because it is simple and finds high-quality pages early since good pages are linked from many places. Choose best-first with a priority score when you serve search users and freshness of important pages matters; the cost is a ranking pipeline and the risk of never visiting the long tail.
Partition frontier by host versus by URL hash. Partition by host (our choice) so that politeness and robots.txt state are local, and per-host queues are in one place. The cost is imbalance: a huge site becomes a hot shard, so we split very large hosts into virtual hosts (host + path prefix hash) while keeping the per-host rate through a shared token in a small coordination store. Partition by URL hash when there is no politeness need (for example crawling your own internal pages): the load is even and the design is simpler.
Bloom filter versus exact set for seen URLs. Choose the Bloom filter (36 GB for 30 billion at 1%) when memory is the constraint and a small loss of discovery is acceptable. Choose an exact set on disk (RocksDB, about 400 GB) when each missed URL has a cost, or when you need deletion and counts. A cuckoo filter or a counting Bloom filter helps when URLs expire.
Own crawler versus a crawl service or a dataset. Choose Common Crawl or a vendor API when your use is analysis or training data and a monthly snapshot of a few billion pages is enough; it costs nothing to build. Choose to build when you need freshness (hours), specific sites, custom parsing or legal control. Building costs a team and a lot of operational work: abuse complaints, IP reputation and legal requests.
Plain fetch versus rendering JavaScript. Choose plain HTTP for most pages and render selectively. Choose full rendering for single-page applications if their content is important and no server-side version exists; budget 10 to 50x CPU and add a separate queue.
Pull model versus push model between frontier and fetchers. In pull (fetcher asks for n URLs), slow fetchers take less, and the frontier does not need to track them. In push, the frontier controls assignment but must handle failed fetchers. We use pull with leases: a batch is leased for 5 minutes and returns to the frontier if not reported.
failures: Fetcher crash: its leases expire in 5 minutes and the URLs return to the frontier; fetches are idempotent. Frontier shard crash: it restarts from RocksDB and the log; during that time its hosts are not crawled, but no other host is affected. If a shard disk is lost, we restore from the last snapshot plus the Kafka log of results, or rediscover from the link graph.
Network or provider problems: if DNS resolvers fail, fetchers pause new hosts and continue on hosts with cached IPs. If one data centre loses outbound connectivity, other regions take over its shard ownership (with consistent hashing the ring is updated, and politeness state is rebuilt from host_state replicas, with a conservative first delay).
Getting blocked. Some sites block our IP range. We detect a sudden rise in 403 and 429 per host and slow down automatically, then flag the host for a human. We do not rotate IPs to avoid blocks; we publish a user-agent string and a contact page so owners can ask us to slow down. Respecting the owner is also a legal and a reputational need.
Storage and pipeline failures. If the content store is slow, fetchers apply backpressure (stop pulling), the Kafka results topic buffers, and the frontier stops handing out URLs. We never drop fetched content silently. A bad parser release can write wrong links for hours; the raw HTML is stored first, so we can re-parse without re-fetching.
Poison pages. A page with malformed HTML that crashes the parser is isolated by running parsing in a sandbox with time and memory limits; after two crashes the URL is blacklisted and logged.
Traffic to our own systems. A burst of discovered links (for example a huge sitemap) is absorbed by the frontier's rate-limited admission per host and the global size cap.
evolution: At 1,000 pages a simple script works: a queue in Redis, a set of seen URLs, 10 threads, one sleep per host. At 1 million pages you need a real frontier with per-host queues and robots.txt caching, and storage in object files. At 1 billion pages and beyond, you need sharding by host, a disk-based frontier, Bloom filters, SimHash dedup, change-rate based scheduling, priority from a link graph, a DNS cache, rendering pools and operations for abuse and legal contacts. The scale is mostly bounded by politeness and by how well you pick which pages deserve a visit, not by bandwidth.
followups: How do you guarantee you never hit one site more than once per second across 40 machines? || Partition the frontier by host with consistent hashing so each host belongs to exactly one shard. That shard's heap, ordered by next allowed time, enforces the delay. No cross-machine coordination is needed. Large hosts are split into virtual hosts that share a small token.
How do you avoid crawling the same URL twice? || Normalise URLs, then check a Bloom filter per shard. A 1% false positive rate is acceptable for discovery. For fetch scheduling we also keep the exact state keyed by URL hash. Duplicate content under different URLs is caught by content hash and SimHash after the fetch.
How do you decide when to re-crawl a page? || Estimate each page's change rate from past visits using a Poisson model; schedule the next visit to maximise expected freshness weighted by importance, within the crawl budget. Use conditional GET so unchanged pages cost a 304. News pages are daily or hourly, static pages are monthly.
What is a spider trap and how do you detect it? || An infinite or very large URL space such as calendars, session ids, and faceted search. Use limits on URL length, depth and pages per host, detect repeating path segments, watch the duplicate ratio per host, and cut the budget for suspicious hosts. Monitor the top hosts by volume.
How would you scale the DNS part? || Run caching resolvers close to the fetchers, long cache times with our own minimum TTL, prefetch the hosts at the head of queues, and store resolved IPs in host_state. Avoid the public resolvers because of their rate limits.
How do you crawl JavaScript-heavy sites without ten times the cost? || Render only a flagged subset: pages with little text and many scripts, or hosts on an allow list. Use a separate pool and queue with strict timeouts. Where the site exposes an API or server-side HTML, prefer that.
How do you find new pages quickly, for example breaking news? || Use sitemaps, feed (RSS, Atom) polling, push signals from publishers, and re-crawl hub pages (home pages) often, since new links appear there first. Give discovered links from high-priority hubs a priority boost.
What do you do with 5 billion pages per month downstream? || Raw HTML goes to object storage, parsed text and link graph to the data lake, and the index builder reads snapshots. Keep raw HTML so parsers can improve without re-fetching.

summary: Search autocomplete (typeahead) shows ten likely queries while the user types, after every key press or two. It must answer in well under 100 ms from the user's point of view, for billions of searches per day, using a list of hundreds of millions of past queries. The work is almost all reading, so the question is how to precompute answers for every prefix, how to keep them fresh when something becomes popular suddenly, and how to keep offensive, private or harmful suggestions out.
requirements: Functional. As the user types a prefix, return the top 10 suggested queries that start with it (or contain the typed words), ranked by popularity and relevance. Suggestions reflect trending queries within minutes. Results can be personalised and localised (language, country). Offensive, illegal and private suggestions are removed. The service tolerates typos for longer prefixes.
Non-functional. Latency: the server answers in under 20 ms at p99, so with the network the user sees suggestions in under 100 ms; otherwise suggestions arrive after the user has typed more and feel useless. Availability: a failure should degrade to "no suggestions", never to a broken search box. Freshness: base popularity updates daily or hourly, trends in minutes. Scale: handle 700,000 requests per second at peak. Consistency is not important: two users may see slightly different lists.
Assumptions we choose: 5 billion searches per day, an average of 4 suggestion requests per search after the client waits 100 ms between key presses (debounce), 100 million distinct queries worth suggesting (after removing rare ones), average query length 25 characters.
estimates: Request rate. 5e9 searches x 4 requests = 20 billion per day. 20e9 / 86,400 = 231,000 per second on average. Peak is about 3x, so about 700,000 per second. Each response is a list of 10 strings of about 25 bytes with JSON overhead: roughly 400 bytes; after compression about 250 bytes. Egress at peak: 700,000 x 400 B = 280 MB/s = 2.2 Gbit/s. Small.
Query data size. 100e6 queries x 25 bytes = 2.5 GB of raw text. Add a count (8 bytes) and an id: about 3.5 GB. This fits in the memory of one machine.
Prefix table. A query of length L has L prefixes, but many queries share prefixes. For 100M queries of average length 25 the number of distinct prefixes is roughly 300 million (shared at the short end, mostly unique at the long end). If we store for each prefix the ids of the top 10 suggestions (4 bytes each = 40 bytes) plus a key of about 10 bytes: 300e6 x 50 B = 15 GB. The structure in Lucene style (FST) is much smaller, about 1 to 2 GB. Either way one machine can hold a full copy, so we replicate the whole index and do not shard by prefix.
Machines. One in-memory server answers a prefix lookup in about 50 microseconds, so a core can do 20,000 per second; with HTTP and JSON overhead about 5,000 per second per core. A 16-core machine: 80,000 per second. 700,000 / 80,000 = 9 machines at peak; with 3x headroom and 3 regions, about 90 machines. The cost is small; the system is memory-light but latency-sensitive.
Cache hit rate. Query prefixes follow a power law (Zipf): the top 1 million prefixes (all 1 to 4 characters and the popular longer ones) take about 70% of requests. 26 letters + digits to the power of 3 is 36^3 = 46,656 prefixes of 3 characters; they alone are a large share of requests (assume 30%). A cache with 1 million entries x 400 bytes = 400 MB gives a hit rate above 70%, in the CDN and in the application cache.
Offline job. Counting queries over 7 days: 5e9 x 7 = 35 billion log lines x 100 bytes = 3.5 TB. A Spark job with 200 cores reads at about 1 GB/s per 20 cores = 10 GB/s for 200 cores, so the scan takes about 6 minutes plus aggregation: the daily or hourly build is cheap.
api: GET /v1/suggest?q=<prefix>&lang=en&country=IN&limit=10&session=<id>. Returns {query: "new y", suggestions: [{text: "new york weather", score: 0.93, type: "query"}, ...], took_ms}. The response has cache headers (max-age=60 for short prefixes; no-store for personalised responses) so the CDN and the browser cache can help. The server returns the original prefix so the client can drop late answers that no longer match the text box.
POST /v1/suggest/feedback with {session, query_prefix, chosen_text, position}. Records which suggestion was picked, which is a strong signal for ranking. Batched on the client and sent in the background.
POST /internal/queries (to the log pipeline, not a public API) with {user_hash, query, ts, country, clicked}. The logging path is fire-and-forget into Kafka.
PUT /internal/blocklist with {pattern, reason}. Immediately removes matching suggestions from all serving nodes (pushed by the config system within seconds).
datamodel: Query dictionary: key query_id, value {text normalised (lower case, Unicode normalised, spaces collapsed), count_7d, count_1d, trend_score, language, flags (adult, blocked)}. Built offline.
Prefix index: a trie or FST over normalised query text. In the trie each node stores the top 10 query ids under it (precomputed). The trie is serialised as one immutable file per language and region, loaded into memory by serving nodes with a memory-mapped read.
Trending overlay: a small in-memory map prefix -> list of (query, short-term score), updated every minute from the stream job, with entries expiring after 6 hours.
Personal history: key user_id, value last 50 queries (hashed id, retention 90 days, opt-out supported), stored in a key-value store such as Redis and read only when the user is signed in.
design: Serving path. The browser sends GET /v1/suggest only after 100 ms without typing, and cancels the previous request when a new key arrives. The request goes to a CDN edge which answers from cache for common short prefixes. On a miss it goes to the suggestion service. The service normalises the prefix, looks in an application cache (an in-process LRU with a hit rate of 50% for what the CDN missed), and otherwise walks the in-memory trie: from the root, follow one edge per character to the prefix node, and read the precomputed top-10 list stored in that node. That is O(L) steps for a prefix of length L, with no sorting at request time.
Merging layers. The base list comes from the trie. The service then merges the trending overlay (the stream job's short-term list for the same prefix), the user's personal history (queries the user typed before that match the prefix), and applies filters: blocklist, language, country. A small scoring function combines the signals: score = w1 x log(count_7d) + w2 x trend + w3 x personal_match + w4 x position_prior. The merged top 10 is returned. The whole path costs under 1 ms of CPU.
Building the index (batch layer). A daily or hourly Spark job reads the query logs from the data lake (partitioned by hour), removes bots and abusive traffic, normalises text, counts queries per week with exponential decay (so older counts weigh less: weight = 0.5 per 3 days), drops queries seen by fewer than 5 distinct users (privacy and quality), and applies the blocklist and a safety classifier. It then builds the trie with top-10 per node and writes the files to object storage. Serving nodes download the new version, load it in the background, and switch with an atomic pointer change; the old version is kept for fast rollback.
Trending (speed layer). A Flink job reads the live query stream from Kafka, counts queries in sliding windows (for example 15 minutes sliding every minute) with a count-min sketch to keep memory small for the long tail, and finds queries whose count is far above their normal rate (ratio of the current window to the 7-day average). The top few thousand trending queries are pushed to all serving nodes every minute, each with a time to live. This is the Lambda-style combination: a slow, exact batch view plus a fast, approximate real-time view.
Client behaviour. Debounce, cancel stale requests, keep a small local cache of recent prefixes, and drop responses that no longer match the current text. For mobile, start a connection (DNS, TLS) when the search box gets focus, since the first request would otherwise pay 3 round trips. Use HTTP/2 or HTTP/3 keep-alive so each keystroke request costs one round trip and no handshake.

deepdive: The data structure. The simplest design is a trie with a count at each word end, and at request time walking the subtree of the prefix node to find the best 10. That subtree can have millions of nodes for a short prefix like "s", so the walk is far too slow. The fix is to precompute: every node stores its own top-10 list. Lookup becomes O(L) for L characters. The cost is memory: each node holds up to 10 ids. We reduce it three ways: store ids (4 bytes) instead of strings; compress chains of single-child nodes into one edge (a radix tree); and store top-k only at nodes above a minimum count, because deep nodes have few children and can be scanned at request time. The Lucene FST (finite-state transducer) with weights is a compact alternative: it shares prefixes and suffixes, and finds the top-N completions of a prefix by a best-first search with a priority queue; Elasticsearch's completion suggester uses it. Hsu and Ottaviano (2013) describe space-efficient top-k completion structures that are about as fast.
Ranking and freshness. Pure counts favour old, big queries. A good score blends: long-term popularity (log of the 7-day decayed count), short-term velocity (current 15-minute count divided by the 7-day average rate), location, language, and click-through of the suggestion itself (position-bias corrected). Trending needs care: a spike of 50 searches in a minute for a rare query could be a bot. We require a minimum number of distinct users (for example 100 in the window) before a trending query is allowed, and we use the count-min sketch only to find candidates, then verify with exact counts for the top few thousand.
Hot prefixes and caching. A few prefixes receive a huge share of traffic. These are exactly the cheapest to cache: short prefixes, with a stable top-10, tolerate a 60-second TTL. The CDN cache key includes language and country but not the user, so personalised results must be added after the cache: the service sends cached base results to the edge, and the client (or an edge worker) merges the user's recent searches. This keeps the hit rate high and privacy simple.
Replication, not sharding. The full prefix index is 1 to 15 GB, so each node holds all of it. The cluster scales by adding identical replicas behind a load balancer and the index rollout is a file copy. If the index grew to hundreds of GB (many languages, every product title), we would shard by language first and then by a hash of the first 3 characters with a small fan-out to merge. Sharding by the first letter alone creates hot shards because letters are very unequal.
Index rollout. A new index version is validated before it receives traffic: size checks, a sample of 10,000 known prefixes with expected top results, a check that no blocked term is present, and a drift check (the overlap of top-10 lists with the old version should be above 80% for popular prefixes). Then a canary: 1% of nodes load it for 30 minutes. The switch is an atomic pointer change; rollback is the same change in reverse.
Safety and privacy. Suggestions can leak private data: if a user searches "john smith's phone number 98xxxx" and enough such queries exist, the system could show it to others. Rules: a query must come from at least 5 (or more) distinct users in the window; patterns of emails, phone numbers and ids are removed; the user's personal history is never shown to other users; there is an opt-out; and for sensitive categories (health, politics) the suggestions are conservative. Offensive or defamatory suggestions are handled by a blocklist (instant) plus a classifier in the build, plus a fast takedown path.
Typos and non-prefix matches. Many users type "facbook". Strict prefix matching shows nothing. For prefixes of 4 or more characters, we add a fallback: a spelling index (character n-grams or an edit-distance automaton, Levenshtein distance 1) that proposes corrections. For multi-word queries we also index word-level suffixes, so "york" can suggest "new york weather". Both add memory, so they are turned on by language and measured by acceptance rate.
tradeoffs: Precomputed top-k per prefix versus compute at request time. Choose precomputed top-k when reads are 1000x more frequent than updates and latency must be under 1 ms of CPU, which is the case here. Choose computing at request time (a search engine query on an inverted index with prefix match and scoring) when the suggestions depend on many filters (product catalogs with stock and price, permissions per user), because you cannot precompute every combination; you pay with 10 to 50 ms per request and a larger cluster.
Trie in memory versus Elasticsearch or Lucene completion. Choose your own in-memory trie or FST service when you want the lowest latency, full control of scoring and simple operations (immutable file plus atomic switch). Choose Elasticsearch (completion suggester or search-as-you-type fields) when you already run it, your data is a catalog that changes often, and 10 to 30 ms per request is fine. The managed route costs less engineering and gives less control over freshness and ranking.
Batch only versus batch plus stream. Choose batch only (hourly) if the product is stable and trends are not a business need: the system is simple, and you can rebuild everything from logs. Choose batch plus stream when the product is news-like or event driven and a trending term must appear in minutes; you pay with two pipelines, a merge step, and two places for bugs. A Kappa-style design with only the stream job is possible if you can keep the state needed for the full history in the stream engine, which is usually more expensive.
Exact counts versus sketches. Choose exact counts (Spark group-by) for the batch layer because the data is already on disk and you need exactness for the ranking of big queries. Choose count-min sketch and heavy-hitter algorithms in the stream layer, where the long tail would use too much state; the sketch over-estimates a little, which is harmless for finding the top few thousand.
CDN caching versus personalisation. Choose to cache the generic response at the edge and add personal results later when privacy and hit rate matter. Choose server-side personalised responses when personalisation is the main value (for example a shopping app), accepting a lower cache hit rate and more servers.
failures: Serving node crash: the load balancer removes it after failed health checks within seconds; other replicas hold the same index. The client has timeouts of 300 ms and shows nothing rather than blocking the search box.
Bad index build. A broken Spark job could produce an empty or offensive index. The validation gates and the canary stop it; if a bad version reaches production, we revert the pointer in seconds to the previous version, which is kept on every node.
Stream job failure or lag. Trending data goes stale but the base index still works. Trending entries have a time to live, so a stuck stream job cannot keep a stale trend forever. We alert on lag.
Hot query storm. A major event produces a huge spike on a few prefixes. The CDN and application caches absorb it; requests are coalesced (when 1,000 requests for the same missing key arrive, only one goes to the service and the others wait for it).
Overload. Under extreme load, the service sheds load by returning an empty list to a percentage of requests with a 429-like signal, and the client backs off for 10 seconds. Suggestions are optional; search must continue to work.
Region loss: DNS or anycast moves traffic to another region; each region has a full copy of the index, so no data transfer is needed. The user's personal history may be unavailable for a few minutes; the system returns generic results.
Data poisoning. Attackers can send many fake searches to push a phrase into the suggestions. Defences: count distinct users and not raw counts, discount traffic from suspicious IP ranges and devices, minimum age of accounts, and a human review queue for fast-rising new queries before they are shown to all users.
evolution: At 1,000 users, a SQL query "SELECT query FROM queries WHERE query LIKE 'new y%' ORDER BY count DESC LIMIT 10" with an index on the text column works. At 1 million users, load the data in memory in one trie service and cache the results; rebuild nightly. At 1 billion users, add the CDN layer, a stream job for trends, regional replicas, personalisation, multi-language handling, a safety pipeline and an experiment system to test ranking changes (the acceptance rate of suggestions is the metric to improve).
followups: Why precompute the top 10 at each trie node instead of searching the subtree? || The subtree of a short prefix can contain millions of queries; scanning it takes milliseconds to seconds. Precomputed lists make lookup O(length of prefix). The price is memory and a rebuild when counts change, which we accept because updates are periodic.
How do you handle a new trending topic within minutes? || A stream job counts queries in sliding windows with a count-min sketch, compares with the 7-day baseline and pushes the top trending queries with a short TTL to all serving nodes. The service merges them with the base list at request time. We require a minimum number of distinct users to resist bots.
How do you keep the latency under 100 ms for users far from the data centre? || CDN edge caching for common prefixes, regional replicas of the whole index, a persistent HTTP/2 or HTTP/3 connection opened when the search box is focused, debounce and cancellation on the client, and small responses (under 1 KB compressed).
How would you shard this if the index was 500 GB? || First by language and region, which have natural boundaries. Then by hash of the first 2 to 3 characters of the normalised prefix, not by the first letter, to avoid hot shards. A router sends the request to one shard for prefixes of length 3 or more; shorter prefixes are cached and precomputed globally.
How do you make sure private or harmful suggestions never appear? || Minimum distinct-user thresholds, pattern removal for personal data, a blocklist pushed to all nodes in seconds, a safety classifier in the build, review of fast-rising queries, and a rollback path. Personal history is added only for that user and never enters the shared index.
What metrics tell you the system works? || Server-side p99 latency and error rate, cache hit rates, acceptance rate (the share of searches that used a suggestion), keystrokes saved per search, freshness lag of the trending layer, and the share of searches with zero suggestions.
How do you support typos? || For prefixes of at least 4 characters, fall back to a fuzzy lookup with an edit-distance 1 automaton or n-gram index over popular queries, and rank corrected suggestions below exact prefix matches. Measure whether corrections are accepted before enabling widely.

title: Design a search engine for posts
category: Data & analytics
level: Senior / Staff
concepts: invindex, postings, bm25, lucene, elasticsearch, docvalues, scattergather, partitioning, replication, kafka, bitmap, searchengine, queuesbuf, tieredstorage, compaction, cachelayer, recsys, lockfree, memhier, ratelimit, queryopt
summary: A post search engine lets a user type words and find matching short posts from billions of posts, newest and most relevant first. A new post must be searchable within seconds, and the results must hide deleted, private and blocked content. This is the same problem as a web search engine, but with three differences that shape everything: documents are tiny, new documents arrive constantly and are wanted at once, and recency matters as much as text match. The central mechanism is the inverted index; the hard part is keeping it fresh, sharded and fast.
requirements: Functional. Keyword search over post text, hashtags, mentions and author names. Query operators: AND by default, "exact phrase", -exclude, from:user, lang:xx, since:date, has:image. Results ordered by recency ("Latest") or by relevance ("Top"). Cursor-based pagination. Posts appear within seconds of publishing and disappear soon after deletion. Respect visibility: no posts from private accounts the viewer does not follow, none from blocked or muted accounts.
Non-functional. Latency: p99 under 200 ms for a query, of which the index part is under 50 ms. Freshness: a new post is searchable within 10 seconds at p99. Availability: 99.95%; search can serve slightly stale results during failures, but not wrong visibility. Scale: 200 million new posts per day, 500 million searches per day. Cost: serve the most recent week from memory and the older archive from cheaper storage.
Assumptions we choose: average post of 20 tokens after tokenizing, 200M posts per day, a real-time window of the last 7 days, an archive of the last 3 years, and a search peak of 3x the average.
estimates: Query rate. 500e6 searches per day / 86,400 = about 5,800 per second on average, about 17,000 per second at peak (3x).
Index writes. 200e6 posts per day / 86,400 = 2,300 per second on average; peak 7,000 per second. Each post adds about 20 postings (one per distinct term), so the index absorbs 140,000 postings per second at peak. That is small for in-memory structures: a single thread can add more than 100,000 postings per second.
Real-time tier size. 7 days x 200M = 1.4 billion posts. Per post in memory: 20 postings x 6 bytes (document id delta, position or flags) = 120 bytes; document values for ranking (author id 8 B, timestamp 4 B, language 2 B, like/repost/reply counters 12 B, flags 4 B, quality score 4 B) = about 40 bytes; the stored text and metadata for display, 300 bytes. Total about 460 bytes per post. 1.4e9 x 460 B = 644 GB. We round to 650 GB for one copy.
Shards for the real-time tier. Keep one shard at about 100 million posts (46 GB), a size that fits in memory with room for growth and rebuilds in minutes. 1.4e9 / 100e6 = 14 shards. The query fan-out is to the shards that can contain the answer.
Replicas for query load. One query in the real-time tier touches up to 14 shards (we use early termination for "Latest", so average maybe 4, but plan for the worst). Peak shard queries per second: 17,000 x 14 = 238,000. An in-memory shard replica on a 16-core machine handles about 4,000 queries per second at 10 to 20 ms. 238,000 / 4,000 = 60 replicas, which is about 4.3 copies of the 14 shards. We deploy 5 replicas: 14 x 5 = 70 machines with 64 GB RAM each.
Archive. 3 years x 365 x 150M (average) = about 164 billion posts. Compressed on disk without stored text (text is fetched from the posts store): about 100 bytes per post, which is 16.4 TB. On NVMe SSDs of 4 TB each, that is 5 disks per copy; we use 24 shards of about 700 GB each with 2 replicas. Archive queries are rare (about 2% of traffic) but slow, 100 to 500 ms.
Network. A query response is 20 results x 500 bytes = 10 KB. 17,000 x 10 KB = 170 MB/s at peak at the front end; internally, each shard returns only 20 ids and scores (about 200 bytes), so 238,000 x 200 B = 48 MB/s. Small.
api: GET /v1/search/posts?q=<query>&sort=latest|top&lang=&since=&until=&cursor=&limit=20. Returns {posts[], next_cursor, took_ms, partial}. "partial": true if some shards timed out and results may be incomplete.
GET /v1/search/count?q= returns an approximate number of matching posts per hour for the last 24 hours (for trend charts). It uses the counts stored per term and does not need document ids.
POST /internal/index/post (not public) with {post_id, author_id, text, created_at, lang, flags}. It is the ingest call used by the indexing pipeline through Kafka rather than direct HTTP.
POST /internal/index/delete with {post_id} and POST /internal/index/engagement with {post_id, likes, reposts, replies}. Delete is applied in seconds; engagement updates are batched every few seconds.
datamodel: Posts store (not part of search): key post_id, value full post. The search index holds only what it needs to match and to rank.
Segment (the unit of index): documents are numbered from 0 within a segment in order of arrival; because ids are time-sortable, a higher segment-local doc id means a newer post. Term dictionary: a hash map or FST from term to posting list pointer. Posting list for a term: an array of doc ids, ordered newest first, with term frequency and optionally positions (needed for phrase queries). Doc values (columnar arrays indexed by doc id): timestamp, author id, language, engagement counters, quality score, flags (has_image, is_reply, is_protected). A deleted-documents bitmap per segment, one bit per doc.
Tiering by time: tier 0 "now" (the active segments of the last 24 hours, taking writes), tier 1 "week" (immutable, optimised segments), tier 2 "archive" (compressed on SSD). A routing table maps time ranges to shard sets.
Visibility data (small, separate): blocked/muted lists per user, protected-account follow lists. They are not in the index; they are applied at query time.
design: Write path. When a post is published, the posts service writes it to the posts store and publishes a "post created" event to Kafka, as in any event-driven design. Indexer workers consume the topic. Each worker runs the analyzer: Unicode normalisation, language detection, tokenization (words, hashtags, mentions, URLs, emoji, and for Chinese or Japanese, a dictionary-based segmenter), lower-casing, and optional stemming. The worker then sends the tokens to the target shard of tier 0. The shard for a post is chosen by the post's time bucket and then by hash(post_id) to spread the load across the several partitions of the current tier. One writer thread per partition appends to the active segment. Readers use the index at the same time without locks: the writer publishes new documents by advancing a volatile "max doc id" counter after writing the postings, so a reader only looks at documents below the counter (a lock-free single-writer design, as in Twitter's Earlybird).
Read path. A client sends GET /v1/search/posts to the API gateway. The search front end (the "blender") parses the query, expands it (for example synonyms for hashtags, spelling), checks the rate limit, loads the viewer's visibility lists (blocked, muted, followed protected accounts), and picks which tiers and shards to query. It sends the query in parallel to one replica of each shard (scatter-gather) with a deadline of 80 ms. Each shard evaluates the query on its inverted index: it intersects the posting lists of the terms (smallest list first, skipping ahead in the others), applies the delete bitmap, scores each candidate with a light function from the doc values (recency, engagement, language match, quality), and keeps the best 100 in a heap. For "Latest", posting lists are walked newest first, so the shard stops as soon as it has 100 matches. The shard returns ids and scores.
Merge and rank. The blender merges the shard results, removes posts the viewer may not see (blocked, muted, protected), hydrates the top 20 from the posts cache, and for "Top" sort calls a second-stage ranker (a model with features such as author reputation, the viewer's relationship to the author, and engagement velocity) on the best 200. It returns 20 posts and a cursor containing the last score and post id.
Freshness details. A post is indexed in memory in less than 2 seconds after the event is consumed; with Kafka, analysis and network the 99th percentile is under 10 seconds. Engagement counts change often (a viral post gets 10,000 likes per minute). We do not reindex; a stream aggregator sends the new counts to the shards every 5 to 10 seconds and the shard overwrites the 4-byte integers in the doc values array in place. A reader may see an old or new value but never a torn one, since a 32-bit write is atomic.
Moving data between tiers. When an active segment reaches 100 million posts or 24 hours, it is sealed. A background job merges the small segments of one day into an optimised read-only segment: posting lists are compressed (delta encoding plus bit-packing, in blocks of 128 doc ids), the delete bitmap is applied, and the term dictionary is rebuilt as an FST. Sealed segments are copied to the tier-1 shards. After 7 days a segment moves to the archive tier on SSD. Because segments are immutable once sealed, replicas are created by copying files, and a lost replica is rebuilt by copying from a peer.

deepdive: The inverted index and why it is fast. Instead of scanning every post for a word, the index maps each term to the list of documents that contain it. A query with two terms is the intersection of two sorted lists. With lists of length n and m (n smaller), a merge with skipping costs about O(n log(m/n)), so a rare term makes the whole query cheap: "coffee" has 50 million matches, but "bangalore" in the last day has 80,000, and we walk the smaller list and probe the bigger one. We order terms by list length and start with the shortest. BM25 or TF-IDF is a way to rank by term rarity and frequency; for posts of 20 words, term frequency is almost always 1, so text scoring matters less than recency and engagement, and we use a simple additive score.
Real-time index structure. A normal Lucene-style segment is immutable and sorted by term; adding one document means creating a new tiny segment and merging later, which costs a refresh interval (1 second at best) and a lot of merge work. For a stream of 7,000 posts per second, we use a special in-memory segment: posting lists are stored in linked blocks in large pre-allocated arrays (pools), each block holding up to 4 to 256 postings; new documents are appended at the head of the list; the dictionary is a hash map from term to the list head. Because only one thread writes, and readers see only documents below the published counter, no lock is needed on the read path. This costs about 6 bytes per posting uncompressed, which we accept for the fresh data because it is only 10% of the total and speeds up writes.
Sharding by time, not by term. A web search engine usually splits by document (each shard has a subset of documents and a full index for them) rather than by term, because a term-partitioned query needs to move long posting lists across the network. We shard by document and organise the documents by time. Time sharding has a big benefit: for "Latest", we query the newest shard first and stop when we have enough results; most queries never touch the archive. The drawback is that the newest shard receives all the writes and most of the reads, so we split it into hash partitions and give it more replicas.
Hot terms and hot posts. When a big event happens, a term like a team name is in 1% of all new posts, so its posting list grows by thousands per second, and 50% of queries use it. The list itself is not a problem: reading the newest 100 entries takes microseconds. The pressure is on the shards that hold the newest data, so we scale by adding replicas of tier 0 on demand (autoscaling from a template, copying the current segment files from a peer in a couple of minutes) and by caching the first page of popular queries in the front end for 5 seconds. The cache key contains the query, the sort and a coarse viewer class; visibility filtering is applied after the cache.
Deletes and privacy. A delete event sets one bit in the segment's deleted bitmap. Readers check the bit for each candidate. The bit is set within a second of consumption. Compaction later removes the post physically (to meet legal requirements the physical removal must finish within a set period, for example 30 days). Visibility rules depend on the viewer, so they are not indexed: we over-fetch (ask each shard for 100 when we need 20) and filter. If a viewer blocks many accounts, or searches a topic where most results are filtered, a second round with a larger limit is made, bounded to 2 rounds.
Query understanding. Short queries are ambiguous. The front end normalises the query like the indexer (same analyzer, or results will not match), detects operators, and for "Top" can expand with related hashtags. Query rewriting runs in single digit milliseconds, from caches and small dictionaries. A spelling corrector uses an n-gram index of popular queries and tokens from the last 7 days.
Ranking and evaluation. "Top" uses a learned ranker. To avoid circular feedback (popular posts get more clicks, so they rank higher, so they get more clicks), we use position-bias-corrected click data and occasional exploration. Quality is measured offline with human labelled queries (NDCG) and online with A/B tests on click-through, long clicks and query reformulation rate.
tradeoffs: Build on Elasticsearch or OpenSearch versus a custom in-memory engine. Choose Elasticsearch (Lucene) when the corpus is up to a few billion documents, freshness of 1 to 5 seconds is acceptable, and a small team must ship in months: you get sharding, replication, a query language and operations tools. Choose a custom engine when you have hundreds of millions of writes per day, need freshness in under a second, need in-place updates of counters, and have a team to maintain it; you save memory per document and can use time-based early termination, but you own all bugs. Twitter built Earlybird on top of Lucene ideas for this reason.
Shard by document (and time) versus by term. Choose document sharding in nearly all cases: each shard answers a query alone, and the failure of a shard only loses a part of the results. Choose term sharding if memory is so tight that the full dictionary cannot be replicated per shard and most queries are single-term; the price is network movement of posting lists and the hot term problem.
Memory versus SSD for the index. Choose memory for the last days, where most queries land and tail latency matters. Choose NVMe SSD with memory-mapped segments for the archive: 100 microseconds per random read versus 100 nanoseconds in RAM, and about 10 times lower cost per byte. A cold query on SSD touches maybe 50 blocks, so 5 ms of I/O per shard if it is not cached.
Index only text versus also store the posts. Choose to store only ids and doc values in the index and fetch the text from the posts store and its cache when the index is large and the text is already stored elsewhere. Choose to store the text inside the index for the real-time tier when the post cache would otherwise be a bottleneck and the documents are small (300 bytes). We do the second for tier 0 only.
Relevance versus recency. For events, recency dominates. For evergreen topics (a recipe), relevance and quality matter more. Choose two modes ("Latest" and "Top") so the user decides, instead of one blended score that is bad for both. The price is two code paths and a ranking team for "Top".
Exact counts versus approximate counts. For result totals and trend charts, approximate counts from per-term time buckets are enough and are 1000 times cheaper than counting all matches. Choose exact counting only for compliance and billing use cases.
failures: A shard replica crashes: the front end sends the query to another replica; the hedged request (send a second request after the 95th percentile latency) reduces tail latency. The crashed replica restarts by copying sealed segments from a peer and replaying the Kafka log from the last checkpoint for the active segment.
A whole shard group is down (all replicas): the front end returns results from the other shards with partial: true. For "Latest" this hides a time range, so the client shows a notice. Better a partial answer than none. We alert at once, because partial results for the newest tier are a visible problem.
Indexer lag: if Kafka consumers are slow, freshness drops. We monitor "indexing delay" as the time between event time and index time. The first response is to scale consumers; the second is to drop optional work (for example the engagement update stream) to keep new posts flowing.
Bad deploy of the analyzer: a tokenizer bug creates wrong tokens, and queries do not match the new posts. We keep the analyzer version in each segment, test queries against a golden set after each deploy, roll out by shard, and if needed reindex a day of posts from Kafka or from the posts store (the index is a derived view, so it can always be rebuilt).
Region loss: each region has a full tier 0 and tier 1 (they are small), fed by its own consumers of a mirrored Kafka topic. The archive may exist in two regions only. A user in a failed region is routed to another one with a few tens of milliseconds more latency.
Privacy leak: a bug that returns a protected post. The visibility filter is a final step of the front end and is tested with many cases; a kill switch disables search for protected accounts' posts quickly, and an audit job compares results against policy.
Query of death: a query with hundreds of terms or a pathological wildcard can use a lot of CPU. Each shard has a time and a work budget per query (number of postings visited), and aborts with a partial result. Rate limits per user and per IP protect the cluster from scraping.
evolution: At 1,000 posts a day, a SQL LIKE query or Postgres full-text search (tsvector with a GIN index) is enough. At 1 million posts, a single Elasticsearch or OpenSearch cluster with a few shards and a refresh interval of 1 second is the right tool. At 1 billion posts per day scale, you move to a tiered design: a custom in-memory real-time tier, immutable sealed segments, an SSD archive, a learned ranker, and strict tooling for visibility, deletes and capacity. The rule is to move to the next step only when one measurement (indexing delay, p99 latency, or memory) forces it.
followups: Why is a new post searchable in seconds when Lucene normally needs a refresh? || Lucene creates a new segment at each refresh, which is a delay plus merge cost. A real-time tier uses an in-memory append-only segment with one writer and lock-free readers, so a document becomes visible when the writer advances a counter, about a second after it is consumed.
How do you handle queries for very common words? || Walk posting lists newest first and stop after enough matches for "Latest". For intersections, start from the rarest term. Stop words can be dropped from the query only for single common words. A work budget per query protects the shard.
How do you update like counts without reindexing? || Counters live in a doc values array indexed by doc id, outside the postings. A stream aggregator sends new values every few seconds and the shard overwrites them in place. Readers may see an older value but never a torn one.
How would you hide posts from blocked accounts? || Visibility depends on the viewer, so it is not part of the index. The front end loads the viewer's block and mute sets, over-fetches from shards, removes hidden posts, and does a bounded second round if too many were removed. Protected-account posts get a flag in doc values and a check against the viewer's follow list.
What happens to results when one shard is slow? || The front end sets a deadline, uses hedged requests to another replica, and returns what it has with a partial flag. Quality drops a little but latency stays bounded.
How do you reindex the archive after a tokenizer change? || The index is derived data. Rebuild segments in a batch job (Spark) from the posts store with the new analyzer, write them as new immutable files, and switch the routing table shard by shard. The old version stays for rollback.
How do you rank 'Top' results fairly and avoid spam? || Two-stage retrieval then ranking, with features such as author reputation, engagement velocity, text quality and relationship to the viewer. Spam signals demote or remove posts; click data is corrected for position bias; evaluate with A/B tests and labelled sets.
Why not partition the index by term? || A query then needs a long posting list moved between machines, and hot terms overload their owner. Document sharding lets each shard answer alone, and time-based sharding allows early termination for latest-first search.

title: Design a video streaming platform like YouTube or a CTV service
category: Ads & media
level: Senior / Staff
concepts: mediastream, hlsdash, abr, codecs, ffmpeg, cdn, s3, erasurecoding, workflow, kafka, cachelayer, eviction, powerlaws, quic, tcp, fingerprint, contentid, tieredstorage, adtech, pixels, partitioning, idempotence
summary: A video platform lets creators upload videos and lets hundreds of millions of viewers watch them on phones, browsers and TV sets, starting in about two seconds and without stalls, on networks from 1 Mbit/s to 1 Gbit/s. The hard parts are the two big pipelines and the network between them. Upload and transcoding turn one source file into dozens of versions at a huge compute cost. Delivery moves tens of terabits per second, which is only possible by putting copies of popular segments near viewers in a content delivery network (CDN). On a connected TV (CTV) service the same design also has to insert personalised ads into the stream and report that they were seen.
requirements: Functional. Creators upload videos (up to 12 hours or 256 GB). The platform validates them, transcodes them into several resolutions and codecs, creates thumbnails and captions, and publishes them. Viewers search or browse, press play, and the video starts fast and adapts its quality to the network. Seek, pause, resume on another device, subtitles and multiple audio tracks must work. Premium content uses DRM (digital rights management). On CTV, ad breaks are inserted into the stream, and impressions are reported to advertisers. We exclude live streaming (we note the changes), recommendation and comments.
Non-functional. Start-up time under 2 seconds at p95; rebuffering (stalls) in under 0.5% of watch time; availability of playback 99.99%, more important than upload. Upload to "playable at low quality" in minutes for a 10-minute video; all renditions within an hour. Durability of original files: 11 nines (they are the source of truth for re-encoding). Cost control: egress bandwidth and storage dominate the bill, so efficiency (codecs, cache hit ratio) is a first-class goal.
Assumptions we choose: 300 million daily active viewers (DAU) watching 1 hour per day each at an average of 3 Mbit/s; uploads of 500 hours of new video per minute (a figure that YouTube has reported publicly for several years); source videos average 20 Mbit/s; a ladder of 8 renditions; 90% of views go to 10% of videos.
estimates: Watch traffic. 300e6 viewers x 1 hour x 3 Mbit/s x 3,600 s = 3.24e18 bits per day = 405 PB per day (3.24e18 / 8 = 4.05e17 bytes). Average rate: 3.24e18 bits / 86,400 s = 3.75e13 bit/s = 37.5 Tbit/s. Evening peak is about 2x: 75 Tbit/s. No origin could do this; the CDN must serve more than 95% of bytes. If the origin shield sees 5%, origin traffic is 1.9 Tbit/s at peak 3.75 Tbit/s.
Upload traffic. 500 hours per minute x 1,440 minutes = 720,000 hours of video per day. Source size per hour: 20 Mbit/s x 3,600 s / 8 = 9 GB. Uploaded bytes: 720,000 x 9 GB = 6.5 PB per day, about 75 GB/s on average. That is a few hundred 100-Gbit/s links, easy to spread over regions.
Transcoding compute. The cost depends on codec: assume 10 core-hours to produce the full H.264 ladder for one hour of video (more for VP9, 5 to 10x more for AV1). 720,000 hours x 10 core-hours = 7.2 million core-hours per day = 300,000 cores running all day. This is why large platforms have built video encoding chips, and why they use the expensive codecs only for videos that are watched a lot.
Stored size. A ladder for 1 hour of video with 8 renditions (240p 0.4, 360p 0.8, 480p 1.2, 720p 2.5, 1080p 5, 1440p 9, 2160p 16 Mbit/s, plus audio) has a total of about 35 Mbit/s if all are made; we assume an average of 20 Mbit/s over all videos because many sources are small. 20 Mbit/s x 3,600 / 8 = 9 GB per hour. Per day: 720,000 x 9 GB = 6.5 PB; per year 2.4 EB. With erasure coding (1.5x overhead) about 3.5 EB. Plus the originals: 6.5 PB per day x 365 = 2.4 EB. So storage grows by about 5 EB per year before replication; the long tail of videos that nobody watches is moved to cheaper storage or reduced to fewer renditions.
Objects. With 4-second segments, 1 hour has 900 segments per rendition, 7,200 for 8 renditions. 720,000 hours per day x 7,200 = 5.2 billion segment objects per day. That is why real systems pack segments of one rendition into one file with a byte-range index (fragmented MP4), and serve ranges.
Metadata. 800 million videos x 2 KB = 1.6 TB: small, but with 10 million reads per second for metadata and counters; it needs a sharded database with heavy caching.
CDN cache size. If 10% of videos get 90% of the views, then to hold the hot set at an edge site we need the segments of the top videos in that region. Suppose 500,000 hot hours x 9 GB = 4.5 PB total across all regions' hot sets; one site of one region may need 100 to 300 TB of SSD to hit 90%.
api: POST /v1/uploads with {title, size, content_type} returns {upload_id, upload_url}. The client uploads the file in chunks (resumable protocol): PUT upload_url with Content-Range, 8 MB per chunk, and the server answers the next expected offset. A final POST /v1/uploads/{id}/complete starts processing.
GET /v1/videos/{id} returns metadata: title, channel, duration, counts, available renditions, thumbnail URLs, and the manifest URL (https://cdn.example.com/v/{id}/master.m3u8, or an MPD file for DASH).
GET /v/{id}/master.m3u8, /v/{id}/{rendition}/index.m3u8, /v/{id}/{rendition}/seg_{n}.m4s. These are plain HTTP GETs served by the CDN. The master manifest lists the renditions with bandwidth and codec; each rendition playlist lists the segments.
POST /v1/drm/license with {video_id, device_cert, challenge} returns a license (keys) for Widevine, FairPlay or PlayReady if the user is entitled.
POST /v1/playback/events batched client events: start-up time, bitrate switches, stalls, errors, and heartbeats every 10 to 30 seconds. They feed quality dashboards, resume position and billing.
GET /v1/ads/decision?session=... (CTV and ad-supported) is called by the server-side ad insertion service, not by the TV; it returns the ad creatives for a break (see design).
datamodel: videos: key video_id; fields channel_id, title, description, status (uploaded, processing, ready, blocked), duration, created_at, renditions[], original_ref, region restrictions, monetization flags. Sharded relational database (MySQL with a sharding layer such as Vitess is a common choice) by video_id, because the main access is by id; secondary lookups (by channel) use a second index table sharded by channel_id.
Object store layout: originals/{video_id}.mp4 (cold tier, erasure coded); renditions/{video_id}/{codec}/{height}p.mp4 (fragmented MP4 with sidx index); thumbnails and sprite sheets; manifests are generated at request time or stored small.
view_state: key (user_id, video_id), value last position and timestamp. A key-value store (DynamoDB or Cassandra style), written every 30 seconds by heartbeats; used for "continue watching".
counters: views, likes. Sharded counters in a log-structured pipeline: events go to Kafka, a stream job aggregates by video per minute and writes to the counter store; the displayed number lags by a minute or more.
transcode jobs: key (video_id, chunk_id, rendition), value state, attempt, worker, output ref. The workflow engine owns this table and makes each task idempotent.
design: Upload path. The client asks for an upload session and sends chunks directly to object storage through a regional upload endpoint (signed URLs), so the application servers never carry the bytes. A resumable protocol means that a lost connection on a 4 GB upload restarts from the last confirmed chunk. On completion, an event "video.uploaded" is published to Kafka.
Processing pipeline. A workflow engine (a DAG scheduler) takes the event and runs a graph of tasks. Task 1: inspection with ffprobe: container, codec, duration, frame rate, and a safety check on the file. Task 2: split the video at keyframe boundaries into chunks of about 30 seconds. Task 3: transcode every chunk in parallel for every rendition on a pool of workers: with 20 chunks per 10-minute video and 8 renditions that is 160 independent tasks, so a 10-minute video finishes in the time of one 30-second chunk, about 1 to 2 minutes, instead of 30 minutes. Task 4: package the chunk outputs into one file per rendition, with a segment index, and generate the manifests. Task 5 in parallel: thumbnails, audio extraction, speech-to-text for captions, content fingerprinting against a reference database (content ID), and policy classifiers. The low renditions (240p to 480p) are published first so the video is playable in minutes; higher ones follow. Each task is idempotent and writes its output to a deterministic path, so retries and duplicates are safe.
Packaging and DRM. We store the video once in CMAF format (fragmented MP4) and serve it through both HLS and DASH manifests, with common encryption (CENC) so that one encrypted file works with Widevine, PlayReady and FairPlay. Keys are held in a key management service. The player gets a license only after the entitlement check.
Playback path. The player calls the metadata API, then gets the manifest from the CDN. It downloads the first segment of a low or middle rendition to start fast (a conservative first choice, for example 720p), measures the throughput, and the adaptive bitrate (ABR) algorithm picks the next rendition for every segment: rules based on measured throughput and on buffer level (for example, if the buffer holds more than 20 seconds, move up; below 8 seconds, move down). The buffer target is 30 seconds. All requests are plain HTTP GETs of 1 to 3 MB segments over HTTP/2 or HTTP/3 (QUIC), which are cacheable by the CDN and need no application server.
CDN design. Three levels: edge caches inside or next to the viewer's ISP (Netflix's Open Connect and Google Global Cache are appliances installed in ISP networks), regional caches, and an origin shield in front of the object store. On a miss, the edge asks the regional cache, which asks the shield, which asks the origin, and the response fills each cache on the way back; concurrent misses for the same segment are collapsed into one upstream request. For the most popular titles, content is pushed to the edge in advance during the night (pre-positioning) using predicted demand; for the long tail, the cache fills on demand and uses LRU-style eviction with admission rules so that one-time views do not push out hot content.
CTV and ads. On a connected TV, ads are a large part of the business. Client-side ad insertion makes the TV app request ads itself, which is easy to block and varies by device. Server-side ad insertion (SSAI) stitches ads into the manifest: when the player requests a manifest for a session, an ad-stitching service builds a personalised playlist: content segments, then ad segments, then content, with a discontinuity marker between them so the decoder resets. For live and linear channels the content has splice markers (SCTE-35) that say "an ad break starts here for 120 seconds"; the stitcher calls an ad decision server (often with a VAST response or an OpenRTB-style auction) to choose creatives, and tracking beacons (impression, quartiles) are fired by the server or by the player from tracking URLs. Ad creatives are pre-transcoded to the same ladder, so they look like content to the CDN.

deepdive: Adaptive bitrate in detail. A video is cut into segments of 2 to 6 seconds, each available at every rendition, aligned at keyframes so the player can switch at any segment boundary without a glitch. The player is the controller: it measures the download speed of recent segments and the buffer level, and chooses the next rendition. A pure throughput rule oscillates when throughput is noisy; a buffer-based rule (the buffer is a smooth signal) is more stable. Production players combine both, with hysteresis: switch up slowly (after 2 to 3 good segments) and down quickly. The server is dumb on purpose: it only serves files over HTTP, which is why a normal CDN can deliver video and the system scales by adding caches.
Choosing the ladder: per-title encoding. A fixed ladder wastes bits: a cartoon looks fine at 1.5 Mbit/s at 1080p, while a sports match needs 8 Mbit/s. Netflix (2015) introduced per-title encoding: analyse each title with trial encodes and pick the bitrate and resolution pairs along the convex hull of quality (VMAF) versus bitrate. This saves 20% or more of bandwidth at equal quality, which at 75 Tbit/s is worth a great deal. The extra compute is paid once, while the savings are paid back on every view, so it is applied first to popular titles.
Codec economics. H.264 plays on every device but is the least efficient. HEVC, VP9 and AV1 need about 30%, 35% and 50% fewer bits at the same quality, but cost 3x to 10x more to encode and need device hardware decoding to save battery. Therefore a cascade: encode H.264 for all videos; after a video passes a view threshold (for example 1,000 views), add VP9 or AV1 for the top renditions; for the top 1% encode with the best codec in several passes. The decision is an expected value: encode cost versus (views x bytes saved x price per byte).
Cache hit ratio and the long tail. Watch time follows a power law, but the tail is long: 10% of videos get 90% of views, yet the other 90% of videos still get 10% of 405 PB, which is 40 PB per day that cannot all come from edge caches. These requests flow to the regional caches and the origin. To protect the origin: the origin shield collapses duplicate requests; segments of the same video are routed to the same cache node (consistent hashing within the site) so that popular content is not duplicated across nodes in a cluster; and long-tail videos are stored on cheaper storage with slightly higher latency.
Start-up latency. The budget for 2 seconds is: DNS (cached), connection setup with TLS 1.3 and HTTP/3 (0 to 1 round trip when resumed), manifest (1 round trip, 30 ms), first segment (1 to 3 MB at 10 Mbit/s is about 1 second if it is a high rendition, so we start at a lower rendition with a smaller first segment), and decoder start. Tricks: prefetch the manifest and first segment while the user hovers on a thumbnail, shorter first segment (1 s), a lower first rendition, and a start-up bitrate remembered from the last session.
Resume and counters. Heartbeats every 30 seconds save the position to the view_state store. Views are counted only after 30 seconds of play and deduplicated per user to resist fraud. Counters go through Kafka and a stream aggregator, because updating a single row for a viral video at 100,000 views per second would be a hot key. Aggregation per minute reduces it to one update per minute per video.
Content ID and policy. At upload, audio and video fingerprints are compared with a reference database of rights holders' works (perceptual fingerprints, indexed for nearest-neighbour search). A match triggers the rights holder's policy: block, monetise, or track. The work happens in the pipeline before publishing for known high-risk categories, and after publishing otherwise, to keep latency low.
Live streaming differences. For live, the chunking and packaging happen continuously: the encoder outputs 2-second segments, the packager updates the manifest every segment, and the CDN caches the manifest for 1 second. End-to-end delay is segments in the buffer (3 x 2 s) plus encoding and delivery: 6 to 10 seconds. Low-latency variants (chunked transfer, partial segments) get to 2 to 4 seconds at the price of lower cache efficiency and smaller buffers.
tradeoffs: HLS and DASH over HTTP versus a streaming protocol such as RTMP or WebRTC. Choose HTTP-based adaptive streaming for video on demand and most live: it uses normal CDNs, works through firewalls, and scales to millions of viewers by file caching; you accept 5 to 30 seconds of delay for live. Choose WebRTC (sub-second delay) for interactive use such as auctions or video calls; it needs special servers (SFUs), costs much more per viewer, and does not benefit from standard CDN caching.
Buy a commercial CDN versus build your own. Choose commercial CDNs (several, with traffic steering) when your traffic is below roughly 5 Tbit/s or you are starting out; you pay per GB, around a few cents to under one cent per GB at large commit, and avoid operations. Choose your own edge appliances inside ISPs when you serve tens of Tbit/s: at 405 PB per day, even $0.002 per GB would be $810,000 per day, and your own caches placed in ISP networks cut transit cost and improve quality. Netflix's Open Connect and Google's global cache are examples. The price is hardware logistics and operations in hundreds of locations.
Pre-position versus fill on demand. Choose pre-positioning (push popular content to edges at night) when demand is predictable, such as a catalog service where a new show is released on a date: you avoid peak-time fills. Choose pull-through caching (fill on demand) when the catalog is huge and unpredictable, such as user-generated content; with request collapsing, misses are tolerable.
Transcode everything up front versus on demand (just in time). Choose full up-front transcoding when views per video are high, as for premium catalog. Choose just-in-time packaging or transcoding for the long tail: store only the mezzanine and the lowest ladder, and create other renditions when first requested; this saves petabytes at the cost of a slow first view and more complex serving.
Server-side versus client-side ad insertion. Choose SSAI for CTV and mobile where consistent playback, ad-block resistance and one manifest per session matter; you pay with per-session manifests that are not cacheable across viewers (manifests are small, but this breaks the pure-file model) and with measurement challenges (the server cannot see that the TV was muted). Choose client-side insertion (using the IMA SDK or similar) where the device can run rich ad logic and you want precise viewability and interactivity.
Single large file versus many small segments in storage. Choose a few packed files with range requests to cut object counts (5 billion per day otherwise). Choose individual segment objects only when your CDN cannot do range-to-cache mapping well.
failures: A transcode worker dies: its task lease expires, the workflow engine reschedules it elsewhere; the output path is deterministic so partial files are overwritten. A poison video that crashes the encoder fails after 3 attempts and goes to a dead letter state with a clear message to the creator.
A CDN edge site fails: DNS or anycast steering (or the player's list of several CDN hostnames) moves viewers to the next best site; the player retries failed segments on an alternative host. Buffer of 30 seconds hides this for most viewers. Multi-CDN switching is done by a steering service using real-user measurements.
Origin or object store issue: caches serve existing content (stale-if-error); new uploads wait in the pipeline. We keep the origin in at least three zones; originals are erasure coded across zones so that a zone loss does not lose data.
Thundering herd: a new, very popular release makes millions request the same segments that are not yet cached. Request collapsing at each tier and pre-positioning for known releases cut the origin load to roughly one request per segment per tier.
Metadata database shard failure: replicas promote in seconds; the metadata API has a cache, so most plays continue; counters and view_state writes are queued in Kafka.
Bad packaging deploy: wrong manifests make a rendition unplayable on some devices. We canary, run automated playback tests on device farms, and keep versioned manifests so we can switch back; the segments themselves remain unchanged.
DRM license service outage: licenses are cached in the player for the offline period; the service runs active-active in several regions. A long outage affects only new playbacks.
Ad system failure: if the ad decision times out (for example after 300 ms), the stitcher inserts a house ad or skips the break; the content must never stall because an ad call failed. Impressions that could not be reported are queued and replayed, and reconciliation reports compare server and client counts.
evolution: At 1,000 users, store MP4 files on one server or in S3 behind a normal CDN, and transcode with ffmpeg in a queue worker into 3 renditions. At 1 million users, add HLS with ABR, a managed CDN, a transcoding fleet with a workflow engine, and a metadata database with replicas. At 1 billion users, you need chunk-parallel transcoding, custom encoders and codec cascades, a multi-CDN or your own edge network, per-title encoding, tiered storage, a view-count pipeline, rights management, and (for CTV) an ad platform with SSAI, measurement and fraud controls.
followups: How does the player decide what quality to play? || The player measures segment download throughput and buffer level and chooses the rendition for the next segment. It starts conservatively, steps up after a few good segments and steps down fast when the buffer falls. The server only serves files, so the CDN can cache everything.
How do you make a 2-hour upload playable quickly? || Split the video into chunks at keyframes, transcode all chunks and renditions in parallel, publish low renditions first, and use idempotent tasks in a workflow engine. Latency becomes the time of one chunk plus queueing.
What if a video suddenly goes viral? || The first minutes cause misses at all tiers. Request collapsing keeps the origin load at one fetch per segment per tier, consistent hashing keeps copies per cluster limited, and hot objects are replicated across edge nodes. A background job adds the better codec renditions once the view count passes the thresholds.
How do you reduce bandwidth cost without losing quality? || Better codecs where the device supports them, per-title ladders, capped bitrates for small screens, a higher cache hit ratio with ISP-embedded caches, and not prefetching more than needed. Measure with a perceptual metric such as VMAF instead of bitrate alone.
How does server-side ad insertion work for a CTV service? || The stitcher builds the manifest per session. It asks an ad decision server for creatives at each break, adds the ad segments with discontinuity tags, and the player sees one stream. Tracking beacons for impression and quartiles are fired from the server or from URLs the player calls. Ad creatives are pre-transcoded to the same ladder.
How would you design the view counter? || Events go to Kafka with a dedup key per user and video. A stream job counts per video per minute and writes to a counter store. The display lags by a minute. This avoids a hot row for viral videos, and the pipeline can also filter fraud.
How do you handle DRM across Apple, Android and smart TVs? || Encrypt once with common encryption in CMAF. Each platform requests a license from our license server using its DRM system (FairPlay, Widevine, PlayReady). Keys are stored in a key management service and the license reflects entitlements and device security level.
How would live streaming change the design? || Continuous ingest, 2-second segments, a packager that updates manifests, tiny cache TTL for the live manifest, more delay buffers, and a separate low-latency mode. There is no time to do per-title encoding; the ladder is fixed and the encoders are hardware accelerated.

title: Design a file sync service like Dropbox
category: Infrastructure
level: Senior / Staff
concepts: merkle, hashfn, partitioning, mysql, s3, erasurecoding, occ, eventsourcing, reconcile, filesystems, sepstorage, consmodels, pubsub, sockets, dst, idempotence, retries, bloom, tieredstorage, conshash, cachelayer
summary: A file sync service keeps a folder identical on many devices and in the cloud. A user saves a file on a laptop, and a few seconds later it appears on a phone and on a colleague's computer, even if the devices were offline for days. The design splits into two very different problems: storing huge amounts of immutable data cheaply (blocks addressed by their hash), and keeping a small, strongly consistent history of who changed which path (metadata). The hard parts are efficient transfer of small edits to large files, conflict handling, shared folders, and getting a sync engine to be correct when files change while it is syncing.
requirements: Functional. Install a client that watches a folder. Create, edit, rename, move and delete files and folders, and see the change on all linked devices. Share a folder with other users with read or write permission. Keep version history for 30 days and allow restore. Work offline and merge on reconnect. Files up to 2 TB. Download a file or folder in a browser. We exclude real-time co-editing (see the collaborative editing design), full-text search and content scanning.
Non-functional. Latency: a small file appears on another online device in under 5 seconds at p95. Durability: 11 nines for file content; a lost block is a lost customer file. Consistency: the metadata for one folder is strongly consistent (everyone sees the same order of changes), while blocks are immutable. No silent data loss: if two people edit the same file, both versions are kept. Efficiency: sync only the bytes that changed, and do not upload a block that is already in the system. Client cost: the sync client must use little CPU, disk I/O and battery.
Assumptions we choose: 300 million registered users, 100 million daily active users (DAU), 3 GB stored per user on average, 1,000 files per user on average, 4 MB maximum block size, 1.5 devices per user, 10 file changes per DAU per day.
estimates: Logical storage. 300e6 users x 3 GB = 900 PB. Deduplication of identical blocks (the same installer or PDF in thousands of accounts, and unchanged blocks of edited files across versions) removes perhaps 30%: 630 PB of unique data. With erasure coding (for example 1.5x overhead across zones) the physical size is 630 x 1.5 = about 945 PB. With triple replication it would be 1,890 PB, so erasure coding saves about 945 PB of disk.
Files and metadata. 300e6 x 1,000 = 300 billion file entries. At about 300 bytes per entry (path, name, size, mtime, block list reference, revision) that is 90 TB of metadata, plus history of versions (about 3x): 270 TB. This is stored in sharded relational databases and is the hard consistency problem; it is 0.03% of the data volume but 90% of the engineering complexity.
Blocks. 630 PB / 4 MB = 1.6e11, but small files take less than a block, so assume 300 billion blocks. A block index entry is a 32-byte hash plus a 16-byte location: 48 bytes x 300e9 = 14 TB. Sharded by hash prefix across maybe 500 shards of 30 GB; each shard fits in memory with a bloom filter in front of the on-disk part.
Change rate. 100e6 DAU x 10 changes = 1 billion file changes per day. 1e9 / 86,400 = 11,600 per second on average, about 35,000 per second at peak (3x). Each change is one metadata commit (a few KB) and, on average, one or two missing blocks.
Upload bandwidth. Suppose the average change uploads 500 KB after deduplication and delta (most edits are small, a few are huge). 11,600 x 500 KB = 5.8 GB/s = 46 Gbit/s on average, about 140 Gbit/s at peak. Download is about 1.5x this, since each change goes to other devices: 70 Gbit/s on average.
Connections. At peak 50% of 150 million devices are online: 75 million long-lived connections to the notification service. At 250,000 connections per server (small, mostly idle), that is 300 servers, 600 with redundancy.
Cost check. Storing 945 PB at $0.01 per GB-month would be about $9.5 million per month; this is why own hardware and erasure coding matter at this scale.
api: POST /v1/commit with {namespace_id, device_id, changes: [{path, op: add|edit|move|delete, parent_rev, size, mtime, block_hashes[]}]}. Returns {accepted: [...new revs and journal cursor], need_blocks: [hashes], conflicts: [...]}. The first call is often answered with need_blocks; after the upload the client repeats it. The call is idempotent through a client-chosen commit id.
PUT /v1/blocks/{sha256} uploads one block (at most 4 MB) to a block server. Returns 200 if stored. If the block already exists, the server answers 200 without storing again. The server recomputes the hash and rejects a mismatch.
GET /v1/blocks/{sha256} downloads a block; served through a cache or CDN for popular shared files.
POST /v1/list_changes with {namespace_id, cursor} returns {entries[], new_cursor, has_more}. This is the sync feed: all changes after the cursor, in order. A new device starts with an empty cursor and receives a full listing.
POST /v1/subscribe (long poll or WebSocket) with {namespace_cursors: {ns1: c1, ns2: c2}}. Returns when any namespace has changes after its cursor, or after 90 seconds with "no change". The reply holds no data: it only tells the client to call list_changes.
POST /v1/share with {folder_id, user, role}. Creates a namespace mount for the invited user. POST /v1/restore with {path, rev}.
datamodel: Namespace: the unit of sharing and of consistency. Every user has a root namespace; every shared folder is its own namespace, mounted into the root namespaces of its members. A namespace has an id, an owner or ACL list, and a monotonically increasing journal cursor.
File journal (the metadata): table sharded by namespace_id; rows (namespace_id, cursor, file_id, path, op, rev, size, mtime, block_list, device_id). The cursor is the primary ordering, assigned by the shard. The current state of the folder tree is a materialised view (table file_head keyed by (namespace_id, file_id), with path indexed) of the journal, kept in the same shard and the same transaction. All history is kept for the version window.
Block list: a file revision stores an ordered list of block hashes (32 bytes each; a 1 GB file has 250 blocks = 8 KB of hashes). A small file stores its hash list inline.
Block store: content-addressed. Key sha256(block), value the (compressed, encrypted) bytes, stored in a blob system with erasure coding; a block index maps hash to storage location and a reference count or a periodic garbage-collection mark.
Device table: (user_id, device_id, last_seen, per-namespace cursors). The server does not need client cursors for correctness (the client holds its cursor), but it helps for diagnostics.
MySQL (InnoDB) is a common choice for the journal because transactions per shard are exactly what is needed; Dropbox has described its metadata system, Edgestore, as sharded MySQL with a layer above it.
design: Detecting changes. The client registers with the operating system file watcher (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows) and also scans at startup, because events can be lost. When a file changes, the client waits until it is stable (writes finish; for 2 seconds no more events), then reads it.
Chunking and hashing. The client splits the file into blocks of up to 4 MB and computes SHA-256 for each block. For a file that was seen before, only blocks whose bytes changed produce a new hash, so editing a few bytes of a 1 GB file creates one new 4 MB block and 249 known ones. The client keeps a local database of the last synced state to know which blocks it already has.
Commit protocol. The client sends commit with the block list. The metadata server checks permissions, then checks which hashes are missing in the block index (a lookup per hash, with a bloom filter in front of it) and answers need_blocks. The client uploads those blocks in parallel (4 to 8 connections) to block servers; each block is written, verified by hash and made durable before the answer. Then the client repeats the commit. The server, in one transaction on the namespace's shard, verifies that parent_rev equals the current head revision of that path (optimistic concurrency control), appends a journal row with the next cursor, and updates the head table. The file becomes visible to others only at this atomic step, and never as a half-written file: blocks first, metadata last.
Notification. After the commit, the metadata service publishes "namespace N is now at cursor C" to a publish-subscribe system. The notification servers hold long-lived connections from clients, keyed by namespace; each server subscribes to the namespaces of its connected clients, and pushes a tiny "check now" message. The client then calls list_changes from its cursor, receives the entries in order, downloads the blocks it does not have (from its local block cache or from the block servers), writes a temporary file, and renames it in place, which is atomic on a local file system.
Reconciliation. The core of the client is a loop that compares three states: what the remote journal says (remote tree), what the local disk looks like (local tree), and what was last in sync (synced tree). Every difference between the trees is turned into operations (upload, download, rename, delete) that bring the local and remote trees to the same state, as in the reconciliation loop pattern of cluster controllers. Dropbox described a design of this kind when it rewrote its sync engine (called Nucleus, written in Rust) in 2019 and 2020. The synced tree makes it possible to know the intent: if a file is in the synced tree and missing locally, the user deleted it; if it is missing from the synced tree and remote, it is new and must be downloaded.
Offline work and conflicts. A device that was offline for 3 days comes back with local edits and a cursor. It first pulls all changes. For a file edited on both sides, its commit has a parent_rev that is no longer the head, so the server rejects it. The client then renames its version to "report (Alice's conflicted copy 2026-10-24).docx" and commits it as a new file. Both versions survive, and the user decides. For a delete on one side and an edit on the other, the edit wins and the file is restored. The rule is: never lose data silently.
Sharing. A shared folder is a namespace. Each member's root namespace contains a mount entry pointing to it. A member's client subscribes to its root namespace and to each mounted namespace, so changes by any member are in the same ordered journal. Permission checks are made on every commit and read, against the namespace's ACL.

deepdive: Block size and delta sync. Fixed-size blocks are simple but have a weakness: inserting one byte at the start of a file shifts every later byte, so every block changes. Two techniques help. Content-defined chunking splits at positions where a rolling hash of the last 48 bytes matches a pattern (for example the low 22 bits are zero), giving blocks of average 4 MB whose edges move with the content; an insert changes one or two blocks. The rsync algorithm (Tridgell, 1996) goes further: the receiver sends weak rolling checksums (cheap, Adler-style) and strong hashes of its blocks, and the sender slides a window over the new file to find matching regions at any offset, then sends only the differences. The cost is CPU and a round trip, so it is used for large files with small edits. Compressed formats (ZIP, DOCX, which are zip files) defeat all of these: one edit changes the whole compressed stream, so smart clients re-chunk based on the inner structure or accept re-upload.
Deduplication and its dangers. Because a block is named by its SHA-256, an upload of a block that exists is skipped; across users this saves storage and bandwidth. But it leaks information: if my upload completes instantly, someone has the same file. An attacker who knows a file's hash could ask for it and get the content (the "hash as a bearer token" problem). The fix is a proof of possession: the server asks for the hash of a random sub-range or a salted hash of the block, which only someone holding the data can compute. A second danger is hash collision, which for SHA-256 is cryptographically negligible.
Garbage collection. A block may be referenced by many file revisions. Deleting a file does not delete its blocks at once, because versions are kept for 30 days and other files share them. We run a mark-and-sweep over the metadata: collect all referenced hashes (a distributed job over the journal), then delete blocks unreferenced for more than the version window plus a safety margin (7 days). A race exists between an upload of a new reference and the sweep; the grace period closes it, and a block's creation time is never swept inside the grace period.
Ordering and the journal cursor. All changes to a namespace go through one shard and are appended in order in a transaction, so every client sees the same total order of changes for that namespace, and a cursor is a complete description of "what I have seen". This is event sourcing: the journal is the truth; the head table is a cache. Clients can resume from a cursor, and a crash in the middle of a sync only repeats work. The price is that one very hot namespace (a company-wide shared folder with 50,000 members and heavy automation) cannot be split across shards. We rate-limit commits per namespace, batch commits from one device, and give hot namespaces their own dedicated shard.
Rename and move are the hard operations. A move of a folder with 100,000 files should be one metadata operation, not 100,000 journal rows. Paths are therefore not stored in every row; files point to a parent id and the path is computed (or cached), so a folder rename changes one row. Clients must handle remote "move" arriving together with local edits to files inside the folder: the three-tree comparison treats identity (file id) separately from path, and so can re-apply a local edit to the new location.
Correctness testing. Sync is an infamous source of data-loss bugs: two events race with the file system, partial writes, power loss in the middle of a rename. Dropbox has described building Nucleus so that it can run under a deterministic, randomised test harness: all inputs (file system events, network responses, clock) come from a controlled scheduler, so millions of randomised runs with injected faults replay exactly. This approach is called deterministic simulation testing. The invariants to check are: never lose a user's data, converge to the same state on all devices, and never upload a partial file.
Large files and bandwidth. A 100 GB file is uploaded as 25,000 blocks in parallel streams with resumable state in the local database; a crash resumes with the blocks not yet acknowledged. To protect the user's network, the client throttles and prioritises small files and metadata first (a "recent small files" lane), so a big video upload does not block a 20 KB note.
tradeoffs: Content-addressed immutable blocks versus mutable files. Choose content-addressed blocks (our design) when edits are small relative to files, many users store the same content and you want idempotent uploads and simple caching (an immutable block can be cached forever). The cost is garbage collection, a hash lookup per block, and no in-place update. Choose a plain object per file (for example a simple S3 key with versioning) when files are small, the product is not synchronised across devices and complexity must stay low.
Fixed-size versus content-defined chunking. Choose fixed blocks (4 MB) when files are mostly appended or modified in place (databases, VM disks, photos) and CPU on the client is limited. Choose content-defined chunking when users insert text into documents or logs and bandwidth is expensive (mobile, large files); the cost is about 2x to 3x client CPU for the rolling hash and more complex code. Block size is a trade between metadata size (smaller blocks mean more hashes) and dedup granularity.
Strong metadata consistency versus eventual consistency. Choose strong consistency per namespace (sharded SQL with transactions) because path conflicts, renames and permission changes are hard to reason about without a total order, and users notice anomalies. Choose eventual consistency with CRDTs only if you want multi-master offline operation without a central server (local-first apps); the cost is complex semantics for renames and deletes. We use the central journal and pay with a per-namespace write limit of about a few thousand commits per second.
Client-side watching and polling. Choose OS file events plus a startup scan for responsiveness; polling every few seconds costs battery and disk I/O (scanning a million files takes minutes). The scan is still needed as a safety net. A virtual (placeholder) file system, which lists files without downloading them, saves disk but needs OS integration (kernel hooks) and adds failure modes.
Own storage versus a cloud object store. Choose S3 or an equivalent when you have less than a few petabytes: no operations burden. Choose your own storage (Dropbox built Magic Pocket and moved most data from S3 in 2015 and 2016) at hundreds of petabytes, where purpose-built hardware, erasure coding tuned for your access pattern and freedom from egress fees repay the investment. The downside is operating disks, repairs and capacity yourself.
Push notification versus polling. Choose long poll or WebSocket subscriptions; a poll every 30 seconds from 75 million clients would be 2.5 million requests per second. The subscription costs memory for connections but yields near-instant sync, and the message carries no data, so it is safe to lose.
failures: Block server or disk failure: erasure-coded fragments are spread across zones. Reads reconstruct from any k of n fragments, and a repair job rebuilds missing fragments; durability depends on repair time, so repair has priority.
Metadata shard failure: the primary is replaced by a replica with synchronous replication within the region (so no committed change is lost). Commits to that shard fail for a short time; clients retry with backoff and the commit id makes the retry idempotent.
Notification service outage: clients fall back to polling every 60 seconds, so sync still works but with a delay. After reconnect, the cursor guarantees that nothing is missed because notifications are only hints.
Client crash or power loss in the middle of a sync: the client writes downloaded files to temporary names and renames them when complete, keeps its local database in a transaction log, and on restart rescans and reconciles from the three trees. An interrupted upload resumes at the block level.
Corruption: every block has its hash, so a read verifies integrity; background scrubbing reads data and compares to its hash; the client verifies downloaded blocks. A block that fails verification is refetched from another replica or fragment set.
Region failure: metadata is replicated to a second region asynchronously (to protect against loss of a whole region), with a possible loss of the last seconds of commits in a disaster; blocks are erasure coded across three zones and, for premium plans, replicated across regions. On regional failover, a device whose committed change was lost sees its parent_rev as unknown and re-commits it.
Accidental mass deletion or ransomware: the version history keeps files for 30 days, and an account-level "rewind" restores a whole namespace to a point in time by replaying the journal backwards. Detection of a sudden change of thousands of files triggers an alert to the user.
evolution: At 1,000 users, store files as objects in S3 and keep a Postgres table of paths with an updated_at column; clients poll every minute and download changed files fully. At 1 million users, add blocks and hashes, the commit protocol, a journal with cursors and a long-poll service; one sharded MySQL cluster handles metadata. At 1 billion files and beyond, add content-defined chunking for hot file types, your own block storage with erasure coding, shared-namespace sharding with dedicated shards for hot namespaces, a rewritten, simulation-tested sync engine and a team for storage operations and abuse.
followups: How do you upload only the changed part of a large file? || Split the file into blocks, hash each, and ask the server which hashes it lacks. Only new blocks are sent. Fixed 4 MB blocks work for in-place edits; content-defined chunking or rsync-style rolling checksums handle inserts. Compressed container formats limit the gain.
Two people edit the same file offline. What happens? || The second commit carries an out-of-date parent revision, so the server rejects it as a conflict (optimistic concurrency). The client stores its version as a separate "conflicted copy" file. Both versions survive. Never overwrite silently.
How do other devices learn about a change within seconds? || A notification service holds long-lived connections, subscribed per namespace. After a commit, the metadata service publishes the new cursor and the notifier sends a small hint. The client calls list_changes from its cursor. Hints can be lost without harm since the cursor is the truth.
How do you make sure a half-uploaded file is never visible? || Blocks are uploaded and verified first, and the metadata commit is the last step, one atomic transaction. Until the commit exists, no other device sees the file. On the client side, downloads go to a temporary file and are renamed atomically.
How do you delete blocks safely? || Blocks are shared across files, versions and users, so we use mark-and-sweep with a grace period: compute the set of referenced hashes from the journal, delete only unreferenced blocks older than the retention window plus a margin, so a concurrent upload cannot be orphaned.
How do you shard metadata, and what is the hot spot? || Shard by namespace_id, so a folder's journal is totally ordered in one place. A huge shared namespace is a hot shard. Mitigation: batching, rate limits per namespace, a dedicated shard, and moving heavy automation to bulk APIs.
Is cross-user deduplication safe? || It leaks existence of a file and can be abused with a known hash. Require proof of possession (a challenge on a random part of the block), or scope dedup to the account for sensitive tiers. Encryption with a per-account key makes dedup impossible across accounts, a clear trade between privacy and cost.
How would you test the sync client? || Use deterministic simulation: control file system events, network and time from a seeded scheduler, inject crashes and reorderings, and check invariants (convergence, no data loss, no partial files) over millions of runs. Failing seeds replay exactly.

title: Design collaborative editing like Google Docs
category: Web & product
level: Senior / Staff
concepts: crdt, lamport, vectorclocks, leaderelect, fencing, occ, eventsourcing, wal, pubsub, sockets, conshash, partitioning, idempotence, consmodels, coordination, spanner, retries, backpressure, logcompaction, trees
summary: Collaborative editing lets several people type in the same document at the same time and see each other's changes within a fraction of a second, with no locking and no lost text. Everyone's screen must end in exactly the same document, even though edits cross each other on the network. The core problem is concurrency control for text: two users change the same place at once, and the system must merge both edits in a way that keeps each user's intent. There are two families of solutions, operational transformation (OT) with a central server, and conflict-free replicated data types (CRDTs). This design uses OT with a server as the single ordering point, and explains where CRDTs win.
requirements: Functional. Create and open documents. Several users edit text (insert, delete, formatting) at the same time and see changes live. Show other users' cursors and selections (presence). Undo and redo of one's own changes. Version history with restore. Comments and suggestions are attached to ranges of text. Edits made while offline are merged when the connection returns. Access control: owner, editor, commenter, viewer. We exclude spreadsheets and drawings (they use similar ideas with different data types), and import and export.
Non-functional. Latency: the editor's own typing appears at once (local echo, under 16 ms); a remote user sees it in under 200 ms in the same region. Convergence: all replicas end with the same document; this is the main correctness property. Intention preservation: if I type "x" after the word "cat" and you delete "cat", my "x" stays where it makes sense. Durability: no acknowledged edit is lost. Scale: up to 100 simultaneous editors in a document, and thousands of viewers. Availability: a user can keep typing during short network failures.
Assumptions we choose: 100 million daily active users (DAU), 20 minutes of editing per user per day, 10 million documents open at the peak hour, 1.3 editors per open document on average, typing sessions are active 10% of the time, a client batches keystrokes into one operation every 500 ms while typing, an operation is 100 bytes.
estimates: Concurrent editors. At peak, 10M open docs x 1.3 = 13 million connected editors. At any moment 10% are typing: 1.3 million active typists.
Operation rate. 1.3M typists x 2 operations per second (one batch every 500 ms) = 2.6 million operations per second at peak. Each operation goes to the doc's owner, is written to the log, and is sent to the other editors of that document: with 1.3 editors per doc, 0.3 recipients on average, so about 0.8 million outgoing messages per second. In a popular doc with 100 editors, 100 typists produce 200 ops per second and each op fans out to 99 others: 20,000 messages per second for one document. That is the worst case we support.
Daily volume. 100M DAU x 20 min x 60 s = 1.2e11 user-seconds of editing. With 10% of that time typing and 2 ops per second: 1.2e10 x 2 = 2.4e10 = 24 billion operations per day. At 100 bytes: 2.4 TB per day, about 880 TB per year of raw log. With compaction (we replace old log segments with snapshots after 30 days) the long-term store holds much less. Snapshots: 1 billion documents x 50 KB average = 50 TB.
Servers for sessions. Each open document has an in-memory state on one owner server: document text and recent log, about 100 KB. 10M docs x 100 KB = 1 TB of memory. A server with 64 GB RAM can hold 300,000 docs, but CPU and connections limit us earlier: 50,000 open docs and 65,000 connections per server. 13M connections / 65,000 = 200 servers; with headroom for deploys and failure, 300. Operations per server: 2.6M / 300 = about 8,700 per second, which is easy (each transform costs microseconds).
Log write rate. 2.6M ops per second would be too many tiny writes. We batch per document per 50 ms: a doc with typists produces 1 write per 50 ms = 20 writes per second per active doc; active docs are 1.3M typists / 1.3 = 1M docs, but all typing at once is not likely; the number of log appends is about 1M x 2 = 2M per second without batching and about 1M with 50 ms group commit. The log store is a partitioned, replicated store (for example a Spanner-like database, or a Kafka-like log per shard) and handles 1M appends per second across about 500 partitions at 2,000 per second each.
api: WebSocket /v1/docs/{id}/session?rev=<last_known_revision> upgrades to a bidirectional connection. After authentication, the server answers with {snapshot_rev, ops_since_rev[]} or a full snapshot if the client is too far behind.
Client to server message: {type: "op", client_id, seq, base_rev, ops: [retain(n), insert("text", attrs), delete(n)]}. base_rev is the last server revision the client had integrated when it made this edit.
Server to client messages: {type: "ack", seq, rev} for the sender's own op, {type: "op", rev, author, ops} for others' ops (already transformed so they apply to the client's current state), and {type: "presence", user, cursor, selection} (ephemeral).
GET /v1/docs/{id}?rev=N returns the document at revision N (for history and export). GET /v1/docs/{id}/revisions lists named versions and auto-saved points.
POST /v1/docs/{id}/comments with {range anchor, text}. The anchor is stored as two positions that are themselves transformed as the text changes.
POST /v1/docs/{id}/share with {user, role}.
datamodel: Document record: doc_id, title, owner, ACL, latest_snapshot_rev, created_at; in a sharded relational database (or Spanner), key doc_id.
Operation log: key (doc_id, rev) with rev increasing by 1; value {author, client_id, seq, ops (transformed, final form), timestamp}. Partition key doc_id so a document's log is on one partition, ordered by rev, and a range read gives "everything since rev N". Append is conditional on the expected rev (a compare-and-set), which protects against two owners.
Snapshots: key (doc_id, rev), value the full document state in a compact tree form (paragraphs, runs of text with attributes), stored in blob storage with a pointer in the document record. Created every 1,000 ops or 5 minutes, whichever comes first, by a background compactor.
Session routing table: doc_id -> owner server with a lease (in a coordination service), time to live 10 seconds, renewed by the owner.
Presence: not stored; kept in the owner's memory and broadcast.
Dedup table (in the owner memory, rebuilt from the log): (client_id, last seq applied) so retries are idempotent.
design: One owner per document. All editors of a document connect, through any front end, to the same owner server. The router finds the owner in the lease table, or if no owner exists chooses one by consistent hashing on doc_id and acquires the lease. The owner loads the latest snapshot and replays the log after it, then holds the state in memory. The owner is the single point of ordering for that document: it assigns revision numbers 1, 2, 3, ..., which form a total order of all edits, a logical clock for the document. Different documents are independent, so the system scales by adding owner servers and sharding by doc_id.
The client protocol (the Jupiter model). Each client keeps the document and a small state: the last server revision it has integrated, one operation "in flight" (sent, not yet acknowledged) and a buffer of local operations made since. When the user types, the client applies the edit locally at once, and if nothing is in flight it sends the operation; otherwise it appends it to the buffer. This limits the problem to a client talking to a server, never two arbitrary peers.
Transforming. When the server receives an op based on revision b while the current revision is r > b, the op is concurrent with the r - b operations after b. The server transforms the incoming op against each of them, in order, to get an op that applies to revision r; then appends it as revision r+1, acknowledges the sender, and broadcasts it to the others. When a client receives a remote op, it transforms it against its in-flight op and its buffer (and transforms those against the remote op in return), applies the transformed remote op to its document, and continues. The transform function is defined for each pair of operation types; for text, insert versus insert breaks a tie at the same position by client id, and insert versus delete shifts positions.
Persistence. The owner appends the transformed op to the log (batched for up to 50 ms, group commit), waits for a durable quorum write, and only then sends the ack and the broadcast. If the append fails, nothing is acknowledged, and the client resends. The ack carries the revision number. A background process creates snapshots and trims or archives old log segments.
Presence and cursors. Cursor positions are small and frequent (a mouse or caret move can happen 10 times per second). They go through the same connection but are not logged and are rate-limited to a few updates per second per user. A position is transformed with each op so that a cursor stays at the right character, then broadcast. If a message is dropped, the next one replaces it, so no recovery is needed.
Reconnection and offline. When a connection drops, the client keeps editing locally. On reconnect it sends its last integrated revision, receives all operations since, transforms its in-flight and buffered operations against them (the same procedure as online, just with a longer list), and resends. Operations carry (client_id, seq), so if the server already applied the in-flight op before the drop, the retry is recognised and acknowledged without applying it again.

deepdive: Why transformation is needed. Without it, the same pair of concurrent edits applied in different orders gives different texts. In the animation Alice inserts at position 3 and Bob deletes at position 0. If Bob applied Alice's insert at position 3 unchanged to his text "AT", the position is beyond the end, or on the wrong character. The transform function adjusts positions: an insert that comes after a concurrent delete moves left by the deleted length; an insert at the same position as another insert is ordered by a tie-breaker (client id) so that every replica makes the same choice. For the algorithm to converge on all replicas, the transform must satisfy a property (called TP1): applying op A then the transformed B gives the same result as applying B then the transformed A. In a system with a central server and the one-in-flight rule, only TP1 is needed, and that is why Google chose this model: the server's total order removes the need for the much harder TP2, which caused many published peer-to-peer OT algorithms to be wrong.
Data model for rich text. A document is not a string. It is a sequence of paragraphs with runs of text and attributes (bold, link, list level), plus tables and images. An operation is a list of components: retain(n) (skip n characters), insert(text, attributes) and delete(n), plus attribute changes on retained ranges. Transform and compose are defined on these lists, which gives an efficient algorithm that is linear in the sizes of the two operations. Tables and nested structures need tree operations, which are much harder: moving a paragraph into a list item concurrently with an edit inside it is a classic source of bugs, and real systems restrict such operations or serialise them.
CRDTs as the alternative. A CRDT gives every character a unique, immutable identity and defines the order by those identities, so concurrent edits merge on any replica in any order, with no server and no transformation. In RGA and Yjs (YATA), each inserted character records the identity of its left neighbour at insert time; in Logoot-style systems each character gets a position between two others in a dense order. Deletes become tombstones (the character is hidden but its identity stays), so that later references still make sense. The advantages: offline editing for days, peer-to-peer sync, no central ordering service. The costs: metadata per character (a naive implementation can use many times more memory than the text itself; modern ones compress runs of consecutive characters and reduce this a lot), tombstones that grow with edit history, and the difficulty of permission checks and "undo to a past version" without a central authority. Figma wrote that it uses an approach inspired by CRDTs, with a central server that settles order, to avoid some of this cost.
Hot documents. A document that 5,000 people view (a company announcement) cannot send 5,000 sockets from the owner. Viewers connect to relay servers that subscribe once to the owner's broadcast stream through a publish-subscribe system and fan out to their clients. Editors (limited to 100) stay directly on the owner. When too many editors join, the product enforces limits; the owner also applies backpressure by slowing acknowledgements for clients that send too fast.
Ownership, leases and fencing. If an owner crashes or is partitioned, another server can take the lease after the time to live (10 seconds) expires. A slow old owner might still believe it owns the doc and keep appending, producing two histories (split brain). Protection: every append to the log is conditional on the expected revision (compare-and-set); if the new owner has appended revision 100, the old owner's attempt to write revision 100 fails, and it stops. The lease also carries a fencing token that increases with each acquisition, and the log rejects writes with an older token.
Undo. Global undo ("undo the last change in the document") would remove other people's work. Collaborative editors implement local undo: each user's undo reverts only their own last operation, by computing its inverse and transforming that inverse against all operations that came after it. The result is the undo of that user's intent in the current text.
Version history. Because the log is an ordered list of operations, any revision is reproducible from the nearest snapshot plus replay, and a "named version" is just a pointer to a revision. The history viewer groups operations by author and time (for example 10-minute windows). Restoring creates a new revision whose operations bring the text to the old state; the history is never rewritten.
tradeoffs: OT with a central server versus CRDTs. Choose OT with a server when you already need a server (permissions, storage, comments, search), want the smallest client state and wire format, and expect users to be online most of the time. The server's total order makes the algorithm simple. Choose a CRDT when offline editing for long periods matters, when you want local-first behaviour with peer-to-peer or many-server replication, or when the data type is a map or counter where the merge is simple. You pay with metadata and tombstone growth, and harder access control.
Single owner per document versus multi-master replicas. Choose a single owner (our design) because ordering is trivial and a document is a small unit that fits one machine; throughput of one document is limited to tens of thousands of ops per second, far above the need. Choose multi-region active-active editing only when users in different continents co-edit the same doc often and 150 ms of cross-ocean latency is not acceptable; this requires CRDTs or a heavier protocol. Most products pin a document to the owner's region (usually near the creator) and accept the latency.
WebSocket versus long polling or server-sent events. Choose WebSocket for bidirectional low-latency messages; a typist sends 2 messages per second, and the server answers within milliseconds. Choose HTTP long polling as the fallback for restrictive proxies. The price of WebSockets is stateful connections that make deploys and load balancing harder (drain servers slowly).
Operation granularity: per keystroke or batched. Choose batching every 300 to 500 ms for network efficiency (a typist makes 5 keystrokes per second) and less server work, accepting a slightly longer remote latency. Choose per-keystroke sending only for very small teams where 100 ms matters, since it multiplies the load by 2 to 5.
Log only, or log plus snapshots. Choose event sourcing with snapshots: the log is the truth and gives history and audit, the snapshot bounds the load time (a 10-year-old doc with 5 million ops would take minutes to replay). Choose snapshot-only for simple products without history; you lose recovery from bugs and the ability to rebuild derived data.
Server-side transform versus client-side. Transform at the server for ordering (required), and also at the client to integrate remote ops with local pending ones (required). Both sides run the same code, so ship it as one library (in JavaScript or WebAssembly) tested against each other by randomised tests.
failures: Owner server crash: connections drop; clients reconnect through the router to a new owner, which loads the snapshot and replays the log. Acknowledged edits are in the durable log, so nothing acknowledged is lost. Unacknowledged edits remain in the client's in-flight slot and are resent; the (client_id, seq) dedup prevents double application. Recovery takes a second or two for a normal doc.
Network partition between a client and the server: the client keeps typing locally and shows "offline". On reconnect, it rebases. For a long offline period the transform list is long, so the client may need a full snapshot reload and a three-way merge if its base is older than the retained log.
Log store partition failure: appends fail, so the owner stops acknowledging. Users see "saving" turn into a warning, while local edits stay in the browser's local storage (IndexedDB) until the store returns. The owner does not accept edits it cannot persist, which is a choice of consistency over availability for writes.
Coordination service outage: existing leases cannot be renewed; owners keep serving until the lease expires, and then stop. To lower the effect, leases are long enough (10 s) and the coordination service is deployed over three zones. Documents already open on a healthy owner can usually continue by using the log's conditional append as the safety net, even if lease renewal fails for a short time.
Bad transform bug (divergence). If a bug causes two clients to end in different states, users see different texts. Defences: the client computes a hash of the document every N revisions and sends it with acks; the server compares to its own hash; a mismatch triggers a resync from the server's state (the server is the truth). Divergence is logged with the operation sequence, and this data becomes a regression test.
Flood from one client or a malicious client: validate op size and structure, limit to 50 ops per second per client, and cut the connection when exceeded. ACL changes revoke the session immediately because the owner subscribes to permission events.
Region failure: documents owned in the lost region are reassigned to another region; the log is replicated across regions synchronously for the strongest plans, or asynchronously with a small chance of losing the last second of edits; this choice is a business decision.
evolution: At 1,000 users, a single Node server with all documents in memory, Postgres storing the op log, and a plain OT library is enough. At 1 million users, add a router with consistent hashing on doc_id, leases through etcd or ZooKeeper, snapshots, relay servers for viewers and a presence channel. At 1 billion users, add multi-region placement of documents, a separate comments service, structured data types (tables), search and AI features reading the log, careful capacity planning of owner servers per region, and a test system that runs millions of randomised concurrent-editing simulations before each release.
followups: Two users type at the same position at the same time. What does the system do? || Both inserts are concurrent. The server orders them as revision r and r+1. The second is transformed against the first; for equal positions a tie-break by client id keeps a consistent order on all replicas. Both texts survive; the order is deterministic, not necessarily the one a user expected, but the same for everyone.
Why does a central server make OT simpler? || It gives a total order, so only the property that transforming one op against another gives the same result in both orders (TP1) is needed. With peers and no server, you also need TP2 for three-way concurrency, which has been the source of many incorrect algorithms.
How would you support offline editing for a week? || Pure OT struggles: the transform list is long and old base revisions may be compacted. Options: keep the log long enough, or use a CRDT for the text, or make the client send a three-way merge (base, mine, theirs). A CRDT design handles this naturally at the cost of metadata.
How do you keep cursors correct when text changes? || Store a cursor as an index and transform it through every op exactly as an insert position would be. A cursor after a deleted character moves left. Send presence updates at a limited rate; they are ephemeral.
What happens if two servers both think they own the same document? || Conditional appends on (doc_id, rev) mean only one can write revision N. The loser's append fails, so it stops serving that doc. Leases with fencing tokens reduce the window. The cost is a short unavailability when the owner fails.
How do you load a document with 5 million operations? || Do not replay from the start. Snapshots are made every 1,000 ops, so load the latest snapshot and replay the log after it. Background compaction produces new snapshots and archives old log segments.
How do you implement undo in a collaborative editor? || Undo only the user's own operations: compute the inverse of the op and transform it against all later operations, then apply it as a new operation. Redo works the same way.
How do you test that all replicas converge? || Randomised simulation: many virtual clients generate random ops with random delays, drops and reorderings; at the end compare all documents and a hash. Use seeds so a failure replays exactly. Run it in CI for every change to the transform code.

title: Design a ride-sharing service like Uber
category: Web & product
level: Senior / Staff
concepts: partitioning, conshash, gossip, kafka, redis, pubsub, streamproc, windowing, maxflow, graphsalgo, occ, idempotence, outbox, ratelimit, sockets, cachelayer, consmodels, failuredetect, mysql, queueing, metricspaces, flink
summary: A ride-sharing service connects riders who want a trip with nearby drivers, tracks the car on a map in real time, prices the trip, and takes payment. Three million drivers send their position every second or every few seconds, so the system is dominated by a stream of tiny location updates and by a spatial question asked in real time: which free drivers are close to this rider, by road time, not by straight line? The hard parts are the geospatial index, matching riders to drivers without double booking, surge pricing from live supply and demand, and keeping a trip correct when phones lose signal.
requirements: Functional. A rider enters a destination and sees a price estimate and arrival times for each ride type. The rider requests a ride; the system finds a nearby available driver and offers the trip; the driver accepts or declines (with a timeout). Both see each other's position live. The trip goes through states: requested, driver assigned, driver arrived, in progress, completed. At the end the fare is computed and paid; both rate each other. Riders and drivers can cancel (with rules). We exclude ride pooling, scheduled rides, food delivery, driver onboarding and fraud systems.
Non-functional. Match latency: a driver is offered within 2 seconds of the request at p95. Location freshness: positions shown to riders are under 5 seconds old. Availability: matching must work during partial failures; a trip in progress must never be lost, since the rider is in the car. Consistency: a driver is never assigned to two trips; a trip is charged exactly once. Scale: a few hundred requests per second but more than a million location updates per second. Fairness and cost: keep the pickup time low for riders and idle time low for drivers.
Assumptions we choose: 20 million trips per day, average trip 20 minutes, 3 million drivers online at the peak hour, a location update every 4 seconds per driver (every second during a trip), 100 bytes per update, 100 cities with very uneven size, peak is 3x the daily average.
estimates: Trip requests. 20e6 / 86,400 = 231 requests per second on average, about 700 per second at peak. A single huge city may receive 50 per second.
Concurrent trips. Little's law: concurrent trips = arrival rate x duration = 231/s x 1,200 s = 278,000 on average, about 830,000 at the peak (3x). Each concurrent trip has a rider app and a driver app connected.
Driver location updates. At the peak 3,000,000 drivers are online. 830,000 of them are on a trip and send one update per second; the other 2,170,000 are idle and send one every 4 seconds. Total: 830,000 + 2,170,000 / 4 = 830,000 + 542,500 = about 1.37 million updates per second. At 100 bytes that is 137 MB/s of ingest. Over a day the average is about half of the peak, so about 6 TB per day. We keep 7 days hot for disputes and analytics: 42 TB, then move it to cold storage.
Rider-facing updates. Each trip forwards the driver's position to the rider: 830,000 trips x 1 per second = 830,000 messages per second at peak sent through persistent connections. Riders waiting for a match see the nearby cars (the map "ghost cars"): 1 million idle app opens x 1 refresh per 5 seconds = 200,000 queries per second against the location index (served from a cache that is 5 seconds old).
Location index size. 3,000,000 drivers x 64 bytes (id, lat, lon, heading, status, timestamp, cell) = 192 MB. It is tiny, so the write load, not the size, drives sharding. A node with an in-memory index handles about 100,000 updates per second, so 1.37 million per second needs 14 shards; we plan 40 for headroom and city skew.
Matching routing load. Each request evaluates the 10 to 20 closest candidates with road-network ETA. 700 per second x 20 = 14,000 routing queries per second. A route query with contraction hierarchies takes about 0.1 to 1 ms, so a dozen cores suffice; the system uses far more for the many ETA estimates on the map screen (every rider sees ETAs for several ride types): 200,000 x 3 = 600,000 estimates per second, which are answered from a precomputed ETA grid and a cache rather than full routing.
Storage for trips. 20e6 trips per day x 2 KB metadata = 40 GB per day, 14.6 TB per year; the GPS trace per trip is 1,200 points x 50 bytes = 60 KB, so 20e6 x 60 KB = 1.2 TB per day, 438 TB per year, kept in object storage in compressed form for audit.
api: POST /v1/rides/estimate with {pickup, dropoff} returns {options: [{type, eta_pickup_s, fare_range, surge_multiplier, quote_id}]}. The quote_id locks the price for 5 minutes.
POST /v1/rides with {quote_id, pickup, dropoff, payment_method} and an Idempotency-Key header. Returns {trip_id, state: "matching"}. A retry with the same key returns the same trip.
POST /v1/drivers/location with {driver_id, lat, lon, heading, speed, ts, accuracy} sent every 4 seconds (or over a WebSocket). It is fire-and-forget, with no response beyond a status code. The server ignores updates older than the last one.

datamodel: Driver location index: in memory, per shard. Key: geo cell id (hexagon at resolution 8, about 0.74 km2 each, from Uber's H3 system, or S2 cells), value: set of driver ids with last known position and state (available, offered, on_trip). A second map driver_id -> (cell, position, timestamp) allows O(1) updates and moves between cells. Shard key: the cell id at a coarser level (resolution 4, about 1,700 km2), so a city is covered by a few shards and neighbouring cells are mostly on the same shard.
Driver state: key driver_id, value {status, current_trip, offer_id, version}. The authoritative owner is the dispatch shard that owns the driver (by consistent hashing of driver_id); the version field supports compare-and-set when reserving a driver.
Trip: key trip_id (time-sortable), partitioned by trip_id in a sharded SQL store (MySQL-style, which gives transactions for state transitions); fields rider_id, driver_id, state, pickup, dropoff, quote_id, fare_estimate, timestamps for each state, payment_id. Secondary tables by rider_id and driver_id for history.
Trip state events: an append-only log (Kafka topic keyed by trip_id) of every transition, which feeds payments, notifications, analytics and fraud systems.
GPS traces: key (trip_id, seq), value (lat, lon, ts) in a wide-column or object store, written in batches from the Kafka location topic.
Demand and supply counters per cell and minute: key (cell, minute), value (requests, available drivers), in a fast key-value store, maintained by a stream job, used for surge pricing and for the ETA grid.
Road graph: nodes and edges with speed profiles by time of day and live traffic factors, loaded in memory on routing servers (a city graph has 1 to 20 million edges).
design: Location ingestion. Driver apps send updates to a regional gateway over persistent connections. The gateway applies rate limits, checks timestamps, and forwards each update to the dispatch shard that owns the driver's cell. The shard updates the in-memory index (remove from the old cell, add to the new one if the cell changed) and publishes the update to a Kafka topic for history, trip tracking and analytics. The write path does not touch a database. If an update is lost, the next one arrives 4 seconds later, so we choose speed over durability for locations.
Requesting a ride. The rider app asks for estimates; the pricing service calls the ETA service (nearest available drivers per product type from the index, road-time ETAs from the routing service) and the surge service, and returns a quote. When the rider confirms, the trip service creates the trip in state "requested" in the database (idempotent by the idempotency key), publishes the event, and calls the dispatch service.
Matching. The dispatch shard for the pickup location gets the request. It finds candidate drivers: take the pickup's cell and ask for drivers in rings of neighbouring cells (a k-ring: the cell itself, then the six neighbours, then the next ring) until it has about 20 available drivers or has reached 5 km. It filters by product type, vehicle, driver rating rules and whether the driver is heading in a bad direction. For the best 10 to 20 by straight-line distance, it calls routing for the road ETA to the pickup. It then chooses a driver. The simplest rule: nearest ETA first. A better rule: collect requests for a short window (for example 2 seconds) and solve a bipartite matching that minimises the total pickup time across all requests and drivers in the area; this is a min-cost assignment problem (Hungarian algorithm or a min-cost flow). A greedy choice for one rider can make the next rider wait, while a batch assignment lowers the sum of waiting times by 5 to 10% in dense areas.
Offer and accept. The shard reserves the chosen driver: it changes the driver's state from available to offered with a compare-and-set on the version and an offer timeout of 15 seconds. If the reservation fails (another request took the driver), it picks the next candidate. It sends the offer to the driver app through a push channel (the live connection, with a push notification as a backup). The driver accepts or declines. On accept, the trip row moves from requested to assigned in a database transaction with the driver_id, and the driver's state becomes on_trip. On decline or timeout, the driver returns to available (with a cooldown) and the shard offers the trip to the next candidate. After N failed offers (for example 5), the search radius grows and the rider sees "still looking".
During the trip. The driver app sends location every second. The gateway forwards it to the trip's channel in a publish-subscribe system; the rider's connection (kept by a gateway server) is subscribed to the trip channel and receives updates. The trip service moves the state through arrived, started and ended on the driver's events. ETA is recalculated every 10 seconds using the road graph and live traffic.
Completion and payment. When the driver ends the trip, the trip service computes the fare from the quote and the GPS trace (distance, time, tolls), writes state "completed" and the outbox row in the same transaction. A relay publishes "trip.completed" to Kafka; the payment service consumes it, charges the rider's payment method with an idempotency key equal to the trip id, and pays the driver's balance. If the charge fails, it retries with backoff and falls back to a secondary card. Receipts and ratings follow.
Surge pricing. A stream job over the request and driver-status topics computes, per cell and per minute with a sliding window of 5 minutes, the ratio of open requests to available drivers. The multiplier is a smoothed function of that ratio (with caps and a slow decay so prices do not jump), averaged with neighbouring cells to avoid sharp borders. The multiplier is part of the quote, so the rider confirms the price before the trip.

deepdive: The geospatial index. Latitude and longitude are two numbers, and a B-tree on one of them cannot answer "within 2 km" well. We want a one-dimensional key that keeps nearby places close. Options: a geohash (interleave the bits of lat and lon, then base32), a quadtree, S2 (cells on a cube projected on the sphere, with a Hilbert curve order), or H3 (hexagons). Hexagons have a useful property: all six neighbours are at the same distance from the centre, so a ring of radius k has no unequal diagonal neighbours, and "within k cells" approximates a circle better than squares do. A driver belongs to one cell; moving drivers change cells every few updates, and the cost is two hash map operations. A query becomes: compute the rider's cell, then the cells in k-ring(k), then union the driver sets of those cells. With res-8 cells of 0.74 km2 and a k of 3 the area is about 37 cells, about 27 km2 in total, and a city centre has 10 to 100 drivers per cell at the peak.
Straight-line distance lies. A driver across a river or on the other side of a divided road is 100 m away but 15 minutes by road. So the straight-line step only produces candidates; the decision uses road-network ETA. For the shortest path on a road graph with 10 million edges, Dijkstra takes tens of milliseconds, too slow for 14,000 queries per second plus many ETA estimates. Contraction hierarchies precompute shortcut edges by contracting less important nodes, which makes a query visit only about a few hundred nodes and take well under a millisecond. Live traffic changes edge weights; the hierarchy uses customisable weights so that new speed data are applied without redoing the whole preprocessing. For the many map-screen ETAs we use a coarse grid: precomputed cell-to-cell times updated every minute.
Sharding and hot cities. Dispatch state is partitioned geographically: a driver's location, state and the requests near it live on the same shard, so matching needs no cross-node calls. The shards form a hash ring with consistent hashing (membership is maintained with a gossip protocol, as Uber described with its Ringpop library); when a node fails or joins, only its range moves. A big city has uneven density: a stadium event moves 20,000 requests into a few cells. We use a finer partition key for dense areas (the ring operates on cells at resolution 5 or 6) and add shards dynamically. Requests near the shard border read neighbouring cells on another shard through a cross-shard call, which is rare if shards are at least 50 km wide.
No double booking. The most important invariant: a driver gets at most one active offer or trip. All state changes of a driver go through its owner shard with a version number, as optimistic concurrency control: reserve(driver, expected_version) succeeds only if the version has not changed. The owner is single-threaded per driver (an actor or a partition), which removes races. The trip row is a second source of truth, and the transition requested to assigned happens in a database transaction that includes the driver_id; a unique constraint "one active trip per driver" in the trip database catches any bug in the first layer.
Accuracy of locations. GPS has errors of 5 to 20 m, drops in tunnels and jumps between buildings. Raw points are smoothed with a filter and snapped to the road network (map matching) before use in ETA and fare. On the phone, update frequency adapts: 4 s idle, 1 s in a trip, slower when the battery is low or the car is still. Out-of-order updates are discarded by timestamp (last-write-wins by the device clock, with a server receive time as a check).
Realtime to the rider. 830,000 trips with a position per second is a large fan-out but each message has one recipient. The trip channel maps to one connection server. For rider apps that cannot keep a socket (background), we send push notifications for state changes only (driver assigned, arrived), not positions.
Cancellations and no-shows. Real trips are messy: the rider cancels after assignment; the driver does not move; the driver goes offline. Timers in the trip service (a driver must start moving in 2 minutes; a rider has 5 minutes after arrival) trigger transitions. Timers are stored durably (a delayed queue), not in memory, so a restart does not lose them. Every transition is validated against the allowed state machine, so late or duplicate events are ignored.
tradeoffs: Nearest driver (greedy) versus batched global matching. Choose greedy when latency matters more than efficiency, supply is thin (matching one request at a time is nearly optimal), or the city is small. Choose batching in a window of 1 to 5 seconds in dense markets where many requests and drivers are present together; the matching improves total wait time but adds up to the window to every match and needs an assignment solver. The window length is a tuning knob; adaptive windows (shorter at night) are common.
Hexagons (H3), S2 cells, geohash or quadtree. Choose H3 when you do many neighbourhood queries and aggregations by area (surge, supply and demand heat maps), because of the equal-distance neighbours. Choose S2 when you need covering regions with arbitrary shapes at multiple levels and a stable Hilbert order for range scans in a database. Choose geohash when you want to index in a general key-value store or SQL with prefix queries and simplicity; the cost is edge effects and unequal cell shapes. Choose a dynamic quadtree when density varies by 1000x within a region (cities versus deserts), since the tree splits only where it is crowded.
In-memory index versus a database with geo support. Choose in-memory sharded state (our design) for the live location data at about 1.4 million writes per second where reads need 1 ms and data can be rebuilt in seconds from the next updates. Choose Redis GEO commands or PostGIS for a smaller scale (up to about 50,000 updates per second per node) since they are quick to build. Do not put live locations in a durable relational database; use it for trips and money.
Push versus poll for rider tracking. Choose WebSocket or MQTT-like persistent connections for in-trip tracking: one message per second per rider, 830,000 messages per second, small. Choose polling every 5 seconds only for the idle map where staleness is fine and a cache serves all riders in a cell from one shared snapshot.
Strong consistency for trips versus eventual for locations. Choose transactional storage for trips, payments and driver reservation, where a wrong answer costs money or safety, and accept eventual consistency and loss of some updates for locations. This split is the main design principle.
failures: A dispatch shard dies: the hash ring detects the failure through heartbeats and gossip (a few seconds) and a neighbouring node takes the range. Its in-memory index is empty, but it fills within 4 seconds from the next driver updates. Offers that were in flight time out and are retried; the trip database still has the committed states, so assigned trips are not affected, and the new owner reads on_trip drivers from the trip store at start.
Driver phone loses connection mid-trip: the app buffers GPS points and uploads on reconnect; the rider sees the last position with "reconnecting". The fare uses the buffered trace, and if it is missing, it falls back to the route estimate. The trip does not end by itself; a long silence triggers a safety check.
Trip database shard failure: replicas promote; writes to the shard pause for seconds. Dispatch continues for existing trips from memory and queues state events in Kafka. New requests for riders on that shard fail fast with a retry hint. Because the trip row is only written at a few moments (request, assign, start, end), the load is low (hundreds of writes per second), so the database is not the first bottleneck.
Payment provider outage: the trip completes anyway; the payment is retried for hours with backoff by the payment service using the idempotency key; the rider is charged once. Drivers are paid from a ledger independent of the card charge.
Region failure: each city is assigned to a primary region with a warm standby in another. Failover moves the city's shards; drivers and riders reconnect; trips in progress are recovered from the replicated trip database and drivers' fresh updates. We accept a gap of a few seconds.
evolution: At 1,000 users, a single server with Postgres and PostGIS (a GiST index on location), polling every 5 seconds, is enough: "SELECT drivers WHERE ST_DWithin(...) ORDER BY distance LIMIT 10". At 1 million users, move live locations to Redis (GEOADD, GEOSEARCH) or an in-memory service, keep trips in SQL, and add WebSockets for tracking and a push-notification fallback. At 1 billion users, you need cell-sharded dispatch on a hash ring, contraction-hierarchy routing with live traffic, batched matching, a stream platform for surge and forecasting, an ETA grid, multi-region deployments per city, and a payments ledger with strong audit.
followups: How do you find the nearest drivers quickly? || Index drivers by hexagonal (or S2) cell in memory. Compute the rider's cell, expand rings of neighbouring cells until enough drivers are found, filter by status and product, then rank the best few by road ETA from the routing service.
How do you prevent assigning one driver to two riders? || The driver's state lives on one owner shard and changes only through compare-and-set on a version. Offers have timeouts. The trip database has a unique constraint for one active trip per driver as a second line of defence.
Why not store driver locations in a SQL database? || 1.4 million writes per second of data that is stale after 4 seconds do not need durability or transactions. An in-memory sharded index handles the rate at a tiny cost. SQL is kept for trips and payments.
How is surge pricing computed, and how do you avoid wild swings? || A stream job computes requests divided by available drivers per cell over a sliding window. Smooth over time and across neighbouring cells, cap the multiplier and its rate of change, and lock the price in the quote.
How do you make payments exactly once? || Use an outbox row written with the trip completion, a relay to Kafka, and a payment consumer that uses the trip id as an idempotency key with the payment provider. Retries are safe; the ledger records one entry per trip.
How would you scale to a new city with 10x the density of your biggest? || Shard finer (smaller cells as the ring key), batch matching with a narrower window per area, scale routing servers, and cache ETAs per cell pair. Cross-shard queries at borders must stay rare. Load-test with synthetic traffic from the busiest hours.
What happens when GPS is wrong or the driver is in a tunnel? || Snap to the road graph with map matching, drop points with low accuracy or impossible speed, rely on the last good point with a growing uncertainty, and buffer the trace on the device. Fare uses the corrected trace.

category: Web & product
level: Senior / Staff

summary: A nearby-places service answers "good coffee shops within 2 km of me, open now, under $$" for 100 million users. The data is 200 million businesses that change slowly, and the load is read-heavy: about 17,000 searches per second at peak. The hard part is the spatial question: a plain database index on latitude or longitude cannot find points within a radius efficiently, so we need a structure that maps two-dimensional space to something an index can use (geohash, quadtree, S2/H3 cells, or an R-tree). Around it we add filters, ranking by distance and quality, and a cache that uses the fact that many users stand close together.
requirements: Functional. Search businesses near a point (the user's location or a typed place) within a radius, optionally by text ("ramen"), category, price level, minimum rating and "open now". Sort by distance, rating or a relevance score. Show a business page with address, hours, photos and reviews. Business owners add and edit businesses; users add reviews and photos. New and changed businesses appear in search within 10 minutes. Pagination. We exclude check-ins, reservations, ads and the map tile service.
Non-functional. Latency: p99 under 200 ms for a search including ranking and fetching the page of results. Availability: 99.99% for reads; a stale index is much better than no answer. Read-heavy: about 5,000 reads for each write. Accuracy: results must be inside the radius, and a business 1.9 km away must not be missed because it lies in the next grid cell. Cost: the whole search index should fit in memory of a few machines, so we favour simplicity.
Assumptions we choose: 200 million businesses worldwide, 100 million daily active users (DAU), 5 searches per DAU per day, 100,000 business adds or edits per day, 20 million new reviews per month, a peak of 3x the average, and a skewed distribution: the top 100 metropolitan areas hold 40% of the businesses.
estimates: Search rate. 100e6 x 5 = 500 million searches per day. 500e6 / 86,400 = about 5,800 per second on average, 17,400 per second at peak (3x). Business page views are 3x searches, about 52,000 per second at peak, and are mostly cache hits.
Search record size. For ranking and filtering we keep in the index: business id (8 bytes), latitude and longitude (2 x 8 = 16 bytes), category ids (8 bytes), price level and flags (4 bytes), rating and review count (8 bytes), weekly opening hours as a compact bit pattern in 15-minute slots: 7 x 96 bits = 84 bytes, geo cell id (8 bytes), name tokens (about 50 bytes). Total about 200 bytes. 200e6 x 200 B = 40 GB. This fits in the RAM of one 128 GB server with room to spare.
Full business records. 200e6 x 2 KB (name, address, description, phone, attributes, links) = 400 GB in the primary database, plus photos in object storage: 200e6 x 10 photos x 300 KB = 600 TB, served from a CDN.
Reviews. 20e6 per month x 1 KB = 20 GB per month, 240 GB per year. Small.
Index writes. 100,000 edits per day / 86,400 = 1.2 per second. Writes are negligible; we can rebuild the whole index from the database in a few minutes. This is the big difference from a ride-sharing service, where the location of the object changes every few seconds.
Query cost and servers. A radius query in a dense city touches about 1 to 10 thousand candidates, applies filters and scores about 100 to 500 survivors. About 0.5 ms of CPU per query on one core. A 16-core server then handles 16 / 0.0005 = 32,000 per second in theory; with ranking, networking and overhead we assume 3,000 per second. 17,400 / 3,000 = 6 servers at peak. We deploy 4 servers in each of 3 regions = 12 servers, enough for the failure of a server and for growth.
Cache. If we snap the user's position to a cell of about 600 m (geohash precision 6) and cache results by (cell, category, filters, sort), then users in the same neighbourhood share entries. Assume a hit rate of 50% at peak: the search servers then see 8,700 queries per second. The cache holds the top 100 candidate ids per key, about 800 bytes; 20 million active keys x 800 B = 16 GB.
Geohash arithmetic. At a latitude of about 13 degrees (Bengaluru), one degree of latitude is 111 km and one degree of longitude is 111.32 x cos(13 degrees) = 108.5 km. A geohash of length 5 is a cell of about 4.9 km x 4.9 km; length 6 is 1.2 km x 0.6 km; length 7 is 153 m x 153 m. For a 2 km radius search we use length 5 with the 9 cells (the centre and 8 neighbours), a square area of about 14.7 km x 14.7 km, 216 km2, to cover a circle of 12.6 km2: the candidate set is 17 times larger than needed, so a distance filter follows. Length 6 would need about 5 x 8 = 40 cells of 1.2 km x 0.6 km, an area of about 6 km x 4.8 km = 29 km2, which is much tighter, at the cost of 40 lookups instead of 9.

datamodel: Businesses (the source of truth): relational (MySQL or Postgres), key business_id, fields name, address, lat, lon, geohash (precision 9, indexed), category ids, price, phone, website, hours (JSON or rows), attributes, status, updated_at. Sharded by business_id when it exceeds one primary (at 400 GB it still fits on one large database with replicas, which is simpler; sharding is a later step).
Geo index (read-optimised search copy): built from the database through change data capture (CDC) and held in memory in the search service. Structure: a quadtree or a sorted array of (cell id, business id) at a fixed level, plus columnar arrays for filter fields (category, price, rating, hours bitmap, status) indexed by an internal integer id. A bitmap per category and per price level makes filters fast: the candidate set is intersected with the bitmap before scoring.
Reviews: key (business_id, review_id) in a table or wide-column store, partitioned by business_id so that a business's reviews are in one place. Aggregates (count, sum of ratings, Bayesian score) are kept on the business record, updated by a stream job.
Photos: object storage keyed by photo id, with a table (business_id, photo_id, rank, caption).
Search result cache: key (geohash6, category, filter hash, sort), value list of top candidate ids with scores, time to live 60 seconds.
design: Data flow. Owners and users write through the business service to the relational database. Change data capture (a connector such as Debezium reading the MySQL binary log) publishes each change to Kafka. An index builder consumes the stream and updates the in-memory index of each search server (or writes an incremental file that servers load). Because writes are 1 per second, each server can apply changes directly, and a full rebuild from a database snapshot runs nightly to remove drift. The system is a classic separation of the write store from a read-optimised view.
Search path. The client sends the search to the API gateway. The search service snaps the location to a cell and checks the result cache. On a miss: (1) it picks the cell precision from the radius, (2) fetches the businesses in the centre cell and its 8 neighbours from the geo index, (3) applies filters with bitmaps and the hours check ("open now" uses the local time of the business, from its timezone, and the 15-minute slot bit), (4) computes the exact distance with the haversine formula for each candidate and drops those outside the radius, (5) scores the rest, (6) keeps the top 100, stores them in the cache, and returns the first 20. A second call to the business service (with its own cache) hydrates names, thumbnails and snippets for the 20 results. Photo bytes come from the CDN.
Choosing the structure. Our default is a quadtree or a geohash/S2 cell index held in memory because writes are rare and the index is only 40 GB. In the quadtree, the root covers the whole world; each node splits into four children when it holds more than 100 businesses. Dense Manhattan splits down to cells of about 50 m, while the Sahara stays one big cell. A query descends to the leaf for the point, collects businesses, and if too few are within the radius, visits neighbouring leaves in order of distance until the radius is covered. With 200M businesses and a leaf capacity of 100, there are about 2 to 4 million leaves and about 1 million internal nodes, which is a few GB of memory. Building takes minutes: 200M inserts x 1 microsecond x depth 20 is about 1 hour single-threaded, parallelised by region to a few minutes.
Ranking. The score combines distance (decays smoothly; people accept 300 m for coffee and 5 km for a dentist, so the decay depends on the category), quality (the Bayesian average rating, see below), popularity (recent review and click volume), text match (BM25 on the name and categories when q is present), and personalisation (past clicks, saved places). A first pass uses cheap features over all candidates; a learned model re-ranks the top 100. We evaluate by click-through and "call or direction" actions.
Bayesian rating. A place with a single 5-star review should not outrank one with 4.7 stars from 800 reviews. We shrink each business rating toward the global mean m with a prior weight C: score = (C x m + sum of ratings) / (C + n). With m = 3.8 and C = 10: one 5-star review gives (38 + 5) / 11 = 3.9; 800 reviews at 4.7 give (38 + 3,760) / 810 = 4.69. The formula is a simple use of Bayesian inference and removes most of the noise from low counts.
Pagination. Results are produced once and cached per query for a few minutes; the cursor refers to the cached list and an offset, so page 2 is consistent with page 1 even if ratings change in between.

deepdive: Why not a SQL index on latitude and longitude. A query WHERE lat BETWEEN a AND b AND lon BETWEEN c AND d can use one B-tree index for one column; it then scans every row in that latitude band (a strip around the whole world: 100 km tall, 40,000 km long), and filters on longitude. A composite index (lat, lon) helps the first column only. We need a structure where a two-dimensional neighbourhood is one or a few ranges of a one-dimensional key. A space-filling curve gives that: the geohash interleaves the bits of latitude and longitude (Z-order), so that a shared prefix means a shared rectangle, and a B-tree prefix scan on the geohash column returns a cell. The S2 library uses a Hilbert curve on cube faces, which has better locality (fewer jumps) than the Z-order curve. The R-tree (PostGIS GiST index, or the BKD tree in Lucene) builds a tree of bounding boxes that adapts to density.
The boundary problem. Two places 10 m apart may sit on opposite sides of a cell boundary and have totally different geohash prefixes (and near the 0 degree meridian or the equator the prefixes differ in the first character). That is why we always query the centre cell and its 8 neighbours. The cell side must be at least the radius, so that the 9-cell block covers the circle wherever the user stands inside the centre cell: with length 5 (sides of about 4.9 km) a radius of up to 4.9 km is safe. For a larger radius, use a coarser precision or search the cells that intersect the circle (a covering). Near the poles and the date line neighbour computation needs special cases, handled by libraries.
Density skew. Density follows a power law: a fixed precision of 6 gives cells with 3 businesses in the suburbs and 3,000 in a central business district. A fixed grid forces a compromise. The quadtree adapts by splitting dense cells, and a hybrid is common: use geohash/S2 prefixes for sharding and caching, and a hierarchical structure inside. In the search service, we cap the candidate count (for example 5,000) and if the cell has more, descend to a finer level and take the cells nearest to the user first.
Partitioning and replication. At 40 GB the geo index is replicated in full on every search node instead of being partitioned. This avoids scatter-gather (querying all shards and merging) and the cross-shard boundary problem. Scaling is done by adding replicas. If the data grew to 4 TB (more attributes, many more entities) we would partition by region, mapping a top-level cell (geohash length 2 or 3, with splitting of very dense cells across nodes) to a shard, and route queries to the shards that cover the 9 cells, usually one, sometimes two at borders, and merge the results.
Opening hours. "Open now" is a filter that depends on time and time zone. Storing hours as a bit pattern in 15-minute slots for the week (672 bits) makes the check one bit lookup after computing the local slot index. Holidays and exceptions are applied as an overlay for dates near today, which the index builder refreshes every hour. A bitmap index on "open at slot s" is possible but costs 672 bitmaps; the per-record bit check is cheaper at this scale.
Cache design. The cache key uses a snapped location, so two users 50 m apart share the entry. The cached value is a list of candidates with a score computed without personalisation; the user's exact distance is recomputed from the exact position when the page is hydrated, and a light personalised re-ranking is done on the top 100. The time to live is 60 seconds for freshness, but the business open/closed state is applied after the cache because it changes with time of day.
Consistency of writes. A new business should appear within 10 minutes. The path (database, CDC, Kafka, index builder) usually takes seconds. Edits that must be removed fast (a closed or reported business) set a status flag and a fast path pushes the flag directly to all search nodes; the flag is checked in the filter step. Moderation delays new businesses, but deletions apply at once.
Abuse and quality. Fake reviews and spam listings are common. A review is not counted before a quality filter runs; ratings are aggregated from accepted reviews only, and the Bayesian prior reduces the effect of a small number of fake reviews. Rate limits per user and per IP slow the attack; moderation signals feed the ranking.
tradeoffs: Geohash, quadtree, S2/H3 or R-tree. Choose geohash when you must use a general store (SQL, Redis, DynamoDB) and want the simplest solution: a prefix query on an indexed column; accept edge cases and uneven cell sizes. Choose a quadtree when density varies a lot and the index is in memory and rebuilt from the database; it is easy to write and gives the nearest-neighbour search naturally, but it is harder to update on disk and to share between processes. Choose S2 or H3 when you also need regions, hierarchy and area aggregations (heat maps, neighbourhood stats), or very accurate covering of circles. Choose an R-tree (PostGIS, Lucene BKD) when you have complex shapes (polygons, delivery zones) or mixed text and geo queries in an existing search engine.
Custom in-memory service versus Elasticsearch/OpenSearch. Choose Elasticsearch (geo_point and geo_distance queries, filters, text relevance, aggregations) when you need rich text and faceted search, a small team and operations tools, and 20 to 50 ms latency is acceptable; a 200-million-document index in 10 to 20 shards is normal. Choose a custom in-memory service when the data is small (40 GB), the filters are fixed, and you want 1 to 5 ms latency and complete control of ranking. The custom path costs development and on-call time.
Replicate everything versus shard the index. Replicate when the index fits in memory and read QPS is the only problem: simpler, faster, no merge. Shard when the data exceeds one machine, or when you need different regions to hold different data for latency or law. Sharding by geographic region keeps most queries on one shard (unlike sharding by business id, which touches all shards and needs a merge).
Precompute results versus compute on request. Precompute (and cache) lists for popular cells and categories when queries repeat (dense cities, common categories) and 60 seconds of staleness is fine. Compute on request when filters have too many combinations (price, hours, attributes) and personalisation matters. A mixed approach, caching the unpersonalised candidate list and applying filters and re-ranking on top, is common.
Relational database versus NoSQL for the source of truth. Choose a relational database (MySQL, Postgres) at 400 GB and 1 write per second: transactions, constraints and ad-hoc queries are valuable and the size fits a single primary with replicas. Choose DynamoDB or Cassandra only if you expect the data to be 100x larger or multi-region writes; you lose joins and flexible queries.
Distance sort versus relevance sort. Choose distance sort for a map view (everything within the viewport should be visible) and relevance for lists. The choice changes the retrieval: a map query is a bounding-box query returning up to N points by importance, not a radius query.
failures: A search node dies: the load balancer removes it after failed health checks within seconds; the other replicas carry the load because capacity is planned for N-1 failure. A new node loads the index snapshot (40 GB at 1 GB/s is 40 seconds) from object storage and then applies the change stream from its offset.
Index builder or Kafka failure: the index becomes stale, but search continues. We alert when the index age is over 15 minutes. After recovery, consumers catch up from the saved offset. A nightly full rebuild repairs drift and any lost updates.
Database primary failure: replicas promote in less than a minute; reads are not affected (they use the index and caches); only writes fail temporarily, and the clients show a retry message. A cross-region replica handles a region loss.
Cache failure or stampede: if the cache is down, search nodes absorb the load: 17,400 queries per second against 12 nodes with 36,000 capacity is still within limits. When a popular key expires, many requests may miss at once; we use request coalescing (one computation per key) and jittered time to live.
Bad data: a business with wrong coordinates (0, 0 off the coast of Africa, or swapped lat and lon) pollutes results. Validation rules check country bounds and distance to the address geocode; the index builder rejects invalid records and reports them. A bad index build is blocked by checks on count, size, and sample queries, and old versions are kept for rollback.
Hot area: a major event or disaster makes one area receive a large part of the traffic. The cache absorbs repeated queries; if needed we add replicas, since each is a complete copy.
Region failure: DNS or anycast moves traffic to the next region, which has a full replica of the index; photos come from the CDN. The write path may be unavailable for a short time, which is acceptable for this product.
evolution: At 1,000 businesses, store lat and lon in Postgres and run a bounding-box query with an ordinary index; compute distance in SQL. At 1 million businesses, add a geohash or PostGIS GiST index, Redis for caching and a read replica; the query is still one SQL statement. At 200 million businesses, move search to a dedicated read-optimised service (in-memory index or Elasticsearch) fed by CDC, add the result cache with snapped locations, ranking models, photo CDN, moderation pipelines and regional replicas. Keep the relational database as the source of truth throughout.
followups: Why can't you just index latitude and longitude with a B-tree? || A B-tree orders by one key, so a range on latitude returns a thin band around the whole world, and longitude is filtered row by row. A space-filling curve (geohash, S2) or a tree of bounding boxes (R-tree, quadtree) maps a 2D neighbourhood to a few 1D ranges or tree nodes.
What is the boundary problem with geohash and how do you fix it? || Neighbouring points can have different prefixes. Query the centre cell plus its 8 neighbours, choosing a precision where the cell side is at least the radius. Always compute the true distance afterwards, because the 9-cell block is a larger square than the circle.
How do you handle cities where one cell has 10,000 businesses? || Use adaptive structures: a quadtree that splits dense nodes, or multiple geohash precisions that go finer for dense areas. Cap the candidates per query and take the cells nearest to the user first. Rank within the candidates.
How do you ensure a new business appears in search soon? || Write to the database, capture changes with CDC into Kafka, update the in-memory index on all nodes within seconds. A nightly rebuild corrects drift. For removals, a status flag is pushed quickly and checked at filter time.
How do you sort fairly between a place with one 5-star review and one with 800 reviews at 4.7? || Use a Bayesian average that shrinks each rating toward the global mean in proportion to the number of reviews, for example (C x mean + sum) / (C + n). The one-review place gets about 3.9 and the established place stays at 4.69.
Would you shard this service? How? || Not at first: 40 GB fits in memory and replication solves QPS. If needed, shard by geographic region (top-level geohash or S2 cell), so most queries touch one shard and boundary queries touch two. Avoid sharding by business id because every query would hit every shard.
How is this different from the nearby-drivers problem in ride-sharing? || Businesses are almost static and queried with rich filters, so we use a read-optimised index built from a database, a result cache and replication. Drivers move every few seconds, so the index is in memory with constant updates, sharded by cell, with strict reservation logic for matching.
How would you support a map viewport search? || Query by bounding box, not radius, and return the most important N businesses in the box (clustered by zoom level). Precompute clusters per zoom level and tile, cache them by tile id, and refresh them periodically.
