@@ a2a
== Agent card discovery then task delegation
kind: service-discovery, request-reply
when: An agent must find a partner agent from another team or vendor and hand it a job, without custom glue code.
how: The partner publishes an Agent Card, a JSON file usually at /.well-known/agent-card.json. It lists the agent's skills, its endpoint, the transports it speaks and the auth it needs. The client agent fetches the card first, and picks a skill that matches the job.
The client then sends a message to the endpoint, for example with the SendMessage call over JSON-RPC, gRPC or HTTP+JSON. The server answers with a Task that has an id and a state. The client keeps the task id and uses it for every later call.
The client never sees the partner's prompts, tools or memory. It only sees messages and artifacts. This keeps each side opaque, which is the main reason to use A2A and not a shared library.
used: Multi-vendor agent setups built with Google ADK, LangGraph and other frameworks; the Linux Foundation A2A project lists SDKs for Python, Go, Java, JavaScript and .NET.
avoid: When the partner is only a stateless function; call it as an MCP tool or a plain API instead.
flow:
  Client agent [svc: orchestrator] -> Agent Card URL [store: /.well-known] : GET agent-card.json | The client fetches the card and reads skills, endpoint and auth scheme.
  Client agent -> Partner agent [svc: opaque remote] : SendMessage + token | The client sends a message with a bearer token, as the card required.
  Partner agent -> Client agent : Task t-81, working | The partner replies at once with a task id and the state working.
  Client agent -> Partner agent : GetTask t-81 | The client asks for the state later, using only the task id.
  Partner agent -> Client agent : completed + artifact | The task ends in completed, with a result document as an artifact.
ref: docs | Agent2Agent protocol specification | A2A project, Linux Foundation | https://a2a-protocol.org/latest/

== Long-running task with streaming and push callback
kind: async-request-reply, webhook-callback
when: The partner agent needs minutes or days to finish, and the client cannot hold a connection open that long.
how: Work between agents is often slow: a background check or a booking can take hours. A2A models this as a Task with states such as submitted, working, input-required and completed. The client can watch the task in three ways.
For short jobs it streams: the server sends status and artifact updates over server-sent events on one open connection. For long jobs the client registers a push notification URL. The server then calls that webhook when the state changes, and the client fetches the task for details. Polling with GetTask is the simple fallback.
If the partner needs more data it moves the task to input-required. The client answers with a new message that carries the same task id, and work continues. This is the pattern's main strength over a plain request and response.
used: Agent hand-offs in enterprise workflows such as hiring or travel booking; any pair of A2A clients and servers built with the official SDKs.
avoid: For sub-second calls that return one value; a normal API call is simpler.
flow:
  Hiring agent [svc] -> Check agent [svc: vendor] : SendMessage + webhook url | The hiring agent submits the job and registers a push notification URL.
  Check agent -> Hiring agent : Task t-7 submitted | The server returns the task id at once; the connection closes.
  Check agent -> Hiring agent : input-required | The vendor needs the candidate's consent number, so the task state changes.
  Hiring agent -> Check agent : message with task t-7 | The client answers on the same task id, so the context is kept.
  Check agent ~> Webhook receiver [svc: client side] : task t-7 completed | Hours later the server calls the webhook URL with the new state.
  Webhook receiver -> Check agent : GetTask t-7 | The client fetches the task and reads the result artifact.
ref: docs | Life of a Task | A2A project | https://a2a-protocol.org/latest/topics/life-of-a-task/

== MCP for tools, A2A for peer agents
kind: agent-loop, plugin-arch
when: One agent needs both its own tools and help from specialist agents owned by other teams.
how: The agent keeps two kinds of outside links. Tools and data sources are reached over MCP: they are passive, have clear schemas and return at once. Other agents are reached over A2A: they are active, have their own goals, and may take a long time.
The orchestrator loop picks the link by the job. A SQL query goes to an MCP server. "Find three suitable hotels and hold a room" goes to a hotel agent through A2A. The hotel agent may itself use MCP tools and other A2A agents, so the pattern nests.
Each hop has its own auth and its own audit log. Do not give a remote agent the tools of the caller; give it a task and let it use its own.
used: The A2A documentation presents this split (MCP vertical, A2A horizontal); common in multi-agent platforms from Google Cloud and other vendors.
avoid: When one agent with a few tools is enough; extra agents add latency and cost.
flow:
  User [user] -> Orchestrator agent [svc: LLM loop] : plan a trip | The user states a goal; the orchestrator plans the steps.
  Orchestrator agent -> Calendar MCP server [svc: tool] : tools/call | A simple lookup is a tool call over MCP.
  Calendar MCP server -> Orchestrator agent : free dates | The tool returns a result at once.
  Orchestrator agent -> Hotel agent [svc: remote agent] : SendMessage | A larger goal is handed over as an A2A task.
  Hotel agent -> Booking MCP server [svc: tool] : tools/call | The remote agent uses its own tools; the caller never sees them.
  Hotel agent -> Orchestrator agent : artifact: booking | The hotel agent returns a finished artifact.
ref: docs | A2A and MCP | A2A project | https://a2a-protocol.org/latest/topics/a2a-and-mcp/

@@ feast
== Offline store for training, online store for serving
kind: feature-store, online-offline
when: A model is trained on history but must read the same features in under 10 ms at prediction time.
how: Features are declared once in a repo: entities, feature views and their sources. A materialization job (feast materialize) reads the batch source, such as a warehouse table, and writes the latest value per entity key into the online store, for example Redis or DynamoDB.
For training, the offline store (BigQuery, Snowflake or files) answers get_historical_features. This does a point-in-time join: for every training row it takes the feature value as it was at the row's timestamp, not today's value. This stops label leakage.
At serving time the model service calls get_online_features with entity ids and gets the latest values by key lookup. Both paths use one definition, so training and serving cannot drift in code.
used: Teams using Feast with BigQuery, Snowflake, Redshift, Redis or DynamoDB; common in recommender and fraud systems.
avoid: When there is one model with a few simple features; compute them in the service. Also avoid it when no feature needs sub-second freshness and batch scoring is enough.
flow:
  Feature repo [store: feast apply] -> Registry [db: feature definitions] : apply | The repo defines entities and feature views; apply writes them to the registry.
  Warehouse [lake: BigQuery] -> Feast job [svc: materialize] : read new rows | A scheduled job reads source rows since the last run.
  Feast job -> Online store [cache: Redis] : latest per user id | Only the newest value per entity key is written, so reads are single lookups.
  Training job [svc] -> Warehouse : get_historical_features | The training job joins features as of each label timestamp, which avoids leakage.
  Model service [svc: serving] -> Online store : get_online_features | The service looks up features by user id in a few milliseconds.
ref: docs | Feast architecture | Feast project | https://docs.feast.dev/getting-started/architecture

== Streaming features pushed to the online store
kind: feature-store, event-driven
when: A feature such as "clicks in the last 10 minutes" must be fresh, and a daily batch job is too slow.
how: A stream job (Flink or Spark Structured Streaming) reads events from Kafka and computes the rolling aggregate. It then calls Feast's push API with the new rows. Feast writes them to the online store, and optionally to the offline store as well.
The same feature view serves both the batch source and the push source. A batch job still backfills history, so training data and online values are computed from the same logic when possible. Keep the stream logic and the batch logic equal, or the values will differ.
The cost is one more running system. Streaming jobs need state, checkpoints and monitoring, so only use them for features where minutes matter.
used: Fraud and ads ranking teams that mix Kafka streams with Feast push sources; the Feast documentation describes push sources for this.
avoid: When hourly freshness is fine; schedule a materialize job instead.
flow:
  Click events [log: Kafka] -> Flink job [svc: 10 min window] : click stream | The stream job reads click events as they arrive.
  Flink job -> Feast push API [svc] : push rows | Each window result is pushed as a row with an event timestamp.
  Feast push API -> Online store [cache: Redis] : write latest | The newest aggregate overwrites the old one for that user.
  Feast push API ~> Offline store [lake: Parquet] : append rows | Rows are also kept for later training joins.
  Ranker [svc] -> Online store : get_online_features | The ranker reads a feature that is minutes old, not a day old.
ref: docs | Push source | Feast project | https://docs.feast.dev/reference/data-sources/push

== Feature server behind the model service
kind: feature-store, horizontal-scale
when: Many services in different languages need features, and you do not want each to embed a Feast client.
how: Run the Feast feature server as an HTTP service in front of the online store. Clients send entity ids and feature names as JSON and get values back. The server is stateless, so you run many copies behind a load balancer.
The model service, the batch scorer and a notebook all use the same endpoint. Access control and feature names are in one place. The registry is read from a shared store, so every copy sees the same definitions after feast apply.
Latency is the sum of one network hop and one key lookup, so keep the server in the same region as the online store. Cache the registry in memory and refresh it every few minutes.
used: Feast feature server on Kubernetes, common in teams that serve Python and non-Python callers.
avoid: When one Python service is the only caller; use the SDK in process and skip the hop.
flow:
  Model service [svc: Go] -> Load balancer [svc] : POST get-online-features | A non-Python service sends entity ids over HTTP.
  Load balancer -> Feature server [svc: stateless x3] : route | Any copy can answer, because none holds state.
  Feature server -> Registry [db: S3 or SQL] : read definitions | Copies load feature definitions and cache them.
  Feature server -> Online store [cache: Redis] : lookup by key | The server reads values for the requested ids.
  Feature server -> Model service : feature vector | The service gets values and calls the model.
ref: docs | Python feature server | Feast project | https://docs.feast.dev/reference/feature-servers/python-feature-server

@@ hf
== Hub as model registry with pinned revisions
kind: external-config, immutable-infra
when: Many jobs and services load the same model and must get the same weights, and updates must be controlled.
how: Models, datasets and Spaces live in Git repositories on the Hugging Face Hub. Large files use Git LFS (or Xet storage). Code calls from_pretrained("org/model", revision="<commit sha>"), which downloads the files once and keeps them in a local cache.
Pinning to a commit hash makes the load repeatable, because a branch name like main can move. In production, copy the model once into your own bucket or an internal mirror, so a Hub outage or a deleted repo cannot stop a deploy.
Safetensors files are preferred over pickle files, because loading them cannot run code.
used: Most open-model workflows; teams that mirror Hub models into S3 or an internal artifact store before deploy.
avoid: When the model is private and tiny; a plain object store with versioned paths is enough.
flow:
  Fine-tune job [svc] -> HF Hub [store: Git + LFS] : push model | The training job pushes weights and config as a new commit.
  Release script [svc] -> HF Hub : resolve main to sha | The release step records the exact commit hash in a config file.
  Release script -> Internal mirror [store: S3 bucket] : snapshot_download | The files at that commit are copied to the company bucket.
  Inference pod [svc] -> Internal mirror : from_pretrained(path) | The pod loads the pinned copy; it does not call the public Hub.
  Inference pod -x> HF Hub : blocked in prod | Production has no outbound route to the Hub, so a Hub outage cannot break it.
ref: docs | Hugging Face Hub documentation | Hugging Face | https://huggingface.co/docs/hub/index

== Pretrained model, then fine-tune and serve
kind: online-offline, feedback-loop
when: You need a model for your own task, but you do not have the data or money to train one from scratch.
how: Start from a pretrained checkpoint on the Hub. Load it with Transformers, and use Datasets to read your labeled data. Train with the Trainer or with TRL. For large models use PEFT with LoRA, which trains small adapter matrices (often under 1 percent of the weights) and keeps the base frozen.
Evaluate on a held-out set, then push the model or the adapter back to the Hub. Serving reads the same repo. A LoRA adapter can be merged into the base weights for speed, or loaded at run time so one base model serves many tasks.
The loop repeats as new labeled data arrives: log hard cases in production, label them, train again.
used: Open-model fine-tuning with Transformers, PEFT and TRL; many teams then serve through vLLM or Text Generation Inference.
avoid: When a prompted hosted model already meets the quality target; fine-tuning adds a training and evaluation burden.
flow:
  HF Hub [store: base model] -> Training job [svc: GPU] : load checkpoint | The job downloads the base model and its tokenizer.
  Labeled data [lake: Datasets] -> Training job : stream batches | The data loader reads examples in batches.
  Training job -> Eval job [svc] : LoRA adapter | The adapter is scored on a held-out set.
  Eval job -> HF Hub : push if better | Only a better adapter is pushed as a new version.
  Inference server [svc: vLLM or TGI] -> HF Hub : pull base + adapter | The server loads the base and attaches the adapter.
  Inference server ~> Labeling queue [queue] : low-confidence cases | Hard cases go to people for labels, for the next round.
ref: docs | PEFT documentation | Hugging Face | https://huggingface.co/docs/peft

== Inference endpoint with a dedicated model server
kind: horizontal-scale, continuous-batching
when: An open model must serve many users with steady latency, and calling pipeline() in a web handler is too slow.
how: Do not load a Transformers model inside each web process. Run a model server such as Text Generation Inference (TGI) or vLLM on GPU nodes. It loads the weights once and uses continuous batching and a paged key-value cache to share the GPU among many requests.
An API layer in front handles auth, rate limits and retries, and calls the server over HTTP. Add nodes behind a load balancer when the queue grows. Hugging Face Inference Endpoints runs this setup as a managed service.
Pin the model revision in the server's start command so a new deploy cannot change weights by accident.
used: TGI and vLLM deployments of Hub models; Hugging Face Inference Endpoints.
avoid: For offline scoring of a fixed dataset; run a batch job with the Transformers library instead.
flow:
  App [client] -> API gateway [svc: auth + limits] : chat request | The app sends a request with a user token.
  API gateway -> Model server [svc: TGI + GPU] : /generate | The gateway forwards it to a model server.
  Model server -> GPU batch [model: continuous batch] : join batch | The request joins the running batch at the next step.
  GPU batch -> Model server : stream tokens | Tokens are sent back as soon as they are made.
  Model server -> App : SSE stream | The user sees text appear while the model still decodes.
ref: docs | Text Generation Inference | Hugging Face | https://huggingface.co/docs/text-generation-inference

@@ jax
== Compile once with jit, run on any accelerator
kind: interpreter-compiler, offload-accelerator
when: A numeric function is called many times on arrays, and Python overhead and unfused operations waste the GPU or TPU.
how: JAX traces a pure Python function with abstract values and builds a graph of primitive operations. jax.jit sends this graph to XLA, which fuses operations, plans memory, and emits code for the CPU, GPU or TPU. The compiled program is cached by the input shapes and dtypes.
The first call pays the compile cost, often seconds. Later calls with the same shapes run at once. A new shape triggers a new compile, so pad inputs to a few fixed sizes.
Functions must be pure: no hidden state, no Python side effects inside the traced code. Random numbers use explicit keys, which makes runs repeatable on any device.
used: Google DeepMind and Google research code; libraries built on JAX such as Flax, Optax and Orbax.
avoid: For code with data-dependent Python control flow and changing shapes on every call; it recompiles. Use eager PyTorch or NumPy.
flow:
  Python function [svc: pure] -> Tracer [svc: abstract values] : jit(f)(x) | The first call traces f with shapes and dtypes, not real numbers.
  Tracer -> XLA compiler [svc: fuse + codegen] : jaxpr graph | The graph of primitive operations goes to XLA.
  XLA compiler -> Executable cache [cache: by shape] : compiled program | The program is stored with its input shapes as the key.
  Executable cache -> GPU or TPU [model: device] : run | The compiled code runs on the device.
  Python function -x> XLA compiler : new shape, recompile | A new input shape misses the cache and compiles again.
ref: docs | Just-in-time compilation | JAX documentation | https://docs.jax.dev/en/latest/jit-compilation.html

== SPMD sharding across many devices
kind: data-parallel, model-parallel
when: A model or batch is too big for one device, and you want one program text for 8 or 4,000 chips.
how: You write the program as if for one device. You then place arrays on a mesh of devices, with named axes such as data and model, and give each array a sharding (a PartitionSpec). The XLA compiler splits the program and inserts the needed collective operations such as all-reduce and all-gather.
Data parallelism shards the batch axis and replicates weights. Tensor parallelism shards weight axes. You can combine both on a two-dimensional mesh. Changing the layout means changing the specs, not rewriting the model.
Training on many hosts means every host runs the same Python program, and the runtime joins the devices into one mesh.
used: Large model training on Google TPU pods with JAX frameworks such as MaxText and Flax; the JAX documentation covers sharded computation.
avoid: For small models that fit on one GPU; plain jit is enough.
flow:
  Training script [svc: same on all hosts] -> Device mesh [note: data x model axes] : create mesh | Each host builds the same mesh over all devices.
  Device mesh -> Weights [store: sharded] : PartitionSpec | Weights are split along the model axis, and batches along the data axis.
  Weights -> XLA SPMD [svc: partitioner] : jit step | The compiler splits one step into per-device programs.
  XLA SPMD -> Devices [model: 8 chips] : step + collectives | Each chip computes its part; all-reduce joins the gradients.
  Devices -> Checkpoint store [store: Orbax] : save shards | Each host writes its own shards, so a save is parallel.
ref: docs | Distributed arrays and automatic parallelization | JAX documentation | https://docs.jax.dev/en/latest/sharded-computation.html

== Composable transforms: grad, vmap, jit
kind: pipes-filters, interpreter-compiler
when: You need gradients, per-example operations and compiled speed from one plain function.
how: JAX treats grad, vmap and jit as functions that take a function and return a new function. You write a loss for one example. grad gives the gradient function. vmap maps it over a batch, so you get per-example gradients without a Python loop. jit compiles the result.
The order is free. jit(vmap(grad(loss))) works because each transform acts on the traced program, not on the numbers. This is why techniques such as per-example gradient clipping, used in differential privacy, are short in JAX.
Keep the function pure. Print and global state inside it run only at trace time and cause confusing bugs.
used: JAX research code for per-example gradients, ensembles and physics simulation; libraries such as Optax build on it.
avoid: When your model is a stack of standard layers and you only need training; PyTorch eager is simpler to debug.
flow:
  Loss function [svc: one example] -> grad [svc: transform] : grad(loss) | grad returns a new function that gives the gradient for one example.
  grad -> vmap [svc: transform] : vmap(grad_fn) | vmap maps it over the batch axis, with no Python loop.
  vmap -> jit [svc: transform] : jit(batched) | jit compiles the batched gradient into one XLA program.
  jit -> Accelerator [model: GPU or TPU] : call on batch of 256 | One call returns 256 per-example gradients.
ref: docs | Automatic differentiation and vectorization | JAX documentation | https://docs.jax.dev/en/latest/automatic-differentiation.html

@@ langchain
== RAG chain with retriever and vector store
kind: rag, llm-workflow
when: A chat answer must use your own documents, and the model must cite them instead of guessing.
how: At index time a loader reads files, a text splitter cuts them into chunks of a few hundred tokens, an embedding model turns each chunk into a vector, and a vector store (pgvector, Chroma, Pinecone and others) saves vector and text.
At question time a retriever embeds the question and fetches the top k chunks, for example k = 4. A prompt template places the chunks and the question into one prompt. The chat model answers, and an output parser returns text with the source ids. LangChain gives a common interface for each step, so you can swap the vector store or the model without changing the chain.
Quality depends mostly on chunking and retrieval, not on the chain code. Measure retrieval hit rate on a test set before you tune prompts.
used: Document question-answering and support bots built with LangChain and a vector database; common in enterprise knowledge search.
avoid: When the corpus is small enough to fit in one prompt, or when exact keyword search or SQL answers the question.
flow:
  Loader and splitter [svc: index time] -> Vector store [db: pgvector] : chunk + embedding | Documents are cut into chunks and stored with their vectors.
  User [user] -> Retriever [svc: top k = 4] : question | The question arrives at the retriever.
  Retriever -> Vector store : nearest 4 vectors | The retriever embeds the question and asks for the four closest chunks.
  Vector store -> Prompt template [svc] : 4 chunks | The chunks are inserted next to the question.
  Prompt template -> Chat model [model: LLM] : full prompt | The model answers only from the given context.
  Chat model -> User : answer + sources | The user gets the answer with the source ids.
ref: paper | Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks | Lewis et al., NeurIPS 2020 | https://arxiv.org/abs/2005.11401

== LangGraph agent with checkpointed state
kind: agent-loop, checkpoint-restart
when: An agent runs many steps, may wait for a person, and must survive a crash without starting over.
how: LangGraph models the agent as a graph: nodes are functions (call the model, run a tool) and edges choose the next node. A shared state object moves through the graph. After every step a checkpointer saves the state, for example to Postgres, under a thread id.
If the process dies, the run resumes from the last saved step with the same thread id. A node can call interrupt to pause for human approval, such as before a payment tool runs. The graph stops, the state stays in the database, and the run continues when the person answers.
Checkpoints also allow time travel: replay from an earlier step or fork the state to try another path.
used: LangGraph agents with Postgres or SQLite checkpointers; the LangGraph documentation describes persistence and human-in-the-loop.
avoid: For a fixed two-step flow; a plain chain is simpler than a graph.
flow:
  User [user] -> Agent graph [svc: LangGraph] : message, thread 42 | The user sends a message with a thread id.
  Agent graph -> Chat model [model: LLM] : decide next action | The model node picks a tool call.
  Agent graph -> Checkpointer [db: Postgres] : save state, step 3 | The state is saved after each step.
  Agent graph -> Approver [user: human] : interrupt: approve refund? | A sensitive tool call pauses the graph until a person answers.
  Agent graph -x> Checkpointer : worker crash | The worker dies while waiting; no state is lost.
  Agent graph -> Checkpointer : resume thread 42 | A new worker loads step 3 and continues after approval.
ref: docs | LangGraph overview | LangChain | https://docs.langchain.com/oss/python/langgraph/overview

== Tracing every step to an observability back end
kind: observability-pipeline, feedback-loop
when: A chain or agent gives odd answers, and you need to see each model call, tool call, prompt, latency and token count.
how: LangChain calls callbacks at the start and end of every step. A tracer turns these into a tree of runs: the top chain, the retriever call, each model call and each tool call, with inputs, outputs, time and token usage.
The tracer sends the runs to a back end such as LangSmith, or to any OpenTelemetry collector. Engineers open one failing trace and see which step went wrong. Bad traces can be added to a dataset, and an evaluation job replays them after each prompt change.
Redact personal data before export, and sample traces in high traffic, because prompts are large.
used: LangSmith; teams that export LangChain traces through OpenTelemetry to Datadog, Grafana or similar tools.
avoid: When prompts hold data that must not leave your network; self-host the back end or turn tracing off.
flow:
  Agent [svc: LangChain app] -> Tracer [svc: callbacks] : step start and end | Each step reports its inputs, outputs and timing.
  Tracer -> Redactor [svc: PII filter] : run tree | A filter removes personal data from the run tree.
  Redactor ~> Trace back end [db: LangSmith or OTel] : batched upload | Runs are uploaded in the background, so users do not wait.
  Engineer [user] -> Trace back end : open failing trace | The engineer inspects each step of one bad answer.
  Trace back end -> Eval dataset [store] : save as test case | The bad case is saved and replayed after every prompt change.
ref: docs | LangSmith observability | LangChain | https://docs.langchain.com/langsmith/observability

@@ llamacpp
== Quantized local inference with GPU layer offload
kind: offload-accelerator, memory-tiering
when: You want to run an LLM on a laptop, a small server or a single consumer GPU with limited memory.
how: The model is stored as a GGUF file, one file with weights, tokenizer and metadata. Weights are quantized, for example to 4 bits per weight, so a 7B model shrinks from about 14 GB (16-bit) to roughly 4 GB.
llama.cpp memory-maps the file. With the option -ngl you choose how many transformer layers go to the GPU; the rest run on the CPU. If the model does not fit in video memory, the split lets it run, at lower speed. On Apple Silicon the GPU uses unified memory through Metal.
Token generation is limited by memory bandwidth, because every token reads all weights. That is why a smaller quantization is often faster, and why quality should be checked on your task.
used: Local assistants and desktop apps that embed llama.cpp, for example Ollama and LM Studio; edge and offline deployments.
avoid: For high-throughput serving to many users on data-centre GPUs; use vLLM or SGLang with continuous batching.
flow:
  GGUF file [store: Q4 + about 4 GB] -> llama.cpp runtime [svc: mmap] : load weights | The runtime memory-maps the quantized weights from disk.
  llama.cpp runtime -> GPU [model: 24 of 32 layers] : offload layers | The first 24 layers go to GPU memory.
  llama.cpp runtime -> CPU threads [svc: 8 threads] : remaining 8 layers | The other layers run on the CPU.
  User [user] -> llama.cpp runtime : prompt | The prompt is processed in batches.
  llama.cpp runtime -> User : tokens | Tokens stream back one at a time.
ref: docs | llama.cpp project | ggml-org | https://github.com/ggml-org/llama.cpp

== llama-server as a local OpenAI-compatible endpoint
kind: sidecar, api-gateway
when: Apps already speak the OpenAI API, and you want to point them at a model that runs on your own machine.
how: llama-server loads one GGUF model and offers HTTP endpoints, including chat completions in the OpenAI format. An app only changes its base URL. A few parallel slots let several requests share the model, and each slot keeps its own context.
Run it as a sidecar next to the app, or as a small shared service on an internal network. A gateway such as LiteLLM can route some requests to the local model and others to a hosted model, with fallback when the local one is busy.
Slots are limited, so it suits a team or a desktop app, not thousands of users.
used: Local development stand-ins for hosted APIs; private on-premises chat tools; Ollama and similar tools wrap llama.cpp in the same way.
avoid: When you need many concurrent users with strict latency; use a data-centre server.
flow:
  App [client: OpenAI SDK] -> Gateway [svc: router] : chat/completions | The app calls its usual API through a router.
  Gateway -> llama-server [svc: 4 slots] : same request | Simple requests go to the local server.
  llama-server -> Model [model: GGUF Q4] : decode in a slot | The request takes a free slot and decodes.
  Gateway -> Hosted API [svc: cloud model] : hard requests | Hard requests go to a hosted model.
  llama-server -x> Gateway : all slots busy | When slots are busy, the server answers with an error.
  Gateway -> Hosted API : fallback | The router retries on the hosted model.
ref: docs | llama.cpp server | ggml-org | https://github.com/ggml-org/llama.cpp

== Speculative decoding with a draft model
kind: none
when: Generation is slow because each token waits for one full pass of a large model, and a small model is available.
how: A small draft model guesses the next several tokens, for example 5. The large target model checks all five in one forward pass. Tokens that match the target's own choice are accepted; at the first mismatch the target's token is used and the rest are dropped.
The output is the same as the large model alone, but each large pass can yield more than one token. The gain depends on the acceptance rate: code and repeated text accept well, creative text less.
llama.cpp supports a draft model for llama-server, and also draft-free methods that look up repeated text in the prompt. The draft model needs the same tokenizer and extra memory.
used: llama.cpp speculative examples; the technique is described in papers by Leviathan et al. and Chen et al., 2023.
avoid: When memory is already tight, or when acceptance is low; the extra work then slows decoding.
flow:

@@ pytorch
== Distributed data parallel with all-reduce
kind: data-parallel
when: The model fits on one GPU, and you want to train faster by using many GPUs with different data batches.
how: Launch one process per GPU with torchrun. Each process builds the same model and wraps it in DistributedDataParallel. A DistributedSampler gives each rank a different shard of the data.
Each rank runs forward and backward on its own batch. DDP groups gradients into buckets, and runs an all-reduce on each bucket with NCCL while backward still computes earlier layers. When backward ends, every rank holds the same averaged gradient, so every optimizer step gives the same weights on all ranks.
Scaling is limited by network speed and by batch size. Check that step time does not grow when you add GPUs.
used: Standard multi-GPU training in PyTorch; most vision and mid-size language training jobs on NVLink or InfiniBand clusters.
avoid: When weights, gradients and optimizer state do not fit on one GPU; use FSDP.
flow:
  torchrun [svc: launcher] -> Rank 0 to 7 [svc: 1 process per GPU] : start workers | The launcher starts one process per GPU with the same code.
  Data sampler [store: shards] -> Rank 0 to 7 : different batches | Each rank gets its own slice of the dataset.
  * Rank 0 to 7: forward + backward | Each rank computes gradients on its own batch.
  Rank 0 to 7 -> NCCL [svc: all-reduce] : gradient buckets | Buckets are sent while earlier layers still compute.
  NCCL -> Rank 0 to 7 : averaged gradient | All ranks get the same gradient and make the same step.
  Rank 0 to 7 -> Checkpoint [store: rank 0 writes] : save state | One rank saves the model for restart.
ref: docs | Distributed Data Parallel | PyTorch documentation | https://pytorch.org/docs/stable/notes/ddp.html

== Fully sharded data parallel for large models
kind: data-parallel, model-parallel
when: Weights, gradients and optimizer state together do not fit on one GPU.
how: FSDP shards parameters, gradients and optimizer state across all ranks. Each rank stores about 1/N of the state. Before a layer runs, FSDP does an all-gather to rebuild that layer's full weights on every rank. After use, it frees them.
In backward it gathers again, then does a reduce-scatter so each rank keeps only its own gradient shard. Optimizer state stays sharded, so for Adam with 16-bit weights the state per GPU falls roughly in proportion to the GPU count.
The price is more communication than DDP. Wrap at the level of transformer blocks and overlap communication with compute. Use sharded checkpoints for fast save.
used: Large language model training with PyTorch FSDP; libraries such as torchtitan and Hugging Face Accelerate use it.
avoid: For models that fit on one GPU; DDP communicates less. For very large models, combine with tensor and pipeline parallelism.
flow:
  Training job [svc: 64 ranks] -> Sharded state [store: 1/64 per GPU] : keep own shard | Each rank holds one part of weights and optimizer state.
  Sharded state -> Layer 12 [model: full weights] : all-gather | The full weights of one layer are rebuilt just in time.
  Layer 12 -> Training job : forward, free | After forward, the extra weight copies are freed.
  Training job -> Layer 12 : all-gather again | Backward gathers the weights once more.
  Layer 12 -> Sharded state : reduce-scatter grads | Each rank receives the summed gradient for its own shard only.
  Sharded state -> Checkpoint store [store: sharded] : each rank saves | Ranks write shards in parallel.
ref: docs | Fully Sharded Data Parallel | PyTorch documentation | https://pytorch.org/docs/stable/fsdp.html

== torch.compile from eager code to fused kernels
kind: interpreter-compiler, offload-accelerator
when: An eager PyTorch model is limited by many small GPU kernels and Python overhead.
how: You keep writing normal eager code and add torch.compile(model). TorchDynamo watches the Python bytecode and captures tensor operations into a graph. Where it meets code it cannot trace, it breaks the graph and falls back to Python for that part.
AOTAutograd builds the backward graph. The default backend, Inductor, fuses operations and generates kernels, with Triton for GPUs. Compiled code is cached, and guards check that shapes and types still match. If a guard fails, the function recompiles.
The first step is slow, often tens of seconds. Many graph breaks or changing shapes cut the gain. Mark dynamic dimensions or pad to fixed sizes.
used: PyTorch 2.x training and inference; many open-source model repositories enable it with one line.
avoid: For short scripts, or code with changing shapes on every call; compile time can exceed the gain.
flow:
  Eager model [svc: Python] -> TorchDynamo [svc: capture graph] : torch.compile(model) | Dynamo reads bytecode and captures the tensor operations.
  TorchDynamo -> Inductor [svc: fuse + codegen] : FX graph | The graph goes to the backend, which fuses operations.
  Inductor -> Kernel cache [cache: guards] : Triton kernels | Compiled kernels are cached with guards on shape and type.
  Kernel cache -> GPU [model: device] : run fused kernels | Later steps run fused kernels, with fewer launches.
  Eager model -x> TorchDynamo : guard fails, recompile | A new shape fails a guard and triggers another compile.

== Radix prefix cache for shared prompt prefixes
kind: none
when: Many requests share a long start, such as a system prompt, few-shot examples or earlier chat turns, and you want to skip recomputing it.
how: SGLang's RadixAttention keeps the key-value cache of all processed tokens in a radix tree. Each path in the tree is a token sequence. A new request walks the tree, finds the longest matching prefix, and reuses its cached keys and values. Only the new tokens go through prefill.
When memory is full, the least recently used leaves are evicted first. Requests that share a prefix are best run together, so the scheduler favours them.
For a chat with a 3,000-token system prompt, the prefix is computed once, and later requests prefill only their own few hundred tokens. This cuts time to first token and GPU work. It helps agents with repeated tool context and multi-turn use.
used: SGLang servers for chat, agents and structured-output workloads; vLLM and others have similar automatic prefix caching.
avoid: When prompts rarely share a prefix; the tree adds bookkeeping with little gain.
flow:
  Request A [client: system + Q1] -> SGLang scheduler [svc] : 3,300 tokens | The first request has a long shared system prompt.
  SGLang scheduler -> Radix tree [cache: KV by prefix] : insert 3,300 tokens | After prefill, the key-value cache is stored by token path.
  Request B [client: system + Q2] -> SGLang scheduler : 3,250 tokens | A second request starts with the same system prompt.
  SGLang scheduler -> Radix tree : match prefix | The tree reports 3,000 matching tokens.
  Radix tree -> GPU [model: prefill 250] : reuse cache | Only the 250 new tokens are prefilled.
  * Radix tree: evicting old leaves | When memory is low, the least recently used branches are dropped.

== Prefill and decode on separate GPU pools
kind: none
when: Prefill (reading the prompt) and decode (producing tokens) disturb each other on the same GPUs, and you need both fast first tokens and smooth streaming.
how: Prefill is compute-heavy and runs once per request. Decode is memory-bound and runs for each token. On one GPU, a long prefill stalls the decode of other users. In disaggregation, one pool of GPUs only does prefill and another pool only does decode.
A router sends the request to a prefill worker. It builds the key-value cache, and transfers it over a fast link (RDMA or NVLink) to a decode worker. The decode worker streams tokens. You size and scale the pools on their own, for example more decode GPUs for long answers.
The costs are the cache transfer and a harder system to run. SGLang supports this mode with a router in front.
used: Large serving fleets; SGLang and vLLM both support disaggregated prefill and decode, and the idea comes from the DistServe paper.
avoid: For small deployments of one or two GPUs; the transfer cost is larger than the gain.
flow:
  User [user] -> Router [svc: SGLang router] : chat request | The router receives the request and picks a prefill and a decode worker.
  Router -> Prefill pool [svc: compute-heavy GPUs] : prompt | A prefill worker reads the whole prompt.
  Prefill pool -> Decode pool [svc: memory-heavy GPUs] : KV cache over RDMA | The key-value cache is sent to a decode worker.
  Decode pool -> User : stream tokens | The decode worker streams tokens without prefill stalls.
  Decode pool ~> Router : queue depth | The router uses load figures to balance later requests.
ref: paper | DistServe: Disaggregating Prefill and Decoding for Goodput-optimized LLM Serving | Zhong et al., OSDI 2024 | https://arxiv.org/abs/2401.09670

how: tf.data builds the input as a chain of steps: read files (TFRecord), shuffle, map a preprocessing function, batch and prefetch. Each step is an operation on a dataset, so the chain is a pipeline.

Read files in parallel with interleave, and cache small datasets after the first pass. Check the profiler: if the GPU is idle between steps, the input is the bottleneck.
used: TensorFlow and Keras training jobs; TFRecord data on Cloud Storage with a TPU needs this to keep up.
avoid: For tiny datasets that fit in memory as arrays; plain tensors are fine.
flow:
  TFRecord files [lake: GCS] -> Reader [svc: interleave x8] : parallel reads | Eight readers open different files at once.
  Reader -> Map [svc: decode + augment] : raw records | Threads decode images and apply augmentation.
  Map -> Prefetch buffer [queue: 2 batches] : batch of 256 | Finished batches wait in a bounded buffer.
  Prefetch buffer -> Training step [model: GPU] : next batch | The GPU takes a ready batch, with no wait.
  Training step ~> Prefetch buffer : slot freed | A taken batch frees a slot, and the producers continue.
ref: docs | Better performance with the tf.data API | TensorFlow documentation | https://www.tensorflow.org/guide/data_performance

@@ vllm
== Continuous batching with a paged KV cache
kind: continuous-batching
when: Many users call an LLM at once, and static batches waste GPU time and memory.
how: Each request keeps a key-value (KV) cache for every token so far. Old systems reserved one big contiguous block per request, which wasted much memory. vLLM's PagedAttention splits the KV cache into small fixed-size blocks, kept in a block table like pages in an operating system. Memory is allocated as the text grows, so little is wasted, and more requests fit in the batch.
At every decoding step the scheduler adds waiting requests and removes finished ones, so the batch never waits for the slowest request. Long prompts can be split into chunks (chunked prefill) so they do not block decoding.
When memory runs out, a request can be paused and its blocks freed, and then resumed later.
used: vLLM servers in production at many companies; it is the base of several cloud LLM services.
avoid: For a single-user local run on a laptop; llama.cpp is lighter.
flow:
  Client A [client] -> Scheduler [svc: vLLM engine] : prompt 800 tokens | A request arrives while others decode.
  Client B [client] -> Scheduler : prompt 40 tokens | A second request arrives at the same time.
  Scheduler -> Block manager [cache: 16-token blocks] : allocate blocks | KV blocks are allocated only as tokens are produced.
  Scheduler -> GPU [model: one step + 24 requests] : mixed prefill + decode | New and old requests share one forward pass.
  GPU -> Client A : token | Each request gets its token after every step.
  GPU -> Block manager : B done, free blocks | When B finishes, its blocks return to the pool.
ref: paper | Efficient Memory Management for Large Language Model Serving with PagedAttention | Kwon et al., SOSP 2023 | https://arxiv.org/abs/2309.06180

== Tensor-parallel serving of a model that exceeds one GPU
kind: model-parallel
when: A model's weights are larger than the memory of one GPU, or you want lower latency from several GPUs.
how: With tensor parallelism, vLLM splits each layer's weight matrices across GPUs, for example 4 GPUs for a 70B model in 16-bit (about 140 GB of weights). Every GPU computes its slice, and an all-reduce joins the results after the attention and feed-forward blocks. This needs a fast link such as NVLink.
For models too large for one node, pipeline parallelism puts groups of layers on different nodes, with tensor parallelism inside each node. Ray or multiprocessing starts the workers. Quantized weights such as FP8 reduce the number of GPUs needed.
Tensor parallelism helps latency but costs communication. Use the smallest degree that fits the weights and leaves room for the KV cache.
used: vLLM tensor-parallel and pipeline-parallel serving of 70B and larger open models on multi-GPU nodes.
avoid: When the model fits on one GPU; run replicas of it instead, which scale more simply.
flow:
  API server [svc: vLLM] -> Worker 0 to 3 [model: 4 GPUs NVLink] : request + token ids | The engine sends each step to all four workers.
  Worker 0 to 3 -> All-reduce [svc: NCCL] : partial results | Each GPU has computed a slice of the layer.
  All-reduce -> Worker 0 to 3 : summed output | Every GPU gets the joined output for the next layer.
  Worker 0 to 3 -> API server : next token | One GPU returns the sampled token.
  API server -> Client [client] : stream token | The user sees text as it is produced.
ref: docs | vLLM documentation | vLLM project | https://docs.vllm.ai/en/latest/

== Distributed gradient boosting with histogram all-reduce
kind: data-parallel, map-reduce
when: The training table is too large or too slow for one machine, and you want boosted trees on a cluster.
how: XGBoost builds trees one after another. For each split it needs the sum of gradients per feature bin. With the histogram method, each worker owns a part of the rows and builds local histograms of its rows. Workers then do an all-reduce, so everyone has the global histogram and finds the same best split.
You run this through Dask, Spark or Ray. Each worker keeps its data partition in memory, or in GPU memory. No raw rows move over the network; only histograms do, which are small (bins times features).
Check data balance, because the slowest worker sets the speed. The model on the driver is the same as one trained on a single machine, apart from small numeric differences.
used: XGBoost on Dask and Spark clusters; GPU training with NVIDIA RAPIDS and Dask.
avoid: When the data fits on one big machine; single-node training is simpler and often fast enough.
flow:
  Driver [svc: Dask client] -> Worker 1, Worker 2, Worker 3 [svc: row partitions] : train(dtrain) | The driver starts a training task on each worker.
  * Worker 1: local histogram | Each worker counts gradients per bin for its own rows.
  Worker 1, Worker 2, Worker 3 -> Allreduce [svc: Rabit or NCCL] : histograms | The small histograms are summed across workers.
  Allreduce -> Worker 1, Worker 2, Worker 3 : global histogram | All workers pick the same split and grow the same tree.
  Worker 1 -> Model store [store: model.json] : save booster | The model is saved once after all rounds.

== Search, then structure inference pipeline
kind: pipes-filters, offload-accelerator
when: A prediction needs a slow CPU database search first and a fast GPU model second.
how: The input is an amino-acid sequence. The first stage searches large sequence databases (with tools such as jackhmmer and HHblits) and builds a multiple sequence alignment (MSA). avoid: When speed matters more than the last bit of accuracy for many sequences; use a single-sequence language-model predictor.

  Network -> Structure [store: PDB + pLDDT] : coordinates, confidence | It outputs atom positions and a confidence per residue.
  Structure -> Relax [svc: optional] : fix geometry | A short physics step fixes small clashes.

== Job queue with separate CPU and GPU worker pools
kind: competing-consumers, load-leveling
when: A lab or company must run thousands of predictions, and the CPU search and GPU steps have very different cost.
how: Users submit sequences to a job queue. CPU workers take jobs from the queue and run the MSA search. They write the features file to shared storage and put a second message on a GPU queue. GPU workers take these and run the network.
Splitting the queues lets you size each pool alone. Search is often the bottleneck, so you may run more CPU nodes than GPUs. The databases are large (hundreds of gigabytes), so put them on fast local or shared SSD.

  Search queue -> CPU workers [svc: MSA search] : one job each | CPU workers compete for jobs.
  CPU workers -> MSA cache [cache: by sequence hash] : features file | The result is cached by a hash of the sequence.
  CPU workers -> GPU queue [queue: ready features] : feature path | A second message tells a GPU worker that the features are ready.
  GPU queue -> GPU workers [svc: inference] : one job each | GPU workers run the model.
  GPU workers -> Results store [store: structures] : PDB + confidence | Finished structures are stored for the scientist.
  GPU workers -x> GPU queue : failed, retry | A failed job goes back; after 3 tries it moves to a dead-letter queue.

how: You mark the end of the stable part with a cache_control breakpoint. Claude stores the processed prefix.
