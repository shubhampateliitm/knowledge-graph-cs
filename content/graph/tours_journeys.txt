## What happens when you open https://www.example.com in a browser | From a typed URL to photons leaving the screen
browser | You press Enter. Before any network call, the browser parses the text into scheme (https), host (www.example.com), port (443 by default) and path (/). It checks its own memory first: an HSTS list that says "always use HTTPS", the HTTP cache (is a fresh copy of this page already on disk?), and the list of open connections it can reuse. A cold load finds nothing, so the browser's network process takes over. Modern browsers run each tab in a separate sandboxed renderer process, and only the privileged network process is allowed to open sockets. The browser also starts speculative work in parallel, such as asking for the IP address while it still checks the cache. Everything that follows is a chain of small requests, each one hidden behind a single keypress, and the whole chain has about 100 to 300 ms to finish before the page feels slow.
dns | The browser needs an IP address for www.example.com. It asks the operating system's stub resolver, which checks its cache and then sends one UDP packet of about 40 bytes to a recursive resolver (your router, your ISP or something like 1.1.1.1) on port 53. If the resolver does not know the name, it walks the tree: a root server says "ask the .com servers", a .com TLD server says "ask example.com's name servers", and that authoritative server answers with an A record (IPv4) and an AAAA record (IPv6), each with a TTL such as 300 seconds. A cold lookup costs 20 to 120 ms; a cached one costs under 1 ms. The answer is about 60 bytes. Browsers often ask for A, AAAA and HTTPS records at once, and the HTTPS record can already announce that the site supports HTTP/3 and which TLS settings to use.
sockets | With an address in hand, the network process asks the kernel for a connection through system calls. socket() creates a file descriptor, connect() starts the handshake, and from then on read() and write() or an event loop built on epoll move bytes. The kernel keeps a structure for this connection with send and receive buffers (often 64 KB to several MB) and a small state machine. The application never builds packets; it only writes bytes into a buffer and the kernel decides how to cut them into segments. Chrome opens several sockets at once, for example one for IPv6 and one for IPv4, and races them ("Happy Eyeballs": the second attempt starts after about 250 ms) so that a broken IPv6 path does not slow you down. The first packet leaves only after the kernel has chosen a source port from the ephemeral range, usually 32768 to 60999.
tcp | TCP opens with a three-way handshake. The client sends SYN (60 bytes with options: MSS 1460, window scale, SACK, timestamps), the server answers SYN-ACK, and the client sends ACK. That costs one full round trip, say 30 ms to a nearby server and 150 ms across an ocean. Both sides now agree on starting sequence numbers, so that lost, duplicated or reordered packets can be detected. TCP then gives the application a reliable ordered byte stream on top of an unreliable network. A new connection starts in slow start with a congestion window of 10 segments, about 14.6 KB, because the sender does not know the capacity of the path yet. Each ACK lets the window grow, roughly doubling per round trip, until a loss or delay says the path is full. This is why small pages are fast: example.com's HTML fits in the first window.
quic | Many sites advertise HTTP/3 (through the HTTPS DNS record or an Alt-Svc header), and then the browser uses QUIC instead of TCP plus TLS. QUIC runs over UDP port 443 and puts the transport, loss recovery and TLS 1.3 handshake into one protocol, so the first connection needs only one round trip instead of two to three, and a returning client can send data in 0 RTT. The first client packet must be padded to at least 1200 bytes, which limits abuse as an amplification attack. Streams inside a QUIC connection are independent: one lost packet blocks only its own stream, not the whole page, which fixes the head-of-line blocking of TCP. Every packet is encrypted, even most headers, which stops middleboxes from meddling with the protocol. If UDP is blocked, the browser silently falls back to HTTP/2 over TCP.
tls | On the TCP path the browser now sends a TLS 1.3 ClientHello, typically 300 to 1500 bytes. It contains the server name (SNI), the cipher suites it supports, and a key share: a public value for an elliptic-curve Diffie-Hellman exchange (X25519, often combined with a post-quantum ML-KEM share). The server replies with its own key share, so both sides can compute the same shared secret without ever sending it. From that moment everything is encrypted, including the server's certificate chain (about 2 to 4 KB) and a Finished message that proves nobody tampered with the handshake. TLS 1.3 needs just one round trip. The browser and server then derive separate keys for each direction from the secret using HKDF. A session ticket is also issued, so the next visit can resume with fewer round trips.
signatures | Encryption alone would be useless if you were talking to an attacker. So the server sends a certificate chain: a leaf certificate for www.example.com, signed by an intermediate CA, which is signed by a root CA that is already in your operating system or browser trust store. The browser checks each signature (an ECDSA P-256 signature is 64 bytes and takes about 0.1 ms to verify), the validity dates, that the name matches, and that the certificate was logged in public Certificate Transparency logs. The server also signs the whole handshake transcript with its private key, which proves it really owns the certificate. If any check fails you see a full-page warning. This web of trust is the only reason you can type a password into a Wi-Fi hotspot run by a stranger.
aead | After the handshake, every byte is protected by an AEAD cipher: AES-128-GCM on CPUs with AES instructions, or ChaCha20-Poly1305 on phones without them. A TLS record carries up to 16 KB of plaintext plus a 16-byte authentication tag, so the receiver can detect any flipped bit and reject the record. A counter forms the nonce, so the same message never encrypts the same way twice. Modern CPUs encrypt at several GB per second per core, so the cost is small. This is also the moment when your request is sent: the browser builds a plain-text request, hands it to the TLS library, and gets back a record of roughly 400 to 800 bytes that goes to the kernel as one write() call and leaves as one or two TCP segments.
http | The decrypted request is plain text: GET / HTTP/1.1 (or the binary HTTP/2 or HTTP/3 equivalent), a Host header, Accept, Accept-Encoding: gzip, br, zstd, a User-Agent and cookies if any, usually 300 to 800 bytes. With HTTP/2 the header names are compressed with HPACK, and with HTTP/3 with QPACK, so repeated requests cost only a few bytes. The server answers with a status line (200 OK), headers (Content-Type: text/html, Cache-Control, ETag) and a body. For example.com the HTML is about 1.2 KB, which shrinks to roughly 600 bytes with Brotli. The browser uses the ETag and Cache-Control headers to decide whether it can skip the request next time. The same request-response pattern, and its small set of verbs and status codes, is what makes the web easy to cache, proxy and debug.
cdn | The IP address you got from DNS usually does not belong to the site's own server but to a nearby CDN edge. DNS or anycast routing steers you to the closest of hundreds of locations, so the round trips in the handshakes above are 10 to 30 ms instead of 150. The edge terminates TLS, keeps hot objects in memory and on SSD, and answers example.com's tiny page without ever calling the origin. On a miss it fetches over an already-warm connection to the origin and caches the result for the time allowed by Cache-Control. The CDN also absorbs attacks, compresses responses and speaks the newest protocol versions even if the origin does not. Physics sets the floor: light in fibre needs about 5 µs per km, so a distant server can never be fast.
nginx | Inside the edge, a web server such as nginx receives the bytes. It uses an event loop: a few worker processes, one per CPU core, each handling tens of thousands of connections with epoll instead of one thread per connection. When the request arrives, the worker parses the headers, picks a virtual host by the Host header and finds a rule for the path. For a static file it opens the file, which usually sits in the OS page cache, and calls sendfile() so that the kernel copies bytes from the cache to the socket without passing through user space. If the content is dynamic, nginx forwards the request to an application server over a local socket or a pooled connection. The response header and body are written back through the TLS layer in 16 KB records.
iprouting | Every TCP segment travels as an IP packet, up to 1500 bytes including 20 bytes of IP and 20 of TCP header. Your laptop sends it to the default gateway; your home router rewrites the private source address (such as 192.168.1.20) to its public one (NAT) and forwards it. Across the internet, 10 to 20 routers each look at the destination address, find the longest matching prefix in their forwarding table, and pass the packet on in a few microseconds. Routes between networks are learned with BGP. Each router decrements the TTL field, so a routing loop cannot live forever. Packets of one connection can take different paths, and some are dropped when queues overflow, which is how TCP discovers congestion and slows down.
ethernet | On each hop the IP packet is wrapped in a link-layer frame. On Wi-Fi or Ethernet it gets a 14-byte header with the destination MAC address (found with ARP), and a 4-byte checksum at the end. On a fibre link the frame becomes a stream of bits encoded with a line code, sent at 10 or 100 Gbit/s. A 1500-byte frame takes 1.2 µs at 10 Gbit/s but 12 µs at 1 Gbit/s, plus a fixed 24-byte gap and preamble. Switches learn which MAC address sits on which port and forward the frame only there. At the data center the frame reaches a network card that uses DMA to write the packet into memory and raises an interrupt, so the CPU can pick it up.
parsing | The response is back in the browser. The renderer receives the HTML bytes, decodes them (UTF-8), and a tokenizer turns the text into tags, which a tree builder arranges into the DOM, the Document Object Model. A robust algorithm defined in the HTML standard handles even broken markup without errors. Whenever the parser meets a link to a stylesheet, script or image, it asks the network process for it, and the page's critical path grows by another round trip or two. CSS is parsed into rules; combined with the DOM, the browser computes a style for each element (font, color, size, display). A page like example.com has about 20 elements and no scripts, so this takes under 5 ms. A heavy modern page can have 2,000 to 10,000 elements and megabytes of JavaScript, and then the parsing and script execution dominate everything above.
unicode | Text must become shapes. The characters are Unicode code points (UTF-8 bytes in the file, "E" is 1 byte, a Hindi letter is 3). Layout breaks the text into lines using the font's advance widths and the box width, and a shaping engine such as HarfBuzz turns code points into glyph IDs, handling ligatures, combining marks and right-to-left scripts. The font file (TrueType or OpenType) stores each glyph as curves, and hinting or anti-aliasing decides how to place them on a pixel grid. The result is a display list: draw a rectangle here, draw these glyphs there, in this color and size. The page then goes through layout, where each box gets x, y, width and height, and paint, which records drawing commands in order but does not yet touch pixels.
simt | The drawing commands go to the GPU. The browser's compositor splits the page into layers and tiles (typically 256 by 256 pixels), the GPU rasterizes each tile, and the compositor assembles the tiles with the right scroll offset and transforms. A GPU has thousands of small cores that run the same program on many pixels at once in groups of 32 or 64 threads (SIMT). A fragment shader computes the color for each pixel: blend glyph coverage, mix with the background, apply gamma. For a 1920 by 1080 screen that is 2.07 million pixels, each 4 bytes, so one frame is 8.3 MB in the framebuffer. The GPU does this in about 1 to 2 ms, well under the 16.7 ms budget of a 60 Hz display. Because layers are cached as textures, scrolling needs no re-rasterization.
dma | The finished frame sits in GPU memory. At every vertical refresh the display controller reads the framebuffer through DMA, line by line, without involving the CPU, and sends the pixels over DisplayPort or HDMI. At 1920 by 1080 and 60 Hz, that is about 500 MB/s of pixel data read from memory, and roughly 4.5 Gbit/s on the cable once blanking intervals and line encoding are added. Double buffering keeps the controller from showing a half-drawn image: the GPU draws into a back buffer and swaps pointers during vertical blank. If the frame misses the deadline, the screen shows the old frame again, and you perceive a stutter. Variable refresh rate lets the display wait for the GPU instead. Total time from Enter to the first pixels is usually 150 to 400 ms, and you wait most of it on round trips, not on computation.
display | The frame has left memory; now the monitor decides what to do with the stream. When it was plugged in, it described itself in a small EDID block, read over a slow side channel in the cable, and the GPU chose one of its modes. For 1080p at 60 Hz that mode is 2200 pixel slots by 1125 lines at 148.5 MHz, so one line lasts 14.8 µs. Inside the monitor, a timing controller receives the stream and drives the panel as a grid. A gate driver switches on one row of transistors at a time, while the source drivers put an analogue voltage on each of the 5,760 columns (1,920 pixels times three subpixels). Row by row, the page is written from top to bottom in about 16 ms, so the bottom of the page appears nearly one frame after the top. Once example.com is painted and nothing moves, a laptop can switch on panel self-refresh: the panel keeps its own copy of the frame, the GPU stops scanning out, and memory and the link sleep until something changes.
photonics | The panel turns numbers into light. In an LCD, a white LED backlight passes through a polarizer, a layer of liquid crystal whose twist is set by the voltage at each subpixel, a second polarizer, and a red, green or blue color filter. In an OLED, each subpixel is itself a thin organic film that emits light when current drives electrons and holes to recombine. A thin-film transistor next to every subpixel holds the voltage on a tiny capacitor for one frame; there are 6.2 million of them on a full-HD screen. Brightness uses 8 bits per color, so 256 levels, and the eye's response is roughly logarithmic, so gamma curves spend those levels carefully. Light leaves the glass at 300,000 km/s and reaches your eye in about a nanosecond.
transistor | Everything above ran on transistors. A modern phone or laptop chip has 10 to 100 billion MOSFETs, each a switch about a few tens of nanometres across that opens when a voltage on its gate pulls electrons into a channel. A CPU core switches them 3 to 5 billion times a second, and each switching event moves a few thousand electrons. The same switches build the network card, the GPU and the display driver. Each logic gate spends energy when it flips, which turns almost all the electrical power into heat; a laptop browser tab costs about one to a few watts. Every layer in this journey, from the URL to the shape of the glyph, is finally a pattern of electrons moving through doped silicon and copper wires.
maxwell | Even the long-distance part is physics. The bits that left your laptop became radio waves on 2.4 or 5 GHz, or pulses of light in glass fibre, and both are solutions to Maxwell's equations: changing electric and magnetic fields sustain each other and travel at the speed of light in the medium, about 200,000 km/s in glass. A round trip from Bengaluru to a server in Virginia is about 13,000 km each way, so even with perfect equipment it cannot take less than about 130 ms. Your screen's light is the same kind of wave, only at 430 to 750 THz. The retina's cone cells absorb photons, and the signal reaches the visual cortex, which is the last step: you read the word "Example".

## What happens when you run ssh user@host | From a command line to a remote shell, with every packet protected
process | You type ssh user@host and your shell forks a child that calls execve() on /usr/bin/ssh. The ssh program first reads its configuration: ~/.ssh/config, /etc/ssh/ssh_config and command-line options. It decides which port (22), which identity files (id_ed25519, id_rsa), and whether an ssh-agent is available through the SSH_AUTH_SOCK environment variable. It also puts your terminal into raw mode with a tcsetattr() call, so that every key, including Ctrl-C, is passed on as a byte instead of being interpreted locally. The whole program is one process with one thread; it waits for events from three sources, the network socket, your terminal, and sometimes the agent socket, using a single poll or select loop. Startup takes a few milliseconds before the first network call.
dns | The host name must become an address. ssh calls getaddrinfo(), which reads /etc/nsswitch.conf and /etc/hosts and then asks the DNS resolver configured in /etc/resolv.conf, usually with a single UDP packet of about 40 bytes and a reply of 60 to 100 bytes. An answer may hold several addresses, IPv4 and IPv6, and ssh tries them in order. If the name was in your /etc/hosts file or already cached, this takes microseconds; a fresh lookup takes 1 to 100 ms. For hosts inside a company, an ssh config file may add a ProxyJump line, and then ssh first opens a connection to a bastion host and tunnels the real connection through it as a channel. Using a short-lived cache like this is why the second ssh to the same host feels instant.
tcp | ssh creates a socket() and calls connect() to port 22. The kernel sends a SYN, gets a SYN-ACK and sends an ACK: one round trip, about 1 ms inside a data center and 150 ms across the world. After that TCP gives a reliable ordered stream, which is what SSH needs, because its own packet format has no retransmission. Both sides immediately send an identification line in plain text, for example SSH-2.0-OpenSSH_9.8, ending with CR LF. This line tells each side which protocol version and software the other runs, and it later becomes part of the signed key-exchange hash, so that a man in the middle cannot silently downgrade the protocol. ssh also sets TCP_NODELAY on interactive sessions, so that single keystrokes are not held back by Nagle's algorithm.
sockets | On the server, sshd has been sitting in accept() on a listening socket on port 22 since boot. When the SYN completes, the kernel puts the new connection in the accept queue and sshd's main process wakes up. It forks a child process for this connection and splits it into a privileged monitor and an unprivileged child (privilege separation). The unprivileged child, running with almost no rights in an empty chroot, parses all the untrusted network data. The monitor does only the few operations that need root, such as reading the host private key or checking passwords. If an attacker finds a memory bug in the packet parser, he lands in the weak process with no files and no ability to start programs.
ssh | Before the next messages make sense, look at what SSH actually is: three small protocols stacked on one TCP connection, defined in RFC 4251 to 4254. The transport layer makes a secure packet pipe. On top of it, the user-authentication layer decides who you are. On top of that, the connection layer splits the pipe into channels. Every message starts with one byte that names its type, and the numbers are grouped by layer: 1 to 49 for transport and key exchange, 50 to 79 for authentication, 80 to 127 for channels. So a receiver needs no extra framing to know which layer must handle a packet. KEXINIT is 20, NEWKEYS is 21, USERAUTH_REQUEST is 50 and CHANNEL_OPEN is 90. This layering is why one handshake serves everything: the same pipe carries your shell, an sftp transfer or a forwarded port, and each layer can change without the others. A new login method, for example, needs no change to the encryption. The price is that SSH is its own protocol with its own host-key trust model, instead of reusing TLS and certificate authorities. The next steps follow the layers in order.
pkcrypto | The two sides now send KEXINIT messages, each a list of about 10 to 20 algorithm names for key exchange, host key type, cipher and MAC. The first match in the client's order wins. Modern defaults are mlkem768x25519-sha256 or curve25519-sha256 for key exchange. Each side generates a temporary key pair (an X25519 key is 32 bytes) and sends the public half; both multiply their private value by the other side's public value and get the same 32-byte shared secret, which never crosses the wire. The key pair is thrown away right after, so recording the traffic today and stealing the server key tomorrow does not help (forward secrecy). The hybrid ML-KEM option adds protection against future quantum computers. The negotiation also means old, weak algorithms can be switched off in the server configuration without changing the protocol.
signatures | How does the client know it talks to the right machine and not an impostor in the middle? The server includes its host public key (for example ssh-ed25519, 32 bytes) and a signature over the exchange hash, made with the matching private key from /etc/ssh/ssh_host_ed25519_key. The client verifies the signature, which proves the server holds the private key and took part in this very exchange. But who owns the key? The client looks the host up in ~/.ssh/known_hosts. On the very first connection it asks "The authenticity of host can't be established... Are you sure?" and you compare the fingerprint; this trust on first use is the weak spot, which SSH certificates and DNS records can fix. If the key later changes, ssh refuses loudly with a big warning.
hashfn | A hash function appears three times in this handshake. First, both sides hash everything they have exchanged so far (both identification lines, both KEXINIT messages, the host key and both public keys) with SHA-256 into the 32-byte exchange hash H; this is what the server signs, so any tampering changes H. Second, the session keys are derived from the shared secret and H by hashing with different letters (A to F), giving separate keys and IVs for each direction. Third, the fingerprint you see is SHA256: and 43 base64 characters, a hash of the host key, which is short enough for people to compare. Collision resistance is what makes all three safe. Without a good hash, none of the three jobs could be trusted: an attacker who could find two inputs with the same hash could make two different handshakes look identical.
aead | Both sides now send a NEWKEYS message, and from that point every packet is encrypted and authenticated. OpenSSH defaults to chacha20-poly1305@openssh.com or aes256-gcm. A packet has a length, a padding length, the payload, random padding to hide the true size, and a 16-byte authentication tag; each direction has its own sequence number, so replayed or reordered packets are rejected. A 32-byte payload becomes about 64 bytes on the wire. The encryption costs under a microsecond per packet; the real cost of ssh in bulk transfers is the single-threaded cipher at about 1 to 2 GB/s and its internal 2 MB flow-control window. After this point, an observer sees only sizes and timing. The tag check happens before any decrypted byte is used, so a corrupted or forged packet ends the connection at once.
filesystems | Next the client must prove who it is. The server announces the allowed methods (publickey, password, keyboard-interactive). The client offers its public key, and the server's monitor process opens ~user/.ssh/authorized_keys. sshd first checks that the file and its parent directories are not writable by anyone else (StrictModes), because otherwise another user could add a key. It looks for a line with the same key blob, together with optional limits such as from= or command=. This is a normal file read through the VFS: open(), read() and close(), usually answered from the page cache, in tens of microseconds. If the file does not list the key, the client simply tries the next key, up to the server's attempt limit of 6.
finitefields | The client has to show it owns the private key. It builds a message that holds the session ID (the exchange hash H), the user name, the service name and the public key, and signs it with the private key. With an Ed25519 key the signature is 64 bytes and takes about 50 µs; inside, it is arithmetic on points of an elliptic curve over the finite field of integers modulo 2^255 - 19, so every number is reduced by the same prime and nothing grows without bound. If the key is in an ssh-agent, the signing request goes over a Unix socket to the agent, which holds the decrypted key in memory and never hands it out, so the private key does not even have to be on the machine that you ssh from; agent forwarding extends this over a hop. The server verifies the signature with the public key from authorized_keys. Because H is unique to this session, the signature cannot be replayed on another connection. No password ever crosses the network.
syscalls | Authentication succeeded, so the monitor now acts for the user. The sshd child calls setgid(), initgroups() and setuid() to drop all root rights and become the user, sets environment variables such as HOME, SHELL and SSH_CONNECTION, and PAM modules may run to create a login session, write to /var/log/lastlog and utmp, and apply limits. Each of these is a system call: the CPU traps into the kernel, switches to kernel mode, checks arguments and permissions, and returns, which costs roughly 100 to 300 ns when it does nothing slow. The kernel decides what a process may do by its user ID, its group IDs and its capabilities. The step from root to the user's identity cannot be undone, which is why a bug after this point does not give the attacker root.
iomodels | SSH multiplexes many logical streams over the one encrypted connection. The client sends a channel-open request of type "session" with a channel number, a window size (2 MB is common) and a maximum packet size (32 KB). The server confirms with its own channel number. Each channel has its own flow control: the sender may transmit only as many bytes as the receiver's window allows, and the receiver sends window adjustments as it drains data. This is why one ssh connection can carry your shell, a scp or sftp transfer, a forwarded port and an X11 session without them blocking each other. Both programs use a single event loop with poll() or epoll to wait on the socket, the terminal and every child process at once.
linux | The client sends a pty-req (a pseudo-terminal request) with the terminal type (xterm-256color) and the window size, say 120 columns by 40 rows. The server kernel creates a pty pair with posix_openpt(): a master end held by sshd and a slave end, /dev/pts/3, which looks to programs exactly like a serial terminal. The kernel's line discipline sits between them: it does echo, line editing, and turns Ctrl-C into SIGINT for the foreground process group. When you resize your window, ssh sends a window-change message and the server sets TIOCSWINSZ, which makes the kernel send SIGWINCH so that programs such as vim redraw. The pty is a small piece of kernel code that allows ancient terminal software and modern network sessions to meet.
scheduling | The client now asks for a "shell" request. sshd forks, the child calls setsid() to become a session leader, opens /dev/pts/3 as its controlling terminal, duplicates it onto file descriptors 0, 1 and 2, and calls execve() on your login shell, such as /bin/bash with a leading dash so that it reads your profile. fork() copies the page tables lazily, with copy-on-write, so it takes only about 100 µs. The shell reads ~/.bashrc, prints the prompt, and blocks in read() on the pty slave. The kernel scheduler marks it as sleeping, uses the CPU for something else, and wakes it up when bytes arrive. Total time from pressing Enter to prompt is usually 0.2 to 1 s, mostly the round trips and the profile scripts.
interrupts | Now you press a key, say "l". Your terminal emulator writes the byte to the ssh process's stdin; ssh wraps it in a channel-data message, encrypts it (about 50 bytes on the wire for 1 byte of data) and writes it to the socket, and TCP sends one small segment immediately. On the server, the network card receives the frame, uses DMA to write it to memory and raises an interrupt; the kernel's network stack hands the bytes to sshd, which decrypts them and writes the byte to the pty master. The line discipline echoes "l" back and wakes the shell. The echo takes the same path in reverse, so every keystroke costs one full round trip: with 150 ms of latency typing feels sluggish, which is why tools such as mosh predict the echo locally.
lightspeed | Every interactive keystroke is limited by the speed of light in fibre, about 200,000 km/s or 5 µs per km. A server in a data center 100 km away adds at least 1 ms for the round trip; a server on the other side of the planet adds more than 100 ms, and real routes are longer than straight lines, so 150 to 250 ms is typical. No software trick can remove this delay, only hide it: local echo, connection multiplexing with ControlMaster (so that the next ssh to the same host skips the whole handshake and starts in about 10 ms), and moving the work closer to the person. When you type exit, the shell ends, the pty closes, the channel closes, sshd's child exits, and the TCP connection is torn down with FIN packets.

## What happens when you press a key and the letter appears on screen | From a switch closing to light leaving a pixel, in about 20 milliseconds
digitallogic | Under each keycap is a switch, but a keyboard with 104 keys does not have 104 wires. The keys are wired as a matrix, for example 6 rows by 18 columns, which needs only 24 pins. A small microcontroller inside the keyboard sets one row line high at a time and reads all column lines. If you press "A", it closes a contact between its row and column, and the controller sees a 1 in exactly that cell. The scan of the whole matrix repeats about 1,000 times per second (more on gaming boards). This is plain digital logic: pull-down resistors, tri-state pins, a few shift registers. Because a mechanical contact bounces open and shut for 1 to 5 ms, the firmware accepts a change only after it stays the same for a debounce time, typically 5 ms, or sooner on fast boards that debounce on the first edge.
hwclocks | The scan loop, the debounce timer and the USB timing all come from a crystal oscillator in the keyboard, commonly 8 to 16 MHz, multiplied by a PLL inside the microcontroller. The clock is a quartz crystal that vibrates at a fixed frequency (accurate to about 20 parts per million) and every operation in the chip is counted in its ticks. USB full-speed signalling at 12 Mbit/s needs a clock accurate to 0.25%, so the controller is locked to the crystal or to the bus itself. Time in the host works the same way: the host has its own oscillators and counters, and the kernel will later stamp this key event with a nanosecond timestamp read from a hardware counter (the TSC on x86). Without agreed clocks, no two chips could exchange a bit.
binary | The firmware now builds a USB HID report, a tiny data structure agreed between all keyboards and all operating systems. The classic boot report is 8 bytes: one byte of modifier bits (Ctrl, Shift, Alt, GUI in one bit each), one reserved byte, and up to six key codes. The key "A" has the HID usage code 0x04, so the report is 00 00 04 00 00 00 00 00. When you release the key, a report of all zeros follows. The usage codes name physical positions, not letters; the letter comes from the layout later. Modern keyboards use a longer report with a bitmap that allows n-key rollover, so any number of keys can be down at once. The encoding is just bytes, packed so that a few bits carry state.
usb | The 8 bytes now have to cross the cable. When you plugged the keyboard in, the host already read its descriptors and learned that it has one interrupt IN endpoint with 8-byte packets. Every poll is a short exchange on two wires, D+ and D−, which carry one differential signal, so noise picked up by both wires cancels. The host sends a token packet: a sync pattern, the IN code, the device address and endpoint number, and a 5-bit CRC. If the keyboard has a report, it answers with a data packet: sync, a DATA0 or DATA1 code, the 8 bytes and a 16-bit CRC, 96 bits in all. The host replies ACK. Bits use NRZI coding, where a 1 means no change of level and a 0 means a change. After six 1s in a row the sender inserts an extra 0, so the receiver always sees edges and keeps its clock locked. At low speed, 1.5 Mbit/s, the data packet lasts about 64 µs; at full speed, 12 Mbit/s, about 8 µs. The alternating DATA0 and DATA1 codes let the host drop a repeated packet when an ACK was lost, so one press is never typed twice.
interrupts | The keyboard cannot talk by itself; USB is host-driven. The host controller polls the keyboard's interrupt endpoint every 8 ms by default (every 1 ms or 125 µs on gaming boards) by sending an IN token. If nothing has changed, the keyboard answers NAK and nothing else happens, which costs the CPU nothing because the controller does this in hardware. When your report is ready, the keyboard answers with the 8 bytes plus CRC and the controller acknowledges. The controller then signals the CPU with an interrupt, a message-signalled write (MSI-X) to the interrupt controller. The CPU stops what it was doing, saves a few registers, jumps to the kernel's interrupt handler and, in a few microseconds, finds out which device spoke. The average wait for the next poll is half the polling interval, 4 ms at 8 ms.
dma | The USB host controller (xHCI) does not hand the 8 bytes to the CPU one by one. The driver set up ring buffers in RAM at boot, and the controller writes completion events into them by DMA, directly over the PCIe bus, without CPU instructions. It then raises one interrupt per batch. In the kernel the interrupt handler does the minimum: it acknowledges the controller and schedules a softirq or a threaded handler to process the ring. This split between a fast top half and a slower bottom half keeps interrupts short and the system responsive. The same pattern, a ring buffer in memory, DMA, and an interrupt, is used by network cards, NVMe disks and GPUs. From the key switch to this point only 5 to 10 ms have passed, mostly waiting for the poll.
linux | The kernel's usbhid driver reads the HID report descriptor (which the keyboard sent at plug-in time) to learn how to interpret the 8 bytes, and finds that usage 0x04 means "A". It translates this into the Linux key code KEY_A = 30 and reports it to the input subsystem as events: an EV_MSC scan code, an EV_KEY with code 30 and value 1 (pressed), and an EV_SYN marker that closes the packet. Each struct input_event is 24 bytes on 64-bit systems, so this press is 72 bytes, with a timestamp. The events are copied into a ring buffer of the device node /dev/input/event3 and any process waiting on it is woken. The kernel itself knows nothing about letters or languages; it deals with key codes. Auto-repeat after about 250 ms is also created at this level.
syscalls | The display server or compositor (Mutter, KWin, Sway, Windows' win32k) holds /dev/input/event3 open, usually through libinput. It sits in an epoll_wait() system call, sleeping. The wake-up makes the scheduler pick it as runnable, which takes a few microseconds if a core is idle, and then it calls read() to copy the 72 bytes from kernel to user space. A system call is a controlled jump into the kernel: the CPU switches mode, checks the arguments, runs kernel code, and returns, costing around 100 to 300 ns plus the work. libinput filters the events: palm rejection, debounce for faulty keyboards, and pointer acceleration for the mouse. Then it hands "key 30 pressed" to the compositor, which must decide which window gets it: the one with keyboard focus.
unicode | A key code is not yet a letter. The compositor uses the xkbcommon library and your keymap (for example "us" or "de" or "in-hindi") to convert key code 30 plus the modifier state (Shift, Caps Lock, AltGr) into a keysym, here "a", or "A" with Shift. Input methods can change it further: dead keys give é, Compose sequences give ©, and for Chinese, Japanese or Hindi, an input method editor collects several keys into a candidate word. The result is a Unicode code point, U+0061 for "a", which is encoded in UTF-8 as one byte, 0x61. Characters outside ASCII take 2 to 4 bytes. The layout, not the hardware, decides what the key means, which is why the same physical key prints "q" on QWERTY and "a" on AZERTY.
sockets | The compositor and the application are different processes, so the key event is sent over a Unix domain socket. In Wayland the compositor writes a wl_keyboard.key message of 24 bytes: an 8-byte header, a serial number, a timestamp in milliseconds, the key code and the state. The client receives the keymap once as a file descriptor to a shared memory file, so only key codes travel on every press. A Unix socket is a kernel buffer between two processes; the message is copied once into the receiver's queue (one memcpy of 24 bytes and no network), which takes a few microseconds. In X11 the same job is done by a socket to the X server, and in a browser or Electron app one more hop crosses to the renderer process.
eventloop | The application, for example a terminal or a text editor, runs an event loop: wait for events, handle one, repeat. It was blocked in poll() on the Wayland socket and the kernel wakes it. The toolkit decodes the message, sends a key-press event to the focused text widget, which inserts "a" into its text buffer at the cursor and marks a rectangle (maybe 10 by 20 pixels) as needing redraw. Nothing is drawn yet; the app schedules a frame for the next display refresh instead of painting immediately, so that many changes are combined in one frame. This work is a few microseconds to a millisecond, depending on how heavy the toolkit is. A busy loop with long handlers is what you experience as a laggy app, because the key sits waiting in the queue.
fourier | Now the glyph is drawn. The font gives the letter "a" as a few Bezier curves (quadratic in TrueType, cubic in CFF fonts) in font units, 1000 or 2048 per em. The renderer scales them to the pixel size, say 14 px, and decides, for each pixel, how much of it the shape covers. A hard on/off decision would look jagged, because the shape contains frequencies finer than the pixel grid can show. Anti-aliasing is therefore a low-pass filter: partial coverage becomes a grey level between 0 and 255. Subpixel rendering goes one step further and uses the separate red, green and blue stripes of the pixel with a small 5-tap filter to triple the horizontal detail. The sampling theorem explains why, and why blurrier results are the price of fewer artefacts. The result is cached as a glyph bitmap, so "a" is rasterized once per size, not once per press.
memhier | Rasterizing every glyph for every frame would waste time, so the text system keeps a glyph atlas: one large texture, say 2048 by 2048 pixels, in GPU memory holding every glyph in use. A press of "a" is nearly free if it is already in the atlas. This is the memory hierarchy at work: the CPU's L1 cache (a few ns) holds the hot glyph lookup table, main memory (about 80 ns) holds the font data, and the GPU's texture cache and VRAM (hundreds of GB/s) hold the atlas. The app draws a small quad that points to the "a" rectangle of the atlas, and the draw call, a handful of bytes, is put into a command buffer. The shared-memory or GPU buffer is passed to the compositor with a file descriptor, never copied.
simt | The compositor combines all windows into the final screen image. It sends the GPU a list of textured rectangles, the windows, and the GPU runs a small shader program over each covered pixel, many pixels in parallel in groups of 32 or 64 threads that execute the same instruction at the same time (SIMT). For a 2560 by 1440 screen that is 3.7 million pixels, each 4 bytes, about 14.7 MB per frame; the GPU only needs to redraw the damaged rectangle, but must still produce a complete image to scan out. The work usually takes 1 to 3 ms. The result is a finished frame in a buffer, queued for the next vertical blank. If the app and compositor miss the frame deadline, the old frame stays on the screen for another 16.7 ms at 60 Hz, which you perceive as lag.
display | The finished frame must now reach the screen at exactly the right moment, and the kernel's display driver (KMS) arranges it. The display controller is a hardware block with its own counters. For 2560 by 1440 at 60 Hz its timing is 2720 pixel slots per line and 1481 lines per frame on the 241 MHz pixel clock, so one line lasts about 11 µs and one frame 16.7 ms. The compositor waits until the GPU's fence says that rendering is complete, then submits an atomic commit: show this buffer on the main plane at the next vertical blank. The driver writes the buffer's address into shadow registers, and the hardware copies them into the live registers only inside the blank, so the scan never reads a half-changed pointer. The kernel then sends a page-flip event with a timestamp, and the compositor uses it to start the next frame. The scan engine reads through a small FIFO; if memory is too slow to refill it, the screen shows an underrun glitch. Your letter waits for this flip: it appears at the first blank after the commit, 8 ms later on average at 60 Hz.
queuesbuf | Finished frames wait in a small queue, a swap chain of two or three buffers. The GPU draws into the back buffer while the display controller scans out the front one, and the two are swapped during the vertical blank. At the next vertical refresh the display controller reads the finished frame buffer from memory by DMA, line after line, and sends it over DisplayPort or HDMI to the monitor as a serial stream. At 2560 by 1440 and 60 Hz that is 14.7 MB times 60, about 880 MB/s, or around 8 to 10 Gbit/s on the cable. The stream is paced by a pixel clock of about 241 MHz, so each pixel gets about 4 ns. Because the monitor scans from the top to the bottom, a change near the bottom of the screen appears up to one frame later than a change at the top; average display latency is about half a frame, 8 ms at 60 Hz and 3 ms at 165 Hz. The monitor's own scaler or timing controller receives the pixels and drives the panel rows one by one.
photonics | The panel turns voltages into light. Each pixel has three subpixels with a thin-film transistor each. In an LCD, a voltage twists liquid crystals between two crossed polarizers and so controls how much of the backlight's white light passes through a red, green or blue filter. In an OLED, the voltage drives current through an organic layer in which electrons and holes recombine and emit photons directly, which also gives faster pixel response, near 0.1 ms. The grey level at the edge of the letter has 256 steps, shaped by a gamma curve. Light leaves the screen at 300,000 km/s and arrives at your eye in a nanosecond. The total latency, key switch to photons, is typically 15 to 40 ms.
perception | The last layer is you. Photons are focused on the retina, where cone cells (about 6 million) absorb them in three types with different sensitivity to red, green and blue light. Retinal circuits compress the signal and send it along the optic nerve to the visual cortex, which recognises the shape as the letter "a" in about 100 to 150 ms. That is slower than all the machinery above, which tells you where the real bottleneck sits. You only notice lag when it exceeds about 50 to 100 ms in typing and when mouse movement is delayed by more than a few frames. Screen designers use this fact: gamma, refresh rate and anti-aliasing are tuned to what the eye can and cannot see, and the same facts are used by video codecs to drop details you would not notice.

## What happens when you run git push | How a few new commits travel to a server and move a branch pointer atomically
git | You run git push origin main. Git first looks in .git/config to turn the name "origin" into a URL, such as https://github.com/org/repo.git or git@github.com:org/repo.git, and reads refs/heads/main to learn which commit you want to publish. If a pre-push hook exists in .git/hooks, it runs now and can veto the push with a non-zero exit code. Nothing has been sent yet. Your repository on disk is a content-addressed database: every commit, directory listing (tree) and file version (blob) is an object stored under .git/objects, named by the hash of its content. A branch is only a 41-byte text file containing a commit hash. A push is therefore a simple idea: make the server's database contain the objects reachable from your commit, then move the server's branch file.
vcs | History in Git is a graph of snapshots. Each commit points to one root tree (the full snapshot of the project) and to its parent commit or commits. To decide what must be sent, Git needs to know what the server already has. That knowledge comes from the server itself in the next step, plus the remote-tracking ref refs/remotes/origin/main that remembers where the server's main was at your last fetch. If you have made 3 local commits since then, the work to ship is those 3 commits, the trees that changed and the file blobs that changed, and nothing else. A commit that changes one file creates about 4 new objects: the blob, the tree of its folder, the root tree and the commit itself. This is why a push of a tiny change is tiny, even in a repository of 10 GB.
tls | For an https:// remote, git runs the transport through libcurl. It resolves the name through DNS, opens a TCP connection to port 443, and performs a TLS 1.3 handshake: the server presents a certificate chain, the client validates it against the system's trust store, and an ephemeral key exchange gives both sides fresh keys. That takes one to two round trips (30 to 150 ms). With an SSH remote, git instead starts the ssh program, which does the key exchange, host-key check and public-key login described in the ssh journey, and then runs git-receive-pack on the server as a remote command. Either way the same Git protocol bytes flow inside an encrypted, authenticated tunnel. Credentials, such as a personal access token or an OAuth token from the credential helper, are sent over this channel and never in plain text.
http | Smart HTTP begins with a GET request to /org/repo.git/info/refs?service=git-receive-pack, with an Authorization header. The reply has content type application/x-git-receive-pack-advertisement and uses Git's pkt-line format: every line starts with 4 hex digits that give its length, for example 003f for 63 bytes. The server lists every branch and tag with the hash it points to, typically 40 bytes of hash plus the ref name, and announces its capabilities after the first line: report-status, delete-refs, side-band-64k, atomic, push-options and the hash algorithm. For a repository with 10,000 tags this answer can be hundreds of kilobytes, which is why big repositories prefer protocol v2 for fetches and trim refs. A 401 or 403 response ends the push here with a message about permissions.
merkle | Git now computes which objects the server lacks. It walks backwards from your new commit through the parent links, stopping at commits whose hashes appeared in the server's advertisement. Because the hash of a commit covers its tree and its parents, and the hash of a tree covers every entry below, the hash of a commit uniquely identifies the entire project at that point (a Merkle tree). If the server has commit X, it is guaranteed to have all of X's trees and blobs, so none of them needs to be sent. The same rule skips any subtree whose hash is unchanged: of a project with 5,000 files, a change to one file creates new trees only along the path from that file to the root, perhaps 3 to 6 objects. The client does this with git pack-objects --revs --thin, a stream of only the missing objects.
hashfn | Every object ID is a hash of the object's type, length and content: SHA-1 (20 bytes, 40 hex digits) in most repositories, and SHA-256 in repositories that use the newer format. Hashing is what makes sending safe. The receiver recomputes every hash from the bytes it receives, so it cannot be tricked into accepting a corrupted object, and the sender cannot send a different file under the same name. Git's SHA-1 uses a hardened implementation (SHA-1DC) that detects the known collision attacks. An accidental collision between two different objects is not a practical risk. Hashing is also fast: about 1 GB/s per core, so even a pack of 100 MB is hashed in 100 ms, and the cost is dominated by the network.
encoding | The objects are packed into a packfile, a compact stream: a 12-byte header (the text PACK, a version and an object count), the objects, and a 20-byte trailing checksum. Each object is compressed with zlib (deflate). Most clever of all is delta compression: if a file is a small edit of an older version, Git stores only the edit as copy and insert instructions against the base object. A thin pack may use as its base an object that the server already has, which makes it smaller still. A 200 KB source file with a 3-line change becomes a delta of perhaps 200 bytes, which zlib shrinks a little more. For one small commit the whole pack is 300 to 2,000 bytes, and the request fits into a single TCP segment.
rpc | The client sends a second request, POST /org/repo.git/git-receive-pack. The body begins with the command lines in pkt-line format: the old hash (what the client believes the branch points to), the new hash and the ref name, for example 0000...0000 or a1b2... then c3d4... refs/heads/main, followed by a NUL byte and the list of capabilities it chose, such as report-status side-band-64k atomic. A flush packet 0000 ends the command list. The packfile follows directly. For big pushes the client uses chunked transfer encoding, because it does not know the final size, and the server may answer 100 Continue first. For a push over 1 MB the client first sends a small probe so that a bad credential does not waste the upload. TCP slow start matters now: a cold connection can carry only about 14 KB in its first round trip.
loadbalancing | On the server side the request arrives at a load balancer in front of the hosting service. It terminates TLS, checks DDoS and rate limits, and routes the request to a front-end server by hashing the repository name or consulting a table, so that all pushes to one repository meet the same set of storage servers. A large hosting service stores each repository on three replica servers chosen from thousands. The front end authenticates the token, asks the permission service whether the user may write to this branch (branch protection can require pull requests or reviews), and only then starts a git receive-pack process, connecting its standard input to the request body. The authorization check usually takes 5 to 20 ms in total, and a wrong answer here is a security incident, so it is applied before a single byte is stored.
process | git receive-pack is an ordinary process, spawned with fork and exec, with the pack on its standard input. It starts git index-pack --stdin --fix-thin (or git unpack-objects when there are fewer than 100 objects, which writes loose files). index-pack reads the stream, inflates each object, resolves deltas by finding their bases, and computes the SHA-1 of every object. For thin packs it appends the missing base objects to make the pack self-contained. It checks the trailing checksum, and then a connectivity check walks from the new tip to be sure that no object is missing, because accepting a commit whose parent or tree does not exist would corrupt the repository. Many servers also run fsck-style checks to reject malformed objects. For a small push the whole step takes 10 to 50 ms.
filesystems | Objects go first into a quarantine directory such as objects/incoming-AbC123/, so that rejected pushes never pollute the real repository. receive-pack writes the pack as pack-<hash>.pack with an index file pack-<hash>.idx next to it. The index is a sorted table of the object hashes with offsets, built with a 256-entry fan-out table keyed by the first byte, so lookups are a binary search in a small range. Then the pre-receive hook runs (enforcing policy such as no secrets, commit-message rules, or size limits), and if it passes, the files are moved into the objects/pack directory with rename(), an atomic operation within one file system. Old packs are merged into bigger ones later by git gc or a maintenance job, otherwise a repository with thousands of small packs gets slow.
fsync | Before it says "ok", the server makes the data durable. Git fsyncs the new pack and its index (core.fsync controls this, and recent versions sync pack files by default), then the containing directory, so that a power loss cannot leave a ref pointing at objects that were never written. Without this order, a crash can create the worst corruption in a repository: a branch that points to a missing commit. A single fsync on an SSD costs 0.1 to 1 ms, on a spinning disk 8 to 15 ms; large hosting services use storage with a battery-backed or capacitor-backed cache to make it cheaper. The order matters more than the speed: objects first, then the ref. Only after the data is stable does the server start moving the branch.
occ | Updating the branch uses optimistic concurrency. receive-pack creates refs/heads/main.lock with O_EXCL, so only one process at a time can hold it, reads the current value of main and compares it with the old hash from your command. If it matches, it writes the new hash into the lock file and renames it over refs/heads/main, one atomic step. If somebody else pushed in the meantime, the current value differs from your "old", and the server answers "ng refs/heads/main non-fast-forward" or "fetch first". Git never overwrites the other person's work silently; you must fetch, merge or rebase and push again. This is the same compare-and-swap idea that databases and table formats use: do the work without locks, and make only the final switch atomic. Conflicts are rare, so the cheap optimistic path wins almost every time. A force push only changes the rule: --force-with-lease still asserts the old value you saw, which protects against surprise.
replication | A hosting service never trusts one disk. Before it acknowledges the push, the front end sends the new objects and the ref update to the other replicas, and requires a majority (for example 2 of 3) to confirm. If one replica is down, the push still succeeds with a quorum and the lagging replica repairs itself later. A ref update that applied on only one server would be a lost write if that server died. Different branches can be updated independently, but one push with --atomic updates all its refs or none. This adds one more network round trip of about 1 ms within a data center, which is a small price for surviving a disk, a machine or a rack failing.
pubsub | The server sends back a report through the side-band channel: unpack ok, then ok refs/heads/main, plus text lines that your client prints with the prefix "remote:" (for example the link to open a pull request). Your client then updates refs/remotes/origin/main to the new hash, and prints a line like a1b2c3d..e4f5a6b main -> main, with counters such as "Writing objects: 100% (4/4), 412 bytes". On the server, the push is published as an event to subscribers: the web interface refreshes the branch, webhooks fire (an HTTP POST of a few kilobytes of JSON to each URL), and integrations, chat bots and the search indexer receive the event from internal queues. The push is one write that many independent systems react to.
cicd | The most important subscriber is CI. The webhook or internal event starts a pipeline: a scheduler picks the commit, allocates a runner (a container or a VM), clones the repository by fetching just that commit (a shallow fetch, often 1 to 5 seconds), restores dependency caches keyed by a hash of the lock file, and runs build and test jobs. Each job reports its status back to the commit, shown as a green or red mark next to the hash. Deployment tools may promote the commit through staging to production, and pull-request rules can block a merge until required checks pass. So the end of git push is the beginning of a long chain: a pointer moved on a distant disk, and minutes later your change may be running in production.
birthday | One last question is why a 160-bit hash can name every object safely. If you pick N random objects among 2^160 possible names, the chance that any two collide is about N squared divided by 2^161 (the birthday bound). With a billion objects, roughly 2^30, that is 2^60 over 2^161, about 2^-101, far below the chance of a cosmic ray flipping a bit in memory. An attacker is a different case, which is why Git moves toward SHA-256 and detects crafted SHA-1 collisions. This arithmetic is the reason content addressing works without any central authority handing out IDs: two people on two continents can create commits at the same moment, and the names still never clash in practice. The same bound also tells you how much room a short hash has: an abbreviated 7-hex-digit name has only 28 bits, so in a repository with about 20,000 objects, collisions between abbreviations are already likely, and Git lengthens the abbreviation automatically.

## What happens when you run docker run nginx | From a CLI call to an isolated process serving HTTP, on one shared kernel
docker | The docker command is only a thin client. It parses docker run -d -p 8080:80 nginx, expands "nginx" to docker.io/library/nginx:latest and talks to the Docker daemon (dockerd) with HTTP requests over a Unix socket, /var/run/docker.sock. The daemon is a long-running root process. The client sends POST /containers/create with a JSON body of a few hundred bytes (image, port mappings, limits) and later POST /containers/{id}/start. Who may write to that socket is who is effectively root on the machine, which is why the docker group is dangerous. The daemon itself delegates the real work: it asks containerd to manage images and container lifecycle, and containerd starts a small shim process and the low-level runtime runc. Nothing here is virtualized; "container" is a naming convention for a normal Linux process that has been given a restricted view of the system.
sockets | The Unix domain socket is a file in the filesystem, but communication through it does not touch a disk or a network card. The client's connect() creates a pair of kernel buffers between the two processes; write() copies the HTTP request into the receiver's buffer and read() copies it out, in a few microseconds. The kernel even passes the caller's user and group IDs along with the connection (SO_PEERCRED), which lets a daemon know exactly who is asking. The same mechanism connects dockerd to containerd (gRPC over /run/containerd/containerd.sock) and containerd to the shim. Because a Unix socket is just a file, access is controlled with ordinary file permissions, mode 660 owned by root:docker. Compared with TCP over loopback, it saves the protocol work of segmentation, checksums and congestion control.
http | The image is not on this machine, so dockerd pulls it from the registry using plain HTTPS APIs. It first asks for a token (GET auth.docker.io/token?service=registry.docker.io&scope=repository:library/nginx:pull), then GET /v2/library/nginx/manifests/latest at registry-1.docker.io. The answer is a manifest list, a small JSON of about 1 KB with one entry for each platform (linux/amd64, linux/arm64 and so on). The daemon picks the entry matching its CPU, downloads that manifest, and finds the digest of the image config and the digests of about 6 to 8 layers. Each blob is fetched with GET /v2/library/nginx/blobs/sha256:... The registry may answer with a 307 redirect to a CDN, and the daemon downloads up to 3 layers in parallel by default. The registry protocol is just HTTP with resumable range requests.
merkle | Everything in the image is addressed by the SHA-256 digest of its bytes. The manifest names the config blob and the layer blobs by digest; the manifest itself has a digest, and "nginx:latest" is only a mutable tag that points to one such digest. If you pull by digest (nginx@sha256:...), you get exactly the same bits forever, and the daemon verifies each downloaded blob by hashing it, so a corrupted or swapped layer is rejected. Because layers are named by content, two images that share a base layer share one copy on disk and one download: the second nginx-based image you pull often needs only a few megabytes. The same Merkle idea appears in Git, in IPFS and in table formats such as Delta; here it makes a 190 MB image cheap to cache and safe to distribute.
encoding | Each layer travels as a compressed tar archive, usually gzip (about 3:1 on typical Linux files) or zstd. The nginx image has a Debian base layer of about 30 MB compressed, plus layers for the nginx package, config files and entry-point scripts; the whole image is around 70 MB to download and 190 MB unpacked. The daemon decompresses each layer on the fly while verifying two digests: the compressed digest (what the registry has) and the DiffID (the digest of the uncompressed tar), which lets it detect corruption and share layers across registries. Decompression runs at about 300 MB/s per core and writing runs at disk speed, so pulling is limited by the network, typically 5 to 20 seconds for a first pull and 0 seconds when the image is already cached.
filesystems | Each unpacked layer lives in its own directory under /var/lib/docker/overlay2/. To run the container, the daemon mounts an overlay filesystem: a stack of read-only lower directories (the layers, top to bottom) and one empty writable upper directory. The merged view shows the union; a file that exists in several layers appears once, from the highest layer, and a deleted file is hidden with a "whiteout" marker. The first time a container writes to a file from a lower layer, the kernel copies the whole file up into the upper directory (copy-on-write), which can be slow for big files. When the container is removed, the upper directory is thrown away, and the image layers stay untouched. That is why container storage is ephemeral, and why databases use volumes (bind mounts of a host directory) to keep their data.
containers | The runtime follows the OCI specification: a bundle with a root filesystem (the merged overlay) and a config.json of a few KB that lists the process to run, environment, mounts, namespaces, cgroup limits, capabilities and the seccomp profile. containerd writes this file and starts runc. runc is a short-lived program, in Go with a small C helper, that creates the isolation, starts the process, and exits; a tiny shim stays as the process's parent so that the daemon can be restarted without killing the containers. The ideas are older than Docker (chroot, FreeBSD jails, Solaris zones, LXC); Docker made them easy by adding the image format and a good workflow. The cost is small: no guest operating system boots, so a container starts in about 100 to 500 ms and uses only the memory of its processes.
nscgroups | runc calls clone() with namespace flags: CLONE_NEWPID (the process sees itself as PID 1 and cannot see host processes), CLONE_NEWNS (its own mount table), CLONE_NEWNET (its own network stack), CLONE_NEWUTS (its own host name), CLONE_NEWIPC (own shared memory and semaphores) and often CLONE_NEWUSER. Namespaces control what a process can see. Control groups (cgroups v2) control what it can use: runc creates a directory such as /sys/fs/cgroup/system.slice/docker-<id>.scope, writes the PID into it and sets files like memory.max (for example 512 MB) and cpu.max ("50000 100000" means half a core). Kernel code consults these structures on every allocation and on every scheduling decision. Both mechanisms add only a pointer lookup to the normal path, which is why containers cost almost nothing at runtime.
syscalls | Isolation also needs to restrict what the process may ask the kernel to do. runc drops most Linux capabilities, keeping 14 of about 40 (for example it removes CAP_SYS_ADMIN and CAP_NET_ADMIN), so even uid 0 inside the container cannot mount disks or reconfigure the host network. It then installs a seccomp-bpf filter: a small program that the kernel runs for every system call, comparing the call number to a list. Docker's default profile allows about 300 syscalls and blocks around 40 to 50 dangerous ones, such as reboot, kexec_load, mount and the key-ring calls. A blocked call returns EPERM or kills the process. The filter costs tens of nanoseconds per call. All containers still share one kernel, so a kernel bug can break the walls; this is the main security trade-off against virtual machines.
nat | The new network namespace is empty, so Docker builds a network. It creates a veth pair, a virtual Ethernet cable with two ends, puts one end inside the container as eth0 and attaches the other to the bridge docker0 on the host. The container gets an address from 172.17.0.0/16, for example 172.17.0.2, with the bridge 172.17.0.1 as its default gateway. For outgoing traffic, an iptables (or nftables) MASQUERADE rule in the NAT table rewrites the private source address to the host's address and remembers the connection in conntrack. For -p 8080:80 it adds a DNAT rule: packets to host port 8080 are rewritten to 172.17.0.2:80. Every packet through these rules pays a lookup of a few hundred nanoseconds; with thousands of rules, linear iptables chains become a bottleneck, which is one reason big clusters moved to eBPF.
ethernet | Inside the host, a packet from the outside world to your container is an Ethernet frame. The physical NIC receives it, DMA puts it into memory, and the kernel's IP stack sees destination port 8080, applies the DNAT rule in the PREROUTING hook and finds that 172.17.0.2 is reachable through docker0. The bridge works like a software switch: it keeps a table of MAC addresses and, for a frame to the container's MAC, forwards it to that veth port, where the frame appears inside the container's namespace as if it had arrived on a real card. The bridge learned the MAC addresses through ARP. A veth hop is a memory copy of at most 1500 bytes, adding about 5 to 20 µs, and no wire is involved; "network virtualization" here is just software pointers.
process | Now runc executes the container's main program. In the new namespaces it calls pivot_root() so that the overlay becomes "/", unmounts the old root, mounts /proc, /sys and /dev as private views, sets the host name, applies the cgroup and seccomp settings, and finally calls execve() on the entry point. The nginx image's ENTRYPOINT is /docker-entrypoint.sh, a shell script that runs the scripts in /docker-entrypoint.d (such as one that renders templates into nginx.conf) and then uses exec to replace itself with nginx -g "daemon off;". Because of exec, nginx becomes PID 1 in the container and receives signals from docker stop: SIGTERM first, SIGKILL after 10 seconds. PID 1 has special duties, like reaping orphaned child processes, which is why small init programs (tini) are sometimes added.
nginx | nginx starts as a master process that reads /etc/nginx/nginx.conf, opens the listening socket on port 80 and then forks one worker per CPU core, as set by worker_processes auto. Each worker runs an event loop on epoll and accepts connections on the shared socket, handling thousands of connections without a thread each. When your first request arrives (the packet that went through DNAT, the bridge and the veth), the worker reads it, maps the URL / to /usr/share/nginx/html/index.html and answers with the 615-byte Welcome to nginx page using sendfile. The access log lines go to /dev/stdout, which the image links to the container's log pipe. The first response usually leaves about 300 to 600 ms after you pressed Enter, if the image was already on disk.
observability | The container's stdout and stderr are pipes read by the shim, which hands the lines to dockerd; the default json-file logging driver appends each line as a JSON record to /var/lib/docker/containers/<id>/<id>-json.log, and docker logs reads the same file. The daemon also collects metrics from the cgroup files (memory.current, cpu.stat, io.stat) and exposes them to docker stats and to monitoring agents such as cAdvisor or Prometheus exporters. Because everything is a normal process in a normal cgroup, the standard Linux tools work on it: ps on the host shows nginx with a different PID than inside, strace and perf attach by host PID, and the kernel's OOM killer picks the process if it exceeds memory.max. In production the same data feeds dashboards and alerts.
virtualization | A virtual machine solves a similar problem differently: a hypervisor uses CPU hardware support (VT-x, AMD-V) to run a whole guest kernel with its own memory map, taking 1 to 30 seconds to boot and about 100 MB of RAM for the kernel itself. A container skips the guest kernel and so starts 10 to 100 times faster, but its isolation is only as strong as the shared host kernel's code. For multi-tenant clouds that run code from strangers, providers therefore wrap containers in lightweight VMs (Firecracker, Kata Containers) or user-space kernels (gVisor), buying hardware-enforced walls at a cost of tens of milliseconds. Your docker run nginx took the cheap route: one process, a view, some limits, and a pointer to the layers on disk.

## What happens when you run kubectl apply and a pod starts | From a YAML file to a running container, through a chain of independent controllers
kubernetes | You run kubectl apply -f web.yaml, where the file declares a Deployment with 3 replicas of an nginx container. kubectl is only a client. It reads ~/.kube/config to find the API server address (for example https://10.0.0.1:6443) and your credentials, which are a client certificate, a bearer token, or an exec plugin that fetches a short-lived cloud token. It then asks the server which resource types exist (a discovery document, cached in ~/.kube/cache for 10 minutes), so that it can map "kind: Deployment, apiVersion: apps/v1" to the URL /apis/apps/v1/namespaces/default/deployments. The key idea of Kubernetes is that you do not tell it what to do; you write down the desired state, and the system works until the real state matches. Everything below is the machinery that achieves that.
iac | kubectl reads the YAML, converts it to JSON, and checks it against the OpenAPI schema (so a typo such as replcas fails before any request). With client-side apply it fetches the live object, if one exists, and computes a three-way merge between three versions: the last configuration you applied (stored in the annotation kubectl.kubernetes.io/last-applied-configuration), your new file, and the live state. Fields that you removed from the file are deleted, and fields set by other controllers, such as an autoscaler's replica count, are left alone. With --server-side the server tracks which manager owns which field instead. The result is a PATCH or POST request with a body of about 1 to 2 KB. This declarative style is what lets you rerun the same command ten times and get the same result.
mtls | The request goes out over HTTP/2 on a TLS 1.3 connection to the API server. The server presents a certificate signed by the cluster CA, which kubectl has in its kubeconfig, so you know that you are talking to the real control plane. If you authenticate with a client certificate, this is mutual TLS: the server checks your certificate against the same CA and takes your user name from its subject (CN=alice) and your groups from the organization fields. The handshake takes one round trip, and kubectl's connection is reused for the following calls. Inside the cluster all control-plane components, the API server, etcd, the kubelets and the controllers, authenticate each other the same way, and certificates are rotated automatically before they expire. A leaked certificate with no revocation is a real risk, so lifetimes are kept short.
apigateway | The kube-apiserver is the single front door to the cluster state, and nothing else touches the database. Each request goes through a fixed chain. First authentication turns the credential into an identity. Then authorization asks RBAC rules whether this identity may "create deployments in namespace default". Then mutating admission plugins and webhooks may change the object: set defaults (a missing imagePullPolicy becomes IfNotPresent), add a service-account token volume, or inject a sidecar. The object is validated against its schema. Then validating admission checks policies, such as Pod Security rules or a CEL policy that forbids the "latest" tag. Only an object that passes everything is stored. Each stage takes microseconds to a few milliseconds, except external webhooks, which add a network call each and can make the whole cluster slow or unavailable if they hang.
etcd | The accepted Deployment is serialized as protobuf (about 1 to 2 KB) and written to etcd under the key /registry/deployments/default/web. etcd is a small, strongly consistent key-value store, usually run as 3 or 5 members. Every key has a revision number, a cluster-wide counter that increases with each write, so the API server can express "give me everything that changed since revision 41877". The API server stores the object with a compare-and-swap on the revision it read, which is how two people applying at the same moment do not overwrite each other: the second one gets a 409 Conflict and must retry. etcd keeps its data in a memory-mapped B+tree (bbolt) and recommends fast SSDs and less than 8 GB of data, because everything in the cluster, every Pod, Secret and Event, lives here.
raft | A write to etcd is not final until a majority agrees. The leader member appends the entry to its Raft log and sends AppendEntries messages to the two followers in parallel; when at least 2 of 3 have the entry on their disks, the entry is committed, and the leader applies it to the database and answers. That costs one network round trip inside the cluster (0.2 to 1 ms) plus one disk flush on the slowest of the two fastest members. If the leader dies, the followers hold an election within about 1 second, and no committed write is lost, because any new leader must have won votes from a majority that contains a copy of every committed entry. That is also why clusters have odd member counts: 3 tolerate 1 failure and 5 tolerate 2, while 4 still tolerate only 1.
wal | Before the leader or a follower acknowledges an entry, it appends it to the write-ahead log, a file written strictly sequentially, and calls fdatasync() so the bytes are on stable storage. This is the durability step, and it dominates the cost: a good NVMe SSD does it in about 100 µs to 1 ms, a cloud network disk in 2 to 10 ms, and a slow disk can reach 50 ms. etcd's own documentation says the 99th percentile of this flush must stay below 10 ms, otherwise heartbeats are missed and leaders change. Periodically etcd takes a snapshot and trims the WAL. After the commit, the API server returns 201 Created and kubectl prints deployment.apps/web created. Elapsed time since you pressed Enter is about 50 to 300 ms, and not a single container has started yet.
reconcile | The Deployment controller, part of kube-controller-manager, has been listening for changes. Through an informer it made one LIST at startup and then holds a long-lived WATCH connection to the API server (an HTTP response that streams JSON events as they happen). The API server keeps a watch cache, fed by one watch on etcd, so thousands of watchers do not hit the database. Within a few milliseconds the controller receives an ADDED event for the Deployment, puts its key in a rate-limited work queue, and a worker runs the reconcile function: compare the desired state (a Deployment with a pod template) with the actual state (no ReplicaSet), then create a ReplicaSet named web-<hash of the template>. Controllers are level-triggered, not edge-triggered: if they miss an event, the next resync still finds the difference.
queuesbuf | The work queue inside every controller is a small data structure with a strong set of rules. It deduplicates keys, so that 100 events for the same object cause one reconcile; it allows a single worker on a key at a time; and failed items return after an exponential backoff, from 5 ms up to 1000 s. A shared informer cache (an in-memory copy of all objects of a kind) lets controllers read their inputs without calling the server. Next, the ReplicaSet controller sees the new ReplicaSet and, as it has 0 pods but wants 3, sends three POST requests to create Pod objects, each with an owner reference back to the ReplicaSet (so that deleting the owner garbage-collects the pods). The pods now exist in etcd with status Pending and an empty spec.nodeName: they are only records, and no machine knows about them.
orchestration | The kube-scheduler watches for Pods with no node. For each one it runs a scheduling cycle. Filtering removes nodes that cannot work: not enough unreserved CPU or memory (it sums the pod's resource requests against the node's allocatable amount), taints the pod does not tolerate, mismatched node selectors or affinity, no volume available in that zone. Scoring ranks the remaining nodes, for example by spreading replicas across zones and preferring balanced utilization. The best node wins, and the scheduler writes a Binding object, which sets spec.nodeName in etcd through the API server. One cycle takes roughly 1 to 10 ms, and a large cluster schedules hundreds of pods per second. The scheduler does not start anything; it only writes down a decision. The node's own agent must see it.
grpc | On the chosen node, the kubelet has a watch on pods whose spec.nodeName is its own name. It receives the update, and its sync loop decides what to do. It speaks to the container runtime (containerd or CRI-O) over the Container Runtime Interface, a gRPC API on a local Unix socket: RunPodSandbox, PullImage, CreateContainer, StartContainer. gRPC uses HTTP/2 with protobuf messages, so a call is a few hundred bytes and about 100 µs of overhead. The kubelet also mounts volumes, fetches Secrets and ConfigMaps from the API server and writes them as files, and sets up the cgroup tree for the pod, so that the CPU request becomes a share weight and the memory limit becomes memory.max. It reports each step back to the API server by patching the pod's status.
nscgroups | The runtime first creates the pod sandbox: a tiny "pause" container whose only job is to hold the Linux namespaces (network, IPC, UTS) that all containers of the pod share. This is why containers in one pod can talk to each other over localhost and why they share an IP address. Next it pulls the nginx image if the node does not have it (about 70 MB, 5 to 20 seconds, or zero if cached), unpacks the layers into an overlay filesystem, and starts the container in its own PID and mount namespaces and the cgroup the kubelet prepared, with the seccomp profile and capabilities configured. These are the same kernel features as in docker run; Kubernetes did not invent any isolation, it schedules and wires up the same primitives for thousands of nodes. Starting the container itself takes about 100 to 300 ms.
iprouting | The kubelet's runtime now calls the CNI plugin (Calico, Cilium, the cloud provider's plugin, or flannel) with ADD. The plugin creates a veth pair, puts one end in the pod's network namespace as eth0, and assigns an IP from the node's pod range, such as 10.244.1.7, so that every pod gets its own cluster-wide routable address and needs no NAT between pods. To reach pods on other nodes, the plugin either programs routes (each node announces its pod subnet, often with BGP), or wraps packets in an overlay such as VXLAN (50 bytes of extra header, so the pod's MTU is lowered to about 1450). Cilium does the forwarding with eBPF programs instead of iptables. The IP is reported to the API server in the pod's status.podIP. This takes 10 to 100 ms.
control | The kubelet runs the probes defined in the pod spec. A readiness probe is, for example, an HTTP GET / against 10.244.1.7:80 every 10 seconds (the period is configurable); a liveness probe uses the same mechanism to restart a container that is stuck. As soon as the readiness probe succeeds, the kubelet patches the pod's Ready condition to True. This is a feedback loop in the sense of control theory: measure the actual state, compare it to the setpoint, act on the difference. If a container crashes, the kubelet restarts it with an exponentially growing delay (10 s, 20 s, up to 5 minutes: CrashLoopBackOff); if a node dies, the controller marks its pods for deletion after a timeout (5 minutes by default) and the ReplicaSet creates replacements elsewhere.
loadbalancing | A Ready pod becomes part of a Service. The EndpointSlice controller watches pods that match the Service's label selector and adds the pod's IP to an EndpointSlice object (up to 100 addresses per slice). On every node, kube-proxy (or Cilium) watches the slices and programs the kernel: in iptables mode, a chain of rules per Service that picks one backend at random with a probability of 1/n, rewriting the destination from the virtual ClusterIP (10.96.0.15:80) to a pod IP (DNAT); in IPVS or eBPF mode, a hash table lookup in constant time. Cluster DNS (CoreDNS) answers web.default.svc.cluster.local with the ClusterIP. A client in another pod can now reach nginx through the name, and traffic is spread over the three replicas. The whole journey took 2 to 10 seconds with a cached image.
observability | At every stage the components wrote Events to the API server: Scheduled, Pulling, Pulled, Created, Started. kubectl describe pod shows them in order, with timestamps, and they are your first debugging tool: ImagePullBackOff means the registry or credentials failed, Pending with FailedScheduling means no node fits, CrashLoopBackOff means the process exits. Metrics follow, too: the kubelet exposes cAdvisor data, the API server and etcd expose Prometheus metrics (request latency histograms, watch counts, etcd_disk_wal_fsync_duration_seconds), and logs come from the container's stdout files on the node. Because every component is a controller acting on shared state in one database, a person with kubectl get -w sees the same events that the system saw, which is what makes Kubernetes understandable even when it is complex.

## What happens when a SQL transaction commits in PostgreSQL | From a COMMIT message to a durable log record, and why the data pages can wait
sql | Your application sends three statements: BEGIN, UPDATE accounts SET balance = balance - 100 WHERE id = 1, and COMMIT. Over a TCP socket (or a Unix socket) PostgreSQL's wire protocol frames each message as one type byte, a 4-byte length and a payload. A simple query is 'Q' + length + the SQL text + a zero byte, so the UPDATE is about 60 bytes. The server answers with CommandComplete ('C', "UPDATE 1"), then ReadyForQuery ('Z', 6 bytes in total, with a status flag that says whether you are inside a transaction). Drivers usually use the extended protocol (Parse, Bind, Execute), which sends the statement once with placeholders and then only parameters, saving parsing time. Each round trip costs network latency, 0.2 ms in a data center, which is why chatty code that sends 100 statements one by one is slow even if each one is fast.
process | PostgreSQL gives every client connection its own operating-system process. The postmaster listens on port 5432, accepts the connection, forks a backend process, and lets it do the authentication (SCRAM-SHA-256 password check or a certificate). A backend takes about 5 to 10 MB of private memory and 1 to 5 ms to fork, which is why applications use a pool such as PgBouncer instead of opening a connection per request. All backends share one big region of memory, created at start-up with shared memory: shared_buffers (typically 25% of RAM), the lock tables, and the WAL buffers. Processes were chosen over threads for isolation, so that a crash of one backend is contained, although the postmaster restarts everything after a crash because shared memory may be corrupt. From here on your session is one process executing your SQL.
parsing | The backend receives the text of the UPDATE and runs it through a lexer and a grammar written for Bison, which produces a raw parse tree. The analyzer then looks up "accounts" and "balance" in the system catalogs (themselves ordinary tables, cached in memory), checks types, resolves the "-" operator to int8 minus, and builds a query tree. The rewriter expands views and rules, and the planner takes over. Parsing and analysis of a simple statement take 20 to 100 µs. If you use prepared statements, this work is done once and the saved result is reused. Errors such as a missing column or a type mismatch are caught here, before any data is touched, and abort the current transaction so that every later statement fails until ROLLBACK.
queryopt | The planner chooses how to find the row. With a WHERE clause on id and a primary key index, it compares the estimated cost of a sequential scan (read all pages of the table, cost proportional to its size) against an index scan (read about 3 to 4 index pages plus one table page). Costs come from statistics collected by ANALYZE: the number of rows, a histogram of values, and the fraction of distinct values. For this table with 10 million rows the index scan costs about 8 cost units against 160,000 for the full scan, so the plan is Update on accounts, Index Scan using accounts_pkey. A planning failure, usually because the statistics are stale, is the most common reason a good query suddenly becomes slow. EXPLAIN shows the plan without running it.
btree | The executor opens the primary-key index, a B+tree whose nodes are 8 KB pages. With 10 million keys of 8 bytes and a fan-out of a few hundred per page, the tree has 3 levels: a root page, a middle level and leaf pages. The search reads the root, picks the child by binary search among its keys, goes down, and reaches a leaf entry that holds the key 1 and the tuple identifier (block 4521, offset 7) of the row in the table. That is 3 page accesses to find one row among 10 million, and the upper levels are almost always already in memory. B-trees are used because they keep sorted order, work well with block devices (a page is a disk read) and stay balanced under inserts and deletes through page splits.
pagecache | The table page, block 4521 of the file base/16384/16397, must be in shared_buffers before it can be changed. The backend hashes the page's identity (relation, block number) into the buffer table, finds the slot and pins it so it cannot be evicted. If the page is not there (a miss), it picks a victim page with a clock-sweep algorithm, and reads 8 KB through read(), usually served from the operating system's page cache, which makes it a second layer of caching, in about 5 µs; from an SSD it takes 50 to 100 µs, from cloud block storage 0.5 to 1 ms. A hit costs about 100 ns. The backend takes a lightweight lock on the buffer in exclusive mode, so no other backend can change the page while this one does. A high hit ratio, above 99%, is the first thing to check in a healthy OLTP database.
mvcc | PostgreSQL never overwrites a row in place. The UPDATE creates a new version of the tuple and marks the old one as dead for later transactions. Every tuple has a 23-byte header with xmin (the transaction that created it) and xmax (the transaction that deleted or updated it). The transaction gets a 32-bit transaction ID when it first writes, say 7,501,233. The old version gets xmax = 7501233; the new version gets xmin = 7501233 and is placed in the same page if there is room (a heap-only tuple, so no index change is needed). Readers that started earlier still see the old version, with no locks, because each looks at its own snapshot. Dead versions pile up until autovacuum removes them. That is the price of readers never blocking writers, and why long-running transactions cause table bloat.
locks | Two sessions must not update the same row at once. When the UPDATE finds the target tuple, it checks xmax. If another in-progress transaction already deleted or updated it, our backend waits on that transaction's ID lock, in the lock manager's hash table in shared memory, until it commits or aborts. After a commit, a READ COMMITTED transaction re-checks the WHERE condition against the newest version and proceeds; a REPEATABLE READ transaction would instead fail with "could not serialize access". Row locks are recorded in the tuple header itself (xmax plus flag bits), not in a big memory table, so locking a million rows needs no extra memory. Short internal locks protect buffers and the lock table. Deadlocks are found by a detector that runs after deadlock_timeout (1 s by default) and aborts one victim.
isolation | What rows may this transaction see? In READ COMMITTED mode (the default) each statement takes a new snapshot: the list of transaction IDs that were in progress at that moment, with the lowest still-running ID and the next ID to be assigned. A tuple version is visible if its xmin committed before the snapshot and its xmax did not. In REPEATABLE READ, one snapshot is taken at the first statement and held to the end, so repeated reads agree, and in SERIALIZABLE the system also tracks read-write dependencies (SSI) and aborts a transaction that would create a cycle. Taking a snapshot costs about a microsecond. The isolation level you pick decides which anomalies, such as non-repeatable reads, phantoms or write skew, your application must handle.
wal | Before the page in memory is changed, the backend writes a WAL record. This is the rule of write-ahead logging: the log must reach disk before the modified data page may. The record for our update is small: a header of 24 bytes (length, transaction ID, previous record pointer, type, checksum) plus around 50 to 100 bytes of data, such as the block reference and the new tuple's changed fields. The first change to a page after a checkpoint also logs a full copy of the 8 KB page (full_page_writes) to protect against torn writes. The record is copied into the WAL buffers (16 MB, in memory) and gets a log sequence number, LSN, its byte offset in the infinite log. Only now is the buffer page changed and marked dirty. The data file is not written; the log is the truth.
fsync | COMMIT writes a commit record of about 30 bytes into the WAL buffer, then calls XLogFlush up to that record's LSN: write() the buffered WAL bytes to the current 16 MB segment file in pg_wal, then fdatasync() to force them to stable storage. Only when the call returns does the backend report success to the client. This single flush is the cost of durability and takes 20 to 100 µs on an enterprise NVMe disk with a protected write cache, 1 to 2 ms on a consumer SSD or a cloud volume, and about 8 ms on a spinning disk. If many sessions commit at the same time, one flush covers all of them (group commit), so throughput reaches tens of thousands of commits per second. With synchronous_commit = off, the flush is delayed by up to 3 times wal_writer_delay (200 ms by default): faster, but you can lose the last few transactions in a crash.
fsjournal | The file system must not undermine the WAL. PostgreSQL pre-allocates and zero-fills each 16 MB WAL segment, and recycles old segments by renaming them, so that fdatasync only has to flush data and not the file's size or block map, which would add another journal write. On ext4 or XFS, the journal records metadata changes first; the file system writes its own little write-ahead log, using the same idea, to stay consistent after a power cut. Using fdatasync instead of fsync skips timestamp updates. If the file system lied about fsync, or a RAID controller with a volatile cache ignored flush requests, the database would be corrupt after a crash though everything seemed fine, which is why pg_test_fsync exists, and why in 2018 a fsync error-handling bug (fsyncgate) made the project change how it reacts to a failed flush: it now panics instead of retrying.
storagedev | At the bottom the flush reaches the SSD. The drive's controller must make the data survive power loss before acknowledging. Enterprise drives have capacitors that keep power long enough to write the DRAM cache into NAND; so a flush can be acknowledged from the cache in tens of microseconds. Consumer drives often have to program the flash itself before they can acknowledge, or lie about it, and their latency is 1 to 2 ms. NAND flash cells cannot be rewritten in place: a page of 4 to 16 KB is programmed (a few hundred µs), and a block of hundreds of pages is erased as a whole (ms). So the controller appends the small sequential WAL writes into fresh pages, which is the friendliest pattern for flash. Sequential logging is the reason a database can commit quickly even on slow random-write media.
replication | If the cluster has a synchronous standby (synchronous_standby_names), the commit is not finished yet. A walsender process streams the WAL bytes over TCP to the standby, whose walreceiver writes and flushes them in its own pg_wal and reports back the flushed LSN. The primary's backend waits until that LSN covers its commit record; the extra time is one network round trip plus the standby's flush, about 0.5 to 2 ms in the same region. With ANY 1 of 2 standbys, one slow replica does not stall commits. Failover then promises no loss of acknowledged transactions. With asynchronous replication the client gets its answer first, and a failover can lose the last few hundred milliseconds of commits. This is the practical form of the consistency versus latency trade-off in distributed systems.
acid | The transaction is durable now, but other sessions still need to learn that it committed. The backend marks the transaction ID as committed in the commit log, pg_xact, a bit array with 2 bits per transaction (in-progress, committed, aborted, sub-committed), so one 8 KB page covers 32,768 transactions. It then removes itself from the list of running transactions (the ProcArray). New snapshots now treat transaction 7501233 as finished, and all of its changes become visible together: the new balance and nothing else changed. That atomic visibility switch is one bit write in shared memory. The client gets 'C' and 'Z', and the entire commit took about 1 ms. Atomicity, consistency, isolation and durability each came from a different mechanism: the commit bit, constraints, snapshots and the WAL flush.
recovery | Why is it safe that the data page is still only in memory? After a power cut, PostgreSQL restarts and reads pg_control to find the last checkpoint's redo pointer. It replays every WAL record after that point: for each record, if the page's LSN is older than the record's LSN, the change is applied; if not, it is skipped, which makes redo idempotent. The commit record in the log is what makes the transaction count; changes without a commit record are simply invisible because their transaction ID is never marked committed. Meanwhile, the background writer and the checkpointer write dirty pages to the data files, spread over a checkpoint interval of 5 minutes by default. A short checkpoint interval makes recovery fast but writes more full pages; a long one does the opposite.
tunneling | The final layer is quantum mechanics. A NAND flash cell stores your bit as charge on a floating gate, a conductor wrapped in oxide only a few nanometres thick. To program the cell, the controller applies about 15 to 20 volts; electrons then tunnel through the oxide barrier in a process called Fowler-Nordheim tunneling, which no classical particle could do. To erase, a reverse voltage pulls them out. Every pass damages the oxide a little, which is why a cell survives only about 1,000 to 100,000 program-erase cycles and why SSD controllers spread writes evenly (wear levelling). The charge stays for years without power. So the durability promise of your COMMIT, "the data survives a power cut", is finally kept by electrons parked behind a barrier they could not climb.

## What happens when a producer sends a Kafka message and a consumer reads it | From send() to a sequential append, a replicated commit and a zero-copy fetch
kafka | Your code calls producer.send(new ProducerRecord("orders", "user-42", json)). Nothing goes on the network yet. The producer first serializes the key and value to bytes (say 12 and 1,000 bytes), and needs to know which broker leads the target partition. If it has no metadata, it asks one of the bootstrap servers with a Metadata request and receives the list of brokers and, for each partition of "orders", the leader, the replicas and the leader epoch; it caches that for 5 minutes or until a request fails with NOT_LEADER. The call returns a Future within microseconds, because send() only places the record in an in-memory buffer. A separate sender thread does the networking. This split lets one producer thread hand over hundreds of thousands of records per second.
partitioning | A topic is split into partitions, and a record goes to exactly one of them. With a key, the default partitioner hashes it with murmur2 and takes the result modulo the number of partitions: all records for "user-42" land in the same partition, say 7 of 12, so they stay in order relative to each other. Without a key, newer clients use a sticky strategy: fill one batch for a partition, then switch, which makes batches bigger. Order is guaranteed only inside a partition, never across the topic. Choosing the key is therefore a design decision: it sets the unit of ordering, and a hot key (one user with 100 times more traffic) makes one partition and one broker busier than the rest. Adding partitions later changes the modulo result, which breaks the old key-to-partition mapping.
batching | Records are collected per partition in the RecordAccumulator into batches of up to batch.size (16 KB by default). The sender thread ships a batch when it is full or when linger.ms has passed (5 ms by default since Kafka 4.0, formerly 0). Waiting a few milliseconds costs a little latency but can multiply throughput: sending 1,000 records of 1 KB in 62 batches instead of 1,000 requests saves almost all of the per-request overhead of headers, system calls and acknowledgements. If compression.type is lz4 or zstd, the whole batch is compressed as a unit, usually 2 to 5 times smaller for JSON, because similar records compress together. Batches for all partitions with the same leader are grouped into one ProduceRequest, so one TCP round trip can carry several partitions' data.
idempotence | Retries could create duplicates: if the broker wrote the batch but the acknowledgement was lost, a naive resend would write it twice. With enable.idempotence (the default since Kafka 3.0), the broker gives the producer a producer ID and an epoch, and the producer numbers the batches per partition with a sequence number. The leader remembers the last 5 sequence numbers per producer and partition. A repeated batch with a sequence number it has already seen is acknowledged without being appended again, and a gap in the sequence is rejected with an error, which preserves the order even when up to 5 requests are in flight. This turns the producer-to-broker hop into exactly-once for one partition within one producer session, using only a few bytes of metadata per batch.
tcp | The sender thread uses non-blocking sockets and a Java NIO Selector, so a single thread handles connections to every broker. The ProduceRequest, about 1 KB to 1 MB, travels over TCP (optionally with TLS), pipelined: up to 5 requests per connection can be in flight, without waiting for responses. The client's socket send buffer and the broker's receive buffer, 100 KB or more, together with TCP's congestion window, determine throughput on a long-distance link: with 100 ms RTT and a 128 KB window, a single connection cannot exceed 1.3 MB/s, so cross-region producers need larger buffers (send.buffer.bytes = -1 lets the OS tune them). Inside one data center the round trip is 0.2 to 0.5 ms, and the network is rarely the limit; the replication and disk work below are.
eventloop | On the broker, the Acceptor thread accepts the connection and hands it to one of the network threads (3 by default). Each network thread runs a selector loop that reads complete requests into a bounded request queue (500 entries). A pool of I/O threads (8 by default) takes requests from the queue, executes them, and puts responses back for the network thread to write. The structure is a classic reactor: few threads wait for I/O events, and a different pool does the work, so a slow disk operation does not block the sockets of thousands of other clients. If the request queue fills up, network threads stop reading and the pressure is felt by clients as higher latency. The per-request CPU cost is small, about 10 to 50 µs, because most data is simply copied.
commitlog | The I/O thread hands the batch to the partition's leader replica, which validates it (CRC32C checksum, magic number, size limits) and appends it to the partition's log. The log is an append-only file that never changes in place. The leader assigns offsets: if the log ends at offset 41,999, the 20 records in the batch get 42,000 to 42,019. The batch is stored as received, in the on-disk record-batch format: a 61-byte header (base offset, length, leader epoch, CRC, attributes, producer ID, sequence, timestamps, record count) followed by the records with variable-length fields, so the broker rewrites only a few header fields and does not decompress. The offset is the record's permanent address in the partition. A consumer's position is just this number, which makes replay possible by moving it back.
segments | A partition is not one big file but a sequence of segments: 00000000000000000000.log, 00000000000000042000.log, and so on, named after the first offset they hold. The active segment grows until it reaches 1 GB (log.segment.bytes) or 7 days, then it is closed and a new one starts. Next to each segment live a sparse offset index (one entry every 4 KB of data, mapping offset to file position) and a time index. To find offset 42,017 a reader binary-searches the segment names, then the index, then scans at most 4 KB forward. Retention deletes whole old segments with a simple unlink, in constant time, never record by record. That design is why deleting 100 GB of expired data costs no more than deleting 1 MB.
pagecache | The append is a write() into the operating system's page cache. Kafka does not call fsync for each batch by default. The bytes sit in kernel memory as dirty pages and the kernel flushes them to disk within about 30 seconds (dirty_expire) or when dirty pages exceed a threshold. A write into page cache costs about 1 µs per KB, 1,000 times cheaper than an fsync. The broker also keeps no large heap cache of its own, so the memory is used once and a restarted broker process still has a warm cache. Recently written data stays in RAM and is served to consumers without touching a disk, which is why a consumer that keeps up costs almost no disk reads. Safety comes from replication, not from flushing a single machine's disk.
replication | Each partition has, say, 3 replicas on three brokers: one leader and two followers. Followers are consumers of the leader: a fetcher thread on each follower sends Fetch requests with its next offset, the leader replies with new batches, and the follower appends them to its own log. The leader tracks the in-sync replicas (ISR): those that are fully caught up within replica.lag.time.max.ms (30 seconds). The high watermark is the highest offset replicated to all ISR members, and only records below it count as committed. With acks=all and min.insync.replicas=2, the produce request is held in a "purgatory" until at least 2 replicas have the batch, so one machine failing loses nothing. That adds one follower round trip, typically 1 to 5 ms in the same availability zone and about 2 ms or more across zones.
raft | Who decides which replica is the leader? In current Kafka, a small group of controller nodes (3 or 5) keeps the cluster metadata in a replicated log managed by KRaft, a variant of the Raft consensus protocol, replacing the old ZooKeeper. The active controller assigns leaders and ISR changes to partitions, and brokers learn about them by fetching the metadata log themselves. If the leader of partition 7 crashes, the controller picks a new leader from the ISR, increases the leader epoch, and clients get NOT_LEADER on their next request, refresh the metadata and retry. Failover for one partition typically takes a few hundred milliseconds. The epoch is stored in every batch, so a stale leader that was only partitioned away cannot silently accept writes that conflict with the new leader's log.
deliverysem | When the high watermark passes the batch, the purgatory completes the ProduceResponse: for each partition it returns the base offset and a timestamp, a few dozen bytes. The producer's callback fires with "partition 7, offset 42,000". The delivery guarantee comes from the combination you choose: acks=0 (fire and forget, may lose), acks=1 (the leader wrote it, may lose on a leader crash before replication), acks=all (survives f failures out of f+1 in-sync replicas), and retries until delivery.timeout.ms of 2 minutes. At-most-once, at-least-once and exactly-once are properties of the whole pipeline, not of one setting. End-to-end, a send with acks=all inside one region typically takes 3 to 10 ms from send() to callback, and a good cluster handles hundreds of thousands to millions of such records per second.
consumergroups | A consumer starts with consumer.subscribe(["orders"]) and a group.id. It finds the group coordinator, the broker leading the __consumer_offsets partition that hashes from the group name. In the classic protocol it sends JoinGroup, one consumer is chosen as leader and computes the assignment, and everyone gets their partitions through SyncGroup. (With the new group protocol in Kafka 4.0, the coordinator assigns partitions incrementally, so a rebalance no longer stops the whole group.) Each partition is read by exactly one consumer of the group; a topic with 12 partitions is spread over up to 12 consumers, and extra consumers sit idle. Heartbeats go every 3 seconds, and a consumer silent for 45 seconds is removed, triggering a rebalance. The consumer then finds its starting point from the committed offset, or from auto.offset.reset.
zerocopy | The consumer's poll() sends a Fetch request for partition 7 with offset 42,000, maxBytes 1 MB and a maximum wait of 500 ms: if there is no data yet, the broker parks the request (long polling) and replies as soon as a record exists, usually in under a millisecond after it was committed. Only records below the high watermark are returned. To send them, the broker finds the file position through the index and calls sendfile(): the kernel moves the bytes from the page cache straight to the network card's buffers by DMA, without copying them through the broker's JVM at all. This saves two of four copies and the CPU cost of crossing the user-kernel boundary, and lets one broker serve several GB per second. With TLS enabled the data has to pass through user space for encryption, and this optimization is lost.
encoding | The consumer receives the compressed batch exactly as it was stored and decompresses it on its own CPU, at about 500 MB/s to 1 GB/s with LZ4. Compression happened once in the producer, was kept through the leader, the followers and the disk, and gets undone only at the end; the brokers never spent CPU on it. The client's record iterator then deserializes each key and value, verifies the CRC, and returns up to max.poll.records (500) records to your code. The headers, timestamps and offsets are included with a few bytes of varint-encoded deltas, so 1 KB of payload costs only about 1.03 KB of storage and network. The full path from send() to your handler is typically 5 to 20 ms when the consumer is caught up and the system is idle.
backpressure | Kafka consumers pull, so they control the pace, which is Kafka's built-in backpressure. If processing is slow, the consumer simply polls less often and its position falls behind the log end: the lag, measured in offsets or seconds, grows. Nothing breaks, because the data stays on disk until retention (7 days by default) deletes it. The only limit is that the consumer must call poll() at least every max.poll.interval.ms (5 minutes), or the group decides it is dead and rebalances. Lag is the most important metric of a Kafka pipeline, and it behaves like any queue: when the arrival rate nears the processing rate, waiting time rises sharply, and you add consumers (up to the partition count) or make the handler faster. A lagging consumer also reads older data from disk instead of page cache, making the brokers slower for everyone.
exactlyonce | The consumer commits its progress by writing the next offset to __consumer_offsets, a compacted internal topic with 50 partitions: key (group, topic, partition), value 43,000. Auto-commit does this every 5 seconds; committing after processing gives at-least-once (a crash between processing and committing replays a few records), and committing before gives at-most-once. For exactly-once processing in a consume-transform-produce pipeline, Kafka transactions write the output records and the offset commit in one atomic transaction using a two-phase commit run by a transaction coordinator, and consumers with isolation.level=read_committed skip aborted data. The cost is a few extra round trips per transaction and some delay. Whenever the sink is outside Kafka, you still need an idempotent write or a deduplication key, since no protocol can span arbitrary systems.

## What happens when a Spark job runs a SELECT ... GROUP BY on a Delta table | From SQL text to files in object storage, a shuffle and a final result
spark | You run spark.sql("SELECT country, count(*), sum(amount) FROM sales WHERE dt >= '2026-10-01' GROUP BY country"). The code runs in the driver, one JVM process that holds the SparkSession and plans the whole job. Nothing is read yet: DataFrame and SQL calls are lazy and only build a plan. The work starts when you call an action such as show() or write(). The driver then asks the cluster manager (YARN, Kubernetes or Databricks' own) for executors, JVM processes with a few cores and several GB of memory each, perhaps 20 executors with 8 cores for 160 parallel task slots. On a warm cluster the executors are already running. The driver is the brain and a single point of failure: it keeps the plan, the task bookkeeping and the results, so a huge collect() into it is a classic way to crash a job.
parsing | The SQL text goes through an ANTLR-generated parser, which turns it into an abstract syntax tree and then an unresolved logical plan: Aggregate(country; count, sum) over Filter(dt >= ...) over UnresolvedRelation(sales). Words like "sales", "country" and "amount" are only names at this point. A typo in the SQL fails here in a few milliseconds, with a syntax error and a line and column. Parsing is a standard compiler front end: a lexer produces tokens, and a grammar of nested rules gives the tree. The same SQL in the DataFrame API produces the same plan, because both are just different ways of building the tree, and the optimizer works on the tree, not on your syntax. Spark's own planner then never sees raw text again; every later rewrite works on this tree of small Scala case-class nodes, which is why rules are short and easy to compose.
unity | The analyzer must resolve the names. It asks the catalog (Unity Catalog, Hive Metastore or Glue) to look up main.default.sales: the table's format (Delta), its location (s3://lake/sales), its schema, and whether you are allowed to read it. A governance layer checks your privileges, perhaps also column masks and row filters, and returns short-lived credentials that allow only this table's path in object storage, so executors never hold long-lived keys. Then the analyzer binds each column name to a column of the schema with a type: country is a string, amount is a decimal(12,2), and count(*) is a bigint. If a column does not exist, you get an AnalysisException. The metadata call usually takes 10 to 100 ms and is cached for later queries.
delta | A Delta table is a directory of Parquet files plus a _delta_log directory of JSON commit files (00000000000000001234.json) and a checkpoint Parquet file every 10 commits. To know which files belong to the table, Spark reads the latest checkpoint and the few JSON commits after it, and replays their actions: "add file X with these statistics" and "remove file Y". The result is the table's state at version 1234, for example 4,000 active files totalling 500 GB. This replay is itself a small Spark job, which finishes in 0.2 to 2 seconds. Each add action carries per-file statistics: row count and the min, max and null count for the first 32 columns. The log is what turns a pile of files in an object store into a table with consistent snapshots, since the object store has no directory-level atomic operations.
mvcc | Because the Delta log is append-only and each commit makes a new numbered version, a reader works on a snapshot: version 1234 as of the moment the query started. Writers that commit version 1235 while your query runs do not affect it, since the files it needs are never modified in place, only added or logically removed. Physical deletion happens much later by VACUUM, after a retention period of 7 days by default, which is also what makes time travel (VERSION AS OF 1200) possible. This is multi-version concurrency control at the table level: readers do not block writers and writers do not block readers, and every query sees one consistent state, even though the table is only files on S3. A long-running query that outlives the retention period can fail with "file not found".
queryopt | The Catalyst optimizer rewrites the logical plan using rules until nothing more applies. It pushes the filter dt >= ... down to the scan, prunes the columns so only country, amount and dt are read (3 of maybe 40), folds constants, and simplifies expressions. Then the planner turns the plan into a physical plan and uses statistics and costs to choose strategies. For an aggregation the standard plan is two-phase: HashAggregate(partial) on each partition, then an Exchange (shuffle) that hashes on country, and a final HashAggregate. A partial aggregation shrinks 1 billion rows to a few thousand per task before any data crosses the network. You can see the result with EXPLAIN FORMATTED. Planning takes tens of milliseconds, and it saves orders of magnitude of work compared to a naive plan.
zonemaps | Before launching any task, Spark uses what it knows to skip data. If the table is partitioned by dt, files in directories with older dates are discarded without even looking at them, leaving 300 of the 4,000 files. Delta's file statistics add data skipping on columns: a file whose max(dt) is below 2026-10-01 cannot contain a match, so it is skipped using only the min and max values in the log, without reading a byte of the file. If the data was written with clustering such as Z-order or liquid clustering, similar values sit in the same files, and skipping works much better. Skipping 90% of files means the query reads 10% as many bytes, and each byte not read is a saving in network, CPU and money.
dagsched | The physical plan is cut into stages at each shuffle boundary: stage 1 = scan, filter and partial aggregate, stage 2 = final aggregate. The DAG scheduler creates one task per input split. The 300 remaining files are bin-packed into splits of about 128 MB (spark.sql.files.maxPartitionBytes), giving around 300 tasks. The task scheduler sends them to executors, preferring ones that already have the data cached, and each executor runs as many tasks at once as it has cores. With 160 slots, 300 tasks finish in two waves. Stage 2 starts only when all stage 1 tasks are done, because a final aggregate needs every partial result. If a task fails, only that task is retried; slow stragglers may get a speculative copy on another executor. The scheduler is event-driven and dispatches about 1,000 tasks per second.
sepstorage | The executors are not where the data lives. In a lakehouse design, storage (S3, ADLS or GCS) and compute are separated: the files sit in an object store reached over HTTPS, and the cluster can grow, shrink or disappear without moving data. Reading a Parquet file means HTTP range GET requests: the first byte arrives after 20 to 60 ms, then a stream delivers 50 to 100 MB/s per connection. To hide the latency, executors issue many parallel and prefetching requests. The cost model is also different from a local disk: S3 charges per request (about $0.0004 per 1,000 GETs), so thousands of tiny files hurt both speed and money. Decoupling is flexible and cheap, but every query has to pay the network cost that HDFS-style local data avoided.
parquet | Each task opens its Parquet file by reading the footer, the last few KB to MB, which holds the schema, the row groups (about 128 MB each) and, for each column chunk in each row group, offsets, encodings and min/max statistics. Using the footer, the task reads only the byte ranges of the country and amount columns, and skips the 37 other columns altogether. Within a row group it may skip further if the statistics prove the dt filter cannot match. A column chunk is a series of pages of about 1 MB that are read one at a time. For a 128 MB file with 40 columns, the task fetches perhaps 6 MB over the network, which is the whole reason columnar formats win for analytics: the I/O is proportional to the columns used, not to the width of the table.
encoding | The bytes in a column chunk are encoded cleverly and then compressed. The country column has about 200 distinct values, so Parquet stores a dictionary of the 200 strings once, and every row as a small integer index of 8 bits; runs of repeated values are further stored as run-length (value, count) pairs, and booleans and small numbers use bit-packing. After that, the page is compressed with Snappy or Zstd, typically by another factor of 2. The reader reverses this: decompress at about 500 MB/s to 1 GB/s per core, and decode dictionary indices at several GB/s. A column of 1 million countries therefore costs about 1 MB on disk instead of 8 MB. The aggregation can sometimes even run on the dictionary codes without decoding to strings, which is a large saving.
vectorized | The decoded data are held in column batches of about 4,096 values and not as rows. The scan hands such a batch to the filter and aggregate operators, which run tight loops over arrays: compare 4,096 dates against a constant in one pass, producing a selection vector, with the CPU's SIMD instructions handling 8 or 16 values per instruction. Everything the loop touches fits in the L1/L2 cache, and there is no per-row virtual function call or object allocation. In Databricks, the Photon engine implements this in C++; open-source Spark does the same with columnar readers and whole-stage code generation. A good vectorized engine processes 100 million to 1 billion values per second per core. The CPU, not the network, becomes the bottleneck for well-pruned scans.
hashtables | Per task, the partial HashAggregate keeps a hash table from country to a running (count, sum) pair. For each row it hashes the country (Murmur3), finds the slot, and updates two numbers in place. With 200 distinct countries the table has 200 entries and fits easily in the CPU's L1 cache, so each update costs a few nanoseconds; 10 million rows per task are processed in well under a second. With a high-cardinality key such as user ID, the table would have millions of entries, would overflow cache and memory, and Spark would spill sorted runs to local disk or fall back to sort-based aggregation. Therefore the number of distinct groups, not the number of rows, controls the cost of a GROUP BY. At the end of the task, the table's 200 entries, a few KB, are emitted.
shuffle | The partial results must meet by key. Each map task hashes each country into one of spark.sql.shuffle.partitions reducer buckets (200 by default), and writes its small output to a single local shuffle file with an index, a few KB per task, on the executor's local SSD. The next stage's tasks fetch their bucket from every one of the 300 map outputs over the network, via the shuffle service or the executors directly. In a big sort or join this is the most expensive step: all data is written, sent over the network, and read again; with 1 TB it means 1 TB of disk and network traffic and can take minutes. Here, because the partial aggregation shrank 500 GB to about 300 files of 5 KB each, the shuffle moves only 1.5 MB in total, and takes less than a second.
aqe | Adaptive Query Execution now looks at the real sizes of the shuffle output. The planner assumed 200 reducer partitions, but the statistics show 1.5 MB in total, so AQE coalesces the 200 tiny partitions into 1 (target 64 MB per partition) and avoids 199 pointless tasks, each of which would have cost 10 to 50 ms of scheduling overhead for no work. For joins, AQE can also switch a sort-merge join into a broadcast join if one side turns out to be small, and it splits skewed partitions that are much larger than the median. Runtime re-optimization is useful because estimates before the query are often wrong by 10 times or more, while the measured sizes after the first stage are exact.
mpp | The final stage runs one task that fetches its 300 tiny pieces, merges the partial aggregates (adding counts and sums for each country, an operation that is associative and commutative, so the order does not matter), and produces about 200 rows. The driver collects them and show() prints a table. The whole query took perhaps 5 to 15 seconds on a cold cluster, of which 1 to 2 seconds went to the Delta log and planning, 3 to 8 seconds to reading about 6 MB from each of 300 files from S3 and decoding it, and under a second to the shuffle and final merge. This is the massively parallel model: the same small program runs on many pieces of data, and then a narrow exchange combines the answers. Without partial aggregation and pruning, the same query would read 80 times more bytes.
cachelayer | Running the query a second time is faster because of caching at several levels. The Delta log snapshot is kept in the driver's memory, so the metadata step is skipped. Each executor has a local disk cache (the Databricks disk cache, or OS page cache) holding recently read Parquet byte ranges on NVMe SSD, which reads at 1 to 3 GB/s with 100 µs latency, 100 times better than S3's first-byte latency. Results of the same query can be reused if the underlying files have not changed. Cache hit rates of 80% or more are common for repeated dashboards. But the cache is only a speed-up: because the Delta log and the immutable files are the source of truth, an executor can lose its cache or even die at any time without losing any information.

## What happens when an ad is chosen and shown on a smart TV | From automatic content recognition to bids, stitched video, playback and beacons
acr | Long before the ad, the TV has been learning what its household watches. With the viewer's consent, a smart TV with automatic content recognition (ACR) takes a copy of the video frames just before the on-screen menus are drawn, about once every 500 ms, and sometimes a short audio snippet. The frame is shrunk to a tiny grid (for example 16 by 16 luma values) and turned into a small fingerprint of a few bytes, all on the TV's own chip, so raw pictures never leave the set. Every few minutes the TV uploads a batch of a few KB over HTTPS: a device ID, timestamps and the fingerprints. A TV that is on 5 hours a day produces around 36,000 fingerprints a day, which is only a few hundred KB. Multiplied by millions of TVs, the stream is huge, and the next steps have to cope with it.
fingerprint | The fingerprint must survive everything between the broadcaster and your living room: re-encoding, brightness and contrast settings, scaling, a channel logo, and noise. It therefore does not use exact pixel values but robust features, such as whether each block of the frame is brighter or darker than its neighbour (a 1-bit comparison, not a value), or peaks in the audio spectrogram. Many such bits are packed into a hash of 32 or 64 bits per frame. Two copies of the same frame differ by only a few bits, while two different frames differ in about half their bits. Because a single frame is ambiguous (a black frame matches many), the matcher uses a sequence of fingerprints over a few seconds, which gives high accuracy, and makes the match robust against short glitches.
lsh | The server has to compare each incoming fingerprint to a reference set that holds every frame of hundreds of channels and thousands of ads, perhaps billions of entries, and do it up to 20 million times per second when 10 million TVs are on and sampling twice a second. Brute-force comparison is impossible. Locality-sensitive hashing cuts each fingerprint into several chunks and builds tables keyed by each chunk. A query looks up its own chunks in each table and gets a short list of candidates in microseconds: similar fingerprints share at least one chunk with high probability, different ones almost never do. The candidates are then verified by comparing the full bit strings (Hamming distance), and by checking whether the matches line up in time, one per 500 ms, along the same channel. This is a nearest-neighbour search with a tunable trade-off between recall and cost.
contentid | The reference database is built continuously. For linear TV, capture servers record every channel in each market, cut the video into frames in real time (with a delay of a few seconds), and add their fingerprints to the index with a label: channel, program, ad creative and time. Ads are fingerprinted from the creative files directly. When a batch from a TV matches, the system learns "this TV watched ESPN, program X, from 20:14:03 to 20:31:40, and saw ad Y at 20:18:15". The match is usually found in 1 to 2 seconds. Video-on-demand and streaming apps cannot be captured the same way, so their content is recognised by metadata or by pre-fingerprinted catalogues. The output is a viewing log with one row per contiguous segment, instead of a flood of single frames.
identity | The logs say what a device watched; ads need to be bought for a household. The device ID is linked to other IDs in an identity graph: the same TV's streaming advertising ID, the household's IP address, perhaps other TVs on the same Wi-Fi network. Linking can be deterministic (the same login) or probabilistic (a shared IP address and similar usage patterns, with a confidence score). From viewing history the platform computes audience segments each night in batch jobs: "watched live sports 3 or more times this week", "saw a competitor's car ad in the last 7 days", "frequently watches cooking shows". A segment ID is just a number attached to a device ID in a lookup table, so that it can be read in under a millisecond when an ad request arrives.
privacytech | None of this is allowed without rules. The TV asks for consent at set-up and lets you turn ACR off in the settings; opt-out and deletion requests (for example under California's laws and similar rules in other states and countries) must reach every table that holds the device's data, including segment tables and logs. Engineers apply tokenization (a hashed device ID instead of an identity), data minimization (keep segments, drop raw fingerprints after matching), retention limits of weeks or months, and aggregation thresholds so that no report is made for fewer than a minimum number of households. Some analyses add calibrated noise (differential privacy). Privacy engineering is a part of the data path and a deletion request is a concrete pipeline job, in the same way as any other write.
adtech | Now the viewer is watching a show in a streaming app, and the video reaches a mid-roll break: a marker in the stream (SCTE-35 in the broadcast world, or a cue point in the manifest) says "break of 120 seconds starts in 4 seconds". The publisher's ad server, or a supply-side platform acting for it, turns the break into several ad slots (each 15 or 30 seconds) and starts an auction for each, or for the whole pod. This is the sell side of ad tech. For connected TV a very large part of ads is bought programmatically, in real time, at a price per thousand impressions (CPM) between 10 and 40 dollars, and each auction must finish in a small fraction of a second so that the viewer sees no gap.
openrtb | The supply side sends a bid request to many demand-side platforms (DSPs) at once. It is an HTTP POST with an OpenRTB JSON body of 2 to 5 KB: the impression (video, 30 seconds, supported formats, minimum bitrate, floor price), the app and content details (genre, rating), the device (TV model, OS, IP address, a resettable advertising ID, location at city level), and the user's segment IDs. Each DSP has a tmax, often 100 to 150 ms in total, in which to answer; a response that comes late is discarded. A typical exchange handles 100,000 to a million such requests per second and fans each one out to 5 to 20 bidders, so the network carries gigabytes per second just for questions. Much of the budget is spent just on network travel, so DSPs place their servers in the same data centers as the exchanges.
pacing | Inside a DSP, the request is checked in a few milliseconds against thousands of campaigns. A fast filter drops campaigns whose targeting does not match (wrong geography, no matching segment, brand-safety rules). A frequency cap check looks up how many times this household has seen the campaign today in a low-latency key-value store. A pacing controller decides whether this campaign should bid now: if it has spent 30% of its daily budget by noon but should have spent 50%, it bids more often or higher; if it is ahead of plan, it throttles. A model predicts the chance that this impression produces the goal (a completed view, a store visit) and turns it into a bid price. The campaign with the best expected value wins the internal contest, and the bid response, with a price and a link to the creative, is sent back.
auction | The exchange collects the responses that arrived in time and runs the auction. Most exchanges now use a first-price auction: the highest bidder wins and pays exactly what it bid, so bidders try to shade their bids using models of what others would pay (bid shading). Older systems used a second-price rule, where the winner pays one cent above the runner-up, which makes honest bidding the best strategy. The winning bid must exceed the publisher's floor price, and the exchange may apply deal priorities and brand-safety checks. The winner receives a win notice with the clearing price (an HTTP GET), and the response also contains the creative: a VAST XML document or a URL to one. The entire process, from the ad-break marker to a winner, has used around 100 to 200 ms, which is why the break is announced seconds ahead.
codecs | The VAST file points to a video creative and lists tracking URLs. The advertiser delivered a mezzanine file (a high-quality master), and an ad-processing system has already transcoded it into a ladder of renditions that match the show's stream: for instance H.264 at 1080p 6 Mbit/s, 720p 3 Mbit/s and 480p 1.2 Mbit/s, with the same frame rate, audio loudness (normalized to about -24 LKFS) and aligned segment boundaries. A transcode uses motion compensation and DCT to compress about 100 times; a 30-second ad is roughly 20 MB at the top rung. The work is done ahead of time, because a transcode at 1x real-time speed is too slow to do when the auction ends. If the winning ad has not been prepared, the stitcher either skips it or falls back to a default ad.
hlsdash | With server-side ad insertion (SSAI), the viewer's player does not know there is an ad. The origin stream is HLS or DASH: a manifest (playlist) lists 2 to 6 second segments for each bitrate. A manifest-manipulation service sits in front, and for this viewer it replaces the segment entries of the break with the ad's segments, adding a discontinuity tag so that the decoder resets cleanly. The new playlist is a few KB of text. Because ads and content now come from the same domain in the same format, ad blockers do not see anything to block, and the player never waits for a separate ad request. The stitcher also keeps a session so that it can report which segments the viewer actually fetched, which becomes the evidence that the ad ran.
cdn | The segments are ordinary files on a CDN. The player requests each one with an HTTP GET to the nearest edge, which answers from cache in a few milliseconds if the segment was requested recently by someone else. Popular ads and shows have very high hit rates, 95% or more. A 30-second ad at 3 Mbit/s consists of about 11 MB in 5 segments of 6 seconds each. Edge servers are placed inside ISPs and at internet exchanges, so the path to the TV is a handful of router hops. The TV's own Wi-Fi may be the weakest link. Because the same ad is shown to thousands of households in the same hour, the CDN sees the same few segments again and again, which is almost the best case for caching.
abr | The player measures how fast each segment downloads and how many seconds of video are buffered (usually 10 to 30 s). If throughput is 8 Mbit/s and the buffer is healthy, it requests the top rendition; if the Wi-Fi drops to 2 Mbit/s, it switches down to 480p at the next segment, and avoids a stall at the cost of a softer picture. Because the ad is in the same ladder as the content, the switch is seamless and the viewer cannot tell where the ad starts. Rebuffering is the most disliked outcome: two seconds of spinning wheel during the ad leads to abandonment, so the algorithm prefers lower quality over stalls. Before the break the player may prefetch the first segments of the ad into the buffer, which is another reason the decision must be made seconds ahead.
mediastream | The TV's media pipeline decodes the segments. Compressed H.264 or HEVC data goes to a hardware decoder on the TV's SoC, which uses motion compensation, inverse DCT and a loop filter to rebuild 30 or 60 frames per second at 1080p or 4K, using few watts. DRM may be applied on the way, so that frames are decrypted only inside a secure video path that applications cannot read. Audio is decoded and synchronized to video by timestamps, to within about 40 ms. The finished frames are composited with the user interface layer and sent to the display panel each refresh. The viewer sees a 30-second ad as a seamless continuation of the show, after a chain of about 200 ms of decision-making and a few seconds of earlier preparation.
pixels | As the ad plays, tracking events fire. VAST lists URLs for impression, start, firstQuartile (25%), midpoint, thirdQuartile and complete, and with SSAI the server-side stitcher (or the player) requests them when the segments are served or played. Each is an HTTP GET to a measurement or ad-server domain, with macros replaced by values such as the campaign ID, the creative ID, the device ID, the timestamp and the price. The response is a 1x1 GIF or an empty 204, about 40 bytes, because only the request matters: the server logs one line. Third-party verifiers add their own pixels to check viewability and fraud (a real TV and not a data-center bot). Missing beacons are common, because of network loss and app exits, so reports differ by 5 to 15% between systems and everyone has to reconcile.
kafka | The beacon servers write each request as an event to a Kafka topic. At peak this is hundreds of thousands of events per second: impressions, quartiles, clicks, bid logs and win notices. A partition key such as the device or the campaign keeps related events together in order. Stream processors read the topics to keep real-time counters (spend per campaign over the last minute) that feed back into pacing, so the controller learns within seconds that a campaign has over- or underspent. Duplicates are removed by an event ID, because beacons are retried. The same topics are written to object storage by a connector, so that the batch systems below see the full history. The stream is the shared backbone of billing, optimization and reporting.
delta | The events land in Delta tables on object storage, where hourly and nightly jobs join them: impressions with bid logs (to compute the effective price paid), with the ACR viewing logs (who really watched the ad on the TV, whether it was skipped or the channel was changed) and with outcomes such as a later visit to a store or a purchase. Because Delta commits atomically, finance and analytics can read a consistent table while writers are still adding data. The last step is measurement: to know whether the ad caused anything, a holdout group of similar households is withheld, and an experiment compares conversion rates between exposed and unexposed households. Those results change the segments, the models and the budget, and the loop closes before tomorrow's ad break.

## What happens when you tap a credit card to pay | From a 13.56 MHz field to an approval, a hold on your account, and a settlement two days later
maxwell | A card has no battery. The payment terminal drives a flat coil with an alternating current at 13.56 MHz, producing a magnetic field of roughly 1.5 to 7.5 amperes per metre within about 4 cm. When you bring the card near, its own printed antenna coil sits in the changing field, and Faraday's law makes a voltage appear across it, a transformer without a core. A small rectifier turns this into a few milliwatts of direct current, just enough to start the chip in about a millisecond. The same coupling carries data. The reader switches the amplitude of its field on and off to send bits at 106 kbit/s; the card answers by loading its coil on and off, which a reader can detect as a tiny change in its own field. The field falls off with the cube of distance, which is why a tap must be a real tap.
noise | Between a card and a terminal there is only a few centimetres of air, but the signal is weak: the card's answer is a tiny fraction of the reader's own field, buried in thermal noise, in interference from the shop's lights and in the clutter of the terminal's own electronics. The reader filters the 847 kHz subcarrier that the card uses and demodulates it. Every frame carries a CRC, and a wrong CRC makes the reader ask again. Because the exchange takes only about 100 to 300 ms and the card must stay in the field for all of it, a card pulled away too early gives the error "try again". Anti-collision logic ensures that when two cards are in the field, the reader detects the clash and does not mix their data.
nfc | Once the card is awake and the radio link works, both sides run the protocol stack of ISO 14443. The reader sends a 7-bit command, REQA, and every Type A card in the field answers with ATQA. Each card has a unique ID of 4, 7 or 10 bytes; the reader asks for it and settles any clash bit by bit, then selects one card with SELECT. The card replies with a SAK byte that says whether it speaks the ISO-DEP transport. The reader then sends RATS, and the card answers with its largest frame (up to 256 bytes) and its waiting time. From here on, the APDUs travel in numbered blocks with a CRC, and the card can ask for extra time while it computes. A byte with its parity bit takes 9 bits of 9.44 µs, about 85 µs, so a 255-byte answer needs 22 ms. If the card is a phone, its chip does not just switch a load: it generates the reply itself (active load modulation) and routes each SELECT by application ID, to the secure element for a bank card or to an app for a transit pass. This setup takes about 5 to 10 ms.
digitallogic | The chip that wakes up is a secure element: a tiny computer on a 3 by 3 mm die with a CPU, a few KB of RAM, 100 to 500 KB of non-volatile memory, a hardware cryptographic engine and many physical protections (sensors for voltage, light and clock glitches, and shielding against probing). It runs a Java Card or similar operating system and has no way to be read out other than through a narrow command interface. The card's secrets, including its unique keys, are generated or injected in a secure facility and cannot leave the chip. A phone does the same with a secure element or a hardware-isolated enclave, and releases the keys only after your fingerprint, face or passcode. Everything the chip does is sequential logic switched at around 13.56 MHz, the rate of the field.
binary | Reader and card talk in short command-response pairs called APDUs, with a binary format from ISO 7816: a header of class, instruction and two parameters, a length and data; the reply has data and a two-byte status word, 90 00 meaning success. The terminal first sends SELECT with the name "2PAY.SYS.DDF01" to ask which payment applications the card has. The card lists them, such as Visa (AID A0000000031010) or Mastercard (A0000000041010). Next, SELECT of the chosen application returns a list of data the terminal must supply (the PDOL). GET PROCESSING OPTIONS follows, with the amount, currency, country, date and a random number from the terminal. All data are in a tag-length-value format: a tag byte, a length, then the value. A full tap is about 5 to 10 exchanges of at most 255 bytes.
symcrypto | The most important thing the card produces is the application cryptogram. It is a MAC, an 8-byte code, calculated from the transaction data (amount, currency, date, terminal's random number) and the card's own transaction counter, using a session key that is derived from a master key known only to the issuer and the card. The cipher is 3DES or AES, depending on the scheme. Because it covers the amount and a fresh random number and counter, an eavesdropper who records it cannot replay it on another purchase or change the amount. The card number is not secret enough to stop fraud; this one-time code is. Phones go one step further and send a token (a stand-in number valid only for this device and merchant type) instead of the real card number, so that a merchant breach reveals nothing useful.
pkcrypto | Some checks can happen without a network. Cards for offline use carry public-key certificates: the card's key is certified by the issuer, and the issuer's key by the card scheme, whose root keys are loaded into every terminal. In the fast contactless modes the card signs a short piece of dynamic data with its private RSA key (1024 to 1984 bits), and the terminal verifies the chain of certificates and signature (a few milliseconds on its small processor). This proves that the chip is genuine and not a clone made from copied data. A magnetic-stripe clone fails because the stripe holds only static data. Offline checks matter when the network is down in a tunnel or on a plane, where the terminal may accept small payments against a floor limit and settle later.
tls | The terminal now has what it needs, and sends an authorization request to the merchant's payment processor (the acquirer side). The terminal's connection is usually TLS over Wi-Fi, Ethernet or a mobile network; older systems use a leased line or a VPN. The request is a message in ISO 8583 format, a compact binary standard from the 1980s: a message type (0100 authorization request), a bitmap of 8 or 16 bytes saying which of up to 128 fields are present, and then the fields: card number, amount, processing code, a system trace number, terminal ID, merchant ID, merchant category code, the local time, and the EMV data with the cryptogram. A message is 300 to 600 bytes. Sending it takes under a millisecond; the round trip on the network is 20 to 100 ms.
hashtables | The processor and the card network decide where the request must go by looking at the first 6 to 8 digits of the card number, the Bank Identification Number. The network's routing tables, millions of entries in memory, map each BIN range to an issuer and its processor in constant time. Visa or Mastercard receives the message from the acquirer over dedicated links, checks its format, adds its own fields, and forwards it to the issuer's processor, usually in a second data center in another city. The networks run few data centers with active-active pairs and handle tens of thousands of messages per second at peaks, and they answer their part in a handful of milliseconds. They also pre-screen: stand-in processing can approve or decline on the issuer's behalf if the issuer is unreachable.
oltp | At the issuer, the message becomes a database transaction. A hardware security module (HSM) takes the card's identity, derives its unique key from the issuer master key, recomputes the cryptogram from the same data and compares it to the one in the message; a match proves the real card was used. Then the authorization system looks up the account: is the card active and not reported stolen, has the expiry passed, is the available balance or credit limit above the amount, are the country and merchant type allowed, and does the daily limit hold? This is a typical online transaction processing workload: a few reads and one write on one account row, under strict time limits. The issuer's p99 budget is 50 to 100 ms, and it has to be correct every time.
xgboost | In parallel the issuer's fraud system scores the transaction. A model such as gradient-boosted trees gets a few hundred features in 5 to 20 ms: amount compared with your usual spending, the merchant's category and its risk, the distance to your last transaction and the time since it, the number of attempts in the last hour on this card or this terminal, the device and its token age. The output is a probability of fraud. Above a high threshold the transaction is declined, in a middle band the issuer can ask for a PIN or send an app notification (step-up), and below it is approved. Fraud rates are about 5 to 10 basis points, so false declines of good customers are costly too; models are retrained with confirmed fraud and chargeback labels, and rules are added for new attack patterns within hours.
idempotence | Networks lose messages. If the terminal does not receive an answer within about 3 to 30 seconds, it does not know whether the issuer approved. Every request therefore carries a system trace number and a retrieval reference number, and the issuer remembers recent ones. When the terminal times out, it sends a reversal (message 0400) that cancels the earlier authorization if it was granted; the issuer applies the reversal at most once, and ignores a reversal for a request it never saw. The same keys prevent a retry from charging you twice. This is idempotence in practice: the operation can be repeated safely because it carries an identifier which the receiver checks, and the cost is one lookup in a table of recent keys, which is held in memory and replicated.
eventsourcing | An approval does not move money. The issuer records an authorization hold on your account: the available balance drops by the amount, but the posted balance does not yet change. The ledger is modelled as a log of events, the authorization, later a clearing, possibly a reversal or a tip adjustment, and balances are derived by replaying them, which allows reconciliation and audits. The hold usually expires after 7 days if no clearing arrives, which is why a hotel or fuel pre-authorization shows as pending. The approval response goes back through the same chain: 0110 with response code 00 and an approval code of six characters, 150 to 400 ms in total from the tap. The terminal beeps; to you, it feels instant.
twopc | Money moves in a second phase, later. This is an authorization first and capture afterwards, a pattern that resembles two-phase commit: the first phase asks the issuer to reserve, and the second makes it final. Many merchants batch their authorizations at the end of the day and send them to the acquirer as clearing records. The acquirer submits a clearing file to the network, which calculates fees and routes each record to the issuer. The interchange fee, about 0.2% for debit cards in the EU (capped by law) and 1.5 to 2% for credit cards in many markets, is subtracted and shared between the issuer, the network and the acquirer. If a capture never arrives, the hold lapses. If a card is refunded, a new message reverses the flow. The pattern lets merchants adjust the final amount, as for tips.
batchproc | Settlement is a large batch job. Each night, the network adds up millions of clearing records into net positions between banks, for example "Bank A owes Bank B 12.4 million", and instructs the transfers through the banks' accounts at the central bank or a settlement bank. The acquirer receives the money one to two business days after the sale and pays the merchant the amount minus the fees. The issuer posts the transaction to your statement, so the pending line becomes final, and you owe the issuer at the end of the billing cycle. Reconciliation jobs compare the three records of the same sale, the acquirer's, the network's and the issuer's, and flag differences, such as an amount mismatch or a missing clearing, which are resolved manually or through disputes and chargebacks.
lightspeed | Look at the numbers again. The tap itself takes 100 to 300 ms, most of it in the exchange between card and reader. The network trip from the shop to the acquirer, to the card network, to the issuer and back covers maybe 2,000 to 6,000 km of fibre in total, which alone costs 10 to 30 ms at 5 µs per km. The issuer's processing and fraud check take 50 to 100 ms, and every hop adds queueing. The total of 300 to 800 ms has been the design target for decades, because a customer at a till will wait about a second but no longer. The reason a card payment feels like a single event is that a dozen independent systems, each with a few milliseconds' budget, agreed on one small binary format.

## What happens when you send an email | From a message draft to the recipient's inbox, across two mail servers, checked by signatures and spam filters
unicode | You press Send. Your mail app first turns your draft into an Internet Message, the format of RFC 5322: lines of text headers (From, To, Subject, Date, Message-ID) followed by an empty line and the body. All of it must travel as 7-bit ASCII, because the format dates from 1982. So a Hindi subject line is encoded as UTF-8 and wrapped in an "encoded word" (=?UTF-8?B?...?=), and a body with accented letters is declared as Content-Type: text/plain; charset=UTF-8 and encoded for transport. A modern client builds a MIME multipart/alternative message with a plain-text part and an HTML part, so that old clients can still show something. It also generates a unique Message-ID such as <abc123@mail.example.com>, which is how replies are threaded. Nothing has left your device yet.
binary | Attachments and non-ASCII text are encoded with base64: every 3 bytes (24 bits) are cut into four 6-bit groups, each mapped to one printable character, so binary data becomes safe text at a cost of 33% more bytes plus line breaks. A 3 MB PDF becomes a 4.1 MB part, and a mailbox limit of 25 MB means roughly 18 MB of real files. The parts are separated by a boundary string, and a header says which encoding each part uses. The whole message in a typical case is 50 to 100 KB, mostly HTML with images and the headers that grow at every hop (a received message commonly has 10 to 20 Received lines). The receiver decodes the same way. The representation is wasteful, and it exists because early mail gateways could not be trusted to carry 8-bit data.
tcp | Your client connects to the outgoing (submission) server of your provider, typically smtp.example.com on port 587, or 465 for TLS from the first byte. Its address comes from DNS, a lookup of 1 to 50 ms, usually cached. The TCP handshake takes one round trip, and the server greets with "220 smtp.example.com ESMTP". The client says EHLO and receives a list of extensions: STARTTLS, AUTH, SIZE (for example 35,882,577 bytes), 8BITMIME and PIPELINING. SMTP is a text protocol of commands and three-digit replies, 2xx for success, 4xx for a temporary failure and 5xx for permanent failure, designed so that a person with telnet could use it. A command and its answer cost one round trip each unless PIPELINING lets the client send several together.
tls | Before sending the password, the client issues STARTTLS, and both sides upgrade the plain connection to TLS 1.3 in one more round trip. The server certificate for smtp.example.com is checked against the trust store; this protects your login and your message from anyone on the Wi-Fi network. After the upgrade, the client repeats EHLO because the earlier negotiation is discarded, which defeats an attacker who stripped the STARTTLS offer. Port 465 with implicit TLS avoids that downgrade risk altogether and is again the recommended choice. Whether the later server-to-server hops are encrypted depends on the next server: about 90% of mail between big providers uses TLS, but plain SMTP is not required to use it, so end-to-end secrecy of email still needs S/MIME or PGP.
oauth | Next you prove who you are. Older setups send a username and password with AUTH PLAIN, base64 encoded (which is encoding, not encryption, so TLS is essential). Modern providers use OAuth 2.0: the app holds an access token, obtained earlier through a browser login with your consent, and sends it with AUTH XOAUTH2. The token lasts about an hour and covers only mail access, so a stolen token is less harmful than a stolen password and can be revoked alone. The server verifies the token (a signed JWT or an introspection call) in a few milliseconds and checks that the From address belongs to your account; otherwise anybody could send mail as anybody else, which is how forged mail was easy for decades.
mqueue | The client sends MAIL FROM:<you@example.com>, then RCPT TO:<friend@other.org>, then DATA, and the message text ending with a line that holds one dot. The server must now take responsibility for the message. It writes the whole message to its queue directory (or a replicated database) and flushes it to stable storage, and only then answers "250 2.0.0 OK queued as 7F3A91". If the server crashed before that line, the client would still hold the message and resend it; after that line, the server owns it, and the client may forget it. This hand-over of responsibility is the heart of store-and-forward mail, and the reason email works even when the other side is down. A queue also lets the server smooth out bursts, since a busy provider takes thousands of messages per second.
signatures | Before the message leaves the provider, a DKIM signature is added. The server canonicalizes the chosen headers (From, To, Subject, Date, Message-ID) and the body, hashes the body with SHA-256, and signs the hash together with the headers using the domain's private key (RSA 2048 or Ed25519), which gives a DKIM-Signature header of about 400 bytes with the fields d=example.com and s=selector1. Anybody can later verify it with the public key published in DNS at selector1._domainkey.example.com. This proves that the domain's servers sent the message and that signed parts were not changed on the way. It does not prove that the message is good; spammers sign their mail too. But it ties a reputation to a domain name, and that is the basis of everything that follows.
retries | A mail transfer agent (MTA) now delivers to the recipient's domain. It asks DNS for the MX records of other.org, which list mail servers with priorities, for instance 10 mx1.other.org and 20 mx2.other.org, and then for their A and AAAA records. It tries the lowest number first, opening a TCP connection to port 25. If the server is down or answers 4xx, the message stays in the queue and is retried with growing delays (for example 5 min, 10 min, 20 min, up to about 1 hour) for up to 5 days; after that the sender receives a bounce message. Greylisting servers deliberately answer "451 try again later" to unknown senders, because spam software seldom retries. A retry loop with exponential back-off converts unreliable links into reliable delivery, at the cost of latency.
ratelimit | Before the message even starts, the receiving server decides how much it trusts the connecting IP address. It queries DNS blocklists (a lookup of the reversed IP under a blocklist domain returns an answer if the address is listed), consults its own reputation data about this IP and sending domain, and applies rate limits: how many connections, recipients and messages per minute this source may make. A new sender that suddenly sends 50,000 messages gets throttled with 421 or 451 replies. Roughly half of all email traffic worldwide is spam, so a big provider rejects most of it at this early stage, cheaply, before reading any content: refusing a connection costs microseconds, while scanning a message costs milliseconds. The limiter is usually a token bucket per source: tokens refill at a steady rate, each message spends one, and a burst is allowed only up to the bucket size.
dns | The receiving server consults DNS about the sender. The Sender Policy Framework check looks up a TXT record on example.com, such as "v=spf1 ip4:203.0.113.0/24 include:_spf.google.com -all", and tests whether the connecting IP address is listed. The DKIM check fetches the public key as described above. DMARC looks up _dmarc.example.com, for instance "v=DMARC1; p=reject; rua=mailto:...", which says what to do when neither SPF nor DKIM aligns with the visible From domain, and where to send reports. A reverse DNS (PTR) lookup of the sender IP is also checked. A few DNS queries, 1 to 20 ms each and run in parallel, determine whether the sender is who they claim. SPF has a limit of 10 lookups so that checks stay cheap and cannot be used to attack DNS.
pkcrypto | Verifying DKIM is a public-key operation. The receiver recomputes the body hash from the message as received, re-canonicalizes the signed headers, and verifies the signature against the public key from DNS: an RSA-2048 verification takes about 50 µs, much faster than signing, because the public exponent is small (65537). If a mailing list or gateway changed the subject or footer, the hash no longer matches and verification fails, which is why mailing lists have to re-sign or rewrite the From address. ARC headers let intermediaries vouch for the original result. Together, the three checks decide whether the mail is "authenticated": since 2024 large providers require SPF, DKIM and DMARC from bulk senders, and unauthenticated mail increasingly goes straight to spam or is rejected with a 550 error.
bayes | The content filter reads the message. A classic component is a naive Bayes classifier: it has counts of how often each word and token appeared in known spam and in known good mail, and combines the log-odds of the tokens in this message under an assumption that tokens are independent, which is wrong but works surprisingly well. Today's filters add machine-learning models over hundreds of features (links, URL reputation, header patterns, image hashes, how users of the provider treated similar messages), plus the authentication results and the sender's history with this recipient. The result is a score; high scores go to the spam folder, extreme ones are rejected, the rest pass. Filtering takes 5 to 50 ms and is retrained continuously, because spammers adapt, and a user clicking "Report spam" is one of the strongest training signals.
storageengine | The accepted message is stored. A large provider does not keep a file per message on one server: the message body goes to a distributed storage system, replicated across machines and data centers (or erasure-coded), and a small record per message (labels, flags, thread ID, size, a pointer to the body) goes to a database keyed by user. The server answers "250 OK" only after the message is safely stored in at least two places, since after the 250 the sending server deletes its copy and the responsibility moves. Storing is a few milliseconds in the same region. Classic servers using Maildir write one file per message into the user's directory, with a unique name, so that delivery needs no locks. Either way, the rule is the same as before: acknowledge only after the data is durable.
invindex | A mailbox with 100,000 messages must be searchable in a fraction of a second, so each new message is also added to the user's search index. The text of headers and body is split into tokens (lowercased, with stemming for some languages), and an inverted index maps each token to the list of message IDs that contain it. A search for "invoice from Alice" intersects the posting lists of the three terms, which are sorted lists, in a few milliseconds even in a mailbox of gigabytes, and the results are ranked by recency and relevance. Updating the index is done in small in-memory segments that are merged in the background. Indexing happens a moment after delivery, so a brand-new message can briefly be in the inbox before it is searchable.
pubsub | The recipient's devices should know about the message within seconds. The mail system publishes a "new mail" event on a topic for this mailbox. Subscribers include an IMAP connection waiting in IDLE (the server sends "* 1 EXISTS" over an open TCP connection), a webmail tab with an open stream (WebSocket or server-sent events), and push services: Apple's APNs or Google's FCM carry a small notification, a few hundred bytes, to the phone over its single always-on connection, which wakes the app or shows a banner. Delivering this takes 100 ms to a couple of seconds. The pattern is publish-subscribe: the mailbox does not know who listens, and a new device just subscribes, which is why a message can appear on a laptop, a watch and a phone at roughly the same moment.
http | When the recipient opens the message, the client fetches it with IMAP FETCH or with JMAP or the webmail API over HTTPS: a request of 300 bytes returns the headers and the body, often compressed, tens of KB. The client does not trust the content: the HTML is sanitized, scripts are removed, remote images are blocked or proxied by the provider, links are checked for phishing, and the display shows whether SPF, DKIM and DMARC passed. Marking the message as read is another small request that sets a flag in the database, and every other device syncs that flag through the same mechanism as before. The page you see is rendered by the browser's engine from the message HTML. Opening a message costs about one round trip plus some milliseconds, 50 to 200 ms in total.
pixels | Many marketing emails contain a tracking pixel: a one-pixel image whose URL holds a unique ID, such as https://track.example/o/9f8e7d.gif. When your client loads it, the sender's server logs one line with the time, your IP address (which hints at your location) and your client, and returns a 43-byte GIF. That is how senders count "opens". Privacy features now change the picture: Apple Mail Privacy Protection preloads every image through a proxy at delivery time, so the open counts are inflated and do not show your IP address, and Gmail serves images through its own cache. Links in the mail use the same idea with redirects, each click logged in a short URL. A trivial HTTP request is enough to carry information back to the sender, and your mail client decides if it is allowed to send it.

## What happens when your laptop boots | From a power button to a login screen, through firmware, a signed bootloader, a kernel and the first process
liion | You press the power button. It is not wired to the CPU but to a small embedded controller (EC) that is always powered from the battery, even when the laptop is "off", and uses a few milliwatts. The EC checks the battery and charger, and starts the power sequence. A power management chip turns the battery's 11 to 15 volts into a dozen rails: 1.8 V, 1.1 V, about 0.8 to 1.2 V for the CPU cores, 1.1 V for the memory, and so on, and it turns them on in a strict order, waiting for a "power good" signal from each. A lithium-ion battery of 50 to 70 Wh can deliver tens of amps for this. When everything is stable, the EC releases the reset line of the CPU. All of this takes 20 to 100 ms, before a single instruction runs.
hwclocks | Chips cannot run until clocks tick. A crystal oscillator at 24 or 38.4 MHz (and a 32.768 kHz one for the real-time clock) produces the reference; phase-locked loops inside the processor multiply it to bring up the core at 1 to 5 GHz, the memory controller, the PCIe lanes and the USB. A PLL compares its output, divided down, to the reference, and adjusts a voltage-controlled oscillator until they match; it needs tens of microseconds to lock. At boot the cores start at a conservative speed and the firmware raises it later. The real-time clock, kept alive by the battery or a coin cell, is read to set the date. A wrong clock is a serious problem for the next steps, because certificate validity and file timestamps depend on it.
x86 | The CPU wakes in its oldest state. An x86 core starts in 16-bit real mode and fetches its first instruction from the reset vector at the address 0xFFFFFFF0, 16 bytes below the 4 GB line, where the chipset maps the firmware flash chip (an SPI flash of 16 to 32 MB). On modern machines a separate security processor (Intel ME or AMD PSP) starts even earlier, verifies the first firmware block with a signature burned into fuses (Boot Guard), and only then lets the main cores run. The first instructions are a short jump and setup code that has no memory yet: the firmware uses the CPU's cache as a scratch RAM ("cache as RAM"), a few hundred KB, to run its first C code. ARM laptops follow the same idea from a boot ROM inside the chip, which verifies the next stage.
dram | The firmware cannot do much without main memory, so it must first wake the DRAM. It reads the module's SPD chip over a slow serial bus to learn its size and timings. Then comes memory training: DDR5 runs at 4,800 to 6,400 MT/s, so each data bit lasts about 150 to 200 picoseconds, and the signal travels on traces of different lengths. The controller sends test patterns and adjusts delays and voltage references per lane until the eye of the signal is centred, which takes 100 ms to 2 seconds on a cold boot. Results are cached in flash for a fast restart. Then the firmware tests a bit of memory, sets up the address map and switches from cache-as-RAM to the real DRAM; there are now 16 GB to use.
isa | With memory working, the firmware (UEFI) runs in phases: security, pre-EFI initialization, driver execution and boot device selection. Early on it switches the CPU from 16-bit real mode, which can address 1 MB, to 32-bit protected mode and then to 64-bit long mode, which turns on paging: the CPU sets control register bits, loads the global descriptor table and installs page tables that map memory with 4 KB, 2 MB or 1 GB pages. After this, the instruction set seems to be the same 64-bit one that your programs use, but with a full memory model and privilege rings (ring 0 for firmware and kernel, ring 3 for applications). The legacy modes still exist in silicon for compatibility, which is why a modern CPU boots like an 8086 from 1978.
nvme | The firmware discovers the hardware: it scans the PCIe bus, assigning each device a range of addresses and enumerating the NVMe SSD, the GPU, USB and network controllers. It loads a small driver for each class from the firmware volume. The NVMe driver sets up an admin queue pair and an I/O queue pair in memory (ring buffers) and tells the SSD where they are. To read a block, the firmware writes a 64-byte command into the submission queue and rings a doorbell register; the SSD fetches it with DMA, reads the flash and writes a 16-byte completion entry. A first read of the GPT partition table (sector 1) takes about 100 µs. The same queue design is used later by the Linux kernel, with up to 64,000 queues.
signatures | If Secure Boot is enabled, UEFI refuses to run code it cannot verify. The boot loader file is read from the EFI System Partition (described in the next step), and before it is executed, the firmware computes its SHA-256 hash and checks the embedded RSA-2048 signature against the certificates in its db database; a distribution's first-stage loader (shim) is signed by Microsoft's UEFI CA, which then verifies the distribution's own boot loader and kernel. A revoked or unsigned binary is rejected. In parallel, measured boot extends hashes into the TPM: each stage computes the hash of the next stage and extends a register as PCR = SHA-256(PCR || hash). The register can never be set, only extended, so its final value records the whole sequence. Disk encryption keys can then be released only if the chain is exactly the expected one.
filesystems | The ESP is a small FAT32 partition (100 to 500 MB) at the start of the disk. The firmware's FAT driver finds the file \EFI\ubuntu\grubx64.efi (or systemd-boot) and loads it into memory, about 1 to 4 MB, and starts it. The boot loader reads its configuration, may show a menu for 0 to 5 seconds, and then loads the Linux kernel image (vmlinuz, about 12 MB compressed) and an initial RAM file system (initramfs, 30 to 100 MB) from /boot into memory using the firmware's disk services. It builds the kernel command line, for example root=UUID=... quiet splash, and jumps to the kernel entry point. The boot loader has to understand just enough of a file system to read a file, and then it disappears.
linux | The kernel starts decompressing itself (zstd or xz), which turns 12 MB into about 50 MB in 100 to 200 ms, and relocates to a random address (KASLR) so that attackers cannot predict where its code is. It then runs start_kernel: it parses the ACPI tables that describe the hardware, sets up its own page tables, a memory allocator over all RAM, the console and the timer. Many subsystems are initialized one after another: the scheduler, the interrupt system, the virtual file system, networking, cryptography, and hundreds of drivers matching the discovered PCI and USB devices. The log you see with dmesg has 1,000 to 5,000 lines, each with a timestamp in seconds. Kernel boot usually takes 1 to 3 seconds on a desktop machine, and a lot of that is waiting for hardware.
vmem | One of the first things the kernel does is take control of virtual memory. It builds its own page tables with a direct map of all physical RAM at a high virtual address, so that kernel code can reach any physical page, and a separate region for kernel code and modules. Each process will later get its own page table root, switched through the CR3 register, so processes see private address spaces from 0 up to 128 TB and cannot see each other's memory. A page table walk has 4 levels (5 on the newest CPUs) and costs up to 4 memory accesses, hidden by the TLB, which caches recent translations. Kernel address space layout randomization, guard pages and the no-execute bit on data pages make exploitation harder. After this step, no code can reach memory unless the kernel maps it.
interrupts | Next the kernel programs the interrupt hardware. The local APIC of each core and the I/O APIC route device signals to cores; PCIe devices use message-signalled interrupts, which are just memory writes to a special address. The kernel installs an interrupt descriptor table with 256 entries, each pointing to a handler. It starts the timer: a periodic or one-shot interrupt (from the APIC timer or HPET) that fires up to 1,000 times a second and gives the kernel control, so that it can run its scheduler even if a program never yields. The other cores, which have been parked, are woken with inter-processor interrupts; a laptop with 8 or 16 cores now has all of them running kernel code, each with its own run queue and idle loop.
fsjournal | The kernel unpacks the initramfs into memory. The small programs inside load the storage driver, and if the disk is encrypted, ask for your passphrase: a key-derivation function such as Argon2 or PBKDF2 turns it into the disk key, deliberately taking about 1 to 2 seconds to slow down guessing, and the TPM can supply the key without asking. The root file system (ext4, btrfs or XFS) is then mounted. If the machine was shut down uncleanly, ext4 replays its journal: the operations that were logged but not yet applied are re-applied in 100 ms to a few seconds, and the file system becomes consistent without scanning the whole disk. The kernel then switches to the real root with pivot_root and is ready for the first program.
process | The kernel starts the first user-space process by executing /sbin/init, which is typically systemd. This process is PID 1 and its parent is the kernel itself; every other process descends from it with fork and exec. systemd reads about 200 to 300 unit files and builds a dependency graph of services, mounts, sockets and timers. It starts everything it can in parallel, in the right order: udev for devices, journald for logs, the network manager, the Bluetooth daemon, a time sync service, and finally a display manager. Each service runs in its own control group with limits. When PID 1 dies the kernel panics, because nothing can adopt orphaned processes. Typical user space start-up is 3 to 10 seconds, and systemd-analyze blame lists the slow services.
scheduling | With dozens of processes ready and only 8 cores, the scheduler decides who runs. Linux uses the Completely Fair Scheduler or its successor EEVDF: each task has a virtual runtime, and the one that has received the least CPU time per unit of weight goes next. Time slices are a few milliseconds. When a service waits on the disk or network, it is taken off the run queue and a different one gets the core; a context switch takes 1 to 5 µs plus cache refill costs. During boot the machine is busy in bursts, and the scheduler balances tasks across cores and keeps each task near its cached data. Nothing is slow because of a lack of CPU time for long; mostly systemd is waiting for disks, devices and timeouts.
simt | The graphical session needs the GPU. The kernel's DRM driver (i915, amdgpu or nouveau/nvidia) loads firmware blobs into the GPU, allocates a framebuffer in memory and performs mode setting: it reads the display's EDID, chooses 2560 by 1600 at 60 Hz, programs the display controller's timing registers and starts the scan-out by DMA. Early in boot you saw a low-resolution picture from the firmware; the switch to native resolution is the flicker that happens during startup. The display manager (GDM or SDDM) then starts a Wayland compositor, which uses the GPU to draw the login screen: the GPU runs thousands of shader threads in parallel to paint the background, text and animations at 60 frames per second. Your fingerprint reader and keyboard now send input events to it.
memhier | The login screen waits and the machine looks idle, but every cache in the system is still cold. The first time a program runs, its code must be read from the SSD (about 100 µs per 4 KB page), then lands in the page cache in DRAM (about 80 ns per access), then in the L3 (about 10 ns), the L2 (about 4 ns) and finally the L1 (about 1 ns). That is why the first launch of a browser takes two seconds and the second takes half a second. After boot, the page cache holds hundreds of MB of system libraries and the CPU's branch predictors have learned the common paths. A boot is a long chain in which each stage warms the memory hierarchy for the next, and speeding it up usually means doing less work, not doing it faster.
transistor | At the very bottom, everything you just read is signals in silicon. The CPU holds 10 to 30 billion transistors, each a switch controlled by a voltage on its gate; a power button press ultimately had to lift the supply to the chip and let those switches change state billions of times per second. When the reset line is released, the first instruction fetch moves electric charge through gates only nanometres wide, and from there everything is the same hardware doing different amounts of work. The time of boot, 10 to 30 seconds, is mostly spent waiting for physical things: DRAM calibration, a disk read, a hardware initialization with timeouts, a human typing a password. Computation itself, billions of instructions, takes just a second or two.

## What happens when you make a video call | From a camera sensor and a microphone to packets, a media server and the other person's screen
http | You click Join. The web page loads over HTTPS and opens a signaling channel to the service, usually a WebSocket over TLS, which is only used to set up the call and to carry control messages. Your browser creates an SDP offer, a text document of 2 to 5 KB describing what it can send and receive: audio codecs (Opus), video codecs (VP8, H.264, AV1), encryption fingerprints, and the network candidates it found. The server forwards it to the other participants or to a media server, and an answer returns the same way, taking 50 to 200 ms. Then the browser asks permission to use the camera and microphone (getUserMedia) and shows the picture. Signaling is slow and reliable text over TCP; the media itself will never touch this path, because voices and faces move over UDP.
bandgap | The camera sensor is a silicon chip. Each pixel contains a photodiode: a photon of visible light with more energy than silicon's band gap of about 1.1 eV knocks an electron from the valence band into the conduction band, and the pixel collects these electrons in a small potential well for the duration of the exposure, 1/30 s or less. About 70 to 90% of photons produce one electron in a good sensor. A colour filter array (Bayer pattern: 50% green, 25% red, 25% blue) sits above the pixels, so each one measures only one colour. In dim rooms only a few hundred electrons are collected per pixel per frame, and the camera must work with that. A 1080p sensor has 2 million pixels, and it is read out 30 or 60 times each second.
noise | A pixel with 300 collected electrons has an unavoidable statistical error: photons arrive randomly (shot noise), so the uncertainty is the square root of the count, about 17 electrons, or 6%. On top of that come thermal noise from the readout electronics and dark current in the silicon. An analog-to-digital converter turns each pixel's voltage into 10 or 12 bits. The image signal processor then reconstructs full colour from the Bayer samples (demosaicing), reduces noise by averaging neighbours and frames, adjusts white balance and exposure, and sharpens. A dark room means a noisy image that is much harder to compress, since random noise has no patterns. This is why video calls look worse in poor light, and why encoders sometimes blur the noise away on purpose.
dma | The camera sends each frame to the computer: over USB (as uncompressed YUV or MJPEG) or MIPI CSI on a laptop or phone. A 1080p frame in YUV 4:2:0 is 1920 x 1080 x 1.5 = 3.1 MB, so 30 frames per second are about 93 MB/s, or 750 Mbit/s. A DMA engine writes the lines of the frame directly into buffers in main memory, and an interrupt tells the kernel when a whole frame is complete. The kernel's video driver (V4L2 on Linux) hands the buffer to the browser through a shared memory file descriptor; no copy is needed. The frame is available about 33 ms after the exposure began, and every later step adds to the delay. Audio takes its own path: the microphone's 48,000 samples per second arrive in chunks of 10 ms (480 samples).
fourier | Audio needs more cleaning than video. The microphone also picks up the other person's voice coming from your speakers, so an acoustic echo canceller uses the signal you played to predict the echo and subtract it, with adaptive filters that work in the frequency domain with FFTs. Noise suppression removes fans and keyboards by estimating the noise spectrum, and automatic gain control levels the volume. Then Opus encodes 20 ms frames (960 samples) using the MDCT, a transform to frequencies, and a speech model for low bitrates. At 32 kbit/s, 20 ms of audio becomes about 80 bytes, which is 50 packets per second. Opus can go from 6 kbit/s to 510 kbit/s, adapts to the network in real time and adds only 5 to 26 ms of delay.
codecs | The raw video would need 750 Mbit/s, which no network can carry, so an encoder compresses it by 300 times or more to about 1 to 2.5 Mbit/s for 720p to 1080p. Real-time encoding has strict limits: no B-frames, because they need future frames; very short groups of pictures; and about 5 to 15 ms per frame, using a hardware encoder in the GPU or system chip, or an optimized software encoder with SIMD instructions on 2 to 4 cores. Most frames are P-frames, small ones that describe changes against the previous frame. An occasional keyframe (I-frame), 5 to 20 times bigger, is sent on request, for example when a new participant joins or a packet was lost beyond repair. The encoder's output is a stream of 10 to 40 KB frames, each split into packets of at most 1,200 bytes.
motioncomp | Inside the encoder, the main saving comes from not repeating what did not change. For each 16 by 16 block of a new frame, motion estimation searches the previous frame for the best-matching block, within a window of maybe 32 pixels. It stores a motion vector (a few bits) and the small difference left over. In a video call, the background is static and the person moves slowly, so most blocks reduce to "same as before, shifted by one pixel" and the residual is nearly zero, which a DCT and quantizer then reduces to a handful of bytes. This is the reason a call with a still background fits in 1 Mbit/s and a screen share of a scrolling document or a sudden camera shake needs much more. The encoder constantly trades bits against quality under the bitrate limit set by the network.
nat | Your laptop sits behind a home router with a private address such as 192.168.1.20; the other person is behind a different one. Neither can accept a new inbound connection. ICE solves this: each side collects candidate addresses, its own local ones, one learned by asking a STUN server "which public address and port do you see for me?" (a UDP request of 20 bytes, an answer of 32 bytes), and a relay address allocated on a TURN server. The candidates travel through the signaling channel. Both sides then send STUN checks to each other's candidates at the same time; the outgoing packets create mappings in each NAT that let the other side's packets in ("UDP hole punching"). The best working pair is chosen in 100 to 500 ms. About 80 to 90% of calls connect directly; the rest go through the TURN relay.
tls | A path exists, but it is not trusted yet. The peers run a DTLS handshake (TLS adapted to UDP, with its own retransmission timers) over the chosen path. Each side presents a self-signed certificate, and the hash of that certificate was already sent in the SDP through signaling, so a man in the middle who does not control the signaling cannot substitute his own. The handshake takes 2 to 4 round trips, a few hundred bytes to a few KB, and ends with keying material exported for SRTP. WebRTC makes encryption mandatory: there is no unencrypted call. If the signaling server is malicious it can still redirect the call, which is why apps that want true end-to-end security add their own identity or key verification layer.
aead | Every media packet is an RTP packet protected with SRTP: a 12-byte RTP header (payload type, sequence number, timestamp, SSRC identifying the stream), the encoded payload and an authentication tag, using AES-GCM or AES-CTR with HMAC. The sequence number is also the nonce input, so a repeated or forged packet is rejected, and the header is authenticated but, except for selected extensions, not hidden. Encrypting 1,200 bytes costs less than a microsecond on a CPU with AES instructions. Add 8 bytes of UDP and 20 of IP header, and an audio packet is about 120 bytes, a video packet about 1,240. At 50 audio and 100 to 300 video packets per second, the call sends about 200 to 300 packets per second per direction, which is trivial for any network card.
congestion | UDP has no congestion control, so WebRTC brings its own. Every received packet is reported back in transport-wide feedback messages; the sender compares departure and arrival times, and if the one-way delay grows from packet to packet, a queue is filling up somewhere, usually in the router at the narrowest link. A Kalman-like filter estimates this delay gradient (Google Congestion Control), and the sender cuts its rate by about 15% when it sees overuse, or probes gently upwards when it sees none. Loss is used as a second signal. The result is a target bitrate, updated every 100 ms or so, which is given to the video encoder, in direct contrast to TCP which waits for packet loss. Meanwhile the call has to share the link fairly with a download running on the same Wi-Fi.
pubsub | In a call with more than a few people, the peers do not connect to each other in a full mesh (with 8 people, each would send 7 copies of its video). Each participant sends one stream to a server called a Selective Forwarding Unit (SFU), which forwards packets to every subscriber without decoding them, only rewriting headers (sequence numbers, SSRC) and checking subscriptions. It is a publish-subscribe system for media: a sender publishes tracks and receivers subscribe to the ones they want to see. The uplink of a participant stays constant, while the SFU's downlink grows with the number of viewers. An SFU on a cheap server forwards hundreds of Mbit/s and costs the sender about 1 ms of latency. A server that decodes and mixes all streams (an MCU) would use 10 to 100 times more CPU.
abr | The same participant is watched by some people on a phone and by others on a big screen, with different bandwidths. So the sender uses simulcast: it encodes the camera three times in parallel, for example 180p at 150 kbit/s, 360p at 500 kbit/s and 720p at 1.5 Mbit/s, or one scalable stream with temporal and spatial layers (SVC). The SFU picks, for each receiver, the highest layer that fits the receiver's estimated bandwidth and the size of the tile on the screen; the tile of a person who is not speaking gets the small layer. When the receiver's bandwidth drops, the SFU switches layers at the next keyframe (or at once with SVC) and nobody has to renegotiate. This is adaptive bitrate for live video, but with decisions every few hundred milliseconds instead of every 4 seconds.
codingtheory | Packets are lost: Wi-Fi loses 1 to 3% in a bad room, and a mobile link bursts. Retransmitting costs a round trip, so the receiver uses a mix of methods. For video, a lost packet is requested again with a NACK if there is time (a round trip under about 100 ms); otherwise forward error correction sends extra parity packets (an XOR of a group of packets, or Reed-Solomon style codes) so the receiver can rebuild a missing one without asking; and if all fails, the receiver asks for a keyframe (PLI). For audio, Opus has in-band FEC that carries a lower-quality copy of the previous frame in the next packet, and packet loss concealment makes up a missing 20 ms by extending the last waveform. Error correction trades extra bits for lower latency under loss.
queuesbuf | Packets arrive with irregular timing and sometimes out of order: they travelled through different queues, and Wi-Fi retries add delay. Playing them at the moment of arrival would make the audio crackle. So the receiver puts them in a jitter buffer, a queue sorted by sequence number, and releases each frame at a scheduled time. The buffer is adaptive: it measures the variation in arrival times and keeps just enough delay to cover it, usually 20 to 80 ms for audio, and it speeds up or slows down the playback by a few percent (time-stretching) to change the size without audible jumps. Too small a buffer gives dropouts; too large a buffer makes conversation awkward, since people start to talk over each other. The video jitter buffer is separate and is synchronized to the audio.
hwclocks | Audio and video travel separately and must meet at the screen with a lip-sync error below about 45 ms early or 125 ms late, or it becomes noticeable. RTP timestamps count ticks of a media clock, 48,000 per second for Opus and 90,000 per second for video, starting at a random value, so they say nothing about real time. RTCP sender reports, every second or so, pair an RTP timestamp with the sender's wall-clock time (NTP format), so the receiver can map both streams onto the sender's timeline and play them together. The two ends' crystals differ by tens of parts per million, so the receiver's audio clock drifts about 1 ms every 20 to 50 seconds against the sender's; the player resamples by a tiny amount to keep up. Without this the delay would grow forever, or the buffer would run dry.
perception | After decoding, the speaker plays your voice and the screen shows your face. The human senses decide what counts as good enough. Hearing masks quiet sounds near loud ones, so Opus spends no bits on them; vision detects fine detail poorly in moving areas and in colour, so the encoder uses coarse chroma and heavy quantization there. Delay is the most important quality factor: ITU-T G.114 says one-way delay up to 150 ms is acceptable for most people; at 300 ms or more conversations break down into awkward overlaps. The video you see is also a little late compared with the sound you hear, and the brain tolerates audio arriving slightly after video, as in a distant thunderclap, better than the reverse. Perceptual coding is the reason a 300x compression looks like a face.
lightspeed | Add up the delays from your mouth to the other person's ear: microphone and capture buffer 10 to 20 ms, audio processing and encoding 20 to 30 ms, sender-side pacing a few ms, network 20 to 100 ms, jitter buffer 40 to 80 ms, decoding and playout 10 to 20 ms; for video, add 33 ms capture, 10 ms encoding, 10 ms decoding and 16 ms display. The total is typically 150 to 300 ms. The part that no software can reduce is the speed of light in fibre: 5 µs per km, so a call between Bengaluru and San Francisco, about 14,000 km, needs at least 70 ms one way, even with perfect equipment. Real routes are 1.5 to 2 times longer than a straight line. That is why services put media servers close to the callers, and why a call between neighbours feels more natural than one between continents.

## What happens when a program calls malloc and touches the memory | From a pointer returned in nanoseconds to a page fault, a DRAM row and a leaking capacitor
allocators | Your C program calls p = malloc(100). This is not a system call but a function in the C library (glibc's ptmalloc). It adds an 8-byte size header and rounds up to a multiple of 16, so it needs a chunk of 112 bytes. The fastest path is the per-thread cache (tcache): an array of 64 singly linked free lists, one for each chunk size from 32 to 1040 bytes, each holding up to 7 recently freed chunks. If the 112-byte list has an entry, malloc pops it, which takes about 20 instructions and 5 to 10 ns, and returns the address with no lock and no kernel involvement. No memory is cleared either, so the old contents are still there. This path serves the great majority of all allocations in a typical program, which is why a good allocator can make 100 million small allocations per second per thread.
thread | If the tcache list is empty, malloc turns to the arena, the shared heap structure. Every thread is attached to one arena, and the library creates up to 8 arenas per core, so that threads rarely fight over one structure. A first, smaller fallback checks the fastbins (exact-size lists of small chunks, up to 128 bytes, with no merging) and the smallbins, then the unsorted list of recently freed chunks, then larger bins that hold sorted ranges of sizes. At each step it can split a bigger chunk and put the remainder back. This takes 50 to 200 ns. Per-thread caching is the central design idea: by giving each thread its own small stock, most calls never touch shared data, and the program scales with the number of cores instead of waiting in line.
locks | When a thread must use its arena, it takes the arena's mutex. A mutex is built from an atomic compare-and-swap instruction on a word in memory; if it succeeds, the lock is taken in about 20 cycles when the cache line is already local. If another thread holds it, the second thread spins briefly and then calls futex(), a system call that puts it to sleep until the holder wakes it. Contention is the enemy: with 64 threads hammering one arena, an allocation can cost microseconds instead of nanoseconds, and the lock's cache line bounces between cores. Free-list manipulation under the lock is short (tens of instructions), so uncontended locking is cheap. Allocators such as jemalloc and tcmalloc use more per-thread and per-CPU caches to avoid the lock almost entirely.
syscalls | If the arena has no suitable free chunk, malloc must get more address space from the kernel. For the main arena it calls brk() (or sbrk) to move the end of the heap up, asking for the request plus a top pad of 128 KB, so that the next 1,000 small allocations are free. For a request of 128 KB or more (the threshold grows dynamically up to 32 MB), it calls mmap() with MAP_ANONYMOUS to get a fresh region of its own. A system call costs about 100 to 300 ns for the mode switch plus the work: brk takes about 1 µs because it only changes a number in the process's memory descriptor. Other arenas get their memory from mmap'd 64 MB heaps. The kernel has handed over only addresses, not memory: no byte of RAM has been assigned yet.
mmap | A large allocation, say malloc(1 GB), becomes an anonymous mmap. The kernel creates a virtual memory area (a vm_area_struct, about 200 bytes) describing the range, its permissions (read and write) and the fact that it is anonymous, zero-filled and private. It checks the overcommit policy: by default Linux allows the call even if the machine has only 8 GB of RAM, because most programs never touch everything they ask for. That is why malloc can succeed for sizes that the machine could never provide, and why the real failure shows up much later as the OOM killer and not as a NULL pointer. With a file instead of the anonymous flag, the same call maps the file's pages into your address space, and loading a library or a database file works the same way.
vmem | The pointer you got is a virtual address, a number in your process's private 48-bit address space. To the CPU, every memory access must be translated by the page tables into a physical address. For a new region, the page table entries are absent. The process owns a tree of 4 levels with 512 entries each; the root's physical address is held in the CR3 register and is replaced on every switch to another process. The CPU walks the tree in hardware: up to 4 memory accesses, though most are caught by the TLB, a small cache of recent translations with about 64 entries in L1 and 1,500 to 2,000 in L2, which hits in 1 to 7 cycles. A walk with missing entries finds a "not present" mark and the CPU raises an exception.
interrupts | The first time you write p[0] = 'x', the page does not exist. The MMU raises a page fault, exception 14, a kind of synchronous interrupt: the CPU saves the faulting instruction's address, stores the faulting virtual address in CR2, and jumps to the kernel's fault handler. The handler finds the VMA covering the address, checks that a write is permitted, and takes a free 4 KB frame from the buddy allocator. It zeroes the frame (about 100 to 300 ns, because no program may see another's leftover data), writes a page table entry pointing to it, and returns to the instruction, which now runs again and succeeds. A minor page fault like this one costs 0.5 to 1.5 µs; touching a 128 KB heap area costs 32 faults, about 30 µs. If the kernel is using transparent huge pages, one fault maps 2 MB and zeroing costs 100 µs but saves 511 further faults.
nscgroups | In a container or a systemd service, the memory cgroup counts every page the process uses. When a fault allocates a frame, the kernel charges 4 KB to the group, and if the total would exceed memory.max, it first reclaims pages inside the group: dropping clean page-cache pages, writing dirty ones, and swapping anonymous memory if allowed. If that fails, the kernel's OOM killer picks the process with the highest score (largest memory use, adjusted by oom_score_adj) in that group and sends SIGKILL; your program just dies with no error message from malloc. This is why a container with a 512 MB limit can crash even though malloc never returned NULL: the failure comes from the touch, not from the request. Setting limits and watching memory.events are the main tools for this.
cachelines | Your write does not go straight to memory. The CPU moves data in 64-byte cache lines. The 112-byte chunk you hold spans two or three lines, and the allocator's 16-byte alignment guarantees that p is a valid target for any ordinary type, though it does not align to cache lines. The store brings the line into the L1 data cache (32 to 48 KB, 8 to 12 ways). Sequential use is cheap: after the first miss, the hardware prefetcher fetches the next lines. Placement matters more than people expect: two threads writing to two different variables that happen to sit in the same line will force it to bounce between cores, "false sharing", and can make a program 10 times slower. This is why per-thread allocations and padding exist.
coherence | With 8 cores, each core has private L1 and L2 caches, so the same memory line may be in several places. A coherence protocol (MESI and its relatives) keeps them consistent: before core 2 may write to a line, it asks for exclusive ownership, and other cores' copies are invalidated. If core 5 later reads the pointer you stored, the line moves from core 2's cache into core 5's through the on-chip interconnect in about 40 to 100 ns, much slower than an L1 hit. Memory ordering rules then say when each core sees the writes of the others; you need atomics or locks to publish the data safely. malloc is affected too: when thread A frees a chunk that thread B allocated, the chunk's header line moves to A's core and the chunk joins A's cache, so memory slowly migrates between threads.
numa | On a server with two CPU sockets, memory is attached to a particular socket. The kernel's default policy gives a page from the node of the CPU that first touches it ("first touch"), so a thread that allocates and uses memory on the same core gets local DRAM at about 80 ns, while a page on the other socket costs 130 to 200 ns and shares a limited interconnect link. A program in which one thread initializes a giant array and 32 others read it will find all pages on one node and slow down. numactl and libnuma, or the scheduler's automatic NUMA balancing, move pages or threads to fix it. On a laptop you will never notice, but in a data center it is one of the commonest hidden causes of poor scaling.
memhier | Now the hierarchy decides the speed of every later access to p. L1 hit: 4 to 5 cycles, about 1 ns. L2 hit: 14 cycles, 4 ns. L3 hit: 40 to 70 cycles, 10 to 20 ns, shared among cores. DRAM: 70 to 100 ns, about 300 cycles during which an out-of-order core can run 1,000 or more other instructions if it finds independent work. Bandwidth is 50 GB/s or more, but one thread chasing pointers in a linked list gets a single miss at a time, about 100 MB/s. Your first touch of a new page therefore costs the fault (about 1 µs), the TLB fill, and a cache miss, and subsequent accesses cost 1 ns. The cost of malloc is small; the cost of touching new memory, and of cold caches, is what you usually pay for.
dram | When the line is not in any cache, the request goes to the memory controller. DRAM is organized in channels, ranks, banks and rows: a bank has 65,536 rows of 8 KB. To read, the controller issues ACTIVATE for the row (about 14 ns to copy the row into the bank's sense amplifiers), then READ for the column (about 14 ns), and a burst moves 64 bytes over a 64-bit bus in 8 transfers. If the next access falls in the same open row, only the second step is needed ("row hit"); a different row requires closing it first (PRECHARGE, another 14 ns). The controller reorders requests to keep rows open and many banks busy. Every cell also needs a refresh: all rows are re-read and rewritten every 32 to 64 ms, which takes a few percent of the bandwidth.
transistor | A DRAM bit is a tiny capacitor, about 10 femtofarads, with a single access transistor that connects it to a bit line. A "1" is a few tens of thousands of extra electrons stored on it; a "0" is none. The charge leaks within tens of milliseconds, through the transistor's off-state current and through the dielectric, which is why refresh exists; each time you read a row, the read is destructive and the sense amplifier writes the value back. The 8 GB in your machine contains 69 billion such cells, each a nanometre-scale structure of silicon, oxide and metal. A write by your program ends as tens of thousands of electrons pushed onto one of them. When you power off, the electrons drain away, and your 'x' is gone in seconds.
exploitmit | The memory around p is also an attack surface. The chunk header sits in front of your 100 bytes and the next chunk's header is right behind them. A buffer overflow from p[100] onwards overwrites the next chunk's size and free-list pointers, and a clever attacker can turn a later malloc or free into a write of a chosen value to a chosen address. Allocators defend themselves: glibc XORs free-list pointers with a value derived from their own address (safe-linking), checks the sizes and the double-free key stored in freed tcache chunks, and aborts with "free(): invalid pointer" when something looks wrong. ASLR randomizes where the heap lives, and tools such as AddressSanitizer or hardened allocators add red zones and guard pages. Memory-safe languages remove the problem at the source.
amortized | The average cost of a malloc is therefore much less than its worst case. Most calls return in 10 to 50 ns from the thread cache. One call in thousands falls through to the arena for 100 ns, and one in a hundred thousand makes a brk call (1 µs) which sets up 32 pages whose first touches then cost 30 µs. Thanks to the 128 KB top pad, the expensive events occur rarely. When you free(p), the chunk usually goes back on the tcache list in about 10 ns, with no kernel call; only when a large contiguous space at the top of the heap becomes free (more than 128 KB) does the allocator return it with a negative brk or madvise. Averaged over millions of calls, the cost per allocation is a few tens of nanoseconds, which is amortized analysis at work.
gc | In languages with garbage collection, the same layers exist but the free is automatic. The JVM allocates objects by bumping a pointer in a thread-local buffer, one add instruction, and the collector later finds which objects are reachable from roots, copies the live ones, and discards the rest; the dead objects cost nothing. The price is pauses (milliseconds, with modern concurrent collectors) and memory overhead of 20 to 100%. In C you pay at each free, in Java at each collection, and in Rust the compiler inserts the free where ownership ends. Underneath all of them is the same stack: a virtual address, a page fault, a cache line, a DRAM row and tens of thousands of electrons. Understanding one allocation end to end makes performance numbers in any language make sense.

## What happens when a process starts with fork and exec | From a shell command to a running program, through copy-on-write, an ELF file and the dynamic linker
parsing | You type ls -l *.txt and press Enter in a shell such as bash. The shell reads the line and parses it: it splits it into words with quoting rules, expands the wildcard *.txt by reading the directory (the command becomes ls -l a.txt b.txt), handles redirections like > out.txt and pipes with |, and checks whether the first word is a built-in such as cd. A built-in runs inside the shell itself, because only the shell process can change its own working directory. ls is not a built-in, so the shell must create a new process. The shell searches the directories listed in PATH, calling stat() on /usr/local/bin/ls, /usr/bin/ls and so on in order, which is why a long PATH slows down command lookup (bash remembers the answer in a hash table). Parsing takes microseconds.
syscalls | Unix creates processes in two steps. First the shell calls fork() (in modern glibc this is the clone system call). The CPU executes the SYSCALL instruction, which switches to ring 0, loads the kernel entry address from a model-specific register, and swaps to the kernel stack of the calling thread in about 50 to 100 ns. The kernel saves the user registers in a structure on that stack (pt_regs), looks up the system call number in a table (56 for clone on x86-64), runs the handler, and returns with SYSRET. The return value is different for the two copies: the parent gets the new process ID, such as 28141, and the child gets 0, so the same code can tell which one it is. The whole mechanism is the only gate from user programs into the kernel.
vmem | fork() must give the child a copy of the parent's whole memory, but copying 50 MB each time would be absurd. The kernel instead copies the bookkeeping: a new task_struct (a few KB, with the process ID, credentials, signal handlers and scheduling state), a new memory descriptor, and a copy of the page tables (the shell with 10 MB of resident memory has 2,500 pages, taking 20 to 100 µs to copy). Then it marks every writable private page read-only in both processes. The data pages themselves are shared. This is copy-on-write: the two processes appear to have private memories, but physical memory is duplicated one page at a time, and only for pages that are actually modified. A fork of a large server with 100 GB can still take tens of milliseconds because of the page tables alone.
iomodels | The kernel also duplicates the file descriptor table. Descriptors 0, 1 and 2 (standard input, output and error) in the child point to the same open file descriptions as in the parent: the terminal, or a pipe. Shared descriptions mean that they share a file offset, which is why parent and child writing to the same file append in order. This is also the trick behind redirection and pipes. Between fork and exec, the child runs shell code that opens out.txt and calls dup2() to make it descriptor 1, or sets up the read and write ends of a pipe, so that the program that runs next just writes to "standard output" and does not know where it goes. Descriptors marked close-on-exec are closed automatically at exec, so secrets do not leak into the new program.
interrupts | Right after fork, both processes are about to write to their stacks and variables. The first write by either of them to a read-only shared page causes a page fault. The kernel's handler sees that the page is copy-on-write and shared (reference count 2), allocates a new 4 KB frame, copies the 4096 bytes (about 200 to 500 ns), points the writer's page table entry to the copy with write permission, and restarts the instruction. The other process, now the only owner, gets its write permission back at its next fault. The child will never touch most of its inherited pages, because it is about to replace everything, so very few of these faults happen; a child that execs immediately costs only the page-table copy. For this reason vfork() and posix_spawn() skip even that by letting the child borrow the parent's memory until exec.
scheduling | The new child is put on a CPU's run queue. The scheduler picks a core for it, usually the parent's or a near one that shares a cache, and the parent now calls wait4() to wait for the child. That puts the parent to sleep, taking it off the run queue, until the child terminates. With a multicore machine, the parent and child could in principle run side by side, but a shell waiting for a foreground job has nothing else to do. The kernel's fair scheduler accounts CPU time for each task by a virtual runtime, and a newly forked task is placed so that it does not unfairly starve others. Creating the task costs 30 to 60 µs in total, including the allocation of a 16 KB kernel stack, and a modern machine can create about 20,000 to 50,000 processes per second per core.
ctxswitch | When the CPU changes from the parent to the child, the kernel performs a context switch: it saves the callee-saved registers and stack pointer of the old task, loads those of the new one, and switches the address space by writing the page-table root of the child into CR3. With PCID, the CPU tags TLB entries with a process identifier, so the switch does not need to flush the whole TLB. A switch itself takes 1 to 3 µs, but the indirect cost is larger: the new process's code and data are not in the L1/L2 caches or the TLB, so it starts slowly, "cold". The child begins running at the point where fork returned, in the shell's code, sees the return value 0, and goes on to do the redirections and then calls execve().
filesystems | The child calls execve("/usr/bin/ls", argv, envp). The kernel resolves the path by walking its components from the root: "usr", "bin", "ls". Each step looks up a name in the directory entry cache (dcache), a hash table in memory, taking 50 to 100 ns per component if cached, and reading a directory block from disk (100 µs) if not. At the end it holds the inode of the file and checks that the user has execute permission, the file system is not mounted noexec, and the file is a regular file. Set-user-ID bits are processed here as well. Then it opens the file and reads its first 256 bytes into a buffer. The kernel looks at the first bytes to find the right loader: the magic bytes 0x7F 'E' 'L' 'F' mean an ELF executable, and a "#!" at the start means a script, which is handled by running the named interpreter instead.
binary | An ELF file starts with a header of 64 bytes that gives the machine type (x86-64), the entry point address and the location of the program headers. Each program header (56 bytes) describes a segment to load: the code segment (readable, executable), the read-only data, the writable data and the BSS (zero-initialised variables that take no space in the file). The header PT_INTERP names the dynamic linker, /lib64/ld-linux-x86-64.so.2. The kernel reads this table, about 500 bytes, and decides what to map. Everything here is a binary layout designed for two-way use: the same bytes tell tools such as readelf what is in the file and tell the kernel how to build an address space from it, with no parsing beyond reading fixed-size fields at known offsets.
mmap | Now the point of no return: the kernel throws away the child's copy of the shell's address space (releasing the copy-on-write references) and builds a new one. For each loadable segment it calls the equivalent of mmap on the file: the code is mapped read-only and executable, the data read-write and private. The BSS and the heap start become anonymous zero pages. A stack is created at the top with the argument strings, the environment strings and the auxiliary vector (page size, entry point, a pointer to 16 random bytes). The kernel also maps the vDSO, a small shared library that lets programs read the time without a system call. Mapping is lazy: no file data is read yet, only the kernel's records are set up, which costs about 20 to 50 µs.
exploitmit | At this moment the kernel also applies security layout rules. Address space layout randomization picks random base addresses for the executable (if it is position-independent), the stack, the heap, the libraries and the vDSO, with 28 bits of entropy or so on 64-bit Linux, so an attacker cannot know where code is. The no-execute bit marks stack and heap pages as non-executable. The 16 random bytes in the auxiliary vector seed the stack canary, a secret value that the compiled code puts before each return address and checks before returning, to detect smashed stacks. Credentials are recomputed (for set-user-ID programs), capabilities are dropped as the rules say, and signal handlers are reset to their defaults. After execve the process looks completely new, but it keeps its process ID and its open file descriptors.
pagecache | When the CPU first fetches an instruction from the mapped code, there is no page-table entry, and a page fault happens. The kernel looks for the page in the page cache, the in-memory copy of the file. For a command run often, like ls, the page is already there, so it just maps that physical page, the same one that every other running ls uses, at a cost of 0.5 µs (a minor fault), and sometimes maps 16 pages around it ("fault-around") to cut the number of faults. If the file is not in memory (a major fault), the kernel issues a block read: about 100 µs on NVMe, 10 ms on a spinning disk. So running a program for the first time after boot is much slower than the second run: all of its pages come from disk once, and then 100 processes share one copy in memory.
hashtables | The first user-space code to run is not ls but the dynamic linker, ld.so. It reads the dynamic section of the executable to find the list of needed libraries (libc.so.6 and perhaps libselinux), finds each one through the cache file /etc/ld.so.cache, opens it, and maps its segments in the same way as above. Then it resolves symbols: every call to a library function, such as printf or malloc, must be bound to an address. The linker looks the name up in the libraries' symbol tables, which have a GNU hash table so that a lookup takes a few probes instead of a scan of thousands of symbols. By default binding is lazy: the first call goes through the PLT stub into the linker, which patches the GOT entry so that later calls jump directly. This phase takes 300 µs to 1 ms for a small program.
memhier | The process now starts, and it starts cold. Every first access to a page of code, data or stack causes a minor page fault (a short run of ls has around 100 to 150), every new cache line is fetched from the page cache in DRAM at about 80 ns, and the TLB and branch predictors know nothing about this program. The first instructions per cycle are very low, around 0.2 to 0.5 instead of 2 to 4. A trivial program like /bin/true takes about 300 to 500 µs from fork to exit on a modern Linux machine, of which the actual work is a few microseconds. Everything else is setup: fork about 50 µs, exec about 100 µs, dynamic linking about 300 µs, page faults the rest. That is why shell scripts that start thousands of tiny processes are slow, and why static linking and vfork are used in performance-sensitive tools.
isa | Finally the kernel returns to user mode. It sets the instruction pointer to the program's entry point (or the dynamic linker's, for a dynamically linked program), the stack pointer to the new stack, and clears the other registers, then executes SYSRET or IRET, which changes the privilege ring from 0 to 3 and begins fetching user instructions. The entry symbol _start, written in a few lines of assembly, calls __libc_start_main, which initializes the C library (locale, stdio buffers, thread-local storage), runs the constructors, and calls main(argc, argv, envp). From the point of view of the instruction set, this is the same ordinary x86-64 code as any other; the ring and the page tables are the only things that make user code unable to harm the kernel.
process | ls reads the directory (getdents64), writes the formatted lines with write(1, ...) to the terminal and calls exit_group(0). The kernel closes all descriptors, releases the address space (page tables and frames, with the shared library pages staying in memory because others use them), and turns the task into a zombie: only its small task_struct remains, holding the exit status, to be collected. It sends SIGCHLD to the parent, which wakes up from wait4(), receives the status (0) and lets the kernel free the last bits. The shell stores the status in $? and prints the next prompt. If a parent never calls wait, zombies pile up until the parent dies, and then PID 1 adopts and reaps them. Total time from Enter to the next prompt: about 1 ms, and a process has lived and died.

## What happens when you ask an AI assistant a question that uses a tool | From a prompt to a tool call, a vector search, and an answer built on what came back
agents | You type: "What was our Q3 revenue, and how does it compare with Q2?" The model cannot know your company's numbers, so the assistant is run by an agent harness: ordinary program code that holds the conversation and repeats a loop. Send the messages and the list of available tools to the model; if the model asks for a tool, run it and add the result; call the model again; stop when the model answers in plain text. The model itself is only a function from text to text. It does not run anything, open files or reach the network. All the actions of an "agent" are done by the harness on its behalf, in a loop that usually runs 1 to 10 times for one question. The harness also enforces limits, such as a maximum number of steps, a time budget and a token budget.
mcp | The harness learned about its tools when it started. Each tool is described by a name, a plain-language description and a JSON Schema for its arguments. Tools can be built into the harness or served by external programs through the Model Context Protocol (MCP): a JSON-RPC protocol over a local pipe or HTTP, in which the harness sends tools/list and gets back descriptions, for example search_docs(query: string, top_k: integer) and calculator(expression: string). The descriptions are the interface the model sees, so they are written like documentation, and each costs 100 to 300 tokens in every request. With 30 tools you can spend 5,000 tokens before the user says a word. MCP lets one tool server work with many different assistants, but a connected server is also trusted code and text, which is why permission prompts and sandboxes matter.
contexteng | Before each call, the harness assembles the context window: the system prompt (rules, tone, today's date), the tool definitions, the earlier messages in this chat, any retrieved memory, and your new question. This is context engineering. The window is limited, 200,000 tokens or more for current models but with real costs: every token is paid for in compute, attention quality falls when the window is crowded with irrelevant text, and latency grows with length. A typical first request here has about 3,000 tokens: 800 for the system prompt, 1,500 for tools, 100 of chat history, 30 for your question. If a long chat exceeds the budget, the harness drops or summarizes old messages and keeps the key facts. The prompt is the only way to give the model information, so what you leave out does not exist for it.
bpe | The text is converted to tokens. A byte-pair-encoding tokenizer splits the string into pieces from a vocabulary of 100,000 to 200,000 entries, built by repeatedly merging the most frequent adjacent pairs of bytes in the training text. Common words are single tokens (" revenue" is one), rare words become several, and numbers are cut into short pieces, which is one reason arithmetic is hard. English averages about 4 characters or 0.75 words per token; code and other languages take more tokens per word. Your 30-token question becomes a list of integers such as [3923, 574, 1057, ...]. The model never sees letters, only these IDs, and they are the unit that you are billed for and the unit that the context limit is counted in.
http | The harness sends an HTTPS POST to the model API with a JSON body of about 12 KB: model name, system prompt, tools, messages, and parameters such as max_tokens and temperature. It sets stream: true, so the reply arrives as server-sent events, an HTTP response that stays open and sends a small text event every few tokens, each about 100 bytes. The request passes the edge, an API gateway that authenticates the key, checks quotas and rate limits, and picks a region. This takes 10 to 50 ms before the model is touched. Because tokens are produced one at a time over seconds, streaming makes the assistant feel fast: the first words appear after about half a second even if the full answer takes 10 seconds.
llmserving | Inside the provider, a scheduler routes the request to a cluster of GPU servers, each holding a copy of the model sharded over several GPUs (for a model with hundreds of billions of parameters, 8 GPUs with tensor parallelism). Requests wait in a queue and are grouped with others into batches, because a GPU is hugely underused by one user: it can serve dozens to hundreds of sequences in the same memory read. The key resources are GPU memory (weights plus the KV cache of every active sequence) and memory bandwidth. A serving system makes trade-offs between latency for you and throughput for everybody, and prices and rate limits reflect that. Under heavy load your request may wait tens to hundreds of milliseconds before it starts.
promptcache | The first 2,500 tokens of your prompt (system prompt and tool definitions) are identical to those of thousands of other requests. The server hashes the prompt in blocks, finds that this prefix was computed recently, and reuses the stored keys and values instead of recalculating them. This is prompt caching: it skips most of the prefill work, cutting the time to first token and the price of cached input tokens (often to about a tenth). The cache is keyed on the exact prefix, so one changed word at the beginning invalidates everything after it, which is why harnesses keep the stable parts first and the changing parts last. Entries live a few minutes to an hour and are kept in GPU or host memory. A multi-step agent benefits most, since each loop repeats the whole earlier conversation.
attention | The remaining new tokens go through prefill: the model processes all of them in parallel in one pass through its layers, 80 or so. In each layer, every token is turned into a query, a key and a value vector by matrix multiplications, and attention computes for each token a weighted mix of the values of all earlier tokens, with weights softmax(QKᵀ/√d). This is how "Q3" in your question can look back at "revenue" and at the tool descriptions. The work grows with the square of the prompt length, optimized by fused kernels like FlashAttention that keep the intermediate matrices in on-chip memory. Prefill is compute-bound: for a 3,000-token prompt and a 100-billion-parameter model it is about 2 x 10^11 x 3,000 = 6 x 10^14 operations, around 0.1 to 0.5 s on a few GPUs.
tensorcores | Almost all of those operations are matrix multiplications, and GPUs have special units for them. A tensor core multiplies small matrix tiles (for example 16 by 16) and adds the result in one instruction, with 8-bit or 16-bit inputs and 32-bit accumulation. An H100 delivers around 1,000 TFLOPS of 16-bit dense matrix math, and nearly 2,000 at 8 bits, a hundred times more than the same chip could do with ordinary arithmetic units. Weights are often stored in 8 or 4 bits (quantization) so more of them fit into memory and fewer bytes need to move. The thousands of threads in the GPU run in lockstep over tiles of the matrices. Feeding the tensor cores with data fast enough is the real challenge, so the hardware depends on large on-chip caches and very fast memory.
kvcache | During prefill, each layer stores the keys and values of every token, the KV cache, so that later steps need not recompute them. Its size per token is 2 (K and V) x layers x KV heads x head dimension x bytes: for example 2 x 80 x 8 x 128 x 2 bytes = 327 KB, so the 3,000-token prompt takes about 1 GB and a 100,000-token conversation 30 GB. The KV cache, not the weights, often limits how many users a GPU can serve. Systems like vLLM store it in fixed-size pages (PagedAttention) addressed through a page table, as an operating system does for virtual memory, so that memory is not wasted by gaps and a shared prefix needs only one copy. Grouped-query attention shrinks the cache by sharing key and value heads among query heads.
decoding | Now the answer is generated one token at a time. For each step the model reads the whole last token through all layers, uses the KV cache for the attention over the past, and produces a score (logit) for each of the 100,000+ vocabulary entries. These are turned into probabilities by a softmax, and one token is chosen: at temperature 0 the most likely one, otherwise a random sample from the top-p part of the distribution. The chosen token is appended and fed back in. Decoding is memory-bound: every step must read all the weights (for 100 GB, at 3 TB/s of memory bandwidth that is about 30 ms) however few tokens it makes, which is why one stream gets 30 to 100 tokens per second, and why batching and speculative decoding, where a small model drafts tokens and the big one checks them in one pass, help so much.
contbatch | To keep the expensive GPU busy, the server uses continuous batching. At every decoding step it forms the batch from all sequences that are active, and a sequence that finishes leaves immediately while a new one joins, with no need to wait for the whole batch. Your sequence shares each weight read with, say, 64 others, so the 30 ms step produces 64 tokens instead of one, and the cost per token falls by almost that factor. Prefill of new requests can be chunked and mixed into the steps so that long prompts do not stall everyone else's output. This scheduling is the difference between serving a model at a loss and at a profit, and it is the main reason latency on a busy service varies from request to request.
toolcall | After about 40 tokens, the model does not write prose. It produces a structured block: a tool call with the name search_docs and arguments {"query": "Q3 revenue and Q2 revenue", "top_k": 5}. The model was trained to emit this format when a question needs outside facts, and the serving layer ends generation at the special end-of-call token. The API returns it as a content block of type tool_use with an ID and a stop reason "tool_use", rather than as text. The model has not run anything: it has only written what it wants to be done. It might even write several calls in parallel, for example one search for Q3 and one for Q2. The first response took about 1.0 to 1.5 seconds in total, most of it prefill and queueing.
reactloop | The harness receives the block and now acts. It checks that the tool exists, validates the arguments against the JSON Schema (a malformed call is returned to the model as an error it can correct), applies permission policy (read-only search may run silently; sending an email or deleting a file asks you first), and runs the tool with a timeout. The outcome goes into the conversation as a tool_result block that refers to the call ID, and the harness calls the model again with the longer context. This is the reason-act-observe loop of agents: the model decides, the harness executes, and the result is the observation on which the model reasons next. An error, like a timeout, is also an observation, and good agents recover by trying a different approach.
embeddings | The search_docs tool is a retrieval system. It passes the query string to an embedding model, a smaller transformer that maps text to a vector of 768 to 3,072 numbers so that texts with similar meaning land near each other (trained contrastively, with matching pairs pulled together). This takes 5 to 30 ms. The documents were embedded earlier: each report, wiki page or spreadsheet was cut into chunks of 200 to 500 tokens with some overlap, and each chunk got its vector, stored with its source and metadata. The vector for "Q3 revenue" will be close to the vectors of chunks on quarterly financial results even if they use the words "turnover" or "fiscal third quarter". Meaning is represented as geometry, and similarity as the cosine of the angle between two vectors.
ann | The index might hold 10 million chunk vectors, 1,024 floats each, about 40 GB. Comparing the query with all of them would need 10 billion multiplications, around 1 second on a CPU. Instead an approximate nearest neighbour index (HNSW, a layered graph of neighbours) starts at the top layer, walks greedily towards the query through a few hundred vectors, and returns the 50 closest in 1 to 5 ms with about 95% recall. Many systems also run a keyword search (BM25) and merge the lists, because exact terms like a product code are found better lexically. The index can be sharded over servers and filtered by permissions, so you only find documents that you are allowed to see. The trade is clear: a small loss of accuracy for a 100-fold speed-up.
rag | The best 50 candidates are re-ranked by a cross-encoder, a model that reads the query and a chunk together and scores their relevance more precisely than vector distance (20 to 100 ms for 50 pairs). The top 5 chunks, around 2,000 tokens, are formatted as the tool result with their titles and links. This is retrieval-augmented generation: instead of hoping that the model memorized your financial results (it never saw them), the system finds the right text and puts it in front of the model at question time. The data can change daily without retraining, access control is enforced in the retrieval layer, and every statement can cite a source. The quality limit is now the retrieval: if the right chunk is not in the top 5, the model will answer from the wrong ones.
cot | The harness calls the model again with the question, the first tool call and the result: about 5,500 tokens, of which 2,500 come from the prompt cache. The model reads the chunks: "Q3 revenue: $12.4M ... Q2 revenue: $11.1M". Many models first write reasoning tokens (a chain of thought) that are hidden or shown separately: "growth = (12.4 - 11.1) / 11.1". Because language models are bad at exact arithmetic, a good assistant calls the calculator tool for this, sending {"expression": "(12.4-11.1)/11.1"} and receiving 0.1171 in a few milliseconds. Writing steps before the answer improves accuracy, since each generated token adds computation the model can build on. This second round costs another 0.5 to 1 s, and the loop has now run twice.
rlhf | Why does the model behave this way, calling tools at the right moment and then citing what it found? It was trained to. After pre-training on text, it is fine-tuned on examples of tool use and then improved with reinforcement learning, in which outputs are scored by human preferences, by a reward model, or by automatic checks such as whether the final answer matches a known result, and the model is pushed toward high-scoring behaviour. A good assistant has learned to search before it guesses, to say when the result does not contain the answer, and not to follow instructions hidden in retrieved text. That last point is a real risk called prompt injection: a document chunk saying "ignore your instructions" is just more tokens to the model.
evals | The final model call produces no tool call, only the answer, streamed to you as server-sent events at roughly 50 tokens per second: "Q3 revenue was $12.4M, up 11.7% from Q2's $11.1M (source: Q3 financial summary)." Everything from your Enter key to the first word took perhaps 1.5 to 4 seconds, and to the last word a few seconds more. How would anyone know the answer is right? Teams run evaluations: a fixed set of questions with known answers, measuring whether the tool was called, whether the retrieved chunk contained the fact, and whether the final claim is supported by it. Each run of a changed prompt, tool description or retriever is scored again, because small changes can break behaviour without any warning.

## What happens when a file is saved and survives a power cut | From write() to fsync, a journal commit, an SSD translation layer and electrons trapped in NAND
filesystems | You press Ctrl-S in an editor. A careful editor does not overwrite your file in place, because a crash in the middle would leave half of the old file and half of the new. Instead it writes the new content, 20 KB for example, to a temporary file in the same directory (report.txt.tmp), calls fsync() on it, and then calls rename("report.txt.tmp", "report.txt"). On POSIX file systems, rename within one file system is atomic: after a crash you find either the old complete file or the new complete file, never a mix. The file system turns your file name into an inode and your bytes into blocks of 4 KB; 20 KB means 5 data blocks plus metadata updates to the directory, the inode, the allocation bitmap and the free-space counters.
syscalls | The editor's write(fd, buf, 20480) is a system call. The CPU switches into the kernel (about 100 ns), the kernel looks up the open file description, checks permissions and offset, and copies the 20,480 bytes from the user buffer to pages in the kernel's memory. It returns the number of bytes written after about 5 to 10 µs. The application is told "done". Nothing has been sent to the disk. This is a deliberate speed-up: without it, every write would wait 100 µs to several ms for the device, and a program that writes a line at a time would crawl. But it creates the central problem of this journey: the success of write() means only that the kernel has accepted the data, not that it is safe.
pagecache | The 5 pages now live in the page cache, the kernel's RAM copy of files, marked dirty. Reads of the file come from there at memory speed (about 10 GB/s). A flusher thread writes dirty pages back in the background: it wakes every 5 seconds and writes pages that have been dirty for more than 30 seconds, or sooner when dirty memory exceeds 10 to 20% of RAM. So, if the power is cut now, within these seconds, your data are lost with no trace, though the editor displayed "saved". The same cache is why a program reading a freshly written file is fast, and why a read-after-write on the same machine always sees the new data even before it reaches the disk.
fsync | Because of this, programs that care call fsync(fd) to demand durability. The call blocks until the kernel has written all dirty pages of that file to the device, committed the file system's metadata for it, and asked the device to flush its own volatile write cache; only then does it return. It typically takes 0.1 to 2 ms on an SSD and 10 to 20 ms on a hard disk. Developers avoid it because it is slow, and bugs where it is skipped explain many "my file vanished after a crash" stories; others, such as databases, call it on every commit. There are subtle traps: fsyncing the file does not make a new directory entry durable unless you also fsync the directory, and after a failed fsync the kernel may have dropped the dirty pages, so a retry can falsely succeed.
fsjournal | The file system is the next layer. ext4 keeps a journal, a circular log of about 128 MB to 1 GB, managed by the jbd2 thread. In the default ordered mode, it first writes the file's data blocks to their final location, then writes the metadata changes as a transaction to the journal: a descriptor block listing which blocks follow, the new copies of the changed metadata blocks (inode, bitmap, directory), and finally a commit block carrying a checksum. Only when the commit block is on stable storage is the transaction valid. Later, in the background, the metadata is checkpointed to its real place and the journal space is freed. The journal makes a multi-block update atomic: after a crash either the whole transaction is replayed or none of it is. Several operations share one transaction, which commits every 5 seconds or at fsync.
queuesbuf | Writes now enter the block layer as bio structures, each describing a run of sectors and the memory pages that hold their data. The block layer merges adjacent ones (5 pages of a file often form one 20 KB request), orders them where useful, and puts them into per-CPU submission queues, ring buffers with a bounded size. For NVMe SSDs the I/O scheduler is usually "none", because the device is fast and reorders by itself; for hard disks, an elevator algorithm sorts the requests by position to reduce head movement. Barriers and cache-flush flags in the bios express the ordering that the journal needs: the commit block must not become durable before the descriptor and metadata blocks. Sending requests in batches reduces the interrupt rate and the lock contention in a system doing a million I/Os per second.
nvme | The driver writes a 64-byte command into the NVMe submission queue in RAM and rings a doorbell, a register in the SSD's memory-mapped PCIe space. The SSD fetches the command with DMA, then fetches the data from RAM with DMA over PCIe, at 3 to 14 GB/s for a Gen4 or Gen5 x4 link. After processing, it writes a 16-byte completion entry to the completion queue and raises an MSI-X interrupt on the CPU that submitted the request. The journal commit also sends a Flush command, which tells the drive to make all data it has acknowledged durable. The command, data transfer and completion take 10 to 20 µs of protocol time. NVMe has up to 64,000 queues of up to 64,000 entries, so every CPU core gets its own pair without locking.
ftl | Inside the SSD, a controller runs the flash translation layer. NAND cannot overwrite data in place, so the controller never writes to the same physical location twice: it appends your 20 KB to a currently open flash block and records in a mapping table (about 1 GB of RAM per 1 TB of drive) that logical address 4,812,033 now lives at channel 3, die 1, block 902, page 17. The old copy, if any, is marked invalid and cleaned up later by garbage collection, which copies live pages out of a block and erases it. Writes are first collected in a DRAM buffer and a fast cache to be programmed in full pages across several channels at once. Because DRAM loses its contents when power is lost, drives for servers have capacitors that supply enough energy to write the buffer into flash when power fails; consumer drives often must write the data to flash before acknowledging a flush, which takes longer.
storagedev | The physical organization limits what the controller can do. A flash die is split into planes with blocks of 256 to 1,024 pages, and a page is 16 KB. You can read a page in 50 to 100 µs, program (write) an empty page in 400 to 1,000 µs for TLC cells, but you can only erase a whole block, which takes 3 to 10 ms. Pages must be programmed in order within a block. The controller hides this by spreading writes over 8 to 16 channels and dozens of dies in parallel, which gives the drive its multi-GB/s throughput although a single program takes about a millisecond. A drive that is nearly full has less room for garbage collection, so write amplification rises and speed drops. Each block survives only a limited number of erase cycles, 1,000 to 3,000 for TLC, so the controller also spreads wear evenly (wear levelling).
codingtheory | Flash is not a perfect memory. Cells drift and are disturbed by neighbours, so a freshly written page already has a raw bit error rate of 10^-4 to 10^-3, rising as the cell wears. Every page is therefore stored with parity bits in its spare area (about 10 to 15% extra) using strong error-correcting codes, today LDPC codes with soft-decision decoding. On a read, the controller decodes and fixes up to a few hundred bit errors per page, bringing the error rate to below 10^-15. If the first read cannot be corrected, it re-reads the page with slightly different voltage thresholds, and in the worst case reports an unrecoverable error. The redundancy is the price of storing three or four bits in one cell, where the voltage levels are only tens of millivolts apart.
tunneling | To program a cell, the controller applies a program voltage of about 18 to 20 V to the control gate while the channel is grounded. The strong electric field across the thin tunnel oxide, 7 to 9 nm thick, makes electrons cross the barrier that a classical particle could not climb: quantum tunneling, in its Fowler-Nordheim form. The electrons land in the storage layer and stay there. To erase, the field is reversed and the electrons tunnel back out. One program operation moves a few hundred to a few thousand electrons. Each crossing damages the oxide a little by creating defects that trap charge, which is the physical origin of limited write endurance. A TLC cell must place its charge into one of 8 levels, so the controller programs in small voltage steps and checks the result after each pulse.
oxides | The electrons are held in a storage layer insulated from everything by oxide. In older planar flash it is a conductive floating gate of polysilicon; in modern 3D NAND, a stack of 200 to 300 layers, it is a charge-trap layer of silicon nitride wrapped around a vertical channel hole, with oxide above and below. Silicon dioxide is an excellent insulator with a band gap of about 9 eV, and that wall keeps the charge for years without power: the standard requires 1 year at the end of life for consumer drives and more when the drive is fresh. The threshold voltage of the transistor shifts depending on how much charge is stored, and that shift is what a later read senses by applying test voltages. Heat speeds up leakage, so a hot, worn drive in a powered-off drawer loses data first.
hashfn | Checksums guard the data on its way. The journal's commit block contains a CRC-32C of the transaction, so after a crash the file system can tell a complete transaction from a torn one: it replays only transactions whose checksum matches. ext4 also checksums its metadata blocks (metadata_csum), and file systems such as ZFS and btrfs checksum the file data themselves and store the checksum separately from the block, so they can detect corruption introduced by a disk, cable or firmware bug ("silent data corruption"), and repair from a mirror. NVMe drives add end-to-end protection information as well. A CRC-32C over 4 KB takes about 0.3 µs with the CPU's CRC instruction, cheap enough to run on every I/O. A hash only detects damage; repair needs redundancy.
acid | The flush returns, the commit block is durable, and fsync returns to the editor. Now the rename: it is a metadata-only operation recorded in a new journal transaction (an entry removed for the old name, one added for the new), which the editor can make durable by fsyncing the directory. Atomicity here comes from the journal: the transaction either fully commits or does not exist. The user-visible result is the classic atomic-replace guarantee, with consistency (the directory is never left half-updated), isolation (other processes see old or new, not partial), and durability after the fsync. Compared with a database, a file system gives you these properties only for operations you carefully compose out of write, fsync and rename. If the editor skipped the first fsync, a crash could leave the new name pointing to a file with empty or partial contents, because the rename can become durable before the data does.
recovery | Now the power is cut. The power supply's capacitors hold for 10 to 20 ms, and the SSD's own capacitors give it a few milliseconds to finish writing its buffer. At the next boot, the kernel mounts the file system. ext4 sees from the superblock that the journal needs recovery, reads it from the start, and replays each complete transaction (verified by checksum), copying the logged blocks to their real locations; an incomplete transaction at the end is discarded. This takes 0.1 to 2 seconds regardless of the size of the disk, whereas a full fsck of a 4 TB disk could take an hour. Your report.txt is either the previous version or the new one in full, depending on whether the rename committed, and the temporary file is gone or still there.
erasurecoding | One disk can still die, so serious systems add redundancy above all this. A RAID 1 mirror writes each block twice; RAID 5 or 6 stores parity so that one or two disks can fail; cloud storage uses erasure codes such as 10 data + 4 parity shards spread over different machines or racks, which survives any 4 losses with just 1.4 times the space instead of 3 times for triple copies. Each layer in this journey adds its own redundancy: the page cache is volatile, the journal protects metadata, the SSD uses ECC, the array uses parity, and a backup protects against deletion or ransomware. Durability is a chain of promises, and a weak link anywhere, such as a drive that lies about flushes, breaks the whole chain.

## What happens when you search on Google | From a keystroke to ranked results, through a sharded inverted index and many caches (illustrative numbers)
browser | As you type "best way to learn rust", the browser does not wait for Enter. Every keystroke or two, it sends a small request to a suggestion service, for example /complete/search?q=best+way+to+le, and gets back a JSON list of 5 to 10 completions of about 1 KB within 30 to 80 ms. The suggestions come from an index of frequent past queries held as a prefix structure. When you press Enter, the browser builds a navigation request, GET /search?q=best+way+to+learn+rust, with cookies, language headers and, on a phone, a rough location hint. If you choose a suggestion, the exact query string is known before you press the key, and some browsers even start fetching the results in advance (prefetch). Your question is already in the data center while your finger is still moving.
quic | The browser needs a connection to a search front end. The domain name resolves, using DNS tricks like anycast and geo-aware answers, to the address of an edge location close to you, ideally within 10 to 20 ms of round-trip time. Google's servers speak HTTP/3 over QUIC, so a returning visitor with a stored session ticket can send the request in the very first packet (0-RTT), and a new visitor needs one round trip for the handshake. QUIC runs over UDP port 443 and encrypts almost everything. The connection is usually already open from the previous search, and then no handshake is needed at all. The request, a few hundred bytes, reaches the edge in one packet; the user has used maybe 15 ms of the total time.
loadbalancing | The edge server (a front-end proxy) terminates TLS, applies abuse checks and rate limits, and forwards the request across Google's private backbone to a data center chosen by load, distance and health. Inside, software load balancers spread requests over thousands of identical web-server replicas, avoiding unhealthy machines and using the "power of two choices" (pick two at random and take the less loaded) to keep queues short. The web server itself holds little state: it is the coordinator for the request, which will fan out to dozens of other services (query understanding, the index, ads, maps, news) and then assemble the page. A hop inside the data center takes 0.1 to 0.5 ms, so one request can afford dozens of them. By now about 20 to 30 ms of the budget is gone.
nlp | First the query is analysed. It is normalized (case, punctuation, Unicode forms), split into words, and checked for spelling mistakes by comparing it with common queries ("did you mean"). The system identifies the language, finds entities (Rust is a programming language here, not iron oxide, judging by "learn" and your history), and expands the query with synonyms ("study", "tutorial"). It decides on intent: informational, navigational, local or shopping, and which special result types (video, map, news, answer box) are worth showing. This is natural language processing with neural models, run within a few milliseconds on dedicated servers, and the result is not one query but a structured request: terms, alternatives, filters (language, region, freshness) and weights. Getting this step wrong is costly: if the system reads the intent badly, even a perfect index returns the wrong kind of page.
cachelayer | Many queries have been asked before. A cache layer in front of the expensive work stores full result lists for recent popular queries, keyed on the normalized query plus location, language and device type. For a hit the answer comes back in about 1 ms from memory, and the whole search is cheap. Real traffic is highly skewed: a few million popular queries account for a large share of volume, while a big fraction of all daily queries have never been seen before, so the caches help but cannot replace the real machinery. Entries expire quickly for news-like queries because freshness matters, and personalized results are harder to cache. Caches exist at many levels: for query results, for individual posting lists, for snippets and for parts of the page.
partitioning | Our query is a miss, so the index must be consulted. The web index is far too large for any single machine: hundreds of billions of pages, with a compressed index of many petabytes. It is split into shards by document, each shard holding a slice of all documents with its own complete inverted index, and each shard is replicated on several machines for throughput and failure tolerance. Sharding by document means that every shard can compute the best matches in its own slice independently. The index is also tiered: the most important and most visited pages live in fast memory-based tiers, the long tail in cheaper tiers consulted only if the first tiers did not yield enough good results.
scattergather | The coordinator sends the query to a tree of servers: a root sends it to a few dozen mixers, each of which sends it to a few hundred leaf servers, so that thousands of machines receive the request within a millisecond or two. Each leaf searches its shard and returns its own best 100 or so candidates with scores. The parents merge the sorted lists and keep the top results, and the root merges again. This is scatter-gather, and it makes the total latency equal to the slowest leaf, not the average. If any leaf is slow, the whole query waits, so the system sets deadlines and returns partial results from the leaves that answered in time. With 1,000 leaves, even a 1% chance of a slow response per leaf means that 99.996% of queries meet at least one slow leaf.
invindex | On each leaf, the search runs on an inverted index, which maps every term to the sorted list of documents that contain it, called a posting list. The term dictionary is kept in compact structures (such as finite-state transducers or hash tables) so that looking up "learn" takes microseconds. For the query terms best, way, learn and rust, the leaf fetches four posting lists. For a common word like "way" the list may contain tens of millions of documents in the shard; for "rust" much fewer. Instead of reading the pages themselves, the engine works only on numbers: document IDs, the term frequency in each document, and positions to check phrases like "learn rust". The index was built beforehand, and searching it is a matter of intersecting sorted lists.
postings | Posting lists are big, so they are compressed. Because the document IDs are sorted, only the gaps between consecutive IDs are stored, and small gaps are encoded with variable-length codes or bit-packed in blocks of 128 integers using SIMD instructions; a list that was 4 bytes per entry shrinks to 1 or 2 bytes, and the whole index fits in RAM or fast flash. To intersect lists, the engine begins with the rarest term ("rust") and uses skip pointers to jump over runs of document IDs that cannot appear in the others, so the work is proportional to the shortest list and not the longest. The engine decodes at several billion integers per second per core. A query that touches 100,000 candidate documents in each shard can therefore be answered in a few milliseconds.
bm25 | The leaf scores the candidates that contain the terms. The classic formula, BM25, adds up for each query term its frequency in the document (with diminishing returns), multiplied by how rare the term is across the corpus (inverse document frequency), normalised for document length so a long page does not win only because it is long. "Rust" in a page title scores more than in a footer. This cheap first-pass score is combined with dozens of other signals computed from the index, such as where the terms appear, how close together they are and whether the page is on a good domain. A small heap keeps the top 100 per shard; everything else is dropped. This stage reduces billions of pages to hundreds of candidates in a few milliseconds.
pagerank | Some signals do not depend on the query. PageRank, the original idea, models a random surfer who follows links: a page's importance is the probability of finding the surfer there in the long run, the stationary distribution of a Markov chain over the link graph, computed by repeated multiplication of a vector by the link matrix (power iteration) over trillions of links, in batch jobs. A page that is linked from many important pages gets a high score, and the scores are stored in the index next to each document. Today it is one of hundreds of signals, along with freshness, page speed and mobile friendliness, and the quality of the site. Link-based signals made it expensive to fake relevance, which is why spammers then moved to buying links and the engine to detecting them.
lsh | The index was created in advance by a pipeline. Crawlers fetch billions of pages, obeying robots.txt and politeness limits, and render them with a browser engine to run JavaScript. The pages are parsed, their text and links extracted, and duplicates removed: the web is full of copies, and near-duplicates are found by fingerprinting each page (shingles of word sequences hashed to small signatures) and putting pages with similar signatures into the same bucket using locality-sensitive hashing. Only one canonical version stays in the index. The pipeline runs as large batch jobs (MapReduce-like) on thousands of machines for days, with fresh content such as news handled through a faster path that updates a small real-time tier within minutes. The part you wait for is only the lookup. The part that took the effort happened before you asked.
embeddings | Keyword matching misses questions that use other words: "how do I get started with Rust programming" may be best answered by a page that never says "best way". Neural models therefore turn the query and the documents into embedding vectors of a few hundred dimensions, trained on clicks and relevance judgments so that a question and its good answers are close. The query vector is computed once on the coordinator (a few milliseconds on an accelerator), and the document vectors were computed during indexing. Meaning-based matching is now a standard part of retrieval and complements the term index. It handles synonyms, misspellings and long conversational queries, which the pure lexical approach handles badly. The two candidate lists are then merged.
ann | To search by vector, leaves hold an approximate nearest-neighbour index over their share of document vectors, for example a partition tree or a graph, with compressed vectors (quantized to a byte or less per dimension) so that millions fit in memory. A query visits only a small fraction of the data, scoring perhaps a few thousand vectors out of a hundred million, and finds the closest 100 in about 1 to 5 ms with high recall. The result is a second set of candidates with similarity scores. A document can appear in both lists. Here, as elsewhere, the choice is approximate versus exact: missing the 100th best document is harmless, and a 100-fold saving in work is not. This is the same machinery used in recommendation and in retrieval for language models.
dl | The merged list of several hundred candidates goes to the ranking stage, where the expensive models can run because there are only a few hundred documents left. A deep neural network (a transformer in the style of BERT, much smaller than a chat model) reads the query and each candidate's title, snippet and features together and produces a relevance score; others predict quality, freshness and whether users tend to be satisfied by the page (from aggregated click and dwell-time data). A learned ranking function combines all of these scores, trained on human raters' judgments and on logged behaviour. Scoring 500 candidates takes 10 to 30 ms on accelerators. This is why a search engine feels as if it understands: most of the intelligence is applied at this small stage, after the cheap stages did the heavy filtering.
adtech | At the same time, other systems work on the page. Ads are chosen by an auction among advertisers who bid on keywords like "learn rust course"; the auction ranks ads by bid multiplied by predicted quality and click-through rate, charges the price needed to hold the position (a generalized second-price rule), and has to finish within the time budget of the page, tens of milliseconds. Other services supply a knowledge panel, a "People also ask" box, video results, and local results. A policy layer removes illegal or unsafe results and demotes low-quality pages. The coordinator also fetches a snippet for each of the top 10 results from a document store, picking the sentences that best match the query terms, and bolds them. All these requests run in parallel, and each has its own timeout.
replication | The search is done in about 100 to 200 ms, but the slowest parts determine the experience. Large services fight tail latency: if a request to one replica has not returned by the 95th percentile of the expected time (say 10 ms), the coordinator sends the same request to another replica of the shard and uses whichever answer comes first ("hedged requests"), cancelling the other one. That adds only about 5% more load and cuts the 99.9th percentile latency severalfold. Replicas also allow a machine to be down or updating without any visible effect. Data centers run at moderate utilization on purpose, because queueing delay explodes when a server is nearly full. Reliable behaviour of the whole depends on many unreliable parts being repeated and raced.
http | The coordinator assembles the final HTML: a document of about 100 to 200 KB with the ten results, inline CSS, and a small amount of JavaScript. It sends the first chunk, the page header and the search box, immediately, while the slower result parts are still being computed, using HTTP chunked transfer so that the browser can start rendering earlier. The response is compressed with Brotli or gzip, 3 to 5 times smaller, so about 30 to 50 KB goes over the wire, fitting in the first congestion window (about 14 KB) plus a second round. The browser parses it, applies CSS, and paints the results. The whole path, from Enter to a readable page, typically takes 200 to 500 ms, and the server-side search itself is only a fraction of it.
experimentation | The engine you used today is not the one of yesterday. Ranking is changed thousands of times a year, and each change is tested before launch. A fraction of users, say 1%, is randomly assigned to a variant with a new model or layout, and metrics such as the time to a successful click, query reformulations, and satisfaction surveys are compared with a control group using statistics and confidence intervals, together with side-by-side comparisons by human raters. Because the number of users is huge, effects of 0.1% can be detected, but effects can also be an artifact of novelty or of interference between experiments, so analysis is careful. Your query is also logged, anonymized after a time, to supply the training data for the next round of models. The loop closes: search results make behaviour, and behaviour improves search.

## What happens when your phone joins Wi-Fi and gets an IP address | From radio beacons to an encrypted link, a DHCP lease and the first DNS query
osi | You tap a network name and enter a password. Joining takes about 1 to 3 seconds and walks up the network layers. First the physical layer: your phone and the access point (AP) must hear each other. Then the link layer: the phone authenticates and associates with the AP, which gives it permission to send frames, and the two derive encryption keys. Only after that does the network layer start: the phone has no IP address yet, so it asks for one with DHCP, learns the address of the router and of the DNS server, and can finally talk to the internet. Each layer relies on the one below and knows nothing about the ones above. On Android this is orchestrated by wpa_supplicant, on iOS by the system networking daemons; both talk to a Wi-Fi chip that runs its own firmware.
dma | The Wi-Fi chip is a small computer of its own, connected to the phone's processor by PCIe or SDIO. The driver does not move bytes one at a time. It sets up ring buffers (descriptor rings) in main memory for outgoing and incoming frames; the chip reads the transmit descriptors and frame data with DMA, and writes received frames into the receive ring, then raises an interrupt, usually coalesced so that one interrupt covers many frames. The chip's firmware handles the time-critical parts of the radio protocol: ACKs must be sent 16 µs after a frame ends, far too quickly for the phone's operating system to react. The host handles the slow parts, such as choosing a network and the key handshakes. This split is why a phone can keep the Wi-Fi connected while its main CPU sleeps.
maxwell | The medium is electromagnetic waves. A 5 GHz signal has a wavelength of 6 cm, which is why a phone antenna is only a few centimetres long, and 2.4 GHz has 12.5 cm. The AP transmits at about 20 to 23 dBm, 100 to 200 mW, and the power falls off with the square of the distance in free space and much faster through walls: 5 GHz loses 10 to 15 dB per wall. Every 102.4 ms the AP broadcasts a beacon frame announcing its name (SSID), supported rates, security methods and capabilities. Your phone either listens passively on each channel or sends probe requests (active scanning), channel by channel, spending 20 to 100 ms on each; a full scan of the 2.4 and 5 GHz bands takes 1 to 3 seconds, which is why it is skipped when a network is already known.
wifi | The phone now has a list of access points that answered. In a house there is one. In an office there are dozens that share one network name (SSID) and form one extended network. The phone chooses by signal strength and band. A 2.4 GHz signal passes walls best but has only three channels that do not overlap (1, 6 and 11), so it is crowded. 5 GHz has many more 20 MHz channels, and an AP must leave some of them when it detects radar. 6 GHz, added by Wi-Fi 6E and Wi-Fi 7, is nearly empty but reaches the least far. Each AP has its own MAC address, the BSSID, and works as a bridge: it turns Wi-Fi frames into Ethernet frames for the wired network. The generation decides the toolbox: Wi-Fi 5 (802.11ac, 2013) and Wi-Fi 6 (802.11ax, 2021) differ in modulation, OFDMA and scheduling, and Wi-Fi 7 (802.11be, published in July 2025) adds 320 MHz channels and links on several bands at once. After joining, the phone decides by itself when to move to another AP, and it sleeps between beacons to save battery.
ethernet | Frames in Wi-Fi look like Ethernet frames with extra fields. An 802.11 frame has a 24-byte header with a frame-control field, a duration, up to four MAC addresses (receiver, transmitter, destination, source), a sequence number, and a 4-byte checksum (FCS) at the end. Joining takes four management frames: the phone sends an Authentication request (a legacy open-system step that carries no real proof, "algorithm 0"), the AP answers, the phone sends an Association request listing its capabilities (rates, 802.11n/ac/ax features, security suites), and the AP answers with an Association response and an association ID. Each frame is 100 to 300 bytes, and the exchange takes a few milliseconds. The phone is now associated, but the AP still does not forward its data, because the link has no encryption keys yet.
randalgo | Many devices share one channel, and radios cannot hear while they transmit, so Wi-Fi uses CSMA/CA: listen before talk, and avoid collisions with randomness. Before sending a frame, a station senses the channel for a fixed gap (DIFS, 34 µs) and then waits a random number of 9 µs slots drawn from a contention window, initially 0 to 15. If another station talks first, the counter freezes and resumes later. If two pick the same slot and collide, no ACK arrives, and both double their window (to 31, 63, up to 1023) and draw again. The randomness spreads the retries over time without any coordination, which is the same trick as in the exponential backoff of network protocols. On a crowded channel with 30 devices, much of the time is spent waiting, not sending, and real throughput is a fraction of the headline rate.
retries | Wireless links lose frames: interference, a microwave oven, a person walking between you and the AP. Unlike Ethernet, Wi-Fi therefore acknowledges every unicast frame at the link layer. The receiver sends a 14-byte ACK 16 µs after the frame (SIFS). If no ACK arrives, the sender sets the retry bit, backs off with a doubled window, and tries again, up to 7 times for short frames. The sequence number and retry bit let the receiver discard a duplicate when the frame arrived but its ACK was lost. Rate adaptation algorithms watch the success ratio: after a few failures the sender steps down to a slower, sturdier modulation. Link-layer retries hide 10 to 30% frame loss from TCP, which would otherwise treat each loss as congestion and slow down sharply.
fourier | Data is carried by OFDM. A 20 MHz channel is divided into 64 narrow subcarriers (in 802.11ac/ax with an 80 MHz channel, 234 to 980 data subcarriers), each 312.5 kHz or 78.125 kHz wide, and each carries its own piece of the data at the same time. The transmitter builds the signal with an inverse FFT: it places one QAM symbol on each subcarrier in the frequency domain and computes the corresponding time-domain waveform, and the receiver applies an FFT to recover them. Because the subcarriers are orthogonal, they do not interfere, and each lasts long enough (3.2 to 12.8 µs) that echoes from walls, which arrive a few hundred nanoseconds later, hurt little; a cyclic prefix guard interval of 0.8 µs absorbs them. A problem like multipath, which ruins narrow-band signals, becomes a mild fading of individual subcarriers.
noise | How fast can the link go? That depends on the signal-to-noise ratio. Thermal noise sets the floor: -174 dBm per Hz, so a 20 MHz channel has about -101 dBm of noise, and the receiver's electronics add 5 to 10 dB. A signal at -60 dBm is 35 to 40 dB above the noise, enough for the fastest modulations; at -80 dBm you are 15 to 20 dB above and must slow down; at -90 dBm the link barely works. Each subcarrier's QAM constellation has to be dense enough to carry bits yet sparse enough that noise does not push a point into its neighbour's cell. 256-QAM carries 8 bits per symbol and needs about 30 dB; 1024-QAM carries 10 and needs 35 dB; BPSK carries 1 and works at 5 dB. Distance, walls and interference all reduce SNR, and the data rate follows.
infotheory | Shannon's theorem sets the ceiling: capacity C = B log2(1 + SNR). For a 80 MHz channel at 30 dB SNR (a factor of 1000), that is 80 million x log2(1001), about 800 Mbit/s per spatial stream, and the best real systems come within 10 to 20% of it. Doubling bandwidth doubles capacity, but adding 3 dB of SNR only adds one bit per second per hertz at high SNR, which is why newer Wi-Fi standards use wider channels (160 MHz, 320 MHz in Wi-Fi 7) and several antennas (MIMO) to transmit parallel streams. The phone and AP estimate the channel and pick a modulation and coding scheme index (MCS 0 to 11) for each transmission. A phone with two antennas at 80 MHz and MCS 9 reaches about 866 Mbit/s of raw physical rate, and real application throughput is about half.
codingtheory | Before modulation, every frame is protected with forward error correction. The data bits are run through an LDPC code (or a convolutional code in older standards) at a code rate of 1/2, 2/3, 3/4 or 5/6: for each 3 data bits, 1 parity bit is added at rate 3/4. The receiver uses all the received analogue values (soft decisions), not only 0 or 1, in an iterative decoder that passes beliefs between bits and checks, and can correct many errors per frame. Thanks to this coding, the link works at an SNR only a dB or two above Shannon's limit. The FCS checksum at the end of the frame catches what is left. Stronger coding at lower rates is chosen when the channel is poor. The bits per second you finally get come from a trade-off between modulation density and code rate.
hashfn | Now the security handshake. With WPA2-Personal, the password is never sent. Both the phone and the AP compute the same 256-bit pairwise master key (PMK) from the passphrase and the network name: PBKDF2 with HMAC-SHA1, 4,096 iterations, using the SSID as the salt. The iterations are meant to make guessing costly: the phone needs a few milliseconds, but an attacker's GPU still tries hundreds of thousands to millions of guesses per second, so a short or common passphrase falls in minutes. Because the SSID is the salt, popular names like "linksys" are covered by precomputed tables, so a unique network name is a mild extra defence. The PMK is cached on the phone, so the work is done once per network. A weak passphrase is the real danger here, since an eavesdropper who records the handshake can try millions of guesses offline.
pkcrypto | WPA3-Personal replaces this with SAE, the "Dragonfly" key exchange, a password-authenticated key exchange based on elliptic curves. Each side maps the password to a point on a curve, picks a random secret and sends a commit message containing a scalar and a curve point (about 100 bytes), then a confirm message. The two derive the same key only if both know the password, and an eavesdropper learns nothing that lets him test guesses offline: each guess requires a live interaction with the AP, which can rate-limit it. The key is also fresh for every session, so recording traffic now and learning the password later does not decrypt it (forward secrecy). The exchange takes 2 to 4 frames and some 10 ms of elliptic-curve arithmetic on the phone. The result is a PMK as before.
symcrypto | Next comes the four-way handshake of 802.1X (EAPOL frames, about 120 to 190 bytes each). The AP sends a random number ANonce; the phone replies with its own SNonce and a message integrity code (MIC). Both compute the pairwise transient key (PTK) from the PMK, both MAC addresses and both nonces using a keyed hash function, and split it into a key for the MIC, one for encryption and one for the temporary data. The MIC in message 2 proves that the phone knows the PMK; message 3 from the AP proves the same and delivers the group key (GTK) used for broadcast traffic, encrypted with AES key wrap; message 4 confirms. The whole exchange takes 4 frames and under 10 ms. Using fresh nonces means that the keys differ for each association, even with the same password.
aead | Data frames are now encrypted and authenticated. WPA2 uses AES in CCM mode (CCMP) and WPA3 prefers GCMP-256: a counter-mode encryption together with a message integrity code over the header and payload. Each frame carries a 48-bit packet number that must increase, in an 8-byte CCMP header, and an 8-byte MIC at the end, so a replayed or modified frame is dropped. A 1,500-byte packet grows by 16 bytes. AES hardware in the Wi-Fi chip does this at line rate with negligible energy. This is also why the open-network "free Wi-Fi" is risky: without the handshake, everyone in range can read all frames, whereas with WPA2 or WPA3 each client has its own key. Enhanced Open (OWE) gives encryption even without a password.
sockets | The link is secured, but the phone has no IP address. It uses DHCP, a four-step conversation over UDP with broadcast. DISCOVER: from address 0.0.0.0 port 68 to 255.255.255.255 port 67, containing the phone's MAC address and often a random MAC for privacy, about 300 bytes in all. OFFER: the DHCP server (in a home, the router; in an office, a server reached through a relay) proposes 192.168.1.23 with a lease of 24 hours. REQUEST: the phone asks for exactly that address (broadcast, so other servers know they were not chosen). ACK: the server confirms and lists options: subnet mask 255.255.255.0, default gateway 192.168.1.1, DNS servers, and domain name. Typically the phone is online within 50 to 200 ms. At half the lease time, it asks to renew.
dhcp | Behind the four DHCP messages, the server has real work to do. When the DISCOVER arrives, it decides which address to offer: the phone's old address if it has one on record, then a fixed reservation for its MAC address, then any free address from the pool. It may ping the address first to see whether another device already uses it. The OFFER only holds the address for a few seconds. The server writes the lease (MAC, address, expiry time) to disk when it sends the ACK, so a crash cannot give one address to two phones. In a large office the server is not on the phone's subnet. The router in front of the phone's VLAN acts as a relay: it hears the broadcast, writes its own interface address into a field called giaddr, and forwards the packet by unicast to the server. The server uses giaddr to choose the right pool and answers through the relay. When the phone later returns to a known network, it skips DISCOVER and asks for its old address directly, which costs one round trip. If it leaves without a release message, the address stays reserved until the lease ends.
iprouting | Before using the address, many phones check that no one else has it with an ARP probe: a broadcast "who has 192.168.1.23?" with no reply expected. Then it needs the gateway's MAC address: an ARP request "who has 192.168.1.1?" goes out as a broadcast frame, and the router replies directly with its MAC address, which the phone caches for a few minutes. Now the phone's routing table is simple: 192.168.1.0/24 is on-link (send directly), and everything else goes by the default route via 192.168.1.1. For each outgoing packet the phone compares the destination with its subnet by AND-ing with the mask; if it falls outside, the frame is addressed to the gateway's MAC, while the IP destination stays that of the remote server. The same ARP mechanism works for every neighbour on the LAN.
dns | The DHCP lease named a DNS server, usually the router itself, which forwards queries on to the ISP or a public resolver. The phone's first act on the new network is a connectivity check: it asks DNS for a well-known name (like connectivitycheck.gstatic.com) and sends an HTTP GET, expecting an empty "204 No Content" answer. If a hotel's captive portal intercepts the request and returns a login page, the phone notices that the answer is wrong, shows "Sign in to Wi-Fi", and opens the portal. A DNS query is a single UDP packet of about 40 bytes with an answer of about 60 bytes, taking 1 ms to the router and 10 to 30 ms if forwarded upstream. After a positive check, the Wi-Fi icon shows "connected" and apps start their pending requests.
nat | When your phone sends its first packet to a server on the internet, the source is the private address 192.168.1.23. The home router, which has one public address given by the ISP, translates: it rewrites the source address and port to its public address and a free port, and stores the mapping in a connection-tracking table (for example 192.168.1.23:50312 maps to 203.0.113.9:40001). Replies to that public port are translated back and delivered. Mappings expire after 30 seconds to a few minutes of silence for UDP and hours for established TCP. NAT is why a whole household shares one IPv4 address, and why servers cannot easily connect in to your phone. IPv6 offers every device a public address and removes the need for it, but a firewall still decides what may come in.
batching | After the link is up, throughput depends on how efficiently frames are sent. Each transmission has fixed costs: the contention gap, a preamble of 20 to 40 µs and a trailing ACK, together about 100 µs; sending one 1,500-byte packet at 600 Mbit/s takes only 20 µs, so overhead would dominate. 802.11n introduced frame aggregation: up to 64 frames (A-MPDU) are sent in one transmission, up to about 5 ms long, acknowledged by one block ACK that has a bitmap for each of the 64 frames. This raises efficiency from about 20% to 70% or more. Aggregation increases latency a little and works against power saving, so the AP balances it against the needs of voice and video. Also, OFDMA in Wi-Fi 6 lets one transmission serve several clients at once on different subcarrier groups. The throughput you see in a speed test is the product of all these layers working together.
