value: Operational transformation (OT) lets several people edit the same document at the same time and still end with identical text. Each user sees their own edits immediately, with no waiting for a server. The problem is that edits are made against different versions of the document. If Alice inserts a character at position 1 while Bob deletes the character at position 2, then applying Bob's "delete at 2" after Alice's insert deletes the wrong character, because everything after position 1 has moved by one. OT fixes this by rewriting each incoming operation so that it means the same thing in the document state where it is applied.
This is the technique behind Google Docs, and earlier behind Google Wave and Etherpad. It gives three things at once: low latency (local edits apply at once), convergence (everyone ends with the same document) and intention preservation (an edit lands where its author meant it, even if text moved). The alternative of locking a paragraph while someone types prevents concurrent editing. The alternative of "last writer wins" loses edits.
For the layer above, real-time collaboration (live cursors, shared documents, co-editing in browsers) needs a way to merge concurrent edits without conflicts that users must resolve. Real-time update channels such as WebSockets carry the operations to every client, and OT decides what each client does with them. The layers below make the design possible. Consistency models (L2) define what "everyone sees the same document" means when updates arrive in different orders. Lamport clocks and causal ordering (L2) tell us which operations were concurrent and so need transformation, and which came one after another and do not. Order theory (L4) describes the document histories as a partial order whose concurrent branches must meet again. Proofs and induction (L4) are how the transformation functions are shown correct, which is the hardest part.
terms: Operation — a small description of a change, such as insert("X", position 1) or delete(position 2), instead of the full new text.
Concurrent operations — two operations made without either user having seen the other; neither happened before the other.
Transformation function — a function T(a, b) that rewrites operation a so it can be applied after operation b has already been applied.
Convergence — all replicas end in the same document state after they have applied the same set of operations.
Intention preservation — each operation has the effect its author wanted, in the state where it is finally applied.
Revision number — the count of operations the server has accepted; a client says which revision its operation was based on.
TP1 — the property that two concurrent operations a and b, transformed against each other, reach the same state in either order.
Tombstone — a marker that keeps a deleted item's slot; CRDTs use it, and classic OT does not.
history: OT was introduced by Clarence Ellis and Simon Gibbs in "Concurrency Control in Groupware Systems" (SIGMOD 1989), in the GROVE collaborative outliner. They saw that locking was too slow for people typing together, and proposed that operations execute at once and are transformed when they meet others. Their algorithm, dOPT, worked for the cases they tested, but Ressel, Nitsche-Ruhland and Gunzenhäuser (1996) found a case where replicas diverged, now called the dOPT puzzle, and proposed the adOPTed algorithm with a formal framework.
Nichols, Curtis, Dixon and Lamping's Jupiter system (UIST 1995, at Xerox PARC) made a decisive simplification: use a central server. Each client talks to the server only, so there are only two sites to reconcile at any time. Jupiter is the ancestor of the designs used in production today. Sun, Jia, Zhang, Yang and Chen (1998) defined the goals of convergence, causality preservation and intention preservation for the peer-to-peer case, with more complex algorithms. Many peer-to-peer algorithms were published, and many were later shown wrong. Imine, Molli, Oster and Rusinowitch (2003) used automated verification to find counterexamples in published transformation functions. This history is the reason people say OT is hard.
OT reached users on a large scale in Google Docs and in Google Wave (2009), whose protocol was a client-server OT design described in public white papers. Etherpad used OT, was acquired by Google in 2009, and was later released as open source. The open source library ShareJS, later ShareDB, by Joseph Gentle, brought OT to many JavaScript applications, and Quill's Delta format gives a modern, compact operation type for rich text. Meanwhile Oster and colleagues (2006) published WOOT, an early algorithm that avoids transformation altogether, and this started the line of CRDTs that is the main alternative today.
how: The basic setting of a production OT system is client-server, in the style of Jupiter. The server holds the authoritative document and a numbered history of accepted operations. Each client holds a copy of the document and a revision number: the count of server operations it has applied. When the user types, the client applies the operation to its local copy at once and sends it to the server, tagged with the revision it was based on.
The central problem appears when an operation arrives at the server based on revision r, but the server is already at revision r + k. The k operations that were accepted in between are concurrent with the new one: its author had not seen them. The server transforms the new operation against those k operations, one by one, producing a version that applies to the current document. It then appends the result as revision r + k + 1, applies it, and broadcasts it. The server order is the total order of the document, which is what makes the system simple: it gives a single history that everyone agrees on.
The transformation function is the core. For text with single-character operations it is a small table. Let ins(p, c) insert character c at position p and del(p) delete the character at position p. To transform operation a against operation b (already applied), adjust a's position to account for b:
Step 1: if b is ins(pb, c) and a is ins(pa, d): if pa < pb, a is unchanged; if pa > pb, a moves to pa + 1; if pa = pb, a tie-break rule is needed (for example the lower client id goes first), and it must be the same on every site.
Step 2: if b is ins(pb, c) and a is del(pa): if pa < pb unchanged, otherwise a moves to pa + 1.
Step 3: if b is del(pb) and a is ins(pa, d): if pa ≤ pb unchanged, otherwise a moves to pa − 1.
Step 4: if b is del(pb) and a is del(pa): if pa < pb unchanged; if pa > pb, pa − 1; if they are equal, both users deleted the same character and a becomes a no-op.
The client side adds the second half of the protocol. A client may have sent an operation and not yet received the acknowledgement. In the Jupiter and Google Wave designs, the client has at most one operation in flight and buffers the rest, composing them into one pending operation. While it waits, server operations from other users arrive. The client transforms each incoming server operation against its in-flight and buffered operations, and also transforms those against the incoming one. Both sides apply the same transformation pairs, so they reach the same state. Because there are only two parties at each step (client and server), the number of transformation cases stays small. The cost for one operation is about one transform per concurrent operation, so a client that is k revisions behind costs O(k) transforms.
The correctness condition is called TP1. For two concurrent operations a and b that start from the same state S, applying a and then the transformed b must give the same state as applying b and then the transformed a:
\[ S \circ a \circ T(b, a) \;=\; S \circ b \circ T(a, b) \]
This is a "diamond": two paths from the same start that end at one point. Here order theory and proofs enter. Document states reached by different orderings of concurrent operations form a lattice, and TP1 says that the squares of this lattice commute. For client-server OT, TP1 is enough, because the server's total order means that you never need to transform one operation against two sites' views at once. Peer-to-peer OT needs the stronger property TP2 (transformation order independence for three concurrent operations), which is very hard to get right and was the source of most published bugs. Proving TP1 for a given pair of operation types is a case analysis over their combinations, and for richer data (rich text, JSON trees) the number of cases grows, which is why correctness is checked by both proofs and exhaustive or randomized testing.
Causality still matters. The revision number is a simple causal clock: it tells the server exactly which operations the client had seen when it made its edit, so the server transforms against precisely the concurrent ones and not more. In a peer-to-peer system, a Lamport timestamp or a vector clock fills that role. The result is a system with strong eventual consistency: all replicas that have applied the same operations hold the same document, and with a central server they pass through one agreed history.

    |                  |  1 <= 2, so del(3)

  "AXB"                |      transform ins(1,X) vs. del(2):

example: Walk through the diagram above with numbers, then one harder case.
Step 1: start with the text "ABC" at revision 0 on the server and on both clients. Positions start at 0, so A is at 0, B at 1, C at 2.
Step 2: Alice types X between A and B, which is ins(1, "X"). Her screen shows "AXBC" at once. At the same time Bob deletes C, which is del(2). His screen shows "AB". Neither has seen the other's change.
Step 3: the server receives Alice's operation first and it is based on revision 0, which equals the current revision, so no transformation is needed. The document becomes "AXBC" and the revision becomes 1. It is sent to Bob and acknowledged to Alice.
Step 4: the server receives Bob's del(2), based on revision 0. The server is at revision 1, so one operation has happened in between. Transform del(2) against ins(1, "X"): the insert is at position 1, which is not after position 2, so everything at or after 1 shifted right, and the delete becomes del(3). The server applies it to "AXBC", which deletes C and gives "AXB" at revision 2.
Step 5: Alice's client receives del(3) as revision 2. It has no pending operations of its own (her operation was acknowledged), so it applies del(3) to "AXBC" and gets "AXB". Bob's client receives Alice's ins(1, "X") as revision 1. It has one pending operation, del(2), already applied. It transforms the incoming insert against the pending delete: position 1 is before position 2, so it is unchanged. Bob applies it to "AB" and gets "AXB". The third message for Bob is the acknowledgement of his own delete. All three copies show "AXB".
Step 6: a tie case. Both Alice and Bob insert at position 1 of "AB": Alice inserts "X", Bob inserts "Y". The server takes Alice first, giving "AXB". Bob's ins(1, "Y") transforms against ins(1, "X"): positions are equal, so a rule is needed. If the rule is "the operation that arrives later goes to the right", Bob's insert becomes ins(2, "Y") and the result is "AXYB". Bob's own client already shows "AYB". When it receives Alice's insert it must produce "AXYB" as well, so it inserts X at position 1, to the left of its own Y. The tie rule has to be consistent on both sides, or the documents diverge: "AXYB" on one and "AYXB" on the other.
intuition: Operational transformation is like two people editing a printed page by phone: when Bob says "delete the third word", Alice, who has just added a word at the start, translates it to "the fourth word" before she acts.
The design is natural because an edit is relative to the state it was made in. Instead of forcing everyone to wait for the same state (locking), OT lets each person act on their own state and then corrects the meaning of the edit when it travels. The server only has to choose one order. After that, each pair of operations is a small geometry problem: if the two paths in the diamond meet at the same state, any combination of paths does too. This is the commutation of the diamond, and it is why the transformation functions are small even though the number of possible histories is huge.
mistakes: People often think OT sends the whole document or a diff of it. In fact it sends tiny operations such as insert and delete with a position, and the server stores a log of them. This keeps messages small, usually a few dozen bytes, and makes transformation possible, since there are no document snapshots to merge.
People often think OT needs no server. In fact the algorithms that scale in production use a central server for ordering, because that removes the need for TP2. Fully peer-to-peer OT exists but is complex, and its published algorithms had many errors. Without a central coordinator, CRDTs are the usual choice.
People often think OT is a conflict-resolution trick that picks a winner. In fact OT merges both edits: nothing is dropped. The tie rule only decides the order of two inserts at the same place. The only information lost is in cases where two operations are truly contradictory, such as two users changing the same word to different spellings, where one change necessarily comes after the other.
People often think that if the text converges, the result is what the users meant. In fact convergence only means that all replicas are equal. Two users who each fix the same sentence differently can converge to a garbled sentence. Intention preservation works at the level of positions and ranges, not meaning.
friction: Correctness is the hardest part. Every pair of operation types needs a transformation function, so the number of cases grows with the square of the number of operation types. Rich documents have many: insert, delete, format a range, move, split a paragraph, edit a table cell, comment anchors. Each new operation needs transforms against all existing ones, and each must satisfy TP1. Many published algorithms were later proven incorrect, and production teams rely on randomized tests that generate random operation pairs and check convergence.
The server is a bottleneck and a single point of failure for a document. All operations for a document must pass through one ordering point, so a document is sharded by its id, and a failure or a network partition stops collaboration for that document. Offline editing is limited: a client that was offline for an hour has a long list of pending operations, and the server must transform them against everything that happened in the meantime. Transform cost grows with the length of the gap, and merges can produce surprising results.
tradeoffs: Choose OT with a central server when you have a web application with an authoritative backend, mostly online users, and a document model of text or a tree of modest size. The ordering point makes the system simple and gives a single history for audit, permissions and undo. You give up offline editing, peer-to-peer operation and independence from the server.
Choose a CRDT (Yjs, Automerge, Loro) when users edit offline for long periods, devices sync peer-to-peer, or the server should not need to understand the data. A CRDT carries per-item metadata (identifiers, sometimes tombstones), so memory and document size grow, but merging needs no transformation functions and no ordering point. Libraries have narrowed the overhead to a small multiple of the text size, and the cost is a design that must stay compatible with the CRDT's data model.
Choose operation-based sync with a simple rule, such as last-writer-wins per field, when conflicts are rare and structured, like form fields or settings. Choose OT or CRDTs only when many people edit the same text or list at the same time. For these simple cases, transformation is more machinery than the problem needs.
practice: Do not invent your own transformation functions for production data. Use an existing library: ShareDB with its JSON0 or rich-text types, the Quill Delta library for rich text, or a CRDT library such as Yjs if your architecture fits. If you must write transforms, make the operation set as small as possible, define it with the full TP1 checks, and write a randomized test that creates thousands of pairs and sequences of concurrent operations on a few clients, plays them through your server in random orders, and asserts that all documents are equal at the end.
Design the protocol around one operation in flight per client. Tag each operation with the base revision, have the server acknowledge it, and let the client buffer. Make operations idempotent at the transport level (a client retry must not apply twice) using client ids and sequence numbers. Keep the operation log, with periodic snapshots, so that new clients load the latest snapshot and then the later operations.
interview: Explain why applying a delete at position 2 after a concurrent insert at position 1 breaks the document, and how OT fixes it. || The insert moved every later character one place to the right, so position 2 now names a different character. OT transforms the delete against the insert: because the insert is at or before the delete's position, the delete shifts to position 3. The operation then deletes the character its author saw.
Why is a central server such a big simplification? || It supplies a total order, so only two parties (the client and the server) ever need to be reconciled, and TP1 is enough. Peer-to-peer OT must also satisfy TP2 for three or more concurrent operations, which was the source of most incorrect algorithms.
What are TP1 and TP2? || TP1 says that for two concurrent operations a and b, applying a then T(b, a) equals applying b then T(a, b). TP2 says the transformed forms of a third operation c are the same regardless of the order in which a and b were transformed against it. TP2 is needed when there is no single server ordering.
How does the client handle operations while waiting for the server's acknowledgement? || It keeps one operation in flight and buffers further ones, composing them. Incoming server operations are transformed against the in-flight and buffered operations, and those operations are transformed against the incoming one, so the client's local view stays consistent and the next send is based on the latest acknowledged revision.
When would you choose a CRDT instead of OT? || When devices work offline for long periods, when peers sync directly, or when no central server should order operations. I accept metadata overhead and a data model fixed by the CRDT library. With a reliable central backend, OT is smaller in memory and gives a simple history.
How would you test an OT implementation? || Property-based tests: generate random document states and random concurrent operations, check TP1 for every pair, then simulate several clients and a server with random delays and reorderings and assert convergence. Also replay recorded production traces, and fuzz rich-text and structured operations separately.
quiz: What problem does operational transformation solve? || Concurrent edits are made against different document versions, so a position in one operation may point to the wrong place after another operation is applied. OT rewrites the operation so that it keeps its meaning in the new state and all copies converge.
Why does an insert transformed against a concurrent delete before its position move to the left by one? || The delete removed a character before that position, so every later character shifted left by one place; the insert must shift too to land at the same spot in the text.
Why must the tie-break for two inserts at the same position be the same on all sites? || If sites order the two characters differently, one ends with "XY" and the other with "YX", and the documents diverge. A deterministic rule, such as ordering by client id, gives one result everywhere.
A client based its operation on revision 40 and the server is at revision 47. How many transformations does the server do for this operation? || One against each of the 7 operations accepted since revision 40, so 7 transformations.
When is OT the better choice than a CRDT, and what do you give up? || When there is a reliable central server and users are mostly online. You get smaller documents, simple history and easier permissions. You give up offline and peer-to-peer editing and must write and prove transformation functions.
