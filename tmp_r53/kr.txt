value: Knowledge representation (KR) is the part of AI that asks how to write down what is known about the world so that a computer can use it, not only store it. The most common form today is the knowledge graph: facts are stored as triples of the form subject, predicate, object, such as (Bengaluru, locatedIn, India) or (Ada, worksFor, AcmeCo). Entities have types (Person, City), and a layer of rules called an ontology says what the types and relations mean: every Manager is an Employee, every Employee is a Person, and locatedIn is transitive. A reasoner can then derive facts that nobody wrote down, for example that AcmeCo is located in India.
This solves two problems that tables and text handle badly. First, the data is about many kinds of things connected in many ways, and the schema changes often. Adding a new kind of link is adding a new predicate, not altering a table. Second, systems must combine facts from many sources and answer questions that follow from them. A search engine that knows that Mount Everest is a mountain, in Nepal and China, and 8,849 metres high can answer a question directly, not return ten links. A model of the domain, with explicit meaning, is also something humans can read, check and correct.
For the layer above, graph databases store knowledge graphs, either as RDF triple stores or as property graphs, and retrieval-augmented generation increasingly uses a graph extracted from documents (GraphRAG) so that an LLM can follow relations across many documents. The layers below give KR its meaning. Propositional and first-order logic (L4) say what it means for a fact to follow from others; ontologies are fragments of first-order logic called description logics, chosen so that reasoning terminates. Logic programming and Datalog (L3) give a way to apply rules to facts until nothing new appears. Relations and functions (L4) show that a triple is a row in a three-column relation and that a path query is a join. Graph theory (L4) describes the whole as a labelled directed graph, where reachability and transitive closure answer many questions.
terms: Triple — one fact as (subject, predicate, object), such as (Ada, worksFor, AcmeCo).
Knowledge graph — a collection of triples viewed as a labelled directed graph whose nodes are entities and whose edges are relations.
Ontology — a formal description of the types of things and relations in a domain, with axioms such as "Manager is a subclass of Employee".
RDF — the Resource Description Framework, the W3C standard in which every entity and predicate is a global identifier (IRI) and data is a set of triples.
OWL — the Web Ontology Language, a W3C standard for ontologies based on description logics.
SPARQL — the query language for RDF; a query is a graph pattern with variables that is matched against the triples.
Reasoner — a program that derives new facts (entailments) from the stored facts and the ontology.
Open-world assumption — a fact that is not stated is unknown, not false; RDF and OWL reason this way, while databases assume the closed world.
Property graph — a graph model in which nodes and edges can carry key-value properties; used by Neo4j and similar systems.
Entity linking — deciding which entity in the graph a mention in text refers to, such as "Paris" the city or the person.
history: The roots are in the 1960s and 70s. Quillian's semantic networks (1968) drew concepts as nodes and relations as labelled links, with inheritance along "is-a" links. Minsky's frames (1974) grouped the properties of a concept into a record with default values. These were intuitive but had no precise meaning, and different systems gave the same diagram different semantics. Brachman's KL-ONE (1985) separated the structure of concepts from the facts about individuals and gave it a formal meaning, which started the line of description logics. Hayes and others pointed out that these notations could be read as first-order logic, so questions of what follows from what could be answered by logic.
Description logics balanced expressive power against decidability: how much can you say before reasoning becomes impossible or too slow. This work led to OWL (a W3C recommendation in 2004, OWL 2 in 2009). In parallel Lenat's Cyc project (from 1984) tried to hand-write common-sense knowledge, with millions of assertions, and showed both the potential and the cost of manual knowledge engineering. The Semantic Web vision (Berners-Lee, Hendler and Lassila, 2001) proposed putting machine-readable data on the web using RDF (a W3C standard since 1999), RDFS, OWL and, from 2008, the SPARQL query language. The Linked Data principles (Berners-Lee, 2006) simplified the message: give things URIs, make them dereferenceable, link them.
Practical knowledge graphs grew from crowds and from search. DBpedia (2007) extracted structured data from Wikipedia. Freebase (Metaweb, 2007; bought by Google in 2010) was a collaborative graph. In 2012 Google launched its Knowledge Graph under the slogan "things, not strings", and Wikidata started the same year as a shared, multilingual, editable knowledge base that now holds over 100 million items. Schema.org (2011) gave web publishers a shared vocabulary that Google, Microsoft, Yahoo and Yandex read. In machine learning, Bordes and colleagues' TransE (2013) learned vector embeddings of entities and relations to predict missing links. Property-graph databases (Neo4j, from 2007) grew in industry, and the ISO standard graph query language GQL was published in 2024. Since 2024, GraphRAG (Edge and colleagues at Microsoft) uses an LLM to extract entities and relations from documents into a graph, which is then used to answer questions about the whole collection.
how: Start with the data model. A knowledge graph is a set of triples. In RDF, each subject and predicate is an IRI, a global identifier such as `https://www.wikidata.org/entity/Q1355` for Bengaluru, so that data from different sources can be merged by identifier. The object is either another IRI or a literal value (a string, number or date). Because a triple is a row with three columns (this is the relations concept), the whole graph is one table with columns S, P and O, and a query that follows a path is a series of self-joins. Because the same data is a graph (graph theory), each triple is an edge from S to O labelled P, and a path query asks for a walk through the graph.
```text
:Ada      a            :Manager .
:Ada      :worksFor    :AcmeCo .
:AcmeCo   :locatedIn   :Bengaluru .
:Bengaluru :locatedIn  :India .
:Manager  rdfs:subClassOf  :Employee .
:Employee rdfs:subClassOf  :Person .
:locatedIn a owl:TransitiveProperty .
```
Storage turns names into integers. A dictionary maps every IRI and literal to a 64-bit identifier, and triples are stored as three identifiers (24 bytes). Several sorted indexes are kept, such as SPO, POS and OSP, so that any pattern with one or two bound positions is a range scan in one of them. For a graph with one billion triples, each index takes about 24 GB uncompressed, so three indexes take 72 GB before compression, which fits in the memory of a large server. Compression of sorted identifiers typically cuts this by two to four times.
Querying uses graph patterns. A SPARQL query is a set of triple patterns with variables, and the engine finds all bindings of the variables that match triples in the graph, joining the patterns on shared variables. Property paths add navigation: `:worksFor/:locatedIn+` means "works for something, then follow one or more locatedIn links".
```text
SELECT ?person WHERE {
  ?person a :Person ;
          :worksFor/:locatedIn+ :India .
}
```
The query planner chooses a join order using statistics, as in a relational database: it starts from the most selective pattern. This is why a triple store is a specialised relational engine, and why the performance questions (join order, index choice, cardinality estimates) are those of databases.
Reasoning is what separates a knowledge graph from a graph database. The ontology adds axioms, and a reasoner derives entailments. RDFS gives simple rules: if x has type C and C is a subclass of D, then x has type D; if a relation has a declared domain or range, the types of its subject and object follow. OWL adds more: transitive, symmetric and inverse properties, class definitions by restriction ("a Parent is a Person with at least one child"), and disjointness. These can be written as Datalog-style rules, for example `locatedIn(X, Z) :- locatedIn(X, Y), locatedIn(Y, Z)`, and evaluated bottom-up: apply every rule to the current facts, add the new conclusions, and repeat until nothing changes (a fixed point). Semi-naive evaluation, in each round, uses only the facts that were new in the previous round, so work is not repeated. This is the logic programming concept. Materialization stores the derived triples so queries are fast, at a cost in storage and update time. The other approach, query rewriting, expands the query at run time to include the subclasses and subproperties, which keeps the store small and the data fresh.
Logic decides how much can be said. Full first-order logic is undecidable: no program can always decide whether a conclusion follows. Description logics restrict the language so that reasoning terminates. OWL 2 DL is based on the logic SROIQ, with a worst-case reasoning cost that is very high (N2EXPTIME-complete), so OWL 2 also defines profiles: OWL 2 EL (polynomial time, used in large biomedical ontologies such as SNOMED CT), OWL 2 QL (queries rewritten to SQL) and OWL 2 RL (rules that run in a rule engine). Choosing a profile is choosing which reasoning cost you accept. Separately, SHACL (a W3C standard from 2017) validates data against shapes under a closed-world view, because the open-world reasoning of OWL does not report "required field missing" as an error.
Knowledge graphs are built from sources in several ways: mapping databases and spreadsheets to triples, extracting entities and relations from text with NLP or LLMs, and merging records that describe the same entity (entity resolution, then a single identifier). In embedding methods such as TransE, each entity and relation is a vector and a true triple (h, r, t) should satisfy \( h + r \approx t \); the model ranks candidate links, which complements logical reasoning with statistical guesses about missing facts.

example: Use the seven triples shown in the first code block of the "how" section and trace what the system can answer.
Step 1: ask a question with only the stored facts. "Which Persons work for a company in India?" Nothing says Ada is a Person: the data says only that Ada is a Manager. Nothing says AcmeCo is in India either, only that it is in Bengaluru. A table or a plain graph database would return no result.
Step 2: apply the rules, round 1. Rule A: if x has type C and C is a subclass of D, then x has type D. From (Ada type Manager) and (Manager subClassOf Employee) we derive (Ada type Employee). Rule B: transitivity of locatedIn. From (AcmeCo locatedIn Bengaluru) and (Bengaluru locatedIn India) we derive (AcmeCo locatedIn India). Also the subclass chain: (Manager subClassOf Person) by transitivity of subClassOf.
Step 3: round 2. Using only the new facts, Rule A applies to (Ada type Employee) and (Employee subClassOf Person) and derives (Ada type Person). Nothing else is new.
Step 4: round 3 derives nothing new, so we have a fixed point. Four facts were derived from seven. The query now matches: Ada is a Person, Ada worksFor AcmeCo, and AcmeCo locatedIn India, so the answer is Ada. Nobody wrote the fact that makes the answer.
Step 5: size of derived data. Suppose the containment hierarchy is a chain of 1,000 places, each located in the next (street, district, city, region, and so on). There are 999 stored locatedIn edges. With transitivity, every pair (place, an ancestor) is derived: 1,000 × 999 / 2 = 499,500 triples, about 500 times the stored data. In real hierarchies, with depth 6 to 10, the blow-up is a factor of 3 to 5. Materializing helps queries and costs storage. Query rewriting avoids the storage and costs time at query time, with a path query like `locatedIn+`.
intuition: A knowledge graph is a set of index cards, each with one fact, plus a rule book that says what the words mean, so that a clerk can answer questions the cards never mention.
The design is natural because facts about the world are many small statements about things and their relations, and a triple is the smallest unit that holds a relation. Meaning does not live in the cards but in the rules, so separating them lets many people add cards while a few people maintain the rules. Logic is the guarantee: if the cards and the rules are true, every answer that follows from them is true. This is the opposite of a statistical model, which gives a likely answer to anything. A knowledge graph gives a certain answer to what it knows, and says nothing about what it does not.
mistakes: People often think a knowledge graph is just a graph database. In fact a graph database stores and traverses the data. A knowledge graph adds shared meaning: identifiers, types and an ontology with a reasoner or rules, so facts can be derived and merged across sources. You can store a knowledge graph in a graph database, but a graph database without an ontology is not yet a knowledge graph.
People often think the absence of a fact means it is false. In fact RDF and OWL use the open-world assumption: not stated means unknown. Many data problems come from mixing this with SQL's closed world. Constraints such as "every Person has a birth date" must be checked with a validation language like SHACL, not left to OWL reasoning.
People often think a reasoner makes the graph correct. In fact reasoning only passes truth along. A wrong fact or a wrong axiom produces wrong conclusions, often many of them. A mistaken `subClassOf` link between two top-level classes can make thousands of entities share a wrong type.
People often think LLMs make knowledge graphs unnecessary. In fact an LLM gives fluent, probably right text, with no guarantee and no source. A knowledge graph gives exact, auditable facts with provenance, and is cheaper to update. The two are used together: LLMs build and query graphs, and graphs ground LLM answers (GraphRAG, entity linking).
friction: Knowledge acquisition is the oldest problem. Writing facts and rules by hand is slow and expensive, and extracting them from text is error-prone: an extractor with 90% precision on a graph of 100 million triples creates 10 million false facts. Entity resolution (deciding that two records are the same person) is hard, and a false merge is worse than a missed one because it joins unrelated facts.
Schema and ontology design is difficult. Teams disagree on categories, and edge cases are everywhere: is a company a legal entity, a brand or a place of work? Ontologies drift as the business changes, and changing a widely used class breaks consumers. Heavy ontologies are costly to maintain, and many successful graphs (Wikidata, schema.org) use light schemas with human curation.
Reasoning has limits in cost and in what it can say. Expressive description logics have very high worst-case complexity, and even moderate reasoners can be slow on graphs with hundreds of millions of triples. Materialization increases storage and makes deletes hard: when a base fact is removed, you must retract the derived facts that depended only on it, which needs truth maintenance. Logical reasoning also handles uncertainty poorly: facts have confidence, time and source, and RDF has no built-in place for them (RDF-star and named graphs add one).
tradeoffs: Choose an RDF knowledge graph with an ontology when you must integrate many sources with shared identifiers, need inference (hierarchies, equivalences), want open standards for exchange (SPARQL, OWL, SHACL), or publish data for others. Choose a property graph (Neo4j or similar, queried with Cypher or GQL) when the main need is fast traversal and application development, edges need properties without the extra machinery, and inference is not central. You give up built-in semantics and standards-based exchange for developer convenience, and the reverse.
Choose a light ontology (a few dozen classes, subclass and domain/range axioms, validation by SHACL) when you need a shared vocabulary and consistency checks. Choose a rich ontology with a reasoner (OWL 2 EL or RL profiles) only when the domain is stable and derived knowledge is valuable, as in biomedical terminologies. The richer the ontology, the higher the reasoning cost and the maintenance burden.
Choose materialization of inferred triples when reads dominate and the data changes rarely, because queries become simple lookups. Choose query-time reasoning (rewriting) when the data changes often or the closure would be huge. You trade storage and update cost against query latency.
practice: Start from questions. List the 20 questions the graph must answer, then design the minimum set of types and relations that answer them. Reuse existing vocabularies (schema.org, Dublin Core, SKOS for taxonomies, and domain standards such as the IAB content taxonomy in advertising) instead of inventing every term. Give every entity a stable, resolvable identifier that does not encode meaning that can change, and keep a mapping from source identifiers to it.
Treat data quality as engineering. Validate with SHACL shapes in the pipeline, keep provenance (source, date, confidence) on facts, and measure the precision of a sample of extracted triples before loading. Do entity resolution with blocking and scoring, and keep merge decisions reversible. Version the ontology, and make changes additive where you can. Test the reasoning on small examples and include them as regression tests.
For tools, use an RDF store such as Apache Jena Fuseki, GraphDB, Stardog, Virtuoso or Amazon Neptune when you need SPARQL and reasoning, a property graph database when an application needs traversals, and keep heavy analytics in your warehouse or lakehouse, with the graph as a serving layer. For LLM applications, extract entities and relations with a schema, check them against the ontology, store them with the source passage, and retrieve both the neighbourhood and the passage so that answers can cite sources.
interview: What is the difference between a knowledge graph and a graph database? || A graph database is a storage and query engine for nodes and edges. A knowledge graph is a data model with shared identifiers, types and an ontology, so facts can be integrated across sources and new facts inferred. Many knowledge graphs run on graph databases or triple stores, but the semantic layer is the difference.
Explain open-world versus closed-world reasoning with an example. || In a SQL database, a missing row means the fact is false, so "employees without a manager" returns Ada. In RDF/OWL, a missing triple means unknown, so the system cannot conclude that Ada has no manager. You choose by what the application needs, and use SHACL or rules when you need closed-world checks.
How would you evaluate inferred facts, and what can go wrong with materialization? || Test the rules on small known cases, sample derived triples and have people check them, and compare counts before and after to catch explosions. Materialization can multiply storage (a chain of n places gives n(n−1)/2 pairs), and deletions need truth maintenance to remove derived facts that lose their support.
Why is full first-order logic not used for ontologies, and what do description logics change? || First-order entailment is undecidable, so reasoning may never finish. Description logics restrict the constructs so that reasoning is decidable, and the profiles (EL, QL, RL) restrict them further to get polynomial time or SQL rewriting. You trade expressive power for guaranteed termination and speed.
You need to unify customer, device and household data from five systems. Would you use a knowledge graph? || Possibly, if relationships and entity resolution across sources are the core need. I would define the identifiers and a light ontology, do entity resolution with confidence scores and reversible merges, keep provenance, and use the graph as an integration and serving layer next to the warehouse. If the need is mostly aggregation, plain tables are simpler.
How do knowledge graphs help LLM applications, and where do they fall short? || They give structured, verifiable facts and multi-hop relations that retrieval over text misses, and they allow citations. Shortcomings are the cost of building and curating the graph, extraction errors that become false facts, and coverage: what is not in the graph is invisible, so it is combined with passage retrieval.
quiz: What is a triple, and why can a set of triples be seen both as a table and as a graph? || A triple is (subject, predicate, object), one fact. As a table it is a row in a three-column relation; as a graph it is a labelled edge from the subject node to the object node.
What does the open-world assumption mean? || A fact that is not stated is unknown, not false. A system cannot conclude "no" from the absence of data, unlike a SQL database, which treats missing rows as false.
Why do description logics restrict the logic language? || Full first-order logic is undecidable. Restricted description logics make reasoning decidable, and their profiles make it fast enough for large ontologies.
A chain of 2,000 places each located in the next has 1,999 stored edges. How many locatedIn triples exist after materializing the transitive closure? || 2,000 × 1,999 / 2 = 1,999,000 triples, about 1,000 times the stored edges.
When would you choose a property graph over an RDF knowledge graph? || When the main need is application-driven traversal and fast development, with properties on edges and little need for inference or standards-based data exchange.
