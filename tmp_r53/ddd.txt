value: Domain-driven design (DDD) is a way to build software for a complicated business by making the code follow the language and structure of that business. Its most useful idea is the bounded context: a boundary inside which every word has one precise meaning and one model is consistent. The word "campaign" means a signed contract with a budget to the sales team, a set of targeted line items with a delivery schedule to the ad server, and a billable line to the finance system. Trying to build one Campaign class that serves all three produces a huge, fragile model that nobody understands. DDD says: let each context have its own model, and connect the contexts with explicit translations.
The problem DDD addresses is not technical. It is that large systems fail because people do not share a clear understanding of the business, and because every team depends on every other team's data model. A change to one table breaks five services. Developers and domain experts use different words, and the code drifts from what the business actually does. DDD gives a method to find the right boundaries, a shared vocabulary (the ubiquitous language) inside each boundary, and patterns for how contexts relate to each other.
For the layer above, microservices usually draw their service boundaries along bounded contexts, because a context is the unit that can be owned by one team and changed without coordinating with others. Data mesh applies the same idea to analytics: data products are owned by domains, and each publishes data in its own vocabulary as a contract. The layers below supply the reasoning. Software engineering principles (L3) give modularity and information hiding: a module hides its internal decisions behind a small interface, so changes stay local. Reductionism and abstraction (L5) explain why a model must leave things out to be useful, and why one model of everything is impossible. Architectural styles (L2) give the shape of the code inside a context; DDD is usually combined with hexagonal architecture, which keeps the domain model free from databases and frameworks.
terms: Domain — the area of business activity the software serves, such as ad delivery, payments or shipping.
Ubiquitous language — the vocabulary shared by developers and domain experts inside one context, used in conversation, documents and code alike.
Bounded context — the explicit boundary within which a particular model and its language apply consistently.
Subdomain — a part of the business domain: core (the competitive advantage), supporting (needed but not special) or generic (solved the same way by everyone, such as authentication).
Context map — a diagram and description of how bounded contexts relate: who depends on whom, and how they translate.
Aggregate — a cluster of objects treated as one unit for changes, with one root object, inside which the rules (invariants) are always true after each transaction.
Entity and value object — an entity has an identity that persists as its data changes (an order); a value object has no identity and is defined by its values (a money amount).
Domain event — a record that something meaningful happened in the domain, named in the past tense (CampaignBooked).
Anti-corruption layer — a translation layer that stops another context's model from leaking into yours.
history: Eric Evans published "Domain-Driven Design: Tackling Complexity in the Heart of Software" in 2003. He collected patterns from object-oriented projects in which teams had succeeded by keeping a rich model of the business in code. The book's roots are older. Parnas (1972) argued that modules should be divided by design decisions that are likely to change, and hide them. Conway (1968) observed that a system's structure copies the communication structure of the organization that builds it. Fowler's "Analysis Patterns" (1997) and Beck's and Cunningham's early object work on shared metaphors shaped the ideas.
For a decade, DDD was read mostly as a set of object-oriented building blocks: entities, value objects, repositories. The "strategic design" half of the book, with bounded contexts and context maps, was read less. Vaughn Vernon's "Implementing Domain-Driven Design" (2013) gave practical examples and made aggregates and events clearer. Alberto Brandolini introduced Event Storming (2013), a workshop in which experts and developers place domain events on a wall, which became the standard way to discover contexts and aggregates. Martin Fowler's short article on bounded contexts (2014) spread the idea widely.
The rise of microservices (2014 onward) brought DDD to the centre. Teams that split systems by technical layers or by guesses found tight coupling, and bounded contexts offered a rule to split by. Evans has said in later talks that the strategic part, and the bounded context in particular, deserved more emphasis than it got. Cockburn's hexagonal architecture (2005) and its relatives (onion and clean architecture) became the usual way to organize code in a context. Zhamak Dehghani's data mesh (2019) carried domain ownership into analytics. Today DDD is mostly used for its strategic part, and critics note that the tactical patterns are often overused in simple applications.
how: The method starts with language. Developers and domain experts work together, using real examples, until they agree on the terms the business uses. Each term must have one meaning inside a given context, and the code uses the same words: if the business says "book a campaign", the code has a `Campaign.book()` method, not `createRecord`. When the same word keeps meaning two things, that is the signal of a boundary. The word "segment" in an audience-building context means a rule that selects devices; in a measurement context, it means a group for reporting. Forcing one definition would blur both.
A bounded context is that boundary made explicit. Inside it, there is one model, one language, usually one team, and ideally one deployable unit with its own data store. This is information hiding applied to the business: the model is the hidden decision, and other contexts see only a small published interface. Contexts are discovered, not decreed, and they follow the structure of the business and of the organization (Conway's law). They are often found by Event Storming: lay out the events in time order, and notice where the vocabulary or the owner changes.
Subdomains guide investment. The core subdomain is where the company differs from competitors (for an ad platform, perhaps bidding and audience modelling), and it deserves the best people and the richest model. Supporting subdomains (campaign management screens) get simpler solutions. Generic subdomains (identity, email, payments) should be bought or taken from a library. This avoids the common error of spending months building a custom model for something that is not a competitive advantage.
Contexts must relate, and the context map names the relationship. In a customer-supplier relationship, the upstream context publishes what the downstream one needs, and they plan together. A conformist downstream accepts the upstream model as it is, which is cheap but couples the two. An anti-corruption layer lets the downstream keep its own model by translating on the boundary, and is the right choice when the upstream model is poor or foreign (a legacy system, an external vendor). An open-host service with a published language offers a stable, documented protocol for many consumers. A shared kernel is a small piece of model that two teams own together, and it must be kept very small. Separate ways means no integration at all. Integration usually happens through events or APIs, and not through a shared database: a shared database would make the two models one.
Inside a context, tactical patterns shape the model. An aggregate is the unit of consistency. All rules that must hold at the same time (for example "the sum of line budgets does not exceed the campaign budget") are enforced inside one aggregate, in one transaction, through its root. Other aggregates are referenced by identifier only, and changes across aggregates are made eventually consistent, with domain events. The practical rule is: one transaction changes one aggregate. This keeps aggregates small, which keeps lock contention low and makes them fit naturally into a document or a row group.
```python
class Campaign:                      # aggregate root
    def __init__(self, id, budget_cents):
        self.id, self.budget = id, budget_cents
        self.lines = []              # value objects inside
        self.events = []

    def add_line(self, line_id, cents):
        if sum(l.cents for l in self.lines) + cents > self.budget:
            raise ValueError("line budgets exceed campaign budget")
        self.lines.append(Line(line_id, cents))
        self.events.append(LineAdded(self.id, line_id, cents))
```
Domain events are how contexts stay loosely coupled. An event states a fact that already happened, in the language of the context that produced it: `CampaignBooked`, not `UpdateDeliveryTable`. The producer does not know who listens. Each consumer decides what the fact means for its own model, usually through its anti-corruption layer, and updates its own data. Delivery between contexts is at least once, so consumers must handle duplicates by checking an event id.
The domain model is kept free of infrastructure. In hexagonal architecture, the model sits in the centre. It talks to the outside through ports (interfaces such as `CampaignRepository`), and adapters (a SQL implementation, a Kafka publisher, an HTTP controller) are plugged in around it. Domain events recorded by the aggregate are published after the transaction commits, commonly through an outbox table, so other contexts can react. The result is code that reads like the business, a model that can be tested without a database, and boundaries that can become services when the organization needs it.

example: Take an ad platform, which has a clear problem of different meanings.
Step 1: collect the words. In an Event Storming session the team lists events in time order: ContractSigned, CampaignBooked, CreativeApproved, LineItemActivated, ImpressionServed, BudgetExhausted, InvoiceIssued. The experts say "campaign" in every context, but the sales lead means "what the advertiser bought for 500,000 dollars", the ad-ops person means "the 14 line items with targeting and frequency caps", and the finance person means "a line on the monthly invoice".
Step 2: split by language. The team draws three bounded contexts, Sales, Delivery and Billing, and a fourth, Measurement. In Sales, `Campaign` has a signed budget, an advertiser and a period. In Delivery, `Campaign` has line items, targeting and a pacing plan, and it has no price. In Billing, there is `InvoiceLine`, and the word campaign is only a reference.
Step 3: choose the relationships. Sales is upstream and publishes a `CampaignBooked` event with the advertiser id, the total budget in cents, and the dates. Delivery is downstream as a customer: it consumes the event through an anti-corruption layer which translates `total_budget_cents = 50_000_000` into a delivery `Budget` of 500,000 dollars to be paced over 30 days, about 16,667 dollars a day. Delivery never reads the Sales database.
Step 4: set the aggregate boundary. Delivery receives 20,000 impressions per second for one large campaign. If the whole campaign, with its 14 line items, were one aggregate that also held the spent amount, every impression would update the same row and 20,000 transactions a second would collide. So the team makes the spend counter a separate aggregate (a `Pacing` record per line item) updated asynchronously, and keeps the budget rule "line budgets do not exceed the campaign budget" in the small `Campaign` aggregate that changes only a few times a day. The price of this split is that spend is eventually consistent. If a counter is updated every 5 seconds, then at a rate of 20,000 impressions per second the system can overshoot by up to 100,000 impressions before it sees the limit. At a price of 2 dollars per thousand impressions, the potential overspend is 200 dollars, which the business must accept or reduce with a safety margin.
intuition: A bounded context is a country with its own language and its own law, and the context map is the treaty list: inside the border, people understand each other, and at the border, an interpreter translates.
The idea is natural because meaning depends on context in human language too. The same word is not a defect to be removed; it is the way people compress a lot of shared knowledge. Forcing one global definition costs more than translating at the edges. This is also why the structure works for software. A boundary around a consistent model means the model can be understood by one team, changed by one team, and tested without the rest of the company.
mistakes: People often think DDD means microservices. In fact DDD is a way of finding and describing boundaries; it works equally well inside a modular monolith. A bounded context can be a package or a module. It becomes a service only if independent deployment is worth the cost of a network and distributed data.
People often think one bounded context equals one service, or that every service needs its own context. In fact a context may contain several deployable parts, and a service that covers half of a context splits its model. The rule of thumb is: a service should not span contexts, and a context should have one owning team.
People often think DDD is entities, repositories and factories. In fact these tactical patterns are the lesser half. Teams that adopt them without the strategic design produce elaborate class structures around a simple database table.
People often think there should be one canonical enterprise data model that all contexts share. In fact a single shared model forces compromise among teams, and every change needs everyone's agreement. DDD replaces it by several models plus explicit translation, which is more work at the boundary and much less work everywhere else.
friction: The first problem is finding the right boundaries. They are a hypothesis about the business, and the first guess is often wrong. Wrong boundaries are expensive to fix after services, schemas and team structures have grown around them. Boundaries that follow the org chart instead of the domain, or that cut through one strongly consistent workflow, create chatty services that must change together.
DDD needs people. It depends on regular conversations with domain experts, who are usually busy, and on a team willing to learn the business. In organizations where requirements arrive through tickets with no access to experts, the benefits are small. The method also asks for judgment about where to invest: modeling everything richly is waste, and treating the core subdomain as a CRUD form is a mistake.
Integration between contexts brings distributed-system costs. Data is duplicated, because each context keeps its own copy of what it needs, and changes spread by events with delay. Cross-context transactions are no longer possible, so you design sagas or compensation steps and accept eventual consistency. Reports that need data from several contexts need a separate integration layer or a data platform.
tradeoffs: Choose DDD with explicit bounded contexts when the domain is complex, several teams work on it, and the business rules change often: ad delivery, payments, logistics, insurance. Choose a simple layered CRUD design when the rules are few and a small team owns the whole application. The cost of DDD is workshops, modelling time and translation code; the saving appears only if the domain is complicated enough to be worth it.
Choose a modular monolith with context boundaries enforced in code when you have fewer than about 20 to 30 engineers, deployments are not yet a bottleneck, and the boundaries are not yet certain. Choose separate services only when teams need independent release cycles or scaling, and the contexts are stable. You trade the simplicity of local calls and transactions for independence, and a wrong boundary is cheaper to move in a monolith.
Choose a small aggregate with eventual consistency across aggregates when throughput and contention matter (many writers). Choose a larger aggregate when a business rule truly needs strong consistency at once, like a hard budget limit, and writes are rare. The first gives scale and may allow brief violations of a rule; the second gives correctness and a lower write rate.
practice: Start with language and events, not classes. Run an Event Storming session with developers and domain experts, write the events in the past tense on a wall, mark the places where terminology or the responsible group changes, and draw candidate contexts. Write a short glossary for each context and keep it next to the code. Draw a context map with the relationship types, including the political ones: who is upstream, who has the power to change an interface.
Match teams to contexts so that the team structure and the architecture agree. Begin with a modular monolith, with each context in its own module that other modules reach only through a defined interface, and with its own schema or tables. Check dependencies in the build (a static check that fails when module A imports the internals of module B). Move a context to a separate service later, when you have evidence that it needs it.
For integration, publish domain events or stable APIs, not database access. Put an anti-corruption layer in front of legacy systems and vendors. Use the outbox pattern so that an event is recorded in the same transaction as the state change and published afterwards. Version event schemas, and treat them as contracts that consumers can test against. For analytics, publish each context's data as a documented data product rather than letting reports read its tables.
interview: What is a bounded context, and how do you find one? || It is an explicit boundary within which a model and its language are consistent. I look for places where the same word means different things, where different experts or teams own the concept, and where the rules and the rate of change differ, usually through Event Storming and interviews. A context is a hypothesis that I test against how often changes cross it.
Is a bounded context the same as a microservice? || No. A context is a modelling boundary, a service is a deployment boundary. A context can live in a module of a monolith, and a context may be served by more than one deployable. Services should not cross contexts, but contexts need not be services.
How do you decide the size of an aggregate? || I include only the objects that must satisfy an invariant together in one transaction. Smaller is better: it reduces contention, load size and cross-team coupling. Other aggregates are referenced by id, and cross-aggregate rules use events and eventual consistency, accepting possible short violations.
When do you use an anti-corruption layer instead of conforming? || When the upstream model is a poor fit, changes without notice, or comes from a legacy system or a vendor, and my context is core enough that its model must stay clean. When the upstream is a stable standard or my context is minor, conforming is cheaper.
Your teams own services that each need data from one another and release together. What is wrong, and what do you do? || The boundaries probably cut through one context, so the services are coupled by shared concepts. I would map the language and the change patterns, merge the services that always change together into one context (a module or service), and put explicit contracts at the remaining boundaries.
How does DDD relate to data mesh? || Data mesh applies the same domain ownership to analytics: each domain owns and publishes its data as a product in its own vocabulary, with a contract. The bounded contexts give the natural domain boundaries, and translation happens when analysts combine data from several domains.
quiz: What does a bounded context protect? || It protects the consistency of one model and one language. Inside the boundary each term has one meaning; across it, translation is explicit, so models do not leak into each other.
Why should one transaction change only one aggregate? || It keeps aggregates small, which reduces lock contention and coupling, and it makes each aggregate a clear consistency boundary. Consistency across aggregates is reached through events, eventually.
What is the role of the anti-corruption layer? || It translates between another context's model and your own at the boundary, so that a foreign or legacy model does not spread into your domain code and a change upstream affects only the layer.
A counter aggregate is flushed every 5 seconds while 20,000 impressions per second arrive. What is the largest unseen overshoot? || 5 × 20,000 = 100,000 impressions can be served before the limit is seen. At 2 dollars per thousand impressions this is up to 200 dollars.
When would you not use DDD? || For a simple CRUD application with few business rules and one small team, where modelling workshops and translation layers cost more than they return.
