@@ planning
value: Automated planning is the problem of finding a sequence of actions that takes a system from its current state to a state that satisfies a goal. A warehouse robot must decide the order of moves to deliver five items. A spacecraft must schedule observations, turns and data downloads so that power and time limits hold. A software agent must call a series of tools to reach a user's goal. In each case there is a start, a goal, and a set of actions with rules about when each action can be used and what it changes. Planning searches for a path through the space of states that these actions create.
What makes classical planning different from ordinary search is that the problem is described, not coded. You write the actions once in a formal language (PDDL, the Planning Domain Definition Language): each action has preconditions (what must be true to do it) and effects (what it adds and removes). A general-purpose planner then solves any problem written in that language, with no special code. The planner finds this by searching from the start state, guided by a heuristic that it computes automatically from the description, usually by solving a relaxed, easier version of the problem.
For the layer above, AI agents break a goal into steps and tool calls, which is planning in a loose form, and robotics uses task planners to sequence actions before motion planners handle geometry. Space agencies have used planners to operate spacecraft. The layers below make it work. Heuristic search (L3) supplies A* and greedy best-first search over the state graph. Propositional and first-order logic (L4) give the language for states and actions. SAT solvers (L3) offer a second route: write the plan as a logical formula and let the solver find a satisfying assignment. Complexity theory (L3) says how hard this is: classical planning is PSPACE-complete, so no planner is fast on every problem. Constraint satisfaction (L3) handles the scheduling part, such as time windows and resources.
terms: State — a complete description of the world at one moment, written as the set of facts that are true.
Action (operator) — a possible step with preconditions (facts required before) and effects (facts added and facts deleted).
Goal — a set of facts that must hold at the end.
Plan — a sequence of actions that, applied from the start state, gives a state satisfying the goal.
Closed-world assumption — any fact not listed as true is false, so a state is just the list of true facts.
Delete relaxation — a simplified problem in which actions never remove facts, so facts only accumulate; its solution cost is a lower-bound-style guide for the real problem.
Heuristic (h) — an estimate of the number of steps (or cost) still needed from a state to the goal.
Admissible heuristic — one that never overestimates the true remaining cost; A* with such a heuristic returns an optimal plan.
PDDL — the standard text language for describing planning domains (actions) and problems (start and goal), introduced for the planning competitions.
history: Planning began with the Shakey robot at SRI. Fikes and Nilsson (1971) introduced STRIPS, the Stanford Research Institute Problem Solver, in which an action is a precondition list plus an add list and a delete list. This compact form is still the base of nearly all classical planners. In the 1970s and 80s work focused on partial-order planning (do not decide the order of steps that do not interact), and on the frame problem: how to say that most facts stay unchanged after an action without writing it out.
Three changes in the 1990s made planning practical. Blum and Furst's Graphplan (1995) built a layered graph of facts and actions and searched it backward, and was far faster than earlier planners. Kautz and Selman (1992, 1996) showed that planning problems could be translated to SAT and solved with fast SAT solvers. Bonet and Geffner's HSP (1999) and Hoffmann and Nebel's FF (2001) computed heuristics automatically from the delete relaxation and used them in forward search, which changed the field: the planner became a heuristic search engine. Bylander (1994) had meanwhile proved that propositional STRIPS planning is PSPACE-complete.
Standardization followed. McDermott and colleagues defined PDDL (1998) for the first International Planning Competition, and the yearly competitions since then have driven rapid progress. Helmert's Fast Downward (2006) became the reference system, with a translation to multi-valued variables, landmark heuristics and later the LM-cut heuristic (Helmert and Domshlak, 2009). Real deployments include NASA's Remote Agent on Deep Space 1 (1999), the first on-board planner to run a spacecraft, and later mission planning tools for the Mars rovers.
Since 2022 large language models are used for plan-like reasoning in agents. Studies such as Valmeekam and colleagues (2022, 2023) showed that LLMs alone are poor at generating valid plans in classical benchmarks such as Blocksworld, which has led to hybrid designs: an LLM translates a task into PDDL and a classical planner solves it (for example LLM+P, 2023), or a planner or verifier checks the LLM's proposals (Kambhampati's "LLM-Modulo" view, 2024).
how: A planning problem has a domain and an instance. The domain lists the predicates (types of facts) and the actions. The instance gives the objects, the initial state (a set of true facts) and the goal (a set of facts that must be true). Take the standard blocks-world domain with facts `on(x, y)`, `ontable(x)`, `clear(x)`, `holding(x)` and `handempty`. An action such as `stack(x, y)` has the precondition `holding(x)` and `clear(y)`, the add list `on(x, y)`, `clear(x)`, `handempty`, and the delete list `holding(x)`, `clear(y)`. Logic is what makes this precise. A state is the set of facts that are true, with the closed-world assumption that everything else is false. An action is applicable in state s if its preconditions are a subset of s, and the result is the new state \( s' = (s \setminus \text{del}) \cup \text{add} \). The frame problem is solved by a convention: whatever is not mentioned in the effects stays as it was.
Planning is then graph search. States are nodes and applicable actions are edges. A forward planner starts at the initial state, expands applicable actions, and stops when a state contains the goal facts. Breadth-first search finds a shortest plan but explodes. In blocks world with n blocks, the number of states is 1, 3, 13, 73, 501, 4051 for n = 1 … 6, and about 59 million for n = 10. In general the number of states is exponential in the number of facts. Heuristic search (A* or greedy best-first search) is used with a function h(s) that estimates the cost to the goal. A* returns an optimal plan if h is admissible, and greedy search is much faster but gives no optimality guarantee.
The crucial question is where h comes from. In domain-independent planning, it must be computed from the problem description alone. The delete relaxation is the main idea. Remove the delete lists from all actions, so facts are never lost. Now the problem becomes easy to reason about: every action that has become applicable can be applied, and facts only accumulate. Finding some plan in the relaxed problem takes polynomial time. Several heuristics read the answer from it. The FF heuristic extracts an actual relaxed plan and counts its actions. The \( h_{\max} \) heuristic takes the longest chain of dependent facts and is admissible, but weak; \( h_{\text{add}} \) sums the costs of the goal facts and is informative but can overestimate. LM-cut and other landmark-based heuristics find facts that every plan must make true at some time (landmarks), such as "the key must be picked up", and count them. Because a relaxed plan is never longer than a real plan (the optimal relaxed cost \( h^+ \) is a lower bound), these heuristics guide the search well on many problems.
The second route is compilation to SAT. Fix a horizon T, the maximum number of steps. Make a Boolean variable for each fact at each time \( f_t \) and for each action at each time \( a_t \). Write clauses: the initial state holds at time 0; the goal holds at time T; an action at time t implies its preconditions at t and its effects at t + 1; a fact that changes between t and t + 1 must be explained by an action that causes the change (the frame axioms); and mutually exclusive actions cannot both occur. A SAT solver finds a satisfying assignment if a plan of length at most T exists. Then T is increased until a plan is found. This reuses decades of SAT solver engineering, and it is strong for problems that need many parallel steps. Its size grows with the horizon times the number of facts and actions. For 1,000 facts, 5,000 actions and a horizon of 30, there are \( (1000 + 5000) \times 30 = 180{,}000 \) variables before the frame clauses.
Scheduling and resources move planning toward constraint satisfaction. When actions have durations, time windows or shared resources, the problem is written as variables (start times, resource choices) and constraints, and solved by backtracking with propagation. Temporal planners, such as those used for spacecraft, join causal reasoning with such constraint networks.
Complexity explains the limits. Deciding whether a plan exists for a propositional STRIPS problem is PSPACE-complete (Bylander, 1994). Each state is small (polynomial in size), so a search needs only polynomial memory if it forgets visited states, but the number of states is exponential and a shortest plan can be exponentially long: in the Towers of Hanoi with n disks, the shortest plan has \( 2^n - 1 \) moves, so 20 disks need 1,048,575 moves. No planner can output that plan quickly, let alone find it by trying alternatives.

example: Solve a small blocks-world problem by hand. Blocks A and B are on the table, and C is on top of A. The goal is `on(A, B)`.
Step 1: write the start state as facts: `ontable(A)`, `ontable(B)`, `on(C, A)`, `clear(C)`, `clear(B)`, `handempty`. The goal needs `on(A, B)`. The only action that adds `on(A, B)` is `stack(A, B)`, which needs `holding(A)` and `clear(B)`. `clear(B)` is already true. `holding(A)` comes from `pickup(A)`, which needs `clear(A)`, `ontable(A)` and `handempty`. But `clear(A)` is false because C is on A.
Step 2: the relaxed plan, used to compute h. Ignore all delete lists. `unstack(C, A)` needs `on(C, A)`, `clear(C)` and `handempty`, all true. It adds `holding(C)` and `clear(A)`. In the relaxed world `handempty` is still true, since deletions are ignored. Then `pickup(A)` is applicable and adds `holding(A)`. Then `stack(A, B)` is applicable and adds `on(A, B)`. The relaxed plan has 3 actions, so h(start) = 3.
Step 3: the real search. A* expands the start state. Applicable actions are `unstack(C, A)` and `pickup(B)`. Their relaxed costs: after `unstack(C, A)`, the state has `holding(C)` and `clear(A)`, but no `handempty`. Relaxed plan from there: `putdown(C)` (to get `handempty` back), `pickup(A)`, `stack(A, B)`: h = 3, and g = 1, so f = 4. After `pickup(B)`, the hand holds B and A is still covered by C: the relaxed plan needs `putdown(B)`, `unstack(C, A)`, `pickup(A)`, `stack(A, B)`, so h = 4, g = 1, f = 5. A* picks the first (f = 4), and the tie-breaking details do not change the result here.
Step 4: continue. From the state holding C: `putdown(C)` gives g = 2, and h = 2 (`pickup(A)`, `stack(A, B)`), f = 4. Then `pickup(A)` gives g = 3, h = 1, f = 4. Then `stack(A, B)` gives g = 4 and h = 0. The plan has 4 actions and is optimal, because h never exceeded the true remaining cost at any step. The planner expanded 4 states on the plan path and a few side states, not the 13 possible configurations of three blocks, and the saving is far larger on bigger problems.
Step 5: scale. With 10 blocks there are about 59 million states, and a blind search may visit a large part of them. An informative heuristic steers the search toward the goal, so it usually expands only a small fraction. At 20 blocks the number of states is astronomically large, and only heuristic search has a chance.
Step 6: the SAT view of the same problem. With horizon T = 4 the solver gets variables like `holding_C_1` and `unstack_C_A_0`. With T = 3 the formula is unsatisfiable, since no 3-step plan exists. With T = 4 it is satisfiable, and the true assignment gives the same four actions. The solver proves optimality by the failure at T = 3.
intuition: Planning is finding a route on a map you have not seen yet: the actions are the roads, but you only learn the map from the rules, and a heuristic is a rough guess of the distance left, such as the straight-line distance.
The design works because the rules of the world are local and repeated. Each action affects a few facts, and the same few action patterns create an exponentially large map. By describing the actions instead of the states, one planner can solve any domain. The relaxation trick is natural because most of the difficulty of planning is in the interactions among actions (one action destroys what another needs). If you remove interactions, the problem becomes easy, and the cost of the easy problem is a good first estimate of the cost of the hard one.
mistakes: People often think planning is the same as pathfinding on a map. In fact the state graph is not given; it is defined implicitly by rules and is exponentially large. A path planner searches a graph that fits in memory, whereas a task planner must discover relevant parts of a graph with more states than atoms in the universe.
People often think a planner needs a program written for each domain. In fact domain-independent planners take the PDDL description and need nothing else. Domain-specific knowledge (HTN methods, hand-written heuristics) makes them faster, but it is optional.
People often think a better computer will solve any planning problem eventually. In fact the problem is PSPACE-complete, and plans can be exponentially long. What helps is structure: good heuristics, decomposition and pruning. Hardware helps only linearly against exponential growth.
People often think large language models have made planners obsolete. In fact LLMs generate plausible steps, but their plans are often invalid when checked against the preconditions and effects, and they get worse as the plan grows longer. Classical planners are sound, give guarantees (valid and sometimes optimal plans), and can verify an LLM's proposals. The strong designs use the LLM to understand the task and the planner to solve it.
friction: The main limit is the cost of writing a correct model. Someone must define predicates, actions and all their preconditions and effects, and a missing precondition produces plans that are valid in the model and absurd in the world. Models are brittle, and verifying them is as hard as testing a program. Learning models from data, or having an LLM write them and a human review them, is an active area but not solved.
The second limit is scale and expressiveness. Classical planning assumes a fully known, deterministic, static world with instant actions. Real problems have uncertainty (actions with random outcomes), partial observation, time, continuous quantities such as fuel and battery, and other agents. Extensions exist (probabilistic, temporal, numeric planning, POMDPs), and each is much harder to solve than the classical version, so practical systems often relax the problem or add hand-built structure.
tradeoffs: Choose a domain-independent classical planner (Fast Downward and similar) when the world is well understood and discrete, the rules change often, and you want guaranteed valid plans: logistics, assembly sequences, test generation, workflow synthesis. Choose a hand-built scheduler or a mathematical optimizer (integer programming, constraint programming) when the problem is mainly about resources, time and cost with fixed structure, since these exploit numeric structure that PDDL planners handle poorly. You give up the flexibility of declarative actions for performance.
Choose SAT or constraint-based encoding when the plan needs many parallel actions, the horizon is short and bounded, or you want to add arbitrary extra constraints; choose heuristic forward search when plans are long and the horizon is unknown. SAT gives proof of optimality for a given horizon and extensibility; forward search gives speed on most benchmark domains.
Choose satisficing search (greedy best-first with the FF heuristic) when any good plan will do: it often answers in seconds. Choose optimal search (A* with LM-cut) when plan cost is money or risk and the problem is small. The optimal planner can be hundreds of times slower for a plan only a few percent cheaper.
Choose an LLM-based planner for fuzzy, open-ended tasks with no formal model, and add a verifier or a classical planner when errors are costly.
practice: Begin by writing the model carefully. List the objects, predicates and actions. State each precondition explicitly and check effects, especially deletes. Test the model on tiny problems by hand before scaling up. Use a validator (such as VAL) to check that plans are valid, and use several planners on the same model, as a bug in the model usually appears as a surprising plan.
Use an existing planner and not your own: Fast Downward is the standard open-source system with many heuristics and search algorithms, and the International Planning Competition benchmarks provide test domains. For a first run, use a satisficing configuration (a lazy greedy search with the FF heuristic and preferred operators). If you need quality, use an anytime configuration that finds a fast plan and then improves it. For scheduling with time and resources, consider a CP-SAT or similar constraint solver.
For LLM agents, separate the roles. Let the LLM translate the user request to a structured goal (or to PDDL), let a symbolic planner or a checker generate or verify the plan, and execute step by step with checks on preconditions before each tool call. Log the state after each action, and re-plan when an observation differs from the expected effect. Limit plan length, as errors accumulate over steps.
interview: Describe a planning problem formally. What is a state, an action, and how is an action applied? || A state is a set of true facts under the closed-world assumption. An action has preconditions, an add list and a delete list. It is applicable when its preconditions are a subset of the state, and applying it gives (state minus delete list) plus add list. A plan is a sequence of actions that leads from the initial state to one containing the goal.
What is the delete relaxation, and why does it produce a useful heuristic? || Remove all delete effects, so facts only accumulate. Finding a plan then takes polynomial time, and its length estimates the remaining work of the real problem. Optimal relaxed cost never exceeds the true cost, so it is a lower bound; practical heuristics such as FF use a non-optimal relaxed plan, which is informative but not always admissible.
Why is classical planning hard, and what does PSPACE-complete tell you? || The state space is exponential in the number of facts, and plans can be exponentially long (Towers of Hanoi needs 2^n − 1 moves). PSPACE-completeness means there is no known polynomial algorithm, and planners succeed through heuristics and structure, not worst-case guarantees.
When would you compile planning to SAT instead of using heuristic search? || When the plan length is short and bounded, when many actions can occur in parallel, or when I need to add side constraints. SAT solvers prove that no plan of length T exists, but the formula grows with the horizon, so it is poor when plans are hundreds of steps long.
How would you use an LLM in an agent that has to produce correct multi-step plans? || The LLM interprets the request and proposes a plan or a PDDL model. A verifier or a symbolic planner checks preconditions and effects, rejects invalid steps and returns feedback, and execution is monitored with re-planning. This uses the LLM for flexibility and the planner for guarantees.
Your planner returns a plan that is valid in the model but wrong in reality. Where is the bug? || Most likely in the model: a missing precondition or effect, or an assumption such as a deterministic action. I would replay the plan against the real system or a simulator, find the first step where the real state differs from the model state, and fix the action definition.
quiz: What are the three parts of a STRIPS action? || Preconditions (facts needed to apply it), an add list (facts that become true) and a delete list (facts that become false).
What does the delete relaxation remove, and why does that make the problem easier? || It removes the delete effects of all actions. Facts then never disappear, so there are no harmful interactions between actions, and a relaxed plan can be found in polynomial time.
Why can plans be exponentially long even for simple domains? || Some problems force many repeated moves. In the Towers of Hanoi with n disks the shortest plan has \( 2^n - 1 \) moves, which is already over a million for 20 disks.
In the SAT encoding, a problem has 400 facts and 900 actions and a plan horizon of 25. How many variables are there for facts and actions? || (400 + 900) × 25 = 32,500 variables, before the frame and exclusion clauses are added.
When would you choose optimal A* search over greedy search? || When plan cost matters more than planning time and the problem is small enough to solve exactly. Otherwise greedy search with the FF heuristic usually finds a good plan in a small fraction of the time.
